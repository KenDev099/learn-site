階段 2：面試實戰 · 第 4 課

行為面試：STAR 與故事庫

技術面試考你會不會做，行為面試考你過去實際怎麼做：和 PM 意見不合時怎麼辦、自己造成事故後做了什麼、沒人負責的問題有沒有主動接。這一關不寫程式，很多工程師因此不準備，臨場講出一段三分鐘的背景介紹、一堆「我們」、沒有結果的故事。資深職缺常常就在這一關分出高下。

這一課教你把工作經驗整理成可以重複使用的故事，聽出題目在問什麼，選對故事回答。

這課的路線：
  1. 為什麼問「你上次怎麼做」與開場題：面試官在故事裡聽哪幾件事；自我介紹、為什麼離職、為什麼轉後端怎麼誠實回答。
  2. STAR：把一件事講成兩三分鐘，行動段落講「我」做了什麼，結果有數字。
  3. 題目背後的能力與故事庫：聽出題目在問六種能力的哪一種，事先準備 6～8 個故事涵蓋全部，被追問也接得住。
  4. 失敗與衝突怎麼講：最容易答壞的兩類題，怎麼說清楚自己的責任、怎麼講分歧而不貶低對方。
  5. 資深視角：故事的範圍更大，也敢說自己錯了。
這課會用到：
  • 第 2 課的影響力句子（動作＋範圍＋結果）：履歷上的每一條都可能被追問成一個故事，句子裡的數字就是故事的結果。

為什麼問「你上次怎麼做」

行為面試（behavioral interview）問的是你過去的行為，背後的假設是：一個人過去在類似情境怎麼做，最能預測他未來會怎麼做。比較兩種問法：

問法例子面試官拿到什麼
假設題如果 PM 要你週五前上線一個做不完的功能，你會怎麼做？每個人都答得出標準答案：「我會溝通、評估風險、提出替代方案」。分不出誰真的做過
行為題說一次 PM 要你在做不完的期限前上線的經驗。你當時怎麼做？具體的人、時間、數字、你的選擇。有細節就能追問，追問三層還答得出來，多半是真的

面試官在聽的是三件事：你做了什麼（不是團隊）、你為什麼這樣做（判斷）、結果怎麼樣、你學到什麼。每家公司想評估的特質叫能力（competency），例如主導、影響力、處理衝突。公司會把能力清單發給面試官，每位面試官負責問其中幾項，面完依你的故事打分數。

這也是為什麼這一關要事先準備：臨場想故事，你會想到最近的事，而不是最能證明那項能力的事。

開場題：自我介紹、為什麼離職、為什麼轉後端

台灣幾乎每一場面試都從「請先自我介紹」開始。自我介紹（self-introduction，英文面試常問 Tell me about yourself）不是念履歷，而是用 1～2 分鐘決定面試官接下來想問什麼。分三段：

  1. 現在：你的定位與技術棧，一句話。
  2. 證據：1～2 個有數字的成果，直接用第 2 課寫好的影響力句子。挑你最想被追問、也最有把握的。
  3. 未來：為什麼是這家公司、這個職缺。要具體到這個職缺，不能每家都通用。

一個前端轉後端的版本（大約 1 分 15 秒）：

我是前端工程師，4 年經驗，主要用 Vue 3 和 TypeScript 做咖啡連鎖的點餐網站。這一年我開始往後端走：工作上我和後端一起訂 API 規格，結帳頁一次重複送出的事故讓我開始研究冪等；下班後我完成了一套後端課程，做了一個 NestJS 的訂單 API 作品，有 64 個自動化測試，壓測下建立訂單的 p95 是 140 ms，也用 Docker 部署、做過零停機上線。我應徵這個全端職缺，是因為你們的團隊前後端一起做，我的前端經驗馬上用得上，後端是我接下來兩年想專注的方向；前端的經驗也讓我知道 API 怎麼設計，前端用起來比較順。

p95 延遲是 100 個請求裡第 95 慢的那個花了多久（系統設計課第 3 課），比平均值更能反映尖峰時顧客的感受。注意這段話替面試官準備好了題目：「重複送出那次怎麼處理的？」「作品的測試怎麼寫？」這些都是你準備好的故事。流水帳從大學科系講起、照念履歷，都是把這個機會浪費掉。

另外兩題幾乎一定會出現：

  • 「為什麼想離開現在的公司？」講你想要什麼，不批評前公司或前主管。「我想做更多後端與系統的工作，現在的團隊這部分由另一組負責」比「主管很難溝通」好：前者讓面試官判斷這個職缺給不給得起，後者讓他擔心你下次也會這樣講他們。真的是因為薪水或加班，可以說「我希望工作量能長期維持」，不需要編理由，也不需要細說。
  • 「為什麼從前端轉後端？」用做過的事回答，不用形容詞。「我一直對後端有興趣」沒有證據；「我在工作上追過一次結帳頁重複送出的事故，下班後在 Learn 完成 NestJS 與部署的期末專題，發現我更喜歡處理資料一致性和效能問題」有證據，也替你開出下一個話題。前端經驗是優勢，不需要道歉：你知道 API 被怎麼用、哪些錯誤訊息前端接不住。怎麼把前端經驗翻譯成後端的說法，見第 1 課的「轉職定位」。

投外商時，面試可能部分或全部用英文。自我介紹、離職理由和兩三個主要故事先寫好英文版並念出聲練習；用英文講不熟的故事，最先掉的是細節和數字。

STAR：把一件事講成兩三分鐘

STAR 是回答行為題的常見格式，Amazon 官方的面試準備頁就建議應徵者用 STAR 回答行為題，並把例子對應到它的領導準則（Leadership Principles）。它把一個故事分成四段：

  • S（Situation，情境）：發生什麼事，一兩句，只講聽懂故事需要的背景。
  • T（Task，任務）：你在這件事裡的責任是什麼。這一句區分「我是值班工程師，要止血」和「我是旁邊看的人」。
  • A（Action，行動）：你具體做了什麼、為什麼這樣做。這是面試官打分數的主要依據，要佔一半以上的時間，主詞是「我」。
  • R（Result，結果）：改變了什麼，最好有數字。最後補一句學到什麼或之後改了什麼，這句常常是資深與否的分界。

用一個咖啡店的事故示範。先看面試現場常聽到的爛版本：

那時候我們公司在做咖啡連鎖的點餐系統，有 5 家分店，用的是 NestJS 和 PostgreSQL，金流串第三方……（背景再講 1 分半）……後來有一天尖峰時段出了問題，我們先看 log，我們發現是重試造成的，我們就修好了。後來就上線了，大家都很開心。

問題有三個：背景佔了大半；行動全是「我們」，面試官不知道你做了哪一件；結果停在「修好了」，沒有改變了什麼。同一件事的 STAR 版本：

段落內容
S週六早餐尖峰，付款閘道變慢，訂單服務逾時後自動重試，部分顧客被扣了兩次。
T我是訂單服務的開發者，也是當天的值班工程師，要止血、退款，並防止再發生。
A我先暫停付款的自動重試，讓重複扣款不再增加。接著寫退款腳本，用金流的對帳檔比對訂單，退回 37 筆重複扣款。根本原因是重試時沒有辨識「同一筆付款」，所以我在付款 API 加上冪等鍵（系統設計課第 9 課），同一筆訂單重試只會扣一次；再加上重複扣款率的告警，超過 0.1% 就通知值班。最後我寫了事後檢討，把「重試前先查詢付款狀態」加進上線檢查清單。
R之後 3 個月，尖峰重複扣款率從 1.2% 降到 0；37 位顧客都在 4 小時內收到退款。我學到重試一定要搭配冪等鍵，而且外部服務變慢時要先止血，再查原因。

💡 實務上：事後檢討就是現成的 STAR 草稿
咖啡店後台出過事故，團隊通常會寫事後檢討（postmortem）：時間線、影響、根本原因、改善項目。它的段落幾乎直接對應 S、A、R，你只要補上 T（你當時的角色）並把「團隊」改寫成你負責的那幾步。寫的時候小心兩件事：檢討文件裡的內部系統名稱、顧客資料不能講出去；數字只講你確定、量得到的。資深工程師會在事故結束、記憶還清楚時就順手寫好自己的故事卡，而不是等到要面試才回想。

題目背後在問哪一種能力

行為題的說法很多，但背後常見的能力就幾種。這一課選六種最常見的（每家公司的清單不同，Amazon 有自己的 Leadership Principles，其他公司會列在職缺或招募頁上；面試前去找，找不到就問 HR）：

能力常見問法面試官想看什麼
衝突（conflict）說一次你和同事意見不合的經驗你怎麼理解對方的理由、用什麼資料取得共識；不是誰贏
失敗（failure）說一次你搞砸的事你承認自己的責任、怎麼補救、之後改了什麼流程
主導（ownership）有沒有一件沒有人負責、你主動接下來的事？沒人指派但需要有人做的事，你有沒有接起來做到完
影響力（influence）你怎麼說服團隊採用你的提案？不是主管，也能讓別人改變做法：證據、試點、降低對方的成本
模糊（ambiguity）需求不清楚的時候你怎麼開始？你怎麼把模糊的目標變成可以開工、可以驗收的範圍
帶人（mentoring）你怎麼帶新人？你怎麼讓別人變強，而不是自己把事情做完

兩個名詞要先說清楚。主導（ownership）是把事情當成自己的責任做到完，包括沒人指派、但需要有人做的事，例如大家都抱怨卻沒人修的慢 API。沒有職權的影響力（influence without authority）是你不是對方的主管，卻能讓對方採用你的提案，例如讓整個團隊開始寫測試。

同一題可能同時碰到兩種能力。「說一次你和主管衝突、後來發現自己做錯的經驗」既是衝突也是失敗，這時先答題目的主軸（衝突），再在結果與學到的地方帶出失敗的部分。

故事庫：6～8 個故事涵蓋所有能力

一場行為面試通常問 4～6 題，同一天的幾位面試官還可能問到相似的能力。只準備一兩個故事，第三題就只能臨場想。故事庫（story bank）是你事先整理好、可以重複使用的工作故事清單，用一張表確認每種能力都有故事：

故事衝突失敗主導影響力模糊帶人
尖峰重複扣款✓✓
和 PM 談週年慶的範圍✓✓
說服團隊在結帳模組寫測試✓
沒人管的慢菜單 API✓✓
沒有規格的會員制度✓
帶兩位新人遷移訂單服務✓

幾個整理原則：

  • 一個故事可以從不同角度講。重複扣款的故事，被問失敗時強調「重試沒加冪等鍵是我寫的」；被問主導時強調「事後我把檢查清單補起來」。行動段落挑不同的句子講，事實不變。
  • 但不要什麼都標。一個故事標了四五種能力，通常代表你沒想清楚它最能證明什麼。每個故事標 1～3 種，選最強的。
  • 素材從哪裡來。第 2 課的履歷句子（每一條都是一個故事的 R）、事故與事後檢討（系統設計課第 21 課、DevOps 課第 25 課，是失敗與主導故事最常見的素材）、時程延誤時的範圍協商與升級（工程實務課第 4 課，衝突與影響力故事的素材）、專案回顧、第 1 課建議的面試紀錄。資深之後每週寫成果紀錄，第 9 課會教。
  • 工作經驗不夠的能力。例如還沒帶過人，可以用 Learn 期末專題、社群活動、帶同學做專題的經驗，講清楚背景：「這是我的學習專案」。不要把別人的經驗講成自己的，追問三層就露餡。
  • 每個故事寫成同樣的結構：S、T、A（3～6 句）、R（數字）、學到什麼，以及下面的三個追問。寫成結構化資料，練習 1～4 就能用程式檢查。

每個故事準備三個追問

面試官聽完故事會追問（follow-up，也叫 probing）：確認故事是真的、確認你的角色、看你的判斷有多深。常見的追問：

  • 「你具體做了哪一部分？其他人做了什麼？」
  • 「為什麼選這個做法？當時考慮過什麼替代方案？」
  • 「你怎麼知道成功了？數字怎麼量的？」
  • 「當時其他人怎麼想？有人反對嗎？」
  • 「如果重來一次，你會怎麼做？」

每個故事寫下三個你預期會被追問的問題，並準備好答案。以重複扣款為例：「為什麼先暫停重試而不是直接修？」（先止血：每多一分鐘就多幾筆重複扣款）、「37 筆是怎麼算出來的？」（用金流對帳檔比對同一訂單的成功扣款數）、「重來你會怎麼做？」（上線前就要求付款相關的重試都有冪等鍵，並在 code review 檢查）。答不出追問的故事，比沒有故事還傷。

💡 實務上：面試官手上有一張評分表
很多公司的面試官面完要填一張表：每項能力打分，並寫下支持分數的具體證據，例如「他自己寫了退款腳本、用對帳檔驗證」。追問就是在收集這些證據，所以答追問時給事實（做了什麼、數字、當時的選項），不要給形容詞（「我很負責」）。如果真的不記得某個細節，直接說「這個數字我不確定，大約是…」，比編一個精確數字安全：被追問到矛盾，整個故事的可信度都會被打折。

失敗與衝突怎麼講

這兩類題目最容易答壞，因為人的本能是保護自己。

失敗題：選一個真的失敗、而且是你的責任。「我太追求完美」「我太投入工作」這種偽裝成優點的缺點，面試官一聽就知道你在迴避。好的失敗故事有三個部分：發生了什麼（你的責任說清楚）、你怎麼補救、之後改了什麼，例如加了測試、告警、檢查清單，或改了估工方式。改了什麼比錯了什麼重要，這代表同樣的錯不會再犯。不要選造成重大損失卻沒有改進的事，也不要選小到不算失敗的事。

衝突題：說一個真實的分歧，不貶低對方。結構是：雙方各自的理由（對方的理由要講得合理，不然聽起來像你沒理解）、你怎麼了解對方真正在意什麼、用什麼資料或小實驗取得共識、結果。「後來主管支持我」不是解決分歧，是把決定交給別人。

有時候討論完還是沒有共識，團隊做了你不同意的決定。這時常見的做法叫 disagree and commit（不同意，但全力執行）：你清楚說出反對理由和風險，決定一旦做出就全力把它做好，不在背後扯後腿。能講出一個「我不同意、但照決定做，並且做好了」的故事，是成熟的訊號；能講出「後來證明我錯了」的更好。

💡 實務上：衝突故事裡的對方，可能就是面試官的同事
台灣的業界圈子小，你描述的 PM、主管或另一個團隊，面試官可能認識，背景調查（reference check）也可能打給他們。所以衝突故事只講事實與雙方的理由，不提名字、不下評語。選故事時優先選「後來關係變好」或「事後證明對方有道理」的，這種結尾最能看出你處理分歧的能力，也最不怕被查證。

資深視角：範圍更大，也敢說自己錯了

同樣是行為面試，資深職缺的故事要多三樣東西：

  • 範圍：不只是你自己的任務，而是影響一個團隊或跨團隊。「我修了一個 bug」是初階的故事；「我發現同類事故一季發生三次，推動團隊在所有付款相關的重試加上冪等鍵與 code review 檢查」是資深的故事。
  • 取捨：說出你放棄了什麼、為什麼。「我們先上線集點、延後兌換，因為兌換牽涉金額，需要完整測試」比「我們如期上線」更能看出判斷。
  • 讓別人成功：帶新人、讓團隊採用新做法、讓另一個團隊願意配合。資深的成果常常是透過別人達成的。

還有一點常被忽略：資深面試官會刻意問「你什麼時候改變過想法？」「什麼時候發現自己錯了？」。能具體說出你被資料或同事說服的經驗，代表你做決定是看證據，不是看面子。

練習

四題用同一組型別：能力（Competency）用字面值聯合表示（TypeScript 課第 15 課：值只能是列出的其中一個字串），字數一律用 [...text].length 算（TypeScript 課第 6 課），故事（Story）照 STAR 分欄。程式只檢查結構和可以機器判斷的規則，不評你的文字寫得好不好；寫得好不好，留給離開頁面後的模擬面試。

練習 1：寫 checkStory(s)，檢查一個故事，依規則回傳問題清單。規則寫在起始程式的註解裡。注意「我們」裡也有「我」、只有空白的字串也算空白、字數用 [...text].length 算。

練習 2：起始程式有一段面試錄音整理出來的爛故事，以及那次事件的事實表。用事實表把它重寫成 fixed。要求：checkStory(fixed) 回傳空陣列；competencies 只標這個故事真的證明得了的能力（看事實表：事故是誰的責任、誰接起來處理到完）；actions 3～6 句，至少 3 句的主詞是「我」，至少 3 句各自對得上事實表裡你做的一件事，合起來至少用到 keywords 裡的 3 個詞（每句可以用自己的話寫）；result.metric 照事實表；result.text 裡的數字只能是事實表 outcome 出現過的數字。

練習 3：寫 buildCoverage(stories, required)，算出故事庫的覆蓋情況。covered 要有全部 6 種能力當 key，值是能回答該能力、而且 checkStory 沒有問題的故事 id（依故事的原順序；沒有故事就是空陣列）；gaps 是 required 裡沒有任何故事的能力（依 required 的順序）；overused 是標了 4 種以上能力的故事 id（不管有沒有問題，依原順序）。

練習 4：寫 pickStory(question, stories)：面試官問了一題，從故事庫挑一個故事。先用 KEYWORDS 把題目分類到一種能力：依表的順序，第一個有任何關鍵詞出現在題目裡的能力就是答案（題目同時碰到兩種能力時，取表裡較前面的）。再從涵蓋這個能力、checkStory 沒有問題的故事中，選能力數最少（最聚焦）的；一樣少就取原順序的第一個。分類不到能力或沒有合適的故事，回傳 null。

練習 5：面試官問「說一次你和同事意見不合的經驗」。哪個回答方向最好？

✓ b：面試官想看你怎麼處理分歧，對方的理由講得合理、你用證據取得共識，才看得出這個能力。a 否認衝突，聽起來不真實，也沒有故事可以評分；c 貶低對方，讓面試官擔心你怎麼跟他們的團隊相處；d 把決定交給主管，沒有展示你自己解決分歧。

練習 6：一個 STAR 故事裡，哪一段應該佔最多時間？

✓ a：面試官評分的依據是你的行為與判斷，所以行動要佔一半以上。b 背景只要夠聽懂就好，講太久行動就只剩幾句；c 結果要有數字，但一兩句就夠，反覆強調沒有新資訊；d 平均分配等於把一半時間花在背景和結果上。

練習 7：面試官問「說一次你的失敗」。下面哪個回答最不好？

✓ d 最不好：這是偽裝成優點的缺點，迴避了題目，面試官一聽就知道。a、b、c 都是真的失敗、說得出自己的責任，而且有之後的改變；改了什麼，正是失敗題要看的東西。

練習 8：面試開場「請先自我介紹」。哪個做法最好？

✓ c：自我介紹決定面試官接下來問什麼，放進你最想被追問的成果，等於自己出題。a 的流水帳和 b 照念履歷都在重複面試官手上已經有的資料，而且花太多時間；d 太短，把整場面試的方向交給對方。

離開頁面要做的事

  • 寫出你的自我介紹（中文，投外商再加英文版），用手機計時念出來，控制在 1～2 分鐘。
  • 從第 2 課的履歷句子和第 1 課的面試紀錄找素材，寫出 6～8 個故事，每個照 STAR 分欄、寫上能力和三個預期追問。用練習 1 和練習 3 的程式檢查結構與缺口。
  • 每個故事念出來錄音，聽一次：背景有沒有超過 30 秒？行動是不是「我」？結果有沒有數字？
  • 找朋友或同事模擬一次，請對方每個故事至少追問兩層。答不出來的地方補進故事卡。
  • 你的真實故事會提到公司、同事和客戶，存在私人的地方，不要放到公開的 repo 或網站上。

常見錯誤

  • 全是「我們」：面試官要評估的是你。團隊做的說清楚分工，你做的用「我」。
  • 背景太長：前兩分鐘都在講公司和系統，行動只剩幾句。情境一兩句，夠聽懂就好。
  • 沒有結果：故事停在「後來就上線了」。說出改變了什麼，最好有數字，再補一句學到什麼。
  • 只準備一個故事：一場行為面試會問 4～6 題。準備 6～8 個故事，涵蓋六種能力。
  • 一個故事標所有能力：什麼都能答的故事，通常什麼都證明得不夠強。每個故事標 1～3 種。
  • 背稿：記重點與數字，不要逐字背，被追問打斷才接得回去。
  • 失敗題講假缺點、衝突題貶低對方：選真的失敗並說出之後的改變；衝突題把對方的理由講得合理，重點放在怎麼取得共識。
  • 批評前公司：「為什麼離職」講你想要什麼，不講前公司哪裡不好。

小結

  • 行為面試問過去的行為，因為具體的經驗可以追問、可以驗證；面試官在找你做了什麼、為什麼、結果與學到什麼。
  • 自我介紹分現在、證據、未來三段，1～2 分鐘；「為什麼離職」講想要什麼，「為什麼轉後端」用做過的事回答。
  • STAR：情境一兩句、任務說清楚你的責任、行動佔一半以上而且主詞是「我」、結果有數字，最後補一句學到什麼。
  • 常見能力有衝突、失敗、主導、影響力、模糊、帶人；先聽出題目在問哪一種，再挑最聚焦的故事。
  • 故事庫 6～8 個故事，每個標 1～3 種能力，每種能力至少一個故事，並為每個故事準備三個追問。
  • 失敗題講真的失敗與之後的改變；衝突題不貶低對方，講怎麼取得共識，或怎麼 disagree and commit。
  • 資深的故事範圍更大、說得出取捨、透過別人達成，也講得出自己改變想法的時候。
