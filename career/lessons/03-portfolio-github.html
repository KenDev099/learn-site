階段 1：看懂流程，準備材料 · 第 3 課

作品集與 GitHub：把期末專題變成看得懂的作品

從前端轉後端，履歷上的後端工作經歷通常不多。這時作品集（portfolio）就是你的證據：一組公開的作品，讓面試官不用相信你的說法，自己點進去就能驗證你做得出來。但只把程式碼推上 GitHub 不夠：面試官不會花一小時讀你的程式，他會花幾分鐘看 README，跑不起來、看不懂就關掉。

這一課教你把 Learn 的期末專題整理成「別人 5 分鐘看得懂、10 分鐘跑得起來」的作品。

這課的路線：
  1. 面試官怎麼看作品、選哪幾個：他只花幾分鐘、照什麼順序看，所以要挑 2～3 個撐得住 30 分鐘追問的專案。
  2. 把期末專題改成作品：每個學員都做了一樣的東西，怎麼加上你自己的變化、真實的數字與角色說明。
  3. README 骨架：問題、角色、架構圖、怎麼執行與測試、設計決定、已知限制，依讀者需要的順序排。
  4. 公開前檢查與 GitHub 個人頁：repo 設成 public 前要找出哪些機密與個資，個人頁 README 和釘選放什麼。
  5. 資深視角：作品要展示判斷，每個設計決定都配上考慮過的替代方案。
這課會用到：
  • 第 2 課的影響力句子（動作＋範圍＋結果，結果要有數字）與身分證字號的正規表示式：README 的成果用同樣的寫法，練習的公開前檢查沿用那條比對規則。

選哪幾個專案

作品集不是越多越好。面試官的時間只夠深入看一兩個，面試時也會挑一個追問 20～30 分鐘：「為什麼這樣設計？」「如果訂單量變 10 倍呢？」「這個測試在擋什麼？」20 個跟著教學做的 TODO app，每一個都撐不過這種追問；2～3 個你真的想過每個決定的專案才撐得住。

選的方法是對照目標職缺（第 1 課讀 JD 的方法）：

目標職缺建議放的作品證明什麼
後端工程師NestJS 期末專題＋DevOps 期末專題寫得出有交易、快取、佇列、測試的 API，也送得上線、維運得了
全端工程師上面兩個＋Vue 期末專題前後端都做得到，而且懂兩邊怎麼接
資深後端NestJS＋DevOps 專題，加上系統設計期末專題的設計文件除了寫程式，也做得出取捨、寫得出別人能審查的設計

你在前端累積的作品不用刪，但不要讓它們擠掉後端作品的釘選位置（後面「GitHub 個人頁」會講釘選）。

💡 實務上：面試前一天，重讀你要被追問的那個專案
技術面試常見的開場是「挑一個你最有把握的專案講講看」，接著面試官就順著你說的追問。專案做完幾個月後，很多細節會忘記，所以面試前一天把 README 的設計決定逐條講出聲：決定是什麼、考慮過什麼、為什麼不選它、現在回頭看會不會改。答不出來的那條，要嘛補功課，要嘛從 README 拿掉。寫在 README 上卻說不清楚，比沒寫更扣分。

把期末專題改成作品

主力作品建議用作品專案課的多租戶 SaaS 後台：業務題目是你自選的，本來就跟別人不一樣，包裝方式見它的第 19 課。各課的期末專題適合當第二、第三個作品，但要先改造。

期末專題有一個問題：每個學 Learn 的人都做了一樣的東西。直接推上去，面試官看到的是「照著課程做完」，看不出你的判斷。要把它變成你的作品，做三件事：

  1. 加上你自己的變化：一個課程沒要求的功能（例如訂單完成時用 BullMQ 寄收據信，NestJS 課第 20 課的佇列），或換一種做法（例如把部署從 DevOps 課第 10 課的 Docker Compose 換成別的平台），並寫下為什麼。面試時最好聊的就是這部分，因為只有你做過。
  2. 放真實的數字：測試數、壓測的 p95 延遲（把所有請求依花費時間排序，第 95% 的那個花多久；系統設計課第 3 課）、從 clone 到能跑的時間。第 2 課說過，沒有營收數字時，工程數字就是你的結果；每個數字都寫出怎麼量的，別人才能重現。
  3. 標明這是學習專案與你的角色：「Learn NestJS 課期末專題，獨力完成；收據信與菜單快取是我自己加的延伸」。沒標明的話，面試官問「有多少使用者？」你只能尷尬地說沒有；標明了，對話會轉向你做了哪些延伸、遇到什麼問題。
不要把在公司寫的程式碼放進作品集，即使是你寫的、即使拿掉了公司名稱。受僱期間寫的程式碼權利通常屬於公司，很多公司也會要你簽保密協議（NDA，non-disclosure agreement：約定你不能公開公司的資訊）。放上去可能違約，面試官看到也會懷疑你會不會把他們的程式碼帶走。想展示在公司做過的事，改成在 README 或面試裡描述做法，或用咖啡店專案重現相同的概念。

README 骨架

作品 README 依讀者的順序排：先讓人知道這是什麼，再讓人跑起來，最後才是細節。下面是一個咖啡店訂單 API 的骨架，每一段都要有內容：

# 咖啡店訂單 API

## 簡介
咖啡店的點餐、付款與庫存 API。Learn NestJS 課期末專題，獨力完成；
訂單完成時寄收據信（BullMQ）與菜單快取（Redis）是我自己加的延伸。
（這裡放一張截圖或一段 API 呼叫的示範）

## 架構
（一張圖：Vue 前台 → NestJS API → PostgreSQL，API 旁邊是 Redis 與 BullMQ worker）

## 快速開始
```bash
cp .env.example .env
docker compose up -d --wait
```
打開 http://localhost:3000/docs 看 API 文件。

## 測試
```bash
npm test          # 單元測試 38 個、資料庫整合測試 26 個
```

## 設計決定
- 庫存扣減用交易＋條件更新，不用「先查再扣」：兩筆訂單同時搶最後一杯時不會賣超。
- 模組化單體，不拆微服務：一個人維護、流量小，模組邊界先在程式裡守住。

## 已知限制
- 只支援單一店家；金流是假的；沒有正式環境的監控告警。
- 下一步：多店家（需要在每張表加 store_id 並調整索引）。

每一段在回答什麼：

段落回答的問題常見的錯
簡介這是什麼、你做了哪部分、是不是學習專案只有專案名稱
架構有哪些元件、資料怎麼流只列技術名詞，沒有圖
快速開始怎麼在自己電腦跑起來超過 3 步、少了 .env.example、依賴你電腦上才有的東西
測試怎麼跑測試、測了什麼沒寫、或寫了但測試跑不過
設計決定你選了什麼、考慮過什麼替代方案、為什麼只寫「使用 Redis」，沒寫為什麼、沒寫放棄了什麼
已知限制哪裡還不夠、下一步做什麼不寫，假裝完美

幾個寫法上的重點：

  • 快速開始控制在 3 步以內。最理想的是一行 docker compose up：資料庫、Redis 都在 Compose 裡，面試官電腦上只需要 Docker。需要的環境變數放在 .env.example（只有變數名稱和假的值，可以公開），讓人 cp 一份就能用。寫完之後，自己用一個全新的資料夾重新 clone、照著 README 做一次，這是唯一確定它跑得起來的方法。
  • 設計決定照 ADR 的格式寫：系統設計課第 18 課的 ADR（architecture decision record，架構決策紀錄）要寫出決定、考慮過的替代方案和理由。只寫「用了 BullMQ」不是決定，「寄信放進 BullMQ 佇列、不在 request 裡同步寄，因為郵件服務慢或掛掉時不能拖垮下單」才是。
  • 已知限制是加分。資深工程師知道自己的系統哪裡會壞；寫出限制和下一步，面試官就知道你看得到。
  • 標題用固定的名稱。中文、英文都可以，但同一份 README 裡一致。練習 2 會寫一個檢查器，用標題找出缺了哪一段。

用程式檢查 README 時，最容易出錯的是「什麼算標題」。Markdown 的 ## 開頭是第二層標題，### 是第三層（子標題）；但寫在程式區塊（用 ``` 包起來的區域）裡的 ## 只是文字。下面是一個天真的寫法，看看它錯在哪：

公開前檢查

repo 一旦設成 public，裡面的東西就要當作全世界都看過了：有程式會自動掃描公開 repo 找金鑰，推上去幾分鐘內就可能被拿去用。推之前檢查這些：

要找的東西為什麼不能公開怎麼處理
.env、.env.local、.env.production放著真的密碼與金鑰加進 .gitignore；只提交 .env.example
寫死在程式裡的金鑰例如 AWS 的 access key，拿到就能用你的帳號開機器改從環境變數讀（DevOps 課第 11 課）
私鑰檔（.pem、id_rsa）拿到就能冒充你的伺服器或登入你的主機永遠不進 Git
node_modules/、dist/不是機密，但是是安裝與建置的產物：幾萬個檔案、別人 npm ci 就有加進 .gitignore
資料庫備份（.sql dump）常含真實的顧客資料不進 Git；示範資料改用 seed 程式（啟動時往資料庫寫入示範資料的腳本）產生假資料
個資（身分證字號、電話、地址）測試資料裡混進真人資料換成假資料

上面的「金鑰」「密碼」統稱機密（secret）：不能公開的值。怎麼保存與輪替機密是 Auth 課第 23 課的內容；這一課只做公開前的檢查。

檢查可以用程式自動做，原理是比對格式。以 AWS 的長期 access key ID 為例，常見格式是 AKIA 開頭、後面 16 個大寫英文字母或數字，共 20 個字元（AWS 文件裡的範例值是 AKIAIOSFODNN7EXAMPLE）。寫成正規表示式要注意兩件事：剛好 16 個（{16}），以及前後不能還接著別的英數字。後者用 \b（單字邊界，word boundary）：它不比對任何字元，只要求這個位置一邊是英數字或底線、另一邊不是；第 2 課的環視是另一種寫法：

寬鬆的寫法會把只有 10 碼的字串也當成金鑰，誤報多了，大家就會開始忽略檢查結果。這只是規則的示範，真正的機密掃描工具（例如 DevOps 課第 11 課用的 gitleaks）內建上百種格式。另外，GitHub 對個人帳號預設開啟 push protection for users：你 push 到 public repo 的內容如果像是已知格式的機密，push 會被擋下來。它只在 push 到 public repo 時檢查，repo 還是 private 時推上去的機密不會被擋；它是最後一道防線，不能取代推之前的檢查。

機密已經 commit 過了怎麼辦

最常見的誤會是「我再 commit 一次把檔案刪掉就好」。Git 保存每個 commit 當時的完整快照，刪除只是多一個新的 commit，舊的 commit 裡金鑰還在，任何人 clone 下來都看得到。只要 push 過，就當作已經外洩，依 DevOps 課第 11 課的順序處理：

  1. 輪替並撤銷：產生新的金鑰換上，再讓舊的失效（Auth 課第 23 課）。這一步最優先，舊金鑰失效後，別人手上那份就沒用了。
  2. 查紀錄：外洩期間舊金鑰有沒有被用過、做了什麼。
  3. 清理歷史：用 git filter-repo 從所有 commit 移除那個檔案（DevOps 課第 14 課）。這只減少之後被撿到的機會，不能取代第 1 步。
  4. 預防：.gitignore、commit 前的自動檢查。

把 repo 改成 private 也不能取代第 1 步：已經被複製走的金鑰還是有效的。

💡 實務上：作品 repo 從第一個 commit 就當成 public 來寫
最常出事的時機不是寫程式時，而是「把一直是 private 的練習 repo 改成 public」那一刻：幾個月前為了方便寫死在程式裡的測試金鑰，早就埋在歷史裡了。所以作品 repo 一開始就放 .gitignore 與 .env.example，改 public 前跑一次機密掃描（gitleaks 會掃整段歷史，不只目前的檔案）。真的掃到了，照上面的順序：先輪替並撤銷金鑰，再清歷史。清歷史的另一個選擇是開一個新的 repo、只放整理過的最終版本，代價是看不到你一步步做的 commit 歷史。

GitHub 個人頁

面試官從履歷上的連結點進你的 GitHub，先看到的是個人頁。這一頁有兩個地方可以安排：

個人頁 README（profile README）會顯示在個人頁最上方。依 GitHub 官方文件（2026 年 11 月查證），它要同時符合四個條件才會顯示：

  1. 有一個名稱跟你的 GitHub 帳號完全相同的 repo（帳號是 xiaoming-dev，repo 就叫 xiaoming-dev）。
  2. 這個 repo 是 public。
  3. 根目錄有 README.md。
  4. README.md 有內容。

內容寫三樣東西就夠：一句定位、2～3 個代表作品的連結、聯絡方式。

# 王小明

後端工程師（NestJS・PostgreSQL），前端出身，熟悉 Vue 3 與前後端串接。

- [咖啡店訂單 API](https://github.com/xiaoming-dev/cafe-api)：交易防超賣、Redis 快取、BullMQ 寄信，64 個測試
- [咖啡店部署與維運](https://github.com/xiaoming-dev/cafe-ops)：Docker、CI/CD、監控與告警

聯絡：LinkedIn https://www.linkedin.com/in/xiaoming-dev

不用放動畫徽章、統計圖卡或「今年寫了幾行程式」，那些不能證明你的能力，只會把作品擠到下面。

釘選的 repo（pinned repositories）：個人頁可以釘選最多 6 個 repo 或 gist（gist 是 GitHub 上分享單一程式片段的小型 repo；官方文件寫的是兩者合計 6 個），顯示在 README 下方。放你最想被看的 2～3 個作品，其他位置可以空著；空著比放課堂練習好。

同樣的 2～3 個作品連結，也放在 LinkedIn 個人檔案的 Featured（精選）區，和第 2 課的履歷、LinkedIn 經歷用同樣的說法與數字。

💡 實務上：用沒登入的瀏覽器檢查一次
你登入時看到的 GitHub 跟面試官看到的不一樣：private repo 你看得到，他看不到。投履歷前用無痕視窗打開履歷上的每一個連結：個人頁 README 有沒有出現、釘選的是不是你想給人看的、作品 README 的快速開始照著做能不能跑。最好再請一位朋友從 clone 開始照 README 跑一次，卡住的地方就是要補的說明。履歷上一個 404 的連結，會讓面試官懷疑其他內容也沒更新。

資深視角：作品要展示判斷

初階的作品證明「我做得出來」；資深的作品要證明「我知道為什麼這樣做，也知道什麼時候不該這樣做」。面試官會沿著 README 的設計決定追問，你要準備好這種回答：

  • 為什麼不用：「為什麼不拆微服務？」→ 一個人維護、一個資料庫、流量小，拆了只多出網路呼叫與部署成本（系統設計課第 15 課）；如果之後真的要拆，模組邊界已經畫好了。
  • 為什麼選這個：「為什麼寄信用 BullMQ？」→ 郵件服務慢或掛掉時不能拖垮下單；BullMQ 有重試與失敗佇列，而且 Redis 本來就有了，不用多一個元件（NestJS 課第 20 課）。
  • 測試策略：哪些用單元測試、哪些一定要接真的資料庫測（例如庫存的並發扣減），為什麼。
  • 規模變化：「如果訂單量變 10 倍，你會先改哪裡？」→ 先量哪裡慢（p95、資料庫連線數），再說會先動哪裡、為什麼不是全部重寫。

一個好用的檢查：把 README 的每個設計決定都配上「考慮過的替代方案」。寫不出替代方案的決定，通常只是照著教學做，面試被問到也答不出來。練習 3 就是把這些整理成一張作品卡。

練習

練習 1：寫 auditRepo(files)，在把 repo 設成 public 之前，找出不該公開的檔案。規則寫在起始程式的註解裡；注意 .env.example 可以公開、node_modules 只報一次資料夾、金鑰可能藏在任何檔案的內容裡。

練習 2：寫 parseSections(md) 把 README 切成段落，再用它寫 checkProjectReadme(md)，找出缺了哪幾段、哪幾段是空的，以及快速開始有幾步。規則寫在起始程式的註解裡；回想上面那個天真寫法的兩個錯。第 6 課寫帶回家作業的 README 檢查器時會直接沿用 parseSections。

練習 3：把 NestJS 課期末專題整理成一張作品卡 project，作為 README 和面試的底稿。起始程式裡有你的專題紀錄（練習用的虛構數字；k6 是壓力測試工具，DevOps 課第 22、26 課會用到）和測試會檢查的規則：每個設計決定都要有替代方案和出處課程，每個數字都來自紀錄、而且寫出怎麼量的，至少一條真正的限制，並誠實填寫角色與是否為學習專案。

練習 4：你不小心把含有 AWS 金鑰的 .env commit 並 push 到 public repo，發現後馬上用一個新 commit 把它刪掉。這樣夠嗎？

✓ b：公開過的機密要當作已經外洩，第一步是讓它失效。a 錯：刪除只是新的 commit，舊 commit 裡金鑰還在；c 錯：已經被複製走的金鑰改成 private 也還是有效；d 錯：清理歷史只減少之後被撿到的機會，沒輪替的話，別人手上那份還能用。

練習 5：作品集放 20 個跟著教學做的小專案，和放 2 個有 README、測試、部署與設計決定的專案，哪個比較有說服力？

✓ b：面試官時間有限，能說清楚決定與取捨的專案才撐得住追問。a 錯：教學專案人人都有，數量證明不了判斷；c 錯：面試官先看 README 和能不能跑，很少從頭讀程式碼；d 錯：沒有後端工作經歷時，作品就是履歷上那些句子的證據。

練習 6：把在前公司寫的程式碼整理後放到 GitHub 作品集，可以嗎？

✓ b：權利歸屬不會因為「是我寫的」而改變。c、d 錯：拿掉公司名稱或放舊版本，權利還是屬於公司，面試官看到也會擔心你會帶走他們的程式碼。用 Learn 的咖啡店專案重現相同概念是安全的做法。

練習 7：帳號是 xiaoming-dev，想在 GitHub 個人頁最上方顯示自我介紹。下面哪個做法會顯示出來？

✓ c：四個條件都符合：repo 名稱和帳號相同、public、根目錄、有內容。a 名稱不同；b 不是 public；d 不在根目錄。

離開頁面要做的事

  • 挑 2～3 個期末專題當作品，每個都照「README 骨架」寫好六段，再用練習 2 的規則自己檢查一次。
  • 用一個全新的資料夾重新 clone 你的作品，照 README 的快速開始做一遍；任何一步要你「想一下」，就改 README。
  • 推上 GitHub 之前，照練習 1 的清單檢查；確認 .gitignore 有 .env、node_modules、dist。
  • 建立與帳號同名的 public repo，寫個人頁 README；釘選 2～3 個作品；LinkedIn 的 Featured 區放同樣的連結。
  • 每個作品準備「如果流量變 10 倍我會改哪裡」的答案，寫在 README 的已知限制或你自己的筆記裡。

常見錯誤

  • README 只有專案名稱：面試官不會讀程式碼來猜它在做什麼。至少寫簡介、架構、快速開始、測試、設計決定、已知限制六段。
  • 跑不起來：快速開始超過 3 步、缺 .env.example、依賴你電腦上才有的東西，面試官就會放棄。自己用全新的 clone 照著做一次。
  • 機密進了歷史：刪檔不等於安全。只要 push 過就當作外洩：先撤銷、更換金鑰，再清理歷史。
  • 沒標明是學習專案：被問到使用者數時會很尷尬。誠實標示，對話會轉到你做了哪些自己的延伸。
  • 作品太多、太淺：20 個教學專案不如 2～3 個能談 30 分鐘的。釘選位置留給最好的作品。
  • 設計決定只寫選了什麼：「使用 Redis」不是決定。寫出考慮過的替代方案和理由。
  • 放公司的程式碼：權利屬於公司、可能違反保密協議。改成描述做法，或用自己的專案重現。

小結

  • 面試官依序看 README 開頭、快速開始、資料夾結構、測試、commit 歷史，每一步都可能是最後一步。
  • 作品集放 2～3 個對應目標職缺、能被追問 30 分鐘的專案。期末專題加上你自己的延伸、真實數字，並標明是學習專案與你的角色。
  • README 六段：簡介、架構、快速開始（3 步以內）、測試、設計決定（決定、替代方案、理由）、已知限制。
  • 公開前檢查 .env、金鑰、私鑰、node_modules／dist、資料庫備份與個資。機密 push 過就當作外洩：先輪替、撤銷，清理歷史只是其次。
  • 不放公司的程式碼。
  • 個人頁 README 的四個條件：與帳號同名、public、根目錄的 README.md、有內容。釘選最多 6 個，放最好的 2～3 個。
  • 資深的作品展示判斷：為什麼不用、為什麼選、測試策略、流量變 10 倍先改哪裡。
