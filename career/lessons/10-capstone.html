階段 4：期末專題 · 第 10 課

期末專題：轉職全端的求職包與第一年成長計畫

前九課各自教了一種材料：履歷句子、作品、故事、面試計畫、offer 計算。真的去應徵時，這些材料會同時被同一群人看到：HR 看履歷、技術主管點開 GitHub、行為面試官追問你履歷上的數字、系統設計面試官問你作品裡的取捨。材料之間有一個數字對不上，或作品說成是正式工作、被追問兩層就露餡，前面的準備就白費了。

這一課把前面的東西組成一份求職包（application kit：投遞與面試要用的整套材料），用第 1 課的轉職定位，針對一個真實格式的全端（後端為主）中階職缺從頭做一次，最後再寫一份進公司之後 12 個月的成長計畫：從全端、中階走向能獨當一面。

這課的路線：
  1. 目標與缺口分析：對著一份真實格式的 JD，把每條要求對到你的證據，「沒有後端正式經歷」這個缺口怎麼誠實處理。
  2. 履歷、作品與故事庫：材料之間的數字要對得上，兩個作品展示不同的判斷，故事對著 JD 先猜會被問什麼。
  3. 系統設計「咖啡外送即時追蹤」：JD 點名的題目，照系統設計面試的流程完整準備一次。
  4. offer 與一年計畫：用時間軸比較兩個 offer，寫出在容量內、每季都有產出的第一年計畫。
  5. 資深視角：求職包是活的文件，每季跟著成果紀錄更新。
這課會用到：
  • 第 1 課的轉職定位與 matchJob：瞄準全端或中階後端，用作品補上沒有後端正式經歷的缺口；把 JD 每一條對到證據，必要條件最多缺 1 項才值得投。
  • 第 2 課的影響力句子：動作＋範圍＋結果，具體動詞開頭、有數字。
  • 第 4 課的故事庫：6～8 個 STAR 故事，涵蓋衝突、失敗、主導、影響力、模糊、帶人六種能力。
  • 第 7 課的系統設計面試流程：需求 → 估算 → API → 資料模型 → 高層架構 → 深入 → 總結，用 estimate 算 QPS 與儲存量。

目標：一個職缺、一份背景

專題用一個具體的職缺當目標。求職包一定要對著某個職缺做：同一份材料對不同職缺，該強調的東西不一樣。下面是一份常見格式的 JD（豆香咖啡是虛構的咖啡連鎖品牌）：

豆香咖啡｜全端工程師（後端為主，中階）
你會：開發門市點餐、會員與後台管理系統的 API（NestJS）和管理介面（Vue）；和資深工程師一起維護訂單服務，熟悉後參與值班輪值（on-call，輪到的那週要接告警、處理線上問題）；參與 code review，協助新進同事上手；和產品一起規劃即時外送追蹤。
必要條件：TypeScript、Vue、NestJS、PostgreSQL、REST API 設計、2 年以上後端開發經驗（有相關作品可討論）。
加分條件：Docker、Redis、AWS、CI/CD、系統設計經驗。
關鍵字（我們在意的事）：API、冪等、測試、CI/CD。

你的背景：前端工程師 4 年，在咖啡連鎖的點餐網站用 Vue 3 和 TypeScript；工作上和後端訂過 API 規格、處理過結帳頁重複送出的事故，但沒有後端的正式職稱與經歷。下班後完成了 Learn 的技術課，有 NestJS 課與 DevOps 課的期末專題當作品。這就是第 1 課說的轉職：瞄準全端或中階後端，前端經驗是優勢，作品補上缺的後端經歷。

你真正投出去的求職包，主力作品是作品專案課的兩個作品：一個小專案，以及一個用 NestJS、Prisma、PostgreSQL 做的多租戶 SaaS 後台（一套系統服務很多家店，每家的資料要隔離；包裝方式見作品專案課第 19 課）。這一課的練習為了能自動判分，用每個人都一樣的兩個期末專題當示範資料；做完練習後，照同樣的流程把作品專案換進事實表、作品卡與故事庫。

練習裡的事實表（FACTS）列出你所有可以引用的數字，工作上的事和 Learn 的作品分開標示。履歷上的每一個數字都要能在這張表找到；同一件事出現在故事、作品 README 裡時，數字也要和表上一樣。

事實表是求職包的底。履歷寫串接 bug 從每月 12 件降到 3 件，故事裡就不能變成 2 件，作品 README 的測試數也要和履歷一致。面試官會交叉比對：數字不一致，比沒有數字更傷，因為它讓人懷疑其他內容。

步驟 1：缺口分析

缺口分析（gap analysis）是把目標職缺的每一條要求，對到你手上的證據，找出還缺什麼。第 1 課的 matchJob 就是在做這件事：proof 是空的證據不算，必要條件最多缺 1 項才值得投。這一課再加一條規則：每個證據要寫出出處（例如 nestjs#27），面試官問「你在哪裡做過」時答得出來，自己整理材料時也找得到。

必要條件你的證據強度
TypeScript工作 4 年；TypeScript 課期末專題強
Vue工作 4 年；Vue 課期末專題強
NestJSNestJS 課期末專題（個人練習專案）中
PostgreSQL期末專題的交易與條件更新；交易與鎖的練習中
REST API 設計工作上和後端訂 OpenAPI 規格；期末專題的 API 與 OpenAPI 文件中
2 年以上後端開發經驗沒有後端的正式經歷；Learn 的作品不能充當年資缺

結果：缺 1 項（後端年資），可以投，而且 JD 自己寫了「有相關作品可討論」。這個缺口是轉職的人一定會遇到的，有三種處理方式：

  • 用相近的真實經驗回應：工作上碰過的後端事，例如和後端訂 API 規格、一起處理重複送出的事故、改過一支 API，寫成故事並誠實說明範圍：「我沒有後端的正式職稱，但我在前端工作裡處理過……」。
  • 用作品證明做得到：作品證明你能獨立做完一個後端功能：交易不賣超、有測試、能部署上線。面試時主動說明是個人練習專案，談你的判斷與除錯過程（第 3 課）。
  • 寫進一年計畫：缺口是成長計畫的輸入（步驟 6b）。進公司後第一季的主題，就是把這個缺口變成正式經歷：獨立交付第一個後端功能。

不能做的是把缺口補成假的：把前端 4 年寫成「全端 4 年」，或把 Learn 作品寫在工作經歷裡當成年資，第一個追問「上線後多少人在用、你們怎麼值班？」就答不出來。

💡 實務上：接新任務前也做一次缺口分析
同一張表在工作中也用得到，不只是求職。假設豆香咖啡要你負責步驟 5 的外送追蹤，先把需要的能力列出來（SSE、Redis、佇列），對到團隊裡誰真的做過：沒人在正式環境跑過長連線，這就是缺口。缺口要寫進估時，例如「多留兩天先做一個小原型」，或先約做過的人花半小時看設計，而不是開工後才發現卡住。和投履歷一樣，缺一項是正常的，重點是開工前就說出來。

步驟 2～3：履歷與作品

履歷照第 2 課的規則寫：每條是「動作＋範圍＋結果」，以具體動詞開頭，有數字，改善類的結果要有改善前的數字。這一課多做兩件事：

  • 對著 JD 選句子：主清單可以有 8 條，但只有對到 JD 的會被選進一頁的版本。第 2 課的 tailor 用句子的 keywords 和 JD 關鍵字算分；keywords 要照實填「這條句子證明了什麼」，不是把 JD 的字全部塞進去。全端職缺也看前端，結帳頁 LCP 那條會被選進來；同一份主清單投純後端職缺時，JD 沒有 Vue，tailor 就不會選它，這是對的。
  • 標清楚練習專案：Learn 的期末專題可以寫進履歷，但要寫在「作品」或在句子裡寫明「練習專案」，不能混在工作經歷裡，看起來像在公司做的。

作品用兩個期末專題：NestJS 課的訂單 API 證明你會寫後端，DevOps 課的上線與維運 證明你會把它送上線、出事時處理得了。兩張作品卡要展示不同的判斷：訂單 API 談交易、佇列、快取；上線專案談容量、不可變映像、備份與還原。兩張卡寫同一組決定，等於只有一個作品。作品專案課的多租戶 SaaS 後台完成後，它會取代訂單 API 成為第一張卡：多租戶隔離、權限與資料表設計，是中階後端面試最常追問的題目。

公開 repo 前跑第 3 課的 auditRepo。修正的原則是「只動有問題的檔案」：.env、私鑰、資料庫備份檔、node_modules 刪掉；寫死在程式裡的 AWS 金鑰改成讀環境變數（真的金鑰還要去 AWS 撤銷，見DevOps 課第 11 課）；.env.example 要留著，別人才知道要設哪些變數。把整個 repo 清空當然掃不到問題，但也沒有作品了。

步驟 4：故事庫對著 JD 準備

第 4 課的故事庫要涵蓋六種能力。對著這份 JD，可以先猜面試會問什麼：「和產品一起規劃」會問衝突與模糊的需求；「熟悉後參與值班」會問事故與失敗；「協助新進同事上手」會問帶人。最弱的那一項（後端年資）最需要準備好的故事，面試官一定會問「你為什麼覺得自己做得來後端？」：準備一個工作裡碰到後端問題的真實經驗，加一個作品裡自己解決的後端問題（第 1 課的轉職定位）。

故事可以來自 Learn 的專題，但要在情境裡講明：「這是 DevOps 課的期末專題，個人練習」。練習專案的故事重點放在你的判斷與除錯過程（怎麼發現連線池超過資料庫上限、怎麼驗證），面試官在意的是你怎麼想，不是誰付你錢。說成正式工作，追問「上線後用量多少、誰在用」就會出事。

步驟 5：系統設計「咖啡外送即時追蹤」

JD 提到「規劃即時外送追蹤」，系統設計面試很可能就考它。題目：顧客下了外送單後，在 App 上看到外送員的即時位置與預計到達時間。面試官給的數字：每天 30 萬個活躍使用者（顧客加外送員）、尖峰時同時有 3,000 筆配送中的訂單、外送員 App 每 5 秒回報一次位置、軌跡保存 30 天。

中階職缺不一定有完整的系統設計關卡，常改成概念問答（第 5 課）或只問 API 與資料表。這份 JD 提到外送追蹤，所以照第 7 課完整準備一次：準備到完整的程度，面試只問到 API 和資料表那一層時也答得出來。流程照第 7 課的七個階段，分鐘加總 45。估算先用最直接的方法算寫入量：3,000 筆配送中 × 每 5 秒一次 = 每秒 600 次位置寫入。再把題目換成 estimate 的輸入交叉檢查：每人每天 100 次請求（外送員回報位置佔大多數）、尖峰 3 倍、寫入佔 60%、每筆位置 100 bytes、保存 30 天：

avgQps       = ceil(300,000 × 100 ÷ 86,400) = 348
peakQps      = 348 × 3 = 1,044
writeQpsPeak = ceil(1,044 × 60 ÷ 100) = 627      ← 和「每秒 600 次」同一個量級
storageGB    = 300,000 × 100 × 60% × 100 bytes × 30 天 ≈ 54 GB

兩種算法對得上，面試官就知道你的數字不是猜的。每秒 600 多次的小寫入，每一次都直接寫 PostgreSQL 做得到，但沒必要：顧客只需要「最新的」位置，歷史軌跡晚幾秒寫進資料庫也沒關係。這就是這一題的三個關鍵元件：

  • 最新位置快取：每個配送單的最新位置放 Redis，讀寫都快，覆蓋舊值即可。
  • 位置寫入佇列：軌跡先進佇列，由 worker 批次寫入資料庫（系統設計課第 12 課），資料庫的寫入次數少一個數量級。
  • 推送閘道：維持和顧客瀏覽器的長連線，位置一更新就推過去（系統設計課第 17 課）。這裡只需要伺服器往顧客單向推，SSE（Server-Sent Events）就夠，不需要 WebSocket。

長連線一定會斷：顧客進電梯、切換網路、推送閘道重新部署。面試時要主動講斷線怎麼辦。瀏覽器的 EventSource 在連線斷掉後預設會自動重連；伺服器送事件時帶上 id，重連時瀏覽器會用 Last-Event-ID 標頭告訴伺服器最後收到哪一筆，伺服器再從快取補送最新位置。外送員那一端離線時，畫面要標示「位置更新中斷」，而不是讓地圖上的點停著，看起來像外送員沒在動。

💡 實務上：先問「多即時才夠」再選元件
「外送即時追蹤」這種需求在公司裡通常先出現在 PM 的規格裡，只寫著「要即時」。資深工程師在設計審查的第一個問題是「延遲幾秒顧客能接受？」：每 5 秒和每秒更新一次，寫入量差 5 倍，元件的選擇可能就不同。第二個問題是位置資料：外送員的即時位置是個人資料，要確認誰看得到（只有這張單的顧客、只在配送中）、軌跡為什麼要留 30 天，以及送達後就停止推送。這兩個問題在面試裡主動講，跟在工作中主動問，是同一種能力。

步驟 6：offer 與一年計畫

假設面試都過了，手上有兩個 offer。用第 8 課的 annualComp 算：

豆香咖啡快送豆（外送新創）
月薪 × 保障月數72,000 × 14 = 1,008,00070,000 × 14 = 980,000
預期績效獎金1 個月 = 72,0000
簽約金0200,000（未滿 1 年離職全額退回）
第一年總報酬1,080,0001,180,000
穩定年度總報酬1,080,000980,000
勞退提繳估計（另列）51,84050,400

兩個都是轉職的人實際會拿到的條件：職級是中階，月薪和你現在的前端薪水差不多，這是第 1 課說的「職級可能被往下定」。只看第一年，快送豆多 10 萬；從第二年起豆香每年多 10 萬，兩年累計剛好追平（2,160,000 對 2,160,000），第三年起豆香領先。簽約金只發一次，還附退回條款，所以第 8 課的 compareOffers 用穩定年度總報酬比較。勞退提繳不得低於工資的 6%，這筆錢進個人退休金專戶，不是月薪，所以另列、不加進總額。

錢只是一個因素。compareOffers 把錢換成 1～5 分，和範圍、團隊、成長、on-call 負擔、通勤一起加權。權重由你決定，但要先寫下來再算，不要算完再調權重讓喜歡的那個贏。決定可以和排名不同（例如你真的很想要快送豆的技術環境），這時把原因寫出來：「排名不同的原因：……」。寫得出來，代表你知道自己在用什麼換什麼。

決定前在團隊訪談問清楚三件事：on-call 怎麼排、一個月被叫幾次、有沒有補休；績效評估多久一次、各職級的標準有沒有文件、轉職進來的人多久重新評估職級；目前最大的技術債是什麼、有沒有時間處理。這三件事決定你進去之後每天過得怎樣，也決定一年計畫有沒有時間做。轉職的人再多問一件：團隊裡有沒有資深後端帶你、每個 PR 有沒有 code review。第一份後端工作最值錢的是有人帶，這常常比每年差幾萬元更影響你一年後的位置。

最後是一年計畫，目標是從全端、中階走向獨當一面：一年後交給你一個功能，你能從規格、資料表、API、測試一路做到上線與值班，不需要資深工程師幫你收尾。第 9 課的 planCapacity 算出新工作在輪到 on-call 那一週（到職 3 個月後開始輪）的可承諾時數：40 小時扣掉 8 小時會議、20% 中斷、on-call 週再打 7 折、只承諾 80%，得到 14 小時。計畫用最緊的那一週來算，輪到值班時才不會斷掉。學習在下班後，但精力是同一份，這門課把可持續的學習時數定為它的 25%：14 × 25% = 3.5，四捨五入是每週 4 小時，大約兩個晚上。計畫寫得再好，每週要 10 小時就撐不過第一個 on-call 週。

每一季的主題要回答三個問題：

  • 為什麼是這個：對到哪個缺口（步驟 1 的後端年資）或職缺條件（AWS、系統設計）。
  • 從哪裡學：Learn 的哪幾課；Learn 之外的資源寫 external: 加上主題，例如 external:AWS 官方文件。每一季至少連到一課 Learn，讓計畫和你已經學過的東西接得上。
  • 怎麼算完成：可驗證的產出（verifiable output）是別人看得到的成果：一個 repo、一篇發布的文章、一次內部分享、一個被合併的 PR。「學會 AWS」沒辦法檢查，「用 OpenTofu 把作品部署到 AWS，repo 公開、README 通過第 3 課的檢查」可以。

四季的順序通常是：先在公司交付第一個完整的後端功能，把缺口變成正式經歷；再接值班與效能問題；再補職缺的加分條件；最後主導一個功能的設計。學習跟著工作走，下班的時數拿來補工作上正好需要的那一塊。

產出的種類要混合：一年下來有作品、有文章、有分享，下一次更新履歷時就有不同種類的證據，也對應到第 9 課說的資深期待：不只自己會，還能讓別人也會。

資深視角：求職包是活的文件

求職包不是找工作時才做的東西。第 9 課的成果紀錄每週寫 5 分鐘，每季整理一次時順便更新三樣東西：事實表加上新數字、故事庫換掉最舊或最弱的故事、一年計畫勾掉完成的、調整下一季。這樣不管是績效評估、升遷文件，還是哪天有人找你面試，材料都是現成的，而且數字一致。

進階範例：同一套流程對準資深職缺
幾年後有了後端正式經歷，同樣的流程可以對準資深後端職缺。差別在三個地方：必要條件多出 Redis、AWS、on-call 與帶新人，每一條都要有正式工作的證據（例如「重寫訂單 API，p95 從 800 ms 降到 180 ms」「值班 6 個月、寫過 3 份事後檢討」），作品退到輔助；故事庫最需要的是帶人和事故處理；系統設計一定會考，而且會深入到故障與擴展。轉職的第一份工作，就是在替這張表累積正式經歷。

做判斷時也一樣：缺口要誠實面對，不是補成假的；offer 要算清楚時間軸，不是看哪個第一年最多；計畫要在容量內，不是寫給別人看的願望清單。這三件事和系統設計一樣，都是在限制下做取捨，而且說得出代價。

練習

六題對應六個步驟，都是「填資料」：起始程式貼好了前面課的檢查器，你只寫材料與決定。測試用自己的一份參考實作判分，改起始程式裡的檢查器不會讓測試通過。測試只檢查結構和可以機器判斷的規則；內容好不好，留給離開頁面後的模擬面試。

每題先寫「做完的樣子」，再拆成幾個小步驟，每步標出回去看哪一節；照步驟做、每做完一步就按「執行」看輸出。六題不用一次做完，可以分幾天做。

練習 1（步驟 1＋2）：填 myEvidence（缺口分析的證據）與 resume（履歷主清單）。起始程式已經貼好第 1 課的 matchJob、第 2 課的 lintBullet 與 tailor，還有豆香咖啡的 JD（JOB）和你的事實表（FACTS）。完整規則在起始程式的註解裡，測試照那份規則判分。

做完的樣子：matchJob(JOB, myEvidence).apply 是 true，只缺「2 年後端經驗」這一項；resume 有 6～8 條通過 lintBullet 的句子，數字都查得到事實表，tailor(resume, JOB.keywords, 12) 至少選中 5 條。

  1. 對證據（「步驟 1：缺口分析」的表）：JOB.must 的前 5 條各寫一筆 { skill, proof }，proof 寫出處並帶課號，例如 'nestjs#27'。「2 年後端經驗」不要列：它是缺口。加分條件有證據也可以列。
  2. 寫句子（第 2 課的影響力句子）：從 FACTS 挑 6～8 件事，各寫一條「動作＋範圍＋結果」，text 以 action 開頭、每條換一個動詞；result 填結果的數字，改善類（metric 含「降低」「減少」等字）要填 baseline。
  3. 標關鍵字（「步驟 2～3：履歷與作品」）：每條的 keywords 填 1～3 個，寫這條句子證明了什麼；要被 tailor 選中，用的字要和 JOB.keywords 一樣。
  4. 按「執行」看兩行輸出：第一行的 missingMust 只剩 ['2 年後端經驗']，第二行至少 5 個 id，再按「檢查答案」。
卡住時的提示
  • skill 的寫法要和 JOB.must 一樣（例如 'REST API'，不是 'REST'），matchJob 只忽略大小寫和前後空白。
  • 句子裡的每個數字都會被拿去查事實表，連「3 個月」的 3 也算；p95、k6、E2E 這種名稱裡的數字不算。
  • Learn 作品的句子在 text 裡寫明「練習專案」，不要寫得像工作經歷。
  • text 最多 80 個字，不能以「負責」「參與」「協助」「熟悉」「處理」開頭。

練習 2（步驟 3）：把兩個期末專題整理成可以公開的作品：填 projects（兩張作品卡）、readmes（兩份 README）和 fixedFiles（公開前清理過的檔案清單）。起始程式貼好了第 3 課的 auditRepo、checkProjectReadme 和兩個 repo 目前的檔案清單（REPOS）。

做完的樣子：兩張作品卡各講 3 個以上不同的決定，數字只用事實表裡的；兩份 README 的 6 個段落都有內容，快速開始 1～3 步；auditRepo 對兩個 repo 清理後的檔案都回傳空陣列，沒問題的檔案原封不動。

  1. 作品卡（第 3 課的作品卡；本課「步驟 2～3」）：source 分別是 'nestjs#27' 與 'devops#26'。訂單 API 的 decisions 談交易、佇列、快取，上線專案談容量、不可變映像、備份與還原，兩張卡的 decision 不能重複。numbers.value 只能用 PROJECT_FACTS 裡的數字，isLearningProject 誠實填。
  2. README（第 3 課的 README 骨架）：每份有 ## 簡介、## 架構、## 快速開始、## 測試、## 設計決定、## 已知限制 六段（英文標題也可以），每段有內容；快速開始用 1～3 行指令或 1～3 個編號步驟。
  3. 清理 repo（本課「步驟 2～3」最後一段，「公開 repo 前跑第 3 課的 auditRepo」）：先執行看 auditRepo 抓到哪些檔案，只處理這些：.env、.env.production、私鑰、資料庫備份、node_modules、dist 刪掉；src/storage/s3.ts 寫死的金鑰改成讀環境變數。.env.example 和其他檔案留著，內容一字不改。
卡住時的提示
  • fixedFiles 可以從 REPOS[...] 開始，用 filter 拿掉要刪的檔案，再用 map 換掉 s3.ts 的內容，例如改成 process.env.AWS_ACCESS_KEY_ID。
  • README 用樣板字串寫，程式區塊的三個反引號用起始程式的 FENCE 常數接起來。
  • oneLiner 最多 60 個字；lessonRef 寫存在的課號，例如 'devops#13'（擴充與容量）。

練習 3（步驟 4）：完成故事庫 bank。起始程式有 4 個照你的背景寫好的故事（直接用，不用改）和一個沒準備好的帶人故事 onboarding。

做完的樣子：bank 有 6～8 個故事，每個都通過 checkStory；buildCoverage(bank, ALL) 的 gaps 和 overused 都是空的，QUESTIONS 的 6 題 pickStory 都挑得到故事。

  1. 重寫帶人故事（第 4 課的 STAR 與 checkStory）：照註解「你的事實」第一點重寫 onboarding。動作用「我」開頭、寫出具體做了什麼；situation 簡短，總字數不到 actions 的一半；result.metric 填 before: 10, after: 4，和事實表一致；learning 寫一句學到的事。
  2. 補一個 Learn 專題的故事（本課「步驟 4」第二段）：照註解第二點寫 DevOps 期末專題的壓測故事，situation 寫明「Learn」「devops#26」「練習」，例如「這是 Learn DevOps 課（devops#26）的期末專題，個人練習……」。
  3. 檢查涵蓋：每個故事標 1～3 種能力，新故事標它真正證明的能力。執行看第一行的 gaps 是空陣列、第二行 6 個都不是 null，再按「檢查答案」。
卡住時的提示
  • pickStory 只挑通過 checkStory 的故事，所以第 1 步沒寫好，「你怎麼帶新人？」就挑不到故事。
  • 壓測故事是自己發現問題、重算、修正、驗證，適合標 failure 或 ownership；result.metric 可以用錯誤率 4 → 0。

練習 4（步驟 5）：起始程式是第 7 課「線上點餐」的面試計畫 sdPlan。把它改成這課的新題目「咖啡外送即時追蹤」。

做完的樣子：sdPlan 的每一塊都在講外送追蹤：估算等於 estimate(INPUT)，有 deliveries 表、三個關鍵元件至少一個，深入的重點放在即時推送（'system-design#17'），失敗情境有處理斷線重連。

  1. 時間分配與需求（第 7 課的七個階段）：phases 順序不變、加總 45 分鐘，可以照抄；functional 改成外送追蹤的 3 條以上，nonFunctional 要有 latency 與 availability，target 都寫數字（例如「位置更新到顧客畫面 p95 < 3 秒」）。
  2. 估算（本課「步驟 5」的兩種算法）：estimates: estimate(INPUT)，不要手填。
  3. API 與資料表：apis 4～6 個，保留建立訂單 POST /orders（idempotencyKey: true），加上回報位置、查詢配送、訂閱位置等；tables 加 deliveries 表，至少一個索引。
  4. 架構與深入（本課的架構圖）：components 寫進「推送閘道」「位置寫入佇列」「最新位置快取」，寫法一字不差；deepDives 1～2 個，其中一個是即時推送（'system-design#17'）。
  5. 取捨與失敗：tradeOffs 3 條以上（例如 SSE 對 WebSocket），failureModes 3 條以上，至少一條寫斷線或重連怎麼處理（本課架構圖後面那段）。
卡住時的提示
  • 起始程式的點餐計畫只能當格式參考，裡面的數字、表、元件幾乎都要換。
  • 每個 tradeOffs 的 alternative 要和 decision 不同，cost 寫你為這個選擇付出的代價。

練習 5（步驟 6a）：比較兩個 offer，寫下權重 myWeights 和決定 decision。

做完的樣子：decision.ranking 是用你的權重算出來的 compareOffers 結果；choice 是其中一個 offer，理由至少 3 條，選的不是第一名時有一條「排名不同的原因：」；questionsAsked 問到 on-call、績效評估、技術債。

  1. 先定權重（本課「步驟 6」的「錢只是一個因素」那段；第 8 課的 compareOffers）：讀完註解裡的團隊訪談紀錄，填 6 個 0 以上的整數。先寫權重再算，不要算完再調。
  2. 算排名：ranking: compareOffers(OFFERS, myWeights)，不要手填。
  3. 做決定：choice 填 'douxiang' 或 'kuaisong'；reasons 至少 3 條、不重複。選排名第二的可以，但要有一條以「排名不同的原因：」開頭，寫出權重沒反映到的考量。
  4. 寫下問過的問題（本課「步驟 6」的「決定前在團隊訪談問清楚三件事」那段）：questionsAsked 至少各一題問到 on-call（或值班）、績效評估、技術債。
卡住時的提示
  • 執行會印出兩個 offer 的 annualComp，可以先對照本課的 offer 表，確認第一年和穩定年度的差別。
  • 測試用關鍵詞判斷問題：on-call／值班／輪值、績效／考核／升遷、技術債。

練習 6（步驟 6b）：寫第一年的學習計畫：先算每週學習時數上限 studyLimit，再填 12 個月的 plan12。起始程式的那一項是「學會 Kubernetes」，四個地方都不合格，要換掉。

做完的樣子：studyLimit 用 planCapacity 算出來（4 小時）；四季都有 1～2 個主題，每季時數加總不超過 studyLimit，每季至少連到一課 Learn；每項的完成條件別人看得到，四季的產出至少 2 種。

  1. 算上限（本課「步驟 6」的「最後是一年計畫」那段；第 9 課的 planCapacity）：Math.round(planCapacity(MY_WEEK).capacity * 25 / 100)。
  2. 排四季主題（本課「步驟 6」最後的「每一季的主題要回答三個問題」與「四季的順序」）：第 1 季先把缺口「2 年後端經驗」變成正式經歷，接著值班與效能、職缺的加分條件、主導設計。why.gap 從 GAP_OPTIONS 挑，Kubernetes 不在裡面。
  3. 連到課程：每項 lessonRefs 至少 1 個，寫存在的課號（例如 'devops#15'，CI）或 'external:主題'；每季至少 1 個 Learn 課號。
  4. 寫完成條件：output.doneWhen 要含數字，或含「發布」「合併」「分享」；output.kind 混合作品、文章、分享、開源貢獻。
卡住時的提示
  • 上限是 4，一季兩個主題就是 2＋2 或 3＋1；只排一個主題也可以。
  • 「學會 X」「熟悉 X」不算完成條件；「發布一篇部署紀錄」「1 個 PR 被合併」「團隊分享 30 分鐘」算。

練習 7：JD 的必要條件寫「2 年以上後端開發經驗」，你只有 4 年前端工作經歷和 Learn 的後端作品。最好的處理是？

✓ b：年資是參考值，證據比年資有說服力，但要誠實說明範圍。a 和 d 都是捏造，追問「上線後多少人在用、你們怎麼值班」就會露餡；c 太保守，必要條件缺一項通常仍值得投，這份 JD 還寫了「有相關作品可討論」。

練習 8：學習計畫寫「Q3：學會 AWS」。主要的問題是？

✓ b：計畫要能檢查。改成「用 OpenTofu 把作品部署到 AWS，repo 公開、README 通過第 3 課的檢查，並發布一篇部署紀錄」，再寫出它對應職缺的哪一條。a 錯在主題本身，這份 JD 把 AWS 列為加分條件；c、d 都不是問題的核心。

練習 9：兩個 offer：X 第一年總報酬較高（含 20 萬簽約金），Y 的穩定年度總報酬每年多 10 萬。只看錢，哪個說法正確？

✓ b：比較要看時間軸與條件。a 被一次性的簽約金誤導；c 忽略第一年 X 確實多，待不滿兩年的話 X 比較多；d 錯在簽約金是真的錢，該算進第一年，只是不能當成每年都有。只看錢之後，還要加上 on-call、成長等非金錢因素。

離開頁面要做的事

  • 在私人資料夾建立你自己的求職包：事實表（換成你的真實數字）、履歷主清單、兩張作品卡、故事庫、一份系統設計計畫。不要放進公開的 repo，裡面會有公司、同事與客戶的資訊。
  • 挑一份你真的想投的全端或中階後端 JD，照步驟 1 做缺口分析，再用 tailor 選出一頁的履歷。
  • 把兩個作品的 README 照練習 2 的骨架改好，跑過 auditRepo 再設成 public。
  • 排一次和朋友的模擬面試：45 分鐘的現場寫程式（演算法課第 27 課的流程）加 45 分鐘的系統設計（第 7 課），錄音回聽。
  • 在行事曆設每季一次的提醒：更新成果紀錄、事實表、故事庫與一年計畫。

常見錯誤

  • 材料彼此矛盾：履歷、作品、故事的數字不一致，面試官交叉比對時會發現。所有數字都從同一張事實表來。
  • 把學習專案說成正式工作：追問上線後的使用量就會露餡。誠實標示「練習專案」，談你的延伸與判斷。
  • 缺口補成假的：沒做過的寫成做過、把前端年資寫成全端、把作品算成工作經歷，第一個追問就答不出來。用相近的真實經驗與作品回應，或寫進計畫。
  • 轉職第一份就對準資深職缺：資深職缺看正式環境的經歷，作品補不了。先對準全端或中階後端，資深版本留到有正式經歷之後。
  • 被簽約金誤導：只比第一年總報酬。用穩定年度總報酬比較，簽約金另外看退回條款與預期待多久。
  • 學習計畫沒有產出：沒有完成條件的計畫無法檢查，也放不進下一份履歷。
  • 計畫超出容量：每週時數要在工作與 on-call 之外仍然做得到；做不到的計畫比沒有計畫更打擊士氣。

小結

  • 求職包要對著一個職缺做：缺口分析、履歷、作品、故事庫、系統設計計畫、offer 比較，所有數字都來自同一張事實表。轉職的第一份工作對準全端或中階後端。
  • 缺口分析把每一條必要條件對到有出處的證據；「沒有後端正式經歷」用工作裡碰過的後端事與作品回應，並寫進成長計畫，不補成假的。
  • 履歷用 tailor 對 JD 選句子；作品要展示不同的判斷，公開前只移除或修正有問題的檔案。
  • 故事庫要涵蓋六種能力，JD 裡最弱的證據最需要準備好的故事；Learn 專題的故事要標明是練習。
  • 系統設計題先用兩種方法估算互相驗證，再找出關鍵元件與取捨；長連線要主動講斷線重連。
  • offer 用穩定年度總報酬比較，簽約金看時間軸與退回條款；決定和排名不同時，寫出原因。
  • 一年計畫的目標是獨當一面：每季一個主題，對到缺口、連到課程、有可驗證的產出，時數在容量之內；第一季先把缺口變成正式經歷。

接下來可以學什麼：把作品專案課的兩個作品換進求職包；然後照你的一年計畫走。第一季從缺口最大、職缺最在意的那一項開始，每季回來更新求職包；Learn 之外的主題（例如雲端供應商的官方文件與認證教材），用 external: 的資源補上，並用同樣的方式寫出完成條件。
