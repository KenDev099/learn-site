階段 2：面試實戰 · 第 7 課

系統設計面試：45 分鐘的流程與限時演練（資深）

系統設計面試（system design interview）給你一個很大的題目，例如「設計一個咖啡店的線上點餐系統」，請你在 45～60 分鐘內，在白板或線上繪圖工具上說明系統怎麼做。沒有程式要寫，也沒有標準答案。資深職缺幾乎都有這一關，而且常常影響職級：其他關表現差不多時，設計面的表現會決定你被定在資深還是中階。

常見的失敗不是不會，而是時間和順序：一聽完題目就畫微服務、在 API 細節上講了 20 分鐘、到最後才發現沒時間講最重要的下單流程。這一課把系統設計課學過的東西，整理成 45 分鐘裡一步一步的做法。

這課的路線：
  1. 面試官在看什麼、45 分鐘的流程：題目故意模糊，看你怎麼把它變成能做決定的問題；需求、估算、API、資料模型、架構、深入、總結各給多少時間，每段要留下什麼。
  2. 需求與估算：先問問題，再從 DAU 算出尖峰 QPS、寫入量與一年的儲存量，用數字決定要不要快取、要不要分片。
  3. API、資料模型與高層架構：只寫關鍵的端點與表，從最簡單能動的架構開始，依數字一個一個加元件。
  4. 深入下單路徑：冪等、庫存並發、付款逾時、outbox，每一步說出做法、理由與替代方案。
  5. 總結與限時演練：用三句話收尾，自己做一次 45 分鐘演練，用程式替自己評分。
這課會用到：
  • 系統設計課第 1 課的需求與設計步驟：功能需求是系統要做什麼，非功能需求是要做到多好（多快、多可靠、多少人用）。
  • 系統設計課第 2 課的估算：從每日使用量除以一天 86,400 秒得到平均 QPS，乘上尖峰倍數得到尖峰；儲存量以 1 GB＝109 bytes 計。
  • 系統設計課第 9 課的冪等鍵：客戶端每次操作帶一把唯一的鍵，伺服器認出重送的請求，只執行一次。
  • 系統設計課第 12 課的 outbox：要送出的事件和資料修改寫在同一個交易裡，再由背景程序送進佇列，不會改了資料卻漏送事件。

面試官在看什麼

系統設計題刻意出得很模糊：「設計一個點餐系統」沒說多少人用、要多快、哪些功能要做。模糊是故意的，面試官想看你怎麼把一個模糊的問題變成可以做決定的問題。評分表（rubric，面試官評估時對照的清單）各公司不同，常見的面向是這些：

面向看什麼加分的表現扣分的表現
釐清需求動手前有沒有問清楚範圍與規模問使用者數、尖峰時段、哪些功能不做、一致性要求沒問就畫，設計建立在猜測上
估算能不能用數字支撐決定算出尖峰 QPS 和儲存量，用它們決定要不要快取、分片「量很大，所以用 Kafka」
API 與資料介面和資料表合不合理端點對應功能需求、建立訂單有冪等鍵、索引對應查詢花 15 分鐘寫每個欄位的型別
架構元件的組合能不能滿足需求從最簡單能動的開始，每加一個元件說出它解決的數字問題一開始就畫十個微服務
深入挑一個難點講到可以實作的程度下單流程講到並發、逾時、重試的每一步每個元件都講一點、都不深
取捨與風險知不知道自己的設計放棄了什麼主動說出代價、替代方案，以及什麼條件下會改只講優點；被問「掛了怎麼辦」才開始想
溝通與時間面試官跟不跟得上、時間有沒有失控每段開始前說要做什麼、每段結束時確認時間到了還在畫第一張圖

同一個題目，中階和資深的差別常常不在「知道多少元件」，而在誰主動。中階候選人說：「菜單加 Redis 快取。」資深候選人說：「菜單讀取尖峰約 313 QPS，命中 90% 的話打到資料庫的剩 31 QPS。代價是改價後最多 60 秒顯示舊價格，所以結帳時以資料庫價格為準。」面試官不用追問，就聽到了數字、代價和處理方式。

還有一點：整場由你主導。面試官像一位要一起做這個專案的同事，會回答你的問題、提出質疑，有時會把你帶往他想聽的方向。他明確轉向時跟著走，他想評的東西比你原本的計畫重要。

💡 實務上：面試前先問清楚這一關的形式
同樣叫「系統設計面試」，各公司差很多：有的用線上白板（Excalidraw、Miro 這類工具），有的只用共享文件打字；有的題目偏後端架構，有的給前端工程師出「設計一個元件庫或前端資料流」。收到面試通知時，直接問招募人員：時長多久、用什麼工具、題目偏向哪一層、評分看重什麼。先在那個工具上畫過一次圖，現場就不會花 5 分鐘找怎麼畫箭頭。

45 分鐘的流程

建議的時間分配如下。每一段結束時，白板上都要留下一樣具體的東西；時間到了還沒做完，就說一句「這部分我先停在這裡，深入時再回來」，然後往下走。現場的溝通方式（先講計畫、邊想邊說、接住提示）和第 5 課的現場寫程式相同。

階段分鐘白板上要留下什麼
需求53～5 條功能需求、2～4 條有數字的非功能需求、明確「不做」的功能
估算5DAU 與假設、平均與尖峰 QPS、讀寫比、一年的儲存量，寫在白板角落，後面一直引用
API54～6 個端點：方法、路徑、哪些要冪等鍵
資料模型5主要資料表、關鍵欄位、對應主要查詢的索引
高層架構10元件圖，加上一條主要請求從頭到尾的路徑
深入10一兩個重點的詳細流程、替代方案、失敗情境
總結5一句話的設計、主要風險與取捨、有更多時間會做什麼

時長不同時，主要放大深入段落。60 分鐘的面試可以分成需求 6、估算 6、API 6、資料模型 6、架構 12、深入 18、總結 6。很多面試開頭有幾分鐘自我介紹、最後留幾分鐘讓你發問，實際可用的時間可能只有 35～40 分鐘：開始時看一下時鐘，照比例縮短。估算段落有些面試官會說「不用算了，假設每秒 1 萬個請求」，那就把省下的時間給深入。

需求與估算：先問，再用數字說話

這一課的題目：「設計全台 300 家分店的咖啡店線上點餐系統。」聽完題目，第一句話是問問題，不是拿起筆畫圖。下面是一組問題，以及面試官可能的回答：

你問為什麼要問面試官回答
使用者是誰？要做哪些功能？決定範圍會員用 App 選門市、點餐、付款、到店取餐；門市要看到待做的訂單
外送、集點、推播要做嗎？把「不做」講清楚，省下時間這次不做外送和集點
每天多少人用？每人大約做幾次操作？估算 QPS 的起點DAU 50 萬，每人每天約 20 個請求（看菜單、查訂單、下單）
尖峰在什麼時候？高多少？容量要照尖峰算早上 7:30～9:30，約平均的 3 倍
讀寫比例？決定快取有沒有用約 10% 是寫入（下單、付款、取消）
一致性要求？錯了會怎樣？決定哪裡要強一致不能重複扣款、不能賣超過庫存；菜單晚一點更新沒關係
資料保存多久？每筆多大？估算儲存量線上保存 1 年；每筆寫入約 2 KB

把回答整理成需求寫在白板上。功能需求（系統要做什麼）和非功能需求（要做到多好）的分法是系統設計課第 1 課教的。非功能需求一定要有數字：「要很快」不能驗證，「尖峰時段下單 API 的 p99 小於 500ms」可以。p99 是把所有請求的回應時間排序後，第 99% 的那個值：100 個請求裡只有 1 個比它慢（系統設計課第 3 課）。

接著是粗估（back-of-the-envelope estimation）：用整數和幾個假設，在幾分鐘內算出量級。公式和系統設計課第 2 課一樣，只是面試時用「尖峰倍數」簡化：

  • 平均 QPS（每秒請求數）＝ DAU × 每人每天請求數 ÷ 86,400，無條件進位：容量寧可多估一點。
  • 尖峰 QPS ＝ 平均 QPS × 尖峰倍數。
  • 尖峰寫入 QPS ＝ 尖峰 QPS × 寫入百分比 ÷ 100，無條件進位。
  • 一年儲存量 ＝ 每天寫入筆數 × 每筆大小 × 365。儲存量看全天總量，不乘尖峰倍數：尖峰改變的是每秒的速度，不是一天寫了幾筆。

結果：平均 116 QPS、尖峰 348 QPS（寫入 35、讀取 313）、一年約 730 GB。接著要把數字變成決定，這是面試官最想聽的一段：

  • 寫入每秒幾十筆、一年幾百 GB：這個量級，單一 PostgreSQL（一台主要、一台備援）就放得下也寫得動（系統設計課第 7 課：分片要等單機撐不住才考慮）。現在分片，只會多出跨片查詢與維運成本。確切的上限要靠壓測，面試時說「這個量級單機可以，上線前用壓測確認」。
  • 讀取是寫入的 9 倍，而且多半是菜單：菜單很少變，適合快取（系統設計課第 5 課），能大幅減少資料庫讀取。
  • 說出觸發改變的門檻：「寫入成長到現在的 10 倍、或資料超過單機能舒服處理的大小時，先考慮讀副本（read replica：從主要資料庫複製資料、只負責讀取的資料庫，系統設計課第 6 課）和依時間分割資料表（PostgreSQL 課第 35 課），最後才是分片。」資深的答案不只說現在怎麼做，還說什麼時候要改。
估算時一律寫出假設（「每筆 2 KB」「尖峰 3 倍」），面試官可能會改其中一個數字，問你結論會不會變。有寫下來才能快速重算。也不要把時間花在小數點：116 和 115.74 的結論一樣，116 和 1,160 的結論不一樣。
💡 實務上：這套估算進公司後每年都會再用
面試裡的粗估，在工作中就是容量規劃：週年慶、新門市開幕、行銷活動上線前，維運和 PM 會問「系統撐得住嗎？」。資深工程師的回答方式和面試一樣：寫出假設（活動預計多少人、尖峰幾倍）、算出 QPS、對照壓測或監控上的實際容量，說出要不要加機器、哪裡會先撐不住。差別是工作中的數字要從監控與壓測拿，不能用猜的；假設被證明錯了，就更新文件重算。

API 與資料模型：只寫關鍵的部分

API 段落列出 4～6 個對應功能需求的端點，標出哪些需要冪等鍵（idempotency key）：客戶端為每一次「使用者意圖」產生一個唯一的鍵放在請求標頭，伺服器用它認出重送的請求，只執行一次（系統設計課第 9 課）。顧客在電梯裡按下結帳、網路斷了、App 自動重送，沒有冪等鍵就會建出兩張訂單、扣兩次錢。

方法路徑用途冪等鍵
GET/stores/{storeId}/menu門市菜單與價格不需要（讀取本身不改狀態）
POST/orders建立訂單並付款需要
GET/orders/{orderId}顧客查訂單狀態不需要
GET/stores/{storeId}/orders?status=paid門市的待做清單不需要
PATCH/orders/{orderId}門市更新狀態（製作中、完成）不需要：「設成完成」做兩次結果一樣

資料模型只寫主要的表、關鍵欄位，以及從查詢推出來的索引。上面兩個最常跑的查詢是「某門市的待做訂單」和「某顧客的訂單」，所以 orders 要有對應的兩個索引（索引設計見 PostgreSQL 課第 27 課）：

orders           (id, customer_id, store_id, status, total, created_at)
                 INDEX (store_id, status, created_at)   -- 門市待做清單
                 INDEX (customer_id, created_at)        -- 我的訂單
order_items      (order_id, product_id, quantity, unit_price)
stock            (store_id, product_id, qty)            -- 每家門市各自的庫存
idempotency_keys (key UNIQUE, request_hash, response, created_at)
outbox           (id, topic, payload, created_at, sent_at)

這兩段各只有 5 分鐘。欄位型別、錯誤碼、分頁格式這類細節，除非面試官追問，否則一句帶過。完整的版本在系統設計課第 22 課，面試時能講出它的骨架就夠了。

高層架構：從最簡單能動的開始

先畫出最簡單、能滿足需求的版本：App → 幾台無狀態的 API 伺服器 → PostgreSQL（主＋備援）。然後依數字一個一個加元件，每加一個都說出它解決的問題：

加的元件解決的數字問題代價
API 多台、無狀態尖峰 348 QPS，一台壞掉其他台要撐得住（N+1：撐住尖峰要 N 台，就多準備 1 台，系統設計課第 4 課）狀態要放在資料庫或 Redis
Redis 菜單快取讀取 313 QPS 多半是菜單；命中 90% 時打到資料庫的只剩約 31改價後最多 60 秒舊資料；結帳以資料庫價格為準
outbox＋佇列通知廚房、推播不能拖慢 p99 500ms 的下單路徑多一個元件要維運；通知可能晚幾秒
（先不加）讀副本、分片現在的數字不需要說出門檻：寫入或資料量到多少才加

畫完元件，用一條路徑走一次：「顧客按結帳 → API 檢查冪等鍵 → 同一個交易裡建訂單、扣庫存 → 呼叫金流 → 確認訂單並寫 outbox → relay 送進佇列 → 廚房收到單。」走一遍，你和面試官都能確認每個元件都有用到。

接著面試官常問：「流量變成 20 倍呢？」這時要找瓶頸（bottleneck）：負載增加時最先撐不住的元件。做法是算每個元件的使用率（負載 ÷ 容量），最高的那個就是瓶頸。不要等到 100% 才處理：使用率越接近滿載，排隊越嚴重、延遲越高，還要留空間給突然的流量，所以常用 70% 當作要動手的門檻。

用週年慶當例子：尖峰是平常的 20 倍，讀取 6,260 QPS、寫入 700 QPS。假設壓測結果是 API 一台撐 500 QPS、資料庫每秒讀 3,000、寫 800（真實系統要自己壓測，不能拿別人的數字）。下面算快取命中率對資料庫的影響：

深入與取捨：下單路徑

深入（deep dive）是選一兩個最關鍵或最難的部分，講到可以照著實作的程度。選哪裡？選「做錯會出大事」的地方。咖啡店題目裡，錢和庫存都在下單路徑上。可以直接問面試官：「我想深入下單路徑，因為重複扣款和超賣都在這裡發生，您同意嗎？還是您比較想聽別的部分？」

下單路徑分四步講，每一步說出做法、為什麼、替代方案：

  1. 冪等鍵：先查 idempotency_keys，同一把鍵已經完成就回傳上次的結果，執行中就回 409 請客戶端稍後再查（系統設計課第 9 課）。
  2. 庫存扣減的並發：兩個人同時買最後一個起司蛋糕。「先查庫存、再扣」會兩個都成功。改成一句條件更新：UPDATE stock SET qty = qty - 1 WHERE store_id = $1 AND product_id = $2 AND qty >= 1，更新到 0 列就是賣完了（PostgreSQL 課第 19 課）。
  3. 付款逾時：金流呼叫逾時，不代表付款失敗，請求可能已經到了金流、扣了款，只是回應沒回來。訂單保持 pending（待確認），用同一把冪等鍵重試或查詢付款結果；還是不確定就交給對帳排程（定期拿金流的交易紀錄比對訂單、補上正確狀態的背景工作）。確定付款失敗時，在同一個交易裡把訂單改成 failed、把扣掉的庫存加回去，不然庫存會被沒付錢的訂單佔住。直接判失敗，顧客會被扣錢卻沒有咖啡（系統設計課第 8 課）。
  4. outbox：付款成功後，「訂單改成已付款」和「寫一筆要通知廚房的事件」放在同一個資料庫交易裡，由 relay（一個背景程序，把 outbox 裡還沒送出的事件送進佇列）送出。不會出現訂單改了、廚房卻永遠收不到單（系統設計課第 12 課）。

每個決定用同一個句型說出取捨：「我選 A，不選 B，因為〔數字或需求〕；代價是 C；如果〔條件〕改變，我會改成 B。」例如：

決定替代方案代價什麼時候改
單一 PostgreSQL，不分片依門市分片寫入成長很多時要重新評估寫入使用率長期超過 70%，而且換大機器不划算
庫存用條件更新Redis 分散式鎖熱門商品的那一列會有鎖競爭限量活動每秒上千人搶同一個商品時，改成預先分配庫存
通知走 outbox＋佇列下單 API 裡同步呼叫多一個元件；通知晚幾秒幾乎不會改：同步呼叫讓廚房系統的故障變成結帳故障

最後主動說失敗情境，不要等面試官問。每一個依賴都問自己「它掛了或變慢，系統怎麼做、顧客看到什麼」：

  • PostgreSQL primary 掛掉：切換到備援的這段時間（假設要 1 分鐘，實際以演練測到的為準），下單回 503（服務暫時無法使用），加上 Retry-After 標頭告訴 App 幾秒後再試；菜單靠快取照常顯示。
  • Redis 掛掉：它是軟相依（soft dependency：壞了有替代做法，功能不會跟著壞），菜單改讀資料庫並限制同時查詢的數量，下單不受影響。
  • 金流變慢：重試要受整體時間預算限制、失敗率高就用斷路器（circuit breaker：失敗太多時暫時不再呼叫，直接回錯誤）快速失敗（系統設計課第 11 課），必要時降級成「到店付款」。
  • 某支 App 失控狂送請求：用限流擋下（系統設計課第 10 課），保護資料庫。
面試官質疑你的決定時，先別急著改。先確認他擔心的是什麼（「您擔心的是熱門商品的鎖競爭嗎？」），再用數字回答：現在的量不需要，說出到什麼程度要改、怎麼改。質疑通常是在測試你懂不懂自己的取捨，不一定代表你錯了。
💡 實務上：深入段落的說法，就是設計審查的說法
進公司後，寫設計文件（系統設計課第 18 課）和在設計審查會議上回答同事的質疑，用的是同一套句型：做法、替代方案、代價、什麼時候改。面試官在深入段落想確認的，就是你進來之後能不能主導這種討論。平常在工作裡練最有效：每次做技術決定時，用一句話寫下「我選 A 不選 B，因為…，代價是…」，累積下來也是第 4 課故事庫的素材。

總結與限時演練

最後 5 分鐘不要再畫新東西。用三句話收尾：這個設計一句話是什麼、主要的風險與取捨是什麼、有更多時間會深入哪裡。例如：「單一 PostgreSQL 加菜單快取、下單用冪等鍵和 outbox；風險是週年慶時寫入會先到瓶頸；有更多時間我會設計付款的對帳流程。」這比硬塞三個元件更有用，因為它讓面試官看到你知道設計的邊界與優先順序。

系統設計面試只能靠練習。一次演練的做法：

  1. 挑一個題目，手機計時 45 分鐘、開錄音，準備紙或線上白板。
  2. 假裝有面試官：把需求問題大聲說出來，自己給一個合理的回答並寫下來。
  3. 照時間表走；手機每 5 分鐘震動一次，提醒自己看進度。
  4. 結束後回聽錄音，填一份自評（練習 4 的 MockNotes）：每段花了幾分鐘、白板上留下了什麼、問了幾個問題、說了幾個取捨與失敗情境。
  5. 用練習 4 的 scoreMock 算分，下一次只專注改最弱的一兩段。

練習

練習 1 和 3 寫面試時要算的數字，練習 2 把整場面試的計畫寫成資料，練習 4 寫演練後的自評函式。後面四題選擇題練判斷。

練習 1：寫 estimate(input)，把面試時問到的數字換算成平均與尖峰 QPS、尖峰寫入 QPS 和儲存量。規則寫在起始程式的註解裡，照著寫才會和判分的結果逐位相同。注意哪裡無條件進位、哪裡四捨五入，儲存量不乘尖峰倍數，以及「先乘再除」（先除會產生浮點誤差，TypeScript 課第 5 課）。

練習 2：把課文的題目「全台 300 家分店的線上點餐」整理成一份面試計畫 plan。起始程式附了練習 1 的 estimate 和課文問到的數字 COFFEE_INPUT；規則寫在註解裡。內容可以用自己的話寫，測試只檢查結構、數字和每段該有的東西：分鐘數加總 45 而且深入至少 10 分鐘、估算要用函式算、建立訂單要有冪等鍵、每個取捨都有代價、深入只選一兩個。

練習 3：寫 nextBottleneck(load, capacity)，算出 API、資料庫讀取、資料庫寫入的使用率（千分比），回傳下一個瓶頸。起始程式附了課文的五個情境。注意快取命中的讀取不會到資料庫、門檻是「大於」700‰，以及同分時的順序。

練習 4：寫 scoreMock(notes)，替一次限時演練的自評算分，並找出最弱的一兩個階段。評分規則和每段要留下的東西（REQUIRED）寫在起始程式裡。注意每缺一項都要扣、超時的門檻是「超過 50%」、分數最低是 0，以及 weakest 最多 2 個。

練習 5：題目是「設計咖啡店線上點餐系統」，你的第一步是？

✓ b。需求與規模決定後面所有的選擇：沒問就畫架構，等於在猜題目。a 的架構可能完全不符合需求；c、d 都在還不知道要解決什麼問題之前就做了決定。

練習 6：估算結果尖峰寫入約 40 QPS、一年資料約 700 GB。資料庫怎麼決定？

✓ b。用數字選最簡單夠用的架構，並說出觸發改變的門檻，這正是面試官想聽的判斷。a 過早分片，跨片查詢與維運的成本從第一天就要付；c 沒有數字支撐；d 把訂單與付款這類不能遺失的資料放在記憶體資料庫，耐久性沒有交代。

練習 7：深入時面試官問：「付款服務逾時了怎麼辦？」最好的回答方向是？

✓ c。逾時時付款可能已經成功，只是回應沒回來。a 讓顧客和連線一起卡住，下單 p99 守不住；b 會讓已扣款的顧客重新下單、再扣一次；d 沒有冪等鍵和次數上限，可能重複扣款，也會放大金流的負載（系統設計課第 8、9、12 課）。

練習 8：時間剩 5 分鐘，你還有很多想講的元件。最好的做法是？

✓ a。總結讓面試官看到你知道設計的邊界與優先順序。b 硬塞內容，重點反而模糊；c、d 把收尾的機會讓掉了，面試官只能憑零散的印象寫評語。

離開頁面要做的事

  • 用手機計時器做一次 45 分鐘的完整演練，題目用本課的咖啡店點餐，錄音回聽，填 MockNotes 後用練習 4 算分。
  • 一週後換一個延伸題目（集點、外送追蹤或會員推播）再做一次，只專注改上次最弱的兩段。
  • 把練習 2 的 plan 改成你自己會講的版本，存在筆記裡，面試前看一次。
  • 找一位同事或朋友扮演面試官，請他在你講到一半時質疑一個決定，練習先確認對方的擔心、再用數字回答。
  • 投外商時，把需求問題和取捨句型各準備一份英文版，例如「What's the expected daily active users?」「I chose A over B because…, the cost is…」。

常見錯誤

  • 沒問需求就畫：設計建立在猜測上，畫得再漂亮也可能在解錯的題目。先花 5 分鐘問範圍、規模、不做什麼。
  • 沒有數字：「要很快」「量很大」沒辦法支撐任何決定。算出尖峰 QPS 與儲存量，寫在白板角落，每個決定都引用它。
  • 一開始就微服務、分片、Kafka：複雜度沒有數字支撐。從最簡單能動的開始，每加一個元件都說出它解決的數字問題。
  • 只有快樂路徑：資深面試一定會問「X 掛了怎麼辦」。深入時主動說出逾時、重試、冪等、降級。
  • 時間失控：在 API 細節花 20 分鐘，沒時間深入。每段開始前看時鐘，時間到就說「這部分先停在這裡」往下走。
  • 什麼都想深入：10 分鐘講五個重點，每個都只講到表面。選一兩個做錯會出大事的地方講透。
  • 被質疑就改答案：先確認對方擔心什麼，再用數字說明現在的選擇和什麼時候會改。

小結

  • 系統設計面試看的是釐清需求、估算、合理的架構、深入、取捨與溝通；沒有唯一正解，資深的差別在主動說出數字、代價與風險。
  • 45 分鐘的建議分配：需求 5、估算 5、API 5、資料模型 5、高層架構 10、深入 10、總結 5；時長不同時主要放大深入。
  • 估算：平均 QPS ＝ DAU × 每人請求數 ÷ 86,400（無條件進位），尖峰乘倍數，儲存量看全天總量、不乘尖峰；寫出每個假設。
  • 用數字選最簡單夠用的架構，並說出觸發改變的門檻；每加一個元件都說出它解決的數字問題與代價。
  • 瓶頸看使用率（負載 ÷ 容量），不看請求數；解決一個瓶頸，下一個就會出現。
  • 深入選做錯會出大事的地方：下單路徑的冪等鍵、庫存條件更新、付款逾時不等於失敗、outbox。
  • 取捨句型：「選 A 不選 B，因為…；代價是…；如果…改變，我會改成 B。」
  • 最後 5 分鐘總結設計、風險與下一步；每次演練後自評，下一次只改最弱的一兩段。
