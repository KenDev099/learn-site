階段 2：面試實戰 · 第 6 課

帶回家作業：範圍、測試、README 與取捨說明

帶回家作業（take-home assignment）是公司寄一份題目給你，讓你在自己的電腦、自己的時間做完再交回去，例如「做一個點餐 API，建議花 4 小時」。它跟第 5 課的現場寫程式不同：沒有人在旁邊看，評審只看得到你交出去的東西。所以你怎麼想、為什麼這樣做、哪些刻意沒做，全部要寫在 repo 裡。

很多人做作業的方式是「把功能做越多越好」，結果時間不夠、沒有測試、README 只有一行，評審跑不起來就打了低分。這一課教你把作業當成一個小型專案來交付。範例用 NestJS 課的技術棧（NestJS＋Prisma＋PostgreSQL），版本以 NestJS 課為準。

這課的路線：
  1. 評審在看什麼：他打開 repo 的順序，以及為什麼「說明哪些沒做、為什麼」跟做了什麼一樣重要。
  2. 先讀題，再寫範圍計畫：開專案前花 10～15 分鐘列出必做、選做、不做，並保留收尾的時間。
  3. 釐清與假設、做的順序：題目沒說清楚的地方怎麼問、怎麼寫成假設；用垂直切片、測試與 commit，讓任何時候交出去都是能跑的版本。
  4. README 與交件前檢查：寫出評審 10 分鐘看得懂的 README 與取捨說明，避開過度設計這類常見扣分。
  5. 資深視角：判斷一份作業合不合理，太長或像免費工作時怎麼問、怎麼婉拒。
這課會用到：
  • 第 3 課的作品 README 與 parseSections：README 依讀者的順序排段落；parseSections 把 Markdown 依標題切成一段一段，練習 2 直接拿來用。

評審在看什麼

評審通常是團隊裡的工程師，手上有自己的工作。他打開你的 repo，大約依下面的順序看，每一關都可能是最後一關：

評審在看他怎麼確認扣分的樣子
跑不跑得起來照 README 的指令在自己電腦執行一次第二步就報錯，缺 .env、缺套件、版本不對
需求有沒有做對對照題目的需求一條條試做了很多額外功能，卻漏掉題目寫的庫存不足要拒絕
有沒有測試執行測試指令，看測了什麼沒有測試，或只有框架產生的範例測試
程式結構翻幾個檔案：分層、命名、錯誤處理所有邏輯塞在一個 controller，或為了 4 小時的作業拆成 5 層抽象
判斷讀 README 的假設、取捨、沒做的事沒寫，評審只能猜你是刻意不做還是漏掉

最後一列最容易被忽略，卻是資深職缺最在意的。兩個人都沒做分頁，一個在 README 寫「分頁沒做，因為時間優先給了並發測試；要做的話我會用 cursor 分頁（NestJS 課第 16 課），理由是……」，另一個什麼都沒寫。前者展示了判斷，後者看起來像漏掉了。功能多不等於分數高：評審要的是「在有限時間內做對重要的事，並說得清楚」。

先讀題，再寫範圍計畫

這一課用同一份題目當例子：

咖啡店點餐 API（建議花 4 小時，請在 7 天內交回 GitHub repo 連結）

R1 建立訂單：顧客選商品與數量下單
R2 查詢訂單：用訂單 id 查訂單內容與總金額
R3 下單時扣庫存；庫存不足要拒絕，不能賣超
R4（加分）查詢某位顧客的訂單列表
R5 資料要能持久保存，資料庫自選
R6 不合法的輸入回 400，錯誤訊息要看得懂

拿到題目不要馬上開專案。先花 10～15 分鐘做三件事：

  1. 把需求編號（像上面的 R1～R6）。之後的任務、測試、README 都用編號對回需求，評審一眼就能對照。
  2. 拆成任務並估時間。用工程實務課第 3 課的方法，每個任務估一個分鐘數。估不準沒關係，重點是把整體加起來跟時間上限比。
  3. 標優先序。常用的分法叫 MoSCoW：must（一定要做）、should（應該做）、could（有時間才做）、won't（這次不做）。這一課用前三個，放不進時間的就是 won't。

這裡有兩個新名詞。範圍（scope）是這次要做與不做的事；時間盒（timebox）是先決定花多少時間，時間到就收尾，而不是「做完為止」。作業寫「建議 4 小時」，就是給你一個時間盒：評審會用「4 小時能做到這樣」的標準看，你花 12 小時做出來的東西，評審不知道，或知道了反而扣分。

咖啡店題目拆出來的任務：

接著算時間。4 小時是 240 分鐘，先扣掉 20% 當收尾時間：寫完 README、把 repo clone 到一個乾淨的資料夾照 README 從頭跑一次、修掉跑不起來的地方。這段時間最常被吃掉，所以一開始就扣掉，不要指望「最後再擠」。

必做 160 分鐘，剩 32 分鐘。依 should、could 的順序，短的先放：並發測試 20 分鐘放得進去（剩 12）；訂單列表 35 分鐘放不進去，但這時不要停，繼續看下一個：OpenAPI 文件 10 分鐘還放得進去（剩 2）；其他都放不進去。結果是：

如果必做加起來就超過可用時間呢？那代表題目的範圍和時間對不上，先跟對方溝通，不要默默做到 8 小時：「我估必做部分約 5 小時，超過建議的 4 小時。是否可以把 R6 簡化成只驗證必填與數量範圍？或者我照完整範圍做，README 會寫實際花費時間。」練習 1 會把這套規則寫成程式。

R4 被放到「不做」看起來很可惜，但想想評審的角度：R3 的並發測試證明你的系統不會賣超，這是後端最難、也最能看出功力的部分；列表查詢誰都會寫。把 R4 的做法寫進 README 的「沒做的事」，評審照樣知道你會。

💡 實務上：範圍計畫就是你上班後的估工
收到作業的同一套做法，進公司後每個 sprint（團隊固定一到兩週的開發週期）都會用：PM 丟來「做顧客訂單列表」，你先把需求編號、估時、分出 must 和 won't，再跟 PM 對齊。作業裡寫進 README 的「不做」，在工作中就是寫進 ticket（追蹤工作的單子，例如 Jira）的「這次不含」。資深工程師拿到時程時會先問：「哪一條最不能少？」然後把風險最大的那一條排在最前面。範圍砍不下來時，用數字說話：「必做估 5 小時，時間盒是 4 小時，請選一條延後。」

釐清與假設

題目一定有沒說清楚的地方：要不要登入？一筆訂單最多幾項？商品下架了還能不能買？金額要不要含稅？遇到這種地方，順序是：

  1. 能問就問。大部分公司歡迎你問，有些評審甚至把「有沒有問」當評分重點。把問題集中成一封信，一次寄出，不要想到一個寄一個：
您好，我開始做點餐 API 作業了，想確認三件事：
1. 需要身分驗證嗎？如果不用，我會讓 customerId 由請求帶入。
2. 一筆訂單的品項數與數量有上限嗎？如果沒有，我會設最多 20 項、每項 1～10 杯。
3. 可以使用 AI 程式助手嗎？如果可以，我會在 README 註明用在哪裡。
如果這幾天不方便回覆，我會照上面的做法進行，並寫在 README。謝謝！
  1. 不能問、或等不到回覆，就寫成假設。假設（assumption）是題目沒說清楚時你自己做的決定。每一條假設要寫出「我假設什麼」和「這個假設影響了什麼」，例如：「假設不需要身分驗證：customerId 由請求帶入。正式環境要從登入資訊取得，否則任何人都能用別人的名義下單。」

上面那封信每個問題都附上「如果不行，我打算怎麼做」，對方只要回「可以」就好，你也不用停下來等。

假設要選合理且最小的那個。題目沒提身分驗證，就不要自己做一套完整的 OAuth：多花 2 小時，評審還得多讀一堆不在題目裡的程式。也不要什麼都不說，評審會以為你沒想到。

AI 工具：先問規則，用了就寫出來

2026 年各公司對作業能不能用 AI 程式助手的規定不同：有的允許、有的明文禁止、有的沒寫。題目沒寫就問（上面那封信的第 3 點）。可以用的話，照工程實務課第 9 課的做法：每一段產出都自己讀懂、用測試驗證，並在 README 寫出用在哪裡、怎麼驗證，例如「用 AI 產生 DTO 與 E2E 測試的初稿，逐行檢查後修改了數量上限與錯誤訊息；並發扣庫存的邏輯是我自己寫的」。

不管能不能用，有一條規則不變：交出去的每一行，你都要能在下一關面試時解釋。很多公司的下一關就是請你分享螢幕，一起看你的作業、問「這裡為什麼這樣寫」「如果要加 R4 你會改哪裡」。說不出來，比作業沒做完更糟。

做的順序：切片、測試、commit

常見的失敗是「先把所有 model 寫完、再寫所有 service、最後串 controller」，到第 3.5 小時才第一次跑起來，結果有 bug、沒時間修。改用工程實務課第 2 課的垂直切片：先讓一條最細的流程從 HTTP 一路通到資料庫，再一層層加東西。

  1. 骨架能跑：docker compose up 起資料庫、App 能啟動、一個健康檢查端點（NestJS 課第 24 課）回 200。
  2. 主流程一條龍：POST /orders 寫進資料庫、GET /orders/:id 查得到，加一個 E2E 測試鎖住它。
  3. 加重要的規則：扣庫存與庫存不足（R3）、輸入驗證（R6），每加一條規則就加對應的測試。
  4. 選做：時間還夠才做。
  5. 收尾：README、從乾淨資料夾重跑。

這樣做的好處是：任何時候時間到了，你手上都是一個能跑、有測試的版本，只是功能少一點。

測試寫哪一種？作業時間有限，CP 值最高的是 NestJS 課第 10 課的 E2E 測試：從 HTTP 打進去、接真的資料庫，一個測試就驗證了路由、驗證、商業邏輯和資料庫。至少涵蓋：

  • 主流程：下單成功、查得到、總金額對（2 杯拿鐵＋1 個可頌 = 110 × 2 + 70 = 290 元）。
  • 題目明寫的規則：庫存不足回錯誤、庫存沒有被扣成負數；不合法的輸入回 400。
  • 有時間再加：並發。20 個請求同時搶剩 5 杯的商品，只能成功 5 筆、庫存剛好歸零（NestJS 課第 15 課）。這個測試一放上去，評審就知道你懂並發。

commit 歷史也是作品的一部分。評審會看你是一步步做出來的，還是最後一次倒進來。每完成一個小步驟就 commit，訊息寫做了什麼：

不好的歷史好的歷史
init
update
fix
final
final2		建立 NestJS 專案與 Compose 的 PostgreSQL
新增訂單 schema 與 migration
POST /orders 與 GET /orders/:id，含 E2E 測試
下單時用條件更新扣庫存，庫存不足回 409
DTO 驗證：數量 1～10、最多 20 項
並發測試：20 個請求搶 5 杯只成功 5 筆
README：假設、取捨與沒做的事

上面「庫存不足回 409」的 409 Conflict 是「請求跟資源目前的狀態衝突」的狀態碼（Node 課第 14 課）：請求本身格式正確，是庫存不夠，所以不用 400。

不要在交件前把所有 commit 壓成一個（squash）：那等於把過程藏起來，評審會懷疑你在藏什麼。

README 與取捨說明

第 3 課的作品 README 寫給「想認識你的人」；作業 README 寫給「拿著評分表、只有 10 分鐘的評審」。所以段落要直接對應評審的問題：

段落回答評審的問題
執行方式我要打哪幾行指令才能跑起來？需要先裝什麼？
測試怎麼跑測試？測了什麼？
功能每一條需求做了沒有？
假設題目沒說清楚的地方，你怎麼決定的？
設計決定與取捨為什麼這樣做？考慮過什麼？代價是什麼？
沒做的事哪些刻意沒做、為什麼、要做的話怎麼做？
花費時間實際花了多久？有沒有超時？

先看一個不好的版本：

# cafe-api
NestJS + Prisma + PostgreSQL

## 執行方式
npm install
npm run start:dev

## 沒做的事
無

評審照做會發生什麼：沒有資料庫（沒說要先起 PostgreSQL）、沒有 .env（不知道連線字串）、不知道怎麼測試。「沒做的事：無」更糟：R4 明明沒做，這樣寫等於說你沒發現。好的版本：

# 咖啡店點餐 API（帶回家作業）

## 執行方式
需要 Node.js 24 與 Docker。
```bash
cp .env.example .env
docker compose up -d --wait
npm ci
npx prisma migrate deploy
npm run start
```
打開 http://localhost:3000/docs 看 API 文件。

## 測試
```bash
npm run test:e2e   # 9 個：下單、查詢、庫存不足、並發搶最後 5 杯、驗證錯誤
```

## 功能
- R1 建立訂單 POST /orders：完成
- R2 查詢訂單 GET /orders/:id：完成
- R3 扣庫存、不賣超：完成，有並發測試
- R4 顧客訂單列表：沒做，見「沒做的事」
- R5 PostgreSQL：完成；R6 驗證錯誤回 400：完成

## 假設
- 不需要身分驗證：customerId 由請求帶入。正式環境要從登入資訊取得。
- 每筆訂單最多 20 項、每項 1～10 杯：題目沒寫上限，設上限避免一張單扣光庫存。

## 設計決定與取捨
- 扣庫存用交易裡的條件更新（stock >= 數量才扣，更新筆數是 0 就回 409），
  不用「先查再扣」：兩個請求同時搶最後一杯時，先查再扣會賣超。
  代價：庫存不足時只知道「不夠」，要再查一次才知道剩幾杯。

## 沒做的事
- R4 訂單列表：時間優先給 R3 的並發測試。要做的話用 cursor 分頁，依 (ordered_at, id) 排序。
- 下單冪等鍵：正式環境需要，避免網路重試造成重複下單。

## 時間
花費時間：4 小時（讀題與寄問題信另外約 20 分鐘）

幾個重點：

  • 執行方式要能整段複製貼上。放在 ``` 程式區塊裡，一行一個指令，不要寫成散文。npm ci 依 package-lock.json（lockfile，Node 課第 3 課）安裝鎖定的版本（npm 官方文件：沒有 lockfile 或 lockfile 和 package.json 對不上時會直接報錯），比 npm install 更能保證評審裝到跟你一樣的版本，所以 lockfile 一定要 commit。需要的環境變數放 .env.example：列出要設哪些變數、只放本機能用的假值，不放真正的密碼（NestJS 課第 11 課）；真正的 .env 不進 git。
  • 功能段落用需求編號，一條一條寫「完成／沒做」。
  • 「沒做的事」一定有內容。4 小時的作業不可能什麼都做完，寫「無」只會讓評審覺得你沒看出來。
  • 寫出花費時間。超時沒關係，誠實寫出來並說明原因（「花了 5 小時，其中 1 小時在處理 Prisma 的交易逾時」）；不寫、或寫 4 小時其實做了 12 小時，下一關被問到細節就露餡。

取捨怎麼寫

取捨（trade-off）是「選了 A、放棄 B」的理由與代價。只寫「使用 PostgreSQL」不是取捨，那只是事實。用系統設計課第 18 課 ADR 的精簡版，每條寫五件事：

欄位R3 扣庫存的例子
決定交易裡用條件更新扣庫存（stock >= 數量 才扣）
考慮過的替代方案先查再扣；SELECT … FOR UPDATE 先鎖再扣（PostgreSQL 課第 19 課）；Redis 分散式鎖
為什麼一句 SQL 就不會賣超，不用另外管鎖；只有一個資料庫，不需要 Redis
代價庫存不足時不知道剩幾杯，錯誤訊息要再查一次
什麼時候要重新考慮熱門商品同時搶的人多到資料庫的列鎖成為瓶頸時（UPDATE 會鎖住那一列，同時搶同一個商品的請求要排隊）

「代價」最常被寫成「無」。每個決定都有代價，寫不出代價通常代表沒想過替代方案。「什麼時候要重新考慮」讓評審知道你看得到這個決定的邊界，這正是資深評審想看的。練習 3 要你為這份作業寫出 4 條取捨。

💡 實務上：取捨寫在 PR 描述裡，審查的人才不用猜
上班後這五欄最常出現在 PR 描述：例如上面扣庫存那一條，原樣濃縮成兩三句放進 PR，審查的人就不必在留言裡來回問「為什麼不用 X」。半年後有人看 git 紀錄想改回去，這段說明就是他的線索。不是每個 PR 都要寫：改文案、修錯字不用；動到資料、金額、權限或換套件時才值得寫。資深工程師審 PR 時常問的一句就是「你考慮過什麼別的做法？」

練習 2 會寫一個 README 檢查器，用第 3 課的 parseSections 找出缺的段落、空的段落、執行指令有幾行，以及有沒有寫花費時間。花費時間的規則要寫得夠嚴格：「花費時間：很多」不算，因為評審要的是數字。

交件前：常見扣分與檢查

README 寫好之後，交出去之前對照下面這張表，逐項擋掉評審最常扣分的地方：

扣分原因交件前怎麼擋
跑不起來缺 .env.example、沒 commit lockfile、指令依賴你電腦上已經裝好的東西（例如本機剛好有 PostgreSQL）clone 到一個新資料夾，照 README 一字不改從頭跑；資料庫一律放 Docker Compose
沒有測試想說最後再補，結果沒時間測試列在 must，跟著功能一起寫
過度設計為了展示技術，把 4 小時的作業做成微服務、加 Kafka（訊息佇列系統）、加 Kubernetes（管理大量容器的平台）每個元件都要對得到某一條需求；對不到的寫進 README「規模變大時會怎麼做」
超時很多卻沒說覺得說了會扣分寫在 README 的花費時間，說明原因
機密進了 repo.env 被 commit用第 3 課的公開前檢查

過度設計（over-engineering）是為了不存在的需求增加複雜度。它在作業裡特別傷：評審要多花時間讀與執行，而且會懷疑你的判斷。資深的做法是選夠用的最簡單方案，再用一句話說出「規模變大時我會怎麼拆」（系統設計課第 15 課）。

最後一步一定要做：git clone 你的 repo 到一個全新的資料夾，照 README 從第一行執行到最後一行，再跑一次測試。只在原本的資料夾測過，常常會漏掉沒 commit 的檔案或只存在你電腦上的設定。
💡 實務上：「從乾淨資料夾跑一次」就是新人上手的第一天
評審照 README 跑你的 repo，跟新同事第一天照 README 建開發環境是同一件事。團隊裡常見的狀況是：README 寫的指令早就過時，新人花兩天問人才跑起來。資深工程師會把「clone 下來照 README 能跑」當成 repo 的驗收條件，有人改了環境設定（新增環境變數、換資料庫版本）就順手更新 .env.example 和 README；能放進 CI（每次 push 自動跑測試與檢查的流程）的，就不要靠人記得。

資深視角：判斷與作業的合理性

同一份作業，初階和資深的評審看的重點不同。初階看「做出來了沒」；資深評審特別看判斷：

  • 知道什麼不做：範圍計畫裡有 won't，而且每一項都說得出理由。
  • 把風險放前面：最難、最容易出錯的部分（這份題目是 R3 的並發）先做、先測。
  • 想到正式環境：在「沒做的事」寫出上線前還缺什麼（冪等鍵、監控、身分驗證），但不在作業裡做。

你也在評估這家公司。作業本身透露了團隊怎麼對待別人的時間。以下情況可以禮貌地詢問：

狀況可以怎麼說
預估超過 8 小時，或沒有時間建議「我估這份題目需要約 12 小時。請問建議花多少時間？是否可以縮小範圍，或改成現場一起討論設計？」
題目看起來是公司真正要上線的功能（例如要你串他們正式環境的 API、題目寫著「完成後我們會使用」）「想確認這份作業的程式碼權利與用途。」如果確定是拿去用，可以婉拒並說明原因
同時有好幾家公司的作業，時間排不過來主動說明並問能不能延後交件，大部分公司接受；不要用超時趕工來換

婉拒不等於失禮：「這份作業的時間超出我目前能投入的範圍，如果有其他評估方式（例如現場寫程式或討論過去的專案），我很樂意參加。」有些公司會改用其他方式評估，有些不會；那是你在決定這家公司值不值得投入。

練習

三題都用課文的咖啡店作業。練習 1 寫範圍規劃、練習 2 寫 README 檢查器、練習 3 寫取捨說明。

練習 1：寫 planScope(tasks, budgetMinutes)，把課文「先讀題，再寫範圍計畫」那一節的做法寫成程式。規則寫在起始程式的註解裡；注意兩件事：放不下的任務不要讓後面的任務沒機會，以及不能改到傳進來的陣列。

練習 2：寫 checkReadme(md)，檢查作業 README 是否寫齊評審要的段落。第 3 課寫好的 parseSections 已經放在起始程式裡，直接用它切段落，不要自己重寫（還記得程式區塊裡的 ## 不是標題）。其他規則寫在起始程式的註解裡。

練習 3：為課文的咖啡店作業寫取捨說明，填 notes。起始程式已經有一條 R4 的範例，你要再寫至少 3 條，一共至少 4 條，而且三個關鍵決定要各寫一條：R3 扣庫存的並發做法、R5 資料庫的選擇、R6 驗證做到什麼程度。程式只檢查結構與規則（寫在起始程式的註解裡），不評你的文字；寫完自己讀一次，想像評審會不會被說服。

練習 4：4 小時的作業，你做到第 3.5 小時才把功能做完，還沒有測試，也還沒寫 README。最好的做法是？

✓ b：評審最先看的是能不能跑、能不能驗證、判斷清不清楚，最關鍵路徑的測試和 README 比多一個功能有價值。a 隱藏超時，下一關被問到細節就露餡；c 評審只有 10 分鐘，沒有 README 連怎麼執行都不知道；d 把過程藏起來，評審會懷疑你在藏什麼。下次要在一開始就扣掉收尾時間。

練習 5：題目沒說要不要做身分驗證。你應該？

✓ b：沒說清楚的需求是判斷題，問或寫下假設，讓評審知道這是刻意的決定。a 多花好幾個小時做題目沒要的東西，是過度設計；c 評審看不出你是刻意不做還是沒想到；d 可以在問題信裡附上「如果不行我打算怎麼做」，不用停下來等。

練習 6：一份標明 4 小時的作業，你決定做成 3 個微服務，用 Kafka 傳訊息。評審最可能怎麼看？

✓ b：資深的判斷是選夠用的最簡單做法，每個元件都要對得到需求。評審要多花時間把三個服務和 Kafka 跑起來，4 小時也很難把它們都做好、測好。想展示你懂拆分，在 README 寫「規模變大時會怎麼拆」就夠了。a、d 把技術清單當成能力；c 忽略了評審也在看判斷。

練習 7：一家公司寄來的作業沒寫建議時間，你估要 15 小時，內容是「串接我們的會員系統 API，完成點數兌換功能」。比較合適的回應是？

✓ c：超過 8 小時、又像是要上線的真實功能，詢問與協商是合理的，對方怎麼回應也讓你看到這家公司怎麼對待別人的時間。a 投入過多，還可能是在做免費工作；b 不回覆沒有禮貌，也失去協商的機會；d 自行縮小範圍可以，但一定要在 README 說明範圍與理由，不說明會被當成沒做完。

離開頁面要做的事

  • 用課文的咖啡店題目，自己做一次 4 小時的作業：先花 15 分鐘寫範圍計畫（可以直接用練習 1 的程式算），用手機計時器設時間盒，時間到就收尾。
  • 收尾時用練習 2 的檢查器檢查 README，再把 repo clone 到新資料夾照 README 從頭跑一次。
  • 請朋友或同事當評審，只給他 10 分鐘：跑起來了嗎？看得懂你為什麼這樣做嗎？他問的每個問題，都是 README 少寫的地方。
  • 把這次的作業留著。下一次收到真正的作業時，你已經有一份 README 範本和一套收尾的流程。

常見錯誤

  • 跑不起來：沒有 .env.example、沒 commit lockfile、資料庫依賴你電腦上已經裝好的。交件前 clone 到乾淨的資料夾，照 README 從頭跑一次。
  • 沒有測試：至少要有主流程與題目明寫的規則（例如庫存不足）。測試列在必做，跟著功能一起寫，不要留到最後。
  • 沒留收尾時間：功能做到最後一分鐘，README 只剩一行。一開始就扣掉 20% 的收尾時間。
  • 過度設計：作業要展示判斷，不是技術清單。每個元件都要對得到需求，其他的寫進 README 的「規模變大時」。
  • 沒寫假設與沒做的事：評審會當成你漏掉了。「沒做的事：無」比不寫還糟。
  • 隱藏超時或過程：不寫花費時間、把 commit 壓成一個。誠實寫出來並說明原因，下一關才答得出細節。
  • 交出自己解釋不了的程式：不管有沒有用 AI，每一行都要能在面試時說明為什麼。

小結

  • 評審看的順序：跑得起來、需求做對、有測試、結構清楚、判斷寫得清楚。功能多不等於分數高。
  • 拿到題目先把需求編號、拆任務估時、用 must／should／could 排優先序；先扣 20% 收尾時間，必做放不下就先溝通。
  • 題目沒說清楚的地方能問就問，問題信附上「不行的話我打算怎麼做」；問不到就寫成假設並說明影響。AI 工具先問規則，用了就寫出用在哪裡、怎麼驗證。
  • 用垂直切片推進，任何時候手上都是能跑、有測試的版本；E2E 測試 CP 值最高；每個小步驟一個 commit。
  • README 寫給只有 10 分鐘的評審：執行方式、測試、功能對應需求、假設、取捨、沒做的事、花費時間。取捨要寫出替代方案、代價與什麼時候重新考慮。
  • 資深的判斷是知道什麼不做；作業太長或像是免費工作時，可以詢問、協商或婉拒。
