每一關評的都是過程，不只是答案。行為面試看你做了什麼，現場寫程式看你怎麼想；作業看你知道什麼不做，系統設計看你用數字說出取捨。[回 面試與職涯 學習地圖](../index.html)

## A STAR：把一件事講成兩三分鐘 {span=2}
```timeline h
約 25 秒 | S 情境 | 只講聽懂故事需要的背景
15 秒 | T 任務 | 你在這件事裡的責任
*約 100 秒 | A 行動 | 主詞是「我」：做了什麼、為什麼
約 40 秒 | R 結果＋學到 | 有數字，再補一句學到什麼
```
| 段落 | 這課的示範：尖峰重複扣款 |
|---|---|
| S | 週六早餐尖峰，付款閘道變慢，訂單服務逾時後自動重試，部分顧客被扣了兩次 |
| T | 我是訂單服務的開發者，也是當天的值班工程師 |
| A | 我先暫停自動重試止血；寫退款腳本用對帳檔比對，退回 37 筆；在付款 API 加冪等鍵；加重複扣款率告警；寫事後檢討、補上線檢查清單 |
| R | 之後 3 個月，尖峰重複扣款率從 1.2% 降到 0；學到重試一定要搭配冪等鍵 |

團隊做的事說清楚分工。記重點與數字，不逐字背稿：被追問打斷一次就接不回去。

## B 故事庫：六種能力
| 能力 | 常見問法 | 面試官想看什麼 |
|---|---|---|
| 衝突 | 和同事意見不合 | 怎麼理解對方、用資料取得共識 |
| 失敗 | 你搞砸的事 | 承認責任、補救、之後改了什麼 |
| 主導 | 沒人負責、你接下來的事 | 有沒有接起來做到完 |
| 影響力 | 怎麼說服團隊採用提案 | 不是主管也能讓別人改變做法 |
| 模糊 | 需求不清楚時怎麼開始 | 把模糊目標變成可開工、可驗收的範圍 |
| 帶人 | 怎麼帶新人 | 讓別人變強 |

準備 6～8 個故事，每個標 1～3 種能力，每種至少一個故事；一場行為面試通常問 4～6 題。資深的故事範圍更大、說得出取捨、透過別人達成，也講得出自己改變想法的時候。

## C 開場題、追問、失敗與衝突
```kv cols=1
自我介紹: 1～2 分鐘，分現在、證據（有數字的成果）、未來（為什麼是這個職缺）
為什麼離職: 講你想要什麼，不批評前公司
為什麼轉後端: 用做過的事回答，不用形容詞：前端工作裡碰到的後端問題（例如結帳頁重複送出）、作品裡自己解決的後端問題、接下來要補什麼；前端經驗是優勢，不用道歉
追問: 每個故事準備三個預期的追問，例如你做了哪部分、為什麼選這個做法、數字怎麼量的
失敗題: 選真的失敗；改了什麼比錯了什麼重要
衝突題: 對方的理由講得合理，講怎麼取得共識；沒共識就 disagree and commit
```
```callout warn 不要這樣答
「我太追求完美」這種假缺點；「後來主管支持我」把決定交給別人；不記得的數字就說「大約」，不要編。
```

## D 現場寫程式：45 分鐘的流程 {span=2}
| 階段 | 分鐘 | 要做完的事 |
|---|---|---|
| 釐清與舉例 | 5 | 重述題目、問輸入範圍與邊界、舉一個例子對答案 |
| 思路與複雜度 | 8 | 說出暴力解與 Big-O、為什麼不夠、改進後的 Big-O；面試官同意再寫 |
| 寫程式 | 20 | 邊寫邊說，先寫主流程 |
| 測試與修正 | 7 | 用小例子手動執行、檢查邊界、修 bug |
| 總結與問答 | 5 | 最終複雜度、取捨、正式環境還會加什麼 |

評分面向：釐清、解法與複雜度、溝通、程式品質、測試、接提示；答案正確只是其中一部分。時長不同就照比例換算。

```flow LR
(卡住) -> [承認卡住] -> [說出已知的部分] -> [說出考慮中的方向] -> *[接住提示：先複述再調整]
```
沉默不超過 1 分鐘。好的測試案例要能讓錯的實作失敗，也要檢查有沒有改到輸入。讀程式找 bug 要回報行號、問題、修法、證明的案例；在既有程式加功能先讀測試、小步修改。

技術概念問答（本土公司與中階職缺常見，口頭或線上筆試）用四段回答，約 40 秒：結論（第一句直接回答）→ 原因 → 取捨（另一個做法與代價）→ 實例（作品或練習，說明是練習）。不從定義背起；不會的說出已知的部分和怎麼查證，不要編。題庫是各技術課的「階段檢核」，遮住選項自己講一遍再對照解說。

AI 工具開始前問清楚，沒說可以就不用；被允許時，重點是你怎麼驗證它的產出。資深面試多看可讀性、不改輸入、明確的錯誤處理，以及「正式環境我還會加什麼」。

## E 帶回家作業：範圍與時間盒
這課的示範：建議 4 小時的點餐 API 作業。

```kv cols=1
時間盒: 240 分鐘
先扣收尾 20%: 48 分鐘，寫 README、從乾淨資料夾重跑
必做（must）: 160 分鐘：R1 R2 R3 R5 R6 加 E2E 測試
選做: 並發扣庫存測試 20、OpenAPI 文件 10
不做（寫進 README）: 訂單列表、統一錯誤格式、菜單快取、冪等鍵
```
```flow TB
[骨架能跑] -> [主流程一條龍加 E2E 測試] -> [加重要規則與測試] -> [選做] -> *收尾
```
需求編號、估時、用 must／should／could 排序；必做放不下就先溝通。題目沒說清楚能問就問，問不到就寫成假設並說明影響。E2E 測試 CP 值最高；每個小步驟一個 commit，不要 squash。

## F 作業 README 與取捨
| 段落 | 回答評審的問題 |
|---|---|
| 執行方式 | 打哪幾行指令才能跑 |
| 測試 | 怎麼跑、測了什麼 |
| 功能 | 每一條需求做了沒有 |
| 假設 | 沒說清楚的地方怎麼決定 |
| 設計決定與取捨 | 為什麼、考慮過什麼、代價 |
| 沒做的事 | 刻意沒做什麼、要做怎麼做 |
| 花費時間 | 實際多久、有沒有超時 |

取捨每條寫五件事：決定、替代方案、為什麼、代價、什麼時候要重新考慮。資深的判斷是知道什麼不做；作業太長或像是免費工作時，可以詢問、協商或婉拒。

```callout warn 常見扣分
「沒做的事：無」比不寫還糟；過度設計（4 小時的作業做成微服務加 Kafka）讓評審懷疑你的判斷。
```

## G 系統設計：45 分鐘與估算 {span=2}
```timeline h
5 | 需求 | 功能、有數字的非功能、不做什麼
5 | 估算 | QPS、讀寫比、儲存量
5 | API | 4～6 個端點、冪等鍵
5 | 資料模型 | 主要表與索引
10 | 高層架構 | 元件與一條請求路徑
*10 | 深入 | 一兩個重點
5 | 總結 | 設計、風險、下一步
```
| 數字 | 算法 | 這課的題目：300 家分店線上點餐 |
|---|---|---|
| 平均 QPS | DAU × 每人請求數 ÷ 86,400，無條件進位 | 50 萬 × 20 → 116 |
| 尖峰 QPS | 平均 × 尖峰倍數 | × 3 → 348（寫 35、讀 313） |
| 一年儲存量 | 每天寫入筆數 × 每筆大小 × 365，不乘尖峰 | 約 730 GB |

這題的量級（寫入每秒幾十筆、一年幾百 GB），單一 PostgreSQL（主＋備援）就放得下也寫得動，確切上限上線前用壓測確認；並說出門檻：寫入或資料量成長到什麼程度，先考慮讀副本和依時間分割資料表，最後才是分片。從最簡單能動的架構開始，每加一個元件說出它解決的數字問題與代價。瓶頸看使用率（負載 ÷ 容量），解決一個，下一個就會出現。時長不同時主要放大深入。

## H 系統設計：深入下單路徑
```sequence
participants: App, API, DB, 金流
App -> API: POST /orders 帶冪等鍵
API -> DB: 同一把鍵已完成就回上次結果
API -> DB: 條件更新扣庫存，0 列就是賣完
API -> 金流: 付款
note 金流: 逾時不代表失敗：保持 pending，同一把鍵重試或查詢，交給對帳
API -> DB: 訂單改已付款＋寫 outbox，同一個交易
note DB: relay 把 outbox 送進佇列，通知廚房
```
主動說失敗情境：資料庫切換時下單回 503 加 Retry-After；Redis 是軟相依，菜單改讀資料庫；金流變慢用斷路器；失控的 App 用限流擋。

```callout ok 取捨句型
「我選 A，不選 B，因為〔數字或需求〕；代價是 C；如果〔條件〕改變，我會改成 B。」被質疑時先確認對方擔心什麼，再用數字回答。最後 5 分鐘不畫新東西，總結設計、風險與下一步。每次演練後自評，下一次只改最弱的一兩段。
```
