階段 5：狀態與資料 · 第 16 課

API 層：把 fetch 包成可靠的介面

咖啡店的點餐網站有 30 個元件直接寫 fetch。某天後端把網址從 /api 改成 /api/v2，要改 30 個地方；商品頁收到 404 卻顯示一片空白，因為 fetch 沒有丟錯；token 過期時三個元件同時跳出「請重新登入」；顧客在網路不穩時按了兩次「送出訂單」，廚房做了兩杯拿鐵。

這四件事看起來不相干，根源卻是同一個：跟後端說話的程式散在各個元件，每個人各寫各的規則。這課用咖啡店的結帳頁當主線：進頁面時載入購物車、會員資料、可用優惠券，顧客按下「送出訂單」時建立訂單。我們把它從元件裡的 fetch 一步步搬進 API 層，也就是一個負責所有後端呼叫的模組。每一節解決結帳頁會遇到的一種失敗，最後元件只會看到兩種結果：成功就拿到資料，失敗就拿到一個分好類的錯誤。

這課的路線：
  1. 元件裡各寫各的 fetch 錯在哪：API 層是什麼，request 和端點函式怎麼分工（開場問題的最小答案）。
  2. 404 為什麼沒有丟錯、失敗了畫面該說什麼：fetch 什麼時候才 reject、狀態碼代表什麼，怎麼把失敗整理成固定幾種錯誤。
  3. 回應 200 就能信嗎：後端改了欄位格式時，在 API 層就攔下來，而不是購物車總額算錯。
  4. 伺服器不回、顧客離開時怎麼停掉請求；進結帳頁三個請求同時 401，怎麼只刷新一次 token。
  5. 送出訂單逾時了能不能重送：哪些請求可以自動重試，冪等鍵怎麼避免廚房做兩杯拿鐵。
這課會用到：
  • TS 課第 4 課的 Error 子類別與 cause：class XxxError extends Error 讓錯誤可以用 instanceof 分辨，cause 保留造成它的原始錯誤。
  • TS 課第 16 課的可辨識聯合：每個成員都有同一個欄位（例如 kind），值各不相同，switch 它就能縮小成某一種。
  • TS 課第 11 課的 AbortSignal：AbortSignal.timeout(ms) 時間到自動中止，AbortSignal.any 合併多個訊號；被中止的工作以 AbortError 或 TimeoutError 失敗。
  • TS 課第 12 課的單一飛行：同一件事已經在進行時，後來的呼叫共用同一個 Promise，不再發一次。
這課的練習都是純邏輯，在瀏覽器的 Web Worker 裡執行，不能 import 套件，也不連網路：每一題的 fetch 都由測試注入一個假的版本，回傳用 new Response(…) 做出來的回應。Response 是瀏覽器內建的類別，真的 fetch 回傳的就是它。

元件裡各寫各的 fetch，問題出在哪？

先看結帳流程現在的樣子。商品頁和結帳頁各自寫了一段 fetch：

// ProductPage.vue
const res = await fetch('https://api.coffee.test/v1/products/' + id, {
  headers: { Authorization: 'Bearer ' + localStorage.getItem('token') },
})
product.value = await res.json()

// CheckoutPage.vue
const res = await fetch('https://api.coffee.test/v1/orders', {
  method: 'POST',
  body: JSON.stringify(cart),    // 忘了 Content-Type
})
if (res.status !== 200) alert('失敗')   // 201 也被當成失敗

這兩段各藏著 bug。結帳頁送出 JSON 卻沒加 Content-Type: application/json 標頭。body 是字串時，fetch 預設把它標成純文字，後端多半依這個標頭決定要不要把 body 當 JSON 解析，於是收到一張空的訂單。結帳頁又用 res.status !== 200 判斷失敗，但「建立成功」的標準狀態碼是 201：訂單明明建好了，畫面卻跳出「失敗」，顧客再按一次，就多一筆訂單。商品頁則完全沒檢查回應，後端回 404 時，res.json() 讀到的是一個錯誤訊息物件，被當成商品塞進畫面。這個物件只有 message，沒有 name、price，畫面讀不到欄位，就是開場看到的一片空白。

這些 bug 不只是寫的人粗心。每個元件都要自己記得同一串規則：網址前綴、帶 token、送 JSON 要加標頭、哪些狀態碼算成功、失敗時顯示什麼。30 個元件就有 30 份副本，只要一份寫錯就是一個 bug；後端改了網址前綴或錯誤格式，就得把 30 份全部翻一遍。開場第一個事故就是這樣來的。

API 層的做法是把這串規則收進一個地方，分成兩層：

  • 最底下是一個函式 request(method, path, options)。它是全 app 唯一呼叫 fetch 的地方，負責組網址、加標頭、送 JSON、檢查狀態碼，並把各種失敗變成固定幾種錯誤。這課後面加的逾時、token 刷新、重試，也都加在這一層。
  • 上面是一個個有名字的端點函式，例如 getProduct(id)、createOrder(cart)。它們只描述「這個端點用什麼方法、什麼路徑，回應長什麼樣」，實際的工作交給 request。

元件只呼叫端點函式，從不碰 fetch。這樣分層換來三件事：

  • 規則只寫一次：網址、標頭、token、逾時、重試都在 request 裡。後端改網址前綴，只改建立 API 層時傳入的 baseUrl。
  • 錯誤有固定的形狀：元件拿到的一定是幾種已知的錯誤之一，畫面可以照種類顯示。
  • 好測試：request 不直接用全域的 fetch，而是由建立 API 層的人把 fetch 傳進來。這種「需要的東西由外面給」的做法叫依賴注入，第 13 課的 provide／inject 是同一個想法。測試時傳一個假的 fetch，就能模擬 404、斷線、逾時，不需要真的後端；本課的練習全部這樣測。
💡 實務上：接手專案先找 API 層在哪
進到新團隊，先找 api/ 或 services/ 這類資料夾，看 token、錯誤、逾時是在哪裡統一處理的。很多專案用 axios 這個 HTTP 套件，它的攔截器（interceptor）是在每個請求送出前、每個回應回來後執行的函式，做的就是這課 request 做的事，概念一樣。後端有 OpenAPI 文件時（一份描述每個端點的路徑、參數和回應格式的規格檔），團隊常用工具直接產生端點函式和型別，不必手寫。不要過度分層：咖啡店這種規模，一個 request 加幾個端點檔案就夠，不需要在中間再多包好幾層。Code review 看到元件裡直接寫 fetch，就值得提出來。

到這裡，開場問題有了最小答案：規則集中在 request，元件不再各自判斷成功失敗。但 request 本身要怎麼「檢查狀態碼」？要回答這個，得先知道 fetch 回給你的到底是什麼，以及它在什麼情況下才算失敗。這也是商品頁 404 一片空白的原因。

後端回 404，為什麼 fetch 沒有丟錯？

商品頁的 bug 要從 fetch 的行為講起。前端每次呼叫後端，都是送出一個 HTTP 請求，收到一個 HTTP 回應。寫 request 之前，先認識它們由哪些部分組成（Node 課第 12 課會從伺服器那一端深入）：

組成是什麼例子
方法（method）這個請求要做什麼GET 讀取、POST 建立、PUT／PATCH 修改（整筆換掉／改部分欄位）、DELETE 刪除
網址（URL）要操作哪一個資源https://api.coffee.test/v1/products/2
標頭（header）請求或回應附帶的鍵值資訊Content-Type: application/json（body 是 JSON）、Authorization: Bearer …（登入憑證）
body要送出或收到的內容{"items":[{"productId":2,"quantity":1}]}
狀態碼（status code）回應的結果，三位數字見下表

跟「成功還是失敗」有關的是狀態碼。它的第一位數字代表大類：2xx 成功、4xx 是請求方（前端或使用者）的問題、5xx 是伺服器的問題。下表是結帳流程會遇到的幾個，以及前端該怎麼對待它們：

狀態碼意思前端怎麼處理
200 OK、201 Created成功；201 表示建立了新資料讀 body
204 No Content成功，但沒有 body（常見於刪除）不能讀 JSON
400 Bad Request請求格式錯了通常是前端的 bug，記錄下來
401 Unauthorized沒登入，或 token 過期換新 token 或請使用者重新登入
403 Forbidden登入了，但沒有權限顯示「沒有權限」，換 token 也沒用
404 Not Found找不到這個資源顯示找不到
422 Unprocessable Content格式對，但資料驗證沒過把錯誤顯示在表單欄位旁
5xx（500、502、503…）伺服器那一端出錯請使用者稍後再試；讀取類的請求可以自動重試

各家後端用的狀態碼會有出入，例如有的驗證失敗回 400 而不是 422。所以 request 的判斷要照自己後端的約定寫，這課照上表。

接下來是 fetch 最常害人的地方，也就是商品頁一片空白的原因：只要伺服器有回應，不管狀態碼是多少，fetch 的 Promise 都會 resolve。只有在根本拿不到回應時，它才 reject：網路斷了、請求被取消，或是 DNS 查詢失敗。瀏覽器要連上 api.coffee.test，得先透過 DNS 把這個網域名稱換成 IP 位址，換不到就連不上，也就沒有回應。MDN 的說法是：收到 404 或 504 這類錯誤狀態碼時，fetch() 不會 reject，要自己檢查 Response.ok 或 Response.status。res.ok 在狀態碼是 200–299 時才是 true。

為什麼這樣設計？對 fetch 來說，404 是一個完整、合法的 HTTP 回應：伺服器收到了請求，也清楚回答了「沒有這個商品」。傳輸本身沒有出錯，出問題的是業務上的結果，而那要由呼叫的人判斷。所以檢查狀態碼是你的責任；不檢查，錯誤回應的 body 就會被當成資料。

下面用假的 fetch 示範。執行後看兩件事：三個回應的 Promise 都 resolve 了，只有 ok 不同；後面兩種情況呼叫 json() 會丟出什麼錯。

後面兩種情況，request 都要接住。第一種是 204：成功但沒有 body，對空的內容呼叫 json() 會丟 SyntaxError，所以要先看狀態碼，204 直接回傳 undefined。第二種在正式環境很常見：單頁應用程式為了讓 /checkout 這種網址重新整理後還打得開，前端伺服器常設定成把所有找不到的路徑都導回 index.html。結果打錯的 API 網址回了 200 加一份 HTML，狀態碼是 200，res.json() 卻丟 SyntaxError。這種情況要歸成「回應格式不對」，而不是讓 SyntaxError 一路冒到畫面上。

所以 request 的第一步很明確：拿到回應先看 res.ok，不是 2xx 就丟錯。但該丟什麼錯？如果只丟 new Error('失敗')，結帳頁就只能對顧客說「失敗」兩個字。

失敗了，結帳頁怎麼知道該對顧客說什麼？

想像顧客按下「送出訂單」後請求失敗了。不同的失敗原因，畫面該有的反應完全不同：

  • 斷線：請顧客檢查網路，連上後再試。
  • 422：電話格式不對，訊息要出現在電話欄位旁邊。
  • 401：登入過期，要導到登入頁。
  • 500：後端出問題，請顧客稍後再試，同時要讓工程師知道。
  • 顧客自己離開結帳頁造成的取消：什麼都不用說。

元件要做出這些反應，前提是知道「是哪一種失敗」。所以 request 不能只丟一種錯誤，要把所有失敗整理成固定幾種，每一種帶著畫面需要的資訊。這就是開場說的「失敗就拿到一個分好類的錯誤」：

類別kind什麼時候帶什麼資訊
NetworkErrornetworkfetch 本身 reject（斷線、DNS）cause：原本的 TypeError
TimeoutErrortimeout超過時間沒回應
CanceledErrorcanceled呼叫的人自己取消（例如離開頁面）
HttpErrorhttp非 2xx 的回應status、body
ValidationErrorvalidation422fieldErrors：欄位 → 訊息
UnauthorizedErrorunauthorized換 token 也救不回來的 401
ParseErrorparse回應不是 JSON，或格式跟約定的不一樣cause：驗證錯誤

表中有幾種這一節還用不到：TimeoutError、CanceledError 在講逾時時才出現，UnauthorizedError 在講 token 刷新時才出現，先知道它們會加進來就好。

每一種錯誤同時有兩個身分。第一，它是一個 Error 子類別（TS 課第 4 課），例如 class NetworkError extends Error。用類別的好處是 instanceof 可以辨認它，而且 Error 的 cause 選項能保留造成它的原始錯誤：斷線時 fetch 丟出的 TypeError 就存在 NetworkError 的 cause 裡，查問題時不會遺失。

第二，每一種都有一個 kind 欄位，值各不相同。所有錯誤合起來，就是 TS 課第 16 課的可辨識聯合：switch (e.kind) 走進某個 case 時，TypeScript 就知道 e 是哪一種、有哪些欄位，例如只有在 'validation' 裡才讀得到 fieldErrors。

kind 還帶來類別給不了的好處：窮舉檢查。在 switch 的 default 裡，把 e 指定給一個 never 型別的變數。每一種 kind 都處理過時，走到 default 的 e 已經被縮小成「不可能存在」的 never，指定成功；哪天有人新增第八種錯誤卻忘了在這裡處理，那一種會掉進 default，指定失敗，編譯器就會指出這個漏處理的地方（TS 課第 16、27 課）。

下面把錯誤翻成顧客看得懂的訊息。執行後看三行輸出各對應哪個 case，特別注意第一行顯示的內容。

第一個例子的 500 回應裡夾了一段資料庫錯誤，畫面卻只顯示「系統忙碌中」。不要把伺服器的原始錯誤訊息直接顯示給使用者，原因有兩個：顧客看不懂，看了也不知道該做什麼；而且它可能洩漏資料表名稱、SQL、程式路徑，等於幫攻擊者畫地圖。原始內容（status、body、cause）不是丟掉，而是送到錯誤監控（第 21 課）給工程師查。422 的 fieldErrors 是例外，那是後端特地寫給使用者看的訊息，所以第二行把欄位列出來。第三行是取消，回傳 null，畫面什麼都不顯示。

💡 實務上：錯誤格式要在開工前跟後端約好
串接新功能前，先和後端確認：驗證失敗回 400 還是 422、欄位錯誤放在 body 的哪個欄位、要不要附錯誤代碼（例如 COUPON_EXPIRED）讓前端對應文案。約定寫進 API 文件，不要靠讀後端程式碼猜。客服回報「結帳一直失敗」時，監控裡有 kind、status、端點，才查得出是斷線、優惠券過期還是後端掛了。畫面上的錯誤文案通常要給 PM 或設計看過，不是工程師自己決定。

到這裡，「有回應但不是 2xx」和「根本拿不到回應」都有了對應的錯誤。但還有一種失敗會躲過所有檢查：狀態碼是 200、JSON 也解析成功，資料的格式卻不是你以為的樣子。

回應是 200，資料就能信嗎？

結帳頁要用購物車裡每個商品的 price 算總額。元件裡常見的寫法是 const menu: Product[] = await res.json()。這行看起來有型別，其實 TypeScript 什麼都沒檢查：res.json() 的回傳型別是 Promise<any>，any 可以指定給任何型別，冒號後面的 Product[] 只是你對資料的期望，編譯器照單全收。

這個期望在後端改版那天就會落空。假設後端把 price 從數字 80 改成字串 "80"：請求成功、JSON 解析成功、型別也「對」，沒有任何地方報錯。直到購物車用 + 加總，數字加字串變成字串相接，總額成了 "0" + "80" + "110" 接出來的一串字。錯誤出現在離 API 很遠的畫面深處，看到的人第一個懷疑的是購物車的程式，很難想到是後端改了格式。

解法是 TS 課第 26 課的「unknown → 驗證 → 型別」。unknown 是 TypeScript 裡代表「還不知道是什麼」的型別：它可以接住任何值，但在檢查之前不能拿來用（TS 課第 17 課）。API 層把每個回應都先當成 unknown，交給端點提供的 parse 函式檢查：通過了，才變成有型別的資料交給元件；沒通過，就丟 ParseError。這樣格式出錯時，錯誤發生在 API 層，訊息直接寫出哪個端點、哪個欄位不對，而不是在購物車裡算出一個奇怪的總額。

parse 可以手寫，但實務上用 schema 套件。schema 是用程式描述「資料應該長什麼樣」的物件；zod 的 schema 既能在執行時檢查資料，也能推導出 TypeScript 型別，同一個形狀不用寫兩遍：

// api/products.ts：用 zod 4（vue/practice 安裝的是 4.6.7）寫端點的 parse
import { z } from 'zod'

const Product = z.object({ id: z.number(), name: z.string(), price: z.number() })
export type Product = z.infer<typeof Product>

export function createProductApi(api: Api) {
  return {
    getMenu: (signal?: AbortSignal) =>
      api.request('GET', '/menu', { parse: d => z.array(Product).parse(d), signal }),
    getProduct: (id: number) =>
      api.request('GET', `/products/${id}`, { parse: d => Product.parse(d) }),
  }
}

getMenu 多收的 signal 是用來取消請求的，下一節講逾時與取消時會用到，這裡先照抄。Product 是 schema，z.infer 從它推導出同名的型別。schema.parse 在資料符合時回傳資料，不符合時丟出 ZodError，裡面記著哪個欄位、期望什麼。request 接住這個錯誤，包成 ParseError，cause 留著 ZodError 的細節，送到監控時就看得到是 price 的型別不對。也可以用 safeParse，它不丟錯，回傳 { success: true, data } 或 { success: false, error }，適合想自己決定失敗時怎麼辦的地方。

取捨：驗證有成本，要多寫 schema，大的列表也要多花一點時間檢查。換來的是後端改格式時立刻知道是哪個欄位。後端和前端在同一個 repo、型別由同一份 schema 產生時，可以只驗證關鍵端點；呼叫第三方 API 時一定要驗證。

端點函式寫好了，元件要怎麼拿到它們？API client 在整個 app 只建立一份，用第 13 課的 provide／inject 交給元件，測試時注入假的 client：

// main.ts
const api = createApi({ baseUrl: import.meta.env.VITE_API_URL, fetch: (url, init) => fetch(url, init) })
app.provide(ApiKey, { products: createProductApi(api), orders: createOrderApi(api) })

注意傳進去的是 (url, init) => fetch(url, init)，不是直接傳 fetch。直接傳 fetch，只要實作裡用 options.fetch(…) 這種方式呼叫，Chrome 就會以 TypeError: Illegal invocation 失敗，原因見課末〈補充與查表〉。

到這裡，只要伺服器有回應，不論成功、失敗還是格式不對，request 都能給元件一個明確的結果。剩下的是伺服器遲遲不回應的時候。

伺服器一直不回、顧客已經離開，請求怎麼停？

fetch 本身沒有逾時。伺服器卡住不回，請求就一直掛著，結帳頁的按鈕一直轉圈，顧客不知道訂單到底送出了沒。另一種情況方向相反：顧客在菜單還在載入時就切到別頁，這個請求已經沒人要了，回來的結果也沒地方放，應該停掉，不要白白佔著連線。

兩件事都用 TS 課第 11 課的 AbortSignal 處理。AbortSignal 是一個中止訊號：把它傳給 fetch，訊號一觸發（abort），fetch 就中止這個請求並 reject，reject 的值是訊號上的 reason。產生訊號的方式有三種，正好對應我們要的三件事。DOMException 是瀏覽器 API 丟出的錯誤類別，不同情況用 name 欄位區分，所以下面看的是 e.name：

  • AbortSignal.timeout(ms)：時間到自動 abort，reason 是名稱為 TimeoutError 的 DOMException。用來做逾時。
  • 呼叫的人自己的 AbortController：abort() 時 reason 是名稱為 AbortError 的 DOMException。用來做取消，例如元件卸載時呼叫。
  • AbortSignal.any([a, b])：任何一個 abort 就跟著 abort，reason 用最先 abort 的那一個。用來把前兩者合併成一個傳給 fetch。

所以 request 的做法是：把呼叫端傳進來的 signal 和 AbortSignal.timeout(ms) 用 AbortSignal.any 合併，傳給 fetch。不管哪一個先發生，請求都會真的被中止。fetch reject 之後，還要分辨是哪一種，因為它們要變成不同的錯誤：取消變成 CanceledError（畫面什麼都不說），逾時變成 TimeoutError（請顧客稍後再試）。分辨方法是看呼叫端自己的 signal 有沒有 abort：有，就是取消；沒有，就是逾時。

下面用一個 1 秒才回應的假菜單請求示範，逾時設成 100ms。執行後看兩行輸出的錯誤名稱，以及「使用者取消了嗎？」這一欄怎麼把兩者分開。

寫逾時有兩個常見的錯，都會讓程式看起來有逾時，實際上沒有。第一個是用 Promise.race([fetch(…), 計時器]) 做逾時：計時器先到，race 結束、你不再等了，但請求本身沒有被中止，它還在跑、還佔著連線，伺服器也還在做事。只有把 signal 傳給 fetch，請求才會真的停下來。

第二個是自己用 setTimeout 做逾時，卻沒有清掉計時器。成功的請求留下一個 10 秒的計時器，在伺服器上會讓程序結束不了，在測試裡會讓測試跑很久。自己寫計時器，就一定要在 finally 裡 clearTimeout；AbortSignal.timeout 沒有這個問題。練習 2 的測試會檢查這一點。AbortSignal.any 在比較舊的瀏覽器上不存在，要支援哪些版本見課末〈補充與查表〉。

逾時和取消處理完，request 能應付所有拿不到回應的情況。接下來是結帳頁最麻煩的一種有回應的失敗：401。它不能只翻成「請重新登入」了事，因為多數時候它可以自動救回來。

進結帳頁三個請求同時 401，怎麼只刷新一次？

先說 401 為什麼救得回來。登入後，後端給前端兩樣東西（auth 課第 10 課深入）：

  • access token：短效期（例如 15 分鐘）的通行證，每個請求放在 Authorization 標頭送出。過期了後端回 401。
  • refresh token：長效期的憑證，唯一用途是換新的 access token。

為什麼要分兩個？access token 每個請求都要送，送得越多，被偷走的機會越多，所以讓它短效，被偷了也很快失效。但如果只有它，顧客每 15 分鐘就得重新登入一次。refresh token 解決這個矛盾：它只在換新 token 時才送出，平常不露面，所以效期可以長。也因此，access token 過期造成的 401 是正常、可預期的，API 層應該自己處理：收到 401 → 用 refresh token 換新的 access token → 把原本的請求重送一次。顧客完全不會察覺。

麻煩在同時。進到結帳頁時，購物車、會員資料、可用優惠券三個請求一起送出，一起拿到 401。如果每個請求各自刷新，就會打 3 次 refresh。很多後端採用 refresh token 輪替：每次刷新時連 refresh token 也換一個新的，舊的用過一次就作廢。第一次刷新成功後，第二、三次拿的是已經作廢的舊 refresh token，一定失敗，結果顧客明明可以繼續用，卻被登出。開場「三個元件同時跳出請重新登入」就是這樣來的。

解法是 TS 課第 12 課的單一飛行：同一件事已經在進行時，後來的呼叫不再重做，而是共用同一個 Promise。套到刷新上：第一個遇到 401 的請求開始刷新，把這次刷新的 Promise 存起來；之後遇到 401 的請求看到有刷新在進行，就等同一個 Promise。刷新結束後，每個請求各自重送一次。

圖的最下面兩行是兩條邊界，少守一條都會出事：

  • 每個請求最多重送一次。重送後還是 401，代表新的 token 也不被接受（帳號被停用、refresh 的實作有 bug），再刷新只會變成無限迴圈。
  • 登出只做一次。三個請求一起失敗時，onAuthFailure（清掉登入狀態、導到登入頁）只能呼叫一次，否則會跳三個提示、導頁三次。

也只有 401 才刷新。403 是「登入了但沒權限」，例如一般顧客呼叫了店長才能用的 API；換一個新 token，身分還是同一個，結果不會變。

access token 和 refresh token 要存在哪裡？

上面的 refresh() 要拿 refresh token 去換新的 access token，這兩個 token 存在瀏覽器的哪裡，是一個安全上的取捨。先認識兩個名詞。Cookie 是伺服器請瀏覽器保存的一小段資料，之後瀏覽器每次請求同一個網站都會自動帶上（auth 課第 4 課）。加上 HttpOnly 屬性的 httpOnly cookie，JavaScript 讀不到。

再認識兩種攻擊，每種放法要防的就是它們。XSS 是攻擊者把惡意腳本注入你的網站（例如藏在商品評論裡），讓它在顧客的瀏覽器裡、以你網站的身分執行（auth 課第 7 課）。CSRF（跨站請求偽造）是別的網站誘導顧客的瀏覽器對你的網站發請求；因為瀏覽器會自動帶上 cookie，這個請求看起來就像顧客本人發的（auth 課第 6 課）。表裡的對策還有兩個名詞：CSP（Content Security Policy）是一個回應標頭，限制頁面只能執行哪些來源的腳本，讓注入的腳本跑不起來；SameSite 是 cookie 的屬性，限制從別的網站發出的請求要不要帶上這個 cookie。

放哪裡JavaScript 讀得到嗎主要風險對策
localStorage可以你網站上的 XSS 腳本可以把 token 讀走，拿到別台電腦用防 XSS、設定 CSP；token 效期短
JavaScript 變數（記憶體）可以，重新整理就消失XSS 不容易把它偷走，但仍能在頁面開著時拿它發請求重新整理後用 refresh 換一個新的
httpOnly cookie不行瀏覽器會自動帶上，別的網站可以誘導瀏覽器發請求：CSRFcookie 的 SameSite 屬性、CSRF token

常見的組合是 access token 放在記憶體、refresh token 放在 httpOnly cookie：refresh() 呼叫 POST /auth/refresh，瀏覽器自動帶上 cookie，回應給新的 access token。沒有一種放法同時擋住 XSS 和 CSRF，差別在把風險放在哪裡、用什麼對策補。

💡 實務上：token 放哪裡是團隊決定，不是前端自己選
這通常在專案初期由後端、前端和資安一起決定，接手專案時先照現有做法，不要因為看到一篇文章就把 token 改放到 localStorage。要用 cookie 時，先問清楚：refresh token 由誰發、cookie 的 SameSite 怎麼設、API 和前端是不是同一個來源。協定、網域、port 三者都相同才算同一個來源，所以 api.coffee.test 和 coffee.test 不算。不同來源時，瀏覽器套用 CORS 這套跨來源請求規則：fetch 要加 credentials: 'include' 才會帶 cookie，後端也要在 CORS 設定裡允許前端的網址並允許帶 cookie，這是串接時很常卡住的地方。

401 處理完，結帳頁進頁面時的載入在各種失敗下都有對的反應。最後剩下開場最貴的那個事故：顧客按了兩次「送出訂單」，廚房做了兩杯拿鐵。它牽涉到一個看似簡單的問題：失敗了，能不能再送一次？

送出訂單逾時了，可以自動再送一次嗎？

網路偶爾斷一下、伺服器偶爾回 503，自動重試一兩次，顧客就感覺不到。所以很自然會想在 request 裡加上「失敗就重試」。但不是每個請求都能重試。

看建立訂單的例子：前端送出 POST /orders，3 秒後逾時。逾時只代表前端沒等到回應，不代表伺服器沒收到。請求可能根本沒到伺服器；也可能伺服器已經建好訂單、通知了廚房，只是回應在路上掉了。前端分不出這兩種。如果是後者，這時自動重送，或顧客看到「請再試一次」又按一次，就會多一筆訂單、多扣一次款。

那菜單為什麼可以放心重試？因為讀兩次菜單，結果和讀一次一樣。這個性質叫冪等（idempotent）：同一個操作做一次和做多次，結果相同。依 HTTP 規格（RFC 9110），GET、HEAD、PUT、DELETE 是冪等的：讀兩次、把同一筆資料設成同樣的值兩次、刪同一筆兩次，結果都一樣。POST（建立）和 PATCH 不保證冪等，建立兩次就是兩筆。所以重試的第一條規則是：冪等的請求可以自動重試，不冪等的不行。

可是送出訂單偏偏是最需要「失敗了再試」的操作。要讓它也能安全重送，就得讓伺服器認得出「這是同一次操作的重送」。做法是冪等鍵（idempotency key）：前端為一次「建立」操作產生一個唯一的 id（例如 crypto.randomUUID()），放在 Idempotency-Key 標頭送出。伺服器記住看過的 key，重複的 key 就回傳第一次的結果，不再建立一次。這個標頭還不是正式標準（狀態見課末），但很多金流 API 已經這樣用。後端要配合實作，系統設計課第 9 課會深入。

冪等鍵的重點是同一次操作要用同一個 key：在顧客按下「送出訂單」時產生一次，自動重試和顧客因逾時再按一次，都帶同一個 key；等訂單成功或顧客改了購物車，才換新的。每次重送都產生新 key，伺服器看到的就是兩次不同的操作，等於沒有用。

方法決定「能不能重試」，錯誤的種類決定「值不值得重試」。斷線、逾時、5xx 可能是暫時的，下一次就好；4xx 是請求本身的問題，再送幾次結果都一樣，電話格式錯的 422 不會因為重送就變對。429「請求太多」是例外，要照回應的 Retry-After 標頭等待後再送（系統設計課第 10 課）。

最後是什麼時候重試。重試之間要等待，而且越等越久，這叫退避（backoff）：200ms、400ms、800ms……伺服器正在過載時，大家立刻重試只會讓它更慢。還要加上隨機的抖動（jitter）：一千個使用者在同一秒斷線，如果都在 200ms 後一起重試，又是一波尖峰；各自多等 0～100ms 就分散開了（系統設計課第 8 課）。

下面的 withRetry 把這些規則拆成兩個由外面傳入的函式：shouldRetry 決定這次失敗要不要再試，delayFor 決定等多久。範例用會先失敗兩次的菜單 API，因為 GET 可以放心重試。執行後看每次失敗後等了多久，以及第幾次成功。

重試只放在一層。API 層重試 3 次、上面的 composable 又重試 3 次、後端呼叫下游時再重試 3 次，一個失敗會被放大成 27 個請求，剛好在伺服器最脆弱的時候。決定好由哪一層負責，其他層不要再試。
💡 實務上：「送出訂單」按鈕一定要防重複
付款、下單這類 POST 重複送出，就是客服收到「被扣兩次款」「訂單多一筆」的典型原因。前端最基本的做法是按下後停用按鈕、顯示處理中，但逾時後按鈕恢復、使用者再按一次，或 API 層自動重試，停用按鈕都擋不住，所以還是要冪等鍵。冪等鍵需要後端實作，前端單方面加標頭沒有用，開工前要確認後端支不支援。後端還不支援時，POST 就不要自動重試，逾時後提示使用者先到訂單列表確認，而不是直接叫他再送一次。

回頭看開場的四個事故：網址前綴只在 baseUrl 改一次；404 被 res.ok 的檢查攔下，變成 HttpError；三個同時的 401 共用一次刷新，最多登出一次；送出訂單帶著冪等鍵，重送也不會讓廚房做兩杯拿鐵。練習會把這些一步步寫成完整的 request。

為什麼不直接把 fetch 傳進去

瀏覽器的 fetch 被存成別的物件的屬性、再用 obj.fetch(…) 呼叫時，Chrome 會以 TypeError: Illegal invocation 失敗。如果 createApi 的實作寫成 options.fetch(…)，或某個套件把它存成屬性再呼叫，就是這種情況。包一層箭頭函式 (url, init) => fetch(url, init)，裡面呼叫的永遠是全域的 fetch，不管實作怎麼呼叫都安全。

版本備註

  • AbortSignal.any() 的相容性：從 2024 年 3 月起主要瀏覽器才都支援（Chrome 116、Firefox 124、Safari 17.4，依 MDN 的相容性資料）。Vite 8 預設的建置目標是 Chrome 111、Safari 16.4，而且 Vite 預設只轉換語法、不補 API（polyfill）。要支援更舊的 Safari，得自己補上或改用 AbortController 手動串接。
  • Idempotency-Key 標頭：目前還是 IETF 的草案（2026 年 10 月是 draft-08）。

練習

四題由小到大做出完整的 API 層。每一題上方都附了「不用改」的錯誤類別，和這一題需要的型別。

練習 1：完成 createApi({ baseUrl, fetch }) 的 request(method, path, { body, parse })。起始程式就是散在元件裡的寫法，按下執行會看到 404 被當成成功。要做到：

  • 網址是 baseUrl + path，把 method 傳給 fetch。
  • 有 body 時用 JSON.stringify 送出，並加上 Content-Type: application/json；沒有 body 就兩個都不加。
  • fetch 本身 reject 時丟 NetworkError，用 { cause } 保留原本的錯誤。
  • 422 丟 ValidationError（欄位錯誤用 fieldErrorsOf(await readErrorBody(res)) 取出）；其他不是 2xx 的丟 HttpError(status, body)，body 用 readErrorBody 讀。
  • 204 回傳 undefined；其他成功的回應讀 JSON，有 parse 就回傳 parse 的結果。
  • JSON 解析失敗或 parse 丟錯時，丟 ParseError，用 { cause } 保留原因。

練習 2：讓 request 支援 { timeoutMs, signal }。起始程式是練習 1 的答案。要做到：

  • 把使用者的 signal 和 timeoutMs 合併成一個 signal 傳給 fetch（兩個都沒有就不用傳）；時間到或使用者取消時，fetch 收到的 signal 要真的變成 aborted。
  • 使用者取消丟 CanceledError，逾時丟 TimeoutError，其他 fetch 的失敗仍是 NetworkError。
  • 不論成功或失敗，都不能留下計時器（測試裡有設 10 秒逾時的成功請求，留下計時器就會超過 3 秒的執行上限）。
  • 不要 abort 使用者傳進來的 signal，那是呼叫的人的東西。

練習 3：寫 withAuthRefresh(api, { refresh, onAuthFailure })，回傳一個形狀一樣的 Api，在外面包上 token 刷新。起始程式只是原封不動地轉呼叫，按下執行會看到三個請求都失敗。要做到：

  • 請求丟出 status 是 401 的 HttpError 時，呼叫 refresh()，成功後用同樣的參數重送一次。
  • 同一段時間裡有好幾個請求 401，只呼叫一次 refresh()，其他請求等同一個 Promise；這一輪結束後，新的 401 要能開始新的一輪。
  • refresh() 失敗，或重送後還是 401：請求丟 UnauthorizedError，不再刷新；onAuthFailure() 每一輪只呼叫一次。
  • 其他錯誤（包含 403、500）原封不動地丟出同一個錯誤物件。

練習 4：寫 retryPolicy({ maxRetries = 2, random })，回傳兩個函式，給重試迴圈（上面範例的 withRetry）使用：

  • shouldRetry(request, error, attempt)：request 是 { method, idempotencyKey? }，attempt 是這個請求已經失敗幾次。attempt 超過 maxRetries 就不重試。GET、PUT、DELETE 可以重試；POST、PATCH 只有帶了 idempotencyKey 才可以。錯誤只有 NetworkError、TimeoutError、5xx 的 HttpError 值得重試，4xx 和其他錯誤一律不重試。
  • delayFor(attempt)：第 1 次失敗後等 200ms，之後每次加倍（400、800…），再加上 random() * 100 毫秒的抖動。random 由外面注入，測試才能得到固定的結果。

練習 5：const res = await fetch('/api/orders/99')，伺服器回了 500。下面哪個描述正確？

✓ 只要伺服器有回應，fetch 就 resolve，狀態碼只是回應的一部分；只有拿不到回應（斷線、DNS、被取消）才 reject。a 是最常見的誤解，結果是 500 的錯誤頁被當成資料，畫面一片空白；c 錯在 fetch 不會重試也不會等狀態碼變好。

練習 6：顧客按「送出訂單」，POST /orders 10 秒後逾時，畫面顯示「請再試一次」，顧客又按了一次。可能發生什麼？

✓ 逾時只代表前端沒等到回應，請求可能已經到了伺服器、訂單已經寫進資料庫，只是回應沒回來。a 是這題要破除的誤解；b 錯在兩個請求彼此獨立，第二次通常會成功，所以才會多一筆。解法是按下送出時產生一個冪等鍵，重送都帶同一個，伺服器看到重複的 key 就回傳第一次的結果。

練習 7：把 access token 存在 localStorage，主要的風險是什麼？

✓ localStorage 對同一個來源（origin：協定、網域、port 都相同）的所有 JavaScript 都開放，包含被 XSS 注入的腳本。b 錯在 localStorage 依來源隔離，別的網站讀不到；c 描述的是 cookie，localStorage 不會自動帶上，要你的程式自己放進 Authorization 標頭，所以它反而沒有 CSRF 的問題。

常見錯誤

  • 沒檢查 res.ok：404、500 的錯誤頁被當成資料，畫面空白或顯示奇怪的內容。fetch 只在拿不到回應時 reject，狀態碼要自己看。
  • 用 res.status !== 200 判斷失敗：建立成功的 201 也被當成失敗，顧客以為沒送出又按一次。成功要看 res.ok（200–299）。
  • 對沒有 body 的回應呼叫 json()：204 會丟 SyntaxError。先看狀態碼，204 直接回傳 undefined。
  • 假設回應格式一定正確：res.json() 回傳 any，型別只是你的期望。端點用 schema 驗證，格式不對時在 API 層就丟 ParseError。
  • 把伺服器的原始錯誤訊息直接顯示給使用者：可能洩漏 SQL、資料表、程式路徑。畫面依 kind 顯示寫好的訊息，原始內容送去監控。
  • 逾時計時器沒有清掉：成功的請求留下計時器，測試跑很久、伺服器程序結束不了。用 AbortSignal.timeout，或在 finally 裡 clearTimeout。
  • 用 Promise.race 做逾時：只是不等了，請求沒有被中止。要把 signal 傳給 fetch。
  • 每個請求各自刷新 token：同時 401 時打好幾次 refresh，refresh token 輪替時還會把使用者登出。共用同一個刷新的 Promise。
  • 重送後還是 401 就再刷新一次：無限迴圈。每個請求最多重送一次，之後統一登出。
  • 自動重試不冪等的請求：建立訂單、付款逾時後重送，可能變成兩筆。只重試冪等的方法，POST 要帶冪等鍵，而且同一次操作用同一個 key。
  • 重試沒有上限、沒有退避：伺服器過載時，重試把它壓得更垮。設次數上限、指數退避加抖動，而且只在一層重試。

小結

  • API 層把網址、標頭、JSON、狀態碼、逾時、token、重試集中在一個 request 裡；元件只呼叫有名字的端點函式，fetch 從外面注入，方便測試。
  • fetch 只在拿不到回應時 reject。2xx 才算成功，204 沒有 body，422 轉成帶 fieldErrors 的 ValidationError，其他非 2xx 轉成帶 status、body 的 HttpError。
  • 錯誤分成固定幾種，用 kind 組成可辨識聯合，畫面用 switch 決定顯示什麼；不把伺服器的原始訊息給使用者看。
  • 回應先當成 unknown，經過 schema 驗證才變成有型別的資料，後端改格式時錯誤停在 API 層。
  • 逾時與取消用 AbortSignal.any([使用者的 signal, AbortSignal.timeout(ms)])，看使用者的 signal 有沒有 abort 來分辨兩者；signal 一定要傳給 fetch。
  • access token 過期的 401 是可預期的：同時 401 只刷新一次，大家等同一個 Promise，各自重送一次；刷新失敗或重送仍是 401 時登出一次。
  • 只自動重試冪等的請求和可能自己好的錯誤（斷線、逾時、5xx），有次數上限、指數退避加抖動；建立類的請求靠冪等鍵讓重送安全。
