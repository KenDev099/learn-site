階段 6：路由、權限與錯誤處理 · 第 19 課

路由：巢狀路由、參數與 URL 狀態

咖啡店的線上點餐上線第一天，就收到三則回報：店長把「茶飲分類」的網址傳給同事，對方打開看到的卻是咖啡；顧客在商品頁按「下一個商品」，網址從 /menu/1 變成 /menu/2，畫面還是美式咖啡；有人在商品頁按重新整理，看到伺服器的 404 頁面。三個問題都和路由有關，而且都不是把 Vue Router 裝好就會自動解決的。

這課從頭到尾處理這批回報，目標是讓點餐網站的每個網址都可靠：貼給別人、重新整理、換商品、按上一頁，看到的都是網址指的那個畫面。三則修完之後，還會順著遇到兩個連帶的問題：顧客從商品頁按上一頁，菜單重新載入又捲回頂端；路由表加進店員用的後台之後，顧客的手機也得下載後台的程式碼。

範例使用 Vue 3.5.44 與 vue-router 5.4.0。

這課的路線：
  1. 站內點進去正常，為什麼重新整理就 404：SPA 怎麼換網址卻不重新載入、伺服器要怎麼配合（第三則回報的答案，也說明另外兩則的根源）。
  2. 伺服器把所有路徑交給前端之後，每個網址該畫哪個元件：路由表的動態參數、找不到頁面、具名路由、巢狀路由，以及頁面怎麼拿到參數。
  3. 從 /menu/1 換到 /menu/2 畫面為什麼不動：同一個元件被重用，改用 watch 載入（第二則回報）。
  4. 茶飲分類傳給同事為什麼變回咖啡：把篩選放進網址的 query，驗證、寫入、包成 composable（第一則回報）。
  5. 兩個連帶問題：按上一頁回菜單怎麼不重新載入、不捲回頂端（KeepAlive 與 scrollBehavior）；顧客怎麼不用下載後台（懶載入路由）。
這課會用到：
  • 第 8 課的生命週期：onMounted 只在元件掛載時執行一次，元件沒有重新掛載就不會再跑。
  • 第 5 課的 watch：值改變時執行 callback，immediate: true 讓它一開始就先跑一次，onWatcherCleanup 在下一次執行前取消上一次的請求。

站內點進去正常，為什麼重新整理就 404？

先從第三則回報開始，因為它牽涉到「網址到底由誰負責」，另外兩則回報的根源也在這裡。

傳統網站每換一頁，瀏覽器就向伺服器要一份新的 HTML：點「菜單」，瀏覽器發出 GET /menu，伺服器找到對應的頁面回傳，整個畫面重畫一次。每個網址在伺服器上都有對應的東西，所以重新整理、把網址貼給別人，都只是「再要一次同一個網址」，不會出問題。

Vue 寫的點餐網站不是這樣運作。它是單頁應用（SPA，single-page application）：整個網站只有一份 index.html。第一次打開網站時，伺服器回傳這份 HTML 和打包好的 JavaScript；之後換頁都由 JavaScript 把畫面裡的元件換掉，不再向伺服器要 HTML。好處是換頁不用整頁重新載入，比較快，記憶體裡的狀態（例如購物車）也不會因為換頁而消失。代價是網址不再由伺服器維護：如果 JavaScript 換了畫面卻沒有改網址，網址列永遠停在首頁，使用者沒辦法分享、收藏，按上一頁也會直接離開網站。

所以 SPA 需要一個「改網址但不發請求」的方法。瀏覽器提供的 History API 就是做這件事的：

  • history.pushState(state, '', '/menu/2')：網址變成 /menu/2，並新增一筆歷史紀錄。
  • history.replaceState(state, '', '/menu?category=tea')：網址改變，但換掉目前這一筆紀錄，上一頁的筆數不變。
  • popstate 事件：使用者按上一頁／下一頁時觸發，JavaScript 讀新的網址、換上對應的畫面。

pushState 和 replaceState 只改網址列和歷史紀錄，不會讓瀏覽器發出請求，也不會觸發 popstate；popstate 只在使用者按上一頁／下一頁（或程式呼叫 history.back() 這類方法）時出現。換句話說，「網址變了要換哪個畫面」這件事，瀏覽器完全不管，要由 JavaScript 自己決定。

負責做這個決定的就是路由。路由（route）是「一種網址對應到哪個畫面」的規則，例如「/menu/數字 顯示商品頁」；路由器（router）是管理這些規則的物件，網址一改變就找出對應的規則、換上那個畫面。Vue Router 就是 Vue 的路由器：它的 router.push() 底層就是 pushState，router.replace() 是 replaceState，它也替你監聽 popstate，所以你不用直接碰 History API。

現在可以回答第三則回報了。進入 /menu/3 有兩種方式，經過的路完全不同：

從首頁點連結進去時，Vue Router 用 pushState 改網址、自己換上商品頁，伺服器從頭到尾不知道發生了什麼，所以一切正常。按重新整理就不一樣了：瀏覽器把目前記憶體裡的頁面整個丟掉，照網址列向伺服器發出 GET /menu/3。這時 JavaScript 還沒載入，前端的路由表根本還不存在；而 /menu/3 只存在於前端的路由表，伺服器上沒有這個檔案，只好回 404。

所以 Vue Router 沒有設定錯，要改的是伺服器：找不到檔案的路徑一律回傳 index.html，讓前端接手。瀏覽器拿到 index.html 後載入 JavaScript，Vue Router 啟動時讀網址列上的 /menu/3，畫出商品頁。Nginx 的寫法是 try_files $uri $uri/ /index.html;：先找同名的檔案、再找同名的資料夾，都沒有就回 index.html（DevOps 課第 12 課會實際設定）。

這個設定有代價：伺服器不再回 404，打錯的網址也會拿到 index.html。「這個網址不存在」的判斷因此落到前端，前端路由表要有自己的「找不到頁面」，下一節會加上。另一種不必改伺服器設定的做法是 hash 模式，網址會變成 /#/menu/3，取捨見課末〈補充與查表〉。

💡 實務上：「重新整理就 404」通常是部署設定，不是程式問題
SPA 第一次部署到 Nginx，或 AWS S3 這類雲端靜態檔案空間時，最常見的回報就是「點進去正常，重新整理就壞掉」。上線前要和負責部署的人確認：找不到的路徑會回傳 index.html。如果前端和 API 放在同一個網域，還要確認 /api/ 開頭的路徑不會也被導到 index.html，否則打錯的 API 會回 200 和一份 HTML，前端解析 JSON 時才報錯，很難追。資深工程師會在測試環境直接重新整理幾個深層網址（例如 /orders/7），而不是只從首頁點進去測。

開場另外兩則回報，原因也在「網址由前端維護」：分類要寫進網址的 query（/menu?category=tea），只放在元件的 ref 裡，網址傳給別人就失去了篩選；從 /menu/1 換到 /menu/2 時元件被重用，onMounted 不會再跑，要改成監看參數。這兩則留到第三、四節。在那之前要先把前端的路由表寫對：伺服器現在把所有路徑都交給 index.html，哪個網址畫什麼、哪個網址算不存在，全由它決定。

伺服器全交給前端之後，每個網址該畫哪個元件？

上一節讓伺服器對每個找不到的路徑都回 index.html，於是「/menu/3 是商品頁」「/menu/abc 不存在」這些判斷，全部要寫在前端的路由表裡。路由表是一個陣列，每一筆至少有 path（要比對的網址）和 component（對到時顯示的元件）。Vue Router 拿目前的網址逐筆比對，把對到的元件畫在 App 裡的 <RouterView />：這是 Vue Router 提供的元件，本身不畫任何東西，只是一個「依網址換內容」的位置。

咖啡店需要這些頁面：

import { createRouter, createWebHistory } from 'vue-router'

const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/', name: 'home', component: HomePage },
    { path: '/menu', name: 'menu', component: MenuPage },
    {
      path: '/menu/:id(\\d+)',                       // 動態參數，只接受數字
      name: 'product',
      component: ProductPage,
      props: route => ({ id: Number(route.params.id) }),
    },
    {
      path: '/orders',
      component: OrdersLayout,                       // 版面裡有自己的 <RouterView />
      children: [
        { path: '', name: 'order-list', component: OrderList },          // /orders
        { path: ':orderId(\\d+)', name: 'order-detail', component: OrderDetail },  // /orders/7
      ],
    },
    { path: '/:pathMatch(.*)*', name: 'not-found', component: NotFound },
  ],
})

history: createWebHistory() 就是上一節講的做法：用 History API 維護正常樣子的網址，需要伺服器配合回傳 index.html。下面依序看每一種路由解決什麼問題。

動態參數（params）。咖啡店有六個商品，不可能每個商品寫一條路由。路徑裡以 : 開頭的部分是變數，/menu/:id 能對到 /menu/1 到 /menu/6，對到的值放在 route.params.id。網址是文字，所以 /menu/2 的 route.params.id 是字串 '2'，不是數字。

只寫 :id 的話，任何東西都能填進那個位置：/menu/abc 也會顯示商品頁，然後拿 'abc' 去打 API，畫面變成一個奇怪的錯誤。以前伺服器會替你擋下不存在的網址，現在不會了，所以參數的格式要在路由表裡限制。括號裡可以寫正規表示式：:id(\\d+) 只接受一個以上的數字，/menu/abc 就不會對到商品頁，而是落到下面的找不到頁面。反斜線在 JavaScript 字串裡要寫兩次，路由實際收到的才是 \d+。

找不到頁面。這一條取代了伺服器原本的 404。/:pathMatch(.*)* 對到所有路徑，顯示 NotFound 元件，網址列維持使用者打的那個網址，他看得出自己哪裡打錯。它寫在最後，但順序其實不影響結果：Vue Router 依路徑的明確程度排序，/menu/3 一定先對到更明確的商品頁，不怕被這條搶走。結尾那個 * 的用途見課末〈補充與查表〉。

具名路由。每條路由可以有 name，程式用名稱導航：router.push({ name: 'product', params: { id: 3 } })。如果到處寫死 '/menu/3' 這種字串，哪天網址改成 /products/3，就得在整個專案裡搜尋替換，漏一個就是壞掉的連結。用名稱的話，只改路由表的 path，所有連結自動跟著變。

巢狀路由（nested routes）。店員後台的訂單列表 /orders 和訂單明細 /orders/7 共用同一個版面：上方的「訂單管理」標題、左邊的側欄。如果寫成兩條平行的路由，兩個頁面元件都得各自放一份版面，從列表點進明細時，版面也會跟著被卸載再重建。巢狀路由把版面做成父路由 OrdersLayout，列表和明細做成它的 children；OrdersLayout 裡也放一個 <RouterView />，子路由的元件就畫在那裡。進入 /orders/7 時，App 的 RouterView 顯示 OrdersLayout，OrdersLayout 的 RouterView 再顯示 OrderDetail：

子路由的 path 是相對於父路由的，所以不以 / 開頭：寫成 '/:orderId' 會變成根路徑 /7，跟 /orders 無關了。path 是空字串 '' 的子路由，是進入 /orders 本身時預設顯示的內容，這裡就是訂單列表。

路由表對到商品頁之後，還剩一件事：ProductPage 怎麼拿到 id？最直接的寫法是在元件裡呼叫 useRoute()，讀 route.params.id。但這樣元件就綁死在 router 上：它只能在 router 底下使用，測試時也得架起整個 router 才能掛載它。路由的 props 選項換一個方向：由路由把參數當成 props 傳進去，元件只宣告 defineProps<{ id: number }>()，不知道自己是被路由顯示的，測試時直接傳 id: 2 就能掛載。

props 選項有兩種常見寫法，差別在型別：

寫法元件收到的 id
props: true字串 '2'，參數一律是字串，和 id: number 的宣告不符，開發模式出現 Invalid prop 警告
props: route => ({ id: Number(route.params.id) })數字 2；搭配 (\\d+)，不會出現 NaN

正規表示式和 props 函式是一組的：(\\d+) 保證進得來的一定是數字字串，Number() 才能放心轉型。到這裡，/menu/2 會對到 ProductPage，並傳進數字 2。但第二則回報還在：從 /menu/1 點到 /menu/2，畫面依然是美式咖啡。路由表沒有錯，問題出在商品頁什麼時候載入資料。

網址從 /menu/1 換到 /menu/2，畫面為什麼還是美式咖啡？

兩個網址都對到同一條路由、同一個 ProductPage，問題就出在「同一個」。商品頁目前在 onMounted 抓資料：

const props = defineProps<{ id: number }>()
onMounted(async () => {
  product.value = await api.getProduct(props.id)
})

從 /menu/1 到 /menu/2，Vue Router 發現新舊網址對到同一條路由、要顯示同一個元件，就不會卸載再重建，而是重用同一個元件實例，只更新 props。Vue Router 這樣做是因為重用比重建便宜，不必拆掉再重做整棵 DOM。官方文件也寫明：參數改變時，元件的生命週期鉤子不會再被呼叫。

於是 props.id 確實變成 2 了，但 onMounted 只在元件掛載時執行一次（第 8 課），這次沒有重新掛載，它就不會再跑，product 還是第一次抓到的美式咖啡。畫面停在美式咖啡，不是因為資料錯，而是根本沒有人去抓拿鐵。

要的是「id 每次改變都重新抓」，這正是 watch 的工作。和第 5 課的搜尋框一樣，要一開始就跑一次，還要取消過期的請求：

import { onWatcherCleanup, ref, watch } from 'vue'

watch(() => props.id, (id) => {
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort())     // id 又變了或元件卸載：取消舊請求
  status.value = 'loading'
  api.getProduct(id, { signal: controller.signal }).then(
    p => { product.value = p; status.value = 'success' },
    e => { if (!controller.signal.aborted) status.value = 'error' },
  )
}, { immediate: true })                            // 第一次進入也要抓

這段程式的三個部分各擋一種狀況，少一個都會出錯：

immediate: true 取代了原本的 onMounted。watch 預設只在值「改變」時執行，第一次進入商品頁時 id 從沒變過，少了這個選項，watch 一次都不會跑，畫面一直停在載入中。

取消舊請求處理的是競態。使用者快速從 1 點到 2，兩個請求都送出去了；如果 1 的回應比較晚回來，它會蓋掉已經顯示的拿鐵，網址是 /menu/2，畫面卻是美式咖啡，正好重現第二則回報。onWatcherCleanup 在 id 又變了、或元件卸載時執行，把上一次的請求取消；被取消的請求會走到錯誤的分支，所以那裡要先確認 signal.aborted，不把「我們自己取消的」當成真的錯誤。

換 id 時把狀態設回 loading：新資料回來之前，畫面上還是上一個商品。不先切回載入中，使用者會在 /menu/2 的網址下看到一陣子的美式咖啡，甚至以為點錯了。

另一個做法是讓每個網址都重建元件：<RouterView :key="route.fullPath" />。key 改變，Vue 就卸載舊的、掛載新的（第 7 課），onMounted 又會執行。程式比較簡單，但代價是每次換參數都重建整頁的元件樹、丟掉所有元件狀態（展開的區塊、輸入到一半的備註），也可能讓轉場動畫重跑。只在頁面本身很輕、而且本來就希望狀態全部歸零時才這麼做。Vue Router 也提供在路由更新前執行的鉤子，為什麼這課不用它，見課末〈補充與查表〉。

💡 實務上：看到 onMounted 裡讀路由參數，先問「參數會不會在同一頁裡改變」
咖啡店裡會在同一頁換參數的地方比想像中多：商品頁的「下一個商品」、後台訂單明細的「上一筆／下一筆」、從推薦商品的連結點到另一個商品。這類 bug 在開發時很難發現，因為開發者多半是從列表點進去，每次都是全新掛載。審查程式碼時看到頁面元件在 onMounted 裡依 id 抓資料，就該問這一句；測試也要涵蓋「同一個元件，props 從 1 改成 2」，練習 2 就是這樣測的。

商品頁修好了，剩下第一則回報：茶飲分類的網址傳給同事，打開卻是咖啡。這次不是載入時機的問題，而是分類根本沒有寫進網址。

茶飲分類的網址傳給同事，為什麼打開是咖啡？

菜單頁現在把分類放在元件的 ref 裡：const category = ref('coffee')。店長點「茶飲」時，ref 變成 'tea'，畫面換成茶飲，但網址一直是 /menu。同事打開 /menu，菜單元件全新掛載，ref 從預設值 'coffee' 開始，自然看到咖啡。同樣的事也發生在自己身上：從茶飲點進伯爵紅茶、再按上一頁，菜單元件重新掛載，篩選又回到咖啡。

第 15 課問過「狀態放哪裡」。網址也是一個可以放狀態的地方，而且它有元件和 store 都沒有的特性：會跟著連結被分享、被收藏，按上一頁時瀏覽器會把它還原。所以判斷標準是：使用者會想分享、收藏，或按上一頁要還原的狀態，就放在網址。菜單的分類、搜尋字、頁碼都是；購物車、展開了哪個區塊則不是。

網址裡放篩選的位置是 query string：網址 ? 後面的鍵值，例如 /menu?category=tea&page=2，在 Vue Router 裡讀 route.query。上一節的商品 id 用的是 params，分類為什麼不也做成 /menu/tea？兩者代表的意思不同：

params：/menu/2query：/menu?category=tea
代表資源的身分：哪一個商品、哪一筆訂單怎麼看這份清單：篩選、排序、頁碼
可以省略不行，少了就是另一條路由可以，沒有就用預設值
可以組合順序固定，難加新條件任意組合：?category=tea&sort=price&page=2

分類可以不給（用預設值），之後還會加排序、搜尋字、頁碼，這些都是 query 擅長的。放進 params 的話，每多一個條件就得改一次路徑。

決定放 query 之後，要先面對一件事：query 是使用者可以亂改的外部輸入。任何人都能把網址改成 ?category=<script> 再貼給別人，所以它和 API 回應一樣要驗證（TS 課第 26 課）。Vue 的插值會跳脫 HTML，<script> 顯示在畫面上只是一串文字，不驗證的麻煩主要在程式邏輯：分類變成不存在的值，菜單就篩成一份空清單，顧客以為店裡什麼都沒賣；同一個鍵出現兩次時值變成陣列，程式對它呼叫 .toLowerCase() 或做數字運算就直接拋錯，整頁白掉；page=-1 則原樣送去 API。等到哪天有人把這個值放進 v-html，或直接拼進請求，才會從 bug 變成安全問題。query 的值一律是字串；鍵沒有值時是 null；同一個鍵出現兩次會變成陣列。下面用瀏覽器內建的 URLSearchParams 看這些情況，Vue Router 的解析結果相同（?category 在 Vue Router 是 null，在 URLSearchParams 是空字串）。執行後看每一行印出的值和型別，最後一行是驗證後的結果：

驗證的做法是白名單：分類只接受 coffee、tea、food，頁碼只接受合理範圍內的正整數，其他任何值（包括 <script>、負數、陣列、沒給）一律退回預設值。不合法時不報錯、不顯示錯誤頁，因為使用者多半只是拿到一個舊的或被截斷的網址，讓他看到預設的菜單比較合理。

讀取解決了，接著是寫入：店長點「茶飲」時，要把 category=tea 寫進網址。這裡有兩個容易寫錯的地方。

第一，用 router.replace，不是 push。push 會新增一筆歷史紀錄，使用者在分類間切換五次，就多出五筆紀錄，想回首頁要按六次上一頁。切換篩選是「用不同方式看同一頁」，用 replace 換掉目前這一筆，上一頁直接回到進入菜單前的頁面。換到商品頁這種「到另一個地方」才用 push。

第二，保留其他 query。寫成 router.replace({ query: { category: 'tea' } })，會把網址上原有的 page=2、keyword 一起清掉，因為這等於指定「新的 query 只有 category」。要寫 router.replace({ query: { ...route.query, category: 'tea' } })，先展開原本的再覆蓋要改的那個。沒有給 path 或 name 時，Vue Router 留在目前的路徑。

讀要驗證、寫要 replace 又要保留其他鍵，每個篩選都寫一次很容易漏。把它包成 composable（第 12 課），回傳一個可寫的 computed，讀寫都經過網址，元件裡沒有另一份狀態：

const category = useQueryFilter('category', { allowed: ['coffee', 'tea', 'food'], fallback: 'coffee' })
category.value          // 從 route.query 讀，驗證過
category.value = 'tea'  // router.replace，網址變了，category 跟著變

這就是單一資料來源：網址是唯一的真相，畫面從網址算出來。常見的另一種寫法是「進入時從網址讀一次存進 ref，之後改 ref 再同步回網址」，看起來也能動，但它有兩份狀態，遲早不一致：使用者按上一頁、或點了另一個帶 query 的連結時，網址變了，ref 不會跟著變，畫面就和網址對不上。用 computed 直接讀 route.query，網址怎麼變，畫面就怎麼變，沒有同步的問題。

搜尋框每打一個字就 replace 網址，等於每個字觸發一次導航。實務上搭配第 5 課的防抖（debounce），停止輸入 300ms 後才寫入網址；輸入框本身的文字可以先放在本地 ref，那是「還沒送出的草稿」，送出後才成為網址的狀態。
💡 實務上：後台列表的篩選放網址，客服回報就能直接重現
咖啡店後台的訂單列表會有日期區間、狀態、頁碼，店長常說「你看這個」然後貼網址給你。篩選放在 query，你打開就是同一個畫面，不用再問「你選了哪些條件」。但網址會留在瀏覽器歷史、伺服器 log、分享出去的訊息裡，所以 token、手機號碼、Email 這類個資不要放進 query。篩選條件很多、很長（例如勾選幾十個商品）時，就不適合全塞進網址，可以改存在伺服器、網址只帶一個 id。

開場的三則回報都修好了。但顧客從茶飲點進伯爵紅茶、再按上一頁時，還有一個不舒服的地方：分類已經從網址還原成茶飲，菜單卻重新載入了一次，而且捲回最頂端。

從商品頁按上一頁，菜單為什麼重新載入、捲回頂端？

分類能還原，是因為它在網址裡；但菜單元件本身在顧客進入商品頁時就被卸載了，按上一頁回來時重新掛載：重新抓一次菜單資料，元件裡的狀態全部從頭開始。另外，整個視窗的捲動位置也回到頂端。這是兩件不同的事，要分開處理。

先處理元件被卸載。KeepAlive 是 Vue 內建的元件：被它包住的元件切走時不卸載，而是把實例（連同資料和 DOM）快取起來，切回來時原封不動地放回去，不用重新抓資料，也不用重建畫面。和 RouterView 一起用時，KeepAlive 要放在 RouterView 的 slot 裡，快取的是路由元件：

<RouterView v-slot="{ Component }">
  <KeepAlive include="MenuPage" :max="5">
    <component :is="Component" />
  </KeepAlive>
</RouterView>

RouterView 透過 slot 把「這次要顯示的元件」交給你（Component），你用 <component :is> 畫出它，外面再包 KeepAlive。這樣寫，KeepAlive 才包得到真正的頁面元件。

include 決定快取誰：只快取名稱符合的元件，不設就是全部快取。比對的是元件的 name；<script setup> 的元件從 Vue 3.2.34 起會依檔名推斷，MenuPage.vue 的名稱就是 MenuPage。咖啡店只需要菜單被保留，商品頁每次都該顯示最新資料，所以只 include MenuPage。

max 決定最多快取幾個實例，超過時丟掉最久沒用的。快取不是免費的：每個快取的實例連同它的資料、DOM 都留在記憶體裡，一定要設上限。

被快取的元件也有自己的生命週期。切回來時不會再執行 onMounted，而是執行 onActivated；被切走時執行 onDeactivated，而不是 onUnmounted。這會影響兩件事：快取的資料可能已經過期（例如顧客看商品的時候，可頌售完了），要在 onActivated 裡重新整理；元件裡的計時器在被切走時不會隨卸載清掉，要在 onDeactivated 暫停（第 8 課）。

KeepAlive 保留的是元件的狀態：資料、輸入框內容、元件內可捲動區塊的位置。整個視窗的捲動位置不屬於任何元件，由 router 的 scrollBehavior 處理。它是建立 router 時多給的一個函式，每次導航完成、新頁面畫出來之後，router 會呼叫它，依它回傳的位置捲動視窗：

const router = createRouter({
  history: createWebHistory(),
  routes,
  scrollBehavior(to, from, savedPosition) {
    return savedPosition ?? { top: 0 }
  },
})

to 和 from 是這次導航的目的地與出發點，和導航守衛拿到的一樣。第三個參數 savedPosition 是 router 在離開某個網址時替它記下的捲動位置，只有按瀏覽器的上一頁／下一頁（觸發 popstate）回到那個網址時才會帶進來（重新整理頁面時也會帶上那一頁記下的位置）；一般點連結、呼叫 router.push 時它是 null。所以這一行的意思是：有記下的位置就回到那裡；沒有就是去新頁面，捲到頂端 { top: 0 }。不寫 scrollBehavior 時，router 不會替你處理視窗捲動。

vue-router 5.4.0 的型別宣告已把 scrollBehavior 標成 deprecated，但替代方案仍是實驗性的，目前照用即可（細節見課末〈補充與查表〉）。

KeepAlive 和 scrollBehavior 雖然分開設定，效果卻有因果關係：savedPosition 要捲得到，頁面在那一刻必須已經夠高。菜單被 KeepAlive 快取時，DOM 原封不動放回來，頁面高度和離開前一樣，馬上就能捲回原位；沒有快取時，菜單重新掛載、資料還在路上，頁面只有一小截，瀏覽器最多只能捲到底，捲不到原本的位置。這種情況下，scrollBehavior 可以回傳一個 Promise，router 會等它 resolve 再捲動，例如等資料載入完成後才回傳 savedPosition。

回頭比較一下網址和 KeepAlive 各做了什麼：篩選放在網址之後，就算菜單沒被 KeepAlive 快取，按上一頁回來也會從網址還原分類；KeepAlive 省掉的是重新抓資料與重建畫面。兩者解決的是不同的問題，不能互相取代：分享給同事的連結沒有任何快取可用，只能靠網址。

菜單的來回體驗順了。最後一個問題出在路由表本身：店員用的後台 /admin 加進路由表之後，顧客的手機第一次打開點餐網站，也得下載後台的程式碼。

後台頁加進路由表後，顧客為什麼也要下載它？

路由表的 component 如果寫成檔案開頭 import 進來的元件，打包時這些頁面都會跟著入口一起打包，第一次打開網站就要全部下載。後台管理頁只有店員會用，顧客卻每次都替它付下載時間。懶載入（lazy loading）就是「用到才下載」：

{ path: '/admin', component: () => import('./views/AdminPage.vue') }

差別在 component 給的不再是元件，而是「回傳 Promise 的函式」。Vue Router 第一次進入這條路由時才呼叫它、等它載入完成再顯示頁面，之後用快取的結果，不會重複下載。動態 import() 也讓 Vite 把這個檔案切成獨立的 chunk（打包後的一個 JavaScript 檔），顧客沒進後台就不會下載它。官方文件建議所有路由都用動態 import，不只後台。

容易犯的錯是用 Vue 的 defineAsyncComponent 包路由元件。兩者看起來很像，但官方文件寫明不要把非同步元件當路由元件：路由元件直接給函式就好。defineAsyncComponent 是用在頁面裡面的大元件（例如圖表）。拆完的效果要用建置結果驗證，第 23 課會看 chunk 的大小。

💡 實務上：懶載入的頁面，部署新版後可能載不到
Vite 建置出的 chunk 檔名帶有依內容算出的雜湊（例如 AdminPage-a1b2c3.js），內容一改檔名就變，部署新版後舊檔名就不見了。如果使用者一直開著舊版的分頁，之後才點進後台，瀏覽器會去要已經不存在的舊 chunk，導航就失敗、畫面停住。常見的處理是部署時保留上一版的檔案一段時間，或在 router.onError 偵測到載入模組失敗時重新整理頁面。上線前可以問負責部署的人：「舊版的 JS 檔會不會被直接刪掉？」

回到開場：重新整理靠伺服器回傳 index.html 加上前端的找不到頁面；換商品靠 watch 監看 props；分享篩選靠把分類放進 query、網址當唯一來源；按上一頁的體驗靠 KeepAlive 與 scrollBehavior；顧客不下載後台靠懶載入。點餐網站的每個網址，現在都會畫出它指的那個畫面。

補充與查表

以下是主線用不到、但接手專案或查問題時會遇到的細節。

  • hash 模式與 memory 模式：hash 模式（createWebHashHistory()）的網址長得像 /#/menu/3，# 後面的部分不會送到伺服器，所以伺服器不用設定。代價是網址比較醜，官方文件也說明它對 SEO 不利。能改伺服器設定時，用 createWebHistory()；只能放在無法設定的靜態空間時，才選 hash 模式。測試和伺服器渲染用 createMemoryHistory()：歷史紀錄只存在記憶體，不碰瀏覽器的網址。
  • /:pathMatch(.*)* 結尾的 *：讓 pathMatch 變成陣列（/a/b → ['a', 'b']），用名稱導航過去時斜線才不會被編碼成 %2F。
  • onBeforeRouteUpdate：Vue Router 也有 onBeforeRouteUpdate((to, from) => …)，在同一個元件、路由要更新之前執行，可以取消導航。它只在 router 底下有用；用 props 加 watch 的寫法，元件不接 router 也能單獨測試。
  • scrollBehavior 的 deprecated 標記：vue-router 5.4.0 的型別宣告已經把 scrollBehavior 標成 deprecated，指向 vue-router/experimental 的 useScrollRestoration()，但後者還在實驗階段，目前 scrollBehavior 仍可使用。
  • vue-router 5 改了什麼：vue-router 5.0.0 在 2026-01-29 發布，官方稱它是「無聊」的過渡版本。
    • API 和 4 相同：沒有用 unplugin-vue-router 的專案升級沒有破壞性變更（IIFE 版本不再內含 @vue/devtools-api 是例外）。這課所有寫法 4 和 5 都適用。
    • 併入檔案式路由：原本的 unplugin-vue-router 併進核心套件，入口是 vue-router/vite、vue-router/auto-routes：依 src/pages/ 的檔案結構自動產生路由表，路由名稱和 params 自動有型別。data loaders（在導航時先載入頁面資料）放在 vue-router/experimental，仍是實驗性的。
    • 守衛的 next 已標成 deprecated：導航守衛改成回傳值，return false 取消、回傳路由位置則轉址，什麼都不回傳就放行。看到舊程式 (to, from, next) => { …; next() } 要知道它將被移除，第 20 課會用回傳值的寫法。
    • 官方預告 Vue Router 6 只支援 ESM，並移除已過時的 API。

練習

在 learn/ 執行 node check.mjs vue 19。測試用 createMemoryHistory() 建立真正的 router，在 happy-dom 裡掛載 <RouterView />；商品資料來自第 5 課用過的假 API，透過 menu-api.ts 的 MENU_API 注入（第 13 課）。三題互相獨立：練習 2、3 的測試自己建路由表，不依賴練習 1。

練習 1：完成 router.ts 的 createAppRouter(history)。路由名稱依序是 home（/）、menu（/menu）、product（/menu/:id，id 只接受數字，用 props 函式轉成數字傳給 ProductPage）、orders（/orders，顯示 OrdersLayout）、它的子路由 order-list（空字串，OrderList）與 order-detail（:orderId，只接受數字，轉成數字傳給 OrderDetail），以及 not-found（其他所有路徑，顯示 NotFound，網址不變）。頁面元件都已經寫好。測試會走過每個網址、檢查收到的 props 型別，並用名稱組出網址。

練習 2：ProductPage.vue 現在只在 onMounted 抓商品，從 /menu/1 換到 /menu/2 時畫面不變。改成一進入就載入、props.id 每次改變都重新載入，換 id 時先回到「載入中…」；舊的請求比較晚回來也不能蓋掉新的（用 api.getProduct(id, { signal }) 並在清理時取消）。只用 props 拿 id，不要用 useRoute()：測試也會不接 router 單獨掛載它。顯示的文字照檔案開頭的註解。

練習 3：寫出 useQueryFilter(key, { allowed, fallback })，回傳可寫的 computed。讀取時從 route.query[key] 取值：不在 allowed 裡、沒有、或是陣列都回傳 fallback。寫入時用 router.replace，保留路徑和其他 query。測試會直接改網址看它是否跟著變、塞入 <script>、切換兩次篩選後按上一頁（要直接回到首頁），以及從商品頁按上一頁後檢查篩選是否從網址還原。

練習 4：用 createWebHistory() 的咖啡店網站，在首頁點連結進入 /menu/3 一切正常，但在 /menu/3 按重新整理，出現伺服器的 404 頁面。原因是？

✓ 從首頁點連結時，Vue Router 用 pushState 改網址，沒有發請求，所以正常；路由表沒問題。重新整理時瀏覽器真的對伺服器發出 GET /menu/3，這時 JavaScript 還沒載入，前端的路由表、NotFound 路由都幫不上忙。伺服器要把找不到的路徑都回傳 index.html（Nginx 的 try_files $uri $uri/ /index.html），JavaScript 載入後 Vue Router 再讀網址畫出商品頁。push 和 replace 只影響歷史紀錄的筆數。

練習 5：菜單的分類篩選，該用 params（/menu/coffee）還是 query（/menu?category=coffee）？

✓ 篩選是「怎麼看這份清單」，可以沒有（用預設值），之後還會加上排序、搜尋字、頁碼，query 能任意組合。放進 params 的話，/menu/coffee 還會跟 /menu/:id 搶同一個位置，每加一個條件都要改路徑。params 適合「這是哪一個資源」，例如商品 id。不管哪一種，值都來自使用者可以亂改的網址，都要驗證。

練習 6：App 寫了 <RouterView v-slot="{ Component, route }"><KeepAlive><component :is="Component" :key="route.fullPath" /></KeepAlive></RouterView>，沒有設 max。使用者逛了 50 個商品頁，會怎樣？

✓ KeepAlive 用 key 區分快取。key 是 fullPath，每個商品網址各自是一份快取；沒設 max 就沒有上限，記憶體會一直長。沒有 key 時，同一個元件只有一個實例被重用（要用 watch 處理參數改變）。快取不是越多越好：用 include 只快取需要的頁面（例如列表），用 max 設上限。

常見錯誤

  • 以為重新整理 404 是 Vue Router 的問題：history 模式要伺服器把找不到的路徑回傳 index.html。
  • 子路由的 path 以 / 開頭：'/:orderId' 變成根路徑，不在 /orders 底下。子路由寫相對路徑。
  • 用 props: true，卻把 prop 宣告成 number：params 一律是字串。用 props 函式轉型，並用 (\\d+) 擋掉非數字。
  • 參數改變時只靠 onMounted 載入：同一條路由換參數時元件被重用，onMounted 不再執行。用 watch(() => props.id, …, { immediate: true })，並取消過期的請求。
  • 相信 query 的值，不驗證：使用者可以把網址改成任何東西，包括陣列和 <script>。只接受白名單，其他用預設值。
  • 打字或切換篩選用 push：歷史紀錄被塞滿，上一頁按到手酸。篩選用 replace，到另一個頁面才用 push。
  • 寫入 query 時覆蓋其他鍵：{ query: { category } } 會清掉頁碼和搜尋字。用 { ...route.query, category }。
  • 篩選同時存在 ref 和網址：兩份狀態不同步，按上一頁時畫面和網址對不上。讓網址當唯一的來源，用 computed 讀寫。
  • KeepAlive 沒設 max：快取的實例只會增加。設 include 和 max，在 onActivated 重新整理可能過期的資料。
  • 用 defineAsyncComponent 當路由元件：官方文件明確不建議。路由直接給 () => import('…')。
  • 沿用守衛的 next()：已標成 deprecated。守衛改用回傳值。

小結

  • SPA 用 History API 改網址不重新載入；Vue Router 的 push／replace 對應 pushState／replaceState。重新整理時瀏覽器真的向伺服器要那個路徑，所以 history 模式需要伺服器把找不到的路徑回傳 index.html；hash 模式不用設定，但網址較醜、不利 SEO。
  • 伺服器不再回 404 之後，路由表負責所有判斷：動態參數加正規表示式限制格式；/:pathMatch(.*)* 接住其他路徑；具名路由讓連結不依賴路徑；巢狀路由的子元件顯示在父元件的 RouterView。
  • 用 props 函式把參數轉型後傳給頁面，元件不依賴路由物件，可以單獨測試。
  • 同一條路由換參數時元件被重用：用 watch（immediate＋取消舊請求＋先回到載入中）處理；RouterView 加 key 可以強制重建，但會丟掉所有狀態。
  • 可分享、要能用上一頁還原的狀態放進 query；query 是外部輸入，要驗證；篩選用 replace 並保留其他鍵；網址是唯一的來源。
  • KeepAlive 放在 RouterView 的 slot 裡，用 include、max 控制，用 onActivated 重新整理；視窗的捲動位置由 scrollBehavior 還原。路由元件用 () => import() 懶載入，不要用 defineAsyncComponent。
  • vue-router 5 的 API 和 4 相同，併入了檔案式路由；data loaders 仍是實驗性；守衛的 next 已不建議使用（課末〈補充與查表〉）。

下一課在路由上加上守衛：未登入導向登入頁、沒有權限導向 403，並搞清楚前端的權限檢查能做到什麼、不能做到什麼。
