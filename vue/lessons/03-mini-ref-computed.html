階段 1：響應式原理：自己做一個 · 第 3 課

完成迷你版：ref 與 computed

前兩課做出了迷你版的 reactive 和 effect：effect 執行時讀到哪些屬性，就被記成它的依賴；那些屬性被改，effect 就重跑。這一課用這套工具做咖啡店點餐頁上的一張拿鐵卡片，卡片上有四樣東西：

  • 杯數 qty：使用者按 ＋／－ 改的數字。
  • 小計 subtotal：杯數 × 110。
  • 總額 total：小計再加 10 元提袋費。
  • 「偶數杯享折扣」徽章：杯數是偶數時顯示。

目標是：使用者按一下 ＋，卡片上用到的值全部自動跟上；沒必要的計算一次都不做；結果沒變的地方，畫面也不白白重畫。只用第 2 課的工具會卡在三個地方：杯數只是一個數字，reactive(1) 包不了；小計和總額是算出來的，每次重畫都重算很浪費，另外存一份又容易忘記更新；杯數從 2 變 4 時徽章的結果沒變，畫面卻還是會重畫。這課依序解掉這三個問題，中間還會遇到一個新問題：算出來的值被畫面讀了，畫面卻收不到通知。全部解完，做出來的就是 Vue 的 ref 和 computed。

這課的路線：
  1. 杯數只是一個數字，怎麼讓它被追蹤？做出 ref，也就是 Vue 的 .value 為什麼存在。
  2. 小計要在什麼時候算？從「每次都算」和「算一次就存著」兩個錯誤版本，改到依賴改了才過期的 computed。
  3. 畫面讀小計和總額，杯數改了畫面為什麼不動？讓 computed 也能被別人依賴。
  4. 杯數從 2 變 4，徽章為什麼不該重畫？computed 的值沒變就不通知。
  5. 知道 computed 怎麼運作之後，哪些寫法會出事，迷你版和真正的 Vue 又差在哪。
這課會用到：
  • 第 2 課的 effect、track、trigger：effect 執行時讀到的屬性被 track 記進依賴表，屬性被改時 trigger 讓它們重跑；每次重跑前清掉舊依賴，有 scheduler 的 effect 由 scheduler 決定何時重跑。
  • TS 課第 3 課的 getter／setter：get value() { … } 讓讀 .value 時執行函式，set value(v) { … } 讓寫入時執行函式。
  • TS 課第 19 課的泛型：Ref<T> 表示「.value 的型別是 T」的 ref。
練習區在瀏覽器的 Web Worker 裡跑 TypeScript，不能 import 套件，所以每一題最上面附了一份迷你核心，往下捲到「你要寫的部分」才是題目。灰底的程式區塊是真正的 Vue，不能執行。

杯數只是一個數字，怎麼讓它被追蹤？

先回想響應式靠的是什麼：讀取的那一刻記下「誰在讀」，寫入的那一刻通知「讀過的人」。兩個時機都要能插手執行我們自己的程式碼。第 1 課用 Proxy 做到這件事，但 Proxy 只能包物件，傳一個數字進去會直接丟錯。

那把杯數放在一般的變數裡呢？let qty = 1 之後寫 qty = 2，JavaScript 沒有提供任何機制讓你在「讀變數」或「寫變數」時執行程式碼。讀寫變數就是讀寫變數，中間沒有地方可以加 track 或 trigger。所以一個單獨的數字，不管怎麼寫都追蹤不到。

能攔截的只有物件的屬性。解法就是把值放進一個物件的屬性裡，所有讀寫都經過這個屬性。而要攔截「一個已知名字的屬性」，不需要 Proxy，用 getter／setter 就夠了：讀 .value 時執行 getter，寫 .value 時執行 setter。下面這格執行後看兩件事：第一行是 Proxy 包數字時丟出的錯誤訊息；之後每次讀、寫 price.value 都會印出一行，表示這兩個時機我們都插得上手。

把 getter 裡換成 track、setter 裡換成 trigger，就是 ref：一個只有 value 屬性的物件，讀 .value 時記下誰在讀，寫 .value 時通知讀過的人。所以 .value 不是 Vue 的怪癖，而是讓 JavaScript 能攔截讀寫必須付出的代價。你在 Vue 範本裡寫 {{ qty }} 不用加 .value，是因為 Vue 在範本裡遇到 ref 時會自動幫你讀 .value，這個動作叫自動解包（unwrap），它的規則在第 4 課講。

上面的 price 只會印 log。要把它接上第 2 課的追蹤，變成真正能用的 ref，還要回答三個問題：依賴記在哪裡、寫入一樣的值要不要通知、存的是物件時怎麼辦。

依賴要記在哪裡？

reactive 物件的依賴放在第 2 課的依賴表（targetMap）裡：先用物件查出它的 Map，再用屬性名稱查出那個屬性的 Set，Set 裡是讀過它的 effect。要查兩層，是因為一個 reactive 物件有很多屬性，每個屬性要分開記。

ref 只有一個屬性 value，不需要這兩層查詢，直接在每個 ref 裡放一個自己的 Set，叫 dep，讀過這個 ref 的 effect 都記在裡面。每個 ref 一份 dep 很重要：點餐頁上方還有一個「目前分店」的 ref，杯數的 ref 和分店的 ref 如果共用同一個 Set，改杯數就會讓只顯示分店名稱的 effect 一起重跑。

為了讓 ref 能直接操作自己的 Set，這課在核心裡加了兩個小函式：trackDep(dep) 把目前的 effect 記進某個 Set，triggerDep(dep) 通知某個 Set 裡的 effect。原本的 track、trigger 改成先從依賴表查出 Set，再呼叫這兩個函式。這樣 reactive 和 ref 走同一套記錄與通知的程式，差別只在 Set 從哪裡來。

寫入一樣的值，要不要通知？

使用者在杯數輸入框打了 1，原本就是 1。值沒變，讀過它的 effect 重跑也只會得到一樣的結果，所以 setter 裡要先比較新舊值，一樣就不通知。

比較時直覺會寫 newValue !== oldValue，但它有一個例外：NaN（not a number，數字運算失敗時得到的值）跟任何值比較都不相等，包括它自己。使用者在杯數欄位打了「abc」，Number('abc') 就是 NaN；之後每次再寫入 NaN，NaN !== NaN 都成立，ref 會以為值變了，每次都通知。Object.is 是 JavaScript 內建的「是不是同一個值」判斷，它把 NaN 和 NaN 視為相同。下面這格執行後看兩行的差別：

存的是物件時怎麼辦？

ref 也可以存物件，例如 const cup = ref({ qty: 1 })。問題出在改物件裡面的屬性：cup.value.qty++ 這一行，先讀 cup.value（呼叫 getter），拿到物件後再改它的 qty。整個過程沒有寫 cup.value，setter 沒被呼叫，ref 不知道有東西變了，讀過 cup.value.qty 的 effect 不會重跑。

物件屬性的讀寫，第 1、2 課已經有工具處理：reactive。所以 ref 收到物件時，存的不是物件本身，而是 reactive(物件)。這樣就有兩層分工：qty 的讀寫由 reactive 的 Proxy 追蹤；整個換掉（cup.value = { qty: 5 }）由 ref 的 setter 追蹤。換上去的新物件也要先包成 reactive，不然換過之後，改裡面的屬性又追蹤不到了。

這三件事就是練習 1。做完之後杯數可以被追蹤了，下一步是卡片上從杯數算出來的小計。

小計要在什麼時候算？

小計是杯數 × 110，只要知道杯數就算得出來，不需要另外存。像這樣可以從其他狀態算出來的資料，叫衍生狀態（derived state）。衍生狀態有兩種直覺的寫法，各有一個問題：每次要用都重新算，或者算一次就存起來。下面這格把兩種都寫出來，執行後看三行：第一版讀 3 次算了幾次、第二版讀 3 次算了幾次、杯數改成 3 之後第二版回傳什麼。

第一版永遠正確，但讀幾次就算幾次。小計只是一個乘法，看不出差別；換成「從幾千筆訂單裡過濾出今天的、再加總」，而畫面每次重畫、好幾個地方都要讀它，就會一直重做同樣的工作。第二版只算一次，但快取永遠不會過期，杯數改成 3 之後還是回傳 220，畫面顯示錯的金額。

所以要的是第三種：有快取，而且快取在該過期的時候過期。那快取什麼時候該過期？答案是「getter 讀過的資料，有任何一個改變時」。這正好是 effect 已經會做的事：把 getter 放進 effect 裡執行，getter 讀了哪些資料就自動記成依賴；那些資料改變時，effect 會被觸發。我們不用自己列出小計依賴杯數。

但 effect 被觸發時會馬上重跑，這不是我們要的：杯數改了，不代表現在就有人要讀小計，馬上算可能白算。第 2 課的 scheduler 正好解決這件事：effect 有 scheduler 時，trigger 不會直接重跑 effect，而是呼叫 scheduler，由它決定怎麼做。我們的 scheduler 只做一件事：記下「快取過期了」。

記錄的方式是一個布林變數，慣例叫 dirty 旗標（dirty flag）。dirty 是 true 表示快取過期，下次讀要重算；false 表示快取還能用。還剩一個細節：第 2 課的 effect 建立時會先執行一次，好收集依賴；但小計建立時也還沒人讀，不該先算。所以核心的 effect 多了一個 lazy 選項，設成 true 時建立後不執行，等你自己呼叫 run()。三樣東西組起來就是第三版：

function computed(getter) {
  let value
  let dirty = true                          // 一開始沒有快取
  const runner = effect(() => { value = getter() }, {
    lazy: true,                             // 建立時先不執行
    scheduler: () => { dirty = true },      // 依賴改變：只標記過期，不算
  })
  return {
    get value() {
      if (dirty) { runner.run(); dirty = false }   // 有人讀、而且過期了，才算
      return value
    },
  }
}

注意它只在讀 .value 時才可能執行 getter。這種「有人要用才算」的策略叫延遲計算（lazy evaluation）。用 getter 的執行次數看各個時間點：

💡 實務上：列表頁的篩選、排序、合計幾乎都是 computed
咖啡店後台的訂單列表很典型：狀態篩選、關鍵字搜尋、排序、「今日營業額」都是從同一份訂單資料算出來的，各寫成一個 computed，資料一變全部自動跟上。新手常改成在範本裡呼叫函式（{{ filterOrders() }}），結果正確，但元件每次重新渲染都會重跑，連使用者只是在旁邊的備註欄打字也一樣；computed 只在依賴改變時才重算。反過來，qty * price 這種一行就算完的便宜運算，直接寫在範本裡也可以，不必每個都包成 computed。真正重算起來貴的是「過濾、排序幾千筆」這類工作，這種一定要放在 computed 裡。

到這裡小計會快取、會過期了。但拿鐵卡片的畫面是要讀小計和總額的，杯數改了，畫面會跟著更新嗎？用這個第三版，答案是不會。

畫面讀小計和總額，杯數改了畫面為什麼不動？

先把「畫面」換成我們熟悉的東西：第 2 課講過，Vue 的元件渲染本身就是一個 effect。所以拿鐵卡片的畫面，等於一個讀 total.value 的 effect；總額是第二個 computed，total = computed(() => subtotal.value + 10)，它讀小計，小計讀杯數。

照第三版跟著執行一次。畫面 effect 執行時讀 total.value，執行 total 物件上的 get value()，拿到值，但這段程式碼沒有呼叫任何 track，沒有東西記下「畫面依賴 total」。接著杯數從 1 改成 2：杯數的 dep 裡記著的是小計內部的 runner，所以 trigger 呼叫小計的 scheduler，小計的 dirty 變成 true，然後就結束了。總額不知道小計過期，畫面也沒人通知，卡片上還是 120。

問題在於 computed 只做了一半的角色。對杯數來說，computed 是依賴者：它的 runner 讀了杯數，杯數改了要通知它。但對畫面來說，computed 是被依賴者：畫面讀了它，它過期了要通知畫面。被依賴者這一半，跟 ref 要做的事完全一樣，所以做法也一樣：給每個 computed 一個自己的 dep，搭配上一節的 trackDep、triggerDep。接下來把讀了某個 computed 的人（例如總額、畫面 effect）叫做它的「下游」，它讀的來源（例如杯數）叫「上游」；通知從上游往下游傳。要改三個地方，每一個都有它的理由：

  • 讀 .value 時 trackDep(dep)：記下是誰讀了這個 computed，這樣過期時才知道要通知誰。
  • scheduler 先把 dirty 設成 true，再 triggerDep(dep)：順序不能反。下游被通知後會立刻重跑，重跑時就會讀 .value；如果那時 dirty 還是 false，getter 判斷快取還能用，下游拿到的是舊的小計。
  • scheduler 被呼叫時如果已經是 dirty，直接 return：已經 dirty 表示上一次通知過下游，下游還沒來讀。再通知一次不會帶來新的資訊，只會讓下游多跑一次。

注意 scheduler 裡還是不呼叫 runner.run()：過期時只標記、只通知，不計算。沒有人讀的 computed，依賴改多少次都不執行 getter，lazy 的好處保留下來。

兩層 computed 串起來時，通知和計算的方向相反，看下面這張圖：

①杯數被寫入時，通知從左往右傳：小計標記 dirty 並通知總額，總額標記 dirty 並通知畫面 effect，一路上都沒有計算。②畫面 effect 重跑時，計算從右往左拉：它讀 total.value，總額發現自己 dirty 而重算，重算時讀 subtotal.value，小計也發現自己 dirty 而重算。所以只有最後真的有人讀的那條路線會被算，沒人讀的分支永遠不會算。這是練習 3。

現在杯數一改，卡片上的小計和總額都會更新。輪到最後一樣東西：「偶數杯享折扣」徽章。照現在的做法，它會多重畫好幾次。

杯數從 2 變 4，徽章為什麼不該重畫？

徽章依賴一個 computed：isEven = computed(() => qty.value % 2 === 0)，畫面讀 isEven 決定要不要顯示。杯數從 2 改成 4，isEven 還是 true，徽章的畫面完全不用變。但照練習 3 的做法，杯數一變，isEven 的 scheduler 就把自己標成 dirty 並通知畫面；畫面重跑，讀到 isEven 重算的結果還是 true，重畫出一模一樣的東西。一張卡片多重畫一次看不出來，但一個頁面上幾十個元件都依賴某個很少變的 computed（例如「是不是會員」「營業中嗎」）時，每次來源一動，這幾十個元件都會白白重新渲染。

Vue 3.4 起改掉了這件事：computed 算出來的值沒變時，依賴它的 effect 不會重跑（Vue 3.4 發布公告）。在 Vue 3.5.44 實際執行的結果：

const qty = ref(2)
const isEven = computed(() => qty.value % 2 === 0)
watchEffect(() => console.log(isEven.value))   // 印出 true

qty.value = 4   // 沒有印出任何東西：isEven 還是 true
qty.value = 5   // 印出 false
qty.value = 7   // 沒有印出任何東西

要做到這件事有一個矛盾：要知道「值沒變」，就得重算一次再比較；但 computed 是 lazy 的，依賴改了不想馬上算。Vue 的做法是分兩步：依賴改變時，只把下游標記成「可能過期」；下游真的要重跑之前，先問它依賴的 computed「你的值變了嗎」，這時 computed 才重算並比較，值沒變就不重跑下游。

我們的迷你版用比較簡單的規則，在畫面上的效果相同。關鍵是看有沒有人依賴這個 computed，也就是它的 dep 是不是空的：

  • 沒有人依賴（dep.size === 0）：跟原本一樣，只把 dirty 設成 true，保持 lazy。沒人要讀，就沒理由現在算。
  • 有人依賴：既然通知出去之後下游一定會來讀，就現在重算，用 Object.is 比較舊值和新值，不一樣才 triggerDep(dep)。舊值要在重算之前先存起來，否則重算完 value 已經是新值，等於拿新值跟新值比，永遠相等，下游永遠不會被通知。

代價是：有下游時，迷你版在依賴改變的當下就算，而 Vue 會等到下游要重跑時才算。結果一樣，時機不同，本課最後一節的對照表會再提到。這是練習 4，題目裡杯數改叫 count。

做完練習 4，拿鐵卡片的目標都達成了：杯數可追蹤、小計和總額有快取且會過期、畫面跟著更新、值沒變就不重畫。但這也表示 computed 的 getter 什麼時候執行，已經不是寫程式的人決定的，這會直接影響 computed 該怎麼寫。

知道 computed 怎麼跑之後，哪些寫法會出事？

回頭看前三節做出來的 computed，有三個特性：getter 什麼時候執行，由誰在什麼時候讀決定；算出來的結果是一份快取；值有沒有變，用 Object.is 判斷。每一個特性都對應一條規矩，違反了就會出現很難查的 bug。

getter 只算值，不做別的事

從實作可以看出：getter 可能 0 次都不執行（沒人讀）、可能延後到讀取時才執行、也可能在依賴一改就執行（迷你版有下游時）。如果在小計的 getter 裡順便呼叫 API 查會員折扣、或把購物車寫進 localStorage，這些動作就變成時機不可預期：有時沒發請求，有時一次改動發了好幾次。

所以 getter 要寫成純函式（pure function）。純函式有兩個條件：同樣的輸入一定得到同樣的輸出；除了回傳值，不改動外面的任何東西（不發請求、不改其他狀態、不寫儲存空間），這些「改動外面」的事叫副作用（side effect）。純函式執行 0 次或 10 次都不會造成差別，正好配得上 computed 不固定的執行時機。要在資料改變時「做事情」，用 watch（第 5 課）。

這也引出一個常見的判斷：一份資料該用 computed、watch 還是 ref？先問它是從哪裡來的：

需求用什麼例子
從現有狀態算出一個值，給畫面或其他程式讀computed（或在範本裡呼叫的純函式）購物車總額、篩選後的商品清單、「可以結帳」
資料改變時對外做一件事watch／watchEffect關鍵字改變時呼叫搜尋 API、把草稿存進 localStorage
使用者輸入、伺服器回傳的資料ref／reactive（狀態本身）備註欄的文字、API 回來的訂單

最常見的誤用是把第一列寫成第二列：const total = ref(0)，再加一個 watch 在購物車改變時更新它。這就是「小計要在什麼時候算？」那節的第二版「另外存一份」的問題換個樣子出現：多一個要維護的地方，而且 watch 是在購物車改變之後才執行，中間那段時間讀到的 total 是舊的。能算出來的，就用 computed。

不要改 computed 回傳的物件

computed 回傳的是快取，也就是某個時間點算出來的快照。依賴一變，下次讀取時會整個重算出一份新的，換掉舊快取。如果你拿到 filteredOrders.value 之後改了裡面的某筆訂單，改的是快照，來源的訂單資料沒變；下次重算時你的修改就不見了。要改，就改它依賴的來源狀態，讓 computed 重算出新結果。

每次回傳新物件，「值沒變就不通知」會失效

上一節的判斷靠 Object.is，而 Object.is 比的是物件的身分，不是內容。computed(() => ({ even: qty.value % 2 === 0 })) 每次重算都建立一個新物件，就算 even 一樣，新舊物件也不是同一個，下游每次都會被通知。最簡單的避法是回傳原始值（數字、字串、布林）；一定要回傳物件時，Vue 3.4 起可以在內容相同時回傳上一次的物件，寫法見課末「補充與查表」。

💡 實務上：code review 時看 computed，先看 getter 有沒有偷改東西
最常見的一個坑是排序：computed(() => orders.value.sort(byTime)) 看起來只是算值，但陣列的 sort() 會直接改掉原本的陣列，等於在 getter 裡改了來源狀態；要寫成 [...orders.value].sort(byTime) 或 orders.value.toSorted(byTime)。reverse()、splice() 也一樣會改原陣列。其他要抓的還有：getter 裡呼叫 API、跳頁、寫 localStorage，以及用「一個 ref 加一個 watch」去同步一個其實用 computed 就能算出來的值。這些不用全靠人眼，eslint-plugin-vue 的 vue/no-side-effects-in-computed-properties 規則能抓到一部分（例如在 getter 裡直接改狀態），團隊開好 lint 比每次 review 時提醒有效。

規矩講完，迷你版也完成了。下一課開始改用真正的 Vue，先對照一下兩者差在哪。

迷你版和真正的 Vue 差在哪？

到這裡，迷你版的四個零件都齊了：reactive、effect、ref、computed。真正的 Vue 用的資料結構不同，觀念相同，對照如下：

迷你版Vue 3.5差別
reactive(obj)reactive(obj)Vue 另外處理陣列方法、Map／Set、readonly、shallow 等
ref(value)：getter／setter＋自己的 depref(value)：RefImpl 類別，同樣有自己的 dep，比較時用原始值（toRaw）Vue 的 ref 在範本和 reactive 物件裡會自動解包
computed(getter)：dirty 旗標＋自己的 depcomputed(getter)：ComputedRefImpl，也是同時是依賴者與被依賴者Vue 用版本號判斷是否過期，有下游時也維持 lazy
effect(fn, { scheduler })應用程式裡不直接用；元件渲染和 watchEffect 都是 effectVue 的 scheduler 把更新排進佇列、批次執行（第 6 課）
Set 組成的依賴表版本號＋雙向鏈結串列Vue 3.5 為了省記憶體改寫，行為相同（Vue 3.5 發布公告）

你寫出來的版本和 Vue 用的資料結構不同，但觀念是同一套：讀取時記下誰依賴我、寫入時通知依賴我的人、computed 夾在中間做快取。之後遇到「畫面沒更新」或「怎麼多跑了一次」，都可以回到這三件事來查。

練習

每題最上面的迷你核心不用改：第 2 課的 effect、track、trigger（含依賴清理、還原外層 effect、跳過自己、scheduler），reactive 加上第 1 課的巢狀物件包裝與 WeakMap 快取，以及這課加的 trackDep、triggerDep 和 lazy 選項。

練習 1：完成 ref(initial)。要求：

  • 讀 .value 時用 trackDep 記下目前的 effect，寫入時用 triggerDep 通知；每個 ref 有自己的 dep。
  • 寫入的值跟原本相同（用 Object.is 判斷，NaN 也算相同）時不觸發。
  • initial 或之後寫入的值是物件時，.value 回傳 reactive 包過的版本，所以 cup.value.qty++ 也會觸發讀過 cup.value.qty 的 effect。

練習 2：完成 computed(getter)，先不管有沒有 effect 讀它。要求：

  • 建立時不執行 getter，第一次讀 .value 才算。
  • 依賴沒變時再讀，用快取，不重算。
  • 依賴改變時不要馬上重算，等下一次讀 .value 才重算；中間改了好幾次，也只重算一次。

提示：用核心的 effect(fn, { lazy: true, scheduler }) 執行 getter，再加一個 dirty 旗標。

練習 3：讓 effect 可以依賴 computed。起始程式是練習 2 的答案，現在 effect 讀 total、total 讀 subtotal、subtotal 讀 qty，改 qty 時 effect 不會重跑。修改 computed，讓它：

  • 被讀時記下讀它的 effect。
  • 依賴改變時通知下游，下游重跑時讀到的是新值（多層 computed 也一樣）。
  • 沒有人讀時，仍然不執行 getter。

練習 4：加上「值沒變就不通知」。起始程式是練習 3 的答案。改 computed 的 scheduler：

  • 有人依賴這個 computed 時（dep.size > 0），立刻重算，新舊值用 Object.is 比較，不一樣才通知下游。
  • 沒有人依賴時，跟原本一樣只標記 dirty，保持 lazy。

完成後，count 從 2 改成 4 時，讀 isEven 的 effect 不重跑；從 4 改成 5 時要重跑。

練習 5：在 computed 的 getter 裡呼叫 API 取得最新價格，或順便更新另一個 ref，會有什麼問題？

✓ 從練習 2 到 4 可以看到，getter 可能 0 次（沒人讀）、可能延後到讀取時、也可能在依賴改變後、下游要確認值有沒有變時執行（迷你版是有下游就立刻重算）。把副作用放進去，就變成「不知道什麼時候會發請求」。a 錯在 computed 的前提是 getter 是純函式；b 錯在有快取，依賴沒變時根本不會重新執行。資料改變時要做事，用 watch（第 5 課）。

練習 6：const report = computed(() => 很貴的統計(orders.value))，之後整個程式都沒有讀過 report.value。getter 會執行幾次？

✓ computed 是 lazy 的：建立時不算，依賴改變時也只把 dirty 設成 true，有人讀才算。所以宣告了沒用到的 computed 幾乎沒有成本。b 是練習 2 擋掉的「建立時就算」；c 是把 computed 誤當成 watch。

練習 7：結帳頁有三樣資料：購物車總額、使用者輸入的備註、API 回來的訂單紀錄。哪一個該用 computed？

✓ 總額可以從購物車算出來，是衍生資料，用 computed 就不會跟購物車不同步。備註是使用者打的字、訂單紀錄是伺服器給的，都算不出來，只能存成狀態。a 錯在 computed 一定要有來源可以算；c 多存一份總額再手動同步，watch 執行前會讀到舊值，也多了一個會忘記改的地方。

常見錯誤

  • ref 用 !== 判斷有沒有變：NaN 每次寫入都會觸發。用 Object.is，Vue 內部也是如此。
  • ref 收到物件時沒有包成 reactive：cup.value.qty++ 只讀了 .value，ref 的 setter 沒被呼叫，畫面不會更新。整個換掉的新物件也要包。
  • computed 的 getter 裡有副作用：發請求、改其他狀態、寫 localStorage 的時機都不可預期。副作用放在 watch。
  • 把衍生資料另外存一份，再用 watch 同步：多一個要維護的狀態，watch 執行前還會讀到舊值。能算出來的就用 computed。
  • 修改 computed 回傳的物件或陣列：那是快照，下次重算就被換掉。要改就改來源狀態。
  • 以為依賴一改 computed 就立刻重算：在 Vue 裡，computed 要等有人讀（或下游要確認值有沒有變）才算。在 getter 裡打 log 除錯時，看到「沒執行」通常是因為沒有人讀它。
  • computed 每次回傳新物件：Object.is 永遠不相等，「值沒變就不通知」失效，下游每次都重跑。回傳原始值，或用 getter 的 previous 參數在內容相同時回傳舊物件。

補充與查表

主線用不到、但遇到時要知道的細節。

  • Vue 2 也是用 getter／setter：Vue 2 的物件響應式用 Object.defineProperty 替每個屬性定義 getter／setter，跟這課的 ref 是同一個手法。它只能替建立時已經存在的屬性裝上，所以新增屬性、陣列索引寫入攔不到，Vue 3 改用 Proxy（第 1 課）。
  • 回傳物件時保持「值沒變」（Vue 3.4 起）：computed 的 getter 第一個參數是上一次的值，內容相同時回傳它，Object.is 就會判斷為沒變（官方效能指南，第 23 課再談）： 
    const status = computed((previous) => {
  const next = { even: qty.value % 2 === 0 }
  return previous && previous.even === next.even ? previous : next
})
  • 可寫入的 computed（writable computed）：同時提供 get 與 set，適合「畫面上的格式」和「存的格式」不同的雙向轉換，例如輸入框是字串、狀態存數字： 
    const qty = ref(1)
const qtyText = computed({
  get: () => String(qty.value),
  set: (text) => { qty.value = Math.max(0, Number(text) || 0) },
})
    set 裡改的是來源狀態，不是 computed 自己。大部分 computed 都不需要 set，需要時通常是在做表單（第 10 課的 v-model 會用到）。

小結

  • JavaScript 只能攔截物件屬性的讀寫，所以杯數這種單一的值要放進 ref 的 .value，用 getter／setter 在讀時 track、寫時 trigger。每個 ref 有自己的 dep，同值用 Object.is 判斷（NaN 才不會每次都觸發），物件值包成 reactive。
  • 小計這類衍生狀態用 computed ＝ lazy 的 effect ＋ dirty 旗標：建立時不算，依賴改變時只標記過期，有人讀才重算；連改好幾次也只算一次。
  • 畫面要跟著小計、總額更新，computed 必須同時是依賴者和被依賴者：被讀時記下讀它的人，過期時先設 dirty 再通知下游。通知往下推，計算往上拉，沒人讀的不算。
  • Vue 3.4 起，computed 的值沒變時不通知下游，所以杯數 2 變 4 時徽章不重畫；迷你版用「有下游就重算並比較舊值」做出同樣的效果。
  • getter 的執行時機由讀取決定，所以要寫成純函式；副作用用 watch，使用者輸入與伺服器資料用 ref 存；不要改 computed 回傳的快照；回傳新物件會讓「值沒變」失效。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：面試官問：「cart.qty 改了，Vue 怎麼知道要重新執行哪些地方？」最接近原理的回答是？

✓ 響應式就是讀取時記錄、寫入時通知：track 把 activeEffect 記進依賴表，trigger 查出讀過這個屬性的 effect。依賴是「這次執行真的讀到的東西」，不是程式碼裡寫了什麼。b 是髒值檢查（dirty checking）的做法，Vue 不用事後掃過所有資料，寫入的那一刻就知道誰受影響。（第 1、2 課）

練習 9：同事問：「ref(0) 背後到底是什麼，為什麼一定要寫 .value？」哪個說法對？

✓ JavaScript 只能攔截物件屬性的讀寫，所以單一的值要放進物件的 value 屬性，用 getter／setter 插手；每個 ref 有自己的 dep。b 錯在 Proxy 根本包不了數字，new Proxy(80, {}) 直接丟 TypeError。範本裡不用寫 .value 是 Vue 自動解包，不是編譯器改寫。（第 1、3 課）

練習 10：訂單頁這樣寫，呼叫 markPaid() 之後畫面還是「未付款」，為什麼？

const raw = await fetchOrder()
const order = reactive(raw)      // 範本顯示 order.status

function markPaid() {
  raw.status = 'paid'
}

✓ proxy 是另一個物件，只攔截對自己做的操作；改原物件繞過了 trap，沒人被通知。proxy 讀的仍是同一個 target，所以值是新的，只是畫面不知道要更新。修法是拿到 reactive 之後所有讀寫都只經過 proxy：order.status = 'paid'。a 錯在 reactive 沒有複製，proxy 和原物件共用同一份資料。（第 1 課）

練習 11：Vue 2 專案升級到 Vue 3，this.$set(this.items, 1, '可頌') 可以直接改成 items[1] = '可頌'。面試官問 Vue 2 為什麼需要 $set？

✓ Vue 2 建立時逐一改造已存在的屬性，新增、刪除屬性和陣列索引寫入都攔不到；Vue 3 的 Proxy 攔截「對這個物件的操作」，全都偵測得到。a 錯在 Vue 2 的陣列有響應，push、splice 能用是因為 Vue 2 另外改寫了陣列的方法。（第 1 課）

練習 12：訂單列表這樣抓資料，第一次載入正常，切換分店時卻不會重抓，為什麼？

watchEffect(async () => {
  await checkLogin()
  orders.value = await fetchOrders(filter.storeId)
})

✓ 追蹤靠「讀取當下 activeEffect 是誰」，只發生在同步執行期間；第一個 await 之後的讀取，get trap 有被呼叫，但沒有 effect 可記。修法是在 await 之前先讀出 storeId，或改用明確列出來源的 watch。b 錯在 .then() 的 callback 一樣是之後才執行，結果相同。（第 2 課）

練習 13：shop.open 一開始是 true，之後改成 false，接著再改 shop.special。這個 effect 會因為 special 改變而重跑嗎？

effect(() => {
  if (!shop.open) { banner = '休息中'; return }
  banner = `今日特價：${shop.special}`
})

✓ 依賴每次重新收集：重跑前用 effect.deps 把自己從所有 Set 移除，執行時讀到什麼才記什麼。open 再變回 true 時 effect 重跑，又會讀到 special、重新記上。a 是沒有清理的第一版：不再讀的屬性改了還是白跑，在元件裡就是多一次沒必要的渲染。（第 2 課）

練習 14：除錯時在 computed 的 getter 裡加了 console.log，qty 確定是 ref，但改了 qty 之後什麼都沒印。範本也已經不再用到這個 computed，原因是？

✓ computed 是 lazy 的 effect 加 dirty 旗標：建立時不算，依賴改變時只標記過期，有人讀而且過期才重算，所以沒人讀的 computed 幾乎沒有成本。c 是把 computed 當成 watch：它不會自己在背景重算，等多久都不會印。a 錯在 dirty 一被標記，下次讀取就會自動重算。（第 3 課）

練習 15：後台訂單列表要依時間排序，同事這樣寫。哪裡會出事？

const sorted = computed(() => orders.value.sort(byTime))

✓ getter 要是純函式：什麼時候執行、執行幾次由誰在什麼時候讀決定，裡面改狀態就是時機不可預期的副作用。改寫成 [...orders.value].sort(byTime) 或 orders.value.toSorted(byTime)。b 錯在 sort 是就地排序，回傳的就是原本那個陣列。（第 3 課）
