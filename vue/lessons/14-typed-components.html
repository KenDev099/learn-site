階段 4：重用與型別 · 第 14 課

元件的型別：泛型元件與 vue-tsc

咖啡店的菜單頁上線後，客服說每張卡片都顯示「拿鐵 $」，價格不見了。原因是商品卡片的範本裡把 product.price 打成 product.prise。專案明明用 TypeScript，Vitest 的測試也全部通過，部署流程沒有任何一步報錯。TypeScript 不就是為了抓這種錯而存在的嗎？問題不在 TypeScript，而在於整條流程裡沒有任何工具真的在檢查型別。

這課的任務：讓咖啡店的元件被用錯時，錯誤在合併前就被擋下。不只是這一個打錯字，商品卡片 ProductCard 被傳錯資料、團隊共用的選單 PickList 被綁錯值、搜尋框的 composable 呼叫不存在的方法，都要在編譯時失敗。做法分兩半：先讓流程裡真的有一步在檢查型別（vue-tsc），再把每個元件對外的介面寫成型別，讓那一步有東西可以比對。

這課的路線：
  1. 「拿鐵 $」為什麼能通過測試和部署：Vite、Vitest 只擦掉型別、不檢查，要在合併前的自動檢查流程（CI）加上 vue-tsc 才擋得住（開場問題的最小答案）。
  2. vue-tsc 跑了，為什麼購物車傳錯商品還是沒報錯：元件的 props、emits、v-model、slots 要用型別宣告，vue-tsc 才有東西比對；再用 @ts-expect-error 證明錯的用法真的會被擋。
  3. 共用的 PickList 該寫什麼型別：泛型元件記住傳進來的是商品還是顧客，讓型別一路流到 v-model 和 slot。
  4. 邏輯搬進 composable 後，型別為什麼變成 unknown：template ref 與 inject 要怎麼補上型別。
  5. vue-tsc 有沒有看到每一個檔案：tsconfig 該開哪些選項，檢查的代價怎麼安排。
這課會用到：
  • 第 9 課的 defineProps、defineEmits 與 第 10 課的 defineModel：元件對外的三種介面，父元件傳資料進來、子元件發事件出去、雙向綁定一個值。
  • 第 11 課的作用域 slot：子元件透過 <slot :item="item"> 把資料交給父元件，由父元件決定怎麼顯示。
  • TS 課第 19 課的泛型：用型別參數 T 讓函式記住傳進來的型別，T extends … 限制 T 至少要有哪些屬性。

「拿鐵 $」是怎麼通過測試和部署的？

先把出事的卡片縮成最小的樣子。這個 Demo.vue 的 script 和範本各有一個錯誤：範本把 price 打成 prise，按鈕 emit 時把商品 id 轉成了字串，但事件宣告說 id 是 number。

<script setup lang="ts">
import type { Product } from '../../helpers/fake-api.ts'
const { product } = defineProps<{ product: Product }>()
const emit = defineEmits<{ add: [id: number, qty: number] }>()
</script>

<template>
  <h3>{{ product.name }} ${{ product.prise }}</h3>                 ← 第 8 行：打錯字
  <button @click="emit('add', String(product.id), 1)">加入</button>  ← 第 9 行：id 要是 number
</template>

它的測試只確認畫面有顯示品名、按下按鈕會 emit。在這門課的練習資料夾實際執行（Vitest 5.0.5），兩個錯誤都在，測試照樣通過：

$ npx vitest run demo.test.ts
 Test Files  1 passed (1)
      Tests  1 passed (1)

Vitest 明明讀得懂 lang="ts"，為什麼沒發現？因為「處理 TypeScript」其實有兩件不同的事，TS 課第 13 課講過它們的差別：

  • 擦掉型別：把 : Product、<{ product: Product }> 這類標註刪掉，剩下的就是瀏覽器和 Node 能跑的 JavaScript。這件事一次只要看一個檔案，不用知道 Product 長什麼樣，所以很快。
  • 檢查型別（type check）：不執行程式，逐一比對每個值的型別和宣告是否一致，例如 product 的型別 Product 到底有沒有 prise 這個屬性。要回答這個問題，就得把 Product 的定義、它 import 的檔案、整個專案的型別關係都讀進來，所以慢。做這件事的是 TypeScript 編譯器 tsc。

Vite 的目標是存檔後畫面立刻更新，所以它只擦型別、不檢查；Vitest 用 Vite 的轉換流程，也一樣。擦掉型別之後，product.prise 就是一段普通的 JavaScript：讀一個不存在的屬性得到 undefined，不會丟錯，於是畫面顯示「拿鐵 $」，測試也沒有理由失敗。專案裡常見的工具分工如下：

工具擦掉型別檢查型別
Vite 開發伺服器、vite build✓✗（Vue 官方文件：Vite 只做轉譯）
Vitest✓✗（用 Vite 的轉換）
Node 直接跑 .ts✓✗
tsc—✓，但看不懂 .vue 檔
vue-tsc—✓，包含 .vue 檔的 script 和範本

表裡唯一會檢查型別的 tsc 只認得 .ts 檔，.vue 檔的 <script> 和 <template> 都不在它的範圍。能檢查 .vue 的是最後一列的 vue-tsc。同一個 Demo.vue 交給 vue-tsc 3.3.14：

$ npx vue-tsc --noEmit
Demo.vue(8,38): error TS2551: Property 'prise' does not exist on type 'Product'. Did you mean 'price'?
Demo.vue(9,31): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
$ echo $?
2

兩個錯誤都抓到了，連範本裡的也是。vue-tsc 是 Vue 官方的命令列型別檢查工具，它的做法是：把每個 .vue 檔（包含範本）轉成一份 TypeScript 的「虛擬程式碼」，交給 TypeScript 檢查，再把錯誤位置對應回 .vue 檔。所以 Demo.vue(8,38) 指的就是 .vue 檔的第 8 行第 38 個字元，不是虛擬程式碼的位置，你在編輯器裡直接跳到那一行就對了。

vue-tsc 屬於 Vue 官方的語言工具專案 Volar（GitHub 上的 vuejs/language-tools）。編輯器裡的 Vue - Official 擴充套件用的是同一套程式，所以編輯器在範本畫紅線的地方，vue-tsc 也會報錯；兩者看到的錯誤是一致的。

最後一步是讓這個檢查擋住合併。指令裡的 --noEmit 表示只檢查、不輸出任何檔案（輸出 JavaScript 是 Vite 的工作）。有錯誤時，vue-tsc 的結束碼不是 0，上面的 echo $? 印出 2；在 shell 和自動化流程裡，非 0 的結束碼就代表「這一步失敗」。

團隊通常有一條持續整合流程，英文是 continuous integration，簡稱 CI：每次推送程式碼或開 PR，伺服器就自動安裝套件、跑測試、打包，任何一步的結束碼非 0，整條流程就標成失敗。開場那次的 CI 只有 vitest run 和 vite build，兩步都只擦型別，所以一路綠燈。在旁邊加一步 vue-tsc --noEmit，prise 就會讓它變紅。npm create vue 建立的專案已經在 package.json 寫好 "type-check" 這個 script，用的是 vue-tsc --build，和 --noEmit 的差別見課末。

還有一件事要先知道：vue-tsc 和 TypeScript 的版本要一起管。這門課的練習資料夾鎖 typescript 6.0.3 搭配 vue-tsc 3.3.14。npm 上已經有 TypeScript 7，但 vue-tsc 3.3.14 不能搭配它，裝錯版本 type-check 這一步會直接無法執行。原因和升級時要注意什麼，整理在課末「補充與查表」。

💡 實務上：type-check 是 PR 合併前的必過關卡
團隊通常把 npm run type-check 放進 CI，並在 GitHub 的分支保護設成「必須通過才能合併」，開場那種 prise 就不會進到 main。開發時不想等 CI，可以靠編輯器的擴充套件即時檢查，或用 Vue 官方文件提到的 vite-plugin-checker 在另一個執行緒跑 vue-tsc。不要把型別檢查塞進 Vite 的轉換流程本身：那會讓每次存檔都變慢，這正是 Vite 選擇只擦不查的原因。接手新專案時，資深工程師會先打開 package.json 和 CI 設定，確認真的有這一步；很多專案寫著 TypeScript，其實從來沒人跑過檢查。

到這裡，開場的事故有了最小的答案：CI 加上 vue-tsc。但 vue-tsc 只能拿元件宣告的型別來比對。Demo.vue 抓得到 prise，是因為它寫了 defineProps<{ product: Product }>()；如果元件沒有把介面寫成型別，vue-tsc 有跑也沒東西可查。

CI 跑了 vue-tsc，為什麼購物車傳錯商品還是沒報錯？

上一節的結論是 vue-tsc 只能比對宣告過的型別。咖啡店真正的 ProductCard 是早期寫的，用的是 第 9 課提過的執行時宣告：

const props = defineProps({ product: Object, soldOut: Boolean })   // product：任意物件，裡面的屬性都是 any
const emit = defineEmits(['add'])                                   // add 帶什麼參數都可以

它在執行時運作正常；開發模式下，Vue 發現 product 不是物件、soldOut 不是布林值時，會在 console 印警告（不會擋下，正式版也不檢查）。問題出在給型別系統的資訊太少。購物車頁把 :product="cartItem" 傳進來，CartItem 只有 unitPrice、沒有 price，CI 的 vue-tsc 卻沒報錯。原因有兩層：

  • Object 在型別上只表示「某個物件」，裡面的 price、name 都是 any。any 的意思是「這個值不檢查」，所以傳什麼物件都可以，範本讀 product.price 也不會被質疑。
  • ['add'] 只有事件名稱，沒有參數型別。父元件的 @add 處理函式把 id 當字串用，也沒有東西可以比對。

而且 any 會傳染：從 any 讀出來的東西還是 any，再傳給別的函式、別的元件，一路都不檢查。型別檢查在這裡就斷了，vue-tsc 有跑也擋不住，畫面上的價格就是空的。所以 TypeScript 專案一律改用型別宣告：把每個介面的形狀寫成型別參數，交給 vue-tsc 去比對。

元件對外的介面，就是父元件能碰到的所有東西，共有四種：父元件傳進來的 props、子元件發出去的 emits、雙向綁定的 v-model、父元件填內容的 slots。四種都可以用型別宣告：

介面型別寫法父元件寫錯時
props（第 9 課）defineProps<{ product: Product; soldOut?: boolean }>()漏傳必填、型別不符都報錯
emits（第 9 課）defineEmits<{ add: [id: number, qty: number] }>()@add 的處理函式參數型別不符就報錯
v-model（第 10 課）defineModel<Size>()，具名的寫 defineModel<number>('qty')v-model 綁的 ref 型別不符就報錯
slots（第 11 課）defineSlots<{ option(props: { item: Product }): any }>()slot 裡讀不存在的屬性就報錯

逐列看 ProductCard 改完會擋下什麼：

  • props：product: Product 是必填，漏傳會報錯；傳 CartItem 會報錯，因為它沒有 price。soldOut?: boolean 的 ? 表示可以不傳，但傳了就要是布林值，傳字串 "true" 會報錯。
  • emits：add: [id: number, qty: number] 是一個具名 tuple，意思是 add 事件依序帶兩個參數，第一個叫 id、型別 number。父元件的 @add 處理函式如果把 id 宣告成 string，或子元件自己 emit 時傳錯（像開場的 String(product.id)），都會報錯。名稱 id、qty 只是讓錯誤訊息和編輯器提示好讀，不影響比對。
  • v-model：defineModel<Size>() 宣告了綁定值的型別，父元件 v-model 綁一個型別不符的 ref 就報錯。
  • slots：見下一段。

slots 用的 defineSlots 是 Vue 3.3 起的編譯器巨集，只接受型別參數：每個 key 是 slot 名稱，值是一個函式型別，第一個參數就是這個 slot 給出去的 slot props，回傳型別目前沒有作用，寫 any。沒寫 defineSlots 時，vue-tsc 會從範本裡的 <slot :item="item"> 推論 slot props 的型別；寫了之後，slot 的型別變成明確的公開介面：讀 <script> 就知道有哪些 slot、各給什麼，範本裡 <slot> 傳錯東西也會在元件自己這裡報錯。

ProductCard 改成型別宣告之後，購物車頁的 :product="cartItem" 就會在 CI 報錯。這是練習 1 要做的事。

怎麼證明錯的用法真的會被擋？

改完還有一個疑問：「沒有報錯」有兩種可能，一種是用法真的正確，另一種是型別寫得太寬（例如某處還留著 any），什麼都放行。兩種情況 vue-tsc 都安靜，從外面看不出差別。一般的單元測試也幫不上忙，因為型別在執行時已經被擦掉了。

辦法是寫一段故意錯的用法，並要求它一定要報錯。TypeScript 的 // @ts-expect-error 註解就是這個意思：「下一行應該要有型別錯誤」。下一行真的有錯，錯誤被這個註解吸收，檢查通過；下一行沒有錯，TypeScript 反而報 TS2578：Unused '@ts-expect-error' directive，表示「該擋的沒擋到」。這種專門確認型別行為的程式叫型別測試。這課的練習就是這樣判分，在 .ts 檔裡用 h() 建立元件。h(元件, props) 是 Vue 在程式碼裡建立元件節點的函式，第二個參數的型別就是元件的 props（事件寫成 onAdd），所以在 .ts 檔裡也能用 // @ts-expect-error 檢查 props 與 emits：

h(ProductCard, { product: latte })                                         // ✓
// @ts-expect-error 價格是字串
h(ProductCard, { product: { ...latte, price: '110' } })
// @ts-expect-error add 的參數是 number
h(ProductCard, { product: latte, onAdd: (id: string) => console.log(id) })

第一行是正確用法，必須通過；後兩行是錯誤用法，必須報錯。如果 ProductCard 的 price 被寫成 any，第二行就不會報錯，TS2578 會立刻指出來。

範本裡不能寫 // 註解，對應的寫法是 @vue-expect-error：<!-- @vue-expect-error --> 表示緊接在它後面的那個運算式應該有型別錯誤。它只管「正後方」的東西，位置要對。假設 ProductCard 照上表 slots 那一列，宣告了 option(props: { item: Product }) 這個 slot，父元件在範本裡讀 item.nope 應該要報錯：

<!-- @vue-expect-error  ✗ 放在 <template #option> 前面，管不到裡面的 {{ }} -->
<template #option="{ item }">
  <!-- @vue-expect-error  ✓ 放在要報錯的運算式正前方 -->
  {{ item.nope }}
</template>

這兩個註解是寫型別測試用的，不是用來讓錯誤消失。產品程式碼裡看到 @ts-expect-error，要問的是「為什麼這裡型別對不上」。

💡 實務上：code review 時盯住型別的「破口」
型別寫法的價值在於元件被別人使用的時候：咖啡店的 ProductCard 可能有菜單頁、購物車、後台三個地方在用，有人改了 props，vue-tsc 會一次列出所有要跟著改的地方。審 PR 時，資深工程師會特別看新增的 any、as、@ts-ignore，每一個都是型別檢查斷掉的地方，要問「能不能把型別宣告寫對」。接手的舊專案如果還是執行時宣告或滿是 any，不要一次全改：先從最多人用的共用元件改成型別寫法，改一個、跑一次 vue-tsc、修完再下一個。

ProductCard 只處理商品，型別很好寫：product: Product。但團隊還有一個共用的選單元件，同時要放商品、顧客、門市，它的 props 該寫什麼型別？

共用的 PickList 該寫什麼型別？泛型元件

菜單頁要選商品、結帳頁要選顧客、外帶頁要選門市。三種清單長得一樣，你寫了一個共用的 PickList。為了什麼都能放，第一版只要求每個選項有 id：

defineProps<{ items: { id: number }[] }>()   // 為了什麼都能放，只要求有 id

傳商品陣列進去可以通過，因為商品確實有 id。但型別資訊在這裡被丟掉了：PickList 只知道選項是 { id: number }，slot 拿到的 item 也就只剩 { id: number }，在 slot 裡寫 item.name 會報錯。改成 any[] 錯誤就消失了，但那等於回到上一節的破口，打錯字也不會被發現。

兩種寫法都不對，缺的是一種「元件不在乎選項是什麼，但要記得是什麼」的寫法。這正是 TS 課第 19 課的泛型：函式 first<T>(list: T[]): T 不在乎陣列裝什麼，但傳商品陣列進去，回傳的就是商品。元件也可以這樣宣告。

泛型元件（generic component）是用型別參數宣告的元件。Vue 3.3 起在 <script setup> 加上 generic 屬性，內容就像 TypeScript 角括號裡的參數列：

<!-- PickList.vue -->
<script setup lang="ts" generic="T extends { id: number }">
defineProps<{ items: T[] }>()

const selected = defineModel<T | null>({ default: null })

defineSlots<{
  option(props: { item: T; selected: boolean }): any
}>()
</script>

<template>
  <ul>
    <li v-for="item in items" :key="item.id">
      <button type="button" @click="selected = item">
        <slot name="option" :item="item" :selected="selected?.id === item.id">{{ item.id }}</slot>
      </button>
    </li>
  </ul>
</template>

逐段看：

  • T extends { id: number } 是限制（constraint）：T 可以是任何型別，只要有 id: number。有了這個保證，元件內部才能寫 :key="item.id"；沒有限制的話，TypeScript 不知道 T 有沒有 id，會報錯。
  • props、v-model、slot 三個地方都用同一個 T：items: T[]、defineModel<T | null>、slot props 的 item: T。這就是型別「被記住」的方式。
  • selected 用 id 比對，不比對物件參考：父元件重新載入清單後，選中的那筆可能是內容相同的新物件，用 === 比物件會判成沒選中。

使用的人不用手動指定 T。就像呼叫 first(menu) 時 TypeScript 從參數推論出 T，泛型元件的「參數」就是 props，TypeScript 從傳進來的 items 推論 T：

菜單頁的用法如下。menu 是 Product[]，所以 T 是 Product：slot 裡讀得到 item.name、item.price，v-model 必須綁 Product | null；第二個 PickList 綁了字串，vue-tsc 就報錯。

<script setup lang="ts">
const menu = ref<Product[]>([])
const picked = ref<Product | null>(null)
const wrong = ref('')
</script>

<template>
  <PickList v-model="picked" :items="menu">
    <template #option="{ item, selected }">
      {{ item.name }} ${{ item.price }} {{ selected ? '✓' : '' }}   ← ✓ item 是 Product
    </template>
  </PickList>

  <PickList v-model="wrong" :items="menu" />   ← ✗ string 不是 Product | null
</template>

結帳頁把顧客陣列傳給同一個 PickList，T 就是 Customer，slot 裡的 item.name 是顧客名稱。一個元件、多種型別，每個用的地方都有完整的檢查。

泛型也有代價：錯誤訊息會變長、變難讀，元件的宣告也比較難懂。所以只有在「同一個元件真的會被不同型別使用」時才值得。元件只處理一種資料時，例如 ProductCard 就是商品，直接寫具體型別。generic 的其他寫法（多個型別參數、import 型別當限制）放在課末。

💡 實務上：泛型元件多半出現在團隊的共用元件
後台系統最常見的是表格、下拉選單、多選清單這類「資料長什麼樣都要能放」的元件：咖啡店後台的訂單表、商品表、顧客表可以共用同一個 DataTable，欄位的 slot 拿到的列資料就是各自的型別。做之前先確認手上已經有兩三個真實用法，不要為了「以後可能會用到」先寫成泛型。寫好後至少用兩種型別各試一次，並放一行 @ts-expect-error 確認錯的用法真的會報錯，否則 T 可能早就默默變成 any，泛型形同虛設。

元件本身的型別都寫好了。但有些和元件相關的邏輯會搬出 .vue 檔，放進 composable，這時型別會出另一種問題。

邏輯搬進 composable 後，型別為什麼變成 unknown？

菜單頁 SearchPage 有一個「找飲料」按鈕，按了讓游標跳進搜尋框 SearchBox；價格標籤還要知道目前是哪一家門市。這兩段邏輯被搬進了 composable：一個拿搜尋框的 template ref，一個 inject 目前門市。在 .vue 檔裡好好的型別，搬進 .ts 檔之後變成了 unknown，有人就順手寫 any 讓錯誤消失。這一節分兩半看：template ref 和 inject。

template ref：為什麼在 .vue 檔裡會自動推論，搬出去就不會？

第 8 課寫過 useTemplateRef<InstanceType<typeof SearchBox>>('box')，手動給型別參數。在 .vue 檔裡其實可以省略：根據 Vue 官方文件，Vue 3.5 搭配 @vue/language-tools 2.1 以上（編輯器和 vue-tsc 都是），在 .vue 檔裡用固定字串的 ref，型別可以自動推論：

<script setup lang="ts">
const box = useTemplateRef('box')   // vue-tsc 看到範本的 <SearchBox ref="box">，推論出 SearchBox 的實例型別
box.value?.focus()                  // ✓
box.value?.open()                   // ✗ SearchBox 沒有公開 open（vue-tsc 3.3.14 實測會報錯）
</script>

<template><SearchBox ref="box" /></template>

推論的原理是：vue-tsc 把整個 .vue 檔轉成虛擬程式碼時，同時看得到 script 裡的 'box' 和範本裡的 ref="box"，兩邊對得起來，才知道 box 指的是 SearchBox。所以推論只在同一個 .vue 檔、ref 名稱是固定字串時才做得到。下面這些情況就要自己寫型別參數：

  • 在 composable 裡（.ts 檔）：useSearchFocus('box') 裡面的 useTemplateRef(key) 看不到任何範本，不寫型別就是 unknown，box.value?.focus() 會報錯。很多人在這裡寫 <any> 讓它閉嘴，結果打錯方法名稱也不會報錯。
  • 動態元件（<component :is>）或 ref 名稱是變數：範本裡的元件或名稱要到執行時才確定，編譯時對不起來。

composable 的正確寫法：

import { useTemplateRef } from 'vue'
import type SearchBox from './SearchBox.vue'   // 只要型別，執行時不用載入元件

export function useSearchFocus(key: string) {
  const box = useTemplateRef<InstanceType<typeof SearchBox>>(key)
  return { box, focusSearch: () => box.value?.focus() }
}

typeof SearchBox 是元件定義的型別，可以把它想成一個建構子；InstanceType（TS 課第 21 課的工具型別）從建構子型別取出「建出來的實例」的型別。元件實例的型別裡只有 defineExpose 公開的東西和 $el、$props 這類內建屬性，所以 focus() 通過、沒公開的 open() 報錯，和 .vue 檔裡自動推論的結果一樣。

泛型元件不能用 InstanceType，因為它的型別要等 T 決定之後才完整。官方文件指定用 vue-component-type-helpers 套件的 ComponentExposed，它取出元件 defineExpose 的內容。例如要拿上一節 PickList 的 ref：

import type { ComponentExposed } from 'vue-component-type-helpers'
const list = useTemplateRef<ComponentExposed<typeof PickList>>('list')

要用的話，把 vue-component-type-helpers 明確寫進 devDependencies，不要依賴它剛好被別的套件裝進 node_modules。

inject：字串 key 為什麼拿到 unknown？

另一個 composable 用 inject 拿目前門市。第 13 課用 InjectionKey<T> 當 provide／inject 的 key，當時說它帶有型別；現在從型別檢查的角度比較三種寫法：

provide('currentStore', store)
const a = inject('currentStore')                 // unknown：字串 key 不帶任何型別資訊
const b = inject<Ref<Store>>('currentStore')     // Ref<Store> | undefined：只是「你說了算」，provide 塞錯也不會報錯

export const CURRENT_STORE_KEY: InjectionKey<Ref<Store>> = Symbol('currentStore')
provide(CURRENT_STORE_KEY, 123)                  // ✗ 報錯：要 Ref<Store>
const c = inject(CURRENT_STORE_KEY)              // Ref<Store> | undefined，跟 provide 的型別綁在一起

第一種：字串 'currentStore' 只是一個名字，provide 那邊放了什麼，inject 這邊不可能知道，所以是 unknown。

第二種看起來有型別，但 inject<Ref<Store>>(...) 和 as Ref<Store> 是同一類東西：型別斷言，你對編譯器保證「這裡是 Ref<Store>」，它就相信你，不會去對照 provide 的那一邊。哪天 provide 改成塞門市 id 的數字，這裡照樣通過。

第三種，InjectionKey 把型別綁在 key 本身上：provide 和 inject 用同一個 key，就共用同一個型別來源，兩邊有一邊寫錯就報錯。這就是練習 3 要把字串 key 換掉的原因。

到這裡，元件、泛型元件、composable 的型別都寫對了。剩下最後一個前提：vue-tsc 真的讀到了這些檔案，而且用了對的規則。

vue-tsc 有沒有看到每一個檔案？tsconfig 與檢查的代價

前面所有的型別寫法要生效，vue-tsc 和編輯器都要讀到正確的設定。兩者讀同一份 tsconfig.json（TS 課第 25 課），所以編輯器的紅線和 CI 的結果會一致；設定錯了，兩邊會一起放過錯誤。這門課的練習資料夾主要的設定如下（節錄；每個選項都明寫，因為 TypeScript 6 改了好幾個預設值）：

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",        // 依打包工具（Vite）的規則找模組
    "strict": true,                       // 開啟 strictNullChecks 等嚴格檢查；不開的話 null 檢查形同虛設
    "noEmit": true,                       // 只檢查，輸出交給 Vite
    "allowImportingTsExtensions": true,   // 允許 import './ex1.ts' 寫副檔名
    "verbatimModuleSyntax": true,         // 只有型別的 import 必須寫 import type
    "skipLibCheck": true,
    "lib": ["ES2024", "DOM", "DOM.Iterable"],
    "types": ["node"],
    "jsx": "preserve",
    "jsxImportSource": "vue"
  },
  "include": ["work/**/*", "helpers/**/*"]
}

和這課的任務最相關的是三個選項：

  • include 決定檢查哪些檔案。檔案沒被包含、也沒被包含的檔案 import 到，vue-tsc 就不會看它，錯誤也不會出現。CI 綠燈但某個資料夾的錯誤沒被抓到，先查這裡。
  • strict 打開一組嚴格檢查，其中 strictNullChecks 讓 null、undefined 成為獨立的型別。上一節 box.value?.focus() 要寫 ?.、inject 回傳 | undefined，都是它在提醒你「這裡可能還沒有值」；不開的話，這些檢查形同虛設。
  • verbatimModuleSyntax 要求只有型別的 import 寫成 import type。擦型別的工具一次只看一個檔案，不知道 import 進來的東西是不是只有型別；寫成 import type，它就知道可以整行刪掉。上一節 composable 的 import type SearchBox 就是這個原因，執行時也不會因此多載入一個元件。

用 npm create vue 建立的專案，設定會拆成好幾個檔案，搭配 vue-tsc --build，見課末。

最後是代價。vue-tsc 是完整的型別檢查，要讀進整個專案，專案大了要跑幾十秒甚至更久。所以一般的安排是：編輯器即時提示，CI 每個 PR 跑一次，本機不在每次存檔時跑。這也是第一節那張表的分工：Vite 負責快，vue-tsc 負責對。

出現型別錯誤時，先看錯誤指向的 .vue 行號，在編輯器打開同一個位置，滑鼠移上去看 TypeScript 推論出的型別，通常就能看出是哪一邊的宣告太寬或太窄。回到開場的事故，整條防線現在是：元件用型別宣告介面，型別測試確認錯的用法會被擋，vue-tsc 在 CI 裡用正確的 tsconfig 檢查每一個檔案，結束碼非 0 就不能合併。product.prise 不會再走到客服那裡。

主線用不到、但升級版本或接手專案時會用到的細節。

TypeScript 6、7 與 vue-tsc 的版本

你可能會想把 TypeScript 升到最新版。2026-10-31 時 npm 上 typescript 的 latest 是 7.0.2，但這門課的練習資料夾刻意裝 6.0.3。原因是 TypeScript 7 換了實作：

  • TypeScript 7.0 是用 Go 重寫的原生編譯器，速度快很多。它的 npm 套件只匯出 ./lib/version.cjs、./package.json 和 ./unstable/*，沒有以前那套給其他工具呼叫的 JavaScript 編譯器 API。
  • vue-tsc 3.3.14 啟動時要找 typescript/lib/tsc，也就是那套 JavaScript 編譯器。裝了 TypeScript 7.0，它就找不到可以用的編譯器，無法執行。
  • 官方範本也這樣做：create-vue 3.24.0 的 TypeScript 範本鎖 typescript ~6.0.0、vue-tsc ^3.3.11。6.x 這條線最後一版是 6.0.3。
  • TypeScript 7.1 beta（2026-10-20 發表）加入 content mappers：讓 tsc 透過外掛把 .vue 這類檔案轉換後再檢查。Vue 的 mapper 已經有原型，但還沒發布到 npm。將來也許能直接用 tsc 檢查 .vue，現在還不行。

資深的做法：typescript 和 vue-tsc 都鎖版本，兩個一起升級，升級前先看 vue-tsc 的 release notes 支援哪個 TypeScript。鎖版本靠的是 lockfile，也就是 package-lock.json，它記下每個套件實際裝的版本，一定要進 git。依賴更新工具（Renovate、Dependabot）送來「typescript 6 → 7」的 PR，CI 的 type-check 步驟會直接壞掉，這不是你的程式有錯，而是工具鏈還沒跟上。

vue-tsc --noEmit 與 --build、create-vue 的設定拆分

npm create vue 產生的專案（create-vue 3.24.0）把型別檢查寫成 "type-check": "vue-tsc --build"。它的 tsconfig 拆成 tsconfig.app.json（瀏覽器程式）和 tsconfig.node.json（vite.config.ts 這類 Node 端的檔案），用 references 串起來，兩者繼承 @vue/tsconfig 的共用設定。--build 會依 references 分別檢查瀏覽器端和 Node 端的設定，並把結果存成 .tsbuildinfo，下次只重新檢查有變動的部分。只有一份 tsconfig 時用 --noEmit 就好。哪一種都可以，重點是 CI 要有這一步，而且排在測試旁邊，不要等到部署後才發現。

generic 的其他寫法

generic 可以有多個參數，也可以 import 型別來當限制：generic="T extends Product, K extends keyof T"。

練習

在 learn/ 執行 node check.mjs vue 14，要改的檔案在 vue/practice/work/14/，每個檔案最上面的註解寫了要求。這課的測試除了執行元件，還會在旁邊寫一個隱藏的使用檔，用 vue-tsc（TypeScript 6.0.3）檢查：正確的用法要通過，故意寫錯的用法要報錯。所以每個型別測試要跑一兩秒。測試失敗時印出的訊息就是 vue-tsc 的輸出，看到 TS2578 表示「該報錯的地方沒報錯」，型別寫得太寬了。

練習 1：ProductCard.vue 用執行時的寫法 defineProps({ product: Object, soldOut: Boolean })、defineEmits(['add'])，畫面和行為都正常，但沒有型別。改成型別宣告：product: Product、soldOut?: boolean（預設 false），add: [id: number, qty: number]。完成後，父元件把價格傳成字串、soldOut 傳字串、@add 的處理函式參數（id 或 qty）寫成 string、漏傳 product，vue-tsc 都要報錯。不能用 any、Record 或型別斷言。

練習 2：把 PickList.vue 寫成泛型元件 T extends { id: number }：props items: T[]；用 defineModel 宣告 T | null 的 v-model（預設 null）；用 defineSlots 宣告作用域 slot option，slot props 是 { item: T; selected: boolean }，沒傳 slot 時顯示 item.id。每個選項是一個按鈕，點了就把 model 設成它；selected 用 id 比對。隱藏的 Usage.vue 會傳商品陣列，slot 裡讀 item.name、item.price 要通過，讀不存在的屬性、v-model 綁字串要報錯；只有 id 的選項陣列（[{ id: 7 }]）也要能用。

練習 3：SearchPage.vue（不用改）透過兩個 composable 拿到搜尋框和目前門市。use-search-focus.ts 用 useTemplateRef<any>，打錯方法名稱也不會報錯；current-store.ts 用字串當 key，useCurrentStore() 回傳的型別不是 Ref<Store>。改成：template ref 是 SearchBox 的實例型別（focus()、$el 通過，open() 報錯；只 import type SearchBox），key 是 InjectionKey<Ref<Store>>（provide(KEY, 123) 報錯）。不能用 any 或 as，按「找飲料」仍然要讓游標跳進搜尋框。

練習 4：專案用 TypeScript 寫 .vue 檔，CI 只跑 vitest run 和 vite build，兩個都成功。這代表什麼？

✓ Vite 和 Vitest 只擦掉型別、把剩下的 JavaScript 拿去跑或打包，不做型別檢查，.ts 檔也一樣（a、c 錯）。開場的 product.prise 在測試通過、打包成功的情況下照樣上線。CI 要另外加 vue-tsc --noEmit（或 create-vue 範本的 vue-tsc --build），它會檢查 .ts 和 .vue 的 script 與範本。

練習 5：2026 年 10 月，npm 上 typescript 的最新版是 7.0.2，這門課的練習資料夾卻裝 6.0.3。為什麼？

✓ TypeScript 7.0 是 Go 寫的原生編譯器，npm 套件不再提供舊的 JavaScript 編譯器 API，而 vue-tsc 需要它（找 typescript/lib/tsc），所以要跟官方範本 create-vue 一樣鎖 6.0.x。不是 TypeScript 7 不懂 Vue 語法（a 錯：TypeScript 本來就不直接讀 .vue，是 vue-tsc 負責轉換），也不是「新就不穩」這種通則（b 錯：選版本看的是工具鏈相容性）。TypeScript 7 當然有泛型（d 錯）。

練習 6：PickList.vue 宣告 generic="T extends { id: number }"、items: T[]。父元件寫 <PickList :items="customers" v-model="who">，customers 是 Customer[]。T 是怎麼決定的？

✓ 泛型元件的 T 跟一般泛型函式一樣，從使用時傳入的參數推論，元件的「參數」就是 props，所以 items: Customer[] 讓 T 成為 Customer，slot 的 item 和 v-model 也跟著是 Customer。範本裡不需要也沒有手動指定 T 的寫法（b 錯），限制只規定 T 至少要有 id。型別在執行時已經被擦掉，Vue 不會在執行時決定型別（c 錯）。

常見錯誤

  • 以為測試或 Vite 會檢查型別：它們只擦掉型別。CI 要有 vue-tsc --noEmit（或 vue-tsc --build），結束碼非 0 就擋下。
  • 把 typescript 升到 7.0 後 vue-tsc 無法執行：vue-tsc 3.3.14 需要 TypeScript 6 的 JavaScript 編譯器 API。typescript 和 vue-tsc 一起鎖版本、一起升級，跟 create-vue 範本一樣用 ~6.0.0。
  • 用執行時的 props 宣告：defineProps({ product: Object }) 的型別是「任意物件」，父元件傳錯不會報錯。TypeScript 專案用 defineProps<{ … }>()，emits 用具名 tuple。
  • 用 any 讓錯誤消失：any 會一路傳染，之後讀出來的東西都不檢查。找出型別對不上的真正原因，宣告正確的型別；真的不知道型別時用 unknown，再縮小範圍。
  • slot 型別寫成 any：defineSlots<{ option(props: any): any }>() 讓 slot 裡的 item 變成 any，打錯屬性也不報錯。slot props 要寫具體型別，泛型元件寫 { item: T }。
  • @vue-expect-error 放錯位置：放在 <template #option> 前面管不到裡面的運算式。放在要報錯的那個運算式正前方。
  • composable 裡的 template ref 寫 any：.vue 檔裡固定字串的 ref 會自動推論，composable 裡不會。寫 useTemplateRef<InstanceType<typeof X>>(key)，泛型元件用 ComponentExposed。
  • inject 用字串 key 加型別參數或斷言：inject<Ref<Store>>('key') 只是你說了算，provide 那邊塞錯不會報錯。用 InjectionKey<T> 讓兩邊共用同一個型別。

小結

  • Vite、Vitest、Node 只擦掉型別，不檢查，所以 product.prise 能通過測試和打包。vue-tsc 把 .vue（含範本）轉成 TypeScript 虛擬程式碼交給 TypeScript 檢查，錯誤行號對應回 .vue 檔；CI 要跑它，結束碼非 0 就不能合併。
  • vue-tsc 只能比對宣告過的型別。props、emits、v-model、slots 都用型別宣告：defineProps<…>、defineEmits<{ add: [id: number] }>、defineModel<T>、defineSlots<…>（3.3+）；執行時宣告的 Object 是 any，擋不住傳錯。
  • 用 @ts-expect-error／@vue-expect-error 寫型別測試，確認錯誤用法真的會報錯；TS2578 表示該擋的沒擋到。
  • 泛型元件 <script setup generic="T extends …">：T 從 props 推論，流到 v-model 和作用域 slot。只有一種資料時不用泛型。
  • .vue 檔裡固定字串的 template ref 會自動推論；composable 裡要寫 InstanceType<typeof X>，泛型元件用 ComponentExposed。inject 用 InjectionKey<T>，不用字串 key 加斷言。
  • tsconfig 的 include 決定 vue-tsc 看哪些檔案；開 strict，用 moduleResolution: "bundler"、verbatimModuleSyntax；編輯器和 vue-tsc 共用同一份設定。
  • vue-tsc 3.3.14 需要 TypeScript 6（6.0.3）；TypeScript 7.0 的 npm 套件沒有它要的 JavaScript 編譯器 API，兩者一起鎖版本、一起升級（課末）。

練習 7：顧客詳細頁呼叫 useCustomerOrders(() => Number(route.params.id))。從顧客 1 點到推薦的顧客 2，網址換了、頁面元件被重用。訂單會怎樣？

export function useCustomerOrders(customerId: MaybeRefOrGetter<number>) {
  const orders = ref<Order[]>([])
  const id = toValue(customerId)
  watch(() => id, async () => {
    orders.value = await api.orders(id)
  }, { immediate: true })
  return { orders }
}

✓ toValue 只是「現在讀一次」，id 之後就是常數，getter 永遠回傳 1，只會執行 immediate 那一次。改成 watch(() => toValue(customerId), load, { immediate: true })，在 getter 裡讀才會追蹤。b 是修好之後才要處理的競態，現在連第二次請求都不會發。（第 12 課）

練習 8：叫號螢幕的背景模組不是元件，用 effectScope().run(() => usePolling(refresh)) 啟動輪詢，關閉功能時呼叫 scope.stop()。usePolling 在 onUnmounted 裡 clearInterval。stop 之後會怎樣？

✓ onUnmounted 只認元件實例，沒有元件時只警告，清理函式沒登記上。改用 onScopeDispose（或 watch 的清理函式），元件卸載和 scope.stop() 時都會執行。b 是把 onScopeDispose 的行為套到 onUnmounted 上；Vue 不丟錯，所以 c 也不對，問題是靜靜地洩漏。（第 12 課）

練習 9：店內點餐頁和外帶頁各自呼叫 useCartBadge()，結果在店內加一杯拿鐵，外帶的徽章也加 1。先查什麼？

✓ ES module 只執行一次，最外層的 ref 被所有呼叫共用；寫在函式裡才是每呼叫一次一份。真的要整個 app 共用就交給 Pinia，模組層級的狀態在 SSR 時還會外洩給別的顧客。b 的症狀是畫面不更新，不是兩份互相影響；composable 只是函式，Vue 不會快取它（c 錯）。（第 12 課）

練習 10：App 用 provide 交出可寫的 ref<Store>，有三個元件直接寫 store.value = … 切換門市。現在要加「只能切到有權限的門市」，怎麼做才能讓下一個新元件也繞不過檢查？

✓ readonly 讓後代讀得到最新值、寫不進去，所有修改都經過提供者的 switchStore，驗證、記錄、同步網址都只改這一處。a 靠紀律，新元件忘了呼叫就繞過去了。c 交出去的是普通物件，切換門市後後代也不會更新。前端檢查只讓畫面合理，後端 API 仍要擋越權。（第 13 課）

練習 11：PriceTag 在頁面上正常顯示價格，但單元測試 mount(PriceTag) 丟出「useCurrentStore() 必須在 provideCurrentStore() 之下使用」。先查什麼？

✓ inject 只往祖先找，單獨 mount 時上面沒有任何提供者，錯誤訊息正是在說這件事。補上提供者再測；外掛提供的依賴則用 global.plugins 或 global.provide。a 讓錯誤消失，卻改成在很遠的地方顯示錯的門市。同一個元件在頁面上正常，代表呼叫位置沒問題（b 錯）。（第 13 課）

練習 12：API client 的外掛這樣寫，瀏覽器裡一切正常。哪裡會出事？

let current: ApiClient

export function createApiPlugin(client: ApiClient) {
  return { install() { current = client } }
}
export function useApi() {
  return current
}

✓ 模組層級的變數整個程式只有一份；伺服器渲染每個請求一個 app、同一個測試檔建好幾個 app 時，大家拿到的都是最後安裝的那個。改成 install(app) { app.provide(API_KEY, client) }，useApi() 用 inject 取出，依賴存在各自的 app 上。c 錯在測試安裝一個帶假 client 的外掛照樣換得掉，出事的是兩個 app 同時存在。（第 13 課）

練習 13：吸取開場的教訓，同事在 CI 加了 tsc --noEmit，結果通過了，範本裡的 product.prise 還是上線。為什麼？

✓ tsc 只處理 .ts，.vue 檔的 script 和範本都不在它的範圍。vue-tsc 把 .vue（含範本）轉成 TypeScript 虛擬程式碼交給 TypeScript 檢查，prise 就會被抓到。c 錯在這正是 vue-tsc 做的事；--noEmit 只是不輸出檔案，型別照樣檢查（d 錯）。（第 14 課）

練習 14：ProductCard 寫 defineProps({ product: Object })，範本用 product.price。購物車頁傳了 :product="cartItem"，CartItem 只有 unitPrice。CI 的 vue-tsc 會怎樣？

✓ 執行時宣告的 Object 在型別上是「任意物件」，屬性都是 any，vue-tsc 有跑也擋不住；改成 defineProps<{ product: Product }>()，傳 CartItem 的地方就會報錯。c 錯在執行時只檢查「是不是物件」，cartItem 是物件，不會有警告，畫面上價格就是空的。（第 14 課）
