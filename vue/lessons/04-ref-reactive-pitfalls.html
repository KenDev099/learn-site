階段 2：Vue 響應式實戰 · 第 4 課

ref、reactive 與失去響應的陷阱

前三課你自己做出了迷你版的 reactive、ref、computed。從這一課開始換成真正的 Vue，第一件事是處理一張客服單：「點餐頁加了兩杯拿鐵，購物車清單裡兩杯都在，右上角的徽章卻還是 0。」程式沒有報錯，語法也沒寫錯，就是資料改了、畫面有一部分沒動。這是 Vue 專案裡最常見的一類 bug，原因幾乎都是同一件事：你手上拿的已經不是 Vue 在追蹤的那個東西。

出問題的是點餐頁的購物車邏輯 useCart()，程式長這樣：

export function useCart() {
  const state = reactive({ items: [] as CartItem[], count: 0 })
  function add(item: CartItem) {
    state.items.push(item)
    state.count++
  }
  const { items, count } = state
  return { items, count, add }
}

這一課沿著這張客服單往下走：先在自己的電腦上用測試重現它，找出斷線的原因並修好，再處理同一個點餐頁上另外三個會踩到的坑：5000 筆品項的菜單看板、結帳時要呼叫的收據印表機、不想被其他元件隨手改掉的狀態。這段程式就是練習 1 的起始程式，這課的本機練習環境也會在第 1 節裝好，之後的 Vue 練習都在這裡寫。

這課的路線：
  1. 要重現這個 bug，先把能跑 Vue 測試的環境裝好：用測試證明 bug 存在：count 不是 ref，add() 兩次之後 count.value 也不是 2。
  2. 為什麼徽章停在 0：解構拿到的只是當下的值；還有哪兩種寫法會用同樣的方式斷線。
  3. 怎麼修：toRefs／toRef、改用 ref、傳 getter，以及「畫面沒更新」時的排查順序。
  4. 一開始就用 ref 會不會比較好：ref 與 reactive 怎麼選，選了 ref 之後 .value 什麼時候可以不寫。
  5. 菜單看板 5000 筆、收據印表機、共用狀態：哪些東西不該深層響應（shallowRef、markRaw），怎麼讓別人只能看不能改（readonly）。
這課會用到：
  • 第 1 課的 Proxy：proxy 是包在原物件外面的另一個物件，只能包物件。
  • 第 2 課的依賴追蹤：透過 proxy 讀屬性時 track 記下誰讀了，寫入時 trigger 通知它們重跑。
  • 第 3 課的 ref 與 computed：ref 把單一的值放進 .value 讓它能被追蹤；computed 從別的狀態算出值並快取，依賴改了才重算。

為什麼徽章停在 0，清單卻有更新？

先用普通 JavaScript 看清楚一件事：解構拿到的是當下的值，之後跟原物件沒有關係（TS 課第 2 課）。執行後看 count 和 card.count 是不是一樣：

count 變成 1，card.count 還是 0。let { count } = card 等於 let count = card.count：讀一次、把數字複製到新的變數，之後兩邊各走各的。

reactive 也一樣。Vue 能追蹤，是因為你透過 proxy 讀屬性：讀的那一刻 get trap 執行 track，記下「誰讀了 state.count」，之後寫入 state.count 時才知道要通知誰（第 2 課）。const { items, count } = state 這一行確實透過 proxy 讀了一次 state.count，但讀完就把數字 0 放進一個區域變數。之後徽章讀的是這個區域變數，區域變數的讀寫攔截不到（第 3 課就是因為這樣才需要 ref），Vue 沒有東西可以追蹤；add() 改的是 state.count，跟徽章手上的 0 也沒有關係。

那為什麼清單有更新？因為 reactive 是深層的：透過 proxy 讀到的屬性值如果是物件或陣列，拿到的也是包好的 proxy。解構出來的 items 是 state.items 那個陣列的 proxy，清單讀 items 的內容時照樣被 track，push 時照樣 trigger。同一行解構，物件值還連著，原始值（數字、字串、布林）就斷了，所以這類 bug 常常是「一半會動、一半不會」，更難一眼看出來。

解構不是唯一會斷線的寫法。下面三種寫法，斷線的原因都一樣：

const state = reactive({ count: 0 })

// 1. 解構：count 只是數字 0
let { count } = state

// 2. 整個替換：畫面追蹤的是第一個 proxy，換掉之後沒人通知它
let cart = reactive({ items: [] })
cart = reactive({ items: [latte] })

// 3. 把屬性值傳給函式：函式收到的是數字，之後 state.count 變了它也不知道
useBadge(state.count)
  • 解構：就是客服單這一種，count 只是複製出來的數字。
  • 整個替換：畫面第一次渲染時，讀的是 cart 這個變數當時指向的第一個 proxy，track 記在那個 proxy 上。cart = reactive(...) 只是讓區域變數改指向另一個新的 proxy，舊 proxy 上沒有任何寫入，沒有 trigger；新 proxy 上又還沒有人讀過，也沒有人可以通知。畫面就停在舊資料。
  • 把屬性值傳給函式：JavaScript 呼叫函式時，state.count 會先被讀成當下的數字再傳進去。useBadge 收到的是 0 這個值，跟解構一樣，之後 state.count 變了它也不知道。

三種寫法的共同點：手上剩下的是一個值，不是通往 proxy 的路。修法也就圍繞一件事：讓拿到東西的那一方，每次要用時都能回頭讀 proxy。

怎麼修，讓呼叫端解構之後還連著？

Vue 提供的工具都在做同一件事：給你一個「讀它時會轉去讀 proxy」的東西，而不是一個值。對應三種斷線寫法：

  • 要解構：用 toRefs(state)，把每個屬性轉成連回原物件的 ref；只要一個屬性就用 toRef(state, 'count')。讀寫這個 ref 的 .value，等於讀寫 state.count，所以讀的時候會被 track，state.count 改了也會通知讀過它的人。
  • 要整個替換：改用 ref，換 .value：大家讀的都是同一個 ref，換掉的只是它裡面的值，寫入 .value 就會 trigger。或保留 reactive，用 Object.assign(state, 新內容) 改屬性：proxy 還是同一個，每個屬性的寫入都經過它。
  • 要傳給函式：傳 ref（toRef(state, 'count')）或 getter（() => state.count）。getter 是一個「呼叫時才去讀 state.count」的函式。watch 是資料變了就執行你給的函式的工具（第 5 課）；函式在 watch 或 computed 裡呼叫這個 getter，每次都會重新讀，也就重新被追蹤。第 5 課的 watch 和第 12 課的 composable 都靠這個寫法。

套用到 useCart 這種回傳狀態的函式上，常見的寫法是回傳前先 toRefs。useCart 本身留給練習 1 自己改，這裡用結構相同的集點卡示範：

import { reactive, toRefs } from 'vue'

function useStampCard() {
  const state = reactive({ points: 0, rewards: 0 })
  const stamp = () => { state.points++ }
  return { ...toRefs(state), stamp }   // 呼叫端解構也不會斷線
}

const { points, stamp } = useStampCard()
stamp()
points.value   // 1

...toRefs(state) 把 points、rewards 都變成連回 state 的 ref，呼叫端解構拿到的是 ref 本身，不是數字；stamp() 改了 state.points，讀 points.value 就是新的值。練習 1 就是把同樣的想法用在 useCart 上，讓客服單上的徽章跟著動。

這也解釋了 composable 的一個慣例。composable 是把有狀態的邏輯包成 useXxx() 函式，讓好幾個元件共用（第 12 課深入），例如上面的 useStampCard。composable 習慣回傳「裝著 ref 的普通物件」，而不是一個 reactive 物件，因為呼叫端最常做的事就是解構。同樣的坑在 Pinia 也會遇到：Pinia 是 Vue 官方的狀態管理套件，store 是放共用狀態的地方。store 是 reactive 物件，解構前要先用 storeToRefs，第 15 課會再遇到。

這次是測試先告訴我們哪裡斷線；在真實的專案裡，常常只有一張客服單。這時候的另一個工具是 Vue DevTools：瀏覽器擴充套件（也可以當 Vite 外掛裝進專案），能看元件樹、每個元件目前的狀態、Pinia store 和效能。畫面沒更新時，先在 DevTools 看資料到底有沒有變，就知道問題在資料還是在畫面。

💡 實務上：「畫面沒更新」的 bug，先找斷線的那一行
客服回報「購物車加了拿鐵，右上角的數字還是 0」，這類 bug 很常是上一節的三種寫法之一。排查順序：先用 Vue DevTools 確認資料有沒有變；狀態有變、畫面沒動，就往上找這個值是不是被解構、被整個替換，或是以數字的形式傳進了 composable。反過來，資料根本沒變，問題就在更新的邏輯，不是響應性。Code review 看到 const { count } = state、useBadge(state.count) 這類寫法，值得停下來多看一眼。

徽章修好了。但回頭看，這個 bug 之所以有機會發生，是因為 useCart 選了 reactive。如果一開始就用 ref 呢？

一開始就用 ref，會不會比較好？

Vue 有兩種宣告響應式狀態的方式，你在第 1～3 課都做過迷你版。把上兩節的發現放在一起比：

ref(value)reactive(obj)
能放什麼任何值，包括數字、字串只能放物件、陣列、Map、Set（Proxy 只能包物件）
怎麼讀寫count.valuestate.count
整個換掉items.value = 新陣列，可以不行，換掉就斷線（第 2 節）
解構、傳給函式傳的是 ref 本身，連線還在拿到的是當下的值，斷線

差別的根源在「誰被追蹤」。ref 被追蹤的是 ref 這個物件自己的 .value，你把 ref 傳到哪裡，連線就跟到哪裡；reactive 被追蹤的是「透過 proxy 讀屬性」這個動作，一旦把屬性值拿出來，連線就留在 proxy 上。如果 useCart 一開始寫成 const count = ref(0)，回傳的就是 ref 本身，呼叫端怎麼解構都不會斷。

Vue 官方文件（Reactivity Fundamentals）因為 reactive() 的這些限制，建議以 ref() 為主要的宣告方式。reactive 適合「一直是同一個物件、不會被整個換掉」的狀態，例如一張表單的欄位集合。

選了 ref，.value 什麼時候可以不寫？

預設用 ref 的代價是到處都要寫 .value。Vue 在幾個地方會自動幫你取出 ref 的 .value，這叫解包（unwrap）。例如修好後徽章的範本只寫 {{ count }}，不用寫 {{ count.value }}。但規則不是「到處都解包」，寫錯地方就會拿到 ref 物件本身或 undefined。下面是在 Vue 3.5.44 實際跑過的結果：

情況會解包嗎例子
範本裡，<script setup> 頂層的 ref會const count = ref(0)，{{ count + 1 }} 顯示 1
reactive 物件的屬性會reactive({ c: ref(1) }).c 是 1
reactive 陣列的元素不會reactive([ref('拿鐵')])[0].value
reactive Map 的值不會map.get('a').value
範本裡，普通物件裡的 ref，拿去運算不會{{ order.total + 1 }} 顯示 [object Object]1
範本裡，{{ }} 最後算出來的值剛好是 ref會（只是顯示上的方便）{{ order.total }} 顯示 100

最後兩列最容易搞混：order = { total: ref(100) } 時，只有「整個 {{ }} 的結果就是那個 ref」才會幫你取值；一拿去運算，算的就是 ref 物件本身，加 1 時被轉成字串 [object Object] 再接上 1。修法是把 ref 放到頂層：const { total } = order，範本寫 {{ total + 1 }}。

反過來也要注意：ref 放進 reactive 物件後就被解包了，state.c 已經是數字，不是 ref，寫 state.c.value 會得到 undefined。

💡 實務上：團隊先講好用哪一種，比哪一種比較好重要
接手別人的專案時，常看到同一個檔案裡 ref 和 reactive 混著用，讀的人每一行都要想「這裡要不要寫 .value」。多數團隊的做法是寫進慣例：預設 ref，只有像咖啡店後台「新增商品」表單那種欄位固定、不會整個換掉的物件才用 reactive。要注意的是「從 API 拿回整包資料再換上去」的狀態，例如訂單列表、目前登入的使用者，這種幾乎都會被整個替換，用 ref 最省事。Code review 看到 reactive 時，資深工程師會先問一句：這個物件之後會不會被整個換掉、會不會被解構？

購物車的狀態放對了容器。點餐頁上還有兩樣東西要放進狀態：一份 5000 筆的菜單，和一台收據印表機。照「預設用 ref」的慣例直接放進去，兩個都會出問題。

菜單看板有 5000 筆：每一筆都需要被追蹤嗎？

點餐頁旁邊有一塊菜單看板，顯示所有門市的品項，共 5000 筆。資料每隔一段時間從 API 整包重新拿回來換上去，只有偶爾某一筆會被標成售完。

問題在於 ref 和 reactive 都是深層的：前面解釋清單為什麼會更新時看過，透過 proxy 讀到的物件也會被包成 proxy。ref(5000 筆品項) 的每一筆在被讀到時都會被包成 proxy，每次讀屬性都要經過 track。看板渲染時會讀每一筆的名稱、價格、售完狀態，於是 5000 筆都被包成 proxy、每個讀到的屬性都記下依賴。但這份資料只用來顯示、不會一筆一筆改，這些成本是白花的。

Vue 為這種情況提供了淺層響應：shallowRef 只追蹤 .value 本身，內容原樣保存，不轉成 proxy；shallowReactive 只追蹤第一層屬性。換 .value 會通知，改 .value 裡面的東西不會。

代價是你必須把內容當成不可變的（TS 課第 2 課的不可變更新）：不直接改原本的物件，而是做一份改好的新陣列、新物件，再換掉整個 .value。標售完就變成這樣：

const menu = shallowRef(rows)   // rows 是 5000 筆品項

menu.value[0].soldOut = true    // ✗ 不會通知：shallowRef 不管內部
menu.value = menu.value.map(r => (r.id === 1 ? { ...r, soldOut: true } : r))   // ✓ 換掉 .value 才通知

第一行改的是陣列裡某個物件的屬性，.value 還是同一個陣列，shallowRef 沒有攔截到任何寫入。第二行用 map 產生新的陣列，售完的那一筆用展開語法做成新物件，其他品項沿用原本的物件，最後把新陣列寫進 .value，這一次寫入才會通知。

triggerRef(menu) 可以在改完內部後手動通知，看起來比較省事，但這就變成「直接改原本的物件」。原物件如果也被別處拿著（例如上一次的查詢結果、比較用的舊值），會一起被改到，而且改的人和受影響的人在不同的地方，很難查。能換整個值就換，triggerRef 留給沒辦法複製的情況。

練習 2 要你把菜單看板改成這個寫法。菜單的問題用「整個換掉」就解決了；收據印表機不一樣，它是別人寫的物件，你換不掉它的內部，而且一放進 reactive 就直接丟錯。

收據印表機一放進 reactive 就壞了：proxy 不是原物件

結帳時要呼叫的 ReceiptPrinter 是第三方套件提供的類別，它用 #private 欄位（TS 課第 3 課）存待印的佇列。把它放進點餐頁的 reactive 狀態，結帳時一呼叫 state.printer.print() 就丟錯。不用 Vue，用普通 Proxy 就能重現（reactive 回傳的也是 Proxy），執行後看第二次呼叫印出的錯誤：

在 Vue 3.5.44 裡把它放進 reactive，錯誤一樣：TypeError: Cannot read private member #queue from an object whose class did not declare it。這個訊息不會提到 proxy 或 Vue，第一次遇到很難聯想到是響應式造成的。

為什麼會這樣？第 1 課講過，Proxy 是包在原物件外面的另一個物件。Vue 的 reactive 也一樣：

const raw = { name: '拿鐵' }
const a = reactive(raw)

a === raw              // false：proxy 跟原物件是兩個物件
raw.name = '美式咖啡'   // 改原物件：資料真的變了，但沒經過 proxy，畫面不會更新

a === raw 是 false，這就是印表機壞掉的原因。#private 欄位只有宣告它的 class 自己的實例能存取，JavaScript 檢查的是「這個物件是不是那個實例本身」，不是「長得像不像」。放進 reactive 之後，你拿到的是 proxy。呼叫 proxy.print() 時，方法裡的 this 是點號前面的物件，也就是 proxy，而不是原本的實例。方法裡讀 this.#queue，proxy 不是宣告 #queue 的那個實例，就丟錯了。

同一件事反過來也會出事，就是上面最後一行：直接改原物件，資料真的變了，但沒經過 proxy 的 set trap，沒有 trigger，畫面不知道要更新。proxy 和原物件還有幾條身分規則（同一個物件 reactive 兩次、toRaw、isReactive），以及拿它們做比較、快取時會怎麼對不上，整理在課末「補充與查表」。

修法是 markRaw：標記這個物件永遠不會被轉成 proxy，放進 reactive 也是原樣。或者整個實例放在 shallowRef 裡，上一節看過，shallowRef 不會把內容轉成 proxy。

const state = reactive({
  status: 'idle',
  printer: markRaw(new ReceiptPrinter()),   // printer 原樣保存，status 仍然是響應式
})
markRaw 只標記這一個物件（官方文件稱為只作用在 root level）。之後寫 state.printer = new ReceiptPrinter()，新的實例沒有標記，讀回來又是 proxy；被標記物件裡面的子物件也沒有標記，另外放進 reactive 一樣會變成 proxy。所以第三方實例要在建立的那一行就 markRaw，每次建立都要。

到這裡有三種放狀態的方式，取捨是：預設用 ref；資料量大而且只會整批替換，用 shallowRef；第三方實例用 markRaw 或 shallowRef。不要為了「可能比較快」把所有狀態都改成 shallow，那會讓每次修改都得記得換整個值，第 23 課會教先量測再優化。練習 3 要你修好結帳時的印表機。

💡 實務上：圖表、地圖、SDK 實例一律不要變成響應式
後台的營收圖表（例如 Chart.js、ECharts 的實例）、門市地圖、金流或推播 SDK 的 client，都是「建立一次、呼叫它的方法」的物件，你只需要 Vue 追蹤你自己的資料（例如圖表要畫的數字），不需要追蹤實例內部。放進深層 reactive 輕則每次操作多一層 proxy 的成本，重則像上面一樣丟錯，而且錯誤訊息不會提到 proxy，很難一眼看出原因。實務上常見的寫法是：實例用普通變數或 shallowRef 保存，資料變了再用 watch 呼叫它的更新方法。

點餐頁的狀態都放對了位置。最後一個問題是誰可以改它們：狀態一旦交出去給好幾個元件用，任何一個元件都可能繞過你寫好的函式直接改。

狀態交出去之後誰都能改？用 readonly 只給看

回到 useCart：它回傳 add()，是因為加品項時要同時改清單和數量。如果某個元件直接對 items push，清單多了一筆，count 卻沒加，兩邊就對不上，又是一張「徽章數字不對」的客服單。而且這次不是斷線，是有人繞過了 add()，要從所有用到購物車的元件裡找出是誰改的。

readonly 回傳唯讀的 proxy：讀到的永遠是最新的值，但透過它寫入會失敗，開發模式下印出警告，例如 Set operation on key "count" failed: target is readonly.，引號裡是你試著寫入的屬性名稱。唯讀是深層的，透過它讀到的巢狀物件、陣列也一樣不能改。它常用來設計「狀態只能透過函式修改」的介面。把 useCart 改成這樣（為了聚焦 readonly，這裡回傳整個 state，不做練習 1 的解構）：

function useCart() {
  const state = reactive({ items: [] as CartItem[], count: 0 })
  function add(item: CartItem) {
    state.items.push(item)
    state.count++
  }
  return { state: readonly(state), add }   // 外面看得到最新的 items、count，但只能用 add 改
}

外面拿到的 state 是唯讀的 proxy，讀 state.items、state.count 照樣被追蹤，add 改了內部的 state，外面也會看到新的值；但外面想直接 state.items.push(...) 只會得到警告，清單和數量就不會再對不上。陣列的 push 實際上會寫入新索引和 length，所以警告裡的 key 會是 "0"、"length" 這類名稱。這樣出問題時，所有修改都集中在 add，查 bug 只要看一個地方。訂單佇列這類其他共用狀態也是同一招。第 13 課的 provide/inject 和第 15 課的 Pinia 會再用到這個寫法。

proxy 與原物件的身分規則

const raw = { name: '拿鐵' }
const a = reactive(raw)

a === raw              // false：proxy 跟原物件是兩個物件
reactive(raw) === a    // true：同一個物件 reactive 兩次，拿到同一個 proxy
toRaw(a) === raw       // true：toRaw 取得 proxy 背後的原物件
isReactive(a)          // true
isRef(ref(1))          // true

「比較、快取時對不上」指的是這種情況：用原物件當 key 存進 Map，之後拿 proxy 去查，因為 Map 用的是同一個物件才算相等，proxy 不是原物件，就查不到：

const raw = { id: 2, name: '拿鐵' }
const cache = new Map([[raw, '已快取']])
const item = reactive(raw)

cache.get(item)          // undefined：proxy 不是當初存進去的那個 key
cache.get(toRaw(item))   // '已快取'

同樣的事也會發生在 ===、array.includes、Set 上：一邊拿原物件、一邊拿 proxy，就不相等。所以比較兩個東西時，要嘛兩邊都是 proxy，要嘛兩邊都先 toRaw。

toRaw 是「暫時繞過追蹤」的逃生門，用在這幾種地方：上面那種需要原物件身分的比較或查表；把狀態交給不需要響應性的函式庫讀（例如序列化、交給圖表繪製），省掉每次讀屬性經過 proxy 的成本。不用的後果就是上面的查不到、或多付追蹤成本。但官方文件不建議一直拿著原物件：之後透過它修改，沒經過 proxy，畫面不會知道。拿來讀、用完就丟。

isReactive、isRef 用來在寫共用函式時判斷收到的是什麼，例如練習 1 的測試就用 isRef(count) 檢查你回傳的是 ref 還是數字。

元件測試的最小入門

這一課的練習只寫 .ts，但第 5、6 課的練習會出現元件，先認識這幾樣就夠，第 7、8 課再完整說明。

單檔元件（SFC，single-file component）是一個 .vue 檔，裡面有三個區塊：

<script setup lang="ts">
import { ref } from 'vue'
const count = ref(0)
const input = ref<HTMLInputElement | null>(null)   // 跟範本裡 ref="input" 同名，掛載後拿到那個 <input>
</script>

<template>
  <input ref="input">
  <button @click="count++">加一杯（{{ count }}）</button>
</template>

<style scoped>
button { font-weight: bold; }
</style>

<script setup> 裡宣告的變數，範本可以直接用。在元素上寫 ref="input"，掛載後就能在程式裡拿到那個 DOM 元素，這叫 template ref（第 8 課深入）。

測試用 VTU 操作元件：

import { mount } from '@vue/test-utils'
import Counter from './Counter.vue'

const wrapper = mount(Counter)                 // 掛載：在 happy-dom 裡渲染出來
await wrapper.find('button').trigger('click')  // 找到按鈕並點一下
expect(wrapper.text()).toContain('加一杯（1）')
await wrapper.find('input').setValue('拿鐵')   // 在輸入框輸入
wrapper.unmount()                              // 卸載

trigger、setValue 一定要 await：Vue 不是改了資料就立刻更新畫面，而是等一下批次更新（第 6 課的主題），await 會等到畫面更新完。

練習

練習 1：useCart() 回傳 { items, count, add }。起始程式把 reactive 狀態解構後回傳，所以呼叫端 add() 之後 count 永遠是 0。修改成呼叫端解構後仍有響應性：count 是 ref，items 是 ref 或 reactive 陣列；依賴 count 的 computed 會重新計算；每次呼叫 useCart() 各自一份購物車。

練習 2：createMenuBoard(rows) 管理 5000 筆品項的菜單看板。起始程式用 ref 存陣列，售完時直接改原本的物件。改成：rows 用 shallowRef，品項不被轉成 proxy；replaceAll(next) 直接把 next 換上去（不用複製）；markSoldOut(id) 產生新的陣列，售完的那一筆換成新物件，其他品項沿用原本的物件，任何原本的物件都不能被改到；用 id 找品項，不能假設 id 跟陣列位置對得上。每次 replaceAll、markSoldOut 之後，watch(board.rows) 都要觸發一次。

練習 3：ReceiptPrinter 有 #queue 私有欄位（當成第三方類別，不能改它）。useCheckout() 把它放進 reactive 狀態，結果 state.printer.print('#12') 丟 TypeError。修好它：state.printer 不能是 proxy，也不要用 Object.freeze 這類方法讓實例不能再改，state.printer.print() 可以直接呼叫，state.status 仍然要是響應式（watch(() => state.status) 會觸發）。

練習 4：const state = reactive({ count: 0 })，接著 let { count } = state，再執行 count++。畫面上用到 state.count 的地方會更新嗎？

✓ 解構時把當下的值 0 複製到 count，之後 count++ 只改這個區域變數，沒有經過 proxy，Vue 不知道。如果寫成 const { count }，count++ 會直接丟 TypeError（不能改 const）。要解構又保持連線，用 toRefs 或 toRef。c 的 nextTick（等 Vue 這一輪批次更新完，第 6 課）跟這件事無關：根本沒有觸發任何更新，等多久都一樣。

練習 5：const books = reactive([ref('拿鐵')])，要怎麼讀到 '拿鐵'？

✓ reactive 陣列和 Map 的元素不會解包，所以要自己寫 .value。會解包的是 reactive 物件的屬性（reactive({ c: ref(1) }).c 是 1）。books 本身是 reactive 陣列，不是 ref，沒有 .value。

練習 6：<script setup> 裡有 const order = { total: ref(100) }，範本寫 {{ order.total + 1 }}，畫面顯示什麼？

✓ 範本只會解包頂層的 ref。order 是普通物件，order.total 拿到的是 ref 物件，加 1 時被轉成字串 [object Object] 再接上 1。只寫 {{ order.total }} 會顯示 100，因為 {{ }} 最後的結果剛好是 ref 時會幫你取值，但一拿去運算就不會。修法：const { total } = order，範本寫 {{ total + 1 }}。

常見錯誤

  • 解構 reactive 物件或 Pinia store：拿到的是當下的值；物件值還是 proxy 會繼續更新，數字、字串這類原始值就斷了。用 toRefs／toRef，store 用 storeToRefs。
  • 用 state = reactive({...}) 整個替換：畫面還追蹤著舊的 proxy。要整個換就用 ref 換 .value，或 Object.assign 改屬性。
  • 把 state.count 傳給 composable：函式收到的是數字。傳 ref 或 getter () => state.count。
  • 以為 reactive 物件的屬性還是 ref：放進去就解包了，state.c.value 是 undefined。
  • 把含 #private 欄位的第三方實例放進 reactive：呼叫方法時 this 是 proxy，讀私有欄位丟 TypeError。建立時用 markRaw，或放在 shallowRef。
  • 大陣列用深層 ref：每一筆都包成 proxy、每次讀屬性都要追蹤。只會整批替換的資料用 shallowRef。
  • shallowRef 裡直接改內容：不會通知。換掉整個 .value；triggerRef 會讓舊物件也被改到，能不用就不用。
  • toRaw 之後修改原物件，期待畫面更新：沒經過 proxy 就沒有 trigger。
  • 改測試檔或 node_modules 讓練習通過：每次檢查都會換回原本的測試檔，重新安裝會蓋掉 node_modules。要改的只有題目列出的檔案。

小結

  • 修 bug 先重現：node check.mjs vue 04 跑測試，讀懂測試名稱、中文說明、Expected／Received，就知道要修什麼。
  • 失去響應的三種寫法：解構、整個替換 reactive、把屬性值傳給函式。共同原因是手上剩下的是值，不是通往 proxy 的路。修法是 toRefs／toRef、改用 ref、傳 getter。
  • 預設用 ref：可以整個替換、可以安全地解構和傳遞。reactive 只用在不會被換掉的物件。
  • 自動解包：範本頂層的 ref、reactive 物件的屬性會解包；陣列元素、Map 的值、範本裡普通物件的巢狀 ref 拿去運算時不會。
  • 大量、只會整批替換的資料用 shallowRef，更新時換掉整個 .value。
  • proxy 不是原物件：reactive(raw) !== raw，改 raw 不會更新畫面；toRaw 只拿來暫時繞過追蹤。第三方實例用 markRaw。
  • 只給看不給改用 readonly，修改集中在自己提供的函式。
