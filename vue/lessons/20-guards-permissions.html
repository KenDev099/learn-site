階段 6：路由、權限與錯誤處理 · 第 20 課

路由守衛與權限：前端權限的界線

咖啡店後台的第一版只做了一件跟權限有關的事：店員登入後，選單裡看不到「菜單管理」。上線一週，出了兩件事。第一件，一位店員在網址列直接輸入 /admin/menu，頁面照樣打開，他把拿鐵的價格改成 1 元，伺服器也照存了。第二件，客服接到顧客來電：他點了一封信裡的「登入確認訂單」連結，網址確實是咖啡店的網域，登入後卻跳到一個長得一模一樣的頁面，要他「再輸入一次密碼」。

這課的任務是把後台的權限補完整。後台有三種人共用：顧客看自己的訂單，店員在吧台把自己門市的訂單標成「可取餐」，店長管菜單和門市的所有訂單。我們要先分清楚哪些事前端做了也擋不住人、前端真正該負責什麼；再把「誰能做什麼」寫成一份規則，依序接到換頁、登入後的回跳、重新整理後的登入狀態、頁面上的按鈕。最後用同一套守衛機制處理一個相鄰的問題：結帳表單填到一半被誤按離開。

這課的路線：
  1. 藏起按鈕、擋住網址，為什麼店員還是改得到菜單：認證與授權的差別，前端權限的界線，真正的防線在哪裡（開場問題的最小答案）。
  2. 誰能對哪筆訂單做什麼：只看角色不夠，把「店員只能動自己門市的訂單」寫成一個可以測試、預設拒絕的 can()。
  3. 換頁時在哪裡檢查：全域守衛讀路由上的標記，沒登入導去登入頁、沒權限導去 403。
  4. 登入後要回到哪裡：開場第二件事的成因，?redirect= 怎麼擋下釣魚網站。
  5. 店長一重新整理就被踢到登入頁：守衛要等登入狀態載入，而且只載入一次。
  6. 頁面裡的按鈕和伺服器回的 403：同一個 can() 用在畫面上，401 與 403 各怎麼處理。
  7. 結帳填到一半誤按離開：守衛反過來用，把人留在頁面上。
這課會用到：
  • 第 19 課的路由：路由表把網址對到元件，巢狀路由的子路由掛在父路由底下；測試用 createMemoryHistory() 建立真正的 router。

藏起按鈕、擋住網址，為什麼店員還是改得到菜單？

要回答這個問題，先分清楚兩個常被混在一起的詞。認證（authentication）是確認「你是誰」：輸入帳號密碼登入，伺服器確認你是店員小陳，這就是認證。授權（authorization）是在知道你是誰之後，決定「你能做什麼」：小陳能不能改菜單、顧客王小明能不能看陳美華的訂單，都是授權的問題。開場的店員已經通過認證，他是合法登入的店員；出問題的是授權：系統沒有在「改菜單」這個動作上確認他有沒有這個權限。

那前端藏按鈕、擋網址為什麼不算授權？因為前端程式碼整份送到使用者的瀏覽器上執行。使用者可以在開發者工具裡改它、跳過它，或乾脆不用它：在 Network 分頁看一次「改價格」送出的請求長什麼樣，複製成 curl 指令，換個價格再送一次，整個 Vue 應用完全沒有參與。伺服器收到請求時，只看得到請求本身，分不出它是從你的畫面發出的，還是有人手打的。所以把「菜單管理」按鈕藏起來、在路由擋住 /admin，都不是安全措施。開場的店員之所以改得了價格，根本原因是伺服器的菜單 API 沒有檢查權限。

圖裡的三層各管一件事。瀏覽器裡的守衛和隱藏按鈕，決定使用者看到什麼。API 伺服器在每一個請求進來時檢查「這是誰、他能不能做這件事」，這是真正的防線。資料庫還能再擋一層：Row Level Security 讓同一句查詢只回傳這個人看得到的列，就算伺服器某個 API 忘了檢查，資料也不會整批外洩。

既然擋不住人，前端為什麼還要做權限？因為使用者體驗。顧客點進 /admin，應該看到「你沒有權限」，而不是一頁載入失敗、到處跳錯誤的畫面；店員的選單不該出現按了只會失敗的按鈕。前端的權限檢查服務的是有權限的人與誤闖的人，不是攻擊者。

這帶出整課的原則：前端和伺服器用同一套規則。伺服器依規則決定能不能做，前端依同樣的規則決定要不要顯示。兩邊的規則一旦不一致，就會出現「按鈕在、按下去卻 403」或「明明有權限、按鈕卻不見」。後端怎麼實作授權，auth 課第 1 課和第 18 課會從伺服器的角度深入。所以下一步是把這套規則寫清楚：咖啡店裡，到底誰能做什麼？

誰能對哪筆訂單做什麼？把規則寫成一個 can()

最直覺的寫法是按角色分：每個使用者有一個角色，角色決定能做哪些動作。這種模型叫角色型存取控制，英文 role-based access control，通常簡稱 RBAC。咖啡店有三個角色：customer（顧客）、barista（店員）、manager（店長）。

但只看角色，規則寫不完整。「顧客可以查看訂單」，不是每一筆訂單都能看，只能看自己的；「店員可以把訂單標成可取餐」，也只限自己門市的。要回答這些問題，光知道使用者的角色不夠，還要看資源本身：這筆訂單是誰下的、屬於哪間門市。這叫資源層級授權（resource-level authorization）。

漏掉資源層級會怎樣？顧客王小明打開自己的訂單 /orders/7，把網址改成 /orders/8，就看到陳美華的訂單，因為系統只確認了「他是顧客、顧客可以看訂單」，沒確認「這筆是不是他的」。這種漏洞叫 IDOR，全名 insecure direct object reference，中文是「不安全的直接物件參照」：網址或請求裡直接帶著資料的 id，系統拿到 id 就照做，沒檢查這個人能不能碰這筆資料。後端課稱它 BOLA，auth 課第 19 課會講伺服器怎麼擋。

所以一條完整的權限規則有三個維度：誰（角色）、做什麼（動作）、對哪個資源。咖啡店訂單的三個動作寫成表：

角色order:view 查看order:cancel 取消order:ready 標成可取餐
customer自己的訂單自己的、狀態是 pending不行
barista自己門市的不行自己門市的
manager自己門市的自己門市的自己門市的

接著把這張表變成程式，而且要寫成純函式 can(user, action, order)。純函式的意思是：輸入一樣，輸出就一樣，不碰畫面、不呼叫 API、不讀全域狀態。這樣寫有兩個好處。第一，可以照表把每一格都測過，表上有 9 格，加上各種缺資料的情況，每一種都是一行測試。第二，等一下的路由守衛、頁面上的按鈕、選單全部呼叫它，規則就只有一份。如果改用在各個範本裡寫 v-if="user.role === 'manager' || …"，同一條規則會散落在十個地方，哪天規則改了，一定有地方漏改。

這個例子背後的原則叫預設拒絕（fail closed）：只有在明確符合某條允許規則時才放行，其他任何情況都拒絕。資料缺了、型別不對、角色不認得、動作不認得，一律回傳 false。反過來的寫法是「沒有被禁止就放行」，那麼每一種沒想到的情況都會變成漏洞。同樣的道理，角色比對也不要轉大小寫：收到 'Manager' 代表資料出了問題，它不是合法的角色，該拒絕，而不是猜它大概是 'manager'。

💡 實務上：權限表要跟後端、PM 對同一份
實際專案裡，「誰能做什麼」通常先由 PM 寫成一張表，後端照它實作、前端照它顯示；新功能上線前，資深工程師會先問「這個動作誰能做？資料是誰的？」並把答案補進表裡。常見做法是後端在「取得目前使用者」的 API（例如 /me，後面「重新整理」那一節會用到）回應裡直接給權限清單（例如 ['menu:edit', 'reports:view']），前端只負責查表，少一份會跟後端不一致的規則；但「這筆訂單是不是他的」這種資源層級的判斷，前端還是需要訂單資料才能算。角色少、規則簡單時，一個 can() 就夠，不需要引入權限框架。

規則寫好了，但它還沒被任何地方呼叫。開場的店員是從網址列直接進 /admin/menu 的。伺服器那邊要補上檢查；前端這邊，至少要讓他進去時看到「沒有權限」，而不是一個能操作的頁面。所以前端第一個要接上規則的地方，是換頁的那一刻。

換頁時在哪裡檢查？全域守衛與 route meta

在 SPA 裡，使用者每點一次 RouterLink、程式每呼叫一次 router.push、使用者每按一次上一頁，vue-router 都會從目前的路由換到另一個路由，這個過程叫導航（navigation）。vue-router 允許我們在導航的前後掛上自己的函式，這些函式叫導航守衛（navigation guard）。守衛可以讓這次導航照常進行，也可以取消它，或改把使用者帶到別的頁面。用 router.beforeEach 註冊的是全域守衛：不論從哪一頁換到哪一頁，每一次導航在真正換頁之前都會先經過它。

守衛要做判斷，得先知道「這一頁需要什麼」。一種寫法是在守衛裡列出路徑：if (to.path.startsWith('/admin'))。這等於把規則又寫了一份在守衛裡，新增一個後台頁面時很容易忘記改。比較好的做法是把需求標在路由本身：vue-router 的每一條路由都可以有一個 meta 欄位，放任意的自訂資料，叫 route meta。我們在需要登入的路由標 requiresAuth: true，在需要權限的路由標 permission，守衛只要讀標記，不用知道有哪些路徑。

巢狀路由有一個方便的性質：守衛拿到的 to.meta，會把父路由到子路由一路上的 meta 合併起來。所以只要在 /admin 標了權限，底下的 /admin/menu 自動繼承，新增後台子頁面時不會漏標。

meta 預設沒有我們自訂欄位的型別。vue-router 把 meta 的型別宣告成一個叫 RouteMeta 的介面，TypeScript 允許在自己的專案裡對別的套件宣告過的介面補上欄位，這種寫法叫 module augmentation。補上之後，permission 寫成清單以外的值，vue-tsc 會報錯，守衛讀 to.meta.permission 時也拿得到正確的型別：

declare module 'vue-router' {
  interface RouteMeta {
    requiresAuth?: boolean
    permission?: 'orders:board' | 'menu:edit' | 'reports:view'
  }
}

const routes = [
  { path: '/login', name: 'login', component: () => import('./views/Login.vue') },   // 不要求登入
  { path: '/403', name: 'forbidden', component: () => import('./views/Forbidden.vue') },
  { path: '/orders', component: () => import('./views/Orders.vue'), meta: { requiresAuth: true } },
  {
    path: '/admin',
    meta: { requiresAuth: true, permission: 'menu:edit' },
    children: [{ path: 'menu', component: () => import('./views/AdminMenu.vue') }],
  },
]

這裡的 permission 不是上一節表格裡的 order:view 那些動作，為什麼？因為換頁的那一刻還沒有任何一筆具體的訂單，守衛要回答的只是「這個角色能不能進這一頁」。這是頁面層級的權限，不需要看資源，所以不必動用 can(user, action, order)，另外寫一個只看角色的 hasPermission(user, permission)，查一張「角色 → 可進入的頁面」對照表：

const ROLE_PERMISSIONS = {
  customer: [],
  barista: ['orders:board'],
  manager: ['orders:board', 'menu:edit', 'reports:view'],
}

function hasPermission(user, permission) {
  if (!user || !Object.hasOwn(ROLE_PERMISSIONS, user.role)) return false   // 沒登入、不認得的角色：拒絕
  return ROLE_PERMISSIONS[user.role].includes(permission)
}

它跟 can() 放在同一個權限模組（練習 3 的 permissions.ts），一樣預設拒絕：沒登入、角色不在表上，都回傳 false。用 Object.hasOwn 而不是 user.role in ROLE_PERMISSIONS，是因為 in 會往原型上找，角色如果是 'toString' 會被當成存在。前面「實務上」提到後端在 /me 直接給權限清單的做法，換到這裡就是：hasPermission 不查本地的表，改成查 /me 回來的那份清單，守衛完全不用改。

守衛怎麼告訴 vue-router「放行」「取消」或「改去別頁」？用回傳值（這是 vue-router 5.4.0 官方文件的寫法）：

回傳結果
什麼都不回傳（或 true）放行
false取消這次導航，留在原頁
路由位置，例如 '/'、{ name: 'login' }放棄這次導航，改導到那裡（會再經過一次守衛）

把這三種回傳組合起來，就是後台的全域守衛：

router.beforeEach((to) => {
  if (to.meta.requiresAuth && !auth.user) {
    return { name: 'login', query: { redirect: to.fullPath } }   // 帶上回跳網址
  }
  if (to.meta.permission && !hasPermission(auth.user, to.meta.permission)) {
    return { name: 'forbidden' }
  }
  if (to.name === 'login' && auth.user) return '/'            // 已登入不用再登入
})

這段程式有三個地方的寫法是刻意的。第一是檢查的順序：先看登入、再看權限。還不知道使用者是誰之前，談不上他有沒有權限；沒登入的人點進 /admin/menu，該看到的是登入頁，不是 403。

第二是導去登入頁時，把使用者原本要去的地方用 redirect 參數帶著，登入完才能送他回去。這裡用 to.fullPath 而不是 to.path：fullPath 包含 query 和 hash，例如 /orders?status=ready；path 只有 /orders，店員登入完回到訂單頁，原本篩好的「可取餐」條件就不見了。

第三是導向迴圈。守衛導去的登入頁和 403 頁，本身不能要求登入。想像守衛寫成「只要沒登入就導去登入頁」：前往登入頁的那次導航也沒登入，於是又被導去登入頁，永遠繞不出來。所以守衛只對標了 requiresAuth 的頁面導向，登入頁和 403 頁不標。vue-router 對這種迴圈的偵測很有限，帶著 redirect 參數的迴圈偵測不到，頁面會直接卡死，細節見課末。

舊教學裡守衛常寫成 (to, from, next) => { …; next() }，用第三個參數 next 決定結果。vue-router 5 已經不建議這種寫法，這課一律用回傳值；看到舊程式時怎麼對照改寫，見課末。

守衛到這裡已經擋得住誤闖的人，但它在導去登入頁時，順手在網址上放了一個 redirect 參數。開場的第二件事，就出在登入頁怎麼使用這個參數。

登入後要回到哪裡？擋下開放式重新導向

登入頁的做法看起來很自然：讀網址上的 ?redirect=，登入成功後導過去。問題是這個參數不只有我們的守衛會寫，任何人都能寫。攻擊者寄一封信給顧客：「你的訂單有問題，請登入確認」，信裡的連結是 https://你的網站/login?redirect=https://evil.example/login。顧客看到網域是咖啡店的，放心登入，登入頁照著 redirect 把他帶到攻擊者準備好、長得一模一樣的頁面，要他「再輸入一次密碼」。這正是開場客服接到的那通電話。網站把使用者導向攻擊者指定的外部網址，這種漏洞叫開放式重新導向（open redirect）。

修法的方向很明確：回跳網址只接受站內路徑，也就是以單一個 / 開頭的字串。但只檢查 startsWith('/') 不夠，因為瀏覽器解析網址的方式比想像的寬鬆。下面用 new URL(目標, 基準網址) 模擬瀏覽器怎麼解析每個目標，執行後看每一行的 origin：還是 https://shop.example 的才是站內。

第一行是正常的站內路徑。其餘幾行從上到下：

  • //evil.example 是「協定相對網址」：沿用目前的 https，主機換成 evil.example。它以 / 開頭，startsWith('/') 擋不住。
  • WHATWG URL 標準（瀏覽器和 Node 都照它解析）把 http、https 網址裡的 \ 當成 /，所以 /\evil.example 等於 //evil.example。
  • tab、換行這類控制字元會在解析前被刪掉，/\t/evil.example 也變成 //evil.example。控制字元在正常網址裡不會出現，直接拒絕。
  • https://evil.example 是完整的外部網址，最明顯的一種。
  • javascript: 網址被導過去時會執行裡面的程式，是 XSS（auth 課第 7 課）。

所以最穩的做法是兩道檢查。第一道用字串規則擋掉明顯的：不是 / 開頭、// 開頭、含反斜線或控制字元，都不要。第二道再用 new URL(target, 基準網址) 讓瀏覽器自己的解析規則確認一次，解析完的 origin 必須沒變。字串規則好讀、好審查，但可能漏掉沒想到的寫法；解析器的規則跟瀏覽器實際導向時一致，兩道一起用，任何一道沒想到的情況另一道還能擋住。驗證不過就導回預設頁，不要報錯給使用者看：會被擋下的多半是惡意連結，使用者也無從修正。

還有一個容易忽略的地方：route.query.redirect 的型別不一定是字串。?redirect=a&redirect=b 會變成陣列，只寫 ?redirect 沒有值時是 null，參數不存在則是 undefined。所以檢查函式要接受 unknown，第一步先確認它是字串。練習 2 會把這些規則寫成 safeRedirect。

💡 實務上：回跳網址檢查只寫一份，所有入口都用它
會帶回跳網址的地方不只登入頁：登出後、第三方登入（Google、LINE）的回呼、Email 裡的「點此登入」連結、權限不足後的「申請後返回」都有。把 safeRedirect 放在共用的工具模組，code review 時看到 router.push(route.query.…) 或 location.href = … 直接拿外部輸入，就要求改用它。開放式重新導向是資安掃描和滲透測試報告的常客，修起來很便宜，被回報了才補反而要走一輪緊急上線。

到這裡，開場的兩件事都有了答案。但這個守衛一上線，店長馬上回報一個新問題：他明明登入了，每次按重新整理都被踢回登入頁。

店長一重新整理就被踢到登入頁？登入狀態只載入一次

原因在守衛讀的 auth.user。它存在 第 15 課的 Pinia store 裡，store 只活在記憶體中。使用者按重新整理，整個應用從頭載入，store 也從頭建立，auth.user 回到 null。瀏覽器裡還留著登入用的 cookie 或 token，但前端要知道「現在是誰」，得先呼叫一次 /me：帶著 cookie 或 token 問伺服器「我是誰」。重新整理後的第一次導航發生得比 /me 回來更早，守衛如果不等這個請求完成就看 auth.user，看到的是 null，於是把已經登入的店長導去登入頁。

最直接的修法是在守衛裡每次都先呼叫 /me 再判斷，但這樣每換一頁就多一個請求，換頁變慢，伺服器也多一份不必要的負擔。使用者是誰，在這次開啟頁面的期間不會因為換頁而改變，只需要問一次。

做法是：第一次導航時開始載入，並把那個 Promise 存起來；之後的每次導航都 await 同一個 Promise：

let ready: Promise<void> | null = null

router.beforeEach(async (to) => {
  ready ??= auth.loadMe()    // 只有第一次會呼叫
  await ready                // 已經完成的 Promise，await 幾乎不花時間
  // …接著才看 auth.user
})

??= 只在 ready 還是 null 時才賦值，所以 auth.loadMe() 只會在第一次導航被呼叫。守衛本身改成 async 函式，vue-router 會等它回傳的 Promise 完成，才依結果決定放行或導向。

為什麼存 Promise，而不是存一個 loaded = true 的布林值？因為 loaded 要等 loadMe() 完成才會設成 true。在那之前如果又開始一次導航（例如使用者連點兩個連結），第二次導航看到的還是 false，又呼叫一次 /me。存 Promise 的話，請求一發出去 ready 就有值了，第二次導航拿到的是同一個還在進行中的 Promise，跟著一起等。這和第 17 課合併重複請求是同一招。練習 3 會把這個等待和上一節的守衛規則組成完整的 installGuards。

這解決了「一開始不知道是誰」。另一種情況是登入之後 token 過期，那是 API 層的事（第 16 課）：收到 401 先用 refresh token 換新的 token 重試一次，刷新也失敗才清掉 auth.user，導到 { name: 'login', query: { redirect: 目前的 fullPath } }。refresh token 怎麼輪替，auth 課第 10 課會從伺服器端講。

守衛現在完整了：等登入狀態、先看登入再看權限、回跳網址安全。但守衛只在換頁時執行。進到吧台看板之後，畫面上每一筆訂單的按鈕要不要顯示，守衛管不到。

頁面裡的按鈕和伺服器回的 403 怎麼處理？

吧台看板列出門市的所有訂單，每一筆旁邊有「可取餐」按鈕。這裡的判斷跟資源有關：店員只能標自己門市的訂單，所以要拿著每一筆訂單去問第二節寫好的 can()：

<button v-if="can(auth.user, 'order:ready', order)" @click="markReady(order)">可取餐</button>

按鈕要看的是這一筆訂單，所以呼叫的是資源層級的 can()；它和守衛用的 hasPermission 放在同一個權限模組，規則仍然只有一處。但前端算出「可以」，不代表伺服器一定會答應。HTTP 狀態碼 403 的意思是 Forbidden：伺服器知道你是誰，但拒絕你做這件事。為什麼前端判斷可以、伺服器卻回 403？例如店長剛把這位店員調到別間門市，伺服器的資料已經更新，前端的 auth.user 卻還是頁面載入時拿到的舊資料。前端的權限資料只是一份副本，隨時可能過期。所以 API 回 403 時，畫面要告訴使用者「你沒有權限做這件事」，並且重新取得使用者資料，讓前端的權限跟上伺服器（權限改變後怎麼讓舊的 token 失效，auth 課第 18 課會談）。

403 很容易和上一節提到的 401 混在一起，但兩者的處理方式完全不同。401 的意思是「不知道你是誰」：沒登入，或 token 過期了，該走刷新流程、不行就導去登入頁。403 是「知道你是誰，但你不能做」，導去登入頁沒有用，登入完還是同一個人、同樣沒權限，反而會讓使用者在登入頁和原頁之間來回。

最後回到第一節的原則：v-if 拿掉的只是按鈕。如果某些資料已經在 API 回應裡，例如訂單列表回傳了顧客的完整手機號碼，畫面上不顯示，打開開發者工具的 Network 分頁照樣看得到。不該給這個人看的欄位，要由伺服器不回傳，隱藏不等於保護。

💡 實務上：按鈕要「藏起來」還是「停用並說明」，是產品決定
對完全無關的人（顧客）直接藏起來；對「應該知道有這功能、但目前不能用」的人（店員看到「取消訂單」），停用並提示「請找店長處理」通常比較不會讓人困惑，也少一堆「按鈕不見了」的客服回報。這要跟 PM、設計師一起決定，不要每個工程師各做各的。另外，畫面上的 403 錯誤訊息要讓使用者知道下一步（找誰、怎麼申請），只寫「Forbidden」會變成客服單。

權限的部分到這裡完成了。到目前為止，守衛做的都是決定使用者「能不能進來」；同一套機制也能反過來用，決定使用者「能不能離開」。

結帳填到一半誤按離開？用守衛把人留下來

顧客在結帳頁填了取餐人和備註，手一滑按到「回菜單」，填的內容全部不見。這跟權限無關，但解法用的是同一個工具：在導航發生前攔下來，問使用者一聲，他反悔就取消這次導航。

前面的全域守衛對每一次導航都執行，這裡只有結帳頁需要，所以改用元件層級的守衛 onBeforeRouteLeave：在結帳頁元件的 setup 裡註冊，只在使用者要離開這個路由元件之前呼叫。它的回傳值規則和全域守衛一樣，回傳 false 就是取消導航、留在原頁。

什麼時候該問？只有表單裡有還沒送出的修改時。這個狀態就是第 18 課的 dirty：目前的值和上次存下的不同。

const saved = ref({ name: '', note: '' })     // 最後一次成功送出的內容
const dirty = computed(() => name.value !== saved.value.name || note.value !== saved.value.note)

onBeforeRouteLeave(() => {
  if (dirty.value && !confirm('還沒送出的資料會不見，確定要離開嗎？')) return false
})

dirty 用「跟最後一次存下的內容比」來算，而不是用一個「打過字」的旗標。差別在使用者把內容改回原樣時：跟存下的內容比，改回原樣就不再是 dirty，離開不用問；用旗標的話，打過一個字就永遠是 dirty。saved 要在送出成功之後才更新；送出失敗時資料其實還沒存到伺服器，離開仍然要詢問。

程式裡的 confirm 不要寫死成瀏覽器的 window.confirm，而是由外面注入。正式環境可以傳 window.confirm，或傳第 11 課用 Teleport 做的對話框；後者是非同步的，守衛可以寫成 async，await 使用者的回答。測試時則傳一個假的函式，由測試決定使用者按了「確定」還是「取消」。練習 4 就是這樣測的。

onBeforeRouteLeave 只管 vue-router 的導航。使用者按重新整理、關掉分頁、在網址列輸入別的網站，都不經過 vue-router，守衛攔不到，要另外用瀏覽器的 beforeunload 事件：在事件上呼叫 event.preventDefault()，瀏覽器會顯示它自己的確認視窗，文字不能自訂。只在 dirty 時加上這個監聽，存好就移除。

💡 實務上：離開保護只放在「填很久、丟了會痛」的表單
結帳、商品編輯、長篇的客訴回覆值得加；搜尋框、篩選條件這類隨手可重填的不要加，到處跳確認視窗反而讓人煩到直接按「確定」。內容很長的表單（例如店長寫的菜單說明）比起擋住離開，更好的做法常是自動存成草稿，回來時還原。要做之前先跟 PM 對齊：哪些頁面要詢問、文案怎麼寫。上線前手動測一輪：改了再改回、送出失敗、送出成功、重新整理，四種情況都走過。

vue-router 偵測得到哪些導向迴圈

vue-router 5.4.0 只在開發模式、而且每次都導到完全相同的位置時，繞超過 30 次才中止並警告「possibly infinite redirection」。帶著 redirect 參數的迴圈每繞一次網址就變長（/login?redirect=%2Flogin%3Fredirect%3D…），每次的位置都不同，偵測不到，頁面就卡死。所以不能指望框架幫你抓，登入頁和 403 頁不能要求登入。

舊寫法：守衛的第三個參數 next

舊教學會用守衛的第三個參數 next：(to, from, next) => { …; next() }。vue-router 5 的 API 文件把它標成 Deprecated，5.4.0 在開發模式用它就會印出「The next() callback in navigation guards is deprecated」。它最常見的錯是同一條路徑呼叫了兩次 next（例如 if (…) next('/login') 後面忘了 else，又跑到最後的 next()），或某條路徑忘了呼叫，導航就永遠卡住。改寫成回傳值的對照：

舊寫法回傳值寫法
next()不回傳
next(false)return false
next('/x')return '/x'

練習

練習 1、2 在頁面上寫，練習 3、4 在 work/20/。

練習 1：寫 can(user, action, order)，照上面的權限表：

  • 顧客（customer）：只能查看自己的訂單（order.customerId === user.id）；只能取消自己的、狀態是 'pending' 的訂單。
  • 店員（barista）：可以查看、可以標成 ready 的，都只限自己門市的訂單；不能取消。
  • 店長（manager）：自己門市的訂單三個動作都可以，別的門市一律不行。
  • 預設拒絕：user 是 null、角色不認得（包括大小寫不同的 'Manager'）、動作不認得、門市或 id 缺少或型別不對，一律 false。

練習 2：寫 safeRedirect(target, fallback = '/')，登入頁用它處理 route.query.redirect：

  • target 不是字串（null、undefined、陣列）→ 回傳 fallback。
  • 只接受站內路徑：以單一個 / 開頭。擋下 //evil.example、/\evil.example、https://evil.example、javascript:alert(1)、含控制字元（\u0000～\u001f、\u007f）的字串，回傳 fallback。
  • 合法的路徑原樣回傳，query 和 hash 都要保留，例如 /orders?status=ready#top。

練習 3：完成 guards.ts 的 installGuards(router, auth)。起始版只看 auth.user，重新整理後 loadMe() 還沒跑，已登入的人就被踢走。要求：第一次導航前等 auth.loadMe() 完成，之後（包括同時開始的兩次導航）共用同一次，總共只呼叫一次；meta.requiresAuth 而沒登入 → { name: 'login', query: { redirect: to.fullPath } }；有 meta.permission 而 hasPermission() 不通過 → { name: 'forbidden' }（先看登入，再看權限）；已登入去 login → '/'；每次都讀最新的 auth.user。用回傳值，不要用 next：測試會檢查 vue-router 沒有印出任何警告。permissions.ts 已經寫好，不用改。

練習 4：CheckoutPage.vue 的取餐人、備註填了一半，離開頁面就不見了。用 onBeforeRouteLeave 加上離開保護：表單 dirty（跟最後一次成功送出的內容不同，一開始是空的）時離開要呼叫 props 注入的 confirm(訊息)，回傳 false 就留在原頁；沒改過、改回原樣、送出成功之後離開都不詢問；送出失敗時仍要詢問。測試用真正的 router，透過路由的 props 把假的 submit、confirm 傳進來。

練習 5：把「菜單管理」按鈕對店員藏起來，路由守衛也擋住 /admin。後台的菜單 API 還需要檢查權限嗎？

✓ c：前端程式整份在使用者的瀏覽器上，可以被修改、跳過；API 收到請求時並不知道它是不是從你的畫面發出的，所以每個 API 都要自己檢查身分與權限，資料庫的 RLS 再擋一層。a 錯：看不到按鈕只是畫面上的事，API 網址在前端程式裡找得到。b 錯：使用者完全掌控自己的瀏覽器，可以改、也可以不用你的程式。

練習 6：使用者資料和訂單資料都沒有 storeId，user.storeId === order.storeId 的結果是？

✓ b：讀不存在的屬性得到 undefined，undefined === undefined 是 true，缺資料變成越權。要先確認兩邊都是數字（typeof user.storeId === 'number'）再比較。a 錯：這正是常見的誤解。c 錯：user 本身存在，讀它不存在的屬性不會丟錯，只會得到 undefined。

練習 7：登入頁的 ?redirect= 是我們自己的守衛加上去的，登入後直接 router.push(redirect) 或 location.href = redirect 有什麼問題？

✓ a：網址是使用者（和攻擊者）能自己輸入的外部輸入，不能因為「平常是我們產生的」就相信它。這叫開放式重新導向，常被拿來做釣魚：連結的網域是你的，顧客就放心登入。b 錯：攻擊者不需要經過你的守衛，直接寫一個連結就好。c 錯：編碼只是讓字元能安全放進網址，解碼後還是 https://釣魚網站，要檢查的是解析後的 origin。

常見錯誤

  • 只在前端做權限檢查：隱藏按鈕、守衛擋頁面都只是使用者體驗，任何人都能跳過前端直接打 API。API 每個請求都要檢查，資料庫再用 RLS 擋一層。
  • 只看角色、不看資源：「顧客可以看訂單」寫成只檢查角色，改網址上的 id 就看到別人的訂單（IDOR）。規則要同時看角色、動作和資源本身。
  • 用 == 或沒檢查 undefined 的比較：兩個 undefined 相等，缺資料就被放行。先確認型別再用 ===，預設拒絕。
  • 權限判斷散落在各個範本裡：v-if="user.role === 'manager' || …" 寫在十個地方，改規則時一定漏。寫成一個 can()，畫面、守衛都呼叫它。
  • 導向迴圈：守衛對所有沒登入的導航都導去登入頁，登入頁自己也被導走。只對 requiresAuth 的頁面導向，登入頁、403 頁不要求登入。
  • 每次導航都重新載入使用者：每換一頁打一次 /me。存第一次的 Promise，之後 await 同一個；用布林值記錄擋不住同時進行的導航。
  • 開放式重新導向：?redirect= 不檢查就導過去。只接受單一 / 開頭、沒有反斜線和控制字元、解析後 origin 不變的路徑。
  • 回跳網址用 to.path：query 和 hash 不見，登入後篩選條件全沒了。用 to.fullPath。
  • 收到 403 就導去登入頁：403 是知道你是誰但不能做，登入完還是一樣。401 才走刷新、導去登入；403 顯示沒有權限並重新取得使用者資料。
  • 還在用 next：已標成 Deprecated，呼叫兩次或忘了呼叫都會出錯。直接回傳值。
  • 離開保護用「打過字」的旗標：改回原樣也要詢問；送出成功後忘了重設又一直詢問。跟最後一次成功存下的內容比較。

小結

  • 認證是「你是誰」，授權是「你能做什麼」。前端的權限檢查是使用者體驗，伺服器與資料庫才是防線；兩邊用同一套規則。
  • 權限 = 角色 × 動作 × 資源，漏掉資源就是 IDOR。寫成純函式 can(user, action, resource)，預設拒絕，用表格把每一格測過。
  • 全域守衛讀 to.meta（巢狀路由會合併）：先看登入、再用只看角色的 hasPermission(user, permission) 看頁面權限；回傳 false 或路由位置，不用 next；登入頁、403 頁不能要求登入；回跳網址用 to.fullPath。
  • 回跳網址是外部輸入：只接受站內路徑，字串規則加上 new URL 確認 origin 沒變，不通過就導回預設頁。
  • 重新整理後守衛要等登入狀態：存第一次 loadMe() 的 Promise，每次導航 await 同一個。
  • 畫面上的按鈕呼叫同一個 can()；隱藏不等於保護。401 走刷新流程，403 顯示沒有權限並重新取得使用者。
  • onBeforeRouteLeave 保護還沒存的表單，dirty 跟最後一次成功存下的內容比；關分頁、重新整理另外用 beforeunload。

下一課處理出錯的時候：元件、事件、Promise 的錯誤從哪裡來，怎麼用錯誤邊界顯示替代畫面，怎麼把正式環境的錯誤收集起來。
