階段 3：元件如何運作 · 第 11 課

slots 與 Teleport：把畫面交給使用者

咖啡店後台改版，你拿到兩張單。第一張：菜單要出現在三個地方，點餐頁每一列有大大的「加入」按鈕，吧台只要品名和數量，後台還要顯示分類和「下架」按鈕。現在的做法是複製出三份幾乎一樣的 MenuList，改一次價格格式就要改三個地方，而且總有一份忘了改。第二張：訂單列表裡按「刪除」跳出的確認框，被列表的 overflow: hidden 裁掉了一半，店員看不到「確定」按鈕。

兩張單看起來無關，其實是同一類問題：共用元件把某一塊畫面抓得太緊。MenuList 把「每一列長什麼樣」寫死在自己裡面，所以每多一種樣子就只能複製；確認框的 DOM 留在列表裡面，所以被列表的 CSS 裁掉。這課學兩個把畫面交出去的工具：slot 讓元件把「某一塊畫面長什麼樣」交給使用它的父元件決定；Teleport 讓元件把一部分 DOM 放到別的地方（例如 <body>），邏輯仍然留在原元件。做完這課，一份 MenuList 撐起三種畫面，確認框不再被裁掉，而且只用鍵盤、用螢幕報讀器也能操作。

這課的路線：
  1. 三種菜單畫面，props 為什麼撐不住：用 props 硬撐會怎麼失控，slot 怎麼把「畫面」交給父元件（第一張單的最小答案）。
  2. slot 放進每一列之後為什麼讀不到商品，作用域 slot 怎麼解：slot 內容看得到哪些變數，MenuList 怎麼把這一列的商品和「加入」動作交出去。
  3. 一張卡片要好幾個位置：具名 slot 和後備內容，父元件沒傳內容時怎麼不畫出多餘的外框。
  4. 確認框為什麼被裁掉：overflow、fixed、z-index 都看 DOM 位置，Teleport 把 DOM 搬到 <body>，邏輯留在原元件（第二張單）。
  5. 搬出去之後誰都用得了嗎：鍵盤和螢幕報讀器需要的角色與焦點管理，以及怎麼用測試確認。
這課會用到：
  • 第 9 課的 props 與 emits：父元件用 props 把資料傳進子元件，子元件用 emit 通知父元件發生了什麼。
  • 第 10 課的 defineModel：宣告一個可以 v-model 的值，這課拿來控制對話框開或關。

三種菜單畫面，props 為什麼撐不住？

先試最直覺的做法：只留一份 MenuList，用 props 告訴它要顯示什麼。點餐頁要大按鈕，就加一個 big-button；後台要分類和下架按鈕，再加 show-category、show-remove：

<!-- 點餐頁 -->
<MenuList :products="menu" big-button />

<!-- 後台 -->
<MenuList :products="menu" show-category show-remove />

每多一種畫面就多幾個開關，MenuList 的範本跟著長出一堆 v-if。下個月行銷想在品名旁邊加「新品」標籤，又要回來改 MenuList，再加一個 prop。元件越長越大，而且每個開關的組合都可能出錯。根本原因是 props 只能傳資料：一個字串、一個布林值、一個陣列。MenuList 收到資料之後，畫面還是得由它自己決定。父元件真正想說的是「這一列照我的樣子畫」，props 傳不了「樣子」。

有人會退一步，改傳 HTML 字串，在子元件裡用 v-html 插進去：

<!-- 不好：內容只能是純文字 -->
<MenuList :products="menu" action-text="加入" />

<!-- 更糟：為了放按鈕，改傳 HTML 字串再 v-html -->
<MenuList :products="menu" action-html="<button>加入</button>" />

第一種只能放文字。第二種看起來可以放任何東西，實際上有兩個問題。第一，按鈕綁不了 @click：v-html 插進去的只是一段 HTML，Vue 不會把它當範本編譯，裡面寫的 @click 不會變成事件監聽。第二，只要字串裡混進使用者輸入的內容，例如後台輸入的商品名稱，就是第 7 課講過的 XSS（跨站腳本）：攻擊者把會執行的 HTML 藏在資料裡，v-html 不會跳脫，攻擊者的腳本就在店員的瀏覽器裡直接執行。第 25 課會把這件事整理成安全規則。

slot（插槽）的想法反過來：子元件在範本裡用 <slot> 留一個位置，父元件把自己的範本內容塞進去。塞進去的不是字串，是真正的 Vue 範本，可以有元件、事件、v-if，跟寫在父元件其他地方一模一樣。先用一個最小的按鈕元件看它怎麼運作：

<!-- 子元件 FancyButton.vue -->
<button class="fancy">
  <slot />          <!-- 父元件的內容放在這裡 -->
</button>

<!-- 父元件 -->
<FancyButton>加入 <b>拿鐵</b></FancyButton>

<!-- 渲染結果 -->
<button class="fancy">加入 <b>拿鐵</b></button>

對照這段看三件事：子元件只寫了 <slot />，它不知道、也不需要知道會放進什麼；父元件把內容寫在元件的開始和結束標籤之間；渲染之後，那段內容出現在 <slot /> 原本的位置，按鈕的外框和 class 仍然是子元件的。父元件如果在裡面放一個帶 @click 的元素，事件也照常運作，因為那段內容是父元件範本的一部分，由 Vue 編譯，不是一段被插進去的字串。

這就是第一張單的最小答案：props 傳「資料」，slot 傳「畫面」。外框、間距、狀態由元件負責，中間長什麼樣由使用者決定。套到 MenuList 上，MenuList 該保留的是列表的骨架（<ul>、<li>、每一列的 key），每一列的內容則留一個 slot 給三個頁面各自決定。可是真的把 slot 放進 v-for 的每一列，馬上會撞到一個問題。

slot 放進每一列之後，為什麼讀不到 product？

照上一節的想法，把 MenuList 的每一列改成一個 slot，後台在 slot 內容裡顯示品名和分類：

<!-- MenuList.vue -->
<ul>
  <li v-for="product in products" :key="product.id">
    <slot />
  </li>
</ul>

<!-- 後台：想用 MenuList 的 v-for 變數 product -->
<MenuList :products="menu">
  {{ product.name }}（{{ product.category }}）
</MenuList>

直覺上，slot 內容最後渲染在 MenuList 的 <li> 裡，那裡正好有 product，應該讀得到。實際上讀不到：在 Vue 3.5.44 會得到「Property "product" was accessed during render but is not defined」的警告，再接著丟 TypeError。

原因是 slot 內容在父元件的作用域編譯。作用域（scope）指的是「一段程式看得到哪些變數」。Vue 官方文件的說法是：父元件範本裡的運算式只能存取父元件的作用域，子元件範本裡的只能存取子元件的作用域。這跟 JavaScript 的詞法作用域（lexical scope）是同一個規則：一個函式看得到哪些變數，看的是它寫在哪裡，不是它最後在哪裡被呼叫。

換成範本來講：上面那段 {{ product.name }} 寫在後台頁的範本裡，Vue 就把它編譯成後台頁的一部分，變數從後台頁找。後台頁沒有 product，所以讀不到；MenuList 的 v-for 變數屬於 MenuList 的範本，外面看不到。這條規則的另一面是好處：slot 內容可以自由使用父元件自己的資料和函式，例如後台的 isAdmin、removeProduct，寫起來跟父元件其他地方的範本完全一樣，不用透過 MenuList 轉手。

同一條規則也管到樣式。子元件的 <style scoped> 只套用在子元件自己範本產生的元素上；slot 內容的元素屬於父元件，所以子元件的 scoped 樣式套不到它們。子元件真的要替 slot 內容加樣式時有專用的選擇器，見課末「補充與查表」。

所以問題變成：「這一列是哪個商品」只有 MenuList 知道，畫面卻要父元件決定。MenuList 必須主動把這份資料交給 slot 內容。

作用域 slot：MenuList 怎麼把這一列的商品交出去？

解法是作用域 slot（scoped slot）：子元件在 <slot> 上像綁 props 一樣綁屬性，這些屬性叫 slot props，會傳給父元件的 slot 內容；父元件在接收的地方把它們解構出來用。資料仍然只從子元件流向父元件的那一段範本，父元件其他地方看不到。

寫出完整的 MenuList 之前，還要兩個寫法。第一個是給這個位置取名字。上一節沒有名字的 <slot /> 叫預設 slot（default slot）。預設 slot 其實也能接 slot props（父元件寫 #default="{ product }"），那為什麼還要取名？因為名字說明了用途：取名 item，使用 MenuList 的人一眼就知道這段內容會放進每一列；以後要加列表標頭之類的位置，也不會跟它混在一起。練習 1 也要求這個位置叫 item。有名字的 slot 叫具名 slot（named slot），子元件寫成 <slot name="item">，父元件用 <template #item> 指定內容要放進哪個位置，#item 是 v-slot:item 的縮寫。要接 slot props 時，在後面加上 ="{ product, add }"，寫法跟解構函式參數一樣。

第二個寫法回到吧台的需求：吧台不需要自訂，用原本那種「品名加價錢」的一列就好。如果每個不想自訂的頁面都要自己傳一份一樣的內容，就白白重複了。寫在 <slot> 開始和結束標籤中間的內容是後備內容（fallback content）：父元件沒有傳這個 slot 時才顯示，傳了就整個被取代。所以吧台什麼都不傳，拿到的就是預設的一列。

<!-- MenuList.vue -->
<ul>
  <li v-for="product in products" :key="product.id">
    <slot name="item" :product="product" :add="() => emit('add', product.id)">
      {{ product.name }} ${{ product.price }}    <!-- 後備內容 -->
    </slot>
  </li>
</ul>

<!-- 後台：自己決定一列長什麼樣，資料由 MenuList 給 -->
<MenuList :products="menu" @add="addToCart">
  <template #item="{ product, add }">
    <span>{{ product.name }}（{{ product.category }}）</span>
    <button @click="add()">+1</button>
  </template>
</MenuList>

照執行順序讀：MenuList 的 v-for 每跑一列，就把這一列的 product 和一個 add 函式綁在 slot 上；後台的 #item="{ product, add }" 把它們解構出來，決定這一列畫成「品名（分類）＋ +1 按鈕」；吧台不寫 #item，每一列就顯示後備內容的品名和價格。按下 +1 時，add() 讓 MenuList emit add 事件，後台的 @add="addToCart" 收到商品 id。下面這張圖是同一件事的資料流向：

為什麼傳 add 函式，而不是讓父元件自己處理點擊？因為「加入」可能還有規則，例如售完不能加、要先記錄是從哪個頁面加的。把規則放在 MenuList 裡，點餐、吧台、後台三種畫面都共用同一套行為；父元件只決定按鈕放哪裡、長什麼樣。如果每個頁面各自處理點擊，規則就又複製了三份，回到開場的老問題。

把「元件只給資料和行為，畫面全部交出去」推到底，就是無渲染元件（renderless component）：元件自己不產生任何畫面，只提供邏輯，所有畫面都透過作用域 slot 交給使用者，例如 <MouseTracker v-slot="{ x, y }"> 只把滑鼠座標交出去。不過在 Vue 3 裡，純邏輯（滑鼠位置、倒數計時、取資料）優先寫成 composable（第 12 課）：它就是一個函式，不用多掛一層元件實例，範本裡也不會多一層巢狀。官方文件也是這樣建議的。無渲染元件適合的是「邏輯和一部分 DOM 結構綁在一起」的情況，MenuList 就是：它要負責 <ul>、<li> 和 key，這些不是一個函式能給的。

到這裡，四種工具各自解決什麼問題可以整理成一張表：

要解決的問題用什麼例子
傳資料、設定props商品陣列、是否售完、尺寸
外框固定，中間的畫面由使用者決定slot卡片、版面、對話框的內容
畫面由使用者決定，但需要元件內部的資料作用域 slot列表的每一列、表格的儲存格
只有邏輯，沒有畫面composable滑鼠位置、倒數計時、取資料
💡 實務上：元件庫的表格和列表幾乎都靠作用域 slot
你最常「使用」作用域 slot 的地方是 UI 元件庫：例如 Element Plus 的表格欄位用 #default="{ row }" 拿到這一列的資料，自己決定要顯示狀態標籤還是操作按鈕，跟後台用 #item="{ product }" 是同一件事。自己寫共用元件時，資深工程師會先問「真的有第二、第三種畫面嗎？」MenuList 是因為已經有三種畫面才值得開 slot；只有一種畫面時，props 就夠了，太早開一堆 slot 反而讓元件難用、難改。slot 一旦被別人用了，slot 名稱和 slot props 就是公開的介面，改名等於改 API，所有使用的頁面都要跟著改。

一張卡片要好幾個位置：具名 slot 與沒傳內容時的外框

上一節的 item 是 MenuList 唯一的具名 slot；InfoCard 需要好幾個。MenuList 的每一列只需要一個位置，門市頁的 InfoCard 不一樣：上面是門市名稱，中間是地址，底部是「導航」之類的操作按鈕，三塊內容都由使用它的頁面決定，所以需要三個位置。上一節的具名 slot 可以有好幾個，一個沒名字的預設 slot 加上幾個具名 slot，同一個元件裡留幾個位置都行：

<!-- InfoCard.vue -->
<section class="card">
  <header><slot name="header" /></header>
  <div class="body"><slot /></div>
  <footer><slot name="footer">沒有操作</slot></footer>
</section>

<!-- 父元件 -->
<InfoCard>
  <template #header><h3>{{ store.name }}</h3></template>
  <p>台北市信義路 1 號</p>          <!-- 沒包 template 的內容進預設 slot -->
  <template #footer><button @click="navigate">導航</button></template>
</InfoCard>

對照這段看三件事：#header 的內容進 <header>；沒有包在 <template> 裡的 <p> 進預設 slot；#footer 的按鈕進 <footer>。父元件沒傳 #footer 時，<footer> 裡顯示後備內容「沒有操作」。{{ store.name }}、navigate 都是父元件的東西，跟上一節的作用域規則一樣，因為這段範本寫在父元件裡。

麻煩出在沒有底部操作的卡片。InfoCard 的 <footer> 有上邊框和內距，有些門市卡片根本不該有底部那一塊；後備內容只能換掉 <footer> 裡面的字，<footer> 元素本身還在，畫面底下就多出一條線和一塊空白。要讓整個外框消失，元件得先知道「父元件有沒有傳這個 slot」。在範本裡用 $slots，在 <script setup> 裡用 useSlots()：

<footer v-if="$slots.footer"><slot name="footer" /></footer>

<script setup lang="ts">
import { useSlots } from 'vue'
const slots = useSlots()
const hasFooter = () => !!slots.footer   // 要在 script 裡用時
</script>

$slots 是一個物件，父元件傳了哪些 slot，它就有哪些屬性，值是會回傳虛擬節點的函式；沒傳的就是 undefined。所以 v-if="$slots.footer" 讀起來就是「有傳 footer 才畫 <footer>」。

常見的另一種做法是要父元件多傳一個 :show-footer="true"。這等於讓同一件事有兩個來源：傳了 footer 卻忘了設 prop，內容不會出現；設了 prop 卻沒傳 footer，又是空框。直接看 slot 有沒有傳，判斷依據只有一個來源，不會互相矛盾。TypeScript 專案還可以替每個 slot 的 slot props 宣告型別，見課末「補充與查表」。

到這裡，slot 讓元件把畫面「長什麼樣」交了出去，第一張單完成。第二張單的確認框不一樣：它長什麼樣沒有問題，問題是它在 DOM 裡「放在哪裡」。

刪除確認框為什麼被裁掉？Teleport 把 DOM 搬出去

訂單列表為了捲動，在 .list 上加了 overflow: hidden，意思是「超出這個元素範圍的內容不顯示」。確認框寫在列表元件的範本裡，渲染出來的 DOM 也就在 .list 裡面，確認框比列表可見範圍高的那一截就被裁掉了。

常見的兩個補救都不可靠。第一個是改成 position: fixed，讓確認框相對整個視窗定位。但只要某個祖先元素有 transform、filter 或 perspective，fixed 就改成相對那個祖先定位，又被困回去。第二個是把 z-index 調大。z-index 決定元素重疊時誰蓋誰，但它只在同一個堆疊脈絡裡比較。堆疊脈絡（stacking context）是瀏覽器把元素分層的單位：某個元素符合特定條件（例如設了 transform），它和它所有的子孫就成為一層，這一層先整體跟外面的其他層比高低，裡面的 z-index 只決定層內的順序。祖先那一層比隔壁區塊低，對話框的 z-index: 9999 再大也蓋不過去。

這幾個現象有同一個根源：overflow 裁切、fixed 定位、z-index 堆疊，都由元素在 DOM 裡的位置決定。要根治，就得讓確認框的 DOM 不在列表裡面。可是確認框的開關狀態、按「確定」之後要刪哪一筆訂單，都在列表元件裡；把確認框拆成頁面最外層的另一個元件，又要多出一串 props 和事件把狀態接過去。

<Teleport> 解的就是這個衝突。Vue 心裡有兩棵樹：元件樹記錄「哪個元件是哪個元件的子元件」，決定 props、emit、狀態怎麼傳；DOM 樹是瀏覽器實際畫出來的元素，決定 CSS 怎麼套。平常兩棵樹的形狀一致。Teleport 讓它們分開：被包住的內容渲染到另一個 DOM 位置，但在元件樹裡仍然屬於原元件，props、emit、provide/inject（第 13 課）、響應式狀態都照常運作。

<button @click="open = true">刪除訂單</button>

<Teleport to="body">
  <div v-if="open" class="backdrop">
    <div class="dialog">…</div>
  </div>
</Teleport>

這段寫在列表元件裡：open 是列表自己的狀態，按鈕改它，v-if 讀它，跟沒有 Teleport 時一模一樣。唯一的差別是 .backdrop 渲染出來會是 <body> 的直接子元素，不在 .list 裡面，.list 的 overflow 和堆疊脈絡就管不到它。

to 接 CSS 選擇器或 DOM 元素，目標在 Teleport 掛載時必須已經存在；body 一定存在，所以最常用。暫時讓內容留在原位、延後找目標、好幾個 Teleport 指向同一個目標等選項，見課末「補充與查表」。

什麼時候不用：Teleport 不是效能工具，內容沒有被父層的 overflow 或堆疊脈絡困住，就不需要它。另外，做伺服器端渲染（SSR，第 24 課）時 Teleport 的內容要另外處理，不能直接以 body 為目標，細節也在課末。

瀏覽器原生的 <dialog> 搭配 showModal() 會把對話框放進頂層（top layer），不受 overflow 和 z-index 影響，按 Esc 也會觸發關閉。新專案值得先評估它；這課用 Teleport，是因為它也適用於提示訊息、下拉選單這些不是對話框的東西，而且概念在各種環境都一樣。
💡 實務上：對話框和提示訊息通常由團隊統一處理
正式專案很少在每個功能裡各自寫 Teleport：通常是元件庫的 Modal、Toast 已經內建，或團隊做一個共用的 ConfirmDialog，大家照用，這課練習 3 做的就是這種元件。這樣 z-index 的層級（下拉選單、對話框、提示訊息誰蓋誰）只需要定義一次，不會出現「這個彈窗被那個彈窗蓋住」的 bug。遇到「彈窗被裁掉、被蓋住」的回報時，先檢查祖先的 overflow、transform 和 z-index，確認是 DOM 位置的問題，再決定要不要搬出去，而不是先把 z-index 越調越大。

確認框看得到了，鍵盤和螢幕報讀器用得了嗎？

搬到 <body> 之後，確認框完整顯示，店員用滑鼠點「確定」這條路通了。但「看得到」不等於「用得了」。POS 的店員常常只用鍵盤操作；視障使用者靠螢幕報讀器（screen reader）使用網頁，它是把畫面上的內容念出來、讓人用鍵盤操作的軟體。讓這些人和各種裝置都能使用介面，叫可近用性（accessibility，常寫成 a11y）。對話框是最常做壞的地方：滑鼠點得到，鍵盤卻用不了。一個能用的確認框要做到兩件事：讓報讀器知道它是什麼，讓鍵盤焦點跟著它走。

第一件事是告訴螢幕報讀器「這是什麼」。報讀器讀的是 DOM，一個 <div class="dialog"> 在它眼裡只是一塊普通內容，它不知道這是對話框，也不知道該念哪一句當標題。ARIA（Accessible Rich Internet Applications）就是用來補這個資訊的一組屬性：role 說明元素的角色，aria-* 描述它的狀態和跟其他元素的關係。確認框需要三個：

  • role="dialog"：這是一個對話框。
  • aria-modal="true"：告訴螢幕報讀器對話框外的內容暫時無效，不要念出來。它只是一個說明，不會真的擋住滑鼠和鍵盤；擋住外面要靠遮罩和下面講的焦點管理。
  • aria-labelledby="標題的 id"：對話框的名稱是哪個元素的文字，報讀器打開時會念出「確定刪除訂單？，對話框」。id 用 Vue 3.5 的 useId() 產生，同一頁有好幾個對話框也不會重複，SSR 時伺服器和瀏覽器產生的 id 也一樣。

第二件事是焦點管理（focus management）。焦點是「鍵盤輸入現在會送到哪個元素」：鍵盤使用者靠 Tab 移動焦點、Enter 按下按鈕，焦點在哪裡就只能操作哪裡。對話框打開時，焦點如果還停在後面的列表上，鍵盤使用者根本進不了對話框。所以確認框要做到三件事：

  1. 開啟時聚焦對話框裡的元素（這裡是「確定」），不然焦點還停在後面的列表上。要等 DOM 更新完才有按鈕可以聚焦，用第 6 課的 await nextTick() 或 flush: 'post' 的 watcher。
  2. Esc 關閉：鍵盤使用者預期的行為。在對話框元素上寫 @keydown.esc，焦點在對話框裡時按鍵事件會冒泡上來。
  3. 關閉後焦點回到開啟它的元素：否則焦點掉回 <body>，店員要從頁面最上面重新 Tab 到原本的位置。開啟時記下 document.activeElement，關閉後呼叫它的 focus()。
const confirmButton = useTemplateRef<HTMLButtonElement>('confirmButton')
let returnFocusTo: HTMLElement | null = null

watch(open, (isOpen) => {
  if (isOpen) {
    returnFocusTo = document.activeElement as HTMLElement | null   // 焦點還沒移動
    confirmButton.value?.focus()                                    // post：按鈕已經在 DOM 裡
  } else {
    returnFocusTo?.focus()
  }
}, { flush: 'post' })

照 open 的兩個方向讀：變成 true 時，先記下現在有焦點的元素（通常是「刪除訂單」按鈕，但不一定），再把焦點移到「確定」；變成 false 時，把焦點還給剛才記下的元素。flush: 'post' 讓 callback 等 DOM 更新完才跑，這時「確定」按鈕已經渲染出來；用預設的時機，callback 會在 DOM 更新之前跑，v-if 還沒把按鈕放進 DOM，confirmButton.value 是 null，什麼都聚焦不到。

完整的模態對話框還要焦點陷阱（focus trap）：Tab 到最後一個按鈕時繞回第一個，不讓焦點跑到後面的頁面。這部分邊界情況很多（隱藏元素、iframe、Shift+Tab），正式專案建議用成熟的套件或原生 <dialog>，不要自己重寫。這課的練習先做好上面三件事。

寫完之後怎麼確定它真的做到了？手動點一遍只能確認這一次，下次有人改 ConfirmDialog 就可能悄悄壞掉，所以要寫成測試。Teleport 讓測試裡的一個習慣失效，檢查焦點還有另一個要求。第一，Vue Test Utils 的 wrapper.find() 只在元件的根元素底下找；對話框已經被搬到 document.body，wrapper.find('.dialog') 找不到，要直接在 document.body 裡找。第二點跟 Teleport 無關：只要測試要檢查焦點，不管有沒有用 Teleport，元件都必須用 attachTo: document.body 掛進真正的 document，focus() 才會改變 document.activeElement（第 8 課）。

const wrapper = mount(Host, { attachTo: document.body })
await wrapper.get('.opener').trigger('click')
const dialog = document.querySelector('[role="dialog"]')
expect(wrapper.element.contains(dialog)).toBe(false)   // 真的被搬到 body 了

這段測試先把有「刪除訂單」按鈕的父元件掛進 document，按下按鈕打開對話框，再用 document.querySelector 找到對話框，最後一行確認它不在元件自己的元素裡，也就是真的被 Teleport 搬走了。練習 3 的測試也是這樣找對話框、檢查 document.activeElement。

💡 實務上：最快的檢查是把滑鼠放一邊
可近用性的問題常到驗收時才被發現：政府、金融或大型品牌的網站常把無障礙列為交付要求，內部系統也有習慣全用鍵盤的使用者，例如咖啡店 POS 的店員。上線前最便宜的檢查是只用鍵盤把刪除訂單走一遍：Tab 得到嗎、看得出焦點在哪、Esc 關得掉、關閉後回到原位嗎？再用 macOS 內建的螢幕報讀器 VoiceOver 實際聽一次，或用 Chrome DevTools 的 Lighthouse（自動檢查工具）掃標籤和角色，但自動工具只抓得到一部分問題。能用元件庫或原生 <dialog> 就用，它們通常已經處理好焦點，省下自己踩邊界情況的時間。

✓ slot 內容寫在父元件的範本裡，運算式只看得到父元件的作用域，跟 JavaScript 的詞法作用域一樣，看的是寫在哪裡，不是渲染在哪裡。所以 a、b 都錯。要用子元件的資料，子元件必須在 <slot :product="product"> 上傳出來，父元件用 #default="{ product }" 接。

練習 5：什麼時候該用 Teleport？

✓ Teleport 只改 DOM 位置，解決的是 CSS 由 DOM 位置決定的問題：overflow 裁切、fixed 定位、z-index 堆疊。它不是效能工具，a 錯；在元件樹裡內容仍然屬於原元件，props、emit、響應式狀態都照常運作，c 錯。

練習 6：好幾個頁面都要「滑鼠位置」和「倒數計時」這種沒有畫面的邏輯，最適合做成什麼？

✓ 純邏輯用 composable（第 12 課），不用多建一個元件實例，也不會在範本裡多一層巢狀，官方文件也這樣建議。無渲染元件適合邏輯跟 DOM 結構綁在一起的情況，b 錯。mixin 的屬性來源不明、名稱會互相衝突，Vue 3 已經不建議，c 錯。

常見錯誤

  • 用 props 傳 HTML 字串再 v-html：綁不了事件，混進使用者輸入就是 XSS。要讓使用者決定畫面就用 slot。
  • 以為 slot 內容看得到子元件的變數：slot 內容在父元件的作用域編譯。需要子元件的資料，就用作用域 slot 傳出來，名字要和 #item="{ product }" 解構的名字一致。
  • 沒傳 slot 也渲染外框：產生空的 <footer>、多一條線。用 v-if="$slots.footer" 或 useSlots() 判斷，不要另外加一個 prop。
  • 以為 Teleport 能加速渲染，或以為它切斷了元件關係：它只改 DOM 位置。內容沒被 overflow 或堆疊脈絡困住就不需要。
  • SSR 時 Teleport 到 body：內容不在 renderToString 的字串裡，hydration 也找不到起點。改用專用容器，或掛載後才渲染 Teleport。
  • 對話框只做滑鼠操作：沒有 role 和 aria 屬性、開啟不聚焦、Esc 關不掉、關閉後焦點掉回 body。鍵盤和螢幕報讀器使用者就用不了。
  • 開啟時在同一段同步程式裡 focus()：按鈕還沒渲染，template ref 是 null。等 nextTick() 或用 flush: 'post'。
  • 測試 Teleport 時用 wrapper.find()：內容不在元件根元素底下。改在 document.body 裡找；要測焦點記得 attachTo: document.body。

補充與查表

  • 替 slot 內容加樣式：子元件的 <style scoped> 套不到 slot 內容，因為那些元素屬於父元件。子元件真的要替 slot 內容加樣式時，用 :slotted(p) 這種選擇器。
  • slot 的型別：useSlots() 拿到的 slot 沒有具體型別。TypeScript 專案可以用 defineSlots()（Vue 3.3+）宣告每個 slot 的 slot props 型別，第 14 課會用到。
  • Teleport 的 disabled：:disabled="true" 時內容留在原位，例如手機版想讓內容直接排在頁面裡。
  • Teleport 的 defer（Vue 3.5+）：等這一輪掛載完才找目標，所以目標可以是同一個應用程式裡、寫在後面的元素。目標必須在同一輪掛載或更新裡出現，晚一秒才出現還是會報錯。
  • 多個 Teleport 指向同一個目標：內容依掛載順序附加在後面。
  • SSR 與 Teleport：SSR 時 Teleport 的內容不在 renderToString 產生的字串裡，要從 SSR context 的 teleports 取出來自己插進頁面；官方文件建議 SSR 時不要以 body 為目標，改用專用的容器（例如 <div id="teleported">），或是乾脆等掛載後才渲染 Teleport。

小結

  • props 傳資料，slot 傳畫面。props 硬撐多種畫面會長出一堆開關，改傳 HTML 字串配 v-html 綁不了事件，還有 XSS 風險。
  • slot 內容在父元件的作用域編譯：看的是寫在哪裡，不是渲染在哪裡。要用子元件的資料，子元件在 <slot> 上綁 slot props，父元件用 #item="{ product, add }" 接；共用的行為（例如 add）也由子元件傳出來。
  • 預設 slot、具名 slot（#header 是 v-slot:header 的縮寫）、後備內容（寫在 <slot> 中間，沒傳才顯示）。
  • 純邏輯用 composable；邏輯跟 DOM 結構綁在一起時，才考慮無渲染元件。
  • 用 $slots／useSlots() 判斷有沒有傳某個 slot，沒傳就不渲染外框，不另外加 prop。
  • overflow、fixed、z-index 都由 DOM 位置決定。Teleport 只改 DOM 位置，元件樹不變，用來脫離 overflow 和堆疊脈絡；不是效能工具，SSR 時避免以 body 為目標。
  • 可用的對話框：role="dialog"、aria-modal、aria-labelledby，開啟時聚焦、Esc 關閉、關閉後焦點回到原元素。測試時在 document.body 裡找、用 attachTo 掛進 document。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：Cart 的範本直接顯示每一杯的數量和總價。店員按「+」執行 line.quantity = 2，從這一行到畫面更新，Vue 做了什麼？

✓ 元件的 render 是一個 effect，資料改變時排進佇列，下一輪才重跑；新舊 vnode 樹比對（patch）後只動有差異的 DOM。追蹤的單位是元件，整個 Cart 的 render 都會重跑，Patch Flags 只是讓比對跳過不會變的部分，b 錯在這裡。虛擬 DOM 的價值是讓「每次重新描述整個畫面」夠快，不是保證比手寫的 DOM 操作快。（第 7 課）

練習 8：購物車依序是美式、拿鐵、可頌，用 <CartLine v-for="(line, i) in lines" :key="i" :line="line" />，CartLine 用自己的 ref(false) 記住「展開客製化明細」。店員展開拿鐵那列，再刪掉美式，結果是？

✓ patch 靠 type 和 key 判斷是不是同一個節點。刪除後 key 0、1 還在，Vue 沿用這兩個 CartLine 實例、只換掉 line prop，key 2 被卸載，所以 key 1 的展開狀態留在原位、內容卻變成可頌。改用 :key="line.id"，狀態才會跟著資料走。a 是用穩定 id 當 key 才有的結果，Vue 不會自己找出哪一筆是哪一筆。（第 7 課）

練習 9：營收儀表板整天開著，店員在頁面間切換幾次後，調整視窗大小越來越卡。圖表元件的程式如下，問題在哪？

onMounted(() => {
  window.addEventListener('resize', () => chart.resize())
  timer = setInterval(refresh, 30_000)
})
onUnmounted(() => {
  window.removeEventListener('resize', () => chart.resize())
  clearInterval(timer)
})

✓ 長得一樣的兩個箭頭函式是兩個不同的函式，removeEventListener 找不到要移除的那一個；SPA 換頁不會重新載入，舊的處理函式和它留住的圖表一直累積。把函式存在變數裡（const onResize = () => chart.resize()），註冊和移除用同一個。b 錯在 Vue 只管它自己綁在範本上的事件，你自己加在 window 上的要自己收。（第 8 課）

練習 10：後台「編輯商品」對話框收到 product prop，範本寫 <input v-model="product.price" type="number">。店員把價格改成 0 再按「取消」，列表上的價格卻已經是 0。為什麼？

✓ props.product = … 會被擋下並警告，但讀出來的 product 是父元件的同一個物件，設定它的屬性沒有警告、直接改到父元件。修法是開啟時複製一份草稿給表單綁，按「儲存」才 emit('save', draft)，讓擁有資料的元件去改。b 錯在 Vue 不會幫你複製，不管是不是 reactive，傳的都是同一個物件的參照。（第 9 課）

練習 11：左邊是商品清單，右邊是 <ProductDetail :product-id="selectedId" />。點了別的商品，右邊還是第一個。ProductDetail 是這樣寫的，問題在哪？

const { productId } = defineProps<{ productId: number }>()
const product = ref<Product | null>(null)
onMounted(async () => {
  product.value = await api.getProduct(productId)
})

✓ prop 改變時 Vue 重用同一個實例、只更新 prop，所以要用 watch(() => productId, …, { immediate: true })，並在清理函式裡取消過期的請求。a 錯在 3.5 的解構 props 由編譯器改寫成 __props.productId，本來就有響應；問題是讀它的地方只執行一次，改成 props.productId 一樣只載入一次。另一個做法是父元件寫 :key="selectedId" 整個重建，代價是元件內所有狀態都重來。（第 9 課）

練習 12：<QuantityInput v-model="qty" />，子元件寫 const model = defineModel<number>()，按「+」執行 model.value++。父元件的 qty 是怎麼變成新值的？

✓ 元件上的 v-model 就是 modelValue prop 加 update:modelValue 事件，資料仍然單向流動；defineModel 回傳的 ref 讀的是 prop、寫的時候 emit。所以 v-model 不違反單向資料流，限制和轉換也可以放在 set 轉換器裡。a 錯在兩邊不是同一個 ref，父元件沒用 v-model 時子元件的寫入只會變成本地狀態。（第 10 課）

練習 13：MenuList 寫了 <slot name="item" :product="product" :add="add" />，父元件 MenuPage 有自己的 isAdmin，沒有 add。這樣用會怎樣？

<MenuList :products="menu">
  <template #item="{ product }">
    {{ product.name }}
    <button v-if="isAdmin" @click="add(product.id)">加入</button>
  </template>
</MenuList>

✓ slot 內容在父元件的作用域編譯：看得到父元件自己的 isAdmin，加上這次解構出來的 slot props；add 子元件有傳，但父元件沒接，就不存在。a 錯在作用域看的是寫在哪裡，不是渲染在哪裡，跟 JavaScript 的詞法作用域一樣。（第 11 課）

練習 14：訂單列表 .list 有 overflow: hidden，寫在列表元件裡的確認框下半部被裁掉，同事把 z-index 調到 9999 也沒用。改成用 <Teleport to="body"> 包住確認框之後會怎樣？

✓ overflow 裁切、fixed 定位、z-index 堆疊都由 DOM 位置決定，Teleport 只把 DOM 搬到 body，元件關係不變：props、emit、響應式狀態都照常運作。z-index 只在同一個堆疊脈絡裡比較，祖先的層級低，調再大也沒用。b 錯在把 DOM 位置和元件樹混為一談；Teleport 也不是效能工具，沒被困住就不需要它。（第 11 課）

這個階段的重點整理成一頁圖解。
