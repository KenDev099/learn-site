階段 6：路由、權限與錯誤處理 · 第 21 課

錯誤處理與前端監控

咖啡店的點餐 App 改版後，客服陸續接到三種電話：「菜單區塊一片空白」「按結帳沒反應」「頁面一直自己重新整理」。工程師打開自己的電腦，每一個都重現不了。錯誤只發生在客人的瀏覽器裡，只印在客人的 console，沒有人看得到。

這三通電話是三個不同的問題，卻有同一個根源：錯誤發生了，畫面整塊壞掉，工程師卻要等客人打電話才知道，知道了也查不出是哪一行。這課從頭到尾處理這個事故，目標有兩個：第一，錯誤發生時，畫面要壞得有限度，只壞一個區塊，而且能重試；第二，每個錯誤都自動帶著足夠的脈絡回報給工程師，但不能把 token 和客人的手機號碼一起送出去。

這課的路線：
  1. 工程師為什麼看不到：錯誤在哪裡發生、哪些 Vue 攔得到、攔到之後交給誰，沒人處理時去了哪裡（第 1、2 節，開場問題的最小答案）。
  2. 「菜單一片空白」：用錯誤邊界讓菜單只壞那一塊，按「重試」重新建立（第 3 節）。
  3. 讓每個錯誤都送到工程師手上：Vue 攔不到的錯誤從哪裡接，回報帶什麼、不帶什麼，壓縮過的 stack 怎麼還原成原始碼的行號（第 4–6 節）。
  4. 「按結帳沒反應」「頁面一直自己重新整理」：部署新版後舊頁面載入不到結帳頁，怎麼修，又怎麼避免修成無限重新整理（第 7 節）。
  5. 客人在畫面上該看到什麼：說什麼、給什麼按鈕（第 8 節）。
這課會用到：
  • 第 8 課的生命週期：setup 先執行，元件放進 DOM 後執行 onMounted，卸載時執行 onUnmounted。
  • 第 11 課的 slot 與作用域 slot：父元件決定子元件某一塊顯示什麼，作用域 slot 還能從子元件拿到資料（例如 error、retry）。
  • TS 課第 4 課的 throw 與 Error：任何值都能被 throw，Error 帶著 message、stack，cause 保留原始錯誤。
  • TS 課第 9 課的 async 錯誤：async 函式丟錯會變成 rejected Promise，沒有人 await 或 catch 就成了 unhandled rejection。

工程師為什麼看不到？先弄清楚錯誤在哪裡發生

要讓工程師看得到錯誤，第一步是知道錯誤會在哪裡發生、誰有機會接住它。JavaScript 丟出錯誤時，會沿著呼叫堆疊一層一層往上找 try/catch：誰呼叫了你的函式，誰就有機會在外面包一層 try/catch 接住它。所以問題變成：你寫的程式碼，是誰呼叫的？

一個 Vue app 裡，程式碼在好幾種地方執行。setup、render、生命週期鉤子、watcher、範本上綁的事件處理函式，都是 Vue 在適當的時機呼叫的；計時器的 callback 是瀏覽器呼叫的；第三方套件的 callback 是那個套件呼叫的。前端的錯誤也就不只有「API 失敗」，每個地方都可能丟出錯誤，而 Vue 只接得住它自己呼叫的那些：

來源例子Vue 攔得到嗎
setup、render讀到 undefined.price攔得到
生命週期鉤子onMounted 裡初始化圖表失敗攔得到
watcherwatch 的 callback 丟錯攔得到
事件處理函式@click="pay"，包括 async 函式在 await 之後丟錯攔得到：Vue 會接住事件處理函式回傳的 Promise
計時器、第三方 callbacksetTimeout(() => { throw … })攔不到：不是 Vue 呼叫的，錯誤直接到 window 的 error 事件
沒有 catch 的 Promise在 setup 裡呼叫 api.track() 沒有 await 也沒有 catch攔不到：瀏覽器在 window 觸發 unhandledrejection
動態 import懶載入的結帳頁檔案下載失敗看在哪裡發生；Vite 另外會發出 vite:preloadError（第 7 節講）

「攔得到」的意思是：Vue 呼叫你的程式碼時，外面包了一層 try/catch，抓到的錯誤會交給 Vue 的錯誤處理流程，並附上一個說明錯誤發生在哪種地方的字串，叫做 info，例如 'setup function'、'mounted hook'、'native event handler'。這是開發版的寫法，正式版的 info 會縮成代碼，細節見課末。之後回報錯誤時，info 會跟著送出去，工程師一看就知道是 render 壞了還是按鈕的處理函式壞了。

async 事件處理是常被誤會的一點。很多人以為「async 的錯誤 Vue 一定攔不到」，理由是 async 函式丟錯時不會立刻丟出來，而是變成一個 rejected Promise。但想想是誰呼叫了 pay：@click="pay" 是 Vue 綁上去的，點擊時是 Vue 呼叫 pay()，所以 Vue 拿得到它回傳的 Promise，並在上面接 .catch。async function pay() { await …; throw new Error('付款失敗') } 在 await 之後丟出的錯誤，會以 'native event handler' 送進錯誤處理流程（實測版本見課末）。反過來，setTimeout 的 callback 是一秒後由瀏覽器呼叫的，那時 Vue 不在呼叫堆疊上，完全不知道它存在。

回到開場的客訴：「菜單一片空白」多半是菜單元件在 setup 或 render 讀到了不存在的資料，屬於 Vue 攔得到的那一類；「按結帳沒反應」跟懶載入的結帳頁有關，留到第 7 節。既然菜單的錯誤 Vue 攔得到，為什麼工程師還是看不到？要看 Vue 攔到之後把錯誤交給了誰。

Vue 攔到錯誤之後，交給誰？

Vue 攔到錯誤之後，不會直接印出來，而是先問出錯元件的祖先們要不要處理。從出錯的元件開始往上找，每一層祖先元件如果註冊了 onErrorCaptured，就依序被呼叫，由下往上，像 DOM 事件的冒泡；一路上都沒人攔下，最後交給 app.config.errorHandler。

onErrorCaptured 是元件用來攔截子孫元件錯誤的鉤子，收到三個參數：錯誤、出錯的元件實例、info。它的回傳值決定錯誤要不要繼續往上：回傳 false 代表「這個錯誤我處理好了」，錯誤就停在這一層，更上層的 onErrorCaptured 和 app.config.errorHandler 都不會收到；沒有回傳 false，錯誤會繼續往上傳。

app.config.errorHandler 則是整個 app 只有一個的函式，接收所有一路上沒被攔下的 Vue 錯誤，參數一樣是錯誤、元件實例、info。它是 Vue 錯誤的最後一站，所以最適合放「統一回報」這件事。

那如果一路上沒有人回傳 false，app 也沒有設定 errorHandler 呢？開發環境和正式環境的行為不同：

環境沒有處理的錯誤為什麼
開發丟出錯誤，可能讓 app 停擺讓你一定注意到
正式（預設）只用 console.error 印出盡量不影響使用者
正式，app.config.throwUnhandledErrorInProduction = true丟出錯誤讓監控服務的全域監聽收得到

這就是開場問題的答案。客人的菜單元件在正式環境出錯，Vue 攔到了，往上找沒人處理，最後只用 console.error 印在客人的 console。客人不會開 console，工程師看不到客人的 console，對工程師來說這個錯誤等於沒發生。在自己電腦上開發時錯誤會直接丟出來，所以「我這邊都正常」只代表你的資料剛好沒觸發它，不代表客人那邊沒事。表格第三列的設定細節見課末；不管用不用它，正式環境一定要有人把錯誤接住並送出去。

這條傳遞鏈剛好給了兩個接手的位置，也就是分層處理的做法：區塊用 onErrorCaptured 攔下自己子孫的錯誤，負責畫面，讓壞掉的那一塊換成替代畫面；app 用 errorHandler 接住剩下的錯誤，負責回報。兩者要注意「回傳 false」和「回報」的關係：區塊回傳 false 之後，errorHandler 就收不到這個錯誤，所以區塊自己要負責回報，不然這個錯誤就被默默吞掉了。

知道了錯誤會往上傳，下一步就能處理第一通客訴：在菜單外面放一個會攔錯的元件，讓菜單壞掉時只有菜單那一塊受影響。

菜單壞了，怎麼只壞菜單那一塊？

「菜單區塊一片空白」的問題不只是菜單壞了，而是菜單壞了之後，客人什麼提示都沒有，也沒有辦法自己恢復。我們要的效果是：菜單壞了，只有菜單那一塊變成「這個區塊暫時無法顯示」，旁邊放一個「重試」按鈕；購物車和結帳按鈕照常能用。

做到這件事的元件叫錯誤邊界（error boundary）：它包在某個區塊外面，攔截裡面子孫元件的錯誤，攔到之後不再顯示原本的內容，改顯示替代畫面。這個詞來自 React，Vue 沒有內建這個元件，但上一節的 onErrorCaptured 加上第 11 課的 slot 就能做出來：預設 slot 放正常內容，fallback slot 放替代畫面，用一個 error 狀態決定顯示哪一個。

<script setup lang="ts">
import { onErrorCaptured, shallowRef } from 'vue'

const props = defineProps<{ report: (error: unknown, info: string) => void }>()
const error = shallowRef<Error | null>(null)

onErrorCaptured((err, _instance, info) => {
  error.value = err instanceof Error ? err : new Error(String(err))
  props.report(err, info)  // 自己回報，因為下面回傳 false
  return false             // 不再往上傳
})
const retry = () => { error.value = null }
</script>

<template>
  <slot v-if="error" name="fallback" :error="error" :retry="retry">
    <p role="alert">這個區塊暫時無法顯示</p>
  </slot>
  <slot v-else />
</template>

首頁把菜單包起來，替代畫面由使用的地方決定，透過作用域 slot 拿到 error 和 retry：

<ErrorBoundary :report="report">
  <MenuSection />
  <template #fallback="{ error, retry }">
    <p>菜單載入失敗</p>
    <button @click="retry">重試</button>
  </template>
</ErrorBoundary>

流程是這樣：MenuSection 在 setup 或 render 丟出錯誤，Vue 往上找到 ErrorBoundary 的 onErrorCaptured；它把錯誤存進 error、呼叫 report 回報、回傳 false 讓錯誤停在這裡。error 有值之後，範本的 v-if 切到替代畫面。客人按「重試」，retry 把 error 清成 null，v-else 那一側重新渲染菜單。這個元件看起來只有十幾行，但有四個地方寫錯就不能用，下面一個一個看。

第一個是錯誤的型別。JavaScript 可以丟出任何值，throw '逾時' 也合法，所以 onErrorCaptured 收到的 err 型別是 unknown，不保證有 message。替代畫面可能要顯示 error.message，所以給畫面用之前先包成 Error（TS 課第 4 課）。回報時則送原本的值，不要送包過的那個，保留最多資訊給工程師。

第二個是重試要真的讓菜單重新建立。用 v-if／v-else 切換時，出錯的那一刻 v-else 那一側整個被卸載；清掉 error 時預設 slot 從頭渲染，裡面的 MenuSection 是新的實例，setup 會再跑一次，重新抓資料。如果你改用 v-show 把子樹藏起來（例如想保留捲動位置），舊的實例還在，清掉 error 只是把那個壞掉的實例重新露出來，重試等於沒做。這時要像第 7 課那樣改 key，強迫 Vue 丟掉舊的、建立新的。

第三個是替代畫面不能再渲染出錯的內容，Vue 文件特別提醒這點。替代畫面如果又包含出錯的子元件，或是讀了同一份壞掉的資料，錯誤會再發生、error 狀態再改、畫面再渲染，形成無限迴圈。替代畫面要盡量簡單，不要依賴出錯的資料。

第四個是時機。錯誤發生在第一次渲染當中時，error 被設定之後，替代畫面要等下一次更新才出現（第 6 課的排程器）。畫面上看不出差別，但寫測試時要先等一下再檢查，練習 1 會遇到。

最後是錯誤邊界要放在哪裡。太大，例如整個 app 包一個，菜單一壞整頁都換成替代畫面，跟沒包差不多；太小，例如每個按鈕包一個，程式碼雜亂。常見的切法是：每個路由頁面一個，加上頁面裡可以獨立失敗的區塊（菜單、推薦商品、評論、地圖）各一個。

錯誤邊界只能攔到 Vue 攔得到的錯誤。setTimeout 的 callback、沒有 catch 的 Promise 不會經過 onErrorCaptured，畫面也不會自動切到替代畫面。這類錯誤要靠下一節的全域監聽來回報。
💡 實務上：錯誤狀態是規格的一部分，不是工程師自己補的
設計稿常常只畫了「資料正常」的畫面。接到咖啡店首頁這種由好幾個區塊組成的頁面時，先跟 PM、設計確認：哪些區塊可以自己壞掉（推薦商品、評論），哪些壞了整頁就不能用（結帳金額），替代畫面要寫什麼、要不要重試按鈕。沒問清楚就上線，最常見的結果是推薦商品的 API 一掛，整個首頁跟著空白。Code review 時看到新的頁面或區塊，資深工程師會問兩件事：它壞掉時客人看到什麼？這個錯誤會不會被回報？

Vue 攔不到的錯誤，怎麼也送到工程師手上？

錯誤邊界處理了「菜單空白」的畫面，也替它攔下的錯誤呼叫了 report。但第 1 節的表格裡還有兩類錯誤不會經過任何 onErrorCaptured：計時器與第三方 callback 丟出的錯誤，和沒有 catch 的 Promise。它們不會讓某個區塊換成替代畫面，卻一樣會讓功能壞掉，例如輪詢訂單狀態的計時器壞了，畫面就停在舊狀態。要讓「所有錯誤都被看見」，就要在 Vue 之外也接住它們。

瀏覽器本身就有接這兩類錯誤的地方：沒人接住的錯誤，最後都會在 window 上觸發事件。加上 Vue 的最後一站，總共三個入口：

app.config.errorHandler = (err, instance, info) => send(err, info)       // Vue 攔到、沒被處理的
window.addEventListener('error', (e) => send(e.error, 'window error'))      // 計時器、第三方 callback
window.addEventListener('unhandledrejection', (e) => send(e.reason, 'unhandledrejection'))  // 沒有 catch 的 Promise

window 的 error 事件在同步丟出的錯誤一路都沒被 catch 時觸發，例如計時器的 callback 丟錯。錯誤物件在 event.error，不是 event 本身。

unhandledrejection 是 Promise 失敗而且沒有任何 .catch 或 try/await 接住時，瀏覽器在 window 上觸發的事件。失敗的原因在 event.reason，它跟 throw 一樣可以是任何值，不一定是 Error。在 setup 裡呼叫 api.track() 卻沒有 await 也沒有 catch，那個請求失敗時就會走到這裡。

三個入口都呼叫同一個 send，第二、三個入口沒有 Vue 給的 info，就自己填一個字串標出來源，工程師看到 'unhandledrejection' 就知道要去找哪個 Promise 漏了 catch。這三個入口加上錯誤邊界自己的 report，就涵蓋了第 1 節表格的每一列。

設定 errorHandler 有一個副作用：設定之後 Vue 就把錯誤交給你，不再自己印出來，連開發環境都一樣。開發時記得在 errorHandler 裡自己 console.error(err)，不然錯誤在開發環境也看不到了。

現在每個錯誤都會走到 send。但 send 到底要送什麼？只送一行 message，工程師收到「Cannot read properties of undefined」還是不知道從哪裡查起；把手邊的資料全部送出去，又可能把客人的個資一起送走。

回報要帶什麼，才查得出原因又不洩漏個資？

先說錯誤要送去哪裡。錯誤監控（error monitoring）是把正式環境的錯誤收集到一個服務，例如 Sentry，工程師在那裡看到每個錯誤發生幾次、影響多少人、從哪一版開始，用來發現問題和排查原因。不管用不用現成服務，一筆有用的錯誤回報都要回答四個問題：什麼錯、在哪一行、使用者在做什麼、是哪一版。對應到欄位：

欄位用途
message、stack什麼錯、從哪一行來
infoVue 給的錯誤來源，或 unhandledrejection、window error
route發生在哪一頁，重現時從這裡開始
release 版本每次部署的版本識別，例如 web@2026.10.31-1；知道錯誤從哪一版開始、修好的版本上線後有沒有消失
匿名的使用者 id算影響多少人、聯絡客服時對得上；不要用姓名、Email、手機

有了欄位清單，第一個坑出現在把它們送出去的時候。Error 物件不能直接 JSON.stringify：message、stack 不是可列舉的屬性，JSON.stringify 只序列化可列舉的屬性，所以出來是空物件，送到監控的是一筆什麼都沒有的回報。執行後比較前兩行的輸出：

所以回報時要自己把欄位一個一個取出來。

第二個坑是送了不該送的東西：token、密碼、手機號碼、身分證字號、完整的信用卡號。這些資料一旦送進監控服務，能看監控的人都看得到，還會被保存很久，等於一次資料外洩。最常見的漏洞是「把整個 store 或整個 request 當脈絡送出去」，想說資訊越多越好查，裡面剛好有 accessToken、客人的手機。做法是送出前依欄位名稱遮罩：名稱含 token、password、phone 的欄位，值換成 '[已遮罩]'，巢狀物件裡的也要處理。網址的 query 裡如果可能有 token（例如 Email 驗證連結），route 也要處理。

第三個坑是量。一個在 render 裡丟錯的元件，每次更新都會丟一次；一萬個客人同時遇到，就是幾十萬筆一樣的回報。監控服務的額度一下就用完，真正的新問題被淹沒在同一個錯誤裡。所以要去重：同一個錯誤一段時間內只送一次，用 message＋stack 當識別。量大時再加上抽樣：只送一定比例，例如 10%。去重處理「同一個客人重複送」，抽樣處理「很多客人都在送」。

練習 2 會把這節的三件事寫進同一個函式：三個入口、取出欄位並遮罩、去重。

💡 實務上：多半是接現成的監控服務，你的工作是設定好、有人看
公司裡通常直接用 Sentry 這類服務的 Vue SDK，它會幫你掛上 errorHandler 和 window 的監聽；自己寫回報模組多半是公司不能用外部服務、或只需要很簡單的收集。用現成服務時，這節的重點變成檢查設定：遮罩規則有沒有涵蓋你們的欄位名稱、有沒有帶 release 和匿名 id、抽樣比例跟方案額度合不合。最容易被忽略的是「沒人看」：監控接好了，卻沒有設定新錯誤的通知、也沒指定誰負責處理，跟沒接差不多。資深工程師會先跟團隊約定好：哪種錯誤要通知、通知到哪個頻道、誰在什麼時間內處理。

欄位都送了，菜單的錯誤也進了監控，打開來卻發現還有一個問題：正式環境的 stack 看不懂。

正式環境的 stack 只有 Ke、Xn，怎麼還原？

監控收到菜單的錯誤，stack 長這樣：

TypeError: Cannot read properties of undefined (reading 'price')
    at Ke (https://brew.example.tw/assets/index-3f9a.js:1:48213)
    at Xn (https://brew.example.tw/assets/index-3f9a.js:1:51022)

函式叫 Ke，位置是第 1 行第 48213 個字元，看不出是哪個元件。原因是正式環境的程式碼經過壓縮（minify）：建置時刪掉空白與註解、把變數和函式改成 a、Ke 這種短名稱、整個檔案擠成一行。這樣客人要下載的量小很多，代價就是 stack 裡的名字和行號都對不回你寫的原始碼。

解法是在壓縮的同時留一份對照表。source map 就是這份對照表：建置時另外產生的 .map 檔，JSON 格式，記錄「壓縮後第幾行第幾欄，對應到原始碼哪個檔案的第幾行第幾欄、原本叫什麼名字」，通常還附上完整的原始碼，放在 sourcesContent 欄位。監控服務有了它，同一個 stack 就能還原成：

TypeError: Cannot read properties of undefined (reading 'price')
    at itemPrice (src/components/MenuSection.vue:42:18)
    at setup (src/components/MenuSection.vue:17:9)

瀏覽器怎麼找到 .map？產生 source map 時，JS 檔最後會多一行註解 //# sourceMappingURL=index-3f9a.js.map，開著 DevTools 時瀏覽器照這行去下載。Vite 用 build.sourcemap 決定要不要產生、要不要加這行註解：設成 true 會產生 .map 並加上註解，適合內部測試環境，開 DevTools 直接看原始碼；設成 'hidden' 會產生 .map 但不加註解，這是正式環境要用的。四種值的完整對照見課末。

為什麼正式環境不用 true、直接公開 .map？因為 sourcesContent 就是你的完整原始碼：註解、還沒上線的功能、內部 API 路徑，任何人打開 DevTools 都能逐檔閱讀。但 'hidden' 也只是不告訴瀏覽器 map 在哪裡；.map 檔如果跟著部署出去，網址就是「JS 檔名＋.map」，一猜就中。所以 map 只能給監控服務，不能留在網站上。正式環境的流程是：

  1. 建置：設定 build: { sourcemap: 'hidden' }，並用環境變數帶入這次的 release，例如 VITE_RELEASE=web@2026.10.31-1 vite build。VITE_ 開頭的環境變數會變成程式裡的 import.meta.env.VITE_RELEASE，回報錯誤時帶上它。
  2. 上傳：用監控服務提供的 CLI 或 Vite 外掛，把 dist 裡的 .map 上傳，標上同一個 release。
  3. 刪除：上傳完把 dist 裡的 .map 刪掉，再部署。

這個流程裡最容易出錯的是 release 對不上。監控服務收到一筆錯誤，是用錯誤上的 release 去找那一版上傳的 map。回報沒帶 release，或建置時和上傳時用了不同的字串（例如一邊是 commit hash、一邊是日期），就找不到 map，stack 還是 Ke、Xn。做法是 release 只在 CI 決定一次。CI（持續整合）是每次推上程式碼就自動建置、測試、部署的流程，release 在這個流程開頭決定（例如日期＋commit），建置、上傳、回報都從同一個變數讀，不要各自產生。另一個前提是上傳的 map 必須來自部署出去的同一次建置：重新建置一次產生的 map 對不上。有些服務用另一種配對方式，原則相同，見課末。

stack 還原之後，菜單空白的原因查得到了。這時監控裡還有另一群錯誤特別顯眼：每次中午部署之後，就冒出一批 Failed to fetch dynamically imported module，時間點剛好對上第二通客訴「按結帳沒反應」。

按結帳沒反應：部署後為什麼載入不到結帳頁？

要看懂這個錯誤，先要知道結帳頁是怎麼被下載的。打包工具會把程式切成好幾個 JS 檔，每個叫一個 chunk，客人不需要的部分可以晚一點才下載。第 19 課的懶載入路由 () => import('./CheckoutPage.vue')，結帳頁就是一個獨立的 chunk，客人按「結帳」時才下載。

chunk 的檔名會帶著一段雜湊值（hash）。hash 是由檔案內容算出來的一小段字串，內容改一個字，hash 就不同，例如 Checkout-3f9a.js。這樣做是為了快取：內容一變檔名就變，所以同一個檔名的內容永遠一樣，瀏覽器可以放心存很久，不用每次都問伺服器。代價是舊頁面記得的是舊檔名：

  1. 客人上午打開點餐頁，瀏覽器載入的 HTML 和主程式記得「結帳頁是 Checkout-3f9a.js」。
  2. 中午部署新版，結帳頁變成 Checkout-81bc.js，舊檔被主機刪掉。
  3. 客人下午按「結帳」，瀏覽器去下載 Checkout-3f9a.js，得到 404，動態 import 失敗，畫面沒反應。

客人沒有重新整理，所以手上一直是上午的那份程式。這也是工程師重現不了的原因：工程師每次都打開最新版，舊檔名根本不會出現。錯誤訊息依瀏覽器不同：Chrome 是 Failed to fetch dynamically imported module，Firefox 是 error loading dynamically imported module，Safari 是 Importing a module script failed.。監控裡這幾種錯誤集中出現在部署之後，就是這個問題。

處理分成四層，越前面越根本：先讓客人每次打開網站都拿到最新的 HTML，再讓舊檔在部署後還下載得到，然後在真的失敗時自動補救，最後對開很久的頁面主動提醒。

第一層：客人打開網站時，怎麼一定拿到新版 HTML？

客人拿到哪一版程式，取決於瀏覽器用的是哪一份 index.html，因為 chunk 清單寫在它載入的主程式裡。而瀏覽器要不要重新下載 index.html，由快取標頭決定。正式環境的網站前面常有一層 CDN：分散在各地、替你的網站快取並回應檔案的伺服器網路，客人連到離他最近的節點，所以 CDN 自己也會保存一份 index.html。Cache-Control 是伺服器（或 CDN）回應時帶的標頭，告訴瀏覽器這個回應能快取多久、用之前要不要先問。SPA 的兩類檔案要設得不一樣：

檔案Cache-Control原因
index.htmlno-cache不是「不快取」，而是「每次用之前先問伺服器有沒有變」；沒變時伺服器回 304、不重傳內容。部署後下一次載入就拿到新的 chunk 清單
/assets/*-[hash].js、.csspublic, max-age=31536000, immutable同一個網址的內容永遠不變，快取一年；immutable 告訴瀏覽器連重新整理時都不必再問
index.html 的網址不會變，所以它不能長期快取。設成 max-age 一年的話，部署後客人再打開網站，瀏覽器直接用快取裡的舊 HTML、不問伺服器，載入的是舊 chunk 清單。重新整理時瀏覽器通常會向伺服器確認主頁面，但前面有 CDN 時，CDN 自己也快取了這份 HTML，確認到的還是舊的，後面「失敗就重新整理」的修正就完全失效。所以 CDN 上的 HTML 也要設 no-cache，部署後並清掉 CDN 上 index.html 的快取。

這一層讓「重新打開」或「重新整理」一定拿到新版。但上午打開、一直沒關的分頁不會重新下載 HTML，它還是會去要舊檔名。

第二層：舊頁面要的舊檔，部署後還在嗎？

舊分頁要的是舊檔名，那就讓舊檔繼續存在。部署時只新增、不刪除：新版的 assets 上傳上去，舊版的留著，開著舊頁面的客人照樣下載得到。上傳順序也有關係：先傳 assets，最後才換 index.html；反過來的話，會有幾秒新 HTML 指向還沒上傳的檔案。以 S3 為例：

aws s3 sync dist/assets s3://brew-web/assets --cache-control "public,max-age=31536000,immutable"   # 不加 --delete，舊檔留著
aws s3 cp dist/index.html s3://brew-web/index.html --cache-control no-cache                          # 最後才換 HTML

舊檔總要清，清的時候以「最近幾版都沒用到」為準，不要只看檔案的建立時間：內容沒變的 chunk 檔名也沒變，可能幾個月前就上傳了，現在還在用。保留期間外還開著的分頁（例如放了一週沒關的點餐機）還是會遇到 404，所以下一層仍然需要。

第三層：真的失敗了，怎麼自動補救又不會一直重新整理？

失敗時最直接的補救是重新整理：重新整理會拿到新版 HTML（第一層保證的），新 HTML 指向新檔名，結帳頁就下載得到了。Vite 在動態 import 失敗時會在 window 上發出 vite:preloadError 事件，event.payload 是原本的錯誤。呼叫 event.preventDefault() 之後，這個錯誤就不會再丟出來，那個 import 會得到 undefined，所以 preventDefault 一定要搭配重新整理。Vite 文件的建議就是在這個事件裡重新整理頁面，拿到新版的 HTML，這也是第一層 HTML 要 no-cache 的原因。

改版時同事照 Vite 文件，在 vite:preloadError 裡寫了一行 location.reload()，結帳頁的問題看似修好了，第三通客訴「頁面一直自己重新整理」卻正是它造成的：只寫 location.reload()，如果重新整理之後還是失敗（CDN 還沒更新完、或是檔案真的壞了），頁面一載入就失敗、失敗就重新整理，變成無限重新整理，客人的手機發燙、伺服器收到大量請求。解法是記下「上次因為這個原因重新整理的時間」，短時間內又發生就不再重新整理，改讓錯誤正常丟出，由錯誤畫面告訴客人「請稍後重新整理」。

這個時間要記在哪裡？重新整理之後，所有 JS 變數都從頭開始，模組裡的 let lastReload 永遠是初始值，等於什麼都沒記。要用重新整理後還在的地方：sessionStorage，它在同一個分頁內保留，關掉分頁就清掉，正好符合需求。sessionStorage 在某些瀏覽器設定下讀寫會丟錯，這時記不住時間，安全的做法是不重新整理：寧可讓客人看到錯誤畫面，也不要冒無限重新整理的風險。練習 3 會寫這個函式，接上去的方式是：

window.addEventListener('vite:preloadError', (event) => {
  handlePreloadError(event, { storage: sessionStorage, reload: () => location.reload(), now: Date.now })
})

location.reload() 重新整理的是目前這一頁：客人在菜單頁按「結帳」失敗，重新整理後還在菜單頁，要再按一次。一般從這個做法開始；客人抱怨「按了沒反應要再按一次」時，可以改由 Vue Router 的 router.onError 負責，重新整理後直接進到結帳頁。兩者只能選一個負責重新整理，原因和寫法見課末。

第四層：開很久的頁面，能不能在出錯前就知道有新版？

前三層都是失敗之後才補救。對會開很久的頁面（點餐機、後台），可以主動檢查：部署時多輸出一個 version.json（內容是 release，同樣設 no-cache），app 每隔幾分鐘、或分頁回到前景時（visibilitychange 事件）抓一次，跟自己建置時的 release 比對：

const res = await fetch('/version.json', { cache: 'no-store' })  // 不用瀏覽器快取
const { release } = await res.json()
if (release !== import.meta.env.VITE_RELEASE) showUpdateBanner()  // 「有新版本，點這裡重新整理」

這裡比對的 release，就是第 6 節建置時帶入的同一個變數。只顯示提示，讓客人自己按，不要自動重新整理：客人可能正在填地址或付款。代價是多一個定時請求，只開幾分鐘的頁面不需要這一層。

💡 實務上：部署是前端和維運一起的事，上線後先盯監控
快取標頭、CDN 清快取、S3 要不要刪舊檔，很多公司是由維運或後端在管，前端工程師常常改不到、也不知道現在怎麼設。第一次負責 SPA 部署時，先找管部署的人對齊前兩層的設定：HTML 是不是 no-cache、舊 assets 留多久、部署時上傳的順序。部署完的頭一段時間打開監控，照 release 篩選，看有沒有新出現的錯誤、chunk 載入失敗有沒有暴增；有問題就決定要修還是回滾到上一版。這也是 release 一定要帶的另一個原因：沒有它，你分不出錯誤是新版造成的還是本來就有。

到這裡，三通客訴背後的錯誤都會被回報、查得出原因，也各自有了修法。剩下最後一件事：錯誤發生的那一刻，客人在畫面上看到什麼。

客人在畫面上該看到什麼？

監控是給工程師看的，畫面上的錯誤是給客人看的，兩者的內容不一樣。三通客訴的起點都是客人看到的畫面：一片空白、按了沒反應、一直閃，客人不知道發生什麼事，只好打電話。好的錯誤畫面要讓客人知道哪裡壞了、自己能做什麼。依影響範圍選呈現方式：

方式適合例子
行內訊息跟某個欄位或區塊有關「優惠碼已過期」顯示在輸入框下面
toast（幾秒後消失的小提示）背景動作失敗、不影響目前畫面「收藏失敗，請再試一次」
區塊替代畫面一個區塊壞了錯誤邊界的「菜單暫時無法顯示」＋重試
整頁錯誤這一頁完全無法使用「找不到這筆訂單」＋回到首頁

不管用哪一種，原則都一樣：說人話、告訴客人能做什麼（重試、稍後再來、聯絡客服）、能重試的給按鈕。不要把 TypeError: Cannot read properties of undefined 或伺服器回的 SQL 錯誤直接顯示出來：客人看不懂，而且等於把系統內部的結構告訴攻擊者。原始的錯誤內容已經送進監控了，畫面上不需要再出現。

畫面和監控之間可以用一個錯誤代碼或時間串起來：錯誤畫面附上它，客人聯絡客服時報出來，客服就能在監控裡找到同一筆，不用再請客人描述「我按了什麼」。訊息內容則依錯誤種類決定：第 16 課把錯誤分成網路、逾時、4xx、5xx，就是為了在這裡選對訊息，網路錯誤說「請檢查網路」，5xx 說「系統忙碌中」，403 說「沒有權限」。

回到開場的三通電話：菜單壞了，現在只壞菜單那一塊，有重試按鈕，錯誤自動回報；按結帳沒反應，現在舊檔還在、失敗時重新整理一次；一直自己重新整理，現在有 sessionStorage 擋住，重整一次還失敗就停下來顯示錯誤畫面。三種情況工程師都會在監控裡看到，帶著還原過的 stack 和 release。

補充與查表

主線提到「細節見課末」的地方都在這裡，查表用，不用背。

  • 正式版的 info：開發版的 info 是 'setup function' 這類字串，正式版會縮成代碼，對照表在 Vue 文件的 Production Error Code Reference。
  • async 事件處理的實測：「async 事件處理函式在 await 之後丟出的錯誤，會以 'native event handler' 送進錯誤處理流程」是在 Vue 3.5.44 實際測過的結果。
  • onErrorCaptured 自己出錯：如果 onErrorCaptured 本身又丟出錯誤，新錯誤和原本的錯誤都會送到 errorHandler。
  • throwUnhandledErrorInProduction：Vue 3.5 加入的設定，預設 false。正式環境預設只印在 console，客人的 console 你看不到，等於沒發生；設成 true 讓沒處理的錯誤照樣丟出，監控服務的全域監聽才收得到。不管開不開，正式環境都要有 errorHandler 或監控服務接住錯誤。
  • "Script error."：window 的 error 事件裡，如果出錯的是載入自其他網域的 script，瀏覽器為了安全只給你 "Script error."，沒有 stack。
  • 後端的錯誤：後端的集中 log 與錯誤追蹤在 DevOps 課第 21 課。
  • debug ID：有些監控服務改用建置時寫進 JS 和 map 裡的識別碼（debug ID）配對，不靠 release 字串，但原則一樣：上傳的 map 必須來自部署出去的同一次建置，重新建置一次產生的 map 對不上。

Vite 的 build.sourcemap（Vite 8.3.5）有四種值：

值結果用途
false（預設）不產生不需要還原 stack 時
true產生 .map，JS 檔加上 sourceMappingURL 註解內部測試環境，開 DevTools 直接看原始碼
'inline'map 以 data URI 塞在 JS 檔最後只適合開發；正式環境的 JS 會大好幾倍
'hidden'產生 .map，但不加註解正式環境：map 只給監控服務

改由 router.onError 重新整理：懶載入路由失敗時，Vue Router（5.4.0）會呼叫 router.onError 註冊的函式，參數是 (error, to, from)，to 就是客人要去的頁面，可以直接整頁載入那一頁：

router.onError((error, to) => {
  if (isChunkLoadError(error) && canReloadNow()) window.location.assign(to.fullPath)  // 部署在子路徑時改用 router.resolve(to).href
})

isChunkLoadError 用第 7 節的三種瀏覽器訊息判斷，canReloadNow 是同一套 sessionStorage 防迴圈檢查。路由的 chunk 失敗時，兩個機制都會收到，而且 vite:preloadError 先觸發。它 preventDefault 之後，那個 import 得到 undefined，Vue Router 收到的就不是 chunk 錯誤，而是它自己丟的 Couldn't resolve component "default" at "/checkout"，isChunkLoadError 不會成立。所以只選一個負責重新整理：

  • 只用 vite:preloadError：最簡單，路由、defineAsyncComponent 等所有動態 import 都涵蓋；代價是重新整理後停在原本那頁。
  • 只用 router.onError：重新整理後直接進到目標頁；但它只管路由，其他動態 import 失敗時要另外處理（例如交給錯誤邊界顯示重試）。

一般從第一種開始，客人抱怨「按了沒反應要再按一次」時再換第二種。

練習

在 learn/ 執行 node check.mjs vue 21。練習 1 用 VTU 掛載你的錯誤邊界，子元件由測試定義、可以控制要不要丟錯，並用 global.config.errorHandler 的假函式確認錯誤沒有再往上傳。練習 2 用 createApp 建立真的 app，window 換成測試傳入的 EventTarget，時間由 now() 決定。練習 3 用 vi.resetModules() 重新 import 你的模組來模擬重新整理：模組變數會清空，傳入的 storage 不會。

練習 1：完成 ErrorBoundary.vue：用 onErrorCaptured 攔截子孫元件的錯誤，改顯示 #fallback slot（slot props 有 error 和 retry；丟出的不是 Error 時包成 Error），沒傳 #fallback 時顯示 role="alert" 的「這個區塊暫時無法顯示」和「重試」按鈕；每個錯誤呼叫 report(原本的錯誤, info) 一次並回傳 false；retry() 之後子元件要重新 setup。測試也會用 async 點擊處理丟出的錯誤檢查。

練習 2：完成 installErrorReporting(app, options)：設定 app.config.errorHandler，並在 options.target 監聽 unhandledrejection 與 error；每筆回報包含 message、stack、info、route、release、context（route 與 context 在回報當下才取）；context 裡名稱含 token、password、phone 的欄位（不分大小寫，巢狀物件、陣列裡的物件也算）改成 '[已遮罩]'；同一個 message＋stack 60 秒內只回報一次；回傳的函式移除監聽。檔案開頭的註解有完整規格。

練習 3：把「失敗就 reload」的 handlePreloadError(event, { storage, reload, now }) 改成只重新整理一次：第一次發生時 preventDefault()、把時間存進 storage、reload()；距離上次重新整理不到 10 秒又發生，就不 preventDefault、不 reload；storage 讀寫丟錯時也不 reload。

練習 4：元件的 setup 裡寫了 setTimeout(() => { throw new Error('計時器出錯') }, 1000)。app 設定了 app.config.errorHandler，它收得到這個錯誤嗎？

✓ Vue 只能攔下「由 Vue 呼叫」的程式碼丟出的錯誤：setup、render、生命週期、watcher、事件處理函式。setup 只是「排定」了計時器，一秒後執行 callback 的是瀏覽器，那時 Vue 不在呼叫堆疊上，沒有機會 try/catch，所以 a、c 都不對。要收到這類錯誤，得在 window 監聽 error 事件。

練習 5：<button @click="pay"> 的 pay 是 async 函式，在 await api.pay() 之後丟出錯誤。app.config.errorHandler 收得到嗎？

✓ 事件處理函式是 Vue 呼叫的，Vue 拿到它回傳的 Promise 後會接上錯誤處理，所以 await 之後丟出的錯誤也會走 onErrorCaptured → errorHandler。a 的直覺來自「async 錯誤很難抓」，但這裡 Vue 幫你接住了；當然，需要在畫面上顯示具體訊息（例如「付款失敗，請再試一次」）時，你還是要自己 try/catch。b 是 Promise 沒人接時才會發生，這裡 Vue 接了。

練習 6：錯誤邊界的 onErrorCaptured 回傳 false，代表什麼？

✓ Vue 文件的說法是「這個錯誤已經處理好，應該忽略」，它會阻止之後所有的 errorCaptured 和 app.config.errorHandler。b 把 false 當成「失敗」，意思正好相反。c 是常見的誤會：回傳 false 之後 errorHandler 收不到，所以錯誤邊界要自己回報，不然錯誤就被吞掉了。

練習 7：同事提議「assets 都快取一年了，index.html 也設 Cache-Control: max-age=31536000，首頁會更快」。照做之後會怎樣？

✓ 會換檔名的是帶 hash 的 assets，index.html 的網址永遠是 /，Vite 也不會替它加版本號，所以 a、b 都不對。快取一年，客人這一年內打開網站，瀏覽器都不問伺服器、直接用舊 HTML 載入舊 chunk；舊 chunk 刪掉後畫面就壞了。前面有 CDN 時，CDN 也照這個標頭快取，連重新整理確認到的都是舊 HTML。index.html 要用 no-cache：每次先問，沒變時回 304，成本很低。

練習 8：團隊設了 build.sourcemap: 'hidden'，然後把整個 dist（含 .map）部署到網站，理由是「hidden 的 map 瀏覽器找不到，很安全」。哪個說法正確？

✓ 'hidden' 只拿掉「map 在哪裡」的註解，不會讓檔案消失；部署出去就能被下載，sourcesContent 裡是完整原始碼，所以 b 不對。c 更糟：inline 的 map 直接塞在每個客人都會下載的 JS 裡，原始碼一定公開，檔案還大好幾倍。正確流程是 hidden 產生 → 上傳並標上 release → 刪掉 .map → 部署。

常見錯誤

  • 以為 Vue 攔得到所有錯誤：計時器 callback 和沒有 catch 的 Promise 不會經過 errorHandler。window 的 error 和 unhandledrejection 都要監聽。
  • 默默吞掉錯誤：catch {} 什麼都不做、或錯誤邊界回傳 false 卻沒回報，畫面沒提示、監控沒紀錄。每個 catch 都要決定：顯示給使用者、回報、或往上丟。
  • 錯誤邊界的替代畫面又渲染出錯的元件：錯誤一再發生，形成無限迴圈。替代畫面要簡單、不依賴出錯的資料。
  • 重試沒有重建子元件：用 v-show 保留了壞掉的實例，清掉錯誤之後還是壞的。用 v-if 切換，或改 key 重建。
  • 回報資料裡有 token 或個資：把整個 store、request 當脈絡送出。依欄位名稱遮罩，只送需要的欄位，使用者只用匿名 id。
  • 沒有去重：render 裡的錯誤每次更新都丟一次，監控額度用完、新問題被淹沒。同一個錯誤一段時間內只送一次，量大時抽樣。
  • source map 公開在網站上：以為 'hidden' 就安全，把 .map 一起部署。上傳給監控服務後從 dist 刪掉。
  • 建置、上傳 map、回報用了不同的 release：監控找不到對應的 map，stack 還是壓縮後的名字。release 在 CI 決定一次，三處共用。
  • index.html 長期快取：部署後客人一直拿到舊 HTML 和舊 chunk 清單。HTML 用 no-cache，只有帶 hash 的檔案長期快取。
  • 部署時刪掉舊 assets：開著舊頁面的客人立刻 404。只新增不刪除，舊檔保留一段時間；先傳 assets，最後換 HTML。
  • chunk 載入失敗時無限重新整理：只寫 location.reload()。把時間記在 sessionStorage，短時間內再發生就停下來顯示錯誤；HTML 設 Cache-Control: no-cache。
  • 把內部錯誤訊息直接給使用者看：看不懂，還洩漏系統結構。顯示人話和能做的下一步，細節送監控。

小結

  • 工程師看不到錯誤，是因為正式環境沒處理的 Vue 錯誤只印在客人的 console。所以一定要集中回報。
  • Vue 攔得到它呼叫的程式碼丟出的錯誤（setup、render、生命週期、watcher、事件處理含 async）；計時器與沒有 catch 的 Promise 要靠 window 的 error 與 unhandledrejection。
  • 錯誤由下往上經過每一層的 onErrorCaptured，最後到 app.config.errorHandler；回傳 false 停止傳遞，這時要自己回報。
  • 錯誤邊界：替代畫面＋重試，用 v-if 切換讓子元件重建，替代畫面不能再渲染出錯的內容。
  • 回報 message、stack、info、route、release、匿名 id；遮罩 token、密碼、手機；去重、抽樣。
  • source map 用 build.sourcemap: 'hidden' 產生，上傳給監控服務並標上同一個 release，然後從 dist 刪掉，不公開。
  • 部署後舊 chunk 不見：index.html no-cache、帶 hash 的檔案長期快取；舊檔保留一段時間；vite:preloadError 或 router.onError（擇一）重新整理一次，用 sessionStorage 防迴圈；開很久的頁面再加版本檢查提示「有新版本」。
  • 給使用者的錯誤說人話、給下一步、能重試就給按鈕，不洩漏內部細節；附上錯誤代碼或時間，讓客服在監控裡找得到同一筆。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：訂單後台部署到 Nginx 後，從首頁點進 /orders/7 一切正常，在那一頁按重新整理卻出現 Nginx 的 404 頁面。先查什麼？

✓ 站內點連結是 pushState，不發請求；重新整理時瀏覽器真的向伺服器要 /orders/7，伺服器沒有這個檔案就回 404。Vue Router 沒有設定錯，要讓伺服器把找不到的路徑回傳 index.html（Nginx 用 try_files），前端路由表再自己接住找不到的頁面。b 錯在這個請求根本還沒到 Vue Router，路由表寫得再對也沒機會執行。（第 19 課）

練習 10：菜單頁進入時把 route.query.category 讀進一個 ref，之後切換分類時改 ref 並 router.replace 網址。客人在 /menu?category=coffee 點了頁首的「看茶飲」（連到 /menu?category=tea），網址變了，畫面還是咖啡。原因是？

✓ 網址和 ref 是兩份狀態，網址從外面被改（點連結、按上一頁）時 ref 不知道，遲早不一致。讓網址當唯一的來源：用可寫的 computed，讀從 route.query 驗證後取，寫用 router.replace 並保留其他鍵。b 錯在 replace 只影響歷史紀錄的筆數，網址照樣更新，route.query 也跟著變。（第 19 課）

練習 11：吧台看板不該讓店員看到顧客的手機號碼。同事在範本用 v-if="can(user, 'customer:contact')" 把手機欄位藏起來，訂單 API 照樣回傳 phone。這樣夠嗎？

✓ v-if 拿掉的只是元素，資料已經送到瀏覽器，店員打開 Network 分頁或 Vue DevTools 就看得到。不該看的欄位要伺服器依權限不回傳。前端的權限檢查只負責體驗，防線在 API 和資料庫。c 錯在 v-show 反而會渲染元素、只是用 CSS 藏起來，而且問題本來就不在 DOM。（第 20 課）

練習 12：「標成可取餐」的權限函式這樣寫，角色只有 customer、barista、manager 三種。哪裡會出事？

function canReady(user: User, order: Order) {
  if (user.role === 'customer') return false
  return user.storeId === order.storeId
}

✓ 這是預設允許：任何不是 customer 的角色都走到最後一行，undefined === undefined 又是 true。改成預設拒絕：只對認得的角色回 true，先確認 typeof user.storeId === 'number' 再比較。c 錯在 'Barista' 不是合法角色，代表資料有問題，該拒絕而不是猜。（第 20 課）

練習 13：全域守衛這樣載入登入狀態。重新整理後客人很快連點兩個連結，Network 出現兩次 /me。為什麼？

let loaded = false
router.beforeEach(async (to) => {
  if (!loaded) { await auth.loadMe(); loaded = true }
  if (to.meta.requiresAuth && !auth.user) return { name: 'login', query: { redirect: to.fullPath } }
})

✓ 布林值只記得「做完了沒」，擋不住同時進行的導航。改成存那個 Promise：ready ??= auth.loadMe(); await ready，第二次導航 await 的是同一個還在進行的請求。a 錯在守衛回傳 Promise 時 Vue Router 會等它完成才決定結果，這也是守衛能 await 的原因。（第 20 課）

練習 14：登入頁用這個函式處理 ?redirect=，通過就 router.push。哪裡會出事？

function safeRedirect(raw: unknown): string {
  return typeof raw === 'string' && raw.startsWith('/') ? raw : '/'
}

✓ //evil.example 是協定相對網址，/\evil.example、夾了 tab 的 /\t/evil.example 也會被解析成同樣的外部網址，這就是開放式重新導向。字串規則再擋掉 //、反斜線、控制字元，最後用 new URL(target, 基準網址) 確認 origin 沒變。c 錯在前面的 typeof raw === 'string' 已經把陣列擋下，會回 '/'。（第 20 課）

練習 15：首頁的推薦區塊包在錯誤邊界裡，app.config.errorHandler 負責送監控。客服說推薦區塊常常顯示「暫時無法顯示」，監控卻一筆紀錄都沒有。最可能的原因是？

onErrorCaptured((err) => {
  error.value = err instanceof Error ? err : new Error(String(err))
  return false
})

✓ 回傳 false 代表「已處理」，上層的 onErrorCaptured 和 errorHandler 都不會收到，錯誤被默默吞掉。邊界在回傳 false 之前要自己呼叫回報函式。b 錯在替代畫面出現了，代表 onErrorCaptured 確實收到這個錯誤，Vue 有攔到。（第 21 課）

練習 16：中午部署新版後，監控出現大量 Failed to fetch dynamically imported module，幾乎都來自上午就打開、一直沒關的分頁。最先懷疑什麼？

✓ 錯誤集中在部署後、來自舊分頁，就是舊頁面記得的舊 chunk 檔名不見了。對策：部署只新增不刪除、先傳 assets 最後換 HTML、index.html 用 no-cache，失敗時用 sessionStorage 防迴圈重新整理一次。c 錯在帶 hash 的檔名內容永遠不變，長期快取加 immutable 本來就是正確設定。（第 21 課）
