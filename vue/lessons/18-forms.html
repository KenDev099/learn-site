階段 5：狀態與資料 · 第 18 課

複雜表單：驗證、錯誤顯示與送出

咖啡店的外帶訂單表單上線第一週，客服收到三種抱怨：顧客才打了手機的「09」，下面就跳出紅字「手機格式錯誤」；網路慢的時候顧客多按了一次「送出」，廚房收到兩張一模一樣的訂單；伺服器回「這個時段已額滿」，畫面上只寫「送出失敗」，顧客不知道要改哪一格。這三件事都不是驗證規則寫錯，而是表單的狀態、時機和送出流程沒有設計好。

這課只用這一張外帶訂單表單，從頭修到尾。表單有這些欄位：姓名、手機、取餐時間、明細（品項與數量，可以增減）、優惠碼、備註。先釐清表單除了值還要記什麼，修好第一個抱怨；接著把每一格的檢查做對；最後處理送出，讓多按一次不會變成兩張訂單、伺服器的拒絕能回到正確的格子，而且每位顧客，包括用螢幕報讀器的顧客，都知道哪裡要改。

這課的路線：
  1. 表單要記哪些狀態：顧客才打「09」為什麼不該馬上跳紅字，錯誤什麼時候才顯示（開場第一個抱怨的答案）。
  2. 錯誤從哪裡算出來、優惠碼要問伺服器：規則怎麼寫成不用掛元件就能測的函式；要問伺服器的檢查，怎麼少打幾次 API、丟掉過期的結果。
  3. 明細可以增減：刪掉一列明細，為什麼另一列的備註會跑掉。
  4. 送出：多按一次「送出」怎麼不會變成兩張訂單（第二個抱怨）；伺服器回「這個時段已額滿」怎麼顯示在那一格旁邊，以及為什麼伺服器每一條規則都要再驗一次（第三個抱怨）。
  5. 可近用性：看不到紅字的顧客，怎麼知道哪一格錯了。
這課會用到：
  • 第 10 課的 v-model 與 defineModel：model 是物件或陣列時，子元件指定一個新的值，不直接改它的內容。
  • 第 5 課的競態與 onWatcherCleanup：先送出的請求比較晚回來會蓋掉新結果；onWatcherCleanup 在 watcher 下一次執行前清掉上一次的工作。
  • 第 16 課的 ValidationError 與冪等鍵：API 層把 422 轉成帶 fieldErrors 的錯誤；冪等鍵讓伺服器認得「同一筆請求又送了一次」。
  • 第 17 課的 AbortController：每次請求建立一個 AbortController，把它的 signal 交給 fetch；controller.abort() 取消請求，controller.signal.aborted 判斷是否已取消。

顧客才打「09」就跳紅字：表單除了值，還要記什麼？

先看第一個抱怨是怎麼來的。範本裡手機欄位的寫法是「errors.phone 有值就顯示」。顧客打下第一個字「0」，值是 '0'，當然不是合法的手機號碼，紅字立刻出現；打到「09」還是不合法，紅字繼續掛著。驗證規則本身沒錯，「09」確實不是手機號碼。錯的是畫面分不出兩種情況：「還沒打完」和「打完了但打錯」。

畫面分不出來，是因為表單只記了每一格的值。光看值，「09」在兩種情況下長得一模一樣。要分辨，就得另外記下使用者做過什麼：他有沒有離開過這一格、有沒有按過送出。同樣的道理，開場第二個抱怨也需要值以外的資訊：要擋住第二次送出，得知道「現在正在送出中」。第三個抱怨需要的「伺服器回來的錯誤」也是另外存的狀態，送出那一節再處理。另外，後台常見的「有未儲存的修改」提醒，要知道值跟一開始比有沒有變。整理起來，一張表單要記的狀態是這幾樣：

狀態意思用來做什麼
values每個欄位目前的值送出的資料
touched（碰過）使用者曾經離開（blur）過的欄位決定錯誤訊息什麼時候出現
dirty（改過）目前的值和初始值不同「放棄修改？」的提醒、只送出有改的欄位
errors每個欄位的錯誤訊息，由 values 算出來顯示訊息、擋住送出
submitting送出中按鈕顯示「送出中…」、擋住重複送出

表裡的 blur 是輸入框失去焦點的那一刻：使用者按 Tab 跳到下一格、或用滑鼠點了別的地方，原本那一格就觸發 blur 事件。「離開過」就是用這個事件記下來的。

這五樣東西在程式裡分成兩類。errors 完全由 values 決定：同樣的值，錯誤一定一樣，所以用 computed。如果把錯誤也存成 ref，就得在每一個改值的地方記得重算一次，漏掉一處，畫面就會掛著上一個值的錯誤。touched、submitting 則是使用者操作留下的事實，從值推不出來（同一個值，使用者可能碰過也可能沒碰過），只能用 ref 或 reactive 存。dirty 介於兩者之間：只要把初始值存起來，就能拿目前的值跟它比出來，也可以用 computed。

錯誤什麼時候顯示

有了 touched，第一個抱怨就能修了。常見的規則是：打字時不罵人，離開欄位或按過送出之後才顯示。打字時值本來就還沒完成，這時候的錯誤沒有意義；離開欄位代表使用者認為自己填好了，這時候才值得告訴他哪裡不對。按「送出」等於使用者宣告整張表都填好了，所以要把所有欄位的錯誤一次顯示出來，連他沒碰過的欄位也算。

寫成程式，就是在顯示前多一個判斷。touched 記哪些欄位離開過，submitted 記有沒有按過送出，兩者有一個成立才把 errors 裡的第一則訊息拿出來：

const touched = reactive<Partial<Record<Field, boolean>>>({})
const submitted = ref(false)          // 按過送出
const errors = computed(() => validatePickup(values))

function shownError(field: Field) {
  return touched[field] || submitted.value ? errors.value[field]?.[0] : undefined
}
<input v-model="values.phone" name="phone" @blur="touched.phone = true">
<p v-if="shownError('phone')" class="error">{{ shownError('phone') }}</p>

注意圖裡最後一格「改正中」：錯誤已經顯示之後，顧客把手機改對，紅字要立刻消失，不用等他再離開一次。這不需要額外的程式。errors 是 computed，值一改就重算；touched.phone 已經是 true，所以 shownError('phone') 會立刻變成 undefined。前面把 errors 設計成由值推導出來，好處就在這裡。

也有人選「打字時就即時檢查，但只在值變成正確時給綠勾」。取捨在於：太早顯示錯誤會讓人分心、覺得被責備；太晚（只在送出時）會讓人填完整張表才發現第一格就錯了。離開欄位時顯示是多數設計系統的預設。

💡 實務上：錯誤顯示時機先跟設計師對好，全站一致
錯誤什麼時候出現通常是設計系統的規範，不是每個工程師各自決定：咖啡店的訂購頁、會員註冊、後台的品項編輯如果各有一套時機，使用者會覺得系統很亂。動手前先問設計師或 PM 有沒有既定規則，沒有就提議「blur 後顯示、送出時全部顯示」，寫成共用的 composable。dirty 在後台最常用：店長改了一半菜單就點別的頁面，要跳「有未儲存的變更，確定離開？」。不要什麼都用 dirty 擋，唯讀頁或只有搜尋框的頁面跳這個提醒只會惹人煩。

顯示的時機解決了，但 shownError 讀的 errors 是 validatePickup(values) 算出來的，這個函式還沒寫。下一節就來寫它。

錯誤從哪裡算出來？把驗證規則寫成純函式

上一節的 errors = computed(() => validatePickup(values)) 把「驗證」交給一個函式：給它表單的值，它回傳每一格的錯誤。這個函式要寫成純函式（pure function）。純函式指的是：同樣的輸入永遠得到同樣的輸出，而且不改動外面任何東西。

為什麼要這樣要求？第一，computed 本來就假設「輸入沒變，結果就不會變」，它只在 values 改變時重算。如果函式的結果還取決於別的東西，畫面上的錯誤就可能跟實際情況不一致。第二，純函式不用掛載元件就能測試：準備一筆值、呼叫函式、比對結果，練習 1 就是這樣判分的。第三，同一份規則可以給好幾個元件用，例如外帶表單和後台的「代客下單」頁。

最容易寫壞的規則：跟現在時間有關

大部分規則寫成純函式很自然，例如「手機要是 09 開頭的 10 位數字」只看手機這一格。最容易出事的是「取餐時間至少要在 15 分鐘後」。直覺的寫法是在函式裡寫 new Date() 拿現在時間，但這樣函式就不純了：輸入多了一個看不見的「現在」，同一筆資料早上驗證會過、晚上驗證不會過，測試也會時好時壞，看當下是幾點。修法是把「現在幾點」當成參數，由呼叫的人傳進來。這樣測試可以傳任何時間，正式程式則在呼叫時傳入當下的時間。

時間要怎麼比較也有陷阱。new Date('2026-10-31T09:00') 會用執行環境的時區解讀（TS 課第 6 課），顧客的瀏覽器和你的伺服器時區不同時，結果就不同。但表單裡的取餐時間其實是「店家當地的幾點幾分」，根本不需要時區。把 'HH:mm' 字串換成「從 0 點算起的分鐘數」再比較，最簡單，也不會受時區影響。下面的範例執行後看三行輸出：前兩行是 15 分鐘的邊界，第三行示範字串直接比較會錯在哪：

第三行是錯的：'9:30' 和 '10:00' 當字串比較時，是從第一個字元開始一個字一個字比，先比 '9' 和 '1'，'9' 比較大，就判定 9:30 比 10:00 晚。所以規則裡要先檢查格式是兩位數的 HH:mm，格式不對就只回「格式錯誤」，格式對了再換成分鐘數比較。（這個做法假設營業時間不跨過午夜，見課末「補充與查表」。）

「取餐時間要在營業時間內」是另一種要注意的規則：它要同時看取餐時間和店家的營業時間兩個值，叫跨欄位驗證（cross-field validation）。「確認密碼要和密碼一樣」也是。跨欄位的規則要決定錯誤掛在哪一格：掛在顧客要改的那一格，這裡是取餐時間，因為營業時間不是顧客能改的。

一次回傳所有錯誤

驗證函式回傳的形狀是 { 欄位: 訊息[] }。每一格是陣列，因為一格可能同時違反好幾條規則：取餐時間 18:05、現在 17:55，既超過營業時間、又不到 15 分鐘後，兩則訊息都該讓顧客看到。沒有錯誤的欄位不出現在結果裡，這樣 errors.value[field]?.[0] 拿到 undefined 就代表「這格沒問題」。

另一個要求是檢查完每一條規則再回傳。遇到第一個錯誤就 return 的話，顧客改好手機、按送出，才發現取餐時間也錯，再改、再送，又發現備註太長，一張表單要來回好幾輪。練習 1 就是照這些要求寫出 validatePickupForm。

用 schema 寫：zod 4

手寫規則能用，但欄位一多，每條規則都是一串 if。另一種寫法是 schema：用一個資料結構描述「每個欄位該長什麼樣子」，交給套件去檢查（TS 課第 26 課介紹過）。用 zod 4.6.7 寫同樣的規則，要認識三個 API：safeParse 不會丟錯，而是回傳成功或失敗；z.flattenError 把錯誤整理成 { formErrors, fieldErrors }，其中 fieldErrors 正好是本節要的「欄位 → 訊息陣列」；跨欄位的規則用 refine，並用 path 把錯誤掛到指定的欄位（zod 官方文件 Error formatting 與 API 章節）：

import { z } from 'zod'

function pickupSchema({ now, openAt, closeAt }: { now: string; openAt: string; closeAt: string }) {
  return z.object({
    name: z.string().trim().min(1, '請填姓名'),
    phone: z.string().regex(/^09\d{8}$/, '手機要是 09 開頭的 10 位數字'),
    pickupTime: z.string().regex(/^([01]\d|2[0-3]):[0-5]\d$/, '時間格式要是 HH:mm'),
    note: z.string().max(50, '備註最多 50 字'),
  }).refine(v => toMinutes(v.pickupTime) >= toMinutes(now) + 15, {
    error: '取餐時間至少要在 15 分鐘後',
    path: ['pickupTime'],                  // 錯誤掛在 pickupTime，而不是整張表單
  })
}

const result = pickupSchema(rules).safeParse(values)
const fieldErrors = result.success ? {} : z.flattenError(result.error).fieldErrors
// { phone: ['手機要是 09 開頭的 10 位數字'], pickupTime: ['取餐時間至少要在 15 分鐘後'] }

注意 schema 是包在函式裡回傳的：「現在幾點」和營業時間是參數，跟手寫版本的道理一樣，這樣 schema 仍然是純的。瀏覽器練習不能 import 套件，所以練習 1 手寫純函式，先弄懂規則怎麼寫；本機練習（環境在第 4 課設定過）已經安裝 zod，練習 2 的 pickup-schema.ts 就是用它寫的。zod 遇到前面欄位錯誤時 refine 還會不會執行，見課末「補充與查表」。

💡 實務上：前後端共用 schema，但伺服器還是要驗
前後端都用 TypeScript、放在同一個 repo（monorepo，前後端程式碼放在同一個儲存庫）時，常見做法是把 zod schema 放進共用套件，表單和 API 用同一份規則，改了手機格式兩邊一起變。共用的是規則，不是信任：伺服器仍然要自己 parse 一次，而且「時段有沒有額滿」這種要查資料庫的規則只能放後端。後端是別的語言或別的團隊時，就不要硬共用，改用 API 規格文件（例如 OpenAPI，描述每支 API 欄位與限制的標準格式）對齊欄位和限制。錯誤訊息是給使用者看的文案，要和 PM 或設計師確認用詞，不要讓工程師的「Invalid input」直接出現在畫面上。

到這裡的規則都只看表單自己的值就能判斷。但表單上還有一格不是這樣：優惠碼 LATTE10 有沒有效，表單自己不知道，要問伺服器。

優惠碼要問伺服器：非同步驗證怎麼不亂？

要問伺服器才知道結果的檢查，叫非同步驗證（async validation），例如優惠碼是否有效、帳號是否已被註冊。它不能放進上一節的純函式：純函式要立刻回傳結果，問伺服器卻要等。所以它的結果要另外存成一個狀態，而且這個狀態比「對或錯」多：

  • idle：沒有輸入，不用檢查。
  • checking：已經在問伺服器，還沒有答案。
  • valid、invalid：伺服器回答了。
  • error：問不到伺服器（斷線、500），不知道有沒有效。

輸入一改變就要切到 checking。如果不切，顧客把有效的 LATTE10 改成 LATTE1，畫面還掛著上一個碼的「可以使用」，直到新的答案回來。

最直覺的寫法是 watch 優惠碼，每改一次就呼叫一次 API。這會碰到兩個問題。第一個是請求太多：顧客打 LATTE10 要打 7 個字，就送出 7 個請求，前 6 個問的都是還沒打完的碼，答案沒人要。解法是防抖（debounce）：輸入停下來一段時間（例如 400ms）才真的送出；這段時間內又有輸入，就把計時器清掉重新計時。像電梯門，有人進來就重新等，沒人進來才關門。

第二個問題是回應的順序不保證。先送的 LATTE 可能比後送的 LATTE10 晚回來，畫面就被舊的答案蓋掉。這是第 5 課的競態：新的輸入出現時，舊的請求就過期了，它的結果要丟掉。防抖減少了請求數，但沒有解決這個問題：只要防抖等待之後仍然送出了兩個請求，它們回來的順序一樣不保證。所以兩者都要做。

下面的範例用計時器模擬（時間縮短了，方便執行）：使用者每 50ms 打一個字，防抖等 200ms，假伺服器碼越短回得越慢，故意讓舊請求晚回來。程式用一個序號 latest 標記「最新的那次」，只有序號相符的回應能寫入狀態。執行後比較兩行的呼叫次數和最後的狀態：

兩個版本最後都是 valid，因為序號擋掉了晚回來的舊答案；但不防抖的版本送了 7 次，防抖的版本只送了 1 次。在 Vue 裡，序號可以換成 watch 加 onWatcherCleanup：輸入改變時，Vue 先執行上一輪的清理函式，在那裡清掉計時器、取消進行中的請求。取消靠的是 AbortController：每次送請求前建立一個 AbortController，把它的 signal 交給 fetch；清理函式呼叫 controller.abort()，請求回來時檢查 controller.signal.aborted，過期了就不寫入。這就是練習 3。

姓名、手機、取餐時間、優惠碼、備註這些單一的欄位都處理完了。表單裡還剩一格不是單一的值：明細，一個可以新增、刪除的陣列。

明細可以增減：刪掉一列，另一列的備註為什麼跑掉？

顧客點了三列：拿鐵、可頌、起司蛋糕，在可頌那一列的備註輸入框打了「加熱」。然後他刪掉第一列的拿鐵，「加熱」卻出現在起司蛋糕那一列。

原因在 v-for 的 key。第 7 課說過，Vue 用 key 判斷「這個 DOM 屬於哪一筆資料」。用 index 當 key 時，刪掉第一列之後，可頌從 index 1 變成 index 0、起司蛋糕從 2 變成 1；Vue 看到 key 0、1 還在、key 2 不見了，就保留前兩列的 DOM、拿去顯示可頌和起司蛋糕，刪掉的是最後一列的 DOM。有綁定資料的欄位（品項、數量）會跟著新資料更新，所以看起來沒問題；但備註輸入框沒有綁定資料，它的內容只存在 DOM 裡，原本第二列 DOM 裡的「加熱」就留在原地，現在那一列顯示的是起司蛋糕。

修法是每一列在建立時給一個穩定的 id（crypto.randomUUID()），用它當 key。id 跟著資料走，刪掉拿鐵時 Vue 就知道該移除的是拿鐵那一列的 DOM，其他列保留自己的 DOM 和備註。

明細列通常寫成一個獨立的元件，用 v-model 跟表單雙向綁定，它的 model 是陣列。依照第 10 課的規則，子元件不直接改父元件傳進來的陣列或物件，而是算出一個新陣列再指定給 model。這樣所有修改都經過 update:modelValue 事件，父元件知道明細改了：

const model = defineModel<OrderLine[]>({ required: true })

function update(id: string, change: Partial<OrderLine>) {
  model.value = model.value.map(line => (line.id === id ? { ...line, ...change } : line))
}
function remove(id: string) {
  model.value = model.value.filter(line => line.id !== id)
}

所以數量輸入框不寫 v-model="line.quantity"（那會改到父元件的物件），而是 :value="line.quantity" 配 @input="update(line.id, { quantity: Number(…) })"。練習 4 會把 key、新增一列和最後一節講的 id 一起做完。

到這裡，表單的每一格都能正確填寫、正確檢查了。接下來顧客要按「送出」，也就是開場第二個抱怨發生的地方。

多按一次「送出」：怎麼不會變成兩張訂單？

disabled 不夠

最直覺的防重複送出是 <button :disabled="submitting">：送出中就把按鈕停用。它只擋得住「點這顆按鈕」，但表單還有別的送出途徑：你可能在備註欄加了 Ctrl+Enter 快捷鍵、表單裡有第二顆送出按鈕、別的程式呼叫了 onSubmit() 或 form.requestSubmit()。還有一個時間上的空檔：如果送出前要先 await 檢查優惠碼，submitting 還沒設成 true 的這段時間，按鈕還沒停用，第二次送出也進得來。

這些途徑最後都會走到同一個送出函式，所以在函式的開頭擋，就一次擋住全部。這叫進行中保護：開頭先檢查是不是已經在送出，是就直接離開；不是就立刻標成送出中，finally 保證成功或失敗都會把它恢復：

async function onSubmit() {
  if (submitting.value) return     // 進行中保護：不管從哪裡觸發，第二次都直接離開
  submitting.value = true
  try { … } finally { submitting.value = false }
}

按鈕的 disabled 仍然可以留著，它讓顧客看得出「正在送出」；真正擋住重複的是函式開頭那一行。

送出函式要掛在 <form @submit.prevent> 上，而不是按鈕的 @click。在輸入框按 Enter 會觸發表單的 submit 事件，這叫隱式送出（implicit submission）；掛在表單上，滑鼠和鍵盤才會走同一條路，也才會經過同一個進行中保護。.prevent 阻止瀏覽器整頁送出；<form novalidate> 關掉瀏覽器內建的驗證提示框，改用你自己的訊息。

冪等鍵：同一筆訂單重送用同一把

進行中保護擋得住同一個頁面的連點，卻擋不住這種情況：請求送到了，伺服器建立了訂單，但回應在路上逾時了。這時 finally 已經把 submitting 恢復成 false，顧客看到「送出失敗」，再按一次，伺服器又建立一張。前端在這裡無能為力，因為前端根本不知道第一張其實建好了。

第 16 課的冪等鍵（idempotency key）就是為這個設計的。冪等的意思是「同一個操作做一次和做很多次，結果一樣」。前端替「這一筆訂單」產生一個唯一的 key，放在請求的 Idempotency-Key 標頭；伺服器記住處理過的 key，看到同一把 key 再來，就回傳第一次的結果，不再建立。

關鍵是 key 的生命週期：第一次送出時產生，失敗重送時沿用，成功之後清掉，下一筆訂單再產生新的。有兩種常見的錯，剛好是這個生命週期的兩個反方向。第一種是每次點擊都產生新的 key：重送時伺服器看到的是沒見過的 key，以為是新訂單，等於沒有冪等鍵。第二種是整個頁面永遠用同一把 key：第一筆成功之後，顧客再點一筆，第二筆也帶著舊 key，伺服器回傳第一筆的結果，第二筆根本沒建立。

也要記得，冪等鍵只是前端送過去的一個標頭，真正擋住重複的是伺服器：伺服器要記住 key、比對、回傳第一次的結果。沒有伺服器配合，前端送什麼 key 都沒用。伺服器遇到同一把 key 帶著不同內容、或第一個請求還在處理時該回什麼，見課末「補充與查表」。

下面的範例用一個假伺服器比較四種做法。假伺服器的第一個請求一定會建立訂單、但回應「逾時」，前端失敗就重送同一筆，連續下兩筆訂單（拿鐵、可頌）。執行後看每一行伺服器上最後留下哪些訂單：

  • 沒有冪等鍵、每次點擊新 key：拿鐵被建立兩次，跟開場的廚房收到兩張一模一樣的訂單一樣。
  • 永遠同一把 key：只有拿鐵，可頌被當成拿鐵的重送，沒有建立。
  • 一筆訂單一把：拿鐵、可頌各一張，這才是對的。

第二個抱怨解決了。但送出還有另一種結局：請求順利到了伺服器，伺服器卻拒絕了它。

伺服器回「這個時段已額滿」：錯誤怎麼回到那一格？

前端驗證全部通過，伺服器還是可能拒絕，因為有些規則前端根本無法判斷：這個時段剛好被別人訂滿、這支手機號碼被停用了，這些資訊只在伺服器的資料庫裡。這類「格式正確，但內容不符合規則」的錯誤，伺服器回 422 Unprocessable Content。第 16 課的 API 層把 422 轉成 ValidationError，帶著 fieldErrors，例如 { pickupTime: ['這個時段已額滿'] }，形狀跟前端驗證函式回傳的一樣。

開場的第三個抱怨，就是表單拿到這個錯誤之後只顯示「送出失敗」。要讓顧客知道改哪一格，表單要把它存起來、顯示到欄位下面。但它不能直接放進前端的 errors：errors 是 computed，由目前的值算出來；伺服器的錯誤卻是針對「送出那一刻的值」的評語，值一改，評語就過時了。所以伺服器的錯誤另外存在 serverErrors，形狀和 errors 一樣是 { 欄位: 訊息[] }。

存起來之後，要回答兩個問題。第一，顯示時誰優先？第一節的 shownError 只讀 errors，現在要先看 serverErrors：有伺服器的錯誤就顯示它，因為它是送出當下的最終判定，前端驗證通過不代表伺服器接受。伺服器的錯誤也不受 touched 限制，它是按過送出才有的，那一格一定該顯示。沒有伺服器錯誤時，才照原本的 touched || submitted 判斷回前端錯誤。第二，什麼時候清掉？顧客改了那一格，伺服器對舊值的評語就不適用了，所以在欄位的 @input 裡刪掉那一格的伺服器錯誤；這時如果新值在前端也不合法，前端的錯誤會接著顯示出來：

const serverErrors = ref<Partial<Record<Field, string[]>>>({})

function shownError(field: Field) {
  const server = serverErrors.value[field]?.[0]
  if (server) return server                        // 伺服器的判定優先，也不等 touched
  return touched[field] || submitted.value ? errors.value[field]?.[0] : undefined
}

function onInput(field: Field) {
  delete serverErrors.value[field]                 // 值改了，伺服器對舊值的評語就過時了
}
<input v-model="values.pickupTime" name="pickupTime"
       @blur="touched.pickupTime = true" @input="onInput('pickupTime')">

還有兩種錯誤對不到欄位：伺服器回的欄位名稱表單上沒有（例如 storeId），或根本不是驗證錯誤（逾時、500）。這些顯示在表單層級的訊息，並加上 role="alert"。role="alert" 是一個 ARIA 屬性，作用是內容一插入頁面，螢幕報讀器（把畫面唸出來的軟體）就立刻唸出來，不需要使用者先把焦點移過去；報讀器和 ARIA 屬性下一節會詳細說明。訊息不要把伺服器的內部錯誤原文丟給顧客。送出函式的 catch 寫成這樣：

} catch (error) {
  if (error instanceof ValidationError) {
    serverErrors.value = error.fieldErrors
    await focusFirstError()
  } else {
    formError.value = '送出失敗，請稍後再試'
  }
}

focusFirstError() 把焦點移到第一個有錯的欄位，最後一節會寫出它。

💡 實務上：開工前先跟後端對好錯誤格式
表單能不能把錯誤放回正確的欄位，取決於後端回的格式。開工前先確認幾件事：422 的 body 長什麼樣、fieldErrors 的欄位名稱和表單的 name 是否一致、明細列的錯誤怎麼表示（例如用 lines.2.quantity 代表第 3 列的數量）、冪等鍵伺服器會記多久、重複時回什麼狀態碼。這些寫進 API 文件，前端在 API 層統一轉換一次，不要每個表單各自解析。資深工程師在 code review 時也會看：失敗之後按鈕有沒有恢復、重送是不是沿用同一把 key。

反過來問：前端驗證過了，伺服器可以不驗嗎？

這一節看到伺服器會拒絕前端驗證過的資料。反過來的問題同樣重要：前端已經擋掉不合法的值，伺服器能不能省掉那些檢查？答案是不行。前端驗證的目的是讓顧客早點知道哪裡要改、少等一次來回，它不是安全措施。前端的程式在使用者的電腦上執行，任何人都可以打開 DevTools 改掉你的檢查，或用 curl 直接呼叫 API，完全不經過你的表單。所以每一條規則伺服器都要再驗一次（Node 課與 NestJS 課會在後端做），價格、庫存、權限這類只能由伺服器決定的東西，前端只負責顯示。

錯誤現在會在對的時機、出現在對的格子。但「紅字出現在格子下面」這件事，只對看得到畫面的顧客有用。

看不到紅字的顧客：怎麼讓每個人都知道哪一格錯？

可近用性（accessibility，簡稱 a11y）是讓使用螢幕報讀器、只用鍵盤的人也能使用。螢幕報讀器是把畫面內容唸出來的軟體，視障者靠它操作電腦和手機；它唸的不是畫面上的樣子，而是 HTML 的結構與屬性。所以一個把字變紅的錯誤訊息，對報讀器來說只是一段普通的文字，它不知道這段文字屬於哪一格，也不知道哪一格有錯。表單要讓報讀器唸得出來，最常出問題的是三件事：

  1. label 要對到輸入框：<label for="x"> 對到 id="x" 的輸入框，報讀器才會唸出「手機，編輯文字」，點標籤也會聚焦到輸入框。id 在整頁必須唯一。同一個元件出現兩次、或明細有好幾列時，寫死的 id="quantity" 就重複了，label 會對到錯的輸入框。Vue 3.5 起有 useId()：在 setup 裡呼叫，回傳這個 app 裡唯一的字串，同一個元件的每個實例都不同，伺服器渲染和瀏覽器也會產生一樣的值（官方文件 Composition API Helpers）。明細列也是用「useId() 的前綴＋列的 id＋欄位名稱」組出 id。useId() 的使用限制見課末「補充與查表」。
  2. 錯誤要關聯到欄位：只把字變紅，報讀器使用者聽不到。有錯的輸入框加 aria-invalid="true"，告訴報讀器這格有錯；再加 aria-describedby="錯誤訊息的 id"，聚焦到這格時一起唸出錯誤說明。沒有錯時兩個屬性都拿掉。注意 Vue 3 對非布林屬性綁 false 會輸出 aria-invalid="false"，要移除屬性得綁 undefined 或 null。
  3. 送出失敗時聚焦第一個錯誤欄位：長表單的錯誤可能在畫面外，看得到畫面的人要捲動才找得到，報讀器使用者更不會知道。前端驗證沒過或伺服器回 422 時，等 DOM 更新後（nextTick，第 6 課），錯誤訊息和 aria-invalid 都已經畫上去，再找到第一個 aria-invalid="true" 的欄位，呼叫 focus()。焦點一移過去，報讀器就會唸出這格的名稱和錯誤說明。下面用 template ref（第 8 課）拿到表單元素再往裡找。

把三件事放進手機欄位，就是下面這段。shownError 是第一節的那個判斷，它同時決定紅字、aria-invalid 和 aria-describedby，三者永遠一致：

<script setup lang="ts">
const id = useId()                                  // 例如 'v-0'
const formEl = useTemplateRef<HTMLFormElement>('form')

async function focusFirstError() {
  await nextTick()
  formEl.value?.querySelector<HTMLElement>('[aria-invalid="true"]')?.focus()
}
</script>

<template>
  <form ref="form" novalidate @submit.prevent="onSubmit">
    <label :for="`${id}-phone`">手機</label>
    <input
      :id="`${id}-phone`"
      v-model="values.phone"
      :aria-invalid="shownError('phone') ? 'true' : undefined"
      :aria-describedby="shownError('phone') ? `${id}-phone-error` : undefined"
      @blur="touched.phone = true"
    >
    <p v-if="shownError('phone')" :id="`${id}-phone-error`" class="error">{{ shownError('phone') }}</p>
  </form>
</template>
💡 實務上：上線前用鍵盤和報讀器走一遍
可近用性的問題光看畫面看不出來，最省事的檢查是自己當一次使用者：拔掉滑鼠，只用 Tab、Enter 填完整張訂單並送出；再打開系統內建的報讀器（macOS 的 VoiceOver、Windows 的「朗讀程式」），確認每一格和錯誤訊息都唸得出來。這幾分鐘的檢查可以放進 PR 的檢查清單。瀏覽器 DevTools 的 Lighthouse 能抓到 label 缺漏這類問題，但抓不到「錯誤沒被唸出來」，自動工具不能取代實際操作一次。

回到開場的三個抱怨：「09」跳紅字，靠 touched 和 submitted 決定顯示時機；兩張一樣的訂單，靠送出函式開頭的進行中保護加上一筆訂單一把的冪等鍵；「送出失敗」不知道改哪格，靠把 422 的 fieldErrors 放回欄位。再加上 aria-invalid 與聚焦，每位顧客都知道哪裡要改。練習 2 會把這些全部做進同一個 PickupForm.vue。這些行為表單套件也做得到；什麼時候值得改用套件，見課末「補充與查表」。

補充與查表

zod 的 refine 什麼時候執行

實際跑過（zod 4.6.7）：手機格式錯的時候，refine 仍然會執行，所以一次拿得到所有欄位的錯誤。但這也代表取餐時間格式錯時，refine 拿到的是不合法的字串；需要時可以用 refine 的 when 選項控制它什麼時候執行。

跨過午夜的營業時間

本課把 HH:mm 換成分鐘數比較，前提是營業時間不跨過午夜。跨夜營業（例如 18:00～02:00）時，02:00 換成分鐘數比 18:00 小，簡單的大小比較就不成立，要改成帶日期的時間。

Idempotency-Key 標頭草案的狀態碼

IETF 的 Idempotency-Key 標頭草案（draft-ietf-httpapi-idempotency-key-header-08）建議伺服器：同一把 key 帶著不同的內容時回 422，同一把 key 的第一個請求還在處理時回 409。

useId() 的使用限制

useId() 不要在 computed 裡呼叫；同一頁有兩個 Vue app 時，用 app.config.idPrefix 讓它們的 id 不撞在一起。

什麼時候改用表單套件

欄位很多、巢狀結構深、很多表單要共用同一套狀態管理時，可以考慮 VeeValidate、FormKit、TanStack Form 這類表單套件，它們幫你管 touched、dirty、陣列欄位和 schema 整合。選之前先確認它支援你的 Vue 版本與 schema 套件。本課的練習不安裝它們，因為你要先能自己寫出這些行為，才判斷得出套件做得對不對。

練習

練習 1：寫 validatePickupForm(values, rules)，回傳 { 欄位: 訊息[] }，沒有錯誤的欄位不要出現在結果裡。toMinutes 和訊息 MSG 已經寫好，姓名的規則也寫好當範例。規則（一次檢查完所有欄位，同一個欄位的訊息依下面的順序）：

  • phone：09 開頭、共 10 位數字，否則 MSG.phone。
  • pickupTime：不符合 TIME（兩位數的 HH:mm）時只回 MSG.timeFormat。格式正確時：不在 openAt～closeAt 之間（含兩端）→ MSG.closed(rules)；早於 now 之後 15 分鐘（剛好 15 分鐘可以）→ MSG.tooSoon。兩條都違反就兩個訊息都要有。
  • items：一筆都沒有 → MSG.noItems；每一筆的數量要是 1～20 的整數，否則 MSG.quantity(第幾項)（從 1 開始），每一筆錯的各一則。
  • note：超過 50 個字 → MSG.noteTooLong。
  • 現在幾點只能用 rules.now，不能在函式裡讀系統時間。

練習 2：PickupForm.vue 是外帶訂單表單（姓名、手機、取餐時間、備註），驗證規則已經用 zod 寫在 pickup-schema.ts。起始版有開場說的所有問題，把它改好：錯誤在欄位 blur 後或按過送出後才顯示，沒碰過的欄位不顯示；送出進行中再觸發 submit 事件不會重送；失敗重送沿用同一個冪等鍵，成功後清空表單、下一筆換新的；ValidationError 的 fieldErrors 顯示在對應欄位下面，使用者改了哪一格就清掉那一格的伺服器錯誤，其他錯誤顯示在 .form-error；有錯的欄位加上 aria-invalid 與指向錯誤訊息的 aria-describedby；送出失敗（前端驗證沒過或 422）時聚焦第一個錯誤欄位。檔案開頭的註解有完整要求。

練習 3：useCouponCheck(code, check) 回傳優惠碼的檢查狀態 idle／checking／valid／invalid／error。起始版每打一個字就呼叫一次 check，舊結果也會蓋掉新結果。改成：停止輸入 400ms 後才檢查；輸入一改變就是 checking；過期的請求 abort，結果不寫入；空白輸入是 idle；scope 停止（第 12 課的 effect scope，元件卸載時也一樣）時清掉計時器並中止請求。

練習 4：OrderItemsField.vue 是可增減的明細列，每列有品項選單、數量和一個沒有綁定資料的「備註」輸入框。起始版用 index 當 key，id 也寫死成 product、quantity、note，「新增一項」還沒寫。改成：key 用 line.id，刪除前面的列時其他列保留自己的 DOM 與備註；用 useId() 當前綴組出整頁唯一的 id，label 的 for 對到它（測試會在同一個 app 裡放兩個這個元件，也會比對伺服器渲染和瀏覽器產生的 id 是否相同，所以不能用亂數或自己的計數器）；寫好新增：用 props.newId() 產生 id，預設 props.products 的第一個商品、數量 1，指定新陣列給 model。

練習 5：手機欄位的錯誤訊息，什麼時候顯示比較好？

✓ 打字時值本來就還沒完成，a 會讓使用者還沒打完就看到紅字，像被責備。b 太晚：填完整張表才發現第一格就錯了。c 用 touched 和「按過送出」決定是否顯示，兼顧兩者；而錯誤消失不需要等 blur，改正的當下就讓它消失，使用者才知道改對了。

練習 6：送出按鈕加了 :disabled="submitting"，就能防止重複建立訂單嗎？

✓ disabled 只擋住「點這顆按鈕」。送出的途徑不只一條，所以在 onSubmit 開頭寫 if (submitting.value) return。就算前端完全擋住連點，網路逾時後的重送仍然可能建立第二筆，這要靠冪等鍵和伺服器配合。c 跟 a 是同一個盲點，只是換了擋按鈕的方法。

練習 7：前端已經用和後端相同的 zod schema 驗證過了，後端還需要驗證嗎？

✓ 前端的程式在使用者的電腦上執行，可以被改掉、跳過。前端驗證是為了體驗（早點告訴使用者哪裡要改），伺服器驗證才是規則真正的守門員。共用 schema 的好處是兩邊規則一致、訊息一致，不是讓其中一邊可以省略。c 錯：登入只證明「是誰」，不保證送來的資料合法。

常見錯誤

  • 打字時就顯示錯誤：使用者還沒打完就看到紅字。用 touched（blur 過）或「按過送出」決定要不要顯示。
  • 驗證函式裡用 new Date()：同一筆資料不同時間驗證結果不同，測試時好時壞，還會受時區影響。把現在時間當參數傳入，取餐時間用 HH:mm 換成分鐘數比較。
  • 遇到第一個錯誤就 return：使用者要改一格、送一次，反覆好幾輪。一次回傳所有欄位的錯誤。
  • 只停用按鈕防重複送出：快捷鍵、程式呼叫和 await 之前的空檔都會繞過。送出函式開頭檢查 submitting。
  • 每次點擊都產生新的冪等鍵：重送時伺服器當成新訂單。key 屬於一筆訂單：失敗重送沿用、成功後才換新的。反過來，整頁永遠同一把 key，下一筆訂單會被當成重送。
  • 伺服器的 422 錯誤沒有顯示到欄位：只顯示「送出失敗」，使用者不知道改哪裡。把 fieldErrors 對應回欄位，對不到欄位的才放表單層級。
  • 錯誤訊息沒有關聯到欄位：只把字變紅，報讀器唸不到。加 aria-invalid、aria-describedby，送出失敗時聚焦第一個錯誤欄位。
  • id 寫死或只用列的 id：同一個元件出現兩次就重複，label 對錯輸入框。用 useId() 當前綴；同一頁有兩個 Vue app 時再設 app.config.idPrefix。
  • 非同步驗證沒有防抖、沒有丟掉過期結果：請求太多，舊答案蓋掉新答案。計時器加上 onWatcherCleanup 裡的 abort()。
  • 以為前端驗證就是安全措施：API 可以直接被呼叫。伺服器一定要再驗一次。

小結

  • 表單除了 values，還要記使用者做過什麼：touched、submitting 用 ref 存；errors 由 values 推導，用 computed；dirty 拿目前的值和初始值比。錯誤在 blur 或按過送出後才顯示，改正的當下就消失。
  • 驗證寫成純函式：現在時間由參數傳入，取餐時間用 HH:mm 換成分鐘數比較；跨欄位規則的錯誤掛在使用者要改的那一格；一次回傳所有錯誤（zod 4 的 refine ＋ path，z.flattenError 取得 fieldErrors）。
  • 非同步驗證：有自己的 idle／checking／valid／invalid／error 狀態；防抖減少請求，過期的請求 abort 並丟掉結果，兩者都要做。
  • 明細列：穩定 id 當 key，沒有綁定資料的輸入框才不會錯位；指定新陣列給 model。
  • 送出：送出函式開頭的進行中保護擋住所有途徑的重複送出；冪等鍵一筆訂單一把，失敗重送沿用、成功後才換。
  • 422 的 fieldErrors 另外存、對應回欄位，改了那一格就清掉；對不到欄位的放表單層級。前端驗證只是為了體驗，伺服器一定要再驗一次。
  • 可近用性：label for ＋ useId()、aria-invalid、aria-describedby、送出失敗時聚焦第一個錯誤欄位。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：菜單頁的篩選條件（分類、排序）要做到：把連結傳給同事，他打開看到一樣的結果，重新整理也還在。放哪裡？

✓ 狀態放哪裡看誰要讀、正本在哪：要跟著連結走、重新整理還在的，只有網址做得到。store 和元件的 ref 重新整理就沒了。b 錯在 localStorage 只存在自己的瀏覽器，同事打開連結看不到這些條件。（第 15 課）

練習 9：這個 setup store 上線後，畫面切換內用／外帶都正常。哪裡會出事？

export const useCartStore = defineStore('cart', () => {
  const items = ref<CartItem[]>([])
  const orderType = ref<'here' | 'togo'>('here')
  const isTogo = computed(() => orderType.value === 'togo')
  function setOrderType(t: 'here' | 'togo') { orderType.value = t }
  return { items, isTogo, setOrderType }
})

✓ Pinia 看回傳物件裡有哪些 ref 來決定 state。沒回傳的 ref 在閉包裡照樣能用，所以畫面正常，但 $state 裡沒有它。把 orderType 加進 return。c 錯在 ref 的響應性不靠回傳，isTogo 照樣會更新。（第 15 課）

練習 10：進結帳頁時，購物車、會員資料、優惠券三個請求同時收到 401。API 層的寫法是「收到 401 就呼叫 refresh()，再重送」，後端採用 refresh token 輪替。會發生什麼？

✓ 輪替代表 refresh token 用過一次就作廢，後到的兩次拿的是作廢的那一張。修法是共用一次刷新：第一個 401 開始刷新並存下 Promise，其他請求等同一個，再各自重送一次；重送仍是 401 就登出一次。a 錯在沒有輪替時才只是浪費，有輪替就會把人登出。（第 16 課）

練習 11：客人在商品頁快速從拿鐵點到可頌，畫面偶爾停在拿鐵的內容。最可能的原因是什麼？

const product = ref<Product | null>(null)
watch(productId, async (id) => {
  product.value = await getProduct(id)
}, { immediate: true })

✓ 這是競態：回應回來的順序不一定跟送出的順序一樣。用 AbortController 取消上一次，await 回來後再檢查 signal.aborted，成功和失敗兩條路都要檢查，因為不是每個 fetcher 都理會 signal。a 錯在 callback 收到的 id 已經是新的值，flush 只決定執行的時機，管不到回應的順序。（第 17 課）

練習 12：後台把拿鐵改成 120 元，成功後呼叫自己寫的 invalidate('menu')，它的內容是 cache.delete('menu')。同一頁的菜單列表還是顯示 110 元，為什麼？

✓ invalidate 要做兩件事：把這個 key 標成過期，有人在用就立刻重抓。只從 Map 刪掉，正在顯示的元件還拿著舊的 ref，下一次有人呼叫 useQuery('menu') 才會重抓。c 錯在 SWR 是先給舊資料、同時在背景重抓，抓回來就換掉，不用等重新整理。（第 17 課）

練習 13：收藏按鈕用樂觀更新，寫法如下。客人從「未收藏」連點三次，哪裡會出事？

async function toggle() {
  const next = !isFavorite.value
  isFavorite.value = next
  try {
    await api.setFavorite(id, next)
  } catch (e) {
    isFavorite.value = !next
    error.value = e
  }
}

✓ 回應的順序不固定：第二、三次已經成功、伺服器是「已收藏」，第一次才逾時失敗，它的 catch 卻改回「未收藏」。修法是每次點擊拿一個序號，只有最新那一次失敗才回滾，而且回滾到伺服器最後確認過的值。a 錯在「點擊前的值」在連點時早就不是伺服器現在的值。（第 17 課）

練習 14：外帶表單的送出函式如下。請求逾時，客人看到「送出失敗」又按了一次。哪裡會出事？

async function onSubmit() {
  if (submitting.value) return
  submitting.value = true
  try {
    await api.createOrder(values, { idempotencyKey: crypto.randomUUID() })
  } finally {
    submitting.value = false
  }
}

✓ 冪等鍵屬於一筆訂單，不是一次點擊：第一次送出時產生，失敗重送沿用，成功之後才換新的。a 錯在進行中保護只擋得住「同時」的第二次，逾時之後 submitting 已經回到 false，第一張訂單可能早就建好了。c 是反方向的錯：整頁一把 key，下一筆訂單會被當成重送而沒有建立。（第 18 課）

練習 15：「取餐時間至少在 15 分鐘後」的驗證函式裡寫了 new Date()。測試時好時壞，在國外的客人也回報合法的時間被擋。怎麼改？

✓ 函式裡讀現在時間就不是純函式，同一筆資料早上過、晚上不過；new Date('…T09:00') 又是用執行環境的時區解讀。時間由參數傳入、用分鐘數比較，結果只由輸入決定，也不受時區影響。b 只修好了測試，客人瀏覽器的時區照樣讓結果出錯。（第 18 課）
