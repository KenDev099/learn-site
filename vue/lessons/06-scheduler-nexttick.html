階段 2：Vue 響應式實戰 · 第 6 課

排程器：批次更新、nextTick 與 flush 時機

結帳頁有一個「輸入優惠碼」按鈕。按下去，handler 先把 showCoupon 改成 true，讓 v-if 把輸入框畫出來；下一行呼叫 input.value?.focus()，讓客人可以直接打字。實際按下去，輸入框出現了，游標卻不在裡面。同事替這個元件寫的測試也一直失敗：點了按鈕之後，斷言「目前聚焦的是輸入框」不成立。每一行程式單獨看都沒錯。

原因是 Vue 改完資料不會立刻改 DOM，呼叫 focus() 的那一刻，輸入框還不存在。這課就從這個優惠碼欄位出發，弄清楚 Vue 什麼時候改 DOM、你在元件裡和測試裡各該等什麼，最後看「更新停不下來」的錯誤是怎麼來的。學完你能修好這個欄位和它的測試，也能判斷任何「改了資料卻讀到舊畫面」的問題。

這課的路線：
  1. 按下按鈕時，輸入框為什麼還不存在；Vue 怎麼把好幾次改動併成一次更新：先給最小修法 await nextTick()，再自己做一個迷你排程器，看懂它等的是什麼。
  2. nextTick 怎麼用、什麼時候用不上：改完資料要碰 DOM 時寫在哪裡，為什麼不能用 setTimeout 代替。
  3. 一輪更新的順序，與 watcher 該排在畫面更新之前還是之後：購物車加了品項要捲到最新一筆，flush 選項怎麼選。
  4. 測試點了按鈕，斷言為什麼還看到舊畫面：該 await 哪一個。
  5. 更新停不下來：「Maximum recursive updates exceeded」是怎麼來的，怎麼避免。
這課會用到：
  • 第 2 課的 scheduler 選項：有 scheduler 的 effect 被觸發時不直接重跑，而是交給 scheduler 決定什麼時候跑。
  • TS 課第 7 課的事件迴圈：同步程式跑完後，先清空 microtask 佇列（Promise.then 的 callback），才輪到下一個 task（setTimeout、點擊事件）。
  • 第 4 課的 template ref 與 VTU 入門：ref="input" 拿到 DOM 元素；測試裡用 mount 掛上元件、trigger 模擬點擊。

按下按鈕時，輸入框為什麼還不存在？

先看 handler 做的兩件事：第一行 showCoupon.value = true，第二行 input.value?.focus()。直覺上，第一行執行完，v-if 就該把輸入框畫出來，第二行就拿得到它。Vue 刻意不這樣做，原因要從另一個情境看。

假設結帳頁有「匯入團購單」的功能，用迴圈把 1000 筆品項加進購物車。第 2 課的 effect 在資料一改就立刻重跑；如果元件的渲染也這樣做，這個迴圈會讓畫面重畫 1000 次。使用者只看得到最後一次的結果，前面 999 次都是白做的工，而且每一次都要比對、修改 DOM。

所以 Vue 換了一個做法：資料改了，先記下「這個元件需要更新」，等目前這段同步程式全部跑完，再一次把畫面更新。這個做法叫批次更新（batching）。1000 次改動只留下一個「要更新」的記號，更新時讀到的已經是最後的資料，畫面只重畫一次。

「等這段同步程式跑完」要靠事件迴圈裡的 microtask 才做得到。TS 課第 7 課講過：JavaScript 一次只做一件事，一段同步程式（例如整個 click handler）跑完之前，別的程式插不進來。跑完之後，引擎先把 microtask 佇列清空，也就是用 Promise.resolve().then(fn)（TS 課第 8 課）或 queueMicrotask(fn) 排進去的 fn；清空之後，才輪到下一個 task，例如 setTimeout 的 callback、使用者的下一次點擊。microtask 剛好落在「這段同步程式的改動都收齊了、別的事情還沒開始」的時間點，所以 Vue 把更新排在這裡。

下面這格用 Proxy 模擬兩種做法：不批次的每次寫入都立刻「渲染」；批次的第一次寫入時排一個 microtask，之後只改資料。執行後看三行輸出裡的渲染次數，特別是第二行：迴圈剛結束時，批次的版本一次都還沒渲染。

第二行的 0 就是優惠碼 bug 的縮影：資料已經改了，渲染還沒發生。在 Vue 3.5.44 的元件裡實際量過也是如此：同一個 click handler 裡 count.value++ 三次，render 只跑一次；handler 剛結束時畫面還是 0，等到 microtask 之後才變成 3。

回到優惠碼按鈕。第一行 showCoupon.value = true 只是排了一個「更新結帳元件」的工作；第二行執行時，更新還沒發生，畫面上沒有輸入框，input.value 還是 null，?. 讓 focus() 根本沒被呼叫。最小的修法是在兩行中間插一句 await nextTick()：先等這一輪 DOM 更新做完，再往下執行。測試失敗的原因相同，點完按鈕要先 await 再斷言，細節在〈測試點了按鈕，斷言為什麼還看到舊畫面？〉。

但「這一輪更新」是誰排的、什麼時候開始、什麼時候算做完？不知道這些，就只能把 nextTick 當咒語用。下一節打開 Vue 裡決定更新時機的那段程式。

Vue 怎麼把好幾次改動併成一次更新？

決定「什麼時候執行哪些更新」的那段程式，Vue 叫它排程器（scheduler）。排程器的核心是一個工作佇列（job queue）：裡面放著等待執行的工作（job），每個 job 是一個函式，例如「重新渲染結帳元件」。

它跟第 2 課接起來是這樣：每個元件都有一個負責渲染的 effect，這個 effect 建立時帶著 scheduler。資料改變時，trigger 不直接重跑 render，而是呼叫 scheduler；scheduler 再呼叫 queueJob(update)，把「更新這個元件」排進佇列。

ReactiveEffect 就是第 2 課 effect 的 Vue 版本；componentUpdateFn 是「跑 render、把結果套到 DOM」的函式。

// 概念上（不是 Vue 的原始碼）
const effect = new ReactiveEffect(componentUpdateFn)
effect.scheduler = () => queueJob(update)   // trigger 時只排工作
const update = () => effect.run()           // 真的重新渲染

effect.scheduler = … 那一行是批次更新的關鍵：資料改變時執行的只有 queueJob，真正的渲染（effect.run()）被延後了。queueJob 要做三件事，每一件都是為了讓「1000 次改動、1 次渲染」成立：

  1. 去重（dedupe）：同一個 job 在佇列裡只放一次。count 改三次，scheduler 被呼叫三次，但「更新這個元件」只排一次。少了這一步，佇列裡會有 1000 個相同的 job，又回到渲染 1000 次。
  2. 只排一次 flush：把佇列裡的工作全部執行完，這個動作叫 flush，執行它的函式叫 flushJobs。第一個 job 進來時，用 microtask 排一次 flushJobs；之後進來的 job 只加進佇列，不再另外排。所以同一段同步程式裡的所有改動，都由同一次 flush 處理。
  3. 依 id 排序：每個元件建立時拿到一個遞增的 id（uid）。父元件一定比子元件先建立，所以父的 id 比較小；flush 時由小到大執行，就是父先於子。

為什麼要父先於子？父元件更新時，可能把子元件卸載掉（例如包著子元件的 v-if 變成 false），也可能把新的 props 傳給子元件並順手更新它。如果子元件先跑，前一種情況是更新了一個馬上就要消失的元件，後一種情況是子元件用舊 props 更新一次、父元件更新後又更新一次。父先跑，這些白工就都不會發生。

有了 flush 這個概念，nextTick 就說得清楚了。Vue 3.5.44 的 nextTick() 回傳的是「這一輪 flush 的 Promise」；目前沒有排著的 flush 時，回傳一個已經 resolve 的 Promise。所以 await nextTick() 等的就是「這一輪更新全部做完」。套回優惠碼按鈕：showCoupon.value = true 讓結帳元件的更新被 queueJob 排進佇列、排好一次 flush；nextTick() 拿到的就是這次 flush 的 Promise；await 回來時，flush 已經跑完，輸入框已經在 DOM 裡。練習 1 你會自己寫出這個 queueJob 和 nextTick。

原理清楚了，接下來回到元件裡：nextTick 該寫在哪裡，又有哪些情況其實等不到你要的東西？

改完資料要碰 DOM：nextTick 怎麼用、什麼時候用不上？

從上一節的機制可以直接推出使用規則：改完資料之後，同一個函式裡接著要讀或操作新的 DOM，就要先 await nextTick()。優惠碼欄位的聚焦是這一類；量新列表的高度、捲到剛加進來的那一筆也是。

下面用結帳頁的杯數按鈕觀察同一件事（優惠碼欄位留給練習 3 自己修）。按一下按鈕，兩行 console.log 讀的是同一個 DOM 元素，差別只在中間有沒有等過這一輪 flush：

<script setup lang="ts">
import { nextTick, ref } from 'vue'

const count = ref(0)
const counter = ref<HTMLElement | null>(null)

async function add() {
  count.value++
  console.log(counter.value!.textContent)   // 舊的：'0'，DOM 還沒更新
  await nextTick()
  console.log(counter.value!.textContent)   // 新的：'1'
}
</script>

<template>
  <button ref="counter" @click="add">{{ count }}</button>
</template>

count.value++ 只排了更新，所以第一行讀到 '0'；await nextTick() 讓函式暫停，等 flush 把按鈕的文字改成 1，第二行才執行。

注意要等的只有 DOM。count.value 改完立刻就是新值，只讀資料的話不需要 nextTick；被延後的是「把資料畫到畫面上」這一步。

常有人用 setTimeout(fn, 0) 代替 nextTick，而且看起來能用：setTimeout 排的是 task，一定在 microtask（也就是 flush）之後才執行，所以通常「剛好」等到了 DOM 更新。問題在於它等的不是你要的東西。task 之間可能插進別的事件，等多久沒有保證；在測試裡更糟，測試工具可以把 setTimeout 換成第 5 課用過的假計時器（fake timers），不手動推進時間，它就永遠不會執行。nextTick 等的正好是「這一輪更新完成」，不多也不少。

反過來，nextTick 也有等不到的東西：它只等已經改了的資料反映到 DOM。如果資料要等 API 回來才會改，呼叫 nextTick 時資料根本還沒變，這一輪 flush 裡沒有你要的更新，它很快就 resolve，DOM 還是舊的。這時要先 await 那個 API，資料寫進去之後，再 await nextTick()。

💡 實務上：nextTick 幾乎都出現在「聚焦、捲動、量尺寸」
最常見的三個場景：彈出視窗或優惠碼這類欄位出現後聚焦、點餐頁加入品項後捲到購物車最下面、展開區塊後量高度做動畫。寫之前先問自己「我等的是 DOM 嗎？」：如果是 API 還沒回來，nextTick 等不到它。看到一個函式裡連續好幾個 await nextTick()，通常代表時機沒想清楚，code review 時值得問一句。

nextTick 適合「自己寫的函式裡，改完資料接著做事」。但有些事不是某個函式觸發的：購物車的品項一變多就要捲到最新一筆，不管是誰加的。這種「資料一變就做事」，第 5 課寫在 watch 裡。watch 的 callback 也經過排程器，那它跟元件更新誰先誰後？

一輪更新裡，watch、元件更新、onUpdated 誰先誰後？

佇列裡除了元件更新，還有兩種會在 flush 時執行的東西。一種是 watch 的 callback。另一種是生命週期鉤子（lifecycle hook）：Vue 在元件一生中的特定時間點呼叫你登記的函式，例如 onUpdated(fn) 登記的 fn，會在元件每次重新渲染、DOM 更新完之後被呼叫（第 8 課深入）。

這些 callback 依照「需要看到更新前還是更新後的 DOM」分成兩類：在元件更新之前執行的叫 pre，預設的 watch 屬於這一類；在所有元件更新之後執行的叫 post，onUpdated 屬於這一類。Vue 3.5.44 的一輪 flush 是這樣：

由左到右讀這張圖：

  • 同步程式改資料時，只排工作，DOM 不變。
  • flush 開始後，元件依 id 由小到大更新；每個元件的 pre watcher 排在它自己的元件更新之前。父元件更新時如果把新 props 傳給子元件，Vue 會先跑子元件的 pre watcher，再更新子元件。官方文件的說法是：在父元件更新之後、自己的 DOM 更新之前執行。所以 pre watcher 讀自己元件的 DOM，讀到的是舊的。
  • 所有元件更新完，才執行 post callback，這時看到的是新 DOM；post callback 裡又改了資料，排出來的新工作也會在同一輪處理完，nextTick 的 Promise 才 resolve。

練習 2 會用簡化的模型：pre 全部先跑，再跑所有元件更新，最後跑 post。差別只在 pre watcher 有沒有穿插在元件之間，三段的先後關係是一樣的。元件以外建立的 watcher 排在哪裡，見課末「補充與查表」。

這張圖說明了一件事：watch 的 callback 預設排在自己元件的 DOM 更新之前。可是「捲到最新一筆」需要的是更新之後的 DOM。下一節就用這個情境看怎麼改。

購物車要捲到最新一筆：watcher 該排在畫面更新之前還是之後？

先照第 5 課的寫法：監聽購物車品項的筆數，變多就把列表的最後一個子元素捲進畫面。加入一杯拿鐵後，列表確實捲動了，可是捲到的是上一筆，拿鐵那一列還在畫面外。照上一節的順序就說得通：預設的 watcher 是 pre，執行時這個元件的 DOM 還沒更新，拿鐵那一列還沒畫上去，最後一個子元素是上一筆。

決定 callback 排在哪裡的，是 watch 的 flush 選項，有三個值：

flush什麼時候執行看到的 DOM適合
'pre'（預設）父元件更新之後、自己的元件更新之前，有批次自己的舊 DOM大部分副作用：發請求、存草稿
'post'這一輪所有元件更新之後，有批次。watchPostEffect 是 watchEffect 加上這個選項新 DOM要讀或操作更新後的 DOM：捲動、量尺寸、交給第三方圖表
'sync'每次改動當下立刻執行，沒有批次舊 DOM很少需要；要在同一段同步程式裡立刻反應時才用

在 Vue 3.5.44 實際跑過：同一個 count 加三種 watcher，點一下按鈕，執行順序是 sync → pre → post。每個 callback 都讀按鈕的 textContent：sync 讀到 '0'、pre 讀到 '0'、post 讀到 '1'；count.value 三者讀到的都是 1。資料一改就是新值，慢一步的只有 DOM。迴圈 push 1000 筆時，flush: 'sync' 的 watcher 執行 1000 次，預設的只執行 1 次。

購物車要的是新 DOM，所以加上 flush: 'post'，callback 就等這一輪所有元件更新完才執行：

watch(() => items.value.length, () => {
  cartEl.value!.lastElementChild?.scrollIntoView()   // 要捲到「新的」最後一筆
}, { flush: 'post' })

這跟上一節的 nextTick 是同一個道理的兩種寫法：在函式裡改完資料就接著做，用 await nextTick()；資料不管被誰改都要做，用 flush: 'post' 的 watcher。兩者都是「等這一輪更新完再碰 DOM」。

剩下的 'sync' 看起來最「即時」，但它放棄了批次：watcher 裡有昂貴的工作時，每次改動都付一次成本，迴圈改 1000 次就付 1000 次；而且 callback 在改動當下就執行，其他相關的資料可能才改到一半，讀到的是不一致的狀態。

💡 實務上：預設的 pre 就夠用，post 留給碰 DOM 的事
專案裡大部分 watcher 是「條件變了就重新查詢」「表單改了就存草稿」，用預設的 'pre' 就好。'post' 常用在像購物車捲到最新一筆這種要讀新 DOM 的事，或把資料交給要讀 DOM 的第三方套件，例如營收圖表、地圖。'sync' 在一般業務程式裡很少需要，code review 看到時先問「為什麼不能批次？」，答不出來就拿掉。

到這裡，元件裡的寫法都有答案了：handler 裡用 nextTick，watcher 用 flush: 'post'。可是開場那個一直失敗的測試呢？測試沒有真的使用者在點，它本身就是一段「改完馬上讀 DOM」的程式。

測試點了按鈕，斷言為什麼還看到舊畫面？

看優惠碼測試做了什麼：用 mount 掛上元件，trigger('click') 點按鈕，下一行檢查聚焦的元素。trigger 送出點擊事件，handler 跟著執行，但 handler 只排了更新；測試的下一行馬上就執行了，這時 flush 還沒發生，輸入框還不存在。這跟元件裡「改完資料馬上讀 DOM」是同一個 bug，只是寫的人換成了測試。

修法也一樣：先等，再斷言。不過測試裡要等的東西不只一種，VTU 提供了幾種等待方式，各自等的東西不同：

寫法等什麼什麼時候用
await wrapper.trigger('click')、await setValue()它們回傳 nextTick()：等這一輪 DOM 更新操作之後檢查畫面
await nextTick()這一輪 DOM 更新測試直接改資料、或 handler 裡又 await 了一次 nextTick
await flushPromises()VTU 2.5.1 用 setImmediate（沒有時用 setTimeout）排一個 task 再 resolve，所以在那之前已經 resolve 的 Promise callback 都會跑完元件裡等了假 API 的 Promise（await api.getMenu()），之後才改資料
await vi.advanceTimersByTimeAsync(ms)推進假計時器，並在中間跑完 microtask用了 vi.useFakeTimers() 時

前兩列等的是 DOM 更新，對應前面講的 flush。第三列處理的是另一種等待：元件裡呼叫了 API。測試裡通常會把真的 API 換成假的函式，回傳一個馬上 resolve 的 Promise；但元件拿到資料、寫進 ref，是在那個 Promise 的 callback 裡，而寫進 ref 之後還要再一輪 flush 才會反映到 DOM。nextTick 只等「已經改了的資料」，等不到還沒回來的 API；flushPromises 排一個 task，讓在那之前排好的 microtask，包含 API 的 Promise 和後續的 flush，全部跑完。

flushPromises 靠的是真的 setImmediate／setTimeout，所以用了 vi.useFakeTimers() 之後，它要等的計時器永遠不會觸發，測試就卡到逾時（在 Vitest 5.0.5 實際測過）。這時改用 await vi.advanceTimersByTimeAsync(0)。nextTick 用的是 microtask，假計時器不會影響它。

不要在測試裡寫 await new Promise(r => setTimeout(r, 100)) 這種 sleep：慢機器上不夠、快機器上浪費時間，而且看不出你在等什麼。先想清楚要等的是 DOM 更新、API 的 Promise 還是計時器，再挑對應的寫法。

優惠碼這個例子要兩邊一起修。第一步，元件照第一節的修法，在 showCoupon.value = true 和 focus() 中間加 await nextTick()；元件沒修，focus() 還是在輸入框出現之前就執行，測試怎麼等都沒用。第二步，測試把 trigger 改成 await wrapper.trigger('click') 再斷言。為什麼 await trigger() 回來時 focus 已經發生了？trigger 回傳的也是這一輪 flush 的 Promise；handler 執行時就 await nextTick()，比測試先在同一個 Promise 上登記，所以 flush 完先接著跑 handler 剩下的 focus()，測試才往下執行。練習 3 的測試會開假計時器，這也是為什麼用 setTimeout 延後 focus 過不了。

團隊通常會設定 CI（continuous integration）：每次推上程式碼，就在伺服器上自動跑全部測試。CI 上偶爾失敗、重跑又過的測試叫 flaky test，在元件測試裡，常見原因正是等錯了東西。

💡 實務上：時好時壞的測試，多半是等錯了東西
flaky 的元件測試，常見原因是斷言跑在 DOM 或 API 的 Promise 完成之前，或靠 sleep 碰運氣。團隊遇到這種測試時，不要加長等待時間了事，而是照上面的表找出它該等的是哪一種。元件裡會呼叫 API 的，習慣在測試裡把 API 換成假的，再用 flushPromises() 等它，結果才會每次都一樣。

元件修好了，測試也知道怎麼等了。最後還有一種跟排程器有關的 bug，方向正好相反：不是更新太晚，而是更新停不下來。

更新停不下來：「Maximum recursive updates exceeded」是怎麼來的？

假設有人在結帳元件的 onUpdated 裡改了畫面用到的資料，例如 onUpdated(() => { count.value++ })，而範本裡顯示 count。一步一步看會發生什麼：元件更新完，onUpdated 執行，count 加一；畫面讀了 count，所以排程器又排一次這個元件的更新；更新完，onUpdated 又執行，count 又加一……。上一節說過，post callback 排出來的新工作會在同一輪處理完，所以這一輪 flush 永遠結束不了。watch 也一樣：callback 改了「會讓自己再跑一次」的資料，就形成同樣的迴圈。

為了讓開發時看得到這種迴圈，開發模式下，排程器會數同一輪裡每個工作執行了幾次。Vue 3.5.44 的 RECURSION_LIMIT 是 100：要執行某個工作前，先看它這一輪已經執行的次數，超過 100（也就是已經跑了 101 次）就不再執行，並報錯：

Maximum recursive updates exceeded. This means you have a reactive effect
that is mutating its own dependencies and thus recursively triggering itself.

訊息裡的 mutating its own dependencies，就是上面那個迴圈：effect 讀了 count（count 因此被 track，成為它的依賴），又去改 count。

下面用迷你版看這個保護怎麼運作：update 每次執行都把 stock 加一，再把自己排回佇列，模擬 onUpdated 改了畫面用到的資料。執行後看印出的執行次數和 stock：

在 Vitest 裡跑同樣的元件（onUpdated(() => { count.value++ })），這個錯誤會讓測試失敗。修法是找出誰在改自己依賴的資料，讓資料的流向只有一個方向：

  • 衍生的值改用 computed，不要在 watch 或 onUpdated 裡回寫。computed 從來源算出值，不會反過來改來源，就沒有迴圈。
  • 真的要在更新後改資料，加上條件，只在值真的不同時才寫入，讓迴圈收斂。
  • 錯誤訊息裡有元件名稱時從那個元件查起；沒有時看 onUpdated 和 watcher。
💡 實務上：開發時看到這個警告就要修，不要放著
這個次數檢查只在開發模式才有，正式環境沒有這道防線，排程器會一直同步跑下去，頁面卡住沒有反應，變成使用者回報「點了就當掉」。常見的來源是「watch A 改 B、watch B 又改 A」的雙向同步，例如購物車的商品數量和小計互相回寫。資深工程師的習慣是讓資料只有一個來源：小計用 computed 從數量算出來，而不是用兩個 watcher 互相同步。

下面的練習把整條路走一遍：先自己寫出排程器和 pre／post 的順序，再修好優惠碼欄位，最後用 flush: 'post' 處理吧台的新訂單列表。

練習

練習 1：起始程式的 queueJob 一收到工作就立刻執行。把它改成迷你排程器：

  • 同一輪裡，同一個 job 只執行一次。
  • job 在 microtask 裡執行，不能同步執行，也不能用 setTimeout（要比先排好的 setTimeout 早）。
  • 依 job.id 由小到大執行；flush 途中新加入的 job 也在同一輪執行，而且照 id 插到剩下的工作中間。
  • nextTick() 回傳的 Promise 在這一輪全部執行完之後才 resolve；flush 結束後，下一次 queueJob 要能再排一輪。

練習 2（簡化模型：真正的 Vue 會把 pre watcher 依元件順序穿插在元件更新之間）：起始程式是練習 1 的一種寫法，queuePreFlushCb 和 queuePostFlushCb 只是把 callback 當成一般 job 排進去。改成一次 flush 依序執行：

  • 所有 pre callback → 所有 job（依 id）→ 所有 post callback。pre callback 不管 id 多大，都比 job 先執行。
  • post callback 也要去重：同一輪排兩次只執行一次。
  • pre callback 排入的 job、post callback 排入的 job，都要在同一輪、nextTick() resolve 之前執行完。
  • job 執行時又排了 pre callback（例如父元件更新後觸發子元件的 watcher），它和它排的 job 都要在 post 之前跑完：pre 和 job 都清空了才跑 post。

練習 3：結帳頁的 CouponField.vue：按「輸入優惠碼」後用 v-if 顯示輸入框，並自動聚焦。起始版在同一段同步程式裡呼叫 focus()，那時輸入框還不存在。修好它：按下按鈕、等一輪 DOM 更新後，document.activeElement 就是那個輸入框；按下前畫面上沒有輸入框（不能改成 v-show）。測試會開假計時器，用 setTimeout 延後 focus 不會過。

練習 4：吧台的訂單列表有新訂單時要捲到最新那一筆，捲動前必須看到已經畫上新訂單的列表。在 ex4.ts 寫 useNewOrderNotice(listEl, orders)：orders（ref 陣列）筆數變多時，把 listEl.value 當下的子元素數量 push 進回傳的 seen 陣列。連續各新增一筆要記到 1、2、3；同一段同步程式裡一次新增 3 筆只記一次 3；刪掉訂單時不記。

練習 5：同一個 click handler 裡執行三次 count.value++，這個元件會重新渲染幾次？

✓ 每次改動都只是 queueJob，同一個元件的更新工作在佇列裡去重，handler 結束後的 microtask 裡只渲染一次。畫面不是立刻更新，所以 a 錯；nextTick 只是讓你「等」這一輪更新，不呼叫它畫面也會更新，所以 c 錯。

練習 6：在 handler 裡執行 count.value = 5，下一行馬上讀這個元件的 el.textContent，讀到的是？

✓ 改資料只會排一個更新工作，DOM 要等這段同步程式結束後的 flush 才更新，所以同一段程式裡讀到的是舊內容。count.value 本身已經是 5，需要等的只有 DOM。渲染時不會先把內容清空，c 錯。

練習 7：watch(() => items.value.length, cb, { flush: 'sync' })，接著用迴圈 push 1000 筆，cb 會執行幾次？

✓ flush: 'sync' 不經過佇列，每次改動當下就執行，沒有批次，所以是 1000 次（在 Vue 3.5.44 實際量過；同樣情況預設的 'pre' 只執行 1 次）。批次只發生在 'pre' 和 'post'，a 錯；sync 不等 nextTick，b 錯。

常見錯誤

  • 改完資料在同一段同步程式裡讀 DOM：DOM 還沒更新，像優惠碼欄位的 focus() 找不到輸入框。先 await nextTick()，或把讀 DOM 的程式放進 flush: 'post' 的 watcher。
  • 用 setTimeout(fn, 0) 代替 nextTick：等的時間沒有保證，假計時器下也不會執行。要等的是 DOM 更新就用 nextTick。
  • 用 nextTick 等 API：nextTick 只等已經改了的資料反映到 DOM。先 await API、資料寫進去之後再 await nextTick()。
  • 在預設 flush 的 watcher 裡讀自己元件的 DOM：pre watcher 在元件更新之前執行，讀到的是舊 DOM，捲動會捲到上一筆。改用 flush: 'post'。
  • 為了「立刻反應」到處加 flush: 'sync'：沒有批次，迴圈改 1000 次就跑 1000 次，而且 callback 執行時相關資料可能只改到一半。
  • 在 onUpdated 或 watch 裡改自己依賴的資料：形成更新迴圈，超過 100 次報「Maximum recursive updates exceeded」。衍生值用 computed，或只在值真的不同時寫入。
  • 測試裡沒有 await trigger()：斷言跑在 DOM 更新之前。元件等了 API 的 Promise 時還要 await flushPromises()；用了假計時器就改用 await vi.advanceTimersByTimeAsync()。

補充與查表

  • 元件以外的 pre watcher：沒有屬於任何元件的 pre watcher（例如在元件外建立的 watch）排在一輪 flush 的最前面。
  • Pinia 的 $subscribe：Pinia 4.1.0 的 $subscribe 底層也是 watch，直接改 state 時跟著預設的 'pre' 批次；需要每次改動都立刻收到時才加 { flush: 'sync' }（第 15 課）。
  • 這課提到的版本：Vue 3.5.44、@vue/test-utils（VTU）2.5.1、Vitest 5.0.5，與 vue/practice/package.json 一致。

小結

  • Vue 改資料只排工作，等這段同步程式結束後的 microtask 才一次更新 DOM（批次更新）。所以優惠碼的 focus() 緊接在 showCoupon = true 後面時，輸入框還不存在。
  • 排程器的 queueJob 去重、用 microtask 排一次 flush、依元件 id 由小到大（父先於子）執行，所以同步改 1000 次只渲染一次。nextTick() 回傳這一輪 flush 的 Promise。
  • 改完資料要讀或操作新 DOM：在函式裡用 await nextTick()；資料不管被誰改都要做，用 flush: 'post' 的 watcher。nextTick 等不到 API，setTimeout 不是替代品。
  • 一輪 flush：pre watcher 在自己的元件更新之前（父元件更新之後）、元件依序更新、最後 post callback。預設 'pre' 適合大部分副作用；'sync' 沒有批次，少用。
  • 測試裡：await trigger()／nextTick() 等 DOM，flushPromises() 等 Promise，假計時器下改用 vi.advanceTimersByTimeAsync()，不要 sleep。
  • effect 改自己的依賴會無限更新，Vue 3.5.44 的開發模式在同一個工作同一輪執行超過 100 次時報錯；正式環境沒有這道檢查。資料只留一個來源，衍生值用 computed。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：商品卡片要在庫存低於 5 時顯示「快賣完」，product 是 reactive。庫存從 8 降到 3，標籤一直沒出現，為什麼？

function useLowStock(stock: number) {
  return computed(() => stock < 5)
}

const isLow = useLowStock(product.stock)

✓ product.stock 在呼叫前就被讀成數字，函式拿到的值跟 proxy 沒有連線，computed 沒有任何依賴，永遠是 false。改成傳 getter () => product.stock 或 toRef(product, 'stock')，在 computed 裡讀它，每次重算都會重新追蹤。a 錯在 computed 重不重算看它讀到的依賴，跟寫在哪個函式裡無關。（第 4 課）

練習 9：門市地圖 SDK 的實例放進 reactive({ map: new StoreMap(el), selected: null })，呼叫 state.map.flyTo(store) 就丟 TypeError: Cannot read private member。原因是什麼？

✓ reactive 不複製物件，而是包一層 proxy；方法照樣找得到，但執行時 this 是 proxy，只有原本的實例能讀 #private。在建立的那一行就 markRaw(new StoreMap(el))，或把實例放在 shallowRef；之後換新實例也要再標記一次。b 錯在 proxy 跟原物件是同一份資料的兩個入口，沒有複製這回事。（第 4 課）

練習 10：滿 500 元要提示免運。加入剛好湊滿 500 的那一杯時，提示沒有出現，下一次加購才出現，哪裡出錯？

const total = ref(0)
watch(items, list => {
  total.value = list.reduce((s, i) => s + i.price, 0)
}, { deep: true, immediate: true })

function addItem(item: Item) {
  items.value.push(item)
  if (total.value >= 500) showFreeShipping()
}

✓ watch 的 callback 被排進佇列，等這段同步程式結束後的 flush 才更新 total，addItem 裡讀到的是加入前的金額。total 是從 items 算出來的值，改成 computed：讀的時候發現依賴變了就重算，沒有時間差。a 錯在 deep: true 已經讓 push 會觸發，問題是執行的時機，不是有沒有觸發。（第 5、6 課）

練習 11：訂單看板快速切換門市時，有時顯示的是上一間門市的訂單。這個 watcher 哪裡出事？

watch(storeId, async id => {
  const controller = new AbortController()
  const data = await api.orders(id, { signal: controller.signal })
  onWatcherCleanup(() => controller.abort())
  orders.value = data
})

✓ 清理函式只能在 watcher 同步執行期間登記；await 之後 Vue 不知道是哪個 watcher，只印警告，舊請求沒被取消，晚回來就蓋掉新結果。把 onWatcherCleanup 移到第一個 await 之前，catch 裡先檢查 signal.aborted，被取消的不當成錯誤。a 錯在每次各建一個正是對的：清理函式記住的是這一次的 controller，下一次執行前 Vue 會呼叫它。（第 5 課）

練習 12：訂單頁寫了 onMounted(async () => { await loadConfig(); watch(storeId, load) })。在點餐頁和訂單頁之間切換幾次後，換一次門市，Network 面板裡 load 的請求出現好幾次，為什麼？

✓ 只有在 setup 同步執行期間建立的 watcher 會綁在元件上、卸載時自動停止；寫在 await 之後就沒人負責停它，次數隨切換頁面累積。最好改成在 setup 裡同步建立；真的要延後，就留著 watch() 回傳的把手，在 onUnmounted 呼叫。b 錯在排程器會去重，同一輪的多次改動只讓同一個 watcher 執行一次。（第 5 課）

練習 13：展開菜單面板後要量面板高度做動畫，量到的卻是空列表的高度。loadMenu() 會打 API，回來後才寫入 menu.value，問題在哪？

async function openMenu() {
  loadMenu()
  await nextTick()
  height.value = panel.value!.offsetHeight
}

✓ nextTick 只等「已經改了的資料」反映到 DOM；這時資料根本還沒變，等的是 API。先 await loadMenu()，資料寫進去之後再 await nextTick() 量高度。c 錯在多等幾輪 nextTick 只是碰運氣，API 回來的時間不固定；一個函式裡連續好幾個 nextTick，通常代表沒想清楚在等什麼。（第 6 課）

練習 14：吧台的訂單列表用 watch(() => orders.value.length, () => listEl.value!.lastElementChild?.scrollIntoView()) 在新訂單進來時捲到底。捲完之後，最新那一筆總是還在畫面外，為什麼？

✓ 預設的 'pre' watcher 在自己的元件更新之前執行，看到的是舊 DOM，新訂單的那一列還沒畫上去。加上 { flush: 'post' }，等這一輪所有元件更新完才執行，就捲得到新的最後一筆。a 錯在 getter 回傳的 length 變了就會觸發，不需要 deep；它有捲動，只是捲到舊的最後一筆。（第 6 課）

練習 15：同事想在後台角落顯示「畫面更新了幾次」來除錯，寫了下面這段。開發和正式環境各會發生什麼事？

const renders = ref(0)
onUpdated(() => { renders.value++ })

// 範本：<small>畫面更新了 {{ renders }} 次</small>

✓ 畫面讀了 renders，onUpdated 改它就又排一次更新，更新完又改，形成迴圈；開發模式下同一個工作同一輪執行超過 100 次，Vue 報 Maximum recursive updates exceeded。不要在 onUpdated 裡改畫面用到的資料，衍生的值用 computed，非寫不可就只在值真的不同時寫入。c 錯在次數檢查只在開發模式才有，正式環境會一直跑下去。（第 6 課）
