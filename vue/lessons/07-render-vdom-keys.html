階段 3：元件如何運作 · 第 7 課

從範本到畫面：render、虛擬 DOM 與 key

店員在點餐頁的訂單明細裡，替拿鐵打了備註「少冰」，接著刪掉第一筆美式咖啡。每一列的備註欄是一個單純的輸入框，店員打的字先留在輸入框裡，按「送出訂單」時才一次讀出來，還沒有存回品項資料。畫面上的「少冰」卻跑到可頌那一列，廚房照著做錯了飲料。翻遍程式碼，沒有任何一行把備註從拿鐵搬到可頌。

搬動備註的不是你的程式，而是 Vue 更新畫面時重用了錯的 DOM 元素。要看懂這句話，得先知道你寫的 <template> 怎麼變成畫面，資料改了之後 Vue 又怎麼決定要改哪些 DOM。這課沿著這張訂單明細走一遍：先看 Vue 怎麼把它畫出來，再看刪掉一筆時 Vue 怎麼比對新舊畫面，找出備註跑掉的原因並修好。最後處理同一張明細上另外兩個常見問題：展開收合的面板該用 v-if 還是 v-show，以及顧客打的備註顯示在後台時安不安全。

這課的路線：
  1. 程式沒搬備註，是誰改了 DOM：範本怎麼變成 render 函式和虛擬 DOM，資料改了 Vue 怎麼只改差異（開場問題的最小答案），再讀一段真正的編譯結果。
  2. 刪掉一筆時 Vue 怎麼對應新舊兩列、key 該用什麼：用 index 當 key 為什麼讓備註跑到別列，怎麼修。
  3. 每次重跑 render、比對整棵樹，不會慢嗎：編譯器替虛擬 DOM 做的三種最佳化。
  4. 客製選項面板用 v-if 還是 v-show：兩者的成本差在哪，跟 key 是同一條規則。
  5. 顧客打的備註顯示在後台安不安全：為什麼 {{ }} 擋得住 XSS、v-html 擋不住。
這課會用到：
  • 第 2 課的 effect：執行時記下讀了哪些資料，資料改了就重跑。
  • 第 6 課的排程器：資料改了不立刻更新 DOM，而是把工作排進佇列，這段同步程式跑完後一起更新。
  • TS 課第 16 課的型別縮小：用 typeof x === 'string' 檢查之後，那個分支裡 TypeScript 就知道 x 是字串，練習 1 用它分開處理兩種節點。
  • 第 4 課的本機練習環境：練習在自己的電腦上寫，用測試判分。

程式沒有搬備註，那是誰改了 DOM？

要回答這個問題，得先看 Vue 從你的 .vue 檔到畫面上的 DOM，中間做了哪些事。這一節先把整條路走一遍，路上會遇到四個名詞，每個都在用到之前講清楚。

第一個是範本（template）。一個 .vue 檔把範本、程式和樣式放在同一個檔案裡，Vue 稱它為單檔元件（single-file component，簡稱 SFC）；範本就是其中 <template> 那一段。它長得像 HTML，但瀏覽器看不懂 {{ }}、v-for、@click，所以範本不能直接交給瀏覽器，要先轉換成 JavaScript。

轉換的結果是一個函式，叫 render 函式（render function）。它不直接建立 DOM，而是在每次被呼叫時，回傳一份「畫面現在應該長什麼樣子」的描述。這份描述由一個個虛擬節點（vnode）組成：每個 vnode 是一個普通的 JavaScript 物件，記下「這裡要有一個什麼元素、有哪些屬性、裡面放什麼」，大致是 { type, props, children }。vnode 的 children 裡又可以有 vnode，於是整個畫面就是一棵 vnode 樹。

這棵在記憶體裡表示整個畫面的 vnode 樹，就是虛擬 DOM（virtual DOM）。叫它「虛擬」，是因為它不是瀏覽器裡真正的 DOM 元素，只是物件；建立物件很便宜，建立和修改真正的 DOM 則要瀏覽器重新計算版面、重畫畫面，貴得多。Vue 的工作就是把這棵便宜的樹同步到真正的 DOM 上。

有了這四個名詞，就能看懂 Vue 官方文件（Rendering Mechanism）描述的三個步驟：

  1. 編譯（compile）：範本被編譯成 render 函式。用 Vite 開發時，這一步由 @vitejs/plugin-vue 在建置時完成，瀏覽器拿到的已經是 JavaScript。
  2. 掛載（mount）：執行 render 函式得到 vnode 樹，依照它建立真正的 DOM。執行 render 時讀到的響應式資料會被追蹤：元件的 render 本身就是一個 effect，跟你在第 2 課做的一樣。
  3. 更新（patch）：render 用到的資料改變，這個 effect 被排進第 6 課的佇列，下一輪重新執行 render，得到一棵新的 vnode 樹。Vue 拿新樹和舊樹比對，只把差異套用到 DOM。這個比對叫 patch，也常聽到 diff、reconcile 這兩個說法，指的是同一件事。

為什麼要繞這一圈，不直接改 DOM？第 1 課講過，Vue 讓你用「畫面 = f(狀態)」的方式寫程式：你只描述「狀態是這樣時，畫面長這樣」，不用自己寫「刪掉第一個 li、改第二個 li 的文字」這種一步一步的 DOM 操作。這種寫法要求每次狀態改變都重新描述整個畫面。如果每次都照著描述把整個 DOM 砍掉重建，不只慢，輸入框的游標、捲動位置都會不見，訂單明細輸入框裡打到一半的「少冰」也會直接消失。

虛擬 DOM 解決的就是這個矛盾：你每次重新描述整個畫面，但描述只是物件；Vue 拿新舊兩份描述比對，算出最少要動哪些地方，能重用的舊 DOM 元素就重用，只改內容不同的部分。它的價值是讓宣告式寫法夠快，不是比你親手寫的精準 DOM 操作更快：它多了建 vnode、比對的成本。

開場的 bug 就出在「重用」這一步。要重用舊元素，Vue 必須決定「新的這一列，用舊的哪一個元素來顯示」，而列表的對應靠的是 v-for 上的 key。key 用 index 時，刪掉第一筆美式咖啡之後，拿鐵的 index 從 1 變成 0，Vue 就把原本顯示美式咖啡的那個 <li> 拿來顯示拿鐵，把原本顯示拿鐵、輸入框裡打著「少冰」的那個 <li> 拿來顯示可頌。Vue 只改了品名文字，輸入框是同一個元素，「少冰」自然留在原地。修法是 key 改用品項自己的 id。

這是答案的最小版本。要真的理解它，還得看清楚 Vue 比對時手上拿的是什麼：render 函式實際長什麼樣、vnode 裡到底有哪些欄位？下一節讀一段真正的編譯結果。

範本實際被編譯成什麼？

先從訂單明細頁最上面那塊標頭看起：顯示顧客、總額和結帳按鈕。它沒有列表，最容易逐行對照；列表的部分留到下一節。範本是這樣：

<div class="order">
  <h2>今日訂單</h2>
  <p :class="{ paid }">{{ customer }}：{{ total }} 元</p>
  <button @click="pay">結帳</button>
</div>

用 Vue 3.5.44 的 @vue/compiler-sfc（compileTemplate 的預設選項）編譯，得到下面的 render 函式（省略 import）。你可以在官方的 Vue SFC Playground 貼上範本，切到 JS 分頁看到類似的輸出：

const _hoisted_1 = { class: "order" }

export function render(_ctx, _cache) {
  return (_openBlock(), _createElementBlock("div", _hoisted_1, [
    _cache[1] || (_cache[1] = _createElementVNode("h2", null, "今日訂單", -1 /* CACHED */)),
    _createElementVNode("p", {
      class: _normalizeClass({ paid: _ctx.paid })
    }, _toDisplayString(_ctx.customer) + "：" + _toDisplayString(_ctx.total) + " 元", 3 /* TEXT, CLASS */),
    _createElementVNode("button", {
      onClick: _cache[0] || (_cache[0] = (...args) => (_ctx.pay && _ctx.pay(...args)))
    }, "結帳")
  ]))
}

函式名稱前面的底線、_openBlock、_cache 這些先不用管，後面「不會很慢嗎」那一節會回來解釋。現在只看對應關係：範本裡的每一種寫法，在 render 函式裡都變成了普通的 JavaScript。不用背函式名稱，看懂這張表就好：

<p>…</p>createElementVNode("p", props, children)：建立一個 vnode
{{ customer }}toDisplayString(_ctx.customer)：轉成字串，當成文字
:class="{ paid }"{ class: normalizeClass({ paid: _ctx.paid }) }：普通的 props 物件

表的最後兩列不在上面的範例裡，但值得記住：v-for 編譯出來就是一個 map，v-if 就是一個三元運算。範本沒有魔法，它只是 JavaScript 的另一種寫法。

這段程式也解釋了 render 為什麼是 effect。render 裡的 _ctx.paid、_ctx.customer 都是在讀元件的資料：讀 paid 時被 track，之後改 paid 就會 trigger 這個元件重新渲染。哪些資料會讓元件重新渲染，取決於 render 執行時讀了什麼，跟第 2 課的 effect 一模一樣。

既然範本最後只是變成一個回傳 vnode 的函式，你也可以跳過範本，直接手寫 render 函式。Vue 公開了建立 vnode 的函式 h()，名字來自 hyperscript，意思是「用 JavaScript 產生 HTML 結構的腳本」：

import { h } from 'vue'

// 等同 <p class="price">拿鐵 110 元</p>
h('p', { class: 'price' }, `${name} ${price} 元`)

真正的 vnode 欄位更多，其中兩個跟這課的 bug 直接有關。一個是 key，就是 v-for 上寫的那個值，下一節的主角。另一個是 el：掛載之後，它指向這個 vnode 對應的那個真正 DOM 元素。Vue 決定重用一個舊元素時，做的事就是把舊 vnode 的 el 交給新 vnode，再把差異改到這個元素上。其他還有 component（元件實例）、patchFlag（講效能那一節會看到）等欄位，但核心就是 type、props、children。

現在知道每次重新渲染都會得到一棵新的 vnode 樹，而每個舊 vnode 身上掛著一個真正的 DOM 元素。剩下的問題是：新樹和舊樹要怎麼比，Vue 才知道哪個舊元素該交給哪個新 vnode？

刪掉美式咖啡之後，Vue 怎麼對應新舊兩列？

比對新舊兩個 vnode 時，Vue 第一個問題是：它們是不是「同一個節點」？Vue 3.5.44 的判斷是 type 相同，而且 key 相同（runtime-core 的 isSameVNodeType）。答案決定了後面怎麼做：

  • 不是同一個：舊的整個卸載，DOM 刪掉、子元件的狀態丟掉；新的整個重新掛載。例如 <div> 換成 <section>，或元件 A 換成元件 B。
  • 是同一個：沿用舊的 DOM 元素，比對 props，只改變了的屬性；再比對 children。

這條規則的道理是：type 不同的兩個節點，例如一個 <div> 和一個 <section>，DOM 元素不可能互相轉換，只能重建；type 相同就值得重用，改幾個屬性比重建便宜，元素自己的狀態（輸入框裡的字、焦點）也能保留。

難處在 children 是一個列表的時候。訂單明細刪掉美式咖啡前有三個 <li>，刪掉後新的 vnode 樹只有兩個。三個舊 <li> 的 type 全都是 li，光看 type 分不出誰是誰；Vue 也不能比內容，因為「內容不一樣」正是 patch 要去改的東西，不能拿來判斷身分。Vue 需要一個額外的資訊告訴它「新的這一列，就是舊的那一列」，這就是 key 的工作。

先看沒寫 key 的情況。沒寫 key 時，每個 vnode 的 key 都是 null，彼此「相同」。Vue 3.5.44 的編譯器會把這種 v-for 標成沒有 key 的列表，執行時只能按位置對應（runtime-core 的 patchUnkeyedChildren）：新的第 0 項對舊的第 0 項，新的第 1 項對舊的第 1 項，多出來的舊元素卸載。

Vue 官方文件把這種做法叫就地更新（in-place patch）：順序變了也不移動 DOM 元素，而是把每個位置上的元素改成「新資料在這個位置該顯示的內容」。官方文件也寫明了它的限制：只適合畫面不依賴子元件狀態或暫時的 DOM 狀態的列表。暫時的 DOM 狀態指的是存在 DOM 元素自己身上、Vue 不知道的東西，例如輸入框裡打的字（沒有用 v-model 綁到資料時）、焦點、捲動位置。Vue 改的是它從 vnode 知道的內容，這些狀態它管不到，於是留在原來那個元素上。

用 index 當 key，效果跟不寫一模一樣。刪掉第一筆後，拿鐵從 index 1 變成 index 0，Vue 認為「key 0 還在，只是內容變了」，於是把原本美式咖啡那個 <li> 的文字改成拿鐵。<li> 裡的輸入框是同一個元素，打過的字還在原位：

你可能會想：我的備註欄都是 v-model="item.note"，綁在品項資料上，還會出事嗎？文字本身不會錯位。v-model 讓備註變成 Vue 知道的資料：重新渲染時，Vue 會把每個位置上新 vnode 綁的值寫回輸入框（Vue 3.5.44 的 vModelText 在更新前比對 el.value 和綁定值，不同就改寫）。key 是 index 時，原本美式咖啡那個輸入框會被寫上拿鐵的「少冰」，原本拿鐵那個輸入框會被寫上可頌的空字串，畫面上的字跟著資料走。

但被重用的仍然是錯的元素，v-model 只救回了「值」。焦點、游標位置、選取範圍這些存在輸入框元素身上、沒有綁到資料的狀態，還是留在原來那個元素上：店員正在拿鐵的備註欄打字時，另一台裝置同步刪掉了美式咖啡，焦點會留在同一個輸入框，而那個輸入框現在顯示的是可頌。所以 key 的問題不會因為用了 v-model 就消失，只是從「字跑掉」變成比較不顯眼的錯位。開場的 bug 只是在備註還沒綁到資料時最容易看見。

子元件的情況也一樣。如果每一列不是單純的 <li>，而是一個 <OrderRow> 元件，它內部沒有綁到外部資料的 ref（例如「客製選項展開中」）就是子元件狀態，跟焦點一樣是 Vue 不會照資料重新寫入的東西。key 用 index 時，子元件實例被留在位置上重用，只換了 props，展開狀態一樣會跟著錯位。

反過來看 key 用 id 的那一行：刪掉美式咖啡後，key 2 和 key 5 都還在，Vue 找到原本的兩個元素，只把 key 1 那個卸載。拿鐵那個 <li> 原封不動，「少冰」跟著拿鐵走。開場的 bug 到這裡就完整解釋了：Vue 沒有搬備註，它只是照 key 重用元素，而 index 告訴它的對應是錯的。下一個問題是，什麼值才配當 key？

key 該用什麼？

上一節的結論是：key 要讓 Vue 在每次渲染時認出「同一筆資料」。照這個標準，選 key 的規則都推得出來：

  • 用資料本身穩定、唯一的身分：資料庫的 id、商品編號。同一筆資料每次渲染都要得到同一個 key。
  • 不要用 index：index 是「這筆資料現在排第幾」，不是「這是哪一筆」，刪除、插入、排序後同一筆資料的 index 會變。`${item.name}-${index}` 也一樣，只要 index 變了，key 就變了。
  • 不要用 Math.random()：每次渲染 key 都不同，Vue 認為每一列都是新的，全部卸載再重建，輸入框內容、子元件狀態、焦點全部消失，效能也最差。
  • 同一層的 key 不能重複：兩列 key 相同，Vue 就無法分辨誰是誰。Vue 3.5.44 在開發模式會警告「Duplicate keys found during update」，對應會出錯。品名、價格這類欄位看起來像身分，但同一張訂單可能點兩杯拿鐵，它們就會重複。
  • 還沒存進資料庫、沒有 id 的新項目：建立時就產生一個前端 id（例如 crypto.randomUUID()），存在項目上，之後一直用它。在建立時產生一次，跟每次渲染都產生新值是兩回事。

key 的規則也可以反過來利用：key 變了，Vue 就認為這是另一個節點，把舊的卸載、建立全新的。想把一個元件的狀態整個重置，例如換了訂單就清空表單，可以寫 <OrderForm :key="orderId" />：orderId 一換，舊表單連同裡面打到一半的內容一起卸載，新的表單從頭建立，不用寫一堆 watch 去清空每個欄位。第 21 課會用這招讓出錯的區塊重新來過。

那 index 什麼時候可以用？回到就地更新的限制：列表只顯示文字、不會刪除中間項或重新排序、每一列沒有輸入框和有狀態的子元件時，就地更新的結果是對的。但列表的需求常常會變，今天只顯示文字的列表，下個月可能就加了輸入框或拖曳排序，所以用 id 是比較安全的預設。key 對了之後，Vue 怎麼用最少的 DOM 搬動完成重新排序，屬於演算法細節，見課末「補充與查表」。

寫 v-for 時還有一個常見錯誤跟 key 無關，但同樣是「v-for 怎麼寫才對」：菜單列表只想顯示還沒賣完的品項，於是把 v-if 和 v-for 寫在同一個元素上。用第二節的表就能推出為什麼不行：v-if 編譯成三元運算，v-for 編譯成 renderList，也就是一個 map。兩個寫在同一個元素上時，Vue 3 讓 v-if 先處理，編譯結果是三元運算包在外面、renderList 在裡面，大致是 !item.soldOut ? renderList(items, item => …) : createCommentVNode("v-if")。判斷條件時還沒進入 map，item 這個變數根本還沒被建立，所以讀不到。這兩個不要寫在同一個元素上，改成下面兩種寫法之一：

<!-- 錯：v-if 先執行，這時還沒有 item -->
<li v-for="item in items" v-if="!item.soldOut" :key="item.id">{{ item.name }}</li>

<!-- 對：先用 computed 過濾 -->
<li v-for="item in available" :key="item.id">{{ item.name }}</li>
const available = computed(() => items.value.filter(item => !item.soldOut))

<!-- 或把 v-for 移到外層的 <template> -->
<template v-for="item in items" :key="item.id">
  <li v-if="!item.soldOut">{{ item.name }}</li>
</template>
💡 實務上：key 的 bug 常在「刪除、排序、拖曳」之後才出現
這類 bug 很少在開發時被發現，通常是客服轉來「我改的是 A，結果存到 B」：訂單明細刪掉一列、購物車調整順序、後台拖曳排序商品之後才錯位，就像開場的「少冰」。所以 code review 看到 v-for，資深工程師會先看 key 從哪來，再問兩個問題：這個 id 在這份列表裡真的唯一嗎（例如把兩支 API 的資料合併成一個列表，兩邊的 id 可能撞號，要加前綴區分）？列表會不會刪除中間項、排序或拖曳？專案通常也會開 eslint-plugin-vue 的 vue/require-v-for-key，讓忘了寫 key 的地方在編輯器和 CI 裡就被標出來。

備註的 bug 修好了。但回頭看整個流程，會冒出一個疑問：店員每刪一筆，整個元件的 render 就重跑一次，產生一棵完整的新 vnode 樹，再跟舊樹整棵比對。訂單頁很大的時候，這樣不會很慢嗎？

每次重跑 render、整棵樹比對，不會很慢嗎？

如果比對真的要逐一走過每個節點、比較每個屬性，畫面越大就越慢。一般的虛擬 DOM 實作確實是這樣，因為它不知道哪些部分會變，只能全部比。

Vue 的不同之處在於它同時掌握編譯器和執行時。編譯範本時，編譯器看得出哪些部分永遠不會變（例如標頭裡的「今日訂單」），哪些部分會變、會怎麼變（例如顧客名字和 paid 的 class），就在 render 函式裡留下提示，讓執行時的比對跳過不會變的部分。官方文件稱這種做法為 Compiler-Informed Virtual DOM，列出三種最佳化，在第二節的編譯結果裡都看得到。這就是當時先略過的 _cache、3 /* TEXT, CLASS */、_openBlock：

名稱做了什麼在編譯結果裡
Cache Static（快取靜態內容）完全沒有綁定的部分，第一次建立 vnode 後就快取起來，之後重用同一個 vnode，比對時直接跳過。連續很多個靜態元素還會合併成一個用 innerHTML 掛載的靜態節點_cache[1] || (_cache[1] = …"今日訂單"…)
Patch Flags（更新標記）patch flag 是編譯器標在 vnode 上的數字，告訴執行時這個元素只有哪些部分會變，比對時只看那些部分3 /* TEXT, CLASS */：這個 <p> 只要比文字和 class；<button> 的 onClick 已被快取、不會變，所以沒有 patch flag，更新時完全不比
Tree Flattening（攤平樹）把範本切成結構穩定的「區塊」（block），每個區塊記下底下所有動態節點，更新時只走這份攤平的清單，不走整棵樹。v-if、v-for 會開新的區塊_openBlock()、_createElementBlock(…)

三種裡最不直觀的是 Tree Flattening，用第二節的訂單標頭來看。外層的 <div> 用 _openBlock() 和 _createElementBlock 建立，它就是一個區塊（block）。建立區塊時，Vue 會把底下帶 patch flag 的後代 vnode 收進一份清單，存在這個 vnode 的 dynamicChildren 欄位。標頭裡：<h2> 被快取了，標記是 -1 /* CACHED */，不收；<button> 沒有 patch flag，不收；只有 <p> 的標記是 3，收進去。所以這個區塊的清單只有 [p]，更新時 Vue 直接比對這一個節點，不必逐一走過 div 的三個子節點。如果這個 <p> 包在好幾層 <div> 裡，清單裡一樣只有它，中間那幾層完全不比，這就是「攤平」的意思：不管動態節點藏得多深，都直接列在區塊的清單上。

這份清單能成立，前提是區塊底下的結構固定：每次渲染，動態節點的數量和順序都一樣，新舊兩份清單才能一個對一個比。v-if 和 v-for 打破了這個前提：v-if 讓一塊內容出現或消失，v-for 讓列表的長度和順序改變，事先沒辦法列成固定的清單。所以編譯器讓它們各自開一個新的區塊：外層區塊把整個 v-if 或 v-for 當成清單上的一個節點，裡面變動的部分由它自己的區塊和上一節的 key 比對處理。

三種最佳化合起來，更新時 Vue 不是走過整棵樹，而是只走一份記錄了動態節點的清單，每個節點也只比它會變的那幾個部分。訂單頁再大，靜態的標題、說明文字、按鈕都不會進入比對。

這也解釋了為什麼範本比手寫 render 函式容易最佳化：範本的結構固定，編譯器看得懂；手寫的 h() 是任意 JavaScript，編譯器無從分析，只能全部比對。所以除非需要範本表達不了的高度動態結構，例如依設定檔產生任意元件樹，否則用範本。Vue 3.6 另外有一種不使用虛擬 DOM 的編譯模式，見課末「補充與查表」；這門課以 3.5 為準，這課講的規則（包括 key）都適用。

編譯器的最佳化只是讓比對少做事，比對的規則沒有變：同一個位置上的新舊 vnode，仍然先問第三節那個問題，「是不是同一個節點」。v-if 的條件一變，那個位置上的節點就整個換掉，套的正是這條規則。這帶到訂單明細上的下一個需求。

每列的客製選項面板，該用 v-if 還是 v-show？

訂單明細的每一列還有一個「客製選項」面板，可以調甜度、冰塊，店員點一下品名就展開或收合。讓元素出現或消失有兩種寫法，v-if 和 v-show，看起來效果一樣，但在 Vue 內部走的是完全不同的路。

v-if 的運作，用前面學到的規則就能推出來。第二節的表裡，v-if 編譯成三元運算：條件成立時是元素的 vnode，不成立時是一個註解節點佔位。條件從成立變成不成立，同一個位置上的 vnode 從元素換成註解節點，type 不同，照第三節的規則就是「不是同一個節點」：舊的整塊卸載，連同裡面的子元件和它們的狀態。條件再變回成立時，整塊重新掛載，子元件從頭建立。這跟換 key 重置元件是同一條規則。

v-show 則完全不碰結構：元素一直都在，Vue 只切換它的 CSS display: none。整理成表：

v-ifv-show
條件不成立時完全不渲染，只留一個註解節點佔位照樣渲染，只設 display: none
切換時卸載或重新建立整塊 DOM 與子元件，子元件狀態會重置只改 CSS
成本切換成本高，初次渲染成本低（條件不成立就不做事）初次渲染成本高，切換成本低
適合條件很少改變；或想在隱藏時讓子元件真的被卸載（停止計時器、釋放資源）頻繁開關，例如菜單分類的展開收合

客製選項面板會被店員一直開開關關，用 v-show 每次只改一個 CSS 屬性；用 v-if 每次都要卸載、重建面板裡的整塊 DOM 和子元件。反過來，像「只有店長才看得到的報表區塊」這種一進頁面就決定、之後很少變的條件，用 v-if：條件不成立時根本不渲染，省下初次渲染的成本。

💡 實務上：對話框要不要保留草稿，決定用 v-if 還是 v-show
咖啡店後台的「新增商品」對話框：如果希望每次打開都是空白表單，用 v-if，關掉時表單元件被卸載，狀態自然清空；如果希望店員關掉再打開還看得到剛打一半的內容，用 v-show 或把草稿存到外層。分頁（tab）切換也是同樣的取捨：v-if 每次切回來都會重新掛載、可能重新打 API。另外要記得，v-show 隱藏的內容還在 DOM 裡，開發者工具打開就看得到，不能拿來「藏」沒有權限的資料，權限要在伺服器端擋（第 20 課）。

面板和每一列上都顯示著備註。到目前為止，備註都是店員自己打的；但如果備註來自顧客的線上點單，裡面寫的不是「少冰」，而是一段 HTML 呢？

顧客打的備註顯示在後台，安全嗎？

假設顧客在線上點單的備註欄輸入 <img src=x onerror=alert(1)>，店員後台用 <p>{{ note }}</p> 顯示。如果瀏覽器把這串字當成 HTML 解析，就會建立一個 <img> 元素；圖片網址 x 載入失敗，觸發 onerror，裡面的 JavaScript 就在店員的瀏覽器裡執行了。

這就是 XSS（跨站腳本，cross-site scripting）攻擊：攻擊者讓自己寫的程式在你的網站上執行。這段程式跑在店員已登入的後台頁面裡，能做到店員能做的所有事：讀走訂單和顧客資料、冒用店員身分操作。範例裡的 alert(1) 只是證明「程式跑得起來」，真正的攻擊會換成送出資料的程式碼（auth 課第 7 課深入）。

用 {{ }} 不會出事，原因在第二節的編譯結果裡就看得到：插值經過 toDisplayString 變成字串，最後用 textContent 或文字節點放進 DOM。用這兩種方式放進去的內容，瀏覽器一律當成文字，不會解析成 HTML，畫面上就是那串字本身。:title="note" 這類屬性綁定也一樣，是設定屬性值，不會被當成 HTML。

Vue 能這麼做，是因為它手上有 DOM，可以直接把字串放進文字節點。伺服器端產生 HTML 字串時沒有 DOM 幫忙，輸出的就是一整段要交給瀏覽器解析的文字，顧客的備註如果原樣接進去，就會被當成標籤。這時要自己跳脫（escape）：把 &、<、>、"、' 換成 &amp;、&lt;、&gt;、&quot;、&#39; 這類實體（entity）。實體是 HTML 表示特殊字元的寫法，瀏覽器顯示成原本的字元，但不會把它當成標籤或屬性的開頭結尾。練習 1 就是把 vnode 樹轉成跳脫過的 HTML 字串，第 24 課的 SSR 會用到。

v-html="note" 會把字串原樣當成 HTML 插入（等於設定 innerHTML），上面那串 <img> 就會執行。Vue 官方的安全指南：不要把使用者提供的內容放進 v-html，也不要把它當成範本來編譯。真的要顯示使用者寫的格式化內容，先經過可靠的 HTML 清理（sanitize）套件。第 25 課會把這些整理成專案的安全規則。

所以訂單明細和後台顯示備註，用 {{ }} 就是安全的寫法，不需要額外處理。要小心的是有人為了「讓備註可以換行、加粗」而改成 v-html。

💡 實務上：v-html 最常出現在「後台編輯器寫的內容」
真正需要 v-html 的情況通常是：商品說明、最新消息、公告這類由後台富文字編輯器或 Markdown 產生的 HTML。遇到時資深工程師會先問：這段內容誰能寫？只有內部編輯，還是顧客也能輸入？只要來源不是完全可信，顯示前就用 DOMPurify 這類維護良好的套件清理，不要自己寫正規表示式過濾。很多團隊會開 eslint-plugin-vue 的 vue/no-v-html 規則，每個 v-html 都會被標出警告，真的要用就得加註解關掉並寫明原因，code review 時一眼就看得到。

練習

練習 1：寫 renderToString(node)，把 vnode 樹轉成 HTML 字串（h 已經寫好）。規則：

  • 元素輸出 <type 屬性>子節點</type>；VOID 裡的元素（br、img、input）沒有子節點和結尾標籤，只輸出 <input 屬性>。
  • children 是字串時當成文字；是陣列時逐一轉換、接起來，陣列裡的字串也是文字。
  • 屬性依物件裡的順序輸出，每個前面一個空白：字串和數字輸出 name="值"；true 只輸出名稱（disabled）；false、null、undefined 不輸出。
  • 文字和屬性值都要跳脫：& → &amp;、< → &lt;、> → &gt;、" → &quot;、' → &#39;。

練習 2：寫 patchChildren(oldNodes, newVnodes, ops)，用 key 更新一個列表。oldNodes 是目前畫面上的節點（每個有 key），newVnodes 是新的 vnode 列表。規則：

  • 新 vnode 的 key 在舊節點裡找得到：重用那個舊節點，呼叫 ops.patch(舊節點, 新vnode) 更新內容。
  • 找不到：呼叫 ops.mount(新vnode)，用它回傳的新節點。
  • 舊節點的 key 在新列表裡不見了：呼叫 ops.unmount(舊節點)。
  • 回傳依新順序排列的節點陣列，重用的節點必須是原本那個物件（不是複製出來的）。

練習 3：OrderItemList.vue 是訂單明細，每一列有品名、「備註」輸入框（沒有 v-model，打的字只存在輸入框本身）和「刪除」按鈕，下面有「依價格排序」按鈕。起始版用 :key="index"，所以在拿鐵那列打「少冰」、刪掉第一列的美式咖啡之後，「少冰」跑到可頌那列；排序後也一樣錯位。改成穩定的 key，讓每個品項的 <li> 在刪除、排序後都還是同一個 DOM 元素。注意同一張訂單可能點兩杯拿鐵，品名和價格都會重複。不要加 v-model，這題練的是 key。

練習 4：v-for 用 index 當 key，什麼情況下結果是對的？

✓ index 當 key 等於按位置就地更新：同一個位置的元素被改成新資料的內容。如果每一列的畫面完全由資料決定（沒有輸入框裡打的字、沒有子元件的內部狀態），而且順序不會變，結果是對的。Vue 不會自己找對應，它只看 key；出錯與否也跟筆數無關。所以 b 太絕對，但 id 仍然是比較安全的預設，因為需求常常變。

練習 5：點餐頁有一個很大的「客製化選項」面板，店員會一直按按鈕開開關關。用 v-if 還是 v-show？

✓ 官方文件：v-if 的切換成本高、v-show 的初次渲染成本高。頻繁開關時，v-if 每次都要卸載、重新建立整塊 DOM 和子元件（子元件狀態也會重置），v-show 只改 CSS。v-if 只在「條件很少改變」或「希望隱藏時真的卸載」時比較省。c 錯：v-if 不成立時只留一個註解節點，元素根本不存在。

練習 6：範本寫 <p>{{ note }}</p>，顧客填的 note 是 <img src=x onerror=alert(1)>，會發生什麼事？

✓ 插值經過 toDisplayString 後當成文字放進 DOM（textContent／文字節點），瀏覽器不會把它解析成 HTML。b 是用 v-html 才會發生的事，所以使用者提供的內容不能放進 v-html。Vue 也不會偷偷刪掉內容，它只負責「當成文字顯示」。

常見錯誤

  • 用 index 當 key：刪除、插入、排序後同一筆資料的 key 變了，輸入框的內容和子元件狀態留在原位置，跑到別的資料上。用資料的 id。
  • 用 Math.random() 或每次渲染都會變的值當 key：每次渲染都全部卸載重建，狀態和焦點消失，效能最差。沒有 id 的新項目，在建立時產生一次並存起來。
  • 同一層的 key 重複：Vue 會警告「Duplicate keys found during update」，對應錯亂。檢查資料是否真的唯一，品名、價格這類欄位通常不是。
  • v-if 和 v-for 寫在同一個元素：v-if 先執行，讀不到 v-for 的變數。用 computed 先過濾，或把 v-for 移到外層 <template>。
  • 以為虛擬 DOM 一定比直接操作 DOM 快：它多了建立 vnode 和比對的成本。它的價值是讓你用宣告式的寫法，效能也夠好；真的遇到效能問題，先量測（第 23 課）。
  • 想重置元件狀態，卻寫一堆 watch 去清空每個欄位：直接換 key（:key="orderId"），讓 Vue 建立全新的元件。
  • 把使用者輸入放進 v-html：等於設定 innerHTML，會執行裡面的腳本。用 {{ }}；一定要顯示 HTML 就先用可靠的套件清理。

補充與查表

主線用不到、但查資料或讀原始碼時會遇到的細節，查表用，不用背。

  • 有 key 的列表怎麼少搬 DOM：Vue 對有 key 的列表會先比對頭尾相同的部分，中間亂序的部分再用「最長遞增子序列」（longest increasing subsequence）算出哪些元素不用移動，盡量少搬 DOM（runtime-core 的 patchKeyedChildren）。這些細節不需要背，記住結論：key 對了，Vue 只會移動、新增、刪除真正改變的元素。
  • Vapor Mode：Vue 3.6（目前是 RC 候選版）加入了 Vapor Mode：一種完全選用、不使用虛擬 DOM 的編譯模式。這門課以 3.5 為準，虛擬 DOM 的規則（包括 key）都適用。

小結

  • 範本 → 編譯成 render 函式 → 產生 vnode 樹 → 掛載成 DOM。render 是 effect，資料改變就重跑，新舊 vnode 樹比對（patch）後只更新差異，能重用的舊 DOM 元素就重用。
  • vnode 是 { type, props, children } 這樣的普通物件，el 指向它對應的 DOM 元素；v-for 編譯成 map、v-if 編譯成三元運算、@click 變成 onClick prop。
  • patch 判斷「同一個節點」靠 type 和 key。沒有 key 或用 index 時按位置就地更新，輸入框這類 DOM 狀態和子元件狀態會錯位，這就是「少冰」跑到可頌的原因。key 用穩定、唯一的 id；換 key 可以重置元件。
  • 編譯器的三種最佳化：Cache Static、Patch Flags、Tree Flattening，讓更新只比會變的部分。所以範本比手寫 render 函式容易最佳化。
  • v-if 切換時 vnode 的 type 改變，整塊卸載重建，適合很少改變的條件；v-show 只切換 CSS，適合頻繁開關。v-if 不要和 v-for 寫在同一個元素。
  • {{ }} 和屬性綁定都會被當成文字或屬性值，不會執行；v-html 會。伺服器端產生 HTML 字串時要自己跳脫。
