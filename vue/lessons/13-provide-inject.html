階段 4：重用與型別 · 第 13 課

provide/inject：跨層傳遞與依賴注入

咖啡店的後台可以切換門市：總店和分店的價格標籤、訂單標題都要顯示目前是哪一家。門市在最外層的 App 選，真正用到它的 PriceTag 在第 4 層。於是 Layout、MenuPage、ProductList 這三層明明用不到門市，也得宣告 storeId 這個 prop、再原封不動往下傳。哪天要多傳一個「營業中」，這三個檔案又要各改一次。

這課從頭到尾做同一件事：替後台做出「目前門市」這個功能。先讓第 4 層直接拿到門市，再讓它有型別、切換時會更新、只有一個地方能改；接著處理切換門市後要抓菜單的 API client，以及門市頁裡的分頁元件。用到的工具是 Vue 的 provide／inject：祖先元件把值放出來，任何一層後代直接拿，中間的元件不用經手。

這課的路線：
  1. 為什麼中間三層要一直轉手、怎麼讓第 4 層直接拿到門市：逐層傳遞的代價，以及 provide／inject 的最小用法和它找值的規則（開場問題的最小答案）。
  2. key 寫錯、忘了放提供者怎麼第一時間知道：用帶型別的 key 包成 useCurrentStore()。
  3. 切換門市時後代怎麼跟著更新、誰可以改門市：provide 響應式的值，再用 readonly 只留一個修改入口。
  4. 切換門市後要抓菜單，元件該不該自己 import API client：用 app.provide 和外掛做依賴注入，測試時換成假的。
  5. 門市頁的分頁、以及最後怎麼選：<Tabs> 和 <Tab> 怎麼共享選取；props、provide／inject、Pinia 各適合什麼資料。
這課會用到：
  • 第 9 課的 props 與單向資料流：資料由父元件用 props 往下傳，子元件要改就發事件請擁有者改。
  • 第 12 課的 composable：以 use 開頭、在 setup 裡同步呼叫的函式，封裝一段有狀態的邏輯。

為什麼中間三層要一直轉手門市？

先把開場的元件樹畫出來。App 擁有「目前門市」，PriceTag 要顯示它，中間隔著 Layout、MenuPage、ProductList。用第 9 課的 props，唯一的做法是每一層都宣告 storeId、再傳給下一層。

這種寫法叫逐層傳遞（prop drilling）：為了讓很深的元件拿到一份資料，中間每一層都要接收這個 prop、再傳給下一層。左半張圖就是現在的後台。

代價有兩個。第一是改動範圍：PriceTag 多需要一份「營業中」，Layout、MenuPage、ProductList 都要加 prop、加綁定，三個跟這個需求無關的檔案進了同一個 commit。第二是元件的介面被污染：ProductList 的 props 裡出現 storeId，讀程式的人會以為它拿門市做了什麼事，其實它只是轉手。中間的元件因此知道了它不需要知道的東西。

逐層傳遞不一定是壞事。只有兩三層、而且中間的元件本來就會用到時，props 最清楚：看元件的宣告就知道它需要什麼，資料從哪裡來也一目了然。問題出在「很多層」和「中間層用不到」同時發生的時候，後台的門市正是這種情況。所以我們要的是右半張圖：App 把門市放出來，PriceTag 直接拿，中間三層完全不用知道。

怎麼讓第 4 層直接拿到門市？

右半張圖要靠一對函式完成。provide（提供）是祖先元件把一個值登記在某個 key 底下；inject（注入）是後代元件用同一個 key 把它拿出來。key 就像一個約定好的名字，提供的一方和使用的一方只要對上同一個名字，中間隔幾層都不影響。

<!-- App.vue（提供者） -->
<script setup lang="ts">
import { provide, ref } from 'vue'
const store = ref({ id: 1, name: '總店' })
provide('currentStore', store)
</script>

<!-- PriceTag.vue（任何一層後代） -->
<script setup lang="ts">
import { inject } from 'vue'
const store = inject('currentStore')   // 拿到的就是 App 的那個 ref，不會自動拆開
</script>

Layout、MenuPage、ProductList 一行都不用改，開場的問題到這裡已經有最小的答案。但要放心使用，得先知道 inject 是怎麼「找到」App 的那個值，因為接下來的幾條規則都是從這個機制推出來的。

每個元件實例身上都有一個存放 provide 值的物件。元件沒有 provide 任何東西時，它直接沿用父元件的那一個；第一次 provide 時，Vue 才替它建立一個新物件，並把這個新物件的原型（prototype）設成父元件的那一個。所以整棵元件樹的 provide 值串成一條「往祖先方向」的原型鏈。inject 從父元件的那個物件開始查 key，查不到就沿著原型鏈往上，一路查到 app 層級。（以上是 Vue 3.5.44 原始碼 runtime-core 的做法。）

從這個機制可以推出三條規則，每條都用門市的例子看一次（Vue 3.5.44 實測）：

  • 只往祖先找：鏈只往祖先方向串，所以兄弟元件 provide 的值，另一個兄弟 inject 不到，Vue 印出 injection "s" not found. 並回傳 undefined。provide 不是全域的，它只對自己這棵子樹有效。例如門市切換器如果放在 Header 裡 provide，旁邊的 MenuPage 是 Header 的兄弟，拿不到；門市必須由它們共同的祖先 App 提供。
  • 最近的祖先優先：好幾層都 provide 同一個 key 時，查找先碰到的是離自己最近的那一個。所以中間的元件可以為自己的子樹「蓋掉」上面的值，例如後台有一個「分店對照」區塊，在區塊的根元件 provide 分店，區塊裡的 PriceTag 就固定顯示分店，區塊外照舊是 App 選的門市。
  • 看不到自己 provide 的值：inject 從父元件開始找，不看自己。同一個元件先 provide 再 inject 同一個 key，拿到的是祖先的值（或預設值）。App 自己要顯示門市，就直接用手上的 store 變數。

還有一種情況是根本沒有人提供。例如 PriceTag 被拿去另一個沒有門市概念的頁面重用，這時可以給預設值，寫在第二個參數：

const theme = inject('theme', 'light')                          // 沒有提供者就用 'light'，也不會警告
const cache = inject('cache', () => new Map(), true)            // 第三個參數 true：第二個參數是工廠函式，需要時才呼叫

預設值是物件或建立成本高的東西時用工廠函式。直接寫 inject('cache', new Map()) 的話，每次 setup 都會先建立一個 Map，就算有提供者、根本用不到也一樣。改成工廠函式之後，每個元件拿到自己的一份，而且有人提供時根本不會建立。

除了怎麼找值，還有一個使用上的限制：inject 能寫在哪裡。inject 和 provide 一樣，要在 setup（或 <script setup>）裡同步呼叫。原因和第 12 課的 composable 相同：Vue 在執行某個元件的 setup 期間，會記住「目前正在 setup 的是哪個元件」，inject 就是靠它找到那個元件的父元件、再沿著上面說的鏈往上查。setup 一結束這個記錄就清掉了，所以放進 setTimeout、await 之後或事件處理函式裡，Vue 已經不知道是誰在問，會印出 inject() can only be used inside setup() or functional components. 並回傳 undefined。要在之後用到，就在 setup 先 inject 出來存著。

到這裡 PriceTag 已經拿得到門市。但這段程式還有兩個隱患：key 是一個隨手寫的字串，inject('currentStore') 的型別也不知道是什麼；而且哪天有人把 PriceTag 放到沒有提供者的地方，它只會安靜地拿到 undefined。下一節先處理這兩件事。

key 寫錯、忘了放提供者，怎麼在第一時間知道？

先看字串 key 的兩個問題。第一，會撞名：你的 'currentStore' 和某個套件的 'currentStore' 是同一個 key，依照上一節「最近的祖先優先」，近的那個會蓋掉遠的，PriceTag 可能拿到套件的東西而你完全不知道。第二，沒有型別：inject('currentStore') 的型別是 unknown，只能自己斷言成 Ref<Store>，key 拼錯或斷言錯了，TypeScript 都不會發現。

撞名的解法是換成 Symbol。Symbol 是 JavaScript 的一種原始值，每次呼叫 Symbol('…') 都會產生一個獨一無二的值，就算括號裡的說明文字一樣，兩個 Symbol 也不相等。拿它當 key，別人除非拿到你這個變數，否則不可能碰巧用到同一個 key。

型別的解法是 Vue 提供的 InjectionKey<T>。它是一個帶著型別資訊的 Symbol 型別：你宣告「這個 key 底下放的是 T」，provide 就會檢查你放進去的值是不是 T，inject 也會回傳 T，不用再斷言。

key 寫錯的問題也一起解決了：key 現在是一個 import 進來的變數，不再是字串，拼錯變數名稱在編譯時就會報錯（TypeScript 和 ESLint 都會抓到「找不到這個名稱」）；搭配 InjectionKey<T>，連放錯型別也擋得住。

import type { InjectionKey, Ref } from 'vue'

type Store = { id: number; name: string }
const CURRENT_STORE: InjectionKey<Ref<Store>> = Symbol('CurrentStore')   // 括號裡的字只用來除錯時辨認

provide(CURRENT_STORE, ref({ id: 1, name: '總店' }))   // 放錯型別會報錯
const store = inject(CURRENT_STORE)                  // 型別是 Ref<Store> | undefined

注意回傳型別還帶著 | undefined：TypeScript 只看得到這一個檔案，不知道元件樹上有沒有祖先提供了這個 key。如果照原樣用，每個使用的地方都得寫 store?.value.name 或自己判斷 undefined；更常見的是有人寫 store!.value 硬過，等於把問題藏起來。

資深的做法是把 key 藏起來，只公開兩個函式：一個給提供者用，一個給使用者用。

// current-store.ts
const CURRENT_STORE: InjectionKey<Ref<Store>> = Symbol('CurrentStore')   // 不 export

export function provideCurrentStore(initial: Store) {
  const store = ref(initial)
  provide(CURRENT_STORE, store)
  return store
}

export function useCurrentStore() {
  const store = inject(CURRENT_STORE, null)
  if (!store) throw new Error('useCurrentStore() 必須在 provideCurrentStore() 之下使用')
  return store                                       // 型別是 Ref<Store>，沒有 undefined
}

這樣寫解決了三件事。

第一，錯誤在源頭爆。忘了放提供者時，useCurrentStore() 在 setup 當下就丟錯，錯誤訊息直接說出原因和修法。如果讓它回傳 undefined，PriceTag 要等到模板讀 store.value 時才出錯，訊息是 Cannot read properties of undefined (reading 'value')，堆疊指向渲染函式，你得倒查回去才知道是少了提供者。

第二，inject(KEY, null) 給了預設值 null。上一節說過，有給預設值時，沒有提供者 Vue 不會印 injection … not found 警告（3.5.44 實測）。這樣 console 裡只會出現你自己寫的那一則錯誤，不會先冒出一則 Vue 的警告干擾判斷。用 null 而不是 undefined，是因為 null 讓「我刻意給了預設值」這件事在程式裡看得出來。

第三，key 不外流。key 沒有 export，別的檔案沒辦法繞過這兩個函式偷偷 provide 或 inject。以後要改內部結構（例如下一節要改成唯讀加修改函式），只改 current-store.ts 這一個檔案。提供者自己要用門市，就用 provideCurrentStore() 回傳的那一份，這也順便解決了上一節「看不到自己 provide 的值」的問題。

💡 實務上：你每天用的 useXxx() 很多就是這個模式
vue-router 的 useRoute()、Naive UI 的 useMessage() 底層都是 inject：Naive UI 忘了在外面包 <n-message-provider> 就會直接丟錯，說找不到外層的 provider，跟你寫的 useCurrentStore() 一樣。所以看到「找不到外層提供者」這類錯誤，先檢查元件樹上有沒有對應的提供者，而不是去查 useXxx 本身。自己寫的時候，一個功能一個檔案（例如 current-store.ts），裡面只 export provideXxx／useXxx 兩個函式和需要的型別。Code review 時看到元件直接 inject('字串')，通常就是要請對方改成這個寫法。

型別和錯誤都處理好了，但門市功能的重點是「切換」。店員在 App 選了分店，PriceTag 真的會跟著變嗎？這取決於你 provide 進去的是什麼。

切換門市時，所有後代怎麼跟著更新？

provide 不會幫你把值變成響應式。它只是把你給的東西交給後代，給什麼就是什麼。下面三種寫法，只有最後一種會讓 PriceTag 跟著切換：

// ✗ 普通值：之後改了，後代不知道
let storeName = '總店'
provide('storeName', storeName)       // 交出去的是字串 '總店'
storeName = '分店'                    // 後代拿到的還是 '總店'

// ✗ 普通物件：後代拿到同一個物件，但改它的屬性不會觸發重新渲染
const store = { name: '總店' }
provide('store', store)
store.name = '分店'                   // 畫面還是「總店」（3.5.44 實測）

// ✓ ref（或 reactive、computed）：後代讀 .value 時被追蹤，改了會更新
const store = ref({ id: 1, name: '總店' })
provide(CURRENT_STORE, store)

逐一看原因。第一種，provide 收到的是字串 '總店' 這個值本身；之後讓變數 storeName 指向另一個字串，跟已經交出去的值無關。第二種，後代拿到的確實是同一個物件，所以資料其實改到了；但它是普通物件，沒有第 2 課講的依賴追蹤，PriceTag 渲染時讀 store.name 不會被記下來，改了也沒有人通知它重新渲染。第三種，ref 本身就是響應式的容器，PriceTag 在模板裡讀 store.value.name 時被追蹤，App 改 store.value 就會觸發 PriceTag 更新。

結論是：要讓後代跟著變，provide 的必須是 ref、reactive 或 computed，而且交出去的是「容器」，不是容器裡某一刻的值。前一節的 provideCurrentStore 已經是 provide 一個 ref，所以切換門市沒問題。

可是能更新之後，新的問題出現了：既然交出去的是可寫的 ref，任何一層後代都能寫 store.value = …。下一節處理誰可以改。

誰可以改門市？

把可寫的 ref 交出去，等於讓整棵子樹的每個元件都有權限改門市。哪天門市莫名其妙變了，你得搜遍整棵子樹找是誰改的，而且 provide／inject 的使用者不會出現在元件的 props 宣告裡，搜起來比 props 還難。這跟第 9 課的單向資料流是同一個道理：資料由擁有者修改，其他人要改就請擁有者改。

做法是用第 4 課的 readonly：交出去的是唯讀版本，另外提供修改用的函式。我們把 provideCurrentStore 改成提供一個 context 物件，裡面一個是唯讀的門市，一個是唯一的修改入口。provide 的東西換了形狀，有三處要跟著改：

  • key 的型別：從 InjectionKey<Ref<Store>> 改成 InjectionKey<CurrentStore>，其中 CurrentStore = { store: Readonly<Ref<DeepReadonly<Store>>>; switchStore: (id: number) => void }（DeepReadonly 是 Vue 匯出的型別，對應 readonly() 連內層屬性都唯讀）。useCurrentStore() 的回傳型別也就跟著變成 CurrentStore。
  • 參數：因為之後要用 id 切換門市，參數從整個門市物件 initial 改成 initialId。findStore(id) 是這個檔案裡的小函式：從門市清單用 id 找出門市，找不到就丟錯（練習 1 要求給不存在的 id 要丟錯，就是在這裡做）。
  • 使用的一方：PriceTag 改寫成 const { store, switchStore } = useCurrentStore()，不需要切換的元件只取 store 就好，模板照樣讀 store.value.name。
export function provideCurrentStore(initialId: number) {
  const store = ref(findStore(initialId))
  const context = {
    store: readonly(store),                              // 讀得到最新的值，寫不進去
    switchStore: (id: number) => { store.value = findStore(id) },   // 唯一的修改入口
  }
  provide(CURRENT_STORE, context)
  return context
}

readonly(store) 回傳的是原本 ref 的一個唯讀代理：讀它會讀到最新的值，也照樣被追蹤，所以上一節的更新機制完全不受影響；寫它則會被擋下。可寫的 store 只留在 provideCurrentStore 的閉包裡，外面拿不到。

後代如果寫 store.value = …，寫入不會生效，開發模式印出 Set operation on key "value" failed: target is readonly.。readonly 是深層的，store.value.name = … 也一樣擋得住。所有修改都經過 switchStore，要驗證 id、記錄 log、同步到網址，都只要改這一個函式。

型別上也有一道檢查：readonly(ref(x)) 回傳的 ref 和裡面的屬性都是唯讀的，store.value = … 在編譯時就報錯。但型別可以被 as any 繞過，執行時的 readonly 才是最後一道防線，兩邊都要有。

💡 實務上：唯一的修改入口，之後的需求都會往這裡加
咖啡店後台上線後，切換門市很快會長出這些需求：店員只能切到自己有權限的門市、切換後重新抓該店的訂單、把門市記在網址上讓重新整理後還在。這些全都只要加在 switchStore 裡，元件不用動。注意前端的權限檢查只是讓畫面合理，真正擋住越權的是後端 API，兩邊都要做。如果一開始就把可寫的 ref 交出去，這些邏輯會散在好幾個元件裡，漏掉一個就是 bug。

上面提到「切換後重新抓該店的資料」。要抓門市的資料，就要用 API client，於是下一個問題是：元件要從哪裡拿到這個 client？

切換門市後要抓菜單：元件該自己 import API client 嗎？

看後台現有的 MenuCount 元件，它顯示目前門市的菜單有幾個品項，現在是自己 import 真正的 client：

<script setup lang="ts">
import { realClient } from './real-client.ts'   // ✗ 寫死用哪個 client
const menu = await realClient.getMenu()
</script>

這段只是示意，有兩點先說明。第一，這裡先不帶門市 id，把焦點放在 client 從哪裡來；實際專案會寫成 getMenu(store.value.id)。第二，<script setup> 頂層寫 await 會讓元件變成非同步元件，必須放在 <Suspense> 裡才會渲染，不要照抄。練習 3 要先顯示「載入中…」，所以要在 setup 裡呼叫 getMenu()（不 await），用 ref 記錄載入中、結果和失敗三種狀態（第 17 課會細講非同步資料）。

這個元件和「真正連到後端」綁死了。寫測試時，掛載它就會真的發請求，測試變慢、會因為網路失敗，還可能寫到真的資料；要做一個用假資料的展示頁，或在測試站、正式站用不同的 baseUrl，都得改元件本身。問題的根源是：元件自己決定了「用哪一個 client」，而這個決定本來不該由它做。

把這個決定交出去的寫法叫依賴注入（dependency injection，DI）。「依賴」是元件要能運作所需要的東西，例如 API client、設定、記錄器；「注入」是這些東西不由元件自己 import 或 new 出來，而是由外部交給它。元件只說「我需要一個能 getMenu() 的東西」，由組裝 app 的地方決定給真的還是假的。TS 課第 24 課做過迷你 DI 容器：用 token 登記實作，需要的地方用 token 取。provide／inject 就是 Vue 內建的 DI，key 就是 token。

API client 和門市不同的地方是，它不屬於某一棵子樹，整個 app 都要用。這時不用找一個根元件來 provide，可以直接在 app 層級提供：app.provide(key, value)。上一節說 inject 的查找會一路查到 app 層級，所以 app 底下所有元件都 inject 得到。

app 層級的設定通常包成外掛（plugin）。外掛是一個有 install(app) 方法的物件（或一個函式），用 app.use() 安裝；Vue 安裝時會呼叫它的 install，把 app 交給它，它就可以在裡面呼叫 app.provide、註冊全域元件等。Pinia（第 15 課會教）和 vue-router 都是外掛，這也是為什麼它們都寫成 app.use(…)。把 API client 包成外掛之後，「用哪個 client」就變成安裝時傳進去的參數：

// api-plugin.ts
const API_KEY: InjectionKey<MenuApi> = Symbol('MenuApi')

export function createApiPlugin(client: MenuApi): Plugin {
  return { install(app) { app.provide(API_KEY, client) } }
}
export function useApi() { /* inject(API_KEY, null)，沒有就 throw */ }

// main.ts：正式環境
createApp(App).use(createApiPlugin(realClient)).mount('#app')

// 測試：換成假的
mount(MenuCount, { global: { plugins: [createApiPlugin(fakeApi)] } })
// 或直接提供：mount(MenuCount, { global: { provide: { [API_KEY]: fakeApi } } })

useApi() 的寫法和前面的 useCurrentStore() 一模一樣：用不 export 的 InjectionKey，inject(API_KEY, null)，沒有就丟出說明怎麼修的錯誤。MenuCount 改成呼叫 useApi().getMenu() 之後，它不再知道 client 是真是假；正式環境在 main.ts 裝真的，測試用 Vue Test Utils 的 global.plugins 裝假的。兩種測試寫法的差別見課末「補充與查表」。

寫外掛時最容易犯的錯，是把 client 存在模組層級的變數：let current; install() { current = client }，useApi() 回傳 current。單一 app 的瀏覽器看起來沒事，因為整個頁面只有一個 app。但模組只會載入一次，同一個程式裡的所有 app 共用同一個 current。同一個程式裡有兩個 app 時（伺服器渲染每個請求一個 app，第 24 課；或同一個測試檔裡建立好幾個 app），後安裝的會蓋掉先安裝的：測試 A 裝了假 client 1，測試 B 裝了假 client 2，A 的元件拿到的卻是 2。app.provide 存在各自的 app 上，不會互相影響。

💡 實務上：哪些東西值得注入，哪些直接 import 就好
值得注入的是「會碰外部世界、或不同環境要換掉」的東西：API client、記錄器（正式環境送到監控服務，開發時印在 console）、功能開關、多語系。像格式化價格 formatPrice() 這種純函式，直接 import 最簡單，硬要注入只是多一層間接。判斷時資深會問一句：「寫測試或做展示頁時，我需要把它換掉嗎？」需要就注入，不需要就 import。

到這裡，provide 的提供者都是「一個擁有者對很多使用者」：App 擁有門市，app 擁有 client。門市頁上還有一種不太一樣的情況：分頁元件的選取狀態，要在一個外層元件和幾個由使用者寫進 slot 的子元件之間共享。

門市頁的分頁：Tabs 怎麼和放進 slot 的 Tab 共享選取？

門市頁要分成「菜單」「訂單」「會員」三個分頁。我們希望使用的人只要這樣寫結構，狀態由外層元件管理：

<Tabs>
  <Tab title="菜單">…</Tab>
  <Tab title="訂單">…</Tab>
  <Tab title="會員">…</Tab>
</Tabs>

像 <Tabs> 和 <Tab>、<Select> 和 <Option> 這樣，一組要一起使用、共享狀態的元件，叫複合元件（compound components）。難處在於 Tab 是透過 Tabs 的 slot 傳進來的（第 11 課）：在模板裡寫 <Tab> 的是使用 Tabs 的頁面，不是 Tabs 自己，所以 Tabs 沒有機會在 <Tab> 上綁 props，也就沒辦法用 props 告訴每個 Tab「目前選的是誰」。

provide／inject 剛好補上這個缺口。Tab 雖然寫在頁面的模板裡，渲染出來後在元件樹上仍是 Tabs 的後代，所以 Tabs provide 的東西，Tab inject 得到。整個結構分三步：

  1. Tabs 擁有狀態（有哪些分頁、選了哪個），provide 一個 context：唯讀的 selectedId、register、unregister。這和門市的「唯讀狀態加修改函式」是同一個模式。
  2. 每個 Tab 在 setup 時 inject，呼叫 register({ id, title }) 登記自己，onUnmounted（第 8 課）時取消；面板只在 selectedId 等於自己的 id 時顯示。
  3. Tabs 依照登記的清單畫出分頁按鈕。分頁有幾個，由使用者寫了幾個 Tab 決定。

為什麼選取狀態一定要放在 Tabs？看反例：「每個 Tab 自己記有沒有被選取」。點了「訂單」，訂單把自己設成選取，但「菜單」並不知道要關起來，畫面上同時開著兩個分頁。要讓它們互相通知，又得多出一套協調機制。同一份狀態只能有一個擁有者，其他人讀它、請擁有者改它，這和門市的道理一樣。

這個設計有一個取捨：Tab 在 setup 時才登記，所以 Tabs 第一次渲染時清單還是空的，等下一輪更新才畫出按鈕。對使用者來說看不出差別，但測試要等一次更新（await flushPromises()）才找得到按鈕。

功能做出來之後，分頁還要讓鍵盤和螢幕閱讀器用得了，這是後台交付時常被要求的項目，也是練習 2 會檢查的內容。ARIA（Accessible Rich Internet Applications）是一組 HTML 屬性，用來告訴螢幕閱讀器這類輔助科技「這個元素扮演什麼角色、現在是什麼狀態」。一個 <button> 在螢幕閱讀器眼中只是「按鈕」；加上 ARIA，使用者才聽得出它是一組分頁裡的一個、目前有沒有被選取。WAI-ARIA 的分頁模式（tabs pattern）要求：

元素屬性
按鈕的容器role="tablist"
每個分頁按鈕role="tab"、aria-selected="true／false"、aria-controls 指向面板的 id
內容面板role="tabpanel"、aria-labelledby 指向按鈕的 id

鍵盤的部分：在分頁按鈕上按左右鍵切到上一個／下一個（頭尾相接），焦點跟著移動。按 Tab 鍵則只停在目前的分頁按鈕，再按一次就進入面板，不用逐一經過每個分頁。這個做法叫 roving tabindex：目前的按鈕 tabindex="0"，其他是 tabindex="-1"。-1 的意思是「可以用程式聚焦，但 Tab 鍵會跳過」，所以方向鍵的處理函式要自己呼叫下一個按鈕的 focus()。

ARIA 屬性要用 id 互相指向，id 用 Vue 3.5 的 useId()（第 11 課）產生，同一個 app 裡不會重複；同一頁放兩組 Tabs 時，兩組的 id 也不會撞。按鈕的模板大致如下：

<button v-for="(tab, i) in tabs" :key="tab.id"
  role="tab" :id="`${tab.id}-tab`" :aria-controls="`${tab.id}-panel`"
  :aria-selected="tab.id === selectedId" :tabindex="tab.id === selectedId ? 0 : -1"
  @click="select(i)" @keydown="onKeydown($event, i)">{{ tab.title }}</button>

:aria-selected 直接綁布林值就會輸出 "true"／"false"，原因見課末「補充與查表」。

💡 實務上：先用 UI 套件的，自己做時才需要這些細節
一般專案的 Tabs、Select、Menu 大多直接用 Naive UI、Element Plus 這類套件，它們內部就是同樣的 provide／inject 結構，也已經處理好 ARIA 和鍵盤。你會自己寫複合元件的時機，通常是公司要做自己的設計系統，或套件的樣式、行為跟設計稿差太多。這時把鍵盤操作和 ARIA 列進驗收：拔掉滑鼠只用鍵盤操作一輪，再用 macOS 的 VoiceOver 聽一次。有些客戶會把無障礙列入驗收，事後補比一開始就做難很多。

這課到這裡，用 provide／inject 做了三種東西：子樹裡的門市、app 層級的 API client、複合元件的選取狀態。下一個問題自然是：它是不是什麼都能放？後台接下來還有購物車要做。

門市、API client、購物車：各該放哪裡？

後台現在有三種共享資料的工具可選：props、provide／inject，以及第 15 課會教的 Pinia（Vue 官方的全域狀態管理套件）。它們不是誰取代誰，而是適合的資料範圍不同：

工具適合代價
props／emits直接的父子、或中間層本來就要用到層數多時每層都要轉手
provide／inject一棵子樹裡的情境資料：目前門市、表單的欄位狀態、Tabs 的選取；app 層級的依賴（API client、設定）從元件宣告看不出它依賴什麼；只對子樹有效；沒有 devtools 的狀態時間軸
Pinia（第 15 課）整個 app 共享、跨頁面的狀態：購物車、登入的使用者多一個套件與概念；不適合「每個 Tabs 各一份」的局部狀態

判斷時先問：這份資料屬於「一棵子樹」還是「整個 app」？

屬於子樹的，provide 是強項。門市頁裡放兩組 Tabs 時，各自需要獨立的選取狀態，每個 Tabs 元件各 provide 一份，彼此不會干擾；前面的「分店對照」區塊也是靠子樹覆蓋才做得到。這種「每個實例一份」的狀態，用全域 store 反而要自己處理「是哪一組 Tabs 的」。

屬於整個 app 的，例如購物車：要在 header 的徽章、菜單頁、結帳頁之間共用，換頁後還在，需要在 devtools 看到每次變化，伺服器渲染時每個請求一份。這是 Pinia 的工作。用 provide 也做得出來，但等於自己重做一個沒有 devtools、沒有慣例的 store。Pinia 本身也是用 app.provide 把 store 容器注入 app 的，所以它和這課學的東西並不衝突，是在同一個機制上加了狀態管理的工具。

回到開場的後台：門市只影響後台這棵子樹，用 provide 加 useCurrentStore()；API client 是 app 層級的依賴，用外掛 app.provide；門市頁的分頁用複合元件；購物車留給第 15 課的 Pinia。

補充與查表

以下是主線用不到、但實際寫專案時會查的細節。

  • Vue Test Utils 的 global.plugins 與 global.provide：global.plugins 會在掛載前對測試用的 app 執行 app.use()，所以外掛的 install 邏輯也一起被測到；global.provide 直接在 app 層級 provide，key 可以是字串或 Symbol，適合只想塞一個值、不經過外掛的情況。練習 3 用的是 global.plugins。
  • 在元件以外用 app 層級的值：路由守衛、store 這些地方沒有「正在 setup 的元件」，直接呼叫 inject 會拿到 undefined。可以用 app.runWithContext(() => inject(KEY))（3.3 起）：callback 同步執行期間，inject 會到這個 app 找值。
  • aria-selected="false" 為什麼會出現：Vue 3 對非布林屬性綁定 false 時會輸出字串 "false"，所以 :aria-selected="tab.id === selectedId" 會得到 aria-selected="false"，符合 ARIA 的要求。

練習

在 learn/ 執行 node check.mjs vue 13。測試用 Vue Test Utils 在 happy-dom 裡掛載元件，提供者和中間層由測試自己組出來；練習 3 用 global.plugins 安裝你的外掛，傳入第 5 課用過的假 API。

練習 1：current-store.ts 寫出 provideCurrentStore(initialId) 和 useCurrentStore()。用 InjectionKey 當 key；提供的是唯讀的 store（isReadonly(store) 為 true）和 switchStore(id)，provideCurrentStore 也回傳同一份；switchStore 之後所有後代自動更新，給不存在的 id 要丟錯。找不到提供者時，useCurrentStore() 丟出 Error('useCurrentStore() 必須在 provideCurrentStore() 之下使用')，而且 Vue 不能先印出 injection not found 警告。測試會在第 3 層讀門市、檢查 key 是 Symbol、同時掛兩個提供者、讓子元件嘗試直接修改、從子元件和提供者各切換一次。

練習 2：完成 Tabs.vue 和 Tab.vue（key 與型別已經在 tabs-context.ts，可以修改）。Tab 在 setup 時透過 inject 向 Tabs 註冊、卸載時取消；Tabs 依照註冊的分頁畫出 role="tablist" 和 role="tab" 按鈕，預設選第一個。目前的按鈕 aria-selected="true"、tabindex="0"，其他是 "false"、"-1"；只看得到目前分頁的 role="tabpanel" 面板；按鈕和面板用 aria-controls／aria-labelledby 互相指向。選取狀態用分頁的 id 記錄，不要用索引（前面的 Tab 被移除時，選取的分頁不能跑掉）。點擊可以切換；在按鈕上按 ArrowRight／ArrowLeft 切到下一個／上一個（頭尾相接），焦點也要移過去。測試會換成不同的分頁標題、用 v-if 移除 Tab、在同一頁放兩組標題相同的 Tabs。

練習 3：api-plugin.ts 的 createApiPlugin(client) 回傳外掛，安裝時用 app.provide 提供 client；useApi() 用 inject 取出，沒有安裝時丟出訊息提到 createApiPlugin 的錯誤。不要用模組層級的變數，兩個 app 要各自拿到自己的 client。MenuCount.vue 改用 useApi().getMenu()，顯示「載入中…」→「菜單共 N 個品項」，失敗時顯示「菜單載入失敗」。real-client.ts 不用改：它在測試環境一被呼叫就丟錯，所以 MenuCount 不能再 import 它。

練習 4：同一個父元件底下有兩個兄弟元件 A 和 B。A 在 setup 裡 provide('draft', draft)，B 在 setup 裡 inject('draft')，B 拿到什麼？

✓ inject 只沿著自己的祖先往上找，A 是 B 的兄弟、不是祖先，所以找不到，沒有預設值時 Vue 警告並回傳 undefined。渲染順序不影響結果。要讓兩個兄弟共用，把 provide（或狀態）提升到它們共同的父元件；要整個 app 都拿得到，用 app.provide 或 Pinia。

練習 5：App 裡寫 let name = '總店'; provide('storeName', name)，之後在按鈕的事件裡執行 name = '分店'。用 inject('storeName') 顯示門市的子元件會怎樣？

✓ provide 交出去的是當下的值：字串 '總店'。之後讓變數 name 指向新的字串，跟已經交出去的值無關，Vue 也沒有任何東西在追蹤這個變數。要會更新，provide 一個 ref（或 reactive、computed），改 .value；再用 readonly 包起來、另外提供修改函式，控制誰能改。nextTick 只是等排程好的更新，前提是有東西觸發了更新。

練習 6：購物車要在 header 的徽章、菜單頁、結帳頁共用，換頁後還要在，團隊也想在 devtools 看到每次的變化。該怎麼放？

✓ 這是整個 app 共享、跨頁面的狀態，Pinia 正是為此設計：devtools 看得到每次變化，伺服器渲染時每個請求一份，測試時用 createTestingPinia 替換。b 做得到，但等於自己重做一個沒有 devtools、沒有慣例的 store；provide 更適合一棵子樹裡的情境資料。c 是模組層級的狀態，伺服器渲染時所有請求共用同一台購物車，會把別人的商品顯示出來（第 12 課、第 24 課）。

常見錯誤

  • provide 普通值或普通物件，期待後代會更新：provide 不會把值變成響應式，普通值交出去的是當下的值，普通物件改了也沒有人追蹤。提供 ref、reactive 或 computed。
  • 把可寫的狀態直接交出去：任何一層後代都能改，出問題時找不到是誰。用 readonly() 包起來，另外提供 switchStore() 這類修改函式。
  • 用字串當 key：容易和別的套件撞名，inject 的型別是 unknown。用 InjectionKey<T>（帶型別的 Symbol），並把 key 包在 provideX()／useX() 裡。
  • 找不到提供者時默默回傳 undefined：錯誤會在很遠的地方爆。inject(KEY, null) 之後檢查，丟出說明怎麼修的錯誤。
  • 在 setup 以外呼叫 inject：放在 await、計時器或事件處理函式裡，Vue 已經不知道是哪個元件在問，警告並回傳 undefined。在 setup 同步 inject，存起來之後用。
  • 期待提供者自己 inject 得到自己 provide 的值：inject 從父元件開始找。讓 provideX() 回傳同一份值給提供者用。
  • 元件直接 import 真正的 API client：測試和其他環境換不掉。用外掛 app.provide 注入，測試用 global.plugins 或 global.provide 換成假的。
  • 外掛把依賴存在模組層級的變數：同一個程式有兩個 app 時互相蓋掉。存在 app 上（app.provide）。
  • 把 provide 當全域狀態管理：跨頁面、整個 app 共享的狀態用 Pinia，provide 留給子樹的情境資料和依賴注入。

小結

  • 逐層傳遞的代價是中間層只是轉手、每加一份資料都要改它們。provide／inject 讓祖先把值交給任何一層後代：provide 的值沿著元件樹串成往祖先方向的鏈，所以 inject 只往祖先找、最近的提供者優先、看不到自己 provide 的值。
  • inject 要在 setup 同步呼叫，因為 Vue 只在 setup 期間知道是哪個元件在問；預設值用第二個參數，物件或昂貴的預設值用工廠函式加 true。
  • 用 InjectionKey<T> 得到型別和不會撞名的 key；包成 provideX()／useX()，找不到提供者時丟出清楚的錯誤。
  • provide 的值要是 ref、reactive 或 computed 才會更新；用 readonly 加修改函式，讓修改只發生在提供者。
  • 依賴注入：元件不自己 import 依賴。外掛在 install 時 app.provide，測試用 global.plugins／global.provide 換成假的；不要存在模組層級的變數。
  • 複合元件（Tabs／Tab）由外層擁有狀態，slot 裡的子元件 inject 後註冊自己；再加上 ARIA 的 role、aria-selected、roving tabindex 和方向鍵。
  • 直接父子用 props，子樹情境用 provide／inject，整個 app 共享的狀態用 Pinia。
