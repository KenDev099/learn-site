階段 7：品質、效能與架構 · 第 26 課

期末專題：咖啡店線上點餐

咖啡店要上線點餐 App。顧客在手機上看菜單、選甜度、結帳、看訂單做到哪了；店員在吧台用平板看自己門市的訂單，把做好的標成「可以取餐」。這課要你把它做出來，而且用一筆具體的訂單來檢驗：王小明在捷運上用手機點了兩杯大杯拿鐵，一杯正常甜、一杯無糖，網路斷斷續續，他按了結帳，接著盯著訂單狀態頁等；總店的店員小陳在平板上看到這筆訂單，做好後按下「可以取餐」。這筆訂單從菜單走到取餐，中間每一步都可能出事：分類分享給朋友變回預設、兩杯拿鐵被合併成一種甜度、網路慢時成立兩筆訂單、訂單明細壞掉整頁跟著消失、別間門市的店員改了這筆訂單。

這課不介紹新的 API，前 25 課的技術全部會用上。你要練的是資深工程師每天在做的事：拿到一句模糊的需求，先講清楚「怎樣才算做完」，再決定每一塊資料放哪裡、程式碼放哪個資料夾，然後沿著王小明這筆訂單經過的路徑，一段一段做出來，並且說得出每個決定的代價。

這課的路線：
  1. 「顧客可以結帳」怎樣才算做完？把需求寫成驗收條件。
  2. 這筆訂單經過的每塊資料該放在哪裡？決定狀態的位置、資料夾和依賴方向。
  3. 王小明怎麼找到拿鐵、怎麼把兩杯不同甜度放進購物車？菜單頁與購物車。
  4. 捷運上網路斷斷續續，怎麼保證只成立一筆訂單？查得到狀態之後，明細壞掉又怎麼辦？結帳、輪詢與錯誤邊界。
  5. 小陳怎麼只動得了自己門市的訂單？王小明為什麼不用下載店員區的程式？守衛、權限與懶載入。
這課會用到：
  • 第 15 課的狀態放哪裡：只有一個元件用的放元件裡，要能分享的篩選條件放網址，前端擁有、多處共用的（購物車）放 Pinia store。
  • 第 16 課的 API 層與冪等鍵：所有後端呼叫經過同一個模組，失敗時丟出分好類的錯誤；冪等鍵讓伺服器認得重送的同一筆訂單。
  • 第 17 課的伺服器狀態：菜單、訂單這類資料的正本在伺服器，前端當成快取管理，用輪詢追蹤訂單狀態。
  • 第 25 課的 feature 資料夾與依賴規則：同一個功能的檔案放在一起，feature 之間只經過 index.ts 往來。

「顧客可以結帳」怎樣才算做完？

需求單上常常只有一句話：「顧客可以結帳」。照著這句話，你可以做出一個在辦公室 Wi-Fi 下按一次就成功的結帳頁，然後宣布完成。但王小明是在捷運上按的：網路慢的時候他可能按兩次，伺服器可能其實建立了訂單、回應卻在路上斷掉，取餐時段可能已經額滿。這些情況這句需求一個都沒提，所以它沒辦法回答「做完了沒有」。不先把它講清楚，工程師、PM、QA 各自心裡有一套標準，上線後才發現彼此想的不一樣。

解決的辦法是把需求改寫成驗收條件（acceptance criteria）：需求完成的具體標準，每一條寫成「在什麼情況下、做什麼、應該得到什麼結果」。例如「送出失敗時，購物車不變、留在結帳頁」。這句話可以判斷對錯：拿一個失敗的請求試一次，看購物車還在不在就知道。也正因為可以判斷對錯，好的驗收條件能直接改寫成測試，這課每一題的隱藏測試就是從下面這張表來的。

咖啡店點餐 App 的驗收條件，依照王小明那筆訂單經過的順序排列：

功能驗收條件（節錄）
菜單分類在網址上，分享、上一頁都還原；搜尋停止輸入 300ms 才查，舊結果不蓋掉新結果；載入中、錯誤加重試、沒有結果三種畫面
購物車同商品不同甜度是兩列；重新整理後還在；storage 裡的壞資料不讓 app 當掉
結帳錯誤在離開欄位後才顯示；網路慢時不會下兩次單；伺服器說「時段額滿」要顯示在取餐時間下面；失敗不清空購物車
訂單狀態每 5 秒更新，分頁隱藏時暫停，可以取餐就停；查詢失敗有重試；明細壞掉只壞明細
店員區只有店員、店長能進，而且只能進自己門市的；一般顧客不用下載店員區的程式

仔細看會發現，一條好的驗收條件通常同時寫出兩件事：做對的樣子，以及最常見的做錯方式。「失敗不清空購物車」會出現在清單上，不是因為有人想不到，而是把 cart.clear() 寫在 finally 裡是真的常見的 bug：finally 不管成功失敗都會執行，送出失敗時購物車也一起被清空，王小明得重新點一次。把這種常見錯誤寫進條件，等於提前告訴實作的人和寫測試的人「這裡要特別檢查」。

這張表就是這課的「完成」定義，後面每一節做完，都回頭對照它。

💡 實務上：開工前先跟 PM 把驗收條件對齊
真實工作中，需求單常常只有成功的畫面，失敗、空資料、網路慢、權限不足這些情況要靠工程師主動問。資深工程師拿到「顧客可以結帳」時，會先回問：送出失敗購物車要不要保留？時段額滿怎麼提示？重複點擊怎麼辦？把答案寫進需求單或 PR 描述，PM、QA、設計看的是同一份標準，驗收時就不會變成「我以為你知道」。問題不用一次問完，但會影響資料或金額的情況一定要在開工前問清楚。

這筆訂單經過的資料，各該放在哪裡？

驗收條件說清楚了「要做到什麼」，但還沒說「怎麼組起來」。直接開始寫菜單頁，很快就會遇到這種問題：購物車的資料要給頁首徽章、商品頁、結帳頁共用，放在菜單頁的元件裡顯然不行；那菜單資料呢？分類呢？每遇到一塊資料才臨時決定，結果通常是全部丟進 Pinia，因為那裡「哪裡都拿得到」。

所以動手之前，先把王小明這筆訂單會經過的資料列出來，用第 15 課的決策方式決定每一塊放哪裡。這個決策方式問的是兩件事：資料的主人是誰（前端自己產生，還是伺服器上的正本），以及誰需要它、要活多久（只有一個元件、要能分享、還是跨頁面且重新整理後還要在）。先自己填一次再往下看：分類篩選、搜尋關鍵字、菜單、購物車、結帳表單、訂單狀態、登入的使用者。

資料放哪裡為什麼
分類篩選網址 query要能分享、上一頁要還原；網址就是它的唯一來源
搜尋關鍵字元件的 ref打字中的暫時狀態，放進網址會塞滿歷史紀錄；需要分享搜尋結果時再改成防抖後寫入網址
菜單、訂單狀態有快取的查詢（伺服器狀態）資料的主人是伺服器，前端手上的是會過期的副本，要能重抓、失效
購物車Pinia ＋ storage客戶端的全域狀態：頁首徽章、商品頁、結帳頁都要用，重新整理還要在
結帳表單元件的 ref只有結帳頁用，離開就不要了
登入的使用者Pinia（auth store）守衛、頁首、權限判斷都要讀

這張表裡最容易放錯的是菜單。它看起來跟購物車很像：好幾個頁面都要用，那為什麼不也放進 Pinia？差別在主人。購物車的主人是前端，王小明加了什麼，前端就是唯一知道的人，存在 store 裡就是正本。菜單的正本在伺服器，前端拿到的只是某個時間點的副本：店長改了拿鐵的價格，副本就過期了。把菜單放進 store 之後，一連串問題都要自己回答：誰負責重抓？價格改了怎麼讓舊副本失效？兩個頁面同時要菜單，會不會抓兩次？這些正是伺服器狀態快取（第 17 課）替你處理的事，store 不會。「全部丟進 Pinia」是這類專案最常見的錯誤，它省下的是規劃時的思考，付出的是之後每一次資料不同步的除錯。

決定了資料放哪裡，接著要決定程式碼放哪裡。照第 25 課依功能分資料夾：菜單、購物車、結帳、訂單、店員區各是一個 feature，所有 feature 共用的東西（API 層、通用元件）放在 shared/，路由和守衛這類把整個 app 組起來的程式放在 app/。三者之間的 import 只能單向流動：

依賴只往一個方向，換到的是「改一個地方，影響範圍看得出來」。shared/api 是唯一知道怎麼呼叫伺服器的模組，後端改了網址或認證標頭，只改這一個檔案；結帳要讀購物車，只能透過 cart 的 index.ts，cart 內部怎麼拆檔、改名，結帳都不受影響。練習資料夾每個檔案的位置，整理在課末的「補充與查表」，做題時再查。

路由表也在這一步定下來：/ 菜單、/checkout 結帳、/orders/:id 訂單狀態、/login、/403、/staff/:storeId 店員區。每條路由先取好名稱，feature 之間用名稱導航，例如結帳成功後導到 { name: 'order-status', params: { id } }。這樣之後要把 /orders/:id 改成別的路徑，只改路由表，結帳頁的程式不用動。

規劃做完了，接下來沿著王小明的路徑實作。他打開 App 的第一件事，是在菜單裡找拿鐵。

王小明怎麼找到拿鐵？

菜單頁（練習 1）是王小明最先看到的畫面，驗收條件對它有三個要求：分類在網址上、搜尋不能亂送請求、每種結果都有畫面。這三個要求各對應前面教過的一個技術，這一節把它們組在同一個元件裡。

分類放在網址。王小明把「咖啡」分類分享給同事，同事打開應該也看到咖啡；他點進商品頁再按上一頁，也應該回到咖啡。如果分類存在元件的 ref 裡，這兩件事都做不到：網址上沒有分類，元件重新建立時 ref 回到預設值。所以分類只存在網址的 ?category=，用第 19 課的可寫 computed 讀寫它：讀的時候從網址取出並檢查是否合法，寫的時候改網址。元件不另外存一份，網址就是唯一來源，兩份資料不同步的問題從根本上不存在。

搜尋要等使用者打完字。王小明在搜尋框打「拿鐵」，如果每個按鍵都送一次請求，打兩個字就送兩次；更糟的是，先送出的請求可能比較晚回來，舊結果蓋掉新結果，畫面顯示的不是他最後打的字。這裡要兩個機制。第一個是防抖（debounce）：停止輸入 300ms 才查。用第 5 課的 onWatcherCleanup，每次輸入改變時清掉上一個計時器，只有最後一次輸入的計時器會跑完。第二個是第 17 課的「最新的請求勝出」：查詢條件改變時，用 AbortController 取消上一次請求，過期的回應不准改畫面。防抖減少請求數量，取消保證順序，兩個缺一不可。

每一種結果都要有畫面。只做成功的畫面，API 失敗時王小明會一直看到「載入中」，搜尋不到時看到一片空白，兩種情況他都不知道該怎麼辦。畫面用一個 status 欄位表示載入中、錯誤、成功三種狀態，再從成功裡分出「沒有結果」：

<p v-if="state.status === 'loading'" role="status">載入中…</p>
<div v-else-if="state.status === 'error'">…重試…</div>
<p v-else-if="state.products.length === 0" class="empty">找不到符合的商品</p>
<ul v-else>…</ul>

用一個 status 欄位而不是 loading、error 兩個布林值，是為了讓「同時是載入中又是錯誤」這種不可能的組合根本寫不出來。

你可能注意到，規劃表說菜單是「有快取的查詢」，這裡卻直接在元件裡用 watch 抓。這是刻意的取捨：目前只有菜單頁用到菜單，元件自己抓最簡單。等首頁、商品頁也要顯示菜單，好幾個元件要共用同一份資料時，就該換成第 17 課的查詢快取或 Pinia Colada，由它負責去重和失效。

💡 實務上：先用最簡單的寫法，但知道什麼時候該換
真實專案的菜單頁多半一開始就是元件裡的 watch 加 fetch，沒什麼問題。資深工程師在意的是能說出換掉它的訊號：第二個頁面也要同一份資料、使用者回報「改了價格首頁還是舊的」、DevTools 的 Network 看到同一個請求連發兩次。這些訊號出現時再引入查詢快取，比一開始就為每個請求加一層抽象省事。不管哪一種寫法，載入中、錯誤加重試、空狀態三種畫面都不能省，那是王小明實際會碰到的情況。

王小明找到了拿鐵。下一步他要選大杯、選甜度，把兩杯不同甜度的拿鐵放進購物車，問題就轉到購物車上。

兩杯不同甜度的拿鐵，為什麼不能合併成一列？

購物車（練習 2）要決定的第一件事是：什麼算「同一列」。直覺的做法是比商品 id：同一個商品再加一次，數量加一。但王小明點的是一杯正常甜、一杯無糖的拿鐵，只比商品 id，購物車會顯示「拿鐵 ×2」，送到吧台的訂單只有一種甜度，小陳做出兩杯一樣的，其中一杯就做錯了。錯誤不在畫面，在資料：合併的那一刻，「無糖」這個資訊已經丟掉了。

所以一列的 key 要包含商品加上所有會影響製作的選項。大小、甜度不同，吧台做出來就是不同的飲料，應該是不同的列：

export function lineKey(productId: number, { size, sugar }: CartOptions) {
  return `${productId}-${size}-${sugar}`
}

這個 key 會在很多地方用到：加入購物車時找有沒有同一列、改數量時找要改哪一列、v-for 渲染購物車列表時當作 :key。全部用同一個 lineKey() 算，「同一列」的定義就只有一份。

選大小、甜度的畫面是 ProductOptions 元件。它用第 10 課的具名 model：defineModel('size') 和 defineModel('sugar')，父元件寫 v-model:size、v-model:sugar 綁上去。值存在父元件，選項元件只負責顯示和回報變更，不另存一份。如果選項元件自己也存一份，父元件改了預設值或重設表單時，兩份就會對不上。

頁首的 CartBadge 要顯示購物車裡有幾杯，讀 store 時有一個坑。如果寫成 const { count } = useCartStore()，徽章會一直停在 0：解構那一刻只讀了一次 count，拿到的是當下的數字，之後讀這個變數不再經過 store，響應式追蹤就斷了。所以徽章改用 storeToRefs，或在範本直接寫 cart.count，練習 2 要求「不要直接解構 store」就是這個原因。詳細原理見練習 14 與第 15 課。

購物車還有一個驗收條件：重新整理後還在。王小明在捷運上切到別的 App 再回來，瀏覽器可能已經把分頁重新載入，購物車不見了他就得重點。所以 store 的內容要寫進 storage，啟動時再讀回來，這是持久化外掛的工作（第 15 課）。讀回來這一步要特別小心：storage 是外部資料，裡面可能是被截斷的 JSON，也可能是舊版程式存的、缺了欄位的格式。直接 JSON.parse 再放進 store，壞掉的 JSON 會讓整個 app 在啟動時丟錯，舊格式會讓購物車出現沒有價格的列。正確做法是先 try/catch 包住解析，再用 schema 驗證每一列；不合法就刪掉那份資料、從空車開始。丟掉一台購物車，總比 App 打不開好。

💡 實務上：「什麼算同一筆」是業務問題，不只是程式問題
購物車的 key、訂單明細的合併規則、報表的分組方式，背後都是同一個問題：哪些差異對業務有意義。拿鐵的甜度對吧台有意義，所以要分開；如果之後加了「外帶杯」選項，也會影響製作或成本，要不要放進 key 就得問 PM 和店長。這類規則寫錯時，畫面看起來完全正常，要等吧台做錯飲料、客人抱怨才發現，所以值得在驗收條件裡寫明，並用測試鎖住。

購物車裡現在有兩列拿鐵，王小明按下「結帳」。這一步牽涉金額，而他的網路正好斷斷續續。

網路斷斷續續時，怎麼保證只成立一筆訂單？

結帳頁（練習 3）的基礎是第 18 課的表單：欄位驗證、錯誤在離開欄位後才顯示、伺服器回 422 時把錯誤顯示在對應欄位。這一節要處理的是表單課沒有遇到的問題：王小明按下送出之後，畫面轉了好幾秒都沒反應，他又按了一次。最後咖啡店收到兩筆一模一樣的訂單，他被收了兩次錢。

先把驗收條件表裡那一列對上。王小明選的 12:30 取餐時段剛好額滿，這件事前端事先不知道，只有伺服器查得到。伺服器拒絕這筆訂單，回 422，fieldErrors 是 { pickupTime: '時段額滿' }。結帳頁把這個訊息顯示在取餐時間欄位下面，不要做成頁面頂端一條通用的「送出失敗」：王小明要知道是哪一欄出了問題，才知道改選別的時段就好。購物車維持不變，他改完時段直接再送一次。伺服器錯誤怎麼對應回欄位，做法和第 18 課相同。

重複下單有兩種來源，要分開處理。第一種是同一時間送出了兩次：第一個請求還在路上，又觸發了一次 submit。第二種比較隱蔽：第一個請求其實成功了，伺服器已經建立訂單，但回應在回來的路上斷掉。前端看到的是失敗，王小明合理地再按一次，這時第一個請求早就結束了，任何「進行中」的檢查都擋不住。

第一種用前端的進行中保護擋。在 onSubmit 開頭寫 if (submitting.value) return：送出進行中，再觸發 submit 直接返回。只把按鈕設成 disabled 不夠，disabled 只擋得住「點這顆按鈕」，擋不住快捷鍵、第二顆送出按鈕、程式呼叫 requestSubmit() 這些送出途徑（第 18 課）。檢查放在送出函式裡，不管從哪條路觸發都會經過它。

第二種要靠冪等鍵，而且只有伺服器擋得住。冪等（idempotent）的意思是同一個操作做一次和做很多次，結果都一樣。建立訂單本來不是冪等的，按兩次就有兩筆，冪等鍵就是用來讓它變成冪等。冪等鍵（第 16 課）是前端產生的一串唯一識別碼，隨著建立訂單的請求一起送出，意思是「這是同一次結帳」。伺服器記住看過的冪等鍵，再看到同一個鍵，就回傳第一次的結果，不建立第二筆。前端要負責的是讓「同一次結帳」的每次嘗試都帶同一個鍵：第一次送出時產生，失敗重送時沿用，成功之後才清掉。如果每次送出都產生新的鍵，伺服器看到的就是兩次不同的結帳，冪等鍵形同虛設。回應斷掉的那個情況，王小明第二次按下送出，帶的是同一個鍵，伺服器認出來，回傳第一筆訂單的 id，他只被收一次錢。

這兩層的分工要分清楚。前端的保護只是減少重複的請求，真正擋住重複的是伺服器：只要有人繞過前端直接重送請求，能判斷「這是不是同一次結帳」的只有記著冪等鍵的伺服器。伺服器那一端怎麼存、存多久，系統設計課第 9 課會講。

最後是成功和失敗之後要做什麼，順序很重要。成功時清空購物車、導到訂單狀態頁；cart.clear() 只能放在 await 成功之後，不能放在 finally，這就是驗收條件裡特別寫出來的那個 bug。送出失敗時，購物車、表單內容和網址都要維持原樣，王小明才能直接再按一次，而那一次會帶著同一個冪等鍵。

💡 實務上：重複下單通常是客服先發現的
上線後，這類 bug 很少在測試環境出現，常見的是客服轉來「客人說按一次卻收到兩筆訂單」或「被扣兩次款」，而且多半發生在網路不穩的手機上。只要牽涉金額（結帳、付款、退款、儲值），資深工程師會先確認後端有沒有冪等處理，而不是只在前端加 disabled。查問題時，前端送出的冪等鍵如果有寫進錯誤回報或請求紀錄，後端就能直接比對是不是同一次結帳，省下很多來回猜測。

結帳成功，王小明被導到訂單狀態頁，開始等他的拿鐵。這一頁要持續向伺服器查詢，而查詢和顯示都可能出錯。

訂單做到哪了？查不到、或明細壞掉怎麼辦？

訂單狀態頁（練習 4）要做的事是輪詢：每隔一段時間問伺服器一次「這筆訂單現在是什麼狀態」，直到可以取餐。做法沿用第 17 課：上一次請求結束後才用 setTimeout 排下一次，請求就不會在伺服器慢的時候一個疊一個；分頁隱藏時暫停，王小明切去看訊息時不浪費流量；狀態變成 ready 就停；所屬的 scope 停止時清掉計時器和進行中的請求。

這次多了一個要求：查詢失敗要在畫面上顯示錯誤和「重試」按鈕。捷運進隧道，某一次查詢失敗了，如果錯誤被吞掉，畫面會停在「製作中」，王小明以為拿鐵還在做，其實是畫面沒在更新。他需要知道「查不到最新狀態」，並且能按重試。

這裡會有一個念頭：第 21 課不是教過錯誤邊界嗎？把整頁包起來，錯誤就有人接了。這行不通，原因在於錯誤是誰丟出來的。錯誤邊界靠的是 Vue 的錯誤處理機制，它只接得到 Vue 自己呼叫的程式碼丟出的錯誤：渲染、生命週期、watcher 這些。setTimeout 的 callback 是瀏覽器在計時器到期時呼叫的，不經過 Vue，裡面丟出的錯誤 Vue 根本看不到（第 21 課的表格列過這件事）。所以輪詢的錯誤只能由輪詢自己 catch，存進 error，再由頁面根據 error 顯示錯誤和重試；按下重試就清掉 error、立刻再查一次，成功後恢復輪詢。

那錯誤邊界在這一頁負責什麼？它負責另一種錯誤：渲染時丟出的錯誤。訂單明細元件相信每一列都有 name，後端哪天改版少給了這個欄位，line.name.trim() 就在渲染時丟出 TypeError。這種錯誤發生在 Vue 呼叫的渲染函式裡，錯誤邊界接得到。如果沒有包，壞掉的明細可能讓整頁都無法顯示，王小明連「可以取餐」都看不到。把明細包進 <ErrorBoundary>，壞掉的只有明細，訂單狀態和取餐提醒照常顯示：

<ErrorBoundary v-if="order">
  <OrderDetails :order="order" />
</ErrorBoundary>

注意這個錯誤邊界在 onErrorCaptured 裡回傳 false：錯誤就停在這裡，不會再往上傳到 app 的 errorHandler，練習 4 要求「app 的 errorHandler 不會收到」就是這個意思。代價是 errorHandler 原本負責的回報也收不到這個錯誤，所以回報要由錯誤邊界自己呼叫（第 21 課），下面實務上提醒的就是這件事。

這一頁的兩種錯誤，處理方式不同，目標卻一樣：讓壞掉的範圍越小越好，主要任務（告訴王小明拿鐵好了沒）不受影響。

💡 實務上：錯誤邊界包在「壞掉也不影響主要任務」的區塊外
錯誤邊界要包多大？包整頁，一個小區塊壞掉整頁都換成替代畫面；每個元件都包，程式碼很吵。常見的包法是明細、推薦商品、評論這類輔助區塊。訂單狀態是這一頁的主要任務，不該跟著明細一起消失。另外，錯誤邊界回傳 false 之後 errorHandler 收不到這個錯誤，要確認錯誤邊界自己有回報出去（第 21 課），不然畫面看起來正常，bug 卻被默默藏起來，要等客訴才知道。

王小明這一端做完了。訂單現在出現在總店的平板上，輪到店員小陳把它標成「可以取餐」，問題換成：誰有資格按這顆按鈕？

小陳怎麼只動得了自己門市的訂單？

店員區（練習 5）在 /staff/:storeId，例如總店是 /staff/1、分店是 /staff/2。驗收條件要求只有店員、店長能進，而且只能進自己門市的。要擋的人有好幾種：王小明好奇在網址列打 /staff/1；小陳把網址改成 /staff/2 偷看分店；懂一點技術的人改掉前端的 JavaScript，或乾脆跳過畫面、直接對 API 發請求。沒有一個機制擋得住全部，所以分成三層，各自負責不同的事：

層次做什麼擋得住什麼
路由守衛沒登入去登入頁並帶 redirect；角色不對、門市不對去 403顧客或別間店的店員誤入看板
can()決定每筆訂單要不要顯示「可取餐」按鈕按了只會失敗的按鈕
伺服器標成 ready 的 API 再檢查一次身分、角色、門市改網址、改 JavaScript、直接打 API 的人

路由守衛在導航時檢查：沒登入就導到登入頁，並把原本要去的網址放進 redirect，登入後才回得來；角色不是店員或店長、或門市不是自己的，就導到 403。can() 在畫面上檢查：每一筆訂單，這個人能不能做這個動作，不能就不顯示按鈕。

前兩層有一個共同點：它們在使用者的瀏覽器裡執行。瀏覽器是使用者的地盤，他可以打開 DevTools 改掉任何一行 JavaScript，讓守衛永遠放行、讓按鈕永遠顯示。所以前兩層的目的是體驗：讓正常使用的人不會走進進不去的頁面、不會按到只會失敗的按鈕。安全只靠第三層：伺服器收到「把訂單標成 ready」的請求時，用同一套規則再檢查一次身分、角色、門市，這一層使用者碰不到。

前端這兩層雖然只為體驗，寫錯了一樣會出事。can() 裡的門市比較有一個第 20 課看過的陷阱：如果寫成 user.storeId === order.storeId，某個店長帳號少了 storeId、訂單也剛好少了 storeId，undefined === undefined 是 true，他就能動別間店的訂單。正確寫法是先確認 storeId 是數字，再比較。守衛的門市檢查也一樣。

守衛寫完之後，怎麼確認它真的擋住了每一種情況？練習 5 的最後一題用第 22 課「測試你的測試」的方式：你要替守衛寫檢查函式 checkStaffGuard()。判分時它要讓兩個寫法不同的正確版本通過，並抓到四個錯誤版本。這題反過來考你：寫得出抓錯的檢查，代表你知道規格的每一條在防什麼，例如「總店店員去 /staff/2 要被擋」防的就是小陳偷看分店。

💡 實務上：權限 bug 常常出在「沒想到的資料」
權限檢查的邏輯通常不難，出事的多半是邊界資料：舊帳號沒有門市欄位、新角色還沒加進權限表、id 從網址讀進來是字串。資深工程師寫權限判斷時會預設拒絕，只有明確符合條件才放行，並把「缺欄位」「型別不對」當成測試案例。上線前也會跟後端確認同一套規則在 API 也有檢查，因為前端的檢查只要被繞過一次，就等於沒有。

小陳能進、王小明和別間店的店員進不來了。但還有一個問題：店員區的程式碼，現在是不是也打包進了王小明下載的那個檔案裡？

王小明為什麼不用下載店員區的程式？

Vite 打包時，會把程式切成一個或多個 JavaScript 檔，每一個叫一個 chunk。所有靜態 import 串起來的程式會進到同一個主 chunk，它是 App 啟動時一定要下載的那個檔。每個打開 App 的人都要先下載主 chunk，畫面才出得來。如果路由表在檔案最上面寫 import StaffPage from '...'，店員區的看板就在主 chunk 裡，王小明在捷運上用不穩的網路，也要多下載一份他永遠用不到的程式。

懶載入（lazy loading）就是讓這段程式只在需要時才下載。路由的 component 改成一個載入函式：component: () => import('../features/staff/StaffPage.vue')。動態的 import() 讓 Vite 打包時把店員區拆成獨立的 chunk，只有第一次進 /staff 才下載。店員區只有少數人會進來，最適合拆出去：拆了之後，每個顧客都少下載一份程式。

那為什麼不每個頁面都懶載入，讓主 chunk 最小？因為懶載入有代價：進入那一頁時要多一次請求，還要處理下載中和下載失敗的畫面。菜單和結帳是幾乎每個人一進來就要用的，拆出去只是讓他們多等一次往返，所以維持靜態 import。判斷標準是「多少人會用到」：大部分人不會進的頁面才值得拆。

最後，「拆出去了」要用量測確認，不是看程式碼覺得有拆。常見的情況是路由已經改成 () => import()，但別的檔案還有一行靜態 import 同一個元件，它就被拉回主 chunk，拆分無效。所以練習 5 的測試會真的跑一次 Vite 的 build()，檢查主 chunk 裡沒有店員區的程式。這跟第 23 課的原則一樣：沒有量測就不要宣稱效能變好。

到這裡，王小明這筆訂單經過的每一段都有了對應的實作，驗收條件表的五列也都對到了練習。接下來動手做。

練習

在 learn/ 執行 node check.mjs vue 26。五題都在 work/26/，測試在最外層（ex1.test.ts～ex5.test.ts），每一題先讀檔案開頭的註解（那就是這題的驗收條件），再看測試失敗的訊息。shared/ 和標著「已經寫好」的檔案不用改。建議照順序做：練習 3 會用到練習 2 的購物車 store，練習 5 的打包測試會把練習 1、3、4 的頁面一起打包。

練習 1：菜單頁。分類只存在網址的 ?category=（不合法、陣列都當成 coffee），點分類改網址並保留其他 query，進商品頁再按上一頁要還原；搜尋停止輸入 300ms 後才查，條件改變時 abort 上一次，過期的回應不能改畫面；做出載入中、錯誤加重試、沒有結果三種畫面。

練習 2：購物車。store 用「商品＋大小＋甜度」當作同一列的 key；ProductOptions 用兩個具名的 defineModel，radio 包在有 legend 的 fieldset 和 label 裡；CartBadge 不要直接解構 store；持久化外掛只處理 cart，壞掉的 JSON、舊格式、不合法的列都不能讓 app 當掉，要刪掉壞資料、從空車開始。

練習 3：結帳頁。錯誤在 blur 或按過送出後才顯示，並加上 aria-invalid、aria-describedby；送出進行中再觸發 submit 不重送；失敗重送沿用同一個冪等鍵；422 的 fieldErrors 顯示在對應欄位；成功才清空購物車並導到 /orders/:id，失敗時購物車和網址都不變。

練習 4：訂單狀態頁。把 setInterval 版的輪詢改成請求不重疊、分頁隱藏時暫停、ready 就停、卸載時清理；查詢失敗時在頁面上顯示 .poll-error 和「重試」，重試成功後恢復輪詢；訂單明細包進錯誤邊界，明細渲染出錯時只換掉明細，app 的 errorHandler 不會收到。

練習 5：店員區。修好 can() 的門市比較；/staff/:storeId 改成懶載入並加上 meta，打包後主 chunk 不能有店員區的程式；守衛檢查登入（帶 redirect）、角色、門市；最後完成 checkStaffGuard()，讓它通過兩個正確版本、抓到四個錯誤版本。

練習 6：購物車和菜單資料各該放在哪裡？

✓ 購物車是客戶端的全域狀態：資料的主人是前端，好幾個頁面要用，重新整理還要在，所以是 Pinia 加持久化。菜單是伺服器狀態：主人是伺服器，前端手上的是會過期的副本，需要快取、去重、過期重抓、失效，這些查詢快取都做好了。a 把菜單放進 store，這些事都要自己寫，而且常常沒寫。b 讓每個頁面重複抓同一份菜單，購物車也跨不了頁面。d 的網址放不下購物車，localStorage 的菜單會一直是舊價格。

練習 7：怎麼防止同一筆訂單被建立兩次？

✓ 重複有兩種來源：同一時間送了兩次，以及「第一次其實成功、回應沒收到」之後的重送。進行中保護處理第一種；第二種只有伺服器能判斷，前端要做的是讓兩次嘗試帶同一個冪等鍵。a 只擋得住點這顆按鈕，快捷鍵、程式觸發的 submit 都繞得過，也擋不住回應遺失後的重送。c 讓每次嘗試看起來都是新訂單，等於沒有冪等鍵。

練習 8：哪些頁面最值得懶載入？

✓ 懶載入的好處是「不需要的人不用下載」，代價是進入那一頁時多一次請求、要處理載入中和下載失敗（第 21 課的 vite:preloadError）。店員區只有少數人用，拆出去讓所有顧客都受益。b 把每個元件都拆開，換來一堆小請求和到處閃爍的載入中。c 每個人都要看首頁，拆出去只是多一次往返，首頁反而更慢。拆完之後要量測（看打包結果、看 LCP），不是覺得變快就算數。

測試全過之後，還要檢查什麼？

測試全過，代表驗收條件裡寫得出來的部分都做到了。但有些品質沒辦法寫成一條「在什麼情況下、應該得到什麼結果」：焦點有沒有移到該去的地方、錯誤有沒有回報出去、某個檔案有沒有偷偷繞過 API 層。這些要靠你自己再看一次程式。下面的清單照前 25 課的主題分類，每一項都是 code review 時會被問的：

  • 可近用性：每個 input、radio 都有 label；錯誤訊息用 aria-describedby 連到欄位；載入中用 role="status"、錯誤用 role="alert"；送出失敗時焦點移到第一個錯誤欄位（第 18 課）。
  • 錯誤處理：每個抓資料的地方都有載入中、空狀態、錯誤、重試四種畫面；計時器和第三方 callback 裡的錯誤自己 catch；渲染錯誤有錯誤邊界；錯誤有回報（第 21 課）。
  • 效能：少用的頁面懶載入，而且用打包結果確認；傳給子元件的 props 穩定，不在範本裡建立新的物件或函式（第 23 課）。
  • 安全：沒有 v-html 顯示使用者內容（第 25 課）；登入後的 redirect 只接受站內路徑，用第 20 課的 safeRedirect() 檢查（只看開頭是不是 / 不夠）；前端的權限檢查只為體驗，API 一定再檢查。
  • 架構：API 呼叫只在 shared/api；feature 之間只透過 index.ts；每塊狀態放在規劃時決定的地方，沒有「先丟 store 再說」。

常見錯誤

  • 所有狀態都丟進同一個 store：伺服器資料沒有失效機制、表單的暫時狀態離開頁面還留著。先分類：網址、元件、客戶端全域、伺服器狀態，各放各的地方。
  • API 呼叫散落在元件裡：錯誤處理、逾時、認證標頭到處各寫一份，測試也要到處 mock fetch。只讓 shared/api 呼叫伺服器，元件透過注入拿到 client。
  • 只做成功的路徑：API 失敗時畫面卡在載入中，沒有結果時一片空白。每個非同步畫面都要有載入中、空狀態、錯誤加重試。
  • 購物車只用商品 id 當一列的 key：不同甜度、大小被合併成一列，吧台做錯飲料。key 要包含所有會影響製作的選項，全部用同一個 lineKey() 算。
  • 每次送出都產生新的冪等鍵：回應遺失後的重送被伺服器當成新訂單。第一次送出時產生，失敗重送沿用，成功後才清掉。
  • 購物車在 finally 裡清空：失敗時客人要重新點一次。只在成功之後清空。
  • 以為前端權限檢查就是安全：守衛和 v-if 只決定畫面，改網址、直接打 API 就繞過了。伺服器一定要用同一套規則再檢查。
  • 沒有量測就宣稱效能變好：以為改成 () => import() 就拆出去了，結果別的檔案還靜態 import 同一個元件，它還在主 chunk。看打包結果、用 Lighthouse 或 DevTools 量 LCP 再下結論。

小結

  • 先把一句需求寫成驗收條件，它同時說明「做對的樣子」和「最常見的做錯方式」，而且可以直接變成測試。
  • 動手前先決定每塊狀態的位置，判斷依據是資料的主人和生命週期：分類在網址、購物車在 Pinia 加持久化、菜單和訂單是伺服器狀態、表單在元件裡。
  • 依功能分資料夾，依賴只往 shared 的方向走，feature 之間透過 index.ts，只有 shared/api 呼叫伺服器。
  • 菜單：分類以網址為唯一來源；搜尋用防抖減少請求、用取消保證最新結果勝出；載入中、錯誤、空結果都有畫面。
  • 購物車：一列的 key 是商品加上所有影響製作的選項；從 storage 讀回的資料先驗證，壞了就從空車開始。
  • 防重複下單靠前端的進行中保護加上冪等鍵，最後由伺服器擋；失敗時不改購物車、不換頁。
  • 計時器裡的錯誤 Vue 接不到，由輪詢自己處理並提供重試；渲染錯誤由錯誤邊界圍住，讓壞掉的範圍越小越好。
  • 守衛和 can() 是體驗，伺服器才是安全；少用的頁面懶載入，並用打包結果確認。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：結帳頁的測試想確認「送出中不能重送」，submit 是回傳 deferred().promise 的 vi.fn()。這樣寫哪裡會出事？

await wrapper.get('form').trigger('submit')
expect(wrapper.vm.submitting).toBe(true)
expect(submit).toHaveBeenCalledTimes(1)

✓ 好測試在錯誤版本上失敗、在重構過的正確版本上通過，這個剛好相反。改成使用者的角度：再觸發一次 submit，檢查 submit 仍只被呼叫一次，並用 role 和文字找到按鈕、確認它停用。a 錯在 handler 一開始就同步設好 submitting，問題不在等待，在於測的是實作。（第 22 課）

練習 10：菜單頁有 80 張 ProductCard，每張收到 :lines="cart.lines"，自己算「已加入 N 杯」。Vue DevTools 顯示加一杯拿鐵，80 張卡片全部重新渲染。怎麼改？

✓ 每張卡片都讀了同一個 cart.lines，它一變，80 張都要重算。改成只收到跟自己有關的值，props 只有一張變了，就只更新那一張。c 錯在 computed 回傳的還是同一個陣列，卡片照樣讀它、照樣全部更新。（第 23 課）

練習 11：店員區的路由已經寫成 () => import('../features/staff/StaffPage.vue')，vite build 的主 chunk 卻還有店員區的程式。先查什麼？

✓ 動態 import 會切出 chunk，但同一個模組只要有一處靜態 import，它就留在主 chunk，分割無效。搜尋誰 import 了它，改掉之後再看一次 vite build 的輸出。b 錯在路由直接給載入函式就好，defineAsyncComponent 是給一般元件用的。（第 23 課）

練習 12：菜單頁改成 SSR 之後，頁首 CartBadge 出現 hydration 不一致的警告：伺服器渲染「0 件」，瀏覽器從 localStorage 還原成「3 件」。怎麼修？

✓ hydration 的前提是兩邊第一次渲染結果相同；只有瀏覽器知道的值，兩邊先用同一個值，掛載後再改。a 是最常見的錯：伺服器不丟錯了，但瀏覽器的第一次渲染是 3、伺服器是 0，照樣不一致。c 更糟，伺服器上模組層級的狀態被所有請求共用，陳美華會看到王小明的拿鐵。（第 24 課）

練習 13：結帳頁要讀購物車，同事寫了 import { useCartStore } from '../cart/cart-store'，測試全過。這行哪裡會出事？

✓ feature 之間只 import 對方的 index.ts，內部檔案才能自由重構；需要什麼就請 cart 在 index.ts 公開，再用 lint 或測試自動擋下深層 import。b 錯在 feature 可以依賴別的 feature，只是要經過公開介面；自己存一份購物車，兩份遲早對不上。（第 25 課）

練習 14：CartBadge 寫了 const { count } = useCartStore()，範本顯示 {{ count }}。加入拿鐵之後，徽章一直停在 0。為什麼？

✓ 依賴追蹤靠 proxy 的 get：render 執行時讀了哪個物件的哪個屬性，寫入時才知道要通知誰。解構把值複製到普通變數，之後的讀取不再經過 store，連結就斷了。改成 storeToRefs(cart)，或範本直接寫 cart.count。c 錯在從 reactive 物件讀屬性時 ref 已經解包，拿到的就是數字，不是 ref。（第 1、4、15 課）

練習 15：購物車每列有「加備註」按鈕，按下去輸入框出現了，卻沒有取得焦點。為什麼？

<input v-if="editing" ref="noteInput">

function startNote() {
  editing.value = true
  noteInput.value?.focus()
}

✓ Vue 改資料只排工作，用 microtask 批次更新，同一個 handler 改三次也只渲染一次；所以下一行的 DOM 還是舊的，輸入框還不存在。await nextTick() 等這一輪更新完再操作。b 錯在 sync watcher 是改資料的當下就執行，比 DOM 更新還早，一樣拿到 null。（第 6 課）

練習 16：code review 時，同事把購物車列表 <CartLine v-for="line in cart.lines" :key="line.productId" /> 的 key 從 index 改成這樣，說「用 id 就不會錯位」。哪裡會出事？

✓ patch 靠 type 和 key 判斷是不是同一個節點，同一層的 key 重複時開發模式會警告，對應也會錯亂。key 要穩定而且唯一：購物車的「一列」是商品加上所有選項，用 lineKey() 算出的字串。a 只看到「穩定」，漏了「唯一」；index 換成 id 的方向是對的，但 id 在這份列表裡不唯一。（第 7 課）
