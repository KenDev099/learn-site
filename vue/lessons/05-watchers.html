階段 2：Vue 響應式實戰 · 第 5 課

watch：副作用、清理與競態

咖啡店的點餐頁收到客服轉來的兩張單。第一張：客人在菜單搜尋框打「拿」，再補一個字變「拿鐵」，畫面卻顯示「拿」的結果。第二張：點餐備註會自動存草稿，客人打十個字就存了十次，而且離開點餐頁之後，Network 面板裡還一直出現存檔請求。

兩張單都出在 watch：資料改變時要做的事（打 API、存檔）沒有在該停的時候停下來。這課從打開點餐頁的程式碼開始，一步步把搜尋和存草稿這兩段 watch 改對。學完你會知道什麼時候該用 watch、怎麼讓它在對的時機停下來，以及 code review 時怎麼一眼認出這類 bug。

這課的路線：
  1. 點餐頁的三個 watch 哪個不該存在：要一個值用 computed，要做一件事才用 watch；兩張單的最小修法是什麼（開場問題的最小答案）。
  2. watch 要盯什麼、什麼時候開始：第一個參數為什麼不能直接傳 state.qty、push 為什麼沒觸發，immediate、deep、once 解決什麼。
  3. 能不能不寫來源：watchEffect 自動追蹤，但 await 之後讀的資料不算。
  4. 搜尋框為什麼顯示舊結果、備註為什麼存十次：競態怎麼發生，用清理函式取消上一次的請求和計時器。
  5. 離開頁面後為什麼還在存：watcher 什麼時候自動停止，什麼時候要自己停、暫停與恢復。
這課會用到：
  • 第 3 課的 computed：從別的狀態算出值並快取，依賴改了、有人讀時才重算。
  • 第 4 課的 ref、reactive 與傳 getter：把 cart.qty 的值傳出去會斷線，傳 () => cart.qty 才能讓對方每次重新讀；練習在第 4 課裝好的本機環境寫。
  • TS 課第 11 課的 AbortController：呼叫 controller.abort() 取消帶著它 signal 的請求，請求以 AbortError 失敗。

點餐頁的三個 watch，哪個不該存在？

打開點餐頁的 <script setup>，先別急著修搜尋，先看清楚這裡有幾個 watch、各自在做什麼。檔案裡有三個：一個在購物車品項改變時重算總金額，一個在關鍵字改變時搜尋菜單，一個在備註改變時存草稿。要判斷它們該不該存在，需要一把尺：這段程式是在「算出一個值」，還是在「對外做一件事」。

「對外做一件事」有個正式的名字：副作用（side effect）。一段程式除了算出結果以外，還改變了它外面的世界，就叫有副作用，例如發請求、寫 localStorage、操作 DOM、送統計事件。副作用做了就收不回來，做幾次、什麼時候做都會影響結果：存兩次草稿就是伺服器收到兩個請求。算總金額則沒有副作用，它只是從現有的資料推出一個數字，算幾次都一樣，也不會影響任何人。

Vue 的 watch() 是為副作用設計的：你指定要盯著哪份資料，那份資料一改，Vue 就執行你給的函式。這種「盯著資料、改了就執行一段程式」的東西叫 watcher，這課都用這個名字。第 3 課做過的 computed 則是為「值」設計的。所以判斷只要問一個問題：你要的是一個值，還是要做一件事？

需求用什麼
購物車總金額、篩選後的菜單、按鈕能不能按computed：從別的資料算出來的值
關鍵字改了就搜尋、表單改了就存草稿、門市改了就重新載入watch：資料改變時對外做事

用這把尺看第一個 watch，它在維護總金額：

// ✗ 用 watch 維護 total
const total = ref(0)
watch(items, list => {
  total.value = list.reduce((s, i) => s + i.price * i.qty, 0)
}, { deep: true, immediate: true })

// ✓ total 本來就是從 items 算出來的
const total = computed(() => items.value.reduce((s, i) => s + i.price * i.qty, 0))

callback 裡只有 total.value = …，沒有對外做任何事，它要的是一個值，該用 computed。watch 版本的根本問題是：total 變成另一份獨立的狀態，要靠 watch 追著 items 更新，而「追」的每個環節都可能漏掉：

  • 第一次：watch 預設只在資料「改變」時執行，頁面剛打開時不會跑。忘了 immediate，總金額一開始就是 0。
  • 深層：改某個品項的數量，items 陣列本身沒有被換掉。忘了 deep，總金額不會更新（下一節會看到原因）。
  • 時機：Vue 不會在 items 改動的當下呼叫 watch callback，而是先把同一輪的改動收集起來，稍後一起執行（細節在第 6 課的排程）。所以改完 items 立刻讀 total，watch 還沒跑，讀到的是舊值。

computed 沒有這些問題，因為它不存一份會過期的副本：讀的時候發現依賴變了就當場重算（第 3 課做過），所以沒有「還沒同步」的時刻。

💡 實務上：code review 看到 watch 先問「這能不能是 computed」
接手的專案裡很常看到 watch 加 deep、immediate 在維護總金額、篩選結果、表單能不能送出，這類 bug 多半是「某個情況忘了同步」。資深工程師看到 watch callback 裡只有 xxx.value = …、沒有對外做事，就會建議改成 computed。真正該用 watch 的地方通常有個明確的外部對象：API、localStorage、網址參數、統計事件。寫之前先說得出「資料變了要通知誰」，說不出來多半就是 computed，就像點餐頁的總金額。

剩下兩個 watch 是真正的副作用：搜尋要打 API，存草稿要寫到伺服器，它們確實該用 watch。客服的兩張單就出在這兩個 watcher，原因也相同：該停的時候沒停。最小的修法是：新的一次開始前，先取消上一次還沒完成的請求或計時器；元件卸載時，讓 watcher 跟著停止。前者在〈搜尋框為什麼顯示舊結果？〉和〈備註為什麼打十個字存十次？〉，後者在〈離開點餐頁後，為什麼還在存草稿？〉。要動手修之前，得先確定這兩個 watcher 盯對了東西，這是下一節。

watch 要盯什麼？為什麼傳錯了不會觸發

上一節說搜尋和存草稿要用 watch，第一步是告訴 Vue 要盯哪份資料。這就是 watch() 的第一個參數，叫來源（source）。

來源不能是隨便一個值，必須是 Vue 追蹤得到的東西。回想第 2 課的機制：Vue 知道「誰依賴誰」，靠的是在函式執行期間，透過 proxy 讀屬性時記下來。一個普通的數字或字串沒有經過 proxy，Vue 無從得知它之後會不會變。所以來源只能是下面這幾種：

來源例子什麼時候觸發
refwatch(keyword, cb)keyword.value 被換掉
getter 函式watch(() => state.qty, cb)getter 的回傳值改變（用 Object.is 比較）
reactive 物件watch(form, cb)任何一層的屬性改變（自動深層）
陣列（以上幾種的組合）watch([keyword, () => state.storeId], cb)其中任何一個改變；cb 收到的新值、舊值也是陣列

搜尋框的關鍵字是 ref，直接傳 keyword 就好。容易出錯的是 reactive 物件裡的某個屬性，例如購物車狀態 state 裡的數量。最常見的寫法是把屬性的值直接傳進去：

const state = reactive({ qty: 1 })

watch(state.qty, cb)        // ✗ 傳進去的是數字 1
// [Vue warn]: Invalid watch source: 1 A watch source can only be a getter/effect function,
//   a ref, a reactive object, or an array of these types.

watch(() => state.qty, cb)  // ✓ 傳 getter：每次執行都重新讀 state.qty，也就重新被追蹤

JavaScript 在呼叫 watch 之前，就先把 state.qty 讀成數字 1 了，watch 收到的只是 1，跟 proxy 沒有任何連線。這和第 4 課「把 state.count 傳給函式會斷線」是同一件事。Vue 不會丟錯，只在開發模式印出警告，這個 watcher 什麼都不做。改成傳 getter，也就是一個「每次呼叫都去讀 state.qty」的函式，Vue 執行它時就會經過 proxy，追蹤也就建立起來了。

傳對了 getter，還有第二個坑：getter 來源只比較回傳值本身。Vue 每次重新執行 getter，用 Object.is 比較這次和上次的回傳值，一樣就不觸發。Object.is 對數字、字串比的是值；對物件和陣列比的是「是不是同一個物件」，不看裡面的內容有沒有變。

const state = reactive({ items: [] as string[] })

watch(() => state.items, cb)
state.items.push('拿鐵')     // ✗ 不觸發：getter 回傳的還是同一個陣列，Object.is 判定沒變
state.items = ['可頌']       // ✓ 觸發：換成另一個陣列

watch(() => state.items, cb, { deep: true })   // ✓ push 也觸發
watch(state, cb)                                // ✓ 整個 reactive 物件當來源，本來就是深層

在 Vue 3.5.44 實際跑過：getter 版本 push 之後 callback 執行 0 次；直接監聽 reactive 物件，改到第三層的屬性也會觸發。記法：reactive 物件來源預設深層，ref 和 getter 來源預設不深層。這也是上一節總金額的 watch 忘了 deep 就不更新的原因。

來源盯對了，還有兩件事沒指定。備註表單有巢狀欄位（例如 options.sugar），改了它也要存草稿；有些 watcher 則希望頁面一打開就先跑一次，而不是等資料第一次改變。這兩件事靠 watch 的選項決定。

巢狀欄位也要觸發、頁面一打開就要跑？immediate、deep、once

watch 的第三個參數是選項物件，用來調整「什麼時候執行」和「追蹤多深」。常用的有三個：

選項作用要注意
immediate: true建立時先執行一次 callback，之後照常第一次的舊值是 undefined
deep: true遍歷來源的每一層，巢狀屬性改了也觸發可以給數字，限制往下追幾層
once: true只執行一次 callback，之後自動停止例如「第一次選了門市才載入引導教學」

這三個選項的最低版本見課末〈補充與查表〉；練習用的 Vue 3.5.44 全部都有。

先看 immediate。watch 預設是「等改變才執行」：建立的那一刻不跑，資料第一次改變才跑。這對搜尋框是對的，關鍵字還沒打就不該搜尋；但像「目前門市的訂單看板」這種頁面，一打開就要載入一次，之後門市改了再重新載入，就需要 immediate: true。代價是第一次執行時根本沒有「上一個值」，所以舊值是 undefined：

watch(storeId, (id, oldId) => {
  // immediate 時，第一次 oldId 是 undefined，別拿它去比較或當參數
  if (oldId !== undefined) sendEvent('切換門市', { from: oldId, to: id })   // 送統計事件
  loadBoard(id)
}, { immediate: true })

再看 deep。上一節看到 getter 和 ref 來源只比較回傳值，裡面的屬性改了不算；深層監聽（deep watch）就是讓 Vue 走過來源的每一層，把每個屬性都讀一次、建立追蹤，於是任何一層改了都會觸發。備註表單直接把 reactive 物件 form 當來源，本來就是深層，options.sugar 改了會觸發；如果表單放在 ref 裡，就要加 deep: true。

深層監聽有代價：每次執行，Vue 都要走過整棵物件，把每個屬性讀一次來建立追蹤。一張點餐表單沒差；一個 5000 筆品項的陣列，每改一個字就整個走一遍，就會變慢。處理方式依序是：

  • 能用 getter 指出真正關心的欄位就用 getter：watch(() => menu.value.length, cb)。
  • 只需要前幾層就給數字：{ deep: 1 } 只追蹤第一層屬性。實測 deep: 1 時，改 o.a.b.c 不觸發，換掉 o.a 才觸發。
  • 大陣列配第 4 課的 shallowRef，整個換掉才通知，watch 不用 deep。

最後是 once：只想在資料第一次改變時做一件事，做完就不再管，例如客人第一次選了門市才載入引導教學。它執行一次就自動停止，不用自己記得關掉。

到這裡，你已經能精確指定「盯什麼、多深、什麼時候開始」。不過來源寫錯這麼容易，自然會想問：能不能乾脆不寫來源，讓 Vue 自己找出函式用到了哪些資料？

能不能不寫來源？watchEffect 與 await 之後的讀取

可以，這就是 watchEffect(fn)。它不用寫來源：建立時立刻執行 fn 一次，執行期間讀到的響應式資料全部變成依賴，之後任何一個改變就重跑。這就是你在第 2 課自己寫的 effect。

watchEffect(() => {
  document.title = `${store.name}（${cart.count}）`   // 讀到 store.name 和 cart.count，兩個都是依賴
})

點餐頁把門市名稱和購物車數量放在分頁標題上，用 watchEffect 很合適：依賴就是函式裡讀到的那兩個，不用另外列一次，以後加了第三個也會自動追蹤。

那搜尋能不能也改用 watchEffect？問題出在 await。第 2 課講過，追蹤只發生在函式同步執行的期間：那時「目前正在執行的 effect」才有設定，track 才知道要記在誰身上。遇到 await（TS 課第 9 課），函式先回傳，後半段在之後的 microtask 才執行，那時已經沒有目前的 effect 了：

watchEffect(async () => {
  const res = await fetch(`/api/menu?q=${filters.keyword}`)   // filters.keyword 在 await 之前讀：有追蹤
  const list = await res.json()
  menu.value = list.filter(p => p.storeId === filters.store)   // await 之後讀：沒有追蹤
})

客人改了門市篩選 filters.store，這個 effect 不會重跑，菜單停在舊門市。官方文件的說法是：async 的 watchEffect，只有第一個 await 之前讀到的屬性會被追蹤。在 Vue 3.5.44 驗證過，改 await 之後讀的值，effect 執行次數不變。更麻煩的是程式看起來完全正常，要等有人剛好改了那個值才會發現。

所以兩者的分工是：

  • watch：依賴很明確、需要舊值、不想一建立就執行、callback 裡有 await。讀程式的人一眼看得出「什麼改了會觸發」。
  • watchEffect：依賴就是函式裡讀到的那幾個、全部同步，例如同步 document.title。

有 await 的副作用，用 watch 把來源寫清楚，比記住「await 之前要先讀」可靠。所以點餐頁的搜尋維持用 watch(keyword, …)。但來源寫對了，第一張單的問題還在：打「拿鐵」仍然可能顯示「拿」的結果。這和追蹤無關，而是兩個請求誰先回來的問題。

搜尋框為什麼顯示舊結果？競態與清理函式

先看點餐頁原本的搜尋 watcher，它在追蹤上沒有任何錯：

// ✗ 天真的搜尋
watch(keyword, async kw => {
  results.value = await api.search(kw)
})

客人打「拿」，watcher 送出請求 A；接著補一個字變「拿鐵」，watcher 再送出請求 B。兩個請求同時在路上，誰先回來由網路和伺服器決定，不由送出的順序決定。只要 A 比較慢，就會發生下面這件事：

這種「結果取決於誰先完成，而先後順序你控制不了」的狀況叫競態（race condition）。TS 課第 12 課看過純 JavaScript 的版本，現在它發生在 watcher 裡。天真版本的問題是：每個請求回來都直接寫進 results，沒有人去問「這個回應還是不是客人要的」。

修法的想法很直接：新的一次開始時，取消上一次。上一次的請求被取消，就不會有晚回來的舊結果。要做到這件事，需要一個時機點：「watcher 要重跑了，在跑新的一次之前，讓我先收拾上一次留下的東西」。Vue 提供的就是這個時機點，叫清理函式（cleanup）：你在 callback 裡登記一個函式，Vue 會在兩個時候呼叫它：

  • watcher 下一次執行之前：用來取消上一次的請求或計時器。
  • watcher 停止時：例如元件卸載，用來取消最後一次還沒完成的事。

登記的方法是從 vue import onWatcherCleanup，在 callback 裡呼叫它（另一種舊寫法見課末）。搭配 TS 課學過的 AbortController，搜尋改成這樣：

import { onWatcherCleanup, ref, watch } from 'vue'

watch(keyword, async kw => {
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort())   // 在 await 之前登記
  try {
    results.value = await api.search(kw, { signal: controller.signal })
  } catch (e) {
    if (controller.signal.aborted) return       // 我們自己取消的，不是錯誤
    error.value = e
  }
})

照著時間軸走一次：打「拿」時，watcher 建立 controller A、登記「abort A」、送出請求 A。打「拿鐵」時 watcher 要重跑，Vue 先呼叫上一次登記的清理函式，A 被 abort；然後才執行新的一次，建立 controller B、送出請求 B。真正的 fetch 收到 abort 會以 AbortError reject（TS 課第 11 課），所以 A 的 await 丟出錯誤，進到 catch，不會寫 results。

catch 裡為什麼要先檢查 signal.aborted？因為被取消不是失敗：是我們自己決定不要這個結果了，不該在畫面上跳出「搜尋失敗」。先確認是不是自己取消的，是就直接 return；不是才當成真正的錯誤存起來。

每次執行都 new 一個新的 controller 看起來很浪費，其實正是重點：清理函式是一個閉包，它記住的是「這一次」的 controller，所以下一次執行前 Vue 呼叫它，abort 到的剛好是上一次的請求。

onWatcherCleanup 一定要在第一個 await 之前呼叫。官方文件寫明它只能在 watcher 同步執行期間呼叫，理由和 watchEffect 的追蹤一樣：await 之後 Vue 不知道你是哪個 watcher。在 Vue 3.5.44 放到 await 後面，會印出 [Vue warn] onWatcherCleanup() was called when there was no active watcher to associate with.，而且清理函式根本沒登記上，舊請求照樣蓋掉新結果。

下面用普通 JavaScript 模擬同樣的事，不需要 Vue：run 扮演 watcher，每次執行前先呼叫上一次的清理函式。執行後比較兩行輸出：沒清理時最後顯示的是「拿」的舊結果，有清理時是「拿鐵」。

第一張單修好了。第二張單的「打十個字存十次」看起來是另一個問題，其實可以用同一個清理函式解決，只是這次要取消的不是請求，而是計時器。

備註為什麼打十個字存十次？用清理函式做防抖

存草稿的 watcher 盯著備註表單 form，每改一個字就觸發一次，每次都馬上存，所以打十個字就存十次。客人其實只在乎最後的內容，中間九次都是浪費，還可能因為競態讓較舊的草稿最後才寫進去。

我們要的行為是：客人還在打字時先不存，停下來一段時間（例如 800ms）都沒再改，才存一次。這個做法叫防抖（debounce）：每次改動都取消上一個還沒到時間的計時器，重新計時，所以只有最後一次改動之後的計時器能走完（TS 課第 12 課）。

「每次改動都取消上一個計時器」正是清理函式的工作：watcher 重跑前，Vue 先呼叫上一次登記的清理函式，我們在裡面 clearTimeout 就好。

watch(form, () => {
  const timer = setTimeout(() => saveDraft(), 800)
  onWatcherCleanup(() => clearTimeout(timer))   // 下一次改動、或 watcher 停止時取消
})

客人連打十個字：第一個字設了計時器，第二個字讓 watcher 重跑，Vue 先清掉第一個計時器，再設新的；如此一路到第十個字。只有第十個字的計時器沒被清掉，800ms 後存一次。form 是 reactive 物件，當來源本來就是深層，巢狀的 options.sugar 改了也會觸發。

存草稿時還有一件事要處理：交出去的資料。form 是 reactive proxy，直接把它交給 saveDraft，對方拿到的是同一個 proxy，之後客人再改表單，「已存的草稿」也跟著變。要交出去的資料要先複製成普通物件，但 structuredClone(form) 會丟 DataCloneError（Proxy 不能被結構化複製，3.5.44 實測），要先用第 4 課的 toRaw 取出原物件：structuredClone(toRaw(form))。交給 postMessage、IndexedDB 也是同樣的道理。

放回防抖程式，就是在計時器到時的那一刻才複製，存的是客人停手時的內容：

watch(form, () => {
  const timer = setTimeout(() => saveDraft(structuredClone(toRaw(form))), 800)
  onWatcherCleanup(() => clearTimeout(timer))
})

練習 2 要求的「draft 是當下內容的普通物件複本，之後再改 form 不會影響它」，指的就是這一步。

💡 實務上：凡是「輸入就打 API」的地方都要處理競態
搜尋框、切換門市重新載入訂單、分頁或篩選條件改變重抓列表，都是同一個模式：使用者改得比回應快，就會出現舊結果蓋掉新結果。這種 bug 在本機網路快時幾乎重現不了，常是客服回報「畫面跟我選的不一樣」才發現，可以在 DevTools 把網路調慢來驗證。實務上通常防抖和取消一起用：防抖減少送出的請求數，abort 確保只採用最後一次。注意 abort 只是前端不再等，伺服器可能已經收到並處理了，所以會改資料的請求（送出訂單）不能靠取消來防重複，要另外擋重複送出。專案裡通常會把這套包成共用的資料載入工具（第 17 課），不會每個頁面各寫一次。

「存十次」解決了，但第二張單還有後半句：離開點餐頁之後還在存。清理函式只會在 watcher 重跑或停止時被呼叫，如果這個 watcher 從來沒有停止，它就會一直活著。下一節看 watcher 什麼時候會停。

離開點餐頁後，為什麼還在存草稿？停止、暫停與恢復

先把上一節的存草稿 watcher 放回它在點餐頁裡的真實位置。點餐頁要先拿到門市設定（例如草稿要存到哪個門市），才開始自動存草稿，所以原本是這樣寫的：

onMounted(async () => {
  await getConfig()
  watch(form, () => { /* 上一節的防抖存草稿 */ })   // ✗ 離開點餐頁後還在存
})

上一節只修了防抖，沒動它建立的位置；離開頁面後還在存，就出在這個位置。要回答為什麼，得先知道 watcher 平常是怎麼停下來的。你在元件裡寫 watch，從來沒有手動關過它，卻不會在離開頁面後繼續跑，是因為 Vue 在背後替你收拾了。

收拾的機制叫 effect scope：一個收集 watcher、computed 的容器。在這個容器存在期間建立的 watcher 都會被放進去；停止容器，就一次停止裡面全部的 watcher，並執行它們的清理函式。每個元件都有自己的 effect scope，元件卸載時 Vue 就停止它。你也可以用 effectScope() 自己建一個（第 12 課深入）。

關鍵在「建立的時候，目前的容器是誰」。Vue 只有在執行 <script setup>（或 setup()）的同步期間，才知道「目前在建立哪個元件」，這時建立的 watcher 會放進這個元件的 effect scope，卸載時自動停止。問題出在非同步建立的 watcher。存草稿是 await 之後建立的一例，練習 3 的訂單看板是另一例：它在 setTimeout 裡建立 watch(storeId, load)。下面用同一個 watch(storeId, load) 對照三種寫法：

<script setup lang="ts">
watch(storeId, load)          // ✓ 同步建立：卸載時自動停止

setTimeout(() => {
  watch(storeId, load)        // ✗ 這時已經不在 setup 的同步執行期間，不屬於任何元件
}, 300)

onMounted(async () => {
  const config = await getConfig()
  watch(storeId, load)        // ✗ 一般 async 函式的 await 之後也一樣
})
</script>

這和 watchEffect 的追蹤、onWatcherCleanup 是同一個道理：Vue 靠「目前正在執行什麼」來做記錄，await 或計時器之後，那個「目前」已經不在了。官方文件的說法：在非同步 callback 裡建立的 watcher 不會綁在元件上，必須自己停止，否則會造成記憶體洩漏：元件卸載後，它還在對著已經不存在的畫面執行，切換頁面幾次就累積好幾個。本節開頭的存草稿 watcher 就是寫在 onMounted 的 await 之後，所以離開頁面也沒停。（<script setup> 最上層的 await 有個例外，見課末。）

非同步建立的 watcher 要自己停。watch() 和 watchEffect() 都會回傳一個把手（WatchHandle），也就是控制這個 watcher 的函式；呼叫它就停止，停止時同樣會執行清理函式：

const stop = watch(storeId, load)
stop()                        // 停止，之後 storeId 改了也不會執行

// 3.5 起也有 pause／resume
const { pause, resume } = watch(storeId, load)
pause()                       // 暫時不執行，例如分頁切到背景時
resume()                      // 恢復

除了停止，把手上還有 pause() 和 resume()：暫時不執行、之後再恢復，例如分頁切到背景時先暫停。3.5.44 實測：pause() 期間來源有改變的話，resume() 時 callback 會補執行一次，不是把那段期間的改變丟掉。

原則：能同步建立就同步建立；真的要延後（等設定載入、等動畫）時，留著把手，在 onUnmounted 停止它，延後用的計時器也一起清掉。點餐頁的存草稿改成在 setup 裡同步建立，第二張單就完整修好了：防抖讓它只存一次，effect scope 讓它在離開頁面時停止，停止時清理函式順便清掉還沒走完的計時器。

💡 實務上：沒停掉的 watcher 會變成「重複打 API」的 bug
單頁應用切換頁面不會重新載入，元件卸載後沒停掉的 watcher 還活著：在點餐頁和訂單頁之間切幾次，換一次門市就打好幾次同樣的 API，或在已經離開的頁面跳出錯誤提示。徵兆通常是 Network 面板裡同一個請求重複出現，而且次數隨著切換頁面越來越多。review 時看到 watch 寫在 setTimeout、.then() 或 async 函式的 await 之後，就該問「誰負責停止它」；最好的答案通常是改成在 setup 裡同步建立，用條件判斷要不要執行。

補充與查表

主線用不到、但查版本或看到舊程式碼時會用到的細節。

版本備註

練習用的是 Vue 3.5.44，以下全部可用。維護舊專案時，先看 package.json 的 Vue 版本（依 Vue 官方 API 文件）：

  • once: true：3.4 起。
  • deep 給數字（例如 { deep: 1 }）限制往下追幾層：3.5 起。
  • onWatcherCleanup(fn)：3.5 起，從 vue import。
  • pause()／resume()：3.5 起，從 watch()、watchEffect() 回傳的把手取得。

清理函式的另一種寫法：onCleanup

3.5 以前沒有 onWatcherCleanup，清理函式是用 callback 的第三個參數 onCleanup 登記的：watch(src, (val, old, onCleanup) => { onCleanup(fn) })。這個寫法現在也能用，舊專案裡常看到，作用和 onWatcherCleanup 一樣。

<script setup> 最上層的 await

非同步建立的 watcher 不屬於元件，有一個例外：<script setup> 最上層的 await（這種元件要放在 <Suspense> 裡使用）。編譯器會在 await 之後把目前的元件接回來，所以那之後建立的 watcher 仍然屬於元件（Vue 官方 <script setup> 文件）。這個保護只限最上層，寫在 onMounted(async …)、setTimeout 裡的都沒有。

練習

在 learn/ 執行 node check.mjs vue 05。練習 2、3 的測試用假計時器（fake timers）：vi.useFakeTimers() 之後，setTimeout 不會真的等，測試用 vi.advanceTimersByTime(800) 手動把時間往前推 800ms，所以每次結果都一樣、也不用真的等。練習 1 的假 API 由測試決定每個請求什麼時候、以什麼順序回來；請求的 signal 被 abort 時，它會像真正的 fetch 一樣以 AbortError reject。

練習 1：useMenuSearch(keyword, api) 回傳 { results, error }。keyword 改變時呼叫 api.search(keyword, { signal })；新的搜尋開始或關鍵字被清空時，取消上一個還沒回來的請求，results 只採用最新一次的結果。keyword 是空字串（或只有空白）時清空 results、不發請求。被取消的請求不能設定 error；真正的錯誤要存進 error 並清空 results；每次開始新的搜尋，error 先設回 null。所屬的 effect scope 停止（元件卸載）時，進行中的請求也要取消，所以要用清理函式，不能只靠「下一次執行時自己 abort 上一個」。測試會讓「拿鐵」先回來、「拿」後回來，並檢查沒有 Vue 警告。

練習 2：useDraftAutosave(form, save, { delay = 800 })：form 的任何欄位（包括巢狀的 options.sugar）改變後 800ms 呼叫一次 save(draft)；800ms 內連續修改只存最後一次。draft 是當下內容的普通物件複本，之後再改 form 不會影響它。測試在 effectScope() 裡呼叫你的函式，scope.stop() 之後不能再存檔，也不能留下計時器。

練習 3：OrderBoard.vue 等進場動畫跑完（300ms）才開始監聽 session.storeId，所以 watch 寫在 onMounted 的 setTimeout 裡，結果卸載之後切換門市還會呼叫 load()。修正它：保留「300ms 後開始監聽」的行為，卸載後不再呼叫 load()；300ms 還沒到就卸載的話，也不能開始監聽、不能留下計時器。

練習 4：state 是 reactive({ qty: 1 })，寫 watch(state.qty, cb)，之後 state.qty++，會怎樣？

✓ state.qty 在呼叫 watch 之前就被讀出來，傳進去的只是數字 1，跟 proxy 沒有連線。Vue 不會丟錯，而是在開發模式下警告 Invalid watch source: 1，這個 watcher 什麼都不做。要寫 watch(() => state.qty, cb)，讓 Vue 每次執行 getter 時重新讀、重新追蹤。nextTick 只影響「什麼時候執行」，前提是有東西被追蹤。

練習 5：watchEffect(async () => { const res = await fetch(url); list.value = filterBy(await res.json(), filters.store) })。之後改 filters.store，effect 會重跑嗎？

✓ 追蹤只發生在同步執行期間。第一個 await 之後的程式在之後的 microtask 才執行，那時 Vue 已經不知道是哪個 effect 在讀，所以 filters.store 不會變成依賴，不管什麼時候改都一樣。修法：在 await 之前先讀出來（const store = filters.store），或改用 watch 明確寫出來源。

練習 6：watch(() => state.items, cb) 沒有加 deep，執行 state.items.push('可頌')，cb 會執行嗎？

✓ getter 來源只用 Object.is 比較回傳值：push 之後 state.items 還是同一個陣列，判定沒變。自動深層只適用於「直接把 reactive 物件當來源」（watch(state, cb)）。要讓 push 觸發，加 { deep: true }，或監聽 () => state.items.length 這類會變的值，或用不可變更新換掉整個陣列。

常見錯誤

  • 用 watch 同步衍生資料：多一份狀態要追著更新，第一次、深層、時機都容易錯。算得出來的值用 computed。
  • 把 state.qty 當來源：傳進去的是值，Vue 警告 Invalid watch source。改成 getter () => state.qty。
  • 混淆 getter 來源與 reactive 物件來源：watch(() => form, cb) 不深層，巢狀屬性改了不觸發；watch(form, cb) 本來就深層。
  • 對大型物件 deep watch：每次都走過整棵物件。用 getter 指出真正關心的欄位、deep 給數字，或用 shallowRef 整個替換。
  • 忘了 immediate 時第一次的 oldValue 是 undefined：拿它比較或當參數前先判斷。
  • async 的 watchEffect 在 await 之後讀資料：那些資料沒被追蹤，改了不會重跑。有 await 的副作用改用 watch 寫清楚來源。
  • onWatcherCleanup 放在 await 之後：沒登記上，Vue 只印警告，舊請求照樣蓋掉新結果。在第一個 await 之前登記。
  • 把取消當成錯誤顯示：被 abort 的請求會以 AbortError reject。先檢查 signal.aborted，是自己取消的就直接 return。
  • 把 reactive 物件直接交給外部（存檔、送出、postMessage）：對方拿到的是 proxy，之後的修改會改到它；structuredClone(proxy) 會丟 DataCloneError。用 structuredClone(toRaw(obj)) 或自己組出普通物件。
  • 在 setTimeout 或 async 函式的 await 之後建立 watcher 卻不停止：它不屬於元件，卸載後繼續執行。留著 watch() 回傳的把手，在 onUnmounted 呼叫，延後用的計時器也要清掉。

小結

  • 要一個值用 computed，要對外做事（請求、存檔、操作 DOM）才用 watch。點餐頁的總金額改成 computed，搜尋和存草稿才是 watch。
  • 來源要是 ref、getter、reactive 物件或它們的陣列；reactive 物件來源預設深層，getter 只用 Object.is 比較回傳值。
  • immediate 第一次的舊值是 undefined；deep 有成本，3.5 起可以給數字；once（3.4 起）只執行一次。
  • watchEffect 只追蹤同步執行期間讀到的資料，await 之後的讀取不算；有 await 就用 watch。
  • 競態用清理函式解決：在 await 之前用 onWatcherCleanup（或 onCleanup）登記 controller.abort()；被取消不是錯誤。同一招登記 clearTimeout 就是防抖。
  • 同步建立的 watcher 放在元件的 effect scope，隨元件停止；非同步建立的要自己 stop()。3.5 起還有 pause()／resume()。
