階段 4：重用與型別 · 第 12 課

composables：抽出有狀態的邏輯

咖啡店的點餐頁和外帶頁都要顯示「目前離線，訂單會在恢復連線後送出」，也都有取餐倒數。兩頁各自複製了一份 addEventListener('online') 和 setInterval。後來有人修了點餐頁的計時器沒清掉的問題，外帶頁忘了改，記憶體洩漏還在。另一位同事想避免這種事，把購物車的數量抽成共用函式，結果店內點餐和外帶的購物車數字開始互相影響：店內加一杯，外帶的角標也跟著變成 1。

這課的任務是把這兩頁重複的邏輯整理成一組 composable：連線狀態、取餐倒數、集點卡、購物車數字，而且要抽得對：修一次兩頁都好、離開頁面會清乾淨、該各自一份的不會互相干擾。最後會修好叫號看板（PickupBoard）離開後計時器還在跑的 bug。

這課的路線：
  1. 兩頁重複的連線監聽要抽成什麼？composable 是什麼、為什麼一定是「有狀態」的邏輯才抽，以及開場兩個問題的最小答案。
  2. 抽出來的 composable 該回傳什麼，呼叫端才能放心解構、又不會到處亂改狀態？
  3. 顧客換了，集點卡的點數為什麼沒跟著換？讓參數接受數字、ref 或 getter，並在對的地方讀它。
  4. 搬進 composable 之後，誰來清掉計時器和監聽？沒有元件的地方（測試、store）又怎麼清？
  5. 購物車數字為什麼互相影響？composable 該在哪裡呼叫？最後回頭檢查：好的 composable 長什麼樣、什麼時候不要抽。
這課會用到：
  • 第 5 課的 watch 與清理函式：來源改變時執行副作用，用 onWatcherCleanup 在下一次執行前取消上一次；setup 裡同步建立的 watcher 會隨元件停止。
  • 第 8 課的 onMounted／onUnmounted：掛載後才碰 DOM、開計時器，卸載時把計時器和事件監聽收掉。
  • TS 課第 1 課的閉包：函式回傳之後，回傳出去的東西仍然記得函式裡的變數，每呼叫一次就有一組新的。

兩頁各複製一份的連線監聽，要抽成什麼？

先看開場第一個問題為什麼會發生。點餐頁和外帶頁的連線監聽是用複製貼上共用的：程式碼有兩份，修 bug 就要修兩次，漏一次就留一個洩漏。要讓它只有一份，就得把這段邏輯搬到兩頁都能呼叫的地方。

問題是這段邏輯不是一般的函式。它有一個會變的值（現在有沒有網路），有兩個事件監聽在背景更新這個值，畫面要跟著這個值重畫，頁面關掉時監聽還要移除。這些在元件裡是用 ref、onMounted、onUnmounted 寫的，它們能不能搬出元件？

可以。ref、computed、watch、onMounted 這一組函式叫做組合式 API（Composition API），你每天在 <script setup> 裡用它們組出元件的邏輯。它們都是普通的 JavaScript 函式，不是只能寫在元件檔案裡的語法，所以可以被搬進另一個函式，由那個函式在元件的 setup 期間代為呼叫。

這樣的函式就叫 composable（組合式函式）：用組合式 API 封裝一段有狀態的邏輯，讓好幾個元件重用。慣例是以 use 開頭，看到 useXxx() 就知道它會建立響應式狀態、可能註冊副作用，要照 composable 的規則呼叫（後面會講規則）。

// composables/useOnline.ts
import { ref } from 'vue'
import { useEventListener } from './useEventListener'

export function useOnline() {
  const online = ref(navigator.onLine)
  useEventListener(window, 'online', () => { online.value = true })
  useEventListener(window, 'offline', () => { online.value = false })
  return { online }
}

// 點餐頁、外帶頁都只要一行
const { online } = useOnline()

這裡的 useEventListener 是另一個更小的 composable：註冊事件，並負責在不用的時候移除。它怎麼做到「自動移除」，是後面〈誰來清掉計時器和監聽〉那一節的主題，練習 1 你會自己寫一個。現在只要看出結構：清理的邏輯寫在 composable 裡一次，兩頁呼叫同一個函式，修一次兩頁都好。

為什麼強調「有狀態」？把價格格式化成 NT$ 110 這種函式，給同樣的輸入永遠得到同樣的輸出，不記得任何東西、也不需要清理，寫成 utils/ 裡的普通工具函式就好，不需要叫 useFormatPrice。composable 管的是會隨時間改變的東西：連線狀態、倒數的秒數、目前的搜尋結果，以及讓它們改變的事件監聽和計時器。判斷方法是問：這段邏輯裡有沒有 ref、watch 或生命週期？沒有，就不是 composable。

那 composable 裡的 online 是存在哪裡？答案是閉包，和 TS 課第 1 課的 makeStampCard() 一樣：useOnline() 每被呼叫一次，就在那次呼叫裡建立一個新的 online；函式回傳之後，回傳出去的物件和那兩個監聽器仍然記得它。差別只在這個變數是 ref，所以改了會通知畫面。點餐頁和外帶頁各呼叫一次，就各有一個 online，互不相干。

這也就是開場兩個問題的最小答案：

  • 連線監聽和倒數重複：抽成 composable，清理寫在裡面一次，兩頁都呼叫它。
  • 購物車數字互相影響：同事抽的函式把 count 寫在函式外面，所以整個 app 只有一份；寫在函式裡面，才會像 online 一樣每次呼叫各一份。

答案的方向有了，但「抽出來」只是開始。接下來要決定這個函式交給呼叫端的東西長什麼樣子：同樣是回傳狀態，有一種寫法會讓呼叫端一解構就壞掉。

抽出來的 composable 該回傳什麼，呼叫端才能放心解構？

上一節的 useOnline 回傳 { online }，呼叫端寫 const { online } = useOnline()。這個形狀不是隨手寫的，它是官方文件建議的慣例：composable 回傳一個普通物件，裡面的每個值是 ref。用取餐倒數來看：

// ✓ 普通物件，裡面是 ref
function useCountdown(seconds: number) {
  const left = ref(seconds)
  // …每秒減 1…
  return { left, reset }
}
const { left } = useCountdown(300)    // left 還是 ref，範本裡會更新

// ✗ 回傳 reactive
function useMouse() {
  const state = reactive({ x: 0, y: 0 })
  return state
}
const { x } = useMouse()              // x 是數字 0，和 state 斷線，之後永遠不變

第二段換成了滑鼠座標，因為倒數只有一個值，沒有人會想把它包進 reactive；當狀態有兩個以上相關的值（x 和 y），才會有人順手寫成一個 reactive({ x, y }) 回傳，這正是會出事的形狀。

為什麼會斷線？解構 const { x } = state 等於 const x = state.x：在那一刻讀一次屬性，把讀到的數字 0 存進一個普通變數。reactive 的響應性靠的是「每次讀屬性都經過 Proxy」，存進普通變數之後就再也不經過 Proxy，之後 state.x 怎麼變都和 x 無關。這就是第 4 課的「解構 reactive 會失去響應」。更麻煩的是 Vue 不會報錯，畫面只是靜靜地不更新。

回傳 ref 組成的普通物件就沒有這個問題：解構拿到的是 ref 物件本身，不是它當下的值，讀 .value 時才取值，範本裡也會自動展開。呼叫端如果比較喜歡 mouse.x 的寫法，可以自己包一層 reactive(useMouse())，裡面的 ref 會被自動展開。回傳 ref 讓兩種寫法都可行，決定權留給呼叫端；回傳 reactive 則替呼叫端做了一個會出錯的決定。

回傳的形狀還有第二個慣例：狀態對外唯讀，修改透過函式。用購物車數字想想看：如果 useCartBadge() 直接回傳可寫的 count，任何元件都能寫 count.value = 99。某天角標顯示錯了，你得搜尋整個專案找誰寫了 count.value。改成回傳 readonly(count) 加上 add()、clear()：

  • 能改數字的程式只在 composable 裡那兩個函式，出錯時只要看這兩處。
  • 規則（例如數量不能是負的）寫在 add() 裡一次，所有呼叫端都會遵守。
  • 有人還是寫了 count.value = 99，開發模式下 Vue 會警告，值不會變，問題在開發時就浮現。

練習 3 要做的就是這個形狀。回傳值處理好了，但目前的參數都是寫死的：useCountdown(300) 收一個數字就結束。集點卡不一樣，它要依「目前的顧客」載入點數，而目前的顧客會換。

顧客換了，集點卡的點數為什麼沒跟著換？

點餐頁和外帶頁都要顯示顧客的集點卡，所以載入點數也抽成 useStampCard(customerId, api)。問題出在 customerId：呼叫端手上的它可能是三種樣子。

  • 寫死的數字：例如測試裡直接傳 1。
  • 一個 ref：頁面自己用 ref 記住目前選的顧客。
  • 一個 getter () => props.customerId：顧客 id 從 prop 傳進來。這裡不能直接傳 props.customerId，那樣傳出去的只是當下的數字，之後 prop 改了 composable 也不知道；包成 getter，composable 才能在需要時再讀一次（第 9 課）。

如果 composable 只接受 ref，用 prop 的呼叫端就得先 computed(() => props.customerId) 轉一次；只接受數字，就不會跟著顧客切換。理想是三種都收，Vue 為此提供了一個型別和一個函式：

  • MaybeRefOrGetter<T>：一個泛型型別（TS 課第 19 課），等於 T | Ref<T> | (() => T)。把參數宣告成 MaybeRefOrGetter<number>，數字、ref、getter 三種都能傳。
  • toValue(x)：把三種統一取出值。ref 取 .value、getter 呼叫它、普通值原樣回傳。

型別解決了「能傳進來」，真正決定會不會跟著換的是在哪裡呼叫 toValue。toValue 只是「現在讀一次」，它本身不會追蹤任何東西：

// ✗ 在函式開頭讀一次
export function useStampCard(customerId: MaybeRefOrGetter<number>, api: StampApi) {
  const id = toValue(customerId)          // 這時是 1，之後就固定是 1
  watch(() => id, load, { immediate: true })
  …
}

// ✓ 在 watch 的 getter 裡讀：每次 getter 執行都重新讀、重新追蹤
watch(() => toValue(customerId), load, { immediate: true })

第一種寫法的錯誤很隱蔽：它有 watch，看起來會追蹤。但 getter () => id 讀的是普通變數 id，裡面沒有任何響應式資料。第 5 課講過，watch 只追蹤 getter 執行期間讀到的響應式資料；這個 getter 什麼都沒讀到，所以顧客換了也不會再執行。

第二種寫法把 toValue 搬進 getter。每次 getter 執行，toValue 都會重新讀一次來源，這個「讀」發生在 getter 執行期間，所以被追蹤：

  • 傳 ref：toValue 讀了 .value，ref 改變時 watch 重新執行。
  • 傳 getter：toValue 呼叫了它，它又讀了 props.customerId，prop 改變時 watch 重新執行。
  • 傳數字：getter 永遠回傳同一個值，只會執行 immediate 那一次，剛好就是「載入一次」。

同一行程式碼對三種輸入都做出正確的事，這就是 MaybeRefOrGetter 加 toValue 要配在一起用的原因。

還有一個省略 getter 的誘惑：直接寫 watch(customerId, load)。ref 和 getter 是 watch 能接受的來源，數字不是。呼叫端傳數字時，Vue 3.5.44 實測會印出 Invalid watch source: 5 警告，數字這條路就不成立。包一層 () => toValue(customerId)，三種輸入都成立。

這個參數設計不只用在集點卡，最常見的場景其實是商品詳細頁。

💡 實務上：網址變了，資料卻沒跟著換
在「拿鐵」的商品頁點推薦的「卡布奇諾」，網址換了，但用的是同一個頁面元件，Vue Router（第 19 課）會直接重用它，setup 不會重跑。如果 composable 只在開頭讀一次 id，畫面就停在拿鐵，這是「要重新整理才會對」這類回報的常見原因。把 () => route.params.id 這樣的 getter 傳進去、在 watch 裡 toValue，切換時就會自己重新載入。使用者快速連點時，舊請求可能比新請求晚回來，所以會載入資料的 composable 都要「只採用最新一次」，練習 2 練的就是這件事。

到這裡，useStampCard 裡有一個 watch，useOnline 裡有兩個事件監聽，useCountdown 每秒減 1 要靠一個計時器。開場的洩漏就是這類東西沒被移除造成的。它們現在住在 composable 裡，不在元件裡，誰負責在離開頁面時清掉它們？

搬進 composable 之後，誰來清掉計時器和監聽？

在元件裡，第 8 課的做法是在 onUnmounted 裡移除。composable 在元件的 setup 裡被呼叫時，這樣寫也能動，因為 Vue 知道是哪個元件正在執行 setup。但 composable 不一定在元件裡被呼叫：下一節會看到測試和 Pinia store 也會呼叫它。這時 onUnmounted 不知道要掛在哪個元件上，Vue 3.5.44 會警告：

[Vue warn]: onUnmounted is called when there is no active component instance to be associated with.

而且清理函式根本沒登記上，計時器永遠不會被清掉。所以 composable 需要一個不依賴元件的清理方式。要理解它，得先認識 Vue 管理副作用的單位：effect scope。

effect scope 是一個收集副作用的容器。只要有一個 scope 處於「作用中」，這段期間建立的 watch、computed，以及登記的清理函式，都會被記在這個 scope 裡。之後呼叫這個 scope 的 stop，它會一次停掉所有記下的 watcher、執行所有記下的清理函式。第 5 課提過「setup 裡同步建立的 watcher 會隨元件停止」，背後就是這個機制：每個元件都有自己的 effect scope，setup 執行期間它是作用中的 scope，元件卸載時 Vue 呼叫它的 stop。

有了 scope，清理就不必綁元件，綁 scope 就好。onScopeDispose(fn) 做的就是這件事：把 fn 登記到目前作用中的 scope，scope 停止時執行。在元件裡，scope 停止就是卸載；在元件外，就是有人呼叫 stop()。官方 API 文件把它描述為「可重用組合式函式裡，不綁定元件的 onUnmounted 替代品」。

三種清理方式在兩個環境裡的行為整理如下：

在元件 setup 裡在 effectScope().run() 裡
onUnmounted(fn)卸載時執行✗ 警告，永遠不執行
onScopeDispose(fn)卸載時執行scope.stop() 時執行
watch 的清理函式（onCleanup／onWatcherCleanup）下次執行前、卸載時執行下次執行前、scope.stop() 時執行

表的最後一列是另一種情況要用的。useOnline 的目標是 window，從頭到尾不會變，用 onScopeDispose 在最後移除一次就夠。但如果目標會變，例如 template ref 一開始是 null，掛載後才是元素，之後還可能換成另一個元素，只在最後移除一次就不夠：目標換掉時，舊元素上的監聽也要移除。這時把「註冊」寫在 watch 裡、把「移除」寫在 watch 的清理函式裡：目標換掉時，清理函式先從舊目標移除，再對新目標註冊；scope 停止時清理函式也會執行一次。練習 1 的 useEventListener 就是這個寫法。

所以 composable 的清理只要守一條規則：每個註冊都配一個移除，放在 onScopeDispose 或 watch 的清理函式裡。這樣不管它在元件裡還是元件外被呼叫，都會清乾淨。

回到開場那個沒清掉的取餐倒數。照這條規則，把「開計時器」和「清計時器」綁在一起，抽成一個更小的 composable useInterval，組法和 useOnline 用 useEventListener 一樣：

// composables/useInterval.ts
import { onScopeDispose } from 'vue'

export function useInterval(fn: () => void, ms: number) {
  const id = setInterval(fn, ms)
  onScopeDispose(() => clearInterval(id))   // 註冊和移除寫在一起
}

// useCountdown 裡每秒減 1，就交給它
useInterval(() => { if (left.value > 0) left.value-- }, 1000)

之後任何地方要定時做事，都呼叫 useInterval，不再直接寫 setInterval，就不會再有哪一頁忘了清。後面的叫號看板也用它。

💡 實務上：漏掉的清理，常在「開很久」的頁面才出事
後台的訂單看板、店內的叫號螢幕這種一整天不關的頁面最容易出事：每切換一次畫面就多一組沒移除的監聽或計時器，幾個小時後變慢，同一支 API 一次被打好幾次。開發時頁面常重新整理，很難發現。Code review 時資深工程師會逐一對照：每個 addEventListener、setInterval、WebSocket 或訂閱，有沒有對應的移除放在 onScopeDispose 或 watch 的清理函式裡。懷疑有洩漏時，來回切換幾次頁面，再看瀏覽器 Network 面板的請求有沒有越來越密，比用猜的快。

上面一直說「在元件外被呼叫」，但沒有元件，就沒有元件替你建 scope、在卸載時 stop。這時 scope 要從哪裡來？

沒有元件的地方（測試、store），scope 從哪裡來？

composable 在元件外被呼叫的情況比想像中常見：Pinia 的 setup store（第 15 課）、測試、某個只在背景執行的模組。這些地方沒有元件，你就用 effectScope() 自己建一個 scope，扮演元件原本的角色：

import { effectScope } from 'vue'

const scope = effectScope()
const card = scope.run(() => useStampCard(customerId, api))!   // run 期間建立的 watch、computed、onScopeDispose 都收進 scope

// 用完了
scope.stop()   // 停掉裡面所有 watcher，執行所有清理函式

對照元件來看：scope.run(fn) 相當於元件執行 setup，執行 fn 的期間這個 scope 是作用中的，fn 裡建立的東西都記進來，fn 的回傳值就是 run 的回傳值；scope.stop() 相當於元件卸載。上一節的 onScopeDispose 在這裡照樣有效，這正是它比 onUnmounted 通用的地方。

這也是測試 composable 的方法。不用掛載任何元件，在 effectScope().run() 裡呼叫 composable，操作它、檢查回傳的 ref，最後 scope.stop()，再確認計時器停了、監聽移除了、請求不再發出。本課練習 1–3 的測試就是這樣檢查你的函式有沒有清乾淨。stop 之後 scope 還有一些行為細節（再 run 會怎樣、computed 會不會凍結），放在課末〈補充與查表〉。

不是每個 composable 都能這樣測。用到 onMounted 或 inject（第 13 課）的 composable 需要元件實例，光有 scope 跑不了。官方測試指南示範的作法是寫一個 withSetup() 輔助函式：建一個空的 app，在它的 setup 裡呼叫 composable。這也是設計 composable 時偏好用 onScopeDispose、少用元件生命週期的另一個理由：依賴越少，越容易在元件外重用和測試。

用 scope 測試還有一個好處：每個測試建自己的 scope、呼叫自己的 composable，彼此應該完全獨立。如果你發現前一個測試加進購物車的數字，在下一個測試裡還在，那就是開場第二個問題的線索：狀態沒有跟著呼叫走。

店內和外帶的購物車數字，為什麼會互相影響？

同事寫的 useCartBadge 把 count 寫在檔案最外層，函式只是回傳它。寫在檔案最外層、不在任何函式裡的變數，叫做模組層級狀態（module-level state）。它的關鍵在於 ES module 的載入方式：一個模組檔案在整個 app 裡只執行一次，之後每個 import 它的地方拿到的都是那一次執行產生的同一個變數。所以不管 useCartBadge() 被呼叫幾次，回傳的都是同一個 count：

共用有時正是你要的，例如整個 app 只有一個「目前登入的會員」。但用模組最外層的 ref 來共用，有三個代價：

  • 看不出來：呼叫端看到 useCartBadge()，以為拿到自己的一份，實際上和別人共用，bug 出現在離修改處很遠的地方，就像開場的外帶角標。
  • 測試互相污染：同一個測試檔共用一份模組，前一個測試留下的值會影響下一個，測試的結果取決於執行順序。
  • 伺服器端渲染會外洩：伺服器端渲染是在伺服器上先執行 Vue、產生 HTML 再送給瀏覽器。伺服器上的程式模組只載入一次，卻同時服務很多使用者，模組層級的 ref 會讓 A 顧客的購物車出現在 B 顧客的頁面上（第 24 課）。

所以預設把狀態寫在函式裡。真的需要全 app 共用時，明確地用 Pinia（第 15 課）：它為每個 app 實例各建一份 store，伺服器上每個請求建立自己的 pinia，不會跨使用者外洩；而且能在瀏覽器擴充功能 Vue DevTools 裡看到每次狀態變化。

💡 實務上：先問「這份狀態該有幾份」
寫 composable 之前先決定範圍：表單輸入、某一頁的搜尋條件、某個彈窗的開關是每個元件一份，寫在函式裡；登入的會員、店家設定是整個 app 一份，交給 Pinia。Code review 看到 composables 檔案最外層有 ref，就該停下來問：這是刻意要共用的嗎？將來會做伺服器端渲染（SSR）嗎？如果真的是刻意的（例如純前端後台裡的全域提示訊息），至少寫註解說明，讓下一個人不會以為每次呼叫都拿到新的一份。

購物車的 composable 寫在哪裡已經對了。但 composable 寫得再對，呼叫的位置錯了一樣會出事：叫號看板的計時器在離開頁面後還在跑，問題不在 useInterval 本身，而在它被呼叫的地方。

叫號看板離開後計時器還在跑：composable 要在哪裡呼叫？

叫號看板（PickupBoard）掛載後先載入一次「等待中的訂單數」，之後每 10 秒更新。寫的人覺得「先等第一次載入完，再開始計時」很合理，於是把 useInterval 放在 await 後面。useInterval 就是前面從取餐倒數抽出來的那個，自己用 onScopeDispose 清理，照規則是對的，計時器卻還是在離開頁面後繼續跑：

// ✗ await 之後：已經沒有作用中的元件實例
onMounted(async () => {
  waiting.value = await api.getQueue()
  useInterval(refresh, 10_000)        // onScopeDispose 找不到 scope：警告，計時器永遠不會被清除
})

// ✗ 在條件或事件處理裡
if (props.showClock) useNow()          // props 之後改變，也不會補呼叫
button.onclick = () => useOnline()     // 每點一次多一組監聽，而且都不會清掉

// ✓ setup 頂層同步呼叫，需要的話用 getter 或旗標控制行為
useInterval(refresh, 10_000)
onMounted(refresh)

原因要回到上一節的機制：onScopeDispose 把清理登記到「目前作用中的 scope」。元件的 scope 只在 setup 同步執行的期間（以及 Vue 執行生命週期鉤子的同步部分時，見下方例外）是作用中的，Vue 也只有在這些時候知道「目前的元件實例」是誰；一旦遇到 await，後面的程式就落在這段期間之外。

await 會把後面的程式切到之後才執行：api.getQueue() 回來時，setup 早就跑完，onMounted 鉤子的同步部分也結束了，這時沒有作用中的元件，也沒有作用中的 scope。useInterval 照樣開了計時器，但 onScopeDispose 只能警告，清理函式沒地方登記。每進出這一頁一次，就多一個永遠不會停的計時器。

條件和事件處理是同一個問題的變形：

  • 寫在 if 裡：setup 只執行一次，當時 showClock 是 false 就永遠沒呼叫，之後 prop 改成 true 也不會補。
  • 寫在事件處理裡：點擊發生在 setup 之後，沒有作用中的 scope，每點一次就多一組清不掉的監聽。

所以官方文件的規則是：composable 只在 <script setup> 或 setup() 裡同步呼叫。需要「等資料來才做」或「條件成立才做」時，不要延後呼叫 composable，而是在頂層呼叫，再用 getter 或旗標控制它做什麼。練習 4 就是把 PickupBoard 改成這樣。

這條規則有兩個例外，看舊程式碼時會遇到：

  • 生命週期鉤子的同步部分：官方文件說某些情況可以在 onMounted() 裡呼叫，因為 Vue 執行鉤子時會暫時恢復元件實例。只限第一個 await 之前，PickupBoard 的錯就是越過了這條線。
  • <script setup> 頂層的 await：編譯器會在 await 之後幫你恢復元件實例，所以之後仍可呼叫 composable。但它會讓元件變成非同步元件，帶來另一組限制，一般專案避免這樣寫，改在 onMounted 或 watch 裡載入（第 17 課）。為什麼避免，見課末〈補充與查表〉。

最後把「呼叫位置」和上一節的 scope 接起來：只用到 ref、computed、watch、onScopeDispose 的 composable，只要有作用中的 scope 就能正確清理，所以在元件 setup 和 effectScope().run() 裡都能用；用到 onMounted、inject（第 13 課）的，就一定要在元件的 setup 裡。

到這裡，開場的四個 composable 都抽完了，也都呼叫在對的地方。最後退一步，把這課做過的決定整理成一份檢查清單，並回答一個常被忽略的問題：什麼時候根本不該抽。

抽完之後回頭檢查：好的 composable 長什麼樣、什麼時候不要抽？

下表每一列都對應這課的一個決定，寫新的 composable 或 review 別人的時，逐列對照：

面向建議理由
輸入會變的參數用 MaybeRefOrGetter；選項多時收一個選項物件，例如 { delay = 800 }呼叫端不用為了配合你而先包 ref；加選項不會打亂參數順序
輸出ref 組成的普通物件；狀態唯讀，修改透過函式可以解構；修改集中、好追查
依賴API client、now()、storage 從參數傳入（或第 13 課的 inject），不要在裡面直接 import 真正的 client測試換成假物件；不偷偷依賴全域
副作用每個註冊都配一個清理，用 onScopeDispose 或 watch 的清理函式元件內外都會清乾淨
大小一個 composable 做一件事，大的用小的組起來（useOnline 用 useEventListener）好測、好重用

「依賴」那一列這課還沒正面講過：useStampCard(customerId, api) 的 api 是參數，不是在檔案裡 import 進來的。這樣測試就能傳一個假的 api，自己決定每個請求什麼時候、以什麼點數回來，練習 2 的測試正是這樣檢查「只採用最新一次」。如果 composable 裡直接 import 真正的 client，測試就只能真的打網路，或想辦法替換模組。

事件、計時器、localStorage、視窗大小這類常見需求，實際專案不用自己寫：VueUse 是社群維護的 composable 集合，useEventListener、useOnline 這類函式都有現成的，而且處理了很多邊界情況。它的原始碼也是學寫 composable 的好教材，可以對照它的 useEventListener 怎麼處理「目標是 ref」和清理。本課練習不安裝它，因為重點是你能寫出、也看得懂這些行為；遇到 VueUse 的函式行為不如預期時，你才知道該往哪裡查。版本需求見課末。

什麼時候不要抽 composable：邏輯只在一個元件用、而且很短。抽出來不會少寫程式，只是多一個檔案要跳，讀的人要在兩個檔案之間來回才看得懂這個元件。開場的情況是兩頁複製了同一段程式、而且已經因為只修一邊出過事，那才是該抽的時機。實務上的判斷點是：第二個地方要用了，或者元件長到看不出重點了，再抽。

補充與查表

主線用不到、但查版本或看到舊程式碼時會用到的細節。

版本備註

  • MaybeRefOrGetter 與 toValue 從 Vue 3.3 起提供。
  • onScopeDispose 從 3.5 起有第二個參數 failSilently，設成 true 就不會在沒有 scope 時警告，給「有 scope 就清理、沒有就算了」的函式庫用。
  • @vueuse/core 15.0.0 需要 Vue 3.5 以上（npm，2026-10-31）。
  • 本課提到的警告訊息與行為，都是在練習使用的 Vue 3.5.44 實測。

toValue 與舊的 unref

舊程式碼常見 unref()。它只處理 ref：把 getter 交給它，拿回的是函式本身，不會呼叫。所以接受 getter 的地方要用 toValue。

scope stop 之後的行為

Vue 3.5.44 實測：

  • 對已停止的 scope 再 run()，會警告 cannot run an inactive effect scope 並回傳 undefined，函式不會執行。
  • scope 裡的 watch 不再執行，但 computed 被讀取時仍然會重新計算。stop 是「停掉副作用並清理」，不是「把所有值凍結」。

頂層 await 與 Suspense

<script setup> 頂層寫 await，元件就變成非同步元件，外層一定要有 <Suspense>，否則元件不會顯示。<Suspense> 是 Vue 內建的元件：等裡面的非同步元件準備好才顯示，之前先顯示替代內容。它在官方文件中仍標為實驗性功能，所以一般專案避免頂層 await。

composable 與無渲染元件

第 11 課的無渲染元件也能分享邏輯，但它要多一層元件、資料只能在 slot 裡用。純邏輯優先用 composable；邏輯跟 DOM 結構綁在一起時，才考慮無渲染元件。

練習

在 learn/ 執行 node check.mjs vue 12。練習 1–3 的測試在 effectScope().run() 裡呼叫你的函式；練習 2 用假的集點 API，由測試決定每個請求什麼時候、以什麼點數回來，還會用 vue-tsc 檢查參數型別（大約 2 秒）。練習 4 用假計時器把時間往前推。

練習 1：useEventListener(target, type, handler)：target 可以是元素、ref 或 getter，值是 null 時什麼都不做。在 target 上註冊事件；target 換成另一個元素時，從舊元素移除、在新元素註冊；所屬的 scope 停止時（元件卸載或 scope.stop()）移除。不能用 onUnmounted，也不能出現 Vue 警告。

練習 2：useStampCard(customerId, api) 回傳 { points, loading, reload }。把 customerId 的型別改成 MaybeRefOrGetter<number>，數字、ref、getter 都要能用：一建立就呼叫 api.getPoints(id)，ref 或 getter 的值改變時重新載入，數字只載入一次。reload() 用現在的 id 再載入；回應順序不一定，只採用最新一次請求的結果：舊請求先回來時不能寫進 points，loading 要等最新的請求完成才變回 false。不能有 Vue 警告。

練習 3：useCartBadge() 的 count 寫在模組最外層，店內和外帶的購物車數字互相影響。改成每次呼叫各自一份，從 0 開始；回傳 { count, add, clear }，解構後 count 仍是 ref；count 對外唯讀，只能用 add(n = 1)、clear() 修改。

練習 4：PickupBoard.vue 掛載後載入「等待中的訂單數」，之後每 10 秒更新。起始程式在 onMounted 的 await 之後才呼叫 useInterval，卸載後計時器還在跑、還在呼叫 load()。修正它：行為不變，卸載後不再呼叫 load()、不留下計時器、沒有 Vue 警告。useInterval.ts 不用改。

練習 5：useMouse() 回傳 reactive({ x, y })，元件裡寫 const { x, y } = useMouse()，滑鼠移動時畫面會更新嗎？

✓ 解構就是讀屬性：x 拿到的是那一刻的數字，之後 reactive 物件怎麼變都和它無關（第 4 課）。Vue 不會丟錯，只是靜靜地不更新，nextTick 也救不回來。所以 composable 回傳由 ref 組成的普通物件，呼叫端解構出來的仍然是 ref；想要 mouse.x 寫法的人可以自己包 reactive(useMouse())。

練習 6：元件裡寫 onMounted(async () => { await load(); useInterval(refresh, 10_000) })，useInterval 用 onScopeDispose 清除計時器。離開這一頁後會怎樣？

✓ Vue 執行 onMounted 鉤子時會暫時恢復元件實例，但只到第一個 await 為止。await 之後的程式在之後的 microtask 執行，那時沒有目前的元件、也沒有目前的 scope，onScopeDispose 只會警告，清理函式沒登記上。每進出這一頁一次就多一個計時器。修法：在 setup 頂層同步呼叫 useInterval，需要等資料的話用旗標或 getter 控制它做什麼。

練習 7：購物車要在 header、菜單頁、結帳頁共用，還要支援伺服器端渲染。把它寫成「ref 放在模組最外層的 composable」好嗎？

✓ 模組層級的 ref 確實能共享，但伺服器上模組只載入一次，所有請求共用同一份，A 顧客的購物車會出現在 B 顧客的畫面上；也沒有 devtools、測試之間會互相污染。每個使用者（每個元件）一份的邏輯用 composable；整個 app 共享、需要 devtools 與 SSR 安全的狀態用 Pinia（第 15 課），它為每個 app 實例建立自己的 store。composable 被很多元件呼叫正是它的用途，c 錯。

常見錯誤

  • 回傳 reactive 物件：呼叫端一解構就失去響應，而且不會有任何警告。回傳 ref 組成的普通物件。
  • 在函式開頭 toValue 一次：只拿到當下的值，之後不追蹤，顧客或網址換了資料不會跟著換。在 watch 的 getter、computed 或 watchEffect 裡呼叫 toValue。
  • 用 unref 處理 getter：unref 不會呼叫函式，拿回的是函式本身。接受 getter 就用 toValue。
  • watch(customerId, …) 直接傳參數：參數是數字時是無效來源，Vue 只警告。用 () => toValue(customerId)。
  • composable 在元件外使用卻用 onUnmounted 清理：在 effectScope 裡只會警告、永遠不執行。用 onScopeDispose 或 watch 的清理函式。
  • 把 ref 寫在模組最外層：所有呼叫共用同一份，兩個購物車互相影響，測試互相污染，SSR 還會跨使用者外洩。預設寫在函式裡；要共享就明確用 Pinia。
  • 在條件判斷、事件處理或 await 之後呼叫 composable：沒有作用中的元件實例和 scope，清理掛不上，或每次都多一份。在 setup 頂層同步呼叫，用 getter 或旗標控制行為。
  • 在 <script setup> 頂層 await，卻沒有外層 <Suspense>：元件變成非同步元件，不會顯示。改在 onMounted 或 watch 裡載入。

小結

  • composable 是用組合式 API 封裝有狀態邏輯的函式，以 use 開頭；狀態靠閉包，每呼叫一次一份。沒有 ref、watch 或生命週期的邏輯寫成普通工具函式。
  • 回傳 ref 組成的普通物件，呼叫端解構後仍有響應；狀態唯讀、修改透過函式。
  • 會變的參數用 MaybeRefOrGetter，在 watch 的 getter 或 computed 裡呼叫 toValue 才會追蹤。
  • effect scope 收集副作用，stop 時一次清理。清理用 onScopeDispose 或 watch 的清理函式，在元件和 effectScope 裡都會執行；onUnmounted 只在元件裡有效。
  • effectScope().run() 讓 composable 在元件外使用，也是測試 composable 的方法。
  • 狀態寫在函式裡才是每次呼叫一份；寫在模組最外層會全 app 共用，需要共用就用 Pinia。
  • 在 setup 頂層同步呼叫；await、條件、事件處理之後呼叫會讓清理掛不上。
