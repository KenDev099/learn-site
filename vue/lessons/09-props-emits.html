階段 3：元件如何運作 · 第 9 課

props 與 emits：單向資料流

咖啡店的點餐頁原本是一個八百行的檔案。這週團隊把它拆成幾個元件：菜單上的每張商品卡是 ProductCard，購物車的每一列是 CartLine，點商品打開的明細是 ProductDetail，結帳按鈕用共用的 BaseButton。拆完交給 QA，回報了三個 bug：購物車按「+」，那一列的數字變了，總金額卻沒重算、草稿也沒存；從清單點別的商品，詳情頁還停在第一個；讀螢幕軟體唸不出結帳按鈕的說明。

三個 bug 都出在元件跟元件的交界：資料屬於誰、子元件要怎麼把改變傳回去、父元件寫在子元件上的東西最後落在哪個元素。這課從購物車那一列開始，一個一個修。修完你會知道怎麼替元件設計輸入和輸出，也知道 code review 時從哪幾行看出這三類 bug。

這課的路線：
  1. 購物車的數字為什麼變了、總金額卻沒動：元件的輸入和輸出是什麼，資料屬於誰（開場問題的最小答案）。
  2. 元件收什麼：用 defineProps 宣告輸入、給預設值，以及解構之後為什麼還會跟著更新。
  3. 拿得到 line 為什麼不能直接改、「+」要怎麼讓數量變：單向資料流，用 defineEmits 把請求送回擁有資料的元件。
  4. 詳情頁為什麼停在第一個商品：prop 改變時，用 watch 重新載入。
  5. 結帳按鈕的 aria-label 去哪了：沒宣告的屬性會透傳到根元素；最後整理拆元件時怎麼決定什麼該是 prop。
這課會用到：
  • 第 8 課的元件實例與 VTU：每使用一次元件就跑一次 <script setup>，各有自己的狀態；測試用 mount 掛上元件、trigger 模擬點擊。
  • TS 課第 14 課的可選屬性與第 15 課的字面值聯合：soldOut?: boolean 的 ? 表示可以不傳；'new' | 'hot' 只能是這兩個字之一。
  • TS 課第 18 課的具名 tuple：[productId: number] 是只有一個數字的陣列，productId 只是給人看的名字。

購物車的數字為什麼變了，總金額卻沒動？

先看第一個 bug 的現場。購物車頁 Cart.vue 持有購物車的資料 lines，每一筆用一個 CartLine 顯示。Cart 有一個 setQuantity(productId, quantity) 函式，改數量時一律經過它：改完數量，順便重算總金額、存草稿。拆元件的人在 CartLine 的「+」按鈕上寫了 props.line.quantity++，那一列的數字確實加一了，可是 setQuantity 從頭到尾沒被呼叫，總金額和草稿當然沒動。

要看懂為什麼這樣寫不對，先要知道兩個元件之間是怎麼溝通的。把元件想成一個函式：呼叫的人給參數，函式做完事回報結果。元件的「參數」叫 props，是父元件傳給子元件的輸入，例如「要顯示哪個商品」「這一列是哪個品項、幾杯」。元件的「回報」是事件（event）：子元件發生了某件事，例如客人按了「加入」，它就發出一個事件通知父元件。發出事件這個動作叫 emit，事件可以附帶資料，例如「被按的商品 id 是 2」，這份附帶的資料叫 payload。

菜單頁是最單純的例子，父元件在範本裡同時用上這兩個方向：

<!-- 父元件：Menu.vue -->
<ProductCard
  v-for="p in menu" :key="p.id"
  :product="p"                   ← props：往下給資料
  :sold-out="soldOutIds.has(p.id)"
  @add="cart.add"                ← 事件：往上收通知
/>

:product="p" 是 v-bind:product 的縮寫，意思是「把 JavaScript 運算式 p 的值當成 product 這個 prop 傳下去」。@add 是 v-on:add 的縮寫，意思是「ProductCard emit add 的時候，呼叫 cart.add」，emit 時帶的參數會原封不動傳給 cart.add。

這樣分工之後，ProductCard 只負責兩件事：顯示一張卡片、回報「被按了」。它不知道購物車資料怎麼存，也不該知道。好處是同一張卡片可以放在菜單頁、推薦區、搜尋結果，每個父元件自己決定按了要做什麼。元件的介面除了 props 和事件，還有第三種叫 slots，讓父元件決定元件裡一塊畫面要長什麼樣，第 11 課再講。

回到 CartLine。lines 是 Cart 的資料，Cart 是它的擁有者：只有 Cart 知道數量改了之後還要重算總額、存草稿。CartLine 只是拿到其中一筆來顯示。所以開場第一個 bug 的最小答案是：子元件不改 props，用 emit 請擁有資料的父元件改。CartLine 按「+」時 emit 一個「請把 2 號商品改成 4 杯」的事件，Cart 收到後呼叫 setQuantity，總額和草稿就都會跟著更新。第二個 bug 的最小答案也在同一個想法裡：資料是父元件的，詳情頁要跟著父元件給的 productId 走，就不能在 setup 裡複製一份當下的值。更關鍵的是，從清單換商品時 ProductDetail 通常不會重新掛載，只寫在 onMounted 裡的載入不會再跑；所以最小答案是：詳情頁要在 productId 改變時重新載入，不能只在掛載時用複製的 id 載入一次。第三個 bug 跟前兩個不同：父元件寫在子元件上、但子元件沒宣告的屬性（例如 aria-label），落到了錯的元素上，最後一節處理。

這三個答案後面會逐一寫成程式碼。第一步是讓元件清楚說出自己收什麼：宣告 props。

元件收什麼？用 defineProps 宣告

宣告 props 的目的，是讓元件的輸入有明確的名字和型別：父元件傳錯了，編輯器當場標紅；別人打開檔案，一眼就看得到這個元件要吃什麼。在 <script setup> 裡用 defineProps 宣告。ProductCard 的輸入比 CartLine 多幾種形態（必填、可選、限定幾個字），先用它看完整寫法：

<script setup lang="ts">
import type { Product } from './types'

const props = defineProps<{
  product: Product        // 必填
  soldOut?: boolean       // 可選：沒傳時是 false（布林 prop 的特例，見下面）
  badge?: 'new' | 'hot'   // 字面值聯合：只能是這兩個字之一
}>()
</script>

<template>
  <h3>{{ product.name }} ${{ product.price }}</h3>   <!-- 範本裡直接用 prop 的名字 -->
</template>

defineProps 看起來像函式，但沒有 import。原因是它不是一般的函式，而是編譯器巨集（compiler macro）。.vue 檔不能直接交給瀏覽器執行，要先經過 SFC 編譯器轉成 JavaScript；defineProps 是寫給這個編譯器看的記號，編譯時就被換成元件的 props 設定，執行時已經不存在。這也說明了它的限制：只能寫在 <script setup> 的最上層，不能放進 if 或函式裡，因為編譯器要在編譯時就讀得到它。CartLine 的宣告只有一行：defineProps<{ line: CartItem }>()。

宣告的名字用 camelCase（soldOut），父元件在範本裡傳的時候慣例寫 kebab-case（:sold-out），Vue 會自動對應，這就是上一節 Menu.vue 裡寫 :sold-out 的原因。布林型的 prop 有個特例：宣告成 boolean 的 prop 沒傳時是 false，不是 undefined；只寫屬性名 <ProductCard sold-out /> 就是 true，跟 HTML 的 disabled 一樣。

型別宣告在執行時能擋住錯誤嗎？不能。編譯器會把型別轉成執行時的檢查設定，例如 type: Object，但開發模式下傳錯型別，Vue 只印警告：在練習用的 Vue 3.5.44，宣告一個物件型別的 prop order（一張訂單物件），父元件卻傳了字串，會印出 [Vue warn]: Invalid prop: type check failed for prop "order". Expected Object, got String…，元件照樣渲染。正式版連警告都沒有。真正在上線前擋住錯誤的是型別檢查，第 14 課會用 vue-tsc 在建置前檢查整個專案。

沒傳的 prop 要有預設值：解構

可選的 prop 常常需要預設值，例如替 ProductCard 加一個可選的杯型 prop size，沒傳就當 M。練習用的 Vue 3.5 可以直接解構 defineProps 的結果，用 JavaScript 原本的預設值語法 = 給預設值，這叫響應式 props 解構（reactive props destructure）：

const { product, size = 'M', soldOut = false } = defineProps<{
  product: Product
  size?: 'S' | 'M' | 'L'
  soldOut?: boolean
}>()

const label = computed(() => `${product.name}（${size}）`)   // 父元件改了 size，label 會跟著變

這裡要停一下。第 4 課說過，解構 reactive 物件會失去響應：解構出來的只是當下的值，之後原物件改了，變數不會變。那這裡的 size 為什麼會跟著父元件變？因為這是編譯器做的特例。在同一個 <script setup> 裡，編譯器把每一個用到 size 的地方改寫成 __props.size，所以執行時讀的其實還是 props 這個響應式物件，computed 也就追蹤得到。

既然是編譯器在原始碼裡逐一改寫，它就只在這個檔案裡直接使用時成立。把 size 當參數傳給別的函式，傳出去的就只是當下的值，跟第 4 課的情況一樣。這一點在後面修詳情頁時會直接踩到。舊專案沒有解構，給預設值用的是 withDefaults，寫法和版本見課末補充與查表。

到這裡 CartLine 已經能拿到 line，範本也能顯示數量。接下來就是第一個 bug 的核心：既然拿得到 line，為什麼不能直接改它？

拿得到 line，為什麼不能直接改？

Vue 元件之間的資料有固定的流向，叫單向資料流（one-way data flow）。資料只由父元件往子元件流；子元件想改資料，就發事件給擁有這份資料的元件，由它來改，改完新的值再經由 props 往下流到子元件。下圖是購物車的版本：

這個規則的價值在於「修改只發生在一個地方」。Cart 的 setQuantity 是數量唯一的入口，重算總額、存草稿、檢查庫存上限這些「改了之後要做的事」都放在那裡，就不會漏。子元件一旦自己改，這個入口就被繞過了。

那 Vue 會不會擋住子元件去改？要分兩種情況看，結果不一樣。下面的實測和模擬用一個訂單物件 order（有 note 備註欄位）當 prop，它跟 line 是同一種情況：父元件傳下來的物件。

第一種是重新指定 prop 本身，例如 props.order = other。開發模式下 props 物件對子元件是唯讀的（shallowReadonly），Vue 3.5.44 會印 [Vue warn] Set operation on key "order" failed: target is readonly.，值不變。正式版沒有這層唯讀包裝，寫入會暫時生效，直到父元件下一次重新渲染把值蓋回去，所以更不能依賴 Vue 幫你擋。

第二種是改 prop 物件裡面的屬性，例如 props.order.note = '少冰'，或開場的 props.line.quantity++。這種比較危險。就算在開發模式，props 物件也只有第一層是唯讀，裡面的 order 是父元件傳來的同一個物件參考，不是複本，所以這行真的會改到父元件的資料，而且 Vue 不會警告。在 3.5.44 實測，父元件的 order.note 變成「少冰」，警告數是 0。畫面看起來正常，問題在別處出現：

  • 擁有資料的元件不知道資料被改了：它在「修改時」做的事（重算總額、存草稿、送統計、檢查庫存上限）全部被跳過。開場的總金額不動，就是這個原因。
  • 出錯時找不到兇手：資料是被哪個元件改的，要翻遍所有拿到這個物件的子元件。
  • 資料如果來自 store 的唯讀狀態或凍結的快取，修改會直接出錯。這課的練習就是傳入 Object.freeze 過的物件，改了會丟 TypeError。

為什麼第一層擋得住、裡面擋不住？開發模式下，Vue 用 第 1 課的 Proxy 包住 props 物件，只攔第一層的寫入。下面用普通的 Proxy 模擬這個行為，執行後看最後一行印出的 note：

第二次寫入的時候，JavaScript 先執行 props.order，這是一次讀取，拿到的是父元件的原物件；接著對那個原物件設定 note，這次寫入根本不經過 props 的 set 陷阱。Proxy 只能攔到「對它自己」的操作，攔不到「對它交出去的物件」的操作。

Vue 擋不住，就只能靠寫法守住：子元件不改，請擁有者改。下一節把這個「請」寫成程式碼。

改不了，「+」要怎麼讓數量變？用 emit 請 Cart 改

CartLine 要做的事是：按「+」時告訴 Cart「2 號商品請改成 4 杯」。先用 defineEmits 宣告元件會發出哪些事件，它跟 defineProps 一樣是編譯器巨集，不用 import。型別寫成一個物件：每個 key 是事件名稱，值是具名 tuple，代表這個事件帶的參數。

const props = defineProps<{ line: CartItem }>()
const emit = defineEmits<{ changeQuantity: [productId: number, quantity: number] }>()

function inc() {
  emit('changeQuantity', props.line.productId, props.line.quantity + 1)   // 只請求，不自己改
}

注意 inc 只算出「想要的新數量」放進事件裡，沒有改 props.line。父元件用 @change-quantity 監聽這個事件：

<!-- 父元件 -->
<CartLine v-for="l in lines" :key="l.productId" :line="l" @change-quantity="setQuantity" />

整個流程走一遍：客人按「+」，CartLine 執行 inc，emit changeQuantity，payload 是 2, 4；Vue 呼叫父元件的 setQuantity(2, 4)；Cart 改 lines，順便重算總額、存草稿；lines 變了，Cart 重新渲染，把新的 line 傳給 CartLine；CartLine 顯示 4。數量只在 Cart 被改了一次，開場第一個 bug 就修好了。

宣告事件的型別有實際的好處：emit 時名字或參數寫錯，型別檢查當場抓到。

const emit = defineEmits<{
  add: [productId: number]
  changeQuantity: [productId: number, quantity: number]
  close: []                                  // 不帶 payload
}>()

emit('add', product.id)        // ✓
emit('add', '2')               // ✗ 型別錯誤：要 number
emit('ad', 2)                  // ✗ 型別錯誤：沒有這個事件

命名慣例跟 props 一樣：宣告和 emit() 用 camelCase，父元件範本裡監聽用 kebab-case（@change-quantity），Vue 會對應。事件名稱描述「發生了什麼」或「請求什麼」，例如 add、changeQuantity、remove；不要用 handleClick 這種描述子元件內部實作的名字，父元件不需要知道你是用 click 還是鍵盤觸發的。

宣告 emits 不只是為了型別。打開一個元件檔，看 defineProps 和 defineEmits 就知道它吃什麼、吐什麼，不用讀完整個範本，這兩段就是元件的說明書。另外，宣告過的事件 Vue 才會當成事件處理；沒宣告的，會被當成一般屬性往下傳，造成重複觸發，最後一個 bug 會遇到。怎麼在測試裡檢查元件 emit 了什麼，見課末補充與查表。

能不能把 prop 複製一份，自己改？

emit 要繞父元件一圈，有人會想：把 prop 複製成自己的 ref，改自己的不就好了？大多數情況不行，因為複製出來的是「當下的值」，跟父元件從此斷線：父元件之後更新，複本不會跟著變；子元件改複本，父元件也不知道。

只有一種情況可以複製：這個 prop 的意思本來就是初始值，之後由子元件自己管，不再跟父元件同步。例如「編輯備註」對話框，打開時帶入目前的備註；客人修改的過程只存在對話框裡，按「儲存」才 emit 出去，按「取消」就丟掉。這時把 prop 取名叫 initialNote，讓讀程式的人一看就知道它只在一開始用一次：

const { initialNote } = defineProps<{ initialNote: string }>()
const draft = ref(initialNote)   // 刻意的複製：之後父元件改 initialNote，draft 不會變

如果你期待它跟著父元件更新，就不能這樣複製。數量、選中的商品這類資料，直接讀 props，或用 computed 從 props 算出來。

💡 實務上：改 props 的 bug 多半在 code review 被抓到
最常見的場景是編輯表單：後台「編輯商品」把 product 傳進表單元件，表單裡直接 v-model="product.price"，還沒按儲存，列表上的價格就先變了，按取消也改不回來。這跟開場的 props.line.quantity++ 是同一件事。資深的人 review 時會看：子元件裡有沒有對 props.xxx.yyy 賦值或 v-model，有的話請他改成 emit，或複製成草稿、按儲存才送出。很多團隊會開 eslint-plugin-vue 的 vue/no-mutating-props 規則，把直接改 prop 的寫法擋在提交前，但它抓不到所有間接修改（例如把 prop 物件傳給別的函式去改），review 時還是要留意。

「期待跟著更新，卻複製了當下的值」正是開場第二個 bug 的寫法。下一節回到詳情頁。

詳情頁為什麼停在第一個商品？

ProductDetail 收一個 productId，自己打 API 載入商品。起始版本是這樣：

const product = ref<Product | null>(null)
const props = defineProps<{ productId: number }>()
const id = props.productId          // ✗ 複製了當下的值：之後永遠是第一個 id
onMounted(async () => {
  product.value = await api.getProduct(id)   // ✗ 只在掛載時載入一次
})

這段有兩個問題，而且要一起看才知道為什麼畫面停住。第一，從清單點別的商品時，Vue 通常不會把 ProductDetail 拆掉再建一個新的，而是重用原本那個元件，只把 productId 這個 prop 換成新的值。第 7 課講過，比對新舊畫面時，同一個位置的元件類型和 key 都沒變，Vue 就沿用原本的實例，只更新它的 props。路由切換參數時也是這樣，第 19 課會再遇到。元件沒有重新掛載，onMounted 就不會再跑。第二，就算它會再跑，id 是 setup 時複製的數字，也永遠是第一個商品的 id。

需求其實是「productId 每次改變都重新載入」，這正是第 5 課的 watch：盯著一份資料，改了就執行一段程式。改寫成解構 props 加 watch：

const product = ref<Product | null>(null)
const { productId } = defineProps<{ productId: number }>()

watch(() => productId, async id => {
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort())   // 換商品時取消上一個請求
  product.value = await api.getProduct(id, { signal: controller.signal })
}, { immediate: true })                        // 掛載時也要載入第一次

逐行看它解決了什麼。immediate: true 讓 watch 建立時就先執行一次，取代原本的 onMounted。之後 productId 每變一次就再載入一次。onWatcherCleanup 是第 5 課的清理函式：下一次執行前，先取消上一次還沒回來的請求，客人連點兩個商品時，比較晚回來的舊商品就不會蓋掉新的。

為什麼第一個參數要寫成 getter () => productId，不直接寫 productId？這裡就是上一節預告的地方。解構出來的 productId 在原始碼裡只是個名字，編譯器會把 getter 裡的它改寫成 __props.productId，watch 每次執行 getter 都重新讀、重新追蹤。如果直接寫 watch(productId, …)，執行時傳進去的就是一個數字，watch 沒辦法盯著一個數字的變化，跟第 5 課 watch(state.qty, cb) 是同一個錯誤。這個錯誤常見到編譯器會直接擋下，Vue 3.5.44 的 SFC 編譯器會讓整個檔案編譯失敗：

[@vue/compiler-sfc] "productId" is a destructured prop and should not be passed directly to watch().
Pass a getter () => productId instead.

同樣的道理也適用於把 prop 傳給 composable（第 12 課）：要傳 () => productId，對方才能追蹤到變化。

💡 實務上：「點了別筆，還顯示上一筆」是很常見的回報
後台的訂單列表左邊清單、右邊明細，或商品頁底下的「相關商品」，都是同一個元件被重用、只換 id 的情況。QA 或客服回報「切換很快時明細對不上」，第一個要檢查的就是 watch 有沒有寫、舊請求有沒有取消。除了資料，也要記得把 loading、錯誤訊息、表單草稿這些跟著 id 走的狀態一起重設。另一個做法是在父元件寫 <ProductDetail :key="productId" />，id 一變就整個重建元件，簡單直接，代價是元件內所有狀態和子元件都重來，畫面較重或有捲動位置要保留時就不適合。

前兩個 bug 都是資料怎麼在父子之間流動。第三個 bug 不一樣：問題出在父元件寫在子元件上、子元件卻沒宣告的東西。

結帳按鈕的 aria-label 去哪了？

結帳頁這樣使用共用的 BaseButton：<BaseButton text="結帳" class="primary" aria-label="結帳，共 3 項" @click="pay" />。BaseButton 只宣告了 text 一個 prop，class、aria-label、@click 都沒宣告。這些沒宣告的東西會去哪？

答案是它們會變成透傳屬性（fallthrough attributes）。父元件寫在子元件上、但沒有被宣告成 props 或 emits 的屬性與監聽器，常見的有 class、style、id、aria-label、data-*、@click，Vue 會自動加到子元件的根元素上，也就是範本最外層的那個元素。class 和 style 會跟根元素原有的合併，不是取代。這個預設行為的好處是：包一層的元件用起來像原生元素，父元件想加個 class 或 aria 屬性，不用子元件一個一個宣告。

根元素就是真正的按鈕時，結果正是我們要的：

<!-- BaseButton.vue 的根元素就是 <button> -->
<template><button type="button" class="btn">{{ text }}</button></template>

<!-- 父元件 -->
<BaseButton text="結帳" class="primary" aria-label="結帳，共 3 項" @click="pay" />

<!-- 結果 -->
<button type="button" class="btn primary" aria-label="結帳，共 3 項">結帳</button>   ← 點它會呼叫 pay

但拆元件時，有人為了放載入中的轉圈圖示，在按鈕外面包了一層 span，根元素就變成外框了：

<template>
  <span class="wrap">                 ← class、aria-label、onClick 都落在這裡
    <button type="button">{{ text }}</button>
    <span class="spinner" v-if="loading" />
  </span>
</template>

這就是第三個 bug。aria-label 掛在 <span> 上，讀螢幕軟體聚焦到按鈕時唸不出說明；.primary 的樣式也套錯了元素。點按鈕時，click 事件會從 button 冒泡到外層的 span，pay 碰巧還是會被呼叫，功能看起來正常，所以這個錯誤很容易被忽略。

解法是關掉自動透傳，自己指定要放在哪個元素上。這需要兩樣東西。第一樣是 inheritAttrs: false，它是元件的設定選項，意思是「不要自動加到根元素」；在 <script setup> 裡用 defineOptions 這個編譯器巨集來寫元件選項。第二樣是 $attrs，它是一個物件，裝著所有透傳屬性，範本裡可以直接用；v-bind="$attrs" 把它整個展開到指定的元素上，監聽器也包括在內。父元件寫的 @click="pay"，在子元件這邊是一個名叫 onClick 的屬性，值就是 pay 這個函式，所以它跟 class 一樣會被透傳；展開到 button 上，onClick 就變成 button 的 click 監聽器。

<script setup lang="ts">
defineOptions({ inheritAttrs: false })   // 不要自動加到根元素
defineProps<{ text: string; loading?: boolean }>()
</script>

<template>
  <span class="wrap">
    <button type="button" v-bind="$attrs">{{ text }}</button>   ← 全部透傳屬性放這裡
  </span>
</template>

如果要在 <script setup> 的程式碼裡讀透傳屬性，用 useAttrs() 取得同一個物件。

只加 v-bind="$attrs"、忘了 inheritAttrs: false，屬性會同時出現在 span 和 button 上。按一下按鈕：button 上的 onClick 執行一次，事件冒泡到 span 再執行一次，pay 被呼叫兩次，客人被扣兩次款的那種 bug 就是這樣來的。

前面說過「每個事件都要宣告」，這裡是它的實際理由。假設子元件寫 <button @click="$emit('click', 2)">，卻沒有在 defineEmits 宣告 click。對 Vue 來說，父元件的 @click 沒有對應的事件宣告，就被當成透傳屬性綁到根元素的原生 click 上；同時子元件又 emit 了 click，父元件也收到。Vue 3.5.44 實測：點一次，父元件的處理函式被呼叫兩次，一次收到 2，一次收到原生的 Event。宣告了 click 之後就只收到一次 2。範本最外層有兩個以上元素的元件，透傳又是另一種行為，見課末補充與查表。

💡 實務上：團隊的基礎元件幾乎都要處理透傳
設計系統或共用元件庫裡的 BaseInput 是最典型的例子：根元素通常是包著 label、錯誤訊息的 <div>，但使用的人傳的 placeholder、maxlength、autocomplete、@blur 都應該落在 <input> 上，所以這類元件幾乎都會用上面的 inheritAttrs: false 加 v-bind="$attrs"。寫這種元件時，打開 DevTools 看一下 aria-*、data-*（埋點常用）到底掛在哪個元素，比讀程式碼快。無障礙稽核或資料團隊說「這顆按鈕抓不到點擊」，常常就是屬性掛錯了元素。一般的業務元件（例如某一頁專用的卡片）通常不需要特別處理，根元素就是你要的元素時用預設行為就好。

三個 bug 都修好了。回頭看，它們都跟「元件的介面怎麼設計」有關：收什麼、回報什麼、沒宣告的東西怎麼處理。點餐頁還有其他元件要拆，最後整理拆的時候怎麼決定介面。

拆下一個元件之前：什麼東西該是 prop？

props 和 emits 一旦宣告，就是別人在用的介面。設計時常遇到的判斷有這幾個：

  • props 是公開的 API：一旦很多地方在用，改名、改型別都要改所有呼叫的地方。只開放真正需要外部決定的東西，例如 product、soldOut，不要把子元件內部的 UI 狀態（展開沒、滑鼠在不在上面）做成 prop。
  • 傳完整物件還是傳 id：傳 product 物件，子元件不用自己載入，好測、好重用，ProductCard 就是這樣；傳 productId，子元件要自己載入資料，適合 ProductDetail 這種本來就要打 API 的元件，代價是要處理上一節的重新載入和取消請求。
  • props 一層一層往下傳很多層：這種情況叫 prop drilling，中間的元件自己不用這份資料，只是在轉手，是介面設計出問題的警訊。第 13 課的 provide／inject 和第 15 課的 Pinia 處理這種情況。
  • 雙向綁定的需求，例如「數量輸入框」：本質還是 prop 加事件，跟 CartLine 的 line 加 changeQuantity 一樣。Vue 提供 v-model 把這兩個包在一起，下一課的主題。

拆元件時照這幾點問一遍：這個值該由誰決定、誰擁有它、改了要通知誰。答得出來，props 和 emits 就自然定下來了。

補充與查表

主線用不到、但查版本、看舊程式碼或寫測試時會用到的細節。

版本備註

練習用的是 Vue 3.5.44，以下全部可用。維護舊專案時，先看 package.json 的 Vue 版本：

  • 響應式 props 解構：Vue 3.5 起預設啟用。3.5 以前給預設值用 withDefaults，舊專案很常見，要看得懂： 
    const props = withDefaults(defineProps<{ size?: 'S' | 'M' | 'L'; tags?: string[] }>(), {
  size: 'M',
  tags: () => [],   // 物件、陣列的預設值要用函式產生，每個元件實例各拿一份
})
  • defineEmits 的具名 tuple 寫法：Vue 3.3 起。3.3 以前的寫法是呼叫簽章（call signature），意思一樣，舊專案會看到：defineEmits<{ (e: 'add', productId: number): void }>()。
  • defineOptions：Vue 3.3 起的巨集。

在測試裡檢查事件

Vue Test Utils 的 wrapper.emitted() 記錄元件 emit 過的每個事件：emitted('add') 是一個陣列，每次 emit 一個元素，每個元素是那次的參數陣列。沒 emit 過就是 undefined。

const wrapper = mount(ProductCard, { props: { product: latte } })
await wrapper.get('button').trigger('click')
await wrapper.get('button').trigger('click')

expect(wrapper.emitted('add')).toEqual([[2], [2]])   // 兩次，每次的參數都是 [2]

另一種寫法是把監聽器當成 props 傳進去（@add 編譯後就是名叫 onAdd 的 prop），用假函式檢查它被怎麼呼叫，這樣測到的是父元件真正會收到的東西，不管子元件 emit 時寫 camelCase 還是 kebab-case。vi.fn() 是 Vitest 的假函式（mock function）：本身什麼都不做，只記錄每次被呼叫時收到的參數；toHaveBeenCalledWith(2, 4) 檢查它曾經用這組參數被呼叫過，.mock.calls 是全部呼叫的參數陣列。

const onChangeQuantity = vi.fn()
mount(CartLine, { props: { line, onChangeQuantity } })
// …按 +
expect(onChangeQuantity).toHaveBeenCalledWith(2, 4)

多個根元素時的透傳

範本最外層有兩個以上的元素時，Vue 不知道透傳屬性要放在哪個，就不會自動透傳，開發模式印出 Extraneous non-props attributes (class) were passed to component but could not be automatically inherited because component renders fragment or text or teleport root nodes.。要在其中一個元素上寫 v-bind="$attrs"。

練習

在 learn/ 執行 node check.mjs vue 09，要改的檔案在 vue/practice/work/09/，每個檔案最上面的註解寫了要求。測試傳給元件的商品、購物車列都是用 deepFreeze 凍結過的物件：元件只要改了它們任何一個屬性，就會丟 TypeError，測試失敗。

練習 1：ProductCard.vue 現在是寫死的樣板。用型別宣告 props：product（Product）和 soldOut?（預設 false）；<h3> 顯示「品名 $價格」（拿鐵 $110、可頌 $70）；用 defineEmits 宣告 add，按「加入」時 emit('add', product.id)。售完時按鈕要 disabled，而且處理函式本身也不能 emit（測試會拿掉 disabled 再按一次）。

練習 2：CartLine.vue 在「+」「−」按鈕裡直接改 props.line.quantity。改成 emit：宣告 changeQuantity: [productId, quantity] 和 remove: [productId]；數量限制 1～20，已經 20 時按「+」什麼都不 emit，數量 1 時按「−」改 emit remove。事件的 productId 一律用 props.line.productId（測試會換別的商品）。.qty 永遠顯示 props.line.quantity：測試會模擬父元件依事件更新 props，也會從外面直接改數量。

練習 3：ProductDetail.vue 只在 onMounted 載入一次商品，切換 productId 後畫面還是舊的。改成解構 props，用 getter 監聽 productId：掛載時立刻呼叫 api.getProduct(productId, { signal })，之後每次改變都重新載入；切換太快時，比較晚回來的舊請求不能蓋掉新的商品。

練習 4：BaseButton.vue 的根元素是 <span class="wrap">，父元件傳的 class、aria-label、onClick 都落在 span 上。讓它們全部落在 <button> 上，其他沒宣告的屬性（例如 data-track）也一樣，span 只保留自己的 class="wrap"，點一次按鈕父元件的 click 處理函式只被呼叫一次。

練習 5：父元件傳了一個 reactive 的 order 物件當 prop，子元件執行 props.order.note = '少冰'，會怎樣？

✓ props 物件只有第一層是唯讀：props.order = … 會被擋下並警告，但 props.order 讀出來的是父元件的同一個物件，對它設定屬性不經過 props 的攔截，所以會改到父元件，而且沒有警告。Vue 不會幫你複製（b 錯）。只有物件被凍結時才會丟 TypeError（d 錯），一般資料不會。正確做法是 emit 給擁有 order 的元件去改。

練習 6：Vue 3.5 的 <script setup> 裡寫 const { size = 'M' } = defineProps<{ size?: string }>()，範本與 computed 裡用 size。父元件之後把 size 改成 'L'，會怎樣？

✓ 3.5 起響應式 props 解構預設啟用，這是編譯器的特例：size 在這個檔案裡被改寫成 __props.size，讀取仍經過響應式的 props。第 4 課「解構會失去響應」講的是一般的 reactive 物件，不適用這裡（a 錯）。但改寫只發生在直接使用的地方，watch(size, cb) 傳進去的會是一個值，3.5.44 的編譯器直接報錯，要寫成 watch(() => size, cb)（c 錯）。

練習 7：父元件寫 <ProductCard class="highlight" :product="p" />，ProductCard 沒有宣告 class 這個 prop，根元素是 <article class="card">。結果是什麼？

✓ 沒宣告成 props 或 emits 的屬性是透傳屬性，預設加到子元件的根元素；class 和 style 會和根元素原有的值合併，不是取代（c 錯）。不會被丟掉（b 錯），單一根元素時也沒有警告（d 錯）；只有多個根元素又沒有用 v-bind="$attrs" 時才警告。要放到別的元素上，用 inheritAttrs: false 加 v-bind="$attrs"。

常見錯誤

  • 修改 props 或 props 裡的物件：重新指定 prop 會被擋下並警告；改裡面的屬性會偷偷改到父元件的資料，Vue 不警告，擁有資料的元件也不知道，它在修改時該做的事（重算總額、存草稿）全被跳過。改用 emit，讓擁有資料的元件去改。
  • 把 prop 複製成 ref，卻期待它跟著更新：ref(props.line.quantity) 只複製了當下的值。需要同步的資料直接讀 props 或用 computed；只有「初始值」語意時才複製，並把 prop 取名為 initialXxx。
  • 把解構出來的 prop 直接傳給 watch：watch(productId, cb) 傳的是值，3.5.44 編譯器會報錯。寫成 watch(() => productId, cb)；需要第一次就執行時加 immediate: true。
  • 只在 onMounted 依 prop 載入資料：元件被重用時 prop 會變，但不會重新掛載。用 watch 監聽 prop，並用第 5 課的清理函式取消過期的請求。
  • 沒有宣告 emits：監聽器被當成透傳屬性綁到根元素，原生事件和 emit 各觸發一次。每個事件都用 defineEmits 宣告。
  • 只加 v-bind="$attrs"、沒關 inheritAttrs：屬性同時落在外框和內層，click 處理函式被呼叫兩次。兩個要一起用。
  • 多根元件沒處理 $attrs：Vue 警告 Extraneous non-props attributes，屬性沒有落到任何元素上。在該接收的那個元素寫 v-bind="$attrs"。
  • 以為 props 的型別會在執行時擋住錯誤：開發模式只是警告，正式版完全不檢查。靠 vue-tsc 在建置前擋（第 14 課）。

小結

  • 元件的介面是 props（輸入）和事件（輸出），之後還有 slots。資料屬於擁有它的元件，修改只發生在那裡。
  • defineProps<…>()、defineEmits<…>() 是編譯器巨集，不用 import，只能寫在 <script setup> 最上層。宣告用 camelCase，範本裡用 kebab-case。型別在執行時只會警告，真正擋錯的是 vue-tsc。
  • Vue 3.5 可以解構 props 並用 = 給預設值；編譯器把同一個檔案裡的使用改寫成 __props.xxx，所以仍有響應性，但傳出這個檔案就只是值。
  • 單向資料流：資料往下、事件往上。props 只有第一層唯讀，改 props 裡物件的屬性 Vue 擋不住也不警告，要靠寫法守住；子元件 emit 請求，擁有者修改。只有「初始值」語意才複製成本地狀態。
  • 元件會被重用：依 prop 載入資料要用 watch(() => productId, …, { immediate: true })，並取消過期的請求。
  • 沒宣告的屬性和監聽器會透傳到根元素；根元素不是對的目標時，用 inheritAttrs: false 加 v-bind="$attrs"。每個事件都宣告，避免被觸發兩次。
