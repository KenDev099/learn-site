階段 5：狀態與資料 · 第 17 課

非同步資料：載入狀態、競態與快取

咖啡店的點餐 App 上線一週，客服收到五個回報。把它們照一位客人的使用順序排好，剛好是一條完整的路：客人打開商品頁，畫面同時出現「載入中」和「載入失敗」；他在菜單上快速點了幾個商品，最後停在燕麥拿鐵，畫面顯示的卻是上一個美式咖啡；工程師打開瀏覽器 DevTools 的 Network 分頁，發現側欄和主畫面各打了一次菜單 API；客人按收藏，愛心等了一秒才變色，他以為沒按到，又多按了兩下；下單之後他切去看別的網頁，取餐頁在背景每 5 秒打一次 API，打了一整個下午。

這五件事裡，API 都沒有壞，第 16 課的 API 層也照常工作：每個請求都正確送出、正確回應。出問題的是 API 層上面那一層：前端什麼時候去拿資料、拿回來存在哪裡、畫面怎麼表示「還在拿」和「拿失敗」、什麼時候該重拿。這課跟著這位客人從商品頁走到取餐頁，一個回報修一個。學完你會有四個 composable：能正確表示載入狀態並丟掉過期回應的 useAsyncData、多個元件共用的查詢快取、先變色再等伺服器確認的收藏按鈕、不重疊也不在背景浪費的訂單輪詢；也會知道什麼時候該換成成熟的套件。

這課的路線：
  1. 商品頁同時顯示「載入中」和「載入失敗」、快速切換後停在舊商品：用一個 status 欄位表示四種狀態，再用「取消上一次、丟掉過期回應」讓最新的請求說了算（開場問題的最小答案）。
  2. 側欄和主畫面各打一次菜單 API：伺服器的資料為什麼要當成快取來管，合併請求、新鮮時間、快取失效各解決什麼；然後自己做一個查詢快取。
  3. 收藏要等一秒才變色：樂觀更新先改畫面、失敗再回滾，連點時以最後一次為準；哪些操作不能這樣做。
  4. 取餐頁在背景打了一下午 API：輪詢怎麼寫才不重疊、背景時暫停、做好就停；什麼時候改用伺服器主動推送。
  5. 這些都要自己寫嗎：自己寫的版本夠用到哪裡，什麼時候改用 Pinia Colada 或 TanStack Query。
這課會用到：
  • 第 5 課的競態與 onWatcherCleanup：先送出的請求比較晚回來會蓋掉新結果；onWatcherCleanup 在 watcher 下一次執行前清掉上一次的工作。
  • 第 12 課的 composable：useXxx() 把狀態和邏輯包成函式；toValue 讀 ref、getter 或一般值，onScopeDispose 在元件卸載時清理。
  • TS 課第 11 課的 AbortController：controller.abort() 讓傳了 controller.signal 的 fetch 中止並 reject。
  • TS 課第 16 課的可辨識聯合：每個成員都有同一個欄位（例如 status），值各不相同，檢查它就能縮小成某一種。

商品頁為什麼會同時顯示「載入中」和「載入失敗」？

先看商品頁現在怎麼寫。客人打開商品頁時，元件向 API 層要這個商品的資料，等它回來再畫出來。等待的這段時間畫面不能空著，所以元件除了資料本身，還要記住「請求進行到哪裡了」。最常見的寫法是三個 ref，各管一件事：

const isLoading = ref(false)
const error = ref<Error | null>(null)
const data = ref<Product | null>(null)

async function load(id: string) {
  isLoading.value = true
  try {
    data.value = await api.getProduct(id)
  } catch (e) {
    error.value = e as Error
  } finally {
    isLoading.value = false
  }
}

範本則是每個欄位各自一個 v-if：isLoading 為 true 就顯示轉圈，error 有值就顯示紅字和「重試」按鈕，data 有值就顯示商品。

現在重現開場第一個回報。第一次載入時網路斷了，error 存進一個錯誤。客人按「重試」，load 再跑一次：isLoading 變成 true，可是整段程式沒有任何一行把 error 設回 null。範本裡兩個 v-if 各自成立，畫面就同時出現轉圈和紅字。

在 load 開頭補一行 error.value = null 能修好這一次，但根源還在。三個獨立的欄位能組出 2 × 2 × 2 = 8 種組合，而一個請求實際上只有四種樣子：

  • 還沒開始（idle）：根本還沒有要抓的東西，例如搜尋框是空的。
  • 載入中（loading）：請求已經送出，還沒回來。這時常顯示骨架畫面（skeleton）。骨架畫面是先用灰色方塊畫出內容的大致形狀，佔住它的位置；資料回來後換成真的內容，版面就不會因為內容突然出現而跳動。
  • 成功（success）：拿到資料了。資料是空陣列也算成功，但畫面要顯示「沒有符合的商品」這類說明，這種畫面叫空狀態（empty state）。留一片空白的話，客人分不出是還在載入還是真的沒有。
  • 失敗（error）：顯示錯誤訊息，加一個「重試」按鈕。

多出來的 4 種組合，每一種都是 bug 的來源。isLoading = true 加上 error 有值，畫面不知道該顯示哪一個，就是剛才的回報。isLoading = false、error = null、data = null 也說不準：是還沒開始，還是 API 真的回了 null？三個欄位要靠每個寫 load 的人記得同時改對，漏一行就組出一個不存在的狀態，而且 TypeScript 不會提醒你。

根本的解法是讓不存在的狀態寫不出來。TS 課第 16 課的可辨識聯合（discriminated union）是幾個物件型別的聯合，每個成員都有同一個欄位，值是不同的字面值。這裡用 status 當這個欄位，四種狀態各寫成一個成員，每個成員只帶自己需要的資料：

export type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading'; previous?: T }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error }

const s = state.value
if (s.status === 'success') s.data.price   // ✓ 這裡才有 data
s.data                                      // ✗ 型別錯誤：還沒檢查 status

一個值同一時間只能有一個 status，所以「又載入又失敗」在型別上就寫不出來；data 只存在於 success，沒先檢查 status 就讀它是型別錯誤。這就是 TS 課第 27 課講的「讓不合法的狀態無法表示」：與其靠每個人記得把三個欄位同時改對，不如讓錯的組合根本存在不了。loading 裡那個可選的 previous 先放著，下一節換商品時會用到。

範本也改成照 status 分支。用 v-if／v-else-if 串起來，同一時間只會有一段成立，四種狀態各對應一段畫面：

<ProductSkeleton v-if="state.status === 'loading'" />
<ErrorBox v-else-if="state.status === 'error'" :error="state.error" @retry="refresh" />
<ProductView v-else-if="state.status === 'success'" :product="state.data" />

範本裡的 refresh 是「用目前的 key 再呼叫一次 load」，下一節的 useAsyncData 會把它和 state 一起回傳。重試時把 state 整個換成 { status: 'loading' }，舊的錯誤跟著舊物件一起消失，不需要記得清任何欄位。

💡 實務上：設計稿常只畫「成功」那一張
接到咖啡店「訂單列表」的需求時，設計稿多半只有資料滿滿的樣子。資深工程師在開工前會先問設計師或 PM：載入中長什麼樣？沒有訂單時顯示什麼、要不要放「去點餐」按鈕？失敗時文案是什麼、能不能重試？這些在 code review 或 QA 階段才補，常變成各頁寫法不一。團隊通常會做共用的骨架、空狀態、錯誤元件，每頁照著 status 套上去就好。用 status 欄位的好處也在這裡：漏寫哪一種狀態，看範本就一目了然。

狀態的形狀對了。但客人接著在菜單上快速點了幾個商品，畫面卻停在上一個商品。這次每個狀態都合法，錯的是「誰最後寫進狀態」。

快速切換商品，為什麼最後顯示的是上一個商品？

先把狀況重現出來。商品頁用 watch 盯著網址上的商品 id，id 一變就呼叫 load。客人先點美式咖啡，馬上又點燕麥拿鐵，兩個請求幾乎同時送出。網路不保證先送先回：美式咖啡那次剛好碰到比較慢的伺服器，晚了幾百毫秒才回來。時間軸是這樣：

  1. 送出「美式咖啡」的請求。
  2. 送出「燕麥拿鐵」的請求。
  3. 燕麥拿鐵先回來，state 變成燕麥拿鐵。
  4. 美式咖啡後回來，state 被改回美式咖啡。

網址上的 id 是燕麥拿鐵，畫面上卻是美式咖啡，客人很可能就這樣把錯的商品加進購物車。第 5 課講過，這叫競態（race condition）：結果取決於幾個非同步工作完成的先後順序，而這個順序不是你能控制的。上一節的可辨識聯合救不了它，因為第 4 步寫進去的是一個完全合法的 success，只是內容過期了。

修法的原則是最新的請求勝出：只有最後送出的那個請求有資格寫入狀態，比它早的不管什麼時候回來都要丟掉。實作分兩步：

  1. 送出新請求前，用 AbortController 取消上一次。TS 課第 11 課教過，呼叫 abort() 之後，傳了那個 signal 的 fetch 會中止並 reject。
  2. await 回來之後，檢查自己這次的 signal 有沒有被 abort。被 abort 了，代表已經有更新的請求送出，這次的結果直接丟掉，不寫進 state。

商品頁、搜尋頁、訂單頁都會遇到同樣的事，所以把「呼叫 API、更新狀態、處理競態」包成一個 composable（第 12 課）：useAsyncData(key, fetcher)。key 是決定要抓什麼的值，例如商品 id 或搜尋關鍵字，可以是字串、ref 或 getter，裡面用 toValue 讀出目前的值；fetcher 是真正呼叫 API 的函式，收到 key 和 signal。key 一改變就重新抓：

async function load() {
  controller?.abort()                       // 取消上一次
  const k = toValue(key)
  const c = (controller = new AbortController())
  state.value = { status: 'loading', previous: … }
  try {
    const data = await fetcher(k, c.signal)
    if (!c.signal.aborted) state.value = { status: 'success', data }   // 過期的就丟掉
  } catch (e) {
    if (!c.signal.aborted) state.value = { status: 'error', error: … }
  }
}
watch(() => toValue(key), load, { immediate: true })

套回剛才的時間軸：第 2 步送出燕麥拿鐵前，美式咖啡的 controller 被 abort；第 4 步美式咖啡就算真的回來了，c.signal.aborted 是 true，結果被丟掉，畫面停在燕麥拿鐵。

為什麼不用第 5 課的 onWatcherCleanup 登記 abort？因為 load 不只由 watch 在 key 改變時呼叫，重試按鈕的 refresh 也會直接呼叫它，那時並不在 watcher 裡執行，onWatcherCleanup 登記不了。所以把 controller 存在 composable 自己的變數裡，每次 load 一開頭就 abort 上一個，不管是誰呼叫的都適用。

既然已經 abort 了，為什麼 await 之後還要再檢查一次？因為 abort 管不到所有情況。不是每個 fetcher 都理會 signal：有的 API 函式根本沒把 signal 傳給 fetch，abort 對它毫無作用；有的在 abort 之前就已經拿到回應，只差還沒寫進 state。abort 的意思是「瀏覽器別等了，能停就停」，而且只停得了瀏覽器這一端，伺服器那邊可能早就處理完了。檢查的意思則是「不管它有沒有做完，過期的結果不准寫進狀態」。前者省資源，後者保證正確，兩件事都要。

成功和失敗兩條路都要檢查。被 abort 的請求會 reject，走進 catch；如果 catch 不檢查，就會把「被取消」當成「載入失敗」，客人明明只是換了商品，卻看到一個錯誤畫面。

現在回頭看 loading 裡的 previous。換商品時要不要先清空畫面？清空最簡單，但畫面會閃一下白，列表的捲動位置也會跳。loading 帶著 previous（上一次的資料），畫面就可以先顯示舊的內容、旁邊放一個小的載入圖示。上一節的範本因此要多一個分支：手上沒有任何資料時才顯示骨架，有上一次的資料就繼續顯示它：

<ProductSkeleton v-if="state.status === 'loading' && !state.previous" />
<ErrorBox v-else-if="state.status === 'error'" :error="state.error" @retry="refresh" />
<template v-else-if="state.status === 'success' || state.status === 'loading'">
  <ProductView :product="state.status === 'success' ? state.data : state.previous!" />
  <SmallSpinner v-if="state.status === 'loading'" />
</template>

代價是使用者可能誤以為舊資料就是新的，所以要有明顯的「更新中」提示。換到完全不同的東西（例如從商品頁換到會員頁）就不該帶，舊內容跟新頁面毫無關係，顯示它只會誤導。

最後，狀態存在 shallowRef 而不是 ref。load 每次都把 state.value 整個換成新物件，從來不會去改 state.value.data.price 這種深層欄位，所以只需要追蹤「.value 被換掉了」。用 ref 的話，Vue 會把整份資料（可能是幾百筆的商品列表）轉成深層的 Proxy，白做工；shallowRef 只追蹤 .value 本身（第 4 課）。

商品頁的兩個回報都修好了。但打開 Network 分頁，會看到另一件事：側欄的菜單和主畫面的菜單各呼叫了一次 useAsyncData，菜單 API 被打了兩次。useAsyncData 的狀態屬於呼叫它的那個元件，兩個元件就是兩份資料、兩個請求。

側欄和主畫面都要菜單，為什麼送了兩次請求？

兩次請求不只是浪費。兩個請求在不同時間點抓，如果中間剛好有人在後台改了價格，側欄和主畫面就會顯示兩個不同的價格。問題出在我們把菜單當成「元件自己的狀態」，但菜單根本不屬於任何一個元件。

第 15 課把狀態分成兩種。客戶端狀態（購物車、目前分頁、表單草稿）由前端擁有，前端說了算。伺服器狀態（菜單、訂單、會員點數）真正的版本在伺服器上，前端拿到的只是某個時間點的複本，店員、其他客人隨時可能改動它。

前端手上那份既然只是複本，它的本質就是快取（cache）：把從別處拿來的資料暫存在手邊，下次要用時不必再拿一次。快取省下請求和等待，代價是它可能過時。所以伺服器狀態要當成快取來管理，而任何快取都要回答三個問題：

  • 多個元件同時要同一份資料，該送幾個請求？一個。同一份資料同時有多個人要時只送一次請求，叫合併請求（dedupe）。做法就是 TS 課第 12 課的單一飛行：第一個要菜單的人送出請求，把進行中的 Promise 記在快取裡；第二個人看到已經有進行中的 Promise，就直接等同一個，不再送。側欄和主畫面的兩次請求，就是這樣變成一次，兩邊也保證拿到同一份資料。
  • 抓回來之後，多久算舊？菜單一小時改一次，訂單狀態一分鐘改好幾次，不能用同一個標準。資料抓回來後，在一段時間內視為新鮮、直接用快取不重抓，這段時間叫新鮮時間（staleTime）。超過了就是過期（stale），下次有人要時該重抓。
  • 資料被改了之後，誰負責更新畫面？客人收藏了商品、店員改了價格，用到這份資料的畫面都該重抓，不能等新鮮時間自然過完。主動把某份快取標成過期、讓正在用它的地方立刻重抓，叫快取失效（invalidation）。

過期的資料也不是沒用。客人回到菜單頁時，快取裡那份菜單可能已經過期幾分鐘，但它多半還是對的。stale-while-revalidate（SWR）的做法是：先顯示快取裡可能已經舊的資料，同時在背景重抓，抓回來再換掉。畫面立刻有東西，幾百毫秒後變成最新的。相比之下，過期就清空、重新顯示骨架畫面，客人每回到一頁就要等一次。

最後還有記憶體的問題。客人瀏覽過一百個商品，快取裡就有一百筆，客人早就不看的那些也一直佔著記憶體。所以沒有任何元件在用的資料，放一段時間就要從快取清掉，這段時間叫 gcTime。gc 是垃圾回收（garbage collection）的縮寫，指把沒人用的東西從記憶體清掉。

把這些串起來，就是一筆快取資料的生命週期：

💡 實務上：staleTime 是產品問題，不只是技術參數
「多久算舊」要問的是：資料舊了會出什麼事？菜單、門市營業時間晚幾分鐘更新沒人在意，可以設長一點；庫存、訂單狀態舊了會讓客人點到賣完的品項，就要短，或修改後馬上 invalidate。拿不準時去問 PM 或後端「這份資料多常變、誰會改它」。也別忘了前端快取只影響「畫面顯示」：結帳時的價格和庫存一定要由伺服器重新確認，不能相信前端手上的那份。

觀念有了，接著把它做出來：一個 Map 加上幾個欄位，就能讓側欄和主畫面共用同一個請求。

動手做查詢快取：每份資料要記住什麼？

查詢快取的核心是一個 Map<key, entry>。key 跟 useAsyncData 的 key 一樣，用來分辨要的是哪份資料，例如 'menu' 或某個商品的 id；entry 是這份資料的紀錄。元件不會直接碰這個 Map，而是透過一個 composable：useQuery(key, fetcher, { staleTime })，回傳 { data, error, isFetching }。每個呼叫 useQuery 的元件，就是這筆 entry 的一個「使用者」；側欄和主畫面都要菜單，'menu' 這筆就有兩個使用者。上一節的每個問題，都對應 entry 要多記一樣東西：

  • 新鮮時間 → 記住資料和抓回來的時間：entry 存 data 和 updatedAt，now() - updatedAt < staleTime 就直接回傳快取，不呼叫 fetcher。目前時間由參數 now 傳入而不是直接呼叫 Date.now()，測試才能自己決定「現在是幾點」，不必真的等 60 秒。
  • 合併請求 → 記住進行中的 Promise：entry 上已經有進行中的 Promise，就回傳它，不再呼叫 fetcher；請求結束時把它清掉，下一次過期才能重抓。
  • SWR → 另外記「現在有沒有在抓」：過期時 data 不清空，繼續給畫面用，同時背景重抓，並用 isFetching 表示「正在更新」。useQuery 沒有 status 欄位，資料的狀態看 data／error 有沒有值，isFetching 另外表示「有沒有請求在跑」。為什麼要分開？對照第一節的 status：status 說「資料是什麼狀態」（有沒有、成不成功），isFetching 說「現在有沒有請求在跑」。SWR 背景重抓時，資料是 success、同時 isFetching 是 true，用一個欄位表示不了這種組合。
  • 快取失效 → 把時間改舊，再通知使用中的人：invalidate 把 updatedAt 設成很久以前，有人在用就立刻重抓。只把 entry 從 Map 刪掉是不夠的：正在顯示的元件手上還拿著那份舊資料的 ref，刪掉 entry 不會有人去更新它，畫面會一直停在舊的。
  • gcTime → 記住有幾個使用者：useQuery 在 effect scope 裡呼叫（第 12 課：每個元件 setup 時 Vue 建立的副作用容器，元件卸載時會 stop），被呼叫時使用者加一，用 onScopeDispose（第 12 課）在元件卸載時減一。降到零的 entry 過了 gcTime 就從 Map 刪掉，不然記憶體只會越長越大。

下面這格先不用 Vue：query() 是拿掉 ref 和 scope 的 useQuery 骨架，只看合併與新鮮時間這兩件事：兩個「元件」同時要菜單，接著在 30 秒、61 秒後各再要一次，新鮮時間設 60 秒。執行後看 fetcher 被呼叫的次數：同時要的兩次只算一次，30 秒時還新鮮不重抓，61 秒時過期才重抓。

這個迷你版有個已知的洞：invalidate 時如果已經有請求在進行中，合併會共用那個舊請求，它可能在你改價之前就讀到資料了。正式的套件會取消或忽略進行中的請求、重新發一次。另外 key 在這裡只是字串；真實專案的 key 常是陣列（['product', id]），還要能「讓所有 product 開頭的 key 一起失效」。這些細節就是最後一節要談的「什麼時候用套件」。

到這裡，「讀資料」的三個回報都修好了：狀態不會矛盾、過期的回應會被丟掉、多個元件共用同一份資料。接下來客人按了收藏，這次不是讀資料，而是改資料，問題也跟著換了一種。

按收藏要等一秒才變色：怎麼讓畫面先動？

現在的收藏按鈕是這樣運作的：按下去、呼叫 API、等伺服器回應成功，才把愛心改成實心。網路慢一秒，畫面就一秒沒有反應，客人以為沒按到，又多按了兩下。這是「等伺服器確認才更新畫面」的代價：畫面的反應速度被網路綁住了。

收藏這類操作有個特點：幾乎每次都會成功。既然如此，可以反過來做。樂觀更新（optimistic update）是先假設伺服器會成功，立刻更新畫面，再在背景送出請求；萬一伺服器回報失敗，再回滾（rollback），也就是把畫面恢復成之前的狀態，並提示客人。成功的時候（絕大多數時候），客人完全感覺不到網路的延遲：

async function toggle() {
  const next = !isFavorite.value
  isFavorite.value = next          // 1. 立刻改畫面
  try {
    await api.setFavorite(id, next)
  } catch (e) {
    isFavorite.value = !next       // 2. 失敗回滾（這行還有問題，看下面）
    error.value = e
  }
}

這段程式單擊時沒問題，問題出在連點，而開場那位客人正好連點了。從「未收藏」開始連點三次，依序送出三個請求：

  1. A：收藏，畫面變實心。
  2. B：取消收藏，畫面變空心。
  3. C：收藏，畫面變實心。客人最後的意圖是收藏。

B、C 都成功了，A 卻在最後才逾時失敗。A 的 catch 執行 isFavorite.value = !next，把畫面改回「未收藏」。這時畫面說沒收藏，伺服器說有收藏，跟客人的意圖也不一樣。這和第二節的競態是同一種問題：一個過期的請求，在比較晚的時間點改寫了狀態。

修法也是同一個想法：以最後一次為準。每次點擊拿一個遞增的序號，失敗時先看自己是不是最新的那次，只有最新那一次才回滾、才設定錯誤；較早的請求失敗了，它的意圖早就被後來的點擊取代，什麼都不做。

回滾的目標也要換。上面的程式回滾到「這次點擊之前的值」，但連點時，點擊前的值往往是上一次點擊樂觀寫進去的，伺服器從來沒有確認過它。正確的目標是「伺服器最後一次確認過的值」：另外記一個變數，每次請求成功就更新它，失敗時回到它。這樣回滾後的畫面一定和伺服器一致。

什麼時候不要樂觀更新：付款、下單、退款這類高風險、不可逆的操作。畫面先顯示「付款成功」再改口「其實失敗了」，客人可能已經離開櫃台，店員可能已經開始做飲料，回滾畫面挽回不了現實裡已經發生的事。這類操作要顯示「處理中」、停用按鈕，等伺服器確認。樂觀更新適合失敗機率低、失敗了回滾也無妨的操作：收藏、按讚、勾選待辦。

收藏修好了。客人接著下了單，切到取餐頁等飲料，最後一個回報就發生在這裡。

取餐頁怎麼問「飲料好了沒」，才不會在背景問一整個下午？

取餐頁要知道飲料做好了沒，但伺服器不會主動告訴瀏覽器，只能由前端去問。輪詢（polling）就是每隔一段時間問伺服器一次。直覺的寫法是 setInterval(check, 5000)：每 5 秒呼叫一次 check，開場那個「打了一整個下午」的回報就是它造成的。

setInterval 版本其實有四個問題，背景分頁只是其中一個，下表整理原因和修法。

表格第二列要用到一個瀏覽器 API：要修背景分頁的問題，得先有辦法知道分頁是不是在背景。瀏覽器的 Page Visibility API（頁面可見性 API）提供這個資訊：document.visibilityState 告訴你分頁在前景（'visible'），還是被切到背景、視窗被縮小（'hidden'）；每次在兩者之間切換時，document 會發出 visibilitychange 事件。

問題原因修法
請求疊在一起伺服器慢到 8 秒才回，setInterval 不管上一個請求，照樣每 5 秒送一個上一次結束後才用 setTimeout 排下一次；用旗標確保同時只有一個請求
背景分頁一直問客人切去看別的網頁，請求照送，耗電、耗流量、浪費伺服器Page Visibility API：document.visibilityState 是 'hidden' 時不排計時器；監聽 visibilitychange，回到 'visible' 時立刻查一次
做好了還在問沒有停止條件狀態變成 ready 就停止，並移除監聽
離開頁面還在問計時器不屬於元件onScopeDispose 裡清計時器、移除監聽、abort 進行中的請求

四個修法合起來，核心是 check 自己排下一次，而不是交給一個固定節奏的計時器：

async function check() {
  timer = undefined
  if (stopped || inFlight || document.visibilityState === 'hidden') return
  inFlight = true
  try { status.value = await api.getOrderStatus(id, { signal }) }
  catch (e) { … }
  finally { inFlight = false }
  if (status.value === 'ready') return stop()
  if (!stopped && document.visibilityState === 'visible') timer = setTimeout(check, 5000)
}

由上往下對照表格：開頭的判斷擋掉「已經停止」「已經有請求在跑」「分頁在背景」三種情況；inFlight 旗標確保同時只有一個請求；請求結束後，狀態是 ready 就停止，否則在分頁可見時才用 setTimeout 排下一次，所以下一次一定在這一次結束 5 秒後。分頁隱藏時不排計時器，輪詢就自然停下來，等 visibilitychange 回到 'visible' 再立刻查一次、重新接上節奏。

輪詢的本質是前端一直問，大部分的回答都是「還沒好」。另一個方向是讓伺服器有變化時主動通知瀏覽器，常見的方式有兩種：

  • SSE（Server-Sent Events）：瀏覽器用 EventSource 開一條 HTTP 長連線，只有伺服器往瀏覽器送，斷線時瀏覽器會自動重連。適合通知、進度、即時看板。
  • WebSocket：雙向的長連線，兩邊隨時都能送。適合聊天、協作編輯、遊戲。

代價是：伺服器要維持很多條長連線、要處理斷線重連與漏掉的訊息、後端和負載平衡器都要支援。狀態變化頻繁、需要即時時才值得。訂單狀態幾分鐘才變一次，取餐慢 5 秒知道也沒關係，所以取餐頁用輪詢最簡單。

💡 實務上：輪詢間隔要和後端一起決定
一個人每 5 秒問一次不多，但尖峰時段幾百個客人同時開著取餐頁，就是後端要扛的固定流量。上線前先和後端確認這支 API 撐不撐得住、有沒有速率限制（每人每分鐘最多幾次，超過會回 429，第 16 課），查詢是不是夠輕（只回狀態，不回整張訂單）。常見做法還有：越久沒變化就把間隔拉長、輪詢一段時間後停下來改顯示「重新整理」按鈕。

到這裡，開場的五個回報都修好了。回頭看這課寫的東西：狀態模型、競態處理、查詢快取、樂觀更新、輪詢，每一個都還有沒處理的邊角。那麼正式專案裡，這些都要自己寫嗎？

這些都要自己寫嗎？什麼時候改用套件

這課自己做的東西，成熟的套件都有，而且多做了很多：失敗自動重試（含第 16 課的退避）、視窗重新聚焦或網路恢復時重抓、分頁與無限捲動、伺服器端渲染（第 24 課）時把伺服器抓好的資料帶到瀏覽器、DevTools。查詢快取那一節最後提到的洞（invalidate 時共用了舊請求、陣列 key 的批次失效），它們也都處理好了。Vue 生態系常見的兩個是 Pinia Colada 和 TanStack Query，版本、預設值與適合的情境整理在課末的補充與查表。

判斷方式：一兩個頁面要抓資料，useAsyncData 這種幾十行的 composable 就夠，少一個依賴。很多頁面共用伺服器資料、要 invalidate、要重試與聚焦重抓時，用套件，別把這課的迷你版一路長成自己的半套 TanStack Query。

套回咖啡店的 App：如果只有商品頁要抓資料，useAsyncData 就夠了；但菜單在側欄、主畫面、搜尋頁都會用到，收藏之後要讓好幾個畫面一起更新，這正是套件擅長的情況。即使改用套件，這課的原理也沒有白學：套件的 staleTime、gcTime、invalidate 調的就是你剛剛親手做過的東西，出問題時你知道該從哪裡查。

練習

在 learn/ 執行 node check.mjs vue 17。四題都是 composable，測試在 effectScope() 裡呼叫你的函式（模擬元件的 setup），用 deferred() 手動決定每個假請求什麼時候、以什麼結果完成，所以「舊的比較晚回來」每次都能重現。練習 4 用假計時器（第 5 課），並用 Object.defineProperty 改寫 document.visibilityState、發出 visibilitychange 事件來模擬切換分頁。

練習 1：把三個 ref 的 useAsyncData(key, fetcher) 改成回傳 { state, refresh }，AsyncState<T> 寫成 idle、loading（帶 previous）、success、error 四種的可辨識聯合。key 是空字串時是 idle、不抓（從別的 key 變成空字串時，也要 abort 進行中的請求）；key 改變時 abort 上一次的 signal 並重新抓，過期的回應（成功或失敗）都不能改 state；換 key 或 refresh 時，loading 帶著上一次的資料。測試也會用 vue-tsc 確認沒檢查 status 就讀 data 是型別錯誤。

練習 2：完成 createQueryCache({ now })。useQuery(key, fetcher, { staleTime }) 回傳 { data, error, isFetching }：同一個 key 同時被兩個 scope 使用只呼叫 fetcher 一次；新鮮時間內再使用直接給快取；過期後先給舊資料、背景重抓；invalidate(key) 讓使用中的 query 立刻重抓、更新原本的 data，沒人使用時等下一次 useQuery 才抓。失敗時 error 存 Error、data 保留原值，成功時 error 設回 null。快取放在 cache 物件裡，不要放在模組最外層。

練習 3：把等 API 回來才變色的 useFavorite(productId, initial, api) 改成樂觀更新：toggle() 立刻反轉 isFavorite；失敗時回到伺服器最後確認過的值並設定 error；連點時以最後一次為準，較早請求的失敗不能回滾、也不能設定 error。

練習 4：把 setInterval 版的 useOrderPolling(orderId, api) 改好：一建立就查；上一次結束後 5 秒才查下一次，任何時候最多一個請求；分頁隱藏時暫停、不留計時器，回到前景立刻查一次；狀態變成 ready 就停止；scope 停止時清掉計時器、移除監聽、abort 進行中的請求。

練習 5：一個元件的狀態是 isLoading = false、error = null、data = null。這代表什麼？

✓ 三個獨立的欄位有 8 種組合，好幾種狀態會落在同一個組合上：「還沒開始」和「成功但資料是 null」看起來一模一樣，a、b 都只猜對一半。可辨識聯合用 status: 'idle' | 'loading' | 'success' | 'error' 明確寫出是哪一種，每種狀態只帶自己需要的欄位。d 也有可能（例如 catch 裡忘了設定 error），這正是三個欄位容易出錯的地方。

練習 6：側欄和主畫面同時掛載，都用 useQuery('menu', getMenu)，快取裡還沒有菜單。應該送出幾個請求？

✓ 伺服器狀態是共用的快取，不屬於某個元件。第二個 useQuery 發現同一個 key 已經有請求在進行中，就共用那個 Promise（合併請求），兩個元件拿到同一份資料。各自抓會浪費一倍的請求，而且兩邊可能顯示不同時間點的資料。c 不對：沒有資料時 useQuery 本來就該自動抓。

練習 7：結帳頁的「付款」按鈕，適合用樂觀更新（先顯示付款成功，失敗再改回來）嗎？

✓ 樂觀更新的前提是「失敗機率低、失敗了回滾也無妨」。付款失敗時，客人可能已經看到「成功」就離開、或店員已經開始做飲料，回滾畫面挽回不了現實裡的事。付款這類操作要顯示處理中、停用按鈕防止重複送出、等伺服器確認。收藏、按讚這種小事才適合樂觀更新。

常見錯誤

  • 用多個布林值表示載入狀態：會組出「又載入又失敗」這種不存在的狀態。用 status 欄位的可辨識聯合。
  • 沒處理過期的回應：舊請求比較晚回來就蓋掉新結果。abort 上一次，並在 await 之後檢查自己是否已被取代，成功和失敗兩條路都要檢查。
  • 換參數時把畫面清空：畫面閃白、捲動位置跳掉。loading 帶著上一次的資料，加上明顯的更新中提示。
  • 每個元件各自抓同一份資料：請求加倍、畫面不一致。以 key 為單位快取，進行中的請求共用。
  • 快取永遠不過期：別人改了價格，畫面一直是舊的。設定 staleTime，修改之後 invalidate。
  • invalidate 只刪掉快取：正在顯示的元件手上的 ref 不會更新。使用中的 query 要立刻重抓。
  • 對不可逆的操作做樂觀更新：付款、下單要等伺服器確認。
  • 回滾時沒管連點：較早請求的失敗把新的狀態改回去。用序號，只讓最新一次回滾，回滾到伺服器確認過的值。
  • 用 setInterval 輪詢：伺服器慢時請求互相重疊。上一次結束後才 setTimeout 排下一次。
  • 背景分頁、完成之後、元件卸載之後輪詢還在跑：看 document.visibilityState、設停止條件、在 onScopeDispose 清掉計時器和監聽。

小結

  • 非同步狀態用可辨識聯合（idle、loading、success、error）表示，一個值只有一個 status，「又載入又失敗」這種不合法的組合寫不出來。
  • 參數改變時，abort 上一次並在 await 之後丟掉過期的回應（成功和失敗都要檢查），最新的請求勝出；loading 可以帶著上一次的資料，避免畫面閃爍。
  • 伺服器狀態是快取：以 key 為單位、合併同時的請求、新鮮時間內不重抓、過期先給舊資料再背景更新、修改後 invalidate、沒人用的過一段時間清掉。
  • 樂觀更新讓小操作即時反應，失敗回滾到伺服器確認過的值，連點以最後一次為準；付款、下單這類不可逆的操作不要樂觀更新。
  • 輪詢用 setTimeout 串起來，不重疊、分頁隱藏時暫停、完成就停、卸載時清理；需要即時才考慮 SSE 或 WebSocket。
  • 一兩頁用自己寫的 composable 就夠；多頁面共用伺服器資料時改用 Pinia Colada 或 TanStack Query，懂了原理才看得懂它們的選項。
