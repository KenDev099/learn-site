階段 7：品質、效能與架構 · 第 22 課

元件測試：測行為，不測實作

咖啡店的結帳按鈕有一套測試，全部是綠的。上週有人把按鈕的 class 從 btn-primary 改成 btn-main，又把 submitting 變數改名成 isSending，畫面和行為完全沒變，測試卻紅了十幾個，花了半天修。同一週，另一個人不小心刪掉了 :disabled，客人連點兩下就送出兩張訂單，這次測試全部是綠的。

該失敗的時候通過，不該失敗的時候失敗，兩件事是同一個原因：這套測試檢查的是「程式怎麼寫」，不是「使用者看到什麼、能做什麼」。這課從頭到尾做一件事：把結帳按鈕的測試重寫成「改名不會紅、刪掉 :disabled 一定紅」，再把同一套做法用到菜單頁和路由守衛上，最後確認這些測試本身可靠。

這課的路線：
  1. 舊測試錯在哪：為什麼改名會紅、刪掉 :disabled 卻是綠的。
  2. 重寫第一個測試：像使用者一樣找到按鈕、按兩下、看它能不能按（開場問題的最小答案）。
  3. 送出之後呢：讓測試決定 submit 什麼時候成功或失敗，每一步都知道自己在等什麼。
  4. 菜單頁和守衛：API 物件、store、router 這類依賴，在哪裡換成假的。
  5. 測試本身可不可靠：新測試真的抓得到刪掉 :disabled 嗎；CI 上時好時壞的紅燈從哪裡來；最後回頭看什麼該用元件測試、什麼不該。
這課會用到：
  • 第 8 課的 Vue Test Utils（以下簡稱 VTU）入門：mount 掛載元件，find 找元素，trigger 觸發事件；vi.useFakeTimers() 讓測試自己推進時間。
  • 第 6 課「測試裡要等什麼」那張表：DOM 更新等 nextTick，Promise 接續的工作等 flushPromises。

舊測試錯在哪：它檢查的是程式怎麼寫

先看出事的那個測試長什麼樣。這是結帳按鈕原本的測試之一（簡化過）：

test('送出中按鈕會停用', async () => {
  const submit = () => new Promise<void>(() => {})   // 永遠不完成，元件會停在「送出中」
  const wrapper = mount(CheckoutButton, { props: { submit } })
  await wrapper.get('.btn-primary').trigger('click')
  expect(wrapper.vm.submitting).toBe(true)
})

它做的事很直接：用 mount 把元件掛起來，用 class .btn-primary 找到按鈕點一下，然後讀元件內部的變數 submitting，確認它是 true。submit 回傳一個永遠不會完成的 Promise，所以點下去之後元件一直停在「送出中」，正好可以檢查這個狀態。

為什麼改名會紅？class 改成 btn-main 之後，wrapper.get('.btn-primary') 找不到元素，直接丟錯；變數改名成 isSending 之後，wrapper.vm.submitting 變成 undefined，斷言失敗。這兩個改動客人完全感覺不到，測試卻把它們當成 bug。十幾個測試都這樣寫，一次重構就紅十幾個。

為什麼刪掉 :disabled 卻是綠的？因為點下去之後 submitting 照樣變成 true，測試要看的東西沒變。測試從頭到尾沒有看「按鈕還能不能按」。客人在乎的是按鈕不能再按，測試檢查的是某個變數是 true；平常這兩件事一起成立，靠的就是 :disabled="submitting" 這一行把它們接起來。有人刪掉這一行，兩件事分開了，測試只盯著其中一邊，自然看不到另一邊壞掉。

內部變數、方法名稱、class、DOM 的巢狀結構，這些使用者看不到、重構時隨時可能改的東西，叫做實作細節（implementation detail）。測試依賴實作細節，就會同時出現開場的兩種毛病：重構時誤報，真正壞掉時漏報。和它相對的是行為：使用者看得到、做得到的事，例如按鈕上的字、按鈕能不能按、錯誤訊息有沒有出現、按下去有沒有送出。只要行為不變，測試就不該壞；行為一變，測試就該紅。

依賴實作細節依賴行為
expect(wrapper.vm.submitting).toBe(true)expect(button.element.disabled).toBe(true)：使用者看到的是按鈕不能按
wrapper.get('.btn-primary')wrapper.get('button')，或用文字找「送出訂單」那顆
wrapper.find('.error-text')wrapper.find('[role="alert"]')：螢幕閱讀器也靠它唸出錯誤
wrapper.vm.load() 直接呼叫內部方法點「重試」按鈕

wrapper.vm 特別容易讓人上當。第 8 課提過，它連 <script setup> 沒有 defineExpose 的變數都看得到，寫起來很方便。但使用者和父元件都拿不到這些東西，測它們等於把測試綁死在現在的寫法上：誰把變數改個名字，測試就壞。

所以方向是：測試要像使用者一樣找到按鈕、按它、看它的反應，完全不碰元件內部。下一節照這個方向，把這個測試重寫一次。

重寫第一個測試：像使用者一樣找按鈕、按按鈕

到這課為止你都在讀別人寫的測試（結構從第 4 課開始看過），現在要自己寫。先交代測試在哪裡跑：練習專案的測試跑在 Node 裡，Node 本身沒有 document，所以專案裝了 happy-dom 21.0.4。它是用 JavaScript 寫的假 DOM，提供元素、事件、表單屬性，元件可以掛在上面、按鈕可以被點，不用開真的瀏覽器，一個測試只要幾十毫秒。它也有做不到的事（例如沒有版面計算），最後一節談測試該放在哪一層時再說。

下面是重寫後的完整測試檔。它跟舊測試檢查的是同一個時刻（送出中），但看的是使用者看得到的東西：

import { describe, expect, test, vi } from 'vitest'
import { mount } from '@vue/test-utils'
import CheckoutButton from './CheckoutButton.vue'

describe('結帳按鈕', () => {
  test('送出中按鈕停用，連點也只送出一次', async () => {
    const submit = vi.fn(() => new Promise<void>(() => {}))   // 永遠不完成：停在「送出中」
    const wrapper = mount(CheckoutButton, { props: { submit } })
    const button = wrapper.get('button')

    await button.trigger('click')
    await button.trigger('click')

    expect(button.element.disabled, '送出中按鈕要停用').toBe(true)
    expect(submit, '連點只能送出一次').toHaveBeenCalledTimes(1)
  })
})

由上往下一行一行看：

  • describe 把同一個元件的測試放在一組，test 是一個情境，名字寫的是規則本身。紅燈時看名字就知道哪個行為壞了，所以一個 test 只檢查一件事。
  • vi.fn(…) 建立一個假函式。它跟一般函式一樣可以被呼叫，括號裡的函式就是它被呼叫時實際執行的內容（這裡回傳一個永遠不完成的 Promise）；不一樣的是它會記下自己被呼叫了幾次、每次的參數是什麼。元件需要一個 callback 時，傳 vi.fn() 進去，事後就能問它「被呼叫了幾次」。這種會記錄呼叫的假函式叫 spy。
  • wrapper.get('button') 用元素種類找按鈕。結帳按鈕的畫面上只有一顆按鈕，使用者也是靠「這是一顆按鈕」找到它的，所以 class 怎麼改都影響不到這一行。
  • 點兩下，每一下都 await，等這一輪畫面更新完再點下一下，就像真人的兩次點擊。
  • button.element 是真正的 DOM 元素，.disabled 就是瀏覽器裡那個屬性。這一行問的是「按鈕現在能不能按」，跟元件內部的變數叫什麼無關。

expect(實際值) 後面接的檢查方法叫 matcher。這裡用了兩個：toBe(x) 檢查是不是同一個值（用 Object.is 比較，適合數字、字串、布林）；toHaveBeenCalledTimes(n) 問假函式被呼叫了幾次。expect 的第二個參數是失敗時顯示的說明，寫清楚「哪條規則壞了」，半年後看到紅燈的人才不用去讀測試猜意思。其他常用的 matcher 整理在課末的「補充與查表」。

關鍵在第二下點擊。VTU 2.5.1 的 trigger 遇到有 disabled 屬性的按鈕時不會發出事件，跟真正的使用者點不到一樣。所以：

  • 元件正確時，第一下之後按鈕停用，第二下沒有效果，submit 只被呼叫一次，測試通過。
  • 有人刪掉 :disabled，按鈕在送出中仍然能按，第二下照樣送出：disabled 是 false、submit 被呼叫兩次，測試紅。
  • 有人把 class 改成 btn-main、把 submitting 改名成 isSending，測試根本沒碰這兩樣東西，照樣通過。

這就是開場問題的最小答案：測試只透過使用者看得到的東西操作和檢查，重構就不會誤報，真的壞了也不會漏報。

結帳按鈕只有一顆按鈕，用元素種類找就夠了。畫面複雜一點時，要先認識 role。role 是螢幕閱讀器這類輔助技術用來判斷元素「是什麼」的語意：<button> 天生就是 button role，<ul> 是 list，不用另外寫。元素本身沒有這種語意時，可以用 role 屬性標上，例如錯誤訊息加 role="alert"，它一出現螢幕閱讀器就會馬上唸出來。有了這個概念，找元素的優先順序是：role（這個元素是按鈕、清單還是警示）→ label（表單欄位的標籤、aria-label）→ 使用者看得到的文字。例如菜單頁失敗時，畫面上可能同時有「重試」和其他按鈕，就要用文字挑出要的那一顆：

function buttonWithText(wrapper: VueWrapper, text: string) {
  const button = wrapper.findAll('button').find(b => b.text().includes(text))
  if (!button) throw new Error(`找不到文字含「${text}」的按鈕`)
  return button
}
await buttonWithText(wrapper, '重試').trigger('click')

findAll('button') 回傳所有按鈕，b.text() 是按鈕上的文字。這樣找還有一個附帶的好處：一個元素用 role、label、文字都找不到，常常代表螢幕閱讀器的使用者也認不出它，測試順便替你抓到了無障礙的問題。專門做這件事的 Testing Library 見課末「補充與查表」，這課的練習只用 VTU。

不過這個測試只停在送出中，因為 submit 永遠不會完成。規格還要求成功後顯示「已送出」、失敗時出現錯誤而且能再按。要測這些，測試得能決定 submit 什麼時候完成、是成功還是失敗。

送出之後呢：讓測試決定 submit 什麼時候完成

上一節的 submit 永遠停在半路。最直覺的改法是讓它真的去等一段時間再成功，測試也跟著睡一下再檢查。問題是測試這時是在「猜」：猜 submit 多久會好、猜畫面多久會更新。猜錯了，測試就時好時壞。正確的做法是反過來，讓測試決定 submit 什麼時候完成。

工具是練習專案的 deferred()（helpers/deferred.ts）。它回傳 { promise, resolve, reject }：這個 promise 會一直等著，直到測試呼叫 resolve() 讓它成功、或呼叫 reject(錯誤) 讓它失敗。把它交給假的 submit 回傳，元件 await submit() 時就卡在那裡，什麼時候放行由測試說了算。下面是「失敗」這個情境：

import { flushPromises } from '@vue/test-utils'
import { deferred } from '../../helpers/deferred.ts'

const d = deferred()
const submit = vi.fn(() => d.promise)          // submit 會一直等，直到測試說可以
const wrapper = mount(CheckoutButton, { props: { submit } })

await wrapper.get('button').trigger('click')   // 等這一輪 DOM 更新：按鈕變成停用
expect(wrapper.get('button').element.disabled).toBe(true)

d.reject(new Error('網路斷線'))                 // 現在讓它失敗
await flushPromises()                           // 等元件裡 await 之後的程式和畫面更新跑完
expect(wrapper.find('[role="alert"]').exists()).toBe(true)

這段用到兩種等待，各自在等不同的東西；第三種是用了假計時器時的替代：

  • await trigger() 只等「這一輪 DOM 更新」。元件在 click handler 裡 await submit()，submit 完成之後的程式不在這一輪裡。
  • await flushPromises() 等目前已經完成的 Promise 的後續程式全部跑完，接著的畫面更新也一起完成。讓假 API 成功或失敗之後，用它。
  • 用了 vi.useFakeTimers() 時，flushPromises 會卡住（第 6 課），改用 await vi.advanceTimersByTimeAsync(ms)。

順序是：點擊、確認送出中的樣子、讓 submit 有結果、等後續程式跑完、確認結果的樣子。每一個 await 都說得出它在等什麼，測試每次跑的結果就一樣。

成功、失敗、失敗後重試，每個情境都要自己 mount 一次、建立自己的 deferred 和 vi.fn()。不要讓「失敗」的情境接著用「成功」那個情境留下的 wrapper：那個元件已經顯示「已送出」，按鈕根本不在畫面上，後面的檢查不是在測失敗，而是在測上一個情境的殘留。重試的情境則是在失敗之後再點一次按鈕，檢查 submit 被呼叫了第二次。練習 1 就是把這幾個情境寫完整。

不要寫 await new Promise(r => setTimeout(r, 100))。它沒說清楚在等什麼；CI 機器忙的時候 100ms 不夠，測試就時好時壞；每個測試都多等 100ms，幾百個測試加起來就是好幾分鐘。

忘了 await 是另一個常見的洞：斷言在畫面更新前就執行，或根本沒執行到。Vitest 5 對其中一種情況多了一道保險，見課末「補充與查表」。

結帳按鈕好測，是因為它唯一的依賴 submit 從 props 傳進來，測試直接塞一個假函式就好。菜單頁的依賴不再只是一個函式，而是一個 API 物件，掛載時呼叫一次、按重試又呼叫一次，每次的結果都要由測試決定；路由守衛更是根本沒有 props，它要的是 router 和登入狀態。這些依賴，測試要從哪裡把它們換成假的？

菜單頁和守衛：依賴不只是一個 callback 時，在哪裡換成假的？

先給「換成假的」一個名字。測試裡代替真實依賴的假東西統稱測試替身（test double），依用途分幾種：只回傳固定資料、不記錄任何事的叫 stub；上一節的 vi.fn() 會記錄自己被怎麼呼叫，叫 spy；事先設定好「應該被怎麼呼叫」、呼叫不符就失敗的叫 mock。日常對話裡這幾個詞常混著用，重點不在名字，在於換掉哪些東西。

原則是只在邊界換。邊界指元件跟外面世界接觸的地方：網路、時間、亂數、全域狀態。這些東西慢、每次結果不一樣、或者會被別的測試動到，換成假的，測試才快而且每次結果相同。邊界以內的東西，元件自己和它的子元件，保持真的：測試要看的正是它們合在一起的行為，把子元件也換掉，就又變成在測「元件怎麼組起來」這種實作細節（相關的 shallowMount 見課末「補充與查表」）。

每種常見的依賴，在測試裡各有慣用的換法。這張表查表用，不用背：

依賴測試裡怎麼換
API client用 props 或 provide 傳進去（第 13 課）。練習專案的 createFakeMenuApi({ manual: true })（helpers/fake-api.ts）是一個假的菜單 API：每次呼叫都會記在 api.calls，等測試用 api.callsOf('getMenu')[0].resolve()／reject(錯誤) 決定結果
callbackvi.fn()，需要控制完成時間就回傳 deferred().promise

菜單頁用的是第一列。它的 API 從 props 傳進來，所以測試傳一個假 API：元件掛載時呼叫 getMenu()，這次呼叫被記下來，像上一節的 deferred 一樣停著，測試看完「載入中」再決定讓它成功或失敗。跟結帳按鈕是同一套做法，只是假的東西從一個函式變成一個物件。也正因為 API 從 props 傳進來，測試不需要 vi.mock（本節最後一段）去換掉元件 import 的模組。練習 2 就是這樣測菜單頁的載入、失敗和重試。

守衛用的是路由那一列，這裡要特別說明為什麼用真的 router。守衛本身只是一個函式，看起來可以假造一個 to 物件直接呼叫它。但真正導航時，to.meta 會合併父路由的 meta、redirect 會再跑一次守衛，這些只有真的 router 才會做；假造的 to 少了它們，測試通過也不代表上線後正確。createMemoryHistory() 讓 router 把網址記在記憶體裡，不碰瀏覽器的網址列，在 Node 裡也能跑，守衛照樣執行。下面這段裡，installGuards(router, auth) 是第 20 課寫的函式，會在 router 上用 beforeEach 註冊守衛；routes 是路由表，練習 3 的起始檔照第 20 課的路由寫了一份，帶著 meta.requiresAuth、meta.permission；fakeAuth 是假的登入狀態，這裡是沒登入的使用者：

const router = createRouter({ history: createMemoryHistory(), routes })
installGuards(router, fakeAuth)
await router.push('/orders?status=ready')
expect(router.currentRoute.value.name).toBe('login')
expect(router.currentRoute.value.query.redirect).toBe('/orders?status=ready')

這段測試以「沒登入的使用者」身分去 /orders?status=ready，檢查最後停在登入頁、而且 redirect 帶著完整的網址（含 ? 後面的 query）。真正的依賴只換了 fakeAuth（登入狀態），路由表、守衛、導航都是真的。練習 3 用同樣的方式檢查第 20 課的每一條守衛規則。

還有一種換法是 vi.mock()：它把元件 import 的整個模組換成假的，不用改元件就能替換依賴。它是最後手段，因為它讓測試知道「元件 import 了哪個檔案」，這也是實作細節：有人把 API 呼叫搬到另一個檔案，行為沒變，測試就壞了。能用 props 或 provide 傳進去，就不要用 vi.mock。Vitest 5 對它的寫法位置有限制，見課末「補充與查表」。

💡 實務上：很難測，通常是元件設計的訊號
如果一個元件的測試要 vi.mock 五六個模組才跑得起來，代表它自己直接 import 了 API、store、時間，依賴全藏在裡面。這時該改的常常是元件，不是測試：把依賴改成從外面傳進來、把計算抽成純函式，測試自然變簡單，元件也更好重用。結帳按鈕好測，就是因為 submit 從外面傳進來。另一個常見的坑是假 API 和真的後端慢慢對不上：後端改了欄位，假資料沒改，測試全綠、上線卻壞。讓假資料使用和正式程式碼同一份型別定義，再靠少數 E2E 連真的（或測試用的）後端兜底。

到這裡，結帳按鈕、菜單頁、守衛都有了只看行為的測試。但我們還沒證明一件事：新的結帳測試，真的會在有人刪掉 :disabled 時變紅嗎？舊測試當初也是「看起來有在測」。

新測試真的抓得到刪掉 :disabled 嗎？測試你的測試

舊測試的教訓是：測試本身也是程式，也會寫錯，而且寫錯的測試照樣是綠的。所以光看到綠燈不夠，要能說出這個測試為什麼有用。一個有用的測試要滿足兩個條件：

  1. 元件壞掉時，它要失敗。
  2. 元件換一種寫法但行為一樣時，它要通過。

開場的舊測試兩個都沒做到：刪掉 :disabled（壞掉）時它通過，改 class 和變數名稱（換寫法）時它失敗。檢驗方法就是照這兩個條件真的去試：故意把程式改錯，看測試抓不抓得到。這叫做變異測試（mutation testing），每一個改錯的版本叫一個變異（mutant）；「刪掉 :disabled」就是結帳按鈕的一個變異。有工具會自動產生大量變異版本（例如把 > 換成 >=、刪掉一行），這裡先用手做的版本體會。元件不能在這個頁面上掛載，所以換一個能直接執行的小例子：結帳時的折扣規則。執行後看兩行輸出的「抓到幾個」：

弱的測試抓到兩個，漏掉了「>= 改成 >」：剛好 300 元的客人少了折扣，它完全沒發現。強的測試檢查了邊界的兩邊（299、300），三個全抓到，而且兩個正確版本都通過。弱測試的問題跟開場的舊測試一樣：它檢查的那一點，在對的版本和錯的版本上剛好都成立，所以分不出兩者。結帳按鈕的新測試之所以抓得到刪掉 :disabled，也是因為它檢查的「第二下點擊」正好落在對錯兩版行為不同的地方。

這課的練習就這樣判分：你寫的不是一般的測試，而是一個「檢查函式」，接收一個元件，元件不符合規格就丟錯。判分程式把你的函式套在兩個內部寫法不同的正確版本上（都要通過），再套在好幾個錯誤版本上（每個都要丟錯）。所有版本的元件名稱都一樣，你只能看行為分辨。

測試抓得到錯之後，還有一個條件：同一份程式，每次跑的結果要一樣。如果一個測試今天紅、重跑一次又綠，大家很快就不再相信它，它抓到的錯也會被當成運氣不好。

不穩定測試：CI 上時好時壞的紅燈從哪裡來？

程式沒改，卻有時通過有時失敗的測試，叫做不穩定測試（flaky test）。它比沒有測試還糟：大家學會「紅了就重跑」，真正的錯誤也被當成運氣不好。這課前面幾節的做法，有一半就是在防它：用 deferred 取代 sleep、每個情境自己 mount、每個測試建立新的 router。常見的原因整理成一張表：

原因症狀修法
用真實時間過午夜、跨月、CI 比較慢時失敗假計時器，或把 now() 當參數傳入
用亂數偶爾抽到邊界值時失敗把 random() 當參數傳入，測試給固定值
測試之間共用狀態單獨跑會過，全部一起跑就失敗；換順序結果不同每個測試建立新的 pinia、router、API 替身；不要放在模組最外層
等待時間不夠本機會過，CI 上失敗用 deferred 控制完成時間，再 await flushPromises()；不要 sleep
忘了 await斷言在畫面更新前就跑了，或斷言根本沒跑trigger、setValue、flushPromises、rejects 都要 await

共用狀態最難發現，因為每個測試單獨看都對。前面「菜單頁和守衛」那節的守衛測試就是典型的例子：第 20 課的守衛把「loadMe 的 Promise」存在閉包裡，第一次導航時呼叫 loadMe，之後都沿用同一個 Promise。如果兩個情境共用同一個 router，第二個情境的守衛不會再呼叫 loadMe，使用者還是第一個情境的那個人，正確的守衛也會被判錯；換個順序跑，結果又不一樣。練習 3 的錯誤寫法之一就是這樣，所以起始檔的 setup() 每次都建立新的 router 和假 auth。

💡 實務上：CI 上的不穩定測試要當成 bug 處理
團隊裡最傷士氣的就是「CI 紅了，重跑一次就好」。發現不穩定測試時，常見做法是開一張單、指定負責人，必要時先暫時跳過（test.skip 並註明單號），而不是加上自動重試把問題蓋掉。查原因時先在本機單獨跑那個檔案、連續跑多次、或打亂測試順序，看是時間、亂數還是共用狀態造成的。自動重試會讓真正的偶發錯誤（例如元件裡的競態）也被吞掉，資深工程師會很謹慎地使用。

到這裡，結帳按鈕、菜單頁和守衛的元件測試都只看行為、抓得到錯、每次結果一樣。最後退一步看：元件測試不是唯一一種測試，哪些東西該交給它，哪些不該？

這套測試放在哪一層：什麼該用元件測試，什麼不該？

前端的自動化測試大致分三層，越往上越接近真實使用，也越慢、越難查錯：

層次測什麼速度與成本例子
純函式（單元測試）沒有畫面的邏輯：計算、轉換、驗證規則每個幾毫秒，失敗時馬上知道是哪一行購物車小計、折扣規則、hasPermission
元件測試（component test）掛載一個元件、模擬使用者操作、檢查畫面與發出的事件每個幾十毫秒，在 Node 裡用 happy-dom 模擬瀏覽器結帳按鈕、菜單頁的載入／失敗／重試
E2E 測試（end-to-end）在真正的瀏覽器裡操作整個 App，連真的（或測試用的）後端每個數秒，要啟動伺服器和瀏覽器；失敗原因可能在任何一層登入 → 點餐 → 結帳 → 看到訂單

上一節的折扣規則就屬於第一層：它沒有畫面，抽成純函式之後幾毫秒就能測完邊界的兩邊。這課寫的結帳按鈕、菜單頁屬於第二層。常見的分配是：純函式測試最多，元件測試涵蓋主要的使用者行為，E2E 只留給少數「壞了就不能做生意」的關鍵流程。能抽成純函式的邏輯先抽出去測，元件測試就只需要確認「畫面有接好」：按鈕有沒有停用、錯誤有沒有出現、重試有沒有再呼叫 API。

元件測試的上限來自 happy-dom。第二節說過它是假的 DOM，它沒有版面計算：元素的寬高、位置都是 0，不知道 CSS 讓元素看不看得見，也不會真的捲動；IntersectionObserver 雖然存在，但 observe() 什麼都不做，callback 永遠不會被呼叫。結帳按鈕的停用、菜單頁的重試只牽涉事件、屬性和文字，happy-dom 完全夠用。但要測「被別的元素擋住點不到」「捲到底載入更多」「深色模式的顏色」，就要用真的瀏覽器：Vitest 的 browser mode，或 E2E 工具 Playwright（@playwright/test 1.64.1）。

💡 實務上：先替「壞了會賠錢」的流程寫測試
接手一個幾乎沒有測試的專案很常見，不必一開始就追求覆蓋率（測試跑過的程式碼占多少比例）。先挑結帳、下單、登入這類壞了會直接影響營收或客訴的流程：純邏輯補單元測試、主要畫面補元件測試，再寫一兩條 E2E 跑通「點餐到結帳」。客服回報 bug 時，先寫一個能重現它的失敗測試再修，這個 bug 就不會在下次重構時偷偷回來：開場那張「連點送出兩張訂單」的單，就該先變成上面那個連點兩下的測試。PR review 時資深工程師常問的不是「覆蓋率幾 %」，而是「這次改的行為，壞了哪個測試會紅？」

補充與查表

常用的 matcher

查表用，不用背。

matcher檢查什麼
toBe(x)同一個值（Object.is）：數字、字串、布林、同一個物件
toEqual(x)內容相同：兩個不同的物件或陣列，欄位一樣就算
toContain(x)字串包含子字串、陣列包含元素
toHaveLength(n)陣列或字串的長度
toHaveBeenCalledTimes(n)、toHaveBeenCalledWith(…)假函式被呼叫幾次、用什麼參數
await expect(p).rejects.toThrow('…')Promise 失敗，錯誤訊息含某段文字；resolves 是成功的版本
.not.toContain(x)任何 matcher 前面加 .not 就是反過來

這課常用的 VTU 操作

VTU 的操作在第 8 課看過，這課常用的再加幾個：wrapper.findAll('li') 回傳所有符合的元素；el.text() 是元素的文字；el.attributes('aria-label') 讀屬性；el.element 是真正的 DOM 元素，例如 button.element.disabled。

Testing Library

Testing Library（@testing-library/vue 8.1.0）把「用 role、label、文字找元素」的想法做成了 getByRole('button', { name: '重試' }) 這類查詢。這課的練習只用 VTU，用 buttonWithText 那種寫法做到同樣的事。

shallowMount

shallowMount 會把所有子元件換成空殼（stub），只渲染元件自己這一層。如果「送出」按鈕其實在子元件 BaseButton 裡，shallowMount 之後根本按不到，測試只能退回去檢查 props 有沒有傳對，又變成測實作。預設用 mount；只有某個子元件真的很重（圖表、地圖）或有副作用時，用 global: { stubs: { SalesChart: true } } 單獨換掉它。

快照測試

快照測試（snapshot，expect(wrapper.html()).toMatchSnapshot()）把整段 HTML 存起來，之後每次比對。任何一個 class、空白改了都會紅，大家很快就養成「更新快照」直接按過的習慣，它就什麼都抓不到了。要用的話，只用在小而穩定的輸出上。

Vitest 5 跟這課有關的變化

以下來自官方遷移指南：

  • expect(p).rejects.toThrow() 忘了 await，以前測試會在斷言還沒跑完時就算通過，現在 Vitest 會發現沒有 await 的非同步斷言，直接讓測試失敗。
  • clearMocks 預設開啟：每個測試開始前清掉所有假函式的呼叫紀錄。在模組最外層或 beforeAll 裡呼叫過的紀錄，進到測試時已經沒了。
  • vi.mock() 只能寫在檔案最外層。寫在 describe 或 test 裡會直接丟錯，因為它本來就會被提到檔案最前面執行，寫在裡面只會讓人誤會。

練習

在 learn/ 執行 node check.mjs vue 22。三題都是寫「檢查函式」：CheckoutButton.vue、MenuPage.vue、guards.ts 是寫好的正確版本，開頭的註解就是規格，你的檢查只能依賴規格寫到的東西。隱藏的測試會把你的函式套在多個正確和錯誤版本上，告訴你哪個版本沒過。

練習 1：完成 checkCheckoutButton(Component)：用 vi.fn() 加 deferred() 做出你能控制的 submit，檢查送出中按鈕停用、連點只呼叫一次、成功後顯示「已送出」、失敗時有 role="alert" 而且沒有「已送出」、失敗後可以再按而且真的會再呼叫 submit。兩個正確版本的變數、class、送出中的文字都不一樣，不能讀 wrapper.vm、不能用 class 找按鈕；七個錯誤版本都要抓到。

練習 2：完成 checkMenuPage(Component, makeApi)：每個情境用 makeApi() 拿新的假 API，檢查載入中、成功時列出全部品項、失敗時顯示 role="alert" 的錯誤和「重試」、按重試會再呼叫 API 並回到載入中、重試成功後錯誤消失。每一步都要確認「載入中」該出現或不該出現。讓 API 完成後用 await flushPromises() 等，不能用 setTimeout；另一個正確版本錯誤時有兩顆按鈕。

練習 3：完成 checkGuards(installGuards)：用起始檔的 setup() 為每個情境建立新的 router（createMemoryHistory）和假 auth，檢查第 20 課的規則：沒登入導向登入頁並帶完整的 redirect（含 ? 後面的 query）、沒登入去需要權限的頁面也是先到登入頁、沒登入進得了登入頁和 403、權限不足到 403、有權限進得去、已登入去登入頁回到 /、多次導航 loadMe 只呼叫一次。不要把 router 或 auth 放在函式外面。

練習 4：結帳按鈕的測試要找到「送出訂單」按鈕。哪一種寫法最不怕重構？

✓ 使用者靠「這是一顆按鈕、上面寫送出訂單」找到它，只要這件事不變，測試就不該壞；文字真的改了，使用者看到的東西也變了，測試失敗是合理的。a 綁死在樣式上，換設計系統或改名就壞，b 綁死在 DOM 結構上，多包一層 div 就壞。d 不怕改樣式，比 a、b 好，但它是只為測試存在的東西，使用者和螢幕閱讀器都看不到，沒辦法順便抓到「按鈕沒有可讀的名稱」這類問題；找不到合適的 role 或文字時才用它。

練習 5：菜單頁的測試寫了 await new Promise(r => setTimeout(r, 100)) 等 API 回來，本機一直都過。這樣寫有什麼問題？

✓ sleep 是在猜時間。猜少了，機器慢的時候測試就時好時壞（不穩定測試）；猜多了，幾百個測試一起浪費時間。a 把等待加長，只是把問題變慢、變少見。c 不對：nextTick 只等這一輪 DOM 更新，不等元件裡 await api.getMenu() 之後的程式。用 deferred 讓測試自己決定 API 什麼時候完成，再用 flushPromises 把後續的程式跑完，結果每次都一樣。

練習 6：下面哪一種情況，用 happy-dom 的元件測試不夠，需要真的瀏覽器（Vitest browser mode 或 Playwright）？

✓ happy-dom 不計算版面：元素沒有真正的大小和位置，也不會捲動，IntersectionObserver 這類依賴版面的 API 不會像瀏覽器那樣觸發。d 要在真的瀏覽器裡測，或把「看到最後一個元素就載入」的邏輯抽出來，元件測試只測接線。a、b、c 都只牽涉事件、屬性和文字，happy-dom 夠用，而且快得多。

常見錯誤

  • 測內部狀態：讀 wrapper.vm.submitting、直接呼叫 wrapper.vm.load()。重構就壞，元件壞了反而可能沒發現。檢查使用者看得到的結果，用使用者的方式操作。
  • 用 class 或 DOM 結構找元素：換樣式、多包一層就壞。依序用 role、label、文字。
  • 全部用 shallowMount：子元件變成空殼，按鈕在子元件裡就按不到，只能退回去測 props。預設 mount，只把真的很重的子元件 stub 掉。
  • 用 sleep 等待：慢而且不穩定。用 deferred 控制完成時間，再 await flushPromises()。
  • 忘了 await：trigger、flushPromises、rejects 沒 await，斷言在畫面更新前就跑，或根本沒跑。
  • 測試之間共用 pinia、router、API 替身：單獨跑會過、一起跑會壞。每個測試（每個情境）都建立新的。
  • 只測成功的路徑：失敗、重試、連點這些路徑才是最常出事的地方。
  • 濫用快照測試：大段 HTML 快照什麼改動都會紅，最後大家直接更新快照。只對小而穩定的輸出用。
  • 不知道測試有沒有用：故意把元件改錯，看測試會不會紅；換一種寫法，看測試會不會誤報。

小結

  • 測行為不測實作：依賴內部變數、class、DOM 結構的測試，重構時誤報、真的壞掉時漏報。用 role、label、文字找元素，檢查使用者看得到的結果，不讀 wrapper.vm、不用 class。
  • 結帳按鈕的最小答案：get('button') 找按鈕、連點兩下，檢查 element.disabled 和 vi.fn() 的呼叫次數；VTU 的 trigger 不會點到停用的按鈕，所以刪掉 :disabled 一定紅。
  • 非同步要知道自己在等什麼：await trigger() 等 DOM 更新，deferred 決定 API 何時完成，flushPromises 等後續程式跑完，假計時器配 advanceTimersByTimeAsync；不要 sleep。每個情境自己 mount。
  • 只在邊界換依賴：API 用注入的替身、callback 用 vi.fn()、store 用 createTestingPinia、路由用真的 router 加 createMemoryHistory，每個測試建立新的；vi.mock 是最後手段。
  • 好測試在錯誤版本上失敗、在重構過的正確版本上通過；用手做的變異版本檢驗自己的測試。
  • 不穩定測試多半來自真實時間、亂數、共用狀態、sleep、忘了 await，要當成 bug 處理。
  • 純函式測試最多、元件測試涵蓋主要行為、E2E 只留給關鍵流程；需要版面、捲動、真實 CSS 時才用真的瀏覽器。
