階段 7：品質、效能與架構 · 第 25 課

前端架構：模組邊界、依賴方向與設定

咖啡店的點餐系統上線一年，從三個頁面長到三十個。這週你接到兩張單。第一張：老闆要把「會員 9 折」改成「會員 95 折」。你搜尋 0.9，在四個元件裡找到四份計算，而且彼此不太一樣，有的先算運費再打折，有的反過來。第二張：外送功能已經停用，要把它的程式刪掉。你刪掉外送的 store，整個 app 就編譯不過，原因是共用的按鈕元件 import 了外送的 store。

每個檔案單獨看都沒問題，問題出在檔案之間的關係：同一條規則散在四個地方，最底層的共用按鈕反過來依賴一個業務功能。這課的任務是把這個專案整理到「改折扣只改一個地方、刪一個功能不會拖垮別的功能」，並且讓整理後的規則由測試自動把關，半年後不會又長回原樣。整理完的程式要部署到測試與正式環境，所以最後處理兩件跟架構一起決定的事：每個環境不同的設定（環境變數）怎麼放才不外洩、不漏設；門市在後台填的連結與公告，怎麼顯示才不會變成攻擊入口。

這課的路線：
  1. 為什麼改一個折扣要找四個地方：依類型分資料夾怎麼讓規則散開、讓依賴失控；改成依功能分資料夾，換到什麼、付出什麼（開場兩張單的最小答案）。
  2. 誰可以 import 誰：依賴方向、每個功能的公開介面 index.ts、循環依賴，以及怎麼用 lint 和測試在 CI 擋下違規，讓共用按鈕不再綁住外送。
  3. 會員折扣寫在哪裡：元件分三層，業務規則寫成一個純函式，改 95 折只改一處。
  4. 部署到不同環境：VITE_ 變數為什麼等於公開，漏設時怎麼在啟動時就發現；後台填的連結和公告怎麼處理 v-html 與使用者提供的網址。
  5. 半年後有人問「這條規則為什麼存在」：用 ADR 把決策和理由留下來。
這課會用到：
  • TS 課第 25 課的模組：每個檔案是一個模組，用 export 公開、用 import 取用別的檔案公開的東西。
  • 第 16 課的 API 層：所有後端呼叫都經過同一個模組，網址、錯誤分類、逾時、token 集中在那裡處理。

為什麼改一個折扣要找四個地方？

先看這個專案現在的樣子。它跟多數 Vue 專案一樣，一開始依「檔案的類型」分資料夾：create-vue 產生的專案就有 components/、stores/、views/，後來大家照同樣的習慣加了 api/、composables/、utils/。一年後長這樣：

src/
  components/   MenuList.vue  CartBadge.vue  LoginForm.vue  OrderRow.vue …（40 個）
  stores/       cart.ts  session.ts  orders.ts
  api/          menu.ts  orders.ts  auth.ts
  composables/  useMenu.ts  useCheckout.ts
  utils/        price.ts  date.ts  format.ts

三個頁面的時候，這種分法很好找：要元件就去 components/，要 store 就去 stores/。但這種資料夾回答的是「這是什麼類型的檔案」，而你接到需求時問的是「結帳功能的東西在哪裡」。兩個問題的答案不同，專案一大就出現三個問題，開場的兩張單都是從這裡來的：

  • 改一個功能要跨很多資料夾：改「結帳」要動 components、stores、api、composables、utils 五個地方，每個資料夾裡又混著其他功能的檔案。會員折扣散成四份就是這樣發生的：寫購物車頁的人沒找到結帳頁那份計算，就自己在元件裡再寫一份。
  • 不知道誰用了誰：components/ 裡的任何檔案都可以 import 任何 store，沒有東西阻止。共用按鈕 import 外送的 store 就是這樣混進來的；想刪掉 orders.ts，也要搜尋整個專案才知道會不會壞。
  • utils 變成垃圾桶：不知道放哪裡的東西都丟進去，最後 utils/format.ts 裡同時有價格格式、訂單狀態文字和折扣規則。

三個問題的共同原因，是資料夾沒有表達模組邊界。TS 課第 25 課說過，每個檔案是一個模組；把好幾個檔案當成一組，這一組也可以看成一個模組，例如「購物車」。模組邊界（module boundary）就是畫在這一組外面的那條線：線內的檔案可以互相自由使用；線外的程式只能用這一組刻意公開的東西，其他都碰不到。

邊界的價值在於它限制了「改一個東西會影響到哪裡」。有邊界時，你改購物車內部的檔案，只要公開的東西沒變，就能確定外面不會壞；刪掉一個功能，壞掉的地方也只會是那些用到它公開介面的程式。沒有邊界時，任何檔案都可能被任何地方依賴，改任何東西之前都得搜尋整個專案，刪功能只能靠編譯器一個一個報錯。現在的資料夾分法畫不出任何邊界，所以第一步是換一種分法，讓資料夾本身就是邊界。

把同一個功能的檔案放在一起：依功能分資料夾

要讓資料夾變成邊界，分類的依據要從「檔案的類型」改成「檔案屬於哪個功能」（feature）：同一個功能的元件、store（第 15 課）、composable（第 12 課）放進同一個資料夾。咖啡店可以分成這樣：

src/
  app/              最上層：建立 app、router、安裝外掛、提供全域依賴（main.ts、App.vue）
  pages/            頁面：接路由、組合 feature（MenuPage.vue、CheckoutPage.vue）
  features/
    menu/           菜單：MenuList.vue、index.ts
    cart/           購物車：cart-store.ts、CartBadge.vue、index.ts
    orders/         訂單
    auth/           登入狀態、權限
    delivery/       外送（已停用，準備刪除）
  shared/
    ui/             設計系統：BaseButton.vue、BaseDialog.vue（沒有業務邏輯）
    api/            API client：唯一呼叫 fetch 的地方
    lib/            通用小工具：formatPrice、日期格式

features/ 底下每個資料夾是一個業務功能，也就是一個模組邊界。pages/ 和 app/ 在它上面，負責把功能組起來；shared/ 在它下面，放的是跟任何業務都無關、每個功能都可能用到的東西。

shared/ui 放的是設計系統。設計系統（design system）是一組共用的 UI 元件與規範，例如按鈕、對話框、表單欄位的樣式與行為。它只管「長什麼樣子、怎麼互動」，不知道什麼是購物車、什麼是會員。開場那顆共用按鈕就屬於這裡，而它去 import 外送的 store，正好違反了這個定義：一顆設計系統的按鈕知道了「外送」這個業務名詞。

換成這種分法的好處：改購物車只看 features/cart/；停用外送功能時刪掉 features/delivery/，編譯器會告訴你哪些地方還在用它，而那些地方應該都在 pages 或 app 這種負責組裝的上層。代價：每個新檔案都要先決定「它屬於哪個功能」，新人第一次看會多一層要理解。

依類型分依功能分
適合小專案（十幾個元件）、原型、一個人維護多個功能、多人同時開發、會持續長大
改一個功能跨好幾個資料夾大部分在同一個資料夾
刪除一個功能要搜尋整個專案刪資料夾，看哪裡編譯錯
主要風險utils 變成垃圾桶、誰都能 import 誰功能切太細、feature 之間互相深入對方內部

不用一開始就分到最細。專案還小時用依類型分，等到「改一個功能要跨三個以上資料夾」成為日常，再搬成依功能分。咖啡店的點餐系統三十個頁面、好幾個人同時開發，已經過了這條線。

回到開場的兩張單，最小答案是：會員折扣這類業務規則只寫成一個函式，四個元件都呼叫它，改折扣只改一處；共用的按鈕放進 shared/，規定它不能 import 任何 feature，刪掉外送功能就不會拖垮它。兩件事的細節分別在下一節和〈會員折扣該寫在哪裡？〉那一節。

但光把檔案搬進資料夾，還擋不住共用按鈕去 import 外送的 store：import 只看路徑，路徑寫得出來，編譯器就接受。要讓資料夾真的成為邊界，還得規定誰可以 import 誰。

誰可以 import 誰？依賴方向與公開介面

先把「依賴」講清楚。A 檔案 import 了 B 檔案，就說 A 依賴 B：B 一改名、改參數或被刪掉，A 就會壞；B 則完全不需要知道 A 存在。依賴方向（dependency direction）就是規定這些箭頭只能往哪個方向指。

規則是只往更穩定、更底層的方向依賴。「底層」指被越多地方使用的程式：shared/ui 的按鈕被三十個頁面用，它一改就影響三十個頁面，所以它應該很少改、很穩定。如果它反過來依賴上層的程式，上層一改，底層就跟著壞，而底層一壞，所有用到它的地方都壞。開場刪掉外送就讓整個 app 編譯失敗，正是因為箭頭從最底層的按鈕指向了一個隨時可能被刪掉的業務功能。咖啡店的四層由上到下是 app → pages → features → shared，箭頭只能往下：

落到程式碼上是三條規則，每一條都對應一個實際會出的問題：

  • shared 不能 import features、pages、app。共用的按鈕不能知道「有沒有登入」「有沒有外送」，要停用就由使用它的 feature 傳 disabled 進來。按鈕只依賴自己的 props，刪掉任何 feature 都影響不到它。
  • feature 之間只能 import 對方的 index.ts。index.ts 是這個 feature 的公開介面（public API）：刻意提供給外部使用的函式與元件。其他檔案都是內部實作，可以自由改名、拆檔、重寫，只要 index.ts 公開的東西不變，外面就不受影響。
  • 只有 shared/api 呼叫 fetch。網址、錯誤分類、逾時、token 都在第 16 課的 API 層處理；這裡的 client 是 API 層建立的物件，例如有 getMenu() 方法的菜單 API。它由 app 層的 createRootApp 建立後用 app.provide 放進整個 app，元件再用第 13 課的 inject 取用。測試時傳一個假 client 給 createRootApp，元件拿到的就是假的，完全不知道 fetch 存在。如果 MenuList 自己呼叫 fetch，這些處理就要在元件裡再寫一份，測試時也沒辦法換掉。

公開介面在程式碼裡長這樣。cart 的 index.ts 只公開 store 和徽章，menu 要用購物車就只能從這裡拿：

// features/cart/index.ts：cart 對外只公開這兩個
export { useCartStore } from './cart-store.ts'
export { default as CartBadge } from './CartBadge.vue'

// features/menu/MenuList.vue
import { useCartStore } from '../cart/index.ts'        // ✓ 經過公開介面
import { useCartStore } from '../cart/cart-store.ts'   // ✗ 深層 import：cart 一重構就壞

第二種寫法今天能動，問題在以後。負責購物車的同事哪天把 cart-store.ts 拆成兩個檔案，他檢查自己的 index.ts 公開的東西沒變，合理地認為外面不受影響，結果 menu 壞了。公開介面要能發揮作用，前提是外面沒有人繞過它。

方向規則管的是「往上」的箭頭，還有一種違規是箭頭繞成一圈：循環依賴（circular dependency），也就是 A import B、B 又 import A，或繞好幾個檔案再回到 A。ES 模組允許循環，但載入時其中一邊會先執行，另一邊拿到的匯出可能還沒初始化，出現「Cannot access 'X' before initialization」這類只在某些載入順序才發生的錯誤。更大的問題是兩個模組變成一體：改一邊一定要看另一邊，也無法單獨刪除，邊界等於不存在。常見的修法是把兩邊都需要的東西往下搬：購物車徽章要顯示金額，就去 import 菜單的 formatPrice，菜單又 import 購物車，圈就形成了。formatPrice 跟菜單、購物車都無關，放進 shared/lib，兩邊都依賴它，彼此就不用互相依賴。

規則到這裡定好了，但它現在只存在這一頁和你的腦中。下一個趕著上線的同事寫下 import … from '../cart/cart-store.ts' 時，沒有任何東西會阻止他。

規則寫在文件裡沒人會記得，怎麼讓 CI 擋下違規？

寫在文件裡的規則，三個月後一定有人違反，因為違反的那一刻沒有任何東西會提醒他。所以規則要能自動檢查，並且放進 CI。CI 是每次有人推送程式碼或開 PR 時，自動執行建置、測試等檢查的流程，任何一項失敗，PR 上就會標成失敗；團隊通常會在 GitHub 這類平台把這些檢查設成必須通過，失敗的 PR 就不能合併。邊界規則變成 CI 裡的一項檢查之後，違規的 import 在合併前就會被擋下，錯誤訊息還會直接告訴寫的人規則是什麼、該怎麼改。

最常用的檢查工具是 lint。lint 工具（linter）不執行程式，只讀原始碼，找出有問題的寫法，例如 ESLint（加上 eslint-plugin-vue 才看得懂 .vue）或 oxlint。ESLint 內建的 no-restricted-imports 規則可以禁止某些路徑：

// eslint.config.js（片段）：shared 底下的檔案不能 import features
{
  files: ['src/shared/**'],
  rules: {
    'no-restricted-imports': ['error', {
      patterns: [{ group: ['**/features/**'], message: 'shared 不能依賴 features，改成參數或 props' }],
    }],
  },
}

files 指定這段設定只套用在 src/shared 底下的檔案；patterns 列出禁止的 import 路徑；message 是違規時顯示的訊息。開場那顆按鈕如果當初有這條規則，import 外送 store 的那一行在送出 PR 時就會被擋下。

這種規則一條一條寫，涵蓋不到「feature 之間只能經過 index.ts」和循環依賴這類需要看整張依賴圖的檢查，社群有專門的外掛處理。練習 1 的隱藏測試用另一種方式：用 fs 讀出每個檔案的 import，畫成依賴圖，再逐條檢查。原理一樣，只是用測試寫，你可以直接讀它在檢查什麼。

靜態檢查只看字串，擋不住刻意繞過的寫法，例如把 fetch 寫成 globalThis['fe' + 'tch']。所以練習 1 另有行為測試：把全域的 fetch 換成一呼叫就丟錯的假函式，資料只能從注入的 client 拿到。規則檢查和行為測試要一起用。
💡 實務上：架構調整是一點一點搬，不是一次重寫
接手一個已經糾纏的專案時，很少有機會停下來花兩週全部重排，咖啡店這個專案也一樣。常見做法是先加上邊界檢查但只對新資料夾生效，之後每次改到某個功能，就順手把它搬進 features/，舊程式碼慢慢收斂。大搬家的 PR 要跟功能修改分開送，否則 reviewer 在幾百個「檔案移動」裡找不到真正的邏輯變更，也很難單獨 revert（還原）。資深工程師在動手前會先問：這次調整解決的是哪個實際痛點，例如這次刪外送整個 app 壞掉，而不是「別人的專案長這樣」。

到這裡，第二張單已經解決，而且有檢查保護：共用按鈕不再依賴外送，刪掉 features/delivery/ 也拖垮不了它。第一張單還沒有：會員折扣的四份計算，搬進 feature 資料夾之後仍然是四份。

會員折扣該寫在哪裡？元件分層與業務規則

四份計算會出現，是因為折扣寫在元件裡：每個要顯示金額的元件，各自在 computed 裡算一次。要讓規則只剩一份，先要分清楚每種元件該負責什麼。資料夾有 pages、features、shared 三層，元件也對應三層：

層做什麼不做什麼咖啡店例子
頁面元件（pages）接路由參數、組合 feature 元件不寫業務規則MenuPage 放上 MenuList 和 CartBadge
feature 元件業務：呼叫 store、API，決定能不能按不管按鈕長什麼樣子MenuList 判斷「登入後才能加入」
UI 元件（shared/ui）外觀與互動：按鈕、對話框、欄位不知道任何業務名詞BaseButton 只接收 disabled

表裡「不做什麼」那一欄比「做什麼」重要：每一層只要做了不屬於自己的事，就會在某一天變成開場那樣的問題。不過這張表還沒回答折扣該放哪裡。折扣是業務規則，也就是店裡的生意規則：折扣怎麼算、運費怎麼收、什麼情況可以下單。它不屬於任何一個畫面，購物車頁、結帳頁、訂單明細都要用同一套。

所以業務規則不寫在任何元件裡，而是寫成純函式（pure function）：只依賴傳進來的參數，不讀也不改外部狀態（store、全域變數、目前時間），同樣的輸入永遠得到同樣的輸出。元件只負責把資料傳進去、把結果顯示出來。這樣有兩個好處：規則可以不掛載元件就測試；需要時也能搬到後端（Node）共用同一份，讓前端顯示的金額和後端實際收的金額一致。

同樣的規則寫在元件的 computed 裡也能動，但要測「會員外送 290 元收不收運費」就得掛載元件、準備 store；而且結帳頁和購物車頁各寫一份，改規則時一定會漏一份。quote() 放在購物車 feature 裡，從它的 index.ts 公開，結帳頁和購物車頁都呼叫它。第一張單的答案因此只有一行：把 0.1 改成 0.05，所有頁面同時生效。

程式碼的結構整理好了，接下來要把它部署出去。測試環境和正式環境的 API 網址不同，這個值不能寫死在程式裡。

測試環境和正式環境的 API 網址不同，設定要放哪裡？

同一份程式要在三個地方執行：你電腦上的開發環境、給 QA 驗收的測試環境（staging）、顧客使用的正式環境。三個地方的 API 網址都不同，開發時是 http://localhost:3000，正式環境是 https://api.coffee.example。如果網址寫死在 shared/api 裡，每換一個環境就要改一次程式碼。這類「程式碼相同、但每個環境不同」的值，交給環境變數（environment variable）處理：它是部署時才決定的設定值，由執行或建置程式的環境提供，程式碼只寫「去讀哪個名字」。

Vite 的做法（以下依 Vite 8 官方文件「Env Variables and Modes」）是把設定寫在專案根目錄的 .env 檔，前端程式用 import.meta.env 讀取。開發時讀 .env.development、正式建置時讀 .env.production 這類依環境分開的檔案，完整的載入順序見課末。讀進前端時有兩條規則：

  • 只有 VITE_ 開頭的變數會出現在前端程式的 import.meta.env 裡，其他的（例如 DB_PASSWORD）不會。這個前綴的用途就是防止不小心把變數送進前端。
  • 建置時，import.meta.env.VITE_API_BASE_URL 會被直接替換成字串，寫進打包出來的 JS。值一律是字串，'false' 也是字串。

所以把設定交給 VITE_ 變數，第一個要小心的是外洩。第二條規則的結果：放進 VITE_ 變數的值就等於公開。前端程式最後是一包送到每個使用者瀏覽器的 JS 檔，任何人打開瀏覽器的開發者工具，在 JS 檔裡搜尋就看得到這個字串。.env 沒有進 git 也不代表它是私密的：git 只管原始碼倉庫，而它的內容在建置時已經被複製進前端程式。付款密鑰、資料庫密碼這類值只能放在後端，前端需要時呼叫後端的 API。

# .env.production
VITE_API_BASE_URL=https://api.coffee.example
VITE_FEATURE_FLAGS=newMenu,darkMode
VITE_PAYMENT_SECRET=sk_live_…   # ✗ 會被打包進前端，任何人都看得到

第二個要小心的是漏設。CI 建置正式環境時如果忘了設 VITE_API_BASE_URL，import.meta.env.VITE_API_BASE_URL 就是 undefined，app 照樣啟動，請求打到 undefined/menu，使用者只看到「載入失敗」，你要花很久才查到原因。錯誤發生的地方（設定）和顯現的地方（菜單載入）離得太遠。

做法是啟動時驗證設定：在 main.ts 最前面把 import.meta.env 交給一個驗證函式，缺少或格式不對就立刻丟錯，並且一次列出所有問題，不要修好一個才看到下一個。這跟 TS 課第 26 課驗證 API 回應是同一件事：環境變數也是外部資料，程式不能假設它一定對。

// app/main.ts
const config = loadConfig(import.meta.env)   // 有問題就丟 ConfigError，列出所有問題
createRootApp(createHttpMenuApi(config.apiBaseUrl)).mount('#app')

驗證網址時有一個容易寫錯的地方：不要比對字串開頭。'http://localhost.evil.com'.startsWith('http://localhost') 是 true，但它的主機是 localhost.evil.com；http://localhost@evil.com 的 localhost 其實是帳號，主機是 evil.com。網址有自己的結構（協定、帳號、主機、port、路徑），字串比對看不出結構，要用 new URL() 解析後檢查 protocol 和 hostname。執行後比較每行的 hostname 和最後的 startsWith 結果：

三行的 startsWith 都是 true，但只有第一行的 hostname 真的是 localhost。練習 2 的 loadConfig 就要用這種方式判斷。另外，讓 import.meta.env 有型別的寫法見課末；型別只在編譯時有用，執行時的值仍然可能缺少，所以驗證函式還是要寫。

💡 實務上：VITE_ 變數是建置時決定的，每個環境要各自建置
咖啡店的測試環境和正式環境 API 網址不同。因為 VITE_ 的值在建置時就寫死在 JS 裡，staging 驗過的那包檔案不能直接搬到正式環境，否則會打到 staging 的 API；CI 要用各自的 mode 分別建置（例如 vite build --mode staging），或改成啟動時從伺服器讀一份設定檔。上線前常見的檢查：CI 有沒有設好每個環境的變數、.env.example 有沒有列出所有必要變數讓新同事照著填。遇到「這個值要不要放前端」的問題，判斷標準很簡單：可以讓任何使用者看到的才放，否則請後端提供 API。

new URL() 檢查網址這件事，下一節還會用到。設定只有部署的人能改，但門市在後台填的連結，任何能登入後台的人都能改。

門市在後台填的連結和公告，怎麼不變成攻擊入口？

點餐 app 有一頁顯示各門市的資訊，其中的外部連結和公告是門市在後台自己填的。這些內容不是你寫的程式，而是使用者提供的資料，你無法保證裡面是什麼。最需要防的是跨站腳本攻擊。跨站腳本攻擊（XSS，cross-site scripting）是攻擊者把一段會執行的程式塞進你的頁面，讓它在其他使用者的瀏覽器裡、以你網站的身分執行，可以讀取頁面上的資料、用使用者的身分送出請求。

第 7 課看過：{{ }} 插值和屬性綁定的值會被跳脫，使用者輸入的 <script> 只會顯示成文字。所以大部分情況下 Vue 已經替你擋住了。Vue 官方的安全指南列出幾個 Vue 保護不到的地方，門市資訊頁正好會碰到前兩個：

  • v-html：把字串當 HTML 插入，等於讓使用者寫你的頁面。使用者的評論、暱稱一律用 {{ }}。門市公告真的需要粗體、連結這類格式時，先用 sanitize（消毒）函式庫處理，例如 DOMPurify，把危險的標籤與屬性移除，再交給 v-html。
  • 使用者提供的網址：:href 綁定會跳脫引號，但不會檢查網址的內容。javascript:… 一被點就執行。用 new URL() 解析後只允許 http:、https:（白名單）。不要用黑名單擋 javascript:：瀏覽器解析網址時會去掉中間的 tab 與換行，java script: 也是 javascript:，還有 data: 等其他協定。官方指南也提醒：這類檢查應該在後端存進資料庫前就做，前端的檢查是第二道防線。
  • 不要把使用者的內容當成範本：createApp({ template: '<div>' + userInput + '</div>' }) 會把輸入編譯成 JS 執行。

門市連結是外部網站，還要再加上 target="_blank" rel="noopener noreferrer"：noopener 讓新分頁拿不到 window.opener，不能把你的頁面導去別處；noreferrer 不送出來源網址。

這些規則跟前面的依賴方向一樣，要變成習慣，不能靠記憶：eslint-plugin-vue 的 vue/no-v-html 會回報每一個 v-html；外部連結統一用一個 StoreLink 這樣的元件，網址檢查只寫一次，所有地方都經過它，這正是練習 3 要做的；code review 清單列上「新增套件要說明理由」。Vue 程式以外還有兩道防線：伺服器設定的 CSP，以及對 npm 套件的管理，細節見課末。

💡 實務上：最常出事的是後台與 CMS 內容
使用者評論多半會用 {{ }}，真正容易漏的是門市公告、商品描述這類由後台或 CMS（內容管理系統，讓非工程師編輯網站內容的後台）填的內容：大家覺得是自己人寫的就直接 v-html，但後台帳號被盜或內容是從外部匯入時，這就是注入點。code review 看到 v-html、:href 綁定使用者資料、新增套件時，資深工程師會停下來問「資料從哪裡來、誰能改它」。被資安檢測（滲透測試）回報 XSS 時，修法通常不是改一個地方，而是把 sanitize 或網址檢查集中到一個元件，讓所有地方都經過它。

半年後有人問「這條規則為什麼存在」，答案在哪裡？

這課替咖啡店的專案訂了好幾條限制：shared 不能 import features、feature 之間只經過 index.ts、只有 shared/api 呼叫 fetch。每一條都讓寫程式多一道手續。半年後新同事問「為什麼 shared 不能 import features？很麻煩」，如果答案只在某人的腦袋裡，那個人又離職了，規則很快就會被當成多餘的東西拿掉，開場的問題就會再發生一次。

答案要寫下來，放在程式碼旁邊。ADR（架構決策紀錄，architecture decision record）就是做這件事的短文件：一個重要的技術決策寫一份，放在專案的 docs/adr/，跟程式碼一起進 git。咖啡店這次的整理可以寫成這樣：

# ADR 0007：前端依功能分資料夾，並限制依賴方向

狀態：採用（2026-10）
背景：專案有 30 個頁面、4 人同時開發；改結帳要動 5 個資料夾；
      上個月刪外送功能時，共用按鈕 import 了外送 store，整個 app 編譯失敗。
考慮過的選項：
  1. 維持依類型分，只靠 code review
  2. 依功能分，加上依賴規則與自動檢查
決定：選 2。規則：app → pages → features → shared；feature 之間只經過 index.ts；
      只有 shared/api 呼叫 fetch。CI 執行邊界檢查。
後果：新檔案要先決定屬於哪個 feature；跨 feature 的需求要先在 index.ts 公開。

最有價值的是「背景」和「考慮過的選項」。規則本身在程式碼和 lint 設定裡都看得到，看不到的是當初為什麼這樣選、放棄了什麼。之後情況改變（例如團隊縮成一個人），讀的人看得出當初的理由還成不成立，可以有根據地修改或推翻它，而不是憑感覺。「後果」則誠實寫下代價：架構規則本身也是取捨，規則越多，寫新功能越慢。只有一個人維護的小後台，全套規則可能是負擔。技術債的取捨在系統設計課第 18 課和第 20 課會從整個系統的角度再談。

補充與查表

主線用不到、但設定專案或做決定時會查的細節。

Vite 的 .env 檔載入順序

依 Vite 8 官方文件「Env Variables and Modes」：從專案根目錄的 .env 檔讀取，載入順序 .env → .env.local → .env.[mode] → .env.[mode].local，越後面越優先；執行 Vite 時終端機裡已經存在的環境變數優先權最高。.local 結尾的檔案應該加進 .gitignore。

讓 import.meta.env 有型別

Vite 文件的做法是在 src/vite-env.d.ts 再宣告一次 ImportMetaEnv 介面，靠 interface 的宣告合併加上 readonly VITE_API_BASE_URL: string（TS 課第 25 課的全域擴充）。型別只在編譯時有用，執行時的值仍然可能缺少，所以驗證函式還是要寫。

Vue 程式以外的兩道防線

  • CSP（內容安全政策，Content Security Policy）：伺服器用回應標頭告訴瀏覽器只能執行哪些來源的腳本，就算有人成功注入 <script>，瀏覽器也不執行。由後端或 Nginx 設定，auth 課第 7 課深入。
  • 供應鏈攻擊（supply chain attack）：攻擊者在你依賴的 npm 套件（或它依賴的套件）裡放惡意程式。每裝一個套件，就是把別人的程式碼放進使用者的瀏覽器。鎖住 lockfile（package-lock.json 進 git，CI 用 npm ci）、定期 npm audit、能用幾行解決的就不裝套件。

什麼時候值得抽出共用元件

常見的經驗是出現第三次再抽。第一次直接寫；第二次複製也沒關係；第三次才看得出哪些部分真的一樣、哪些只是剛好相似。太早抽出來的共用元件會長出一堆 if (mode === 'checkout') 的參數，變成誰都不敢改的東西。這跟業務規則不同：業務規則從第一次就該只有一份，因為兩份規則算出不同金額是錯誤，兩個長得相似的元件只是重複。

練習

在 learn/ 執行 node check.mjs vue 25。三題互相獨立。練習 1 的 src/ 是一個小專案：先打開 ex1.test.ts 看它怎麼畫依賴圖，再動手改。不要刪除或改名檔案（check.mjs 會把缺少的起始檔補回來），需要的目標檔案已經以空殼存在。

練習 1：work/25/src 糾纏在一起：MenuList 直接 import 購物車 store 的內部檔案、自己呼叫 fetch；shared/ui 的 BaseButton import auth 判斷有沒有登入；MenuPage 深層 import CartBadge；CartBadge 為了 formatPrice 去 import menu。依規則修改 import 與程式內容，讓這些檢查通過：依賴只往下、feature 外面只 import 對方的 index.ts、沒有循環依賴（改完 MenuList 之後會出現一個，想想 formatPrice 該放哪）、fetch 只在 shared/api、shared 裡沒有 store。功能要保持不變：測試用 createRootApp(假 API) 掛上整個 app，檢查菜單、未登入時「加入」停用、登入後加入兩杯拿鐵、徽章顯示「購物車 2 件 · 220 元」。每個檔案開頭的註解寫了它的問題。

練習 2：寫 config.ts 的 loadConfig(env)。VITE_API_BASE_URL 必填，用 new URL() 解析後必須是 https:，或是 http: 而且 hostname 是 localhost，回傳時去掉結尾的 /；VITE_FEATURE_FLAGS 選填，逗號分隔轉成 Set；名稱以 VITE_ 開頭又含 SECRET、PASSWORD、PRIVATE（不分大小寫）的變數要報錯。有問題就丟出 ConfigError，problems 一次列出所有問題，每一條都包含變數名稱。測試會試 http://localhost.evil.com、http://localhost@evil.com 和好幾個錯誤同時出現的情況。

練習 3：StoreLink.vue 顯示門市在後台填的外部連結（props：label、url）。只有 http: 與 https: 才渲染成 <a>，href 用 new URL(url).href，加上 target="_blank" 和 rel="noopener noreferrer"；其他（javascript:、data:、解析不了的字串）顯示成純文字「門市名稱（原始網址）」。不能用 v-html，props 改變時要重新判斷。測試會試大小寫、前面有空白、中間夾 tab 的 javascript:，以及含 HTML 的 label。

練習 4：同事在 .env.production 寫了 VITE_PAYMENT_SECRET=sk_live_…，並說「.env 有加進 .gitignore，不會外流」。實際會怎樣？

✓ VITE_ 開頭的變數會被靜態替換成字串、寫進前端程式，這就是它的用途。沒進 git 只保護原始碼倉庫，保護不了已經發給每個瀏覽器的 JS。正式建置也會讀 .env.production；Vite 不會檢查變數名稱，所以練習 2 自己寫了這個檢查。密鑰只能放在後端。

練習 5：從「依類型分資料夾」改成「依功能分資料夾」，最主要的好處是？

✓ 檔案數量和打包大小都不變，只是換位置；import 也一樣要寫。好處在邊界：改購物車只看 features/cart/，它的內部檔案外面不能直接用，所以可以放心重構；刪除一個功能就是刪一個資料夾，再看哪裡編譯失敗。代價是要先決定每個檔案屬於哪個功能。

練習 6：「會員 9 折、外送未滿 300 收 40 元運費」這個規則，購物車頁和結帳頁都要用。寫在哪裡最好？

✓ 純函式只依賴參數，不用掛載元件就能測各種邊界（剛好 300 元、會員外送），規則只有一份，之後也能搬到後端共用。複製兩份的話，改規則時遲早漏改一份，兩個頁面算出不同的金額。shared/ui 是設計系統，不能有業務規則。

常見錯誤

  • shared 或 utils 變成垃圾桶：不知道放哪就丟進 shared。只有「跟任何業務都無關」的東西才放 shared；帶業務名詞（購物車、會員）的，放回對應的 feature。
  • 深層 import 別的 feature 的內部檔案：import … from '../cart/cart-store.ts'。對方一重構就壞。需要什麼就請對方在 index.ts 公開。
  • 循環依賴：兩個 feature 互相 import。把共同需要的東西往下搬到 shared，或重新想清楚誰依賴誰。
  • 規則只寫在文件裡：沒有自動檢查的規則一定會被違反。寫成 lint 規則或測試，在 CI 擋下。
  • 業務規則寫在元件裡、每頁各一份：改規則時一定漏改一份，兩頁算出不同金額。寫成一個純函式，所有元件都呼叫它。
  • 過早抽出共用元件：只用過一次就抽，參數越長越多。出現第三次、看清楚共同點再抽。
  • 把密鑰放進 VITE_ 變數：它會被打包進前端。密鑰放後端，前端呼叫後端的 API。
  • 沒有驗證設定：漏設變數時 app 照樣啟動，錯誤在很遠的地方才出現。啟動時驗證，一次列出所有問題。
  • 用 startsWith 檢查網址：localhost.evil.com、localhost@evil.com、httpx: 都會通過。用 new URL() 解析後比對 protocol 和 hostname。
  • 用 v-html 顯示使用者內容：用 {{ }}；真的需要富文字就先 sanitize，並開啟 vue/no-v-html 讓每個例外都要說明理由。
  • 什麼套件都裝：每個套件都是要審查、會跟著上線的程式碼，也是供應鏈攻擊的入口。幾行能寫完的就自己寫。

小結

  • 改一個折扣要找四個地方、刪一個功能拖垮整個 app，原因是資料夾沒有畫出模組邊界。依類型分資料夾適合小專案；專案長大、多人開發時，依功能分，讓同一個功能的檔案在一起。
  • 依賴只往下：app → pages → features → shared。shared 不知道任何 feature；feature 之間只經過對方的 index.ts。
  • 公開介面讓內部可以自由重構；循環依賴的修法通常是把共同的東西往下搬。
  • 規則要在 CI 自動檢查（lint 或測試），並搭配行為測試，擋住繞過字串檢查的寫法。
  • 業務規則寫成純函式，只有一份；UI 元件不知道業務；只有 API 層呼叫 fetch。
  • 只有 VITE_ 變數會進前端，而且是建置時直接寫進 JS：絕不放密鑰，每個環境各自建置。啟動時驗證設定，一次列出所有問題；網址用 new URL() 解析後檢查。
  • 使用者提供的 HTML 不用 v-html，網址只允許 http／https，集中到一個元件處理；再加上 CSP 與謹慎的套件管理。
  • 用 ADR 記下重要決策的背景、選項與代價，讓規則在半年後仍然有人說得出理由。
