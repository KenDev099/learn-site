階段 5：狀態與資料 · 第 15 課

狀態放哪裡：從元件狀態到 Pinia

咖啡店的線上點餐，購物車要在三個地方出現：頁首的小徽章、菜單頁的「加入」按鈕、結帳頁的明細。客人在菜單頁按一下「加入」，頁首的數字和結帳頁的明細都要跟著變。同一頁上還有菜單篩選器的「只看咖啡」開關，它只有菜單頁用得到。

團隊裡常見兩種極端。有人把所有東西都塞進一個全域 store，結果開關、表單草稿、API 抓回來的菜單全混在一起，改一個地方要追十個檔案；也有人什麼都用 props 往下傳，購物車的數字要經過五層元件才到頁首徽章。

這課的任務是把這台購物車做好：先判斷它和其他狀態各該放在哪裡，再用 Pinia（Vue 官方的狀態管理套件）寫成一個 store，讓三個地方看到同一份資料、重新整理後還在、改程式時有測試保護。

這課的路線：
  1. 開關和購物車該放哪裡：每種狀態從最小的範圍開始放，什麼才需要全域 store（開場問題的最小答案）。
  2. 為什麼用 Pinia、怎麼寫購物車 store：模組層級的 ref 也能共用，Pinia 多給了什麼；setup store 的寫法與兩條規則；修改為什麼都要經過 action。
  3. 三個地方怎麼讀 store：頁首徽章解構 store 後為什麼不會動，storeToRefs 怎麼修。
  4. 重新整理後購物車還在：寫一個存到 localStorage 的外掛，讀回來的資料怎麼驗證。
  5. 怎麼確定它是對的：測 store 本身，以及測用到 store 的元件。
這課會用到：
  • 第 12 課的模組層級狀態：寫在檔案最外層的 ref，所有 import 它的地方共用同一份。
  • 第 13 課的 provide／inject 與 Vue 外掛：祖先元件或 app.use() 裝的外掛提供一個值，底下任何元件用 inject 拿到同一份。

「只看咖啡」開關和購物車，該放在同一個地方嗎？

先把名詞說清楚。狀態（state）是會隨時間改變、而且畫面要跟著它變的資料：開關是開還是關、購物車裡有幾杯拿鐵、菜單有哪些品項，都是狀態。

「狀態放哪裡」聽起來是一個問題，其實是在問兩件事。第一件是誰需要讀它：「只看咖啡」開關只有菜單頁的篩選器和商品列表要讀；購物車則是頁首、菜單頁、結帳頁都要讀，這三個地方在元件樹上離得很遠，也不一定同時出現在畫面上。第二件是它的正本在哪裡：客人按「送出訂單」之前，購物車只存在瀏覽器裡，前端手上那份就是正本；菜單的正本在後端的資料庫，前端拿到的只是某一刻抓回來的副本。

這兩件事各對應一個常用的名詞。整個 app 很多地方共用的狀態叫全域狀態（global state），購物車、目前登入的使用者都是。正本在伺服器、前端只拿到副本的狀態叫伺服器狀態（server state），菜單、訂單紀錄都是；副本會過期，店長可能剛在後台把可頌改成售完。

判斷的原則是從最小的範圍開始選，不夠用才往外擴。範圍越小，能改到它的程式就越少，出錯時要追的地方也越少。下表由小到大排列：

情境放哪裡咖啡店的例子
只有一個元件用元件內的 ref「只看咖啡」開關、彈窗是否打開
兄弟元件共用提升到共同的父元件，用 props 和事件（第 9 課）菜單頁的篩選器和商品列表共用的分類
一棵子樹共用的情境provide／inject（第 13 課）Tabs 和它底下的 Tab；某個區塊的目前門市
整個 app 共用、跨頁面Pinia store購物車、登入的使用者
要能分享、重新整理後還在的篩選條件網址（URL query，第 19 課）?category=coffee&sort=price
正本在伺服器伺服器狀態快取（第 17 課）菜單、訂單紀錄

照這張表，開場的兩個東西就有答案了。「只看咖啡」開關如果只有篩選器自己用，就放在篩選器元件裡；商品列表也要依它過濾時，提升到菜單頁這個共同的父元件，用 props 和事件傳下去。如果 PM 希望客人能把「只看咖啡」的連結傳給朋友，再改放網址。購物車要跨頁面、在元件樹上相距很遠的地方讀，才放進 Pinia store。用 props 一路往下傳購物車，中間每一層元件都得接一個自己用不到的 prop；provide／inject 只照顧一棵子樹，頁首和結帳頁不在同一棵子樹下時就搆不著。

表的最後一列常被忽略。菜單當然可以抓回來放進 store，但接著就要自己處理：什麼時候算過期、要不要重新抓、兩個元件同時要時是不是發了兩次請求、抓失敗時顯示什麼。這些是伺服器狀態快取的工作，第 17 課專門處理。放進 Pinia 的，主要是正本就在前端的狀態：客人還沒送出的購物車就是這種。

💡 實務上：新增狀態前先問「誰要讀、正本在哪、誰負責清掉」
接到「結帳頁要顯示優惠券」這類需求時，資深工程師會先決定狀態放哪，而不是直接開一個新 store。常見的取捨：表單草稿放元件內，離開頁面就消失通常剛好；如果 PM 要「切到別頁再回來還在」，才考慮往外放。放進全域的狀態要想好生命週期：使用者登出、切換門市時，購物車和使用者資料要不要清掉、由誰清？code review 看到新的 store 時，可以直接問「這個只有一頁用嗎？」，很多時候答案是「是」，留在元件裡就好。

購物車確定要全 app 共用了。不過第 12 課已經看過一種不用任何套件的共用方式，下一節先回答：為什麼不用它就好？

模組最外層的 ref 也能共用購物車，為什麼還要 Pinia？

第 12 課看過：把 ref 寫在檔案最外層、不放在任何函式裡，因為 ES module 在整個程式裡只執行一次，所有 import 它的地方拿到的都是同一個 ref。購物車寫成這樣，頁首、菜單頁、結帳頁確實會看到同一份：

// cart.ts：模組層級的購物車
import { ref } from 'vue'

export const items = ref<CartItem[]>([])

在單純的瀏覽器 app 裡這能用。問題出在「整個程式只有一份」，這在幾個情境會變成缺點。Pinia 的做法不同：store 不存在模組裡，而是存在 createPinia() 建立的 pinia 實例裡。pinia 實例是裝所有 store 的容器，用 app.use(pinia) 裝進 Vue app；建幾個 pinia，就有幾份互不相干的購物車。這一個差別帶來下面四件事。

伺服器端渲染時，購物車不會外洩給別的顧客。伺服器端渲染（SSR，server-side rendering）是在伺服器上先把頁面產生成 HTML，再送給瀏覽器。關鍵在於：同一個伺服器程序同時服務很多顧客，而模組在這個程序裡同樣只載入一次。模組層級的 ref 只有一份，A 顧客加進去的拿鐵，會出現在 B 顧客的頁面上。用 Pinia 時，SSR 為每個請求建立自己的 app 和 pinia，購物車各自一份。細節在第 24 課。

測試之間互相隔離。模組層級的 ref 在同一個測試檔裡也只有一份，上一個測試加的兩杯拿鐵會留到下一個測試，結果取決於測試的執行順序。用 Pinia 時，每個測試開頭 setActivePinia(createPinia()) 換一個新的 pinia，就是一台全新的購物車。

看得到誰在什麼時候改了什麼。Vue DevTools 是檢查 Vue 元件與狀態的瀏覽器開發者工具。它看得到每個 store 的 state、每一次修改和是哪個操作造成的，還可以回到之前的狀態。客人回報「購物車突然少一杯」，你在開發環境重現後，可以一步步看是哪個操作改的。

能用外掛幫 store 加功能。Pinia 外掛是一個函式，pinia 每建立一個 store 都會經過它，所以「存到 localStorage」這種功能寫一次就好。這課後面會自己寫一個。

代價是多一個套件和幾個新名詞。只有兩個兄弟元件共用的值，用 Pinia 是殺雞用牛刀，照上一節的表放在父元件就好。購物車要跨頁面、要測試、之後還要存檔，值得用 Pinia。接下來就把它寫出來。

怎麼用 Pinia 寫出購物車 store？

Pinia 裡，集中管理一塊狀態和操作它的函式的單位叫 store。購物車就是一個 store：它擁有購物車的資料，也提供「加入」「清空」這些操作。元件不用知道資料怎麼存，只要呼叫操作。

store 用 defineStore(id, …) 定義。id 是這個 store 在 pinia 裡的名字，devtools 顯示、外掛判斷是哪個 store、測試設定初始資料，都用它找 store。第二個參數有兩種寫法，這門課用 setup store：傳一個函式，寫法和元件的 setup() 一樣，裡面就是你熟悉的 Composition API。另一種寫法 option store，下一節講 $reset 時會用到。

// cart-store.ts
import { defineStore } from 'pinia'
import { computed, ref } from 'vue'

export const useCartStore = defineStore('cart', () => {
  // ref → state
  const items = ref<CartItem[]>([])

  // computed → getter
  const count = computed(() => items.value.reduce((sum, i) => sum + i.qty, 0))

  // function → action
  function clear() {
    items.value = []
  }

  return { items, count, clear }
})

setup 函式最後 return 的物件，決定 store 上有什麼。Pinia 依照每個值是什麼東西，把它歸成三類，各有一個名字：

setup 函式裡寫的在 store 上變成用途
ref()、reactive()state資料本身
computed()getter從 state 算出來的值（數量、小計）
functionaction修改 state 的操作，可以是 async

完整的購物車還有 subtotal（小計）getter，以及 add(product)、changeQty(id, qty) 兩個 action，寫法同上，練習 1 會完整寫出來；後面的 LATTE 代表一筆拿鐵商品 { id, name, price }。

這三個名字後面會一直用到：state 是資料本身；getter 是從 state 算出來、不用另外存的值，購物車的數量和小計都是；action 是修改 state 的操作，例如加入、清空。

元件呼叫 useCartStore() 就拿到購物車。這裡有兩個行為要知道。第一，useCartStore() 第一次被呼叫時，Pinia 才執行 setup 函式，之後同一個 pinia 裡每次呼叫都拿到同一個 store。所以頁首、菜單頁、結帳頁各自呼叫 useCartStore()，拿到的是同一台購物車，這正是開場要的。第二，store 本身是一個 reactive 物件，裡面的 ref 會自動解開：在 store 外面寫 cart.count，不是 cart.count.value。

store 能動了，三個地方也共用同一份。但 setup store 有兩條規則，違反時畫面看起來完全正常，問題要到別的地方才會冒出來。

畫面都正常，為什麼外掛存不到、購物車清不乾淨？

這兩條規則，Pinia 官方文件（v4）寫得很明白。

第一條：所有 state 都要放進 return。Pinia 不會去看 setup 函式裡宣告了哪些 ref，它只看回傳的物件，裡面的 ref 才算 state。假設購物車多了 orderType（內用或外帶），getter 和 action 都用到它，但你忘了 return。畫面會正常，因為 getter 和 action 透過閉包還是讀得到它。可是 Pinia 不知道它存在，store.$state（Pinia 整理出來、這個 store 的全部 state）裡就沒有它，所有依賴 $state 的功能都看不到它：devtools 看不到、外掛存不到、SSR 無法把伺服器的狀態帶到瀏覽器、測試的 initialState 也設不進去。也不要把 state 包成 readonly 再回傳，一樣會壞。

第二條：setup store 沒有內建的 $reset()。要了解原因，先看另一種寫法。option store 用一個物件定義 store：defineStore('cart', { state: () => ({…}), getters, actions })，state 由一個專門的函式產生。因為有這個函式，Pinia 要重設時再呼叫一次 state() 就拿到初始值，所以 option store 有內建的 $reset()。setup store 只有一個整體的 setup 函式，沒有這樣一個單獨產生初始 state 的函式，所以也沒有 $reset()。要重設，就自己寫一個叫 $reset 的 action，把每一個 state 設回初始值：

function $reset() {
  items.value = []
  orderType.value = 'here'   // 加了新的 state，這裡也要記得加
}

這個函式最容易出的錯是漏改：之後加了新的 state，$reset 沒跟著補，客人清空購物車後，內用／外帶還停在上一次的選擇。練習 1 要你自己寫這個 $reset()。

兩條規則守住了，store 本身沒問題。下一個問題是：誰可以改它？

二十個元件都能改購物車，「數量上限 20」要寫在哪裡？

修改 state 有三種方式：在 action 裡改、從元件直接寫 cart.items = []、或用 cart.$patch(…) 一次改好幾個欄位。三種都會觸發畫面更新，功能上都「能動」。

差別在可追蹤性。假設菜單頁、結帳頁、推薦區塊等二十個元件各自直接改 cart.items，「同一個商品數量上限 20」這條規則就得在二十個地方各寫一次，漏一個，客人就能點出 21 杯；出問題時你也不知道是誰改的。全部經過 add、changeQty 這幾個 action，規則只寫在 action 裡一次，devtools 也看得到每一次 action 呼叫。所以元件只呼叫 action，不直接改 state。這課後面的外掛和測試會用到 $patch，那是在元件以外、要一次設定好資料的地方。$patch 可以傳物件（cart.$patch({ orderType: 'togo' })），也可以傳一個函式，函式收到 state、在裡面直接改；改陣列這類要整個換掉或推入的情況，常用函式寫法。

💡 實務上：一個領域一個 store，不要一個大 store 包全部
真實專案常見的切法是按領域分：useCartStore、useUserStore、useCheckoutStore，每個檔案只管自己的 state 和 action。store 之間可以互相使用：在結帳 store 的 action 裡呼叫 useCartStore()，結帳成功後執行購物車的 $reset()；要避免的是兩個 store 在 setup 函式最外層就互相讀取對方的 state，這會形成循環。登出是最容易漏的地方：每個存了使用者資料的 store 都要被重設，通常集中在一個 logout() 裡依序呼叫各 store 的 $reset()，漏一個就會讓下一位使用者看到上一位的資料。

store 寫好、修改也集中了。接下來回到開場的三個地方，看元件怎麼讀它；第一個坑就在頁首徽章。

頁首徽章解構了 store，為什麼加了拿鐵數字卻不動？

第 4 課說過：把 reactive 物件解構，拿到的只是當下的值。前面提過 store 是 reactive 物件，所以這一行有問題：

const { count, subtotal, clear } = useCartStore()
// count、subtotal 只是數字，購物車之後再變，畫面也不會動

解構等於執行 const count = cart.count：從 reactive 物件讀出一個數字，存進一個普通變數。讀的那一刻是 0，之後購物車再變，這個變數不會知道，範本用的也是這個不會變的數字。

解法是 Pinia 提供的 storeToRefs：它把 store 的 state 和 getter 轉成一個個 ref，每個 ref 讀寫時都回到 store 上，所以解構之後仍然連著 store。action 是普通函式，不是會變的資料，沒有響應性的問題，直接從 store 解構。

<script setup lang="ts">
import { storeToRefs } from 'pinia'
import { useCartStore } from './cart-store.ts'

const cart = useCartStore()
const { count, subtotal } = storeToRefs(cart)   // state、getter
const { clear } = cart                          // action
</script>

<template>
  <p>共 {{ count }} 個，小計 {{ subtotal }} 元</p>
  <button type="button" @click="clear()">清空</button>
</template>

也可以完全不解構：直接在範本寫 cart.count，每次都透過 store 讀，一樣有響應性。要不要解構是寫法偏好，重點是不能把 state 或 getter 解構成普通變數。

為什麼 action 要分開一行？因為 storeToRefs 只挑 ref、reactive 和 computed，不包含 action。如果圖方便寫成 const { count, clear } = storeToRefs(cart)，clear 會是 undefined：頁面載入時不會報錯，客人按下「清空」才出錯。資料從 storeToRefs 拿，action 從 store 拿。

還有一件事跟「三個地方看到同一份」直接相關：pinia 從哪裡來。在元件裡呼叫 useCartStore() 不用傳參數，它會 inject 到 app.use(pinia) 裝的那一個 pinia。不要在元件裡 createPinia() 再傳進去，那是另一個 pinia、另一台空的購物車，頁首徽章就會和菜單頁各看各的。

三個地方現在看到同一份，也會跟著變了。但客人加了三杯拿鐵後按一下重新整理，購物車又空了。

重新整理購物車就空了：存檔的程式要寫在哪裡？

原因很單純：store 存在記憶體裡。重新整理時整個 JavaScript 程式重新執行，pinia 和裡面的 store 都重新建立。要讓購物車撐過重新整理，就要存到瀏覽器會保留的地方。最常用的是 localStorage：瀏覽器提供的鍵值儲存，只能存字串，關掉分頁、重開瀏覽器都還在。做法是購物車每次變動就寫進去，下次開頁面時讀回來。

這段程式可以直接寫在購物車 store 裡，但它跟購物車的業務規則無關：「同一商品數量上限 20」是購物車的事，「存到哪、用什麼格式存」是儲存的事。混在一起，測購物車規則時就得一起處理 storage；哪天使用者的 store 也要存，又得再寫一遍。所以這件事適合寫成 Pinia 外掛（plugin）。

Pinia 外掛就是一個函式。用 pinia.use(plugin) 註冊之後，pinia 每建立一個 store 就呼叫它一次，傳入 { store, pinia, app, options }，外掛可以讀寫這個 store、監聽它的變化。因為每個 store 都會經過外掛，外掛裡要先判斷是不是自己要處理的那一個，例如比對 store.$id，也就是 defineStore 的 id。

註冊有一個時間點要注意：外掛只在 pinia 裝進 app 之後生效。pinia.use() 在 app.use(pinia) 之前呼叫時，Pinia 會先記著，等裝進 app 才套用。正常的 main.ts 照「建 pinia → 註冊外掛 → 裝進 app」的順序寫不會有問題；但測試裡沒有 app，要自己 createApp({}).use(pinia)，外掛才會跑。

外掛的骨架有了。接下來的問題是：要存什麼、存成什麼樣子，讀回來的東西能不能直接用？

存進去的是什麼，讀回來的能信嗎？

localStorage 只能存字串，所以存之前要先序列化（serialization）：把物件轉成字串，通常用 JSON.stringify；讀回來再用 JSON.parse 轉回物件。JSON 只認得純資料，store 卻不只有資料。下面的範例模擬一個帶著函式、getter、Date 的 store，執行後看兩件事：印出的 JSON 字串裡少了什麼，以及三段壞資料讀回來各是什麼結果。

從結果可以看到，對照輸出由上到下：

  • 函式不見了：JSON 字串裡沒有 add，讀回來也沒有。
  • getter 被存成當下的數字：count 變成固定的 2，之後不會再跟著算。
  • Date 變成字串，讀回來不會自動變回 Date。
  • 三段讀回的字串：第一段不是完整的 JSON，解析直接丟錯；第二段解析成功，但整個值是 null，所以輸出的 items 是 undefined；第三段看起來像樣，items 卻是 null。

這帶出兩個結論。存的時候，只存 state 裡真正需要的欄位：購物車只存 items，數量和小計每次都能從 items 重新算出來，不用存。讀的時候，要像對待 API 回應一樣驗證（TS 課第 26 課）：storage 裡的東西是外部資料，可能是壞掉的 JSON、舊版程式存的格式，或被使用者在 DevTools 裡改過。驗證失敗就刪掉、從空車開始，不能讓整個 app 因為一筆壞資料開不起來。

還有一種「舊格式」是你自己造成的：哪天明細多了「甜度」欄位，舊使用者電腦裡存的還是沒有甜度的舊資料。所以存的時候加上版本號，存成 { version: 1, items }；格式改了就把版本改成 2。讀回來一看版本不對，就丟掉或轉換成新格式，不會把舊資料當成新格式讀進來。

把這些放進外掛：

export function persistPlugin({ storage, key }: Options): PiniaPlugin {
  return ({ store }) => {
    if (store.$id !== 'cart') return        // 只處理購物車
    const items = load(storage, key)        // 讀＋驗證，不合法就 removeItem 並回傳 null
    if (items) store.$patch(state => { state.items = items })
    store.$subscribe((mutation, state) => {
      storage.setItem(key, JSON.stringify({ version: 1, items: state.items }))
    })
  }
}

const pinia = createPinia()
pinia.use(persistPlugin({ storage: localStorage, key: 'cart' }))
app.use(pinia)

這段程式做三件事：只處理 id 是 'cart' 的 store；建立時用 load 讀回並驗證，合法才用 $patch 寫進 store；之後用 $subscribe 在每次變動時寫回 storage。

store.$subscribe(callback) 的意思是：這個 store 的 state 每次改變就呼叫 callback，參數是這次修改的資訊和新的 state。它底層是 watch，所以跟 watch 一樣，預設不是同步的：直接改 state 之後，callback 要等到下一個 microtask 才執行，也就是第 6 課講的「等這一輪排程的工作做完」。測試裡改完 state，要先 await nextTick() 才看得到 storage 被寫入。需要每次修改都立刻通知時，傳 { flush: 'sync' }，代價是連續改十次就寫十次。

注意 storage 沒有寫死成 localStorage，而是從參數傳入。這樣測試可以給一個用 Map 做的假 storage，直接檢查寫了什麼、刪了什麼，不必碰真的瀏覽器儲存。

localStorage 是明文存在使用者電腦上的，同網站的任何 JavaScript 都讀得到（遇到 XSS 就會被偷走，第 7 課）。不要把 access token、手機、地址這類敏感資料放進持久化的 store。購物車的商品和數量可以；token 放哪裡在第 16 課和 auth 課第 7 課討論。
💡 實務上：持久化先找現成外掛，但格式變更要自己負責
工作中通常不會自己寫持久化外掛，而是用社群維護的套件；選之前確認它支援你用的 Pinia 版本，並看它怎麼處理讀回失敗。不管用哪個，上線後才改存的格式，舊使用者電腦裡的舊資料都還在，版本號和驗證仍然是你的責任。另一個常被問到的情境：客人開了兩個分頁，在 A 分頁加了商品，B 分頁的購物車不會自動更新；需不需要同步（例如監聽 storage 事件：別的分頁改了 localStorage 時，瀏覽器會在其他分頁觸發它）要和 PM 確認，多數購物車在結帳時以伺服器重新計算的金額為準就夠了。

購物車的規則、元件的讀法、外掛都寫好了。最後一個問題是：怎麼確定它們真的對，而且下次有人改程式時不會悄悄壞掉？

怎麼確定購物車的規則是對的？先測 store 本身

先測最核心的部分：購物車的 state、getter、action。這不需要掛載任何元件，因為 store 不依賴畫面。唯一要準備的是 pinia：useCartStore() 要知道用哪一個 pinia，在元件裡它靠 inject 找到，測試裡沒有 app 可以 inject，所以用 setActivePinia() 指定一個「目前使用中」的 pinia。

import { beforeEach, expect, test } from 'vitest'
import { createPinia, setActivePinia } from 'pinia'

beforeEach(() => setActivePinia(createPinia()))

test('加兩杯拿鐵', () => {
  const cart = useCartStore()
  cart.add(LATTE)
  cart.add(LATTE)
  expect(cart.count).toBe(2)
})

beforeEach 讓每個測試開始前都換一個新的 pinia，這就是前面說的測試隔離：上一個測試加的拿鐵不會留到這一個。store 的規則這樣測就夠了，但頁首徽章、結帳明細這些元件還沒測到，而元件測試要關心的是另一件事。

測頁首徽章這類元件：不想真的執行 action 怎麼辦？

元件測試關心的是：畫面顯示的數字對不對、按下按鈕有沒有呼叫對的 action。action 裡的邏輯已經在上一節驗證過，元件測試不需要再跑一次；如果 action 會打 API，元件測試真的執行它反而麻煩。

這時用的是 spy：一個假的函式，被呼叫時什麼都不做，但會記錄自己被呼叫了幾次、收到什麼參數，測試事後可以查。Vitest 的 vi.fn() 產生的就是 spy。

@pinia/testing 的 createTestingPinia 是專門給元件測試用的 pinia，它做三件事：

  • 用 initialState 直接設定 store 的初始 state，key 是 store 的 id，例如 { cart: { items: [LATTE] } }。不必先呼叫好幾次 action 才湊出想要的購物車。
  • 把所有 action 換成 spy：元件呼叫了哪個 action、呼叫幾次都查得到，但 action 本身不執行。
  • getter 在測試裡可以直接指定值。

元件測試只關心「畫面對不對、有沒有呼叫對的 action」，action 的邏輯留給 store 的測試。

import { createTestingPinia } from '@pinia/testing'

const wrapper = mount(CartSummary, {
  global: {
    plugins: [createTestingPinia({
      createSpy: vi.fn,
      initialState: { cart: { items: [LATTE] } },
    })],
  },
})
const cart = useCartStore()          // 拿到測試用 pinia 裡的同一個 store
await wrapper.get('button').trigger('click')
expect(cart.clear).toHaveBeenCalledTimes(1)

createSpy: vi.fn 一定要給，它告訴 createTestingPinia 用什麼產生 spy。沒給的話，@pinia/testing 會先找全域的 jest.fn 或 vi.fn。Vitest 有一個 globals 設定，開了之後 vi、test 這些名字不用 import 就能用；這個練習專案沒有開，所以找不到，丟出「You must configure the "createSpy" option.」。注意傳的是 vi.fn 本身，不是 vi.fn()：它要的是產生 spy 的函式，不是一個已經產生好的 spy。

最後有一種錯從畫面測不出來。讀 store 那一節（頁首徽章解構 store）說過，元件裡自己 createPinia() 再傳給 useCartStore()，會拿到另一台空的購物車。但在測試裡，測試用的 pinia 啟用時，useCartStore(somePinia) 傳進去的 pinia 會被忽略，一律拿測試用的那一個，所以這個錯在測試裡畫面照樣正確。練習 2 的測試改用 vi.mock('pinia', …) 把 createPinia 換成會記錄呼叫的版本，直接檢查元件有沒有呼叫它；實務上這種錯多半靠 code review 擋下。這個行為的出處見課末。

補充與查表

主線用不到、但升級套件或看到舊程式碼時會用到的細節。

Pinia 4 改了什麼

練習專案用的是 pinia 4.1.0 和 @pinia/testing 2.0.2。Pinia 4.0.0 在 2026-07-14 發布，官方說明只有技術性的破壞性變更，API 用法不變：

  • 只支援 ESM：套件不再提供 CommonJS 版本，要用 import 載入。用 Vite 的專案不受影響。
  • @vue/devtools-api（v8）要一起安裝：它從 pinia 自己的依賴，變成必要的 peer dependency。peer dependency 是套件宣告「我需要它，但由你的專案安裝」，整個專案只裝一份。所以要把它寫進自己專案的 package.json。
  • 錯誤訊息與開發時的警告改寫，例如 createSpy 的錯誤附上 why、fix 和文件連結。
  • storeToRefs 遇到 store 上值是 null／undefined 的一般屬性（不是 ref，例如外掛直接掛上去的）會略過，不再丟錯。值是 null 的 state 仍是 ref，照樣會被轉出來。
  • 4.1.0（2026-10-14）新增 getStores(pinia)，列出一個 pinia 裡已經建立的所有 store。
  • @pinia/testing 2.0.2 需要 pinia 4.1.0 以上。

舊教學的 defineStore({ id })

網路上的舊教學會寫 defineStore({ id: 'cart', state: … })。這種寫法在 Pinia 3.0 已經移除，現在第一個參數一定是 id 字串。

toRefs 與 storeToRefs

Vue 的 toRefs(store) 也能用，但它會把 action、$patch 這些也包成 ref，Pinia 文件建議用 storeToRefs。

本課行為的出處

  • $subscribe 預設在下一個 microtask 才通知：在 pinia 4.1.0 本機驗證過，直接改 state 之後要 await nextTick() 才看得到寫入。
  • pinia.use() 在 app.use(pinia) 之前呼叫時先記著、裝進 app 才套用：pinia 4.1.0 原始碼。
  • 測試用的 pinia 啟用時，useCartStore(somePinia) 傳入的 pinia 被忽略：pinia 4.1.0 原始碼，NODE_ENV 是 test 時。

練習

三題都在 work/15/。練習 2 的元件用到練習 1 的 store，先做練習 1；練習 3 自帶一個簡化的購物車 store，可以單獨做。

練習 1：完成 cart-store.ts 的 setup store。state 有 items（每列 { id, name, price, qty }）和 orderType（'here'／'togo'，預設 here），兩個都要回傳。add(product) 同一個商品數量加一、不多一列，新的一列只放這四個欄位，不能改到傳進來的商品物件；changeQty(id, qty) 改數量，≤ 0 就移除那一列；數量上限 20。getter count 是 qty 總和、subtotal 是 price × qty 總和。自己寫 $reset()，讓所有 state 回到初始值。測試會加拿鐵兩次、可頌一次，檢查 count 3、小計 290，也會換一個新的 pinia 確認拿到空車。

練習 2：CartSummary.vue 直接解構 store，購物車變了畫面卻停在舊的數字。改成用 storeToRefs 取 count、subtotal，clear 直接從 store 解構；按「清空」呼叫一次 clear()。測試用 createTestingPinia 設定初始購物車，再用 $patch 改內容，檢查畫面有沒有跟著變。

練習 3：寫 persistPlugin({ storage, key })。只處理 id 是 'cart' 的 store；建立時讀回 { version: 1, items }，每一列要是 { id: 數字, name: 字串, price: 數字, qty: 1～20 的整數 }。JSON 壞掉、version 不是 1、items 不合法（不是陣列、任何一列格式不對）時，removeItem(key) 並從空車開始，不能丟錯。之後 state 每次變動就寫入 { version: 1, items }，只存 items。測試會改完 state 後 await nextTick() 再看 storage，所以預設的 flush 或 flush: 'sync' 都可以。

練習 4：菜單資料從 API 抓回來，好幾個頁面都要用。直接放進 Pinia store 適合嗎？

✓ b：菜單的正本在伺服器，前端拿的是會過期的副本。放進 store 能用，但「多久算舊、什麼時候重抓、兩個元件同時要時只發一次」都得自己寫，這正是第 17 課伺服器狀態快取在做的事。a 錯：「共用」不等於「放 store」，還要看正本在哪裡。c 錯：action 可以是 async。

練習 5：const { count, add } = useCartStore()，count 是 getter、add 是 action。哪一個會出問題？

✓ a：store 是 reactive 物件，解構 state 或 getter 只拿到當下的值（第 4 課）。要用 storeToRefs(cart)。b 錯：setup store 的 action 是閉包裡的普通函式，不靠 this，直接解構就能用。c 錯：只有 action 可以直接解構。

練習 6：為什麼伺服器端渲染（SSR）時，不能用模組最外層的 reactive() 當作購物車 store？

✓ c：Node 的模組載入一次之後就被快取，同一個伺服器程序同時服務很多人。Pinia 的 store 存在 pinia 實例裡，每個請求 createPinia() 一份就互不影響（第 24 課）。a 錯：Node 有 Proxy，reactive 能跑，問題是共用。b 錯：模組不會每個請求重新載入，這正是外洩的原因。

常見錯誤

  • 什麼都放進 store：開關、表單草稿、API 回應全進全域 store，改一個地方要追很多檔案。先從元件內開始，真的要全 app 共用才放 Pinia。
  • setup store 沒有回傳所有 state：畫面看起來正常，但 $state、devtools、外掛、SSR、測試的 initialState 都看不到它。每個 ref 都放進 return。
  • 以為 setup store 有 $reset()：只有 option store 有。自己寫，而且每加一個 state 都要記得補進去。
  • 很多元件直接改 state：規則散在各處，出錯時不知道是誰改的。修改都經過 action。
  • 直接解構 store：state 和 getter 失去響應，畫面停在舊值。用 storeToRefs 取 state 與 getter，action 直接解構。
  • 讀回 storage 的資料不驗證：一筆壞 JSON 或舊格式就讓 app 開不起來，或讓 items 變成 null。包 try/catch、檢查版本和每一列的格式，不合法就刪掉。
  • 持久化的格式改了卻沒有版本號：新版程式把舊資料當新格式讀。存 { version, … }，版本不符就丟棄或轉換。
  • 把 token 或個資存進持久化的 store：localStorage 是明文，XSS 就能讀走。
  • 用 createTestingPinia() 沒給 createSpy：沒有開 Vitest globals 時會丟錯。傳 createSpy: vi.fn。

小結

  • 狀態從最小範圍開始放：元件內 → 提升到父元件 → provide／inject → Pinia；可分享的條件放網址，伺服器的資料用伺服器狀態快取。購物車是正本在前端、跨頁面共用的狀態，所以放 Pinia。
  • Pinia 的 store 存在 pinia 實例裡，不存在模組裡：每個 app、每個 SSR 請求、每個測試各一份，還有 devtools 和外掛。
  • setup store：ref 是 state、computed 是 getter、function 是 action；所有 state 都要回傳；$reset 自己寫。修改都經過 action，規則只寫一次。
  • 元件裡用 storeToRefs 取 state 與 getter，action 直接從 store 解構；不要自己 createPinia() 傳給 store。
  • 持久化寫成外掛，用 pinia.use() 註冊，在 app.use(pinia) 之後生效；$subscribe 預設在下一個 microtask 通知。只存需要的欄位、加版本號、讀回時驗證，不存敏感資料。
  • 測 store 用 setActivePinia(createPinia())；測元件用 createTestingPinia({ createSpy: vi.fn, initialState })，action 預設被換成 spy。
  • Pinia 4：只支援 ESM、@vue/devtools-api v8 要一起安裝；4.1 新增 getStores()。細節在課末〈補充與查表〉。
