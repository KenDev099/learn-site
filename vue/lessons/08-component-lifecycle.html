階段 3：元件如何運作 · 第 8 課

元件的一生：生命週期、template ref 與清理

咖啡店櫃台有一台平板，整天開著點餐系統。系統有兩頁：「菜單」讓店員搜尋飲料、幫顧客點餐；「訂單看板」列出每一筆訂單的取餐倒數，上方還有一張今日營收圖表。店員一整天在兩頁之間切來切去。早上一切正常，到了下午，平板越來越卡。工程師打開 DevTools 一查：記憶體裡留著好幾十個早就不在畫面上的倒數元件，它們的計時器還在背景每分鐘跑一次。

這個點餐系統是單頁應用（single-page application，簡稱 SPA）：換頁時瀏覽器不會重新載入整個網頁，而是由 Vue 把舊頁面的元件拿掉、把新頁面的元件放上去。瀏覽器沒有重新載入，也就沒有人幫你把舊頁面開的計時器、註冊的事件、建立的圖表收掉。店員進出「訂單看板」二十次，背景就可能跑著二十份倒數計時器。

這課就拿這台平板當任務，跟著一個元件從建立到消失走一遍，把看板上的三個元件一個一個修好：取餐倒數要在對的時候開始、在對的時候停；「找飲料」按鈕要讓游標跳進搜尋框；營收圖表要用到真正的 DOM 元素，離開頁面時也要收乾淨。最後用測試證明修好了。

這課的路線：
  1. 看板上每一筆訂單的倒數為什麼各走各的：元件實例與 setup，以及「實例消失，計時器卻還在」這個問題從哪裡來。
  2. 計時器該在什麼時候開、什麼時候關：生命週期鉤子，開場問題的最小答案在這一節。
  3. 到底要收哪些東西、怎麼收才算收乾淨，以及怎麼用 DevTools 確認真的有洩漏。
  4. 「找飲料」要讓游標跳進搜尋框：用 template ref 拿到 DOM 元素，用 defineExpose 讓父元件呼叫子元件。
  5. 營收圖表：包裝第三方套件，把前面兩件事（拿到 DOM、卸載時清理）合在一起。
  6. 修好了怎麼證明：用 Vue Test Utils 測掛載、卸載與焦點；最後看懂舊專案的 Options API 寫法。
這課會用到：
  • 第 4 課的 template ref 與 VTU 入門：ref="input" 拿到 DOM 元素；測試裡用 mount 掛上元件、trigger 模擬點擊。
  • TS 課第 1 課的閉包：函式記住建立它時的變數，makeStampCard() 每呼叫一次就發一張各自記點數的新卡。

看板上每一筆訂單的倒數，為什麼各走各的？

先看「訂單看板」怎麼寫。每一筆訂單用一個 <PickupCountdown /> 元件顯示「取餐倒數 N 分鐘」，三筆訂單就寫三次：

<!-- 三個實例，三次 setup，三份狀態 -->
<PickupCountdown :minutes="5" />
<PickupCountdown :minutes="8" />
<PickupCountdown :minutes="12" />

畫面上三個倒數各自從 5、8、12 開始往下數，互不干擾。這是因為 Vue 每看到一次 <PickupCountdown />，就建立一個元件實例（component instance）。元件檔案 PickupCountdown.vue 像是一份設計圖；實例是照著設計圖做出來的一個成品，Vue 替它記住這一份自己的 props、狀態和畫面。同一份設計圖用三次，就有三個成品。

實例裡的狀態從哪裡來？你寫的 <script setup> 會被編譯成元件的 setup() 函式。Vue 建立實例時呼叫一次 setup()，函式裡宣告的 left、computed、watch 都屬於這個實例；接著再用第 7 課的 render 函式產生這個實例的畫面。

這跟 TS 課第 1 課的 makeStampCard() 是同一個道理：每呼叫一次就發一張新卡，每張卡的點數存在那一次呼叫的閉包裡，彼此無關。setup 每個實例跑一次，所以畫面上三個倒數元件，就有三份 left。

目前的 PickupCountdown.vue 長這樣（練習 1 的起始程式就是它）：

<script setup lang="ts">
import { ref } from 'vue'
const props = defineProps<{ minutes: number }>()
const left = ref(props.minutes)
setInterval(() => left.value--, 60_000)   // 在 setup 裡開、從不清除
</script>

<template>取餐倒數 {{ left }} 分鐘</template>

問題就出在這裡。目前的 PickupCountdown 在 setup 裡直接呼叫 setInterval，所以計時器也是每個實例各一個。店員離開「訂單看板」時，Vue 會把這三個實例從畫面上拿掉，但 Vue 只知道自己建立的東西（狀態、畫面），不知道你另外向瀏覽器要了一個計時器。計時器是瀏覽器的，瀏覽器不知道元件已經不在了，就繼續每分鐘呼叫一次。下次進入看板，又建立三個新實例、三個新計時器。這就是開場平板越來越卡的原因。

要修，就得在「這個實例要被拿掉」的那一刻，告訴 Vue 順便把計時器停掉。Vue 怎麼讓你在那一刻插入自己的程式？這就是下一節的生命週期鉤子。

計時器該在什麼時候開、什麼時候關？生命週期鉤子

一個實例從建立到消失會經過幾個固定的階段：建立（跑 setup）、掛載（產生 DOM 並放進頁面）、更新（資料改變後重新 patch 畫面）、卸載（從頁面拿掉）。這一連串階段叫做元件的生命週期（lifecycle）。

生命週期鉤子（lifecycle hook）是你在 setup 裡交給 Vue 的函式，意思是「走到這個階段時，請呼叫它」。組合式 API 的鉤子都是 on 開頭的函式，例如 onMounted(fn) 是「掛載完成時呼叫 fn」，onUnmounted(fn) 是「卸載完成時呼叫 fn」。整個流程長這樣：

每個鉤子在什麼時候被呼叫、常拿來做什麼：

鉤子什麼時候常拿來做
setup（<script setup> 本身）建立實例時，只跑一次宣告狀態、computed、watch、註冊其他鉤子
onMounted元件的 DOM 已經建好、插入父容器之後操作 DOM、量尺寸、開計時器、建立第三方圖表
onBeforeUpdate／onUpdated響應式資料改變、重新 patch 之前／之後很少需要；要等 DOM 更新完通常用 nextTick（第 6 課）
onBeforeUnmount要卸載了，DOM 還在需要在 DOM 還在時做的事，例如存捲動位置
onUnmounted子元件都卸載完、這個元件的 render effect 與 setup 裡同步建立的 watcher 都停了之後清除計時器、事件監聽、observer、第三方實例

回到取餐倒數，最小的修法是兩個鉤子配成一對：在 onMounted 裡開計時器、把 setInterval 回傳的 id 存起來；在 onUnmounted 裡用 clearInterval(id) 停掉。實例被拿掉時 Vue 呼叫 onUnmounted，計時器跟著停，進出看板二十次也不會累積。

你可能會問：計時器又不碰 DOM，為什麼不在 setup 裡開、只在 onUnmounted 收就好？有兩個理由。

第一，setup 執行時 DOM 還不存在。看上面的圖，setup 在 onBeforeMount 之前，Vue 還沒產生任何元素。計時器剛好不需要 DOM，但同樣的習慣套到量尺寸、focus、建立圖表就會出錯：在 setup 裡用 document.querySelector 找元件自己的元素，拿到的是 null。「要等畫面出來才做的事都放進 onMounted」這條規則一致套用，比每次判斷要不要 DOM 好記。

第二，伺服器渲染（SSR，第 24 課）。SSR 是在伺服器上先把元件跑一次、產生 HTML 送給瀏覽器。這時 setup 會在伺服器上執行，但 onMounted、onUnmounted 都不會。計時器寫在 setup 裡，伺服器上就會留下一個永遠不會被清掉的計時器；寫在 onMounted 裡，它只會在瀏覽器裡開始，也一定有對應的 onUnmounted 收掉它。用 typeof window 判斷「是不是在瀏覽器」再在 setup 裡開，雖然避開了伺服器，卻把「開」和「關」拆到兩個不對稱的地方，練習 1 的測試也不接受這種寫法。

看板和倒數，誰先掛載好？

「訂單看板」是父元件 OrderPage，裡面放著子元件 PickupCountdown。兩個都寫了鉤子時，順序是固定的。下面是在 Vue 3.5.44 實際記錄的順序：

父 setup
父 onBeforeMount
子 setup
子 onBeforeMount
子 onMounted        ← 子元件先掛載完
父 onMounted        ← 父元件最後：這時整棵子樹都在了
（卸載時）
父 onBeforeUnmount
子 onBeforeUnmount
子 onUnmounted
父 onUnmounted

父元件先開始建立，但它的畫面包含子元件，要等每個子元件都掛好，父元件的畫面才算完整，所以 onMounted 由內往外：子先、父後。卸載也一樣，子元件先 onUnmounted，父元件最後。這個順序有一個實際的好處：父元件在自己的 onMounted 裡，一定拿得到子元件，後面第四節父元件呼叫子元件的方法就靠這一點。

鉤子一定要在 setup 裡「當下」註冊

呼叫 onMounted(fn) 時沒有傳「這是哪個元件的」，Vue 怎麼知道 fn 屬於看板上的哪一個倒數？它靠一個內部記錄：「目前正在執行 setup 的是哪個實例」。setup 開始時設定，setup 一跑完就清掉。所以只要在 setup 執行的當下呼叫 onMounted，Vue 就能把 fn 掛到正確的實例上。

反過來，如果在 setTimeout、Promise 的 .then 回呼，或一般 async 函式的 await 之後才呼叫，那時 setup 的同步部分早就跑完，記錄已經清空，Vue 找不到實例，鉤子永遠不會執行。開發模式下只會印出警告，不會丟錯，很容易漏看：

setTimeout(() => {
  onMounted(() => { /* 永遠不會執行 */ })
}, 0)

// [Vue warn]: onMounted is called when there is no active component instance
// to be associated with. Lifecycle injection APIs can only be used during
// execution of setup(). …

規則看的是「呼叫的那一刻 setup 還在不在跑」，不是「程式碼寫在哪個檔案」。所以在 setup 裡同步呼叫的其他函式（例如第 12 課的 composable）也可以註冊鉤子。第 5 課的 watcher 是同一條規則：setup 裡同步建立的 watcher 會綁在元件上，卸載時自動停止；在非同步回呼裡建立的不會。

現在知道要在 onUnmounted 收東西了。但計時器只是其中一種：看板上還可能有視窗大小的監聽、即時訂單的連線、圖表。哪些要自己收、為什麼不收就一直留著、怎麼收才算真的收掉？下一節講清楚。

切換二十次為什麼留下二十份？卸載時要收掉哪些東西

先看傳統網站。每換一頁，瀏覽器就丟掉整份文件，連同上面所有的計時器和事件監聽，下一頁從乾淨的狀態開始。SPA 不換文件，元件卸載只是把它的 DOM 從頁面上拿掉，你另外向瀏覽器要的東西全都還在。

「還在」為什麼會讓平板變卡？JavaScript 的記憶體由垃圾回收（garbage collection）管理：一個物件只要還有人參照它，就不能被釋放；沒有任何人參照了，才會被回收。不再需要、卻因為仍被參照而無法釋放的物件，叫做記憶體洩漏（memory leak）。

倒數元件的情況是這樣一條參照鏈：瀏覽器的計時器清單參照著你傳進去的回呼函式；回呼是閉包（TS 課第 1 課），它記住了元件的狀態 left；元件的狀態又留住了 DOM。只要計時器沒被清掉，整條鏈都回收不掉。每進出看板一次就多一條，記憶體越積越多，背景要跑的回呼也越來越多。

收掉的方法是呼叫對應的清除 API，把源頭那一個參照拿掉。計時器用 clearInterval；事件監聽用 removeEventListener。後者有一個常見的坑：removeEventListener 要傳同一個函式，瀏覽器才知道要移除哪一個。寫兩次一樣的箭頭函式，內容相同，卻是兩個不同的函式物件，移除不會成功，也不會報錯。

下面用 EventTarget 模擬 window，模擬「進入頁面註冊、離開頁面移除」三次，最後觸發一次 resize。執行後看兩行輸出的數字：錯誤的寫法留下幾個處理函式，正確的留下幾個。

錯誤的寫法離開三次後還留著三個處理函式，每次 resize 都會跑三遍；正確的寫法一個都不剩。放進元件裡，就是把處理函式存成變數，在 onMounted 註冊、在 onUnmounted 用同一個變數移除：

const width = ref(0)
const onResize = () => { width.value = window.innerWidth }

onMounted(() => {
  onResize()
  window.addEventListener('resize', onResize)
})
onUnmounted(() => window.removeEventListener('resize', onResize))

判斷要不要自己收，看一個原則：你呼叫瀏覽器或第三方 API 拿到的東西，都要自己收；Vue 自己建立的東西（元件內部的響應式狀態、computed、setup 裡同步建立的 watch）Vue 會處理。下表是常見的建立與清除對照，查表用，不用背：

在 onMounted 建立在 onUnmounted 清理
const id = setInterval(…)clearInterval(id)（setTimeout 對應 clearTimeout）
window.addEventListener('resize', fn)window.removeEventListener('resize', fn)，同一個 fn
new ResizeObserver(cb).observe(el)observer.disconnect()
new WebSocket(url)socket.close()
第三方圖表、地圖：createChart(el, data)套件提供的 destroy()／dispose()
在非同步回呼裡建立的 watch呼叫它回傳的停止函式（第 5 課）

怎麼確認真的有洩漏

改完之後，平板真的不會再越來越卡了嗎？不要用猜的。Chrome DevTools 的 Memory 面板可以拍 heap snapshot（記憶體快照），記錄當下記憶體裡有哪些物件、各有多少個。拍兩張比較，就看得出進出頁面之後多了什麼：

  1. 打開頁面，在 Memory 面板拍第一張快照。
  2. 在「菜單」和「訂單看板」之間進出 5～10 次，回到原本的頁面。按面板上的垃圾桶圖示強制回收一次，讓本來就該回收的物件先清掉。
  3. 拍第二張，切到 Comparison（比較）檢視，或在搜尋框輸入 Detached。

Detached 元素是已經從頁面移除、卻還被 JavaScript 參照的 DOM，也就是上面那條參照鏈的尾端。如果它的數量、或某個元件相關物件的數量跟著進出次數一起增加，就是洩漏。點進去看 Retainers（是誰留住它），通常會看到某個計時器或事件監聽的閉包，順著找就能找到忘了收的那一行。

💡 實務上：洩漏最常出現在整天不關的頁面
咖啡店櫃台的訂單看板、後台的營收儀表板，常常一開就是一整天，店員在頁面間切來切去，沒清的計時器和 WebSocket 會越積越多，最後變成「下午開始變卡」「同一筆新訂單通知響兩次」這種客服回報。一般官網用完就關，比較不容易察覺，但不代表沒有問題。Code review 時的習慣是：看到 addEventListener、setInterval、new WebSocket，就往下找對應的清除；重複出現的模式之後會包成 composable（第 12 課），把建立和清除寫在一起，呼叫的人就不會忘。

到這裡，倒數計時器修好了。它和事件監聽有一個共同點：都不需要碰 DOM。點餐系統上另外兩個元件就不一樣了：「找飲料」要把游標放進某一個輸入框，營收圖表要畫在某一個 <canvas> 上，兩者都得先拿到真正的 DOM 元素。先從簡單的搜尋框開始。

「找飲料」要讓游標跳進搜尋框：怎麼拿到 DOM 元素？

「菜單」頁上方有一個搜尋框，旁邊有一個「找飲料」按鈕。店員按下去，游標要跳進搜尋框，直接打字。瀏覽器的做法是對輸入框元素呼叫 focus()，所以問題變成：程式裡怎麼拿到「這個元件自己的那個輸入框」？

直覺的做法是 document.querySelector('input')。但第一節講過，同一個元件可以有很多個實例：如果頁面上有兩個搜尋框，querySelector 永遠拿到整份文件裡的第一個，第二個實例的按鈕會把游標送到別人的輸入框。元素是 Vue 依照範本產生的，應該由 Vue 告訴你「這個實例的那個元素是哪一個」。

這就是 第 4 課看過的 template ref：在範本的元素上加 ref="名字"，Vue 掛載時就會把這個實例裡對應的 DOM 元素交給你。Vue 3.5 起建議用 useTemplateRef('名字') 取得，參數是範本上那個名字的字串：

<script setup lang="ts">
import { onMounted, useTemplateRef } from 'vue'

const inputEl = useTemplateRef<HTMLInputElement>('input')

console.log(inputEl.value)          // null：setup 時元素還不存在
onMounted(() => inputEl.value?.focus())   // 掛載後才有值
</script>

<template>
  <input ref="input" placeholder="搜尋飲料">
</template>

useTemplateRef 回傳一個 ref，它的 .value 一開始是 null。這跟前面講生命週期那一節直接相關：setup 執行時還沒有 DOM，Vue 沒有元素可以給你；掛載時 Vue 建立元素，才把它填進 .value，所以 onMounted 裡讀得到。之後如果元素被 v-if 移除，.value 會變回 null。因此讀它的時候一律用 ?.，元素不在時就什麼都不做，不會丟錯。

你在 3.5 以前的專案會看到另一種寫法，以及放在 v-for 裡的情況，細節見課末〈補充與查表〉。

搜尋框是子元件：父元件怎麼呼叫它？defineExpose

實際上，搜尋框通常會抽成一個 SearchBox 元件，「找飲料」按鈕在父元件 MenuPage 上。這時輸入框在子元件裡，父元件拿不到它。

template ref 也可以放在子元件上：<SearchBox ref="box" />，這時拿到的不是 DOM 元素，而是子元件的實例。但 <script setup> 寫的元件預設對外封閉：父元件從這個實例上看不到子元件裡宣告的任何變數或函式。這是刻意的設計，子元件的內部狀態本來就不該讓外面隨意碰。

子元件要讓父元件呼叫某些東西，就用 defineExpose 明確列出要公開什麼。沒列出的，父元件一樣看不到。為了不直接給出練習 2 的答案，下面先用同一個 SearchBox 公開另一個動作 clear（清空搜尋字），focus 的寫法一模一樣：

<!-- SearchBox.vue -->
<script setup lang="ts">
import { ref, useTemplateRef } from 'vue'
const keyword = ref('')
const inputEl = useTemplateRef<HTMLInputElement>('input')

function clear() { keyword.value = '' }

defineExpose({ clear })   // 父元件只看得到 clear
</script>

<!-- MenuPage.vue -->
<script setup lang="ts">
import { useTemplateRef } from 'vue'
import SearchBox from './SearchBox.vue'
const box = useTemplateRef<InstanceType<typeof SearchBox>>('box')
const reset = () => box.value?.clear()
</script>

<template>
  <SearchBox ref="box" />
  <button @click="reset">清除</button>
</template>

這個例子公開的是 clear，「找飲料」需要的 focus 是同樣的做法，就是練習 2。父元件這邊的 InstanceType<typeof SearchBox> 是「SearchBox 實例的型別」，有了它，box.value?.clear() 寫錯方法名稱時 TypeScript 會報錯。前面〈看板和倒數，誰先掛載好？〉講的父子順序在這裡派上用場：子元件比父元件先掛載完，所以父元件的 onMounted 和之後的點擊事件裡，box.value 一定已經有值。

要公開什麼，是一個設計上的取捨。公開的東西就成了子元件的介面，其他元件開始依賴它，以後就很難改。所以只公開「動作」，例如 focus、clear；不要把輸入框元素或內部狀態整個交出去，否則父元件會開始直接改子元件的內部，兩邊綁死，改一邊就壞另一邊。也不是所有父子溝通都該用 ref：能用 props 和事件（第 9 課）表達的資料流，就不要用 ref 呼叫子元件；ref 留給 focus、捲動、播放這類「叫它做一件事」的命令式動作。

💡 實務上：ref 呼叫子元件最常見在表單和彈窗
工作中最常見的是 UI 元件庫的表單：送出前呼叫 formRef.value?.validate() 跑一次驗證，或在送出失敗後讓游標跳回第一個錯誤欄位。自己寫的元件則多半是搜尋框的 focus()、列表的 scrollToTop()。Code review 時資深工程師會問：這件事能不能用 props 表達？例如「彈窗開或關」是狀態，用 props／v-model 比父元件呼叫 open() 好追；公開的方法越多，之後改子元件越綁手綁腳。

搜尋框只需要拿到元素、呼叫一次 focus()，不需要清理。營收圖表兩件事都要：它得拿到真正的 <canvas> 才能建立，又會自己占用資源，卸載時要銷毀。下一節把這兩件事合在一起。

營收圖表：第三方套件怎麼包，才不會壞也不會洩漏？

「訂單看板」上方的今日營收圖表，用的是第三方圖表套件。這類套件（圖表、地圖、文字編輯器）的共同點是：它們不是 Vue 元件，而是一個普通的 JavaScript 函式庫，你要交給它一個真正的 DOM 元素，它在上面自己畫，並且回傳一個物件讓你之後更新或銷毀。包成 Vue 元件時，有三件事要做對：

import { onMounted, onUnmounted, useTemplateRef, watch } from 'vue'
import { createChart, type Chart } from 'some-chart-lib'

const props = defineProps<{ data: number[] }>()
const canvasEl = useTemplateRef<HTMLCanvasElement>('canvas')
let chart: Chart | undefined        // 1. 普通變數，不要 ref(chart)

onMounted(() => {                   // 2. 有元素之後才建立
  chart = createChart(canvasEl.value!, props.data)
})
watch(() => props.data, data => chart?.update(data))
onUnmounted(() => chart?.destroy()) // 3. 卸載時銷毀

第 2 點和第 3 點就是前兩節的內容：createChart 需要 canvas 元素，setup 時 canvasEl.value 還是 null，所以要等 onMounted；圖表物件是你向第三方要來的，Vue 不知道它存在，卸載時要自己呼叫套件提供的 destroy()，否則它占用的資源和監聽會像倒數計時器一樣留下來。中間的 watch 負責 props 換成新資料時通知圖表重畫。

第 1 點是新的坑。直覺上會想把圖表物件存進 ref()，但第 4 課說過：放進 ref() 的物件會被包成深層的 proxy，之後透過它呼叫方法時，方法裡的 this 是 proxy，不是原本的物件。很多套件的物件用 #private 欄位存內部資料，而 #private 欄位只認原本的物件，透過 proxy 讀就丟 TypeError。況且圖表物件根本不需要被 Vue 追蹤，畫面不會因為它改變而重新渲染，所以用普通的 let 變數就好。如果範本真的需要用到它（例如在圖表建立好之前顯示「載入中」），就用 shallowRef 或 markRaw，讓 Vue 只追蹤「換了一個物件」或完全不包裝它。

💡 實務上：第三方套件包一次，全專案共用
後台的營收圖表、門市地圖、文章編輯器，團隊通常只包一個 <SalesChart> 之類的元件，把建立、更新、銷毀都藏在裡面，其他人只傳 props。動手前先查套件有沒有官方或社群維護的 Vue 版本，有的話直接用，通常比自己包更完整。自己包時另外留意兩件事：容器尺寸改變時圖表要不要重畫（常配 ResizeObserver），以及套件是否一載入就用到 window：SSR 時伺服器上沒有 window，這類套件要等到 onMounted 裡才建立，甚至才載入。

三個元件都修好了。但「卸載時有沒有真的清乾淨」在畫面上看不出來，每次改完都開 DevTools 拍快照也不實際。下一節把這些行為寫成測試。

修好了怎麼證明？用 Vue Test Utils 測掛載與卸載

計時器在背景跑，不會顯示在任何地方，要靠測試把它變成看得到的數字。Vue Test Utils（VTU）是 Vue 官方的元件測試工具，它讓你在測試裡掛載一個元件、操作它、讀它的畫面，再卸載它，完整走一遍生命週期。練習用的版本是 2.5.1。

測倒數元件還需要一個東西：假計時器。真的等 60 秒太慢，第 5 課練習用過的 vi.useFakeTimers() 會把 setInterval 換成測試能控制的版本。之後 vi.advanceTimersByTime(60_000) 讓時間直接往前跳 60 秒；vi.getTimerCount() 回傳還沒清掉的計時器數量。開場的問題「卸載後計時器有沒有留下來」，就變成「卸載後這個數字是不是 0」：

vi.useFakeTimers()
const wrapper = mount(PickupCountdown, { props: { minutes: 15 } })
vi.advanceTimersByTime(60_000)
await nextTick()
expect(wrapper.text()).toBe('取餐倒數 14 分鐘')
wrapper.unmount()
expect(vi.getTimerCount()).toBe(0)

逐行看：mount 建立實例並掛載，跑完 setup 和 onMounted，計時器在這時開始；時間往前跳 60 秒，計時器的回呼執行一次，left 變成 14；await nextTick() 等 Vue 把畫面更新完（第 6 課講過，Vue 會把更新排到下一個 tick 批次處理，不 await 讀到的還是舊文字）；最後 unmount() 卸載，會跑 onBeforeUnmount／onUnmounted，計時器應該被清掉。起始程式把計時器開在 setup 又從不清除，最後一行就會失敗。

同樣的理由，會改到畫面的操作（trigger、setValue、setProps）都回傳 Promise，要 await 之後再讀畫面。

測「找飲料」的焦點時要多一個設定：attachTo。VTU 預設把元件掛在一個沒有放進 document 的元素上，這種元素呼叫 focus() 不會改變 document.activeElement（目前取得鍵盤焦點的元素），測試就判斷不出焦點有沒有跳過去。寫 mount(Comp, { attachTo: document.body }) 把元件真的放進頁面，focus() 才會生效。

VTU 常用的寫法整理如下，查表用，不用背：

寫法做什麼
const wrapper = mount(Comp, { props })建立實例並掛載，跑完整的 setup → onMounted
wrapper.get('button')／wrapper.find('input')用 CSS 選擇器找元素；get 找不到就丟錯，find 回傳一個 .exists() 為 false 的結果
await el.trigger('click')、await el.setValue('拿鐵')觸發事件、輸入文字
wrapper.text()、el.element讀畫面文字、拿到真正的 DOM 元素
wrapper.emitted('add')元件發出過的事件與參數（第 9 課）
await wrapper.setProps({ data })換 props，觸發更新
wrapper.unmount()卸載，會跑 onBeforeUnmount／onUnmounted
wrapper.vm 在測試裡看得到 <script setup> 的內部狀態，就算元件沒有 defineExpose。所以「父元件拿得到什麼」不能用 wrapper.vm 判斷，要像真正的父元件一樣用 template ref 去拿。練習 2 的測試就是這樣做的。測試盡量檢查使用者看得到的結果（文字、焦點、事件），第 22 課會再深入。

看板的三個元件都修好、也有測試了。最後一個問題是：這個點餐系統如果是前一位同事很早以前寫的，你打開檔案看到的可能不是 <script setup>，而是另一種寫法。

接手的舊元件是 Options API：對應到組合式 API 的哪裡？

Vue 3 支援兩種寫元件的方式。這門課一律用組合式 API（<script setup>），但你接手的舊專案、Stack Overflow 的回答、很多套件的文件還在用 Options API（選項式 API）：把狀態、方法、鉤子分別寫在一個物件的不同選項裡。它不是 Vue 2 才有，Vue 3 照樣支援。同一個倒數元件用 Options API 寫，清理也已經做對了：

<script lang="ts">
import { defineComponent } from 'vue'

export default defineComponent({
  props: { minutes: { type: Number, required: true } },
  data() {
    return { left: this.minutes, timer: undefined as ReturnType<typeof setInterval> | undefined }
  },
  computed: {
    urgent(): boolean { return this.left <= 2 },   // Options API 的 computed 常要標回傳型別
  },
  watch: {
    left(n) { if (n === 0) this.notify() },
  },
  methods: {
    notify() { /* 通知取餐 */ },
  },
  mounted() {
    this.timer = setInterval(() => { this.left-- }, 60_000)
  },
  unmounted() {
    clearInterval(this.timer)
  },
})
</script>

讀 Options API 的關鍵是 this：它就是元件實例，data 回傳的屬性、computed、methods、props 全都掛在它上面，所以 mounted 裡寫 this.timer、this.left。組合式 API 沒有 this，同樣的東西都是 setup 裡的變數。鉤子的名字少了 on 前綴，時機跟前面講的完全相同：mounted 開計時器、unmounted 收掉，就是這課的修法。對照如下：

Options API組合式 API
data() 回傳的屬性ref／reactive
computed: { … }computed(() => …)
methods: { … }一般函式
watch: { left(n) {…} }watch(left, n => …)
mounted、updated、beforeUnmount、unmountedonMounted、onUpdated、onBeforeUnmount、onUnmounted
this.$refs.inputuseTemplateRef('input')
this.left：this 指向元件實例直接用變數，沒有 this

Options API 還有 beforeCreate、created 兩個鉤子，在組合式 API 沒有對應的鉤子：setup 本身就在那個時間點執行，那段程式直接寫在 setup 裡。

💡 實務上：接手舊專案不必急著全部改寫
接手的專案若是 Options API，能正常運作的元件通常不會為了改寫而改寫：改寫有風險，又沒有直接的功能收益，PM 也很難排進時程。比較常見的做法是新元件用 <script setup>，舊元件等到要大改功能時再順手轉換，同一個專案兩種寫法並存沒問題。真要整批改寫，先確認那些元件有測試，改完行為才有東西比對。

主線用不到、但遇到時要知道的細節。

版本備註

  • useTemplateRef 是 Vue 3.5 起的寫法；練習用的是 Vue 3.5.44。
  • 本課父子鉤子的順序是在 Vue 3.5.44 實際記錄的。
  • 練習用的 Vue Test Utils 是 2.5.1。

3.5 以前的 template ref 寫法

舊寫法是宣告一個跟範本 ref 同名的變數：const input = ref<HTMLInputElement | null>(null) 配 ref="input"，仍然可以用，你會在 3.5 以前的專案看到。兩種寫法的值都要等掛載後才有，元素被 v-if 移除後都會變回 null。

放在 v-for 裡的 template ref

放在 v-for 裡的 ref 會拿到陣列，而且官方文件說明這個陣列的順序不保證跟資料一樣。需要「第幾筆資料對應哪個元素」時，用每一筆的 id 自己記錄。

defineExpose 要寫在 await 之前

defineExpose 要寫在 setup 裡任何 await 之前，否則 await 之後才公開的東西父元件拿不到。

例外：<script setup> 頂層 await 之後仍可註冊鉤子

主線說「await 之後註冊鉤子會失效」，指的是一般 async 函式裡的 await。<script setup> 的頂層 await 不一樣：編譯器會把它編成能在 await 之後還原目前元件實例的形式，所以頂層 await 之後呼叫 onMounted、composable 仍然會綁到這個實例上。代價是這個元件會變成 async setup()，必須搭配 <Suspense> 使用（官方文件標示 Suspense 仍是實驗性功能）。注意兩條規則不同：鉤子在頂層 await 之後可以註冊，defineExpose 卻仍要寫在 await 之前。

KeepAlive 包住的元件

<KeepAlive> 包住的元件切走時不會卸載，而是被快取起來，所以 onUnmounted 不會執行。這種元件用 onDeactivated／onActivated 暫停與恢復計時器。

練習

在 learn/ 執行 node check.mjs vue 08，在 vue/practice/work/08/ 裡改檔案。chart-lib.ts 是假的第三方套件，不要改。

練習 1：PickupCountdown.vue 顯示「取餐倒數 N 分鐘」，每 60 秒減 1。起始程式在 setup 裡 setInterval，而且從不清除。改成：在 onMounted 裡才開始計時（用 typeof window 判斷後在 setup 開始也不行），每 60 秒都要更新一次，卸載時清除，卸載後 vi.getTimerCount() 要是 0。

練習 2：按「找飲料」要讓游標跳進搜尋框。在 SearchBox.vue 用 useTemplateRef 取得輸入框，提供 focus()，用 defineExpose 只公開 focus；在 SearchPage.vue 用 template ref 拿到 SearchBox，按鈕呼叫它的 focus()。測試會確認焦點真的在輸入框上、SearchPage 確實呼叫了 SearchBox 的 focus()（不是自己 querySelector）、頁面上有兩個 SearchBox 時各自聚焦自己的輸入框，而且父元件從 ref 上只看得到 focus。

練習 3：SalesChart.vue 包裝假的圖表套件 createChart(canvas, data)。起始程式在 setup 就建立圖表（那時 canvas 還是 null），而且放進 ref()。改成：掛載後用真正的 <canvas> 建立；props.data 換成新陣列時呼叫一次 chart.update(新資料)；卸載時呼叫 chart.destroy()。圖表物件有 #private 欄位，過程中不能丟 TypeError。

練習 4：OrderPage 裡面有 PickupCountdown，兩個元件都寫了 onMounted。第一次渲染時，哪一個的 onMounted 先執行？

✓ setup 和 onBeforeMount 是父元件先，但父元件要等整棵子樹都掛載完才算掛載完成，所以 onMounted 是子元件先、父元件後。順序是固定的。也因此父元件在 onMounted 裡一定拿得到子元件的 template ref。

練習 5：<script setup> 裡寫 const el = useTemplateRef('input')，下一行立刻 console.log(el.value)，會印出什麼？

✓ setup 執行時還沒渲染，DOM 不存在，所以 template ref 的值是 null。掛載後（onMounted 之後）才會被設成那個元素。useTemplateRef 回傳的是一個唯讀的 ref，只要一層 .value。

練習 6：在 setup 裡寫 setTimeout(() => onMounted(() => console.log('掛好了')), 0)，會怎樣？

✓ onMounted 靠「目前正在執行 setup 的實例」知道鉤子屬於誰。setTimeout 的回呼執行時 setup 早就結束了，Vue 找不到實例，只印出「onMounted is called when there is no active component instance…」的警告，鉤子不會被執行。鉤子一律在 setup 裡同步註冊。

常見錯誤

  • 在 setup 就操作 DOM：那時元素還不存在，template ref 是 null。量尺寸、focus、建立圖表放進 onMounted。
  • 開了計時器、事件監聽、observer、第三方實例卻沒清：SPA 換頁不會重新載入，每進出一次就多一份。在 onUnmounted 對應地清除，用 heap snapshot 確認。
  • removeEventListener 傳了另一個箭頭函式：移除不會成功。把處理函式存在變數裡，註冊和移除用同一個。
  • 用 ref() 存第三方實例：會被包成 proxy，讀 #private 丟 TypeError，也多了不必要的追蹤。用普通變數、shallowRef 或 markRaw。
  • 沒有 defineExpose 卻想從父元件呼叫子元件：<script setup> 預設封閉，ref 上什麼都沒有。只公開需要的動作，不要把整個元素交出去。
  • 在 setTimeout、.then 回呼或一般 async 函式的 await 之後才註冊鉤子：鉤子不會執行。在 setup 裡同步註冊（<script setup> 頂層 await 是例外，見課末）。
  • 用 document.querySelector 找元件自己的元素：頁面上有兩個實例時，永遠拿到第一個。用 template ref 拿這個實例自己的元素。
  • 測 focus 沒有 attachTo：元件不在 document 裡，document.activeElement 不會變。mount(Comp, { attachTo: document.body })。

小結

  • 每使用一次元件就建立一個實例、跑一次 setup，每個實例有自己的狀態，也有自己開的計時器與監聽；實例被拿掉時，你向瀏覽器要的東西不會自己消失。
  • 順序：setup → onBeforeMount → onMounted →（onBeforeUpdate／onUpdated）→ onBeforeUnmount → onUnmounted。onMounted 由子到父；setup 時沒有 DOM，伺服器渲染時也不會跑 onMounted。
  • 鉤子要在 setup 裡同步註冊：Vue 靠「目前正在跑 setup 的實例」知道鉤子屬於誰；計時器、.then 回呼與一般 async 函式 await 之後都找不到實例（<script setup> 頂層 await 由編譯器還原，是例外）。
  • 自己開的東西自己收：在 onMounted 開、在 onUnmounted 收，計時器、事件監聽（同一個函式）、observer、WebSocket、第三方實例都一樣；有沒有洩漏用 heap snapshot 確認。
  • useTemplateRef('名字')（3.5）拿這個實例自己的元素或子元件，掛載後才有值；子元件用 defineExpose 決定公開什麼，只公開動作。
  • 包第三方套件：掛載後建立、卸載時銷毀，實例用普通變數存，不放進 ref()。
  • VTU：mount、get／find、await trigger、setProps、unmount；計時器用假計時器測、卸載後 vi.getTimerCount() 是 0，focus 要 attachTo。
  • Options API 的 data／methods／mounted 對應 ref／函式／onMounted，看得懂就好，新程式碼用 <script setup>。

下一課講元件之間怎麼溝通：用 props 把資料傳進去、用 emits 把事件傳出來，以及為什麼子元件不能直接改 props。
