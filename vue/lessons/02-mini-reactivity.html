階段 1：響應式原理：自己做一個 · 第 2 課

自己做迷你響應式系統：effect、track、trigger

第 1 課的購物車頁面有三個地方讀同一份 cart：小計、右上角徽章的件數、結帳按鈕。我們用 Proxy 攔截到了「讀」和「寫」，但只做到印 log：get trap 知道有人讀了 cart.qty，卻不知道是哪一段程式讀的；set trap 知道 cart.qty 被改了，也還沒辦法讓讀過它的地方重新執行。

這一課把第 1 課的購物車放進一個更完整的場景：咖啡店的點餐頁。頁面上除了購物車 cart（qty 杯數、price 單價、note 備註），還有每個品項的價格標籤（item.show 有沒有貨、item.price 價格），以及店面資訊 shop（open 是否營業中、menu 菜單）。後面每一節的例子都從這三個物件取材。

這一課的任務：把第 1 課的 Proxy 做成一個真的會動的響應式系統，讓點餐頁上的每一塊畫面，在資料改變時自動重新執行，而且不漏跑、不白跑、不當掉。成果是一個叫 effect 的函式：寫 effect(() => console.log(cart.qty * cart.price)) 一行，之後改 cart.qty 就會自動重印。Vue 的 watchEffect 和每個元件的重新渲染用的是同一套機制，所以做完之後，碰到「畫面沒更新」或「watch 跑太多次」，你會知道該往哪裡查。

這課的路線：
  1. 系統怎麼知道一段程式讀了哪些屬性、記錄要存在哪裡：activeEffect 與依賴表，寫出能動的第一版。
  2. 第一版會在哪裡壞：品項售完後改價格還在白跑、外層區塊該更新卻不更新、effect 改自己讀的資料就當掉，各自怎麼修。
  3. 一次改好幾個屬性，怎麼只重跑一次：用 scheduler 把「什麼時候重跑」交出去，這是 computed、watch 與畫面批次更新的基礎。
  4. 為什麼 await、setTimeout 之後讀的值不會被追蹤，以及迷你版跟真正的 Vue 差在哪。
這課會用到：
  • 第 1 課的 Proxy 與 Reflect：get／set trap 攔截對物件的讀寫，trap 裡用 Reflect.get(target, key, receiver)、Reflect.set 完成原本的操作，set 要回傳 true。
  • TS 課第 19 課的泛型：Map<K, V> 是鍵為 K、值為 V 的 Map，Set<T> 是裝 T 的 Set。

effect 執行時，系統怎麼知道它讀了哪些屬性？

先替「資料改了要重跑的那段程式」取一個名字。點餐頁上的小計是一段函式：讀 cart.qty 和 cart.price，算出金額，更新畫面。徽章是另一段函式：讀 cart.qty，更新件數。這種「會讀響應式資料、資料改了就要重新執行」的函式，叫做 effect，全名是響應式副作用（reactive effect）。叫它副作用，是因為它執行的目的是對外界造成影響，例如改畫面、印 log、發請求。Vue 的 watchEffect 傳進去的函式是 effect，每個元件的渲染函式也是 effect。

要讓 effect 自動重跑，系統得先知道「小計這個 effect 讀了 cart.qty」。第 1 課的 get trap 會在讀 cart.qty 時被呼叫，可是它收到的參數只有 target、key、receiver，沒有一個告訴它「是誰在讀」。JavaScript 也沒有辦法在函式裡問「呼叫我的是哪段程式」。

解法利用了一個事實：JavaScript 是單執行緒，一段函式開始執行後，除非它自己呼叫別的函式，否則不會有其他程式插進來（effect 裡面又建立 effect 的情況，後面巢狀 effect 那節會處理）。所以只要在執行 effect 之前，把它放進一個全域變數，get trap 被呼叫時去看這個變數，就知道是誰在讀。這個變數叫 activeEffect（目前正在執行的 effect）：

  • 執行 effect 之前，把 activeEffect 設成這個 effect。
  • effect 執行期間讀到的每個屬性，get trap 都看得到 activeEffect，就記下「activeEffect 依賴這個屬性」。
  • effect 執行完，把 activeEffect 清掉。之後在 effect 外面的讀取，例如你在 console 裡看一下 cart.qty 的值，activeEffect 是空的，就不記。

get trap 裡「記下依賴」的動作叫 track（追蹤）；set trap 裡「找出依賴這個屬性的 effect，讓它們重新執行」的動作叫 trigger（觸發）。整個流程畫成圖是這樣：

到這裡我們知道「誰讀了什麼」可以在 track 當下取得。但 track 記下來的東西要存在哪裡？trigger 被呼叫時手上只有 target 和 key，它得靠這兩個值查出要重跑的 effect，下一節就來設計這張表。

記下來的依賴要存在哪裡，trigger 才查得到？

trigger 要回答的問題是：「cart 這個物件的 qty 屬性，被哪些 effect 讀過？」問題裡有物件、有屬性，答案是一群 effect，所以資料結構剛好是三層，我們叫它依賴表（targetMap）：用物件查出這個物件的所有屬性，再用屬性查出讀過它的 effect。

為什麼不能只用屬性名稱當鍵，省掉最外層？因為點餐頁上不只一個物件有 qty：拿鐵的品項有 qty，伯爵紅茶的品項也有 qty。只用 'qty' 當鍵，改紅茶的杯數會讓所有讀過拿鐵杯數的 effect 一起重跑。所以要先用物件分開，再用屬性分開。

每一層用的容器也都有理由：

  • 最內層用 Set：同一個 effect 讀 cart.qty 兩次（例如小計裡寫了 cart.qty * cart.price，又在判斷式裡讀一次），只要記一次。Set 會自動去掉重複，trigger 時就不會讓同一個 effect 重跑兩次。
  • 中間用 Map：屬性名稱可能是字串，也可能是 Symbol，Map 都能當鍵。
  • 最外層用 WeakMap：這一層的鍵是物件本身，選 WeakMap 是為了記憶體，下面講清楚。

先講垃圾回收（garbage collection）。TS 課第 2 課講過，JavaScript 引擎會自動找出「已經沒有任何變數或物件參照到」的物件，把它佔的記憶體釋放掉。反過來說，只要還有一個地方參照著某個物件，它就永遠不會被釋放。

如果最外層用 Map，Map 本身就是一個參照：購物車物件放進依賴表之後，就算頁面上已經沒有任何程式在用這個購物車，Map 還抓著它，它和它底下整份依賴都不會被回收。使用者在點餐頁來回切換，每次產生的新物件都被留下來，頁面開越久，記憶體越大。這種「不再需要的記憶體一直釋放不掉」的情況叫記憶體洩漏（memory leak）。

WeakMap 的鍵不算參照，垃圾回收判斷「還有沒有人用這個物件」時不會把 WeakMap 算進去。購物車物件沒人用之後可以被回收，依賴表裡那一筆也跟著消失。代價是 WeakMap 不能遍歷、沒有 size，但依賴表只需要「拿物件查資料」，用不到這些。Vue 官方文件〈Reactivity in Depth〉描述的也是這個結構：WeakMap<target, Map<key, Set<effect>>>。

💡 實務上：自己寫「以物件為鍵」的快取時，先想 WeakMap
你自己的程式也常需要「替某個物件附加資料」，例如咖啡店後台替每筆訂單物件快取格式化後的明細，或記錄某個 DOM 元素綁過哪些事件。用 Map 存，訂單列表換頁後舊物件仍被 Map 抓住，後台開一整天記憶體就越來越大，這類洩漏很難從畫面上看出來。鍵是物件、而且資料應該跟著物件一起消失時，用 WeakMap。反過來，鍵是字串或數字（例如訂單 id），或你需要列出全部項目、計算數量時，WeakMap 做不到（它不能遍歷），這時用 Map 並自己決定何時刪除。

activeEffect 告訴 track「是誰」，依賴表告訴 trigger「找誰」。兩塊都有了，可以把第一版寫出來，看小計是不是真的會自動重印。

第一版：改 cart.qty，小計真的會自動重印嗎？

第一版要寫四個東西：

  • reactive：沿用第 1 課的 Proxy，只多兩行。get 裡先呼叫 track(target, key) 再回傳值。set 裡先寫入，再判斷值有沒有真的改變，有改變才呼叫 trigger(target, key)：值沒變，畫面本來就不用動，通知只是白跑。比較新舊值用 Object.is 而不是 ===，差別在 NaN：NaN === NaN 是 false，用 === 會把「NaN 改成 NaN」當成改變。為了專心在依賴追蹤，這一課的 reactive 只包一層，巢狀物件的處理第 1 課做過了。
  • track：沒有 activeEffect 就直接回傳；有的話，從依賴表一層一層找到 target、key 對應的 Set，沒有就建立，再把 activeEffect 加進去。
  • trigger：從依賴表找出 Set，讓裡面每個 effect 執行 run()。
  • effect：把傳進來的函式包成一個物件，它的 run() 做上一節說的三件事：設定 activeEffect、執行函式、清掉 activeEffect。建立時要立刻執行一次，因為依賴是執行時才收集的，一次都沒跑過的 effect，依賴表裡沒有它，之後改什麼都不會通知它。

按「執行」，看三件事：依賴表裡記了什麼；改 qty 時誰重跑；改成同樣的價格、改沒人讀過的 note 時，是不是都沒有 effect 重跑。

結果裡有兩個值得注意的地方：

  • 依賴表的鍵是 raw（原物件），不是 proxy：trap 收到的 target 就是原物件，所以範例最後用 targetMap.get(raw) 才查得到。
  • 改 note 沒有任何 effect 重跑，因為沒有 effect 讀過它，依賴表裡根本沒有 note 這一格。這就是「精準更新」：資料改了，只有真的讀過它的 effect 會重跑。放到 Vue 裡，就是只有用到這筆資料的元件會重新渲染，其他元件完全不受影響。

第一版在這個例子裡運作正常，原因是小計和徽章每次執行讀的屬性都一樣。點餐頁上不是每一塊都這麼單純，有些區塊會依條件讀不同的屬性，第一版遇到這種區塊就會開始白跑。

品項售完之後，改價格為什麼還在重跑？

點餐頁上每個品項有一個價格標籤：有貨時顯示價格，售完時顯示「售完」。用 item.show 表示有沒有貨：

effect(() => {
  label = item.show ? `${item.price} 元` : '售完'
})

一步一步看第一版的依賴表怎麼變：

  1. 建立時執行一次。show 是 true，所以讀了 show，也讀了 price。依賴表記下 show → {標籤}、price → {標籤}。
  2. 拿鐵賣完，item.show = false。標籤重跑，這次只讀了 show，三元運算子的另一邊沒有執行，price 沒被讀到。
  3. 可是第一版的 track 只會往 Set 裡加東西，從來不刪。price → {標籤} 那一筆還在。
  4. 之後老闆調整拿鐵的價格，標籤又重跑一次，畫面上照樣是「售完」，這次執行完全是白費的。

effect 每次執行走的分支可能不一樣，讀到的屬性也就不一樣。這叫分支切換（branch switching）的問題：依賴應該是「這一次執行讀到的東西」，而不是「歷來讀過的所有東西的聯集」。這裡只是多印一次 log，但放到 Vue 裡，白跑一次就是元件多渲染一次；如果 effect 做的是發請求，就是多打一次 API。舊的 Set 也會一直抓著這個 effect，跟上一節的記憶體問題是同一類。

修法是每次重新執行之前，先把這個 effect 從所有 Set 裡移除，執行時讀到什麼再加回去。問題是：effect 怎麼知道自己在哪些 Set 裡？依賴表的方向是「屬性 → effect」，要反查「這個 effect 在哪些屬性的 Set 裡」，得把整張表掃一遍，而 WeakMap 連遍歷都做不到。

所以讓 effect 自己反向記一份：每個 effect 多一個 deps 陣列，track 把 effect 加進某個 Set 的同時，也把這個 Set 推進 effect.deps。重新執行前，照著 deps 把自己從每個 Set 刪掉，再清空 deps，這個動作叫 cleanup。接著執行函式，這次讀到的屬性會重新加回來。這次讀到什麼，依賴就是什麼。

type Effect = { run(): void; deps: Set<Effect>[] }

function cleanup(e: Effect) {
  for (const dep of e.deps) dep.delete(e)
  e.deps.length = 0
}
// track 裡：dep.add(activeEffect) 之後再 activeEffect.deps.push(dep)
// run 裡：先 cleanup(e)，再設定 activeEffect、執行 fn

注意 cleanup 用的是 dep.delete(e)，只刪掉自己。同一個 Set 裡可能還有別的 effect，例如 price 的 Set 裡除了標籤，還有小計；清空整個 Set 會讓小計也收不到通知。

加了清理之後，trigger 會出現一個新陷阱。trigger 原本用 dep.forEach(e => e.run()) 遍歷 Set，而 run 會先把 e 從這個 Set 刪掉，執行函式時又把 e 加回同一個 Set。JavaScript 規定 Set 在 forEach 期間新加入的元素也會被走到，於是「刪掉、加回、又被走到、又刪掉、又加回」永遠停不下來，變成無窮迴圈。所以 trigger 要先複製一份再遍歷：[...dep].forEach(e => e.run())。複製出來的陣列在遍歷開始時就固定了，run 怎麼改原本的 Set 都不影響它。

清理解決了「白跑」：依賴永遠只有這一次讀到的屬性。接下來是相反的問題：該重跑的 effect 卻沒有重跑，而且它出現在 Vue 最常見的結構裡，也就是一個區塊包著另一個區塊。

店面區塊裡放了菜單區塊，為什麼外層不再更新？

Vue 的父元件渲染時會建立子元件，子元件的渲染函式也是 effect，所以「effect 執行到一半，裡面又建立並執行另一個 effect」在 Vue 裡隨處可見，這叫巢狀 effect。點餐頁的店面區塊就是這樣：外層顯示「營業中」提示，讀 shop.open；裡面放著菜單區塊，讀 shop.menu。

effect(() => {          // 外層：店面
  effect(() => { … shop.menu … })   // 內層：菜單。結束時 activeEffect = undefined
  console.log(shop.open)            // 這個讀取已經沒人記了
})

照第一版的 run 走一遍，看 activeEffect 怎麼變：

  1. 外層開始執行，activeEffect 設成外層。
  2. 外層建立內層，內層的 run 把 activeEffect 設成內層，讀 shop.menu，記給內層，正確。
  3. 內層執行完，run 的最後一行把 activeEffect 設成 undefined。
  4. 回到外層繼續執行，讀 shop.open。這時 activeEffect 是空的，track 直接回傳，什麼都沒記。

結果是店家打烊、shop.open 改成 false 時，外層不會重跑，畫面還寫著「營業中」。問題出在第 3 步：內層結束時應該把 activeEffect 還原成「進來之前的那一個」，也就是外層，而不是一律清空。

「後進來的先離開，離開時回到前一個」，這種存取順序叫堆疊（stack），這裡需要的就是一個 effect 堆疊（effect stack）：進入 effect 時把它疊上去，結束時拿掉，最上面那個就是目前的 activeEffect。不用真的建一個陣列，函式呼叫本身就是堆疊：在 run 裡用區域變數 prev 記住進來時的 activeEffect，結束時還原它。每一層 run 各有自己的 prev，巢狀幾層都能一層一層退回去。Vue 原始碼也是這樣做，用 prevEffect 存外層：

run() {
  cleanup(e)
  const prev = activeEffect
  activeEffect = e
  try {
    fn()
  } finally {
    activeEffect = prev    // 就算 fn 丟錯，也要還原外層
  }
}

為什麼要包 try／finally？如果 fn 執行到一半丟出錯誤，沒有 finally 的話，還原那一行不會執行，activeEffect 會一直指著這個已經結束的 effect。之後任何 effect 外面的讀取都會被記到它身上，它開始為不相干的屬性重跑，這種 bug 跟最初的錯誤距離很遠，很難查。finally 保證不管正常結束還是丟錯，都會還原。

巢狀 effect 還有一個迷你版沒處理的問題（外層重跑時會重建內層），Vue 用元件與 effect scope 解決，細節見課末「補充與查表」。還原外層之後，run 管理 activeEffect 的方式就完整了。但還有一種寫法，會讓 effect 一路呼叫自己停不下來：effect 改到自己讀的資料。

effect 改到自己讀的資料，為什麼會當掉？

假設點餐頁要記錄「這個區塊執行了幾次」，有人寫了 effect(() => { state.count++ })。state.count++ 看起來是一個動作，其實是兩個：先讀 state.count，再把加一之後的值寫回去。

  1. 讀：get trap 呼叫 track，activeEffect 是這個 effect，於是它被記進 count 的 Set。
  2. 寫：set trap 發現值變了，呼叫 trigger，trigger 從 count 的 Set 找到的正是這個 effect，叫它 run()。
  3. 重跑時又是一讀一寫，又觸發自己，一層疊一層。

每一次 run 都還沒結束就呼叫下一次 run，函式呼叫一直往呼叫堆疊上疊，直到 JavaScript 引擎的堆疊空間用完，丟出 RangeError: Maximum call stack size exceeded。這叫自我觸發。

修法：trigger 跳過「正在執行的那個 effect」，也就是只在 e !== activeEffect 時才執行。道理是：這個 effect 此刻正在執行，從它自己裡面再叫它重跑一次，除了無限遞迴沒有別的結果。之後從 effect 外面改 count，那時 activeEffect 不是它，trigger 照常讓它重跑。Vue 的 effect 行為相同：effect(() => state.count++) 只執行一次，之後從外面改 count 才會再跑（驗證版本見課末）。

這個防護只擋得住「一個 effect 寫自己讀的資料」。兩個 effect 互相寫對方讀的資料，trigger 看到的 activeEffect 是另一個，擋不住，就會來回觸發。實務上碰到的多半是這一種：

💡 實務上：能用 computed 算出來的值，就不要在 effect 裡寫回去
新手常寫 watchEffect(() => { order.total = order.qty * order.price })，把算出來的值寫回響應式資料。一個 effect 寫自己讀的資料，Vue 會擋住；但兩個 watcher 互相寫對方讀的資料，就會來回觸發，輕則多跑好幾次，重則停不下來（開發模式下 Vue 會中斷並在 console 報警告）。這種「由別的資料推導出來的值」應該用 computed（下一課），effect／watch 留給真正的副作用：打 API、寫 localStorage、操作 DOM。Code review 看到 watch 裡在改另一份狀態，資深工程師通常會先問：這個值能不能改成 computed？

到這裡，迷你版不漏跑、不白跑、不當掉了。但 trigger 仍然是一被呼叫就「立刻」重跑 effect，點餐頁一次改好幾個屬性時，這會變成效能問題。

一次改了三個屬性，畫面要重畫三次嗎？

使用者在點餐頁按「套用上次的訂單」，程式一口氣改了 cart.qty、cart.price、cart.note。小計讀了前兩個，所以照目前的寫法會連續重跑兩次，而且第一次算出的是「新杯數乘舊價格」，是個用不到的中間值。瀏覽器要等同步程式跑完才繪製，使用者看不到它，但這次計算、這次 DOM 更新都白做了；如果 effect 會發請求，還會帶著不一致的資料打出去。換成元件渲染，就是一次點擊讓渲染函式跑好幾遍、DOM 改好幾次，只有最後一次有意義。

問題在於 trigger 把兩件事綁在一起：「知道要重跑」和「立刻重跑」。Vue 裡很多地方需要把這兩件事拆開：

  • 元件渲染：同一個事件裡改了 10 個屬性，畫面只該更新一次（第 6 課的批次更新）。
  • computed：依賴改了，先標記「過期」，等有人讀才重算（第 3 課）。
  • watch：比對新舊值之後才呼叫你的 callback（第 5 課）。

做法是讓 effect 可以帶一個排程器（scheduler）：一個由建立 effect 的人提供的函式。有 scheduler 的 effect 被觸發時，trigger 不直接執行它，而是把「重新執行」包成一個 job 交給 scheduler，要不要跑、什麼時候跑，由 scheduler 決定。沒有 scheduler 的 effect 行為不變，照樣立刻重跑。

下面這個 scheduler 做的是批次：第一次被觸發時，排一個「等目前的同步程式跑完再執行」的工作，之後的觸發看到已經排過就直接略過。「等同步程式跑完」用的是 Promise.resolve().then(...)：TS 課第 7 課講過，.then 的 callback 是 microtask，要等目前這段同步程式全部執行完才會跑，那時三個屬性都已經改好了。

let pending = false
effect(fn, {
  scheduler(job) {
    if (pending) return                    // 已經排過了，這次寫入不用再排
    pending = true
    Promise.resolve().then(() => {         // 等目前的同步程式跑完
      pending = false
      job()                                // 連續寫入 3 次，fn 只重跑 1 次
    })
  },
})
// trigger 裡：e.scheduler ? e.scheduler(() => e.run()) : e.run()

job 一定要呼叫 e.run()，不能直接呼叫 fn。run 才會清理舊依賴、設定 activeEffect、重新收集依賴；直接呼叫 fn，activeEffect 不是這個 effect，等於在 effect 外面讀資料，什麼都不會被記住。Vue 的 effect() 也有 scheduler 選項，呼叫方式跟迷你版略有不同，見課末。

scheduler 讓「重跑」可以延後，但「追蹤」這一半仍然綁在 run 的同步執行期間。這個限制在 effect 裡寫非同步程式時最容易出事。

為什麼 await、setTimeout 之後讀的值不會被追蹤？

回頭看 run：設定 activeEffect、執行 fn()、還原。fn() 一回傳，activeEffect 就不是這個 effect 了。TS 課第 7 課講過，setTimeout 的 callback 和 await 之後的程式，都要等目前的同步程式跑完才執行。那時 fn() 早就回傳了，在那裡讀屬性，get trap 照樣被呼叫，但 track 看到的 activeEffect 是空的，什麼都不記。追蹤看的是「讀取發生的時間」，不是「程式碼寫在 effect 的大括號裡面」。

按「執行」，看兩次印出的執行次數：改 qty 之後次數不變，改 price 之後才增加。

price 是在 effect 同步執行時讀的，被追蹤了；qty 是在 setTimeout 的 callback 裡讀的，雖然寫在 effect 的函式裡面，執行時 effect 早已結束，所以沒被追蹤。

Vue 的 watchEffect 是同一條規則，官方文件寫明它只在同步執行期間追蹤依賴，async callback 只有第一個 await 之前讀的屬性會被追蹤。實務上的做法有兩種：要追蹤的值在 await 之前先讀出來存成區域變數；或改用明確指定來源的 watch（第 5 課），由你直接告訴 Vue 要看哪些值，不靠執行時收集。

💡 實務上：「切換分店後列表沒重抓」常是 await 後才讀條件
典型場景：咖啡店後台的訂單列表，在 watchEffect(async () => { await checkLogin(); list = await fetchOrders(filter.storeId) }) 裡抓資料。第一次載入正常，但切換分店時不會重抓，因為 filter.storeId 是在 await 之後才讀，根本沒被追蹤。這種 bug 在開發時不容易發現，因為重新整理頁面一切正常，常常是客服回報「切換後資料沒變」才被注意到。打 API 這類非同步工作，團隊多半直接用 watch 明確列出來源，看程式碼就知道「哪些條件變了會重抓」，review 時也比較好檢查。

迷你版該有的部分到這裡都齊了：track 和 trigger、每次重跑前的清理、還原外層與自我觸發的防護、scheduler。最後把它跟真正的 Vue 放在一起比，看哪些是一樣的，哪些是 Vue 多做的。

練習

四題一步一步把迷你版補完，每一題的起始程式都是前一題的答案加上新的 TODO。

練習 1：完成 track、trigger、effect。要求：effect(fn) 建立時立刻執行一次；改到 fn 讀過的屬性時重新執行；改到沒讀過的屬性（包括另一個物件的同名屬性）不執行；effect 外面的讀取不記錄。reactive 已經寫好（同值寫入不會呼叫 trigger）。

練習 2：加入清理。Effect 多了 deps：記錄自己在哪些 Set 裡。完成 cleanup，並修改 track、trigger、run：每次重新執行前先把自己從所有 Set 移除再重新收集；trigger 遍歷前先複製一份 Set。完成後，show 為 false 時改 price 不會重跑。

練習 3：支援巢狀 effect 與自我觸發。修改 run：結束時還原外層的 activeEffect（用區域變數記住外層，並用 try／finally 確保 fn 丟錯也會還原）；修改 trigger：跳過正在執行的 effect，讓 effect(() => state.count++) 只執行一次。

練習 4：加入 scheduler 選項。effect(fn, { scheduler })：被觸發時呼叫 scheduler(job)，不直接執行；之後呼叫 job() 才重新執行 fn，而且要重新收集依賴。沒有 scheduler 的 effect 行為不變。

練習 5：依賴表最外層為什麼用 WeakMap，而不是 Map？

✓ WeakMap 的鍵不算參照，購物車物件沒人用之後可以被回收，依賴表裡那一筆也一起消失。換成 Map，執行結果看起來一樣，但每個用過的物件都會永遠留在記憶體裡，頁面開越久越大，所以 a 錯。WeakMap 的重點不是速度（c），Map 也能用物件當鍵（d），只是它會阻止回收。

練習 6：effect(() => { setTimeout(() => console.log(cart.qty), 0) })，之後執行 cart.qty = 3，effect 會重跑嗎？

✓ 追蹤靠的是「讀取當下 activeEffect 是誰」。effect 同步跑完就還原 activeEffect，setTimeout 的 callback 之後才執行，讀取時沒人可記。追蹤看的是讀取發生的時間，不是程式寫在哪裡，所以 a、b 錯。Proxy 其實攔截得到（get trap 有被呼叫），只是 track 發現沒有 activeEffect 而不記，所以 d 錯。Vue 的 watchEffect 遇到 await 也是一樣。

練習 7：為什麼 effect 每次重新執行前要清掉舊依賴？

✓ 依賴應該是「這次執行讀到的東西」。show ? price : '售完' 在 show 為 false 時不讀 price，舊依賴留著，改 price 就多跑一次；在元件裡就是多一次沒必要的渲染，effect 做的事越重（發請求、改 DOM）代價越大，所以 c 錯。不清理是「跑太多」而不是「不跑」，所以 b 錯。

常見錯誤

  • 依賴表外層用 Map：每個用過的物件都被抓住，不再使用也無法被垃圾回收，頁面開越久記憶體越大。用 WeakMap。
  • trigger 直接遍歷依賴 Set：加了清理之後，run 會從同一個 Set 刪掉再加回自己，forEach 會一直走到新加入的元素，無窮迴圈。先 [...dep] 複製一份。
  • effect 結束時把 activeEffect 設成空的，而不是還原外層：巢狀時外層後半段的讀取沒被記到，外層該重跑卻不跑。用區域變數記住外層，在 finally 裡還原。
  • effect 修改自己讀的屬性，沒有防護：讀了又寫，trigger 叫自己重跑，無窮遞迴到 RangeError。trigger 要跳過正在執行的 effect。
  • scheduler 的 job 直接呼叫 fn：沒有經過 run，依賴沒被重新收集，之後的寫入不再觸發。job 要呼叫 run()。
  • 以為 await、setTimeout 之後的讀取也會被追蹤：追蹤只在同步執行期間。要追蹤的值在 await 之前讀，或用明確指定來源的 watch。

小結

這一課把第 1 課只會印 log 的 Proxy，做成讓點餐頁自動更新、而且不漏跑、不白跑、不當掉的迷你響應式系統：

  • 響應式系統三步：effect 執行時設定 activeEffect；get 裡 track 把它記進依賴表；set 裡 trigger 找出依賴的 effect 重新執行。
  • 依賴表是 WeakMap<物件, Map<屬性, Set<effect>>>，先用物件、再用屬性分開；外層用 WeakMap 讓物件能被回收。
  • 不白跑：依賴每次重新收集，重跑前用 effect.deps 把自己從所有 Set 移除；trigger 先複製再遍歷。
  • 不漏跑：巢狀 effect 結束時還原外層的 activeEffect，用 try／finally 保證丟錯也會還原。
  • 不當掉：trigger 跳過正在執行的 effect，避免自我觸發的無窮遞迴；推導出來的值用 computed，不要在 effect 裡寫回去。
  • scheduler 決定「什麼時候重跑」，是 computed、watch、批次更新的基礎；job 要呼叫 run 才會重新收集依賴。
  • 追蹤只發生在 effect 同步執行期間，setTimeout、await 之後的讀取不算。

迷你版沒處理的巢狀問題：外層重跑時會重建內層

迷你版的外層 effect 每次重跑都會再呼叫一次 effect(...)，建立一個新的內層；舊的內層還留在依賴表裡，之後改 shop.menu，新舊兩個內層都會跑。Vue 的父元件重新渲染時不會重建子元件，而是更新它。子元件裡的 effect 都收在元件自己的 effect scope 裡：effect scope 是一個收集 effect 的範圍，可以一次把裡面的 effect 全部停掉（第 5 課）。元件卸載時，它的 effect scope 會一起停掉（第 8 課）。

Vue 的 scheduler 呼叫方式

Vue 的 effect() 也有 scheduler 選項，本機用 3.5.44 驗證過：連續寫入兩次，scheduler 被呼叫兩次、effect 本身不執行。差別是 Vue 呼叫 scheduler 時不傳參數，由 scheduler 自己決定要不要呼叫 effect 的 run()；迷你版把 job 傳進去，是為了讓「重跑要經過 run」看得清楚。

自我觸發的驗證版本

本機用 Vue 3.5.44 的 @vue/reactivity 驗證過：effect(() => state.count++) 只執行一次，之後從外面改 count 才會再跑。

Vue 響應式系統的版本變化

Vue 3.5 起，依賴表改用版本號（version counting）與雙向鏈結串列，重跑時重用舊的節點，不再像迷你版一樣全部清掉再收集。Vue 3.5 的官方公告說，響應式系統重構後記憶體用量減少 56%，行為沒有改變。Vue 3.6 從 2026 年 7 月的 3.6.0-rc.1 起進入 RC，到 2026 年 10 月還沒有正式版（npm 的 latest 仍是 3.5.44），@vue/reactivity 在 3.6 以 alien-signals 重寫。資料結構一直在換，但主線講的觀念沒變。
