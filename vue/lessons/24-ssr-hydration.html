階段 7：品質、效能與架構 · 第 24 課

渲染策略：CSR、SSR、SSG 與 hydration

咖啡店的行銷同事提了兩個需求：「門市與菜單」頁要能被 Google 搜到、貼到 LINE 群組要有預覽圖；顧客用手機打開首頁，白畫面要等好一陣子才出現內容。有人提議「整站改成伺服器渲染」。改完上線，第一天就出了三個事故：首頁在伺服器上直接丟錯；營業狀態一下顯示「休息中」、一下又變成「營業中」；最嚴重的是陳美華打開購物車，看到王小明剛放進去的拿鐵。

這課從頭走一遍這個決定：先判斷門市頁到底需不需要伺服器渲染，再弄懂伺服器產生的 HTML 怎麼交給瀏覽器接手，接著依序修好三個事故，最後決定正式專案要自己做還是交給 Nuxt。範例使用 Vue 3.5.44。

這課的路線：
  1. 門市頁要被搜到，一定要改成 SSR 嗎：CSR、SSR、SSG 各在哪裡、什麼時候產生 HTML，各付出什麼代價。
  2. 伺服器的 HTML 怎麼變成按得動的頁面：renderToString 與 hydration，三個事故各出在哪一步（開場問題的最小答案）。
  3. 首頁為什麼丟錯、「營業中」為什麼閃動：伺服器上的元件只執行到哪裡，伺服器和瀏覽器的第一次渲染為什麼必須一樣。
  4. 陳美華為什麼看到王小明的拿鐵：伺服器上的模組層級狀態被所有人共用，怎麼讓每個請求有自己的一份。
  5. 看得到卻按不動、正式上線怎麼做：延遲 hydration，以及自己做 SSR 還是用 Nuxt。
這課會用到：
  • 第 7 課的虛擬 DOM 與 patch：render 產生描述畫面的 JavaScript 物件（虛擬 DOM），Vue 比對新舊兩份，只改真正不同的 DOM。
  • 第 8 課的生命週期：setup（Options API 是 created）在建立元件時執行，onMounted 等元件放進真的 DOM 之後才執行。

門市頁要被搜到，一定要改成 SSR 嗎？

要回答這個問題，先看清楚一件事：使用者看到的畫面，它的 HTML 是在哪裡、什麼時候產生的。產生的地點和時機不同，就是三種渲染方式的差別。

到目前為止的咖啡店都是 CSR，客戶端渲染（client-side rendering）。伺服器回傳的 HTML 幾乎是空的，只有一個 <div id="app"></div> 和一個 JavaScript 檔的連結。瀏覽器要先下載、執行 JavaScript，Vue 再去呼叫 API 拿資料，最後才把畫面畫出來。第 19 課的 SPA 就是這樣運作的。好處是伺服器只要放靜態檔案；代價是在 JavaScript 跑完之前，使用者看到的是白畫面，而只讀 HTML 的程式（例如社群平台的預覽）看到的也是一個空的 div。

SSR 是伺服器端渲染（server-side rendering）。每次收到請求，伺服器上的 Node 程序先執行 Vue 元件，產生一份已經有內容的 HTML 回傳。使用者一收到就看得到內容；接著 JavaScript 下載完，Vue 在瀏覽器裡接手這份 HTML，按鈕才按得動。代價是要多維運一台一直開著的 Node 伺服器，每個請求都要花它的 CPU。

SSG 是靜態網站產生（static site generation），也叫預先渲染（prerender）。它在建置（build）時就把每一頁的 HTML 產生好，部署成一般的靜態檔案，之後的請求不用執行任何程式。靜態檔案可以放上 CDN：CDN 是內容傳遞網路（content delivery network），一群分散在各地的伺服器，使用者向離自己最近的節點拿檔案，所以回應最快。代價是內容停在上次建置的那一刻，要更新就得重新建置。

比較三者時要用兩把尺。第一把是 TTFB，首位元組時間（time to first byte）：從瀏覽器發出請求，到收到回應的第一個位元組花了多久。SSR 要等伺服器抓完資料、渲染完才開始回傳，TTFB 通常比直接回傳靜態檔案晚。第二把是 SEO，搜尋引擎最佳化（search engine optimization）：讓搜尋引擎讀得到、正確收錄頁面內容。CSR 的 HTML 裡沒有內容，要靠爬蟲願意執行 JavaScript；SSR 和 SSG 的 HTML 一開始就有內容。下圖把三種方式放在同一條時間軸上：

回到開場的提議。資深工程師的判斷是：SSR 不是「比較好的 CSR」。它多了一台要維運的 Node 伺服器、多了一整類 bug（這課後面全部都是），也限制了程式能怎麼寫。店員用的訂單後台需要登入、不需要被搜尋，第一次載入慢一點大家也能接受，用 CSR 就好。對外的菜單、門市頁才值得考慮 SSR 或 SSG，而且同一個網站可以混用：門市介紹 SSG、商品頁 SSR、會員區 CSR。至於手機白畫面，先照第 23 課的方法量測：原因常常是 JavaScript 太大，切分程式碼就解決了，不需要動渲染方式。

💡 實務上：先問清楚「誰要看到這份 HTML」
這類需求最常從行銷來：「菜單連結貼到 LINE 群組沒有預覽圖」「Google 搜不到門市頁」。社群平台產生分享預覽時，通常只讀 HTML 裡的 og:title、og:image 等 meta，不會等 JavaScript 執行，所以 CSR 頁面常常只顯示網站預設的標題。資深工程師會先問三件事：哪幾頁真的要被搜尋或分享、內容多久變一次、誰負責維運那台 Node 伺服器。答案常常是「只有門市和菜單頁」，做成 SSG 就夠了，不必整站改 SSR。

這次團隊的結論是分頁處理：門市與菜單頁內容不常變，用 SSG，建置時就產生好 HTML；首頁要顯示即時的營業狀態，又要被搜尋，只能用 SSR；訂單後台維持 CSR。開場的三個事故，都出在改成 SSR 的首頁上。要看懂它們，得先回答一個問題：伺服器送出的只是一段 HTML 字串，它要怎麼變回那個按得動的 Vue app？三個事故都發生在這個交接的過程裡。

伺服器的 HTML，怎麼變成按得動的頁面？

Vue 的 SSR 分成兩半，分別在伺服器和瀏覽器執行。先看伺服器那一半：用 vue/server-renderer 的 renderToString() 把 app 渲染成 HTML 字串。兩邊都用 createSSRApp 建立 app，原因在看完瀏覽器那一半就會清楚。

// server.ts（Node，每個請求執行一次）
import { createSSRApp } from 'vue'
import { renderToString } from 'vue/server-renderer'
import App from './App.vue'

const app = createSSRApp(App)
const html = await renderToString(app)   // '<section><h2>營業時間…'
// 把 html 放進頁面範本的 <div id="app">…</div> 裡回傳，再加上 <script src="/client.js">

這份 HTML 送到瀏覽器，使用者馬上看得到營業時間和菜單。但它只是瀏覽器把一段文字解析出來的 DOM：上面沒有任何事件監聽，按「加入購物車」不會有反應；Vue 也不知道哪個節點對應哪個 ref，資料改了畫面不會跟著變。要讓它活起來，瀏覽器還得再執行一次 Vue。

最直覺的做法是照 CSR 的寫法 createApp(App).mount('#app')。問題是一般的 mount 會先清空容器，再建立自己的 DOM（Vue 3.5.44 的 runtime-dom 在掛載前把容器的 textContent 設成空字串）。伺服器辛苦產生的 DOM 被整個丟掉重建，SSR 等於白做，畫面還會閃一下。所以瀏覽器那一半要用同一個元件，改用 createSSRApp（不是 createApp）掛載到那個已經有內容的容器：

// client.ts（瀏覽器）
import { createSSRApp } from 'vue'
import App from './App.vue'

createSSRApp(App).mount('#app')

這一步叫 hydration（水合）。名字的意思是：伺服器送來的是「乾」的 HTML，只有結構沒有行為，瀏覽器把狀態和事件「注入」進去。具體的過程是：Vue 在瀏覽器裡照樣執行每個元件的 setup 和 render、產生虛擬 DOM，但不建立新的 DOM，而是拿虛擬 DOM 逐一對照伺服器給的 DOM 節點，把它們認領下來、掛上事件監聽。完成後，這個 app 就和一般 CSR 的 app 一樣，之後的更新照第 7 課的 patch 進行。

「認領」而不是「重建」，帶來一個前提：瀏覽器第一次渲染的結果，必須和伺服器的 HTML 一樣。假設 Vue 在瀏覽器算出「營業中」，DOM 上卻寫著伺服器算的「休息中」，它就得決定要信哪一邊。這種情況叫 hydration mismatch（水合不一致）。開發模式下 Vue 會發出警告，指出是哪個元素、兩邊各是什麼值。例如首頁電話欄位的 id 兩邊不同時，Vue 會印出：

[Vue warn]: Hydration attribute mismatch on <input id="phone-xhr9d64qimg" type="tel">
  - rendered on server: id="phone-xhr9d64qimg"
  - expected on client: id="phone-1omj4b56ng7"
  Note: this mismatch is check-only. The DOM will not be rectified in production due to performance overhead.
  You should fix the source of the mismatch.

這個 id 是怎麼來的，修第二個事故時會回來看。

Vue 遇到不一致時的處理方式，依不一致的種類而不同：

  • 屬性不一致（像上面的 id）：只檢查、不修正。DOM 留著伺服器的值，元件卻以為是另一個值，畫面和狀態從此對不上。注意警告裡 Note 那一行：正式建置預設連檢查都不做，完全沒有訊息。
  • 文字或節點不一致：Vue 改用瀏覽器算出的內容，文字直接換掉、節點整段重建。正式建置也會在 console 印出一行沒有細節的 Hydration completed but contains mismatches.；開發模式下兩種不一致都會印這一行。

兩種都是 bug：前者畫面和狀態對不上，後者白做了那一段 SSR，使用者還會看到內容閃一下才變。

知道 SSR 的兩半之後，開場的三個事故都找得到位置。第一個發生在伺服器那一半：伺服器上沒有 window，元件在伺服器碰到它就丟錯，HTML 根本產生不出來。第二個發生在兩半的交接：伺服器和瀏覽器各算一次畫面，用到「現在時間」的營業狀態兩邊算出不一樣，就是剛才說的 hydration 不一致。第三個也在伺服器那一半，但原因不同：伺服器是一個程序服務所有人，寫在模組最外層的購物車被大家共用。接下來三節依序修它們，先從最直接的第一個開始：伺服器在產生 HTML 的途中就丟錯了。

首頁為什麼在伺服器上丟錯？伺服器只執行到產生 HTML 為止

丟錯的是首頁的 StoreHours.vue。它要依螢幕寬度決定顯示內容，起始寫法在 setup 裡直接讀視窗寬度：

const width = ref(window.innerWidth)   // 伺服器上：ReferenceError: window is not defined

這行在瀏覽器裡沒問題，因為 window、document、localStorage 是瀏覽器提供的，不是 JavaScript 語言本身的一部分。伺服器上的 Node 沒有它們，一讀就丟出 ReferenceError，整頁渲染失敗，使用者拿到一個錯誤頁。

要判斷哪些程式碼會在伺服器上跑、哪些不會，得先知道伺服器上的元件在做什麼。它只有一個任務：產生 HTML。伺服器上沒有真的 DOM，元件不會被「放進畫面」，也就沒有「掛載」這件事。所以它只執行到這裡：

在伺服器上會執行不會執行
Composition APIsetup、render（template）、onServerPrefetchonBeforeMount、onMounted、onUpdated、onUnmounted 等所有掛載之後的鉤子
Options APIbeforeCreate、created、serverPrefetchmounted 之後的鉤子
響應式ref、computed 照常計算出值Vue 預設在 SSR 關閉響應式追蹤：資料改變不會重新渲染（HTML 已經送出去了）

setup 和 template 兩邊都會執行，onMounted 只在瀏覽器執行。所以讀 window 的程式要從 setup 搬出去。

搬之前，先看一個很多人會先試的修法：typeof window === 'undefined' ? null : window.innerWidth。伺服器不再丟錯了，但伺服器算出 null（不顯示寬度那一行），瀏覽器 hydration 時算出 1024（顯示那一行），兩邊第一次渲染的結果不一樣，正好就是上一節的 hydration 不一致。錯誤沒有消失，只是從「伺服器丟錯」變成「畫面閃動」。

正確的做法是讓兩邊第一次渲染都用同一個值，等掛載之後再改：

const width = ref<number | null>(null)   // 伺服器和 hydration 都是 null
onMounted(() => {
  width.value = window.innerWidth        // 只在瀏覽器、hydration 之後執行，之後照一般更新
})

hydration 時兩邊都是 null，對得上；hydration 完成後 onMounted 才執行，這時改 width 就是一般的響應式更新。代價是使用者會先看到沒有寬度的畫面，下一刻才出現。這是 SSR 的本質：只有瀏覽器知道的東西，伺服器的 HTML 裡就不會有。

把這個事故推廣開來，寫要在伺服器上執行的元件有三條規則：

  • setup 和 template 不碰瀏覽器 API：window、document、localStorage 在伺服器上不存在，要用就放進 onMounted，它只在瀏覽器執行。
  • 副作用放進 onMounted：在 setup 裡 setInterval、加事件監聽，伺服器上會真的建立它們，卻沒有 unmount 可以清掉，每個請求留下一個，記憶體一直長（第 8 課的練習 1 就是為了這個）。放在 onMounted 就只在瀏覽器建立，也一定有對應的 onUnmounted。
  • 伺服器要先拿到的資料用 onServerPrefetch：它可以回傳 Promise，伺服器會等它完成才渲染。抓到的資料要放進每個請求自己的狀態（例如 Pinia store），和 HTML 一起送到瀏覽器，hydration 時直接用，不要在瀏覽器再抓一次。這段「傳遞狀態」是自己做 SSR 最麻煩的部分之一，第三個事故那一節會再看到它。

第一個事故修好了，但修的過程也看到：比「丟錯」更難發現的，是伺服器和瀏覽器算出不同的畫面。第二個事故「營業中」閃動，就是這一類。

「營業中」為什麼一下有一下沒有？讓兩邊第一次渲染一樣

StoreHours.vue 的營業狀態是用 new Date() 取現在幾點，在 07:00 到 19:00 之間就顯示「營業中」。這行程式在伺服器和瀏覽器各執行一次，兩次之間有兩個差異。

第一個是時間。伺服器在 10:00:00.120 渲染，瀏覽器在 10:00:02.480 hydrate，中間隔了網路傳輸和 JavaScript 下載。剛好跨過整點、或顯示到分鐘的內容，兩邊就會不同。

第二個是時區，影響更大（TS 課第 6 課）。new Date() 拿到的是一個時間戳，getHours() 會用「執行環境的時區」把它換成小時。伺服器通常設在 UTC，台北的瀏覽器在 UTC+8，同一個時間戳算出的小時差 8 小時。下面用同一個時間戳在三個時區算小時，執行後比較三行的數字：

台北早上 10 點，UTC 的伺服器算出 2 點，判斷「休息中」，寫進 HTML；台北的瀏覽器 hydrate 時算出 10 點，判斷「營業中」。這是文字不一致，Vue 用瀏覽器的值換掉，於是使用者先看到「休息中」，一瞬間又變成「營業中」。換成紐約的顧客，瀏覽器算出 22 點，兩邊又是另一種組合。

修法有兩個方向，看這個值是誰的：

  • 由參數傳入同一個值：營業狀態是店的事實，不該依看的人而變。伺服器渲染時決定 now，序列化進頁面，瀏覽器 hydrate 時用同一個 now；計算時指定時區（營業時間是台北時間，就用 timeZone: 'Asia/Taipei'），不依賴執行環境的時區。這樣不管伺服器在哪、顧客在哪，兩邊算出的都一樣。怎麼把伺服器的值序列化進頁面、讓瀏覽器拿到，下一節修購物車時會一起處理。
  • 放到 onMounted：「現在幾分」這種只在使用者畫面上有意義的值，伺服器渲染一個中性的佔位，掛載後再算，和上一節的螢幕寬度是同一招。

時間只是「每次執行結果都不同」的一種。亂數是另一種：Math.random()、crypto.randomUUID() 每次執行都不同。最常踩到的地方是表單欄位的 id：首頁的 PhoneField.vue 用亂數產生 id，讓 label 和 input 對上，第二節那段警告訊息就是它，伺服器和瀏覽器各抽一次，當然不同。

id 有專門的工具：第 18 課用過的 useId()（Vue 3.5+）。它的計數器存在 app 裡：每個 app 從 0 開始，依元件執行 setup 的順序產生 id（例如 v-0、v-1）。伺服器和瀏覽器渲染的是同一棵元件樹、setup 順序相同，所以 id 一定相同；同一個元件出現兩次也不會重複。自己寫一個模組層級的計數器做不到：伺服器程序處理過其他請求，計數器早就不是 0 了，而瀏覽器是從 0 開始。

最後一種來源和程式無關，是 不合法的 HTML 巢狀，例如 <p><div>…</div></p>。HTML 規定 <p> 裡不能放 <div>，瀏覽器解析伺服器的 HTML 時會自動把 p 提早關掉，解析出來的 DOM 結構和 Vue 預期的不同。CSR 不會遇到，因為 Vue 是直接用 JavaScript 建立節點，不經過 HTML 解析。

有些不一致真的避免不了，例如顯示「使用者當地格式」的訂單時間，伺服器無從得知使用者的地區設定。Vue 3.5 起可以在元素上加 data-allow-mismatch，告訴 Vue 這裡的不一致是預期的。值可以限定為 text、children、class、style、attribute，不寫值就是全部允許：

<time data-allow-mismatch="text">{{ orderedAt.toLocaleString() }}</time>

它只是讓警告閉嘴，不會讓兩邊一致。只用在「確定不一致、而且不一致沒關係」的地方，不要拿來蓋掉自己的 bug；營業狀態就不該用它，因為兩邊不一致代表 HTML 裡寫的是錯的。

出問題時怎麼查：開發模式的警告會指出是哪個元素、伺服器和瀏覽器各是什麼值，照著看是時間、時區、亂數、瀏覽器 API 還是 HTML 巢狀。正式環境預設不印細節，要先在本機用正式建置重現，必要時打開細節（做法見課末「補充與查表」）。

💡 實務上：hydration 不一致常以「怪現象」的樣子被回報
客服收到的不會是「hydration mismatch」，而是「時間、數字閃一下就變了」「只有某些人的畫面怪怪的」。最後一種要想到使用者的環境：翻譯、廣告阻擋等瀏覽器擴充功能會在 hydration 前改動 DOM，這種警告不是你的 bug，先用無痕視窗確認能不能重現。團隊上的做法是把「渲染時不用 Date.now()、Math.random()、window」列進 code review 檢查項目，並在 CI 或上線前用正式建置跑一次 SSR 頁面、看主控台有沒有警告，比上線後追查便宜得多。

到這裡，兩個事故都屬於「畫面不對」。第三個事故不一樣：它把一個人的資料送到了另一個人的瀏覽器。

陳美華為什麼看到王小明的拿鐵？每個請求一份狀態

第三個事故最危險。起始的購物車寫在模組最外層，也就是第 12 課的模組層級狀態：所有 import 它的地方共用同一份。

// cart.ts
export const cart = reactive({ owner: '', items: [] as string[] })

在瀏覽器裡這樣寫沒問題：一個分頁就是一個使用者，模組載入一次，這個使用者用一份。換到伺服器，前提就變了：Node 程序只啟動一次，模組只載入一次，所有使用者的請求都在同一個程序裡處理。這份 cart 於是被每個請求共用。王小明的請求把拿鐵放進去，陳美華的請求渲染購物車時就讀到了它。這叫跨請求狀態污染（cross-request state pollution）：輕則畫面錯，重則把一個人的資料送到另一個人的瀏覽器。

第一個想到的修法通常是「每次渲染開始時，把共用的購物車清空、填上這個人的資料」。這只在請求一個接一個處理時成立。Node 在等資料庫回應（await）的空檔不會閒著，會去處理別的請求；等資料回來繼續往下執行時，共用的購物車可能已經被另一個請求改掉了。下面用純 JavaScript 模擬兩個同時進來的請求：王小明的請求等資料庫 20ms，陳美華的等 10ms。執行後比較兩行：第一行用共用的購物車，第二行每個請求自己一份。

第一行兩個結果都是「陳美華 的購物車：可頌」：王小明的請求清空、放進拿鐵之後去等資料庫，陳美華的請求趁這段時間又清空了一次、換成自己的資料，王小明的請求回來時讀到的已經是陳美華的購物車。第二行每個請求的購物車是自己函式裡的區域變數，別人碰不到，結果各自正確。

所以問題不在「有沒有清空」，而在「只有一份」。官方的做法是：每個請求建立一整套新的 app，包括 router 和 store，用 app 層級的 provide（第 13 課）交給元件，元件用 inject 取得，不直接 import 模組層級的狀態：

// create-app.ts（伺服器和瀏覽器共用）
export function createApp(owner: string) {
  const app = createSSRApp(App)
  const cart = reactive({ owner, items: [] })   // 每次呼叫都是新的
  app.provide(CART_KEY, cart)
  const pinia = createPinia()                   // 用 Pinia 的話：每個請求一個 pinia
  const router = createRouter({ history: createMemoryHistory(), routes })  // 伺服器上用 memory history
  app.use(pinia).use(router)
  return { app, cart, pinia, router }
}

伺服器每收到一個請求就呼叫一次 createApp，拿到一個全新的購物車；瀏覽器只呼叫一次，和 SPA 時一樣。這也是第 15 課說 Pinia 比模組層級 reactive 安全的原因：store 存在 pinia 實例裡，每個請求一個 pinia 就各自一份。

還剩一件事：伺服器在渲染時抓到的狀態，瀏覽器 hydration 時也要有，否則瀏覽器算出的畫面又和 HTML 不一樣了。Pinia 官方文件的做法是渲染後把 pinia.state.value 序列化，放進頁面裡的一段 <script>，瀏覽器在呼叫任何 useStore() 之前先還原。這裡有一個資安陷阱。HTML 的部分，SSR 產生的字串一樣會跳脫插值（第 7 課），v-html 一樣不跳脫；但序列化的狀態是另外塞進頁面的，內容幾乎都來自使用者（姓名、備註），沒跳脫的話，顧客在備註裡寫一段 </script>，瀏覽器就會在那裡結束這段 script，後面的文字被當成 HTML 解析，等於讓使用者把程式注入頁面。所以序列化一定要跳脫，Pinia 文件建議用 Nuxt 也在用的 devalue。

只要在伺服器上執行，「模組層級」就等於「全站共用」。除了 reactive，也包括模組層級的 Map 快取、計數器、目前使用者的變數。真的需要全站共用的（例如設定），要確定它不含任何使用者的資料。
💡 實務上：這是資安事故，而且本機測不出來
自己在本機一次只開一個分頁，請求一個接一個，永遠看不到別人的購物車；要到上線後同時有很多人使用才會出現，而一出現就是個資外洩，資安和 PM 都會被找來。常見的另一種寫法是在伺服器上設定全域的 HTTP 用戶端，例如把登入 token 寫進共用 axios 實例的預設 header，下一個請求就帶著上一個人的身分去呼叫 API。資深工程師在 review SSR 程式碼時會特別搜尋模組最外層的 let、reactive、new Map() 和「設定一次全域用」的實例；要驗證時，用兩個不同帳號同時發請求，確認回應沒有混在一起。

三個事故都修好了。但 SSR 本身還留著一個代價，就是第一節那張圖上的 hydration 空窗：畫面已經出現，使用者卻還按不動。

看得到卻按不動：hydration 能不能晚一點做？

hydration 要執行每個元件的 setup、走過整棵元件樹，頁面越大，「看得到」到「按得動」的空窗越長。咖啡店首頁最下面有一張門市地圖，元件又大、又很少人捲到那裡，卻和最上面的「加入購物車」按鈕一起排隊等 hydration。

非同步元件就是第 23 課用 defineAsyncComponent 包起來的元件：loader 寫成動態 import()，建置時這個元件會被切成獨立的檔案，要用到時才下載。Vue 3.5 起，非同步元件可以指定延遲 hydration：伺服器照樣把它渲染進 HTML，使用者看得到地圖的樣子；但瀏覽器等到指定的條件成立，才下載這個元件的程式、hydrate 它。其他元件不用等它，首屏的按鈕更早按得動。

import { defineAsyncComponent, hydrateOnVisible } from 'vue'

// 頁尾的門市地圖：捲到看得見時才 hydrate
const StoreMap = defineAsyncComponent({
  loader: () => import('./StoreMap.vue'),
  hydrate: hydrateOnVisible(),
})

內建策略還有 hydrateOnIdle()（瀏覽器閒置時）、hydrateOnInteraction('click')（使用者第一次互動時，並在 hydrate 後重播那個事件）、hydrateOnMediaQuery('(max-width: 500px)')。適合畫面下方、不急著互動的大元件；首屏的按鈕不要延遲，否則使用者按了沒反應。

到這裡，為了一個首頁，我們已經手寫了伺服器端渲染、瀏覽器端 hydration、每個請求的 createApp、狀態的序列化與還原。一個正式上線的 SSR 網站還不只這些，所以最後一個問題是：這些要自己做，還是交給框架？

正式上線：自己做 SSR，還是交給 Nuxt？

這課的練習只碰到 SSR 的核心。一個正式的 SSR 網站還要：伺服器和瀏覽器兩套建置設定；路由在伺服器上先解析完才能渲染；每個頁面的資料抓取（onServerPrefetch）、錯誤與 404 狀態碼；把狀態序列化、跳脫、在瀏覽器還原；Teleport 的內容要另外插進頁面（見課末「補充與查表」）；<head> 的標題與 meta；串流輸出、快取；部署一台 Node 伺服器。自己做的成本主要在這串清單，不在 renderToString 那幾行。

Vue 官方的 SSR 指南也說：需要 SSR 時強烈建議用框架。Nuxt（目前 4.6.3）是 Vue 生態系最主要的 SSR 框架，上面這些都做好了。例如修購物車時自己處理的狀態傳遞，它的 useFetch 在伺服器抓資料、把結果放進頁面的 payload（隨 HTML 一起送出的序列化資料），瀏覽器 hydrate 時直接用、不會再抓一次。第一節「同一個網站混用三種渲染方式」的判斷，也可以用 routeRules 逐條路由寫下來：

// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/stores': { prerender: true },     // 門市頁：建置時產生（SSG）
    '/menu/**': { swr: 3600 },          // 商品頁：SSR，結果快取一小時，過期後在背景重新產生
    '/admin/**': { ssr: false },        // 後台：只在瀏覽器渲染（CSR）
  },
})

判斷方式：

  • 不需要 SSR（後台、內部工具）：維持 Vite＋Vue 的 SPA，不要為了「看起來進階」加 SSR。
  • 需要 SSR 或 SSG 的新專案：用 Nuxt。
  • 只有少數幾頁要被搜尋：考慮只把那幾頁做成 SSG，或交給 Nuxt 的 routeRules 混用。
  • 自己做 SSR 的合理時機：已有自己的 Node 伺服器、只需要渲染少數元件（例如 email 範本），或需要 Nuxt 不支援的特殊整合。

用了 Nuxt，這課修三個事故的規則一條都沒有消失：setup 裡不碰 window、不在渲染時用亂數和現在時間、不寫模組層級的使用者狀態。框架做的是組裝，不會幫你修這些 bug。

補充與查表

SSR 時的 Teleport

第 11 課的 <Teleport> 在 SSR 有兩個限制。第一，被傳送的內容不在 renderToString 回傳的字串裡，而是放在第二個參數 SSR context 的 teleports 裡，要自己插進頁面範本。第二，不要 Teleport 到 body：body 裡還有其他伺服器渲染的內容，hydration 時找不到傳送內容從哪裡開始。官方建議用一個只放傳送內容的容器（另一個做法是掛載之後才渲染 Teleport，例如對話框只在使用者打開時出現）：

const ctx = {}
const html = await renderToString(app, ctx)
// ctx.teleports → { '#modals': '<div class="dialog">…</div>' }
// 範本：<div id="app">${html}</div><div id="modals">${ctx.teleports['#modals'] ?? ''}</div>

正式建置印出 hydration 不一致的細節

正式建置預設不印不一致的細節。可以用編譯期旗標 __VUE_PROD_HYDRATION_MISMATCH_DETAILS__ 打開：它在建置時由打包工具換成常數，例如在 Vite 設定的 define 裡設成 true。先在本機用正式建置重現，再打開它看是哪個元素。

hydration 不用檢查每一個節點

Vue 編譯器加上的 patch flags 讓 hydration 只需要檢查會變動的部分，範本裡靜態的部分直接跳過。

練習

在 learn/ 執行 node check.mjs vue 24。測試用 helpers/ssr.ts 模擬兩端：serverRender 在 window、document 都是 undefined 的情況下呼叫 renderToString；hydrate 把 HTML 放進容器、用 createSSRApp 掛載，收集 Vue 的警告。三題互相獨立。

練習 1：StoreHours.vue 在 setup 讀 window.innerWidth、用 new Date() 判斷營業中。改成：伺服器能渲染；營業狀態只由 props.now 決定，營業時間是台北時間 07:00（含）到 19:00（不含）；寬度在掛載後才讀並顯示「螢幕寬度：1024px」。測試會讓伺服器在 UTC、瀏覽器在紐約，兩邊的系統時間也不同，hydrate 時不能有任何警告，也不能用 data-allow-mismatch。

練習 2：購物車是模組層級的 reactive，renderPage 會把王小明的拿鐵帶到陳美華的頁面。改成：cart.ts 不再建立狀態，改匯出 CART_KEY 和 useCart()；createApp(owner) 每次建立新的購物車並用 app.provide 提供；CartPage.vue 用 useCart() 取得，拿不到時 useCart() 要丟出錯誤。測試會先後渲染兩個人，也會讓兩個渲染同時進行（中間有 await），「開始時清空」擋不住後者。

練習 3：PhoneField.vue 的 label 和 input 用 Math.random() 產生 id。改成伺服器和瀏覽器一致、同一頁兩個欄位也不重複的 id。測試會在同一頁放兩個 PhoneField，也會先讓伺服器渲染別的頁面再渲染這一頁，檢查 hydrate 後的 id 和伺服器的 HTML 相同、沒有警告。

練習 4：咖啡店要做一套店員用的訂單管理後台（要登入、只在店內電腦使用）。同事說「現在都流行 SSR，後台也做 SSR 比較好」。你的判斷是？

✓ SSR 的好處是更早看到內容和 SEO，後台不需要被搜尋，使用者也能接受第一次載入稍慢；代價卻一樣不少：要維運 Node 伺服器、每個請求都花 CPU、要處理 hydration 與跨請求狀態。SSR 的 TTFB 還比較晚，不是「一定比較快」。訂單隨時在變、而且要登入，SSG 在建置時產生不出來。CSR 一樣可以呼叫 API。

練習 5：元件在 onMounted 裡開了一個 setInterval，在 onUnmounted 清掉。伺服器渲染這個元件時會怎樣？

✓ 伺服器上的元件只做到產生 HTML 為止，沒有「掛載」這件事，掛載之後的鉤子都不會執行。所以副作用要放在 onMounted：它只在瀏覽器執行，也一定有對應的 onUnmounted。反過來，寫在 setup 裡的計時器在伺服器上會被建立，卻永遠沒有人清掉。

練習 6：export const cart = reactive({ items: [] }) 寫在模組最外層，在 SPA 用得好好的，為什麼改成 SSR 後陳美華會看到王小明的拿鐵？

✓ 在瀏覽器裡一個分頁就是一個使用者，模組層級等於「這個使用者一份」；在伺服器上模組層級等於「所有使用者一份」。換成 ref 一樣是模組層級、一樣共用。這是伺服器端產生的 HTML 本身就錯了，和瀏覽器快取、hydration 無關。修法是每個請求呼叫 createApp，建立新的 app、store、router，用 provide 交給元件。

常見錯誤

  • 在 setup 或 template 用 window、document、localStorage：伺服器上丟出 ReferenceError。初始值用中性的值，掛載後在 onMounted 讀。
  • 用 typeof window 判斷後輸出不同內容：伺服器不丟錯了，但兩邊第一次渲染不同，造成 hydration 不一致。第一次渲染一律相同，差異留到 onMounted 之後。
  • 渲染時用 Date.now()、new Date()、Math.random()：兩端執行的時間、時區、亂數都不同。時間由參數傳入同一個值並指定時區；id 用 useId()。
  • 在 setup 開計時器、加監聽：伺服器上沒有 unmount，每個請求留下一個。放進 onMounted。
  • 伺服器上的模組層級狀態：所有使用者共用，會外洩資料。每個請求 createApp，連同新的 pinia、router，用 provide 交給元件。「開始時清空」在同時有多個請求時無效。
  • 序列化狀態時沒有跳脫：使用者輸入的 </script> 會提早結束頁面裡的 script，等於讓人注入程式。用 devalue 這類會跳脫的工具。
  • 用 data-allow-mismatch 隱藏問題：警告沒了，畫面還是錯的。只用在確定無法避免、也無所謂的地方，並限定類型。
  • SSR 時 Teleport 到 body：hydration 找不到傳送內容的起點。用專用的容器，從 SSR context 的 teleports 插進頁面。
  • 不合法的 HTML 巢狀：<p> 裡放 <div>，瀏覽器解析後的 DOM 和 Vue 預期的不同。
  • 複雜的 app 自己做 SSR：建置、路由、資料抓取、狀態傳遞、head、快取全部要自己處理。需要 SSR 的新專案用 Nuxt；不需要 SSR 就不要做。

小結

  • CSR 在瀏覽器產生畫面，部署最簡單；SSR 每個請求在伺服器產生 HTML，利於 SEO 與首次顯示，但要維運 Node 伺服器、TTFB 較晚；SSG 在建置時產生，最快但資料只到上次建置。內部後台通常用 CSR；先問哪幾頁真的要被搜尋或分享，手機白畫面先量測再決定。
  • 伺服器用 createSSRApp＋renderToString，瀏覽器用同一個元件 createSSRApp(...).mount() 做 hydration：認領現有 DOM、掛上事件，不重建。前提是兩邊第一次渲染結果相同；屬性不一致不會被修正，文字和節點不一致會被瀏覽器的值換掉。
  • 伺服器只執行 setup、render、onServerPrefetch（Options API 加上 beforeCreate、created）；onMounted 之後都不執行。瀏覽器 API 和副作用放進 onMounted，不要用 typeof window 讓兩邊輸出不同內容。
  • 不一致的來源：瀏覽器才有的資料、時間與時區、亂數、不合法的 HTML 巢狀。修法：由參數傳同一個值、指定時區、放到 onMounted、id 用 useId()；data-allow-mismatch 只用在無法避免的地方。
  • 伺服器上模組層級的狀態被所有請求共用，「開始時清空」擋不住同時進來的請求。每個請求建立新的 app、pinia、router，用 provide／inject 傳遞；序列化給瀏覽器的狀態一定要跳脫。
  • Vue 3.5 的延遲 hydration（hydrateOnVisible 等）讓畫面下方的大元件晚一點 hydrate，首屏更早按得動；SSR 時的 Teleport 要用專用容器，不要 Teleport 到 body。
  • 需要 SSR 的新專案用 Nuxt（routeRules 可逐頁混用 SSG、SSR、CSR）；規則本身不會因為用了框架而消失。
