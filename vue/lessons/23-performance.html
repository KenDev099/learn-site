階段 7：品質、效能與架構 · 第 23 課

效能：先量測，再優化渲染與打包

咖啡店後台上線一個月，店長回報兩件事：訂單看板有 200 筆訂單，點一下某一筆要等半秒才變色；顧客用手機打開點餐頁，白畫面好幾秒才出現菜單。工程師的第一個反應常是「到處加 v-memo、全部改 shallowRef」，結果改了一週，使用者感覺不到差別，程式卻變難讀了。

這課從頭到尾處理店長這兩個抱怨：先把「好慢」量成數字，找出慢的原因，針對原因修，最後再量一次證明真的變快了。範例使用 Vue 3.5.44、vue-router 5.4.0、Vite 8.3.5。

這課的路線：
  1. 「好慢」是哪一種慢：點訂單變色慢和手機白畫面各是什麼指標、用什麼工具量（開場問題的最小答案也在這節）。
  2. 點一筆訂單，為什麼 200 列都重新渲染：子元件什麼時候會更新，怎麼用 props 穩定性降到只更新 2 列。
  3. props 沒變也重新渲染時：用 onRenderTriggered 直接問 Vue「你為什麼更新」。
  4. props 已經穩定了還不夠時：v-once、v-memo 叫 Vue 跳過一段範本，以及畫面因此不更新時怎麼查。
  5. 手機白畫面：用動態 import 讓首頁不下載報表頁，再看 vite build 的輸出確認真的拆出去了。
  6. 報表頁自己也慢：2 萬筆唯讀資料用 shallowRef、markRaw 少包一層響應式。
這課會用到：
  • 第 2 課的 effect：一段會記下自己讀過哪些響應式資料的函式，那些資料改了就重新執行。
  • 第 7 課的 patch 與 key：狀態改變後 Vue 重新執行 render 產生新的虛擬 DOM（由一個個 VNode 組成，VNode 是描述一個元素或元件的普通 JS 物件），和舊的比對（patch），只改真正不同的 DOM；v-for 的 key 讓 Vue 認得哪一列是哪一列。
  • 第 4 課的 shallowRef、markRaw 與失去響應的情況：只追蹤 .value 的替換、標記物件不轉成 proxy。

「好慢」是哪一種慢？先把兩個抱怨變成數字

店長說的「好慢」，背後可能是好幾種完全不同的問題：網路下載的東西太多、JavaScript 執行太久、一次更新太多 DOM、圖片太大、API 回應太慢。這些問題的修法互相沒有關係，修錯了對使用者毫無幫助。開場那位工程師到處加 v-memo，就是在不知道是哪一種慢的情況下猜答案。所以第一步不是改程式，而是先分清楚是哪一種慢，並且量出一個數字，之後才能比較改了有沒有用。

要把「使用者覺得慢」變成數字，業界有一套共通的指標，叫 Core Web Vitals（核心網頁指標），是 Google 定義、用來描述使用者實際感受的幾個數字。跟店長兩個抱怨有關的是其中兩個：

  • LCP（Largest Contentful Paint，最大內容繪製）：從開始載入到畫面上最大的那塊內容（主圖、標題、菜單列表）畫出來的時間，代表「主要內容多久出現」。好的標準是 2.5 秒內。打包太大、API 太慢都會拖慢它。
  • INP（Interaction to Next Paint，互動到下一次繪製）：使用者點擊、打字之後，到畫面真的更新的延遲，取整段瀏覽期間的互動裡，接近最慢的那一次。好的標準是 200 毫秒內。一次更新太多元件、事件處理裡做太多計算會拖慢它。

店長的兩個問題剛好各對應一個：點訂單之後要等半秒才變色，是「互動之後多久畫面更新」，屬於 INP；手機打開點餐頁白畫面好幾秒，是「主要內容多久出現」，屬於 LCP。分出這兩類之後，要查的方向就不同了：INP 要看點下去之後 JavaScript 做了什麼，LCP 要看載入時下載了什麼、等了什麼。各自用的工具如下：

工具看什麼
Chrome DevTools 的 Performance 面板按錄製、操作一次、停止，看時間軸上哪段 JavaScript 執行最久（長條越寬越久）。也會標出 LCP、INP。勾選 CPU 降速（例如 4 倍）模擬一般手機。
Chrome DevTools 的 Network 面板、Lighthouse首次載入下載了哪些檔案、各多大、誰在等誰；Lighthouse 跑一次給出 LCP 等分數和建議。
Vue DevTools元件樹與每個元件的狀態；Timeline 記錄元件的渲染、更新事件與耗時，看得出一次操作讓哪些元件更新了幾次。
app.config.performance = true開發模式下，把每個元件的初始化、編譯、渲染、patch 用 performance.mark 標在瀏覽器 Performance 面板的時間軸上，看得到元件名稱。
PageSpeed Insights、WebPageTest用真實網路、真實裝置測正式網站；PageSpeed Insights 也會顯示真實使用者的 LCP、INP 統計。

INP 這一類，Performance 面板會告訴你「哪段 JavaScript 很久」，但只看得到函式名稱；打開 app.config.performance 之後，時間軸上會直接標出是哪個 Vue 元件在渲染、在 patch，才看得懂時間花在誰身上：

// main.ts：只在開發時打開，正式環境本來就不會作用
const app = createApp(App)
if (import.meta.env.DEV) app.config.performance = true
量測要在接近使用者的條件下做：開發模式的 Vue 比正式版慢很多（多了警告和除錯檢查），你的筆電也比顧客的手機快很多。看「哪一段比例最大」用開發模式可以；要報告「改善了幾毫秒」，用 vite build 之後的 vite preview，並開 CPU 降速。

實際用 Performance 面板錄下「點一筆訂單」，會看到一段很寬的 JavaScript 執行，展開後幾乎都是 OrderRow 的 render 和 patch，而且有 200 次。這就是線索：只點了一列，200 個元件都更新了。手機白畫面那邊，用 Network 面板看首頁載入，會發現首頁下載的整包 JavaScript 裡，包含只有店長會開的報表頁和它用的圖表套件。

有了這兩個證據，店長兩個問題的最小答案就出來了：訂單看板讓每一列只收到跟自己有關的 props，點一下就只有兩列更新；手機白畫面則把報表頁拆成另一個檔案，首頁少下載一點。接下來兩節處理訂單看板，〈手機白畫面〉那節處理首頁。

💡 實務上：效能問題多半從一句「好慢」開始
工作中很少有人直接給你 LCP 數字，常見的是客服轉來「店長說訂單頁很卡」。先問清楚：哪一頁、做了什麼操作、用什麼裝置和網路、資料大概幾筆，再自己開 CPU 降速重現一次。重現不出來就先別改，請對方錄影或提供當時的帳號情境。公開且有一定流量的頁面（例如線上點餐頁），可以先看 PageSpeed Insights 的真實使用者資料，確認是普遍現象還是少數裝置；要登入的後台頁面沒有這份資料，只能自己重現。資深工程師會先把「慢」變成一個能重複量測的操作步驟，之後每次修改都用同一個步驟比較。

量測只告訴我們「200 個 OrderRow 都更新了」，沒告訴我們為什麼。只點了一列，另外 199 列為什麼也要重畫？

點一筆訂單，為什麼 200 列都重新渲染？

要回答「為什麼 199 列也更新」，得先知道一個元件在什麼情況下會重新渲染。每個元件都有一個 render effect：就是第 2 課的 effect，裡面執行的是這個元件的範本（render 函式），執行時讀到哪些響應式資料，就記下哪些。之後元件重新渲染，只有兩個來源：

  1. 它自己讀過的響應式資料被改了：render effect 記下的依賴有一個改變，effect 重新執行。
  2. 父元件重新渲染，傳給它的 props 變了：父元件重新執行 render 時，會為每個子元件產生新的 VNode、帶著新的 props。Vue 逐一比對每個 prop 的新舊值：全部相同就跳過這個子元件，任何一個不同，就整個子元件重新渲染、再 patch 它的 DOM。

訂單看板的寫法是這樣：

<OrderRow v-for="order in orders" :key="order.id" :order="order" :selected-id="selectedId" />

點一筆訂單時，selectedId 從 1005 變成 1151。OrderBoard 的範本讀了 selectedId，所以 OrderBoard 自己因為第 1 種原因重新渲染。它重新渲染時，200 個 OrderRow 都拿到新的 props：order 還是同一個物件，比對結果相同；但 selectedId 對每一列都從 1005 變成了 1151。於是 200 個 OrderRow 因為第 2 種原因全部重新渲染，即使其中 198 列的畫面跟原本一模一樣。

問題出在 props 的「形狀」：每一列真正需要的只是「我是不是被選取」，卻收到了一個所有列共用、而且會變的值。官方效能指南把這個原則叫做 props 穩定性（props stability）：傳給子元件的 props 盡量不變，子元件就不用更新。修法是在父元件先算好，每列只收到自己的選取狀態：

<OrderRow v-for="order in orders" :key="order.id" :order="order" :selected="order.id === selectedId" />

OrderBoard 還是會重新渲染，因為它仍然讀 selectedId；但現在選取從 1005 換到 1151，只有這兩列的 selected 改變，一列從 true 變 false、一列從 false 變 true。其他 198 列的 props 全部相同，被跳過。

改完要確認真的只剩 2 列更新，不能只看程式碼覺得對。Vue DevTools 的 Timeline 可以看到這次點選讓哪些元件更新了幾次；也可以在子元件加 onUpdated(() => count++) 數一數。練習 1 的測試就是用全域 mixin 數每個元件的 updated 次數。最後回到上一節的 Performance 面板，用同樣的 CPU 降速、同樣的操作再錄一次，那段很寬的 JavaScript 應該明顯變窄。

💡 實務上：列表的 props 形狀在 code review 就看得出來
後台的訂單列表、商品管理、會員清單，最常見的寫法就是把「目前選取的 id」「目前展開的 id」整個傳給每一列。review 時看到 v-for 裡每一列都收到同一個會變的值，就可以問：能不能先在父元件算成每列自己的布林值？另一個常見的坑是在範本裡呼叫函式產生新陣列，例如 :items="itemsOf(order)"，每次父元件渲染都是新陣列，子元件永遠被判定為 props 變了。列表只有十幾筆時改了也量不出差別，不必為此開一張單；但這個寫法幾乎沒有成本，新寫的列表直接照這個習慣寫就好。

訂單看板的原因看範本就推得出來，因為 OrderRow 的更新來自 props。但前面說過還有第 1 種原因：元件自己讀過的資料被改了。這種情況從範本上不一定看得出來，元件甚至可能沒有收任何 props。這時要怎麼找原因？

props 沒變也重新渲染：怎麼問 Vue「你為什麼更新」？

OrderRow 的例子示範不了第 1 種原因，所以換點餐頁上的一個元件來看。點餐頁右上角有一個購物車徽章（CartBadge），只顯示購物車裡有幾件，不收任何 props，直接讀共用的 cart 物件。用上一節的方法數更新次數，發現顧客在備註欄打字時，它每打一個字就重新渲染一次。範本只用到 cart.count，打備註卻讓它更新，表示它的 render effect 記下了比 count 更多的依賴。光看範本猜是哪一個很慢，Vue 提供了兩個除錯鉤子，可以直接問：

  • onRenderTracked(e => …)：render 讀到一個響應式資料、把它記成依賴時呼叫。e.type 是 get、has、iterate，可以看到「這個元件依賴了什麼」。
  • onRenderTriggered(e => …)：某個依賴改變、讓元件要重新渲染時呼叫。e.target 是被改的物件、e.key 是屬性名稱、e.type 是 set（改值）、add（新增屬性或陣列元素）、delete、clear，還有 newValue、oldValue。

前者回答「它依賴了誰」，後者回答「這次是誰改了什麼讓它更新」。查「為什麼多更新」用後者：

import { onRenderTriggered } from 'vue'

onRenderTriggered(e => {
  console.log('重新渲染，因為', e.target, e.key, e.type)
  // debugger   // 在這裡停下來，看呼叫堆疊就知道是哪段程式改的
})

在 CartBadge 加上這個鉤子，顧客打字時會印出 key: 'note', type: 'set'：徽章依賴了 note。可是範本裡明明沒寫 note。回頭仔細看範本，找到之前除錯留下的 :title="JSON.stringify(cart)"：JSON.stringify 為了轉成字串，會讀 cart 的每一個屬性，而 render 期間讀到的每個屬性都會被記成依賴。所以 cart 任何一個屬性改了，徽章都會更新。拿掉它，徽章就只依賴 count。練習 4 就是這個情境。

同樣的問題也會發生在 watch 和 computed 上：watch 被觸發得太頻繁、computed 一直重算。它們有對應的除錯選項 onTrack、onTrigger，用法一樣：

watch(() => cart.count, save, {
  onTrigger(e) { console.log('watch 被觸發', e.key, e.type) },
})
const total = computed(() => sumOf(cart.items), {
  onTrigger(e) { console.log('total 要重算', e.key, e.type) },
})
這四個鉤子只在開發模式有效，正式版（production build）會整段移除，伺服器渲染時也不會呼叫。它們是除錯工具，不能拿來做線上監控；線上要量真實使用者的 LCP、INP，用 Google 的 web-vitals 這類套件在瀏覽器裡收集，再像第 21 課回報錯誤那樣送到監控服務。

到這裡，訂單看板和購物車徽章「多更新」的原因都找得到，也都靠讓依賴、props 變得更精準來修。但有些情況 props 已經不能再穩定了，元件還是需要被比對很多次。這時能不能直接叫 Vue 別比了？

props 已經穩定了還不夠：什麼時候叫 Vue 跳過一段範本？

props 穩定性減少的是「重新渲染的子元件數量」，但父元件每次重新渲染時，仍然要為 200 列（或 2000 列）各產生一個新的 VNode、逐一比對 props，才知道哪些可以跳過。列表非常長的時候，光是這段比對也會花時間。另一種情況是內容根本不會變，比對本身就是多餘的。Vue 有兩個指令可以直接告訴它「這段不用比」：

  • v-once：只渲染一次，之後整段（含子元件）都當成靜態內容跳過。適合真的不會變的內容，例如開店時讀進來的店名、使用條款。
  • v-memo="[a, b]"：給一個固定長度的陣列，重新渲染時陣列裡每個值都和上次相同（用 Object.is 比較），就整段跳過，連 VNode 都不建立。v-memo="[]" 等於 v-once。

上一節已經把訂單看板改成傳 selected，那為什麼還要 v-memo？有兩種常見情況。第一種：OrderRow 是別的團隊維護的共用元件，它的 props 就是要收 selectedId，形狀改不了，props 穩定性這條路走不通。第二種：列表有上千筆，就算已經傳 selected，每次點選仍要為上千列建立 VNode、比對 props，這段成本也想省掉。下面用第一種情況示範，因為它最能看出 v-memo 做了什麼：子元件一行都不改，只在父元件的 v-for 上加一個指令：

<OrderRow
  v-for="order in orders"
  :key="order.id"
  v-memo="[order.id === selectedId]"
  :order="order"
  :selected-id="selectedId"
/>

這段的意思是「這一列只有在選取狀態改變時才更新」。即使每列仍然收到 selectedId，只要 order.id === selectedId 的結果沒變，Vue 連這一列的 VNode 都不建立、也不比 props。效果和上一節改傳 selected 一樣，只有兩列更新，但 OrderRow 的 props 完全沒動。第二種情況則是兩者疊加：保留 :selected，再加同樣的 v-memo。這時 props 穩定性已經讓 198 列不重新渲染，v-memo 多省下的是那 198 列「建立 VNode、逐一比對 props」的工作。官方文件說 v-memo 最常用在超過 1000 筆的 v-for 列表，就是指這種比對本身已經變成瓶頸的情況。order.id 不用放進陣列，Vue 會從 :key 推得。v-memo 要和 v-for 寫在同一個元素上，寫在 v-for 裡面的子元素沒有作用。

v-memo 的陣列寫錯，畫面會停在舊的狀態，而且不會有任何錯誤訊息。例如寫成 v-memo="[order.id]"：id 永遠不變，選取改了，這一列卻永遠不更新。陣列裡要放所有會影響這段畫面的值。所以優先調整 props 的形狀；props 穩定性做不到時，才用 v-memo，而且要有測試確認畫面正確。

這個警告帶出效能優化常見的副作用：優化完，換成「該更新的畫面沒更新」。這時的查法跟前一節反過來。先確認資料真的改了（Vue DevTools 看元件狀態）；資料改了畫面沒動，就檢查第 4 課的失去響應清單：解構了 reactive、整個替換了 reactive 物件、shallowRef 就地修改、用了 markRaw 的物件。最後看是不是被 v-once 或依賴寫錯的 v-memo 擋掉。用 onRenderTracked 印出元件到底依賴了什麼，常常一眼就看出少了哪一個。

訂單看板的 INP 問題到這裡處理完了：用 props 穩定性降到 2 列，真的需要時再用 v-memo。店長的另一個抱怨是手機白畫面，那是 LCP，問題不在點下去之後，而在一開始下載了什麼。

手機白畫面：怎麼讓首頁不下載報表頁？

第一節用 Network 面板看到，首頁下載的整包 JavaScript 裡，包含只有店長會開的報表頁和它用的圖表套件。顧客用手機點餐，永遠不會打開報表頁，卻要先下載、解析這些程式，菜單才畫得出來。要解決，得先知道打包工具怎麼決定「什麼東西放進哪個檔案」。

Vite 在建置時會從入口檔（通常是 main.ts）開始，順著 import 找出所有用到的模組，合併成幾個 JavaScript 檔案。打包輸出的每一個 JavaScript 檔案叫一個 chunk。入口所在的那個叫主 chunk，首頁一定要下載它。模組被放進哪個 chunk，取決於它是怎麼被 import 的：

  • 靜態 import（寫在檔案開頭的 import X from './X.vue'）：X 和它 import 的一切，都跟 import 它的檔案放進同一個 chunk，一開始就下載。
  • 動態 import（import('./X.vue')，是一個回傳 Promise 的函式呼叫）：打包工具把 X 切成另一個 chunk，程式執行到這一行時才下載。

利用動態 import 把程式拆成多個 chunk、需要時才下載，這個做法叫程式碼分割（code splitting）。咖啡店的路由現在是在檔案開頭靜態 import 了報表頁，所以報表頁和它 import 的圖表套件全都進了主 chunk。改成動態 import，它們就會被切出去，只有店長導航到報表頁時才下載。

Vue 裡有兩個地方會用到動態 import。路由（第 19 課）直接給載入函式，vue-router 導航到那一頁時才呼叫它；不是路由的元件，例如很少打開的退款對話框，用 defineAsyncComponent 包起來，元件第一次要顯示時才下載：

// 路由：直接給 () => import()，不要包 defineAsyncComponent（官方文件不建議用在路由）
{ path: '/admin/reports', component: () => import('./pages/AdminReports.vue') }

// 一般元件：顯示時才下載
const RefundDialog = defineAsyncComponent({
  loader: () => import('./RefundDialog.vue'),
  loadingComponent: LoadingSpinner,  // 下載中顯示
  delay: 200,                        // 預設 200 毫秒後才顯示 loading，網路快時不會閃一下
  errorComponent: LoadFailed,        // 下載失敗或逾時顯示
  timeout: 10000,                    // 預設 Infinity：不設就永遠等
})

因為是需要時才下載，下載就可能慢、可能失敗，所以 defineAsyncComponent 讓你指定下載中和失敗時要顯示什麼。timeout 預設是永遠等，網路斷掉時使用者會一直看著 loading，正式環境建議設一個上限。

只要有一處靜態 import 了那個模組，動態 import 就白寫了：模組已經在主 chunk 裡，打包工具不會再切出來。常見的情況是為了拿一個常數，import { REPORT_TITLE } from './pages/AdminReports.vue'，整個元件就被拉回主 chunk。共用的常數放在獨立的小檔案。

拆出去是一種讓首頁少下載的方法，另一種是一開始就別把用不到的程式包進來。tree-shaking 指的是打包時移除「被 import 進來、但沒被用到」的程式碼，像搖樹把枯葉搖掉。它要靠 ES module 的靜態 import { x } 才能分析出用到了哪些，所以選套件時要注意：import _ from 'lodash' 會帶進整個 lodash（它是 CommonJS，沒辦法分析）；import { debounce } from 'lodash-es' 只帶進 debounce 和它用到的函式。很多時候瀏覽器內建的 API 就夠了（structuredClone、Intl.NumberFormat、Array.prototype.toSorted），連套件都不用裝。

知道怎麼拆之後，容易犯的錯是拆過頭。分割不是越細越好：每個 chunk 都是一個網路請求；頁面載入後才發現要 A，A 載入後才發現要 B，形成請求瀑布（一個請求等另一個請求結束才開始），反而更慢。所以首頁一定會用到的東西留在主 chunk，只有「很多人用不到」或「很大」的部分才分割。咖啡店的報表頁兩個條件都符合，首頁和菜單則維持靜態 import。

程式改完了，但前面那個警告說過，任何一處靜態 import 都會讓分割悄悄失效，而且不會有錯誤訊息。光看 router.ts 沒辦法確定報表頁真的被拆出去，要怎麼確認？

怎麼確認真的拆出去了？看 vite build 的輸出

最直接的證據是打包結果本身。npx vite build 跑完，最後會列出輸出的每個檔案和大小：

dist/index.html                        0.11 kB │ gzip:  0.11 kB
dist/assets/AdminReports-XoBM5jsw.js   0.30 kB │ gzip:  0.29 kB
dist/assets/index-BLNMNsmx.js         88.49 kB │ gzip: 34.47 kB

這是練習 3 的答案加上一個 index.html 之後實際 build 的輸出。由上到下讀：

  • index.html 是入口網頁。
  • AdminReports-XoBM5jsw.js 是報表頁自己的 chunk。它有自己的檔案，就表示分割成功；如果某處又靜態 import 了它，這一行會消失，內容併回下面的主 chunk。
  • index-BLNMNsmx.js 是主 chunk，首頁一定會下載它。看 gzip 那一欄：伺服器通常會壓縮後再傳送，這一欄才接近使用者實際下載的大小。

檔名裡的亂碼是依檔案內容算出的雜湊，內容改了才會變，所以瀏覽器可以放心長期快取這些檔案，下次部署只有改過的 chunk 需要重新下載。想看每個 chunk 裡到底包了哪些套件、各佔多少，可以用 rollup-plugin-visualizer 這類套件畫出佔比圖。

Vite 也可以手動指定哪些模組放進哪個 chunk，例如把所有第三方套件集中成一個 vendor chunk。這是進階調整，多數專案用預設的自動分割就好；看過 build 結果、確認有問題才動它。Vite 8 改用 Rolldown 打包，這部分的設定名稱跟以前不同，升級時的變化和寫法見課末「補充與查表」。

💡 實務上：量、改、再量，數字寫進 PR
效能工作的成果是數字，不是寫法。每次優化都記下改之前和改之後的量測（在同樣的條件下），一起寫進 PR，例如「訂單看板點選的 INP：開發機 4 倍降速下 480 ms → 60 ms；OrderRow 每次點選更新 200 次 → 2 次」。打包也一樣：附上改前改後 vite build 輸出裡主 chunk（index-xxx.js）的 gzip 大小，reviewer 一眼就看得出有沒有把報表套件拉回首頁。量不出差別、又讓程式變複雜的優化（例如到處加 v-memo），就不要合併。

首頁不再下載報表頁，顧客的白畫面縮短了。但報表頁本身還沒處理：它被拆出去，只是讓不用它的人不必下載；店長打開它時，它還是一樣慢。

報表頁自己也慢：2 萬筆資料要不要每一筆都是響應式？

報表頁一次載入 2 萬筆銷售紀錄給圖表用，店長切換門市篩選時也會卡一下。照第一節的方法錄下來，時間有一大部分花在 Vue 的響應式處理上。原因在資料是用 ref 存的：ref 裡放物件或陣列時是深層響應，Vue 會在讀取時把每一筆紀錄都包成 proxy，存取每個屬性都要經過 get 攔截、記錄依賴。響應式的用途是「資料改了，畫面跟著變」；可是這 2 萬筆只會整批換掉，從來不會改其中一筆的某個欄位，花在每一筆上的成本全是浪費。

第 4 課教過兩個工具，可以讓 Vue 少包一層：

  • shallowRef：只追蹤 .value 本身的替換，裡面的物件保持原本的普通物件，不包 proxy、不記依賴。代價是就地修改不會通知：rows.value.push(x) 畫面不會變，要寫 rows.value = [...rows.value, x] 整個換掉。
  • markRaw(obj)：標記這個物件永遠不要被轉成 proxy。適合第三方函式庫的實例（地圖、圖表、編輯器），它們有自己的內部狀態，被包成 proxy 反而會出錯或變慢。

報表頁兩個都用得上：銷售紀錄用 shallowRef，圖表實例用 markRaw。

const rows = shallowRef<Sale[]>([])
async function load() {
  rows.value = await api.getSales()      // 整批換掉，依賴 rows 的 computed、watch 才會更新
}
const chart = markRaw(new SalesChart(el))   // 第三方圖表實例不需要響應式

報表頁還有依門市篩選的 computed，下游的圖表依賴它。這裡會遇到第二節 props 穩定性的同一個道理，只是發生在 computed 上：值穩定，下游才不用動。第 3 課說過 Vue 3.4 起「computed 算出的值沒變就不通知下游」，但「沒變」是用 Object.is 比較的。篩選每次都產生一個新陣列，就算裡面的元素跟上次一樣，Object.is 也判定為不同，下游照樣重算、圖表照樣重畫。回傳物件也一樣。篩選陣列的寫法留給練習 2，這裡先用結構最簡單的物件示範：圖表上方的摘要 summary，從篩選結果算出筆數和總金額，每次重算都會產生新物件。解法是用 computed 的第一個參數拿到上一次的值，內容相同就回傳舊的：

// filtered：依門市篩選後的銷售紀錄（computed）；amount 是每筆的金額
const summary = computed(old => {
  const next = {
    count: filtered.value.length,
    total: filtered.value.reduce((sum, r) => sum + r.amount, 0),
  }
  // 先算出新值（這樣每次都會追蹤到依賴），內容相同就回傳舊物件
  return old && old.count === next.count && old.total === next.total ? old : next
})

練習 2 把這兩件事放在一起：用 shallowRef 存 2 萬筆，篩選結果和上次相同時回傳上一次的陣列。

如果店長還要在圖表下方捲動看篩選後的明細，例如一家門市就有 1 萬筆，瓶頸就從「響應式」變成「DOM 太多」：1 萬列的表格就算 Vue 一行都不更新，瀏覽器光是排版 1 萬列就很慢。這時的工具是虛擬列表（virtual list）：只渲染畫面看得到的那幾十列，捲動時換掉這幾列的內容，並用上下兩塊空白撐出總高度，讓捲軸看起來像有 1 萬列。現成的套件有 vue-virtual-scroller、TanStack Virtual 等，不用自己寫。代價是每列高度要能預測、瀏覽器內建的「Ctrl+F 搜尋頁面」找不到沒渲染的列，所以幾百列以內的列表不需要它。

大型列表裡還有一個便宜的優化：少包一層元件。每個元件實例都有自己的 render effect 和生命週期，1 萬列各包一個只負責排版的元件，成本會累加。列表的每一列很簡單時，直接寫在父元件的 v-for 裡。

💡 實務上：資料太多時，先問「真的要一次全部載入嗎」
報表頁、操作紀錄、匯出前的預覽，是最常遇到大量資料的地方。動用 shallowRef 或虛擬列表之前，先和後端、PM 確認：使用者真的需要一次看到 2 萬筆嗎？很多時候改成分頁、加篩選條件，或請後端先彙總好（例如每天的銷售總額）就解決了，前端什麼都不用優化。真的需要整批資料在前端（例如圖表要畫完整走勢），才用 shallowRef 存、markRaw 包圖表實例。要引入虛擬列表套件前，也先確認設計稿的列高是否固定，不固定的話實作和維護成本會高很多。

店長的兩個抱怨和報表頁都有了量測、原因、修法和驗證方式。下面的練習用同一個咖啡店後台，把每一步自己做一次。

練習

在 learn/ 執行 node check.mjs vue 23。四題互相獨立。練習 1、4 的測試用一個全域 mixin 數每個元件 mounted、updated 的次數；練習 3 的測試會在 Node 裡真的執行一次 vite build（不寫入檔案），檢查輸出的 chunk。

練習 1：OrderBoard.vue 把 selectedId 傳給 200 個 OrderRow，點一列時 200 列全部重新渲染。改成只有選取狀態改變的列會更新（換選另一列時 OrderRow 最多更新 2 次）。每筆訂單仍然是一個 OrderRow，選取的 <li> 是 aria-selected="true"，其他是 "false"。可以改兩個檔案。

練習 2：useSalesReport() 用深層的 ref 存 2 萬筆唯讀的銷售資料。改成 shallowRef，load(data) 整批替換（依賴 rows 的 watch 每次 load 都要觸發）；依門市篩選的 filtered 在結果的元素和上一次完全相同時，回傳上一次的陣列，讓下游不重算，但結果真的改變時要通知。

練習 3：app/src/router.ts 靜態 import 了管理報表頁。讓 AdminReports.vue 懶載入：vite build 的入口 chunk 不能包含它，要有一個動態載入的 chunk 包含它；導航到 /admin/reports 仍然顯示它。首頁維持靜態 import。測試也會擋下 defineAsyncComponent 的寫法。

練習 4：先寫 useRenderLog(log)：用 onRenderTriggered 把每次觸發記成 { key, type }（key 轉成字串）。再修 CartBadge.vue：它只顯示購物車數量，改 cart.note、cart.items 時卻也重新渲染。暫時在它的 setup 呼叫 useRenderLog、印出紀錄找原因，修好後只有 cart.count 改變時才重新渲染，畫面和 title（「購物車有 N 件」）都要跟著更新。

練習 5：店長說「訂單看板很慢」。你第一步該做什麼？

✓ 「慢」可能是載入（LCP）也可能是互動（INP），原因可能是下載、計算、DOM 更新或 API。先重現、量測，看到「點一下 OrderRow 更新了 200 次」這種具體證據，才知道該改什麼。a 和 b 可能都打不中真正的瓶頸，還讓程式變複雜（每個元件都懶載入還會造成請求瀑布）；升級也是在猜。

練習 6：const status = computed(() => ({ busy: orders.value.length > 5 }))。訂單從 6 筆變成 7 筆，busy 還是 true。依賴 status 的 watch 會被觸發嗎？

✓ length 改了，computed 重算；「值沒變就不通知」比較的是 Object.is(新值, 舊值)，({ … }) 每次都是新物件，所以永遠算「變了」，下游照樣執行。Vue 不會深入比較物件的內容。穩定的寫法是內容相同時回傳 old，或讓 computed 直接回傳原始值（computed(() => orders.value.length > 5)）。

練習 7：同事想在正式環境用 onRenderTriggered 統計「每個元件被重新渲染幾次」，送到監控系統。可行嗎？

✓ onRenderTracked／onRenderTriggered、watch 的 onTrack／onTrigger 都是開發模式專用的除錯鉤子，正式版不會呼叫。app.config.performance 也只在開發模式作用。線上監控要收的是使用者感受得到的指標（LCP、INP、錯誤率），找原因時再在開發環境重現、用這些鉤子查。

常見錯誤

  • 沒有量測就優化：改了一堆寫法，瓶頸其實在別處。先重現、錄下來、找到最寬的那段，改完在同樣條件下再量一次。
  • 把會變的值傳給每一個子元件：例如把 selectedId 傳給每一列，一改全部更新。在父元件算好，每個子元件只收到和自己有關的值。
  • v-memo 的依賴寫錯：畫面停在舊狀態，沒有任何錯誤訊息。陣列要包含所有影響畫面的值；能用 props 穩定性解決就不要用 v-memo。
  • computed 每次回傳新物件：「值沒變不通知」失效。內容相同時回傳 old，或回傳原始值。
  • 對大量唯讀資料用深層響應：每一筆都變成 proxy。改用 shallowRef 整批替換；第三方實例用 markRaw。
  • shallowRef 卻就地修改：push、splice 不會通知，畫面不更新。要整個換掉 .value。
  • 小列表也用虛擬列表：多了套件和限制（高度、頁面搜尋），幾百列以內換不到明顯的好處。
  • 動態 import 了，別處又靜態 import 同一個模組：模組留在主 chunk，分割無效。用 vite build 的輸出確認有切出來。
  • 每個元件都懶載入：請求變多、互相等待，形成瀑布。只分割大的、多數人用不到的部分。
  • 整包 import lodash：import _ from 'lodash' 帶進整個套件。用 lodash-es 的具名 import，或直接用瀏覽器內建的 API。
  • 升級到 Vite 8 還在用 manualChunks 物件寫法：已不支援。改用 build.rolldownOptions.output.codeSplitting。
  • 拿除錯鉤子做線上監控：onRenderTriggered 等只在開發模式有效。

小結

  • 先量測：分清楚是載入（LCP）還是互動（INP）慢。點訂單變色慢是 INP，用 Performance 面板、Vue DevTools、app.config.performance 找出時間花在哪個元件；手機白畫面是 LCP，用 Network 面板看首頁下載了什麼。改完在同樣條件下再量，結果寫進 PR。
  • 元件重新渲染只有兩個來源：自己讀過的響應式資料改了，或父元件傳來的 props 變了。訂單看板是後者：傳「和自己有關的值」（selected）而不是共用的值（selectedId），200 列降到 2 列，這叫 props 穩定性。
  • 找不到原因時用 onRenderTriggered 問 Vue 是哪個物件的哪個屬性觸發了更新（購物車徽章被 JSON.stringify 多記了依賴）；watch、computed 用 onTrigger。它們只在開發模式有效。
  • v-once 跳過不會變的內容；v-memo 依陣列決定要不要跳過，依賴寫錯畫面就停住，是最後手段。畫面沒更新時，對照第 4 課的失去響應清單，再查 v-once、v-memo。
  • 首頁少下載：動態 import 切出 chunk；路由給載入函式，一般元件用 defineAsyncComponent；一處靜態 import 就會把模組拉回主 chunk；選 tree-shaking 友善的套件；只分割大的、多數人用不到的部分，避免請求瀑布。
  • 用 vite build 的輸出驗證報表頁有自己的 chunk，比較主 chunk 的 gzip 大小。Vite 8 改用 Rolldown，手動分 chunk 的設定改成 build.rolldownOptions、output.codeSplitting（見補充與查表）。
  • 報表頁的 2 萬筆唯讀資料用 shallowRef 整批替換、圖表實例用 markRaw；computed 內容相同時回傳舊值；上千列再考慮虛擬列表。

補充與查表

v-if 與 v-show 的取捨

第 7 課講過：v-if 每次切換都建立、銷毀整個子樹，v-show 只切換 CSS。頻繁切換的東西用 v-show，很少顯示的用 v-if。

Vite 8 的打包設定變化

Vite 8（2026 年 3 月發布）把打包工具換成 Rolldown：用 Rust 寫的打包工具，相容 Rollup 的外掛介面，建置速度快很多。設定上的變化（Vite 官方遷移指南）：

  • build.rollupOptions 改名為 build.rolldownOptions，舊名稱已標為 deprecated。
  • output.manualChunks 的物件寫法不再支援，函式寫法 deprecated，改用 Rolldown 的 output.codeSplitting。
  • 預設的 build.target 是 Baseline Widely Available（2026-01-01 的版本）：Chrome 111、Edge 111、Firefox 114、Safari 16.4。要支援更舊的瀏覽器，用 @vitejs/plugin-legacy。
// vite.config.ts（Vite 8）：把 node_modules 裡的套件放進 vendor chunk
export default defineConfig({
  build: {
    rolldownOptions: {
      output: {
        codeSplitting: {
          groups: [{ name: 'vendor', test: /node_modules/ }],
        },
      },
    },
  },
})
