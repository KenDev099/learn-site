階段 3：MongoDB 與文件模型 · 第 7 課

MongoDB 入門：文件建模（內嵌還是參照）與 schema 驗證

行銷部門要做「門市活動頁」：每家門市有介紹、地址、營業時間、照片、推薦商品、限時活動，前台打開一頁就要全部讀出來。欄位每個月都在變：這個月加「寵物友善」，下個月加「插座座位數」，有的門市有、有的沒有。第 1 課說過，這種「以一整份內容為單位讀寫、結構因每筆而異」的資料，放 PostgreSQL 的 JSONB（PostgreSQL 課第 14 課）或 MongoDB 都合理。這三課用 MongoDB 來做，順便學會它的思考方式；訂單、付款仍然留在 PostgreSQL。

這課的任務是替活動頁建好 stores 集合：後台表單送來一份門市資料，要決定它存進資料庫長什麼樣子、價格和日期用什麼型別、哪些東西放在同一份文件裡、之後怎麼修改才不會互相蓋掉，最後讓資料庫自己擋下格式錯誤的寫入。練習 1～4 分散在這條路上：型別與文件形狀是練習 1，評論的獨立集合是練習 4，更新與 upsert 是練習 3，資料庫端驗證是練習 2。

這課的路線：

一份門市資料存進 MongoDB 是什麼樣子？

在 PostgreSQL，門市會是一張 stores 表：先定義好有哪些欄位、每個欄位什麼型別，每一列都長得一樣；營業時間這種一對多的資料，會拆到另一張表再 JOIN 回來。活動頁的需求剛好跟這個方式衝突：欄位每個月在變，而且前台每次都要整份一起讀。

MongoDB 用另一種單位存資料。它是文件資料庫：一筆資料叫一份文件（document），長得像一個 JSON 物件，裡面可以有巢狀物件和陣列，所以一家門市的地址、營業時間、照片可以全部放在同一份文件裡。很多份文件放在一個集合（collection）裡，集合的角色相當於 PostgreSQL 的表，差別在於集合預設不檢查每份文件有哪些欄位：這份有「寵物友善」、那份沒有，都存得進去。這正是活動頁要的彈性，也是這課最後一節要回頭處理的風險。

文件在硬碟上和網路上並不是用 JSON 文字傳的，而是用 BSON。BSON 是 MongoDB 定義的二進位格式，名字來自 Binary JSON：結構跟 JSON 一樣是物件和陣列，但多了 JSON 沒有的型別，例如日期、精確的十進位小數。下一節選型別時就是在選這些 BSON 型別。

後台是 Node 程式，要從程式裡做同樣的事，用官方 driver mongodb（這門課鎖定的版本見課末）。driver 的入口是 MongoClient：它內含一個連線池，也就是預先開好、可以重複使用的幾條資料庫連線，查詢時借一條、用完歸還。所以整個程序只建立一個 MongoClient、大家共用；每個請求都 new 一個，就等於每次重新連線，連線數也會跟著請求量一起長。

import { MongoClient, type ObjectId } from 'mongodb'

type Store = { _id?: ObjectId; name: string; city: string; tags: string[] }

const client = new MongoClient('mongodb://127.0.0.1:16417/?directConnection=true')
const stores = client.db('ds_play').collection<Store>('stores')   // 型別參數：之後的查詢與更新都會檢查欄位

const { insertedId } = await stores.insertOne({ name: '台中門市', city: '台中市', tags: [] })
const doc = await stores.findOne({ _id: insertedId })      // 找不到回 null
const list = await stores.find({ city: '台北市' }).toArray() // find 回傳 cursor，要 toArray()
await client.close()

網址最後的 directConnection=true 是這門課的環境需要的參數，少了它從你的電腦會連不上，原因見課末。

find 回傳的是 cursor（游標），不是陣列：查詢結果還留在伺服器上，driver 會分批取回。toArray() 把所有批次讀完、放進一個陣列；資料量大時改用 for await (const doc of cursor) 一批批處理，避免一次把全部結果載進記憶體。

collection<Store> 的型別參數讓 TypeScript 檢查你寫的欄位名稱，但這個型別只存在 TypeScript 裡，資料庫完全不知道。別的程式、mongosh、舊版的程式都可能寫進不同形狀的文件，讀回來時 TypeScript 仍然說它是 Store。這個問題留到最後一節。眼前更直接的問題是：型別只在 TypeScript 裡，那真正存進資料庫的值是什麼型別？後台表單送來的價格是 '110'、活動結束時間是 '2026-12-31T15:59:59.000Z'，都是字串。

表單送來的價格、日期都是字串，要存成什麼型別？

練習 1 的輸入就是這種樣子：推薦商品的 price 是 '110'、'70.5'，promoEndsAt 是 ISO 字串。最省事的做法是原樣存字串，或者 Number(price) 轉成數字。兩種都存得進去、也讀得回來，錯誤不會在寫入時出現，而是之後在排序、加總、比較時才冒出來。

原因在型別。JSON 只有字串、數字、布林、null、物件、陣列；BSON 多了幾種，正是為了這些情況：

資料該用常見的錯會出什麼事
金額Decimal128（十進位小數，bsonType: 'decimal'）JS 的 numbernumber 是二進位浮點數（TypeScript 課第 5 課），0.1 + 0.2 是 0.30000000000000004；加總、比較金額會有誤差
時間Date（BSON date，bsonType: 'date'）ISO 字串字串只能照字元排序；時區寫法不同的字串比較會錯，也不能用日期運算
整數number（在 int32 範圍內存成 int）—超過 int32 的整數會存成 double；要精確的 64 位元整數用 Long
idObjectId把 ObjectId 轉成字串存{ _id: '6ae6…' } 查不到 ObjectId('6ae6…')，型別不同就不相等

先看金額。存成字串，資料庫只知道它是一串字元：照字元排序時 '70.5' 會排在 '110' 後面（先比第一個字元，'7' 大於 '1'），也沒辦法加總。轉成 JS 的 number 能排序也能加，但 number 是二進位浮點數，很多十進位小數存不精確，加總幾千筆之後就可能差一分錢。Decimal128 是 BSON 的十進位小數型別，用十進位的方式存數字，110.5 存進去就是 110.5。建立時要從字串建，如果先 Number('110.5') 再轉，誤差在變成 number 的那一刻就已經發生了：

import { Decimal128 } from 'mongodb'

const price = Decimal128.fromString('110.5')   // 從字串建立，才不會先經過浮點數
price.toString()                               // '110.5'
// PostgreSQL 的 numeric 經 pg 讀出來本來就是字串，直接 fromString

時間的道理一樣。ISO 字串只有在每一筆都用同一種寫法（同樣的時區標示、同樣的位數）時，照字元排序才剛好等於照時間排序；一旦有人寫 +08:00、有人寫 Z，比較結果就會錯，而且字串不能做「活動結束前 3 天」這類日期運算。存成 BSON date，資料庫存的是一個時間點，排序、比較、運算都正確。轉換只要 new Date('2026-12-31T15:59:59.000Z')。

型別存對了，還有反方向要處理：讀出來回給前端。把文件直接 JSON.stringify，Date 變成 ISO 字串（還好），Decimal128 變成 {"$numberDecimal":"110.5"}，ObjectId 變成字串。API 回應前要自己轉成約定好的格式（例如金額轉成字串 '110.5'），不要讓前端去解析 $numberDecimal。也就是說，進資料庫時把字串轉成 BSON 型別，出資料庫時再轉回 API 約定的格式，型別轉換集中在這兩個邊界。

到這裡，練習 1 的 toDocument 一半已經清楚：價格轉 Decimal128、日期轉 Date。另一半是形狀：地址要組成內嵌物件、推薦商品只留三個欄位。為什麼地址放進門市文件，推薦商品卻要丟掉庫存和描述？這就是下一節的問題。

地址、照片、推薦商品、評論，哪些放進門市文件？

活動頁上的每一樣東西，都有兩種存法。內嵌（embedding）是把相關資料直接放在門市文件裡，例如 address: { city, line }；讀門市時它就跟著回來。參照（referencing）是只存另一份資料的 id，例如 productId: 12，要用時再查一次，或者用 $lookup 在查詢時拼回來（第 8 課）。

PostgreSQL 的正規化會把地址、營業時間拆成別的表再 JOIN，目的是同一件事只存一份、改一處就全部正確。MongoDB 的內嵌刻意反過來，是有意的反正規化：既然活動頁每次都把門市、地址、營業時間一起讀，就一起存，一次讀取拿到全部，不用 JOIN。內嵌還有第二個好處：MongoDB 保證單一文件的更新是原子的，也就是一次更新裡改的所有欄位，要嘛全部生效、要嘛全部不生效，別人不會讀到改一半的文件。放在同一份文件裡的東西，改起來最安全；跨文件的修改要用交易（第 9 課）。

但不是什麼都適合內嵌。內嵌的資料是複製進來的，正式資料一改，複本不會跟著變；內嵌的陣列會讓文件變大，每次讀都要整份傳。所以每一樣東西都要問三個問題：

問題答案做法活動頁的例子
是不是總是一起讀？是，而且只屬於這一份內嵌地址、營業時間、照片清單
會不會獨立變動、被很多地方用到？會參照，必要時內嵌當下的快照商品：正式資料在 PostgreSQL，活動頁存 productId＋放上去當下的品名與價格
會不會無限增加？會獨立集合，用欄位參照回來評論、打卡紀錄

把活動頁的東西逐一套進去，結果是下面這張圖：

地址、營業時間只屬於這家門市，每次都一起讀，內嵌最直接。照片也是一起讀，但它是陣列，會一直有人上傳，所以內嵌時要有上限：活動頁最多放 20 張，怎麼在更新時維持這個上限是下一節的事。

推薦商品是最需要想清楚的一項。商品的正式資料在 PostgreSQL 的 products，會改價、會改庫存。只存 productId，每次顯示都要再查一次商品；整個商品內嵌進來，庫存一變就跟正式資料不一致。答案是兩者都要一點：存 productId 當參照，再內嵌放上去當下的品名與價格，這叫快照。快照不是重複資料：活動頁上「拿鐵 110 元」記錄的是放上去那一刻的事實，商品之後漲價，活動頁不該跟著變（要變就重新上架）。PostgreSQL 的 order_items.unit_price 是同一個道理。快照只放顯示需要的欄位：庫存、描述這些會一直變的東西留在正式資料，內嵌進來就會跟正式資料不一致，還得想辦法同步。這就是練習 1 要把推薦商品裁成 { productId, name, price } 的原因。

評論會一直增加，不能內嵌。一份 BSON 文件最大 16 MB，但真正的問題通常在碰到上限之前就出現了：把每則評論 $push 進門市文件，一年後這份文件有幾萬則評論，每次讀活動頁都要把它們全部傳過網路、解析，每次更新都要改寫一份很大的文件。這叫無限成長的陣列，是最常見的 MongoDB 建模錯誤。陣列只在「有明確上限」時內嵌（照片最多 20 張），沒有上限的放獨立集合：每則評論一份文件，用 storeId 指回門市，要看最新 10 則就只讀 10 份。這是練習 4。

參照有一個代價要知道：MongoDB 沒有外鍵。reviews.storeId 指向的門市被刪了，資料庫不會阻止，也不會連帶刪評論，這件事要由程式負責。PostgreSQL 的外鍵會替你擋下這種情況。

反過來的錯誤也常見：把 PostgreSQL 的每張表一對一搬成集合，再到處用 $lookup 拼回來。這樣得到的是一個沒有外鍵、沒有 JOIN 最佳化器的關聯式資料庫。資料高度關聯就留在 PostgreSQL；用 MongoDB 的前提是大部分讀寫以一份文件為單位。
💡 實務上：建模從「畫面和查詢清單」開始，不是從欄位開始
PostgreSQL 先畫實體關係圖，MongoDB 要先列出存取模式：活動頁一次讀整份（每天幾萬次）、後台改營業時間（偶爾）、評論列表分頁讀（每次 10 則）。每個陣列都問三件事：最多幾筆？誰會改？要不要單獨查？答不出「最多幾筆」的，就不內嵌。設計審查時把這張清單和預估的量寫進文件，前端、PM 加新畫面時，先看它是否符合現有的存取模式；不符合再決定加欄位、加集合，還是這份資料其實該放 PostgreSQL。

模型定好了：一份門市文件裡有地址、營業時間、最多 20 張照片、推薦商品快照和幾個活動。但這份文件不是寫一次就不動：後台的人會加照片、改活動名稱，前台每次有人打卡都要記一筆，而且這些修改可能同時發生。怎麼改，才不會把別人剛改的東西蓋掉？

加照片、改活動、記打卡，怎麼不把別人的修改蓋掉？

前端工程師最直覺的寫法是「讀出、改、寫回」：findOne 拿到整份門市，在 JS 裡 photos.push(...)，再用 replaceOne 把整份存回去。只有一個人在改時沒事。現在想像兩位同事同時操作：A 加一張照片，B 改一個活動名稱。兩人都先讀到同一份舊文件，A 先寫回（有新照片、舊活動名），B 再寫回（舊照片、新活動名），A 的照片就不見了。這叫遺失更新（lost update）：後寫的人把先寫的人的修改整份蓋掉，而且沒有任何錯誤訊息。

問題出在「改」發生在程式裡，資料庫只收到一份完整的新文件，不知道你其實只想改哪一個欄位。解法是把「要改什麼」告訴資料庫，讓它自己改。updateOne(篩選, 更新) 的第二個參數由更新運算子組成，例如 $set（設定欄位）、$push（加進陣列），資料庫在伺服器上直接改那幾個欄位，其他欄位不動。前一節說過單一文件的更新是原子的，所以 A 的 $push 和 B 的 $set 各自完整生效，誰也不會蓋掉誰。這跟第 2 課 Redis 的 HINCRBY 一樣，不會有「讀出、改、寫回」之間被別人插隊的問題。

在 mongosh 試（先建一份），每一行執行後用 db.stores.findOne({ _id: 1 }) 看文件變成什麼樣：

db.stores.insertOne({ _id: 1, name: '信義門市', views: 0, photos: [],
  promos: [{ id: 11, title: '早鳥拿鐵' }, { id: 12, title: '週末可頌' }] })

db.stores.updateOne({ _id: 1 }, { $set: { status: 'open', 'address.city': '台北市' } })  // 設定欄位；用點號改巢狀欄位
db.stores.updateOne({ _id: 1 }, { $inc: { views: 1 } })                                  // 數字加減
db.stores.updateOne({ _id: 1 }, { $unset: { status: '' } })                              // 刪掉欄位
db.stores.updateOne({ _id: 1 }, { $push: { photos: { $each: [{ url: 'a.jpg' }], $slice: -20 } } })
db.stores.updateOne({ _id: 1 }, { $pull: { photos: { url: 'a.jpg' } } })                 // 刪掉符合條件的元素
db.stores.updateOne({ _id: 1 }, { $set: { 'promos.$[p].title': '週末可頌買一送一' } },
                                { arrayFilters: [{ 'p.id': 12 }] })                       // 只改 id 12 的那一個

前三個 updateOne 是最基本的運算子：$set 設定欄位，欄位名稱用點號（'address.city'）就能改巢狀物件裡的一個欄位，不用整個 address 換掉；$inc 把數字加減，瀏覽次數這種計數就用它；$unset 刪掉欄位。

第四個 updateOne（$push 那行）解決上一節留下的「照片最多 20 張」。$push 把元素加進陣列，搭配 $slice 可以在加入後立刻截斷。$slice 要搭配 $each（只加一個也要包成陣列）。負數 -20 是推入後只留最後 20 個；正數 20 是留最前面 20 個，新加的會被丟掉。這就是讓內嵌陣列有上限的方法：上限在每次寫入時由資料庫維持，不用另外排程清理。第五個的 $pull 反過來，刪掉陣列裡符合條件的元素。

最後一個 updateOne 處理「改陣列裡的某一個元素」。直覺寫法是 'promos.1.title' 這種寫死位置的路徑，但陣列的順序會變：前面插入一個活動，位置 1 就變成別的活動，改錯人。改成依條件找元素：$[p] 是一個佔位名稱，arrayFilters: [{ 'p.id': 12 }] 說明 p 指的是 id 等於 12 的元素，所以只有那一個活動的標題會改。只改第一個符合的，也可以在篩選寫 { _id: 1, 'promos.id': 12 }，再用位置運算子 'promos.$.title'。

如果忘了寫運算子，直接 updateOne({ _id }, { name: 'x' })，driver 會擋下來，錯誤是 Update document requires atomic operators，避免你以為在改一個欄位、其實在換整份。真的要整份換掉時用 replaceOne，但先 findOne、在程式裡改、再 replaceOne，就是本節開頭的遺失更新。

打卡是另一種修改。上一節說過打卡紀錄會無限增加，不能 $push 進門市文件；活動頁要的其實只是「每家門市每天幾次」，所以改成每家門市每天一份計數文件，放在 checkins 集合。麻煩在於：今天第一個打卡的人進來時，這份文件還不存在，要新增；之後的人要加 1。這就是 upsert（update 加 insert）：找不到就新增、找到就更新，一個指令完成：

await checkins.updateOne(
  { storeId, date: '2026-11-02' },     // 找這一份
  { $inc: { count: 1 } },              // 找到：加 1；找不到：用篩選條件的欄位建一份新的，再套用 $inc（count 從 0 加成 1）
  { upsert: true },
)
await checkins.createIndex({ storeId: 1, date: 1 }, { unique: true })

最後那個 createIndex 建的唯一索引（unique index）保證集合裡不會有兩份文件的 storeId 和 date 都相同。這個索引要在開始收打卡之前就建好（練習 3 的 ensureCheckinIndex），不是事後補。為什麼 upsert 還需要它？兩個請求同時 upsert，都發現「還沒有」，可能各自新增一份，這一天就有兩份文件、各記一半的數。查詢條件的欄位上有唯一索引時，第二個新增會撞到重複鍵，伺服器會把符合條件的 upsert 自動重試成更新，結果只有一份。官方文件的說法是：要避免多次新增，篩選欄位要有唯一索引。索引的細節在第 8 課。

自己寫「先 findOne，沒有就 insertOne，有就 updateOne」更糟：沒有唯一索引會產生重複，有唯一索引則是後到的請求直接收到 E11000 duplicate key 錯誤。一個 upsert 就把「判斷」和「寫入」交給資料庫一步做完。練習 3 的測試會刻意讓每次資料庫往返變慢、同時打卡 10 次，「先讀再寫」的寫法一定會出錯。

💡 實務上：計數、每日彙總、同步匯入，幾乎都是 upsert＋唯一索引
常見的場景：每日打卡或瀏覽次數、每小時的銷售彙總、每晚把 PostgreSQL 的商品同步一份到 MongoDB（用商品 id 當篩選條件，重跑幾次結果都一樣）。上線前檢查兩件事：篩選條件的欄位有沒有唯一索引，以及篩選條件是否「同一筆資料每次都算出同一個值」（日期要先固定時區，像練習 3 的 taipeiDate，否則午夜前後會分成兩份）。程式碼審查看到「先 find、沒有再 insert」，就請對方改成 upsert；真的收到 E11000 時，API 回 409 並說明是哪個欄位重複，不要回 500。

到這裡，後台程式寫進來的每份文件型別都對、形狀都對，修改也不會互相蓋掉。但這一切都假設寫入的是我們這支寫好型別的程式。第一節留下的問題還在：資料庫本身不檢查任何東西。

後台、匯入腳本、mongosh 都會寫進來，怎麼讓資料庫擋下壞資料？

常聽到「MongoDB 沒有 schema」，更準確的說法是：資料庫預設不檢查，結構的責任移到程式。問題是程式不只一個。活動頁的 stores 集合，除了後台會寫，還有每月把新門市匯入的腳本、加盟品牌的同步程式，以及半夜有人在 mongosh 手動修資料。後台程式的 TypeScript 型別或 Zod 只管得到後台自己；匯入腳本把價格寫成 number、有人手動把 status 打成 'opne'，資料庫都會收下，直到前台讀到才爆炸。

要擋住所有來源，檢查就必須發生在資料庫裡。MongoDB 可以在集合上設定 $jsonSchema 驗證規則：用 JSON Schema 的語法描述文件必須長怎樣，每次新增和更新都由資料庫檢查，不合規則就拒絕寫入。JSON Schema 是一套描述 JSON 結構的標準寫法，required 列必填欄位、properties 描述每個欄位；MongoDB 版本多了 bsonType，讓你指定 BSON 型別：

await db.createCollection('stores', {
  validator: {
    $jsonSchema: {
      bsonType: 'object',
      required: ['name', 'status'],
      additionalProperties: false,              // 不允許 properties 沒列出的欄位
      properties: {
        _id: { bsonType: 'objectId' },          // additionalProperties: false 時一定要列 _id
        name: { bsonType: 'string', minLength: 1, maxLength: 50 },
        status: { enum: ['open', 'closed', 'renovating'] },
        photos: {
          bsonType: 'array', maxItems: 20,
          items: { bsonType: 'object', required: ['url'], properties: { url: { bsonType: 'string' } } },
        },
        price: { bsonType: 'decimal' },
      },
    },
  },
  validationAction: 'error',   // 預設就是 error；寫出來讓讀程式的人知道
})

bsonType 用 BSON 的型別名稱：'string'、'int'、'double'、'decimal'、'date'、'objectId'、'object'、'array'、'bool'。第二節選的型別在這裡變成規則：'number' 表示任何數字型別都可以，所以金額要寫 'decimal' 才擋得住 double；日期寫 'date' 才擋得住字串。照片的 maxItems: 20 則是第三節那個上限的最後一道保險，就算有程式忘了用 $slice，第 21 張也寫不進去。maxLength 算的是字元數，50 個中文字可以。

additionalProperties: false 表示「只允許 properties 列出的欄位」，可以擋下打錯的欄位名稱，但有一個坑：設了它卻沒把 _id 列進 properties，每一份文件都會因為「多了 _id」被擋下，整個集合寫不進任何東西。

違反規則的寫入會失敗，錯誤碼 121（DocumentValidationFailure），errInfo.details 說明哪一條不符合。在 MongoDB 9.0.4 實際試的結果，下面是匯入腳本把價格寫成 number 的情況。看結果裡的 propertyName（哪個欄位）、specifiedAs（規則要求什麼）和 consideredType（實際收到什麼）：

import { MongoServerError } from 'mongodb'

try {
  await stores.insertOne({ name: '信義門市', status: 'open', price: 110 })
} catch (e) {
  if (e instanceof MongoServerError && e.code === 121) console.log(JSON.stringify(e.errInfo?.details))
}
// {"operatorName":"$jsonSchema","schemaRulesNotSatisfied":[{"operatorName":"properties","propertiesNotSatisfied":
//   [{"propertyName":"price","details":[{"operatorName":"bsonType","specifiedAs":{"bsonType":"decimal"},
//   "reason":"type did not match","consideredValue":110,"consideredType":"int"}]}]}]}

新建的集合照上面寫就好。但活動頁不是全新的：集合裡已經有幾百份舊文件，有些可能不符合新規則，而且每月都要加欄位。規則加上去之後，舊文件怎麼辦？不合法時要直接拒絕，還是先記下來觀察？這由兩個設定決定：

設定值意思
validationAction
不合法時怎麼辦		error（預設）拒絕寫入
warn照樣寫入，只在 log 記一筆。用在「先觀察有多少舊程式會違反」的過渡期
validationLevel
哪些寫入要檢查		strict（預設）所有新增與更新都檢查；設定規則之前就存在的舊文件不會被回頭檢查，但更新一份不合法的舊文件時，要把它整份改到合法才寫得進去
moderate新增、以及「原本就合法」的文件的更新才檢查；原本就不合法的舊文件更新時不檢查，讓舊資料可以慢慢修
constraint（9.0 新增）所有新增與更新都檢查，並保證集合裡每一份文件都符合：從既有集合升級時會掃過全部文件，有一份不合法就失敗（其他限制見課末）

兩個設定各管一件事：action 管「不合法時怎麼辦」，level 管「哪些寫入要檢查」。要注意 strict 和 constraint 的差別：strict 不會回頭檢查舊文件，所以集合裡仍然可能有不合法的舊資料；只有 constraint 保證整個集合都乾淨。既有的集合用 collMod 加上或修改規則：

await db.command({ collMod: 'stores', validator: { $jsonSchema: { /* … */ } }, validationLevel: 'moderate' })

資料庫的驗證和程式端的驗證（TypeScript 課第 26 課的 Zod）不是二選一：程式端在使用者送出表單時就給友善的錯誤訊息（「名稱最多 50 字」），資料庫端是最後一道防線，擋住所有寫入的來源。錯誤碼 121 不該是使用者平常會看到的東西，它應該出現在寫入方的錯誤 log 或監控裡；看到它，代表有某個寫入來源繞過了程式端的檢查。

💡 實務上：驗證規則跟程式碼一起進版控，分階段收緊
新集合直接 strict（或 constraint）＋error。替已經有資料的集合加規則時，先 warn 觀察 log，修好資料與程式，再改成 error；需要「整個集合保證乾淨」才升到 constraint，它要掃全部文件，大集合要挑離峰時間。規則寫成 migration 腳本放進專案、跟程式一起部署，不要有人直接在 mongosh 改正式環境。活動頁每月加欄位：先部署「新欄位可有可無」的規則與程式，舊文件補完資料後，再把它加進 required；反過來先加 required，還沒更新的舊程式寫入就會全部失敗。

活動頁的 stores 集合到這裡完整了：型別對的文件（練習 1）、資料庫端的驗證（練習 2）、不互相覆蓋的更新與 upsert（練習 3）、放在獨立集合的評論（練習 4）。換到用 Mongoose 的專案時，這些概念各對到哪裡，整理在課末。

練習

先開 MongoDB（docker compose --profile mongo up -d --wait），每一題都在 learn/ 執行 node check.mjs data-stores 07 判分。測試用 ds_t07 資料庫，每個測試檔開始前會清空。每個檔案開頭的註解寫了欄位與規則。

練習 1：在 model.ts 實作 toDocument(input)，把後台表單的資料轉成 stores 集合的文件。地址組成內嵌物件 { city, line }、營業時間原樣內嵌；推薦商品只留 { productId, name, price } 三個欄位，價格從字串轉成 Decimal128；promoEndsAt 轉成 Date。測試會把結果存進 MongoDB 再讀回來檢查型別。

練習 2：在 validation.ts 實作 createStoresCollection(db)：建立 stores 集合，用 $jsonSchema 寫出檔案開頭列的規則（只允許列出的欄位、name 1～50 字、status 三選一、照片最多 20 張且都有 url、推薦商品的 price 是 decimal），不合法的寫入要失敗。測試會插入一份合法文件和十幾份不合法文件，不合法的都要得到錯誤碼 121，更新成不合法的內容也要被擋下。

練習 3：在 updates.ts 用更新運算子實作：addPhoto 把照片加到最後面、只留最新 20 張；renamePromo 只改 id 相符的那一個活動（不能寫死位置）；checkIn 用 upsert 把當天（taipeiDate(now)）的打卡計數加 1；ensureCheckinIndex 建立 { storeId: 1, date: 1 } 的唯一索引。測試會同時呼叫 addPhoto 5 次、checkIn 10 次，而且讓每次資料庫往返變慢，「先讀再寫」的寫法一定會出錯；也會檢查其他欄位沒有被整份覆蓋。

練習 4：顧客評論會一直增加。在 reviews.ts 把評論設計成獨立的 reviews 集合，用 storeId 參照門市：addReview 新增一則（createdAt 用參數 now），latestReviews(db, storeId, limit) 回傳這家門市最新的 limit 則，由新到舊。在檔案開頭用註解寫下為什麼不內嵌（提到無限成長或 16 MB）。測試寫入 300 則後，用 $bsonSize 確認門市文件的大小沒變。

練習 5：活動頁的推薦商品要怎麼存？

✓ 快照記錄的是「當時的事實」：活動頁寫 110 元，商品之後改價，活動頁不該自己變；保留 productId 讓你需要時還找得到正式資料。a 每次顯示都多一次查詢，而且價格會在活動期間悄悄改變。c 把庫存、描述這些會一直變的東西複製一份，正式資料一改就不一致，還得想辦法同步。

練習 6：既有的 stores 集合已經有一些不合法的舊文件，你用 collMod 加上規則並設 validationLevel: 'moderate'。之後會怎樣？

✓ moderate 讓舊資料可以一份一份慢慢修。a 是 strict（預設）的行為；c 是 validationAction: 'warn'，那是 action 不是 level；d 是升級到 9.0 新增的 constraint 時才會做的事。

練習 7：同事把每位顧客的打卡紀錄 $push 進門市文件的 checkins 陣列。一年後最可能發生什麼？

✓ 這是最常見的建模錯誤：無限成長的陣列。一份文件最大 16 MB，在那之前讀寫就已經越來越慢。會一直增加的資料放獨立集合（像練習 4 的 reviews），或像練習 3 改成每天一份計數文件。a 錯在文件有上限；b MongoDB 不會自動搬資料。

常見錯誤

  • 用 number 存金額：存成 int 或 double，小數加總會有誤差，驗證規則寫 'number' 也擋不住。用 Decimal128.fromString，規則寫 bsonType: 'decimal'。
  • 日期存成字串：排序、比較、日期運算都不可靠。存之前 new Date(…)，規則寫 bsonType: 'date'。
  • 無限成長的陣列內嵌在文件裡：評論、打卡、紀錄放獨立集合；要內嵌的陣列用 $push＋$each＋$slice 設上限。
  • 讀出、改、replaceOne 寫回：同時改的人會互相蓋掉，也會把別人剛加的欄位刪掉。用 $set、$inc、$push 只改要改的部分。
  • 寫死陣列位置：'promos.0.title' 在陣列順序變了之後就改錯元素。用 arrayFilters 或位置運算子 $。
  • 沒有 validator：只靠某一支程式的型別，其他寫入來源的壞資料會默默存進去，讀的人才爆炸。
  • additionalProperties: false 卻沒列 _id：每一份文件都被擋下。
  • 並發 upsert 卻沒有唯一索引：同一天出現兩份打卡文件，各記一半。篩選欄位要有唯一索引。
  • 把 PostgreSQL 的表一對一搬成集合：到處 $lookup，又沒有外鍵。高度關聯的資料留在 PostgreSQL。

補充與查表

這課用到的版本

Node 用官方 driver mongodb 7.8.0（相容表上完整支援 MongoDB 9.0，需要 Node 20.19 以上），課程的 MongoDB 是 9.0.4。很多 Node 專案用的 Mongoose 目前是 9.11.4。

為什麼連線網址要加 directConnection=true

課程的 MongoDB 是單節點的 replica set（複本集）。replica set 是 MongoDB 讓多台伺服器保存同一份資料的機制，第 9 課的交易需要它，所以就算只有一台也設成 replica set。它對外宣告自己的位址是容器裡的 localhost:27017。driver 預設會改連那個位址，從你的電腦連不到；加上這個參數，driver 就只連你給的 127.0.0.1:16417。

constraint 等級的其他限制

validationLevel: 'constraint' 是 MongoDB 9.0 新增的。除了升級時會掃過全部文件、有一份不合法就失敗之外：它不能被略過，規則也不能直接改（要先降回 strict 再改）；action 必須是 error（或同時記 log 的 errorAndLog），不能是 warn。

小結

  • MongoDB 以文件（BSON）為單位讀寫，集合預設不檢查結構；每份文件都有不重複的 _id，預設是含建立時間的 ObjectId。整個程序共用一個 MongoClient。
  • 型別要選對：表單送來的字串，金額轉 Decimal128（用 fromString）、時間轉 Date；回給前端前自己轉格式。
  • 建模看存取模式：一起讀、只屬於這份 → 內嵌；獨立變動 → 參照，需要時存當下的快照；會無限增加 → 獨立集合。單一文件上限 16 MB，單一文件的更新是原子的；沒有外鍵。
  • 「讀出、改、replaceOne 寫回」會遺失更新。用 $set、$inc、$push＋$slice、arrayFilters 做部分更新；upsert 一步完成「找不到就新增」，並發時靠唯一索引保證只有一份。
  • 用 $jsonSchema 讓資料庫擋下所有寫入來源的壞資料：action 用 error；level 有 strict、moderate、9.0 新增的 constraint；additionalProperties: false 要列 _id。
