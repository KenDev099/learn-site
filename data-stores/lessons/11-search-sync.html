階段 4：搜尋與檔案 · 第 11 課

讓搜尋跟資料庫同步（資深）：outbox、重建索引與別名切換

老闆在後台把伯爵紅茶下架了。隔天有客人在 App 搜「紅茶」，伯爵紅茶還在結果裡，點進去卻是 404。查了紀錄：後台更新商品時，程式先改 PostgreSQL，再呼叫 Elasticsearch，那一刻 Elasticsearch 剛好在重啟，錯誤被 catch 吞掉了。資料庫說「已下架」，搜尋引擎說「還在賣」，而且沒有人知道兩邊不一樣。

這一課從頭到尾處理這個事故。目標有兩個：一、資料庫改了，搜尋最後一定會跟上，不管中間 Elasticsearch 重啟、程式崩潰、還是兩個請求交錯；二、兩邊真的對不上時，你會比客人先知道，而且修得回來。只要資料存在兩個地方，就一定會遇到這個問題，所以這套做法在正式環境很常見。

這課的路線：
  1. 伯爵紅茶為什麼還搜得到：先改資料庫、再呼叫 Elasticsearch 這種寫法，到底在哪幾種情況下會漏；目標該怎麼重新定義。
  2. outbox：把「搜尋要更新」寫進同一個資料庫交易，事故就不會再漏（開場問題的最小答案）。
  3. worker 與版本號：誰把事件送到 Elasticsearch、怎麼逐筆確認成敗；重送或順序顛倒時，怎麼不讓舊資料蓋掉新資料。
  4. 改 mapping：同步的路通了之後，要換分析器時怎麼建新索引、用別名切換，而且這段期間的修改不會漏。
  5. 同步延遲與對帳：怎麼在客人抱怨之前知道搜尋落後了、哪幾筆不一樣，以及最糟時怎麼整份重建。
這課會用到：
  • 第 10 課的菜單索引：mapping 決定每個欄位怎麼分析，已經存在的欄位不能改分析器。
  • PostgreSQL 課第 18 課的交易：同一個交易裡的修改一起提交，或一起回滾。
版本：PostgreSQL 18.6、pg 8.23.1、Elasticsearch 9.5.5、@elastic/elasticsearch 9.5.1。

伯爵紅茶為什麼還搜得到？先寫資料庫再寫搜尋，哪裡會漏

先看出事的程式。後台的「更新商品」長這樣：

async function updateProduct(id: number, patch: Patch) {
  await pool.query('UPDATE products SET available = $2 WHERE id = $1', [id, patch.available])  // 1. 寫資料庫
  try {
    await es.update({ index: 'menu', id: String(id), doc: patch })                              // 2. 寫搜尋引擎
  } catch (e) {
    console.error(e)        // 不想讓後台出錯，就吞掉
  }
}

同一段程式分別寫兩個系統，這種寫法叫雙寫（dual write）。它的根本問題是：PostgreSQL 和 Elasticsearch 是兩個獨立的系統，沒有一個「共同的交易」能讓兩邊一起成功或一起失敗。第 1 步提交之後，資料庫的修改就生效了，第 2 步不管發生什麼事都撤銷不了它。所以第 1 步和第 2 步之間發生的任何事，都會讓兩邊不一樣。把所有可能列出來：

失敗方式結果
資料庫成功，ES 失敗（逾時、重啟、網路斷）開頭的事故：搜得到已下架的商品。吞掉錯誤就沒人知道；改成回 500，資料庫其實已經改好了，使用者以為失敗又按一次
先寫 ES 再寫資料庫，資料庫回滾（違反約束、交易衝突）搜尋裡出現資料庫根本沒有的內容
程式在兩步之間崩潰（部署重啟、OOM）跟第一種一樣，而且連錯誤紀錄都沒有
兩個請求交錯資料庫和 ES 的最終值不同，見下圖

前三種至少有一邊「失敗」了，還算看得出來。第四種最麻煩，因為沒有任何一步出錯：店長和副店長幾乎同時改了同一個商品的價格，一個改 120 元、一個改 130 元。

看完這四種，可以得到一個結論：「讓兩邊同時成功」這個目標本身就做不到，再怎麼調整 try/catch 的位置都一樣。所以要換一個目標。

換目標的依據來自第 1 課的分工。PostgreSQL 是記錄系統：一筆資料「真正的值」以它為準，它說伯爵紅茶下架了，就是下架了。Elasticsearch 裡的菜單索引則是衍生資料：它的內容全部是從 PostgreSQL 抄過去、為了搜尋而換個形狀存的副本，就算整份刪掉，也能從資料庫重新產生。既然搜尋只是副本，它可以暫時落後，只要「之後一定會跟上」就好。這種「現在可能還不一樣，但沒有新的修改時，過一段時間一定會一樣」的保證，叫最終一致（eventual consistency）。

所以這一課的目標改成四件事：

  • API 只負責把資料庫的交易做對。資料庫提交了，搜尋之後一定會跟上，通常在幾秒內。
  • 送到搜尋引擎的過程可以失敗、重試、亂序，結果仍然正確。
  • 不管搜尋索引壞成怎樣，都能從資料庫整份重建。
  • 有指標看得出「現在落後多少」，有對帳找得出「哪幾筆不一樣」。

第一件事馬上帶出一個問題：API 提交資料庫交易之後就回應店長了，那「Elasticsearch 還沒更新」這件事要記在哪裡？如果只記在 API 程式的記憶體裡，程式一崩潰就忘了，跟事故一模一樣。

「搜尋要更新」記在哪裡才不會忘？outbox

答案是記在資料庫裡，而且跟商品的修改放在同一個交易。做法叫 outbox（寄件匣）：建一張表，專門存放「等著送出去的事件」。下架伯爵紅茶時，API 在同一個交易裡做兩件事：把 products 的 available 改成 false，並且在 outbox 新增一筆「伯爵紅茶變了，內容是這樣」的事件。因為是同一個交易，這兩個寫入只有兩種結局：一起成功，或一起失敗，不可能出現「商品改了、事件沒寫」。

交易提交後，API 的工作就結束了。另一個獨立的程式，叫 worker，會持續讀 outbox 裡還沒送的事件，把它們送到 Elasticsearch，送成功才標記完成。回到開場的事故：Elasticsearch 在重啟的那一刻，worker 送不出去，事件就留在 outbox 裡；等 Elasticsearch 恢復，worker 下一輪再送，伯爵紅茶就從搜尋結果消失了。差別在於「還沒送」這件事被寫進資料庫，不會因為錯誤被吞掉或程式崩潰而消失。

PostgreSQL 課第 33 課和系統設計課第 12 課已經用 outbox 送過訊息；這一課把它用在搜尋同步，重點放在搜尋特有的問題。先看兩張表：

CREATE TABLE products (
  id int PRIMARY KEY,
  name text NOT NULL, category text NOT NULL, price int NOT NULL,
  available boolean NOT NULL DEFAULT true,
  version int NOT NULL DEFAULT 1          -- 每次修改加 1，等一下給 ES 當版本號
);
CREATE TABLE outbox (
  id bigserial PRIMARY KEY,               -- 寫入順序
  aggregate_id int NOT NULL,              -- 哪個商品
  version int NOT NULL,                   -- 這次變更後的版本
  op text NOT NULL CHECK (op IN ('upsert', 'delete')),
  payload jsonb,                          -- 變更後的內容（delete 時是 null）
  created_at timestamptz NOT NULL DEFAULT now(),
  processed_at timestamptz,               -- 送成功才填
  attempts int NOT NULL DEFAULT 0,        -- 失敗幾次
  last_error text
);
CREATE INDEX outbox_pending ON outbox (id) WHERE processed_at IS NULL;   -- 只索引還沒送的

逐欄看。aggregate_id 記這個事件屬於哪一個東西；「aggregate」（聚合）是設計上的說法，指「一起被修改的一組資料」，這裡就是一個商品。op 分兩種：upsert 表示「搜尋裡這個商品要變成 payload 的內容」，不存在就新增；delete 表示「從搜尋移除」。processed_at、attempts、last_error 是給 worker 記錄送出結果用的，下一節會用到。

最後一行是部分索引（partial index）：只替符合 WHERE 條件的列建索引。outbox 跑久了，絕大部分是已經送完的事件，worker 卻只查還沒送的那些；索引只放未處理的列，就能一直保持很小、很快。

products.version 現在看起來多餘，它是為了「worker 重送或亂序」準備的，後面「重送或晚到的舊事件」那一節會用它擋住舊資料。先記住一件事：每次修改商品，版本都要加 1，而且 outbox 事件要記下「這次修改後的版本」。

接下來寫 API 的交易。用 pg 8.23.1 寫交易，要從 pool 借一條連線，在同一條連線上 BEGIN、執行、COMMIT：

const client = await pool.connect()      // 交易一定要在同一條連線上，pool.query 每次可能換連線
try {
  await client.query('BEGIN')
  const { rows } = await client.query(
    `UPDATE products SET price = COALESCE($2, price), version = version + 1
      WHERE id = $1 RETURNING id, name, category, price, available, version`, [id, patch.price ?? null])
  if (rows.length === 0) throw new NotFoundError()
  const { version, ...payload } = rows[0]
  await client.query(`INSERT INTO outbox (aggregate_id, version, op, payload) VALUES ($1, $2, 'upsert', $3)`,
    [id, version, payload])                // pg 會把物件轉成 JSON 存進 jsonb
  await client.query('COMMIT')
  return version
} catch (e) {
  await client.query('ROLLBACK')
  throw e
} finally {
  client.release()                         // 還給 pool，不還的話連線會被用光
}

為什麼一定要 pool.connect()？pool 裡有好幾條連線，pool.query 每次呼叫可能拿到不同的那條。交易是綁在「一條連線」上的：如果 BEGIN 送在 A 連線、UPDATE 送在 B 連線，UPDATE 根本不在交易裡，outbox 寫入失敗時它也不會被回滾。所以借一條連線，整個交易都在它上面跑，最後在 finally 還回去。

版本號用 version = version + 1 讓資料庫算，不在程式裡算。如果先 SELECT 出版本、在程式裡加 1 再寫回，店長和副店長的兩個並發請求會讀到同一個版本，寫出兩個「第 5 版」，之後就分不出誰比較新。UPDATE 會鎖住那一列，第二個請求要等第一個提交才能更新，所以讓資料庫加 1，版本一定連續；RETURNING 再把加完的版本和更新後的內容一次拿回來，直接放進 outbox 事件。

COALESCE($2, price) 的意思是「有給值就用新值，沒給（null）就維持原值」，讓同一個 SQL 能處理「只改部分欄位」。傳參數時用 patch.price ?? null，不要用 ||：?? 只把 undefined 和 null 換成 null，|| 會把所有假值都換掉，而 available: false、price: 0 都是有意義的值。伯爵紅茶的下架就是 available: false，用 || 的話它會被當成「沒給」，商品根本不會下架。

刪除商品也要寫事件，不然搜尋不知道要移除它。刪除事件的 op 是 delete、payload 是 null，版本是「刪除前的版本 + 1」；為什麼要加 1，後面講版本號時會看到。

事件裡要不要帶完整內容，有兩種做法：本課的做法是帶 payload，worker 照著送就好；另一種是事件只帶 id，worker 送之前再讀一次最新的 products。商品這種小文件、修改不頻繁，帶內容最直接。兩者的比較，以及「用 trigger 自動寫 outbox」「用 CDC 讀資料庫的變更紀錄」這兩條替代路線，放在課末「補充與查表」。

💡 實務上：最終一致要先講好：PM、畫面與不要強制 refresh
改成 outbox 之後，店長在 Vue 後台存檔成功，切到前台搜尋可能還要等一兩秒才看到新價格，客服就會收到「改了沒反應」的回報，所以上線前要跟 PM 說清楚「改完多久內搜得到」，寫進需求。畫面也要配合：後台的商品列表直接查資料庫、不查搜尋，存檔的 API 回傳更新後的商品，Vue 用它更新畫面。前台的搜尋結果只是入口，商品頁、加入購物車、結帳一律再查一次資料庫，商品已下架就顯示「已停售」：就算搜尋還沒跟上，客人點進伯爵紅茶看到的也是「已停售」而不是 404。也不要為了「馬上搜得到」，讓 worker 每筆寫入都帶 refresh: true：每次強制 refresh 都會產生一個小區段（segment，第 10 課），拖慢寫入和搜尋，官方文件也建議維持預設的 refresh=false。

到這裡，「伯爵紅茶下架了」這件事已經安全地躺在 outbox 裡，不會再被忘掉。但事件只是被記下來，還沒有任何東西把它送到 Elasticsearch。worker 要怎麼取事件、怎麼送、怎麼知道送成功了沒？

誰把事件送到 Elasticsearch？worker 取一批、bulk 送出、逐筆確認

worker 是一個獨立執行的程式，通常跟 API 分開部署，固定每隔一小段時間跑一輪。每一輪做這些事：

BEGIN;
SELECT id, aggregate_id, version, op, payload FROM outbox
 WHERE processed_at IS NULL
 ORDER BY id
 LIMIT 100
 FOR UPDATE SKIP LOCKED;          -- 鎖住這批，別的 worker 跳過它們去拿下一批
-- 用一個 bulk 請求送到 ES
-- 成功的：UPDATE outbox SET processed_at = now() WHERE id = ANY(…)
-- 失敗的：UPDATE outbox SET attempts = attempts + 1, last_error = … WHERE id = …
COMMIT;

先看取事件這一步。正式環境常會開兩個以上的 worker，一個掛了另一個還在，事件多時也能一起分擔。這時就要回答：兩個 worker 同時查 outbox，怎麼不拿到同一批？FOR UPDATE 會鎖住取出的列，直到這個交易結束；SKIP LOCKED 讓另一個 worker 遇到被鎖的列時直接跳過，去拿後面還沒被鎖的。PostgreSQL 課第 33 課示範過少了任一個會怎樣：只寫 FOR UPDATE 的話，第二個 worker 會卡在同一批列的鎖上等，兩個 worker 變成輪流做；什麼都不鎖，兩個 worker 會拿到同一批、各送一次。

取到一批之後，送 ES 用 bulk API。一次一筆地送，100 個事件就是 100 個 HTTP 請求，大部分時間花在來回等待；bulk 把很多個動作放進一個請求。每個動作是一行描述（要做什麼、哪個索引、哪個 id），index 動作後面再接一行文件內容，delete 不用。下面每個動作裡的 version 和 version_type 是下一節的主角，先看整體結構：

const res = await es.bulk({
  operations: [
    { index: { _index: 't11-menu', _id: '12', version: 3, version_type: 'external' } },
    { id: 12, name: '拿鐵', category: 'coffee', price: 125, available: true },
    { delete: { _index: 't11-menu', _id: '16', version: 4, version_type: 'external' } },
  ],
})
// res.errors：只要有任何一筆失敗就是 true
// res.items：每個動作一個結果，順序跟送出去的一樣，例如
// [{ index: { _id: '12', status: 201, result: 'created', _version: 3 } },
//  { delete: { _id: '16', status: 404, result: 'not_found' } }]

bulk 的回應最容易讀錯。一個請求裝了很多動作，有的成功、有的失敗都很正常，所以 ES 不會因為其中一筆失敗就讓整個請求失敗：

bulk 回 HTTP 200 不代表每筆都成功。只要請求本身送到了，ES 就回 200，每一筆的成敗寫在 items[i].index.status（或 .delete.status）和 error 裡。只看有沒有丟例外，就會把被拒絕的事件（例如 mapping 不符）標成完成，那筆資料永遠不會進搜尋。

所以 worker 要拿 items 的第 i 筆對回送出去的第 i 個事件，逐筆決定要不要標記完成。最基本的兩種：status 是 200 或 201，表示寫入或刪除成功，標記完成；status 是 400 這類錯誤，表示文件被拒絕，例如 price 是字串、多了 mapping 沒有的欄位，這時不標記，attempts + 1、記下 last_error，讓之後查得到原因。還有 409 和 404 兩種結果要特別處理，它們跟版本號有關，下一節再補完這張規則。

另一種失敗是整個 bulk 請求都沒送成，例如 ES 連不上、逾時，這正是開場事故的情況。這時 bulk 會丟例外，worker 要 ROLLBACK，把錯誤往外丟：ROLLBACK 放掉了鎖，事件都還是未完成，下一輪再送。錯誤要讓排程看得到（記 log、計數、告警），不能吞掉，否則又回到「沒人知道」。

ES 在重啟或過載時，worker 不能每秒狂送，那只會拖慢它恢復。worker 連續失敗時要拉長每輪的間隔，例如 1、2、4、8 秒，最多 1 分鐘，這種「失敗越多次、等越久」的做法叫退避（backoff）。ES 恢復、送成功之後，再回到正常的間隔。

還有一種事件，問題不在 ES，而在資料本身：某一筆因為內容有問題被 mapping 拒絕，重試幾次都一樣會失敗。這種事件叫毒事件（poison message）。如果不處理，它每一輪都會被取出來、佔掉批次的一個位置，也會讓告警一直響。attempts 超過門檻（例如 10 次）就不要再取它（WHERE attempts < 10），並發告警讓人處理。

上面的寫法在 ES 回應前一直開著交易；outbox 也只增不減，需要定期清理。這兩件正式環境的維運細節放在課末「補充與查表」。

worker 的流程有了，但它有一個先天的性質：同一個事件可能被送不只一次，兩個 worker 送出的順序也不一定。開場那張「請求交錯」的圖，會不會換個形式在 worker 身上重演？

重送或晚到的舊事件，怎麼不蓋掉新資料？版本號

先說清楚為什麼會重送。worker 送完 bulk、ES 已經寫入了，但在 COMMIT 標記完成之前 worker 當機，資料庫裡這批事件仍然是「未完成」，下一輪會再送一次。這是刻意的取捨：寧可多送，也不能漏送。這種「每個事件保證送到，但可能送到不只一次」的保證叫至少一次（at-least-once）送達。

再說為什麼會亂序。兩個 worker 並發時，worker A 拿到「拿鐵第 4 版」、worker B 拿到「拿鐵第 5 版」，兩個 bulk 請求誰先到 ES 沒有保證，B 可能先到。如果 ES 照收到的順序寫，最後留下的是第 4 版，跟雙寫那張圖一模一樣，而且沒有任何錯誤。

要防的是同一件事：不能讓舊的資料蓋掉新的。worker 本身判斷不了「ES 現在是第幾版」，所以解法是讓 ES 自己判斷新舊，這就是 products.version 存在的原因。

Elasticsearch 每份文件都有一個 _version。預設的模式叫 internal，由 ES 自己在每次寫入時加 1，它只知道「被寫了幾次」，不知道資料庫裡哪一版比較新。寫入時帶 version 和 version_type: 'external'，就改成用你給的版本，規則是（Elasticsearch 9.5 index API 文件）：

  • 給的版本嚴格大於目前的版本（或文件不存在）才寫入，寫入後 _version 就是你給的值。
  • 否則回 409 version_conflict_engine_exception，什麼都不改。版本一樣也是 409，所以同一個事件重送不會重複寫。

在課程的 Elasticsearch 9.5.5 上實測：先送第 5 版、再送第 4 版，第 4 版得到 409，文件停在第 5 版。所以只要每個事件帶的是「資料庫裡那次變更後的版本」，送幾次、什麼順序都沒關係，ES 最後一定是最新版。重送不會改變結果，這叫寫入冪等（系統設計課第 9 課）；版本只會往上、不會倒退，這叫單調。

這也決定了 worker 怎麼看 409：它要當成成功。409 的意思是「ES 已經有一樣新或更新的資料」，這筆事件要做的事已經有人做了。如果把 409 當失敗重試，版本永遠不會變大，這筆事件會永遠重試下去。

刪除也要帶版本，否則會出現「刪掉的商品復活」。ES 刪除文件後，會暫時記住這份文件被刪時的版本，這個紀錄叫墓碑（tombstone）。在墓碑還在的期間，版本不比墓碑新的寫入一樣回 409。刪除事件的版本設成「刪除前 + 1」，墓碑記住的就是比所有舊事件都大的版本，晚到的舊事件會被擋住。下面比較刪除帶版本和不帶版本：

順序delete 帶 version 6（external）delete 沒帶版本
寫入第 3 版_version 3_version 3
刪除墓碑記第 6 版ES 自己加 1，墓碑記第 4 版
晚到的第 5 版409，商品維持已刪除5 > 4，商品復活

墓碑不會永遠留著，課程的 9.5.5 預設保留 60 秒（設定名稱和查法見課末）。比這更晚到的舊事件仍可能讓刪掉的商品復活，這種少見的情況靠最後一節的對帳抓出來。

現在可以補完 worker 對每一筆結果的規則。404 只會出現在 delete：文件本來就不在，「從搜尋移除」這個目的已經達成，所以也標記完成：

status意思事件怎麼辦
200、201寫入或刪除成功標記完成
409版本衝突：ES 已經有一樣新或更新的版本標記完成，這筆已經過時了
404（delete）文件本來就不在標記完成，想要的結果已經達成
400 等其他文件被拒絕，例如 price 是字串、多了 mapping 沒有的欄位不標記，attempts + 1、記下 last_error

版本號的做法有一個前提：一份 ES 文件由一個來源整份寫入。如果文件由好幾個來源各寫一部分，版本號就不能共用，這種情況的處理方式見課末。

到這裡，日常的同步已經完整：API 寫 outbox，worker 送出，版本號讓重送和亂序都無害。接著團隊想改善搜尋本身，要把 name 換成另一個分析器。第 10 課說過已有欄位的分析器不能改，只能建新索引重新匯入；可是 worker 一刻不停地在寫，搜尋也一刻不能停，這要怎麼換？

要改 mapping 換分析器，怎麼重建索引而搜尋不中斷？別名切換

具體的需求是：把 name 從預設分析器改成 cjk，再加一個 name.keyword。第 10 課提過，已經存在的欄位不能改型別或分析器，因為舊文件已經照舊規則切好詞存進倒排索引了。唯一的辦法是建一個新索引、把資料重新寫進去。

難處在「換過去」的那一刻。如果程式裡寫死 index: 'menu-v1'，換索引就要改程式、重新部署，而且部署的那段時間有的機器讀 v1、有的讀 v2。解法是讓程式永遠不知道真正的索引名稱，只用別名（alias）。別名是一個指向一或多個索引的名稱，查詢別名就等於查詢它指向的索引。程式讀寫 menu，menu 實際指向 menu-20261001，換索引只要改別名指向哪裡，程式完全不用動。別名只指向一個索引時，寫入也可以直接寫別名，所以 worker 一樣寫 menu。

別名解決了「怎麼換過去」，但還有「換過去之前，新索引的資料要怎麼齊」。新索引的資料從 PostgreSQL 全量匯入，因為資料庫是記錄系統；可是匯入要花時間，這段期間後台照常有人改商品，worker 照常把變更寫進別名，也就是舊索引。這些變更要想辦法補到新索引。前面幾節做好的 outbox 和版本號，在這裡剛好派上用場。完整步驟：

  1. 查出別名目前指向哪個索引：es.indices.getAlias({ name: 'menu' }) 回傳 { 'menu-20261001': { aliases: { menu: {} } } }。不要假設舊索引叫 v1，上一次重建可能改過名字。
  2. 記下 outbox 目前最大的 id。之後的變更都在它後面，第 5 步從這裡開始重播。（這個起點在正式環境要往前多拉一段，原因見課末。）
  3. 建新索引：es.indices.create({ index: 'menu-20261101', mappings })。名稱常加日期或版本號，一看就知道是哪一次建的。
  4. 從 PostgreSQL 全量匯入：讀出所有商品，bulk 寫進新索引，每筆帶 version: products.version、version_type: 'external'。資料來源是記錄系統，不是舊索引：舊索引可能本來就有錯。資料量大時分批讀：用 WHERE id > 上一批最後的 id ORDER BY id LIMIT n 一批接一批往下讀，不用 OFFSET，越後面也不會越慢（這叫 keyset 分頁，詳見 PostgreSQL 課第 27 課）；bulk 每批幾百到幾千筆。
  5. 補上匯入期間的變更：把 outbox 裡 id 大於第 2 步記錄的事件，全部重播到新索引。不用管它們有沒有被 worker 處理過，版本號會擋掉重複和舊的：同一個商品如果全量匯入時已經是第 7 版，重播第 6 版只會得到 409。
  6. refresh 新索引：ES 寫入的文件要等 refresh（預設每秒一次）後才搜得到。切換前先 es.indices.refresh({ index })，不然切換後的第一秒，使用者可能搜到 0 筆。
  7. 原子切換： 
    await es.indices.updateAliases({
  actions: [
    { remove: { index: 'menu-20261001', alias: 'menu' } },
    { add: { index: 'menu-20261101', alias: 'menu' } },
  ],
})
    官方文件說明同一個 _aliases 請求裡的動作是一個原子操作，別名不會同時指向兩個索引，也不會有指不到任何索引的空窗。分成 deleteAlias 再 putAlias 兩個請求，中間那幾毫秒的搜尋就會得到「索引不存在」的錯誤。
  8. 再補一次第 5 步：第 5 步做完到切換之間，worker 可能又把幾筆變更寫進舊索引。切換後再重播一次，就不會漏。
  9. 刪除舊索引。正式環境常先留一兩天，新索引有問題時把別名切回去就是回滾。
不要先刪舊索引再建新的。從刪除到匯入完成這段時間，搜尋不是出錯就是 0 筆。新的一定先建好、資料補齊，才切換。

Elasticsearch 也有內建的 _reindex API，可以直接從舊索引複製；它跟從資料庫匯入的差別與適用時機見課末。

💡 實務上：重建索引當成一次上線來排
會遇到的時機：搜尋要支援新的篩選欄位、改中文分詞、調整欄位型別。動手前先確認三件事：ES 的磁碟放得下新舊兩份索引；全量讀取會對 PostgreSQL 造成多少壓力（排在離峰時段，或從唯讀副本讀）；整個流程要跑多久。資料量大時，新索引匯入期間可以先把 refresh_interval 設成 -1、number_of_replicas（每份資料另外存幾份副本）設成 0，匯入完再改回原值並等副本建好，這是官方「提升寫入速度」建議的做法。切換前比對新舊索引的文件數，跑幾個常用查詢（例如「拿鐵」「紅茶」）看結果合不合理；舊索引留著，出問題時把別名切回去。這些步驟寫成操作手冊（runbook），跟維運約好時間再做。

到這裡，日常同步和重建索引都不會漏資料了，至少在設計上是這樣。可是開場事故真正可怕的地方是「沒有人知道」。墓碑過期後才到的事件、有人直接下 SQL 改資料庫、某次部署帶進來的 bug，都可能繞過前面所有的機制。怎麼在客人抱怨之前發現？

怎麼比客人先知道搜尋沒跟上？同步延遲、對帳與全量重建

要回答兩個問題：一、現在搜尋落後資料庫多久？二、到底是哪幾筆不一樣？前者靠同步延遲的指標，後者靠對帳。

同步延遲（lag）是「資料庫改了之後多久才搜得到」。outbox 剛好提供了量它的方法：最舊的那一筆未處理事件，建立到現在經過的時間，就是目前最久的一筆變更已經等了多久。

SELECT coalesce(extract(epoch FROM now() - min(created_at)), 0) AS lag_seconds,
       count(*) AS pending
  FROM outbox WHERE processed_at IS NULL;

把 lag_seconds 定期送進監控（DevOps 課第 22 課），設告警，例如「超過 60 秒持續 5 分鐘」。worker 當掉、ES 掛掉、有毒事件卡住，這個數字都會一直變大。只看 ES 的 CPU 或 API 回應時間看不出來：它們都很正常，但資料就是沒過去。另外也監控 attempts 超過門檻的事件數，那是被跳過的毒事件，不會反映在延遲上。如果開場的事故發生時已經有這個告警，Elasticsearch 重啟後事件卡住的那幾分鐘，值班的人就會收到通知。

延遲指標只看得到「還在 outbox 裡等的事件」。根本沒寫進 outbox 的變更，或 ES 收到後又被覆蓋的錯誤，它都看不到。這時要靠對帳（reconciliation）：定期（例如每天半夜）把兩邊的資料拿出來比對，找出差異並修正。它是兜底的機制，專門抓前面所有機制都漏掉的情況：墓碑過期後才到的事件、有人直接改了資料庫卻沒寫 outbox、某次部署的 bug。

比對不用比內容，比 (id, version) 就夠了：每次修改商品版本都會加 1，ES 的 _version 又是照資料庫的版本寫進去的，兩邊版本一樣，內容就一樣。差異分成三種：

差異意思修正
missing資料庫有、ES 沒有用資料庫的內容 index，帶資料庫的版本
staleES 的 _version 比資料庫舊同上
orphanedES 有、資料庫沒有（刪掉的商品還搜得到）delete，帶「ES 的版本 + 1」

修正時一定要帶版本號：不帶的話 ES 用自己的 internal 版本（原本加 1），跟資料庫對不上，下次對帳又被判成 stale。

對帳要讀出 ES 全部的 id 和版本，這裡有一個上限要注意。一般的分頁用 from（跳過幾筆）加 size（取幾筆），但兩者相加不能超過 index.max_result_window，預設 10,000，超過直接回錯誤（9.5.5 實測：「Result window is too large」）。要走訪全部文件，改用排序加 search_after：每頁依 id 排序，下一頁從上一頁最後一筆的排序值之後開始，不管走到第幾頁，每次都只取一頁，沒有上限：

let after: estypes.SortResults | undefined
for (;;) {
  const res = await es.search({
    index: 'menu', size: 1000, sort: [{ id: 'asc' }], search_after: after,
    version: true,           // 回傳 _version
    _source: false,          // 只要 id 和版本，不要整份文件
    query: { match_all: {} },
  })
  const hits = res.hits.hits
  // 處理 hits：h._id、h._version
  if (hits.length < 1000) break
  after = hits.at(-1)!.sort  // 這一頁最後一筆的排序值
}

排序要用唯一而且穩定的欄位（這裡是文件裡的 id），不然同樣排序值的文件可能在換頁時被跳過或重複。走訪期間還有寫入時怎麼辦，見課末。

最後一道防線是全量重建：當 ES 整個壞掉、或對帳發現大量差異，直接跑上一節的重建流程（新索引＋從資料庫匯入＋別名切換）。這是「搜尋是衍生資料」最大的好處：最糟的情況就是重建一次，不會掉資料。重建要定期演練、記下需要多久，事故時才知道「搜尋會不完整多久」。

💡 實務上：同步延遲告警響了，照這個順序查
半夜收到「搜尋同步延遲超過 60 秒」的告警，值班的人照順序查：一、pending 是一直增加，還是卡在固定幾筆？一直增加通常是 worker 沒在跑或 ES 連不上，看 worker 的 log，再用 GET _cluster/health 確認 ES 本身是否正常。二、卡在固定幾筆，就查 attempts 高的事件和它的 last_error，多半是 mapping 拒絕（欄位型別不符），修好資料或 mapping 後把這些事件的 attempts 歸零，讓 worker 重新取。三、ES 恢復後，pending 應該開始下降；不降就是 worker 自己有問題。這份清單寫進 runbook，新人值班也能處理。告警門檻跟 PM 約定的「多久內搜得到」對齊，不要設得比需求還嚴，不然值班的人會開始忽略它。

回頭看開場的伯爵紅茶：outbox 讓「下架」不會被忘掉，worker 和版本號讓它最後一定送到、不會被舊資料蓋回去，延遲告警和對帳讓「兩邊不一樣」不再沒人知道，真的壞了還能整份重建。

補充與查表

這裡收主線提過、但做到這一步不需要記住的細節，查表用，不用背。

事件要帶內容，還是讓 worker 讀最新資料？

事件帶內容（payload，本課的做法）事件只帶 id，worker 讀最新的 products
worker 的工作照事件送，不用查資料庫每批再查一次 products
outbox 大小每筆都存一份內容，比較大很小
同一個商品連改 10 次送 10 次（版本號會擋掉舊的）可以合併成 1 次，讀到的就是最新的
要注意payload 的格式就是 ES 文件的格式，改 mapping 時兩邊要一起改版本號要用讀到的那一列的 version，不能用事件的 version，不然內容和版本對不上

兩種都常見。商品這種小文件、修改不頻繁，帶內容最直接；文件大或同一筆改得很頻繁（例如熱銷度每分鐘變），讀最新資料比較省。

用 trigger 寫 outbox。也可以用 trigger（PostgreSQL 課第 23 課）在 products 改變時自動寫 outbox：好處是任何地方改資料（包括有人直接在資料庫下 SQL）都不會漏；代價是邏輯藏在資料庫裡，看應用程式碼看不出來，payload 的格式改起來也要寫 migration。團隊都透過同一個 API 改資料時，寫在程式裡比較好懂；常有批次腳本或多個服務直接改表時，trigger 比較保險。

CDC：不改應用程式的另一條路。CDC（change data capture，變更資料擷取）是讀資料庫自己的變更紀錄，把每一筆 INSERT／UPDATE／DELETE 送出去。PostgreSQL 的變更紀錄是 WAL，邏輯解碼把它轉成「哪張表、哪一列、改成什麼」（PostgreSQL 課第 37 課）；常用的工具是 Debezium，它佔用一個 replication slot，把變更送進 Kafka，再由另一個程式寫進 ES。

outbox＋workerCDC（Debezium 等）
應用程式每個改資料的地方都要寫 outbox（或用 trigger）不用改，連直接下 SQL 的修改都會被捕捉
多出來的元件一個 worker 程式Debezium、通常還有 Kafka／Kafka Connect，各自要部署、監控、升級
事件格式你決定（例如完整的搜尋文件）資料表的一列，欄位改名、拆表會直接影響下游
出事時outbox 表堆積，SQL 就查得到CDC 停太久，replication slot 讓 WAL 一直堆，可能塞滿資料庫的磁碟

CDC 也可以搭配 outbox：只讓 Debezium 讀 outbox 表（outbox event router），省掉 worker 的輪詢，事件格式仍由你決定。小團隊、一個資料庫、幾個需要同步的索引，outbox＋worker 就夠了；當很多服務都要訂閱資料變更、或已經在跑 Kafka，CDC 的成本才划算。

交易開著等 HTTP。worker 的寫法在 ES 回應前一直開著交易、鎖著這批列。批次小、ES 正常時沒問題；如果 ES 很慢，交易拖太久會擋住 VACUUM。另一種做法是 PostgreSQL 課第 33 課的租約（lease）：先用一個短交易把事件標成「處理中，到 X 時間為止」並提交，送完再用另一個交易標完成。

outbox 清理。outbox 只增不減，一年後會有幾千萬列。排程刪掉 processed_at 超過 7 天的事件（留幾天方便查問題）。

墓碑保留多久。由索引設定 index.gc_deletes 決定，課程的 9.5.5 預設 60 秒（GET t11-menu/_settings?include_defaults=true 可以查）。

一份文件由多個來源寫入。版本號只在「一份文件由一個來源整份寫入」時好用。如果 ES 文件由好幾個來源各寫一部分（商品資料來自 products、熱銷度來自訂單統計），它們的版本號不能共用，要嘛在送出前組成完整文件，要嘛用 if_seq_no／if_primary_term 這類樂觀並發控制，這是期末專題會處理的情況。

重播起點為什麼要往前拉。重建的第 2 步記下最大 id 時，可能有交易已經拿到比較小的 id、但還沒提交（bigserial 的值在 INSERT 時就決定，提交順序不一定跟 id 一樣）。這個變更不在全量匯入讀到的快照裡，id 又比記下的值小，重播時會漏掉。正式環境把重播的起點往前多拉一段（例如記下的 id 減去最近一分鐘的事件數，或改用 created_at >= 開始時間 - 1 分鐘），反正版本號讓重播多少次都安全；漏網的情況還有對帳兜底。

_reindex API。Elasticsearch 內建的 _reindex 可以把舊索引的文件直接複製到新索引。只是改分析器、文件內容不變時，它比從資料庫匯入快；但它的資料來源是舊索引，舊索引已經錯的東西會照抄過去。文件結構改了（新增欄位、改計算方式）時，還是從資料庫重建。

走訪期間有寫入。對帳走訪全部文件時如果還有寫入，官方建議搭配 point in time（es.openPointInTime）讓每一頁都看到同一個時間點；對帳本來就容許「剛好在改的那幾筆」下次再修，所以本課省略。

練習

先啟動 PostgreSQL 與 Elasticsearch（在 learn/data-stores/practice 執行 docker compose --profile pg --profile search up -d --wait，Elasticsearch 第一次啟動要一兩分鐘），每一題都在 learn/ 執行 node check.mjs data-stores 11 判分。測試用 PostgreSQL 的 schema t11 與 t11- 開頭的索引，每個測試檔開始前會清空。表和 mapping 寫在 schema.ts（不用改），每個檔案最上面的註解寫了規則與要回傳什麼。

練習 1：在 outbox.ts 實作 updateProduct(pool, id, patch) 與 deleteProduct(pool, id)：在同一個交易裡改 products（版本加 1）並寫一筆 outbox 事件，upsert 事件帶更新後的內容。測試會暫時加一個讓 outbox 寫入失敗的 CHECK 約束，確認商品也沒被改；並讓同一個商品並發更新 10 次，版本要剛好是 2～11。BEGIN／COMMIT 要送在 pool.connect() 借來的 client 上，直接用 pool.query 送會被判錯。

練習 2：在 sync-worker.ts 實作 runOnce(pool, es, index, batchSize)：用 SKIP LOCKED 取一批事件，用一個 bulk 請求寫進 ES（index 與 delete 都帶外部版本號），逐筆檢查結果，成功、409、delete 的 404 才標記完成，回傳完成的數量。測試會送亂序的版本、刪除後才到的舊事件、一筆會被 mapping 拒絕的事件，用一個連不上的 client 模擬 ES 當機，最後讓兩個 worker 並發處理 200 個事件，檢查每個事件只送一次、而且兩個 worker 真的同時在工作。

練習 3：在 reindex.ts 實作 reindexWithAlias(pool, es, alias, newIndex, mappings)，照「改 mapping」那一節的 9 個步驟零停機重建。測試會在你的全量讀取一回傳時，偷偷改 3 個商品、刪 1 個（其中 2 筆的事件 worker 已經處理過，processed_at 有值）；第一次重播讀完 outbox 時再改 1 個，要靠切換後的第二次重播補上。另一個迴圈在整個過程中不停搜尋別名，不能有任何一次出錯或得到 0 筆；測試建新索引時會關掉自動 refresh，切換前要自己 refresh。舊索引的名稱不是 v1，要從別名查出來。

練習 4：在 reconcile.ts 實作 reconcile(pool, es, alias)：比對兩邊的 (id, version)，回傳 { missing, stale, orphaned } 並修正。測試資料有 10,500 筆（超過 from + size 的上限），差異分散在前段和 10,000 之後；修正後再對帳一次，三種差異都要是空的。

練習 5：API 先更新 PostgreSQL，再呼叫 Elasticsearch，ES 失敗就回 500 給使用者。這樣有什麼問題？

✓ b。兩個系統沒有共同的交易，回 500 不會撤銷已經提交的資料庫修改，ES 也沒更新。正確做法是 API 只做資料庫交易（同時寫 outbox），同步交給 worker。ES 不會、也沒辦法回滾 PostgreSQL；這也不只是變慢的問題。

練習 6：worker 把事件寫進 ES 時帶 version 與 version_type: 'external'，主要是為了什麼？

✓ c。external 版本只接受比目前更大的版本，重送的事件（版本相同）和晚到的舊事件（版本較小）都回 409，寫入因此冪等而且只會往前。它不會讓寫入變快，也不是必填（預設是 ES 自己管版本）；delete 不存在的文件本來就只回 404。

練習 7：要把菜單索引的 name 改成 cjk 分析器，哪個順序對？

✓ b。新索引先準備好、資料補齊，再原子切換，使用者不會看到錯誤或空結果。a 在匯入完成前搜尋全部失效；c 做不到，已存在欄位的分析器不能改；d 的兩個請求之間別名不存在，那一瞬間的搜尋會出錯。

練習 8：要設一個告警，在「資料庫改了但搜尋一直沒跟上」時通知值班，該監控什麼？

✓ b。這個值就是「最久的一筆變更已經等了多久還沒進搜尋」，worker 停了、ES 掛了、毒事件卡住都會讓它持續上升。CPU、回應時間、連線數在同步停擺時可能都很正常。

常見錯誤

  • 在 API 裡雙寫，再把 ES 的錯誤吞掉：兩邊不一致而且沒人知道。API 只寫資料庫（加 outbox），同步交給 worker。Code review 時搜尋一下 es.index、es.update：出現在 API 的存檔流程裡，就是雙寫。
  • outbox 在另一個交易寫：先提交 products、再寫 outbox，中間失敗就漏事件。兩個寫入用同一個 client、同一個 BEGIN … COMMIT。
  • 版本號在程式裡算：先讀再加 1，並發時兩個請求寫出同一個版本。讓資料庫 version = version + 1 … RETURNING version。
  • 刪除沒有寫事件，或刪除沒帶版本：搜尋裡留著已刪除的商品，或被晚到的舊事件救活。刪除事件帶「刪除前 + 1」的版本，用 external 版本刪除。
  • worker 沒有 SKIP LOCKED：沒鎖會重複處理，只有 FOR UPDATE 會互等，多開 worker 也不會變快。
  • 只看 bulk 有沒有丟例外：HTTP 200 也可能有其中幾筆失敗。逐筆看 items 的 status。
  • 把 409 當失敗重試：409 代表 ES 已經有更新的版本，這筆事件該標完成，不然它會永遠重試。
  • ES 失敗也把事件標成完成：那批變更永遠不會進搜尋。整個請求失敗就 ROLLBACK 並丟錯，事件留到下一輪。
  • 程式寫死索引名稱：換索引要改程式、重新部署，不可能零停機。程式只用別名，舊索引名稱從別名查。
  • 重建時先刪舊索引、或切換別名分兩個請求、或切換前沒 refresh：搜尋會出錯或得到 0 筆。新索引補齊、refresh 之後，用一個 _aliases 請求切換。
  • 重建時只做全量匯入：匯入期間的變更寫到舊索引去了。重播這段期間的 outbox 事件，切換後再重播一次。
  • 沒有延遲指標、沒有對帳：出事時要等客人來抱怨才知道。監控最舊未處理事件的年齡，每天對帳一次。
  • 對帳用 from／size 一次讀完：超過 10,000 筆直接出錯，或只讀到前一萬筆。用 sort＋search_after 分頁。
  • outbox 從不清理：表和索引無限長大，worker 的查詢越來越慢。排程刪掉處理完超過幾天的事件。

小結

  • 雙寫沒有共同交易，失敗、崩潰、請求交錯都會讓資料庫和搜尋不一致，所以目標改成最終一致：資料庫是記錄系統，搜尋是可以重建的衍生資料，之後一定跟上，而且看得到落後多少。
  • outbox：改資料和寫事件在同一個交易、同一個 client；版本由資料庫 version = version + 1 遞增；刪除也要有事件。事件可以帶內容，也可以只帶 id 讓 worker 讀最新資料（比較見課末）。
  • worker 用 FOR UPDATE SKIP LOCKED 取一批、一個 bulk 送出、逐筆看 status：成功、409、delete 的 404 標完成，其他記 attempts；整個請求失敗就 ROLLBACK 並丟錯，連續失敗要退避，毒事件設上限。
  • 送達是至少一次而且可能亂序；version_type: 'external' 只接受更大的版本，讓重送和亂序無害；delete 也帶版本，墓碑預設保留 60 秒（index.gc_deletes）。
  • 改 mapping：建新索引 → 從資料庫全量匯入 → 重播期間的 outbox 事件 → refresh → 一個 _aliases 請求原子切換 → 再重播一次 → 刪舊索引。程式永遠只用別名。
  • 上線要有：最舊未處理事件的年齡（同步延遲）告警、用 search_after 走訪的每日對帳、演練過的全量重建流程、outbox 清理。
  • CDC（Debezium、邏輯複寫）不用改應用程式，但多一套要維運的系統；需要的服務多了才划算（見課末）。
