階段 2：Redis 不只是快取 · 第 2 課

Redis 的資料結構：string、hash、list、set、sorted set

在 NestJS 課第 19 課，Redis 用來放快取：把查詢結果 JSON.stringify 成一個字串存起來，過期就丟。咖啡店會員中心後來又加了四個小功能，也照同樣的方式存，每個功能一個 key，值是一整包 JSON 字串：購物車、最近瀏覽的商品、今天來過的會員、每週人氣排行。上線一個月，客服轉來四個回報：客人在手機和電腦同時把拿鐵、可頌加進購物車，結帳時只剩一樣；「最近瀏覽」越存越長，Redis 的記憶體一直漲；後台的「今日來客數」比門市實際刷卡的人數少；人氣排行每次都要把整週的銷量拿出來在程式裡排序，越來越慢。

這四個問題都不是 Redis 不穩，而是存法選錯了。Redis 的值不只有字串，還有 hash、list、set、sorted set，每一種都有自己的指令，而且每個指令都在 Redis 伺服器上一次做完。這一課的任務是把這四個功能一個一個換成合適的結構，最後在 Node 裡寫成練習的四個模組。做完之後，下次遇到新需求，你會知道先問哪幾個問題、該挑哪種結構。

這課的路線：
  1. 開好練習用的 Redis，查出購物車為什麼會少一樣商品，以及四個功能各該換成哪種結構（開場問題的最小答案）。
  2. 換結構之前，每個 key 都要先決定的三件事：型別、名稱、什麼時候消失。
  3. hash、list、set、sorted set：依序改好購物車、最近瀏覽、每日訪客、人氣排行，每換一個都看它解決了什麼、還留下什麼。
  4. 搬進 Node：ioredis 拿回來的是 number 還是字串；資料變大時哪些指令會卡住所有人，以及怎麼替新需求挑結構。
這課會用到：
  • NestJS 課第 12 課的 Docker Compose：docker compose up -d 開服務，docker compose exec 進容器下指令。
  • NestJS 課第 19 課的 Redis：資料放在記憶體的 key-value 資料庫，key 可以設 TTL，到期自動刪除。

先開好這門課的 Redis

要查購物車的問題，得先有一台可以下指令的 Redis。這門課會用到好幾種服務：Redis、MongoDB、Elasticsearch 等等，全部同時開，筆電的記憶體撐不住。所以 learn/data-stores/practice/compose.yaml 把它們分組：Docker Compose 的 profile 就是替服務分組的標籤，每個服務標上屬於哪一組，啟動時用 --profile 指定組名，只有那一組會開。這課只需要 redis 這一組。第一次先安裝套件，再開 Redis：

$ cd learn/data-stores/practice
$ npm ci                                         # 第一次才需要：裝 ioredis 等套件
$ docker compose --profile redis up -d --wait    # 只開 redis 這一組；--wait 等到 healthcheck 通過
$ docker compose exec redis redis-cli            # 進到容器裡的 redis-cli
127.0.0.1:6379> SET ds:hello "world"
OK
127.0.0.1:6379> GET ds:hello
"world"

看到 "world" 就代表 Redis 在跑。接下來是兩個連線時會碰到的數字。

第一個是 port。容器裡的 Redis 聽 6379，對外發布在你電腦的 127.0.0.1:16479。這門課的 port 都在 16400～16499，避開你電腦上可能已經有的 Redis（6379）和 NestJS 課的 6380。你在 redis-cli 的提示字元看到的 6379 是容器裡面的 port；程式從你的電腦連進來，要用 16479。

第二個是資料庫編號。程式連線的網址是 redis://127.0.0.1:16479/0，最後的 /0 是資料庫編號：一個 Redis 有 16 個互相隔開的資料庫，編號 0～15，在 DB 0 寫的 key，切到 DB 2 就看不到。redis-cli 預設在 0，用 SELECT 2 切換。這門課用這個隔離來保護判分：

練習的測試用 DB 2（第 N 課用 DB N），而且每次判分前會把 DB 2 清空。你在 redis-cli 的 DB 0 隨便試，不會影響判分。正式環境通常只用 DB 0，用 key 的前綴區分功能；把資料分散到多台 Redis 的 Redis Cluster 只有 DB 0（第 6 課）。

環境好了，回到開場的第一個回報：購物車為什麼會少一樣商品。

購物車為什麼會少一樣商品？

先看現在的購物車怎麼存。它是一個 key ds:cart:42（42 是會員 id），值是整個購物車的 JSON 字串，例如 {"2":1}，代表商品 2（拿鐵）1 杯。加一樣商品，程式要做三步：GET 讀出整包字串、JSON.parse 之後在程式裡把新商品加進去、JSON.stringify 再 SET 寫回。

只有一個請求時，這三步沒有問題。問題出在客人同時用兩台裝置：手機按下「加入拿鐵」、電腦按下「加入 2 個可頌」，兩個請求幾乎同時到達，購物車原本是空的：

時間   手機（加拿鐵）                  電腦（加 2 個可頌）
 1     GET → {}
 2                                     GET → {}
 3     在程式裡改成 {"2":1}，SET
 4                                     在程式裡改成 {"5":2}，SET   ← 整包蓋掉手機寫的拿鐵

兩個請求在第 1、2 步讀到同一份舊資料，各自在自己的記憶體裡改完，再整包寫回。電腦那一包裡根本沒有拿鐵，它一寫回，手機的修改就不見了。這種「兩個請求都讀到舊值，後寫的蓋掉先寫的」的情況叫遺失更新（lost update），PostgreSQL 課第 19 課在資料庫裡看過同一件事。

Redis 本身沒有做錯任何事：它忠實執行了每一個 GET 和 SET。出問題的是「讀出、修改、寫回」被拆成三個指令，中間有空隙，別人的指令可以插進來。要補這個空隙，得知道 Redis 怎麼執行指令：Redis 主要用一個執行緒依序處理指令，一個指令開始執行到結束，中間不會有別的指令插進來。所以只要「讀出、修改、寫回」是同一個指令，就不會有空隙。最直接的例子是 string 的 INCR。購物車要換成下一節的 hash 才能一步改一個商品，所以先用最簡單的計數器 ds:visits（店裡今天被瀏覽了幾次）看「一步做完」長什麼樣子。

string 是 Redis 最基本的值，也就是購物車現在用的那種：文字、數字、甚至圖片的位元組都可以，最大 512 MB。Redis 不分「數字型別」，數字也是以字串存，只是 INCR 這類指令會把它當整數算：

127.0.0.1:6379> SET ds:visits 10
OK
127.0.0.1:6379> INCR ds:visits          # 加 1，回傳新的值（整數）
(integer) 11
127.0.0.1:6379> INCRBY ds:visits 5
(integer) 16
127.0.0.1:6379> GET ds:visits
"16"                                     # 讀出來是字串

INCR 在伺服器上把「讀出、加一、寫回」一步做完，一百個請求同時 INCR，結果一定是加了一百。換成在程式裡 GET、加一、SET，就是上面的時間軸：兩個請求可能都讀到 10、都寫回 11，少算一次。這就是這一課挑結構的核心：挑 Redis 的資料結構，很大一部分就是在挑「哪個指令能一步做完我要的修改」。

用這個標準看開場的四個功能，最小的答案是：

功能要做的修改換成一步做完的指令
購物車某個商品的數量加減hash：一個 key 底下很多欄位，每個商品一個HINCRBY，只動那一個欄位
最近瀏覽放到最前面，只留 5 個list：有順序的一排LPUSH 放入、LTRIM 剪短
今天來過的會員記一位會員，重複的不算set：不重複的集合SADD，重複的自動忽略
每週人氣排行賣一杯就加分，隨時要前幾名sorted set：依分數排好的集合ZINCRBY，Redis 隨時維持排序

後面四節會一個一個換。但這些結構都掛在 key 上，而且舊的 key 現在還是 string，換之前要先弄清楚 key 共通的規則。

換結構之前：每個 key 都要決定型別、名稱和過期時間

Redis 裡所有的 key 合起來叫 key 空間（keyspace）。每個 key 對應一個值，值有型別，型別決定能對它用哪些指令。對 string 下 list 的指令會直接被拒絕：

127.0.0.1:6379> SET ds:x 1
OK
127.0.0.1:6379> LPUSH ds:x a
(error) WRONGTYPE Operation against a key holding the wrong kind of value
127.0.0.1:6379> TYPE ds:x
string

這跟換結構直接相關：ds:cart:42 現在存的是 JSON 字串，新程式直接對它下 hash 的指令，也會拿到 WRONGTYPE。一個 key 同一時間只能是一種型別，所以「換結構」實際上是「換一個 key」或「先刪掉舊的 key」。後面講命名時會看到怎麼用 key 名稱處理這件事。

檢查和清理 key 時，有幾個指令不分型別都能用（查表用，不用背）：

指令做什麼回覆
TYPE key看值的型別string、hash、list、set、zset；不存在是 none
EXISTS key存不存在1 或 0
DEL key刪掉刪掉幾個
EXPIRE key 秒／PEXPIRE key 毫秒設定多久後自動刪掉1；key 不存在時是 0，什麼都沒設
TTL key／PTTL key還剩幾秒／幾毫秒-1：沒有過期時間；-2：key 不存在

過期時間。表裡的 TTL（time to live）是 key 自動過期的時間：時間一到，Redis 自己把 key 刪掉，不用寫程式去清。開場的「最近瀏覽越存越長、記憶體一直漲」，一部分就是因為那些 key 從來沒有過期時間。購物車、最近瀏覽這類暫時的資料，都該有 TTL。TTL 有三個規則，練習 1 會用到。

第一，EXPIRE 對不存在的 key 什麼都不做，回 0。所以順序一定是先寫入資料、再設過期時間；反過來寫，EXPIRE 那一步等於沒做。

第二，用 SET 整個蓋掉一個 key，原本的 TTL 會被清掉，TTL 變成 -1；INCR、HINCRBY 這類「改內容」的指令不會動到 TTL。這代表「購物車 7 天沒動才過期」不能只在建立時 EXPIRE 一次：之後每次加減都不會延長它，7 天一到，客人正在用的購物車也會消失。要做到「7 天沒動」，每次寫入後都要再 EXPIRE 一次，把倒數重新設回 7 天。

第三，TTL 掛在整個 key 上：購物車過期是整車一起消失，不是一個商品一個商品消失。需要單一欄位各自過期的做法見課末「補充與查表」。

key 的命名。Redis 沒有表、沒有 schema，key 名稱就是你唯一的結構。常見的慣例是用冒號分層：

ds:cart:42              ds（這個系統）: cart（功能）: 42（使用者 id）
ds:rank:2026-W45        每週人氣排行，週次放進 key
ds:v2:menu:7            資料格式改版時加版本：新舊程式同時上線也不會讀到對方的格式

前綴讓不同功能不會撞名，也讓你在 redis-cli 一眼看出這個 key 是誰的。第三行對應剛才的 WRONGTYPE：資料格式改版時把版本放進 key，新程式寫新 key、舊程式讀舊 key，部署期間兩版同時在跑也不會讀到對方的格式；舊的 key 有 TTL，時間到就自己消失。

key 裡帶進 id、日期、週次，就等於在設計查詢：要拿會員 42 的購物車，算出 ds:cart:42 就拿得到；要拿第 45 週的排行，算出 ds:rank:2026-W45 就拿得到，不需要搜尋。這一點很重要，因為在 Redis 裡「搜尋 key」很貴：

KEYS ds:cart:* 能列出符合的 key，但它會走過整個 key 空間。Redis 主要用一個執行緒依序處理指令，key 有幾百萬個時，這一個 KEYS 跑的期間所有其他請求都在排隊。正式環境不要用；要列舉 key 用 SCAN 分批走，第 6 課會教。更好的做法是設計 key，讓你根本不需要列舉。
💡 實務上：key 名稱和 TTL 是 code review 會問的事
同一台 Redis 常被好幾個服務共用：API、後台、排程工作都往裡面寫。團隊通常會約定前綴（服務名稱，必要時加環境），並把每個功能的 key 寫成一個小函式（例如 cartKey(userId)），不在程式各處手動拼字串，改名或加版本時才找得到所有地方。審程式時資深工程師會先問兩件事：這個 key 會不會自己消失（TTL 多久、誰負責刪）？它最大會長到多大？兩個都答不出來，上線幾個月後就是記憶體告警。

型別、名稱、過期時間都想好了，開始換第一個功能：購物車。

hash：怎麼讓手機和電腦各改各的商品？

購物車的問題是整包讀、整包寫。需要的是一種結構，讓「拿鐵的數量」和「可頌的數量」各自是一個可以單獨修改的值。hash 就是這樣：一個 key 底下有很多個欄位（field），每個欄位有自己的值，像一個只有一層的小物件。購物車的 key 是 ds:cart:<userId>，欄位是商品 id，值是數量。

127.0.0.1:6379> HINCRBY ds:cart:42 2 1      # 商品 2（拿鐵）加 1 杯；欄位不存在就從 0 開始
(integer) 1
127.0.0.1:6379> HINCRBY ds:cart:42 5 2      # 商品 5（可頌）加 2 個
(integer) 2
127.0.0.1:6379> HINCRBY ds:cart:42 2 -1     # 拿鐵減 1
(integer) 0
127.0.0.1:6379> HDEL ds:cart:42 2           # 數量 0 的欄位要自己刪
(integer) 1
127.0.0.1:6379> HGETALL ds:cart:42
1) "5"
2) "2"
127.0.0.1:6379> EXPIRE ds:cart:42 604800    # 7 天沒動就過期
(integer) 1

HINCRBY 是 hash 版的 INCR：在伺服器上一步完成「讀出這個欄位、加上數字、寫回這個欄位」。把開場的時間軸換成 hash 再走一次：手機送 HINCRBY ds:cart:42 2 1，電腦送 HINCRBY ds:cart:42 5 2。兩個指令不管誰先到，Redis 都是一個做完再做下一個，而且各自只動自己的欄位，沒有人需要先讀出整包、也沒有人會整包寫回。結果拿鐵 1 杯、可頌 2 個都在。

上面的例子裡還有兩個行為要注意。第一，HINCRBY 減到 0 不會自動刪欄位，留著一個數量 0 的商品，前端會顯示「拿鐵 × 0」，所以要自己 HDEL。第二，反過來，hash 的最後一個欄位被刪掉時，整個 key 會自動消失；空的 hash、list、set 在 Redis 裡不存在。購物車清空之後，EXISTS ds:cart:42 會是 0。

那什麼時候該用 JSON string，什麼時候用 hash？購物車用 JSON string 也存得下，NestJS 課的快取也是這樣存。兩者的差別在修改：

一個 JSON string一個 hash
改一個商品的數量GET 整包 → 在程式裡改 → SET 整包，三步之間別人的修改會被蓋掉HINCRBY 一步完成，只動這個欄位
讀整個購物車GET + JSON.parseHGETALL，值都是字串，要自己轉
巢狀資料可以不行，只有一層，值只能是字串
適合整份一起讀寫、不會部分修改的資料，例如快取的 API 回應會一個欄位一個欄位修改的資料：購物車、使用者設定、計數

判斷的問題是：會不會有兩個請求同時改同一份資料的不同部分？會，就用 hash 讓每個修改只碰自己的欄位。快取的 API 回應永遠是整份算好、整份寫入，沒有「只改其中一部分」的時候，所以 NestJS 課存成 string 是對的；購物車每次只改一個商品，就該用 hash。

hash 解決了大部分的問題，但還留一個小空隙。「HINCRBY 之後如果 ≤ 0 就 HDEL」是兩個指令，又回到了「兩步之間有空隙」：

兩步之間另一個分頁剛好又加了一杯，HDEL 會把那一杯一起刪掉。機率很低，購物車可以接受；要完全沒有空隙，得讓伺服器把兩步一起做完，那是第 4 課的 Lua 腳本。
💡 實務上：購物車放 Redis，TTL 是產品決定
購物車、表單草稿這類「常改、丟了不致命」的資料很適合 Redis：每次加減都是一個指令，不用為了它在資料庫開交易。要先想清楚的是：Redis 重啟或記憶體滿時資料可能不見（持久化與淘汰在第 6 課），所以真正要留下的東西（訂單、付款）結帳時一定寫進 PostgreSQL。7 天還是 30 天過期要跟 PM 確認：這是「客人隔多久回來還看得到購物車」的產品規格，不是工程師隨手填的數字。

購物車改好了。第二個回報是「最近瀏覽越存越長」，它要的不是各自加減，而是順序和長度。

list：最近瀏覽怎麼只留最新的 5 筆？

現在的「最近瀏覽」是一個 JSON 陣列字串：每看一個商品，程式就 GET、把 id 推進陣列、SET 回去。它有兩個毛病：跟購物車一樣是三步的讀改寫，而且從來沒有人把陣列剪短，每位會員的陣列一直長，這就是記憶體一直漲的原因。畫面上只顯示 5 個，存的卻是一年份。

需要的操作有三個：把剛看的商品放到最前面、同一個商品不要出現兩次、只留最新的 5 個。list 是有順序、可以重複的字串序列，像一排隊伍。從兩端放入、取出都很快，因為 Redis 直接知道頭和尾在哪裡；從中間找某個值就要從一端一個一個看過去。「最近瀏覽」只碰最前面，正好落在 list 擅長的地方。三個操作各對應一個指令：

127.0.0.1:6379> LREM ds:recent:42 0 3     # 先刪掉已經在裡面的 3（0：全部刪掉）
(integer) 0
127.0.0.1:6379> LPUSH ds:recent:42 3       # 放到最左邊（最前面）
(integer) 1
127.0.0.1:6379> LTRIM ds:recent:42 0 4     # 只留索引 0～4，其他丟掉
OK
127.0.0.1:6379> LRANGE ds:recent:42 0 -1   # 0 到 -1：全部；-1 是最後一個
1) "3"

一個一個看為什麼是這三個、為什麼是這個順序。

LREM 先把已經在裡面的同一個商品刪掉。list 允許重複，它不會幫你擋：客人來回看拿鐵三次，沒有這一步，5 格裡就有 3 格是拿鐵。LREM 要從頭到尾看一遍 list 才知道哪些要刪，但這個 list 永遠不超過 5 個，所以花費很小；指令的花費怎麼隨資料量成長，這課最後會整理。

LPUSH 放到最前面。L 是左邊（前面）、R 是右邊（後面），RPUSH 放到最後面。用 RPUSH 也做得到，但最新的就在最後面，下一步的 LTRIM 要改成 -5 -1，讀出來還要反轉。選一個方向，讓最常用的讀法最直接：畫面要「最新的在前」，就從左邊放、從 0 開始讀。

LTRIM 剪短，這一步正是開場記憶體問題的解法。它只留指定範圍內的元素，其他丟掉，所以每次放入之後剪一次，list 的長度永遠固定在 5。沒有它，每看一個商品 list 就長一格，一年後每位使用者都有幾千個元素。資料只增不減的結構，一定要有東西把它剪短：LTRIM、TTL，或兩個都有。

要知道 list 現在有幾個元素，用 LLEN key，它回傳 list 的長度，是一個整數。最後注意索引的寫法：結尾包含在內。LRANGE key 0 4 是 5 個，不是 4 個，這跟 JS 的 slice(0, 4) 不同；負數從尾巴算，-1 是最後一個。前 n 個永遠是 0 到 n - 1，後面的 sorted set 也一樣。

list 還有一些拿來做工作佇列的指令，跟最近瀏覽無關，放在課末「補充與查表」。

最近瀏覽的長度固定了，但「不重複」是靠 LREM 自己維護的。下一個功能「今天來過幾位不同的會員」，需要的就是不重複本身，而且要能算人數。

set：今天來過幾位不同的會員？

這是開場的第三個回報「今日來客數比實際少」。現在的做法是把今天的會員 id 存成 JSON 陣列，每來一位就 GET、檢查 includes、沒有才 push、再 SET。又是三步的讀改寫：兩位會員同時進來，兩個請求都讀到舊陣列、各自 push 一位，寫回時就少一位。而且「有沒有來過」要在程式裡掃一遍陣列。

set 是沒有順序、不重複的字串集合，同一個成員加兩次，只會有一個。「不重複」由 Redis 保證，不用自己檢查；加成員、問某個成員在不在、算有幾個成員，都是一個指令。每天一個 set，日期放進 key：

127.0.0.1:6379> SADD ds:visitors:2026-11-01 1 2 3 2
(integer) 3                                   # 2 重複，只加了 3 個
127.0.0.1:6379> SCARD ds:visitors:2026-11-01   # 有幾個成員
(integer) 3
127.0.0.1:6379> SISMEMBER ds:visitors:2026-11-01 2
(integer) 1
127.0.0.1:6379> SADD ds:visitors:2026-11-02 2 5
(integer) 2
127.0.0.1:6379> SINTER ds:visitors:2026-11-01 ds:visitors:2026-11-02   # 交集：兩天都有來
1) "2"

SADD 回的是「這次真的新加了幾個」，第一行送了 4 個 id，其中 2 重複，所以回 3。SCARD 就是「今天來過幾位不同的會員」的答案，SISMEMBER 回 1 或 0 回答「這位會員今天來過沒有」。要列出今天所有來過的會員，用 SMEMBERS key，一次拿回全部成員。

因為每天是一個獨立的 set，還能拿幾天的 set 互相比較：SINTER 是交集（每一天都來過，最後一行就是），SUNION 是聯集（任一天來過），SDIFF 是差集（第一天來、第二天沒來）。「連續每天都來的忠實會員」就是一個 SINTER，練習 4 會用到。要注意成員的順序不固定，需要排序就在程式裡排。

set 擋得住重複、算得出人數，但它沒有順序。最後一個功能人氣排行，要的正是「依數字排好的順序」。

sorted set：人氣排行怎麼在加分時就排好？

現在的排行是一個 JSON 物件，記著每個商品這週的銷量。每次有人打開排行頁，程式就把整包讀出來、在程式裡依銷量排序、取前 10 名。商品越多、看的人越多，每次排序的成本就越高；而且賣出一杯時一樣要 GET、加、SET，跟購物車有同樣的遺失更新。

換個想法：與其每次讀的時候排序，不如在寫入的時候就維持排好的順序，讀的時候直接拿前面幾個。sorted set（也寫成 ZSET）就是這樣：每個成員帶一個分數（score，一個數字），Redis 隨時依分數把成員排好。成員跟 set 一樣不重複，所以很適合排行榜：成員是商品 id，分數是累計銷量，同一個商品永遠只有一筆。

127.0.0.1:6379> ZINCRBY ds:rank:2026-W45 3 2      # 商品 2 賣了 3 杯，分數累加
"3"
127.0.0.1:6379> ZINCRBY ds:rank:2026-W45 5 1
"5"
127.0.0.1:6379> ZINCRBY ds:rank:2026-W45 4 2
"7"
127.0.0.1:6379> ZRANGE ds:rank:2026-W45 0 9 REV WITHSCORES   # 前 10 名，由高到低，附上分數
1) "2"
2) "7"
3) "1"
4) "5"
127.0.0.1:6379> ZREVRANK ds:rank:2026-W45 1       # 商品 1 是第幾名（從 0 算）
(integer) 1

ZINCRBY 是「加上」分數，在伺服器上一步完成，所以兩筆訂單同時賣出拿鐵，兩筆都會算進去。它的兄弟 ZADD 是「設定」分數，會把前面的數字直接蓋掉；累計銷量要用 ZINCRBY，用 ZADD 的話分數永遠只是最後一筆訂單的數量。

ZRANGE 依名次取一段，預設由低到高，排行榜要加 REV 才是由高到低。結尾跟 list 一樣包含在內：前 10 名是 0 9。加上 WITHSCORES 會連分數一起回，但回覆是「成員、分數、成員、分數…」攤平的一個陣列，而且分數也是字串：上面的 "2"、"7" 是商品 2 賣了 7 杯，不是兩個商品。ZREVRANK 反過來回答「這個成員是第幾名」，名次從 0 算。（還有一個舊寫法 ZREVRANGE，見課末。）

最後是同分怎麼排：同分時依成員字串的位元組順序排，不是數字大小也不是加入的先後。由低到高時商品 "10" 排在 "9" 前面，因為字串比較先比第一個字元，"1" 小於 "9"；加 REV 整個反過來。需要別的規則（例如同分時先達到的人在前），就把規則編進分數，或在程式裡再排一次。

💡 實務上：排行榜的麻煩在「週」和「退款」
週次放進 key 之後，要先決定用哪個時區算週次：伺服器用 UTC，台灣週一早上 8 點前的訂單會被算到上一週。通常在訂單付款成功時 ZINCRBY，退款時 ZINCRBY 一個負數，兩邊都要做，不然排行榜會跟報表對不起來。舊的週次用不到了就要清掉：建立 key 時一起設 TTL（例如保留幾週），不然每週多一個永遠不會消失的 sorted set。排行榜是「大概正確、即時」的資料，跟財務對帳的數字以資料庫為準。

四個功能在 redis-cli 裡都換好了。接下來要把它們搬進 Node 程式，而程式裡拿到的值，跟 redis-cli 顯示的不完全一樣。

搬進 Node：拿回來的是 number 還是字串？

寫程式之前，先把這課用到的五種結構放在一起看一次。它們的共通點會直接影響程式怎麼寫：

圖說的最後一句就是這一節的重點：裡面存的東西全都是字串。購物車的數量、排行的分數，在 Redis 裡都是字串，程式拿回來時要自己轉型別。

課程用 ioredis 6.0.0 從 Node 連 Redis。一個 Redis 物件就是一條長連線，整個程序共用一個，跟 pg 的 pool（Node 課第 20 課）一樣不要每個請求 new 一個。指令就是同名的方法，參數照 redis-cli 的順序。下面每一行的註解是它回傳的值：

import { Redis } from 'ioredis'

const redis = new Redis('redis://127.0.0.1:16479/0')

await redis.hincrby('ds:cart:42', '2', 1)          // 1：number，Redis 回的是整數
await redis.hgetall('ds:cart:42')                  // { '2': '1' }：值是字串
await redis.hgetall('ds:cart:沒有這個')             // {}：不是 null
await redis.get('ds:沒有這個')                      // null
await redis.lrange('ds:recent:42', 0, -1)          // ['3']：值是字串
await redis.zrange('ds:rank:2026-W45', 0, '9', 'REV', 'WITHSCORES') // ['2', '7', '1', '5']
await redis.quit()                                 // 程式結束前關掉連線

規則很簡單：Redis 回整數的指令（INCR、HINCRBY、SCARD、LLEN）拿到 number，其他的值一律是字串，包括 ZINCRBY 回的分數。回頭看 redis-cli 的輸出就對得上：顯示 (integer) 的是 number，有雙引號的是字串。所以 getCart 要把 '1' 轉成 1、getRecent 要把 ['3'] 轉成 [3]，排行的分數也要轉，數字、JSON 都要自己轉。

ioredis 6.0.0 的型別定義還有兩個小地方，寫 TypeScript 時會碰到。zrange 的結尾索引型別只接受字串：寫 '9' 或 String(n - 1)，寫 number 會有型別錯誤，執行結果一樣。hash 的欄位名稱（hincrby、hdel、hget）也只接受字串，商品 id 是 number 時要寫 String(productId)。

最容易出錯的是「不存在」的樣子。hgetall 對不存在的 key 回 {}，因為 Redis 把不存在的 key 當成空的 hash（hash 那一節看過，空的 hash 本來就不存在）；只有 get 這種讀單一值的指令才回 null。所以「沒有購物車」要用 Object.keys(cart).length === 0 判斷，寫 if (cart === null) 永遠不會成立。

work/02/try.ts 可以直接執行看看這些回傳值：

$ cd learn/data-stores/practice/work/02      # 先在 learn/ 執行一次 node check.mjs data-stores 02 建立這個資料夾
$ node try.ts

型別轉好，四個模組就能動了。但上線之後資料會長大：會員變多、商品變多、排行累積好幾週。下一個問題是，哪些指令會隨著資料變大而變慢。

資料變大時，哪些指令會卡住所有人？

開場的第四個回報「排行越來越慢」，本質是一個成長的問題：商品從 20 個變成 2,000 個，每次在程式裡排序的時間也跟著漲。描述這種成長的說法叫時間複雜度：指令花的時間隨資料量怎麼成長。O(1) 是跟資料量無關，資料多一千倍也一樣快；O(log N) 是資料變 1000 倍，時間只多一點；O(N) 是跟著資料量成正比，資料多一千倍，時間也大約多一千倍。

在 Redis 裡這件事比在一般程式裡更要緊，原因是前面看過的那一點：Redis 一次只處理一個指令。你的 Node 程式裡一個慢的函式，只拖慢呼叫它的那個請求；Redis 裡一個 O(N) 的指令碰到很大的 key，執行的那段時間，所有連到這台 Redis 的請求都要排隊等它做完。所以挑結構時，除了「能不能一步做完」，還要問「最常用的指令是 O(幾)」。以下是在 Redis 8.10.3 上用 COMMAND DOCS 指令（Redis 內建、回傳每個指令官方說明的指令）查到的複雜度（查表用，不用背）：

用這張表回頭檢查這課的四個功能。人氣排行的 ZRANGE … 0 9 是 O(log N + M)：sorted set 寫入時就維持排好的順序，取前 10 名只要先找到起點、再往後拿 10 個，商品從 1 千變成 100 萬，花費幾乎不增加。這正是開場「每次排序越來越慢」的解法：排序的成本攤到每次 ZINCRBY 的 O(log N) 裡，讀的時候不用再排。

最近瀏覽的 LREM、LRANGE 是 O(N)，但 LTRIM 讓 N 永遠是 5，所以沒有問題。這也說明了 list 的定位：只適合「從兩端存取」和「長度很小」的資料；要依分數查前幾名，用 sorted set，不要用一個很長的 list。

要小心的是 HGETALL、SMEMBERS 這種一次拿全部的指令。購物車只有幾個商品，HGETALL 很便宜；但同樣的指令用在一個有幾十萬個欄位的 hash 上，就會卡住別人。所以 key 的大小也要控制，這就是前面 code review 會問「它最大會長到多大」的原因。第 6 課會教怎麼找出過大的 key。

💡 實務上：先寫下「怎麼讀」，再挑結構
團隊討論新功能要放 Redis 時，資深工程師會先問：畫面要怎麼讀這份資料（整份、前 10 名、是否存在）？最多會有幾筆？答案常常不只一種：例如「今天有幾位不同的會員來過」和「最近來的 5 位」，就是一個 set 加一個 list 兩個 key，寫入時兩個都要更新，也都要有 TTL 或 LTRIM 把它剪短。另外，字串轉 number、{} 當成「沒有」這些細節，通常集中在一個小模組（例如 cartStore.get(userId) 回傳已轉好型別的物件），API 和排程都呼叫它，不在各處各自轉。

把這課的判斷整理成順序：先寫下要做的修改和要的讀法，挑一個能一步做完修改、讀法的複雜度又低的結構，再替 key 決定名稱、TTL 和長度上限。練習的四個模組，就是照這個順序把會員中心的四個功能做完。

練習

先確認 Redis 有在跑（docker compose --profile redis up -d --wait），每一題都在 learn/ 執行 node check.mjs data-stores 02 判分。所有函式的第一個參數 redis 由測試傳入，連到 DB 2。

練習 1：在 cart.ts 用 hash 做購物車，key 是 ds:cart:<userId>，欄位是 productId。addItem 把數量加上 qty（負數代表減少），減到 0 或以下時刪掉這個欄位；removeItem 刪掉一個商品；getCart 回傳 { productId: 數量 }，數量是 number，空購物車回傳 {}；clearCart 刪掉整個購物車。每次 addItem（加、減、減到 0 刪掉欄位都算）都要把 TTL 重設為 7 天（CART_TTL_SECONDS）。測試會同時送出 20 個 addItem（20 種不同商品，以及同一個商品 20 次），一個都不能少。

練習 2：在 recent.ts 用 list 記錄最近瀏覽，key 是 ds:recent:<userId>。recordView 把商品放到最前面，已經在裡面的要先拿掉（不重複），而且每次呼叫後 list 都不能超過 5 個；getRecent 回傳 productId 的 number 陣列，最新的在前。

練習 3：在 leaderboard.ts 用 sorted set 做每週人氣排行，key 是 ds:rank:<week>。addSales 把這次賣出的數量累加到商品的分數；top(redis, week, n) 回傳前 n 名 [{ productId, sold }]，由高到低，兩個欄位都是 number。n 比商品數多時回傳全部；n 是 0 或負數時回傳 []（想想結尾索引 n - 1 變成 -1 時 Redis 會怎麼解讀）；不同週的排行互不影響。

練習 4：在 visitors.ts 自己設計 key（ds: 開頭、帶日期，每天一個 set）。markVisit 記錄某天來過的會員；countVisitors 回傳那天來過幾位不同的會員；loyal(redis, dates) 回傳 dates 裡每一天都有來的會員 id，由小到大排序，dates 是空陣列時回傳 []。

練習 5：客人在手機和電腦同時把不同商品加進購物車，要兩邊都留住。哪種存法最合適？

✓ HINCRBY 在伺服器上一步完成，而且只改那一個欄位，兩個分頁各改各的。a 的 GET→改→SET 有三步，兩邊同時讀到舊的購物車，後寫的會把先寫的蓋掉（遺失更新）。c 把數量變成 list 的長度，計數要 LLEN 每個 key，讀整個購物車要先知道有哪些 key，還要靠 KEYS 或另外記錄。

練習 6：await redis.hgetall('ds:cart:7')，而 ds:cart:7 不存在，會得到什麼？

✓ Redis 把不存在的 key 當成空的 hash，HGETALL 回空的陣列，ioredis 轉成 {}。用 cart === null 判斷「沒有購物車」永遠不成立，要看 Object.keys(cart).length。只有 GET 這種讀單一值的指令，key 不存在時才回 null。

練習 7：人氣排行的 sorted set 從 1 千個商品變成 100 萬個，ZRANGE key 0 9 REV 取前 10 名的時間大約會？

✓ sorted set 在寫入時就維持排好的順序，取一段範圍只要先找到起點（log N）再往後拿 M 個。a 是 LRANGE 一個很長的 list 或 HGETALL 這類 O(N) 指令的情況；c 是把銷量存在 hash、每次拿出全部再在程式裡排序的做法，sorted set 不需要。

常見錯誤

  • 所有資料都 JSON.stringify 成 string：改一個欄位要讀整包、寫整包，兩個請求同時改就會互相覆蓋。會部分修改的資料用 hash，計數用 INCR、HINCRBY、ZINCRBY。
  • 以為 Redis 回傳數字：GET、HGETALL、LRANGE、ZRANGE 的值全是字串。'3' + 1 是 '31'；排序字串陣列 ['10', '9'].sort() 得到 ['10', '9']。回傳給呼叫端之前先轉好型別。
  • 暫時的資料沒有 TTL，或只在建立時設：購物車、最近瀏覽、驗證碼都是暫時的，忘了 TTL 就永遠佔著記憶體。「7 天沒動才過期」要在每次寫入後都 EXPIRE；用 SET 覆蓋整個 key 還會把 TTL 清掉。
  • key 沒有前綴、沒帶必要的維度：cart:42 可能跟別的系統撞名；排行榜的 key 沒帶週次，每一週的銷量都混在一起。把「要依什麼查」放進 key。
  • 結尾索引差一：LRANGE、LTRIM、ZRANGE 的結尾都包含在內，前 n 個是 0 到 n - 1。
  • 只增不減的結構沒有上限：list 沒有 LTRIM、set 和 sorted set 沒有 TTL，一年後就是大 key，HGETALL、SMEMBERS 一次拿全部時會卡住整台 Redis。
  • 用 KEYS 找資料：KEYS 走過整個 key 空間，正式環境會讓所有請求排隊。設計好 key 名稱讓你直接算得出來；真的要列舉用 SCAN（第 6 課）。

補充與查表

用 SET 的 NX、EX 搶位子

string 的 SET 可以加條件和過期時間。NX 是「key 不存在才寫」，EX 30 是「30 秒後過期」，兩個合起來就是一個在伺服器上一步完成的「搶位子」：

127.0.0.1:6379> SET ds:lock:order:9 1 NX EX 30
OK                                       # NX：不存在才寫；EX 30：30 秒後過期
127.0.0.1:6379> SET ds:lock:order:9 1 NX EX 30
(nil)                                    # 已經存在，沒寫入

只有第一個 SET 成功，後面的拿到 nil 就知道已經有人在處理訂單 9。30 秒後 key 自動消失，就算拿到位子的程序當掉也不會永遠卡住。第 3 課的冪等會用到它：冪等（idempotent）是指同一個請求送兩次，結果跟送一次一樣，例如客人按兩次「送出訂單」，訂單只建立一次。

hash 的單一欄位過期：HEXPIRE

TTL 掛在整個 key 上。hash 想讓單一欄位過期要用 HEXPIRE，這是 Redis 7.4 才有的指令（課程用 8.10.3，可以用）。

list 當工作佇列：BLPOP

list 還有 BLPOP：list 是空的時候等到有東西才回傳，可以拿來做簡單的工作佇列。但「處理到一半程式當掉，工作就不見」這類問題它不處理；正式的佇列交給 BullMQ 或第 5 課的 Streams。

ZREVRANGE 是舊寫法

舊寫法 ZREVRANGE 在 Redis 6.2 起標為已棄用（deprecated），還能用，新程式寫 ZRANGE … REV。

Redis 8 內建的擴充功能

Redis Open Source 8 把原本 Redis Stack 的模組併進主程式：JSON、查詢引擎（search）、時間序列、機率型結構（bloom filter 等），另外新增向量集合（vector set）。課程的 redis:8.10.3-alpine 執行 MODULE LIST 就看得到這些模組。這門課只用五種基本結構和第 5 課的 Streams；全文搜尋交給第 10 課的 Elasticsearch。要不要用 Redis 的這些擴充功能，跟選其他儲存一樣，用第 1 課的四個問題判斷。

小結

  • 購物車少一樣商品，是「讀出、修改、寫回」拆成三個指令造成的遺失更新。INCR、HINCRBY、ZINCRBY、SADD 這類指令在伺服器上一步完成，不會有遺失更新；在程式裡讀改寫會有。
  • Redis 的每個 key 有一個型別的值：string、hash、list、set、sorted set，型別決定能用哪些指令；對錯的型別下指令會拿到 WRONGTYPE。
  • 挑結構看存取模式：部分更新用 hash（購物車）、兩端進出用 list（最近瀏覽）、不重複用 set（每日訪客）、依分數排序用 sorted set（人氣排行）、單一值或計數用 string。
  • key 用 ds:功能:id 分層，把查詢需要的 id、日期、週次放進名稱；暫時的資料一定要有 TTL，而且看清楚哪些指令會重設或清掉它，只增不減的結構要用 LTRIM 或 TTL 剪短。
  • 注意複雜度：Redis 一次只做一個指令，O(N) 的指令碰上大 key 會卡住所有人；KEYS 不要在正式環境用。
  • ioredis 只有整數回覆是 number，其他都是字串；HGETALL 對不存在的 key 回 {}。
