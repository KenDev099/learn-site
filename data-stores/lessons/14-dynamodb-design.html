階段 5：分析、規模與期末專題 · 第 14 課

大規模 key-value（資深）：DynamoDB 的分區鍵與 single-table 設計

假設咖啡店三年後變成連鎖外送平台：全台 800 家門市，尖峰時每秒幾萬次「我的訂單到哪了」查詢、每秒幾千筆新訂單。PostgreSQL 主機已經升到最大規格，讀副本也加到第五台，團隊開始討論 Amazon DynamoDB。它的賣點是：只要你依 key 查詢，資料從 1 GB 長到 100 TB、流量從每秒 10 次長到每秒 10 萬次，單次讀寫的延遲都差不多，而且不用自己管機器。代價是你得放棄 SQL 的大部分自由：沒有 JOIN、沒有任意的 WHERE，查詢方式要在建表時就想好。

這一課你要替外送平台設計訂單服務的表：它要回答五種查詢（「我的訂單到哪了」、訂單明細、顧客最近 5 筆、顧客某段期間的訂單、門市待做清單），撐住尖峰的新訂單，還要支援一個限量優惠碼活動。設計完之後，你也要能說出：咖啡店現在的規模，不該選 DynamoDB。練習在頁面上的模擬器裡做，不需要 AWS 帳號。

這課的路線：
  1. 第 1、2 節：DynamoDB 為什麼撐得住、代價是什麼。資料怎麼分到很多台機器、為什麼因此只能靠 key 讀；key 由哪兩部分組成，有哪三種讀法。
  2. 第 3 節：先列出訂單服務的五種存取模式，再決定 key。用 single-table 讓訂單和品項放進同一張表、一次讀出（開場任務的最小答案：模式 1、2）。
  3. 第 4 節：「顧客最近 5 筆訂單」這類查詢，主表的 key 幫不上忙，用 GSI 換一組 key。
  4. 第 5、6 節：今天的新訂單全寫在同一個 key 會被限流，怎麼分散；限量優惠碼被兩個人同時領，怎麼保證只有一個成功。
  5. 第 7 節：回到開頭，這套設計付出了什麼，咖啡店現在為什麼不該選。
這課會用到：
  • 第 7 課的依存取模式建模：先列出查詢，一起讀的資料放在一起，有意地反正規化。
  • 系統設計課第 7 課的分片與熱點：資料依 key 分散到多台，某個 key 特別熱門時，壓力全落在同一台。

DynamoDB 為什麼流量再大都撐得住？

先看開場的賣點從哪裡來。PostgreSQL 撐不住外送平台，卡在「所有寫入都進同一台主機」：讀取可以分給讀副本，寫入只能靠那台主機往上加規格，加到最大就沒有路了。要把寫入拆到好幾個資料庫也可以，但跨庫的 JOIN、交易都要自己處理，非常麻煩。DynamoDB 從設計上就讓寫入也能分給很多台機器。

DynamoDB 是 AWS 的託管 key-value 資料庫，也能存文件形狀的資料。「託管」的意思是：沒有伺服器要開、沒有版本要升級，備份和複寫由 AWS 做，你只建立表（table），然後讀寫。在背後，它把一張表的資料切成很多分區（partition），每個分區放在不同的機器上；資料或流量變多，就多切幾個分區。

每筆資料要放進哪個分區，由它的 key 決定。DynamoDB 把 key 的值丟進內部的雜湊函式，算出來的結果對應到一個分區。讀取時也一樣：給它 key，它算一次雜湊就知道要去哪個分區拿，不需要問其他機器。這就是它能一直加機器的原因：每一次讀寫都只碰到一個分區，不需要跨機器協調，分區從 10 個變成 1,000 個，單次讀寫要做的事都一樣多。這跟第 6 課 Redis Cluster 用 CRC16 算 slot 是同一個想法。

同一個設計也帶來最大的限制：不知道 key，就不知道去哪裡找。「找出所有狀態是 pending 的訂單」這種條件，PostgreSQL 可以走索引或掃表；DynamoDB 不知道這些訂單散在哪些分區，只能把每個分區都讀一遍。所以它沒有 JOIN、沒有任意的 WHERE，每一種查法都要在設計 key 時就想好。兩者的對照：

PostgreSQLDynamoDB
查詢方式任意 SQL：JOIN、WHERE、GROUP BY，事後加索引就好只能依 key 查；新的查法要改 key 或加索引，有時要搬資料
擴展一台主機往上加規格，讀副本分攤讀取；寫入要拆庫就很麻煩自動加分區，寫入也能水平擴展
延遲看查詢寫得好不好、資料多大依 key 讀寫，資料量變大延遲也差不多
維運自己或託管服務管版本、連線數、VACUUM沒有伺服器可管；要管的是容量與成本
適合大部分業務系統，需求常變存取模式固定、流量極大的少數幾種查詢

表的最後一列就是這課的取捨：DynamoDB 拿查詢的彈性換擴展能力。這筆交易值不值得，要先看規模。

規模先估再說（系統設計課第 2 課）：現在的咖啡店一天幾千筆訂單，換算每秒不到 1 筆寫入，PostgreSQL 連汗都不會流。DynamoDB 在這個規模只會帶來代價：查詢要先想好、報表要另外匯出、團隊要學一套新的建模方式。這課的情境是「假想的規模」，學的是大流量系統的設計方式，不是建議現在就換。

既然一切都從 key 出發，下一個問題是：key 長什麼樣，拿著 key 又能怎麼讀？

一筆訂單怎麼存，拿著 key 能怎麼讀？

DynamoDB 的一筆資料叫 item，像一個 JSON 物件，最大 400 KB。item 裡的每個欄位叫屬性（attribute）。除了 key，每個 item 可以有不同的屬性，不需要事先定義欄位。以訂單 1043 為例：訂單本體是一個 item，有 status、total 這些屬性；它的兩個品項各是一個 item，有品名、數量、單價。

每個 item 都有主鍵（primary key），它決定 item 放在哪裡、怎麼被找到。主鍵可以由兩部分組成。第一部分是 partition key（分區鍵，常簡稱 PK），就是上一節拿去算雜湊的那個值，決定 item 住在哪個分區。因為要算雜湊，查詢時一定要給出完整、相等的值：「以 ORDER#10 開頭」這種條件算不出雜湊，也就不知道要去哪個分區。

只有 partition key 的話，一個 key 只能對應一個 item。但訂單 1043 有本體和兩個品項，我們希望它們放在一起、一次讀出來。這就是第二部分 sort key（排序鍵，常簡稱 SK） 的用途：PK 相同的 item 存在同一個分區，並依 SK 排好序。查詢時 PK 要完全相等，SK 則可以加範圍條件：=、<、<=、>、>=、between（兩端都包含）、begins_with（以某段開頭）。

PK＋SK 合起來必須唯一：兩個 item 的 PK、SK 都一樣，後寫的會蓋掉先寫的。同一個 PK 的所有 item 合稱一個 item collection，例如訂單 1043 的本體和兩個品項。它們放在一起、排好序，所以一次就能讀出一段。

有了這兩把 key，讀取只有三種方式，差別在你手上有多少 key：

操作要給什麼做什麼什麼時候用
GetItem完整的 PK＋SK讀一筆已知確切是哪一筆，最便宜
Query完整的 PK，SK 可以加範圍條件讀一個 item collection 的一段，依 SK 排序（可以反向），可以限制筆數大部分的列表查詢
Scan什麼都不用給把整張表一筆一筆讀過幾乎不該出現在線上 API：表有 1 億筆就讀 1 億筆、照讀到的量付錢

表上看不出來的是「讀太多」的代價。Query 和 Scan 都可以再加篩選條件（FilterExpression），但篩選發生在讀出來之後：讀了 1,000 筆、篩到剩 3 筆，還是付 1,000 筆的讀取費用。

篩選也幫不了另一個上限：一次 Query 或 Scan 最多讀 1 MB 的資料，這個上限是在篩選之前算的。讀滿 1 MB、篩完可能只剩幾筆，甚至 0 筆。還有資料沒讀完時，回應會帶一個 LastEvaluatedKey（這次讀到的最後一個 key），下一次請求把它當成 ExclusiveStartKey 帶回去，才能從那裡接著讀，這就是 DynamoDB 的分頁。所以靠篩選的查詢，可能要來回好幾次才湊滿一頁畫面。

所以「讀少一點」要靠 key 設計，不是靠篩選。後面設計每一種查詢時都會用到這個原則。

還有一個細節會直接影響 Query 的結果：SK 怎麼排序。SK 是字串時，排序是逐字比較（照 UTF-8 位元組），不是照數字大小。訂單的品項如果用 ITEM#1、ITEM#2…ITEM#10 當 SK，第 10 個品項會排在第 2 個前面，明細頁的順序就亂了。這是 DynamoDB 設計最常踩的坑。下面用一個 Map 模擬 item collection，執行後比較「沒補零」和「補零」兩行的順序，以及兩種日期寫法：

知道了 key 的形狀和讀法，就能替訂單服務決定 key 了。但 key 要照顧到哪些查詢，得先問清楚這個服務會被怎麼查。

訂單服務會被怎麼查？先列存取模式，再定 key

PostgreSQL 的設計順序是「先把資料正規化成表，查詢之後再說」，因為之後加個索引就能支援新的查法。DynamoDB 反過來：先列出所有存取模式（access pattern），再設計 key。原因是上一節看到的：查詢只能從 key 出發，key 沒照顧到的查法就只剩 Scan。存取模式就是「誰、用什麼條件、要拿到什麼、多常發生」。外送平台的訂單服務有這五種：

#存取模式頻率怎麼查
1依訂單編號查訂單狀態（「我的訂單到哪了」）極高GetItem PK=ORDER#1043, SK=ORDER
2訂單明細頁：訂單＋所有品項高Query PK=ORDER#1043（一次拿到整個 item collection）
3顧客最近 5 筆訂單高需要第二組 key：下一節的 GSI1
4顧客某段日期的訂單中GSI1，SK 用 between
5門市今天待做的訂單，舊的在前高（每家店的平板每幾秒刷新）需要第三組 key：GSI2

這一節先解決模式 1、2。關聯式的直覺是 customers、orders、order_items 三張表。DynamoDB 沒有 JOIN，三張表就要查三次、在程式裡拼起來：明細頁一個請求變成三個，延遲和失敗的機會都跟著變多。常見的做法是 single-table 設計：把不同實體放在同一張表，用 key 的前綴區分是哪種實體，讓「一起讀的東西」落在同一個 item collection。

具體來說，訂單本體和品項都用 ORDER#1043 當 PK，用不同的 SK 區分；顧客用 CUSTOMER#12 當 PK。這樣模式 1 是一次 GetItem（PK=ORDER#1043, SK=ORDER），模式 2 是一次 Query（PK=ORDER#1043），訂單和品項一起回來。每個 item 再加一個 type 屬性，程式讀回來時用它區分形狀（就是 TypeScript 課第 16 課的可辨識聯合）。整張表長這樣：

這張表裡每個選擇都有原因。先看前綴，它不能省。如果顧客寫成 PK=12、訂單也寫成 PK=12，「訂單 12 的明細」就會把「顧客 12 的資料」一起查出來，PK＋SK 剛好相同時還會互相覆蓋。加上 CUSTOMER#、ORDER# 之後，不同實體就算 id 相同，也落在不同的 item collection。

再看 SK 的值，它決定 Query 回來的順序。品項編號補零（ITEM#001），理由是上一節的字串排序；訂單本體用 ORDER，因為 I 排在 O 前面，Query 的結果是品項在前、訂單在後。順序不重要時不用刻意調整，要用到時才設計。key 欄位的名稱就叫通用的 PK、SK，不叫 orderId，因為同一個欄位放的是不同實體的值。

最後是反正規化：品項裡直接存品名和當時的單價（第 7 課的快照），訂單本體直接存 total。在沒有 JOIN 的資料庫裡，讀的時候再去查商品就是多一次請求；寫入時多存一份，讀取就只要一次。

single-table 不是教條。實體之間沒有一起讀的需求、或由不同團隊負責時，分成幾張表反而清楚（各自的權限、備份、容量設定）。它解決的是「一次請求拿到要一起顯示的資料」，不是「表越少越好」。

💡 實務上：設計審查先交存取模式表，再談 key
用 DynamoDB 的新服務，設計審查時資深工程師第一個要看的是上面那種表：每一種查詢是誰發的、條件是什麼、每秒幾次、要多快。表裡沒有的查詢，上線後只能 Scan 或補 GSI，所以要先跟 PM、客服、營運把「後台要怎麼找訂單」問清楚，不要只列前台的頁面。key 的格式（前綴、日期格式、時區）寫成一份對照表放進 repo，新人才看得懂 console 裡混在一起的各種 item。

模式 1、2 解決了，但它們都是「手上有訂單編號」的查詢。模式 3「顧客最近 5 筆訂單」手上只有顧客編號，主表的 key 幫不上忙。

顧客最近 5 筆訂單：主表的 key 查不到，怎麼辦？

模式 3 用主表查不到：訂單的 PK 是 ORDER#…，只知道顧客編號，就算不出訂單在哪個分區，只能 Scan 全表再篩出顧客 12 的訂單。解法是 GSI（global secondary index，全域次要索引）。

GSI 的運作方式是：你指定另外兩個屬性當它的 partition key 和 sort key，DynamoDB 就維護一份用這組 key 重新組織的資料副本。主表寫入一筆帶有這兩個屬性的 item，DynamoDB 會在背後把它放進 GSI，依新的 partition key 分區、依新的 sort key 排序。查詢時指定要查哪個索引，用法跟查主表一樣：partition key 完全相等，sort key 可以加範圍條件。等於同一份資料換一組 key 再排一次。

咖啡店的訂單本體加上四個屬性，就同時進了兩個 GSI：

索引partition keysort key支援的存取模式
GSI1GSI1PK = CUSTOMER#12GSI1SK = ORDER#2026-10-31T08:15:00.000Z3：beginsWith ORDER#，反向、取 5 筆
4：between 兩個日期
GSI2GSI2PK = STORE#4#2026-10-20GSI2SK = STATUS#pending#2026-10-20T09:12:00.000Z5：beginsWith STATUS#pending#

逐一看這張表怎麼回答模式 3～5。模式 3：GSI1 的 partition key 是顧客，sort key 是 ORDER# 加上 ISO 時間，所以顧客 12 的訂單在 GSI1 裡依時間排好。Query GSI1PK=CUSTOMER#12、beginsWith ORDER#，反向、取 5 筆，就是最新的 5 筆。

結果裡不會混進品項，因為品項沒有 GSI1PK、GSI1SK 屬性。沒有索引屬性的 item 不會進 GSI，這叫稀疏索引（sparse index）。這也是可以主動利用的技巧：只想索引一部分資料（例如只有待處理的），就只在那些 item 上寫索引屬性。

模式 4 用同一個 GSI1，SK 改用 between。between 兩端都包含，上界要能包住整天：要查 10/05～10/12，下界 ORDER#2026-10-05 沒問題（當天任何時間的 SK 都比它大）；上界寫 ORDER#2026-10-12 會漏掉 10/12 當天，因為 ORDER#2026-10-12T09:00… 比它大。常見做法是上界加一個比日期後面所有字元都大的字元，例如 ORDER#2026-10-12~（~ 在 ASCII 裡比數字、大寫字母都大）。

模式 5 的門市待做清單，用上了第 2 節「讀少一點要靠 key 設計」的原則：把條件放進 sort key，而不是事後篩選。GSI2SK 開頭是狀態，beginsWith STATUS#pending# 只會讀到待做的訂單。如果 SK 只放時間、讀出來再用 JS 濾掉 done，讀取量（和費用）是那天的全部訂單。狀態改成 done 時，更新訂單本體的 GSI2SK，它在 GSI 裡的位置就跟著換。

GSI 是一份由 DynamoDB 維護的副本，副本就有代價。第一個是一致性。GSI 是非同步更新、最終一致的：寫入主表成功後，GSI 通常在一秒內跟上，但在跟上之前查 GSI 可能看不到剛寫的訂單。主表的讀取預設也是最終一致，但可以用 ConsistentRead: true 要求強一致，保證讀到最新寫入；GSI 不支援強一致讀取。所以剛下單後要馬上顯示的頁面，用主表的 GetItem 或 Query 讀。

第二個是成本與容量：每次寫主表，若影響到 GSI，GSI 也要消耗寫入容量；GSI 被限流時會反過來拖慢主表的寫入。每張表預設最多 20 個 GSI。「寫入容量」和「限流」是什麼，下一節會講。另外還有一種只換 sort key 的 LSI，大部分情況用不到，細節見課末。

到這裡五種查詢都有了 key。但存取模式表只寫了「怎麼讀」，沒寫寫入集中在哪裡。營運接著要一張「今天全部訂單」的即時看板，有人提議讓今天的訂單都寫到 PK=ORDERS#2026-11-01，看板 Query 一次就拿到。這個設計在尖峰時會出事。

今天的訂單全寫進同一個 key，尖峰時會怎樣？

要看出問題，得先知道 DynamoDB 怎麼計算流量。它用容量單位（capacity unit）計費和限流，讀和寫分開算：

  • RCU（read capacity unit）：每秒一次 4 KB 以內的強一致讀取，或兩次最終一致讀取。
  • WCU（write capacity unit）：每秒一次 1 KB 以內的寫入。item 越大用得越多（3 KB 的 item 寫一次用 3 WCU）。

每個分區有固定的吞吐上限：每秒 3,000 RCU、1,000 WCU。超過的請求會被限流（throttling）：DynamoDB 直接拒絕，SDK 收到 ProvisionedThroughputExceededException 或類似的錯誤，重試幾次後失敗。對使用者來說，就是 API 偶爾失敗、延遲飆高。

容量單位也是計費的單位。DynamoDB 有兩種計費模式：provisioned 是預先設定這張表每秒要多少 RCU、WCU（可以搭配自動調整），照設定的量付錢，用不到也付，超過就可能被限流；on-demand 不用預先設定，照實際讀寫的次數付錢。要注意的是，上面那個每分區 3,000 RCU、1,000 WCU 的上限不管哪種計費模式都存在，計費模式只決定「表整體」的容量怎麼來。

表的總量可以遠大於一個分區的上限，因為 DynamoDB 會自動處理流量不平均的情況。第一步，它會立即提高流量大的那個分區可用的容量（官方稱 adaptive capacity），但最多只到每分區的上限。流量持續偏高時，它會把那個分區切成兩個、放到不同機器上，讓每一半各自有完整的上限（官方稱 split for heat）。但同一個 partition key 的資料能不能拆，要看流量的形狀：官方文件說明，item collection 可以依 sort key 切成幾段放到不同分區，前提是流量不是跟著遞增的 sort key 走。看板的提議正好踩中：所有訂單寫到 PK=ORDERS#2026-11-01、SK 是時間，所有新寫入都打在同一個 key 的最尾端，切開也沒用。這就是熱分區（hot partition）：流量集中在一個分區，表的其他容量再多也幫不上。

會出現熱分區的不只依日期分的 key（「今天」永遠最熱），還有低基數的值（只有 pending／done 兩種狀態、只有 3 家門市）和一個超級熱門的 key（活動商品）。

讀到這裡你可能會回頭看上一節的 GSI2：GSI2PK = STORE#4#2026-10-20 也是「門市＋日期」，它是不是也會熱？不會，差別在單一 key 分到的流量。外送平台有 800 家門市，每家店每天一個 key，尖峰每秒 3,000 筆新訂單平均分到每家店大約每秒 4 筆，就算加上狀態更新，單一 key 的寫入也是每秒個位數，離每分區 1,000 WCU 很遠。熱不熱看的是「一個 key 每秒扛多少」，不是 key 裡有沒有日期。同樣的形狀，如果只有 3 家店、或改成 STORE#全部#日期，流量就會集中到少數幾個 key，那時要用下面同樣的分片後綴。

解法是寫入分片（write sharding）：在 key 後面加一個後綴，把一個邏輯上的 key 拆成 N 個實際的 key，每個實際的 key 各自落在自己的分區、各自有 1,000 WCU。下面模擬尖峰每秒 3,000 筆新訂單，執行後看每種設計最熱的 key 每秒要扛幾筆：

不分片時 3,000 筆全在一個 key，每秒約 2,000 筆被限流；分 4 片後每片 750 筆，回到上限內。分幾片之外，後綴怎麼算，決定了之後讀不讀得回來：

  • 亂數後綴（Math.random()）：寫入最平均，但之後要找「訂單 1043」時不知道它在哪一片，只能 N 片都查。
  • 計算出來的後綴：用訂單編號算，例如 orderId % N，或對字串 id 算雜湊再取餘數。同一筆訂單永遠算出同一片，GetItem 一次就找到；只要 id 本身分布平均，寫入也一樣平均。id 有規律（例如都是 10 的倍數）時取餘數會集中，改用雜湊。

代價在讀取：看板要「今天的所有訂單」，就得對 N 個 key 平行送 N 個 Query，再把結果合併並重新排序（每一片各自依 SK 排好，接起來並不是整體有序）。N 怎麼選：尖峰每秒寫入量 ÷ 1,000 再留餘裕；N 越大寫入越分散、讀取要發的請求越多。如果熱的是讀取而不是寫入，解法則是在前面加快取，不是分片。AWS 有一個放在 DynamoDB 前面的記憶體快取服務叫 DAX，程式改連 DAX，熱門的讀取就由快取回應；也可以用 NestJS 課第 19 課的 Redis 快取。

💡 實務上：被限流時先找出是哪個 key，不是先加容量
告警通常是「API 偶爾 5xx、延遲飆高」，CloudWatch（AWS 的監控服務）上看到 throttle 指標在跳。直覺是調高容量或改成 on-demand，但前面說過，分區的吞吐上限不管哪種計費模式都存在，熱 key 加錢也救不了。先開 CloudWatch Contributor Insights（列出存取最多、被限流最多的 key；選「throttled keys」模式只在被限流時記錄，可以長期開著），看是同一筆 item 一直出現（熱 key：讀多加快取、寫多就分片），還是同一個 partition key 底下 SK 一直往後長（像上面的 ORDERS#日期：改 key 的設計，加分片後綴）。GSI 也會有自己的熱 key，像只放狀態或日期的 GSI partition key，要分開查。

分片處理的是「寫得太集中」。外送平台還有另一種寫入問題：同一筆資料被兩個請求同時搶著寫。行銷部門要辦一個限量優惠碼活動。

限量優惠碼：兩個人同時領，怎麼保證只有一個成功？

活動規則是：每個碼只能被一個人領走，每位顧客也只能領一張。直覺寫法是先查有沒有人領過、沒有再寫入：

const used = await db.get({ PK: `COUPON#${code}`, SK: 'COUPON' })
if (!used) await db.put({ PK: `COUPON#${code}`, SK: 'COUPON', customerId })   // ✗ 兩個請求可能同時查到「沒有」

這跟第 4 課的「讀 → 判斷 → 寫」中間被插隊一樣：兩個請求同時查到沒有，就都寫進去，後寫的蓋掉先寫的，兩個人都以為自己領到了。問題出在「查」和「寫」是兩個請求，中間的空檔裡別的請求可以插進來。DynamoDB 的解法是條件寫入（condition expression）：把條件交給資料庫，在寫入的同一個動作裡檢查，中間沒有空檔。

防重複用的條件是 attribute_not_exists(PK)：這個 PK＋SK 的 item 不存在才寫入。DynamoDB 會對「這次要寫的那個 key」評估條件，所以它的意思就是「這筆還沒有人寫過」。條件不成立時丟 ConditionalCheckFailedException，什麼都不寫。兩個人同時領同一個碼，只有一個人的寫入會成功。條件寫入也能做別的檢查，例如寫 version = :expected，更新時帶上讀到的版本號：這就是樂觀鎖，跟 第 9 課的做法相同。

「每位顧客只能領一張」是另一個唯一條件，要再寫一個 PK=CUSTOMER#12, SK=COUPON 的 item 當作「這位顧客已經領過」的標記，也加上 attribute_not_exists。兩個 item 必須一起成功或一起失敗：如果分開寫，優惠碼寫成功、顧客標記失敗，就留下一張「被領走但對不上人」的碼。這要用 TransactWriteItems：最多 100 個寫入動作、合計不超過 4 MB，全部成功或全部不做。任何一個條件不成立，整個交易丟出 TransactionCanceledException，裡面的 CancellationReasons 依動作順序列出每一個的原因（例如 [ConditionalCheckFailed, None]）。同一個交易不能對同一個 item 做兩個動作。

最後要處理重送。網路逾時後，前端或 SDK 可能重送同一個「領取」請求。第一次其實成功了，第二次會因為條件不成立而失敗，使用者卻看到「領取失敗」。所以條件失敗時要再讀一次：如果這張碼的主人就是自己，回報「已經領過」而不是錯誤。這跟第 3 課的冪等鍵是同一個想法：重送不能改變結果。用真正的 AWS SDK 怎麼寫 GetItem、查 GSI、交易，放在課末的「補充與查表」。

到這裡，訂單服務的表設計完成了：五種查詢各有 key、尖峰寫入分散了、優惠碼不會重複。最後回到開場的另一半：這套設計付出了什麼，咖啡店現在該不該用？

回到開頭：咖啡店現在該選 DynamoDB 嗎？

前面幾節換來的是：只要依 key 查詢，流量再大延遲都差不多。代價都在彈性上，用第 1 課的四個問題（存取模式、一致性、規模、維運成本）逐一檢查。每一條前面標的是它屬於哪個問題，規模留到這份清單之後的結論：

  • 存取模式：存取模式會變：新的查法要新的 GSI；如果需要的屬性舊資料沒有，就得寫程式掃過整張表補上（backfill）。key 本身設計錯，就是整張表搬家。需求每週都在變的後台，用 PostgreSQL 加個索引就好。
  • 存取模式：臨時查詢與報表：「上個月每家店每個品項賣了多少」在 DynamoDB 只能 Scan 全表。正確做法是把資料匯出到分析資料庫（匯出到 S3 再用第 13 課的 DuckDB，或 AWS 直接用 SQL 查 S3 檔案的 Athena），不在線上表上跑報表。
  • 一致性：交易與關聯：TransactWriteItems 有 100 個動作的上限，成本是一般寫入的兩倍；大量跨實體的一致性需求（例如結帳同時扣庫存、建立訂單、寫帳）還是關聯式資料庫的強項。
  • 維運成本：成本模型：第 5 節的兩種計費模式各有適合的流量。on-demand 不用預估，適合流量難預測的服務；provisioned 在流量穩定時比較便宜。不管哪種，Scan、大 item、過多的 GSI 都直接變成帳單。上線前要用存取模式表估算每秒讀寫量 × item 大小。
  • 維運成本：鎖定在 AWS：API、計費方式、監控工具都是 AWS 專屬的。Apache Cassandra、ScyllaDB 是模型相近的寬欄式資料庫，ScyllaDB 還提供相容 DynamoDB API 的 Alternator，但功能與維運方式不同，真的要搬仍是一個專案，選之前就要接受這個綁定。

適合的情境：存取模式少而固定、流量極大或極不平均（購物車、session、裝置最新狀態、訂單狀態查詢）、團隊不想管資料庫伺服器、可以接受「報表另外處理」。

所以開場的答案是：咖啡店現在不該選。第一節估過，一天幾千筆訂單換算每秒不到 1 筆寫入，上面這些代價每一個都會立刻付，擴展的好處卻用不到。就算真的長到外送平台的規模，也不是整個系統一起換。

💡 實務上：搬到 DynamoDB 通常只搬一條熱路徑
真的遇到規模問題時，團隊很少把整個系統搬過去。常見的順序是：先加快取、讀副本撐住；確定瓶頸是某一條固定、流量極大的路徑（例如「訂單狀態查詢」）後，只把那條搬到 DynamoDB，訂單、帳務仍以 PostgreSQL 為記錄系統。報表需求用官方的匯出到 S3（需要先開啟 point-in-time recovery，也就是可以還原到過去任一時間點的持續備份；匯出不消耗表的讀取容量）交給分析工具，不在線上表跑。提案時把「誰是權威資料、兩邊怎麼同步、出錯怎麼對帳」一起寫進去（第 11 課的 outbox 同樣適用）。

補充與查表

LSI（local secondary index，本地次要索引）：partition key 跟主表相同、只換 sort key，支援強一致讀取，但只能在建表時建立，而且最多 5 個。大部分情況用 GSI。

真正的 AWS SDK 寫法：用 @aws-sdk/lib-dynamodb 3.1161.0（DocumentClient 會把 JS 物件轉成 DynamoDB 的格式），模式 1 的 GetItem、模式 3 的 GSI1 Query、優惠碼的交易寫起來像這樣：

import { DynamoDBClient } from '@aws-sdk/client-dynamodb'
import { DynamoDBDocumentClient, GetCommand, QueryCommand, TransactWriteCommand } from '@aws-sdk/lib-dynamodb'

const doc = DynamoDBDocumentClient.from(new DynamoDBClient({ region: 'ap-northeast-1' }))

await doc.send(new GetCommand({ TableName: 'coffee', Key: { PK: 'ORDER#1043', SK: 'ORDER' } }))

await doc.send(new QueryCommand({
  TableName: 'coffee',
  IndexName: 'GSI1',
  KeyConditionExpression: 'GSI1PK = :pk AND begins_with(GSI1SK, :prefix)',
  ExpressionAttributeValues: { ':pk': 'CUSTOMER#12', ':prefix': 'ORDER#' },
  ScanIndexForward: false,   // 由新到舊
  Limit: 5,
}))

await doc.send(new TransactWriteCommand({
  TransactItems: [
    { Put: { TableName: 'coffee', Item: { PK: 'COUPON#LATTE50', SK: 'COUPON', customerId: 12 }, ConditionExpression: 'attribute_not_exists(PK)' } },
    { Put: { TableName: 'coffee', Item: { PK: 'CUSTOMER#12', SK: 'COUPON', code: 'LATTE50' }, ConditionExpression: 'attribute_not_exists(PK)' } },
  ],
}))

本機開發：可以用官方的 DynamoDB Local（Java 寫的，映像 amazon/dynamodb-local:3.3.2），程式只要把 endpoint 指過去，金鑰填任意值（只能是英數字）：

docker run --rm -p 127.0.0.1:8001:8000 amazon/dynamodb-local:3.3.2 -jar DynamoDBLocal.jar -inMemory

const db = new DynamoDBClient({ endpoint: 'http://localhost:8001', region: 'local',
  credentials: { accessKeyId: 'local', secretAccessKey: 'local' } })

容器預設用 8000 port，這裡對應到主機的 8001，避免跟課程網站衝突。它適合測 API 用法與 key 設計，但不會模擬分區上限、限流和 GSI 延遲，這些只能在真正的服務上觀察（CloudWatch 的 throttle 指標與 Contributor Insights 的熱 key 報表）。

練習

這頁的練習用一個模擬器 db，參數簡化成物件：db.get({ PK, SK })、db.put(item, { condition })、db.query({ index, pk, beginsWith, between, reverse, limit })、db.scan()、db.transactWrite([{ put, condition }])。reverse: true 對應真正 API 的 ScanIndexForward: false，index 對應 IndexName（見課末的 SDK 寫法）。模擬器的每個方法都會先 await 一次才讀寫，所以「先 get 再 put」的競態在並發測試裡一定會出現；它的 GSI 是立刻更新的，真正的 GSI 會晚一點。

四題都在頁面上寫。模擬器的型別已經宣告好（編輯器裡打 db. 就會提示）；實作在隱藏測試裡，測試會建立一個新的 db 傳進你的函式，並記錄你呼叫了哪些方法、幾次。「執行」只會跑你自己的程式，「檢查答案」才會跑測試。

練習 1：照上面的 single-table 設計實作主表的 key。customerItem(c) 回傳顧客的 item（type: 'customer'，含 customerId、name）；orderItems(o) 回傳訂單本體 1 筆（type: 'order'，含 orderId、customerId、storeId、at、status，以及 total = 各品項 qty × price 的總和）和每個品項各 1 筆（type: 'line'，含 orderId、從 1 開始的品項序號 n、productId、name、qty、price）。再實作存取模式 1、2：getOrder(db, orderId) 只能呼叫 1 次 get；orderDetail(db, orderId) 只能呼叫 1 次 query，回傳訂單本體和全部品項，品項依序號排好（訂單本體在前在後都可以）。測試會寫入 16 位顧客、300 多筆訂單（有的訂單有 12 個品項，有的顧客編號跟訂單編號相同）。

練習 2：主表的 key 已經寫好。在 orderItems 的訂單本體加上 GSI1、GSI2 的屬性（品項不要加），再實作存取模式 3～5，每個函式只能呼叫 1 次 query、不能用 get、scan，而且 query 讀到的每一筆都要是答案（不能讀出來再用 JS 篩選）。recentOrders(db, customerId, n)：最新的 n 筆訂單本體，新的在前。ordersBetween(db, customerId, from, to)：from、to 是 YYYY-MM-DD，兩天都包含，舊的在前。pendingOrders(db, storeId, date)：該門市在 date 那天（at 的前 10 個字，UTC）狀態是 pending 的訂單，舊的在前。測試的資料包含剛好落在日期邊界上的訂單。

練習 3：營運要一張「今天全部訂單」的即時看板，有人提議用 PK=ORDERS#<日期>。改用寫入分片：實作 shardKey(date, orderId, shards)，回傳這筆訂單要寫入的 partition key（同一筆訂單每次都要算出同一個 key，不同日期的 key 不能相同）；再實作 queryAllShards(db, date, shards)，平行查詢那天的每一片（剛好 shards 次 query、不能用 scan），合併成依 SK 排序的一個陣列。測試寫入的 item 長這樣：{ PK: shardKey(date, orderId, shards), SK: `${at}#${orderId}`, orderId, at }；它會用 10 片寫入 10,000 筆同一天的訂單，檢查最熱的 key 佔全部寫入的比例低於 2 ÷ 片數，並用 get 依 key 找回指定的訂單。

練習 4：實作 registerCoupon(db, code, customerId)。一個優惠碼只能被一個人領，一位顧客只能領一張。用一次 transactWrite 同時寫兩個 item，兩個都加上 condition: 'attribute_not_exists(PK)'：{ PK: `COUPON#${code}`, SK: 'COUPON', code, customerId } 和 { PK: `CUSTOMER#${customerId}`, SK: 'COUPON', code, customerId }。成功回傳 'ok'；交易被取消時讀一次這張碼，主人就是這位顧客（重送的請求）就回傳 'already-mine'，否則把錯誤丟出去。測試會同時送出 100 個請求（同碼不同人、同人不同碼、同一個請求重送），檢查每個請求的結果，以及表裡的優惠碼和顧客標記是否一一對應。

練習 5：DynamoDB 表的設計應該從哪裡開始？

✓ DynamoDB 只能有效率地依 key 查詢，不知道有哪些查詢就無法設計 key。a 是關聯式資料庫的順序，在沒有 JOIN 的 DynamoDB 會變成一次頁面要查好幾張表；c 在 DynamoDB 不成立：key 設計錯時加索引救不了，要搬資料；d 的容量要從存取模式的頻率估出來，是後面的步驟。

練習 6：每天的所有訂單都寫到 PK = ORDERS#<日期>、SK 是時間，尖峰每秒 3,000 筆。會發生什麼？

✓ 自動拆分能分散的是不同的 key，或流量不是跟著遞增 sort key 走的 item collection；所有新訂單都寫在同一個 key 的最尾端，拆開也沒用。a 忽略了這個前提；c 的「每天不同」只代表歷史資料分散，今天的流量仍然全在一個 key；d 不存在這種行為，超過上限就是限流錯誤。解法是寫入分片。

練習 7：顧客剛下單，前端立刻呼叫「我的最近訂單」（查 GSI1），新訂單沒有出現。最可能的原因？

✓ 寫入主表成功後，GSI 稍後才更新，而且 GSI 不支援強一致讀取。a、d 的話主表也查不到，可以用 GetItem 確認；c 不需要，GSI 由 DynamoDB 自動維護。剛寫入就要讀到的畫面，用主表的 GetItem 或 Query（可以強一致讀），或把剛建立的訂單直接放進前端的列表。

練習 8：哪種情況最不適合選 DynamoDB？

✓ 存取模式不穩定時，每個新查法都要加 GSI、補資料甚至改 key 搬家；臨時報表只能 Scan。這種需求用 PostgreSQL，加索引、寫 SQL 就好。a、b、d 都是「已知 key、查法固定、量大」，正是 DynamoDB 擅長的。

常見錯誤

  • 照關聯式的方式一個實體一張表，再在程式裡拼：一個頁面要查好幾次、沒有交易保護。先列存取模式，把一起讀的資料放在同一個 item collection。
  • 用 Scan 當查詢：表越大越慢、越貴，還會吃光容量讓其他請求被限流。查不到就是 key 或 GSI 設計少了一種存取模式。
  • 讀出來再篩選：FilterExpression 或 JS 的 filter 都是讀完才丟，費用照讀到的算。把篩選條件放進 sort key（例如 STATUS#pending#…）。
  • sort key 的數字和日期沒補零：字串比較下 ITEM#10 排在 ITEM#2 前面、2026-10-5 排在 2026-10-12 後面。固定寬度、ISO 格式。
  • key 沒有實體前綴：不同實體的 id 相同時混在同一個 item collection，甚至互相覆蓋。
  • 低基數或依日期的 partition key：狀態、門市、「今天」都會變成熱分區。用計算出來的後綴分片，讀取時平行查完再合併排序。
  • 以為 GSI 是強一致的：剛寫入時查 GSI 可能查不到。要讀自己剛寫的，用主表。
  • 先 get 再 put 檢查唯一性：並發時會重複。用 attribute_not_exists 條件寫入，多個 item 要一起成立就用 TransactWriteItems。
  • 為了「以後可能很大」在小規模專案選 DynamoDB：查詢彈性、報表、開發速度的代價是立刻付的，擴展的好處可能永遠用不到。

小結

  • DynamoDB 對 partition key 算雜湊，把資料分散到很多分區，每次讀寫只碰一個分區；只要依 key 讀寫，資料和流量變大延遲都差不多。代價是只有 GetItem、Query（一個 PK 內依 SK 範圍）、Scan 三種讀法，沒有 JOIN 與任意 WHERE。
  • 設計從存取模式表開始。single-table 用前綴（CUSTOMER#、ORDER#）區分實體，把一起讀的資料放進同一個 item collection；SK 是字串，數字補零、時間用 ISO。
  • 主表 key 照顧不到的查法用 GSI：用另一組屬性重新組織資料。它是最終一致的，沒有索引屬性的 item 不會進去（稀疏索引）。條件要放進 key，而不是讀完再篩。
  • 每個分區每秒最多 3,000 RCU、1,000 WCU；依日期或低基數的 key 會變成熱分區。用計算出來的後綴做寫入分片，讀取時平行查 N 片、合併後重新排序。
  • 唯一性用 attribute_not_exists 條件寫入；多個 item 要一起成立用 TransactWriteItems（最多 100 個動作）。條件失敗時檢查是不是自己的重送，讓請求冪等。
  • 存取模式常變、需要臨時報表、規模還小的時候，不要選 DynamoDB；真的需要時通常只搬一條熱路徑。本機可以用 amazon/dynamodb-local:3.3.2 測 API，但它不模擬限流。
