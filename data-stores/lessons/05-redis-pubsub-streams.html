階段 2：Redis 不只是快取 · 第 5 課

訊息：pub/sub 與 Streams

咖啡店的訂單 API 跑在三台伺服器上，每一台都連著幾個店內平板的 WebSocket。這一課要處理兩件同時發生的事。第一件：吧台按下「飲料做好了」，請求只會打到其中一台伺服器，但另外兩台連著的平板也要馬上亮起來。第二件：客人付款成功，要寄一封電子收據。寄信慢個幾秒沒關係，但一封都不能漏。

兩件事的形狀一樣：一個地方發生了事，要讓別的程式知道。Redis 為它們各準備了一個工具，差別在「訊息送出去之後，Redis 還記不記得它」。這一課從通知平板開始，接著把重點放在第二件事：一步一步做出一個不漏信的收據 worker，並回答它在正式環境會遇到的每一個問題，包括 worker 當機、某一筆一直寄失敗、事件越存越多。

這課的路線：
  1. 通知平板和寄收據，能不能用同一個工具？用「沒人收到會不會有人發現」來分（開場問題的最小答案）。
  2. 三台伺服器怎麼都知道飲料做好了：pub/sub 的運作方式，以及它為什麼不能拿來寄收據。
  3. 收據不能漏，付款事件要先存下來：stream 是什麼；兩台 worker 怎麼分工、寄完才算數（consumer group）。
  4. worker 當機、某一筆一直寄失敗時，卡住的收據誰接手；stream 越長越大要留多少。
  5. 收據 worker 一定要自己用 Streams 寫嗎：跟 BullMQ、PostgreSQL 佇列、Kafka 比較。
這課會用到：
  • 系統設計課第 12 課的送達語意：至多一次可能丟、至少一次可能重複；worker 處理完才 ack，一直失敗的訊息移到死信佇列。
  • 第 2 課的 ioredis 回傳值：hash 等結構讀回來的值都是字串，數字要自己轉。

通知平板和寄收據，能用同一個工具嗎？

先別急著看指令。兩件事表面上都是「通知別人」，但如果把每一個細節攤開來問，會發現它們對工具的要求幾乎相反：

飲料做好了，通知平板付款成功，寄電子收據
誰要收到每一台伺服器都要收到（扇出，系統設計課第 17 課）只要一個 worker 處理（分工）
收的人剛好不在沒關係：平板重新整理時會重新查一次狀態不行：收據永遠不會寄出
處理失敗不用重送，下一則很快就來要重試，試太多次要有人看
工具pub/subStreams + consumer group（或 BullMQ、資料庫佇列）

第一列講的是「一則訊息要給幾個人」。平板的通知要讓三台伺服器每一台都收到，因為每一台各自連著不同的平板；收據只要某一個 worker 寄出就好，兩個 worker 都寄，客人就收到兩封。

第二、三列才是關鍵：收的人剛好不在、或處理失敗時，後果是什麼。平板漏掉一則「飲料做好了」，最壞的情況是店員多等幾秒、手動重新整理，畫面就對了，因為真正的訂單狀態存在資料庫裡，通知只是提醒平板「該去查一下了」。收據漏掉一封，沒有任何地方會再補寄，也沒有任何 API 會報錯，要等客人來問才會發現。

所以選工具時只要先問一個問題：這則訊息如果沒人收到，會不會有人發現？不會，就用送完即忘的 pub/sub；會，就要用能把訊息存下來、能確認、能重送的工具，這一課用的是 Redis Streams。接下來先處理簡單的那一件：讓三台伺服器都知道飲料做好了。

怎麼讓三台伺服器都知道飲料做好了？

吧台的請求打到伺服器 A，A 自己連著的平板可以直接推；問題是 B、C 根本不知道這件事發生了。需要一個三台都連得到的地方，讓 A 把事件丟進去，B、C 立刻收到。這就是 pub/sub 做的事。

pub/sub 是「發布／訂閱」（publish/subscribe）的簡稱。它有三個角色：

  • 頻道（channel）：就是一個名稱，例如 ds:ready。不用事先建立，也不會存任何東西。
  • 訂閱者：一條對 Redis 下了 SUBSCRIBE 頻道 的連線，之後就一直等這個頻道的訊息。三台伺服器各開一條，訂閱同一個頻道。
  • 發布者：任何一條連線下 PUBLISH 頻道 訊息，Redis 就把這則訊息複製給「這一刻」正在訂閱的每一條連線。

重點在「這一刻」。Redis 收到 PUBLISH 時，查一下現在有誰訂閱這個頻道，逐一送出，然後就把訊息忘掉，不寫進記憶體裡的任何資料結構。開兩個終端機試試，執行後看兩件事：終端機 1 什麼時候冒出訊息，以及 PUBLISH 回的數字：

# 終端機 1：訂閱。這條連線之後就一直在等訊息
$ docker compose exec redis redis-cli
127.0.0.1:6379> SUBSCRIBE ds:ready
1) "subscribe"
2) "ds:ready"
3) (integer) 1
1) "message"                    # 終端機 2 PUBLISH 之後出現
2) "ds:ready"
3) "{\"orderId\":12}"

# 終端機 2：發布
127.0.0.1:6379> PUBLISH ds:ready "{\"orderId\":12}"
(integer) 1                     # 有 1 個訂閱者收到
127.0.0.1:6379> PUBLISH ds:nobody hi
(integer) 0                     # 沒人訂閱：訊息直接丟掉，不是錯誤

PUBLISH 的回覆是這次有幾個訂閱者收到。最後那一行回 0：沒有人在聽，訊息就消失了，而且這不算錯誤，發布的程式不會收到任何例外。同樣的道理，先 PUBLISH、後 SUBSCRIBE 的人，永遠收不到之前那一則。

這種送達方式叫做至多一次（at-most-once）：每則訊息最多送到一次，也可能一次都沒送到。訂閱者斷線的那幾秒、重新部署的那段空檔、收到後處理時出錯，這些時候的訊息都不會補送。對平板來說這可以接受，上一節說過，漏一則只是晚幾秒看到；但這也代表 pub/sub 的使用者要自己準備「漏了怎麼補」，通常就是平板重新連線時，重新跟 API 查一次訂單狀態。

接著把它寫進 Node。訂閱要用一條另外開的連線，原因是一條連線一旦訂閱，就進入「等訊息」的狀態，它的用途和生命週期都跟平常下指令的連線不同：共用連線要一直開著給所有請求用，訂閱連線不用時要整條關掉。ioredis 的 duplicate() 會用同樣的網址和選項複製出一條新連線，專門拿來訂閱（ioredis 版本對這件事的細節見課末）：

import { Redis } from 'ioredis'

const redis = new Redis('redis://127.0.0.1:16479/0')   // 整個程式共用
const sub = redis.duplicate()                            // 訂閱專用：同樣的網址與選項

sub.on('message', (channel, message) => {               // 每則訊息都觸發一次，message 是字串
  console.log(channel, JSON.parse(message))
})
await sub.subscribe('ds:ready')                          // await 之後訂閱才生效

await redis.publish('ds:ready', JSON.stringify({ orderId: 12 }))   // 用共用的連線發布

await sub.quit()                                         // 不用了：整條關掉，不只 unsubscribe

這段程式有三個地方要照著做，每一個都對應一種會出事的寫法：

  • 訊息內容是字串：Redis 只傳字串，要傳物件就 JSON.stringify 發、JSON.parse 收，發布和訂閱兩邊約定同一個格式。
  • subscribe 要 await：訂閱要等 Redis 回覆才生效。不等就馬上發布，訊息可能在訂閱生效前送出，剛才說過，那一刻沒人訂閱的訊息就被丟掉。
  • 不用了就 quit()：只 unsubscribe 的話，那條連線還開著。每訂閱一次就多一條關不掉的連線，久了 Redis 的連線數會一直漲。

還有一件跟效能有關的事：訂閱者收到訊息後要做什麼。

慢的訂閱者會被踢掉。Redis 替每個訂閱者暫存還沒送出的訊息。訂閱者處理太慢、暫存越積越多，超過上限 Redis 就直接切斷它的連線。課程的 Redis 8.10.3 預設 client-output-buffer-limit pubsub 32mb 8mb 60：超過 32 MB，或連續 60 秒超過 8 MB，就斷線。所以訂閱者收到訊息只做很快的事（例如轉給 WebSocket），慢的工作交給 Streams 或佇列。

到這裡，飲料做好了的通知已經完成：A 發布，A、B、C 三台都訂閱，各自轉給自己連著的平板。

💡 實務上：多台伺服器的即時推播，大多是 pub/sub 在底下傳
咖啡店後台的「新訂單」提示、吧台平板的出餐狀態，只要 API 開了第二台伺服器，就需要 pub/sub 把事件傳到每一台。Node 常用的 WebSocket 套件 Socket.IO 用 Redis adapter 時，底下就是 Redis pub/sub；它另有一個 Redis Streams adapter，Redis 短暫斷線後能接著讀、不漏封包。設計時先問：「漏了一則，畫面會錯多久？」答案通常是「前端重新連線時重新查一次 API 就對了」，所以要把「重連後重新載入」寫進前端。訊息只放 id 和狀態，完整資料讓前端自己查，每則訊息小，訂閱者的暫存就不容易積到上限被踢掉。

那收據能不能也這樣做？付款成功時 PUBLISH 一則「訂單 42 已付款」，收據 worker 訂閱。問題出在 worker 重新部署的那 10 秒：這段時間沒有任何人訂閱，進來的付款事件 PUBLISH 都回 0、全部消失，收據永遠不會寄。收據需要的是另一種東西：訊息先存起來，worker 回來後還讀得到。

收據不能漏：付款事件怎麼先存下來？

要讓 worker 不在的時候訊息也不會不見，訊息就得存在 Redis 裡，等 worker 來拿。Redis 的 stream 就是為這件事設計的資料型別，跟第 2 課的 hash、list 並列。

stream 可以想成一本只能往後寫的流水帳：每有一件事發生，就在最後面加一行，前面寫過的行不能改、也不會因為被讀過而消失。每一行叫做一筆 entry，有兩個部分：

  • id：Redis 替這一筆產生的編號，一定比前一筆大。
  • 欄位：幾組「名稱 值」，例如 type paid orderId 42，像一個只有一層的 hash。

付款成功時，API 用 XADD 寫一筆進 stream，收據 worker 之後再來讀。下面依序示範寫入、看長度、讀全部、等新訊息，執行後注意 XADD 回傳的 id 長什麼樣子：

127.0.0.1:6379> XADD ds:orders * type paid orderId 42       # * 讓 Redis 產生 id
"1793489375364-0"
127.0.0.1:6379> XADD ds:orders * type paid orderId 43
"1793489375950-0"
127.0.0.1:6379> XLEN ds:orders
(integer) 2
127.0.0.1:6379> XRANGE ds:orders - +                         # - 最舊、+ 最新：全部
1) 1) "1793489375364-0"
   2) 1) "type"
      2) "paid"
      3) "orderId"
      4) "42"
2) 1) "1793489375950-0"
   2) ...
127.0.0.1:6379> XREAD COUNT 10 BLOCK 5000 STREAMS ds:orders $   # 等最多 5 秒，只要從現在起的新訊息

先看 id。1793489375364-0 的格式是「毫秒時間戳-序號」：前半段是寫入時的時間（從 1970 年起算的毫秒數），後半段是同一毫秒內的第幾筆，從 0 開始。因為 id 一定遞增，它有兩個用途：

  • 當書籤：讀的人只要記住「我讀到 id X」，下次從 X 之後接著讀，不會漏也不會重複。
  • 用時間查詢：id 的前半段就是時間，所以 XRANGE key 1793489000000 + 就是「這個時間點之後的所有事件」。

再看欄位。XRANGE 回來的欄位是攤平的陣列：名稱、值、名稱、值。跟 hash 一樣值都是字串，ioredis 回傳 [id, ['type', 'paid', 'orderId', '42']]，要自己兩兩配成物件，'42' 也要自己轉成數字。

最後一行的 XREAD 是讓程式「等新訊息」的指令。BLOCK 5000 表示沒有新訊息就等最多 5 秒；$ 表示「從現在 stream 的最後一筆之後開始」，也就是只要新的。worker 用一個迴圈不斷呼叫它，就能在事件進來時立刻拿到。不過 $ 只能用在第一次呼叫：之後每一輪都要把上一輪拿到的最後一筆 id 傳進去取代 $，否則兩次呼叫之間進來的事件會被跳過。這就是上面說「id 當書籤」的實際用法。要注意 BLOCK 期間那條連線整個卡在等待，其他指令都要排隊，所以要 BLOCK 的 worker 給它一條專用的連線，跟上一節訂閱另開連線是同樣的道理。

現在 worker 重新部署也不怕了：事件存在 stream 裡，worker 回來後從記住的 id 接著讀就好。但新的問題來了。收據量變大，開兩台 worker 一起寄。XREAD 的書籤是每個讀的人自己記的，Redis 不知道這兩台是同一夥的，兩台都會從頭讀到尾、每一筆都拿到，每位客人收到兩封收據。我們需要 Redis 幫忙記「這一筆已經交給誰了」。

兩台 worker 怎麼分工，而且寄完才算數？

兩台 worker 要分工，需要一個所有 worker 共用的進度，由 Redis 來記。這個共用的進度叫做 consumer group（消費者群組）。它掛在一個 stream 上，裡面有幾個消費者（consumer），一個消費者就是一台 worker，用名字區分，例如 w1、w2。group 保證每一筆新訊息只交給其中一個消費者。

光是分工還不夠。w1 拿到一筆、寄信寄到一半當機了，這筆要算寄過了嗎？所以 group 還要知道「交出去的訊息到底處理完了沒」。這靠兩個東西：

  • ACK（acknowledge，確認）：消費者處理完一筆，用 XACK 告訴 Redis「這筆好了」。
  • PEL（pending entries list，待確認清單）：交出去、但還沒 ACK 的訊息都記在這裡。每一筆記著三件事：在哪個消費者手上、交出去多久了、總共交出去過幾次。

一筆訊息在 group 裡的一生是：還沒交出去 → 交給某個消費者，進入它的 PEL → 那個消費者處理成功、XACK，從 PEL 移除。stream 本身從頭到尾都沒有變，變的只有 group 的記錄。下面是建立 group、讀、確認的完整過程：

127.0.0.1:6379> XGROUP CREATE ds:orders receipts 0 MKSTREAM
OK                                   # 0：從 stream 最開頭讀；$：只讀建立之後的新訊息
127.0.0.1:6379> XGROUP CREATE ds:orders receipts 0 MKSTREAM
(error) BUSYGROUP Consumer Group name already exists
127.0.0.1:6379> XREADGROUP GROUP receipts w1 COUNT 10 STREAMS ds:orders >
1) 1) "ds:orders"                    # >：還沒交給任何消費者的新訊息
   2) 1) 1) "1793489375364-0"
         2) 1) "type" 2) "paid" 3) "orderId" 4) "42"
      ...
127.0.0.1:6379> XACK ds:orders receipts 1793489375364-0
(integer) 1                          # 這筆從 PEL 移除

逐行看每個指令在做什麼，以及寫錯會怎樣：

  • XGROUP CREATE … 0 還是 $：建立 group 時要決定從哪裡開始交。收據 worker 第一次上線前，stream 裡已經有付款事件了，要寫 0 從最開頭開始，那些收據才會寄；寫 $ 只會交建立之後的新事件，之前的收據永遠不會寄。只關心之後事件的功能才用 $。MKSTREAM 讓 stream 還不存在時順便建立。
  • BUSYGROUP：group 已經存在時再 CREATE 會回這個錯。worker 通常在啟動時建立 group，第二次啟動一定會遇到，所以這個錯誤要忽略；其他錯誤（例如連不上 Redis）照樣往外丟。
  • XREADGROUP GROUP receipts w1 … >：以 group receipts 的消費者 w1 身分來拿訊息。最後的 > 表示「還沒交給任何消費者的新訊息」，拿到的訊息同時記進 w1 的 PEL。w2 用同一行（換成 w2）來拿，拿到的是別筆，這就是分工。最後的 id 改寫成 0，則是重讀自己 PEL 裡還沒 ACK 的訊息，用在 worker 重啟後先清自己的舊帳；別人 PEL 裡的拿不到。
  • XACK 一定在處理成功之後：先 ACK 再寄信，寄到一半當機，這筆已經從 PEL 移除，Redis 認為它好了，再也沒有人會處理。

下圖是某個時間點 group 的狀態：前三筆已經 ACK；第四到六筆分別在 w1、w2 的 PEL 裡；第七筆還沒交出去，下一次有人用 > 讀就會拿到它。

ioredis 的寫法照 redis-cli 的參數順序。XREADGROUP 沒有新訊息時回 null，有的話是「每個 stream 一組」的巢狀陣列，這裡只讀一個 stream，所以直接解構出第一組：

const reply = await redis.xreadgroup('GROUP', 'receipts', 'w1', 'COUNT', 10, 'STREAMS', 'ds:orders', '>')
// null，或 [['ds:orders', [['1793489375364-0', ['type', 'paid', 'orderId', '42']], …]]]
if (reply) {
  const [[, entries]] = reply
  for (const [id, fields] of entries) { /* 處理，成功才 await redis.xack('ds:orders', 'receipts', id) */ }
}

現在兩台 worker 會分工，每筆只交給一台，而且寄成功才 ACK。但看一下圖裡 w1 的 PEL：有一筆已經閒置 15 分鐘、交過 3 次。「處理完才 ACK」的另一面是，沒處理完的訊息會一直留在 PEL。如果 w1 當機了不再回來，這些收據誰來寄？

worker 當機或一直寄失敗，卡住的收據誰接手？

假設 w1 一次讀了 5 筆，還沒 ACK 就當機了。這 5 筆留在 w1 的 PEL 裡，而 XREADGROUP > 只交「還沒交給任何人」的訊息，所以它們不會再被交給 w2。w1 不回來，這 5 封收據就永遠卡著。Redis 不會自動把它們轉給別人，因為 Redis 分不出 w1 是當機了，還是只是寄得比較慢。要由我們的程式來判斷、來接手。

第一步是看清楚誰手上卡了什麼，用 XPENDING。不帶範圍是摘要，帶範圍是逐筆明細：

127.0.0.1:6379> XPENDING ds:orders receipts                  # 摘要
1) (integer) 5                          # 總共幾筆待確認
2) "1793489375364-0"                    # 最小、最大的 id
3) "1793489380046-0"
4) 1) 1) "w1"                           # 每個消費者手上幾筆
      2) "5"
127.0.0.1:6379> XPENDING ds:orders receipts - + 10           # 明細：id、在誰手上、閒置毫秒、送達次數
1) 1) "1793489375364-0"
   2) "w1"
   3) (integer) 912345
   4) (integer) 1

明細的第三項是閒置時間：這筆交出去之後過了多久都沒有被 ACK，這裡是 912345 毫秒，大約 15 分鐘。正常寄一封信只要幾秒，閒置這麼久，幾乎可以確定 w1 已經不在了。

第二步是接手。XAUTOCLAIM（Redis 6.2 起）的意思是：「把閒置超過某個時間的訊息改記到我名下，並把內容一起給我」。下面由 w2 接手閒置超過 60 秒的訊息：

127.0.0.1:6379> XAUTOCLAIM ds:orders receipts w2 60000 0-0 COUNT 100
1) "0-0"                                # 下一次的起點；0-0 表示掃完了
2) 1) 1) "1793489375364-0"              # 接手到的訊息
      2) 1) "type" 2) "paid" 3) "orderId" 4) "42"
   ...
3) (empty array)                        # 已經被刪掉的 id（Redis 7.0 起才有這一項）

這一行有兩個參數要想清楚：

  • min-idle-time（這裡的 60000 毫秒）決定「多久沒動就當作當機」。設太短，w1 只是在寄一封比較慢的信，訊息就被 w2 搶走，兩邊各寄一次；所以要設成比最慢的正常處理時間再長一些。
  • 起點與 COUNT：一次只掃 COUNT 筆，回覆的第一項是下一次要從哪裡繼續。要一直呼叫、把上次回的起點傳回去，直到它回 0-0 才算全部掃完。

回覆的第三項是「PEL 還指著、但 stream 裡已經不存在的 id」，這跟後面講的修剪有關，XAUTOCLAIM 會順便把它們從 PEL 拿掉。

接手解決了 worker 當機。但還有另一種卡住：訊息本身有問題。例如訂單 42 在寄信前被刪除了，或欄位格式錯，不管誰來寄、寄幾次都會失敗。這種怎麼重試都會失敗的訊息叫做毒訊息（poison message）。如果不特別處理，它會被 w2 接手、失敗、閒置、再被接手，永遠循環，每次都佔掉 worker 的時間。

要分辨「暫時失敗」和「毒訊息」，看它被交出去過幾次，也就是 XPENDING 明細的第四項送達次數（delivery count）。每交出去一次就加一，XREADGROUP、XAUTOCLAIM、XCLAIM 都算。這個數字記在 Redis，所以任何一台 worker 查到的都一樣。如果改成在程式記憶體裡自己數，worker 一重啟或換一台接手，計數就歸零，毒訊息又會無限重試。

超過上限之後的做法，跟系統設計課第 12 課的死信佇列一樣，依序做三件事：

  1. 把它複製到另一個 stream，例如 ds:orders:dead，加上原本的 id 方便追查。
  2. 對原本那筆 XACK，讓它離開 PEL，不再佔著 worker。
  3. 讓監控通知人來看：毒訊息通常代表程式或資料有 bug，要有人修。

接手和重試帶來一個無法避免的副作用。回到最危險的時間點：w1 已經把信寄出去了，正要 XACK 時當機。對 Redis 來說這筆沒有 ACK，60 秒後 w2 接手、再寄一次，客人收到兩封。

處理一定要冪等。Streams 是至少一次（at-least-once）送達：worker 寄完信、XACK 之前當機，這筆會被別人接手再寄一次。Redis 沒辦法替你避免，處理的那一邊要能承受重複，例如用事件 id 當去重的 key（第 3 課的冪等鍵）或在資料庫存「這個 id 處理過了」（NestJS 課第 20 課講過同一件事）。

pub/sub 是至多一次（可能漏），Streams 是至少一次（可能重複）。收據寧可重複、也不能漏，所以選至少一次，再用冪等把「重複」擋在寄信這一步。Redis 新版在接手和重送附近還加了兩個選項，這一課用 XAUTOCLAIM 是因為它把「接手」獨立成一步，方便在處理前先檢查送達次數；新選項見課末。

💡 實務上：worker 上線前，先想好怎麼看出它卡住了
收據 worker 停了，不會有任何 API 報錯，通常是客人來問「怎麼沒收到收據」才發現。上線前把這幾個數字接上監控並設警報：XINFO GROUPS 的 lag（還沒交出去的筆數）與 pending、XPENDING 裡最久的閒置時間、dead-letter stream 的長度。dead-letter 裡的訊息要有人負責看，修好原因後能重新放回主 stream。容器每次部署換一個 consumer 名字時，舊名字會一直留在 group 裡；可以用 XGROUP DELCONSUMER 清掉，但它手上還沒 ACK 的訊息會變成沒人接得走，所以要先等 XAUTOCLAIM 接手完、PEL 是空的再刪。

收據 worker 現在能分工、能接手當機的訊息、能隔離毒訊息。上線一陣子之後會發現另一件事：stream 一直在變長。讀過、ACK 過的訊息都還留在裡面，因為 ACK 只改 group 的記錄，從來不刪 stream 的內容。

stream 會一直變長，要留多少？

stream 存在 Redis 的記憶體裡。每天 2,000 筆付款事件，一年就是 73 萬筆，全部佔著記憶體。而且這些舊事件對收據 worker 已經沒有用了：收據早就寄完，留著只是在等哪天需要重讀。所以 stream 不該當成永久的事件庫，只保留「還可能需要重讀」的那一段，其他的要修剪（trim）掉。

修剪有兩種標準：留最新的幾筆（MAXLEN），或刪掉某個時間點之前的（MINID）。可以在寫入時順便修，也可以另外定期修：

XADD ds:orders MAXLEN ~ 10000 * type paid orderId 42   # 寫入時順便修剪，大約留最新的 1 萬筆
XTRIM ds:orders MINID 1793400000000                    # 刪掉 id 比這個時間（毫秒）早的
XTRIM ds:orders MAXLEN 10000                           # 精確留 1 萬筆

三件事要搞清楚：

  • ~ 是近似修剪：stream 在 Redis 內部是把很多筆訊息打包成一個個節點存的。加 ~ 時，Redis 只刪「整個節點都超出範圍」的部分，不拆開節點，所以長度會比上限多一點點，但很便宜；不加 ~（或寫 =）就要拆開節點逐筆刪，精確但比較慢。每次寫入都修剪的 XADD 用 ~，多留幾十筆沒有影響（節點大小的預設值見課末）。
  • MINID 比的是 id 的前半段，單位是毫秒。上一節說過 id 的前半段是毫秒時間戳，所以「留 7 天」就是 Date.now() - 7 * 86400_000。拿秒（Date.now() / 1000）去比，數字小了一千倍，等於什麼都沒刪。依時間保留用 MINID，依筆數保留用 MAXLEN。
  • 修剪不管訊息處理了沒：預設的修剪只看長度或 id，不看 group 的進度。收據 worker 停了兩天，修剪可能先把還沒寄的付款事件刪掉，這些收據就跟用 pub/sub 一樣消失了。所以保留量要大於「worker 最久可能停多久」那段時間的事件量，並且監控 group 的落後（XINFO GROUPS 的 lag、pending）。新版 Redis 有只刪已確認訊息的選項，見課末。

如果真的需要一年的事件可以重播（稽核、重建報表），權威的那一份應該放在 PostgreSQL 的事件表或 Kafka 類的系統，Redis Stream 只留最近、要即時處理的部分。

到這裡，用 Streams 做的收據 worker 已經完整：存下事件、分工、處理完才確認、接手當機、隔離毒訊息、修剪。回頭看，這些功能有不少是我們自己寫的：接手的迴圈、送達次數的上限、dead-letter、監控。那麼一開始就該自己用 Streams 寫嗎？

收據 worker 一定要自己用 Streams 寫嗎？

上一節列的那些功能，有些工具已經內建。把這一課的兩個工具跟另外三種常見的選擇放在一起比，每一列都是前面某一節遇到的問題：

Redis pub/subRedis StreamsBullMQPostgreSQL SKIP LOCKEDKafka 類

表裡有三個前面沒出現過的詞。退避（backoff）是失敗後等待的時間越拉越長再重試，例如 1 秒、2 秒、4 秒，避免對方還沒恢復就被重試打垮。租約（lease）是 worker 從資料表拿走一筆工作時寫下到期時間，過期還沒完成就讓別人接手，相當於 Streams 的 PEL 加上 min-idle-time。offset 是 Kafka 消費者記錄「讀到第幾筆」的位置，提交 offset 就相當於 XACK。

表裡「跟業務資料同一個交易」那一列在說的是雙寫的問題，上面任何一個 Redis 工具都替你做不到。付款流程是先把訂單寫進 PostgreSQL，再 XADD 付款事件。如果訂單寫入成功、XADD 卻失敗（或反過來），事件就跟資料不一致：客人付了錢卻收不到收據，或收到一封根本沒成立的訂單的收據。要兩邊一定一致，先把事件寫進跟訂單同一個交易的 outbox 表，這張 outbox 表就是一般的資料表，訂單和事件在同一個交易裡要嘛一起成功、要嘛一起失敗；再由程式把它搬到 Stream（PostgreSQL 課第 33 課）。第 11 課讓搜尋索引跟資料庫同步時還會用到。

依需求對照這張表：

  • 通知、即時畫面更新：pub/sub。漏了也沒關係，前端重新查一次就對了。
  • 背景工作（寄信、產生 PDF，需要重試、延遲、排程）：BullMQ（它底層也是 Redis，替你寫好了重試與失敗清單）；量不大、要跟訂單同一個交易時用 PostgreSQL 佇列。
  • 一份事件給好幾個獨立的功能各自讀（收據、點數、報表各一個 group，各自的進度），而且要能從某個位置重讀：Streams。
  • 大量事件要保存很久、很多團隊訂閱：Kafka 類的系統，代價是要維運一整套叢集。

所以如果咖啡店只有寄收據這一個背景工作，BullMQ 會省掉這一課自己寫的大部分程式。Streams 的優勢出現在同一筆付款事件要給收據、會員點數、營收報表三個功能各自處理的時候：每個功能建立自己的 group，各有各的進度和 PEL，互不影響。而這一課學到的 ACK、PEL、接手、送達次數、冪等，不管用哪一個工具都是同一套觀念，只是有的工具替你寫好了。

💡 實務上：選工具前，先跟團隊對齊這五個問題
新功能要「非同步處理」時，資深工程師會先問：漏一則會怎樣？重複一則會怎樣？要不要延遲或排程？要保留多久、要不要重播？跟訂單資料要不要同一個交易？多數團隊的背景工作直接用 BullMQ 或資料庫佇列，Streams 留給「一份事件、好幾個功能各自讀」的情況。多加一套 Kafka 之前，要算上誰來維運、誰半夜被叫起來；量還小的時候，這個成本通常比它解決的問題大。

補充與查表

主線略過的版本細節與冷門選項，需要時再查。

  • ioredis 6.0.0 與 RESP3：課程用的 ioredis 6.0.0 預設走 RESP3 協定（Redis 6 起的新版回覆格式），訂閱中的連線其實還能下別的指令；但 RESP2 的 client（設定 protocol: 2，或其他語言的舊 client）會直接拒絕。主線仍一律用 duplicate() 另開連線，理由是兩種連線的生命週期不同。
  • PSUBSCRIBE：PSUBSCRIBE ds:ready:* 用萬用字元一次訂閱多個頻道，例如每間門市一個頻道。
  • 頻道跟資料庫編號無關：在 DB 9 PUBLISH，DB 1 的訂閱者也收得到。所以這門課的頻道名稱都加 ds:t05: 前綴，避免跟別的課撞到。
  • sharded pub/sub：Redis Cluster（第 6 課）裡，一般的 PUBLISH 會廣播到叢集的每一個節點，節點越多越浪費。Redis 7.0 起有 sharded pub/sub（SPUBLISH／SSUBSCRIBE）：頻道跟 key 一樣依名稱分到某個 slot，只在負責那個 slot 的節點之間傳。單機 Redis 用 PUBLISH 就好。
  • XAUTOCLAIM 的第三項：回覆裡「已經被刪掉的 id」這一項是 Redis 7.0 起才有。
  • 接手與去重的新選項：Redis 8.4 起 XREADGROUP … CLAIM min-idle-time 可以在讀新訊息時順便接手閒置太久的訊息；Redis 8.6 起 XADD … IDMP 讓生產者重送同一筆時不會寫進兩次。
  • stream 的節點大小：課程的 Redis 預設 stream-node-max-entries 100，一個節點最多 100 筆。
  • 只刪已確認的訊息：Redis 8.2 起 XADD／XTRIM 可以加 ACKED，只刪所有 group 都確認過的訊息。

練習

先確認 Redis 有在跑（docker compose --profile redis up -d --wait），在 learn/ 執行 node check.mjs data-stores 05 判分。函式的第一個參數 redis 由測試傳入，連到 DB 5；stream 與頻道的名稱都用 ds:t05: 開頭。

練習 1：在 notify.ts 做「飲料做好了」的通知。publishReady(redis, orderId, at) 把 { orderId, at } 轉成 JSON 發布到 READY_CHANNEL，回傳收到的訂閱者數。subscribeReady(redis, onMessage) 用 redis.duplicate() 另開一條連線訂閱，每則訊息解析成物件交給 onMessage；回傳之前訂閱要已經生效；回傳的函式要取消訂閱並關掉那條連線。測試會比對 Redis 上的連線清單，確認每次訂閱都多一條連線、取消後那條連線消失。

練習 2：在 receipts-worker.ts 寫收據 worker 的 consume，每呼叫一次處理一批：group 不存在就從 stream 開頭建立（已存在的 BUSYGROUP 錯誤要忽略）；用 XREADGROUP 讀最多 count 筆新訊息；逐筆交給 handle，成功才 XACK，失敗就不 ACK、繼續下一筆；回傳讀到幾筆。測試先寫 20 筆事件，讓兩個 worker 輪流跑，每筆要恰好處理一次。

練習 3：在 reclaim.ts 寫 reclaimStuck：用 XAUTOCLAIM 接手閒置至少 minIdleMs 的訊息（掃到游標回 0-0），用 XPENDING 查每筆的送達次數；超過 maxDeliveries 的寫到 <stream>:dead（保留原欄位，加上 originalId）並 XACK，其他的回傳給呼叫的人重新處理。

練習 4：在 trim.ts 替 stream 設上限。appendEvent 寫入一筆並用近似修剪讓長度維持在 maxLen 附近，回傳新的 id；trimOlderThan(redis, stream, cutoffMs) 精確地刪掉時間早於 cutoffMs 的訊息，回傳刪了幾筆。測試會一次寫 5,000 筆，長度要落在 1000～1100。

練習 5：用 Redis pub/sub 通知「寄電子收據」的 worker。worker 重新部署的 10 秒內進來 30 筆訂單，結果會怎樣？

✓ pub/sub 不保存訊息，PUBLISH 只送給當下正在訂閱的連線，沒人時回 0，不是錯誤，所以 d 的 API 根本不知道出事了。a、c 描述的是 Streams 或佇列的行為。不能丟的工作用 Streams、BullMQ 或資料庫佇列。

練習 6：consumer group 裡的 w1 已經寄出收據，卻在 XACK 之前當機。之後會怎樣？

✓ 沒 ACK 的訊息一直留在 PEL，Redis 不會自動重送（c），也不會擋住其他新訊息（d）。要有人用 XAUTOCLAIM 接手，接手的人再處理一次，所以這是至少一次送達，寄信的邏輯要用事件 id 去重。a 是「先 ACK 再處理」才會發生的事。

練習 7：想保存一年的訂單事件，以後可以重播來重建報表。把 Redis Stream 當唯一的儲存好嗎？

✓ stream 沒有筆數上限（d 錯），但每一筆都佔 Redis 的記憶體，一年的事件很貴；AOF（c）只決定當機時丟多少，不解決成本與備份。a 說對了「讀過不會消失」，但這正是要修剪的原因。長期、權威的資料放在便宜、可備份的地方。

常見錯誤

  • 用 pub/sub 傳不能丟的工作：訂閱者斷線、部署的那幾秒，訊息就沒了，而且沒有任何錯誤。寄信、扣點數這類工作用 Streams、BullMQ 或資料庫佇列。
  • 拿共用的連線訂閱，或取消時只 unsubscribe：訂閱用 duplicate() 另開一條，取消時 quit() 整條關掉，不然每訂閱一次就漏一條連線。
  • 處理前就 ACK，或失敗也 ACK：當機或出錯的那筆就從 PEL 消失、再也沒人處理。處理成功才 XACK。
  • 用 XREAD 讓多個 worker 分工：每個 worker 都會讀到全部，工作被做好幾次。分工用 consumer group 的 XREADGROUP >。
  • group 用 $ 建立，漏掉上線前的事件：要處理已經在 stream 裡的訊息，從 0 開始。
  • 沒人處理 PEL：當機的 worker 手上的訊息永遠卡著。定期用 XAUTOCLAIM 接手，並監控 XPENDING 的筆數與最久的閒置時間。
  • 毒訊息無限重試，或送達次數記在程式記憶體：用 XPENDING 的送達次數判斷，超過上限移到 dead-letter stream 並 ACK。
  • stream 沒有修剪，或 MINID 用秒：XADD 加 MAXLEN ~，或定期 XTRIM … MINID（毫秒）。保留量要比 worker 可能停機期間的事件量多。
  • 處理邏輯不冪等：至少一次送達代表一定會有重複，用事件 id 去重。

小結

  • 選工具先問「這則訊息沒人收到，會不會有人發現」：不會（通知平板）用 pub/sub，會（寄收據）用能存、能確認、能重送的工具。
  • pub/sub 是至多一次的即時廣播：PUBLISH 回收到的人數，沒人聽就丟掉；適合通知、扇出 WebSocket，不適合工作。訂閱用另開的連線，不用時整條關掉。
  • stream 是只能附加、id 為「毫秒-序號」的紀錄，讀過也不會消失；consumer group 讓每筆只交給一個消費者，交出去還沒 ACK 的記在 PEL。
  • 處理成功才 XACK；當機的訊息用 XPENDING 找、XAUTOCLAIM 接手；送達次數超過上限的移到 dead-letter stream 並 ACK。
  • Streams 是至少一次送達，處理要冪等。
  • stream 要修剪：寫入時 MAXLEN ~，依時間用 MINID（毫秒）；保留量要撐得過 worker 停機；長期、權威的事件放在 PostgreSQL 或 Kafka 類系統。
  • 選工具看能不能丟、要不要重試與排程、要不要重播、要不要跟業務資料同一個交易，以及多一套系統的維運成本；只有一個背景工作時 BullMQ 通常比自己寫 Streams 省事。
