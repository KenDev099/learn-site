階段 3：MongoDB 與文件模型 · 第 9 課

MongoDB 交易與一致性（資深）：write concern、read concern 與何時不用 MongoDB

咖啡店的門市活動頁開放「拉花體驗，限量 50 名」。上線第一週出了兩件事：第一，報名人數變成 53 人；第二，有位客人拿著「報名成功」的截圖來店裡，名單上卻找不到他。查了紀錄，那天晚上 MongoDB 的主機剛好故障切換過一次。

這一課就是這場事故的檢討：從這兩件事出發，一路把報名系統修到「名額守得住、回了成功就不會消失、客人看到的是對的」，再處理檢討時冒出來的換場次、多人編輯活動頁，最後回答會議上一定會有人問的那一題：這些資料到底該不該放在 MongoDB。

這課的路線：
  1. 名額為什麼變成 53 人：先讀再寫為什麼會超賣，一次帶條件的更新怎麼守住名額。
  2. 「報名成功」卻不見：正式環境的 MongoDB 是好幾台機器，「成功」是幾台說的，write concern 怎麼讓回了成功的寫入不再消失（開場第二個問題的答案）。
  3. 剛報名完卻顯示「尚未報名」：讀取送到哪台機器、讀到的資料有多可靠（讀取偏好與 read concern）。
  4. 換場次要改兩份文件：一次更新做不到時，多文件交易怎麼寫、為什麼會重試、代價是什麼。
  5. 多人編輯活動文案、該不該用 MongoDB：版本欄位防止修改被蓋掉；用第 1 課的四個問題判斷哪些資料該留在 PostgreSQL。
這課會用到：
  • 第 7 課的內嵌與部分更新：一起讀的放同一份文件；$inc、$push 只改文件的一部分。
  • PostgreSQL 課第 18 課的交易：多個修改要嘛一起提交、要嘛一起回滾。

名額為什麼變成 53 人？

先處理第一件。報名的第一版寫法，把活動的名額和名單存在 events 集合的同一份文件裡：seatsLeft 是剩下幾位，attendees 是已報名客人的陣列。程式先讀、再判斷、再寫：

const ev = await events.findOne({ _id: 'latte-art-11' })              // 1. 讀
if (ev.seatsLeft <= 0 || ev.attendees.includes(customerId)) return false   // 2. 判斷
await events.updateOne({ _id: 'latte-art-11' },                         // 3. 寫
  { $inc: { seatsLeft: -1 }, $push: { attendees: customerId } })

只有一個人報名時，這段程式完全正確。問題出在同時有很多人報名。API 伺服器同一時間會處理好幾個請求，每個請求在 await 等資料庫回應時，Node 就去處理別的請求，所以兩個請求的步驟會交錯執行，這種情況叫並發（concurrency）。

假設只剩最後 1 位，客人甲和客人乙同時按下報名：

  1. 甲的請求執行第 1 步，讀到 seatsLeft: 1。
  2. 甲還沒執行第 3 步，乙的請求就執行了第 1 步，讀到的同樣是 seatsLeft: 1，因為甲還沒寫。
  3. 兩個請求的第 2 步都判斷「還有名額」，都往下走。
  4. 甲寫入，seatsLeft 變 0；乙寫入，seatsLeft 變 -1，名單多了一個人。

判斷用的是「讀的那一刻」的資料，寫入發生在「之後」，中間這段空檔誰都可以插進來。開放報名的瞬間有幾十個人同時按，空檔被插了 3 次，就是 53 人。這跟第 4 課的限量優惠券是同一類問題，修法的想法也一樣：讓「判斷」和「寫入」變成一個不能被插隊的動作。

「不能被插隊」在資料庫裡叫原子（atomic）。一個原子操作要嘛整個做完、要嘛完全沒做；別人看不到它做到一半的樣子，也插不進它的中間。MongoDB 保證單一文件的寫入是原子的：一次 updateOne 裡的篩選條件和所有修改，在那份文件上一次完成，別的寫入要等它做完才能動這份文件。

所以把「判斷」搬進篩選條件，讀、判斷、寫三步就變成一次更新：

const r = await events.updateOne(
  { _id: 'latte-art-11', seatsLeft: { $gt: 0 }, attendees: { $ne: customerId } },  // 有名額、還沒報名
  { $inc: { seatsLeft: -1 }, $push: { attendees: customerId } },
)
return r.modifiedCount === 1    // 1：報名成功；0：條件不成立（額滿、已報名或活動不存在）

再跑一次甲和乙搶最後一位：兩個更新到了 MongoDB，在這份文件上一個接一個執行。先到的甲檢查條件成立，把 seatsLeft 改成 0、名單加入甲；後到的乙再檢查條件時，seatsLeft: { $gt: 0 } 已經不成立，這次更新什麼都不改，modifiedCount 是 0，API 就回「已額滿」。程式不再自己讀名額，判斷交給資料庫在寫入的同一刻做。

篩選裡的 attendees: { $ne: customerId } 意思是「陣列裡沒有這個值」，擋掉同一個人連按兩次。這個條件一定要放在篩選裡，不能只靠更新運算子：

只用 $addToSet（陣列裡沒有才加）取代 $push 不夠：同一個人第二次報名時，$addToSet 不會重複加入，但同一個更新裡的 $inc 照樣扣了名額。「還沒報名」一定要寫在篩選條件裡，條件不成立時整個更新都不做。

這招之所以可行，是因為名額和名單放在同一份文件。這就是第 7 課說「一起讀寫的資料放在同一份文件」的另一個好處：需要一起成立的規則（名額和名單要一致），放在同一份文件就能用一次更新守住，不需要交易。MongoDB 官方文件也這樣建議：交易比單一文件寫入慢，不能拿來取代好的資料模型。

反過來說，規則一旦跨了好幾份文件，一次更新就做不到：把客人從 A 活動移到 B 活動（兩份活動文件）、報名同時要寫一筆紀錄到另一個集合、扣門市庫存同時建立訂單。名單太大也不能內嵌（一份文件最大 16 MB，幾萬人的名單要改成每人一份文件）。這些情況要用多文件交易，後面「換場次」那一節會遇到。

💡 實務上：看到「先 find 再 update」就停下來問一句
限量報名、優惠券、庫存扣減、點數折抵，都是「先檢查還夠不夠、再扣」的需求，程式碼審查時最常看到的就是先 findOne 再 updateOne。資深的人會先問：這個檢查能不能寫進更新的篩選條件？能，就一次條件更新，用 modifiedCount（或 findOneAndUpdate 回傳的文件）判斷成功沒，API 依結果回「報名成功」或 409「已額滿」。單機測試幾乎測不出這種錯，要像練習 1 那樣讓幾百個請求同時打才會出現。

名額守住了。但第二件事還沒解釋：那位客人的報名明明拿到了「成功」，資料卻不在。要回答這個問題，得先知道正式環境的 MongoDB 不是一台機器。

「報名成功」卻不見：成功是幾台機器說的？

只放一台資料庫伺服器，它當機時整個報名系統就停了，硬碟壞掉資料也跟著沒了。所以正式環境的 MongoDB 幾乎都是 replica set（複本集）：同一份資料存在三台（或更多台）機器上，每台叫一個節點。

這幾個節點的分工不一樣。其中一台是 primary（主節點），所有寫入都只送到它；其他的是 secondary（次節點），不直接接受寫入，而是跟著 primary 複製資料。primary 每做一筆修改，就記一行到自己的操作紀錄裡，這份紀錄叫 oplog；secondary 在背景不斷讀 primary 的 oplog，照著同樣的順序在自己身上重做一次。這個複製是非同步的：primary 寫好就繼續做下一件事，不等 secondary，所以 secondary 總是落後 primary 一點點。

primary 當機時，剩下的節點會投票，選出一台資料最新的 secondary 當新的 primary，這叫故障切換（failover），通常十幾秒內就能恢復寫入。開場那天晚上發生的就是這件事。這套架構就是系統設計課第 6 課的主從複寫。

問題就藏在「非同步」裡。primary 寫好一筆、還沒被任何 secondary 複製走之前，這筆資料只存在 primary 上。如果這時 primary 當機，新選出來的 primary 根本沒有這筆。

那應用程式什麼時候會收到「成功」？由 write concern（寫入確認等級）決定：它設定一次寫入要被多少個節點確認，資料庫才回你成功。開場那位客人的報名用的是 w: 1，意思是「primary 自己寫好就回成功」：

由上往下讀這張圖：節點 1 寫好報名、回了成功，客人截圖；接著節點 1 還沒把這筆複製出去就當機；節點 2 當選新的 primary，它和節點 3 上都沒有這筆報名，之後的報名都寫在節點 2 上。

節點 1 修好回來時，它身上多了一筆新 primary 沒有的寫入，兩邊的歷史對不起來。它只能變成 secondary、跟著新 primary 走，所以必須先撤銷自己多出來的那筆。這個撤銷叫 MongoDB 的 rollback：被撤銷的寫入會存成 <dbpath>/rollback/ 底下的 BSON 檔，不會自動放回去，要管理員用 bsondump 讀出來再決定怎麼處理。實務上幾乎沒人去撈，所以等於遺失。這就是那位客人的報名不見的原因。注意這和 PostgreSQL 交易的 ROLLBACK（回滾）不同：交易的回滾是程式主動放棄一筆還沒提交的交易；這裡的 rollback 是舊 primary 重新加入時，被迫撤銷已經回過成功的寫入。

修法是讓「成功」等到資料已經安全再回。把 write concern 設成 w: 'majority'，資料庫要等多數有投票權的節點（3 台裡的 2 台）都寫好才回成功。故障切換時，新 primary 必須拿到多數票才能當選，而節點不會投票給資料比自己舊的候選人；多數節點已經有這筆，能拿到多數票的新 primary 一定也有這筆，所以回了成功的寫入不會被 rollback。

write concern 的幾個設定放在一起比較：

設定等到什麼才回成功故障時
w: 0不等任何回應，送出就算寫入失敗你也不知道
w: 1primary 寫好primary 在複製出去之前當機，這筆會被 rollback
w: 'majority'多數有投票權的節點（3 台裡的 2 台）都寫好回成功之後，故障切換也不會消失
journal: true（舊寫法 j: true）另外要求寫進磁碟上的日誌（journal）防的是程序當機、斷電；單獨使用不防故障切換
wtimeoutMS等確認最多等多久逾時只回錯誤，已經寫入的不會撤銷

表裡的 journal 是每個節點磁碟上的日誌：寫入先記進 journal，程序當機重啟時可以從這裡補回來。它保護的是「這一台」的資料，跟要不要複製到別台是兩回事，所以只開 journal 擋不住開場那種故障切換。wtimeoutMS 則是給 majority 配的上限：多數節點連不上時，majority 會一直等，加上逾時才能讓 API 不卡住。

從 MongoDB 5.0 起，大多數部署的預設 write concern 就是 w: 'majority'，但有例外（例如 primary＋secondary＋arbiter 這種架構，arbiter 是只投票、不存資料的節點，這時預設會降成 w: 1），細節見課末。既然預設多半是安全的，為什麼還要寫出來？因為預設會被改：有人為了壓測數字在連線字串加 w=1、雲端服務的設定被調過、或架構有例外。開場的事故就是這樣：報名用的是 w: 1。重要的寫入在程式碼裡明寫 w: 'majority'，看程式的人一眼知道這筆不能丟，部署設定被改也不受影響。driver 的寫法（課程用的是 Node.js driver mongodb 7.8.0）：

// 單一操作
await db.collection('registrations').insertOne(reg, { writeConcern: { w: 'majority' } })
// 整個 client 的預設，也可以寫在連線字串：mongodb://…/?w=majority
const client = new MongoClient(url, { writeConcern: { w: 'majority' } })

majority 不是免費的：它要多等一個網路來回，加上 secondary 寫入的時間，延遲比 w: 1 高一些。所以要依「這筆丟了會怎樣」來選。報名、付款、稽核紀錄這類「回了成功就不能消失」的寫入用 majority；活動頁瀏覽次數這種少幾筆沒關係的計數，可以用 w: 1 換一點延遲。w: 0 連錯誤都收不到，幾乎沒有適合的場合。練習 3 就是要你替這三種寫入做選擇。課程的容器只有一個節點，在本機看不出 w: 1 和 majority 的差別，原因見課末。

💡 實務上：接手專案時，先查清楚「預設」到底是什麼
在 mongosh 執行 db.adminCommand({ getDefaultRWConcern: 1 })：defaultWriteConcern 是整個部署的預設，defaultWriteConcernSource 是 implicit 代表沒人設定過、用的是隱含預設，是 global 代表有人用 setDefaultRWConcern 改過。接著看環境變數裡的連線字串有沒有 w=1，再搜尋程式碼裡的 writeConcern。架構裡有 arbiter 時，跟維運確認預設是不是被降成了 w: 1。w: 'majority' 在多數節點連不上時會一直等，所以 API 的寫入通常再加 wtimeoutMS（例如 5000）；逾時只代表「不確定」，這筆可能已經寫進去，重試要靠冪等，也就是同一個請求送兩次，結果和送一次一樣（系統設計課第 9 課），例如報名用唯一索引擋重複。

寫入不會再消失了。但這個架構還有另一面：資料存在好幾台機器上，讀取的時候也有「讀哪一台」的問題。

剛報名完重新整理，為什麼顯示「尚未報名」？

修好 write concern 之後，團隊為了減輕 primary 的負載，把整個服務的讀取改去 secondary。隔週客服轉來新的回報：客人剛報名完、重新整理頁面，畫面卻顯示「尚未報名」，有人因此又報名一次。報名確實寫進去了，問題出在讀。

讀取送到哪個節點，由讀取偏好（read preference）決定。預設是 primary：所有讀取都送到 primary，讀到的一定是最新寫入的資料。團隊改成的 secondaryPreferred 則是「有 secondary 可用就讀 secondary」。讀 secondary 的好處是分擔 primary 的負載，代價來自上一節講的非同步複製：secondary 落後 primary 一點點，可能讀到舊資料。另外還有幾種模式，列在課末。

客人遇到的就是這個落後：報名寫進了 primary，重新整理的讀取被送到還沒複製到這筆的 secondary，讀到的是報名之前的狀態。「自己剛寫的東西，自己馬上讀得到」這個保證叫 read-your-writes，讀 secondary 時它就不成立了。

解法依情況選：

  • 使用者剛改過的東西，讀 primary。最簡單，大部分服務這樣就夠了；讀 secondary 只用在報表、推薦這類晚幾秒沒關係的地方。報名狀態就屬於前者。
  • 因果一致 session（causally consistent session）：真的需要讀 secondary，又要看得到自己剛寫的，就讓讀寫在同一個 session 裡。做法在下面說明。

session 是 driver 裡代表「同一串相關操作」的物件，用 client.startSession() 開，用完要 endSession() 歸還，每個操作傳 { session } 表示它屬於這一串。因果一致的意思是：同一個 session 裡，後面的讀取保證看得到前面的寫入。driver 會在讀取時帶上前一次操作的時間點，secondary 還沒跟上這個時間點就先等，跟上了才回結果。Node.js driver 用 client.startSession() 明確開的 session 預設就是因果一致。

讀 primary 就一定安全嗎？還差一層。從上一節知道，primary 上的資料不一定被多數節點確認過，之後可能被 rollback。讀取也有對應的設定，叫 read concern（讀取一致性等級），決定讀到的資料要多「確定」：

等級讀到什麼什麼時候用
local（預設）這個節點上最新的資料，不管有沒有被多數確認，可能是之後會被 rollback 的一般讀取
majority已經被多數節點確認的資料，故障切換後也不會變依讀到的值做重要決定（例如讀到「已付款」就出貨）
snapshot同一個時間點的一致快照交易裡、需要多次讀取彼此一致時

write concern 管「回成功之前要確認到什麼程度」，read concern 管「讀到的要確認到什麼程度」，兩者配成一對。因果一致 session 要在故障切換時也成立，官方建議寫入用 w: 'majority'、讀取用 read concern majority。合在一起的寫法：

const session = client.startSession()        // 明確開的 session 預設 causalConsistency: true
try {
  await regs.insertOne(reg, { session, writeConcern: { w: 'majority' } })
  const mine = await regs.find({ customerId: reg.customerId }, {
    session, readPreference: 'secondaryPreferred', readConcern: { level: 'majority' },
  }).toArray()                                  // 讀 secondary 也看得到剛剛那筆
} finally {
  await session.endSession()
}

這段程式看兩件事：寫入和讀取傳的是同一個 session；讀取雖然送到 secondary，但因為在同一個因果一致 session 裡，看得到剛剛那筆報名。表中的 snapshot 是給交易用的：同一個交易裡讀好幾次，看到的都是同一個時間點的資料。下一節的換場次交易裡每一步都是條件更新，不需要先讀出資料再比對，所以用不到它。

💡 實務上：讀 secondary 之前，先量複寫延遲，也減少「寫完馬上讀」
適合讀 secondary 的是後台報表、推薦清單、熱門活動排行這類晚幾秒沒關係的查詢；報名、付款狀態、會員資料一律讀 primary。決定之前，在 primary 上用 rs.printSecondaryReplicationInfo() 看每台 secondary 落後幾秒（Atlas 的監控頁有 Replication Lag 圖表），平常就落後好幾秒的，讀它的頁面會常常「看起來沒更新」。前端也能幫忙：報名 API 直接回傳更新後的報名狀態，Vue 頁面用這個回應更新畫面，不要報名成功後立刻再打一次 GET。客服回報「剛改完又變回舊的」時，先查那支 API 的讀取偏好。

到這裡，報名這一份活動文件的寫和讀都處理好了。檢討會上接著提出新需求：讓客人把報名從這一場換到另一場。這要同時改兩份活動文件，第一節的一次條件更新做不到。

換場次要同時改兩份活動文件，怎麼用交易守住？

換場次是三個動作：從 A 場的名單移除客人並把 A 的名額加 1、把客人加進 B 場並把 B 的名額減 1、在 moves 集合記一筆換場紀錄。它們分散在兩份活動文件和另一個集合，單一文件的原子性管不到。如果 A 已經移除、B 卻剛好額滿加不進去，客人就兩場都沒有。我們要的是三個動作一起成功或一起失敗。

這就是多文件交易（multi-document transaction）：讓多份文件、甚至多個集合的修改一起提交、或一起回滾，對應 PostgreSQL 課第 18 課的 BEGIN／COMMIT／ROLLBACK。MongoDB 的伺服器程式叫 mongod，交易只能在 replica set（上一節的架構）上用，單獨跑一台 mongod 不能用交易；課程的容器怎麼滿足這個條件，見課末。

Node.js driver 的寫法。交易綁在上一節介紹的 session 上：

const session = client.startSession()          // 1. 開一個 session：交易綁在 session 上
try {
  await session.withTransaction(async () => {   // 2. 開始交易、執行函式、提交
    const out = await events.updateOne(
      { _id: fromId, attendees: customerId },
      { $pull: { attendees: customerId }, $inc: { seatsLeft: 1 } },
      { session },                               // 3. 每個操作都要傳 session
    )
    if (out.modifiedCount === 0) throw new NotRegisteredError()   // 丟錯 → 中止交易
    const into = await events.updateOne(
      { _id: toId, seatsLeft: { $gt: 0 }, attendees: { $ne: customerId } },
      { $push: { attendees: customerId }, $inc: { seatsLeft: -1 } },
      { session },
    )
    if (into.modifiedCount === 0) throw new SeatsFullError()      // 前面的 $pull 也會一起回滾
    await moves.insertOne({ customerId, from: fromId, to: toId }, { session })
  })
} finally {
  await session.endSession()                     // 4. 用完歸還 session
}

注意每一步本身仍是第一節的條件更新：A 場的篩選確認客人在名單裡，B 場的篩選確認有名額、客人還沒報名。交易沒有取代條件更新，它做的是把這幾次更新綁在一起。

withTransaction(fn) 依序做這些事：開始交易 → 執行 fn → fn 正常結束就提交，fn 丟錯就中止（abort）並把錯誤往外丟。成功時它回傳 fn 的回傳值。所以上面 B 場額滿時丟出 SeatsFullError，交易中止，A 場的 $pull 也一起撤銷，客人留在 A 場。寫的時候有四條規則：

  • 每個操作都要傳 { session }。漏傳的那個操作不在交易裡，它會立刻生效，交易中止時也不會跟著回滾。這是最常見、也最難發現的錯：平常都成功，只有失敗的時候資料才不一致。
  • 錯誤要往外丟，不能自己 catch 吞掉。fn 正常結束，withTransaction 就會提交。上面的 SeatsFullError 如果被你 catch 後 return，交易照樣提交，客人從 A 移除了、卻沒加進 B。
  • 交易裡的操作要一個一個 await。driver 的文件寫明：同一個交易裡用 Promise.all 平行執行是未定義行為。
  • fn 可能被執行好幾次，所以裡面只放資料庫操作。寄信、呼叫金流、推播放在交易成功之後，不然重試時會寄兩封。為什麼會執行好幾次，下面說明。

第四條要從交易怎麼處理衝突講起。開放換場那晚，好幾個人同時換進熱門的 B 場，他們的交易都要改 B 場這份文件。PostgreSQL 遇到這種情況，會讓後來的交易等前面的提交；MongoDB 不等，而是讓後來的那個交易立刻失敗，錯誤是 WriteConflict。失敗的交易什麼都沒寫進去，只要從頭再跑一次，通常就成功了。

程式怎麼知道一個錯誤「重跑就好」？MongoDB 在這類錯誤上附了錯誤標籤（error label），告訴程式該怎麼處理。跟交易有關的有兩個：

標籤代表什麼該怎麼做
TransientTransactionError暫時性的錯：寫入衝突、故障切換中找不到 primary、網路斷線。交易已經中止，什麼都沒寫進去從頭重跑整個交易
UnknownTransactionCommitResult送出 commit 後沒收到回覆，不知道到底提交了沒只重送 commit（commit 是冪等的，重送不會做兩次）

第二種要多解釋一句。前面提過的冪等（idempotent），意思是同一個動作做一次和做好幾次，結果一樣。commit 送出後連線斷了，程式不知道交易到底提交了沒；因為重送 commit 是冪等的，已經提交過的不會再提交一次，所以只要重送 commit，不需要、也不應該重跑整個交易。

withTransaction 已經照這張表處理：遇到 TransientTransactionError 就稍等一下、重跑整個 fn，遇到 UnknownTransactionCommitResult 就重送 commit，有總時間上限（driver 的實際數字見課末）。這就是 fn 會被執行好幾次的原因，也是第四條規則的由來。自己用 session.startTransaction()、commitTransaction() 手寫，就要自己做這些重試；沒做的話，並發一高就會有請求因為 WriteConflict 直接失敗。除非有特別理由，一律用 withTransaction。

這跟 PostgreSQL 課第 31 課的「SERIALIZABLE 遇到序列化失敗（40001）就重跑整個交易」是同一個想法：資料庫負責偵測衝突，程式負責重試。

交易能解決跨文件的問題，但不是免費的，這也是第一節說「能用一次條件更新就不要用交易」的原因。它的代價與限制：

  • 時間：交易預設要在 60 秒內完成（伺服器參數 transactionLifetimeLimitSeconds），超過會被背景程序中止。交易裡不要等使用者輸入、不要呼叫外部 API。
  • 同時開啟的數量：MongoDB 9.0 起，伺服器限制同時開啟的多文件交易數（maxConcurrentMultiDocumentTransactions，預設 10000），超過時新的交易會收到 TooManyOpenTransactions 錯誤。交易拖太久或忘了結束，就會慢慢佔滿這個額度。
  • 記憶體：交易中的修改都留在 WiredTiger 快取（第 8 課提過的儲存引擎記憶體）裡，太大放不下會收到 TransactionTooLargeForCache。一次改上萬份文件的批次作業不要包成一個交易。
  • 讀取偏好：交易裡有讀取時，讀取偏好必須是 primary，所有操作都送到同一個節點。上一節改成 secondaryPreferred 的設定，不能用在交易裡。
  • write concern 設在交易上：交易裡的單一操作不要各自設 write concern，要設在 withTransaction(fn, { writeConcern: { w: 'majority' } }) 或 client 上。換場次和報名一樣不能丟，交易提交也要等多數節點確認。單一操作寫了會怎樣，見課末。
💡 實務上：交易函式只做資料庫的事，其他動作排在後面
常見的場景是後台的「把客人換到另一場」「取消報名並退回名額」。程式碼審查時看三件事：交易函式裡每個呼叫都有 { session }；業務錯誤（SeatsFullError）往外丟，到 API 層才轉成 409 和「這場已額滿」的訊息，不要變成 500；寄確認信、推播、呼叫金流都在 withTransaction 回傳之後。如果信「一定要寄出」，就在同一個交易裡多寫一筆待寄送紀錄，由背景程式讀出來寄，這就是系統設計課第 12 課的 outbox。交易函式會被重跑，所以也不要在裡面累加記憶體裡的計數器或陣列。

換場次在一次請求內就做完，交易撐得住。但後台還有一種並發，時間長到交易撐不住：兩個人同時編輯同一份活動文案。

店長和行銷同時改活動文案，誰的修改會被蓋掉？

事故之後，活動頁要補上說明。店長和行銷同時打開「拉花體驗」的後台編輯頁，畫面上是同一份文件的第 3 版。店長改了標題先存；幾分鐘後行銷改完內文也存了。行銷的編輯頁送出的是她打開時看到的整份內容，裡面的標題還是舊的，店長的修改就被蓋了回去。這叫遺失更新（lost update），PostgreSQL 課第 19 課看過。

前面兩個工具在這裡都不適用。第一節的條件更新，前提是規則能寫成篩選條件，但「我打開之後沒有別人改過」不是文件裡現成的欄位。交易也不行：編輯頁會開好幾分鐘，交易有 60 秒上限，不可能從打開頁面一路撐到按下儲存；就算能撐，也會一直佔著資源。

解法是讓「有沒有被別人改過」變成文件裡的一個欄位。樂觀並發控制（optimistic concurrency control）的做法是：文件帶一個 version 欄位，編輯頁打開時把它一起讀出來；儲存時要求「版本還是我讀到的那個，才更新，並把版本加 1」。它叫「樂觀」，是因為它不事先鎖住文件，假設衝突很少發生，真的發生時才在儲存那一刻擋下來。版本檢查放進篩選條件，又回到第一節那一招：

const { _id, version, ...fields } = patch    // 不讓前端送來的 _id、version 混進 $set
const doc = await promos.findOneAndUpdate(
  { _id: id, version: expectedVersion },     // 版本還是我讀到的那個
  { $set: fields, $inc: { version: 1 } },    // 套用修改，版本加 1
  { returnDocument: 'after' },               // 回傳更新後的文件（預設是更新前的）
)
if (!doc) throw new VersionConflictError()   // 被別人改過了（或文件不存在）

套回店長和行銷：兩人都拿 version: 3 送出。店長先到，篩選 version: 3 找到文件，套用修改，版本變成 4。行銷後到，篩選 version: 3 已經找不到文件，findOneAndUpdate 回傳 null。API 回 409 Conflict，前端提示「這份內容剛被別人修改，請重新載入」，讓行銷看過最新版本再決定怎麼改，店長的標題就保住了。

第一行先把 _id 和 version 從 patch 拿掉，有兩個原因。第一，如果讓呼叫端能改 version，版本檢查就形同虛設。第二，同一個更新裡同時 $set 和 $inc 同一個欄位，MongoDB 會直接回錯誤（路徑衝突），改 _id 也會被拒絕（_id 不能修改）。

到這裡，這課的三種工具可以放在一起選：同一份文件、條件能寫進篩選的，一次條件更新就好；一次請求內做完、跨多份文件的修改，用交易；衝突少、操作時間長（人在編輯），用版本欄位。

💡 實務上：版本號要從資料庫一路走到前端
後台編輯頁的 API 常見做法：GET 回傳文件時帶上 version，前端把它存在表單狀態裡，儲存時原樣送回（放在 body，或用 HTTP 的 ETag／If-Match 標頭；用 If-Match 時慣例回 412 Precondition Failed，放 body 時回 409）。Vue 編輯頁收到衝突時，提示「內容已被其他人修改」並提供重新載入，不要自動用新版本重送，那樣等於把別人的修改蓋掉。不是每份資料都需要版本欄位：計數器用 $inc、只有本人會改的偏好設定，直接更新就好；多人會長時間編輯的內容（活動文案、菜單、價格）才值得加。

報名系統修完了。檢討會的最後，有人提出更根本的問題：既然 MongoDB 要額外處理這麼多一致性的事，咖啡店的訂單要不要也放進來統一管理？或者反過來，報名要不要乾脆搬回 PostgreSQL？

事故檢討的最後一題：這些資料該不該放在 MongoDB？

先說清楚這題不是在問「做不做得到」。這課已經看到，MongoDB 有交易、有 majority write concern，技術上能存訂單。選型真正的問題是「用它做，程式和團隊要多付出多少」。把第 1 課的四個問題套在 MongoDB 上，以下情況要付出的特別多：

情況為什麼不適合 MongoDB
資料高度關聯：訂單、品項、付款、庫存彼此引用沒有外鍵，資料之間的一致性全靠程式；幾乎每個寫入都要跨文件交易，交易又比單一文件慢
需要大量約束：金額不能為負、庫存不能超賣、帳要平schema 驗證只檢查單一文件，跨文件的規則（總和、唯一組合以外的關係）資料庫幫不上忙
臨時的複雜報表：老闆要「上個月每家門市、每種商品、每個時段」$lookup 可以做，但寫起來長、效能難預測；SQL 的 JOIN 與 GROUP BY 是這種需求的強項
團隊只有 PostgreSQL 的維運經驗replica set、備份、升級、監控都要重新學，事故時沒人知道 rollback 檔是什麼

拿訂單對照這張表：一張訂單牽涉品項、付款、庫存，每次下單都是跨文件的寫入，等於每個寫入都要走換場次那一節的交易；「庫存不能超賣」「帳要平」這類規則，MongoDB 只能靠程式守。表上四項它幾乎全中。

報名則相反。它以「一份活動文件」為單位讀寫，名額和名單放在一起，靠第一節的一次條件更新就守住了，只有換場次需要交易。這正是 MongoDB 適合的樣子。適合的情況還有：每筆的結構差很多（不同類別商品有不同屬性），或寫入量大到需要水平擴展。水平擴展在 MongoDB 叫 sharding：依某個欄位把資料切開，分散到好幾組 replica set，每組只負責一部分資料。

所以咖啡店的分工是：訂單、付款、庫存留在 PostgreSQL，活動頁內容、報名與評論放 MongoDB。如果只是需要「幾個彈性欄位」，PostgreSQL 的 JSONB 就夠了，還保留交易和外鍵。

💡 實務上：選型討論講需求，不講工具的好惡
在團隊討論時，不要說「MongoDB 不適合做交易」，這句話不精確，這課就用交易做了換場次。要說「這份資料的存取模式是 X，一致性需求是 Y，用 MongoDB 要額外處理 Z」，例如「訂單每次寫入都跨品項、付款、庫存三種資料，用 MongoDB 每個寫入都要包交易，約束也要自己寫」。這樣大家討論的是需求，不是誰喜歡哪個工具。

補充與查表

主線略過的版本細節與冷門選項，需要時再查。

  • 課程環境的 replica set：課程的容器以 --replSet rs0 啟動成只有一個節點的 replica set，所以交易可以用，連線字串要加 directConnection=true。只有一個節點時，多數就是 1，w: 1 和 majority 在本機看不出差別，差別只在真正有多台機器時出現。
  • sharded cluster 與交易：除了 replica set，多文件交易也能用在 sharded cluster（分片叢集：資料依某個欄位切開，分散到好幾組 replica set）上。
  • 預設 write concern 的細節：從 MongoDB 5.0 起，大多數部署的隱含預設 write concern 是 w: 'majority'。例外是有仲裁節點（arbiter，只投票、不存資料的節點）的 replica set：存資料的有投票權節點數不超過「多數」時，預設會降成 w: 1，例如 primary＋secondary＋arbiter 的三節點架構。另外，伺服器參數 writeConcernMajorityJournalDefault 預設 true，所以 w: 'majority' 也會等 journal 寫進磁碟。（來源：MongoDB 官方文件 Write Concern 與 Rollbacks During Replica Set Failover 頁面。）
  • write concern 的選項名稱：mongodb 7.8.0 的型別裡，j 和 wtimeout 已標為 deprecated，改用 journal 和 wtimeoutMS；送到伺服器的命令裡還是 j、wtimeout。
  • withTransaction 的重試參數：看 driver 7.8.0 的原始碼，遇到 TransientTransactionError 會退避一小段時間（5 ms 起，最多 500 ms，帶隨機抖動）後重跑 fn，遇到 UnknownTransactionCommitResult 就重送 commit，總共最多重試 120 秒。
  • 交易裡的單一操作設了 write concern：官方文件寫明伺服器收到會回錯誤；mongodb 7.8.0 的 driver 則是在交易中直接不送出這個選項（實測），寫了也沒作用。
  • 其他讀取偏好：除了 primary、secondaryPreferred，還有 primaryPreferred（primary 不在時才讀 secondary）、secondary（只讀 secondary）、nearest（讀延遲最低的節點）。後三種同樣可能讀到舊資料。
  • 其他 read concern：另外還有 available（sharded cluster 上最快但最不保證）和 linearizable（只用在單一文件、讀 primary，成本高），一般業務很少用到。
  • findOneAndUpdate 的回傳值：mongodb 7.x 的 findOneAndUpdate 預設直接回傳文件（找不到時是 null），不是包一層結果物件。

練習

先啟動 MongoDB（在 learn/data-stores/practice 執行 docker compose --profile mongo up -d --wait），每一題都在 learn/ 執行 node check.mjs data-stores 09 判分。測試用資料庫 ds_t09，每個測試檔開始前會清空。集合由測試傳入，每個檔案最上面的註解寫了文件格式與規則。

練習 1：在 register.ts 實作 register(col, eventId, customerId)，不用交易，只對 col 呼叫一次 updateOne：名額大於 0 而且這位客人還沒報名，才把他加進 attendees、seatsLeft 減 1，回傳 true；其他情況（額滿、已報名、活動不存在）什麼都不改，回傳 false。測試會讓 200 個請求（150 位客人，其中 50 位按兩次）同時搶 50 個名額，而且每個操作都故意慢 30 ms，先讀再寫的寫法一定會超賣。

練習 2：在 transfer.ts 實作 transfer(client, db, customerId, fromId, toId)，用 session.withTransaction 把客人從活動 A 移到活動 B：從 A 移除並把 A 的名額加 1、加進 B 並把 B 的名額減 1、在 registrations 新增一筆 { customerId, from, to }。不在 A 裡丟 NotRegisteredError，B 沒名額丟 SeatsFullError，這兩種情況三個集合都要保持原樣。B 沒名額或客人已經在 B 裡都算 SeatsFullError；不論成功或丟錯都要 endSession()。測試會用 command monitoring（driver 每送出一個命令就發出一個 commandStarted 事件，測試收集起來看命令內容）檢查每個命令都在同一個交易裡，並讓 30 個移轉同時搶 B 的 20 個名額（會發生 WriteConflict），名額與人數都要守恆。

練習 3：在 concern.ts 替三種寫入填好 WRITE_CONCERNS：activityPageView（活動頁瀏覽計數）、registration（報名）、auditLog（稽核紀錄），規則寫在檔案的註解裡，要自己判斷每一種該用哪個等級。再實作 saveRegistration(db, reg)，把報名寫進 registrations 集合並使用對應的設定。測試會檢查 driver 實際送出的 insert 命令帶了什麼 write concern，也會暫時改動 WRITE_CONCERNS.registration，確認 saveRegistration 讀的是這份設定而不是另外寫死。

練習 4：在 optimistic.ts 實作 updatePromo(col, id, expectedVersion, patch)：文件的 version 還是 expectedVersion 才套用 patch 並把版本加 1，回傳更新後的文件；版本不符或文件不存在丟 VersionConflictError。patch 裡就算有 _id 或 version 也要忽略，而且不能改動傳進來的 patch 物件。測試會讓兩位編輯者同時拿第 3 版儲存，只能有一位成功。

練習 5：寫入用 w: 1 回應成功，接著 primary 當機、一台 secondary 被選為新的 primary。這筆寫入會怎樣？

✓ w: 1 只代表 primary 寫好了。還沒複製出去就當機，新 primary 上沒有這筆；舊 primary 重新加入時撤銷它，寫成 rollback 目錄裡的檔案，不會自動補回去（c 錯），也不會留兩份（d 錯）。要「回了成功就不會消失」，用 w: 'majority'。

練習 6：把名額和報名名單放在同一份活動文件裡，用一次 updateOne 帶條件 { seatsLeft: { $gt: 0 }, attendees: { $ne: id } } 扣名額並加入名單。還需要交易嗎？

✓ MongoDB 保證單一文件寫入的原子性，同一個更新裡改幾個欄位都一樣（a 錯）。並發的更新在這份文件上一個接一個執行，後到的看到條件不成立就不改，不會死結（c 錯）；文件大小跟原子性無關（d 錯）。交易留給真的跨文件的情況，因為它比單一文件寫入慢。

練習 7：下列哪一種資料，最不適合把 MongoDB 當主要資料庫？

✓ 高度關聯、需要外鍵與約束、幾乎每次寫入都跨好幾種資料，是關聯式資料庫的強項；放在 MongoDB 要靠程式和交易補，成本高。a、b、d 都以「一份文件」為單位讀寫，結構也因每筆而異，正是文件模型適合的地方。

練習 8：服務把讀取偏好設成 secondaryPreferred 後，客人剛報名完重新整理，卻看到「尚未報名」。最可能的原因是？

✓ secondary 是非同步複製，會落後 primary 一點點。使用者剛改過的資料要讀 primary，或在同一個因果一致 session 裡讀寫（搭配 majority）。a 的話報名當下就會看到錯誤；d 剛好相反，majority 是等多數節點寫好才回成功，不會讓寫入延後生效。

常見錯誤

  • 先 findOne 判斷，再 updateOne：中間會被插隊，並發時超賣。把判斷寫進 updateOne 的篩選條件，用 modifiedCount 看成功沒。
  • 什麼都包交易：先看能不能調整建模，讓需要一起成立的資料在同一份文件，用一次條件更新完成；交易留給真的跨文件的情況。
  • 為了快把 write concern 降到 w: 1 或 w: 0：故障切換時，已經回成功的寫入會被 rollback。不能丟的寫入明寫 w: 'majority'。
  • 從 secondary 讀取，卻期待讀到剛寫的資料：複製有延遲。剛改過的資料讀 primary，或用因果一致 session。
  • 交易裡的操作忘了傳 session：那個操作不在交易裡，失敗時不會回滾。每個 find、updateOne、insertOne 都要帶 { session }。
  • 在 withTransaction 的函式裡 catch 錯誤不往外丟：函式正常結束，交易就提交，前半段的修改留了下來。要中止就把錯誤丟出去。
  • 手寫 startTransaction／commitTransaction 卻沒有重試：並發寫入同一份文件會得到 WriteConflict。用 withTransaction，它會依錯誤標籤重試。
  • 交易函式裡寄信、呼叫外部 API：函式可能被重跑好幾次，副作用也會做好幾次；交易太久還會超過 60 秒被中止。外部動作放在交易成功之後。
  • 樂觀鎖的版本沒遞增，或讓 patch 改到 version：兩個人都能拿同一個版本存成功，等於沒檢查。只在更新函式裡 $inc 版本，patch 裡的 _id、version 拿掉。
  • 因為「比較彈性」就把訂單與金流搬到 MongoDB：彈性欄位用 PostgreSQL 的 JSONB 就有；關聯、約束、跨實體交易才是訂單真正需要的。

小結

  • 名額變成 53 人，是因為先讀再寫中間會被插隊。單一文件的寫入是原子的：把判斷寫進 updateOne 的篩選條件，用 modifiedCount 看成功沒，很多需求不需要交易。
  • 報名成功卻不見，是 w: 1 遇上故障切換：只有 primary 寫好就回成功，還沒複製出去就當機，舊 primary 回來時把它 rollback。w: 'majority' 等多數節點寫好才回成功，就不會消失；5.0 起大多數部署預設 majority，重要寫入仍要明寫。
  • 讀 secondary 可能讀到舊資料，剛寫的東西讀 primary 或用因果一致 session；read concern local 可能讀到之後被 rollback 的資料，majority 不會。
  • 跨文件時用 session.withTransaction：每個操作傳 session、錯誤往外丟、操作依序 await、函式裡沒有副作用；它會依 TransientTransactionError 重跑交易、依 UnknownTransactionCommitResult 重送 commit。
  • 交易有代價：預設 60 秒上限、MongoDB 9.0 起同時開啟數上限 10000、修改要放得進快取。
  • 長時間的編輯用版本欄位做樂觀並發控制：篩選帶 version、成功就 $inc，對不上就回衝突。
  • 高度關聯、約束多、需要臨時報表的資料（訂單、金流、庫存）留在 PostgreSQL；以文件為單位讀寫、結構多變的資料才是 MongoDB 的位置。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：門市活動頁要顯示營業時間、推薦商品（含品名與價格）、顧客評論。哪一種建模最合理？

✓ 建模看存取模式：一起讀、只屬於這份的內嵌；獨立變動的參照，需要時存當下的快照；會無限增加的放獨立集合。c 錯在 $slice 會把舊評論永久刪掉，評論是要保留的資料，不是只留最新幾筆的清單；價格也會在活動期間悄悄改變。（第 7 課）

練習 10：後台的「上傳照片」API 這樣寫。兩位店長同時上傳，同一時間還有人改營業時間，哪裡會出事？

const store = await stores.findOne({ _id: id })
store.photos.push(photo)
await stores.replaceOne({ _id: id }, store)

✓ 讀出、改、整份寫回，中間別人的修改都會被蓋掉（遺失更新）。改成 updateOne({ _id: id }, { $push: { photos: { $each: [photo], $slice: -20 } } })，由伺服器只改那個陣列。b 錯在原子性只保證一次寫入不會寫一半，擋不住「拿舊的整份去覆蓋」。（第 7 課）

練習 11：打卡計數用 updateOne({ storeId, date }, { $inc: { count: 1 } }, { upsert: true })，date 已經固定用台北時區。上線後偶爾出現同一家門市同一天有兩份文件、各記一半，原因是？

✓ upsert 的「找不到就新增」在並發時要靠篩選欄位上的唯一索引：第二個新增撞到重複鍵，伺服器會自動重試成更新，結果只有一份。a 更糟：沒有唯一索引照樣重複，有的話後到的直接收到 E11000。（第 7 課）

練習 12：查詢 find({ city: '台北', rating: { $gte: 4 } }).sort({ createdAt: -1 }).limit(20)。哪個索引能讓它只掃台北的索引項，而且不用在記憶體排序？

✓ ESR：等值 city 在前，排序 createdAt 接著，範圍 rating 最後；台北的索引項已經依時間排好，rating 在索引裡直接篩。a 照「條件寫的順序」排，範圍放在排序前面，符合的索引項依 rating 排而不是依時間，explain 會出現 SORT。c 沒有 SORT，但要走過每個城市的索引項。（第 8 課）

練習 13：限量 50 名的報名 API 這樣寫，壓力測試報名人數變成 53。哪裡出錯？

const ev = await events.findOne({ _id: eventId })
if (ev.seatsLeft > 0 && !ev.attendees.includes(customerId)) {
  await events.updateOne({ _id: eventId },
    { $inc: { seatsLeft: -1 }, $push: { attendees: customerId } })
  return true
}
return false

✓ 先讀再判斷，中間會被插隊。把條件搬進篩選：{ _id: eventId, seatsLeft: { $gt: 0 }, attendees: { $ne: customerId } }，用 modifiedCount 看成功沒，一次更新就做完，不需要交易。a 錯在單一文件的一次更新本來就是原子的，問題出在更新之前的那次讀取。（第 9 課）

練習 14：「換場次」用 withTransaction 包起來，並在函式最後寄確認信。活動開放換場那晚，有客人收到三封同樣的信，為什麼？

await session.withTransaction(async () => {
  await events.updateOne({ _id: from, … }, { … }, { session })
  await events.updateOne({ _id: to, … }, { … }, { session })
  await mailer.send(customer, '已換到新場次')
})

✓ 交易函式可能被重跑好幾次，副作用也會做好幾次。函式裡只放帶 { session } 的資料庫操作，寄信放在 withTransaction 回傳之後；一定要寄就在交易裡寫一筆待寄送紀錄（outbox）。c 錯在 UnknownTransactionCommitResult 只重送 commit，不重跑函式。（第 9 課）

練習 15：報名寫入用 { w: 'majority', wtimeoutMS: 5000 }，某次 API 收到 write concern 逾時的錯誤。這筆報名該怎麼看？

✓ 逾時只代表「等不到確認」，這筆可能已經寫進去。重試要冪等，例如用唯一索引擋重複報名。a 錯在逾時不會撤銷已寫入的資料，讓客人重報可能變成兩筆；c 回了成功，故障切換時卻可能被 rollback。（第 9 課）

練習 16：店長和行銷同時打開同一份活動文案，各自編輯幾分鐘後儲存，店長改的標題被行銷存的舊標題蓋回去。該怎麼防？

✓ 樂觀並發控制：版本還是我讀到的那個才更新，後到的找不到文件，前端提示「內容已被其他人修改」並重新載入。a 錯在編輯會開好幾分鐘，交易有 60 秒上限，不能撐那麼久；b 送的仍是她打開時看到的整份表單，標題照樣被蓋回去。（第 9 課）
