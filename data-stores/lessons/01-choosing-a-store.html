階段 1：選型的思路 · 第 1 課

為什麼不只用 PostgreSQL：從存取模式選資料儲存

咖啡店的後端到目前為止只有一個 PostgreSQL。週會上同事提了兩個建議：「訂單改放 MongoDB 比較彈性，以後加欄位不用 migration；購物車反正量不大，放 PostgreSQL 就好。」主管請你在下週的技術評審前回覆：咖啡店的每一種資料該放在哪裡，理由是什麼。

兩個建議聽起來都有道理，但其實都放錯了地方。要說服大家，你需要的不是「哪個資料庫比較紅」，而是一套能套在任何資料上、別人也能檢查的判斷步驟。這一課從頭到尾都在做這份回覆：先看出兩個建議錯在哪裡，再把判斷整理成四個問題，一步一步替咖啡店的六種資料做決定，最後寫成一年後的人也看得懂的紀錄。這套步驟也是後面 14 課的地圖：每一課都在回答「某一種資料該放哪裡、放過去要付什麼代價」。

這課的路線：
  1. 同事的兩個建議錯在哪：列出六種資料，寫下程式怎麼用它們，得到開場問題的最小答案。
  2. 四個問題：把剛才的直覺整理成存取模式、一致性、規模、維運成本，對每一份資料都問得出答案。
  3. PostgreSQL 能撐到哪、資料放兩個地方信哪一份：確認現有的資料庫做不到才加；加了之後分清記錄系統與衍生資料。
  4. 每種儲存用什麼換什麼、報表現在要不要換：看各種儲存的代價，再用估算決定還沒定的那幾格。
  5. 團隊扛得起嗎、怎麼寫下來：多一種資料庫的永久工作，以及把決定寫成 ADR。
這課會用到：
  • PostgreSQL 課第 14 課的 JSONB：把 JSON 存成一個欄位，可以查裡面的鍵、加 GIN 索引。
  • PostgreSQL 課第 28 課的全文檢索與 pg_trgm：用 GIN 倒排索引做關鍵字與模糊搜尋。
  • PostgreSQL 課第 33 課的 FOR UPDATE SKIP LOCKED 與 outbox：多個 worker 各自拿走沒被鎖的列，用一張表當工作佇列；要通知別的系統的事件，跟業務資料寫在同一個交易裡，之後再送出。
  • NestJS 課第 19 課的 Redis：資料放在記憶體的 key-value 資料庫，key 可以設 TTL，到期自動刪除。
這一課只有瀏覽器練習，不需要 Docker。

同事的兩個建議，錯在哪裡？

要判斷資料放哪裡，第一步不是挑資料庫，而是把要存的東西列出來，並寫清楚程式會怎麼用它。咖啡店的網站和 App 會產生這六種資料：

資料長什麼樣子程式怎麼用它
訂單（orders、order_items）一筆訂單幾個品項，每列幾百 bytes下單時寫入、依顧客或日期查、對帳
購物車每位顧客一份，幾個商品 id 和數量每次加減商品都改一次，結帳後就沒用
菜單搜尋商品名稱、描述、標籤顧客打「拿鐵 燕麥」找商品，結果依相關程度排序
電子收據檔每筆訂單一個 PDF，約 100～200 KB產生一次、之後整個檔案下載
營運報表每日營收、品項排行、尖峰時段店長每天看，查詢要掃過幾個月的訂單
門市活動內容每間門市的活動頁：標題、圖片、各種長短不一的區塊行銷人員編輯，前台整頁讀出

先只看「程式怎麼用它」這一欄，再回頭看同事的兩個建議。

訂單是錢。每一筆都要正確，不能因為伺服器當機就消失；也要跟顧客、商品對得起來：訂單上的 customer_id 必須是真的存在的顧客，一筆訂單和它的品項要一起寫進去，不能只寫進一半。這些保證，PostgreSQL 課教過的交易與外鍵直接就提供了，這正是關聯式資料庫最擅長的事。同事說 MongoDB「加欄位不用 migration」，解決的是訂單沒有的問題：訂單的欄位很固定，多年都不會大改；換過去反而要放棄或另外找方法取得訂單真正需要的保證（MongoDB 的關聯與交易怎麼做，第 9 課會講）。

購物車正好相反。顧客每加一次、減一次商品就要寫一次，結帳之後就沒用了；就算整份不見，顧客頂多重新加一次。它要的是每次讀寫都快，以及放著不結帳的購物車會自己消失。放進 PostgreSQL 也做得到，但它為訂單準備的那些保證，購物車用不到；而「到期自動刪除」PostgreSQL 沒有內建，要另外寫排程去清。Redis 的 key 可以直接設 TTL，剛好符合。

所以開場問題的最小答案是：訂單留在 PostgreSQL，購物車放 Redis。兩個建議犯的是同一個錯：從資料庫的特色出發（「MongoDB 比較彈性」「量不大放哪都行」），而不是從這份資料怎麼被使用出發。

「程式怎麼用它」這一欄有個正式的名字，叫存取模式。它是選型的第一個問題，但不是唯一一個：剛才判斷購物車時，其實還偷偷用了另外兩件事，「丟了可以接受」和「量不大」。這種直覺在訂單和購物車上很明顯，碰到剩下四種資料就沒那麼好判斷了。下一節把這些直覺整理成四個固定的問題，讓你對任何一份資料都能用同樣的方式問一遍。

怎麼對任何一份資料都問得出答案？四個問題

上一節對訂單和購物車的判斷，可以拆成四個問題。替任何一份資料挑儲存時，依序問這四個。

1. 存取模式（access pattern）：程式實際怎麼讀寫這份資料。重點不是「存什麼」，而是「怎麼拿」。同樣是商品資料，後台「依 id 改價格」和前台「打關鍵字找商品」是兩種完全不同的存取模式，適合的儲存也不同。常見的有五種：

  • 依 key 讀一筆：知道 id 就直接拿，例如「顧客 42 的購物車」。幾乎所有資料庫都做得好，Redis 這種記憶體 key-value 儲存最快。
  • 依範圍或條件查：「這位顧客最近 20 筆訂單」「昨天的訂單」，需要索引和排序，關聯式資料庫的強項。
  • 全文搜尋：依文字相關程度排序，要處理斷詞、同義詞、錯字，搜尋引擎的強項。
  • 掃描大量資料做統計：「過去一年每個月每個品項的營收」，一次讀幾千萬列但只用其中幾欄，分析型資料庫的強項。
  • 整個檔案讀寫：收據 PDF、商品照片，一次存、一次拿整份，不會只查其中一段，物件儲存的強項。

前兩種和「掃描大量資料做統計」的差別特別大，大到業界有專門的名詞。第一種叫 OLTP（online transaction processing，線上交易處理）：大量、小而短的讀寫，每次只碰幾列，但每秒有很多次，例如下單、改購物車。第二種叫 OLAP（online analytical processing，線上分析處理）：次數少，但每次要掃過大量資料，例如算年度營收。同一個資料庫很難兩種都做到最好，第 13 課會說明原因。之後看到「報表該不該離開 OLTP 資料庫」，講的就是這件事。

套回咖啡店：購物車是依 key 讀一筆；訂單是依範圍或條件查；菜單搜尋是全文搜尋；營運報表是掃描大量資料做統計；電子收據是整個檔案讀寫；門市活動內容是依門市整頁讀出，也算依 key 讀一筆，只是讀出來的是一大份結構不固定的內容。

2. 一致性：能不能丟、能不能舊。這裡問的是兩件事。第一件是「能不能丟」：資料寫進去之後，如果伺服器當機或重啟，可以接受它不見嗎？第二件是「能不能舊」：讀到的值比最新的晚幾秒、甚至晚一天，可以嗎？兩件事要分開問，因為同一份資料的答案常常不一樣。

咖啡店的答案：訂單兩個都不行，少一筆帳就對不起來，顧客付了錢卻看不到訂單。購物車可以丟，顧客重加就好。菜單搜尋可以舊 1 秒左右，新上架的商品晚一點才搜得到沒關係；這個數字來自 Elasticsearch 的行為，它寫入後預設最快約 1 秒才搜得到，第 10 課會看到。報表可以舊一天，店長看的本來就是昨天以前的數字。

這個問題決定了一份資料能不能放進「為了速度或功能放棄某些保證」的儲存。不能丟的資料，只能放在保證寫進去就不會消失、而且有人負責備份的地方；能丟或能舊的資料，選擇就多很多。

3. 規模：多大、多快。要三個數字：總筆數（或總容量）、每秒讀寫幾次、單筆多大。沒有數字，「量很大」「量不大」都只是感覺；同事那句「購物車反正量不大」就是一個沒有數字的判斷。咖啡店每天 2,000 筆訂單，三年下來 order_items 約 500 萬列，一台 PostgreSQL 輕鬆處理；同樣的表變成 50 億列，報表查詢才會開始痛。單筆大小也會改變答案：收據 PDF 每份 100～200 KB，比一列訂單大幾百倍，就算筆數不多，放進資料庫也會讓表和備份一起變大。這三個數字怎麼估，後面「用數字判斷」那一節會用程式算一次。

4. 維運成本（operational cost）：部署、備份、監控、升級、處理事故所花的人力與錢。資料庫不是裝好就沒事：要有人知道它怎麼備份、磁碟滿了怎麼辦、半夜出事誰會修。這一項常被忽略，卻往往是最後的決定因素：一個功能上最合適的儲存，如果團隊裡沒有人照顧得了，選了反而讓系統更脆弱。後面「團隊要多扛什麼」那一節會把這些工作一項一項列出來。

四個問題的順序有意義：先用存取模式和一致性找出「哪些儲存做得到」，再用規模判斷「現在需不需要」，最後用維運成本判斷「值不值得」。跳過前兩個直接比功能清單，就會變成「MongoDB 比較彈性」這種討論。
💡 實務上：選型討論先問數字，不先比功能
這種討論常出現在週會、技術評審，或有人貼了一篇「我們改用 X 之後快了 10 倍」的文章。資深工程師會先問：這份資料怎麼讀寫、丟了誰會受影響、現在多少筆、尖峰每秒幾次、誰來維護。答不出來的，先回去量。PM 關心的是「丟了顧客會不會抱怨」，維運關心的是「半夜誰被叫起來」，把這兩種人的問題帶進討論，結論通常會比只比功能清單穩。你下週的回覆，也應該照這四個問題的順序寫。

用這四個問題再看一次同事的建議：「訂單放 MongoDB 比較彈性」只回答了「加欄位方不方便」，沒有回答存取模式和一致性；「購物車量不大放 PostgreSQL」只回答了規模的一半，沒有問它要不要過期、能不能丟。不過問完前兩個問題，你會發現搜尋、報表、活動內容看起來都「需要另一種資料庫」。真的加之前，還有一件事要先確認。

這些需求，PostgreSQL 自己能撐到哪裡？

上一節留下的問題是：活動內容欄位不固定、菜單要搜尋、報表要掃大量資料，這些看起來都需要另一種資料庫。但很多這類需求，PostgreSQL 內建的功能就能處理，而且還保留了交易、外鍵和同一份備份。所以加新資料庫之前，先確認現有的做不到。

下面的表會用到三個還沒解釋的名詞，先講清楚：

  • 分片（sharding）：把一張表的資料依某個 key 切開，分散存在多台機器上，每台只放一部分。單台機器的磁碟或寫入量不夠時才需要它。
  • 分面統計（facet）：搜尋結果旁邊列出「咖啡 12 項、茶 5 項」這種依分類計數的統計，使用者點一下就能縮小範圍。
  • 唯讀副本（replica）：另一台持續複製主資料庫內容的機器，只能讀不能寫。把報表這種重的查詢導過去，就不會拖慢主資料庫上的下單（PostgreSQL 課第 37 課）。

下表是常見的需求、PostgreSQL 的做法，以及什麼時候才真的撐不住：

需求PostgreSQL 的做法什麼時候撐不住
欄位不固定的資料（活動頁區塊、商品規格）JSONB 欄位＋GIN 索引（第 14 課、第 28 課）整個應用都以巢狀文件為單位讀寫、幾乎不需要 JOIN，而且需要文件資料庫內建的分片
搜尋商品全文檢索 tsvector、模糊比對 pg_trgm（第 28 課）要中文斷詞、同義詞、錯字容忍、可調的相關性排序、分面統計，或搜尋流量大到拖慢主資料庫
背景工作佇列FOR UPDATE SKIP LOCKED、outbox（第 33 課）每秒上千個工作、需要延遲重試與優先順序的大量訊息，或多個服務要訂閱同一串事件
資料越來越多的表分割表（partitioning），依月份切開、舊分割整個刪（第 35 課）單一節點的磁碟或寫入量到頂，需要多台機器分擔寫入
報表調校查詢與索引（第 29 課）、物化檢視（第 23 課）、把報表查詢導到唯讀副本（第 37 課）每次要掃幾千萬列以上，調校後仍要幾十秒，或報表拖慢下單

讀這張表要看第三欄。它寫的幾乎都是可以量的條件（每秒幾個工作、掃幾千萬列、調校後仍要幾十秒），或是 PostgreSQL 內建功能做不好的事（中文斷詞、同義詞、錯字容忍）。還沒碰到第三欄之前，資料留在 PostgreSQL。另一種常見需求「向量相似度搜尋」也有 PostgreSQL 的做法，這門課不實作，細節見課末。

套回咖啡店那三種看起來需要新資料庫的資料：

  • 門市活動內容：區塊結構不固定，正是 JSONB 的用途，所以它不一定需要 MongoDB。咖啡店的活動頁也沒有大到需要分片。
  • 營運報表：還沒有證據顯示調校查詢不夠用。PostgreSQL 課第 23 課的物化檢視是把一個查詢的結果實際存成一張表，之後讀它不用每次重算，很適合「每天看一次」的報表。
  • 菜單搜尋：要中文斷詞和同義詞（顧客打「鮮奶」也要找到寫「牛奶」的商品），落在第三欄，是六種資料裡最有理由離開 PostgreSQL 的一個。

所以這門課的預設答案是 PostgreSQL，而加一個新儲存需要理由：存取模式 PostgreSQL 做不好，或量測證明它撐不住。這也是回覆同事第一個建議時最該講的一句：「沒有 schema 比較彈性」不是理由。資料總有結構，沒寫在資料庫裡，就是散在每一段讀它的程式裡，而且沒有東西幫你檢查。

不過菜單搜尋確實要搬出去，購物車也確實適合放 Redis。資料一旦放在兩個地方，就多了一個問題：兩邊對不起來的時候，該信哪一份？

資料放在兩個地方，對不起來時該信哪一份？

菜單搜尋放進 Elasticsearch 之後，商品資料就同時存在兩個地方：PostgreSQL 的 products 表，和搜尋引擎裡的索引。兩邊遲早會對不起來：同步晚了、同步程式有 bug、索引壞了。那時候要能立刻回答「哪一份是對的」，而這個答案要在選型時就決定好，不是事故當下才討論。選型裡最重要的觀念，就是把資料分成這兩種：

  • 記錄系統（system of record）：一份資料唯一的權威來源。兩個地方的數字對不起來時，以它為準。咖啡店的訂單，記錄系統是 PostgreSQL 的 orders 表。
  • 衍生資料（derived data）：從記錄系統算出來或複製出來的資料，例如快取、搜尋索引、報表、排行榜。它們可以整份丟掉，再從記錄系統重建。

這個區分決定了三件事：

  • 備份：記錄系統要完整備份、演練還原；衍生資料只要能重建，可以不備份或只做輕量備份。
  • 一致性：衍生資料晚幾秒、甚至錯了都能修，因為有權威來源可以對照。所以「搜尋結果跟資料庫不一致」是可以設計處理的問題（第 11 課），「訂單在兩個資料庫各有一半」不是。
  • 事故處理：Redis 被清空、搜尋索引壞掉時，有明確的重建步驟；如果沒人說得出哪一份是權威，事故當下就只能猜。

購物車是第三種情況：它不是衍生資料，因為它只存在 Redis，沒有來源可以重建；但它也可以接受遺失。這不是錯，但要在選型時寫下來並跟產品確認：「Redis 重啟時購物車會清空，顧客要重新加」。沒寫下來，事後就會變成一場「資料遺失事故」的爭論。這也是你回覆同事第二個建議時要補上的一句：購物車放 Redis 的前提，是大家都同意它可以丟。

💡 實務上：事故時第一個問題是「哪一份是對的」
客服回報「App 顯示的訂單金額跟收據不一樣」，或「搜尋得到已下架的商品」，第一步是去記錄系統（PostgreSQL）查，以它為準修正衍生資料。為了讓值班的人做得到，每個衍生資料都要有一份重建 runbook。runbook 是寫給值班的人、照著做就能處理事故的步驟文件（系統設計課第 21 課），重建 runbook 要寫清楚：從哪裡讀、要跑多久、重建期間使用者看到什麼。資深工程師在加 Redis 或搜尋引擎的同一個 PR，就會把「怎麼整份重建」一起寫好，而不是等出事才想。

到這裡，每一份資料都能標上「它是不是記錄系統、壞了從哪裡重建」。接下來要看候選的那幾種儲存，各自擅長什麼、又放棄了什麼。

每種儲存用什麼換什麼？

上一節把資料分成記錄系統與衍生資料，這一節把候選的儲存擺上來。同一個系統裡用多種資料儲存、各放適合的資料，這種做法叫多語言持久化（polyglot persistence）。這門課會教的儲存，每一種都擅長某些存取模式，也都為此放棄了一些東西。

表裡有三個名詞後面的課才會細講，這裡先知道意思就好。持久化是把記憶體裡的資料寫到磁碟，讓伺服器重啟後資料還在，Redis 可以設定（第 6 課）。限流計數是記錄每個人每分鐘呼叫了幾次 API、超過就擋下的計數器（第 3 課）。replica set 是 MongoDB 由多台互相複製的機器組成的部署方式（第 9 課）。

儲存擅長的存取模式代價與限制咖啡店拿來放課
PostgreSQL依條件查、JOIN、交易、約束單機寫入有上限；全文搜尋與大量統計不是最強訂單、顧客、商品PostgreSQL 課
Redis依 key 存取，資料在記憶體，單次操作通常在 1 毫秒內容量受記憶體限制；可以設定持久化，但選型時要把它當成可能遺失購物車、排行榜、限流計數第 2～6 課
MongoDB以一整份文件（巢狀 JSON）為單位讀寫跨文件的關聯要自己維護；一次改多份文件的交易，要部署成 replica set（或分片叢集）才能用門市活動頁內容第 7～9 課
Elasticsearch全文搜尋、相關性排序、分面統計寫入後約 1 秒才搜得到；不適合當記錄系統菜單搜尋第 10～11 課
物件儲存（S3）用 HTTP 整個檔案存取，單一物件最大約 50 TB，按容量計費很便宜不能查詢檔案內容、不能只改檔案的一部分電子收據 PDF第 12 課
DuckDB／ClickHouse掃大量資料、只讀幾欄做統計不適合大量的單筆更新與交易營運報表第 13 課
DynamoDB已知 key 的讀寫，加機器（水平擴展）幾乎沒有上限，由 AWS 代管只能照事先設計的 key 查；改需求很痛這間咖啡店用不到，第 14 課看大規模時的設計第 14 課

電子收據也在這張表裡定下來：收據 PDF 是整個檔案讀寫、每份 100～200 KB，放物件儲存，資料庫只存它的 key。

重點在「代價」那一欄：每個儲存都是用某些能力換來另一些。Redis 用容量和持久性換速度，Elasticsearch 用即時性和交易換搜尋能力，DynamoDB 用查詢彈性換擴展性。它們是 PostgreSQL 的補充，不是替代品。

「咖啡店拿來放」這一欄，是每種儲存最典型的用途，可以當成選型草稿。但對照前面「PostgreSQL 自己能撐到哪裡」那一節，有兩格還不能直接照抄：門市活動頁寫的是 MongoDB，可是 JSONB 也許就夠；營運報表寫的是 DuckDB／ClickHouse，可是咖啡店三年 500 萬列真的需要嗎？要定下這兩格，得回到第三個問題，用數字說話。

報表很慢，現在就要換分析型資料庫嗎？用數字判斷

店長抱怨報表慢，有人提議「上 ClickHouse」。這是第三個問題「規模」要回答的事，而且要用數字回答。下面用咖啡店的數字估算三年後 order_items 有多大，以及尖峰每秒寫幾列。

估算裡有一個係數要先說明：尖峰係數（peak factor）。一天的訂單不是平均分散在 24 小時，而是集中在早上上班前和午餐時間。尖峰係數就是「尖峰時每秒的量 ÷ 全天平均每秒的量」；平均值乘上它，才是系統最忙的時候要撐住的量。系統設計課第 2 課算過它的由來。

按「執行」，看印出的三行；再把 ordersPerDay 改成 20 萬（200_000）執行一次，比較兩次差多少：

結果是三年約 500 萬列、1 GB、尖峰每秒 1 列。這個量級整份放得進一台小主機的記憶體，報表慢一定是查詢寫法或索引的問題，該做的是先用 EXPLAIN 查（PostgreSQL 課第 21 課），不是換資料庫。每日訂單變成 20 萬，三年是 5 億列、100 GB，這時候分析型資料庫才值得討論。所以報表這一格先填 PostgreSQL，它仍是從訂單算出來的衍生資料，量長大了再搬。

這段估算有三個容易出錯的地方，每一個都會讓結論差一個數量級。第一，容量要無條件進位（Math.ceil）：估算是為了確認撐不撐得住，寧可多估不要少估。第二，單位一律寫清楚：bytes 還是 KB、天還是月，混用一次就差 1,024 倍或 30 倍。第三，尖峰係數一定要乘：系統出事都在尖峰，用全天平均挑主機規格，早上就會撐不住。

💡 實務上：估算寫進提案，量測寫進結論
估算用在提案階段：還沒寫程式前，判斷方向對不對、數量級差多少。真的要加新資料庫時，還要附上量測，常見的有三種：EXPLAIN ANALYZE 的結果，它會真的執行一次查詢，列出每一步花多久；正式環境的慢查詢紀錄，PostgreSQL 可以設定把執行超過指定時間的查詢寫進 log；尖峰時段的 CPU 與連線數。估算的假設也要寫出來（例如「尖峰係數 6 是看了上個月的流量圖」），別人才能挑戰你的數字，而不是挑戰你的結論。你給主管的回覆裡，報表那一格就該附上這段估算。

報表這一格靠數字定下來了。活動內容那一格不一樣：放 MongoDB 或 PostgreSQL 的 JSONB 功能上都做得到，量也都不大。剩下的差別，要靠第四個問題：多一套資料庫，團隊要付出什麼。

多一種資料庫，團隊要多扛什麼？

功能和數字都分不出高下時，決定答案的是維運成本。每加一種資料儲存，團隊就多了這些工作，而且是永久的：

  • 備份與還原：它怎麼備份？多久演練一次還原？
  • 監控與告警：記憶體、磁碟、延遲、連線數的指標與告警門檻。
  • 升級與資安修補：主版本升級、安全性修正、client 套件的相容性。
  • 連線與設定：本機、測試、正式環境各一套；密碼與網路權限。
  • 資料同步：衍生資料怎麼跟記錄系統保持一致、不一致時怎麼修（第 11、15 課）。
  • 值班知識：半夜它出事，值班的人知道怎麼看、怎麼處理嗎？

這份清單不會因為資料量小就變短。三位工程師的團隊同時維護 PostgreSQL、Redis、MongoDB、Elasticsearch，等於每個人都要懂四種東西的故障。所以小團隊的原則是：證明 PostgreSQL 不夠才加，而且加的時候先問「這份資料可以只當衍生資料嗎」。衍生資料壞了能重建，備份可以從簡，事故時也有固定的處理方式，維運壓力小很多。

套回咖啡店最後兩個還在猶豫的決定：

  • 門市活動內容：為它多維運一套 MongoDB，換來的只是 JSONB 已經能做的事，所以放 PostgreSQL 的 JSONB 欄位。如果哪天整個應用都改成以文件為單位讀寫，再重新評估。
  • 菜單搜尋：確實需要 Elasticsearch，維運成本要付；但它是衍生資料，壞了能從 products 整份重建，這筆代價付得起。

六種資料的決定都有了。最後一步是把決定和理由寫下來：一年後有人看到系統裡多了一套 Elasticsearch，要知道它為什麼在那裡、什麼情況下可以拿掉。

怎麼把決定寫下來，讓一年後的人看得懂？

程式碼只看得出系統現在長什麼樣子，看不出為什麼長這樣。一年後的人看到三種資料庫，要嘛不敢動，要嘛在不知道原因的情況下把其中一個拿掉，然後重新踩一次當初避開的坑。解決這個問題的文件叫架構決策紀錄（architecture decision record），通常簡稱 ADR：一個決定寫一份，記下當時的需求、考慮過的選項、選了哪個、付出什麼代價，以及什麼情況下該重新評估。完整寫法在系統設計課第 18 課。

六個決定裡，菜單搜尋是唯一真的多加一套儲存的，最需要寫 ADR。下面是它的 ADR：

# ADR-007：菜單搜尋改用 Elasticsearch

狀態：已採用（2026-11）
需求數字：商品 300 項、尖峰搜尋 50 次/秒；需要中文斷詞與同義詞（「鮮奶」=「牛奶」）
選項：
  A. PostgreSQL 全文檢索＋pg_trgm：零新增維運；中文斷詞要自己處理
  B. Elasticsearch：內建 cjk 分析器（中文兩字一組切詞）、同義詞、相關性調整；多一個要維運的叢集
決定：B。記錄系統仍是 PostgreSQL 的 products，搜尋索引是衍生資料，可整份重建
代價：寫入後約 1 秒才搜得到；需要同步機制（outbox）與重建 runbook
何時重新評估：搜尋需求退回只要前綴比對，或維運人力不足時改回 A

這份 ADR 的每一行，都對應這課走過的一步：

  • 需求數字是存取模式和規模：要全文搜尋、多少商品、尖峰每秒幾次。
  • 選項 A 是「PostgreSQL 自己能撐到哪裡」那一步：先寫出不加新儲存的做法，以及它做不好的地方。
  • 決定寫明記錄系統與衍生資料：誰是權威、索引壞了從哪裡重建。
  • 代價是一致性與維運成本：接受舊 1 秒，並承擔同步與重建的工作。
  • 何時重新評估讓決定可以被推翻：條件改變時，後來的人知道可以改回 A，不必從頭爭論。

回到週會。你給主管的回覆，就是把這課走過的步驟寫出來：六種資料各自的存取模式與能不能丟；訂單留在 PostgreSQL，因為它是要交易與外鍵的記錄系統；購物車放 Redis，並寫明重啟會清空、產品同意；收據 PDF 放物件儲存；活動內容用 JSONB、報表先調校查詢，附上估算；只有菜單搜尋加 Elasticsearch，附上這份 ADR。練習會讓你把這些判斷親手寫成程式。

向量相似度搜尋：pgvector

向量相似度搜尋是把文字轉成一串數字（向量），再找意思最接近的商品，例如顧客打「不苦的咖啡」也能找到描述裡沒有這幾個字的商品。PostgreSQL 的做法是 pgvector 擴充，這門課只提到，不實作。它撐不住的時候，是向量數量與查詢量大到單機記憶體放不下索引。

練習

三題都在瀏覽器裡寫 TypeScript。第 1 題把這課的判斷寫成規則，第 2 題做估算，第 3 題替咖啡店做完整的選型。

練習 1：團隊把選型規則整理成下表。實作 classifyAccess(need)，由上往下檢查，第一條符合的規則決定答案：

順序條件回傳
1單筆大小 sizeBytes 超過 FILE_BYTES（102,400）'object-storage'
2durability 是 'must-not-lose'（記錄系統）'postgres'
3lookup 是 'full-text''search'
4lookup 是 'scan-aggregate'，而且總筆數 rows 超過 OLAP_ROWS（5,000 萬）'olap'
5lookup 是 'by-key'，而且每秒讀寫合計 reads + writes 超過 HOT_OPS（1,000）'redis'
6其他'postgres'

「超過」不含等於。name 只是說明用，不能拿來判斷；測試會用沒看過的名稱和數字。

練習 2：把上面「用數字判斷」的估算寫成函式。estimate(load) 回傳：

  • rowsPerDay：每天新增的 order_items 列數 = 每日訂單 × 平均品項數，無條件進位成整數
  • rowsTotal：rowsPerDay × 保留天數
  • bytesTotal：rowsTotal × 每列 bytes，單位是 bytes
  • writesPerSecPeak：rowsPerDay ÷ 86,400 × 尖峰係數，無條件進位

再寫 needsSeparateOlap(est)：rowsTotal 超過 5,000 萬，或 bytesTotal 超過 50,000,000,000（50 GB）時回傳 true，否則 false。「超過」不含等於。

練習 3：替咖啡店的六種資料各寫一筆決定，填進 decisions。每一筆寫出放在哪個儲存（store）、是不是記錄系統（systemOfRecord）、一句理由（why，至少 5 個字）。衍生資料或可接受遺失的資料（systemOfRecord: false）一定要寫 rebuildFrom：從哪裡重建（例如 'postgres'），沒有來源、丟了就沒了的寫 'none'；記錄系統不寫 rebuildFrom。照這課的原則判斷，有些資料不只一個合理答案，測試會接受。

練習 4：同事說「MongoDB 沒有 schema，所以改需求比較快，訂單改放 MongoDB 吧」。最需要先問哪個問題？

✓ b。選型先看存取模式與一致性：訂單要交易、要跟顧客與商品對得起來、不能丟。「沒有 schema」只是把 schema 搬到程式碼裡；真的有不固定的欄位，JSONB 就能存，而且保留交易與外鍵。a 的速度和 c 的熟悉度是在確認「做得到」之後才比較的次要因素；d 跟需求無關。

練習 5：Redis 重啟後，所有顧客的購物車都清空了。這算不算資料遺失事故？

✓ b。Redis 可以設定持久化，也可以不設；重點是事先決定這份資料能不能丟、丟了誰受影響，並寫進 ADR。a 太絕對，Redis 很適合放可以遺失或可以重建的資料；c 把「Redis 就是快取」當定律，會漏掉 session、限流計數這些不是快取、丟了會有影響的用途；d 的物件儲存不適合每次加減商品都要改的小資料。

練習 6：團隊有 3 位工程師，每天 2,000 筆訂單，店長抱怨月報表要跑 20 秒。最先做什麼？

✓ c。每天 2,000 筆，三年約 500 萬列，這個量級跑 20 秒幾乎一定是查詢或索引的問題。a 會多一套要備份、監控、同步、值班的系統，3 個人的團隊負擔很重，而且分析型資料庫要到數千萬、數億列的掃描才明顯有優勢；b 搬資料庫解決不了查詢寫法的問題；d 繞過問題，也讓店長看不到當天的數字。

常見錯誤

  • 從資料庫的特色出發，而不是從資料怎麼被使用出發：「MongoDB 比較彈性」「量不大放哪都行」都跳過了存取模式。先寫出程式怎麼讀寫這份資料，再挑儲存。
  • 因為「大公司在用」或履歷好看而加新資料庫：大公司的規模和人力跟你不同。先用四個問題和估算證明需要，再加。
  • 沒有分清楚記錄系統與衍生資料：事故時兩份數字對不起來，沒人知道該信哪一份。每份資料都寫下記錄系統是誰、衍生資料從哪裡重建。
  • 只比較功能，不算維運成本：功能清單上都打勾，但備份、升級、監控、值班的人力沒算進去。把這些工作列出來，確認誰負責。
  • 把 Redis、MongoDB 當成 PostgreSQL 的替代品：它們是補充，各自用某些能力換另一些。訂單這種要交易、要約束的資料留在 PostgreSQL。
  • 可以遺失的資料沒有事先說好：購物車放 Redis 沒問題，但要寫下「重啟會清空」並讓產品知道，否則每次重啟都是一場爭論。
  • 估算單位或進位錯：天當成月、bytes 當成 KB、四捨五入少估、忘了乘尖峰係數，結論就差一個數量級。
  • 沒有把選型理由寫下來：一年後沒人知道為什麼有三種資料庫，也不知道什麼時候可以拿掉。寫 ADR，包含需求數字和「何時重新評估」。

小結

  • 選型從資料怎麼被使用出發，不從資料庫的特色出發：先列出每份資料，寫下程式怎麼讀寫它。
  • 替資料挑儲存時依序問四個問題：存取模式、一致性（能不能丟、能不能舊）、規模（筆數、每秒讀寫、單筆大小）、維運成本。前兩個找出做得到的儲存，規模判斷現在需不需要，維運成本判斷值不值得。
  • PostgreSQL 是預設答案：JSONB、全文檢索、SKIP LOCKED、分割表、物化檢視與唯讀副本已經涵蓋很多需求（向量搜尋的 pgvector 見課末）；加新儲存要有存取模式或量測上的理由。
  • 每份資料只有一個記錄系統；快取、搜尋索引、報表、排行榜是衍生資料，要能從記錄系統重建。只存在一處又可以遺失的資料（購物車）要事先說好。
  • Redis 換速度、Elasticsearch 換搜尋、物件儲存換便宜的大容量、分析型資料庫換掃描速度、DynamoDB 換擴展性，每一個都有代價。
  • 用估算判斷「現在需不需要」：容量無條件進位、單位寫清楚、乘上尖峰係數。咖啡店三年約 500 萬列，報表慢先查查詢與索引。
  • 每多一種資料庫，就多一份備份、監控、升級、同步與值班的工作；決定和理由寫成 ADR，包含需求數字、選項、代價與何時重新評估。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 5 件事。先在心裡回答，再選。

練習 7：Redis 的人氣排行顯示燕麥拿鐵本週賣了 520 杯，店長用 PostgreSQL 的訂單算出來是 488 杯。該怎麼處理？

✓ 訂單的記錄系統是 PostgreSQL，排行是從它衍生的資料；對不起來時以記錄系統為準，照重建 runbook 從訂單重算。衍生資料錯了能修，正是因為有權威來源可以對照。b 最危險：拿衍生資料回頭改記錄系統，等於憑空多出 32 杯的營收。（第 1 課）

練習 8：為了省掉 PostgreSQL 到 Elasticsearch 的同步，同事提議商品資料只寫進 Elasticsearch，不再寫 products 表。哪裡會出事？

✓ Elasticsearch 不適合當記錄系統。搜尋索引當衍生資料，壞了能從 products 整份重建；拿掉 products，索引一壞商品資料就沒有來源。做法是記錄系統留在 PostgreSQL，用 outbox 同步、寫好重建 runbook。b 錯在約 1 秒的延遲是選型時就接受的代價，菜單搜尋舊 1 秒沒關係。（第 1 課）

練習 9：同事看到 DynamoDB「加機器幾乎沒有上限」，提議把訂單搬過去。店長每個月都會提新的報表條件（依門市、依品項、依時段），這個提議最大的問題是？

✓ DynamoDB 用查詢彈性換擴展性：只能照事先設計的 key 查，店長每提一個新條件就要改設計，改需求很痛。每天 2,000 筆也遠用不到它的擴展性，訂單留在 PostgreSQL。a 把它說反了：DynamoDB 由 AWS 代管，問題不在維運，在查詢。（第 1 課）

練習 10：替每天 5 萬筆訂單的連鎖店估算寫入量，同事照下面的結果，用「每秒 2 列」去挑主機規格。哪裡會出事？

const ordersPerDay = 50_000
const itemsPerOrder = 2.4
const rowsPerDay = Math.ceil(ordersPerDay * itemsPerOrder)
const writesPerSec = Math.ceil(rowsPerDay / 86_400)
console.log('每秒寫入', writesPerSec, '列')  // 2

✓ 每秒 2 列是把寫入平均攤在 24 小時，實際集中在尖峰；要乘尖峰係數（尖峰每秒 ÷ 平均每秒），系統出事都在尖峰。a 錯在估算本來就要無條件進位，寧可多估不要少估。（第 1 課）

練習 11：新功能要在下單後寄確認信，尖峰約每分鐘 60 封。3 位工程師的團隊，這個工作佇列該放哪裡？

✓ 每分鐘 60 個工作遠在 PostgreSQL 撐得住的範圍，SKIP LOCKED 加 outbox 就夠，還保留交易和同一份備份。每多一種儲存，就永久多一份備份、監控、升級與值班的工作；要到每秒上千個工作、需要延遲重試與優先順序，或多個服務訂閱同一串事件才值得。a 錯在為了還沒發生的流量先付維運成本，加新儲存要有量測上的理由。（第 1 課）
