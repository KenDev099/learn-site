替資料挑儲存先問存取模式、一致性、規模、維運成本。PostgreSQL 是預設答案，加新儲存要有存取模式或量測上的理由；每份資料只有一個記錄系統。[回 資料儲存選型 學習地圖](../index.html)

## A 咖啡店的六種資料 {span=2}
| 資料 | 長什麼樣子 | 程式怎麼用它 |
|---|---|---|
| 訂單 | 一筆訂單幾個品項，每列幾百 bytes | 下單時寫入、依顧客或日期查、對帳 |
| 購物車 | 每位顧客一份，幾個商品 id 和數量 | 每次加減商品都改一次，結帳後就沒用 |
| 菜單搜尋 | 商品名稱、描述、標籤 | 打「拿鐵 燕麥」找商品，依相關程度排序 |
| 電子收據檔 | 每筆訂單一個 PDF，約 100～200 KB | 產生一次、之後整個檔案下載 |
| 營運報表 | 每日營收、品項排行、尖峰時段 | 查詢要掃過幾個月的訂單 |
| 門市活動內容 | 標題、圖片、長短不一的區塊 | 行銷人員編輯，前台整頁讀出 |

同事提議「訂單改放 MongoDB 比較彈性、購物車放 PostgreSQL」：寫出「程式怎麼用它」就站不住。訂單是錢，要正確、不能丟、要跟顧客和商品對得起來；購物車要的是快和自動過期。

## B 四個問題的順序
```flow TB
[存取模式] & [一致性：能不能丟、能不能舊] -> [哪些儲存做得到]
[哪些儲存做得到] -> [規模：筆數、每秒讀寫、單筆大小]
[規模：筆數、每秒讀寫、單筆大小] -> [現在需不需要]
[現在需不需要] -> [維運成本]
[維運成本] -> *[值不值得]
```
跳過前兩個直接比功能清單，就會變成「MongoDB 比較彈性」這種討論。OLTP 是大量小而短的讀寫，OLAP 是次數少、每次掃很多資料的統計。

## C PostgreSQL 先撐多遠 {span=2}
| 需求 | PostgreSQL 的做法 | 什麼時候撐不住 |
|---|---|---|
| 欄位不固定 | JSONB＋GIN 索引 | 整個應用以巢狀文件為單位讀寫、幾乎不 JOIN，又需要內建分片 |
| 搜尋商品 | tsvector、pg_trgm | 要中文斷詞、同義詞、錯字容忍、可調排序、分面統計，或搜尋拖慢主資料庫 |
| 背景工作佇列 | `FOR UPDATE SKIP LOCKED`、outbox | 每秒上千個工作、延遲重試與優先順序，或多個服務訂閱同一串事件 |
| 越來越大的表 | 分割表，依月份切、舊分割整個刪 | 單一節點的磁碟或寫入量到頂 |
| 報表 | 調校查詢與索引、物化檢視、唯讀副本 | 每次掃幾千萬列以上，調校後仍要幾十秒，或拖慢下單 |
| 向量相似度搜尋 | pgvector（這門課只提到） | 單機記憶體放不下索引 |

「沒有 schema 比較彈性」不是理由：資料總有結構，沒寫在資料庫裡，就散在每一段讀它的程式裡。

## D 記錄系統與衍生資料
```flow LR
*[(PostgreSQL orders)] -> 快取 & 搜尋索引 & 報表 & 排行榜: 可整份重建
```
| 影響 | 記錄系統 | 衍生資料 |
|---|---|---|
| 備份 | 完整備份、演練還原 | 能重建就不備份或輕量備份 |
| 一致性 | 權威來源，以它為準 | 晚幾秒、錯了都能修 |
| 事故 | 先查它 | 照重建 runbook 處理 |

```callout warn 可以遺失的資料要事先說好
購物車只在 Redis、沒有來源可重建。這不是錯，但要寫下「Redis 重啟時購物車會清空」並跟產品確認。
```

## E 每種儲存換到什麼、付出什麼 {span=3}
| 儲存 | 擅長 | 代價與限制 | 咖啡店拿來放 | 課 |
|---|---|---|---|---|
| PostgreSQL | 依條件查、JOIN、交易、約束 | 單機寫入有上限；全文搜尋與大量統計不是最強 | 訂單、顧客、商品 | PostgreSQL 課 |
| Redis | 依 key 存取，資料在記憶體 | 容量受記憶體限制；選型時當成可能遺失 | 購物車、排行榜、限流計數 | 第 2～6 課 |
| MongoDB | 以整份巢狀文件為單位讀寫 | 跨文件關聯自己維護；多文件交易要 replica set 或分片叢集 | 門市活動頁內容 | 第 7～9 課 |
| Elasticsearch | 全文搜尋、相關性排序、分面統計 | 寫入後約 1 秒才搜得到；不適合當記錄系統 | 菜單搜尋 | 第 10～11 課 |
| 物件儲存（S3） | 用 HTTP 整個檔案存取，按容量計費便宜 | 不能查詢內容、不能只改一部分 | 電子收據 PDF | 第 12 課 |
| DuckDB／ClickHouse | 掃大量資料、只讀幾欄做統計 | 不適合大量單筆更新與交易 | 營運報表 | 第 13 課 |
| DynamoDB | 已知 key 的讀寫，水平擴展，AWS 代管 | 只能照事先設計的 key 查；改需求很痛 | 咖啡店用不到 | 第 14 課 |

它們是 PostgreSQL 的補充，不是替代品。

## F 用估算判斷「現在需不需要」
```kv cols=1
容量: 無條件進位（Math.ceil），寧可多估
單位: bytes 還是 KB、天還是月，一律寫清楚
尖峰係數: 尖峰每秒 ÷ 平均每秒，一定要乘
```
這課的示範：每天 2,000 筆訂單，三年約 500 萬列、1 GB、尖峰每秒 1 列，報表慢先用 EXPLAIN 查；每日訂單變 20 萬，三年 5 億列、100 GB，分析型資料庫才值得討論。提案用估算，加新資料庫還要附 EXPLAIN ANALYZE、慢查詢紀錄、尖峰 CPU 與連線數。

## G 多一種資料庫的代價與 ADR {span=2}
- 每加一種儲存就永久多出：備份與還原、監控與告警、升級與資安修補、各環境的連線與設定、資料同步、值班知識。
- 小團隊的原則：證明 PostgreSQL 不夠才加；加的時候先問「這份資料可以只當衍生資料嗎」。
- 決定寫成 ADR：需求數字、選項、決定、代價、何時重新評估。

```callout info ADR 範例：菜單搜尋改用 Elasticsearch
選 Elasticsearch 是為了 cjk 分析器、同義詞與相關性調整；記錄系統仍是 PostgreSQL 的 products，搜尋索引是衍生資料，可整份重建。代價是約 1 秒才搜得到，要有 outbox 同步與重建 runbook。
```
