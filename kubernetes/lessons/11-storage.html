階段 4：資料、安全與打包 · 第 11 課

儲存與有狀態服務：PVC、StatefulSet，以及資料庫為什麼放 RDS

到目前為止，cafe-api 的每個 Pod 都可以隨時丟掉：刪掉一個，Deployment 建一個新的，什麼都沒少。這是因為它沒有自己的資料，訂單只放記憶體。可是咖啡店總有要留下來的東西：收據檔案、資料庫、上傳的照片。把它們寫在 Pod 裡，下一次換版、節點維護、Pod 被驅逐，資料就跟著消失。

這一課讓資料活過 Pod，並做一個資深工程師常被問的判斷：正式環境的資料庫要不要放進 Kubernetes。

這課的路線：
  1. 資料放在哪裡會不見：寫在容器裡、emptyDir、PVC 的檔案，各活到什麼時候。
  2. PVC 與 StorageClass、Deployment 掛一顆 RWO 磁碟：怎麼向叢集要一塊持久的磁碟，掛上之後為什麼只能 1 個副本、換版要先關舊的。
  3. StatefulSet：資料庫這類每個副本各有一份資料的服務，怎麼拿到固定的名字和自己的磁碟。
  4. 正式環境的資料庫要不要放叢集、ExternalName：咖啡店為什麼選 RDS，應用怎麼用固定的名稱 db 連外部資料庫。
  5. 暫存資料：處理完就不要的檔案放 emptyDir，並讓根目錄唯讀，被入侵時攻擊者改不了程式。
這課會用到：
  • devops 課第 18 課的 AWS 儲存：RDS 是代管的資料庫，EBS 是掛在 EC2 上的雲端磁碟、綁在一個可用區（AZ），S3 是不用掛載、用 SDK 存取的物件儲存。
  • 第 4 課的 headless Service：clusterIP: None 的 Service 沒有虛擬 IP，DNS 直接回每個 Pod 的 IP。
  • 第 9 課的滾動更新：Deployment 換版時先建新 Pod、等它準備好再關舊 Pod。

資料放在哪裡會不見

容器裡的程式寫檔案時，檔案落在哪裡，決定了它能活多久。Kubernetes 裡有三個層級：

  • 容器自己的檔案系統（可寫層，writable layer）：映像上面多疊的一層，寫進去的東西只屬於「這一次啟動的容器」。容器崩潰被 kubelet 重啟時，是用映像重新建一個容器，可寫層是新的，舊的檔案就沒了。
  • emptyDir：Pod 層級的暫存空間。Pod 排到節點上時建立一個空資料夾，Pod 裡的容器都可以掛載它；容器重啟時資料還在，Pod 刪除時資料夾跟著刪除。
  • PersistentVolume（PV）：叢集裡的一塊儲存，例如雲端磁碟、NFS，或 kind 節點上的一個目錄。它的生命週期跟 Pod 無關：Pod 刪了，新的 Pod 掛上同一個 PV，資料都在。

在叢集裡親手看一次。cafe-api 的 POST /receipts 會把收據寫成 /data/<id>.json，GET /receipts 列出 /data 裡的收據。先用練習 1 的起始檔（/data 是 emptyDir）：

node check.mjs kubernetes 11          # 第一次執行：把起始檔複製到 kubernetes/practice/work/11/
export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"
kubectl create namespace try-11
kubectl apply -n try-11 -f kubernetes/practice/work/11/ex1/deployment.yaml
kubectl exec -n try-11 deploy/cafe-api -- wget -qO- --post-data='{"total":110}' \
  --header='content-type: application/json' 127.0.0.1:3000/receipts
kubectl exec -n try-11 deploy/cafe-api -- wget -qO- 127.0.0.1:3000/receipts     # 看得到一張
kubectl delete pod -n try-11 -l app.kubernetes.io/name=cafe-api
kubectl exec -n try-11 deploy/cafe-api -- wget -qO- 127.0.0.1:3000/receipts     # []：收據不見了

（容器裡用 127.0.0.1 而不寫 localhost：映像裡的 localhost 會先解析成 IPv6 的 ::1，cafe-api 只聽 IPv4。）emptyDir 對「Pod 刪除」無能為力。要讓收據活下來，就要一塊不屬於 Pod 的儲存。

PVC 與 StorageClass：向叢集要一塊磁碟

Pod 不直接指定「用哪一顆 EBS 磁碟」，而是提出申請：

  • PersistentVolumeClaim（PVC）：Pod 對儲存的申請單，寫要多大、怎麼存取。Pod 的 volume 寫 persistentVolumeClaim.claimName 引用它。PVC 屬於 namespace。
  • StorageClass：「怎麼動態建立 PV」的設定。PVC 沒有對應的 PV 時，StorageClass 指定的外掛會自動建一個（叫動態佈建，dynamic provisioning）。PV 與 StorageClass 都是整個叢集共用的物件。
  • CSI（Container Storage Interface）：儲存外掛的標準介面。EKS 上建 EBS 磁碟的是 EBS CSI driver，建 EFS 的是 EFS CSI driver；Kubernetes 本身不認識任何雲端磁碟，靠這些外掛。
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: receipts-data
spec:
  accessModes: [ReadWriteOnce]     # 存取方式，下面說明
  resources:
    requests:
      storage: 1Gi                 # 要多大
  # 沒寫 storageClassName：用叢集標成 (default) 的那個

課程叢集的 StorageClass：

$ kubectl get storageclass
NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false

kind 預設安裝 local-path-provisioner：它的「磁碟」就是某個節點上的一個目錄。把 PVC 套用上去，你會看到它停在 Pending，Events 寫著在等第一個使用者：這就是 volumeBindingMode: WaitForFirstConsumer，PVC 要等到有 Pod 用它、而且排程器決定好 Pod 去哪個節點之後，才在那個節點（雲端上是那個可用區）建立磁碟。如果一建 PVC 就馬上建磁碟（Immediate），磁碟可能落在 a 區，Pod 卻因為 CPU 不夠只能排到 b 區，永遠掛不上。Pod 出現後 PVC 變成 Bound，綁定到一個自動建立的 PV：

$ kubectl get pvc -n try-11
NAME            STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS
receipts-data   Bound    pvc-3f1c…                                  1Gi        RWO            standard

綁定之後，磁碟的位置就固定了。local-path 的 PV 帶有節點親和性（node affinity）：之後這個 PVC 的 Pod 只能排到那個節點，節點壞了 Pod 就起不來。EKS 的 EBS 也一樣，只是範圍是可用區：一顆 EBS 磁碟只存在於一個可用區，Pod 不能搬到別的可用區。你的 3 個副本分散在 3 個可用區（第 9 課），但掛 EBS 的那個 Pod 只能待在磁碟那一區。

access mode：誰可以同時掛

存取方式意思常見的儲存
ReadWriteOnce（RWO）同一時間只能掛在一個節點上讀寫（同節點的多個 Pod 仍然可以一起掛）EBS、local-path，大部分區塊儲存
ReadWriteOncePod（RWOP）只有一個 Pod 能掛，連同節點的第二個 Pod 都不行要 CSI driver 支援
ReadWriteMany（RWX）多個節點同時讀寫EFS、NFS 這類網路檔案系統
ReadOnlyMany（ROX）多個節點同時唯讀預先放好資料的磁碟

一般的雲端磁碟都是 RWO。需要「很多 Pod 讀同一批檔案」時，先想的應該是物件儲存（S3），而不是 RWX：S3 不用掛載、沒有可用區限制，應用用 SDK 讀寫就好。

reclaim policy：PVC 刪掉之後

PV 的 persistentVolumeReclaimPolicy 決定 PVC 被刪除後磁碟怎麼處理。動態建立的 PV 沿用 StorageClass 的 reclaimPolicy，沒寫就是 Delete：PVC 一刪，PV 和底下的磁碟一起刪除。Retain 會保留 PV 與磁碟，要人工清理或接回去。kubectl delete namespace 會刪掉裡面所有 PVC，搭配 Delete 就是資料全部消失。Retain 只是多一層保護，真正能救回資料的是備份。

💡 實務上：看到 PVC，先問備份與還原
code review 或接手服務時看到一個 PVC，資深會先問三個問題：這份資料壞了或被誤刪，最多能接受掉多少（RPO）？備份在哪裡、多久做一次？上一次真的還原是什麼時候？最常見的事故不是磁碟壞掉，而是有人清理環境時 kubectl delete namespace 刪錯了，或 helm uninstall 把 chart 建立的 PVC 一起刪掉。正式環境的 StorageClass 可以設 reclaimPolicy: Retain 多一層保護，但沒演練過還原的備份等於沒有備份（devops 課第 24 課）。

Deployment 掛一顆 RWO 磁碟：只能 1 個副本，用 Recreate

把練習 1 的 /data 改成掛 PVC 後，資料活過了 Pod。但 Deployment 的兩個預設行為會跟 RWO 磁碟打架：

  • 多個副本：所有副本引用的是同一個 PVC。排到別的節點的 Pod 掛不上，停在 ContainerCreating（EBS 的 Events 是 Multi-Attach error for volume … Volume is already used by pod(s)）；剛好在同一個節點的 Pod 掛得上，但兩個程式同時寫同一份資料，誰也不知道對方存在。
  • 滾動更新（RollingUpdate）：先建新 Pod、等它 Ready 再關舊的。新 Pod 要等舊 Pod 放開磁碟，舊 Pod 要等新 Pod Ready 才關，換版就卡住。

所以一個 Deployment 掛一顆 RWO 磁碟時：replicas: 1，strategy.type: Recreate（先關掉舊 Pod，再建新的）。代價是換版時有幾秒沒有服務，也只能有一個副本。這適合內部的小工具；面對顧客的服務要多副本、不停機，就應該讓它不在本機存狀態：檔案放 S3、資料放資料庫。

💡 實務上：從 Compose 搬上 Kubernetes，先盤點應用寫了哪些檔案
典型的情況：原本 docker-compose 裡有一行 ./uploads:/app/uploads（devops 課第 10 課的 volume），搬到 Kubernetes 時直接換成 PVC，結果服務只能跑 1 個副本、換版會中斷，HPA 也開不了。寫 manifest 之前，先列出應用會寫到哪些路徑、每一份要活多久：使用者上傳的照片、產生的 PDF 改存 S3，session 改放 Redis，暫存檔放 emptyDir。這份清單通常會變成一兩個改程式的 PR，跟 PM 說明時可以講成「先讓服務能多開幾台」。改完之後真的需要 PVC 的，多半只剩資料庫這類有狀態服務，而它們在正式環境要不要放叢集，本課後面會談。

StatefulSet：每個 Pod 有自己的名字和自己的磁碟

有些服務的每個副本本來就各有一份資料，而且彼此要能點名找到對方：資料庫的主節點與複本、Kafka、Elasticsearch。StatefulSet 是給這種有狀態服務的控制器，它跟 Deployment 的差別：

DeploymentStatefulSet
Pod 名稱隨機：cafe-api-7d9f…-x2k4p，重建就換固定編號：pg-0、pg-1，重建後還是 pg-0
DNS只有 Service 的名稱搭配 headless Service，每個 Pod 有自己的名稱：pg-0.pg
磁碟所有副本共用 Pod 範本寫的同一個 PVCvolumeClaimTemplates 替每個 Pod 建自己的 PVC：data-pg-0、data-pg-1
啟動與關閉同時預設依序：pg-0 Ready 才建 pg-1；縮減時從編號最大的開始關
Pod 重建後新名字、新身分同一個名字，掛回同一個 PVC

開發用的 PostgreSQL 寫成 StatefulSet（練習 2 的答案就是這個形狀）：

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: pg
spec:
  serviceName: pg                  # 負責 DNS 的 headless Service
  replicas: 1
  selector:
    matchLabels: {app.kubernetes.io/name: pg}
  template:
    metadata:
      labels: {app.kubernetes.io/name: pg}
    spec:
      containers:
        - name: postgres
          image: postgres:18.6-alpine3.24
          …                        # 環境變數、readinessProbe（pg_isready）、resources
          volumeMounts:
            - name: data           # 名稱對應下面的 volumeClaimTemplates
              mountPath: /var/lib/postgresql
  volumeClaimTemplates:            # 每個 Pod 一個 PVC，名稱是 <範本名稱>-<Pod 名稱>
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 1Gi
---
apiVersion: v1
kind: Service
metadata:
  name: pg
spec:
  clusterIP: None                  # headless：DNS 直接回 Pod 的 IP，並建 pg-0.pg 這種名稱
  selector: {app.kubernetes.io/name: pg}
  ports:
    - port: 5432

第 4 課說過，headless Service 沒有虛擬 IP，DNS 查詢直接回 Pod 的 IP。StatefulSet 的 serviceName 指向它之後，每個 Pod 還會多一個自己的名稱：pg-0.pg（完整是 pg-0.pg.<namespace>.svc.cluster.local）。要連「主節點」就連 pg-0.pg，不會被負載平衡分到複本去。

postgres 18 的資料目錄換位置了：17 以前官方映像的 PGDATA 是 /var/lib/postgresql/data；18 起改成 /var/lib/postgresql/18/docker（跟 Debian 的 pg_ctlcluster 一致，以後升級大版本用 pg_upgrade --link 比較方便），映像宣告的 VOLUME 也改成 /var/lib/postgresql。照舊教學把 volume 掛在 /var/lib/postgresql/data，18 的入口腳本會偵測到並報錯結束。磁碟掛在 /var/lib/postgresql。另外，Kubernetes 不會替映像的 VOLUME 建匿名 volume：沒掛 PVC 時資料寫在容器可寫層，容器一重啟就沒了。

兩個常被誤會的行為：

  • 刪除 StatefulSet 不會刪 PVC。persistentVolumeClaimRetentionPolicy 的 whenDeleted 與 whenScaled 預設都是 Retain，縮減副本或刪掉 StatefulSet 後，data-pg-0 留著，重新建立時會接回去。要清掉資料就自己刪 PVC。
  • StatefulSet 不會複寫資料。replicas: 3 只是三個各自有空磁碟的 PostgreSQL，誰是主節點、怎麼串流複寫、主節點掛了誰接手，Kubernetes 全都不知道。這些是資料庫自己的事，也是下一節的重點。

正式環境的資料庫要不要放叢集

會寫 StatefulSet 之後，下一個問題是：咖啡店正式環境的 PostgreSQL，要自己在 EKS 裡跑，還是用 RDS？先列出「讓資料庫可以上線」要做的事（PostgreSQL 課第 37 課、devops 課第 24 課），再看誰來做：

工作RDS（ElastiCache 對 Redis 類似）叢集裡自己跑（StatefulSet）
每日備份、保留期限自動備份，設定保留天數自己寫備份 Job、放到 S3、監控它有沒有成功
還原到某個時間點（PITR）保留期內任意時間點還原自己保存 WAL、自己練習還原
主節點故障Multi-AZ 自動切換到另一個可用區的備援自己設串流複寫與切換機制；EBS 綁可用區，那一區掛了 Pod 也搬不走
小版本升級、安全修補維護時段自動套用自己換映像、自己測試
磁碟擴充、監控主控台調整，內建 CloudWatch 指標自己擴 PVC、自己裝 exporter 與告警
節點維護不影響drain 節點時資料庫 Pod 要搬家：PDB、停機時間、可用區限制（第 9 課）
成本RDS 的費用比自己開同規格的 EC2 高機器便宜，但上面每一列都是人力與風險

咖啡店的決定：正式環境用 RDS for PostgreSQL（Multi-AZ）和 ElastiCache for Redis，叢集只跑無狀態的應用。理由是團隊沒有專職的資料庫管理員，「備份從沒還原過」「主節點掛了要半夜手動切換」的風險，比 RDS 多出的費用貴得多；人力應該花在產品上。這個決定要寫下來，並寫明何時重新評估：例如資料庫費用大到可以養一個專職人員、或要用 RDS 不支援的擴充套件時。

如果真的要在叢集裡跑正式資料庫，不要自己從 StatefulSet 寫起，而是用 operator：把維運知識寫成控制器的程式，例如 PostgreSQL 的 CloudNativePG，你寫一個 Cluster 物件，它幫你建複本、做故障切換、排程備份到 S3。operator 讓自管容易很多，但不會讓你不需要懂 PostgreSQL 維運：還原演練、升級、出事時判斷該不該切換，還是你的工作。

本課程的 postgres StatefulSet（練習 2）與第 10 課的 postgres，都只給開發與測試用：資料壞了就重建，沒有人在乎。

固定名稱連外部資料庫：ExternalName

資料庫在叢集外，應用的 DATABASE_URL 要寫 RDS 的端點，例如 cafe.c9xxxx.ap-northeast-1.rds.amazonaws.com。直接寫進每個 Deployment 的話，staging 與正式環境的值不同、換資料庫要改每一個用到它的服務。讓應用永遠連一個叢集內的固定名稱 db:5432，由 Service 決定 db 指到哪裡：

apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  type: ExternalName
  externalName: cafe.c9xxxx.ap-northeast-1.rds.amazonaws.com

ExternalName Service 不選 Pod、沒有虛擬 IP、不轉送任何流量，它只讓叢集的 DNS 對 db 回答一筆 CNAME（「這個名字其實是那個名字」），應用再去查那個名字的 IP。所以：

  • 不寫 selector，也不需要 ports（應用自己連 5432）。
  • externalName 一定要寫 DNS 名稱。寫 IP 的話，它會被當成「由數字組成的名稱」做 CNAME，查不到。只有 IP 時，用沒有 selector 的一般 Service，再手寫一個 EndpointSlice（label kubernetes.io/service-name: db、addresses 寫那個 IP）。
  • 叢集內的服務也可以當目標，例如另一個 namespace 的 ext-pg.k8s-11-ex3-ext.svc.cluster.local（練習 3 用它假裝成 RDS）。
  • 換資料庫（RDS 從快照還原成新的執行個體、搬到另一個區域）時，只改 Service db。DNS 結果會被快取、已經開著的連線不會自己換，所以改完後 kubectl rollout restart 讓應用重新連線。
TLS 與主機名稱：RDS 的憑證上寫的是 RDS 的端點名稱。應用連 db 並要求驗證主機名稱（PostgreSQL 的 sslmode=verify-full）時，它比對的是連線字串裡的 db，跟憑證不符，連線會被拒絕；HTTPS 也有一樣的問題（官方文件因此提醒 ExternalName 用在 HTTP、HTTPS 要小心）。正式環境要求 verify-full 時，常見的做法是把真正的端點放在每個環境各自的 ConfigMap 或 Secret（第 6 課），而不是用 ExternalName 改名。ExternalName 適合不驗證主機名稱的連線，以及開發、測試環境。

暫存資料：emptyDir、sizeLimit 與唯讀根目錄

不是所有檔案都要持久。上傳的照片在轉存到 S3 之前、產生報表的中間檔、快取，處理完就不要了：這些放 emptyDir。兩個設定一定要知道：

  • sizeLimit：emptyDir 預設用節點的磁碟，沒有上限。一個失控的上傳可以寫滿節點磁碟，同節點的每個 Pod 都受影響。設了 sizeLimit: 64Mi，kubelet 定期量用量，超過就驅逐整個 Pod（Events 的 reason 是 Evicted，訊息是 Usage of EmptyDir volume "tmp" exceeds the limit "64Mi"），Deployment 再建新的。
  • medium: Memory：改用記憶體（tmpfs），比磁碟快，但寫進去的檔案算在容器的記憶體用量裡，會讓容器更接近 limit 而被 OOMKilled（第 8 課）。只放小而需要快的東西。

emptyDir 的另一個用途是安全：readOnlyRootFilesystem。容器的 securityContext.readOnlyRootFilesystem: true 讓整個根目錄唯讀，被入侵時攻擊者沒辦法改程式、下載工具到容器裡。程式真的需要寫的目錄（通常是 /tmp）再掛 emptyDir：

    spec:
      containers:
        - name: api
          securityContext:
            readOnlyRootFilesystem: true
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir:
            sizeLimit: 64Mi

這樣「哪裡可以寫、最多寫多少」都寫在 manifest 裡，一眼看得出來。第 12 課的 Pod Security 會把唯讀根目錄列入檢查清單。長期要留的檔案（收據 PDF、顧客上傳的照片）放 S3，不放 PVC：S3 不綁節點與可用區，多副本可以一起用。

練習

在 learn 資料夾執行頁面上的指令，起始檔會複製到 kubernetes/practice/work/11/。每一題先做靜態檢查，通過了才套用到叢集的專屬 namespace（k8s-11-ex1 這種名字），需要的 Secret 由測試用隨機值建立，最後刪掉 namespace（包括裡面的 PVC）。叢集很忙時一題要幾分鐘。前面的 try-11 用完記得 kubectl delete namespace try-11。

練習 1：收據要活過 Pod。在 ex1/pvc.yaml 寫 PersistentVolumeClaim receipts-data（1Gi、ReadWriteOnce，用預設的 StorageClass），把 ex1/deployment.yaml 的 /data 從 emptyDir 改成掛這個 PVC，並把更新策略改成適合單一 RWO 磁碟的那一種，副本維持 1。測試套用後確認 PVC 是 Bound，POST 一張收據、刪掉 Pod，新的 Pod 用 GET /receipts 還要看得到它。

練習 2：開發用的 PostgreSQL。ex2/pg.yaml 現在是 Deployment 加一個手寫的 PVC，而且磁碟掛在舊版的路徑。把它改成 StatefulSet pg：serviceName: pg、1 個副本、用名為 data 的 volumeClaimTemplates（ReadWriteOnce、1Gi）取代手寫的 PVC，掛在 postgres 18 該掛的位置；容器的設定（映像、密碼來自 Secret pg-admin、pg_isready 的 readinessProbe）不變。ex2/service.yaml 改成 headless。測試會用 psql -h pg-0.pg 帶密碼連進去寫一筆資料，刪掉 pg-0 後確認新的 pg-0 還讀得到，最後刪掉 StatefulSet，確認 PVC data-pg-0 還在。

練習 3：namespace k8s-11-ex3-ext 裡有一個假裝是 RDS 的 PostgreSQL，Service 叫 ext-pg（測試會建立）。在 ex3/service.yaml 寫 ExternalName Service db，指到 ext-pg 的完整 DNS 名稱；把 ex3/deployment.yaml 裡 DATABASE_URL 的主機改成 db。cafe-api 的 /health/ready 會用 TCP 檢查資料庫連不連得上。測試確認它是 200 之後，把 db 改指到另一個 namespace（k8s-11-ex3-new）的資料庫、刪掉舊的那個，再 rollout restart：應用設定一行都不改，要照樣 Ready。

練習 4：ex4/deployment.yaml 的 cafe-api 已經設了 readOnlyRootFilesystem: true，結果 POST /uploads 要把暫存檔寫到 /tmp 時回 500。只用 emptyDir（sizeLimit: 64Mi）讓上傳恢復，不能關掉唯讀。測試會確認上傳回 200、寫 /app/x 仍然因唯讀失敗，接著在 /tmp 寫入 80MB，等 Pod 因超過 sizeLimit 被驅逐（約一分鐘）。

練習 5：一個 Deployment 有 3 個副本，Pod 範本都掛同一個 ReadWriteOnce 的 PVC，會發生什麼事？

✓ RWO 限制的是節點，不是 Pod 數，所以會同時出現「掛不上」和「同節點一起寫」兩種問題。Kubernetes 不會複製資料（c），access mode 也不會自己改（d）。每個副本要各自一份資料，用 StatefulSet 的 volumeClaimTemplates；要共享，用 RWX 儲存（EFS）或物件儲存（S3）；只要一份，就 1 個副本加 Recreate。

練習 6：咖啡店要在 EKS 上線，團隊 4 個人、沒有專職的資料庫管理員。正式環境的 PostgreSQL 最合理的預設是？

✓ 自己跑資料庫要負責備份與還原演練、複寫與故障切換、升級、節點維護，人力與風險通常比 RDS 多出的費用貴。a 的「便宜」沒算人力；c 在 Pod 刪除時資料全部消失；d 重建得了 Pod，但 EBS 綁在一個可用區，那一區出事就搬不走，也沒有備份與故障切換。

練習 7：用預設 StorageClass 動態建立的 PVC 被刪除（例如有人刪了整個 namespace），資料還在嗎？

✓ PV 雖然是叢集層級，但 reclaim policy 是 Delete 時，PVC 一刪它就跟著刪（a 錯）。Pod 只是使用者，跟 PVC 刪除後的處理無關（b）。Retain 可以保留磁碟（d 錯），但真正能保護資料的是備份與還原演練。

常見錯誤

  • 把資料庫當成一般服務放進叢集：StatefulSet 只給你固定名稱和磁碟，備份、還原演練、複寫與故障切換都要自己做。沒有這些就是在賭；正式環境預設用 RDS／ElastiCache。
  • 以為 PVC 會跟著 Pod 跨可用區：EBS 綁一個可用區、local-path 綁一個節點，Pod 只能排到磁碟所在的地方。要跨可用區的高可用，靠資料庫自己的複寫（RDS Multi-AZ），不是靠磁碟。
  • 刪 namespace 順手刪掉 PVC：reclaim policy 是 Delete 時資料跟著消失。正式資料要有備份；StatefulSet 的 PVC 刪除前先確認裡面是什麼。
  • 多副本 Deployment 掛 RWO 磁碟：不是卡在 ContainerCreating 就是同時寫壞資料。用 StatefulSet、改成 1 個副本加 Recreate，或讓服務不在本機存狀態。
  • postgres 18 的 volume 掛在 /var/lib/postgresql/data：18 的 PGDATA 是 /var/lib/postgresql/18/docker，入口腳本會報錯結束。掛在 /var/lib/postgresql。
  • ExternalName 寫 IP、或加了 selector：externalName 只接受 DNS 名稱；selector 對它沒有作用。只有 IP 時用沒有 selector 的 Service 加 EndpointSlice。
  • 暫存檔寫在容器檔案系統：容器重啟就沒了，也讓根目錄不能設成唯讀。用 emptyDir 並設 sizeLimit。

小結

  • 資料的壽命：容器可寫層到容器重啟為止，emptyDir 到 Pod 刪除為止，PV 活過 Pod。
  • Pod 用 PVC 申請儲存，StorageClass 動態建立 PV（雲端上透過 CSI driver）。WaitForFirstConsumer 讓磁碟建在 Pod 所在的節點／可用區；綁定後 Pod 只能待在那裡。
  • access mode 限制的是節點：雲端磁碟多半是 RWO，RWX 要 EFS 這類網路檔案系統，多副本共享檔案優先用 S3。reclaim policy 預設 Delete，PVC 刪了磁碟就沒了。
  • 一個 Deployment 掛一顆 RWO 磁碟：1 個副本、Recreate。每個副本各自一份資料、需要固定名稱：StatefulSet（固定的 pg-0、headless Service 給的 pg-0.pg、volumeClaimTemplates、依序啟動，刪除時預設保留 PVC）。
  • 正式資料庫預設用 RDS／ElastiCache，用錢換備份、PITR、Multi-AZ 與升級的人力；要自管就用 operator，而且仍要懂資料庫維運。叢集內的 postgres 只給開發與測試。
  • 應用連固定名稱 db，用 ExternalName（CNAME）或無 selector 的 Service＋EndpointSlice 指到外部；要驗證 TLS 主機名稱時，改由每個環境的設定提供真正的端點。
  • 暫存檔放 emptyDir 並設 sizeLimit，搭配 readOnlyRootFilesystem 讓其他地方都不能寫；長期檔案放 S3。
