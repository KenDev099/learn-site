階段 2：網路與設定 · 第 4 課

Service 與叢集內 DNS：用名字找到會變動的 Pod

上一課的 cafe-api 已經有 3 個副本，壞了會自己補回來。可是還沒有人連得到它：點餐前端、收據 worker 要呼叫 API 時，網址該寫什麼？Pod 有 IP，但 Pod 隨時會被重建，IP 跟著變，而且一次有 3 個。

這一課學 Service：給一群 Pod 一個固定的名字和固定的 IP，連線自動分給後面準備好的 Pod。

這課的路線：
  1. Pod IP 為什麼不能直接用、Service：Pod 會重建、IP 會變，一次還有 3 個，網址該寫成 Service 的名字（開場問題的最小答案）。
  2. port、targetPort 與叢集內 DNS：Service 的兩個 port 各是誰的，跨 namespace 呼叫別的服務時名字怎麼寫。
  3. Service 的類型：只給叢集內用、從節點進來、還是請雲端開一台負載平衡器；本機怎麼從 Mac 連進叢集。
  4. 長連線與負載平衡：為什麼三個副本一個很忙、兩個很閒，用連線池和 gRPC 的服務都會遇到。
  5. Service 沒有流量：照固定順序排查，值班時不用亂猜。
這課會用到：
  • 第 3 課的 Deployment 與 selector：Deployment 維持 N 個 Pod，用 selector 挑出帶有特定 label 的 Pod 認作自己的。
  • devops 課第 4 課的網路基礎：IP 加 port 找到一個程序，DNS 把名字查成 IP，TCP 連線建立後會一直用到關閉。
  • 第 1 課的練習叢集：下面的指令都假設你已經在 learn 資料夾執行過 export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"。

Pod IP 為什麼不能直接用

每個 Pod 都會分到一個叢集內的 IP（kind 裡是 10.244.x.x）。-o wide 會多印出 IP 和所在節點：

kubectl get pods -n demo -o wide
NAME                       READY   STATUS    IP           NODE
cafe-api-549b54d94-6ghn2   1/1     Running   10.244.1.9   learn-k8s-worker
cafe-api-549b54d94-vncjq   1/1     Running   10.244.2.7   learn-k8s-worker2

kubectl delete pod -n demo cafe-api-549b54d94-6ghn2
kubectl get pods -n demo -o wide
NAME                       READY   STATUS    IP            NODE
cafe-api-549b54d94-qz8kd   1/1     Running   10.244.1.12   learn-k8s-worker     ← 補回來的新 Pod，IP 不一樣
cafe-api-549b54d94-vncjq   1/1     Running   10.244.2.7    learn-k8s-worker2

把 10.244.1.9 寫進前端的設定會出三個問題：

  • IP 會變：Pod 被刪、節點當機、部署新版本，新 Pod 都拿到新的 IP（第 3 課的自我修復就是建新 Pod，不是修舊的）。
  • 有好幾份：3 個副本要連哪一個？呼叫端得自己記住全部的 IP、自己輪流、自己避開壞掉的。
  • 不知道誰準備好了：剛啟動、還沒開始聽 port 的 Pod 也有 IP。

devops 課第 12 課用 nginx 的 upstream 解決過同樣的問題：呼叫端只認 nginx，nginx 知道後面有哪些副本。Kubernetes 把這件事做成內建的物件，叫 Service。

Service：固定的名字、固定的 IP

Service 是「一群 Pod 的穩定入口」。它有三個部分：

  • selector：用 label 挑出後面是哪些 Pod，跟第 3 課 Deployment 的 selector 是同一種寫法。
  • ClusterIP：建立 Service 時分到的虛擬 IP（kind 裡是 10.96.x.x），Service 存在一天就不會變。只在叢集內連得到，這也是預設的 Service 類型名稱。
  • 名字：叢集的 DNS 伺服器會替每個 Service 建立一筆紀錄，cafe-api 這個名字查出來就是它的 ClusterIP。

最小的 Service：

apiVersion: v1
kind: Service
metadata:
  name: cafe-api            # 這就是 DNS 名稱
spec:
  selector:                 # 挑出 label 完全符合的 Pod
    app.kubernetes.io/name: cafe-api
    app.kubernetes.io/instance: main
  ports:
    - name: http
      port: 80              # 呼叫端連的 port
      targetPort: http      # 轉到 Pod 的哪個 port（下一節）

Service 本身不是一個程序，也沒有容器在「代理」流量。它背後是兩個元件合作：

  • EndpointSlice：記錄「這個 Service 現在後面有哪些 Pod IP、port、是否 Ready」的物件。控制平面裡的控制器一直盯著 Pod，Pod 增加、刪除、Ready 狀態改變，它就更新 EndpointSlice。這是第 1 課控制迴圈的又一個例子。
  • kube-proxy：每個節點上都有一份（第 1 課的元件圖），它讀 EndpointSlice，把「連到 ClusterIP:80 的封包改送到某個 Pod IP:3000」寫成節點的 Linux 轉送規則（iptables 或 nftables；這門課的 kind 叢集用 iptables，kubectl get configmap kube-proxy -n kube-system -o yaml 裡的 mode 看得到）。

所以 Service 只是一筆設定，壞不了也不會變慢；能不能連通取決於 EndpointSlice 裡有沒有東西、規則寫得對不對。後面排查的順序就是照這張圖走。

EndpointSlice 只放 Ready 的 Pod 收流量：Pod 的容器起來了但還沒準備好，就不該收流量。「準備好」由 readiness probe 判斷，第 7 課教。這一課的 Pod 沒有寫 probe，容器一啟動就算 Ready。Service 本身不做健康檢查，它只看 Pod 的 Ready 狀態。

port、targetPort 與具名 port

一個 Service 的 port 有兩個數字，很多人第一次寫會搞混：

欄位是誰的 portcafe-api 的值
portService（ClusterIP）的 port，呼叫端連這個80，所以網址寫 http://cafe-api 就好
targetPortPod 裡容器真正在聽的 port3000（cafe-api 的程式聽 3000）
containerPort（在 Deployment）容器宣告自己聽哪個 port，可以取名字name: http、containerPort: 3000

targetPort 可以寫數字，也可以寫容器 port 的名字。寫名字時，Deployment 要先替 port 取名：

# Deployment 的容器
containers:
  - name: api
    image: learn-k8s/cafe-api:v1
    ports:
      - name: http            # 名字最多 15 個字元，小寫英數與 -
        containerPort: 3000

# Service
ports:
  - port: 80
    targetPort: http          # 找容器上叫 http 的 port

具名的好處：哪天 cafe-api 改聽 8080，只改 Deployment 的 containerPort，Service 不用動；滾動更新期間新舊 Pod 的 port 不同也照樣能轉。containerPort 本身不會開 port 也不會擋 port（程式聽哪個就是哪個），它是給人和 Service 看的說明，名字寫了才有 targetPort 可以參照。

省略 targetPort 時，它預設等於 port。寫了 port: 80 卻沒寫 targetPort，流量就會送到 Pod 的 80，而 cafe-api 沒在聽 80，連線被拒。

叢集內 DNS：用名字連線

叢集裡有一個 DNS 伺服器 CoreDNS（在 kube-system，它自己的 Service 叫 kube-dns，ClusterIP 是 10.96.0.10）。每建一個 Service，它就能回答這個 Service 的名字。完整的名稱是：

<service 名稱>.<namespace>.svc.cluster.local
cafe-api.k8s-04-ex1.svc.cluster.local

平常不用寫這麼長，因為 kubelet 替每個 Pod 寫好了 /etc/resolv.conf。看 k8s-tools 裡 probe Pod 的：

kubectl exec -n k8s-tools deploy/probe -- cat /etc/resolv.conf
search k8s-tools.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
  • search：名字不完整時，依序在後面補上這些尾巴再查。第一個是 Pod 自己的 namespace。
  • ndots:5：名字裡的點少於 5 個，就先試 search 的尾巴，最後才把它當完整名稱查。

於是同一個名字，在不同 namespace 的 Pod 裡查到的結果不同：

在 namespace shop 的 Pod 裡寫補完後查到結果
cafe-apicafe-api.shop.svc.cluster.local只找得到 shop 裡的 cafe-api
menu.catalogmenu.catalog.svc.cluster.local（第二個尾巴）namespace catalog 的 menu
menu.catalog.svc.cluster.local同上完整名稱，在哪裡查都一樣

規則：同一個 namespace 寫短名稱，跨 namespace 一定要寫 <service>.<namespace>。只寫 menu 在別的 namespace 會查不到，Node 的 fetch 會丟 ENOTFOUND。設定檔裡也絕不寫 ClusterIP 或 Pod IP：Service 刪掉重建，ClusterIP 就換了。

自己查查看（第 3 課的 Deployment 加上一個 Service 之後）：

kubectl exec -n k8s-tools deploy/probe -- getent hosts cafe-api.demo
10.96.67.173      cafe-api.demo.svc.cluster.local  cafe-api.demo
kubectl exec -n k8s-tools deploy/probe -- curl -s http://cafe-api.demo/version
{"version":"v1","instance":"cafe-api-549b54d94-vncjq"}
nslookup 不一定會用 search：probe 和 busybox 映像裡的 nslookup 是 BusyBox 的版本，它不套用 search 的尾巴，所以 nslookup cafe-api.demo 會回 NXDOMAIN，看起來像 DNS 壞了。用 nslookup 時給完整名稱 cafe-api.demo.svc.cluster.local，或改用 getent hosts，它跟你的程式一樣走系統的解析流程。

ndots:5 的代價：程式呼叫外部網域 api.stripe.com（只有 2 個點）時，會先依序查 api.stripe.com.shop.svc.cluster.local 等三個不存在的名字，最後才查真正的網域，多了幾次 DNS 往返。在網域最後加一個點（api.stripe.com.）代表「這已經是完整名稱」，就不會先試 search。大部分服務不需要理會；DNS 查詢量大到 CoreDNS 吃緊時，平台團隊才會調這些設定。了解即可。

💡 實務上：服務網址寫進設定，不寫死在程式裡
呼叫別的服務的網址應該放在設定裡（第 6 課的 ConfigMap），例如 MENU_URL=http://menu.catalog。常見的事故是：開發時兩個服務在同一個 namespace，程式裡寫短名稱 menu 一切正常；到了 staging，menu 由另一個團隊部署在 catalog namespace，上線就變成 ENOTFOUND。跨團隊呼叫一律寫 <service>.<namespace>，並且先跟對方確認這組名稱會不會變：對方改 Service 名稱或搬 namespace，對你來說就等於改了 API。

Service 的類型：誰連得到

spec.type 決定 Service 從哪裡連得到：

類型做了什麼什麼時候用
ClusterIP（預設）只有叢集內部連得到的虛擬 IP＋DNS 名稱服務之間互相呼叫。絕大多數 Service 都是這種
NodePortClusterIP 之外，在每個節點開同一個 port（預設範圍 30000–32767）轉進來很少直接用：port 號不好記，要知道節點 IP；通常是給外部負載平衡器接的底層機制
LoadBalancerNodePort 之外，再請雲端建立一台外部負載平衡器指進來，位址寫在 EXTERNAL-IP非 HTTP 的協定、或少數要直接對外的服務
headless（clusterIP: None）沒有 ClusterIP；DNS 直接回傳每個 Ready Pod 的 IP呼叫端要自己挑 Pod 的情況，例如資料庫叢集的成員（第 11 課的 StatefulSet）
ExternalName沒有 selector 也沒有 IP；DNS 回一筆 CNAME 指到外部主機讓程式用叢集內的固定名稱連外部服務，例如第 11 課用它指到 RDS

三種主要類型是一層包一層：LoadBalancer 也有 NodePort，NodePort 也有 ClusterIP。kubectl get svc 的 PORT(S) 欄位會顯示 80:30451/TCP，冒號後面就是自動分配的 NodePort。

LoadBalancer 在本機怎麼運作：雲端上，建立 LoadBalancer Service 會由雲端的控制器建一台真的負載平衡器（在 EKS 上由 AWS Load Balancer Controller 建一台 NLB，按小時計費）。kind 沒有雲端，這門課用第 1 課裝的 cloud-provider-kind 代替：它看到 LoadBalancer Service，就啟動一個 kindccm-… 的 Envoy 容器當負載平衡器，填好 EXTERNAL-IP。Mac 連不到 kind 的 Docker 網路，所以它把 Envoy 的 80 port 對應到 Mac 上一個隨機的 port。bin/url.mjs 幫你查出這個 port：

kubectl get svc -n demo cafe-api
NAME       TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
cafe-api   LoadBalancer   10.96.214.169   172.26.0.7    80:30451/TCP   36s

node kubernetes/practice/bin/url.mjs demo cafe-api
http://localhost:60629
curl -s http://localhost:60629/version
{"version":"v1","instance":"cafe-api-549b54d94-6ghn2"}

EXTERNAL-IP 剛出現時，Envoy 可能還要幾十秒才接上 Pod，這段時間 curl 會收到 Empty reply from server，等一下再試即可。Service 刪掉重建，Envoy 容器也重建，Mac 上的 port 會換一個，所以腳本裡絕不寫死 port。

💡 實務上：對外的 HTTP 服務共用一個入口
在雲端，每個 LoadBalancer Service 都是一台要付錢、要管安全群組的負載平衡器，服務一多，帳單和資安要審的對外入口都跟著變多。對外的 HTTP 服務正確的做法是共用一個入口，依網域和路徑分給各個 ClusterIP Service，這是第 5 課的 Gateway API。review 時看到新服務寫了 type: LoadBalancer，資深工程師會先問：它真的要直接對外嗎？走的是 HTTP 嗎？多半的答案是掛到 Gateway 上就好。kubectl port-forward 也能從 Mac 連進叢集，但它是開發時的臨時通道（關掉終端機就斷），不是對外服務的方式。

長連線與負載平衡

kube-proxy 的規則是在建立 TCP 連線時挑一個 Pod，之後這條連線上的所有請求都送到同一個 Pod。它看不懂 HTTP，所以叫 L4（傳輸層）負載平衡。用 cafe-api 回應的 x-instance 標頭（處理請求的 Pod 名稱）可以看到差別：

# 一次 curl 送 4 個請求：curl 會重用同一條連線（keep-alive）
kubectl exec -n k8s-tools deploy/probe -- sh -c \
  'curl -s -o /dev/null -D - http://cafe-api.demo/version http://cafe-api.demo/version http://cafe-api.demo/version http://cafe-api.demo/version | grep x-instance'
x-instance: cafe-api-549b54d94-vncjq
x-instance: cafe-api-549b54d94-vncjq
x-instance: cafe-api-549b54d94-vncjq
x-instance: cafe-api-549b54d94-vncjq

# 每次都開新連線
kubectl exec -n k8s-tools deploy/probe -- sh -c \
  'for i in 1 2 3 4; do curl -s -o /dev/null -D - http://cafe-api.demo/version | grep x-instance; done'
x-instance: cafe-api-549b54d94-vncjq
x-instance: cafe-api-549b54d94-6ghn2
x-instance: cafe-api-549b54d94-6ghn2
x-instance: cafe-api-549b54d94-vncjq

正式環境的影響：服務之間的呼叫通常是長連線。Node 的 fetch 預設 keep-alive、資料庫連線池、gRPC 都會讓一條連線用很久。結果是三個副本裡一個很忙、兩個很閒，剛擴出來的新 Pod 也分不到舊連線的流量。查的時候看每個 Pod 的請求數或 CPU（第 8 課的 kubectl top），不要只看總量。

處理方式依需求選：

  • 大部分 HTTP 服務：連線會因為閒置逾時、部署重啟自然換掉，不平均的程度通常可以接受。
  • 需要每個請求都平均分配：在前面放 L7（應用層，看得懂 HTTP）的代理，例如第 5 課的 Gateway，或 service mesh（Istio、Linkerd 這類在每個 Pod 旁邊加代理的平台）。
  • gRPC 這類單一長連線：用客戶端負載平衡（搭配 headless Service 拿到每個 Pod 的 IP），或設定連線的最長壽命讓它定期重連。

Service 沒有流量：照順序排查

最常見的狀況：Service 建得起來（apply 沒報錯），可是呼叫一直失敗。照著上面那張圖，從 Pod 往外查，每一步都有明確的指令：

  1. EndpointSlice 有沒有東西： 
    kubectl get endpointslice -n demo -l kubernetes.io/service-name=cafe-api
NAME             ADDRESSTYPE   PORTS     ENDPOINTS   AGE
cafe-api-79pvt   IPv4          <unset>   <unset>     3s
    ENDPOINTS 是 <unset>：selector 一個 Pod 都沒挑到，或挑到的 Pod 都沒 Ready。下一步。
  2. selector 和 Pod 的 label 對不對得上： 
    kubectl describe service cafe-api -n demo
Selector:   app.kubernetes.io/instance=mian,app.kubernetes.io/name=cafe-api
TargetPort: web/TCP
Endpoints:
kubectl get pods -n demo --show-labels
    把 Selector 跟 Pod 的 LABELS 逐字比對（這裡 mian 拼錯）。label 都對，就看 Pod 的 READY 欄是不是 1/1。
  3. port／targetPort：ENDPOINTS 有 IP、PORTS 卻是 <unset>，代表 targetPort 寫的名字在容器上找不到： 
    NAME            ADDRESSTYPE   PORTS     ENDPOINTS               AGE
badport-pcv8g   IPv4          <unset>   10.244.1.9,10.244.2.7   20s
    PORTS 有數字但連線被拒（Could not connect to server），就是數字不對：targetPort 要等於程式真正聽的 port。用 kubectl get service cafe-api -n demo -o yaml 和 Deployment 的 containerPort 對照。
  4. 名字：錯誤是 Could not resolve host 或 ENOTFOUND：檢查呼叫端在哪個 namespace、名字有沒有帶上 Service 的 namespace（getent hosts 試一次）。

你可能在舊文章看到 kubectl get endpoints。Endpoints 是 EndpointSlice 的前身，從 Kubernetes 1.33 起標為 deprecated，這個叢集執行時會印出 Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice。看的內容一樣，新的習慣用 EndpointSlice。

💡 實務上：「API 連不到」先看 EndpointSlice
很多人一連不上就先懷疑 DNS 或網路，花一小時查 CoreDNS，最後發現是 label 拼錯。資深的做法是照順序、不跳步：EndpointSlice 一行指令就能排除一半的可能，有 ready 的 endpoint 才往 port、名字查。在事故頻道回報時也照這個順序寫，例如「EndpointSlice 有 3 個 ready、port 3000、getent hosts 解析得到」，接手的人不用從頭再查一遍。第 14 課會把這個順序擴大成完整的除錯流程。

練習

四題都在 kubernetes/practice/work/04/，執行頁面上的指令跑測試。測試會把你的 manifest 套用到專屬的 namespace（k8s-04-ex1、k8s-04-ex2…），從 k8s-tools 裡的 Pod 用真的請求檢查，跑完刪掉 namespace。叢集很忙時一題要跑幾分鐘。想自己動手試，可以用 kubectl apply -n k8s-04-ex1 -f kubernetes/practice/work/04/ex1/（先 kubectl create namespace k8s-04-ex1），測試開始時會把同名的 namespace 清掉重建。

練習 1：deployment.yaml 是第 3 課的 cafe-api（3 個副本）。替容器的 3000 port 取名 http，再在 service.yaml 寫 ClusterIP Service cafe-api：port 80，targetPort 用名字 http，selector 只挑這個 Deployment 的 Pod。測試會在同一個 namespace 另外放一個同名（app.kubernetes.io/name: cafe-api）、但 instance 是 canary 的 Deployment，然後從叢集裡用新連線呼叫 http://cafe-api.k8s-04-ex1/health/live 200 次：要全部成功、至少分到 2 個 Pod，而且一次都不能打到 canary。

練習 2：ex2/ 的 Service 套用後沒有任何流量，裡面有兩個錯。先套用到自己建的 namespace，只用 kubectl 照「排查順序」找出原因（不要先看 YAML 猜），修好 service.yaml，再在 diagnosis.md 寫下你用了哪些指令、各看到什麼。不能把 Service 改成別的類型繞過。測試要求：EndpointSlice 有 3 個 ready 的 endpoint、port 是 3000，http://cafe-api.k8s-04-ex2/version 回 200；diagnosis.md 要提到看 EndpointSlice 的指令，以及 describe、-o yaml 或 --show-labels 其中之一。

練習 3：菜單由另一個團隊負責，跑在 namespace k8s-04-ex3-menu（ex3/menu/，GET /products 回傳菜單）；點餐 API 在 k8s-04-ex3-api（ex3/api/），它的 GET /menu-proxy 會去抓環境變數 MENU_URL 的網址。測試把兩個資料夾分別套用到這兩個 namespace，manifest 裡不要寫 namespace。完成兩件事：寫 menu/service.yaml 的 Service menu（port 80），以及填好 api/deployment.yaml 的 MENU_URL，指到菜單服務的 /products。不能寫 IP；測試會把 menu 的 Service 刪掉重建（ClusterIP 改變），API 要照樣拿得到菜單。

練習 4：把 cafe-api 開到 Mac。在 service-lb.yaml 寫 LoadBalancer Service cafe-api（port 80 → 容器的 http），在 curl.sh 用 node kubernetes/practice/bin/url.mjs k8s-04-ex4 cafe-api 取得網址，再 curl 它的 /version。腳本在 learn 資料夾執行（bash kubernetes/practice/work/04/ex4/curl.sh）。Envoy 剛建好時會有幾十秒連不上，可以用 curl 的 --retry 10 --retry-all-errors --retry-delay 3 重試。測試會跑一次，把 Service 刪掉重建讓 Mac 上的 port 改變，再跑一次；不能寫死 port，也不能用 kubectl port-forward。

練習 5：Service cafe-api 的 EndpointSlice 是空的（ENDPOINTS 是 <unset>），最先檢查什麼？

✓ EndpointSlice 只放 selector 挑到、而且 Ready 的 Pod。空的代表 selector 和 label 對不上，或 Pod 還沒 Ready（第 7 課的 readiness）。a：DNS 只負責把名字變成 ClusterIP，就算 DNS 正常，後面沒有 Pod 一樣連不到。c：EndpointSlice 是 API 裡的紀錄，跟防火牆無關。d：重建一模一樣的 Service，selector 還是錯的。

練習 6：訂單服務用 HTTP keep-alive 呼叫 cafe-api Service，三個副本裡只有一個 CPU 很高。最可能的原因是？

✓ ClusterIP 是 L4 負載平衡，分配發生在建立連線時。要每個請求都平均，需要 L7 的代理（第 5 課的 Gateway、service mesh），或讓客戶端定期換連線。c：沒 Ready 的 Pod 確實收不到流量，但那樣另外兩個應該是完全沒有請求，而且 kubectl get pods 一眼就看得出來；三個都 Ready 卻不平均，是長連線。d：DNS 回的是 Service 的 ClusterIP，不是 Pod IP（headless Service 才回 Pod IP）。

練習 7：namespace shop 裡的 Pod 要呼叫 namespace pay 的 Service gateway，下面哪個名稱一定查得到？

✓ <service>.<namespace> 會被 search 補成 gateway.pay.svc.cluster.local。a：短名稱先補上自己的 namespace，變成 gateway.shop.svc.cluster.local，shop 裡沒有就查不到。c：順序反了，Service 名稱在前。d：指到 shop，namespace 錯了。

練習 8：Service 寫了 port: 80、沒寫 targetPort，容器聽 3000。EndpointSlice 有 3 個 ready 的 IP，但呼叫都是連線被拒。為什麼？

✓ targetPort 預設等於 port。EndpointSlice 的 PORTS 會顯示 80，這就是線索；改成 targetPort: http（容器 port 的名字）或 3000。a：EndpointSlice 裡是 ready，代表 Pod 已經 Ready。b：Service 的 port 可以是任何數字，跟容器的 port 無關。d：連線被拒代表已經連到 Pod 的 IP，只是那個 port 沒人聽；名字查不到的錯誤長得不一樣。

常見錯誤

  • 在設定裡寫 Pod IP 或 ClusterIP：Pod 重建、Service 重建都會換 IP。一律用 DNS 名稱，跨 namespace 寫 <service>.<namespace>。
  • 跨 namespace 只寫短名稱：短名稱只會在呼叫端自己的 namespace 找，結果是 ENOTFOUND。
  • targetPort 寫錯或沒寫：Service 建得起來，但連線被拒，或 EndpointSlice 的 PORTS 是 <unset>。替容器 port 取名，targetPort 用名字。
  • selector 太寬：只寫 app.kubernetes.io/name，同 namespace 的 canary 或別的 Deployment 也會被挑進來收流量。selector 要能唯一指到這組 Pod（例如再加 app.kubernetes.io/instance）。
  • 以為 Service 會做健康檢查：Service 只看 Pod 的 Ready 狀態。程式卡死但容器還在，沒有 readiness probe 就會繼續收流量（第 7 課）。
  • 長連線造成負載不平均：kube-proxy 以連線為單位分配。看每個 Pod 的請求量或 CPU，需要逐請求分配時改用 L7。
  • 每個服務都開 LoadBalancer：雲端上每個都是一台要付錢的負載平衡器。服務之間用 ClusterIP，對外 HTTP 統一走第 5 課的 Gateway。
  • 用 BusyBox 的 nslookup 查短名稱就斷定 DNS 壞了：它不套用 search，給完整名稱或改用 getent hosts。

小結

  • Pod IP 會變、有好幾份、不知道誰準備好了，所以呼叫端不直接連 Pod。
  • Service 用 selector 挑 Pod，給它們固定的 ClusterIP 和 DNS 名稱；控制器把挑到而且 Ready 的 Pod 寫進 EndpointSlice，每個節點的 kube-proxy 依此寫轉送規則。Service 本身不是程序。
  • port 是呼叫端連的，targetPort 是容器聽的；替容器 port 取名，targetPort 寫名字。
  • 同 namespace 用 cafe-api，跨 namespace 用 cafe-api.<ns>，完整名稱是 cafe-api.<ns>.svc.cluster.local；靠的是 resolv.conf 的 search 和 ndots:5。
  • ClusterIP 給內部、LoadBalancer 給外部（本機由 cloud-provider-kind 開 Envoy 容器，用 bin/url.mjs 查 port）、headless 回 Pod IP、ExternalName 指外部主機，NodePort 很少直接用。
  • kube-proxy 是 L4、以連線為單位分配，長連線會讓負載不平均。
  • 沒有流量時照順序查：EndpointSlice → selector 與 Ready → port／targetPort → DNS 名稱與 namespace。
