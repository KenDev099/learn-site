階段 3：穩定上線 · 第 9 課

不停機部署：滾動更新、回滾與 PodDisruptionBudget（資深）

第 7 課讓單一 Pod 啟動和關機都不掉請求。但一次部署會換掉所有 Pod，平台團隊升級節點時也會把整台節點清空。換的節奏太快，容量會在中途掉下來；新版本啟動就崩潰，要有人發現並退回去；三個副本剛好都在被維護的那台節點上，服務就整個中斷。

這一課處理「一群 Pod」層級的不停機，學完你能在負載下完成更新、回滾、drain 一個節點，全程 0 錯誤。

這課的路線：
  1. 滾動更新的數學：maxSurge、maxUnavailable 決定換版途中最少、最多有幾個 Pod，容量會不會在中途掉下來。
  2. 壞版本會怎樣：新版一啟動就崩潰時，滾動更新停在哪裡，部署腳本怎麼偵測到並自動回滾。
  3. 新舊版本同時在線：哪些程式與資料庫變更能直接滾動更新，PR review 時先問什麼。
  4. drain、PDB 與分散副本：平台團隊升級節點時，怎麼保證不會一次趕走所有副本，副本也不會全擠在同一台節點。
  5. 非自願中斷：節點真的當機時 PDB 管不到，靠什麼撐住服務。
這課會用到：
  • 第 3 課的 rollout：改 Pod 範本就建一個新的 ReplicaSet 換版，rollout status 等它換完、rollout undo 退回上一版；節點失聯要 300 秒後 Pod 才會被搬走。
  • 第 7 課的 probe 與關機：readinessProbe 通過才收流量；Pod 被刪時先跑 preStop，應用在寬限期內排空。
  • devops 課第 17 課的 expand／contract：不相容的資料庫變更拆成先加（expand）、等舊版下線再刪（contract）好幾次部署。

滾動更新的數學

滾動更新（RollingUpdate）是 Deployment 預設的換版方式：一次換一部分 Pod，直到全部換成新版。第 3 課看過它的外觀，這裡算清楚它的節奏。節奏由兩個欄位決定：

  • maxSurge：更新期間，Pod 總數最多可以比 replicas 多幾個。
  • maxUnavailable：更新期間，可用的 Pod 最多可以比 replicas 少幾個。

兩個都可以寫數字或百分比，預設都是 25%。百分比換算成個數時，maxSurge 無條件進位、maxUnavailable 無條件捨去；兩個不能同時是 0（既不能多、也不能少，就換不動了）。於是：

replicasmaxSurge／maxUnavailable最多同時幾個 Pod最少幾個可用
4預設 25%／25%（＝1／1）53
3預設 25%／25%（＝1／0）43
41／054
40／143
1025%／25%（＝3／2）138

以 4 個副本、maxSurge 1、maxUnavailable 0 為例，過程是這樣：

怎麼選：

  • maxUnavailable 0、maxSurge 1：容量從不下降，代價是更新比較慢，而且叢集要有多放一個 Pod 的空間（第 8 課的 requests）。流量吃緊的 API 用這組，是安全的預設。
  • maxUnavailable 大於 0：叢集已經滿了、多開不了 Pod 時才用。它表示「這段時間少一點容量也撐得住」，要先確定剩下的副本扛得住尖峰流量。
  • maxSurge 調大（例如 50%）：副本很多、想快一點換完時用，代價是更新時多佔資源。

「可用」（available）不等於 Ready。minReadySeconds 是新 Pod Ready 之後還要穩定多久才算可用，預設 0。設成 5～10 秒，可以擋住「剛 Ready 幾秒就崩潰」的版本：它還沒算可用，Deployment 就不會關下一個舊 Pod，壞版本不會一路擴散。kubectl get deploy 的 AVAILABLE 欄位、status.availableReplicas 數的就是它。

另一種策略是 Recreate：先把舊 Pod 全部關掉，再建新的，中間一定有一段時間沒有任何 Pod。只用在新舊版不能同時存在的情況，例如兩版同時寫同一個檔案會損壞資料，或者只能有一個程序持有某個鎖。一般的 API 不用它。

壞版本會怎樣：progressDeadlineSeconds 與自動回滾

課程映像 learn-k8s/cafe-api:bad 啟動就以 1 結束。用練習 1 的設定換成它：

kubectl create namespace try-09
kubectl apply -n try-09 -f kubernetes/practice/work/09/ex2/        # 練習 2 的 Deployment（先把 TODO 做完）
kubectl set image -n try-09 deployment/cafe-api api=learn-k8s/cafe-api:bad
kubectl get pods -n try-09 -w

你會看到：多出 1 個新 Pod，在 Error 和 CrashLoopBackOff 之間循環（第 7 課），4 個舊 Pod 一個都沒少。原因是 maxSurge 只允許多 1 個，而新 Pod 永遠不會變成可用，maxUnavailable 0 又不准關舊的。滾動更新的設計讓壞版本吃不掉超過 maxUnavailable 的容量；如果 maxUnavailable 是 1，就會少 1 個舊 Pod，但也只有 1 個。

然後呢？Kubernetes 會等。progressDeadlineSeconds（預設 600 秒）是「多久沒有進展就標成失敗」：沒有新的 Pod 變成可用、也沒有舊的被關掉，超過這個時間，Deployment 的 Progressing 條件變成 False，原因 ProgressDeadlineExceeded：

$ kubectl get deploy cafe-api -n try-09 -o jsonpath='{.status.conditions[?(@.type=="Progressing")]}'
{"reason":"ProgressDeadlineExceeded","status":"False","message":"ReplicaSet \"cafe-api-…\" has timed out progressing.", …}

就這樣。Kubernetes 不會自動回滾，壞的 Pod 會一直留在那裡重啟，Deployment 控制器也會繼續嘗試。回不回滾要由部署流程決定。部署腳本的基本形狀：

set -euo pipefail
kubectl set image -n "$NS" deployment/cafe-api api="learn-k8s/cafe-api:$TAG"
if ! kubectl rollout status -n "$NS" deployment/cafe-api --timeout=120s; then
  kubectl rollout undo -n "$NS" deployment/cafe-api                     # 回到上一個 revision
  kubectl rollout status -n "$NS" deployment/cafe-api --timeout=120s    # 等回滾真的完成
  exit 1                                                                 # 這次部署失敗：CI 要亮紅燈
fi
# 成功之後做煙霧測試，例如打一次 /version 確認是新版本

幾個細節，每個都是事故的來源：

  • if ! 包住 rollout status：腳本開了 set -e，指令失敗會讓腳本立刻結束，後面的 undo 永遠不會執行。if 的條件裡失敗不會觸發 set -e。
  • progressDeadlineSeconds 和 --timeout 兩個都設：前者讓 Deployment 自己的狀態變成「失敗」，kubectl get、監控、Argo CD 都看得到；後者讓腳本不會無限等。rollout status 在兩者之一先到時就以非 0 結束。progressDeadlineSeconds 要大於正常版本完成一次的時間，不然慢一點的正常部署也會被判失敗。
  • undo 之後也要等：undo 只是送出「改回上一版」的請求。腳本立刻結束，CI 就以為已經回到好版本，下一個步驟（例如通知、下一個服務的部署）可能在回滾還沒完成時就開始。
  • 回滾成功仍然 exit 1：這次部署的目標沒有達成。回滾是止血，不是成功。
  • 不要刪掉 Deployment 再重建：所有 Pod 同時消失、服務中斷，rollout history 也沒了。

Helm（第 13 課）的 helm upgrade --rollback-on-failure（Helm 3 叫 --atomic）做的是同一件事：等資源就緒，失敗就回到上一個 release。在 CI 裡，這段「部署＋等待＋回滾」不能被取消：跑到一半被新的 commit 取消，叢集會停在半套狀態（devops 課第 16 課）。

💡 實務上：回滾是止血，接著要讓 git 跟上
典型的情境：下午部署 v2 後錯誤率上升，值班的人先 rollout undo，五分鐘後服務恢復。這時 git 裡的 manifest 還是新版本（第 3 課提過），下一次有人合併別的 PR、CI 重新部署，壞版本又會被送上去。資深的做法是止血後馬上在事故頻道說明「已回到 v1，git 還沒改」，在 git 改好之前先暫停這個服務的自動部署，接著開 revert PR，或把修正和新的 tag 一起送 review。部署腳本回滾後仍以非 0 結束、CI 亮紅燈，也是在提醒大家「現在叢集和 git 不一致」。

新舊版本同時在線

滾動更新有一個常被忽略的後果：更新期間 v1 和 v2 同時在接流量。同一個使用者連續兩個請求，可能一個打到 v1、一個打到 v2；v2 寫進資料庫的資料，下一秒可能被 v1 讀出來。出事時回滾，又會變成 v2 寫的資料給 v1 用。所以每個變更都要問：新舊兩版同時跑、互相讀寫對方的資料，會不會出事？

變更能直接滾動更新嗎做法
新增 API 端點、回應多一個欄位可以只增不改，舊客戶端不會用到
資料表新增可為 NULL 的欄位可以migration 在新版上線前跑完；舊版的 INSERT 不寫它也合法
刪掉回應欄位不行舊版前端、使用者手機上的舊版 App 還在讀；先讓所有客戶端不再讀，之後的部署才刪
欄位改名（例如 total → amount）不行expand：加 amount → 新版兩邊都寫、回填舊資料 → 全部換成新版後 contract：刪 total
改佇列訊息格式不行佇列裡還有舊訊息，新舊 worker 同時在消費；訊息帶版本號，消費端先能讀兩種，生產端再換

這就是 devops 課第 17 課的 expand／contract：一次不相容的變更，拆成好幾次相容的部署。順序是：

  1. migration 先跑：在新版 Pod 上線之前，用第 10 課的 Job 把 schema 擴充好（expand）。schema 只增不刪，舊版照常運作。
  2. 滾動更新應用程式：新版能處理新舊兩種資料，舊版不受新 schema 影響。
  3. 確認沒有舊版、回滾也不會回到舊版之後，下一次部署才 contract：刪掉舊欄位。

前端也一樣：Vue 的 SPA 被使用者開著好幾天，它呼叫的 API 格式要比後端的部署活得更久（API 怎麼相容地演進，見 系統設計課第 19 課）。這也是為什麼「回滾」不一定安全：如果新版已經跑了 contract 的 migration，退回舊版會讀不到被刪掉的欄位。contract 和程式的變更不要放在同一次部署，回滾才永遠有路可退。

💡 實務上：review 時先問「這次能不能直接滾動更新」
後端 PR 改到 API 回應、資料表或佇列訊息時，reviewer 第一個問題就是上面那張表：新舊兩版同時跑會不會出事、出事時回滾有沒有路。很多團隊把它寫進 PR 範本，例如「有沒有 migration？是不是只做 expand？回滾到上一版安全嗎？」。PM 眼中很小的「欄位改名」，實際上要拆成兩、三次部署、跨好幾天，排時程時就要先講清楚。前端同事也要知道這件事：SPA 和手機 App 的舊版會比後端的部署活得更久。

不只是部署會中斷：drain 與 PodDisruptionBudget

Pod 被關掉不只在部署時。正式環境裡更常見的是節點維護：

  • 節點升級：EKS 的受管節點群組更新 Kubernetes 版本或 AMI 時，會一台一台把舊節點清空再關掉。
  • 節點整併：Karpenter（EKS 常用的節點自動調整工具，第 15 課）發現兩台節點都很空，會把一台上的 Pod 搬走、關掉那台省錢。
  • 手動維護：換掉有問題的節點、調整核心參數。

這些都是自願中斷（voluntary disruption）：人或系統主動造成、事前可以控制節奏的中斷。相對的是非自願中斷：節點當機、硬體故障、核心崩潰，沒有人能先問一聲。

清空節點的指令是 kubectl drain：

kubectl drain learn-k8s-worker --ignore-daemonsets --delete-emptydir-data --timeout=180s
#   1. 先 cordon：把節點標成不可排程（新的 Pod 不會再放上來）
#   2. 再逐一「驅逐」上面的 Pod，每個 Pod 走第 7 課的正常關機流程
#   --ignore-daemonsets：DaemonSet 的 Pod 本來就每台一個，不驅逐
#   --delete-emptydir-data：Pod 用了 emptyDir（第 11 課），驅逐後裡面的資料會消失，明確表示同意
kubectl uncordon learn-k8s-worker       # 維護完，讓節點重新接受 Pod

cordon 只做第 1 步：標成不可排程，現有的 Pod 不動。drain 的第 2 步用的是驅逐 API（eviction），不是直接刪除。差別在於：驅逐前，API server 會檢查這個 Pod 有沒有被 PodDisruptionBudget（PDB）保護；這次驅逐會讓可用的 Pod 低於預算，就回 429 Too Many Requests 拒絕，drain 每 5 秒重試一次，直到別處的新 Pod Ready、預算又夠了。

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: cafe-api
spec:
  maxUnavailable: 1            # 自願中斷時，最多只能有 1 個不可用
  selector:
    matchLabels:               # 跟 Deployment 的 Pod label 一樣（第 3 課）
      app.kubernetes.io/name: cafe-api
      app.kubernetes.io/instance: main

沒有 PDB 時，drain 一台放了 2 個 cafe-api 的節點，2 個會同時被驅逐，3 個副本瞬間剩 1 個扛全部流量。有了 PDB，第 2 個要等第 1 個的替代 Pod 在別的節點 Ready 才會被驅逐。

PDB 有兩種寫法，只能擇一：

  • maxUnavailable: 1：最多少 1 個。副本數變動（例如第 8 課的 HPA 擴縮）時不用跟著改，推薦。
  • minAvailable: 2：至少留 2 個。也可以寫百分比。
PDB 不能把路堵死：3 個副本設 minAvailable: 3（或 maxUnavailable: 0），等於「一個都不准驅逐」。drain 永遠卡住，平台團隊的節點升級跟著卡住，最後只能來找你，或是強制處理。PDB 要留出可以中斷的空間。單一副本的服務，PDB 也救不了：唯一的 Pod 被驅逐，服務就中斷；不准驅逐，節點就不能維護。正式服務至少 2～3 個副本。

PDB 還有一個欄位 unhealthyPodEvictionPolicy（1.31 穩定）。預設 IfHealthyBudget：服務本來就有 Pod 不健康時，連那些壞掉的 Pod 也不能驅逐，drain 會被一個 CrashLoopBackOff 的 Pod 卡住。官方文件建議設成 AlwaysAllow：Running 但還沒 Ready 的 Pod 隨時可以驅逐，健康的 Pod 照常受預算保護。

PDB 只管驅逐：drain、Karpenter、受管節點群組升級都走驅逐 API，所以都會遵守。它不管直接刪除（kubectl delete pod）、Deployment 自己的滾動更新（那是 maxUnavailable 的工作），也擋不住節點當機。

💡 實務上：平台團隊升級節點那天
EKS 升級、換 AMI 前，平台團隊會先跑 kubectl get pdb -A，看 ALLOWED DISRUPTIONS 欄：是 0 的服務，drain 就會卡在它身上。常見的原因是 PDB 寫成跟副本數一樣、只有 1 個副本，或服務本來就有 Pod 不健康。負責任的平台團隊不會直接強制刪除，而是來問你：「cafe-api 的 PDB 讓節點升級卡住了，可以調嗎？」。上線前自己先確認這個欄位平常至少是 1，比升級當天被追著跑好得多。

分散副本：topologySpreadConstraints

PDB 保護的是「一次少幾個」，但如果 3 個副本全在同一台節點上，PDB 也只能讓 drain 一個一個來；那台節點如果是當機，3 個同時消失。副本要分散到不同節點，正式環境還要分散到不同的可用區（AWS 的 AZ，一個機房區域停電不會拖垮全部）。

spec:
  template:
    spec:
      topologySpreadConstraints:
        - maxSkew: 1                             # 任兩個節點的 Pod 數最多差 1
          topologyKey: kubernetes.io/hostname    # 以「節點」為單位；EKS 跨可用區用 topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule       # 做不到就不排程（Pending）
          nodeTaintsPolicy: Honor                # 不把放不了 Pod 的節點算進來
          labelSelector:
            matchLabels:                         # 數哪些 Pod：通常就是這個 Deployment 的 Pod
              app.kubernetes.io/name: cafe-api
              app.kubernetes.io/instance: main

scheduler 放每個新 Pod 時，會數每個節點（topologyKey 相同的一組節點叫一個「網域」）上已經有幾個符合 labelSelector 的 Pod，選一個放了之後最多和最少差不超過 maxSkew 的節點。whenUnsatisfiable 決定做不到時怎麼辦：DoNotSchedule 讓 Pod Pending，保證分散；ScheduleAnyway 只是盡量，做不到也照放。關鍵服務用 DoNotSchedule，不在意的用 ScheduleAnyway。

還有一個陷阱。kind 的 control-plane 節點有一個 taint（污點：節點上的標記，沒有對應 toleration 的 Pod 不能放上去），cafe-api 放不上去。但分散規則預設 nodeTaintsPolicy: Ignore，計算時仍然把它當成一個網域。結果是：

  1. 前兩個 Pod 分別放在 worker 和 worker2，control-plane 是 0 個。
  2. 第 3 個 Pod 不管放哪個 worker，那個 worker 就是 2 個，和 control-plane 的 0 個差 2，超過 maxSkew 1。
  3. 它又不能放 control-plane，於是一直 Pending：0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 node(s) didn't match pod topology spread constraints。

drain 時也一樣：被 cordon 的節點會自動帶上 node.kubernetes.io/unschedulable 這個 taint，Ignore 會把它也算成 0 個 Pod 的網域，被驅逐的 Pod 在別處建不起來，PDB 不准下一個驅逐，drain 就卡住。nodeTaintsPolicy: Honor（1.33 穩定）讓計算時排除 Pod 不能容忍 taint 的節點。nodeAffinityPolicy 則是對 nodeSelector／nodeAffinity 做同樣的事，預設已經是 Honor。

另一個常見的寫法是 反親和性（podAntiAffinity）：要求「不要跟同樣 label 的 Pod 放在同一個節點」。它的問題是副本數超過節點數時，多出來的 Pod 一律 Pending；topologySpreadConstraints 允許每個節點放好幾個、只要求平均，所以新寫的設定用分散規則。

非自願中斷：PDB 管不到的時候

節點當機時沒有人呼叫驅逐 API，PDB 完全不參與。這時候撐住服務的是另外三件事：

  • 多副本＋分散：一台節點消失，只損失三分之一的容量，而不是全部。
  • readiness：失聯節點上的 Pod 會在控制平面把節點標成 NotReady 後從端點拿掉（第 4 課的 EndpointSlice），流量轉到其他節點。
  • 容量餘裕：第 3 課說過，Pod 要等約 50 秒確認節點失聯、再加 300 秒的容忍時間才會在別處重建。這 5、6 分鐘裡，剩下的副本要扛得住全部流量；HPA（第 8 課）會幫忙，前提是有節點放得下新 Pod。

資深工程師的檢查清單：至少 3 個副本、分散到不同節點（正式環境不同可用區）、PDB maxUnavailable 1、readiness 正確、滾動更新 maxUnavailable 0。這幾樣都有了，部署、節點升級、單一節點故障都不會讓使用者看到錯誤。

練習

在 learn 資料夾執行頁面上的指令，起始檔會複製到 kubernetes/practice/work/09/。練習 1～3 先做靜態檢查，通過了才套用到叢集的專屬 namespace（k8s-09-ex1 這種名字），在 loadgen 每秒 10 個請求的負載下檢查，每題要幾分鐘。練習 4 只檢查檔案。自己想先試的話，用前面的 try-09 namespace，用完 kubectl delete namespace try-09。

練習 1：ex1/deployment.yaml 是 4 個副本的 cafe-api，啟動要 3 秒，preStop 與寬限期已經設好。替它加上 readinessProbe（HTTP GET /health/ready，periodSeconds 不超過 5）、明確寫出 strategy（RollingUpdate 與 rollingUpdate 的兩個欄位），讓更新期間可用的 Pod 永遠不少於 4 個，並設 minReadySeconds: 5。映像、副本數、環境變數不要改，ex1/service.yaml 不用改。測試在持續負載下把映像從 v1 換成 v2，用 kubectl get -w 記錄 status.availableReplicas 的每一次變化：要 0 錯誤、最低值 ≥ 4、最後 4 個 Pod 都是 v2。

練習 2：ex2/deployment.yaml 是練習 1 的答案，替它加上 progressDeadlineSeconds: 60。然後完成 ex2/deploy.sh <tag>（操作 namespace k8s-09-ex2，換映像的兩行已經寫好）：用 rollout status --timeout=120s 等它完成；沒完成時 rollout undo、再用 rollout status --timeout 等回滾完成，最後 exit 1。測試先套用你的 manifest，在負載下依序執行 deploy.sh v2（要以 0 結束、4 個 Pod 都是 v2）和 deploy.sh bad（要在 180 秒內以非 0 結束，結束時 Deployment 回到 v2、4 個 Ready 的 Pod 都是 v2），全程 0 錯誤。不能刪掉重建 Deployment。

練習 3：ex3/deployment.yaml 是 3 個副本的 cafe-api，probe 與 preStop 都設好了。在 Pod 範本加上 topologySpreadConstraints（topologyKey: kubernetes.io/hostname、maxSkew: 1、whenUnsatisfiable: DoNotSchedule、nodeTaintsPolicy: Honor、labelSelector 選到這個 Deployment 的 Pod），並在 ex3/pdb.yaml 寫名為 cafe-api、maxUnavailable: 1 的 PodDisruptionBudget，selector 選到同樣的 Pod。測試套用後確認兩個 worker 上都有 Pod、PDB 允許 1 次中斷，接著在負載下執行 kubectl drain learn-k8s-worker --ignore-daemonsets --delete-emptydir-data --timeout=180s：要成功、0 錯誤，最後 uncordon。測試另外加了 --pod-selector，只驅逐這一題的 Pod，不打擾叢集裡其他練習；真正維護節點時不加。

練習 4：ex4/review.json 有 6 個變更情境。照「新舊版本同時在線」一節的想法，替每一個填 safeForRollingUpdate（能不能直接一次滾動更新）、requiredSteps（從檔案裡的 steps 選代碼；能直接更新的填 []）和一句話的 reason。migration 一律在新版上線前跑完，requiredSteps 只填除此之外還要多做的事。測試比對每題的判斷與步驟集合，答錯時會給提示。

練習 5：4 個副本、maxSurge 1、maxUnavailable 0。更新期間最多同時存在幾個 Pod？可用的最少幾個？

✓ maxSurge 允許多 1 個（4＋1＝5），maxUnavailable 0 表示可用的不能低於 4，新 Pod 可用了才關舊的。a 是 maxSurge 0、maxUnavailable 1 的結果；c 是 Recreate 加上同時建立全部新 Pod 的想像，滾動更新不會這樣；d 把兩個欄位都當成 1，那是 4 個副本用預設 25%／25% 的情況。

練習 6：部署了一個啟動就崩潰的版本，Kubernetes 會怎樣？

✓ 滾動更新的設計讓壞版本吃不掉全部容量，但 Kubernetes 只會把 Progressing 標成 False（ProgressDeadlineExceeded），回滾要由部署流程執行（rollout undo 或 Helm 的 --rollback-on-failure）。a 是最常見的誤解；c 只會發生在 Recreate 策略；d 沒有任何機制會這樣做。

練習 7：3 個副本的服務設了 PDB minAvailable: 3。平台團隊升級節點時會發生什麼？

✓ 驅逐任何一個都會讓可用數低於 3，驅逐 API 一律回 429，drain 不斷重試直到逾時。PDB 要留出可以中斷的空間，例如 maxUnavailable 1。a、c 錯在 drain 走的驅逐 API 一定會檢查 PDB；d 錯在 PDB 只是驅逐時的檢查，不會幫你開副本。

練習 8：下列哪個變更最不能直接一次滾動更新？

✓ 更新期間舊版仍在讀寫 total，新版寫的訂單舊版讀不到，回滾後也讀不到。要先新增 amount（expand）、新版兩邊都寫並回填、全部換成新版後再移除 total（contract）。a 只增不改；c 不影響資料與介面；d 舊版的 INSERT 不寫它也合法。

常見錯誤

  • 以為 Kubernetes 會自動回滾：它只會停住並標記 ProgressDeadlineExceeded。部署流程要用 rollout status --timeout 偵測、rollout undo 回滾、等回滾完成，再以非 0 結束。
  • set -e 的腳本裡直接寫 rollout status：失敗時腳本立刻結束，後面的 undo 不會執行。用 if ! …; then 接住失敗。
  • 容量吃緊的服務用預設的 25%／25%：4 個副本以上時，更新期間會少 1 個以上的可用 Pod。流量吃緊時設 maxUnavailable 0。
  • PDB 設得跟副本數一樣：minAvailable 等於副本數或 maxUnavailable 0，所有節點維護都會卡住。用 maxUnavailable 1。
  • PDB 的 selector 選不到 Pod：PDB 存在但保護 0 個 Pod，drain 會同時驅逐全部。用 kubectl get pdb 看 ALLOWED DISRUPTIONS，和 Deployment 的 label 對照。
  • 副本都在同一個節點或可用區：一台節點出事就全滅。用 topologySpreadConstraints 分散。
  • 分散規則把不能排程的節點算進去：control-plane 或 cordon 中的節點有 taint，預設 nodeTaintsPolicy Ignore 會讓 DoNotSchedule 的 Pod Pending、drain 卡住。設 nodeTaintsPolicy: Honor。
  • 只測新版本，沒想到新舊並存：API 與 schema 要同時相容兩個版本，migration 照 expand／contract，contract 不和程式變更放在同一次部署。
  • 單副本跑正式服務：任何節點維護都會中斷，PDB 也救不了。

小結

  • 滾動更新期間，Pod 總數最多 replicas＋maxSurge、可用的最少 replicas−maxUnavailable；百分比時 surge 進位、unavailable 捨去，預設都是 25%。maxUnavailable 0、maxSurge 1 是安全的預設。
  • minReadySeconds 讓新 Pod 穩定一段時間才算可用；Recreate 只用在新舊版不能並存時。
  • 壞版本最多吃掉 maxUnavailable 的容量；progressDeadlineSeconds 到了只標成失敗，回滾由部署腳本負責：rollout status --timeout → undo → 等回滾 → exit 1。
  • 更新期間兩個版本同時在線，API 只增不刪、schema 照 expand／contract、migration 在上線前跑完。
  • drain、節點升級、Karpenter 整併是自願中斷，走驅逐 API，受 PDB（maxUnavailable 1）保護；節點當機是非自願中斷，靠多副本、分散與 readiness。
  • topologySpreadConstraints 讓副本平均分散；有 taint 的節點要用 nodeTaintsPolicy: Honor 排除。
