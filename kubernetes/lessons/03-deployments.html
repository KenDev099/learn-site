階段 1：起步：從 Compose 到叢集 · 第 3 課

Deployment 與 ReplicaSet：副本、自我修復與標籤

上一課你把 cafe-api 寫成一個 Pod，用 kubectl apply 跑起來了。但那個 Pod 只要被刪掉、或它所在的節點壞掉，就不會再回來，而且你只有一份。正式環境要的是「cafe-api 隨時有 3 份在跑、換版本時一份一份換、換壞了能退回去」。這些都是 Deployment 的工作。

學完你能把一個無狀態服務用 Deployment 部署上去，並寫出一個在壞版本時會失敗而不是卡住的部署腳本。

這課的路線：
  1. 為什麼不直接建 Pod、三層結構：Deployment、ReplicaSet、Pod 各管什麼，刪掉的 Pod 為什麼會長回來。
  2. selector 與 template 的 label：Deployment 怎麼認出「哪些 Pod 是我的」，寫錯會發生什麼事。
  3. 自我修復實驗：刪掉 Pod、停掉節點，親眼看控制器把副本補回來。
  4. 換版本與調整副本數：一份一份換新版、壞版本退回去，部署腳本怎麼在壞版本時失敗而不是卡住；尖峰時手動加的副本為什麼隔天消失。
  5. Deployment 以外的控制器：有資料的服務、每個節點一份的程式、跑完就結束的工作，各該用什麼。
這課會用到：
  • 第 1 課的期望狀態與課程叢集：你宣告要的結果，控制器一直把實際狀態拉回去。練習前先用 node kubernetes/practice/bin/cluster.mjs up 建好叢集，並在終端機設好 export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"。
  • 第 2 課的 Pod：Pod 的 YAML、貼在物件上的 label，以及 kubectl apply（照檔案建立或更新）、describe（看事件）、logs（看輸出）。

為什麼不直接建 Pod

先回想第 2 課的 Pod 會遇到什麼事：

  • 有人 kubectl delete pod cafe-api，或某個工具清掉它：Pod 就沒了，沒有東西會把它建回來。
  • Pod 所在的節點當機：Pod 跟著消失。Pod 一旦被分到某個節點，就一輩子綁在那個節點上，不會自己搬家。
  • 要 3 份：你得寫 3 個名字不同的 Pod，換版本時一個一個改、一個一個重建。
  • 要換映像：Pod 的大部分欄位建立後不能改，只能刪掉重建，中間服務會斷。

第 1 課說過 Kubernetes 的做法是「宣告期望狀態，讓控制器去維持」。Deployment 就是這份宣告：「我要 3 份長這樣的 Pod，換版本時一份一份換。」你不再直接管 Pod，而是管 Deployment，Pod 交給控制器去建、去補、去換。

三層結構：Deployment → ReplicaSet → Pod

把第 2 課的 Pod 改成 Deployment，只是把 Pod 的內容搬到 spec.template 底下，再加上副本數和 selector：

apiVersion: apps/v1            # Deployment 在 apps 這個 API 群組，v1 長期穩定
kind: Deployment
metadata:
  name: cafe-api
spec:
  replicas: 3                  # 要幾份（數字，不要加引號）
  selector:                    # 這個 Deployment 管哪些 Pod：用 label 挑
    matchLabels:
      app.kubernetes.io/name: cafe-api
      app.kubernetes.io/instance: main
  template:                    # Pod 範本：每一份 Pod 都照這個建
    metadata:
      labels:                  # 建出來的 Pod 會帶這些 label，必須被上面的 selector 挑得到
        app.kubernetes.io/name: cafe-api
        app.kubernetes.io/instance: main
    spec:                      # 這裡就是第 2 課 Pod 的 spec，原封不動
      containers:
        - name: api
          image: learn-k8s/cafe-api:v1
          imagePullPolicy: IfNotPresent
          env:
            - name: REQUIRE_DB   # cafe-api 預設要連資料庫才算準備好；這課還沒有資料庫
              value: "0"
          resources:
            requests: { cpu: 50m, memory: 64Mi }
            limits: { memory: 128Mi }

Pod 範本（pod template）就是 spec.template：一個沒有名字的 Pod，Deployment 用它當模子印出每一份 Pod。Pod 的名字由控制器自動產生。

apply 之後，叢集裡其實多了三種物件。Deployment 自己不建 Pod，它建一個 ReplicaSet：一個只負責「這個 Pod 範本隨時要有 N 份」的物件，再由 ReplicaSet 建 Pod。

為什麼要多一層？因為換版本時需要「新舊兩組 Pod 同時存在、一邊加一邊減」。每一組由一個 ReplicaSet 管，Deployment 只要調整兩個 ReplicaSet 的副本數就能完成更新（後面「換版本」那一節會看到）。ReplicaSet 通常不自己寫，讓 Deployment 建。

用 --show-labels 一次看三層：

$ kubectl get deploy,rs,pod --show-labels
NAME                       READY   UP-TO-DATE   AVAILABLE   LABELS
deployment.apps/cafe-api   3/3     3            3           <none>

NAME                                  DESIRED   CURRENT   READY   LABELS
replicaset.apps/cafe-api-6b495df9d8   3         3         3       app.kubernetes.io/instance=main,app.kubernetes.io/name=cafe-api,pod-template-hash=6b495df9d8

NAME                            READY   STATUS    LABELS
pod/cafe-api-6b495df9d8-db7j9   1/1     Running   app.kubernetes.io/instance=main,app.kubernetes.io/name=cafe-api,pod-template-hash=6b495df9d8
…

ReplicaSet 和 Pod 多了一個你沒寫的 label：pod-template-hash。Deployment 把 Pod 範本算出一個雜湊值，加在 ReplicaSet 的 selector 和它建的每個 Pod 上，用來分辨「這個 Pod 是哪一版範本建的」。範本一改，雜湊就變，就是另一個 ReplicaSet。

每個 Pod 怎麼知道自己屬於誰？看 ownerReferences：物件 metadata 裡的「我屬於誰」：

$ kubectl get pod cafe-api-6b495df9d8-db7j9 -o jsonpath='{.metadata.ownerReferences}'
[{"apiVersion":"apps/v1","kind":"ReplicaSet","name":"cafe-api-6b495df9d8","controller":true,"blockOwnerDeletion":true,"uid":"790e4bc1-…"}]

ReplicaSet 的 ownerReferences 指向 Deployment。這條鏈有兩個用途：控制器只管 controller: true 指向自己的物件；擁有者被刪掉時，叢集的垃圾回收（garbage collection）會連帶刪掉它擁有的物件。所以 kubectl delete deployment cafe-api 會把 ReplicaSet 和 3 個 Pod 一起刪掉，你不用一個一個清。反過來，只刪 Pod 沒用，ReplicaSet 會補回來。

除錯時的習慣：看到一個陌生的 Pod，先看 ownerReferences 找出它的擁有者。要讓它消失、或要改它，都是去改擁有者，不是改 Pod 本身。

selector 與 template 的 label

Deployment 靠 spec.selector 認自己的 Pod，有三條規則要記住。

1. selector 一定要挑得到 template 的 label。否則 Deployment 建出來的 Pod 自己都認不得，會一直建下去。API server 直接拒絕這種寫法：

The Deployment "cafe-api" is invalid: spec.template.metadata.labels: Invalid value:
{"app.kubernetes.io/name":"cafe-api"}: `selector` does not match template `labels`

template 可以比 selector 多 label（例如 version: v1），但 selector 裡的每一個 label，template 都要有，值也要一樣。

2. selector 建立後不能改。apps/v1 的 Deployment 一建立，selector 就固定了。改了再 apply 會看到：

The Deployment "cafe-api" is invalid: spec.selector: Invalid value: {…}: field is immutable

真的要改，只能刪掉 Deployment 重建（服務會中斷），或建一個新名字的 Deployment、等它 Ready 後再刪舊的。所以 selector 第一次就要想清楚，選一組以後不會改、而且只屬於這個 Deployment 的 label。

3. 不同 Deployment 的 selector 不要重疊。Kubernetes 不會阻止你，官方文件只警告「重疊的控制器可能衝突、行為難以預期」。在現在的版本，兩個 Deployment 不會互相搶 Pod：每個 Pod 的 ownerReferences 只指向一個 ReplicaSet，ReplicaSet 的 selector 又帶著 pod-template-hash。真正出問題的是其他「用 selector 找 Pod」的東西：

  • kubectl logs -l、kubectl delete pods -l 會一起選到對方的 Pod。
  • Deployment 的 scale 子資源回報的 selector 就是 spec.selector。第 8 課的 HPA 用它找 Pod 算 CPU 平均，會把別人的 Pod 也算進去，擴縮的判斷就錯了。
  • 第 9 課的 PodDisruptionBudget 也用 selector 計算「現在有幾個可用」。

Kubernetes 建議的 label（第 2 課介紹過）剛好解決這件事：

label意思例子
app.kubernetes.io/name這是什麼應用程式cafe-api
app.kubernetes.io/instance這個應用程式的哪一份部署main、canary

每個 Deployment 的 selector 用 name＋instance 兩個 label，組合就是唯一的。要「選到所有 cafe-api」的東西（例如第 4 課的 Service）只用 name；要「只選正式版」的用 name＋instance。version 這種每次部署都會變的 label 不要放進 selector：selector 不能改，放進去下次換版本就卡住了。

自我修復實驗

自我修復（self-healing）是指 Pod 或節點壞掉時，控制器自動把副本數補回期望值。在你自己的叢集上試兩種情況（練習 1 會自動檢查第一種）。

刪掉一個 Pod

kubectl get pods -l app.kubernetes.io/name=cafe-api -w      # 開一個視窗持續看（-w = watch）
kubectl delete pod cafe-api-6b495df9d8-db7j9                # 在另一個視窗刪一個

第一個視窗會看到被刪的 Pod 變成 Terminating，同時多了一個新名字的 Pod 從 ContainerCreating 變成 Running。新 Pod 的名字前半段一樣，因為它屬於同一個 ReplicaSet：Pod 範本沒變，只是補一份。

停掉一個節點

kind 的節點是 Docker 容器，停掉容器就等於主機斷電：

kubectl get pods -o wide                       # 記下哪些 Pod 在 learn-k8s-worker2
docker stop learn-k8s-worker2                  # 模擬節點當機
kubectl get nodes -w                           # 看節點狀態變化
kubectl get pods -o wide -w                    # 另一個視窗看 Pod
docker start learn-k8s-worker2                 # 做完一定要開回來

你會發現 Pod 沒有馬上搬家。時間軸是這樣：

  1. kubelet 定期向 API server 回報節點還活著。停止回報超過 kube-controller-manager 的 NodeMonitorGracePeriod（預設 50 秒），節點的 Ready 變成 Unknown，kubectl get nodes 顯示 NotReady，控制平面在節點加上 node.kubernetes.io/unreachable 這個 taint（污點：標在節點上、表示「沒特別允許的 Pod 不要留在這裡」，第 9 課細講）。
  2. 每個 Pod 建立時，API server 自動幫它加上「容忍 not-ready 和 unreachable 300 秒」的 toleration。用 kubectl get pod <名稱> -o jsonpath='{.spec.tolerations}' 看得到 tolerationSeconds: 300。
  3. 300 秒到了，Pod 被標記刪除。節點上的 kubelet 已經不在，沒辦法確認容器真的停了，所以 Pod 會一直停在 Terminating；ReplicaSet 不把 Terminating 的 Pod 算進副本數，立刻在其他節點補一份。
  4. docker start 之後節點回來，kubelet 清掉那些 Terminating 的 Pod。

為什麼要等 5 分鐘？節點「聯絡不上」不一定是當機，可能只是網路抖了幾秒。如果一聯絡不上就搬，網路一晃，整個節點上的 Pod 都會在別處重建，造成更大的負載。這是刻意的取捨：用幾分鐘的容量下降，換來不會因為小問題大搬家。這也說明了為什麼至少要 2～3 個副本、而且分散在不同節點：等待的這 5 分鐘裡，靠的是其他節點上的副本撐住服務（第 9 課會用 topologySpreadConstraints 確保分散）。

💡 實務上：只有 1 個副本的服務，節點一掛就停 5 分鐘以上
內部後台、報表這類「流量不大」的服務常被設成 1 個副本來省資源。它所在的節點當機時，照上面的時間軸要 5 分鐘以上才會在別的節點重建，這段時間整個服務是斷的；節點例行維護、升級時，它也一定會中斷一下。review 新服務的 manifest 時，資深工程師會問：「這個服務停 5 分鐘，誰會受影響？」會影響顧客或其他團隊，就至少 2 個副本、分散在不同節點；真的可以接受中斷，也把這個決定寫下來，讓值班的人知道。

換版本：rollout、revision 與回滾

從一版 Pod 範本換到另一版的過程叫 rollout（推出）。觸發的方法只有一個：改 Pod 範本。例如把映像從 v1 換成 v2，有兩種寫法：

# 宣告式：改 deployment.yaml 裡的 image 再 apply（正式環境的做法，改動進 git）
kubectl apply -f deployment.yaml

# 命令式：直接改叢集裡的 Deployment（腳本與緊急時用；api 是容器名稱）
kubectl set image deployment/cafe-api api=learn-k8s/cafe-api:v2

Pod 範本變了，雜湊就變，Deployment 建立第二個 ReplicaSet，然後一邊把新的擴大、一邊把舊的縮小：

$ kubectl rollout status deployment/cafe-api --timeout=90s
Waiting for deployment "cafe-api" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "cafe-api" rollout to finish: 2 out of 3 new replicas have been updated...
Waiting for deployment "cafe-api" rollout to finish: 1 old replicas are pending termination...
deployment "cafe-api" successfully rolled out

$ kubectl get rs
NAME                  DESIRED   CURRENT   READY
cafe-api-5c7c4d7979   3         3         3        ← 新版（v2）
cafe-api-6b495df9d8   0         0         0        ← 舊版（v1），縮到 0 但保留著

一次換幾個由兩個設定決定：maxSurge（最多可以比期望多幾個）和 maxUnavailable（最多可以少幾個可用），預設都是 25%。3 個副本時 maxSurge 往上取整是 1、maxUnavailable 往下取整是 0：先多開 1 個新的，等它 Ready 再關 1 個舊的，任何時候都至少有 3 個可用。細節和調整方式在第 9 課。

kubectl rollout status 會一直等到 rollout 完成，成功時以 0 結束、失敗時以非 0 結束，部署腳本靠它知道結果。一定要加 --timeout：新版本起不來時，Deployment 要等 progressDeadlineSeconds（預設 600 秒）沒有進展才宣告失敗，CI 會白等 10 分鐘。

revision 與 change-cause

每次 Pod 範本改變就多一筆 revision（版本紀錄），存在舊的 ReplicaSet 裡（這就是舊 ReplicaSet 縮到 0 卻不刪的原因）。預設保留最近 10 個舊 ReplicaSet（spec.revisionHistoryLimit），被清掉的版本就回不去了。

$ kubectl annotate deployment/cafe-api kubernetes.io/change-cause="release v2" --overwrite
$ kubectl rollout history deployment/cafe-api
REVISION  CHANGE-CAUSE
1         <none>
2         release v2

CHANGE-CAUSE 欄位讀的是 kubernetes.io/change-cause 這個 annotation，Kubernetes 不會自動填，要自己寫。部署腳本在改映像後順手寫上版本或 commit，出事時看 history 就知道每一版是什麼。

只改 replicas 不會產生新 revision：副本數不在 Pod 範本裡，同一個 ReplicaSet 直接擴大或縮小，Pod 也不會重啟。反過來，改 env、resources、label 這些 template 裡的東西，都會觸發一次 rollout。

壞版本與回滾

部署一個不存在的 tag 試試：

$ kubectl set image deployment/cafe-api api=learn-k8s/cafe-api:no-such-tag
$ kubectl rollout status deployment/cafe-api --timeout=90s
Waiting for deployment "cafe-api" rollout to finish: 1 out of 3 new replicas have been updated...
error: timed out waiting for the condition          ← 以非 0 結束
$ kubectl get pods
cafe-api-5c7c4d7979-4bwhg   1/1   Running            ← 舊版 3 個還在服務
cafe-api-5c7c4d7979-b4r4f   1/1   Running
cafe-api-5c7c4d7979-mrzr8   1/1   Running
cafe-api-748cfbd755-82g2x   0/1   ImagePullBackOff   ← 新版第 1 個就起不來，rollout 停在這裡

因為 maxUnavailable 是 0，新 Pod 沒 Ready 之前舊的一個都不會關，服務沒有中斷。但 Kubernetes 不會自動回滾，它會一直卡著，回不回滾由你的部署流程決定：

kubectl rollout undo deployment/cafe-api                  # 回到上一個 revision
kubectl rollout undo deployment/cafe-api --to-revision=2  # 回到指定的 revision
kubectl rollout status deployment/cafe-api --timeout=90s  # 一樣要等它完成

undo 是把上一個 revision 的 Pod 範本拿回來，當成一次新的 rollout，所以 history 會變成 1、3、4（2 被「搬」成 4）。用 undo 而不是自己 set image 回某個 tag，是因為你不用記得上一版是什麼，而且上一版的 env、resources 也一起回來。

💡 實務上：壞版本上線時，先 undo 止血，再修 manifest
undo 是止血，不是修好：kubectl 會提醒 undo 不會更新 last-applied-configuration，git 裡的 deployment.yaml 還寫著壞版本，下一次有人 apply 又會把它部署回去。常見的流程是：在事故頻道說一聲「我要 undo cafe-api」→ 執行 undo、用 rollout status 等它完成 → 確認錯誤率回落 → 開 PR 把 manifest 改回好的版本（或 revert 壞的 commit）。如果新版是程式崩潰（CrashLoopBackOff），undo 之前先用 kubectl logs --previous 存下新版 Pod 的 log：undo 會把新 ReplicaSet 縮到 0，那些 Pod 和它們的 log 就一起消失了。

調整副本數：kubectl scale 與 manifest

kubectl scale deployment/cafe-api --replicas=5     # 命令式：馬上生效

這很方便，但它只改了叢集裡的期望狀態，沒改 git 裡的 deployment.yaml。下一次 CI 執行 kubectl apply，replicas 會被改回檔案裡的 3。尖峰時手動加的副本，隔天部署後就悄悄消失了。

正式環境的規則：宣告的檔案才是真相。要長期改副本數，改 manifest、走 code review、再部署。要依流量自動調整，交給第 8 課的 HPA，並且從 manifest 拿掉 replicas，免得每次 apply 都跟 HPA 搶。

💡 實務上：kubectl scale 只用來救急，當天就補 PR
週六中午點餐尖峰，值班的人用 kubectl scale 加到 5 份撐過去，這樣做沒有問題。要做好的是後續：在事故頻道記下「cafe-api 手動調到 5」，當天就開 PR 改 manifest 或討論要不要改回 3，不然下一次部署會在沒人注意時把副本數改回去。資深工程師會接著問：這次尖峰是可預期的（活動、發薪日），還是天天都有？天天都有，就該交給第 8 課的 HPA，而不是每次靠人手動加。

Deployment 以外的控制器

Deployment 適合無狀態的服務：每一份 Pod 都一樣、可以隨時被替換、資料不存在 Pod 裡（devops 課第 13 課講的條件）。其他情況有別的控制器：

控制器保證什麼例子
DeploymentN 份一樣的 Pod，滾動更新cafe-api、背景 worker
DaemonSet每個節點剛好一份收集節點日誌的 agent、kube-proxy
StatefulSet每一份有固定的名字和自己的儲存空間自己架的資料庫（第 11 課）
Job／CronJob跑完就結束，失敗會重試；CronJob 照排程跑資料庫 migration、每日報表（第 10 課）

練習

在 learn 資料夾執行頁面上的指令，起始檔會複製到 kubernetes/practice/work/03/。測試會把你的 manifest 套用到專屬的 namespace（k8s-03-ex1 這種名字），檢查完就刪掉。自己想先試的話，建一個自己的 namespace：kubectl create namespace try-03，再 kubectl apply -n try-03 -f kubernetes/practice/work/03/ex1/，用完 kubectl delete namespace try-03。

練習 1：ex1/deployment.yaml 現在是第 2 課那種單獨的 Pod。把它改成 Deployment：名稱 cafe-api、3 個副本；selector 和 Pod 範本都用 app.kubernetes.io/name: cafe-api 與 app.kubernetes.io/instance: main；容器名稱 api、映像 learn-k8s/cafe-api:v1、imagePullPolicy: IfNotPresent、環境變數 REQUIRE_DB=0；requests 是 cpu 50m、memory 64Mi，limits 是 memory 128Mi。測試先用 kubeconform 和欄位檢查，再套用到叢集等 3 個 Pod Ready，然後刪掉其中一個，確認在時間內回到 3 個 Ready，而且新 Pod 屬於同一個 ReplicaSet。

練習 2：ex2/deployments.yaml 有正式版 cafe-api（3 份 v1）和金絲雀版 cafe-api-canary（1 份 v2，先讓少量流量試新版）。套用後 Pod 數量都對，但團隊發現 kubectl logs -l 和 HPA 的計算都把兩邊混在一起。找出原因並修好：兩個 Deployment 都要留著、副本數和映像不變、兩邊的 Pod 都保留 app.kubernetes.io/name: cafe-api，但每個 Deployment 的 selector 只能選到自己的 Pod。最後在 ex2/WHY.md 用一句話寫出原因。測試會讀每個 Deployment 的 scale 子資源（HPA 用的那個 selector），確認它只選到自己的 Pod。提醒：你如果已經在自己的 namespace 套用過舊版，改 selector 會遇到 field is immutable，先 kubectl delete -f 再 apply。

練習 3：寫部署和回滾腳本，要操作的是 namespace k8s-03-ex3 裡的 deployment/cafe-api（測試會先建好，內容跟練習 1 一樣，另外把 progressDeadlineSeconds 設成 120 秒）。release.sh <tag>：用 kubectl 把容器 api 的映像換成 learn-k8s/cafe-api:<tag>、寫上包含 tag 的 kubernetes.io/change-cause、用 rollout status 等它完成，最多 180 秒，沒完成要以非 0 結束。rollback.sh：回到上一個 revision 並等它完成。測試依序執行 release.sh v2（要成功、history 有 2 筆）、release.sh no-such-tag（要失敗、舊版 3 個 Pod 照常服務）、rollback.sh（要回到 v2，不是 v1）。不能刪掉重建 Deployment。

練習 4：只把 Deployment 的 replicas 從 3 改成 5 再 apply，kubectl rollout history 會怎樣？

✓ replicas 不在 Pod 範本裡，現有的 ReplicaSet 直接擴大到 5 份，原本的 3 個 Pod 不受影響。改映像、env、resources、template 的 label 才會觸發 rollout、多一筆 revision。a、d 是把「改副本數」誤當成「改範本」；c 只有超過 revisionHistoryLimit 時才會清舊的。

練習 5：kind 的一個 worker 節點停掉後，上面的 Pod 沒有立刻搬到別的節點。為什麼？

✓ 這是刻意的延遲：先等約 50 秒確認節點失聯，再給 300 秒的容忍時間。需要更快搬移的服務可以把 tolerationSeconds 調小，代價是網路抖動時多餘的搬移。a、d 錯在會自動搬，只是有等待時間（drain 是計畫性維護時用的，第 9 課）；c 錯在沒寫 replicas 預設就是 1，一樣會補。

練習 6：同事在正式環境用 kubectl scale --replicas=10 應付尖峰，隔天 CI 部署之後服務又變慢了。最可能的原因是？

✓ 宣告的檔案是真相，命令式的修改會在下一次 apply 被覆蓋。要長期改就改 manifest；要依流量自動調整就用 HPA，並從 manifest 拿掉 replicas（第 8 課）。a 不存在；c 只有設了 HPA 才可能，題目沒有；d 不會讓副本數變少。

常見錯誤

  • 直接建 Pod 跑服務：Pod 被刪或節點壞掉就不會回來。服務一律用 Deployment（或其他控制器）管理。
  • selector 和 template 的 label 對不上：API server 拒絕套用。selector 裡的每個 label 都要原樣出現在 spec.template.metadata.labels。
  • 想改 selector：apps/v1 的 selector 建立後不能改。第一次就用 app.kubernetes.io/name＋instance 這種不會變的組合，不要放 version。
  • selector 和其他 Deployment 重疊：HPA、PDB、kubectl -l 會把別人的 Pod 算進來。每個 Deployment 用自己唯一的 label 組合。
  • 以為改了 ConfigMap 或 Secret 就會更新 Pod：只有 Pod 範本改變才會觸發 rollout（第 6 課教怎麼處理）。
  • rollout status 不加 --timeout：壞版本時 CI 要等 progressDeadlineSeconds（預設 600 秒）。加上 timeout，失敗時以非 0 結束並決定要不要 undo（第 9 課）。
  • 用刪掉重建來換版本：所有 Pod 同時消失，服務中斷，history 也沒了。改 Pod 範本，讓 Deployment 滾動更新。
  • 用 kubectl scale 修正式環境：下次部署被蓋回去。改 manifest 或交給 HPA。
  • undo 之後沒改 manifest：下一次 apply 會把壞版本部署回來。止血後馬上把檔案改回好的版本。

小結

  • Deployment 宣告「N 份這樣的 Pod」；它建 ReplicaSet，ReplicaSet 建 Pod。每一層用 ownerReferences 指向擁有者，刪擁有者會連帶刪掉底下的物件。
  • selector 必須挑得到 template 的 label、建立後不能改、不要跟別的 Deployment 重疊。用 app.kubernetes.io/name＋app.kubernetes.io/instance。
  • Pod 被刪，ReplicaSet 馬上補；節點失聯，約 50 秒後變 NotReady，Pod 再等 300 秒才被驅逐重建。這段時間靠其他節點上的副本撐住。
  • 改 Pod 範本才會觸發 rollout：新 ReplicaSet 擴大、舊的縮小。rollout status --timeout 等結果，rollout history 看紀錄（change-cause 要自己寫），rollout undo 回上一版。Kubernetes 不會自動回滾。
  • 副本數改 manifest，不要靠 kubectl scale；要自動調整用 HPA。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：cafe-api 的 3 個 Pod 都是 CrashLoopBackOff，logs --previous 印出 Cannot find module 'dist/main.js'。值班同事說：「把 Pod 刪掉讓它重建就好。」會怎樣？

✓ 控制器只負責「維持 3 份照範本建的 Pod」，範本沒變，補回來的 Pod 就有同樣的問題。要修的是期望狀態：改 manifest 的 args 再 apply，Deployment 會滾動換成新 Pod。a 錯在 Pod 歸 ReplicaSet 管，刪掉馬上補；單獨建的 Pod 才不會回來。（第 1、2、3 課）

練習 8：咖啡店目前用 Compose 跑兩個 cafe-api 副本，設了 restart: unless-stopped。主管問：「程式崩潰已經會自動重開了，Kubernetes 還多解決了什麼？」最關鍵的一點是？

✓ 程序崩潰兩邊都會重開，差別在主機層級：Compose 只管一台，主機掛了就全停；Kubernetes 的控制器發現副本少了，在其他節點補上。代價是學習、維運和費用，一台主機、一個服務時 Compose 加 systemd 和監控就夠。c 錯在 Compose 可以 --scale，只是不能跨主機，upstream 也要自己改。（第 1 課）

練習 9：告警規則寫成「Pod 的 phase 不是 Running 就通知」。下面哪種狀況會漏掉，不會通知？

✓ 已經排到節點、容器在跑或正在重開時，phase 就是 Running，所以一直崩潰的 Pod 仍是 Running。phase 只是大方向，要看容器的 Waiting／Terminated reason 和重啟次數。a、c、d 的主容器都還沒啟動過，phase 停在 Pending，會被這條規則抓到。（第 2 課）

練習 10：CI 把修好的程式重新 build 成同一個 tag learn-k8s/cafe-api:v1 推上 registry，再 kubectl apply 同一份 manifest，結果印出 unchanged，線上還是舊程式。為什麼？

✓ 只有 Pod 範本改變才會觸發 rollout；映像內容換了但 tag 沒換，對叢集來說期望狀態完全一樣。每次 build 用新的 tag（正式環境用 commit SHA），改 manifest 的 image 再 apply。c 錯在 unchanged 代表根本沒有 rollout，不是在等。（第 2、3 課）

練習 11：同事要下線一個舊的 worker 服務，刪了它的 Pod，馬上冒出新的；再刪 ReplicaSet，過幾秒 ReplicaSet 和 Pod 又全部回來了。為什麼？

✓ 這是兩層控制迴圈：ReplicaSet 補 Pod，Deployment 補 ReplicaSet。用 ownerReferences 往上找到最上層的擁有者，刪 Deployment，垃圾回收會連帶刪掉底下的 ReplicaSet 和 Pod。c 錯在 ReplicaSet 的副本數由 Deployment 決定，你改成 0 也會被改回期望值。（第 3 課）

練習 12：這個 Deployment 已經在線上跑 v1。下一版把兩處的 v1 都改成 v2 再 apply，會怎樣？

spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: cafe-api
      version: v1
  template:
    metadata:
      labels:
        app.kubernetes.io/name: cafe-api
        version: v1

✓ apps/v1 的 selector 一建立就固定，改了會得到 field is immutable。每次部署都會變的 version 只能放在 template 的 label，selector 用 app.kubernetes.io/name＋instance 這種不會變的組合。c 錯在「兩邊一致」只是建立時的檢查，已存在的 Deployment 還有不能改這條規則。（第 3 課）

練習 13：cafe-api 設了 2 個副本，剛好都排在 learn-k8s-worker2。這個節點斷電後，服務會怎樣？

✓ 節點約 50 秒後才變 NotReady，Pod 預設再容忍 300 秒才被驅逐，ReplicaSet 這時才在別處補（1.37 的預設值）。這段時間只能靠其他節點上的副本撐，所以副本要分散到不同節點（第 9 課）。a 錯在控制器不會一聯絡不上就搬，這是為了避免網路抖一下就大搬家的刻意延遲。（第 3 課）

練習 14：部署腳本如下，這次 $TAG 打錯了，registry 上沒有這個映像。cafe-api 原本有 3 個副本，執行後會怎樣？

kubectl set image deployment/cafe-api api=learn-k8s/cafe-api:$TAG
kubectl rollout status deployment/cafe-api
echo "部署完成"

✓ 新 Pod 沒 Ready 之前舊的不會關，服務不中斷；但 Kubernetes 不會自動回滾，rollout status 要等 progressDeadlineSeconds（預設 600 秒）才以非 0 結束。修法：加 --timeout，失敗就 rollout undo，再把 manifest 改回好版本。b 是最常見的誤解：回不回滾由你的部署流程決定。（第 3 課）

這個階段的重點整理成一頁圖解。
