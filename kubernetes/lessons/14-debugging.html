階段 5：正式環境與期末專題 · 第 14 課

除錯工作流程：從 Pod 狀態到根因（資深）

前面每一課都教過一兩種壞法：映像 tag 打錯、Secret 少一個 key、記憶體 limit 太小、probe 打錯路徑、Service 的 selector 對不上 label。分開學的時候，症狀和原因是放在一起講的。真正值班時只會看到一句「cafe-api 掛了」，你不知道是哪一種，旁邊還有人在問什麼時候會好。這時候最常見的錯誤是亂猜、先重啟再說，結果證據跟著 Pod 一起消失。

這一課把查法整理成一個固定的順序，找到根因後修在 manifest 裡，並寫一份讓同樣的事不再發生的事故紀錄。

這課的路線：
  1. 固定的查法：值班時只聽到「cafe-api 掛了」，第一步是蒐證，不是重啟。
  2. 狀態字速查、事件與上一次的 log：STATUS 欄出現 CrashLoopBackOff、Pending 這類字時該去哪裡看；容器重啟之後，上一次為什麼死的證據去哪找。
  3. 進到容器裡：沒有 shell、exec 進不去的映像，怎麼在旁邊加一個除錯容器。
  4. 縮小範圍：Pod 都是 Running、使用者還是看到錯誤時，從入口一路往 Pod 切一刀，看是哪半段壞了。
  5. 修在宣告裡、寫事故紀錄：為什麼 kubectl edit 救完火還不算修好，事故紀錄要寫什麼。
這課會用到：
  • 第 2 課的 Pod 狀態與除錯指令：容器還沒跑是 Waiting、跑完是 Terminated，兩者都附一個 reason；get、describe、logs、exec、port-forward 這五個每天用的指令。
  • 第 4 課的 Service 排查順序：先看 EndpointSlice 有沒有 Pod，再看 selector 與 Ready、port 與 targetPort，最後是 DNS 名稱與 namespace。
  • 第 7 課的 probe：readiness 失敗就不收流量，liveness 失敗就重啟容器；容器一直重啟會變成 CrashLoopBackOff。
  • 第 8 課的資源：requests 排不下就 Pending；記憶體超過 limit 被殺是 OOMKilled，exit code 137。

固定的查法：先蒐證，不要先重啟

除錯的方法和 system-design 課第 21 課一樣：觀察、提出假設、一次只改一個變數去驗證。Kubernetes 的好處是「觀察」這一步有固定的入口，每個狀態都有對應該看的地方：

四個原則：

  1. 先蒐證，再動手。kubectl delete pod 看起來能解決很多事，但新 Pod 有新的名字，舊 Pod 的事件、上一次容器的 log、lastState 全部跟著消失。Deployment 底下的 Pod 被刪掉，原本的問題（例如設定錯）在新 Pod 一樣會出現，你只是把證據丟了。
  2. 先看最便宜的證據：get、describe、logs 不改變任何東西，幾秒鐘就有答案。exec、debug、改設定重試，都排在後面。
  3. 一次只改一個變數。同時改了映像、limit 和 probe，就算好了也不知道是哪一個修好的，下次還會再犯。
  4. 邊查邊記時間。幾點部署、幾點發現、幾點找到原因、幾點恢復。事後寫事故紀錄要用，查到一半交接給別人時也要用。
💡 實務上：半夜被叫醒的前五分鐘
告警響了，主管在頻道裡問「多久會好」，這時最想做的就是先重啟看看。資深的做法是先花一兩分鐘把證據存下來：kubectl get pods -o wide、有問題的 Pod 的 describe 和 logs --previous、kubectl events，存成檔案或貼進事故頻道，再去止血。接著問的第一個問題是「最近改了什麼」：剛剛的部署、設定或 Secret 的變更、平台團隊的節點升級，大部分事故都跟某個變更有關。如果剛好有一次部署，先回滾通常比當場找根因快。

狀態字速查：看到什麼、去哪裡看

第 2 課列過容器的 Waiting reason。這裡把它擴大成值班時用的表。根因（root cause）是讓問題發生的真正原因，例如「Secret 的 key 名稱打錯」；STATUS 欄的字只是症狀。同一個症狀可能有好幾種原因，所以表的重點是「去哪裡看」：

看到去哪裡看常見原因修法
Pendingdescribe pod 的 FailedSchedulingInsufficient cpu／memory：requests 太大或叢集滿了；untolerated taint；didn't match Pod's node affinity/selector；PVC 沒有綁定；quota 已滿（Pod 根本建不出來，看 ReplicaSet 的 FailedCreate）依訊息調整 requests、nodeSelector、toleration、PVC 的 StorageClass 或 quota
ErrImagePull、ImagePullBackOffdescribe pod 的 Failed 事件tag 打錯或沒有推上去；私有 registry 沒有 imagePullSecrets 或節點沒有權限；映像沒有這個平台（arm64／amd64）修正 tag（用 CI 產生的 tag，不要手打）、補上拉映像的權限
CreateContainerConfigErrordescribe pod 的 Failed 事件引用的 ConfigMap、Secret 或其中某個 key 不存在（第 6 課）修正名稱或 key，或先建立它；不要用 optional: true 掩蓋
CrashLoopBackOff、Errorlogs --previous、lastState 的 reason 與 exit codeexit 1：應用自己結束（缺設定、連不到依賴、程式錯誤）；137：被 SIGKILL（OOM 或 liveness 失敗被殺）；139：segfault（原生模組）依 log 修設定或程式；liveness 太嚴就放寬或改用 startupProbe（第 7 課）
OOMKilledlastState：OOMKilled、137記憶體 limit 比實際需要小，或記憶體洩漏依量測調整 limit 與 --max-old-space-size（第 8 課），洩漏要查程式
Running 但 READY 0/1事件裡的 Unhealthy：Readiness probe failedprobe 路徑或 port 打錯；readiness 檢查的依賴（資料庫、Redis）斷了修正 probe，或修好依賴；不要刪掉 probe
Running 1/1 但請求失敗EndpointSlice、port-forward、從叢集內 curlService 的 selector 或 targetPort 錯；DNS 名稱或 namespace 錯；NetworkPolicy 擋住見後面「縮小範圍」
Terminating 一直不消失get pod -o yaml 的 finalizers、節點狀態有 finalizer 等著控制器清理；Pod 所在的節點 NotReady，kubelet 沒辦法回報容器已停止修好負責清理的控制器或節點；強制刪除是最後手段

表裡有幾個新名詞：

  • taint／toleration（污點／容忍）：節點上的 taint 會拒絕一般 Pod，Pod 宣告了對應的 toleration 才能排上去。kind 的 control-plane 就有一個，所以練習的 Pod 不會排到它（第 9 課）。
  • nodeSelector／affinity：Pod 指定「只能排到有某個 label 的節點」，例如 nodeSelector: {disktype: ssd}。沒有任何節點有這個 label，Pod 就永遠 Pending，事件寫 0/3 nodes are available: 3 node(s) didn't match Pod's node affinity/selector。
  • finalizer：寫在物件 metadata.finalizers 裡的標記，意思是「刪除前有人要先做清理」。物件會先被標上 deletionTimestamp（顯示 Terminating），等負責的控制器做完清理、把標記拿掉，才真的刪除。控制器壞了或被移除，物件就卡住。
遇到 Terminating 卡住，網路上常見的解法是 kubectl delete pod --grace-period=0 --force 或把 finalizers 清空。官方文件提醒：強制刪除時 API server 不等 kubelet 確認容器已經停止，節點恢復後舊容器可能還在跑。對 StatefulSet 這種「同一個名字只能有一個」的工作負載，會造成兩個同名的程序同時寫資料。先確認節點真的不會回來、或負責 finalizer 的控制器為什麼沒做完，再決定要不要強制。

事件與上一次的 log

表裡大部分的「去哪裡看」都是兩個地方：事件，以及容器上一次結束的紀錄。

事件

describe pod 最下面的 Events 只列這個 Pod 的事件。看整個 namespace、照時間排，用 kubectl events：

kubectl events -n k8s-14-a --types=Warning              # 只看警告
LAST SEEN             TYPE      REASON   OBJECT                          MESSAGE
80s (x4 over 2m58s)   Warning   Failed   Pod/cafe-api-855c47df6c-wg775   Failed to pull image "learn-k8s/cafe-api:v1.0": ... pull access denied, repository does not exist or may require authorization ...
80s (x4 over 2m58s)   Warning   Failed   Pod/cafe-api-855c47df6c-wg775   Error: ErrImagePull
13s (x10 over 2m57s)  Warning   Failed   Pod/cafe-api-855c47df6c-wg775   Error: ImagePullBackOff

kubectl events -n k8s-14-c --for pod/cafe-api-748885bcc4-bjkh6    # 只看一個物件
kubectl get events -n k8s-14-d --sort-by=.lastTimestamp           # 舊寫法，一樣能排序

讀法：真正的原因在第一行。ErrImagePull、ImagePullBackOff 只是後續的狀態；pull access denied, repository does not exist 的意思是 registry 找不到這個名字或 tag（它不會告訴你是不存在還是沒權限，兩個都要查）。x4 over 2m58s 是同一個事件重複了 4 次。

事件有保存期限：kube-apiserver 的 --event-ttl 預設 1 小時，過了就被刪掉。半夜出的事，早上再查就只剩 log。所以正式環境會把事件也收進 log 系統（devops 課第 21 課），這是建置可觀測性時常被漏掉的一塊。

上一次的容器：logs --previous 與 lastState

容器一直重啟時，kubectl logs 看到的是目前這一次的容器，它可能剛啟動、什麼都還沒印。崩潰的原因在上一次：

kubectl logs -n k8s-14-c deploy/cafe-api --previous     # 上一次容器的 stdout／stderr
kubectl describe pod -n k8s-14-c -l app.kubernetes.io/name=cafe-api
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137

這一組的 logs --previous 什麼都沒有：容器在 Node 還沒印出第一行就被核心殺掉了。沒有 log 本身就是線索：應用自己出錯（exit 1）幾乎都會留下錯誤訊息，被 SIGKILL 的程序沒機會寫任何東西。這時 lastState 的 reason 與 exit code 就是唯一的證據。

exit code 的讀法：0 是正常結束；1～125 是程式自己決定的（Node 未處理的例外是 1）；大於 128 的是「被訊號結束」，減掉 128 就是訊號編號，137＝SIGKILL（9），143＝SIGTERM（15），139＝SIGSEGV（11，記憶體存取錯誤，常見於原生模組）。137 不一定是 OOM：liveness 失敗、寬限期到了還沒結束，kubelet 也是用 SIGKILL，所以要看 reason 是不是 OOMKilled。

進到容器裡：exec、臨時容器與節點

事件與 log 不夠時，才需要到容器裡面看：檔案在不在、環境變數是什麼、從這個容器連得到資料庫嗎。第 2 課的 kubectl exec -it pod -- sh 前提是映像裡有 shell。越來越多正式環境的映像是 distroless：只有應用與它的執行環境（例如 node），沒有 shell、套件管理器和常用工具。攻擊者進來能用的工具少，映像也小，代價就是 exec 進不去：

kubectl exec -n k8s-14-f deploy/cafe-hash -- sh
error: ... OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH

ephemeral container（臨時容器）

ephemeral container（臨時容器）是加進一個執行中 Pod 的除錯容器，用你指定的映像（例如有 shell 和工具的 busybox），不需要重啟 Pod。1.25 起是 Stable。--target 讓它跟目標容器共用程序空間（process namespace），看得到對方的程序：

kubectl debug -it -n k8s-14-f pod/cafe-hash-5db76cc546-4nc4m --image=busybox:1.38.0 --target=api
/ # ps
PID   USER     TIME  COMMAND
    1 65532     0:01 {MainThread} /nodejs/bin/node server.ts   ← api 容器的 node
   28 root      0:00 ps
/ # tr '\0' '\n' < /proc/1/environ                  ← node 實際拿到的環境變數
/ # ls /proc/1/root/app                               ← 透過 /proc 看 api 容器的檔案系統

/proc/1/environ 是 PID 1 啟動時的環境變數，以 \0 分隔，所以用 tr 換成換行。這裡看到的是容器實際拿到的值：映像的 ENV、Pod 的 env、Service 自動注入的變數合在一起，比讀 manifest 可靠。

讀別的使用者的 /proc/1/environ 需要 SYS_PTRACE 這個 capability。kubectl 用 --profile 決定臨時容器的權限，本課程的 kubectl 1.36 預設是 general，會加上 SYS_PTRACE；舊的 legacy 與 baseline 不加，讀的時候會得到 Permission denied。在這個叢集實測：

--profile臨時容器的 securityContextcat /proc/1/environ
general（1.36 的預設）capabilities.add: [SYS_PTRACE]讀得到
baseline沒有額外權限Permission denied
legacy（已棄用，預計 1.39 移除）沒有額外權限Permission denied

臨時容器的限制：加上去就移除不了，會一直留在 Pod 的 spec.ephemeralContainers，直到 Pod 被刪除；它沒有 port、probe、resources，也不會被重啟。所以名字不能重複（不指定 -c 時 kubectl 會自動取 debugger-xxxxx）。

不想互動、只要一次輸出時，不加 -it，改用 --attach：指令跑完容器就結束，太快結束 attach 不上時 kubectl 會改讀它的 log（會印一行 falling back to streaming logs 的 warning），一樣拿得到輸出。練習 2 就用這個寫成腳本。

複本與節點

  • kubectl debug pod/x --copy-to=x-debug ...：建一份 Pod 的複本，可以換映像（--set-image）或改容器的指令。適合一啟動就崩潰的容器：把指令換成 sleep 3600，進去手動執行看錯在哪。複本不屬於 Deployment，也不在 Service 的流量裡，查完要自己刪掉。
  • kubectl debug node/learn-k8s-worker -it --image=busybox:1.38.0：在節點上建一個 Pod，跑在節點的程序與網路空間，節點的根目錄掛在 /host。可以看 /host/var/log/pods/、用 chroot /host crictl ps 看節點上的容器。這個 Pod 建在目前的 namespace（沒指定就是 default）、名字是 node-debugger-…，用完要自己 kubectl delete pod。
exec、debug、port-forward 都是高權限操作：能 exec 就能讀容器裡的所有機密，能 debug node 幾乎等於拿到節點的 root。正式環境只給值班人員（第 12 課的 RBAC：pods/exec、pods/ephemeralcontainers、pods/portforward 這些子資源），並開啟 API server 的稽核 log，事後查得到誰在什麼時候進去做了什麼。

縮小範圍：從入口一路往 Pod

Pod 都是 1/1 Running，使用者還是看到錯誤，問題就在 Pod 和使用者之間。請求的路徑是 Gateway → HTTPRoute → Service → EndpointSlice → Pod（第 4、5 課）。不要從中間亂猜，用「切一刀，看前半段還是後半段壞」的方式縮小範圍：

  1. 直接打 Pod，跳過 Service 與 Gateway： 
    kubectl port-forward -n k8s-14-e pod/cafe-api-5b97d7c48f-vzzcs 18140:3000
curl localhost:18140/version          # 另開一個終端機
{"version":"v1","instance":"cafe-api-5b97d7c48f-vzzcs"}
    成功：應用本身沒問題，問題在 Pod 之外。失敗：回到上一節，看應用的 log。
  2. 從叢集內打 Service： 
    kubectl exec -n k8s-tools deploy/probe -- curl -sS -m 5 http://cafe-api.k8s-14-e.svc.cluster.local/version
curl: (7) Failed to connect to cafe-api.k8s-14-e.svc.cluster.local:80 after 30 ms: Could not connect to server
    Pod 好、Service 壞：看 EndpointSlice（第 4 課的順序）。 
    kubectl get endpointslice -n k8s-14-e -l kubernetes.io/service-name=cafe-api
NAME             ADDRESSTYPE   PORTS     ENDPOINTS   AGE
cafe-api-69s9h   IPv4          <unset>   <unset>     2m58s
kubectl describe service -n k8s-14-e cafe-api | grep Selector
Selector:   app.kubernetes.io/name=cafe
    ENDPOINTS 是空的，Selector 是 cafe，Pod 的 label 是 cafe-api。
  3. Service 也好，從外面還是失敗：問題在入口。看 Gateway、HTTPRoute 的 status 與 conditions（第 5 課）。

注意 kubectl port-forward svc/cafe-api 不會經過 Service：kubectl 只是用 Service 的 selector 挑一個 Pod 直接連。selector 挑不到 Pod 時，它會等 --pod-running-timeout（預設 1 分鐘）後印出 timed out waiting for the condition。要測 Service 本身，從叢集裡的 Pod 用 Service 的名字 curl。

反方向：Pod 是 0/1、log 寫著連不到資料庫或 Redis 時，從「呼叫端」那個 Pod 往外查：

  • 名字查不到（ENOTFOUND、EAI_AGAIN）：在同一個 namespace 的 Pod 裡 nslookup postgres（distroless 就用臨時容器）。查不到，看名字與 namespace 對不對；namespace 有預設拒絕的 NetworkPolicy 時，看有沒有放行到 CoreDNS 的 53 port（第 12 課）。
  • 查得到但連線逾時：多半是 NetworkPolicy 擋住。kubectl get networkpolicy -n <ns>，對照呼叫端與目標的 label。連線被拒（ECONNREFUSED）則是目標沒在聽那個 port。
  • 呼叫 Kubernetes API 得到 403 Forbidden：是 RBAC。用 kubectl auth can-i get configmaps -n <ns> --as system:serviceaccount:<ns>:<sa> 確認那個 ServiceAccount 的權限。
💡 實務上：找平台團隊之前，先切出是哪一段壞
Pod 都 Running，使用者還是看到 502，很容易直接說「叢集網路有問題」，請平台團隊來看。這種回報查到最後，很多是應用自己的 Service selector 或 NetworkPolicy 寫錯。先照上面的順序切一次：直接打 Pod 成功、從叢集內打 Service 失敗、EndpointSlice 是空的，問題就在你自己的 manifest。真的要找平台團隊時，帶著這幾步的結果，他們可以直接從 Gateway 或節點那一段開始查。

修在宣告裡，然後寫事故紀錄

找到根因後，最快的修法通常是 kubectl edit deployment 把錯的值改掉，服務也真的恢復了。問題是叢集的狀態跟 git 裡的 manifest 不一樣了：下一次 CI 部署會把錯誤的 manifest 再套用一次，同樣的事故再發生一次，而且這次沒人想得到原因（第 1 課：宣告的檔案才是真相）。正確的順序：

  1. 止血：讓使用者先恢復。最常用的是 kubectl rollout undo 回到上一個好的版本（第 3、9 課），或把流量切走。止血可以在叢集上直接做，但要記下做了什麼。
  2. 修在宣告裡：在 manifest 或 Helm chart（第 13 課）修正根因，經過 code review，走正常的 CI 部署。之後的 GitOps（第 15 課）還可以設定成自動把叢集上的手動修改改回去。
  3. 驗證：部署後確認 Pod Ready、請求成功，不是「應該好了」。
  4. 寫事故紀錄：devops 課第 25 課的格式。重點不是追究誰打錯字，而是讓同樣的錯進不了叢集。

修的時候也要分清楚「修正根因」與「讓症狀消失」：

根因讓症狀消失（不要這樣做）修正根因
readinessProbe 打錯路徑刪掉 readinessProbe，Pod 馬上變 Ready改成正確的路徑；之後壞掉的 Pod 才會被移出流量
記憶體 limit 太小拿掉 limit依量測調到夠用，加上 heap 上限
Secret 的 key 打錯加 optional: true，Pod 起得來改成 Secret 裡真正的 key；密碼是空的，問題只是延後到連資料庫時才爆
liveness 太嚴，一直被殺拿掉 liveness改用 startupProbe 保護啟動期、放寬 failureThreshold（第 7 課）

事故紀錄的六個部分：時間軸（幾點發生、發現、找到原因、止血、修好）、影響（誰、多久、多少請求）、偵測（怎麼發現的，是告警還是使用者回報；偵測慢本身就是一個問題）、根因、修正、行動項目（每一條有負責人，至少一條是自動化的檢查）。行動項目的好壞差很多：

  • 「部署前多檢查」「大家注意 Secret 的 key」：靠人記得，下次換人就忘了。
  • 「CI 加 kubeconform 與 policy 檢查」「部署步驟加 kubectl rollout status --timeout，沒完成就失敗並回滾」「Secret 的 key 改由 chart 的 values 統一產生」：讓同一類錯誤在進叢集前就被擋下，或發生時自動恢復。

練習

在 learn 資料夾先執行 export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"，再執行一次頁面上的指令，起始檔會複製到 kubernetes/practice/work/14/。然後執行 bash kubernetes/practice/work/14/break.sh：它把六組壞掉的服務部署到 k8s-14-a～k8s-14-f（第一次要建置映像，約 2～3 分鐘）。用前面的流程查，查完在 work/14/ 修檔案。你可以把改好的檔案 kubectl apply 到同一個 namespace 確認；測試則會在自己的 namespace（k8s-14-ex1-a 這種名字）重新套用你的檔案。全部做完執行 kubectl delete namespace k8s-14-a k8s-14-b k8s-14-c k8s-14-d k8s-14-e k8s-14-f。

練習 1 的根因代碼，從這裡選（不是每個都會用到）：

image-tag-typo        image-pull-auth        missing-secret-key     missing-configmap
oom-limit             readiness-wrong-path   liveness-too-strict    selector-mismatch
target-port-wrong     networkpolicy-dns      node-selector-unsatisfiable
quota-exceeded        pvc-wrong-storageclass

練習 1：五個故障。k8s-14-a～k8s-14-e 各有一組壞掉的 cafe-api，來源 manifest 是 ex1/a/～ex1/e/。每一組照流程找出根因，在 diagnosis.json 填上 cause（上面的根因代碼）與 evidence（你看到證據的那一行 kubectl 指令），再修改該組資料夾的 manifest 讓服務恢復。要修正根因：不能拿掉 readinessProbe 或 limits.memory、不能把 Secret 參照設成 optional，第 a 組要部署的是 learn-k8s/cafe-api:v1。測試先檢查診斷與檔案，再把五組套用到全新的 namespace（第 b 組的 Secret 由測試建立），每組的 Pod 要 Ready，從叢集內經過 Service 的請求要成功。

練習 2：沒有 shell 的映像。k8s-14-f 的 cafe-hash 是 distroless 映像，GET /hash 在併發時很慢；它的 UV_THREADPOOL_SIZE（libuv thread pool 的執行緒數，pbkdf2 在這裡算）與 NODE_OPTIONS 寫在映像的 ENV 裡，manifest 看不到。先手動用 kubectl debug 找出來，再把做法寫成 ex2/inspect.sh：bash inspect.sh <namespace> 找出 app=cafe-hash 的 Pod，用 busybox:1.38.0 的臨時容器（--target=api）讀 /proc/1/environ，印出 UV_THREADPOOL_SIZE=… 與 NODE_OPTIONS=… 兩行。然後在 ex2/deployment.yaml 不換映像，用 env 把 UV_THREADPOOL_SIZE 改成 "4"。測試會建置一個 ENV 是隨機值的映像來跑你的腳本（猜或寫死都過不了），確認 Pod 上真的加了臨時容器；再套用你的 deployment，GET /config 回報的 UV_THREADPOOL_SIZE 要是 4。

練習 3：事故紀錄。從 a～e 挑一組你覺得最嚴重的，假設它發生在正式環境，在 INCIDENT.md 照六個標題寫：時間軸至少 4 個時間點（例如 - 14:05 部署）；影響、偵測、修正都要有具體內容；根因寫出 diagnosis.json 裡那一組的根因代碼並說明它怎麼造成症狀；行動項目至少 2 條（用 - 開頭），其中至少一條是自動化的檢查（CI、kubeconform、policy…）。

練習 4：Pod 是 CrashLoopBackOff，kubectl logs 什麼都沒印出來。下一步最該看什麼？

✓ logs 看的是剛重啟、可能還沒輸出的這一次容器；崩潰的線索在上一次的 log 與 lastState（OOMKilled／137 是被殺，exit 1 是應用自己結束）。上一次也沒有 log 時，reason 與 exit code 就是唯一的證據。刪 Pod（a）會讓這些證據消失，重建的 Pod 一樣會壞；重啟節點（c）影響其他服務、也不解決設定錯誤；改 restartPolicy（d）只是讓它不再重啟，Deployment 的 Pod 也不允許設成 Never。

練習 5：Pod 一直 Pending，事件寫 0/3 nodes are available: 3 node(s) didn't match Pod's node affinity/selector。最可能是？

✓ 排程失敗的原因直接寫在 FailedScheduling 事件裡，這一句就是「沒有節點有你要的 label」。用 kubectl get nodes --show-labels 對照 Pod 的 nodeSelector。記憶體不夠（c）會寫 Insufficient memory；拉映像（a）與 readiness（d）都是排上節點之後才會發生的事，Pending 階段還輪不到它們。

練習 6：服務掛掉，你用 kubectl edit 把 Deployment 的錯誤映像改回來，服務恢復了。還缺什麼？

✓ 叢集上的手動修改只是止血，git 裡的 manifest 還是錯的，下一次 CI 部署會再套用一次。修在宣告裡、走正常部署，再用事故紀錄的行動項目防止同類錯誤。a 會在下一次部署重演同一個事故；c、d 對已經恢復的服務沒有幫助，只會增加風險。

練習 7：映像是 distroless，kubectl exec -it pod -- sh 回傳 executable file not found。怎麼進去看？

✓ 臨時容器（1.25 Stable）就是為這種情況設計的：不重啟 Pod，帶著自己的工具進去，--target 讓它看得到目標容器的程序與 /proc/1/environ。attach（c）只是接上主程序的輸入輸出，沒有 shell 可用；換映像（d）會改變你正在查的東西、要重新部署，也太慢。

常見錯誤

  • 第一步就刪 Pod 或重啟：事件、上一次的 log、lastState 跟著消失，設定錯誤在新 Pod 照樣發生。先 describe、logs --previous，需要止血用 rollout undo。
  • 只看最新的 log：一直重啟的容器，崩潰原因在上一次的輸出；連上一次都沒有 log，就看 lastState 的 reason 與 exit code。
  • 把狀態字當成原因：CrashLoopBackOff、ImagePullBackOff 是症狀。事故紀錄與診斷要寫到「哪個設定錯了」。
  • 以為 Running 就是正常：看 READY 欄位與 EndpointSlice。0/1 的 Pod 不收流量，1/1 的 Pod 也可能沒被任何 Service 選到。
  • 用 port-forward svc/ 測 Service：它只是挑一個 Pod 直接連，不經過 Service。測 Service 要從叢集內的 Pod 用名字 curl。
  • 修在叢集上：kubectl edit 的修改，下一次部署就被蓋回去。修在 manifest／chart，走正常部署。
  • 用拿掉 probe、limit 或加 optional 讓問題消失：症狀不見了，根因還在，而且之後出事更難發現。
  • 以為事件會一直在：預設只保留 1 小時。正式環境要把事件收進 log 系統。
  • 強制刪除 Terminating 的 Pod 前不查原因：節點可能還在跑舊容器；先看 finalizers 與節點狀態。
  • debug node 之後忘了清：node-debugger-… Pod 會一直留著，帶著節點的權限。用完就刪。

小結

  • 固定順序：get pods -o wide → describe 與 kubectl events → logs --previous 與 lastState → exec 或 kubectl debug → Service、DNS、NetworkPolicy、RBAC。先蒐證、一次改一個變數、記下時間。
  • 狀態字只指出去哪裡看：Pending 看 FailedScheduling；ImagePullBackOff、CreateContainerConfigError 看 Failed 事件；CrashLoopBackOff、OOMKilled 看上一次的 log 與 exit code（137＝SIGKILL）；0/1 看 Unhealthy 事件；1/1 卻不通看 EndpointSlice。
  • 沒有 shell 的映像用臨時容器：kubectl debug -it pod/x --image=busybox:1.38.0 --target=api，從 /proc/1/environ、/proc/1/root 看目標容器；--profile=general 才有讀它需要的 SYS_PTRACE。--copy-to 建可以改指令的複本，debug node/… 看節點，用完要清掉。
  • 縮小範圍：直接打 Pod（port-forward pod/）→ 從叢集內打 Service → 入口；呼叫端連不出去時查 DNS、NetworkPolicy、auth can-i。
  • 止血可以在叢集上做，修正一定要回到 manifest／chart 走正常部署；事故紀錄寫時間軸、影響、偵測、根因、修正、行動項目，行動項目要有自動化的檢查。
