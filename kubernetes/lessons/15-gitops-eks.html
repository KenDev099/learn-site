階段 5：正式環境與期末專題 · 第 15 課

GitOps 與 EKS：正式環境的叢集怎麼運作（資深）

到目前為止，部署都是你（或你的腳本）下指令：kubectl apply、helm upgrade。在公司的正式叢集，這樣做會遇到三個問題：CI 要拿著能改正式叢集的憑證；誰在什麼時候改了什麼，只散落在各個人的終端機；有人半夜手動改了設定，沒人知道，下次部署又被蓋掉。另一方面，正式叢集不是 kind，而是雲端代管的叢集，例如 AWS 的 EKS，它有自己的網路、身分、費用與升級規則。

這一課學兩件事。GitOps：讓 git 成為唯一的真相，叢集裡的 Argo CD 自己把叢集調整成 git 的樣子。EKS：你在 kind 學的每個概念，在 EKS 上對應到什麼，以及怎麼規劃一次不出事的版本升級。

這課的路線：
  1. 從 push 到 pull：CI 拿著正式叢集的憑證直接部署有什麼問題，GitOps 怎麼反過來讓叢集自己去讀 git。
  2. Argo CD 的 Application、drift 與 selfHeal：怎麼告訴 Argo CD 部署哪個 repo 的哪個路徑；半夜手動加的副本為什麼幾秒後被改回去，救火也要走 git。
  3. CI 與 GitOps 的分工：CI 只建映像、開 PR，不碰叢集。
  4. 從 kind 到 EKS：同樣的物件在 EKS 底下換成什麼，Pod 多了為什麼子網路的 IP 會用完，費用花在哪裡。
  5. 版本與升級、和平台團隊合作：每年都要排的叢集升級怎麼做才不出事，交付服務前用哪份清單檢查自己。
這課會用到：
  • 第 1 課的期望狀態與控制迴圈：你宣告要的結果，控制器一直比對實際狀態、把差異改回來。
  • 第 13 課的 Helm chart：一份範本加上每個環境的 values 檔，部署時用 --set image.tag=… 指定版本。
  • devops 課第 18 課的 AWS 網路：VPC 是自己的私有網路，切成公有、私有子網路，私有子網路的機器經過 NAT Gateway 連外，對外流量由負載平衡器接。
  • devops 課第 19 課的 IAM：人和程式都用 IAM 角色拿短期憑證，政策決定能做什麼。

從 push 到 pull：GitOps 是什麼

devops 課第 16 課的部署是 push 型：CI 建好映像，接著自己連上伺服器（或叢集）去部署。換到 Kubernetes，就是 CI 裡有一步 kubectl apply 或 helm upgrade，而 CI 必須持有正式叢集的憑證。

GitOps 反過來，是 pull 型：叢集裡跑一個代理程式，它定期讀 git，把叢集調整成 git 描述的樣子。CI 只負責建置映像，再把「prod 要用這個新版本」寫進 git。GitOps 的四個原則：

  1. 宣告式：整個系統用期望狀態描述（第 1 課的 YAML），不是一串指令。
  2. 版本化在 git：期望狀態存在 git，每次變更都是一個 commit，有作者、時間、review。
  3. 自動拉取：代理程式自己從 git 拉，不用外部推進來。
  4. 持續調和：代理程式一直比對 git 與叢集，不一樣就修正，也就是第 1 課的控制迴圈，只是期望狀態從 etcd 換成了 git。

這樣換來的好處：

  • CI 不需要正式叢集的權限：CI 是最常被攻擊的地方之一（第三方 action、外部 PR）。CI 被入侵，最多能開一個 PR，還要有人 review 才會合併。
  • 每次變更都有紀錄：「prod 現在跑哪一版」看 config repo 就知道；「誰改的」看 commit。
  • 回滾就是 git revert：把 image tag 改回上一版的 PR，合併後 Argo CD 自己同步。
  • 偵測手動修改：叢集跟 git 不一樣，Argo CD 會顯示出來，可以設定自動改回去。

代價：多一個要維運的元件（Argo CD 本身），部署多了「開 PR、合併、等同步」幾個步驟，救火時不能直接 kubectl edit（下一節）。小團隊只有一個叢集時，CI 用最小權限的部署角色直接 helm upgrade 也是合理的選擇；叢集與團隊一多，GitOps 的紀錄與權限分離才值回成本。

常見的 GitOps 工具有兩個：Argo CD（有網頁介面，這課用它）和 Flux（沒有內建介面，全部用 Kubernetes 物件設定）。Argo CD 目前維護 3.5、3.4、3.3 三條版本線，最新是 v3.5.6。

Argo CD 的 Application

Argo CD 用一個自訂資源 Application 描述「哪個 repo 的哪個路徑，要部署到哪個叢集的哪個 namespace，用什麼規則同步」。Application 物件放在 Argo CD 所在的 namespace（通常是 argocd），它本身也存在 git 裡。

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cafe-staging
  namespace: argocd
spec:
  project: cafe                      # AppProject：平台團隊限制這個團隊能用哪些 repo、部署到哪些 namespace
  source:
    repoURL: https://github.com/example-cafe/cafe-config
    path: charts/cafe                # repo 裡 chart 的資料夾（第 13 課寫的 chart）
    targetRevision: main             # 要讀哪個分支、tag 或 commit
    helm:
      valueFiles:
        - values-staging.yaml        # 相對於 chart 的資料夾
  destination:
    server: https://kubernetes.default.svc   # Argo CD 所在的叢集
    namespace: cafe-staging
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true         # namespace 不存在就建立

幾個要做判斷的欄位：

  • targetRevision：寫分支（main）時，合併就上線，適合 staging。prod 釘 tag 或 commit SHA：看設定就知道 prod 跑哪一版，回滾有明確的目標，也不會有人誤合併就直接上 prod。不要用 HEAD：等於「預設分支的最新 commit」，看不出版本。
  • project：default 專案什麼都允許。正式環境由平台團隊為每個團隊建 AppProject，限制來源 repo 與目的 namespace，一個團隊寫錯 Application 不會部署到別人的 namespace。
  • sync（同步）：把叢集調整成 git 的樣子。沒有 automated 時，要有人在介面上按 Sync。
  • prune：git 裡刪掉的資源，叢集也刪掉。預設不刪，因為刪除比較危險；不開的話，改名或移除的 CronJob、Service 會一直留在叢集。
  • selfHeal：叢集被人手動改了，自動改回 git 的樣子（下一節）。

Argo CD 對每個 Application 顯示兩種狀態，分開看：

狀態值意思
同步狀態Synced／OutOfSync叢集跟 git 一不一樣
健康狀態Healthy／Progressing／Degraded／Missing資源本身好不好：Deployment 更新完成且可用是 Healthy，正在滾動更新是 Progressing，Pod 一直起不來是 Degraded

「Synced 但 Degraded」很常見：git 裡的設定已經套上去了，可是新版本起不來（第 14 課的 CrashLoopBackOff）。同步成功不等於服務正常。

順序：第 10 課的 migration 要比新版本先跑。Argo CD 用 annotation 控制：argocd.argoproj.io/hook: PreSync 讓 Job 在同步前執行（失敗就停止同步），argocd.argoproj.io/sync-wave: "-1" 這類數字讓資源依波次套用，小的先。

一個團隊有很多服務、很多環境時，Application 會有幾十個。app of apps 是用一個 Application 指向「放了很多 Application YAML 的資料夾」；ApplicationSet 用範本加產生器（例如列出每個環境）一次產生多個 Application。兩者都是平台團隊常用的管理方式，你多半只會在既有的結構裡加一個值檔或一個 Application。

這門課不在本機安裝 Argo CD：它有十幾個元件，會吃掉 kind 叢集不少記憶體。練習只用 kubeconform 檢查 Application 的結構；想實際玩的話，照 Argo CD 官方文件安裝到一個新的 namespace，用完刪掉。

drift 與 selfHeal：救火也要走 git

drift（漂移）是叢集的實際狀態偏離了 git 的宣告。情境：半夜流量暴增，值班的人 kubectl scale deployment cafe-api --replicas=10。開了 selfHeal 時，Argo CD 幾秒後發現 replicas 跟 git 的 3 不一樣，把它改回 3。

這是設計上的行為，不是 bug。git 是唯一的真相，叢集上的手動修改都算 drift。正確的處理：

  • 平常：副本數交給 HPA（第 8 課），救火時改 HPA 的 maxReplicas 也是開 PR。
  • 緊急：先暫停這個 Application 的自動同步（在介面關掉，或把 automated.enabled 設成 false），在事故頻道記下「幾點、誰、為什麼暫停」，止血後把修正寫回 git，再恢復自動同步。暫停卻忘了恢復，之後的部署都不會上線，所以要有人負責。

HPA 本身也會造成 drift：它一直在改 Deployment 的 spec.replicas。如果 chart 輸出了 replicas（第 13 課提醒過不要），Argo CD 會跟 HPA 搶。即使 chart 沒輸出，也建議在 Application 宣告忽略這個欄位：

spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true

ignoreDifferences 預設只影響「算不算 OutOfSync」；真的同步時（例如換了新 tag），Argo CD 還是把整份期望狀態套上去，replicas 會被寫回 git 的值。加上 RespectIgnoreDifferences=true，同步時也會略過這些欄位（資源已經存在時才有效）。

比對「一不一樣」時還有一個細節：YAML 的欄位順序不代表任何意思，{cpu, memory} 和 {memory, cpu} 是同一個設定。用 JSON.stringify 比對就會出錯：

💡 實務上：一直 OutOfSync，先看是誰改的
Argo CD 上某個 Application 永遠是 OutOfSync，不一定是有人手動改了叢集。常見的來源是其他控制器：HPA 改 replicas，某些工具的 mutating webhook 在 Pod 範本注入 sidecar 或 annotation。處理前先打開 Argo CD 的 diff，看是哪幾個欄位不一樣、是誰改的，再用 ignoreDifferences 只忽略那幾個欄位；整個資源一起忽略，真正的 drift 就看不到了。如果 diff 顯示的是人改的（例如 resources 被調大），那是一次救火還沒寫回 git，要找到當事人把它變成 PR。

CI 與 GitOps 的分工

常見的做法是兩個 repo：app repo 放程式，config repo 放 chart、每個環境的值檔與 Application。分開的原因：改程式的人很多，能改 prod 設定的人比較少，權限可以分開設；Argo CD 只要讀 config repo。

app repo 的 CI（devops 課第 15 課的 GitHub Actions）在合併到 main 後做三件事：

  1. 建置並推送映像，tag 用這次的 commit SHA（devops 課第 16 課）。
  2. 取出 config repo，用 yq（命令列的 YAML 編輯工具，GitHub 的 ubuntu-24.04 runner 已內建 4.54.1）只改一個欄位：yq -i '.image.tag = strenv(TAG)' charts/cafe/values-prod.yaml。strenv(TAG) 讀環境變數 TAG 並當成字串。yq 會保留檔案的註解與排版，PR 的差異只有一行。
  3. 推到新分支，用 GitHub CLI（gh pr create）開 PR。

要注意權限：每個 workflow 自動拿到的 GITHUB_TOKEN 只能操作自己這個 repo，推不到 config repo。要另外建一把只對 config repo 有「內容寫入、開 PR」權限的 token（GitHub App 或 fine-grained token），存成 secret，例如 CONFIG_REPO_TOKEN。它的權限比「正式叢集的 admin」小得多，而且改動還要經過 PR review。

staging 可以讓 PR 自動合併，prod 要人核准。合併之後，Argo CD 在幾分鐘內（預設每 3 分鐘內檢查一次 git，也可以設 webhook 立刻通知）偵測到新 commit 並同步。

💡 實務上：出事時 revert 哪一個 repo
prod 上了壞版本，直覺是去 app repo revert 那個 commit。但那樣要重新跑測試、建置映像、再開一次 config repo 的 PR，十幾分鐘後才會上線。止血要 revert 的是 config repo 裡改 image tag 的那個 commit：上一版的映像還在 registry，Argo CD 同步完就回去了。程式的修正再照正常流程從 app repo 走一次。值班 runbook 要寫清楚 config repo 在哪、誰有權限合併 prod 的 PR，半夜才不會卡在找人核准。

從 kind 到 EKS

EKS（Amazon Elastic Kubernetes Service）是 AWS 代管的 Kubernetes：AWS 負責控制平面，你負責節點上的工作負載。叢集本身通常用 OpenTofu 建立（devops 課第 20 課）。你在 kind 學的物件（Deployment、Service、HTTPRoute、PVC、RBAC）在 EKS 上完全一樣，不同的是底下的實作：

項目這門課的 kindEKS對你的影響
控制平面control-plane 容器，看得到 etcd 的 PodAWS 代管、跨可用區，看不到 etcd 與控制平面節點不用備份 etcd、不用維護 API server；按叢集每小時收費（標準支援 0.10 美元、延伸支援 0.60 美元）
節點Docker 容器EC2：managed node group、Karpenter、Auto Mode；或 Fargate見下方
網路（CNI）kindnet，Pod 用叢集內部網段VPC CNI：每個 Pod 直接拿 VPC 子網路的 IPPod 多了子網路會用完 IP，新 Pod 卡在 ContainerCreating；建 VPC 時要規劃夠大的 CIDR
對外流量cloud-provider-kind 開 Envoy 容器AWS Load Balancer Controller：Service 變成 NLB、Gateway 變成 ALB 或 NLB第 5 課的 Gateway／HTTPRoute 寫法不變；v3.0.0 起 Gateway API 支援 GA，最新 v3.6.2。每個負載平衡器按小時計費
儲存local-pathEBS CSI driver，常用 gp3EBS 磁碟只存在一個可用區，Pod 只能排到那個可用區的節點（第 11 課）

Pod 的 AWS 權限沒有Pod Identity（第 12 課），不需要 OIDC provider程式不用放 access key
可觀測性kubectl logs、topCloudWatch Container Insights，或自建 Prometheus＋Grafanalog 與指標要送出叢集，Pod 刪掉後還查得到

節點有四種提供方式，選擇取決於你想管多少：

  • managed node group：AWS 幫你管理一組 EC2（Auto Scaling group），升級時由 AWS 滾動替換節點，但什麼時候升級、用哪種機型由你決定。
  • Karpenter：開源的節點自動擴展工具。看到 Pending 的 Pod，直接開一台大小剛好的 EC2；節點閒置就收掉。省錢，但它本身要安裝與維護。
  • EKS Auto Mode：節點、擴展、負載平衡、區塊儲存都交給 AWS，控制平面升級後節點也由它逐步換新（會遵守 PDB）。除了 EC2 費用，還有依執行個體計算的管理費。
  • Fargate：每個 Pod 跑在自己的小虛擬機，沒有節點要管。限制多：不能跑 DaemonSet、不能用特權容器與 hostNetwork、不能掛 EBS、只能在私有子網路、不支援 Pod Identity（要用 IRSA）。

費用的大項：控制平面的時數、節點、NAT Gateway（私有子網路的節點拉映像、呼叫外部 API 都經過它，按時數加流量計費）、負載平衡器。每個 type: LoadBalancer 的 Service 都是一個獨立計費的負載平衡器，所以對外入口集中在少數幾個 Gateway。

版本與升級

Kubernetes 每年大約發佈三個小版本（1.35、1.36、1.37…）。EKS 每個版本有 14 個月的標準支援，之後是 12 個月要加錢的延伸支援（extended support）。目前標準支援 1.34～1.37、延伸支援 1.31～1.33；1.37 在 2026-10-01 上 EKS。延伸支援結束後，AWS 會自動把控制平面升到最舊的受支援版本，但節點群組不會跟著升。等到被迫升級最危險，所以要每年排兩三次升級，當成例行工作。

升級的規則（AWS 的升級文件）：

  • 一次只能升一個小版本：1.35 要到 1.37，必須 1.35 → 1.36 → 1.37。
  • 控制平面先，節點後：Kubernetes 的版本差距政策是 kubelet 可以比 API server 舊最多 3 個小版本，但不能比它新。EKS 更嚴格：升級控制平面之前，managed node group 和 Fargate 要先跟控制平面同版本。所以每升一版控制平面，就把外掛與節點跟上，再升下一版。
  • 開始後不能暫停：控制平面升級一旦開始就不能停；EKS 檢查失敗會自動退回原版本。升級後 7 天內可以退回上一個小版本，超過就只能新建叢集搬遷。
  • 需要空的 IP：升級時 EKS 要從叢集的子網路拿最多 5 個 IP，子網路用光了升級會失敗（又是 VPC CNI 的 IP 規劃問題）。

升級前的檢查：

  1. upgrade insights：EKS 會自動掃描叢集，列出已棄用 API 的呼叫、節點版本落後等問題。對照 Kubernetes 的已移除 API 清單（Deprecated API Migration Guide）：這份清單最後一次移除內建 API 是 1.32，但 CRD 與第三方外掛的 API 版本由它們自己的版本決定，一樣要查。
  2. 外掛：VPC CNI、CoreDNS、kube-proxy、Load Balancer Controller、Karpenter 都有對應 Kubernetes 版本的相容表。AWS 文件特別提到：VPC CNI 早於 1.8.0 的，要先升級再升叢集。
  3. PDB：節點升級就是一台一台 drain（第 9 課）。minAvailable 等於副本數（或 100%、maxUnavailable: 0）的 PDB 允許中斷 0 個 Pod，drain 會永遠卡住。
  4. 落後的節點群組：還停在舊版本的節點群組，要先升到跟控制平面同版本。

每一版的順序是：控制平面 → 外掛（升到對應這一版的建議版本）→ 節點（滾動替換，靠 PDB、多副本、分散規則、優雅關機做到不中斷）。先在 staging 叢集完整跑一遍，再升 prod。

實務：和平台團隊合作

在有一定規模的公司，叢集由平台團隊維運，你是使用叢集的應用團隊。分工大致是：

平台團隊應用團隊（你）
建立與升級叢集、節點、外掛；Argo CD 本身；AppProject、namespace、ResourceQuota；監控與 log 的基礎設施；Gateway 與憑證服務的 chart 與每個環境的值檔；Application；映像與 CI；服務的 dashboard、告警與 runbook；配合升級修正自己的設定

平台團隊排升級時，最常被卡住的是應用團隊的設定：PDB 堵死 drain、沒有 requests 讓新節點排不下、單一副本一換節點就中斷。交付一個服務前，用這份清單檢查自己（期末專題第 16 課要全部通過）：

  • resources 的 requests 與 memory limit（第 8 課）
  • readiness、liveness probe 與優雅關機（第 7 課）
  • 至少 2～3 個副本、PDB 留出可中斷的空間、topologySpreadConstraints 分散到不同節點與可用區（第 9 課）
  • securityContext 通過 restricted、專用的 ServiceAccount、NetworkPolicy（第 12 課）
  • 映像釘版本、設定與機密分開（第 6 課）
  • dashboard 與告警：出事時看得到、被叫得醒

開口問平台團隊時，帶著具體資料：「cafe-prod namespace 的 Pod 卡在 ContainerCreating，事件是 failed to assign an IP address」比「叢集壞了」快得多被處理。

練習

練習 1 在頁面上寫。練習 2～4 在 learn 資料夾執行頁面上的指令，起始檔會複製到 kubernetes/practice/work/15/。這三題都是靜態檢查，不需要叢集；練習 3 用 Docker 跑 actionlint（和 devops 課第 15 課同一個映像），並在暫存資料夾執行你寫的 yq 指令（需要 brew install yq）。

練習 1：寫出 Argo CD 每一輪的決定 planSync(desired, live, opts)。資源用 kind/namespace/name 當鍵（例如 Deployment/cafe/cafe-api）。desired 是 git 裡的資源，live 是叢集裡的資源，managedByApp: true 表示是這個 Application 建立的。規則：

  • git 有、叢集沒有：缺少。兩邊都有但 spec 不同：有差異。叢集有、git 沒有、而且 managedByApp：多出來。三者任一存在，outOfSync 就是 true。沒有 managedByApp 的資源不屬於這個 Application，不算差異，永遠不能刪。
  • 比對 spec 時，物件的欄位順序不算差異，陣列的順序算。opts.ignore 裡每一條 { kind, path }（path 是 /spec/replicas 這種 JSON pointer）對符合 kind 的資源，兩邊都不比這個欄位。
  • 要不要動手：opts.selfHeal 是 true，或 git 有新 commit（opts.revision 不等於 opts.syncedRevision）時才動手；否則全部只回報（三個陣列都空，outOfSync 照實回報）。動手時缺少的放 create、有差異的放 update；多出來的只有 opts.prune 為 true 才放 delete。
  • 三個陣列都放鍵、依字串排序。不能修改傳入的資料。

真正的 Argo CD 比這個多做幾件事：比對前會先正規化（例如補上 Kubernetes 自動填的預設值），依 sync wave 與資源種類排順序，套用後還要等健康狀態。但「git 是期望狀態、叢集是實際狀態、只做差額、有開關決定要不要動手」就是它的骨架，也是第 1 課控制迴圈的同一套想法。

練習 2：完成 ex2/cafe-prod.yaml，一個名為 cafe-prod、放在 argocd namespace、project 是 cafe 的 Application：部署 config repo https://github.com/example-cafe/cafe-config 的 charts/cafe，valueFiles 用 values-prod.yaml，targetRevision 是這次發佈的 tag release-2026.11.1；目的地是同一個叢集（https://kubernetes.default.svc）的 cafe-prod namespace。開啟自動同步並打開 prune 與 selfHeal，syncOptions 自動建立 namespace。prod 的 chart 開了 HPA：對所有 Deployment 的 /spec/replicas 設 ignoreDifferences，並讓同步時也遵守它。測試先用 kubeconform（含 Argo CD Application 的 schema，strict）檢查，再逐欄檢查。

練習 3：ex3/.github/workflows/release.yml 現在是 push 型：deploy job 拿 AWS 角色、產生 kubeconfig、直接 kubectl set image，映像還是 latest。改成 GitOps：build job 推的映像 tag 改用 ${{ github.sha }}；刪掉 deploy，寫一個 bump-config job（在 build 之後）：用 actions/checkout（同一個釘好的 SHA）以 repository: example-cafe/cafe-config、token: ${{ secrets.CONFIG_REPO_TOKEN }}、path: config 取出 config repo；用 yq 把 config/charts/cafe/values-prod.yaml 的 image.tag 改成這次的 SHA（用 step 的 env 傳入、yq 裡用 strenv）；最後在新分支 commit、push，用 gh pr create 開 PR（gh 讀 GH_TOKEN 環境變數）。最上層 permissions 只有 contents: read，所有 uses 釘 40 字元 SHA。測試跑 actionlint、檢查工作流程裡沒有 kubectl、helm upgrade、kubeconfig 或 AWS 部署角色，再到暫存資料夾實際執行你的 yq 指令，確認 values-prod.yaml 只有 image.tag 那一行改變。

練習 4：ex4/upgrade.json 的 cluster 是一個 EKS 1.35 叢集的現況（節點群組、外掛、PDB），不要改它。填兩個陣列，把它升到 1.37：

  • steps：依序寫出步驟代碼。可以用的代碼：check-insights（看 upgrade insights 與已棄用 API）、fix-blockers（排除阻擋項目）、cp-1.36、cp-1.37（升級控制平面到該版）、addons-1.36、addons-1.37（外掛升到對應該版的建議版本）、nodes-1.36、nodes-1.37（滾動替換所有節點群組到該版）。每個代碼都要用到、各一次。
  • blockers：開始升級前必須先處理的項目，格式 pdb/<名稱>、addon/<名稱>、nodegroup/<名稱>。沒有問題的項目不要列。

練習 5：Argo CD 開了 selfHeal。值班的人用 kubectl scale 把 cafe-api 從 3 個副本改成 10 個救火，幾秒後又變回 3 個。正確的做法是？

✓ GitOps 下 git 是唯一的真相，手動修改就是 drift，會被修回。長期解法是 HPA，緊急時只暫停這一個 Application 並留紀錄。a 影響所有服務的部署；c 跟 Argo CD 互相拉扯；d 在 EKS 根本碰不到 etcd，而且 Argo CD 比對的就是 API server 回報的狀態，照樣會改回去。

練習 6：公司的 EKS 叢集停在 1.33，延伸支援也到期了。會發生什麼事？

✓ AWS 文件：延伸支援結束後控制平面會被自動升級，外掛與節點群組要自己處理。被動升級時你沒有先在 staging 測過，也沒檢查 PDB 與外掛相容性，所以要主動規劃。延伸支援期間每小時的費用也比標準支援高。a、d 都不是 AWS 的行為；c 錯在控制平面會被強制升級。

練習 7：EKS 上的 cafe-api 尖峰擴展時，新的 Pod 一直卡在 ContainerCreating，事件寫著 failed to assign an IP address。最可能的原因？

✓ 這是 EKS 和 kind 很不一樣的地方：kind 的 Pod 用叢集內部的網段，EKS 的 Pod 佔用真的 VPC 位址。子網路太小會成為擴展的天花板，連控制平面升級都需要空的 IP。建 VPC 時就要規劃夠大的 CIDR，或請平台團隊加子網路。a、c 都不是事實；d 只是讓 Pod 變多，真正的限制是位址。

常見錯誤

  • targetRevision 用 HEAD 或 main 部署 prod：看不出 prod 跑哪一版，誤合併就直接上線。prod 釘 tag 或 commit。
  • CI 持有正式叢集的 admin 憑證：CI 被入侵就等於整個叢集被入侵。用 GitOps，CI 只能開 PR；或至少用只能部署單一 namespace 的最小權限角色。
  • GitOps 與 HPA 搶 replicas：chart 不輸出 replicas，Application 加 ignoreDifferences 與 RespectIgnoreDifferences。
  • 救火時直接 kubectl edit：開了 selfHeal 會被改回去，沒開則留下 git 不知道的設定。止血後一定要寫回 git。
  • 沒開 prune：git 裡刪掉的資源一直留在叢集，佔資源也讓人誤會。開 prune，並用 project 限制範圍。
  • 以為 EKS 會幫你升級節點：控制平面與節點分開升級，延伸支援到期也只會強制升控制平面。
  • 一次跳兩個小版本：EKS 一次只能升一個小版本，每一版都要把外掛與節點跟上再往下。
  • PDB 設成 minAvailable 等於副本數：drain 永遠卡住，整個叢集的升級被你的服務擋下。
  • 子網路太小：VPC CNI 的 Pod 用 VPC 的 IP，擴展與升級都會因為 IP 不夠失敗。
  • 沒算 NAT Gateway 與負載平衡器的費用：常是 EKS 帳單的大項。對外入口集中在少數 Gateway，不要每個服務一個 LoadBalancer。

小結

  • GitOps：宣告式、版本化在 git、叢集裡的代理程式自動拉取、持續調和。CI 不碰叢集，回滾是 git revert，手動修改會被偵測。
  • Argo CD 的 Application：source（repoURL、path、targetRevision、helm.valueFiles）、destination、syncPolicy（automated、prune、selfHeal、syncOptions）。同步狀態與健康狀態分開看；PreSync hook 與 sync wave 控制順序。
  • drift 是叢集偏離 git。selfHeal 會把它改回去，所以救火也走 git，緊急時暫停自動同步並留紀錄。HPA 管的 replicas 用 ignoreDifferences＋RespectIgnoreDifferences。
  • CI 建置映像（tag 用 commit SHA），用 yq 改 config repo 的 image.tag，用專屬 token 開 PR；Argo CD 在合併後同步。
  • EKS 和 kind 的物件一樣，底下不同：代管控制平面、四種節點（managed node group、Karpenter、Auto Mode、Fargate）、VPC CNI 用真的 IP、Load Balancer Controller 實作 Gateway、EBS 綁可用區、IAM 與 access entries、Pod Identity。
  • 升級：標準支援 14 個月＋延伸支援 12 個月；一次一個小版本；每一版控制平面 → 外掛 → 節點；先查 insights、外掛相容性、會卡住 drain 的 PDB、落後的節點群組。
  • 平台團隊管叢集，你管服務；交付前用 resources、probe、PDB、分散、securityContext、NetworkPolicy、告警這份清單檢查自己。
