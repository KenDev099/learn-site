階段 2：網路與設定 · 第 5 課

對外流量：Gateway API（以及 Ingress 為什麼退場）

上一課的 Service 讓叢集裡的程式用名字找到 cafe-api。但顧客在叢集外面：手機 App 打 https://cafe.test/products，網站打 https://cafe.test/，這些請求要有一個入口接住，依網域和路徑分給不同的服務，還要處理 HTTPS。在 devops 課，這個入口是 nginx；在 Kubernetes，入口是一組 API 物件，由控制器替你設定真正的代理伺服器。

這一課學 Kubernetes 官方的新一代入口 API：Gateway API，最後也會教你看懂舊專案的 Ingress、把它搬過來。

這課的路線：
  1. 入口要做什麼：nginx.conf 裡的網域、路徑、HTTPS、轉發，在 Kubernetes 變成哪些物件。
  2. Ingress 與 Gateway API、三種物件兩種角色：舊的 Ingress 卡在哪裡，平台團隊管入口、應用團隊管自己的路由，權限怎麼分開。
  3. 第一條 HTTPRoute 與比對規則：路由沒生效時怎麼讀 status，一個請求符合好幾條規則時送去哪裡，怎麼用權重做 90:10 的金絲雀上線。
  4. HTTPS：在入口解密，憑證只放一個地方，cafe-api 不用處理 TLS。
  5. 舊的 Ingress 怎麼搬：接手舊專案時讀懂它的 annotation，改寫成 HTTPRoute。
這課會用到：
  • 第 4 課的 Service：給一群 Pod 固定的名字，port 是 Service 自己的、targetPort 是容器的；LoadBalancer 類型在本機由 cloud-provider-kind 給位址，用 bin/url.mjs 查。
  • devops 課第 12 課的 nginx 反向代理：server_name 比對網域、location 比對路徑、proxy_pass 轉給後面的服務。
  • devops 課第 5 課的 TLS 憑證：憑證的 SAN 列出它對哪些網域有效，本機可以自己當 CA 簽一張。

入口要做什麼：從 nginx.conf 到 Kubernetes 物件

devops 課第 12 課的 nginx 設定，拆開來就是一個入口要做的四件事：

server {
    listen 443 ssl;                                  # 1. 在哪個 port、用什麼協定接請求
    server_name cafe.example.tw;                     # 2. 依網域（Host 標頭）分辨是哪個網站
    ssl_certificate     /etc/nginx/certs/fullchain.pem;   # 3. 在入口解密 HTTPS
    ssl_certificate_key /etc/nginx/certs/privkey.pem;
    location /api/ { proxy_pass http://api:3000/; }  # 4. 依路徑決定轉給哪個後端
    location /     { proxy_pass http://web:80; }
}

在 Kubernetes 裡你不寫 nginx.conf。你把這四件事寫成 API 物件交給叢集，一個控制器（第 1 課的控制迴圈）讀這些物件，替你設定真正處理流量的代理程式。對照表：

nginx.confGateway API誰負責
listen 443 sslGateway 的 listener：port、協定平台團隊
ssl_certificatelistener 的 tls.certificateRefs，指到一個存憑證的 Secret平台團隊
server_nameHTTPRoute 的 hostnames應用團隊
locationHTTPRoute 的 rules[].matches應用團隊
proxy_passHTTPRoute 的 backendRefs：Service 名稱與 port應用團隊

本機叢集的控制器是 cloud-provider-kind（第 4 課替 LoadBalancer Service 開 kindccm 容器的那個）。它看到一個 Gateway，就開一個跑 Envoy 的 kindccm 容器（Envoy 是一個跟 nginx 同類的代理伺服器），之後每次你改 HTTPRoute，它就把新的路由規則推給這個 Envoy。在 EKS 上，同樣的物件會由 AWS Load Balancer Controller 變成一台 ALB。

為什麼不每個服務開一個第 4 課的 LoadBalancer Service 就好？LoadBalancer 是第 4 層（L4）的：它只看 IP 和 port，不看 HTTP 的網域和路徑，所以一個服務就要一個對外位址，在雲端就是一台要付錢的負載平衡器。入口是第 7 層（L7）的：看得懂 HTTP，一個位址就能依網域、路徑、標頭分給很多服務，還能逐個請求分配流量（第 4 課講過 kube-proxy 是以連線為單位）。

Ingress 與 Gateway API：為什麼換

Kubernetes 最早的入口 API 叫 Ingress。它只定義了兩件事：主機名稱與路徑。其他功能（改寫路徑、逾時、上傳大小、金絲雀、轉址）都沒有欄位，每一家實作 Ingress 的程式（叫 Ingress controller）各自用 annotation 擴充，寫法互不相容：

metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2          # 只有 Ingress NGINX 看得懂
    nginx.ingress.kubernetes.io/proxy-body-size: 8m
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"

annotation 是任意字串，API server 不檢查，打錯字不會報錯，只是沒效果；換一家 controller，整套 annotation 要重寫。更麻煩的是一個 Ingress 物件同時放了「入口設定」和「各服務的路由」，誰能改它，誰就能動整個入口。

現況（2026 年 11 月）：

  • Ingress NGINX 已退役：這是最多人用的 Ingress controller（kubernetes/ingress-nginx）。SIG Network 與安全回應委員會在 2025 年 11 月 11 日宣布退役，2026 年 3 月起不再發佈新版、不修 bug、不修安全漏洞，GitHub repo 已封存。已經裝的不會自己壞掉，但出了漏洞沒有人修。
  • Ingress API 凍結：networking.k8s.io/v1 的 Ingress 沒有被移除，舊 manifest 照樣能 apply，但不會再加新功能。
  • Gateway API（gateway.networking.k8s.io/v1）是官方的接班人：Gateway、GatewayClass、HTTPRoute 都已 GA（正式穩定）。最新版是 v1.7.0；本機的 cloud-provider-kind 0.12.0 內建的是 v1.6.1 的 standard channel，這課只用 v1 的 GA 欄位。

Gateway API 本身只是規格（一組 CRD，也就是 Kubernetes 的自訂物件型別），要有實作才會動。常見的實作：

實作在哪裡用
cloud-provider-kind這門課的本機 kind 叢集（底層 Envoy）
AWS Load Balancer ControllerEKS：v3.0.0（2026 年 1 月）起 Gateway API 支援 GA，HTTPRoute 變成 ALB 的規則
Envoy Gateway、Traefik、Istio、Cilium自己管理入口代理、或已經用這些網路／service mesh 元件的叢集

規格把功能分成 Core（每個實作都必須支援，有一致性測試）和 Extended（選擇性支援）。實作支援哪些 Extended 功能，寫在 GatewayClass 的 status.supportedFeatures：

kubectl get gatewayclass cloud-provider-kind -o jsonpath='{range .status.supportedFeatures[*]}{.name}{"\n"}{end}'
# Gateway、HTTPRoute、HTTPRoute303RedirectStatusCode、HTTPRouteQueryParamMatching、ReferenceGrant……
# 沒有 HTTPRoutePathRewrite、HTTPRouteSchemeRedirect：這兩個功能本機用不了，後面會實際看到後果

選實作、或從 Ingress 搬家之前，先拿你需要的功能對這張清單。

三種物件、兩種角色

Gateway API 把 Ingress 那一個物件拆成三種，對應公司裡兩種角色：

  • GatewayClass：用哪一種實作，例如 cloud-provider-kind。叢集層級，通常安裝實作時就建好了。
  • Gateway：一個實際的入口，有一個或多個 listener（接收點：port、協定、主機名稱、TLS 憑證）。由平台團隊管理，常放在 infra 這類專用的 namespace。
  • HTTPRoute：符合哪些條件的 HTTP 請求要送到哪些 Service。由應用團隊寫在自己服務的 namespace，用 parentRefs 指定掛在哪個 Gateway 上。

這樣切開的好處是權限可以分開給（第 12 課的 RBAC）：應用團隊只要有自己 namespace 的 HTTPRoute 權限，不用碰得到入口的憑證或其他團隊的路由。Ingress 把兩者放在同一個物件，常常只好給應用團隊過大的權限。

Gateway 用 listener 的 allowedRoutes 決定哪些 namespace 的 Route 可以掛上來：

allowedRoutes.namespaces.from意思什麼時候用
Same（預設）只有跟 Gateway 同一個 namespace 的 Route一個團隊自己的入口；這課的練習
Selectornamespace 的標籤符合 selector 的才行共用入口：平台團隊替可以上線的 namespace 加標籤
All任何 namespace幾乎不要用：任何人寫一條 hostnames: [cafe.test] 的 Route 就能分走你的流量

反方向也有管制：HTTPRoute 的 backendRefs 指到別的 namespace 的 Service 時，那個 namespace 要建一個 ReferenceGrant，明確說「允許某 namespace 的 HTTPRoute 參照我的 Service」，否則參照無效。這樣別人不能隨便把流量導進你的服務：

apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-infra-routes
  namespace: orders           # 被參照的一方建立
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    namespace: infra          # 允許 infra 的 HTTPRoute
  to:
  - group: ""
    kind: Service             # 參照這個 namespace 的 Service
💡 實務上：新服務要對外，開發初期就跟平台團隊確認入口
在有平台團隊的公司，應用團隊通常不自己建 Gateway，而是把 HTTPRoute 掛到共用的 Gateway 上。要掛得上去，有幾件事是平台團隊的設定：自己的 namespace 有沒有被 allowedRoutes 允許、要用的網域歸誰管、listener 的憑證有沒有涵蓋這個網域。臨上線才發現 Route 掛不上去，就得等別人排時間。資深工程師會在開發初期就開單確認，順便問清楚入口的逾時、上傳大小這些限制是多少。

第一條 HTTPRoute，以及怎麼讀 status

先建入口。listener 的名字之後可以用來指定「只掛在這個 listener」：

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: cafe-gw
spec:
  gatewayClassName: cloud-provider-kind   # 用哪種實作
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces:
        from: Same                         # 預設就是 Same，寫出來讓讀的人一眼看懂

再寫路由。cafe-api 自己的路由是 /products、/orders，其他路徑交給網站 web：

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: cafe
spec:
  parentRefs:
  - name: cafe-gw              # 掛在哪個 Gateway（同 namespace 時只寫名字）
  hostnames:
  - cafe.test                  # 只接 Host: cafe.test 的請求
  rules:
  - matches:                   # 兩個 match 之間是「或」
    - path: { type: PathPrefix, value: /products }
    - path: { type: PathPrefix, value: /orders }
    backendRefs:
    - name: cafe-api           # Service 名稱
      port: 80                 # Service 的 port（不是容器的 3000）
  - matches:
    - path: { type: PathPrefix, value: / }
    backendRefs:
    - name: web
      port: 80

套用之後，從 Mac 打打看。cafe.test 不是真的網域，所以用 -H 'Host: …' 自己帶 Host 標頭，效果跟瀏覽器打 http://cafe.test 一樣：

kubectl apply -n k8s-05-ex1 -f kubernetes/practice/work/05/ex1/
URL=$(node kubernetes/practice/bin/url.mjs k8s-05-ex1 gateway/cafe-gw)    # http://localhost:5xxxx
curl -i -H 'Host: cafe.test' $URL/products     # 200，x-instance: cafe-api-…
curl -i -H 'Host: cafe.test' $URL/about        # 200，{"name":"web",…}
curl -i -H 'Host: other.test' $URL/products    # 404，server: envoy，沒有 x-instance：Gateway 自己回的

沒有通的時候，第一件事是看 status。kubectl apply 只檢查格式，路由能不能生效是控制器之後才決定的，結果只寫在物件的 status.conditions，apply 永遠顯示成功：

kubectl get gateway -n k8s-05-ex1          # PROGRAMMED 要是 True
kubectl describe httproute cafe -n k8s-05-ex1
# Status:
#   Parents:
#     Conditions:
#       Type: Accepted      Status: True    Reason: Accepted        ← Gateway 接受了這條 Route
#       Type: ResolvedRefs  Status: True    Reason: ResolvedRefs    ← backendRefs 都找得到
你看到的原因怎麼查、怎麼修
Route 的 status 是空的parentRefs 指的 Gateway 名稱不對，或 Gateway 的 class 沒有控制器kubectl get gateway 對名稱；kubectl get gatewayclass 看 ACCEPTED
Accepted=False，NotAllowedByListenerslistener 的 allowedRoutes 不允許這個 namespace請平台團隊加標籤或調 allowedRoutes
Accepted=False，UnsupportedValue用了這個實作不支援的功能看 message 和 GatewayClass 的 supportedFeatures
ResolvedRefs=False，BackendNotFoundbackendRefs 的 Service 名稱打錯或不存在kubectl get svc 對名稱
ResolvedRefs=False，RefNotPermitted跨 namespace 參照，對方沒有 ReferenceGrant請對方建 ReferenceGrant
status 都正常，但請求 404Host 或路徑沒有任何規則符合對 hostnames 與 matches
status 都正常，但請求 503 或逾時Service 沒有 Ready 的 Pod，或 backendRefs 的 port 寫錯第 4 課的排查順序：EndpointSlice、targetPort
本機實測（cloud-provider-kind 0.12.0）：backendRefs 的 port 寫成容器的 3000（Service 只有 80）時，它不會把 ResolvedRefs 設成 False，status 全部正常，請求卻卡住直到逾時。只有名稱錯才會變 BackendNotFound。不同實作檢查的嚴格程度不一樣，所以 status 正常之後還要真的打一個請求。

比對規則：路徑、標頭、優先順序

路徑有兩種常用的比對方式：

typevalue: /orders 符合不符合
PathPrefix/orders、/orders/、/orders/42/ordersx：前綴以「/ 分隔的一段」為單位比，不是字串開頭
Exact只有 /orders/orders/、/orders/42

一個請求可能同時符合好幾條規則（例如 /orders/42 符合 /orders 也符合 /），但只會送到一條。規格定的優先順序，依序比：

  1. Exact 比 PathPrefix 優先。
  2. PathPrefix 之間，字元多（越長）的優先。
  3. 有 method 條件的優先。
  4. 標頭條件越多的優先。
  5. 查詢參數條件越多的優先。
  6. 還是平手：建立時間早的 Route 優先，再來是「namespace/名稱」的字母順序；同一個 Route 裡才看 rule 列出的順序。

跟 nginx 的 location 一樣，前面幾項分得出高下時跟你寫的順序無關，所以 / 放第一條也不會搶走 /orders。

標頭比對寫在 match 裡。同一個 match 裡的條件是「而且」，同一個 rule 的多個 match 之間是「或」：

matches:
- path: { type: PathPrefix, value: /orders }
  headers:                      # 同一個 match：路徑是 /orders 而且 X-Canary 是 1
  - name: X-Canary
    value: "1"                  # 值一定是字串，1 要加引號
- path: { type: Exact, value: /healthz }    # 另一個 match：或者路徑剛好是 /healthz

權重分流（weighted routing）：一個 rule 的 backendRefs 列好幾個後端，各給一個 weight，流量依比例分配（90 和 10、9 和 1 都是 9:1；沒寫 weight 時是 1，寫 0 就不送）。Envoy 是逐個請求抽籤，所以實際比例會在 10% 附近上下跳。這就是 devops 課第 16 課的金絲雀：新版 v2 先拿 10% 的真實流量，觀察錯誤率和延遲，沒問題再調成 50、100；有問題就把 v2 的 weight 改回 0，不用重新部署。

另一種常見需求是「公司內部的人先試新版，顧客不受影響」：用標頭當開關，帶 X-Canary: 1 的一律到 v2。兩者的取捨：

權重標頭
誰會用到新版隨機一部分真實顧客只有知道要帶標頭的人（QA、內部 App 版本）
適合驗證新版在真實流量下的錯誤率、延遲上線前在正式環境做功能測試
要注意同一個使用者連續兩個請求可能一個 v1 一個 v2，兩版的 API 與資料格式要相容不能測到真實流量的壓力

練習 2 會把兩種組在同一條 HTTPRoute 裡：標頭那條規則的條件比較多，所以比權重那條優先。

💡 實務上：金絲雀要先講好看哪些指標、誰決定往下推
把 v2 的 weight 調成 10 只是開始，真正的工作是觀察：v2 的錯誤率、p95 延遲跟 v1 比有沒有變差（devops 課第 22 課的指標）。上線前先跟團隊講好「看哪幾個數字、觀察多久、超過多少就把 weight 改回 0」，出事時才不用臨時開會。資深工程師還會先問：v2 有沒有改資料庫 schema 或 API 的回應格式？同一個使用者可能前後打到兩版，不相容的改動要拆成幾次上線，讓兩版能同時存在。

HTTPS：在 Gateway 終結 TLS

TLS 終結（TLS termination）是在入口把 HTTPS 解密，後面到 Service 用 HTTP。這跟 devops 課 nginx 的做法一樣：憑證只放在入口，cafe-api 不用處理 TLS。步驟：

步驟一：產生憑證。本機用 devops 課第 5 課的方法自己當 CA，簽一張 SAN 是 DNS:cafe.test 的憑證（openssl req -x509 … 做 CA、openssl req -newkey … 產生金鑰和 CSR、openssl x509 -req … -extfile 簽發）。

步驟二：把憑證和金鑰放進叢集。Secret 是 Kubernetes 存機密資料的物件（第 6 課會詳細講），type: kubernetes.io/tls 的 Secret 有固定的兩個欄位 tls.crt、tls.key。直接從檔案建立，不要寫成 YAML 檔：

kubectl create secret tls cafe-tls -n k8s-05-ex3 --cert=server.crt --key=server.key \
  --dry-run=client -o yaml | kubectl apply -f -
# --dry-run=client -o yaml 只產生 YAML 不送出，交給 apply：Secret 已存在時會更新，腳本可以重複執行
Secret 的 YAML 裡金鑰只是 base64，不是加密，任何人 base64 -d 就還原了。把它寫進 manifest 檔再 commit，等於把金鑰公開在 git 歷史裡。正式環境用 cert-manager 自動簽發並寫進 Secret，或在 EKS 上用 AWS Certificate Manager（ACM）管理憑證、掛在 ALB 上，金鑰根本不進叢集。

步驟三：Gateway 加一個 HTTPS listener：

listeners:
- name: http
  protocol: HTTP
  port: 80
  allowedRoutes: { namespaces: { from: Same } }
- name: https
  protocol: HTTPS
  port: 443
  hostname: cafe.test             # 這個 listener 只接 cafe.test（要跟憑證的 SAN 一致）
  tls:
    mode: Terminate               # 在 Gateway 解密
    certificateRefs:
    - name: cafe-tls              # 同 namespace 的 tls Secret
  allowedRoutes: { namespaces: { from: Same } }

步驟四：HTTP 的請求不要直接送到後端，一律轉址到 HTTPS。路由用 sectionName 指定只掛在某個 listener：

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web
spec:
  parentRefs:
  - name: cafe-gw
    sectionName: https            # 只掛在 HTTPS listener
  hostnames: [cafe.test]
  rules:
  - backendRefs: [{ name: web, port: 80 }]
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: to-https
spec:
  parentRefs:
  - name: cafe-gw
    sectionName: http             # 只掛在 HTTP listener
  hostnames: [cafe.test]
  rules:
  - filters:                      # filter：對請求做額外處理
    - type: RequestRedirect       # 直接回轉址，不送到任何後端
      requestRedirect:
        scheme: https
        statusCode: 301           # 不寫是 302（暫時轉址）

沒寫 sectionName 的話，web 這條會同時掛在兩個 listener 上，HTTP 也直接送到 web，等於沒有強制 HTTPS。

驗證。--resolve 讓 curl 把 cafe.test 解析到 127.0.0.1，同時送正確的 SNI 和 Host，--cacert 只信任你自己的 CA：

URL=$(node kubernetes/practice/bin/url.mjs k8s-05-ex3 gateway/cafe-gw 443); PORT=${URL##*:}
curl -i --cacert kubernetes/practice/work/05/ex3/ca.crt --resolve cafe.test:$PORT:127.0.0.1 https://cafe.test:$PORT/menu
HTTP=$(node kubernetes/practice/bin/url.mjs k8s-05-ex3 gateway/cafe-gw 80)
curl -i -H 'Host: cafe.test' $HTTP/menu      # 301 Moved Permanently
本機實測：cloud-provider-kind 0.12.0 回了 301，但 Location 仍是 http://cafe.test/menu。轉址的 scheme 屬於 Extended 功能 HTTPRouteSchemeRedirect，它的 supportedFeatures 裡沒有，產生 Envoy 設定時只用了 hostname 和 statusCode，scheme 被略過了，status 還是顯示 Accepted。Envoy Gateway、AWS Load Balancer Controller 這類支援這項功能的實作，Location 會是 https://…。這是「先看 supportedFeatures」的實際例子：規格寫得到，不代表你用的實作做得到。練習 3 的測試因此只檢查 301 與 YAML 裡的 scheme: https。

舊的 Ingress 怎麼搬

接手舊專案時，常看到這種 Ingress（練習 4 的檔案）。先讀懂它：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cafe-menu
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx                   # 交給 Ingress NGINX 處理
  rules:
  - host: www.cafe.test                     # = hostnames
    http:
      paths:
      - path: /menu(/|$)(.*)                # 正規表示式，(.*) 抓到的是 $2
        pathType: ImplementationSpecific    # 比對方式由 controller 決定
        backend:
          service: { name: menu, port: { number: 80 } }   # = backendRefs

這條規則的意思：/menu/items 轉給 menu 時改成 /items，/menu 改成 /。就是 devops 課 proxy_pass http://api:3000/; 結尾斜線那個效果。對應的 Gateway API 寫法是 URLRewrite filter：

rules:
- matches:
  - path: { type: PathPrefix, value: /menu }
  filters:
  - type: URLRewrite
    urlRewrite:
      path:
        type: ReplacePrefixMatch    # 把比對到的前綴 /menu 換掉
        replacePrefixMatch: /       # 換成 /：/menu/items → /items
  backendRefs: [{ name: menu, port: 80 }]

其他欄位的對應：Ingress 的 pathType: Prefix 就是 PathPrefix（兩者都以 / 分隔的段落比對）、Exact 就是 Exact，host 變成 hostnames，backend.service 變成 backendRefs。

可是 URLRewrite 是 Extended 功能（HTTPRoutePathRewrite），本機的 cloud-provider-kind 0.12.0 不支援。實際套用的結果：

kubectl get httproute www -o jsonpath='{.status.parents[0].conditions}'
# Accepted=True
# PartiallyInvalid=True  Dropped Rule(s): rule[0] has unsupported filter type "URLRewrite"
curl -H 'Host: www.cafe.test' $URL/menu/items
# {"name":"web","path":"/menu/items"}     ← /menu 那條被丟掉，請求落到 / 的 web

這是遷移最危險的情況：沒有錯誤、Route 也是 Accepted，只是有一條規則沒生效，流量默默送錯地方。只有讀 status 的 PartiallyInvalid 或實際打請求才發現得到。

官方有轉換工具 ingress2gateway（目前 v1.2.0，brew install ingress2gateway），讀 Ingress 和 Ingress NGINX 的 annotation，印出對應的 Gateway API 物件，翻不了的會列出警告：

ingress2gateway print --providers=ingress-nginx --input-file ingress.yaml

工具只是起點，產出要逐項檢查。annotation 是遷移時最容易漏的，常見的幾個：

Ingress NGINX annotationGateway API要確認的事
rewrite-targetURLRewrite filter實作是否支援 HTTPRoutePathRewrite；不支援就換實作，或讓服務直接用對外的路徑
ssl-redirectRequestRedirect filterIngress 有設 TLS 時，Ingress NGINX 預設就會把 HTTP 用 308 轉到 HTTPS；搬過來要自己寫轉址路由，否則 HTTP 會直接送到後端
proxy-read-timeoutrule 的 timeouts（Extended：HTTPRouteRequestTimeout）預設值各家不同，SSE、長輪詢的路徑特別注意
proxy-body-size沒有標準欄位用實作自己的擴充設定；上傳功能要實際測大檔案
canary-weightbackendRefs 的 weightCore 功能，各實作都支援
💡 實務上：從 Ingress NGINX 搬家，先盤點再切換
Ingress NGINX 不再修安全漏洞之後，很多團隊的待辦清單上都有這一項。第一步是盤點：列出所有 Ingress 和用到的 annotation，對照目標實作的 supportedFeatures，先找出翻不過去的功能。切換時，新的 Gateway 跟舊的 Ingress 先並存（不同的對外位址），用同一組請求表打兩邊、比對回應，全部一致再切 DNS，舊的留到確定不用回滾再刪；練習 4 的測試就是這個做法的縮小版。上傳大小、逾時這類沒有標準欄位的設定最容易漏，要找負責上傳、匯出功能的人一起確認。

練習

四題都在 kubernetes/practice/work/05/，每題一個資料夾。backends.yaml 是測試提供的後端（cafe-api，或設了 ECHO_NAME、會回傳收到的主機與路徑的版本），不用改。測試會把整個資料夾套用到 k8s-05-exN 這個 namespace；自己試的時候也用同一個名字：

export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"
kubectl create namespace k8s-05-ex1
kubectl apply -n k8s-05-ex1 -f kubernetes/practice/work/05/ex1/
kubectl get gateway,httproute -n k8s-05-ex1

每個 Gateway 會多開一個 kindccm 容器，做完一題就 kubectl delete namespace k8s-05-exN（測試結束時也會自己刪）。

練習 1：完成兩個檔案。gateway.yaml：Gateway cafe-gw，class cloud-provider-kind，一個 HTTP 80 的 listener，明確寫出只允許同 namespace 的 Route。route.yaml：HTTPRoute cafe 掛在 cafe-gw，只接 cafe.test；/products 與 /orders 開頭的路徑送到 Service cafe-api，其他路徑送到 web。測試會跑 kubeconform，套用後檢查 Gateway Programmed、Route 的 Accepted 與 ResolvedRefs，再從 Mac 經 bin/url.mjs 的網址打 /products、/orders/42、/about，以及 Host 是 other.test 的請求（要 404）。

練習 2：金絲雀。ex2/ 有 cafe-api-v1、cafe-api-v2 兩個 Service 和現成的 Gateway cafe-gw。改 route.yaml：帶 X-Canary: 1 標頭的請求一律到 v2；其他請求 v1:v2 依 9:1 分流。只改路由，不要再建 Gateway。測試從叢集裡經 Gateway 送 30 個帶標頭的請求（要全部到 v2）和 300 個不帶標頭的請求（v2 的比例要在 4%～18% 之間，留了機率波動的餘裕），並檢查 YAML 的權重比例。

練習 3：HTTPS。完成 setup.sh：在 ex3/ 產生 CA（ca.key、ca.crt）與 cafe.test 的憑證（server.key、server.crt，SAN 是 DNS:cafe.test），再建立 tls Secret cafe-tls；namespace 從第一個參數拿，重複執行也要成功。gateway.yaml 加一個 HTTPS 443 listener（hostname cafe.test，用 cafe-tls 終結 TLS）；routes.yaml 改成 HTTPS 送到 web、HTTP 一律 301 轉到 https。任何 YAML 檔都不能有 Secret 或金鑰（.gitignore 已經排除金鑰與憑證檔）。測試會執行兩次 bash setup.sh k8s-05-ex3，套用後用 ca.crt 驗證 https://cafe.test，再確認 HTTP 回 301 而且沒有送到 web。

練習 4：把 ex4/ingress.yaml.txt（舊專案的兩個 Ingress：兩個主機、四條路徑、一個 rewrite-target）改寫成 route.yaml 裡的 HTTPRoute，掛在現成的 cafe-gw 上，rewrite 用 URLRewrite filter。測試先比對兩邊的每一條規則（主機、比對方式、路徑、後端、rewrite），再對 Gateway 打一組請求，確認送到的後端和後端收到的路徑都跟 Ingress 時一樣。本機實作不支援 URLRewrite，/menu 那條規則會被丟掉（status 會出現 PartiallyInvalid），所以 rewrite 只做靜態檢查，請求表不含 /menu；套用後自己用 kubectl describe httproute 看看那個條件。

練習 5：新專案要對外提供 HTTP API，入口應該選哪個？

✓ 入口直接面對網際網路，選一個不再有安全修補的元件風險最高。a 範例雖多，但控制器已退役；c 是 L4，看不懂網域和路徑，在雲端每個服務都是一台要付錢的負載平衡器；d 等於自己維護入口的設定、高可用和更新，Kubernetes 的好處都沒用到。

練習 6：HTTPRoute 的 status 顯示 ResolvedRefs=False、reason BackendNotFound。最可能的原因是？

✓ ResolvedRefs 檢查的是 Route 參照的物件找不找得到（跨 namespace 沒有 ReferenceGrant 時則是 RefNotPermitted）。c 的參照本身有效，status 正常，但請求會 503；d 是請求比對不到規則，Gateway 回 404；a 跟這條 Route 的參照無關。

練習 7：為什麼 Gateway API 把 Gateway 和 HTTPRoute 分成兩個物件？

✓ 角色分離是 Gateway API 的設計重點，配合 RBAC 與 allowedRoutes 控制誰能掛什麼。Ingress 把兩者混在一個物件，常常要給應用團隊過大的權限。c 不對：兩者都只是設定，真正處理請求的是 Envoy、ALB 這類代理；d 不對：一個 Gateway 可以掛很多 Route。

練習 8：你把舊的 Ingress 搬成 HTTPRoute，kubectl apply 成功，Route 也是 Accepted=True，但 /menu/items 的請求跑到了網站首頁的服務。第一步該看什麼？

✓ 實作遇到不支援的 Extended 功能時，可能只丟掉那一條規則，Route 仍然 Accepted，流量落到下一條符合的規則（這裡是 /）。status 的 PartiallyInvalid 會寫出被丟掉的規則和原因。a、b 不會改變結果；d 是回到已經退役的元件。

常見錯誤

  • apply 成功就以為生效了：Route 被拒絕、後端找不到、規則被丟掉，都只寫在 status 的條件裡。apply 之後看 kubectl describe httproute 的 Accepted、ResolvedRefs、PartiallyInvalid，再真的打一個請求。
  • HTTPRoute 沒寫 hostnames：它會接下這個 listener 上所有網域的請求，可能搶走別的服務的流量。每條 Route 都寫 hostnames。
  • Gateway 的 allowedRoutes 設成 All：任何 namespace 的人都能寫一條 Route 掛上你的網域。用 Same 或 Selector 限制。
  • backendRefs 的 port 寫成容器的 port：backendRefs 指的是 Service，要寫 Service 的 port（第 4 課的 80），不是 containerPort 3000。
  • 用 Exact 比對一整組 API 路徑：Exact /orders 不包含 /orders/42。一組 API 用 PathPrefix，只有單一端點（例如 /healthz）才用 Exact。
  • 標頭條件和權重放在同一個 rule：同一個 rule 的 matches 是「或」，帶標頭的請求也照權重分流。要「帶標頭一律到 v2」，標頭條件自己一個 rule。
  • 把憑證金鑰寫進 YAML：base64 不是加密，進了 git 就外流。用 kubectl create secret tls 從檔案建立；正式環境用 cert-manager 或 ACM。
  • 以為所有實作功能都一樣：Core 功能有一致性測試，Extended 功能各家不同。選實作、搬 Ingress 之前先對 GatewayClass 的 supportedFeatures。
  • 繼續用 Ingress NGINX：已退役，不再有安全修補。用 kubectl get pods -A -l app.kubernetes.io/name=ingress-nginx 檢查叢集有沒有在用，盡快規劃遷移。

小結

  • 入口做四件事：依 port 接請求、依網域分辨、終結 TLS、依路徑轉給後端。Kubernetes 用 API 物件描述這些事，由控制器設定真正的代理（本機是 Envoy，EKS 上是 ALB）。
  • Ingress 只有主機與路徑，其他靠各家 annotation；Ingress API 已凍結，Ingress NGINX 已退役。新專案用 Gateway API（gateway.networking.k8s.io/v1）。
  • GatewayClass 選實作；Gateway 是平台團隊的入口（listener、憑證、allowedRoutes）；HTTPRoute 是應用團隊的路由（parentRefs、hostnames、matches、backendRefs）。跨 namespace 參照要 ReferenceGrant。
  • 比對優先順序看規則本身（Exact、較長的前綴、較多的標頭），不看寫的順序；同一個 match 裡是「而且」，同一個 rule 的 matches 之間是「或」。weight 是相對比例，用來做金絲雀。
  • HTTPS：憑證放 tls Secret（從檔案建立，不進 git），listener 用 tls.mode: Terminate；HTTP listener 掛 RequestRedirect 轉到 https，用 sectionName 讓路由只掛在對的 listener。
  • apply 成功不等於生效：讀 status 的 Accepted、ResolvedRefs、PartiallyInvalid，再實際打請求。Extended 功能先查 supportedFeatures。
  • 搬舊 Ingress：ingress2gateway 當起點，逐項確認 annotation 在新實作的對應，兩邊並存、用同一組請求比對後再切換。
