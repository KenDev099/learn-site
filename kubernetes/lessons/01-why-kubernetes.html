階段 1：起步：從 Compose 到叢集 · 第 1 課

為什麼需要 Kubernetes：期望狀態、控制迴圈與本機叢集

咖啡店的 API 在 devops 課已經上線了：一台 EC2、Docker Compose 跑 nginx、兩個 cafe-api 副本、PostgreSQL 和 Redis。生意變好之後，問題跟著來：週末尖峰流量是平常的三倍、主機半夜當機沒人知道、每週要部署五次而且不能停機。這些事 Compose 都不會自動處理，全部要你自己寫腳本、自己半夜起來處理。

Kubernetes（常寫成 k8s：k 和 s 中間有 8 個字母）是管理「很多台主機上的容器」的平台：你告訴它要跑什麼、跑幾份，它負責挑主機放、壞了重開、主機掛了搬家、更新時一個一個換。

這課的路線：
  1. 咖啡店長大了、Kubernetes 接手了什麼：一台主機的 Compose 在哪些情境要靠人半夜處理，Kubernetes 接手哪些、代價是什麼；主管問「要不要上 k8s」時怎麼回答。
  2. 期望狀態與控制迴圈：為什麼你只說「要 3 份」，主機壞了它就會自己補回來。
  3. 叢集裡有誰：control plane 和節點上各跑哪些元件，出事時知道該看誰。
  4. 本機叢集與 kubeconfig：在 Mac 上用 kind 建三節點叢集，並確保指令不會打到公司的 production 叢集。
  5. 第一次看叢集：只讀不改的 kubectl 指令，看節點、namespace 和系統元件。
這課會用到：
  • devops 課第 7 課的容器與映像：映像打包了程式和執行環境，容器是從映像啟動、彼此隔離的程序。
  • devops 課第 10 課的 Docker Compose：用一個 YAML 在一台主機上啟動多個容器，這課拿它當對照組。
  • devops 課第 13 課的多副本：同一個服務跑好幾份，前面用 nginx 的 upstream 分流量，下線前先排空。

咖啡店長大了：誰來做這些事？

把 devops 課的做法攤開，逐項問「出事的時候，誰來處理」：

情境Compose＋nginx（一台主機）怎麼辦
cafe-api 的程序崩潰restart: unless-stopped 會重開容器。這一項 Compose 做得到。
主機半夜當機整個服務停擺。要有人收到告警、開新主機、裝 Docker、拉映像、改 DNS。全部手動或自己寫腳本。
流量變三倍手動 docker compose up --scale api=6，再改 nginx 的 upstream。一台主機的 CPU 用完就沒辦法了。
要擴到三台主機Compose 只管一台。要自己決定哪個容器放哪台、每台的 nginx 設定怎麼同步。
每週部署五次、不停機自己寫腳本：先起新版、等健康檢查、改 nginx、排空舊版、出錯回滾（devops 課第 16 課那一套）。
三個團隊共用機器誰都能 docker rm 別人的容器，沒有權限分隔，也沒有資源配額。

每一項都能用腳本解決，但腳本要人寫、要人維護、出錯時要人看懂。Kubernetes 把這些常見的維運動作做成平台內建的功能，而且做法跟你寫腳本時想的一樣，只是一直有程式在執行它們。

Kubernetes 接手了什麼，代價是什麼

能力Kubernetes 的做法這門課

代價也要講清楚：

  • 學習成本：Pod、Deployment、Service、probe、RBAC……名詞多，出錯時要知道去哪裡查（第 14 課整課在練這件事）。
  • 維運成本：叢集本身也是要維護、要升級的系統。用 AWS 的 EKS 可以把最難的部分交給 AWS 代管，但每個叢集每月有固定費用，節點也要自己升級（第 15 課）。
  • YAML 量：一個服務要寫好幾個檔案，多環境還要再加一層打包工具（第 13 課的 Helm）。

所以「要不要用 Kubernetes」是取捨，不是越新越好。

💡 實務上：要不要上 Kubernetes，是寫進 ADR 的取捨
只有一個服務、一台主機、一個小團隊、每月部署一次的時候，Compose 加上 systemd 和監控就夠了，devops 課第 26 課的 ADR（架構決策紀錄）就是這樣決定的。值得重新評估的訊號是：服務變多、需要自動擴展、一台主機撐不住或不能接受單點故障、好幾個團隊要共用同一套平台。主管或 PM 問「要不要上 Kubernetes」時，資深工程師會先問：現在痛的是上面表格的哪一項？叢集由誰維護、誰負責升級？如果痛點只是「不想自己管主機」，AWS 的 ECS 這類比較簡單的代管容器服務也是選項。回答時把條件寫下來，條件出現時再導入。

期望狀態與控制迴圈

用 Compose 時，你下的是命令：「啟動這個容器」「再開一份」。命令執行完就結束了，之後容器怎樣，Compose 不會一直盯著。這叫命令式（imperative）。

Kubernetes 換了一個做法：你不下命令，而是宣告你要的結果，例如「cafe-api 要有 3 份，用 v1 的映像」。這份宣告叫期望狀態（desired state），存在叢集裡。叢集現在真正的樣子叫實際狀態（actual state）。這種做法叫宣告式（declarative）：說「要 3 份」，而不是說「再開 1 份」。

接著由控制器（controller）負責讓兩者一致：它不斷觀察實際狀態、跟期望狀態比對、做出縮小差距的動作，然後再觀察。比對兩種狀態並做出動作這件事叫調和（reconcile），一直重複調和就是控制迴圈（control loop）。

最貼近的比喻是冷氣的恆溫器：你設定 26 度（期望狀態），它不斷量室溫（觀察），太熱就送冷風（動作），你不用每五分鐘去按一次「降溫」。開門讓熱氣跑進來，它自己會補回來。

放到咖啡店：你宣告 cafe-api 要 3 份。某個副本所在的主機當機，實際狀態變成 2 份；負責副本數的控制器下一輪觀察就發現少了一份，建立一個新的，放到還活著的主機上。沒有人寫「主機當機時要做什麼」的腳本，因為控制器只在乎「現在是不是 3 份」。下面是這個迴圈的極簡模擬，按執行看每一輪做了什麼：

從這裡可以推出 Kubernetes 最重要的一個習慣：沒有「執行一次就算了」的指令，只有「一直被維持的狀態」。你用 kubectl delete pod 刪掉 Deployment 底下的一個 Pod，幾秒後會冒出一個名字不同的新 Pod，因為期望狀態還是 3 份。想要改變結果，就改期望狀態（改 YAML 再 apply），而不是去跟控制器搶著動手。

Pod、Deployment 是什麼？這兩個詞第 2、3 課才正式教。現在先知道：Pod 是 Kubernetes 裡最小的執行單位，大多數時候就是「一個容器」；Deployment 是「這個 Pod 要跑幾份、用哪一版」的期望狀態。叢集裡的每一筆紀錄叫物件（object），它的種類叫資源類型（resource kind），例如 Pod、Deployment 都是資源類型。
💡 實務上：救火時手動改的東西，事後一定要寫回 git
典型的場景：半夜 cafe-api 出事，值班的人用 kubectl edit 改了環境變數、用 kubectl scale 加了副本，服務恢復了。隔天 CI 照常部署，kubectl apply 把叢集改回 git 裡的樣子，昨晚的修正悄悄消失，問題重演。團隊的規矩通常是：手動修改只用來止血，同時在事故頻道記下改了什麼，事後開 PR 把同樣的修改寫進 manifest。第 3 課的 scale、第 15 課的 GitOps 都會再遇到這件事。

叢集裡有誰

叢集（cluster）是一組由 Kubernetes 管理的主機，每一台叫節點（node），可以是實體機、雲端的 VM，或者這門課裡的一個 Docker 容器。節點分成兩種角色：

control plane（控制平面）是叢集的大腦：

  • API server：叢集唯一的入口。所有的讀和寫，不管來自你的 kubectl、控制器還是節點，都經過它；它檢查身分和權限，再把資料存進 etcd。
  • etcd：存放叢集所有物件的鍵值資料庫。期望狀態就存在這裡，它壞了，叢集就失憶了，所以正式環境一定有備份或交給雲端代管。
  • scheduler（排程器）：看到還沒分配節點的新 Pod，就依各節點還能分配的 CPU、記憶體（看的是 Pod 事先宣告的需求量，不是當下的實際用量，第 8 課細講）等條件挑一台，把結果寫回 API server。
  • controller manager：裡面跑著很多個控制器，例如維持副本數的、處理節點失聯的。每一個都是前面那個控制迴圈。

每個節點上有：

  • kubelet：節點上的代理程式。它向 API server 查「分到我這台的 Pod 有哪些」，叫 container runtime 把容器跑起來，再把狀態回報給 API server。
  • container runtime：真正啟動容器的程式。kind 和 EKS 用的都是 containerd，跟 Docker Desktop 底下用的是同一套。
  • kube-proxy：設定節點上的網路規則，讓「用名字找到一群副本」能運作（第 4 課）。

重點是：kubectl 永遠只跟 API server 說話。它不會連到節點、不會直接讀 etcd。所以你能操作哪個叢集，完全取決於 kubectl 連的是哪一個 API server，這是後面 kubeconfig 那一節的伏筆。

在 AWS 的 EKS 上，control plane 整塊由 AWS 代管（你看不到 etcd 那台機器），你只管節點和上面跑的東西，第 15 課會細講。這門課用的 kind 則是把每個節點跑成一個 Docker 容器，control plane 也在其中一個容器裡，所以你可以在 docker ps 看到它們。

在 Mac 上建立本機叢集

本機叢集的工具有好幾個，這門課用 kind（Kubernetes IN Docker）：

工具做法適合
kind每個節點是一個 Docker 容器，跑上游原版的 Kubernetes多節點、版本可以釘死、Kubernetes 專案自己的測試也用它；這門課用它練 drain 節點、跨節點分散
k3d在 Docker 裡跑 k3s（精簡過的 Kubernetes 發行版）省資源；但元件和預設值跟上游不完全一樣
minikube用 VM 或容器跑叢集，附很多附加元件（addon）單節點練習、需要它的附加元件時
Docker Desktop 內建設定裡打勾開啟；新版可選 kind 模式（多節點、選版本）最省事；但叢集跟著 Docker Desktop 的設定走，不容易用一份檔案重建出一模一樣的叢集

選 kind 的理由：它跑的是上游原版的 Kubernetes，跟 EKS 最接近；叢集的樣子寫在一個 kind.yaml 裡，刪掉重建永遠一樣。它沒有的東西是雲端的負載平衡器，這門課用 cloud-provider-kind 補上（第 4、5 課會用到）。

安裝與建立叢集

先在 Docker Desktop → Settings → Resources 把記憶體上限設到 6 GB 以上（三個節點加上 cloud-provider-kind 閒置時約佔 1.7 GB，練習尖峰約 3 GB）。接著在終端機執行：

brew install kind helm kubeconform yq        # kind 0.33、Helm 4、kubeconform 0.8、yq 4
cd learn
npm --prefix kubernetes/practice ci          # 測試用的套件（只有 yaml）
node kubernetes/practice/bin/cluster.mjs up  # 建立叢集

四個工具的用途：kind 建本機叢集；Helm 是 Kubernetes 的打包工具（第 13 課）；kubeconform 離線檢查 YAML 的欄位和型別寫得對不對，之後練習的測試會用它；yq 是終端機裡讀寫 YAML 的工具，用法像處理 JSON 的 jq。第一次 up 要下載超過 1 GB 的映像、建置課程映像，視網路和電腦速度要十幾分鐘到半小時；之後再執行只要幾分鐘。

kubectl 不用另外裝：Docker Desktop 附的是 1.36 版，叢集是 1.37，Kubernetes 官方支援 kubectl 跟 API server 差一個小版本以內。cluster.mjs up 做了這些事（可以重複執行，已經做過的會跳過）：

  1. 用 kubernetes/practice/kind.yaml 建立叢集 learn-k8s，kubeconfig 只寫到 kubernetes/practice/.kube/config（下一節講為什麼）。
  2. 在每個節點預先拉好練習會用到的映像（node、curl、busybox、postgres、redis），之後的練習不用連網路。
  3. 建置課程的 learn-k8s/cafe-api 映像（v1、v2 和幾個故意壞掉的版本），用 kind load 放進每個節點。
  4. 安裝 metrics-server（kubectl top 與第 8 課的自動擴展需要）、啟動 cloud-provider-kind 容器、建立測試工具用的 k8s-tools namespace。

kind.yaml 只有幾行：

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: learn-k8s                 # 叢集名稱；context 會叫 kind-learn-k8s
nodes:
  - role: control-plane         # 1 個 control plane
    image: kindest/node:v1.37.0@sha256:a1ed56cf…   # 節點映像，用 digest 釘住
  - role: worker                # 2 個 worker
    image: kindest/node:v1.37.0@sha256:a1ed56cf…
  - role: worker
    image: kindest/node:v1.37.0@sha256:a1ed56cf…

節點映像後面的 @sha256:… 是 digest：映像內容的雜湊，比 tag 更精確。kind 0.33.0 的 release notes 要求用 digest，才保證拿到的是為這一版 kind 建置的節點映像。建好之後執行 docker ps，會看到 learn-k8s-control-plane、learn-k8s-worker、learn-k8s-worker2 三個容器，它們就是三台「主機」。

其他指令：cluster.mjs status 檢查每一樣東西是否正常；stop 停掉節點容器釋放記憶體（不讀書時用）、start 再開回來；down 整個刪掉。

kubeconfig 與 context：不要打錯叢集

kubectl 怎麼知道要連哪個 API server？答案在 kubeconfig：一個 YAML 設定檔，預設是 ~/.kube/config。裡面有三種清單：

  • clusters：叢集的 API server 位址和 CA 憑證（用來確認連到的真的是這個叢集的 API server，作用跟瀏覽器檢查 HTTPS 憑證一樣）。
  • users：用什麼身分登入（憑證、token 或取 token 的指令）。
  • contexts：一組「哪個叢集＋哪個身分＋預設哪個 namespace」的組合。

最後還有一行 current-context：目前用哪一組。kubectl 的每一個指令都送到 current-context 指的叢集，而且不會問你「確定要對正式環境執行嗎？」。工作後你的 ~/.kube/config 很可能有公司 staging 和 production 叢集的 context；kind create cluster 預設會把新叢集寫進同一個檔案，並且把 current-context 切過去。哪天你以為自己在練習叢集、其實 current-context 是 production，一個 kubectl delete 就是正式事故，這種事真的發生過很多次。

這門課的做法是讓兩邊連不在同一個檔案：課程叢集的 kubeconfig 放在 kubernetes/practice/.kube/config，你在要練習的終端機設定環境變數 KUBECONFIG，kubectl 就只讀這個檔案：

export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"   # 在 learn 資料夾執行；只影響這個終端機視窗
kubectl config get-contexts        # 列出所有 context，* 是目前的
kubectl config current-context     # 只印目前的：kind-learn-k8s

關掉終端機、開新的視窗，KUBECONFIG 就沒了，kubectl 回到讀 ~/.kube/config。練習時先看一眼 current-context 是好習慣。

💡 實務上：正式叢集的 context 要多幾道防呆
工作後同一台筆電常同時有 staging 與 production 的 context，事故多半發生在「以為自己在 staging」。資深工程師常見的做法：終端機提示字元顯示目前的 context（例如 kube-ps1、starship 的 kubernetes 模組），production 顯示紅色；正式環境的 context 預設用唯讀身分，需要改東西時才切換到有寫入權限的身分（第 12 課的 RBAC）；腳本開頭先檢查 context，不對就停下來，而不是自動切過去，練習 2 就是寫這個。很多團隊還有一條規矩：對 production 下寫入指令前，先把指令貼到頻道讓另一個人看一眼。

第一次看叢集

設好 KUBECONFIG 之後，從這幾個指令開始。它們都只會讀，不會改任何東西：

kubectl get nodes -o wide                 # 節點、角色、版本、內部 IP、container runtime
kubectl get pods -A                       # 所有 namespace 的 Pod（-A = --all-namespaces）
kubectl get pods -n kube-system           # 只看 kube-system 這個 namespace
kubectl describe node learn-k8s-worker    # 一個節點的詳細資料與最近的事件
kubectl api-resources                     # 叢集認得的所有資源類型
kubectl explain deployment.spec.replicas  # 某個欄位的說明，不用上網查

namespace 是叢集裡的分組，把物件分開放，名稱只需要在同一個 namespace 裡不重複；權限和資源配額也是以 namespace 為單位設定（第 12 課）。叢集自己的元件放在 kube-system。kubectl get pods -n kube-system 會看到：

Pod 名稱開頭是誰
etcd-、kube-apiserver-、kube-scheduler-、kube-controller-manager-control plane 的四個元件，各一個，都在 control-plane 節點上
kube-proxy-每個節點一個
kindnet-kind 的網路外掛，每個節點一個，負責 Pod 之間的網路
coredns-叢集內的 DNS（第 4 課）
metrics-server-cluster.mjs up 安裝的，收集 CPU 與記憶體用量

describe node 的輸出裡，Capacity 是節點的總資源，Allocatable 是扣掉系統保留之後、可以分給 Pod 的部分。第 8 課設定 Pod 的資源需求時，排程器看的就是 Allocatable。kind 的每個節點回報的都是 Docker Desktop 整台虛擬機的資源，所以三個節點的數字一樣，這是 kind 跟真實叢集不同的地方。

預設的輸出是給人看的表格。要給腳本用時，改成機器好讀的格式：

kubectl get node learn-k8s-worker -o yaml                       # 物件的完整內容（就是存在 etcd 裡的那份）
kubectl get nodes -o jsonpath='{.items[*].metadata.name}'       # 只取某個欄位，空白隔開
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'   # 一行一個
kubectl get pods -n kube-system --no-headers | wc -l            # 不要標題列，再數行數

-o jsonpath 的路徑跟 -o yaml 的結構一一對應：先用 -o yaml 看欄位在哪裡，再寫 jsonpath。{range …}{end} 是對清單裡每一個項目重複中間那段。

kind 不等於正式叢集：kind 沒有雲端負載平衡器、三個「節點」其實在同一台 Mac 上、資源數字是假的。這門課會在每個不同的地方標出 EKS 怎麼做。

練習

本機練習的流程：在 learn 資料夾執行頁面上的指令，第一次會把起始檔複製到 kubernetes/practice/work/01/，你改那裡的檔案、存檔、再執行一次，切回這一頁就看得到結果。需要叢集的測試會先檢查 Docker 和叢集，缺什麼會直接告訴你要執行哪個指令。

練習 1：用 Homebrew 安裝 kind、helm、kubeconform（brew install kind helm kubeconform yq），分別執行 kind version、helm version --short、kubeconform -v，把印出來的那一行原樣貼進 versions.json 對應的欄位。測試會自己再執行一次這三個指令比對，並檢查版本：kind 0.33.x、Helm 4.x、kubeconform 0.8.x、kubectl 至少 1.36、Docker Desktop 在跑。

練習 2：執行 node kubernetes/practice/bin/cluster.mjs up 建好叢集，然後完成 check-context.sh：用 kubectl 取得目前的 context，不是 kind-learn-k8s 時把錯誤訊息印到 stderr（echo "…" >&2）並 exit 1；是的話只印出節點數（一個數字）。測試會檢查叢集本身（3 個 Ready 節點、v1.37.0、metrics-server、cloud-provider-kind、~/.kube/config 沒被動到），再用課程的 kubeconfig 和一份假的「prod-eks」kubeconfig 各跑一次你的腳本：context 不對時，除了讀 kubeconfig 以外不能呼叫任何 kubectl，也不能自己切換 context。

練習 3：寫一個簡化版的控制器 reconcile(desired, actual)。desired 是每個 app 要幾份，例如 { 'cafe-api': 3 }；actual 是目前的 Pod 清單。回傳要做的動作：{ type: 'create', app } 建一個新的 Pod，或 { type: 'delete', name } 刪掉某個 Pod。規則：

  • Failed 的 Pod 不算一份：刪掉它，並補一個新的。Pending（正在啟動）算一份。
  • 某個 app 的 Pod 比要的少就補；比要的多就刪掉最新的（createdAt 最大的）。
  • desired 裡沒有的 app，它的 Pod 全部刪掉。
  • 已經一致時回傳空陣列；把回傳的動作套用之後再呼叫一次，也要回傳空陣列。
  • 不能修改傳入的 desired、actual 和裡面的物件。

真正的副本控制器（ReplicaSet 控制器，第 3 課）比這個複雜一點：縮減時會優先刪還沒排到節點的、還沒 Ready 的 Pod，再來才是比較新的；它也不是自己去建立容器，而是在 API server 新增 Pod 物件，交給 scheduler 和 kubelet 接手。但「觀察、比對、只做差額、重複執行也不會多做」的骨架是一樣的。

練習 4：在 inspect.sh 用 kubectl 即時讀出叢集資訊，印出剛好三行：第 1 行是每個節點的「名稱=可分配記憶體」（Allocatable 的 memory，例如 learn-k8s-worker=8024556Ki），用空白隔開；第 2 行是 kube-system 裡 Pod 的數量；第 3 行是 etcd 的映像（含 tag）。測試會跟自己從 API 查到的值比對，然後在 kube-system 和另一個 namespace 各加一個 Pod 再跑一次，你的第 2 行要跟著變，而且只算 kube-system。腳本只能讀，不能建立、刪除或修改任何東西。

練習 5：你用 kubectl delete pod 刪掉 Deployment 底下的一個 Pod，幾秒後又出現一個名字不同的新 Pod。原因是？

✓ 期望狀態是「3 份」，控制器一直在比對，少一份就補一份，補的是全新的 Pod，所以名字不同。a、d 描述的機制不存在。c 是另一件事：kubelet 會在同一個 Pod 裡的容器崩潰時重開容器，但 Pod 物件被刪掉之後，kubelet 不會把它帶回來。

練習 6：kubectl get pods 的請求會經過哪條路？

✓ API server 是叢集唯一的入口，也只有它直接讀寫 etcd。kubelet、scheduler、控制器都是 API server 的客戶端，kubectl 不會直接連它們，也不會直接連 etcd。

練習 7：團隊只有一個 API 服務、一台 EC2、每月部署一次，主管問要不要導入 Kubernetes。比較好的回答是？

✓ 資深的回答是講取捨，並寫下什麼時候重新評估。Kubernetes 帶來的能力有代價（學習、維運、費用）；a、d 忽略了代價，c 是絕對化的說法，規模長大後就不成立。

練習 8：你的 ~/.kube/config 有公司正式叢集的 context。為什麼本課程要你用獨立的 KUBECONFIG？

✓ kubectl 沒有「確定要對正式環境執行嗎？」這一步，送到哪個叢集只看 context。分開 kubeconfig 是最簡單的防呆。a、b 不對；d 不完全對：kind 不會刪掉別的 context，但預設會把 current-context 切到新叢集，這正是另一個要分開的理由。

常見錯誤

  • 把 Kubernetes 當成比較複雜的 docker run：它的核心是期望狀態。手動 kubectl delete、kubectl edit 做的修改，會被控制器或下一次 apply 蓋掉；要改結果，就改宣告（YAML）再 apply。
  • 沒看 current-context 就下指令：先 kubectl config current-context，或像這門課一樣用獨立的 KUBECONFIG；寫腳本時開頭先檢查。
  • 用 kind create cluster 直接建叢集：它會寫進 ~/.kube/config 並切換 current-context。這門課一律用 cluster.mjs up，kubeconfig 只寫在 kubernetes/practice/.kube/config。
  • Docker Desktop 的記憶體給太少：節點容器被系統殺掉時，API server 會無預警斷線、指令一直逾時。記憶體上限設 6 GB 以上，不讀書時 cluster.mjs stop。
  • 以為 kind 叢集等於正式叢集：kind 沒有雲端負載平衡器、沒有真的多台主機、資源數字是整台虛擬機的。正式環境的差異這門課會逐一標出來。
  • 開了新的終端機就忘了 KUBECONFIG：環境變數只在設定它的那個視窗有效。新視窗裡 kubectl 會讀 ~/.kube/config，找不到叢集或連到別的叢集，先 export KUBECONFIG=… 再操作。

小結

  • Compose 管一台主機上的容器；主機當機、跨主機排程、依負載擴展、不停機更新、多團隊共用，都要自己寫腳本。Kubernetes 把這些做成平台功能，代價是學習、維運和費用。
  • Kubernetes 是宣告式的：你寫下期望狀態，控制器不斷觀察、比對、動作（控制迴圈），讓實際狀態收斂。改結果要改宣告，不是手動動手。
  • control plane 有 API server、etcd、scheduler、controller manager；每個節點有 kubelet、container runtime、kube-proxy。所有人都只跟 API server 說話，只有它讀寫 etcd。
  • 這門課用 kind 在 Mac 上跑 1 個 control-plane＋2 個 worker 的 v1.37.0 叢集，節點映像用 digest 釘住，用 cluster.mjs 建立、停止、刪除。
  • kubectl 的指令送到 current-context 指的叢集。練習用獨立的 KUBECONFIG，腳本開頭先檢查 context，不對就停。
  • get、describe、api-resources、explain 和 -o yaml／-o jsonpath 是看懂叢集的基本工具。
