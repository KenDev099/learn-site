階段 5：正式環境與期末專題 · 第 16 課

期末專題：把咖啡店 NestJS 服務搬上 Kubernetes 並處理事故

前十五課，每一課練一個零件：Pod、Service、probe、HPA、PDB、NetworkPolicy、Helm、除錯流程。真正接手一個服務時，這些零件會同時出現，而且互相影響：NetworkPolicy 寫錯會讓 readiness 失敗，readiness 失敗會讓 Helm 回滾，回滾之後資料庫的 migration 卻不會退回去。期末專題把它們組成一次完整的上線：咖啡店的 API、寄收據的 worker、資料庫 migration，從一份「同事在自己電腦上跑得起來」的 chart 開始，做到能交給值班的人。

做完你會有一份能交給值班同事的 chart、部署腳本、事故紀錄與 runbook，這些也是面試或接手新服務時，資深工程師會問的東西。

這課的路線：
  1. 需求：把老闆說的「尖峰不能卡」「收據不能漏」翻成可以自動檢查的項目。
  2. 架構：API、寄收據的 worker、migration 為什麼是三種不同的物件，資料庫為什麼要分兩個帳號。
  3. 步驟一、二：把同事留下的 chart 修到上線標準，部署腳本為什麼「順序就是可靠性」。
  4. 步驟三、四：在持續流量下換版、維護節點，證明一個請求都沒掉；再照固定的除錯流程處理三個埋好的事故。
  5. 步驟五、上線那天：寫給半夜被叫醒的同事看的 runbook 與決策紀錄，以及程式碼以外決定上線成敗的事。
這課會用到：前面每一課，下面四課最常翻回去：
  • 第 13 課的 Helm：chart 的範本加上 values，helm upgrade 加上 --wait 與 --rollback-on-failure，一個指令完成部署、等待、失敗自動回滾。
  • 第 10 課的 migration Job：每個版本跑一次，部署腳本等它成功才更新應用，失敗就停。
  • 第 14 課的除錯流程：先看狀態，再看事件與 logs --previous，往外查 Service、NetworkPolicy，最後修在 chart 裡並寫事故紀錄。
  • 第 15 課的交付清單：交付服務前逐項確認 requests 與 memory limit、probe 與優雅關機、多副本＋PDB＋分散、securityContext 與 NetworkPolicy、映像釘版本與機密分開、dashboard 與告警。

需求：把老闆的話翻成檢查項目

咖啡店老闆不會說「我要 PDB」。他會這樣說：

「中午尖峰的客人是平常的三倍，不能卡。白天換版不能讓點餐失敗。付了錢一定要收到收據，不能漏也不能寄兩張。真的出事，十分鐘內要恢復。新來的工程師要能照文件部署和回滾，不用打電話問你。」

工程師的工作是把每一句翻成可以檢查的項目。這種「上線前逐項確認服務能被安全地維運」的流程叫上線準備度檢查（production readiness review，devops 課第 26 課）。一項沒有辦法自動檢查的要求，上線後通常會悄悄壞掉，所以這一課每一項都對應到一個測試：

架構：三種工作負載，兩種帳號

NestJS 課期末專題的咖啡店服務有三個部分：處理 HTTP 的 API、從 BullMQ 佇列拿工作寄收據的 worker、資料庫 migration。部署到 Kubernetes 時，它們變成三種不同的物件，因為它們的生命週期不同：

  • api：長時間執行、要收流量、數量隨負載變動 → Deployment＋Service＋HPA＋PDB。
  • worker：長時間執行、不收流量、數量固定 → Deployment，沒有 Service；關鍵是被終止時不能把寄到一半的收據丟掉。
  • migration：每個版本跑一次、跑完就結束 → Job（第 10 課），排在換版之前。

為了不在你的電腦上建置 NestJS 映像（安裝套件、映像約 400 MB、載入叢集要好幾分鐘），練習用課程的 learn-k8s/cafe-api 映像代替 NestJS API（端點、健康檢查、SIGTERM 的行為跟 NestJS 課第 24 課一樣），用一個沒有任何套件的 Node 程式（chart/files/worker.mjs）代替 BullMQ worker，migration 用 postgres 映像的 psql 執行 SQL 檔，代替 prisma migrate deploy。對 Kubernetes 來說，三者的形狀跟真的 NestJS 服務完全一樣，換成真的映像只是改 image。

資料庫與 Redis 放在另一個 namespace（k8s-16-data），由課程的 dev-up.sh 建立。正式環境它們是 RDS 與 ElastiCache（第 11 課），不屬於這個服務的 chart，所以這裡也刻意分開：chart 只知道 Secret cafe-secrets 裡的連線字串。

步驟一：把 chart 做到上線標準

起始的 chart 是前一位同事留下的：helm install 跑得起來，api 也收得到請求，但離上線還差很多。打開 chart/ 對照上面的表格，你會找到這些問題（每一個都是前面某一課的常見錯誤）：

同事的寫法會出什麼事改成
replicas: 2開了 HPA 之後，每次部署都把擴出來的 Pod 縮回 2不輸出 replicas，交給 HPA（第 13 課）
liveness 打 /health/readyRedis 斷線 → 所有 api 一起被重啟 → 雪崩liveness 打 /health/live，加 startupProbe（第 7 課）
沒有 preStop換版時有幾秒的請求被送到已經關門的 PodpreStop.sleep.seconds: 5，寬限期涵蓋 preStop＋關機時間
worker 沒寫寬限期（預設 30 秒）寄信服務最慢 45 秒，job 做到一半被 SIGKILLterminationGracePeriodSeconds: 60
worker 沒有 memory limit記憶體洩漏時拖垮整台節點requests＋limits（第 8 課）
config.DATABASE_URL 寫在 values密碼進了 git、ConfigMap 和 helm get values 的輸出從 Secret cafe-secrets 用 secretKeyRef 取（第 6 課）
沒有 securityContext、用 default ServiceAccountrestricted 的 namespace 直接拒絕 Pod；Pod 帶著用不到的 token共用的 cafe.podSecurity、專屬 ServiceAccount、不掛 token（第 12 課）
沒有 HPA、PDB、分散、NetworkPolicy尖峰撐不住；drain 一次驅逐全部；兩個副本可能在同一台節點；任何 Pod 都能連資料庫補上四個範本

_helpers.tpl 已經有 cafe.podSecurity 與 cafe.containerSecurity 兩段共用的安全設定，api 與 worker 都 include 它們，restricted 的規則只寫一次。

NetworkPolicy 是這一步最容易寫錯的地方，有兩件事前面的課沒遇過。第一，資料庫在另一個 namespace：peer 只寫 podSelector 時只會選到同一個 namespace 的 Pod，要在同一個 peer 裡加上 namespaceSelector（兩者寫在同一個 - 底下是「而且」，分成兩個 - 是「或者」）：

egress:
  - to:
      - namespaceSelector: {}           # 任何 namespace……
        podSelector:                    # ……裡 label 是 postgres 的 Pod（同一個 - 底下＝而且）
          matchLabels: { app.kubernetes.io/name: postgres }
    ports:
      - { protocol: TCP, port: 5432 }

正式環境的 RDS 不是 Pod，這條要改成 RDS 子網路的 ipBlock；所以這段放在 values 或範本裡都可以，但要在 ADR 寫清楚 EKS 上怎麼做。

第二，migration Job 也要一條規則。第一次部署時，Job 在 helm upgrade 之前跑，那時預設拒絕還不存在，所以會過；第二次部署時預設拒絕已經在了，Job 連不到資料庫，部署卡住。這種「第一次會過、第二次才壞」的錯誤，只有真的部署兩次才會發現，練習 3 會幫你部署三次。

做完用三個指令自己檢查，跟測試做的事一樣：

cd kubernetes/practice/work/16
helm lint chart -f chart/values-local.yaml --set image.tag=v1
helm template cafe chart -n k8s-16 -f chart/values-local.yaml --set image.tag=v1 | kubeconform -strict -summary -
helm template cafe chart -n k8s-16 -f chart/values-local.yaml --set image.tag=v1 \
  | kubectl apply --dry-run=server -n k8s-16 -f -     # namespace 有 restricted 標籤時，違規會在這裡被拒絕

最後一行的 --dry-run=server 會把物件送到 API server 走完驗證與 admission（包括 Pod Security），但不存下來。只靠 kubeconform 檢查不出「這個 Pod 在 restricted 的 namespace 會被拒絕」。

💡 實務上：接手同事的 chart，不要一次全改
上面那張表有八列問題，最直覺的做法是一個 PR 全部改完。在正式環境這很危險：部署後如果出事，你不知道是 probe、NetworkPolicy 還是寬限期造成的（第 14 課的「一次只改一個變數」）。動手前先用 helm template … | kubectl diff -n <ns> -f - 確認叢集現在跟 chart 一致，有不一致的先弄清楚是誰手動改的。接著依影響範圍拆成幾個 PR：先改 resources、preStop 這類小的，再改 securityContext 和 probe，最後才上 NetworkPolicy，每個 PR 部署後觀察一段時間再做下一個。

步驟二：deploy.sh，順序就是可靠性

部署腳本只做三件事，但順序不能換：

  1. 這一版的 migration：用 migrate/sql/ 建 ConfigMap cafe-migrate-<版本>，把 migrate/job.yaml 的 __VERSION__ 換掉再套用，等 Job 的 condition：Complete 繼續，Failed 印出 log 並以非 0 結束。這時線上的應用完全沒被動到。
  2. helm 換版：helm upgrade --install cafe ./chart -n "$NS" -f chart/values-local.yaml --set image.tag="$VERSION" --wait --timeout 5m --rollback-on-failure。新版沒 Ready 就自動回到上一個 revision，腳本以非 0 結束。
  3. 煙霧測試（smoke test）：部署後用幾個關鍵請求確認主要功能可用。從叢集內經過 Service 打 /health/ready 與 /products：kubectl exec -n k8s-tools deploy/probe -- curl -fsS -m 5 -o /dev/null http://cafe-api.$NS.svc.cluster.local/products。-f 讓 curl 遇到 4xx／5xx 時以非 0 結束，沒有它的話 503 也算「成功」。

為什麼 migration 不放在 api 的 initContainer（第 10 課）？initContainer 每個 Pod 都跑一次：HPA 擴到 4 個就跑 4 次、滾動更新時新 Pod 的 migration 跟線上的舊版搶鎖，而且 api 得拿著能改表的帳號。這就是架構圖裡兩種帳號的意義：dev-up.sh 在資料庫建了 cafe_migrator（擁有資料表，可以 ALTER）和 cafe_app（只能 SELECT／INSERT／UPDATE／DELETE），Secret 裡分別是 DATABASE_URL_MIGRATOR 與 DATABASE_URL。api 被入侵時，攻擊者拿到的帳號刪不了表。

還有兩個細節。同一版重新部署時（例如回滾之後再上一次 v2），cafe-migrate-v2 已經存在，Job 的 Pod 範本建立後不能改：先 kubectl delete job "$JOB" --ignore-not-found --wait 再建立；migration 執行器會略過 schema_migrations 裡已經有的檔案，所以重跑是安全的。另外，叢集很忙時 kubectl get 偶爾會逾時，在 set -e 底下 state=$(kubectl get …) 失敗會讓整個腳本直接結束；查詢失敗要當成「還在跑」：state=$(kubectl get …) || state=""。

rollback.sh 一行就夠：helm rollback cafe -n "$NS" --wait --timeout 3m（不給 revision 就回到上一個）。不要用 kubectl rollout undo：它只改 Deployment，Helm 的紀錄、ConfigMap、HPA 都不會跟著回去，下次 helm upgrade 又是另一個樣子。回滾不碰資料庫，這是下一步要 expand 的原因。

步驟三：上線驗收，在流量下證明

「我部署過，沒問題」不算驗收。驗收要在持續流量下做會出事的動作，看錯誤數是不是 0。練習 3 的測試會用 loadgen 每秒送 10 個請求，同時依序做：

  1. deploy.sh v2：v2 帶一個新的 migration。
  2. rollback.sh：回到 v1，但資料庫已經是 v2 的樣子。
  3. 再 deploy.sh v2：同一版第二次部署。
  4. drain 一個 worker 節點（測試只驅逐這一題的 Pod，不打擾其他練習），同時送 20 張收據進佇列。

第 2 步決定了 v2 的 migration 怎麼寫。v1 的程式在新的資料庫上要能正常跑，所以只能做 expand：加一個可以是 NULL 的欄位。改名、刪欄位、加 NOT NULL 都是 contract，要等確定不會再回到 v1 的下一版才做（devops 課第 17 課）：

-- migrate/sql/002_add_receipt_sent_at.sql
SET lock_timeout = '5s';
ALTER TABLE orders ADD COLUMN receipt_sent_at timestamptz;

lock_timeout 是給 ALTER TABLE 的保險。ALTER 要拿到表的排他鎖，如果剛好有一個長交易拿著鎖，ALTER 會排隊，而排在它後面的所有查詢也一起等，整個訂單功能就停了。設了 lock_timeout，拿不到鎖就失敗，Job 變 Failed，deploy.sh 停下來，線上照常運作，換個時間再部署。

第 4 步驗證兩件事。api 這邊，PDB 的 maxUnavailable: 1 讓 drain 一次只驅逐一個 Pod，分散規則的 nodeTaintsPolicy: Honor 讓新的 Pod 排到另一台節點（第 9 課）；如果 PDB 寫成 minAvailable: 2，而 HPA 的最小值也是 2，drain 會永遠卡住。worker 這邊，被驅逐的 worker 收到 SIGTERM 後不再拿新的 job，把手上那張收據寄完才結束，留在佇列的由另一個 worker 接手。

「不漏」靠優雅關機與寬限期，「不重複」靠冪等，兩者都要。就算優雅關機寫對了，節點突然斷電時 job 還是會中斷，BullMQ 在鎖過期後會重試它（NestJS 課第 20 課）。所以寄送本身要能安全地重複：worker.mjs 用 SET receipt:<訂單> … NX，同一張訂單只會記一次。測試比對的是「收據數＝訂單數」，而不是「worker 沒有出錯」。

HPA 的擴縮在第 8 課已經在叢集上驗證過，這裡只靜態檢查它的設定。要自己看它動作，可以在部署好之後對 /burn?ms=200 加壓，用 kubectl get hpa -n k8s-16 -w 看副本數變化；values-local 把縮容穩定視窗設成 60 秒，加壓停止後大約一兩分鐘就縮回 2。如果擴出來的 Pod 一直 Pending，看事件裡的 Insufficient cpu：本機叢集只有兩個 worker 節點，節點數不會自己增加。

步驟四：事故演練

同事把 v3 的變更合併進了團隊的正式版 chart（ex4/chart/），部署後值班的人收到三個告警：

  • 事故 A：cafe-api 部署後一直沒有 Ready。
  • 事故 B：cafe-worker 一直重啟。
  • 事故 C：中午尖峰時 cafe-api 的 Pod 數沒有增加。

執行 bash kubernetes/practice/work/16/ex4/start.sh，它會在 k8s-16-incident 從零建立環境、部署這份 chart（不加 --wait，壞掉的狀態會留著給你查），再放 5 張收據進佇列。用第 14 課的流程：kubectl get pods -o wide 看狀態 → describe 看事件與 Last State → logs --previous → 往外查相關的物件（Service、EndpointSlice、NetworkPolicy、HPA）。先蒐證，不要先改。

事故 C 跟另外兩個不同：它不會讓任何 Pod 壞掉，平常的流量也看不出來，要到尖峰才會發現。這類「設定錯了但不會立刻爆」的問題，只能靠主動檢查物件的狀態找到。HPA 的狀態寫在 kubectl describe hpa 的 Conditions：AbleToScale 表示找不找得到要擴展的目標，ScalingActive 表示拿不拿得到指標。

找到原因之後，修在 ex4/chart/，然後再執行一次 start.sh，確認從零部署也不會再出事。用 kubectl edit 在叢集上改好只是止血，下一次部署會把錯誤帶回來。修的時候也不能拿掉安全措施：把整個 NetworkPolicy 刪掉，Redis 確實連得到了，但那是用一個更大的問題蓋住原本的問題。

根因代碼從這裡選（多數是干擾選項）：

netpol-dns-blocked     netpol-redis-port       secret-key-renamed     image-tag-typo
readiness-wrong-path   worker-oom-limit        worker-no-grace-period hpa-wrong-target
hpa-no-requests        pdb-blocks-drain        migration-no-lock-timeout

做完執行 kubectl delete namespace k8s-16-incident k8s-16-incident-data。

步驟五：寫給下一個人的文件

服務能跑之後，剩下的風險是「只有你知道怎麼操作它」。兩份文件解決這件事：

runbook：照著做就能部署、回滾、擴展、處理告警的操作手冊。讀的人通常是半夜被叫醒、對這個服務不熟的同事，所以每一節是一兩句說明加上可以直接複製執行的指令，不是解釋原理的文章。寫 runbook 時最常見的錯誤是指令跑不動：少了 -n 打到 default namespace、release 名稱跟部署腳本不一樣、少了一個步驟。每個指令都要真的執行過一次。

💡 實務上：輪替資料庫密碼，容易漏最後一步
員工離職、密碼外洩，或資安要求定期更換時，都要照 runbook 輪替資料庫密碼。Secret 用環境變數注入時，只在容器啟動時讀一次；更新 Secret 之後，正在跑的 Pod 還拿著舊密碼，等到舊密碼停用的那一刻才一起失敗。所以順序是：資料庫加新密碼（舊的先不停）→ 更新 Secret → kubectl rollout restart api 與 worker → 確認新 Pod 都 Ready → 停用舊密碼。第一次做選在離峰時段，先在 staging 跑一遍，順便確認 runbook 的每個指令都能直接執行。

ADR（架構決策紀錄，devops 課第 26 課）：每個重要的設計決定一份，寫背景、決策、後果、以及在 EKS 上的做法。「後果」最重要也最常被省略：沒有寫代價的決策紀錄，一年後的人不知道當初接受了什麼風險，也就不知道什麼時候該重新考慮。這個專題值得寫的決定，例如 migration 用 Job 而不是 initContainer、資料庫用 RDS 而不是叢集裡的 StatefulSet、Helm 還是 Kustomize、HPA 用 CPU 還是請求數。

實務：上線那天與之後

這一課的練習在本機叢集跑完。真正的上線還有幾件跟程式碼無關、但決定成敗的事：

  • 挑時間、找人：第一次上線避開尖峰與週五下午；確定誰按部署、誰看監控、誰有權限決定回滾。回滾的條件事先講好（例如 5xx 比例超過 1% 持續 2 分鐘），不要出事時才開會討論。
  • 先看得到，再上線：dashboard 至少有請求數、錯誤率、延遲、Pod 數與重啟次數、佇列長度；告警設在使用者感受得到的症狀上（錯誤率、延遲、佇列堆積），而不是 CPU 高。這一項沒有自動測試，但第 15 課的交付清單裡有它。
  • 交接：值班的人要知道 runbook 在哪、有哪些告警、上游下游是誰。上線後一週內出的第一個事故，事後檢討通常會改 runbook。
  • 清單會長大：每一份事故紀錄的「預防」都可能變成上線檢查的一項。練習 1 的測試就是一份可以執行的清單，放進 CI 之後，同樣的錯誤就不會再進到叢集。

回頭看，從第 1 課的控制迴圈到這裡，你寫的每一個物件都是在宣告期望狀態，由某個控制器負責讓現實追上它：Deployment 控制器維持副本、HPA 調整副本數、Job 控制器跑到完成、kube-proxy 與 NetworkPolicy 的實作把規則寫進節點。除錯就是找出「哪一個迴圈追不上、為什麼」。

練習

在 learn 資料夾執行 export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"，再執行頁面上的指令，起始檔會複製到 kubernetes/practice/work/16/。五題是同一個專案：練習 2、3 用的是你在練習 1 改好的 chart。想自己先試時，bash kubernetes/practice/work/16/dev-up.sh 會從零建立 k8s-16 與 k8s-16-data（約 2～5 分鐘），之後在 work/16/ 執行 bash deploy.sh v1；用完 kubectl delete namespace k8s-16 k8s-16-data。練習 1、5 和練習 4 的檔案檢查幾秒就跑完；練習 2、3、4 的叢集部分要部署到測試自己的 namespace（k8s-16-ex2 等），每題要 5～20 分鐘。

練習 1：把 chart/ 做到上線標準。api：不輸出 replicas、startupProbe 與 livenessProbe 打 /health/live、readinessProbe 打 /health/ready、preStop.sleep 至少 3 秒、寬限期 ≥ preStop＋15 秒、topologySpreadConstraints（hostname、maxSkew 1、nodeTaintsPolicy: Honor）、DATABASE_URL 與 REDIS_URL 用 secretKeyRef 從 cafe-secrets 的同名 key 取。worker：寬限期 ≥ 60 秒、memory limit。每個容器都有 CPU／記憶體 requests 與 memory limit、明確的映像 tag 與 IfNotPresent；api、worker 用 chart 的 ServiceAccount 且不掛 token、Pod 範本有 checksum annotation，並套用 _helpers.tpl 的兩段安全設定。補上 HPA（cafe-api，2～4、CPU，縮容穩定視窗用 values 控制，values-local 設 ≤ 60 秒）、PDB（只選 api，maxUnavailable: 1）、NetworkPolicy（預設拒絕；所有 Pod 能查 DNS；api 收 3000、連 postgres 5432 與 redis 6379；worker 只連 redis；component: migrate 的 Pod 只連 postgres）。values 檔裡不能有連線字串或密碼。測試跑 helm lint、kubeconform、上面每一項，最後把 chart 與 migration Job 用 --dry-run=server 送到 restricted 的 namespace。

練習 2：完成 deploy.sh <版本>（namespace 用 NS 環境變數，預設 k8s-16）：用 migrate/sql/ 建 ConfigMap cafe-migrate-<版本>、刪掉同名的舊 Job、把 migrate/job.yaml 的 __VERSION__ 換成版本後套用；等 Job 完成（Failed 就印 log 並以非 0 結束，查詢失敗當成還在跑）；再 helm upgrade --install cafe ./chart -f chart/values-local.yaml --set image.tag=<版本> --wait --timeout 5m --rollback-on-failure；最後用 kubectl exec -n k8s-tools deploy/probe -- curl -fsS … 對 /health/ready 與 /products 做煙霧測試。api 不能用 migrator 帳號，migration 不能放在 initContainer。測試用 dev-up.sh 從零建環境、執行 deploy.sh v1：Job 要在 api 的 Deployment 建立前完成、orders 的擁有者是 cafe_migrator、api 與 worker 各 2 個 Ready、煙霧測試的 curl 有 -f，放進佇列的 3 張收據要被寄出。

練習 3：寫 v2 的 migration migrate/sql/002_add_receipt_sent_at.sql：先 SET lock_timeout，再在 orders 加可以是 NULL 的 receipt_sent_at timestamptz，不改名、不刪除。完成 rollback.sh：用 helm rollback cafe、-n "$NS"、--wait。測試先部署 v1，然後在每秒 10 個請求下依序 deploy.sh v2 → rollback.sh → deploy.sh v2：每一步結束時 Ready 的 api 全部是那一版、helm history 有 4 個 revision、全程 0 錯誤、回滾後欄位還在、每個 migration 只套用一次；接著在流量下 drain learn-k8s-worker2（只驅逐這一題的 Pod）同時送 20 張收據：drain 成功、0 錯誤、收據剛好 20 張。PDB 要允許驅逐（練習 1 寫對的話不用改）。

練習 4：事故演練。執行 ex4/start.sh，用第 14 課的流程查出 A、B、C 三個事故的根因，在 incidents.json 填 cause（上面的根因代碼）與 evidence（你看到證據的那一行 kubectl 指令）；修在 ex4/chart/（不能拿掉預設拒絕、不能把 egress 放寬成任何 port、不能拿掉 worker 的 memory limit）；在 INCIDENTS.md 的三份紀錄寫時間軸（至少 3 個時間點）、影響、根因（寫出根因代碼並說明怎麼造成症狀）、修正、預防（至少一條，用 - 開頭）。測試檢查這三個檔案，再從零部署你的 ex4/chart：api 與 worker 都 Ready、worker 沒有重啟且寄得出收據、HPA 的 AbleToScale 是 True。

練習 5：完成 RUNBOOK.md 的五節（部署、回滾、擴展、處理 CrashLoopBackOff、輪替資料庫密碼），每節一兩句說明加上一個 ```bash 區塊。每個 kubectl、helm 指令都明寫 -n k8s-16（不屬於 namespace 的指令除外），helm 的 release 是 cafe，區塊要通過 bash -n；CrashLoopBackOff 一節要有 describe 與 logs --previous；輪替密碼一節要更新 Secret，再 rollout restart cafe-api 與 cafe-worker。完成 DECISIONS.md：至少 3 個 ADR（## 標題），每個都有內容充實的 ### 背景、### 決策、### 後果、### 在 EKS 上。

練習 6：worker 正在寄收據時，Pod 因為滾動更新被終止。這張收據會怎樣？最穩妥的設計是？

✓ 優雅關機讓中斷變少，冪等讓中斷之後的重試不會寄兩張，兩者都要（NestJS 課第 20、24 課）。a 不對：佇列會重試沒有完成的 job，不一定遺失；c 會在寄到一半時直接 SIGKILL，正好造成中斷；d 失去了自我修復與滾動更新，節點一掛 worker 就沒了，也不會讓 SIGTERM 消失。

練習 7：你修好了事故 A（NetworkPolicy 擋掉 Redis），服務恢復了。最該確認的是？

✓ 修在宣告裡、加上預防，同樣的錯才不會回來。a 只是止血，下次部署會把錯誤帶回來；c 用移除安全措施換方便，是掩蓋而不是修正，被入侵的 Pod 從此可以連任何地方；d 跟根因無關，Redis 本身一直是好的。

練習 8：上線驗收時 HPA 擴到 4，但新的 Pod 一直 Pending，事件是 Insufficient cpu。在 kind 和在 EKS 上分別怎麼處理？

✓ HPA 只負責建立 Pod，節點的容量是另一層（第 8、15 課）。a 會建立更多 Pending 的 Pod；c 讓排程器以為 Pod 不用資源，節點被塞爆，HPA 也算不出使用率；d 是換版策略，跟容量無關，還會在換版時停機。

常見錯誤

  • 只顧 API 忘了 worker：worker 也要 resources、優雅關機、寬限期、NetworkPolicy 與告警（佇列長度）。它沒有 Service，壞了不會有人收到 5xx，只會有客人沒收到收據。
  • migration 與應用同時上線：寫在 initContainer 或啟動程式裡，每個副本都跑、跟舊版搶鎖、應用拿著能改表的帳號。先 Job、等成功、再換版。
  • migration 不是 expand：改名或刪欄位之後，回滾到舊版也救不回來。這一版只加，下一版才刪。
  • 忘了 migration Job 的 NetworkPolicy：第一次部署會過（預設拒絕還不存在），第二次就卡住。部署兩次再說它能用。
  • 修在叢集上：kubectl edit 止血之後沒改 chart，下次部署事故又回來。
  • 為了過關移除安全設定：NetworkPolicy、memory limit、probe 都是上線標準的一部分。拿掉它們讓症狀消失，問題還在。
  • 煙霧測試不會失敗：curl 沒加 -f、指令後面接 || true，壞掉的部署也顯示成功。
  • 文件裡的指令跑不動：少了 -n、release 名稱打錯、輪替密碼後沒有 rollout restart。runbook 的每個指令都要實際執行過。

小結

  • 上線準備度檢查：把需求翻成可以自動檢查的項目，每一項對應到一個設定、一課、一個測試。
  • 三種工作負載三種物件：api 是 Deployment＋Service＋HPA＋PDB，worker 是沒有 Service 的 Deployment（寬限期大於最長的 job），migration 是每版一次的 Job。
  • chart 的上線標準：不輸出 replicas、三種 probe 各司其職、preStop 與寬限期、requests 與 limits、restricted、專屬 ServiceAccount、預設拒絕的 NetworkPolicy、機密只從 Secret 來。
  • 部署順序：migration（migrator 帳號，失敗就停）→ helm upgrade --wait --rollback-on-failure → 會失敗的煙霧測試。回滾不碰資料庫，所以 migration 只做 expand，加上 lock_timeout。
  • 驗收要在流量下做會出事的動作：換版、回滾、再換版、drain，錯誤數是 0；收據數等於訂單數。
  • 事故照第 14 課的流程查，修在 chart，從零部署驗證，寫事故紀錄與預防；runbook 的指令都能直接執行，ADR 寫出後果與 EKS 上的做法。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：上線一週後，cafe-api 在尖峰時偶爾重啟。logs --previous 是空的，describe 的 Last State 是 Terminated、Exit Code 137，下一步的判斷哪個對？

✓ 大於 128 是被訊號結束，137－128＝9，也就是 SIGKILL；被殺的程序沒機會寫 log，所以空的 log 本身就是線索。OOM 會殺，liveness 失敗、寬限期到了 kubelet 也用 SIGKILL，要看 reason 才知道是哪一個。b 錯在沒看證據就改設定：如果是 liveness 殺的，加大 limit 什麼都沒修到，還多改了一個變數。（第 14 課）

練習 10：deploy.sh 的煙霧測試失敗：api 都是 1/1 Running，port-forward pod/ 直接打 /products 是 200，從 k8s-tools 用 Service 名字打卻連不上。kubectl get endpointslice 的 ENDPOINTS 是 <unset>，最可能的原因？

✓ EndpointSlice 是控制器依 Service 的 selector 挑出 Ready 的 Pod 寫進去的；Pod 都 Ready 卻一個都沒有，就是 selector 沒選到。用 describe service 的 Selector 對照 get pods --show-labels，修在 chart。a 錯在 NetworkPolicy 擋的是封包，不會讓 EndpointSlice 變空，症狀是連線逾時。（第 4、14 課）

練習 11：期末專題的 chart 改由 Argo CD（automated、selfHeal）部署到 prod。v4 合併後 Argo CD 顯示 Synced 但 Degraded，新 Pod 一直 CrashLoopBackOff，要怎麼回到 v3？

✓ Synced 只表示叢集跟 git 一樣，git 裡就是壞掉的 v4；GitOps 的回滾是 git revert，Argo CD 再把叢集同步成 v3。b 錯在 rollout undo 是叢集上的手動修改，對 selfHeal 來說就是 drift，幾秒後又被改回 v4；真的等不及時，要先暫停這個 Application 的自動同步並留紀錄。（第 15 課）

練習 12：資安要求「CI 被入侵，也不能改到正式叢集」，而 deploy.sh 現在在 CI 裡跑。怎麼改才符合？

✓ GitOps 是 pull 型：CI 手上沒有叢集的憑證，被入侵最多開一個 PR，還要有人 review 才會上線。a 最多人選，它縮小了範圍，但被入侵的 CI 照樣能改 cafe-prod 裡的任何東西，不符合要求。d 也不行：GITHUB_TOKEN 推不到別的 repo，跳過 PR 也就跳過了 review。（第 15 課）

練習 13：部署完成後，同事想省資源，執行 kubectl scale deployment cafe-api --replicas=1，不到一分鐘又變回 2 個。是誰改回去的？

✓ 每個物件都是期望狀態，由各自的控制器不斷比對、動作；HPA 每 15 秒算一次，結果夾在 2～4 之間，再改 Deployment 的 replicas。要改常態的副本數，就改 chart 裡 HPA 的 minReplicas 走正常部署。a 錯在 Deployment 控制器只追 spec.replicas，scale 已經把它改成 1，它照做；chart 也沒輸出 replicas。（第 1、8 課）

練習 14：平台團隊升級節點時說 cafe-api 所在的節點 drain 一直卡住。chart 的 PDB 是下面這樣，HPA 最小 2 個，現在正好 2 個 api，為什麼？

apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2
  selector: { matchLabels: { app.kubernetes.io/name: cafe-api } }

✓ drain 走驅逐 API，要先問 PDB 還能中斷幾個；2 個副本、至少要 2 個可用，答案永遠是 0，節點升級就被你的服務擋下。改成 maxUnavailable: 1，一次驅逐一個，新 Pod 在別台 Ready 後再驅逐下一個。c 錯在 drain 不會繞過 PDB 改用刪除，它就是因為尊重 PDB 才卡住。（第 9、15 課）

練習 15：同事想讓一台節點多放幾個 api，把 requests 寫得比量測值小很多。這樣會出什麼事？

resources:
  requests: { cpu: 50m, memory: 128Mi }   # 量測：平常 300m、400Mi
  limits:   { memory: 512Mi }

✓ requests 是保留量，排程器只看它，實際用量加起來會超過節點；HPA 以 requests 為分母，300m 對 50m 是 600%，永遠擴到最大。requests 要設在量測的平常用量附近。b 最多人選，但 requests 不是上限，節點有空閒 CPU 時可以用超過，只有 CPU limit 才會節流。（第 8 課）

練習 16：負載下換版時出現少量 connection refused，都在某個舊 Pod 開始終止後的一兩秒內。readiness 設定正確、maxUnavailable 是 0，原因與修法？

✓ Pod 終止時，EndpointSlice 移除它和 kubelet 執行 preStop→SIGTERM 是平行的；kube-proxy 與 Gateway 還沒更新前，新連線仍會送到已經關門的程序。preStop 先等幾秒再讓應用關門，寬限期 ≥ preStop＋最長請求＋收尾。c 錯在終止中的 Pod 一開始就被移出端點，不用等 probe 失敗。（第 7、9 課）

這個階段的重點整理成一頁圖解。
