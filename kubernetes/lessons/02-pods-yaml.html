階段 1：起步：從 Compose 到叢集 · 第 2 課

第一個 Pod：映像、YAML 與 kubectl apply

上一課建好了叢集，但叢集裡還沒有咖啡店的東西。這一課把 devops 課那個 docker run 起來的 cafe-api 搬進 Kubernetes：寫成一份 YAML，用 kubectl apply 交給叢集，看它從 Pending 走到 Running。

這課的路線：
  1. 從 docker run 到 Pod、manifest 的骨架：同一個 docker run 寫成 YAML 長什麼樣，每個欄位對應哪個參數，YAML 又會把哪些值悄悄讀錯。
  2. 把映像放進叢集、apply 與除錯指令：kind 的節點看不到 Mac 上的映像怎麼辦；Pod 卡在 Pending 或一直崩潰時，哪個指令告訴你原因。
  3. label 與 namespace：用標籤挑出一群物件（之後的 Deployment、Service 都靠它），用 namespace 隔出自己的試驗區。
  4. 一個 Pod 多個容器：主程式啟動前先等資料庫的 init container、在旁邊幫忙的 sidecar，什麼時候該放在同一個 Pod。
  5. 為什麼幾乎不直接建 Pod：Pod 被刪掉就不會回來，正式環境交給下一課的 Deployment。
這課會用到：
  • 第 1 課的叢集與 kubectl：本機的三節點 kind 叢集，終端機先設好 KUBECONFIG 指向練習用的設定檔，指令才不會打到別的叢集。
  • devops 課第 8 課的 Dockerfile：ENTRYPOINT＋CMD 決定容器啟動時執行什麼，EXPOSE 只是標示程式聽的 port。

從 docker run 到 Pod

在 devops 課，你這樣跑一個 cafe-api：

docker run -d --name cafe-api -e REQUIRE_DB=0 -e APP_ENV=dev -p 3000:3000 learn-k8s/cafe-api:v1

Kubernetes 不接受這種「現在就去執行」的命令，它要的是一份描述「我要什麼」的檔案，叫 manifest（描述物件期望狀態的 YAML 或 JSON 檔）。同一件事寫成 manifest：

apiVersion: v1                  # 這個物件屬於哪個 API 群組與版本
kind: Pod                       # 物件的種類
metadata:                       # 名字與標籤
  name: cafe-api                #   ← --name cafe-api
  labels:
    app.kubernetes.io/name: cafe-api
spec:                           # 你要的樣子
  containers:
    - name: api                 # 容器在 Pod 裡的名字
      image: learn-k8s/cafe-api:v1          # ← 映像
      imagePullPolicy: IfNotPresent         # 節點上有就不去 registry 拉（下一節講）
      ports:
        - containerPort: 3000   # ← 程式聽的 port（只是宣告，不是 -p）
      env:                      # ← -e
        - name: REQUIRE_DB
          value: "0"
        - name: APP_ENV
          value: dev
      resources:                # 資源需求與上限，第 8 課細講；練習的每個 Pod 都寫
        requests: { cpu: 50m, memory: 64Mi }
        limits: { memory: 128Mi }

這就是一個 Pod：Kubernetes 裡最小的部署單位。它包住一個或多個容器，這些容器共用同一個 IP、可以共用 volume，而且一定被排到同一個節點上。大多數時候一個 Pod 只有一個容器，你可以先把它想成「Kubernetes 版的 docker run」。

docker run／ComposePod 的欄位差別
--name／service 名稱metadata.name同一個 namespace 裡不能重複
映像containers[].image節點要拉得到（下一節）
-e／environmentcontainers[].env值一律是字串（用環境變數注入設定，見 devops 課第 11 課）
-p 3000:3000／portscontainerPort 只是宣告對外開放靠 Service、Gateway（第 4、5 課）；除錯用 port-forward
映像後面的參數／commandcommand、args後面「apply 與狀態」一節
restart: unless-stoppedspec.restartPolicy預設 Always：容器結束就在同一個 Pod 裡重開
volumesspec.volumes＋volumeMounts後面「一個 Pod 多個容器」一節

manifest 的骨架與 YAML 的陷阱

每個 Kubernetes 物件都有同樣的頂層欄位：

  • apiVersion：物件屬於哪個 API 群組與版本。核心物件（Pod、Service、ConfigMap）是 v1；Deployment 是 apps/v1，斜線前面是群組。
  • kind：物件種類。
  • metadata：name、namespace、labels、annotations。namespace 是叢集裡的資料夾：名稱只要在同一個 namespace 裡不重複，權限與配額也以它為單位。annotation 也是 key: value，但只是說明資料（例如「誰負責」「從哪個 commit 部署」），不能拿來挑物件。
  • spec：你要的樣子，也就是第 1 課的期望狀態。
  • status：叢集回報的現況（Pod 的 IP、跑在哪個節點、容器狀態）。這是叢集填的，你的 YAML 不要寫。

欄位這麼多，不用背。kubectl explain 會從叢集讀出每個欄位的說明（第 1 課用過），用點號一層一層往下查：

kubectl explain pod.spec.containers                   # 容器有哪些欄位
kubectl explain pod.spec.containers.imagePullPolicy   # 某個欄位：型別、可用的值、預設值
kubectl explain pod.spec --recursive | less           # 整棵欄位樹

YAML 有幾個會讓新手卡很久的地方：

  • 縮排就是結構：只能用空白、不能用 Tab。containerPort 少縮兩格，就從 ports 清單裡跑到容器那一層，變成容器上一個不存在的欄位。
  • - 開頭是清單的一項：containers、env、ports 都是清單，每一項前面一個 -。
  • 型別看寫法：3000 是數字、"3000" 是字串、true 是布林值。env 的 value 規定是字串，寫 value: 0 或 value: true 會被 API server 拒絕。數字、true／false、看起來像數字的版本號（"1.10"）都要加引號。
  • YAML 1.1 的 yes／no：有些工具會把 yes、no、on、off 讀成布林值。要的是字串就加引號。

寫完先檢查，不要直接打到叢集。兩道檢查各管不同的事：

kubeconform -strict -kubernetes-version 1.37.0 pod.yaml   # 離線：欄位存不存在、型別對不對
kubectl apply --dry-run=server -f pod.yaml               # 送到 API server 驗證，但不存進去

kubeconform 用 JSON Schema 檢查，不連叢集，適合放在 CI；但它只看結構，例如 label 的值超過 63 個字元，它不會發現。--dry-run=server 走完 API server 的全部驗證，只差最後不寫進 etcd，能抓到值的錯誤。

💡 實務上：manifest 的檢查放進 CI，不靠人眼
manifest 的 PR 跟程式碼一樣要過 CI：kubeconform 不用連叢集，每個 PR 都跑得起來；--dry-run=server 要連得到 API server、也要有權限，通常放在部署前一步。部署前還可以跑 kubectl diff -f pod.yaml，它印出叢集現況和檔案之間的差異，review 時看得出這次到底改了什麼，也會抓到有人手動改過叢集。code review 時，資深工程師會特別看映像 tag、resources 和 label 有沒有照團隊的慣例寫。

把映像放進叢集

kind 的節點是 Docker 容器，裡面有自己的 containerd（第 1 課），看不到你 Mac 上 Docker 的映像。節點要拿到映像只有兩條路：

  1. 從 registry（Docker Hub、ECR）拉。正式環境都是這樣：CI 建好映像推到 ECR，節點去拉（devops 課第 16 課）。
  2. 本機叢集專用：kind load docker-image learn-k8s/cafe-api:v1 --name learn-k8s，把 Mac 上的映像直接複製進每個節點，省掉 registry。cluster.mjs up 已經用 bin/images.mjs 幫你做了這件事。

節點什麼時候去 registry 拉，由 imagePullPolicy 決定：

值行為
Always每次啟動容器都去 registry 確認；拉不到就失敗
IfNotPresent節點上已經有就直接用，沒有才拉
Never只用節點上的，沒有就失敗（ErrImageNeverPull）

沒寫 imagePullPolicy 時，API server 依映像的寫法幫你填（官方文件）：tag 是 :latest 或沒寫 tag，填 Always；其他 tag 或用 digest，填 IfNotPresent。這條規則在 kind 上會造成一個經典的錯誤：

image: learn-k8s/cafe-api:latest     # 或 image: learn-k8s/cafe-api（沒寫 tag 就是 latest）
→ imagePullPolicy 被填成 Always
→ kubelet 一定去 Docker Hub 找 learn-k8s/cafe-api:latest，找不到
→ ErrImagePull，接著 ImagePullBackOff（等一段越來越長的時間再試）

就算你 kind load 過，也一樣失敗。所以這門課一律寫明確的 tag，並寫上 imagePullPolicy: IfNotPresent。正式環境的理由更重要：latest 看不出現在跑的是哪一版，回滾也不知道要回到哪裡。正式環境用不可變的 tag（例如 git commit SHA）或 digest。

💡 實務上：「線上現在是哪一版」要能馬上回答
事故時第一個問題常是「線上跑的是哪個 commit？」。常見做法是 CI 用 git commit SHA 當映像 tag（例如 cafe-api:3f9c2ab），同時把版本寫進 app.kubernetes.io/version label（後面「label 與 namespace」一節），kubectl get pods -L app.kubernetes.io/version 一眼就看得到。每次覆寫同一個 tag 的話，節點上已經有舊映像的會繼續用舊的（IfNotPresent），兩個節點可能跑著內容不同的「同一版」，回滾也不知道要回到哪裡。

apply、狀態與除錯指令

先建一個 namespace 當自己的試驗區，再 apply：

export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"   # 在 learn 資料夾；新終端機都要先做
kubectl create namespace k8s-02-try
kubectl apply -n k8s-02-try -f pod.yaml        # pod/cafe-api created
kubectl get pods -n k8s-02-try -w              # -w 持續看變化，Ctrl+C 結束

kubectl apply 把檔案裡宣告的狀態送到叢集：沒有就建立、有就更新成檔案的樣子，可以重複執行，第二次會印 unchanged。這就是第 1 課說的宣告式：檔案是真相，手動 kubectl edit 的修改，下次 apply 就被蓋回去。

Pod 有一個 phase，是整個 Pod 的大方向：

phase意思
PendingAPI server 收下了，但容器還沒全部跑起來：在等排程、在拉映像、在跑 init container，或卡住了
Running已經排到節點，至少一個容器在執行（或正在重開）
Succeeded所有容器都以 exit 0 結束，而且不會再重開（一次性的工作，第 10 課的 Job）
Failed所有容器都結束了，至少一個失敗，不會再重開
Unknown跟節點失聯，不知道狀況

phase 很粗。真正的原因在每個容器的狀態：Waiting（還沒跑，附一個 reason）、Running、Terminated（附 reason 與 exit code，也就是程序結束時回報的數字，0 是成功，見 Node 課第 2 課）。例如一直崩潰的容器，Pod 的 phase 仍是 Running，容器卻是 Waiting: CrashLoopBackOff。kubectl get pods 的 STATUS 欄顯示的通常是容器的 reason，不是 phase。

容器 Waiting 的 reason通常的原因去哪裡看
ContainerCreating、PodInitializing正常的過渡狀態等一下
ErrImagePull、ImagePullBackOff拉不到映像：tag 打錯、latest、沒有權限describe 的 Events
CrashLoopBackOff容器啟動後結束，一直被重開，重開的間隔越來越長logs --previous
CreateContainerConfigError引用的 ConfigMap／Secret 不存在（第 6 課）describe 的 Events

五個每天都會用的指令：

kubectl get pods -n k8s-02-try -o wide           # 狀態、重啟次數、Pod IP、在哪個節點
kubectl describe pod cafe-api -n k8s-02-try      # 詳細資料；最下面的 Events 是叢集對它做過的事
kubectl logs cafe-api -n k8s-02-try              # 容器的 stdout／stderr；-f 持續看；--previous 看上一次崩潰前的
kubectl exec -it cafe-api -n k8s-02-try -- sh    # 進到容器裡執行指令（-- 後面是要執行的指令）
kubectl port-forward -n k8s-02-try pod/cafe-api 18020:3000   # 本機 18020 → Pod 的 3000，另開終端機 curl localhost:18020/version

事件（event）是叢集對物件發生的事的紀錄：Scheduled（排到哪個節點）、Pulling／Pulled、Created、Started、BackOff。Pod 卡住時，先看 describe 最下面這一段，比盯著 STATUS 有用得多。事件預設只保留約一小時。

port-forward 把本機的 port 透過 API server 接到 Pod，只在你的電腦上有效、終端機關掉就斷，連線全部經過 API server。它是除錯工具，不是對外服務的方式。

💡 實務上：Pod 出問題時，先存證據再動手
客服回報「下單一直失敗」，你查到某個 Pod 一直重啟。直覺是刪掉讓它重建，但刪掉之後就不能再 describe 它、也看不到它上一次崩潰的 log，事件本來也只保留約一小時。資深工程師會先把現場存下來：kubectl describe pod、kubectl logs --previous、kubectl get events -n <namespace> --sort-by=.lastTimestamp 的輸出存成檔案、貼到事故頻道，再決定要不要重啟或回滾。事後檢討要回答「為什麼壞」，靠的就是這些紀錄。

command 與 args

cafe-api 的 Dockerfile 最後一行是 CMD ["node", "server.ts"]。容器的 command 換掉映像的 ENTRYPOINT，args 換掉映像的 CMD，兩個都不寫就照映像的設定執行：

Pod 寫了實際執行
都沒寫映像的 ENTRYPOINT＋CMD（cafe-api 是 node server.ts）
只寫 args: ["dist/main.js"]映像的 ENTRYPOINT＋dist/main.js（node 映像的 ENTRYPOINT 會把它交給 node 執行，找不到檔案就 exit 1）
寫了 command只執行你寫的 command＋args，映像的兩個都不用

把 NestJS 專案的習慣 args: ["dist/main.js"] 抄過來，就會得到一個 CrashLoopBackOff。這種時候 kubectl logs --previous 會直接印出 Cannot find module。

Pod 大部分的欄位建立後不能改：env、port、容器的增減都不行，apply 會被拒絕（例如 pod updates may not add or remove containers）。少數例外是容器的 image。直接管 Pod 時，改設定要 kubectl delete pod 再 apply；下一課的 Deployment 會自動做「換一個新 Pod」這件事。

label 與 namespace

label（標籤）是貼在物件上的 key: value；selector（選擇器）是用標籤挑出一群物件的條件。Kubernetes 裡物件之間幾乎都靠 label 連起來：下一課的 Deployment 用 selector 認出「哪些 Pod 是我的」，第 4 課的 Service 用 selector 決定流量送給哪些 Pod。名字會變（Deployment 建的 Pod 名稱後面有亂碼），label 不會。

kubectl get pods -n k8s-02-try -l app.kubernetes.io/name=cafe-api          # 等於
kubectl get pods -n k8s-02-try -l 'app.kubernetes.io/part-of=cafe,tier!=db' # 多個條件用逗號，都要符合
kubectl get pods -n k8s-02-try -L app.kubernetes.io/version                 # 多一欄顯示這個 label 的值
kubectl label pod cafe-api -n k8s-02-try tier=api                          # 手動加（實務上改 YAML）

規則：key 可以有前綴（app.kubernetes.io/），名稱部分與值都最多 63 個字元、要以英數字開頭結尾。官方建議的一組 key（Recommended Labels），工具（Helm、監控）也會認：

key咖啡店的例子
app.kubernetes.io/namecafe-api
app.kubernetes.io/part-ofcafe（cafe-api、cafe-worker 都屬於這個系統）
app.kubernetes.io/version"1.4.0"（看起來像數字要加引號）
app.kubernetes.io/componentapi、worker

namespace 常見的分法是按環境（cafe-staging、cafe-prod）或按團隊。正式環境的 staging 與 production 通常是不同叢集，namespace 用來分團隊與服務。這門課的練習每一題一個 namespace，叫 k8s-02-ex1 這樣的名字，測試會先刪掉重建，所以你手動在裡面做的事不會影響判分。

一個 Pod 多個容器：init container 與 sidecar

同一個 Pod 裡的容器共用網路：同一個 IP、同一組 port，彼此用 localhost 連得到，就像同一台機器上的兩個程序，所以也不能兩個都聽 3000。檔案系統則各自獨立，要共用檔案得掛同一個 volume。最簡單的是 emptyDir：Pod 建立時產生的空資料夾，Pod 刪掉就跟著消失。

init container 放在 spec.initContainers，在主容器之前依序執行，每一個都要成功結束（exit 0）才換下一個；全部跑完主容器才啟動。這段期間 kubectl get pods 顯示 Init:0/2。常見用途是等相依的服務：

initContainers:
  - name: wait-db
    image: busybox:1.38.0
    imagePullPolicy: IfNotPresent
    command: ["sh", "-c", "until nc -z -w 2 fake-db 5432; do echo waiting; sleep 2; done"]

nc -z 只試著連線、不送資料，連得上就回傳 0。重點是真的去檢查，不是 sleep 30 猜一個時間：資料庫 10 秒就好了，你白等 20 秒；資料庫 60 秒才好，你的程式照樣連不上。

sidecar container 是跟主容器一起長期執行的輔助容器，例如把 log 檔轉送出去、代理流量。從 1.33 起它是正式功能（SidecarContainers Stable）：寫在 initContainers 裡、加上 restartPolicy: Always。這樣寫，kubelet 會（官方文件）：

  • 依 initContainers 的順序啟動它，它開始執行後就接著啟動下一個，不會等它結束；所以它比主容器早啟動。
  • 它結束了就重開，不管 Pod 的 restartPolicy 是什麼。
  • Pod 要關閉時，等主容器都停了才停 sidecar，而且依宣告的相反順序停。
  - name: heartbeat
    image: busybox:1.38.0
    imagePullPolicy: IfNotPresent
    restartPolicy: Always                # 這一行讓它變成 sidecar
    command: ["sh", "-c", "while true; do cat /shared/heartbeat 2>/dev/null; sleep 5; done"]
    volumeMounts:
      - name: shared
        mountPath: /shared

舊的寫法是把 sidecar 當成 containers 裡的第二個容器。問題是兩個容器同時啟動、沒有順序；Pod 關閉時也同時收到 SIGTERM，主容器還在處理最後的請求，log 轉送的 sidecar 可能已經先走了。到了 Job（第 10 課），主容器做完了，sidecar 卻還在跑，Job 永遠不會結束。

什麼時候該拆成兩個 Pod？只要兩個程式不需要 localhost 或同一個檔案就能合作，就拆開。同一個 Pod 的容器一起排程、一起擴展：把 cafe-api 和 Redis 放在同一個 Pod，加一個 API 副本就多一個 Redis，資料也各自分開。

為什麼幾乎不直接建 Pod

單獨的 Pod 只有「容器結束就在原地重開」這一層保護。Pod 本身被刪掉、或它所在的節點壞掉，沒有人會再建一個新的，因為沒有任何控制器記得「這裡應該有一個 cafe-api」。試試看：

kubectl delete pod cafe-api -n k8s-02-try
kubectl get pods -n k8s-02-try          # No resources found，不會回來

所以正式環境幾乎不寫 Pod，而是寫 Deployment（下一課），讓控制器負責「隨時要有 N 個這樣的 Pod」。但 Deployment 裡的 Pod 範本就是這一課寫的這些欄位，除錯時看到的也是一個一個的 Pod，所以這一課的東西每天都會用到。練完記得清掉試驗區：kubectl delete namespace k8s-02-try。

練習

先確認叢集在跑（node kubernetes/practice/bin/cluster.mjs status）。測試會把你的檔案 apply 到每一題自己的 namespace（例如 k8s-02-ex1），只看檔案、不看你手動在叢集做過什麼。叢集忙的時候一題要跑一到兩分鐘。想自己先試，用 kubectl apply -n k8s-02-try -f kubernetes/practice/work/02/ex1/。

練習 1：完成 ex1/pod.yaml，把 cafe-api 寫成一個 Pod：名稱 cafe-api、映像 learn-k8s/cafe-api:v1（cluster.mjs up 已經載入節點，docker exec learn-k8s-worker crictl images | grep cafe 可以確認）、拉取規則用節點上的映像、宣告容器 port 3000、label app.kubernetes.io/name: cafe-api、環境變數 REQUIRE_DB=0（這幾課沒有資料庫）和 APP_ENV=dev。測試先檢查檔案（kubeconform、映像要有明確的 tag 而且不是 latest、拉取規則不能是 Always、env 的值要是字串），再套用到叢集，等 Pod Ready 後從叢集裡的 probe Pod 連 <Pod IP>:3000/health/live 與 /config。

練習 2：ex2/pod.yaml 有三個錯。先自己用 kubeconform -strict -kubernetes-version 1.37.0 kubernetes/practice/work/02/ex2/pod.yaml 和 kubectl apply -n k8s-02-try --dry-run=server -f … 找出兩個，第三個要 apply 之後看 kubectl get pods、kubectl logs --previous 才會發現。修好之後：兩道檢查都通過、port 3000 的宣告還在、restartPolicy 維持預設；套用後 Running、重啟 0 次，log 第一行是 cafe-api 的 {"msg":"listening",…}。不要用 restartPolicy: Never 把錯誤藏起來。

練習 3：補完 ex3/pod.yaml（主容器 api 已經寫好，HEARTBEAT_FILE=/shared/heartbeat 讓它每 2 秒把現在時間寫進這個檔案）：

  • 一個 emptyDir volume，主容器和 sidecar 都掛在 /shared。
  • 一個一般的 init container（busybox:1.38.0），一直重試到 fake-db:5432 連得上才結束。fake-db 是測試在你的 Pod 卡在 Init 至少 40 秒之後才建立的 Service（第 4 課才教 Service，這裡只要知道這個名字到時候連得上）。
  • 一個原生 sidecar（busybox:1.38.0），每 5 秒把 /shared/heartbeat 的內容印到 stdout。

測試會確認：fake-db 出現之前 init container 一直在跑、主容器沒有啟動；fake-db 出現後 Pod 變成 Running；kubectl logs cafe-api -c <sidecar 名稱> 看得到時間。sidecar 必須在 initContainers 裡設 restartPolicy: Always，不能寫成 containers 裡的第二個容器。

練習 4：完成 ex4/report.sh，用 kubectl 讀 namespace k8s-02-ex4，依序印出：app.kubernetes.io/part-of=cafe 的 Pod 名稱（每行一個、排序）；一行 ---；其中容器正在等待（Waiting）的 Pod，每行「名稱 原因」（例如 cafe-worker-3fa21c ErrImageNeverPull，排序）。測試每次隨機建立一組 Pod：有在跑的、卡在等待的，也有名字是 cafe- 開頭但屬於別的系統的、名字不是 cafe- 開頭但屬於 cafe 的。腳本只能讀叢集。提示：第 1 課的 -o jsonpath 加 {range}，原因在 .status.containerStatuses[0].state.waiting.reason；等待中的 Pod，phase 是 Pending。

練習 5：Pod 的映像寫 learn-k8s/cafe-api:latest，你已經用 kind load 載入過，Pod 卻一直 ImagePullBackOff。原因是？

✓ 沒寫 imagePullPolicy 時，tag 是 latest 或沒寫 tag 會填 Always，其他 tag 填 IfNotPresent。改用明確的 tag（並寫上 IfNotPresent），kubelet 才會用節點上已經有的映像。a 錯：映像在節點上，跟 namespace 無關；c 錯：kind 照樣能載入 latest，問題在拉取規則；d 錯：kind load 指令結束時已經載入完成。

練習 6：同一個 Pod 裡的兩個容器要怎麼互相連線？

✓ 同一個 Pod 的容器共用 IP 與 port 空間，就像同一台機器上的兩個程序，所以兩個容器也不能聽同一個 port。a、c 也連得到，但繞了遠路，而且 Service 會把流量分給別的 Pod；d 錯：網路是共用的，隔離的是檔案系統（要共用檔案得掛同一個 volume）。

練習 7：Git 裡的 manifest 寫映像 learn-k8s/cafe-api:v1。你為了救火，用 kubectl edit 把執行中 Pod 的映像改成 v2（image 是 Pod 少數可以在執行中修改的欄位）。下次 CI 執行 kubectl apply -f 之後會怎樣？

✓ apply 把物件改成檔案宣告的樣子，檔案才是真相，手動修改在下一次 apply 就消失了。救火改了叢集，就要同一時間改 Git 裡的 manifest。a 錯：apply 會更新有變動的欄位；c 錯：不同正是 apply 要處理的情況；d 錯：一個容器只有一個 image 欄位，換映像是重開那個容器。

常見錯誤

  • 用 :latest 或不寫 tag：拉取規則變成 Always，在 kind 上直接 ImagePullBackOff；正式環境則看不出跑的是哪一版。一律寫明確的 tag。
  • 只看 kubectl get 的 STATUS：原因在 describe 最下面的 Events、容器的 Waiting／Terminated reason 與 logs --previous。
  • YAML 的數字與布林值沒加引號：env 的 value 必須是字串，"0"、"true"、"3000" 都要加引號，否則 apply 被拒絕。
  • 縮排錯一層：欄位跑到別的物件上，變成「unknown field」。寫完先跑 kubeconform 與 --dry-run=server。
  • 把 sidecar 寫成 containers 裡的第二個容器：沒有啟動與關閉的順序保證，用在 Job 上還會讓 Job 永遠不結束。1.33 起用 initContainers＋restartPolicy: Always。
  • init container 用 sleep 猜等待時間：要真的檢查相依服務能不能連，連得上才結束。
  • 用 restartPolicy: Never 讓 CrashLoopBackOff 消失：錯誤還在，只是容器結束後不重開，Pod 變成 Failed。要修的是容器為什麼結束。
  • 用 port-forward 提供正式服務：它經過 API server、只在你的電腦上有效，只用來除錯。對外服務用 Service 與 Gateway（第 4、5 課）。

小結

  • manifest 的頂層是 apiVersion、kind、metadata、spec；status 由叢集填。不知道欄位就 kubectl explain。
  • Pod 是最小的部署單位：一個或多個容器，共用 IP 與 volume、一起排到同一個節點。
  • kind 的節點看不到 Mac 的 Docker 映像，要 kind load；沒寫 imagePullPolicy 時 latest 或沒寫 tag 會變成 Always。一律寫明確的 tag 與 IfNotPresent。
  • kubectl apply 是宣告式的，可以重複執行，檔案是真相。寫完先用 kubeconform 與 --dry-run=server 檢查。
  • phase 只是大方向，原因看容器的 Waiting／Terminated reason、describe 的 Events 與 logs --previous。
  • label 是物件之間的膠水，用 -l 挑物件；名稱開頭不可靠。
  • init container 依序跑完主容器才啟動；原生 sidecar 寫在 initContainers 並設 restartPolicy: Always，比主容器早啟動、晚關閉。
  • 單獨的 Pod 被刪掉或節點壞掉就不會回來。
