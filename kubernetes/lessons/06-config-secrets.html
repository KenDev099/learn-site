階段 2：網路與設定 · 第 6 課

ConfigMap 與 Secret：設定與機密

到目前為止，cafe-api 的設定都直接寫在 Deployment 的 env 裡：REQUIRE_DB: "0"、日誌等級、功能開關。等到要放資料庫密碼時，這個做法就出問題了：密碼會跟著 YAML 進 git，staging 和正式環境要各改一份 Deployment，改個日誌等級也要動到部署檔。

這一課把設定從 Pod 範本裡拿出來：非機密的設定放 ConfigMap，機密放 Secret，再用環境變數或檔案交給容器。

這課的路線：
  1. 設定放哪裡、ConfigMap：同一個映像跑在 staging 和正式環境，不一樣的設定放進 ConfigMap，注入成環境變數。
  2. Secret：資料庫密碼這類機密放哪裡，為什麼建議掛成檔案。
  3. 設定改了之後 Pod 什麼時候看得到：改了 ConfigMap 服務卻沒變的原因，怎麼讓設定跟著滾動更新、跟著回滾。
  4. Secret 不等於加密：base64 誰都解得開，真正的保護來自權限、etcd 加密和外部的機密管理系統。
  5. 缺少設定、什麼不該進叢集：Pod 卡在 CreateContainerConfigError 時看哪裡；大檔案、使用者資料該放哪。
這課會用到：
  • devops 課第 11 課的設定與機密：映像只建一次，環境差異由執行時的設定決定；機密不進映像、不進 git，用 _FILE 結尾的環境變數告訴程式去哪個檔案讀密碼。
  • 第 3 課的 Deployment：Pod 範本（spec.template）一改就觸發滾動更新，kubectl rollout undo 把 Pod 範本換回上一版。

設定放哪裡：同一個映像、不同環境

devops 課第 11 課的原則是：映像只建一次，staging 和正式環境跑的是同一個映像，差別只在執行時給的設定。在 Compose 裡，設定來自 .env 檔與 environment:；在 Kubernetes 裡，設定是叢集裡的兩種物件：

  • ConfigMap：存放非機密設定的鍵值物件，例如 LOG_LEVEL: info。誰都可以看，內容就是明文。
  • Secret：存放機密的物件，例如資料庫密碼、金流 API key、TLS 私鑰。值以 base64 表示，Kubernetes 會把它跟 ConfigMap 分開對待（權限可以分開設、可以設定在 etcd 裡加密），但後面會看到，預設並沒有加密。

兩者都屬於 namespace：Pod 只能引用同一個 namespace 裡的 ConfigMap 和 Secret。咖啡店的設定這樣分：

設定放哪裡理由
LOG_LEVEL、APP_ENVConfigMap外洩也沒有損失，值班時要能直接看
FEATURE_LOYALTY（集點功能開關）ConfigMap同上；改它要能追蹤、能回滾
資料庫密碼、Redis 密碼Secret拿到就能讀寫所有訂單
金流 API keySecret拿到就能用你的帳號收款、退款
TLS 憑證與私鑰Secret（kubernetes.io/tls 類型），或在 EKS 改用 ACM 憑證放在負載平衡器上第 5 課的 Gateway 用過
菜單圖片、幾 MB 的商品資料都不放：映像或物件儲存（S3）ConfigMap 上限 1 MiB，而且每個節點都要快取一份

判斷的問題只有一個：這個值被貼到公開的 Slack 頻道，會不會出事？會的話就是機密。

ConfigMap：寫出來，注入成環境變數

ConfigMap 的 YAML 很短，重點在 data：每個 key 對應一個字串。YAML 會把 true、3 解析成布林與數字，所以要加引號，不然 API server 會拒絕。

apiVersion: v1
kind: ConfigMap
metadata:
  name: cafe-config
data:
  LOG_LEVEL: info
  FEATURE_LOYALTY: "true"     # 不加引號是布林值，會被拒絕
  APP_ENV: staging

容器要拿到這些值，有兩種寫法變成環境變數：

containers:
  - name: api
    image: learn-k8s/cafe-api:v1
    envFrom:                       # 整個 ConfigMap：每個 key 變成一個同名的環境變數
      - configMapRef:
          name: cafe-config
    env:
      - name: REQUIRE_DB
        value: "0"
      - name: CAFE_REGION          # 只拿一個 key，而且可以換名字
        valueFrom:
          configMapKeyRef:
            name: cafe-shared
            key: region
  • envFrom：把整個 ConfigMap（或 Secret）一次變成環境變數。key 和環境變數同名時最方便。
  • env[].valueFrom：只取其中一個 key，名稱可以不同。適合從共用的 ConfigMap 挑一兩個值。
  • 同一個名稱同時出現在 env 和 envFrom 時，env 的值優先。所以把設定搬到 ConfigMap 時，要記得刪掉 env 裡的舊值，不然 ConfigMap 怎麼改都沒用。

動手試一次。在 learn 資料夾、設好 KUBECONFIG 的終端機裡，用一個自己的 namespace：

kubectl create namespace k8s-06-play
kubectl -n k8s-06-play create configmap cafe-config --from-literal=LOG_LEVEL=info --from-literal=APP_ENV=staging
kubectl -n k8s-06-play get configmap cafe-config -o yaml        # 看 data 長什麼樣子
kubectl -n k8s-06-play run cfg --image=busybox:1.38.0 --image-pull-policy=IfNotPresent --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"cfg","image":"busybox:1.38.0","command":["sh","-c","env | grep -E \"LOG_LEVEL|APP_ENV\"; sleep 3600"],"envFrom":[{"configMapRef":{"name":"cafe-config"}}]}]}}'
kubectl -n k8s-06-play logs cfg                                   # LOG_LEVEL=info、APP_ENV=staging

kubectl create configmap --from-literal 適合試驗；正式的設定寫成 YAML 檔、放進 git、用 kubectl apply 套用，才能審查與回滾。

Secret：放機密，掛成檔案

Secret 的結構跟 ConfigMap 幾乎一樣，差別是 data 的值要 base64 編碼（寫 stringData 可以直接寫明文，API server 會幫你編碼）。不過這門課的練習不寫 Secret 的 YAML，原因在後面「Secret 不等於加密」：只要 YAML 裡有密碼，進了 git 就等於外洩。Secret 由測試（正式環境是外部的 secret 管理系統）建立：

kubectl -n k8s-06-play create secret generic cafe-db --from-literal=password='s3cr3t-latte'

Secret 一樣可以用 envFrom: - secretRef: 或 valueFrom.secretKeyRef 變成環境變數，但機密比較好的做法是掛成檔案：

    env:
      - name: DB_PASSWORD_FILE            # 告訴應用：密碼在這個檔案裡
        value: /run/secrets/db/password
    volumeMounts:
      - name: db-secret
        mountPath: /run/secrets/db        # 這個資料夾裡，每個 key 是一個檔案
        readOnly: true
  volumes:                                # 跟 containers 同一層
    - name: db-secret
      secret:
        secretName: cafe-db

volume 掛載的意思是：kubelet 把 Secret（或 ConfigMap）的每個 key 寫成一個檔案，放進 mountPath 這個資料夾。Secret cafe-db 有一個 key password，容器裡就會出現 /run/secrets/db/password，內容是解碼後的密碼。Secret 的檔案放在記憶體裡（tmpfs），不會寫到節點的磁碟。

為什麼機密用檔案比環境變數好（devops 課第 11 課的 _FILE 慣例）：

  • 環境變數會被整包帶走：子程序會繼承所有環境變數；錯誤回報工具、除錯頁面、console.log(process.env) 常常整包印出來；同一台機器上權限夠的程序可以讀 /proc/<pid>/environ。檔案要有人主動去讀才拿得到。
  • 檔案可以更新：掛成 volume 的 Secret 改了之後，檔案會在一段時間內換成新值（下一節），應用重讀檔案就能換密碼，不用重啟。環境變數在程序啟動後就固定了。

這不是加密，只是降低意外外洩的機會。有些函式庫只認環境變數（例如 PostgreSQL 的 client 函式庫 libpq 會讀 PGPASSWORD），那時用 secretKeyRef 是合理的取捨，練習 4 就是這種情況。

cafe-api 支援 DB_PASSWORD_FILE：設了它，/config 會多一個 dbPasswordLoaded，說明檔案讀不讀得到，但不會回傳密碼本身。/config 只回固定幾個非機密的 key，這也是一個好習慣：不要寫「印出所有設定」的端點或 log。

設定改了之後，Pod 什麼時候看得到

這是最常見的誤會：改了 ConfigMap，以為服務馬上換成新設定。實際上要看設定是怎麼進到容器的：

  • 環境變數：程序啟動時由作業系統交給它，之後就是程序記憶體裡的值。Kubernetes 官方文件明寫：以環境變數使用的 ConfigMap 不會自動更新，要重新啟動 Pod。
  • volume 掛載：kubelet 每次定期同步時檢查 ConfigMap 有沒有變，有的話換掉檔案。延遲最多是 kubelet 的同步週期（預設 1 分鐘）加上它的快取延遲。檔案換了，但應用如果只在啟動時讀一次，還是看不到；要應用自己監看檔案或收到訊號（例如 SIGHUP）時重讀。
  • subPath：只把一個 key 掛成某個路徑的單一檔案（例如 mountPath: /app/config.json、subPath: config.json），常用在「資料夾裡已經有別的檔案，不想整個蓋掉」。代價是這種掛法永遠不會更新，官方文件也這樣寫。

你可以在剛才的 namespace 驗證第一種：

kubectl -n k8s-06-play create configmap cafe-config --from-literal=LOG_LEVEL=debug --from-literal=APP_ENV=staging \
  --dry-run=client -o yaml | kubectl apply -f -          # 把 ConfigMap 改成 debug
kubectl -n k8s-06-play exec cfg -- env | grep LOG_LEVEL   # 還是 info：程序啟動時就固定了

第一個指令會印出缺少 last-applied-configuration 的 Warning：這個 ConfigMap 是用 create 建的，第一次改用 apply 管理時會自動補上，之後就不會再出現。

大部分服務（包括 cafe-api 和 NestJS 的 ConfigModule）只在啟動時讀設定。所以實務上的結論是：改了設定，就讓 Pod 換新，而且要用滾動更新換，不能一次全刪。有三種做法：

做法怎麼做適合
kubectl rollout restartkubectl apply -f configmap.yaml 之後執行 kubectl rollout restart deployment/cafe-api。它在 Pod 範本加上 kubectl.kubernetes.io/restartedAt 時間戳 annotation，範本變了，Deployment 就照第 3 課的方式一個一個換手動或腳本部署；最簡單
checksum annotation把設定檔的雜湊值寫進 Pod 範本，例如 checksum/config: 3f2a…。設定一變，雜湊就變，kubectl apply 就會觸發滾動更新；設定沒變時重複 apply 不會多重啟一次宣告式：所有變更都經過 git 與 apply。第 13 課的 Helm 可以自動算這個值
不可變設定＋改名每次改設定就建一個新名稱的 ConfigMap（cafe-config-v2），Deployment 改引用新名稱需要「設定跟著版本一起回滾」的服務；下面詳細講
不要用 kubectl delete pods 套用新設定：所有舊 Pod 同時被刪，新 Pod 還沒 Ready 之前，Service 後面可能一個能接流量的 Pod 都沒有。滾動更新會先等新 Pod Ready 再關舊的。練習 2 的 Deployment 已經附上 readinessProbe 與 preStop，讓換 Pod 的過程不掉請求，原理是第 7 課的主題。
💡 實務上：「改了設定沒生效」先問三個問題
值班時常見的求救是「我把 LOG_LEVEL 改成 debug 了，log 還是沒變」。資深工程師會先問：這個值是環境變數還是掛成檔案？改完之後 Pod 換過了嗎（看 kubectl get pods 的 AGE）？env 裡有沒有同名的舊值蓋掉 ConfigMap？這三個問題通常就找到原因。為了查問題臨時開 debug，查完要記得改回來，而且改動要回到 git，不然下一次部署又被改回去，或 debug log 一直開著，日誌量和費用跟著變大。

不可變設定與改名

前兩種做法有一個共同的問題：設定和 Deployment 是分開的物件。假設你在 v2 版同時改了映像和 ConfigMap，上線後出問題，kubectl rollout undo 只會把 Pod 範本（映像）換回去，ConfigMap 還是新的，於是你得到「舊程式＋新設定」這個從沒測試過的組合。

解法是讓設定的名稱進到 Pod 範本裡：

apiVersion: v1
kind: ConfigMap
metadata:
  name: cafe-config-v2        # 每次改設定，換一個新名稱
immutable: true               # 跟 data 同一層
data:
  FEATURE_LOYALTY: "true"
---
# Deployment 的 Pod 範本
        envFrom:
          - configMapRef:
              name: cafe-config-v2
  • immutable（不可變）：設成 true 之後，data 不能再改，這個設定本身也改不回 false，只能刪掉重建。好處是不會有人「順手改一下」正在使用的設定；而且 kubelet 不用再監看它有沒有變，叢集裡 ConfigMap 很多時能減輕 API server 的負擔。
  • Deployment 改引用 cafe-config-v2，Pod 範本變了，就觸發滾動更新。
  • kubectl rollout undo 時，Pod 範本回到引用 cafe-config-v1 的那一版，設定跟著一起回滾。前提是 v1 的 ConfigMap 還在，所以舊版本要保留一段時間（例如最近 3 版）再清掉。

手動取名容易忘記，第 13 課會提到 Kustomize 的 configMapGenerator 會自動在名稱後面加上內容的雜湊值，做的就是這件事。

Secret 不等於加密

base64 是編碼，不是加密：任何人都能還原，不需要金鑰。能讀這個 Secret 的人，就拿得到密碼：

kubectl -n k8s-06-play get secret cafe-db -o jsonpath='{.data.password}' | base64 --decode
# s3cr3t-latte

所以 Secret 的保護不是來自 base64，而是來自這幾層：

  • 誰能讀 Secret：由 RBAC（第 12 課）決定。要特別注意的是，官方文件寫明：能在某個 namespace 建立 Pod 的人（包括能建 Deployment 的人），就能把那個 namespace 的任何 Secret 掛進自己的 Pod 讀出來。所以「能部署」幾乎等於「能讀機密」，權限要一起設計。
  • etcd 加密（encryption at rest）：Kubernetes 預設把 Secret 不加密存在 etcd 裡，拿到 etcd 的備份就拿到所有密碼。叢集管理者可以設定 API server 在寫入 etcd 前加密。EKS 在 Kubernetes 1.28 以上的叢集預設就用 AWS KMS 做信封加密（envelope encryption），涵蓋所有 API 資料，金鑰可以用 AWS 的或自己的 KMS 金鑰（auth 課第 23 課講過信封加密）。kind 沒有設定這一層。
  • 機密的正本不放在叢集：正式環境的密碼存在 AWS Secrets Manager 這類外部系統，有稽核紀錄、能自動輪替。再由 External Secrets Operator 把它同步成 Kubernetes 的 Secret。它是一個控制器（第 1 課的控制迴圈）：你寫一個 ExternalSecret 物件說「從 Secrets Manager 的哪個 key 拿值、做成哪個 Secret」，它定期去拿、更新 Secret：
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: cafe-db
spec:
  refreshInterval: 1h               # 多久重新拿一次（輪替後最慢這麼久同步）
  secretStoreRef:
    name: aws-secretsmanager        # 平台團隊設定好的連線方式
    kind: ClusterSecretStore
  target:
    name: cafe-db                   # 產生的 Kubernetes Secret
  data:
    - secretKey: password
      remoteRef:
        key: prod/cafe/db
        property: password

這份 YAML 裡沒有任何密碼，可以放心進 git。另一種做法是 Secrets Store CSI Driver：把外部的機密直接掛成檔案，不經過 Kubernetes 的 Secret。不管哪一種，原則跟 devops 課第 11 課一樣：機密不進 git，CI 用 gitleaks 擋。

💡 實務上：機密外洩時，先輪替再清理
有人把含密碼的 Secret YAML 推上 git，或密碼被印進 log，就當作密碼已經外洩：先在 Secrets Manager 輪替密碼，再清理 git 歷史，順序不能反。輪替後還要確認服務真的拿到新值：ExternalSecret 最慢要等 refreshInterval 才同步，用環境變數注入的服務還要 rollout restart。這類事件要通知資安，由他們查外洩期間有沒有人用過舊密碼。事後檢討時也記得「能部署就能讀機密」：看一下誰有權限在這個 namespace 建立 Pod。

缺少設定：CreateContainerConfigError 與 optional

Pod 引用的 ConfigMap 或 Secret 不存在，或引用的 key 不存在時，kubelet 沒辦法組出容器的環境變數，容器根本不會被建立。kubectl get pods 的 STATUS 會顯示：

NAME                        READY   STATUS                       RESTARTS   AGE
cafe-api-844b8bffff-6gs89   0/1     CreateContainerConfigError   0          27s

CreateContainerConfigError 的意思是「容器的設定組不出來」，跟 CrashLoopBackOff（容器啟動了、然後一直結束）不一樣：這時容器沒有跑過，kubectl logs 什麼都看不到。原因寫在 kubectl describe pod 最下面的 Events：

kubectl -n k8s-06-ex4 describe pod -l app.kubernetes.io/name=cafe-api
...
Events:
  Warning  Failed  27s (x3 over 41s)  kubelet  spec.containers{api}: Error: couldn't find key db-password in Secret k8s-06-ex4/cafe-db

接著查 Secret 裡實際有哪些 key（只看 key 的名稱，不要把值印到螢幕上）：

kubectl -n k8s-06-ex4 describe secret cafe-db
...
Data
====
password:  12 bytes

describe secret 只列出 key 與長度，不顯示值，適合貼到事故頻道。這裡看得出 key 叫 password，Deployment 卻要 db-password。

環境變數引用的 key 不存在會是 CreateContainerConfigError；掛成 volume 的 Secret 不存在則會讓 Pod 停在 ContainerCreating，Events 是 FailedMount。兩種都會在 describe 寫清楚。

每種引用都可以加 optional: true：找不到時當作沒有，容器照樣啟動。這是一個要想清楚的取捨：

  • 問題被延後：Pod 起來了、Ready 也可能是綠的，第一個要連資料庫的請求才失敗，而且錯誤訊息變成「密碼錯誤」或「undefined」，比「找不到 key db-password」難查得多。
  • 跟 NestJS 課第 11 課的原則一致：缺必要設定就應該啟動失敗，讓滾動更新卡在第一個新 Pod，舊版繼續服務。
  • optional: true 只適合真的可有可無的東西，例如「有這個 ConfigMap 就套用額外的功能開關，沒有就用預設值」，而且應用要自己驗證設定。
💡 實務上：新版本要新設定時，先建設定、再部署程式
新版 cafe-api 多讀一個 Secret key（例如新的金流 API key），程式已經合併，但正式環境還沒建這個 key，部署就會卡在 CreateContainerConfigError。沒有用 optional: true 的話，這反而是好結果：滾動更新停在第一個新 Pod，舊版繼續服務。上線清單要把順序寫清楚：先在每個環境建好 ConfigMap／Secret（或 ExternalSecret 指到的值），再部署讀它的程式。PR 說明裡列出「這次新增的設定」，review 的人和負責部署的人才看得到。

多大算太大，什麼不該進叢集

前面都在講怎麼把設定放進叢集；最後看哪些東西不該放進 ConfigMap 和 Secret：

  • ConfigMap 上限 1 MiB（Secret 也是）。它的設計是放設定，不是放資料：每個用到它的節點都會快取一份，大的 ConfigMap 會拖慢 API server 與 kubelet。幾 MB 的靜態資料打包進映像，或放 S3 讓應用啟動時下載。
  • 不常改、跟程式碼綁在一起的值（例如 SQL 查詢、商品分類的預設清單）放在程式碼裡，跟著映像版本走。ConfigMap 放的是「同一份程式在不同環境要不一樣」的值。
  • 正式環境的機密正本不在叢集：在 Secrets Manager，叢集裡的 Secret 只是同步過來的副本。
  • 使用者資料（訂單、顧客資料）屬於資料庫，不屬於設定。

試完之後清掉練習用的 namespace：kubectl delete namespace k8s-06-play。

練習

在 learn 資料夾執行頁面上的指令，起始檔會複製到 kubernetes/practice/work/06/。每一題的測試會建立自己的 namespace（k8s-06-ex1 到 k8s-06-ex4），需要的 Secret 由測試用隨機值建立，套用你的檔案、檢查結果，最後刪掉 namespace。叢集很忙時一題要幾分鐘。

練習 1：ex1/deployment.yaml 把所有設定和資料庫密碼都寫死在 env 裡。把它整理好：

  • 在 configmap.yaml 寫 ConfigMap cafe-config，data 剛好是 LOG_LEVEL=info、FEATURE_LOYALTY=true、APP_ENV=staging，Deployment 用 envFrom 整包注入，並刪掉 env 裡的同名舊值。
  • 刪掉 DB_PASSWORD。密碼在 Secret cafe-db 的 key password（測試會建立，不要自己寫 Secret 的 YAML）：把它掛成檔案 /run/secrets/db/password，並設環境變數 DB_PASSWORD_FILE=/run/secrets/db/password。

測試會檢查 /config 的三個值與 dbPasswordLoaded、在容器裡讀那個檔案比對隨機密碼，並確認密碼沒有以任何形式變成環境變數。

練習 2：叢集上已經跑著 2 個 cafe-api（LOG_LEVEL=info），一直有流量。把 ex2/configmap.yaml 的 LOG_LEVEL 改成 debug，再寫 apply.sh：用 kubectl apply 套用 ConfigMap，讓所有 Pod 換成讀到新設定的新 Pod，並等到完成（最多 180 秒，沒完成要以非 0 結束）。deployment.yaml 和 service.yaml 不用改（要用 checksum annotation 的話，只能動 Pod 範本的 annotations）。測試會在背景每秒送 5 個請求，執行你的腳本，然後檢查：每個 Pod 都是新建立的、/config 都是 debug、流量 0 個錯誤、ConfigMap 是用 kubectl apply 改的、腳本沒有刪除任何東西。

練習 3：ex3/v1/ 與 ex3/v2/ 是同一個服務的兩個版本，v2 打開了集點功能（FEATURE_LOYALTY: "true"）。現在兩版共用一個叫 cafe-config 的 ConfigMap，回滾時設定不會跟著回去。改成：v1 的 ConfigMap 叫 cafe-config-v1、v2 的叫 cafe-config-v2，兩個都 immutable: true，每一版的 Deployment 引用自己那一版的 ConfigMap。測試會依序套用 v1/、v2/，執行 kubectl rollout undo，確認 /config 回到 v1 的值，最後嘗試修改 cafe-config-v2，必須被 API server 拒絕。

練習 4：ex4/deployment.yaml 套用後 Pod 一直沒有 Running。先自己重現：kubectl create namespace k8s-06-ex4、kubectl -n k8s-06-ex4 create secret generic cafe-db --from-literal=password=test、kubectl -n k8s-06-ex4 apply -f kubernetes/practice/work/06/ex4/deployment.yaml，用 get pods 和 describe 找出原因。在 diagnosis.md 寫下 Pod 的狀態、你用來看到原因的指令、缺的是哪個 key，然後修好 deployment.yaml。Secret cafe-db 是別的團隊管的，你改不到它；也不能用 optional: true 掩蓋。做完執行 kubectl delete namespace k8s-06-ex4 再跑測試（測試也會自己重建這個 namespace）。

練習 5：關於 Secret，哪一句正確？

✓ base64 是編碼，base64 --decode 就還原了。a 錯：Kubernetes 預設不加密 etcd 裡的 Secret，要叢集管理者設定（EKS 1.28 以上預設用 KMS 加密）。c 錯：不需要金鑰就能還原的東西不算保護。d 錯：有讀取權限就看得到 data，所以真正控制誰拿得到的是 RBAC，以及誰能在 namespace 裡建 Pod。

練習 6：cafe-api 用 envFrom 讀 ConfigMap。你 kubectl apply 把 LOG_LEVEL 改成 debug，等了五分鐘，Pod 的行為還是沒變。原因與做法是？

✓ 程序啟動後，環境變數就是它記憶體裡的值，ConfigMap 改了也不會變。a 只適用於掛成 volume（而且不是 subPath）的檔案，而且應用還要自己重讀。c 錯：apply 和 replace 改到的是同一個物件，差別只在怎麼合併。d 沒有必要，也會影響同一個節點上的其他服務。

練習 7：把資料庫密碼掛成檔案、而不是放進環境變數，主要的好處是？

✓ 這是降低「意外外洩」的做法。a 不是重點。c 錯：檔案裡就是解碼後的明文，能進容器的人一樣讀得到。d 錯：secretKeyRef、envFrom.secretRef 都可以用，只是風險比較高；只認環境變數的函式庫（例如 libpq 的 PGPASSWORD）就只能這樣用。

常見錯誤

  • 以為 Secret 是加密的：base64 一解就是明文。控制 RBAC（包括誰能建 Pod）、確認 etcd 有加密，正式環境的機密正本放在 Secrets Manager，用 External Secrets 同步進來。
  • 把 Secret 的 YAML 放進 git：等於公開密碼。git 裡只放 ExternalSecret 這類不含值的物件（或 Sealed Secrets 這種只有叢集解得開的加密檔）；已經推上去的就輪替密碼。
  • 改了 ConfigMap 就等 Pod 自己更新：環境變數永遠不會變，subPath 掛的檔案也不會。改設定要觸發滾動更新：rollout restart、checksum annotation，或換成新名稱的 ConfigMap。
  • 用 kubectl delete pods 套用新設定：所有 Pod 同時消失，新 Pod Ready 前的請求會失敗。用滾動更新一個一個換。
  • 搬到 ConfigMap 後忘了刪 env 裡的舊值：同名時 env 優先，ConfigMap 怎麼改都沒效果。
  • 用 optional: true 讓 Pod 先起來：問題延後到執行時才出現，而且更難查。缺必要設定就應該啟動失敗，讓滾動更新停在第一個新 Pod。
  • log 或除錯端點印出整包設定：只印非機密的 key。cafe-api 的 /config 只回固定幾個 key，密碼只回「有沒有讀到」。
  • ConfigMap 的值沒加引號：FEATURE_LOYALTY: true 在 YAML 裡是布林值，API server 會拒絕；值一律寫成字串。

小結

  • 同一個映像、不同環境的設定放在叢集裡：非機密的放 ConfigMap，機密放 Secret；判斷標準是「貼到公開頻道會不會出事」。
  • 注入方式：envFrom 整包、valueFrom 單一 key、volume 掛成檔案。機密優先用檔案搭配 _FILE 慣例。
  • 改了設定：環境變數要建新 Pod；volume 檔案約一分鐘內更新、應用要自己重讀；subPath 永遠不更新。用 rollout restart、checksum annotation 或「immutable＋改名」觸發滾動更新，後者讓設定跟著 rollout undo 一起回滾。
  • Secret 只是 base64。保護來自 RBAC（能建 Pod 就能讀 Secret）、etcd 加密（EKS 1.28 以上預設用 KMS），以及外部的 secret 管理（Secrets Manager＋External Secrets Operator）。機密不進 git。
  • 引用不存在的 ConfigMap、Secret 或 key 時，Pod 卡在 CreateContainerConfigError，原因在 kubectl describe pod 的 Events。不要用 optional: true 掩蓋必要的設定。
  • ConfigMap 與 Secret 上限 1 MiB；大的資料放映像或物件儲存。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：cafe-api 有一個 Pod 的程式卡死了，容器還在、但不回應，大約三分之一的請求逾時。Deployment 沒有寫任何 probe，為什麼 Service 還一直把請求送給它？

✓ Service 本身不是程序，不做健康檢查；控制器只把 selector 挑到而且 Ready 的 Pod 寫進 EndpointSlice，沒有 probe 時容器一啟動就算 Ready，卡死了也還在名單裡。修法是加 readiness probe（第 7 課）。a 錯在 Service 根本沒有健康檢查這件事，判斷「能不能收流量」的是 Pod 的 Ready。（第 4 課）

練習 9：訂單服務透過 Service cafe-api 呼叫，約四分之一的回應裡 version 是實驗版。同一個 namespace 有 3 個副本的 cafe-api 和 1 個副本的 cafe-api-canary。先查什麼？

✓ 四分之一正好是 4 個 Pod 裡的 1 個：selector 只寫了 app.kubernetes.io/name，canary 也有這個 label，就被挑進 EndpointSlice 一起收流量。修法是 selector 再加 app.kubernetes.io/instance，讓它只指到這組 Pod。b 錯在 DNS 只回 ClusterIP，從來不會指到某個 Pod；排查從 EndpointSlice 開始，不要先懷疑 DNS。（第 4 課）

練習 10：尖峰時把 cafe-api 從 3 個副本擴到 6 個，訂單服務用 keep-alive 長連線呼叫它。新的 3 個 Pod 已經 Ready，卻幾乎分不到請求，為什麼？

✓ ClusterIP 是 L4 負載平衡，分配以連線為單位，連線不換，請求就一直送到同一個 Pod。需要逐請求平均時，在前面放 L7 代理（第 5 課的 Gateway、service mesh），或讓客戶端設連線最長壽命、定期重連。a 錯在 DNS 回的是 ClusterIP，擴展前後都一樣，新 Pod 的 IP 不需要被查到。（第 4 課）

練習 11：平台團隊在 namespace infra 開了一個共用的 Gateway，orders 和 menu 兩個團隊要在自己的 namespace 寫 HTTPRoute 掛上來。listener 的 allowedRoutes 該怎麼設？

✓ Gateway 和 HTTPRoute 分開，就是為了讓平台團隊決定「誰能用入口」，應用團隊只管自己的路由。Selector 只放行有標籤的 namespace。a 錯在 hostnames 是每條 Route 自己寫的，任何 namespace 的人都能寫一條 hostnames: [cafe.test] 分走你的流量；c 的 Same 只收同 namespace 的 Route，parentRefs 寫了也掛不上。（第 5 課）

練習 12：新的 HTTPRoute 套用後，curl -i -H 'Host: cafe.test' $URL/orders/42 回 404，回應標頭有 server: envoy，沒有 cafe-api 會加的 x-instance。先查什麼？

✓ 沒有 x-instance 代表請求沒到後端，是 Gateway 自己回的 404：沒有任何規則比對得到。Exact /orders 不包含 /orders/42，一組 API 要用 PathPrefix。b 錯在應用回的 404 會帶 x-instance；c 是規則比對到了、後端沒有 Ready 的 Pod，那會是 503。（第 5 課）

練習 13：v2 同時改了映像和 ConfigMap cafe-config（同一個名稱，直接 apply 覆蓋）。上線後出錯，執行 kubectl rollout undo，Pod 換回舊映像，卻出現另一種從沒見過的錯誤。為什麼？

✓ ConfigMap 和 Deployment 是分開的物件，回滾只動 Pod 範本。修法是 immutable＋改名：每次改設定建 cafe-config-v2 這種新名稱，名稱寫在 Pod 範本裡，回滾時設定跟著回到 v1，前提是舊版本的 ConfigMap 要保留。a 錯在 undo 根本不碰 ConfigMap，而且環境變數只在容器啟動時讀一次，不會被同步更新。（第 6 課）

練習 14：實習生在 namespace shop 只有建立 Deployment 的權限，沒有讀 Secret 的權限。他拿得到 shop 裡 Secret cafe-db 的資料庫密碼嗎？

✓ 官方文件寫明：能在某個 namespace 建立 Pod（包括透過 Deployment）的人，就能把該 namespace 的任何 Secret 掛進自己的 Pod 讀出來，所以「能部署」幾乎等於「能讀機密」，兩種權限要一起設計。a 錯在只看了直接讀 Secret 這條路，掛進 Pod 不需要 get secret 的權限。c 錯在 etcd 加密只防備份外流，Pod 拿到的是解開後的明文。（第 6 課）

練習 15：新版 cafe-api 的滾動更新卡住了：新 Pod 是 CreateContainerConfigError，舊 Pod 還在服務。kubectl logs 新 Pod 什麼都沒有。下一步該做什麼？

✓ 這個狀態是設定組不出來，容器根本沒有建立，所以沒有 log；Events 會寫明哪個 ConfigMap、Secret 或 key 找不到。滾動更新停在第一個新 Pod、舊版繼續服務，正是缺設定時想要的結果。a 錯在那是 CrashLoopBackOff 的查法，容器沒跑過就沒有上一次；b 只是把錯誤延後到第一個連資料庫的請求，更難查。（第 6 課）
