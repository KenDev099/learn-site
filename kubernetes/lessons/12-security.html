階段 4：資料、安全與打包 · 第 12 課

權限與隔離：RBAC、ServiceAccount、NetworkPolicy 與 Pod Security（資深）

到目前為止，咖啡店的叢集裡人人都是管理員：你的 kubeconfig 可以做任何事，每個 Pod 都能連到任何 Pod，容器想用 root 跑也沒人攔。開發時很方便，上線後就是事故的放大器：CI 的憑證外洩，攻擊者可以讀走所有 Secret；cafe-api 有一個漏洞被利用，攻擊者從那個 Pod 直接連 PostgreSQL；某個映像用 root 執行，逃出容器的難度就低很多。

這一課把「誰能做什麼」一層一層收緊，學完你能說得出每個設定擋下的是哪一種攻擊。

這課的路線：
  1. 請求進到叢集要過三道關、RBAC：每個請求都要過驗證、授權、准入；替 CI 寫出剛好夠用的部署權限，為什麼不能「先給 cluster-admin 再說」。
  2. ServiceAccount：Pod 在叢集裡的身分，用不到 Kubernetes API 的應用為什麼不該拿到 token。
  3. NetworkPolicy：預設所有 Pod 互通，怎麼讓被入侵的 cafe-api 連不到不該連的服務。
  4. Pod Security：強制容器以非 root、最少權限執行，讓應用通過 restricted 等級。
  5. Pod 怎麼拿 AWS 權限、資深的安全清單：EKS 上不放 access key 也能寫 S3；上線前逐項檢查，每一項擋下哪種攻擊。
這課會用到：
  • auth 課第 18 課的 RBAC：權限先打包成角色、再把角色指派給人；最小權限是只給完成工作需要的那些。
  • 第 6 課的 Secret：值只是 base64 編碼，能讀到 Secret 物件就拿得到密碼。
  • devops 課第 19 課的 IAM：程式不放長期的 access key，而是扮演 IAM 角色拿短期憑證；角色的信任政策決定誰能扮演，OIDC 讓外部的身分（例如 GitHub Actions）換到角色。

請求進到叢集要過三道關

不管是你打 kubectl、CI 跑部署腳本，還是 Pod 裡的程式呼叫 API，最後都是一個 HTTPS 請求送到 API server。API server 依序做三件事：

  1. 認證（authentication）：你是誰。kind 的 kubeconfig 用客戶端憑證；EKS 用 IAM 身分；Pod 用 ServiceAccount 的 token。Kubernetes 沒有「使用者」這種物件，人的身分來自外部（憑證、IAM、公司的 SSO），叢集只拿到一個名字和所屬群組。
  2. 授權（authorization）：這個名字能不能對這個資源做這個動作。通常由 RBAC 決定，沒有任何規則允許就拒絕（403 Forbidden）。
  3. 准入控制（admission control）：動作被允許了，但物件的內容合不合規定。Pod Security Admission 就在這一關，檢查 Pod 有沒有要 root、要特權。

RBAC：Role、RoleBinding 與最小權限

RBAC（role-based access control，以角色為基礎的存取控制）：先把權限打包成角色，再把角色綁給身分。auth 課第 18 課在應用程式裡做過同一件事，Kubernetes 的版本有四種物件：

物件範圍內容
Role一個 namespace一組規則：哪些 apiGroup 的哪些資源，可以做哪些動作
ClusterRole整個叢集同上；也能描述節點、namespace 這類不屬於 namespace 的資源
RoleBinding一個 namespace把 Role（或 ClusterRole）綁給使用者、群組或 ServiceAccount，只在這個 namespace 生效
ClusterRoleBinding整個叢集把 ClusterRole 綁給身分，在所有 namespace 生效

RBAC 只有「允許」，沒有「禁止」：所有綁到你身上的規則取聯集，沒寫到的一律拒絕。規則裡的動作叫 verb，對應 HTTP 請求：

verbHTTPkubectl 的例子
getGET 單一物件kubectl get deployment cafe-api
listGET 一整批kubectl get deployments
watchGET ?watch=true（長連線，持續收變化）kubectl rollout status、kubectl get -w
createPOSTkubectl create job、第一次 kubectl apply
update／patchPUT／PATCHkubectl set image、kubectl annotate、之後的 apply
deleteDELETEkubectl delete

咖啡店的 CI 要執行第 9 課的 deploy.sh：換映像（patch deployments）、等 rollout 完成（get、watch deployments，看 ReplicaSet）、失敗時 rollout undo；部署前還要建立 migration 的 Job（第 10 課）。它不需要刪東西、不需要讀 Secret、不需要進容器。寫成 Role：

apiVersion: v1
kind: ServiceAccount
metadata:
  name: ci-deployer
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployer
rules:
  - apiGroups: [apps]                 # Deployment、ReplicaSet 在 apps 群組
    resources: [deployments]
    verbs: [get, list, watch, patch, update]
  - apiGroups: [batch]                # Job 在 batch 群組
    resources: [jobs]
    verbs: [create, get, list, watch]
  # …ReplicaSet、Pod 的唯讀規則，練習 1 補齊
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: deployer
roleRef:                              # 綁哪個角色（建立後不能改，要改就刪掉重建）
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: deployer
subjects:                             # 綁給誰
  - kind: ServiceAccount
    name: ci-deployer                 # 沒寫 namespace 時，指 RoleBinding 所在的 namespace

apiGroups 怎麼知道？Pod、Service、ConfigMap、Secret 這些最早的資源在核心群組，寫成空字串 ""；其他的看 kubectl api-resources 的 APIVERSION 欄（apps/v1 的群組是 apps，batch/v1 是 batch）。子資源寫成「資源/子資源」：pods/exec、pods/log、deployments/scale。

寫完一定要驗證：kubectl auth can-i

RBAC 寫錯不會報錯，只會在 CI 半夜部署時 403。用 kubectl auth can-i 以別人的身分問 API server，--as 是模擬身分（impersonation，你自己要有這個權限，kind 的管理員有）。ServiceAccount 的使用者名稱固定是 system:serviceaccount:<namespace>:<名稱>：

SA=system:serviceaccount:k8s-12-ex1:ci-deployer
kubectl auth can-i patch deployments -n k8s-12-ex1 --as $SA      # yes
kubectl auth can-i get secrets -n k8s-12-ex1 --as $SA            # no
kubectl auth can-i create pods --subresource=exec -n k8s-12-ex1 --as $SA   # no
kubectl auth can-i patch deployments -n default --as $SA         # no：RoleBinding 只在自己的 namespace 生效
kubectl auth can-i --list -n k8s-12-ex1 --as $SA                 # 列出它在這個 namespace 能做的全部事情

最小權限的幾個陷阱

  • *：verbs: ["*"] 或 resources: ["*"] 不只包含今天的資源，也包含以後新增的資源與動作（例如 escalate、impersonate）。一個一個列出來。
  • 內建的 ClusterRole：叢集預設有 cluster-admin（全部）、admin、edit、view。「給 CI 綁 edit 就好」很常見，但 edit 可以讀寫 Secret、可以 exec 進 Pod。
  • list 等於讀內容：list 回應裡就是每個物件的完整內容。kubectl get secrets -o yaml 一次印出所有密碼。對 Secret 來說 get、list、watch 都等於能讀。
  • exec 也是權限：能 create pods/exec 就能進容器讀環境變數、拿 Pod 的 token。正式環境只有少數值班人員有，而且留稽核紀錄。
  • 能建立 Pod，就幾乎能拿到 namespace 裡的一切：自己寫一個 Pod 掛載任何 Secret、用任何 ServiceAccount 執行就好。所以「能 create pods／deployments」本身就是高權限，給的時候要知道這件事；CI 只 patch 既有的 Deployment，比能建立任意工作負載安全。
EKS 上「人」與「CI」的身分是 IAM：叢集用 access entry 把 IAM 角色對應到 Kubernetes 的群組或 AWS 提供的存取政策，再由 RoleBinding 授權給那個群組。CI（例如 GitHub Actions）用 OIDC 拿到短期的 IAM 角色，不需要長期的 Kubernetes token。這裡了解即可，第 15 課會再遇到。
💡 實務上：有人說「先給我 cluster-admin，比較好查」
新同事、外包或其他團隊來要權限時，最省事的回答是綁 cluster-admin，也是之後最難收回的。資深會先問：要做什麼事、在哪幾個 namespace、要用多久。多數情況給 view 就能查問題（它不能讀 Secret）；需要部署的給自己寫的 deployer Role；值班要 exec 的，透過公司的 SSO／IAM 申請有時效的角色，並開啟稽核 log。RoleBinding 也放在 git 裡走 PR，誰在什麼時候拿到什麼權限，review 時一目了然。

ServiceAccount：Pod 在叢集裡的身分

ServiceAccount 是給程式用的身分：Pod 用它呼叫 API，CI 也可以用它。每個 namespace 建立時都會自動有一個 default，Pod 沒寫 serviceAccountName 就用它。先在練習用的叢集裡放一組 cafe-api、postgres、redis 和一個假裝被入侵的 attacker（練習 2 的環境），看一下 cafe-api 的 Pod 裡有什麼：

node check.mjs kubernetes 12          # 第一次執行：把起始檔複製到 kubernetes/practice/work/12/
export KUBECONFIG="$PWD/kubernetes/practice/.kube/config"
kubectl create namespace try-12
kubectl apply -n try-12 -f kubernetes/practice/work/12/fixtures/ex2-app.yaml

$ kubectl exec -n try-12 deploy/cafe-api -- ls /var/run/secrets/kubernetes.io/serviceaccount
ca.crt     namespace  token

kubelet 自動掛進了三個檔案：API server 的 CA 憑證、namespace 名稱，以及 token。這個 token 是 projected token：kubelet 向 API server 申請、有效期限約一小時、快到期前 kubelet 自動換新，而且綁定這個 Pod，Pod 刪除後就失效。它比舊式的永久 token 安全很多，但只要它在檔案系統裡，入侵 cafe-api 的人就能拿來呼叫 API。用 curl 的話長這樣（cafe-api 的映像沒有 curl，練習 4 的 config-watcher 用的 curlimages/curl 有）：

T=/var/run/secrets/kubernetes.io/serviceaccount
curl --cacert $T/ca.crt -H "Authorization: Bearer $(cat $T/token)" \
  https://kubernetes.default.svc/api/v1/namespaces/try-12/configmaps

能做什麼完全取決於這個 ServiceAccount 被綁了哪些 RBAC。default 預設沒有任何權限，但大家很容易為了某個工具「先綁一下」，結果同一個 namespace 每個用 default 的 Pod 都拿到了。所以兩條規則：

  1. 每個應用用自己的 ServiceAccount：權限跟著應用走，不會互相沾到。
  2. 不呼叫 Kubernetes API 的應用不掛 token：cafe-api 只處理 HTTP 和資料庫，它不需要 token。
apiVersion: v1
kind: ServiceAccount
metadata:
  name: cafe-api
automountServiceAccountToken: false     # 用這個 ServiceAccount 的 Pod 預設都不掛
---
# Deployment 的 Pod 範本
spec:
  serviceAccountName: cafe-api
  # automountServiceAccountToken: false  # 也可以寫在 Pod 上；兩邊都寫時以 Pod 為準

需要讀 API 的程式（例如監看 ConfigMap 變化的工具）就給它專屬的 ServiceAccount 和剛好夠用的 Role。只需要某一個物件時，用 resourceNames 限定名稱：

rules:
  - apiGroups: [""]
    resources: [configmaps]
    resourceNames: [cafe-flags]     # 只有這一個
    verbs: [get, watch]

resourceNames 管不到 create（建立時還沒有名字）；list、watch 要搭配 fieldSelector=metadata.name=cafe-flags 才會被允許。不加 resourceNames 的 list 會讀到 namespace 裡每個 ConfigMap。

CI 要一個暫時的 token 時，用 kubectl create token ci-deployer -n k8s-12-ex1 --duration 10m：有期限，過期就沒用。不要再建立永久 token 的 Secret，外洩了只能刪掉重建。

NetworkPolicy：Pod 之間誰能連誰

Kubernetes 預設所有 Pod 互通：任何 namespace 的任何 Pod 都能連到任何 Pod 的任何 port。在 try-12 試試看，attacker 直接連得到資料庫（映像裡有 busybox 的 nc，-z 只測連線、結束碼 0 表示連上）：

kubectl exec -n try-12 attacker -- nc -z -w 3 postgres 5432 && echo 連上了

cafe-api 被入侵時，攻擊者可以直接連 postgres、redis，或掃整個叢集。NetworkPolicy 是 Pod 層級的防火牆規則，用標籤選 Pod：

  • podSelector 選出這條規則要「保護」的 Pod；{}（空的）表示這個 namespace 的每個 Pod。
  • policyTypes 寫要管哪個方向：Ingress（進來）、Egress（出去）。
  • 某個 Pod 只要被任何一條管某方向的 policy 選到，那個方向就只剩列出的流量能通過，其他全部擋掉。多條 policy 取聯集，同樣只有允許、沒有禁止。
  • 一條連線要兩端都允許：A 的 egress 放行到 B，而且 B 的 ingress 放行來自 A。兩端都要寫好：哪天有人為了某個工具放寬了別的 Pod 的 egress，資料庫的 ingress 只收 cafe-api，仍然擋得住。
  • Pod 所在節點來的流量（kubelet 的健康檢查）一律放行，所以 readinessProbe 不受影響。

正式做法是預設拒絕（default deny）：先一條擋掉全部，再一條一條打開需要的路：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
spec:
  podSelector: {}                  # 每個 Pod
  policyTypes: [Ingress, Egress]   # 兩個方向都隔離，而且一條允許規則都沒有

最常見的坑：預設拒絕把 DNS 也擋了

cafe-api 用 postgres 這個名字連資料庫，名字要先問 kube-system 裡的 CoreDNS（第 4 課）。預設拒絕 egress 之後，DNS 查詢也出不去，應用的 log 會出現 getaddrinfo EAI_AGAIN postgres：不是資料庫掛了，是名字查不到。每個預設拒絕 egress 的 namespace 都要有這條：

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:                 # 同一個 to 元素裡的兩個 selector 是「而且」
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }        # 回應太大時 DNS 會改用 TCP

kubernetes.io/metadata.name 是 Kubernetes 自動加在每個 namespace 上的標籤，值就是名稱，用來選特定 namespace 最方便。

第二個坑：一個減號的差別

from／to 是陣列。namespaceSelector 和 podSelector 寫在同一個元素裡是「那些 namespace 裡的那些 Pod」；各自加一個 - 變成兩個元素，就成了「那些 namespace 的所有 Pod，或本 namespace 的那些 Pod」：

    - from:
        - namespaceSelector: { matchLabels: { team: cafe } }
          podSelector: { matchLabels: { app.kubernetes.io/name: cafe-api } }   # 而且：cafe namespace 裡的 cafe-api

    - from:
        - namespaceSelector: { matchLabels: { team: cafe } }                   # 或：cafe namespace 的所有 Pod
        - podSelector: { matchLabels: { app.kubernetes.io/name: cafe-api } }   # 或：本 namespace 的 cafe-api

兩種寫法都是合法的 YAML，kubectl 不會提醒你。寫完一定要從「不該連得到」的 Pod 實際試一次。

NetworkPolicy 不一定有效

NetworkPolicy 只是 API 物件，真正擋流量的是 CNI 外掛（Container Network Interface，負責 Pod 網路的元件）。CNI 不支援時，policy 照樣建立成功，然後什麼都不擋。kind 0.24 起內建的 kindnetd 會執行 NetworkPolicy，所以練習 2 能真的擋下來；EKS 的 Amazon VPC CNI 要另外開啟 network policy 功能，其他 CNI（Calico、Cilium）各有自己的設定。新叢集上線前，用一個 attacker Pod 驗證一次。

NetworkPolicy 管的是叢集內的第 3、4 層（IP 與 port）。cafe-api 要連外部的 RDS 時，egress 用 ipBlock 寫 VPC 的網段；EKS 上還有 Security Group 這一層，兩者是疊加的。它看不懂網域名稱與 HTTP 路徑，那是 service mesh 或 egress gateway 的工作。
💡 實務上：導入預設拒絕，壞掉的常常是別人
在一個已經上線的 namespace 加上 default-deny，自己的 API 測過沒問題，隔天監控團隊說 Prometheus 抓不到指標：它從 monitoring namespace 連進來，你沒列進允許清單。另一個 namespace 的批次工作呼叫你的 API、你的服務要連的外部 API，也常被漏掉。上線前先盤點所有連線：誰會連進來（Gateway、監控、其他服務）、這個服務要連出去哪裡（資料庫、Redis、外部 API、DNS）。先在 staging 開一段時間，確認沒有被擋的正常連線，再上正式環境，並事先通知可能受影響的團隊。

Pod Security：強制容器不拿多餘的權限

RBAC 決定誰能建立 Pod，但沒管 Pod 本身要了什麼：privileged: true 的容器幾乎等於節點上的 root；以 root 執行、保留所有 capability 的容器，一旦有漏洞，逃出容器的路就多很多。capability 是 Linux 把 root 權限拆成的小塊（devops 課第 7 課），例如 NET_BIND_SERVICE 讓程式聽 1024 以下的 port、NET_RAW 讓程式送自製的封包。

Pod Security Admission（PSA）是內建的准入控制（1.25 起 Stable），用 namespace 的標籤選擇三個等級之一：

等級意思給誰用
privileged不限制kube-system、CNI、儲存外掛這類要碰節點的元件
baseline擋掉已知的提權：privileged、hostNetwork、hostPath、加危險的 capability還沒改完的舊應用
restrictedbaseline 再加上：非 root、不能提權、丟掉所有 capability、要有 seccomp一般應用，咖啡店的目標

每個等級可以用三種模式套用：enforce（違規的 Pod 被拒絕建立）、warn（允許，但 kubectl 印警告）、audit（允許，寫進稽核 log）。

kubectl label namespace cafe \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted

restricted 要求 Pod 寫出這些設定（沒寫就違規，不是預設就安全）：

spec:
  securityContext:                    # Pod 層級：所有容器共用
    runAsNonRoot: true                # kubelet 確認不是 UID 0，否則拒絕啟動容器
    runAsUser: 1000                   # node 映像裡 node 使用者的 UID
    seccompProfile:
      type: RuntimeDefault            # 用容器執行環境預設的系統呼叫過濾，擋掉少用又危險的 syscall
  containers:
    - name: api
      securityContext:                # 容器層級
        allowPrivilegeEscalation: false   # 不能透過 setuid 程式變成比自己更高的權限
        capabilities:
          drop: [ALL]                     # restricted 只允許再加回 NET_BIND_SERVICE
        readOnlyRootFilesystem: true      # restricted 沒要求，但建議一起做（第 11 課）

runAsNonRoot 只是檢查，能不能真的以非 root 執行，要看映像：devops 課第 9 課的 Dockerfile 寫了 USER node，程式和檔案的權限也照著設好。映像以 root 建置、執行時才硬改 UID，常會遇到程式寫不進自己的資料夾。

違規時長什麼樣子

PSA 的 enforce 只檢查 Pod。Deployment 本身會建立成功，接著 ReplicaSet 建 Pod 時被拒絕，kubectl get pods 什麼都沒有：

$ kubectl apply -n k8s-12-ex3 -f deployment.yaml
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "api" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "api" must set securityContext.capabilities.drop=["ALL"]), runAsNonRoot != true (pod or container "api" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "api" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
deployment.apps/cafe-api created

$ kubectl describe rs -n k8s-12-ex3
  Warning  FailedCreate  …  Error creating: pods "cafe-api-…" is forbidden: violates PodSecurity "restricted:latest": …

上面那行 Warning 是 warn 模式印的（warn 和 audit 也會檢查 Deployment 這類工作負載的 Pod 範本，enforce 不會）。所以 namespace 一定要把 warn 設成跟 enforce 一樣，部署的人才會在 apply 時就看到問題，而不是去猜「為什麼沒有 Pod」。

既有的 namespace 要收緊時，先用 server 端 dry-run 看看有哪些現有的 Pod 會違規，不會真的改標籤：

kubectl label --dry-run=server --overwrite namespace cafe pod-security.kubernetes.io/enforce=restricted
💡 實務上：收緊 Pod Security 要分階段
導入順序：先在所有 namespace 開 warn=restricted，一個一個修應用，修完用上面的 dry-run 確認沒有違規，才把 enforce 調上去。最花時間的通常不是自己的服務，而是第三方 chart：不少預設以 root 執行或沒寫 seccomp，要靠 values 補上 securityContext；補不了的，放進單獨一個用 baseline 的 namespace。資安問「什麼時候全部 restricted」時，給一張 namespace 清單和每一個卡住的原因，比給一個日期可靠。

Pod 怎麼拿 AWS 權限

cafe-api 要把收據寫進 S3（第 11 課）。它需要 AWS 權限，常見的兩種錯誤做法：

  • IAM 使用者的 access key 放進 Secret：長期有效的金鑰，會出現在 Secret、環境變數、某個人的筆電裡，外洩了很難知道、也很難輪替。
  • 把權限加在節點的 IAM 角色：節點上的每個 Pod 都能透過節點的中繼資料服務（IMDS）拿到這個角色，cafe-api 要寫 S3，結果同節點的每個 Pod 都能寫。

正確做法是讓 ServiceAccount 對應到 IAM 角色，只有用那個 ServiceAccount 的 Pod 拿得到短期憑證。EKS 有兩種：

EKS Pod IdentityIRSA（IAM Roles for Service Accounts）
怎麼對應在 EKS 建立關聯：叢集＋namespace＋ServiceAccount → IAM 角色ServiceAccount 加 annotation 寫角色 ARN
需要什麼Pod Identity Agent（DaemonSet，EKS Auto Mode 已內建）；不需要 OIDC provider替叢集建立 IAM OIDC provider
角色的信任政策Service principal pods.eks.amazonaws.com，同一個角色可給多個叢集用寫死某個叢集的 OIDC 網址與 ServiceAccount
限制不支援 FargateFargate 也能用

新叢集優先用 Pod Identity。應用程式碼不用改：AWS SDK 會自動找到注入的憑證。權限照最小權限寫，例如只能寫收據這個 bucket：

{
  "Effect": "Allow",
  "Action": ["s3:PutObject"],
  "Resource": "arn:aws:s3:::cafe-receipts/*"
}

再補一刀：限制 Pod 連到節點的 IMDS（例如 IMDSv2 的 hop limit 設 1），沒有對應角色的 Pod 就拿不到節點角色。

資深的安全清單

上面每一項都只擋一種攻擊，安全是疊起來的。把咖啡店的上線前檢查寫成清單，第 16 課的期末專題會逐項檢查：

檢查擋下什麼
人、CI、應用各自的身分；Role 不用 *、不碰 Secret；不給任何應用 cluster-admin一個憑證外洩就拿下整個叢集
exec、port-forward 只給值班人員，並開啟 API server 的稽核 log（EKS 的控制平面 log）有人進容器讀密碼卻查不到是誰

namespace 套 restricted（enforce＋warn），映像以非 root 建置，根目錄唯讀容器逃逸、改寫程式

「不准用 latest」「一定要設 resources」這類組織自己的規則，PSA 沒有。可以用 ValidatingAdmissionPolicy（1.30 起 GA，用 CEL 運算式寫規則）或 Kyverno、OPA Gatekeeper 這類政策引擎在准入關卡擋下。先把上面的清單做好，再考慮這一層。

練習

在 learn 資料夾執行頁面上的指令，起始檔會複製到 kubernetes/practice/work/12/，fixtures/ 裡是測試會先套用的環境（不用改）。每一題先做靜態檢查，通過了才套用到叢集的專屬 namespace（k8s-12-ex1 這種名字），測完刪掉。想自己先試，用同一個 namespace 名稱套用 fixtures/ 與你的檔案；前面範例用的 try-12 用完記得 kubectl delete namespace try-12。

練習 1：CI 部署帳號。在 ex1/rbac.yaml 補齊 Role deployer 與 RoleBinding，讓 ServiceAccount ci-deployer 能讀取與更新 deployments（get、list、watch、patch、update）、讀取 replicasets 與 pods（看 rollout 進度）、建立與讀取 jobs；不能讀 secrets、不能刪除 deployments、不能 exec，權限只在 k8s-12-ex1 生效。測試用 kubectl auth can-i 背後的 API 檢查 14 個組合，再用 kubectl create token 拿到的 token 執行 fixtures/deploy.sh v2，要成功把 cafe-api 換成 v2。

練習 2：網路隔離。k8s-12-ex2 裡有 cafe-api、postgres、redis 和一個模擬被入侵的 attacker Pod（fixtures/ex2-app.yaml），另一個 namespace k8s-12-ex2-outside 有一個 echo 服務。在 ex2/netpol.yaml 寫出：預設拒絕所有 ingress 與 egress；所有 Pod 都能查 DNS；cafe-api 只收 k8s-tools 來的 3000、只能連 postgres:5432 與 redis:6379；postgres 與 redis 只收 cafe-api。測試先檢查 postgres、redis 的 ingress 只選 cafe-api，套用後確認 cafe-api Ready、probe 連得到它，然後從 attacker 試連 postgres、redis、cafe-api 與 echo，從 cafe-api 試連 echo，全部要連不上。

練習 3：Pod Security restricted。測試建立 k8s-12-ex3 時加上 enforce=restricted 與 warn=restricted，起始的 ex3/deployment.yaml 套用後一個 Pod 都建不出來。修改 securityContext（runAsNonRoot、runAsUser 1000、seccomp RuntimeDefault、allowPrivilegeEscalation false、丟掉所有 capability、readOnlyRootFilesystem）並在 /tmp 掛 emptyDir。測試先跑 kubectl apply --dry-run=server 要沒有任何 PodSecurity 警告，再確認 3 個 Pod Ready、程序以 UID 1000 執行、POST /uploads 回 200，namespace 的等級沒被改掉。

練習 4：不需要 token 就不要掛。在 ex4/cafe-api.yaml 替 cafe-api 建立專屬 ServiceAccount cafe-api（automountServiceAccountToken: false）並讓 Deployment 使用它。ex4/config-watcher.yaml 的 config-watcher 需要讀 ConfigMap cafe-flags：給它自己的 ServiceAccount，以及只能 get、watch cafe-flags 這一個 ConfigMap 的 Role 與 RoleBinding。測試確認 cafe-api 裡沒有 token 檔案，再在 config-watcher 裡用它的 token 呼叫 API：讀 cafe-flags 是 200，讀 cafe-menu 與 list configmaps 都是 403。

練習 5：namespace 設了預設拒絕 egress，並允許 cafe-api → postgres:5432。結果 cafe-api 連不上資料庫，log 寫著 getaddrinfo EAI_AGAIN postgres。原因是？

✓ EAI_AGAIN 是名稱解析失敗：連線根本還沒開始。預設拒絕 egress 也擋掉了 DNS 查詢，每個這樣的 namespace 都要放行到 CoreDNS 的 UDP／TCP 53。postgres 沒啟動會是連線被拒或逾時（a）；NetworkPolicy 支援任何 port（c）；規則套用後幾秒內生效，不用重啟（d）。

練習 6：給 CI 帳號 list secrets，但不給 get secrets，這樣安全嗎？

✓ list（和 watch）回傳的是完整物件，kubectl get secrets -o yaml 一次就讀到全部。Secret 的 data 只是 base64（第 6 課），不是加密（c）。部署帳號通常根本不需要碰 Secret，三個動詞都不給。

練習 7：EKS 上的 cafe-api 要把收據寫進 S3，最好的做法是？

✓ c 給的是短期、只屬於這個 ServiceAccount 的憑證，權限也只限一個 bucket。a 是長期金鑰，外洩難以察覺、輪替麻煩；b 讓同節點的所有 Pod 都能寫 S3；d 讓任何人都能寫。

練習 8：namespace 設了 pod-security.kubernetes.io/enforce: restricted（沒有設 warn），你的 Deployment 套用成功，但一個 Pod 都沒有出現。最可能的原因是？

✓ apply 成功不代表 Pod 建得起來。kubectl describe rs 會看到 FailedCreate 和違反哪幾項。把 warn 設成跟 enforce 一樣，apply 時就會印出警告。PSA 不會刪除已經在跑的 Pod（b）；標籤改了立刻對新的 Pod 生效（c）；它對任何有標籤的 namespace 都有效（d）。

常見錯誤

  • 給應用或 CI cluster-admin、或綁內建的 edit：被入侵就是整個叢集（或整個 namespace 的 Secret）。用自己寫的 Role，只列需要的動詞與資源，寫完用 kubectl auth can-i --as 驗證。
  • 以為 list 不算讀：list、watch 回傳完整內容，對 Secret 來說跟 get 一樣危險。
  • 預設拒絕忘了 DNS：所有連線都因為名稱查不到而失敗，log 是 EAI_AGAIN。每個預設拒絕 egress 的 namespace 都要放行 CoreDNS 的 UDP／TCP 53。
  • namespaceSelector 與 podSelector 多寫一個 -：「而且」變成「或」，整個 namespace 都被放行。寫完從不該連的 Pod 實際試一次。
  • 以為 NetworkPolicy 一定有效：要看 CNI 支不支援（kind 0.24 起支援；EKS 的 VPC CNI 要開啟）。不支援時物件照樣建立，什麼都不擋。
  • 每個 Pod 都掛 ServiceAccount token、都用 default：大部分應用不需要 token。給每個應用自己的 ServiceAccount，不需要就 automountServiceAccountToken: false。
  • 映像以 root 建置：restricted 會拒絕，硬改 UID 又常寫不進檔案。在 Dockerfile 就用非 root 使用者（devops 課第 9 課）。
  • 只設 enforce 不設 warn：Deployment 套用成功卻沒有 Pod，只能去翻 ReplicaSet 的事件。warn 設成跟 enforce 一樣。
  • 把 AWS access key 放進 Secret 或加權限到節點角色：用 Pod Identity／IRSA，權限只給需要的 ServiceAccount、只到需要的資源。

小結

  • 請求進 API server 要過認證（是誰）、授權（RBAC，能不能做）、准入（PSA，內容合不合規）；Pod 之間的連線另外由 NetworkPolicy 控制。
  • RBAC 只有允許：Role／ClusterRole 列出 apiGroup × 資源 × verb，RoleBinding／ClusterRoleBinding 綁給身分。不用 *、不碰 Secret（list 也算讀）、exec 與建立 Pod 都是高權限。寫完用 kubectl auth can-i … --as system:serviceaccount:ns:名稱 驗證。
  • ServiceAccount 是 Pod 的身分，kubelet 掛進有期限、會輪替的 projected token。每個應用用自己的 ServiceAccount，不呼叫 API 的就關掉自動掛載；需要特定物件時用 resourceNames。
  • NetworkPolicy：被選到的方向只剩列出的流量；兩端都要允許。做法是預設拒絕＋放行 DNS＋逐條打開需要的路；同一個元素裡的兩個 selector 是「而且」。要 CNI 支援才有效。
  • Pod Security Admission 用 namespace 標籤套 privileged／baseline／restricted；restricted 要 runAsNonRoot、allowPrivilegeEscalation false、drop ALL、seccomp RuntimeDefault。enforce 只擋 Pod，warn 設成一樣才會在 apply 時看到問題。
  • EKS 上 Pod 用 Pod Identity（或 IRSA）把 ServiceAccount 對應到最小權限的 IAM 角色，不用 access key、不加在節點角色。
