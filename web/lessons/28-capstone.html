階段 6：資深整合實戰 · 第 28 課

期末專題：咖啡店公開網站（RWD、無障礙、效能、SEO 驗收報告）

週一早上，老闆在群組裡說：「官網下週五上線。上線前給我一份東西，讓我決定能不能上。」豆留咖啡的公開網站有首頁、菜單、門市三頁。它需要的每一件事，前面 27 課你都分別練過：手機版面、鍵盤與螢幕閱讀器、圖片與載入速度、搜尋結果。真實的工作不會這樣一課一課切好，這一週你要同時顧到全部，最後還要回答老闆的問題：可以上線了嗎？你怎麼證明？

這一課從頭到尾都在回答這個問題。答案不是「我覺得差不多了」，而是一份驗收報告：列出事先談好的每一項標準，逐項寫出通過或沒通過、證據是什麼、沒通過的會造成什麼影響。學完你能把一個網站從頁面規劃做到可以上線，並寫出一份別人能核對、能拿來做決定的報告。

這課的路線：
  1. 要交什麼：三個頁面放什麼，以及營業時間這類資料為什麼只能存一份、怎麼在建置時產生。
  2. 怎樣才算做好：把「做好了」寫成誰量都一樣的 14 項驗收標準，這也是「能不能上線」的最小答案。
  3. 先做什麼、後做什麼：為什麼每做完一頁就驗一次；這次唯一的新寫法，是不靠 JavaScript 的手機選單。
  4. 自動檢查全過就代表能用嗎：鍵盤、螢幕閱讀器、200% 字級、深色模式要人來檢查，結果怎麼留成證據。
  5. 交給做決定的人：驗收報告怎麼寫、已知問題怎麼誠實列出，以及 code review 被問「為什麼這樣選」時怎麼回答。
這課會用到：
  • 第 27 課的 Playwright 與 axe：用真的瀏覽器操作頁面並斷言結果，axe 在測試裡掃描無障礙問題；這課的驗收套件就是這樣寫的。
其他各課在「驗收標準」表格的出處欄都有連結，做到那一項時再回去看。

要交什麼？三個頁面，和一份不能各寫各的資料

回答「能不能上線」之前，先把「上線的是什麼」講清楚。老闆說的「官網」是三個公開頁面加一個錯誤頁，每頁放什麼、會用到前面哪些課的重點如下：

網址內容重點
/ 首頁頁首（logo、主選單、購物車）、主視覺、本週推薦、門市資訊與營業時間、電子報表單、頁尾LCP 圖片、手機選單、表單、深色模式
/menu/ 菜單麵包屑、分類目錄、各分類的品項卡片、價目表表格語意、sticky 標題、subgrid、BreadcrumbList
/store/ 門市門市照片、地址與交通、營業時間、電話CafeOrCoffeeShop JSON-LD 與畫面一致
/404.html找不到頁面回 404 狀態碼、noindex、不放進 sitemap

設計稿給了手機（375px）與桌機（1280px）兩種版面，也給了深色模式的配色。手機的主選單收在「選單」按鈕裡，桌機直接排開。

看表格的「內容」欄會發現，同一份資料會出現在好幾個地方。營業時間在首頁和門市頁的畫面上各有一份，門市頁的 JSON-LD 裡又有一份（第 24 課教過，JSON-LD 是寫給搜尋引擎讀的結構化資料）。電話、地址、價格也一樣。如果每個地方各自手寫，遲早會發生這種事：

店長說週末改成 10:00 開門。你改了首頁畫面上的營業時間，忘了門市頁的 JSON-LD。網站上看起來一切正常，但搜尋引擎讀的是 JSON-LD 裡的 09:00，可能拿它來理解或顯示這間店的營業時間；客人照著來，門還沒開。（地圖與商家面板上的時間另外來自 Google 商家檔案，那邊也要有人改，見第 24 課。）第 24 課說過，結構化資料跟畫面不一致違反 Google 的政策，而比政策更直接的代價是客人白跑一趟。更麻煩的是，這種錯沒有任何地方會報錯，只會在某天被客人發現。

解法是讓這些資料只存在一個地方。專題規定：營業時間、電話、地址、價格只存在 data/store.json。頁面要用到時，由程式從這份檔案產生，不是手抄。

「由程式產生」發生在建置（build）這一步。建置是部署之前先跑一支程式，把原始檔加工成真正要放上伺服器的檔案。你在 Vue 專案跑的 npm run build 就是建置：把 .vue 檔編譯成瀏覽器看得懂的 JavaScript 與 CSS，輸出到 dist/。這個專題的建置更單純：build.ts 讀 site/ 裡的頁面範本，在範本留好的佔位註解處填進 store.json 的營業時間（範本裡在要放營業時間的位置寫一行 <!-- build:hours -->，build.ts 找到這行，把它換成產生好的 <dl>），同時產生門市的 JSON-LD 與 sitemap.xml，全部輸出到 dist/：

畫面上的營業時間和 JSON-LD 來自同一份資料，店長下次再改時間，你只改 store.json、重新建置，兩邊一定一起變。驗收套件是這個專題附的一組自動測試，寫在 ex1.test.ts，每一項驗收標準對應一項檢查；用 node check.mjs web 28 執行，它會先跑 build.ts 建置、用 serve.ts 啟動伺服器，再用 Playwright 開本機 Chrome 檢查 dist/。驗收套件也利用同一份資料這一點來檢查：它會換一組營業時間重新建置，再看畫面與 JSON-LD 是否都跟著變；哪一頁把舊時間寫死在 HTML 裡，就會在這裡被抓到。菜單頁的價格這次還寫在 HTML 裡，由驗收套件核對它跟 store.json 一樣；之後可以比照營業時間改成建置時產生。

「建置時把資料填進 HTML，部署出去的是純靜態檔案」這種做法有個名字：靜態網站產生（static site generation，SSG），第 25 課比較過它跟 CSR、SSR 的差別。它的好處是搜尋引擎第一次抓就看得到完整內容，不用等 JavaScript 執行。實務上會用 Nuxt、Astro、VitePress 這類工具，原理相同；這裡用一支短短的 build.ts，是為了讓你看清楚它到底做了什麼。

到這裡，要做哪些頁面、資料放在哪裡都清楚了。但如果老闆現在問「做好了嗎」，你還是答不出來，因為「做好」還沒有定義。

怎樣才算「做好了」？把它寫成誰量都一樣的條件

「做好了」最常見的麻煩，是每個人心中的標準不一樣。你覺得手機版可以了，設計師覺得間距不對，老闆用自己的手機打開，發現字被切掉。三個人都沒說錯，因為「手機版要好看」這句話本來就沒有唯一的答案，討論到最後只會變成誰的意見比較大聲。

要讓這個問題有答案，就要把「做好了」寫成驗收標準（acceptance criteria）：判斷工作完成的明確條件。「手機版要好看」不是驗收標準，兩個人量會有兩種結果；「320px 寬時不能橫向捲動」是，因為任何人在 DevTools 把寬度設成 320，看到的結果都一樣。每一條驗收標準都要回答三件事：

  • 檢查什麼：例如「頁面會不會橫向捲動」。
  • 怎麼檢查：例如「比較 scrollWidth 與 clientWidth」，或「拔掉滑鼠，只用鍵盤走一次」。
  • 多少算過：例如「在 320、768、1280px 三種寬度都不能捲動」。

專題訂了 14 項標準，分成四組，對應這門課的四條主線：R 開頭的是版面，A 開頭的是無障礙，P 開頭的是效能，S 開頭的是搜尋。每項有一個代碼，測試名稱、報告、會議上的討論都用同一個代碼，有人說「A2 沒過」，大家就知道在講哪一件事。出處欄連回教過的那一課，做到那一項時再回去看；這張表查表用，不用背：

效能那四項（P1–P4）要多說明一點：它們量的都不是使用者真正感受到的速度。第 20 課說過，LCP、INP、CLS 的真實數字要從真實使用者的瀏覽器收集，取決於他們的手機、網路與當下的狀況，這是上線前拿不到的。實驗室（你電腦上的 Lighthouse 或 DevTools）量得到 LCP、CLS，但那只是一台機器、一種網路下的一次結果，會隨機器波動，不代表使用者的體驗；INP 還需要真的有人操作。所以驗收不拿實驗室的秒數當門檻，而是檢查「會決定速度的那些設定有沒有做對」：LCP 圖片有沒有被 lazy、有沒有優先下載、圖片有多大、有沒有擋住解析的 script。這種「不直接量結果，改檢查決定結果的原因」的指標叫代理指標。四項全過，代表最常見的拖慢原因已經排除，不代表上線後一定快；所以報告的「下一步」要寫上線後怎麼追蹤真實數字。

表裡有幾項同時標了「自動」與「手動」，原因是自動工具只看得到一部分問題。這一點會一路影響到報告能怎麼寫：

自動工具只涵蓋一部分 WCAG 準則。axe 0 個違規、Lighthouse 無障礙 100 分，都不代表「符合 WCAG 2.2 AA」：替代文字寫得對不對、焦點順序合不合理、螢幕閱讀器唸起來通不通，要人來判斷。報告只能宣稱你實際檢查過的範圍。

現在可以回答開場那個問題的最小版本了：「能不能上線」＝這 14 項逐條的結果，加上每一項的證據。全部通過，你可以說「照我們事先談好的標準，可以上線」；有沒過的，就說清楚是哪一項、影響什麼，讓老闆決定要不要帶著它上線。

💡 實務上：驗收標準要在開工前談好，不是做完才補
在團隊裡，驗收標準通常寫在需求單（ticket）上，開工前由 PM、設計師和工程師一起確認。如果需求單只寫「改版首頁」，開工前先問清楚：要支援哪些裝置與瀏覽器、無障礙要做到哪個等級、誰來判定過關。做完才補的標準，很容易變成「照著做出來的東西寫標準」，失去把關的意義。也不要一次訂太多：每一條都要有人或測試真的去檢查，沒人檢查的標準只會讓報告看起來很漂亮。這次老闆只給了一句「下週五上線」，所以這 14 項要在週一就拿給他看過，週五他才會認這份報告。

後面幾節都在補這個答案的細節：先從動手開始，三頁要照什麼順序做，才能讓這 14 項過得了、又不用一直返工。

先做什麼、後做什麼？每做完一頁就驗一次

14 項標準橫跨 HTML、CSS、head、伺服器，動手的順序會直接決定返工的量。建議照下面的順序做，而且每完成一頁就跑一次驗收，不要三頁都做完才跑：

  1. HTML 與內容：先不寫 CSS，把語意寫對：landmark、標題階層、清單、表格、表單 label。這時候頁面醜但能用，鍵盤和螢幕閱讀器已經走得通。這一步放最前面，是因為後面每一步都建立在它上面：CSS 選擇器跟著結構寫，結構一改樣式就要重寫。
  2. 版面：mobile-first，先寫 320px 的版面，再用 media query 或 container query 往上加。每加一段就看 320、768、1280 三個寬度。
  3. 視覺與互動：設計變數、深色模式、hover 與焦點樣式、動畫（全部包在 prefers-reduced-motion: no-preference 裡）。
  4. head 與資料：title、description、canonical、Open Graph、JSON-LD。放在畫面完成之後，是因為 description 與 JSON-LD 要跟畫面上的內容一致，畫面還在改的時候寫，等於要寫兩次。
  5. 驗收：跑自動檢查，看哪一項沒過，回到對應的課修；再做手動檢查。

為什麼每頁都要驗，而不是最後一起驗？因為問題會疊在一起。假設首頁頁首有一個元素在 320px 寬時撐破了版面，它會讓 R1 失敗，也可能同時讓焦點被擋住、200% 字級時溢出，幾個測試一起紅。三頁都做完才跑，你會看到一長串失敗，分不出哪些其實是同一個原因、該先修哪一個。一頁一頁驗，每次失敗的範圍小，剛寫的東西也還記得，原因很快就找得到。

大部分的標準照前面各課的寫法就能通過。只有一項需要這門課還沒完整做過的寫法：R3 要求手機主選單用原生元素開關，不靠 JavaScript。三頁共用同一個頁首，選單做錯會讓三頁一起不及格，所以下一節把它講清楚。

手機選單怎麼不靠 JavaScript 開關？

先看 R3 為什麼這樣規定。第 11 課的漢堡選單是用 JavaScript 做的：點按鈕時切換選單的顯示，同時把按鈕的 aria-expanded 在 true 與 false 之間切換，讓螢幕閱讀器知道選單現在是開還是關。這樣可以用，但每個細節都要自己寫，也都可能寫漏：忘了切 aria-expanded，螢幕閱讀器的使用者不知道選單開了；忘了處理 Esc，鍵盤使用者關不掉；JavaScript 載入失敗或還沒下載完，選單就打不開，用手機的訪客連菜單頁都進不去。

第 10 課提過的 popover 把這些行為交給瀏覽器。它是 HTML 的一個屬性：元素加上 popover 之後預設隱藏；另一個按鈕用 popovertarget 指向它的 id，按下按鈕就會打開或關閉它，不用寫任何 JavaScript：

<button class="menu-toggle" type="button" popovertarget="site-nav">選單</button>
<nav id="site-nav" class="site-nav" popover aria-label="主選單">…</nav>

/* 寬螢幕：選單直接排開。作者樣式的 display 會蓋過瀏覽器把 [popover] 藏起來的預設樣式 */
@media (min-width: 48em) {
  .menu-toggle { display: none; }
  #site-nav { display: block; position: static; inset: auto; margin: 0; padding: 0; border: 0; }
}

HTML 那兩行換到的行為，正好是 JavaScript 版容易寫漏的那幾件：

  • 按按鈕開、再按一次關；按 Esc 或點選單外面也會關閉。
  • 瀏覽器自動把按鈕和選單的展開關係（相當於 aria-expanded）告訴輔助科技，不用自己切換。
  • 打開後，選單裡的連結緊接在按鈕之後進入 Tab 順序，鍵盤使用者按下一個 Tab 就進到選單裡。

CSS 那一段處理寬螢幕。popover 的元素平常是隱藏的，這是瀏覽器內建樣式給 [popover] 的規則；在 48em 以上，作者自己寫的 display: block 會蓋過這條內建規則，選單就直接排開。同一段把「選單」按鈕藏起來，也把 popover 預設的定位、外距、內距與邊框清掉，讓選單回到頁首的一般排版裡。

還有一件事要考慮：popover 是比較新的功能，不是每個訪客的瀏覽器都支援。不支援的舊瀏覽器會忽略 popover 屬性，選單就變成一般區塊直接顯示出來，按鈕沒有作用，但連結都點得到，網站仍然可以用。這種「舊瀏覽器少一點功能、但不會壞」的設計叫漸進增強（progressive enhancement）：先確保最基本的版本人人能用，再替支援的瀏覽器加上更好的體驗。支援狀態與資料來源見課末〈補充與查表〉。

為什麼不用其他看起來也能開關的寫法？最常見的有兩種，都過不了這一節開頭的要求。<div onclick>：div 不是按鈕，Tab 停不到、Enter 和空白鍵按不了，沒有 JavaScript 時也打不開。隱藏的 checkbox 加 label：靠 :checked 切換顯示，確實不用 JavaScript，但螢幕閱讀器唸的是「核取方塊」，使用者聽不出它能展開選單。popover 的觸發器是真正的 <button>，角色、鍵盤操作、展開狀態都是對的。

三頁做完、選單也換成 popover，自動驗收跑過一輪全部通過。這時候能跟老闆說「網站可以用」了嗎？

自動檢查全過，就代表能用嗎？手動檢查清單

還不能。上一節的選單就是例子：自動檢查可以確認按下按鈕後連結出現了，但「按 Esc 關掉選單之後，使用者知不知道焦點跑到哪裡」，要有人實際用鍵盤走一次才知道。驗收標準那一節的警告說的也是同一件事：自動檢查證明的是「沒有它抓得到的錯」，手動檢查確認的是「真的能用」。

R2、A2、A3、A4 標了「自動＋手動」，就是這個原因。每次大改版，至少照下表走一次：

項目怎麼做看什麼
鍵盤拔掉滑鼠，只用 Tab、Shift+Tab、Enter、空白鍵、Esc 走完三頁；在手機寬度打開、關閉選單每一步都知道焦點在哪；順序跟畫面一致；不會被 sticky 頁首蓋住；Esc 關選單後焦點回到按鈕
螢幕閱讀器macOS 按 Command+F5 開關 VoiceOver；Control+Option+U 打開轉輪（rotor），用左右鍵切換標題、landmark、連結清單標題清單讀起來像目錄；landmark 有主選單、主要內容、頁尾；表格移動時會唸欄標題；圖片的替代文字有意義
200% 字級Chrome 設定 › 外觀 › 自訂字型，把「字型大小」拉到 32（預設 16 的兩倍；「字型大小」下拉選單裡最大的選項只有 24，也就是 1.5 倍）；另外用 Command++ 把頁面縮放到 200%文字不被截斷、不重疊，不需要左右捲動才讀得完
深色模式系統切到深色，或 DevTools 的 Rendering 面板模擬 prefers-color-scheme: dark（第 18 課）每個區塊都換了顏色，沒有白底刺眼的區塊或看不清的灰字；把截圖附在報告裡

「看什麼」那一欄的每一項，都是自動工具判斷不了的：焦點順序合不合理、標題清單讀起來像不像目錄、替代文字有沒有意義、字放大後讀不讀得完。這些判斷需要人。

手動檢查的結果也要當成證據留下來：寫下用什麼工具、在哪個瀏覽器、看到什麼。只寫「已檢查」的手動項目，下一個人沒辦法重現，也沒辦法判斷可不可信；放進報告後，讀的人分不出你是真的走過一次，還是只勾了格子。

到這裡，14 項的自動結果與手動檢查的紀錄都有了。最後一步是把它們交給老闆，而老闆不會去讀測試程式。

怎麼讓老闆一眼決定能不能上線？驗收報告

測試的輸出是寫給工程師看的：一長串 ✓ 與 ✗、錯誤訊息、檔名。老闆要的是另一種東西：能不能上線、不能的話差在哪、風險多大。把前面的結果翻譯成這種形式，就是驗收報告（acceptance report）：說明作品有沒有達到驗收標準，以及證據是什麼。讀的人通常是 PM、老闆或客戶，他們要決定照原訂時間上線、延後，還是帶著已知的問題先上。

範本有六段，順序照讀者的需要排：最前面先給結論，越往後越細，只讀摘要的人也能做決定。

段落寫什麼常見的錯
摘要3 句以內：結論（能不能上線）、通過幾項、最重要的風險寫成過程紀錄，結論藏在最後
範圍檢查了哪些頁面、裝置、瀏覽器；依據哪些標準與版本；什麼不在範圍內沒寫範圍，讀者以為整個網站（包括別人負責的點餐系統）都驗過
方法自動檢查的指令（別人能重跑）與工具版本；手動檢查清單只寫「用工具測過」
結果表格：代碼、標準、通過／未通過、證據證據寫「OK」
未通過與已知問題每個問題的影響、風險、負責人、預計處理時間不寫，或寫「之後再修」
下一步修正計畫、上線後的監控（RUM、Search Console）空白

六段裡最容易寫壞的是「未通過與已知問題」。已知問題（known issue）是已經發現、這次決定不修、但有追蹤與說明的問題。它跟「沒發現的問題」差別很大：老闆知道門市頁有一段文字在深色模式下看不清楚，就能判斷值不值得延後上線、要不要先跟客服說一聲；不知道的話，他只能等客人來抱怨。也因為報告的價值就在這裡，把未通過的項目寫成通過，報告就失去意義，被發現一次，下一份報告也不會有人相信。

第二容易寫壞的是「結果」表的證據欄。證據要具體到別人能核對。比較同一項的兩種寫法：

代碼結果不好的證據好的證據
A4通過OK驗收套件 A4：color-contrast 0 個違規；三頁深色模式截圖 dark-home.png、dark-menu.png、dark-store.png
P4通過圖片有壓縮375px、DPR 2 首頁圖片合計約 18 KB（只有 hero-960.webp），預算 600 KB
A2未通過鍵盤有點問題門市頁第一個 Tab 停點是 logo，沒有跳到主要內容的連結；見已知問題 K2

好的證據寫出了用什麼量、量到多少、標準是多少，或附上別人打得開的檔案。A2 那一列也示範了未通過怎麼寫：哪一頁、哪裡不對，再指到已知問題的編號，讓讀者知道它有人追蹤。

💡 實務上：報告是給「能不能上線」的那場會用的
上線前常有一場簡短的確認會議，PM 或主管看著報告決定照原訂時間上線、延後，還是帶著已知問題先上。這時候摘要寫得清楚、每個已知問題都有負責人和處理時間，決策很快就能做完；寫得含糊，就會變成大家在會議上重新問一遍。已知問題如果會影響使用者（例如門市頁電話打錯），記得先通知客服或店長，別讓他們從客人口中才知道。上線後把報告和 CI 執行紀錄的連結留在需求單上，下次改版或有人問「當時怎麼驗的」時才找得到。

報告回答的是「能不能上線」。不過在交給老闆之前，程式碼還要過另一關，那裡的人問的是另一個問題：為什麼這樣做。

code review 被問「為什麼這樣選」時，怎麼回答？

專題的程式碼要合併進主線之前，會先經過 code review：同事讀你的改動，確認沒有問題才合併。驗收報告說明「結果如何」，code review 問的是「為什麼這樣做、代價是什麼」，資深工程師被期待的不是列出用了什麼，而是說得出選擇的理由。這個專題有五個決定值得先寫好說明，最好直接寫在 PR 的說明裡。

用了比較新的功能，不支援時會怎樣。這個網站用了 container queries（本週推薦卡片）、subgrid（菜單卡片的價格對齊）、popover（手機選單）。前兩個是 Baseline 普遍可用，popover 是新近可用（第 12 課講過 Baseline 怎麼分級）。新近可用的功能，說明時要講清楚不支援時的樣子，例如「選單會直接顯示，連結都點得到」，而不是只說「Chrome 可以」。

沒用什麼也要說。這個網站沒有載入網頁字型，用系統字型，因為中文字型太大（第 15 課）；也沒有放客服 widget 的載入程式，因為第三方 script 會拖慢首屏（第 21 課）。這些「刻意不做」的決定要寫下來，不然下一個人看到少了東西，會「順手」加回去。

資料只有一份。這是第一節做的決定：營業時間只在 store.json，畫面與 JSON-LD 都從它產生。審查的人可能會問「直接寫在 HTML 不是比較簡單嗎」，你的理由是那位照著搜尋結果白跑一趟的客人，證據是驗收套件「換一組營業時間重建」的檢查。

staging 與正式環境的差別。staging 是上線前給團隊測試的環境，內容跟正式網站一樣，但不該被搜尋引擎收錄，所以它的 robots.txt 常寫 Disallow: /。上線時如果把檔案整包複製過去，忘了換掉這一行，整個網站就不會被爬（第 23 課）。設定要跟著環境產生，不要手動複製。

伺服器也是網站的一部分。找不到的網址如果回首頁加 200 狀態碼，對使用者看起來友善，對搜尋引擎卻是 soft 404。第 23 課講過這個名詞：內容其實是「找不到」或不相干的頁面，狀態碼卻說成功，搜尋引擎可能把它當成正常頁面收錄，連打錯字的網址也一起進了索引。所以 S3 要求不存在的網址回 404 並加 noindex。部署到靜態主機（Nginx、Netlify、S3＋CloudFront）時，要確認它的 404 設定。

這些決定在驗收套件裡大多有對應的檢查。套件做的事跟第 27 課練習 2 的 auditPublicPages 類似（狀態碼、title、canonical、axe），再加上版面、鍵盤、深色模式、圖片大小與資料一致性。前面說過它寫在 ex1.test.ts 裡，現在回頭打開來看，就知道每一項怎麼量；你在工作上可以照這個樣子，把團隊的驗收標準寫成 CI 的檢查，讓「能不能上線」在每次合併前就有答案。接下來的練習，就是把這一週的工作實際做一遍。

補充與查表

  • popover 的行為與支援度：本課描述的行為（popovertarget 開關、Esc 與點選單外面關閉、自動告知輔助科技展開關係、打開後選單裡的連結緊接在按鈕之後進入 Tab 順序）依據 MDN Popover API 文件（2026-10-20 版）。popover 是 Baseline 新近可用（web-features 3.44.0）。
  • container queries 與 subgrid 的支援度：container queries 是 Baseline 普遍可用（2025-08），subgrid 是普遍可用（2026-03）。

練習

練習 1、2 在瀏覽器裡做首頁與菜單頁，練習 3、4 在自己的電腦上把三頁組成完整網站並寫報告。練習 3 的首頁與菜單頁已經放好練習 1、2 的成果，要你處理的是門市頁、整站設定與建置程式。

練習 1：首頁（整份文件，HTML 與 CSS 都可以改）。目前的版本有很多地方不合格，照驗收標準修好：頁首加「跳到主要內容」；手機選單改成 <button popovertarget>（或 <details>）開關，寬螢幕直接排開；主視覺用 srcset（14-latte-480.webp、14-latte-960.webp、14-latte-1440.webp，原圖 1440×960）加 sizes，立刻載入並優先下載；本週推薦卡片用 container query；電子報欄位要有 label、type="email"、autocomplete、必填；JSON-LD 的營業時間要跟畫面一致；補上 canonical（https://brew.example.tw/）與 Open Graph；支援深色模式與減少動態；焦點看得見；字級 200% 時 320px 寬不能撐破。檢查前可以先用預覽工具列切換寬度看看。

練習 2：菜單頁（網址 https://brew.example.tw/menu/，整份文件）。修好這些問題：價目表要有 <caption>、<thead>、th scope，在手機上放進可以聚焦、有名稱的捲動容器（overflow-x: auto、tabindex="0"、role="region" 加 aria-labelledby），不要用 main 的 overflow-x: hidden 把問題藏起來（它也會讓 sticky 的分類標題失效）；品項卡片用 subgrid 讓同一列的價格對齊，不要固定描述的高度；點分類目錄跳過去時，標題不能被 sticky 頁首擋住；麵包屑的 BreadcrumbList JSON-LD 要跟畫面一致；補上 canonical。

練習 3：完成整個網站，通過 14 項驗收標準。site/ 是網站原始檔，build.ts 把它建置到 dist/，serve.ts 提供 dist/。先執行一次下面的指令，讀每一項沒過的訊息，再逐項修：

  • build.ts：寫 sitemapXml()（只列出不是 noindex 的路由、絕對網址、不輸出 priority 與 changefreq）、hoursHtml()（每天一組 <dt>週一</dt><dd>07:30–18:00</dd>，沒營業寫「公休」）、storeJsonLd()（完整的 CafeOrCoffeeShop，營業時間跟 hoursHtml() 用同一份 store.hours）。首頁與門市頁的營業時間都由 <!-- build:hours --> 產生。測試會換一組營業時間、也會用另一組路由表直接呼叫 sitemapXml()，寫死的值會被抓到。
  • site/robots.txt：現在還是 staging 的設定。
  • serve.ts：找不到的網址要回 404 狀態碼與 404.html；site/404.html 要 noindex。
  • site/index.html：主視覺給手機下載 1600px 的 JPEG（344 KB），改用 img/hero-480.webp、hero-960.webp、hero-1440.webp。
  • site/menu/index.html：head 裡有第三方客服程式、canonical 是相對路徑。
  • site/store/index.html：title 跟首頁重複、沒有 canonical、沒有跳到主要內容的連結、照片沒有替代文字與尺寸、head 裡的 <style> 有兩個問題（深色模式看不清楚的顏色、拿掉 outline）。

想在瀏覽器裡看：在 web/practice/work/28/ 執行 node build.ts && node serve.ts dist，打開 http://localhost:4173/ 。驗收要開 Chrome 跑三個頁面，一次大約一到兩分鐘。

練習 4：照範本在 REPORT.md 寫驗收報告。六個二級標題照範本的順序（摘要、範圍、方法、結果、未通過與已知問題、下一步）；摘要 3 句以內；方法寫出自動檢查的指令 node check.mjs web 28 與手動檢查清單（鍵盤、VoiceOver、200% 字級、深色模式，實際做一次再寫）；結果表列出全部 14 個代碼，每列寫「通過」或「未通過」與具體的證據；未通過或已知問題寫出影響、風險、負責人、預計處理時間；全文 400～3000 字。測試會用練習 3 的驗收結果核對：自動檢查沒過的項目不能寫「通過」。內容寫得好不好測試判斷不了，寫完用下面的清單自己檢查：

  • 只讀摘要的人，知道能不能上線、風險是什麼嗎？
  • 別人照「方法」能重跑出同樣的結果嗎？工具有寫版本嗎？
  • 每個「通過」都有別人能核對的證據嗎？手動項目有寫在哪個瀏覽器、看到什麼嗎？
  • 報告有沒有宣稱超過實際檢查範圍的事（例如「符合 WCAG 2.2 AA」）？

練習 5：axe 0 個違規、Lighthouse 無障礙 100 分，驗收報告可以寫「網站符合 WCAG 2.2 AA」嗎？

✓ b：替代文字是否恰當、焦點順序是否合理、螢幕閱讀器唸起來是否通順，自動工具判斷不了，所以 axe 與 Lighthouse 都只能證明「沒有它們能抓到的錯」。a 把工具的結果當成全部準則。c 重跑不會增加涵蓋範圍。d 客戶接受與否不會改變事實，誇大的宣稱出事時責任在寫報告的人。

練習 6：上線前發現門市頁一段文字在深色模式對比不足，這次來不及修，報告應該怎麼寫？

✓ b：報告的價值是讓決策者知道真實狀態，知道風險才能決定要不要延後、要不要先處理。a、c 隱瞞問題，被發現後整份報告都不可信。d 為了通過驗收刪掉內容，傷害的是需要那段資訊的使用者，問題也沒解決。

練習 7：專題首頁與門市頁都有營業時間，門市頁還有 CafeOrCoffeeShop 的 JSON-LD。營業時間應該從哪裡來？

✓ b：單一資料來源，改一處全部一致，驗收套件也能用「換一組資料重建」來證明。a 遲早會漏改，畫面與 JSON-LD 不一致違反結構化資料政策。c 搜尋引擎要等渲染才看得到，還依賴外部服務。d 營業時間是門市 rich result 的建議欄位，搜尋的人常常就是要找它。

常見錯誤

  • 沒有先談好驗收標準就開工：做完才補的標準會變成照成品寫標準，「做好了沒」又回到各說各話。開工前把每一條寫成檢查什麼、怎麼檢查、多少算過，給決策者確認。
  • 最後才做驗收：問題疊在一起，很難分辨原因。每完成一頁就跑一次。
  • 報告只寫通過的部分：決策者看不到風險，被發現後整份報告失去可信度。未通過與已知問題一定要寫，附負責人與時間。
  • 同一份資料寫死在好幾處：營業時間改了只改到首頁，JSON-LD 還是舊的。從單一資料來源產生。
  • 手機選單用 <div onclick> 或隱藏的 checkbox：前者鍵盤按不到、沒有 JavaScript 打不開；後者螢幕閱讀器唸成「核取方塊」。用 <button popovertarget>。
  • 只測桌機：多數訪客用手機。320px、200% 字級、手機選單都要驗。
  • 用 overflow: hidden 消滅橫向捲動：被裁掉的內容讀不到，還會讓 sticky 失效。找出撐破的元素，讓它自己換行或在自己的容器裡捲動。
  • staging 的設定帶上正式環境：robots.txt 的 Disallow: /、noindex、測試用的 canonical。讓設定跟著環境產生，並放進驗收。
  • 把工具分數當成結論：axe 0 個違規不等於符合 WCAG，Lighthouse 100 分不等於真實使用者很快。報告寫清楚檢查了什麼。

小結

  • 「能不能上線」的答案，是事先談好的驗收標準逐條的結果加上證據，不是「感覺差不多了」。
  • 驗收標準要可以檢查：檢查什麼、怎麼檢查、多少算過，每項給代碼，讓測試、報告、討論都對得上。效能在上線前只能量代理指標，真實數字要上線後追蹤。
  • 會出現在多處的資料只存一份，建置時產生 HTML 與 JSON-LD；用換一組資料重建來驗證。
  • 順序是內容 → 版面 → 視覺與互動 → head 與資料 → 驗收，每頁做完就驗一次。
  • 手機選單用 popover：開關、Esc、展開狀態由瀏覽器負責；不支援的瀏覽器直接顯示選單，這是漸進增強。
  • 自動檢查證明沒有已知的錯，手動檢查（鍵盤、螢幕閱讀器、200% 字級、深色模式）確認真的能用；兩者都要寫進報告。
  • 驗收報告寫給要做決定的人：摘要先講結論，證據具體到能核對，未通過與已知問題寫出影響、風險、負責人、時間。
  • code review 時說明取捨：用了哪些新功能、不支援時會怎樣、刻意不用什麼、設定怎麼跟著環境走。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：菜單頁的「只看熱飲」篩選按鈕照下面這樣寫，點了會切換 class，按下時變成深棕色。哪裡會出事？

<button type="button" class="chip is-pressed">只看熱飲</button>

.chip.is-pressed { background: var(--color-action-primary); }

✓ 狀態要放在 DOM：切換 aria-pressed="true"／"false"，選擇器寫 .chip[aria-pressed="true"]，外觀和輔助科技讀到的狀態就不會分家。b 錯在圖示只是看得到的提示，無障礙樹裡還是沒有狀態；「不只靠顏色」是另一條規則，兩件事都要做。（第 26 課）

練習 9：設計系統的 <CafeButton> 沒給 type 時原本輸出 <button>（預設是 submit），新版改成預設 type="button"，避免表單被誤送。props 和樣式都沒變，該發哪種版本？

✓ 改預設行為是不相容的改動：靠預設 submit 的電子報表單升級後就送不出去，而且不會報錯。用 ^ 範圍安裝的專案會自動拿到 minor 與 patch，所以只能放在 major，並寫清楚怎麼遷移。c 錯在版本看的是使用者的程式會不會壞，不是改動的動機。（第 26 課）

練習 10：這段驗收在本機都通過，在 CI 上大約十次失敗一次，失敗時讀到的是「購物車：0 件」。原因是？

await page.getByRole('button', { name: '加入購物車' }).click()
const text = await page.getByRole('status').textContent()
expect(text).toBe('購物車：1 件')

✓ expect(await …) 先讀值再比對，比的是一個不會再變的字串；web-first assertion 把 locator 交給斷言，重查到成立或逾時為止。c 錯在固定等待只是把機率調低：本機白等 1 秒，CI 更忙時照樣失敗。（第 27 課）

練習 11：網站之後加了線上點餐：大杯加 20 元、燕麥奶加 15 元、會員 9 折，團隊把 40 種組合都寫成 E2E，CI 跑 25 分鐘而且常常紅。最根本的改法是？

✓ E2E 證明各部分接得起來，規則的細節交給下層：單元測試一個組合幾毫秒，壞了直接指到出錯的函式。E2E 的數量少了，慢與時好時壞的來源也跟著少。a 錯在重試只是止血，根因還在，真的 bug 也會被當成運氣不好。（第 27 課）

練習 12：首頁頁首的購物車原本是 <div class="cart" onclick="openCart()"> 包一個圖示。同事加上 role="button" 與 aria-label="購物車"，說 axe 已經沒有違規。還有什麼問題？

✓ ARIA 只改無障礙樹，div 加了 role 只是讓輔助科技以為它是按鈕。原生 <button> 一次給齊角色、焦點與鍵盤行為，能用原生就不用 ARIA。c 錯在把 axe 沒報錯當成能用：鍵盤操作要實際用 Tab 走一次，這正是手動檢查的項目。（第 5 課）

練習 13：tokens 轉成 CSS 後如下。切到深色主題，連結都變成淺色了，結帳按鈕卻還是深棕色。問題在哪？

:root {
  --color-brown-700: #6e401e;
  --color-action-primary: var(--color-brown-700);
  --button-primary-bg: #6e401e;
}
:root[data-theme="dark"] { --color-action-primary: #d9a477; }

✓ 轉換工具把 button.primary.bg 的別名抄成最後的值，畫面平常一樣，但換主題只改語意變數時，按鈕早已寫死。別名要輸出 --button-primary-bg: var(--color-action-primary)。d 錯在按鈕根本沒參照任何變數，改哪一層都一樣；換主題本來就該改語意層。（第 26 課）

練習 14：改版上線兩週，官網從搜尋結果幾乎消失，原因是 staging 的 robots.txt（Disallow: /）隨部署整包複製到了正式機。改回來之後，怎麼避免再發生？

✓ 設定跟著環境產生，不靠手動複製；再把「正式環境沒有 Disallow: /、沒有 noindex」放進部署後的驗收。a 錯在全站 noindex 一樣會被帶上正式環境，而且這次是整站從索引移除；staging 要靠登入擋。（第 23、28 課）

練習 15：首頁的視覺回歸基準圖是同事在自己的 Linux 工作機上用 -u 產生的，推上去後 CI 每次都失敗，差異集中在所有文字的邊緣。怎麼處理？

✓ 不同機器的字型與反鋸齒畫出來不一樣，在自己的電腦產生基準圖、在 CI 比對，永遠對不上；基準圖要在跟 CI 相同的映像裡產生。a 錯在容許 10% 的差異，按鈕文字消失（約 0.3% 的像素）也抓不到，等於沒測。b 也沒用：每次都失敗不是 flaky。（第 27 課）
