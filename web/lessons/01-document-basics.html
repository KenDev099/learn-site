階段 1：HTML 與可操作的網頁 · 第 1 課

網頁文件基礎：DOM、head、metadata、資源載入與路徑

豆留咖啡的新官網用 Vue 3 和 Vite 做，上線第一週，客服轉來五張單：

  1. 手機打開首頁，字小到要用兩隻手指放大才看得清楚。
  2. 網路慢的時候，首頁白了好幾秒才出現內容。行銷上週剛在 <head> 最上面貼了一段追蹤碼。
  3. 商品頁的「商品說明」只要有條列，樣式就整個跑掉，但開發時寫的 CSS 明明有套到。
  4. 從 /menu 進去，菜單照片全部破圖；從 /menu/ 進去就正常。
  5. 每次部署完，有些人看到白畫面，重新整理就好。

五張單看起來各不相干，其實都發生在同一段過程裡：瀏覽器收到一份 HTML，把它變成畫面。寫 Vue 的時候，這段過程被框架和 Vite 包起來，平常不必想；一出問題，不懂這段過程就只能猜。這一課沿著這段過程從頭走一遍，每走到一步，就解掉卡在那一步的那張單。學完你能看著症狀判斷是哪一步出錯、該去 DevTools 的哪裡查。

這課的路線：
  1. 瀏覽器拿到 HTML 之後做了哪些事：先畫出整段過程的地圖，把五張單各自放到它出錯的那一步（開場問題的最小答案）。
  2. 商品說明為什麼跑版：解析器會自動修正寫錯的結構，DevTools 裡看到的 DOM 跟原始碼不一樣（第 3 張單）。
  3. 手機上字為什麼那麼小：文件開頭的 doctype、lang、charset、viewport、title，每一行少了會出什麼事（第 1 張單）。
  4. 首屏為什麼白好幾秒：head 裡會讓畫面停下來等的兩種東西，以及 script 的 defer、async、module（第 2 張單）。
  5. 同一個網址為什麼一邊破圖一邊正常、部署後為什麼白畫面：瀏覽器怎麼算出要請求的網址，伺服器回應的 Content-Type 和快取（第 4、5 張單）。
這課會用到：
  • Node 課第 12 課的 HTTP 請求與回應：瀏覽器送出請求，伺服器回傳狀態碼、標頭與內容，Content-Type 標頭說明內容是什麼格式。
這門課的 HTML／CSS 練習：左邊編輯，下方即時預覽，按「檢查答案」後，隱藏測試會讀預覽裡的 DOM、計算後的樣式和版面。預覽不會執行你寫的 JavaScript（iframe 沒有開放 scripts），所以練習只靠 HTML 和 CSS 完成。

瀏覽器拿到一份 HTML 之後，做了哪些事？

要判斷五張單各卡在哪裡，先要有一張地圖：從使用者打開網址，到畫面出現，中間依序發生了什麼。

使用者打開 https://brew.example.tw/menu/，瀏覽器送出 HTTP 請求，伺服器回傳一串位元組，標頭寫著 Content-Type: text/html。瀏覽器不等整份下載完，收到一段就處理一段。這一點後面會一直用到：解析是由上往下、邊收邊做的，所以寫在 <head> 裡的東西，一定比 <body> 的內容先被讀到；head 裡任何一行讓瀏覽器停下來，body 就跟著等。

收到的位元組依序經過這幾步：

  1. 解碼與切 token：位元組本身只是數字，瀏覽器先照編碼（通常是 UTF-8）把它們解成字元，再把字元切成一個個有意義的片段，例如「開始標籤 p」「文字 推薦：」「結束標籤 p」。這些片段叫 token。
  2. 建出 DOM：解析器拿 token 組出一棵樹，每個元素是一個節點，子元素掛在父元素底下。這棵在記憶體裡的樹叫 DOM（Document Object Model）。DOM 是之後所有事情的依據：JavaScript 的 document.querySelector 找的是 DOM 裡的節點，CSS 選擇器比對的也是 DOM，不是你寫的原始碼。Vue 的 ref 拿到的元素、v-if 插入和移除的，也都是 DOM 節點。
  3. 發出更多請求：解析途中遇到 <link rel="stylesheet">、<img>、<script src>，瀏覽器各自再送一個 HTTP 請求。每個請求都要先把 href 或 src 算成完整網址，伺服器每個回應也都帶著自己的 Content-Type。
  4. 算樣式、排版、繪製：CSS 下載回來後被解析成另一棵樹，叫 CSSOM，全名是 CSS Object Model，跟 DOM 是同一個概念，只是對象換成樣式規則。光有 DOM 只知道有哪些元素，光有 CSSOM 只知道有哪些規則；兩者合起來，瀏覽器才知道每個要顯示的元素長什麼樣子，這個合起來的結構叫 render tree。接著算出每個元素的位置與大小（排版），最後畫到螢幕上（繪製）。

有了這張地圖，五張單就能各自放回它出錯的那一步：

單出錯的那一步一句話原因

接下來照這個順序一張一張解。最靠近起點的是建出 DOM 這一步：解析器組 DOM 時並不是照抄你寫的東西，這正是第 3 張單的原因。

商品說明為什麼跑版？原始碼不等於 DOM

上一節說解析器拿 token 組出 DOM。關鍵在於：HTML 解析器從不報錯。寫錯的結構不會讓頁面停住，而是照規範自動修正後繼續往下讀。

這是刻意的設計。網路上有大量手寫、結構不完整的舊網頁，如果瀏覽器遇到錯就拒絕顯示，這些頁面全部會壞掉。所以 HTML 規範把「遇到每一種錯誤該怎麼修」都寫死了，每個瀏覽器照同一套規則修，結果一致。代價是：修正後的 DOM 可能跟你寫的原始碼差很多，而且沒有任何錯誤訊息提醒你。

第 3 張單就是這樣來的。後台的商品說明是用富文字編輯器寫的，存成一段 HTML。商品頁要讓搜尋引擎讀得到說明，所以不是等 Vue 在瀏覽器裡把內容畫出來，而是由伺服器先把整頁 HTML 組好再送出，商品說明直接輸出在 <p class="desc"> 裡；CSS 寫了 .desc ul { … } 來排條列。只要說明裡有 <ul>，瀏覽器收到的是 <p class="desc"><ul>…</ul></p>，但 <p> 裡只能放文字和行內元素，放不了清單、<div> 這類區塊元素。解析器一看到 <ul> 就先把 p 關掉，ul 變成 p 的兄弟而不是孩子；後面多出來的 </p> 再變成一個空段落。DOM 裡已經沒有「在 .desc 裡面的 ul」，.desc ul 自然一個都選不到，樣式就跑了。

這裡有一個前提要說清楚：會被拆開，是因為這段 HTML 是伺服器送來、交給文件解析器從頭讀的。同一段字串如果是在瀏覽器裡用 Vue 的 v-html（底層就是設定 innerHTML）塞進 p，走的是另一套「片段解析」規則：解析器只處理塞進去的那一段，外面那個 p 不在它手上的開放元素清單裡，遇到 <ul> 時沒有 p 可以關，ul 就留在 p 裡面，.desc ul 選得到。所以只開 Vite dev server、內容全由瀏覽器畫出來時，這個問題重現不了；要看伺服器實際輸出的 HTML 才會遇到。

開發時沒發現，一部分是這個原因，另一部分是測試資料的說明剛好沒有條列。下面是最常遇到的幾種修正，左邊是你寫的，中間是瀏覽器實際建出來的：

原始碼瀏覽器建出的 DOM原因
<p>推薦：<div>耶加雪菲</div></p><p>推薦：</p><div>耶加雪菲</div><p></p><p> 裡不能放區塊元素，遇到 <div> 就先把 p 關掉；多出來的 </p> 變成一個空段落
<table><tr>…</tr></table><table><tbody><tr>…</tr></tbody></table>表格列一定放在 <thead>、<tbody> 或 <tfoot> 裡，沒寫就自動補 tbody
<a href="/a">外<a href="/b">內</a></a><a href="/a">外</a><a href="/b">內</a>連結不能包連結，第二個 a 出現時先關掉第一個

要分辨兩者，Chrome 給了兩個入口。按右鍵「檢視網頁原始碼」，看到的是伺服器回傳的原始碼，一個字都沒動過；DevTools 的 Elements 面板，看到的是修正後的 DOM。兩者不同時，CSS 選擇器和 JavaScript 都照 DOM 走：例如寫 table > tr 會選不到任何東西，因為 DOM 裡 tr 的父元素是自動補上的 tbody。

豆留商品頁這種「伺服器先組好 HTML 再送出」的做法，在 Vue 裡叫伺服器端渲染（SSR），而用了 SSR，這個落差還會多出一個症狀。SSR 是伺服器先把 Vue 元件執行一次、產生成完整的 HTML 送出，使用者不必等 JavaScript 下載完就看得到內容；瀏覽器載入 Vue 之後，Vue 不重畫一次，而是把元件的狀態和事件「接上」這份已經存在的 DOM，這一步叫 hydration。Vue 接上時會假設 DOM 的結構跟它在伺服器上產生的一樣；如果伺服器輸出的 HTML 被瀏覽器修正過，兩邊對不上，就是 hydration mismatch（Vue 課第 24 課）。

解法在源頭：結構寫對，原始碼和 DOM 就會一致，修正規則根本不會被觸發。練習 3 會練這件事。

💡 實務上：畫面怪怪的，先看 DOM 而不是原始碼
像豆留的商品說明這種富文字內容不受你控制，外層容器用 <div> 比較保險，裡面放什麼都不會被拆開；自己寫的模板也避免 p 包區塊、a 包 a。資深工程師遇到「CSS 明明寫了卻沒套上」，第一步是打開 Elements 面板對照 DOM，確認元素真的在你以為的位置，而不是反覆改 CSS。用 SSR 的專案，Console 出現 hydration mismatch 警告時也先往這個方向查。Code review 時看到這種巢狀，值得直接指出來。

DOM 是解析出來的結果；而解析器要用什麼規則讀、手機要用多寬去排，取決於文件開頭那幾行。第 1 張單就是開頭少了一行。

手機上字為什麼那麼小？文件開頭每一行的用途

打開豆留首頁的原始碼，開頭長這樣：<head> 裡有 title、樣式表、分析程式，但沒有 <meta name="viewport">。第 1 張單就出在這一行。

要懂它為什麼重要，得回到智慧型手機剛出現的時候。當時幾乎所有網站都是照桌機寬度（大約一千像素）設計的；如果手機瀏覽器老實用三百多像素的螢幕寬度去排，這些網站會擠成一團。所以手機瀏覽器採用的折衷是：先假裝自己的螢幕很寬（例如 980px），用這個虛擬寬度把整頁排好，再整頁縮小塞進手機螢幕。舊網站因此看得到全貌，代價是字小到要放大才看得清楚。

這個預設行為到今天都還在。豆留的頁面雖然寫了響應式 CSS，但沒有 viewport 那一行，手機瀏覽器就照舊用 980px 排版：寫給手機的 @media (max-width: 600px) 不會生效，因為瀏覽器認為自己有 980px 寬；排完再縮小，字就變得很小。加上這一行，等於告訴瀏覽器「這一頁已經為各種寬度設計好了，請直接用裝置的寬度排版」：

<meta name="viewport" content="width=device-width, initial-scale=1">

width=device-width 是用裝置寬度排版，initial-scale=1 是一開始不縮放。第 1 張單解了。

不要禁止縮放：有些範本會在 viewport 加上 user-scalable=no 或 maximum-scale=1，想避免使用者不小心放大。這會讓視力不好的人沒辦法放大頁面。WCAG 是 W3C 制定的網頁無障礙指引（第 5 課會細講），它的 1.4.4 要求文字能放大到 200%。MDN 也註明 iOS 10 起預設忽略這幾個設定，寫了只會傷到其他瀏覽器的使用者。

既然開頭的每一行都可能出事，就一次把它們看完。這是一份完整的文件骨架：

<!doctype html>
<html lang="zh-Hant">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>菜單｜豆留咖啡</title>
</head>
<body>…</body>
</html>

<!doctype html> 決定排版規則。它跟 viewport 的故事很像，也是為了舊網頁留下來的相容機制。早期瀏覽器各自有不合標準的排版方式，很多網頁就是照那些錯誤寫的；後來瀏覽器改成照標準排版時，為了不讓這些舊網頁壞掉，保留了一套舊規則，叫怪異模式（quirks mode），照標準的那套叫標準模式（standards mode）。瀏覽器用文件開頭有沒有 doctype 來判斷：有就是新網頁，用標準模式；沒有就當成 1990 年代的舊網頁，用怪異模式。怪異模式的差別藏在細節裡，例如表格不繼承字級、某些高度與行高的計算不同。版面「看起來差不多」但細節錯，很難查，所以第一行一定要有。

lang="zh-Hant" 宣告內容的語言。螢幕閱讀器靠它決定用哪種語言的發音唸內容，lang 錯了，中文可能被當成英文唸；瀏覽器選字型、決定怎麼斷行、要不要提示翻譯，也都會參考它。繁體中文寫 zh-Hant（或 zh-Hant-TW）。

<meta charset="utf-8"> 宣告編碼，放在 head 第一個。第一節說過，瀏覽器要先照編碼把位元組解成字元。伺服器通常會在 Content-Type 標頭寫明 charset；沒寫時，瀏覽器只能從文件裡找，再找不到就只能猜，中文可能變亂碼。規範要求這一行完整出現在文件的前 1024 bytes 內，所以把它放在 head 第一個，讓瀏覽器在讀任何中文之前就知道編碼。

<title> 是分頁、書籤、歷史紀錄、搜尋結果顯示的標題。沒寫時分頁會顯示網址，或腳手架預設的「Document」之類的字，使用者開了很多分頁時找不到；搜尋引擎也會自己湊一個標題。寫法是頁面主題在前、品牌在後，例如「菜單｜豆留咖啡」：分頁變窄、搜尋結果被截斷時，使用者先看到的是這一頁在講什麼，而不是每一頁都一樣的店名。

💡 實務上：新專案、新頁面先對一次開頭
用腳手架建立的 Vue 專案，index.html 已經有大部分的行，但 lang 和 title 是範本給的值，很容易就這樣上線。豆留的第 1 張單，是有人從舊的活動頁複製 head 時漏了 viewport。這幾行少了都不會報錯，只會在特定使用者身上出問題（手機使用者、螢幕閱讀器使用者、搜尋結果），所以要靠檢查而不是靠運氣：練習 1 就是一份會被測試逐行檢查的殘缺首頁，課末的「補充與查表」也整理了一張對照表。

開頭這幾行決定瀏覽器「怎麼讀、怎麼排」。head 裡其他的東西則會在解析途中觸發下載，其中有兩種會讓畫面停下來等，第 2 張單就卡在這裡。

首屏為什麼白了好幾秒？head 裡會讓畫面停下來的兩種東西

先定義一個詞：首屏是使用者打開頁面、還沒捲動時看到的第一個畫面。第 2 張單的症狀是：網路慢時，首屏要等好幾秒才出現。要找原因，得先分清楚 head 裡的東西各在做什麼。

<head> 放的是 metadata，也就是描述這份文件本身的資料，而不是要顯示給使用者看的內容。大部分 metadata 只是給機器讀的說明，例如給搜尋引擎的摘要、給 LINE 分享卡片的圖片，它們不影響畫面什麼時候出現（完整清單見課末「補充與查表」）。會讓畫面停下來的只有兩種：樣式表和 script。它們擋的東西不一樣，要分開看。

樣式表會阻擋渲染（render-blocking）。第一節說過，DOM 要和 CSSOM 合起來才畫得出畫面。如果瀏覽器不等 CSS 下載完就先畫，使用者會先看到一頁沒有樣式的純文字，等 CSS 到了再突然跳成正常的樣子。這個「沒有樣式的內容先閃一下」的現象有個名字，叫 FOUC（flash of unstyled content）。為了避免它，瀏覽器選擇等：<link rel="stylesheet"> 下載完之前，畫面不畫。但解析不停，DOM 照樣往下建。這種等待是刻意的，不要為了快把樣式表移走或刪掉；樣式表太大時該做的是縮小它，而不是移走它。

沒有任何屬性的 <script src> 會阻擋解析（parser-blocking）。這比阻擋渲染更嚴重：解析器停在這一行，等 script 下載完、執行完，才繼續往下讀 HTML。瀏覽器這麼保守，是因為 script 可能用 document.write 往文件裡插入新的 HTML，在它執行完之前，瀏覽器不知道後面的內容會變成什麼，只好等。

把這兩件事放回豆留首頁，第 2 張單就清楚了。行銷把分析程式貼在 head 最上面，沒加任何屬性。網路慢的時候，下載它要好幾秒，這段時間解析器停在 head，body 一個字都還沒讀到，DOM 裡沒有任何要顯示的內容，畫面只能是白的。電腦網路快，下載只要幾十毫秒，所以開發時完全感覺不到。

解法不是把 script 刪掉，而是告訴瀏覽器「這個 script 不需要你停下來等」。script 有三種寫法做得到這件事。比較它們之前先認識一個事件：DOMContentLoaded 是 HTML 整份解析完、DOM 建好時觸發的事件，不等圖片下載完。下面的時間軸把四種寫法並排：

  • defer：下載跟解析同時進行，下載完先等著，等 HTML 解析完成後才執行，而且照它們在文件裡出現的順序，全部執行完才觸發 DOMContentLoaded。適合大多數網站自己的程式：它們通常要操作 DOM，等 DOM 建好再執行剛好，順序也有保證。
  • async：下載也跟解析同時，但下載完就立刻執行，可能在解析中途插隊，多個 async script 誰先下載完誰先跑，順序不保證。適合不依賴別人、也沒人依賴它的程式，例如分析程式。
  • type="module"：ES 模組的 script，預設行為就跟 defer 一樣；再加上 async 就變成下載完立刻執行。

整理成一張表：

寫法下載什麼時候執行順序適合
<script src>擋住解析下載完立刻文件順序幾乎不需要；要放就放 body 最後
defer跟解析同時解析完成後、DOMContentLoaded 之前文件順序大多數網站程式
async跟解析同時下載完立刻（可能在解析中途）不保證不依賴別人、也沒人依賴它的，例如分析程式
type="module"跟解析同時預設等同 defer；加 async 就變成下載完立刻沒加 async 時照文件順序Vite 打包出來的就是這種

這也說明了為什麼豆留的 Vue 程式本身沒事：Vite 產生的 index.html 裡是 <script type="module" src="/assets/index-…js">，本來就不會擋解析。會出事的，幾乎都是後來手動貼進 head、沒加屬性的第三方程式碼。給分析程式加上 async 或 defer，它就不再擋住解析，body 照常被讀到、畫出來，第 2 張單解了。練習 1 會要你用 defer 修好同樣的問題；練習 4 則讓你自己模擬這幾種 script 的執行順序。

💡 實務上：第三方 script 是首屏變慢的常見來源
行銷貼來的追蹤碼、客服聊天視窗、廣告程式，往往直接要求「貼在 head 最上面」。貼之前先問三件事：它需要在畫面出現前執行嗎？有沒有加 async 或 defer？它掛了或很慢，頁面會不會跟著卡？大多數追蹤與聊天程式用 async 就夠，供應商的官方安裝說明通常也是這樣寫。貼完在 DevTools 的 Network 把網路調成 Slow 4G 重新整理，看首屏有沒有被它拖慢，不要只看自己電腦上感覺快不快。豆留這次就是少了這一步。

前三張單都跟「怎麼讀、怎麼排、要不要等」有關。剩下兩張不一樣：瀏覽器確實送出了請求，卻拿不到對的東西。先看請求的網址是怎麼算出來的。

同一個 src，為什麼從 /menu 進來就破圖？

第 4 張單的菜單照片，是店長從 CMS 貼進商品內容的，寫成 <img src="images/latte.jpg">。同一份內容，網址是 /menu/ 時正常，/menu 時破圖。要知道為什麼，得先知道瀏覽器怎麼把 src 算成完整網址。

href、src 裡的網址有四種寫法，差別在「從哪裡開始算」：

  • 絕對網址：https://cdn.example.com/app.js，寫什麼就是什麼，不用算。
  • 協定相對網址：//cdn.example.com/app.js，沿用目前頁面的協定（https 頁面就是 https）。現在網站幾乎都是 https，直接寫 https:// 比較清楚。
  • 根相對網址（root-relative URL）：/assets/logo.svg，開頭是斜線，從網站根目錄開始，跟目前在哪一頁無關。
  • 相對網址（relative URL）：images/latte.jpg、../stores/，從目前這一頁的位置開始算。基準是目前文件網址最後一個斜線之前的部分。

豆留的照片用的是最後一種。「最後一個斜線之前」這條規則來自網址最早的樣子：網址路徑模仿的是伺服器上的資料夾和檔案。/menu/ 結尾有斜線，代表「menu 這個資料夾」，相對網址就從資料夾裡面開始找；/menu 沒有斜線，代表「根目錄裡一個叫 menu 的檔案」，相對網址從這個檔案所在的資料夾，也就是根目錄開始找，menu 這一段直接被換掉。

瀏覽器內建的 new URL(href, 頁面網址) 用的就是同一套規則，可以拿來驗算瀏覽器實際會請求的網址。執行後看第一組三行，比較三個頁面網址算出的結果：

第二行就是第 4 張單：/menu 沒有結尾斜線，menu 被當成「檔名」而被取代，圖片跑到 /images/latte.jpg，那裡沒有檔案，就 404。這種問題在 Vue 專案特別容易出現：用 Vue Router 的網站，伺服器對 /menu 和 /menu/ 都回同一份 index.html，畫面一模一樣，使用者兩種網址都可能點到，但相對網址算出來的結果不同。

避開它有兩種做法，各有前提。一種是統一網址格式，例如目錄網址一律加結尾斜線，不帶斜線的自動轉過去；另一種是資源一律用根相對網址，不管在哪一頁都從根目錄算。但根相對網址假設網站部署在根目錄：從最後兩行可以看到，網站部署在 /shop/ 底下時，/assets/logo.svg 會跳出 /shop/，直接指到根目錄。這時 Vite 的 base 設定要跟著改成部署路徑，不然資源全部 404。

CMS 貼進來的除了圖片，也可能是指到外站的連結；判斷一個連結是不是同一個網站，要比的是 origin，不是只比網域，細節見課末「補充與查表」（練習 2 會用到）。

💡 實務上：測試環境正常、正式環境 404
典型情境是本機跑在 localhost:5173/，正式環境卻部署在 example.com/shop/，或像豆留這樣，從 CMS 貼進來的圖片用了相對網址。客服回報「圖片破圖」時，先在 Network 看瀏覽器實際請求的網址，再用 new URL() 推回是哪個 href 寫錯。上線前最好有一個跟正式環境同樣路徑結構的測試站，子路徑、結尾斜線的問題在那裡就會先爆出來。

網址算對了，請求也送到了伺服器。最後一張單的情況是：請求送到了，伺服器也回應了，瀏覽器卻拒絕使用。問題出在伺服器說「這是什麼檔案」。

部署後為什麼白畫面？伺服器說的檔案類型與快取

第 5 張單的症狀有兩個線索：只發生在部署之後，而且重新整理就好。前一個線索指向伺服器回了什麼，後一個指向快取。先看第一個。

伺服器每個回應都帶一個 Content-Type 標頭，裡面的值叫 MIME type，例如 text/html、text/css、text/javascript，用來告訴瀏覽器這是什麼檔案。瀏覽器照它處理，而不是看副檔名：網址本來就不一定有副檔名，有也只是網址裡的一段文字，不保證內容真的是那種檔案。標頭錯了，常見兩種結果：

  • CSS 回傳成 text/plain：標準模式下，瀏覽器直接忽略這份樣式表，頁面沒有樣式，Console 會出現 MIME type 的錯誤。
  • type="module" 的 script 回傳成 text/html：模組載入失敗，整個 app 白畫面。

第二種就是第 5 張單，但要先解釋 script 怎麼會被回成 HTML。Vue 專案通常是單頁應用（SPA）：整個網站只有一份 index.html，換頁是 Vue Router 在瀏覽器裡換元件。可是使用者直接打開或重新整理 /menu/ 時，伺服器上並沒有 menu 這個檔案；所以 SPA 的伺服器會設定「找不到的路徑一律回 index.html」，交給 Vue Router 決定顯示什麼。這個設定叫 SPA fallback。問題是它如果對所有路徑都生效，連找不到的 JS 檔也會拿到 index.html，標頭是 text/html，瀏覽器就拒絕把它當模組執行。

JS 檔為什麼會找不到？這要看快取。快取的細節在 Node 課第 15 課，這裡只需要一條實務規則：檔名帶內容 hash 的檔案（例如 index-3f9a1c.js）才能放心設長期快取。hash 是從檔案內容算出來的一串字，內容一改，hash 就變，檔名跟著變；所以同一個檔名的內容永遠不會變，瀏覽器快取多久都不會拿到舊內容。index.html 的檔名永遠不變，所以它本身不能長期快取，不然使用者拿不到新的檔名。

現在把線索串起來。部署新版後，打包出來的 JS 換了 hash 檔名，舊的 hash 檔被刪掉。這裡會牽涉到 CDN：它是放在使用者附近、替網站快取檔案的伺服器群，部署之後它手上的檔案不一定立刻更新。如果某個使用者的瀏覽器或 CDN 還留著舊的 index.html，它就會去請求舊檔名的 JS；那個檔已經不在了，SPA fallback 回了 index.html，標頭是 text/html，模組載入失敗，白畫面。重新整理時，瀏覽器重新確認 index.html，拿到新版，指向新檔名，一切正常，所以「重新整理就好」。

💡 實務上：「更新後白畫面」多半是快取和部署順序
豆留這張單要修的不是 Vue 程式碼。資深工程師會確認三件事：index.html 不做長期快取；部署時舊的 hash 檔先保留一段時間，讓還拿著舊 index.html 的人也載得到；SPA fallback 只套用在頁面路徑，/assets/ 底下找不到就老實回 404，至少錯誤訊息會指向真正的原因。這是部署設定，要跟維運一起對齊，不是前端程式碼改得掉的。

五張單都解完了。回頭看，它們卡在地圖上的三步：建出 DOM（第 3 張被解析器修正、第 2 張解析中途被 script 擋住）、排版（第 1 張）、發出更多請求（第 4 張網址算錯、第 5 張回應的類型錯）；之後遇到新的症狀，也可以先問「它卡在哪一步」，再去 DevTools 對應的面板找證據。

origin：判斷是不是同一個網站（練習 2 用）：origin 是網址的 protocol、host、port 三者合起來。例如 https://brew.example.tw/menu/ 的 origin 是 https://brew.example.tw，也就是 https 加 brew.example.tw 加 https 預設的 443 port。判斷「這個連結是不是同一個網站」時，三者要全部相同才算。只比 hostname 會出錯：http://brew.example.tw 和 https://brew.example.tw 的 hostname 一樣，但協定不同、預設 port 也不同（80 和 443），是兩個 origin；瀏覽器的很多安全限制以 origin 為界，例如 JavaScript 能不能讀另一個網址的回應、localStorage 這類儲存空間歸誰，把它們當成同站會判斷錯。用 new URL(href, 頁面網址).origin 就能取得 origin 直接比較。mailto:、tel: 這類網址沒有 origin。origin 跟 site 的差別在認證課第 5 課。

script 與安全：XSS 與 CSP 跟 script 有關，但在認證課第 7 課，這裡不重複。

排版與繪製的細節：DOM、CSSOM 之後的樣式計算、排版、繪製、合成，在第 19 課。

練習

練習 1：咖啡店首頁的文件殘缺不全。把它補完整：加上 <!doctype html>、lang（繁體中文）、<meta charset="utf-8">（要是 head 的第一個元素）、可以縮放的 viewport、有意義的 title（頁面主題在前、品牌「豆留咖啡」在後，8～40 個字）；把 head 裡擋住解析的分析程式改成 defer。樣式表和分析程式都要留在 head，<body> 的內容不要動。這題編輯的是整份文件。

練習 2：寫 resolveHref(pageUrl, href)，回傳瀏覽器實際會請求的絕對網址；再寫 isSameOrigin(pageUrl, href)，判斷 href 指到的網址跟頁面是不是同一個 origin（protocol、host、port 三者都相同）。mailto:、tel: 這類網址沒有 origin，回傳 false，不要丟錯。origin 跟 site 不一樣，site 在認證課第 5 課。

練習 3：這段 HTML 在瀏覽器裡建出的 DOM 跟原始碼不一樣（<p> 裡放 <div>、<table> 直接放 <tr>、連結包連結）。改寫成原始碼與 DOM 一致的版本：段落裡只放行內元素、表格補上 <thead> 與 <tbody>、巢狀連結拆成兩個並排的連結；畫面上的文字與三個連結都不變。每個元素都要寫結束標籤（省略 </p> 是合法的 HTML，但這題要逐一比對原始碼與 DOM）。

練習 4：模擬 head 裡外部 script 的執行順序。寫 executionOrder(scripts, parseEnd) 回傳 name 的陣列。簡化模型：classic 在 foundAt 執行（測試資料保證它被找到時已經下載完）；async 與 module-async 在 loadedAt 執行；defer 與 module 在解析完成後依文件順序執行，每一個的執行時間是 max(parseEnd, 自己的 loadedAt, 前一個 defer／module 的執行時間)。全部依執行時間排序，時間相同時依文件順序。

練習 5：DevTools Elements 面板裡看到 <tbody>，原始碼裡卻沒有，最可能的原因是？

✓ b：HTML 解析器會修正與補齊結構，表格列一定會被放進 <tbody>。Elements 面板顯示的是 DOM，要看伺服器給的原始碼用「檢視網頁原始碼」。a 錯：DevTools 忠實顯示 DOM。c 錯：純 HTML 頁面也會這樣。d 錯：CSS 不會新增元素。

練習 6：頁面網址是 https://brew.example.tw/menu（沒有結尾斜線），<img src="latte.jpg"> 會請求哪個網址？

✓ b：相對網址以最後一個斜線之前的路徑為基準，menu 被當成檔名而被取代。a 是頁面網址有結尾斜線（/menu/）時的結果。c 錯：解析不是字串拼接。d 錯：網址在瀏覽器端就算好了，伺服器只會收到算好的網址。

練習 7：在 head 放 <script src="/analytics.js" defer>，它什麼時候執行？

✓ b：defer 不擋解析，下載完先等，解析完成後依文件順序執行，執行完才觸發 DOMContentLoaded。a 是 async 的行為。c 錯：load 要等圖片等所有資源，defer 早得多。d 錯：瀏覽器沒有這種內建行為，那是自己寫的延遲載入。

常見錯誤

  • 伺服器輸出的 HTML 把富文字內容放進 <p>：內容一帶 <ul>、<div>，p 就被解析器拆開，CSS 選不到，SSR 還會 hydration mismatch。不受你控制的內容用 <div> 包。
  • 照 DevTools 看到的結構寫選擇器或測試：DOM 是修正後的結果，伺服器回傳的 HTML 可能不同；SEO 與 SSR 的問題要看原始回應。
  • viewport 加 user-scalable=no：視力不好的使用者沒辦法放大，違反 WCAG 1.4.4；iOS Safari 也會忽略它。
  • lang 寫錯或不寫：螢幕閱讀器用錯語言發音，中文字型的選擇也可能不如預期。繁體中文寫 zh-Hant 或 zh-Hant-TW。
  • 在 head 貼第三方 script 不加屬性：它下載多久，首屏就晚多久；分析程式用 async 或 defer。
  • 部署到子路徑後資源 404：根相對網址 /assets/… 假設網站在根目錄，打包工具的 base 設定要跟部署路徑一致。
  • SPA fallback 連 /assets/ 也回 index.html：找不到的 JS 拿到 text/html，症狀變成白畫面而不是 404，更難查。

小結

  • 瀏覽器邊下載邊由上往下解析 HTML，建出 DOM；CSS、JavaScript 操作的是 DOM，不是原始碼。DOM 和 CSSOM 合起來才排版、繪製。遇到症狀先問「卡在哪一步」。
  • 結構寫錯時解析器會照規範修正，DOM 就跟原始碼不同（商品說明跑版）。Elements 面板看 DOM，「檢視網頁原始碼」看原始回應。
  • 文件開頭每一行都有用途：doctype 決定標準模式、lang 影響發音與字型、charset 放 head 第一個、viewport 讓手機用裝置寬度（手機字很小）、title 主題在前品牌在後。
  • head 裡的 CSS 阻擋渲染；沒加屬性的 script 阻擋解析（首屏白好幾秒）。defer 與 module 解析完依順序執行，async 下載完就執行。
  • 相對網址以最後一個斜線之前為基準：/menu 和 /menu/ 結果不同（菜單破圖）。用 new URL(href, base) 驗算。
  • 瀏覽器照 Content-Type 處理資源；檔名帶 hash 的檔案才能長期快取，index.html 不行，SPA fallback 不要套到 /assets/（部署後白畫面）。
