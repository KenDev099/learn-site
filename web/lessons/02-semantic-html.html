階段 1：HTML 與可操作的網頁 · 第 2 課

語意化 HTML：標題、landmark、連結、按鈕與列表

豆留咖啡的客服收到一封信。一位視障的老客人說，網站「什麼都按不到」：他用螢幕閱讀器聽首頁，聽不出哪裡是選單、哪裡是主要內容；改用鍵盤按 Tab 一路往下跳，焦點就是停不到「加入購物車」；最新消息頁有三個「更多」，他分不出哪個是哪一則。可是同事打開網站一看，畫面完全正常，每個按鈕用滑鼠都點得到。

問題出在整個網站幾乎都用 <div> 寫。元素「長什麼樣子」可以交給 CSS，但元素「代表什麼」只能靠 HTML 元素本身說清楚；div 什麼都不代表，所以畫面正常，意思卻全丟了。這一課從首頁開始，照客人抱怨的順序，把這個網站一頁一頁修到鍵盤和螢幕閱讀器都用得了。課末的三個練習就是這三個頁面：首頁、商品卡與表單、最新消息頁。

這課的路線：
  1. 全用 div 的首頁到底哪裡壞了：瀏覽器從 HTML 產生一份給輔助科技讀的資料，div 在那份資料裡什麼都不是（開場問題的最小答案）。
  2. landmark 與標題階層：讓客人直接跳到主要內容，再依標題找到想看的那一段。
  3. 連結還是按鈕、按鈕的 type：「加入購物車」為什麼按不下去，換成 button 之後表單為什麼一按就送出。
  4. 連結文字：三個「更多」怎麼寫，單獨唸出來也分得出是哪一則。
  5. 剩下的 div：營業時間和選單該換成清單，哪些 div 留著才是對的。
這課會用到：
  • 第 1 課的 DOM：瀏覽器把 HTML 解析成記憶體裡的樹，下面講的「無障礙樹」就是從 DOM 產生的。

全用 div 的首頁，到底哪裡壞了？

先把問題縮到最小。下面是首頁頁首一角的兩種寫法，加上適當的 CSS 之後，畫面可以一模一樣：

<!-- 寫法 A：div 湯 -->
<div class="header">
  <div class="nav"><span onclick="go('/menu/')">菜單</span></div>
</div>
<div class="title">每天現烘的手沖咖啡</div>
<div class="btn" onclick="addToCart()">加入購物車</div>

<!-- 寫法 B：語意化 -->
<header>
  <nav aria-label="主選單"><a href="/menu/">菜單</a></nav>
</header>
<h1>每天現烘的手沖咖啡</h1>
<button type="button">加入購物車</button>

寫法 A 就是豆留咖啡現在的樣子，同事看到的畫面是對的。差別在畫面以外：寫法 B 的每個元素都說出了自己是什麼，寫法 A 沒有。這裡說的「元素代表什麼意思，而不是長什麼樣子」，就叫語意（semantics）。要看懂語意為什麼會讓客人用不了網站，得先知道客人是用什麼在「看」網頁。

幫身心障礙者使用電腦的軟硬體，統稱輔助科技（assistive technology），例如螢幕閱讀器、語音控制、點字顯示器。其中最常見的是螢幕閱讀器（screen reader）：把畫面內容唸出來或轉成點字的軟體，例如 macOS／iOS 的 VoiceOver、Windows 的 NVDA、Android 的 TalkBack。寫信來的客人用的就是它。

螢幕閱讀器不看像素。它沒辦法從「這行字比較大、放在最上面」推論出這是標題，也沒辦法從「這塊有圓角和底色」推論出這是按鈕。它讀的是瀏覽器另外準備的一份資料：瀏覽器從 DOM 再產生一棵無障礙樹（accessibility tree），交給輔助科技。無障礙樹的每個節點有三樣資訊：

  • 角色（role）：這是什麼，例如 button、link、heading、navigation。
  • 可及名稱（accessible name）：輔助科技唸出來的名字。按鈕的名稱通常來自按鈕裡的文字，圖片的名稱來自 alt，也可以用 aria-label 屬性直接指定。
  • 狀態：例如勾選了沒有、展開了沒有（第 5 課）。

上面提到的 aria-label 屬於 ARIA。ARIA 是 W3C 定義的一組 HTML 屬性，包括 role 和所有 aria- 開頭的屬性，用途是補充或改寫無障礙樹的資訊。這課只會用到其中幾個（aria-label、aria-labelledby、少數 role），第 5 課會完整講它能做什麼、不該做什麼。

角色大多不用自己寫：每個 HTML 元素都帶著一個隱含角色，<button> 是 button、有 href 的 <a> 是 link、<h1> 是 heading。<div> 和 <span> 的角色是 generic，意思是「沒有意義的容器」，螢幕閱讀器不會為它唸任何角色。所以上面兩種寫法，VoiceOver 使用者聽到的大致是：

元素寫法 A 的角色／名稱寫法 B 的角色／名稱
頁首沒有角色（generic），不能跳過去banner（頁首 landmark）
選單只是文字「菜單」，不是連結，Tab 到不了navigation「主選單」裡的 link「菜單」
主標題一般文字heading 第 1 級「每天現烘的手沖咖啡」
加入購物車一般文字，Tab 到不了，Enter 沒反應button「加入購物車」

這張表就是客服信的最小答案。寫法 A 的「加入購物車」在無障礙樹裡只是一段文字：不在 Tab 的順序裡，按 Enter 也沒反應，螢幕閱讀器也不會說它是按鈕。滑鼠點得到，只是因為 click 事件綁在那個 div 上，跟它是不是按鈕無關。修法的方向也清楚了：把每個元素換成本來就帶著正確角色和行為的 HTML 元素，瀏覽器就會自動把無障礙樹填對，不用另外寫程式。

修好之後，受益的不只是這位客人：

  1. 輔助科技的使用者：螢幕閱讀器可以列出頁面所有標題、landmark、連結，直接跳過去；鍵盤使用者能用 Tab 到達每個可以操作的元素。
  2. 搜尋引擎：標題與連結是判斷頁面主題、找到其他頁面的線索。Google 只把帶 href 的 <a> 當成連結（第 22、25 課）。
  3. 維護程式的人：看到 <nav>、<button> 就知道它的用途。第 27 課會教端對端測試（E2E 測試），也就是用程式操作真的瀏覽器，像使用者一樣點擊、輸入；語意寫對了，測試就能用角色找元素，例如 Playwright 的 getByRole('button', { name: '加入購物車' })。
自己看無障礙樹：Chrome DevTools 的 Elements 面板選一個元素，右側的 Accessibility 分頁會列出它的 Role 與 Name。這課每一題的測試做的事情一樣：讀出元素的角色與名稱來判斷。

方向確定是「把元素換對」，接下來的問題是從哪裡換起。客人抱怨的第一件事是聽不出哪裡是選單、哪裡是主要內容，那是頁面最外層的結構，就從這裡開始。

怎麼讓客人直接跳到主要內容？landmark

看得到畫面的人，一眼就知道最上面那條是頁首、中間是內容。螢幕閱讀器的使用者沒有這一眼：如果頁面沒有任何結構標記，他只能從第一個字開始聽，品牌、選單的每個項目、搜尋框……每換一頁就重聽一次，才聽到他要的內容。

landmark（地標）就是為了解決這件事：它把頁面的大區塊標出來，螢幕閱讀器會把它們收成一份「landmark 清單」（VoiceOver 在轉輪裡，按 Control＋Option＋U 打開），使用者可以直接跳到主要內容。產生 landmark 不用寫 ARIA，用對應的 HTML 元素就好，它們的隱含角色就是 landmark。下面這張表的「條件」欄是查表用，不用背；第一次讀先記住兩件事：header、footer 只有在頁面最外層才代表整站的頁首和頁尾，section 要有名稱才算數。

元素隱含角色條件放什麼
<header>banner不在 article、aside、main、nav、section 裡面；在裡面時只是 generic品牌、主選單、搜尋
<nav>navigation一律主要的導覽連結群組
<main>main一頁只能有一個（顯示中的）這一頁獨有的主要內容
<aside>complementary直接在 body 或 main 底下時；放在 article、aside、nav、section 裡時要有可及名稱才算，否則是 generic跟主要內容相關但可以獨立的補充，例如側欄
<section>region有可及名稱時才是；沒有名稱就是 generic，跟 div 一樣值得列進 landmark 清單的一區
<footer>contentinfo條件跟 header 相同版權、聯絡方式、頁尾連結
<article>article（不是 landmark）一律可以單獨拿出去也成立的內容：一則消息、一張商品卡

header 和 footer 為什麼有條件？想想最新消息頁的一則消息：<article> 裡也可以有自己的 <header>，放那則消息的標題和日期。那是這篇文章的標頭，不是整個網站的頁首；如果它也算 banner，landmark 清單裡就會冒出好幾個「頁首」。規定 HTML 元素怎麼對應到無障礙樹的規範叫 HTML-AAM，它就是這樣規定的：放在 article、aside、main、nav、section 裡的 header、footer 只是 generic。

這張圖就是豆留咖啡首頁修好之後的樣子。要把它做對，照下面四條規則：

  • 一頁一個 <main>。客人按一下就要跳到「這一頁的主要內容」，有兩個 main 就不知道該跳哪個。Vue 的 SPA 通常在 App.vue 的版型放一個 <main>，<RouterView /> 放在它裡面，各頁元件就不要再寫 main。
  • 同一種 landmark 出現兩次以上，每個都要有不同的名稱。首頁的主選單和頁尾連結都是 nav，就用 aria-label="主選單"、aria-label="頁尾連結" 區分，不然 landmark 清單裡會出現兩個一模一樣的「navigation」。名稱裡不用再寫「導覽」，螢幕閱讀器會自己唸出角色。
  • section 要取名才有用。沒有名稱的 section 不會進 landmark 清單。區塊已經有可見標題時，用 aria-labelledby 指向標題的 id，名稱就跟畫面一致： 
    <section aria-labelledby="store-title">
  <h2 id="store-title">門市資訊</h2>
  …
</section>
  • 優先用原生元素，不用 role。<div role="navigation"> 也能產生 landmark，但這是 ARIA 的第一條規則：有原生元素可以用，就用原生元素（第 5 課會完整講 ARIA 的界線）。
💡 實務上：landmark 在版型元件裡定一次，各頁不用管
團隊專案裡，header、nav、main、footer 通常只寫在共用的版型元件（Vue 的 App.vue 或 layout 元件），各頁只負責 main 裡面的內容。常見的坑是新頁面複製舊頁面時連 <main> 一起貼過來，或彈出視窗、後台另一套版型又包了一層 main。資深的人 review 新版型時會打開螢幕閱讀器的 landmark 清單或 DevTools 的 Accessibility 面板看一眼：main 只有一個、兩個 nav 名稱不同、該出現的 section 都在清單裡（沒取名的 section 不會列出來，等於沒用）。這一步只要幾十秒，但版型錯了會影響整站每一頁。

有了 landmark，客人可以一步跳進 main。但 main 裡有主視覺、本週推薦、門市資訊，他想直接聽門市地址，要怎麼在 main 裡面找到那一段？

進了 main，怎麼找到想看的那一段？標題階層

靠的是下一層結構：標題。螢幕閱讀器使用者最常用的瀏覽方式是「依標題跳」：NVDA 按 H 跳到下一個標題，VoiceOver 用轉輪列出所有標題。使用者先聽一遍標題清單，再決定跳去哪裡，所以標題扮演的是這一頁的目錄。寫法 A 的首頁標題全是 div，這份目錄是空的，客人只能從 main 的第一個字一路聽下去。

目錄要好用，層次要對。首頁每一區只有一兩個標題，看不出「要不要每個品項都給標題」這種取捨；菜單頁有幾十個品項，規則和判斷都看得更清楚，所以先拿菜單頁當例子，它的大綱是這樣：

h1 菜單
  h2 咖啡
    h3 美式咖啡
    h3 拿鐵
  h2 甜點
    h3 可頌
    h3 起司蛋糕

這份大綱靠三條規則維持：

  • 一頁一個 h1，寫這一頁的主題。網站品牌在每一頁都一樣，通常不當 h1（品牌連結放在 header 裡就好）。HTML 規範沒有禁止多個 h1，但一個 h1 讓大綱最清楚，也是多數團隊的慣例。
  • 不跳級：h2 底下是 h3，不要直接 h4。用標題清單的人看到 h2 之後接 h4，會以為漏了一段。
  • 級數表示結構，字的大小交給 CSS。設計稿上品項名稱比較小，就給 h3 一個 class 調字級，不要因為「h4 預設比較小」就用 h4。反過來，只是想讓字變大的一行文字，不要用 h 元素。

每個品項要不要給 h3？要看使用者會不會想直接跳到某個品項。菜單有 30 個品項時，每個都是 h3 讓標題清單變很長；只在「咖啡」「甜點」用 h2、品項放在清單裡也合理。判斷方式：打開標題清單，看它像不像一份好用的目錄。

回到首頁：主視覺的「每天現烘的手沖咖啡」是唯一的 h1，「本週推薦」「門市資訊」是 h2，兩個推薦品項是 h3。上一節 section 用 aria-labelledby 指向的，正好就是這兩個 h2：同一行標題文字，既是目錄裡的一項，也是 landmark 的名稱。練習 1 要做的就是這兩節的內容。

到這裡，客人可以靠 landmark 和標題在首頁找到想看的區塊。接著他到商品頁看拿鐵的商品卡（練習 2 用的就是這張卡），按 Tab 想停在「加入購物車」上，焦點卻直接跳過去了。

「加入購物車」為什麼按不下去？連結還是按鈕

商品卡上的「加入購物車」「查看完整菜單」都是 <div onclick>。第一節說過，它們在無障礙樹裡只是文字。動手換之前要先決定：該換成連結，還是按鈕？這是前端最常寫錯的語意，判斷只看一件事：按下去之後，網址會不會變。

按下去會……用咖啡店的例子
前往另一頁、另一個網址、頁面裡的某個位置（#id）、下載檔案<a href>查看完整菜單、門市地圖、回到頁首
在原地執行動作：送出、開關、加入、刪除、播放<button>加入購物車、展開甜度說明、開啟選單、送出訂閱

所以「查看完整菜單」是連結，「加入購物車」是按鈕。這不只是名稱上的分類，兩者在瀏覽器裡的行為完全不同：連結可以按右鍵「在新分頁開啟」、可以複製網址、按 Enter 觸發；按鈕按 Enter 和 Space 都會觸發，螢幕閱讀器唸成「按鈕」，使用者預期它不會換頁。用錯了，使用者的預期就錯了。在 Vue 裡，<RouterLink to="/menu/"> 會輸出 <a href="/menu/">，所以換頁用 RouterLink；在 <div @click="router.push('/menu/')"> 上換頁，就失去了上面所有行為。

決定用按鈕之後，再看清楚「加入購物車」原本的 <div onclick> 跟 <button> 比，到底少了什麼。少了四件事：

缺的東西後果用 div 要自己補
焦點Tab 跳過它，鍵盤使用者到不了tabindex="0"
鍵盤操作Enter、Space 沒反應監聽 keydown，自己判斷按鍵、處理 Space 捲動頁面的預設行為
角色螢幕閱讀器唸成一般文字role="button"
名稱與狀態停用時沒有 disabled 的語意，表單也不會因它送出aria-disabled、自己擋點擊…

第一列就是客人遇到的事：焦點跳過它。補齊這四件事要寫十幾行，還很容易漏；<button type="button"> 一行就全部有了。常見的半套修法是只加 role="button"：那只補了角色，螢幕閱讀器會唸「按鈕」，但 Tab 還是到不了、Enter 還是沒反應，這是練習 2 要擋下的寫法。

換成 button 之後，鍵盤使用者還要能看到自己停在哪裡。他們靠的是焦點外框（focus ring）：Tab 到 button 或連結時，瀏覽器會在它外圍畫一圈 outline。不要為了「點擊時有框不好看」寫 outline: none，那等於讓鍵盤使用者看不到游標；外框的樣式可以改，但不能拿掉（第 5 課會教怎麼用 :focus-visible 只在鍵盤操作時顯示）。

另一邊，「查看完整菜單」換成連結時也有一個陷阱：

<a> 一定要有 href：沒有 href 的 a 不是連結（角色是 generic），不在 Tab 順序裡。<a href="#"> 當按鈕也不行：點了會把 # 加到網址並捲回頁首，螢幕閱讀器還是唸成連結。
💡 實務上：「可以點的東西」是 code review 常被退回的語意問題
最常見的場景是後台訂單列表：整列 <tr @click> 跳到訂單明細，結果店員沒辦法按右鍵在新分頁開好幾筆訂單來比對。做法是在列裡放一個真正的 <a href>（例如訂單編號），需要整列可點時再用 CSS 把連結的點擊範圍撐滿。設計師要「長得像按鈕的連結」或「長得像連結的按鈕」都可以，元素照行為選、外觀交給 CSS。另一個實際好處：語意寫對，E2E 測試直接用 getByRole('link', { name: … }) 就找得到，不用為了測試另外加 class 或 id。

商品卡修好了，「加入購物車」終於按得到。同一招用到商品卡裡的甜度表單上，卻出了新問題：這個選甜度的小表單裡，「甜度說明」換成 button 之後，客人一按，表單就送出去了。

換成 button 之後，表單為什麼一按就送出？按鈕的 type

原因在 button 的預設值。<button> 放在 <form> 裡、沒寫 type 時，預設是 type="submit"：按下去會送出它所在的表單。「甜度說明」本來只是要切換一段說明文字，卻因為沒寫 type 變成了送出鍵：客人想看說明，甜度還沒選好、還沒按加入購物車，這個表單就先送出去了。type 有三個值：

type行為什麼時候用
submit（form 裡的預設值）送出所屬的表單表單的送出按鈕。寫出來比較清楚
button沒有預設行為，只觸發你寫的事件處理其他所有按鈕。不在 form 裡也建議寫，元件之後被放進 form 時才不會出事
reset把表單欄位清回初始值幾乎不用，誤按會清掉使用者填好的資料

所以「甜度說明」寫 type="button"。商品卡下方另一個訂閱電子報表單（有 email 欄位的那個），它的「訂閱電子報」按鈕才是真的要送出，所以寫 type="submit"。「不在 form 裡也建議寫」這一條，在元件化的專案裡特別重要：一個今天放在商品卡上的按鈕元件，下個月可能被同事放進結帳表單，沒寫 type 的話它就悄悄變成送出鍵。Vue 元件庫的 Button 元件常常預設 type="button"，但自己寫 <button> 時沒有這層保護。第 4 課的表單會再用到這條規則。練習 2 就是這張商品卡和這個表單。

商品卡和表單的按鈕都修好了。客人的最後一個抱怨在最新消息頁：三個「更多」，他分不出哪個是哪一則。

三個「更多」怎麼分得出來？連結文字

看畫面的人分得出來，因為每個「更多」緊接在消息標題後面，眼睛會自動把它們連起來。螢幕閱讀器使用者卻常用另一種方式找連結：叫出「連結清單」，一次列出頁面上所有連結，跟標題清單一樣挑一個直接跳過去。清單裡只剩每個連結的名稱，沒有前後文，於是出現三個一模一樣的「更多」。所以連結文字要單獨唸出來也看得懂。做法有兩種：

<!-- 1. 直接改可見文字 -->
<a href="/news/osmanthus-latte/">閱讀桂花拿鐵的完整消息</a>

<!-- 2. 設計稿要保留「更多」：可見文字在前，補充文字視覺隱藏 -->
<a href="/news/osmanthus-latte/">更多<span class="visually-hidden">：秋季限定桂花拿鐵</span></a>

第一種最直接，所有人看到的、聽到的都一樣。設計稿堅持要「更多」時用第二種：.visually-hidden 是常見的工具 class，用 position: absolute、1px 大小、clip-path: inset(50%) 把文字藏起來，畫面上看不到，但還在無障礙樹裡。於是看畫面的人看到「更多」，連結清單唸出「更多：秋季限定桂花拿鐵」。

藏文字不能用 display: none 或 hidden 屬性。這兩種做法會把元素從無障礙樹整個移除，螢幕閱讀器也讀不到，名稱又變回「更多」。

那為什麼不直接用 aria-label 換掉名稱？因為它會把可見文字整個蓋掉。<a aria-label="桂花拿鐵消息">更多</a> 的名稱裡沒有「更多」，用語音控制的使用者看著畫面說「點更多」時，叫不到它。語音控制（例如 macOS／iOS 內建的「語音控制」）讓使用者用說話操作：他唸出畫面上看到的文字，軟體再拿這段話去比對無障礙樹裡每個元素的名稱，名稱裡沒有這段字，就找不到。WCAG 是 W3C 的網頁內容無障礙指引，第 5 課會完整介紹；它的 2.5.3 Label in Name（A 級，最基本、一定要做到的等級，第 5 課細講）就是在規定這件事：名稱要包含畫面上看得到的文字，最好放在開頭。第二種做法的名稱「更多：秋季限定桂花拿鐵」以可見文字開頭，符合這條。

連結要不要在新分頁開啟（target="_blank"）是另一個常見問題，細節見課末「補充與查表」。

連結清單整理好了，但最新消息頁還有兩個地方，在畫面上看起來是清單，在無障礙樹裡卻不是：營業時間是用 <br> 一行一行排出來的，主選單的連結只是一串並排的 a。

剩下的 div：哪些該換成清單，哪些就留著？

清單：ul、ol、dl

清單元素會讓螢幕閱讀器先唸出「清單，3 個項目」，使用者一開始就知道有幾項，不想聽也可以跳過整個清單。用 <br> 換行排出來的營業時間，對螢幕閱讀器只是一長串文字，聽不出有幾天、哪個時間對應哪一天。HTML 有三種清單，照內容的形狀選：

元素用在咖啡店的例子
<ul> ＋ <li>順序不重要的清單導覽連結、商品卡列表、過敏原
<ol> ＋ <li>順序有意義手沖步驟、點餐流程、排行榜
<dl> ＋ <dt>／<dd>名詞 → 說明的成對資料營業時間（週一 → 07:30–18:00）、商品規格（產地 → 衣索比亞）

主選單是幾個順序不重要的連結，用 ul；營業時間是「星期 → 時段」的成對資料，用 dl：

<nav aria-label="主選單">
  <ul class="nav-links">
    <li><a href="/menu/">菜單</a></li>
    <li><a href="/stores/">門市</a></li>
  </ul>
</nav>

<dl>
  <dt>週一</dt><dd>07:30–18:00</dd>
  <dt>週日</dt><dd>09:00–17:00</dd>
</dl>

結構上有一條限制：ul、ol 的子元素只能是 li；dl 裡是 dt／dd，或用 div 把每一組包起來（方便排版）。練習 3 就是把最新消息頁的三個問題（「更多」、營業時間、主選單）一起修好。

去掉項目符號時，Safari 有一個差異要注意：

Safari 與 list-style: none：導覽列通常會用 CSS 去掉項目符號。Safari（WebKit）對 list-style: none 的 ul／ol 不回報 list 角色（放在 <nav> 裡的除外），WebKit 說明這是刻意的設計，不是 bug。所以在 Chrome 測沒問題，VoiceOver 使用者卻聽不到「清單」。重要的清單（不在 nav 裡的商品列表、步驟）在 ul 上加 role="list" 把角色補回來，並用 VoiceOver 實測一次。反過來，不要為了「去掉清單樣式」加 role="presentation"，那會連 Chrome 的清單語意也拿掉。豆留咖啡的主選單放在 nav 裡，不受影響；商品列表這類不在 nav 裡的清單，就要加 role="list"。

什麼時候 div 才是對的

修到這裡，網站裡還剩很多 div。語意化不是把所有 div 換掉。<div>（區塊）和 <span>（行內）是沒有語意的容器，用在純粹為了排版或套樣式的地方：Flex／Grid 的外層、卡片內部的分組、要換顏色的一段字。它們在無障礙樹裡是 generic，不會多唸任何東西，這正是排版容器該有的樣子。首頁的 div.hero 就是這樣：它只是把主視覺的標題和說明包在一起排版，不需要 landmark，留著 div 是對的。

遇到一塊內容不知道該用什麼時，照這個順序問：

  1. 這塊內容有沒有對應的元素？標題、段落、清單、連結、按鈕、表格、表單欄位（第 3、4 課），有就用它。
  2. 是不是頁面的大區塊，使用者會想直接跳過去？是就用 landmark 元素；section 記得取名。
  3. 可以單獨拿出去也成立嗎（一則消息、一張商品卡）？用 article。
  4. 都不是：用 div 或 span。

常見的過度修正是到處加 <section>。沒有名稱的 section 跟 div 一樣，只是多了一層看起來有意義、其實沒有的標籤。

💡 實務上：接手舊專案的 div 湯，先修會擋住人的地方
不用一次把整個網站重寫，照影響程度排順序：先修可以點卻 Tab 不到的元素（div 按鈕、沒有 href 的 a），因為那是鍵盤使用者完全無法下單；再補 main 與 nav 這些 landmark，最後才整理標題階層。修的時候順手改共用元件（Button、Card、版型），一次就影響所有頁面，比逐頁修划算。ESLint 是自動檢查程式碼寫法的工具，存檔或送 PR 時就會提醒；在它加上無障礙規則（例如 Vue 的 eslint-plugin-vuejs-accessibility），新寫的程式碼就不會再犯同樣的錯；但工具只抓得到一部分，上線前還是要用鍵盤實際操作一次。

下面三個練習依序是首頁、商品卡與表單、最新消息頁，修完就能回信給那位客人了。

補充與查表

target="_blank"：在新分頁開啟

以前要加 rel="noopener" 避免新頁面透過 window.opener 改寫原頁面；現在 HTML 規範已經讓 target="_blank" 預設有 noopener 的行為，現代瀏覽器都照做。比較需要考慮的是使用者體驗：不預期的新分頁會讓人找不到「上一頁」，站內連結不要開新分頁；真的要開時，在連結文字裡說明（例如「付款說明（另開新分頁）」）。

練習

練習 1：咖啡店首頁全部用 <div> 寫成。只改 HTML，把它換成語意化的結構：頁首（品牌與主選單）、主要內容（主視覺、本週推薦、門市資訊）、頁尾（頁尾連結與版權）。要求：landmark 用原生元素；兩個 <nav> 有不同的名稱；主視覺的標題是唯一的 h1，「本週推薦」「門市資訊」是 h2，兩個推薦品項是 h3；「本週推薦」「門市資訊」兩區是用 aria-labelledby 取名的 <section>。CSS 用 class 選擇且是唯讀的，class 要留在原本的元素上；文字不要增刪。

練習 2：這張商品卡和訂閱表單的四個「按鈕」都是 <div onclick>，鍵盤用不了。把它們換成正確的元素：「加入購物車」是原地執行的動作；「查看完整菜單」前往 /menu/；「訂閱電子報」送出它所在的表單；「甜度說明」在表單裡，但只是切換說明文字，不能送出表單。class="btn" 保留，CSS 已經把 a 和 button 調成一樣的外觀。預覽不會執行 JavaScript，onclick 留著或刪掉都可以，判分只看元素對不對。

練習 3：最新消息頁有三個問題，只改 HTML 修好它們：（1）三個連結都叫「更多」，改成單獨唸出來也知道是哪一則的名稱，可見文字可以保留「更多」，再用 <span class="visually-hidden"> 補上消息標題（唯讀 CSS 裡已經有這個 class）；名稱要包含畫面上看得到的文字，60 個字以內。（2）營業時間改成 <dl>，週一到週日各一組 <dt>／<dd>。（3）主選單改成 <ul class="nav-links"> > <li> > <a>，保有清單語意。

練習 4：<div onclick="order()">點餐</div> 跟 <button type="button">點餐</button> 比，少了什麼？

✓ b：原生 button 直接提供焦點、鍵盤操作、角色與名稱。div 加 tabindex="0" 和 role="button" 之後，Enter／Space 還是要自己寫。a 錯：樣式是最不重要的差別。c 錯：螢幕閱讀器讀的是無障礙樹，onclick 不會產生角色。d 錯：受影響最大的是鍵盤與螢幕閱讀器使用者。

練習 5：設計稿上品項名稱的字比較小，所以在 h2 底下用 h4。問題在哪？

✓ b：h2 底下的子項目是 h3，給它一個 class 調小字級即可。a 錯：任何文字都可以。c 錯：搜尋引擎不會因為某個級數懲罰頁面，問題在結構不清楚。d 錯：瀏覽器預設的字級只是預設樣式，級數的意義是結構。

練習 6：同一頁有主選單和頁尾連結兩個 <nav>，最好的做法是？

✓ b：一頁可以有多個 navigation landmark，有不同的名稱，landmark 清單才分得出來。a 錯：頁尾連結也是導覽，改成 div 就不能直接跳過去了。c 錯：nav 本來就是 navigation，重複寫 role 沒有作用，也沒有解決名稱的問題。d 錯：名稱一樣，清單裡還是兩個「導覽」。

練習 7：商品列表用 <ul>，CSS 設了 list-style: none。Chrome 的 Accessibility 分頁顯示 role 是 list，VoiceOver（Safari）卻沒有唸「清單」。該怎麼辦？

✓ c：WebKit 刻意讓去掉樣式、又不在 nav 裡的清單不回報 list 角色，role="list" 把它明確補回來，樣式不受影響。a 錯：連其他瀏覽器的清單語意也丟了。b 可行但改了設計，不是必要的代價。d 錯：presentation 會把所有瀏覽器的清單語意都拿掉，跟目標相反。

常見錯誤

  • 到處加 section：沒有名稱的 section 不是 landmark，只是 div。需要分區又有標題時，用 aria-labelledby 指向標題；只是為了排版就用 div。
  • 有兩個 nav 卻沒取名：landmark 清單裡出現兩個一樣的「導覽」。
  • 為了字級選標題級數：級數是大綱，字級交給 CSS。
  • 用 <a href="#"> 當按鈕：會改變網址、捲回頁首，螢幕閱讀器唸成連結。原地執行的動作用 <button type="button">。
  • 用按鈕或 div 換頁：失去「在新分頁開啟」、複製網址，搜尋引擎也找不到那一頁。換頁用 <a href>（Vue 用 RouterLink）。
  • 用 outline: none 拿掉焦點外框：鍵盤使用者不知道焦點在哪裡。外框可以改樣式，不能拿掉。
  • form 裡的 button 沒寫 type：預設是 submit，按了就送出表單。不是送出用的按鈕一律寫 type="button"。
  • 連結文字都是「更多」「點這裡」：螢幕閱讀器的連結清單裡全部一樣。文字要能單獨理解，或用視覺隱藏文字補上。
  • aria-label 跟可見文字不同：語音控制使用者說出看到的字卻按不到（WCAG 2.5.3）。名稱要包含可見文字。
  • 以為 Chrome 測過清單就沒問題：Safari 對 list-style: none 又不在 nav 裡的清單不回報 list 角色。重要的清單加 role="list"，用 VoiceOver 實測。

小結

  • 畫面正常不代表能用：瀏覽器從 DOM 產生無障礙樹，每個節點有角色、名稱、狀態；螢幕閱讀器、語音控制、自動化測試都讀它。div 和 span 的角色是 generic，元素選對，這些資訊就自動正確。
  • landmark 讓人直接跳到大區塊：header（banner）、nav、main（一頁一個）、footer（contentinfo）、有名稱的 section（region）。header／footer 放進 article、main 等元素裡就不是 landmark；同種 landmark 有多個時各自取不同名稱。
  • 標題是 landmark 裡的目錄：一個 h1、不跳級，字級交給 CSS。
  • 會換網址用 <a href>，原地動作用 <button>；div 加 role 只補了角色，焦點和鍵盤操作還是缺。form 裡不是送出用的按鈕寫 type="button"。
  • 連結文字要單獨唸出來也看得懂，名稱要包含可見文字；補充文字用 visually-hidden，不用 display: none。
  • 清單用 ul／ol，成對資料用 dl；div 和 span 是排版容器，沒有語意正是它們該有的樣子。
