階段 3：現代 CSS 與視覺品質 · 第 13 課

流動尺寸與邏輯屬性：相對單位、min/max/clamp、viewport units（含多語系與直排/RTL 的影響）

咖啡店首頁改版上線一週，客服轉來三張回報單。第一張來自一位視力不好的老客人：她在瀏覽器設定裡把預設字級調大了，其他網站的字都跟著變大，只有我們首頁的大標題「今天也來一杯手沖」一動也不動。第二張是手機使用者的截圖：一打開首頁，主視覺底部的「線上點餐」按鈕被瀏覽器下方的工具列蓋住一半。第三張不是 bug，是新需求：杜拜分店要上線阿拉伯文網站，同事把頁面切成阿拉伯文試了一下，圖示、價格、箭頭全部站錯邊，估計整份 CSS 要再寫一份。

這課要把這三張單一張一張關掉。三個問題看起來不相干，追下去根源是同一個：CSS 裡寫了太多「固定」的東西，固定的 px 字級、固定的視窗高度、固定的左和右。修法也是同一個方向：問每個尺寸、每個位置「應該跟著什麼變」，再選對應的寫法。學完你能看著一段 CSS 判斷每個數字該用什麼單位，寫出不會擋住使用者設定的流動字級，並讓同一份 CSS 在由右到左與中文直排時都正確。

這課的路線：
  1. 第一張單：使用者調大字級，標題為什麼不變？px 與 rem 差在哪，每個尺寸該跟著什麼變（開場第一個問題的答案）。
  2. 設計師要標題隨螢幕寬度連續變大：用 clamp() 寫流動字級，而且不能讓第一張單又被打開。
  3. 第二張單：點餐按鈕為什麼被工具列蓋住？手機上的四種視窗高度，以及同一個首頁的公告條為什麼多出橫向捲軸。
  4. 第三張單：杜拜分店怎麼共用同一份 CSS？用邏輯屬性描述「行首、行尾」，方向交給 HTML 的 dir，再決定哪些東西不該跟著翻。
  5. 延伸：門市看板要做直排時邏輯屬性怎麼幫上忙，最後整理接到多語系專案時，HTML 與 CSS 這一層先檢查哪些事。
這課會用到：
  • 第 11 課的 media query 與兩條驗收標準：@media (width >= 40em) 這類條件成立才套用樣式；WCAG 1.4.4 要求文字放大到 200% 仍可使用，1.4.10 要求 320px 寬時不需要左右捲動。

第一張單：使用者調大字級，標題為什麼不變？

先重現老客人的狀況。首頁標題的 CSS 是設計稿上量來的 font-size: 40px。使用者要把文字放大，瀏覽器提供兩種方式，結果不一樣：

  • 瀏覽器縮放（Cmd／Ctrl ＋「＋」）：整個頁面一起放大，文字、圖片、間距、用 px 寫的東西全部變大。代價是版面也跟著變寬，窄螢幕上很容易變成要左右捲動。
  • 改預設字級：在瀏覽器設定裡把預設字級從 16px 改成 24px 或 32px。很多視力不好的人用這種，因為它只放大字，版面寬度不變，不會變成要左右捲動。老客人用的就是這種。

第二種方式改的到底是什麼？瀏覽器把使用者設定的預設字級，當成根元素 <html> 的字級。頁面上沒寫字級的文字從根元素繼承下來，所以會跟著變大；但我們的標題寫了 40px，這是一個寫死的值，跟根元素是多少無關，所以使用者把預設字級改成 32px，標題還是 40px。這就是第一張單的原因。

要讓標題跟著使用者的設定走，就要用一個「以根元素字級為基準」的單位，這就是 rem（root em）。1rem 等於根元素的字級：預設 16px 時，2.5rem 是 40px；使用者改成 32px 時，2.5rem 自動變成 80px。把標題改成 font-size: 2.5rem，第一張單就修好了。字級用 rem，使用者的設定才會生效，這也是 WCAG 1.4.4（第 11 課）要求的。

這裡有兩個常見的陷阱，都是在根元素上動手腳。第一個是在 html 上寫死 px，例如 html { font-size: 16px }：它會蓋掉使用者的設定，全站的 rem 都固定以 16px 計算，等於把整個網站變回 px。第二個是為了好算寫 html { font-size: 62.5% }，讓 1rem = 10px：它沒有擋住使用者的設定，但全站的 rem 都要重新換算，第三方元件的字也會跟著縮小。直接用 16px 為基準，1.25rem 就是 20px，習慣了一樣好算。

不是每個尺寸都該跟著根字級

修第一張單的過程其實是在回答一個問題：「這個尺寸應該跟著什麼變？」CSS 的長度分兩種：絕對單位 px 永遠是同一個值；相對單位依照某個基準換算，基準一變它就跟著變。rem 的基準是根元素字級，其他相對單位各有各的基準。選單位，就是替每個尺寸選一個基準。

按鈕的內距是一個例子。按鈕的字變大時，內距也應該跟著變大，否則字會貼到邊框。這時要用 em：它的基準是「目前這個元素」的字級（用在 font-size 本身時，是父元素的字級）。

.btn { font-size: 1rem; padding: 0.5em 1em; }   /* 16px 字，8px 16px 內距 */
.btn.large { font-size: 1.25rem; }              /* 只改字級，內距自動變成 10px 20px */

那字級為什麼不也用 em？因為 em 會疊加：父元素 font-size: 1.2em、子元素也 1.2em，子元素就是 16 × 1.2 × 1.2 = 23.04px。巢狀清單一層比一層大就是這個原因。rem 永遠只看根元素，不管元素包了幾層結果都一樣，所以字級預設用 rem，em 留給「本來就該跟著元件自己的字級走」的距離。

反過來，邊框、分隔線、陰影這種細線不該跟著字變粗，用 px 才對。整理成表，下次寫 CSS 時對照「這個尺寸該跟著什麼」：

單位基準適合例子
rem根元素 <html> 的字級（瀏覽器預設 16px，使用者可以在設定裡改）字級、間距、元件尺寸、斷點font-size: 1.25rem（20px）
em目前元素的字級；用在 font-size 本身時是父元素的字級要跟著「這個元件的字」一起縮放的距離按鈕的 padding: 0.5em 1em
%父元素（包含區塊）的對應尺寸寬度、欄位比例max-width: 100%
frGrid 容器分配剩下的空間（第 9 課）Grid 欄寬grid-template-columns: 1fr 2fr
ch目前字型裡數字「0」的寬度英文的行長、只放數字的欄位寬度（行長見課末）max-width: 65ch
vw、vh視窗寬、高的 1%跟視窗有關的尺寸（下面兩節細講）min-height: 100vh（手機上要改用 svh，見第二張單）
px固定邊框、細線、陰影這種「不該跟著字變粗」的東西border: 1px solid
💡 實務上：設計稿標的是 px，寫進程式時換成 rem
Figma 這類設計工具標示的尺寸都是 px，首頁標題那個 40px 就是這樣來的：設計稿上 20px 的標題寫成 1.25rem、24px 的間距寫成 1.5rem。團隊通常會把常用的字級與間距整理成一組固定的值，大家共用，不在每個元件裡各自除以 16。邊框、分隔線、陰影維持 px，跟文字並排的圖示則用 em 或 rem，字放大時才不會顯得太小。code review 時資深會特別看兩件事：有沒有人把 font-size 寫成 px，有沒有人加了 62.5%。上線前把瀏覽器預設字級調到 32px，看一次後台的訂單列表：字有沒有擠出格子、按鈕的字有沒有被切掉。

標題改成 2.5rem，第一張單可以關了。但設計師看到修正後提了另一個要求：標題在手機上 28px、桌機上 48px，中間要隨螢幕寬度連續變大。一個固定的 rem 做不到這件事。

標題要隨螢幕寬度變大，又不能再擋住使用者的設定，怎麼寫？

設計師的要求寫清楚是：首頁標題在 320px 寬時 28px，1280px 寬時 48px，中間跟著寬度平均變大，更窄或更寬時停在 28px、48px。第 11 課的做法是 media query：320px 到 767px 一個字級、768px 以上另一個字級。問題是斷點之間字級是用跳的，而且每多要一個尺寸就多一段 media query，永遠做不到「連續」。

第一個直覺：用 vw，為什麼不行？

要跟著螢幕寬度變，最直覺的單位是 vw：1vw 是視窗寬度的 1%，視窗 800px 寬時 1vw 就是 8px。所以很多人會寫 font-size: 4vw，練習 2 的起始 CSS 就是這樣寫的。它有兩個問題：

  • 沒有上下限：320px 寬時只有 12.8px，太小；2560px 寬的螢幕上變成 102px，太大。
  • 使用者的設定又失效了：vw 只跟視窗寬度有關，跟根元素字級無關。老客人把預設字級調大時，4vw 完全不變，等於把剛關掉的第一張單又打開。WCAG 把這種寫法列為 1.4.4 的失敗案例（F94：用 viewport 單位決定字級，讓文字沒辦法放大）。

所以我們要的字級有三個條件：會跟著視窗寬度變（需要 vw）、會跟著使用者的字級設定變（需要 rem）、而且有上下限。前兩個可以把 rem 和 vw 加在一起，第三個要靠 CSS 的比較函式。

min()、max()、clamp()：給尺寸一個範圍

CSS 有三個比較函式，都是在幾個值裡挑一個：

  • min(a, b)：取比較小的那個。width: min(100%, 40rem) 等於「最多 40rem，但不超過父元素」，一行取代 width: 100%; max-width: 40rem。
  • max(a, b)：取比較大的那個。padding-inline: max(1rem, 5%)：寬螢幕時 5%，窄螢幕時至少 1rem。
  • clamp(最小, 偏好, 最大)：用偏好值，但不低於最小值、不超過最大值。等於 max(最小, min(偏好, 最大))。

參數裡可以直接做加減乘除，不用另外包一層 calc()，不同單位也能混在一起算，例如 1rem + 2vw，瀏覽器會在當下把 rem 和 vw 各自換成 px 再相加。標題要的就是 clamp()：最小值 28px、最大值 48px，偏好值是「跟著寬度變的那條線」。剩下的問題是那條線怎麼寫。

流動字級：把「兩點之間線性變化」寫成一條直線

「320px 寬時 28px，1280px 寬時 48px，中間平均變大」在數學上就是一條直線：字級 = 截距 + 斜率 × 視窗寬。斜率表示視窗每寬 1px 字級大多少，用 vw 表達；截距是固定的部分，用 rem 表達，這樣使用者調大字級時，截距會跟著變大。最後用 clamp 夾住上下限：

斜率 = (48 − 28) ÷ (1280 − 320) = 0.020833   → 視窗每寬 1px，字大 0.020833px
     = 2.0833vw                              （1vw 是視窗寬的 1%，所以乘 100）
截距 = 28 − 0.020833 × 320 = 21.333px        → 1.3333rem（除以 16）

font-size: clamp(1.75rem, 1.3333rem + 2.0833vw, 3rem);
                 28px      ↑ 直線             48px

驗算一次：800px 寬時 21.333 + 0.020833 × 800 = 38px，剛好在 28 與 48 的中間。使用者把根字級改成 32px 時，所有 rem 的部分（上限、下限、截距）都變成兩倍，vw 的部分不變，所以字還是會跟著變大，第一張單不會被打開。

下面的程式模擬瀏覽器怎麼算這個值，並跟 4vw 比較。執行後每一列看兩件事：clamp 版在根字級 16px 與 32px 時是不是不一樣，4vw 版在 320px 與 1600px 時是不是太小、太大。

流動字級也有界線，問題出在瀏覽器縮放。縮放 200% 的意思是「每個 CSS px 畫成原本兩倍大」，所以同一個螢幕上能放的 CSS px 只剩一半：1280px 寬的視窗，縮放後在 CSS 裡只有 640px 寬。用上面這條 clamp 算一次：縮放前視窗 1280px，偏好值是 21.333 + 0.020833 × 1280 = 48px，螢幕上畫成 48 個實際像素。縮放後視窗剩 640px，偏好值是 21.333 + 0.020833 × 640 ≈ 34.7px，每個 CSS px 畫成兩倍，螢幕上約 69 個實際像素，只放大了 1.44 倍。原因是 rem 的部分（21.333px）照樣跟著放大兩倍，vw 的部分卻因為視窗在 CSS 裡變窄而少了一半，乘上兩倍後等於沒放大。上下限拉得越開，斜率越大，vw 在字級裡占的比重越高，縮放時就越放大不到兩倍。

流動字級不是越大越好。最大值與最小值的比例拉太開（例如 16px 到 80px），使用者縮放時視窗的 CSS 寬度會變小、vw 的部分跟著縮，字可能放大不到兩倍。上下限的比例控制在 2.5 倍以內（Maxwell Barvian 在 Smashing Magazine〈Addressing Accessibility Concerns With Using Fluid Type〉算出的界線：最大值 ≤ 最小值 × 2.5，瀏覽器縮放時字才一定放大得到兩倍），並照第 11 課的方法實際用文字放大 200% 檢查。內文字級通常不用流動，固定 1rem 最穩；流動字級用在大標題。

每次這樣手算很麻煩，而且一個網站會有好幾個流動字級。團隊通常會在設計 token（第 16 課）裡把這些值算好，練習 1 就是寫出這個產生器：給兩端的寬度與字級，算出 clamp 字串。

💡 實務上：流動字級多半只出現在首頁與活動頁的大標題
常見的情境是設計師只給手機與桌機兩張稿，例如咖啡店首頁的主視覺標題，前端用 clamp() 補上中間的寬度。動手前先跟設計師確認兩端的寬度與字級，這就是 clamp 需要的四個數字，不要自己猜。後台、表單、訂單列表這種以資料為主的畫面通常不需要流動字級，固定的 rem 加上一兩個斷點比較好預測，也比較好除錯。如果標題是後台可以改的文字（例如活動名稱），用最長的那種標題在 320px 寬看一次，確認斷行還能接受。

標題的字級處理完了，同一個主視覺還掛著第二張單：手機一打開，點餐按鈕被工具列蓋住。這次的問題不在字級，在主視覺的高度。

第二張單：點餐按鈕為什麼被手機工具列蓋住？

首頁主視覺寫的是 height: 100vh，意思是「剛好一個畫面高」，點餐按鈕放在主視覺底部。上一節用過 vw，vh 是同一類的單位：1vh 是視窗高度的 1%。在桌機上這很單純，視窗多高，100vh 就多高。手機上卻有一個問題：網址列與底部工具列會隨著捲動收起或展開，同一支手機的「視窗高度」有兩個值，vh 要用哪一個？

答案是比較大的那一個：網址列和工具列都收起時的高度。規範為了相容舊網頁這樣定義。但使用者剛打開首頁時，網址列和工具列都是展開的，實際看得到的高度比 100vh 小，主視覺的底部就落在工具列後面，點餐按鈕被蓋住。這就是第二張單的原因。

為了讓開發者能明確選擇，CSS 規範定義了三種視窗高度，加上原本的 vh 共四個單位：

單位以哪個高度為準特性適合
svh（small）網址列、工具列都展開時（最小）固定，不會隨捲動改變首屏主視覺：剛打開時一定完整看得到
lvh（large）網址列、工具列都收起時（最大）固定很少直接用
vh等於 lvh（規範為了相容舊網頁這樣定義）固定桌機上沒差別；手機上會被工具列蓋住
dvh（dynamic）目前實際的可見高度捲動時跟著網址列變，會讓版面跳動全螢幕的對話框、聊天室這種不捲動整頁的介面

咖啡店首頁的主視覺改成 min-height: 100svh：svh 是工具列展開時的高度，也就是剛打開頁面時真正看得到的高度，所以一打開就剛好一個畫面高，點餐按鈕不會被蓋住。用 min-height 而不是 height，是因為使用者把字放大、內容變多時，區塊要能長高，不能把文字切掉（第 11 課：不要固定高度）。

看到 dvh 是「目前實際的可見高度」，很容易覺得它最準，但一般頁面的主視覺不要用它：使用者往下捲、網址列收起時，dvh 的值變大，主視覺跟著長高，下面的內容整個往下移，正在讀的人會找不到剛才的位置。dvh 適合不捲動整頁的介面，例如全螢幕的對話框，它本來就該隨時填滿看得到的範圍。svh 的支援度與舊瀏覽器的備援寫法見課末。

同一個首頁的公告條：100vw 為什麼多出橫向捲動？

修主視覺時，QA（測試人員）回報了同一個首頁的另一個問題：主視覺下面那條全寬的公告條「平日早上 9 點前，美式咖啡 60 元」，在 Windows 的電腦上會讓整頁多出一小段橫向捲動。公告條寫的是 width: 100vw，本意是「跟視窗一樣寬」。

問題出在 vw 怎麼算。CSS 規範定義：根元素是一般的 overflow（沒有寫 overflow: scroll 或 scrollbar-gutter: stable）時，vw「假設捲軸不存在」。首頁內容比一個畫面長，右邊會出現垂直捲軸，捲軸本身占掉一段寬度（傳統的捲軸大約十幾 px），但 100vw 仍然是含捲軸的整個視窗寬，比實際能放內容的寬度多出捲軸那一段，多出來的部分就變成橫向捲動。開發者常用的 Mac 觸控板環境捲軸是浮在內容上的，不占寬度，所以自己看不到這個 bug。

修法是不要用 vw 去量寬度。block 元素本來就會填滿父元素的寬度，全寬條不需要寫 width；要貼齊視窗兩側時，讓它的父元素沒有 padding、body 沒有 margin（瀏覽器預設 body 有 8px margin）。真的要從置中的窄容器裡「破出去」時，不要用 margin-inline: calc(50% - 50vw)（它一樣受捲軸影響），改用第 9 課的 Grid：外層排三欄，內容放中間那欄，全寬條橫跨三欄：

.page { display: grid; grid-template-columns: 1fr min(40rem, 100% - 2rem) 1fr; }
.page > * { grid-column: 2; }            /* 一般內容：中間那欄，最多 40rem、兩側至少各留 1rem */
.page > .band { grid-column: 1 / -1; }   /* 全寬條：從第一條線跨到最後一條線 */

中間那欄用到上一節的 min()：最多 40rem，但不超過容器寬度減掉兩側各 1rem。練習 2 把這一節和上一節的修正一起做一次：流動標題、100svh 的主視覺、不造成橫向捲動的公告條。

💡 實務上：viewport 的 bug 常常只在別人的裝置上出現
開發時用 Mac 與桌機瀏覽器，看不到手機工具列蓋住點餐按鈕，也看不到 Windows 捲軸多出來的橫向捲動；這類問題通常是 QA（測試人員）或客服轉來的使用者截圖。收到回報時，資深會先問是哪個裝置、哪個瀏覽器，再去重現。DevTools 的裝置模擬沒有會伸縮的網址列，不能取代真機，所以上線前至少用 iPhone 的 Safari 與 Android 的 Chrome 打開首頁和結帳頁看一次。橫向捲動可以在 macOS 的設定裡把捲軸改成「總是顯示」，自己的電腦上就看得到。

前兩張單的問題都是「數字寫死」：寫死的字級、寫死的高度、寫死的寬度。第三張單是另一種寫死：寫死的方向。

第三張單：杜拜分店怎麼跟我們共用同一份 CSS？

菜單的每一列左邊是圖示、右邊是價格，CSS 寫了 margin-right: 8px（圖示和品名之間）、margin-left: auto（把價格推到右邊）。阿拉伯文是由右到左（RTL，right-to-left）閱讀的文字，眼睛從右邊開始讀，所以整個版面也要左右對調：圖示應該在右邊、價格在左邊。中文和英文的方向則叫 LTR（left-to-right）。

瀏覽器怎麼知道這一頁是 RTL？方向寫在 HTML 的 dir 屬性：<html dir="rtl">。有了它，文字會從右邊開始排，但我們 CSS 裡寫死的 margin-right 還是加在右邊，margin-left: auto 還是把價格推到右邊，所以版面一半對調、一半沒動，圖示和價格全部站錯邊。

一般的做法是再寫一整份 [dir="rtl"] 開頭的覆寫，把每個 left 和 right 對調。這能動，但之後每改一次樣式就要改兩個地方，漏改一處，杜拜分店的版面就壞一處。同事說「整份 CSS 要再寫一份」指的就是這個。

邏輯屬性：用文字的方向描述位置

問題的根源是 left、right 這種物理方向是固定的，不管文字往哪裡走，左就是左。我們真正想說的其實不是「圖示右邊留 8px」，而是「圖示後面、品名前面留 8px」；不是「價格推到右邊」，而是「價格推到這一行的結尾」。邏輯屬性（logical properties）就是用這種說法描述位置的 CSS 屬性，它以文字的方向為準，不說左右上下。要讀懂它，先認識三個詞：

  • inline 軸：一行文字前進的方向。中文橫排、英文是由左到右；阿拉伯文是由右到左。
  • block 軸：一行一行（段落一個一個）堆疊的方向。橫排時是由上往下。
  • start／end：軸的起點與終點。橫排 LTR 時 inline-start 是左邊，RTL 時是右邊。

把屬性名稱裡的 left、right 換成 inline-start、inline-end，菜單這一列改寫後是這樣：

.icon  { margin-inline-end: 8px; }         /* 圖示「後面」留 8px：LTR 在右邊、RTL 在左邊 */
.price { margin-inline-start: auto; }      /* 把價格推到行尾 */
.title { padding-inline-start: 1rem; text-align: start; }

瀏覽器在算樣式時，會依元素的方向把 margin-inline-end 對到實際的一邊：在 LTR 的頁面上它就是 margin-right，在 dir="rtl" 的頁面上它就是 margin-left。同一份 CSS，兩種方向都對，杜拜分店不需要另一份覆寫。

版面本身也不用另外處理。Flexbox 與 Grid 本來就是以文字方向排的：flex-direction: row 在 RTL 時自動由右往左排，justify-content: flex-start 也會跟著換邊，gap 沒有方向。所以 RTL 時不要用 flex-direction: row-reverse 去「反轉回來」，那會把 RTL 又變成由左到右。上下、左右都相同的值（例如 padding: 12px 16px）不受方向影響，可以保留。

幾乎每個寫了 left、right、top、bottom、width、height 的屬性都有對應的邏輯屬性。下面這張表查表用，不用背，記住命名規則就推得出來：左右變成 inline、上下變成 block、左和上變成 start、右和下變成 end。

💡 實務上：新專案一開始就用，舊專案等有 RTL 市場再換
新專案從一開始就用邏輯屬性，成本跟寫 left、right 一樣，咖啡店首頁改版這種新寫的樣式就該直接用。舊專案不一定要全部改，等真的要做 RTL 語系時再一起換，像這次杜拜分店的需求就是那個時間點。換的時候先搜尋 CSS 裡的 left、right（包含 margin-left、padding-right、text-align: left、定位的 left:），一條一條判斷是不是跟文字方向有關，再換成表裡對應的屬性。練習 3 就是把菜單這一列完整改一次。

換成邏輯屬性之後，菜單的圖示和價格會跟著 dir 自動對調。但切到阿拉伯文還有兩件事沒處理：dir 要寫在哪裡、怎麼切換，以及有些東西其實不該跟著對調。

方向交給 HTML：lang、dir 怎麼寫，哪些東西不該鏡像？

上一節的邏輯屬性跟著 dir 走，所以 dir 寫對是前提。語言與方向寫在 HTML，不是 CSS：<html lang="ar" dir="rtl">。兩個屬性分工不同：

  • dir 決定文字方向，邏輯屬性、Flexbox 的排列都跟著它走。
  • lang 告訴瀏覽器這段文字是什麼語言，讓它選對字型、斷行規則與螢幕閱讀器的發音（第 1 課）。

它們不只能寫在 <html>。頁面裡夾了其他語言時，在那個元素上寫，例如中文頁裡的英文店名 <span lang="en">。使用者自己輸入的文字（評論、暱稱）方向不確定，杜拜分店的評論區可能有人寫阿拉伯文、有人寫英文，這時用 dir="auto"，讓瀏覽器依第一個強方向字元判斷。「強方向字元」是本身有固定方向的字，例如英文字母一定是 LTR、阿拉伯字母一定是 RTL；數字和標點沒有固定方向，不算。

CSS 有時候還是要依方向寫不同的樣式，下面的箭頭就是例子。這時用 :dir(rtl) 偽類。它看的是元素實際的方向（會從祖先繼承 dir），比屬性選擇器 [dir="rtl"] .x 準：後者只看祖先有沒有寫這個屬性，遇到 dir="auto" 就判斷不了，因為屬性值是 auto，不是 rtl。支援度見課末。

RTL 時哪些要鏡像、哪些不要

邏輯屬性把「位置」對調了，但元素裡面的圖形不會自己翻。菜單每一列尾端有一個表示「下一步」的箭頭 ›，在 RTL 的頁面上「下一步」是往左邊走，箭頭卻還指向右邊，意思就錯了。另一方面，價格「110」不能翻成「011」。所以要一個一個判斷：

  • 要鏡像：表示方向的圖示，例如「下一頁」的箭頭 ›、返回鍵、進度條的方向。用 .chev:dir(rtl) { transform: scaleX(-1) } 水平翻轉。
  • 不要鏡像：數字（阿拉伯文裡的數字一樣由左到右讀）、價格、時鐘、播放鍵 ▶（媒體控制的慣例不翻）、商標與照片、打勾 ✓。

判斷的原則是：這個圖形的意思跟「閱讀方向」有沒有關係。箭頭表示「往後讀」，閱讀方向反了它就要反；打勾、播放鍵、照片的意思跟閱讀方向無關，翻了反而錯。也因此不要偷懶對整列或整頁用 scaleX(-1) 達成鏡像：裡面的文字和數字會變成反的。

方向處理好了，但切語言還有一個跟方向無關的副作用：字數變了。

翻譯後文字變長

杜拜分店的網站除了阿拉伯文，通常也會有英文版，同一個按鈕換成另一種語言，字數可能差很多。「點餐」翻成英文是 Order now，德文是 Jetzt bestellen；中文翻成英文常長 1.5 倍，德文更長。如果按鈕寫了固定寬度，翻譯後字就會擠出去或被切掉。按鈕、標籤、導覽列不要用固定寬度，讓它們隨內容變寬或換行（第 7 課的 max-width、第 8 課的 flex-wrap）。測試時把介面切到最長的那個語言看一次。

到這裡三張單都關了。邏輯屬性還有一個好處，在左右對調時看不太出來，要到文字改成直的時候才明顯。

門市看板要直排：邏輯屬性還撐得住嗎？

門市的活動公告、菜單看板有時要做成中文直排，例如練習 4 的萬聖節公告。直排是另一種書寫模式（writing mode）：橫排時字由左往右、行由上往下；中文、日文的直排是字由上往下、行由右往左。書寫模式由 writing-mode 控制：

.board {
  writing-mode: vertical-rl;   /* 字由上往下，行由右往左（中文、日文的直排） */
  inline-size: 20rem;          /* 直排時 inline 是上下方向：這是高度 */
}
.tcy  { text-combine-upright: all; }   /* 縱中橫：兩位數字擠進一個字的寬度橫著放 */
.year { text-orientation: upright; }   /* 英文字母、長數字一個一個直立 */

這裡就看得出邏輯屬性的好處。回到「邏輯屬性：用文字的方向描述位置」那一節的圖（第三格中文直排）：直排時 inline 軸是上下、block 軸是右到左。所以 inline-size: 20rem 在直排時限制的是高度，margin-block-end 加在每個段落（元素）的左邊，也就是下一段開始的方向。用邏輯屬性寫的元件換成直排，間距仍然在正確的位置；用 width、margin-bottom 寫的元件，換成直排後全部錯位，因為「下面」在直排時已經不是「下一段」的方向。

直排裡的數字怎麼排

直排時半形的英文與數字預設是橫躺的（順時針轉 90 度），讀者要歪著頭看。日期「10月31日」裡的兩位數字，傳統排法是縱中橫（tate-chu-yoko）：把兩個數字橫著擠進一個字的寬度。做法是把「10」包進 <span class="tcy">，text-combine-upright: all 讓它橫排擠成一格。超過兩位的數字（例如年份 2026）擠成一格太小看不清楚，改成 text-orientation: upright 逐字直立。瀏覽器不會自動幫你找出數字（原因見課末），所以要自己包元素。

做直排時有兩種常見的偷懶寫法，都不要用。不要用 transform: rotate(90deg) 假裝直排：字是轉了，但每個字也一起躺下，版面占的位置還是橫的。也不要一個字一個 <br>：換字級就亂掉，螢幕閱讀器還會一個字一個字停頓。

窄螢幕放不下時

直排的公告在 320px 寬的手機上，欄數一多就放不下。這時讓它自己左右捲動（overflow-x: auto），而且讓 vertical-rl 的元素自己當捲動容器：直排的第一行在最右邊，vertical-rl 元素的捲動起點也在右邊，所以一打開就看到第一行。如果外面再包一層橫排的捲動框，那一層的捲動起點在左邊，使用者先看到的是最後一行。可以捲動的區塊要加 tabindex="0" 與名稱，鍵盤使用者才能聚焦它、用方向鍵捲動（第 5 課）。

從字級、高度、寬度到方向與直排，這課修的每一件事，倒過來看就是一份接多語系專案時的檢查清單。

資深視角：接到多語系專案，HTML 與 CSS 這一層先檢查什麼？

杜拜分店這種需求有一個正式的名字。讓產品可以換語言、換地區而不用改程式，叫國際化，英文 internationalization，因為 i 和 n 之間有 18 個字母，常寫成 i18n。真的把產品翻成某一個語言、調整成某個地區的習慣，叫在地化，localization，簡寫 l10n。前端在 i18n 這件事上，HTML 與 CSS 這一層要做到：

  • 不把文字做進圖片（不能翻譯、不能放大、搜尋引擎讀不到）。
  • 不固定寬度與高度：按鈕、標籤讓內容決定大小，用 min-／max- 與 clamp() 給範圍。
  • 新寫的樣式用邏輯屬性，不寫 left／right；有方向的圖示準備 :dir(rtl) 的鏡像。
  • <html lang dir> 跟著語言切換；使用者產生的內容用 dir="auto"。
  • 日期、價格、數字的格式交給 Intl（TypeScript 課第 6 課），不要在 CSS 或模板裡自己拼「月」「日」或千分位。
  • 字級用 rem，流動字級的偏好值帶 rem；每次改版用「預設字級 200%」與 320px 寬各看一次。

判斷什麼時候做：只有中文的網站，邏輯屬性與 rem 幾乎沒有額外成本，現在就用；RTL 的完整支援（鏡像圖示、雙向文字的測試）等真的有 RTL 市場再投入，但不要先寫出到時候要整份重寫的 CSS。

補充與查表

  • 行長：一行多少字好讀：一行太長，眼睛換行時容易找不到下一行的開頭。英文常見的建議是 45～75 個字元，寫成 max-width: 65ch。ch 是「0」的寬度，中文字大約是 1em 寬（「0」只有半個字寬左右），所以中文內文用 em 估比較準：一行 30～40 字，寫 max-inline-size: 35em（max-inline-size 在橫排時就是 max-width，見邏輯屬性那一節）。
  • 流動間距：間距也能用流動字級的方式隨寬度變化，例如區塊上下的距離 padding-block: clamp(2rem, 1rem + 4vw, 5rem)。
  • 比較函式的支援度：min()、max()、clamp() 都已經是 Baseline widely available（2023-01；Baseline 的意思見第 12 課）。
  • 寬度方向的新單位：除了 svh、lvh、dvh，寬度方向也有 svw、lvw、dvw，比較少用。
  • svh 的支援度與備援：svh／lvh／dvh 在 2025-06 成為 Baseline widely available，可以直接用；要支援更舊的瀏覽器時，在前面多寫一行 min-height: 100vh 當備援，不認得 svh 的瀏覽器會用它。
  • 邏輯屬性的支援度：邏輯屬性已經是 Baseline widely available。
  • :dir() 的支援度：Baseline widely available，2026-06。
  • 直排相關的支援度：writing-mode 與 text-combine-upright（none、all）都是 Baseline widely available。規範裡還有 text-combine-upright: digits 2 可以自動處理數字，但目前沒有瀏覽器支援，所以要自己包元素。

練習

練習 1：寫 fluidClamp(minPx, maxPx, minVw, maxVw, rootPx = 16)，回傳在視窗寬 minVw 到 maxVw（px）之間、從 minPx 線性變到 maxPx 的 clamp() 字串，格式是 clamp(<min>rem, <截距>rem + <斜率>vw, <max>rem)，數字最多 4 位小數（用 +x.toFixed(4) 去掉多餘的 0）。截距是負數時寫成 -0.5rem + 5vw。minPx > maxPx 或 minVw >= maxVw 時丟 RangeError。測試會在範圍內外好幾個寬度、以及根字級放大兩倍時，算出你的字串的實際字級。

練習 2：首頁改版：標題 .hero h1 的字級在 320px 寬時 28px、1280px 寬時 48px，中間隨寬度連續變化，更窄或更寬時停在 28px、48px；使用者把預設字級放大時標題也要變大。主視覺 .hero 在手機上剛好填滿「網址列展開時」的可見高度（內容多時可以長高）。.band 是全寬的公告條，要貼齊視窗左右兩側，而且有捲軸的電腦上也不能造成橫向捲動。HTML 不能改。

練習 3：杜拜分店要用同一份 CSS。把菜單裡所有寫死左右的屬性換成邏輯屬性，讓頁面在 <html dir="rtl" lang="ar"> 時自動鏡像：圖示在右、價格在左，圖示與品名之間在兩種方向都是 8px，標題文字從行首算起 16px；表示「下一步」的箭頭 .chev 只在 RTL 時水平翻轉（用 :dir(rtl)），價格與文字不能翻。測試會把預覽的 <html> 切成 dir="rtl" 再量。左右相同的 padding: 12px 16px 可以保留。HTML 不能改。

練習 4：把萬聖節公告 .board 做成中文直排（字由上往下、行由右往左），標題在最右邊的第一行。日期「10月31日」的兩組兩位數字用縱中橫（各自包進元素，text-combine-upright: all）；年份「2026」四個數字逐字直立（text-orientation: upright，不要擠成一格）。區塊最多 20rem 高。320px 寬時放不下的欄在公告裡左右捲動、不能撐破頁面，一打開就要看到標題；可以捲動的公告要能用鍵盤聚焦（tabindex="0"），並且有名稱。文字內容不能改。

練習 5：標題寫 font-size: 5vw，有什麼無障礙問題？

✓ b：vw 只跟視窗寬度有關，不看根字級，使用者在瀏覽器設定放大預設字級時完全沒效果（WCAG 1.4.4 的失敗案例 F94）。改成 clamp()，上下限與偏好值都帶 rem，例如 clamp(1.75rem, 1.3333rem + 2.0833vw, 3rem)。a 錯：單位跟字型無關。c 錯：視窗寬度固定時字級不變，不會位移。d 錯：「相對」的基準是視窗，不是使用者的字級設定。

練習 6：手機上 height: 100vh 的主視覺，底部的點餐按鈕被瀏覽器的工具列蓋住。比較好的寫法是？

✓ b：svh 是網址列、工具列都展開時的可見高度，剛打開頁面時一定完整看得到；用 min-height 讓內容多時可以長高。a 錯：百分比高度要父元素有明確高度才有效，通常會算成 auto。c 錯：那是寬度的 100%。d 錯：dvh 會跟著網址列伸縮，使用者捲動時主視覺高度改變，下面的內容跟著跳動；它適合不捲動整頁的全螢幕介面。

練習 7：margin-inline-start: 1rem 在 <html dir="rtl"> 的頁面上，加在元素的哪一邊？

✓ b：inline-start 是一行文字開始的那一邊，RTL 時文字從右邊開始，所以是右邊。a 是 LTR 時的結果。c 是 writing-mode: vertical-rl 直排時的結果（直排的 inline 方向是由上往下）。d 錯：邏輯屬性會依 dir 與 writing-mode 對到不同的物理方向，這正是它的用途。

常見錯誤

  • 字級用 px 或只用 vw：使用者調大預設字級時不會變大。字級用 rem；流動字級用 clamp()，偏好值寫成「rem ＋ vw」。
  • 在根元素寫死字級：html { font-size: 16px } 蓋掉使用者的設定，全站的 rem 都不會跟著變；62.5% 不擋設定，但全站要重新換算。根元素不寫字級，以 16px 為基準換算。
  • 流動字級的上下限也用 px：放大時被 px 的上限卡住。三個參數都用 rem。
  • 手機主視覺用 100vh：vh 等於網址列收起時的高度，剛打開時底部被蓋住。用 min-height: 100svh；一般頁面不要用 dvh。
  • 全寬元素寫 width: 100vw：包含垂直捲軸的寬度，有捲軸的電腦會橫向捲動，用觸控板的 Mac 看不出來。block 元素不寫 width 就會填滿；用 Grid 的欄位處理「破出容器」。
  • 寫死 left／right：RTL 語系要整份覆寫。用 margin-inline-*、padding-inline-*、inset-inline-*、text-align: start／end。
  • RTL 用 row-reverse 或整列 scaleX(-1)：前者把方向又反轉回來，後者讓文字與數字變成反的。Flexbox 本來就跟著 dir 走，只有方向性的圖示要翻。
  • 以為翻譯後長度不變：英文、德文常比中文長 50% 以上，按鈕與標籤不要固定寬度。
  • 直排用 rotate 或 <br>：用 writing-mode: vertical-rl；兩位數字用 text-combine-upright: all，更長的用 text-orientation: upright。

小結

  • 三張回報單的根源相同：CSS 寫死了字級、高度、寬度與方向。修法是問每個尺寸「應該跟著什麼變」，再選單位或屬性。
  • 第一張單：使用者改的預設字級就是根元素的字級，rem 跟著它變，px 不會。字級與間距用 rem、元件內的距離用 em、版面用 % 與 fr、細線用 px；不要在根元素寫死 px。
  • 流動字級是一條直線：截距用 rem、斜率用 vw，再用 rem 的上下限以 clamp() 夾住。只用 vw 會讓使用者的字級設定失效（WCAG F94）；上下限比例控制在 2.5 倍以內。
  • 第二張單：vh 等於 lvh，是工具列收起時的高度；首屏用 min-height: 100svh，dvh 只給不捲動整頁的介面。100vw 包含捲軸寬度，全寬元素不要用它。
  • 第三張單：邏輯屬性用 inline（文字前進）與 block（行堆疊）、start 與 end 描述位置，跟著 HTML 的 dir 自動對到正確的一邊；方向性圖示用 :dir(rtl) 鏡像，數字與文字不翻；翻譯會變長，不固定寬度。
  • 直排用 writing-mode: vertical-rl，兩位數字用縱中橫、更長的數字用 text-orientation: upright；用邏輯屬性寫的元件換成直排也是對的。
