階段 4：除錯、瀏覽器與效能 · 第 20 課

Web 效能量測：LCP、INP、CLS，實驗室與真實使用者資料

店長說「官網好慢」。你在辦公室的 MacBook 上打開，一秒就好；跑 Lighthouse 拿到 98 分。可是 Search Console 寄信來說「手機版網址的 LCP 問題：超過 2.5 秒」。誰說的才對？要怎麼知道慢在哪一段、改完有沒有變好？

這課就處理這一件事：把店長的「好慢」變成數字，判斷 Lighthouse 和 Search Console 誰說的才算數，找出咖啡店官網慢在哪一段，最後在網站上裝好量測，讓之後每次改版都看得出有沒有變好。過程中會學到三個指標：LCP（主要內容多久出現）、INP（點了之後多久有反應）、CLS（畫面會不會亂跳），以及兩種資料來源：實驗室與真實使用者。

這課的路線：
  1. 「很慢」怎麼變成數字：為什麼看 p75 不看平均；Lighthouse 98 分和 Search Console 不及格誰對（開場問題的最小答案）。
  2. 要量哪幾種慢：三個 Core Web Vitals 各量什麼、門檻在哪；兩邊的數字各從哪裡來，為什麼對不起來。
  3. 在自己電腦上重現使用者的慢，再把 LCP 拆成四段，找出該先修的那一段。
  4. 店長的另外兩個抱怨：畫面亂跳（CLS）和按了沒反應（INP）怎麼算。
  5. 在官網裝上 web-vitals 收真實使用者的數字，並把效能變成持續追蹤的目標。
這課會用到：
  • 第 19 課的主執行緒與長任務：主執行緒一次只做一件事，超過 50ms 的任務執行期間，點擊只能排隊等。
  • 第 14 課的首屏圖片：首圖不要 lazy、要寫 width／height 讓瀏覽器先預留空間。

「很慢」要怎麼變成可以比較的數字？

先問店長「慢」是哪一種。是白畫面很久？首頁大圖很晚才出來？按「加入購物車」沒反應？還是讀菜單讀到一半，文字被擠走、點錯按鈕？這四種問題的原因和修法完全不同：白畫面多半要看伺服器，大圖晚出來要看圖片怎麼載，按了沒反應要看 JavaScript 有沒有卡住主執行緒，畫面亂跳要看版面有沒有預留空間。「很慢」這兩個字沒辦法動手修，所以第一步是用指標把感受拆開。

這些指標有一個共同原則：量的是使用者感受到的事，不是伺服器有多忙、檔案有多大。伺服器 CPU 只用了 10%、JS 檔只有 200 KB，使用者還是可能盯著白畫面五秒；反過來，檔案很大但排得好，使用者也可能完全不覺得慢。店長抱怨的是感受，所以量的也要是感受。

拆開之後還有第二個問題：怎麼匯總。官網一天有幾千次造訪，每次的數字都不同：有人用新 iPhone 連公司 Wi‑Fi，有人用三年前的 Android 在捷運上。最直覺的做法是算平均值，但平均值會被少數極端值拉走，而且描述的常常是一個不存在的人。效能資料一律看分布，用百分位數描述。

百分位數（percentile）是把所有樣本由好到壞排好之後，落在某個位置的那一筆值。p75 是「第 75% 那一筆」，意思是 75% 的造訪至少這麼好；p90 就是 90% 的造訪至少這麼好，剩下最慢的 10% 比它更差。延遲為什麼要用百分位數，系統設計課第 3 課從後端 API 的角度講過同一件事。下面用 10 次造訪的數字實際算一次，執行後比較「平均」和 p75 差多少：

平均 2815ms 看起來是「有點慢」，但沒有任何一個使用者真的遇到 2.8 秒：八個人很順，兩個人等了快 7 到 10 秒。如果你拿平均值去跟店長報告「平均 2.8 秒」，你會去優化一個不存在的使用者，而真正等了 10 秒的那兩個人被平均掉了。

百分位數把這兩群人分開看。p75 是 1800ms，說的是「大多數人沒問題」；p90 是 6800ms，告訴你最慢的那群人非常慢。Google 評估 Core Web Vitals 用 p75，它在「照顧大多數人」和「不被極少數異常值左右」之間取平衡；排查問題時，再往 p90、p95 看最慢的那群人是誰。

有了這個觀念，就能先回答開場的問題：兩邊都沒有錯，只是量的東西不同。Lighthouse 是在你的 MacBook 上模擬一次載入，是一個樣本；Search Console 的數字來自真實 Chrome 使用者過去 28 天、手機版的 p75，是一整個分布。使用者實際感受到多快，以真實使用者資料為準；Lighthouse 用來找原因、驗證修改。

不過這個答案還有兩個空白：Search Console 說的「LCP」到底量什麼？它還會看哪些指標？下一節先把要量的東西定清楚。

要量哪幾種慢？三個 Core Web Vitals

上一節把「慢」拆成幾種感受，Google 把其中三種定成標準指標，叫 Core Web Vitals：載入（主要內容多久出現）、互動（點了多久有反應）、視覺穩定（畫面會不會亂跳）。Search Console 寄來的信、PageSpeed Insights 上方的評等，都是依這三個指標判斷。剛好對應店長的三種抱怨：首頁大圖很晚出來、按了沒反應、讀菜單時被擠走。

每個指標都有「好／需要改善／差」三級門檻。下表的門檻依 web.dev 的官方定義（vitals 頁 2024-10-31 更新），web-vitals 函式庫 6.2.3 的 LCPThresholds、INPThresholds、CLSThresholds 也是同樣的數字。web-vitals 是 Google 維護、用來在瀏覽器量這三個指標的 JavaScript 函式庫，這課最後一節會裝到官網上：

指標量什麼好需要改善差
LCP（Largest Contentful Paint，最大內容繪製）從開始導覽到可視範圍內最大的圖片或文字區塊畫出來的時間≤ 2.5 s2.5～4 s> 4 s
INP（Interaction to Next Paint，互動到下一次繪製）整個瀏覽期間，使用者點擊、觸控、按鍵到畫面更新的延遲，取接近最差的一次≤ 200 ms200～500 ms> 500 ms
CLS（Cumulative Layout Shift，累計版面位移）非預期的版面位移分數，取最嚴重的一段時間≤ 0.10.1～0.25> 0.25

邊界值算哪一邊要記清楚：等於門檻算比較好的那一邊。LCP 剛好 2500ms 是「好」，剛好 4000ms 是「需要改善」，4001ms 才是「差」。web-vitals 的判斷寫成 value > 4000 ? 'poor' : value > 2500 ? 'needs-improvement' : 'good'。自己寫報表時用 >= 判斷，剛好卡在門檻的頁面就會被誤判成比較差的等級。

評等不是看單一次造訪，而是看分布，這就接上上一節的 p75。一個頁面（或整個網站）要三個指標的真實使用者資料 p75 都在「好」，才算通過。而且手機和桌機分開評估：手機的 CPU 慢好幾倍、網路也不穩，混在一起算，桌機的好成績會蓋掉手機的問題。Search Console 那封信特別寫「手機版」，就是這個原因。

三個指標裡，LCP 的「最大內容」最需要說清楚，因為後面要拆解它。能當 LCP 的元素有：<img>、<svg> 裡的 <image>、<video>（海報圖或第一個畫格）、用 url() 設背景圖的元素（漸層不算）、含文字的區塊元素。大小只算在可視範圍內的部分；縮放過的圖取「顯示大小」和「原始大小」裡比較小的。頁面還在載入時，候選元素會一直換：先出現標題文字，後來主視覺圖片載入，LCP 就換成圖片。使用者一點擊、捲動或按鍵，瀏覽器就停止更新 LCP。咖啡店首頁的 LCP 元素，多半就是最上面那張主視覺大圖。

診斷 LCP 時還會常看到兩個輔助指標。TTFB（Time to First Byte）是從開始導覽到收到 HTML 第一個位元組的時間，反映伺服器與網路；FCP（First Contentful Paint）是第一次畫出任何內容的時間。它們不是 Core Web Vitals，不參與評等，但 LCP 慢的時候，用它們判斷是不是一開始就慢。舊文章裡的 FID 為什麼不在表上，見課末〈補充與查表〉。

指標定清楚了，可是開場的矛盾還沒完全解開：同樣量 LCP，為什麼 Lighthouse 說很好、Search Console 說不及格？要回答這個，得先知道兩邊的數字各是怎麼來的。

為什麼 Lighthouse 98 分，Search Console 卻說不及格？

兩邊量的是同一組指標，差別在資料來源。效能資料有兩種來源，回答的是不同的問題。

實驗室資料（lab data）是在固定的裝置、網路條件下，由工具自己載入一次頁面量出來的。你在 MacBook 上跑的 Lighthouse 就是實驗室資料。它的好處是可重現、馬上有結果、有完整的時間軸可以一格一格看；缺點是它只代表「一種」情境。

真實使用者資料（field data）是從真實使用者的瀏覽器回報、匯總成分布的數字。它有兩種取得方式。第一種是 CrUX（Chrome UX Report），Google 從同意分享使用統計的 Chrome 使用者收集的公開資料集，Search Console 和 PageSpeed Insights 上半部的數字都來自它；CrUX API 與 PageSpeed Insights 顯示的是過去 28 天的滾動匯總，每天更新，分 PHONE、TABLET、DESKTOP。第二種是真實使用者監測（RUM, Real User Monitoring）：在自己的網站放一段程式，從每個使用者的瀏覽器收集指標，回報到自己的後端，這課最後會實作。

把兩種來源並排比較：

實驗室資料（lab data）真實使用者資料（field data）
工具Lighthouse、PageSpeed Insights 下半部、DevTools Performance 面板CrUX（Chrome UX Report）、PageSpeed Insights 上半部、Search Console、自己做的 RUM
怎麼量在固定的裝置、網路條件下載入一次頁面從真實使用者的瀏覽器回報，匯總成分布
優點可重現，馬上有結果，有完整的時間軸可以除錯；上線前就能量代表真實體驗；涵蓋各種裝置、網路、互動
缺點只是一種情境；沒有真實互動要有流量才有資料；看得到「慢」，不一定看得到「為什麼」
用途除錯、改版前後比較、CI 裡的回歸檢查判斷使用者實際過得好不好、設定目標

有了這張表，就能逐條解釋 98 分和不及格之間的落差：

  • 裝置與網路：Lighthouse 模擬一種中階手機與網路；你的使用者可能大多用更慢的手機。p75 代表的是比較慢的那四分之一，不是平均的那一個。
  • 快取與情境：實驗室每次都是乾淨的第一次載入；真實使用者有回訪（有快取，比較快），也有從廣告點進來、帶著追蹤參數、被 A/B 測試分到另一個版本的。
  • 頁面內容不同：登入後的頁面、購物車有 20 件商品、使用者在台灣但 CDN 節點在美國，實驗室都測不到。
  • 時間點：CLS 和 INP 會一直累積到使用者離開頁面。捲動到下面才載入的廣告把內容推開、第 5 分鐘點了一個很慢的篩選按鈕，這些都只有真實資料看得到。
  • 單次測量會波動：同一頁跑 Lighthouse 五次，分數可能差好幾分。比較改版前後要跑多次取中位數（第 21 課）。

還有一點容易被忽略：Lighthouse 的 98 分本身就不是 Core Web Vitals 評等。它是五個實驗室指標的加權分數，裡面沒有 INP。Lighthouse 的一般報告（導覽模式，PageSpeed Insights 跑的也是這個）只載入頁面、不點任何東西，沒有互動就量不到 INP；它改用 TBT（Total Blocking Time）當替代。TBT 把載入期間每個長任務超過 50ms 的部分加總，代表主執行緒被卡住多久。主執行緒常被卡住，互動時的輸入延遲就容易長，所以兩者相關；但 TBT 沒有真的點擊，不是同一件事。各指標的權重見課末〈補充與查表〉。

所以結論是：用真實資料決定「有沒有問題、問題多大」，用實驗室資料找「為什麼」和驗證修法。兩者不一致時，先相信真實資料，再想辦法讓實驗室條件接近使用者。咖啡店的情況就是這樣：Search Console 告訴你「手機版 LCP 有問題」，這是事實；但它只給一個 p75，不會告訴你慢在哪。CrUX 的涵蓋範圍也有限制（例如只收 Chrome 使用者、流量夠的公開頁面），細節見課末。

要找原因，就得在自己的電腦上把使用者的慢重現出來，而你的 MacBook 偏偏跑得太快。

怎麼在自己電腦上重現使用者的慢？

上一節的結論是「用實驗室找原因」，但前提是實驗室的條件要接近使用者，不然你量到的 1 秒跟使用者的 3 秒不是同一件事。Chrome DevTools 的 Performance 面板（第 18 課介紹過 DevTools 的基本操作）可以同時做三件事：顯示本機的 LCP、INP、CLS，跟 CrUX 的真實資料並排，以及把電腦降速模擬手機。步驟如下：

  1. 開 DevTools，切到 Performance 面板。一打開就會顯示這一頁目前的 LCP、CLS（live metrics），並標示好／需要改善／差。
  2. 在頁面上點按鈕、打字，INP 卡片會跟著更新；下方的 Interactions 分頁列出每次互動的元素與三段時間（輸入延遲、處理時間、呈現延遲，INP 那節會解釋），Layout shifts 分頁列出每次位移的元素與分數。
  3. 右側 Field data 按 Set up，可以拿 CrUX 的真實資料跟你本機的數字並排比較；裝置下拉選單選手機或桌機。
  4. 你的電腦比使用者快很多。用面板上的 CPU throttling（例如 4x slowdown）和網路節流（例如 Slow 4G）讓本機條件接近使用者，再重新量。
  5. 要看細節，按錄製並重新整理（或錄一段互動），錄完在 Insights 側欄找 LCP breakdown：它把 LCP 拆成下一節的四段。

第 3、4 步是關鍵：先看 Field data 知道使用者實際是幾秒，再調節流條件，直到本機數字接近那個值。這時候錄下來的時間軸，才代表使用者遇到的情況。

💡 實務上：接到「網站好慢」時先問清楚再開 DevTools
客服或店長轉來「很慢」的回報，先問：哪一頁、手機還是電腦、是打開很慢還是按了沒反應、從什麼時候開始。接著在 PageSpeed Insights 查那個網址的真實資料，確認是不是大多數人都慢，還是個案（例如對方網路不好）。要重現時，用 DevTools 的手機模擬加上 CPU 與網路節流，別用自己的 MacBook 全速跑完就回「我這邊很快」。團隊裡最好備一支中階 Android 實機，測出來的感受比模擬更接近一般使用者。

在降速後的錄製裡，LCP breakdown 會把咖啡店首頁的 LCP 拆成四段。每一段代表什麼、哪一段該先修，是下一節的事。

LCP 慢在哪一段？拆成四段找該先修的地方

LCP 是一個總時間，慢的原因可能完全不同：伺服器慢、圖片太晚開始下載、圖片太大，或圖片下載完了卻遲遲沒畫上去。只看總時間，就只能每一種都試試看。web.dev 的〈Optimize LCP〉（2025-03-31 更新）把 LCP 拆成四段，四段首尾相接、沒有重疊也沒有空隙，加起來剛好等於 LCP。看哪一段長，就知道該往哪個方向修：

每一段對應不同的原因和修法。下表左邊兩欄說明這段從哪裡到哪裡，右邊兩欄是太長時最常見的原因和對策，很多對策前面幾課已經教過：

段落從哪裡到哪裡太長的常見原因對策
① TTFB導覽開始 → 收到 HTML 第一個位元組伺服器每次都查資料庫產生頁面、沒有 CDN、多次重新導向快取 HTML、CDN、減少重新導向（後端課程會教）
② 資源載入延遲（resource load delay）TTFB → 開始下載 LCP 圖片首圖加了 loading="lazy"；圖片寫在 CSS 背景、要等 CSS 下載完才知道；圖片由 JS 插入（Vue 元件 mounted 後才出現）；排在一堆字型、腳本後面首圖用 <img> 寫在 HTML 裡、不要 lazy、加 fetchpriority="high"（第 14 課）；不在 HTML 裡的圖用 preload（第 21 課）
③ 資源載入時間（resource load duration）開始下載 → 下載完圖片太大（4 MB 的 JPEG）、格式舊、沒有依螢幕大小給不同尺寸AVIF／WebP、srcset／sizes（第 14 課）、CDN
④ 元素渲染延遲（element render delay）下載完 → 畫出來阻擋渲染（render-blocking）的 CSS／JS 還沒處理完；網頁字型還沒載入導致文字不顯示；主執行緒被長任務佔住減少阻擋渲染的資源、script 加 defer（第 1 課）、font-display（第 15 課）、拆長任務（第 19 課）

知道四段之後，下一個問題是先修哪一段。直覺是修最長的那段，但這樣會判斷錯：TTFB 本來就該占四成左右，它最長是正常的。判斷的方法是看哪一段比建議比例超出最多。

用咖啡店的數字算一次。假設降速錄製量到 LCP 2700ms，其中 TTFB 1200ms（44%）、資源載入延遲 800ms（30%）。TTFB 最長，但建議比例約 40%，只超出 4 個百分點；資源載入延遲建議在 10% 以內，實際 30%，超出 20 個百分點，這才是該先處理的。對照上表，它的常見原因是首圖加了 lazy、寫在 CSS 背景，或由 Vue 元件 mounted 後才插入。如果你照直覺去優化伺服器，花了一週把 TTFB 從 1200 壓到 1000，LCP 只少 200ms；把首圖改成寫在 HTML 裡、不要 lazy，資源載入延遲可能直接少掉大半。練習 2 會把這個判斷寫成程式。

這個拆解不只實驗室有。在真實使用者資料裡，web-vitals 的 attribution 版本會直接給你這四段：timeToFirstByte、resourceLoadDelay、resourceLoadDuration、elementRenderDelay，還有 LCP 元素的選擇器 target。也就是說，裝好 RUM 之後，不必每次都靠本機重現，也能知道使用者慢在哪一段。這課最後一節會裝。

💡 實務上：LCP 最常出事的是首頁主視覺
咖啡店官網的首頁大圖、電商的活動 banner，通常由行銷或小編從 CMS 上傳，換一張未壓縮的大圖，LCP 就默默變差，工程師完全沒改程式。所以修一次不夠，要讓流程擋住：上傳時自動轉檔縮圖，或交給圖片 CDN 依裝置產生尺寸。另一個常見坑是首頁用輪播元件，第一張圖被元件設成 lazy 或等 JS 才插入。fetchpriority="high" 只給真正的首屏主圖，每張都加等於都沒加。

LCP 有了方向，但店長的抱怨還有兩項沒處理：讀菜單時畫面會跳，按了按鈕沒反應。這兩件事不是「多久出現」的問題，量法也完全不同。先看畫面亂跳。

讀菜單時畫面亂跳，CLS 怎麼算分？

店長說的「讀到一半被擠走」，在指標裡叫版面位移（layout shift）：元素在兩個畫格之間改變了位置（不是大小），而且不是使用者預期的。它造成的問題不只是不舒服：使用者正要點「拿鐵」，上方突然插進一條橫幅，手指點到的變成「美式」。

要比較「跳得多嚴重」，每次位移要有一個分數。分數由兩個比例相乘：

  • 影響比例：被推動的元素「移動前與移動後的範圍聯集」占 viewport 的比例。被影響的畫面越多，分數越高。
  • 距離比例：移動最多的距離占 viewport 較長邊的比例。被推得越遠，分數越高。

相乘的意思是：一大塊內容只移動 1px，或一小塊內容被推很遠，分數都不會太高；一大塊內容被推很遠，才是真的嚴重。下面用咖啡店菜單頁的情況算一次，執行後看最後一行的分數：

一次就 0.078，離「好」的門檻 0.1 只差一點，再來一次就超過了。這種晚到的東西是 CLS 最常見的來源：圖片沒寫 width／height（第 14 課）、廣告或嵌入內容沒預留空間、晚到的橫幅插在內容上方、網頁字型載入後字寬改變（第 15 課）、用 top／height 做動畫。修法的共通點是讓瀏覽器在內容到之前就知道要留多少空間；動畫則改用 transform，它不會產生版面位移（第 17 課）。

單次分數會算了，但一個頁面的 CLS 不是把所有位移加起來。有兩個問題要先回答：哪些位移算數？算數的位移怎麼合成一個值？

先交代「紀錄」是什麼，下面會一直用到。瀏覽器每發生一次版面位移，就產生一筆效能紀錄（performance entry）：一個帶欄位的物件，例如這次位移的分數 value、發生時間 startTime、是否緊接在使用者輸入之後的 hadRecentInput。下一節的 INP 也一樣，瀏覽器每處理一個事件就產生一筆 Event Timing 紀錄，欄位有 startTime、processingStart、processingEnd、duration、interactionId。指標就是從這些紀錄算出來的；這課最後一節會用 PerformanceObserver 和 web-vitals 訂閱它們。

哪些位移算數：使用者自己造成、預期會發生的位移不算。離散的輸入（點擊、觸控、按鍵）之後 500ms 內發生的位移，瀏覽器會在紀錄上標 hadRecentInput: true，不計入。所以使用者點「載入更多」後列表往下長，不算。但捲動、拖曳、縮放不算輸入：使用者往下捲動時，上方晚到的廣告把內容推開，照樣計入，這正是 CLS 要抓的問題。

怎麼合成一個值：位移通常成群出現，例如幾張圖片接連載入，一秒內跳了三次。CLS 把位移分組成 session window：跟前一次位移相隔不到 1 秒就屬於同一組，但一組從第一次位移起最長 5 秒。每組裡的分數相加，CLS 取分數最高的那一組，不是整頁全部相加。如果全部相加，使用者在單頁應用（SPA）裡停留一小時，零星的小位移一直累積，CLS 一定會不及格，這就不再反映「有一段時間畫面很不穩」這件事。下圖是一個例子：

按了沒反應，INP 怎麼量？

店長說「按了加入購物車要等一下才有反應」。這種慢跟 LCP 不同：頁面早就載入完了，慢的是某一次互動。INP 量的就是這個：使用者點擊、觸控或按鍵，到畫面出現下一次更新，中間隔了多久。

要知道怎麼修，先要知道這段時間花在哪裡。使用者點了「加入購物車」，從手指離開螢幕到看見購物車數字變了，中間經過三段：

三段的成因不同，修法也不同：

  • 輸入延遲（input delay）長：點的當下主執行緒正在跑別的長任務（第三方腳本、一大包 JS 正在解析），事件要排隊。這就是第 19 課講的「主執行緒一次只做一件事」。對策是拆長任務、延後不急的腳本（第 19 課）。
  • 處理時間（processing duration）長：你的事件處理函式本身太慢，例如點一下就同步重算 600 個品項。先更新畫面上看得到的回饋，重活延後做。
  • 呈現延遲（presentation delay）長：處理完之後畫面更新太貴，例如一次改了巨大的 DOM、觸發大範圍 layout。

接著要定義什麼算「一次互動」。只有點擊、觸控、按鍵算互動；滑鼠移過（hover）和捲動不算。一次點擊會觸發好幾個事件（pointerdown、pointerup、click），它們共用同一個 interactionId，算一次互動，延遲取其中 duration 最大的那個事件。

最後一個問題：使用者在菜單頁點了 30 次，整頁的 INP 是哪一次？web.dev 的規則是「每 50 次互動，忽略一次最高的」。大部分頁面的互動少於 50 次，INP 就是最慢的那一次；互動很多的頁面（例如在表單上打字打了 300 次），偶發一次卡頓不該代表整體，所以略過最高的幾次。web-vitals 的實作是把互動依延遲由大到小排序，取第 min(互動數 − 1, floor(互動數 ÷ 50)) 個（從 0 起算）。使用者完全沒互動時，沒有 INP。練習 4 會照這個規則寫出 inp()。

到這裡，店長的三種抱怨都有了指標和拆解方法。但目前的數字不是來自本機重現，就是來自 CrUX 的 28 天匯總：改版後要等好幾週才看得到變化，也看不到每次慢是卡在哪個元素。要在改版隔天就知道有沒有變好，得自己收使用者的數字。

怎麼收到自己使用者的數字？用 web-vitals 做 RUM

自己收真實使用者資料，就是前面提過的 RUM。CLS 那節說過，瀏覽器會為每次版面位移、每個事件產生效能紀錄；訂閱這些紀錄的 API 叫 PerformanceObserver：你指定要哪一種紀錄，有新的 LCP 候選、版面位移、事件時間時它就通知你。但直接用它寫，要自己處理很多邊界情況：分頁切到背景、從返回快取（bfcache）回來、session window 與 INP 的挑選規則。bfcache 是使用者按上一頁時，瀏覽器直接從記憶體還原整個頁面、不重新載入，這時指標要重新計算。web-vitals 函式庫（目前 6.2.3）把這些都處理好了，前幾節的 CLS 分組與 INP 挑選規則，就是它在背後做的事。

在咖啡店的 Vue 專案裡安裝 npm install web-vitals，在 main.ts 加上：

import {
  onCLS, onINP, onLCP,
  type CLSMetricWithAttribution, type INPMetricWithAttribution, type LCPMetricWithAttribution,
} from 'web-vitals/attribution'

// 三種指標的型別用 name 區分，m.name === 'LCP' 之後 TypeScript 就知道 attribution 的欄位
type Vital = LCPMetricWithAttribution | INPMetricWithAttribution | CLSMetricWithAttribution

const queue = new Set<Vital>()

function addToQueue(metric: Vital) {
  queue.add(metric)
}

function flushQueue() {
  if (queue.size === 0) return
  const body = JSON.stringify([...queue].map(m => ({
    name: m.name,                // 'LCP' | 'INP' | 'CLS'
    value: m.value,
    rating: m.rating,            // 'good' | 'needs-improvement' | 'poor'
    id: m.id,                    // 同一次載入的同一個指標，id 相同
    page: location.pathname,     // 只送路徑，不送 query string（可能有個資）
    device: matchMedia('(max-width: 767px)').matches ? 'mobile' : 'desktop',
    // attribution：指出「慢在哪」
    target: m.name === 'LCP' ? m.attribution.target
      : m.name === 'INP' ? m.attribution.interactionTarget
      : m.attribution.largestShiftTarget,
  })))
  // sendBeacon：頁面正在關閉也送得出去
  navigator.sendBeacon('/api/vitals', body)
  queue.clear()
}

onCLS(addToQueue)
onINP(addToQueue)
onLCP(addToQueue)

// 切到背景或關閉分頁時一次送出（比 beforeunload、unload 可靠，手機上尤其如此）
addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flushQueue()
})

這段程式分成三部分：用 onCLS／onINP／onLCP 訂閱指標，把回報的值放進佇列，最後在頁面切到背景時一次送到後端。以下逐一說明為什麼這樣寫。

為什麼從 web-vitals/attribution 匯入：attribution 版本多給「慢在哪」的資訊：LCP 的四段與元素、INP 的 inputDelay／processingDuration／presentationDelay 與互動的元素、CLS 位移最大的元素。檔案比標準版大一些，換來可以行動的資訊。前面比較兩種資料來源時說過「真實資料看得到慢，不一定看得到為什麼」，attribution 補的就是這一塊。程式裡送出的 target，就是三種指標各自的元素。型別上的寫法見課末〈補充與查表〉。

為什麼要等 visibilitychange 才送：回呼不會在頁面載入時立刻被呼叫。LCP 要等使用者第一次互動或切到背景才確定；CLS、INP 會一直累積，每次頁面變成 hidden 時回報目前的值，所以同一次載入可能回報好幾次。回報的 id 相同，後端以最後一次為準（或照 README 改送 delta 再加總）。使用者完全沒互動，就沒有 INP。所以程式先收進佇列，等頁面切到背景或關閉時，用 sendBeacon 一次送出；sendBeacon 在頁面正在關閉時也送得出去，visibilitychange 也比 beforeunload、unload 可靠，手機上尤其如此。

為什麼只在 main.ts 呼叫一次：每次呼叫 onCLS／onINP／onLCP 都會建立新的 observer 與事件監聽。放在元件的 onMounted 裡，元件每掛載一次就多註冊一組，同一個指標會被重複回報。

資料送到後端之後，就是練習 1 的工作：依指標、裝置、頁面類型（首頁、菜單頁、結帳頁）分組算 p75。不要只看全站一個數字：結帳頁很慢會被大量的首頁造訪蓋掉。每次載入只送幾筆，資料量不大；流量大時可以只收一部分使用者（例如 10%），但要在載入時決定一次，同一次載入的三個指標要一起收或一起不收，不然 p75 會偏。

瀏覽器支援：web-vitals 6.2.3 的 README 列出 onLCP、onINP 支援 Chromium、Firefox、Safari；LCP 與 INP 背後的 API（largest-contentful-paint、event-timing）在 2025-12-12 Safari 26.2 支援後成為 Baseline newly available，也就是主流瀏覽器的最新版都已支援。onCLS 背後的 Layout Instability API 只有 Chromium 支援，所以你收到的 CLS 只代表 Chrome、Edge、Android 使用者；iPhone 使用者的版面跳動看不到，要靠實驗室在 Safari 實測。另外這些 API 看不到 <iframe> 裡的內容，CrUX 則會算進去，兩邊數字可能因此不同。
💡 實務上：先用現成服務，有需要再自己收
小團隊通常先用已經在用的監控服務（例如 Sentry）或託管平台內建的分析，不必自己寫後端和報表。自己收的好處是能跟自家資料對起來，例如依會員等級、A/B 測試版本、門市分組看 p75。自建的 /api/vitals 是公開端點，任何人都能亂送：後端要檢查欄位與數值範圍、限制請求頻率，資料也要設保存期限。導入前跟負責隱私或法務的人確認回報內容，只送路徑、不送使用者識別資料。

RUM 裝好之後，咖啡店官網終於有自己的數字。但這只是開始：修好一次之後，要怎麼確保它不會慢回去？

量到之後：怎麼讓數字不再變差？

一次性的「效能優化專案」做完兩個月，新功能、新的第三方腳本、行銷換上的大圖又會把數字拉回去。資深工程師的做法是把效能當成持續監控的品質指標，用這課的工具串成一個循環：

  1. 先有基線：上 RUM，收兩週，按裝置與頁面類型算出現在的 p75。沒有基線就不知道改了有沒有用。
  2. 訂目標：例如「手機 p75 LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1，以 28 天計」。這就是 SLO（服務水準目標）的概念（DevOps 課第 22 課）。
  3. 找最大的問題：用 attribution 找出最常拖慢的元素與段落，用實驗室重現、修正、驗證。
  4. 每次改版比較：上線後看 RUM 的每日 p75 有沒有變差；在 CI 裡跑實驗室測試擋下明顯的退步（第 21 課）。

回到店長。你現在可以用數字回覆，而不是「我這邊很快」：「手機版首頁的 p75 LCP 是 3.4 秒（Search Console／RUM），73% 的造訪在 2.5 秒內；本機降速重現約 2.9 秒，主要卡在首圖排隊太晚開始下載（資源載入延遲占 30%），預估修完可以降到 2.4 秒」。跟主管或 PM 溝通時也用這套語言，比「網站有點慢，想做優化」好推動得多。

至於「首圖排隊太晚」具體怎麼修、怎麼在 CI 擋住退步，是下一課的內容。

練習

練習 1：把 RUM 收到的原始樣本變成報表。寫三個函式：

  • p75(values)：用 nearest-rank（排序後取第 ceil(0.75 × n) 個）算第 75 百分位；空陣列要丟錯。不能修改傳進來的陣列（後端還要拿同一份資料算別的）。
  • assess(metric, value)：依官方門檻回傳 'good'、'needs-improvement' 或 'poor'，等於門檻值時要判對邊。
  • summarize(samples)：依裝置（mobile、desktop）與指標分組，回傳每組的 p75 與評等；沒有樣本的指標不要出現在結果裡。

練習 2：RUM 回報了一次載入的 LCP 時間點（毫秒，都是從導覽開始算）。寫 lcpBreakdown(t) 回傳四段的毫秒數 parts、各占 LCP 的比例 share（四個加起來是 1），以及 lcp（就是 renderTime）。LCP 是文字時沒有 requestStart、responseEnd，資源的兩段都是 0。

再寫 diagnose(b) 回傳最該先處理的那一段對應的建議：ttfb → 'server'、loadDelay → 'discovery'（圖片太晚被發現）、loadDuration → 'size'（圖片太大）、renderDelay → 'render'（被 CSS／JS／字型擋住）。「最該先處理」的定義是 實際占比 − 建議占比（TARGET）最大的那一段。

練習 3：寫 cls(entries)，從一次瀏覽的版面位移紀錄（依 time 由小到大排好）算出 CLS：

  • hadRecentInput 為 true 的紀錄完全略過，也不影響分組。
  • 跟上一筆（有計入的）位移相隔 < 1000ms，而且跟這組第一筆相隔 < 5000ms，就加進同一組；否則開一個新組。
  • 回傳分數最高的那一組的總和；沒有任何計入的位移時回傳 0。

練習 4：寫 inp(entries)，從 Event Timing 的紀錄算出 INP 並拆解最差的那次互動：

  • interactionId 是 0 的紀錄不是互動（例如 mouseover），略過。
  • 同一個 interactionId 的多筆紀錄是同一次互動，用其中 duration 最大的那筆代表。
  • 互動依 duration 由大到小排序，取第 min(互動數 − 1, floor(互動數 ÷ 50)) 個（從 0 起算）。
  • 回傳 value（就是那筆的 duration）、interactionId，以及三段：inputDelay、processing、presentationDelay，三段加起來等於 value。沒有任何互動時回傳 null。

練習 5：咖啡店官網跑 Lighthouse 拿到 100 分，但 Search Console 的 Core Web Vitals 報告顯示手機版 LCP「差」。最可能的解釋是？

✓ 兩種資料回答不同的問題：實驗室用來除錯與比較改版，真實資料（CrUX）代表使用者實際的體驗，以它決定有沒有問題。a 把除錯工具當成真實體驗；c 的 Lighthouse 分數不是 Core Web Vitals 評估，Google 評估看的是真實資料；d 錯在 LCP 占 Lighthouse 分數的 25%。

練習 6：為什麼 Lighthouse 的一般報告裡看不到 INP？

✓ 沒有點擊、按鍵就沒有 INP。實驗室想看 INP，要自己在 DevTools Performance 面板操作頁面；正式的數字靠 RUM 或 CrUX。a 剛好相反，INP 在 2024 年取代了 FID；b 錯，INP 背後的 Event Timing API 在 Chromium、Firefox、Safari 都支援；d 錯，CLS 是版面位移，跟互動延遲無關。

練習 7：菜單頁上使用者點了「載入更多」，300ms 後新的品項出現，把頁尾往下推。另外，使用者往下捲動時，上方晚到的廣告把正在讀的段落推走。哪些會算進 CLS？

✓ 點擊、觸控、按鍵是離散輸入，之後 500ms 內的位移是使用者預期的，不計入。捲動、拖曳不算輸入，捲動中被廣告推開正是 CLS 要抓的問題。c、a 忽略了 500ms 的排除規則（而且是否計入跟位移大小無關）；d 把捲動也當成輸入。

常見錯誤

  • 只看 Lighthouse 分數：分數每次跑都會波動，也不等於真實體驗。用真實資料的 p75 判斷有沒有問題，用實驗室找原因。
  • 用平均值：平均會被極端值拉走，描述的是不存在的使用者。用百分位數，Core Web Vitals 看 p75。
  • 手機與桌機混在一起：桌機的好成績會蓋掉手機的問題。Google 分開評估，你的報表也要分開。
  • 只在載入時測 CLS：捲動、互動之後的位移也算。DevTools 的 Layout shifts 分頁和 RUM 都要看整個瀏覽期間。
  • 看到 TTFB 最長就去修伺服器：TTFB 本來就該占約四成。找的是「比建議比例超出最多」的那一段。
  • 在每個元件裡呼叫 onLCP／onINP／onCLS：每呼叫一次就多一組 observer。在 main.ts 呼叫一次，用 visibilitychange 回報。
  • 以為 RUM 的 CLS 代表所有使用者：Layout Instability API 只有 Chromium 支援，Safari 使用者的 CLS 收不到。

補充與查表

FID 已經不是 Core Web Vital

INP 在 2024 年取代了 FID（First Input Delay，首次輸入延遲）。FID 只量「第一次」互動「開始處理前」等了多久；INP 量整個瀏覽期間的每一次互動，而且一直算到畫面更新為止。舊文章、舊工具還會提到 FID，看到就知道它已經不是 Core Web Vital。

CrUX 收哪些資料

CrUX 的來源是同意分享使用統計的 Chrome 使用者（桌機 Chrome 與 Android Chrome；iOS 上的 Chrome、其他 Chromium 瀏覽器如 Edge 不算），只收公開、可被索引、流量夠的頁面。因為是過去 28 天的滾動匯總，改版後要等幾週，CrUX 才會完全反映出來；登入後的頁面通常沒有 CrUX 資料，只能靠自己的 RUM。

Lighthouse 分數怎麼來（查表用，不用背）

Lighthouse 的效能分數（0–100）是五個實驗室指標的加權平均（Lighthouse 10 起的權重，目前最新版 13.6.0 沿用）：

指標權重說明
TBT（Total Blocking Time）30%FCP 之後，所有長任務超過 50ms 的部分加總；主執行緒被卡住多久，INP 的實驗室替代指標
LCP25%
CLS25%只量載入期間的位移
FCP10%
Speed Index10%畫面內容填滿的速度

實驗室想看 INP，要自己在 DevTools Performance 面板操作頁面（見〈怎麼在自己電腦上重現使用者的慢？〉）。

web-vitals 的 session window 邊界條件

web-vitals 6.2.3 的原始碼裡，判斷「同一組」的條件是：這次位移的時間跟上一次相差 < 1000，而且跟這組第一次位移相差 < 5000（兩個都是嚴格小於）；被標成 hadRecentInput 的紀錄直接略過，不影響分組。

web-vitals 程式的型別與其他管道

  • 型別：從 web-vitals/attribution 匯入的基本型別 Metric 沒有 attribution 欄位，要用 LCPMetricWithAttribution 這類型別組成聯集，m.name 判斷之後才能讀各自的 attribution（已用 6.2.3 的型別檔編譯確認）。
  • 跟錯誤監控共用管道：Vue 課第 21 課的前端錯誤回報也是同樣的模式；Sentry 這類服務也能收 Web Vitals。

小結

  • 「很慢」先拆成使用者感受得到的指標，再用分布匯總：看 p75，不看平均；排查時再看 p90、p95。
  • Core Web Vitals：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1 為「好」；等於門檻算好；以真實使用者的 p75 評估，手機和桌機分開。
  • 實驗室資料（Lighthouse、DevTools）可重現、能除錯，但只是一種情境、沒有互動；真實資料（CrUX、RUM）代表使用者體驗，CrUX 是過去 28 天的 Chrome 使用者。用真實資料判斷有沒有問題，用實驗室找原因；本機重現要先降速。
  • LCP 拆成 TTFB、資源載入延遲、資源載入時間、元素渲染延遲，看哪一段超出建議比例最多。
  • CLS 取分數最高的 session window（間隔 < 1 秒、最長 5 秒），點擊、按鍵後 500ms 內的位移不算，捲動不算輸入。
  • INP 是互動延遲的高百分位：每 50 次互動忽略一次最高的；拆成輸入延遲、處理時間、呈現延遲。
  • 用 web-vitals 的 attribution 版本收 RUM，visibilitychange 時用 sendBeacon 送出；後端依裝置、頁面類型算 p75，持續追蹤。
