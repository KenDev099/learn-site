階段 5：SEO 與內容交付 · 第 22 課

SEO 基礎：搜尋意圖、title、description、標題結構與內部連結

豆留咖啡的官網上線三個月，老闆在 Google 搜尋「豆留咖啡 菜單」，第一筆結果的標題只寫著「豆留咖啡」，下面的說明是頁尾的版權宣告；點進去是首頁，不是菜單。他把菜單頁的網址貼到常客的 LINE 群組，跳出來的預覽卡片沒有圖。你打開原始碼：每一頁的 title 都是「豆留咖啡」、沒有 description、菜單頁的 h1 是店名、首頁連到菜單的連結寫「點這裡」。網站找得到，但搜尋引擎搞不清楚每一頁在講什麼。前任外包還說他們「做過 SEO」。

這一課的任務是把這個網站修好：讓搜「豆留咖啡 菜單」的人落在菜單頁、點進咖啡菜單看得到品項與價格，搜尋結果的那兩行字說得出這頁有什麼，貼到 LINE 的卡片有圖，並把外包留下的違規做法清掉。這類工作叫 SEO（Search Engine Optimization，搜尋引擎最佳化）：讓搜尋引擎能找到、理解並適當呈現網站。它不是一組祕技，大部分工作就是把 HTML 寫清楚。這一課處理「每一頁的內容與標記」；伺服器、路由那一側的設定是下一課。

這課的路線：
  1. 搜尋引擎怎麼看到一頁？Google 從找到網頁到放進搜尋結果分三步，豆留咖啡卡在哪一步，SEO 能控制什麼、不能跟老闆承諾什麼。
  2. 搜「豆留咖啡 菜單」的人該落在哪一頁？先依搜尋意圖決定由哪一頁回答，修 HTML 才有對象。
  3. 搜尋結果那兩行從哪來？title 與 description 怎麼寫，Google 為什麼會改掉你寫的；接著讓頁面本身的 h1、標題與 alt 跟 title 說同一件事。
  4. 爬蟲找得到菜單頁嗎？內部連結、錨點文字、麵包屑與網址。
  5. LINE 卡片為什麼沒圖、外包留下的東西要不要留？Open Graph 與 Google 的 spam 政策。
這課會用到：
  • 第 1 課的 head 與相對網址：<head> 放 title、meta 這類給瀏覽器與搜尋引擎的資訊；相對網址以目前頁面的網址為基準解析成完整網址。
  • 第 2 課的標題階層與連結文字：h1～h6 依內容層級排、不跳級；連結文字要說出點了會到哪裡。
  • 第 3 課的替代文字（alt）：圖片看不到時代替它的文字，螢幕閱讀器會念出來。

搜尋引擎怎麼看到一頁？

要知道豆留咖啡壞在哪，得先知道 Google 怎麼處理一個網頁。它把工作分成三個階段，每個階段需要的東西不同。

第一段是爬取（crawling）。網路上沒有「所有網頁的登記處」，Google 必須自己去找。負責找的是一支叫 Googlebot 的爬蟲程式：它從已知的頁面出發，跟著頁面上的連結找到新網址，也會讀網站主動提交的網址清單（sitemap，第 23 課），然後把頁面下載回去。這代表一個頁面如果沒有任何連結指向它、也不在 sitemap 裡，Googlebot 很可能根本不知道它存在。

第二段是索引（indexing）。Google 分析下載到的內容：文字、title、標題、圖片的 alt、連結，判斷這一頁在講什麼，然後存進一個巨大的資料庫，這個資料庫就叫索引（index）。這一段 Google 主要靠 HTML 標記理解結構，不會只憑樣式去猜哪段是標題；HTML 沒寫清楚的主題，它只能猜。

第三段是排序與呈現（serving）。使用者搜尋時，Google 從索引裡挑出最相關的頁面排序，再替每一頁組出一筆搜尋結果：一行可以點的標題、幾行說明文字。

用這三段回頭看豆留咖啡。搜尋「豆留咖啡」找得到官網，代表 Googlebot 至少爬到了首頁、也收進了索引，第一段沒有全壞。問題出在第二、三段：每一頁的 title 都是「豆留咖啡」、菜單頁的 h1 也是店名，Google 從 HTML 讀不出哪一頁在講菜單，只好把首頁當答案；組搜尋結果時找不到描述這一頁的文字，就從頁面上挑了一段，挑到頁尾的版權宣告。首頁連到菜單的連結又寫「點這裡」，連「菜單在哪一頁」這個線索都沒給。所以這次要修的幾乎都是 HTML 本身。

動手之前，先把 SEO 能控制和不能控制的部分分清楚。老闆接下來一定會問「修完會不會排第一」，你要能說清楚哪些事你負責、哪些事沒有人能保證：

能控制不能控制
內容是否回答使用者的問題排名第幾。Google 官方說它不保證會爬取、索引或呈現任何頁面
title、description、標題、alt 寫得清不清楚搜尋結果最後顯示的標題與摘要（Google 可能改寫）
頁面之間有沒有連結、網址好不好讀多快被收錄、多久重新爬一次
伺服器回應的狀態碼、robots、canonical（第 23 課）付錢買排名：Google 不收費提高自然排名，聲稱能「保證第一頁」的都不可信

所以 SEO 的驗收標準不是「排第一」，而是可以檢查的事：每一頁的 title 都不一樣、連結都能爬、重要頁面都有被索引。前兩項看原始碼就能確認；最後一項要問 Google 本人。Google 免費提供一個給網站管理者的後台，叫 Search Console，在裡面可以看到哪些網址被索引、每一頁被哪些字詞搜尋到（第 25 課會實際操作）。

知道問題在 HTML 之後，還不能直接動手改 title。得先決定一件事：搜「豆留咖啡 菜單」的人，到底該落在哪一頁？

搜「豆留咖啡 菜單」的人該落在哪一頁？

使用者打進搜尋框的字，背後都有一件想完成的事，這件事叫搜尋意圖（search intent）。打「豆留咖啡 菜單」的人，已經知道這家店，想直接看到菜單和價格；他不想讀品牌故事，也不想先看門市地址。Google 排序時判斷的就是「哪一頁最能完成這件事」，所以網站上必須有一頁明確在做這件事。

同一個網站會遇到好幾種意圖，就算字面上都有「咖啡」，要的東西完全不同。豆留咖啡的網站除了菜單，還有豆子介紹、線上商店、門市頁，它們各自回答不同的搜尋：

意圖搜尋的例子使用者要什麼豆留咖啡用哪一頁回答
找資訊（informational）耶加雪菲 風味學到東西：產地、風味、怎麼沖/guide/yirgacheffe/：豆子介紹文章
找特定網站（navigational）豆留咖啡 菜單直接到某一頁/menu/：菜單頁，title 要有「菜單」
要交易（transactional）咖啡豆 訂購現在就買/shop/beans/：商品頁，價格、規格、購買按鈕
找附近店家（local）大安區 手沖咖啡地址、營業時間、怎麼去/stores/daan/：門市頁，地址、營業時間、照片

從這張表推出規劃頁面的第一條原則：一頁回答一個需求。豆留咖啡舊版的首頁同時塞了菜單、門市、品牌故事、訂購，每一樣都講一點。搜「豆留咖啡 菜單」的人點進首頁，還要自己往下找；Google 看這一頁，也只看得出「這是豆留咖啡的網站」，看不出「這是菜單」。把菜單獨立成一頁，title、h1、內容都在講菜單，這一頁才會是那個搜尋最好的答案。這次的修法是：/menu/ 是菜單總覽，回答「豆留咖啡 菜單」；咖啡另外獨立一頁 /menu/coffee/。咖啡要獨立，是因為它品項最多，而且「豆留咖啡 拿鐵 價格」這類更具體的搜尋，需要一頁專門列出咖啡品項與價格來回答；總覽頁只要帶出各分類、連到子頁。咖啡菜單頁也是使用者最常點進去、內容最完整的子頁，後面幾節與練習都以它為示範對象。

第二條原則是反過來的：同一個需求不要做好幾頁。假設網站上有「咖啡菜單」「飲品菜單」「本店菜單」三頁，內容差不多。Google 面對同一個搜尋，要在三頁之間挑一頁，連到菜單的外部連結和使用者的點擊也被拆成三份，結果每一頁都不夠強。這種自己的頁面互搶同一個搜尋的狀況，業界俗稱關鍵字自相殘殺（keyword cannibalization）。解法是合併成一頁，其他網址用重新導向或 canonical 指過去。重新導向是伺服器收到舊網址的請求時，直接把使用者和爬蟲轉到新網址；canonical 是在 head 裡寫 <link rel="canonical" href="…">，告訴 Google「這幾個網址內容一樣，以這一個為正式網址」。兩者的細節都在第 23 課。

怎麼知道使用者實際搜什麼？網站上線後，看 Search Console 的「成效」報表，裡面列出每一頁被哪些查詢字詞看到、點擊（第 25 課）。上線前沒有資料，就自己搜一次：Google 目前對這個查詢給的是文章、商品頁還是地圖，那就是 Google 判斷的意圖，你的頁面類型要對得上。

💡 實務上：開新頁之前，先問「它回答哪一個搜尋」
行銷常會提「做一頁『台北咖啡推薦』的活動頁」。動手前先問兩件事：這個搜尋背後的人要什麼（找資訊、要買、找門市）？站上是不是已經有一頁在回答它？已經有的話，改善那一頁通常比再開一頁好，否則就是自己跟自己搶。活動結束的頁面也要決定去留：留著、合併，還是導向到常設頁，不要讓它變成沒有連結指向、也沒人維護的頁面。

負責回答的頁面決定了，本課接下來以 /menu/coffee/ 為修改對象。但這頁在搜尋結果裡現在只顯示「豆留咖啡」和一段版權宣告，使用者根本不會點。那兩行字是從哪裡來的？

搜尋結果那兩行從哪來？

先看一筆修好之後的搜尋結果長什麼樣子，認識每一塊的名字：

搜尋結果裡那行可以點的大字，Google 叫它 title 連結（title link），通常取自頁面的 <title>。下面的說明文字叫摘要（snippet），可能取自 meta description，也可能直接從頁面內容挑一段。注意圖說那句話：這兩行都是 Google「參考」你的 HTML 產生的，不是照抄。所以這一節要做兩件事：把 title 和 description 寫好，再弄清楚 Google 在什麼情況下不採用你寫的。

title：每一頁都要說出自己是什麼

第 1 課講過 title 的基本寫法：主題在前、品牌在後。這裡從搜尋的角度看，title 要同時讓兩種人分辨這一頁：還在搜尋結果裡挑的人，和已經開了十個分頁、要從分頁標籤找回來的人。豆留咖啡每頁都叫「豆留咖啡」，這兩種人都分不出來。下面是幾種常見的寫法，最後一列才是這次要用的：

寫法問題
豆留咖啡每一頁都一樣：搜尋結果、分頁、書籤裡都分不出是哪一頁
首頁、菜單、Document太模糊，沒有說是誰家的什麼
咖啡 台北咖啡 咖啡店 好喝咖啡｜豆留咖啡關鍵字堆砌（keyword stuffing），違反 spam 政策，使用者也看得出來
咖啡菜單｜豆留咖啡、甜點菜單｜豆留咖啡、輕食菜單｜豆留咖啡只差一個詞的模板（boilerplate），Google 可能自己加字區分
咖啡菜單：手沖、拿鐵與季節特調｜豆留咖啡描述這一頁、跟其他頁不同、品牌在最後用分隔符號隔開

第三列的「關鍵字堆砌」是把想被搜到的詞一個個排進去，最後一節講 spam 政策時會再看到它。第四列的問題比較隱蔽：每一頁確實不同，但只差一個詞，看起來像同一份模板套出來的，Google 會覺得資訊不夠，自己補字來區分。

長度方面，Google 文件寫明 title 沒有長度上限，但顯示時會依裝置寬度截斷。實務上把最重要的詞放前面、中文控制在 30 字左右，這樣真的被截斷時，損失的只是最後的品牌名。

Google 為什麼會改掉你寫的 title？

title 寫好了，Google 也不一定照用。它產生 title 連結時，會參考好幾個來源：<title>、頁面上最顯眼的標題（通常是 h1）、og:title（本課後面會寫到）、別人連到這頁時用的連結文字。當 <title> 看起來不能代表這一頁，Google 就改用其他來源。文件列出的常見原因：

  • title 只剩一半，例如只有「｜豆留咖啡」
  • title 過時，例如還寫著「2025 秋季菜單」但頁面已經換季
  • title 跟頁面內容不符
  • 整個網站的 title 幾乎一樣（micro-boilerplate）
  • 頁面上有好幾個一樣大的標題，看不出哪一個是主標題
  • title 的語言或文字跟內容不同（中文頁面寫英文 title）

豆留咖啡舊版中了第四條：全站都叫「豆留咖啡」，這個 title 對 Google 沒有區分力。反過來說，title 跟 h1 意思一致、每頁不同、內容準確，Google 就沒有理由改它。「一致」不是一字不差：h1「咖啡菜單」給已經在頁面上的人看，不用再報店名；title 多了補充說明和品牌，給還在搜尋結果裡挑的人看。

meta description：摘要為什麼挑到版權宣告？

豆留咖啡的摘要會是頁尾的版權宣告，原因是頁面沒有提供任何描述，Google 只能從頁面內容自己挑。meta description 是寫在 head 裡、用一兩句話描述這一頁的文字，給 Google 一個比「從內文隨便挑」更好的選項：

<meta name="description" content="豆留咖啡共 6 款咖啡：美式、拿鐵、卡布奇諾、耶加雪菲等手沖單品與季節限定的桂花拿鐵，每杯 80～150 元。可以內用、外帶，也能線上點餐、到店取餐。">

先釐清它的作用範圍：description 不影響排名。Google 在官方部落格說明過，有時會用 description 當摘要，但排名不使用它。它影響的是使用者看到摘要後點不點：同樣排在第三名，摘要寫著「6 款咖啡，每杯 80～150 元，可線上點餐」的那一筆，比寫著「© 豆留咖啡 版權所有」的更容易被點。

其次，Google 不保證採用。摘要主要從頁面內容自動產生，而且會依搜尋字詞不同而不同：有人搜「豆留咖啡 拿鐵 價格」，Google 可能直接挑出內文裡「拿鐵 110 元」那一行。只有在 description 比頁面內容更能準確描述這一頁時，它才可能被拿來用。所以寫 description 的目標是「讓它比內文更適合當摘要」。

怎麼讓它更適合？Google 建議每頁不同、寫具體資訊，例如價格、數量、日期，不要寫關鍵字清單；所有頁面共用同一段 description 沒有幫助，跟每頁同一個 title 是一樣的問題。上面那段寫出了品項數、代表品項、價格範圍和點餐方式，都是使用者決定要不要點的資訊。另外要只寫頁面上有的東西：description 寫「買一送一」，點進來找不到，使用者會馬上離開，也可能被當成誤導。長度跟 title 一樣沒有上限、會被截斷，中文寫 50～120 字、重點放前面是常見的範圍。

description 之外還有兩個相關的小工具（控制某段內容不進摘要、早已不用的 keywords meta），細節見課末「補充與查表」。

💡 實務上：title 和 description 通常是從資料「組」出來的
咖啡店有幾十個商品頁，不會一頁一頁手寫，而是用模板組：`${商品名}：${分類}｜豆留咖啡`，description 從商品介紹、價格組成。要考量的是欄位空白時怎麼辦（不要組出「：｜豆留咖啡」這種半截 title）、組出來會不會每頁只差一個字。Vue 的 SPA 只有一份 index.html，換路由時 title 和 description 不會自己變，每個路由都要自己設定，而且要確認搜尋引擎拿到的 HTML 裡有它們（完整做法在第 25 課）。資深工程師上線前會抽幾頁檢視原始碼，確認每一個可以被搜尋到的網址，都有自己的 title 和 description。

現在咖啡菜單頁的 title 寫著「咖啡菜單：手沖、拿鐵與季節特調」，但頁面上最大的 h1 還是「豆留咖啡」。title 說這頁是菜單，頁面本身卻說這頁是店名，這正是 Google 改寫 title 的理由之一。下一步要讓頁面內容跟 title 說同一件事。

頁面本身說得出它在講什麼嗎？

索引那一段，Google 讀的是 HTML 結構。它跟螢幕閱讀器的使用者處境一樣，是「不能只靠畫面設計理解結構」的讀者：你用 48px 粗體做出來的大標，如果在 HTML 裡只是 <div>，它就不知道那是標題。所以頁面能不能被讀懂，取決於 HTML 有沒有把結構寫出來。

最先要改的是 h1：它寫頁面主題。Google 的 title 文件建議讓主標題成為頁面上最顯眼的文字，例如第一個看得見的 h1。咖啡菜單頁的 h1 要是「咖啡菜單」，不是每一頁都一樣的店名；店名留在頁首當品牌標示就好。改完之後，title「咖啡菜單：手沖、拿鐵與季節特調｜豆留咖啡」和 h1「咖啡菜單」意思一致，上一節說的改寫理由就消失了。

h1 下面的標題階層照第 2 課的規則：h2 是分類（經典咖啡、手沖單品），h3 是品項，不跳級。這裡要說清楚一個常見的誤會：Google 的 SEO Starter Guide 寫明，從搜尋的角度，標題的數量和順序不影響排名。不跳級是為了螢幕閱讀器使用者（他們靠標題清單在頁面裡跳著瀏覽）和可讀性，不是 SEO 加分。也因此，不要因為聽說「h1 對 SEO 好」就在一頁放三個 h1：排名不會變好，反而讓「哪一個是主標題」變得不清楚，又回到 Google 改寫 title 的那個理由。

菜單頁上的商品照片要有描述圖片內容的 alt（第 3 課），例如「拉花呈葉子形狀的熱拿鐵」。Google 圖片搜尋會參考 alt，但它首先是給看不到圖的人用的；寫成「咖啡 拿鐵 台北咖啡」這種塞關鍵字的 alt，對兩邊都沒用，也算關鍵字堆砌。

還有一個老網站很常見的做法：價格表做成一張設計好的圖片。這張圖片搜尋引擎讀不到價格，螢幕閱讀器也念不出來。重要的文字用文字寫，品項和價格用 HTML 的列表或表格呈現，排版交給 CSS。

內容本身的寫法也一樣以讀者為準：短段落、一段一個重點、用列表和表格呈現規格與價格。Google 文件寫明沒有「最少幾個字」的規定，把字數灌高不會加分；菜單頁需要的是清楚的品項和價格，不是一大段為了湊字數的介紹。

💡 實務上：標題結構最常壞在 CMS 編輯器
工程師把模板的 h1 寫對了，內容編輯在後台的文字編輯器裡為了「字大一點」又選了「標題 1」，一頁就出現好幾個 h1。常見做法是在編輯器只開放 h2～h4、用樣式選項處理「字要大」的需求，並在交接時跟編輯說明標題是結構、不是字級。檢查時在 DevTools 的 Console 執行 document.querySelectorAll('h1')，看回傳幾個，比用眼睛看畫面上的字級可靠。

到這裡，咖啡菜單頁本身已經說得清楚它是什麼。但這些都建立在一個前提上：Googlebot 得先到得了這一頁。回到三段流程的第一段，豆留咖啡首頁連到菜單的，是一個寫著「點這裡」的連結，有的地方甚至只是一個綁了 click 事件的 div。

爬蟲找得到菜單頁嗎？

第一節說過，Googlebot 是跟著連結找到新頁面的。網站裡一頁連到另一頁，叫內部連結（internal link），它是爬蟲在你的網站裡移動的路。如果某一頁沒有任何站內頁面連過去，它就叫孤兒頁面（orphan page）：爬蟲走不到它，除非它出現在 sitemap 或別的網站上。Google 的建議是：每一個你在乎的頁面，至少要有一個站內頁面連到它。這一節依序檢查三件事：連結本身能不能被爬、連結文字有沒有說出目的地、整個網站的連結和網址有沒有組成清楚的階層。

只有 <a href> 才是連結

對使用者來說，能點、點了會換頁的東西都是連結；對 Googlebot 來說不是。Google 只把帶 href 的 <a> 當成可以爬的連結，因為它要從 href 讀出目的地網址。<div @click="router.push('/menu/')"> 只有在 JavaScript 執行、使用者真的點下去時才知道要去哪裡，爬蟲從 HTML 讀不到網址；<span href> 的 href 對 span 沒有意義；<a href="javascript:…"> 的 href 不是網址。這三種都不算。

如果首頁到菜單頁只有這類「假連結」，菜單頁就可能變成孤兒頁面。Vue 專案的解法很直接：換頁一律用 <RouterLink>，它輸出的就是 <a href>，同時保留 SPA 不重新載入的換頁行為（Vue 課第 19 課）。

錨點文字：連結上的字也是線索

連結能被爬到之後，下一個問題是它帶了什麼資訊。連結上看得到的文字叫錨點文字（anchor text）。它告訴使用者「點了會去哪裡」，Google 也會用它來理解被連過去的頁面：很多頁面用「咖啡菜單」連到 /menu/coffee/，Google 就多了一個「這頁是咖啡菜單」的證據。豆留咖啡的「點這裡」什麼都沒說。檢查方法跟第 2 課一樣：只讀連結文字，不看前後文，還看得懂嗎？

麵包屑：讓每一頁都連回上一層

單一連結修好了，再看整個網站的結構。咖啡菜單頁在「首頁 → 菜單 → 咖啡菜單」這個階層裡，但頁面上沒有任何東西表達這件事。麵包屑（breadcrumb）就是顯示目前頁面在網站階層位置的一列連結，例如「首頁 / 菜單 / 咖啡菜單」。它解決兩個問題：使用者從搜尋結果直接落在咖啡菜單頁時，可以一步回到「菜單」看甜點；每一頁都自動連回上層分類，爬蟲也能順著這些連結走遍整個網站，減少孤兒頁面。寫法：

<nav aria-label="麵包屑">
  <ol>
    <li><a href="/">首頁</a></li>
    <li><a href="/menu/">菜單</a></li>
    <li><span aria-current="page">咖啡菜單</span></li>
  </ol>
</nav>

每個標籤都有它的理由。外層用 <nav aria-label="麵包屑">，因為它是一組導覽連結，而一頁上已經有主選單的 nav，取名字才能讓螢幕閱讀器使用者區分兩者（第 2 課的 landmark 規則）。裡面用 <ol>，因為項目有先後順序；項目之間的「/」用 CSS 的 ::before 畫，不寫進 HTML，螢幕閱讀器才不會唸出一堆斜線。最後一項加 aria-current="page"，告訴螢幕閱讀器「這是目前所在的頁面」；這門課讓它不做成連結，因為連到自己沒有用處（另一種寫法見課末）。

麵包屑還有一個副作用：Google 搜尋結果裡的網址列，有時會顯示成麵包屑的樣子，就是第三節那張圖最上面的「brew.example.tw › menu › coffee」。要讓 Google 確實讀到階層，還可以加結構化資料，見課末。

網址：給人讀的，不是排名技巧

麵包屑的階層，最好也反映在網址上。網址是使用者在搜尋結果、分享訊息裡會看到的東西：

網址說明
/product.php?id=123&cat=7只有編號，看不出內容
/menu/coffee/latte/看得出階層與內容，也跟麵包屑對得上

但要分清楚好處在哪。Google 文件說只有隨機編號的網址對使用者比較沒幫助，同時也把「在網域或路徑放關鍵字」列為不必花心思的事：網址可讀是為了人，不是排名技巧。所以新網站一開始就用可讀的網址，詞之間用連字號 -，例如 /guide/cold-brew/。已經上線的網站則不要為了 SEO 大改網址：每改一個網址，舊網址就要做 301 重新導向，也就是伺服器回覆「這個網址永久搬到新網址」（第 23 課）。漏做一個，那個舊網址的連結就全部失效，代價比可讀網址帶來的好處大得多。

💡 實務上：網站改版最容易在網址上出事
改版常順手把 /product.php?id=123 換成 /menu/coffee/latte/，上線後才發現舊網址全變 404：搜尋結果、LINE 群組裡的舊分享、印在 DM 上的 QR code 都點不進來。資深工程師會在改版前要一份「舊網址 → 新網址」對照表，每一筆都設定 301，上線後抽查舊網址是否正確導向。跟 PM 估工時時把這件事列進去，它不是 SEO 的加分題，是改版的必要工作。

到這裡，搜尋這一側的工作做完了：菜單頁找得到、讀得懂、結果那兩行說得出內容。但老闆貼到 LINE 群組的那張卡片還是沒有圖，而它跟 Google 搜尋是兩套不同的機制。

貼到 LINE 的卡片為什麼沒有圖？

把網址貼到 LINE、Facebook、Threads，平台會派自己的爬蟲去抓那個網址，再組出一張有圖、標題、說明的預覽卡片。這些平台不是照搜尋結果那套規則組卡片，它們讀的是一組專門給分享用的標記，叫 Open Graph：寫在 head 的 <meta property="og:…">，每一個 meta 告訴平台卡片上的一個欄位該放什麼。咖啡菜單頁要補上的是：

<meta property="og:type" content="website">
<meta property="og:title" content="咖啡菜單：手沖、拿鐵與季節特調">
<meta property="og:description" content="6 款咖啡，每杯 80～150 元，可以線上點餐、到店取餐。">
<meta property="og:url" content="https://brew.example.tw/menu/coffee/">
<meta property="og:image" content="https://brew.example.tw/images/og/menu-coffee.jpg">

每個屬性的定位和寫法：

屬性ogp.me 的定位寫法
og:title必填可以不帶品牌（卡片上通常另外顯示網域或 og:site_name）
og:type必填一般頁面寫 website，文章寫 article
og:image必填完整網址（https:// 開頭）。Facebook 建議至少 1200×630、接近 1.91:1，太小的圖會顯示成小縮圖
og:url必填這一頁的正式網址（canonical 網址，第 23 課），同一份內容的各種網址分享後會合併成同一個
og:description選填（建議）一兩句話

表裡最容易出事的是 og:image 的「完整網址」。第 1 課講過，相對網址要以「目前頁面的網址」為基準才能解析；瀏覽器知道自己在哪一頁，但社群平台的爬蟲拿到 /images/og/menu-coffee.jpg 這個字串時，不一定會幫你補上網域，卡片就沒有圖。這是 og:image 最常見的錯，也是豆留咖啡卡片沒圖時第一個該檢查的地方。og:url 同理，要寫完整網址。

Open Graph 跟前面的 SEO 工作是什麼關係？它不影響 Google 排名，它影響的是分享出去的卡片好不好看、有沒有人點。不過第三節提過，Google 產生 title 連結時，og:title 是它參考的來源之一，所以 og:title 的內容也要跟頁面一致，不能寫成另一個主題。

💡 實務上：社群平台會快取預覽，上線前先確認卡片
平台抓過一次網址之後會把卡片快取起來。改了 og:image 之後，舊的貼文和短時間內的新分享可能還是舊圖，老闆會以為「沒改好」。Facebook 有 Sharing Debugger 可以要求重新抓取；其他平台也各有快取時間。所以上線前先在測試頁確認卡片，比上線後再改省事；真的要改，跟老闆說明舊貼文的卡片不會跟著變。

菜單頁和分享卡片都修好了，任務還剩最後一件：前任外包說他們「做過 SEO」，那些做法要不要留？

外包留下的「SEO 技巧」要留嗎？

打開門市頁的原始碼，你會看到一些畫面上看不見的東西：一整塊 font-size: 0 的關鍵字、移到畫面外的文字、白底白字，頁尾還有十個連到 /city/… 的城市頁連結。這些都是曾經流行過的「SEO 技巧」，而它們正好是 Google 在 spam 政策裡明文禁止的做法。

違反的後果分兩種。一種是 Google 的自動系統判定違規，頁面或整個網站的排名下降。另一種是人工處置：Google 的審查人員確認違規後，對頁面或整個網站做出處置，叫人工判決處罰（manual action），嚴重的會從搜尋結果移除。所以接手舊網站時，要能認出這些做法並移除：

做法長什麼樣子正確做法
關鍵字堆砌（keyword stuffing）同一個詞重複到讀起來不自然；整塊列出要搶的城市或地區；alt、title、錨點文字塞滿關鍵字用自然的句子寫，讓使用者讀得下去
隱藏文字與連結（hidden text and links）白底白字、文字藏在圖片後面、用 CSS 移到畫面外（left: -9999px）、font-size: 0 或 opacity: 0、只用一個小字元當連結使用者看不到的關鍵字整段刪掉，不是換一種方式藏
門頁（doorway abuse）「台北咖啡」「新北咖啡」「桃園咖啡」…一堆幾乎一樣的城市頁，都只是把人導向同一個地方每間真實的門市一頁，有自己的地址、營業時間、照片；沒有門市的城市不做頁面
大量產生的低價值內容（scaled content abuse）用程式或生成式 AI 大量產生頁面，對使用者沒有幫助，只為了搶搜尋不管內容怎麼產生，每一頁都要對使用者有用
偽裝（cloaking）判斷是爬蟲就給另一份內容使用者和爬蟲看到同樣的內容

這些做法的共同點是：給搜尋引擎看的，跟給使用者看的不一樣。Google 的判斷標準一直是「這對使用者有沒有用」，這也是為什麼前面每一節的正確做法，最後都落在「寫給人看」。

移除隱藏文字時要小心一個誤會：不是所有看不到的內容都是隱藏文字。Google 的文件明確列出不算違規的情況：手風琴（accordion）、分頁標籤、輪播、互動才出現的提示，以及只給螢幕閱讀器讀、用來改善無障礙的文字。差別在目的。第 2 課用 .visually-hidden 補充「更多：秋季限定桂花拿鐵」，是為了讓連結名稱完整，這要留著；把一串關鍵字塞進 .visually-hidden 才是隱藏文字。清理時不要把無障礙用的視覺隱藏一起刪掉。

門頁也有一個常見的誤會：在連到城市頁的連結加上 rel="nofollow" 就沒事了。nofollow 只是給 Google 的提示：不要跟著這個連結走、不要把這個連結當成推薦。那些城市頁本身還是對使用者沒用的頁面，問題沒有消失。該刪的是頁面和連結；豆留咖啡真正有的大安店、信義店，各做一頁有地址、營業時間、照片的門市頁。

接手網站的第一件事：外包或舊版留下的 spam 常常藏在 CSS 裡，畫面上看不出來。用 DevTools 搜尋 HTML（Elements 面板按 Ctrl＋F／Cmd＋F），找 font-size: 0、-9999px、跟背景同色的文字；在 Search Console 的「人工判決處罰」報表（英文介面是 Manual actions）確認有沒有收到處罰。

補充與查表

  • 不想讓某段內容出現在摘要：例如會過期的公告，可以在那個元素加 data-nosnippet 屬性。
  • <meta name="keywords">：Google 早就不使用，不用寫。
  • description 不影響排名的出處：Google 在 2009 年的官方部落格說明有時會用 description 當摘要，但排名不使用它。
  • 麵包屑最後一項的另一種寫法：WAI-ARIA 的範例讓最後一項仍是連結並加上 aria-current="page"；這門課的做法是不做成連結。兩種都可以，重點是要有 aria-current。
  • BreadcrumbList 結構化資料：要讓 Google 確實讀到麵包屑的階層，可以加 BreadcrumbList 結構化資料（第 24 課）。
  • 版本備註：這一課的 Google 規則以 Google Search Central 文件為準：How Search Works（last updated 2025-12-18）、SEO Starter Guide 與 title links（2025-12-10）、snippets（2026-04-20）、spam policies（2026-08-28）、crawlable links（2025-12-10）。Open Graph 以 ogp.me 為準。

練習

練習 1：「咖啡菜單」頁（https://brew.example.tw/menu/coffee/）的 head 只有一個「豆留咖啡」的 title。只改 <head>，補上：(1) title：寫出頁面主題「咖啡菜單」，品牌放最後，格式「主題｜豆留咖啡」，15～40 個字，不要跟網站其他頁重複（其他頁是「豆留咖啡」「菜單｜豆留咖啡」「甜點菜單：可頌與起司蛋糕｜豆留咖啡」「門市資訊：大安店與信義店｜豆留咖啡」），同一個詞不要重複超過兩次；(2) meta description：50～120 個字，寫頁面上真的有的資訊（品項數、價格範圍、可以線上點餐），不要重複 title；(3) Open Graph：og:type（website）、og:title（含頁面主題）、og:description（同樣只寫頁面上有的資訊）、og:url（這一頁的完整網址）、og:image（分享圖 /images/og/menu-coffee.jpg，要寫成完整網址）。

練習 2：菜單頁的結構讓使用者和搜尋引擎都看不懂。只改 HTML（CSS 的 class 已經設好）：(1) h1 改成頁面主題「咖啡菜單」，店名不再是 h1（改成 <p class="brand">）；(2) 分類「經典咖啡」「手沖單品」用 h2、品項用 h3，保留原本的 class；(3) 把「點這裡」「更多」「詳情」改成說得出目的地的連結文字，連結本身（href）都要留著；(4) 在 h1 前面加麵包屑：<nav aria-label="麵包屑"> 裡放 <ol>，依序是首頁（/）、菜單（/menu/）、咖啡菜單（目前頁：不是連結，加 aria-current="page"）。nav 可以加 class="breadcrumb" 套用現成樣式。

練習 3：前任外包為了「做 SEO」，在門市頁加了 font-size: 0 的關鍵字區塊、移到畫面外的文字、白底白字、4px 的小字，把門市照片的 alt 塞滿關鍵字，還在頁尾放了 10 個連到 /city/… 的城市頁（內容幾乎一樣）。把這些做法全部移除（HTML 和 CSS 都可以改），alt 改成描述照片的文字；門市名稱、介紹、照片、地址、營業時間要留著，而且看得到。

練習 4：meta description 對 Google 排名的影響是？

✓ b：Google 說明排名不使用 description；摘要主要從頁面內容自動產生，description 更準確時才可能被採用。a 錯：它不參與排名。c 錯：長度沒有上限，但顯示時會被截斷，寫長沒有好處。d 錯：沒寫只是讓 Google 自己從內容挑摘要。

練習 5：同一家店做了「台北咖啡」「新北咖啡」「桃園咖啡」…30 個內容幾乎一樣、都導向同一個訂購頁的頁面，這屬於？

✓ b：為了搶不同城市的搜尋而複製幾乎一樣的頁面，是 spam 政策裡的門頁。a 錯：在地 SEO 是每間真實門市一頁，有自己的地址、營業時間、照片。c 錯：結構化資料是 JSON-LD 標記（第 24 課）。d 錯：nofollow 不會讓沒用的頁面變有用，該刪的是頁面本身。

練習 6：og:image 寫成相對路徑，結果分享到 LINE 沒有預覽圖。這個錯誤會影響什麼？

✓ b：Open Graph 是給社群平台產生預覽卡片用的，跟搜尋排名無關，但卡片沒有圖會少很多點擊。a 錯：Open Graph 不是排名因素。c 錯：LCP（第 20 課）量的是頁面上最大的圖片或文字區塊；og:image 只寫在 meta，瀏覽器不會下載它，不影響頁面載入。d 錯：螢幕閱讀器不讀 head 裡的 meta。

常見錯誤

  • 每頁 title 都一樣：搜尋結果、分頁、書籤裡都分不出是哪一頁，Google 也可能自己改寫。每頁寫「主題｜品牌」，主題各不相同。
  • description 寫頁面上沒有的東西：使用者點進來找不到就離開。只寫頁面上真的有的資訊。
  • 關鍵字堆砌：title、alt、錨點文字、頁尾的城市清單塞滿關鍵字，違反 spam 政策，使用者也反感。用自然的句子。
  • 隱藏文字：白底白字、font-size: 0、移到畫面外都是 spam。視覺隱藏只用在補充可及名稱，例如連結或按鈕的完整名稱。
  • 連結文字寫「點這裡」「更多」：對使用者、螢幕閱讀器和搜尋引擎都沒有資訊。寫出目的地。
  • 用 div @click 換頁：爬蟲只跟著 <a href> 走，那一頁可能變成孤兒頁面。用 RouterLink。
  • og:image 寫相對路徑：分享卡片沒有圖。寫 https:// 開頭的完整網址。
  • 為了 SEO 一頁放好幾個 h1、或大改網址：標題數量不影響排名；改網址沒做重新導向會讓舊連結全部失效。

小結

  • 搜尋引擎分三段：爬取（跟著 <a href>）、索引（從 HTML 理解內容）、排序與呈現。豆留咖啡卡在後兩段：HTML 沒說清楚每一頁在講什麼。SEO 能控制的是內容與 HTML，排名與呈現方式由 Google 決定，也不保證收錄。
  • 先依搜尋意圖決定由哪一頁回答：一頁回答一個需求，同一個需求不要分散成好幾頁。
  • title：每頁不同、描述內容、品牌在後、不堆關鍵字；跟 h1 意思一致，Google 就沒有理由改寫。
  • description 不影響排名，只影響點擊：每頁不同、寫頁面上有的具體資訊，Google 不保證採用。
  • h1 寫頁面主題；標題不跳級是為了無障礙與可讀性，不是排名；alt 描述圖片；重要文字不做成圖片。
  • 爬蟲只認 <a href>；錨點文字說出目的地；麵包屑用 nav＋ol＋aria-current="page"；網址可讀，但已上線的不要為了 SEO 改。
  • Open Graph 決定分享卡片，og:image、og:url 寫完整網址；它不影響排名，平台會快取預覽。
  • 關鍵字堆砌、隱藏文字、門頁、大量產生的低價值頁面都違反 Google spam 政策；接手網站時先找出來移除，但保留無障礙用的視覺隱藏。
