階段 4：除錯、瀏覽器與效能 · 第 18 課

DevTools 日常除錯：Elements、Computed、版面工具、Network

星期六上午，店長在群組裡丟了一句：「iPhone 上點餐按鈕不見了。」沒有截圖、沒有網址、不知道是哪一頁。你在自己的電腦打開首頁，按鈕好好的。這時候最常見的反應是猜：改一下 z-index、加個 !important，部署上去再請店長看看。猜對了也不知道為什麼對，猜錯了就再來一輪，而這段時間客人在手機上點不了餐。

這一課從頭到尾只處理這一則回報：先把問題問清楚，在自己的電腦上重現，再用 DevTools 的面板一步步縮小範圍，找到原因才改，最後寫成一份同事照做就能看到問題的報告。前面幾課零散用過的 DevTools 功能（第 7 課找撐破版面的元素、第 11 課的裝置模式），在這裡串成一套固定的流程。

這課的路線：
  1. 從哪裡開始：除錯的六個步驟；回問店長之後，一句「按鈕不見」變成菜單頁上的三個症狀。
  2. 怎麼在桌機看到店長手機上的畫面：裝置模式與偏好模擬。
  3. 按鈕為什麼不見：Elements 與 Styles 看哪些規則在搶，Computed 看最後的值是哪一行給的（答案只改一行）。
  4. 頁面為什麼可以左右滑、為什麼開很慢：版面工具找出比畫面寬的元素，Network 看每個請求的狀態、大小與時間。
  5. 修好之後：無障礙樹與 Lighthouse 的第一輪檢查，再把整件事寫成可重現的 bug 報告。
這課會用到：
  • 第 6 課的層疊：多條規則設同一個屬性時，依 layer、權重、出現順序決定誰贏。
  • Node 課第 15 課的 Cache-Control 與 304：回應標頭決定瀏覽器能快取多久；304 表示「你手上的版本還能用」，不用重傳內容。
面板名稱以 Chrome 156 穩定版的英文介面為準，對照 developer.chrome.com/docs/devtools 的官方文件。DevTools 每幾個版本就會調整按鈕位置，找不到時按 Cmd＋Shift＋P（Windows 是 Ctrl＋Shift＋P）打開指令選單（Command Menu），直接輸入功能名稱最快。

店長只說「按鈕不見了」，要從哪裡開始？

先想想「按鈕不見」可能有多少種原因：按鈕被 CSS 藏起來、被別的元素蓋住、被擠到畫面外、Vue 根本沒把它渲染出來、JavaScript 出錯讓整塊沒畫完，每一種底下又有好幾種寫法會造成。猜，就是從這一大堆可能裡隨手挑一個去改。除錯流程做的事相反：每一步都砍掉一部分可能，直到只剩一個，而且是你親眼確認過的那一個。這套流程不只用在 CSS，後端的 bug 也是同樣的步驟：

  1. 重現（reproduce）：在你的電腦上看到同樣的問題。看不到問題，就沒辦法判斷後面的任何修改有沒有用。所以第一件事是問清楚：哪一頁、什麼裝置、哪個瀏覽器、做了什麼。「iPhone 上」至少代表三個跟你桌機不同的條件：窄螢幕、觸控、Safari。
  2. 縮小範圍：是所有頁面還是一頁？所有寬度還是某個寬度？登入前後都會嗎？每回答一題，可能的原因就少一半。這一步問的是「在什麼條件下會發生」，還不是「為什麼」。
  3. 提出假設：根據縮小後的條件，說出一個具體、可以驗證的原因，例如「按鈕被 sticky 頁尾蓋住」「按鈕在某個寬度被 display: none」。一次只驗證一個，同時改兩個地方，問題消失了也不知道是哪個改對的。
  4. 驗證：在 DevTools 裡改一個值，問題消失就證實了；沒消失就回到上一步換下一個假設。DevTools 的修改只在你的瀏覽器裡，改錯了重新整理就恢復，所以這一步可以放心地試。
  5. 修正：DevTools 的修改重新整理就不見了，要寫回原始碼，再到其他寬度與狀態檢查一次，確認沒有把別的地方改壞。
  6. 防止再發生：補一個測試（第 27 課的自動化驗收）或加進上線前的檢查清單，下次同樣的錯在上線前就被擋下來。

套到店長的回報。第一步就卡住了：你的電腦上按鈕好好的，所以先回問。店長的回答是：菜單頁、她自己的 iPhone、沒登入、往下捲到「本週菜單」就看不到「立即點餐」。她順便又提了兩件事：菜單頁在手機上會左右晃，而且店裡用 4G 開這一頁要等很久。

一句「按鈕不見」變成了三個症狀。這是縮小範圍的第一刀：三個症狀可能是三個不同的原因，混在一起查，很容易把 A 的線索當成 B 的答案。接下來一次處理一個，每一個剛好對應 DevTools 的一組工具：按鈕不見看 Elements、Styles 與 Computed；左右晃看版面工具；開很慢看 Network。先說按鈕這一則的結局：原因是一條原本要藏別的元素的 media query，選擇器寫得太寬，最後只改一行。下面幾節照流程走一遍，看這個結論是怎麼一步步確定的。

💡 實務上：先花時間重現，比直接猜著改省事
工作中的 bug 多半從客服、PM 或店長轉過來，描述常常只有「手機上怪怪的」。資深工程師接到時第一步是回問：哪一頁、什麼裝置與瀏覽器、登入了沒、做了哪些操作，最好附截圖或螢幕錄影。重現不了就別急著改，猜著改上線，等於製造一個新變數，原本的 bug 也不一定真的消失。卡住一段時間沒進展時，把已經排除的假設寫下來再找同事一起看，對方通常一眼就看出你漏問的那個條件。

問清楚之後，重現還是卡著：你手上沒有店長那支 iPhone。下一節解決這件事。

桌機上按鈕好好的，怎麼看到店長手機上的畫面？

同一個網址，桌機和手機看到的畫面不同，是因為頁面的 CSS 會依環境做不同的事：第 11 課的 media query 依畫面寬度套用不同規則，圖片依螢幕密度挑不同大小的檔案，hover 樣式只在有滑鼠的裝置上出現。要在桌機看到店長的畫面，就要讓瀏覽器以為自己在一支手機上。

這就是裝置模式（Device Toolbar）的工作。按 Cmd＋Shift＋M（Windows 是 Ctrl＋Shift＋M）打開，第 11 課用過它調寬度。從上方的下拉選單選一支手機時，它同時模擬四件事：

  • viewport 寬度：頁面以為畫面就這麼寬，所有 media query 都照這個寬度判斷。
  • 裝置像素比（device pixel ratio，DPR）：一個 CSS 像素用幾個螢幕上的實體像素來畫。手機螢幕密度高，DPR 常是 2 或 3，這會影響 srcset 挑哪張圖（第 14 課）。
  • 觸控：頁面會以為使用者用手指操作，而不是滑鼠。
  • User-Agent：瀏覽器每次請求都會附上一段自我介紹的字串，有些網站依它判斷要給手機版還是桌機版。

它不會把 Chrome 變成 Safari：排版、執行 JavaScript 的引擎還是 Chrome 的。所以裝置模式能重現的是「尺寸、密度、觸控造成的問題」；只有 iPhone Safari 才出現的問題（例如 Safari 的網址列高度、某些 CSS 支援差異），在這裡永遠看不到，要用真的 iPhone 接 Mac，在 Mac 的 Safari「開發」選單裡用網頁檢閱器（Web Inspector）檢查。

回到店長的回報。打開菜單頁，在裝置模式選一支 390px 寬的 iPhone，捲到「本週菜單」：按鈕不見了。重現成功，而且這個結果本身就縮小了範圍：Chrome 也重現得出來，代表原因跟 Safari 無關，是寬度造成的。再把裝置模式切到可以自由調整寬度的模式，慢慢拖寬，會發現超過 400px 按鈕就回來了。一個整齊的分界點，很像某條 media query 的條件，這是下一節要驗證的假設。

如果換了寬度還是重現不了，下一個要懷疑的是使用者的系統偏好。有些 bug 只在使用者開了深色模式、減少動態這類設定時出現，而這些設定在你的電腦上通常是關的。打開 Rendering 分頁（指令選單輸入 rendering，選 Show Rendering），可以模擬：

設定用來重現
Emulate CSS media feature prefers-color-scheme深色模式下文字和背景一樣黑（第 16 課）
prefers-reduced-motion: reduce使用者關掉動畫後，還在跑的動畫或卡住的轉場（第 17 課）
forced-colors: activeWindows 高對比模式下消失的按鈕外框
Emulate CSS media type: print列印收據、菜單時的版面
Emulate vision deficiencies模糊、低對比、紅色盲（Protanopia）、綠色盲（Deuteranopia）、藍色盲（Tritanopia）、全色盲（Achromatopsia）時，只靠顏色區分的狀態還看不看得出來

這些模擬是 DevTools 的設定，不會改到作業系統。檢查完把選項改回 No emulation，免得之後忘了還開著模擬，把模擬出來的畫面當成真的問題。

💡 實務上：上線前的 RWD 檢查，裝置模式只是第一關
咖啡店官網改版上線前，常見的做法是用裝置模式依序看 320、375、768、1280 幾個寬度，再切深色模式和減少動態，確認沒有撐破、文字看得清楚。但裝置模式跑的還是 Chrome，iPhone Safari 的網址列、輸入框自動放大、日期選擇器等問題只有真機看得到，所以團隊通常會準備幾支測試機，或使用雲端真機測試服務。使用者回報「只有我的手機有問題」時，先問瀏覽器與系統版本，別在桌機的裝置模式裡試不出來就回「無法重現」。

現在確定了「400px 以下按鈕就不見」。但「不見」還有好幾種可能：被藏起來、被別的元素蓋住、被擠出畫面。下一步要直接看按鈕本身。

按鈕還在不在？用 Elements 與 Styles 看哪些規則在搶

在 390px 寬的畫面上，按鈕已經看不到，沒辦法直接對它按右鍵。先對旁邊看得到的菜單卡片按右鍵選「檢查」（Inspect），或按 Cmd＋Shift＋C（Windows 是 Ctrl＋Shift＋C）再點卡片，Elements 面板會選取它。左邊是 DOM 樹：第 1 課說過，這是瀏覽器建出來的 DOM，不是原始碼，Vue 渲染出來的元素也在這裡。滑鼠移到 DOM 樹的節點上，頁面上對應的元素會被標出內容（藍）、padding（綠）、margin（橘）。

展開卡片的節點，<button>立即點餐</button> 還在 DOM 樹裡。這一眼就排除了一大類原因：Vue 有把按鈕渲染出來（不是 v-if 條件不成立），JavaScript 也沒有在這之前出錯。問題在 CSS。點選這個 button 節點，右邊的 Styles 分頁會列出所有選中它的規則。

Styles 的排列順序就是層疊的結果：越上面的越優先。多條規則設定同一個屬性時，瀏覽器依第 6 課的順序比，先比 layer，再比權重，最後比出現順序，Styles 把比完的結果由贏到輸排好給你看。最上面的 element.style 是元素自己的 style 屬性（inline style）。每條規則右上角是來源，例如 menu.css:42，點下去會跳到 Sources 面板的那一行。用了 @layer 的規則上方會標出 layer 名稱。

同一個屬性可能出現在好幾條規則裡，只有一條會生效。每條宣告的外觀告訴你它的狀態：

看到的樣子意思接著做什麼
整行劃線被層疊中更優先的宣告蓋掉了（overridden）往上找同一個屬性沒被劃線的那條，照第 6 課的步驟判斷它為什麼贏
劃線＋警告圖示屬性名稱打錯或值不合法，瀏覽器直接丟掉這條宣告滑鼠移到圖示上看原因，例如 colr、padding: 10（少了單位）
顏色變淡＋資訊圖示合法但沒有效果（inactive），因為別的屬性讓它不起作用滑鼠移到圖示上看提示，例如在非 flex 容器上寫 justify-content、在 inline 元素上寫 width

看懂狀態之後，Styles 也是驗證假設的地方，對應流程的第 4 步。值可以直接點下去改；數字值按 ↑／↓ 每次加減 1，加 Shift 是 10。每條宣告前面的核取方塊可以暫時停用它：停用之後問題消失，就證明是這條造成的，這是最快的驗證方法。Styles 上方的工具列還有兩個按鈕，用來重現「只在某個狀態才出現」的樣式：

  • :hov（強制狀態，force state）：勾選 :hover、:focus、:focus-visible、:focus-within、:active、:target，元素會一直維持那個狀態。檢查 hover 樣式一定要用它，因為滑鼠一移去 DevTools，:hover 就消失了。
  • .cls：列出元素的 class，可以勾選開關或新增一個，用來驗證「加上 is-active 會不會好」。

改過的內容可以在 Changes 分頁（指令選單輸入 Changes）看到差異。這些修改都只存在記憶體裡，重新整理就不見了：確定答案之後，回到編輯器改原始碼。用 Vite 開發 Vue 專案時，Styles 裡的來源和選擇器會跟你寫的不太一樣，細節見課末「補充與查表」。

💡 實務上：樣式蓋不掉時，先查清楚為什麼輸
最常見的情境是套用元件庫（例如 Naive UI、Element Plus）後，想改按鈕顏色卻怎麼改都沒反應。新手的直覺是加 !important 或疊更長的選擇器，結果下一個人得用更強的寫法蓋回去，專案裡的 CSS 權重越疊越高。先在 Styles 看贏的那條是誰、在哪個 layer、權重多少，再決定用元件庫提供的變數或 class、調整 layer 順序，還是真的要提高權重。Code review 看到 !important 時，資深的人會問「它在跟哪一條規則打架」，答不出來就還沒找到原因。

問題是，「立即點餐」身上的規則有 reset、元件庫、.btn、菜單頁專用的樣式，Styles 一列就是一長串。我們只關心一個屬性：display 最後是多少、是哪一行給的。在 Styles 裡一條條往下捲找太慢，下一節換一個面板。

display 最後是多少、是哪一行給的？Computed 分頁

Styles 回答的是「有哪些規則想設定這個元素」，Computed 分頁回答的是「每個屬性最後算出來是多少」。兩個問題的方向相反：Styles 以規則為單位，一條規則裡有很多屬性；Computed 以屬性為單位，一個屬性底下列出所有想設定它的規則。只想追一個屬性時，從 Computed 進去比較快：

  1. 上方的篩選框輸入屬性名稱，例如 display。
  2. 展開它前面的箭頭，會列出所有設定過這個屬性的宣告，贏的在最上面、輸的被劃線，旁邊有來源檔案與行號，點下去會跳到那一行。
  3. 篩選後什麼都沒列出，可能是這個屬性沒有任何規則設定、用的是預設值或繼承來的值。勾選 Show all 會列出所有屬性。值是繼承來的時候（例如 color、font-size），回到 Styles 往下捲，會看到 Inherited from 某個祖先元素的區塊，這個值是從那裡傳下來的。

對「立即點餐」按鈕這樣做：篩選 display，值是 none。展開來，贏的那條來自 menu.css:58，在一條 @media (max-width: 400px) 裡，選擇器是 .card button。這解釋了上一節找到的 400px 分界點。點過去讀那段 CSS 和它上面的註解，就知道這條規則原本是要在窄螢幕藏卡片裡的另一個按鈕，但 .card button 會選中卡片裡所有的 button，「立即點餐」也被一起藏了。

這還只是假設，要驗證：在 Styles 裡找到這條 display: none，取消它前面的核取方塊，按鈕回來了。原因確定。修正是在原始碼把選擇器改窄，只選中原本要藏的那個按鈕，就是開頭說的「只改一行」。改完再看 390px 與 1280px 兩個寬度：「立即點餐」要出現，原本要藏的按鈕在窄螢幕要繼續藏著。練習 1 是同一類的問題：一個按鈕被層疊中另一條規則蓋掉，要找出是哪一條、為什麼贏，只改那一條。

Computed 還有兩個用途，下一個症狀就會用到。最上方是盒模型圖（第 7 課）：content、padding、border、margin 四層的實際數字。元素比預期寬的時候先看這裡，通常是 box-sizing 或多出來的 padding。另一個是 Computed 顯示的都是算好的值：width 顯示成 px，font-size: 1.25rem 會顯示成 20px，color: var(--brand) 會顯示成實際的顏色。CSS 變數沒有生效時（例如名稱打錯），在 Styles 裡把滑鼠移到 var(--brand) 上，會顯示它解析成什麼值，或是根本沒有定義。

按鈕修好了。但在 390px 寬的畫面上，用觸控板往旁邊一推，整頁真的會左右晃，這是店長說的第二個症狀。

頁面為什麼可以左右滑？找出比畫面寬的元素

手機上整頁可以左右滑，是最常見的版面 bug。它的機制是：只要有任何一個元素的右緣超出畫面，整份文件就比畫面寬，瀏覽器就讓使用者橫向捲動去看超出的部分。所以要找的不是「哪裡壞了」，而是「哪個元素比畫面寬」。常見的原因有三種：

  • 固定寬度的圖片：例如 HTML 寫了 width="480"，畫面只有 375px，圖片照樣 480px 寬。
  • 沒有斷行機會的長字串：長網址、長英文單字裡沒有空格，瀏覽器找不到可以換行的地方，整串排成一行撐出去。
  • width: 100vw 再加上 padding 或 margin：100vw 已經是整個畫面寬，再加上左右的 padding 或 margin，就一定超出。

找的步驟：

  1. 開裝置模式設 375px 寬，往右捲，看是哪一塊露出畫面。
  2. 在 Console 執行第 7 課最後一節「下次遇到版面問題，怎麼自己找出原因？」裡那一行程式。它把頁面上每個元素的 getBoundingClientRect().right（元素右緣離畫面左邊多遠）拿來和畫面寬度比，列出右緣超出畫面的元素。一個元素太寬時，它的祖先常常也被撐寬一起列出來，從最外層的那個開始看，往內找到真正撐出去的那一個。
  3. 選取它，看上一節的盒模型圖和 Computed 的 width：寬度是誰給的（HTML 的 width 屬性、CSS 的固定值、100vw）、多出來的是 padding 還是 margin。
  4. 停用可疑的宣告驗證，再改原始碼。

套回菜單頁走一次。裝置模式設 375px，往右捲，露出畫面的是首屏那張拿鐵大圖。Console 列出的元素裡，最外層是首屏區塊的 section，往內看，它只是被裡面的 <img> 撐寬，真正撐出去的是那張圖。選取這張圖看 Computed：width 是 480px，展開來沒有任何 CSS 規則設定寬度，480 來自 HTML 的 width="480" 屬性，正是上面第一種原因。驗證的方式是在 Styles 的 element.style 暫時加上 max-width: 100%，圖片縮到跟內容區一樣寬，橫向捲動消失，原因確定。修正是在原始碼替這張圖加上 max-width: 100% 與 height: auto：前者讓它最多跟父元素的內容一樣寬，後者讓高度依原本的寬高比跟著縮，否則高度會停在 HTML 屬性寫的值、圖被壓扁（第 7 課）。HTML 的 width、height 屬性留著，瀏覽器靠它們在圖片下載完之前就預留空間。改完在 375px 與 1280px 各看一次：手機上不能再左右滑，桌機上圖片仍是原本的大小。

另一條分支：如果找到的元素在 Grid 或 Flexbox 容器裡，問題常常出在容器怎麼分配空間，例如某一欄的 minmax() 最小值比畫面還寬。這時要看的是格線和欄寬，Elements 面板有疊加層可以把它們畫在頁面上。DOM 樹裡，Grid 容器旁邊有 grid 標籤（badge）、Flex 容器旁邊有 flex 標籤，點一下標籤，頁面上會畫出格線或 flex 項目的範圍，捲動頁面也不會消失。Elements 面板右側的 Layout 分頁列出頁面上所有 Grid 與 Flexbox 容器，可以一次打開好幾個疊加層；其中 Show track sizes 會標出每一欄、每一列實際算出來的寬高，用來檢查 fr、minmax() 的結果（第 9 課）。Layout 分頁其他的選項與 DOM 樹上其他標籤，整理在課末「補充與查表」。

找到元素之後，修法要針對原因：圖片限制最大寬度、長字串允許在任意位置換行、100vw 改成跟著內容區走的寬度。最容易犯的錯是跳過原因、直接把超出的部分藏起來：

不要在 body 加 overflow-x: hidden 了事：元素還是比畫面寬，只是被裁掉看不到（例如網址被截斷），而且祖先有 overflow 不是 visible 時，裡面的 position: sticky 會失效（第 10 課）。

練習 2 是一頁同時有三個元素撐破版面，原因各不相同，就是這一節的流程。版面修好之後，店長的三個症狀只剩最後一個：店裡用 4G 開菜單頁要等很久。剛才那張拿鐵大圖等一下還會再出現。慢不是哪條 CSS 寫錯，在 Elements 裡看不到，要換一個面板。

店裡用 4G 開要等很久：Network 看每個請求

你在辦公室打開菜單頁，一秒就好了，為什麼店長要等很久？差別有兩個。第一是快取：你開發時打開過這一頁幾十次，CSS、JavaScript、圖片都已經存在瀏覽器裡，照 Cache-Control 的規定直接拿來用，不用重新下載；第一次造訪的客人什麼都沒有，每個檔案都要從網路抓。第二是網路：辦公室的網路跟店裡的 4G 差很多。所以要重現「開很慢」，得先讓你的瀏覽器變得像第一次用手機造訪的客人。

Network 面板記錄頁面發出的每一個請求。上方工具列有三個除錯時一定會用的設定：

  • Disable cache：停用瀏覽器快取，模擬第一次造訪。只在 DevTools 開著的時候有效。
  • 節流（throttling）：限制網路速度。下拉選單選 Fast 4G、Slow 4G、3G 或 Offline，模擬較慢的網路。CPU 也可以節流（在 Performance 面板），模擬便宜的手機。
  • Preserve log：換頁時不要清掉紀錄。追重新導向或表單送出後的請求時要勾，否則一換頁，前一頁的請求就不見了。

勾 Disable cache、節流選 Slow 4G，然後重新整理。Network 只記錄打開 DevTools 之後發生的請求，頁面早就載入完的話表格是空的，要重新整理才會從頭記錄。現在菜單頁也要等很久才出來，重現成功，表格裡每一列是一個請求。先看這幾欄：

  • Status：HTTP 狀態碼。4xx、5xx 會變紅，代表請求失敗；301／302 是重新導向。304 不是錯誤：它表示瀏覽器問伺服器「我手上這份還能用嗎」，伺服器回答「能」，所以不用再傳一次內容，是好事。
  • Size：這個請求有多大，下面細講。
  • Time：從開始到收完的時間。
  • Initiator：誰發出這個請求，例如 HTML 解析時遇到 <img>，或某一行程式（點了會跳過去）。用來回答「這張圖是哪裡要求載入的」。

其他欄位（Type、Priority、Waterfall）的意思整理在課末「補充與查表」，查表用，不用背。

Size 欄在設定裡打開 Big request rows 後會顯示兩個數字，例如 18.2 kB 上、64.0 kB 下。上面是傳輸量：壓縮後、含標頭，實際走網路的量，這決定下載要多久，在 4G 上就是店長在等的東西。下面是資源大小：解壓後的大小，瀏覽器要解析、放進記憶體的量。兩個數字差很多，代表伺服器有壓縮這個檔案。從快取拿到的請求不會走網路，Size 會顯示 (memory cache) 或 (disk cache)。

按 Size 排序，找出最大的幾個請求，點一個會打開詳細資料。Headers 看請求與回應的標頭，例如 Cache-Control、Content-Type、Content-Encoding（伺服器用什麼方式壓縮）。Timing 把這個請求的時間拆成幾段，其中最常看的是 Waiting，也就是 TTFB（time to first byte）：從送出請求到收到回應第一個位元組的時間，主要反映伺服器處理請求花了多久。HTML 文件的 TTFB 長，問題通常在後端，不在前端；TTFB 短但下載很久，問題通常在檔案太大。

菜單頁最大的兩個請求是打包後的 JavaScript 和首屏的拿鐵大圖。拿它們的傳輸量和資源大小來比，就看得出該往哪裡修。執行後看括號裡的百分比：它是傳輸量佔資源大小的比例，越接近 100%，代表壓縮越幫不上忙。

所以圖片要從格式與尺寸下手（第 14 課），壓縮已經幫不上忙；文字資源要確認伺服器有開壓縮，回應標頭有 Content-Encoding: br 或 gzip。

套回菜單頁：JS 的傳輸量只有資源大小的三成左右，代表伺服器已經在壓縮，不是主因。元凶是那張約 186 kB 的拿鐵 JPEG：壓縮對它沒效果，而且就是上一節撐破版面的同一張圖，手機只顯示 375px 寬，卻下載了給 480px 用的檔案。修法照第 14 課：換成同畫質下更小的格式（AVIF 或 WebP），再用 srcset 準備幾種寬度，讓手機下載較小的那一份。改完用同樣的條件驗證：勾 Disable cache、節流選 Slow 4G，重新整理，看這張圖的傳輸量變小、頁面比剛才快出來。條件不同（例如忘了停用快取），比出來的快慢就不算數。

找到原因後，常常要把紀錄交給別人看，例如請後端確認壓縮設定。Network 可以把整份紀錄匯出成 HAR（HTTP Archive）：一個 JSON 檔，記錄每個請求的網址、標頭、狀態碼、大小與時間。在請求表格上按右鍵或用工具列的匯出按鈕就能存。預設匯出的是去除敏感資料的版本，不含 Cookie、Set-Cookie、Authorization 標頭；要包含它們得先在設定裡開啟。即使是預設版本，HAR 仍可能含有網址裡的 token 或回應裡的個資，貼到公開的 issue 前先檢查。

HAR 的基本結構是 log.entries 陣列，每一筆一個請求。Chrome 另外加了底線開頭的欄位，例如 _transferSize（傳輸量）、_resourceType、_priority。練習 3 就是寫程式讀 HAR，自動整理出一份摘要，不必在面板上一列一列看。

💡 實務上：Network 是前後端釐清責任的共同證據
「訂單送出沒反應」這類問題，前後端很容易互相懷疑。打開 Network 找到那個請求：沒發出去是前端的事；狀態碼 4xx 先看送出的參數與 Response 裡的錯誤訊息；5xx 或 TTFB 特別長通常要請後端查 log。回報給後端時，可以在請求上按右鍵選 Copy → Copy as cURL。cURL 是在終端機送 HTTP 請求的指令，對方貼上就能重送同一個請求，比截圖有用得多。要注意複製出來的指令會帶著 Cookie 或 Authorization 標頭，不像預設匯出的 HAR 已經去掉，貼到群組或 issue 前先刪掉。

三個症狀都找到原因、修好了。回覆店長之前，先確認這些修改沒有弄壞別的地方，這是流程裡「修正」那一步的後半。

修好之後還要檢查什麼？無障礙樹與 Lighthouse

這次改了菜單卡片的 CSS、圖片和版面，改動越多，越可能順手弄壞別的東西。上線前用 DevTools 跑一輪自動和半自動的檢查，成本很低，又能擋掉明顯的問題。

第一個要確認的是「立即點餐」對所有使用者都是一個能用的按鈕，不只是看起來回來了。Elements 面板右側的 Accessibility 分頁顯示選取元素的角色（Role）與名稱（Name），第 5 課用過：角色是 button、名稱是「立即點餐」，螢幕閱讀器才會念出「立即點餐，按鈕」。勾選整頁無障礙樹（full-page accessibility tree）的選項後，DOM 樹會換成螢幕閱讀器看到的樹。<div> 疊成的按鈕在這裡就不是 button，用鍵盤和螢幕閱讀器的人找不到它。顏色也要看：在 Styles 裡點顏色前面的小方塊，取色器會顯示這個顏色跟背景的對比值，以及 AA／AAA 是否通過。

第二個是 Lighthouse 面板，一鍵跑效能、無障礙、最佳做法、SEO 的檢查，產生報告與建議，適合當上線前的第一輪檢查。它的結果是實驗室資料（lab data），意思是在你的電腦上、用模擬的網路與裝置跑一次得到的結果。所以每次跑會有點差異，也跟真實使用者的體驗不同：Lighthouse 的效能分數很好，不代表店長在店裡的 4G 上也很快。實驗室資料與真實使用者資料的差別在第 20 課。無障礙分數 100 也不代表沒問題：自動檢查只抓得到一部分問題，鍵盤操作與螢幕閱讀器還是要自己試。

檢查都過了。還剩流程的最後一步：防止再發生。做法是把這次的發現寫成一份報告。

怎麼寫一份別人照做就能看到問題的 bug 報告？

bug 已經修好了，為什麼還要寫報告？因為報告有三個用途，只有第一個是「讓別人修」。第一，它寫進 issue 或 PR 的說明，reviewer 照著步驟就能在修改前看到問題、在修改後確認修好，不必相信你一句「修好了」。第二，報告裡的「預期」可以直接變成第 27 課的自動化驗收：「390px 寬時，每張菜單卡片都看得到『立即點餐』按鈕」就是一條測試；不適合寫成測試的，例如在 Slow 4G 下首屏圖片的傳輸量，就加進上線前的檢查清單。做到這一步，流程的「防止再發生」才算完成，下次有人把選擇器改寬，測試會在上線前擋下來。第三，下次換你收到別人的回報時，你知道一份好的報告長什麼樣子，店長那則回報花了很多時間回問，就是因為少了這些資訊。

「iPhone 上點餐按鈕不見了」不是 bug 報告，只是一個現象。收到報告的人第一件事是重現；做不到就只能來回問，這一課的第一節就是在做這件事。可重現步驟（steps to reproduce）是讓別人照做就能看到同樣問題的步驟。把這次查到的東西整理起來，一份可以直接動手的報告長這樣：

標題：390px 寬時菜單頁的「立即點餐」按鈕消失

環境：iPhone 15／iOS 26 Safari；Chrome 156 裝置模式 390×844 也能重現
網址：https://brew.example.tw/menu/

重現步驟：
1. 用 390px 寬打開上面的網址
2. 捲到「本週菜單」區塊

預期：每張菜單卡片下方有「立即點餐」按鈕
實際：按鈕不見了；Computed 顯示 display: none，
      來自 menu.css:58 的 @media (max-width: 400px) .card button
截圖：附上，按鈕位置用框標起來
最小重現：（練習區或 CodePen 的連結，只保留菜單卡片的 HTML 與相關 CSS）

每一欄都對應流程裡的一步。標題寫出現象加上條件（390px 寬、菜單頁），看標題就知道範圍。環境讓對方知道要用什麼重現，也寫出「Chrome 裝置模式也能重現」，對方就不必去找一支 iPhone。重現步驟寫到照做就能看到。預期與實際分開寫，因為「不對」要有一個「對」的樣子才能判斷，修完也用同一條「預期」確認修好了沒。查到的線索（Computed 的值、哪個檔案哪一行）寫進「實際」，對方不用從頭查。

最小重現（minimal reproduction）是把頁面刪到只剩能重現問題的部分，例如只留一張菜單卡片的 HTML 和相關的 CSS。它讓對方不必在整個專案裡找，而且刪的過程常常就找到原因了：刪掉某段 CSS 問題就消失，原因就在那段。這跟流程的「縮小範圍」是同一件事，只是做在程式碼上。

練習

練習 1、2 的預覽是一個 iframe，可以直接在預覽裡按右鍵「檢查」，用這一課的工具除錯。

練習 1：菜單區塊裡的「立即點餐」按鈕變成灰色，頁首和秋季限定區塊的按鈕卻是正常的品牌色。CSS 是六個檔案合在一起的內容（有 layer 也有巢狀規則）。在預覽裡的按鈕上按右鍵「檢查」，用 Styles 與 Computed 找出是哪一條規則讓它變灰、為什麼它會贏，然後只修改那一條規則：不新增規則、不加 !important、不用 ID 選擇器，其他規則都不動。菜單裡的收藏按鈕（♡）本來就該是灰色，修完要維持。HTML 不能改。

練習 2：大安店的門市頁在手機上可以左右滑。撐破版面的有三個元素：門市照片、點餐網址、秋季橫幅，原因各不相同。在 375px 寬的預覽裡用 DevTools 逐一找出它們為什麼比畫面寬，從原因修好：320、375px 寬時整頁不能橫向捲動、三個元素都完整顯示在畫面內、圖片維持原本的長寬比（窄螢幕縮到跟內容區一樣寬，空間夠時維持原本的 480px）、網址在段落裡換行且字級不變、橫幅跟內容區一樣寬；1280px 寬也要正常。不能用 overflow 把超出的部分裁掉或藏起來，也不能把元素藏起來。HTML 不能改。

練習 3：寫 summarize(har)，把 Network 面板匯出的 HAR（已精簡成真實格式的子集）整理成一份摘要，欄位的定義寫在 Summary 型別的註解裡。規則：data: 網址不是網路請求，所有欄位都不算它；傳輸量優先用 response._transferSize，沒有這個欄位時用 response.bodySize，-1 代表未知、當成 0；HTTP 標頭名稱不分大小寫；輸入的 HAR 不能被修改。測試會用三份 HAR 檢查，包括快取命中、304、重新導向與其他工具匯出的檔案。

練習 4：Styles 面板裡一條宣告被劃線（沒有警告圖示），代表什麼？

✓ b：劃線表示同一個屬性有更優先的宣告，往上找沒被劃線的那條，或到 Computed 展開那個屬性看贏的是誰。a、c 錯：值不合法、屬性名稱錯或不支援時，除了劃線還會有警告圖示。d 錯：DevTools 不會因為宣告輸了就刪除它，它仍然在原始碼裡。

練習 5：Network 面板的 Size 欄顯示 18.2 kB 和 64.0 kB 兩個數字，分別是什麼？

✓ b：上面是實際走網路的量，反映下載成本；下面是解壓後的大小，反映瀏覽器解析與記憶體的成本。a 錯：請求本身通常很小，兩個數字都是回應。c 錯：兩個都是實際值。d 錯：從快取拿的請求會直接顯示 (memory cache) 或 (disk cache)。

練習 6：要確認第一次用手機造訪的使用者看到什麼，Network 面板該怎麼設定？

✓ b：你的瀏覽器有快取、辦公室網路又快，跟第一次造訪的手機使用者差很多；停用快取加上節流才接近他們的情況。a 錯：結果只代表「有快取、快網路」的你。c 錯：Preserve log 只是換頁時保留紀錄。d 錯：那是動畫偏好，跟載入無關。

常見錯誤

  • 沒重現就開始改：猜著改上線，等於多加一個變數，原本的 bug 也不一定消失。先回問頁面、裝置、瀏覽器與操作，在自己的電腦上看到問題再動手。
  • 以為裝置模式等於 iPhone：它只模擬尺寸、DPR、觸控與 User-Agent，引擎還是 Chrome。Safari 特有的問題要用真機和 Safari 的網頁檢閱器。
  • 看到被劃線就加 !important 或更長的選擇器：先到 Computed 看贏的是哪一條、在哪個檔案、哪個 layer，通常是那一條寫得太寬，改它就好。
  • 在 DevTools 改好就以為修好了：那些修改重新整理就不見。寫回原始碼，再到其他寬度、狀態（hover、focus、深色模式）驗證一次。
  • 用 overflow-x: hidden 藏撐破版面的元素：元素還是太寬，內容被裁掉，還會讓 sticky 失效。找出是哪個元素、為什麼寬，從原因修。
  • 只在自己有快取、快網路的瀏覽器測：Disable cache 加上節流，才看得到使用者第一次載入的樣子。
  • 把 304 當成錯誤：304 表示快取驗證成功，伺服器不用再傳一次內容。紅色的 4xx、5xx 才是錯誤。
  • bug 報告沒有重現步驟：別人沒辦法驗證，也沒辦法確認修好了。寫環境、步驟、預期、實際，附截圖與最小重現。

Network 面板的欄位（查表用，不用背）

欄位意思看什麼
StatusHTTP 狀態碼4xx、5xx 會變紅；301／302 是重新導向；304 是「你的快取還能用」，是好事
Type資源類型（document、stylesheet、script、font、png、fetch…）CSS 被當成別的類型時，多半是 Content-Type 錯了
Initiator誰發出這個請求：Parser（HTML 解析）、Script（某行程式，點了會跳過去）、Redirect、Other找出「這張圖是哪裡要求載入的」

Time從開始到收完的時間慢的請求再看 Timing

Priority 欄預設沒有顯示：在表頭按右鍵勾選。

Layout 分頁的 Grid 選項

  • Show line numbers／Show line names：畫出格線編號或你命名的格線名稱。grid-column: 2 / -1 放錯格子時，看著編號就知道差在哪。
  • Show area names：畫出 grid-template-areas 的區域名稱（第 9 課）。
  • Show track sizes：每一欄、每一列實際算出來的寬高，檢查 fr、minmax() 的結果。
  • Extend grid lines：把格線延伸到畫面邊緣，用來對齊不同區塊。

DOM 樹上的其他標籤

除了 grid、flex，DOM 樹裡還有其他標籤：scroll 代表這個元素是捲動容器（overflow 是 scroll，或是 auto 而且內容真的超出），container 代表它是 container query 的容器（第 12 課）。

Vue／Vite 專案裡的 Styles

用 Vite 開發時，Styles 顯示的來源可能是 <style> 或轉譯後的檔案。Vue 的 scoped style 會在選擇器後面加上 [data-v-…]，這也算一個屬性選擇器的權重，所以 scoped 樣式常常比全域樣式多贏一截。

小結

  • 除錯流程：重現 → 縮小範圍 → 假設 → 驗證 → 修正 → 防止再發生。DevTools 用在前四步，確定原因才改原始碼。模糊的回報先回問，拆成一個個症狀再逐一處理。
  • 裝置模式模擬寬度、DPR、觸控與 User-Agent，Rendering 模擬深色模式、減少動態、列印與色覺障礙；引擎還是 Chrome，Safari 的問題用真機。
  • Styles 由上到下是層疊的勝負順序；劃線是被蓋掉，加警告圖示是不合法，變淡是沒有效果。:hov 強制狀態、.cls 切換 class、核取方塊停用宣告，都是驗證假設的工具。
  • Computed 以屬性為單位，看最終值與它來自哪個檔案哪一行；盒模型圖看尺寸。
  • 手機可以左右滑，是有元素比畫面寬：找出最外層超出的元素，看它的寬度是誰給的，從原因修，不用 overflow 藏起來。Grid、Flexbox 的問題用 Layout 疊加層看格線與欄寬。
  • Network 看狀態碼、傳輸量與資源大小、時間；Disable cache 加節流模擬第一次用手機造訪；HAR 可以匯出分析，分享前檢查敏感資料。
  • 修好之後用無障礙樹確認角色與名稱、用 Lighthouse 跑第一輪檢查，記得它是實驗室資料。bug 報告要有環境、步驟、預期、實際與最小重現。
