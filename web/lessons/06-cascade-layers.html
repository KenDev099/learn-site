階段 2：CSS 與版面基本功 · 第 6 課

CSS 層疊：來源、權重、繼承與 cascade layers

咖啡店的點餐頁引進了第三方元件庫 coffee-ui，想直接用它的日期選擇器和對話框。上線隔天，設計師貼來一張截圖：商品卡片裡的「加入點餐」按鈕變成藍色、有底線的連結，咖啡色的背景不見了。她順便提到另一件事：按鈕旁邊的數量輸入框，字一直比卡片上的品名小一號，不知道是哪裡設的。你打開自己的 CSS，.btn 的樣式一行都沒少，也從來沒替輸入框設過字級。

瀏覽器沒有壞。同一個元素的同一個屬性，常常有好幾條規則同時在設定它，瀏覽器用一套固定的規則從中選出一個值；沒有任何規則設定它時，也有另一套規則決定值從哪裡來。前者叫層疊（cascade），CSS 的 C 就是它；後者叫繼承，這課後半會講。不懂層疊時，最常見的「修法」是把選擇器越寫越長，最後加上 !important；下一個人遇到同樣的問題只好疊得更高，CSS 就這樣越來越難改。這一課從設計師的兩個回報出發，學完你能說出某條樣式為什麼輸、在 DevTools 裡證明它，並用 @layer 讓第三方樣式永遠排在自己的樣式之下，不必再比誰的選擇器長。

這課的路線：
  1. 為什麼後寫的 .btn 反而輸了：把兩條規則擺在一起看，用 DevTools 證明誰贏（開場問題的最小答案）。
  2. 瀏覽器依什麼順序判輸贏、權重怎麼算：層疊的完整步驟，為什麼 .cu-root .card a 比 .btn 強，加長選擇器為什麼是死路。
  3. 數量輸入框的字為什麼比較小：沒有規則在搶時，值從哪裡來（繼承），以及 reset 該放什麼。
  4. 怎麼讓元件庫永遠輸給自己的樣式：用 @layer 分層，以及 !important 在分層後為什麼反過來。
  5. 團隊怎麼避免下一次再撞：BEM、CSS Modules、Vue 的 scoped 各自怎麼避免衝突，跟 layer 怎麼搭。

為什麼後寫的 .btn 反而輸了？

先把衝突的兩條規則擺在一起。按鈕是 <a class="btn">，放在元件庫要求的外層 .cu-root 與卡片 .card 裡面：

/* 元件庫 coffee-ui.css（先載入） */
.cu-root .card a { color: #1d4ed8; background: transparent; text-decoration: underline; }

/* 自己的 site.css（後載入） */
.btn { color: #fff; background: #6b3e26; text-decoration: none; }

兩條規則都選中了這顆按鈕。元件庫那條的意思是「.cu-root 裡面的 .card 裡面的 a」，按鈕正好符合；你那條的意思是「有 btn 這個 class 的元素」，按鈕也符合。於是按鈕的 color 同時收到 #1d4ed8 和 #fff 兩個值，background、text-decoration 也一樣，每個屬性只能留下一個。這裡先分清兩個名詞：一條規則是一個選擇器加上大括號裡的內容，例如 .btn { … }；大括號裡每一個「屬性: 值」叫一個宣告（declaration），例如 color: #fff。層疊比的就是同一個屬性的多條宣告。

很多人以為「後寫的蓋前面的」，所以後載入的 site.css 應該贏。出現順序確實是比較的項目之一，但它是最後才比的一項。在它之前，瀏覽器會先比權重（specificity），也就是選擇器有多「具體」：描述得越詳細的選擇器，權重越高。精確的算法下一節講，現在只要知道 class 比元素名稱強、兩個 class 比一個 class 強。.cu-root .card a 有兩個 class 和一個元素，.btn 只有一個 class，所以元件庫贏了，跟誰先載入無關。

那為什麼引進元件庫之前一直沒事？因為那時選中這個 a 的只有兩條規則：你的 .btn，和瀏覽器內建「連結是藍色、有底線」的樣式。瀏覽器內建的一般樣式一定輸給網站自己寫的，不用比權重（下一節的「來源」；加了 !important 的例外，下一節也會講）。元件庫的規則跟你的規則同樣是網站寫的，這時才真的要比權重。

這個判斷不用靠猜，可以在瀏覽器裡證明。在 Chrome DevTools 的 Elements 面板選取按鈕，右邊的 Styles 分頁會由強到弱列出所有選中它的規則，輸掉的宣告會被劃線：你會看到 .btn 的 color: #fff 被劃掉，上方 .cu-root .card a 的 color 沒有劃線。旁邊的 Computed 分頁則列出每個屬性最後採用的值，叫計算值（computed value）：瀏覽器處理完層疊與繼承之後的結果。JavaScript 的 getComputedStyle() 讀到的也是它（有些屬性會再多算一步，細節見課末）。除錯的順序是：先在 Styles 找到被劃線的那條，再依下一節的步驟判斷它為什麼輸。

💡 實務上：「樣式沒套上」先開 DevTools，不要先改 CSS
設計師或 QA 回報「按鈕顏色不對」時，先在 Elements 選取那個元素，看目標屬性是被劃線（輸了）、根本沒出現（選擇器沒選中、檔案沒載入），還是有出現但值不對（例如繼承來的值不對，這課的數量輸入框就是這種）。三種情況修法完全不同：沒選中就改選擇器或 class，被劃線才需要處理層疊。常見的坑是只在自己電腦確認：瀏覽器快取了舊的 CSS，或正式環境建置後 CSS 合併的順序跟開發時不同。修好之後在 Computed 分頁確認最後的值，並把「哪條規則蓋掉了它」寫進 PR 說明，下一個人才查得到。

到這裡知道是權重輸了。但權重只是瀏覽器比較的其中一項，它前面還有好幾項；不知道完整的順序，就沒辦法判斷「改哪裡才有用」。

瀏覽器依什麼順序判輸贏？

上一節的按鈕靠權重分出勝負，但權重排在第 5 步。回顧一下，層疊比的是宣告（大括號裡的「屬性: 值」）：同一個元素的同一個屬性有多條宣告時，瀏覽器依序比下面幾項，某一項分出高下就停，後面的不看：

從上往下看每一步在比什麼：

第 0 步「相關性」不是比較，而是篩選：選擇器沒選中這個元素的宣告直接不參加，寫在條件不成立的 @media 區塊裡的也一樣。@media 是「條件成立才套用」的區塊，例如 @media (min-width: 768px) { … } 只在畫面寬度至少 768px 時生效，第 11 課會細講。

第 1 步「來源與重要性」。來源（origin）指這條宣告是誰寫的，有三種：瀏覽器內建的 user agent stylesheet（例如 h1 預設比較大、連結預設藍色），使用者自己加的樣式（user stylesheet，例如視力不好的使用者用瀏覽器擴充功能套上的大字、高對比樣式），以及網站作者寫的樣式，也就是你和元件庫寫的 CSS。一般宣告是作者勝過使用者、使用者勝過瀏覽器，所以你寫的 h1 { font-size: 24px } 一定蓋得掉預設值，不用管權重；上一節「引進元件庫之前為什麼沒事」就是在這一步決定的。加了 !important 的宣告順序反過來：使用者的 !important 勝過作者的，讓需要大字、高對比的使用者有最後決定權。

第 2 步「context」只在 Web Components 的 shadow DOM 裡才會用到，寫 Vue 的日常不會碰到，這課跳過，說明見課末。

第 3 步「inline style」：寫在 style="…" 屬性上的宣告，Vue 的 :style 綁定產生的也是。它在 layer 與權重之前就勝出，樣式表裡的選擇器再長都蓋不掉，只有樣式表裡的 !important 可以。

第 4 步「cascade layer」是這課後半的主角，先記得它排在權重之前：只要兩條宣告在不同的層，權重再高都沒用。

第 5 步「權重」與第 6 步「出現順序」：前面都分不出來，才比選擇器的權重；權重也一樣，才看誰最後出現。「後寫的蓋前面的」只在這最後一步成立。

拿按鈕的兩條宣告走一遍：都選中了按鈕，第 0 步都留下；都是網站作者寫的、都沒有 !important，第 1 步平手；不在 shadow DOM 裡、都不是 inline style，第 2、3 步平手；都還沒分層，第 4 步平手；到了第 5 步權重才分出高下，所以第 6 步的「site.css 後載入」根本沒機會比。日常遇到的衝突幾乎都在第 4 到第 6 步決定。要知道 .btn 差了多少、該怎麼補，得先會算權重。

權重怎麼算？為什麼 .cu-root .card a 比 .btn 強

權重的算法要用到兩種還沒介紹的選擇器。偽類（pseudo-class）依元素的狀態或位置來選，寫一個冒號，例如 :hover 選中滑鼠正停在上面的元素、:first-child 選中父元素的第一個子元素。偽元素（pseudo-element）選的是元素裡的一部分或 CSS 產生的內容，寫兩個冒號，例如 ::before 是在元素內容前面插入的內容、::first-line 是第一行文字。

權重寫成三個數字 (ID, CLASS, TYPE)，把選擇器裡的每個部分歸到其中一欄、數一數有幾個：

欄算進來的例子
IDID 選擇器#app
CLASSclass、屬性選擇器、偽類（pseudo-class）.card、[href]、:hover、:first-child
TYPE元素名稱（型別選擇器）、偽元素（pseudo-element）a、li、::before
不算*、組合符（空白、>、+、~）ul > li 跟 ul li 一樣是 (0,0,2)

套到按鈕上：.cu-root .card a 有兩個 class、一個元素名稱，中間的空白是組合符不算，權重是 (0,2,1)；.btn 是 (0,1,0)。比較時從左到右逐欄比：ID 欄兩邊都是 0，平手；CLASS 欄 2 比 1，元件庫勝出，TYPE 欄就不用看了。

「逐欄比」的意思是左邊一欄分出高下就停，不會進位：11 個 class 的 (0,11,0) 仍然輸給一個 ID 的 (1,0,0)。把三欄當成一個十進位數字相加，是常見的誤解。

知道差多少之後，最直覺的修法是把自己的選擇器寫得更強：

.cu-root .card a.btn { … }   /* (0,3,1)：贏了，但跟元件庫的 DOM 結構綁死 */
#app .btn { … }              /* (1,1,0)：贏了，但之後誰都很難再蓋它 */

兩種都能讓按鈕恢復，代價卻會留給之後的人。第一種把元件庫的外層結構寫進自己的選擇器，元件庫升級改了 class 名稱，你的樣式就默默失效。第二種用了 ID：一個 #app 就讓這條規則壓過所有只有 class 的規則，之後想在某個情況（例如售完時變灰）改它，只能再加 ID 或 !important。所以團隊樣式通常不用 ID 當選擇器，並用 Stylelint 擋下。Stylelint 是 CSS 的 lint 工具，在存檔或 CI 時檢查樣式寫法，selector-max-id: 0 這條規則就是「選擇器裡不准有 ID」。.btn.btn 這種把同一個 class 寫兩次的寫法會算兩次、變成 (0,2,0)，可以小幅提高權重而不用 ID，是不得已時的工具，不是常態。

反過來，也可以刻意把權重壓低。:is(A, B) 選中符合 A 或 B 的元素，權重取括號裡最高的那一個；:where(A, B) 選中的元素一模一樣，但權重永遠是 0，不管括號裡寫什麼。寫給別人覆蓋的樣式（reset、元件庫的預設外觀）適合包在 :where() 裡：選得到元素，但權重是 0，使用的人用一個 class 就蓋得掉。

/* reset：權重 0，任何 class 都能覆蓋 */
:where(ul, ol)[role="list"] { list-style: none; padding: 0; }

:not()、:has()、:nth-child(… of …) 這幾個括號裡能放選擇器的偽類，權重怎麼算有各自的規則，完整對照表放在課末「補充與查表」，練習 1 會用到。

可惜你改不了 coffee-ui 的原始碼，沒辦法替它包上 :where()；只靠權重，就只能跟它比誰寫得長，元件庫下個版本把選擇器寫得更長，你又得跟上。要跳出這場競賽，得用排在權重之前的第 4 步：layer。不過在重排整份 CSS 之前，先處理設計師的第二個回報。分層時最底下會有一層 reset，數量輸入框的修法就要放進那一層。

數量輸入框的字為什麼比較小？

按鈕的問題是好幾條規則在搶同一個屬性；數量輸入框剛好相反，你根本沒替它寫過 font，它的字型和字級是從哪來的？要回答這個，得先知道一個屬性「沒有任何宣告」時會發生什麼事。

這時有兩種可能。有些屬性會繼承（inheritance），沿用父元素的計算值；其他屬性則用規格定義的初始值。繼承存在的理由很實際：字型、文字顏色設在 body 一次，整頁的文字都會跟著，不用每個元素各寫一次。只有部分屬性會繼承，大致的規律是「跟文字有關的會、跟盒子有關的不會」。想像一下 border 如果會繼承，卡片加了框線，裡面每一段文字都會跟著有框線，所以盒子類的屬性設計成不繼承：

會繼承不會繼承
color、font-*（字型、字級、粗細）、line-height、text-align、letter-spacing、visibility、cursor、custom properties（自訂屬性：--brand: #6b3e26 定義、var(--brand) 取用，第 16 課細講）margin、padding、border、background、width／height、display、position

不確定時查 MDN 該屬性頁面的 Formal definition，「Inherited」那一列寫 yes 或 no。

關鍵在於繼承的優先度最低：只要有任何一條宣告選中這個元素，就輪不到繼承，連瀏覽器預設樣式的宣告也算。數量輸入框就是這樣：瀏覽器預設樣式替 button、input、select、textarea 指定了字型（Chrome 是 13.333px，字型依作業系統而定）。輸入框已經有一條 font 宣告，雖然是瀏覽器寫的，body 的網站字型就傳不進來，所以它的字比品名小、字型也不一樣。在 DevTools 選取輸入框，Styles 裡會看到一條標著「user agent stylesheet」的規則在設定字型，這就是證據。修法是明確要求它繼承：button, input, select, textarea { font: inherit; }，通常放在 reset 裡。

同樣的道理也解釋了連結的顏色。瀏覽器預設樣式替 a 指定了連結色，所以把連結放進深色區塊，它不會跟著區塊的白色文字，仍然是看不清楚的藍色。要讓連結跟著文字色，寫 .dark a { color: inherit; }，或 color: currentColor。currentColor 代表「這個元素自己的 color」，用在 color 屬性上時就等於繼承來的值。

font: inherit 裡的 inherit 是四個可以用在任何屬性上的關鍵字之一，它們都在回答「這個屬性要回到哪個值」：

關鍵字意思display 用在 div 上color 用在 a 上
inherit強制用父元素的計算值父元素的 display父元素的文字色
initial規格定義的初始值，跟元素種類無關inline（不是 block！）canvastext（通常是黑色）
unset會繼承的屬性等於 inherit，不會的等於 initialinline父元素的文字色
revert退回上一個來源：作者樣式裡寫它，就退回瀏覽器預設樣式block（div 的預設）瀏覽器的連結色

表中最容易踩到的是 initial。all 屬性一次設定（幾乎）所有屬性，all: initial 常被當成「清空樣式」，但 display 的初始值是 inline，不是 div 平常的 block，所以 div 會變成行內元素。想回到「瀏覽器預設的樣子」用 all: revert，或只重設真正需要重設的那幾個屬性。跟 layer 有關的 revert-layer 放在課末，讀完下一節再看。

💡 實務上：reset 在專案第一天就決定好
新專案一開始通常就放一份 reset（自己寫幾行，或用 modern-normalize 這類維護中的套件），裡面會有 box-sizing、清掉預設 margin、表單控制項的 font: inherit。「按鈕和輸入框的字比旁邊小一號」是 QA 很常回報的視覺問題，常見原因就是少了 font: inherit，跟這課的數量輸入框一樣。已經上線的專案中途加 reset 要小心：每一頁的間距、字級都可能跟著變，要排時間逐頁比對畫面，不要混在功能 PR 裡一起送。用了元件庫的話，先看它是否自帶 reset，兩份疊在一起很難追。

數量輸入框的修法有了，它屬於 reset 這種「修正瀏覽器預設」的樣式。現在可以回到按鈕：怎麼讓元件庫的規則不管權重多高，都排在自己的樣式之下？

怎麼讓元件庫永遠輸給自己的樣式？@layer

回到按鈕。只靠權重，你得一直寫得比元件庫更長；第二節的步驟圖裡，cascade layer 排在權重之前，正好可以換一個比法。cascade layer 是幫樣式分組的機制：你先替每一組取名字、排好順序，例如「第三方」「元件」，再把每條規則放進其中一組（一層）。比較時先看層、再看權重：後宣告的層優先，跟權重無關；權重只在同一層裡面比。

這解決的是「優先順序該由誰決定」。沒有 layer 時，優先順序由選擇器的長度決定，而選擇器長度是寫的人各自的習慣，元件庫寫得長就贏。有了 layer，優先順序由這條樣式的角色決定：第三方的樣式一律放在低層，自己的元件一律放在高層，不管兩邊選擇器怎麼寫。咖啡店的 CSS 可以這樣排：

/* 第一行：宣告所有層的順序，越後面越優先 */
@layer reset, vendor, base, components, utilities;

/* 第三方樣式直接匯入到最低的一層 */
@import url("coffee-ui.css") layer(vendor);

@layer reset {
  *, *::before, *::after { box-sizing: border-box; }
}
@layer base {
  a { color: var(--link); }                /* (0,0,1)，但 base 在 vendor 後面：勝過元件庫的 .cu-root .card a */
}
@layer components {
  .btn { color: #fff; background: var(--brand); }
}
@layer utilities {
  .visually-hidden { position: absolute; width: 1px; height: 1px; /* … */ }
}

逐行說明：

  • @layer 名稱, 名稱, …;：只宣告順序、沒有內容。layer 的順序由第一次出現的位置決定，之後不能改，所以團隊慣例是在最早載入的 CSS 第一行把順序寫死。沒先宣告也能用，但順序就變成各個 @layer 區塊出現的順序，換個 import 順序就可能出事。名稱拼錯（component）會建立一個新的層，排在目前所有層的後面。
  • @import url(…) layer(vendor);：把整個外部樣式檔放進 vendor 層。@import 只能寫在檔案最前面（@charset 與只宣告名稱的 @layer 之後），寫在其他規則後面會被瀏覽器直接忽略。
  • @layer 名稱 { … }：把規則放進那一層。同一層可以分好幾段寫，會合在一起。

現在再走一次步驟：元件庫的 .cu-root .card a 在 vendor 層，你的 .btn 在 components 層。到第 4 步就分出高下，components 宣告在 vendor 之後，.btn 勝出；(0,2,1) 對 (0,1,0) 的權重差距根本沒機會比。連 base 層裡權重只有 (0,0,1) 的 a 也勝過元件庫，卡片裡的一般連結會是自己的連結色。數量輸入框的 font: inherit 則放進 reset 層。

沒分層的樣式比所有 layer 都優先（一般宣告）。這是故意的：舊的樣式不用改就能繼續生效。但反過來，如果你把自己的樣式分層了，卻用沒有 layer() 的 @import 或 <link> 載入第三方 CSS，第三方樣式就變成「沒分層」，蓋過你所有的層。第三方樣式一定要放進最低的層。

每一層的位置都有理由，排錯一層就會出現「誰都蓋不掉」或「怎麼寫都沒用」：

層放什麼為什麼在這個位置
resetbox-sizing、margin: 0、font: inherit只修正瀏覽器預設，誰都能蓋
vendor第三方元件庫、套件附的 CSS你改不到它的原始碼，要讓自己的樣式勝過它
base元素的基本樣式：body 字型、a 顏色、標題勝過第三方，但會被元件覆蓋
components.card、.btn元件的外觀
utilities.visually-hidden、.text-center單一用途、加上就要生效，所以放最後

（Tailwind v4 也用同樣的分層，見課末。）

用一段程式模擬「先比層、再比權重、最後比順序」，前兩個結果就是按鈕分層前後的對照，可以改資料試試看：

DevTools 的 Styles 面板會在規則上方標出它屬於哪個 layer，判斷「為什麼權重高還輸」時先看這個。第三個結果出乎很多人意料：兩邊都加了 !important，後面的 utilities 層反而輸給前面的 vendor 層。元件庫裡如果真的有 !important，分層之後誰贏？

元件庫用了 !important，分層之後誰贏？

先看 !important 本身做了什麼。它把一條宣告移到「重要」那一組，那一組整體勝過所有一般宣告，包括 inline style。問題是它沒有更上一層了：兩邊都 !important 時，又回到比 layer、比權重。團隊裡出現一個，很快就會出現第二個，最後大家又回到比權重。

在 layer 裡，!important 的層順序反過來：

優先度（低 → 高）一般宣告!important 宣告
1reset沒分層的
2vendorutilities
3basecomponents
4componentsbase
5utilitiesvendor
6沒分層的reset

一般宣告整欄都輸給 !important 整欄。inline style 的一般宣告排在一般宣告欄的最上面，inline style 的 !important 又在 !important 欄的最上面。

為什麼反過來？!important 的用途是「這個值不准被後面的人蓋掉」。放在低層的人（reset、第三方）用了 !important，表示他宣告這是必要的，後面的層就不能隨便推翻。這跟第二節「使用者的 !important 勝過作者的」是同一個設計：優先度低的一方用 !important 保住最後決定權。實際後果是：元件庫在 vendor 層用 .vendor-hidden { display: none !important } 藏起來的東西，你在 utilities 層用 !important 也打不開，只能改 HTML 拿掉那個 class，或在更前面的層（reset）寫 !important。

所以分層之後，自己的樣式幾乎不需要 !important。還用得到的情況只有兩種：

  • utility 必須在任何地方生效，例如 .visually-hidden：放在 utilities 層通常就夠了，不需要 !important；只有在還沒導入 layer 的舊專案裡，才需要靠它壓過高權重的元件樣式。
  • 要蓋掉無法修改的 inline style（例如第三方程式寫進 style 屬性的寬度）：樣式表裡只有 !important 能贏過 inline style。

其他情況交給 lint 擋下：Stylelint 有規則可以禁止 !important、限制選擇器的權重上限，例外的地方用註解個別關閉並寫出原因。規則名稱見課末。

💡 實務上：要改第三方元件的樣式，先找它提供的入口
咖啡店後台用了日期選擇器套件、官網嵌了地圖或客服聊天視窗，設計師要求改成品牌色，這是很常見的需求。先查文件有沒有提供自訂屬性（--*）、theme 設定或 class 參數，有就用，套件升級時比較不會壞。真的要覆蓋，就把第三方 CSS 放進 vendor 層、覆蓋寫在自己的層裡，並註解「針對套件哪個版本、為什麼要蓋」，升級套件時把這些地方列入檢查清單。用 iframe 嵌入的內容（例如部分客服或付款視窗）外面的 CSS 根本蓋不到，這時要回頭跟 PM 確認需求，而不是硬改。

到這裡，按鈕回到咖啡色、數量輸入框跟著網站字型，元件庫也排在自己的樣式之下。但這次事故的根源還在：所有人的樣式都在同一個全域空間裡，下一個套件、下一位同事的 .card a，還是可能撞上你的元件。

團隊怎麼避免下一次再撞？CSS 架構怎麼選

layer 決定了「不同角色的樣式誰優先」，但同一層裡面，兩個人寫了同名的 .title 還是會互相影響。權重衝突的根本原因是「大家的樣式都在同一個全域空間」，常見的幾種做法各自從不同方向解決，跟 layer 是互補的：

做法怎麼避免衝突代價跟 layer 怎麼搭
BEM（.card__title--featured）命名規則：每個元素一個 class，權重都是 (0,1,0)名稱長，靠紀律維持放進 components 層
CSS Modules建置時把 class 改成唯一名稱，不會撞名要靠建置工具，覆蓋子元件比較麻煩模組裡可以寫 @layer components { … }
Vue <style scoped>每個選擇器加上元件專屬的屬性，例如 .btn[data-v-f3f3eg9]權重多一個屬性（class 欄 +1）；要改子元件內部要用 :deep()在 scoped style 裡寫 @layer components { … }；層的順序在 main.ts 最先 import 的 CSS 宣告
utility-first（Tailwind）幾乎不寫自己的選擇器，直接在 HTML 上組合 utilityHTML 變長，設計規則要靠設定檔統一Tailwind v4 本身就用 layer

寫 Vue 的你最常遇到的權重問題來自 scoped style。父元件想改子元件裡的 .title，寫 .card .title 不會生效，因為編譯後變成 .card .title[data-v-父元件]，而子元件裡的元素沒有父元件的屬性（只有子元件的根元素例外，它會同時帶父子兩個屬性）。要寫 .card :deep(.title)，編譯成 .card[data-v-父元件] .title，屬性移到父元件自己的元素上，就選得到子元件內部了。

既有專案導入 layer 的實務順序：先把第三方 CSS 放進最低層，風險最小、效果最大，這課的按鈕問題就是在這一步解決的；再把 reset 與 base 分層，最後才整理元件。layer 目前主流瀏覽器都支援（支援起始時間見課末）；如果還要支援很舊的瀏覽器，它們看不懂 @layer，整個區塊會被忽略，樣式等於消失，要先確認使用者的瀏覽器分布。

補充與查表

計算值與解析值：getComputedStyle() 對大部分屬性回傳計算值，但有些屬性回傳的是再往後算出來的「解析值（resolved value）」，例如 width 會是 px。日常除錯不用分這麼細。

層疊第 2 步 context：shadow DOM 是 Web Components 用來把元件內部的 DOM 和樣式跟外面隔開的機制。這一步比的是宣告來自 shadow DOM 的裡面還是外面，寫 Vue 的日常不會碰到。

inline style 的舊說法：舊文章會說 inline style 的權重是 (1,0,0,0)，結果一樣，但現在的規格把它列成獨立的一步。

選擇器清單偽類的權重（查表用，不用背；練習 1 會用到）：這幾個偽類的括號裡可以放好幾個選擇器。:is(A, B) 選中符合 A 或 B 的元素；:where(A, B) 選中的一樣，只是權重不同；:not(A) 選中不符合 A 的元素；:has(A) 選中「裡面有符合 A 的東西」的元素，例如 .card:has(img) 是有圖片的卡片（第 12 課細講）；:nth-child(2n+1 of .x) 先只看符合 .x 的兄弟元素，再選其中第 1、3、5… 個。

選擇器權重說明
.card a(0,1,1)一個 class、一個元素
a.btn:hover(0,2,1)偽類算 class 欄
#app .card .btn(1,2,0)一個 ID 就壓過所有沒有 ID 的選擇器
p::before(0,0,2)偽元素算型別欄（兩個冒號）
:is(#a, .b)(1,0,0):is() 本身不算，取參數裡最高的那一個，即使實際選中的是 .b
div:not(.inner) p(0,1,2):not()、:has() 跟 :is() 一樣
:where(#menu) .item(0,1,0):where() 整個是 0，不管裡面寫什麼
li:nth-child(2n+1 of .x)(0,2,1):nth-child 是一個偽類，再加上 of 後面最高的
.btn.btn(0,2,0)同一個 class 寫兩次會算兩次

revert-layer：跟 revert 類似，但只退回到上一個 cascade layer 的值，而不是一路退回瀏覽器預設。

Tailwind CSS v4 的分層：Tailwind CSS 是 utility-first 的 CSS 框架。@import "tailwindcss"; 載入的檔案第一行就是 @layer theme, base, components, utilities;，Tailwind 自己的樣式全部放在這些層裡（Tailwind 4.2 的 index.css）。所以寫在 layer 外面的自訂 CSS 會勝過所有 Tailwind 的 utility，這是規則，不是 bug。

Stylelint 規則：selector-max-id: 0 禁止 ID 選擇器；declaration-no-important 禁止 !important；selector-max-specificity（例如設 "0,2,1"）限制權重。

瀏覽器支援：cascade layer 是 Baseline widely available（2024-09-14 起；Baseline 的意思見第 4 課）。

練習

練習 1：寫 specificity(selector)，回傳選擇器的權重 [ID 欄, class 欄, 型別欄]；再寫 compare(x, y)，比較兩個選擇器的權重，x 比較高回傳 1、比較低回傳 -1、一樣回傳 0。要支援：型別、*、class、ID、屬性、偽類、偽元素（::）、組合符、:is()／:not()／:has()（取參數清單裡最高的）、:where()（0），以及 :nth-child(An+B of S)（一個偽類再加上 S 裡最高的）。輸入是單一個選擇器（最外層沒有逗號），不會有舊寫法的單冒號偽元素（:before）與跳脫字元。讀名稱、找右括號、切逗號的 helper 已經寫好。測試會跑 40 多組手寫案例和 300 組隨機選擇器。

練習 2：咖啡店引進了第三方元件庫 coffee-ui，它的樣式檔 06-coffee-ui.css 選擇器都掛在 .cu-root 底下（例如 .cu-root .card a），權重很高，目前還沒載入。這題只改 CSS：第一行宣告 layer 順序 reset, vendor, base, components, utilities；第二行用 @import url("06-coffee-ui.css") layer(vendor); 把元件庫放進 vendor 層；再把自己現有的樣式照註解分別放進 reset、base、components、utilities 層。完成後卡片與按鈕要是自己的樣式、卡片裡的連結是自己的連結色、.visually-hidden 在按鈕裡也有效。不能加 ID 或疊 class 提高權重（每個選擇器最高 (0,2,1)），也不能用 !important（.visually-hidden 除外）。

練習 3：點餐頁有三個繼承問題：按鈕與輸入框的字型、字級跟網站不一樣；深色的會員專區裡，連結是瀏覽器預設的藍色，看不清楚；外送小工具的容器用 all: initial 想清掉網站樣式，結果它變成行內元素。只改 CSS，用繼承相關的關鍵字修好：表單控制項跟著網站的字型與字級（字型清單只在 body 寫一次）；深色區塊的連結跟著區塊的文字色，.dark 的顏色以後改了也要跟著變；重設區塊要是區塊元素，而且仍然清掉網站加在 div 上的框線與 padding。

練習 4：兩條宣告都設定 .btn 的 color：一條在 @layer components 裡、選擇器是 #main .btn；另一條在 @layer utilities 裡、選擇器是 .text-white。layer 的宣告順序是 components, utilities。誰勝出？

✓ b：層疊先比 layer、再比權重，權重只在同一層裡面比。utilities 宣告在後，它的一般宣告勝過 components 裡任何權重的宣告。a 錯：權重 (1,1,0) 在不同層之間沒有作用。c 錯：出現順序是最後一步，在 layer 已經分出高下時不會比到。d 錯：衝突一定會選出一條。

練習 5：:where(#menu) .item 的權重是？

✓ b：:where() 整個的權重是 0，不管裡面有沒有 ID，只剩 .item 的 (0,1,0)。a 是把 :where() 當成 :is() 的結果。c 只算了括號裡的 ID。d 忘了 .item 在 :where() 外面。

練習 6：body 設定了網站字型，為什麼 <button> 還是系統字型？

✓ b：繼承只在元素完全沒有宣告時才發生，user agent stylesheet 的宣告也算，所以要自己寫 font: inherit。a 錯：直接替 button 設定字型就會生效。c 錯：!important 只影響宣告之間的勝負，不會讓沒有宣告的屬性改成繼承。d 錯：設在 body 或 html 都會繼承給一般元素。

常見錯誤

  • 樣式沒套上就直接改 CSS：先在 DevTools 確認屬性是被劃線、根本沒出現，還是繼承來的值不對，三種修法不同。
  • 用提高權重解決衝突：加 ID、疊 class，下一個人只能疊得更高，最後只剩 !important。先釐清這條樣式屬於哪一層，用 @layer 排順序。
  • 以為三欄權重可以相加：(0,11,0) 輸給 (1,0,0)，從左到右逐欄比。
  • 以為表單控制項會自動繼承字型：瀏覽器預設樣式已經替它們設了字型，有宣告就不繼承，要寫 font: inherit。
  • all: initial 當成清空：連 display 也變回 inline。要回到瀏覽器預設用 all: revert，或只重設需要的屬性。
  • 第三方 CSS 沒有分層：自己的樣式分層了，元件庫卻用 <link> 或沒有 layer() 的 @import 載入，它就變成「沒分層」，勝過你所有的層。用 @import url(…) layer(vendor) 放進最低層。
  • @import 寫在其他規則後面：瀏覽器直接忽略，不會報錯，元件庫就像沒載入。它只能接在 @layer 宣告之後、所有規則之前。
  • 以為 !important 在後面的層比較強：!important 的層順序是反的，第三方在低層的 !important 你在高層蓋不掉。
  • Vue scoped style 改不到子元件：scoped 會加上 [data-v-xxx]，子元件裡的元素沒有這個屬性；用 :deep()。

小結

  • 「樣式沒套上」先開 DevTools：Styles 看哪條宣告被劃線，Computed 看最後的計算值。
  • 同一個屬性有多條宣告時，依序比：來源與 !important → inline style → cascade layer → 權重 → 出現順序，某一步分出高下就停。「後寫的贏」只在最後一步成立。
  • 權重是 (ID, class／屬性／偽類, 型別／偽元素)，逐欄比不進位；:is()、:not()、:has() 取參數裡最高的，:where() 是 0。靠加長選擇器或 ID 贏，只會讓下一次更難改。
  • 沒有宣告時，文字類屬性會繼承，盒子類不會；任何宣告（包括瀏覽器預設）都會讓繼承失效，所以表單控制項要 font: inherit。initial 是規格的初始值、unset 看屬性會不會繼承、revert 退回瀏覽器預設。
  • 第一行宣告 @layer reset, vendor, base, components, utilities;，第三方用 @import … layer(vendor) 放進低層，優先順序就由樣式的角色決定，不由選擇器長度決定。沒分層的樣式勝過所有層，!important 的層順序反過來。
  • 團隊用 lint 限制 !important 與權重，用 layer 與命名規則（BEM、CSS Modules、scoped）避免衝突。
