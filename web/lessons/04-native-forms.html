階段 1：HTML 與可操作的網頁 · 第 4 課

原生表單：label、input、autocomplete、驗證與錯誤提示

咖啡店開放線上預約座位，表單上線一週，客服收到的抱怨都跟它有關：手機上打電話號碼時跳出全英文鍵盤；有人用密碼管理器自動填入，Email 跑進了電話欄；一位視障客人說螢幕閱讀器每一格都只唸「編輯文字」，不知道要填什麼；還有人送出後才發現自己能同時勾「內用」和「外帶」。後台也有問題：收到的電話少了開頭的 0，偶爾還有人數 999 的預約。

這課的任務是把這張預約表單從頭修到尾：每個人（包括用手機、用鍵盤、用螢幕閱讀器的人）都填得完，送到伺服器的是一筆格式正確的預約。這些問題大多不用寫 JavaScript，HTML 本身就有解法；最後一節會說明為什麼前端修得再好，你寫的後端 API 還是要自己再驗一次。

這課的路線：
  1. 這份預約表單錯在哪、怎麼給每個欄位一個名稱：先看懂表單送出時做了什麼，再用 <label> 讓欄位看得到、也唸得出名稱，以及 placeholder 為什麼代替不了它。
  2. 手機鍵盤與自動填入、一組 radio：type、inputmode、autocomplete 各管什麼；內用和外帶怎麼變成「只能選一個」，並有共同的題目。
  3. 擋下格式錯誤、什麼時候才亮紅框：瀏覽器內建的驗證怎麼運作，為什麼頁面一打開就整片紅，怎麼改成使用者動過才提示。
  4. 錯誤怎麼讓每個人都知道：不只靠顏色，螢幕閱讀器也唸得出來。
  5. 送出與安全邊界：按 Enter 送出的是哪個按鈕；前端驗證擋不住 curl，後端為什麼一定要再驗。
這課會用到：
  • 第 2 課的可及名稱（accessible name）：輔助科技（例如螢幕閱讀器）唸出來的元素名稱，按鈕的名稱來自它的文字，圖片的來自 alt。
  • 第 2 課的 <button>：在 <form> 裡沒寫 type 的按鈕就是送出按鈕。

這份預約表單錯在哪？

先看現在線上的寫法。它在桌機上看起來沒問題，每一格都有灰字提示，按鈕也按得下去：

<form action="/reservations" method="post">
  <input name="name" placeholder="姓名">
  <input name="phone" type="number" placeholder="手機號碼">
  <input name="email" placeholder="Email" autocomplete="off">
  <input type="radio" name="mode-a" value="dine-in"> 內用
  <input type="radio" name="mode-b" value="takeout"> 外帶自取
  <button>送出預約</button>
</form>

要看懂它錯在哪，先知道使用者按下「送出預約」時，瀏覽器做了什麼。<form> 本身就會送資料，不需要寫 fetch：瀏覽器走過表單裡每一個有 name 的欄位，把它的 name 和目前的值配成一對（name=王小明、phone=0912345678），radio 只取被選中的那一個的 value，再用 method 指定的方式（這裡是 POST）送到 action 指定的網址 /reservations。後端收到的就是這些「名稱＝值」，表單上畫了什麼、灰字寫了什麼，伺服器都看不到。

這也說明了 name 的角色：它是送到伺服器的欄位名稱，後端靠它取值。這課後面還會出現 id，兩者常被搞混：id 只在頁面裡用，讓 label、CSS、JavaScript 找到這個元素，不會被送出去。

用這個角度回頭看，上面的表單有四個問題，分別傷到不同的人：

寫法誰會遇到問題發生什麼事
只有 placeholder所有人、螢幕閱讀器使用者開始輸入後提示就消失，填到一半不確定這格在問什麼；有些輔助科技不把 placeholder 當名稱，只唸「編輯文字」
電話用 type="number"手機使用者、伺服器number 只接受數字格式：輸入 0912-345-678 或 +886912345678 時，欄位的值會變成空字串；程式或伺服器把它當數字處理時，開頭的 0 會不見（0912… 變成 912…）；桌機上滾輪捲過去還會改到值
Email 沒有 type、加了 autocomplete="off"手機使用者鍵盤沒有 @ 鍵；瀏覽器不能自動填入，只能一個字一個字打
兩個 radio 的 name 不同所有人瀏覽器把它們當成兩組，兩個都能選、選了取消不掉

第一列影響最大：欄位連名稱都沒有，其他問題修好了，使用者還是不知道每一格要填什麼。下一節先從它開始。

螢幕閱讀器只唸「編輯文字」：怎麼給每個欄位一個名稱？

螢幕閱讀器唸一個欄位時，唸的是它的可及名稱。現在的欄位只有 placeholder，沒有正式的名稱，所以有些輔助科技只唸得出角色「編輯文字」。HTML 給欄位名稱的元素是 <label>：它是一段顯示在畫面上的文字，和某個欄位「關聯」起來之後，就成為那個欄位的名稱。

關聯起來會同時得到三個效果：

  • 螢幕閱讀器聚焦到欄位時唸出 label 的文字（label 成為欄位的可及名稱），視障客人聽到的會是「手機號碼，編輯文字」。
  • 點 label 文字等於點欄位，可以點的範圍變大，在手機上特別有用；radio 和 checkbox 本身很小，這點更明顯。
  • 用語音控制的使用者可以說「點姓名」，直接操作那一格。

關聯有兩種寫法，效果相同：

<!-- 寫法一：for 對到欄位的 id（欄位和 label 可以分開排版） -->
<label for="phone">手機號碼</label>
<input id="phone" name="phone" type="tel">

<!-- 寫法二：label 把欄位包起來（radio、checkbox 常用） -->
<label><input type="radio" name="mode" value="dine-in"> 內用</label>

寫法一是這課主要用的。它靠 id 把兩個元素接起來，所以有兩件事要小心：

  • for 的值必須和 id 一字不差。打錯不會報錯，畫面也一樣，只是關聯失效：點 label 不會聚焦，螢幕閱讀器也唸不到。檢查方法是在 DevTools 的 Accessibility 面板看欄位的 Name，是空的就是沒接上。
  • id 在整頁要唯一。Vue 元件被用兩次時，寫死的 id="phone" 會重複，第二個 label 會指到第一個欄位；Vue 3.5 起可以用 useId() 產生唯一的 id。

注意 name 和 id 在上面的例子剛好都是 phone，但它們是兩回事：name 決定送到伺服器的是 phone=0912345678，id 只是讓 label 找到欄位。改 id 不影響後端，改 name 後端就收不到資料。

那原本的 placeholder 為什麼不夠？它看起來也是在告訴使用者「這格填姓名」：

  • 使用者一開始輸入就消失。填到一半被打斷、或回頭檢查時，看不到這格原本在問什麼。
  • 瀏覽器預設的 placeholder 是淺灰色，對比通常不到 WCAG 要求的 4.5:1，視力不好的人看不清楚。
  • 它也常被誤認成「已經填好的值」，使用者以為不用填就跳過。

placeholder 適合放範例（例如 0912345678），但格式說明更適合寫成欄位下方一直看得到的提示文字，後面講錯誤訊息時會教怎麼把它連到欄位。

另一個常見的替代做法是只寫 aria-label="姓名"。它確實會成為可及名稱，螢幕閱讀器唸得出來；但畫面上一樣沒有名稱，看得到畫面的使用者仍然只看到一個空格，填到一半一樣會忘記這格在問什麼。所以規則是：每個欄位都要有看得到的 <label>。

💡 實務上：設計稿只畫 placeholder 時，先跟設計師對齊
很多設計稿為了畫面乾淨，欄位只放灰字提示、沒有 label，或用「點進去 label 才浮上去」的浮動標籤。接手時先問設計師能不能把 label 放在欄位上方；做成共用的輸入框元件（例如 Vue 元件）時，把 label 文字設成必填的參數，id 用前面提到的 useId() 自動產生，之後每個表單都不會漏。審查同事的程式碼（code review）時看到只有 placeholder 或只有 aria-label 的欄位就提出來，比上線後再補整站表單便宜很多。

現在每一格都有名稱了，使用者知道要填什麼。但「怎麼填」還有問題：手機打電話跳出英文鍵盤，自動填入把 Email 放錯格，後台收到的電話少了 0。這些都跟欄位的「種類」有關。

手機鍵盤不對、自動填入填錯格：type、inputmode、autocomplete 各管什麼？

手機瀏覽器跳出哪種鍵盤、密碼管理器把哪筆資料填進哪一格，都不是瀏覽器猜的，而是讀欄位上的三個屬性。這三個屬性常被混在一起，但各管一件事：

  • type：欄位的種類。它決定值的格式、瀏覽器要不要檢查格式（email、url）、手機用哪種鍵盤、有沒有日期選擇器。沒寫就是 text，什麼都不檢查，鍵盤也是一般文字鍵盤，這就是 Email 欄沒有 @ 鍵的原因。
  • inputmode：只決定手機要顯示哪一種鍵盤（numeric、tel、email、decimal…），不改變驗證，值還是字串。它用在「種類是文字，但只會打數字」的欄位。
  • autocomplete：告訴瀏覽器這格該填使用者的哪一筆資料（姓名、電話、地址、一次性驗證碼）。它的值是一組固定的關鍵字，稱為 token，例如 name、tel、email。自動填入與密碼管理器就是靠這個 token 判斷，沒寫時只能從 name、label 文字去猜，猜錯就會把 Email 填進電話欄。

電話為什麼不能用 type="number"？因為 number 代表「數量」：值要是一個數字，所以 -、+886 會讓值變成空字串，當數字處理時開頭的 0 也會消失。電話號碼看起來是數字，但它不會拿來加減，開頭的 0 有意義，本質上是一段文字。判斷方式是問自己「這個值會不會拿來計算」：會，才是 number。

預約還需要一個人數欄位：現在的表單漏了它（練習 1 會補上），後台那筆 999 是從哪來的，留到最後一節回答。下表把姓名、電話、Email 和人數放在一起看該用什麼寫法，最後一列是常見的對照（會員卡號）：

欄位建議寫法為什麼
姓名autocomplete="name"完整姓名一格就好；拆成姓、名要用 family-name、given-name，但不同文化的姓名結構差很多，非必要不拆
手機號碼type="tel" autocomplete="tel"tel 的值是字串，保留開頭的 0、+886、-；手機顯示電話鍵盤。瀏覽器不檢查電話格式（各國不同），格式要自己用 pattern 限制
Emailtype="email" autocomplete="email"鍵盤有 @；瀏覽器會檢查「有沒有 @ 和網域」這種基本格式
人數type="number" min="1" max="8" 或 <select>真的是「數量」才用 number：有上下箭頭、min／max 驗證。代價是桌機滾輪會改到值、可以輸入 e（科學記號）。選項少時 <select> 更不容易填錯
統一編號、郵遞區號、會員卡號inputmode="numeric"＋pattern看起來是數字但不是「數量」：開頭的 0 有意義、不會加減。用文字欄位，只叫出數字鍵盤

簡訊驗證碼、地址、日期這幾種欄位的寫法收在課末「補充與查表」，查表用，不用背。

原本的 Email 欄還有 autocomplete="off"。這個值不要到處加：它讓自動填入失效，使用者要手打每一格；大部分瀏覽器對帳號密碼欄位也不理會它，想用它擋密碼管理器其實擋不住。無障礙規範也要求反過來做：WCAG 1.3.5 Identify Input Purpose（AA 級）要求收集使用者本人資料的欄位，要讓程式判斷得出用途，做法就是寫對 autocomplete token（axe 的 autocomplete-valid 規則會檢查 token 寫得對不對）。真的不該自動填的欄位（例如「輸入對方的手機號碼來轉送禮物卡」，填進使用者自己的號碼就錯了）才關，而且只關那一格。

💡 實務上：註冊、結帳、預約表單上線前，實際用自動填入走一次
這類表單欄位越好填，越少人填到一半放棄，PM 很在意。上線前用手機的 Chrome、Safari 各自動填入一次，確認電話、Email、地址落在對的欄位。有人要求「為了資安加 autocomplete="off"」時，先問清楚要防的是什麼；真的有不該自動填的欄位，就只關那一格，不要整張表單關掉。自動填入的值伺服器一樣要驗證；被填入的欄位會進入 :autofill 狀態、換上瀏覽器自己的底色，自訂樣式時記得確認這時文字還清楚。

每個欄位單獨看都對了。剩下的抱怨是「內用和外帶可以同時選」，這不是單一欄位的問題，而是兩個欄位之間的關係。

內用和外帶可以同時選：怎麼讓一組 radio 只能選一個？

radio 是「一組選一個」的欄位。但 HTML 裡沒有一個叫「組」的元素，瀏覽器是靠 name 相同來判斷哪些 radio 是同一組。同組的 radio 會有這些行為：

  • 只能選一個，選了別的，原本選的自動取消。
  • 鍵盤用 Tab 進入這組後，用方向鍵在組內切換。
  • 送出時只送被選中那個的 value，例如 mode=dine-in。

原本的寫法 name="mode-a" 和 name="mode-b" 不同，瀏覽器就當成兩組各一個選項：兩個都能選，而且一組只有一個選項，選了就取消不掉。改成同一個 name="mode" 就修好了。

選擇的行為對了，名稱還差一點。每個 radio 用 label 包起來後，名稱是「內用」「外帶自取」，但題目本身「用餐方式」沒有地方放。螢幕閱讀器使用者用 Tab 跳到這組時，只聽到「內用，選項按鈕」，不知道是在選什麼。HTML 的做法是用 <fieldset> 把整組包起來，題目放在 <legend>。這樣螢幕閱讀器進入這組時會先唸「用餐方式，群組」，再唸「內用，選項按鈕，1／2」。

<fieldset>
  <legend>用餐方式</legend>
  <label><input type="radio" name="mode" value="dine-in" checked> 內用</label>
  <label><input type="radio" name="mode" value="takeout"> 外帶自取</label>
</fieldset>

<legend> 必須是 fieldset 的第一個子元素，放在其他位置就不會被當成這組的標題。上面的例子還在「內用」加了 checked，讓它預設被選中：使用者一定得選其中一個時，先選最常見的，少一步，也不會出現「沒選就送出」的情況。

同樣的寫法也適用其他情況。checkbox 是「可以選多個」，例如「加購：可頌、起司蛋糕」，一組 checkbox 也用 fieldset 包；單獨一個 checkbox（「我同意預約規則」）用 label 就好，因為它本身的文字就是完整的題目。fieldset 也適合把「聯絡資料」「取餐資訊」這種一段相關欄位包起來；但不要每個欄位都包，螢幕閱讀器每進一組就唸一次群組名稱，包太多反而吵。

到這裡，表單「填得完」了：每格有名稱、鍵盤對、自動填入對、radio 只能選一個。可是使用者還是可以什麼都不填就送出，或把電話打成 0912-345-678，伺服器照樣收到一筆壞資料。下一步要在送出前擋下它們。

怎麼在送出前擋下空白和格式錯誤的電話？

瀏覽器內建一套表單驗證，稱為約束驗證（constraint validation）：在欄位上寫限制條件（約束），使用者按送出時，瀏覽器檢查每個欄位，有不合格的就不送出，聚焦到第一個錯誤欄位並顯示提示泡泡。整個過程不用寫 JavaScript。

限制條件就是欄位上的屬性：

屬性意思例子
required不能空白；radio 同組只要一個有 required，整組就必選姓名、電話
minlength／maxlength字數下限／上限（maxlength 會直接擋住輸入）備註最多 200 字
pattern值要完全符合這個正規表示式手機 09\d{8}
min／max／step數字、日期的範圍與間隔人數 1～8；日期不能早於今天
type="email"、type="url"內建的格式檢查Email

預約表單的手機號碼要「09 開頭、共 10 個數字」，tel 不檢查格式，所以要靠 pattern。pattern 的值是一個正規表示式，有一個和平常寫 JavaScript 不同的地方：它自動比對整個值。瀏覽器會把它包成 ^(?:你的 pattern)$，不用自己寫 ^ 和 $，所以 09\d{8} 不會讓 0912345678999 通過（如果只是「包含」就算數，多打幾碼也會過）。

另一個地方是空白值：pattern 只檢查有填的值，空白不會被它擋下。所以必填的欄位要 required 和 pattern 一起寫，一個管「有沒有填」，一個管「填得對不對」。下面用 JavaScript 模擬瀏覽器怎麼套用 pattern，執行後看每個值是通過還是不通過，特別是 0912345678999 和空字串：

有時候你會在 <form> 上看到 novalidate，它會關掉送出時的檢查和提示泡泡。用途是：你要用 JavaScript 自己顯示錯誤訊息、錯誤摘要時（例如 Vue 的表單元件），由程式讀 validity 或自己的規則來顯示。沒有替代方案時不要加，否則等於沒有驗證。

驗證擋住了錯誤，接下來要讓使用者「看到」哪一格錯。直覺的做法是用 CSS 把無效的欄位框成紅色，但這一步有一個陷阱。

為什麼頁面一打開就整片紅框？

CSS 有一個 :invalid 選擇器，選到「目前沒通過約束驗證」的欄位，很多人第一個想到的就是寫 input:invalid { border-color: red }。問題在於「目前」：必填欄位一開始就是空的，空的就是沒通過 required，所以頁面一打開，每個必填欄位都是紅框，使用者還沒動就像被罵了一頓。

我們要的其實是「使用者填過、而且填錯」才顯示。CSS 的 :user-invalid 就是這個意思：使用者改了值並離開欄位（或嘗試送出表單）之後，值無效才成立。:user-valid 是對應的有效狀態。主流瀏覽器都已經支援很久，可以直接用（支援度的查法見課末）。

/* 不要：一載入就整片紅 */
input:invalid { border-color: #b00020; }

/* 要：使用者動過之後才顯示 */
input:user-invalid { border-color: #b00020; border-width: 2px; }
input:user-invalid ~ .error { display: block; }

第二段的最後一行把錯誤文字也一起顯示出來。~ 是「後面的兄弟元素」選擇器，所以錯誤文字要放在欄位後面，而且和欄位同一層。結構比較複雜、錯誤文字不在欄位後面時，可以改從外層去選：.field:has(input:user-invalid) .error，:has() 選的是「含有某個子孫元素的元素」，第 12 課會詳細教。

注意上面的錯誤樣式除了換顏色，還加粗了框線、顯示錯誤文字。這不是裝飾：只換顏色的話，有一群使用者還是看不出哪裡錯，而螢幕閱讀器使用者連那段錯誤文字都聽不到。下一節處理這兩件事。

紅框出現了，看不出顏色、看不到畫面的人怎麼知道錯在哪？

好的錯誤提示要同時滿足四件事：

  1. 在欄位旁邊：使用者看得到是哪一格錯。
  2. 說怎麼改：「09 開頭共 10 碼，例如 0912345678」比「格式錯誤」有用。
  3. 不只靠顏色：大約每 12 位男性就有 1 位有某種色覺異常，紅框和灰框對他們可能差不多。WCAG 1.4.1 要求顏色不是傳達資訊的唯一方式，所以要加上文字、圖示或粗細變化，就是上一節加粗框線、顯示錯誤文字的原因。
  4. 螢幕閱讀器也聽得到：畫面上的錯誤文字只是放在欄位附近，螢幕閱讀器聚焦欄位時只唸欄位的名稱，不會自己去找旁邊的段落。

第 4 點要靠 aria-describedby。label 提供的是欄位的「名稱」，aria-describedby 提供的是「補充說明」：它的值是頁面上其他元素的 id（可以有好幾個，用空白分隔），螢幕閱讀器聚焦到欄位時，先唸名稱，再唸這些元素的文字，例如「手機號碼，編輯文字，09 開頭共 10 碼，不加 -，例如 0912345678」。講 label 時說過「格式說明寫在欄位下方的提示文字」，就是用它連到欄位：

<label for="phone">手機號碼</label>
<input id="phone" name="phone" type="tel" autocomplete="tel"
  required pattern="09\d{8}" aria-describedby="phone-hint">
<p class="hint" id="phone-hint">09 開頭共 10 碼，不加「-」，例如 0912345678</p>
<p class="error">⚠ 手機號碼格式不對</p>

只用 HTML 和 CSS 能做到的到此為止：提示文字連到了欄位，錯誤文字看得到，但錯誤文字本身沒有連到欄位，螢幕閱讀器聚焦欄位時不會唸到它。CSS 只能改樣式，改不了 aria-describedby 的值，所以完整的做法需要 JavaScript：

  • 欄位無效時加 aria-invalid="true"，螢幕閱讀器會唸「無效輸入」；並把錯誤訊息的 id 也加進 aria-describedby（aria-describedby="phone-hint phone-error"）。錯誤訊息隱藏時不要放進去，否則沒錯也會被唸出來。
  • 送出失敗時在表單上方顯示錯誤摘要，焦點移到摘要或第一個錯誤欄位。Vue 的寫法在 Vue 課第 18 課。

還有一個常見的做法要避開：用 disabled 擋住送出按鈕「直到全部填對」。看起來很保護使用者，實際上使用者只看到一個按不下去的按鈕，不知道是哪一格還沒填好；disabled 的按鈕鍵盤聚焦不到、螢幕閱讀器也常略過它。讓按鈕一直能按，按下去由驗證告訴使用者哪裡錯，上面做的錯誤提示才有機會出現。

💡 實務上：錯誤訊息是一份要和 PM、設計一起定的清單
規格裡每個欄位都該寫清楚：規則是什麼、錯了顯示哪句話。前端擋得到的只有格式；「這個時段已額滿」「這支手機今天已預約過」只有伺服器知道，回來的錯誤也要顯示在對應的欄位旁或錯誤摘要裡，不要只跳一個「送出失敗」。資深工程師驗收時會用鍵盤從頭填到尾、故意每格填錯一次，再開螢幕閱讀器（macOS 的 VoiceOver）聽錯誤有沒有被唸出來。

錯誤提示做好了，最後要確認的是「送出」這個動作本身。設計師想在送出按鈕旁邊加一個「清除重填」，這看似無害，卻牽涉到按 Enter 時送出的是哪個按鈕。

按 Enter 送出的是哪個按鈕？

第 2 課提過：在 <form> 裡的 <button> 沒寫 type 就是 submit，按下去就送出表單。所以表單裡只要有其他用途的按鈕（「加一位同行者」「顯示密碼」），都要寫 type="button"，否則一按就把還沒填完的表單送出去。

使用者也常常不按按鈕：在文字欄位裡按 Enter，表單一樣會送出，這稱為隱式送出（implicit submission）。瀏覽器的做法是找表單裡依原始碼順序的第一個 submit 按鈕，對它觸發 click，就像使用者按了它。這帶來兩個後果：

  • 第一個 submit 按鈕必須是主要動作。把「清除」寫成沒有 type 的 button 放在「送出」前面，它就變成第一個 submit 按鈕，使用者在電話欄按 Enter 就把表單清掉了。
  • 這個預設按鈕是 disabled 時，按 Enter 不會送出，這是上一節不要用 disabled 擋送出的另一個理由。

至於設計師想加的「清除重填」本身，也不要用 type="reset"。它會把所有欄位還原成初始值，一誤觸就要重填，MDN 也建議不要用。真的要提供「重新開始」，用連結回到空白表單，或在送出成功後由頁面自己清空。

所以按鈕的排法是：主要動作（送出）放前面，次要動作放後面。這樣 Tab 順序也就是「填完欄位 → 送出 → 其他」，鍵盤使用者填完最後一格，下一個停的就是送出。

到這裡，表單從填寫到送出都修好了，送出的是一筆經過驗證的預約。但開頭後台收到的「人數 999」，真的是從這張表單來的嗎？

前端都擋好了，後端為什麼還要再驗一次？

前端驗證能讓使用者早點發現打錯，但它擋不住任何人。所有驗證都在使用者的瀏覽器裡執行，而瀏覽器是使用者控制的：在 DevTools 拿掉 required、關掉 JavaScript，或者根本不打開表單，直接用 curl 送請求，都不會經過你寫的任何檢查。第一節說過，伺服器只收到「名稱＝值」，它分不出這些值是從你的表單來的，還是有人手打的：

curl -X POST https://brew.example.tw/reservations \
  -d 'name=&phone=hello&party=999'

這個請求的姓名是空的、電話是 hello、人數 999，伺服器一樣會收到。所以前端驗證的定位是「改善體驗」，伺服器收到的資料一定要再驗證一次：必填、格式、範圍，以及前端根本無從判斷的規則，例如這個人能不能預約這個時段。後端怎麼寫在 NestJS 課第 7 課。表單用 Cookie 登入狀態送出時，還要防跨站請求偽造（CSRF），在 認證課第 6 課。

表單的 method 也和資料安全有關。method="get" 會把欄位放進網址（/reservations?name=王小明&phone=0912345678），網址會留在瀏覽器歷史、伺服器 log、分析工具裡，等於把客人的電話寫進好幾個地方。搜尋表單用 GET 沒問題，網址還可以分享；有個人資料、會改變資料的表單（例如這張預約表單）用 method="post"。

練習

三題都是同一張預約表單。預覽裡的表單不會真的送出。

練習 1：把預約座位表單修好。每個欄位要有看得到的 label，點 label 會聚焦到欄位；姓名、電話、Email 用正確的 type 與 autocomplete；人數只能是 1～8 人；「用餐方式」的兩個 radio 是同一組，用 fieldset＋legend 包起來。姓名、電話、Email、人數欄位的 name 不要改（name 是送到伺服器的欄位名稱）；兩個 radio 例外，要改成同一個 name。CSS 已經寫好，這題只改 HTML。

練習 2：幫表單加上原生驗證與錯誤提示：三個欄位都必填；手機號碼必須是 09 開頭、共 10 個數字（不接受「-」）。每個欄位下方已經有提示文字（.hint），用 aria-describedby 連到欄位。錯誤樣式改成使用者操作過之後才出現，而且不能只靠顏色：至少再加一項看得出來的差別（例如加粗框線、顯示下方的 .error 文字）。

練習 3：整理表單底部的兩個動作。「送出預約」是表單裡唯一的 submit 按鈕，不要用 disabled 擋送出。「清除重填」常被誤觸，不能是 type="reset"，也不能是按鈕：改成連結 <a href="?reset">（伺服器看到 ?reset 就回傳空白表單），放在送出按鈕後面。

練習 4：為什麼 placeholder 不能取代 label？

✓ b：填到一半就看不到欄位在問什麼，淺灰字也不容易看清楚，有些輔助科技不把它當名稱。a、c、d 都不是事實：placeholder 支援任何文字，不會被當成值送出，也跟搜尋引擎無關。

練習 5：手機號碼欄位最適合哪個寫法？

✓ b：tel 叫出電話鍵盤，值是字串、保留開頭的 0；autocomplete="tel" 讓瀏覽器自動填入。a 把電話當數量：輸入 - 或 +886 時值變成空字串，當數字處理時開頭的 0 會消失，還有上下箭頭；c 鍵盤不對又關掉自動填入；d 沒有這個 type，瀏覽器會當成 text。

練習 6：前端已經用 pattern 檢查過電話格式，後端還需要驗證嗎？

✓ b：前端驗證只改善體驗，任何人都可以用 DevTools 拿掉屬性，或用 curl 送任意資料。跟有沒有登入（c）、用哪種 method（d）都無關，伺服器收到的資料一律要驗證。

常見錯誤

  • 只用 placeholder 當名稱：輸入後就消失、對比不足；每個欄位都要有看得到的 <label>，placeholder 只放範例。
  • for 打錯或 id 重複：不會報錯，只是關聯失效；在 DevTools 的 Accessibility 面板確認欄位的 Name，Vue 元件裡用 useId()。
  • 電話、卡號用 type="number"：開頭的 0 會不見，滾輪會改到值；用 type="tel" 或 inputmode="numeric"＋pattern。
  • autocomplete="off" 到處加：自動填入失效，使用者要手打每一格，欄位用途也沒辦法被程式判斷（WCAG 1.3.5）；拿掉 off，寫上對的 token。
  • radio 的 name 不同：變成好幾組，可以同時選；同一組用同一個 name，外面包 fieldset＋legend。
  • 錯誤樣式用 :invalid：頁面一打開必填欄位就是紅的；用 :user-invalid。
  • 只用顏色表示錯誤：色覺異常的使用者看不出來（WCAG 1.4.1）；加上錯誤文字、圖示或框線粗細。
  • 在 input::after 放圖示：input 是取代元素（replaced element），內容由瀏覽器畫，CSS 的 ::before、::after 在它身上不會顯示。錯誤圖示要放在旁邊的元素（例如 .error 文字前的 ⚠），或用 background-image。
  • 用 disabled 擋送出：使用者不知道哪裡錯；按鈕保持可按，讓驗證訊息說明。
  • 表單裡的其他按鈕沒寫 type="button"：一按就送出表單，按 Enter 也可能觸發到它。
  • 只做前端驗證：請求可以繞過表單；伺服器一定要再驗證一次。

小結

  • 表單送出時，瀏覽器把每個有 name 的欄位配成「名稱＝值」送到 action；name 是給伺服器的，id 只在頁面裡用。
  • 每個欄位都要有看得到的 <label>（for／id 或包住）；它就是欄位的可及名稱，點它會聚焦欄位。placeholder 和只寫 aria-label 都不能代替。
  • type 決定值與驗證，inputmode 只決定鍵盤，autocomplete 決定自動填入什麼。電話用 tel，會拿來計算的數量才用 number；autocomplete="off" 只用在真的不該自動填的那一格。
  • radio 同組同 name，用 fieldset＋legend 給整組一個標題。
  • required、pattern（自動比對整個值，空白不檢查）、min／max 是瀏覽器內建的驗證；錯誤樣式用 :user-invalid，不只靠顏色，提示文字用 aria-describedby 連到欄位。
  • 表單裡第一個 submit 按鈕是按 Enter 時的預設按鈕；其他按鈕寫 type="button"，不用 reset、不用 disabled 擋送出。
  • 前端驗證只改善體驗，伺服器一定要再驗證；有個人資料的表單用 POST。
