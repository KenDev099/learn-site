階段 4：除錯、瀏覽器與效能 · 第 21 課

效能改善與驗收：資源優先序、第三方腳本、效能預算與回歸監控（資深）

第 20 課結束時，咖啡店首頁有了數字：RUM 收到的手機 p75 LCP 是 3.4 秒，比「好」的門檻 2.5 秒慢了將近一秒；實驗室量到的 TBT 是 520 毫秒，代表載入期間主執行緒被卡住的時間加起來超過半秒。PM 看完報告，把這件事排成你下個迭代的任務：「把首頁手機版修到及格，要能證明修好了，之後也不能再慢回去。」

這張任務單其實是三件事：找出首屏到底在等什麼；把它改掉，其中有一部分根本不是你寫的程式（客服聊天、地圖、流量分析）；最後把「不能再慢回去」變成每個 PR 都會自動跑的檢查，並寫出 PM 能驗收的標準。這一課從頭到尾都在處理這一張任務單。重點不是記住更多屬性，而是學會排先後：哪些資源值得插隊、哪些程式不該在首屏載入、怎麼分辨一個 PR 是真的變慢還是量測在跳。

這課的路線：
  1. 首屏在等什麼：用瀑布圖找出拖慢主視覺的四個問題，先給出整體修法。
  2. 調整優先序：拿掉擋住解析與渲染的資源、提前建立連線，再處理太晚被發現的主視覺，以及 preload 為什麼只能給一兩個資源。
  3. 不是你寫的程式：第三方腳本怎麼盤點、延後，或改成點了才載入。
  4. 不再慢回去：把效能預算寫成會擋 PR 的 CI 檢查，分辨真的變慢和量測雜訊，上線後再用真實使用者資料補一道。
  5. 怎麼算修好：寫出可以驗收的標準，和一份 PM 看得懂、願意排進時程的提案。
這課會用到：
  • 第 20 課的指標與資料來源：LCP（主要內容多久出現）、INP（點了多久有反應）、CLS（畫面亂跳）、TBT（實驗室裡主執行緒被卡住的總時間），看 p75，分實驗室與真實使用者資料；RUM（真實使用者監測：從真實訪客的瀏覽器回報指標）就是後者。
  • 第 18 課的 Network 面板：每個請求的狀態、大小、時間與優先順序，可以限速、停用快取。
  • 第 14 課的首屏圖片與 fetchpriority：LCP 圖片不 lazy，用 fetchpriority="high" 讓它先下載。
  • 第 19 課的主執行緒與長任務：主執行緒一次只做一件事，長任務執行期間點擊只能等。

首屏到底在等什麼？

p75 LCP 3.4 秒告訴你「慢」，卻沒告訴你慢在哪裡。主視覺為什麼要 3 秒多才出現？要回答這個問題，得看到它前後每一個請求是什麼時候開始、什麼時候結束、彼此怎麼搶資源。DevTools Network 面板（第 18 課）畫的就是這件事。

打開 Network 面板，做兩個設定再重新整理咖啡店首頁。網路限速選 Slow 4G，因為 RUM 回報的問題出在手機，在辦公室的網路上量什麼都很快；勾選 Disable cache，因為第一次來的訪客沒有快取，要量的是他們看到的情況。重新整理後，每個請求畫成一條橫條，從左到右是時間，橫條從哪裡開始代表請求何時發出，長度代表花了多久。這張圖叫瀑布圖（waterfall），因為請求一個接一個往下、往右排，看起來像瀑布。簡化後長這樣：

圖上的 LCP 是 DevTools Slow 4G 單次量到的 2.9 秒，比 RUM 的 p75 3.4 秒快，因為 p75 包含比限速條件更慢的真實手機（第 20 課：實驗室不等於真實使用者）。實驗室數字用來找原因、比較改前改後，及格與否還是看 RUM。

讀瀑布圖有固定的順序：先找到 LCP 元素那一條（這裡是 hero-1600.avif），往左看它在等誰才開始，再往上下看它跟誰同時在下載。照這個順序讀，四個問題就浮出來了：

  1. LCP 圖片被發現得太晚：瀏覽器有一個預先載入掃描器（preload scanner），在主要的解析器一邊建 DOM 的同時，先快速掃過原始 HTML，看到 <img>、<link>、<script> 的網址就先發出請求（第 14 課）。它只看 HTML，看不到 CSS 裡的東西。咖啡店的主視覺寫在 site.css 的 background-image，瀏覽器要等 site.css 下載完、解析完、算出哪些元素用到這張圖，才開始下載。圖上那條箭頭就是這段等待。
  2. 頻寬被不急的東西佔走：主視覺終於開始下載時，5 個字型、聊天、地圖也正在下載。手機網路的頻寬是固定的一條水管，同時下載的東西越多，每個分到的越少，主視覺就下載得越久。
  3. 有東西擋住解析與渲染：沒加任何屬性的 tag.js 會讓 HTML 解析停下來，等它下載、執行完才繼續往下讀；沒寫 media 的 print.css 會讓螢幕的第一次渲染，等一份只有列印才用到的樣式。這兩種「擋住」的原理下一節會講。
  4. 跨 origin 的連線要另外花時間：圖片在 img.brew.example.tw、字型在 fonts.brew.example.tw，都跟首頁不同網域。origin 是協定、主機名稱、port 三者合起來，三者有任何一個不同就算不同的 origin。瀏覽器每遇到一個新的 origin，都要先建立連線才能開始下載，手機上可能要好幾百毫秒。

這四個問題有一個共同點：真正畫出首屏需要的東西，被排到了不需要的東西後面。畫出首屏最少需要的資源與步驟，叫關鍵渲染路徑（critical rendering path）：HTML、阻擋渲染的 CSS、首屏用到的字型、LCP 圖片。咖啡店首頁的問題，就是這條路徑上的東西沒有先到。

所以整張任務單的修法，可以先用一句話講完：讓關鍵渲染路徑上的東西先到，其他的全部往後排；改完之後寫成自動檢查守住。接下來各節依序把這句話做出來：下一節處理問題 3 和 4，再下一節處理問題 1，問題 2 裡那些不是你寫的腳本另外一節處理，最後是自動檢查與驗收。

要讓某些東西「先到」，得先知道瀏覽器本來是怎麼決定誰先誰後的，以及我們能從哪裡插手。

瀏覽器本來怎麼排隊？先拿掉擋路的，再提前連線

瀏覽器不是照 HTML 的順序一個一個下載，它會替每個請求排一個優先順序。Network 面板可以打開 Priority 欄位看到這個值。大致的規則是：head 裡的 CSS 最高，head 裡的同步 script 高，圖片一般是低（排版後發現在首屏內的會被調高），async／defer 的 script 偏低。先記住這個欄位：本節後半的 preconnect、下一節的 preload 與 fetchpriority，改的都是這個排隊順序，改完要回到這一欄確認有沒有變。

這套規則多數時候猜得對，因為它是照「這種資源通常多重要」來排的。但它不知道你的設計：它不知道 site.css 裡那張背景圖就是 LCP，也不知道 tag.js 其實晚一點跑也沒關係。我們能插手的寫法分成兩類，要分開看。第一類是 defer 和 media：它們處理的是兩個會擋住解析與渲染的資源，這跟優先序無關，屬性寫上就直接改變瀏覽器的行為，一定生效。第二類是後面的 preconnect、preload、fetchpriority：它們是提示，請瀏覽器修正它猜錯的排隊順序。提示不是命令，瀏覽器可以不採用，所以每改一處都要回到瀑布圖和 Priority 欄位確認有沒有效。先從第一類開始：拿掉擋住解析與渲染的兩個資源。

擋住解析的 tag.js：改成 defer

瀏覽器讀 HTML 時，遇到沒有屬性的 <script src> 會停下來：先下載它、執行它，才繼續往下讀。這樣設計是因為 script 執行時可能會改動還沒讀到的 DOM，瀏覽器只好等它。tag.js 是流量分析程式，跟畫出首屏毫無關係，卻讓整份 HTML 的解析停下來等一個別人網域的檔案。

第 1 課教過兩個屬性可以改掉這件事。defer 讓 script 在背景下載、不擋解析，等 HTML 解析完再依出現的順序執行；async 也在背景下載，但一下載完就立刻執行、不保證順序，執行的那一刻還是會打斷解析。需要依順序執行、會用到 DOM 的用 defer，幾乎所有外部 script 都適用。tag.js 改成 defer。

要注意的是，不擋解析不代表沒有成本：下載一樣佔頻寬，執行一樣佔主執行緒。defer 解決的是「HTML 停下來等」，不是「這個程式很重」。重的第三方程式要怎麼辦，留到第三方腳本那一節。

擋住渲染的 print.css：加上 media="print"

head 裡的樣式表會阻擋渲染：所有樣式表下載、解析完之前，瀏覽器不畫第一個畫面。這是刻意的，否則使用者會先看到沒有樣式的內容，再看到它突然跳成有樣式的樣子。問題是瀏覽器不知道 print.css 只在列印時才用到，沒寫 media 的樣式表，就當成螢幕現在需要的。

在 <link rel="stylesheet"> 加上 media="print"，瀏覽器就知道這份樣式現在用不到：它照樣下載，但不阻擋渲染。螢幕用的主樣式 site.css 不能這樣做，它正是畫出首屏需要的東西，延後它就會出現上面說的「先無樣式再跳一下」。

跨 origin 的連線：preconnect，以及什麼時候要加 crossorigin

開頭第 4 個問題說過，origin 是協定、主機名稱、port 三者合起來，所以 https://img.brew.example.tw 和 https://brew.example.tw 是兩個不同的 origin。瀏覽器每次要跟一個新的 origin 拿東西，都要先建立連線，分三步：查 DNS 把網域換成 IP 位址、建立 TCP 連線、做 TLS 握手協商加密。每一步都要跟對方伺服器來回傳訊息，網路延遲越高越久，手機上加起來可能好幾百毫秒，這段時間一個位元組的圖片都還沒開始下載。

瀑布圖上，主視覺的請求要等 site.css 解析完才發出，到那時才開始建立到 img.brew.example.tw 的連線。<link rel="preconnect" href="https://img.brew.example.tw"> 讓瀏覽器在讀到 head 時就先把連線建好，等真正的請求發出，可以直接開始下載。

preconnect 有成本：每條連線都要花 CPU 和網路去建立，建了卻沒用到的連線大約 10 秒後就被關掉，等於白做。所以它只留給首屏一定會用到、但第一個請求比較晚才發出的跨 origin 資源，通常 2–3 個。咖啡店原本的 head 對 6 個 origin 都 preconnect，包括 API、分析、聊天、地圖，真正符合條件的只有圖片和字型這兩個。會用到但不急的 origin，可以改用只先查 DNS、成本很低的 dns-prefetch，或什麼都不做。

字型的 preconnect 還要多一個屬性。瀏覽器對同一個 origin，會依請求模式分開使用連線：字型一律用不帶憑證（cookie）的 CORS 請求下載。CORS 是瀏覽器跨 origin 拿資源時的一套規則：請求會帶上 Origin 標頭，對方伺服器要在回應裡明確允許，瀏覽器才把內容交給頁面（認證課第 5 課）。圖片、CSS、一般 script 則是一般模式，兩種請求不共用同一條連線。preconnect 預設建的是一般模式的連線，加了 crossorigin 才是字型用得到的那種：

<link rel="preconnect" href="https://img.brew.example.tw">               <!-- 圖片：不加 -->
<link rel="preconnect" href="https://fonts.brew.example.tw" crossorigin> <!-- 字型：要加 -->

寫反了，提前建好的連線用不到，等於沒做。同一個 origin 同時放 CSS 和字型（例如字型服務先給 CSS、CSS 再指向字型檔），就需要兩條連線，兩種寫法都要有。

到這裡，HTML 解析不再停下來等 tag.js，首次渲染不再等列印樣式，兩個關鍵 origin 的連線也提早就緒。但瀑布圖上影響最大的問題還在：主視覺仍然要等 site.css 下載、解析完才發出請求。連線再快，請求發得晚，圖還是晚到。

主視覺太晚被發現：preload 該給誰？

主視覺晚到，根本原因是瀏覽器太晚知道它存在。最好的修法是讓它被早點看到：把主視覺改成寫在 HTML 裡的 <img>，預先載入掃描器一讀到就會發出請求（第 14 課的寫法）。但咖啡店的主視覺是舊元件用 CSS 背景圖做的，這個迭代改不動，只能從另一頭下手：直接告訴瀏覽器「這個檔案一定會用到，現在就去下載」。

這就是 <link rel="preload"> 做的事：不用等它在 CSS 或 JS 裡被發現，現在就開始下載。as 屬性必填，它告訴瀏覽器這是哪一種資源（image、font、style、script…），瀏覽器才能決定優先序與請求方式。下載的優先序依 as 而定，不是一律最高：圖片的 preload 預設仍是低優先序，所以 LCP 圖片的 preload 要再加 fetchpriority="high"（下面逐個屬性會講）；之後頁面真正用到這個檔案時，直接拿已經下載好的那份。如果載入後幾秒內都沒被用到，Console 會出現警告。

看起來 preload 是個好東西，那為什麼不把首頁的 CSS、5 個字型、所有圖片都 preload？因為 preload 不會讓網路變快，它只是讓某個請求更早開始、排更前面。頻寬是固定的，有東西排前面，就有東西排後面。全部都 preload，等於大家都說自己是急件，主視覺照樣要跟字型搶頻寬，優先序就失去意義，LCP 甚至可能更慢。

所以判斷要不要 preload，問兩個問題：

  1. 首屏一定用得到嗎？用不到的 preload 是純浪費，Console 會警告。
  2. 瀏覽器自己會不會很早發現？寫在 HTML 裡的 <img>、<link rel="stylesheet">、<script> 在預先載入掃描器階段就被看到了，加 preload 沒有好處。要 preload 的是藏在 CSS、JS 裡的資源：CSS 背景圖、CSS 裡的字型、JS 才插入的圖片。

兩個問題都回答「是」的，才值得 preload，通常一頁只有一兩個。咖啡店的主視覺兩題都符合。它有兩個尺寸，preload 要寫成響應式的，手機才不會下載桌機的大圖：

<link rel="preload" as="image"
  href="https://img.brew.example.tw/hero-1600.avif"
  imagesrcset="https://img.brew.example.tw/hero-800.avif 800w,
               https://img.brew.example.tw/hero-1600.avif 1600w"
  imagesizes="100vw" type="image/avif" fetchpriority="high">

逐個屬性看：

  • imagesrcset、imagesizes 和 <img> 的 srcset、sizes 意思一樣（第 14 課）：列出候選檔案和寬度，瀏覽器依螢幕寬度挑一個下載。
  • type="image/avif" 讓不支援 AVIF 的瀏覽器跳過這個 preload，不會白下載一個用不了的檔案。
  • fetchpriority="high" 在同類資源裡再調高優先序，補上前面說的那一點：as="image" 的 preload 預設是低優先序，不加的話，請求雖然提早發出，還是排在其他高優先序資源後面。preload 讓請求提早發出，fetchpriority 讓它在一群圖片裡排最前面。它也可以直接寫在 <img> 上：LCP 是 HTML 裡的 <img> 時，加 fetchpriority="high" 就夠，不需要 preload；輪播後面幾張看不到的圖則可以用 "low" 讓路。它只是提示，不支援的瀏覽器會忽略。

同樣的兩個問題套到字型上：5 個字型裡只有 h1 用的那一個在首屏一定會出現、又藏在 CSS 的 @font-face 裡，所以只 preload 它（第 15 課）。字型的 preload 和上一節的 preconnect 一樣要加 crossorigin，原因相同：字型一律用 CORS 模式下載，沒加的話 preload 下來的那份對不上，瀏覽器會再下載一次。

preload 寫在 head 裡，會被每一頁的 HTML 帶著。改版換了主視覺的檔名，preload 沒跟著改，就會變成「每頁都下載一張沒人用的大圖」。用打包工具或伺服器範本從同一個來源產生 preload 與 CSS 裡的網址，不要手寫兩份。

這兩節用到的寫法，連同 dns-prefetch、modulepreload 等相關的寫法，整理成一張表放在課末「補充與查表」，查表用，不用背。

💡 實務上：先確認 LCP 元素是誰，再決定要不要動優先序
接手一個慢的頁面，先用 Performance 面板或 Lighthouse 找出手機版的 LCP 元素，它常常和桌機不同（手機可能是標題文字，桌機才是主視覺）。很多框架與 CMS 的圖片元件已經有 preload、fetchpriority 之類的選項，先用框架的寫法，不要在範本裡再手寫一份。每加一個 preload 或 preconnect，都在 Network 面板的 Priority 欄位和瀑布圖比對前後，確認 LCP 圖片真的提早開始、沒有擠掉 CSS。Code review 看到新的 preload，資深會問：「這是哪一頁的 LCP？拿掉會慢多少？」答不出來就先不要加。

自己的 head 整理好了，主視覺也提早開始下載。但瀑布圖上還有兩條大的在跟它搶頻寬：聊天的 loader.js 和地圖的 sdk.js；tag.js 雖然不再擋解析，執行時一樣佔主執行緒。下一節的盤點會看到，首頁的主執行緒時間大多花在它們身上。它們不是你寫的程式，不能打開來改，要換一種處理方式。

聊天和地圖不是你寫的：第三方腳本怎麼處理？

第三方腳本（third-party script）是從別的服務載入、程式碼不歸你管的 JavaScript：流量分析（Google Analytics 這類）、客服聊天、廣告、地圖、A/B 測試、社群按鈕。網站只放一行 <script src>，真正的內容由廠商決定。這帶來三個問題：

  • 大小與主執行緒時間不受你控制：廠商更新版本，你的 TBT 跟著變，你的 PR 一行都沒改。
  • 會再載入更多東西：一個 loader.js 之後又去載 CSS、字型、iframe、追蹤像素，瀑布圖上看到的那一條只是開頭。
  • 安全與隱私：它們在你的頁面上用你的權限執行，能讀 DOM、cookie（沒有 HttpOnly 的）。

但你也不能看到慢就刪。聊天是客服部門要的，地圖是門市營運要的，分析是行銷要的，每一個背後都有人在用它做事。所以處理的第一步不是改程式，而是盤點：搞清楚每個腳本花了多少、換來什麼、誰在負責。用 DevTools Performance 面板錄一次載入，Insights 裡的第三方項目會列出每個第三方的傳輸大小與主執行緒時間；再去問各部門，補上業務資訊，做成一張表：

腳本用途傳輸大小主執行緒時間首屏需要嗎負責人處理
分析 tag.js流量與轉換分析45 KB60 ms不需要，但要算到每次造訪行銷defer
聊天 loader.js線上客服210 KB（含後續載入）400 ms不需要，不到 2% 訪客會開客服facade
地圖 sdk.js顯示門市位置180 KB＋圖磚250 ms不需要，在頁面下方門市營運改成連結（或靜態地圖圖片）
舊的再行銷像素去年的廣告活動12 KB20 ms活動已結束（沒人知道）移除

讀這張表時，「首屏需要嗎」決定處理方式，「負責人」決定你要找誰談。沒有負責人的腳本，沒有人敢刪，就會一直留著，像那個去年的再行銷像素。四個腳本剛好對應四種處理：

  • 已經沒人需要的（再行銷像素）：移除。
  • 每次造訪都要跑、但不急的（分析）：前面「擋住解析的 tag.js」那一小節已經改成 defer，不擋解析，在 HTML 解析完才執行。
  • 只有少數人會用的互動元件（聊天）：改成 facade，下一小節講。
  • 可以用更輕的東西取代的（地圖）：大多數人只想知道門市在哪裡，一個連到地圖服務的連結或一張靜態地圖圖片就夠了，不需要在首頁載入整套互動地圖。

facade：先放一個假的，點了才載入真的

聊天是最難處理的一個：它佔了 400 ms 主執行緒時間，但客服部門真的需要它。可是盤點表也告訴我們，不到 2% 的訪客會打開它。也就是說，現在每一位訪客都在替 2% 的人付這 400 ms。

facade（假介面）就是針對這種情況的做法：先放一個輕量、看起來像真元件的替身，使用者真的要用時才載入真的。聊天 widget 先顯示一顆「線上客服」按鈕，使用者點了才去下載真正的 loader.js。98% 不會點的訪客完全不用付出那 400 ms，要用客服的人也還找得到它。按鈕要用真正的 <button>（第 2 課），鍵盤使用者才按得到。網站自己的 app.js 裡寫：

const button = document.querySelector('.chat-facade')
button?.addEventListener('click', () => {
  button.disabled = true
  button.textContent = '客服載入中…'
  const script = document.createElement('script')
  script.src = 'https://widget.example-chat.com/loader.js'
  script.onload = () => { window.ExampleChat.open(); button.remove() }   // ExampleChat 是假想的廠商 API
  script.onerror = () => { button.disabled = false; button.textContent = '線上客服（載入失敗，再試一次）' }
  document.head.append(script)
}, { once: true })

這段程式做的事依序是：點擊時先把按鈕停用並顯示「載入中」，避免使用者以為沒反應而連點；動態建立一個 script 載入真正的 widget；載入成功就打開聊天視窗、拿掉替身按鈕，失敗就恢復按鈕讓使用者再試。

代價是第一次點擊要等下載，所以「載入中」狀態和失敗處理都不能省；這個等待也要先讓客服主管知道並同意，因為受影響的是他們的使用者。同樣的做法也常用在 YouTube 影片和互動地圖：先放縮圖或靜態地圖，點了才換成 iframe。

其他做法與取捨

咖啡店的四個腳本用上面的方式就處理完了，但遇到別的網站、別的腳本，還有幾種常見做法，各有代價：

  • 延後到首屏之後：分析程式用 defer；更不急的可以等 load 事件之後再插入。代價是頁面很快被關掉時，那次造訪可能沒被記到。
  • 自行託管（self-host）：把第三方檔案放到自己的網域，少一個 origin 的連線，快取也由自己控制（Node 課第 15 課）。代價是要自己追版本更新；有些服務的條款不允許，或腳本本身會再去廠商網域載東西，效果有限。
  • 標籤管理工具（tag manager）的治理：行銷人員可以不經部署就加新腳本，這也是第三方越積越多的主因。規則要寫清楚：新增腳本要誰核准、要填盤點表、每季檢查一次。
  • CSP 一起改（認證課第 7 課）：CSP 的 script-src 是允許清單。移除地圖 SDK 就把它的網域拿掉；聊天改成點擊才載入，網域還是要留在 script-src，否則點了也載不進來。CSP 也是盤點表的另一種實作：沒列在清單上的腳本，載不進來。
💡 實務上：行銷說「幫我加一段追蹤碼」時要先問的事
這是前端最常接到的需求之一，通常來自行銷或廣告投放。資深不會直接貼進 head，而是先問：要放在哪些頁面（只有結帳完成頁需要轉換追蹤，就不要全站載入）、能不能 defer，或等使用者在 cookie 同意視窗按下同意之後才載入（很多地區的隱私法規要求追蹤碼先取得同意）、負責人是誰、活動哪天結束可以拿掉。加之前在盤點表多一列、CSP 補上網域，量一次 TBT 前後差多少，把數字附在 PR 上。半年後有人問「這個腳本還要嗎」，答案才查得到。

到這裡，任務單的第一半做完了：關鍵渲染路徑上的東西先到，首屏用不到的往後排或拿掉。練習 1 就是把到這裡為止對首頁的所有改動（head 的優先序、聊天 facade、地圖連結）實際寫一次。但首頁現在快，不代表下個月還快：行銷再加一段追蹤碼、同事加一個 20 KB 的套件，每個 PR 都只慢一點點，沒有人會覺得是自己的問題。PM 要的「之後不能再慢回去」，要靠什麼守住？

怎麼讓它不再慢回去？把效能預算寫成數字

慢慢變慢最難防，因為沒有一個時間點會讓人警覺：多一個套件 20 KB、多一個追蹤碼 50 ms，每次看都可以接受，半年後首頁就慢了一倍。要防這種事，得先講好一條線，超過就算不行。這條團隊同意不能超過的上限，叫效能預算（performance budget）。

預算可以訂在不同的東西上，常見的有三種，各有適合的用途：

類型例子（咖啡店首頁，手機）優點缺點
數量型：大小、請求數JS 合計 ≤ 300 KB（傳輸大小）；圖片 ≤ 300 KB；字型 ≤ 100 KB；第三方請求 ≤ 3 個穩定，不受量測雜訊影響；開發者知道要刪什麼只是間接指標：大小沒變，執行時間可能變了
時間型：指標實驗室 LCP ≤ 2.5 秒、TBT ≤ 200 ms、CLS ≤ 0.1直接對應使用者體驗有雜訊，要多次量測；實驗室數字不等於真實使用者
規則型：audit 分數Lighthouse 效能分數 ≥ 0.9；某些 audit 必須通過設定容易分數混合了多個指標，退步時不知道是哪裡

實務上常把數量型和時間型一起用：數量型穩定，適合擋 PR，也直接告訴開發者該刪什麼；時間型才真正對應使用者感受，但會跳動，需要下一節的處理。規則型最容易設定，卻最難看出退步在哪，通常只當參考。

數字要怎麼訂？有三個出發點：

  • 從現況出發：先把預算訂在目前的數值，至少不再變差，之後每次改善就往下調。
  • 從目標反推：Lighthouse 預設的手機條件是 150 ms 延遲、1.6 Mbps 下載（約 200 KB／秒）。LCP 要在 2.5 秒內，扣掉連線與 HTML 約 1 秒，剩 1.5 秒，關鍵路徑上的資源大約只能有 300 KB。這種估算不精確，但能說明為什麼「再加一個 200 KB 的套件」不行。
  • 參考競品：用 PageSpeed Insights 看幾個同業首頁的 CrUX 資料，訂一個「至少不輸」的目標。

寫成自動檢查

預算只寫在文件裡，沒有人會在每個 PR 前去翻文件，很快就被忽略。要讓它有效，得放進 CI（DevOps 課第 15 課）：每次開 PR，CI 自動建置網站、量一次，超過預算就讓 PR 的檢查變紅，沒處理就不能合併。

現在常用的工具是 Lighthouse CI（套件名稱 @lhci/cli）。它是一個命令列工具，在 CI 裡啟動網站、對指定網址跑幾次 Lighthouse，再拿結果跟你寫的規則比。這些規則叫 assertions（斷言），每一條的意思是「某個 audit 的數值不能超過多少」；任何一條沒過，指令就以失敗結束，PR 的檢查跟著變紅。設定檔 lighthouserc.json 長這樣：

{
  "ci": {
    "collect": {
      "startServerCommand": "npm run preview",
      "url": ["http://localhost:4173/"],
      "numberOfRuns": 5
    },
    "assert": {
      "assertions": {
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500, "aggregationMethod": "median" }],
        "total-blocking-time": ["error", { "maxNumericValue": 200, "aggregationMethod": "median" }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1, "aggregationMethod": "median" }],
        "resource-summary:script:size": ["error", { "maxNumericValue": 307200 }],
        "resource-summary:third-party:count": ["warn", { "maxNumericValue": 3 }]
      }
    }
  }
}

collect 負責量，assert 負責比。assertions 裡每一行的左邊是 audit 的 id，右邊第一個值是沒過時的處理（error 讓檢查失敗，warn 只印警告），第二個值是上限。上面五行就是把數量型和時間型預算各寫進去。幾個要注意的地方：

  • startServerCommand 先啟動建置好的網站（Vite 的 preview 預設在 4173 port），url 是要量的頁面。
  • numberOfRuns 預設是 3；跑 5 次比較穩，代價是 CI 久一點。
  • 沒寫 aggregationMethod 時預設是 optimistic（取最可能通過的那次），對抓回歸太寬鬆；時間指標建議用 median。
  • resource-summary:<類型>:size 的單位在 Lighthouse CI 裡是 bytes（307200 = 300 × 1024）。單位寫錯，預算就差了 1000 倍或 2.4%。

打包大小也要另外檢查：Vite 建置後比較 dist 裡 JS 的大小（Vue 課第 23 課），在 PR 上就能看到「這次多了 40 KB，是因為新加的日期套件」，比等 Lighthouse 跑完更早發現。練習 2 會把預算檢查自己寫一次，弄清楚每個數字從報告的哪裡來。工具的版本與 Lighthouse 舊功能的變動，見課末「補充與查表」。

💡 實務上：預算檢查先從「警告」開始導入
在既有專案導入時，先把規則都設成 warn，觀察幾個 PR 的數字跳動多大，再把穩定的（打包大小、第三方數量）改成 error；時間型指標雜訊大，太早擋 PR，團隊很快就會把檢查關掉。也要先講好超標時怎麼辦：誰能核准暫時調高預算、要不要開 issue 追蹤降回來。不是每個頁面都需要 Lighthouse CI：給店員用的咖啡店後台要登入、不用 SEO，通常做打包大小檢查就夠，Lighthouse 留給首頁、商品頁這類公開、影響轉換的頁面。

上面的燈泡區塊提到「時間型指標雜訊大」，這是預算檢查最麻煩的地方：同一個版本量兩次，數字就不一樣。CI 回報 LCP 比 main 慢了 8%，是這個 PR 真的變慢，還是量測剛好在跳？

數字會跳：怎麼判斷 PR 真的變慢了？

改版後效能變差，叫效能回歸（performance regression）。抓回歸的難處在於，實驗室量測本身就會跳動：CI 機器同時在跑別的工作、網路有起伏，同一個版本連跑 5 次，LCP 差個 10% 很常見。只跑一次就拿來比，會犯兩種錯：沒變慢卻被擋下來（誤報），或真的變慢卻剛好量到快的一次而放行（漏報）。誤報的傷害比看起來大：擋錯幾次之後，團隊就不再相信這個檢查，開始直接重跑或把它關掉，等到真的回歸時也沒人理。

所以判斷回歸要做四件事：

  1. 多跑幾次取中位數：3–5 次。中位數不受一次極端值影響；平均會被一次特別慢的拉高；最小值（最佳值）看起來穩定，但它代表的是運氣最好的一次。
  2. 同一台機器、同一個條件，比較基準分支：在同一個 CI 工作裡，main 和 PR 各跑 5 次，比的是差異，不是絕對值。機器整體變慢時兩邊一起慢，不會誤報。
  3. 設定容忍值：例如 LCP 中位數增加超過 10%、或 TBT 增加超過 50 ms 才算回歸。容忍值太小會一直誤報，太大會漏掉慢慢累積的退步，所以還要搭配上一節絕對的預算上限。
  4. 次數不夠就不下結論：有一邊量測失敗、只剩 1–2 次，回報「無法判斷」並重跑，不要假裝有結果。

上線後：RUM 警報

CI 這道防線再嚴，也只量得到你設定的那幾個頁面、那一種裝置和網路。真實使用者的裝置更慢、會登入、會捲動、會點擊（INP 只有真實互動才有）。行銷在標籤管理工具裡加的腳本，也根本不會經過 PR。所以上線後要靠第 20 課的 RUM 資料再守一道：

  • 每天計算手機與桌機分開的 p75 LCP、INP、CLS，畫成趨勢圖。
  • 設警報（DevOps 課第 22 課的指標、第 25 課的告警）：例如「手機 p75 LCP 連續 3 天超過 2.5 秒」才通知。看連續幾天而不是單日，是為了避開流量很小的日子（週日半夜）造成的跳動，跟 CI 取中位數是同一個道理。
  • 部署時在 RUM 資料上標記版本號，數字變差時才知道是哪一次部署。
  • CrUX（Search Console、PageSpeed Insights 用的資料）是過去 28 天的滾動資料，改善上線後要等好幾週才會完全反映，不能拿它當部署後的即時回饋。

CI 擋合併前的退步，RUM 抓 CI 看不到的退步，「不能再慢回去」這一項就有了兩道防線。任務單還剩最後一句：「要能證明修好了」。什麼叫修好，得在動工前就講清楚。

怎麼算修好？驗收標準與效能提案

「把首頁變快」沒辦法驗收：快多少算快？用誰的手機量？量一次還是量一個月？每個人心裡的答案不同，做完才發現 PM 要的不是你做的。可以驗收的目標要寫出五件事：哪個指標、哪種裝置、哪個百分位、用哪個資料來源、維持多久。照這個格式，咖啡店首頁的驗收標準是：

驗收標準
- 首頁（/）手機 p75 LCP ≤ 2.5 秒，RUM 資料，上線後連續 28 天
- 首頁手機 p75 INP ≤ 200 ms、p75 CLS ≤ 0.1，同上
- CI：Lighthouse 手機設定 5 次中位數 LCP ≤ 2.5 秒、TBT ≤ 200 ms；JS ≤ 300 KB
- 線上客服的使用量不低於改版前（facade 不能讓人找不到客服）

前兩條用真實使用者的資料，因為任務的起點就是 RUM 的 3.4 秒；第三條把上一節的 CI 預算寫進來，保證之後不退步。最後一條很重要：效能改善常常動到別人的功能。這次把聊天改成 facade、地圖改成連結，動的是客服、門市營運與行銷的東西（分析延後可能少記到一些造訪）。先跟他們說好要守住的業務指標，上線後一起看。

驗收標準說明什麼叫做完；但要排進開發排程，還得先讓 PM 看懂為什麼值得做。PM 要在很多需求之間排優先順序，他需要知道問題多嚴重、要花多少、有什麼風險。一份效能提案寫這幾件事：

這張表每一欄都對應本課的一節：原因來自瀑布圖與第三方盤點表，做法是調整優先序與 facade，驗收方式是預算檢查和驗收標準。「預期改善」要寫你實際量到的數字，不是網路文章的平均值，所以先在分支上照上一節的方法量過多次再寫；不確定的地方就寫範圍，並說明上線後怎麼確認。

回到開場的任務單：首屏在等什麼，瀑布圖回答了；怎麼改，靠調整優先序和處理第三方腳本；怎麼證明修好、不再慢回去，靠驗收標準、CI 預算與 RUM 警報。下面的練習依同樣的順序，把 head 的改動、預算檢查、回歸判斷各寫一次。

練習

練習 1：咖啡店首頁的 <head> 把每樣東西都當成急件。照這一課的做法調整（只改資源載入，不刪內容）：
① 只對兩個關鍵 origin preconnect：主視覺所在的 https://img.brew.example.tw，與字型所在的 https://fonts.brew.example.tw（字型的要加 crossorigin）。
② 主視覺是 site.css 裡的背景圖（舊元件暫時改不動），窄螢幕用 hero-800.avif、寬螢幕用 hero-1600.avif，都在 img 那個 origin：用一個 preload 提早下載，寫 imagesrcset（800w、1600w）、imagesizes="100vw"、fetchpriority="high"。
③ 字型只 preload h1 用的 brewserif-bold.woff2。
④ 分析程式 tag.js 改成 defer。
⑤ 聊天 widget 改成 facade：拿掉 loader.js，把 <div id="chat"> 換成「線上客服」按鈕（app.js 會在點擊時才載入真正的 widget）。
⑥ 地圖 SDK 拿掉，把 <div id="map"> 換成連到 https://maps.example-maps.com/?q=豆留咖啡大安門市 的連結。
⑦ 列印樣式 print.css 不要阻擋螢幕的渲染。
預覽看不到圖片與字型（練習環境擋下所有外部資源），這題檢查的是 head 寫得對不對。

練習 2：把效能預算寫成自動檢查。checkBudget(report, budget) 讀 Lighthouse 13 報告 JSON 的一部分：三個時間指標的 audits[id].numericValue，與 audits['network-requests'].details.items（每個請求的 url、resourceType、transferSize，單位 bytes）。預算有三類，只檢查預算裡有寫的項目：
• timings：LCP、TBT（毫秒）、CLS，實際值大於上限就記 { kind: 'timing', key: 'LCP', actual, limit }。
• resourceSizes：script／image／font 加總對應 resourceType（Script、Image、Font）的 transferSize，total 加總全部；換成 KB（1 KB = 1024 bytes，actual 不四捨五入）後大於上限記 kind: 'size'。
• resourceCounts.thirdParty：siteOf(url) 跟 siteOf(report.finalDisplayedUrl) 不同的請求數，大於上限記 kind: 'count'。site 是網域的「註冊單位」（認證課第 5 課）：img.brew.example.tw、fonts.brew.example.tw 跟 brew.example.tw 是同一個 site，都是自家的；所以第三方要比 site，不能比 hostname。題目已經寫好簡化版的 siteOf，直接用。
報告裡缺少需要的 audit（或沒有 numericValue）時，記 { kind: 'missing', key, actual: null, limit }，不能當成通過。等於上限算通過。failures 先依 kind、再依 key 排序（字串的 < 比較）；ok 是「沒有任何 failure」。不要修改傳進來的物件（測試會凍結它們）。

練習 3：CI 對基準分支（main）與 PR 分支各跑幾次 Lighthouse。寫 regression(base, pr, options)：任一邊的 lcp 或 tbt 少於 3 筆就回傳 { verdict: 'inconclusive' }；否則兩邊各算中位數（偶數筆取中間兩個的平均），diff.lcp = (pr.lcp - base.lcp) / base.lcp、diff.tbt = pr.tbt - base.tbt，LCP 增加的比例超過 lcpTolerance、或 TBT 增加超過 tbtTolerance 毫秒就是 'regression'，否則 'ok'（剛好等於不算）。回傳兩邊的中位數與 diff。輸入是唯讀陣列，不要就地排序。

練習 4：同事把首頁所有的 CSS、5 個字型、8 張圖片都加上 <link rel="preload">，說「這樣全部都會比較快」。實際上會怎樣？

✓ b：頻寬固定，preload 只是讓請求提早、排前面。所有東西都排前面，關鍵的主視覺反而要跟字型與不在首屏的圖片分頻寬。a 錯：提早開始不等於更快完成。c 錯：瀏覽器會照做，用不到的還會在 Console 警告。d 錯：影響的是載入速度，也就是使用者體驗。

練習 5：PR 的 CI 跑了一次 Lighthouse，LCP 比 main 慢 8%。應該怎麼判斷？

✓ b：同一個版本連跑幾次就可能差 10%，一次的差異說明不了什麼。a 會造成大量誤報，團隊很快就不信這個檢查。c 錯：實驗室檢查有雜訊但能在合併前抓到明顯的退步，是 RUM 之外的第一道防線。d 錯：總分混合多個指標，而且一樣有雜訊。

練習 6：客服聊天 widget 讓首頁 TBT 增加 400 ms，但客服部門需要它。比較好的做法是？

✓ c：大部分訪客不會開客服，延到點擊時才載入，功能保留、首屏不用付成本；代價是第一次開啟要等一下，要有載入中狀態。a 忽略了業務需求。b 讓它更早搶頻寬，執行時間一樣。d 只是不擋解析，下載與 400 ms 的執行還是發生在首屏期間。

常見錯誤

  • preload 濫用：全部 preload 等於沒有優先序，還搶走 LCP 資源的頻寬。只 preload 首屏一定用到、而且瀏覽器很晚才發現的一兩個資源。
  • preconnect 給每個看得到的網域：每條連線都有成本，沒用到的約 10 秒後就被關掉。只留 2–3 個關鍵 origin，其他用 dns-prefetch 或什麼都不做；字型的 origin 記得加 crossorigin。
  • 以為 async 就沒成本：async 只是不擋解析，下載和執行仍然在首屏期間搶頻寬、佔主執行緒。首屏不需要的第三方要延後到互動時或改成 facade。
  • 第三方腳本沒人負責：越積越多、沒人敢刪。建立盤點表（用途、大小、主執行緒時間、負責人），標籤管理工具的新增要經過核准，CSP 跟著同步。
  • 只看單次量測：雜訊造成誤報或漏報。多次取中位數，跟基準分支在同一個環境比較，設容忍值。
  • 預算只寫在文件：沒有自動檢查就會被忽略。放進 CI，超過就讓檢查失敗；注意 Lighthouse CI 的大小單位是 bytes。
  • 只看實驗室數字就宣布完成：驗收要看真實使用者的 p75，並確認被改動的功能（客服使用量等）沒有受影響。

這一節收的是主線用不到、但寫程式或查資料時會遇到的細節，查表用，不用背。

調整優先序的寫法

本課第二、三節用到的寫法，加上兩個相關的寫法，整理如下：

寫法做什麼什麼時候用注意
<link rel="preconnect" href="https://img…">提前建立到某個 origin 的連線（DNS、TCP、TLS）首屏一定會用到、但第一個請求比較晚才發出的跨 origin 資源只留 2–3 個關鍵 origin；建了沒用的連線約 10 秒後被關掉，白花成本。字型的 origin 要加 crossorigin
<link rel="dns-prefetch" href="https://…">只先查 DNS會用到但不急的 origin成本很低；跟 preconnect 分成兩個 link 寫，不要寫在同一個 rel 裡
<link rel="preload" as="…">不等它被發現，現在就開始下載這個檔案；優先序依 as 而定，as="image" 預設仍是低，LCP 圖片要再加 fetchpriority="high"這一頁一定會用到、但瀏覽器很晚才發現的資源：CSS 背景圖、CSS 裡的字型、JS 才插入的圖片as 必填；字型要 crossorigin（第 15 課）；載入後幾秒內沒被用到，Console 會警告
fetchpriority="high"／"low"在同類資源裡調高或調低優先序LCP 的 <img> 或它的 preload 用 high；輪播後面的圖用 lowBaseline newly available（2024-10）；只是提示，不支援的瀏覽器會忽略
<script defer>／async不擋 HTML 解析幾乎所有外部 script；需要依順序、要用到 DOM 的用 defer第 1 課；不擋解析不代表免費，下載與執行一樣要時間
<link rel="stylesheet" media="print">條件不符的樣式表照樣下載，但不阻擋渲染列印樣式、只在特定條件用的樣式螢幕用的主樣式不能這樣做，否則畫面會先無樣式再跳一下
<link rel="modulepreload">提前下載並解析 ES module打包工具產生的關鍵 chunkVite 會自動產生；Baseline widely available（2026-03）

Lighthouse 與 Lighthouse CI 的版本

  • Lighthouse 自己的 budgets 功能在 12.0.0 已經移除，所以預算檢查改用 Lighthouse CI（@lhci/cli，目前 0.15.1）的 assertions。
  • Lighthouse 13.0.0（2025）移除了 third-party-facades、uses-rel-preload、preload-fonts 等舊 audit，改由 performance insights 呈現同樣的建議。舊文章或舊 CI 設定裡引用這些 audit id 的，升級後要改。

小結

  • 先從瀑布圖找出關鍵渲染路徑：LCP 資源是不是太晚被發現、頻寬被誰佔走、誰擋住解析與渲染、跨 origin 連線花了多少時間。修法是讓這條路徑上的東西先到，其他的往後排。
  • script 用 defer、列印樣式加 media="print"，直接拿掉擋路的；preconnect、preload、fetchpriority 是提示，越少越有效：preconnect 給 2–3 個關鍵 origin（字型的加 crossorigin），preload 只給首屏一定用到又晚被發現的一兩個資源，fetchpriority="high" 給 LCP。
  • 第三方腳本先盤點再處理：盤點表寫出大小、主執行緒時間與負責人；不需要的移除，不急的延後，少數人用的互動元件改 facade，並同步更新 CSP。
  • 效能預算分數量、時間、規則三型，從現況或目標反推，寫進 CI 才有效；導入時先用 warn。
  • 回歸判斷用多次量測的中位數、跟基準分支比較、設容忍值，次數不夠就不下結論；上線後用 RUM 的 p75 警報補上實驗室看不到的部分。
  • 驗收標準寫清楚指標、裝置、百分位、資料來源與期間，並守住被改動功能的業務指標；效能提案寫問題、原因、做法、預期改善、成本與驗收方式。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：店長說按了「送出訂單」沒反應。你重現後打開 Network（已勾 Preserve log），裡面完全沒有 /api/orders 的請求。問題最可能在哪？

✓ Network 是前後端釐清責任的證據：請求沒出現就是沒發出去，是前端的事；有出現再看狀態碼，4xx 查送出的參數，5xx 或 TTFB 很長才請後端查 log。b 錯在後端連請求都沒收到，查 log 什麼也找不到。（第 18 課）

練習 8：菜單卡片 hover 時用 transition: top .2s 往上浮 4px（卡片是 position: relative），舊手機上一動就卡。為什麼？

✓ 改動從哪一步開始，後面都要重做：top 改的是位置，每一幀都從 Layout 開始；transform: translateY(-4px) 只是挪動畫好的圖層。b 錯在動的屬性還是 top，升成圖層也照樣每幀 layout，還多佔一張點陣圖的記憶體。（第 19 課）

練習 9：要讓 600 張菜單卡片等高，同事這樣寫。哪裡會出事？

const heights = []
for (const card of cards) {
  card.style.height = 'auto'
  heights.push(card.offsetHeight)
}
const max = Math.max(...heights)
cards.forEach(c => { c.style.height = max + 'px' })

✓ 寫了影響版面的樣式後馬上讀 offsetHeight，瀏覽器只能當場 layout 才回答得出來；在迴圈裡讀寫交錯就是版面抖動。改成先把 600 張都設 auto，再一次讀完，最後一次寫完。a 錯在最後一行只寫不讀，修改會在程式跑完後一起處理，只有一次 layout。（第 19 課）

練習 10：點「加入購物車」要 450ms 才看到數字變。Performance 面板錄到點擊時主執行緒正在跑第三方 tag.js 的一個 380ms 長任務，你的 click 處理函式只花 15ms。先改哪裡？

✓ INP 拆成輸入延遲、處理時間、呈現延遲三段；這次 450ms 幾乎都是輸入延遲，點擊排在 380ms 的長任務後面等。對策是延後不急的第三方腳本、拆長任務。b 錯在切的是只花 15ms 的處理時間，點擊開始前的那段等待一點都沒少。（第 19、20 課）

練習 11：web-vitals attribution 版本回報手機 LCP 3.4 秒，其中 resourceLoadDelay 佔了 1.3 秒，其他三段都在建議比例附近。最可能的原因是？

✓ 資源載入延遲是「收到 HTML 到開始下載 LCP 圖片」，太長代表圖片太晚被發現或排太後面。改成寫在 HTML 裡的 <img>、不要 lazy、加 fetchpriority="high"；非得放 CSS 就 preload。b 是資源載入時間（下載本身）那一段的原因，跟何時開始下載無關。（第 20 課）

練習 12：咖啡店首頁的 Lighthouse CLS 是 0，RUM 收到的手機 p75 CLS 卻是 0.18。最可能的原因是？

✓ 實驗室是一種固定情境、沒有捲動和互動；捲動不算輸入，捲動中被推開的位移照樣計入 CLS。修法是找出晚到的元素，替它預留空間。a 錯在 CLS 取分數最高的 session window，不是全部相加。（第 20 課）

練習 13：首頁的 head 只打算加一個 <link rel="preload">，給下面哪一個最有效？

✓ preload 不會讓網路變快，只讓請求提早、排前面；值得給的是首屏一定用到、瀏覽器又很晚才發現的資源。CSS 背景圖要等 CSS 下載、解析完才被發現，正是這種。a 錯在 HTML 裡的 <img> 預先載入掃描器早就看到了，加 fetchpriority="high" 就夠，preload 沒有好處。（第 21 課）

練習 14：CI 在同一個工作裡讓 main 和 PR 各跑 5 次 Lighthouse，要判斷 LCP 有沒有回歸。兩邊各取哪個值來比？

✓ 實驗室量測本身會跳動，中位數不受單次特別慢或特別快的影響；兩邊在同一個環境比差異，超過容忍值才算回歸，上線後再用 RUM 的 p75 確認。b 錯在最小值是運氣最好的那一次，真的變慢時也可能剛好量到快的一次而漏報。（第 21 課）
