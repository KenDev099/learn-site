階段 5：SEO 與內容交付 · 第 24 課

結構化資料：JSON-LD、內容一致性與驗證

你接到一個任務：替豆留咖啡大安門市的頁面（https://brew.example.tw/stores/daan/）加上給搜尋引擎看的資料，讓它不用猜就知道「這頁在講一間咖啡店，地址、電話、營業時間是這些」。任務還有後半段：大安門市上個月平日才從 08:00 提早到 07:30 開門，頁面從後台讀資料，已經跟著改了；之後營業時間還會再變，給搜尋引擎的資料必須每次都跟頁面一起改，不能頁面寫 07:30、給機器的資料還寫 08:00。

這種寫給機器讀的資料叫結構化資料（structured data）。這課從「搜尋引擎為什麼需要它」開始，一路做到大安門市頁的完整標記、跟品牌與麵包屑連起來，最後讓它在改版、改營業時間之後仍然跟頁面一致。

這課的路線：
  1. 搜尋引擎看門市頁時缺了什麼：為什麼它猜不準營業時間，結構化資料能換到什麼、換不到什麼。
  2. 用什麼格式寫進頁面：JSON-LD 的基本寫法，以及內容來自後台時要防的 XSS。
  3. 大安門市該寫哪些欄位：CafeOrCoffeeShop 的地址、電話、營業時間。
  4. 品牌、網站、麵包屑怎麼不每頁抄一次：用 @id 把實體連成一張圖。
  5. 營業時間改了怎麼不脫節、上線後怎麼確認：同一份資料產生、工具驗證、自動測試與監控。
這課會用到：
  • 第 22 課的搜尋結果：每一筆由 title 連結和下面的摘要組成，摘要常取自 meta description。
  • 第 23 課的 canonical：重複的網址裡指定一個代表，要寫含 https:// 與網域的絕對網址。
  • TypeScript 課第 26 課的 unknown：外部資料先當成 unknown，逐一檢查後才縮小成具體型別（練習 3 用到）。

搜尋引擎看門市頁時，到底缺了什麼？

先看大安門市頁現在的 HTML：

<h1>豆留咖啡 大安門市</h1>
<p>106 台北市大安區復興南路一段 100 號</p>
<p>電話：(02) 2345-6789</p>
<dl>
  <dt>週一</dt><dd>07:30–18:00</dd>
  …
</dl>

人一看就懂。但搜尋引擎拿到的只是一串標籤和文字，它得自己判斷：「豆留咖啡 大安門市」是店名還是文章標題？「07:30–18:00」是營業時間還是某場活動的時間？HTML 標籤只說了「這是標題、這是段落、這是定義清單」，沒說「這是一間店的營業時間」。哪天設計師把 <dl> 換成表格，或改成 Vue 元件產生的一堆 <div>，搜尋引擎又要重新猜一次。它會盡力推測，但推測會錯，而你沒辦法知道它猜成什麼。

結構化資料的做法是不讓它猜，直接把答案寫出來：「這頁描述的是一間 CafeOrCoffeeShop，它的 name 是『豆留咖啡 大安門市』，openingHoursSpecification 是週一到週五 07:30–18:00…」。這句話裡的 CafeOrCoffeeShop、name 不是隨便取的名字，要用搜尋引擎都認得的詞彙。

這套共用詞彙叫 schema.org，由 Google、Microsoft、Yahoo、Yandex 共同發起維護。它定義了兩種東西：

  • 型別（type）：「這是什麼東西」，例如 Person（人）、Product（商品）、CafeOrCoffeeShop（咖啡店），一共有幾百種。
  • 屬性（property）：每種型別可以有哪些欄位，例如 name（名稱）、address（地址）。

大家用同一套詞彙，搜尋引擎才不用替每個網站學一套新的欄位名稱。

寫了能換到兩樣東西。第一樣是複合式搜尋結果（rich result）。一般的搜尋結果是藍色標題加兩行摘要；rich result 是多了額外資訊的版本，例如網址那一行換成「豆留咖啡 › 菜單 › 咖啡」的麵包屑，或商品結果多了價格與庫存、活動結果多了日期。每一種 rich result 對應 Google 支援的特定型別與必填欄位，清單在 Google 的 Search Central 文件裡。

第二樣是讓搜尋引擎確定這頁在講哪個實體。實體（entity）是「一個具體存在的東西」：豆留咖啡這個品牌是一個實體，大安門市這間店是另一個實體。結構化資料可以說清楚這頁講的是哪一個，以及它跟其他實體的關係，例如「大安門市屬於豆留咖啡」。這件事在第 4 節會用到。

換不到的也要先講清楚，免得跟主管或行銷同事期待錯了。依 Google 的結構化資料一般指南：

  • 不保證顯示：標記寫對只代表「符合資格」。實際要不要顯示 rich result，由 Google 依查詢內容、使用者的地點與裝置、頁面品質等因素決定。
  • 不是排名捷徑：結構化資料不會讓排名變高。它影響的是結果「長什麼樣子」，不是排第幾。
💡 實務上：營業時間至少有兩個地方要改
門市的地圖資訊（Google 地圖上的營業時間、電話）主要來自 Google 商家檔案（Google Business Profile），要在那邊另外維護；網站上的結構化資料是讓網頁本身被正確理解。商家檔案通常是行銷或門市主管在管，網站是工程團隊在管，最常見的狀況是「颱風天提早打烊，地圖改了、官網沒改」或反過來。大安門市改成 07:30 開門時也一樣：官網這課會處理，商家檔案要有人另外改。接到「搜尋結果顯示的時間不對」的回報時，先問清楚是地圖面板還是官網的搜尋結果，兩者的修法不同。資深的做法是在改營業時間的流程裡寫明兩邊都要改、由誰改。

知道了要寫什麼、能換到什麼，下一個問題是：這份答案要用什麼格式、放在頁面的哪裡？

答案要用什麼格式寫進頁面？JSON-LD

上一節的結論是「用 schema.org 的詞彙把答案寫出來」。寫法有三種：JSON-LD、Microdata、RDFa。Microdata 和 RDFa 是在現有的 HTML 元素上加屬性，例如在 <h1> 上標「這是 name」，資料跟版面混在一起：設計師改版面、搬動元素，標記就可能跟著壞掉。

JSON-LD（JSON for Linking Data）是第三種：一段獨立的 JSON，放在 <script type="application/ld+json"> 裡，跟頁面的 HTML 結構無關。Google 的文件標明推薦 JSON-LD，原因正好對應 Microdata 的缺點：改版面不會弄壞它，而且它就是一段 JSON，最容易從程式產生。這課只用 JSON-LD。

大安門市的最小版本長這樣，先只寫店名、地址和餐飲類型：

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "CafeOrCoffeeShop",
  "name": "豆留咖啡 大安門市",
  "address": {
    "@type": "PostalAddress",
    "streetAddress": "復興南路一段 100 號",
    "addressLocality": "大安區",
    "addressRegion": "台北市",
    "postalCode": "106",
    "addressCountry": "TW"
  },
  "servesCuisine": ["咖啡", "輕食"]
}
</script>

這段裡有四種寫法，之後每一段 JSON-LD 都是它們的組合：

寫法意思
"@context": "https://schema.org"這段資料用 schema.org 的詞彙。寫在最外層物件，裡面的巢狀物件不用重寫
"@type": "CafeOrCoffeeShop"這個物件是什麼型別。型別名稱大小寫要完全一樣，寫錯（例如不存在的 CoffeeShop）搜尋引擎就不認得
"address": { "@type": "PostalAddress", … }巢狀物件：屬性的值本身是另一個有型別的物件
"servesCuisine": ["咖啡", "輕食"]陣列：屬性有多個值。schema.org 的屬性幾乎都可以是單一值或陣列，讀的程式兩種都要接受

這段 script 放在 <head> 或 <body> 都可以，Google 都讀得到。用 Vue SSR 時通常跟 title 一起輸出在 head。

寫的時候要記得它是 JSON，不是 JavaScript。在 Vue 元件裡寫物件常用的寫法，在這裡都不合法：屬性名稱與字串一律要雙引號，不能有尾端逗號、註解、undefined。JSON 語法錯一個字，整段都會被忽略，而且頁面看起來完全正常，沒有任何錯誤訊息提醒你。這也是為什麼後面會一直強調「用程式產生，不要手寫」。

另一件要懂的事是：瀏覽器不會執行這段 script。type 屬性的值決定瀏覽器怎麼對待 script 元素；application/ld+json 是一種資料格式的名稱（MIME type），不是 JavaScript 的類型，瀏覽器就只把它當成一塊資料放著。認證課第 7 課教過 CSP（內容安全政策），它的 script-src 用來限制頁面能執行哪些 script；JSON-LD 不會被執行，所以 script-src 也不會擋它。

「不會執行」容易讓人以為放什麼進去都安全，其實不然。大安門市的介紹文字是店長在後台輸入的，如果把它原封不動放進 JSON-LD，就可能被攻擊者讓自己寫的 script 在別人的頁面上執行。這種攻擊叫 XSS（跨站腳本攻擊）。問題出在 HTML 解析器的運作方式。解析器讀 <script> 元素時不懂 JSON，它只找 </script> 這串字，一看到就結束這個元素，不管這串字是不是在 JSON 的字串裡面。店長（或盜用店長帳號的人）把門市介紹寫成 </script><script>…，JSON-LD 那個元素就在中途被關掉，後面那段變成一個真的會執行的 script。

JSON.stringify 只負責產生合法的 JSON，不會處理這件事。下面這格先直接 stringify，再做跳脫。執行後看兩行「有沒有 </script」的結果，以及最後一行「解析回來一樣」。

\u003c 是 JSON 字串裡 < 的跳脫寫法。JSON.parse 讀回來的值完全一樣，搜尋引擎拿到的資料沒有變；但 HTML 原始碼裡已經沒有 </script 這串字，解析器就不會提早結束元素。用框架的 head 管理工具（例如 Nuxt 的 useHead）輸出時，先查它的文件確認會不會做這個跳脫；自己用字串拼 HTML 時一定要自己做。XSS 的完整說明在認證課第 7 課。

格式有了，也知道怎麼安全地輸出。但最小版本只有店名和地址；大安門市頁上還有電話、價位、每天的營業時間，這些要用哪些欄位、怎麼寫？

大安門市該寫哪些欄位、營業時間怎麼表達？

先確認型別選對了。schema.org 的型別有繼承關係，越往右越具體：

Thing › Organization／Place › LocalBusiness › FoodEstablishment › CafeOrCoffeeShop

子型別會繼承上層的所有屬性。所以 CafeOrCoffeeShop 可以用 LocalBusiness 的 openingHoursSpecification（營業時間）、FoodEstablishment 的 menu 與 servesCuisine、Organization 的 parentOrganization（所屬組織）。Google 的 LocalBusiness 文件建議用最具體的子型別，咖啡店就用 CafeOrCoffeeShop，不要只寫 LocalBusiness：寫得越具體，搜尋引擎越不用猜。

型別確定後，照 Google LocalBusiness 文件列的欄位，一個個對照大安門市頁上的資訊來填。表格右欄是每個欄位的寫法規則，寫練習 1 時回來查：

屬性必填？寫法與規則
name必填門市名稱，跟頁面上的一樣。只放名稱，不要塞地址、電話、關鍵字
address必填PostalAddress，拆成欄位。台灣地址：postalCode 郵遞區號、addressRegion 縣市、addressLocality 鄉鎮市區、streetAddress 路段門牌、addressCountry 用 "TW"
geo建議GeoCoordinates 的 latitude（緯度）與 longitude（經度），小數至少 5 位（約 1 公尺的精度）
telephone建議包含國碼與區碼：+886-2-2345-6789（國碼 886 之後，區碼去掉開頭的 0）
url建議這間門市的網址（不是首頁），用跟 canonical 一樣的絕對網址
menu建議（餐飲）菜單頁的完整網址
servesCuisine建議（餐飲）供應的餐飲類型
priceRange建議價位，少於 100 個字元，例如 "NT$70–120" 或 "$$"；太長 Google 會忽略
openingHoursSpecification建議營業時間，下面細講
aggregateRating、review有條件Google 只接受「收集其他商家評論的網站」標記。店家在自己的官網標記自己的評價，不會得到星等

表裡大部分欄位都是「照抄頁面上的值，換成規定的格式」，例如頁面寫 (02) 2345-6789，telephone 就寫成含國碼的 +886-2-2345-6789。最需要想一下的是營業時間，因為它是這課任務的主角：頁面上是「週一 07:30–18:00、週二 07:30–18:00…」一天一列，機器要的則是結構化的時段。

營業時間用 OpeningHoursSpecification 型別的物件表達，一個物件代表「這幾天，幾點開到幾點」：

  • dayOfWeek：星期幾。寫 "Monday" 或完整網址 "https://schema.org/Monday"，好幾天共用同一個時段就寫成陣列。
  • opens／closes：開門與打烊時間，24 小時制。

大安門市平日 07:30–18:00、週末 09:00–17:00，所以是兩個物件。其他店家可能遇到的情況，寫法如下（查表用，不用背）：

情況寫法
平日與週末不同兩個物件：["Monday",…,"Friday"] 07:30–18:00；["Saturday","Sunday"] 09:00–17:00
跨午夜（週五營業到隔天 01:00）一個物件就好："dayOfWeek": "Friday", "opens": "18:00", "closes": "01:00"，closes 比 opens 早是合法的
24 小時營業"opens": "00:00", "closes": "23:59"
整天公休"opens": "00:00", "closes": "00:00"（Google 文件的寫法）
過年暫停營業加 validFrom／validThrough（YYYY-MM-DD）的時段

寫完之後要逐一檢查：每一個值都能在頁面上找到對應。座標是例外，頁面通常不顯示經緯度，但要是門市真正的位置。練習 1 就是把這份補到大安門市頁上。

到這裡，大安門市頁本身已經描述清楚了。但它只講了「這間店」。網站上還有菜單頁、其他門市頁，它們也都屬於豆留咖啡這個品牌；菜單頁上方還有「首頁 › 菜單 › 咖啡」的麵包屑。如果每一頁都把品牌資料完整抄一遍，會發生什麼事？

品牌、網站、麵包屑也要標記時，怎麼不每頁抄一次？

上一節留下的問題，其實是程式裡很熟悉的問題：同一份資料複製到很多地方。每一頁、每間門市都把「豆留咖啡」這個品牌的名稱、網址、logo 抄一次，資料一多就會不一致，例如品牌改名後，某幾頁還是舊名字。搜尋引擎看到十頁各自描述一個「豆留咖啡」，也無法確定它們是不是同一個品牌。

寫程式時的解法是定義一次、其他地方用參照。JSON-LD 也有同樣的機制：@id。它是替一個實體取的識別名稱，寫成網址的形式，例如 https://brew.example.tw/#organization。在一個地方完整描述這個實體並寫上 @id，其他地方只要寫 { "@id": "https://brew.example.tw/#organization" }，意思就是「就是那一個」，不用再重寫內容。

#organization 這種片段不必真的對應頁面上的錨點。用網址形式，是為了讓識別碼全世界不重複；加上 #…，是為了不跟真實的網頁網址撞名（https://brew.example.tw/ 是首頁這個網頁，https://brew.example.tw/#organization 是品牌這個實體）。

這裡有一個很容易踩的坑：@id 一律用絕對網址。寫成相對的 "#organization" 時，JSON-LD 會以各頁自己的網址為基準去解析，在 /menu/ 頁上就變成 https://brew.example.tw/menu/#organization，跟首頁的 https://brew.example.tw/#organization 不是同一個實體，等於又回到「每頁各自一個品牌」。全站的 @id 值要一字不差（包括結尾斜線），所以通常集中寫在一個常數檔裡，所有頁面都從那裡取。

BreadcrumbList有麵包屑的每一頁跟頁面上的麵包屑一致，見下面

一頁要放好幾個實體時，有兩種寫法：寫好幾個 <script type="application/ld+json"> 區塊，每個一個實體；或只寫一個區塊，把多個實體放進最外層的 "@graph": [ … ] 陣列裡。兩種搜尋引擎都讀得懂。用 @graph 時 @context 只要寫一次，實體之間的參照也集中在一起好檢查，練習 2 用的就是這種寫法。

四種實體裡，前三種上一節和這一節已經講過，剩下麵包屑。麵包屑（breadcrumb）是頁面上方「首頁 › 菜單 › 咖啡」這種顯示目前位置的導覽。HTML 用第 2 課的 <nav aria-label="麵包屑"> 加有序列表 <ol> 寫，目前這一頁的那層加 aria-current="page"。對應的結構化資料是 BreadcrumbList，Google BreadcrumbList 文件的規則：

  • itemListElement 是 ListItem 陣列，至少兩層。
  • position 從 1 開始，1 是路徑的最上層（首頁）。
  • name 是顯示的文字，跟頁面上的麵包屑一樣。
  • item 是那一層的網址，用絕對網址；最後一層（目前這一頁）可以省略，Google 會用目前頁面的網址。
{
  "@type": "BreadcrumbList",
  "itemListElement": [
    {
      "@type": "ListItem",
      "position": 1,
      "name": "首頁",
      "item": "https://brew.example.tw/"
    },
    {
      "@type": "ListItem",
      "position": 2,
      "name": "菜單",
      "item": "https://brew.example.tw/menu/"
    },
    {
      "@type": "ListItem",
      "position": 3,
      "name": "咖啡"
    }
  ]
}

到這裡你會發現，同一份資訊可以有很多種合法寫法：單一區塊或多個區塊、有沒有 @graph、實體直接寫在裡面或只寫 @id 參照。寫的一方可以挑順手的，但讀的一方（搜尋引擎，以及這課最後要寫的自動檢查）必須全部接受。讀取的做法是兩步：先把所有區塊和 @graph 攤平成一份節點清單，再用 @id 建索引，遇到 { "@id": … } 就能找回被參照的完整實體。

下面這格模擬讀取端。執行後看兩件事：攤平後列出了哪幾個節點，以及最後一行有沒有從門市的 parentOrganization 參照找回品牌名稱。練習 3 的 flatten 就是這個做法。

現在大安門市、品牌、網站、麵包屑都標記好了，而且品牌只描述一次。回到開場任務的後半段：營業時間會變，頁面會跟著後台改，JSON-LD 呢？

營業時間改了，JSON-LD 怎麼不跟頁面脫節？

先想像最常見的做法會出什麼事。店長在後台改資料的系統叫 CMS（內容管理系統）。大安門市頁上的營業時間表就是從 CMS 讀出來的。假設 JSON-LD 是工程師照 08:00 手寫在模板裡的，店長在後台改成 07:30 後，頁面立刻變了，JSON-LD 卻還是 08:00。頁面看起來一切正常，沒有任何人會發現。

這不只是「資料舊了」而已。Google 結構化資料一般指南最重要的一條是：不要標記讀者看不到的內容。結構化資料描述的東西要跟頁面主要內容相同，也不能誤導。常見的違規長這樣：

  • 頁面上沒有任何評價，JSON-LD 卻寫了 4.9 顆星的 aggregateRating。
  • 頁面營業時間改成 07:30 開門，JSON-LD 還是舊的 08:00。
  • 標記頁面上沒有的商品價格，或一個不存在的活動。

第二條就是剛才的情境：不是故意造假，只是忘了改，結果一樣是「給機器的資料跟頁面不一樣」。

違反指南時，Google 可能採取人工處置（manual action），也就是 Google 的人員審查後，對違反政策的網站做的處理。結構化資料的人工處置會讓網站失去 rich result 的資格（指南寫明不影響一般排名）。收到時，Search Console 的「人工處置」報告會列出原因，修正後要提出重新審查要求。

回頭看 08:00 的情境，問題的根源是頁面和 JSON-LD 由兩份資料各自維護：只要有兩份，總有一天會只改到一份。靠「記得一起改」守不住，要讓它在結構上不可能脫節：兩者都從同一份資料產生。下面這格用同一份門市資料，同時產生頁面上一天一列的營業時間表和 JSON-LD 的 openingHoursSpecification。執行後對照上下兩段輸出，時間一定相同；試著把 opens: '07:30' 改成別的時間再執行，兩邊會一起變。

資料來源統一之後，還要決定 JSON-LD 在哪裡產生。產生 HTML 的方式有幾種：SSR（伺服器端渲染）是每次有請求進來時，在伺服器產生完整的 HTML 再回傳；SSG（靜態網站產生）是在建置時就先把每一頁的 HTML 產生好；CSR（用戶端渲染）則是伺服器只回傳一個空殼，由瀏覽器執行 JavaScript 把內容畫出來。JSON-LD 要用 SSR 或 SSG 輸出在 HTML 原始碼裡，搜尋引擎第一次抓頁面就看得到。只在瀏覽器端用 JavaScript 插入的 JSON-LD，要等 Google 渲染頁面才看得到，其他爬蟲可能根本不執行 JavaScript；這部分第 25 課細講。

如果產生 JSON-LD 的程式用 TypeScript 寫，還可以讓編輯器幫忙擋掉拼錯的型別與屬性名稱。schema-dts 是 Google 維護的 schema.org 型別套件，只有型別宣告，不會打包進程式（版本見課末）。下面是大安門市 JSON-LD 的產生函式，注意兩個註解：拼錯型別名稱會直接型別錯誤，輸出前要做上一節的 < 跳脫：

// npm install -D schema-dts（只有型別，不會打包進程式）
import type { CafeOrCoffeeShop, WithContext } from 'schema-dts'

export function storeJsonLd(store: Store): WithContext<CafeOrCoffeeShop> {
  return {
    '@context': 'https://schema.org',
    '@type': 'CafeOrCoffeeShop',   // 打成 'CoffeeShop' 會直接型別錯誤
    '@id': `https://brew.example.tw/stores/${store.slug}/#store`,
    name: store.name,
    telephone: store.phoneE164,
    parentOrganization: { '@id': 'https://brew.example.tw/#organization' },
    openingHoursSpecification: store.hours.map(h => ({
      '@type': 'OpeningHoursSpecification',
      dayOfWeek: h.days,             // 型別是 schema-dts 的 DayOfWeek
      opens: h.opens,
      closes: h.closes,
    })),
  }
}

// 輸出到 HTML 前跳脫 <
export const serializeJsonLd = (data: object) => JSON.stringify(data).replace(/</g, '\\u003c')

這個函式同時解決了前面三節的問題：資料來自同一份 store、型別名稱有編輯器把關、輸出前做了跳脫。但它還擋不了兩件事：一是有人改了頁面（例如拿掉電話）卻沒改這個函式，值還是會跟頁面不一致；二是 Google 要求的欄位沒寫：型別只檢查名稱與值的形狀，不知道 Google 對哪種 rich result 要求哪些欄位。這兩件事要靠下一節的驗證工具與自動測試。

💡 實務上：code review 時問「這個值頁面上看得到嗎？」
結構化資料出問題多半不是寫錯語法，而是頁面改版時沒人想到它。例如設計師把門市頁的電話拿掉、改成「線上預約」按鈕，JSON-LD 的 telephone 還留著；或 PM 想「先把評價星等加進去，頁面之後再做」。審 PR 時看到 JSON-LD 多了欄位，就對照頁面有沒有對應的內容；看到頁面拿掉了某段資訊，就回頭查產生 JSON-LD 的函式要不要跟著改。被要求標記頁面上沒有的東西時，直接說明會有人工處置的風險，比事後補救省事。

上線前後，怎麼確認 Google 讀到的是對的？

上一節留下兩個型別系統擋不了的問題：Google 要求的欄位有沒有寫齊，以及值跟頁面是否一致。第一個問題有現成的工具，三個各管一段：

工具檢查什麼什麼時候用
Rich Results Test（search.google.com/test/rich-results）Google 官方工具：這頁的結構化資料能產生哪些 Google 支援的 rich result、缺了哪些必填欄位。可以貼網址（會實際抓取並渲染）或貼程式碼開發與上線前，確認 Google 讀得到、符合資格
Schema Markup Validator（validator.schema.org）通用的 schema.org 檢查：語法、型別與屬性存不存在，不做 Google 特有的規則Google 不支援 rich result 的型別（例如 WebSite 的細節、Organization 的關係）也想確認寫對時
Search Console上線後的監控：各種 rich result 的報告（例如「麵包屑」）列出有效與有錯誤的網址；網址審查工具看 Google 實際抓到的版本；人工處置報告上線後定期看，改版後特別注意錯誤數量的變化

前兩個驗證工具容易搞混，它們是互補的。Schema Markup Validator 說沒問題，只代表 schema.org 語法正確，不代表符合 Google 的要求；Rich Results Test 只看 Google 支援 rich result 的類型，其他型別它不會列出來。以大安門市為例：門市和麵包屑用 Rich Results Test 確認 Google 的資格，品牌與網站之間的 @id 關係則用 Schema Markup Validator 確認寫對。

第二個問題，工具幫不上忙。工具只能檢查語法與欄位，檢查不了內容一致性：08:00 和 07:30 都是合法的時間，工具不知道頁面上寫的是哪一個。所以團隊實務上把「JSON-LD 跟頁面一致」寫成自動測試：讀出頁面上的 JSON-LD 和頁面文字，逐欄比對，不一致就讓部署失敗。練習 3 寫的就是這個比對函式。E2E 測試（端對端測試）是用真的瀏覽器打開頁面、像使用者一樣操作與檢查的測試。第 27 課會把這個比對放進 E2E 測試，每次部署都跑。

到這裡，開場的任務就完整了：大安門市頁有完整的 JSON-LD，跟品牌和麵包屑連成一張圖，跟頁面從同一份資料產生，上線前用工具驗證、每次部署用自動測試比對、上線後用 Search Console 監控。以後再改營業時間時，店長只要在後台改一次。

💡 實務上：上線檢查挑代表頁，不用每頁都測
同一個模板產生的頁面結構都一樣，上線前用 Rich Results Test 各測一頁就好：首頁、一間門市頁（例如大安門市）、一個有麵包屑的菜單頁。真正要盯的是 Search Console：改版或換模板後，看各 rich result 報告的錯誤數有沒有突然變多，那通常代表某個模板壞了。另一個常見的坑是 Search Console 的權限只在離職同事或外包廠商手上，出事時沒人收得到通知；接手專案時先確認團隊自己有擁有者權限。

補充與查表

主線用不到、但規劃或審查結構化資料時會查的細節。

Google 支援的 rich result 會變：不要為了 rich result 硬加標記

Google 會調整支援的 rich result。HowTo（教學步驟）在 2023 年 8 月宣布縮減、9 月起不再顯示；FAQ（常見問題）同年縮減到只對知名的政府與醫療網站顯示，並在 2026 年 5 月完全停止顯示、6 月移除文件。照 Search Central 文件的現況決定要標記什麼，標記的前提是內容本來就在頁面上，而不是為了版面效果去改內容。

Structured Data Testing Tool 去哪了

舊文章常提到的 Google Structured Data Testing Tool，已經拿掉 Google 特有的檢查，移到 schema.org 成為現在的 Schema Markup Validator。要檢查 Google 的資格，用 Rich Results Test。

這課依據的文件與版本

  • Google 結構化資料一般指南：2026-07-10 版。
  • Google LocalBusiness 文件、BreadcrumbList 文件：2026-09-08 版。
  • schema-dts：目前版本 2.1.0。

練習

練習 1：大安門市頁目前的 JSON-LD 只有店名。把它補完整（只改 <script type="application/ld+json">，頁面看得到的內容不要動）：@type 用咖啡店的型別；address 用 PostalAddress 照台灣格式拆欄位（含 addressCountry）；geo 用門市座標緯度 25.041234、經度 121.543561；telephone 含國碼；url 是這間門市頁的完整網址；menu 是菜單頁的完整網址；servesCuisine；priceRange；openingHoursSpecification 涵蓋 7 天。所有的值都要跟頁面上看得到的資訊一致。

練習 2：咖啡菜單頁（https://brew.example.tw/menu/coffee/）的 JSON-LD 只有門市。改寫成一個 @graph，裡面有：Organization（@id 是 https://brew.example.tw/#organization，品牌名稱「豆留咖啡」、網址是首頁）；WebSite（@id 是 https://brew.example.tw/#website，用 publisher 參照 Organization）；原本的門市加上自己的 @id（https://brew.example.tw/stores/daan/#store），用 parentOrganization 參照同一個 Organization，不要重寫品牌資料；以及跟頁面麵包屑一致的 BreadcrumbList。所有 @id 與網址都用絕對網址。頁面看得到的內容不要動。

練習 3：上線前的自動檢查。寫 checkConsistency(jsonLd, page)，找出門市 JSON-LD 跟頁面不一致的地方，回傳問題清單（順序不拘）。jsonLd 是從頁面讀出來的外部資料，型別是 unknown：可能是單一物件、多個區塊組成的陣列、或 { "@graph": [...] }，也可能根本不是物件。先寫 flatten 攤平成節點清單，找出 @type 是（或陣列包含）CafeOrCoffeeShop 的節點；找不到就回傳 ['unparseable']，不要丟錯。找到之後檢查：

  • 'name'：name 不是字串，或去掉空白後不在 visibleText（也去掉空白）裡。
  • 'telephone'：telephone 不是字串，或跟頁面上的電話對不上。頁面可能寫 (02) 2345-6789、02.2345.6789 或 +886 2 2345 6789：寫 nationalNumber 只留數字、去掉開頭的 886 或 0，再看 visibleText 只留數字後是否包含它。
  • 'hours:Monday' … 'hours:Sunday'：那一天標記的 opens–closes 跟 page.hours 不同（包括某一邊沒有那一天）。openingHoursSpecification 與 dayOfWeek 都可能是單一值或陣列；dayOfWeek 可能是 'Monday' 或 'https://schema.org/Monday'；時間可能帶秒（'07:30:00'），只比前 5 個字；跨午夜（closes 比 opens 早）是合法的。每天最多一個時段。
  • 'aggregateRating'：有標記，但 ratingValue 沒出現在頁面上。'review'：有任何一則評論的 reviewBody 不在頁面上。

練習 4：門市頁加了完整、通過 Rich Results Test 的結構化資料，Google 搜尋結果就一定會顯示 rich result 嗎？

✓ b：Google 的一般指南寫明標記正確不保證顯示，rich result 是否出現由演算法依情況決定。a 錯：測試只檢查資格。c 錯：自然搜尋結果不能用錢買。d 錯：沒有固定的等待時間，重新抓取與處理的時間也不保證。

練習 5：行銷同事想在門市頁的 JSON-LD 加上 "aggregateRating": { "ratingValue": 4.9 }，但頁面上沒有任何評價。會有什麼後果？

✓ b：結構化資料必須反映頁面上看得到的內容；違反時 Google 可以人工處置，網站失去 rich result 資格。另外 Google 只接受收集「其他商家」評論的網站標記評價，店家自己的官網本來就拿不到星等。a 錯：Google 會比對頁面內容。c 錯：結構化資料不影響排名。d 錯：被發現後可能收到人工處置，影響範圍可以是部分頁面或整個網站的 rich result 資格。

練習 6：Rich Results Test 與 Schema Markup Validator 差在哪？

✓ b：兩者互補。語法對（Validator 通過）不代表符合 Google 的必填欄位；Rich Results Test 也不會列出 Google 不支援 rich result 的型別。a 錯：檢查的範圍不同。c 錯：Rich Results Test 才是 Google 的官方工具，Validator 在 schema.org。d 錯：兩種工具都支援 JSON-LD、Microdata、RDFa。

常見錯誤

  • 結構化資料與頁面不一致：頁面和 JSON-LD 由兩份資料各自維護，改了一邊忘了另一邊，例如頁面改成 07:30、JSON-LD 還是 08:00。從同一份資料產生，並用自動測試比對。
  • 標記看不到的內容：評分、評論、價格、活動只在 JSON-LD 裡有。違反指南，可能收到人工處置。
  • JSON 語法錯誤：尾端逗號、單引號、註解。整段被忽略，頁面上看不出來。用 Rich Results Test 與自動測試檢查，或用 JSON.stringify 產生而不是手寫字串。
  • 把使用者輸入直接放進 JSON-LD：</script> 會提早結束 script 元素，後面的內容變成可執行的 HTML，造成 XSS。序列化後把 < 換成 \u003c。
  • 型別名稱寫錯：CoffeeShop、Cafe 都不存在。照 schema.org 的名稱寫，或用 schema-dts 讓編輯器檢查。
  • @id 用相對網址或各頁寫法不同：搜尋引擎會當成不同實體。全站用同一個絕對網址常數。
  • 麵包屑 position 從 0 開始、name 跟頁面不同：position 從 1 開始，name 照頁面上的文字。
  • 為了 rich result 加標記：Google 支援的類型會改（HowTo、FAQ 都已不顯示，見課末）。先確定內容對使用者有用並且在頁面上，再看有沒有對應的標記。

小結

  • 搜尋引擎只看得到標籤和文字，營業時間要靠猜；結構化資料用 schema.org 的型別與屬性直接寫出答案。它讓頁面有資格顯示 rich result，但不保證顯示，也不影響排名。
  • 用 JSON-LD 寫在 <script type="application/ld+json">：@context、@type、巢狀物件、陣列。它是嚴格的 JSON，瀏覽器不執行它，但 HTML 解析器看到 </script> 仍會結束元素，內容來自後台時要把 < 跳脫成 \u003c。
  • 咖啡店用最具體的 CafeOrCoffeeShop：必填 name、address（PostalAddress 拆欄位）；geo 小數 5 位、電話含國碼、url 與 menu 用絕對網址、priceRange 少於 100 字元；營業時間用 OpeningHoursSpecification，跨午夜用一個物件、公休寫 00:00–00:00。
  • 用絕對網址的 @id 把 Organization、WebSite、門市、麵包屑連成一張圖，品牌只完整描述一次；麵包屑 position 從 1 開始、name 跟頁面一致。讀取端要能接受多個區塊與 @graph。
  • 結構化資料必須反映看得到的內容：跟頁面從同一份資料、在伺服器端（SSR／SSG）產生，用 schema-dts 擋拼錯的名稱。
  • Rich Results Test 看 Google 資格、Schema Markup Validator 看 schema.org 語法，兩者都查不了一致性，所以要寫自動測試比對 JSON-LD 與頁面；上線後用 Search Console 監控錯誤數與人工處置。
