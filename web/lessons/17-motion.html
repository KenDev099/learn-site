階段 3：現代 CSS 與視覺品質 · 第 17 課

動畫與微互動：transition、keyframes、transform 與 prefers-reduced-motion

咖啡店網站改版後，客服收到三則回報：「按鈕滑過去要等一秒才變色，以為網站當掉」、「手機上捲動菜單時一直卡卡的」、「首頁的推薦一直在動，我看了頭暈，關也關不掉」。三則都出在同一份菜單頁的動畫上，但原因各不相同：第一則是時間太長，第二則是動錯了屬性，第三則是沒有照顧對動態敏感的使用者。

這課的任務就是把這三則回報一則一則關掉。每修一則，就學到一組 CSS 動畫的工具，也學到它什麼時候不該用。做完之後，你手上會有一份檢查清單，之後在 PR 裡看到任何動畫，都能判斷它會不會變成下一則客服回報。

這課的路線：
  1. 三則回報的共同點：動畫是為了什麼，哪些動畫幫得上使用者，哪些只是有代價的裝飾。
  2. 第一則回報（按鈕等一秒）：transition 怎麼運作、寫在哪裡、列哪些屬性；時長多長、easing 怎麼選。
  3. 第二則回報（捲動卡卡）：位移為什麼用 transform 而不是 top、margin；要不要先用 will-change。
  4. 第三則回報的輪播，加上購物車徽章彈一下：這種沒有 hover 可觸發的動畫怎麼寫（@keyframes），無限動畫怎麼停。
  5. 第三則回報的後半：prefers-reduced-motion 替對動態敏感的人拿掉位移，再加上一個所有人都按得到的暫停控制。
這課會用到：
  • 第 5 課的 :focus-visible：只在鍵盤操作時顯示焦點框的偽類。
  • 第 16 課的 custom properties：用 --名稱 宣告、var() 讀取的 CSS 變數，這課拿來管理時長與 easing。
  • 第 10 課的 stacking context：一組元素在裡面比 z-index，跟外面的元素整組一起排；transform 會建立新的 stacking context。

動手之前：這三則回報有什麼共同點？

三則回報都不是「動畫壞了」，而是「動畫做了，但沒想清楚它為什麼存在」。所以修之前，先建立一個判斷標準：一個動畫什麼時候值得放。

網頁上的動畫大多是微互動（micro-interaction），意思是一個操作配一個小小的視覺回應，例如按鈕被滑過時變色、加入購物車後數量徽章彈一下。微互動有用的情況大概三種：

  • 回饋：告訴使用者「收到了」。按鈕 hover 變色、按下去縮一點。
  • 關聯：告訴使用者東西從哪裡來、到哪裡去。下拉選單從按鈕下方展開，使用者就知道是這顆按鈕打開的。
  • 注意：把視線帶到變化的地方。購物車數量變了，徽章彈一下。

說不出屬於哪一種的動畫就是裝飾。裝飾不是免費的，它有三種代價：

  • 效能：動畫的每一幀瀏覽器都要重新計算，動錯屬性就會卡（第二則回報）。
  • 注意力：會動的東西會搶走視線，旁邊的文字就讀不下去。
  • 身體不適：有一群人的內耳平衡系統比較敏感，醫學上叫前庭障礙（vestibular disorder）。大範圍的位移、縮放、視差捲動，會讓他們頭暈、噁心（第三則回報）。

拿這個標準看三則回報：按鈕變色是回饋，值得留，但要快；卡片浮起是回饋，值得留，但要換一種動法；推薦輪播的目的是吸引注意，但它停不下來，代價已經超過好處。接下來就照這個順序修，從最常見、也最簡單的按鈕開始。

第一則回報：按鈕變色為什麼要等一秒？

打開菜單頁的 CSS，按鈕是這樣寫的（下面練習 1 的起始 CSS 也是這一段）：

.btn {
  transition: all 1s;
}
.btn:hover {
  background: var(--brand-hover);
}

要看懂這裡錯在哪，先要知道 transition 在做什麼。

transition 是什麼、怎麼運作

沒有 transition 時，:hover 規則一生效，背景色就在下一幀直接換成新顏色，中間沒有過程。過渡（transition）改變的是這個「換過去」的方式：屬性值改變時，瀏覽器不直接跳到新值，而是在一段時間內，每一幀算出舊值和新值之間的一個中間值，讓顏色慢慢變過去。

所以 transition 本身不會讓任何東西動。它只是一條「如果這些屬性改變了，請花多少時間變過去」的規則，要等某個屬性的值真的改變才會開始，例如滑鼠移入讓 :hover 生效、JavaScript 加了一個 class。

.btn {
  background: #6b3e26;
  /*          要過渡的屬性    時長    easing    延遲 */
  transition: background-color 150ms ease-out 0s;
}
.btn:hover {
  background: #8a5233;
}

transition 是四個屬性的簡寫，對應上面註解的四個位置：

屬性意思預設值
transition-property哪些屬性改變時要過渡，可以用逗號列好幾個all
transition-duration花多久，例如 150ms、0.15s0s（等於沒有過渡）
transition-timing-function緩動函式（easing），決定過程中速度怎麼變化，下一節細講ease
transition-delay改變後等多久才開始0s

兩個屬性要用不同的時間時，用逗號分開：transition: transform 250ms ease-out, box-shadow 250ms ease-out;。

回頭看客服的回報：all 1s 的意思是「任何屬性改變，都花一秒變過去」。滑鼠移入時背景色花了一整秒才變完，使用者在這一秒裡看不出按鈕有沒有反應，就以為網站當掉了。時長怎麼定，下一節講；在那之前，先確認兩件事：transition 寫的位置對不對，以及 all 該不該寫。

transition 要寫在平常的狀態

原本的 CSS 寫在 .btn 上，位置是對的；但很多人會寫在 :hover 裡，先看看那樣會怎樣。把 transition 放進 .btn:hover，結果是滑鼠移入時會慢慢變色，移開時卻瞬間跳回去。原因在於瀏覽器決定「這次變化要不要過渡」時，看的是變化之後那個狀態的 transition：

  • 滑鼠移入：變化之後是 hover 狀態，.btn:hover 裡有 transition，所以會過渡。
  • 滑鼠移開：變化之後回到平常的狀態，:hover 不成立了，用的是 .btn 的 transition。.btn 上沒寫，所以顏色瞬間跳回。

寫在 .btn 上，平常狀態和 hover 狀態都吃得到這條 transition，進出兩個方向都會過渡。

為什麼不要寫 transition: all

只寫 transition: 0.3s 或 transition: all 0.3s，等於「任何屬性改變都過渡」。按鈕現在只有背景色會變，看起來沒差，但問題會在以後出現：

  • 意外的動畫：RWD 在斷點切換 padding、深色模式切換顏色、Vue 加 class 改 width，全部都會慢慢變過去，畫面看起來像壞掉。
  • 效能：width、padding 這類屬性改變時，瀏覽器每一幀都要重新排版（第二則回報那一節會說明）。用 all 時，誰改了這些屬性你根本不會注意到。
  • 難維護：看 CSS 不知道設計上到底想過渡哪幾個屬性。

做法是只列出這個互動真的會改變的屬性。按鈕 hover 只改背景色，就只寫 background-color。

鍵盤使用者也要看到同樣的回饋

修到這裡，滑鼠使用者已經看得到回饋，但不是每個人都有 hover：手機沒有滑鼠，鍵盤使用者也沒有。用 Tab 移到按鈕時，第 5 課的焦點框告訴使用者「焦點在這裡」；hover 的變色是額外的「這顆按鈕可以按」的回饋，同樣的回饋也要給鍵盤使用者。把兩個選擇器寫在一起最不會漏：

.btn:hover,
.btn:focus-visible {
  background: var(--brand-hover);
}

焦點框（outline）照樣保留，變色是加上去的，不是取代它。

💡 實務上：設計稿只畫靜態畫面，狀態要自己追問
設計師交來的通常是按鈕「平常的樣子」，hover、focus、按下、disabled、載入中常常沒畫，也沒寫要多快變過去。這次的「加入購物車」按鈕就是這樣才被寫成 all 1s。接到按鈕時先列出這幾個狀態問設計師，比做完再被退件省事。團隊有元件庫時，按鈕的 transition 只寫在 Button 元件裡一次，頁面上不要各自再補一條。做完用鍵盤按 Tab 走一遍，確認每個狀態鍵盤使用者也看得到。

現在按鈕的 transition 寫對了位置、只列背景色、鍵盤也有回饋。剩下回報裡最直接的那個數字：一秒。要改成多少，速度要怎麼變化？

多快才不會讓人以為當掉？時長與 easing

時長決定使用者要等多久才看到結果。微互動的時長大多在 100～300ms：小於 100ms 幾乎看不出過渡，跟瞬間跳過去差不多；超過 300ms，使用者會開始覺得介面反應慢。在這個範圍裡，變化越小用越短：按鈕變色這種小變化用約 120～150ms，卡片浮起、選單展開這種移動距離比較大的用約 200～300ms。原本的一秒是建議上限的三倍多，這就是「以為網站當掉」的來源。

時長只說了「總共花多久」，沒說「過程中怎麼分配」。同樣 200ms，可以等速前進，也可以一開始衝很快、最後慢慢停下。決定這件事的是緩動函式（easing）：它是一條曲線，把「過了多少時間」對應到「完成了多少進度」。

曲線越陡，那一段走得越快。照著圖看三種常用的曲線：

  • ease-out（先快後慢）：進場、回應使用者操作。一開始就動，使用者覺得反應很快，最後慢慢停穩。hover、展開選單、卡片浮起都用它。
  • ease-in（先慢後快）：離場。元素先停一下才加速離開，例如關閉提示訊息。進場用 ease-in 會覺得遲鈍，因為使用者操作後的前一段時間幾乎沒有變化。
  • linear：等速。適合一直重複的動畫（輪播、載入中的旋轉圖示），用在一般互動上會很生硬。

沒寫時用的是預設值 ease，中間快、頭尾慢。內建的曲線不夠用時，可以用 cubic-bezier(x1, y1, x2, y2) 自訂，DevTools 的 Styles 面板點 easing 旁的圖示可以拖曳調整。這條曲線的橫軸是時間進度、縱軸是動畫進度，固定從 (0, 0) 走到 (1, 1)；四個數字是中間兩個控制點的座標，第一個點 (x1, y1) 決定起步的陡度，第二個點 (x2, y2) 決定收尾怎麼靠近終點。內建的 ease-out 等於 cubic-bezier(0, 0, 0.58, 1)；下面範例的 cubic-bezier(0, 0, 0.2, 1) 把第二個控制點的 x 從 0.58 移到 0.2，曲線更早就貼近終點，所以收得比內建 ease-out 更快。

所以按鈕改成 transition: background-color 150ms ease-out：一滑上去就開始變，150ms 內變完。這兩個數字不該在每個元件裡各寫一次。跟顏色、間距一樣，時長與 easing 也整理成第 16 課的設計變數，全站才會一致：

:root {
  --duration-fast: 120ms;   /* 顏色、透明度 */
  --duration-base: 200ms;   /* 位移、展開 */
  --ease-out: cubic-bezier(0, 0, 0.2, 1);   /* 比內建 ease-out 收得更快 */
  --ease-in: cubic-bezier(0.4, 0, 1, 1);
}
.btn  { transition: background-color var(--duration-fast) var(--ease-out); }
.card { transition: transform var(--duration-base) var(--ease-out),
                    box-shadow var(--duration-base) var(--ease-out); }
💡 實務上：時長寫成變數，「動畫太慢」只要改一行
這次的客服回報如果是「整個網站感覺有點鈍」，而每個元件各寫各的 300ms、0.25s，就得全站搜尋一個個改；整理成 --duration-* 變數只要調一處。成熟的設計系統（例如 Material Design）也都會把動效時長與 easing 定義成 token，可以直接參考，不用自己從頭定。和設計師對齊時，用「快／一般」兩三個等級溝通，比討論每個動畫幾毫秒有效率。

第一則回報關掉了。上面的 .card 已經先寫出卡片的 transition，但它過渡的是 transform，而原本的菜單頁卡片動的是 margin-top。這個差別，就是第二則回報「捲動卡卡的」的原因。

第二則回報：捲動菜單為什麼卡卡的？

原本的卡片 hover 是這樣寫的：

.card {
  transition: all 1s;
}
.card:hover {
  margin-top: -4px;
  box-shadow: 0 8px 20px rgb(0 0 0 / 0.18);
}

時長的問題上一節處理過了，這裡要看的是被動的屬性：margin-top。在工程師的筆電上它很順，在手機上卻會卡。要知道為什麼，得先知道瀏覽器怎麼把 CSS 畫成畫面。

瀏覽器每一幀在做什麼

瀏覽器把 CSS 畫成畫面大致分四步（第 19 課會深入）：

  • Style：算出每個元素最後的樣式。
  • Layout（排版）：算出每個元素的位置和大小。一個元素變大或移動，後面的元素都要重新算位置。
  • Paint（繪製）：把文字、顏色、陰影畫成像素。
  • Composite（合成）：把已經畫好的幾個圖層疊在一起，變成螢幕上的畫面。

靜態頁面只要走一次。動畫不一樣：屬性每一幀都在變，所以每一幀都要從「被影響的那一步」開始重走。螢幕一秒更新 60 次時，每一幀只有約 16ms，這幾步加起來超過這個時間，那一幀就畫不出來，使用者看到的就是一頓一頓的「卡」。改不同的屬性，要重走的步驟不一樣：

改 top 或 margin-top，元素的位置變了，瀏覽器每一幀都要重新排版、重新繪製；頁面元素多、手機效能差時，就是客服回報的「卡卡的」。用 margin-top: -4px 做卡片浮起還有第二個問題：margin 會影響版面，下面的卡片會跟著往上移 4px，整欄都在抖。

transform：只改畫出來的樣子

要讓卡片往上浮、又不重新排版，就要用一個不影響版面的屬性。transform 就是這種屬性：它改變元素「畫出來的樣子」，可以位移（translate）、縮放（scale）、旋轉（rotate），但元素原本佔的位置不變，旁邊的元素不會被推開。

.card:hover {
  transform: translateY(-4px);   /* 往上 4px，負的是往上 */
}
.badge.bump {
  transform: scale(1.2);         /* 放大到 1.2 倍，以中心為準 */
}

因為版面沒變，瀏覽器可以跳過排版。動 transform、opacity 時，瀏覽器通常會把這個元素放在自己的圖層上，每一幀只要把畫好的圖層挪個位置再合成（composite），不必重畫。瀏覽器的 JavaScript、樣式計算與排版都在同一條主執行緒（main thread）上依序執行，JavaScript 跑很久時，這條線上的其他工作都要排隊等。合成則交給另一條合成執行緒（compositor thread）處理，不必排這個隊，所以 JavaScript 忙的時候，只動 transform、opacity 的動畫也不會停。上面那張圖的第三列就是這個情況。

所以卡片的修法是：位移改用 transform: translateY(-4px)，transition 只列 transform 和 box-shadow，用 ease-out、約 250ms。陰影屬於圖中的第二列，要重新繪製但不必排版，代價比 margin 低；只有卡片浮起的那一刻在變，可以接受。transform 也可以拆成 translate、scale、rotate 三個獨立屬性來寫，細節見課末的補充。

自己看差別：Chrome DevTools 的 Performance 面板按錄製，滑過卡片幾次後停止。動 margin 的版本，每一幀都看得到紫色的 Layout；動 transform 的版本幾乎只有綠色的 Paint／Composite。DevTools 的用法在第 18 課。

既然 transform 的好處來自「放在自己的圖層」，很自然會想到：能不能事先叫瀏覽器把卡片放上圖層，動起來更快？

要不要先用 will-change 叫瀏覽器準備？

will-change: transform 就是做這件事的屬性：它告訴瀏覽器「這個元素的 transform 等一下會變」，讓瀏覽器提前把元素放到獨立圖層。聽起來在每張卡片上都加一行很划算，但 MDN 的說法是：這是最後手段，用來處理已經存在的效能問題，不是用來預防。原因有三個：

  • 記憶體：每個獨立圖層都要額外的記憶體。寫在 * 或一長串卡片上，手機的記憶體會被吃掉，反而更慢。
  • 副作用：它跟 transform 一樣會建立 stacking context，也會變成 fixed 子元素的包含區塊：卡片裡 position: fixed 的元素不再以視窗定位，而是以這張卡片定位，例如彈出視窗只蓋住卡片（原因見第 10 課）。第 10 課的下拉選單被卡片蓋住，就是卡片常駐 will-change: transform 的副作用。
  • 多此一舉：正在跑的 transition、animation，瀏覽器本來就會處理，不需要另外宣告。

正確的順序是先量，再加：用 Performance 面板確認真的掉幀，再針對那一個元素加；能在動畫開始前加、結束後移除最好。菜單頁的卡片改成 transform 之後已經只剩合成，不需要 will-change。

💡 實務上：卡頓要在慢的裝置上才看得出來
工程師的筆電很快，用 margin 做的動畫在自己電腦上通常很順，等到客服轉來「手機卡卡的」才發現，這次的第二則回報就是這樣來的。上線前用 DevTools Performance 面板的 CPU 降速（模擬較慢的手機），或拿一支舊手機實際滑過菜單頁，比看程式碼可靠。PR 裡看到動畫在改 top、left、margin、width、height，先問能不能改成 transform。反過來，看到整個列表的卡片都加了 will-change，要問「有量過嗎」。

按鈕和卡片都修好了，它們有一個共同點：都是使用者先做了什麼（滑過、聚焦），某個屬性才改變，transition 才開始。第三則回報裡的輪播不一樣：首頁推薦一載入就自己在動；購物車徽章也有同樣的需求，要在「加入購物車」時自己彈一下。沒有狀態改變可以觸發時，transition 派不上用場。

沒有 hover 可觸發的動畫怎麼寫？@keyframes 與 animation

transition 有兩個限制：它只能從 A 變到 B，而且要有屬性改變才會開始。徽章「放大再縮回」需要三個時間點；輪播要一出現就開始、一直重複。這兩種都要用關鍵影格動畫（keyframes animation）：先用 @keyframes 定義每個時間點的樣子，再用 animation 把它套到元素上。元素一套上這條規則，動畫就開始播，不需要任何狀態改變。

/* 定義：名稱叫 bounce，0% 是開始、100% 是結束 */
@keyframes bounce {
  0%, 100% { transform: scale(1); }
  40%      { transform: scale(1.4); }
}

.badge {
  /*         名稱    時長    easing   */
  animation: bounce 600ms ease-out;
}

這樣寫，徽章出現在畫面上時就會彈一次。注意影格裡動的是 transform: scale()，上一節的原則在這裡一樣適用。animation 的簡寫還能設定播幾次、往哪個方向、開始前結束後要不要保留樣式，完整的屬性表和 animation-fill-mode 的常見坑放在課末的補充。

但「加入購物車時才彈」不是「出現時彈一次」。常見的做法是由 JavaScript 在加入購物車時替徽章加上一個 class（例如 .bump），讓 animation 規則生效；動畫播完時元素會觸發 animationend 事件，在這時把 class 移除，下次加上時才會再播一次。Vue 的 <Transition> 元件也是同樣的原理：在進場、離場的不同階段幫元素加上 v-enter-from、v-enter-active 這類 class，動畫本身還是你寫的 CSS transition 或 keyframes。

無限重複的動畫要能停下來

首頁「本月推薦」的輪播用 animation: slide 30s linear infinite 一直往左捲。infinite 表示無限重複，它不會自己停，所以寫下 infinite 的同時，就要想好怎麼讓它停。控制播放的是 animation-play-state：設成 paused 會停在目前位置，改回 running 時從那裡接著播。

最基本的暫停時機有兩個：滑鼠移到輪播上，以及鍵盤焦點進到輪播裡。後者要用 :focus-within，它是「自己或任何後代元素有焦點」時成立的偽類。使用者用 Tab 移到輪播裡的某個連結時，連結有焦點，包住它的 .carousel 就符合 :focus-within：

/* slide：把整條 .track 用 transform 往左平移一半 */
@keyframes slide {
  to { transform: translateX(-50%); }
}
.track { animation: slide 30s linear infinite; }

/* 滑鼠移入、鍵盤焦點在輪播裡時暫停 */
.carousel:hover .track,
.carousel:focus-within .track {
  animation-play-state: paused;
}

暫停要寫在「有 animation 的那個元素」上：動畫在 .track，就暫停 .track。寫成 .track a:focus { animation-play-state: paused } 沒有作用，因為連結本身沒有動畫，讓它暫停等於什麼都沒做。

這樣輪播在使用者想看、想操作時會停下來。但回頭讀第三則回報：「我看了頭暈」。這位使用者頭暈的時候，滑鼠根本不在輪播上；對他來說，輪播在畫面上動的每一秒都是問題。要照顧他，得先知道「他是會頭暈的人」，CSS 有辦法知道這件事。

第三則回報：怎麼知道使用者會頭暈？prefers-reduced-motion

對動態敏感的人通常不會等網站來照顧他，而是直接在作業系統裡設定。iOS、Android、macOS、Windows 都有「減少動態效果」之類的設定，例如 iOS 在「設定 → 輔助使用 → 動態效果 → 減少動態效果」，Windows 11 在「設定 → 協助工具 → 視覺效果 → 動畫效果」。作業系統的動畫會因此變少，但網頁裡的動畫是你寫的，作業系統管不到。

瀏覽器會把這個設定轉給網頁：CSS 的媒體特性 prefers-reduced-motion 在使用者打開設定時是 reduce，沒打開時是 no-preference。媒體特性的用法跟 RWD 的寬度條件一樣，放進 @media：

@media (prefers-reduced-motion: reduce) {
  /* 使用者要求減少動態時才套用 */
}
@media (prefers-reduced-motion: no-preference) {
  /* 使用者沒有要求時才套用 */
}

會開這個設定的人，常是看到大範圍移動就頭暈、噁心的人，也有人只是覺得動畫分心。不用改作業系統也能測：DevTools 的 Rendering 面板可以模擬這個設定（第 18 課）。

拿掉什麼、留下什麼

知道使用者要求減少動態之後，最直覺的反應是全部拿掉。但「減少」動態不是「沒有回饋」：使用者還是需要知道按鈕被按了、焦點在哪裡、購物車有幾件。判斷原則是看這個變化會不會讓東西移動：

拿掉或換掉保留
位移、縮放、旋轉（卡片浮起、徽章彈跳）顏色變化（hover 變色）
自動播放、無限重複的動畫（輪播、跑馬燈）透明度的淡入淡出
視差捲動、平滑捲動（scroll-behavior: smooth）焦點框、狀態文字、徽章上的數字

無障礙規範 WCAG 2.3.3「互動引起的動畫」（AAA）的說法相同：只改顏色或透明度、不改變元素大小、形狀、位置的變化，不算「動態」。所以徽章可以從彈跳改成淡入：數字的變化還是看得到，但它不會晃。套到菜單頁上：

@media (prefers-reduced-motion: reduce) {
  .card:hover { transform: none; }      /* 不浮起，陰影還在 */
  .badge { animation: fade 200ms ease-out; }  /* 彈跳換成淡入 */
  .track { animation: none; }           /* 輪播不自動播放，使用者自己左右捲 */
}
@keyframes fade { from { opacity: 0; } }

卡片這一行容易寫錯。只把卡片的 transition 拿掉不夠：hover 時 transform 還是 translateY(-4px)，卡片只是從「滑上去」變成「瞬間跳上去」，位置照樣在變。對動態敏感的人在意的是位置在變，不是變得快或慢，所以要拿掉的是 transform 本身。

平滑捲動也要包起來

菜單頁頂端的「看菜單」連結還有一種容易漏掉的動態。html { scroll-behavior: smooth } 讓點錨點連結（href="#menu"）時頁面滑過去，而不是直接跳過去。整頁快速滑動正是最容易讓人頭暈的動作，所以只在沒要求減少動態時開啟：

@media (prefers-reduced-motion: no-preference) {
  html { scroll-behavior: smooth; }
}

這是另一種寫法：先寫「沒有動態」的版本，再用 no-preference 把動態加上去。兩種寫法各有適合的場合：新寫的元件適合這樣做，忘了處理時預設就是安全的；既有的大量 CSS，則在最後加一個 reduce 區塊逐一關掉，像上面菜單頁那樣。

還有一種動畫 media query 管不到：JavaScript 做的動畫，例如用 Web Animations API 或動畫函式庫。它們讀不到 CSS 的 media query，要自己用 matchMedia('(prefers-reduced-motion: reduce)').matches 判斷，決定要不要播。

不要一刀切。網路上常見這樣的寫法：在 reduce 裡寫 * { animation: none !important; transition: none !important; }，或把所有時長改成 0.01ms。前者連顏色、透明度的回饋也一起拿掉；後者動畫只是一瞬間跑完，卡片照樣跳上去、徽章照樣放大，該拿掉的位移其實還在。逐一決定每個動畫要拿掉還是換成淡入。

開了減少動態的人，現在看到的是不會自動播放的輪播。但不是每個被輪播干擾的人都知道有這個設定，或願意為一個網站去改作業系統。他們也需要一個在網頁上就按得到的停止方法。

沒開減少動態的人，怎麼讓輪播停下來？

這一點 WCAG 有明確的要求。WCAG 2.2.2「暫停、停止、隱藏」屬於 A 級，也就是最基本的一級：自動開始、持續超過 5 秒、跟其他內容一起出現的移動、閃爍或捲動內容，要提供使用者暫停、停止或隱藏它的方法。自動輪播、跑馬燈、背景影片都適用。

要求的理由除了頭暈，還有注意力：有閱讀障礙或注意力不足的人，旁邊有東西一直動就讀不下去；使用螢幕放大鏡的人一次只看得到一小塊畫面，內容一直跑就追不上。

前面寫的 :hover、:focus-within 暫停是好的輔助，但不能當成唯一的方法：

  • 只有 :hover：鍵盤與觸控使用者停不下來。
  • 只有聚焦時暫停：W3C 的說明文件指出，只在元素有焦點時才停下來的做法不算數，因為使用者要一直把焦點留在那裡，就沒辦法操作頁面的其他地方。

所以要有一個看得到、鍵盤操作得到的暫停控制，按了之後一直保持暫停。用 JavaScript 做一顆按鈕可以；不用 JavaScript 時，可以用原生 checkbox 記住「暫停中」這個狀態，再用第 12 課的 :has()，在 checkbox 勾選時讓輪播停下：

<input type="checkbox" id="pause">
<label for="pause">暫停自動輪播</label>

.featured:has(#pause:checked) .track {
  animation-play-state: paused;
}

這個 checkbox 必須讓所有人都看得到、操作得到，常見的錯誤是為了美觀把它藏起來：

  • display: none 或 visibility: hidden：元素不能聚焦，鍵盤使用者按 Tab 會直接跳過它。
  • opacity: 0：還能聚焦，但使用者看不到焦點在哪裡，也看不出有沒有勾選。

最簡單可靠的做法是直接顯示原生 checkbox。要配合品牌色，用 accent-color 屬性，它設定 checkbox、radio 這類原生控制項的強調色，例如 #pause { accent-color: #6b3e26; }，不必自己畫一個假的。

💡 實務上：行銷要首頁輪播時，先問「真的需要自動播嗎」
首頁輪播是行銷最常提的需求之一，但它會自動換走使用者正在看的內容，後面幾張的活動也不一定有人看到。資深的做法是先提替代方案：一張固定主視覺，或使用者自己左右滑的推薦清單，就沒有暫停的問題，第三則回報也不會發生。真的要自動播放，把「有看得到的暫停按鈕、鍵盤操作得到、開啟減少動態時不自動播」寫進驗收條件，QA 和 PM 才會一起檢查。接政府或大型企業的案子時，驗收常包含無障礙檢測，這幾項沒做會被退回。

三則回報到這裡都關掉了：按鈕只過渡背景色、150ms、鍵盤也有回饋；卡片改用 transform 浮起；徽章與輪播在減少動態時改成淡入、不自動播，所有人都有一個按得到的暫停控制。下面的練習會把這三件事各做一次。

補充與查表

主線用不到、但查資料或讀別人程式碼時會遇到的細節。

animation 簡寫的其他屬性（查表用，不用背）

主線只用到名稱、時長、easing。animation 的簡寫還可以帶這些屬性：

屬性用途例子
animation-iteration-count播幾次3、infinite（無限重複）
animation-direction播放方向alternate：去程、回程交替
animation-fill-mode動畫開始前、結束後要不要保留影格的樣式forwards：結束後停在最後一格；backwards：延遲期間就先套用第一格；both：兩者
animation-play-state播放或暫停running、paused（停在目前位置，恢復時接著播）
animation-delay延遲多久開始200ms

animation-fill-mode 最常見的坑：淡入動畫從 opacity: 0 到 1，元素本身沒有寫 opacity，又有 animation-delay。延遲期間元素先以完全不透明出現，動畫一開始突然變透明再淡入，畫面閃一下。加 backwards（或 both）讓延遲期間就套用 0% 的樣式。

獨立的 translate、scale、rotate 屬性

主線用的是 transform: translateY(-4px)。位移、縮放、旋轉也可以分開寫成三個獨立屬性：

/* 也可以分開寫成三個獨立屬性，互不覆蓋 */
.card:hover { translate: 0 -4px; }

獨立的 translate、scale、rotate 屬性在 2025 年 2 月成為 Baseline widely available。好處是不會互相覆蓋：transform: translateY(-4px) 寫在 hover、transform: scale(1.2) 寫在另一個狀態時，後面那條會整個蓋掉前面的；分開寫就各管各的。

prefers-reduced-motion 的支援度

prefers-reduced-motion 是 Baseline widely available 的功能，可以直接使用。

新功能一覽：知道有這些就好

下面幾個功能還比較新，這裡只說它們解決什麼問題，實際使用前照第 12 課的方法查 Baseline 狀態（以下依 web-features 3.44.0）。

  • @starting-style 與 transition-behavior: allow-discrete（2024 年 8 月 Baseline newly available）：transition 有兩個限制，元素第一次出現時沒有「之前的樣式」可以過渡，display 也不能內插（只有 none 或 block，沒有中間值），所以從 display: none 出現的彈出視窗沒辦法淡入。@starting-style 提供「出現前」的樣式，allow-discrete 讓 display 也參與過渡：出現時一開始就切成 block，消失時等淡出結束才變成 none，popover 與 <dialog> 就能只用 CSS 淡入淡出。
  • View Transitions（同一份文件內）（2025 年 10 月 Baseline newly available）：JavaScript 呼叫 document.startViewTransition() 更新畫面，瀏覽器自動在新舊畫面之間做過渡，例如清單切換排序、從列表進入詳細頁。
  • 捲動驅動動畫（scroll-driven animations）：讓動畫進度跟著捲動位置走，例如閱讀進度條。還不是 Baseline，有些瀏覽器不支援，要用 @supports 確認不支援時頁面仍然正常。

不管用哪一種，主線的原則都一樣：只動 transform 與 opacity、時間短、在 reduce 時拿掉位移。

練習

練習 1：幫菜單的按鈕與卡片加上微互動，修好起始 CSS 的問題：(1) 按鈕在 hover 與鍵盤聚焦（:focus-visible）時，背景色立刻開始、在 100～300ms 內過渡到 var(--brand-hover)；(2) 卡片 hover 時往上浮 4px 並加上陰影，用 ease-out，時間約 250ms；(3) 只過渡實際會改變的屬性，不用 all；位移要用 transform，不能推動另一張卡片。測試會在 320px 與 768px 量卡片的位置。

練習 2：首頁有四種動態：點「看菜單」時平滑捲動、購物車徽章彈跳（@keyframes）、本月推薦自動輪播（無限重複的 animation）、卡片 hover 浮起；按鈕 hover 會變色。加上 prefers-reduced-motion 支援：使用者要求減少動態時，拿掉平滑捲動、位移、縮放與自動輪播，徽章與輪播的內容要留著，按鈕的顏色過渡也要保留；沒有要求時，所有動態維持原樣。

練習 3：「本月推薦」的輪播會一直自動捲動，起始 CSS 只在滑鼠移入時暫停，而且把暫停用的 checkbox 用 display: none 藏起來了。依 WCAG 2.2.2 修好它（HTML 不能改）：(1) 鍵盤焦點在輪播裡、或滑鼠移入時暫停，離開後繼續播放；(2) 讓原生 checkbox 看得到、按 Tab 到得了，勾選後輪播停下來（內容留在畫面上），取消勾選後繼續；(3) 使用者要求減少動態時，一開始就不自動播放。

練習 4：卡片 hover 時往上浮，為什麼建議用 transform: translateY(-4px)，而不是 position: relative; top: -4px？

✓ b：改 top 會改變元素的位置，瀏覽器每一幀都要重新計算版面並重新繪製；transform 只改變畫出來的樣子，瀏覽器可以把元素放在獨立圖層上，每一幀只要合成，而且可以不佔用主執行緒。a 新舊不是理由。c top 可以過渡，只是代價高。d 兩者都是所有瀏覽器支援很久的功能。

練習 5：使用者開了「減少動態效果」（prefers-reduced-motion: reduce），網站正確的做法是？

✓ b：會讓人不舒服的是移動與縮放；顏色、透明度的變化不改變元素的位置與大小，而且使用者仍然需要知道按鈕被按下、狀態改變了。a 連必要的回饋也一起拿掉。c 動畫還是在動，自動播放還是停不下來。d 對有前庭障礙的人來說，大範圍的動態會造成頭暈、噁心，不是喜好問題。

練習 6：同事在按鈕上寫了 transition: all 0.3s，hover 只改背景色。下面哪一個是這樣寫的實際問題？

✓ c：all 代表所有可以過渡的屬性。現在只有背景色在變，看不出問題；之後 RWD 改 padding、主題切換改顏色、JavaScript 改 width，都會被慢慢過渡，造成意外的動畫，padding、width 還要每一幀重新排版。明確列出 background-color 才能避免。a、d 都不對，語法合法也能用在任何元素。b 剛好相反，all 包括 transform。

常見錯誤

  • transition: all：任何屬性改變都會被過渡，造成意外的動畫，也藏住了會重新排版的屬性。只列出真的會變的屬性。
  • transition 寫在 :hover 裡：只有進入 hover 時有過渡，移開時瞬間跳回。寫在元素平常的狀態。
  • 用 top、margin、width 做位移動畫：每一幀都要重新排版，還會推動旁邊的元素。位移用 transform（或 translate 屬性）。
  • 只做 :hover：鍵盤與觸控使用者沒有回饋。跟 :focus-visible 寫在同一個選擇器。
  • 動畫太長：一秒的按鈕變色讓人以為網站沒反應。微互動用 100～300ms。
  • 全域 will-change：每個元素都佔一個圖層，吃掉大量記憶體，還會建立 stacking context。先量，再針對單一元素加。
  • 減少動態一刀切：* { transition: none !important } 連顏色回饋都拿掉；改成 0.01ms 則位移仍然會發生。逐一決定每個動畫。
  • 減少動態時把內容藏起來：徽章的數字、輪播的商品是資訊。拿掉的是動作，不是內容。
  • 平滑捲動沒有包進 no-preference：整頁快速滑動是最容易讓人頭暈的動作之一。
  • 自動輪播只有 hover 暫停：不符合 WCAG 2.2.2。提供看得到、鍵盤操作得到、會一直保持的暫停控制。
  • 暫停寫在沒有動畫的元素上：animation-play-state 要設在有 animation 的那個元素。

小結

  • 動畫要說得出目的：回饋、關聯或注意。說不出目的的是裝飾，有效能、注意力與身體不適三種代價。
  • 第一則回報（按鈕等一秒）：transition 寫在元素平常的狀態，明確列出會變的屬性，不用 all；hover 與 :focus-visible 一起處理。微互動 100～300ms；進場用 ease-out、離場用 ease-in、重複的動畫用 linear；時長與 easing 整理成設計變數。
  • 第二則回報（捲動卡卡）：位移、縮放用 transform，透明度用 opacity，通常只需要合成；top、margin、width 每一幀都要重新排版，還會推動旁邊的元素。will-change 是量過之後針對單一元素的最後手段。
  • 沒有狀態改變可觸發的動畫用 @keyframes 與 animation；infinite 的動畫一定要能用 animation-play-state: paused 停下來，暫停寫在有動畫的那個元素上。
  • 第三則回報（看了頭暈）：prefers-reduced-motion: reduce 時拿掉位移、縮放、自動播放與平滑捲動，保留顏色、透明度與內容；自動播放超過 5 秒的內容要有看得到、鍵盤操作得到、會一直保持的暫停控制（WCAG 2.2.2）。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：菜單卡片想在空間夠寬時改成左右排，下面的 CSS 放進主欄與側欄，兩邊都完全沒變化。問題在哪？

.card {
  container-type: inline-size;
  display: grid;
  gap: 12px;
}
@container (min-width: 28rem) {
  .card { grid-template-columns: 8rem 1fr; }
}

✓ @container 裡的 .card 規則問的是 .card 的祖先容器；這裡沒有祖先容器，條件永遠不成立。把 container-type: inline-size 移到包住卡片的欄位，主欄、側欄各自當容器。a 錯在沒寫名字時就查最近的祖先容器，名字只在容器一層包一層時才需要。（第 12 課）

練習 8：首頁標題寫 font-size: clamp(28px, 4vw, 48px)，無障礙檢測仍回報「使用者調大預設字級時標題不會變大」。為什麼？

✓ px 與 vw 都跟根字級無關，使用者把預設字級從 16px 調到 32px，這三個值一個都沒動。偏好值寫成一條直線：截距用 rem、斜率用 vw，上下限也用 rem，例如 clamp(1.75rem, 1.3333rem + 2.0833vw, 3rem)。b 錯在 clamp 本身沒問題，問題是裡面的單位。（第 13 課）

練習 9：菜單在桌機是三欄卡片，每張約 400px 寬，Network 卻顯示每張都下載了 1600w 的圖。<img> 寫了 srcset="… 400w, … 800w, … 1600w" sizes="100vw"，該改哪裡？

✓ 瀏覽器在 CSS 套用前就要選圖，只能照 sizes 算；100vw 在 1440px 寬、DPR 2 的螢幕等於要 2880px 的圖，就挑了 1600w。sizes 要描述真實的版面寬度，改完用 $0.currentSrc 確認。a 錯在手機上卡片是全寬，DPR 3 需要約 1100px，拿掉大圖手機就糊了。（第 14 課）

練習 10：首頁主視覺用 .hero { background-image: url(hero.avif) }，圖檔已經壓到 120 KB，LCP 還是比同事用 <img> 做的版本慢很多。最可能的原因是？

✓ <img> 在 HTML 解析時就被預先載入掃描器找到並開始下載；CSS 背景圖要等 CSS 下載、算出哪個元素套用了這條規則才被發現，起跑晚了一大段。重要圖片改成 <img> 加 object-fit 與 fetchpriority="high"。c 錯在尺寸預留影響的是 CLS，LCP 慢是因為太晚開始下載。（第 14 課）

練習 11：設計師要全站的內文和標題都換成品牌繁中字型，一個字重 4 MB。你會怎麼提？

✓ 一頁只用到幾百個字，下載整套幾 MB 的字型讓首屏變慢；內文用系統字型不必下載，品牌字型縮到標題用得到的字，下載量從 MB 降到 KB。a 錯在 WOFF2 已經是壓縮過的格式，仍有幾 MB，preload 它反而搶走 LCP 圖片的頻寬。b 讓網路慢時文字最多消失 3 秒。（第 15 課）

練習 12：系統是深色，使用者在網站選了淺色（<html data-theme="light">），頁面卻還是深色。CSS 如下，問題在哪？

[data-theme="light"] {
  --bg: #fff; --text: #2b1d14;
}
@media (prefers-color-scheme: dark) {
  :root { --bg: #1c140f; --text: #f3e9df; }
}

✓ 兩條規則選中同一個 <html>、權重相同，看前後順序，後面的深色值勝出。修法是深色規則寫成 :root:not([data-theme="light"])，或把手動選擇寫成 :root[data-theme="…"] 拉到 (0,2,0)，四種組合都要測。c 錯在 script 太晚只會先閃一下另一個主題，不會一直停在深色。（第 16 課）

練習 13：購物車抽屜打開時用 transition: width 300ms 從 0 長到 320px，桌機很順，中低階手機上卻一格一格地跳。比較好的修法是？

✓ width 改變會影響版面，瀏覽器每一幀都要重新排版、重新繪製，慢的裝置跟不上；transform 只改畫出來的樣子，通常只需要合成。a 錯在圖層解決不了排版，width 每一幀還是在變；will-change 是量過之後針對單一元素的最後手段。（第 17 課）

練習 14：卡片 hover 會往上浮。下面是為「減少動態效果」加的處理，開了這個設定的使用者會看到什麼？

.card { transition: transform 200ms ease-out; }
.card:hover { transform: translateY(-4px); }
@media (prefers-reduced-motion: reduce) {
  .card { transition: none; }
}

✓ 拿掉的只是過渡，hover 時 transform 還是 translateY(-4px)，從「滑上去」變成「瞬間跳上去」。在 reduce 區塊裡把 .card:hover 的 transform 設成 none，顏色、透明度這類回饋留著。a 錯在把「沒有過渡」當成「沒有動態」，對動態敏感的人在意的是位置在變。（第 17 課）
