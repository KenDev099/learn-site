階段 2：CSS 與版面基本功 · 第 10 課

定位與堆疊：position、sticky、stacking context 與 z-index

咖啡店網站上線後，菜單頁收到兩張回報單：「購物車的下拉選單被商品卡片蓋住」「菜單分類標題本來會黏在頁首下面，改版後不黏了」。同一週，設計師還要在新品照片的右上角加一個「新品」徽章。前一位工程師已經把下拉選單改成 z-index: 9999，沒用；又試了 99999，還是沒用。

這三件事都發生在同一個菜單頁，背後是 CSS 的兩個問題：元素「以誰為準」決定自己的位置，以及瀏覽器怎麼決定「誰疊在誰上面」。猜數字解決不了，因為數字根本不是問題所在。這課從徽章開始，一路修到兩張回報單，最後替全站訂一套不會再失控的層級規則。

這課的路線：
  1. 元素要以誰為準移動？position 的五個值各自以什麼為參考、還佔不佔原本的位置；節末先給兩張回報單的簡短答案。
  2. 新品徽章怎麼疊在照片角落、又不推動標題？absolute 的固定寫法、參考點找錯時會發生什麼事，以及為什麼不拿 absolute 排整頁。
  3. 分類標題為什麼不黏？sticky 黏住的三個條件，以及黏住之後頁首擋住錨點與鍵盤焦點的問題。
  4. 下拉選單寫了 9999，為什麼還被卡片蓋住？瀏覽器的疊放順序與 stacking context。
  5. 全站的層級怎麼排，才不會又變成比數字大？z-index 刻度、isolation 與 top layer。
這課會用到：
  • 第 7 課的正常流與 overflow：沒有定位時元素由上往下、由左往右自動排；overflow: hidden 裁掉溢出、但仍可以用程式捲動，overflow: clip 只裁切、不能捲動。

元素要以誰為準移動？position 的五個值

到目前為止，菜單頁上的每個元素都在正常流（normal flow）裡：瀏覽器由上往下、由左往右把它們一個接一個排好，誰變高，後面的就往下推。這對大部分內容是對的，但這週的三件事都需要「不照正常流」：徽章要蓋在照片上，而不是排在照片下面；頁首和分類標題要在捲動時停在畫面上方；下拉選單要浮在商品卡片之上。position 就是用來把元素從自動排好的位置挪開的屬性。

挪去哪裡，由 top、right、bottom、left 四個偏移屬性（inset properties）指定。top: 8px 的意思是「上緣離參考矩形的上緣 8px」。問題是：參考矩形是誰？

這個參考矩形叫做包含區塊（containing block）。元素計算位置和百分比尺寸時都以它為準：top: 8px 是離包含區塊上緣 8px，width: 50% 是包含區塊寬度的一半。一般元素的包含區塊就是父元素的內容區，所以你平常不會注意到它。但 position 的不同值會換掉包含區塊，這正是「徽章跑到整頁右上角」這類問題的根源。

第二個要先知道的詞是脫離正常流（out of flow）。脫離正常流的元素不再佔用版面空間，其他元素排版時把它當成不存在，後面的內容會往上補位。徽章需要這個性質：它疊在照片上，不該把標題往下推。

有了這兩個詞，五個值的差別就是兩個問題的答案：以誰為準（包含區塊是誰）、原本的空間還佔不佔。

position偏移的參考（包含區塊）原本的空間菜單頁上的用途
static（預設）不能偏移，top 等屬性無效；z-index 也無效（flex、grid 的子項目例外，第 4 節會講）佔著一般內容
relative自己原本的位置還佔著，偏移只是畫的位置變了當 absolute 子元素的參考；微調幾 px
absolute最近的已定位祖先（position 不是 static 的祖先）的 padding 區；都沒有就是初始包含區塊（第一屏的大小）脫離正常流徽章、圖片上的標籤、下拉選單
fixed視窗（viewport），捲動時不動脫離正常流toast 通知、回到頂端按鈕

表裡的 toast 是畫面上方或角落短暫出現的提示，例如「已加入購物車」。它要在使用者捲到哪裡都看得到，所以用 fixed 以視窗為準。表中「已定位」的意思是 position 不是 static；後面說「定位元素」也是指這種元素。

用這張表先回答開頭的兩張回報單。分類標題不黏，最常見的原因是某個祖先寫了 overflow: hidden：sticky 要黏在「捲動容器」上，而 overflow 是 hidden、auto 或 scroll 的祖先會被當成捲動容器，即使它根本沒在捲，sticky 就改以它為準，看起來像沒寫。下拉選單蓋不過，是因為 z-index 只在同一個範圍裡比大小（這個範圍叫 stacking context），選單所在的頁首整層排在商品卡片下面，選單自己寫多大都出不去。這兩個答案分別在第 3 節和第 4 節講透。

在那之前，先處理最單純的一件事：徽章。它只用到表裡的 relative 和 absolute，卻足以讓你看清「包含區塊找錯了」長什麼樣子。

新品徽章怎麼疊在照片角落、又不推動標題？

回到上一節的表，徽章有兩個需求。第一，它不能把標題往下推，所以要脫離正常流，這是 absolute。第二，它要跟著照片走，照片在哪、多寬，徽章都在照片右上角，所以它的包含區塊必須是照片。absolute 的包含區塊是「最近的已定位祖先」，所以要讓照片變成已定位的元素。寫法是固定的兩步：

.photo {
  position: relative;   /* ① 只為了成為參考點，自己不偏移、不影響版面 */
}
.badge {
  position: absolute;   /* ② 脫離正常流，以 .photo 的 padding 區為準 */
  top: 8px;
  right: 8px;
}

第 ① 步的 position: relative 沒寫任何偏移，所以照片本身完全不動、仍佔著原本的空間。它唯一的作用是讓照片變成「已定位祖先」，讓徽章找得到它。這是 relative 最常見的用法。

少了第 ① 步會怎樣？徽章會往上一路找已定位的祖先，找不到就以初始包含區塊為準，跑到整頁的右上角。要確認徽章找到的參考點是誰，可以在 DevTools 的 Elements 面板選取徽章，再到 Console 輸入 $0.offsetParent。$0 代表 Elements 面板目前選取的元素，offsetParent 會回傳它找到的參考祖先。結果是 body 時，通常就是忘了給參考點。

有兩種「看起來也能把徽章放到角落」的寫法，都不對。第一種是 relative 加偏移，例如 position: relative; top: -30px：元素畫的位置動了，原本的空間卻還佔著，下面的內容不會補位，有徽章的卡片標題就比較低。第二種是負 margin：它會真的推動旁邊的元素。這兩種寫法都會讓「有徽章的卡片」跟「沒有徽章的卡片」排得不一樣，只有 absolute 能讓徽章完全不影響版面。

反過來，absolute 也不能用過頭。它只適合「疊在某個東西上面、大小已知的小元件」。拿它排整頁版面，例如三張卡片各寫 left: 0、280px、560px，在設計稿的寬度下看起來對；但標題變兩行、換成手機寬度、使用者放大字級時，因為它們不佔空間，彼此和後面的內容都會疊在一起。排版交給第 9 課的 Grid 與第 8 課的 Flexbox，absolute 只負責點綴。

徽章的位置到這裡就定了，但同一張卡片還藏著一個會讓包含區塊「換人」的設定，之後做彈出視窗時一定會撞到。菜單卡片為了 hover 時浮起來，寫了 transform: translateY(-4px)，並且預先宣告 will-change: transform。transform 用來位移、縮放、旋轉元素，第 17 課會詳談；will-change: transform 是事先告訴瀏覽器「這個屬性等一下會變動」，讓動畫順暢。第 4 節修下拉選單時還會再遇到這行。

現在假設產品要在每張卡片上加「加入購物車」按鈕，按下後跳出彈出視窗，讓使用者選甜度冰塊。元件最直覺的寫法，是把彈出視窗的 HTML 直接放在這張卡片裡面，再寫 position: fixed; inset: 0。inset 是 top、right、bottom、left 四個偏移屬性的縮寫，inset: 0 等於上下左右都是 0，讓元素蓋滿它的包含區塊；寫法細節見課末〈補充與查表〉。照上一節的表，fixed 以視窗為準，所以這個彈出視窗應該蓋滿整個畫面。

實際上它只會蓋住那張卡片。原因是包含區塊除了「最近的已定位祖先」，還有一個不寫 position 也會出現的來源：祖先身上有 transform、will-change: transform 這類屬性時，這個祖先會直接接手當包含區塊，連 fixed 都改以它為準。替圖片加模糊、灰階等濾鏡的 filter 也有同樣效果。完整的條件如下：

fixed 不一定以視窗為準。祖先只要有 transform、filter、perspective、contain: paint（或 layout），或 will-change: transform，這個祖先就變成 fixed 與 absolute 子元素的包含區塊（MDN「Containing block」）。最常見的事故：彈出視窗（modal）寫在一張有 hover 動畫的卡片裡，position: fixed; inset: 0 只蓋住了那張卡片。Vue 3 用 <Teleport to="body"> 把彈出視窗的 DOM 搬到 body 底下，就是為了避開這種祖先；原生的 <dialog> 則用第 5 節講的 top layer 解決。前面的 $0.offsetParent 在 Chrome 也會把這類 transform 祖先算進去，所以一樣可以拿來查。

徽章到此完成。接下來是第一張回報單：分類標題也是定位元素，但它用的是 sticky，而 sticky 的參考點比 absolute 多一層。

分類標題為什麼不黏？sticky 的三個條件

上一節的 absolute 只有一個參考點：包含區塊。黏性定位（sticky）同時跟兩個邊界有關。捲動到門檻之前，它像 relative 一樣待在原位、佔著空間；捲過門檻後，它黏在捲動容器的那條線上，看起來像 fixed；但它不會離開自己的父元素，父元素整個捲走時它也跟著走。菜單頁的分類標題就是這樣：「咖啡」黏在頁首下面，捲到「茶飲」時，「咖啡」被它所在的 section 帶走，換「茶飲」黏上。

所以 sticky 有兩個邊界：「黏在哪條線」由捲動容器決定，也就是往上找到的第一個會捲動的祖先，通常是整個視窗；「能移動的範圍」由父元素決定。下圖把兩個邊界畫在一起：

圖右的三個條件，就是 sticky 沒反應時要依序檢查的三件事。每一件都對應到菜單頁可能出錯的地方：

  1. 沒有寫門檻。position: sticky 本身不會黏，要寫 top（或 bottom、left、right）至少一個；同一軸兩個都是 auto 時，表現就跟 relative 一樣。門檻也要算對：頁首 64px 高時，下面的分類標題寫 top: 64px，寫 0 會鑽到頁首底下。
  2. 祖先有 overflow 不是 visible。sticky 黏在「最近一個有捲動機制的祖先」上：只要祖先的 overflow 是 hidden、auto、scroll，那個祖先就是它的捲動容器，即使那個祖先根本沒有在捲（MDN「position」）。頁面捲動時這個祖先整個跟著走，sticky 就像沒寫。這就是第一張回報單最常見的原因。來源通常是為了藏橫向捲軸寫的 overflow-x: hidden：只寫一個方向時，另一個方向的 visible 會被算成 auto，一樣是捲動容器。只想裁切就改用 overflow-x: clip，它不會建立捲動容器（第 7 課）。
  3. 父元素跟它一樣高。sticky 只在父元素裡面移動，父元素沒有多出來的高度，它就沒有地方可以黏。Vue 元件常把頁首包在一層 <div> 裡，這層 div 剛好跟頁首一樣高；把 sticky 改寫在外層（或拿掉這層）才行。Flex、Grid 裡的側欄也一樣：項目預設被拉伸成跟整列一樣高，要加 align-self: start 讓它恢復內容高度。

標題黏住之後，會冒出一個新問題：黏住的頁首會一直蓋著畫面上方 64px。使用者點目錄裡「茶飲」的錨點連結、或用 Tab 聚焦到頁面中段的連結時，瀏覽器預設把目標捲到視窗最上緣，剛好被頁首擋住。對看得到畫面的人是不方便，對靠鍵盤操作的人則是看不到焦點在哪裡。無障礙規範 WCAG 的 2.4.11 條就是要求鍵盤焦點不能被這類內容完全遮住。第 5 課教過的修法是在捲動容器上寫 scroll-padding-top，告訴瀏覽器「捲動定位時，上方有一段被擋住」：

html {
  scroll-padding-top: 64px;   /* 上方被頁首擋住 64px，捲動定位時扣掉 */
}

只想針對某些目標調整時，用目標自己的 scroll-margin-top。不要用 margin-top 把內容推開：它只讓版面多一段空白，錨點跳轉時目標還是停在最上緣。sticky 各大瀏覽器都支援，不需要 JavaScript 監聽捲動來模擬；支援時間見課末〈補充與查表〉。

💡 實務上：後台長表格的標題列最常要 sticky，也最常失效
咖啡店後台的訂單列表有幾百筆，營運人員捲到下面就看不到「金額」「狀態」是哪一欄，所以 thead th 要 sticky。最常見的坑就是本節的第 2 個條件：為了手機能橫向捲動，表格外面包了 overflow-x: auto 的容器，標題列就改成黏在這個容器上，跟著整頁捲走，看起來像沒黏。這時要嘛讓容器有固定高度、在容器裡捲，要嘛接受手機上不黏，先跟 PM 確認哪個比較重要。另外手機橫放時畫面只剩一點高度，頁首、分類標題、表格標題全部 sticky 會把內容擠到看不見，資深會在矮螢幕和放大字級下實際捲一次，再決定哪些真的需要黏。

第一張回報單修好了：分類標題黏在頁首下面，錨點也不會被擋住。但頁首現在是 sticky，而購物車的下拉選單就在頁首裡。第二張回報單的答案，要從「瀏覽器怎麼決定誰畫在上面」說起。

下拉選單寫了 9999，為什麼還被卡片蓋住？

上一節讓頁首黏在畫面上方，但黏住的頁首會跟捲上來的商品卡片重疊。元素重疊時，誰在上面不是看 z-index 的數字大小那麼簡單。瀏覽器是依一套固定的順序一層一層畫，後畫的蓋住先畫的。在同一個範圍裡，由下往上大致是：

  1. 這個範圍本身的背景與邊框
  2. z-index 為負數的定位元素
  3. 一般（沒有定位）的區塊元素，依 DOM 順序
  4. float 與行內內容
  5. z-index 是 auto 或 0 的定位元素（以及 transform、opacity 等建立了新範圍的元素），依 DOM 順序
  6. z-index 為正數的定位元素，數字小的先畫

從這個順序可以讀出兩條日常規則：「定位元素蓋過一般元素」，以及「同樣沒寫 z-index 時，DOM 後面的蓋前面的」。也可以讀出 z-index 的適用範圍：它只對定位元素（position 不是 static）和 flex、grid 的子項目有效，寫在 static 元素上沒有作用。

這個順序裡一直出現「範圍」兩個字，它就是第 1 節預告過的堆疊上下文（stacking context）：一組元素共用的 z 軸排序範圍。可以把它想成圖層資料夾。資料夾裡的元素先在資料夾內依上面的順序排好，然後整個資料夾壓成一張圖層，拿到上一層去跟別的圖層比。子元素的 z-index 再大，也只是在自己的資料夾裡排第一，出不了資料夾。整份文件的根（html）是最外層的 stacking context。

所以要回答「為什麼蓋不過」，關鍵是知道哪些元素會自己開一個新的資料夾。下表是 MDN「Stacking context」裡常見的條件，查表用，不用背；重點是認得出「原來這個屬性也會」：

條件常見的來源
position: relative／absolute 加上 z-index 不是 auto手動調層級
position: fixed／sticky（不管 z-index）頁首、toast
flex、grid 的子項目設了 z-index不寫 position 也成立
opacity 小於 1淡入動畫、停用狀態
transform、translate、scale、rotate、filter、backdrop-filter、clip-path、mask 不是 nonehover 動畫、毛玻璃效果

isolation: isolate刻意建立，下一節
contain: layout／paint、container-type: size／inline-size效能最佳化、container query（第 12 課）

拿這張表對照菜單頁。頁首是 sticky，建立了 stacking context，但沒寫 z-index，在根層的層級是 0。卡片為了 hover 動畫寫了 will-change: transform，也建立了 stacking context，層級也是 0。兩個同層級，依疊放順序的第 5 層按 DOM 順序畫：卡片在 DOM 後面，畫在上面。下拉選單在頁首這個資料夾裡，它的 9999 只用來跟頁首裡的 logo、按鈕比，所以永遠贏不了卡片。

修法是往上找到「兩個互相比較的 stacking context」，調整它們：給頁首 z-index，讓頁首整層（包含下拉選單）排在卡片之上。有人會想刪掉卡片的 will-change，但沒用：卡片還有 position: relative，仍是 z-index auto 的定位元素，依 DOM 順序照樣蓋過頁首；而且那是拿掉需求。

菜單頁的結構簡單，用眼睛就看得出是頁首和卡片在比。真實專案的元件可能包了七八層，要靠工具找。在 Elements 面板選取被蓋住的元素，到 Console 執行下面這段，它會列出這個元素往上每一個建立 stacking context 的祖先與原因（只檢查常見條件）：

for (let e = $0.parentElement; e; e = e.parentElement) {
  const s = getComputedStyle(e)
  const p = e.parentElement && getComputedStyle(e.parentElement).display
  const why = [
    s.position === 'fixed' || s.position === 'sticky' ? s.position : '',
    s.zIndex !== 'auto' && (s.position !== 'static' || /flex|grid/.test(p)) ? 'z-index ' + s.zIndex : '',
    s.opacity !== '1' ? 'opacity ' + s.opacity : '',
    s.transform !== 'none' ? 'transform' : '',
    s.filter !== 'none' ? 'filter' : '',
    s.isolation === 'isolate' ? 'isolation' : '',
    /transform|opacity|filter/.test(s.willChange) ? 'will-change ' + s.willChange : '',
  ].filter(Boolean)
  if (why.length) console.log(e, why.join('、'))
}

對蓋在上面的那個元素也跑一次，比較兩邊最上層、同一個父範圍裡的那兩個祖先，就知道該調誰。在菜單頁上，兩邊各自列出的最上層就是頁首和卡片。

💡 實務上：「被蓋住」的回報單，先找兩個祖先再動手
這類 bug 通常不是你寫新功能時發生，而是別人加了一個 hover 動畫、淡入效果，或接了第三方的客服聊天視窗、cookie 同意列之後，客服才轉來「按鈕點不到」「選單被擋住」，就像這課的第二張回報單。處理順序：先在出問題的頁面重現，用上面的程式找出互相比較的兩個 stacking context，只調那一層，並在 PR 說明是哪兩個元素在比。不要順手把數字加大，那只是把問題推給下一個人。Review 別人的 PR 時，看到新增 transform、opacity、filter 的元件，可以多問一句：裡面或附近有沒有下拉選單、彈出視窗？

第二張回報單也修好了，但留下一個問題：給頁首的 z-index 要寫多少？之後 toast 要蓋過下拉選單、彈出視窗要蓋過一切，如果每次都臨時挑一個數字，很快又會回到 9999。

全站的層級怎麼排，才不會又變成比數字大？

上一節說修法是「給頁首一個 z-index」。如果每個人都各自挑數字，z-index 會變成軍備競賽：這個 99、那個 999、新的 modal 寫 9999、toast 寫 99999，下一個人不知道該寫多少，只好再加一個 9。資深的做法是把全站會互相比較的層級列成一張刻度，集中在一個地方定義，元件只引用名稱：

:root {
  --z-dropdown: 100;   /* 下拉選單、tooltip */
  --z-sticky: 200;     /* sticky 頁首、側欄 */
  --z-overlay: 300;    /* 遮罩 */
  --z-modal: 400;      /* 彈出視窗 */
  --z-toast: 500;      /* 通知：要蓋過所有東西 */
}
.site { position: sticky; top: 0; z-index: var(--z-sticky); }
.toast { position: fixed; z-index: var(--z-toast); }

層與層之間留 100 的距離，之後要插一層（例如 150 的浮動按鈕）不用改別人。

刻度只在同一個 stacking context 裡有效，這是上一節學到的規則直接套用。下拉選單寫 var(--z-dropdown)，但它在頁首裡，實際跟卡片比的是頁首的 --z-sticky；toast 要蓋過下拉選單，就要比頁首高。所以設計刻度時想的是「哪些元件會在同一層互相比」，而不是「每個元件各自多重要」。

刻度管的是「全站元件之間」的層級。元件內部的疊放，例如卡片裡的徽章要在圖片上面，用 0～10 的小數字就夠，前提是把元件關成自己的 stacking context，讓這些小數字出不去：

.card {
  isolation: isolate;   /* 建立 stacking context，其他什麼都不改 */
}
.badge {
  position: absolute;
  z-index: 2;           /* 只在卡片裡比較 */
}

isolation: isolate 是專門用來建立 stacking context 的屬性，不像 transform、opacity 會帶來視覺效果或改變包含區塊。卡片現在因為 will-change 已經是 stacking context，為什麼還要寫？因為那是副作用：哪天有人把動畫拿掉，徽章的 z-index: 2 就漏到外面，可能蓋過 z-index 只有 1 的東西。用 isolation 把意圖寫明白，元件放到哪裡都一樣。

top layer：不需要 z-index 的那一層

刻度解決了「大家比數字」，但彈出視窗還有第 2 節留下的另一個問題：放在有 transform 的卡片裡時，fixed 會改以卡片為準。瀏覽器對這類元素有更直接的解法：在所有內容之上還有一層 top layer。放進 top layer 的元素，不管它在 DOM 的哪裡、祖先有沒有 transform、別人的 z-index 是多少，都畫在最上面，也不受祖先 transform 的包含區塊影響（MDN「Top layer」）。

會進入 top layer 的有三種：用 showModal() 開啟的 <dialog>；用 popover 屬性顯示的元素，這是 HTML 原生的彈出層，用來做選單、提示框；以及全螢幕的元素。新寫的彈出視窗、選單優先用這兩個原生元素，就不用把它們放進 z-index 刻度；瀏覽器支援程度見課末〈補充與查表〉，彈出視窗的焦點處理見第 5 課的 showModal()。

💡 實務上：z-index 刻度是團隊約定，不是個人寫法
刻度要有用，前提是全組都只用名稱：像上面那樣集中寫在共用的 CSS 變數檔裡，code review 看到寫死的 z-index: 999 就請對方改成變數或說明原因，菜單頁那種 9999 就不會再出現。導入 UI 元件庫（下拉選單、彈出視窗、通知）時，它們通常有自己的 z-index 預設值，先查文件確認，再對到你的刻度上，否則自己的 sticky 頁首可能蓋過套件的彈出視窗。新功能能用原生 <dialog>、popover 就先用，連刻度都不用排。頁面很簡單、只有一個頁首和一個彈出視窗時，不必一開始就設計五層，等第二個會互相比較的元件出現再補。

練習

練習 1：在「桂花烏龍拿鐵」照片的右上角放「新品」徽章，距離照片上緣與右緣各 8px。徽章不能影響卡片裡其他內容的位置（有徽章與沒徽章的卡片，標題離卡片頂端的距離要一樣）；卡片仍由 Grid 排列，不能用絕對定位排卡片。HTML 不能改。

練習 2：菜單頁的分類標題應該在捲動時黏在 64px 高的 sticky 頁首正下方，但現在頁首和標題都不黏。題目的 CSS 有兩個陷阱，找出來修好；右上角的裝飾圓形仍然不能讓頁面出現橫向捲動。另外，點目錄的「咖啡」「茶飲」「輕食」跳到分類時，分類不能被頁首擋住。頁首要維持 sticky。HTML 不能改。

練習 3：修疊層：購物車的下拉選單（題目固定展開）被下面的商品卡片蓋住；頂端的 toast 通知被 sticky 頁首蓋住。建立 z-index 刻度（:root 裡至少 4 個 --z- 開頭的 CSS 變數），讓下拉選單 > 頁首 > 卡片、toast > 下拉選單。卡片為了 hover 動畫常駐 will-change: transform，不能刪；卡片內部徽章的 z-index 要用 isolation 關在卡片裡。z-index 只能寫 var(--z-…)，或 0～10 的元件內局部值。HTML 不能改。

練習 4：下拉選單設了 z-index: 9999，仍然被一張卡片蓋住。最可能的原因是？

✓ b：z-index 只在同一個 stacking context 裡比較。要調的是建立 stacking context 的祖先（例如給 sticky 頁首 z-index），不是把數字加大。a 錯：z-index 沒有 999 的上限。c 錯：grid 容器本身不建立 stacking context（grid 的子項目設了 z-index 才會）。d 錯：快取的話其他樣式也會是舊的，而且 9999、99999 都沒用正是 stacking context 的典型症狀。

練習 5：position: sticky; top: 0 完全沒有效果，下列哪個最可能是原因？

✓ b：sticky 黏在最近一個有捲動機制的祖先上。overflow 是 hidden、auto、scroll 的祖先就是捲動容器，頁面捲動時它整個跟著走，sticky 看起來就像沒寫。只想裁切用 overflow: clip。a 錯：sticky 已是 Baseline widely available。c 錯：block 元素可以 sticky。d 錯：z-index 只影響它跟別人誰在上面，不影響會不會黏。

練習 6：下列哪一個屬性會讓元素建立新的 stacking context？

✓ b：opacity 小於 1 就會建立，所以淡入動畫做到一半時，元素裡的 z-index 也會被關起來。a 錯：flex 容器本身不會，它的子項目設了 z-index 才會。c 跟疊層無關。d 錯：relative 要加上 z-index（不是 auto）才建立；只寫 relative 會讓它變成定位元素、參與疊放順序，但不是新的範圍。

常見錯誤

  • 用 absolute 排版：absolute 元素不佔空間，內容一變長、換成手機寬度就互相重疊。版面用 Grid、Flexbox，absolute 只用在徽章、標籤這種小範圍疊加。
  • absolute 忘了給參考點：父層沒有 position: relative，元素一路找到初始包含區塊，跑到頁面角落。用 $0.offsetParent 確認它找到的是誰。
  • z-index 軍備競賽：9999 蓋不過時再加一個 9，問題其實在 stacking context。建立 z-index 刻度，元件內部用 isolation: isolate 關起來。
  • sticky 遇到 overflow：為了藏橫向捲軸在外層寫 overflow-x: hidden，整頁的 sticky 都失效。找出撐破的元素修好；真的要裁切就用 overflow: clip。
  • sticky 沒寫 top：只寫 position: sticky 不會黏，至少要一個門檻。
  • sticky 頁首擋住錨點與焦點：用 scroll-padding-top（或目標的 scroll-margin-top）扣掉頁首高度，符合 WCAG 2.4.11；不要用 margin 推開內容。
  • fixed 的彈出視窗放在有 transform 的元件裡：它改以那個元件為準。把 DOM 搬到 body（Vue 的 Teleport），或改用原生 <dialog>。

補充與查表

inset：四個偏移屬性的縮寫

四個偏移屬性可以用 inset 一次寫：inset: 0 等於上下左右都是 0，常用來讓 absolute 元素蓋滿父元素，或讓 fixed 的遮罩蓋滿視窗；inset: 8px 8px auto auto 依序是上、右、下、左，等於徽章的 top: 8px; right: 8px。

版本備註

  • sticky 從 2019 年 9 月起各大瀏覽器都支援，2022 年 3 月成為第 4 課講過的 Baseline widely available（web-features 3.44.0）。
  • <dialog> 是 Baseline widely available；popover 是 Baseline newly available（2025 年 1 月起，web-features 3.44.0）。

小結

  • position 的五個值差在兩件事：以誰為準（包含區塊）、還佔不佔原本的空間。relative 以自己原位為準、仍佔空間；absolute 以最近的已定位祖先為準、脫離正常流；fixed 以視窗為準，但祖先有 transform、filter、will-change: transform 等時改以祖先為準；sticky 在父元素裡、相對於最近的捲動容器黏住。
  • 新品徽章這類疊加：父層 position: relative 當參考點、徽章 position: absolute 加偏移。relative 偏移與負 margin 都會影響版面；整頁版面不用 absolute。
  • 分類標題不黏，依序查三件事：有沒有寫 top、祖先有沒有 overflow 不是 visible／clip、父元素有沒有比它高。黏住後搭配 scroll-padding-top，避免擋住錨點與焦點。
  • 下拉選單的 9999 蓋不過，是因為 z-index 只在同一個 stacking context 裡比較。position 加 z-index、fixed／sticky、opacity < 1、transform、filter、will-change、isolation 都會建立新的 context。蓋不過時，調整的是互相比較的那兩個祖先。
  • 全站用 --z-* 刻度管理層級，元件內部用 isolation: isolate 加小數字；<dialog> 與 popover 進入 top layer，不需要 z-index。
