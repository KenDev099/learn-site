階段 5：SEO 與內容交付 · 第 25 課

JavaScript SEO：CSR/SSR/SSG 與可索引內容、Search Console 驗證（資深）

豆留咖啡把官網改寫成 Vue 的單頁應用（SPA）：切換頁面不重新載入，體驗很順。上線兩個月後，行銷帶著三個問題來找你：Search Console 顯示網站只有首頁被索引；在 Google 搜「豆留咖啡 菜單」找不到菜單頁；把菜單網址貼到 LINE，預覽卡片只寫「豆留咖啡」，沒有圖也沒有說明。你打開瀏覽器，每一頁都正常。問題出在：你在瀏覽器看到的，跟爬蟲拿到的不是同一份東西。

前幾課處理的是 HTML 本身該寫什麼：title 與 description（第 22 課）、狀態碼與 noindex（第 23 課）、JSON-LD（第 24 課）。這一課處理的是：這些東西在伺服器回傳的 HTML 裡到底存不存在。整課都在解決豆留咖啡這三個症狀：先查出爬蟲拿到什麼，再決定每類頁面怎麼產生 HTML，把連結、head、狀態碼逐項修好，最後確認 Google 真的看到了，並讓下次改版時自動擋下同樣的問題。

這課的路線：
  1. 爬蟲拿到的是什麼、Google 不是會執行 JS 嗎：同一個網址有兩份 HTML；Google 多了「渲染」這一步，但要排隊、會跳過，而 LINE 這類爬蟲根本不執行 JS。
  2. 菜單頁該在哪裡產生 HTML：CSR、SSR、SSG 對爬蟲的差別，咖啡店每類頁面怎麼選。
  3. Google 怎麼找到每一頁：真正的 <a href>、不用 #/ 路由、內容不等互動、「載入更多」要有分頁網址。
  4. 每一頁的 head 與狀態碼：title、canonical、分享卡片在伺服器就產生好，不存在的品項回 404，noindex 不交給 JS 改。
  5. 驗證與防範：用 curl 和 Search Console 確認 Google 拿到什麼，再寫成每次部署都跑的檢查。
這課會用到：
  • Vue 課第 24 課的 CSR、SSR、SSG 與 hydration：在瀏覽器、在每次請求的伺服器、或在建置時產生 HTML；hydration 是瀏覽器接手伺服器產生的 HTML、掛上事件。
  • 第 22 課的 title、description 與 Open Graph：搜尋結果的那兩行字與社群分享卡片，都讀 head 裡的標籤。
  • 第 23 課的狀態碼、noindex、canonical：狀態碼決定這頁算不算存在，noindex 叫搜尋引擎不要收，canonical 指定重複網址裡的代表。

瀏覽器明明正常，爬蟲拿到的是什麼？

先回想第 22 課：Google 的爬蟲 Googlebot 從已知的頁面出發，跟著連結找到新網址，然後下載那個網址。下載的意思是送出一個 HTTP 請求，拿到伺服器回應的本文。要看到同一份東西，最直接的工具是 curl：它是命令列的 HTTP 工具，送出請求、把回應本文原封不動印出來，不畫畫面，也不執行任何 JavaScript。

對豆留咖啡的菜單頁執行一次。這個官網是用 Vite 建立的 Vue SPA，打包後的 JS 檔名帶有 hash：

$ curl -s https://brew.example.tw/menu/coffee/
<!doctype html>
<html lang="zh-Hant">
<head>
  <meta charset="utf-8">
  <title>豆留咖啡</title>
  <script type="module" src="/assets/index-3f9a1c.js"></script>
</head>
<body>
  <div id="app"></div>
</body>
</html>

沒有菜單、沒有價格、沒有任何連結，title 只有店名。換成 /stores/、/about/ 也一樣：每一個網址回傳的都是這一份。菜單之所以會出現在你的畫面上，是因為瀏覽器接著做了好幾件事：下載 index-3f9a1c.js、執行 Vue、Vue Router 依網址決定要顯示哪個元件、元件向 API 要菜單資料，最後才把 DOM 建進 #app。這種「HTML 的內容在使用者的瀏覽器裡由 JavaScript 產生」的做法，叫客戶端渲染（CSR，Client-Side Rendering）。

所以同一個網址其實有兩份 HTML：

  • 原始 HTML（initial HTML）：伺服器的回應本文，還沒執行任何 JavaScript。curl、「檢視網頁原始碼」、不執行 JS 的爬蟲看到的是這一份。
  • 渲染後 HTML（rendered HTML）：執行 JavaScript 之後的 DOM。你的畫面、DevTools 的 Elements 面板看到的是這一份。

你在瀏覽器裡驗收時，看的永遠是渲染後那一份，所以每一頁都正常。CSR 的兩份 HTML 差距最大：原始的那份幾乎是空的。開頭的 LINE 卡片就是這樣來的：產生預覽卡片的爬蟲下載網址、讀 head 裡的 og:title、og:image（第 22 課），而這些標籤是 Vue 在瀏覽器裡才加上去的，原始 HTML 裡只有 <title>豆留咖啡</title>，卡片就只能顯示店名。

但 Googlebot 跟 LINE 的爬蟲不一樣，它會執行 JavaScript。既然如此，為什麼菜單頁還是沒被收錄？下一節看 Google 為此多做的那一步，以及那一步在哪裡會出事。

Google 不是會執行 JavaScript 嗎？為什麼菜單頁還是沒被收錄？

上一節的空殼 HTML，Google 不會直接拿去索引。第 22 課說過搜尋引擎有爬取、索引、排序三個階段；網頁需要 JavaScript 才能顯示內容時，Google 在爬取和索引中間多了一步渲染（rendering）：把頁面交給瀏覽器執行 JavaScript，得到最後的 DOM，再拿那份結果去索引。

它用的瀏覽器是無頭（headless）的 Chromium。無頭瀏覽器就是沒有畫面的瀏覽器：一樣下載 CSS、JS、呼叫 API、執行程式、建出 DOM，只是不畫到螢幕上。整個流程長這樣：

照圖從左到右走一次，每一個箭頭都是 CSR 網站可能出事的地方。

第一個箭頭：只有回 200 的頁面才會排進渲染佇列。爬取完先看狀態碼，Google 文件寫明 404 這類非 200 的頁面可能跳過渲染。這對 CSR 反而是另一個問題的伏筆：CSR 的伺服器對所有路徑都回 200，連不存在的頁面也是，這件事在後面「每一頁的 head 與狀態碼」那一節處理。

第二個箭頭：渲染要排隊。渲染比單純下載 HTML 貴得多，Google 把要渲染的頁面放進渲染佇列（render queue），通常幾秒就排到，但也可能更久。排到之前，Google 手上只有原始 HTML，也就是上一節那個空的 #app。對 CSR 網站來說，這段時間菜單頁在 Google 眼中沒有任何內容。

「1. 爬取」上方的「robots.txt 擋住就不請求」：這條規則到了渲染也一樣，渲染時的資源要拿得到。無頭 Chromium 執行頁面時，會像一般瀏覽器一樣去下載 /assets/index-3f9a1c.js、呼叫菜單 API。這些請求一樣遵守 robots.txt（第 23 課）：如果 robots.txt 寫了 Disallow: /assets/，Google 渲染時拿不到 Vue 的程式，渲染出來的頁面還是空的；擋住 API，就只有頁首、沒有菜單。

「2. 渲染」上方的「看到 noindex 可能跳過」：原始 HTML 裡有 noindex，Google 可能直接跳過渲染。有些團隊會先在原始 HTML 放 noindex，打算等 JavaScript 載入完再移除；但渲染根本沒發生，移除的程式沒有機會執行，頁面就一直不被索引。

最後一個箭頭：新網址從渲染後 HTML 的 <a href> 找。Google 從連結的 href 屬性找新網址。CSR 的原始 HTML 裡沒有任何連結，所以菜單頁、門市頁的網址要等首頁排到渲染、渲染成功之後才會被發現，發現之後又要再爬取、再排隊渲染。只要中間任何一步失敗，這些內頁就停在「沒被發現」或「沒有內容」，這是「只有首頁被索引」最常見的樣子。

還有一件常被忽略的事：不是所有爬蟲都會執行 JavaScript。Google 文件自己也說不是每個 bot 都能執行 JS，所以仍然建議伺服器端渲染或預先渲染。LINE、Facebook 這類產生分享預覽卡片的爬蟲，也不能假設它們會等你的程式跑完再讀 Open Graph。實務上的判斷規則是：用 curl 拿得到的 og:title、og:image 才可靠。

結論是：CSR 讓 Google「有機會」在渲染後看到內容，但要排隊、會因為 noindex 或 robots.txt 失敗，其他爬蟲則完全看不到。根本的修法是讓原始 HTML 一開始就有內容與正確的 head。要做到這件事，HTML 就不能只在瀏覽器裡產生。下一節決定：咖啡店的每一類頁面，該在哪裡產生 HTML。

菜單頁該在哪裡產生 HTML？CSR、SSR、SSG 怎麼選

上一節的結論是原始 HTML 要有內容，而Vue 課第 24 課教過，同一個 Vue 應用可以在三個地方產生 HTML。這裡用「爬蟲看得到什麼」的角度重看一次：

  • CSR：在使用者的瀏覽器裡產生，就是上一節的空殼。
  • 伺服器端渲染（SSR，Server-Side Rendering）：每次有請求進來，Node 伺服器先執行 Vue 應用，用 renderToString 把這個網址的頁面產生成完整的 HTML 字串再回傳；瀏覽器收到後再 hydration，接手變成可互動的 SPA。
  • 靜態網站產生（SSG，Static Site Generation）：把 SSR 做的事提前到建置時，對每個路由各跑一次，輸出成一個個 HTML 檔，例如 menu/coffee/index.html。上線後主機只是把檔案原樣送出去，一樣再 hydration。

「在使用者請求之前就先產生好 HTML」這類做法統稱預先渲染（prerendering），SSG 是最常見的一種。Google 文件建議的「伺服器端渲染或預先渲染」指的就是 SSR 與 SSG。四種策略放在一起比：

策略原始 HTML 裡有什麼不執行 JS 的爬蟲、分享預覽狀態碼代價
CSR空的 <div id="app">，全站同一個 title看不到內容伺服器對所有路徑都回 index.html，一律 200最簡單，靜態主機就能放
SSR每次請求時在伺服器產生完整內容與 head看得到伺服器可以依資料回 404、301要跑 Node 伺服器，每次請求都花 CPU
SSG建置時就產生每個路由的完整 HTML 檔看得到不存在的路徑由主機回 404 頁內容一改就要重新建置；路由太多時建置很久
混合依路由選上面其中一種依路由依路由設定比較多（Nuxt 的 routeRules 就是做這件事）

「狀態碼」這一欄值得多看一眼。CSR 的伺服器不知道 /menu/mocha/ 存不存在，只有瀏覽器裡的 Vue Router 和 API 知道，所以伺服器只能對每個路徑都回 index.html 和 200。SSR 在伺服器上就查得到資料，可以回正確的狀態碼；SSG 則是根本沒有那個檔案，主機自然回 404。這一欄會在後面處理已下架品項時用到。

咖啡店的頁面依「要不要被搜尋、多久改一次」分成兩類：

首頁、菜單、品項頁、門市頁要被搜尋、要被分享，內容一天改不到幾次，適合 SSG：後台改菜單時觸發一次重新建置，產生新的 HTML 檔。如果價格、庫存需要即時反映，建置趕不上，就改用 SSR。

會員中心、購物車、結帳要登入、每個人看到的內容不同，本來就不該出現在搜尋結果裡，維持 CSR 就好，並在原始 HTML 加 noindex。上一節說「原始 HTML 放 noindex 會讓 Google 跳過渲染」，在這裡正好是我們要的：這些頁面本來就不要被索引。

Google 會執行 JS，為什麼還要 SSG？三個理由：渲染要排隊，原始 HTML 就有內容的頁面不用等；其他搜尋引擎和分享預覽不一定執行 JS；LCP 也比較好，因為主要內容不用等 JS 下載完（第 20 課）。反過來說，不需要被搜尋的頁面做 SSR 只是增加維運成本。

練習 1 就是把菜單頁的 CSR 原始 HTML 改成 SSG 輸出的樣子。不過光是原始 HTML 有內容還不夠：Google 要先找得到 /menu/coffee/ 這個網址，還要把它跟首頁當成不同的頁。下一節處理「找得到」。

💡 實務上：渲染策略在開案時就要決定，事後補很貴
常見的情境是：工程團隊為了開發快選了純 Vite SPA，上線後行銷才發現搜尋與分享預覽都不行，只好把整個專案搬到 Nuxt 或另外加預先渲染，豆留咖啡現在就在付這筆帳。開案時先問 PM 兩個問題：哪些頁面要被搜尋或分享？內容多久更新一次？很多團隊的做法是把「官網、菜單、部落格」和「會員、點餐、後台」拆開，前者用 SSG／SSR，後者維持 CSR。決定之後把「每類路由用哪種策略」寫進技術規格，之後新增頁面時，code review 才有依據判斷它該放哪一邊。

Google 怎麼找到每一頁，又怎麼知道它們是不同頁？

菜單頁改成 SSG 之後，原始 HTML 有內容了，但這只有在 Google 找得到這個網址時才有用。前面說過 Googlebot 跟著 <a href> 找新網址；SPA 有四種常見寫法，會讓網址或內容在爬蟲眼中消失，而且在瀏覽器裡全都看不出來。

導覽要是真正的 <a href>

Vue 寫久了，很容易在任何元素上掛 @click 換頁：

<!-- 爬蟲找不到 /menu/ -->
<span @click="router.push('/menu/')">菜單</span>
<a @click="router.push('/menu/')">菜單</a>
<a href="javascript:goTo('/menu/')">菜單</a>

<!-- 對：router-link 渲染出來就是 <a href="/menu/"> -->
<router-link to="/menu/">菜單</router-link>

前三種在瀏覽器裡點下去都能換頁，但 Google 只從有 href 的 <a> 讀出網址，而且它不會去點任何東西，就算渲染了也一樣。javascript: 開頭的 href 不是一個網址，也一樣不算。router-link 輸出的是真正的 <a href>，再攔截點擊改用 History API 切換頁面，所以爬蟲、鍵盤使用者、「在新分頁開啟」、複製連結都能用（第 2 課講過連結和按鈕的分工）。

路由要用真正的路徑，不要用 #/menu

就算連結都是 <a href>，網址本身也要是搜尋引擎認得的「不同網址」。這取決於 Vue Router 用哪一種歷史模式（Vue 課第 19 課）。

History API 是瀏覽器提供的介面，讓程式改變網址列而不重新載入頁面：history.pushState() 把網址改成 /menu/，之後使用者重新整理或爬蟲直接請求 /menu/，伺服器都真的收得到這個路徑。createWebHistory() 用的就是它。createWebHashHistory() 則把路由放在 # 後面，例如 https://brew.example.tw/#/menu。

網址裡 # 後面的部分叫 fragment，原本的用途是跳到頁面裡的某個位置。它不會送到伺服器，瀏覽器發請求時會把它留在自己這邊。Google 文件明確說不要用 fragment 載入不同的頁面內容。執行下面這格，看伺服器實際收到什麼，以及去掉 fragment 後剩幾個不同的網址：

三個 hash 路由去掉 fragment 後都是同一個 https://brew.example.tw/：對搜尋引擎來說，整個網站只有一頁。用 History API 的 /menu/、/stores/ 則是兩個不同的網址。

要被收錄的內容，不能等使用者操作才出現

找到網址之後，Google 渲染這一頁時只會載入頁面、執行頁面一開始就跑的程式，不會點按鈕，也不會觸發任何要使用者操作才跑的程式。菜單的「查看更多」按鈕、要點開分頁標籤才向 API 要資料的品項說明，對爬蟲就是不存在。要被索引的文字，一開始就要在 DOM 裡；只是想在視覺上先收起來，可以用 <details>，它的內容一直都在 HTML 裡。

「載入更多」後面的品項，要有自己的網址

同樣的道理放到長列表上。菜單有 60 個品項時，常見做法是「捲到底自動載入」或「載入更多」按鈕。Google 不會捲動，也不會按按鈕，所以只有第一批品項會被看到。Google 的分頁與漸進式載入文件給的做法，都是讓每一批品項變成爬蟲找得到的網址：

  1. 每一頁有自己的網址，例如 /menu/?page=2 或 /menu/page/2/。不要用 #page=2，原因就是上面的 fragment。
  2. 每一頁用 <a href> 連到下一頁，爬蟲才能一頁一頁走下去。「載入更多」按鈕旁邊可以同時放一個指向下一頁網址的連結，使用者點按鈕時用 JS 接手。
  3. 第 2 頁的 canonical 指向第 2 頁自己，不要全部指向第 1 頁：第 1 頁沒有第 2 頁的品項，指過去等於告訴 Google 第 2 頁的品項不用收。

分頁標記 rel="next"、排序與篩選網址的處理，見課末「補充與查表」。

到這裡，Google 找得到 /menu/coffee/、/stores/，也知道它們是不同的網址，內容一開始就在原始 HTML 裡。剩下 head 的部分：每一頁的 title、canonical、分享卡片，還有狀態碼，是不是也在原始 HTML 裡就對了？

每一頁的 head 與狀態碼，怎麼在伺服器就決定好？

CSR 的 index.html 只有一個 head，所以全站的 title、description、canonical、og 都一樣。就算 Vue 在切換路由時改了 document.title，改到的也只是渲染後的 DOM：Google 排到渲染後可能看得到新的 title，但 LINE 卡片和其他爬蟲看到的還是「豆留咖啡」。canonical 更要小心：Google 文件說設定 canonical 最好的方式是寫在 HTML 裡；用 JS 設定時，值要跟原始 HTML 一致，而且只能有一個。

修正的方向只有一個：每個路由的 head 在伺服器（SSR）或建置時（SSG）就產生好，瀏覽器端只負責切換路由時同步更新。狀態碼也是同一個原則：在伺服器就決定好，不交給瀏覽器裡的 JS。

用 Unhead 在元件裡宣告這一頁的 head

Vue 生態系常用 Unhead 管理 head，Nuxt 內建的就是它。品項頁元件拿到品項資料後，宣告這一頁的 title、description、canonical：

<script setup lang="ts">
import { useHead } from '@unhead/vue'
const props = defineProps<{ item: { name: string; price: number; slug: string } }>()

useHead({
  title: () => `${props.item.name} ${props.item.price} 元｜豆留咖啡`,
  meta: [{ name: 'description', content: () => `豆留咖啡的${props.item.name}，每份 ${props.item.price} 元。` }],
  link: [{ rel: 'canonical', href: () => `https://brew.example.tw/menu/${props.item.slug}/` }],
})
</script>

同一份宣告在兩個環境各有用途。在瀏覽器裡，Unhead 在切換路由時改寫 head，讓分頁標題跟著變；在伺服器上，renderToString 跑過每個元件後，Unhead 收集到這一頁所有元件宣告的標籤，由你把它們寫進回傳的 HTML。所以 Unhead 分成 client 與 server 兩個入口，兩邊都要接上（入口的寫法見課末「版本備註」）。

最常見的錯誤是只接了 client 那一半：瀏覽器裡分頁標題正確，DevTools 的 Elements 也看得到 canonical，但這些全是渲染後才有的，原始 HTML 還是預設值，結果等於還是 CSR。所以驗收一律看原始 HTML，不看 Elements 面板。

自己產生 head 字串時，要做跳脫

不用框架、自己在 SSG 腳本裡把 head 拼成字串時（練習 2 就是），會把後台輸入的品項名稱直接插進 HTML。後台的人可能輸入 &、引號，甚至誤貼一段 </script>。沒處理的話，品項名稱就能改變頁面結構、注入 HTML 或程式碼，這就是 XSS（認證課第 7 課）。兩種位置的處理方式不同：

插進 HTML 的文字與屬性值要做 HTML 跳脫：& → &amp;、< → &lt;、屬性值裡的 " → &quot;。瀏覽器讀到時會解碼回原本的字元，所以顯示正確，又不會被當成標籤。

JSON-LD 則不做 HTML 跳脫：<script> 裡的內容不會解碼 &amp;，做了反而讓資料多出 &amp; 這些字。要防的是字串裡出現 </script> 提早結束區塊，所以把 JSON 裡的 < 換成 \u003c，JSON 解析後還是同一個字元（第 24 課）。

不存在的品項，要回 404

head 對了，狀態碼也要對。「菜單頁該在哪裡產生 HTML」那一節的表格提過，CSR 的伺服器對任何路徑都回 index.html：已下架的 /menu/mocha/ 也是 200，畫面上再由 Vue 顯示「找不到這個品項」。第 23 課講過，這叫 soft 404：內容說找不到，狀態碼卻說正常，搜尋引擎可能把它當成正常頁面收錄。修法依架構：

  • SSR：伺服器在呼叫 renderToString 之前先解析路由、查資料，查不到就把 HTTP 回應的狀態碼設成 404，再渲染「找不到」的畫面（Vue 課第 24 課把「錯誤與 404 狀態碼」列在正式 SSR 網站要補的清單裡；用 Nuxt 時框架有現成的做法）。
  • SSG：不存在的路徑沒有對應的檔案，靜態主機回 404 頁就好；要確認主機的「SPA fallback」設定沒有把所有路徑都導到 index.html 並回 200。
  • 純 CSR（不得已時）：Google 文件給兩個做法：用 JavaScript 導向到一個伺服器真的回 404 的網址（例如 /not-found），或用 JavaScript 在錯誤頁加上 <meta name="robots" content="noindex">。

noindex 的值，原始 HTML 就要是最終的值

最後是 robots meta。「Google 不是會執行 JavaScript 嗎」那一節看過「先輸出 noindex、再用 JavaScript 拿掉」的寫法，通常出自「內容還沒載入前不要被索引」的想法。Google 文件說：遇到 noindex 可能跳過渲染與 JavaScript 執行，用 JS 改掉或移除 noindex 可能不會照預期生效；要被索引，就不要在原始 HTML 放 noindex。

反方向是原始 HTML 沒有，JS 才加上 noindex。Google 渲染後會照做，文件也把它列為上面純 CSR 處理 soft 404 的做法；但不執行 JS 的爬蟲看不到，頁面也要等排到渲染才會被排除。所以除了這個不得已的情況，robots 的值在原始 HTML 就要是最終的值：公開頁不放 noindex，會員中心這種本來就不該被索引的頁面，noindex 直接寫在原始 HTML。

到這裡，豆留咖啡的三個症狀都有了對應的修法。但「修好了」是你說的，Google 現在實際看到什麼，要另外確認。

💡 實務上：舊站改版成 SPA，先盤點舊網址
這一節和上一節的問題，最常在「舊官網改版成 Vue」時一次出現：舊網址 /menu.php?id=3 改成 /menu/latte/，舊網址卻變成 soft 404，累積的搜尋排名和別人貼過的連結一起失效。上線前從舊的 sitemap 和 Search Console 匯出有流量的網址，逐一決定 301 到哪個新網址（第 23 課），並用 curl 批次確認狀態碼。另外跟行銷確認 LINE、Facebook 分享卡片要顯示什麼，因為這些平台會快取舊卡片，上線後才修要等快取更新。

修完之後，怎麼確認 Google 真的看到了？

上一節修完的東西，不能用自己的瀏覽器驗收：你的瀏覽器有登入狀態、快取、擴充功能，而且一定會執行 JS，看到的永遠是渲染後那一份。依序用三種方法，從「原始 HTML 對不對」查到「Google 實際收到什麼」，再到「全站趨勢」。

1. curl 看原始 HTML

第一節用 curl 發現問題，這裡用同一個工具確認修好了。三行分別檢查 head 的關鍵標籤、主要內容在不在原始 HTML、不存在的品項是不是 404：

$ curl -s https://brew.example.tw/menu/coffee/ | grep -E '<title|name="description"|rel="canonical"|name="robots"|og:title'
$ curl -s https://brew.example.tw/menu/coffee/ | grep -c '拿鐵'          # 主要內容在不在原始 HTML
$ curl -s -o /dev/null -w '%{http_code}\n' https://brew.example.tw/menu/mocha/   # 不存在的品項要是 404

不想開終端機，Chrome 也做得到：「檢視網頁原始碼」看的是原始 HTML；DevTools 按 Ctrl+Shift+P（macOS 是 Cmd+Shift+P）輸入「Disable JavaScript」後重新整理，看到的就是不執行 JS 的爬蟲的視角（第 18 課的 DevTools）。

2. Search Console 的網址審查

curl 證明原始 HTML 對了，但 Google 實際渲染出什麼、有沒有因為 robots.txt 或 JS 錯誤失敗，要看 Google 自己的報告。Google Search Console 是 Google 提供給網站擁有者的免費後台（第 22 課介紹過），使用前要新增資源（property）並證明你擁有這個網站。資源類型與驗證方式見課末「補充與查表」；這裡只記一件跟本課有關的事：用 meta 標籤驗證時，它必須在原始 HTML 的 head 裡，CSR 動態加上的不算。

網址審查工具（URL Inspection）顯示 Google 怎麼爬取、渲染、索引某一個網址。在上方搜尋框輸入網址就會開啟，有兩種結果：

看什麼Google 索引版本（Google Index）即時測試（Live Test）
資料來源上次索引的版本，不是即時的現在即時抓一次
HTML、HTTP 回應、載入的資源、JS console 訊息View crawled pageView tested page
螢幕截圖沒有有（測試成功時）
適合查「為什麼沒被索引」「Google 選了哪個 canonical」修完之後確認 Google 現在看得到

報告裡要看的欄位（括號是英文介面的名稱）：

  • 抓不抓得到（Page fetch）。
  • 有沒有被 noindex 擋下（Indexing allowed?）。robots.txt 擋住時，Google 看不到頁面裡的 noindex，所以這裡會顯示 Yes，不要被它騙了。
  • 你宣告的 canonical（User-declared canonical）與 Google 選定的 canonical（Google-selected canonical）：兩者不同，代表 Google 沒有採用你的 canonical。
  • View crawled page 裡的 HTML：這是渲染後的。拿它跟 curl 的原始 HTML 比較，就能看出哪些東西只靠 JS 才出現（練習 3 把這個比較寫成程式）。
  • 螢幕截圖：如果只有頁首、沒有菜單，常見原因是 API 被 robots.txt 擋住，或 JS 出錯（看同一頁的 console 訊息）。

修好之後可以按「要求建立索引」（Request indexing），它有每日次數限制，也不保證收錄；大量網址請靠 sitemap 的 <lastmod>（第 23 課）。

3. 全站報告：網頁索引、成效與 Core Web Vitals

網址審查一次只看一個網址；「只有首頁被索引」這種問題，要從全站的角度確認修好了沒有：

  • 網頁索引報告（Page indexing，舊名 Index Coverage）：列出哪些網址已索引、哪些沒有以及原因，例如 Discovered – currently not indexed（找到了但還沒索引）、Soft 404、Excluded by ‘noindex’ tag、Alternate page with proper canonical tag（被當成別頁的替代版本）。改版上線後每週看一次未索引的原因有沒有突然增加。
  • 成效報表（Performance）：列出網址與查詢字詞在 Google 搜尋的曝光次數、點擊次數、點閱率（CTR）與平均排名，可以依網頁或查詢篩選。網頁索引報告回答「有沒有被收錄」，成效報表回答「收錄之後有沒有人搜到、點進來」。豆留咖啡修好之後，篩選 /menu/ 開頭的網頁，就能確認菜單頁開始出現「豆留咖啡 菜單」這類查詢；第 22 課說的「使用者實際搜什麼」，資料就是從這裡來。
  • Core Web Vitals 報告：用 CrUX 的真實使用者資料（第 20 課），把網址分成良好、需要改善、不佳。它反映的是過去 28 天，修完不會隔天就變。

這三種方法都是「出事之後去查」。豆留咖啡的問題上線兩個月才被發現，下一節把這些檢查往前移到每次部署之前。

💡 實務上：行銷說「搜尋流量掉了」時，先查什麼
先問清楚是全站還是某一類頁面、從哪一天開始，再對照那幾天的部署紀錄：多數情況是某次上線改了路由、robots.txt 或 head，而不是 Google 演算法變了。接著用網頁索引報告看未索引的原因有沒有突然增加，挑一個掉最多的網址做 curl 與網址審查的即時測試。修好後要跟對方說清楚：重新索引需要時間，報告不會隔天就恢復，避免被當成「沒修好」。

怎麼讓下次改版不會再悄悄壞掉？

回頭看豆留咖啡這次的事故：上線時沒有人發現，因為每個人都用瀏覽器驗收；兩個月後才從 Search Console 看到。SEO 問題最常在「重構路由」「換渲染策略」「升級框架」時被悄悄帶進來，而且要幾週後才在報告裡浮現。資深工程師的做法是把這課每一節修的東西，都寫成每次部署都會跑的檢查，而不是上線後才去搜尋看看：

檢查怎麼驗放在哪裡
每個公開路由的狀態碼正確（200／301／404）對路由表逐一請求，不執行 JSE2E（第 27 課）
原始 HTML 含 h1 與主要內容抓原始回應找 h1 與關鍵字E2E
title、description 每頁唯一收集所有路由的 title 比對重複E2E
canonical 恰好一個、自我參照、原始與渲染後相同比對原始 HTML 與渲染後 DOME2E
公開頁沒有 noindex；會員頁有同上E2E
JSON-LD 與頁面內容一致第 24 課的檢查E2E
導覽都是 <a href>、沒有 #/code review、lintPR 範本的勾選清單

表裡大部分的檢查，核心都是同一件事：拿原始 HTML 和渲染後 HTML 比，任何只在渲染後才出現的 title、canonical、noindex 變化、連結、內容，都是風險。練習 3 的 diffRendered 就是這個比對的核心。第 27 課會用 Playwright 對每個公開路由跑這類檢查，當成合併前的關卡。

上線後的監控交給 Search Console 的網頁索引報告與 Core Web Vitals 報告。把資源的擁有者設成團隊信箱，Search Console 偵測到新問題時寄的通知，才不會只寄到某個已經離職的同事。最後，判斷優先順序時記得 SEO 只處理公開、要被搜尋的頁面：會員中心不用為了 SEO 做 SSR。

補充與查表

主線用不到、但設定 Search Console 或處理分頁時會查的細節。

Search Console 的資源類型與擁有權驗證

新增資源時有兩種類型：

  • 網域資源（例如 brew.example.tw）：包含所有子網域與 http／https，只能用 DNS 記錄驗證。
  • 網址前置字元資源（例如 https://brew.example.tw/）：只包含這個前置字元底下的網址，可以用上傳 HTML 檔、在首頁 head 加 <meta name="google-site-verification">、Google Analytics、Tag Manager 或 DNS 驗證。

驗證用的 DNS 記錄、檔案或 meta 標籤要一直保留：Search Console 會定期檢查，拿掉後一段時間就失去權限。用 meta 標籤驗證時，它必須在原始 HTML 的 head 裡，CSR 動態加上的不算。

分頁的其他細節

Google 已經不使用 rel="next"／rel="prev" 來理解分頁，寫了無害，但不能靠它讓爬蟲找到下一頁，還是要有 <a href>。

排序、篩選產生的網址（?sort=price）內容跟原本的列表重複，用 noindex 或 robots.txt 處理（第 23 課）。

版本備註

Google 的規則以 Search Central 的 JavaScript SEO basics（last updated 2026-03-04）、分頁與漸進式載入（pagination and incremental page loading）文件，以及 Search Console 說明中心的網址審查工具、擁有權驗證文件為準。Vue 的部分依 Vue 3.5.44；head 管理以 @unhead/vue 3.4.3 為例：瀏覽器端用 @unhead/vue/client 的 createHead()，伺服器端用 @unhead/vue/server 的 createHead()，renderToString 之後把收集到的標籤寫進 HTML 回應。

練習

練習 1：這是 CSR 版咖啡菜單頁（https://brew.example.tw/menu/coffee/）的原始 HTML：菜單資料放在 #menu-data，原本要等 JS 執行才畫進 #app。預覽不執行 JavaScript，正好是不執行 JS 的爬蟲看到的樣子。把它改成 SSG 輸出的樣子：(1) 在 #app 裡直接寫出 <main>：h1「咖啡菜單」、三個分類的 h2、6 個品項的名稱與價格（例如「美式咖啡 80 元」），以及一個連到 /stores/ 的門市資訊連結；(2) header 的 5 個連結（豆留咖啡 /、菜單 /menu/、門市 /stores/、關於我們 /about/、線上點餐 /order/）都改成真正的 <a href>；(3) head 加上這一頁專屬的 title（「主題｜豆留咖啡」）、30～160 字的 description、指向這一頁的 canonical；(4) 拿掉「先 noindex 再由 JS 移除」的寫法。/assets/index-3f9a1c.js 要留著，Vue 還要靠它 hydration。

練習 2：寫 renderHead(route, data)，給 SSG／SSR 產生每個路由的 head 標籤字串（標籤之間用換行分隔）。規則：(1) 每一頁有恰好一個 <title> 與 <meta name="description" content="…">，不同網址的 title、description 都不能重複；品項頁的 title 要包含品項名稱與價格；(2) 狀態 200 的頁面輸出一個 <link rel="canonical" href="…">：ORIGIN 加路徑，去掉查詢參數與 #，路徑統一以 / 結尾；(3) 狀態 404 的頁面輸出 <meta name="robots" content="noindex">，不輸出 canonical；(4) 品項頁輸出一段 <script type="application/ld+json">：@context、@type: "MenuItem"、name、offers（@type: "Offer"、price、priceCurrency: "TWD"、offeredBy: { "@id": ORG_ID }）；(5) 插進 HTML 的文字與屬性值都要跳脫 &、<、>、"，屬性一律用雙引號；JSON-LD 裡的 < 換成 \u003c。測試的品項名稱會有 &、引號，以及後台誤輸入的 </script>。

練習 3：上線前的自動檢查：同一個網址，用 curl 拿到原始 HTML、用 headless 瀏覽器（或 Search Console 的 View crawled page）拿到渲染後 HTML，各自整理成 PageFacts。寫 diffRendered(initial, rendered) 回傳風險清單，依型別 Risk 列出的順序：robots-changed-by-js：兩邊「是否 noindex」不同（robots 以逗號分隔、不分大小寫，含 noindex 或 none 就算 noindex；原始有、渲染後拿掉，或原始沒有、渲染後加上都算）；canonical-changed：兩邊的 canonical 不相同（包含一邊是 null）；title-only-in-rendered：渲染後的 title（去掉前後空白）不是空的，而且跟原始的不同；links-only-in-rendered：渲染後的連結去重複後，只出現在渲染後的比例超過 20%；content-only-in-rendered：原始的 wordCount 小於渲染後的 30%；jsonld-only-in-rendered：渲染後有原始沒有的 JSON-LD 型別。description 與 h1 這題用不到。

練習 4：SPA 用 <span @click="router.push('/menu/')">菜單</span> 當導覽，對 SEO 有什麼影響？

✓ b：Google 從 <a href> 的 href 找新網址，執行 JS 也不會去點 span。用 <router-link>，它渲染成真正的 <a href>，使用者也能用新分頁開啟、複製連結。a 錯：渲染不等於點擊。c 錯：Google 一樣受影響。d 錯：這是站內連結，少了它只是爬不到菜單頁。

練習 5：原始 HTML 有 <meta name="robots" content="noindex">，打算等 Vue 載入後用 JavaScript 移除，結果會是？

✓ b：Google 文件說遇到 noindex 可能跳過渲染與 JavaScript 執行；要被索引就不要在原始 HTML 放 noindex。a 是常見的誤解：它假設一定會渲染。c 錯：Google 也遵守 robots meta。d 錯：跟裝置無關。

練習 6：想確認 Google 看到的菜單頁內容，哪一種方式最可靠？

✓ c：curl 是不執行 JS 的視角；網址審查顯示 Googlebot 實際取得的 HTML、渲染結果、canonical 與能不能索引。a 錯：你的瀏覽器有登入狀態、快取，而且一定執行 JS。b 錯：Lighthouse 的 SEO 檢查只看幾項基本標記，量的是渲染後的頁面。d 錯：首頁被索引不代表菜單頁也被索引。

常見錯誤

  • 只靠自己的瀏覽器驗證：你的瀏覽器一定執行 JS，看到的是渲染後 HTML。用 curl 看原始 HTML，用 Search Console 網址審查看 Google 的版本。
  • robots.txt 擋住 /assets/ 或 API：Google 渲染時拿不到 JS 或資料，網址審查的截圖是空的。
  • 為了 SEO 把整站改成 SSR：會員、結帳這些不需要被搜尋的頁面維持 CSR 並加 noindex 就好。
  • 導覽用 @click 換頁，不是 <a href>：Google 只從有 href 的 <a> 找網址，也不會去點。用 <router-link>。
  • 用 #/menu 當路由：fragment 不會送到伺服器，也不會被當成不同網址，整站等於一頁。用 History API（createWebHistory()）。
  • head 只在瀏覽器端更新：title、canonical、og 在瀏覽器裡看起來對，原始 HTML 裡還是預設值，分享預覽與其他爬蟲看不到。SSR／SSG 要把 head 寫進輸出。
  • SPA 的 404 回 200：soft 404。SSR 依資料設定狀態碼；SSG 確認主機不會把所有路徑都 fallback 成 200；純 CSR 導向到真的回 404 的網址或加 noindex。
  • 用 JS 移除 noindex：Google 可能看到 noindex 就跳過渲染，移除的程式沒機會執行，頁面一直不被索引。robots 的值在原始 HTML 就要是最終的值。

小結

  • 同一個網址有原始 HTML 與渲染後 HTML。爬蟲下載到的是原始那一份；CSR 的原始 HTML 只有空的 #app，你在瀏覽器裡看到的是渲染後那一份，所以看不出問題。
  • Google 對 JavaScript 網站是爬取 → 渲染佇列 → 渲染 → 索引：只有回 200 的頁面會排進渲染，渲染要排隊，robots.txt 擋住的資源拿不到，看到 noindex 可能跳過渲染。LINE 這類分享預覽與其他爬蟲不一定執行 JS。
  • 要被搜尋、被分享的頁面用 SSG 或 SSR，讓內容與 head 在原始 HTML 就存在；要登入、每人不同的頁面維持 CSR，原始 HTML 加 noindex。
  • 讓 Google 找得到每一頁：導覽用 <a href>、路由用 History API、要被索引的內容不等互動、「載入更多」的每一批有自己的分頁網址。
  • 每一頁的 title、description、canonical、og 在伺服器或建置時產生；不存在的品項回 404；noindex 在原始 HTML 就是最終值。自己拼 head 字串時，HTML 跳脫，JSON-LD 只把 < 換成 \u003c。
  • 驗證順序：curl 看原始 HTML → Search Console 網址審查看 Google 取得與渲染的版本 → 網頁索引與 Core Web Vitals 報告看全站趨勢。再把這些檢查寫進 PR 範本與 E2E，每次改路由都會跑。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 7：部落格有〈拿鐵和卡布奇諾差在哪〉和〈拿鐵、卡布、馥列白比較〉兩篇，搜尋「拿鐵 卡布 差別」時兩篇輪流出現，名次都不好。怎麼處理？

✓ 兩頁回答同一個需求會互搶同一個搜尋，每一頁都不夠好；一個需求一頁，其他網址用重新導向指過去，舊網址的連結也跟著過去。b 錯在多開一頁變成三頁互搶，問題更嚴重。（第 22、23 課）

練習 8：訂位完成頁 /reserve/thanks/ 不該出現在搜尋結果，同事在 robots.txt 加了 Disallow: /reserve/thanks/。兩週後它還在結果裡，只剩網址、沒有說明，該怎麼改？

✓ robots.txt 管下載、noindex 管收錄；被擋的網址只要有連結指向，仍可能只以網址出現。要不被索引就只用 noindex，而且不能擋住爬取。b 錯在爬蟲被擋在門外，永遠讀不到那個 noindex。（第 23 課）

練習 9：改版後，菜單、門市這些內頁一個個從搜尋結果消失，首頁正常。內頁都回 200、head 裡沒有 noindex、robots.txt 沒擋、sitemap 也有列，最先該查什麼？

✓ canonical 通常寫在共用 layout，從首頁模板複製時寫死，每一頁都在說「代表是首頁」，內頁就被當成首頁的重複版本。用 curl 抽幾種頁面看原始 HTML，修成由路由產生、指向自己的絕對網址。a 錯在 description 不影響排名也不決定收錄，只影響摘要與點擊。（第 23 課）

練習 10：用 SSR 的品項頁裡，某支豆子永久停賣、也沒有後續批次。現在頁面顯示「這個品項已停售」並回 200，Search Console 標成 soft 404。怎麼修？

✓ 狀態碼要表達頁面的真實狀態：永久下架、沒有替代品就是 404／410，頁面內容可以推薦，但狀態碼要對。只有明確的替代品才 301 到替代品。a 錯在把下架商品導到首頁，Google 也可能把它當成 soft 404。（第 23、25 課）

練習 11：門市頁的營業時間寫在 Vue 模板裡，JSON-LD 的 openingHoursSpecification 寫在另一個 JSON 檔。上次改營業時間只改了頁面，怎麼避免再發生？

✓ 結構化資料必須反映頁面上看得到的內容；兩份資料各自維護一定會漂移，從同一份資料產生、用自動測試守住才擋得住。a 錯在兩個工具檢查的是語法與 rich result 資格，時間寫錯但格式正確照樣通過。（第 24 課）

練習 12：咖啡店官網原本是純 Vite SPA，要重新規劃。頁面有菜單與品項頁（一週改一兩次）、會員點餐紀錄、結帳，哪一種分配最恰當？

✓ 要被搜尋、被分享的頁面讓內容與 head 在原始 HTML 就存在；要登入、每人不同的頁面本來就不該被索引，CSR 加 noindex 就好。b 錯在渲染要排隊，其他爬蟲與分享預覽不一定執行 JS，head 只在瀏覽器端更新它們看不到。（第 25 課）

練習 13：新上線、還沒人分享過的品項頁貼到 LINE，卡片只寫「豆留咖啡」、沒有圖。Search Console 網址審查卻顯示 Google 看到正確的品項 title，原因最可能是？

✓ Google 會把頁面排進渲染、執行 JS，所以看得到；分享預覽的爬蟲不能假設會等程式跑完。用 curl 看原始 HTML，拿得到的 og 才可靠，要分享的頁面用 SSR／SSG 把 head 寫進輸出。a 錯在相對路徑只會讓圖片不見，title 不會因此變回店名。（第 22、25 課）
