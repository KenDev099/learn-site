階段 3：現代 CSS 與視覺品質 · 第 14 課

圖片實務：格式、srcset/sizes、尺寸預留與載入策略

咖啡店首頁改版後，店長用手機打開，回報兩件事：「好慢」，還有「看到一半，文字會突然往下跳」。打開 DevTools 一看，問題有三個：首頁的拿鐵主視覺是一張 4000px 寬、4 MB 的 JPEG，手機上卻只顯示 360px 寬；菜單的 8 張照片在頁面一打開就全部下載，連使用者根本還沒捲到的也一樣；每張圖都要等下載完才撐開高度，把下面的文字往下推。另外還注意到，首屏的門市照片是用 CSS 背景圖放的，這點留到後面處理。

這三個問題都出在圖片。圖片通常是網頁裡最大的資源，也常是首屏（使用者不捲動時，畫面一打開就看得到的那一塊）最慢出現的東西，所以這課整課都在修這個首頁：讓每台裝置只下載它需要的大小與格式，讓首屏的主視覺最先到、看不到的圖晚點再下載，並在圖片到之前就把位置佔好。

這課的路線：
  1. 手機到底下載了多大的圖、它其實需要多大？先量，得出「顯示寬度 × DPR」這個標準，以及三個問題的最小答案。
  2. 像素數對了，檔案還能再小嗎？照片、圖示、透明圖各該存成 AVIF、WebP、JPEG 還是 SVG。
  3. 同一張圖準備好幾種寬度，瀏覽器怎麼挑？用 srcset 列出候選、用 sizes 告訴它版面多寬；不支援新格式的瀏覽器、手機要換裁切，交給 <picture>。
  4. 圖片還沒到，怎麼先把位置佔好？主視覺怎麼先下載、菜單的圖怎麼延後？處理「文字往下跳」與「全部一起下載」。
  5. 這麼多尺寸、格式的圖檔由誰產生，上線後怎麼長期快取？
這課會用到：
  • 第 13 課的單位：1vw 是視窗寬度的 1%，calc(100vw - 32px) 可以混用不同單位計算。
  • 第 11 課的 media query：(min-width: 64em) 這類條件在畫面夠寬時成立；media query 裡的 em 等於瀏覽器預設字級（通常 16px）。

手機到底下載了多大的圖、它其實需要多大？

店長說「好慢」，第一步不是改程式，而是先量出瀏覽器到底下載了什麼、下載了多少。但要判斷「多大才算太大」，得先知道一張圖在手機上其實需要多少像素，這要從螢幕的像素說起。

CSS 裡寫的 px 不是螢幕上的實體像素。手機螢幕的實體像素排得很密，如果 CSS 的 1px 就是 1 個實體像素，同樣 16px 的字在手機上會小到看不清楚。所以瀏覽器把一個 CSS px 對應到好幾個實體像素：一般桌機螢幕是 1 個對 1 個，大部分手機是 2×2 或 3×3 個。這個「一個 CSS px 的寬度佔幾個實體像素」的倍數，叫做裝置像素比（DPR, device pixel ratio）。在 Console 輸入 devicePixelRatio 就能看到目前螢幕的值。

DPR 決定了圖檔需要多少像素。CSS 寫 360px 寬的圖，在 DPR 3 的手機上佔了 1080 個實體像素寬：

  • 給它 360px 寬的圖檔，一個圖檔像素要放大成 3 個實體像素，看起來會糊。
  • 給它 1080px 寬的，一個圖檔像素剛好對一個實體像素，清楚而且不浪費。
  • 給它 4000px 寬的，畫面上只用得到 1080 個，其餘的像素在縮小時被丟掉。手機白白下載了 4 MB，等於多花了使用者的流量和等待時間。

知道標準之後，用 DevTools 量首頁實際下載了什麼：

  1. 開 DevTools（F12 或 Cmd+Option+I），切到 Network，勾 Disable cache（不然第二次載入看到的是快取），篩選器選 Img。
  2. 重新整理。Size 欄是實際傳輸量；滑鼠停在圖片的名稱上會顯示縮圖與圖檔的實際尺寸（例如 4000 × 2667）。
  3. 想看手機的情況：按 Toggle device toolbar（Cmd+Shift+M）選一款手機，DPR 會跟著換；工具列的網路下拉選單選 Fast 4G 或 Slow 4G 模擬手機網路。
  4. 在 Elements 選取一張 <img>，到 Console 輸入 $0.currentSrc，看瀏覽器實際選了哪個檔案（後面講 srcset 時會用到）；滑鼠停在 src 屬性上，會同時顯示「Rendered size」（顯示尺寸）與「Intrinsic size」（圖檔實際尺寸）。

判斷的標準：圖檔寬度大約是「顯示寬度 × DPR」就合理；大到兩倍以上就是浪費。照這個標準看首頁，4000px 的主視覺在 360px、DPR 3 的手機上大了將近四倍。

到這裡已經能說出這三個問題的最小答案，後面每一節都是在把這些答案做完整：

  • 主視覺太大：讓手機下載接近「顯示寬度 × DPR」的圖檔，並換成更省的格式（下一節，以及〈同一張圖準備好幾種寬度，瀏覽器怎麼挑？〉）。
  • 文字往下跳：在 <img> 寫上 width 和 height，讓瀏覽器在圖片下載前就預留位置（〈圖片還沒到，怎麼先把位置佔好？〉）。
  • 菜單一次全部下載：首屏以下的圖延後到快捲到時才下載（〈主視覺怎麼先到、菜單的圖怎麼晚點下載？〉）。

先從第一個開始。「顯示寬度 × DPR」決定了圖檔要有多少像素，但同樣多的像素，存成不同的格式，檔案大小可以差好幾倍。

像素數對了，檔案還能再小嗎？選對格式

上一節決定了圖檔要多少像素，這一節決定這些像素用什麼方式存。圖檔格式的差別，在於它怎麼把一大堆像素「壓縮」成比較小的檔案，主要有三種做法：

  • 有損壓縮：丟掉人眼不容易察覺的細節，換取小很多的檔案。照片的顏色變化細碎，丟掉一點細節看不出來，所以照片幾乎都用有損壓縮。代價是邊緣銳利的東西（文字、線條）周圍會出現雜點。
  • 無損壓縮：每個像素都原樣保留，解壓縮後跟原圖一模一樣。適合需要精確像素的截圖；拿來存照片，檔案會大好幾倍。
  • 向量：不存像素，而是用座標描述形狀，例如「從這點到那點畫一條線、填這個顏色」。放到多大都由瀏覽器重新畫，所以任何大小都清楚，但只能描述形狀，存不了照片。

常見的五種格式，就是這三種做法的不同實作：

格式壓縮方式適合不適合
JPEG有損照片；所有瀏覽器都支援，當備援文字、線條（邊緣會出現雜點）、透明背景
WebP有損或無損，支援透明照片、需要透明的圖—
AVIF有損或無損，支援透明照片；同畫質下通常比 WebP 更小編碼比較慢，建置時間較長
PNG無損需要精確像素的截圖、透明的小圖照片（檔案大好幾倍）
SVG向量logo、圖示、簡單插畫；任何大小都清楚，可以用 CSS 改色照片

首頁的主視覺是照片，所以候選是 JPEG、WebP、AVIF。實際差多少，拿這課的練習素材（同一張 1440×960 的拿鐵示意圖）用常見的畫質設定輸出來比：

檔案大小
14-latte-1440.jpg105 KB
14-latte-1440.webp36 KB
14-latte-1440.avif12 KB

這張是用程式畫的、大面積色塊多，AVIF 特別佔便宜；真實照片細節多，差距通常比較小。實際差多少要拿自己的圖、在可接受的畫質下比較，不要只看一個數字。

既然 AVIF 最小，為什麼不全部換成 AVIF 就好？因為不是每個使用者的瀏覽器都看得懂它。WebP 與 AVIF 在所有主要瀏覽器的新版都已經支援（版本與時間見課末），但使用者不一定都更新到新版，看不懂的瀏覽器拿到 AVIF 就顯示不出圖。所以照片的做法是：依序提供 AVIF → WebP → JPEG，讓瀏覽器挑第一個看得懂的，JPEG 是所有瀏覽器都看得懂的最後一道備援。怎麼寫，在〈瀏覽器不支援 AVIF 怎麼辦？〉那一節。

選格式時還有一條跟大小無關的規則：不要把文字做成圖片，例如把「週一公休」寫在 banner 圖上。螢幕閱讀器唸不出來、搜尋引擎讀不到、放大會糊、翻譯工具也翻不了，而且照片格式壓縮時文字邊緣會出現雜點。文字放 HTML，圖片只放圖。

💡 實務上：先跟設計師要對的素材
格式問題常在交付時就決定了：設計師從 Figma 匯出一張 3000px 的 PNG 照片，或把圖示做成 PNG，前端再怎麼優化都事倍功半。修咖啡店首頁時，資深工程師會先講好：照片給原始高解析檔（由建置流程轉格式與尺寸，最後一節會講）、圖示與 logo 給 SVG。另外，SVG 其實是文字檔，裡面可以寫 <script>：使用者上傳的 SVG 如果直接貼進 HTML，或被人從你的網域直接打開，裡面的程式就會執行，資安會關心這點；所以後台上傳通常只開放 JPEG、PNG、WebP。

到這裡，主視覺要準備的檔案已經不只一個：手機和桌機需要不同寬度，不同瀏覽器需要不同格式。可是一個 <img src> 只能寫一個檔案，下一節先解決「不同寬度」。

同一張圖準備好幾種寬度，瀏覽器怎麼挑？srcset 與 sizes

上一節留下的問題是：一個 src 只能寫一個檔案。寫 1440px 的，手機就多下載；寫 480px 的，桌機和高 DPR 的手機就糊。我們需要的是「準備好幾種寬度，讓每台裝置自己挑」，HTML 用兩個屬性做到這件事。

第一個是 srcset：候選圖片的清單，用逗號分隔，每個候選寫成「網址 空白 描述子」。例如 14-latte-480.jpg 480w 裡的 480w 叫 w 描述子，意思是「這個檔案實際寬 480 像素」。注意它寫的是圖檔的真實寬度，不是顯示寬度；寫錯了，瀏覽器會以為檔案比實際大或小而選錯。

有了候選清單，瀏覽器還差一個資訊才能挑。〈手機到底下載了多大的圖〉得出的標準是「需要的像素 = 顯示寬度 × DPR」：DPR 瀏覽器自己知道，但顯示寬度它在挑圖的那一刻還不知道。

原因是瀏覽器開始下載圖片的時間點非常早。瀏覽器收到 HTML 後，會一邊解析、一邊用一個叫預先載入掃描器（preload scanner）的機制往後掃，看到 <img> 就立刻開始下載，不等 CSS 下載完、也不等版面算完。這樣做是為了讓圖片越早開始下載越好；如果每張圖都要等 CSS 到了、版面排好才開始抓，整頁會慢很多。代價是：在這個時間點，瀏覽器根本不知道這張圖最後會被 CSS 排成多寬。

所以需要第二個屬性 sizes：由你事先告訴瀏覽器「這張圖在版面上會顯示多寬」。它是由左到右的「media 條件 寬度」清單，第一個條件成立的就用它的寬度；最後一個不寫條件，當預設。寬度可以用 px、vw、calc()，不能用 %。

主視覺和菜單卡片用的是同一張拿鐵照。這裡先拿菜單卡片示範，因為它的版面會隨視窗寬度從一欄變成三欄，最能看出 sizes 的作用（也是練習 2 的情境）；主視覺的做法完全一樣，只是 sizes 要照主視覺自己的版面寫。

咖啡店菜單的版面是：視窗 ≥ 64em（1024px）時三欄，每張圖約佔視窗的 33%；更窄時一欄，寬度是視窗減掉左右各 16px 的 padding。寫成 sizes 就是 (min-width: 64em) 33vw, calc(100vw - 32px)。完整的 img：

<img
  src="14-latte-960.jpg"
  srcset="14-latte-480.jpg 480w, 14-latte-960.jpg 960w, 14-latte-1440.jpg 1440w"
  sizes="(min-width: 64em) 33vw, calc(100vw - 32px)"
  width="1440" height="960"
  alt="拿鐵，奶泡上有葉子拉花">

這裡的 src 給不支援 srcset 的瀏覽器用，也是沒有任何候選可選時的退路。width、height 是預留空間用的，後面〈圖片還沒到，怎麼先把位置佔好？〉會講。

因為 sizes 是你手寫的版面描述，瀏覽器不會拿它跟 CSS 對照，它必須跟 CSS 的版面一致。如果完全不寫 sizes，瀏覽器就假設圖片佔滿整個視窗，也就是 100vw：桌機三欄、每欄 400px 的卡片，在 1280px 寬的視窗裡會被當成 1280px 寬，下載 1440 的大圖，比需要的大了三倍。

下面把這個步驟寫成程式，換幾種裝置跑一次。執行後看每一行最後的「下載」：同一份 HTML，手機和筆電各選到哪個檔案。

寫完 srcset 和 sizes，還有三個要自己做的判斷。

準備哪些寬度：從「最小顯示寬度 × 1」到「最大顯示寬度 × 2」之間取 3～5 個，間距大約 1.5～2 倍。為什麼上限只到 2 倍？DPR 3 的手機給到 2 倍通常就夠，肉眼很難分辨，檔案卻大很多。寬度間距太密，建置時要產生的檔案變多、快取也比較分散；太疏，選到的圖會比需要的大很多。

sizes 寧可稍大、不要偏小：偏小會選到不夠大的圖而變糊，使用者看得出來；稍大只是多下載一點。上面的 33vw 在 1280px 寬時比實際的 395px 多 7%，可以接受。

改 CSS 版面時要一起改 sizes：sizes 是版面的複本，兩邊不一致時不會報錯，只會默默選錯圖。在 DevTools 選取圖片、輸入 $0.currentSrc 檢查是最直接的方法。

另外還有兩種寫法：只看螢幕密度的 x 描述子，和讓瀏覽器自己量寬度的 sizes="auto"。它們的使用條件比較窄，放在課末。

現在菜單的拿鐵圖能依裝置挑大小了，但 srcset 裡的候選都是同一種格式。如果把 AVIF 也放進 srcset，瀏覽器只會比較寬度，不會檢查自己看不看得懂這個格式。

瀏覽器不支援 AVIF 怎麼辦？手機要換裁切怎麼辦？<picture>

要讓瀏覽器「先看格式、再挑大小」，就要把不同格式分成好幾組候選，讓瀏覽器先挑一組它看得懂的，再在那一組裡用 srcset 與 sizes 挑大小。<picture> 就是這個分組的容器。

<picture> 裡放零到多個 <source>，最後一定是一個 <img>。瀏覽器從上往下找第一個符合的 source，用它的 srcset；都不符合就用 img 的。要分清楚的是：畫在畫面上的永遠是那個 <img>，source 只提供候選檔案。所以 alt（第 3 課）、width、height、class、loading 都寫在 img 上。

把剛才那張菜單圖改成三種格式：

<picture>
  <source type="image/avif"
    srcset="14-latte-480.avif 480w, 14-latte-960.avif 960w, 14-latte-1440.avif 1440w"
    sizes="(min-width: 64em) 33vw, calc(100vw - 32px)">
  <source type="image/webp"
    srcset="14-latte-480.webp 480w, 14-latte-960.webp 960w, 14-latte-1440.webp 1440w"
    sizes="(min-width: 64em) 33vw, calc(100vw - 32px)">
  <img src="14-latte-960.jpg"
    srcset="14-latte-480.jpg 480w, 14-latte-960.jpg 960w, 14-latte-1440.jpg 1440w"
    sizes="(min-width: 64em) 33vw, calc(100vw - 32px)"
    width="1440" height="960" alt="拿鐵，奶泡上有葉子拉花">
</picture>

瀏覽器怎麼判斷一個 source「符合」？靠 type 屬性。它的值是格式的 MIME type（第 1 課教過，伺服器用它說明檔案是什麼格式），例如 image/avif。瀏覽器不支援這個 MIME type 就跳過這個 source，不會下載裡面的任何檔案。如果沒寫 type，瀏覽器會以為自己能用，選了、下載了才發現解不開，圖就破了。

因為瀏覽器用的是「第一個符合的」，順序就是你的偏好：最好的格式放最前面（AVIF → WebP），img 的 JPEG 最後。img 一定要在所有 source 後面；img 放在 source 前面時，後面的 source 全部無效。

還有一點容易漏：每個 source 都要寫自己的 sizes。source 不會沿用 img 的 sizes，沒寫就是 100vw，上一節的問題又回來了。

<picture> 還能解決另一種問題。首頁頂端的店面橫幅，桌機上是一張寬的店面全景；到了手機，整張縮小後人物只剩一個點。這時需要的不是「同一張圖的小版本」，而是另一種裁切：裁成直式、只拍吧檯的版本。不同螢幕用不同裁切或內容的圖，叫做藝術指導（art direction），用 source 的 media 屬性做：

<picture>
  <source media="(min-width: 48em)" srcset="store-wide-1600.jpg 1600w, store-wide-2400.jpg 2400w" sizes="100vw">
  <img src="store-tall-800.jpg" srcset="store-tall-800.jpg 800w, store-tall-1200.jpg 1200w" sizes="100vw"
    width="800" height="1000" alt="吧檯前，咖啡師正在拉花">
</picture>

視窗 ≥ 48em 時用寬圖那組，其他情況用 img 的直式圖。兩種裁切比例不同時，<source> 也可以寫自己的 width、height。

srcset 和 media 都能讓不同螢幕拿到不同的圖，差別在於誰做決定。srcset 是「候選清單」，瀏覽器可以自由選，例如考慮網路狀況或快取裡已經有的檔案；media 是硬性條件，條件成立瀏覽器就一定要用那個 source。所以判斷方式是：只是大小不同，用 img 的 srcset，把選擇權留給瀏覽器；只有裁切或內容不同，才用 media。

💡 實務上：藝術指導會多出一份工
咖啡店首頁的活動橫幅最常遇到：行銷給一張寬圖，上了手機文字和主角都太小。要用 media 換裁切，代表每次換活動都要準備兩張圖，後台也要有兩個上傳欄位。所以先跟 PM、行銷確認「誰負責出手機版的圖、忘了給怎麼辦」（例如沒有手機版就退回寬圖）。只是大小不同的商品照不需要這樣做，srcset 就夠了。

到這裡，每台裝置已經能拿到大小與格式都合適的檔案；主視覺照同樣做法、換上自己的 sizes，「主視覺太大」就解決了。但店長的第二個抱怨「文字往下跳」，跟下載多少無關：檔案再小，下載完的那一刻還是會把文字往下推。

圖片還沒到，怎麼先把位置佔好？width、height 與 aspect-ratio

文字為什麼會往下跳？因為瀏覽器排版時，圖片多半還沒下載完。它不知道圖片多大，只能先當成 0 高度，把下面的文字排在緊接著的位置；圖片到了才撐開，下面的內容全部往下移。

這種跳動不只是不好看。使用者正要點「加入購物車」，上面的圖片剛好載完把按鈕往下推，就點到別的東西。Google 用一個指標衡量這種「畫面元素被推動」的程度，叫累計版面位移（CLS, Cumulative Layout Shift），數字越大代表跳得越多、越嚴重。CLS 怎麼計分、合格門檻在第 20 課，這裡先處理最常見的原因：圖片沒有預留空間。

要預留空間，瀏覽器需要在圖片下載前就知道它的高度。修法是在 <img> 寫上圖檔的 width 與 height 屬性（整數、不寫單位）。現代瀏覽器會用這兩個值算出長寬比，等同於 CSS 的 aspect-ratio: auto 1440 / 960。有了長寬比，只要知道圖片排多寬，就能算出它多高，圖片還沒下載就能先把那塊空間留下來。

但這兩個屬性不只提供比例，也會被當成 CSS 寬高的提示：寫了 width="1440" height="960"，CSS 只寫 width: 100%，寬度被 CSS 縮小了，高度卻仍然是屬性的 960px，圖就被拉長。要讓高度改由「寬度 × 比例」算出來，一定要搭配：

img {
  max-width: 100%;
  height: auto;   /* 高度由寬度和長寬比算出來 */
}

這兩個屬性寫的是什麼值也要注意。width、height 兩個都要寫，只寫一個算不出比例。寫的是圖檔的實際比例，不必是顯示大小，因為顯示大小交給 CSS；用 srcset 時寫最大那張的寬高，同一組候選的比例都一樣。

那能不能直接在 CSS 寫死高度，例如 height: 200px？寬度一變，圖就被壓扁或拉長。只有在你確定要把圖裁成固定高度時才這樣做，而且要同時寫 object-fit: cover：圖片等比例放大到填滿這個框，超出的部分裁掉，不會變形。

有些要預留空間的東西不是 <img>，沒有 width、height 屬性可以寫，這時直接用 CSS 的 aspect-ratio：例如嵌入的地圖 iframe { width: 100%; aspect-ratio: 16 / 9 }、載入中的骨架畫面、還沒載入的影片區塊。

預留空間還跟下一節的延遲載入有關。延遲載入的圖片要等瀏覽器判斷「它快進入畫面了」才下載，而這個判斷靠的是圖片在版面上的位置。如果圖片沒有尺寸，它就是 0 高度，一堆 0 高度的圖疊在一起，全部都「在畫面內」，結果一起被下載，延遲載入就失效了。這正好帶到 DevTools 找到的第三個問題：菜單的 8 張圖為什麼一打開就全部下載。

主視覺怎麼先到、菜單的圖怎麼晚點下載？

瀏覽器預設看到 <img> 就下載，不管它在首屏還是頁面最下面。咖啡店首頁一打開，主視覺和菜單的 8 張圖同時開始下載，手機網路的頻寬被 9 張圖分掉，使用者第一眼最想看到的主視覺反而要排隊。我們要的是反過來：首屏最重要的圖最先到，使用者還看不到的圖晚點再說。

「最重要的圖」有一個指標可以衡量。最大內容繪製（LCP, Largest Contentful Paint）量的是：首屏裡最大的那塊內容（通常是主視覺圖或大標題）畫出來的時間，Google 建議在 2.5 秒內。使用者覺得「頁面出來了」，多半就是這塊內容出現的時候。首頁的主視覺圖幾乎都是 LCP 元素，它下載得越早，LCP 越好；其他圖片則應該讓路。

讓路的方式有兩種。一種是延遲載入（lazy loading）：在 img 寫 loading="lazy"，瀏覽器先不下載，等使用者捲到接近畫面時才下載，使用者沒捲到就不花流量。另一種是調整下載優先順序：fetchpriority 屬性提示瀏覽器這個資源要排前面（high）還是後面（low）。依圖片在頁面上的位置，各自這樣寫：

哪種圖怎麼寫為什麼
首屏的 LCP 圖（主視覺）不加 loading="lazy"；加 fetchpriority="high"lazy 要等版面算完、確認在畫面內才開始下載，比一般圖片晚。high 讓它排在其他圖片前面
首屏的其他圖片什麼都不加（預設 loading="eager"）本來就要馬上看到
首屏以下的圖片loading="lazy"、decoding="async"捲到接近畫面才下載。decoding="async" 讓瀏覽器先畫其他內容，不等這張圖解碼
輪播的第 2 張以後、分頁裡的圖loading="lazy"，必要時 fetchpriority="low"不一定會被看到

表中的「解碼」是指：瀏覽器下載到的是壓縮過的檔案，要先解碼成一個個像素才能畫到畫面上；圖越大，解碼花的時間越久。decoding="async" 讓這段工作不卡住其他內容的繪製。

表裡最容易用錯的是第一列。直覺上「lazy 會比較省」，但 lazy 的圖片要等版面算完、確認它在畫面附近才開始下載；主視覺本來就在首屏，遲早都要下載，加了 lazy 只是讓它晚起跑，LCP 就變慢。這兩個屬性在不支援的瀏覽器上會被忽略，照一般方式下載，不會出錯（各自的支援度見課末）。

fetchpriority="high" 只給一張（最多兩三張）：全部都 high，就沒有誰比較優先。哪張是 LCP 不要猜，用 DevTools 的 Performance 面板錄一次載入，會標出 LCP 元素；第 20 課會詳細教。

還有一個判斷：「首屏」在哪裡會隨裝置不同。同一張圖在桌機在首屏、在手機可能在第二屏。實務上的判斷是「在任何一種常見裝置上可能出現在首屏的，就不要 lazy」。lazy 用錯在首屏的代價（LCP 變慢）比少 lazy 一張的代價（多下載一張圖）大。

這套規則只對寫在 HTML 裡的 <img> 有效。咖啡店首頁的首屏還有一張門市照片，是用 CSS 背景圖放上去的，它完全不在上面的規則裡。

門市照片用 CSS 背景圖，問題在哪？

寫在 CSS 裡的 background-image，預先載入掃描器看不到：它只掃 HTML，而背景圖的網址藏在 CSS 裡。瀏覽器要先下載 CSS、算出哪些元素套用了這條規則，才開始下載圖片，起跑比 <img> 晚了一大段。而且背景圖沒有 alt，螢幕閱讀器不知道那裡有張門市照片；也沒有 srcset 與 sizes，不能依裝置挑大小；也不能 lazy。所以：

  • 有內容的圖片（商品照、門市照、主視覺）用 <img>。要「填滿容器、裁掉多的」的效果，用 <img> 加 object-fit: cover。
  • 純裝飾（花紋、漸層）才用 CSS 背景。

如果真的要把首屏大圖做成背景（例如舊專案一時改不動），就要主動告訴瀏覽器「這張圖一開始就要下載」。<link rel="preload"> 寫在 head 裡，讓瀏覽器在讀到 CSS 之前就提早下載首屏一定用到的資源：

<link rel="preload" as="image"
  imagesrcset="hero-800.avif 800w, hero-1600.avif 1600w"
  imagesizes="100vw"
  type="image/avif"
  fetchpriority="high">

imagesrcset、imagesizes 跟 img 的 srcset、sizes 用同一套選圖規則。圖片本來就寫在 HTML 的 <img> 裡、很早就被看到時，不需要 preload，加了反而多一個要維護的地方。preload 會跟其他資源搶頻寬，取捨在第 21 課。

💡 實務上：列表元件最容易全部 lazy
菜單、商品列表通常是一個元件跑迴圈，寫的人順手給每張圖都加上 loading="lazy"，結果首屏那幾張也被延遲，LCP 變慢。常見做法是讓元件接一個參數（例如前幾筆 eager，第一張加 fetchpriority="high"），由使用它的頁面決定。Code review 看到列表圖片時，資深會先問：「這個列表會出現在首屏嗎？」

到這裡，首頁的 HTML 已經改完：主視覺用 <picture> 提供三種格式、三種寬度，並優先下載；菜單延遲載入；每張圖都預留了空間。但 HTML 裡引用的那些 14-latte-480.avif、14-latte-960.webp……還要有人做出來。

這麼多圖檔由誰產生？上線後怎麼快取？

一張主視覺要 3 種寬度 × 3 種格式 = 9 個檔案，菜單每個品項也一樣。沒有人會手動輸出這些檔案，常見的做法有兩種：

  • 建置時產生：用 Node 的影像處理套件 sharp，在部署前把原圖轉成各種尺寸與格式。Vite、Nuxt、Next.js 都有包好的外掛或元件做這件事。
  • 圖片 CDN：CDN 是分布在各地的快取伺服器（Node 課第 15 課介紹過）。圖片 CDN 讓你只上傳一張原圖，網址帶參數要尺寸與格式（例如 /latte.jpg?w=960&format=avif），CDN 即時轉檔並快取。Cloudinary、imgix 與各家雲端的影像服務都是這種。不用改建置流程，代價是費用與對廠商的依賴。

建置時產生的做法，用 sharp 寫起來大概是這樣（示意，這課不練習）：

import sharp from 'sharp'

for (const w of [480, 960, 1440]) {
  await sharp('src/latte.jpg').autoOrient().resize({ width: w }).avif({ quality: 50 }).toFile(`dist/latte-${w}.avif`)
  await sharp('src/latte.jpg').autoOrient().resize({ width: w }).webp({ quality: 80 }).toFile(`dist/latte-${w}.webp`)
  await sharp('src/latte.jpg').autoOrient().resize({ width: w }).jpeg({ quality: 80 }).toFile(`dist/latte-${w}.jpg`)
}

每個寬度輸出三種格式，正好是前面 <picture> 需要的那 9 個檔案。其中 autoOrient() 跟照片裡的 EXIF 有關。EXIF 是相機或手機寫在照片檔裡的中繼資料，例如拍攝時間、相機型號、拍攝地點（GPS）。sharp 輸出時預設會移除這些資料，手機照片裡的拍攝地點不會被公開。但手機直拍的照片，「要轉幾度才是正的」也只記在 EXIF 的 Orientation 標記裡，資料被移除後圖就變成橫躺的；所以先呼叫 autoOrient()，依 Orientation 把圖轉正再處理。

檔案做好、部署上線後，還剩最後一件事：讓回訪的使用者不必再下載一次。圖片很少變，適合讓瀏覽器長期快取，做法跟 Node 課第 15 課的 JS、CSS 一樣：檔名加上內容的 hash（latte-960.3f9a2c.avif），回應帶 Cache-Control: public, max-age=31536000, immutable，告訴瀏覽器「這個網址的內容一年內都不會變，不用回來問」。換圖時內容變了、hash 也跟著變，HTML 裡的網址跟著換，瀏覽器會去抓新網址，舊快取自然不再使用。

反過來說，檔名不帶 hash 的圖（例如 CMS 上傳、網址固定的）不能這樣設：網址沒變，瀏覽器就繼續用快取裡的舊圖，換了圖使用者一年都看不到。

💡 實務上：使用者上傳的圖不會經過建置流程
建置時產生的做法只處理 repo 裡的圖；咖啡店後台讓店長上傳的商品照、會員頭像，要在上傳時由後端用 sharp 轉檔，或交給圖片 CDN。上傳端要設檔案大小與格式上限，否則店長直接傳一張手機原圖，整個菜單頁就被拖慢，等於這課修好的首頁又回到原點。上傳處理同樣要移除 EXIF、先 autoOrient()：如果省事直接存原檔，頭像裡的 GPS 等於公開使用者住哪裡。選圖片 CDN 前，先問清楚流量計費方式和換廠商的成本。

練習

練習 2、3 的預覽只能載入題目提供的圖檔（放在 web/assets/），網址直接寫檔名，例如 src="14-latte-960.jpg"。素材是程式畫的示意圖，菜單的各品項都用同一張代替。

練習 1：把瀏覽器選圖的規則寫成程式。pickCandidate(candidates, slotCssPx, dpr)：每個候選的密度＝w ÷ slotCssPx，選密度 ≥ dpr 的候選裡最小的那個，沒有就選最大的，回傳它的 url（候選至少一個，沒有照順序排、寬度不重複）。buildSrcset(base, widths, ext)：產生 srcset 字串，例如 latte-480.avif 480w, latte-960.avif 960w：寬度由小到大、重複的只留一個。兩個函式都不能改到傳入的陣列。

練習 2：菜單格線的 CSS 是固定的：64em（1024px）以上三欄，以下一欄，左右各 16px padding（看 CSS 分頁）。三張卡片現在都直接載入 1440px 的 JPEG。改成 <picture>：依序提供 AVIF、WebP 的 <source>，最後是 JPEG 的 <img>（src 用 14-latte-960.jpg）；每個都用 w 描述子列出 480、960、1440 三個尺寸（檔名 14-latte-寬度.格式），寫出跟版面一致的 sizes；img 保留原本的 alt，加上 width 與 height。

練習 3：修首頁的 LCP 與 CLS（預覽 375×700 是手機首屏）。主視覺 .hero 是首屏最大的元素，現在卻 loading="lazy"、沒有尺寸；首屏以下的 8 張菜單圖一打開就全部下載、也沒有尺寸；門市照片用 CSS 背景圖放在首屏。改成：主視覺不 lazy、加 fetchpriority="high"；菜單圖加 loading="lazy" 與 decoding="async"；門市照片改成 <img class="store-photo" src="14-store-800.jpg"> 並寫 alt；每張圖都寫 width 與 height（主視覺 1440×960、門市 800×600、菜單 480×320），而且顯示時不能變形（照素材比例顯示；想要固定高度裁切，就搭配 object-fit: cover），圖片還沒下載時就要佔好空間。

練習 4：<img> 寫了 srcset（w 描述子）卻沒寫 sizes，瀏覽器會假設圖片顯示多寬？

✓ b：瀏覽器在 CSS 套用、版面算好之前就要選圖，只能靠 sizes；沒寫時預設 100vw，桌機上的多欄卡片常因此下載過大的圖。a 錯：圖檔寬度已經寫在 w 描述子裡，那是候選的大小，不是顯示大小。c 錯：選圖時 CSS 通常還沒套用（只有 sizes="auto" 搭配 lazy 才會用實際版面寬度）。d 錯：sizes 沒有這個預設值；300px（×150px）是 iframe 這類元素沒有寬高時的預設大小，跟 srcset 選圖無關。

練習 5：首屏的主視覺圖加了 loading="lazy"，會怎樣？

✓ b：lazy 的圖片要等版面算完、確認在畫面附近才開始下載，比一般圖片晚起跑；主視覺通常就是 LCP 元素，它晚到 LCP 就晚。a 錯：首屏的圖遲早都要下載，lazy 只省得到首屏以下的。c 錯：「在首屏」要等版面算好才知道，這段等待就是延遲。d 錯：有寫 width、height 時 lazy 不影響 CLS；受影響的是 LCP。

練習 6：img 已經用 CSS 設定 width: 100%; height: auto，為什麼還要寫 width 與 height 屬性？

✓ b：瀏覽器用這兩個屬性算出 aspect-ratio，配合 height: auto，圖片還沒到就有正確的高度；沒有屬性時高度是 0，圖片到了才撐開。a 錯：搜尋引擎不靠這兩個屬性理解圖片，alt 與周圍文字才是。c 錯：用屬性算長寬比是現代瀏覽器才有的行為，舊瀏覽器反而沒有。d 錯：選圖看的是 srcset 與 sizes。

常見錯誤

  • sizes 跟 CSS 不一致：版面改成三欄，sizes 還是 100vw，桌機每張卡片都下載最大的圖。改版面時同時改 sizes，用 $0.currentSrc 確認。
  • source 沒寫 sizes，或沒寫 type：source 不沿用 img 的 sizes；沒寫 type，不支援的瀏覽器會選到解不開的格式。
  • LCP 圖片加 lazy：常見於「全站的 img 元件預設 lazy」。元件要能讓呼叫的地方關掉 lazy、加上 fetchpriority="high"。
  • 沒有 width／height，或只寫一個：圖片載入後把內容往下推（CLS）；lazy 的圖還可能全部擠在畫面內而一起被下載。
  • 寫了 width／height 但 CSS 沒有 height: auto：寬度被 CSS 縮小、高度還是屬性的值，圖被拉長。
  • 首屏的重要圖片用 CSS 背景：預先載入掃描器看不到，下載較晚，也沒有 alt。重要圖片用 <img> 加 object-fit。
  • 每張圖都 fetchpriority="high"：大家都優先就沒有優先。只給 LCP 那一張。

補充與查表

這一節收的是主線用不到、但寫程式或查資料時會遇到的細節，查表用，不用背。

x 描述子：固定大小的圖

srcset="logo.png 1x, logo@2x.png 2x" 這種寫法用的是 x 描述子，只看螢幕密度，不看版面寬度：DPR 1 的螢幕拿 logo.png，DPR 2 的拿 logo@2x.png。適合固定大小的圖（例如 120px 寬的 logo），不需要 sizes；不適合會隨版面伸縮的照片，因為它不知道圖片在版面上變寬或變窄了。

sizes="auto"

讓瀏覽器用實際版面寬度選圖，不必手寫版面描述。但只能搭配 loading="lazy"：延遲載入的圖要等版面算好才下載，這時瀏覽器已經知道它多寬。寫法是 sizes="auto, (min-width: 64em) 33vw, 100vw"，不支援的瀏覽器會用後面的清單。目前還不是所有瀏覽器都支援，這課只提到它。

小結

  • 先量再改：Network 面板看實際下載量，圖檔寬度約等於「顯示寬度 × DPR」才合理。DPR 是一個 CSS px 對應幾個實體像素。
  • 像素數決定後再選格式：照片用 AVIF／WebP 並留 JPEG 備援，圖示用 SVG，文字不做成圖片。
  • srcset 用 w 描述子列出真實寬度，sizes 描述版面寬度；因為預先載入掃描器在 CSS 載入前就要選圖，sizes 必須跟 CSS 一致，沒寫就當成 100vw。
  • <picture> 的 source 從上往下比對，用 type 選格式、用 media 換裁切；img 在最後，帶 alt、width、height。只是大小不同就用 srcset。
  • width、height 屬性加上 CSS height: auto 預留空間，避免 CLS；非圖片的容器用 aspect-ratio。
  • LCP 圖不 lazy、加 fetchpriority="high"；首屏以下 lazy；有內容的圖片不用 CSS 背景，不得已時用 preload。
  • 圖檔由建置流程或圖片 CDN 產生；檔名帶 hash 才能 immutable 長期快取。
