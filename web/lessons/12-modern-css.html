階段 3：現代 CSS 與視覺品質 · 第 12 課

現代 CSS：container queries、:has()、nesting 與功能支援檢查

咖啡店首頁改版，你接到一張單：商品卡片元件原本只放在首頁主欄的「本週推薦」，設計師要把同一張卡片也放進右邊 300px 的側欄「店長也推薦」，結帳頁的發票區塊也要改成「勾選需要統一編號才出現統編欄位」。上線後，側欄的卡片文字被擠成一直條。過去的解法是多寫一個 .card--narrow，或在 Vue 裡用 JavaScript 量側欄寬度再加 class；這次技術主管要求只靠 CSS 解決，不再加只為了樣式存在的 class 和 JavaScript。

這課就做完這張單：先讓卡片依自己所在欄位的寬度切換版面，再讓卡片和發票區塊依「裡面有什麼、勾了什麼」改變樣式，接著把越寫越散的卡片 CSS 收回一處，最後回答 PR 審查者一定會問的問題：這些新功能，使用者的瀏覽器支援嗎？

這課的路線：
  1. 側欄的卡片為什麼擠爆、怎麼讓卡片看自己所在欄位的寬度：media query 為什麼答不了這題，container query 怎麼答（開場問題的最小答案）。
  2. 沒照片的新品卡片、勾選才出現的統編欄位：:has() 怎麼依「裡面有什麼」選中外層元素，以及它的代價。
  3. 卡片的規則散在檔案各處：原生 CSS nesting 怎麼把它們收回一起，& 的意思和權重跟 Sass 差在哪。
  4. 審查者問「使用者的瀏覽器支援嗎」：Baseline 怎麼看、不支援時怎麼用 @supports 退回能用的版本、PR 說明要回答哪些問題。
這課會用到：
  • 第 11 課的 media query 與 mobile-first：基本樣式給窄畫面，@media (width >= 40em) 這類條件成立時才疊加寬螢幕的樣式。
  • 第 9 課的 grid-template-columns：定義格線的欄，例如 200px 1fr 是左欄固定 200px、右欄分掉剩下的寬度。
  • 第 6 課的權重計算：權重寫成 (ID, class, 型別) 逐欄比較；:is() 的權重取參數裡最高的那一個。

側欄的卡片為什麼擠成一直條？

先把出事的現場看清楚。首頁有兩欄：主欄放「本週推薦」，右邊 300px 的側欄放「店長也推薦」，兩處用同一個商品卡片元件。卡片的 CSS 照第 11 課的 mobile-first 寫法：窄的時候圖片在上、文字在下，寬螢幕時改成圖片在左、文字在右。卡片的 HTML 長這樣：

<article class="card">
  <img src="yirgacheffe.jpg" alt="衣索比亞耶加雪菲咖啡豆">
  <div class="card__body">
    <h2>衣索比亞 耶加雪菲</h2>
    <p>柑橘與花香，手沖一杯 180 元。</p>
  </div>
</article>

img 和 .card__body 都是 .card 的直接子元素：卡片是一個兩格的 grid，圖片一格、.card__body（卡片的文字區）一格。這種 區塊__元素 的命名方式，在後面 nesting 一節會解釋。寬螢幕的規則是：

@media (min-width: 768px) {
  .card { grid-template-columns: 200px 1fr; }
}

舊專案常見這種 min-width 寫法，意思等同第 11 課的 (width >= 768px)，兩者沒有差別。這條規則在只有主欄的舊首頁上沒問題。改版後，在 1280px 寬的桌機打開首頁：主欄的卡片正常左右排；側欄的卡片也套用了這條規則，因為 media query 問的是「視窗有沒有 768px」，1280px 的視窗當然有。可是側欄只有 300px，扣掉 200px 的圖片欄，文字只剩六十幾 px，一行只塞得下兩三個字。

把斷點改大、或幫側欄的卡片多寫一條覆蓋規則，都只是把問題往後推。卡片真正需要知道的是「我被放在多寬的地方」，而 media query 從頭到尾只知道視窗多寬，回答不了這個問題。同一個元件之後還會被放進彈出視窗、購物車旁的推薦加購、後台的兩欄商品列表，每個地方的寬度都跟視窗沒有固定關係。所以我們需要一種條件，問的不是視窗，而是卡片外面那一層。

怎麼讓卡片看自己所在欄位的寬度？container queries

CSS 提供的就是這種條件，叫容器查詢（container query）：依某個祖先元素的尺寸套用樣式。這個被拿來量尺寸的祖先叫查詢容器（query container），元素要先宣告自己是查詢容器，裡面的元素才能問它多寬。寫法跟 media query 很像，分三步：

/* 1. 指定查詢容器：卡片外層的欄位 */
.main,
.side {
  container-type: inline-size;
}

/* 2. 寫條件：最近的容器寬度 ≥ 28rem 時 */
@container (width >= 28rem) {
  /* 3. 這裡的規則套用在容器「裡面」的元素 */
  .card {
    grid-template-columns: 200px 1fr;
  }
}

第一步的 container-type: inline-size 把主欄和側欄各自變成查詢容器。第二步的 @container 條件沒寫要問誰，瀏覽器就從卡片往上找最近的查詢容器：卡片在主欄裡，量的是主欄的寬度；在側欄裡，量的是側欄的寬度。所以同一份卡片 CSS 只寫一次，放到哪裡都會自己調整。回到開場的 1280px 桌機：主欄約 900px，超過 28rem，卡片左右排；側欄 300px，不到 28rem，卡片維持上下排，擠爆的問題解決了。

條件的寫法跟第 11 課的範圍語法一樣：(width >= 28rem)、(20rem <= width < 40rem)。斷點用 rem，理由也一樣：使用者調大預設字級時，斷點跟著文字一起變大，文字變大、一行放得下的字變少時，卡片會提早改回上下排。斷點的數字也要重新想：原本的 768px 是「視窗」的斷點，現在量的是欄位，28rem（預設字級下 448px）是「圖片 200px 加上一段讀得下去的文字」需要的寬度。

為什麼 container-type 要設在外層，而不是卡片自己身上？

第一次寫的人常把 container-type 直接設在 .card 上，覺得「卡片看自己多寬」比較直覺。要理解為什麼不行，得先看瀏覽器怎麼算出容器的寬度。

瀏覽器必須先知道容器多寬，才能決定裡面的元素套用哪些樣式。如果裡面元素的樣式反過來又能改變容器的寬度，就會繞圈：容器變寬 → 卡片改成左右排 → 卡片內容變窄 → 容器跟著變窄 → 卡片又改回上下排 → 容器又變寬……永遠算不完。為了切斷這個迴圈，container-type: inline-size 會讓容器的寬度不看內容決定，只看外面給它多少空間。這個「把元素跟它的內容隔開來計算」的機制在 CSS 裡叫 containment（限制）。

containment 帶來兩個代價，都是實際會踩到的：

  • 元素沒辦法查詢自己。@container 裡的 .card 規則，問的永遠是 .card 的祖先。把 container-type 設在 .card 身上，再寫 @container (…) { .card { … } }，條件查的是 .card 外面那一層容器，不是它自己；外面沒有容器的話，整段條件就不會成立。所以容器設在外層：欄位、列表的格子、包住元件的 wrapper。
  • 寬度由內容決定的元素不能當容器。既然容器的寬度不看內容，原本「靠內容撐開」的元素就沒有寬度來源：display: inline-block、沒有設寬度的 absolute 元素、只靠內容撐開的 flex 子元素，設成容器後寬度會縮成 0。block 元素、grid 的欄、flex: 1 的子元素寬度都來自父層，可以放心用。這課的 .main 和 .side 是 grid 的欄，正好符合。

container-type 常用的值有三個。差別在容器的哪個方向被限制住、因此能被查詢：

container-type可以查詢什麼時候用
normal（預設）不能查尺寸一般元素
inline-size寬度（水平書寫時）幾乎所有情況。高度仍然由內容撐開
size寬度與高度容器本身有明確高度時（例如固定高度的面板）。沒設高度的話，容器高度不看內容，塌成 0，內容溢出到外面

商品卡片只需要知道欄位多寬，用 inline-size。容器一層包一層、需要指定問哪一個時，可以幫容器取名字，細節見課末「補充與查表」。

品名字級怎麼跟著欄位平滑變化？cqi 單位

版面切換解決了，但品名還有一個小問題：主欄和側欄的品名一樣大，主欄的看起來太小、側欄的又顯得太擠。用 @container 多寫幾個斷點調字級可以，只是每多一種寬度就多一條規則。

更直接的做法是讓字級本身就以容器寬度為單位。容器查詢單位（container query units）是以查詢容器的尺寸為基準的長度，最常用的是 cqi：1cqi 是容器 inline 方向（水平書寫時就是寬度）的 1%。容器變寬，用 cqi 寫的尺寸就跟著連續變大，不用一個斷點一個斷點寫：

.card h2 {
  /* 最小 1.125rem、最大 1.75rem，中間跟著容器寬度 */
  font-size: clamp(1.125rem, 4cqi, 1.75rem);
}

clamp(最小, 理想, 最大) 先算中間的理想值，小於最小值就用最小值，大於最大值就用最大值（細節在第 13 課）。代入兩個欄位：主欄約 900px，4cqi 是 36px，被上限截在 28px；側欄 300px，4cqi 是 12px，被下限拉到 18px。

上下限一定要用 rem。只用 cqi 的字級只跟著容器寬度走，使用者在瀏覽器設定裡調大預設字級時，它不會跟著變大，視力不好的客人就看不清楚。rem 的上下限讓字級至少跟著使用者設定走。另外 cq 單位要有查詢容器才會照預期運作，所以外層一定要真的設了 container-type；附近沒有容器時的行為見課末。

那 media query 還要用嗎？兩者怎麼分工

container query 解決了卡片的問題，但不代表 media query 該全部換掉。判斷方式是問「這個樣式取決於什麼」：

需求用原因
整頁骨架：要不要有側欄、導覽列展開或收合media query頁面本身就是看視窗
可重複使用的元件：卡片、商品列表、表單區塊container query元件不知道自己會被放在哪裡
使用者偏好與裝置能力：prefers-reduced-motion、hover、pointermedia query這些是裝置與使用者的設定，容器沒有

咖啡店首頁就是兩者一起用：「寬螢幕才出現 300px 側欄」是頁面骨架，留在 media query；卡片內部的版面改用 container query。這樣分工之後，整體的 media query 數量會少很多，因為每個元件不再各自寫一套視窗斷點。

💡 實務上：共用元件的 RWD 交給 container query
咖啡店網站的商品卡片會同時出現在首頁主欄、購物車旁的「推薦加購」側欄、後台的商品管理列表，這種跨頁面共用的 Vue 元件最適合 container query。團隊要先講好 container-type 由誰設：通常是版面（欄位、列表格子）負責，元件只寫 @container。最常見的坑是忘了設容器，@container 整段不生效也不報錯，卡片只會一直停在預設樣式。資深工程師驗收元件時，會把它放進最窄和最寬的位置各看一次（或在 DevTools 拖拉欄寬），而不是只縮放瀏覽器視窗。

卡片現在會看欄位寬度了。但測試資料一換成真實商品，又冒出一個 container query 管不到的問題：有幾樣新品還沒拍照。

沒照片的新品卡片、勾選才出現的統編欄位：怎麼依「裡面有什麼」選元素？

沒照片的卡片只有 .card__body 一個子元素。在主欄裡，@container 條件成立，卡片照樣套上 grid-template-columns: 200px 1fr，唯一的子元素被放進第一欄，也就是 200px 的圖片欄：品名和說明擠在左邊 200px，右邊整片空白。卡片需要的條件是「裡面有圖片時才左右排」，這跟寬度無關，是看內容。

CSS 選擇器過去一直只能往下、往後選：「.card 裡面的 img」很容易，「有 img 的 .card」卻做不到。所以以前只能在 Vue 裡多綁一個 class：

<article class="card" :class="{ 'has-image': item.image }">

這樣資料跟樣式綁在一起，每個用到卡片的地方都要記得加，忘了一處就出錯，也正好違反這張單「不加只為樣式存在的 class」的要求。

現在 CSS 有了關係偽類 :has()，專門回答這種問題。A:has(B) 選中的是 A，條件是從 A 的位置出發能找到符合 B 的元素。括號裡的選擇器是「相對於 A」來看的：沒寫連接符號時代表 A 的後代，寫 > 就是直接子元素。把卡片的規則改成只對有圖片的卡片生效：

@container (width >= 28rem) {
  .card:has(> img) {
    grid-template-columns: 200px 1fr;
  }
}

沒照片的卡片不符合 :has(> img)，維持一欄，文字占滿整張卡片。之後商品補上照片，DOM 裡多了 img，同一條規則自動成立，Vue 那邊什麼都不用改。

表單狀態也是「裡面有什麼」：統編欄位

卡片的例子裡，條件（有沒有圖）和要改的元素（卡片）是父子關係。:has() 真正把以前做不到的事變成做得到，是在條件和目標不相鄰的時候，結帳頁的發票區塊正是這種情況：

<fieldset class="invoice">
  <p class="check">
    <input id="need-tax" type="checkbox">
    <label for="need-tax">需要統一編號</label>
  </p>
  <p class="hint">公司報帳用，個人不用填。</p>
  <p class="field tax-id">…統編欄位…</p>
</fieldset>

勾選框和統編欄位中間隔著一段說明。兄弟選擇器 + 只能選「緊接在後面」的那一個，~ 只能選「後面的兄弟」；勾選框被包在 p.check 裡，它的兄弟只有那個 label，統編欄位根本不是它的兄弟，兩者都構不著。而且兄弟選擇器只能往後選，設計稿哪天把勾選框移到欄位下面，就完全沒辦法了。

換個角度，從兩者共同的祖先出發：「這個 fieldset 裡有被勾選的 checkbox」→ 選中 fieldset 裡的統編欄位。這樣跟 DOM 怎麼排無關：

.tax-id {
  display: none;              /* 預設隱藏：看不到，也 Tab 不到 */
}
.invoice:has(#need-tax:checked) .tax-id {
  display: block;
}

隱藏欄位要用 display: none（或 HTML 的 hidden 屬性）。只用 opacity: 0 的話，欄位看不到卻還能用 Tab 聚焦，鍵盤使用者會停在一個看不見的地方，不知道自己在填什麼。

同一個發票區塊還有驗證：統編格式錯時，整個 fieldset 的邊框要變紅。第 4 課講過，Vue 驗證失敗時本來就該在欄位上設 aria-invalid="true"，螢幕閱讀器靠它報出「無效」。CSS 直接用同一個屬性決定外觀，不用再另外維護一個 .has-error class：

.invoice:has([aria-invalid="true"]) {
  border-color: var(--error);
}

這是一種好的分工：狀態只存在一個地方（aria-invalid），外觀和無障礙資訊都從它來，兩者不會不同步。如果另外維護 .has-error，總有一天會出現「框變紅了，螢幕閱讀器卻沒說錯在哪」或反過來的情況。

到這裡用過的寫法，加上幾種常見變化，整理成一張表。查表用，不用背：

選擇器選中
.card:has(img)裡面有圖片的卡片（任何深度）
.card:has(> img)直接子元素是圖片的卡片
.card:not(:has(img))沒有圖片的卡片
h2:has(+ p)後面緊接著段落的 h2（往後看兄弟）
.invoice:has(#need-tax:checked) .tax-id「需要統一編號」被勾選時，同一個 fieldset 裡的統編欄位
.invoice:has([aria-invalid="true"])裡面有欄位被標成驗證失敗的 fieldset

用 :has() 要付出什麼？權重、寫錯一個字、效能

:has() 很方便，但它有幾個特性會在 code review 和正式環境被問到，用之前要清楚。

權重：:has() 跟 :is()、:not() 一樣，本身不算權重，取參數裡最高的那一個（第 6 課）。.card:has(img) 是 .card 的 (0,1,0) 加上 img 的 (0,0,1)，共 (0,1,1)。要注意的是「參數裡最高的」不看實際找到誰：參數寫成 :has(#promo, img) 就是 (1,1,0)，即使實際找到的是 img。這會讓這條規則意外地很難被別處覆蓋。

寫法限制：:has() 裡面不能再放 :has()，也不能放 ::before 這類偽元素。

不寬容：:has() 的參數裡只要有一個選擇器寫錯，整條規則都會被丟掉，而且不會有錯誤訊息。不支援 :has() 的瀏覽器也一樣，整條規則等於不存在。這就是統編欄位的隱憂：顯示它的規則被丟掉，隱藏它的規則卻還在，欄位就永遠不會出現。所以要讓「沒套用 :has 的樣子」也能用，做法在後面的 @supports 一節。

效能：一般的選擇器只要看元素本身、它的祖先和前面的兄弟（都是 DOM 裡在它之前或之上的元素），:has() 卻要往元素「裡面」或後面找。DOM 一改變（勾選、輸入、Vue 重新渲染），瀏覽器就要重新確認哪些元素的 :has() 還成立。:has() 前面那個元素叫錨點（anchor），錨點越大、參數越寬，要檢查的範圍越大。.invoice:has(…) 只牽動一個 fieldset；body:has(…)、:has(*) 讓整頁都跟著重算，在大型列表頁會拖慢互動。錨點盡量貼近要改的元素。

可讀性：:has() 適合「外觀跟著內容或狀態變」，像有沒有圖、有沒有勾選、有沒有驗證失敗。條件牽涉商業邏輯（會員等級、庫存）時，在 Vue 裡算出一個有名字的 class 比較好讀、好測，看 class 名稱就知道為什麼變樣。

💡 實務上：改不到 HTML 時，:has() 最好用
上面的例子都是自己寫的元件，但 :has() 更常救急的是改不到 HTML 的內容：CMS 裡編輯貼上的文章、第三方嵌入或套件產生的標記。例如咖啡店部落格文章裡放了圖片的段落想改成滿版，寫 .article p:has(> img) 就好，不用請編輯手動加 class，也不用改 CMS 模板。自己寫的元件則先問一句：這個狀態 Vue 本來就知道嗎？知道就直接綁 class，:has() 留給狀態只存在 DOM 上的情況。Code review 看到 :has()，資深工程師會確認錨點不是 body 或整個列表，並在 DevTools 把這條規則取消勾選，確認不支援時畫面仍然能操作。

功能都做到了，但打開卡片的 CSS 檔，跟卡片有關的規則已經散成好幾處：基本樣式、.card img、.card h2、檔案後面的 @container 區塊、裡面的 :has()。改一張卡片要上下捲動找三四個地方。

卡片的規則散在檔案各處，怎麼收回一起？原生 CSS nesting

用過 Sass 的人會想到巢狀寫法，以前這得靠 Sass 這類前處理器在建置時把巢狀展開成平面 CSS。現在瀏覽器原生支援CSS 巢狀（nesting）：把子規則直接寫在父規則的大括號裡，瀏覽器自己展開。把卡片的規則收回一起：

.card {
  display: grid;
  gap: 12px;

  .card__body { … }          /* = .card .card__body（後代，自動補空白） */

  &:hover { … }              /* = .card:hover */
  &.is-sold-out { … }        /* = .card.is-sold-out（同一個元素多一個 class） */
  .is-dark & { … }           /* & 放後面：外層還有 .is-dark 時的 .card */

  @container (width >= 28rem) {
    gap: 16px;               /* 直接寫宣告，套用在 .card 身上 */

    &:has(> img) {           /* = .card:has(> img) */
      grid-template-columns: 200px 1fr;
    }
  }
}

讀懂這段只需要一個觀念：& 代表父規則選中的元素。其他規則都從這裡推出來：

  • 沒寫 & 時，瀏覽器在前面補「父選擇器 + 空白」，也就是後代。.card__body 變成 .card .card__body。
  • 要選「同一個元素、多一個條件」（偽類、另一個 class、:has()）一定要寫 &：&:hover、&.is-sold-out。少了 & 的 :hover { } 會被補上空白，變成「.card 裡任何被 hover 的後代」，滑過卡片裡的文字或圖片時，被套用的是那個子元素。
  • & 也可以放在後面：.is-dark & 代表外層有 .is-dark（例如深色主題的區塊）時的 .card，展開成 .is-dark .card。
  • @media、@container、@supports 可以直接寫在規則裡，裡面的宣告套用在父選擇器上。斷點跟元件寫在一起，不用到檔案最後面找。

原生 nesting 跟 Sass 長得很像，但有兩個差別會讓從 Sass 轉過來的人出錯：一個讓規則默默消失，一個讓權重悄悄變高。

跟 Sass 的差別：& 不能拿來串接名稱

先說明一個命名慣例。第 6 課提過 BEM：class 名稱寫成「區塊__元素--狀態」，例如 .card__body 是 card 區塊裡的 body。Sass 使用者很習慣用 & 拼出這種名稱：

.card {
  &__body { … }   /* Sass：變成 .card__body；原生 CSS：無效，整條規則被丟掉 */
}

Sass 在建置時把 & 當成文字，跟 __body 接起來，得到 .card__body。原生 CSS 把 & 當成選擇器，不是文字，&__body 會被解讀成「& 後面接一個叫 __body 的標籤」。標籤必須寫在選擇器的最前面，所以整條規則無效，而且不會有任何錯誤訊息，只是樣式不見了。原生 nesting 裡要寫完整的 class 名稱 .card__body，就像上面的範例。Sass 的其他功能（變數、mixin、函式）原生 CSS 怎麼對應，見課末。

巢狀會改變權重

巢狀的子規則，權重跟把父選擇器包在 :is() 裡一樣。平面寫法的 .card__body 是 (0,1,0)；巢狀在 .card 裡就變成 .card .card__body，(0,2,0)。別處原本用一個 class 就能覆蓋它，改成巢狀後就蓋不過了。父規則是選擇器清單時更明顯：

.card, #promo {
  h2 { … }    /* = :is(.card, #promo) h2，權重 (1,0,1)，即使選中的是 .card 裡的 h2 */
}

所以巢狀不要超過 3 層：層數越多，權重越高、越難覆蓋，也越難一眼看出最後選中的是誰。巢狀是用來把「同一個元件的規則」放在一起，就像上面把卡片的規則收回一處，不是用來照抄 HTML 的結構。

💡 實務上：從 Sass 換成原生 nesting 先搜 &__
很多既有專案還在用 SCSS，換成原生 CSS 時最容易出事的就是 &__item、&--active 這類串接寫法：建置不會失敗，畫面上卻少了樣式。動手前先全專案搜尋 &__、&-，上線前用截圖比對主要頁面（第 27 課的視覺回歸）。不需要為了「用原生」一次改完所有檔案，通常是新元件直接用原生寫法、舊檔案改到時再順手轉。團隊也會在 lint 規則或 code review 約定巢狀層數上限，避免權重越疊越高。

改版的 CSS 寫完、PR 送出。審查者留下的第一個問題是：「container query、:has()、nesting 都很新，我們的使用者瀏覽器支援嗎？」在自己的 Chrome 能跑，不代表客人的瀏覽器能跑。

審查者問「使用者的瀏覽器支援嗎」：Baseline 怎麼看？

要回答這個問題，得先有一個大家都認同的支援度標準，不然每個人憑印象說「應該可以吧」。第 4 課提過的 Baseline 就是這個標準：由 W3C WebDX 社群小組的 web-features 專案維護的支援狀態標籤，看的是一組核心瀏覽器（桌機的 Chrome、Edge、Firefox、Safari，加上 Android 的 Chrome、Firefox 與 iOS 的 Safari）。它分三級：

  • Limited availability：還有核心瀏覽器不支援。
  • Newly available：所有核心瀏覽器的最新版都支援了。但還沒更新瀏覽器的使用者用不了。
  • Widely available：成為 newly available 之後又過了 30 個月。這段時間讓大部分使用者的瀏覽器都更新到支援的版本。

在哪裡看：MDN 每個屬性頁面的最上方有 Baseline 標示；caniuse.com 列出每個瀏覽器版本與全球使用比例；web.dev 有 Baseline 的說明與每月新進的功能。這課用到的功能（web-features 3.44.0，2026-10-22 的資料）：

功能Baseline日期
Container size queries（含 cq 單位）Widely available2025-08-14
CSS nestingWidely available2026-06-11
:has()Widely available2026-06-19
Container style queries（見課末）Newly available2026-05-19
@scope（限定樣式作用範圍，本課不教）Newly available2026-03-24

所以這個 PR 用到的三個功能都已經 widely available，可以回覆審查者「可以用」。但「可以用」的門檻是誰訂的？團隊通常會訂一條支援政策，寫進專案的 README，例如：「Baseline widely available 直接用；newly available 可以用，但不支援時要能退化成可用的樣子；limited availability 只做額外加分。」再用自己網站的使用者資料修正：做企業內部系統，客戶可能還在用沒更新的 iPad；做年輕族群的活動頁，幾乎都是最新的手機瀏覽器。

即使是 widely available，也只是「大部分」使用者。剩下那一小群人打開結帳頁會看到什麼，還是要回答。

不支援的瀏覽器會看到什麼？@supports 與漸進增強

回到統編欄位。前面的寫法是 .tax-id { display: none } 加上一條用 :has() 顯示它的規則。在不支援 :has() 的瀏覽器上：隱藏的規則照常生效，顯示的規則因為不認得 :has() 被整條丟掉，統編欄位永遠不會出現，需要統編的客人沒辦法結帳。問題出在「隱藏」靠舊功能、「顯示」靠新功能，不支援時只吃到隱藏那一半。

解法是反過來想，這個思路叫漸進增強（progressive enhancement）：先做所有瀏覽器都能用的版本，再對支援新功能的瀏覽器加上更好的體驗。CSS 用 @supports 判斷瀏覽器支不支援某個屬性值或選擇器，支援才套用裡面的規則：

/* 基本：統編欄位一直顯示。不支援 :has() 的瀏覽器也能填 */
.tax-id { display: block; }

/* 支援 :has() 才改成「勾選才出現」 */
@supports selector(:has(a)) {
  .tax-id { display: none; }
  .invoice:has(#need-tax:checked) .tax-id { display: block; }
}

/* 屬性值也能判斷 */
@supports (container-type: inline-size) { … }
@supports not (container-type: inline-size) { … }

現在不支援的瀏覽器看到的是一直顯示的統編欄位：多了一個不需要的欄位，但每個人都能結帳。隱藏和顯示被綁在同一個條件裡，要嘛兩條都生效，要嘛兩條都不生效，不會只剩一半。

這課的其他兩個功能退化情況不同，要分開判斷：

  • container query 本身就是漸進增強：不支援的瀏覽器忽略整個 @container 區塊，卡片維持基本的上下排。只要基本樣式在任何寬度都能用，就不需要額外處理。這也是 mobile-first 的好處：基本樣式本來就是最窄的版本。
  • nesting 沒有好的退化方式：不支援的瀏覽器會漏掉巢狀在裡面的規則，而那些規則不是「加分」，是元件的主要樣式。所以它要等到 widely available、或由建置工具展開成平面寫法後才適合全面採用；以 2026-06 成為 widely available 來看，這個 PR 可以用。

到這裡，審查者的問題都有了答案。最後把這些判斷整理成每次採用新功能都要走一遍的清單，寫進 PR 說明。

PR 說明要回答哪些問題？採用新功能的成本

新功能讓程式更短，但每一個都要回答這幾個問題。以這次改版的 PR 為例：

  1. 不支援的瀏覽器看到什麼？用 DevTools 把那條規則取消勾選看看，或在舊版瀏覽器、雲端測試平台實際打開。這次的答案：卡片維持上下排；統編欄位一直顯示。
  2. 退化可以接受嗎？卡片維持上下排可以接受；結帳欄位消失不行。牽涉到能不能完成任務（下單、登入、付款）的地方，基本版一定要能用。
  3. 需要 polyfill 嗎？polyfill 是用 JavaScript 模擬新功能的程式，讓舊瀏覽器也能跑新語法。它會增加下載量，而且通常只模擬部分行為。已經 widely available 的功能通常不需要；只有少數使用者用不了的，給退化版本比載 polyfill 划算。
  4. 真正的使用者用什麼瀏覽器？要看的是真實訪客的資料，不是自己的電腦。網站分析工具會統計訪客的瀏覽器版本分布；更進一步的做法叫真實使用者監測（RUM, Real User Monitoring），在使用者的瀏覽器裡收集實際的瀏覽器版本與效能資料。第 20 課會講怎麼收集。

反過來也要做：功能已經 widely available，就不用再為它保留舊的 JavaScript 量寬度程式或額外的 class。這次改版的最後一步，就是把卡片元件裡量側欄寬度的程式和 has-image 這類 class 刪掉，刪掉它們也是減少維護成本。

練習

練習 1：同一張商品卡片放在主欄與 300px 的側欄。把卡片版面改成依所在欄位的寬度切換：欄位寬度 ≥ 28rem 時圖片在左（200px）、文字在右；更窄時上下排。主欄與側欄要各自當查詢容器；卡片版面不能用 media query 控制（整頁的 .page 版面可以）。另外把品名 .card h2 的字級改成跟著容器寬度變：clamp(1.125rem, 4cqi, 1.75rem)。用預覽工具列切換 375、768、1280 看看兩張卡片。

練習 2：只用 CSS 的 :has() 完成三個需求，不改 HTML、不加 class：(1) 有 <img> 的菜單卡片用兩欄（圖片 120px、文字 1fr），沒圖的卡片維持一欄；(2) 勾選「需要統一編號」時才顯示統編欄位 .tax-id，沒勾選時隱藏而且按 Tab 到不了（注意 checkbox 跟欄位中間隔著一段說明）；(3) 發票 fieldset 裡任何欄位有 aria-invalid="true"（Vue 驗證失敗時會設定）時，fieldset 的邊框變成 var(--error)。測試會自己勾選、取消勾選、設定與移除 aria-invalid。

練習 3：把分類選單的平面 CSS 改寫成原生 nesting：最外層只留一條 .menu 規則，.menu__item、:hover、.is-active、兩個 @media 都搬進去；選擇器巢狀不超過 3 層。改寫後在 320px 與 1280px、有沒有 hover 時，每個元素的計算樣式都要跟原本一樣，只有一個例外：hover 效果改成只在能 hover 的裝置（@media (hover: hover)）生效，手機點一下才不會卡在 hover 的樣子。

練習 4：側欄裡的卡片被 @media (min-width: 768px) 套用成左右兩欄，文字被擠成一直條。最適合的修法是？

✓ b：media query 看的是整個視窗，不知道卡片被放在哪裡；container query 看卡片所在的欄位，同一份 CSS 在主欄與側欄自動不同。a 只是讓主欄的卡片也不能左右排，問題沒解決。c 要針對每個放置位置各寫一條覆蓋規則，元件放到新地方又要再寫。d 做得到，但多了 JavaScript、要處理視窗縮放與首次渲染的閃動，CSS 已經能做的事不需要它。

練習 5：MDN 上某個 CSS 功能標示 Baseline「Widely available」，代表什麼？

✓ b：所有核心瀏覽器（桌機的 Chrome、Edge、Firefox、Safari，加上手機的 Chrome、Firefox、Safari）的最新版都支援時是 newly available；再過 30 個月，大部分使用者都更新了，才是 widely available。a 是 limited availability。c 規範的狀態跟瀏覽器支援是兩回事，Baseline 看的是實際支援。d Baseline 跟 polyfill 無關。

練習 6：.card:has(img) 的權重是多少？

✓ b：:has() 跟 :is() 一樣，本身不計權重，取參數中最高的那一個：img 是 (0,0,1)，加上 .card 的 (0,1,0)，共 (0,1,1)。a 漏算了參數。c 把 :has 當成一個偽類多算了 (0,1,0)。d 是 :where() 的規則，只有 :where() 整個是 0。

常見錯誤

  • container-type 設在元件自己身上：元素不能查詢自己，@container 裡的 .card 規則看的是它的祖先。設在外層的欄位或 wrapper。
  • 用 container-type: size：容器的高度不再看內容，沒設高度就塌成 0，內容溢出。只需要寬度時一律用 inline-size。
  • 把整頁外層當容器：所有元件看到的都是同一個寬度，跟 media query 沒有差別。每個會放元件的區域各自當容器。
  • 容器斷點照抄視窗斷點：@container (width >= 768px) 量的是欄位，主欄可能永遠到不了這個寬度。依元件自己需要的寬度重新訂，例如 28rem。
  • 用 opacity 或移到畫面外隱藏欄位：鍵盤還能 Tab 進去。用 display: none 或 hidden。
  • 用 + 選擇器處理「勾選才顯示」：中間多一段說明就失效，而且只能往後選。從共同祖先用 :has()。
  • 新功能同時負責隱藏與顯示：不支援的瀏覽器只吃到隱藏那一半，功能直接消失。用 @supports 讓基本版可以用。
  • 照搬 Sass 的 &__item：原生 nesting 不能串接字串，整條規則被丟掉而且沒有錯誤訊息。寫完整的 class 名稱。
  • 巢狀越寫越深：每多一層權重就變高，別處蓋不過；超過 3 層就拆開。
  • 只看自己的瀏覽器：用 Baseline 與使用者的瀏覽器統計決定能不能用，並確認不支援時的樣子。

補充與查表

容器名稱：指定要問哪一個容器

沒寫名字的 @container 問的是最近的祖先容器。容器一層包一層時（例如側欄是容器、側欄裡的列表也是容器），可以幫容器取名字，指定要問誰：

.side {
  container: sidebar / inline-size;   /* 簡寫：container-name / container-type */
}

@container sidebar (width < 20rem) {
  .card h2 { font-size: 1rem; }
}

附近沒有查詢容器時的 cq 單位

附近沒有查詢容器時，cq 單位會退回成以視窗為基準的 sv* 單位（small viewport，第 13 課會講），所以要確定外層真的有容器。

container-type 的其他值

container-type 還有 scroll-state 等較新的值，用來查詢捲動狀態，本課不會用到。

Style queries（只介紹）

@container style(--tone: dark) { … } 依容器的 custom property 值套用樣式，例如外層設 --tone: dark，裡面的卡片就改用淺色字。它在 2026-05 才成為 Baseline newly available，目前用在可以接受退化的地方；設計變數與主題在第 16 課。

Sass 的變數、mixin、函式

Sass 的變數、mixin、函式原生 CSS 也沒有，對應的是 custom properties（第 6 課介紹過，第 16 課會深入）。

小結

  • media query 只知道視窗多寬，回答不了「元件被放在多寬的地方」。頁面骨架與裝置偏好用 media query；可重複使用的元件用 container query，看自己所在容器的寬度。
  • container-type: inline-size 設在元件外層：containment 讓容器寬度不看內容，所以元素不能查詢自己、靠內容撐寬的元素不能當容器。cqi 是容器寬度的 1%，搭配 clamp() 用 rem 設上下限。
  • :has() 依「裡面有什麼」或表單狀態選中外層元素，取代只為樣式存在的 class：沒照片的卡片不套兩欄、勾選才出現統編欄位、aria-invalid 同時驅動外觀。權重取參數最高者；錨點貼近目標，避免 body:has()。
  • 原生 nesting 把同一個元件的規則收在一起。& 代表父選擇器，是選擇器而不是文字，不能寫 &__item；巢狀會提高權重，不超過 3 層。
  • Baseline newly available 是核心瀏覽器最新版都支援，widely available 是再過 30 個月；用 @supports 讓隱藏與顯示綁在同一個條件，確保不支援時仍然可以用，並把退化的樣子寫進 PR 說明。
