階段 1：HTML 與可操作的網頁 · 第 5 課

無障礙基礎：鍵盤、焦點、對比、螢幕閱讀器與 ARIA 的使用界線

咖啡店的新首頁上線第一週，客服收到三封信：一位手腕受傷只能用鍵盤的客人，按 Tab 完全看不出自己停在哪裡；一位客人在中午的戶外看手機，淺棕色的價格幾乎看不見；一位視障客人用螢幕閱讀器，聽到的是「按鈕、按鈕、更多、更多」。這些都不是 bug 回報系統會抓到的錯：沒有 console 錯誤、沒有 500，畫面「看起來沒問題」。

這三位客人遇到的是同一類問題：無障礙（accessibility）。它指的是讓不同能力、不同使用情境的人都能使用網頁；英文字太長，業界常寫成 a11y（a 和 y 中間有 11 個字母）。這一課從頭到尾只做一件事：把這三封信修好，並且建立一套驗收方法，讓下次改版不會再收到同樣的信。

這課的路線：
  1. 這三封信要修到什麼程度才算修好：誰需要無障礙，WCAG 的條文和 A／AA 等級怎麼看，三封信各自對到哪一條。
  2. 視障客人為什麼只聽到「按鈕、按鈕、更多、更多」：螢幕閱讀器讀的是無障礙樹，不是畫面。
  3. 只用鍵盤的客人怎麼移動、焦點停在哪裡怎麼讓人看得到：Tab 順序從哪來、skip link、:focus-visible、焦點被 sticky 頁首遮住。
  4. 淺棕色價格為什麼在戶外看不見：對比怎麼算、及格線多少，順便處理手機上點不到的小圖示。
  5. HTML 表達不了的狀態怎麼辦、修好之後怎麼驗收：ARIA 該用和不該用的地方，axe 加手動檢查。
這課會用到：
  • 第 2 課的原生元素：<button>、<a href>、landmark 各自帶有角色（role，例如 button、link、navigation）與名稱，螢幕閱讀器唸的就是「角色＋名稱」。
  • 第 4 課的 <label> 與 aria-describedby：label 是欄位的名稱，aria-describedby 把提示或錯誤文字連到欄位，聚焦時一起唸出來。

這三封信要修到什麼程度，才算修好？

修 bug 之前要先知道「對」長什麼樣子。一般的 bug 有明確的預期結果（價格算錯，正確的價格就是答案），但「焦點看不清楚」「顏色太淡」很容易變成主觀爭論：設計師覺得夠清楚，客人覺得看不到。所以這一節先回答兩件事：這些問題影響的是誰，以及業界用什麼客觀標準判斷修好了沒有。

先看影響的是誰。很多人以為無障礙只跟「身障者」有關，所以優先順序排得很後面。實際上需要它的人分成三種，而且每個人都可能在某個時候屬於其中一種：

類型例子靠什麼使用網頁
永久全盲、弱視、色盲、手部無法精細操作螢幕閱讀器、放大、高對比、鍵盤或開關裝置
暫時手腕骨折、剛做完眼睛手術鍵盤、放大
情境一手抱小孩、強光下看手機、在吵雜的店裡不能開聲音單手、需要更高對比、字幕

對照開場的三封信：手腕受傷的客人是「暫時」，戶外看手機的客人是「情境」，視障客人是「永久」。三封信剛好涵蓋三種類型，也就是說，這不是少數人的問題，而是任何一位客人在某一天都可能碰到的問題。

再看判斷標準。業界通用的是 WCAG，全名是 Web Content Accessibility Guidelines，由 W3C（全球資訊網協會，制定 CSS 等多項網頁標準的組織）發布，目前的版本是 2.2。它把「好不好用」拆成可以逐條驗證的條文，結構由大到小分四層：

  1. 四個原則：可感知（Perceivable，看得到或聽得到）、可操作（Operable，用各種方式都能操作）、可理解（Understandable，內容和操作方式看得懂）、穩健（Robust，輔助科技讀得到正確的資訊）。
  2. 指引：每個原則底下的方向，例如「1.4 可區分」。
  3. 成功準則（success criteria）：可以驗證的條文，編號像 1.4.3。驗收看的是這一層，平常說「違反 WCAG」也是指違反某一條成功準則。
  4. 等級：每條成功準則標有 A（最基本）、AA（大部分法規與合約的目標）或 AAA（最嚴格，通常不要求全站做到）。要符合 AA，A 和 AA 的條文都要做到。

有了這個結構，三封信就能各自對到一條客觀的條文，「修好了沒」不再是看感覺：

客訴對應的條文及格線
按 Tab 看不出停在哪裡2.4.7 焦點可見（AA）鍵盤焦點一定看得到
淺棕色價格看不見1.4.3 對比（最低）（AA）一般文字對比至少 4.5:1
只聽到「按鈕、按鈕、更多、更多」4.1.2 名稱、角色、值（A）、2.4.4 連結目的（A）每個控制項都有名稱，連結文字聽得出要去哪裡

這一課後面每一節都是在把這張表的一列修到及格，過程中還會碰到幾條相鄰的條文（焦點順序、焦點不被遮住、點擊目標尺寸、狀態訊息）。前端常碰到的條文完整列在課末的「補充與查表」，修的時候可以回去對照。

為什麼工作上一定會遇到這件事，除了三封客訴之外還有三個理由：

  • 法規與採購：很多政府與企業的採購規格要求符合 WCAG 的 AA 等級，接案或賣 SaaS 給這些客戶，驗收時就會掃描（具體規範見課末）。
  • 跟 SEO、可用性重疊：有意義的連結文字、正確的標題結構、圖片替代文字，搜尋引擎也靠它們理解頁面（第 22 課）；對比夠、按鈕夠大，所有人都比較好用。
  • 越晚改越貴：元件庫的按鈕一開始用 <div> 做，等到要過驗收時，全站幾百個地方都要改。
💡 實務上：接到「要符合無障礙」的需求，先問清楚驗收標準
需求單上常常只寫一句「網站要無障礙」。資深工程師會先問：依據哪個版本、哪個等級（例如 WCAG 2.1 AA 還是 2.2 AA）？範圍是全站，還是會員註冊、點餐、結帳這幾個主要流程？誰來驗收：客戶自己掃描、第三方稽核，還是要附一份符合程度的說明文件（例如賣給美國客戶常被要求的 VPAT）？這些答案決定工時與優先順序，最好在估時之前就跟 PM 對齊，而不是上線前才發現要補。咖啡店這次的範圍就很清楚：首頁，目標 WCAG 2.2 AA。

標準定好了，接著從最難想像的那封信開始：視障客人看不到畫面，他聽到的「按鈕、按鈕、更多、更多」到底是從哪裡來的？

視障客人為什麼只聽到「按鈕、按鈕、更多、更多」？

要回答這個問題，得先知道視障客人怎麼用網頁。他用的是螢幕閱讀器（screen reader）：一種把畫面內容唸出來（或輸出成點字）的軟體，macOS 內建 VoiceOver，Windows 上常用免費的 NVDA。使用者不會從頭聽到尾，而是用鍵盤快速鍵在標題、連結、表單之間跳，例如「列出這頁所有連結」，再從清單裡挑一個。

關鍵在於：螢幕閱讀器不看你的 CSS 畫面。瀏覽器讀進 HTML 之後會建出 DOM，再從 DOM 另外算出一棵給輔助科技用的樹，叫無障礙樹（accessibility tree）。螢幕閱讀器、語音操控、點字顯示器這些輔助科技（assistive technology）讀的都是這棵樹。樹上每個節點只記三樣東西：

  • 角色（role）：這是什麼，例如 button、link、heading、textbox。螢幕閱讀器靠它告訴使用者「這個可以按」「這個會換頁」。
  • 名稱（accessible name，也叫可及名稱）：叫什麼，例如「加入購物車」。瀏覽器依序找這些來源，找到就停：aria-labelledby、aria-label、<label>／alt、元素裡的文字。
  • 狀態與屬性：例如已勾選、已展開、目前這一頁。

螢幕閱讀器唸一個元素，基本上就是唸出「名稱＋角色＋狀態」。圖裡的按鈕唸成「選單，按鈕，已收合」，三樣都齊了。現在回頭看客訴就清楚了：

  • 「按鈕、按鈕」：首頁上方有幾個只放圖示的按鈕（購物車、搜尋）。圖示是 svg，裡面沒有文字，名稱的每個來源都找不到，節點只剩角色，螢幕閱讀器只能唸「按鈕」。看得到圖示的人知道那是購物車，聽的人完全不知道。
  • 「更多、更多」：每張商品卡下面有一個「更多」連結。看畫面的人靠位置知道是哪張卡的「更多」；但螢幕閱讀器使用者常用「列出所有連結」瀏覽，清單裡只有一排「更多」，脫離了上下文，聽不出每個要去哪裡（WCAG 2.4.4）。

所以修法的方向是「讓每個節點有正確、聽得懂的名稱」：圖示按鈕要補名稱，「更多」連結要補上是哪支豆子。具體寫法（aria-label）會在後面講 ARIA 那一節示範，練習 4 也會實際修這兩個「更多」。

這也解釋了第 2 課為什麼一直強調「按鈕用 <button>」：原生元素一次給齊三樣東西。<button> 的角色是 button、裡面的文字就是名稱，而且不只是樹上的資訊，它還自帶可以聚焦、按 Enter／Space 觸發的行為。用 <div> 做的按鈕在樹上沒有角色，螢幕閱讀器根本不會說它是按鈕。

要確認一個元素在樹上長什麼樣子，不必每次開螢幕閱讀器：Chrome DevTools 的 Elements 面板右側有 Accessibility 分頁，選取元素就看得到它的角色（Role）與名稱（Name）。名稱是空的，就是螢幕閱讀器只會唸「按鈕」的那種。

名稱的問題知道怎麼查、怎麼修了。但「按鈕有名稱」只解決了「聽到什麼」；第一封信的客人看得到畫面，他的問題是用鍵盤操作時找不到自己在哪。要修這個，得先搞清楚鍵盤使用者是怎麼在頁面上移動的。

只用鍵盤的客人，怎麼在頁面上移動？

手腕受傷的客人不能用滑鼠，所以他的「游標」就是鍵盤。理解他的處境最快的方法是自己試：打開任何網站，手離開滑鼠，只用這幾個鍵操作：

按鍵作用
Tab／Shift+Tab移到下一個／上一個可以聚焦的元素
Enter跟隨連結、按下按鈕、送出表單
Space按下按鈕、勾選核取方塊；在頁面上是往下捲
方向鍵在同一組 radio、下拉選單、捲動區域裡移動
Esc關閉對話框、選單

（用 macOS 的 Safari 試的話，預設 Tab 不會停在連結上，要先改一個設定，見課末。Chrome 不用設定。）

試的時候你會發現，Tab 一次只移動一格，每一格都停在「目前接收鍵盤輸入的元素」上，這個元素就叫焦點（focus）。按 Enter 時，被觸發的就是焦點所在的那個連結或按鈕；打字時，字會進到焦點所在的那個輸入框。對鍵盤使用者來說，焦點就是滑鼠游標加上文字游標。

不是每個元素都能拿到焦點。能用 Tab 停下來的是會互動的那些：<a href>、<button>、表單欄位、<summary>，以及加了 tabindex="0" 的元素（tabindex 是讓元素加入或退出 Tab 順序的屬性，值的差別後面會整理成表）。<div>、<p> 這類元素 Tab 會直接跳過，這又是 <div> 按鈕的另一個問題：鍵盤使用者根本到不了它。

下一個問題是：按 Tab 時，焦點按什麼順序移動？答案是照 DOM 的順序，不看畫面位置。瀏覽器從文件開頭往後找下一個可以聚焦的元素，CSS 把它畫在哪裡不影響這個順序。平常 HTML 怎麼寫、畫面就怎麼排，兩者一致，所以不會有感覺；問題出在有兩種寫法會讓兩者分開，焦點就開始亂跳：

  • CSS 重排：flex 的 order、flex-direction: row-reverse、grid 指定位置，都只改畫面順序，DOM 順序沒變（第 8、9 課）。設計稿要求「立即點餐」排第一，如果用 order: -1 做，畫面上它在最前面，Tab 時卻最後才到，看得到畫面的鍵盤使用者會覺得焦點在亂跳。要讓某個按鈕排第一，就把它在 HTML 裡寫在第一個。練習 4 的第一個問題就是這個。
  • 正數的 tabindex：tabindex="1" 會讓這個元素排在全頁所有元素前面。它看起來是「指定順序」的捷徑，但一旦有一個，其他元素想排在它附近也得跟著編號，全站的順序變成一串要人工維護的數字，很快就沒人維護得了。

回到 tabindex，它控制「能不能聚焦、怎麼排」，三種值的效果差很多：

寫法Tab 到得了？程式 el.focus() 可以？用途
不寫（原生可聚焦元素）可以可以大部分情況
tabindex="0"可以，照 DOM 順序可以少數自訂元件（例如可以捲動的區塊）
tabindex="-1"不行可以程式移動焦點的目標，例如換頁後把焦點移到標題、錯誤摘要
tabindex="1" 以上可以，排到最前面可以不要用

結論是：順序交給 DOM 決定，tabindex 只用 0 和 -1。

照 DOM 順序走還有一個代價。咖啡店每一頁開頭都是一樣的頁首：logo、選單的十幾個連結、購物車、搜尋。用滑鼠的人直接點內容，鍵盤使用者每換一頁都要先 Tab 過這十幾個連結才進得了正文。解法是跳到主要內容連結（skip link）：在 body 最前面放一個連結，指向主要內容的 id，鍵盤使用者第一個 Tab 就會停在它上面，按一次 Enter 就跳過整個頁首（WCAG 2.4.1）：

<body>
  <a class="skip" href="#main">跳到主要內容</a>
  <header>…選單…</header>
  <main id="main">…</main>

.skip { position: absolute; top: 8px; left: 8px; z-index: 10; transform: translateY(-200%); }
.skip:focus { transform: none; }   /* Tab 到它時才出現 */

滑鼠使用者不需要這個連結，所以平常把它藏起來。但藏的方式有講究：不要用 display: none，因為 display: none 的元素聚焦不到，Tab 會直接跳過它，等於沒有。上面的寫法是用 transform 把它移到畫面外，Tab 到時 :focus 成立才移回來。

到這裡，鍵盤使用者能照合理的順序到達每一個控制項，也能跳過頁首。但第一封信抱怨的不是「到不了」，而是「看不出停在哪裡」：焦點明明在移動，畫面上卻沒有任何標示。

焦點停在哪裡，怎麼讓人看得到？

顯示焦點在哪裡的樣式叫焦點指示（focus indicator），瀏覽器預設是在元素外圍畫一圈外框（outline）。既然瀏覽器預設就有，咖啡店的首頁為什麼看不到？打開 CSS 就會找到原因：

*:focus { outline: none; }

這是很常見的寫法。設計稿審查時，設計師用滑鼠點按鈕，按鈕外面冒出一圈外框，覺得很醜，於是整站拿掉。滑鼠使用者確實不需要它，因為他知道自己剛點了哪裡；但鍵盤使用者因此失去唯一的位置標示，就像在看不到游標的情況下打字（違反 WCAG 2.4.7）。

所以真正的需求是：滑鼠點的時候不要出現，鍵盤操作時一定要出現。:focus-visible 就是為這件事設計的偽類，它不是「有焦點就成立」，而是「瀏覽器判斷使用者需要看到焦點時才成立」：

  • 用鍵盤 Tab 過來時成立。
  • 用滑鼠點按鈕時通常不成立（使用者已經知道自己點了哪裡）。
  • 點文字輸入框時一定成立，因為接下來要打字，需要知道字會打到哪裡。

它在主流瀏覽器都已支援，可以直接用（支援狀況見課末）。和另外兩個焦點相關的偽類比較：

選擇器什麼時候成立適合
:focus只要有焦點，滑鼠點的也算skip link 這種只會被鍵盤聚焦的元素
:focus-visible瀏覽器判斷需要顯示焦點時大部分的焦點樣式
:focus-within自己或裡面的元素有焦點聚焦欄位時讓整張卡片變色

咖啡店的修法就是把 outline: none 換成用 :focus-visible 自己設計的外框：

:focus-visible { outline: 3px solid #8a4b14; outline-offset: 2px; }
.site :focus-visible { outline-color: #ffd27a; }   /* 深色頁首裡換亮色 */

這兩行背後有幾個判斷，也就是「好的焦點樣式」的條件：

  • 夠粗：至少 2px。1px 的細線很容易看漏，練習 1 也會把 1px 判錯。
  • 跟背景對比至少 3:1（WCAG 1.4.11）：外框要能從旁邊的背景裡被分辨出來。「對比 3:1」具體怎麼算，下一節會講。
  • 不只是換文字顏色：只把文字從棕色換成深棕，鍵盤使用者很難察覺差異。
  • 用 outline 不用 border：outline 不佔版面，加上去不會讓旁邊的元素位移；border 是盒子的一部分，焦點出現時可能讓版面跟著跳動。outline-offset 讓外框跟元素留一點距離，更容易看清楚。
  • 深色區塊要另外設：深棕色外框在白色內文上很清楚，放到咖啡色頁首上就跟背景混在一起了，所以第二行在頁首裡換成亮色。

焦點樣式加上去之後，還有一個情況會讓它「有等於沒有」：被別的東西蓋住。咖啡店的頁首是 sticky，固定在畫面上方。使用者在頁面中段按 Tab，瀏覽器會自動把下一個連結捲進畫面，但瀏覽器不知道上方有一塊被頁首擋住，連結可能剛好停在頁首底下。焦點樣式畫得再清楚，被蓋住一樣看不到，WCAG 2.2 為此新增了 2.4.11「焦點不被遮住」。

解法是 scroll-padding-top：告訴瀏覽器「這個捲動容器的上方有這麼多空間被擋住」，之後不管是聚焦時的自動捲動，還是點 #錨點 連結的跳轉，都會停在這段距離下面：

html { scroll-padding-top: 72px; }   /* 頁首 64px，再留 8px */

這一節和上一節合起來，就是練習 1 要修的三件事：:focus-visible 焦點樣式、skip link、sticky 頁首遮擋。第一封信修好了。修焦點樣式時我們遇到了「對比至少 3:1」，這個數字正好也是第二封信的關鍵：淺棕色的價格到底差在哪裡？

淺棕色價格為什麼在戶外看不見？

設計師在辦公室的螢幕上看淺棕色價格，覺得清楚又有品牌感；客人中午在戶外看手機，螢幕被陽光照得很亮，淺色字和白底之間的差距被稀釋，字就「消失」了。WCAG 不用「看起來清不清楚」判斷，而是用一個可以算出來的數字：對比（contrast ratio）。

對比是前景色和背景色的相對亮度比值。相對亮度是一個顏色在人眼看來有多亮，0 是純黑、1 是純白；人眼對綠色最敏感、藍色最不敏感，所以同樣數值的綠會比藍看起來亮得多，計算時要加權。對比的範圍從 1:1（同一個顏色，完全分不出來）到 21:1（黑字白底）。WCAG 的及格線：

  • 一般文字 4.5:1（1.4.3）。咖啡店的價格是一般大小的文字，要達到這條。
  • 大字 3:1：字大的時候筆畫粗、比較容易辨認，所以要求較低。WCAG 定義大字是 18pt 以上，或 14pt 以上的粗體；換成 CSS 是 24px，或 18.66px 粗體（1pt = 4/3 px）。WCAG 也註明中文字型可以用對應的大字尺寸，實務上用同樣的 px 判斷最保險。
  • 非文字 3:1（1.4.11）：表單欄位的邊框、圖示按鈕的圖示、焦點外框，凡是要「看出來才會用」的都算。上一節焦點外框的 3:1 就是這條。
  • 不用算的：停用（disabled）的元件、純裝飾、logo 文字。

計算步驟是：先把顏色的 R、G、B 三個分量各自轉成線性亮度，再依人眼的敏感度加權相加得到相對亮度 L（程式裡綠色的權重 0.7152 最大、藍色 0.0722 最小），最後算 (L亮 + 0.05) / (L暗 + 0.05)。下面這格把咖啡店用到的配色全部算一次，按執行後看每一列最後的 ✓／✗：

第一列就是第二封信的原因：淺棕色 #c08552 在白底只有 3.13:1，離 4.5:1 差一截。第二列提醒同一個顏色反過來當按鈕底色、上面放白字，也是同一個比值，也不及格：同一個品牌色當文字色和當按鈕底色是兩組對比，都要算。最後一列把同一個淺棕色放到深咖啡色背景上，對比變成 4.37:1，比白底的 3.13 高很多，但還是差一點才到 4.5，一樣不及格。所以對比永遠是「這個前景色在這個背景上」的組合，不是顏色本身的屬性；換了背景就要重算。

修法不是把所有字改成黑色，那樣設計師不會接受，品牌感也沒了。關鍵在於對比只跟亮度有關，跟色相無關，所以可以保留色相、只調亮度：#8a5a2e 還是同一個棕色，只是暗一些，對比就到了 5.86:1。placeholder 的 #bbbbbb 和輸入框邊框 #dddddd 也用同樣的方式調暗。

修完一個顏色還不夠：如果每個元件各自挑顏色，下個月新做的元件又會挑回淺棕色。實務上在 design tokens（把顏色、字級這些設計決定定義成共用變數）裡就把「可以放在白底上的文字色」定好（第 16 課），元件只能從裡面挑。

平常不用自己寫程式算：Chrome DevTools 選取元素後，Styles 面板點顏色方塊，會顯示對比值與 AA／AAA 是否通過；CSS Overview 面板可以一次列出全頁對比不足的地方。

同一位在戶外用手機的客人，還有另一個沒寫進客訴的困擾：頁尾的社群圖示和購物車的 + − 按鈕太小，單手用拇指常常點到隔壁。WCAG 2.2 對此新增了點擊目標尺寸（2.5.8，AA）：可以點的目標至少 24×24 CSS px。以下情況例外：

  • 間距：目標比較小，但以它為中心畫直徑 24px 的圓，不會碰到別的目標（或別的小目標的圓）。
  • 行內：句子裡的連結，大小受行高限制。
  • 有替代：同一頁有另一個符合尺寸的控制項做同一件事。
  • 大小由瀏覽器決定、沒被改過的原生控制項，以及尺寸本身是必要的情況（例如地圖上的點）。

修這個時常見的錯是只把圖示放大。<a> 是 inline 元素，點擊區是由它自己的盒子決定的，裡面的 svg 變大，連結本身的點擊區不一定跟著變。要放大的是 <a> 本身：display: inline-flex 讓它變成可以設定寬高與內距的盒子，再加 padding 撐大。24px 是 AA 的下限，觸控裝置的建議更大（Apple 建議 44pt、Material 建議 48dp）。練習 2 就是這一節的完整版：只改 CSS，修好咖啡卡的對比與社群圖示的點擊區。

💡 實務上：對比問題最好在設計稿階段就擋下來
前端拿到設計稿時，順手用 DevTools 或設計工具的對比外掛量一下主要的文字色與按鈕色，不過就帶著數字回頭找設計師，並附上「同色相調暗」的替代色，比只說「這個顏色不行」好溝通得多。品牌色是行銷與設計共同決定的，工程師不要自己偷改，要讓修正後的顏色回到 design tokens，全站一起生效。小圖示按鈕（購物車的 + −、關閉 ✕）是點擊尺寸最常出包的地方，手機上實際用手指點一次就知道。咖啡店這次如果在設計稿階段就量過淺棕色，第二封信根本不會出現。

到這裡，三封信裡的兩封用原生 HTML 和 CSS 就修好了。第三封信的名稱問題前面說要用 aria-label 修；首頁上還有一些 HTML 本身表達不了的狀態，例如漢堡選單現在是開還是關、「已加入購物車」的提示。這些都要靠 ARIA，而 ARIA 正是最容易「越修越壞」的地方。

HTML 表達不了的資訊，ARIA 怎麼補？又怎麼弄壞？

ARIA（Accessible Rich Internet Applications）是一組 HTML 屬性，包括 role 與各種 aria-*，用來補充或修改無障礙樹上的角色、名稱、狀態。回想第二節的圖：無障礙樹是瀏覽器從 DOM 算出來的，ARIA 就是直接在這個計算結果上覆寫。

理解 ARIA 最重要的一句話是：它只改無障礙樹。它不改畫面、不加鍵盤行為、不讓元素可以聚焦。寫了 role="button"，螢幕閱讀器會說「按鈕」，但瀏覽器不會因此讓它 Tab 得到、按 Enter 有反應。也就是說，ARIA 是在對輔助科技「宣告」某件事，至於這個宣告是不是真的，要由你自己的 HTML 和 JavaScript 負責兌現。宣告了做不到的事，比什麼都沒宣告更糟。

因為這個特性，W3C 的《Using ARIA》文件列出了幾條使用規則：

  1. 能用原生 HTML 元素或屬性做到，就不要用 ARIA。<div role="button"> 還要自己補 tabindex="0"、Enter 與 Space 的事件；<button> 全部內建。
  2. 不要改變原生語意。<a href="/menu/" role="button"> 會讓螢幕閱讀器說「按鈕」，使用者以為按了會執行動作，結果換頁了。換頁就是連結，做動作就是按鈕。
  3. 所有互動的 ARIA 元件都要能用鍵盤操作。寫了 role，就要做出那個角色該有的鍵盤行為（tab 元件要能用方向鍵切換等）。
  4. 可以聚焦的元素不能是 role="presentation" 或 aria-hidden="true"（包括在它們裡面）。否則鍵盤會停在一個螢幕閱讀器「看不到」的地方。
  5. 所有互動元素都要有可及名稱：只有圖示的按鈕要加 aria-label。這正是第三封信「按鈕、按鈕」的修法，WCAG 4.1.2 也要求。

這份文件目前的狀態，以及各種元件（tabs、選單、對話框）該有的角色與鍵盤行為去哪裡查，見課末。

錯的 ARIA 比沒有更糟：沒寫 ARIA 的 <button> 至少是個能用的按鈕；寫錯的 ARIA 會蓋掉原生資訊，讓輔助科技說出錯的東西，例如 aria-expanded="yes" 不是合法值（只能是 true／false），螢幕閱讀器就不會報出展開狀態。

那什麼時候才真的需要 ARIA？答案是 HTML 沒有對應元素或屬性的時候。咖啡店首頁上的情境，加上最常用的幾種寫法：

情境寫法注意
選單、摺疊區塊的開關按鈕<button aria-expanded="false" aria-controls="site-nav">開關時用 JavaScript（Vue 的 :aria-expanded="open"）同步更新；值只能是 true／false
導覽列中目前這一頁<a href="/menu/" aria-current="page">只靠顏色標示目前頁，螢幕閱讀器使用者不知道；Vue Router 的 RouterLink 會自動加
只有圖示的按鈕<button aria-label="關閉公告">✕</button>有看得到的文字時，名稱要包含那段文字（2.5.3），語音操作的使用者會說「按 加入最愛」
非同步的狀態訊息<p aria-live="polite">購物車 2 件</p> 或 role="status"見下方
純裝飾的圖示<svg aria-hidden="true">只用在不能聚焦的東西上

表裡「只有圖示的按鈕」那列的注意事項，也是修「更多、更多」的關鍵。「更多」連結有看得到的文字，如果用 aria-label 補成完整說明，名稱一定要包含「更多」這兩個字，例如「更多：耶加雪菲的介紹」。原因是語音操控的使用者是看著畫面說「點 更多」，名稱裡沒有這兩個字，語音軟體就找不到它（WCAG 2.5.3）。

表裡「非同步的狀態訊息」需要多講一點。客人按「加入購物車」，畫面角落浮出「已加入購物車」，看得到的人一眼就知道成功了；但螢幕閱讀器只唸焦點所在的東西，焦點還停在按鈕上，這段新文字它不會主動唸。把焦點移到訊息上也不對，那會打斷使用者原本在做的事。這時要用 live region：一個被標記為「內容改變時要主動唸出來」的區域，螢幕閱讀器會持續監聽它（WCAG 4.1.3）。

  • aria-live="polite"：等使用者目前聽的句子唸完再說。購物車數量、搜尋結果筆數都用這個；role="status" 的效果相同。
  • aria-live="assertive"：立刻打斷。只用在真的緊急的訊息，例如「連線中斷，訂單沒有送出」。
  • 只包住會變的那一句：包住整個頁首的話，頁首任何一點變化都會整段重唸。
  • 區域要先存在：live region 要在內容改變之前就在 DOM 裡，螢幕閱讀器才會監聽它。在 Vue 裡不要用 v-if 讓整個區域跟著訊息出現，而是區域一直在、只換裡面的文字。

ARIA 最後一個常被誤用的地方是「藏東西」。前面已經看過 display: none 會讓 skip link 聚焦不到，也看過 aria-hidden 可以把裝飾圖示從樹上拿掉。「藏起來」其實有好幾種，差別在於畫面、螢幕閱讀器、鍵盤這三方，誰還看得到：

寫法畫面螢幕閱讀器Tab 得到？用途
hidden 屬性、display: none看不到讀不到不行真的不存在的內容（收合的選單）
.visually-hidden（clip 的寫法）看不到讀得到可以只給螢幕閱讀器的補充文字
aria-hidden="true"看得到讀不到還是可以裝飾性圖示；不能放在可聚焦的元素上
inert 屬性看得到讀不到不行，也點不到模態框打開時的背景、畫面外的抽屜選單

第三列的「還是可以」正好印證了這一節開頭那句話：aria-hidden 只改無障礙樹，不改鍵盤行為。所以如果想讓一整塊區域對所有人「暫時不存在」，aria-hidden 做不到，要用 inert。inert 讓整個區塊（含裡面所有元素）不能聚焦、不能點擊，也從無障礙樹移除，而且主流瀏覽器都已支援。

最典型的用途是模態框（modal），也就是打開時要求使用者先處理它、背後的頁面暫時不能操作的對話框，例如咖啡店的登入框。如果背景沒處理，鍵盤使用者按幾下 Tab 就跑到被遮住的背景連結上，焦點消失在對話框後面。用原生的 <dialog> 時，dialog.showModal() 會自動讓對話框以外的內容變成 inert，還會把焦點移進對話框、讓 Esc 關閉它，所以模態框優先用 <dialog> 加 showModal()（需要 JavaScript；在 Vue 裡搭配 Teleport 的做法在 Vue 課第 11 課）。這一課的練習預覽不執行 JavaScript，所以用 open 屬性加上手動的 inert 模擬。

練習 3 是一頁被「熱心」加滿 ARIA 的頁面，要照這一節的規則把錯的刪掉、必要的寫對；練習 4 則會用到 aria-label 修「更多」和用 inert 處理模態框背景。

💡 實務上：選 UI 元件庫時，把無障礙當成評估項目
下拉選單、日期選擇器、tabs、對話框這類元件，自己用 div 加 ARIA 從零做，要補齊的鍵盤行為很多，也最容易出錯。實務上先問：原生元素（<select>、<dialog>、<details>）夠不夠用？不夠的話，選元件庫前先實際用鍵盤操作它的官方範例，並對照 APG 的鍵盤規則，看文件有沒有寫無障礙支援。程式碼審查時看到 role= 或 aria-，資深會先問一句「這裡為什麼不能用原生元素？」

三封信都有了修法。剩下的問題是：怎麼確認真的修好了，而且下一次改版、下一個新同事加的元件不會讓它們再壞一次？

修好了，上線前怎麼驗收、之後怎麼不再壞？

最直覺的做法是找一個工具自動掃。業界最常用的是 axe（套件名稱是 axe-core，這門課用的版本見課末）：它把 WCAG 裡「可以用程式判斷」的部分寫成規則，對頁面當下的 DOM 逐條檢查，Chrome 的 Lighthouse 無障礙分數也是用它算的。它擅長抓對比不足、缺少名稱的按鈕、ARIA 值不合法、可聚焦元素在 aria-hidden 裡這類錯，也就是這一課修過的很多問題。

但 axe 有清楚的極限：只要需要「人判斷」的事，它就抓不到：

  • 焦點順序跟畫面順序是否一致、焦點樣式看不看得清楚：axe 不知道設計師心中的畫面順序。
  • 替代文字、連結文字寫得對不對：alt="圖片" 也算「有寫」，兩個「更多」也都「有名稱」。
  • 模態框打開時背景還 Tab 得到：這需要真的按 Tab 走一次。
  • 動態內容（打開選單、送出表單之後）的狀態：axe 只檢查掃描當下的 DOM。

對照開場的三封信，「更多、更多」和焦點順序這兩類問題 axe 都不會報。所以axe 沒有違規不等於符合 WCAG，只代表自動規則沒抓到問題。練習 4 就是一頁 axe 全過、但鍵盤和螢幕閱讀器一走就出問題的頁面。每次改版至少再做這幾件事：

  1. 鍵盤走一次主要流程（點餐、結帳）：每一步都 Tab 得到嗎？焦點一直看得到嗎？順序合理嗎？打開的東西 Esc 關得掉、關掉後焦點回到原本的按鈕嗎？這一步直接驗收第一封信。
  2. 放大到 200%、把視窗縮到 320px 寬：內容沒有被切掉、不用左右捲動。
  3. 螢幕閱讀器快速檢查：macOS 用 VoiceOver（Cmd+F5 開關），按 Control+Option+U 打開「轉輪」，看標題清單、連結清單、landmark 清單：每個連結的名稱單獨聽得懂嗎？Windows 用免費的 NVDA。這一步直接驗收第三封信。

第 27 課會把 axe 掃描與鍵盤操作寫成 Playwright 測試，放進 CI 自動跑；但手動的那幾項還是要人做。

💡 實務上：稽核報告列出幾百個問題時，先修共用元件
舊專案第一次跑 axe 或收到稽核報告，常常一次列出幾百條。不要從第一條逐條修：先依「主要流程（點餐、結帳、登入）」與「共用元件」分組，修好一個按鈕或表單元件，可能就解掉全站好幾十條。接著把「鍵盤走一次主要流程」寫進 PR 檢查清單或完成定義（Definition of Done），新功能就不會再增加債務。修完要用鍵盤和螢幕閱讀器親自走一次，不要只看分數變高就結案。咖啡店的三封信也一樣：修完後找人照上面三步走一次首頁，再回信給客人。

版本與規範備註：

  • WCAG 2.2：2023-10-05 成為正式推薦標準，目前版本日期 2024-12-12。2.2 新增了焦點不能被遮住（2.4.11）、點擊目標最小尺寸（2.5.8）等條文，也移除了 4.1.1 Parsing（HTML 語法錯誤由瀏覽器處理，不再單獨要求）。
  • 法規：例如歐盟的 EN 301 549（v3.2.1）對網頁直接引用 WCAG 2.1 AA。
  • 《Using ARIA》：舊版文件把「所有互動元素都要有可及名稱」列為第五條；這條現在由 WCAG 4.1.2 要求，仍然要做到。這份文件在 2026-02-24 改為 Discontinued Draft，W3C 建議改看 ARIA Authoring Practices Guide（APG）；APG 有每種元件（tabs、選單、對話框）該有的角色與鍵盤行為。
  • 瀏覽器支援：:focus-visible 與 inert 都是 Baseline widely available，可以直接用。
  • axe：這門課用 axe-core 4.14.0。
  • Safari 的 Tab：macOS 的 Safari 預設 Tab 不會停在連結上：到 Safari 的「設定 → 進階」，勾選讓 Tab 鍵反白網頁上每個元素的選項。Chrome 不用設定。

練習

練習的預覽不執行 JavaScript。檢查時會用程式模擬按 Tab（照 DOM 與 tabindex 算出順序）、聚焦元素、量焦點樣式與對比，並在背景跑 axe。

練習 1：品牌設計師把所有外框（outline）都拿掉了，鍵盤使用者完全不知道焦點在哪。請修好三件事：
① 用 :focus-visible 幫連結、按鈕、輸入框加上焦點樣式：外框至少 2px，跟旁邊的背景對比至少 3:1（深色頁首與淺色內文的背景不同，顏色可能要分開設）。不要把 outline: none 刪掉了事，要自己設計。
② 在 body 最前面加一個「跳到主要內容」連結，指向 <main id="main">：平常藏起來，聚焦時出現在左上角、疊在頁首上面，大小至少 24×24。
③ 頁首是 64px 高的 sticky，Tab 到頁面中段的連結時，不能被頁首蓋住。

練習 2：這張咖啡卡的配色是品牌設計師給的，但淺棕色在白底上對比不足。只能改 CSS：讓所有文字（含 placeholder 與頁尾小字）對比至少 4.5:1；輸入框邊框、社群圖示至少 3:1；頁尾三個社群連結的點擊區至少 24×24 CSS px。要保留品牌感：--brand 維持同一個棕色色相、只調暗，「本週推薦」與「立即點餐」按鈕仍用品牌色。320px 與 1280px 寬都要成立，不要用 !important。

練習 3：同事為了「讓頁面更無障礙」加了一堆 ARIA，結果有 5 個地方寫錯，反而讓螢幕閱讀器與鍵盤使用者更難用。只能改 HTML，照 ARIA 的規則修正：能用原生元素就刪掉 ARIA，必要的 ARIA 要寫對。保留原本的 class（.menu-btn、.close、.fav），選單按鈕的狀態請設成收合（CSS 會在 aria-expanded="false" 時藏起選單）。

練習 4：這一頁用 axe 掃描沒有任何違規，但用鍵盤和螢幕閱讀器走一次，會發現 3 個問題：① 「立即點餐」用 CSS order 排到最前面，但 Tab 時最後才到；② 兩個「更多」連結，螢幕閱讀器列出所有連結時聽不出要去哪裡；③ 登入的模態框開著，背景的連結還 Tab 得到。修好它們：「立即點餐」畫面上與 Tab 順序都排第一；不改看得到的文字，用 aria-label 補完整的名稱（名稱要包含看得到的「更多」）；模態框開著時背景完全 Tab 不到。修完 axe 仍然要沒有違規。

練習 5：專案導入 axe 之後，CI 掃描全部通過、沒有任何違規。這代表什麼？

✓ b：自動工具只能檢查程式判斷得了的部分，例如對比、名稱是否存在。名稱寫得好不好、順序合不合理、互動後的狀態，都要人判斷（練習 4 就是 axe 全過但還有問題的頁面）。a、c 錯：axe 只涵蓋一部分條文。d 錯：每次改版都可能引入新問題，axe 也要持續跑。

練習 6：同事用 <div class="btn" role="button">加入最愛</div> 做按鈕，說「加了 role，無障礙就沒問題了」。最主要的問題是？

✓ b：ARIA 第一條規則：能用原生元素就不用 ARIA。ARIA 不會帶來聚焦與鍵盤行為，用 div 要自己補 tabindex 和兩種按鍵事件，<button> 全部內建。a 錯：螢幕閱讀器說「按鈕」，鍵盤卻按不下去。c 錯：裡面的文字本來就是名稱，再加 aria-label 也解決不了鍵盤問題。d 錯：「加入最愛」是動作不是換頁，用 link 是改錯語意。

練習 7：模態框打開時，想讓背景完全不能被 Tab 到，最直接的做法是？

✓ b：inert 同時移除聚焦、點擊與無障礙樹；showModal() 會自動讓對話框以外的內容變成 inert。a 錯：aria-hidden 只從無障礙樹移除，裡面的連結還是 Tab 得到，還違反「可聚焦元素不能在 aria-hidden 裡」。c 錯：tabindex 只影響容器自己，裡面的連結不受影響。d 錯：只擋滑鼠，鍵盤照樣進得去。

常見錯誤

  • 全站寫 outline: none 沒有替代：鍵盤使用者不知道焦點在哪，就是第一封信的原因。用 :focus-visible 設計至少 2px、對比 3:1 的樣式，滑鼠點按鈕時通常不會出現，設計師也能接受。
  • 用 tabindex 正值或 CSS order 調順序：焦點順序跟畫面對不上。要改順序就改 HTML 的順序；tabindex 只用 0 或 -1。
  • skip link 用 display: none 藏起來：聚焦不到，等於沒有。用 transform 移到畫面外，:focus 時移回來。
  • 用 div 加 role="button"：role 只改無障礙樹，沒有聚焦與鍵盤行為。做動作用 <button>，換頁用 <a href>。
  • ARIA 寫錯值或放錯地方：aria-expanded="yes" 無效；aria-hidden="true" 包住按鈕讓它變成「看不見的焦點」。錯的 ARIA 比沒有更糟，不確定就先刪掉，用原生元素。
  • live region 包太大、用 assertive，或用 v-if 讓它跟訊息一起出現：整段重唸、打斷使用者，或者根本不唸。只包會變的那一句，用 polite，區域一直留在 DOM 裡、只換文字。
  • 修對比時把品牌色改成黑色：設計師不會接受。保留色相、調整亮度，在 design tokens 裡定好「白底可用的文字色」。
  • 只放大圖示、沒放大連結：點擊區還是很小。放大 <a> 本身的 display 與 padding。
  • 只依賴自動工具：axe 通過不代表可用，「更多、更多」和焦點順序它都不會報。每次改版至少用鍵盤走一次主要流程。

小結

  • 無障礙涵蓋永久、暫時與情境的限制，任何客人都可能碰到；判斷修好了沒有，看的是 WCAG 的成功準則，法規與採購多以 AA 為目標。WCAG 2.2 分原則、指引、成功準則與 A／AA／AAA 等級。
  • 輔助科技讀的是無障礙樹：每個元件要有正確的角色、名稱、狀態。原生元素一次給齊；只有圖示的按鈕、脫離上下文的「更多」連結，就是名稱出了問題。
  • Tab 順序照 DOM 順序；不要用 CSS order 或正數 tabindex 打亂。加 skip link 讓鍵盤使用者跳過選單，不要用 display: none 藏它。
  • 焦點一定要看得到：用 :focus-visible 設計替代樣式，sticky 頁首用 scroll-padding-top 避免蓋住焦點。
  • 文字 4.5:1、大字 3:1、元件與圖示 3:1，對比是前景與背景的組合；修法是保留色相、調整亮度。點擊目標至少 24×24 CSS px，要放大的是連結本身。
  • ARIA 只改無障礙樹：能用原生就不用、不改原生語意、互動元件要能用鍵盤、可聚焦元素不能被 aria-hidden。常用的是 aria-expanded、aria-current、aria-label、aria-live；模態框背景用 inert 或 showModal()。
  • axe 自動檢查只抓得到一部分，鍵盤與螢幕閱讀器的手動檢查不能省。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：head 裡有兩支 script：app.js 要用 vendor.js 提供的函式，還會 document.querySelector('#order-form') 綁定事件。哪個寫法結果一定正確，又不擋住解析？

✓ defer 跟解析同時下載，解析完、DOMContentLoaded 前依文件順序執行，所以 vendor 先跑、表單也已經在 DOM 裡。b 錯在不只擋解析：放在 head 時 body 還沒解析，querySelector 拿到 null。a、c 的 async 下載完就插隊，可能比 vendor 或 body 早。（第 1 課）

練習 9：伺服器輸出的商品頁把富文字說明放進 <p class="desc">，內容帶 <ul><li>。全域 CSS 寫了 .desc li { color: #8a5a2e; }，清單卻沒變色，為什麼？

✓ p 裡不能放區塊元素，解析器照規範修正結構，DOM 就跟原始碼不同，CSS 照 DOM 走。先打開 Elements 面板對照 DOM；外層容器改用 div。b 錯在空白是後代選擇器，隔幾層都選得到；問題是 ul 根本不在 p 裡。（第 1 課）

練習 10：後台訂單列表寫成 <tr @click="router.push(`/orders/${o.id}`)">，店員抱怨沒辦法按右鍵在新分頁開好幾筆來比對。怎麼改最恰當？

✓ 會換網址就用 <a href>（RouterLink 輸出的就是它），右鍵開新分頁、複製網址、Enter 觸發都是瀏覽器內建的。a 錯在 role 只改無障礙樹，它還是沒有 href，右鍵選單一樣沒有「在新分頁開啟」。（第 2 課）

練習 11：預約表單裡有 <button @click="show = !show">顯示密碼</button>，一按頁面就重新整理。原因與修法是？

✓ button 在 form 裡預設 type="submit"，按了就送出；表單裡不是送出用的按鈕一律寫 type="button"。它也可能變成按 Enter 時觸發的第一個 submit 按鈕。a 錯在送出是 submit 按鈕的預設行為，不是冒泡造成的，.stop 擋不住。（第 2、4 課）

練習 12：頁首左上角的店家 logo 是一張 <img>，包在 <a href="/"> 裡，連結裡沒有其他文字。alt 該怎麼寫？

✓ 圖在連結或按鈕裡，alt 就是連結的名稱，要寫它做什麼。b 錯在連結裡只有這張圖，alt 空了連結就沒有名稱，螢幕閱讀器可能改唸網址。a 會唸成「圖片，標誌圖片」又沒說去哪；d 的 title 只在滑鼠停留時出現。（第 3 課）

練習 13：共用的 BaseInput 元件裡寫死了 <label for="phone"> 和 <input id="phone" :name="name">。結帳頁用了兩次（訂購人、收件人手機），會出什麼事？

✓ id 整頁要唯一，重複不會報錯，只是關聯悄悄失效；在 Accessibility 面板看欄位的 Name 是空的。修法是用 Vue 3.5 的 useId() 產生 id。b 錯在送到伺服器的是 name，id 只給頁面裡的 label、CSS、JavaScript 用。（第 4 課）

練習 14：設計師覺得用滑鼠點按鈕後出現的外框很醜，要求拿掉。怎麼做才不會害到鍵盤使用者？

✓ :focus-visible 在瀏覽器判斷需要顯示焦點時才成立：Tab 過來會出現，滑鼠點按鈕通常不會。樣式至少 2px、對比 3:1。a 錯在鍵盤使用者不會觸發 hover，等於看不到游標在哪（WCAG 2.4.7）。c 錯在鍵盤按 Enter 也會觸發 click，焦點一樣被移走。（第 5 課）

練習 15：加入購物車後把 msg 設成「已加入購物車」，畫面出現了，VoiceOver 卻沒有唸。哪裡出了問題？

<p v-if="msg" aria-live="polite">{{ msg }}</p>

✓ 螢幕閱讀器只監聽已經存在的 live region 裡的變化。拿掉 v-if，讓 <p aria-live="polite"> 一直在，只換裡面的文字。a 錯在問題是區域還不存在，改 assertive 一樣唸不出來，還會打斷使用者。（第 5 課）
