階段 2：CSS 與版面基本功 · 第 7 課

盒模型與正常流：尺寸、display、overflow 與 margin

豆留咖啡的菜單頁在桌機上看起來沒問題。上線前，測試的同事用 320px 寬的手機打開同一頁，開了三張單：

  1. 整頁可以左右滑，季節特調卡片的右半邊被切掉。
  2. 「門市資訊」區塊上方多出一段空白，米色背景沒有包住它；兩張門市卡片之間，設計稿是 24px，量出來是 32px。
  3. 頁面頂端的公告列在手機上變成三、四行，把菜單整個往下推。

三張單都不是複雜的 bug，而是 CSS 最底層的幾條規則沒弄清楚：一個元素的寬度怎麼算、沒寫 flex 或 grid 時元素怎麼排、內容比容器大時瀏覽器怎麼處理、上下相鄰的 margin 怎麼互動。這課沿著這三張單，把規則一條一條講清楚，每講完一條就修掉一個問題。第 8、9 課的 Flexbox、Grid 都建立在這些規則上；不懂它們，版面出問題時就只能一個屬性一個屬性試。

這課的路線：
  1. 卡片寫 340px，為什麼實際佔 382px：先看第 1 張單的三個原因，再用盒模型和 box-sizing: border-box 解決第一個（開場問題的最小答案）。
  2. 340px 還是比手機寬：用 max-width 給上限、不給定值，讓卡片和圖片跟著螢幕縮。
  3. 圖片底下為什麼多一條縫：沒寫 flex、grid 時元素怎麼排（正常流與 display），也順便解釋為什麼幫連結設 width 沒反應。
  4. 長品名為什麼伸出卡片、公告列怎麼只顯示一行：溢出、overflow-wrap、overflow 的各種值與省略號（第 1 張單收尾、第 3 張單）。
  5. 門市卡片之間的 24 加 32 為什麼等於 32：外距合併與 BFC（第 2 張單）；最後整理下次遇到時怎麼在 DevTools 自己找出原因。
這課會用到：
  • 第 6 課的層疊與 @layer：同一個屬性有多條宣告時瀏覽器依規則選出贏家；@layer 把樣式分層，後宣告的層優先，reset 放在最低層。DevTools 的 Computed 分頁顯示最後算出來的值。

第 1 張單：卡片為什麼把 320px 的手機撐破？

先看季節特調卡片的 CSS。它是照著 1280px 寬的桌機設計稿寫的，在桌機上看起來正常：

.card {
  width: 340px;
  padding: 20px;
  border: 1px solid #d6c3a8;
}
.card img { width: 300px; }

為什麼特別要測 320px？無障礙規範 WCAG 有一條 1.4.10 Reflow，要求頁面在 320 CSS px 寬時不能出現橫向捲動，使用者只要上下捲就能讀完所有內容。這個寬度對應最窄的常見手機，也對應另一種很常見的情況：使用者把 1280px 寬的瀏覽器放大到 400%，頁面可用的寬度就只剩 320 CSS px。所以「320px 不能橫向捲動」不是挑剔，是視力不好的使用者能不能用這一頁的底線。

在 320px 寬時，這張卡片有三個地方各自把頁面撐寬，每一個單獨存在都足以讓整頁可以左右滑：

  1. 卡片本身：寫了 width: 340px，實際卻佔 382px，比手機還寬。
  2. 圖片：固定 300px，就算卡片縮小了，它也不會跟著縮。
  3. 長字串：品名裡的 Supercalifragilisticespresso 和一段長網址中間沒有空白，瀏覽器找不到可以換行的地方，只好讓它伸出去。

最常見的「修法」是在 body 加 overflow-x: hidden。捲軸確實消失了，但卡片的右半邊還是被切掉，使用者只是滑不過去看而已；問題沒有修，只是被藏起來。正確的做法是三個原因一個一個拆開。先從第一個開始：明明寫了 340px，多出來的 42px 是從哪來的？

卡片寫 340px，為什麼實際佔 382px？

要回答這個問題，得先知道瀏覽器怎麼看待一個元素。瀏覽器把頁面上每個元素都當成一個矩形盒子，這套描述盒子由哪幾層組成、每層多大的規則，叫做盒模型（box model）。盒子由內到外分四層：

  • content（內容）：文字、圖片實際放的地方。
  • padding（內距）：內容和邊框之間的空間。它屬於元素自己，所以會顯示元素的背景色；卡片的米色背景會延伸到 padding 的範圍。
  • border（邊框）：包住 padding 的那一圈線，卡片的 1px solid #d6c3a8 就是它。
  • margin（外距）：邊框外面的透明空間。它不屬於元素的外觀，作用是把旁邊的元素推開。

有了這四層，問題就變成：width: 340px 量的是哪一層？答案由 box-sizing 這個屬性決定，它規定 width、height 要量到哪一層為止：

值width 量到width: 340px; padding: 20px; border: 1px 實際寬
content-box（預設）只有內容340 + 40 + 2 = 382px
border-box內容＋padding＋border340px（內容剩 298px）

瀏覽器的預設值是 content-box：width 只量最裡面的內容，padding 和 border 另外往外加。卡片的 382px 就是這樣來的：340 的內容，加上左右各 20px 的 padding，再加上左右各 1px 的 border。不管是哪一種，margin 都不算在 width 裡，它是盒子外面的空間。

content-box 的麻煩不只是要心算。只要元素有 padding，寫 width: 100% 就一定比父元素寬，因為 100% 先佔滿了父元素，padding 再往外加；改了 padding，實際寬度也跟著變。border-box 則讓「寫多少就是多少」：padding 和 border 從 width 裡面扣，內容自己變窄。所以幾乎每個專案的 reset 都會先寫這一段，讓全站一律用 border-box：

@layer reset {
  *, *::before, *::after {
    box-sizing: border-box;
  }
}

這段為什麼要另外列 ::before、::after？它們是偽元素：由 CSS 產生、HTML 裡沒有的元素，例如在價格前面用 CSS 加一個「NT$」。* 只選得到 HTML 裡真的有的元素，選不到偽元素，所以要明寫。整段放進第 6 課教過的 reset layer，因為它在最低層，任何元件要改回 content-box 都蓋得過它。

回到卡片：加上這段之後，width: 340px 的卡片實際就是 340px。想確認一個元素到底多寬、每層各佔多少，在 DevTools 的 Elements 面板選取它，Computed 分頁最上面有一張盒模型圖，四層的數字都在上面；滑鼠移到元素上，頁面也會用不同顏色標出 content、padding、margin。遇到「為什麼它比我寫的寬」，先看這張圖。

💡 實務上：接手專案先確認 reset 裡有沒有 border-box
多數專案的 reset 或 CSS 框架（例如 Tailwind 的 Preflight）都已經設好 border-box，接手時先打開 reset 檔確認，不要在元件裡各寫一次。真正會出事的是混用：舊頁面、嵌進來的第三方小工具（訂位表單、地圖、客服聊天視窗）可能假設 content-box，放進你的頁面後寬度就差了幾十 px。遇到「別人的元件在我們頁面上變窄或變寬」，第一個查的就是 Computed 裡的 box-sizing。

不過 border-box 只讓數字變誠實：340px 的卡片現在真的是 340px，但 340 還是比 320 寬。下一步是讓它在窄螢幕上縮小。

340px 還是比手機寬：怎麼讓卡片和圖片跟著螢幕縮？

固定 px 寬度的問題是它只在某些螢幕寬度下剛好。設計稿上的 340px，在 1280px 的桌機上綽綽有餘，在 320px 的手機、或放大 400% 的瀏覽器上就超出去。我們真正想要的是「最多 340px，空間不夠時就跟著變窄」，也就是給上限，不給定值：

.card {
  max-width: 340px;   /* 最多 340，空間不夠時跟著父元素縮小 */
}
img {
  max-width: 100%;    /* 圖片不超過父元素的內容寬 */
  height: auto;       /* 寬度縮小時高度等比例縮，不變形 */
}

為什麼卡片拿掉 width 只寫 max-width 就夠了？因為卡片是 block 元素。div、article 這類元素預設是 block，意思是自己佔一整行；寬度沒寫時是 width: auto，也就是撐滿父元素的內容寬。下一節會完整講 block 和 inline 的差別。在 320px 的手機上，它撐滿可用的寬度；在桌機上，它想撐滿但被 max-width: 340px 擋住，停在 340px。一行就同時滿足兩種螢幕。

你可能會想改寫成 width: 100%，看起來跟 auto 一樣是「撐滿」。差別在 content-box 下：width: 100% 是先讓內容寬等於父元素，再把 padding、border 往外加，所以一定超出；auto 則會自動扣掉 padding 和 border。這是統一用 border-box 的另一個原因，也是多數時候乾脆不寫 width 的原因。

圖片也是同一個想法。max-width: 100% 讓它最多跟父元素的內容一樣寬，手機上卡片內容比 300px 窄時，原本 300px 的圖就縮到跟內容一樣寬。卡片的圖片在 HTML 裡寫了 <img width="300" height="200">，這兩個屬性會成為圖片的預設尺寸。只縮寬度的話，高度會停在 HTML 屬性寫的 200px，整張圖被壓扁；加上 height: auto，高度就依原本的寬高比跟著縮。

其他尺寸寫法（百分比相對於誰、fit-content、min-content、aspect-ratio）整理在課末的「補充與查表」，這張單用不到。

卡片和圖片現在都會縮了。但如果仔細看，圖片和下面的品名之間多了一條幾 px 的縫，padding 和 margin 都沒寫，卻怎麼量都在。這條縫跟尺寸無關，跟元素「怎麼排」有關。

圖片底下為什麼多一條縫？沒寫 flex、grid 時元素怎麼排

沒有寫 flex、grid、position 時，瀏覽器用一套預設規則排版，叫正常流（normal flow）。它把元素分成兩大類，排法完全不同：

  • block：自己佔一整行，由上往下一個接一個疊。div、p、h2、article 預設是 block。卡片、卡片裡的品名和說明，都是這樣一塊一塊往下排。
  • inline：像文字一樣，在一行裡由左往右排，排不下就換到下一行。a、span、strong 預設是 inline，還有 <img>。

一個元素屬於哪一類，由 display 屬性決定。每個元素都有預設值，也可以用 CSS 改。常用的四個值：

display怎麼排width／height垂直 margin、padding
block自己佔一整行，寬度預設撐滿父元素的內容寬有效有效
inline跟文字一起排在行裡，寬度由內容決定無效margin 無效；padding 會畫出來，但不會把上下兩行推開
inline-block像 inline 一樣排在行裡，裡面像 block有效有效
none不產生盒子，不佔空間，螢幕閱讀器也讀不到——

表裡最常讓人卡住的是 inline 那一列。inline 元素是文字的一部分，它的寬度由裡面的文字決定，高度由行決定，所以「幫 <a> 設 width: 200px、margin-top: 16px 沒反應」是正常的：width 被忽略，垂直 margin 也不會改變行的位置。要讓連結像按鈕一樣有自己的尺寸，就改它的 display：inline-block 讓它還待在文字行裡、但吃得到 width；block 讓它自己佔一行。

現在可以解釋那條縫了。<img> 預設是 inline，所以瀏覽器把它當成一行文字裡的一個「字」來排。文字是坐在基線（baseline）上的：基線是一行字底部對齊的那條線，g、y 這類字母的尾巴會掛到基線下面。為了留位置給這些尾巴，行在基線下方還有一小段空間。圖片坐在基線上，下面那一小段空間就變成那條縫。修法是讓圖片不要當文字：

.card img {
  display: block;   /* 自己佔一塊，不再坐在文字的基線上 */
  max-width: 100%;
  height: auto;
}

正常流的這兩種排法，接下來兩節各會用到一次。inline 內容「排不下就換行」有一個前提：要有可以換行的地方，而長品名正好沒有。block「由上往下一個接一個疊」，疊起來的兩塊之間距離由 margin 決定，第 2 張單就出在這裡。先處理第 1 張單剩下的長字串。

長品名為什麼伸出卡片？內容比容器大時怎麼辦

上一節說 inline 內容排不下就換行，但瀏覽器不是在任何位置都能換行。它只在空白、標點、中日韓文字之間這類斷點換行。中文每個字之間都是斷點，所以中文很少出問題；英文的長單字和網址中間沒有空白，從頭到尾沒有一個斷點。Supercalifragilisticespresso 寬度比卡片內容還寬，瀏覽器找不到地方拆，只好讓它整串伸出卡片。

這種內容超出容器的情況叫溢出（overflow）。瀏覽器預設的處理方式是 overflow: visible：溢出的內容照樣畫出來，壓到旁邊的元素上，而且會把整頁撐寬。這就是第 1 張單的第三個原因。處理溢出有兩條路：讓內容換行，留在容器裡；或內容就是不該換行，那就決定超出的部分要捲動還是裁掉。

讓長字串換行：overflow-wrap

品名和網址是要讓人讀的，應該完整顯示，所以走第一條路：告訴瀏覽器「真的放不下時，可以在沒有斷點的地方拆開」。有三個屬性做得到類似的事，差別在拆得多積極：

寫法效果適合
overflow-wrap: anywhere只有一整行都放不下時，才在任意位置拆開；計算 min-content 寬度時也把這些斷點算進去使用者輸入的內容、品名、網址。首選
overflow-wrap: break-word跟 anywhere 一樣拆，但計算 min-content 時不算，所以在 flex 項目、fit-content 裡仍可能把容器撐開舊寫法，新程式用 anywhere
word-break: break-all每個英文單字都可以在行尾被拆開，連 Coffee 都會變成 Cof／fee幾乎不用；只有像序號、雜湊值的欄位才合理

表裡的 min-content 寬度是「這個元素最窄能縮到多寬」，通常等於裡面最長那段拆不開的字串的寬度。有些版面（第 8 課的 flex、尺寸設成 fit-content 的元素）會參考這個值決定元素多寬，所以 break-word 雖然畫面上也會拆，但在這些版面裡元素可能先被撐寬，anywhere 就沒有這個問題。

關鍵的差別在「什麼時候拆」。anywhere 和 break-word 只拆放不下的字串，說明裡的 Coffee 放得下，就不會被動到；break-all 則讓每個英文單字都能在行尾被切開，整段英文會變得很難讀。overflow-wrap 是會繼承的屬性，設在卡片上，裡面的品名、說明、網址都會跟著生效：

.card {
  max-width: 340px;
  overflow-wrap: anywhere;
}

到這裡，第 1 張單的三個原因都處理完了：border-box 讓 width 誠實、max-width 讓卡片和圖片跟著縮、overflow-wrap 讓長字串換行。這正是練習 1 要你做的事。

不該換行的內容：捲動還是裁切

不是每種內容都適合換行。很寬的表格、程式碼，拆開反而讀不懂；第 3 張單的公告列，則是希望它只佔一行。這時候走第二條路：用 overflow 屬性決定超出的部分怎麼處理。

讀這張表之前先認識一個名詞：捲動容器（scroll container）。它是內容可以在裡面捲動的盒子，可能有捲軸給使用者拖，也可能沒有捲軸、但程式還是能捲它。一個元素變成捲動容器，會影響裡面的其他行為，下面會看到。

值溢出的內容是捲動容器？建立 BFC？
visible（預設）照樣顯示在外面否否
hidden裁掉，沒有捲軸；但程式（scrollTop、scrollTo()）和 Tab 聚焦仍會把它捲進來是是
clip裁掉，任何方式都捲不動否否
auto溢出時才出現捲軸是是
scroll一律顯示捲軸位置是是

最後一欄的 BFC 留到下一節講 margin 時再解釋。選法依內容而定：

  • 本來就可能很寬的內容（表格、程式碼）：外面包一層 overflow-x: auto，讓它在自己的範圍裡左右捲，頁面本身不會被撐寬。這門課的表格都包在 .table-wrap 裡，就是這樣做的。
  • 只想裁掉一點邊角（例如圓角卡片裡的圖片角落）：用 overflow: clip 就夠了，它只裁切，不會變成捲動容器。

為什麼在意「是不是捲動容器」？因為 position: sticky 會受影響。sticky 是讓元素在捲動時黏在畫面某處的定位方式，例如捲動菜單時一直黏在頂端的分類列（第 10 課）。它黏的對象是離它最近的捲動容器。外層設了 hidden 或 auto，它就改黏在那個外層上，而那個外層通常不會捲，看起來就像 sticky 失效了，這是 sticky 失效最常見的原因；clip 不會造成這個問題。

這也說明了開場那個「修法」為什麼不行：body 加 overflow-x: hidden，除了把被切掉的內容藏起來，還可能讓頁面裡的 sticky 失效。反過來，clip 也有自己的坑：被它裁掉的連結、按鈕，按 Tab 仍會拿到焦點，卻不會被捲進畫面，鍵盤使用者就找不到焦點在哪。所以裁切只適合裁掉裝飾性的邊角，不適合拿來藏可以操作的內容。

第 3 張單：公告列只顯示一行，放不下就顯示 …

公告列的需求是「一行放不下就顯示省略號」，表格欄位、訂單列表也常這樣做。它需要三個屬性一起寫，缺一個都不會出現省略號：

.notice {
  white-space: nowrap;      /* 不換行，文字才會超出 */
  overflow: hidden;         /* 把超出的部分裁掉 */
  text-overflow: ellipsis;  /* 在裁掉的地方畫 … */
}

三者的關係是一條因果鏈：white-space: nowrap 禁止換行，文字才會在同一行超出容器；overflow: hidden 把超出的部分裁掉；text-overflow: ellipsis 只負責在「被裁掉的地方」畫上 …。所以只寫 text-overflow 不會有任何效果，它需要元素本身是 block（或 inline-block）、而且 overflow 不是 visible，也就是真的有東西被裁掉。

省略號只是畫面上的處理，完整文字仍在 DOM 裡，螢幕閱讀器會讀全文。但看得到畫面的使用者讀不到被截掉的部分，所以重要的內容要提供看到全文的方式：點進詳細頁，或聚焦、展開時改回換行（練習 3 用鍵盤聚焦時展開）。不要在 JavaScript 或伺服器端用固定字數截斷字串：同樣 20 個字，在不同字型、寬度、語言下佔的寬度都不同，截完不是太短就是還是溢出，而且全文就真的不見了。最多顯示三行這類多行省略的寫法，見課末的「補充與查表」。

💡 實務上：會溢出的，幾乎都是別人輸入的文字
你寫死的文案自己看得到；真正撐破版面的是店員在後台新增的品名、顧客的評論和 Email、訂單備註、從 API 拿到的網址。季節特調的長品名就是這樣來的。所以列表、卡片這類顯示資料的地方，一開始就加 overflow-wrap: anywhere，測試時也刻意塞一個超長英文字和一段很長的中文。要不要用省略號，先跟 PM 確認哪些欄位可以截斷：價格、過敏原、取貨時間這種資訊一截掉就可能出錯，寧可換行也要完整顯示。

第 1、3 張單都修好了，剩下門市資訊區塊。它的問題不在某個元素太寬，而在前面講正常流時提過的另一半：block 由上往下一個接一個疊，兩塊之間的距離由 margin 決定，而上下的 margin 有一條反直覺的規則。

第 2 張單：門市卡片之間的 24 加 32，為什麼等於 32？

先看門市資訊區塊原本的 CSS。區塊有米色背景，標題 h2 上方留 24px，每張門市卡片上方 32px、下方 24px：

.stores { background: #f3e9dc; }
.stores h2 { margin-top: 24px; }
.store-card {
  padding: 16px;
  margin-top: 32px;
  margin-bottom: 24px;
}

直覺上，第一張卡片下方 24px 加第二張卡片上方 32px，兩張之間應該是 56px，但量出來是 32px。這是正常流的一條規則，叫外距合併（margin collapsing）：在正常流裡，兩個相鄰的垂直 margin 不相加，而是取較大的那一個。

這條規則是為文章設計的。每個 <p> 上下都有 1em 的 margin，如果相加，兩段之間就變成 2em；合併之後，兩段之間是 1em，段落的間距才自然。對連續的段落和標題，這正是想要的結果。但在元件裡，它常常造成意外，第 2 張單的兩個症狀就是其中兩種。會合併的情況有三種：

  1. 相鄰的兄弟元素：上一張卡片的 margin-bottom: 24px 和下一張的 margin-top: 32px，中間只剩 32px。這是第 2 張單的第二個症狀。
  2. 父元素與第一個（或最後一個）子元素之間沒有東西隔開：父元素沒有 padding、border、文字，子元素的 margin-top 就會跟父元素的 margin 合併，表現在父元素外面。門市區塊的 h2 有 margin-top: 24px，而 section 沒有 padding，這 24px 就穿出 section，跑到它的上方。section 的米色背景只畫在自己的盒子裡，包不住外面那段空白，整個區塊看起來像被往下推。這是第一個症狀。
  3. 空元素：沒有內容、padding、border、height 的元素，自己的上下 margin 會合併成一個。

反過來，這些情況不會合併：水平方向的 margin、flex 與 grid 容器裡的子元素、float 與 position: absolute 的元素（第 10 課），以及建立了新 BFC 的父元素與它的子元素之間。最後這一項要先解釋 BFC 是什麼，因為它是修第一個症狀的工具之一。

BFC：在元素周圍畫一道牆

一塊區域裡要用哪一套規則排版，叫做這塊區域的格式化上下文（formatting context）。正常流裡把 block 盒子由上往下疊的那一套規則，叫做 BFC（block formatting context，區塊格式化上下文）。整個頁面本身就是一個 BFC，所有 block 都在裡面一起排，所以它們的 margin 才會互相合併。

某些元素會在自己裡面開一個新的 BFC。建立新的 BFC 等於在這個元素周圍畫一道牆：牆裡面的子元素自己排，它們的 margin 不會穿過牆跟外面的合併。同樣地，float 也不會跑出這道牆。float 是讓元素靠左或靠右、文字繞著它排的舊排版方式，現在很少用來排版，但你在舊程式碼裡會看到。

很多屬性都會順帶建立新的 BFC，例如上一節表格裡的 overflow: hidden、auto，但它們同時帶來裁切、捲動容器這些副作用。display: flow-root 是專門用來「建立新的 BFC、其他什麼都不改」的值，目前瀏覽器已普遍支援。flex 與 grid 容器也會建立自己的格式化上下文，效果類似，所以它們的子元素不會發生 margin 合併。

修法：依情況選

理解了合併的原因，修法就不是去湊數字，而是讓距離由正確的地方決定：

情況修法為什麼
子元素的 margin 穿出父元素父元素加 padding（通常本來就需要），或 display: flow-rootpadding 把兩個 margin 隔開；flow-root 建立新的 BFC
一列卡片之間的距離父元素用 display: grid（或 flex）加 gap，子元素不寫 margin間距由容器統一管理，第一張上面、最後一張下面不會多出空白，也不會合併
文章內的段落、標題保留 margin 合併，統一只寫一個方向，例如只寫 margin-block-end正常流的文字內容就是為這個設計的

表中第二列的 gap 是容器裡子元素之間的間距，只在 flex、grid 這類容器有效，第 8、9 課會再用到。它只加在子元素「之間」，不加在第一個前面或最後一個後面，而且 grid 容器裡沒有 margin 合併的問題，寫 24 就是 24。

套到門市區塊：section 加上 padding，h2 的 margin 就被隔在 section 裡面，背景包得住；卡片的外層 .store-list 改成 grid 加 gap: 24px，卡片自己不再寫 margin。這就是練習 2。

從這裡可以推出一個更一般的原則：元件不在自己的最外層寫 margin。門市卡片不知道自己會被放在哪裡，可能是門市列表、可能是首頁側欄；外面要留多少距離是父層版面的事，交給 gap。這樣同一個元件放在任何地方都不會帶著意外的空白，也不會跟鄰居合併。

用負 margin 把多出來的距離「扣回來」（例如 margin-top: -8px）只是抵銷了合併的結果。內容一變（標題換行、多一張卡片、改了字級），數字就不對了，而且下一個人看不懂為什麼是 -8。
💡 實務上：設計稿上的間距，多半對應到 gap
設計師在 Figma 用 Auto layout 排卡片時，設定的「項目間距」就是 CSS 的 gap，對照時直接寫在父層，不要拆成每張卡片的 margin。門市卡片之間的 24px 就該寫在 .store-list 上。團隊通常也會把間距收斂成固定的幾個值（例如 4、8、16、24、32），寫成變數共用（第 16 課的 design token）。Code review 看到元件最外層有 margin、或出現 -8px 這種數字，資深工程師會先問：「這段距離應該是誰的責任？」答案通常是父層。

三張單都有答案了。但下次遇到的不會剛好是這三種，更常見的是「頁面可以左右滑，不知道是誰撐破的」。最後整理一套從症狀找到原因的查法。

下次遇到版面問題，怎麼自己找出原因？

這課的每一節都對應一種常見的版面症狀。實際遇到時，先依現象找到對應的那一節，再用 DevTools 找證據：

  • 頁面可以左右滑（第 1 張單）：在 DevTools Console 執行下面這段，列出右緣超出畫面的元素，從最外層的那個開始看。找到原因再修，不要用 overflow-x: hidden 蓋掉。 
    [...document.querySelectorAll('body *')].filter(e => e.getBoundingClientRect().right > document.documentElement.clientWidth)
  • 元素比預期寬或高：看 Computed 的盒模型圖，確認 box-sizing、padding、border；固定的 width 改成 max-width。
  • 多出（或少了）一段空白（第 2 張單）：滑鼠移到元素上看橘色的 margin 區域是不是跑到父元素外面；是的話就是 margin 合併。
  • 設了 width、margin 沒反應：看 Computed 的 display，inline 元素不吃 width 與垂直 margin。

DevTools 的完整操作在第 18 課。

補充與查表

尺寸寫法對照（查表用，不用背）：

寫法相對於／意思常見用途
width: 50%父元素的內容寬兩欄並排
height: 50%父元素的高度；父元素高度是 auto（由內容決定）時無效少用，高度通常讓內容決定
padding-top: 10%注意：上下 padding 的百分比也是相對於父元素的寬度以前用來做固定比例的盒子，現在直接寫 aspect-ratio: 16 / 9（寬高比）
min-width／max-width下限／上限，優先於 width內容區最多 40rem、按鈕至少 44px
width: fit-content內容需要多寬就多寬，但不超過可用空間（除非連最長的單字都放不下）標籤、徽章、置中的按鈕
width: min-content縮到最窄：最長的那個單字（或圖片）的寬度讓圖說跟圖片一樣寬
width: max-content完全不換行的寬度，可能超出容器不換行的選單項目，小心溢出

flex 項目的最小寬度：還有一個跟尺寸有關的坑留到第 8 課：flex 項目預設 min-width: auto，不會縮到比內容的 min-content 還窄，長標題就會把 flex 項目撐開，要寫 min-width: 0。

display 其實是兩件事：CSS 規範把 display 拆成兩層：外部是「我在父元素裡怎麼排」（block 或 inline），內部是「我的子元素怎麼排」（flow、flex、grid…）。所以 display: flex 的完整寫法是 display: block flex：自己像 block 一樣佔一行，子元素用 flex 排；inline-flex 就是 inline flex。第 8、9 課的 Flexbox、Grid 改的是內部那一層。

IFC：正文講的 BFC 管 block 盒子怎麼疊；一行裡排 inline 內容的那一套叫 IFC（inline formatting context），這課不需要深入。

多行省略：多行省略（例如最多三行）的標準寫法 line-clamp 還不是 Baseline（第 4 課介紹過的瀏覽器支援度標籤；查詢版本 web-features 3.44.0）；目前普遍可用的是帶前綴的舊寫法：

.desc {
  display: -webkit-box;
  -webkit-box-orient: vertical;
  -webkit-line-clamp: 3;
  overflow: hidden;
}

練習

練習 1：修好季節特調的菜單卡片：320、375、768px 寬時整頁都不能橫向捲動，卡片不比外層寬、圖片不比卡片內容寬，長品名與長網址在卡片裡換行（但 Coffee 這種普通單字不能被拆開）；768px 以上卡片維持設計的 340px 寬。HTML 不能改。不能用 overflow-x: hidden 把問題藏起來。

練習 2：門市資訊區塊有兩個間距問題：h2 上方的空白跑到 section 外面，背景色沒有包住它；兩張門市卡片之間應該是 24px，現在卻是 32px。修好這兩處，間距要用 padding、gap 或明確的規則做出來，不能用負 margin 湊數字。HTML 不能改。

練習 3：頁面頂端的公告列太長，在手機上變成三、四行。改成只顯示一行、放不下的部分顯示省略號；完整文字要留在 HTML 裡（不要自己截斷），而且鍵盤使用者按 Tab 聚焦到公告的連結時，公告要換行展開，看得到全文。提示：父元素裡有東西被聚焦時，:focus-within 會成立。

練習 4：width: 300px; padding: 20px; border: 1px solid;，box-sizing 是預設的 content-box，這個元素實際佔多寬？

✓ b：content-box 的 width 只算內容，再加左右 padding 40px、左右 border 2px，共 342px。a 是 border-box 的結果。c 漏了 border、而且 padding 只算一邊。d 是 border 只算一邊。

練習 5：<header> 沒有 padding 與 border，裡面第一個元素 <h1> 有 margin-top: 32px，會發生什麼？

✓ b：父元素與第一個子元素之間沒有 padding、border、文字，也沒有建立新的格式化上下文時，子元素的 margin-top 會跟父元素的合併，表現在父元素外面。a、d 是 header 加了 padding 或 display: flow-root 之後的樣子。c 錯：margin 還在，只是位置不在你預期的地方。

練習 6：要把圓角卡片超出的圖片角落裁掉，而且不想讓卡片變成可以被程式捲動的捲動容器，用哪個？

✓ b：clip 單純裁切，不是捲動容器，也不建立新的 BFC。a 錯：hidden 仍是捲動容器，scrollTop 與 Tab 聚焦都能把內容捲進來，裡面的 sticky 也會改黏在它上面。c 錯：溢出時會出現捲軸。d 錯：它把整個元素藏起來，跟裁切無關。

常見錯誤

  • body 加 overflow-x: hidden：只是把撐破的元素藏起來，內容照樣被切掉，還可能讓 position: sticky 失效。用課文裡的 Console 片段找出真正溢出的元素。
  • 固定 px 寬度：在 320px 的手機或放大 400% 時就壞。用 max-width、百分比，讓 block 元素自己撐滿。
  • width: 100% 加 padding：content-box 下一定比父元素寬。全站設 box-sizing: border-box，或乾脆不寫 width。
  • word-break: break-all：每個英文單字都可能被拆開。長網址、長單字用 overflow-wrap: anywhere，只有放不下時才拆。
  • 只寫 text-overflow: ellipsis：沒有 white-space: nowrap 文字會換行，沒有 overflow: hidden 就沒有被裁掉的地方，省略號不會出現。三個一起寫。
  • 用負 margin 修間距：掩蓋 margin 合併，換個內容就壞。父元素用 padding 或 flow-root，一列元素用 gap。
  • 元件最外層寫 margin：元件放到別的地方就帶著多餘的空白，還會跟鄰居合併。外面的距離交給父層的 gap。

小結

  • 每個元素是 content、padding、border、margin 四層的盒子。預設 content-box 的 width 只算內容；全站設 box-sizing: border-box，width 就包含 padding 與 border（第 1 張單：寫 340 卻佔 382，改 border-box 後就是 340）。
  • 寬度用 max-width 給上限、不給定值；block 元素的 width: auto 本來就撐滿父元素。圖片 max-width: 100% 加 height: auto。
  • 正常流裡 block 由上往下疊、inline 在行裡由左往右排；inline 元素不吃 width 與垂直 margin。<img> 預設 inline，底下的縫來自文字基線，改 display: block。
  • 溢出：瀏覽器只在斷點換行，長字串用 overflow-wrap: anywhere；可能很寬的內容用 overflow-x: auto 自己捲動；裁切用 clip；單行省略號是 nowrap＋overflow＋text-overflow 三件套，完整文字留在 HTML 裡（第 3 張單）。
  • 相鄰的垂直 margin 取較大的那一個；父子之間沒隔開時子元素的 margin 會穿出去。用 padding、flow-root（建立新的 BFC）、gap 控制間距，不用負 margin（第 2 張單）。
