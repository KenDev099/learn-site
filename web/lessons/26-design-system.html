階段 6：資深整合實戰 · 第 26 課

設計系統：design tokens、元件狀態、文件與版本（資深）

咖啡店現在有三個前端產品：官網、線上點餐、店內的點餐平板。三個團隊各自寫按鈕，結果「加入購物車」在官網是圓角棕色、在點餐頁是直角深咖啡色、在平板上 hover 會變淺色而且文字對比只有 3:1；載入中的樣子有三種，其中一種會讓鍵盤使用者的焦點直接消失。品牌色一改，三個專案各自搜尋取代，總有地方漏掉。

這一課的任務是：做出一顆三個產品共用的「加入購物車」按鈕，而且要做到四件事：品牌色只改一個地方，三個產品一起變；每個狀態（滑鼠、鍵盤、螢幕閱讀器、送出中）都做對；別的團隊拿到它知道怎麼用、不會用錯；之後改版不會悄悄弄壞別人。第 16 課把顏色、間距整理成 CSS 變數，解決的是「一個專案裡」的一致；這一課往上一層，處理好幾個專案、好幾個團隊共用同一套決策與元件。

這課的路線：
  1. 這該用設計系統解決嗎？先看三顆按鈕為什麼會越長越不一樣，設計系統包含哪些部分，什麼時候還不值得做。
  2. 品牌色存在哪裡、寫成什麼格式、怎麼變成 CSS：design tokens 的三層、DTCG 交換格式，以及轉換時為什麼別名要輸出 var()。
  3. 按鈕的每個狀態都做對了嗎：先列狀態矩陣，再用 DOM 本身的狀態寫樣式；送出中為什麼不用 disabled。
  4. 別的團隊怎麼用對、改版會不會弄壞他們：元件文件、語意化版本與棄用流程。
  5. Vue 元件怎麼把這一切接起來：props 一對一對應狀態矩陣。
這課會用到：
  • 第 16 課的兩層變數：palette 描述顏色本身，語意變數描述用途；元件只用語意變數，換主題只改語意層。
  • 第 5 課的焦點與對比：:focus-visible 只在鍵盤操作時顯示焦點框；一般文字對比至少 4.5:1。

「加入購物車」為什麼會長成三個樣子？這該用設計系統解決嗎？

先看問題是怎麼長出來的。三個團隊都沒有做錯什麼：每個人寫按鈕時都要決定一堆事，底色用哪個棕、hover 深多少、圓角幾 px、載入中長什麼樣、焦點框怎麼畫。沒有共同的地方可以查，每個團隊就各自決定一次，再把決定的結果（色碼、px 值）直接寫進自己的程式。三份決定一開始可能差不多，但之後每次調整都只發生在一個專案裡，差異就越來越大。

這也解釋了「品牌色一改總有地方漏掉」：色碼被抄進了幾百個地方，每一處都是一份獨立的副本，搜尋取代只能祈禱沒有漏掉 #6E401E 大寫、rgb() 寫法或某個 hover 色。平板 hover 對比只有 3:1、某種載入樣式讓焦點消失，也是同一個原因：無障礙問題在一個專案修好了，另外兩個專案不會知道。

根本的解法是讓這些決定只存在一個地方，三個產品都去讀它。把這件事做成一套東西，就是設計系統（design system）：一組可以重複使用的設計決策、元件與規範，加上維護它們的流程。它不只是一個元件庫，通常包含五個部分，每個部分都對應開場的一種問題：

部分是什麼咖啡店的例子
design tokens設計決策的最小單位：有名字的顏色、間距、圓角、動畫時間color.action.primary = 咖啡棕
元件（component）用 tokens 組出來、可以直接用的 UI 單位按鈕、輸入框、商品卡
模式（pattern）元件的組合方式，解決一類問題表單錯誤的呈現方式、結帳步驟
文件什麼時候用、什麼時候不用、可及性需求、範例「危險操作用 danger 按鈕，並且要二次確認」
治理（governance）誰可以改、怎麼提案、怎麼發版、怎麼棄用每週一次審查、變更紀錄、SemVer

對照我們的任務：「品牌色改一處就全部變」靠 tokens；「每個狀態都做對」靠元件；「別的團隊用對」靠文件；「改版不弄壞別人」靠治理。模式是元件之上的下一層，這課的按鈕還用不到。

做好之後得到三件事：一致（三個產品的按鈕長一樣，行為也一樣）、速度（做新頁面不用重新決定按鈕的 hover 色）、無障礙內建（焦點框、對比、鍵盤操作在元件裡做對一次，所有使用的地方都對）。第三點最常被低估：一個按鈕元件修好焦點問題，比去三個專案各修一百個按鈕便宜得多。

代價也要講清楚：設計系統是一個要有人長期維護的產品。它需要文件、版本、相容性考量，每次改動都要想「會不會弄壞別人」。什麼時候不值得做：只有一個產品、一個小團隊、設計還在快速試錯時，第 16 課的 CSS 變數加上幾個共用元件就夠了；過早抽象會讓每個改動都卡在「要不要進設計系統」。常見的觸發點是：第二個產品出現、第二個團隊開始複製貼上元件、或同一個無障礙問題在不同地方被回報第三次。咖啡店三個條件都碰到了，所以值得做。

💡 實務上：多數團隊是「站在現成元件庫上」做設計系統
很少公司從零寫每個元件：常見做法是挑一個成熟的元件庫（例如 Vue 生態的 Naive UI，或只給行為、不給樣式的 headless 元件庫），再用自己的 tokens 套上品牌外觀。這樣鍵盤操作、焦點管理這些難做對的部分有人維護，你的團隊專心在 tokens、文件與治理。要考量的是：現成元件的 DOM 與 API 不是你決定的，對方發 MAJOR 時你也得跟著升級。資深工程師提案前會先問：現有元件庫能不能靠主題設定滿足設計？哪幾個元件真的需要自己做？誰負責長期維護？咖啡店的「加入購物車」不管自己寫還是套現成元件庫，下面講的 tokens、狀態與版本都一樣要處理。

決定要做之後，第一件事是把「決定」收到一個地方。最先要收的是品牌色：它要存在哪裡，三個產品才會一起換？

品牌色要存在哪裡，三個產品才會一起換？

第 16 課的答案是 CSS 變數：--color-action-primary 定義一次，元件都用 var() 讀它。在一個專案裡這就夠了。但現在有三個專案，CSS 變數寫在某個專案的 CSS 檔裡，另外兩個專案要嘛複製一份（又回到副本的問題），要嘛直接 import 對方的 CSS。更麻煩的是設計師：他在 Figma 裡用的品牌棕，跟程式裡的 --color-action-primary 是兩份各自維護的值。如果之後點餐平板改成原生 App，Swift 程式也讀不了 CSS 檔。

所以設計系統把決定再往上提一層，寫成跟平台無關的資料，這就是 design token：一個有名字的設計決策，例如「主要操作的顏色是咖啡棕」。它跟第 16 課的 CSS 變數差在：token 是跟平台無關的資料，同一份 tokens 可以轉成 CSS 變數、iOS 的 Swift 常數、Android 的 XML 資源，設計工具（例如 Figma）也讀得懂。這樣設計師改一個值，網頁、App 都跟著改。CSS 變數從「正本」變成「從 tokens 產生出來的一種輸出」。

三層：原始、語意、元件

tokens 的名字怎麼取，決定了之後改起來有多痛。第 16 課有兩層：palette 描述顏色本身（brown-700），語意變數描述用途（action-primary）。換主題時只改語意層指向哪個 palette 色，元件完全不用動。

三個產品共用之後，會出現兩層不夠用的需求。假設行銷說「加入購物車的按鈕主色深一點，但連結不要變」。按鈕和連結都用 color.action.primary，改它兩個一起變；不改它，按鈕又沒有自己的地方可以改。設計系統的做法是再多一層元件 token，專門描述「某個元件的某個部位」：

每一層都只指向上一層，不直接寫值。表格整理每一層的用途與影響範圍：

層名字描述誰可以用改它的影響
原始（primitive）外觀：color.brown.700、space.4只有語意 token所有參照它的語意 token
語意（semantic）用途：color.action.primary、color.text.muted元件 token、一般頁面整個產品裡這種用途的地方（換主題、改品牌）
元件（component）元件的部位：button.primary.bg只有那個元件只有那個元件

回到行銷的需求：改 button.primary.bg 指向 color.action.hover 就好，連結、標籤不受影響。這就是元件層的價值：隔離。代價是 token 數量變多，每個元件都多出一組名字要維護。小型系統可以先只有兩層，等真的出現「某個元件要跟語意色不同」的需求再加元件層；但元件的 CSS 一開始就只用語意層或元件層，不直接用原始色，這條不要妥協。元件一旦直接寫 var(--color-brown-700)，換主題時它就不會跟著換，等於又回到開場的狀況。

層次定下來了，接著要把它們真的寫成一個檔案。這個檔案要同時讓設計工具、轉換工具、各平台都讀得懂，那就得有大家都認得的格式。

tokens 檔怎麼寫，又怎麼變成瀏覽器看得懂的 CSS？

為什麼需要共同格式：DTCG

如果每個工具各有一種 tokens 格式，Figma 外掛匯出的檔案，轉換工具讀不懂，就得再寫一層轉接程式，每換一個工具就多一層。DTCG（Design Tokens Community Group）是 W3C 底下的社群小組，它定義的 Design Tokens Format Module 2025.10 就是這個共同格式（它的正式地位見課末）。內容是 JSON，下面是咖啡店 tokens 的一小段，這課後面都用它：

{
  "color": {
    "$type": "color",
    "$description": "咖啡店的色彩",
    "brown": {
      "700": { "$value": { "colorSpace": "srgb", "components": [0.431, 0.251, 0.118], "hex": "#6e401e" } }
    },
    "action": {
      "primary": { "$value": "{color.brown.700}", "$description": "主要按鈕、連結" }
    },
    "primary": {
      "$value": "{color.action.primary}",
      "$deprecated": "改用 color.action.primary，3.0 移除"
    }
  },
  "space": {
    "$type": "dimension",
    "4": { "$value": { "value": 1, "unit": "rem" } }
  },
  "duration": {
    "$type": "duration",
    "fast": { "$value": { "value": 120, "unit": "ms" } }
  }
}

讀這個檔案要知道四條規則，後面寫轉換程式（練習 1）也是照這四條：

第一，怎麼分辨 token 和群組（group）。有 $value 的物件是 token，沒有的是群組，群組只是用來分類。token 的名字是從最外層到它的路徑，例如 color.brown.700。同一個物件同時有 $value 和子 token 是錯的，因為那樣分不出它到底是值還是分類。$ 開頭的鍵都是規範保留的：$value、$type、$description（說明）、$extensions（工具自己的額外資料）、$deprecated（後面講版本時會用到）。它們不是子 token，走訪時要略過。

第二，型別從哪裡來。每個 token 都要有型別，工具才知道 { "value": 1, "unit": "rem" } 該輸出成 1rem。token 沒寫 $type 時，用最近一個有寫的上層群組的；上面的 color.brown.700 自己沒寫，從 color 群組繼承到 color。規範明確要求工具不能從值的樣子猜型別：沒有型別又不是別名的 token 是無效的。這是為了讓同一個檔案在每個工具裡的意思都一樣，不會有工具把 "#fff" 猜成顏色、另一個猜成字串。

第三，別名（alias）怎麼寫。$value 寫成 "{color.brown.700}"，意思是「值跟那個 token 一樣」。上一節的三層就是靠別名串起來的：color.action.primary 是 {color.brown.700} 的別名。別名的型別就是它指向的 token 的型別。別名只能指向完整的 token，不能指向群組；不能形成迴圈（a 指 b、b 又指 a），工具必須偵測並回報。

第四，值的格式依型別而定。dimension 是 { value, unit }，unit 只能是 px 或 rem（值是 0 也要寫單位）；duration 也是 { value, unit }，unit 是 ms 或 s；color 是 { colorSpace, components, alpha?, hex? }，上面的棕色用 srgb 色彩空間，三個 components 是 0～1 的 R、G、B，hex 是選用的備援值。各型別的完整格式見課末「補充與查表」。

把這個檔案轉成 CSS 的第一步，是把巢狀的群組攤平成一個個變數名稱：color.brown.700 變成 --color-brown-700。這裡有一個 JavaScript 的細節會影響輸出順序：物件的鍵像整數的（"50"、"700"）一律依數字大小排在最前面，其他鍵才依加入的順序。色階剛好是數字，所以 Object.keys 的結果跟檔案裡的順序可能不同。執行後看第一行印出的鍵順序，再看攤平的結果：

轉成 CSS：別名要變成 var()，不是展開

攤平之後，每個 token 要輸出成一行 CSS 變數。原始 token 直接輸出值（#6e401e）沒有疑問，問題在別名：color.action.primary 的值是 {color.brown.700}，該輸出什麼？有兩種做法，畫面看起來一模一樣：

/* 對：保留層次 */
--color-brown-700: #6e401e;
--color-action-primary: var(--color-brown-700);
--button-primary-bg: var(--color-action-primary);

/* 錯：展開成最後的值 */
--button-primary-bg: #6e401e;

差別出在執行時。第 16 課切換深色主題的做法，是在 [data-theme="dark"] 底下只覆寫語意層，例如 --color-action-primary。保留 var() 的版本，--button-primary-bg 是「去讀 --color-action-primary 現在的值」，主題一切換，按鈕跟著變。展開的版本，--button-primary-bg 早就被寫死成 #6e401e，主題怎麼切它都不動。這正是第 16 課的主題切換能成立的前提，轉換工具把別名展開，就等於把三層又壓回一層。

轉換時第二件要做的事，是把所有錯誤在建置時就擋下：別名指向不存在的 token、形成迴圈、dimension 用了 em、沒有型別。為什麼不能輸出了再說？假設 color.action.primary 寫錯成 {color.brown.750}，轉換器照樣輸出 var(--color-brown-750)。瀏覽器讀到時不知道這個變數不存在，只能先收下，等到算樣式時才發現沒有值，這就是第 16 課講過的計算值時期無效（invalid at computed-value time）：按鈕的底色消失，Console 卻沒有任何錯誤。三個產品同時中招，而且要等有人看到畫面才會發現。轉換器在建置時丟錯，CI 就會擋下這次發版。

實務上很少自己從頭寫轉換器：Style Dictionary 等工具讀 tokens 檔、輸出 CSS、Swift、Kotlin 等格式。但自己寫一次（練習 1），你才知道這些工具在做什麼、設定檔裡的選項（要不要保留參照、名字怎麼接）在決定什麼，出錯時看得懂。

💡 實務上：tokens 只能有一個「正本」
常見的流程是 tokens 檔放在 git repo，設計師在 Figma 調整後匯出成 tokens 檔、開 PR，CI 跑轉換工具產生 CSS 等各平台檔案並發版；工程師不手改產生出來的 CSS。最常見的坑是 Figma 與程式各有一份、各自修改，幾個月後誰也說不清哪個才對。導入前先跟設計師講好：正本在哪裡、誰能改、改了怎麼通知前端與 App 團隊。如果團隊只有網頁、沒有 App，直接用 CSS 變數當正本也可以，不必為了格式而導入整套工具鏈。

到這裡，「加入購物車」的顏色在三個產品裡已經一致了。但開場的問題有一半跟顏色無關：平板上 hover 對比不足、停用的按鈕滑過去還會變色、載入中焦點消失。這些都是狀態沒做對。

按鈕的每個狀態都做對了嗎？

先列狀態矩陣

元件出問題，多半出在「某個狀態沒人想到」：停用的按鈕 hover 還會變色、載入中的按鈕焦點消失、切換按鈕按下去只變了一點點顏色。這些不是寫錯程式，是寫的時候根本沒想到那一格。避免的方法是動手之前先列出狀態矩陣（state matrix）：所有變體 × 所有狀態，每一格寫清楚外觀與行為。變體是元件的不同用法（primary、secondary），狀態是使用者或程式造成的暫時情況（hover、停用、送出中）。咖啡店按鈕的矩陣：

狀態怎麼觸發外觀行為
預設—變體的底色、文字、邊框可點、可聚焦
hover滑鼠移上去底色換成 hover token同預設
active按住底色換成 active token同預設
focus-visible鍵盤移到它3px 焦點框，跟按鈕留 2px 距離同預設
disableddisabled 屬性停用色；hover、active 都不變不能點、不能聚焦、不會送出
loadingaria-busy="true"轉圈圖示，文字保留；hover、active 不變仍可聚焦，點了不會重複送出
pressed（切換按鈕）aria-pressed="true"選取色，加上顏色以外的差異（較粗的框）點一下切換

每一格的「外觀」欄都對應到上一節的元件 token，例如 hover 用 --button-primary-bg-hover；「行為」欄則是寫程式時要做到的事。有兩格要特別說明。pressed 為什麼要「顏色以外的差異」：第 5 課的 WCAG 1.4.1（Use of Color）要求不能只靠顏色傳達資訊，色覺障礙的使用者分不出淺棕和更淺的棕，所以按下的切換按鈕要再加一種看得出的差異，例如較粗的框。loading 為什麼觸發方式是 aria-busy 而不是 disabled，下面專門講。

矩陣列好了，下一個問題是：程式裡要用什麼來表示「現在是哪個狀態」，CSS 才能照著畫？

狀態要寫在 DOM 上，不要另外加 .is-* class

常見寫法是 JavaScript 切換 class：

<button class="btn is-loading" disabled>送出中…</button>
<button class="btn is-pressed">加入最愛</button>

問題是同一個狀態存在兩個地方：class 給 CSS 看、屬性給瀏覽器與輔助科技看，兩者遲早不同步。.is-pressed 加上去了，畫面上按鈕看起來是按下的，螢幕閱讀器卻不知道它是按下的切換按鈕，因為沒有 aria-pressed。開場平板那種「看起來對、用鍵盤或螢幕閱讀器就壞」的問題，多半就是這樣來的。

反過來，直接用 DOM 本身的狀態當選擇器，外觀與語意就不可能分家：按鈕有 aria-pressed="true" 才會套到按下的樣式，忘了加屬性，畫面上也看得出來沒按下，問題在開發時就會被發現。矩陣裡每個狀態對應的選擇器：

狀態選擇器說明
hover／active:hover、:active瀏覽器自己判斷
鍵盤焦點:focus-visible第 5 課：滑鼠點擊不出現焦點框，鍵盤操作才出現
停用:disabled對應 disabled 屬性
忙碌[aria-busy="true"]「這個元素正在更新」
按下／選取[aria-pressed="true"]、[aria-selected="true"]、[aria-current="page"]切換按鈕、分頁、目前頁面
錯誤[aria-invalid="true"]、:user-invalid第 4 課的表單錯誤
展開[aria-expanded="true"]、[open]選單、<details>

變體（primary／secondary）不是狀態，是元件的設定，用 class 或 data-variant 都可以；本課用 data-variant，因為它跟 Vue 的 prop 一對一。

表裡最容易選錯的是「送出中」這一列：大多數人的直覺是加 disabled，為什麼矩陣偏偏寫 aria-busy？

送出中為什麼不加 disabled？

直覺的寫法是送出時加 disabled 防止重複點擊。看一個鍵盤使用者實際會遇到什麼：他用 Tab 移到「加入購物車」，按 Enter。程式開始送出，把按鈕設成 disabled。但 disabled 的按鈕不能聚焦，焦點所在的按鈕突然被停用，焦點就掉回 <body>。下一次按 Tab，焦點從頁面開頭重來，他得再按十幾次 Tab 才回得到原本的位置。螢幕閱讀器使用者更糟：他失去「現在在哪裡」的位置，也聽不到任何東西告訴他有沒有送出。這就是開場「有一種載入樣式會讓焦點消失」的來源。

比較好的做法是把 disabled 原本做的兩件事拆開，各自用對的工具：

  • 標記狀態：按鈕保持可聚焦，加上 aria-busy="true" 標記忙碌，樣式用 [aria-busy="true"] 顯示轉圈圖示。
  • 防止重複送出是程式邏輯：點擊處理函式開頭 if (loading) return，不需要靠 disabled。
  • 讓狀態被聽見：螢幕閱讀器對按鈕上的 aria-busy 不一定會唸出來，所以同時把文字改成「送出中…」，完成或失敗時用 role="status" 的區域宣告結果（第 5 課的 live region）。

防重複送出這件事前後端都要做。前端擋的是使用者連點；但網路重送、使用者重新整理這類情況前端擋不到，所以後端也要做到冪等（idempotent）：同一筆請求送兩次，結果跟送一次一樣，只建立一張訂單。前端這層仍然不能省，它讓大多數重複請求根本不會發出去。

停用與忙碌時，hover 怎麼不再變色？

矩陣寫明停用與送出中「hover、active 都不變」。這一格最常出錯，因為瀏覽器對停用的按鈕照樣套用 :hover：寫 .btn:hover 的話，停用的按鈕滑過去也會變色，看起來像能按。做法是在 hover 規則本身用 :not() 排除這兩種狀態：

.btn:not(:disabled, [aria-busy="true"]):hover {
  background: var(--button-primary-bg-hover);
}

為什麼不寫普通的 .btn:hover，再靠後面的 .btn:disabled 把底色蓋回去？因為這樣要靠權重（第 6 課）和順序互相覆蓋，很容易被別的規則打破。算一次就知道：.btn:disabled 是 (0,2,0)。某個變體的 hover 規則，例如 .btn[data-variant="secondary"]:hover，是一個 class、一個屬性選擇器、一個偽類，(0,3,0)，比 .btn:disabled 高，停用的次要按鈕滑過去又會變色。變體越多，這種漏洞越多。

改成把排除條件寫在 hover 規則裡，就不需要誰蓋過誰：:not() 的權重是它參數裡最高的那個，所以 .btn:not(:disabled, [aria-busy="true"]):hover 是 (0,3,0)，比 .btn:disabled 的 (0,2,0) 高。這裡沒關係，因為兩條規則不會同時成立：按鈕停用時 hover 規則根本不符合。排除條件寫在 hover 規則本身，比靠順序互相覆蓋可靠。

💡 實務上：拿到設計稿先補齊狀態，再開始寫
設計稿常常只畫了預設與 hover，loading、停用、錯誤、文字很長、鍵盤焦點都沒畫。開工前拿狀態矩陣跟設計師逐格確認，比上線後客服回報「按了沒反應」再補便宜得多。咖啡店的結帳按鈕就是典型：網路慢時使用者連點，如果 loading 狀態沒做防重複送出，後端就可能收到兩張訂單。Code review 時資深工程師會特別看：狀態是不是用 DOM 屬性表達、停用與忙碌時 hover 有沒有排除、焦點會不會消失。

按鈕本身現在每一格都做對了。但元件做對，不代表別人會用對：如果點餐頁的同事拿它來做「回菜單」的換頁，或在同一個區塊放三個 primary，按鈕再正確也沒用。

別的團隊怎麼知道該怎麼用？

多數元件的文件只有範例程式。範例回答的是「怎麼寫」，沒回答「什麼時候該用、什麼時候不該用」。大家會照抄範例，結果是一頁出現三個 primary 按鈕、連結被做成按鈕、危險操作用一般按鈕。這些都不是元件的 bug，是缺少用法的規範。解法是每個元件的文件頁都用同一個模板，強迫寫元件的人把這些問題回答完：

段落按鈕元件的內容
用途觸發一個動作：送出、加入購物車、開啟對話框
不要用在換頁（用連結 <a href>，第 2 課）；同一區塊超過一個 primary（主要動作只能有一個）
變體primary：一個畫面最重要的動作；secondary：其他動作
狀態上面的狀態矩陣，每一格附截圖
無障礙Enter 與空白鍵都能觸發；名稱就是可見文字，只有圖示時要有 aria-label；文字對比 ≥ 4.5:1、焦點框 ≥ 3:1；點擊範圍至少 24×24 CSS px（WCAG 2.5.8）
內容指引用動詞開頭、說出結果：「加入購物車」不寫「確定」；2～6 個字
程式範例Vue 用法、各 prop 的說明與預設值

上一節的狀態矩陣直接成為文件的「狀態」段，不用另外寫。「不要用在」與「無障礙」這兩段一定要有：前者擋住誤用，後者讓用的人知道哪些責任已經由元件扛了（焦點框、對比），哪些還是他自己要做（只有圖示時補 aria-label）。

文件常放在 Storybook 這類工具：每個狀態寫成一個「story」，同時是文件、手動測試的頁面，也是第 27 課視覺回歸測試的截圖來源。工具是其次，模板的內容才是重點。

文件寫好，三個產品開始用這顆按鈕。從這一刻起，按鈕的每個 token 名稱、每個 prop、甚至 DOM 結構，都有別人在依賴。下一次改它，會不會弄壞別的團隊？

改一個顏色、一個名字，會不會弄壞別的團隊？

設計系統通常發成 npm 套件，三個產品各自安裝。套件的版本號用語意化版本（SemVer 2.0.0）：MAJOR.MINOR.PATCH 三個數字，各自代表一種承諾。PATCH 是修 bug、不改用法；MINOR 是新增功能、舊的寫法照常運作；MAJOR 是有不相容的改動，使用者升級後可能要改程式。版本號就是你對使用者說「這次升級要不要擔心」。

這個承諾為什麼重要：Node 課第 3 課講過，^1.4.0 會自動升到 1.x 的最新版。三個產品的 package.json 多半就是這樣寫的，所以你發的 MINOR、PATCH 會在使用者沒注意的情況下裝進去。不相容的改動只能放在 MAJOR，否則等於直接改壞了別人的產品。

難的是判斷「什麼算不相容」。一般函式庫的公開 API 是函式與參數；設計系統的公開 API 多很多，token 名稱、元件的 DOM 結構、預設行為都算，因為使用者的程式會依賴它們：

改動等級為什麼
移除或改名 token、prop、slot、元件公開的 CSS 變數MAJOR使用者的程式碼直接失效：var(--color-primary) 變成沒定義
改元件的 DOM 結構（例如外層多包一個 div）MAJOR使用者的 CSS 選擇器、測試的定位可能失效
改預設行為（按鈕預設 type 從 button 改成 submit）MAJOR使用者沒改任何東西，表單卻開始被送出
新增 token、prop、元件MINOR舊的寫法照常運作
標記棄用（$deprecated）MINORSemVer 規範明文要求：標記棄用要升 MINOR
改 token 的值（顏色調深一點）、修 bugPATCHAPI 不變；但要檢查對比，視覺改動要在變更紀錄寫清楚

表中最容易被低估的是最後一列「只改值」。它是 PATCH，所以會自動裝進所有專案；如果新的次要文字色讓對比從 4.6 掉到 4.2，三個產品同時違反無障礙要求，而且沒有人改過自己的程式。所以改值時要自動檢查重要的前景／背景組合（練習 3）。

要改名時怎麼辦：棄用流程

表格說改名是 MAJOR，但名字取得不好總有要改的時候。咖啡店早期有一個 color.primary，後來發現它不說明用途，想改成 color.action.primary。直接改名、不保留舊名字，等於在 MINOR 或 PATCH 裡塞了 breaking change，所有用 ^2.3.0 的專案下次安裝就壞掉，而且壞的方式是「顏色消失」，不會報錯：就是上一節講的計算值時期無效。

做法是棄用（deprecation）：先標記即將移除、給替代方案與期限，之後才移除。前面 DTCG 範例裡的 "$deprecated": "改用 color.action.primary，3.0 移除" 就是這一步。$deprecated 的值是 true 或一段說明文字，表示這個 token 即將移除，它還在、還能用，只是工具應該提醒。完整流程：

  1. 2.4.0（MINOR）：新增 color.action.primary；舊的 color.primary 保留，值改成別名 {color.action.primary}，加上 $deprecated: "改用 color.action.primary，3.0 移除"。兩個名字都能用，畫面一樣。
  2. 同時提供提醒：只靠 $deprecated 不夠，因為它只寫在 tokens 檔裡，三個產品的開發者平常不會去讀。所以要把提醒送到他們寫程式的地方，常見三種：
    • 變更紀錄：寫明「var(--color-primary) 改成 var(--color-action-primary)，3.0 移除」，升級時一看就知道要換什麼。
    • lint 規則：Stylelint 是檢查 CSS 寫法的工具（第 6、16 課用它擋 !important 與寫死的色碼）。設計系統可以提供一條規則：只要 CSS 裡出現 var(--color-primary) 就發出警告，開發者在編輯器或 CI 就會看到，不用等到 3.0 畫面壞掉。
    • codemod：一支自動改程式碼的腳本，會掃過整個專案，把所有 var(--color-primary) 一次換成 var(--color-action-primary)。使用的團隊跑一次、檢查 diff 就完成替換，不用自己全文搜尋一個個改。能做的話就附上。
  3. 3.0.0（MAJOR）：移除 color.primary。使用者至少有一整個 MAJOR 週期可以換。

第 1 步裡「舊名字改成別名」是關鍵：因為轉換器會把別名輸出成 var(--color-action-primary)，舊名字永遠跟著新名字走，不會出現兩個值不一致的過渡期。變更紀錄、貢獻流程、採用率統計這些治理工作的細節見課末。

💡 實務上：發 MAJOR 前先算好「誰要跟著改」
咖啡店的官網、點餐、平板三個專案升級節奏不同，設計系統發 3.0 後，可能半年內三個版本並存。發版前先用採用率統計與全文搜尋，列出哪些專案還在用要移除的 token 或 prop，跟各團隊排好升級時間，必要時由設計系統團隊直接幫忙開 PR。如果三個專案都在同一個 monorepo（多個專案放在同一個 git repo），可以一次改完所有使用處，版本管理的負擔小很多；分散在不同 repo 時，棄用期與變更紀錄就是你最主要的溝通管道。不要為了小小的命名潔癖發 MAJOR：每次 MAJOR 都是在消耗其他團隊的時間。

tokens 和 CSS 這一側的規則都齊了。最後一塊是三個產品實際 import 的東西：Vue 元件本身。它的 props 同樣是公開 API，而且要跟狀態矩陣對得起來。

Vue 元件怎麼把 props 接到狀態矩陣？

原則只有一條：每個 prop 對到一個 DOM 屬性，CSS 只看 DOM。元件不自己算 class，也不自己決定顏色，它只負責把「使用者傳進來的狀態」寫到 DOM 上；外觀全部交給前面寫好的 [aria-busy="true"]、:disabled 這類選擇器。這樣狀態矩陣的每一列，在元件裡都找得到唯一一個對應的 prop（Vue 課第 9 課的 props、第 14 課的型別）：

<script setup lang="ts">
const props = defineProps<{
  variant?: 'primary' | 'secondary'
  loading?: boolean
  disabled?: boolean
  pressed?: boolean   // 只有切換按鈕會傳
}>()
const emit = defineEmits<{ click: [event: MouseEvent] }>()

function onClick(event: MouseEvent) {
  if (props.loading) return          // 防重複送出靠邏輯，不靠 disabled
  emit('click', event)
}
</script>

<template>
  <button
    type="button"
    class="btn"
    :data-variant="variant ?? 'primary'"
    :disabled="disabled"
    :aria-busy="loading ? 'true' : undefined"
    @click="onClick"
  ><slot /></button>
</template>

對照矩陣逐一看：variant 寫到 data-variant；disabled 寫到原生的 disabled；loading 寫到 aria-busy，而且 onClick 開頭的 if (props.loading) return 就是上一節「防重複送出靠邏輯」那一行。hover、active、focus-visible 由瀏覽器判斷，不需要 prop。

矩陣裡還有一列 pressed，這裡卻刻意沒有綁 aria-pressed，原因是 Vue 的 Boolean 轉型：型別是 boolean 的 prop 沒傳時值是 false，不是 undefined。如果寫 :aria-pressed="pressed"，每個一般按鈕都會帶 aria-pressed="false"，螢幕閱讀器會把它們全部唸成「切換按鈕，未按下」。aria-pressed 的意思不是「沒按下」，而是「我是切換按鈕」；只有真的是切換按鈕時才能出現。

做法是讓它沒傳時維持 undefined：Vue 文件說明 Boolean prop 設 default: undefined 就不會被轉成 false，綁定時再把 undefined 留成「不輸出這個屬性」。用型別宣告 props 時，要改兩處。第一處是把 defineProps 包進 withDefaults，預設值只寫 pressed: undefined（下面為了聚焦只列出 pressed，實際上其他 props 照原樣留在同一個型別裡）；第二處是在 <button> 上加 :aria-pressed 的條件綁定：

const props = withDefaults(defineProps<{ pressed?: boolean }>(), { pressed: undefined })
:aria-pressed="pressed === undefined ? undefined : String(pressed)"

第一行讓沒傳的 pressed 維持 undefined；第二行在 undefined 時不輸出屬性，傳了 true／false 才輸出 "true"／"false"。另一個做法是乾脆做一個獨立的 ToggleButton 元件，讓一般按鈕根本沒有這個 prop。

type="button" 也是刻意的預設：<button> 在表單裡預設是 submit，元件庫要明確選一個並寫進文件，之後改它就是上一節表格裡的 MAJOR。

到這裡，「加入購物車」從 tokens、狀態、文件、版本到 Vue 元件都接起來了。剩下的問題是怎麼確保它一直是對的：元件有了狀態矩陣，測試也跟著有了清單，每一格是一個 story、一張截圖。第 27 課會用 Playwright 對每個狀態拍照比對（視覺回歸），改了 token 值之後，哪些元件的哪些狀態變了，一眼就看得到。

補充與查表

DTCG 規範細節

  • 規範的地位：DTCG 在 2025-10-28 發布 Design Tokens Format Module 2025.10，是 Final Community Group Report（社群小組的報告），不是 W3C 正式標準。檔名建議用 .tokens 或 .tokens.json，媒體型別是 application/design-tokens+json。
  • 名字的限制：token 與群組的名字不能用 $ 開頭，也不能含 {、}、.；名字區分大小寫。
  • $ref：規範另外有 JSON Pointer 的 $ref 寫法，可以指到值的某一部分，本課不用。
  • color 的細節：colorSpace 可以是 srgb、oklch、display-p3 等十幾種；srgb 的三個 components 是 0～1 的 R、G、B，oklch 是 L、C、H；alpha 0～1，沒寫就是 1；hex 是選用的備援值，規範規定只能寫 6 位數，透明度一律放在 alpha。
  • $deprecated 的繼承：群組上寫的話，底下的 token 都繼承。

治理的其他工作

  • 變更紀錄（CHANGELOG）：每個版本分「破壞性變更」「新增」「修正」「棄用」，破壞性變更附遷移步驟。用 Changesets 這類工具讓每個 PR 自己寫一段，發版時自動彙整。
  • 貢獻流程：誰都可以提案，但要有明確的決策者（通常是設計與前端各一位維護者）。新元件先問「是不是至少兩個產品需要」，只有一個地方用的元件留在那個產品裡。
  • 量化採用率：統計各專案用的版本與舊 token 的使用次數，才知道 MAJOR 能不能發、棄用期要不要延長。

Vue：withDefaults 的 pressed: undefined 編譯成什麼

主線裡的 withDefaults(defineProps<{ pressed?: boolean }>(), { pressed: undefined })，Vue 3.5 會編譯成 { type: Boolean, default: undefined }，所以 Boolean 轉型不會把沒傳的值變成 false。

練習 1：寫 tokensToCss(tokens)，把 DTCG 2025.10 格式的 tokens 轉成 CSS custom properties，一個 token 一行 --名稱: 值;，用 \n 接起來，順序跟 Object.entries 走訪的順序一樣。要求：
① 名稱是路徑用 - 接起來（color.brown.700 → --color-brown-700）；$ 開頭的鍵都不是 token，$description、$extensions、$deprecated 不輸出（棄用的 token 本身照常輸出）。
② $type 用自己的，沒有就用最近一個有寫的上層群組的；兩者都沒有又不是別名，丟錯。
③ 別名 {a.b.c} 輸出 var(--a-b-c)，指向它直接參照的那個 token，不要展開；別名鏈上任何一環指向不存在的 token（或群組）、或形成迴圈，丟錯，訊息要寫出相關的路徑。
④ dimension、duration 輸出 值單位（1.5rem、120ms），dimension 只接受 px／rem、duration 只接受 ms／s，其他丟錯；number 直接輸出數字。
⑤ color：srgb 有 hex 就輸出小寫 hex，alpha < 1 時在後面加兩位數的透明度變成 8 位數（Math.round(alpha * 255) 轉 16 進位，0.5 → 80）；srgb 沒有 hex 輸出 color(srgb r g b)；oklch 一律輸出 oklch(l c h)（hex 只是備援）；後兩種 alpha < 1 時在括號內加 / alpha。其他色彩空間丟錯。
測試會凍結輸入物件，不要修改它。

練習 2：咖啡店的按鈕目前用 .is-loading、.is-pressed 表達狀態，送出中的按鈕還被 disabled，樣式也直接用原始色。依下面的狀態矩陣重寫：
HTML：「送出中…」改用 aria-busy="true"（拿掉 disabled），所有按鈕的 class 只留 btn，其他不要動。
CSS：tokens 那一段不要改；按鈕規則裡的 var() 只能用 --button-*，不能寫死顏色（currentColor、transparent 可以）；只用 :hover、:active、:focus-visible、:disabled、[aria-busy="true"]、[aria-pressed="true"] 這類選擇器，不用狀態 class，不用 opacity、!important。
• 預設：底色、文字、邊框用 --button-{primary|secondary}-bg／-fg／-border，cursor: pointer。
• hover／active：底色換成 -bg-hover／-bg-active（按住時以 active 為準）。
• focus-visible：outline: 3px solid var(--button-focus-ring)、outline-offset: 2px。
• disabled：--button-disabled-bg／-fg／-border、cursor: not-allowed；hover、active 都不變。
• 送出中（aria-busy="true"）：外觀同預設、cursor: progress、hover 與 active 不變；用 ::before 畫轉圈圖示，大小 --button-spinner-size（content 用空字串，名稱才不會變）。
• 按下（aria-pressed="true"）：--button-pressed-bg／-fg／-border，再加一種顏色以外的差異。
測試會在主要、次要兩個按鈕上逐一加上 disabled、aria-busy、aria-pressed 與 hover／active，量出每一格的計算樣式。

練習 3：寫 classifyChange(before, after, contrastPairs)，比較設計系統兩個版本的清單（tokens 與每個元件公開的 props、slots、CSS 變數），回傳建議的升級等級與理由。理由是字串，格式固定為「動作 類別 名稱」：
• tokens：移除 token 名稱、新增 token 名稱；兩版都有的 token，新版多了 deprecated 是 棄用 token 名稱，用 resolve() 解析到最後的色碼不同是 修改 token 名稱（改成別名但顏色一樣不算修改）。
• 元件：移除 元件 Card、新增 元件 Badge；兩版都有的元件，比較 props、slots、cssVars：新增 prop Button.size、移除 slot Card.footer、移除 CSS 變數 Button.--button-radius。
• reasons 用 sort()（不帶比較函式）排序。level：有任何「移除」是 'major'；否則有「新增」或「棄用」是 'minor'；否則有「修改」是 'patch'；什麼都沒有是 'none'。
• a11yRisks：contrastPairs 裡每一組 [前景, 背景]，兩個版本都有這兩個 token、舊版對比 ≥ 4.5、新版 < 4.5 的，依原本順序輸出 '前景 / 背景'。它不影響 level，是給審查者的警告。
contrast() 與 resolve() 已經寫好。測試會凍結輸入。

練習 4：為什麼語意 token（color.action.primary）的值要用別名指向原始色，轉成 CSS 時也輸出 var(--color-brown-700)，而不是直接寫色碼？

✓ b：別名保留了「這個用途用哪個顏色」的決策，輸出成 var() 後，深色主題只要覆寫語意層，元件跟著變；展開成色碼的話，主題切換對它無效。a 錯：檔案大小不是重點。c 錯：規範允許任何 token 直接寫值，分層是設計系統自己的決策。d 錯：var() 要多一步代入，不會比較快，差異也小到不用考慮。

練習 5：按鈕在送出中（loading）時，為什麼不建議加 disabled？

✓ b：狀態要讓所有使用者都感知得到；剛按下 Enter 的按鈕突然停用，焦點掉回 body。防止重複送出是邏輯問題（if (loading) return），不需要靠 disabled。a 錯：:disabled 可以照樣設計樣式。c 錯：disabled 的按鈕不會送出表單，問題不在這裡。d 錯：焦點與可及性的差別很大。

練習 6：設計系統把 token --color-primary 改名為 --color-action-primary，而且不保留舊名稱，應該發哪一種版本？

✓ c：使用者寫的 var(--color-primary) 會變成沒定義，而且不會報錯，是不相容的改動。比較好的做法是先發 minor：新增新名字、舊名字改成別名並標記棄用，下一個 major 再移除。a 錯：值沒變，但名字是公開 API。b 錯：同時移除了舊名字，新增的部分不能抵銷。d 錯：用 ^ 範圍安裝的專案會在不知情的情況下拿到這個改動。

常見錯誤

  • token 只有原始色：元件直接用 --brown-700，換主題或改版要改每個元件。建立語意層（必要時加元件層），元件只用語意或元件 token。
  • 轉換 tokens 時把別名展開：輸出的 CSS 看起來一樣，但深色主題只覆寫語意變數時，元件不會跟著變。別名輸出 var()。
  • 用 class 表達狀態：.is-pressed 加了，aria-pressed 沒加，螢幕閱讀器不知道狀態。用 :disabled、[aria-pressed="true"] 這類 DOM 本身的狀態當選擇器。
  • 停用、送出中的按鈕 hover 仍變色：:hover 對停用的按鈕照樣成立。hover／active 規則本身用 :not(:disabled, [aria-busy="true"]) 排除。
  • 送出中用 disabled：焦點消失、使用者失去位置。用 aria-busy、改文字、在程式裡擋重複送出。
  • 文件只有範例程式：沒寫何時不用、無障礙需求，元件被誤用（連結做成按鈕、一頁三個 primary）。用固定的文件模板。
  • 悄悄改名或改預設行為：在 minor／patch 裡移除 token、改 DOM 結構、改按鈕預設 type，都是 breaking change。先棄用、給替代方案與期限，major 才移除。
  • 改 token 值不檢查對比：patch 會自動裝進所有專案。重要的前景／背景組合放進 CI 自動檢查。

小結

  • 三個產品的按鈕越長越不一樣，是因為每個團隊各自做決定、把結果抄進程式。設計系統＝tokens、元件、模式、文件、治理，讓決定只存在一個地方；它帶來一致、速度與內建的無障礙，代價是要當成產品長期維護，只有一個產品時不急著做。
  • tokens 是跟平台無關的設計決策，分原始、語意、元件三層，每層用別名指向上一層；元件的 CSS 不直接用原始色。DTCG 2025.10 用 $value、$type（從群組繼承，不能猜）、{a.b} 別名描述；轉成 CSS 時別名輸出 var()，主題切換才有效，錯誤在建置時擋下。
  • 元件先列狀態矩陣，再用 :hover、:focus-visible、:disabled、[aria-busy]、[aria-pressed] 實作，外觀與 DOM 狀態不會分家。送出中不用 disabled；停用與忙碌時沒有 hover；按下的狀態不只靠顏色。
  • 元件文件固定寫：用途、不要用在、變體、狀態、無障礙、內容指引、程式範例。
  • SemVer：移除或改名 token／prop、改 DOM 結構、改預設行為是 major；新增與標記棄用是 minor；改值是 patch，但要檢查對比。改名走「新增＋棄用別名 → 下一個 major 移除」。
  • Vue 元件的每個 prop 對到一個 DOM 屬性，CSS 只看 DOM；Boolean prop 沒傳時是 false，aria-pressed 只能出現在真的切換按鈕上。
