階段 1：HTML 與可操作的網頁 · 第 3 課

內容結構：表格、圖片、影音與替代文字

咖啡店的菜單頁下週上線。上線前，負責無障礙的同事打開螢幕閱讀器，閉上眼睛把菜單頁和首頁從頭聽了一遍，回報了一張清單：價目表只聽到一串沒有標題的數字「110、130、120、140」；拿鐵的照片被唸成「latte 下底線 final 點 jpg」；右上角的購物車只唸出「按鈕」，不知道按下去會怎樣；一打開首頁，背景影片的聲音就蓋過了報讀；在手機上看價目表，往右滑看大杯價格時整頁跟著滑走。

這些東西有個共同點：它們都不是純文字。表格的意思藏在列與欄的位置裡，圖片和影片的意思藏在畫面和聲音裡，看得到、聽得到的人一眼就懂，其他人只拿得到 HTML 告訴他們的部分。這一課照著這張回報清單，一條一條修，修完你會知道每一種非文字內容該補上什麼，以及為什麼。

這課的路線：
  1. 價目表只唸出數字：先判斷這份資料該不該用表格，再用 caption、<th> 和 scope 讓每一格唸得出「拿鐵，大杯，130 元」。
  2. 手機上整頁滑走：寬表格怎麼只在自己的範圍裡捲動，而且鍵盤和螢幕閱讀器也捲得動。
  3. 照片唸出檔名：alt 依圖片的用途寫，店面照已經有說明文字時，alt 和 figcaption 怎麼分工。
  4. 首頁影片一開就出聲：教學影片要給字幕和控制項，背景影片要靜音、能暫停、標成裝飾。
  5. 購物車只唸「按鈕」：圖示是 inline SVG、沒有 alt 屬性可寫時，怎麼給它名稱或讓它安靜。
這課會用到：
  • 第 2 課的角色（role）與可及名稱（accessible name）：螢幕閱讀器唸出的是元素的「角色＋名稱」，例如「按鈕，購物車」。這一課的 alt、caption、aria-label 都是在決定那個名稱。瀏覽器會把頁面整理成一棵無障礙樹，交給螢幕閱讀器等輔助科技；ARIA 屬性可以修改樹上元素的角色和名稱。

價目表只唸出一串數字：這份資料該用表格嗎？

回報清單的第一條是價目表。目前的價目表是用一堆 <div> 加 CSS Grid 排出三欄，畫面上看起來就是一張表；但 HTML 裡只有「一格接一格的文字」，沒有任何東西說明哪一格屬於哪一列、哪一欄。螢幕閱讀器只能照原始順序唸：「飲品、中杯、大杯、美式咖啡、80 元、95 元、拿鐵、110 元、130 元……」。聽到「130 元」時，使用者得自己記住這是第幾格、往回推算它是哪一種飲品的哪個尺寸。

要修之前，先回答一個更根本的問題：這份資料是不是表格資料？判斷方法是看一格的意思要靠什麼才說得清楚。價目表是「飲品 × 尺寸」：「130 元」這一格，要同時知道它所在的列是拿鐵、所在的欄是大杯，才有意義。只要資料有這種「列與欄兩個方向一起決定意思」的關係，就用 <table>。HTML 的表格元素會把這層關係寫進結構裡，螢幕閱讀器才有辦法在使用者停在某一格時，告訴他這一格的列標題和欄標題。

同一間咖啡店裡，長得像「排成好幾欄」的東西不只價目表，但不是每個都該用表格：

內容用什麼原因
價目表、營業時間對照、訂單明細<table>每一格要靠列標題和欄標題才看得懂
商品卡片排成三欄列表＋CSS Grid卡片之間沒有「同一欄是同一種資料」的關係，只是排版
一個名詞配一段說明（營業時間：8:00–20:00）<dl>只有「名稱 → 值」一個方向（第 2 課）

商品卡片排成三欄，看起來也有「欄」，但第一欄的卡片和第二欄的卡片是同一種東西，換到哪一欄都不會改變意思；欄只是畫面寬度決定的排法，在手機上會變成一欄。這種是排版，不是表格資料。

這個判斷兩個方向都會出錯。第一種是用表格排版：早期 CSS 不夠用，很多網站用 <table> 切出頁首、側欄、內容。這樣做會帶來三個問題：螢幕閱讀器可能把整頁當成資料表格，唸出「表格，3 欄 5 列」，讓使用者以為接下來是一份資料；在手機上表格不會自動換行，只能整頁橫向捲動；之後要改版面，得動 HTML 結構而不是只改 CSS。版面交給第 8 課的 Flexbox 與第 9 課的 Grid。第二種就是咖啡店現在犯的錯：真的是表格資料，卻用 div 加 grid 排成「看起來像表格」。看得到畫面的人覺得沒差，看不到畫面的人就拿不到列與欄的關係，聽到的正是回報清單上那串數字。

所以第一條的修法方向確定了：價目表要改成 <table>。但光把 div 換成 table 還不夠，螢幕閱讀器要知道哪一格是標題、標題管哪個方向，才唸得出「拿鐵，大杯」。這是下一節的事。

怎麼讓「130 元」唸得出是拿鐵、大杯？

上一節決定了用 <table>，這一節要讓表格的每一格都帶著自己的標題。先看改好的價目表，再一個元素一個元素說明它負責什麼：

<table>
  <caption>飲品價目表</caption>
  <thead>
    <tr><th scope="col">飲品</th><th scope="col">中杯</th><th scope="col">大杯</th></tr>
  </thead>
  <tbody>
    <tr><th scope="row">美式咖啡</th><td>80 元</td><td>95 元</td></tr>
    <tr><th scope="row">拿鐵</th><td>110 元</td><td>130 元</td></tr>
  </tbody>
</table>

<caption> 是表格的標題。它必須是 <table> 的第一個子元素，畫面上會顯示在表格上方，所有人都看得到。它同時是表格的可及名稱：螢幕閱讀器進入表格時，會先唸「飲品價目表，表格，3 欄 3 列」，使用者還沒聽到任何數字，就知道這是什麼表、有多大。沒有 caption 的表格沒有名稱，頁面上有兩張表時，使用者就分不出哪張是哪張。

表格裡的格子分成兩種。說明一欄或一列是什麼的格子叫表頭儲存格（header cell），用 <th>；放實際資料的格子是一般的資料格，用 <td>。「中杯」「大杯」是表頭，「拿鐵」也是表頭（它說明這一列是哪種飲品），「130 元」是資料。瀏覽器預設會把 th 加粗置中，但重點不在樣式：只是加粗的 td，在無障礙樹裡還是一般資料格。

scope 說明一個 <th> 管哪個方向。「中杯」管的是它下面整欄，寫 scope="col"；「拿鐵」管的是它右邊整列，寫 scope="row"。有了 scope，瀏覽器就能替每一個 td 找出它的欄標題和列標題。

<thead>／<tbody> 分出標題列和資料列。第 1 課看過：不寫 <tbody> 瀏覽器也會自動補上，但寫出來原始碼才跟 DOM 一致，用 CSS 或 JavaScript 選取時不會意外。

這幾個元素合起來的效果是：使用者在表格裡移到「130 元」那一格，螢幕閱讀器會唸類似「拿鐵，大杯，130 元」（各家螢幕閱讀器的措辭不同），因為它從 scope 知道這一格的列標題是「拿鐵」、欄標題是「大杯」。對照修改前：如果全部用 <td>、只把第一列加粗，使用者在同一格只會聽到「130 元」，要自己回頭數這是第幾欄。回報清單的第一條，到這裡就修好了。

咖啡店的價目表只有一層表頭，scope 就夠用。表頭有兩層以上時寫法不同，而且容易寫錯，細節見課末「補充與查表」。

價目表在桌機上已經正確了。但回報清單上還有一條也跟它有關：在手機上往右滑看大杯價格時，整頁跟著滑走。

手機上價目表把整頁撐寬，怎麼只讓表格自己捲？

上一節的表格在桌機上沒問題，問題出在窄螢幕。表格不會像段落一樣換行：每一欄至少要寬到放得下欄裡最長、不能斷開的那段內容，欄位一多，加上設計稿常會再給表格一個最小寬度，在 320px 寬的手機上表格就比畫面寬。比畫面寬的東西會把整頁撐開，於是整頁可以橫向捲動：使用者往右滑看大杯價格時，頁首、標題和其他內容也一起滑走，滑回來又找不到剛剛看的那一列。

無障礙指引對這件事有明確要求。第 1 課提過的 WCAG（網頁內容無障礙指引）裡，1.4.10 Reflow（重排）要求內容在 320 CSS px 寬時不需要雙向捲動，也就是不能同時上下捲又左右捲。表格這種本身就需要二維排列的資料是例外，允許橫向捲動，但捲動的範圍要限制在表格自己身上，不能拖著整頁一起走。

做法是在表格外面包一層只負責捲動的容器：

<div class="price-wrap" role="region" aria-labelledby="price-caption" tabindex="0">
  <table>
    <caption id="price-caption">飲品價目表</caption>
    …
  </table>
</div>
.price-wrap { overflow-x: auto; }

這段程式碼的每一個屬性都在解決一個具體的問題，依序來看。

第一個問題：讓捲動只發生在這一塊。overflow-x: auto 的意思是：內容比容器寬時，才在這個容器上出現橫向捲軸。容器本身的寬度跟著頁面，不會超出畫面，所以整頁不再被撐開；超出的欄位留在容器裡，使用者在這一塊上左右滑就看得到。不要用 overflow: hidden，它不會出現捲軸，而是直接把超出的欄位裁掉，使用者根本看不到大杯價格。

第二個問題：只用鍵盤的人捲不動。用鍵盤操作的人，輸入會送到目前被聚焦（focus）的那個元素：按 Tab 就是在可以聚焦的元素（連結、按鈕、表單欄位）之間移動，按方向鍵則是捲動目前聚焦的那一塊。價目表裡沒有任何連結或按鈕，在有些瀏覽器裡，Tab 會直接跳過整個容器，方向鍵也就沒有東西可以捲。也有瀏覽器會讓這種捲動容器自動可以聚焦，但它沒有名稱，而且不是每個瀏覽器都這樣，所以要自己加 tabindex="0"，不要依賴瀏覽器的預設行為（細節見課末「補充與查表」）。tabindex="0" 讓這個 div 本身變成可以聚焦的元素，排進 Tab 的順序裡；聚焦之後，方向鍵捲的就是這個容器。

第三個問題：聚焦到了，卻不知道停在哪裡。一個可以聚焦的 div，在螢幕閱讀器眼中沒有角色也沒有名稱，使用者 Tab 到它時可能什麼都聽不到。role="region" 把它標成「一個有名稱的區塊」，名稱用 aria-labelledby 指向 caption 的 id，直接借用「飲品價目表」這幾個字，不用再寫一次。這樣 Tab 到容器時，使用者會聽到類似「飲品價目表，區域」。

這三樣不是每張表格都要加。你正在看的這頁，表格外面也包了一層 overflow-x: auto 的 .table-wrap，當作防止撐破版面的保險；但這些表格在手機上大多不需要捲動，所以沒有加 tabindex 和名稱。只有確定會比畫面寬的表格（像練習 1 的價目表，設計稿要求至少 30rem 寬），才需要再加 tabindex 與名稱。原因是每個 region 都會變成螢幕閱讀器的地標（landmark，第 2 課），使用者用地標清單快速跳轉時會看到它；不需要捲動的表格也加，清單裡就多了一個沒用的項目。

💡 實務上：後台列表幾乎都是表格，元件庫不一定幫你做對
咖啡店後台的訂單列表、會員列表、營收報表都是表格，而且欄位只會越加越多：訂單編號、顧客、金額、狀態、建立時間、操作按鈕。團隊通常會用 UI 元件庫的資料表格元件，有些為了固定欄位或大量資料，輸出的其實是一堆 div；接手時打開開發者工具看實際的 DOM，確認表頭是 <th>（或用 div 時有對應的 ARIA 角色），表格也有名稱。手機上也不一定要硬塞整張表：給顧客看的「我的訂單」常改成一筆一張卡片、只放幾個重要欄位，給店員用的後台才保留完整表格加橫向捲動。決定之前先問 PM：這頁主要在什麼裝置上用、使用者需要橫向比較多筆資料，還是一次只看一筆。

價目表的兩條回報都處理完了。往下聽，下一條是菜單照片：螢幕閱讀器唸出的是檔名「latte 下底線 final 點 jpg」。

照片唸出檔名：alt 該寫什麼？

上一節修完表格，接下來是圖片。螢幕閱讀器會唸出檔名，原因是這張 <img> 沒有寫 alt 屬性：圖片沒有提供任何文字，有些螢幕閱讀器就退而求其次，唸出它唯一找得到的文字，也就是檔名或網址。

替代文字（alt text）就是用來補上這段文字的：當圖片無法顯示、或使用者看不到圖片時，代替圖片傳達相同資訊的文字，寫在 <img> 的 alt 屬性裡。它會出現在三個地方：圖片載入失敗時，瀏覽器在圖片的位置顯示它；螢幕閱讀器停在圖片上時唸出它；搜尋引擎用它理解圖片內容。對看不到畫面的人來說，alt 就是這張圖本身。

知道 alt 是什麼之後，最常卡住的是「該寫什麼」。直覺是描述圖片長什麼樣子，但這常常是錯的：同一張圖放在不同位置，要傳達的事可能完全不同。所以寫 alt 之前，先問這張圖在這裡做什麼用。下面的分類依據 W3C WAI 的 alt 決策樹（Images Tutorial）：

四種用途各自的道理是：

  • 功能：圖片放在連結或按鈕裡，而且是裡面唯一的內容時，圖片的 alt 就成了連結或按鈕的名稱。使用者要知道的是「按下去會怎樣」，所以寫功能，不寫外觀。回報清單上「購物車只唸出按鈕」，如果那個圖示是 <img>，修法就是寫 alt="購物車"。
  • 資訊：圖片本身傳達了文字沒說的事，例如菜單上的拿鐵照片讓人知道它長什麼樣子。寫出這張圖在這裡要傳達的資訊。
  • 裝飾：拿掉也不影響理解的圖，例如標題旁的花紋。寫 alt=""，讓螢幕閱讀器直接略過。
  • 複雜：一句話說不完的圖，例如位置圖、營收圖表。alt 寫一句簡短的說明，完整的內容寫在圖旁邊的頁面文字裡。

把這套判斷套到咖啡店頁面上的每一張圖：

咖啡店的圖用途alt
菜單上的拿鐵照片資訊alt="拿鐵，奶泡上有葉子形狀的拉花"
只有購物車圖示的按鈕功能alt="購物車"：它就是按鈕的名稱
同一個圖示，但按鈕旁邊已經有文字「購物車」裝飾alt=""：名稱已經有了，再唸一次是重複
連到首頁的 logo功能alt="豆留咖啡 首頁"：店名＋連結的目的地
標題旁的咖啡豆花紋裝飾alt=""
門市位置圖複雜alt="大安店位置圖"，地址與走法寫在圖旁邊的文字裡

第二列和第三列是同一個購物車圖示，alt 卻不同，這就是「先問用途」的意思：按鈕裡只有圖示時，圖示是名稱的唯一來源；按鈕裡已經有文字「購物車」時，圖示只是點綴，再寫 alt 會讓使用者聽到「購物車 購物車」。

決定了用途，實際寫的時候還有幾個常見的坑，每一個都會讓使用者聽到多餘或錯誤的東西：

  • 裝飾圖寫 alt=""，不是不寫。這一節開頭的檔名問題就是這樣來的：空字串是明確告訴輔助科技「這張圖可以略過」，完全不寫 alt 則等於沒交代，有些螢幕閱讀器會改唸檔名或網址，例如「bean-pattern 點 svg」。
  • 不寫「圖片」「照片」。螢幕閱讀器從 <img> 的角色就知道這是圖片，本來就會說「圖片」，alt 再寫一次就變成「圖片，圖片：拿鐵」。
  • 不堆關鍵字。alt="咖啡 咖啡店 台北咖啡 最好喝咖啡" 對使用者是噪音，Google 也把關鍵字堆砌視為垃圾內容。alt 是寫給人聽的一句描述。
  • 長度看資訊量。一句話說完這張圖在這裡要傳達的事。更長的說明（例如圖表的數字）放在頁面文字裡，不要塞進 alt：alt 沒辦法分段、也沒辦法讓使用者跳著聽。
  • title 屬性不能代替 alt。title 只在滑鼠停留時顯示，觸控與鍵盤使用者看不到，各家螢幕閱讀器處理也不一致。
  • 有內容的圖不要用 CSS 背景圖。background-image 沒有 alt 可以寫，只適合裝飾。
💡 實務上：商品圖的 alt 通常來自後台欄位，不是寫死在程式碼裡
菜單上的商品照片多半是店員在後台上傳的，前端只是把資料裡的圖片網址和說明帶進 <img>，所以 alt 要在後台的商品表單就有一個「圖片說明」欄位。沒設計這個欄位，上線後的 alt 不是空的就是檔名；欄位旁邊放一句範例（「拿鐵，奶泡上有葉子拉花」）比只寫「請輸入 alt」有用得多。logo、圖示、花紋這類固定的圖，才由前端在元件裡寫好 alt 或 alt=""。lint 是在存檔或 CI 時自動檢查程式碼的工具，Vue 專案可以用 eslint-plugin-vuejs-accessibility，它的 alt-text 規則抓得到漏寫 alt 的 <img>。不過 lint 和 code review 只抓得到「有沒有寫」，寫得好不好只有人判斷得出來。

菜單照片的 alt 都補上了。頁面下方還有一張大安店的店面照，照片底下已經有一行說明「大安店：每天 8:00–20:00 營業」。這張照片的 alt 要不要也寫營業時間？

店面照已經有說明文字，alt 還要寫什麼？

上一節的照片都是單獨一張圖；店面照不一樣，它旁邊跟著一段說明。HTML 為這種「一張圖配一段說明」的組合準備了專用的元素：<figure> 包住一個獨立的內容（圖片、表格、程式碼都可以），<figcaption> 寫它的說明。用 figure 包起來，瀏覽器和輔助科技就知道這段說明屬於這張圖，而不是頁面上隨便一段相鄰的文字。

figcaption 和 alt 都是「關於這張圖的文字」，最容易被寫成一樣，但它們的讀者不同：figcaption 是所有人都看得到的說明，常放照片本身看不出來的補充資訊；alt 是給看不到圖的人的替代內容，負責交代照片裡看得到的東西。兩者分工，不要寫成一樣：

<figure>
  <img src="storefront.jpg"
       alt="木頭門面的店，左邊是大片窗戶，門口兩側各有一張戶外座位">
  <figcaption>大安店：每天 8:00–20:00 營業</figcaption>
</figure>

alt 描述照片裡看得到的東西，figcaption 給營業資訊。如果 alt 也寫「大安店：每天 8:00–20:00 營業」，螢幕閱讀器使用者會聽到兩次同樣的話，卻始終不知道照片裡有什麼，例如到了現場要找的是木頭門面、大片窗戶的那間店。反過來，figcaption 也不能取代 alt：figure 裡的 img 還是要有自己的 alt，少了它，那張圖又回到上一節唸出檔名的狀態。

到這裡，菜單頁上的圖片都處理完了。回報清單上還有一條是在首頁：一打開背景影片就出聲，蓋過了報讀。影片沒有 alt 可以寫，要照顧的人也比圖片多。

首頁影片一打開就出聲：影片要補上哪些東西？

圖片要照顧的是看不到畫面的人，替代內容是 alt。影片同時有畫面和聲音，所以要照顧的人多了兩種：聽不到聲音的人，以及不想被突然的聲音或動態干擾的人。咖啡店的首頁有兩支影片，用途完全不同，處理方式也不同：一支是「手沖示範」，要教顧客怎麼沖咖啡，內容本身就是資訊；另一支是頁首的背景影片，只是營造氣氛。回報的是背景影片，但先看一般影片該有的配備（控制項、字幕），再看背景影片為什麼要反過來拿掉控制項、改成靜音，比較容易看出差別。所以先看示範影片。

示範影片：要讓所有人都能操作、看懂

一支寫齊了的示範影片長這樣：

<video src="pourover.webm" controls poster="pourover-poster.webp" width="640" height="360">
  <track kind="captions" src="pourover.vtt" srclang="zh-Hant" label="中文字幕" default>
</video>

<video> 上的三個屬性處理的是「操作」和「載入」：

  • controls：顯示瀏覽器內建的播放、暫停、音量、字幕、全螢幕按鈕，而且都能用鍵盤操作。沒有它，使用者只能看著影片，沒辦法暫停、調音量或打開字幕。自己做控制列要處理鍵盤、焦點、名稱等很多事，大部分情況用內建的就好。
  • poster：影片還沒播放時顯示的圖。沒有它，畫面可能是一塊黑色或第一個影格，使用者看不出這是什麼影片。影片檔案大小與載入策略在第 14 課。
  • width／height：先預留空間，影片載入時版面不會跳動。

接著是聽不到聲音的人。示範影片的內容一半在聲音裡：講解的對白，還有熱水壺注水這種提示「現在進行到哪一步」的聲音。聽障使用者、在捷運上靜音看影片的人都拿不到這些資訊，需要的是字幕（captions）：把對白和重要的聲音都轉成文字，聲音用方括號標出來，例如「[熱水壺注水的聲音]」。

字幕要放在一個獨立的檔案裡，格式是 WebVTT（副檔名 .vtt），這是網頁專用的字幕格式。它是純文字，每一段是一個時間碼加上這段時間要顯示的文字：

WEBVTT

00:00.000 --> 00:01.500
[熱水壺注水的聲音]
先用少量熱水悶蒸 30 秒。

影片用 <track> 元素掛上這個檔案，瀏覽器就會在影片上疊出字幕，使用者也能從 controls 的字幕選單開關它。<track> 的屬性各自負責一件事：

  • kind="captions"：這條字幕的種類。最容易搞混的是另一種 kind="subtitles"：subtitles 只有對白的轉錄或翻譯，給聽得到但聽不懂這個語言的人；captions 多了重要的聲音描述，給聽不到聲音的人。<track> 沒寫 kind 時預設是 subtitles，所以含音效描述的字幕要明確寫 kind="captions"。
  • src：WebVTT 字幕檔的位置。字幕檔放在跟頁面同一個網站最單純；放在別的網域時還要額外設定，見課末「補充與查表」。
  • srclang：字幕的語言，寫法跟第 1 課的 lang 一樣，例如 zh-Hant。
  • label：瀏覽器字幕選單裡顯示的名稱。沒有它，選單裡可能只出現一個看不懂的項目。
  • default：預設打開這一條字幕。沒寫的話，字幕檔明明在，使用者還得自己從選單打開，很多人根本不知道有字幕。

只有聲音、沒有畫面的內容用 <audio controls>，規則一樣：要有控制項、不要有聲自動播放；Podcast 這類以講話為主的內容，另外附一份逐字稿。

背景影片：自動播放不能吵人，也要能停下來

示範影片是使用者自己按播放的，背景影片則是一打開頁面就自己開始播。回報清單上的問題就出在這裡：它有聲音，一開頁面就把螢幕閱讀器的報讀蓋掉了。

其實瀏覽器本身就不太讓這種事發生。自動播放（autoplay 屬性）有一套瀏覽器的規則：Chrome 與 Safari 都會擋下有聲音的自動播放，除非使用者已經跟網站互動過（點擊、按鍵），或瀏覽器判斷使用者常在這個網站播放影音；muted 的影片則可以自動播放（MDN 的 Autoplay guide 整理了各瀏覽器的共同規則）。也就是說，有聲自動播放在某些使用者那裡會出聲、在另一些使用者那裡根本不播，結果不可預期。所以首頁背景影片的寫法是：

<video src="hero.webm" autoplay muted loop playsinline aria-hidden="true"></video>
<button type="button" class="hero-pause">暫停背景影片</button>
  • loop：播完從頭重播，背景影片才會一直有畫面。這也是它一定要能暫停的原因：它不會自己停下來。
  • muted：靜音。一方面瀏覽器才允許自動播放，另一方面不會突然出聲蓋過螢幕閱讀器的報讀。WCAG 1.4.2 也要求超過 3 秒的自動播放聲音要能停止。
  • playsinline：在 iPhone 上在頁面裡播放，不自動進入全螢幕。
  • 可以暫停：聲音解決了，畫面還在動。自動開始、持續超過 5 秒的動態內容，要讓使用者能暫停（WCAG 2.2.2）。一直在動的畫面會讓有注意力障礙的人沒辦法讀旁邊的文字。暫停按鈕要用 JavaScript 呼叫 video.pause()，並把按鈕文字切換成「播放背景影片」。為什麼不直接給影片 controls，下一段說明。
  • aria-hidden="true"：背景影片只是營造氣氛、沒有資訊，就把它從無障礙樹拿掉，螢幕閱讀器不會停在它上面。

最後兩點放在一起時有個陷阱。aria-hidden 只是讓螢幕閱讀器不唸，不會讓元素不能被聚焦：有 controls 的影片，控制列還是 Tab 得到，螢幕閱讀器使用者會停在一個什麼都唸不出來的地方，不知道自己在哪裡。所以標成裝飾的背景影片不要同時有 controls，暫停功能改用旁邊那顆看得到、有名稱的按鈕。

💡 實務上：影片需求要在開工前跟行銷講好
行銷常希望首頁形象影片一打開就有聲音播放，工程師要能說明瀏覽器本來就會擋，並提出替代做法：靜音自動播放，旁邊放明顯的「開啟聲音」與暫停按鈕。字幕也要在需求階段就講好由誰交付 .vtt 檔（剪輯廠商、或自動語音辨識後人工校稿），不然常常上線前才發現只有燒進畫面的字幕：關不掉、改一個錯字就要重新輸出影片。如果影片放在 YouTube 或 Vimeo 用嵌入播放器，字幕是上傳到那個平台，不用自己寫 <track>。

影片處理完，回報清單只剩一條：右上角的購物車只唸出「按鈕」。如果那個圖示是 <img>，前面 alt 那一節已經給了答案；但咖啡店的圖示是直接寫在 HTML 裡的 SVG，沒有 alt 屬性可以寫。

購物車只唸「按鈕」：圖示是 inline SVG 時怎麼辦？

前端專案的圖示很常用 inline SVG：把 <svg> 元素直接寫在 HTML（或 Vue 元件的 template）裡，好處是可以用 CSS 改顏色、不用多一次網路請求。但 <svg> 不是 <img>，沒有 alt 屬性。它的替代文字要用 ARIA 屬性處理，判斷方式跟 alt 一樣，先問這個圖示做什麼用：

<!-- 裝飾：按鈕已經有文字，圖示只是點綴 -->
<button type="button">
  <svg aria-hidden="true" viewBox="0 0 24 24">…</svg>
  購物車
</button>

<!-- 有意義：圖示本身就是內容 -->
<svg role="img" aria-label="素食" viewBox="0 0 24 24">…</svg>

裝飾用的 SVG 加 aria-hidden="true"。不加的話，有些螢幕閱讀器會把 SVG 裡的路徑當成一張沒有名稱的圖，唸出一些沒有意義的東西。購物車按鈕最直接的修法就是第一種寫法：按鈕裡放看得到的文字「購物車」，圖示標成裝飾。按鈕的名稱來自文字，螢幕閱讀器唸「購物車，按鈕」。

有意義的 SVG 加 role="img" 和名稱。像菜單上標示「素食」的小圖示，旁邊沒有文字，圖示本身就是資訊。role="img" 讓它在無障礙樹裡被當成一張圖；名稱可以用 aria-label，或在 SVG 的第一個子元素寫 <title>素食</title>。如果設計稿上購物車按鈕只能放圖示、不放文字，也可以把名稱放在按鈕上（例如 aria-label="購物車"），圖示照樣 aria-hidden，重點是按鈕最後要有名稱。

反過來，用 <img src="icon.svg" alt="…"> 載入的 SVG 檔，在 HTML 裡就是一張普通的圖片，照上一節 alt 的規則寫。

到這裡，回報清單上的每一條都修完了：價目表有標題也能在手機上捲、每張圖都依用途寫了 alt、影片有字幕也不再吵人、購物車有了名稱。下面的練習會讓你把這幾件事各自動手做一次。

練習

預覽只能載入題目提供的圖片與影片（放在 web/assets/），網址直接寫檔名，例如 src="03-latte.svg"。

練習 1：下面的價目表用 div 加 CSS Grid 排出來，看起來像表格，但螢幕閱讀器拿不到列與欄的關係。把它改成資料表格：<caption> 寫「飲品價目表」、欄標題（飲品、中杯、大杯）與列標題（飲品名稱）用 <th> 並寫對 scope，價格與資料不變。CSS 已經寫好表格的樣式，設計稿要求表格至少 30rem 寬（rem 是以根元素字級為基準的長度單位，瀏覽器預設 1rem＝16px，30rem 約 480px，細節在第 13 課；這條不要改）：在 320px 寬時，讓表格在自己的容器裡橫向捲動、整頁不能橫向捲動，容器要能用鍵盤聚焦並有名稱。

練習 2：菜單頁有 6 張圖，都還沒有 alt。照每張圖的內容與用途補上 alt（只改 HTML，不增刪圖片）。

03-logo.svg連到首頁的連結裡店名「豆留咖啡」的標誌
03-cart.svg按鈕裡，按鈕沒有其他文字一台推車的圖示，按下去打開購物車

練習 3：首頁的背景影片會自動播放而且有聲音；手沖示範影片沒有控制項、沒有字幕。修正兩支影片：示範影片加上控制項、海報圖 03-pourover-poster.webp、預設開啟的中文字幕（字幕檔 03-pourover.vtt，裡面有音效描述）；背景影片只是營造氣氛，改成靜音自動播放、標成裝飾，並在影片後面加一個「暫停背景影片」的按鈕（按鈕的 JavaScript 由別人接上，這題只寫 HTML）。

練習 4：首頁有一張純裝飾的咖啡豆花紋圖，alt 該怎麼寫？

✓ b：空字串告訴螢幕閱讀器略過這張圖。a、d 會讓使用者聽到對理解沒有幫助的「咖啡豆」「裝飾圖片」。c 錯：沒有 alt 時，有些螢幕閱讀器會改唸檔名，比寫錯更糟。

練習 5：只有購物車圖示的按鈕，圖示 <img> 的 alt 應該描述什麼？

✓ b：按鈕裡只有這張圖時，圖的 alt 就是按鈕的名稱，要說它做什麼。a 描述外觀，使用者不知道按下去會怎樣。c 錯：按鈕會沒有名稱，螢幕閱讀器只唸「按鈕」。按鈕旁邊已經有可見文字「購物車」時，圖示才用 alt=""。d 對使用者沒有意義。

練習 6：把價目表包在 overflow-x: auto 的 div 裡，還需要什麼才能讓鍵盤使用者捲動？

✓ b：可捲動的區域裡沒有能聚焦的東西時，鍵盤使用者 Tab 不進去，方向鍵也捲不動；聚焦後要有角色與名稱，螢幕閱讀器才知道停在哪裡。axe 的 scrollable-region-focusable 規則會抓這個問題。a 錯：只靠鍵盤時不保證能捲動。c 錯：<table> 本來就是 table 角色，跟捲動無關。d 錯：超出的欄位直接被裁掉，誰都看不到。

常見錯誤

  • 用 div 排出「像表格」的價目表：看得到的人覺得沒差，螢幕閱讀器使用者只聽到一串數字。資料表格用 <table>、<th scope>。
  • 寬表格撐破手機版面：整頁橫向捲動。包一層 overflow-x: auto 的容器，加 tabindex="0" 與名稱。
  • alt 塞關鍵字：對使用者是噪音，Google 也把關鍵字堆砌視為垃圾內容，違反它的 spam 政策。alt 寫一句描述就好。
  • 裝飾圖不寫 alt：螢幕閱讀器可能唸出檔名。裝飾圖要明確寫 alt=""。
  • 用 title 屬性代替 alt：title 只在滑鼠停留時出現，觸控與鍵盤使用者看不到，螢幕閱讀器的支援也不一致，它不是替代文字。
  • 只有字幕檔沒有 default：使用者要自己從選單打開。重要的教學影片預設開啟；沒寫 kind 時預設是 subtitles，含音效的字幕要寫 kind="captions"。
  • aria-hidden 加在可以聚焦的元素上：螢幕閱讀器不唸它，Tab 卻停得到。裝飾影片不要加 controls，或乾脆不要藏。

小結

  • 一格的意思要靠列和欄一起決定，才是表格資料，用 <table>；只是排成幾欄的版面用 Flexbox／Grid。caption 當標題，<th scope="col|row"> 讓每一格唸得出對應的標題。
  • 寬表格放進 overflow-x: auto 的容器，加 tabindex="0"（鍵盤才捲得動）、role="region" 和名稱（聚焦時知道停在哪），整頁不橫向捲動。
  • alt 看用途：資訊寫資訊、功能寫功能、裝飾寫 alt=""、複雜圖附完整文字。不寫「圖片」、不寫檔名、不堆關鍵字。
  • figcaption 是給所有人的說明，alt 是看不到圖的人的替代內容，兩者不重複。
  • 影片給 controls、poster、<track kind="captions" default>；自動播放要 muted 並能暫停；aria-hidden 的元素不能被聚焦。
  • inline SVG 沒有 alt：裝飾的加 aria-hidden="true"，有意義的加 role="img" 和名稱。

補充與查表

主線用不到、但遇到特殊情況時會需要的細節，查表用，不用背。

  • 兩層以上的表頭：表頭只有一層時，scope 就夠用。如果表頭有兩層以上（例如「熱飲」底下再分「中杯／大杯」），要用 headers 屬性逐格指定，寫起來容易錯。實務上先考慮能不能拆成兩張簡單的表格。
  • 字幕檔放在別的網域：<track> 的字幕檔預設必須跟頁面同源（same origin：協定、網域、port 都相同）；放在別的網域時，<video> 要加 crossorigin 屬性，對方伺服器也要允許跨來源讀取（CORS）。
  • 捲動容器會不會自動可以聚焦：沒有可聚焦子元素的捲動容器，在有些瀏覽器裡鍵盤聚焦不到（MDN 的 overflow 頁面也這樣提醒），有些瀏覽器的新版本則會自動讓它可以聚焦。各瀏覽器行為不一致，而且自動聚焦的容器沒有名稱，所以仍然自己加 tabindex="0" 與名稱。
  • srclang 的寫法：用 BCP 47 語言標籤，跟第 1 課的 lang 同一套。
  • 多條字幕：一支影片可以有好幾個 <track>（例如中文字幕、英文字幕），但只能有一個 track 帶 default。
