階段 2：CSS 與版面基本功 · 第 11 課

RWD：mobile-first、media queries、內容斷點與觸控

咖啡店的新網站上線一個月，客服轉來三張回報單。第一張：「用手機看首頁，找不到營業時間。」第二張：「菜單上的加入購物車按不到，要在卡片上亂點才會出現，出現了又很難按準。」第三張來自一位熟客：「我把手機瀏覽器的字調大之後，訂單確認頁的結帳按鈕字被切掉一半，整頁還會左右滑。」三張回報單看起來不相干，原因其實是同一個：這個網站只在設計師的桌機螢幕上被認真做過。客人用的螢幕有窄有寬，有人用手指、有人用滑鼠，有人需要把字放大，同一份網頁要在這些情況下都好用。

讓同一份 HTML 依螢幕寬度與裝置能力調整版面的做法，叫做響應式網頁設計（Responsive Web Design，RWD）。這課從頭到尾處理這三張回報單：先修好首頁在窄螢幕的版面，再讓按鈕在觸控裝置上看得到、按得準，最後把「字放大、縮放」也納入上線前的驗收。用到的版面工具都是前幾課的 Flexbox 與 Grid，這課要學的是「什麼條件下套用哪一套版面」。

這課的路線：
  1. 第一張回報單：先認識 media query（CSS 裡的條件區塊），再讀前一位工程師的 desktop-first CSS，看營業時間是怎麼被「刪」掉的。
  2. mobile-first：把寫 CSS 的方向反過來，手機版是基本樣式、螢幕變寬才往上加。這一節結束時，第一張回報單就有解法了。
  3. 斷點：版面該在哪個寬度切換、數字為什麼寫成 40em 而不是 640px、條件怎麼寫才不會在兩段之間留縫。
  4. 第二張回報單：寬度看不出客人用手指還是滑鼠，用 hover、pointer 判斷裝置能力，再把按鈕做到手指按得準。
  5. 第三張回報單與上線驗收：320px 寬、文字放大 200%、縮放 400% 時版面不能壞，這也是無障礙稽核會測的項目。
這課會用到：
  • 第 1 課的 viewport meta：沒有它，手機瀏覽器會用約 980px 的虛擬寬度排版，media query 不會照手機寬度生效。
  • 第 8 課的 flex-wrap: wrap：一行放不下的項目自動換到下一行。
  • 第 9 課的 grid-template-columns：定義格線有幾欄、每欄多寬，例如 repeat(auto-fill, minmax(16rem, 1fr))。

第一張回報單：手機上的營業時間跑去哪了？

先看設計師原本要的樣子。咖啡店首頁有三塊：頁首（logo 和選單）、菜單卡片、營業時間側欄。設計師給了三張圖，分別是手機、平板、桌機的寬度：

三張圖裡，營業時間都在。手機上它排在菜單後面，桌機上它移到右邊成為側欄。也就是說，設計上從來沒有「手機不顯示營業時間」這回事，是寫 CSS 的過程弄丟的。要看懂它怎麼弄丟，得先認識讓「不同寬度套用不同版面」成為可能的工具。

到上一課為止，我們寫的 CSS 規則都是無條件的：.menu { grid-template-columns: repeat(3, 1fr) } 寫下去，不管螢幕多寬，菜單都是三欄。但三張設計圖要的是「窄的時候一欄、寬一點兩欄、更寬三欄」，CSS 需要一種寫法來表達「在某個條件下，才套用這些規則」。這就是 media query：一個用 @media 開頭、括號裡寫條件的區塊，條件成立時，區塊裡的規則才生效。最常用的條件是視窗寬度：

@media (width >= 40em) {     /* 視窗寬度至少 40em（預設字級下是 640px）時 */
  .menu {
    grid-template-columns: repeat(2, minmax(0, 1fr));
  }
}

括號裡的 width >= 40em 讀作「視窗寬度大於或等於 40em」。em 這個單位放在 media query 裡有特別的算法，後面「斷點的數字：為什麼寫 em」那一節再講，現在先把它當成 640px。另一種你在舊專案會常看到的寫法是 (max-width: 639px)，意思是「視窗寬度最多 639px」；對應的 (min-width: 640px) 是「至少 640px」。這兩種寫法的差別也在那一節說明。

這裡的「視窗寬度」是瀏覽器用來排版的寬度，單位是 CSS px。桌機上它大約就是瀏覽器視窗的寬度；手機上則要靠第 1 課的 viewport meta：有寫 <meta name="viewport" content="width=device-width, initial-scale=1">，手機才會用自己螢幕的寬度排版。少了它，手機會假裝自己約 980px 寬，再把整頁縮小顯示，你寫給手機的 media query 一條都不會成立。使用者轉動手機、拖動視窗大小時，瀏覽器會重新判斷每個條件，版面跟著即時切換，不用重新整理。

media query 怎麼跟一般規則互動，是讀懂舊 CSS 的關鍵。它不會提高權重（第 6 課）。條件不成立時，整段規則當作不存在；條件成立時，裡面的規則跟外面的規則照一般的層疊規則比：權重一樣就後寫的贏。所以 media query 通常寫在它要覆蓋的規則後面，寫在前面的話，條件成立了也會被後面的一般規則蓋掉。

有了這些，就可以讀前一位工程師的 CSS 了。版面的部分大致是這樣（完整版在練習 1 的起始程式）：

/* 桌機版寫在最前面 */
.layout { grid-template-columns: minmax(0, 1fr) 16rem; }   /* 主內容 + 右側欄 */
.menu   { grid-template-columns: repeat(3, minmax(0, 1fr)); }

/* 平板：把桌機的設定改回來 */
@media (max-width: 1023px) {
  .layout { grid-template-columns: minmax(0, 1fr); }
  .menu   { grid-template-columns: repeat(2, minmax(0, 1fr)); }
}

/* 手機：再改一次 */
@media (max-width: 639px) {
  .menu { grid-template-columns: minmax(0, 1fr); }
  .info { display: none; }
}

用一支 375px 寬的手機走一遍：最上面的桌機規則一定套用；375 小於 1023，平板那段成立，把側欄和三欄改回來；375 也小於 639，手機那段也成立，再把兩欄改成一欄。三層規則疊在一起，後兩層都在撤銷前一層。最後一行 .info { display: none } 就是營業時間消失的原因。

這一行是怎麼來的，不難想像：先寫好桌機版，縮到手機寬度時，側欄擠在旁邊很難看，最快讓它「不難看」的方法就是藏起來。這是先寫桌機、再往下改的寫法（叫 desktop-first）常見的下場：小螢幕的版本是從桌機版「刪剩的」，不是設計過的。而手機正好是客人最需要查營業時間的地方，在路上、在店門口。

所以問題不在某一行寫錯，而在寫的方向：從最寬的版本往下改，每到一個更窄的寬度就要決定「要撤銷什麼、要刪掉什麼」。下一節把方向反過來。

把方向反過來：mobile-first 怎麼寫？

上一節的 CSS 從桌機往下改，所以叫 desktop-first。反過來的寫法叫 mobile-first：不包在任何 media query 裡的基本樣式，就是給最窄螢幕的版本；螢幕變寬、空間變多時，再用「至少多寬」的條件（width >= 或 min-width）加上調整。

用菜單卡片的欄數看 mobile-first 的寫法長什麼樣：

.menu { display: grid; gap: 1rem; }      /* 基本：一欄，給手機 */

@media (width >= 40em) {                  /* 640px 起：兩欄 */
  .menu { grid-template-columns: repeat(2, minmax(0, 1fr)); }
}

@media (width >= 64em) {                  /* 1024px 起：三欄 */
  .menu { grid-template-columns: repeat(3, minmax(0, 1fr)); }
}

再走一遍不同寬度。375px 的手機：兩個條件都不成立，只有基本樣式，grid 沒有指定欄數時就是一欄。800px 的平板：第一個條件成立，變成兩欄。1280px 的桌機：兩個條件都成立，兩段規則的權重一樣，用上一節講的「後寫的贏」，三欄勝出。這也說明了 mobile-first 的條件為什麼要由小到大排：寬的條件寫在後面，兩個都成立時才會由它決定。

跟上一節對照，差別在手機那一端。desktop-first 的手機要套用三層、撤銷兩次；mobile-first 的手機只套用基本樣式，每一層 media query 都只是「加」。同一個首頁兩種寫法的比較：

desktop-firstmobile-first
基本樣式三欄、側欄在右、選單一行單欄。大部分是正常流（第 7 課），幾乎不用寫
media query(max-width: 1023px)、(max-width: 639px)(width >= 40em)、(width >= 64em)
手機套用幾層三層，後兩層都在「撤銷」前一層：display: block 撤銷 flex、1fr 撤銷三欄只有基本樣式
加一個桌機元件寫在基本樣式，再去每個 max-width 裡想要不要撤銷；漏了，手機就壞寫在 (width >= 64em) 裡，碰不到手機
沒有被測到的寬度落到最複雜的版本落到最簡單、最不會壞的單欄

表格的最後兩列是長期維護時最有感的差別。之後每加一個只給桌機的元件，desktop-first 要回頭檢查每一段 max-width，漏一個手機就壞；mobile-first 把它寫進最寬的那段就好。某個寬度沒人測到時，mobile-first 最壞的情況是看到單欄版：不漂亮，但東西都在、都按得到。

營業時間在 mobile-first 裡怎麼處理？答案是什麼都不用寫。單欄的 grid 裡，子元素照 HTML 順序由上往下排，首頁的 HTML 是先 <main>（菜單）、後 <aside>（營業時間），手機上營業時間自然排在菜單後面；到了 64em 才用 grid-template-columns 把它放到右邊。這背後有一個原則：HTML 的順序就是手機上的閱讀順序，也是鍵盤 Tab 和螢幕閱讀器的順序（第 5 課），所以 HTML 要先依「重要的先讀到」排好，寬螢幕時才用 grid 調整位置。不要用 order 或 grid 的位置把視覺順序改得跟 HTML 不一樣（第 8 課），看的人和用鍵盤的人會走到不同的順序。

實際動手時的順序：

  1. 不開任何 media query，在最窄的寬度（320px）把頁面做好：內容順序對、文字讀得順、按鈕按得到。
  2. 慢慢拉寬預覽，等到版面開始變難看（卡片寬到一行四十幾個字、圖片被拉得很大、兩側空白太多）才加第一個斷點，只在裡面寫「多出來的空間要怎麼用」。
  3. 繼續拉寬，重複第 2 步。

mobile-first 不代表「只做手機」，也不代表手機版比較陽春。它是一種寫 CSS 的方向：從限制最多的情況出發，空間多了才加東西。被拿掉的東西要有理由，像營業時間這種必要資訊，窄螢幕應該換位置，而不是消失。

💡 實務上：設計稿常常只有桌機版，先問手機上什麼最重要
工作中很常拿到只有桌機寬度的設計稿，這時不要自己猜哪些內容可以刪，先跟設計師或 PM 確認：窄螢幕時哪些內容排前面、哪些可以收合，例如咖啡店的營業時間和「線上點餐」按鈕要留在手機第一屏附近。接手 desktop-first 的舊專案時，也不用一次全部重寫：新元件用 mobile-first 寫，舊頁面在改到時再順手整理，比較不會一次弄壞很多頁。也不是每個畫面都要做到手機一樣好用：只給店員在櫃檯電腦用的後台報表，可以先確認「最窄支援到多寬」，把時間花在客人會用手機開的頁面。

方向對了，第一張回報單的解法也有了：基本樣式是單欄、營業時間在菜單後面，寬螢幕才往上加欄位。但上面動手順序的第 2 步說「版面開始變難看才加斷點」，範例裡的 40em、64em 又是哪來的？下一節回答這兩個數字。

斷點要設在哪個寬度？

上一節的 40em、64em 這種「版面在這個寬度切換」的數字，叫做斷點（breakpoint），也就是 media query 條件裡的那個數字。決定斷點，就是決定版面在哪裡從一欄變兩欄、從兩欄變三欄。

最常見的錯誤是照熱門手機寫：375px（某支 iPhone）、768px（某台 iPad）。這看起來很合理，客人用什麼手機就對什麼手機寫，但手機型號每年換，寬度從 320 到 430 都有，還有摺疊手機、分割畫面、沒有全螢幕的瀏覽器視窗。對著型號寫的斷點，下一支手機出來就不準了，而夾在兩個型號之間的寬度沒有人想過會長什麼樣子。

斷點對準的應該是內容在什麼寬度開始變難用。內容不會因為手機換代而改變，菜單卡片在多寬時變難讀，今年和明年是一樣的。判斷「變難用」有三個訊號：

  • 行長：一行太長，眼睛換行時容易跳錯行。英文的建議是每行 45～75 個字元；中文一個字比較寬，大約 30～40 個字。菜單卡片的說明文字到了一行 40 幾個字，就該分成兩欄了。
  • 元素被拉大到不合理：一張卡片佔滿 900px 寬，價格離品名很遠。
  • 擠在一起：反過來，一行塞了四個選單項目，文字開始換行或被擠扁，就該在更窄的時候換成兩欄。

找斷點的工具是瀏覽器本身。在 Chrome DevTools 按 Cmd＋Shift＋M（Windows 是 Ctrl＋Shift＋M）開啟裝置模式，選 Responsive，拖拉右邊的把手改變寬度，觀察版面在哪裡開始出現上面三個訊號，那就是斷點。以首頁來說，從 320px 慢慢拉寬，單欄的菜單卡片在 640px 左右開始顯得太寬，於是在那裡分成兩欄；繼續拉到 1024px 左右，兩欄的卡片又太寬、旁邊也放得下側欄，於是在那裡變三欄並把營業時間移到右邊。

斷點通常 2～3 個就夠了。很多元件根本不需要斷點：第 8 課的 flex-wrap、第 9 課的 repeat(auto-fill, minmax(…)) 會自己依空間換行。斷點只留給整頁骨架這種「要換排法」的地方。

💡 實務上：斷點是團隊約定，不是每個人各自決定
團隊專案通常會有一組共用的斷點，通常會寫在專案的樣式規範裡，或沿用 CSS 框架預設的 sm／md／lg。你的工作是在這幾個斷點裡解決問題，不是看到某個寬度跑版就加一個 (width >= 913px)：這種「只為修一個 bug」的斷點，半年後沒有人知道它為什麼存在。遇到某個元件在某段寬度很難看，先試著讓元件自己能伸縮（flex-wrap、auto-fill，或下一課的 container query），真的需要新斷點時，再跟設計師一起決定、加進共用清單。

位置找到了，接著要把它寫成數字。DevTools 量出來的是 640px、1024px，設計稿標的也是 px，範例裡卻寫成 40em、64em；條件的寫法也有 max-width、min-width、width >= 好幾種。下一節說明該選哪一種、為什麼。

斷點的數字：為什麼寫 em，條件怎麼寫才不會有縫？

先回答單位。media query 裡的 em（和 rem）跟一般屬性裡的不一樣：它以瀏覽器的預設字級計算，不看你在 html 寫的 font-size。預設字級是 16px 時，40em 就是 640px，跟 px 寫法完全一樣。差別出現在使用者到瀏覽器設定裡把預設字級調大的時候（Chrome：設定 → 外觀 → 字型大小）。拿首頁「640px 起菜單兩欄」這條規則比較：

情況(width >= 640px)(width >= 40em)
預設字級 16px、視窗 700px成立，兩欄40 × 16 = 640，成立，兩欄
使用者把預設字級調成 24px、視窗 700px仍然成立：字變大 1.5 倍，卻還是硬擠兩欄，每欄只放得下幾個字40 × 24 = 960，不成立，維持一欄
使用者用 Cmd／Ctrl ＋「＋」縮放到 200%兩種都會跟著變：縮放讓視窗的 CSS 寬度變成一半（1400px 的視窗只剩 700 CSS px）

第二列是關鍵。上一節說斷點要對準「一行放得下幾個字」，字變大 1.5 倍，同樣 700px 寬放得下的字就少了三分之一。px 斷點不知道字變大了，照樣切成兩欄；em 斷點跟著字級移動，切換點仍然對準內容。所以用 em 寫的斷點，正是內容斷點要的。px 字級則有另一個問題：它不會跟著使用者的預設字級放大，這留到第 13 課談單位時細講；這課的練習先記住「字級用 rem」。

media query 的 em 為什麼不看 html 的 font-size？這是規範定的（Media Queries Level 4）：media query 裡的相對單位一律以「初始值」計算，不看頁面上任何 CSS 宣告，所以 em、rem 都等於瀏覽器的預設字級。實際換算很簡單：設計稿通常用 px 標寬度，除以 16 就是 em，640px → 40em、1024px → 64em。團隊可以把斷點集中寫成註解或 design token（第 26 課），不要每個檔案各寫各的。

再來是條件的寫法。舊寫法 min-width／max-width 用冒號，只能表達「至少」和「最多」；Media Queries Level 4 加入了範圍語法，直接用數學的比較符號，主流瀏覽器都已支援（支援狀況見課末「補充與查表」）：

舊寫法範圍語法意思
(min-width: 40em)(width >= 40em)至少 40em，包含 40em
(max-width: 63.99em)(width < 64em)小於 64em，不包含 64em
(min-width: 40em) and (max-width: 63.99em)(40em <= width < 64em)只在平板這一段

範圍語法除了好讀，還解決一個真實的 bug。舊寫法沒有「小於」，只有「最多」，desktop-first 要把兩段接起來時常寫 (max-width: 767px) 配 (min-width: 768px)，以為 767 和 768 之間沒有東西。但視窗寬度不一定是整數：使用者縮放頁面、或在高解析度螢幕上，視窗寬度可能是 767.5 CSS px，兩條都不成立，版面掉進兩套樣式之間，出現一個誰都沒設計過的樣子。width < 768px 與 width >= 768px 剛好接在一起，不會有縫。mobile-first 只寫單向的 width >= 條件，本來就不需要兩段對接，也就不會遇到這個問題。

到這裡，第一張回報單需要的東西都齊了：基本樣式給手機、(width >= 40em) 加兩欄、(width >= 64em) 加三欄和側欄，練習 1 就是做這件事。接下來是第二張回報單「加入購物車按不到」，它在任何寬度的條件下都修不好，因為問題不在寬度。

第二張回報單：寬度看不出客人用手指還是滑鼠

菜單卡片的「加入購物車」按鈕是這樣寫的（完整版在練習 2 的起始程式）：

.add {
  padding: 2px 8px;
  opacity: 0;                 /* 平常透明 */
  transition: opacity 0.2s;
}
.card:hover .add {
  opacity: 1;                 /* 滑鼠移到卡片上才出現 */
}

在桌機上，這個設計看起來很乾淨：滑鼠移到哪張卡片，那張卡片的按鈕才浮出來。到了手機就出事了。:hover 的意思是「游標停在元素上」，手指沒有「停在上面」這個狀態，只有按下和放開。觸控裝置為了相容舊網站，手指點一下會讓被點的元素進入 :hover，而且一直卡在那個狀態，直到點別的地方。結果就是回報單上寫的：客人不知道要點卡片，偶然點到了按鈕才出現，之後那張卡片又一直維持 hover 的樣子，看起來像被選取。更危險的是，opacity: 0 只是看不見，元素仍然佔著位置、仍然接收點擊，所以客人在手機上點卡片時，可能一點就落在透明的按鈕上，商品被加進購物車，客人卻根本沒看到按鈕。這也是下面「必要操作平常就要看得到」的另一個理由。鍵盤使用者也一樣，Tab 到按鈕時不會觸發 :hover，按鈕還是透明的。

直覺的修法是「窄螢幕就讓按鈕一直顯示」，但寬度不等於裝置。iPad 接了觸控板可以 hover，觸控螢幕筆電的寬度跟桌機一樣，手指卻按不準小按鈕。用寬度猜裝置，兩邊都會猜錯。media query 除了寬度，還可以直接問裝置能力。這些可以判斷的條件統稱媒體特性（media feature），寫在 @media 後面的括號裡，width 就是其中一個。跟輸入方式有關的是這幾個：

媒體特性值問的是
hoverhover／none主要輸入裝置能不能方便地 hover。手機是 none（長按模擬的 hover 不算方便）
pointerfine／coarse／none主要輸入裝置的精準度：滑鼠是 fine、手指是 coarse
any-hover、any-pointer同上任何一個輸入裝置符合就成立（例如觸控筆電也接了滑鼠）

兩個條件可以用 and 連起來，兩個都成立時整個 media query 才成立。最常用的組合是只在「能 hover、又點得準」的滑鼠裝置加 hover 效果：

@media (hover: hover) and (pointer: fine) {
  .card:hover .add {
    background-color: #6b4423;
    color: #fff;
  }
}

為什麼除了 (hover: hover) 還要加 (pointer: fine)？hover 只問「能不能停在元素上」，不問「點得準不準」。有些裝置的主要輸入能 hover、卻不精準，Media Queries 規格舉的例子是遊戲機的體感遙控器，在這類裝置上強化 hover 的小按鈕幫助不大。加上 pointer: fine，範圍就收斂到滑鼠和觸控板。這是偏保守的寫法：只寫 (hover: hover) 在多數情況也夠用，兩個都寫只是把「加強效果」限定在最確定適用的裝置上。

包起來之後，觸控裝置上這段規則當作不存在，點過的卡片就不會卡在 hover 的樣子。但注意這段只寫了「加強」：背景變成品牌色。按鈕本身平常就要看得到、按得到，不能把 opacity: 0 留在外面、只在這段裡改成 1，那樣觸控和鍵盤使用者還是看不到按鈕。

這就是處理觸控的規則：必要的資訊與操作平常就看得到，hover 只用來加強（變色、陰影、淡入的背景），而且包在 (hover: hover) 裡。「滑鼠移上去才出現加入購物車」「hover 才顯示價格」這類設計，到了手機就等於沒有。判斷不了裝置的情況，就用「兩邊都能用」的設計：按鈕永遠顯示、尺寸夠大，hover 只是錦上添花。媒體特性用來加強，不用來決定「誰能用這個功能」。

按鈕看得到了，回報單的後半句還沒解決：「出現了又很難按準」。padding: 2px 8px 的按鈕、按鈕之間只隔 4px，對滑鼠游標夠用，對手指不夠。下一節處理大小與間距。

手指按得準嗎？點擊目標的大小與間距

手指比滑鼠游標粗得多。滑鼠游標點的是一個點，手指按下去接觸的是一整片，按到的位置還會因為角度、手的大小而偏移。按鈕太小，客人要按好幾次；兩個按鈕太近，想按「加入購物車」卻按到旁邊的「介紹」，被帶到另一頁。

多小算太小，有明確的標準。WCAG 2.5.8 目標尺寸（Target Size (Minimum)，AA，第 5 課的練習用過這個數字）規定：點擊目標至少 24×24 CSS px。比較小的目標要靠間距補：以每個小目標的中心畫直徑 24px 的圓，這個圓不能碰到別的目標，也不能碰到別的小目標的圓；句子裡的文字連結例外。更嚴格的 2.5.5（AAA）要求 44×44，Apple 的設計指南也建議 44pt。24 是底線，44 是讓手指舒服的大小。

落到 CSS 上的做法：

  • 主要操作（加入購物車、結帳、選單項目）做到 44×44：用 min-height: 44px 加 padding，而不是固定 height。固定 height 在字放大時會出問題，最後一節會看到。
  • <a> 是 inline，要先改成 inline-flex 或 block，padding 才會撐開點擊區（第 7 課）。卡片上的「介紹」連結就是這種情況。
  • 相鄰的按鈕用 gap 至少隔 8px，手指才不會按到隔壁。
  • 段落裡的文字連結維持 inline，不用硬放大（2.5.8 的例外），但不要讓兩個連結緊貼在一起。菜單下方「過敏原說明」那種句子裡的連結就屬於這類。

回頭看首頁練習 1 的起始程式，選單連結已經寫了 min-height: 44px，練習 2 要你把同樣的標準套到卡片的按鈕上，再加上只在滑鼠裝置生效的 hover 效果。觸控相關的其他情況（手機上的漢堡選單、表單的鍵盤）放在課末「補充與查表」。

首頁的兩張回報單到這裡都有解法了。第三張回報單發生在訂單確認頁，情境又不一樣：客人的寬度沒變、裝置也沒變，只是把字放大。這種情況要怎麼在上線前就發現？

第三張回報單：字放大就壞，上線前怎麼驗收？

熟客回報的訂單確認頁，在 320px 寬、預設字級時看起來沒問題，所以開發時沒人發現。熟客說的「字調大」，對網頁來說是瀏覽器的字級設定（手機系統的文字大小設定不一定會套用到網頁），所以重現和驗收都用調大瀏覽器的預設字級來模擬。字放大 200% 之後，結帳按鈕的字被切掉一半、價格欄被撐破、整列擠不下而橫向捲動。這說明 RWD 做完要驗收的，不只是「手機、平板、桌機各看一眼」。WCAG 有兩條跟版面直接相關，也是無障礙稽核會實際操作的項目：

條文要求怎麼測
1.4.10 重排（Reflow，AA）由上往下捲的頁面，在 320 CSS px 寬時內容不能遺失，也不能需要左右捲動（地圖、資料表、圖表這類本來就需要二維版面的內容例外）DevTools 裝置模式設 320px；或把 1280px 寬的瀏覽器縮放到 400%（1280 ÷ 4 = 320），兩者等價
1.4.4 調整文字大小（AA）文字放大到 200% 時，內容和功能不能遺失（不能被裁掉、重疊、看不到）瀏覽器設定把預設字級調大；或在 DevTools 選取 <html>，Styles 加上 font-size: 200%（字級用 rem 時，文字放大的效果相同；但 em 斷點只跟著瀏覽器設定移動，不會因為 html 的 font-size 而切換）

第一條其實就是首頁那張回報單的驗收標準：320px 時營業時間要在，而且不能左右滑。第二條對應熟客的回報。字放大時會壞，原因幾乎都是「盒子的大小寫死了，內容長大時盒子不跟著長」。最常見的四種：

  • 固定 height：height: 40px; overflow: hidden 的按鈕，字變兩倍高就被裁掉。這就是熟客看到的「結帳按鈕字被切掉一半」。改成 min-height 加 padding，讓盒子跟著內容長高。
  • 固定 px 寬度的欄位：width: 80px 的價格欄，字變大就被撐破。讓寬度由內容決定，需要對齊時用 min-width: 5em（em 會跟著字級變大）。
  • 不換行的一列：品名、價格、按鈕硬擠在一行，字變大後擠不下，整頁就能左右滑。加 flex-wrap: wrap，品名給一個 basis（例如 flex: 1 1 10rem），空間不夠時價格和按鈕自動換到下一行。
  • 用 html { font-size: 16px !important } 擋住放大：這是把問題丟給使用者，不是修好。

練習 3 就是修這個訂單確認頁。三張回報單都修好之後，要確保下次改版不會再壞。下面這份驗收清單，每次改版面都跑一次：

  1. 320px 寬：沒有橫向捲動、沒有內容被藏掉。頁面可以左右滑時，用第 7 課的 Console 片段找出撐破的元素。
  2. 最大的設計寬度（例如 1440px）：行長沒有過長、內容有 max-width。
  3. 每個斷點的前後 1px（639／640、1023／1024）：切換是乾淨的，沒有中間狀態。
  4. 文字放大 200%：按鈕文字、價格完整，沒有重疊。
  5. 手機橫放（例如 844×390）：高度很矮，sticky 頁首（第 10 課）不能佔掉半個畫面。
  6. 觸控：用 DevTools 裝置模式選一支手機，再拿真的手機點一遍：確認沒有東西要 hover 才看得到、按鈕按得準、點過的卡片不會卡在 hover 的樣子。

清單的每一項都對應這課的一件事：第 1、3 項是斷點與 mobile-first，第 4 項是第三張回報單，第 6 項是第二張回報單。這些檢查在第 27 課會寫成 Playwright 的自動化測試，不用每次手動點。

💡 實務上：收到「手機上跑版」的回報，先問清楚再修
客服轉來「客人說手機上結帳按鈕按不到」，先問：什麼手機、什麼瀏覽器、直放還橫放、有沒有把字調大、是 App 裡開的網頁還是瀏覽器，最好附截圖。拿到資訊後在 DevTools 用同樣的寬度重現，很多「只有某支手機壞」其實是字級調大或橫放造成的，用上面的清單就測得出來。結帳、點餐這種會影響營收的流程，上線前除了 DevTools，至少再拿一支真的 iPhone 和一支 Android 點過一遍。送 PR（請同事審查、合併程式碼的請求）時附上 320px 和桌機寬度的截圖，審查的人不用自己開環境也能看出版面有沒有問題。

最後要知道 media query 的限制：它只知道視窗多寬，不知道元件被放在多寬的容器裡。首頁的骨架靠它切換沒問題，但同一張卡片放在主欄和側欄要不同的版面時，第 12 課的 container query 比較適合；第 13 課的 clamp() 流動尺寸則能讓字級、間距連續變化，又少寫幾個斷點。

補充與查表

範圍語法的支援狀況

Media Queries Level 4 的範圍語法已經是 Baseline widely available（web-features 3.44.0，2025-09-27 起），可以放心用。

media query 的完整組成

一個 media query 由媒體類型和媒體特性組成。媒體類型只剩 screen（螢幕）、print（列印）、all（預設，可以省略）三個常用；媒體特性是可以判斷的條件，寫在括號裡。組合條件的寫法：

@media (width >= 40em) and (orientation: landscape) { … }   /* and：兩個都成立 */
@media (width < 30em), print { … }                         /* 逗號：任一個成立（or） */
@media not (hover: hover) { … }                              /* not：反過來 */

其他常用的媒體特性

媒體特性值問的是
prefers-color-schemelight／dark使用者選的系統深淺色，第 16 課
prefers-reduced-motionreduce／no-preference使用者要求減少動畫，第 17 課

手機上的選單

頁首選單在窄螢幕常見兩種做法：

做法適合代價
直接全部顯示，排成兩欄或換行（這課練習 1 的做法）選單項目 5 個以內佔一點高度；但客人一眼就看到有哪些頁面
漢堡選單：一個「選單」按鈕，按了才展開項目多、窄螢幕放不下需要 JavaScript；選單被藏起來，使用者比較少點；要處理鍵盤與螢幕閱讀器

真的要做漢堡選單時，開關一定是 <button aria-expanded="false" aria-controls="site-nav">選單</button>（第 5 課）：用 <button> 鍵盤才按得到，按下時用 JavaScript 把 aria-expanded 改成 true 並顯示選單，螢幕閱讀器才知道它展開了。按鈕上只放三條線的圖示時，要有文字名稱（看得見的「選單」兩個字最好）。桌機寬度時按鈕藏起來、選單直接顯示，這部分用 media query 切換。

手機上的表單與鍵盤

手機上填表單最痛苦的是鍵盤。第 4 課的 type="tel"、inputmode="numeric"、autocomplete 在手機上影響最大：選對了，電話欄會跳出數字鍵盤、地址可以自動填入。另外輸入框的字級不要小於 16px：iOS Safari 遇到更小的字級，聚焦時會自動把整頁放大，填完還要自己縮回來。

練習

練習 1：咖啡店首頁的 CSS 是 desktop-first：先寫桌機版，再用兩段 max-width 一路改回來，結果手機版還把營業時間整塊藏掉了。把版面部分改寫成 mobile-first：基本樣式就是手機版（單欄、選單兩欄排在 logo 下面）；40em 起菜單兩欄；64em 起頁首選單跟 logo 排成一行、菜單三欄、側欄（營業時間）移到右邊成為一欄。窄螢幕時側欄排在菜單後面，不能藏起來。斷點用 em／rem、不要有 max-width 型的 media query，各寬度的版面要跟起始程式原本的設計一致（上半部的元件樣式不用動）。HTML 不能改。

練習 2：菜單卡片的「加入購物車」按鈕平常是透明的，桌機要把滑鼠移到卡片上才出現；手機沒有 hover，客人根本看不到它。改成：按鈕永遠看得到、可以按；只有在 (hover: hover) and (pointer: fine) 的裝置上，hover 卡片時按鈕才加上漸變的強化效果（例如背景變成品牌色）。另外，所有按鈕與連結的點擊區至少 44×44（段落裡的文字連結例外），320px 寬時相鄰按鈕至少隔 8px。HTML 不能改。

練習 3：訂單確認頁在 320px 寬、預設字級時看起來沒問題。但視力不好的客人把字放大到 200% 時（測試會在預覽的 <html> 設 style.fontSize = '200%' 再量），固定高度的按鈕把文字裁掉、固定寬度的價格欄被價格撐破、整列擠不下而橫向捲動。修好它：預設字級與放大 200% 時，320、768px 寬都要內容完整、不能橫向捲動；按鈕不要固定高度（用 min-height）；品名、價格、按鈕不要固定 px 寬度，也不要把字縮小；字級用 rem。不能擋住使用者放大，也不能把內容藏起來。HTML 不能改。

練習 4：mobile-first 的 CSS 裡，media query 通常長什麼樣？

✓ b：基本樣式給最窄的螢幕，空間變多時用「至少多寬」（width >= 或 min-width）往上加，斷點用 em。a 是 desktop-first 的「往下改」。c 對著某一支手機的寬度寫，換一支手機就不成立，而且 device-width 已經被規範棄用。d 是列印樣式，跟螢幕寬度無關。

練習 5：為什麼 media query 的斷點建議用 em，不用 px？

✓ b：media query 的 em 以瀏覽器預設字級計算，字級調大後，40em 代表的寬度也變大，大字的使用者會提早看到單欄版。a 不是理由。c 錯：px 斷點完全合法，只是不會跟著字級調整。d 錯：範圍語法 px、em 都能用。另外注意：用 Cmd／Ctrl＋「＋」縮放頁面時，px 與 em 斷點都會跟著變。

練習 6：菜單卡片的價格只在 .card:hover 時顯示。客人用手機看菜單，會發生什麼事？

✓ b：觸控沒有「游標停在上面」這個狀態。手指點一下可能讓元素進入 :hover，但客人不知道要點，點了之後狀態又會卡住。必要資訊要平常就看得到，hover 只做加強，並包在 @media (hover: hover) 裡。a、c、d 都不是瀏覽器的行為；鍵盤使用者也觸發不了 :hover。

常見錯誤

  • 對著手機型號寫斷點：375px、768px 只對某幾台裝置有意義，新裝置一出來就不準。拉寬預覽，在內容開始變難讀的地方加斷點，用 em 寫。
  • desktop-first 的覆寫地獄：手機樣式忙著撤銷桌機樣式，加一個桌機元件就要回頭檢查每個 max-width。基本樣式給手機，用 (width >= …) 往上加。
  • max-width 與 min-width 的斷點中間有縫：767px／768px 在縮放比例下會出現 767.5px，兩邊都不成立。用範圍語法 width < 48em，或乾脆只寫 mobile-first 的單向條件。
  • 窄螢幕直接 display: none：營業時間、篩選器、價格這些「擠不下」的內容，手機使用者一樣需要。換位置、改成可展開，不要刪掉。
  • hover 才出現的必要資訊：觸控和鍵盤使用者看不到。平常就顯示，hover 效果包在 @media (hover: hover) 裡。
  • 固定 height 與固定 px 寬度：文字放大、換行、翻譯變長就被裁掉或撐破。用 min-height、padding、min-width（em），讓盒子跟著內容長。
  • 點擊目標太小、貼太近：padding: 2px 8px 的按鈕在手機上很難按準。主要操作做到 44×44，按鈕之間用 gap 隔開。
  • 忘了 viewport meta：沒有它，手機用 980px 的虛擬寬度排版，你寫的 media query 在手機上全都不會照手機寬度生效（第 1 課）。

小結

  • RWD 是同一份 HTML 依視窗寬度與裝置能力調整版面。media query 是條件區塊，不提高權重，條件成立時照一般層疊規則比，所以寫在要覆蓋的規則後面。
  • mobile-first：基本樣式給最窄的螢幕，再用 (width >= …) 由小到大往上加；desktop-first 的手機版是一層層撤銷、刪剩的，必要資訊（例如營業時間）容易被 display: none 掉。HTML 順序就是手機的閱讀順序。
  • 斷點看內容（行長、元素被拉大或擠扁），不看手機型號，通常 2～3 個就夠。media query 的 em 以瀏覽器預設字級計算，調大字級時斷點跟著移動。
  • 範圍語法 (40em <= width < 64em) 好讀、不會有 767.5px 的縫，已是 Baseline widely available。
  • hover、pointer 問的是主要輸入裝置的能力；hover 效果包在 (hover: hover) 裡，必要的資訊與操作平常就看得到。
  • 點擊目標至少 24×24（AA），主要操作建議 44×44，相鄰按鈕隔 8px 以上。
  • 驗收 320px 寬（1.4.10，等於 1280px 縮放 400%）與文字放大 200%（1.4.4）：不固定 height、不用 px 固定寬度與字級、讓一列可以換行。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：咖啡店的 CSS 第一行是 @layer reset, base, components, utilities;。同事在 HTML 用 <link> 加了日期選擇器套件的 CSS，之後 components 層的 .btn 文字色被套件的 button { color: … } 蓋掉，權重明明比較低，為什麼？

✓ 層疊依序比來源、inline、layer、權重、出現順序，某一步分出高下就停。沒分層的一般宣告勝過所有 layer，權重根本輪不到比。修法是改成 @import url(…) layer(vendor)，並把 vendor 加進第一行、排在 reset 之後。a 錯在出現順序是最後一步，就算套件排在前面載入，它一樣會贏。（第 6 課）

練習 8：結帳表單寫了 .field input { display: block; width: 100%; padding: 12px; border: 1px solid; }，320px 的手機上每個輸入框都比卡片多出 26px。先查什麼？

✓ content-box 下實際寬度是 100% 再加 24px 的 padding 和 2px 的 border，一定比父元素寬。全站在 reset 寫 *, *::before, *::after { box-sizing: border-box; }，width 就包含 padding 與 border。c 錯在 margin 合併只發生在相鄰的垂直 margin，不會讓寬度變大，padding 也不參與合併。（第 7 課）

練習 9：菜單卡片這樣寫，說明的省略號沒出現，整張卡片還被撐出 320px 的畫面。改哪裡？

.menu-item { display: flex; gap: 12px; }
.thumb { width: 96px; flex-shrink: 0; }
.text { flex: 1; }   /* 一般 block，裡面是 .name 和 .desc */
.desc {
  white-space: nowrap;
  overflow: hidden;
  text-overflow: ellipsis;
}

✓ flex 項目的 min-width: auto 會算成 min-content，nowrap 的整行說明就是 .text 的 min-content，它縮不下去，.desc 沒被擠到，省略號就不會出現。min-width: 0 要寫在被撐開的 flex 項目上。a 錯在 .desc 不是 flex 項目，它的 min-width 本來就是 0，被撐寬的是外面那層 .text。（第 8 課）

練習 10：十張菜單卡片用 display: flex; flex-wrap: wrap; gap: 16px 加上 .card { flex: 1 1 240px; } 排列，桌機上最後一列只有 2 張，各比上面的卡片寬一倍。怎麼修？

✓ Flexbox 每一列各自分配剩餘空間，最後一列卡片少，每張分到的就多。卡片格線是二維的，用 Grid：所有列共用同一組欄，最後一列跟上面同寬、右邊留空，也不用寫 media query。a 錯在百分比不扣 gap，4 個 25% 加上 gap 放不下，變成一列 3 張，最後一列那 1 張照樣被拉寬。（第 8、9 課）

練習 11：後台訂單詳細頁是 grid-template-columns: 1fr 1fr，右欄是顧客備註。有人在備註貼了一長串外送平台的網址，右欄就變得比左欄寬，整頁還可以左右滑。為什麼？

✓ 1fr 的下限是 auto，也就是項目的最小內容寬度，跟 flex 項目的 min-width: auto 是同一件事。會放使用者輸入的欄改成 minmax(0, 1fr)，網址再加 overflow-wrap: anywhere。b 錯在 fr 分的是扣掉固定軌道與 gap 後的剩餘空間，跟內容多少無關；欄被撐寬是下限擋住，不是比例變了。（第 9 課）

練習 12：頁首是 position: sticky; top: 0，沒寫 z-index，裡面的購物車下拉選單是 z-index: 9999。下面的商品卡片為了 hover 動畫寫了 will-change: transform，不能拿掉。下拉選單被卡片蓋住，哪個修法有效？

✓ 頁首（sticky）和卡片（will-change）各自建立 stacking context，在根層都是層級 0，DOM 在後面的卡片畫在上面；選單的 9999 只在頁首裡面比。要調的是互相比較的那兩個祖先，所以給頁首 z-index。b 錯在 isolation 只是讓卡片再建一個 context，卡片在根層仍是層級 0、DOM 在後，照樣蓋住選單。（第 10 課）

練習 13：320px 的手機上整頁可以左右滑。同事在包住整頁的 .page 寫了 overflow-x: hidden，橫向捲動不見了，但 sticky 頁首從此不黏。為什麼？

✓ sticky 黏在最近一個有捲動機制的祖先上，即使它根本沒在捲；頁面捲動時 .page 整個跟著走，sticky 就像沒寫。修法是用第 7 課的 Console 片段找出撐破的元素修好；真的要裁切就用 overflow-x: clip，它不建立捲動容器。a 錯在 overflow 不會建立 stacking context，頁首不是被蓋住，是根本沒黏。（第 7、10 課）

練習 14：訂單確認頁在 320px、預設字級時沒問題。客人把瀏覽器字級調到 200% 後，結帳按鈕的字被切掉一半、價格欄被撐破。哪個修法對？

.checkout { height: 40px; overflow: hidden; font-size: 1rem; }
.price { width: 80px; white-space: nowrap; }

✓ 固定 height 和固定 px 寬度不會跟著內容長大，字一放大就被裁掉或撐破。改成 min-height 與 em 的 min-width，盒子跟著內容長，必要時再讓整列 flex-wrap: wrap。a 錯在 px 字級不跟著瀏覽器設定變大，需要大字的客人放大也沒用，這是把問題丟給使用者，不是修好。（第 11 課）
