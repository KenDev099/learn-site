階段 3：現代 CSS 與視覺品質 · 第 15 課

字型與排版：中文字型、子集化、font-display 與版面穩定

豆留咖啡要做秋季改版。設計師交來新的品牌視覺：標題要用一套粗黑的品牌字型。負責的工程師把整套字型檔放上網站、全站套用，在公司的網路上看起來沒有問題。上線隔天，老闆用手機打開首頁：標題和內文空白了好幾秒，字出現之後，整頁又往下跳了一截。打開 DevTools 的 Network 面板一看，首頁多下載了一個 7 MB 的字型檔。

這課就拿這個事故當主線，一步一步修到可以上線：先查清楚 7 MB 從哪裡來，再決定哪些文字根本不需要下載字型、哪些值得下載；值得下載的，把檔案從 MB 減到 KB；接著處理「下載期間畫面顯示什麼」和「換字型時版面跳」這兩個症狀；最後字型都到位了，再把文章頁的內文排得好讀。

這課的路線：
  1. 7 MB 從哪裡來：中文字型為什麼這麼大，為什麼內文交給使用者裝置上的系統字型就好。
  2. 字型堆疊：Mac、Windows、Android 的系統字型名稱都不同，一行 CSS 怎麼讓每台裝置都用到自己的繁中字型。
  3. @font-face 與子集化：標題非用品牌字型不可，怎麼把要下載的檔案從 7 MB 減到 4.4 KB。
  4. font-display 與 preload：字型還在下載時標題顯示什麼（事故裡的「空白好幾秒」），以及怎麼讓它早點開始下載。
  5. 換字型時版面不跳：事故裡的「整頁往下跳」是怎麼來的，用固定行高和度量相同的備援字型消掉它。
  6. 好讀的排版：字型問題修完，文章頁的行高、一行幾個字、標題怎麼換行。
這課會用到：
  • 第 14 課的 <link rel="preload"> 與 CLS：preload 讓瀏覽器提早下載首屏一定用到的資源；CLS 量畫面元素被推動的程度。
  • 第 6 課的繼承：font-family、line-height 寫在父元素上，子元素沒寫就沿用。
  • 第 13 課的 em 與 max-inline-size：em 跟著目前字級縮放，max-inline-size 是文字方向上的最大寬度。

首頁多下載的 7 MB 是從哪裡來的？

要知道字型檔為什麼這麼大，先看它裡面裝了什麼。一個字型檔是一份對照表：每一個字元（character），例如「咖」這個字、字母 A、數字 1，都對應到一個字形（glyph），也就是把這個字畫出來的外框線條。瀏覽器要畫「咖」時，到字型檔裡找「咖」的字形，照著線條畫到螢幕上。字型檔收的字越多，裡面的線條資料就越多，檔案就越大。

英文字型只要大小寫字母、數字、標點，幾百個字元就夠了，檔案通常幾十 KB。中文不一樣：日常用字就有好幾千個，一套完整的繁中字型要收一萬到兩萬多個字。拿這台電腦上的 Noto Sans TC 實際量：

檔案字元數大小
Noto Sans TC Regular（TTF，一個字重）20,7457.1 MB
同一個檔案轉成 WOFF220,7452.9 MB
只留標題用到的 19 個漢字＋空白（這課練習用的 BrewSans）204.4 KB

事故裡的 7 MB 跟第一列是同一個量級：設計師給的完整字型檔原封不動放上網站（表格量的是一般字重，粗黑字重的檔案大小相近）。第二列是同一份字型轉成網頁專用的壓縮格式 WOFF2（第三節會講），小了一半多，但還有 2.9 MB：壓縮能把每個字形的資料壓小，卻減不掉兩萬個字形本身。第三列只留標題會用到的 20 個字元，檔案剩 4.4 KB，差了一千多倍。這三列已經指出這課的方向：要讓中文字型變小，關鍵是少收字，不是壓得更用力。

而且這還只是一個字重（font weight）。字重是字的粗細，一般內文是 400、粗體是 700、最粗的 900。字型檔通常一個字重一個檔案，標題用粗體、內文用一般，就是兩個檔案、兩倍的下載量。對照第 14 課，一張拿鐵照片 100 KB 就嫌大，一個 3 MB 的字型檔會直接拖慢首屏。

那內文的幾千個字怎麼辦？不用下載。使用者的電腦和手機本來就裝了品質很好的中文字型，作業系統自己的介面就是用它們顯示的，這叫做系統字型（system font）。網頁只要在 CSS 裡寫出它們的名字，瀏覽器就直接拿來用，一個位元組都不用下載：

平台內建的繁中字型（font-family 寫法）
macOS、iOS"PingFang TC"（蘋方-繁）
Windows"Microsoft JhengHei"（微軟正黑體）
Android、LinuxNoto Sans CJK（思源黑體），通常靠 sans-serif 加上 lang 選到；使用者自己裝的可能叫 "Noto Sans TC"

所以修這個事故的第一個決定是：內文一律用系統字型。內文的字數多、內容常常變，正是網頁字型最貴的地方；系統字型每個字都有、不用下載、使用者也看習慣了。只有品牌識別需要的地方（logo、大標題）才考慮網頁字型，而且只下載那幾十個字。這兩句話就是這課的最小答案，後面幾節是在把它做對。

不過上面的表也帶出一個問題：三個平台的系統字型名字都不一樣，CSS 只有一個 font-family，要怎麼寫才能讓 Mac 用蘋方、Windows 用微軟正黑體？

三個平台的字型名稱都不同，內文的 font-family 要怎麼寫？

答案是不只寫一個名字，而是寫一串。字型堆疊（font stack）就是 font-family 裡用逗號分隔的候選清單。瀏覽器對每一個字從第一個候選開始找：這個字型在使用者的裝置上存在、而且裡面有這個字，就用它畫；沒有就看下一個。

body {
  font-family: "PingFang TC", "Noto Sans TC", "Microsoft JhengHei", sans-serif;
}

照這個規則走一次：在 Mac 上，第一個候選蘋方就找到了，整頁都用蘋方。在 Windows 上，前兩個都不存在，瀏覽器跳過它們，用到第三個微軟正黑體。同一行 CSS，每台裝置各自挑到自己有的字型。font-family 會繼承（第 6 課），所以寫在 body 上，整頁沒另外寫的元素都套用這串。

清單最後的 sans-serif 和前面幾個不一樣。它是通用字族（generic family），不是某一套字型的名字，而是一個類別：意思是「無襯線字型，由瀏覽器從系統裡挑一個」。serif（襯線，中文是明體類）、system-ui 也是通用字族。堆疊最後一定要放一個通用字族：前面的候選全部找不到時（例如 Linux 上），瀏覽器還有東西可挑；沒放的話，會掉到瀏覽器預設的字型，中文常常是明體，整頁的風格就跑掉了。

寫法上有一個容易錯的地方：字型名稱有空白要加引號，例如 "PingFang TC"；通用字族是 CSS 的關鍵字，不能加引號。寫成 "sans-serif"，瀏覽器會把它當成一套名字剛好叫 sans-serif 的字型去找，找不到就跳過，等於堆疊最後沒有通用字族。

「一個字一個字找」這個規則還帶出一個常用技巧：英文和數字想用另一套字型時，把英文字型放在前面。英文字型裡沒有中文字，遇到中文時瀏覽器在它那裡找不到，自動往後找到繁中字型；英文和數字則在第一站就找到了：

body {
  /* 英文、數字用系統介面字型（Mac 的 San Francisco、Windows 的 Segoe UI），中文往後找 */
  font-family: -apple-system, "Segoe UI", "PingFang TC", "Noto Sans TC", "Microsoft JhengHei", sans-serif;
}

堆疊寫對了，字形還是可能錯：lang 與 system-ui

堆疊決定的是「用哪一套字型」，但有兩種情況，選到的字型對了，畫出來的字形還是不對。

第一種跟 lang 有關。同一個漢字，繁中、簡中、日文的標準寫法有細微差別，例如「骨」「次」的筆畫。Noto Sans CJK 這類字型一個檔案裡收了多種寫法，瀏覽器依元素的 lang（第 1 課）決定用哪一種。<html lang="zh-Hant"> 寫對，通用字族才會挑繁中字形；寫成 lang="en" 或漏掉，Android 上可能出現日文或簡中寫法的字。這種錯在 Mac 上開發時完全看不出來。

第二種跟 system-ui 有關。system-ui 是「作業系統介面用的字型」，看起來是最省事的寫法，一個詞就跟著系統走。問題是它依作業系統的語系挑字型，不看網頁的語言：在簡體中文版的 Windows 上，它可能挑到微軟雅黑（簡中字型），繁體字就用簡中的字形和字距顯示。繁中網站要把繁中字型寫在 system-ui 前面，或乾脆不用它。

這兩種錯都不會讓頁面壞掉，只是字「怪怪的」，所以要知道怎麼在 DevTools 查實際用了哪個字型：

在 DevTools 確認實際用了哪個字型：Elements 面板選取元素 → Computed 分頁最下面的 Rendered Fonts，會列出每個字型實際畫了幾個字（glyph）。font-family 的計算值只是候選清單，真正用到哪個要看這裡。
💡 實務上：你看到的字型，不等於使用者看到的
前端工程師多半用 Mac 開發，整天看到的是蘋方；但咖啡店的店員可能用 Windows 的收銀電腦、客人用 Android 手機，看到的是另一套字型，字寬和行高都不同。常見的客服回報是「按鈕文字在我電腦上換行了」「價格被截掉」，原因就是開發時只在一個平台看過。資深工程師上線前會用 Windows、Android 各看一次重要頁面（實機、虛擬機或雲端測試服務都可以），版面也不寫死「剛好放得下這幾個字」的寬度。設計師的 Figma 若用了使用者電腦沒有的字型，要先講好實際上線用哪個堆疊。

內文交給系統字型堆疊之後，事故裡的 7 MB 已經不必下載給內文用了。剩下標題：設計師要的品牌字型，使用者的裝置上沒有，非下載不可。下一步是讓這個下載盡量小。

標題非用品牌字型不可：怎麼把下載從 7 MB 減到 4.4 KB？

使用者裝置上沒有的字型，要由網站提供檔案讓瀏覽器下載，這叫做網頁字型（web font）。網頁字型用 @font-face 宣告：告訴瀏覽器「有一套字型叫這個名字，檔案在這裡」，之後 font-family 就能用這個名字引用它，就像引用系統字型一樣：

@font-face {
  font-family: "BrewSans";                          /* 自己取的名字，font-family 用這個名字引用 */
  src: url("/fonts/brewsans.woff2") format("woff2");
  font-weight: 900;                                 /* 這個檔案是哪個字重 */
  font-display: swap;                               /* 下載期間怎麼顯示，下一節 */
}

h1, h2 {
  font-family: BrewSans, "PingFang TC", "Noto Sans TC", "Microsoft JhengHei", sans-serif;
}

標題的堆疊是品牌字型放第一個，後面接上一節那串系統字型。BrewSans 裡找不到的字，或 BrewSans 還沒下載完的時候，瀏覽器就往後用系統字型，標題不會變成方框或空白。

這段宣告裡有三件事要講清楚。

第一是檔案格式。WOFF2 是專門給網頁用的字型格式，內建 Brotli 壓縮，同一份字型比 TTF／OTF 小很多（上一節的表：7.1 MB → 2.9 MB）。所有現代瀏覽器都支援，不需要再準備 TTF、WOFF、EOT 當備援。設計師給的通常是 TTF 或 OTF，放上網站前一律轉成 WOFF2。

第二是 font-weight。在 @font-face 裡的 font-weight 是描述子（descriptor）：它不是在設定字要多粗，而是告訴瀏覽器「這個檔案是哪個字重」。沒寫時當成 400（一般）。這時 h1 要粗體（700），瀏覽器在 BrewSans 裡找不到粗的檔案，就用演算法把字「描粗」（synthetic bold）；BrewSans 本來就是最粗的字重，再描一次會糊成一團。檔案是 900，就寫 font-weight: 900。

第三是下載時機。寫了 @font-face 不會馬上下載。瀏覽器排版時發現某個元素真的要用這個字型、而且頁面上有它涵蓋的字，才開始下載。這一點下一節講 preload 時會再用到。

格式換成 WOFF2 只把 7.1 MB 壓到 2.9 MB。要再往下減，得從「少收字」下手。

子集化：只留用得到的字

子集化（subsetting）是把字型檔裡用不到的字元刪掉，只留需要的部分。豆留首頁的標題只有那幾十個字，就只留那幾十個字，上一節表格的第三列就是這樣做出來的。常用的工具是 fontTools 的 pyftsubset（Python）或 glyphhanger（Node.js），在建置時執行，不是在瀏覽器裡：

# 只保留 titles.txt 裡出現的字，輸出 WOFF2
pyftsubset NotoSansTC-Black.ttf --text-file=titles.txt --flavor=woff2 --output-file=brewsans.woff2

代價很明確：之後標題出現子集裡沒有的字，例如新增一道「肉桂捲」，「肉」「桂」「捲」不在字型裡，會用堆疊裡下一個字型顯示，一個標題混兩種字型。所以子集化適合文字固定的地方（logo、導覽、固定的區塊標題），由建置流程從原始資料收集用到的字；使用者輸入、CMS 會改的內容，用系統字型。

改字型檔之前先看授權。這課的 BrewSans 是從 Noto Sans TC 修改的：Noto 用 SIL Open Font License 1.1（OFL），允許子集化、改名、自行託管，修改後的版本也要用 OFL。很多商用字型的授權禁止修改或只允許特定網域，子集化等於修改，要先確認。

unicode-range：告訴瀏覽器這個檔案有哪些字

子集化把檔案變小了，但瀏覽器並不知道這個檔案只有 20 個字。@font-face 沒特別說明時，瀏覽器會以為什麼字都能在這個檔案找到。unicode-range 就是用來說明這件事的描述子：它宣告這個檔案涵蓋哪些字元，用的是 Unicode 碼位（每個字元在 Unicode 裡的編號，例如「咖」是 U+5496）。沒寫時預設是全部字元（U+0-10FFFF）。

@font-face {
  font-family: "BrewSans";
  src: url("/fonts/brewsans.woff2") format("woff2");
  unicode-range: U+20, U+5496, U+5561, U+8C46, U+7559;   /* 空白、咖、啡、豆、留 */
}

寫了 unicode-range，瀏覽器只在頁面上真的出現範圍內的字時才下載這個檔案。範圍要跟子集內容一致：寫得比子集大，頁面出現子集沒有的字時，瀏覽器也會去下載這個檔案，下載完發現裡面沒有那個字形，才往堆疊後面找，等於白下載一次（畫面不會錯，字最後還是由後面的字型畫出來）。寫得比子集小，子集裡明明有的字反而不會用到品牌字型。碼位不用自己查，子集化工具可以輸出子集涵蓋的範圍，貼上即可。

unicode-range 最強大的用法是切片。子集化適合固定的文字，但如果內容會變、又一定要統一字型，就不能只留幾十個字。切片的做法是：把一整套字型切成很多個小檔案，每個檔案一段 unicode-range，全部用同一個 font-family 名稱。頁面用到哪些字，瀏覽器就只下載包含那些字的切片。Google Fonts 對中文就是這樣做的，向它要 Noto Sans TC 一個字重，回傳的 CSS 有 108 個 @font-face：

/* fonts.googleapis.com/css2?family=Noto+Sans+TC 回傳的 CSS（節錄） */
@font-face {
  font-family: 'Noto Sans TC';
  font-weight: 400;
  font-display: swap;
  src: url(https://fonts.gstatic.com/s/notosanstc/v40/….0.woff2) format('woff2');
  unicode-range: U+3401, U+3441, U+34fe, …;          /* 第 0 片：一百多個罕用字 */
}
/* …中間 100 多片，常用字依使用頻率分組… */
@font-face {
  font-family: 'Noto Sans TC';
  font-weight: 400;
  font-display: swap;
  src: url(https://fonts.gstatic.com/s/notosanstc/v40/….woff2) format('woff2');
  unicode-range: U+0000-00FF, U+0131, U+2000-206F, …;  /* 英數與標點 */
}

一頁菜單通常只會下載其中十幾片。自己託管字型時（把字型檔放在自己的網站），要自己做這件事，最常見的錯誤是只下載一個完整的 .ttf 放上去，就失去了切片，又回到事故的狀況。

到這裡有三種做法：系統字型、自己子集化、切片。要用哪一種，資深的判斷是看值不值得那些位元組與風險：

情境建議
內文、表單、使用者產生的內容系統字型堆疊。快、每個字都有、使用者習慣
logo、固定的大標題自己子集化的 WOFF2（幾 KB），或乾脆把 logo 做成 SVG
內容會變、但一定要統一字型（例如品牌刊物）切片的網頁字型（Google Fonts 或自己切），接受多幾百 KB 與換字型的位移，用下面兩節的方法降低影響

豆留首頁的標題是固定的，走第二列：子集化成 4.4 KB 的 BrewSans。

💡 實務上：Google Fonts 方便，但先想清楚使用者在哪裡
專案初期最快的做法是貼一行 Google Fonts 的 <link>，字型切片和 unicode-range 都幫你做好。要考量的是：字型從 Google 的網域下載，等於每個訪客都對第三方發出請求，重視隱私或有法規要求的客戶（金融、醫療、歐洲使用者）可能不接受；中國大陸的使用者連不到 Google 的服務，字型會一直載不到。這些情況就改成自行託管，用工具把字型切片後放在自己的網站（第 21 課會從效能角度再談第三方資源）。資深工程師接到「換品牌字型」的需求，會先問：目標使用者在哪裡、授權允不允許網頁使用與自行託管。

4.4 KB 已經很小，但它還是要經過網路下載。網路慢的時候，下載完成前的那段時間，標題要顯示什麼？事故裡「標題空白好幾秒」就發生在這段時間。

字型還在下載時，標題要顯示什麼？

網頁字型還沒下載完時，瀏覽器面對的是一個兩難：要畫標題，可是畫標題用的字型還沒到。它有兩種選擇：

  • FOIT（Flash of Invisible Text）：先把文字畫成透明的，等字型到了才顯示。字型 3 秒才到，標題就空白 3 秒。事故裡老闆看到的就是這個。
  • FOUT（Flash of Unstyled Text）：先用堆疊裡的備援字型顯示，字型到了再換掉。文字立刻看得到，代價是換的那一下字形改變，尺寸不同時版面會跳。

兩個都有代價：FOIT 讓人看不到字，FOUT 讓版面跳。哪一個比較能接受，要看是哪一段文字，所以 CSS 讓你逐個字型決定。font-display 是 @font-face 的描述子，就是用來做這個決定的。它把下載期間分成三段：阻擋期（block period）文字看不見；交換期（swap period）先用備援字型、字型到了就換；之後是失敗期，字型就算到了也不換，一直用備援字型。font-display 的四個值，差別就在這三段各多長：

把圖整理成表，最後一欄是各自適合的地方：

值阻擋期交換期用在哪裡
block短（建議 3 秒）無限幾乎不用。只有「用錯字型會看不懂」的情況，例如舊式的圖示字型
swap極短（建議 ≤ 100 毫秒）無限品牌標題、logo 文字：一定要換成品牌字型，但等待期間先顯示文字

auto（預設）由瀏覽器決定，多數瀏覽器跟 block 類似不要依賴它，明確寫出來

回到事故：原本的 @font-face 沒寫 font-display，等於 auto，多數瀏覽器的行為像 block，所以字型下載的那幾秒標題是空白的。BrewSans 是品牌標題，一定要換成品牌字型，但等待時應該先看到字，所以用 swap。font-display 各瀏覽器都支援，版本資料見課末。

這個選擇不只影響觀感，也直接反映在第 14 課提過、第 20 課會細講的兩個指標上。LCP（最大內容繪製）量的是首屏最大的元素多久畫出來，而首屏最大的元素常常就是大標題。block 讓標題要等字型到了才畫出來，LCP 跟著延後；swap、optional 讓備援字型先畫出來，LCP 不必等字型。CLS（累計版面位移）量的是畫面元素被推動的程度。swap 換字型時，字變寬、行數改變，下面的內容被推動，算進 CLS；optional 不會中途換，沒有位移。用 swap 的位移，下一節會把它降到接近 0。

讓字型早點開始下載：preload 只給首屏那一個

選了 swap，標題不再空白，但備援字型顯示的時間越長，使用者越容易看到換字的那一下。能不能讓字型早點到？

先看字型平常是什麼時候開始下載的。上面講過，寫了 @font-face 不會馬上下載：瀏覽器要先下載 HTML、發現 CSS、下載並解析完 CSS、開始排版，排版時發現標題要用 BrewSans，才開始下載字型檔。字型排在這一串的最後面，已經晚了一截。第 14 課的 <link rel="preload"> 可以讓瀏覽器在讀到 HTML 時就開始下載，不用等排版：

<link rel="preload" href="/fonts/brewsans.woff2" as="font" type="font/woff2" crossorigin>

這行有一個一定會被問到的屬性：crossorigin 一定要加，即使字型在同一個網域。原因要從 CORS 講起。

CORS（Cross-Origin Resource Sharing，跨來源資源共用）是瀏覽器的一套規則：網頁向別的網域要資源時，瀏覽器先確認對方的回應有沒有明確允許這個網頁使用。瀏覽器發出每個請求時，都會標記它屬於哪種「模式」：用 CORS 規則檢查的叫 CORS 請求；不檢查、拿到的內容也不讓網頁讀取的叫 no-cors 請求。CORS 請求還分要不要帶憑證，crossorigin="anonymous"（匿名模式）表示不帶跨站的 cookie。

CSS Fonts 規範規定，CSS 載入字型時一律發匿名模式的 CORS 請求，不管是不是同一個網域。preload 沒寫 crossorigin 時，發的是 no-cors 請求。瀏覽器只會把模式相同的請求當成同一份資源重用，所以等到 CSS 真的要用字型時，它認不得 preload 下載的那一份，再下載一次。寫上 crossorigin（等同 crossorigin="anonymous"）之後，preload 也改發匿名模式的 CORS 請求，跟 CSS 的請求對上，下載的那一份才會被用到。少了它，Network 面板會看到同一個 .woff2 出現兩次，Console 也會警告 preload 的資源沒有被使用：preload 不但沒加速，還多花了一次下載。

另一個原則是只 preload 首屏一定會用到的那一個檔案。preload 的請求優先順序很高，會跟 LCP 圖片、CSS 搶頻寬；而且 preload 不看 unicode-range，不管頁面有沒有用到都會下載，切片的字型全部 preload，等於把好幾 MB 塞進首屏，又回到事故的狀況。豆留首頁只 preload BrewSans 這一個 4.4 KB 的檔案。

反過來，用 optional 時 preload 特別有用：optional 只給字型極短的時間，字型越早開始下載，越可能趕上那 100 毫秒，第一次瀏覽就用得上。

💡 實務上：設計師要品牌字型時，先談範圍再寫 CSS
「全站換成品牌字型」常常是一句話的需求，背後卻是幾 MB 的下載和版面位移。資深工程師會把這課的取捨攤開來談：哪些地方一定要用品牌字型（通常是 logo 與首頁大標題）、那些文字是不是固定的、能不能接受第一次瀏覽先用系統字型（optional）。談完常見的結論是：內文系統字型、標題子集化 + swap + preload 一個檔案。上線後用 DevTools 確認同一個 .woff2 沒有下載兩次、首屏沒有多出大檔案，這是 code review 時很容易漏看的地方。

到這裡，事故的前兩個症狀解決了：下載量從 7 MB 變成 4.4 KB，下載期間標題先用備援字型顯示。剩下最後一個：BrewSans 到了、換上去的那一下，下面的內容還是會被推動。

換上品牌字型時，下面的內容為什麼會跳？

用 swap 時，同一段標題會被排兩次：先用備援字型排一次，字型到了再用 BrewSans 排一次。如果兩次排出來的每一行高度不一樣，或每個字的寬度不一樣（寬度不同會讓換行位置改變、行數改變），標題的總高度就變了，下面的內容跟著上下移動，這就是版面位移。所以要讓換字型時版面不跳，就是讓兩次排版的行高和字寬一樣。先處理行高，再處理字的度量。

第一步：無單位的 line-height

行高為什麼會跟著字型變？因為 line-height 沒有設定時是 normal，而 normal 的行高由字型檔裡的度量（metrics）決定。度量是字型設計師寫在字型檔裡的一組尺寸數字，記錄這套字預留多少空間：

圖左邊的方框是一個字的格子，叫 em 方框，字型檔把它切成 1000（或 2048）個單位來記錄尺寸。中間那條線是基線（baseline），字「站」在這條線上。ascent 是基線以上預留的高度，descent 是基線以下預留的高度，line gap 是行與行之間額外的空隙。line-height: normal 的行高，就是這三個數字加起來換算成字級的倍數。

BrewSans 的 ascent＋descent 剛好是 1000，行高是字級的 1.0 倍；蘋方大約 1.4 倍、微軟正黑體又不同。用 normal 時，換字型就是換行高：一個兩行的標題先用蘋方排，字型到了換成 BrewSans，可能突然矮十幾 px，下面整頁往上跳。

解法是不讓字型決定行高。寫成無單位的數字，行高就是「字級 × 這個數字」，跟用哪個字型無關：

h1 {
  font-size: 2.5rem;
  line-height: 1.3;   /* 40px × 1.3 = 52px，換字型也是 52px */
}

同樣是固定行高，為什麼不寫 52px 或 1.3em？兩種寫法各有一個問題。

px 不跟著字級變：使用者把瀏覽器的預設字級調大，標題變成 60px，行高還是 52px，比字還矮，上下兩行疊在一起。

em 和百分比的問題在繼承：line-height: 1.3em 或 130% 會在寫它的那個元素上就算成 px，子元素繼承到的是那個算好的 px 值。父元素 16px 時算出 20.8px，子元素就算是 40px 的大字，也只拿到 20.8px 的行高。無單位的數字繼承的是「1.3 這個倍數」，每個元素用自己的字級重算。

第二步：讓備援字型的度量跟品牌字型一樣

行高固定了，每一行的高度不再隨字型改變。但還有兩件事會變：字在行裡的上下位置（ascent、descent 不同，字會在行裡偏上或偏下），以及英文字型的字寬（字寬不同，換行位置就變）。要讓這些也不變，做法是做一個「長得像品牌字型」的備援字型：用 @font-face 包一個本機已經有的系統字型，再用描述子改寫它的度量，讓它的數字跟 BrewSans 一樣。

描述子改什麼怎麼算
ascent-override基線以上的高度品牌字型的 ascender ÷ unitsPerEm
descent-override基線以下的高度品牌字型的 descender（取絕對值）÷ unitsPerEm
line-gap-override行與行之間額外的空隙品牌字型的 lineGap ÷ unitsPerEm
size-adjust整個字型縮放（字寬、字高一起）品牌字型的平均字寬 ÷ 備援字型的平均字寬

套到 BrewSans：它的 ascent 是 880、descent 是 120、line gap 是 0，unitsPerEm 是 1000，所以備援字型寫成：

@font-face {
  font-family: "BrewSans Fallback";
  src: local("PingFang TC Regular"), local("PingFangTC-Regular"),
       local("Microsoft JhengHei");
  ascent-override: 88%;     /* 880 ÷ 1000 */
  descent-override: 12%;    /* 120 ÷ 1000 */
  line-gap-override: 0%;
  size-adjust: 100%;        /* 漢字都是 1em 寬，不用縮放 */
}

h1 {
  font-family: BrewSans, "BrewSans Fallback", "PingFang TC", "Noto Sans TC", "Microsoft JhengHei", sans-serif;
}

這段有三個地方要看懂。

local() 從使用者電腦裡已經安裝的字型載入，不下載任何東西。括號裡要寫字型的完整名稱（full name）或 PostScript 名稱，不是 font-family 的名稱：Chrome 實測 local("PingFang TC") 找不到，local("PingFang TC Regular")、local("PingFangTC-Regular") 才找得到。可以列好幾個，第一個找到的就用。

堆疊的順序是品牌字型 → 調整過的備援字型 → 一般的系統字型。BrewSans 還沒到時，瀏覽器用第二個「BrewSans Fallback」排版，它的度量跟 BrewSans 一樣；BrewSans 到了換上去，每個字的位置不變，下面的內容就不會動。

size-adjust 在中文字型通常是 100%，因為中文字幾乎都是 1em 寬，兩套字型的字寬本來就一樣。英文網頁字型的字寬差很多，一定要算 size-adjust，再把 ascent／descent 的百分比除以它。

這些數字不用手算。Next.js 的 next/font、Nuxt 的 @nuxtjs/fontaine、unjs 的 fontaine 會讀字型檔，自動產生這組備援 @font-face；要自己算時，用 fontTools 讀字型的 hhea、OS/2 表。

支援度：size-adjust 各主流瀏覽器都支援；ascent-override、descent-override、line-gap-override Safari 不支援（版本資料見課末）。不支援的瀏覽器會忽略這幾行，備援字型照原本的度量排，就是沒有優化，不會壞。所以第一步的無單位 line-height 一定要做：它在所有瀏覽器都有效。

改完怎麼確認有效：DevTools 的 Network 面板把網路調成 Slow 4G，重新整理，看標題換字型時下面的內容有沒有動；Performance 面板錄製載入過程，Layout Shift 的軌道上不該出現跟字型有關的位移（第 20 課會細講 CLS 的量測）。

到這裡，事故的三個症狀都修好了：下載從 7 MB 變成 4.4 KB，下載期間標題先顯示，換字型時版面不動。字型的問題處理完，設計師接著反映另一件事：品牌故事那一頁在大螢幕上讀起來很累。這已經不是「用哪個字型」的問題，而是字怎麼排。

字型到位之後，文章頁要怎麼排才好讀？

品牌故事頁讀起來累，原因通常不在字型本身，而在三件事：行與行太擠、一行太長、段落黏在一起。一件一件看。

行高：上一節為了不跳版把行高寫成無單位數字，這裡要決定數字是多少。中文字是方塊字，每個字都填滿整格，沒有英文小寫字母上下的留白，所以行距要比英文寬，眼睛才分得出上下行。英文內文常用 1.4～1.5，中文內文用 1.7～1.8；標題字大、行數少，用 1.2～1.4。寫在 body 上用無單位數字，讓全頁繼承，標題再個別覆寫。

行長：一行太長，眼睛讀完一行要回到下一行開頭時容易找錯行；太短則一直換行，閱讀被切得很碎。中文內文一行約 30～40 個字。中文一個字約 1em 寬，所以用 em 寫上限就等於限制字數：

article {
  max-inline-size: 36em;   /* 一行最多約 36 個字；直排時限制的是高度（第 13 課） */
  margin-inline: auto;     /* 置中 */
}
body {
  padding-inline: 1rem;    /* 窄螢幕時不貼邊 */
  line-height: 1.75;
}

為什麼用 em 而不用 px？用 px（例如 max-width: 600px）時，使用者把字級放大到 24px，600px 只放得下 25 個字；用 em 寫的上限會跟著字級變大，一行永遠約 36 個字。這跟上一節行高不用 px 是同一個道理：跟文字有關的尺寸，要跟著字級走。

段落間距：瀏覽器預設 <p> 上下各有 1em 的 margin（相鄰時合併成 1em，第 7 課）。中文網頁常見的錯誤是 reset 時把它歸零，段落黏在一起，讀者分不出一段在哪裡結束。不要歸零，或歸零後自己補回 1em。

標題換行：text-wrap: balance

內文排好了，還剩標題。品牌故事頁的標題很長，兩行的標題常常變成第一行很長、第二行只剩一兩個字，看起來像排版出錯。text-wrap: balance 讓瀏覽器把字平均分配到各行：

h1, h2 {
  text-wrap: balance;
}

不支援的舊瀏覽器會忽略這行，照一般方式換行，所以加上去沒有風險，是安全的漸進增強。平衡要多算幾次才能找到最平均的分法，所以瀏覽器限制了行數，超過就照一般換行；它只適合標題、圖說這類短文字，不要套在內文上。各瀏覽器的行數上限、給內文用的 text-wrap: pretty，見課末。

💡 實務上：文章頁和後台，排版目標不一樣
這節的 1.75 行高、36em 行長是給「要一直往下讀」的頁面：部落格、品牌故事、商品說明。咖啡店後台的訂單列表、報表是另一回事：使用者要一眼掃過很多筆資料，行高 1.4～1.5 比較緊湊，表格也不該被行長上限擠窄，金額欄加上 font-variant-numeric: tabular-nums（每個數字等寬）讓位數對齊。實務上的做法是全站定好內文的預設（字型堆疊、行高），文章區塊再加上行長限制，而不是每個頁面各寫一套。

練習

這三題的預覽都只能載入 15-brewsans.woff2：它是從 Noto Sans TC（SIL OFL 1.1）取最粗的字重、子集化成 20 個字元（空白和「豆留咖啡秋季菜單本週推薦門市資訊限定上市」）、改名 BrewSans 的 4.4 KB 字型。預覽的本機字型依你的作業系統而定，測試只檢查不受作業系統影響的部分。

練習 1：幫菜單頁設定字型。內文用系統字型堆疊，依序 "PingFang TC" → "Noto Sans TC" → "Microsoft JhengHei" → sans-serif（要讓英文用系統介面字型，可以在最前面加 -apple-system, "Segoe UI"；system-ui 不能放在繁中字型前面）。只有 h1、h2 用品牌字型：寫一個 @font-face，font-family 叫 BrewSans，檔案是 15-brewsans.woff2（字重 900），下載期間先用備援字型顯示，並用 unicode-range 標示子集涵蓋的字元。子集化工具輸出的範圍是：U+20, U+4E0A, U+5496, U+5561, U+55AE, U+5B63, U+5B9A, U+5E02, U+63A8, U+672C, U+7559, U+79CB, U+83DC, U+85A6, U+8A0A, U+8C46, U+8CC7, U+9031, U+9580, U+9650。標題的堆疊在 BrewSans 後面接同一串系統字型。內文（p、li）不能用 BrewSans。

練習 2：標題用 swap，BrewSans 到了會換掉備援字型。讓這次切換不推動版面：BrewSans 的度量寫在 CSS 開頭的註解裡。(1) 新增 @font-face「BrewSans Fallback」，src 只用 local() 列出本機的繁中字型（蘋方寫完整名稱 "PingFang TC Regular" 或 PostScript 名稱 "PingFangTC-Regular"；也可以列 "Noto Sans TC Regular"、"Microsoft JhengHei"），用 ascent-override、descent-override、line-gap-override、size-adjust 對齊 BrewSans 的度量。(2) h1 的 font-family 依序是 BrewSans、BrewSans Fallback、系統字型堆疊。(3) h1 用無單位的 line-height（1.1～1.5）。測試會讓 BrewSans 載入成功一次、載入失敗一次，比較兩次的標題高度。

練習 3：部落格文章在 1280px 寬時一行一百多個字、行距太擠、段落黏在一起，手機上文字貼著螢幕邊緣。改 CSS：內文一行最多約 36 個字（用 em 寫行長上限，下限別低於 28 個字）、行高 1.7～1.8 且用無單位數字、段落之間隔 1em、h2 用 text-wrap: balance；320px 寬時段落左右離畫面邊緣至少 16px，而且不能橫向捲動。

練習 4：中文網頁字型為什麼特別需要子集化或 unicode-range？

✓ b：一套繁中字型收兩萬個字左右，WOFF2 壓縮後一個字重仍有約 3 MB；一頁只用到幾百個字，子集化或 unicode-range 切片讓下載量從 MB 降到 KB。a 錯：WOFF2 就是壓縮過的格式，壓縮後仍然很大。c 錯：瀏覽器可以用大字型檔，只是慢。d 錯：沒有這種規則，影響的是載入速度。

練習 5：內文用 font-display: optional 的特性是？

✓ b：optional 的阻擋期極短、沒有交換期，字型沒趕上第一次繪製就不用了，通常要等下一頁（字型已在快取）才看得到。a 是 block 的行為（而且 block 也只等 3 秒左右）。c 錯：swap 會在字型到了之後換掉，可能造成位移；optional 不會。d 錯：它跟網路連線狀態無關，只看字型來不來得及。

練習 6：<link rel="preload" href="/fonts/brewsans.woff2" as="font" type="font/woff2"> 少了 crossorigin，字型又放在同一個網域，會怎樣？

✓ a：CSS Fonts 規範要求字型用匿名模式的 CORS 請求，即使同網域也一樣。preload 要用相同的模式才能被重用，少了 crossorigin 就白白多下載一次，Network 面板會看到兩個同樣的 .woff2。b 錯：這正是「同網域也要加」的例外。c 錯：第二次下載的字型照樣會用。d 錯：as="font" 決定了請求類型。

常見錯誤

  • 整套中文字型放上網站：一個字重就好幾 MB，手機首屏要等很久。內文用系統字型；品牌字型只子集化需要的字，或用切片。
  • 用 font-display: block 或不寫（auto）：網路慢時文字最多消失 3 秒，標題是 LCP 元素時 LCP 跟著延後。標題用 swap，內文用 optional。
  • 只放 .ttf／.otf：沒有壓縮。一律轉成 WOFF2。
  • @font-face 沒寫 font-weight：瀏覽器把檔案當成 400，粗體標題會被再描粗一次而糊掉。檔案是哪個字重就寫哪個。
  • 堆疊最後沒有通用字族，或把 "sans-serif" 加上引號：前面都找不到時掉到預設的明體。最後寫不加引號的 sans-serif。
  • system-ui 放在繁中字型前面：簡中系統上會用簡中字型顯示繁體字。繁中字型寫在前面。
  • local() 寫 font-family 名稱：local("PingFang TC") 找不到字型。寫完整名稱或 PostScript 名稱。
  • preload 太多字型，或忘了 crossorigin：搶走 LCP 圖片的頻寬，或同一個檔案下載兩次。只 preload 首屏一定用到的一個檔案，並加上 crossorigin。
  • 行高用 px 或 em：放大字級時行與行重疊，或子元素繼承到太小的行高。用無單位數字。
  • 行長用 px 限制：放大字級後一行字數變少。用 em 寫 max-inline-size。

補充與查表

text-wrap 的其他細節

  • 平衡換行的行數上限：Chromium 只處理 6 行以內、Firefox 10 行以內的區塊，超過就照一般換行。
  • text-wrap: pretty 給內文用，主要避免最後一行只剩一個字（孤字）。它還不是 Baseline，不支援的瀏覽器照一般換行，可以加，但不要依賴。
  • text-wrap 是 text-wrap-mode 與 text-wrap-style 的簡寫，在 Computed 面板看到的是 text-wrap-style: balance。

中英混排的空白

「點一杯 Latte 加 1 份濃縮」這種中英數混排，中文和英文、數字之間通常留一點空隙比較好讀。過去只能在內容裡手打半形空白；CSS 的 text-autospace 可以讓瀏覽器自動加間距。主要瀏覽器 2025 年 11 月起都認得這個屬性，但 ideograph-alpha 這類細分的值 Chrome 還不支援，web-features 3.44.0 把整個功能標為還不是 Baseline，各瀏覽器的效果不一致。實務上團隊定一個規則（例如內容一律手打空白），比各自處理一致。

版本備註

  • font-display 是 Baseline widely available（web-features 3.44.0，2022-07-15 起），可以放心用。font-display 各值的秒數來自 CSS Fonts Module Level 4 規範的建議，瀏覽器可以略有不同。
  • size-adjust 是 Baseline widely available（2026-03-18 起）；ascent-override、descent-override、line-gap-override 還不是 Baseline，Safari 不支援（web-features 3.44.0）。
  • text-wrap: balance 是 Baseline newly available（2024-05-13 起）；text-wrap: pretty 還不是 Baseline（web-features 3.44.0）。

小結

  • 7 MB 的來源是字數：繁中字型收兩萬個字左右，WOFF2 壓縮後一個字重仍有約 3 MB。要變小靠少收字，不是壓得更用力。
  • 內文用系統字型堆疊（蘋方 → Noto Sans TC → 微軟正黑體 → 不加引號的 sans-serif），瀏覽器一個字一個字往後找；lang 寫對，system-ui 不放在繁中字型前面。
  • 標題的品牌字型用 @font-face 宣告、一律 WOFF2、寫對 font-weight。固定文字子集化只留用得到的字；unicode-range 標示檔案涵蓋的字，切片讓瀏覽器只下載頁面用到的部分。子集化前先確認授權。
  • font-display 決定下載期間的顯示：標題 swap、內文 optional、幾乎不用 block。preload 只給首屏關鍵的一個檔案，而且要加 crossorigin。
  • 換字型時的位移：先用無單位的 line-height 固定行高（所有瀏覽器有效），再用 ascent-override、descent-override、size-adjust 做一個度量相同的備援字型（Safari 不支援 override，會忽略）。
  • 文章頁：中文內文行高 1.7～1.8、一行約 30～40 字（max-inline-size 用 em）、段落之間留 1em；標題加 text-wrap: balance 當漸進增強。
