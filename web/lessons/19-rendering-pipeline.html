階段 4：除錯、瀏覽器與效能 · 第 19 課

瀏覽器渲染：style、layout、paint、composite 與避免反覆重排

咖啡店的菜單頁有 600 個品項。這週客服轉來三則回報：「通知條滑進來時整頁跟著抖」「點分類篩選後要等半秒才有反應」「在舊手機上捲動會卡」。你打開程式碼，三個地方都沒有寫錯，畫面最後也都是對的。問題出在過程：瀏覽器為了畫出這個畫面，做了很多次本來不用做的工作。

這一課就拿這三則回報當任務，一則一則查到原因、改好。要查得下去，得先知道瀏覽器怎麼把 DOM 變成螢幕上的像素，以及你的每個改動會讓它重做哪些事。學完之後，你看到一段動畫或一個迴圈，能說出它貴在哪一步，也能用 DevTools 證明給回報的人看。

這課的路線：
  1. 瀏覽器畫一幀做了哪些事：五個步驟、主執行緒、一幀的時間預算。三則回報各自卡在哪一步，這節先給出最小的答案。
  2. 通知條為什麼讓整頁跟著抖：一個改動從哪一步開始重做，怎麼把動畫改成只動合成屬性。
  3. 點篩選為什麼要等半秒：先拆掉篩選後那段「改了樣式馬上讀高度」的迴圈（強制同步版面），再處理一次跑太久的 JavaScript（長任務）。
  4. 舊手機捲動為什麼卡：用 content-visibility 讓瀏覽器先跳過畫面外的品項；同事提議的「每張卡片加 will-change」為什麼不是解法。
這課會用到：
  • 第 17 課的 transition、@keyframes 與「位移用 transform 不用 top」：transform 只改畫出來的樣子，不重新排版。
  • 第 1 課的 DOM：瀏覽器解析 HTML 後建出的節點樹，JavaScript 改的是它，不是原始碼。
  • TypeScript 課第 7 課的 event loop：JavaScript 一次只做一件事，一個 task 跑完才輪到下一個。

瀏覽器畫一幀，做了哪些事？

三則回報說的「抖」「慢」「卡」，都是使用者對同一件事的感受：畫面沒有在該更新的時候更新。要知道為什麼沒更新，得先知道瀏覽器每次更新畫面要做哪些事。

第 17 課已經看過 Style、Layout、Paint、Composite 四步。這裡把前面的 JavaScript 也接上，連成完整的渲染流程（rendering pipeline）。它是瀏覽器把 HTML、CSS、JavaScript 變成螢幕上像素的一串固定步驟，每一步都拿上一步的結果當材料：

  1. JavaScript：你的程式改了 DOM 或樣式，例如加 class、改 style、插入元素。CSS 動畫、transition、hover 也會造成改變，只是不經過你的程式。
  2. Style（計算樣式）：拿每個元素去比對所有 CSS 選擇器，算出它最後的樣式值，就是 DevTools Computed 面板看到的那些。
  3. Layout（版面）：拿算好的樣式，算出每個盒子的位置與大小。這一步也常被叫做重排（reflow），兩個名字指同一件事，這課統一叫 layout。一個元素變高，後面的元素都要往下移，所以 layout 常常牽動一大片。
  4. Paint（繪製）：知道每個盒子在哪裡之後，把文字、背景、邊框、陰影變成一串繪製指令，例如「先畫這塊背景、再畫這行字」。這一步也叫重繪（repaint）。指令最後還要變成真正的像素，這個動作叫點陣化（raster）；Chrome 把點陣化交給其他執行緒，但產生繪製指令仍在主執行緒上。
  5. Composite（合成）：頁面可能被分成好幾張各自畫好的圖層（layer），像幾張透明片。合成就是依照每張的位置、透明度，把它們疊成最後的畫面。

因為每一步都依賴上一步的結果，一個改動從哪一步開始影響，後面的步驟就都得重做：盒子大小變了，原本的繪製指令就畫錯位置，所以 layout 之後一定要 paint；但只是把一張已經畫好的圖層挪個位置，前面三步都不用動。下面這張圖把三種典型的改動畫出來，下一節會解釋怎麼判斷一個改動屬於哪一種。

圖上方把步驟分成兩區，因為它們在不同的執行緒上跑。主執行緒（main thread）是瀏覽器替每個頁面執行 JavaScript、Style、Layout、Paint 的那條執行緒。它一次只能做一件事：你的程式在跑的時候，瀏覽器就不能算版面、不能畫畫面，也不能處理點擊。Composite 可以交給另一條合成器執行緒做，所以只動 transform、opacity 的動畫，在 JavaScript 很忙的時候還能順順地跑。

主執行緒還有時間限制。螢幕每次刷新顯示的一張畫面叫一幀（frame）。60Hz 的螢幕每秒刷新 60 次，每一幀約 16.7ms（1000 ÷ 60）；120Hz 的手機只有約 8.3ms。瀏覽器自己也要用掉一部分時間，所以 web.dev 建議把自己的工作壓在 10ms 左右。一幀的時間內做不完，這一幀就掉了，螢幕繼續顯示舊畫面，使用者看到的就是卡頓（jank）。

有了這張圖，三則回報可以先各自對上一個位置：通知條滑進來時，每一幀都在做不必要的 layout；點篩選之後，主執行緒被一段 JavaScript 佔住，畫面停住、後面的點擊排不進去；捲動卡，是因為每次重算都要處理 600 個品項，再加上大量圖層。接下來一則一則驗證。第一則最直觀：同一個滑入效果，為什麼有的寫法順、有的寫法會讓整頁抖？

通知條為什麼會讓整頁跟著抖？

查看通知條的 CSS，進場動畫同時改了 top 與 height：高度從 0 長到實際高度，位置從上方移下來。height 每一幀都在變，通知條下面的整份菜單每一幀都被往下推一點，瀏覽器每一幀都得重新 layout 一整頁。整頁跟著抖，就是這些 layout 做不完、掉幀的樣子。

要判斷一個改動有多貴，就是判斷它從渲染流程的哪一步開始。問兩個問題：它會不會改變盒子的大小或位置？會的話要 layout。它會不會改變畫出來的像素，但不動位置？會的話要 paint。兩者都不會，只是把已經畫好的圖層挪動或調透明度，就只要 composite。常見屬性依這兩個問題分成三類：

類型常見屬性要重做判斷依據
版面屬性width、height、top／left、margin、padding、border-width、font-size、font-weight、display、文字內容Style、Layout、Paint、Composite盒子大小或位置變了，鄰居可能跟著動
繪製屬性color、background-color、background-image、box-shadow、border-color、outlineStyle、Paint、Composite像素變了，位置沒變
合成屬性transform（含獨立的 translate、scale、rotate）、opacityStyle、Composite只是把畫好的圖層挪動、縮放、調透明度

通知條的 top 與 height 都在第一類，所以每一幀全部重做。改法是讓它只動第三類：用 transform 從畫面上方外面移到原位。transform 不改盒子在版面上的位置，只改畫出來的樣子，所以通知條在版面上一開始就佔好自己的位置，滑動過程中不推動任何鄰居，瀏覽器每一幀只要合成。練習 2 就是把這個通知條和一張 hover 會放大的卡片改成這樣。

這張表是大原則，不是規格保證，細節依瀏覽器與情境而定。合成屬性要「通常」才只需要合成：元素還沒有自己的圖層時，第一次改 transform 可能要重畫一次。反過來，有些屬性看起來只改外觀，其實會動到版面：font-weight 看起來只是字變粗，但字也變寬了，同一行的其他字和下一行都要重排。所以表格用來做第一步判斷，最後還是要量。

用 JavaScript 改 class 時也用同樣的方式判斷。el.classList.add('open') 這行本身不貴，貴的是新 class 帶來的樣式：class 讓 max-height 改變，就是 layout；只讓 opacity 改變，就只是合成。另外，Style 這步的成本跟「要重算的元素有多少、選擇器有多複雜」有關。在 body 上切換一個 class，而很多選擇器以它開頭（例如 body.dark .card），全頁的元素都要重算樣式。

💡 實務上：做互動效果前，先想它動的是哪一類屬性
最常見的情境是設計稿上的 hover 卡片浮起、手風琴展開、側邊選單滑入，跟這次的通知條一樣。同樣的視覺，用 top、height 做每一幀都要 layout，用 transform 做通常只要合成；陰影變化可以改成對一層偽元素（::after）調 opacity，而不是直接動 box-shadow。資深工程師 code review 看到 transition 裡有 width、height、top，會先問「能不能改成 transform？」。但不必為了效能硬拗：只在點擊時變一次、不是連續動畫的改動，用什麼屬性都無所謂，有在低階手機上卡了再處理。

通知條解決了。第二則回報不一樣：點分類篩選之後，那半秒裡畫面上沒有任何東西在動，換屬性幫不上忙。錄一次點擊，Main 那一列是一長段黃色的 JavaScript，中間密密麻麻夾著很多紫色的 Layout。版面為什麼會在 JavaScript 執行到一半時被算了這麼多次？

點篩選後，為什麼 JavaScript 跑到一半就一直在算版面？

先看瀏覽器平常怎麼處理樣式修改。正常情況下它很懶：你改了樣式，它只記下「版面髒了」，等這段 JavaScript 跑完、要畫下一幀時，才一次做 style 與 layout。你在一段程式裡改了十個元素，它只算一次版面。這個懶惰是故意的，因為中途的版面沒有人看，算了也是白算。

但如果你改完樣式，馬上讀取一個要算過版面才知道的值，例如元素的實際高度 offsetHeight，瀏覽器就不能再拖了。它不能回答舊的數字，因為你剛改的樣式可能讓高度變了；為了給你正確的答案，它只好當場把 style 與 layout 做完再回答。這叫強制同步版面（forced synchronous layout），也常被叫做 forced reflow。「同步」指的是這次 layout 發生在你的 JavaScript 執行中途，而不是等程式跑完。

偶爾一次強制同步版面沒關係，一次 layout 本來就要做。問題在迴圈：如果每一圈都是「寫入樣式、讀取版面」，每一圈的讀取都碰到上一圈弄髒的版面，每一圈都強制 layout 一次。這種寫與讀交錯、讓 layout 一再重做的情況，叫版面抖動（layout thrashing）。

菜單頁篩選後的程式碼就是這樣。每個品項的說明要能從 0 展開到它的實際高度，所以篩選完之後，程式逐一量出每個說明的完整高度存起來，再把它收合成 0：

// ✗ 每一圈：寫 height → 讀 scrollHeight → 寫 height。600 個品項就強制 layout 600 次
for (const item of items) {
  const desc = item.querySelector('.desc')
  desc.style.height = 'auto'                    // 寫：版面髒了
  const h = desc.scrollHeight                   // 讀：瀏覽器被迫立刻 layout
  desc.style.height = '0px'
  item.dataset.full = String(h)
}

每一圈的讀取都需要前一圈寫入後的最新版面，而且菜單是一整份連續的版面，每次 layout 都可能牽動整份菜單，600 次就是把整份菜單重排 600 次。改法是調整順序，先把所有要讀的讀完，再一次寫完：

const descs = items.map(item => item.querySelector('.desc'))
// ✓ 先讀：篩選剛改過 DOM，第一次讀會 layout 一次；之後版面沒再被弄髒，其餘 599 次直接拿結果
const heights = descs.map(desc => desc.scrollHeight)
// 再寫：只是記下修改，等這段程式跑完才 layout 一次
descs.forEach((desc, i) => {
  items[i].dataset.full = String(heights[i])
  desc.style.height = '0px'
})

要在自己的程式裡認出這個模式，得先知道哪些讀取會逼瀏覽器算版面。最常見的是 offsetTop／offsetLeft／offsetWidth／offsetHeight、clientWidth／clientHeight、scrollTop／scrollHeight、getBoundingClientRect()，以及用 getComputedStyle() 讀版面相關的值（完整清單見課末「補充與查表」）。它們的共通點是：答案取決於元素實際排在哪裡、有多大。讀 el.style.width 就不算，它讀的是你寫在 inline style 上的字串，不需要算版面。

「先讀後寫」有一個前提：讀的值不依賴這次的寫入。上面的例子讀的是說明的完整內容高度，跟稍後把說明框收成 0 無關，所以可以先讀。如果你真的需要「寫完之後」的新尺寸，就接受一次強制 layout，但只做一次，而不是每個元素一次。

上面能在同一個迴圈裡排好順序，是因為讀和寫都在同一段程式裡。真實專案常常不是這樣：菜單頁的篩選邏輯在列表元件裡，量高度、設高度的程式卻散在每張卡片的元件裡，各自在自己的函式裡「讀一下、寫一下」，你沒辦法把它們排進同一個迴圈。這時用 requestAnimationFrame(() => { … })：它的 callback 會在瀏覽器下一次畫畫面之前執行。做法是讓各處當下只讀版面值，把要寫的樣式包進 requestAnimationFrame 排到後面；這些寫入會在下一幀前一起執行，讀和寫自然分成前後兩批。要注意的是，callback 裡只放寫入，不要再讀版面值：前面的 callback 已經寫過樣式，版面是髒的，這時讀 scrollHeight 一樣會強制 layout。

跟 Vue 的關係：Vue 課第 6 課的排程器把同一輪的資料修改批次起來，到 nextTick 才一次更新 DOM，所以 Vue 自己的更新很少造成抖動。抖動通常出在你手寫的量測程式：await nextTick() 之後，在迴圈裡逐一讀 offsetHeight 再設定高度（textarea 自動長高、瀑布流、等高卡片）。一樣先讀完再寫。Performance 面板裡的強制 layout 會在 Layout 事件上標紅色三角形警告（Forced reflow），並指出是哪一行 JavaScript 觸發的。
💡 實務上：抖動多半藏在捲動與尺寸監聽裡
工作中最常見的是「捲到某處讓 header 變小」「元素進入畫面才播動畫」「卡片高度跟著視窗調整」，寫成 scroll 或 resize 事件裡讀 getBoundingClientRect() 再改樣式，捲一下就觸發好幾次。這類需求先找專用的 API：判斷是否進入畫面用 IntersectionObserver，監聽元素尺寸變化用 ResizeObserver，它們在瀏覽器算好版面之後才通知你，不用自己在事件裡量。引入輪播、瀑布流這類套件時，也值得錄一次 Performance，在 Main 那一列看有沒有一長串緊挨著 JavaScript 的 Layout 事件。練習 1 會讓你寫一個計算強制 layout 次數的函式，把「讀寫交錯」這個規則變成能檢查的程式。

量測迴圈改成先讀後寫之後，再錄一次點擊：紫色的 Layout 只剩一次，但前面還有一段約 200ms 的黃色 JavaScript，是篩選和排序 600 個品項。這段程式沒有碰版面，可是在它跑完之前，按鈕不會變成按下的樣子，畫面也完全不動；使用者以為沒點到，再點一次，第二次點擊又要等更久。一段沒碰畫面的 JavaScript，為什麼能讓整個頁面停住？

一段 200ms 的 JavaScript，為什麼讓點擊排隊？

答案在主執行緒「一次只做一件事」。瀏覽器把要做的工作切成一個個 task：執行一段 script 是一個 task，處理一次點擊事件是一個 task，一個 setTimeout 的 callback 也是一個 task。這些 task 排在佇列裡，主執行緒一個跑完才輪到下一個（TypeScript 課第 7 課的 event loop）。使用者的點擊也只是佇列裡的一個 task，前面的 task 還沒跑完，它就只能等，畫面也不會更新，因為 style、layout、paint 同樣在這條執行緒上。

用這個模型回頭看菜單頁，使用者其實在等兩件不同的事：

  • 等這次點擊自己的處理：篩選和排序就寫在點擊的事件處理函式裡，這 200ms 是這次點擊本身的工作。工作沒做完，主執行緒輪不到畫畫面，所以這 200ms 裡按鈕不會出現按下的樣子，列表也不會更新。這一種等待，篩選結果本來就要算完才有，能做的是讓使用者在等的時候看到「有在處理」。
  • 等前一次處理跑完：使用者在這 200ms 裡又點了另一個分類，或試著捲動，這些新輸入變成新的 task，排在還沒跑完的篩選後面。使用者明明點了第二下，卻要先等第一次篩選做完，才輪到第二下開始處理。

執行超過 50ms 的 task 叫長任務（long task）。它執行期間進來的點擊、輸入全部要排隊，排隊的時間會直接加在使用者感覺到的延遲上。下面用忙等（busy loop，一個什麼都不做、只是空轉到時間到的迴圈）模擬「一次算完 600 個品項的篩選與排序，花了 200ms」。這段示範的是第二種等待：setTimeout(…, 0) 代表使用者在篩選剛開始時又點了第二個分類，執行後看這次點擊在第幾毫秒才輪到處理：

第二次點擊整整等了 200ms，因為它排在那個 200ms 的 task 後面。總工作量不變的前提下，能做的是把一個長 task 切成多個短 task，讓點擊有機會插進中間。下面把同樣的工作切成 10 段、每段 20ms，段與段之間用 await 一個 setTimeout：await 讓這個函式先暫停、把主執行緒還給瀏覽器，接續的部分被排成佇列裡一個新的 task。執行後一樣看點擊的時間：

總工作量一樣，第二次點擊卻在第一段之後就被處理了。要說清楚的是：篩選結果並沒有比較早出現，全部做完反而稍晚一點。拆段解決的是第二則回報裡「點了沒反應」的感覺，好處有兩個，各自對應上面兩種等待：

  • 這次點擊能先給回饋：段與段之間主執行緒是空的，瀏覽器有機會畫一幀。點擊處理函式先把按鈕或列表改成載入中的樣式，再開始第一段篩選，使用者在第一段結束後就能看到「有在處理」，不會以為沒點到。
  • 後面的點擊不用排到最後：使用者在中途點了別的分類或捲動，這些輸入能插在段與段之間處理，不必等 200ms 全部跑完。實務上，收到新的篩選條件時，還要讓舊的那次停下來，不要把已經過時的結果畫出來。

這種做法叫讓出主執行緒（yield），代價有兩個：全部做完的時間稍微變長；而且 setTimeout 讓出去之後，接續的工作排到佇列最後面，別的 task（例如第三方分析程式）可能插隊。瀏覽器新增了 scheduler.yield() 讓接續的工作優先，但還不是所有瀏覽器都支援，要用的話先判斷 'scheduler' in window，否則退回 setTimeout（支援情況見課末「補充與查表」）。

拆任務是治標。更根本的做法是讓工作變少：篩選 600 個品項本身很快，慢的常常是之後一次插入 600 個 DOM 節點的 style 與 layout。這時減少 DOM 數量（分頁、虛擬清單，或下一節的 content-visibility）比拆任務有效。

從「使用者點下去」到「畫面出現回應」的這段時間，就是第 20 課的 INP（Interaction to Next Paint），好的標準是 200ms 以內。它包含三段：點擊進來時主執行緒還在忙前一件事（輸入延遲）、你的事件處理函式（處理時間）、處理完之後的 style、layout、paint（呈現延遲）。放回菜單頁，三段各有對應：前一次篩選還沒跑完時又點了一次，第二次點擊排隊等的時間是輸入延遲；篩選與排序的 200ms 加上原本 600 次的強制 layout，是處理時間；篩選後 600 個品項的 style、layout、paint，是呈現延遲。第二則回報的「等半秒」，就是這三段加起來。

💡 實務上：「按了沒反應」先在慢手機條件下重現
這類回報常來自客服或 PM，而且多半發生在使用者的舊手機上，你的開發機重現不了。資深工程師的第一步是開 Performance 面板、CPU 設 4x slowdown，錄一次那個操作，找出超過 50ms 的長任務是誰的：自己的程式、框架一次重新渲染大清單，還是第三方腳本。找到之後先問「這件事能不能少做」（少畫一點 DOM、晚一點再算），最後才拆任務。修完再錄一次，用同樣條件比較前後，向回報的人說明時也有依據。

上一段提到「減少 DOM 比拆任務有效」，這也正是第三則回報的源頭：600 個品項全部在 DOM 裡，不管使用者看不看得到，瀏覽器都得處理它們。能不能讓瀏覽器只處理畫面附近的那些？

舊手機捲動卡：怎麼讓瀏覽器先跳過看不到的品項？

先回答一個疑問：頁面已經渲染完了，捲動時為什麼還跟那 600 個品項有關？因為渲染不是只做一次。600 個品項都在 DOM 裡，即使使用者只看得到最上面 20 個，每次需要重算整頁的 style 或 layout，例如篩選之後、視窗改變尺寸、某個品項的說明展開，瀏覽器都可能要把這 600 個品項全部處理一遍（上一節說過，菜單是一整份連續的版面）。使用者在捲動中途做了這些操作，或捲動途中有東西改了樣式，這次重算就落在捲動期間。開發機算得快，看不出來；舊手機的 CPU 慢，同樣的工作量更容易超出一幀的預算，於是畫面掉幀，感覺就是捲動卡。再加上同事替每張卡片加的 will-change，讓舊手機本來就少的記憶體被大量圖層佔走（下一節細講）。

所以要做的是讓每次重算只處理畫面附近的品項。CSS 有一個屬性專門處理這種情況：content-visibility: auto 告訴瀏覽器，這個區塊離畫面遠的時候，先跳過它內部的渲染，捲到附近再做。篩選、改尺寸引起的重算，就只需要處理畫面附近的區塊。代價也要先講清楚：被跳過的工作沒有消失，而是搬到「區塊捲到附近」的那一刻才做，也就是搬進了捲動期間。所以每個區塊的工作量要小，一次渲染一個區塊不會拖垮一幀；預留的高度也要接近實際高度，否則區塊渲染時長高或變矮，捲軸會跳（後面細講）。菜單頁依分類分成區塊，從第 2 個分類開始套用：

.cat + .cat {                         /* 第 2 個分類起 */
  content-visibility: auto;
  contain-intrinsic-size: auto 1800px;  /* 還沒渲染時，先當成 1800px 高 */
}

這兩行看起來很簡單，但要用對，得先知道瀏覽器憑什麼敢跳過一個區塊。平常它不敢：一個區塊裡的品項變高，後面所有內容都要往下移；區塊裡的下拉選單可以畫到區塊外面。也就是說，區塊內部的變化可能影響外部，瀏覽器不看內部就不知道外部該長什麼樣。

讓它敢跳過的機制叫 containment（包含），由 contain 屬性設定。它是你對瀏覽器的承諾：「這個元素的內部不會影響外部」，瀏覽器據此把這個元素當成獨立的一塊計算，或直接略過。跟這一節有關的承諾有三種：

  • layout containment：內部的版面不影響外部。裡面的品項怎麼重排，外面的內容都不用跟著動。
  • paint containment：子孫不會畫到自己的邊界外。代價是超出的部分會被裁掉。
  • size containment：自己的大小不看內容決定。這是能「完全不看內部」的關鍵，但沒有另外指定尺寸時，高度會變成 0。

contain 的全部值與副作用整理在課末「補充與查表」。content-visibility: auto 會替你一律開啟 layout、style、paint containment；區塊被跳過時，再加上 size containment。問題就出在最後這一個：size containment 讓瀏覽器不看內容就決定區塊大小，這時如果沒有 contain-intrinsic-size，被跳過的區塊高度就是 0（只剩 padding 與 border）。後果是頁面一開始很短，捲動時區塊一個個被渲染、長出真正的高度，捲軸的長度與位置一直跳。

contain-intrinsic-size 就是替被跳過的區塊預留尺寸。auto 1800px 的意思是：還沒渲染過時當成 1800px；前面的 auto 讓瀏覽器記住渲染過的實際大小，之後再被跳過就用記住的值，不會退回 1800px。預留值怎麼決定？在 DevTools 選一個區塊，看盒模型的高度，取典型值。不用精準，接近就好。auto 一定要自己寫上，不要依賴瀏覽器替你補（原因見課末「補充與查表」）。

跳過渲染之後，內容還算不算「在頁面上」？這決定了它能不能取代 display: none 這類隱藏方式，答案是不能，兩者用途不同：

auto 跟 hidden 不一樣：MDN 說明，content-visibility: auto 跳過的內容仍然要能被頁內搜尋（Ctrl＋F）找到、能用 Tab 聚焦、能選取，也留在無障礙樹裡，螢幕閱讀器讀得到。content-visibility: hidden 則跟 display: none 類似：搜尋不到、聚焦不到，用來保留「切回來很快」的隱藏內容（例如分頁標籤），不是拿來做效能優化。用 display: none 藏起畫面外的內容更糟：使用者搜尋不到、錨點連結也捲不過去。

套用到菜單頁之前，還要確認幾件事。第一，首屏不要套：首屏的內容本來就要立刻渲染，套用得不到任何節省，所以上面的選擇器從第二個分類開始。第二，paint containment 會裁切：區塊裡的下拉選單、tooltip 要伸出區塊外時會被切掉。這類元件不要放在套用的區塊裡，或改用 popover 屬性顯示（第 10 課的 top layer，不受祖先的裁切影響）。

第三，錨點與搜尋照常運作：導覽列連到被跳過區塊裡的 #id，瀏覽器會先把它渲染出來再捲過去。前提是預留高度合理，否則捲到之後前面的區塊陸續長高，目標又被擠走。第四，JavaScript 讀版面會破功：對被跳過的區塊讀 offsetHeight、getBoundingClientRect()，瀏覽器還是得把它渲染出來才能回答（web.dev 也提醒要檢查這類呼叫），這跟上一節的強制同步版面是同一個道理。最後，content-visibility 已經是 Baseline，不支援的瀏覽器會忽略這兩行，頁面照常顯示，只是沒有加速，屬於安全的漸進增強（版本細節見課末）。練習 3 就是替一份 12 個分類的菜單做這件事。

content-visibility 也有它的上限。資料上萬筆時它不夠：每個節點仍在 DOM 裡、仍佔記憶體。那時要用虛擬清單（virtual list），只建立畫面附近的幾十個節點。幾百到幾千個、結構固定的區塊，例如這份 600 個品項的菜單，content-visibility 只要兩行 CSS，最划算。

捲動的問題還有一段插曲：在你查到這裡之前，有同事已經試過另一個方法，替每張品項卡片加上 will-change: transform，理由是「讓瀏覽器用 GPU 畫，捲動就會順」。這個方法該不該留？

每張卡片都加 will-change，捲動會變順嗎？

先回到第一節的 Composite。合成之所以便宜，是因為元素已經被畫在自己的圖層上，之後只要移動圖層，不用重畫。這種被單獨畫成一張的圖層叫合成層（compositing layer）。瀏覽器會自動把某些元素升成合成層：正在跑 transform／opacity 動畫的元素、<video>、position: fixed 的元素（視情況）、設了 will-change: transform 的元素等。will-change 就是預先告訴瀏覽器「這個元素等一下會動」，讓它提早升層。

但圖層不是免費的。每個圖層是一張點陣圖，大小約是「寬 × 高 × 裝置像素比² × 4 bytes（RGBA）」。一個在 3 倍螢幕的手機上占滿 390×844 CSS px 的圖層，約 390×3 × 844×3 × 4 ≈ 11.8 MB。替清單裡的 100 張卡片都寫 will-change: transform，就是 100 張點陣圖。GPU 記憶體不夠時，瀏覽器反而變慢，甚至讓分頁被系統關掉。舊手機的記憶體本來就少，同事的做法正好打在第三則回報最弱的地方。

第 17 課講過 will-change 是最後手段；這裡補上怎麼確認：DevTools 的 Layers 面板（⋮ → More tools → Layers）列出每個圖層、它的記憶體估計，以及「為什麼被升成圖層」（Compositing reasons）。原則是先量到問題（例如動畫開始的第一幀卡一下），再只對那個元素加，動畫結束後拿掉。菜單卡片在捲動時並沒有各自的動畫，不符合「先量到問題、只對要動的元素加」，所以這 600 個 will-change 應該拿掉，改用上一節的 content-visibility 減少渲染量。

到這裡，三則回報都有了原因與修法，而且每一個都能用 DevTools 錄給回報的人看：

回報卡在哪一步修法怎麼證明修好了
通知條滑進來整頁跟著抖動 top、height，每一幀都要 Layout改用 transform 滑入Performance 裡每幀的 Layout 消失，Paint flashing 不再整片閃
點篩選要等半秒量測迴圈強制 layout 600 次，加上 200ms 的長任務佔住主執行緒先讀後寫；拆任務讓出主執行緒，並減少要渲染的 DOMForced reflow 警告消失，沒有超過 50ms 的長任務

補充與查表

render tree：display: none 與 visibility: hidden 的差別。Style 與 Layout 之間還有一個中間產物：render tree，只包含要畫出來的元素。display: none 的元素和它的子孫不在裡面，不佔版面、也不畫；visibility: hidden 的元素還在，照樣佔位置、參與 layout，只是不畫出來。所以把一個大區塊從 display: none 切成顯示，要付出的是整塊的 style 與 layout。

會強制同步版面的讀取（查表用，不用背）：offsetTop／offsetLeft／offsetWidth／offsetHeight、clientWidth／clientHeight、scrollTop／scrollHeight、getBoundingClientRect()、getComputedStyle() 讀版面相關的值、innerText，以及 el.focus()、scrollIntoView() 這類要先知道位置才做得了的動作。讀 el.style.width 不算：它讀的是你寫在 inline style 上的字串，不需要算版面。

contain 的值（查表用，不用背）：

值承諾副作用
layout內部的版面不影響外部變成 fixed／absolute 子元素的包含區塊，也建立 stacking context（第 10 課）
paint子孫不會畫到自己的邊界外超出的部分被裁掉：下拉選單、陰影、徽章會被切
size自己的大小不看內容沒有指定尺寸時高度變 0
style計數器（counter）等不往外影響很少單獨用

版本備註：

  • scheduler.yield()：撰寫時（web-features 3.44.0）只有 Chrome 129、Firefox 142 起支援，Safari 還不支援，不是 Baseline，要用的話先判斷 'scheduler' in window，否則退回 setTimeout。
  • contain-intrinsic-size 的 auto：你可能會在 Chrome 的 Computed 面板看到：只寫 contain-intrinsic-size: 1800px，計算後的值也是 auto 1800px，因為 Chrome 對 content-visibility: auto 的元素自動補上了 auto（Chrome 156 實測）。CSS Box Sizing 4 規格沒有這樣規定，別的瀏覽器不一定照做，所以 auto 要自己寫上。
  • 支援度：web-features 3.44.0 的資料裡，content-visibility 在 2025-09-15 成為 Baseline newly available（Safari 26 補上）；contain-intrinsic-size 已是 widely available。

練習

練習 1：寫 countForcedLayouts(ops)，從一串 DOM 操作紀錄算出瀏覽器被迫同步 layout 的次數：讀取 LAYOUT_READS 裡的值時，如果前面有還沒處理的 LAYOUT_WRITES 寫入，就算一次，而且算完之後版面是最新的；寫 color、transform 這類屬性不會讓版面變髒。再寫 batch(ops)：把所有讀取移到前面、寫入移到後面，讀與寫各自保持原本的先後順序，讓 countForcedLayouts(batch(ops)) 是 0。測試除了手寫的案例，還會跑 300 組隨機操作。

練習 2：效能檢查發現三個動畫：(1) 通知條進場時動 top 與 height；(2) 卡片 hover 時把 width、height 從 200×120 放大到 220×132；(3) 購物車數字 hover 變色。把 (1)、(2) 改成只動合成屬性（transform、opacity），外觀的起點與終點不變：通知條從畫面上方外滑到原位，卡片看起來放大成 220×132 而且不推動其他內容。(3) 的顏色過渡保留。只改「動畫」註解以下的 CSS 就好。

練習 3：菜單頁有 12 個分類、每類 50 個品項（品名用編號代替），手機上捲動時卡頓。讓第 2～12 個分類在捲到附近之前不渲染：用 content-visibility: auto，並用 contain-intrinsic-size 預留接近實際的高度（記得 auto 關鍵字）。第 1 個分類在首屏，不要套用。導覽列的錨點連結要能把分類標題捲到畫面頂端。HTML 不能改。

練習 4：菜單分類標籤在 hover 時把字變粗（font-weight: 400 → 700），其他樣式不變。這個改動會讓瀏覽器重做哪些步驟？

✓ b：粗體字每個字都比較寬，標籤的寬度改變，旁邊的標籤要跟著移動，所以要 layout，之後當然要重畫。a 把 font-weight 當成 color 那類繪製屬性，忽略了寬度變化；hover 加粗常讓整排標籤左右跳，就是這個原因，常見做法是預留粗體的寬度，或改用顏色、底線表示狀態。c 文字不會自動放在獨立圖層，而且字形變了一定要重畫。d 瀏覽器不會預先畫好 hover 之後的樣子，hover 改變的樣式跟一般樣式一樣，從 Style 開始往後走渲染流程；字變寬就要 layout。

練習 5：下面哪段程式會造成版面抖動（layout thrashing）？（cards 是 600 張卡片）

✓ b：每一圈先寫 width（版面髒了），馬上讀 offsetHeight，瀏覽器被迫當場 layout；600 圈就是 600 次。a 先讀完再寫完，最多一次 layout。c 只寫不讀，修改會在這段程式跑完後一起處理。d 只讀不寫，版面一直是乾淨的，最多在第一次讀的時候 layout 一次。

練習 6：同事在 600 個品項的頁面上替每個分類加了 content-visibility: auto，但沒寫 contain-intrinsic-size。最可能出現什麼問題？

✓ b：被跳過的區塊套用 size containment，不看內容決定大小；沒有預留尺寸就只剩 padding 與 border。捲到附近才渲染、長出真正的高度，捲軸跟著跳。補上 contain-intrinsic-size: auto 1800px，auto 讓瀏覽器記住渲染過的實際高度。a 正是因為不渲染內容，瀏覽器才不知道高度。c 捲到附近就會渲染。d 那是 hidden 或 display: none 的行為，auto 的內容仍然搜尋得到。

常見錯誤

  • 用 width、top、margin、height 做動畫：每一幀都要 layout，還會推動旁邊的內容，就像開場那個讓整頁跟著抖的通知條。位移與縮放用 transform，淡入淡出用 opacity。
  • 以為改 class 就便宜：成本看的是 class 帶來的樣式。class 改了 height 就是 layout；在 body 上切 class 會讓大量元素重算樣式。
  • 迴圈裡讀寫交錯：每一圈都強制 layout 一次。先把要讀的讀完，再一次寫完；需要寫完後的新尺寸時，只讀一次。
  • 把一大段工作塞在一個事件處理函式裡：超過 50ms 就是長任務，期間點擊都沒反應。切段並讓出主執行緒，或減少要做的事。
  • content-visibility 沒有預留尺寸：被跳過的區塊高度塌成 0，捲軸跳動。加 contain-intrinsic-size: auto <典型高度>。
  • 首屏也套 content-visibility：得不到好處。從第一個畫面外的區塊開始。
  • 用 display: none 或 content-visibility: hidden 做效能優化：內容搜尋不到、聚焦不到、錨點捲不過去。效能優化用 auto。
  • 到處加 will-change：每個圖層都佔一張點陣圖，記憶體不夠時反而更慢。先在 Layers 面板量，只對確定要動的元素加。

小結

  • 渲染流程：JavaScript → Style → Layout → Paint → Composite，每一步都用上一步的結果。改動從哪一步開始，後面都要重做；前四步都在主執行緒上，一幀只有約 16.7ms（120Hz 約 8.3ms）。
  • 改變大小或位置要 layout；只改像素要 paint；transform、opacity 通常只要 composite。通知條改用 transform 滑入，就不再每一幀重排整頁。最後以 Performance 面板與 Paint flashing 量到的為準。
  • 寫了會影響版面的樣式後馬上讀 offsetHeight、getBoundingClientRect() 等值，會強制同步 layout；在迴圈裡交錯就是版面抖動。先讀後寫。
  • 超過 50ms 的長任務會擋住點擊，拉長 INP；切段讓出主執行緒，或減少 DOM 與工作量。
  • content-visibility: auto ＋ contain-intrinsic-size: auto <高度> 讓畫面外的區塊先不渲染，內容仍可搜尋、聚焦、被輔助科技讀到；首屏不要套，注意 paint containment 會裁切。
  • 圖層讓合成便宜，但每層都吃記憶體；will-change 先量再用，不要拿來當捲動卡頓的通用解法。
