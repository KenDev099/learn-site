階段 5：SEO 與內容交付 · 第 23 課

技術 SEO：爬取與索引、robots、noindex、sitemap、canonical、狀態碼與重新導向

豆留咖啡的官網改版上線兩週，老闆在 Google 搜尋「豆留咖啡 菜單」，前幾頁都找不到官網。這次改版做了三件事：換掉前端框架、路由整批改名（例如冰滴咖啡從 /menu/cold-drip/ 搬到 /menu/coffee/cold-brew/）、新增英文版。查原因的工作落到你身上。

第一個原因很快就找到：staging 環境的 robots.txt 寫著 Disallow: /，跟著這次部署一起上了正式環境。查的過程還發現第二個問題，它不會讓官網消失，但會讓排名和點擊被稀釋：同一份咖啡菜單有六種網址都打得開（http／https、有沒有 www、有沒有結尾斜線、LINE 分享帶的 ?utm_source=line、排序用的 ?sort=price），別人連過來的連結和點擊分散在六個網址上。這一課沿著這次事故一路查到修好：先讓搜尋引擎重新拿得到頁面，再決定哪些頁面不收、每份內容收哪一個網址、改名的舊網址怎麼接到新網址，最後把整理好的網址清單交給搜尋引擎。

第 22 課處理的是「每一頁的內容好不好被理解」；這一課往前一步，處理「搜尋引擎拿不拿得到、該不該收、收哪一個網址」。這些設定大多在伺服器、路由和建置流程裡，不在 Vue 元件裡，正是前端轉後端時會接手的部分。

這課的路線：
  1. 官網為什麼消失（第 1–2 節）：搜尋引擎的「爬取」和「索引」是兩件事；robots.txt 的規則怎麼讀，那一行 Disallow: / 為什麼擋掉整站、怎麼防止再發生。
  2. 不想被搜尋到的頁面（第 3 節）：購物車為什麼不能也用 robots.txt 擋，要用 noindex；三種「不讓人看到」的工具怎麼選。
  3. 六個網址收哪一個（第 4–5 節）：用 canonical 指定代表網址；用 301 把 http、www、改名的舊網址導到新網址，下架的商品回對的狀態碼。
  4. 交出清單與多語系（第 6–7 節）：從路由資料產生 sitemap；英文版用 hreflang 標出來，才不會被當成重複內容。
這課會用到：
  • 第 22 課的搜尋引擎三階段：爬取（Googlebot 跟著連結下載網頁）、索引（判斷這頁在講什麼並存起來）、排序與呈現（使用者搜尋時從索引挑出頁面排序）。
  • Node 課第 12 課的狀態碼與回應標頭：200、301、404、500 告訴對方結果；Location 標頭指出重新導向的目的地。
  • DevOps 課第 12 課的 Nginx：server 區塊對應一個網域，location 區塊對應一組路徑。

官網為什麼從搜尋結果消失？先分清楚爬取與索引

要知道一行 Disallow: / 為什麼能讓整個官網消失，得先知道搜尋引擎拿到一個網址之後做了哪些事。第 22 課把它分成三階段；這裡把前兩段拆細，因為每一步各有自己的開關，卡在哪一步，結果就不一樣：

  1. 發現：搜尋引擎從別的頁面的連結知道「有這個網址」。網站也可以主動交一份網址清單，叫 sitemap，第 6 節會做。
  2. 爬取（crawl）：爬蟲（crawler，例如 Google 的 Googlebot）下載這個網址。下載前，它會先讀這個網站根目錄的 robots.txt；這個檔案說不准下載，它就不下載。
  3. 索引（index）：讀懂下載到的內容，決定一組重複的網址裡哪一個是代表（第 4 節），存進搜尋引擎的資料庫。只有在索引裡的頁面，才可能出現在搜尋結果。頁面也可以在自己的 head 裡寫一個 noindex 標記，意思是「這頁不要收」，它在這一步生效（第 3 節）。
  4. 排序與呈現：使用者搜尋時，從索引裡挑出結果排序（第 22 課）。

把事故放進這張圖：User-agent: * 加 Disallow: / 的意思是「所有爬蟲、所有路徑都不准下載」。所以官網的每一個網址都停在 robots.txt 那一格，走左下那條路：Googlebot 不再下載任何頁面，看不到內容。網址就算因為外部連結還留在結果裡，也只剩沒有摘要的一行網址，原本的排名就這樣掉光。

這張圖也說明了兩個開關管的是不同的事：robots.txt 管「能不能下載」，noindex 管「能不能收進索引」。前者在門口擋人，後者寫在頁面裡，要先被下載才讀得到。這個差別是這一課最常用到的判斷，第 3 節會再回來用它。

直接的修法已經很清楚：把正式環境的 robots.txt 改對。但改成什麼才不會又擋錯？robots.txt 的規則怎麼比對，下一節逐條看。

robots.txt 怎麼讀？那一行為什麼擋掉整站

robots.txt 是放在網站根目錄的純文字檔（UTF-8），規格是 2022 年的 RFC 9309。爬蟲要爬一個網站前，會先下載 https://網域/robots.txt，照裡面的規則決定哪些路徑可以爬。它只對同一個 protocol、host、port 有效：https://brew.example.tw/robots.txt 管不到 https://shop.brew.example.tw/，也管不到 http 版本。

先看事故裡那份 staging 的檔案，只有兩行：

# staging 的 robots.txt（被帶上正式環境的那份）
User-agent: *
Disallow: /

User-agent: * 表示「以下規則給所有爬蟲」；Disallow: / 表示「路徑開頭是 / 的都不准爬」，而每個網址的路徑都以 / 開頭，所以整站都擋掉了。在 staging 這是故意的，上了正式環境就是事故。正式環境該有的樣子比較像這樣：

# https://brew.example.tw/robots.txt
User-agent: *
Disallow: /api/
Disallow: /admin/
Allow: /admin/help/
Disallow: /*.json$

User-agent: Googlebot-Image
Disallow: /drafts/

Sitemap: https://brew.example.tw/sitemap.xml

這份檔案有三個概念要懂：群組、規則、誰勝出。

群組：一行或連續幾行 User-agent 開始一個群組，後面跟著這個群組的規則。爬蟲只遵守一個群組：名稱跟自己相符的那個（不分大小寫；同名的群組會合併），沒有相符的才用 *。這點常被誤會成「* 是大家都要遵守的基本規則」。Googlebot-Image 是 Google 專門抓圖片的爬蟲，名稱跟 Googlebot 不同，所以可以有自己的群組。上例的 Googlebot-Image 就只看自己的群組，* 裡的 /api/ 對它不算禁止。想讓它也擋 /api/，要在它的群組裡再寫一次。

規則：Disallow: /路徑 禁止、Allow: /路徑 允許，兩者都是從路徑開頭比對的前綴，而且區分大小寫。* 代表任意字元，結尾的 $ 代表網址到此結束。空的 Disallow:（後面什麼都沒寫）不擋任何東西。

誰勝出：一個路徑常常同時符合好幾條規則，例如 /admin/help/faq 同時符合 Disallow: /admin/ 和 Allow: /admin/help/。這時不是看哪條寫在前面，而是看最長（最具體）的那條；一樣長時 Allow 勝。所以上例可以「整個後台不准爬，只開放說明頁」。

最後一行 Sitemap: 寫 sitemap 的絕對網址，不屬於任何群組，第 6 節會用到。# 之後是註解。底下這張表把比對規則的邊界情況列出來，查表用，不用背；練習 1 會讓你自己實作這套比對：

規則網址路徑結果原因
Disallow: /admin/
Allow: /admin/help/		/admin/help/faq允許/admin/help/ 比較長
Allow: /folder
Disallow: /folder		/folder/page允許一樣長，Allow 勝
Allow: /page
Disallow: /*.htm		/page.htm禁止/*.htm（6 個字元）比 /page（5 個字元）長
Disallow: /*.php$/index.php?lang=zh允許$ 之後還有查詢字串，對不到
Disallow: /fish/Fish.asp、/catfish允許區分大小寫；要從開頭比對
Allow: /$
Disallow: /		/；/menu/允許；禁止/$ 只對到首頁

回到事故。把正式環境的檔案改對只是第一步，還要防止下一次部署又把 staging 的版本帶上去。根本原因是 robots.txt 被當成一個寫死的靜態檔，跟著程式碼一起部署。比較穩的做法是 robots.txt 依環境產生，例如部署時由環境變數決定內容，並把「正式環境的 robots.txt 不含 Disallow: /」放進部署後的自動檢查。

改好之後也不會馬上恢復：Google 通常把 robots.txt 快取 24 小時，之後還要等爬蟲重新爬過各頁。另外，robots.txt 這個檔案本身也要被監控：它回 5xx 錯誤時，Google 會先暫停爬整個網站。Google 怎麼處理 robots.txt 的各種回應，細節見課末「補充與查表」。

改 robots.txt 時還有一個常見的錯：擋住 CSS、JS，例如寫了 Disallow: /assets/。Google 會執行 JavaScript、套用 CSS 來看頁面（第 25 課），資源被擋住，它看到的可能是一頁空白或破版的頁面。改版換框架、打包後的檔案路徑變了，最容易出這個錯。

robots.txt 不是安全機制：它是公開的檔案，任何人都看得到你寫了 Disallow: /admin/，等於告訴別人後台在哪裡；遵不遵守由爬蟲自己決定，惡意爬蟲直接無視。後台要用登入保護（認證課第 1 課），不是靠 robots.txt 藏起來。

robots.txt 修好，整站重新可以爬了。這時同事提議：購物車、結帳頁本來就不該出現在搜尋結果，順手在 robots.txt 加一行 Disallow: /cart 好不好？從上一節那張圖已經可以看出問題，下一節把它講清楚。

購物車不想被搜尋到，為什麼不能用 robots.txt 擋？

回到第 1 節的圖：robots.txt 擋的是「下載」，不是「收錄」。購物車被 Disallow 之後，爬蟲不下載它，但如果有別的網站連到這個網址，網址還是可能以沒有摘要的形式出現在結果裡。同事想要的是「不要出現在搜尋結果」，那是索引那一步的事，要用的工具是 noindex：允許爬蟲下載這頁，但請它不要收進索引。

noindex 有兩種寫法，效果一樣：

<!-- HTML 頁面：寫在 head -->
<meta name="robots" content="noindex">

# 任何檔案（PDF、圖片也可以）：HTTP 回應標頭
X-Robots-Tag: noindex

content 可以用逗號放好幾個值：noindex, nofollow 是「不索引、也不跟著這頁的連結走」，none 等於這兩個加起來。名稱與值都不分大小寫。name="robots" 對所有爬蟲有效，name="googlebot" 只對 Google。規則衝突時，比較嚴格的那個生效。另外，noindex 只有這兩種寫法：寫在 robots.txt 裡的 noindex，Google 不支援。

PDF 沒有 head，只能用標頭。在 Nginx 裡讓所有 PDF 不被索引：

location ~* \.pdf$ {
    add_header X-Robots-Tag "noindex" always;
}

always 讓 404、500 這類回應也帶上標頭。改完用 curl -I https://brew.example.tw/files/menu.pdf 確認標頭真的出現。在 location 裡加 add_header 有一個會讓其他標頭消失的陷阱，見課末「補充與查表」。

現在可以回答同事的提議了：noindex 的頁面不能同時被 robots.txt 擋住。兩個一起用時，爬蟲被擋在門外，永遠讀不到頁面裡的 noindex，結果反而是最想避免的那種：網址仍可能出現在結果裡。Google 的文件也寫明：robots.txt 擋住的網址，meta 標籤與標頭都會被忽略。想讓頁面不出現在搜尋結果，就只用 noindex，讓爬蟲進得來、讀得到。

咖啡店裡該 noindex 的頁面：

  • 購物車、結帳、訂單完成頁：每個人看到的都不一樣，對搜尋的人沒有用。
  • 站內搜尋結果頁（/search?q=…）：網址的組合無限多，內容又跟分類頁重複。
  • 需要登入的會員頁：本來就該靠登入擋住；noindex 只是補充。

noindex 生效也要時間。之後要把某頁的 noindex 拿掉，它不會立刻回到結果裡，要等爬蟲下次來爬。也不要「先輸出 noindex，再用 JavaScript 移除」：Google 讀到原始 HTML 的 noindex 時，可能直接不渲染這頁（第 25 課）。

回頭看事故的源頭 staging。既然 robots.txt 會被帶上正式環境，改成在 staging 全站加 noindex 可以嗎？也不行：

staging 只靠 noindex 不夠：noindex 只是請搜尋引擎配合，staging 的網址被別人分享、被連結時內容照樣公開；而且「staging 全站 noindex」的設定很容易在合併時被帶進正式環境。不想公開的環境要用 HTTP 驗證（例如 Nginx 的 auth_basic）或 IP 白名單，讓沒登入的人與爬蟲只拿到 401／403。

到這裡可以整理出「不讓某些東西被看到」的工具各管哪一步。每次遇到「這頁要不要被搜尋到」時，先問想達成的是哪一件事，再選工具。後兩列會在第 4、5 節講：

想做的事用什麼說明
不要出現在搜尋結果（購物車、結帳、站內搜尋結果頁）noindex，而且不要在 robots.txt 擋要讓爬蟲讀得到 noindex
不要浪費爬取在沒有意義的網址（API、無限的篩選組合）robots.txt Disallow省下爬蟲的請求；但網址仍可能被收錄

做新頁面時（會員專區、限時活動頁、訂單查詢頁），工程師常等到上線後才發現它出現在搜尋結果、或該出現的沒出現。比較好的做法是開需求時就跟 PM、行銷確認：這頁要被搜尋嗎？要公開嗎？再依上表選 noindex、robots.txt 或登入。資深工程師會把「可索引性」當成頁面規格的一欄，跟標題、權限寫在一起，而不是上線後才補。這次改版如果有這一欄，staging 的設定被帶上線時，檢查清單就會先抓到。

事故的第一個問題到這裡處理完了：搜尋引擎拿得到頁面，也知道哪些頁面不收。第二個問題還在：該收的咖啡菜單有六個網址，搜尋引擎到底該收哪一個？

同一份菜單有六個網址，搜尋引擎該收哪一個？

先把事故裡的六個網址列出來，看看它們其實是不是同一頁。下面的程式把各種寫法收斂成同一個網址，執行後看最後一行：

六個網址收斂成同一個，代表它們是同一份內容。但對搜尋引擎來說，這是六個不同的網址，會造成三個問題：別人連過來的連結、分享分散在六個網址上；搜尋結果可能出現你不想要的那個（例如帶著 ?utm_source=line）；爬蟲也把時間花在下載重複的內容上。

canonical（標準網址）就是在一組重複的網址裡指定代表：告訴搜尋引擎「這幾個網址是同一份內容，代表是這一個」。上面程式的 canonicalOf 做的就是這件事，只是搜尋引擎看不到你的程式，要用它讀得懂的方式告訴它。處理方式分三層，從最強的開始：

  1. 能用 301 合併的就 301：http → https（DevOps 課第 5 課）、www → 沒有 www、沒有結尾斜線 → 有結尾斜線。這些網址根本不需要存在，就在伺服器直接導向到代表網址（下一節），使用者與爬蟲不會停在錯的網址上。
  2. 還是需要能打開的變化，用 rel="canonical"：?sort=price（使用者要能排序）、?utm_source=line（行銷要統計來源）不能導走，頁面照常顯示，但在 head 指出代表網址。
  3. 每一頁都寫指向自己的 canonical（self-referencing）：別人帶著任何奇怪參數連過來，代表網址還是清楚的。
<link rel="canonical" href="https://brew.example.tw/menu/coffee/">

# 非 HTML 檔案（例如 PDF）用 HTTP 標頭
Link: <https://brew.example.tw/files/menu.pdf>; rel="canonical"

canonical 寫錯時，搜尋引擎不會報錯，只會默默不採用，所以要知道它在什麼情況下會失效。寫 canonical 的規則：

  • 放在 <head>，用絕對網址。相對網址被支援但不建議：網站被複製到其他網域、或從 http 打開時，會指錯網址。
  • 一頁只給一個答案：兩個 canonical、或 HTML 跟 Link 標頭寫的不一樣，Google 會把這些訊號都當成不可信。
  • 不要指向 noindex、404、或會重新導向的網址：代表網址自己就必須是 200、可以被索引的頁面。
  • 不要用 noindex 或 robots.txt 來「選代表」：noindex 會讓那頁整個從搜尋消失，robots.txt 擋住的網址讀不到 canonical（第 1 節那張圖）。
  • 分頁不要全部指向第一頁：/menu/?page=2 的內容跟第 1 頁不同，不是重複內容，每一頁的 canonical 指向自己。
  • canonical 是建議，不是命令：Google 會綜合重新導向、canonical、sitemap、內部連結判斷。你的內部連結、sitemap 都用代表網址，訊號一致，它才會照你選的。
💡 實務上：canonical 寫在共用 layout，最怕複製貼上寫死
實際專案裡 canonical 不會每頁手寫，而是在共用的 layout 或 SEO 元件裡，由目前的路由統一產生（Nuxt、Next.js 都有對應的 head 管理工具）。常見事故是有人從首頁模板複製一份，canonical 寫死成首頁網址，結果所有頁面都說「代表是首頁」，內頁可能陸續從搜尋消失。像這次換框架的改版，上線前挑幾種頁面（首頁、分類頁、商品頁、帶參數的網址）檢視原始碼，確認每一頁的 canonical 都指向自己，比讀程式碼更快抓到問題。

第一層說「能用 301 合併的就 301」。301 到底告訴搜尋引擎什麼、跟 302 差在哪？改版時改名的那些舊網址、下架的商品，又該回什麼？下一節處理。

改名的舊網址、下架的商品，伺服器該回什麼？

這次改版把冰滴咖啡從 /menu/cold-drip/ 搬到 /menu/coffee/cold-brew/。舊網址還留在別人的部落格、使用者的書籤、Google 的索引裡，有人打開它時，伺服器要回什麼？答案寫在狀態碼（Node 課第 12 課）裡。搜尋引擎下載一個網址，最先看的就是狀態碼：頁面內容寫得再清楚，狀態碼錯了，整頁的意思就錯了。各狀態碼在 Google 的處理方式：

狀態碼意思Google 怎麼處理咖啡店的情境
200成功內容交給索引（不保證收錄）正常頁面
301、308永久移到 Location強訊號：新網址成為代表商品改網址、改版換路由、http → https
302、307暫時移到 Location弱訊號：舊網址可能繼續留在結果裡限時活動頁暫時導到首頁、A/B 測試
404、410找不到／已永久移除不處理內容，已收錄的會移除；Google 對兩者處理相同商品永久下架、沒有替代品
503暫時無法服務放慢爬取，已收錄的頁面暫時保留；持續太久才會移除系統維護，加 Retry-After: 3600（幾秒後再來）
500、502伺服器錯誤同上，放慢爬取要修的事故

冰滴咖啡的情況是「永久換地方」，所以舊網址回 301，Location 指向新網址。搜尋引擎看到永久重新導向，會把新網址當成代表，舊網址累積的連結訊號也跟過去。如果誤用 302，等於說「只是暫時離開」，Google 可能一直把舊網址當代表。

表裡永久、暫時各有兩個碼：301 跟 308 都是永久、302 跟 307 都是暫時。差別在 307／308 規定瀏覽器重送請求時不能把 POST 改成 GET，這對 API 很重要，對 SEO 沒有差別。JavaScript 的 location.href = … 與 <meta http-equiv="refresh"> 也能導向，但要等頁面被下載、甚至被渲染後才看得到，能在伺服器做就在伺服器做。

改版時除了改名，還有一批商品下架了。這裡最常出的錯叫 soft 404：頁面內容寫著「找不到這個商品」，狀態碼卻是 200。對使用者來說看起來沒問題，但搜尋引擎看狀態碼，可能把這頁當成正常頁面收錄。Google Search Console（Google 給網站管理者的後台，第 22 課介紹過）會把這種頁面標成 soft 404。常見來源有三個：SPA 的「找不到」元件（第 25 課）、資料庫查不到資料時仍然用模板渲染出頁面、把所有下架商品 301 到首頁（Google 也可能把這種導向當成 soft 404）。所以商品下架時，要依情況選狀態碼：

  • 暫時缺貨：200，頁面寫「目前缺貨」，網址不變。
  • 永久下架、有明確的替代品（耶加雪菲 2025 年批次 → 2026 年批次）：301 到替代品。
  • 永久下架、沒有替代品：404 或 410，頁面上可以推薦其他商品，但狀態碼要對。
  • 維護中：503 加 Retry-After。不要回 200 的「維護中」頁面，不然維護公告可能取代原本的內容被收錄。

回到上一節的第一層：http、www 這些變化要 301 到代表網址。這裡容易做出重新導向鏈（redirect chain）：A → B → C 要跳好幾次才到終點。Googlebot 最多跟 10 次，但每一跳都多一次往返，使用者等更久；Google 建議直接導到最終網址，真的做不到也盡量不超過 3 次。更糟的是迴圈（A → B → A），永遠到不了，瀏覽器會顯示「重新導向次數過多」。

最常見的鏈是 http → https 一次、再 www → 非 www 一次：http://www.brew.example.tw/menu/ 要跳兩次才到。在 Nginx 把它們合成一次：

server {
    listen 80;
    server_name brew.example.tw www.brew.example.tw;
    return 301 https://brew.example.tw$request_uri;      # http 的兩種主機名稱都一次導到最終網址
}
server {
    listen 443 ssl;
    server_name www.brew.example.tw;
    return 301 https://brew.example.tw$request_uri;      # https 的 www 也一次導到
}

$request_uri 是原本的路徑加查詢字串，這樣 http://www.brew.example.tw/menu/?page=2 會一次到 https://brew.example.tw/menu/?page=2。只寫 return https://… 不加狀態碼時，Nginx 回的是 302，要明確寫 301。

改網址時再做三件事：舊網址的 301 至少保留一年（Google 建議越久越好）；站內連結與 sitemap 直接改成新網址，不要靠導向；每改一次路由就用 curl -sIL 網址 看實際跳了幾次。

💡 實務上：改版換網址前，先做一張新舊網址對照表
網站改版、換框架時，路由常常整批改名，這時要先列出舊網址清單：從舊的 sitemap、Search Console 有流量的頁面、行銷用過的廣告連結收集。每個舊網址對應一個新網址（或決定回 404），把這張表放進專案，部署後用腳本逐一打 curl 確認都是一次 301 到正確位置。特別留意印在實體菜單、海報上的 QR code 網址，那些改不了，導向要一直保留。豆留咖啡這次改版如果先做了這張表，冰滴咖啡這類改名的舊網址，上線前就會逐一確認過導向。

現在每份內容都有唯一的代表網址，改名的舊網址也接上了新網址。剩下的是讓搜尋引擎儘快知道這份新的網址清單，而不是等它慢慢從連結一個一個發現。

修完之後，怎麼把正確的網址清單交給搜尋引擎？

第 1 節提過，搜尋引擎發現網址有兩個來源：別的頁面的連結，和網站自己交出的清單。這份清單就是 sitemap：一份 XML 檔，列出你希望搜尋引擎知道的網址。連結結構完整的小網站沒有它也會被找到；它的用處是讓新頁面、深層頁面更快被發現，並告訴搜尋引擎每頁最後修改的時間（lastmod）。像這次改版，整批網址換新，就是 sitemap 最有用的時候。

<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url><loc>https://brew.example.tw/</loc><lastmod>2026-10-31</lastmod></url>
  <url><loc>https://brew.example.tw/menu/coffee/</loc><lastmod>2026-10-30T09:00:00+08:00</lastmod></url>
  <url><loc>https://brew.example.tw/sets/coffee&amp;cake/</loc></url>
</urlset>

每個 <url> 是一個網址，<loc> 是網址本身。寫的時候注意：

  • 絕對網址：<loc> 寫完整的 https://…。網址是放進 XML 的文字，& 要寫成 &amp;（上例的套餐頁 /sets/coffee&cake/），不然整份 XML 解析失敗。
  • 只列代表網址：這一條把前面幾節串起來。要列的是回 200（第 5 節）、沒有 noindex（第 3 節）、canonical 指向自己（第 4 節）的網址。把 301、404、noindex、?sort= 這類網址放進去，等於一邊說「請收這個」、一邊說「不要收」，給出互相矛盾的訊號，Search Console 會一直回報錯誤。
  • lastmod 要真實：格式是 W3C Datetime（2026-10-31 或帶時區的 2026-10-31T09:00:00+08:00），值是內容真正修改的時間，例如 CMS 裡的 updated_at。每次建置都寫成今天，Google 發現它不可信，之後就不再採用你的 lastmod。
  • Google 忽略 <priority> 與 <changefreq>：不用寫。
  • 上限：一個檔最多 50,000 個網址或 50MB（未壓縮）。超過要拆成多個檔，再用一份 sitemap index 列出它們：
<?xml version="1.0" encoding="UTF-8"?>
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <sitemap><loc>https://brew.example.tw/sitemap-1.xml</loc></sitemap>
  <sitemap><loc>https://brew.example.tw/sitemap-2.xml</loc></sitemap>
</sitemapindex>

寫好之後，讓搜尋引擎找到它有兩個方法。第一是在 robots.txt 寫 Sitemap: https://brew.example.tw/sitemap.xml（第 2 節範例的最後一行）。第二是到 Search Console 的「Sitemap」報表提交，提交之後，會顯示讀到多少網址、有沒有錯誤，事故修完後可以在這裡確認 Google 讀到了新的網址。

sitemap 不該手寫，因為網址會隨商品上下架變動，手寫的清單遲早跟網站不一致，列出已經下架的商品。實務上它由程式從路由表、資料庫的商品清單產生，跟頁面用同一份資料。產生的時間點看網站怎麼渲染：頁面在建置時就產生成靜態 HTML 的網站（SSG），sitemap 也在建置時產生；頁面在每次請求時由伺服器產生的網站（SSR），sitemap 也可以在請求時產生。這兩種渲染方式在 Vue 課第 24 課。練習 2 就是寫這個產生器。

清單裡還有一類網址沒處理：改版新增的英文版 /en/menu/coffee/。它跟中文菜單是同樣的品項、同樣的價格，只是語言不同。照第 4 節的邏輯，它算重複內容、該用 canonical 指回中文版嗎？

英文版算重複內容嗎？用 hreflang 標出語言版本

不算。中文版 /menu/coffee/ 和英文版 /en/menu/coffee/ 是給不同語言的人看的，不是重複內容，不能用 canonical 互指：canonical 的意思是「只收代表」，英文版指向中文版，等於叫搜尋引擎不要收英文版，英文版就從搜尋消失了。

要用的是 hreflang：告訴搜尋引擎「這幾頁是同一份內容的不同語言版本」，讓它依使用者的語言顯示對的那一頁。說英文的人搜尋時看到英文版，說中文的人看到中文版：

<!-- 中文版與英文版的 head 都要放這一整組 -->
<link rel="alternate" hreflang="zh-Hant" href="https://brew.example.tw/menu/coffee/">
<link rel="alternate" hreflang="en" href="https://brew.example.tw/en/menu/coffee/">
<link rel="alternate" hreflang="x-default" href="https://brew.example.tw/menu/coffee/">
  • 互相指向，也要列出自己：中文版列出中文、英文；英文版也列出英文、中文。只有單向時 Google 會忽略，因為單方面宣稱「那頁是我的英文版」可能是別人亂寫的。
  • 語言代碼：ISO 639-1 的兩個字母（zh、en），可以加文字（zh-Hant 繁體、zh-Hans 簡體）與地區（zh-Hant-TW、en-GB）。只寫地區（tw）是錯的，英國是 GB 不是 UK。
  • x-default：使用者的語言都不符合時給哪一頁，通常是預設語言或語言選擇頁。
  • 絕對網址，而且每個版本各自的 canonical 指向自己：英文版的 canonical 是英文版自己，不是中文版。
  • 不要依 IP 或瀏覽器語言自動導向：爬蟲多半從美國、用英文爬，自動導向會讓它看不到中文版。改成在頁面上放語言切換連結。

hreflang 除了寫在 head，還有其他寫法，見課末「補充與查表」。到這裡，事故裡的每一個問題都有了對應的修法：robots.txt 依環境產生、不該被搜尋的頁面用 noindex、staging 加上登入、每頁一個指向自己的 canonical、舊網址一次 301 到新網址、從路由資料產生 sitemap、中英文版用 hreflang 互指。練習會讓你把其中幾項寫成程式，包括一支上線前的檢查腳本。

補充與查表

Google 怎麼處理 robots.txt 本身（Google 文件 2026-10-23 更新）：

  • 最多讀 500 KiB。
  • 通常快取 24 小時，所以改了不會馬上生效。
  • 回 4xx（429 除外）：當成沒有 robots.txt，全部可以爬。
  • 回 5xx 或 429：前 12 小時整站停止爬取，之後最多 30 天沿用上一份成功取得的版本。robots.txt 回 500 會讓整站停爬，所以它要跟首頁一樣被監控。
  • Google 不支援 Crawl-delay，也不支援寫在 robots.txt 裡的 noindex。

Nginx 的 add_header 繼承陷阱：只要某一層（例如第 3 節放 PDF 規則的那個 location）寫了任何 add_header，上一層（server）的 add_header 就全部不繼承了，原本的安全標頭會一起消失。1.29.3 起可以用 add_header_inherit merge; 改變這個行為。改完一樣用 curl -I 確認所有該有的標頭都還在。

hreflang 的其他寫法：除了 head 裡的 <link>，也可以寫在 HTTP Link 標頭或 sitemap 裡，三種方法效果相同，擇一即可。

本課 Google 規則的來源：robots.txt 的處理以 Google 文件 2026-10-23 更新的版本為準；canonical 的規則以 2026-07-10 更新的版本為準；狀態碼的處理以 2026-02-04 更新的版本為準。

練習

練習 1：寫 isAllowed(robotsTxt, userAgent, path)，照 RFC 9309 判斷這個爬蟲能不能爬這個路徑：

  1. 逐行讀：# 之後是註解；欄位名稱（User-agent、Allow、Disallow）不分大小寫；其他欄位（例如 Sitemap）略過。
  2. 連續的 User-agent 行共用同一個群組；出現過規則之後再遇到 User-agent，才是新群組。
  3. 用 userAgent（不分大小寫、整個名稱相同）找群組，同名的群組要合併；一個都沒有才用 * 群組；連 * 都沒有就全部允許。
  4. 在選到的規則裡，找出所有符合 path 的規則，取最長的那條（比規則字串的長度）；一樣長時 Allow 勝。沒有符合的規則就允許。
  5. * 對到任何字元（包括空字串），結尾的 $ 代表網址結尾；路徑區分大小寫；空的 Disallow: 不擋任何東西；/robots.txt 本身永遠允許。
測試有 32 組固定案例（包含 Google 文件的範例）和 200 組隨機案例。

練習 2：寫 buildSitemap(routes, origin)，從咖啡店的路由資料產生 sitemap：

  • 只列出 status 是 200、沒有 noindex、canonical 不存在或（轉成絕對網址後）等於自己的網址。
  • 網址用 new URL(path, origin) 組成絕對網址（中文路徑會變成百分比編碼），放進 <loc> 前做 XML 跳脫（& → &amp;，還有 < > " '）。
  • 有 updatedAt 才輸出 <lastmod>，值照原樣；格式不是 W3C Datetime（2026-10-31，或帶時區的 2026-10-31T09:00+08:00、2026-10-31T01:00:00Z）就丟錯。不能用現在時間（測試期間 new Date()、Date.now() 會丟錯）。
  • 不輸出 priority、changefreq。
  • 回傳 { files: [{ name, xml }] }：50,000 筆以內只有 sitemap.xml（<urlset>）；超過時 sitemap.xml 改成 sitemap index（<sitemapindex>，列出子檔案的絕對網址，可以用第 1 課的 new URL() 組出來），子檔案依序叫 sitemap-1.xml、sitemap-2.xml…，每個最多 50,000 筆。

練習 3：上線前的檢查腳本：寫 auditIndexability(pages)，從爬站工具匯出的資料找出互相矛盾的設定。回傳 { url, code }[]，先依 url、再依 code 排序（一般的字串比較）：

code條件
noindex-in-sitemapnoindex 的頁面卻在 sitemap 裡
noindex-blocked-by-robotsnoindex 的頁面被 robots.txt 擋住（爬蟲看不到 noindex）
soft-404status 是 200，title 卻含「找不到」
canonical-relativecanonical 不是 http:// 或 https:// 開頭
canonical-to-noindex
canonical-to-redirect
canonical-to-non-200		canonical（先用 new URL(canonical, url) 轉成絕對網址）指向清單裡的另一頁，而那一頁是 noindex／有 redirectTo／狀態碼不是 200。同一頁只回報第一個符合的（照這個順序）；指向清單外的網址不判斷
redirect-loop從這頁開始一路跟著 redirectTo（可能是相對網址）走，會回到走過的網址

noindex 的判斷：robotsMeta 或 xRobotsTag 用空白、逗號、冒號切開後（不分大小寫）含有 noindex 或 none。輸入不能修改。

練習 4：使用者從 LINE 分享的連結打開咖啡菜單（網址是 https://brew.example.tw/menu/coffee/?sort=price&utm_source=line）。這頁的 head 有三個問題：兩個 canonical、其中一個是帶著參數的相對路徑、還有 noindex。這是要被搜尋到的菜單頁：只留一個指向乾淨網址的絕對 canonical，拿掉 noindex；再加上 hreflang：zh-Hant 是這頁自己的乾淨網址，en 是 https://brew.example.tw/en/menu/coffee/，x-default 指向中文版。只改 head。

練習 5：想讓結帳頁不出現在搜尋結果，在 robots.txt 寫 Disallow: /checkout，同時在頁面加 <meta name="robots" content="noindex">，會發生什麼？

✓ b。noindex 寫在頁面裡，要被下載才讀得到；robots.txt 讓爬蟲根本不下載。正確做法是只用 noindex（不要 Disallow），真正不該公開的頁面再加上登入保護。a 錯在兩個工具管的是不同步驟，而且會互相抵銷；c 錯在 Google 不會替你修正；d 錯在 robots.txt 只影響爬蟲，不影響使用者。

練習 6：「冰滴咖啡」的網址從 /menu/cold-drip/ 永久改成 /menu/coffee/cold-brew/，舊網址應該怎麼回應？

✓ c。永久改網址用永久重新導向，搜尋引擎會把新網址當代表，舊網址累積的連結訊號也跟過去；站內連結直接改，避免多一次跳轉。a 的 302 是暫時，舊網址可能一直留在結果裡；b 造成兩個網址都有同樣內容，JavaScript 導向還要等渲染；d 讓舊網址的連結與收藏全部失效。

練習 7：staging 網站 staging.brew.example.tw 出現在 Google 搜尋結果裡了。要預防這件事，最可靠的做法是？

✓ b。沒登入就回 401／403，爬蟲拿不到任何內容，人也看不到未發布的功能。a 只是請爬蟲配合，網址仍可能被收錄，而且這行很容易跟著部署到正式環境；c 只保護首頁；d 擋不住：網址會出現在分享的連結、瀏覽器擴充套件、公開的憑證紀錄（Certificate Transparency）裡。

常見錯誤

  • staging 的 Disallow: / 或全站 noindex 帶上正式環境：整站從搜尋結果消失。robots.txt 與 noindex 依環境產生，部署後自動檢查正式環境的 /robots.txt 與首頁的 head；staging 本身用登入保護。
  • noindex 加 robots.txt Disallow：爬蟲讀不到 noindex。要不被索引就只用 noindex。
  • 用 robots.txt 藏後台：robots.txt 是公開的，等於公告後台位置。後台用登入保護。
  • robots.txt 擋住 CSS、JS：Google 看到的是破版或空白的頁面。打包後的資源路徑不要放進 Disallow。
  • canonical 互相矛盾：一頁兩個 canonical、HTML 與 Link 標頭不同、指向 404 或重新導向的網址、分頁全部指向第一頁。每頁一個、絕對網址、指向 200 而且可以被索引的代表網址。
  • sitemap 列出不該列的網址、lastmod 每次建置都是今天：只列代表網址，lastmod 來自內容真正的修改時間。
  • soft 404：不存在的頁面回 200。查不到資料就回 404／410；下架商品不要全部導到首頁。
  • 永久改網址用 302、或留下重新導向鏈：用 301／308 直接導到最終網址，http → https 與 www 在同一次完成。
  • 維護時回 200 的公告頁：回 503 加 Retry-After。
  • 多語系用 canonical 互指，或 hreflang 只有單向：語言版本用 hreflang，每個版本列出全部（含自己）與 x-default。

小結

  • 爬取與索引是兩件事：robots.txt 管「能不能下載」，noindex 管「能不能收進索引」。官網消失是因為 Disallow: / 讓爬蟲什麼都不下載。
  • robots.txt 依 RFC 9309：爬蟲只用一個群組，最長的規則勝出，一樣長時 Allow 勝；* 對任意字元、$ 是網址結尾。它要依環境產生、部署後檢查、跟首頁一樣被監控（回 5xx 會讓整站停爬）。
  • 不想出現在搜尋結果用 noindex，而且不能同時被 robots.txt 擋住；不該公開的東西（後台、staging）靠登入。
  • 重複網址先用 301 合併，剩下的用絕對網址的 canonical，每頁寫指向自己的 canonical；canonical 是建議，所有訊號要一致。
  • 狀態碼表達頁面的真實狀態：永久移動 301／308、暫時 302／307、不存在 404／410、維護 503；避免 soft 404、鏈與迴圈。改版前先做新舊網址對照表。
  • sitemap 從路由資料產生，只列 200、可索引、canonical 指向自己的絕對網址；lastmod 要真實；超過 50,000 筆用 sitemap index；Google 忽略 priority 與 changefreq。
  • 多語系不是重複內容：用 hreflang 互相指向、列出自己，加上 x-default；每個版本的 canonical 指向自己。
