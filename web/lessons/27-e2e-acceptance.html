階段 6：資深整合實戰 · 第 27 課

自動化驗收：Playwright E2E、視覺回歸、無障礙掃描與 flaky test 排查（資深）

前面 26 課教了咖啡店網站「應該長什麼樣子」：語意化的按鈕、有 label 的表單、320px 不會橫向捲動、首圖不 lazy、canonical 是絕對網址。問題是這些東西會在某次改版時悄悄壞掉。上個月的改版就一次出了三件事：

  1. 設計師把「加入購物車」換成只有購物車圖示的按鈕，忘了加 aria-label。看得到的人照樣會點，螢幕閱讀器使用者只聽到「按鈕」，不知道按下去會發生什麼事。
  2. 有人為了「優化效能」把全站圖片都加上 loading="lazy"，連首頁最上面那張主視覺也被延後下載，LCP 變差。
  3. 新的路由設定讓不存在的網址也回 200，搜尋引擎開始收錄一堆空白頁（soft 404）。

三件事都通過了 code review，手動點過也沒發現，上線後才從客服回報與搜尋結果知道，代價是掉訂單和掉排名。這一課的任務：把咖啡店的上線前驗收寫成程式，每個 PR 自動跑，讓這三件事以及同類的問題在合併前就被擋下。學完你會有一套驗收：點餐流程的 E2E 測試、每個公開頁面的無障礙與 SEO 檢查、首頁的截圖比對，也知道這套驗收開始時好時壞時怎麼查。

這課的路線：
  1. 這三件事該用哪一種測試擋、用什麼工具跑：E2E 與元件測試的分工，Playwright 的設定與這課練習的跑法。
  2. 第一件事，按鈕沒有名稱：用 getByRole 找元素讓測試順便驗證可及名稱；畫面晚一點才更新時，用會自動等待的斷言，不用 waitForTimeout。
  3. 流程沒碰到的地方，以及第二、三件事：axe 掃無障礙，再對每個路由檢查狀態碼、noindex、canonical、首圖設定。
  4. DOM 都對、畫面卻壞了：視覺回歸怎麼截圖比對又不被雜訊淹沒。
  5. 驗收本身時好時壞：flaky test 怎麼找根因，最後放進 CI 變成合併前的關卡。
這課會用到：

這三件事該用哪一種測試擋？

你在 Vue 課第 22 課寫過元件測試，第一個直覺可能是：替「加入購物車」按鈕寫個元件測試就好。這對第一件事有一點用，但第二、三件事它完全碰不到。元件測試只把一個元件掛在 Node 裡模擬的 DOM（happy-dom）上：沒有伺服器，所以不知道 404 網址回了什麼狀態碼；沒有真的版面，所以不知道哪張圖在第一個畫面內；也沒有路由與其他頁面。這三件事都是「各部分接起來之後」才看得到的問題。

能看到這些的測試叫 E2E 測試（end-to-end test，端對端測試）：用真的瀏覽器，從使用者的角度操作整個網站，打開網址、點連結、填表單、送出，最後確認畫面出現該出現的東西。網站是真的建置、真的由伺服器提供，CSS、路由、跨頁的 sessionStorage 全都在。

那為什麼不乾脆全部寫成 E2E？因為「真實」是有代價的。一個 E2E 測試要開瀏覽器、等網路、等渲染，一跑就是幾秒，元件測試只要幾毫秒；它失敗時只告訴你「流程某一步不對」，要再去翻執行紀錄才知道是哪個元件、哪個請求出錯；牽涉的東西越多，就越容易因為網路慢一點、動畫沒跑完而時過時不過。業界用「測試金字塔」描述這個取捨：

兩種測試並排比較：

所以 E2E 只留給「壞了會直接損失營收或信任」的流程。咖啡店挑這 5 條，開場的三件事都落在裡面：

  1. 首頁 → 線上點餐 → 選品項與杯型 → 加入購物車 → 結帳 → 看到訂單編號（第一件事會在這裡被抓到）
  2. 手機寬度的主選單打得開、連結點得到
  3. 菜單頁與門市頁可以打開，價格、地址、營業時間有出現
  4. 每個公開頁面的 SEO 設定與無障礙掃描（第二、三件事；這課的練習 2）
  5. 首頁、菜單頁在手機與桌機寬度的截圖跟基準圖一致

反過來，「電話少一碼時顯示哪個錯誤訊息」「大杯加 20 元算得對不對」這種有很多組合的規則，放在單元或元件測試：一樣的覆蓋率，快幾百倍，壞掉時直接指到出錯的函式。如果用 E2E 測二十種電話格式，就是二十次開頁面、填表單，CI 多跑好幾分鐘，換來的資訊跟一個毫秒級的單元測試一樣。資深的判斷是：E2E 證明各部分接得起來，細節的正確性交給下層。

💡 實務上：E2E 清單要跟 PM 一起定，而且要有人顧
常見的情況是 PM 或主管說「每個功能都要有 E2E」，半年後 CI 跑很久、一半的測試沒人敢刪。資深工程師會先問：「這條流程壞了，誰會在什麼時候發現？損失多少？」點餐、結帳、登入這種答案是「客人馬上走掉」的才進清單。E2E 還需要一個能重複使用的測試環境：固定的商品資料、可以一直下單的測試帳號、不會真的扣款的金流，這通常要跟後端或維運一起準備，排時程時別漏掉。每條 E2E 也要有負責人，壞了才有人修。

用什麼開真的瀏覽器？Playwright 的組成與設定

決定了要寫 E2E，接下來需要一個能用程式開瀏覽器、操作頁面、檢查結果的工具。這課用 Playwright：微軟維護的瀏覽器自動化工具，一套 API 可以操作 Chromium、Firefox、WebKit 三種瀏覽器引擎（版本與 Node 需求見課末）。它分成兩層：

  • 瀏覽器操作的 API：chromium.launch() 開瀏覽器、browser.newContext() 開一個瀏覽器 context、context.newPage() 開分頁，再用 page 操作。
  • 測試執行器（test runner）：npx playwright test 找出 *.spec.ts、平行執行、重試、產生報告。每個測試自動拿到一個全新的 context 與 page。

中間那個 瀏覽器 context 值得先弄懂，後面好幾個地方會用到。它像一個全新的無痕視窗：cookie、localStorage、sessionStorage 都跟別的 context 分開。為什麼需要它？咖啡店的購物車存在 sessionStorage 裡，如果兩個測試共用同一個瀏覽器狀態，前一個測試加進購物車的拿鐵會留到下一個測試，後面那個測試就會看到「購物車：2 件」而失敗，而且失敗與否取決於誰先跑。每個測試一個新 context，就是讓每個測試都從「一個剛打開網站的新客人」開始。開一個 context 很便宜，不需要重開整個瀏覽器。

一般專案的設定檔長這樣（你的 Vue 專案會寫在根目錄的 playwright.config.ts）：

import { defineConfig, devices } from '@playwright/test'

export default defineConfig({
  testDir: './e2e',
  retries: process.env.CI ? 1 : 0,          // 重試的用法在後面 flaky 那節
  reporter: [['html', { open: 'never' }]],  // 產生 playwright-report/；不設的話只在終端機印結果（CI 上是 dot）
  use: {
    baseURL: 'http://localhost:4173',       // 測試裡寫 page.goto('/order/') 就好
    trace: 'on-first-retry',                // 第一次重試時錄下 trace
    locale: 'zh-TW',
    timezoneId: 'Asia/Taipei',              // 時間、日期格式不受 CI 機器所在地影響
  },
  projects: [                               // 同一批測試，用不同的裝置各跑一次
    { name: 'desktop', use: { ...devices['Desktop Chrome'] } },
    { name: 'mobile', use: { ...devices['Pixel 7'] } },
  ],
  webServer: {                              // 測試前先把網站跑起來，跑完自動關掉
    command: 'npm run build && npm run preview',
    url: 'http://localhost:4173',
    reuseExistingServer: !process.env.CI,   // 本機已經開著就直接用
  },
})

現在只要看懂三件事，其他設定在用到的小節再講。webServer 讓 Playwright 在測試前自己建置並啟動網站，測試的對象就是會部署出去的那份建置結果，不是開發模式的伺服器。baseURL 讓測試只寫路徑，同一份測試換個網址就能對測試環境跑。projects 讓同一批測試在桌機與手機的裝置設定下各跑一次，手機選單這類只在窄螢幕出現的問題才抓得到。retries 與 trace 是為了時好時壞的測試準備的，在 flaky 那一節才會用到。

工具準備好了，開始寫點餐流程的測試。第一個要解決的問題是：怎麼在頁面上找到「加入購物車」，而且找的方式要在它變成只有圖示時失敗。

第一件事：按鈕只剩圖示，測試怎麼會發現？

要操作按鈕，測試得先「找到」它。Playwright 裡描述「怎麼找到元素」的東西叫 locator。它不是元素本身，而是一個查詢條件：建立時不會去查 DOM，每次拿它做動作或斷言時才重新查一次。

const add = page.getByRole('button', { name: '加入購物車' })   // 這行不會查 DOM
await add.click()                                                // 這時才找，找到後點擊

為什麼要設計成「用到時才查」？Vue 的頁面會一直重新渲染：加入購物車之後，商品卡可能整塊被換成新的 DOM 節點。如果 locator 在建立時就抓住某個節點，重新渲染後它抓著的是已經不在頁面上的舊節點，操作就會失敗。每次重新查詢，同一個 locator 就總是對到「現在畫面上符合條件的那個元素」。

回到第一件事。找元素的方式有好幾種，差別在「用什麼特徵認元素」。越前面的越接近使用者怎麼認東西：

寫法找的是什麼時候用
getByRole('button', { name: '加入購物車' })role 與可及名稱（第 2 課）按鈕、連結、標題、表單元件、landmark：大部分情況
getByLabel('電話')label 對應的表單欄位輸入框
getByText('訂單已成立')畫面上的文字沒有互動的文字內容
getByTestId('cart-count')data-testid 屬性真的沒有使用者看得到的特徵時（例如圖表的某一塊）
locator('.add-to-cart')CSS 選擇器盡量不用：跟實作細節綁死

把兩種寫法放到開場那次改版裡比較。設計師把按鈕改成只有購物車圖示、忘了 aria-label，按鈕的可及名稱變成空的，螢幕閱讀器只會唸「按鈕」。這時 getByRole('button', { name: '加入購物車' }) 找不到任何元素，測試失敗，PR 被擋下。用 locator('.add-to-cart') 的測試呢？class 沒變，照樣找到、照樣點擊、照樣通過，問題上線。getByRole 的好處不只是「class 改名不會壞」，而是測試順便驗證了可及名稱：測試用螢幕閱讀器使用者認按鈕的方式找按鈕，它找不到，就代表那些使用者也找不到。

name 的比對預設是寬鬆的（包含即可、不分大小寫），需要更精確時有其他寫法，見課末。

表單欄位用 getByLabel，不用 getByRole('textbox', { name: '電話' })。原因在可及名稱的計算規則：欄位沒有 label 時，瀏覽器會退而用 placeholder 當名稱，所以只有 placeholder、沒有 label 的欄位，getByRole 照樣找得到。但 placeholder 一輸入就消失，不能取代 label（第 4 課）。getByLabel 只認 <label>、aria-labelledby、aria-label，結帳表單的 label 被拿掉時測試就會失敗，跟按鈕失去名稱是同一類問題、同一個抓法。

一次只能對到一個：strict mode

用 getByRole 找「加入購物車」，在點餐頁馬上會遇到一個問題：點餐頁有美式、拿鐵、卡布奇諾三區，每區都有一個「加入購物車」。page.getByRole('button', { name: '加入購物車' }).click() 會丟出 strict mode violation … resolved to 3 elements。這是 Playwright 的 strict mode：一個要拿來操作的 locator 必須剛好對到一個元素，對到多個時它不會猜你要哪一個，直接報錯。

正確的做法是先縮小範圍，就像使用者會先看「拿鐵」那一塊，再按那一塊裡的按鈕：

// <section aria-labelledby="p-latte"><h2 id="p-latte">拿鐵</h2>…</section>
// 有名稱的 section 的 role 是 region，名稱來自 aria-labelledby 指到的標題
const latte = page.getByRole('region', { name: '拿鐵' })
await latte.getByRole('radio', { name: '大杯' }).check()
await latte.getByRole('button', { name: '加入購物車' }).click()

// 沒有 landmark 可以用時，用文字過濾：
page.getByRole('listitem').filter({ hasText: '拿鐵' })

locator 可以串接：latte.getByRole(…) 只在拿鐵那一區裡找。不要用 .first()、.nth(1) 解決 strict mode 的錯誤：它們靠的是順序，菜單順序一改，測試就點到別的商品，而且還是會通過，比直接失敗更糟。

💡 實務上：用文字找元素，文案改了測試就要跟著改
getByRole 靠的是可及名稱，通常就是按鈕上的文字，行銷把「加入購物車」改成「放進購物車」，測試就紅了。這是預期中的代價：使用者看到的東西變了，驗收本來就該被提醒。團隊的做法是讓文案修改也走 PR，同一個 PR 一起改測試，而不是退回用 class 或 data-testid 找元素。網站有多語系時，E2E 通常固定用一種語系跑，不然每換一種語言就要多寫一套文字；其他語系另外檢查翻譯有沒有漏。

找到拿鐵區的按鈕、點下去之後，下一步是確認購物車變成「購物車：1 件」。但購物車的數字要等 API 回應、Vue 重新渲染才會變，測試什麼時候去檢查才對？

點了之後畫面還沒更新，測試要等多久？

這是 E2E 最常寫錯的地方。點擊之後，畫面更新需要時間：本機可能 0.3 秒，CI 機器同時跑很多工作時可能 3.5 秒。直覺的寫法是「等 3 秒再檢查」，但這同時犯了兩個錯：本機白等 2.7 秒，CI 慢一點又不夠等。

Playwright 的答案是 web-first assertion：會自己重試的斷言。await expect(locator).toHaveText('購物車：1 件') 不是「現在檢查一次」，而是「一直重新查元素、比對文字，直到成立」，超過逾時（預設 5 秒）才算失敗。畫面 0.3 秒更新，它 0.3 秒就繼續；3.5 秒才更新，它也等得到。

問題是，有些寫法看起來也在檢查，實際上不會等。左欄都是常見的寫法：

不會等待（容易時好時壞）會等待
await page.waitForTimeout(3000)直接寫下一個 expect，讓它等
expect(await status.textContent()).toBe('購物車：1 件')await expect(status).toHaveText('購物車：1 件')
if (await submit.isVisible()) await submit.click()await submit.click()（點擊前會等元素出現、可見、穩定、可以點）
expect(await list.count()).toBe(3)await expect(list).toHaveCount(3)

分辨的關鍵在 await 的位置。expect(await x.textContent()) 先 await 讀一次值，這時拿到的是一個普通字串，再拿這個不會變的字串去比對；畫面晚 0.1 秒更新，字串也不會跟著變，斷言就失敗了。await expect(x).toHaveText() 把 locator 本身交給斷言，斷言才有辦法反覆重新讀。isVisible() 也是只看「現在這一刻」：結帳頁的「送出訂單」按鈕 0.5 秒後才出現時，它回傳 false，if 就整段跳過，測試沒點到按鈕卻可能照樣往下跑。Playwright 的文件對 waitForTimeout 的說明是只用來除錯，寫在正式測試裡本質上就是 flaky。

動作本身（click、fill、check）也會等：先確認元素可見、沒有在動畫中移動、沒有被別的元素蓋住、不是 disabled，才真的點下去。沒有找到元素時一直等到動作的逾時。所以寫點餐流程時，你幾乎不用自己寫任何等待：每一步要嘛是會等的動作，要嘛是會等的斷言。

到這裡，點餐流程的測試已經能抓到第一件事（練習 1 就是把整條流程寫完）。但 getByRole 只檢查了流程碰到的那幾個元素；首頁上某張圖片沒有替代文字、某段文字對比不足，流程測試不會知道。

流程沒碰到的元素，無障礙問題誰來抓？axe 當成關卡

逐一替每個元素寫斷言不實際，這正是 第 5 課 axe-core 的用途：它依一組規則檢查整個 DOM，找出沒有替代文字的圖片、沒有名稱的按鈕、對比不足的文字等問題。第 5 課是在瀏覽器裡手動跑；@axe-core/playwright 把它接進 Playwright，在測試裡對當下的頁面掃描，結果就能變成測試的成敗：

import { AxeBuilder } from '@axe-core/playwright'

const context = await browser.newContext()   // AxeBuilder 的 page 必須從 newContext() 建立
const page = await context.newPage()         // 直接 browser.newPage() 會丟錯
await page.goto(url)
const result = await new AxeBuilder({ page })
  .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
  .analyze()
// result.violations：[{ id: 'button-name', help: '…', nodes: [{ target: ['…'] }] }, …]

result.violations 是違規清單，每一筆有規則 id（例如開場第一件事會觸發的 button-name）、說明，以及出問題的元素。驗收的寫法就是「這個陣列必須是空的」。在 Playwright 的測試執行器裡，測試函式從參數拿到的 page 本來就是從 context 建立的，可以直接用；自己開瀏覽器時才要注意上面註解寫的限制。

最容易寫錯的是 withTags。它選擇要跑哪些規則：axe 的每條規則都標了「出自 WCAG 哪個版本的哪個等級」，例如 wcag2a 是 WCAG 2.0 的 A 級、wcag21aa 是 2.1 新增的 AA 級。關鍵是這些標籤不會往前包含：wcag22aa 只代表「2.2 新增的 AA 規則」，不包含 2.0、2.1 的規則。只寫 wcag22aa 的話，實際只跑了極少數規則（axe-core 4.14.0 裡只有 target-size 一條），button-name、image-alt、color-contrast 全都沒跑，掃描結果是「0 個違規」，看起來很安全，其實什麼都沒檢查。所以要達到 WCAG 2.2 AA，要把 2.0、2.1、2.2 的 A 與 AA 都列出來，像上面那樣。各標籤包含哪些規則，查表見課末。

把 axe 放進驗收時還有三件事要想清楚。第一，互動之後要再掃一次。axe 只看得到「掃描那一刻」的 DOM：手機選單打開後的連結、表單送出後的錯誤訊息、彈出的對話框，在頁面剛載入時都不存在，所以只在載入時掃，這些狀態永遠沒被檢查。E2E 流程走到那一步，再掃一次；可以用 .include('#menu') 只掃新出現的區塊。

第二，已知問題列為例外並追蹤，不要關掉規則。某條規則一直報錯時，最省事的是 .disableRules(['color-contrast'])，但這讓整個網站之後新增的對比問題也抓不到，關卡就破了一個洞。第三方元件（例如地圖）暫時修不了時，用 .exclude('.map-embed') 只排除那一塊，旁邊寫上追蹤的 issue 編號與預計處理日期。

第三，axe 通過不代表可以用。第 5 課講過，自動規則抓不到「Tab 順序合不合理」「焦點有沒有被困住」「替代文字寫得對不對」。關鍵流程另外用鍵盤走一次，E2E 也能做：await page.keyboard.press('Tab') 之後 await expect(link).toBeFocused()。

💡 實務上：舊網站第一次掃出一大堆問題時
在已經上線的網站第一次接 axe，常常一掃就是幾十、幾百個違規，要求「全部修完才能合併」只會讓整個關卡被關掉。比較實際的做法是分兩步：新頁面、新元件從第一天就必須零違規；舊頁面先把目前的違規記成清單，關卡只擋「比清單多出來的新問題」，再照流量高低排進排程慢慢清。跟 PM 溝通時說清楚：這是讓問題不再變多，不是已經符合無障礙規範。

axe 把無障礙這一類收進了關卡。但開場的第二、三件事（首圖被 lazy、404 回 200）不是無障礙問題，axe 不會報，要自己寫檢查。

第二、三件事：首圖被 lazy、404 回 200，怎麼每一頁都檢查？

這兩件事有個共同點：它們都是「設定」出錯，而且對網站每一頁都可能發生。第 21～24 課（效能預算、SEO 基礎、技術 SEO、結構化資料）教過的檢查都可以寫成程式，所以做法是：準備一份路由清單，對每個路由跑同一組檢查。路由清單從 sitemap 或路由設定產生，再加上幾個刻意不存在的網址，專門確認 404 真的是 404，第三件事就是靠這幾個網址抓到的。

每個路由要檢查的項目：

檢查怎麼讀出錯時的後果
狀態碼const res = await page.goto(url)、res.status()不存在的頁面回 200（soft 404），搜尋引擎收錄一堆空頁
404 頁有 noindexmeta[name="robots"] 或 X-Robots-Tag 標頭錯誤頁出現在搜尋結果
title 不重複每頁的 await page.title()，全部跑完再比搜尋結果裡分不出哪一頁是哪一頁
canonical讀 DOM 裡所有 link[rel="canonical"]：恰好一個、絕對網址、指向自己排名算到錯的網址上
JSON-LD每個 script[type="application/ld+json"] 的文字 JSON.parse一個逗號就讓整段結構化資料失效
首屏圖片沒有 lazy圖片的 boundingBox() 在第一個畫面內，loading 不是 lazyLCP 圖片延後下載，LCP 變差

最後一列就是第二件事的抓法，值得多看一眼。「首圖不能 lazy」不能寫成「第一張 <img> 不能 lazy」：第一張在 HTML 裡的圖可能是頁首的 logo，主視覺在後面。真正的條件是「在第一個畫面內」，這要有真的版面才知道，所以用 boundingBox() 拿圖片在頁面上的位置，跟視窗高度比較。這也是為什麼這類檢查要在真的瀏覽器裡做，元件測試做不到。

寫這些檢查時有兩個常見的錯。第一個是用正規表示式讀 HTML，而不是讀 DOM。(await page.content()).match(/rel="canonical" href="(.*?)"/) 只拿到第一個 canonical，頁面不小心有兩個時照樣通過；屬性順序換了（href 寫在 rel 前面）就找不到。page.locator('link[rel="canonical"]').evaluateAll(els => els.map(el => el.getAttribute('href'))) 一次拿到全部，再檢查是不是恰好一個。這裡用 CSS 選擇器是對的：前面說盡量不用 CSS 選擇器，是針對使用者會操作的元素；head 裡的元素沒有 role，使用者也看不到，本來就只能用選擇器找。

第二個是用會等待的 API 去讀可能不存在的元素。上一節的「會等待」在這裡反而是問題：locator.getAttribute() 找不到元素時會一直等到逾時，一個沒有 canonical 的頁面就讓整個檢查卡住幾十秒，而你本來只是想知道「有沒有」。「可能有、可能沒有」的東西用 evaluateAll、allTextContents()、count()，它們不等待，沒有就是空陣列或 0。

效能的部分要分清楚分工。第 21 課的 Lighthouse CI 已經負責 LCP、TBT 這類數字的預算，但這些數字受機器快慢影響，每次跑都會有誤差。E2E 這邊補的是「設定有沒有被改壞」這類確定性的檢查：首圖不 lazy、有 fetchpriority="high"、有寬高。它們不受機器快慢影響，不會時好時壞，而第二件事正是這一類，它在 LCP 數字明顯變差之前就能被抓到。

最後，回報格式也是設計的一部分。檢查跑完要讓人一眼看出哪一頁、哪個問題：每個路由一筆 { route, problems }，每個問題開頭寫固定的代碼（canonical、jsonld…）再接說明。CI 可以用代碼統計、把結果留言到 PR，人看說明就知道怎麼修。練習 2 就是照這個格式寫完整套檢查。

到這裡，開場的三件事都有關卡了。但這些檢查都在讀 DOM 與 HTTP 回應；CSS 改壞了，DOM 一點都沒變，它們全都會通過。

DOM 都對、畫面卻壞了：視覺回歸怎麼比對？

開場那三件事之外，還有第四類同樣會悄悄上線的問題，前面的檢查都看不到：菜單頁的商品卡在 768px 疊在一起、首頁「線上點餐」按鈕在深色模式下邊框不見、門市頁的地圖被另一個元素的 padding 擠到看不見的位置。DOM 結構、文字、可及名稱全都正確，只是畫出來不對。要抓這類問題，只能直接比對畫面。

視覺回歸測試（visual regression test）就是做這件事：把頁面截圖，跟之前存好、有人確認過的截圖逐像素比對，差太多就失敗。那張「之前確認過的截圖」叫基準圖（baseline）。「回歸」指的是原本好好的東西退回壞掉的狀態，視覺回歸測試就是抓「畫面跟上次確認的不一樣了」。

test('首頁外觀', async ({ page }) => {
  await page.goto('/')
  await expect(page).toHaveScreenshot('home.png', { fullPage: true })
})

這個斷言的生命週期是這樣的。第一次跑時還沒有基準圖：Playwright 把這次的截圖存成基準圖，但這個測試算失敗，避免 CI 在沒有人看過的情況下「通過」（相關的預設值見課末）。基準圖預設存在測試檔旁邊的「測試檔名-snapshots/」資料夾（例如 home.spec.ts-snapshots/），檔名帶專案名稱與作業系統，例如 home-mobile-linux.png，所以桌機和手機、不同作業系統各有一張。之後每次跑都跟它比對。畫面有意改變時，用 npx playwright test --update-snapshots（-u）更新基準圖，連同程式一起送 PR，由審查的人看新舊圖的差異。失敗時 HTML 報告會並排顯示基準圖、實際截圖與差異圖。

toHaveScreenshot 本身也是 web-first assertion：它會連續截圖，等到畫面穩定（連續兩張相同）才比對，所以頁面還在載入時不會急著截。

視覺回歸最大的問題是雜訊：程式沒變，截圖卻不一樣。首頁右上角顯示目前時間，每分鐘都不同；推薦商品每次隨機排序；輪播停在哪一張取決於截圖的時間點。不處理的話，每個 PR 都會失敗，大家很快就不再相信它。每一種雜訊來源都要先固定下來：

雜訊來源做法
動畫、轉場（第 17 課）、輸入框的游標閃爍toHaveScreenshot 預設 animations: 'disabled'（有限的動畫直接跳到結束，無限的動畫回到初始狀態）、caret: 'hide'；網站自己用 JavaScript 做的輪播不在此列，要另外處理
目前時間、倒數計時await page.clock.setFixedTime('2026-11-01T14:32:00+08:00') 固定時鐘；或遮住、隱藏那一塊
隨機推薦、廣告、使用者頭像測試資料固定（測試環境的 API 回固定內容）；做不到時用 mask 遮住
字型與反鋸齒不同作業系統畫出的字不一樣：基準圖要在跟 CI 相同的環境產生，例如官方映像 mcr.microsoft.com/playwright:v1.64.1-noble；網頁字型自己提供，不用系統字型
時區、語系設定檔的 timezoneId、locale
載入中狀態、骨架畫面等資料載入完成再截圖；骨架的尺寸不要依視窗高度變動

能固定的都固定之後，剩下真的每次會變的區塊（例如做不到固定資料的推薦商品），用 mask 遮住，再給一點容許差異：

await expect(page).toHaveScreenshot('home.png', {
  mask: [page.locator('[data-visual-mask]')],   // 這些區域蓋上一塊粉紅色（#FF00FF）再比對
  stylePath: 'e2e/screenshot.css',              // 截圖時額外套用的樣式：隱藏時間、停止輪播
  maxDiffPixelRatio: 0.01,                      // 最多 1% 的像素可以不同
})

mask 跟隱藏不一樣：被遮住的區域還在版面上，大小、位置照樣會被比對（區塊突然變寬，周圍的內容會移動，照樣抓得到），只是裡面的內容不比。遮罩範圍要剛好：遮整頁等於沒測。maxDiffPixels／maxDiffPixelRatio 容許少量差異，但開太大會漏掉真正的問題（一個按鈕的文字消失可能只占 0.3% 的像素）。

還有一個容易誤會的地方：animations: 'disabled' 只在 toHaveScreenshot 這個斷言裡生效。page.screenshot() 的預設是 'allow'（不處理動畫），Storybook 之類的截圖工具也不會幫你停；時間、骨架高度這些也不是動畫。所以截圖時要停掉動畫、隱藏時間，網站或測試還是要自己處理，有兩種放法。第一種是上面的 stylePath：一份只在測試裡套用的 CSS，網站程式完全不用改。第二種是在網站的 CSS 裡留一個開關，測試在載入前用 page.addInitScript(() => document.documentElement.setAttribute('data-test-mode', '')) 打開：好處是開發時在 DevTools 加上這個屬性就能看到截圖時的樣子，Storybook 等其他截圖工具也能共用；代價是網站裡有一段只給測試用的 CSS。咖啡店的團隊選了後者，練習 3 就是寫這段 CSS。

💡 實務上：視覺回歸只截少數穩定的頁面
改版期間畫面每週都在變，這時加視覺回歸只會讓每個 PR 都在更新基準圖，大家習慣不看差異就直接加 -u 更新，等於沒測。比較適合的時機是設計系統的元件、首頁、菜單頁這種已經穩定、又很多人看的畫面。審查 PR 時要真的打開新舊圖的差異看，基準圖的改動跟程式碼一樣要有人負責核准。如果團隊已經用 Storybook 管元件，元件層級的截圖放那裡，E2E 只截整頁。

到這裡，驗收套件完整了，也開始每天在 CI 上跑。幾週後出現了新的問題：同一個測試，程式沒有改，有時過、有時不過。

驗收開始時紅時綠：flaky test 怎麼找根因？

程式沒變、測試卻時過時不過，這種測試叫 flaky test。它的傷害比看起來大，而且是慢慢累積的：大家開始習慣「紅了就重跑」；某天真的壞掉時，也被當成運氣不好重跑到過；CI 時間被重跑吃掉；最後沒人相信測試，這一課建起來的關卡就形同虛設。

最常見的第一反應是加重試。Playwright 設定 retries 後，失敗的測試會自動再跑；第一次失敗、重試通過的測試在報告裡標成 flaky（不是 passed），所以重試至少讓你看得見它。重試可以當成暫時的止血，讓團隊不被卡住，但每一個 flaky 都要有人追根因，因為「時好時壞」一定有原因。常見的原因可以分成這幾類：

類型症狀根因與修法
等待CI 比較常失敗，本機很少固定時間等待、先讀值再比對、isVisible() 加 if：換成 web-first assertion
測試資料共用平行執行時才失敗兩個測試同時改同一個帳號的購物車：每個測試建立自己的資料（不同的使用者、訂單），不要共用
順序依賴單獨跑會過，整批跑會失敗（或反過來）測試 B 依賴測試 A 留下的狀態：每個測試自己準備需要的狀態；用 --shuffle 打亂順序找出來
動畫與版面點擊落空、截圖差幾個像素點到正在移動的元素、捲動中截圖：等元素穩定、測試模式停掉動畫
外部服務某個時段集中失敗測試連到真的金流、地圖、分析服務：用 page.route() 攔截請求、回固定的假資料
時間與時區每天固定時段、月底失敗「今天的營業時間」跨午夜就變了：固定 page.clock 與 timezoneId

表上的修法大多是前面幾節已經做過的事：web-first assertion、每個測試一個新 context、截圖前停掉動畫、固定時鐘與時區。flaky 多半是這些原則在某個地方被漏掉了。排查的步驟：

  1. 先重現：npx playwright test order.spec.ts --repeat-each 30 同一個測試連跑 30 次；加 --workers 4 製造平行的壓力。重現不了的 flaky 很難確定修好了。
  2. 看 trace：trace 是 Playwright 錄下的執行過程，每個動作前後的 DOM 快照、截圖、網路請求、console 訊息都在裡面。設定 trace: 'on-first-retry' 後，CI 第一次重試時會錄下來，trace 檔會附在 HTML 報告（playwright-report/）裡；把報告上傳成 CI 的產出檔，下載後用 npx playwright show-report 打開，點進失敗的測試就能逐步看 trace：失敗那一刻畫面上是什麼、請求回了什麼。單獨的 trace 檔用 npx playwright show-trace trace.zip 打開。
  3. 對照分類表修根因，再用 --repeat-each 驗證。
  4. 量化：記錄每個測試的 flaky 比例。CI 上可以加 --fail-on-flaky-tests（設定檔的 failOnFlakyTests），讓「重試才通過」也算失敗，逼團隊處理。

修不了的先隔離（quarantine）：從必須通過的關卡移到另一個每天跑的工作，開 issue、指定負責人與期限。不要讓它留在主線上用重試蓋住，也不要直接刪掉。

flaky 處理好了，最後一步是讓整套驗收真的擋得住合併。在本機跑、偶爾手動跑都不算關卡：開場的三件事當初就是沒人跑檢查才上線的。

怎麼讓驗收真的擋住合併？放進 CI

CI 的基本做法在DevOps 課第 15 課。E2E 的工作通常長這樣（GitHub Actions）。注意它在官方的 Playwright 容器映像裡跑：瀏覽器與字型都固定，視覺回歸那一節說的「基準圖要在跟 CI 相同的環境產生」才做得到：

e2e:
  runs-on: ubuntu-latest
  container: mcr.microsoft.com/playwright:v1.64.1-noble   # 版本跟 @playwright/test 相同
  steps:
    - uses: actions/checkout@v7
    - uses: actions/setup-node@v7
      with: { node-version: 24 }
    - run: npm ci
    - run: npx playwright test --fail-on-flaky-tests
      env: { CI: 'true' }
    - uses: actions/upload-artifact@v7
      if: ${{ !cancelled() }}                                # 失敗時更需要報告與 trace
      with: { name: playwright-report, path: playwright-report/ }

幾個細節對應前面的小節：CI: 'true' 讓設定檔裡的 retries 與 reuseExistingServer 切換成 CI 的行為；--fail-on-flaky-tests 讓重試才通過也算失敗；最後一步在測試失敗時也會執行，把報告與 trace 上傳成產出檔，PR 上留言附連結，審查的人不用自己重跑就能看失敗那一刻的畫面。

但工作會跑還不夠，還要把它設成合併前必須通過的檢查（branch protection）：沒通過，PR 的合併按鈕就按不下去。這一步做了，E2E 才真的是關卡。回到開場：圖示按鈕會讓點餐流程的 getByRole 找不到元素、首圖 lazy 會被 lcp-lazy 檢查報出來、404 回 200 會被 status 檢查報出來，三件事都會停在 PR 上，不會再等到客人發現。

getByRole 的 name 怎麼比對

name 預設是「包含、不分大小寫」的比對：{ name: '購物車' } 也會對到「加入購物車」。要完全相同加 exact: true。也可以傳正規表示式：{ name: /^大杯/ }。對到太多元素時（strict mode 報錯），先考慮縮小範圍，再考慮改比對方式。

練習

練習 1、2 在自己的電腦上做（準備步驟在「這課的練習怎麼跑」），練習 3 在頁面上做。

練習 1：在 order.e2e.ts 寫 checkOrderFlow(page, baseUrl)，驗收點餐流程：打開首頁 → 點主選單的「線上點餐」→ 在「拿鐵」那一區選「大杯」→ 按「加入購物車」→ 確認購物車顯示「購物車：1 件」→ 點「前往結帳」→ 填寫姓名與電話（欄位用 getByLabel 找）→ 按「送出訂單」→ 確認畫面出現訂單編號（A 加 4 位數字，例如 A1024）。只能用 getByRole、getByLabel、getByText（可以串接、可以 .filter()）找元素，用 web-first assertion 確認結果；不能用 waitForTimeout、setTimeout、page.$()／$eval、locator('CSS 選擇器')、getByPlaceholder／getByTestId。隱藏測試會拿 5 個網站跑你的函式：正確的網站、「送出訂單」按鈕 2 秒後才出現的網站必須通過；按鈕只剩圖示沒有名稱、購物車數量不更新、送出後沒有訂單編號、電話欄位沒有 label 的網站必須失敗。另外會確認伺服器真的收到一筆「拿鐵、大杯、1 杯」的訂單。

練習 2：在 a11y-seo.e2e.ts 寫 auditPublicPages(context, baseUrl, routes)。routes 是 { path, status: 200 | 404 }[]，對每個路由回傳一筆 { route: path, problems: string[] }，沒有問題就是空陣列，每個問題以代碼開頭：狀態碼跟預期不同 → status；預期 404 的路由沒有 noindex → noindex。下面這些只對預期 200 的路由檢查：title 跟其他路由重複 → 每個重複的路由都回報 duplicate-title；canonical 不是恰好一個、不是絕對網址或路徑不是自己 → canonical；JSON-LD 不能解析 → jsonld；首屏（第一個畫面內）的圖片有 loading="lazy" → lcp-lazy；用 AxeBuilder（WCAG 2.0／2.1／2.2 的 A 與 AA 標籤）掃描，每個違規回報 axe:規則 id。用題目傳入的 context 開 page，同一時間最多開 3 個，檢查完要關掉。隱藏測試會用正確的網站與兩個壞掉的網站（JSON-LD 語法錯誤、首圖 lazy、title 重複、按鈕沒有名稱、404 回 200；canonical 指到別頁、canonical 是相對路徑、canonical 有兩個、文字對比不足、404 頁沒有 noindex）檢查：該報的要報，沒壞的路由不能誤報。

練習 3：讓首頁適合截圖比對，只在 <html data-test-mode> 時生效，一般使用者看到的畫面與動畫都不變（輪播、骨架閃動、按鈕的 transition、目前時間都要保留）。測試模式下：(1) 頁面上所有元素與 ::before／::after 的動畫與 transition 都停止（animation-name 是 none 或 animation-play-state 是 paused；transition-duration 是 0s）；(2) 目前時間 <time> 看不到，但位置與大小不變，版面不移動；(3) 骨架畫面 .skeleton 的高度固定 160px，不再是 40vh。另外在推薦區塊（或它的清單）加上 data-visual-mask 屬性，截圖時遮住每次隨機的推薦商品；遮罩不能包到輪播、最新消息或點餐按鈕。測試會在預覽的 <html> 加上、移除 data-test-mode 來比較兩種模式。

練習 4：為什麼 Playwright 建議用 getByRole('button', { name: '加入購物車' })，而不是 locator('.btn-add')？

✓ b：getByRole 依 role 與可及名稱找元素，跟 class 這類實作細節脫鉤；按鈕變成只有圖示、沒有名稱時找不到元素，測試順便驗證了螢幕閱讀器聽得到什麼。a 錯：長短不是重點，CSS 選擇器常常更短。c 錯：getByRole 要計算無障礙樹，不會比較快。d 錯：locator() 支援 CSS，只是不建議用來找使用者會操作的元素。

練習 5：一個 E2E 測試偶爾失敗，在設定檔加上 retries: 3 之後 CI 就一直是綠的。這樣處理的問題是？

✓ b：重試可以當暫時的止血，但它讓失敗看不見。Playwright 會把「重試才通過」標成 flaky，要有人看 trace 修根因，並用 --fail-on-flaky-tests 或統計 flaky 比例避免累積。a 錯：retries 是給暫時性問題的緩衝，不是修法。c 錯：除了慢，還會讓真的 bug 被當成運氣不好。d 錯：retries 是 Playwright 正式的設定。

練習 6：視覺回歸的基準圖是在 macOS 上產生的，CI 在 Linux 上比對時總是失敗，畫面上看不出哪裡不一樣。最可能的原因是？

✓ b：文字邊緣的像素在不同作業系統、字型、瀏覽器版本下都不一樣，逐像素比對就會失敗；Playwright 也因此在基準圖檔名加上作業系統（-darwin、-linux）。要在 CI 用的映像裡產生基準圖。a 錯：這是預期中的行為。c 錯：每次都失敗就不是巧合，重跑只會一直失敗。d 錯：跟 GPU 無關，關掉也不會讓字型渲染變得一樣。

常見錯誤

  • 用 CSS 選擇器或 .nth() 找使用者會操作的元素：跟實作細節綁死，class 改名、順序調整就壞，或點到別的東西還通過；按鈕失去可及名稱時也抓不到。用 role 與 label，範圍不夠小就先找到所在的區塊。
  • 用 waitForTimeout 等畫面：本機白等、CI 慢一點就失敗，同時造成慢與 flaky。改用 web-first assertion，它只等需要等的時間。
  • expect(await x.textContent())：先讀一次值再比對，不會重試。寫成 await expect(x).toHaveText()。
  • 關掉 axe 規則讓測試通過：問題還在，而且之後新增的同類問題也抓不到。只排除真的修不了的區塊，寫上追蹤的 issue。
  • 只在頁面剛載入時掃 axe：選單、對話框、錯誤訊息出現後的狀態沒有被檢查。在流程中互動之後再掃。
  • 在自己的電腦產生基準圖、在 CI 比對：字型渲染不同，永遠對不上。基準圖在 CI 用的容器映像裡產生。
  • 遮罩或容許差異開太大：mask 遮整頁、maxDiffPixelRatio 設 10%，等於沒有視覺回歸。只遮會變的區塊。
  • 用 retries 掩蓋 flaky：根因還在，真的 bug 也被蓋住。看 trace、分類、修根因，記錄 flaky 比例。

小結

  • E2E 用真的瀏覽器驗證各部分接得起來，慢而且比較容易時好時壞，只留給關鍵流程；規則的細節交給單元與元件測試。每個測試在全新的瀏覽器 context 裡跑，彼此不共用狀態。
  • locator 每次使用時才查詢；優先用 getByRole、getByLabel、getByText，測試同時驗證了可及名稱，按鈕只剩圖示時就會失敗。多個元素符合時先縮小範圍，不用 .nth()。
  • await expect(locator).toHaveText() 這類 web-first assertion 會重試到成立或逾時；動作也會等元素可以操作。固定時間等待與「先讀值再比對」是 flaky 的主要來源。
  • @axe-core/playwright 要用 newContext() 建立的 page，WCAG 各版本的標籤要全部列出；互動之後再掃；例外要追蹤，不要關規則。
  • 狀態碼、noindex、title、canonical、JSON-LD、首圖設定都可以對每個路由自動檢查；用 DOM 讀，可能不存在的元素用不等待的 API 讀。
  • 視覺回歸先固定動畫、時間、資料、字型與環境，再用 mask 遮住剩下會變的區塊；基準圖在 CI 的映像裡產生，改變時隨 PR 審查。
  • flaky test 要重現（--repeat-each）、看 trace、依類型修根因、量化比例；retries 只是止血。整套驗收設成合併前必須通過的檢查，才是真的關卡。
