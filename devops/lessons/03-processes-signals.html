階段 1：伺服器基本功 · 第 3 課

程序、訊號與資源：程式跑起來之後

咖啡店 API 部署上線了。某天改版，你執行 docker stop，它卡了整整 10 秒才停，log 裡最後一筆訂單只寫了一半；隔天容器自己死掉，結束碼 137，log 裡沒有任何錯誤。這兩件事都跟程式碼無關，而是跟「程式跑起來之後」作業系統怎麼對待它有關。

這一課教你看懂一個正在跑的程式。學完你能讓容器在 1 秒內優雅地停下，也能從 137 判斷是被 OOM 殺掉還是停不下來。

這課的路線：
  1. 程序與程序樹：一個跑起來的程式在作業系統眼中是什麼，怎麼查是誰啟動它、誰在聽哪個 port。
  2. 訊號與結束碼：作業系統怎麼叫程式結束，docker stop 為什麼卡 10 秒、137 代表什麼（開場問題的最小答案）。
  3. PID 1 的特殊之處：容器裡的 node 為什麼收到 SIGTERM 也不停，怎麼讓容器 1 秒內停下。
  4. 記憶體、磁碟與檔案：兩種「記憶體不夠」怎麼分辨，磁碟滿了、檔案開太多時去哪裡查。
  5. 背景執行：為什麼正式環境不用 &、nohup 跑服務。
這課會用到：
  • 第 2 課的 shell：管線 | 把前一個指令的輸出接給下一個，$? 是上一個指令的結束碼。
  • 第 1 課的 docker run -d --name：在背景啟動容器並取名字，之後用名字操作它。

程序與程序樹

程序（process）是一個正在執行的程式。同一個 node 執行檔可以同時跑好幾份，每一份都是獨立的程序，有自己的記憶體和一個編號 PID（process ID）。程序一定是由另一個程序啟動的：啟動者是父程序（parent），被啟動的是子程序（child），子程序記得父程序的編號（PPID）。所以整台機器的程序會長成一棵樹。

看程序用 ps（process status）。ps -ef 列出全部程序，下面是一個 Debian 容器裡的實際輸出：

UID          PID    PPID  C STIME TTY          TIME CMD
root           1       0  0 16:13 ?        00:00:00 sh -c … python3 -m http.server 3000 & …
root        3216       1  8 16:13 ?        00:00:00 python3 -m http.server 3000

UID 是哪個使用者、PID 和 PPID 看出父子關係（python3 的父程序是 PID 1 的 sh）、C 是 CPU 使用率、STIME 是啟動時間、TTY 是從哪個終端機啟動（? 表示沒有終端機，服務通常是這樣）、TIME 是累計用掉的 CPU 時間、CMD 是完整指令。想即時看誰最吃 CPU 和記憶體用 top，按 q 離開。

Linux 把每個程序的資訊放在 /proc/<PID>/ 這個虛擬資料夾裡（不是真的檔案，是核心當場產生的）：cmdline 是啟動指令、status 裡有記憶體用量、fd/ 是它開著的檔案、limits 是資源上限。ps、top 其實就是在讀這些檔案。

誰在聽這個 port？

port 是一台機器上區分不同網路服務的編號（例如開發時的 localhost:3000），第 4 課細講。程式要接收連線，得先請核心讓它監聽（listen）某個 port；核心會給它一個 socket（網路連線的端點，程式透過它收送資料），同一個 port 同時只能有一個程式監聽。啟動時看到 EADDRINUSE（port 已經被用了），或想知道 3000 到底是哪個程式在聽，用這兩個工具：

ss -ltnp                                # Linux 伺服器：列出所有在監聽的 TCP port
lsof -nP -iTCP:3000 -sTCP:LISTEN        # Mac 和 Linux 都有：誰在聽 3000

ss（socket statistics）的旗標：-l 只看在監聽（LISTEN）的、-t 只看 TCP、-n 直接顯示數字不轉成名稱、-p 顯示是哪個程序。實際輸出：

State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
LISTEN 0      5            0.0.0.0:3000      0.0.0.0:*    users:(("python3",pid=3216,fd=3))

lsof（list open files）在這台 Mac 上的輸出：

COMMAND   PID USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
node    48053  ken   12u  IPv4 0xdc2068cd43112d4d      0t0  TCP 127.0.0.1:18039 (LISTEN)

精簡的容器映像常常沒有 ss 和 lsof。Alpine 映像裡有 BusyBox（把上百個常用指令做成一個小執行檔）提供的 netstat -ltnp，欄位是 Local Address（例如 :::8080）和 PID/Program name（例如 8/node）。練習 2 會用它。

不要用 ps | grep node 猜誰在聽 port：機器上有兩個 node 時就猜錯了。port 和程序的對應只能從 socket 查。

訊號：作業系統跟程序說話的方式

訊號（signal）是作業系統送給程序的簡短通知，只有一個編號，沒有內容。程序可以為大多數訊號寫處理器（handler），收到時執行自己的程式；沒寫就套用預設動作，通常是直接結束。

訊號編號意思能攔截？誰會送
SIGTERM15請你結束，可以先收尾可以kill 預設、docker stop、systemctl stop、Kubernetes（管理大量容器的平台）停掉容器時
SIGINT2中斷可以在終端機按 Ctrl+C
SIGHUP1原意是終端機斷線；常被拿來要求重新載入設定可以關掉 SSH 視窗、kill -HUP、nginx -s reload 的原理
SIGKILL9立刻殺掉不行kill -9、docker stop 等太久後、核心的 OOM killer
 
kill 2350            # 不寫訊號就是 SIGTERM
kill -TERM 2350      # 同上，寫清楚
kill -HUP 2350       # 請它重新載入設定
kill -9 2350         # SIGKILL：最後手段
kill -l              # 列出所有訊號和編號

SIGKILL 為什麼攔不到？因為它根本沒有送到程序：核心直接把程序移除，程序沒有任何機會執行程式碼。所以 kill -9 不是「比較用力的 kill」，而是「不讓你收尾的 kill」：還沒回應的請求直接斷線、緩衝區裡的 log 沒寫出去、進行到一半的資料庫交易被中斷、暫存檔留在磁碟上。正常的停止流程永遠是先 SIGTERM、等一段時間、真的停不下來才 SIGKILL，docker stop（預設等 10 秒）和 systemd（預設等 90 秒）都是這樣做的。

Node 裡的處理器就是 Node 課第 21 課寫過的 process.on('SIGTERM', …)：停止收新請求、等進行中的請求完成、關資料庫連線，最後 process.exit(0)。

開場的兩件事到這裡有了最小答案：docker stop 先送 SIGTERM，程式 10 秒內沒結束，Docker 就改送 SIGKILL，所以卡滿 10 秒、訂單只寫一半；137 則是被 SIGKILL 殺掉留下的結束碼。為什麼寫了處理器還是停不下來，細節在後面的〈PID 1 的特殊之處〉。

結束碼：0、1 與 128+N

程序結束時留下一個結束碼（exit status），父程序讀得到，shell 放在 $?。自己結束的程式用 0 表示成功、其他數字表示失敗（Node 未捕捉的例外是 1）。被訊號殺掉的程序沒機會自己決定結束碼，shell 和 Docker 用 128 + 訊號編號 來表示。在 Alpine 容器裡實測：

sleep 100 & kill -TERM $!; wait $!; echo $?     # 143 = 128 + 15
sleep 100 & kill -KILL $!; wait $!; echo $?     # 137 = 128 + 9
sleep 100 & kill -INT  $!; wait $!; echo $?     # 130 = 128 + 2
node -e 'process.exit(3)'; echo $?              # 3：程式自己決定的

$! 是最近一個背景程序的 PID，wait 等它結束並取得它的結束碼。

結束碼意思常見原因接著查什麼
0正常結束收到 SIGTERM 後收尾完成—
1程式自己報錯結束未捕捉的例外、設定缺少log 的最後幾行
130被 SIGINT 結束有人按了 Ctrl+C—
143被 SIGTERM 結束、沒有處理器程式沒寫 SIGTERM 處理器，套用預設動作補上優雅關機
137被 SIGKILL 強制殺掉① 記憶體超過上限被核心殺掉 ② 收到 SIGTERM 卻停不下來，逾時後被殺docker inspect 的 State.OOMKilled；docker stop 是不是等滿 10 秒

看到 137 不要先去翻程式碼，先分清楚是哪一種：OOMKilled 是 true 就是記憶體問題，false 就是停不下來。

PID 1 的特殊之處

系統裡的第一個程序 PID 1 叫 init。在伺服器上它是 systemd（Linux 上負責啟動與管理服務的程式，第 6 課），在容器裡是你啟動的第一個程式。它有兩個其他程序沒有的特性：

  1. 核心不會對 PID 1 套用預設的訊號動作。一般程序沒寫 SIGTERM 處理器，收到就結束；PID 1 沒寫，訊號直接被忽略（從容器外面送的 SIGKILL 例外，例如 docker stop 逾時後那一下）。
  2. 它要回收殭屍程序。子程序結束後，核心會保留它的結束碼，等父程序讀取。還沒被讀取的程序叫殭屍程序（zombie），在 ps 裡 STAT 欄是 Z。如果父程序先死了，子程序會被 PID 1 收養，PID 1 要負責讀取它們的結束碼。不做的話殭屍越積越多，最後占滿 PID 編號。

接下來的實驗和練習會用到幾個 Docker 指令，第 7 課會完整介紹，這裡先知道它們做什麼：

指令做什麼
docker stop 名稱送 SIGTERM 給容器的 PID 1，等 10 秒（-t 可改）還沒結束就送 SIGKILL
docker logs 名稱看容器主程序印到 stdout、stderr 的內容，容器結束後還看得到
docker exec 名稱 指令在執行中的容器裡多跑一個指令，例如 cat /proc/1/cmdline 看 PID 1 是誰
docker inspect -f '{{.State.ExitCode}}' 名稱讀容器的設定與狀態；-f 只取一個欄位，例如結束碼
docker run -v "$(pwd)":/app …把主機上目前的資料夾掛進容器的 /app，容器裡看得到你的檔案

先看第一點的後果。node 自己當 PID 1、沒寫 SIGTERM 處理器時，實測：

docker run -d --name ld-03-demo node:24.22.2-alpine3.24 node -e 'setInterval(() => {}, 1000)'
time docker stop ld-03-demo                                   # real 10.36：等滿 10 秒
docker inspect -f '{{.State.ExitCode}}' ld-03-demo            # 137
docker rm ld-03-demo

加上 --init，Docker 會放一個很小的 init 程式（docker-init，就是 tini）當 PID 1，由它轉送訊號、回收殭屍。同一個指令加了 --init 後，docker stop 只花 0.57 秒，結束碼 143：node 不是 PID 1 了，SIGTERM 套用預設動作，直接結束。

包裝腳本與 exec

更常見的情況是用一個 shell 腳本啟動程式，先做點準備（印設定、等資料庫）再跑 node：

#!/bin/sh
echo "cafe-api starting: PORT=${PORT:-3000}"
node server.mjs

這時 sh 是 PID 1，node 是它的子程序（實測 ps：PID 1 是 sh /app/start.sh，PID 8 是 node）。docker stop 把 SIGTERM 送給 PID 1，也就是 sh。sh 沒有處理器、又是 PID 1，訊號被忽略，也不會轉給 node。10 秒後 Docker 送 SIGKILL，整個容器被殺，node 寫好的優雅關機一行都沒跑。

修法是 exec：它讓新程式取代目前的 shell 程序，PID 不變。exec node server.mjs 之後，PID 1 就是 node，SIGTERM 直接送到它的處理器。

其他寫法和代價：

  • node server.mjs & 再 wait：sh 還是 PID 1，訊號一樣到不了 node。
  • trap 'exit 0' TERM（第 2 課的 trap 除了 EXIT，也能註冊收到某個訊號時要執行的指令）：sh 收到 SIGTERM 就自己結束，容器很快停下、結束碼也是 0，看起來修好了。可是 PID 1 一結束，核心會把容器裡其他程序全部 SIGKILL，node 根本沒收尾。這是最危險的「假修好」。
  • 在 trap 裡 kill -TERM "$pid" 轉送再 wait：能動，但每個腳本都要寫對，而且殭屍還是沒人收。能用 exec 就用 exec。
  • docker run --init、或在映像裡放 tini：需要真正的 init（例如程式會產生子程序）時用。
  • Dockerfile 的 CMD node server.js（shell 形式）會被包成 /bin/sh -c "node server.js" 執行。sh 會不會自動用 exec 跑最後一個指令，要看是哪個 shell：實測 Alpine 的 BusyBox sh 會（node 變成 PID 1），Debian 的 dash 不會（sh 留在 PID 1，訊號到不了 node）。不要依賴這種差異，要寫成 CMD ["node", "server.js"]（exec 形式），第 8 課會再講。同理，Node 官方映像的最佳實務建議不要用 npm start 當容器的主程式，因為 npm 會把訊號擋在中間。
💡 實務上：每次部署都會送一次 SIGTERM
滾動更新（一次換掉一部分副本的部署方式，第 16 課）、減少副本、雲端主機維護，都是先送 SIGTERM、等一段時間再送 SIGKILL。訊號處理寫錯，單元測試抓不到，只會變成「每次上線都有幾個請求失敗」，PM 看到的是固定出現在部署時間的錯誤。上線前用 docker stop 量一次：停止的時間剛好等於寬限時間，代表程式根本沒收到訊號，要回頭檢查 PID 1 是誰。

記憶體：兩種「不夠用」

top 和 ps 裡跟記憶體有關的欄位，最重要的是 RSS（resident set size，常駐記憶體）：程序實際占用的實體記憶體。另一個 VSZ（虛擬記憶體大小）包含只預留、沒真正用到的空間，通常大很多，不能拿來判斷用量。Node 裡用 process.memoryUsage().rss 讀得到。

Node 程式的記憶體分兩塊：V8 heap 放 JavaScript 物件、陣列、字串（Node 課第 23 課）；heap 外面放 Buffer 的內容、原生模組和 Node 自己的資料。所以有兩個上限，撞到哪一個，結果完全不同：

V8 heap 上限容器記憶體上限
誰設的Node 啟動時依可用記憶體決定，--max-old-space-size 可以改docker run --memory 512m、Kubernetes 的 limits
誰動手V8 自己放棄Linux 核心的 OOM killer（記憶體不足時強制殺程序的機制）
logFATAL ERROR: … JavaScript heap out of memory什麼都沒有，程序直接消失
結束碼程序自己 abort：常見 134（128 + 6，SIGABRT）；這個映像的 node 當 PID 1 時，abort 送給自己的 SIGABRT 被忽略，最後換成另一種崩潰，實測 139（128 + 11，SIGSEGV）137
State.OOMKilledfalsetrue
處理方向找 JS 物件的洩漏、或調高 heap 上限找 heap 外的用量（Buffer、原生模組）、或調高容器上限；heap 上限不能比容器上限大

Node 在容器裡會讀 cgroup（Linux 核心限制一組程序能用多少 CPU、記憶體的機制，--memory 就是靠它，第 7 課細講）的記憶體上限來決定 heap 上限（process.constrainedMemory() 讀得到容器上限）。在這台 Mac 上用 node:24.22.2-alpine3.24 實測 v8.getHeapStatistics().heap_size_limit：

容器 --memoryheap 上限
256m259 MB（比容器還大）
512m259 MB
1g560 MB
不限制（Docker Desktop 的虛擬機約 8 GB）2240 MB

256 MB 的容器裡 heap 上限比容器還大，所以分配 JS 物件也會先被核心殺掉（實測 137、OOMKilled true）；512 MB 時 heap 先滿（實測 heap OOM、OOMKilled false）。不要憑「heap 大約是容器的一半」這類經驗值，在目標環境量一次，記憶體吃緊的服務直接設 --max-old-space-size，讓 heap 上限明確地小於容器上限。

docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' 容器名稱   # 137 true：被核心 OOM kill

磁碟與檔案

磁碟滿了，服務會以奇怪的方式壞掉：log 寫不進去、資料庫拒絕寫入、上傳失敗、連 docker pull 都不行。最常見的元兇是沒有輪替的 log 和沒清的舊映像（第 21 課處理 log）。

df -h                 # 每個磁碟分割區用了多少（disk free）
du -sh /var/log/*     # 每個檔案或資料夾各占多少（disk usage），-s 加總、-h 用 K/M/G 顯示
docker system df      # Docker 的映像、容器、volume 各占多少（第 1 課）

先用 df -h 找到哪個分割區滿了（Use% 接近 100%），再用 du -sh 一層一層往下找是哪個資料夾。

檔案描述元與 ulimit -n

程序每開一個檔案、每接一條網路連線，核心就給它一個編號，叫檔案描述元（file descriptor，fd），在 /proc/<PID>/fd/ 看得到。每個程序能同時開的數量有上限，用 ulimit -n 查。超過時 Node 會丟出 EMFILE: too many open files：對伺服器來說，就是新的連線接不進來。用 --ulimit nofile=100 啟動容器實測，Node 開了 83 個檔案之後，下一個就收到 EMFILE（其他編號已經被 stdin、stdout、事件迴圈等占走）。

這個上限的預設值因環境而異。Docker Engine 29 的版本說明寫到：containerd 2.1.5 改用 systemd 的預設 LimitNOFILE，Linux 伺服器上的容器預設 ulimit -n 從 1048576 變成 1024。可是這台 Mac 的 Docker Desktop 4.85.0（Engine 29.6.2）實測容器裡還是 1048576。所以要在你真正部署的環境裡執行一次 ulimit -n，需要更多時用 docker run --ulimit nofile=65536:65536 或 daemon 的 default-ulimits 設定。

💡 實務上：磁碟滿是最常見、也最好預防的事故
log 沒有輪替、舊映像沒清、備份檔放在同一顆磁碟，總有一天會把磁碟塞滿；接著資料庫寫不進去，程式出現各種看似無關的錯誤。資深工程師會在新機器上線時就做三件事：設定 log 輪替（第 21 課）、在部署腳本裡清掉用不到的映像、對磁碟使用率設告警（第 25 課）。真的滿了，先用 df -h、du 找出大戶，不要急著刪不認得的檔案。

背景執行：&、nohup 為什麼不夠

在終端機裡，指令後面加 & 就放到背景執行，jobs 列出背景工作。可是關掉 SSH 視窗時，終端機會送 SIGHUP，背景程式跟著結束。nohup node server.mjs & 讓程式忽略 SIGHUP、輸出寫到 nohup.out，登出後還活著。

很多人就這樣把服務跑在正式機上，問題是：

  • 程式當掉沒人重新啟動，機器重開機後也不會自己起來。
  • log 寫進一個會一直長大的 nohup.out，沒人輪替，直到磁碟滿。
  • 要停止時只能自己找 PID 再 kill，沒有固定的優雅關機流程；換人值班就沒人知道它在哪。

正式環境要交給一個專門管程序的「監督者」：第 6 課的 systemd 負責重啟、收 log、開機自動啟動、先 SIGTERM 再 SIGKILL；第 7 課起改用容器，由 Docker 和後來的 Kubernetes 接手。screen、tmux 也一樣，只適合臨時的工作。

練習

練習 1：server.mjs 已經寫好 SIGTERM 的優雅關機，start.sh 是包裝它的腳本。測試用 docker run -d --name ld-03-sig -v 你的資料夾:/app node:24.22.2-alpine3.24 sh /app/start.sh 啟動，等 /health/live 有回應後執行 docker stop。現在它要等 10 秒、結束碼 137。改 start.sh，讓容器裡的 PID 1 是 node、docker stop 之後結束碼 0（不是等到逾時被 SIGKILL）、log 裡有 shutdown complete；啟動時印設定的那行 echo 要保留。

練習 2：寫 who-listens.sh <port>，印出正在監聽這個 TCP port 的程序，每行「PID 名稱」（名稱就是 netstat 的 PID/Program name 斜線後面那段）；同一個程序只印一次；沒有人監聽時什麼都不印，以結束碼 1 結束。測試在 Alpine 容器裡啟動好幾個監聽者（有 8080 也有 18080、有兩個以上的 node、有同時聽 IPv4 和 IPv6 的程序，還有一個從本機 port 9999 連到 8080 的客戶端），再用真正的 PID 比對。容器裡沒有 ss，用 BusyBox 的 netstat -ltnp。先自己看看輸出長什麼樣子（-it 讓你在容器裡互動地打指令，exit 離開）：

docker run --rm -it node:24.22.2-alpine3.24 sh
node -e "require('net').createServer().listen(8080)" &
netstat -ltnp

練習 3：在 run-oom.sh 寫一行 docker run：用 node:24.22.2-alpine3.24 啟動名為 ld-03-oom 的容器，記憶體上限 512 MB 而且不准用 swap（記憶體不夠時把資料暫時搬到磁碟的空間。--memory-swap 是記憶體加 swap 的總量，設成和 --memory 一樣就是 swap 為 0），執行附的 eat-memory.mjs（不斷分配 Buffer，不會撞到 V8 heap 上限）。自己執行 sh run-oom.sh，看 docker logs ld-03-oom 最後一行停在多少 MB，再用 docker inspect 查結束碼和 OOMKilled，填進 answers.json 的 exitCode（數字）和 oomKilled（true／false）。容器結束後不要自動刪除，測試要 inspect 它。

練習 4：每次 docker stop 咖啡店 API 都剛好卡 10 秒，結束碼 137。最可能的原因是？

✓ 「每次剛好 10 秒」就是 docker stop 的預設等待時間：SIGTERM 完全沒產生效果，逾時後才 SIGKILL（137）。收尾太慢的話時間會不固定，而且 log 裡會看到開始收尾的訊息；OOM 會在 inspect 看到 OOMKilled=true，跟 docker stop 無關。先查 PID 1 是誰：docker exec 容器 cat /proc/1/cmdline。

練習 5：同事習慣用 kill -9 停掉正式機上的 API，說「反正都是停掉，-9 比較確定」。問題在哪？

✓ SIGKILL 不會送到程序，核心直接移除它，所以處理器一行都不會執行；結果是客人的請求被斷線、交易被中斷、log 遺失。kill -9 只殺那一個程序，不會往上殺父程序。正確流程是先 SIGTERM、等一段時間，真的停不下來才 SIGKILL。

練習 6：容器 A 的 log 最後一行是「JavaScript heap out of memory」，OOMKilled=false；容器 B 沒有任何錯誤 log，結束碼 137、OOMKilled=true。下面哪個說法對？

✓ V8 heap 滿時是 V8 自己印出 FATAL ERROR 再 abort，核心沒有出手，所以 OOMKilled 是 false；核心 OOM kill 用 SIGKILL，程式來不及印任何東西，結束碼 137。處理方式也不同：A 要找 JS 物件的洩漏或調整 --max-old-space-size，只調大容器上限不一定有用；B 要找 heap 外的用量或調高容器上限。

常見錯誤

  • 包裝腳本最後一行沒寫 exec：sh 成了 PID 1，SIGTERM 到不了程式，每次停止都等滿逾時再被硬殺。最後一行寫 exec node server.mjs。
  • 用 trap 'exit 0' TERM 讓容器「快速停下」：PID 1 結束時核心會殺掉容器裡所有程序，程式根本沒收尾。結束碼 0 是假象，要看 log 有沒有收尾訊息。
  • Node 當 PID 1 卻沒寫 SIGTERM 處理器：PID 1 不套用預設動作，訊號被忽略。寫處理器，或用 --init。
  • 把 kill -9 當成正常的停止方式：先送 SIGTERM，等收尾，逾時才 SIGKILL。
  • 看到 137 就去翻程式碼：先查 State.OOMKilled，再看 docker stop 是不是等滿逾時，兩種原因的處理完全不同。
  • 以為容器裡的 ulimit -n 跟你的 Mac 一樣：Docker Engine 29 在 Linux 伺服器上預設 1024，連線一多就 EMFILE。在部署環境裡實際查一次。
  • 用 nohup、screen 在正式機上跑服務：沒人重啟、沒人收 log、沒有優雅關機。交給 systemd 或容器。
  • 等磁碟滿了才發現 log 和映像吃掉空間：定期看 df -h 和 docker system df，log 要輪替。

小結

  • 程序有 PID 和 PPID，組成一棵樹；ps -ef、top 看程序，/proc/<PID>/ 有它的一切。
  • 誰在聽某個 port：ss -ltnp、lsof -nP -iTCP:3000 -sTCP:LISTEN，Alpine 裡用 netstat -ltnp；不要用 ps | grep 猜。
  • SIGTERM 請程式收尾、SIGINT 是 Ctrl+C、SIGHUP 常用來重新載入設定、SIGKILL 不能攔截。
  • 被訊號 N 殺掉的結束碼是 128+N：130、137、143；137 先查 OOMKilled。
  • PID 1 不套用預設訊號動作、要回收殭屍；包裝腳本用 exec，需要 init 時用 --init。
  • V8 heap 滿：程式自己 abort、OOMKilled=false；容器記憶體滿：核心 OOM kill、137、OOMKilled=true。heap 上限要在目標環境量。
  • df -h、du -sh 找磁碟用量；ulimit -n 是能開的檔案與連線數，超過就 EMFILE。
  • 正式環境不用 &、nohup 跑服務，交給 systemd 或容器。
