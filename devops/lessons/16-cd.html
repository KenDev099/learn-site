階段 4：自動化交付 · 第 16 課

CD 與部署策略：不可變映像、藍綠、金絲雀、回滾

咖啡店的 PR 現在都有 CI 把關（第 15 課），但上線還是靠人：週五傍晚，工程師 SSH 進伺服器，git pull、在伺服器上 docker build、docker compose up -d。新版啟動要幾秒，這幾秒 nginx 回 502；新版有 bug，要回到上一版得再 build 一次，可是伺服器上的映像已經被蓋掉，沒人記得上一版是哪個 commit。結果是大家只敢一個月部署一次，每次部署都是一場賭博。

這一課把「上線」變成一件無聊的事。學完你能寫出部署腳本與部署 workflow，並說得出每一種部署策略的代價。

這課的路線：
  1. 從 CI 到 CD、不可變產物：合併之後還要走哪段路，為什麼映像只建置一次、用 digest 指名，出事時才找得到上一版。
  2. 部署策略比較：recreate、rolling、藍綠、金絲雀各自的停機時間、資源與風險，選平台和面試都會問。
  3. 藍綠部署與金絲雀：用 nginx 切換兩組容器做到零停機，再讓新版先接一小部分流量，用功能旗標把「部署」和「發布」分開。
  4. 回滾與往前修：出事時先退回還是直接修，什麼情況根本退不回去。
  5. 部署 workflow：把整套流程寫成 GitHub Actions，同一個映像從 CI 一路推到 production。
這課會用到：
  • 第 7 課的 tag 與 digest：tag 是可以改掛的名牌，digest 是映像內容算出的雜湊值，內容不同就不同。
  • 第 12 課的 upstream 與 reload：upstream 決定 nginx 把請求轉給誰；改設定後先 nginx -t 檢查，再 reload 讓新設定生效、不中斷連線。
  • 第 15 課的 GitHub Actions：workflow 由 job 組成，needs 排順序，permissions 從 contents: read 開始，action 釘 SHA。

從 CI 到 CD

CI（持續整合）回答「這個改動能不能合併」。合併之後還有一段路：建置出可以部署的東西、放到某個地方、裝到伺服器上、確認它在跑。CD 管的就是這一段，它有兩種意思：

  • 持續交付（continuous delivery）：main 上的每個 commit 都已經建置好、測試過、放在 registry 裡，隨時可以上線。要不要按下 production 的按鈕，由人決定。
  • 持續部署（continuous deployment）：通過所有檢查的改動自動上線，中間沒有人按按鈕。

兩者的差別只在最後一步有沒有人工核准。大多數團隊從持續交付開始：先讓「上線」變得安全、可重複，等部署後的自動檢查夠可靠，再把核准拿掉。

同一個產物從 staging 移到 production 叫做推廣（promotion）。重點是「同一個」：production 跑的必須是 staging 測過的那個映像，而不是用同一個 commit 再建一次的映像。

不可變產物與標籤

為什麼不能每個環境各自 build？同一個 commit 兩次建置的結果不保證一樣：FROM node:24-alpine 這種 tag 在兩次建置之間可能被更新、npm install（沒有 lockfile 或沒用 npm ci）可能抓到新的套件版本、RUN apk add 抓到的是當天的套件。你在 staging 測的是 A，production 跑的是 A'，兩者的差異沒有人測過。

所以規則是建置一次，產物建好之後不再改變（不可變，immutable）：要改就建一個新的。環境之間不同的只有設定，部署時才注入（第 11 課）。映像要能被準確地指名，靠的是標籤策略：

標籤例子會不會變用途
git SHA（第 14 課的 commit 雜湊值）cafe-api:4e1c2a9不會（一個 commit 只建一次）追查「這個映像是哪段程式碼」
semvercafe-api:1.4.2不該變（團隊約定）給人看的版本號、release notes
環境別名cafe-api:production會（每次部署都移動）只用來「看目前是哪個」，不拿來部署
latestcafe-api:latest會（每次推送都移動）不拿來部署
digestcafe-api@sha256:9f86…不可能變（內容的雜湊）部署與回滾

tag 只是指向某個映像的名牌，誰都可以把它改掛到別的映像上（第 7 課）。digest 是映像內容算出來的 SHA-256，內容不同 digest 就不同，所以部署時寫 digest，伺服器跑的一定是你指名的那一個。latest 的問題在回滾：出事時你想回到「上一版」，可是 latest 早就指向新版，上一版叫什麼沒人知道。

在本機用官方的 registry:3.1.2 映像就能有一個私有 registry。推到 localhost 的 registry 不需要設定 TLS，Docker 預設允許：

docker run -d --name ld-16-registry -p 127.0.0.1:18160:5000 registry:3.1.2

sha=$(git rev-parse HEAD)            # 完整 SHA，給 label 用
short=$(git rev-parse --short=7 HEAD)
docker build \
  --label org.opencontainers.image.revision="$sha" \
  --label org.opencontainers.image.version=1.4.2 \
  --label org.opencontainers.image.created="$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  -t localhost:18160/cafe-api:"$short" -t localhost:18160/cafe-api:1.4.2 .
docker push localhost:18160/cafe-api:"$short"
docker push localhost:18160/cafe-api:1.4.2

# 問 registry：這個 tag 現在是哪個 digest
docker buildx imagetools inspect localhost:18160/cafe-api:"$short"

一次 docker build 打兩個 -t，兩個 tag 就是同一個映像，推上去的 digest 相同。org.opencontainers.image.* 是 OCI 規範的標準 label：revision 記錄 commit、version 記錄版本、created 記錄建置時間（RFC 3339，ISO 8601 的一種寫法，要帶時區，例如 2026-11-01T08:30:00Z，Z 代表 UTC）。半夜收到告警時，docker inspect 正在跑的容器就知道它是哪個 commit。

本機的 image ID 和 registry 上的 digest 可能不一樣：本機存的是 Docker 自己的格式，推上去時才產生 registry 上的 manifest。部署要用 registry 回報的 digest（imagetools inspect 或 docker push 最後一行印的 digest: sha256:…）。

發佈前還有一個檢查：工作目錄要乾淨。如果改了檔案沒 commit 就建置，映像裡的程式碼和它的 revision label 對不上，那個 commit 根本沒有這段程式。git status --porcelain 有任何輸出（改了沒 commit、新檔案沒 add）就應該拒絕發佈；git diff 看不到沒追蹤的新檔案，但它們一樣會被 COPY . . 複製進映像。

💡 實務上：出事時第一個問題是「線上跑的到底是哪一版」
客服回報「今天下午開始結帳失敗」，值班的人要先回答：production 現在跑哪個 digest、它是哪個 commit、上一次部署是什麼時候。有 revision label 加上部署紀錄（GitHub 的 environment 頁面就會列出每次部署），這題一分鐘答得出來；靠 latest 和口頭記憶，常常要花半小時猜。資深工程師會讓每次部署都留下「時間、digest、commit、誰觸發」，回滾時直接挑上一筆。

部署策略比較

新版要取代舊版，有幾種做法。先認識名字：

  • recreate：先把舊版全部停掉，再啟動新版。中間有一段時間沒有任何版本在服務。
  • rolling（滾動更新）：有好幾個副本時，一次換掉一部分，直到全部換成新版。過程中新舊版同時在服務。
  • 藍綠部署（blue-green）：準備兩套環境，藍色跑目前的版本、綠色放新版；新版準備好之後一次把流量切過去，舊的那套留著，出事就切回來。
  • 金絲雀（canary）：先讓一小部分流量（例如 5%）走新版，觀察錯誤率和延遲，沒問題再逐步擴大。名字來自礦工帶金絲雀下礦坑，牠先出事，人就知道要撤。
  • 功能旗標（feature flag）：新功能的程式碼已經部署，但用設定開關決定誰看得到。它管的是「發布」，不是「部署」。
策略停機額外資源回滾速度出事影響多少人對資料庫的要求
recreate有（新版啟動的時間）無慢：再部署一次舊版全部最低：同一時間只有一個版本
rolling無少（多開 1～幾個副本）中：要再滾一次逐步變成全部新舊版同時讀寫同一個 schema
藍綠無多（部署期間兩倍）快：切回舊環境，幾秒切換後的全部新舊版都要能用目前的 schema
金絲雀無少到中快：把比例調回 0只有金絲雀那一部分同 rolling，而且共存期更長
功能旗標無（不必部署）無最快：關掉開關只有打開的那群人新舊程式路徑都在同一版裡

除了 recreate，每一種策略都有「新舊版同時在跑」的時間，所以資料庫的改動必須同時相容新舊兩版，這是第 17 課的主題。Kubernetes 的 Deployment 預設就是 rolling（策略 RollingUpdate，預設 maxSurge 與 maxUnavailable 都是 25%），配合 readiness probe，新 Pod ready 才會把舊的拿掉；第 13 課的對照表有它和 compose、nginx 的對應。這一課只有一台主機、一個副本，用 nginx 手動做藍綠，每一步都看得到。

💡 實務上：大多數團隊用平台內建的 rolling，關鍵服務再加金絲雀
用 Kubernetes、ECS 這類平台時，預設就是 rolling，你要做的是把 readiness 和排空設對（第 13 課），而不是自己寫切換腳本。藍綠常見在「不能有新舊版混跑」的情況，例如一次換掉整套前後端，或要先在正式環境的另一套上完整驗證。金絲雀多用在流量大、出錯代價高的服務（結帳、付款）。選策略時資深工程師會先問：能不能接受新舊版同時存在？回滾要多快？有沒有指標能比較兩版？

藍綠部署實作

咖啡店的架構：nginx 是入口，upstream api 指向目前作用中的顏色，例如 ld-16-blue:3000。這一行放在獨立的 active.conf，部署時只改這個檔。一次部署的步驟：

  1. 讀 active.conf 判斷目前是哪個顏色，新版放到另一個顏色。
  2. 移除另一個顏色上一次留下的閒置容器，用新版的 digest 啟動它。
  3. 健康關卡：等它的 /health/ready 回 200（第 13 課的 readiness），設逾時，等不到就放棄。
  4. 煙霧測試（smoke test）：打幾個最重要、最快的請求，例如 GET /products 要回 200 與 JSON 陣列。名字來自硬體：通電之後先看有沒有冒煙。ready 只代表「我覺得我好了」，煙霧測試是從外面確認它真的能做事。
  5. 改寫 active.conf 指向新顏色，nginx -t 通過才 nginx -s reload。
  6. 舊顏色留著不動：它已經不在 upstream 裡、不會收到新請求，但還在跑，回滾（rollback）只要把 active.conf 改回去再 reload。下一次部署才會換掉它。

任何一步失敗都停下來：移除失敗的新容器、active.conf 不動，流量從頭到尾留在舊顏色上。部署失敗不該變成服務中斷。

幾個細節決定了是不是真的零停機：

  • reload，不是 restart：nginx -s reload 讓 master 程序讀新設定、啟動新的 worker，舊 worker 處理完手上的請求才結束（第 12 課）。docker restart 會把 nginx 整個停掉，正在傳的連線全部斷掉，重新啟動前的請求都連不上。
  • 掛資料夾，不是單一檔案：把 nginx/ 整個資料夾 bind mount 到 /etc/nginx/conf.d/。如果只掛 active.conf 一個檔案，很多編輯器和工具改檔案的方式是「寫新檔再改名」，容器裡看到的還是舊檔。
  • 新容器沒有發布 port：健康檢查和煙霧測試從 nginx 容器裡連，例如 docker exec ld-16-nginx curl -fs http://ld-16-green:3000/health/ready。curl -f 讓 4xx／5xx 變成非 0 的結束碼，腳本才判斷得出失敗。
  • nginx -t 也是一道關卡：upstream 寫的主機名稱如果解析不到（例如新容器不存在），nginx -t 會失敗，這時把 active.conf 還原，不要 reload。
  • 依 digest 啟動：deploy.sh 只接受 …@sha256:… 這種參照。給它 tag，它就無法保證跑的是測過的那一個。

藍綠的代價：部署期間要兩倍的資源（兩套環境都在跑），而且切換的那一刻起新版接下全部流量，新版有問題就是所有人一起遇到，只是能很快切回。資料庫只有一個，新舊版都要能用目前的 schema。

金絲雀與功能旗標

藍綠切換是全有全無。金絲雀讓新版先接一小部分流量。nginx 的 split_clients 指令把一個字串用 MurmurHash2 算出雜湊，依雜湊落在哪一段決定變數的值：

split_clients "${cookie_uid}" $canary_pool {
    5%      green;     # 雜湊落在前 5% 的使用者
    *       blue;      # 其餘
}

雜湊的來源決定了分流的單位：

  • 用使用者識別（cookie 裡的 uid、登入的 user id）：同一個人每次都落在同一邊，不會這一頁是新版、下一頁是舊版，資料格式和畫面才對得上。這是一般的做法。
  • 用 $request_id：每個請求各自隨機，比例很準，但同一個人會在新舊版之間跳。
  • 用 $remote_addr：同一個 IP 全部在同一邊。公司、學校、行動網路常常幾千人共用一個 IP，比例會非常不準。

測試人員要能強制走新版，可以用 map 依標頭覆蓋分流結果，再把變數交給 proxy_pass（變數的值剛好是某個 upstream 的名稱時，nginx 就用那個 upstream）：

map $http_x_canary $pool {
    always   green;            # 帶 X-Canary: always 的請求
    default  $canary_pool;     # 其他照比例
}
# location 裡：proxy_pass http://$pool;

金絲雀不會自動讓你安全。它只是把影響範圍縮小到那一部分人，前提是有指標能及時發現問題：比較 green 和 blue 的錯誤率、p95 延遲（第 22 課），green 明顯比較差就把比例調回 0；沒問題就逐步擴大到 25%、50%、100%。如果沒有人在看指標，金絲雀只是「慢一點讓所有人遇到 bug」。

💡 實務上：還沒有 uid cookie 的人全部落在同一邊
依 cookie 分流時，第一次來、還沒有 uid 的訪客，雜湊的來源都是空字串，所以全部進同一邊（可能是新版）。實務上會讓應用程式或 nginx 在第一次回應時就發一個 uid cookie，或改用登入後的 user id。另外要讓客服知道金絲雀正在進行：同一時間只有少數客人回報的問題，可能只發生在新版，查 log 時要看請求是哪個版本處理的（第 21 課）。

功能旗標把「部署」（程式碼到了伺服器）和「發布」（使用者看得到）分開。新的會員集點功能可以先部署、旗標關著，再對員工打開、對 5% 的客人打開、對所有人打開。出問題時關掉旗標就好，不用回滾整個版本，同一版裡其他的修正不會跟著被退掉。

// OpenFeature：旗標的標準 API，背後接哪一家旗標服務可以替換，程式碼不用改
const client = OpenFeature.getClient()
if (await client.getBooleanValue('loyalty-points', false, { targetingKey: userId })) {
  // 新的集點流程
}

OpenFeature 是 CNCF 的開放標準，定義了讀取旗標的 API，各家旗標服務（或你自己存在資料庫的開關）提供對應的 provider。旗標的代價是程式裡多了分支：每個旗標都是一個要測兩種情況的 if。功能全面開放後就要把旗標和舊路徑刪掉，否則幾年後程式裡會堆滿沒人敢動的開關。建立旗標時就寫好負責人和預計移除的日期。

回滾與往前修

新版出事時有兩條路：

  • 回滾（rollback）：回到上一個好的版本。藍綠只要切回、金絲雀只要把比例調回 0、其他策略就是再部署一次上一個 digest。它快，而且不需要理解 bug 在哪，所以出事時的預設動作是先回滾，止血之後再查原因。
  • 往前修（roll forward）：寫修正、走一次完整的 CI 與部署。適合問題很小、修正很明確，或是不能回滾的時候。

什麼時候不能回滾？最常見的是資料庫：新版的 migration 已經刪掉舊版需要的欄位，或新版寫進去的資料舊版看不懂。這時回到舊程式只會換一種壞法。第 17 課會用 expand／contract 安排 migration，讓每次部署之後舊版仍然能跑，回滾才一直是可行的選項。

回滾也可以自動化。部署腳本與 workflow 裡常見的檢查：

  • 健康關卡：新版沒有在時限內 ready，不切流量（藍綠的做法）。
  • 煙霧測試：切換之後再打一次關鍵路徑，失敗就自動切回。
  • 指標關卡：切換後觀察幾分鐘，錯誤率或延遲超過 SLO（第 22 課）就自動回滾。這需要事先寫好門檻，而不是出事當下才討論。

怎麼知道交付流程整體是健康的？DORA（DevOps Research and Assessment，現在是 Google Cloud 底下的研究計畫）定義了五個指標，前三個看速度，後兩個看穩定：

指標意思
變更前置時間（change lead time）一個 commit 從提交到上線花多久
部署頻率（deployment frequency）多久部署一次 production
部署失敗復原時間（failed deployment recovery time）一次失敗的部署，多久恢復正常
變更失敗率（change fail rate）多少比例的部署需要立即處理（回滾、修補）
部署重工率（deployment rework rate）多少比例的部署是為了修正線上問題而臨時做的

DORA 的研究發現速度和穩定通常一起變好：小而頻繁的部署，每次改得少、出事好查、回滾的代價也小。一個月部署一次的團隊，每次部署都塞了一個月的改動，出事時根本不知道是哪一個。

部署 workflow

把上面的流程寫成 GitHub Actions。結構是三個 job：

build ──→ deploy-staging ──→ deploy-production（等核准）
  └─ outputs.digest ─────────────┴─ 兩個部署 job 都用這個 digest

build 建置並推到 GHCR（GitHub 的 container registry，ghcr.io）。推映像需要 packages: write，這個權限只給 build，workflow 最上層仍然只有 contents: read（第 15 課的最小權限）。Docker 官方的幾個 action 分工：docker/login-action 登入 registry（用 GITHUB_TOKEN）、docker/metadata-action 依規則產生 tag 與 OCI label（type=sha 產生 sha- 開頭的短 SHA tag）、docker/build-push-action 建置並推送，它的輸出 digest 就是推上去的映像 digest。這一課用的版本是 build-push-action v7.4.0、login-action v4.7.0、metadata-action v6.2.0、setup-buildx-action v4.4.1，一樣釘完整的 commit SHA。

  build:
    permissions:
      contents: read
      packages: write
    outputs:
      digest: ${{ steps.push.outputs.digest }}   # 讓後面的 job 讀得到
    steps:
      # …checkout、setup-buildx、login、metadata…
      - id: push
        uses: docker/build-push-action@<SHA> # v7.4.0
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha                  # 用 GitHub Actions 的快取存 Docker 的層
          cache-to: type=gha,mode=max

後面的 job 用 needs.build.outputs.digest 讀這個值。要讀某個 job 的 outputs，它必須直接列在 needs 裡，所以 production 要寫 needs: [build, deploy-staging]。部署 job 裡不能再出現 docker build，也不能用 latest。

environment：在 job 上寫 environment: production，GitHub 會把這次執行記成一次部署，並套用這個環境的保護規則，例如「必要審查者」：job 會停下來等指定的人按核准，這就是持續交付的那顆按鈕。環境也能放只給這個環境用的 secret。方案限制要先查：Free 方案只有公開 repo 能用 environment；Pro、Team 的私有 repo 可以用環境的 secret、變數和部署分支限制，但必要審查者、等待計時器與自訂保護規則在私有 repo 要 Enterprise。

一次只能有一個部署：兩個 push 很接近時，兩次部署可能同時在改同一台伺服器。用 concurrency 讓同一群組一次只跑一個：

  deploy-production:
    needs: [build, deploy-staging]
    environment: production
    concurrency:
      group: deploy-production
      cancel-in-progress: false   # 進行中的部署不能被砍

第 15 課的 CI 用 cancel-in-progress: true，因為舊的檢查沒有意義了；部署相反，做到一半被取消，伺服器可能停在新容器起來了、流量還沒切的狀態。false 時後來的那次會排隊。GitHub 預設同一群組最多只留一個等待中的執行，更新的會取代較舊的等待者（部署最新的就好）；需要每次都跑時可以設 queue: max（最多 100 個排隊）。

💡 實務上：核准的人要知道自己在核准什麼
production 的必要審查者常設成 tech lead 或值班的人。核准不該只是按按鈕：先看 staging 的煙霧測試結果、這次包含哪些 PR、有沒有 migration，避開週五晚上和活動檔期。很多團隊會訂「部署凍結期」（例如週年慶前一週只修 bug），用 environment 的部署分支限制或直接暫停 workflow 執行。核准變成例行公事、沒人在看時，就該考慮改成自動檢查（持續部署），而不是保留一顆形式上的按鈕。

部署 job 本身要怎麼碰到伺服器或雲端？不要把長期有效的雲端金鑰放進 secret。GitHub 可以發一個短期的 OIDC token，雲端（例如 AWS IAM）設定成「只信任這個 repo 的 production 環境」，job 用它換到幾十分鐘有效的權限，這需要 permissions: id-token: write，第 19 課會實作。

練習

四題都在 devops/practice/work/16/ 裡做，需要 Docker Desktop 在執行。app/ 是精簡版的 cafe-api：資料放在記憶體、有 /health/ready 和回報版本的 /version，啟動要 1.5 秒。本機 registry 在 127.0.0.1:18160、練習 2 的 nginx 在 18161、練習 3 的在 18162。容器、網路都以 ld-16- 開頭，測試開始和結束時都會清掉。第一次會下載 registry:3.1.2、nginx:1.30.6-alpine、rhysd/actionlint:1.7.12 映像。

練習 1：完成 release.sh（用法 sh release.sh <repo>）。repo 的工作目錄有任何未提交的改動或沒追蹤的檔案就拒絕發佈（exit ≠ 0）；否則從 repo 建置一次映像，同時標記 localhost:18160/cafe-api:<7 碼短 SHA> 與 :<package.json 的 version>，加上 org.opencontainers.image.revision（完整 SHA）、version、created（UTC，例如 2026-11-01T08:30:00Z）三個 label，兩個 tag 都推上去，並在目前資料夾寫 release.json：{ "sha", "version", "digest" }，digest 是 registry 上的。測試每次用隨機版本號產生新的 ex1-repo/，從 registry 的 API 比對兩個 tag 的 digest，再分別製造「改了沒 commit」和「多一個沒追蹤的檔案」，確認你的腳本拒絕發佈、registry 完全沒變。自己試：docker run -d --name ld-16-registry -p 127.0.0.1:18160:5000 registry:3.1.2，跑過一次測試之後 sh release.sh ex1-repo，curl http://localhost:18160/v2/cafe-api/tags/list。

練習 2：完成 deploy.sh <映像參照> 與 rollback.sh，做零停機藍綠部署。up.sh（不用改）會建置 v1、v2 與一個 /health/ready 永遠 503 的壞版本推到 registry、印出三者的 digest 參照，讓 ld-16-blue 跑 v1，並啟動 nginx（nginx/ 掛到 conf.d，active.conf 決定 upstream）。deploy.sh 只接受 …@sha256:… 的參照（給 tag 就 exit ≠ 0、什麼都不動），照課文的六個步驟：判斷顏色、換掉另一個顏色的閒置容器、等 ready（最多 READY_TIMEOUT 秒，預設 30）、煙霧測試 GET /products、改 active.conf 後 nginx -t 再 reload、舊顏色留著；任何一步失敗就 exit ≠ 0、移除新容器、active.conf 不動。rollback.sh 立即切回另一個顏色（它沒在跑就拒絕，active.conf 不動）。測試在每秒約 30 個請求（GET 與 POST 輪流）的持續負載下：部署 v2、回滾（必須用原本那個 ld-16-blue 容器，不能重建或重啟）、再部署 v2、部署壞版本，每一步都不能有失敗的請求；另外會用 tag 呼叫 deploy.sh，以及在另一個顏色已被移除後呼叫 rollback.sh，兩者都要拒絕。自己試：sh up.sh，另開一個終端機 while true; do curl -s localhost:18161/version; echo; sleep 0.2; done，再 sh deploy.sh <V2 那一行的參照>。

練習 3：完成 canary/default.conf。canary/backends.conf（不用改）定義了 upstream blue 與 green，回應內容就是自己的顏色。依 cookie uid 分流：約 10% 的使用者進 green、其餘進 blue，同一個 uid 每次都進同一邊；帶 X-Canary: always 標頭的請求一律進 green。測試先 nginx -t，再用 1000 個隨機 uid（green 要在 5%～15%）、40 個 uid 各送 15 次（每個 uid 只能出現一種顏色）、50 個帶標頭的請求檢查。所有請求都從同一個 IP 來。

練習 4：完成 .github/workflows/deploy.yml。push 到 main 與手動觸發（workflow_dispatch）時執行，最上層 permissions 只有 contents: read。build job：contents: read 與 packages: write；checkout、setup-buildx（建立支援 type=gha 快取的 builder）、用 docker/login-action 登入 ghcr.io、docker/metadata-action 用 type=sha 產生 tag、docker/build-push-action 推送並用 type=gha 的 cache-from／cache-to；把這一步的 digest 設成 job 的 outputs.digest。deploy-staging（environment: staging）與 deploy-production（environment: production，在 staging 之後）都只用 needs.build.outputs.digest 部署（部署步驟用 echo 代替即可），不能自己建置、不能用 latest；production 的 concurrency 群組是 deploy-production，不能取消進行中的部署。所有 uses 釘 40 碼 commit SHA（課文和第 15 課有各 action 的版本，SHA 到該 action 的 Releases 頁查）。測試跑 actionlint，再逐項檢查結構。

練習 5：staging 測過 cafe-api:4e1c2a9。部署 production 時，workflow 從同一個 commit 再 docker build 一次，理由是「同一個 commit 建出來的東西一樣」。這樣做的問題是？

✓ b。建置會抓外部的東西（FROM 的 tag、npm、系統套件），也會寫入建置時間，不保證兩次一樣；推廣的原則是 production 用 staging 測過的同一個 digest。a 把「應該差不多」當成「一定相同」；c 的快取只在同一台機器、同一份快取存在時才命中，換台 runner 或快取過期就是全新建置；d 換名字不會讓內容變成測過的那個。

練習 6：主管問藍綠部署有什麼缺點。哪一個回答最完整？

✓ c。兩個顏色同時在跑，資源是兩倍；切換是全有全無，新版的 bug 會影響所有人（但能很快切回）；資料庫不會跟著分成藍綠兩份，schema 改動要讓兩版都能用（第 17 課）。a 忽略了代價；b 錯在舊版容器還在跑，回滾只是切換；d 錯，練習 2 就是單台主機加 nginx。

練習 7：新版同時帶了兩個修正和一個新的會員集點功能，集點功能在 production 出錯。集點功能是用功能旗標包起來的。比較「關掉旗標」和「回滾整個版本」：

✓ a。旗標把「發布」和「部署」分開，可以只撤掉出問題的那個功能，不必動版本；回滾是整版退回，連好的修正也一起退。b 忽略了修正被退掉；c 旗標的主要用途正是安全發布與緊急關閉；d 旗標的值在執行時讀取（設定或旗標服務），改了就生效，這正是它比部署快的原因。

常見錯誤

  • 部署 latest：latest 每次推送都會移動，伺服器重開或擴容時可能拉到另一個版本，回滾時也不知道上一版是哪個。部署與回滾一律用 digest。
  • 每個環境各自建置：production 跑的不是 staging 測過的東西。建置一次，推廣同一個 digest。
  • 有未提交的改動就發佈：映像裡的程式碼和 revision label 對不上。發佈前檢查 git status --porcelain，它也會列出沒追蹤的檔案。
  • 健康檢查還沒過就切流量：新版還在啟動，nginx 回 502。等 /health/ready，再做煙霧測試，兩個都過了才切。
  • 用 docker restart 重啟 nginx：所有連線被切斷。用 nginx -t 再 nginx -s reload。
  • 只 bind mount 單一設定檔：改寫方式是「寫新檔再改名」時，容器裡還是舊內容。掛整個資料夾。
  • 部署完馬上刪掉舊版本：回滾變成重新部署舊版，要好幾分鐘。舊顏色留到下一次部署。
  • 金絲雀依 IP 或每個請求隨機分流：共用 IP 的一大群人一起進新版，或同一個人在新舊版之間跳。依使用者識別分流。
  • 開了金絲雀卻沒人看指標：比較新舊版的錯誤率和延遲，事先寫好擴大與撤回的門檻。
  • 回滾時忘了資料庫已經 migrate：舊程式碰到新 schema 一樣會壞。讓每次 migration 都相容上一版（第 17 課）。
  • 部署 workflow 允許兩個部署同時跑，或 cancel-in-progress: true：前者互相覆蓋，後者把部署砍在半途。用 concurrency 群組並設 false。
  • 功能旗標永遠不清理：分支越堆越多，沒人知道哪個還有用。全面開放後就刪掉旗標和舊路徑。

小結

  • 持續交付是每個改動都隨時可以上線、由人決定按不按；持續部署是通過檢查就自動上線。
  • 建置一次、推廣同一個產物：git SHA 與 semver 標籤指向同一個映像，部署和回滾用 digest，不用 latest；OCI label 記錄 revision、version、created；工作目錄不乾淨就不發佈。
  • recreate 有停機；rolling、藍綠、金絲雀都有新舊版共存的時間，資料庫要同時相容兩版；藍綠回滾最快但要兩倍資源；金絲雀限制影響範圍，但要有指標才有用；功能旗標把部署與發布分開。
  • 藍綠部署：啟動另一個顏色 → 等 ready → 煙霧測試 → 改 upstream → nginx -t → reload；舊顏色留著，回滾就是切回去；任何一步失敗都讓舊版繼續服務。
  • 金絲雀用 split_clients 依使用者識別分流，用 map 讓測試人員強制走新版。
  • 出事先回滾止血，不能回滾（資料庫不相容）或問題很小時往前修；用健康關卡、煙霧測試、指標關卡自動回滾；用 DORA 的五個指標看交付是否健康。
  • 部署 workflow：build 用 packages: write 推到 GHCR 並輸出 digest，staging、production 都用這個 digest；production 用 environment 等核准，concurrency 群組加 cancel-in-progress: false；雲端權限用 OIDC。
