階段 6：可觀測性與可靠性 · 第 24 課

備份與災難復原：沒還原過的備份不算備份

星期一早上，同事跑 migration 時下錯了一句 DELETE，orders 表少了三個月的訂單。大家鬆了一口氣：「還好每天都有備份。」打開備份資料夾，最新的檔案是 0 byte；往前翻，每一份都是 0 byte。半年前資料庫換了密碼，備份腳本從那天起每晚都失敗，可是它用的是 pg_dump … | gzip > 檔案，結束碼一直是 0，排程也一直顯示成功。

這一課讓備份從「看起來有」變成「證明能用」，再把範圍擴大到整個系統：什麼都沒了的時候，照著哪份文件、花多久能把咖啡店救回來。

這課的路線：
  1. RPO 與 RTO：「要備份」不是需求，「最多能丟多少資料、最多能停多久」才是，這兩個數字要跟老闆一起訂；也先給開場 0 byte 備份的原因（最小答案）。
  2. 備份的種類與不會騙你的備份腳本：pg_dump、實體備份、WAL 封存怎麼選，開場那個 0 byte 的備份為什麼一直「成功」，怎麼讓失敗大聲說出來。
  3. 還原與驗證：用自動化的還原演練證明備份真的能用，量出還原實際要花多久。
  4. 異地、不可變、保留與排程：備份放哪裡才不會跟正式資料一起被刪、被勒索，要留幾份、怎麼排程才不會悄悄停掉。
  5. 整個系統的災難復原：機器、映像、機密、DNS 都沒了的時候，照著 runbook 把服務救回來。
這課會用到：
  • PostgreSQL 課第 37 課的備份：pg_dump 匯出一份邏輯備份，pg_basebackup 複製整個資料目錄，再加上 WAL 封存就能還原到任一時間點。
  • 第 2 課的結束碼與 set -euo pipefail：管線預設只看最後一段的結束碼；pipefail 讓任何一段失敗都算失敗，-e 讓腳本一出錯就停。

從需求開始：RPO 與 RTO

「要備份」不是需求，需求是兩個數字：

  • RPO（復原點目標，Recovery Point Objective）：出事時最多能接受遺失多久的資料。RPO 15 分鐘，表示最近 15 分鐘內的訂單可以不見，再多就不行。
  • RTO（復原時間目標，Recovery Time Objective）：從出事到恢復服務，最多能接受停多久。RTO 1 小時，表示一小時內客人要能再點餐。

兩個數字要跟老闆一起訂，因為越小越貴。不同的資料可以有不同的數字：訂單和集點卡 RPO 5 分鐘、RTO 1 小時；分析報表可以從訂單重算，RPO 一天、RTO 一天就夠了。

從數字推回做法：每天備份一次，RPO 最壞接近 24 小時；要 RPO 5 分鐘，定時匯出做不到，要用 WAL 封存（下一節）。RTO 包含發現問題、決定要還原、拿到備份、還原、驗證、切換流量，每一段都要時間，只有實際演練過才知道總共多久。

不過開場的備份連 RPO 都談不上，因為它根本沒備到東西。原因先講結論：pg_dump … | gzip 這條管線的結束碼只看最後一段的 gzip，換密碼後 pg_dump 連不上資料庫而失敗，gzip 照樣把「什麼都沒有」壓成一個檔、回報成功，排程就一直以為沒事。怎麼寫出失敗會大聲說出來的腳本，細節在後面的〈一個不會騙你的備份腳本〉。

💡 實務上：RPO／RTO 是跟 PM、老闆談出來的
你最常在兩個場合遇到這兩個數字：新服務上線前的檢查清單，以及客戶或資安問卷問「你們的備份策略是什麼」。工程師的工作是把每個選項的代價講清楚，例如「RPO 從 24 小時降到 5 分鐘，要開 WAL 封存或改用 RDS 的 PITR，每月多出儲存費，還要有人維護」，讓決策的人選。談定後寫進文件，之後每次演練拿實測值對照。資深工程師會先問：哪些資料丟了會賠錢或違法？哪些可以重算？停機一小時，客服電話會打給誰？

備份的種類

PostgreSQL 課第 37 課介紹過這幾種，這裡從維運的角度比較：

種類例子RPO還原速度適合
邏輯備份（logical backup）：匯出成 SQL 或封存格式pg_dump兩次匯出的間隔慢：要重新寫入資料、重建索引小型資料庫、搬家、跨大版本升級、只還原一張表
實體備份（physical backup）：複製資料檔pg_basebackup、pgBackRest、Barman搭配 WAL 封存可以到幾秒快：直接放回資料檔，再重播 WAL正式環境的主要備份
WAL 封存與 PITR（時間點還原）archive_command＋基礎備份幾秒到幾分鐘看要重播多少 WAL「還原到誤刪前一分鐘」
快照（snapshot）：某個時間點的磁碟映像EBS snapshot快照的間隔快整台機器；資料庫要確保快照時資料一致
託管服務的備份RDS 自動備份＋手動快照RDS 的 PITR 通常可以到最近 5 分鐘內還原成一個新的執行個體，要改連線位址用 RDS 時的預設選擇

PostgreSQL 18 的 pg_dump 文件自己寫明：除了簡單的情況，pg_dump 通常不適合當正式資料庫的定期備份。它的優點是匯出時不會擋住讀寫、結果可以還原到更新的大版本；缺點是 RPO 只能到匯出的間隔，資料大了以後匯出和還原都很慢。這課的練習用 pg_dump，因為它最容易看清楚「備份、驗證、還原」的每一步；這些步驟換成 pgBackRest 或 RDS 也一樣要做。RDS 的自動備份保留期可以設 0 到 35 天，設 0 等於關掉。

還有兩個常見的誤解：

  • 複寫（replica）不是備份：誤刪的 DELETE 在一秒內就複寫到 replica 了。replica 解決的是「機器壞了」，備份解決的是「資料壞了」。
  • RAID、雲端硬碟的耐用度不是備份：它們保證寫進去的東西不會因為硬體壞掉而不見，但你自己刪掉、勒索軟體加密的資料，它們一樣忠實地保存。

放在哪裡，業界常用 3-2-1 原則：資料至少 3 份（正式資料加兩份備份）、放在 2 種不同的儲存媒介、其中 1 份在異地。雲端上的「異地」通常指另一個 region，而且最好是另一個帳號。

一個不會騙你的備份腳本

開場那個 0 byte 的備份，問題出在管線：第 2 課教過，管線的結束碼只看最後一段，pg_dump 失敗了，gzip 照樣成功壓縮了「什麼都沒有」。可靠的備份腳本要做到：任何一步失敗就以非 0 結束、不留下看起來像備份的半成品、成功時留下可以驗證的資訊。步驟是：

  1. 一致的匯出：用 docker exec（第 10 課）在資料庫容器裡執行 pg_dump -Fc。容器裡的 pg_dump 跟伺服器同一個版本；主機上舊版的 pg_dump 會拒絕匯出比它新的伺服器。-Fc 是 custom 格式：已經壓縮，可以用 pg_restore 選擇性還原。
  2. 寫到暫存檔：寫到同一個資料夾裡的 .cafe-….dump.tmp，全部成功才 mv 成正式檔名。同一個檔案系統裡的 mv 是原子的：別人只會看到完整的檔案或沒有檔案。
  3. 快速驗證：pg_restore --list 讀得出目錄。
  4. manifest：記下各表的列數，還原演練時拿來比對。
  5. 校驗和（checksum）：用 SHA-256（Auth 課第 2 課）算出檔案的雜湊值寫進 .sha256。之後任何一個 byte 改變，雜湊值就不同，可以分辨檔案有沒有壞掉或被換掉。
  6. 更新 LATEST、輸出結果：全部完成才更新「最新一份是哪個」的指標，最後印一行 JSON（大小、耗時），給監控讀。
set -euo pipefail
name=cafe-$(date -u +%Y%m%dT%H%M%SZ)          # 檔名用 UTC 時間
tmp="$OFFSITE_DIR/.$name.dump.tmp"
trap 'rm -f "$tmp"' EXIT                        # 失敗時清掉暫存檔
bytes=$(docker exec ld-24-db pg_dump -U postgres -d cafe -Fc | tee "$tmp" | wc -c)
…驗證、manifest、校驗和…
mv "$tmp" "$OFFSITE_DIR/$name.dump"

pg_restore --list 有一個陷阱。我們把一份 1 MB 的 custom 格式備份截掉後面 30%，模擬「傳到一半連線斷了」：

$ head -c 766622 full.dump > cut.dump
$ docker exec -i ld-24-db pg_restore --list < cut.dump > /dev/null; echo $?
0                                   ← 目錄在檔案開頭，照樣讀得出來
$ docker exec -i ld-24-db pg_restore -f /dev/null < cut.dump; echo $?
pg_restore: error: could not read from input file: end of file
1                                   ← 要真的讀完資料才發現

所以 --list 只能擋下「完全不是備份」的檔案，擋不住只有一半的備份。這就是為什麼 pipefail 不能省：pg_dump 中途失敗時，要靠它讓腳本停下來。完整的驗證交給下一節的還原演練。

用 grep -q 接在管線後面要小心：grep -q 一找到就結束，前面的程式可能因為 SIGPIPE 而以非 0 結束，加了 pipefail 後反而變成「成功也被判失敗」。把輸出先存進變數，再用 grep -q … <<< "$toc" 檢查。

還有兩件事練習沒有要求，正式環境要做：

  • 加密：備份裡有顧客資料。上傳前用 age 或 gpg 以公鑰加密，備份主機上只放公鑰；解密用的私鑰放在別的地方，只有還原時才拿出來。上傳到 S3 也要開伺服器端加密。
  • 角色與權限：pg_dump 只匯出一個資料庫，裡面的 GRANT … TO cafe_app 會被匯出，cafe_app 這個角色本身不會。另外用 pg_dumpall --globals-only 備份角色（裡面有密碼雜湊，跟備份一樣要加密保管），還原時先還原它。

manifest 的列數和 pg_dump 不是在同一個快照裡算的，匯出期間有寫入時兩者可能差幾列。練習時沒有寫入，所以沒問題；正式環境可以改成比對「還原後的列數不少於備份開始前的列數」，或改用實體備份工具內建的驗證。

還原與驗證

備份腳本每天回報成功，只代表檔案產生了。它能不能還原、還原出來的資料對不對、要花多久，只有真的還原一次才知道。還原演練（restore drill）就是定期、自動地做這件事：

  1. 先驗證校驗和：在檔案所在的資料夾執行 sha256sum -c cafe-….sha256。不符就停，壞掉的檔案還原出來的東西不能信。
  2. 還原到全新的臨時容器：不同名稱、跟正式環境同一個映像。絕對不要還原進正式的資料庫：pg_restore --clean 會先刪掉現有的物件，備份之後才寫入的訂單就這樣被蓋掉了。
  3. 還原時遇錯就停：pg_restore 預設遇到錯誤會繼續做完，最後印出 errors ignored on restore: N 並以 1 結束。加 --exit-on-error 在第一個錯誤就停（-1／--single-transaction 也有同樣效果），並且讓 set -e 檢查結束碼。很多人因為「有一些 owner 的錯誤沒關係」而加上 || true，部分還原從此也算成功。
  4. 比對 manifest：用同一句 SQL 數還原後的列數，跟備份時記下的比。
  5. 煙霧測試（smoke test）：對還原出來的資料庫跑 app 最常做的事。練習用 SQL 檢查訂單總額和明細一致、每日營收查得出來；正式環境可以把 app 的映像接到這個資料庫，打幾個 API。
  6. 量 RTO、收拾：從開始到驗證完成花了幾秒，印成 JSON。不論成功或失敗，都用 trap 把臨時容器刪掉。
$ bash restore-drill.sh offsite/cafe-20261101T030000Z.dump
{"ok":true,"rto_seconds":9}

這裡量到的 9 秒只是「還原這份資料」的時間。真正的 RTO 還要加上：發現問題、決定還原、從異地下載備份、改 app 的連線設定、確認服務恢復。資料量長大後還原時間會跟著變長，所以演練要排程（例如每週一次），把 rto_seconds 當成指標記下來，超過目標就告警。

💡 實務上：誤刪資料時，通常只還原一部分
開場那種誤刪，最常見的救法不是把整個資料庫倒回早上 3 點，那樣會把之後的新訂單一起丟掉。做法是把備份還原到旁邊的臨時資料庫（就是演練用的流程），查出被刪掉的那些列，再用 INSERT … SELECT 或匯出、匯入補回正式資料庫；custom 格式可以用 pg_restore -t orders 只還原一張表。動手前先跟負責人確認範圍，補完請 PM 或客服抽查幾筆。平常演練過，這時才不會手忙腳亂。

異地與不可變

備份跟正式資料放在同一台機器、同一個雲端帳號、用同一組權限，等於只有一份：

  • 同事在錯的資料夾 rm -rf，或 IaC（第 20 課）把整個 bucket 刪了。
  • 攻擊者拿到 app 的雲端金鑰，先刪備份、再加密資料庫，然後要贖金（勒索軟體的標準流程）。

保護的層次：

  • 權限分離（第 11 課、第 19 課）：備份程式只有「寫入」權限，沒有刪除；app 的帳號完全碰不到備份。備份放在另一個 AWS 帳號更好，正式帳號被入侵也碰不到。
  • S3 版本控制（versioning）：覆蓋或刪除只會產生新版本或刪除標記，舊版本還在。
  • 不可變備份（immutable backup）：寫入後一段時間內不能修改或刪除。S3 Object Lock 要求 bucket 開啟版本控制，有兩種模式：governance 模式下，有 s3:BypassGovernanceRetention 權限的人仍然可以刪；compliance 模式下，保留期限內任何人都不能刪，包括帳號的 root 使用者，期限也不能縮短。先用 governance 測試設定，確定之後再用 compliance。
  • 生命週期規則（lifecycle）：舊的備份自動轉到較便宜的儲存類別，到期自動刪除，不用自己寫腳本。

保留政策與排程

保留政策（retention policy）決定留哪些備份、留多久。只留最近 7 份，發現「兩週前就開始有髒資料」時就沒救了；全部留，費用一直漲。常見的做法是每日、每週、每月各留幾份：

  • 每日：最近 7 個有備份的日子，每天留最新的一份。
  • 每週：最近 4 個有備份的週（週一到週日），每週留最新的一份。
  • 每月：最近 6 個有備份的月份，每月留最新的一份。

三條規則各自計算，取聯集。日期一律用檔名裡的 UTC 時間判斷：台北時間比 UTC 快 8 小時，23:30 UTC 的備份在台北已經是隔天，用本地時區算，週日的最後一份會被歸到下一週。成熟的備份工具都內建這種規則，例如 restic 的 forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6（它的週也是週一到週日，只計算有備份的日、週、月）。S3 上也可以直接用生命週期規則。練習 3 自己寫一次，是為了看懂這些規則和容易出錯的地方。

排程的選擇：

  • cron（NestJS 課第 21 課）：Linux 傳統的排程程式。crontab 一行是五個時間欄位（分 時 日 月 星期）加一個指令，0 3 * * * /opt/cafe/backup.sh 是每天 03:00。時區是主機的時區；機器剛好關機時那一次就錯過了，執行結果也要自己導到 log。
  • systemd timer（unit 檔的寫法見第 6 課）：用 OnCalendar= 指定時間，觸發同名的 service。Persistent=true 會把上次執行的時間存在磁碟上，關機期間錯過的那次在開機後補跑一次；輸出自動進 journal，systemctl list-timers 看得到下次執行時間。
  • Kubernetes CronJob、雲端的排程服務（例如 EventBridge Scheduler）、託管資料庫內建的備份：在那些平台上就用它們。
# /etc/systemd/system/cafe-backup.service
[Service]
Type=oneshot
ExecStart=/opt/cafe/backup.sh

# /etc/systemd/system/cafe-backup.timer
[Timer]
OnCalendar=*-*-* 03:00:00 UTC
Persistent=true

[Install]
WantedBy=timers.target

排程本身也會壞：timer 被停用、機器下線、腳本卡住。只在「失敗時告警」抓不到這些情況，因為根本沒有執行。要用死人開關（dead man's switch）：每次備份成功就送出「我還活著」（例如把最後成功時間寫成指標 backup_last_success_timestamp_seconds，或呼叫 healthchecks 類服務的網址），一段時間沒收到才告警。告警怎麼送、送給誰，是第 25 課的主題。

整個系統的災難復原

災難復原（disaster recovery，DR）要回答的是：整台機器、整個 AZ、甚至整個 AWS 帳號都沒了，怎麼把咖啡店救回來。資料庫只是其中一項：

項目放在哪裡演練時確認
程式碼git，至少有一份在另一個服務從乾淨的機器 clone 得下來
映像registry，用 digest 釘版本（第 16 課）拉得到上線中的那個 digest
基礎設施IaC（第 20 課）能在另一個 region 建出一套
機密secret manager，另外備份（加密）不靠任何一個人的筆電就拿得到
資料備份、異地、不可變還原演練通過，RTO 在目標內
DNSDNS 服務商TTL 夠短，切換後幾分鐘內生效
runbook不跟系統放在一起的地方新人照著做得完

runbook（操作手冊）是一步一步寫好的處理程序，每一步都有可以直接複製執行的指令和預期結果。出事的時候人很慌，不要指望當下想得起來。

💡 實務上：從「桌上演練」開始
小團隊第一次做 DR，通常不會真的把正式環境關掉，而是先做桌上演練（tabletop exercise）：大家坐下來，主持人說「現在 AWS 帳號被鎖了」，每個人照 runbook 說出自己下一步要做什麼、需要什麼權限、去哪裡拿。這種演練最常發現的是「只有離職同事知道 DNS 帳號密碼」「備份的解密私鑰找不到」這類問題。發現的缺口開成工作單，排進下個迭代修。等桌上演練順了，再挑一個環境真的重建一次。

範圍與成本：第 18 課的多 AZ（RDS Multi-AZ、ALB 跨 AZ）處理的是一個機房掛掉，切換是自動的；整個 region 掛掉要靠跨 region 的備份或複寫，成本和複雜度高很多。大部分的服務做到「多 AZ＋備份複製到另一個 region、演練過怎麼在那裡重建」就夠了，RTO 是幾小時；需要幾分鐘的 RTO，才考慮兩個 region 同時在跑。

演練檢查表：至少一年一次，挑一個上班時間，假設正式環境整個不見了：

  • 只用 runbook 和備份，在全新的環境把服務建起來，記下每一步花的時間。
  • 確認還原出來的資料是哪個時間點的（實際的 RPO），服務多久恢復（實際的 RTO），跟目標比較。
  • 記下 runbook 裡錯的、少的、過時的步驟，當天就修。
  • 換人做：只有一個人會的流程，那個人休假時就等於沒有。

練習

練習 1～3 在 devops/practice 做，都需要 Docker 在跑，寫的都是 bash 腳本（用 bash 檔名 執行）。練習 1、2 的測試每次都會重建 ld-24 的資料庫、寫入隨機數量的訂單，跑完也會收掉；練習 2 需要 jq（第 2 課）。練習 3 在 Debian 容器裡執行，用的是 GNU 版的 date。

練習 1：改寫 backup.sh。環境變數 DB_CONTAINER（預設 ld-24-db）、DB_NAME（預設 cafe）、OFFSITE_DIR（預設 offsite）。用 docker exec 在容器裡執行 pg_dump -Fc，在 OFFSITE_DIR 產生三個檔案：cafe-<UTC 時間>.dump（時間格式 20261101T030000Z）、cafe-<時間>.sha256（sha256sum 的格式，只寫檔名）、cafe-<時間>.manifest.json（{"dump": 檔名, "tables": counts.sql 印出的 JSON}）。先寫暫存檔，用 pg_restore --list 驗證過、全部成功才改名，最後才把 LATEST 的內容改成新的 .dump 檔名；最後一行印出 {"file":…,"bytes":…,"seconds":…}。測試會注入五種失敗：資料庫名稱打錯、pg_dump 傳到一半斷線、pg_dump 回報成功但內容是壞的、OFFSITE_DIR 唯讀、資料庫停了。每一種都要以非 0 結束，OFFSITE_DIR 裡不能多出或少掉任何檔案，LATEST 不變。

練習 2：改寫 restore-drill.sh <dump>（同一個資料夾裡有同名的 .sha256 和 .manifest.json）。依序：在 .dump 所在的資料夾用 sha256sum -c 驗證；用 postgres:18.6-alpine3.24 啟動全新的臨時容器 ld-24-drill，等它就緒（pg_isready -h 127.0.0.1）後建立 cafe 資料庫；用 pg_restore --exit-on-error 還原；用 counts.sql 數列數，跟 manifest 的 tables 比對（jq -e）；跑 smoke.sql（psql -v ON_ERROR_STOP=1）。全部通過印出 {"ok":true,"rto_seconds":秒數}；任何一步失敗都以非 0 結束。成功或失敗都要刪掉臨時容器。測試會用一份好的備份、一份被改了一個 byte 的、一份 manifest 不符的、一份訂單總額跟明細對不起來的（只有煙霧測試抓得到）、一份還原時會出錯的備份來跑，並確認正式的 ld-24-db 完全沒被動到。

練習 3：改寫 prune.sh [--dry-run] <資料夾>。只處理檔名完全符合 cafe-YYYYMMDDTHHMMSSZ.dump 的備份，依檔名裡的 UTC 時間保留：最近 7 個有備份的日子、最近 4 個有備份的 ISO 週（週一到週日，date -u -d 20261101 +%G-%V）、最近 6 個有備份的月份，每一格留最新的一份，三條規則取聯集，最新的一份一定留。刪除時同名的 .sha256、.manifest.json 一起刪；LATEST 和格式不符的檔案一律不碰。每個要刪的 .dump 印一行檔名；--dry-run 只印、不刪。測試會產生 13 個月約 500 份假備份（含 23:30 UTC 的檔案），在 TZ=Asia/Taipei 下執行，比對留下的集合。

練習 4：咖啡店每天凌晨 3 點做一次 pg_dump，備份都有驗證過。資料庫在晚上 11 點損壞，會遺失多久的資料？這套做法能做到的 RPO 是多少？

✓ c。能還原的最新時間點是凌晨 3 點，之後的寫入都不在備份裡，這次丟掉 20 小時；事故發生在下一次備份前一刻時，最多丟掉將近 24 小時，所以這套做法只能承諾「RPO 24 小時」。要更小的 RPO，就要更頻繁的備份或 WAL 封存。a 把「有備份」當成「不會遺失」；b 方向算反了；d 說的是 RTO。

練習 5：備份腳本已經跑了一年，每天都以 exit 0 結束，監控從來沒告警過，但從來沒有人還原過。這份備份可靠嗎？

✓ b。開場的 0 byte 備份就是 exit 0；截斷的備份連 pg_restore --list 都讀得出來；少了角色的備份要真的還原才會出錯。a、c 都只是間接的訊號；d 太絕對，pg_dump 可以當備份，只是 RPO 和還原速度有限，而且同樣要演練。

練習 6：備份上傳到同一個 AWS 帳號的 S3 bucket，app 的 IAM 角色對這個 bucket 有完整權限。同事說：「S3 的耐用度是 11 個 9，不會掉。」風險在哪裡？

✓ a。耐用度保證的是「寫進去的不會因為硬體壞掉而不見」，不管是誰下的刪除指令。要用權限分離（備份只能寫、app 碰不到）、另一個帳號、版本控制加 Object Lock。b 沒開版本控制時刪了就沒了；c 放回同一台機器更糟；d 加密防的是被讀走，防不了被刪。

練習 7：資料庫已經有一台即時同步的 replica，還有自動切換。主管問：「這樣是不是可以不用備份了？」

✓ d。replica 忠實地重現主機做的每一件事，包括錯的那件。要能回到過去，需要和正式資料分開保存、有時間點的備份（最好加上 PITR）。a、b 混淆了高可用和備份；c 延遲不是重點，就算零延遲也一樣救不回誤刪。

常見錯誤

  • 管線沒有 pipefail：pg_dump | gzip 失敗了仍然回 0，留下空的備份。每個腳本開頭都寫 set -euo pipefail。
  • 直接寫到最終檔名：失敗時留下半個檔案，看起來像一份備份。寫暫存檔，成功才 mv，用 trap 清掉暫存檔。
  • 以為 pg_restore --list 讀得出來就是完整的：它只讀開頭的目錄。完整的驗證是實際還原。
  • 從來沒有測試還原：備份唯一的用途是還原。排程做還原演練，記錄 RTO。
  • 用主機上比伺服器舊的 pg_dump：它會拒絕匯出。在資料庫容器裡執行，或裝同一個大版本。
  • 忘了角色與權限：pg_dump 不匯出角色，還原時 GRANT 會失敗。另外備份 pg_dumpall --globals-only。
  • pg_restore 遇錯繼續，或加了 || true：只還原了一部分也算成功。加 --exit-on-error，檢查結束碼。
  • 還原演練還原進正式的資料庫：--clean 會蓋掉備份之後的資料。一律用全新的臨時環境。
  • 備份沒有加密，或和正式環境用同一組權限：外洩一次就是全部的歷史資料；被入侵時一起被刪。用公鑰加密、分開的帳號與權限、Object Lock。
  • 保留政策用本地時區算日期：跨午夜的備份被歸錯天、錯週。一律用 UTC。
  • 把 replica 或 RAID 當成備份：它們會把錯誤一起複製過去。
  • 排程只在失敗時告警：排程沒執行就不會有失敗。用死人開關，監控「最後成功時間」。

小結

  • 從 RPO（最多丟多少資料）和 RTO（最多停多久）推出做法；不同的資料可以有不同的數字。
  • pg_dump 適合小型資料庫與搬家；正式環境的主力是實體備份加 WAL 封存（PITR），或託管服務的自動備份。replica、RAID 不是備份。
  • 可靠的備份腳本：pipefail、暫存檔加原子改名、驗證、manifest、校驗和、最後才更新 LATEST，輸出一行 JSON 給監控。
  • 還原演練：先驗校驗和，還原到全新的臨時環境，--exit-on-error，比對列數，跑煙霧測試，量出 RTO，定期自動執行。
  • 3-2-1、權限分離、另一個帳號、版本控制與 Object Lock，讓備份撐得過誤刪和勒索軟體。
  • 保留政策用 UTC 計算日、週、月；排程用 systemd timer（Persistent=true）或平台的排程，並用死人開關監控。
  • 災難復原涵蓋程式碼、映像、IaC、機密、資料、DNS 與 runbook，定期換人演練。

備份失敗、演練超時、排程沒跑，都要有人知道：下一課處理告警、值班與事故處理。
