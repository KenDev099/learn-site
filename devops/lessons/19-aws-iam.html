階段 5：雲端與基礎設施即程式碼 · 第 19 課

AWS IAM 與帳號安全：最小權限、角色與 OIDC

咖啡店剛開了 AWS 帳號。工程師為了趕上線，用 root 帳號建了一組 access key，放進 cafe-api 的 .env 和 GitHub 的 repository secrets，部署和程式都用這一組。三個月後有人把 .env 推上公開的 fork，幾小時內帳號被拿去開了幾十台挖礦機器，S3 裡顧客上傳的照片也被整包下載。這組金鑰能做任何事，而且不會過期。

這一課處理「誰可以對什麼做什麼」，目標是帳號裡不再有長期金鑰。練習都在瀏覽器裡做，用虛構的帳號 123456789012 和 GitHub 組織 cafe-org，不需要 AWS 帳號。

這課的路線：
  1. 帳號的第一天：root 為什麼不能拿來日常用，開帳號當天要先鎖好哪些東西。
  2. policy 與評估規則：讀寫 IAM policy，預測一個請求會被允許還是拒絕，替 cafe-api 只開它真正需要的權限。
  3. 用角色取代金鑰、GitHub Actions 用 OIDC：程式和部署流程改用會自動過期的臨時憑證，沒有長期金鑰可以外洩。
  4. 危險寫法與驗證政策：權限開太寬最常見的寫法，以及怎麼在 CI 裡自動檢查政策有沒有被改寬。
這課會用到：
  • Auth 課第 1 課的認證與授權：認證確認「你是誰」，授權決定「你能做什麼」。IAM 兩件事都管。
  • Auth 課第 13 課的 OpenID Connect：身分提供者簽一張 ID token（一種 JWT，Auth 課第 8 課），收的一方驗簽章、檢查 claims 才相信它。
  • 第 18 課的 AWS 元件：EC2 是虛擬機，ECS 跑容器，S3 放檔案，它們都在你的帳號裡。

帳號的第一天：root、MFA 與 Identity Center

註冊 AWS 時用的那組 email 和密碼，登入後的身分叫 root 使用者（root user）。它對帳號裡所有服務、所有資源都有完整權限；在單獨的帳號裡，任何 IAM 政策都限制不了它（只有加入 AWS Organizations 之後，組織的 SCP 才能限制成員帳號的 root）。root 外洩等於整個帳號外洩，所以它只用在少數「非 root 不可」的操作，例如關閉帳號、變更 root 的 email 或密碼、某些帳單設定。

開帳號當天要做的事：

  1. root 開 MFA（多因素認證，Auth 課第 14 課）。AWS 現在對 root 預設強制 MFA，但要你自己完成註冊；用實體安全金鑰或 passkey 比簡訊可靠。密碼和 MFA 裝置分開保管，至少兩個人知道怎麼取得。
  2. root 不建 access key。access key 是一組 ID 加上一把私密金鑰（secret access key），讓程式或 CLI 不用登入畫面就能呼叫 AWS API；root 的 access key 等於一把不能被限制的萬能鑰匙。已經建了就刪掉。
  3. 人員用 IAM Identity Center 登入。Identity Center 是 AWS 的單一登入（SSO）：每個人有自己的帳號，透過 permission set（一組要套用到帳號的權限）拿到權限，登入後拿到的是會過期的臨時憑證。CLI 用 aws configure sso 設定一次，之後 aws sso login 就好，電腦上不會留下長期金鑰。
  4. 設 Budgets 警示（第 18 課）。帳號被盜最先出現的徵兆常常是帳單。

IAM（Identity and Access Management）裡有三種身分，常被混在一起：

名稱是什麼憑證什麼時候用
IAM user帳號裡的一個長期身分密碼、長期 access key（AKIA 開頭）盡量不用。只剩無法用角色的舊系統
IAM group一群 user，把政策掛在群組上沒有，它不是身分，不能登入管理多個 user 的權限
IAM role一組權限，誰被允許就可以「扮演」（assume）它臨時憑證（ASIA 開頭，加上 session token），會過期程式、CI、跨帳號存取、人員透過 Identity Center 登入

role 和 Auth 課第 18 課的 RBAC 角色是同一個想法：權限綁在角色上，不綁在個人上。差別是 AWS 的 role 本身也是一個身分，扮演它的人拿到的是一組新的、短期的憑證。

資深一點的做法是一個環境一個帳號：production、staging、開發各自是 AWS Organizations 裡的獨立帳號。帳號是 AWS 最硬的隔離邊界，staging 的權限設錯了，也碰不到 production 的資料。
💡 實務上：接手一個舊帳號，先盤點長期金鑰
到新公司或接手外包留下的 AWS 帳號，第一件事是下載 credential report（IAM 主控台的 Credential report，或 aws iam generate-credential-report 再 aws iam get-credential-report）。它是一份 CSV，每個 user 和 root 一列：有沒有開 MFA、有沒有 access key、金鑰最後一次用在哪天、哪個服務。先找三種：root 有 access key、user 沒開 MFA、很久沒用的金鑰。處理時不要一口氣刪掉，先把金鑰設成 Inactive（停用可以馬上恢復，刪除不行），觀察一兩週沒有東西壞掉再刪。整理成一張表交給主管和資安，每一把金鑰寫上要換成什麼：role、OIDC 或 Identity Center。

policy 長什麼樣子

policy（政策）是一份 JSON，描述允許或拒絕哪些動作。掛在 user、group、role 身上的叫身分型政策（identity-based policy）。下面是 cafe-api 的 role 要用的一段：

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadsReadWrite",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::cafe-uploads-prod/uploads/*"
    }
  ]
}
欄位意思
Version政策語言的版本，固定寫 "2012-10-17"（不是今天的日期）
Statement一條條規則，彼此獨立評估
Sid這條規則的名字，選填，方便閱讀和查 log
EffectAllow（允許）或 Deny（拒絕）
Action哪些 API 動作，格式是「服務前綴:動作名稱」。可以用萬用字元：* 代表任意多個字元、? 代表一個字元，例如 s3:Get*
Resource作用在哪些資源，用 ARN 寫，也可以用萬用字元
Condition選填，在什麼條件下這條規則才成立
Principal對誰。只出現在掛在資源上的政策（例如 bucket policy）和信任政策；身分型政策不寫，因為它掛在誰身上就是對誰

ARN（Amazon Resource Name）是 AWS 資源的完整名稱：arn:aws:服務:region:帳號:資源。S3 的 bucket 名稱全球唯一，所以 region 和帳號兩段是空的：

資源ARN
bucket 本身arn:aws:s3:::cafe-uploads-prod
bucket 裡 uploads/ 底下的物件arn:aws:s3:::cafe-uploads-prod/uploads/*
SSM 參數 /cafe/prod/db-urlarn:aws:ssm:ap-east-2:123456789012:parameter/cafe/prod/db-url
KMS 金鑰arn:aws:kms:ap-east-2:123456789012:key/0f3a9c2e-…
IAM rolearn:aws:iam::123456789012:role/cafe-api（IAM 不分 region，region 那段是空的）

最常見的錯誤是搞混 bucket ARN 和物件 ARN。s3:GetObject、s3:PutObject 作用在物件上，Resource 要寫 bucket/路徑；s3:ListBucket（列出 bucket 裡有哪些物件）作用在 bucket 本身，Resource 要寫不含斜線的 bucket ARN。把 ListBucket 的 Resource 寫成 bucket/*，政策存得進去、也不會報錯，只是永遠不會生效：

ListBucket 要限制只能列某個資料夾，用 Condition。S3 在 ListBucket 的請求裡會帶 s3:prefix 這個條件鍵（condition key），值是使用者要列的前綴：

{
  "Effect": "Allow",
  "Action": "s3:ListBucket",
  "Resource": "arn:aws:s3:::cafe-uploads-prod",
  "Condition": { "StringLike": { "s3:prefix": "uploads/*" } }
}

Condition 的結構是「運算子 → 條件鍵 → 值」。規則：

  • StringEquals 完全相等、StringLike 可以用 * 和 ?，兩者都分大小寫；StringNotEquals、StringNotLike 是反過來。
  • 不同運算子、不同條件鍵之間是「且」；同一個條件鍵給多個值（陣列）是「或」。
  • 請求裡沒有這個條件鍵時，StringEquals、StringLike 不成立；StringNotEquals、StringNotLike 反而成立。寫 Deny 時這點很重要。

其他常見的條件鍵：aws:SourceIp（請求來源 IP，搭配 IpAddress 運算子）、aws:PrincipalTag/team（呼叫者身上的標籤，就是 Auth 課第 19 課的 ABAC：依屬性決定權限）、aws:SecureTransport（是不是走 HTTPS）。

Action 的服務前綴和動作名稱不分大小寫（s3:GetObject 和 S3:getobject 一樣）；Resource 的 ARN 和 StringEquals 的值分大小寫。uploads/ 和 Uploads/ 是兩個不同的前綴。

AWS 怎麼決定允許或拒絕

每一個 API 請求，AWS 都會把所有適用的政策拿出來評估，順序跟政策寫在哪裡、Statement 排第幾條都無關：

三個名詞：

  • 隱含拒絕（implicit deny）：沒有任何 Allow 符合，就拒絕。AWS 預設什麼都不給，所以新建的 role 什麼都不能做。
  • 明確拒絕（explicit deny）：有一條 "Effect": "Deny" 符合，就拒絕，不管別處有多大的 Allow。Deny 用來畫一條誰都跨不過的線，例如「production 的 bucket 任何人都不能刪物件」。
  • 資源型政策（resource-based policy）：掛在資源上的政策，例如 S3 的 bucket policy、KMS 的 key policy。它有 Principal，說明對誰。同一個帳號內，身分型和資源型政策取聯集：任一邊允許、而且沒有 Deny，就允許。

右邊那一欄是進階的上限機制：組織管理者用 SCP（Service Control Policy）規定某些帳號整個不能做什麼（例如不准關掉 CloudTrail），平台團隊用 permission boundary 讓開發者可以自己建 role，但建出來的 role 權限不能超過邊界。它們本身不給權限，只會把能拿到的權限再收窄。

KMS 是例外：每把金鑰都有 key policy，金鑰的權限以它為主。預設的 key policy 把權限交給帳號，帳號裡的 IAM 政策才有作用；如果有人把 key policy 改成只列特定 role，其他人的 IAM 政策寫了 kms:Decrypt 也沒用。查 KMS 權限問題時，兩邊都要看。
💡 實務上：看到 AccessDenied，先讀錯誤訊息的後半句
cafe-api 上線後最常收到的 IAM 問題就是 AccessDenied。很多服務的錯誤訊息長這樣：User: arn:…:role/cafe-api is not authorized to perform: s3:GetObject on resource: … because no identity-based policy allows the s3:GetObject action。後半句是 because no … policy allows 就是隱含拒絕，去補 Allow；是 with an explicit deny in a service control policy 這類寫法就是明確拒絕，要找那條 Deny，它常常不在你正在看的那份政策裡（可能在 SCP、bucket policy）。不是每個服務都會寫出政策類型。查的順序：先 aws sts get-caller-identity 確認程式到底用了哪個身分（SDK 撿到別組憑證很常見），再看身分型、資源型、SCP、permission boundary。不要為了先讓它動起來就加 s3:*，臨時的寬權限很少有人回來收。

用角色取代金鑰

第 11 課處理過金鑰外洩：輪替、撤銷、清 git 歷史。最好的處理是根本沒有長期金鑰可以外洩。AWS 的做法是 STS（Security Token Service）發臨時憑證（temporary credentials）：一組 access key ID、secret、session token，加上到期時間（從十幾分鐘到幾小時），過期就失效。即使被偷，攻擊者能用的時間也很短。

程式跑在 AWS 上時，不用自己拿憑證：

  • EC2 instance profile：把一個 role 掛在機器上。機器上的程式向執行個體中繼資料服務（IMDS，位址 169.254.169.254）要憑證，AWS 會在到期前自動換新。AWS SDK 預設就會去找它，程式碼裡不用寫任何金鑰。
  • IMDSv2：要先用 PUT 拿一個 session token，之後的 GET 都要帶著它。這擋掉了一種經典攻擊：程式有 SSRF 漏洞（Auth 課第 22 課），攻擊者讓伺服器去 GET 169.254.169.254 把 role 的憑證讀出來。新的機器一律設成只接受 IMDSv2。
  • ECS task role：Fargate 上的容器用 task role 拿憑證。注意另一個長得很像的 task execution role：那是 ECS 自己用來拉 ECR 映像、寫 log、讀 secret 注入環境變數的，跟你的程式要用的權限分開。
同一段程式，不同地方跑：
  筆電    → aws sso login 拿到的臨時憑證（Identity Center）
  EC2     → instance profile 的 role
  Fargate → task role
  CI      → OIDC 換到的 role（下一節）
程式碼裡：new S3Client({ region: 'ap-east-2' })，沒有任何金鑰

AWS SDK 會依序找環境變數、本機的設定檔、容器或機器的中繼資料，找到第一組就用。所以程式碼完全不必知道憑證從哪來；環境變數裡出現 AWS_SECRET_ACCESS_KEY 本身就是警訊。

扮演 role 的權限是兩邊都要同意的：role 的信任政策（trust policy）說「誰可以扮演我」，扮演者那邊也要有 sts:AssumeRole 之類的權限（AWS 服務除外）。EC2 和 ECS 的 role，信任政策的 Principal 寫的是 {"Service": "ec2.amazonaws.com"} 或 {"Service": "ecs-tasks.amazonaws.com"}。

GitHub Actions 用 OIDC 部署

CI 跑在 GitHub 的機器上，不是 AWS 的，沒有 instance profile 可以用。以前的做法是把 IAM user 的 access key 放進 repository secrets，第 15 課說過這有多危險。現在的做法是 OIDC 聯合身分（web identity federation）：GitHub 當身分提供者，替每一次 job 簽一張 JWT，寫明「我是哪個 repo、哪個分支或 environment 的 job」；AWS 驗證簽章、檢查 role 的信任政策，通過就發臨時憑證。這跟 Auth 課第 13 課的 OpenID Connect 是同一套：ID token 就是 JWT，你在網站上驗 Google 的 token，這裡換 AWS 驗 GitHub 的。

token 裡跟授權有關的 claims：

claim值意思
isshttps://token.actions.githubusercontent.com簽發者，AWS 用它找到對應的 OIDC provider 與公鑰
audsts.amazonaws.com這張 token 是給誰的。官方的 configure-aws-credentials 預設要這個值
subrepo:cafe-org/cafe-api:environment:production哪個 repo 的哪種 job。job 有 environment 時是 …:environment:名稱；沒有時，PR 觸發的是 …:pull_request，其他是 …:ref:refs/heads/分支 或 …:ref:refs/tags/標籤

在 AWS 這邊要做兩件事。第一，在 IAM 建一個 OIDC provider，URL 是 https://token.actions.githubusercontent.com、audience 是 sts.amazonaws.com，它的 ARN 是 arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com。第二，建 role cafe-deploy-prod，信任政策寫：

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:…（練習 3 要你寫）"
      }
    }
  }]
}

sub 是整個設定裡最重要的一行。GitHub 替每一個 repo 的 workflow 簽 token，簽發者都是同一個。信任政策只檢查 aud 的話，任何人在自己的 repo 寫個 workflow，就能扮演你的部署 role。sub 寫成 repo:cafe-org/*，組織裡任何一個 repo（包括實習生的練習 repo）都能部署 production；寫成 repo:cafe-org/cafe-api:*，任何分支、任何 PR 都能。用 environment:production 綁定，再在 GitHub 把 production environment 設成需要核准、只允許 main 分支部署（第 16 課），「誰能拿到 production 權限」就由 GitHub 的核准流程把關。

workflow 這邊（接第 16 課的 deploy job）：

  deploy:
    runs-on: ubuntu-24.04
    environment: production
    permissions:
      id-token: write    # 讓 job 能向 GitHub 要 OIDC token
      contents: read
    steps:
      - uses: aws-actions/configure-aws-credentials@e1253824e5c10ff9df46874f81ed3ec929e19cfd # v6.3.0
        with:
          role-to-assume: arn:aws:iam::123456789012:role/cafe-deploy-prod
          aws-region: ap-east-2
      - run: aws sts get-caller-identity   # 印出 assumed-role/cafe-deploy-prod/…，確認扮演成功
GitHub 從 2026-07-15 起，新建立的 repo 預設使用不會變的 sub 格式，把組織與 repo 的數字 ID 加進去，例如 repo:octo-org@123456/octo-repo@456789:ref:refs/heads/main；之前建立的 repo 維持舊格式，除非組織或 repo 選擇改用（改名、轉移也會切換）。數字 ID 的好處是：repo 被刪掉或改名後，別人註冊同名 repo 也拿不到同樣的 sub。寫信任政策前，先確認自己的 repo 是哪一種格式。本課練習的 cafe-org/cafe-api 是舊 repo，用舊格式。
💡 實務上：把 CI 裡的 access key 換成 OIDC，不中斷部署的順序
很多團隊的 repository secrets 裡還躺著 AWS_ACCESS_KEY_ID。換掉的順序：① 建 OIDC provider 和 cafe-deploy-prod role，權限先跟舊 user 一樣；② workflow 改用 role-to-assume，部署一次，確認 aws sts get-caller-identity 印出的是 role；③ 刪掉 repository secrets 裡的兩個金鑰；④ 舊 access key 設成 Inactive，用 credential report 或 aws iam get-access-key-last-used 確認沒有其他地方還在用，再刪掉 user；⑤ 最後才收窄 role 的權限（只留推 ECR、更新 ECS 服務需要的）。staging 和 production 各用一個 role、各綁自己的 environment，staging 的 workflow 出事也拿不到 production 的權限。

危險寫法

最小權限（least privilege）是只給完成工作所需的最少權限。真實帳號裡最常看到的違反方式：

寫法問題改成
"Action": "*", "Resource": "*"就是管理員，外洩一次全帳號淪陷列出實際用到的動作與資源
s3:* 對整個 bucket包含刪物件、改 ACL、改 bucket policy；也碰得到不該碰的前綴只列 s3:GetObject、s3:PutObject，Resource 限定前綴
iam:PassRole 給 *PassRole 是「把某個 role 交給 AWS 服務去用」的權限（例如建 EC2 時指定 instance profile）。給 * 時，只能開機器的人可以把管理員 role 掛到新機器上，再從機器上拿到管理員憑證，變相提權Resource 寫具體的 role ARN，加 iam:PassedToService 條件
Allow 搭配 NotAction「除了這些以外全部允許」，連 AWS 以後新增的服務也自動允許Allow 只用 Action 白名單；NotAction 只適合搭配 Deny
bucket policy 的 "Principal": "*" 搭 Allow全世界都能存取（Block Public Access 開著時會擋下，被關掉就公開了）Principal 寫具體的 role；要公開的檔案走 CloudFront
OIDC 信任政策沒有 sub任何 GitHub repo 都能扮演sub 用 StringEquals 寫死 repo 與 environment

AWS 的 IAM Access Analyzer 能幫忙抓：在主控台編輯政策時，它的政策驗證會即時列出語法錯誤與安全警告（例如 PassRole 搭 *），CLI 是 aws accessanalyzer validate-policy；未使用的存取分析會列出 90 天沒用過的權限和 role，讓你慢慢收窄（這個要另外付費）。實務上常見的節奏是：先給一個合理的範圍上線，看 CloudTrail 裡實際呼叫了哪些 API，再把沒用到的拿掉。

驗證政策：simulate-custom-policy

寫完政策，不必真的去刪檔案才知道擋不擋得住。aws iam simulate-custom-policy 把政策 JSON 和一組「動作＋資源＋條件鍵」交給 IAM 評估，不會執行任何動作，資源也不必存在，回傳的 EvalDecision 是 allowed、explicitDeny 或 implicitDeny，就是上面流程圖的三個結果。它需要一個 AWS 帳號和 iam:SimulateCustomPolicy 權限，本課的練習用不到，有帳號時可以這樣試：

aws sts get-caller-identity          # 先確認自己是誰、在哪個帳號

aws iam simulate-custom-policy \
  --policy-input-list file://cafe-api-policy.json \
  --action-names s3:GetObject s3:DeleteObject \
  --resource-arns arn:aws:s3:::cafe-uploads-prod/uploads/a.jpg arn:aws:s3:::cafe-uploads-prod/private/a.csv \
  --query 'EvaluationResults[].[EvalActionName,EvalResourceName,EvalDecision]' --output table

aws iam simulate-custom-policy \
  --policy-input-list file://cafe-api-policy.json \
  --action-names s3:ListBucket --resource-arns arn:aws:s3:::cafe-uploads-prod \
  --context-entries ContextKeyName=s3:prefix,ContextKeyValues=private/,ContextKeyType=string

把「應該允許」和「應該拒絕」的請求各列一組，放進 CI 每次跑，政策被誰改寬了就會失敗。練習 1、3 的隱藏測試就是這樣做的，只是評估器在瀏覽器裡。

練習

三題都是 TypeScript。政策用物件寫，跟 JSON 的差別只在 key 不用加引號；型別已經宣告好，Effect 寫錯字會直接報錯。

練習 1：寫出最小權限的政策。替 cafe-api 的 role 完成 policy，只能：在 cafe-uploads-prod 的 uploads/ 底下 s3:PutObject 與 s3:GetObject；s3:ListBucket 只能列 uploads/ 開頭的前綴（用 s3:prefix 條件）；用 ssm:GetParameter、ssm:GetParameters 讀 ap-east-2 帳號 123456789012 裡 /cafe/prod/ 底下的參數；用 kms:Decrypt 解密，但只限 KEY_ARN 這把金鑰。不能用 *、s3:*、NotAction，Resource 不能只寫 *。測試會用一個 IAM 評估器檢查一組該允許與該拒絕的請求。

練習 2：預測評估結果。實作 conditionMatches、statementMatches 與 evaluate(identity, resource, req)，回傳 'allowed'、'explicitDeny' 或 'implicitDeny'。規則照本課的流程圖：同一帳號內身分型（identity）與資源型（resource）政策取聯集，任何符合的 Deny 優先，Statement 的順序不影響結果。Action 不分大小寫、Resource 與條件值分大小寫；資源型政策的 Principal 是 '*' 或列出的 ARN 之一才適用，身分型政策沒有 Principal；有 NotAction 的 Statement 適用於「不在清單裡」的動作。條件運算子只要支援 StringEquals、StringLike、StringNotEquals、StringNotLike，請求裡沒有該條件鍵時照本課說的規則處理。like 已經寫好，它分大小寫。

練習 3：鎖住 GitHub OIDC 的信任政策。替 role cafe-deploy-prod 完成 trustPolicy：Principal 是帳號 123456789012 裡 token.actions.githubusercontent.com 的 OIDC provider（Federated），Action 只有 sts:AssumeRoleWithWebIdentity，aud 必須是 sts.amazonaws.com，sub 只允許 cafe-org/cafe-api 這個 repo 的 production environment（舊格式，不含數字 ID）。測試會拿一組 token 的 claims 模擬扮演：只有該 repo 的 production 部署 job 能過，同 repo 的其他分支、PR、其他 environment、組織裡的其他 repo、aud 不符都要被拒絕。

練習 4：cafe-api 的 role 掛了兩份政策：一份 Allow s3:*（Resource 是整個 bucket 的物件），另一份 Deny s3:DeleteObject。程式呼叫 DeleteObject 刪 uploads/a.jpg，結果是？

✓ b。評估時先找有沒有符合的 Deny，有就是 explicitDeny，跟 Allow 的範圍大小、政策的順序都無關（a、c 錯）。互相衝突的政策是合法的，而且是刻意的寫法：用大範圍的 Allow 加一條 Deny 畫出誰都跨不過的線（d 錯）。

練習 5：同事寫了 {"Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::cafe-uploads-prod/*"}，說「* 什麼都包含」。程式呼叫 ListObjectsV2 列 bucket，會怎樣？

✓ c。arn:aws:s3:::cafe-uploads-prod/* 要求後面有一個 /，bucket ARN 沒有，所以這條 Allow 永遠不符合，結果是隱含拒絕（a 錯）。政策語法沒問題，存得進去，這正是它難發現的原因（b 錯）。* 是萬用字元，不是字面上的星號（d 錯）。要列 bucket 就把 Resource 寫成 bucket ARN，再用 s3:prefix 條件限制能列的前綴。

練習 6：cafe-deploy-prod 的信任政策只檢查 token.actions.githubusercontent.com:aud 等於 sts.amazonaws.com，沒有檢查 sub。會怎樣？

✓ a。GitHub 替所有 repo 的 job 簽 token，簽發者都是 token.actions.githubusercontent.com，aud 也都是 sts.amazonaws.com；aud 只說明「這張 token 要給 AWS STS」，不說明是哪個帳號、哪個 repo（b 錯）。OIDC provider 只是讓 AWS 信任 GitHub 這個簽發者，不會限制組織（c 錯）。能區分 repo、分支、environment 的只有 sub；官方文件明確建議檢查 sub，但不能指望 AWS 每次都替你擋下（d 錯）。

練習 7：cafe-api 改成跑在 EC2 上，要讀 S3 的 uploads/。哪一種做法最好？

✓ d。instance profile 給的是會自動換新、會過期的臨時憑證，機器上沒有長期金鑰可以外洩；IMDSv2 擋掉透過 SSRF 讀中繼資料的攻擊。a 仍然是長期金鑰，備份、映像、日誌、別人的電腦都可能帶走它（第 11 課）。b 只是把長期金鑰換個地方放，而且要讀 Parameter Store 本來就需要權限，那份權限又從哪來？c 是最糟的：root 不能被任何政策限制。

常見錯誤

  • 日常用 root 帳號，或替 root 建 access key：root 不能被 IAM 政策限制，外洩就是整個帳號。root 開 MFA、不建金鑰，人員用 Identity Center 登入。
  • 程式、CI、筆電用長期 access key：遲早出現在 git、映像、log 或 .env 裡（第 11 課）。程式用 instance profile 或 task role，CI 用 OIDC，人用 aws sso login。
  • 為了方便寫 Resource: "*" 或 s3:*：一次程式漏洞就能刪掉整個 bucket。列出實際的動作，Resource 寫到前綴。
  • 搞混 bucket ARN 與物件 ARN：ListBucket 的 Resource 寫成 bucket/* 不會報錯，只是永遠不生效。ListBucket 用 bucket ARN 加 s3:prefix，物件動作用 bucket/前綴/*。
  • OIDC 信任政策沒有限制 sub，或寫成 repo:組織/*：別的 repo、別的分支、PR 都能拿到 production 權限。sub 用 StringEquals 寫死 repo 與 environment，並確認 repo 用的是舊格式還是含數字 ID 的新格式。
  • iam:PassRole 給 *：能開機器的人就能把管理員 role 掛到機器上，變相提權。Resource 寫具體的 role，加 iam:PassedToService。
  • Allow 搭配 NotAction：等於「其他全部允許」，AWS 新服務也自動被允許。NotAction 只搭配 Deny。
  • 以為 Statement 的順序或政策的先後會影響結果：評估是「有 Deny 就拒絕、有 Allow 就允許、都沒有就拒絕」，跟順序無關。
  • 查 KMS 權限只看 IAM 政策：key policy 也要允許。兩邊都看。
  • 把 task execution role 和 task role 混成一個：拉映像、寫 log 的權限和程式要用的權限混在一起，兩邊都變寬。分開兩個 role。

小結

  • 開帳號第一天：root 開 MFA、不建 access key、只做非 root 不可的事；人員用 IAM Identity Center；設 Budgets 警示。可以的話，一個環境一個帳號。
  • policy 由 Effect、Action、Resource、Condition（資源型政策再加 Principal）組成。Action 不分大小寫，Resource 和 StringEquals 分大小寫；ListBucket 用 bucket ARN，物件動作用 bucket/前綴/*。
  • 評估規則：預設隱含拒絕；任何符合的 Deny 優先；同一帳號內身分型與資源型政策取聯集；SCP、permission boundary 只能收窄。KMS 還要看 key policy。
  • 用角色取代金鑰：EC2 用 instance profile（只接受 IMDSv2）、ECS 用 task role，STS 發的臨時憑證會自動換新、會過期。
  • GitHub Actions 用 OIDC：id-token: write 拿 JWT，STS 依信任政策檢查 aud＝sts.amazonaws.com 與 sub＝指定的 repo 和 environment，換到預設 1 小時的憑證。
  • 危險寫法：*、s3:*、PassRole 給 *、Allow 搭配 NotAction、Principal *、沒有 sub 的信任政策。用 Access Analyzer 和 simulate-custom-policy 驗證，把該允許與該拒絕的請求寫成測試。
