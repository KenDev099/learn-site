階段 4：自動化交付 · 第 14 課

Git 協作與救援：分支、合併、revert、bisect

咖啡店的後端現在有三個人在改：陳美華做歡樂時光折扣，林志豪做會員價，李建國在調菜單。某天早上客人反映稅額少算一塊錢，你發現是昨天合併的一個 commit 造成的，可是它後面已經又有五個別人的 commit。有人說「reset --hard 回去再 force push 就好」，有人說「我昨天不小心 reset 掉三個 commit，還救得回來嗎」，還有人問「上週還好好的，到底是哪個 commit 弄壞的？」

這些都是每天會遇到的事。學完你能安全地改歷史（只改自己的）、撤回已經上線的 commit、救回「不見」的 commit，並為團隊選擇合併方式。下一課的 CI 和之後的部署流程，都建立在這套流程上。

這課的路線：
  1. Git 存了什麼：commit、分支、HEAD 各是什麼，後面每個指令其實都在搬指標；這節開頭先回答開場的三個問題（開場問題的最小答案）。
  2. merge、rebase 與解衝突：功能做完回到 main 有哪幾種結果、哪些分支不能 rebase、衝突時怎麼寫出兩邊都對的內容。
  3. 後悔藥：改錯了該用 restore、reset、revert 還是 reflog，關鍵是「別人拿到了沒」，撤回已上線的 commit 就靠這節。
  4. bisect：「上週還好好的」時，讓 Git 用二分法自動找出弄壞程式的 commit。
  5. 團隊流程：分支、PR（pull request，第 1 課）、保護 main、版本號與 commit 訊息，進新團隊第一週就會碰到的約定。
這課會用到：
  • 第 2 課的結束碼（exit code）：指令成功回 0、失敗回非 0，腳本和 git bisect run 都靠它判斷好壞。
這台 Mac 的 git 是 2.51.2。

Git 其實存的是什麼

先給開場三個問題的最小答案：已經推上去、別人拿到的 commit 用 git revert 做一個抵銷它的新 commit，不要 reset --hard 再 force push；被 reset 掉的 commit 通常還在，用 git reflog 找回來；不知道哪個 commit 弄壞的，用 git bisect 二分搜尋。細節在後面的〈後悔藥：每種情況用哪個指令〉和〈bisect：用二分法找出弄壞程式的 commit〉；要知道為什麼這樣做才安全，先看 Git 存了什麼。

commit 是專案在某個時間點的完整快照（不是「這次改了哪幾行」），加上作者、時間、訊息，以及它的父 commit（parent，前一個 commit）。Git 把這些內容算出一個雜湊值（hash，例如 8b7bfdb2…，40 個十六進位字元，常只寫前 7 個）當作 commit 的名字。內容任何一點不同，雜湊值就不同，所以 commit 一旦建立就不能修改：所謂「改 commit」，其實都是做一個新的 commit。

每個 commit 都指向父 commit，整個歷史就是一張有向無環圖（DAG，directed acyclic graph）：箭頭只從子指向父，不會繞回自己。一般 commit 有一個父，合併產生的 commit 有兩個。

檔案從改動到進入 commit 會經過三個地方：工作目錄（working tree，你正在編輯的檔案）、暫存區（staging area，也叫 index：git add 把改動放進這裡，下一個 commit 的快照就是暫存區的內容），以及 commit 之後的歷史。

分支（branch）只是一個指向某個 commit 的指標（一個檔案，裡面寫著 commit 的雜湊值）。在分支上 commit 時，新 commit 的父是分支原本指的 commit，然後分支往前移到新 commit。HEAD 表示「你現在在哪裡」：通常指向一個分支（git switch main 之後 HEAD → main → 某個 commit）；直接切到某個 commit 時，HEAD 直接指向 commit，叫 detached HEAD。

遠端追蹤分支（remote-tracking branch）如 origin/main，記錄的是你上次和遠端同步時遠端的 main 在哪裡。它不會自己更新，git fetch 之後才會跟上；git pull 等於 fetch 再合併。

用這個指令看整張圖，之後每一節都靠它確認自己在哪裡：

git log --oneline --graph --all
* 8b7bfdb (main) docs: 寫下折扣疊加規則
* ffccbc6 feat: 歡樂時光 8 折
| * f02b615 (HEAD -> feature/loyalty) test: 會員價的測試
| * 7f88413 feat: 會員 9 折
|/
* a092c20 chore: 初始化價格模組

理解「commit 不可變、分支只是指標」之後，後面所有操作都能用一句話說清楚：它是新增 commit，還是移動指標？移動指標會讓某些 commit 不再被任何分支指到，看起來像「不見了」。

merge、fast-forward 與 rebase

feature 做完要回到 main，有三種結果：

  • fast-forward：main 從分出去之後沒有新 commit，git merge feature 只把 main 指標往前移，不產生新 commit。
  • merge commit：兩邊都有新 commit，Git 做一個有兩個父的合併 commit。不改寫任何既有 commit，最安全；代價是圖上多了分岔與合併點，分支很多時不好讀。
  • rebase（重定基底）：git rebase main 把目前分支「在 main 之後才有的 commit」一個一個重新套用到 main 的尖端上。內容一樣、父不同，所以每個都是新的 commit（新的雜湊值），舊的那些不再被分支指到。

rebase 的黃金規則：別人已經拿到的 commit 不要 rebase。你改寫了 feature，同事的電腦上還是舊的 D、E；他再 pull，Git 會把新舊兩套合在一起，同樣的改動出現兩次。只在「只有你在用的分支」上 rebase，例如還沒開 PR、或團隊說好 PR 分支只有作者會推。

改寫過已經 push 的分支後，一般 git push 會被拒絕（遠端有你本機沒有的 commit），要強制推送。不要用 --force，用：

git push --force-with-lease

--force-with-lease 只有在「遠端分支還停在我上次看到的位置（我的 origin/feature）」時才覆蓋；同事在這期間推了新 commit，就拒絕，你不會在不知情下蓋掉他的工作。注意它比對的是你的遠端追蹤分支：如果你在背景跑了 git fetch，origin/feature 已經更新成同事的版本，lease 還是會通過。可以再加 --force-if-includes：遠端追蹤分支的尖端必須能從你本機分支的 reflog（後面會教）裡某一筆走到，也就是你真的把同事的 commit 整合進來過，才允許覆蓋。

💡 實務上：PR 開著，main 又往前了
同事先合併了別的 PR，你的 PR 顯示落後 main 或有衝突。PR 分支只有你在推時，git fetch 後 git rebase origin/main，再 --force-with-lease 推上去；已經有人在你的分支上 commit（例如幫你修測試），就改成把 main merge 進來，不改寫別人拿到的 commit。團隊用 squash merge 時，PR 分支裡多幾個 merge commit 不會進到 main，不用為了「乾淨」冒險 rebase。force push 之後，審查者之前留的行內留言可能對不上新的 commit，在 PR 留一句「已 rebase，改了哪裡」。

解衝突

衝突（conflict）：兩邊改了同一段（或相鄰的）內容，Git 不知道要留哪一個，就停下來交給你。改的地方不重疊時，Git 會自動合併，所以衝突比想像中少。以練習 1 的 repo 為例，把 feature/loyalty rebase 到 main：

git switch feature/loyalty
git rebase main
CONFLICT (content): Merge conflict in package-lock.json
CONFLICT (content): Merge conflict in src/pricing.ts
error: could not apply 7f88413... feat: 會員 9 折

git status --short
UU package-lock.json        ← UU：兩邊都改，有衝突
M  package.json             ← 自動合併成功，已經放進暫存區
UU src/pricing.ts

打開 src/pricing.ts：

export type PriceOptions = {
<<<<<<< HEAD
  happyHour?: boolean   // 歡樂時光 8 折
=======
  member?: boolean      // 會員 9 折
>>>>>>> 7f88413 (feat: 會員 9 折)
}

<<<<<<< 到 ======= 是一邊，======= 到 >>>>>>> 是另一邊。rebase 時兩邊的名字是反的：rebase 是站在 main 上一個個套用你的 commit，所以 HEAD（ours）是 main 那邊（加上已經套好的 commit），theirs 是正在套用的你的 commit。git checkout --ours 檔案 在 merge 時拿的是你的分支、在 rebase 時拿的是 main，用錯會把自己的改動丟掉。

解衝突不是「選一邊」，而是寫出兩個需求都成立的程式。這裡 README 寫著兩種折扣可以疊加，所以兩個選項、兩條規則都要留下，然後拿掉標記：

git diff                      # 看還有哪些衝突（只顯示沒解完的部分）
# 編輯檔案，留下正確的內容、刪掉 <<<<<<< ======= >>>>>>>
git add src/pricing.ts        # 告訴 Git：這個檔案解完了
git rebase --continue         # 繼續套用下一個 commit；有幾個 commit 衝突就重複幾次
git rebase --abort            # 搞砸了：整個回到 rebase 之前

package-lock.json 不要手動合。它是 npm 從 package.json 算出來的結果，裡面有版本、雜湊、相依關係，手動拼起來的版本很容易「看起來是合法 JSON，其實和 package.json 對不上」，npm ci 才發現（Node 課第 3 課）。做法是先把 package.json 合對，再讓 npm 重新產生：

npm install --package-lock-only     # 只更新 lockfile，不動 node_modules
git add package-lock.json

有相依套件時，它會盡量沿用 lockfile 裡已經鎖住的版本；之後跑一次 npm ci 和測試確認。

同一組衝突要解很多次時（例如長命分支反覆 rebase），可以開 rerere（reuse recorded resolution）：git config rerere.enabled true，Git 會記住你怎麼解某個衝突，下次遇到一模一樣的衝突就自動套用。它省的是重複勞動，解完仍要自己看過、跑測試。

衝突標記也是合法的文字。git add 不會檢查你有沒有解完，帶著 <<<<<<< 的檔案照樣 commit 得進去。git add 之前用 git diff --check、之後用 git diff --cached --check（它會列出 leftover conflict marker），或 git grep -n '^<<<<<<< ' 檢查，再跑一次測試。

後悔藥：每種情況用哪個指令

選指令的關鍵只有一個問題：這些 commit 別人拿到了嗎？沒有，就可以改寫（移動指標、做新 commit 取代舊的）；有，就只能往前加 commit。

情況指令做了什麼
改了檔案還沒 add，想丟掉改動git restore 檔案用暫存區的版本蓋掉工作目錄。改動直接消失，沒有 reflog 可救
add 錯了，想移出暫存區git restore --staged 檔案改動還在，只是不 commit
最後一個 commit 訊息打錯或漏了檔案，還沒 pushgit commit --amend做一個新的 commit 取代最後一個
最近幾個 commit 不要了，還沒 pushgit reset --hard HEAD~3分支指標往回移 3 個；那 3 個 commit 沒有分支指著了。--soft 留下改動在暫存區、--mixed（預設）留在工作目錄
已經在 main（別人拉過）上的 commit 有問題git revert <sha>新增一個「反向改動」的 commit，歷史不變
reset、rebase 之後發現弄丟了 commitgit reflog 找到它，git branch 新分支 <sha>重新讓一個分支指著它

reset 是移動分支指標，會讓 commit 從分支上「消失」。在共用的 main 上 reset 再 force push：已經拉過舊 main 的同事，本機還有那些 commit，下次 pull 會跟你的新 main 分岔，一合併就把它們推回來，或者他自己基於舊歷史做的工作要花時間整理。revert 則是新增一個 commit 抵銷舊的，所有人照常 pull 就好，而且歷史裡留著「哪天撤回了哪個 commit」的紀錄：

git log --oneline --grep='^feat: new tax rounding$'     # 用訊息找出那個 commit
3c1e9a0 feat: new tax rounding
git revert 3c1e9a0
git log -1
    Revert "feat: new tax rounding"

    This reverts commit 3c1e9a0d…（完整 SHA）.

revert 只撤回那一個 commit 的改動，後面別人的 commit 都還在。後面的 commit 改到同一段程式時，revert 也會有衝突，解法和上一節一樣。撤回一個 merge commit 要加 -m 1 指定以哪個父為主線，而且之後同一個分支再合併時，被撤回的那些改動不會自動回來，要再 revert 那個 revert；這種情況在 squash merge 的團隊比較少見。

💡 實務上：線上出事時先 revert，再慢慢修
客人反映稅額算錯，值班的人第一件事是讓線上回到已知正常的版本，而不是在壓力下現場寫修正。revert 那個 commit、開成一個 PR、照常跑 CI（下一課）再部署，通常比寫新程式快又安全；修好的版本之後再走一般流程上線。revert 的 PR 說明寫清楚影響範圍與原因，PM 和客服才知道功能暫時拿掉了。要把功能重新上線時，revert 那個 revert，或用新的 commit 重做。

reflog：救回「不見」的 commit

reflog（reference log）是你本機上 HEAD 和每個分支每次移動的紀錄：commit、reset、rebase、switch 都會留一筆。reset 掉的 commit 沒有分支指著，但物件還在 .git 裡，reflog 記得它的雜湊值：

git reflog show feature/menu
1a2b3c4 feature/menu@{0}: commit: chore: 重新整理菜單 1
9f8e7d6 feature/menu@{1}: reset: moving to HEAD~3
5e4d3c2 feature/menu@{2}: commit: feat: 菜單加入起司蛋糕     ← reset 之前的尖端
…
git branch rescue 5e4d3c2       # 讓一個新分支指著它，就「救回來」了

feature/menu@{2} 是「這個分支往前數第 2 次移動之前的位置」，HEAD@{n} 同理。注意數字會隨著之後的操作變動，寫腳本時要依訊息找，不能寫死 @{1}。reflog 只存在你自己的電腦上（clone 不會帶過去），預設保留 90 天，已經沒有分支指著的紀錄是 30 天（gc.reflogExpire、gc.reflogExpireUnreachable），之後垃圾回收才會真的刪掉物件。沒 commit 過的改動不在 reflog 裡，所以想冒險之前先 commit 一下（或 git stash）。

已經推上去的機密

第 11 課講過順序：先輪替，讓外洩的金鑰失效；然後才清歷史。刪檔案再 commit 沒有用，舊 commit 裡還在。要從整個歷史移除，用 git filter-repo（git 沒有內建，brew install git-filter-repo）：

git filter-repo --sensitive-data-removal --invert-paths --path config/prod.env   # 每個 commit 都去掉這個檔案
git filter-repo --sensitive-data-removal --replace-text ../passwords.txt         # 把列出的字串換成 ***REMOVED***

它會改寫從那個 commit 之後的每一個 commit（雜湊值全變），預設只肯在剛 clone 的 repo 上執行。之後要 force push 所有分支，請所有人重新 clone：他們舊的 clone 一 push 就會把機密帶回來，基於舊歷史的分支也要用 rebase 接到新歷史上，不能 merge。GitHub 上的 PR 參照與快取頁面，force push 也清不掉，要聯絡 GitHub Support；fork 裡的則要請 fork 的擁有者處理。代價這麼大，所以輪替才是第一步，清歷史只是減少之後被撿到的機會。

bisect：用二分法找出弄壞程式的 commit

「v1.0 時好好的，現在壞了，中間有 200 個 commit。」一個一個試要很久。bisect 用二分搜尋：你告訴 Git 一個壞的、一個好的 commit，它切到中間那個讓你測；你說好或壞，範圍就少一半。200 個 commit 大約測 8 次（28 = 256）就能找到。

git bisect start main v1.0      # 先壞後好：main 壞、v1.0 好
# Git 切到中間的 commit（detached HEAD），你測試後回答：
git bisect good                 # 或 git bisect bad；這個 commit 沒辦法測就 git bisect skip
…重複到出現「xxxxxxx is the first bad commit」
git bisect reset                # 結束，回到開始前的分支

每一步的「測試」可以交給腳本，git bisect run 會在每個 commit 上執行它，依結束碼判斷（git 2.51 的文件）：

結束碼意思
0好（good）
1～127，但 125 除外壞（bad）
125這個 commit 沒辦法測試，跳過（skip）
其他（例如 128 以上）中止整個 bisect
git bisect start main v1.0
git bisect run sh -c 'npm run build || exit 125; npm test'
git bisect log                  # 每一步的紀錄，可以貼進 issue
git bisect reset

為什麼要 125？歷史裡常有一段 commit 根本建置不起來（重構到一半、少了檔案）。腳本如果讓建置失敗也回傳 1，bisect 會以為「這裡已經壞了」，往前找到「建置第一次失敗的 commit」，跟你要找的 bug 毫無關係。所以腳本要分兩段：建置不起來 → 125（不知道）；建置起來了 → 測試結果決定好壞。測試要只檢查你在追的那個 bug，不要跑整套可能因為別的原因失敗的測試。

bisect 期間 HEAD 是 detached，結束一定要 git bisect reset，不然你會停在某個舊 commit 上，接著做的事都不在任何分支上。另外 bisect 在小而單一目的的 commit 上最有用：如果一個 PR 被壓成一個上千行的 commit，它最多只能告訴你「是這個 PR」。

💡 實務上：客服說「上週還好好的」
先找出確定是好的版本：上一次部署的 tag 最可靠。接著寫一個只重現這個 bug 的最小測試（例如一筆會算錯的訂單），讓它在每個 commit 上都能跑，這比整套測試穩定。bisect 假設每次測試結果都一樣，時好時壞的測試（flaky test）會讓它指錯 commit，找到之後在那個 commit 和它的父 commit 各跑幾次確認。最後把 git bisect log 和找到的 commit 貼進 issue，之後修 bug 的人不用重來。

團隊流程：分支、PR、保護主幹、版本

trunk-based development（主幹開發）：所有人都從 main（主幹，trunk）開短命分支，一兩天內透過 PR 合併回去；main 隨時可以部署，沒做完的功能用功能旗標（feature flag，第 16 課）藏起來。git-flow 則有長期存在的 develop、release、hotfix 分支，適合要同時維護好幾個發佈版本的產品（例如裝在客戶機器上的軟體），但對每天部署的網路服務來說太重：分支活得越久，和 main 的差異越大，最後合併時衝突一大堆（合併地獄）。網路服務多數選 trunk-based。

讓 trunk-based 行得通的習慣：

  • PR 要小：幾百行以內，一個 PR 只做一件事。幾千行的 PR 沒人能好好審，只會被按「核准」。大功能拆成好幾個可以各自合併的步驟。
  • 合併方式：GitHub 提供 merge commit、squash merge、rebase merge。squash merge 把 PR 的所有 commit 壓成一個再放上 main：main 上一個 PR 一個 commit，乾淨、好 revert（撤回整個功能只要 revert 一個 commit），PR 裡「wip」「fix typo」也不會進主幹。代價是 PR 內部細的 commit 不在 main 上，bisect 只能定位到整個 PR；PR 越小，這個代價越小。
  • 保護主幹：用 GitHub 的保護分支（protected branch）或 ruleset（規則集）設定 main：必須透過 PR、必須通過指定的狀態檢查（下一課的 CI）、至少一人審查、禁止 force push 與刪除（保護分支預設就禁止這兩件事）。好幾個 ruleset 套到同一個分支時，每條規則取最嚴格的。
  • CODEOWNERS：放在 .github/、根目錄或 docs/ 的檔案，一行一個路徑模式加上負責人，例如 /migrations/ @cafe/db-team；開了「Require review from Code Owners」之後，改到那些路徑的 PR 必須有負責人核准。

tag（標籤）是指向某個 commit 的固定名稱，不會像分支一樣往前移，常用來標發佈的版本：

git tag -a v1.4.0 -m 'v1.4.0：會員價'     # -a：帶有作者、時間、訊息的 annotated tag
git push origin v1.4.0                     # tag 不會跟著 git push 自動推上去

版本號照 semver（Node 課第 3 課）：不相容的改動升 major、新功能升 minor、修 bug 升 patch。Conventional Commits（1.0.0）把這件事寫進 commit 訊息：類型(範圍): 描述，fix: 對應 patch、feat: 對應 minor，feat!: 或內文最後有 BREAKING CHANGE: 對應 major；docs:、test:、refactor:、chore:、ci: 這類不影響版本。好處是工具可以從 commit 自動決定下一個版本號、產生 changelog（變更紀錄）；人看 git log --oneline 也一眼知道每個 commit 在做什麼。用 squash merge 時，main 上的訊息預設是 PR 標題，所以要規範的是 PR 標題。

feat(orders): 會員價 9 折
fix: 稅額改回四捨五入
feat(api)!: 移除 /v1/orders，改用 /v2/orders

練習

練習在 devops/practice 做，不需要 Docker，只用 git 和 Node。每一題寫一個 shell 腳本，參數 $1 是一個 git repo。測試每次都在這一題的資料夾裡重新產生練習用的 repo（ex1-repo/ … ex4-repo/，作者、內容與 SHA 每次不同），再執行你的腳本、檢查結果。所以先執行一次 node check.mjs devops 14 產生 repo，進去用 git log --oneline --graph --all 看看，試著手動做一遍，再把指令寫進腳本；手動試過的 repo 下次跑測試時會被重新產生，不用自己復原。這些 repo 只用 repo 自己的設定，你的 ~/.gitconfig 不影響結果。

練習 1：完成 ex1.sh：把 feature/loyalty（林志豪的 2 個 commit：會員 9 折、會員價測試）rebase 到最新的 main（陳美華加了歡樂時光 8 折）上。兩邊都改了 src/pricing.ts 和 package-lock.json：pricing.ts 要照 repo 裡 README 的規則同時保留兩種折扣（可以疊加，最後四捨五入）；package-lock.json 不要手動合，用 npm 重新產生。rebase 遇到衝突會以非 0 結束，腳本要接著解衝突、git add、git rebase --continue（前面加 GIT_EDITOR=true 沿用原本的訊息、不開編輯器）。測試會檢查：main 沒被改、是 feature 的祖先、中間沒有 merge commit、2 個 commit 的作者與訊息不變、沒有衝突標記、lockfile 與 package.json 一致，並在分支尖端跑 repo 自己的測試和疊加規則的測試。

練習 2：完成 ex2.sh：main 上訊息是 feat: new tax rounding 的 commit 把稅額改成無條件捨去，之後還有別人的 commit（會議紀錄、李建國加的可頌）。main 已經被大家拉過了，在不改寫歷史的前提下撤回它。SHA 每次都不同，要用訊息找出那個 commit。測試會檢查原本的 main 尖端仍在新 main 上、只多了 1 個 commit、它的訊息含有 This reverts commit <那個 commit 的完整 SHA>.、只抵銷了那個 commit 的改動。

練習 3：完成 bisect.sh：repo 的 main 上約 200 個 commit，tag v1.0 是好的，main 的訂單金額算錯（node --test，Node 課第 6 課，會失敗）。用 git bisect run 自動找出第一個壞 commit，把它的完整 SHA 寫進目前資料夾（work/14）的 answer.txt，最後回到 main。歷史裡有一段 commit 的 src/order.js 連語法都是錯的（node --check src/order.js 會失敗），那些 commit 無法判斷好壞，必須跳過。提示：bisect 找到之後，refs/bisect/bad 指著第一個壞 commit；腳本裡用 git -C "$repo" … 在 repo 裡執行指令。測試會用兩個不同的 repo 各跑一次。

練習 4：完成 ex4.sh：同事在 feature/menu 上執行了 git reset --hard HEAD~3，弄丟了 3 個 commit（拿鐵之後加的卡布奇諾、伯爵紅茶……），之後又 commit 了 1～2 次（每次不同）。用 reflog 找到 reset 之前的位置，建立 rescue 分支指向它，讓原本那 3 個 commit（SHA 完全相同）都在 rescue 上。feature/menu 本身不能動，同事 reset 之後的新 commit 要保留。提示：git log -g --format='%H %gs' feature/menu 一行印出一筆 reflog 的 SHA 和原因，新的在前。

練習 5：main 上昨天合併了一個有問題的 commit，今天已經有好幾個人 pull 過、也在上面開了新分支。同事提議「git reset --hard 回到它之前，再 git push --force，這樣歷史比較乾淨」。會發生什麼事？

✓ c。別人的電腦上還有那個 commit，pull 不會「跟著刪掉」，而是把兩邊合併，問題 commit 就回來了；如果 main 有保護（預設禁止 force push），push 根本會被拒絕。a 錯在 pull 是合併，不是覆蓋；b 問題不在你的 reflog，而在別人的 clone；d reset 只動你本機的指標，任何 commit 都能 reset，擋下 force push 的是遠端的保護規則。

練習 6：你把 feature 分支 rebase 到最新的 main 上，內容一行都沒改，卻發現每個 commit 的雜湊值都變了。為什麼？

✓ b。父 commit 是 commit 內容的一部分，父不同就是不同的 commit；而且新的父帶來不同的快照基底。a rebase 不會壓縮內容；c commit 沒有「搬家」這回事，Git 也沒有編號，只有雜湊值；d 時間確實也算在內，但就算時間一樣，父不同雜湊值還是會變。

練習 7：團隊考慮把 PR 一律改成 squash merge。哪一個說法最正確？

✓ d。squash 是取捨：得到乾淨、好撤回的主幹，失去細的歷史。a 忽略了 bisect 與追查的精細度；b 剛好說反，squash 是壓成一個；c 壓成一個 commit 反而更容易 revert。

練習 8：用 git bisect run ./check.sh 時，check.sh 在某個 commit 以 125 結束，代表什麼？

✓ a。125 是專門保留給「無法判斷」的結束碼，等於 git bisect skip。b 正是這題要擋的誤解：1～127 算壞，但 125 除外，把建置失敗當成壞的會找到錯的 commit；c 中止的是 128 以上這類其他結束碼；d 只有 0 是好的。

常見錯誤

  • 在共用分支上 rebase 或 --force push：別人手上的歷史跟遠端分岔。只 rebase 只有你在用的分支；真的要改寫已經推上去的分支，用 --force-with-lease（可以再加 --force-if-includes），並先告訴會用到它的人。
  • 用 reset 撤回已經推上去的 commit：用 git revert，新增一個抵銷它的 commit，歷史裡也留下撤回的紀錄。
  • rebase 時用錯 --ours／--theirs：rebase 時 ours 是 main 那邊，theirs 才是你的 commit，剛好跟 merge 相反。解衝突時直接編輯檔案、寫出兩邊需求都成立的版本，比較不會選錯。
  • 手動合併 package-lock.json：合出來的 JSON 可能跟 package.json 對不上。先合好 package.json，再 npm install --package-lock-only 重新產生。
  • 把衝突標記一起 commit：git add 不會擋。提交前 git diff --cached --check、跑測試。
  • bisect 腳本把建置失敗當成壞的：會找到「第一次建置不起來的 commit」。建置失敗要 exit 125，只有測試的結果決定好壞；結束後記得 git bisect reset。
  • 以為 reset 掉的 commit 就沒了：先 git reflog，用 git branch 讓一個分支指著它。真正救不回的是從沒 commit 過的改動，冒險之前先 commit 或 stash。
  • 分支活太久：和 main 的差異越積越大，最後合併地獄。一兩天內合併，沒做完的功能用功能旗標藏起來。
  • 一個 PR 改幾千行：沒人能好好審，出事時 bisect 也只能定位到這整包。拆成小的、各自能合併的 PR。
  • 機密進了歷史，只把檔案刪掉：舊 commit 裡還在。先輪替（第 11 課），再用 git filter-repo 清整個歷史、force push、請大家重新 clone。
  • commit 訊息只寫 fix、update：三個月後沒人知道它在修什麼。用 Conventional Commits：fix: 稅額改回四捨五入。

小結

  • commit 是不可變的完整快照，用雜湊值識別，指向父 commit，整個歷史是一張 DAG；分支、HEAD、origin/main 都只是指標，origin/main 要 fetch 才會更新。
  • fast-forward 只移指標；merge 產生有兩個父的合併 commit；rebase 把 commit 重新做成新的 commit 接到新基底上。別人拿到的分支不要 rebase，改寫後用 --force-with-lease 推送。
  • 解衝突要寫出兩邊需求都成立的內容，git add 後 --continue；rebase 時 ours 是 main；lockfile 用 npm 重新產生；提交前檢查衝突標記並跑測試。
  • 沒推出去的歷史可以 restore、amend、reset；已經共用的歷史只能 revert。reflog 記錄每次指標移動，用它救回被 reset 或 rebase 掉的 commit（預設保留 90 天，無法到達的 30 天）。
  • 機密進了歷史：先輪替，再用 git filter-repo 清除、force push、所有人重新 clone。
  • git bisect run 用二分搜尋自動找出第一個壞 commit：0 好、1～127 壞、125 跳過；建置不起來要回 125，結束要 git bisect reset。
  • trunk-based：短命分支、小 PR、保護 main（必須 PR、狀態檢查、審查、禁止 force push）、CODEOWNERS；squash merge 讓主幹乾淨但 bisect 只到 PR；用 annotated tag 加 semver 發佈，Conventional Commits 讓版本與 changelog 可以自動產生。
