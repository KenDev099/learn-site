階段 6：可觀測性與可靠性 · 第 22 課

指標與 SLO：用數字描述服務好不好

週一早上，店長問你：「上週末結帳是不是很慢？」你翻了 log，看到幾千行 200，也看到幾行耗時 3 秒的請求，可是說不出「慢」是多慢、多少客人受影響、跟平常比是好還是壞。上線新版本時也一樣：新版本到底有沒有讓服務變差，大家各說各話。

這一課把「服務好不好」變成大家都認的數字，新版本有沒有讓服務變差，不必再各說各話。

這課的路線：
  1. 指標是什麼、平均值會騙人：指標跟 log、trace 怎麼分工，「慢不慢」為什麼要看 p95 而不是平均（開場問題的最小答案）。
  2. 在 Node 暴露 /metrics 與 Prometheus：在 API 裡記錄請求數和耗時，用 PromQL 算出請求量、錯誤率、p95。
  3. RED 與 USE：儀表板該放哪些圖，出事時先看哪一張。
  4. SLI、SLO 與錯誤預算：替咖啡店訂出「夠好」的標準，用剩下的額度決定這週能不能上新功能，PM 和工程師用同一把尺討論。
  5. 壓測：用 k6 回答「多少流量內做得到這個 SLO」，寫成上線門檻。
這課會用到：
  • 第 21 課的請求 log：每個請求一行 JSON，記下路由、狀態碼與耗時。
  • Node 課第 13 課的 node:http 伺服器：每個請求進到同一個處理函式，用 res.writeHead、res.end 回應。
  • 第 13 課的容量規劃：先量出單一副本撐得住多少流量，再決定要開幾份；Little's law 算出同時在處理的請求數。

指標是什麼：跟 log、trace 的分工

指標是隨時間記錄的數值序列，例如「每秒幾個請求」「現在有幾個請求在處理」。程式不記錄每一件事，只維護幾個計數器，每隔一段時間被讀走一次。所以它很便宜：一天一百萬個請求，跟一天一千個請求，指標的資料量幾乎一樣。

log（第 21 課）指標（這一課）trace（第 23 課）
記錄什麼每一件事的細節彙總後的數字一個請求經過的每一段
成本跟什麼成正比流量序列數（見下面的 label）流量（通常要取樣）
擅長回答這個請求發生了什麼事服務現在好不好、趨勢、告警慢在哪一個服務、哪一段
不擅長長期趨勢、便宜地告警單一請求的細節整體的比例與趨勢

實務上的順序是：指標告訴你「有問題」（錯誤率升高），trace 告訴你「在哪裡」，log 告訴你「為什麼」。

Prometheus 的指標有四種型別：

型別是什麼咖啡店的例子
counter只會增加的累計數；程式重啟會歸零http_requests_total、orders_total
gauge可升可降的當下值http_requests_in_flight（正在處理的請求數）、連線池閒置數
histogram把觀察值分到事先定好的桶子（bucket）裡計數，可以估百分位數http_request_duration_seconds
summary在程式裡直接算好百分位數（不建議，原因見下一節）

counter 的數字本身沒有意義：「累計 1,283,004 個請求」說明不了什麼，重啟後還會變回 0。有意義的是它的變化速度，所以查詢時一定用 rate() 算每秒增加多少（後面會講）。想知道「現在」的值，例如連線池還剩幾條，才用 gauge。

平均值會騙人：百分位數與 histogram

假設上週末某一分鐘有 1000 個結帳請求：980 個在 200ms 內完成（平均 73ms），20 個卡在等資料庫鎖，花了 2.4 秒以上。平均耗時是 120ms，看起來很健康；可是每 50 個客人就有 1 個等了兩秒多，而且常常是購物車最滿的那幾位。

百分位數（percentile）回答「最慢的那群人感受如何」：p95 是「95% 的請求比這個值快」，p99 是 99%。p50（中位數）代表一般客人，p95、p99 代表運氣不好的客人。一個頁面如果要呼叫 API 好幾次，客人碰到 p99 的機會遠大於 1%，所以資深工程師看延遲一律看 p95、p99，不看平均。

要算百分位數，需要知道分布。histogram 不記每個值，只記「落在每個桶子以下的有幾個」：桶子的上限叫 le（less or equal），而且是累加的，le="0.25" 包含所有 ≤ 0.25 秒的請求，最後一個 le="+Inf" 等於總數。估百分位數時，先找出第 95% 個請求落在哪個桶子，再在桶子裡用線性內插。所以估出來的值有誤差，誤差取決於桶子的間距：桶子要密集地放在你在意的範圍（例如 SLO 的 300ms 附近）。

histogram 和 summary 最大的差別在能不能合併。cafe-api 有 3 個副本，每個副本都只看到自己的請求。histogram 的桶子是計數，三個副本同一個 le 的數字加起來，就是整體的分布，再估 p95 就對了。summary 在每個副本裡算好 p95，三個 p95 沒有任何數學方法可以合併成整體的 p95，取平均更是錯的。按「執行」看差多少：

三個 p95 的平均跟真正的 p95 差很多；合併桶子後估出來的值落在同一個桶子裡，誤差只來自桶子的間距。系統設計課第 3 課會更深入談百分位數與尾端延遲。

在 Node 暴露 /metrics

Prometheus 用 pull 模型：服務自己開一個 GET /metrics，Prometheus 每隔一段時間來讀，這個動作叫 scrape（抓取）。回應是純文字的 exposition format，每行一個「名稱{label} 數值」：

# HELP http_requests_total HTTP 請求數
# TYPE http_requests_total counter
http_requests_total{method="GET",route="/orders/:id",status="200"} 1532
http_requests_total{method="GET",route="/orders/:id",status="404"} 17
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.1",method="GET",route="/orders/:id"} 1490
http_request_duration_seconds_bucket{le="0.25",method="GET",route="/orders/:id"} 1541
http_request_duration_seconds_bucket{le="+Inf",method="GET",route="/orders/:id"} 1549
http_request_duration_seconds_sum{method="GET",route="/orders/:id"} 61.7
http_request_duration_seconds_count{method="GET",route="/orders/:id"} 1549
# TYPE http_requests_in_flight gauge
http_requests_in_flight 3

一個 histogram 會產生三種序列：每個桶子的 _bucket、全部耗時加總的 _sum、總數 _count（等於 +Inf 那個桶子）。

命名慣例：小寫加底線；counter 以 _total 結尾；名稱帶上單位，而且用基本單位：秒（_seconds）、位元組（_bytes），不用毫秒、MB。單位寫錯是很常見的事故：名稱寫 _seconds，程式卻記毫秒，200ms 的請求被記成 200 秒，告警規則和儀表板全都錯。

label 讓同一個指標可以依維度切開，例如 method、route、status。要知道的是：每一組不同的 label 值就是一條獨立的時間序列（time series），Prometheus 的記憶體與儲存跟序列數成正比。route 用原始網址 /orders/1155，每張訂單就多一條序列；放 user_id，每個客人一條。這叫基數爆炸（cardinality explosion），會拖垮 Prometheus。規則是：label 的值要是有限的、事先數得出來的集合，例如 HTTP 方法、路由樣板 /orders/:id、狀態碼；比對不到路由的請求（掃描器亂打的網址）一律記成 unmatched。想看單一訂單、單一客人，用 log 或 trace。

💡 實務上：label 是在 code review 時擋下來的
基數爆炸很少是一次寫壞，通常是某天有人「順手」在 label 加了 user_id、tenant 或錯誤訊息全文，幾天後 Prometheus 記憶體用完、整個監控一起掛。資深工程師在 review 新增指標的 PR 時會問：這個 label 最多會有幾種值？乘上其他 label 的組合後有多少條序列？出事時有人會用這個維度切圖嗎？用不到的維度不要加。雲端的託管監控（例如 Grafana Cloud、Datadog）多半依序列數收費，基數直接就是帳單。

Node 用 prom-client（這門課用 15.1.3）。它的 histogram 有 startTimer()，結束時呼叫回傳的函式就會記下經過的秒數：

import { Counter, Histogram, Registry, collectDefaultMetrics } from 'prom-client'

export const register = new Registry()
collectDefaultMetrics({ register })   // CPU、heap、event loop 延遲、GC…

const duration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP 請求耗時（秒）',
  labelNames: ['method', 'route'],
  buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
  registers: [register],
})

const end = duration.startTimer({ method: 'GET', route: '/orders/:id' })
// …處理請求…
end()   // 記下經過的秒數

// GET /metrics 的回應
res.writeHead(200, { 'content-type': register.contentType }).end(await register.metrics())

collectDefaultMetrics 送你一組程序層級的指標，像 process_cpu_seconds_total、nodejs_heap_size_used_bytes、nodejs_eventloop_lag_seconds（Node 課第 23 課的 event loop 延遲），這些在下面的 USE 方法會用到。/metrics 只給內部網路的 Prometheus 讀，不要經過對外的 nginx 公開。

記錄請求有兩個容易漏的地方：處理函式丟出例外時，await handle() 後面的程式不會執行，in_flight 的 dec() 要放在 finally；而狀態碼可能在例外被外層接住後才變成 500，要等回應真的送出（res 的 finish 事件）才讀 res.statusCode。練習 1 會測這兩件事。

Prometheus：抓取與 PromQL

Prometheus 是定期抓取、儲存指標，並用 PromQL 查詢的監控系統。這門課用 3.15.1。設定檔列出要抓哪些目標：

# prometheus.yml
global:
  scrape_interval: 15s      # 每 15 秒抓一次
scrape_configs:
  - job_name: cafe-api
    static_configs:
      - targets: ['api-1:3000', 'api-2:3000', 'api-3:3000']
rule_files:
  - rules.yml

常用的 PromQL，一步只多一樣東西：

想知道PromQL
每條序列每秒幾個請求（5 分鐘平均）rate(http_requests_total[5m])
依路由加總（合併副本與狀態碼）sum by (route) (rate(http_requests_total[5m]))
5xx 佔全部的比例sum by (route) (rate(http_requests_total{status=~"5.."}[5m])) / sum by (route) (rate(http_requests_total[5m]))
p95 耗時histogram_quantile(0.95, sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))
  • [5m] 是範圍選擇器：取過去 5 分鐘的樣本。Prometheus 3 起範圍是左開右閉，剛好落在左邊界的樣本不算。
  • rate() 算這段時間內平均每秒增加多少，而且會處理 counter 重設：看到數字變小，就當作程式重啟、從 0 重新數，不會算出負值。所以 counter 重啟不會讓圖表壞掉。
  • irate() 只看最後兩個樣本，適合看瞬間的尖峰，不適合拿來告警或算 SLO（太跳）。increase(x[5m]) 是 5 分鐘內增加的總數，等於 rate(x[5m]) × 300，要「每秒」就得自己除 300。
  • 比例要先加總再相除。各副本流量不同時，把每個副本的錯誤率取平均，一個很閒卻偶爾出錯的副本會把整體拉得很難看（或反過來掩蓋問題）。
  • histogram_quantile 之前一定要 sum by (le, …)：先把各副本同一個 le 的桶子加起來，le 一定要留著，它就是桶子的上限。
  • Prometheus 3 起 le 的值會正規化成浮點數字串：程式輸出 le="1"，存進去會變成 le="1.0"。查詢或規則裡寫死 le="1" 的會查不到。

儀表板每次打開都要重算一次 histogram_quantile，序列一多就很慢。recording rule 讓 Prometheus 定期把查詢算好，存成新的指標，儀表板與告警直接讀結果。命名慣例是 層級:指標:運算：

# rules.yml
groups:
  - name: cafe-api-red
    rules:
      - record: route:http_requests:rate5m
        expr: sum by (route) (rate(http_requests_total[5m]))

規則寫錯不會報錯，只會算出錯的數字，所以規則也要測。promtool test rules（在 prom/prometheus 映像的 /bin/promtool）讓你餵假的時間序列（'0+60x10' 是「從 0 開始、每個間隔加 60、共 10 次」），在指定的時間點比對結果。練習 2 的測試就是這樣做的。

RED 與 USE：儀表板放什麼

儀表板放太多面板，出事時反而找不到重點。兩個方法幫你決定放什麼：

  • RED，看服務（使用者感受得到的）：Rate 請求量、Errors 錯誤比例、Duration 耗時的 p95／p99。每個路由一組，就是上一節的三個 recording rule。
  • USE，看資源（找原因）：Utilization 使用率（忙碌的時間比例）、Saturation 飽和（有多少工作在排隊）、Errors 資源本身的錯誤。
cafe-api 儀表板面板指標
RED（第一排）每秒請求數、5xx 比例、p95／p99，依路由三個 recording rule
USE：CPU使用率；event loop 延遲（Node 的 CPU 排隊）rate(process_cpu_seconds_total[5m])、nodejs_eventloop_lag_seconds
USE：記憶體heap 使用量、容器記憶體上限nodejs_heap_size_used_bytes
USE：資料庫連線池使用中、閒置、排隊等連線的數量db_pool_total、db_pool_idle、db_pool_waiting
USE：資料庫本身連線數、鎖等待、慢查詢PostgreSQL 課第 36 課的 pg_stat_activity

順序很重要：先看 RED 確認使用者在痛（p95 升高），再看 USE 找哪個資源飽和。只看 CPU 會漏掉最常見的情況：CPU 只用了 20%，請求卻全卡在等資料庫連線，db_pool_waiting 一直往上爬。反過來，CPU 90% 但 RED 都正常，那就不是事故。

SLI、SLO 與錯誤預算

「服務好不好」要先定義清楚：

  • SLI（service level indicator，服務水準指標）：量測服務好壞的數字，通常寫成「好的事件 ÷ 全部的事件」。cafe-api 的兩個 SLI：可用性＝非 5xx 的請求比例；延遲＝300ms 內完成的請求比例。最好在負載平衡器（nginx、ALB）量，因為它看得到 app 掛掉時連不上的請求，app 自己的指標看不到。
  • SLO（service level objective，服務水準目標）：SLI 的目標，加上時間範圍。例如「30 天內 99.9% 的請求不是 5xx」。
  • SLA（service level agreement，服務水準協議）：寫進合約、違反要賠錢的承諾。SLA 一定比內部的 SLO 寬鬆，例如 SLO 99.9%、SLA 99.5%，中間的差距讓你在賠錢之前就發現問題。

錯誤預算（error budget）是 1 − SLO，也就是「允許失敗的額度」。99.9% 的 SLO 在 30 天內：

30 天 × 24 小時 × 60 分鐘 = 43,200 分鐘
43,200 × (1 − 0.999) = 43.2 分鐘
用請求數算：這 30 天有 2,000,000 個請求 → 允許 2,000 個失敗

99.9% 不是「幾乎不能出錯」，而是每個月有 43 分鐘可以「花」：一次 10 分鐘的部署事故、幾次資料庫維護。這也是 SLO 不能訂 100% 的原因：100% 代表永遠不能部署、不能改東西，而且使用者的網路、手機本身就達不到 100%，你付出的成本使用者感受不到。

錯誤預算政策把數字變成決策，事先和產品端講好，出事時就不用吵：

剩餘預算決策
充足（例如剩 25% 以上），燃燒率正常ship：照常上新功能
快用完，或正在快速燃燒ship-with-caution：上線要金絲雀（第 16 課）、避開尖峰、有人盯
用完了（剩 0 或透支）freeze：暫停新功能，工程時間先拿去修穩定性，直到預算回來
💡 實務上：SLO 是工程和產品一起簽的約定
SLO 的數字不是工程師自己定的：先拿過去 30 天的實際表現當起點，再問產品端「客人慢到什麼程度會放棄結帳」。錯誤預算政策要在沒出事的時候寫下來、讓 PM 和主管同意，例如「預算用完就凍結新功能，直到 7 天內的燃燒率回到 1 以下」；等到事故當下才談，只會變成誰嗓門大誰贏。剛開始只挑 1～2 個最重要的路由（結帳、登入）訂 SLO，每季回頭檢查目標是否太鬆或太緊。

燃燒率（burn rate）是消耗預算的速度：觀察視窗內的錯誤率 ÷ (1 − SLO)。燃燒率 1 代表照這個速度，預算剛好在 30 天結束時用完；燃燒率 10 代表 3 天就會用完。注意分母是「允許的錯誤率」，跟觀察視窗多長、整個週期多長無關：過去 1 小時有 3,600 個請求、36 個 5xx，錯誤率 1%，SLO 99.9% 的燃燒率就是 0.01 ÷ 0.001 = 10。第 25 課會用燃燒率設告警：比「錯誤率超過 1%」好，因為它直接回答「這樣下去預算撐得住嗎」。

壓測：SLO 在多少流量內做得到

SLO 說「要多快」，但沒說「在多少流量下」。週末流量是平常的三倍時還做得到嗎？壓力測試（load test）用產生出來的流量量測系統在某個負載下的表現，回答這個問題，也把第 13 課容量規劃要的「單副本能力」從猜測變成實測。

這門課用 k6（Grafana 的開源壓測工具，用 JavaScript 寫情境），版本 2.3.0，用 grafana/k6:2.3.0 映像在 compose（第 10 課）網路的另一個容器裡跑。不要 docker exec 進 api 容器裡壓測：壓測工具和被測程式搶同一份 CPU，量到的是兩者的混合。

開放模型與協調遺漏

很多壓測工具（例如 autocannon 的預設用法、k6 的 constant-vus）是封閉模型（closed model）：固定 50 個連線（虛擬使用者，VU），每個等上一個回應回來才送下一個。問題是：系統卡住 2 秒的期間，50 個 VU 全在等，工具就停止送請求，只量到 50 個慢請求。真實的客人不會因為你變慢就不來，這 2 秒本該有幾百個請求在排隊，它們的等待時間全沒被量到，p99 看起來還不錯。這叫協調遺漏（coordinated omission）：工具跟被測系統「協調」好一起變慢。

開放模型（open model）依固定的到達率送請求：每秒 100 個就是 100 個，不管前面的回來了沒。k6 的 constant-arrival-rate（固定到達率）、ramping-arrival-rate（依 stages 改變到達率）就是開放模型。到達率模式下，k6 需要足夠的 VU 去送請求：大約是「到達率 × 回應秒數」，用 preAllocatedVUs 事先配好。VU 不夠時，送不出去的請求記在 dropped_iterations；它不是 0，就代表你要的到達率沒送到，量到的延遲不可信。

export const options = {
  scenarios: {
    gate: {
      executor: 'constant-arrival-rate',
      rate: 100, timeUnit: '1s',   // 每秒 100 次迭代
      duration: '20s',
      preAllocatedVUs: 100,        // 事先配好，不要在測試中途才建立 VU
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<300'],
    http_req_failed: ['rate<0.001'],
    dropped_iterations: ['count==0'],
  },
}

thresholds（門檻）讓 k6 在不達標時以結束碼 99 結束，CI 看到非 0 就可以擋下這一版。http_req_failed 是失敗請求（預設是狀態碼不在 200–399）的比例。

找出飽和點

做法是逐步加壓：先用低流量暖機 30 秒（JIT 還沒編譯、連線池還沒建好、快取還是空的，這段的慢請求不代表正常狀況，不計分），之後一階一階提高到達率，每一階看 p95、錯誤率、dropped_iterations。每一階寫成一個 scenario，用 startTime 排在前一階之後，摘要裡就能分開看每一階。k6 只替設了門檻的子指標（例如 http_req_duration{scenario:rps_80}）在 handleSummary 的資料裡算出數字，所以每一階都要設門檻；高的幾階沒過門檻、整次以 99 結束，是預期中的事。只想要一條平滑上升的曲線時，用一個 ramping-arrival-rate 搭配 stages 也可以，代價是摘要把所有階段混在一起。

加壓到某一點，吞吐量就不再上升、延遲開始暴增，這叫飽和點（saturation point）。這時同時看 USE 面板，找出最先飽和的資源：

  • db_pool_waiting 一直上升、CPU 卻很閒：瓶頸是連線池（或資料庫太慢，讓每條連線占用太久）。Little's law（第 13 課）告訴你上限：練習 4 的 API 有 5 條連線，9 成請求占用連線 40ms、1 成占用 80ms，平均每個請求占用 0.9 × 0.04 + 0.1 × 0.08 ＝ 0.044 秒，所以每秒最多 5 ÷ 0.044 ≈ 113 個請求。
  • CPU 接近一核、event loop 延遲上升：瓶頸是 CPU，該加副本。
  • 資料庫的 CPU、鎖等待上升：瓶頸是資料庫，加 app 副本只會更糟。

把結果變成上線門檻：「符合 SLO（p95 < 300ms、錯誤率 < 0.1%）的最大到達率」乘上安全係數（例如 0.7，留餘裕給尖峰和量測誤差），寫成 gate.js 的固定到達率與 thresholds，每次上線前在類正式環境跑一次。筆電上的數字只能比較相對變化（這一版比上一版好還是差），正式門檻要在跟正式環境同規格的機器上量；機器很忙時（例如同時開著很多容器），量到的能力會明顯偏低。

💡 實務上：壓測通常在上線前與大活動前做
常見的時機是：新功能上線前、改了資料庫查詢或連線池設定之後、雙 11 或節慶促銷前。不要對正式環境的資料庫壓測（會寫進假訂單、拖慢真客人），用跟正式環境同規格的 staging，並先跟維運、DBA 說好時段。報告要寫清楚條件（到達率、請求組合、資料量、機器規格）和瓶頸是哪個資源，PM 拿到的結論應該是「每秒 X 個請求以內做得到 SLO，再多要先加什麼」，不是一張延遲曲線。
k6 2.x 移除了舊的摘要模式（--no-summary 改成 --summary-mode=disabled），--summary-export 的格式也變了。這一課用 handleSummary() 自己把資料寫成 summary.json，不依賴摘要的格式。

練習

練習 1、2、4 在 devops/practice 做（在 learn/ 執行 node check.mjs devops 22）。練習 1 用本機的 Node 跑，不需要 Docker；練習 2、4 需要 Docker 在跑，第一次會下載 prom/prometheus:v3.15.1 與 grafana/k6:2.3.0。練習 4 的測試每次會重新啟動 ld-22、跑兩次 20 秒的壓測，大約要兩分鐘。

練習 1：shop/server.ts 是一個小型的咖啡店 API（不用改），每個請求都交給 shop/metrics.ts 的 instrument(req, res, route, handle)：route 是比對到的路由樣板（例如 /orders/:id），比對不到時是 null；handle() 會寫出回應，也可能丟出例外（由 server.ts 接住後回 500）。用 prom-client 在 register 上建立：http_requests_total{method,route,status}（counter）、http_request_duration_seconds{method,route}（histogram，單位秒，buckets 是 [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5]）、http_requests_in_flight（gauge），再加上預設指標。比對不到的路由一律記成 unmatched。測試用隨機的次數請求 /orders/<編號>、/orders/abc（404）、/nope/…、/products、會丟例外的 /boom 和 /slow?ms=200，再解析 /metrics：計數要精確、route 只能是樣板、200ms 的請求要落在 le="0.25"、+Inf 等於 _count、處理中的 in_flight 是 1、全部結束後回到 0。

練習 2：在 rules.yml 寫三個 recording rule，結果都只留 route 一個 label：route:http_requests:rate5m（每秒請求數，合併副本與狀態碼）、route:http_errors:ratio_rate5m（5xx 佔全部請求的比例）、route:http_request_duration_seconds:p95_5m（p95 耗時，秒）。都用 5 分鐘的範圍。測試用 promtool test rules 餵兩個副本、兩個路由的假資料：一個副本流量是另一個的十倍、其中一個在第 11 分鐘重啟（counter 歸零）、另一個在第 10 分鐘流量變三倍，在第 12、13、15、25 分鐘比對你的規則跟正確算式的結果。自己檢查語法的指令寫在 rules.yml 開頭。

練習 3：寫一個錯誤預算計算機。SLO 一律用小數表示（99.9% 寫成 0.999）。budgetMinutes(slo, days)：這段期間允許壞掉幾分鐘。errorBudget({ slo, total, bad })：total 是到目前為止的請求數、bad 是失敗數，回傳 allowed（允許的失敗數 ＝ (1 − slo) × total）、remaining（allowed − bad，透支時是負數，不要截成 0）、remainingRatio（remaining ÷ allowed；沒有任何流量時預算完全沒用，回傳 1）。burnRate({ slo, total, bad })：total、bad 是觀察視窗裡的數字，回傳燃燒率（視窗內錯誤率 ÷ (1 − slo)；沒有流量時是 0）。decide(policy, state)：剩餘比例 ≤ 0 回傳 'freeze'；剩餘比例低於 policy.cautionBelow，或燃燒率高於 policy.maxBurnRate，回傳 'ship-with-caution'；其他回傳 'ship'。小數的誤差容許 1e-9。

練習 4：找出 cafe-api 的容量，寫成上線門檻。api/server.ts 模擬一個連線池 5 條的 API（GET /products 占用連線 40ms、POST /orders 占用 80ms），/metrics 有 db_pool_total、db_pool_idle、db_pool_waiting、process_cpu_seconds_total。步驟：

（1）在這一題的資料夾執行 docker compose up -d --wait。（2）在 loadtest.js 的 options 寫 scenarios：名為 warmup 的暖機（從 0 秒開始、至少 30 秒、到達率模式），之後至少 3 階遞增的到達率（例如每秒 40、60、80、100、120），每一階一個 constant-arrival-rate 或 ramping-arrival-rate 的 scenario，用 startTime 排在暖機之後；每一階設 http_req_duration{scenario:名稱}（p95 < 300）、http_req_failed{scenario:名稱}（rate < 0.001）、dropped_iterations{scenario:名稱}（count == 0）的門檻。（3）用 docker run --rm --network ld-22_default -v "$PWD":/scripts -w /scripts grafana/k6:2.3.0 run loadtest.js 執行，同時在另一個終端機每隔幾秒 curl -s localhost:18220/metrics，看飽和時哪個指標在漲。（4）從 summary.json 找出三個門檻都過的最高那一階，寫進 capacity.json：maxRpsWithinSlo（那一階的每秒請求數）、p95Ms、p99Ms、errorRate（那一階的數字）、bottleneck（pool、cpu 或 db）、evidence（{ "metric": 指標名稱, "value": 飽和時讀到的數值 }）。（5）在 gate.js 用 constant-arrival-rate 以 0.7 × maxRpsWithinSlo 跑 20 秒，門檻是 http_req_duration p(95)<300、http_req_failed rate<0.001、dropped_iterations count==0。

測試用 k6 inspect 檢查兩個腳本的設定、比對 capacity.json 與 summary.json，再把 api 的連線池改成 20 條跑你的 gate.js（必須 exit 0），改成 1 條再跑一次（必須因門檻沒過 exit 99），同時讀 /metrics 確認瓶頸。你量到的數字會依電腦忙不忙而不同，沒關係，capacity.json 只要跟你自己的 summary.json 一致。

練習 5：cafe-api 跑 3 個副本，同事的儀表板把三個副本各自的 p95 取平均，當作整體的 p95：「平均一下差不多。」這樣做的問題是？

✓ c。各副本的流量和分布都不同：一個很閒、全是快請求的副本，會把平均拉低，蓋掉另一個副本的慢請求。桶子是計數，加起來就是整體的分布：histogram_quantile(0.95, sum by (le) (rate(…_bucket[5m])))。a 即使副本數一樣，流量也不一樣；b 最大值通常高估，也不是 p95 的定義；d summary 算好的百分位數正是沒辦法合併的那一種。

練習 6：SLO 是「30 天內 99.9% 的請求不是 5xx」。產品經理說：「99.9%，也就是幾乎不能出錯，這個月誰都不准部署。」錯誤預算其實是多少？

✓ b。30 × 24 × 60 × 0.001 ＝ 43.2 分鐘；用請求數算是 0.1%。錯誤預算的用意就是讓團隊放心地「花」在部署和改變上，用完了才依政策凍結。a 把 SLO 當成 100%；c 4.32 小時是 259.2 分鐘，大約是 99.4% 的預算，比 43.2 分鐘多了 6 倍；d 預算是整個 30 天的視窗，不是每天重置。

練習 7：你用固定 50 個連線的壓測工具測 cafe-api。中間系統卡住 2 秒，工具只量到 50 個 2 秒的慢請求，其他都很快，p99 看起來還不錯。問題在哪？

✓ d。封閉模型的每個連線要等回應才送下一個，系統越慢送得越少，延遲被系統性地低估。真實的客人不會因為你慢就晚點來，開放模型照固定到達率送，卡住期間的請求會排隊，等待時間全部算進去。a 正是被低估的結果；b 連線再多仍是封閉模型，只是比較晚才露餡；c 平均值更會掩蓋卡頓。

常見錯誤

  • 用平均延遲判斷服務健康：平均值會被大量的快請求拉低。看 p95、p99，而且用 histogram 記錄。
  • label 放 ID 或原始網址：每個值一條序列，基數爆炸拖垮 Prometheus。label 用路由樣板、方法、狀態碼，比對不到的記成 unmatched；要看單一訂單用 log 或 trace。
  • 單位混用：名稱寫 _seconds 卻記毫秒，buckets 也跟著錯。一律用秒、位元組這些基本單位。
  • 拋例外時 in_flight 沒減回來：dec() 放在 await 後面，例外一來就跳過，gauge 永遠往上漲。放在 finally。
  • 用 summary 記耗時：每個副本算好的百分位數沒辦法合併。用 histogram。
  • 在 PromQL 裡平均百分位數或比例：先 sum by (le, route) 合併桶子再 histogram_quantile；比例先把分子、分母各自加總再相除。
  • 用 irate 算 SLO，或 increase 忘了除秒數：irate 只看最後兩個點；increase 是總數不是每秒。告警與 SLO 用 rate。
  • 規則寫死 le="1"：Prometheus 3 會存成 le="1.0"，查不到。
  • 把 SLO 訂成 100%：沒有預算就不能部署，使用者也感受不到最後那 0.1%。從現在的實際表現和使用者能接受的程度訂起。
  • 只看 CPU：CPU 很閒，客人卻在等連線池。先看 RED 確認使用者在痛，再用 USE 找原因。
  • 用封閉模型量延遲：系統越慢送得越少，p99 被低估（協調遺漏）。用 arrival-rate，並把 dropped_iterations 當成門檻。
  • 壓測工具和被測服務跑在同一個容器或同一台機器：兩者搶 CPU，量到的是混合結果。k6 跑在另一個容器，正式門檻用另一台機器。
  • 沒有暖機就計分：JIT、連線池、快取還沒熱，前幾秒的慢請求混進結果。先暖機，計分的階段排在後面。
  • 上線門檻只設 p95：錯誤回得很快的版本反而會過關；VU 不夠時延遲也不可信。p95、錯誤率、dropped_iterations 三個都要。
  • 把 maxVUs 或平均延遲當成能力：能力是「符合 SLO 的最大到達率」，要從實測的那一階讀出來。

小結

  • 指標是便宜的彙總數字，擅長回答「服務現在好不好」；log 回答發生了什麼，trace 回答慢在哪裡。
  • counter 只增不減（用 rate() 看）、gauge 是當下值、histogram 用累加的桶子估百分位數而且能跨副本合併；summary 不能合併。
  • 看延遲看 p95、p99，不看平均。/metrics 用 prom-client 暴露，名稱帶基本單位，label 只用值有限的維度（路由樣板，不放 ID）。
  • Prometheus 定期 scrape；RED 的 PromQL：sum by (route) (rate(…[5m]))、先加總再相除的錯誤比例、histogram_quantile(0.95, sum by (le, route) (…))；常用的寫成 recording rule，並用 promtool 測試。
  • RED 看服務、USE 看資源；先確認使用者在痛，再找飽和的資源。
  • SLI 是好事件的比例、SLO 是目標、SLA 是合約；錯誤預算 ＝ 1 − SLO（99.9%／30 天 ＝ 43.2 分鐘），燃燒率 ＝ 錯誤率 ÷ (1 − SLO)，政策決定 ship、ship-with-caution 或 freeze。
  • 壓測用開放模型（k6 arrival-rate）避免協調遺漏，先暖機再逐步加壓，同時看 USE 找出瓶頸；符合 SLO 的最大到達率 × 安全係數寫成 thresholds，當作上線門檻。
