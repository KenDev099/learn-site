階段 2：容器化 · 第 11 課

設定與 secret：同一個映像跑在每個環境

咖啡店的 API 要先上 staging 給店長試用新的集點功能，確定沒問題再上 production。同事的做法是建兩個映像：cafe-api:staging 在 Dockerfile 裡寫 ENV APP_ENV=staging，cafe-api:production 再改成 production 重建一次。某天 production 出了 staging 沒出過的錯，查了半天才發現兩次建置之間 npm 裝到了不同版本的套件。staging 測過的，根本不是上線的那一個。同一週，有人把 compose.yaml 連同寫在裡面的資料庫密碼推上了 GitHub。

這一課把「程式」和「設定」分開，再處理機密從交付、外洩到更換的整個過程。

這課的路線：
  1. 同一個映像，不同的設定：為什麼 staging 和 production 要跑同一個映像，設定等到部署時才給。
  2. 設定從哪裡來：Compose 的 .env、env_file、environment 名字很像，各自管什麼。
  3. 機密不放環境變數、改用 secrets 掛成檔案：密碼放在環境變數會從哪些地方漏出去，怎麼改成用檔案交給容器。
  4. 機密外洩了怎麼辦：密碼推上 GitHub 之後先做什麼，怎麼從 git 歷史裡把它找出來。
  5. 輪替不中斷與雲端的 secret manager：換資料庫密碼時服務怎麼不中斷，伺服器多了之後機密集中放在哪裡。
這課會用到：
  • 第 10 課的 compose.yaml：每個服務的 environment 給容器環境變數，healthcheck 加 up --wait 等到服務真的準備好，docker compose config 印出最後生效的設定。
  • Node 課第 2 課的設定：程式用 process.env 讀環境變數，啟動時就驗證，缺了必要的值立刻結束。
  • NestJS 課第 11 課的 .env：本機開發的設定放 .env（不進 git），.env.example 進 git 當範本；那一課把「正式環境怎麼注入」留到這裡。

同一個映像，不同的設定

設定（configuration）是不同部署之間會變的值：資料庫在哪、log 要多詳細、某個功能開不開。機密（secret）是設定的一種，外流就會造成損害：密碼、API token、私鑰。程式碼則是每個環境都一樣的部分。

原則是建置一次、部署時才給設定。The Twelve-Factor App 的第三條（設定放在環境裡）和第五條（嚴格分開建置、發布、執行）說的就是這件事。建出來的映像不再修改，從 staging 一路用到 production，這叫不可變映像（immutable image）。好處是：你在 staging 測過的，就是上線的那一個，位元組完全相同；出事時回滾就是換回上一個映像的 tag 或 digest（第 16 課）。

哪些東西在建置時決定、哪些在部署時才給：

建置時（進映像）部署時（不進映像）
程式碼、編譯結果、正式依賴資料庫位址、使用者、密碼
NODE_ENV=production（每個環境都一樣，影響 npm 和框架的行為）APP_ENV（staging 還是 production）
版本資訊 APP_VERSION、GIT_SHA（第 8 課，描述映像本身）LOG_LEVEL、功能開關、外部服務的網址
port 的預設值API token、私鑰、任何機密

判斷方法：如果這個值換了，你會想重新建置映像嗎？不會的話，它就不屬於映像。

設定從哪裡來：Compose 的四個來源

第 10 課的 compose.yaml 把每個值都寫死在 environment 底下。Compose 其實有好幾個地方可以放設定，名字很像，作用不同：

來源做什麼進容器嗎
.env（專案資料夾裡）或 --env-file替換 compose.yaml 裡的 ${VAR}不會直接進去，只是填空
environment:設定容器的環境變數會
env_file:把一個檔案裡的 KEY=VALUE 全部設成容器的環境變數會
Dockerfile 的 ENV映像內建的預設值會（被上面兩個蓋過）

.env 這個名字最容易誤會。Compose 讀 .env 只是為了變數替換（interpolation）：把 compose.yaml 裡的 ${LOG_LEVEL} 換成值。.env 裡有、但 compose.yaml 沒有用到的變數，容器完全看不到。要把整份檔案設進容器，用的是 env_file。

同一個變數在好幾個地方都有值時，依 Docker 文件（Compose v5.3 適用），從高到低：docker compose run -e > environment > env_file > 映像的 ENV。做替換用的變數則是：shell 的環境變數 > --env-file 指定的檔案 > 專案資料夾的 .env（有給 --env-file 時就不讀 .env）。

把它們組起來，就是這一課練習 1 的做法：

config/staging.env          （進 git：非機密、每個環境固定的值）
APP_ENV=staging
FEATURE_LOYALTY=true

compose.yaml
services:
  api:
    image: learn-devops/cafe-api:11
    env_file: config/${APP_ENV:?要指定 APP_ENV}.env    ← 用 APP_ENV 選哪一份
    environment:
      LOG_LEVEL: ${LOG_LEVEL:-info}                    ← 部署時可以臨時調整

部署時（伺服器上的 .env，不進 git）
APP_ENV=production
LOG_LEVEL=warn

替換語法（Compose 文件列出的形式）：${VAR:-預設} 在沒設定或空字串時用預設值；${VAR:?訊息} 在沒設定或空字串時直接報錯停下來。APP_ENV 用 :? 而不是 :-staging：忘了設定就該失敗，不該默默把 production 部署成 staging 的設定。這和 Node 課第 2 課「啟動時驗證、缺了就 exit 1」是同一個想法，只是提早到部署這一步。

怎麼確認最後的結果？docker compose config 印出替換、合併之後的完整設定，不啟動任何東西；docker compose config --environment 列出替換用到的變數：

docker compose --env-file deploy/production.env config
services:
  api:
    environment:
      APP_ENV: production
      FEATURE_LOYALTY: "false"
      LOG_LEVEL: warn
…
env 檔裡的值，Compose 也會做替換：config/staging.env 寫 LEVEL=${LOG_LEVEL}，用 env_file 載入時會被換掉（單引號包起來的值不會）。但 docker run --env-file 不做替換，${LOG_LEVEL} 會原封不動變成值。同一份檔案換個工具讀，結果就不一樣，所以 env 檔裡最好只放字面值。

最後，app 自己仍然要在啟動時驗證設定。練習的 app/src/config.ts 少了 APP_ENV、或 LOG_LEVEL 不是合法的等級，就印出缺什麼並以 exit 1 結束。Compose 擋的是部署者忘了給，app 擋的是給錯了值。

💡 實務上：部署前先看 docker compose config 的結果
上線出問題時，常見的原因不是程式，而是某台伺服器的 .env 少了一個變數、或拼錯了值。審設定變更的 PR 時，資深工程師會用正式環境的變數檔跑一次 docker compose config，看合併後的結果，而不是只看 diff。CI 也可以跑 docker compose config -q（只檢查、不印），少了 ${VAR:?} 要的變數就失敗。這份輸出會包含所有替換進去的值，不要整份貼到 issue 或聊天室。

機密為什麼不該放在環境變數

環境變數用來放一般設定很方便，用來放密碼就有問題。用第 10 課那種寫法（DB_PASSWORD: cafe-dev-password 直接寫在 environment）啟動之後，看看密碼會出現在哪裡：

docker inspect ld-11-api-1 --format '{{json .Config.Env}}'
["DB_PASSWORD=cafe-dev-password", …]        ← 能執行 docker 指令的人都看得到

docker exec ld-11-api-1 sh -c 'tr "\0" "\n" < /proc/1/environ'
DB_PASSWORD=cafe-dev-password                ← 程序的環境，同一個使用者的程序都讀得到

docker compose config | grep PASSWORD
      DB_PASSWORD: cafe-dev-password         ← 貼到 issue 或 CI log 就外洩了

還有程式碼看不到的地方：

  • 子程序會繼承：app 執行任何外部指令（child_process.spawn、套件偷偷執行的腳本），整份環境都跟著傳過去。
  • 錯誤回報和除錯工具：有些錯誤追蹤服務、crash dump 會附上整份環境變數；有人為了除錯寫 log.info(process.env)，密碼就進了集中 log（第 21 課）。
  • 無法用權限控管：環境變數沒有「只有這個程序能讀」的設定。

檔案就不同了：它可以設權限、只掛進需要的容器、不會出現在 docker inspect 的 Env 裡，程式讀進記憶體之後也不會自動傳給子程序。這不代表放環境變數就一定會外洩，而是外洩的路徑多很多。

用 secrets 把機密掛成檔案

Compose 的 secrets 把一個檔案掛進容器的 /run/secrets/<名稱>（依 Docker 文件，只支援 Linux 容器，用 bind mount 的方式掛進去）。寫法分兩步：頂層的 secrets 宣告有哪些機密、檔案在哪；服務底下的 secrets 列出這個服務能拿到哪些，沒列的服務就沒有。

services:
  api:
    environment:
      DB_PASSWORD_FILE: /run/secrets/db_password    ← 告訴 app 去哪裡讀
    secrets:
      - db_password
  db:
    image: postgres:18.6-alpine3.24
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt

_FILE 慣例：很多官方映像接受「變數名稱加上 _FILE」，值是檔案路徑，映像啟動時從檔案讀出真正的值。postgres 映像支援 POSTGRES_PASSWORD、POSTGRES_USER、POSTGRES_DB、POSTGRES_INITDB_ARGS 四個（docker-library 的 postgres 文件）。POSTGRES_PASSWORD 和 POSTGRES_PASSWORD_FILE 同時設定時，映像會報錯停下。實測 postgres:18.6-alpine3.24：用 _FILE 啟動後，docker inspect 和主程序的 /proc/1/environ 裡都找不到密碼。

自己的 app 要自己實作這個慣例。練習 2 要你在 config.ts 補上這幾行：

function secret(name: string): string | undefined {
  const file = process.env[`${name}_FILE`]
  if (file) return readFileSync(file, 'utf8').replace(/\r?\n$/, '')
  return process.env[name]
}

注意結尾的換行。openssl rand -hex 24 > file 會在最後寫一個換行；postgres 映像讀 _FILE 時用 shell 的 $(< file)，會去掉結尾的換行，你的 app 不去掉的話，送出去的密碼多了一個 \n，就登不進資料庫。

密碼檔本身的規則：

  • 隨機產生、每個環境不同：openssl rand -hex 24。staging 外洩不該連累 production。
  • 權限 600（只有擁有者能讀寫，第 2 課）。產生之前先執行 umask 077。umask 是「新建檔案時要拿掉哪些權限」的遮罩，077 代表群組和其他人的權限全部拿掉，所以新檔案就是 600；檔案已經存在時 umask 不會改它，所以再補一行 chmod 600。
  • secrets/ 寫進 .gitignore，跟 .env 一樣。
postgres 只在資料目錄是空的時候（第一次初始化）用這個密碼建立使用者。之後換了密碼檔再 up，資料庫裡的密碼不會變，app 反而用新密碼連不上。換密碼要在資料庫裡 ALTER ROLE，下面「輪替不中斷」會講；練習時想重來，docker compose down -v 會連資料一起刪掉。

在 Mac 的 Docker Desktop 上，掛進去的檔案在容器裡看起來屬於讀它的那個使用者，600 也讀得到。正式的 Linux 伺服器上，bind mount 保留主機上的擁有者和權限：容器以 node（uid 1000）執行，檔案卻屬於 uid 1001 的部署帳號又是 600，app 就讀不到。部署時要讓檔案的擁有者或群組對上容器裡的使用者，例如 chown 1000 secrets/db_password.txt。

這樣做的界線在哪：能登入這台伺服器、能執行 docker exec 的人仍然讀得到檔案。secrets 檔案擋的是「不小心」的外洩（inspect、log、子程序、貼錯地方），擋不住已經拿到主機權限的人。

💡 實務上：接手專案時先盤點機密
接手咖啡店的後端時，先列一張表：有哪些機密（資料庫密碼、金流 API key、寄信服務的 token）、各放在哪裡、誰讀得到、上次什麼時候換過。資安稽核或客戶的資安問卷常會問這幾題，答不出來就是風險。同事離職時，他碰過的機密都要輪替，這張表就是待辦清單。

機密外洩了怎麼辦

先建立一個觀念：git 歷史保存每個 commit 當時的完整快照。把含有金鑰的檔案刪掉再 commit，只是多了一個「刪除」的 commit，之前那個 commit 裡的檔案還在，任何 clone 過的人、任何 fork 都拿得到（細節在第 14 課）。所以只要 push 出去，就當作已經外洩。

找出來的工具叫機密掃描（secret scanning），用規則（例如 AWS access key 的格式 AKIA 開頭加 16 個字元）比對程式碼。這一課用 gitleaks v8.30.1：

模式掃什麼用在哪
gitleaks git每一個 commit 的變更（預設整個歷史）稽核既有 repo、CI
gitleaks git --staged 或 --pre-commit這次要 commit 的變更pre-commit hook
gitleaks dir目前資料夾裡的檔案，不看歷史不是 git 的資料夾、建置產物

舊版的 detect、protect 從 v8.19.0 起淘汰，網路上的舊文章還在用。找到機密時 gitleaks 以 1 結束，CI 就會失敗；--redact 讓輸出和報告裡不出現機密本身（報告常被存成 CI 的附件、貼進 issue）。另外，gitleaks 已經不再加新功能、只修安全問題，作者轉往新的專案 Betterleaks，選工具時列入考量。

docker run --rm -v "$PWD:/repo:ro" zricethezav/gitleaks:v8.30.1 \
  git /repo --report-format json --report-path - --redact --no-banner

報告的每一筆有 RuleID（哪條規則，例如 aws-access-token）、File、Commit。也可以只用 git 找：git log -S<字串> 列出「這個字串出現次數有變化」的 commit，加入和刪除的都會列出，新的在前面；git show <sha> 看那個 commit 改了什麼。

發現外洩之後的順序（和 Auth 課第 23 課一致）：

  1. 輪替（rotation）：產生新的金鑰 → 部署 → 確認線上在用新的 → 撤銷舊的。舊的一撤銷，攻擊者手上的就沒用了。如果已經確認被濫用、損害正在擴大，可以直接先撤銷，接受服務中斷。
  2. 評估：查舊金鑰外洩期間的使用紀錄（AWS 的 CloudTrail 記錄帳號裡每一次 API 呼叫；資料庫有連線 log），確認有沒有被用過、做了什麼。
  3. 清理歷史：git filter-repo 移除、force push（用改寫過的歷史強制蓋掉遠端）、請所有人重新 clone（第 14 課）。這一步只是減少之後被撿到的機會，不能取代輪替。
  4. 預防：pre-commit hook（每次 commit 前自動執行的檢查）跑 gitleaks；開啟 GitHub 的 push protection，在 push 時擋下疑似機密。
最常見的錯誤順序：先刪 commit、force push，覺得「沒人看到」就結束。從 push 到你發現之間，任何人都可能已經 clone、fork，或被自動掃描公開 repo 的程式抓走。沒輪替，金鑰就還是有效的。
💡 實務上：外洩是事故，不是個人的小失誤
GitHub 的 secret scanning 或雲端廠商常會寄信通知「你的金鑰出現在公開 repo」。收到時馬上告訴主管和負責資安的人，一邊輪替、一邊記下時間線：何時 push、何時發現、何時撤銷。討論時不要把金鑰本身貼進聊天室，只說是哪一把。事後檢討要問的是「流程哪裡沒擋住」（缺 pre-commit、缺 push protection），而不是追究是誰。

輪替不中斷

直接改資料庫密碼會怎樣：密碼一改，還在用舊密碼的 api 容器下一次建立連線就失敗；新容器還沒部署完之前，這段時間就是事故。解法是雙憑證輪替（dual credentials）：讓新舊兩組同時有效一段時間。

  1. 建立第二組：新增一個使用者 cafe_v2（權限和 cafe 相同），或用支援雙密碼的系統。此時新舊都能登入。
  2. 把新的帳號密碼放進 secret，逐批重新部署所有 api（滾動更新：一次換一部分，其他的繼續服務，第 16 課）。
  3. 確認所有連線都用新的：在 PostgreSQL 查 pg_stat_activity 的 usename，舊的使用者沒有連線了。
  4. 移除舊的：DROP ROLE cafe（或停用登入），下次輪替再反過來。

同樣的想法（Auth 課第 23 課的金鑰輪替）也用在 JWT 簽章金鑰（同時接受新舊兩把、只用新的簽）和 API token。更進一步是根本不要長期密碼：在 AWS 上用 IAM（AWS 的權限系統）角色拿到幾小時就過期的短期憑證，CI 用 OIDC 換取臨時權限（第 19 課），沒有東西可以外洩到 git 裡。

雲端的 secret manager

伺服器上的 secrets/db_password.txt 誰放上去的？伺服器多了之後，手動放檔案不可行，也查不到誰在什麼時候讀過。secret manager 是集中存放、授權、稽核機密的服務。AWS 有兩個：

SSM Parameter StoreSecrets Manager
存什麼一般設定和機密（SecureString 用 KMS，也就是 AWS 的金鑰管理服務加密）專門存機密
輪替自己做內建排程輪替（RDS 等服務有現成的輪替流程）
適合功能開關、網址、少量機密資料庫密碼、要定期輪替的憑證

兩者都用 IAM 控制誰能讀哪一個（第 19 課），每次讀取都會留下 CloudTrail 紀錄。交給 app 的方式有兩種：

  • 部署時注入：部署流程（或 ECS 這類 AWS 容器服務、Kubernetes 的整合，第 18 課）讀出值，寫成容器裡的檔案或環境變數。app 不知道 secret manager 存在，本機開發照樣用檔案。缺點是輪替後要重新部署或重啟才會拿到新值。
  • 執行時讀取：app 啟動時（或定期）用 AWS SDK 讀。輪替不用重新部署，但 app 綁定了雲端服務，本機開發要另外處理，服務本身掛了 app 也啟動不了。

從小團隊開始的話，部署時注入成檔案、用這一課的 _FILE 讀取，是最少相依的做法；之後換成 Kubernetes Secret 或 ECS 的整合，app 都不用改。

練習

四題都在 devops/practice/work/11/ 裡做，需要 Docker Desktop 在執行。app/ 是精簡版的 cafe-api（有 /health/ready 和只回非機密設定的 /config），compose.yaml 是第 10 課那種把一切寫死的版本。api 發布在 127.0.0.1:18110。測試用專案名 ld-11，開始和結束時都會 down -v。練習 3 第一次會下載 gitleaks 映像。

練習 1：讓同一個映像跑在 staging 和 production。拿掉 app/Dockerfile 裡燒進去的 ENV；建立 config/staging.env（APP_ENV=staging、FEATURE_LOYALTY=true）和 config/production.env（APP_ENV=production、FEATURE_LOYALTY=false）；在 compose.yaml 用部署時的 APP_ENV 選要載入哪一份（沒給就報錯），LOG_LEVEL 用替換、沒給時是 info；建立 .env.example 列出 APP_ENV、LOG_LEVEL 但不填值；.gitignore 忽略 .env。測試用 --env-file 給兩份不同的部署變數（LOG_LEVEL 每次隨機），檢查 docker compose config 的結果、映像的 Env，再實際啟動並比對 GET /config。自己試：cp .env.example .env 填好值，docker compose -p ld-11 config。

練習 2：把資料庫密碼改成 Compose secrets。完成 new-secret.sh：每次產生新的隨機密碼（至少 16 個字元）寫到 secrets/db_password.txt，權限 600；compose.yaml 宣告 db_password 這個 secret 並交給 api 和 db，postgres 用 POSTGRES_PASSWORD_FILE、api 用 DB_PASSWORD_FILE；在 app/src/config.ts 的 secret() 實作 _FILE 慣例；.gitignore 忽略 secrets/。測試先直接呼叫你的 loadConfig()，用結尾有換行、沒有換行的檔案確認 secret() 讀對了；再執行兩次 new-secret.sh，用產生的密碼啟動整套服務，確認 /health/ready 回 200、用這個密碼登得進資料庫，而且兩個容器的 docker inspect、/proc/1/environ、docker compose config 都找不到它。

練習 3：完成 scan.sh：用 zricethezav/gitleaks:v8.30.1 掃描參數 $1 指定的 git repo 的整個歷史，把 JSON 報告印到 stdout，報告裡不能出現機密本身；找到機密時以非 0 結束。測試每次在 leaky-repo/ 產生新的 repo：某個 commit 加入一組假的 AWS 金鑰，之後的 commit 又把它刪掉，檔名和位置每次不同；也會掃一個乾淨的 repo，要以 0 結束、報告是 []。跑過一次測試之後，自己用 git -C leaky-repo log --stat 看看歷史。

練習 4：完成 find-commit.sh：印出 repo $1 裡第一次加入字串 $2 的 commit 完整 SHA（只印一行）。測試用練習 3 那種 repo 和裡面的金鑰檢查。再把 incident.json 的 options 全部排進 steps，寫出這次外洩的處理順序（服務不能中斷）。

練習 5：專案資料夾有一個 .env，內容是 FEATURE_LOYALTY=true；compose.yaml 的 api 服務沒有 env_file，environment 裡也沒有提到 FEATURE_LOYALTY。容器裡的 process.env.FEATURE_LOYALTY 是什麼？

✓ c。.env 是 Compose 自己讀的變數檔，沒被 compose.yaml 用到的值不會出現在任何地方；env_file 才是「把檔案內容設成容器環境變數」。a、b 把兩者當成同一件事；d 是捏造的，環境變數一律是字串，Compose 不轉換值。

練習 6：同事說：「資料庫密碼放在環境變數 DB_PASSWORD 沒關係，環境變數只有 app 自己看得到。」哪一個反駁最完整？

✓ b。這些都是不用入侵 app 就能拿到密碼的路徑；改用 /run/secrets 檔案可以避開大部分。a 把網路暴露和本機可見性混在一起；c 只有寫在 Dockerfile 的 ENV 才會進映像，部署時給的不會（第 9 課）；d 環境變數不會在網路上傳輸。

練習 7：你發現一個 GitHub token 三小時前被 push 到公開 repo，目前沒有看到異常。第一件事做什麼？

✓ d。公開 repo 會被自動掃描，push 出去就當作已經外洩，只有撤銷能讓它失效；確認已被濫用時可以直接先撤銷。a 不能讓 token 失效，三小時內可能早被 clone；b 舊 commit 裡還在；c 查紀錄很重要，但等查完的這段時間 token 仍然有效。

練習 8：有人提議「staging 和 production 各自 build 映像，每個環境可以用不同的建置參數最佳化」。你的回應？

✓ a。不可變映像讓「測過的」和「上線的」完全相同，回滾也只是換 tag 或 digest。b 除錯工具本來就不該在任何環境的映像裡（第 9 課的多階段建置）；c 同一個 Dockerfile 在不同時間建置，套件、基底映像都可能更新，不保證相同。

常見錯誤

  • 把 .env 推上 git：裡面通常有真的值。.gitignore 寫 .env，提交 .env.example 只列鍵；已經推上去的，裡面的機密一律輪替。
  • 在 log 印出整份設定或 process.env：除錯一時方便，密碼就進了集中 log。只印非機密的欄位，像練習裡的 /config。
  • 用 ARG 或 ENV 傳機密：會留在映像的 metadata 或層裡（第 9 課）。建置時用 build secret，執行時用 /run/secrets。
  • 外洩後只刪檔案、沒有輪替：git 歷史裡還在，金鑰也還有效。先輪替，再清歷史。
  • 所有環境共用同一組密碼：staging 通常保護得比較鬆，外洩就連帶 production。每個環境各自隨機產生。
  • secret 檔案權限 644：同一台機器上的其他使用者都讀得到。umask 077 加 chmod 600，並讓擁有者對上容器裡的使用者。
  • 讀密碼檔沒去掉結尾換行：postgres 去掉了、你的 app 沒去掉，兩邊的密碼就差一個 \n。
  • 換了密碼檔就以為資料庫密碼換了：postgres 只在初始化時讀。輪替要在資料庫裡改，並用雙憑證避免中斷。

小結

  • 映像只建一次、只裝程式；每個環境的設定在部署時才給，staging 測過的就是上線的那一個。
  • .env／--env-file 只替換 compose.yaml 的 ${...}；environment 和 env_file 才設定容器；優先順序 run -e > environment > env_file > 映像 ENV；用 docker compose config 看最後的結果。
  • 必要的部署變數用 ${VAR:?}，app 啟動時再驗證一次。
  • 機密放環境變數會從 inspect、/proc、子程序、log 外洩；用 Compose secrets 掛成 /run/secrets/<名稱>，搭配 _FILE 慣例，檔案 600、不進 git。
  • push 出去就當作外洩：先輪替（新的上線、確認、撤銷舊的），再查紀錄、清歷史、加上 pre-commit 和 push protection；gitleaks 的 git 模式掃整個歷史，git log -S 找出加入的 commit。
  • 雙憑證讓輪替不中斷；能用短期憑證就不用長期密碼；伺服器多了之後用 secret manager 集中存放、授權、稽核。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：cafe-api 把客人上傳的照片存在容器裡的 /app/uploads。昨天容器重開過，照片都還在；今天部署新版之後，照片全部不見了。為什麼？

✓ 可寫層屬於那個容器，stop／start 還在，docker rm 就跟著消失；升級映像一定要換容器。要留下來的資料放具名 volume 或 bind mount。a 錯在新映像從來沒碰過舊容器的可寫層，新容器是從新映像加一層全新的可寫層開始。（第 7 課）

練習 10：staging 驗過的 cafe-api 用的是 node:24.22.2-alpine3.24，你要確保下週 production 部署時跑的是同一個基底映像。部署設定怎麼寫？

✓ digest 是內容的指紋，同一個 digest 永遠拿到同樣的內容；tag 像 git 分支，維護者隨時能指到新映像。index 的 digest 涵蓋每種 CPU，各主機拉自己的平台。b 錯在官方映像會為安全修補重建，最細的 tag 也會指到新內容。（第 7 課）

練習 11：CI 在同一台建置機上連續建置兩個 commit，只改了一行程式，RUN npm ci 卻每次都重跑。哪裡出了問題？

FROM node:24.22.2-alpine3.24
ARG GIT_SHA
ENV GIT_SHA=$GIT_SHA
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build
CMD ["node", "dist/server.js"]

✓ 層快取從第一個變動的步驟開始失效，ENV GIT_SHA 每個 commit 都變，後面的 npm ci 跟著重跑。少變的放前面：版本資訊的 ARG／ENV 移到最後。a 錯在 COPY . . 在 npm ci 之後，它再怎麼變也只影響後面的步驟。（第 8 課）

練習 12：程式有處理 SIGTERM，本機直接跑 node dist/server.js 按 Ctrl+C 會印出 shutdown complete。但部署時每個容器都要等 10 秒才停、結束碼 137，log 沒有那一行。Dockerfile 結尾如下，原因是？

USER node
CMD node dist/check-env.js && node dist/server.js

✓ docker stop 把 SIGTERM 送給 PID 1；sh 當 PID 1 不轉送訊號，等滿 10 秒 Docker 送 SIGKILL，結束碼 137，優雅關機沒跑。改成 exec 形式 CMD ["node", "dist/server.js"]，讓 node 當 PID 1。c 錯在訊號根本沒送到 node，等再久也只是延後被 SIGKILL。（第 8 課）

練習 13：同事想讓映像變小，在單一階段的 Dockerfile 最後加一行 RUN npm prune --omit=dev && rm -rf src /root/.npm，重新建置後 docker images 的大小幾乎沒變。為什麼？

✓ npm ci 那層的 44MB 照樣要下載，也照樣能從那一層把檔案拿出來；機密用 rm 刪也是同一個道理。改成多階段建置，最終階段從乾淨的基底 COPY --from 只拿 dist/ 和正式依賴。b 錯在不用快取重建，產出的層還是一樣，刪除標記依然只是蓋在上面。（第 9 課）

練習 14：咖啡店在 EC2 上用 Compose 上線，ufw 只開 22、80、443。同事在 db 加了 ports: ["5432:5432"]，理由是「api 要連得到資料庫」。這樣會怎樣？

✓ 同一個專案網路裡用服務名稱互連，ports 只管主機怎麼連進來；Docker 的 iptables 規則排在 ufw 之前，"5432:5432" 等於開給全世界。刪掉這行，要查資料用 docker compose exec db psql 或 ssh -L。a 錯在 ufw 擋不住 Docker 發布的 port。（第 10 課）

練習 15：新伺服器第一次 docker compose up -d，api 重啟了好幾次才正常；之後再部署就沒事。api 寫了 depends_on: [db] 和 restart: unless-stopped，最可能的原因？

✓ 只寫名稱等於 service_started，不等 PostgreSQL 能接受連線；第一次要初始化，空窗最長，這種看時機的錯是競態。給 db 加 healthcheck，api 用 condition: service_healthy。b 錯在 depends_on 保證 db 先啟動，問題是「啟動」不等於「準備好」。（第 10 課）

練習 16：code review 指出 DB_PASSWORD 寫在 compose.yaml 的 environment 不妥。哪一個改法真的讓密碼不再從 docker inspect、/proc、子程序外洩？

✓ secrets 是檔案：能設權限、只掛進需要的容器、不在 inspect 的 Env 裡，也不會自動傳給子程序。a 只是換了來源，容器收到的仍然是環境變數，inspect 照樣看得到；它和 c 都只解決了「不進 git」。檔案記得 600、讀的時候去掉結尾換行。（第 11 課）
