階段 1：伺服器基本功 · 第 1 課

部署與維運全貌：從 git push 到使用者

咖啡店的 API 在你的筆電上跑得好好的：node server.ts，瀏覽器打 localhost:3000 就有菜單。可是客人用手機點餐時，連的不是你的筆電。程式要放到一台 24 小時開著的電腦上，讓網路上的人找得到它；它當掉要有人知道、流量變大要撐得住、資料要備份、改版不能讓客人看到錯誤頁。

前兩件事叫部署（deploy）：把某個版本的程式放到伺服器上、開始服務使用者。後面那些叫維運（operations，常簡稱 ops）：讓服務持續可用的工作，包括監控、擴展、備份、處理事故。這一課先畫出整張地圖，讓你知道後面 25 課各自在補哪一塊。

這課的路線：
  1. 一個請求的旅程：客人在手機上點一杯拿鐵，請求經過 DNS、反向代理、app 副本、資料庫哪幾站，每一站在後面哪一課教。
  2. 一次改動的旅程與環境：改了價格怎麼安全地送到客人眼前，為什麼 staging 和正式環境要跑同一個映像。
  3. 啟動 Docker、開第一個容器：Mac 上的 Docker 其實跑在一台 Linux 虛擬機裡；開一台用完即丟的 Linux，再在背景跑一台 nginx。
  4. 這門課的練習怎麼進行：用 check.mjs 取得起始檔、跑測試。
這課會用到：
  • Node 課第 12 課的 HTTP 與 curl：一次請求換一個回應，回應有狀態碼、標頭和內容；curl 在終端機裡送請求。
  • Node 課第 13 課用 node:http 寫的伺服器：聽一個 port、收到請求就回應，就是這門課要部署的東西。
沒用過 Docker 也沒關係，這課從頭講。

一個請求的旅程

客人在手機上打開 https://cafe.example.com、點一杯拿鐵。這個請求在正式環境會經過好幾站：

  1. DNS：瀏覽器只知道網域名稱，先問 DNS「cafe.example.com 的 IP 是多少」，拿到 IP 才能連線。
  2. 反向代理（reverse proxy）：站在 app 前面、替它接住所有請求的程式，常用 nginx。它負責 HTTPS 加解密、擋掉過大的上傳和太密集的請求，也負責負載平衡（load balancing）：把請求分給後面的多份 app。
  3. 多個 app 副本：同一份 cafe-api 跑好幾份。一份當掉，其他份還在服務；流量變大就多開幾份。
  4. 資料庫與快取：Redis 是把資料放在記憶體裡、讀寫很快的資料庫，常拿來放快取和購物車這類暫存資料。所有副本共用同一個 PostgreSQL 和 Redis，所以不管請求被分到哪個副本，看到的訂單和購物車都一樣。

這些站全都跑在伺服器（server）上：長時間開著、透過網路提供服務的電腦。它可以是一台實體機，更常見的是雲端上的虛擬機（virtual machine，VM）：用軟體模擬出的一台完整電腦，有自己的作業系統，跟其他客戶共用同一台實體機。

一次改動的旅程

反過來看你這一端：你改了拿鐵的價格，要怎麼讓客人看到？靠手動登入伺服器、複製檔案、重開程式，遲早會在週五晚上出事。業界的做法是一條自動化的流水線：

  • PR（pull request）：請同事審查你的改動，合併進主線之前的關卡。
  • CI（continuous integration，持續整合）：每次改動都自動跑 lint、型別檢查、測試，沒過就不能合併。
  • 映像倉庫（registry）：存放建置好的映像的伺服器，例如 Docker Hub（Docker 官方的公開映像倉庫）。伺服器部署時從這裡下載（第 7 課）。
  • CD（continuous delivery／deployment，持續交付／部署）：通過檢查的改動自動送到 staging、production。這兩個環境下一節說明。
  • 回滾（rollback）：新版出事時，退回上一個正常的版本。

重點是中間那個產物（artifact）：建置後拿去部署的東西。在這門課，產物是一個 Docker 映像（image），裡面打包了程式、依賴的套件和執行環境。映像只建置一次，staging 和 production 跑的是同一個映像，差別只在設定。出事時回滾，就是把上一個映像再部署一次。

DevOps 這個詞指的就是這種做法：同一群人負責開發與維運，用自動化縮短從寫程式到上線的時間。它是一種工作方式，不是一個職位或一套工具。

💡 實務上：新人最先碰到的是這條流水線
進團隊的第一週，你多半不會直接登入伺服器，而是看到 PR 上的 CI 紅燈、部署頻道裡的通知、等人按下正式環境的核准。先問清楚四件事：改動從合併到上線要多久、誰能按部署、出事時怎麼回滾、半夜誰會被叫醒。答不出來的團隊，代表流程靠某幾個人的記憶在撐，這門課後面每一段都在補這件事。

環境與 dev/prod parity

環境（environment）是同一套程式的不同部署。一般至少有三個：

開發（development）staging（預備環境）正式（production）
在哪裡你的筆電跟正式環境同樣架構的伺服器真正服務使用者的伺服器
資料假資料，隨時可以重建假資料或去識別化的副本真實訂單、真實顧客
誰在用你自己團隊、測試人員客人
出錯的代價重開就好擋下一次壞的上線客人點不到餐、資料可能遺失

staging 存在的目的，是在上線前最後一次驗證：用跟正式環境一樣的映像、一樣版本的資料庫、一樣的反向代理設定跑一遍。它跟正式環境差得越多，就有越多問題要到正式環境才發現。

經典的「在我電腦可以跑」就是環境不一致造成的：你的筆電是 macOS、Node 24、PostgreSQL 18；伺服器卻是 Linux、Node 22、PostgreSQL 16，大小寫不分的檔名、少裝的套件、不同的預設值，都會讓同一份程式碼表現不同。十二要素應用（The Twelve-Factor App，一份描述雲端服務寫法的經典準則）的第 X 條「開發與正式環境等價」（dev/prod parity）就是在講這件事：讓各環境盡量一致。容器讓這件事容易很多：開發、CI、staging、正式環境都跑同一個映像。

💡 實務上：把 staging 和正式環境的差異寫成清單
staging 不可能跟正式環境完全一樣：機器比較小、資料比較少、金流和簡訊接的是第三方的測試環境。差異本身沒問題，問題是沒人知道有哪些，於是「staging 測過了」被當成「正式環境不會出事」。資深工程師會把已知的差異寫在部署文件裡，上線前想一遍「這次的改動會不會剛好落在差異上」。也不要為了測試方便，把正式環境的顧客資料直接複製到 staging：那是個資外洩的風險，資安和法務都會關心。

啟動 Docker：Mac 上的一台 Linux 虛擬機

伺服器幾乎都跑 Linux，而容器是 Linux 核心的功能。macOS 不是 Linux，所以 Docker Desktop 的做法是在你的 Mac 上開一台小小的 Linux 虛擬機，容器全都跑在那台虛擬機裡。

Docker 分成兩半：

  • Client：你在終端機打的 docker 指令，跑在 macOS 上。它本身不跑容器，只負責把要求送出去。
  • Server：真正管理映像和容器的 Docker Engine，是一個 daemon（常駐程式，在背景長時間執行的程式），跑在那台 Linux 虛擬機裡。

Docker Desktop 沒開時，Client 還在，但它找不到 Server。打開它可以點應用程式，也可以從終端機：

docker desktop start      # 或 open -a Docker
docker version

這台 Mac（Docker Desktop 4.85.0）上 docker version 的輸出，節錄重點：

Client:
 Version:           29.6.2
 OS/Arch:           darwin/arm64
 Context:           desktop-linux

Server: Docker Desktop 4.85.0 (235549)
 Engine:
  Version:          29.6.2
  OS/Arch:          linux/arm64

兩段各看一行就夠：Client 的 OS 是 darwin（macOS 的核心名稱），Server 的 OS 是 linux，這證明 daemon 跑在虛擬機裡。Server: 那行後面的 4.85.0 是 Docker Desktop 這個應用程式的版本，Engine 底下的 Version 才是 daemon 本身的版本。

如果 Docker Desktop 沒開，你只會看到 Client 那段，接著是一行錯誤：

failed to connect to the docker API at unix:///Users/你/.docker/run/docker.sock;
check if the path is correct and if the daemon is running

docker.sock 是一個 Unix socket：同一台電腦上兩個程式互相傳訊息用的特殊檔案，Client 透過它把要求送給 daemon。這行的意思是「Client 找不到 daemon」：Docker 有裝，只是沒在跑。解法是啟動 Docker Desktop，不是重裝，也不是加 sudo。如果你設過環境變數 DOCKER_HOST，Client 會改去連它指的位址，指錯了也會出現同樣的錯誤。

第一個容器：一台用完即丟的 Linux

容器（container）的原理留到第 7 課拆解，這一課先把它當成「一台幾秒鐘就開好、用完即丟的 Linux 環境」：

docker run --rm -it ubuntu:24.04 bash
  • ubuntu:24.04：用哪個映像。冒號後面是標籤（tag），指定版本。第一次用會先從 Docker Hub 下載。
  • -it：接上你的鍵盤和終端機，才能互動地打指令。
  • --rm：容器結束時自動刪掉。
  • bash：在容器裡執行的程式。

進去之後試試看：

cat /etc/os-release    # 這是哪個發行版、哪一版
uname -m               # CPU 架構
ls /                   # 一個完整的 Linux 檔案系統
touch /hello.txt
exit

離開後再執行一次同樣的 docker run，/hello.txt 已經不在了：每次 docker run 都從映像開一個全新的容器，而 --rm 讓舊的那個在結束時被刪掉。容器裡寫的檔案不會自己留下來，要保存資料得用 volume（由 Docker 管理、容器刪掉也會留下的儲存空間，第 7 課）。

不需要互動時，可以直接把指令接在後面，跑完就結束：

docker run --rm ubuntu:24.04 uname -m

你的 Mac 是 arm64，伺服器常是 amd64

Apple Silicon 的 Mac 用 ARM 架構的 CPU。同一種架構在不同系統有不同名字：macOS 叫 arm64，Linux 的 uname -m 叫 aarch64。很多雲端伺服器則是 Intel／AMD 的 x86-64 架構，Docker 叫它 amd64，Linux 叫 x86_64。在 Mac 上建置的映像預設是 arm64 版，直接丟到 amd64 的伺服器上會跑不起來，第 9 課會教跨平台建置。

用容器跑一台網站

容器也可以在背景一直跑，像一台伺服器。下面用官方的 nginx 映像開一台網站：

docker run -d --name ld-01-web -p 127.0.0.1:18010:80 nginx:1.30-alpine
curl -I http://localhost:18010
docker rm -f ld-01-web
  • -d：在背景執行（detached），指令馬上回到提示字元，容器繼續跑。
  • --name ld-01-web：給容器取名字，之後用名字操作它。
  • -p 127.0.0.1:18010:80：發布 port，格式是「主機 IP:主機 port:容器 port」。nginx 在容器裡聽 80，從 Mac 這端要連 18010。
  • curl -I：只看回應標頭。
  • docker rm -f：停掉並刪除容器。
只寫 -p 18010:80 時，Docker 預設把 port 發布在主機的所有位址上（0.0.0.0 和 ::），Docker 文件直接說發布 port「預設不安全」。你在咖啡店連 Wi-Fi 時，同一個網路的人都連得到你的練習資料庫。這門課的所有服務一律寫成 127.0.0.1:主機port:容器port，只有你自己的電腦連得到。

這門課的練習怎麼進行

練習在你自己的 Mac 上做，用真的 Docker、真的 shell。流程：

  1. 第一次做這門課的練習，先在 learn/devops/practice 執行一次 npm install，安裝測試用的套件。
  2. 在 learn 資料夾執行 node check.mjs devops 01（01 是課號）。第一次執行會把起始檔從 devops/practice/start/01/ 複製到 devops/practice/work/01/，然後跑測試。
  3. 打開 work/01/ 裡的檔案寫答案，存檔後再執行同一個指令。你改過的檔案不會被蓋掉；想從頭來，刪掉那個檔案再執行，起始檔會重新複製過來。
  4. 測試結果存到 devops/practice/results/01.json，切回課程頁就會更新每一題的結果。

練習用到的資源都有固定的命名，方便你辨認和清理：容器、volume、網路的名稱以 ld- 加課號開頭（例如 ld-01-web），第 NN 課（兩位數課號）發布的 port 在 18NN0～18NN9 之間（第 1 課是 18010～18019，第 12 課是 18120～18129），一律只開在 127.0.0.1。測試開始前會先刪掉同名的舊容器，結束後也會清掉自己開的東西。

容器和映像會占磁碟空間，用這個指令看用了多少：

docker system df

它列出映像（Images）、容器（Containers）、volume（Local Volumes）和建置快取（Build Cache）各占多少、有多少可以回收（RECLAIMABLE）。這門課會下載幾個 GB 的映像，第 7 課會教怎麼安全地清理。

練習

練習 1：啟動 Docker Desktop，執行 docker version，把 Server 段落裡 Engine 的版本（Version）和 OS/Arch 填進 versions.json 的 serverVersion 和 serverOs（OS/Arch 那一行的完整值，斜線兩邊都要）。這門課後面會用到 Engine 29 的預設行為，所以測試也會確認 Engine 主版本至少 29。測試會先確認 daemon 在跑，沒跑的話會告訴你怎麼啟動。

練習 2：用 docker run --rm ubuntu:24.04 … 在容器裡查出 CPU 架構（uname -m）和 Ubuntu 的版本代號（/etc/os-release 裡的 VERSION_CODENAME），填進 container.json 的 arch 和 codename。答案要從容器裡查，不是在 Mac 上查，也不要憑印象填。

練習 3：在 web.sh 寫一行 docker run：在背景啟動 nginx:1.30-alpine，容器名稱 ld-01-web，只發布在 127.0.0.1:18010。自己執行 sh web.sh，再用 curl -I http://localhost:18010 看回應，把 Server 標頭的完整值（含版本）填進 web.json 的 server。測試會刪掉舊容器、執行你的 web.sh、檢查容器和 port，最後清掉容器；你自己試完也記得 docker rm -f ld-01-web，不然下一次執行會因為名稱重複而失敗。

練習 4：客人在瀏覽器輸入 https://cafe.example.com，瀏覽器第一個要問的是誰？

✓ 網路連線要靠 IP 位址，瀏覽器手上只有網域名稱，所以第一步一定是問 DNS。拿到 IP 之後才連得到 nginx（它確實是入口，但要先知道它在哪）；cafe-api 和 PostgreSQL 躲在反向代理後面，客人根本不會直接連到。

練習 5：正式環境用 PostgreSQL 18，有人提議 staging 用比較省事的 PostgreSQL 16，反正只是測試。你的看法？

✓ staging 的價值就是「上線前最後一次在跟正式環境一樣的條件下驗證」。版本不同，支援的 SQL 功能、預設值、效能表現都可能不同，問題會等到正式環境才爆，所以 a 錯。開發環境也要盡量一致（dev/prod parity），但開發環境是你的筆電，資料、反向代理、部署流程都跟正式環境不同，不能取代 staging，所以 b 錯。

練習 6：執行 docker ps 時看到「failed to connect to the docker API at unix:///Users/…/docker.sock; check if the path is correct and if the daemon is running」。該怎麼做？

✓ 能印出這行錯誤，代表 Client（docker 指令）是好的，只是連不到 Server（daemon）。Docker Desktop 沒開時就是這樣，啟動它即可。重裝解決不了沒啟動的問題（a 錯）；sudo 只是換成 root 身分執行 Client，daemon 沒在跑，誰去連都一樣連不上（c 錯）。

常見錯誤

  • Docker Desktop 沒開就打 docker 指令，以為安裝壞了：先看錯誤是 Client 還是 Server 的。看得到 Client 版本、連不上 daemon，就是 Docker Desktop 沒在跑。
  • 把 Server: Docker Desktop 4.85.0 當成 Engine 版本：那是應用程式的版本，daemon 的版本在 Engine 底下的 Version。
  • port 寫成 -p 18010:80：Docker 預設發布在所有位址，同一個 Wi-Fi 的人都連得到。寫成 -p 127.0.0.1:18010:80。
  • 以為 docker run --rm 結束後，容器裡改的檔案還在：容器刪掉，裡面的改動就跟著沒了；要保存的資料放 volume（第 7 課）。
  • 在 learn 以外的資料夾執行 check.mjs：指令是在 learn 資料夾執行 node check.mjs devops 01，不是在 work/01 裡。
  • 部署時用 latest 或沒寫版本的標籤：沒寫標籤時 Docker 用的就是 latest，它會跟著新版移動，今天和明天拉到的可能是不同的東西。這門課的映像一律寫明版本；第 7 課會再用 digest（映像內容算出的指紋，內容一變它就變）把映像完全鎖死。

小結

  • 一個請求的路：DNS → 負載平衡／反向代理 → 多個 app 副本 → 共用的資料庫與快取。
  • 一次改動的路：commit → PR → CI → 建置映像 → 映像倉庫 → staging → production → 監控，出事就回滾到上一個映像。
  • 映像只建置一次，各環境跑同一個映像、只換設定；staging 盡量和正式環境一致（dev/prod parity）。
  • Docker 分 Client（Mac 上的 docker 指令）和 Server（Linux 虛擬機裡的 daemon）。連不上 daemon 就啟動 Docker Desktop。
  • docker run --rm 開用完即丟的容器；-d --name 在背景跑服務；port 一律發布在 127.0.0.1。
  • Mac 是 arm64（Linux 叫 aarch64），很多伺服器是 amd64（x86_64）。
