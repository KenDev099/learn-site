階段 3：流量與擴展 · 第 13 課

無狀態與水平擴展

週末的買一送一活動，咖啡店的點餐量是平常的五倍。只有一個 cafe-api 在跑，CPU 頂在 100%，p99 從 200ms 變成 8 秒。你照著直覺在 Compose 裡把 api 開成 3 份，速度回來了，客服卻開始收到奇怪的回報：「購物車裡的拿鐵一下有一下沒有」「我明明登入了，重新整理又被登出」。

這一課把 cafe-api 從一份變成好幾份，並讓它們真的能互相替代。

這課的路線：
  1. 擴展的兩個方向：換一台大機器還是多開幾份，為什麼 Node 服務靠多開副本。
  2. 狀態藏在哪裡、把狀態搬出去：購物車一下有一下沒有、重新整理就被登出的原因，怎麼把 session 和購物車搬到 Redis（開場問題的最小答案）。
  3. nginx 負載平衡、健康檢查與排空：把流量分給所有副本，副本掛掉、換 IP、被縮減時都不掉請求。
  4. 容量規劃：活動尖峰需要幾個副本，資料庫連線夠不夠分。
  5. Kubernetes：這一課手動做的事換到編排器上叫什麼，什麼規模才值得用。
這課會用到：
  • Auth 課第 4 課的 session：瀏覽器的 cookie 只帶一個 session ID，登入狀態存在伺服器那一端。
  • 第 10 課的 Compose：服務之間用服務名稱互連，healthcheck 讓 Docker 知道服務準備好了沒。
  • 第 12 課的 nginx：proxy_pass 把請求轉給後端，upstream 連線閒置太久會被關掉，所以後端的閒置逾時要比 nginx 長。

擴展的兩個方向

服務撐不住時有兩種做法：

  • 垂直擴展（scale up）：換一台更大的機器，CPU 和記憶體變多，程式不用改。
  • 水平擴展（scale out）：同一個程式多跑幾份。每一份叫一個副本（replica），前面由負載平衡（load balancing）把請求分給它們。
垂直擴展水平擴展
上限最大的機器型號；再上去價格不成比例理論上一直加，實際受限於共用的資料庫、Redis
程式要改嗎不用要：程序不能自己保存狀態
升級時換機器通常要停機一個一個換，其他副本照常服務
單點故障機器掛了就全掛掛一個，其他副本接手
適合資料庫這類難以拆開的服務；流量還小時API、網站這類無狀態服務

Node 特別需要水平擴展：一個 Node 程序只有一條主執行緒執行你的 JavaScript（Node 課第 24 課），機器換成 16 核心，一個程序也只用得到一核。所以 Node 服務的常見做法是「每個副本給 1 個 CPU 左右，用副本數擴展」。

這一課用 Compose 加 nginx 手動做一次，弄懂每個環節；最後一節對照 Kubernetes，你會發現它只是把同樣的事自動化，名字換了而已。

狀態藏在哪裡

無狀態（stateless）指程序本身不保存「下一個請求還需要」的資料。12-factor 第 VI 條的說法是：程序之間不共享任何東西，需要保存的資料一律放在後端服務（資料庫、Redis）裡。做到這點，任何一個副本都能處理任何一個請求，副本才能隨時加、隨時刪。

狀態常常藏在你沒注意的地方：

起始版的 cafe-api 把購物車放在一個 Map 裡。只有一個副本時完全正常；開成 3 個、nginx 輪流分配後，就會出現開頭的狀況：

$ curl -s -b sid=abc -X POST localhost:18130/cart/items -H 'content-type: application/json' -d '{"productId":2}'
{"items":[2]}                     # 副本 1 的 Map 記住了
$ curl -s -b sid=abc localhost:18130/cart
{"items":[]}                      # 這次分到副本 2，它的 Map 是空的
$ curl -s -b sid=abc localhost:18130/cart
{"items":[]}                      # 副本 3，也是空的
$ curl -s -b sid=abc localhost:18130/cart
{"items":[2]}                     # 又輪回副本 1

每個副本是獨立的程序，各有各的記憶體。其他狀態也是同樣的問題：

  • 記憶體限流：每個副本各數各的，「每分鐘 100 次」在 3 個副本下變成大約 300 次。
  • 上傳檔存在容器的磁碟：只有收到上傳的那個副本有，而且容器重建就沒了。
  • 排程用 setInterval 寫在 app 裡：3 個副本各跑一次，日報寄了 3 封。
  • 記憶體快取：每個副本各一份，更新商品價格後，有的副本回新價、有的回舊價，直到快取過期。

把狀態搬出去

原則是：程序裡只放「丟了也沒關係」的東西，其他的放到所有副本都連得到的地方。

狀態搬到哪裡重點
session、購物車Redis一定要設 TTL，不然沒結帳的購物車永遠占著記憶體
訂單、會員資料PostgreSQL要永久保存、要交易保證的
限流計數Redis（INCR 加 EXPIRE）或入口的 nginx所有副本共用同一個計數
上傳檔S3 這類物件儲存（NestJS 課第 22 課）容器裡的磁碟當作隨時會消失
排程單一排程器（另一個只跑 1 份的服務），或每個副本搶 advisory lock同一個工作只有一個執行者
快取可以留在各副本，或改放 Redis能接受幾秒不一致就留著，它最快

購物車搬到 Redis 的寫法（ioredis 6.0.0，用法見 NestJS 課第 19 課）：key 用 cart:<sid>，值用 Redis 的 list（依加入順序排列的清單），每次加入商品都把期限重設成 1 天。

const key = (sid: string) => `cart:${sid}`

export async function addItem(redis: Redis, sid: string, productId: number) {
  // RPUSH 加在清單尾端；EXPIRE 把期限設成 86400 秒
  await redis.rpush(key(sid), productId)
  await redis.expire(key(sid), 86_400)
}

兩個指令分開送，中間程序如果剛好被停掉，會留下一個沒有期限的 key。用 redis.multi() 把它們包成一組一起執行，練習 1 會用到。

排程：最簡單的是把它從 api 拆出去，變成只跑 1 份的 worker 服務。如果一定要留在 api 裡，就讓每個副本在執行前用 PostgreSQL 的 pg_try_advisory_lock 搶鎖，搶到的才執行（PostgreSQL 課第 33 課）。

黏性 session 不是解法。黏性 session（sticky session）是讓負載平衡把同一個使用者固定送到同一個副本，例如 nginx 的 ip_hash，或 1.29.6 起開放原始碼版也能用的 sticky。購物車看起來好了，但只是把問題藏起來：那個副本重啟、被縮減或部署時，它記憶體裡的購物車一起消失；同一個公司或學校的人共用一個對外 IP，全部擠到同一台；新加的副本分不到舊客人。先把狀態搬出去，才談得上擴展。
💡 實務上：加副本之前，先做一次「無狀態檢查」
接手一個服務要開多副本時，先在程式裡搜尋 new Map、模組層級的陣列或物件、setInterval、cron 套件、寫到本機路徑的上傳設定，以及記憶體版的限流與 session 套件（很多套件的預設儲存就是記憶體）。每找到一個，就問同一個問題：「這個副本現在被砍掉，使用者會發現嗎？」會發現的就要搬出去。最可靠的驗證是在測試環境開 2 個以上副本跑一輪主要流程，中途重啟其中一個。購物車消失是 PM 會在意的營收問題，session 存在哪裡則是資安審查會問的事。

nginx 負載平衡

第 12 課的 proxy_pass http://api:3000 只寫了一個位址。要分給多個副本，用 upstream 區塊定義一組後端：

upstream api {
    zone api 64k;                            # 這組後端的狀態放在共用記憶體，所有 worker 看到同一份
    resolver 127.0.0.11 valid=5s ipv6=off;   # Docker 內建的 DNS 伺服器，查到的結果用 5 秒
    least_conn;                              # 分給目前連線最少的副本
    server api:3000 resolve max_fails=2 fail_timeout=5s;
}

server {
    listen 80;
    location / {
        proxy_pass http://api;               # 名稱對到上面的 upstream
        proxy_next_upstream error timeout http_502 http_503;
        proxy_connect_timeout 2s;            # 內部網路建立連線只要幾毫秒，預設 60 秒太久
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Request-ID $request_id;
    }
}

一行一行看（以下依 nginx 官方文件，練習用 nginx 1.30.6）：

  • 分配方式：預設是 round robin，依序輪流分給每一台。least_conn 把請求給目前進行中連線最少的那台，平手時再輪流。請求花的時間差很多時（有的 10ms、有的 3 秒），least_conn 比較不會把請求堆在正在忙的那台。
  • 被動健康檢查（passive health check）：nginx 開放原始碼版不會主動去打健康檢查端點（主動的 health_check 是商業版功能），而是從真實請求的失敗判斷。max_fails=2 fail_timeout=5s 表示 5 秒內失敗 2 次，就把這台當成壞掉，接下來 5 秒不送過去。預設是 1 次、10 秒。
  • proxy_next_upstream：這台失敗時換下一台再試。預設 error timeout，也就是連不上或逾時；加上 http_502 http_503，後端回 502、503 也換。
  • proxy_connect_timeout：建立連線最多等多久，預設 60 秒。副本當掉（例如被 OOM 殺掉）時，它的 IP 常常不會回「拒絕連線」，而是完全沒有回應；送到它的請求會卡滿 60 秒才換下一台。同一個網路裡建立連線只要幾毫秒，設成 1～2 秒就夠。
  • resolve：定期重新查 api 這個名字的 IP。

只重試冪等的請求

冪等（idempotent）是「做一次和做很多次，結果相同」。GET 是冪等的，查幾次都一樣；POST /orders 不是，送兩次就是兩張訂單。

想像副本 1 收到下單請求，訂單已經寫進資料庫，回應時才出錯，nginx 收到 503。如果這時把同一個 POST 重送給副本 2，客人就被扣了兩次錢。所以 nginx 預設（1.9.13 起）：POST、PATCH、LOCK 這類非冪等的請求，只要已經送到後端，就不會再送給下一台；只有「連線根本沒建立」這種確定沒送出去的情況才會換一台。proxy_next_upstream 有一個 non_idempotent 參數會解除這個保護，不要加。POST 要重試，交給客戶端帶冪等鍵（Idempotency-Key）自己重試，由後端判斷是不是同一筆。

容器重建後的 IP

server api:3000 沒有 resolve 時，nginx 只在啟動（或 reload）時查一次 DNS，把查到的 3 個 IP 記下來。Compose 的服務名稱 api 會解析成所有副本的 IP，這部分沒問題；但容器被重建、副本增減時，Docker 不保證新容器拿到原本的 IP（舊位址被別的容器拿走時一定會換），換了之後 nginx 還在連舊的，全部變成 502；新加的副本也永遠分不到流量。

resolve 讓 nginx 依 resolver 的 valid=5s 每 5 秒重新查一次，副本增減、換 IP 都跟得上。它有兩個條件：要有 resolver（寫在 http 或這個 upstream 裡；127.0.0.11 是 Docker 給每個容器的內建 DNS），而且這組 upstream 要放在共用記憶體，也就是要有 zone。少了 zone，nginx -t 直接報錯。resolve 參數在 1.27.3 之前只有商業版有。

Compose 這邊，副本數寫在 deploy.replicas，也可以臨時用 --scale 改：

docker compose up -d --wait --scale api=5     # 開到 5 個
docker compose ps api                         # ld-13-api-1 … ld-13-api-5
curl -si localhost:18130/products | grep -i x-instance   # cafe-api 會回報是哪個副本處理的
副本不能發布固定的主機 port：3 個容器都想要主機的 3000 port，第二個就啟動失敗。api 不發布 port，只讓同一個網路裡的 nginx 連。

健康檢查與排空

有了多個副本，部署和縮減就是「停掉一些副本、開新的」。停的方式不對，正在處理的請求就會失敗。先分清楚兩種健康檢查（Node 課第 21 課）：

liveness（活著嗎）readiness（能接流量嗎）
問的是這個程序要不要被重啟現在要不要送新請求給它
失敗時編排器殺掉它、重開先不送流量，程序照跑
檢查什麼只看程序自己：事件迴圈還在動、沒有卡死資料庫、Redis 連得上；不在排空中
不要檢查資料庫、Redis 等外部依賴—

為什麼 liveness 不能檢查資料庫？資料庫維護 30 秒，所有副本的 liveness 同時失敗，編排器把它們全部重啟；重啟中的副本更接不了客，資料庫回來時又同時湧入一大批重新連線的請求。Kubernetes 文件也警告：錯誤的 liveness 會造成連環故障。資料庫掛了，副本該做的是 readiness 回 503，等它回來。

排空（draining）是停止前先不接新請求、把手上的做完。docker stop、縮減副本、部署時，容器會先收到 SIGTERM，在 stop_grace_period（這裡設 10 秒）內沒結束就被 SIGKILL（exit 137）。收到 SIGTERM 後的順序：

  1. readiness 改回 503：有主動健康檢查的負載平衡（Kubernetes、AWS ALB）看到就不再送新流量。這一步需要時間生效，所以要等。
  2. 繼續服務一段時間（DRAIN_MS），回應加上 Connection: close：nginx 和後端之間的連線會被重用（第 12 課），這個標頭叫對方用完這條就關掉，不再把下一個請求送進來。
  3. server.close()：停止接受新連線；Node 19 起它也會關掉閒置的 keep-alive 連線；進行中的請求不受影響，全部做完才呼叫 callback。之後 nginx 連過來會被拒絕（connection refused），這算「還沒送出」，連 POST 都會被換到下一台。
  4. 關資料庫連線池與 Redis，process.exit(0)。不關的話它們會讓程序一直不結束，最後被 SIGKILL。

起始版的 SIGTERM 處理是直接 process.exit(0)：正在處理的下單請求被切斷，nginx 拿到不完整的回應，客人看到 502。

做到這些，還剩一個很小的競爭：server.close() 關掉閒置連線的那一瞬間，nginx 可能剛好挑中這條連線送出請求，得到 Connection reset by peer。app 這邊沒辦法完全消除它，要靠前面的代理先把副本移出名單、app 後關連線。Kubernetes 的做法是 readiness 失敗或 Pod 進入終止時就把它移出 Service，再用 preStop 多等幾秒讓移除生效；nginx 開放原始碼版不會看 readiness，所以練習 3 容許 1 個這樣的失敗。

閒置逾時要前短後長（第 12 課）。nginx upstream 的 keepalive_timeout 預設 60 秒，Node 的 server.keepAliveTimeout（Node 課第 13 課）預設 5 秒。Node 先關閒置連線時，nginx 可能剛好把請求寫進這條正在關的連線，得到偶發的 502。把 app 的 keepAliveTimeout 設成比前面的代理長，例如 65 秒；前面換成 AWS ALB 時也是一樣，要比 ALB 的閒置逾時長。
💡 實務上：「每次部署都有幾個 502」通常是關機順序的問題
這類回報常被當成「部署本來就會抖一下」而放著不管。查的順序：先看 nginx 的 error log，connect() failed (111: Connection refused) 或 upstream prematurely closed connection 集中在部署的那幾秒，就是副本關得太粗魯；再確認 SIGTERM 真的送到 Node：CMD 寫成 shell 形式或 ["npm", "start"] 時，PID 1 可能不是 node，訊號不一定送得到（第 8 課），結果是每次都等滿 grace period 被 SIGKILL（ExitCode 137）；最後對一下各層的閒置逾時是不是前短後長。資深工程師會把「部署期間錯誤率」放進部署後的檢查清單，而不是等客服轉來。

容量規劃

容量規劃（capacity planning）是事先算出尖峰時需要幾個副本、多少資源。「感覺不夠就加」的問題是：等你感覺到時，客人已經在看 504。

第一步：量出一個副本的能力。用壓測工具（例如 autocannon；壓測時看 p99 而不是平均，見 Node 課第 23 課）逐步加壓一個副本，找出在目標內（例如 p95 < 300ms）能撐的最大 RPS（每秒請求數）。假設 cafe-api 一個副本是 180 RPS。

第二步：算副本數。平常不把副本用滿，留一些餘裕應付突然的流量，這個上限叫目標使用率（例如 70%）；再多留至少一個備用副本（N+1），掛掉一個或部署時少一個還撐得住。

副本數 = 無條件進位( 尖峰 RPS ÷ (單副本 RPS × 目標使用率) ) + 備用副本
       = ceil( 600 ÷ (180 × 0.7) ) + 1
       = ceil( 600 ÷ 126 ) + 1 = ceil(4.76) + 1 = 6

用平均流量算是常見的錯：咖啡店平均 150 RPS，算出來 2 個副本，早上 8 點的尖峰就垮了。也不能四捨五入：4.2 個副本四捨五入成 4，就是 105% 的負載。用程式算時注意浮點數，JavaScript 裡 180 * 0.7 是 125.99999999999999，剛好整除的情況可能被多進位一個。

第三步：算資料庫連線。Little's law：系統裡平均同時在處理的數量 ＝ 每秒到達數 × 平均停留秒數。套到連線池：一個副本每秒 180 個請求，每個請求占用資料庫連線 0.02 秒，平均同時有 180 × 0.02 = 3.6 條連線在用；流量不平均，再乘上安全係數 2，無條件進位成 8，每個副本的連線池設 8。

第四步：檢查資料庫的連線預算。PostgreSQL 的 max_connections 是所有副本共用的（PostgreSQL 課第 36 課）。部署時新副本先起來、舊的才停，會短暫多出幾個副本（Kubernetes 叫 maxSurge），也要算進去：

需要 = (副本數 + maxSurge) × 每個連線池 = (6 + 1) × 8 = 56
可用 = max_connections − 保留給管理與 migration 的 = 100 − 10 = 90     → 56 ≤ 90，夠

超過時的症狀是部署到一半，新副本連資料庫失敗（sorry, too many clients already），或請求卡在等連線池而逾時。解法依序是：把連線池調小（Little's law 算出來的通常比你想的小）、在中間放 PgBouncer、或換更大的資料庫。副本數 × 連線池這筆帳，每次加副本都要重算。

💡 實務上：活動前的容量規劃，是 PM 和工程師一起做的
行銷排了買一送一，工程這邊最先要問的是：預估的尖峰是平常的幾倍、集中在哪個時段、會打到哪些 API（點餐比瀏覽菜單重得多）。拿到數字後，用上面的公式算副本數與連線預算，提前一兩天擴好，不要賭自動擴縮來得及：新副本從建立到通過 readiness 要時間，資料庫也不會跟著自動變大。活動結束後拿實際的流量與 p95 對照當初的估計，修正「一個副本能撐多少」這個數字，下一次就更準（指標怎麼收，見第 22 課）。

練習

練習在 devops/practice 做，需要 Docker 在跑。compose.yaml 已經寫好、不用改：PostgreSQL 18.6、Redis 8.10.3、3 個 cafe-api 副本（app/，第 9 課的多階段建置，server.ts 不用改），以及發布在 127.0.0.1:18130 的 nginx 1.30.6。每個回應都有 X-Instance 標頭，告訴你是哪個副本處理的。測試每次都會先收掉 ld-13、重新建置並啟動，跑完也會收掉；第一次會花幾分鐘下載映像與建置。三題依序做：後面的測試用的是你目前的整份程式。自己試：docker compose up -d --wait --build，curl -si localhost:18130/products，收掉用 docker compose down -v。

練習 1：把購物車從記憶體搬到 Redis。改 app/src/cart.ts：addItem 把商品編號加在 cart:<sid> 這個 list 的尾端，並把期限設成 1 天（86400 秒），兩個指令用 redis.multi() 一起送出；getCart 依加入順序回傳數字陣列。測試會用同一個 sid 加入 3 項隨機商品，連續 10 次 GET /cart 都要看到同樣的 3 項，重啟一個副本後再查一次，再用 redis-cli 檢查 key 是 list、期限約 1 天，並用 MONITOR（印出 Redis 收到的每個指令）確認 RPUSH 和 EXPIRE 包在同一個 MULTI／EXEC 裡；也會檢查 nginx 設定沒有用 ip_hash、hash、sticky 把問題藏起來。

練習 2：改 nginx/default.conf 的 upstream 與 location：用 least_conn；被動健康檢查 5 秒內失敗 2 次就停用 5 秒；用 Docker 的 DNS（127.0.0.11）每 5 秒重新解析 api；遇到連線錯誤、逾時、502、503 換下一台，建立連線最多等 2 秒，但不能讓 POST 被重送。測試會：用一個 2.5 秒的慢請求占住一個副本，確認新請求都分給別人；送 60 個 GET 確認 3 個副本都分得到；docker kill 一個副本後送 30 個 GET，最多只能失敗 1 個（resolve 剛好在換下一台的途中更新名單時，nginx 可能回一次 502）；先移除所有 api 容器、用佔位容器拿走舊 IP，再重新建立 api（IP 全換），10 秒內要恢復，再過一輪解析後 3 個新副本都要分得到；最後讓一個副本進入「訂單寫進資料庫後才回 503」的故障模式，送 30 個 POST /orders，每張訂單在資料庫裡最多只能有一筆。

練習 3：補完 app/src/lifecycle.ts，讓副本能優雅地被縮減。收到 SIGTERM：readiness 立刻回 503、liveness 維持 200、排空 DRAIN_MS 期間照常服務但回應帶 Connection: close，之後 server.close()，手上的請求做完再呼叫 closeDeps() 關掉 pg 與 Redis，exit 0。另外把 server.keepAliveTimeout 設成環境變數 KEEPALIVE_TIMEOUT_MS，沒設時 65 秒（測試會把它設成 75000，確認你真的讀了環境變數）。測試換上自己的 nginx 設定（ex3.nginx.conf，不受練習 2 影響），每 50ms 送一個要處理 1 秒的 POST /orders，同時 docker stop 第 3 個副本、從容器裡面打它的健康檢查，再擴回 3 個：整段期間最多只能失敗 1 個請求（原因見上面「健康檢查與排空」最後的說明），被停止的容器要在 10 秒內以 ExitCode 0 結束；也會用 GET /config 比較 app 與 nginx 的閒置逾時。

練習 4：cafe-api 在程序的記憶體裡計數，做「每個 IP 每分鐘 100 次」的限流，現在開了 3 個副本，nginx 用 round robin。同一個 IP 實際上每分鐘大約能打幾次？

✓ c。每個副本的記憶體各有一份計數器，round robin 把請求平均分過去，每個副本都看到大約三分之一的請求，各自放行到 100 次。a 把「規則一樣」誤當成「計數共用」；b 剛好說反，分流讓每個副本的計數變少、總量變多；d 副本之間根本不知道彼此存在。要全域限流，計數放在 Redis，或在入口的 nginx 做（第 12 課）。

練習 5：同事把資料庫連線檢查加進 /health/live：「檢查越多越安全。」資料庫做 30 秒的維護時會發生什麼事？

✓ b。liveness 的意思是「這個程序要不要被重啟」，資料庫掛了，重啟 api 一點用都沒有。依賴的狀態放在 readiness：失敗時只是不送流量，程序繼續跑，資料庫一回來就恢復。a 描述的是 readiness；c 副本本身沒壞，換了也一樣；d 說的是 startup probe，liveness 在整個生命週期都會檢查。

練習 6：nginx 設定 proxy_next_upstream error timeout http_502 http_503;。副本 1 收到 POST /orders，訂單已經寫進資料庫，接著回了 503。nginx 會怎麼做？

✓ a。POST、PATCH、LOCK 只要已經送到後端，就不會被傳給下一台，除非加了 non_idempotent；只有連線沒建立起來這種確定沒送出的情況才會換一台。b 忽略了冪等的規則，正是重複下單的來源；c nginx 不知道你的訂單是什麼；d nginx 換的是下一台，不會在同一台重試。要安全地重試 POST，用冪等鍵。

練習 7：壓測量到一個副本在 p95 < 300ms 內能撐 200 RPS，尖峰是 500 RPS，目標使用率 0.8，要留 1 個備用副本。要開幾個副本？

✓ d。a 把副本用到 100%，一點餘裕都沒有；b 四捨五入會讓每個副本超過目標使用率；c 忘了備用副本，掛一個或部署時就超載。算完副本數，還要回頭檢查（副本數 + maxSurge）× 連線池有沒有超過資料庫的 max_connections。

常見錯誤

  • 上傳檔存在副本的本機磁碟：只有一個副本有，容器重建就沒了。放 S3 這類物件儲存。
  • 每個副本各自跑排程：開 3 個副本，日報寄 3 次。拆成只跑 1 份的排程服務，或用 advisory lock 讓只有一個執行者。
  • 以為記憶體限流、記憶體快取是全域的：每個副本各一份。限流放 Redis 或 nginx；快取接受短暫不一致，或改放 Redis。
  • 用黏性 session 遮掩狀態問題：副本一重啟、縮減，session 和購物車就消失，負載也不平均。把狀態搬出去。
  • Redis 裡的 session、購物車沒有 TTL：記憶體只增不減，最後 Redis 被塞滿。每次寫入都重設期限。
  • liveness 檢查外部依賴：依賴一出事，所有副本被連環重啟。依賴放 readiness。
  • proxy_connect_timeout 維持預設 60 秒：副本當掉時，送到它的請求每個都卡 60 秒。內部網路設 1～2 秒。
  • nginx 只在啟動時解析一次 DNS：容器重建、換 IP 後一直 502。用 resolve 加 resolver 與 zone。
  • 加了 non_idempotent：失敗的 POST 被重送，訂單重複。POST 的重試交給客戶端和冪等鍵。
  • 收到 SIGTERM 立刻結束：進行中的請求變 502。先排空，再 server.close()，最後關依賴。
  • 收到 SIGTERM 之後一直不結束：連線池、Redis 沒關，被 SIGKILL（137）。關機的每一步都要在 grace period 內完成。
  • app 的 keepAliveTimeout 比前面代理的閒置逾時短：偶發 502。後面要比前面長。
  • 加副本卻忘了資料庫連線總數：部署時多出 maxSurge 個副本，too many clients already。每次調整都重算連線預算，必要時加 PgBouncer。
  • 副本數照平均流量算：尖峰與一台故障都沒算到。用尖峰、目標使用率與備用副本算，無條件進位。

小結

  • 垂直擴展換大機器、有上限；水平擴展加副本，條件是程序無狀態（12-factor 第 VI 條）。Node 一個程序只用一核，特別依賴水平擴展。
  • 狀態藏在記憶體（session、購物車、限流、快取）、磁碟（上傳檔）、計時器（排程）和長連線裡。session、購物車放 Redis 並設 TTL，永久資料放 PostgreSQL，檔案放 S3，排程只留一個執行者。
  • 黏性 session 只是把狀態問題藏起來。
  • nginx 的 upstream：round robin 或 least_conn；max_fails／fail_timeout 是被動健康檢查；proxy_next_upstream 預設不重送已經送出的 POST，不要加 non_idempotent；resolve 搭配 resolver 與 zone 跟上變動的 IP。
  • liveness 只看程序自己，readiness 才看依賴。收到 SIGTERM：readiness 503、排空並帶 Connection: close、server.close()、關依賴、exit 0，全部在 grace period 內。app 的 keepAliveTimeout 要比前面的代理長。
  • 副本數 ＝ 無條件進位(尖峰 ÷ (單副本能力 × 目標使用率)) ＋ 備用；連線池用 Little's law 估；（副本數 ＋ maxSurge）× 連線池不能超過資料庫可用的連線。
  • Kubernetes 的 Deployment、Service、probe、HPA 自動化的是同一套事情；服務和團隊夠多時才值得它的維運成本。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 8：下午尖峰時結帳 API 回 504，nginx 的 error log 寫 upstream timed out，每次都剛好卡 60 秒。同事想把 proxy_read_timeout 調到 300 秒，你會先做什麼？

✓ 504 是後端在逾時內沒回，後端多半還活著，只是卡在某個地方；先找出慢的原因再修。log 加上 $request_id 和 $upstream_response_time，就能對到後端的同一個請求。a 錯在調大逾時只是讓客人多等 4 分鐘，慢的原因還在，連線也被占得更久。（第 12 課）

練習 9：nginx 直接面對客人，同事想「用客人的真實 IP」限流，寫成下面這樣。哪裡會出事？

limit_req_zone $http_x_forwarded_for zone=api:10m rate=5r/s;
server {
    limit_req_status 429;
    location /api/ {
        limit_req zone=api burst=10 nodelay;
        proxy_pass http://api:3000/;
    }
}

✓ key 決定誰是同一個用戶端，X-Forwarded-For 是客人自己能寫的標頭，換一個值就是一個新的桶子，限流形同虛設。key 改用 $binary_remote_addr，也就是 nginx 自己看到的連線位址。a 錯在 nginx 只是把真實位址接在客人送來的值後面，前面那段完全由客人決定。（第 12 課）

練習 10：cafe-api 從 1 個副本開成 3 個之後，客人反映「重新整理就被登出」「購物車一下有一下沒有」。怎麼修最好？

✓ 把狀態搬出程序，副本才能隨時加、隨時刪（12-factor 第 VI 條）；Redis 每次寫入都重設 TTL，不然記憶體只增不減。b 是黏性 session，只是把狀態問題藏起來：副本一重啟或被縮減，那群客人的 session 和購物車就消失，負載也不平均。（第 13 課）

練習 11：cafe-api 的 SIGTERM 處理寫成這樣，部署時哪裡會出事？

process.on('SIGTERM', async () => {
  draining = true          // readiness 改回 503
  await sleep(DRAIN_MS)    // 排空，回應帶 Connection: close
  await closeDeps()        // 關 pg 與 Redis
  server.close(() => process.exit(0))
})

✓ 順序是先 server.close()，等進行中的請求全部做完（callback）才關 pg 與 Redis、exit 0，全部在 grace period 內。a 錯在 liveness 失敗代表「要重啟這個程序」，排空期間 liveness 要維持 200，只有 readiness 回 503。（第 13 課）

練習 12：每次部署都有幾個 POST /orders 回 502。同事提議在 proxy_next_upstream 加上 non_idempotent，讓失敗的 POST 自動換一台送。可以嗎？

✓ nginx 不知道後端做到哪裡，已經送出的 POST 重送可能重複下單，所以預設不重送。部署的 502 要從關機順序修（先排空再 server.close()），POST 的重試交給客戶端帶冪等鍵。c 錯在交易只保證一筆訂單完整寫入，兩個請求就是兩筆各自成功的交易。（第 13 課）

練習 13：cafe-api 平常 4 個副本，max_connections 100、保留 10 條給管理與 migration。活動前把每個連線池從 8 調成 20，平常都正常，一部署（maxSurge 1）新副本就報 too many clients already。原因是什麼？

✓ max_connections 是所有副本共用的，部署時新副本先起來、舊的才停，要用（副本數 ＋ maxSurge）× 連線池算。修法是用 Little's law 把連線池算回需要的大小，不夠再加 PgBouncer。a 錯在每個副本最多只開連線池那麼多條，慢查詢會讓請求排隊等連線而逾時，不會讓總數超過上限。（第 13 課）
