階段 6：可觀測性與可靠性 · 第 21 課

集中 log 與錯誤追蹤

晚上九點，客人回報結帳一直失敗。咖啡店的 API 跑了 3 個副本，加上 kitchen 服務，分散在兩台機器上。你 SSH 進第一台、docker logs 往回翻，找到幾行 502，可是看不出是哪一張訂單、kitchen 那邊發生了什麼；切到第二台，log 檔已經把磁碟塞滿，連 docker logs 都慢得動不了。等你拼湊出原因，已經過了一個小時。

這一課把 log 當成正式環境的基礎設施來處理，讓下一次同樣的事故幾分鐘內就查得到原因。

這課的路線：
  1. 容器的 log 去哪了：程式印出來的每一行經過哪些地方，為什麼機器一多就要集中收集。
  2. 輪替、保留與成本：log 怎麼不把磁碟塞滿，要留多久、會花多少錢。
  3. 寫出好查的 log 與查詢：欄位怎麼命名才查得到，怎麼回答「哪個路由在出錯、這個請求經過了哪些服務」。
  4. log 平台與錯誤追蹤：在本機把整條路走一遍，三千行 error 是同一個 bug 還是三個，交給錯誤追蹤工具歸類。
  5. log 也是資料：哪些東西不能寫進 log，誰能查、留多久。
這課會用到：
  • 第 3 課的 stdout 與 stderr：程式的兩條輸出管道，一般訊息走 stdout，錯誤走 stderr。
  • Node 課第 19 課的結構化 log：每一行是一個 JSON 物件，帶著 request_id，同一個請求的 log 才串得起來。
  • 第 2 課的 jq 與管線：jq 從 JSON 裡挑欄位、過濾，管線把前一個指令的輸出交給下一個。

容器的 log 去哪了

程式在容器裡印到 stdout、stderr 的每一行，都會被 Docker 接走。決定這些輸出去哪裡的機制叫 logging driver：預設的 json-file 把每一行包成一個 JSON 存在主機的檔案裡，docker logs 讀的就是這個檔案。

一台機器時這樣就夠了。機器一多，就需要集中式 log（centralized logging）：把所有服務、所有機器的 log 收到同一個地方，用同一個介面查。中間負責讀取、轉送的程式叫收集器（agent／collector），常見的有 Fluent Bit、Vector、Grafana Alloy、OpenTelemetry Collector。它們在每台機器上讀 Docker 存下的檔案（或直接接 logging driver 的輸出），加上「這是哪個服務、哪個環境」的標記，送到儲存的地方；儲存端建立索引，最後由查詢介面（例如 Grafana）讓你搜尋。

十二要素應用程式（The Twelve-Factor App）第 XI 條把這件事講成一句話：把 log 當成事件流。程式不管 log 要存去哪、要不要輪替，只往 stdout 寫；路由、保存、分析都是執行環境的事。

所以不要在容器裡把 log 寫進 /app/logs/app.log：容器重建，檔案就跟著消失；收集器只看得到 stdout，看不到容器裡的檔案；沒有人輪替，它會一直長到塞滿容器的可寫層。Kubernetes 上也一樣寫 stdout，kubectl logs 只讀得到目前這個容器的 log，加 --previous 可以看重啟前的上一個，再更早的就要靠集中式 log。

輪替、保留與成本

第 10 課已經在 compose 裡設過輪替，這裡把規則說完整（Docker 官方文件）：

drivermax-sizemax-file壓縮
json-file（預設）預設 -1，無上限：不輪替預設 1，只有設了 max-size 才有作用預設關閉
local（官方建議）預設 20m預設 5預設開啟

max-size 要寫正整數加單位 k、m、g。整台機器的預設值寫在 /etc/docker/daemon.json，選項的值一律是字串：

{
  "log-driver": "local",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

改完要重啟 Docker，而且只影響之後新建的容器；已經在跑的容器要重建才會套用。所以 compose 裡每個服務明確寫 logging 比較保險，換到哪台機器都一樣。

輪替處理的是單台機器的磁碟。集中之後，問題變成保留期限（retention）：log 要保存多久。費用大致是「每天的 log 量 × 保存天數」，例如 AWS CloudWatch Logs 的 log group 預設是「永不過期」，沒人設定的話帳單會一直長。常見的做法：

  • 可以即時搜尋的熱資料留 7～30 天，出事時通常只查最近幾天。
  • 稽核、法規需要的部分另外轉存到 S3 這類便宜的儲存，查詢慢但便宜。
  • debug 等級的 log 在正式環境預設關掉，需要時用環境變數 LOG_LEVEL 暫時打開；量很大的成功請求 log 可以取樣，例如只留 10%，錯誤一律全留。

寫出好查的 log

Node 課第 19 課教過結構化 log：每一行是一個 JSON 物件。集中之後，同一個欄位在每個服務都要叫一樣的名字、用一樣的格式，查詢才寫得出來。cafe-api 的請求 log 長這樣：

{"level":30,"ts":"2026-11-01T02:00:04.364Z","service":"cafe-api","version":"1.6.0","env":"production",
 "request_id":"req-0c84117bc09e","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","method":"GET",
 "route":"/orders/:id","path":"/orders/1155","status":200,"duration_ms":38.5,"msg":"request"}
欄位用途
ts時間，ISO 8601，最好統一用 UTC（Z）。各台機器時區設定不同時，同一刻會出現 Z 和 +08:00 兩種寫法，排序前要先轉成時間
levellog 等級，見下表
service、version、env哪個服務、哪一版、哪個環境：新版上線後錯誤變多，靠 version 才看得出來
request_id關聯 ID（correlation／request id）：同一個請求在每個服務的每一行都帶同一個編號，串起整個經過。api 呼叫 kitchen 時用標頭傳過去
trace_id分散式追蹤的編號（第 23 課），從 log 跳到 trace 用
route路由樣板 /orders/:id，統計用這個；path 是原始網址 /orders/1155，每張訂單都不一樣，拿來分組會變成幾萬組
status、duration_ms結果與耗時，算錯誤率和慢請求用
等級什麼時候用正式環境
debug開發時追細節：SQL、外部 API 的回應預設關閉
info正常的事件：請求完成、服務啟動、排程跑完開
warn不正常但自己處理掉了：重試成功、用了備用值開
error這個請求或工作失敗了，需要有人看開，接到錯誤追蹤
fatal程序無法繼續，即將結束開，通常同時告警

兩個常見的破壞者。第一個是 console.log(err)：它印出的是多行的 stack trace，收集器以「行」為單位，一個錯誤被拆成五六筆不相干的 log，而且沒有 request_id。錯誤要交給 logger，用 err 欄位記成一行 JSON。第二個是機密與個資：log.error({ req, body }) 一行就把 Authorization 標頭、密碼、卡號送進一個很多人能看、保存好幾個月的地方。

pino 的解法是遮蔽（redaction）：在 JSON 寫出去之前，把指定路徑的值換掉。以下行為是用專案安裝的 pino 10.4.0 實際跑出來的：

const log = pino({
  redact: {
    paths: ['req.headers.authorization', 'body.payment.card.number', '*.password'],
    censor: '[REDACTED]',          // 不寫的話預設是 '[Redacted]'
  },
})
log.error({ req: { headers: { authorization: 'Bearer abc', 'user-agent': 'curl/8.7.1' } },
  body: { password: 'hunter2', payment: { card: { number: '4111111111111111' } }, account: { password: 'x' } } })
// "req":{"headers":{"authorization":"[REDACTED]","user-agent":"curl/8.7.1"}}
// "body":{"password":"[REDACTED]","payment":{"card":{"number":"[REDACTED]"}},"account":{"password":"x"}}

注意最後一個：*.password 的 * 只代表一層，所以 body.password 被遮了，body.account.password 沒有。路徑區分大小寫，Node 收到的標頭名稱一律是小寫，寫 req.headers.Authorization 什麼都遮不到。censor 也可以是函式 (value, path) => 新的值，path 是路徑陣列，例如 ['body', 'email']，可以只留部分資訊。

遮蔽要在程式寫出之前做。「讓收集器把敏感欄位刪掉」太晚了：原始內容已經寫進主機上的 log 檔，docker logs 看得到，備份裡也有。收集器的過濾只能當第二道防線。
💡 實務上：log 欄位是全團隊的約定
api 寫 request_id、kitchen 寫 requestId、另一個服務寫 reqId，查一個請求就要記三種名字，儀表板和告警也得各寫一份。資深工程師會在服務還少的時候就訂一份欄位清單：時間格式、每個 level 的意思（例如 error 代表需要有人處理）、request_id 和使用者識別欄位怎麼寫。新服務照著寫，code review 時順便檢查。

查詢：從一行到一整個請求

手上只有 log 檔時，第 2 課的 jq 可以回答很多問題。真實的 log 檔常混著幾行不是 JSON 的內容（例如 console.log 印的 stack trace），jq 讀到就報 parse error 停下來。所以下面先用 -R 把每一行當成字串讀進來，再用 fromjson? 解析，? 讓解析失敗的行直接跳過：

# 各路由的 5xx 次數（用 route，不是 path）
jq -rR 'fromjson? | select(.msg == "request" and .status >= 500) | "\(.method) \(.route)"' app.log | sort | uniq -c | sort -rn

# 最慢的 5 個 api 請求
jq -cR 'fromjson? | select(.msg == "request" and .service == "api") | {request_id, duration_ms}' app.log | jq -s 'sort_by(-.duration_ms) | .[:5]'

# 某個請求在所有服務的每一行
grep '"req-0c84117bc09e"' app.log | jq -c '{ts, service, msg}'

最後一個印出來的順序是檔案裡的順序，不是發生的順序：收集器分批送，兩個服務的 log 會交錯。直接 sort_by(.ts) 也不對，"…T02:00:04.371Z" 和 "…T10:00:04.369+08:00" 照字母排，比到小時的 02 和 10 就分出先後，Z 那筆排前面；換算成 UTC，+08:00 那筆是 02:00:04.369，其實比較早。log 有不只一種時區寫法時，要先轉成時間再排，這是練習 2 要用程式處理的原因之一。另一個原因是百分位數：p95 是「95% 的請求都比它快」的耗時，平均值會被大量的快請求拉低，看不到最慢那群客人的感受（第 22 課會再深入）。最簡單的定義是最近排名法（nearest-rank）：由小到大排序，取第 ⌈0.95 × n⌉ 個。

集中到 Loki（Grafana 的 log 儲存與查詢服務）之後，用的是 LogQL。Loki 跟全文搜尋引擎不同，它只替 label 建索引，內容本身只壓縮存放，查詢時再掃描。label 是收集器加在每一串 log 上的少數幾個鍵值，例如 service、env、level。每一種 label 組合是一條串流（stream），所以 label 的基數（cardinality，一個欄位有多少種不同的值）一定要低。Loki 官方文件的例子：有人把 requestId 當 label，結果出現兩萬多條串流，索引暴增、查詢反而變慢。request_id、user_id、order_id、trace_id 都只能放在 log 內容裡，查詢時再過濾：

# 選串流（用 label）→ 解析 JSON → 用欄位過濾
{service="cafe-api", env="production"} | json | status >= 500

# 先用字串過濾縮小範圍再解析，比較快
{service=~"cafe-api|kitchen"} |= "req-0c84117bc09e"

# 過去 5 分鐘各路由的 5xx 次數（route 是 json 解析出來的欄位，不是 label）
sum by (route) (count_over_time({service="cafe-api"} | json | status >= 500 [5m]))
💡 實務上：讓客服回報的 bug 帶著 request_id
「我剛剛點餐失敗」這種回報很難查：哪位客人、幾點、哪一筆？常見的做法是把 request_id 放進回應標頭（例如 X-Request-Id），前端在錯誤畫面顯示一段「錯誤代碼」，請客人截圖或複製給客服。客服把代碼轉給工程師，查詢就從大海撈針變成精準的一整個請求。這需要後端、前端、客服一起約定，前端出身的你很適合推動。

一套能跑的 log 平台

想在自己的電腦上把整條路走一遍，Grafana 官方的 grafana/otel-lgtm 映像（0.39.0）把 OpenTelemetry Collector、Prometheus、Tempo、Loki、Pyroscope 和 Grafana 裝在同一個容器裡，Grafana 在 3000 port，OTLP 收資料在 4317、4318。官方註明它只供開發、示範與測試，不要拿去當正式環境的平台：

docker run --rm --name ld-21-lgtm -p 127.0.0.1:13000:3000 -p 127.0.0.1:4318:4318 grafana/otel-lgtm:0.39.0
# 瀏覽器打開 http://localhost:13000，在 Explore 選 Loki 資料來源查詢

正式環境的收集器要選還在維護的：舊教學常用的 Promtail 已在 2026-03-02 終止支援（EOL），Grafana 的新功能都做在 Grafana Alloy，官方提供把 Promtail 設定轉成 Alloy 設定的工具；不綁定廠商的話用 OpenTelemetry Collector。不想自己維運，就用託管服務，例如 CloudWatch Logs（Docker 有 awslogs logging driver）或 Grafana Cloud。選哪一套都一樣：app 寫 JSON 到 stdout，平台負責其餘的事。

錯誤追蹤

結帳出錯的那一晚，在 log 裡搜尋 level:error 會得到三千行。它們是同一個 bug，還是三個不同的 bug？這個錯誤是今天才出現的，還是上個月就有？是 1.6.0 版才開始的嗎？log 只能一行一行看，回答不了這些問題。

錯誤追蹤（error tracking）工具（例如 Sentry，有 SaaS 也可以自架）專門處理例外：SDK 在程式裡攔下例外，連同 stack trace、版本、環境、request_id、使用者的瀏覽器等情境送出；服務端把同一個 bug 的事件分組成一個 issue，顯示次數、影響多少使用者、第一次與最後一次出現、出現在哪些版本。

在 log 裡搜尋 error錯誤追蹤
同一個 bug 發生 3000 次3000 行1 個 issue，次數 3000
新問題要有人剛好在看第一次出現就通知
修好後又壞看不出來標成回歸（regression），標明哪一版
前端壓縮過的程式index-3f9a.js:1:48213用 source map 還原成原始檔與行號

分組的依據叫指紋（fingerprint）。Sentry 的文件說它的順序是：先看有沒有自訂指紋，再看 stack trace（只用應用程式自己的 frame：模組、正規化後的檔名、那一行的程式碼），沒有 stack trace 時才用例外的類型與訊息，最後才用 log 訊息。為什麼不直接用錯誤訊息？訂單 1155 找不到 和 訂單 1156 找不到 是同一個 bug，用訊息分組就變成每張訂單一個 issue。為什麼不用行號？每次部署行號都會動，同一個 bug 會在每個版本分裂成新 issue。為什麼只看自己的 frame？同一個錯誤可能經過 node_modules 裡不同版本的套件路徑，那些不是你要修的地方。練習 4 會實作一個簡化版。

兩件部署時要做的事。第一，每個事件帶版本（release），通常是 git SHA 或映像 tag（第 16 課），才看得出回歸發生在哪一版。第二，前端特別需要 source map：把壓縮、打包後的程式位置對應回原始碼的對照檔。Vite 建置時產生 source map，CI 上傳到錯誤追蹤服務，但不要跟網站一起公開部署，否則等於把原始碼送給所有人。錯誤事件同樣要清掉個資：SDK 預設會帶的請求標頭、cookie、表單內容，要在送出前過濾。

log 也是資料

log 平台常常是公司裡權限最寬鬆、保存最久的資料庫：工程師都能查、保存好幾個月、還會被複製到備份和第三方服務。所以：

  • 能不記就不記：記 customer_id，不記姓名、電話、地址；需要時只留部分，例如 email 只留第一個字和網域。
  • 存取要有權限控管和稽核，跟資料庫一樣。
  • 保留期限要有明確理由，過期就刪。留越久，外洩時的影響越大。
  • 發現機密進了 log，當成外洩處理：換掉那個 token 或密碼、修程式、確認 log 保存在哪裡、有誰看過（Node 課第 19 課）。

練習

練習 1～3 在 devops/practice 做。練習 1 需要 Docker 在跑：測試每次都會先收掉 ld-21、重新啟動，跑完也會收掉。練習 2、3 在本機用 Node 跑，不需要 Docker。

練習 1：compose.yaml 裡有 api、kitchen、db 三個服務，都還沒設定 log 輪替。替三個服務都加上 logging：用 local driver，或 json-file 加上 max-size（例如 10m）與 max-file（例如 "3"）。三個服務設定一樣，用 x-logging: &logging 錨點寫一次再 logging: *logging 引用。測試用 docker compose config 檢查每個服務的設定與單位，up --wait 之後用 docker inspect 確認容器實際用的設定，再呼叫 POST /debug/log-spam?mb=50 讓 api 印出 50MB 的 log：api 要照常回應、docker logs --tail 讀得到最後一行，留下來的 log 不能超過 max-size × max-file。

練習 2：logs/app.log 是 api 與 kitchen 混在一起的 NDJSON log（一行一個 JSON），裡面也有幾行被 console.log 拆開的 stack trace。在 analyze.ts 實作 analyze(text, requestId)，回傳：routes：只算 msg 是 request 的行，鍵是「方法 路由樣板」（例如 GET /orders/:id），每個路由的 requests、errors（status ≥ 500）、error_rate（errors ÷ requests）、p95_ms（最近排名法）；slowest：api 服務 duration_ms 最大的 3 個 request_id，由慢到快（一樣慢時 request_id 字母順序小的在前）；timeline：指定 request_id 在所有服務的每一行 { ts, service, msg }，依實際時間排序。不是 JSON 的行跳過。執行 node analyze.ts logs/app.log <request_id> 會寫出 report.json，request_id 可以用 grep 'kitchen unavailable' logs/app.log | head -1 | jq -r .request_id 找一個。測試會先跑附的 log，再用 loggen.ts 以新的 seed 產生 10 萬個請求的 log 比對每一個數字。

練習 3：shop/server.ts 的 POST /checkout 一定會失敗，錯誤 log 把請求標頭和 body 整個記下來（這個檔案不用改）。在 shop/logger.ts 設定 pino 的 redact：req.headers 的 authorization、cookie，body 的 password 和 payment.card.number 都變成 [REDACTED]；body.email 只留第一個字和網域，例如 ming@cafe.test 變成 m***@cafe.test。其他欄位照常記：request_id、route、user-agent、商品、卡片到期日都要在。測試會用隨機的 token、密碼、卡號、email 啟動 node server.ts 並觸發錯誤，掃描程序的完整輸出，任何一個原始值都不能出現。自己試的指令寫在 server.ts 開頭。

練習 4：實作錯誤追蹤的分組。fingerprint(e) 依這個規則算出指紋字串：錯誤類型，加上 stack trace 裡前 3 個「應用程式自己的」frame。應用程式自己的 frame 是檔案在 /app/ 底下、而且不在 node_modules 裡的那些；每個 frame 只取函式名稱和檔案路徑，不要行號和欄號（at placeOrder (/app/dist/orders.js:58:9) 取 placeOrder 和 /app/dist/orders.js；沒有函式名稱的 at /app/dist/x.js:1:2 函式名稱當成 <anonymous>）。一個應用程式的 frame 都沒有時，改用類型加上訊息，訊息裡的數字一律換成 <n>。注意 stack 的第一行是 類型: 訊息，訊息裡有訂單編號。測試會檢查：同一個 bug 在不同版本（行號變了）、不同訂單編號、經過不同的 node_modules 路徑時指紋相同；不同的 bug 指紋不同。

練習 5：同事想在 Loki 用 user_id 快速找出某位客人的 log，提議收集器把 user_id 加成 label：「label 越多，查得越快。」這樣做會怎樣？

✓ c。Loki 只替 label 建索引，每一種 label 組合是一條串流；user_id 有幾萬種值，就是幾萬條串流。官方建議 label 只用值的種類有限的欄位（service、env、level），request_id、user_id 留在內容裡，用 |= "…" 或 | json | user_id = "…" 過濾。a 低估了代價；b Loki 不會幫你改；d label 的值本來就是字串，問題不在型別。

練習 6：cafe-api 在容器裡用 pino 把 log 寫到 /app/logs/app.log，stdout 什麼都不印。同事說：「寫檔案比 stdout 可靠，不會掉。」哪個說法正確？

✓ b。stdout 的輸出由 logging driver 寫到主機上，容器重啟後還在，收集器也一直在讀、送到集中的地方，所以容器重建（舊容器被刪掉、主機上的 log 檔跟著刪掉）之後，在集中式 log 裡還查得到。寫在容器裡的檔案，三個問題都有。a 搞錯了 stdout 的去向；c 掛 volume 只解決了重建會消失，輪替和收集還是要自己處理，每個服務都要另外設定；d Docker 只接 stdout 和 stderr。

練習 7：團隊已經有集中式 log，可以搜尋 level:error。主管問：「還需要 Sentry 這類錯誤追蹤工具嗎？」最好的回答是？

✓ d。log 回答的是「這個請求發生了什麼」，錯誤追蹤回答的是「現在有哪些 bug、哪個最嚴重、是不是新的」。a 資料可能一樣，但分組、去重、版本回歸和告警，log 搜尋做不到；b 結構化 log 可以存 stack trace；c 兩者互補，錯誤追蹤只看例外，看不到正常請求和請求的完整經過。

練習 8：結帳偶爾失敗，同事把正式環境的 LOG_LEVEL 改成 debug 並且一直開著：「多記一點總是比較好，出事時才有東西查。」這樣做的問題是？

✓ a。log 不是免費的：量乘以保留天數就是帳單，雜訊越多越難找到真正的錯誤，而且 debug log 最容易把整包資料印出來。用環境變數暫時調整等級、查完改回來，或只保留一部分 debug log。b、d 平台不會替你分辨等級，收到什麼就存什麼；c 效能只是其中一個代價。

常見錯誤

  • 以為 log 預設會輪替：json-file 的 max-size 預設無上限。每個服務都設 local，或 json-file 加 max-size；改 daemon.json 的話記得既有容器要重建。
  • max-size: "10"：沒有單位是 10 bytes。寫 10m。
  • 把 log 寫到容器裡的檔案：重建就消失、收集器看不到、沒有輪替。寫到 stdout。
  • 用 console.log 印錯誤物件：多行的 stack trace 被拆成好幾筆，也沒有 request_id。交給 logger，記成一行 JSON。
  • log 裡有 token、密碼、卡號、個資：在 logger 設定遮蔽，路徑寫到欄位真正的位置；* 只代表一層，標頭名稱是小寫。只靠收集器過濾就太晚了。
  • 用原始網址分組統計：/orders/1155、/orders/1156 各算一組。用路由樣板 route。
  • 只有 log，沒有 request_id：多個服務、多個副本的 log 交錯在一起，串不起一個請求。每一行都帶 request_id，呼叫下游時傳過去。
  • 用平均值看耗時：平均值會被大量的快請求拉低。看 p95、p99。
  • 把時間字串直接排序：Z 和 +08:00 混在一起時順序錯誤。先轉成時間，或統一寫 UTC。
  • 把 user_id、request_id 當 Loki 的 label：串流數暴增。label 只用 service、env、level 這類值有限的欄位。
  • 以為 log 是免費的：量 × 保留期限就是帳單。設定保留期限、關掉正式環境的 debug、對大量的成功請求取樣。
  • 新專案還採用 Promtail：它已在 2026-03-02 終止支援。用 Grafana Alloy 或 OpenTelemetry Collector。
  • 錯誤追蹤用訊息或行號分組：每張訂單、每次部署都變成新的 issue。依錯誤類型加上應用程式自己的 frame 分組。

小結

  • app 只把一行一個 JSON 寫到 stdout；logging driver 存檔並輪替，收集器（Alloy、Fluent Bit、Vector、OpenTelemetry Collector）送到儲存與索引，再用 Grafana 這類介面查詢。
  • json-file 預設不輪替，官方建議 local（20m × 5、壓縮）。集中之後的成本是量 × 保留期限：熱資料留短、封存放便宜的地方、debug 預設關閉、成功請求可以取樣。
  • 好查的 log：一致的欄位（ts、level、service、version、env、request_id、trace_id、route、status、duration_ms）、路由樣板、錯誤記成一行；寫出之前先用 pino 的 redact 遮蔽機密與個資。
  • 查詢：用 jq 或程式算錯誤率、p95、單一請求的完整時間線；Loki 只替 label 建索引，label 要低基數，request_id、user_id 放在內容裡用 LogQL 過濾。
  • 錯誤追蹤把例外依指紋分組成 issue，記錄次數、版本、首次與最後出現，對新問題與回歸告警；分組只看錯誤類型與應用程式自己的 frame，前端要上傳 source map。
  • log 也是資料：少記個資、控管存取、設定保留期限，機密進了 log 就當外洩處理。

log 回答「發生了什麼」，但要知道「服務現在好不好」，需要的是數字：下一課用指標與 SLO 描述服務的健康程度。
