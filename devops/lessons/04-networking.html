階段 1：伺服器基本功 · 第 4 課

網路基礎：IP、port、DNS、TCP

咖啡店 API 裝進容器之後，docker logs 印出 listening on 127.0.0.1:3000，你也寫了 -p 127.0.0.1:18040:3000，可是 curl 只回一句 Empty reply from server。另一天，你把網域換到新機器，一半的客人連到新的、一半還連到舊的。再一天，同事說「API 連不上」，你不知道該先查 DNS、防火牆還是程式本身。

這三件事的原因都在網路的基本觀念裡。學完這一課，你能修好容器綁錯位址的問題、自己寫一份 DNS zone 檔，並且照著固定順序排查「連不上」。

這課的路線：
  1. 位址、port 與私有網路：一個請求靠 IP 和 port 找到程式，家裡、雲端的私有位址怎麼上網，防火牆規則裡的 /24 怎麼讀（開場問題的最小答案）。
  2. 監聽位址：程式聽 127.0.0.1 和 0.0.0.0 差在哪，修好容器回 Empty reply from server 的問題。
  3. DNS：名稱怎麼查成 IP，為什麼換機器時一半客人還連到舊的；自己寫一份 zone 檔。
  4. TCP 與 UDP：連線怎麼建立，connection refused 和 timeout 各代表什麼。
  5. 逐層排查：同事說「API 連不上」時，照 DNS → TCP → TLS → HTTP 的順序查。
這課會用到：
  • Node 課第 12 課的 HTTP 與 curl：HTTP 請求跑在 TCP 連線上，curl -v 會印出連線和請求的過程。
  • Node 課第 13 課的 server.listen(port, host)：第一個參數是 port，第二個決定聽哪個位址。
  • 第 1 課的 -p 127.0.0.1:18010:80：把容器的 port 發布到主機上，格式是「主機 IP:主機 port:容器 port」。
  • 第 3 課的 lsof／ss -ltnp：查出哪個程序在聽哪個 port。

位址與 port：大樓地址和門牌

IP 位址（IP address）是網路上一台機器（更精確地說，一張網卡）的地址。IPv4 是 4 個 0～255 的數字，例如 203.0.113.10，總共約 43 億個，早就不夠用；IPv6 是 8 組 16 進位，例如 2001:db8::1（:: 代表中間連續的 0 省略掉）。

一台機器上同時跑好幾個服務，要靠 port（連接埠）區分：一個 0～65535 的號碼。網路上傳的資料會切成一小段一小段，每段叫封包（packet），上面寫著來源和目的地址。IP 像大樓地址，port 像門牌：封包先送到大樓，再看門牌交給哪個程式。一條連線由「來源 IP、來源 port、目的 IP、目的 port」四個值決定，所以同一個瀏覽器可以對同一台伺服器開很多條連線，每條的來源 port 都不同。

常見的預設 port：22 是 SSH、53 是 DNS、80 是 HTTP、443 是 HTTPS、5432 是 PostgreSQL、6379 是 Redis。在 Linux 上，1024 以下的 port 一般使用者不能聽，要 root 或特別的權限，所以 app 通常聽 3000、8080 這類號碼，再由 nginx 在 80／443 接客（第 12 課）。

開場三件事的最小答案都跟「IP 和 port」有關：程式聽在容器自己的 127.0.0.1，從容器外面進來的連線就找不到它（細節在後面的〈監聽位址〉）；DNS 查到的 IP 會被快取一段時間，換機器期間有人拿到新的、有人還拿著舊的（〈DNS〉）；連不上時，就從「名稱查得到 IP 嗎、port 連得上嗎」開始一層層往上查（〈逐層排查〉）。

私有網路、NAT 與 CIDR

回到第 1 節說的「IPv4 只有約 43 億個，早就不夠用」：網際網路因此保留了三段私有位址（private address），只在內部網路有效，網際網路上的路由器不會轉送它們。每個家庭、公司、雲端 VPC 都可以重複使用：

範圍CIDR 寫法常見在哪
10.0.0.0～10.255.255.25510.0.0.0/8雲端的私有網路（VPC）、公司內網
172.16.0.0～172.31.255.255172.16.0.0/12Docker 的網路（例如 172.17.0.0/16）
192.168.0.0～192.168.255.255192.168.0.0/16家裡和咖啡店的 Wi-Fi
127.0.0.0～127.255.255.255127.0.0.0/8loopback：只代表「這台機器自己」

你的 Mac 在家拿到 192.168.1.23 這種位址，可是網站看到的是另一個公開 IP。中間做轉換的是路由器的 NAT（Network Address Translation，網路位址轉譯）：封包出去時把來源改成路由器的公開 IP，回來時再查表改回你的私有 IP。所以家裡十台裝置共用一個公開 IP；也所以外面的人沒辦法主動連到你家的 Mac，除非路由器特別設定轉送。

CIDR 是描述「一段位址」的寫法：10.0.1.0/24 的意思是前 24 個位元固定（10.0.1），後面 32 − 24 = 8 個位元可以變，所以共有 28 = 256 個位址，從 10.0.1.0 到 10.0.1.255。斜線後面的數字越大，範圍越小：

寫法可變的位元位址數例子
/161665,53610.0.0.0/16：整個 VPC
/24825610.0.1.0/24：一個子網路
/3201198.51.100.7/32：只允許你家這一個 IP
/032全部0.0.0.0/0：任何地方

防火牆（firewall）依規則決定封包要放行還是丟掉；雲端的安全群組（security group）是雲端業者替每台機器提供的防火牆（第 18 課）。兩者都用 CIDR 寫「誰可以連」。把 SSH 開給 0.0.0.0/0 就是開給全世界；開給 你的IP/32 才是只有你。第 18 課設計 VPC 時，會把 /16 切成好幾個 /24 子網路（AWS 每個子網路會保留 5 個位址不能用）。

監聽位址：127.0.0.1、0.0.0.0、::

程式開始聽一個 port 時，除了 port 還要選監聽位址（bind address）：要接受從哪張網卡進來的連線。

監聽位址收得到誰的連線
127.0.0.1（IPv4 loopback）只有同一台機器（同一個容器）裡的程式
::1（IPv6 loopback）同上，但只走 IPv6
0.0.0.0所有 IPv4 網卡：loopback、區網、對外的都收
::所有 IPv6 網卡；多數系統同時也收 IPv4（雙堆疊，dual-stack：一個監聽同時收 IPv4 和 IPv6）

loopback（回送介面）是一張虛擬網卡，封包不出機器就繞回來。關鍵在「機器」的範圍：每個容器有自己的網路空間，也有自己的 127.0.0.1。容器裡的 127.0.0.1 是容器自己，不是你的 Mac。

在這台 Mac 上實際看到的是：

$ docker logs ld-04-api
listening on 127.0.0.1:3000
$ curl http://localhost:18040/health/live
curl: (52) Empty reply from server

Docker Desktop 在 Mac 這端先接下連線，轉進容器時發現 eth0 的 3000 沒人聽，只好把連線關掉，curl 就收到空的回應。修法是讓容器裡的程式聽 0.0.0.0。這不會把服務暴露出去：容器的網卡只在 Docker 的內部網路裡，誰連得到由 -p 127.0.0.1:18040:3000 的主機端決定。

兩個位置別搞混：容器裡的程式要聽 0.0.0.0（收得到 Docker 轉進來的連線）；主機端的 -p 維持 127.0.0.1（只有你的 Mac 連得到）。把 -p 改成 0.0.0.0:18040 修不好問題，反而讓同一個 Wi-Fi 的人都連得到；用 --network host 繞過去則是放棄了容器的網路隔離。

Node 的 server.listen(port) 沒給 host 時，Node 24 文件寫的是：IPv6 可用就聽 ::，否則聽 0.0.0.0；多數作業系統聽 :: 時也會收 IPv4。另一個陷阱是 localhost：Mac 的 /etc/hosts 同時寫了 127.0.0.1 localhost 和 ::1 localhost，curl -v 可以看到它先試 IPv6：

* IPv6: ::1
* IPv4: 127.0.0.1
*   Trying [::1]:18040...
* connect to ::1 port 18040 from ::1 port 55941 failed: Connection refused
*   Trying 127.0.0.1:18040...
* Connected to localhost (127.0.0.1) port 18040

curl 會自動換下一個位址，但不是每個客戶端都這樣。程式只聽 127.0.0.1、客戶端只試 ::1，就會出現「我這邊好好的、他那邊連不上」。要確定一台機器上誰聽在哪個位址，用第 3 課的 lsof -nP -iTCP:3000 -sTCP:LISTEN（Linux 上是 ss -ltnp），看 NAME 欄是 127.0.0.1:3000、*:3000 還是 [::1]:3000。

💡 實務上：新機器上線前，說得出每個在聽的 port
網路上隨時有程式在掃描公開的 IP，資料庫、Redis 這類聽在 0.0.0.0 又沒設好密碼的服務，很快就會被找到。資深工程師的上線檢查清單裡會有一項：在機器上跑 ss -ltnp，每一行都要說得出是哪個程式、為什麼聽在這個位址。對外只該開 80、443，SSH 限定來源（第 6 課）；其他服務只聽 127.0.0.1 或私有網路，再用安全群組（雲端主機外面的一層防火牆）多擋一層（第 18 課）。

DNS：把名稱查成 IP

連線要 IP，人記的是名稱。DNS（Domain Name System）是把名稱查成 IP 的分散式系統：沒有一台伺服器知道全部答案，而是一層一層往下問。替你跑這趟流程的叫解析器（resolver），通常是網路業者（ISP）、公司或 1.1.1.1、8.8.8.8 這類公共服務；最後給出答案的叫權威伺服器（authoritative server），是網域擁有者指定的那幾台。

權威伺服器上的資料是一筆筆 DNS 紀錄：

類型意思例子
A名稱 → IPv4api.cafe.test. 300 IN A 10.0.1.10
AAAA名稱 → IPv6api.cafe.test. IN AAAA 2001:db8::10
CNAME別名：這個名稱的答案去查另一個名稱www.cafe.test. IN CNAME api.cafe.test.
MX這個網域的郵件伺服器cafe.test. IN MX 10 mail.cafe.test.
TXT任意文字，常用來驗證網域所有權、寫寄信政策（SPF）cafe.test. IN TXT "v=spf1 -all"
NS這個網域由哪幾台權威伺服器負責cafe.test. IN NS ns1.cafe.test.

每筆紀錄都有 TTL（time to live）：答案可以被快取多少秒。解析器拿到 TTL 3600 的答案，接下來一小時都直接回快取，不會再問權威伺服器。所以你改了 A 紀錄，已經快取舊答案的人最多要等一個 TTL 才會看到新 IP。正式換 IP 的做法是：前一兩天先把 TTL 降到 60～300 秒，等舊的長 TTL 過期後再換，穩定之後再調回來。

用 dig 查詢（這台 Mac 內建的是 dig 9.10.6）：

dig +short api.cafe.example.com          # 只看答案
dig api.cafe.example.com A               # 完整回應，ANSWER SECTION 第二欄是剩下的 TTL
dig @1.1.1.1 api.cafe.example.com        # 指定問哪台解析器，比對不同地方看到的答案
dig @127.0.0.1 -p 18045 www.cafe.test    # 直接問練習 2 的 CoreDNS
dig +trace api.cafe.example.com          # 自己從根開始一路問，看每一層的回答

查之前作業系統會先看 /etc/hosts，寫在那裡的名稱不會去問 DNS；在那裡手動指定的測試用名稱，忘了刪就會變成「只有我的電腦連錯地方」。Docker 自訂網路裡也有內建 DNS，容器可以用名稱互相連線，練習 3 的 ld-04-open 就是這樣解析的，第 10 課的 Compose 會大量用到。

zone 檔怎麼寫

權威伺服器的資料常寫成 zone 檔（RFC 1035 格式），練習 2 用 CoreDNS 1.15.0 的 file 外掛讀它：

$ORIGIN cafe.test.          ; 沒有以點結尾的名稱，後面都會自動接上這個
$TTL 3600                   ; 沒寫 TTL 的紀錄用這個值
@   IN SOA ns1.cafe.test. admin.cafe.test. (
        2026110101 ; serial
        7200 3600 1209600 3600 )
@   IN NS  ns1.cafe.test.   ; @ 代表 $ORIGIN 本身，也就是 cafe.test.
ns1 IN A   10.0.1.53        ; ns1 → ns1.cafe.test.
  • 結尾的點：api.cafe.test. 是完整名稱；api.cafe.test（沒有點）會被接上 $ORIGIN，變成 api.cafe.test.cafe.test.。CNAME 目標忘了點是最常見的 zone 檔錯誤，dig 會看到一個奇怪的長名稱。
  • SOA 紀錄（Start of Authority）描述這個 zone 本身，最重要的是 serial（序號）。其他伺服器比對序號判斷要不要更新，CoreDNS 的 file 外掛也是每隔一段時間（預設 1 分鐘）檢查序號變了才重新載入。改了內容沒加序號，等於沒改。常見寫法是日期加兩位流水號：2026110101 → 2026110102。
  • TTL 寫在名稱後面：api 300 IN A 10.0.1.10；沒寫就用 $TTL。
  • TXT 有空白要加引號："v=spf1 -all" 是一個字串；不加引號會變成 v=spf1 和 -all 兩段。

TCP 與 UDP

HTTP、PostgreSQL、Redis 都跑在 TCP 上：可靠、有順序、送之前要先建立連線。建立連線的過程叫三向交握（three-way handshake）：客戶端送 SYN（「我想連線」），伺服器回 SYN-ACK（「收到，我也準備好了」），客戶端再回 ACK（「收到」），之後才開始傳 HTTP 請求。那個 port 沒人在聽時，對方主機回的是 RST（reset，「這裡沒人，別連了」）。

UDP 不建立連線、不保證送達、不保證順序，送出去就算了。DNS 查詢平常用 UDP（一問一答，丟了重問就好），所以練習 2 發布的是 53/udp。

連線失敗時要分清楚兩種：

connection refusedtimeout（逾時）
發生什麼對方主機在，回了 RST 明確拒絕SYN 送出去沒有任何回應
多快幾毫秒等到逾時；Linux 預設重送 SYN 6 次，約兩分鐘才放棄
典型原因程式沒在跑、port 寫錯、只聽 127.0.0.1防火牆把封包丟掉、安全群組沒開、IP 錯了或主機不在
先查什麼對方機器上 lsof／ss -ltnp 看誰在聽安全群組、防火牆規則、路由、IP 對不對

curl 的錯誤碼也分得出來：(6) Could not resolve host 是 DNS、(7) Failed to connect … Couldn't connect to server 是 refused、(28) 是逾時（用 --connect-timeout 2 時印 Failed to connect … after 2013 ms: Timeout was reached，用 -m 限制總時間時印 Connection timed out after …）、(52) Empty reply from server 是連上了但對方什麼都沒回。

不要用 ping 判斷服務好壞。ping 用的是 ICMP，不是 TCP，也不看 port：很多雲端主機預設擋 ICMP，ping 不通但網站正常；反過來 ping 得通，3000 port 可能根本沒人聽。要問的是「這個 port 連不連得上」。

逐層排查：連不上時照這個順序

一個 HTTPS 請求要依序通過四層，前一層沒過，後面都不用看：

層要問的問題指令
1. DNS名稱解析成對的 IP 嗎？dig +short api.cafe.example.com、dig @1.1.1.1 …
2. TCP那個 IP 的 port 連得上嗎？refused 還是 timeout？Mac：nc -zv -G 2 host 443（-G 是連線逾時秒數）
3. TLS憑證和握手成功嗎？（第 5 課）curl -v https://… 看 SSL 那幾行
4. HTTP回什麼狀態碼？app 的 log 怎麼說？curl -i、docker logs、journalctl（第 6 課）

curl -v 本身就照這個順序印：先 Host … was resolved（DNS），再 Trying／Connected（TCP），HTTPS 時接著 TLS 握手，最後才是請求和回應。慢的時候用 -w 看每一段花多久，數字都是從請求開始累計的秒數：

curl -s -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} 首位元組=%{time_starttransfer} 總共=%{time_total}\n' https://cafe.example.com/
# dns 就很大 → DNS 慢；tcp 減 dns 很大 → 網路遠或在重送 SYN；首位元組減 tls 很大 → app 自己慢

症狀對照：

症狀可能原因先做
Could not resolve host網域打錯、DNS 紀錄沒建、/etc/hosts 寫錯dig，比對 dig @1.1.1.1
有人連新 IP、有人連舊 IPTTL 快取還沒過期dig 看剩下的 TTL，等它過期
Connection refused程式沒跑、port 錯、只聽 127.0.0.1伺服器上 lsof -nP -iTCP -sTCP:LISTEN
連線逾時防火牆或安全群組丟封包、IP 錯檢查規則；伺服器上 tcpdump 看 SYN 有沒有到
Empty reply／connection reset容器裡程式聽錯位址、程式當掉docker logs，看 listening on 哪裡

真的搞不清楚封包有沒有到，在伺服器上用 tcpdump 擷取經過網卡的封包（需要 root）：

sudo tcpdump -n -i any tcp port 3000
# 只看到 [S]（SYN）一直重複、沒有回應 → 封包到了但沒人回，或回應被擋
# 看到 [S] 接著 [R.]（RST）→ 這台機器上沒人在聽 3000
# 連 [S] 都沒看到 → 封包根本沒到這台：查前面的防火牆、安全群組、路由

Ubuntu 上設定主機防火牆常用 ufw（ufw allow 22/tcp）。要小心的是：Docker 用 -p 發布的 port 會在 ufw 的規則之前就被轉進容器，等於繞過 ufw。Docker 文件也寫明發布 port 預設發布在所有位址。所以「我有開 ufw，資料庫應該很安全」是錯的，資料庫的 port 一開始就不該發布到 0.0.0.0，第 10 課會再處理。

💡 實務上：收到「連不上」，先問三個問題
同事或客服說「API 連不上」，資訊通常不夠用。先問：從哪裡連（客人的手機、公司網路、另一台伺服器）、連到哪裡（完整的網址或 IP:port）、錯誤長什麼樣（逾時、拒絕連線、找不到主機、憑證錯誤）。這三個答案幾乎就決定了要從上面表格的哪一層查起。換你回報問題時也照這個格式寫，對方可以少來回問好幾次。

練習

三題都需要 Docker。練習 2 會下載 coredns/coredns:1.15.0，第一次會花一點時間。在 learn 資料夾執行 node check.mjs devops 04。

練習 1：run.sh 已經寫好，會用 -p 127.0.0.1:18040:3000 在容器裡跑 server.mjs。先執行 sh run.sh，再 curl http://localhost:18040/health/live，看到失敗之後用 docker logs ld-04-api 找原因，修好 server.mjs，讓它回 200。不要動 run.sh 的 -p（主機端維持 127.0.0.1），也不要用 --network host。每次重試前先 docker rm -f ld-04-api。

練習 2：編輯 zone 檔 db.cafe.test，加上三筆紀錄：api.cafe.test 的 A 紀錄指向 10.0.1.10、TTL 300 秒；www.cafe.test 是指向 api 的 CNAME；cafe.test 本身的 TXT 紀錄 v=spf1 -all。改完記得把 SOA 序號加大。測試會用 CoreDNS 載入你的檔案（Corefile 不用改），從 Mac 查詢每一筆。自己試的方法：docker run -d --name ld-04-dns -p 127.0.0.1:18045:53/udp -v "$PWD:/zones:ro" coredns/coredns:1.15.0 -conf /zones/Corefile（在 work/04 裡執行），再 dig @127.0.0.1 -p 18045 www.cafe.test。

練習 3：寫 diagnose.sh <host> <port>，只印出一個字：open、refused 或 timeout，2 秒內一定要結束。測試會在 ubuntu:24.04 容器裡用 bash diagnose.sh 執行它，對三個目標比對輸出：有 nginx 在聽的 port、沒人聽的 port、封包會被丟掉的位址，每次要在 5 秒內結束。容器裡沒有 nc 和 ping，要用兩個工具：bash 的特殊路徑 /dev/tcp/主機/port（不是真的檔案，exec 3<>/dev/tcp/… 會開一條 TCP 連線，連上時結束碼 0，被拒絕時 1 而且錯誤訊息含 Connection refused），以及 timeout 2 指令（指令 2 秒內沒結束就把它結束掉，這時結束碼是 124）。名稱查不到這類其他錯誤，不要硬塞進三種之一。

練習 4：容器裡的程式印出 listening on 127.0.0.1:3000，你也寫了 -p 18040:3000，從 Mac 執行 curl 卻得到 Empty reply from server。原因是？

✓ 每個容器有自己的網路空間，裡面的 127.0.0.1 只代表容器自己，要讓程式聽 0.0.0.0。a 錯：沒寫主機 IP 會綁在所有位址，Mac 一樣連得到（只是不安全），問題在容器裡；c 正是要破除的誤解；d 錯：1024 以下才需要特殊權限，3000 沒問題。

練習 5：你把 api.cafe.example.com 的 A 紀錄改成新 IP，十分鐘後還有一部分客人連到舊機器。最可能的原因是？

✓ DNS 答案會在各地解析器和裝置上被快取 TTL 秒。原本 TTL 是 3600，就可能有人一小時內都拿到舊 IP；所以換 IP 前要先把 TTL 調低。a 錯：權威伺服器改完就回新答案，舊的是別人的快取；b 錯：這是正常現象，來回改只會讓兩邊答案混在一起更久。

練習 6：安全群組要放行 10.0.1.0/24 這個子網路，它有幾個位址？10.0.1.130 在裡面嗎？

✓ /24 表示前 24 位元固定，剩 8 位元可以變，28 = 256 個，範圍是 10.0.1.0～10.0.1.255，130 在裡面。斜線後的數字是「固定的位元數」，不是位址數量，也不是最後一段的上限。

練習 7：同事回報「連資料庫失敗」，一個錯誤是 connection refused，另一個是等了很久之後 timeout。哪一個比較像是被防火牆擋掉？

✓ 防火牆和安全群組通常直接丟掉封包（DROP），客戶端收不到任何回應，只能一直重送 SYN 直到逾時。refused 代表封包到了對方主機、對方回了 RST，最常見是那個 port 沒有程式在聽，該查的是服務有沒有在跑、聽在哪個位址。把兩者混為一談，就會在錯的地方找問題。

常見錯誤

  • 容器裡的服務只聽 127.0.0.1：Docker 轉進來的連線從 eth0 進來，沒人收。容器裡聽 0.0.0.0，主機端的 -p 寫 127.0.0.1。
  • 把資料庫的 port 發布到 0.0.0.0：-p 5432:5432 會開在所有位址，而且 Docker 的轉送規則在 ufw 之前，主機防火牆擋不住。只發布在 127.0.0.1，或根本不發布、只在內部網路連（第 10 課）。
  • CNAME 目標忘了結尾的點：api.cafe.test 會變成 api.cafe.test.cafe.test.。zone 檔裡的完整名稱一律以點結尾。
  • 改了 zone 檔沒加 SOA 序號：次要伺服器和 CoreDNS 的 reload 都看序號，序號沒變就當作沒改。
  • 剛改 DNS 就以為壞了：舊答案還在快取裡。要換 IP 前先把 TTL 調低，用 dig 看剩下的 TTL。
  • 用 ping 判斷服務好壞：ICMP 常被擋，而且不看 port。用 nc -zv 或 curl -v 看那個 port 連不連得上。
  • 把 refused 和 timeout 當成同一件事：refused 去查程式和監聽位址，timeout 去查防火牆、安全群組和 IP。
  • 連線沒設逾時：腳本或程式連到被丟封包的位址，會卡到系統預設的兩分鐘左右。健康檢查和診斷工具一律自己設短的逾時。
  • 以為 localhost 一定是 127.0.0.1：它也可能先解析成 ::1。程式只聽其中一個，就會時好時壞。

小結

  • IP 是機器的地址，port 是同一台機器上的門牌；私有位址（10/8、172.16/12、192.168/16）靠 NAT 共用公開 IP 上網。
  • CIDR 的 /N 是固定的位元數：/24 是 256 個位址，/32 是一個，/0 是全部。
  • 127.0.0.1 只收同一台機器（同一個容器）的連線，0.0.0.0 收所有網卡。容器裡聽 0.0.0.0，主機端 -p 寫 127.0.0.1。
  • DNS 由解析器一層層問到權威伺服器，答案依 TTL 快取；zone 檔注意結尾的點、TTL、SOA 序號。
  • TCP 先三向交握；refused 是對方回 RST（沒人聽），timeout 是封包被丟（防火牆、IP 錯）。
  • 連不上照 DNS → TCP → TLS → HTTP 的順序查：dig、nc -zv、curl -v、curl -w、lsof、tcpdump。
