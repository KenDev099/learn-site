階段 5：雲端與基礎設施即程式碼 · 第 20 課

基礎設施即程式碼：OpenTofu

咖啡店的正式環境是兩年前一位工程師在 AWS 主控台一格一格點出來的：VPC、安全群組、RDS、S3 bucket、IAM role。他離職了。現在要開一套 staging，沒有人說得出正式環境的安全群組到底開了哪些 port、RDS 的參數改過什麼；上個月有人為了除錯把資料庫的 5432 暫時開給 0.0.0.0/0，到現在還開著，也沒有任何紀錄說是誰、為什麼。

這一課把基礎設施寫成程式碼：檔案進 git、改動走 PR、同一份程式碼可以建出第二套一模一樣的環境。工具用 OpenTofu 1.13.2。練習在你的 Mac 上用 Docker provider 管理容器、網路與 volume，不需要雲端帳號、不會產生帳單；換成 AWS provider 時，語法、流程、state 的管理方式完全相同。

這課的路線：
  1. 點滑鼠的問題：在主控台手動建的資源，為什麼之後沒人說得清楚現況，IaC 怎麼解決。
  2. HCL 與 init、plan、apply：逐段讀一份 main.tf，套用前從 plan 看出哪些資源會被修改、哪些會被刪掉重建，審查基礎設施 PR 就看這個。
  3. state：工具靠什麼記住它管了哪些資源，為什麼 state 不能進 git、要放遠端並加鎖。
  4. 漂移與 import：有人在主控台手動改了東西，或要把手動建的資源收進程式碼時怎麼辦。
  5. 模組、環境與 Terraform／OpenTofu：同一份程式碼開出 staging 和正式環境，以及兩套工具的關係。
這課會用到：
  • 第 7 課的容器、volume 與網路：容器從映像啟動，資料放在 volume 才不會跟著容器消失，同一個網路裡的容器用名稱互連。
  • 第 10 課的 Compose：在檔案裡寫「最後要有哪些容器」，docker compose up 自己算出要建立或修改什麼。
  • 第 18 課的 AWS 元件：VPC、安全群組、RDS、S3 是咖啡店正式環境裡要寫成程式碼的東西。

點滑鼠的問題

在主控台手動建立資源，問題不在當下，而在之後：

  • 沒有紀錄：誰在什麼時候改了什麼、為什麼改，主控台不會告訴你（CloudTrail 只記得 API 呼叫，不記得理由）。
  • 無法審查：改安全群組不需要任何人同意；程式碼要開 PR，改資料庫的 port 規則也一樣。
  • 無法重現：要開 staging、要在另一個 region 建災難復原環境（第 24 課），只能照著截圖再點一次，然後一定會漏。
  • 環境慢慢不一樣：staging 和正式環境各自被手動改過，第 1 課講的 dev/prod parity 就沒了，「staging 測過」不再代表什麼。

基礎設施即程式碼（Infrastructure as Code, IaC）是用程式碼描述基礎設施，再交給工具去建立和修改。你在第 10 課已經用過這種想法：compose.yaml 寫的是「最後要有哪些容器、什麼設定」，docker compose up 自己算出要建立、重建還是什麼都不做。這種寫法叫宣告式（declarative）：描述要長什麼樣子，由工具算出步驟。相對的是命令式（imperative）：一行一行寫步驟，例如一份 docker network create …; docker run … 的 shell 腳本。

宣告式的好處是冪等（idempotent）：同樣的程式碼執行第二次，結果一樣，不會多建一份。命令式腳本跑第二次通常會失敗（名稱已存在）或重複建立。IaC 工具做得到冪等，靠的是它記得自己管了哪些東西，這就是後面要講的 state。

Compose 只管一台機器上的容器。OpenTofu 透過 provider（操作某個平台的外掛）可以管 AWS、GCP、Cloudflare、GitHub、Docker 等幾千種平台的資源，而且在套用之前先列出完整的變更清單讓你確認。

HCL：逐段讀一份 main.tf

OpenTofu 的設定檔副檔名是 .tf，語言叫 HCL（HashiCorp Configuration Language）。同一個資料夾裡的所有 .tf 檔會被合併成一份設定，檔名只是方便人看；慣例是 main.tf 放資源、variables.tf 放變數、outputs.tf 放輸出。下面是練習 1 的骨架，一段一段看。

terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"   # registry 上的「發行者/名稱」
      version = "4.6.0"                # 版本限制，也可以寫 "~> 4.6"（4.6 以上、5.0 以下）
    }
  }
}

provider "docker" {}                   # provider 的設定；docker 預設連 unix:///var/run/docker.sock

terraform 區塊放工具本身的設定。區塊名稱叫 terraform 是歷史原因，OpenTofu 為了相容沿用。required_providers 宣告這份設定用到哪些 provider、允許哪些版本。tofu init 會下載符合限制的版本，並把實際選到的版本與檔案雜湊寫進 .terraform.lock.hcl。這個鎖定檔要提交到 git，作用跟 package-lock.json 一樣：每個人、每次 CI 都用同一個 provider 版本，下載的檔案被竄改也會被雜湊擋下。下載下來的 provider 放在 .terraform/，那個資料夾不提交。

variable "db_password" {
  type      = string
  sensitive = true                    # plan、apply 的輸出顯示 (sensitive value)
  validation {
    condition     = length(var.db_password) >= 16
    error_message = "db_password 至少要 16 個字元。"
  }
}

variable "api_image" {
  type = string
}

locals {
  prefix = "ld-20"                     # 同一份設定裡重複用到的值
}

variable 是這份設定的輸入，用 var.名稱 讀。值可以從指令列 -var 'api_image=…'、*.tfvars 檔、或環境變數 TF_VAR_名稱 傳入；都沒有又沒有 default 時，互動模式會問你，CI 裡加了 -input=false 就直接報錯。機密一律不寫 default，因為 .tf 會進 git（第 11 課）。sensitive = true 只讓畫面上的輸出遮住這個值，不會讓它從 state 檔消失，後面會看到。validation 在 plan 時檢查值，不合格就停下來並顯示 error_message。locals 是設定內部的常數或計算結果，用 local.名稱 讀。

resource "docker_network" "cafe" {
  name = "${local.prefix}-net"
}

resource "docker_container" "db" {
  name  = "${local.prefix}-db"
  image = docker_image.postgres.image_id
  env   = ["POSTGRES_PASSWORD=${var.db_password}"]
  networks_advanced {
    name = docker_network.cafe.name
  }
}

output "api_url" {
  value = "http://127.0.0.1:${docker_container.api.ports[0].external}"
}

resource 是 OpenTofu 管理的一個東西：一個容器、一個網路、一個 S3 bucket。第一個字串是資源類型（provider 名稱開頭），第二個是你在這份設定裡給它的名字，兩者合起來的 docker_container.db 叫做位址（address），plan 和 state 都用它指稱這個資源。區塊裡的屬性哪些必填、改了會怎樣，看 provider 的文件。

docker_network.cafe.name 這種寫法是引用：讀另一個資源的屬性。OpenTofu 從所有引用畫出一張相依圖，被引用的先建，沒有相依關係的同時建，刪除時順序相反。你不寫順序，順序由引用決定。output 是 apply 之後要給人或其他設定看的值，tofu output api_url 讀得到。

用 docker_container.db.name 而不是直接寫字串 "ld-20-db"，不只是少打字：直接寫字串時 OpenTofu 看不出 api 依賴 db，可能先建 api、或在刪除時先刪 db。資源之間的關係一律用引用表達；真的沒有屬性可以引用時才用 depends_on = [docker_container.db]。

工作流程：init、plan、apply

指令做什麼什麼時候跑
tofu init下載 provider 與 module、設定 backend、建立或檢查 .terraform.lock.hcl第一次、改了 provider／module／backend 之後；CI 每次都跑
tofu fmt把 .tf 整理成標準格式；-check 只檢查不改，不合格時 exit 非 0存檔時、CI 裡用 -check
tofu validate檢查語法、型別、引用是否存在，不連任何平台CI 裡，比 plan 快
tofu plan讀 state、向平台查目前的實際狀態（refresh），和程式碼比對，列出要做的變更。不改任何東西每次 apply 之前、每個 PR
tofu apply重新算一次 plan，等你輸入 yes 才執行，最後更新 statePR 合併後
tofu destroy刪掉 state 裡記錄的所有資源收掉臨時環境；正式環境幾乎不用

plan 是這套工具最重要的輸出。每個資源前面有一個符號：

符號意思風險
+ create建立新資源低；但要確認不是「同一個東西被建第二份」
~ update in-place原地修改，資源本身不動通常不中斷，例如改容器的重啟策略、改標籤
-/+ replace先刪除再重建（+/- 是先建新的再刪舊的）高：刪的那一刻服務中斷；如果是資料庫、volume、bucket，裡面的資料一起消失
- destroy刪除最高：從程式碼移除一個資源，apply 時它就會被刪

哪些屬性改了會造成重建，由 provider 決定，plan 會在那個屬性旁邊標 # forces replacement。這常常和直覺不同：Docker 的容器建立後不能改環境變數、映像、掛載，所以在 docker provider 裡改 env 就是 -/+；AWS 的 RDS 改了 identifier 也是重建，等於一台新的空資料庫。看 plan 的重點不是「有沒有錯」，而是「有沒有 -/+ 和 -」。

Plan: 4 to add, 1 to change, 4 to destroy.

這一行的 add 和 destroy 都包含 replace（一個重建算一次 add 加一次 destroy）。看到 destroy 不是 0，就逐一找出是哪些資源。

在 CI（第 15 課）裡，tofu plan -detailed-exitcode 用結束碼回報結果：0 沒有變更、1 出錯、2 有變更。PR 的 workflow 跑 plan，把輸出貼成 PR 留言給審查的人看；排程的 workflow 每天對正式環境跑一次 plan，exit 2 就代表有人手動改過東西（下一節的漂移）。plan 用的雲端憑證只給唯讀權限，apply 才用另一個能寫的 role（第 19 課的 OIDC 與最小權限）。

正式環境的做法是 tofu plan -out=plan.bin 存下這份計畫，有人看過之後 tofu apply plan.bin 套用「同一份」計畫；直接 apply 會重新算一次，中間如果有人改了東西，套用的就不是你看過的那份。-auto-approve 跳過確認，只用在臨時環境與測試。

state：工具的記憶

state（狀態檔）記錄「這份設定管理了哪些實際資源、它們目前的屬性」。預設是工作資料夾裡的 terraform.tfstate（JSON）。沒有它，OpenTofu 不知道 docker_container.db 對應的是哪一個容器 ID，下次 plan 會以為什麼都還沒建。

{
  "resources": [{
    "type": "docker_container", "name": "db",
    "instances": [{
      "attributes": {
        "id": "c4a293d8…",
        "name": "ld-20-db",
        "env": ["POSTGRES_DB=cafe", "POSTGRES_PASSWORD=這裡是明文密碼", …]
      },
      "sensitive_attributes": [[{ "type": "get_attr", "value": "env" }]]
    }]
  }]
}

這是練習 1 apply 之後的 state（節錄）。sensitive_attributes 只是標記「這個屬性在畫面上要遮住」，值照樣是明文。資源的屬性裡有什麼，state 就存什麼：資料庫密碼、RDS 的 master 密碼、產生的私鑰都在裡面。所以：

  • state 不能提交到 git。.gitignore 寫 *.tfstate 和 *.tfstate.*（apply 前會留一份 terraform.tfstate.backup），再加 .terraform/；.terraform.lock.hcl 要提交，不要寫成 .terraform* 把它也排除。
  • 多人協作用遠端 state。state 放在本機，就只有你能 apply；兩個人各自一份 state，就是兩套互相不知道對方的記憶。backend 設定 state 存在哪裡，AWS 上常用 S3。
  • 一定要有鎖。兩個人同時 apply，各自讀到舊 state、各自建資源、各自寫回 state，後寫的蓋掉先寫的：一邊建的資源從 state 裡消失，變成沒人管的孤兒，下次 plan 又建一份。state 鎖（state locking）讓同一時間只有一個 apply。
terraform {
  backend "s3" {
    bucket       = "cafe-tofu-state"
    key          = "prod/terraform.tfstate"
    region       = "ap-northeast-1"
    use_lockfile = true          # 用 S3 的條件寫入當鎖；舊做法是另外一張 DynamoDB 表（dynamodb_table）
  }
}

放 state 的 bucket 本身要封鎖公開存取、開版本控制（state 寫壞了可以退回上一版）、開伺服器端加密，而且只有部署用的 role 讀得到（第 19 課）。這個 bucket 通常用另一份小設定（或手動）先建好：要先有 bucket 才能存 state，用同一份設定管它會變成雞生蛋的問題。

OpenTofu 比 Terraform 多一層保護：state 加密。在 OpenTofu 這一端先加密再寫出去，就算 bucket 權限設錯、備份外流，拿到的也只是密文；plan 檔裡有整份設定與變數值，也一樣要加密。

variable "state_passphrase" {
  type      = string
  sensitive = true
}

terraform {
  encryption {
    key_provider "pbkdf2" "main" {
      passphrase = var.state_passphrase      # 至少 16 個字元；從 TF_VAR_state_passphrase 傳入
    }
    method "aes_gcm" "main" {
      keys = key_provider.pbkdf2.main
    }
    state {
      method   = method.aes_gcm.main
      enforced = true                         # 拒絕寫出沒加密的 state
    }
    plan {
      method   = method.aes_gcm.main
      enforced = true
    }
  }
}
  • key_provider 產生加密金鑰。pbkdf2 從一段 passphrase 推導金鑰，passphrase 至少 16 個字元；正式環境常改用 aws_kms，金鑰留在 KMS（Auth 課第 23 課的信封加密）。
  • method 是加密演算法，aes_gcm 同時防竄改：用錯的金鑰解密會直接失敗，不會讀到亂碼。
  • enforced = true：有人想把 method 換成 unencrypted，OpenTofu 會拒絕。
  • 同一份設定也可以放在環境變數 TF_ENCRYPTION（內容是 encryption 區塊裡面那幾段，不含外層的 terraform {}）；兩邊都有時合併，環境變數優先。適合在 CI 裡由 secret 提供整段設定。

加密後的 terraform.tfstate 只剩 serial、lineage、meta（金鑰推導的參數，例如 salt 與迭代次數）、encryption_version 和一大段 encrypted_data。passphrase 弄丟，state 就解不開，等於失去記憶，要像保管資料庫備份的金鑰一樣保管它。

已經有一份沒加密的 state 時直接加上 encryption，OpenTofu 會讀不懂舊檔而報錯。官方的移轉方式是先多定義 method "unencrypted" "migrate" {}，在 state 區塊加 fallback { method = method.unencrypted.migrate }（此時不能 enforced），apply 一次讓 state 用新方法寫回，再拿掉 fallback、加上 enforced。只是在本機練習的話，先 destroy 再加密最快。

漂移與 import

漂移（drift）是實際資源和程式碼不一致：有人在主控台手動改了安全群組、刪了容器、調了 RDS 參數。每次 plan 都會先 refresh（向平台查目前狀態），所以下一次 plan 一定看得到差異，apply 會把它改回程式碼描述的樣子。

這也是危險所在：有人半夜為了救火在主控台把 RDS 的連線數調高，隔天別人的 PR 一 apply，就把它改回去了，事故重演。處理漂移只有兩個方向：

  • 改動是錯的：apply，讓實際資源回到程式碼。
  • 改動是對的：把它寫回程式碼、開 PR，plan 變成沒有變更（exit 0）就收斂了。

規則是：被 IaC 管理的資源不在主控台手動改；緊急時改了，事後立刻補 PR。每天排程跑 plan -detailed-exitcode，exit 2 就通知，漂移不會累積到下一次部署才爆。

反過來，已經存在、但還沒被管理的資源（例如兩年前手動建的 VPC），用 import 收進 state：

import {
  to = docker_network.legacy
  id = "現有網路的 ID"
}

resource "docker_network" "legacy" {
  name = "cafe-legacy"
}

plan 會顯示要 import，屬性不一致的地方會一併列出更新或重建；先調整程式碼直到 plan 只剩 import、沒有 -/+，再 apply。import 之後這個資源就歸程式碼管，destroy 也會刪掉它。

💡 實務上：已經點出來的環境，分批改成程式碼
大多數團隊導入 IaC 時，雲端上已經有一堆手動建的資源。一次全部 import，plan 會很長、風險很高。常見的做法是：新的資源一律用程式碼建；舊的從最常改、最怕改錯的開始 import（安全群組、IAM），每次 import 完確認 plan 沒有變更才合併。在資源加上 managed-by = "opentofu" 這類標籤，同事在主控台看到就知道不要手動改。

模組與環境

module（模組）是一個裝著 .tf 檔的資料夾，可以被其他設定重複使用，有自己的 variable（輸入）和 output（輸出），就像一個函式。你的根目錄本身也是一個 module（root module）。

envs/
  staging/main.tf     # module "cafe" { source = "../../modules/cafe"  instance_size = "small" }
  prod/main.tf        # module "cafe" { source = "../../modules/cafe"  instance_size = "large" }
modules/
  cafe/               # variables.tf、main.tf、outputs.tf：VPC、資料庫、api 服務
    …

每個環境是一個獨立的根目錄：各自的 state、各自的變數、各自的 backend key。staging 的 plan 不會碰到正式環境；正式環境的 apply 可以要求更多審查（第 16 課的 environment protection）。要避免的是一個 state 管所有環境、所有服務：plan 一次要查幾千個資源、任何人改任何東西都鎖住所有人，一個錯誤的 apply 影響範圍是整間公司。常見的切法是按環境、再按變動頻率分層（網路一層、資料庫一層、應用程式一層），上層用 output 或 terraform_remote_state 讀下層的值。

module 的 source 也可以是 registry 或 git，這時要像 provider 一樣鎖版本（version = "5.1.0" 或 git 的 ?ref= 指到 tag），否則別人推一版新的 module，你下次 init 就換掉了。

💡 實務上：模組不要太早抽
只有 staging 和正式環境兩份時，各寫一份、差異一眼看得出來，常常比抽成模組好讀。抽模組的時機是同樣的東西要用第三次，或兩個環境開始「應該一樣卻不小心不一樣」。抽出來之後，模組的 variable 就是對外的介面：加變數容易，改名或刪掉會讓所有呼叫的地方一起壞，跟改函式的參數一樣，要在 PR 裡說明影響。

Terraform 與 OpenTofu

這套語言原本是 HashiCorp 的 Terraform。2023-08-10 HashiCorp 宣布之後的版本從開源授權 MPL 2.0 改成 BSL 1.1（Business Source License：可以看原始碼、自己用，但不能拿來做和 HashiCorp 競爭的產品）。社群從最後一個 MPL 版本分出 OpenTofu，維持 MPL-2.0。

  • 相容：HCL 語法、大部分 provider（provider 是另外發行的，同一個 provider 兩邊都能用）、state 格式（官方文件有從 Terraform 移轉的步驟）。指令把 terraform 換成 tofu。
  • 分歧：分家之後兩邊各自加功能。OpenTofu 有 state 加密；Terraform 有它自己的新功能與 HCP Terraform 雲端服務。用到各自獨有功能的設定，就不能直接換邊。
  • 怎麼選：公司已經用 Terraform 並付費用 HCP Terraform，留著；新專案、在意授權或想要 state 加密，用 OpenTofu。兩者概念完全一樣，這一課學到的都適用。

第 13 課提過的 Kubernetes 也是宣告式：你寫 manifest，它的控制迴圈（controller）一直比對期望狀態和實際狀態，不一致就自動修正，等於每幾秒自動 apply 一次。OpenTofu 只在你執行 apply 時才動作，中間的漂移要靠排程 plan 抓。這也是為什麼常見的分工是：OpenTofu 建雲端資源（VPC、資料庫、Kubernetes 叢集本身），Kubernetes 管叢集裡的應用程式。

練習

練習在 work/20/。OpenTofu 跑在容器裡，不用安裝：tofu.sh 第一次執行時會用 tofu.Dockerfile 建出 learn-devops/tofu:1.13.2（從官方的 -minimal 映像複製 tofu 執行檔，並預先下載 docker provider 4.6.0；OpenTofu 1.10 起官方映像不支援直接執行），之後在 work/20 或它的子資料夾執行 sh tofu.sh init、sh tofu.sh plan…（在 plan/ 裡是 sh ../tofu.sh …）。容器掛上了 /var/run/docker.sock，所以裡面的 tofu 建立的容器就在你的 Docker Desktop 上。設定好的 TF_VAR_db_password、TF_VAR_api_image、TF_VAR_state_passphrase、TF_ENCRYPTION 會自動傳進容器。測試會自己建立和清掉 ld-20-* 的容器、網路、volume，以及 state 檔。

練習 1：用程式碼建出咖啡店的本機環境。main.tf 已經有 terraform、provider 和網路 ld-20-net，你要加上：variable "db_password"（sensitive、沒有 default）；variable "api_image"（沒有 default，加 validation 擋下以 :latest 結尾的值）；volume ld-20-pgdata；postgres 映像用 digest 指定（postgres:18.6-alpine3.24@sha256:10a5c69a83035ab5239f5620d708520e8b28f5aa1f2b20143e6024532edadfb5，用 docker_image 資源並設 keep_locally = true）；容器 ld-20-db：使用者與資料庫都叫 cafe、密碼來自變數、volume 掛到 /var/lib/postgresql、有 pg_isready 的 healthcheck；容器 ld-20-api：映像是 var.api_image，環境變數 DATABASE_URL=postgres://cafe:密碼@db 容器名稱:5432/cafe，容器 port 3000 只發布在 127.0.0.1:18200；兩個容器都接到 ld-20-net；output "api_url" 的值是 http://127.0.0.1:18200（引用 api 容器的屬性組出來，不能直接寫字串）。.gitignore 排除 state 檔與 .terraform/，但不排除 .terraform.lock.hcl。測試依序執行 init、fmt -check，第一次 plan -detailed-exitcode -out 要是 2，從 plan 檢查變數與映像的寫法（TF_VAR_api_image 是 …:latest 時 plan 要失敗）；apply 這個 plan 檔之後 /health/ready 回 200；再 plan 要是 0；用 docker rm -f ld-20-api 製造漂移，plan 要是 2 並要建立 api，apply 後恢復。自己試的指令寫在 main.tf 開頭（先 docker build -t learn-devops/cafe-api:20 app）。

練習 2：讀懂 plan。plan/v1/main.tf 是目前線上的版本，plan/v2/main.tf 是同事的 PR（兩個都不要改）。在 plan/ 裡：cp v1/main.tf main.tf、sh ../tofu.sh init、sh ../tofu.sh apply；再 cp v2/main.tf main.tf、sh ../tofu.sh plan -out=plan.bin，需要的話 sh ../tofu.sh show -json plan.bin 看完整的 JSON（resource_changes[].change.actions）。不要 apply v2。在 plan-review.json 填：actions：每個有變更的資源位址對應 create、update、replace、delete 其中一個（no-op 的不列）；downtime：會讓服務中斷的資源位址；dataLoss：會遺失資料的資源位址。測試自己在另一個資料夾套用 v1、產生 v2 的 plan，從 plan JSON 算出答案再跟你的比對。做完用 sh ../tofu.sh destroy 收掉。

練習 3：state 裡有什麼。先用練習 1 的設定 apply（沒有加密），打開 terraform.tfstate 搜尋你的密碼，在 answers.json 填：addresses：state 裡含有密碼的所有資源位址；attribute：密碼出現在那些資源 attributes 底下的哪個屬性。接著在 encryption.tf 加上 state 加密：variable "state_passphrase"（sensitive、沒有 default）、pbkdf2 從這個變數推導金鑰、aes_gcm，state 與 plan 都加密而且都 enforced = true。passphrase 從 TF_VAR_state_passphrase 傳入，至少 16 個字元。你手上已經有沒加密的 state，先 sh tofu.sh destroy 再加加密設定（或照課文用 fallback 移轉）。測試用隨機的密碼與 passphrase apply 之後檢查：answers 的答案、terraform.tfstate 有 encrypted_data 且沒有密碼明文、plan -out 產生的檔案不是未加密的 zip、換一個 passphrase 會解密失敗、用 TF_ENCRYPTION 把 state 或 plan 改成 unencrypted 會因為 enforced 而失敗。

練習 4：同事說：「terraform.tfstate 就是一份設定檔，提交到 git 最方便，大家都拿得到最新的。」問題在哪？

✓ c。state 存的是資源屬性的實際值，sensitive 只遮住畫面輸出，state 照樣是明文（練習 3 親眼看過）；私有 repo 的每個 clone、每個 fork、每台 CI runner 都有一份，外洩面很大，所以 a、d 都錯。b 解決的是大小，不是機密和並行：git 在你 apply 時不會鎖住別人，兩份 state 合併只會產生衝突或互相覆蓋，造成孤兒資源。正確做法是 S3 之類的遠端 backend 加 state 鎖，必要時再加 OpenTofu 的 state 加密。

練習 5：半夜救火時，值班的人在 AWS 主控台把正式環境安全群組的一條規則改掉了，事後沒有改程式碼。下一次有人對這份設定執行 tofu plan，會發生什麼？

✓ a。plan 預設會 refresh：向 AWS 查每個資源目前的屬性，再跟程式碼比，所以漂移一定看得到（b 錯）。OpenTofu 不會修改你的程式碼（c 錯），它只會把實際資源改成程式碼描述的樣子。所以要嘛 apply 把改動還原（改動是錯的），要嘛把改動寫進程式碼開 PR（改動是對的），而且要在下一個不知情的人 apply 之前決定。

練習 6：PR 的 plan 裡有一行 -/+ resource "aws_db_instance" "main"，旁邊的屬性標著 # forces replacement。審查的人該怎麼理解？

✓ b。-/+ 是 replace，先刪除後建立；原地更新的符號是 ~（a 錯）。先建後刪的符號是 +/-，而且就算先建，新資料庫也是空的（c 錯）。plan 就是 apply 會做的事，不會臨時改變主意（d 錯）。常見原因是改了 identifier、引擎類型、子網路群組這類建立後不能改的屬性；做法是撤回那個屬性的改動，或另外規劃遷移，並在相關資源加上 lifecycle { prevent_destroy = true } 讓這種 plan 直接報錯。

練習 7：state 放在本機檔案、沒有鎖。兩位工程師幾乎同時對同一份設定執行 apply，一個新增 S3 bucket，一個新增 IAM role。最可能的結果是？

✓ d。OpenTofu 不合併 state（a 錯），也只有設定了鎖才會等或拒絕（b 錯）。兩個 apply 各自讀到同一份舊 state、各自成功呼叫 AWS（c 錯），寫回 state 時互相不知道對方，結果有資源不在任何一份 state 裡，成了沒人管的孤兒。遠端 backend 的鎖讓第二個 apply 直接報「state 被鎖住」，等第一個做完再重新 plan。

常見錯誤

  • 提交 terraform.tfstate 或 .terraform/：state 有機密明文、多人會互相覆蓋；.terraform/ 是下載的 provider。.gitignore 排除這些，state 放遠端 backend 加鎖。
  • 沒有提交 .terraform.lock.hcl：每台電腦、每次 CI 可能裝到不同的 provider 版本，同一份程式碼算出不同的 plan。提交它，升級時用 tofu init -upgrade 並透過 PR 更新。
  • 在主控台手動改 IaC 管理的資源：下一次 apply 會把改動還原。改程式碼走 PR；緊急手動改了就立刻補 PR，並排程 plan 抓漂移。
  • 沒看 plan 就 apply、正式環境用 -auto-approve：一個 -/+ 就是一次停機或一個空的資料庫。PR 貼 plan、審查 -/+ 和 -，正式環境 apply 審查過的 plan 檔。
  • 以為 replace 只是 update：哪些屬性會強制重建由 provider 決定，看 plan 上的 # forces replacement；在 docker provider 裡改容器的 env 就是重建。
  • 把機密寫在變數的 default 或 .tfvars 裡進 git：用 TF_VAR_ 環境變數或 secret manager 傳入，變數加 sensitive。記得 sensitive 只遮輸出，state 還是要保護。
  • 映像或 module 用會移動的版本：latest、沒有 version 的 module，今天和明天 plan 出來的東西不同。映像用 digest、provider 與 module 鎖版本。
  • 一個巨大的 state 管所有環境：plan 慢、鎖住所有人、一次錯誤影響全部。每個環境各自的根目錄與 state，再按變動頻率分層。
  • 加了 state 加密卻沒保管好 passphrase：解不開的 state 等於沒有 state。passphrase 或 KMS 金鑰的保管與輪替要跟資料庫備份同等級。

小結

  • IaC 用程式碼描述基礎設施：有紀錄、能審查、能重現。宣告式寫最後的樣子，工具算步驟；冪等代表第二次 plan 沒有變更。
  • HCL 的骨架：terraform（required_providers 鎖版本）、provider、variable（sensitive、validation）、locals、resource、output；引用決定相依圖與建立順序。
  • 流程是 init → fmt → validate → plan → apply。+ 建立、~ 原地更新、-/+ 重建（停機、可能遺失資料）、- 刪除；-detailed-exitcode 的 2 代表有變更。
  • state 記錄管理的資源，含機密明文：不進 git、放遠端 backend、一定要鎖；OpenTofu 可以把 state 與 plan 加密並 enforced。
  • 漂移由 plan 發現：改動錯了就 apply 還原，對了就寫回程式碼；既有資源用 import 納管。
  • module 是可重用的一組資源；每個環境各自的 state 與變數。Terraform（BSL 1.1）與 OpenTofu（MPL-2.0）語法大多相容，各自有獨有功能。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：咖啡店上了 AWS：ALB 跨兩個 AZ，Fargate task 在 1a、1c 各一個；為了省錢，RDS 沒開 Multi-AZ，只在 1a。1a 停電時會怎樣？

✓ c。AZ 是故障單位，只放在一個 AZ 的東西會跟著它停；高可用要每一層都跨 AZ，資料庫這層就是 Multi-AZ。a 錯在只看 app 這層：task 跨 AZ 了，它依賴的資料庫沒有。自動切換到另一個 AZ 正是 Multi-AZ 買的東西，單一 AZ 的 RDS 只能自己從備份還原。（第 18 課）

練習 9：db-sg 的規則寫「5432，來源 10.20.0.0/16」（整個 VPC 的 CIDR），理由是 Fargate task 的 IP 會變。哪裡會出事？

✓ a。路由決定有沒有路，安全群組決定門開不開；私有子網路只擋住網際網路，擋不住 VPC 裡的其他機器。來源寫 app-sg，意思是「掛著 app 安全群組的才能連」，只放行真的需要的那一層。d 錯在把私有子網路當成唯一的防線，被入侵的跳板機、測試機一樣在 VPC 裡。（第 18 課）

練習 10：cafe-api 讀 S3 時收到 AccessDenied，訊息結尾是 with an explicit deny in a service control policy。同事說：「在 role 的政策加一條 Allow s3:GetObject 就好。」該怎麼回？

✓ d。評估規則是有任何符合的 Deny 就拒絕，跟寫得多具體、排第幾條都無關（a、b 錯）。訊息說 Deny 在 SCP 裡，不在你正在看的政策，要請組織管理者確認這個例外該不該開。c 錯在聯集只發生在 Allow 之間，SCP 是上限，bucket policy 加 Allow 也越不過去。（第 19 課）

練習 11：平台團隊讓開發者能自己開 EC2，給了 ec2:RunInstances 與 iam:PassRole，Resource 都是 *。開發者本身沒有 S3 或 IAM 的權限。哪裡會出事？

✓ b。PassRole 是「把某個 role 交給 AWS 服務去用」，給 * 就是任何 role 都能交，機器上的程式再透過 instance profile 拿到那個 role 的臨時憑證，變相提權。修法是 Resource 寫具體的 role ARN，加 iam:PassedToService 條件。a 錯在機器的權限來自掛上去的 role，不是開機器的人。（第 19 課）

練習 12：cafe-deploy-prod 的信任政策檢查了 aud，sub 用 StringLike 寫成 repo:cafe-org/cafe-api:*。同事說：「已經限定只有我們的 repo，夠安全了。」漏洞在哪？

✓ c。sub 是唯一能區分 repo、分支、environment 的欄位，結尾的 * 等於放行這個 repo 的所有 job。改成 StringEquals 綁 environment:production，再在 GitHub 把 production environment 設成需要核准、只允許 main，誰能拿到 production 權限就由核准流程把關。a 錯在只防了別的 repo，沒防自己 repo 裡還沒審過的分支。（第 19 課）

練習 13：PR 只改了 aws_s3_bucket.uploads 的一個屬性，plan 的最後一行是 Plan: 1 to add, 0 to change, 1 to destroy.。審查的人說：「0 to change，一個加一個減，沒動到既有的東西。」怎麼看？

✓ a。重建在總計裡算一次 add 加一次 destroy，不算 change；看到 destroy 不是 0，就逐一找出是哪個資源、是不是 -/+。bucket、資料庫、volume 被重建，裡面的資料一起消失，OpenTofu 不會替你搬資料（d 錯）。b 錯在只看了 change 那一欄，審 plan 的重點是有沒有 -/+ 和 -。（第 20 課）

練習 14：放 state 的 S3 bucket 已經封鎖公開、開了版本控制。為了讓大家能在本機跑 plan，平台團隊給全體開發者這個 bucket 的 s3:GetObject，所有機密變數也都標了 sensitive = true。哪裡會出事？

✓ d。資源的屬性有什麼，state 就存什麼；sensitive 只遮住畫面上的輸出，state 照樣是明文（a 錯）。只讓部署用的 role 讀得到這個 bucket，plan 交給 CI 在 PR 上跑，再加上 OpenTofu 的 state 加密，權限設錯時外流的也只是密文。c 錯在讀權限本身就是外洩：拿到密碼就能直接連資料庫，用不著改 state。（第 19、20 課）

練習 15：咖啡店的 staging 與正式環境、網路、資料庫、所有服務都寫在同一個根目錄，共用一份 state。資源名稱都有環境前綴，從來沒有撞名。這樣的問題是什麼？

✓ b。一份 state 就是一把鎖、一次 plan 要查所有資源、一個錯誤的 apply 影響範圍是全部。每個環境各自的根目錄、state 與 backend key，再按變動頻率分層（網路、資料庫、應用程式），共用的東西抽成 module。c 錯在前綴只避免撞名，鎖、plan 範圍與出錯的影響範圍都還是同一份。（第 20 課）
