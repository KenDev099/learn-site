階段 1：伺服器基本功 · 第 2 課

Shell 基本功：檔案、管線、權限與腳本

晚上十點，咖啡店的 API 開始回 502。你登入伺服器，眼前只有一個黑色視窗和一個閃爍的游標：沒有 VS Code、沒有檔案總管、沒有滑鼠。要從十萬行的 access log 裡找出是哪個路徑在出錯、確認設定檔是不是被改壞了權限、把出問題前的設定備份下來，全都要靠打指令。

這一課教你在 Linux 上靠指令做事。後面每一課的 Dockerfile、CI 設定、部署腳本，用的都是這一課的東西。

這課的路線：
  1. shell 與檔案系統地圖：shell 替你做了什麼，伺服器上的設定、log、程式各放在哪裡。
  2. 指令、資料流與重新導向：一行指令怎麼被找到並執行，正常輸出和錯誤訊息怎麼分開存、怎麼接給下一個程式。
  3. 文字處理流水線：半夜 API 回 502 時，幾秒內從十萬行 access log 找出哪個路徑在出錯。
  4. 權限：誰能讀、寫、執行，密碼檔和跑服務的帳號該給多少權限。
  5. 腳本與 macOS／Linux 的差異：寫一個一出錯就停、不會默默留下爛攤子的腳本，以及為什麼在 Mac 上能跑的腳本到伺服器會壞。
這課會用到：
  • Node 課第 2 課的程序三件事：每個程序有標準輸入／輸出／錯誤三條資料流、讀得到環境變數，結束時留下結束碼（exit code，0 是成功）。
  • 第 1 課的 docker run --rm -it：開一台用完即丟、可以互動打指令的 Linux 容器。

為什麼後端要會 shell

shell 是一個程式：它讀你打的指令、找到對應的程式並執行，再把結果顯示出來。常見的有 bash、zsh、sh。終端機（terminal）則是顯示 shell 的那個視窗。你在 Mac 的「終端機」App 裡打字，接收的是 zsh；你 SSH 到伺服器，接收的通常是 bash。

後端工程師離不開 shell，因為：

  • 伺服器多半沒有圖形介面，登入後只有 shell。
  • Dockerfile 的 RUN（第 8 課）、GitHub Actions 的 run:（第 15 課）、部署和備份腳本，裡面寫的都是 shell 指令。
  • 出事時最快的診斷工具是 grep、tail、awk 這些小程式，組合起來幾秒鐘就能回答「哪個路徑在噴錯」。

伺服器上缺工具時，用套件管理器（package manager）安裝，它負責下載程式、處理相依性。Debian／Ubuntu 用 apt-get，Alpine（很多 Docker 映像的基底）用 apk：

apt-get update && apt-get install -y --no-install-recommends jq   # Debian／Ubuntu
apk add --no-cache jq                                             # Alpine

-y 是不問直接裝（腳本裡沒有人能按 Y），--no-install-recommends 只裝必要的相依套件，--no-cache 不留下套件索引。後兩個都是為了讓映像小一點，第 8 課會再看到。

這一課的指令都可以在 Debian 容器裡試，先開一台：

docker run --rm -it debian:trixie-slim bash

檔案系統地圖

Linux 的所有檔案都掛在一棵樹上，樹根叫 /。沒有 C 槽、D 槽，外接硬碟也只是掛在樹上的某個資料夾。幾個你會常去的地方：

指定一個檔案有兩種寫法：

  • 絕對路徑：從 / 開始，例如 /var/log/nginx/access.log，在哪裡執行都指向同一個檔案。
  • 相對路徑：從目前所在的資料夾開始，例如 nginx/access.log。. 是目前資料夾、.. 是上一層、~ 是家目錄。

腳本裡盡量用絕對路徑，或先 cd 到確定的地方：腳本被誰、從哪裡執行，你控制不了。

pwd                 # 目前在哪個資料夾
cd /var/log         # 移動過去
ls -la              # 列出所有檔案，含隱藏檔（. 開頭）和詳細資訊
cat /etc/hostname   # 印出檔案內容
less /etc/passwd    # 一頁一頁看（q 離開）
tail -f access.log  # 持續印出新寫進來的行（Ctrl+C 停止）

ls -la 每一行長這樣：

-rw-r--r-- 1 root root 13 Oct 31 15:58 hostname

從左到右：類型與權限（第一個字元 - 是檔案、d 是資料夾，後面九個字元是權限，等一下拆解）、連結數、擁有者、群組、大小（位元組）、最後修改時間、名稱。

指令怎麼被找到：選項、參數與 PATH

一行指令由三種東西組成：

grep  -n  ' 502 '  access.log
程式  選項  參數     參數

選項（option）以 - 或 -- 開頭，改變程式的行為；其他的是參數（argument），通常是要處理的東西。不知道有哪些選項時，看 grep --help 或 man grep（說明手冊，Docker 的精簡映像常常沒裝）。

你打 grep，shell 怎麼知道程式在哪？它依序搜尋環境變數 PATH 列出的資料夾，用第一個找到的：

echo "$PATH"     # /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
which grep       # /usr/bin/grep：會執行的是哪一個檔案
type cd          # cd is a shell builtin：shell 自己內建的指令，沒有對應的檔案

「command not found」只有兩種原因：沒安裝，或裝了但它的資料夾不在 PATH 裡。cd 一定是內建的：它要改變 shell 自己的目前資料夾，另外開一個程式做不到。

以 - 開頭的檔名會被當成選項：chmod 600 -deploy.pem 會得到 chmod: invalid option -- 'd'。對付它有兩種寫法：chmod 600 -- -deploy.pem（-- 表示選項到此結束），或 chmod 600 ./-deploy.pem（加上路徑，就不是 - 開頭了）。

資料流與重新導向

Node 課第 2 課教過，每個程序一開始就有三條資料流：標準輸入（stdin，編號 0）、標準輸出（stdout，1）、標準錯誤（stderr，2）。程式的正常結果寫到 stdout，錯誤訊息寫到 stderr，兩條預設都顯示在終端機上，所以平常分不出來。shell 可以把它們接到別的地方：

寫法意思
a | b管線（pipe）：a 的 stdout 接到 b 的 stdin，兩個程式同時執行
cmd > f重新導向（redirect）stdout 到檔案，先清空再寫
cmd >> f附加到檔案尾端
cmd 2> fstderr 寫到檔案
cmd > f 2>&1stdout 和 stderr 都寫到 f
cmd < fstdin 從檔案讀
cmd | tee f同時顯示在畫面並寫進檔案
cmd > /dev/null丟掉輸出（/dev/null 是寫什麼都會消失的特殊檔案）

2>&1 的意思是「把 2 號接到 1 號現在接的地方」。shell 由左到右處理重新導向，所以順序會改變結果：

ls /nope > out.txt 2>&1    # 先把 1 接到檔案，再把 2 接到 1 現在的地方（檔案）：錯誤進檔案
ls /nope 2>&1 > out.txt    # 先把 2 接到 1 現在的地方（終端機），再把 1 改接檔案：錯誤還是印在畫面，檔案是空的

另一個陷阱：sort f > f 會得到空檔案。shell 在執行 sort 之前就先把 f 清空了，sort 讀到的是空的。要寫回原檔，先寫到另一個檔案再改名（後面的「原子寫入」）。

文字處理流水線：從 access log 找出錯的路徑

nginx 每處理一個請求，就在 access log 寫一行。預設的 combined 格式長這樣：

203.0.113.7 - - [31/Oct/2026:09:15:02 +0800] "POST /uploads HTTP/1.1" 502 157 "-" "curl/8.7.1"

用空白切開，每一欄是什麼：

欄位（awk 的編號）例子意思
$1203.0.113.7來源 IP（發出請求的那台電腦）
$2 $3- -$2 固定是 -；$3 是 HTTP 認證的使用者名稱，沒有就是 -
$4 $5[31/Oct/2026:09:15:02 +0800]時間（中間有空白，算兩欄）
$6 $7 $8"POST /uploads HTTP/1.1"請求行：方法、路徑、協定
$9502狀態碼
$10157回應大小（位元組）
其餘"-" "curl/8.7.1"Referer（從哪個頁面連過來）、User-Agent（發出請求的程式，例如瀏覽器或 curl）

問題：「哪幾個路徑回最多 5xx？」一步一步組管線，每加一段就先執行看看：

awk '$9 ~ /^5/ { print $7 }' access.log     # 只留狀態碼 5 開頭的行，印出路徑
  | sort                                      # 排序，讓相同的路徑相鄰
  | uniq -c                                   # 合併相鄰的重複行，前面加上次數
  | sort -k1,1nr -k2,2                        # 依次數（數字、由大到小），同次數依路徑
  | head -n 3                                 # 前 3 名

（實際要寫在同一行，或在行尾加 \ 接到下一行，這裡為了加註解才分開。）

  • awk 把每行依空白切成 $1、$2…，條件 { 動作 } 對符合條件的行做動作。$9 ~ /^5/ 是「第 9 欄符合正規表示式 ^5」。
  • uniq -c 只合併相鄰的重複行，所以前面一定要先 sort。
  • sort -k1,1nr：-k1,1 只看第 1 欄，n 當數字比，r 反過來。不加 n 會變成字串比較，"9" 排在 "10" 後面。

為什麼不用 grep ' 5'？它找的是「整行任何地方有空白加 5」：回應大小 512、路徑 /orders/500 的 200 請求都會被抓進來。要比對欄位，就用懂欄位的工具。同理，算行數用 wc -l，只取某幾欄用 cut -d' ' -f7。

同次數怎麼排：只寫 sort -rn 時，次數相同的行會整行比字串、再整個反過來，路徑變成由大到小（Z 在前）。每天的 log 不一樣，這種「看起來對」的排序很難發現。要穩定的結果，就把第二排序條件明確寫出來：-k2,2。

Node 課第 19 課的 pino 寫的是一行一個 JSON 的結構化 log，這時不要用 awk 切空白，改用專門處理 JSON 的 jq：

jq -r 'select(.status >= 500) | .path' app.log | sort | uniq -c | sort -k1,1nr -k2,2

select(…) 留下符合條件的物件，.path 取欄位，-r 印出不帶引號的字串。欄位有名字，不怕順序或空白改變。

💡 實務上：事故當下，管線常常比儀表板快
客服說「剛剛很多人結帳失敗」，集中 log 平台還沒建好或查詢很慢時，登入機器用 grep、awk、sort | uniq -c 幾秒鐘就能數出哪個路徑在出錯。要注意出問題的機器已經很吃力，不要在上面對好幾 GB 的檔案跑沉重的指令：先用 tail -n 取最近一段，或把檔案複製出來再分析。查到結論的那串指令，順手貼進事故紀錄（第 25 課），別人才能重現。

權限：誰能讀、寫、執行

Linux 是多使用者系統，每個檔案都記錄它的擁有者（user）和群組（group），並對三種人各給三種權限（permission）：

對檔案對資料夾八進位
r 讀讀內容列出裡面有哪些檔名4
w 寫修改內容在裡面新增、刪除、改名2
x 執行當成程式執行進入它、存取裡面的檔案1

-rw-r--r-- 去掉第一個字元，三個一組：擁有者 rw-、群組 r--、其他人 r--。每組把數字加起來：rw- = 4+2 = 6、r-- = 4，所以是 644，只有擁有者能寫。常見的組合：

數字樣子用在
644rw-r--r--一般檔案：大家可讀、只有擁有者能改
755rwxr-xr-x資料夾、腳本與程式
600rw-------私鑰、.env 這類 secret：只有擁有者能讀寫
 
chmod 600 cafe.pem          # 設成 600
chmod u+x deploy.sh         # 只幫擁有者（u）加上執行權限；g 是群組、o 是其他人
chown cafe app.env          # 擁有者改成 cafe（要 root）
chown cafe:cafe app.env     # 擁有者和群組都改

SSH 會拒絕權限太寬的私鑰：私鑰別人讀得到，就等於沒有保密，第 6 課會碰到。

root 是 Linux 的超級使用者（使用者編號 uid 是 0），不受檔案權限限制，可以讀寫任何檔案。sudo 讓一般使用者用 root（或其他使用者）的身分執行一個指令，而且會記錄誰在什麼時候做了什麼。正式環境的做法是最小權限（least privilege）：服務用專屬的一般使用者（例如 cafe）執行，只能讀它需要的檔案；被入侵時，攻擊者拿到的也只是這個使用者的權限。

遇到 Permission denied 就 chmod 777（所有人可讀寫執行）等於把保護整個關掉；什麼都用 sudo 跑，建出來的檔案擁有者會是 root，之後服務自己的使用者改不動。先用 ls -l 看是誰擁有、誰需要存取，再給剛好夠的權限。

寫一個不會騙人的腳本

把指令存成檔案就是腳本。問題是 shell 的預設行為非常寬容：某一行失敗了，它照樣往下跑，最後回報成功。備份腳本「成功」了半年，要還原時才發現每一份都是空的，這種事真的會發生。

#!/usr/bin/env bash
set -euo pipefail

第一行是 shebang：直接執行 ./backup.sh 時，核心用它決定交給哪個程式解讀。/usr/bin/env bash 是「在 PATH 裡找 bash」，比寫死 /bin/bash 好搬家。第二行是三個保護（依 GNU bash 手冊的 set 內建指令）：

設定效果擋下什麼
-e指令回傳非 0 就立刻結束失敗後繼續往下跑
-u用到沒設定的變數就結束變數名稱打錯、忘了傳參數
-o pipefail管線裡任何一段失敗，整條管線就算失敗管線前段失敗被後段蓋掉

為什麼需要 pipefail？管線的結束碼預設只看最後一段：

set -e
false | true
echo "還在跑"                 # 會印出來：false | true 的結束碼是 true 的 0

set -o pipefail
false | true; echo "$?"      # 1

-e 也有不管的地方：if 的條件、&& 和 || 左邊的指令、用 ! 反轉的指令失敗時，腳本都不會停。這些位置的失敗本來就是「預期中可能發生」的。

結束碼：0 是成功，非 0 是失敗，$? 是上一個指令的結束碼。a && b 是 a 成功才跑 b，a || b 是 a 失敗才跑 b。

變數一定加引號

f="my secret.env"
chmod 600 $f       # 變成 chmod 600 my secret.env：兩個參數，兩個都找不到
chmod 600 "$f"     # 一個參數：my secret.env

沒加引號的變數會被 shell 依空白切開，裡面的 * 也會被展開成檔名。最可怕的例子：

rm -rf $DIR/*                   # DIR 沒設定時，展開成 rm -rf /*
rm -rf "${DIR:?DIR 沒設定}"/*   # DIR 是空的或沒設定就印出訊息並結束，rm 根本不會執行

GNU 的 rm 預設會拒絕 rm -rf /（印出 it is dangerous to operate recursively on '/'），但 /* 在 rm 執行之前就被 shell 展開成 /bin /boot /etc /home …，rm 收到的是一串正常的資料夾，照刪不誤。set -u 擋得住「沒設定」，擋不住「設成空字串」；${DIR:?訊息} 兩種都擋。

原子寫入：先寫暫存檔，成功才改名

tar … | gzip > backup.tar.gz 一開始就把舊的備份清空，寫到一半失敗，留下的是一個壞掉的檔案，舊的那份也沒了。安全的做法是寫到旁邊的暫存檔，全部成功才用 mv 換上去：

tmp="$(mktemp "$out.XXXXXX")"    # 在輸出檔旁邊建一個名稱唯一的暫存檔
trap 'rm -f "$tmp"' EXIT         # 腳本不管怎麼結束，都刪掉暫存檔
tar -cf - -C "$src" . | gzip > "$tmp"
mv "$tmp" "$out"

同一個檔案系統裡的 mv 只是改名，是原子的（atomic）：別人看到的要嘛是舊檔，要嘛是完整的新檔，不會看到寫一半的。所以暫存檔要放在輸出檔旁邊，放到 /tmp 可能是不同的檔案系統，mv 會退化成複製。$(指令) 叫命令替換（command substitution）：先執行括號裡的指令，再把它印出的內容放回這個位置，所以 tmp 拿到的是 mktemp 建出來的檔名；外面加雙引號的理由跟變數一樣。trap … EXIT 註冊一段在 shell 結束時執行的指令。第 24 課的資料庫備份腳本會用到同樣的寫法。

💡 實務上：放進 repo 的腳本就是正式程式
部署、備份、清理這類腳本會在半夜被排程或 CI 執行，沒有人盯著看。所以它們要跟應用程式一樣進 git、經過 PR 審查、開頭寫 set -euo pipefail，並用 ShellCheck（專門檢查 shell 腳本常見錯誤的工具）掃過。腳本開始需要解析 JSON、處理很多分支或重試時，改用 Node 寫通常比較好維護，團隊裡每個人都看得懂。

macOS 和 Linux 不一樣

你的 Mac 和伺服器都有「shell」，但不是同一套：

macOS 27Debian trixie 伺服器Alpine 容器
互動 shellzsh（預設）bashsh（BusyBox ash）
bash --version/bin/bash 是 3.2.575.2.37預設沒有 bash
/bin/shbash 3.2（以 sh 模式執行）dashBusyBox
sed、grep、sort…BSD 版本GNU 版本BusyBox 版本

macOS 內建的 bash 停在 3.2，缺少 bash 4 以後才有的關聯陣列（declare -A）、globstar（** 遞迴比對）等功能，在 Mac 上執行會直接報 invalid option。BSD 和 GNU 工具的選項也有差：GNU 的 sed -i 's/a/b/' f 直接改檔；BSD 的 -i 一定要接備份副檔名，要寫成 sed -i '' 's/a/b/' f，照 GNU 的寫法在 Mac 上會報錯。另外 sh 不一定是 bash：Debian 的 /bin/sh 是 dash、Alpine 是 BusyBox，[[ … ]]、陣列這些 bash 語法用 sh script.sh 執行會得到 [[: not found 這類錯誤；在 Mac 上 sh 剛好是 bash，所以本機測不出來。

所以這門課的腳本一律寫 #!/usr/bin/env bash、用 bash 執行，而且在 Debian 容器裡跑，用的是跟伺服器一樣的 GNU 工具和 bash 5.2。練習的測試也這樣做。

docker run --rm -v "$PWD":/w -w /w debian:trixie-slim bash top-errors.sh access.log

練習 1：完成 top-errors.sh：讀取第一個參數指定的 nginx combined 格式 access log，印出 5xx 次數最多的前 3 個路徑，每行「次數 路徑」（例如 5 /orders），次數相同時依路徑由小到大排序。測試會先跑附的 access.log，再跑一份當場產生、放在 /tmp/my logs/（路徑有空白）的 log；裡面有 4xx 很多的路徑、回應大小是 5xx 開頭的 200 請求、路徑含 500 的請求，還有同次數的路徑。

練習 2：完成 fix-perms.sh <資料夾>：遞迴處理資料夾（包含它自己），資料夾設成 755、*.sh 755、*.env 和 *.pem 600、其他檔案 644，並把 *.env 的擁有者改成 cafe，其他保持原本的擁有者。測試在容器裡以 root 建一棵新的資料夾樹 /srv/cafe app：有多層資料夾、空資料夾、檔名有空白的 my secret.env、以 - 開頭的 -deploy.pem，還有隱藏檔 config/.env（*.env 也要包含它）和不算 .env 的 notes.env.bak。提示：find "$dir" -type f -name '*.sh' -exec chmod 755 {} + 會把找到的每個路徑原封不動地當成參數交給 chmod。

練習 3：修好 backup-config.sh <來源資料夾> <輸出檔>（把設定資料夾打包成 tar.gz）。要求：正常時結束碼 0、產生解得開的備份；任何一步失敗都以非 0 結束，輸出檔所在的資料夾不能留下半成品或暫存檔；如果原本就有一份舊備份，失敗時舊備份要原封不動。測試會跑四種情境：正常、來源資料夾不存在、已經有舊備份時來源資料夾不存在，以及用一般使用者 cafe 執行、來源裡有一個它讀不到的 secret.key（tar 會失敗，但 gzip 照樣成功，而且已經有舊備份）。只檢查「來源資料夾存在」擋不住最後一種。

練習 4：腳本開頭只有 set -e，其中一行是 grep foo missing.txt | wc -l，而 missing.txt 不存在。腳本會怎樣？

✓ 沒有 pipefail 時，管線的結束碼只看最後一段。grep 失敗了，但 wc -l 成功印出 0，整條管線回 0，set -e 不會觸發。set -e 也不管 if 條件、&& 和 || 左邊的失敗。shell 判斷成敗只看結束碼，不看 stderr 有沒有輸出。

練習 5：清理腳本裡有一行 rm -rf $DIR/*，某次執行時 DIR 沒有設定，而且腳本沒有 set -u。會發生什麼？

✓ 沒設定的變數預設展開成空字串，$DIR/* 就成了 /*，shell 再把它展開成 /bin /etc /home … 交給 rm。GNU rm 的保護只擋得住參數剛好是 /，擋不住這一串正常的資料夾（a 錯）；刪的是根目錄底下，不是目前資料夾（b 錯）；bash 只有在 set -u 時才會因為沒設定的變數停下來（d 錯）。就算有 set -u，DIR 被設成空字串也擋不住，所以寫成 "${DIR:?DIR 沒設定}"/*，空的或沒設定都會中止。

練習 6：ls -l 顯示 -rw-r--r-- 1 cafe cafe … menu.json。這是八進位的多少？誰能修改它？

✓ 去掉開頭的 - 之後三個一組：rw-（4+2=6）、r--（4）、r--（4），所以是 644。只有第一組有 w，代表只有擁有者能寫；群組和其他人的 r-- 只能讀。（root 不受權限限制，這是例外。）

常見錯誤

  • 變數不加引號：檔名有空白會被切成兩個參數，* 會被展開。一律寫 "$var"。
  • 以為 set -e 擋得住所有錯誤：管線前段、if 條件、&&／|| 左邊的失敗都不會讓腳本停。加上 -o pipefail，並且別用 || true 把真正的錯誤吞掉。
  • 直接寫到最終檔名：失敗時留下半成品，還毀掉舊的那份。寫到旁邊的暫存檔，成功才 mv，用 trap 清掉暫存檔。
  • 用 chmod 777 解決權限問題：等於關掉保護。看清楚擁有者和需要的權限，給剛好夠的。
  • chmod -R 644 整個資料夾：資料夾也失去 x，一般使用者進不去。資料夾和檔案要分開設（find -type d／-type f）。
  • 什麼都用 sudo 跑：root 建出的檔案，服務自己的使用者之後改不了，也讓一個打錯的指令能破壞整台機器。
  • cmd 2>&1 > file 以為錯誤也進了檔案：重新導向由左到右處理，要寫成 cmd > file 2>&1。
  • 用 grep 找某一欄的值：grep ' 5' 會抓到大小、路徑、IP 裡的 5。比對欄位用 awk 或 jq。
  • Mac 上寫好的腳本直接搬到 Linux：bash 3.2 對 5.2、BSD 對 GNU 的選項差異（sed -i）。在跟伺服器一樣的容器裡測試。

小結

  • shell 讀指令、依 PATH 找程式來執行；Linux 的檔案都在 / 底下：/etc 設定、/var/log 記錄、/usr/bin 程式。
  • stdout、stderr 是兩條不同的資料流；| 只接 stdout；> file 2>&1 的順序有意義。
  • 處理 log 的套路：awk 取欄位 → sort → uniq -c → sort -k1,1nr -k2,2 → head；JSON log 用 jq。
  • 權限三組 rwx：644 一般檔案、755 資料夾與腳本、600 secret；資料夾的 x 是「能不能進去」。服務用專屬的一般使用者跑。
  • 腳本開頭 #!/usr/bin/env bash 加 set -euo pipefail，變數加引號，寫檔用暫存檔加 mv。
  • macOS 是 zsh、bash 3.2、BSD 工具；伺服器是 bash 5.2、GNU 工具。腳本在跟伺服器一樣的容器裡測。
