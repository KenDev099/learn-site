階段 7：期末專題 · 第 26 課

期末專題：把咖啡店 API 安全地送上線並維運

前面 25 課各自練了一塊：映像、Compose、設定與 secret、nginx、擴展、CI／CD、migration、log、指標、trace、備份、告警。真正上線時，這些東西要一起運作，而且常常在接縫處出事：映像的 HEALTHCHECK 打錯路徑，Compose 就一直等不到 healthy；nginx 的限流設太嚴，壓測先被自己擋掉；runbook 寫的腳本名稱跟 repo 裡的對不上，半夜照著做才發現。

這一課是期末專題：在你的 Mac 上組出一套類正式環境（production-like：盡量和正式環境一樣的本機或 staging 環境）。每一步都有自動檢查，五題全部通過，就等於通過一次上線準備度檢查。

這課的路線：
  1. 從需求到數字、架構與決策紀錄：把老闆的「推播之後不能掛」換成可以檢查的數字，畫出架構，把「為什麼這樣選」寫成 ADR。
  2. 映像與類正式環境：建出查得到來源的映像，組出 TLS 反向代理、藍綠兩組 api、只能讀寫資料的資料庫帳號、Redis 的 compose.prod.yaml。
  3. 部署、回滾與失敗的時候：在持續的流量下部署和回滾，跑到一半失敗時線上什麼都沒壞。
  4. 壓測驗收：用壓測證明這套環境撐得住尖峰，沒過時從數字找出瓶頸。
  5. 文件、上線準備度檢查與還差什麼：寫出別人半夜照著做就能維運的 runbook，逐項確認可以上線，以及跟真正的正式環境還差哪些。
這課會用到：
  • 第 10 課的 Compose：healthcheck 判斷容器是否真的能服務，depends_on 等前一個服務 healthy 才啟動，--wait 等全部就緒才回來。
  • 第 16 課的藍綠部署：新版在另一個顏色啟動、通過檢查才切 nginx 的 upstream，舊顏色留著，回滾就是切回去。
  • 第 17 課的部署前 migration：一次性 job 用專門的帳號套用 migration，成功才換程式；app 帳號只能讀寫資料。
  • 第 22 課的 SLO 與壓測門檻：用 k6 打出尖峰流量，p95、錯誤率沒達到 SLO 就不能上線。

從需求到數字

老闆不會說「我要 99.9% 的可用性」，他會說「推播之後不能掛」。工程師的第一件事，是把這種句子換成可以量、可以檢查的數字。練習資料夾裡的 NEEDS.md 是開會的結論：

咖啡店的上線需求
  1. 會員與集點卡下個月上線，行銷會在週末早上推播，預估尖峰流量是現在的三倍。
  2. 不能為了部署停機，營業時間也要能上新版本。
  3. 訂單資料遺失不能超過 15 分鐘。
  4. 系統壞了，要在 5 分鐘內有人知道；1 小時內要恢復服務。
  5. 新來的工程師照著文件就能部署、回滾、還原。
需求換成的數字或做法哪一課
推播之後不能掛現在尖峰每秒 12 個請求 × 3 = 每秒 36 個；壓測要在這個到達率下 p95 < 300ms、錯誤率 < 0.1%第 13、22 課
不能停機部署藍綠部署、排空、部署前跑向後相容的 migration第 13、16、17 課

容量也要先算過。第 13 課的公式：同時在處理的請求數 ≈ 到達率 × 每個請求的耗時。每秒 36 個、每個大約 0.05 秒，同一時間只有 2 個左右在處理，2 個 api 副本、每個連線池 8 條綽綽有餘。資料庫的連線預算也要算：藍綠兩組各 2 個副本，4 × 8 = 32 條，加上 migrate、備份、你自己連進去查問題的，都要在 PostgreSQL 預設的 max_connections 100 以內。之後擴展副本數時，這個總數是第一個會撞到的上限。

每 15 分鐘一次 pg_dump 在本機練習是 RPO 15 分鐘的近似：最壞會丟掉 15 分鐘的訂單，資料一大，pg_dump 本身也會跑很久。正式環境用 WAL 封存與 PITR，或 RDS 的自動備份（第 24 課、PostgreSQL 課第 37 課）。
💡 實務上：需求會議要帶著數字去，帶著數字回來
上線前通常會跟 PM、老闆、客服開一次會。資深工程師會先從 log 與指標查出現在的尖峰、錯誤率、延遲，再問「推播大概幾點發、發給多少人」「掛掉 10 分鐘的損失是多少」，把「不能掛」變成 SLO、RPO、RTO。「三倍」是估計，會議紀錄要寫下這個假設，上線後第一個尖峰就拿實際數字對照。每多一個 9、每少一分鐘 RPO 都要花錢，把成本跟老闆講清楚，比自己默默做到最好更重要。

架構與決策紀錄

畫完架構圖，要把「為什麼這樣選」寫下來。ADR（Architecture Decision Record，架構決策紀錄）是一份很短的文件，一個決策一份，固定三段：

  • 背景：當時的需求、限制、團隊狀況。半年後的人看不到當時的會議，只看得到這一段。
  • 決策：選了什麼，具體到看得出怎麼做。
  • 後果：好處，以及缺點與代價。只寫優點的 ADR 沒有用：沒寫出代價，之後的人不知道它在什麼情況下會出問題，也不知道什麼時候該換掉。最後加一句重新評估的時機，例如「服務超過三個時評估 Kubernetes」。

這個專題至少有四個值得記錄的決策：單機 Compose 還是 ECS／Kubernetes（第 13 課）、藍綠還是滾動更新（第 16 課）、pg_dump 還是 PITR（第 24 課）、購物車放 Redis 還是放記憶體（第 13 課）。DECISIONS.md 已經寫好 ADR-1 當範例。設計文件與 ADR 的完整寫法在 系統設計課第 18 課。

資深工程師最常犯的錯不是選錯工具，而是每一項都做到最複雜。兩個人維護一個服務，Kubernetes 的叢集升級、網路外掛、權限設定，會吃掉比服務本身更多的時間。依需求選最簡單、能滿足 SLO 與 RPO 的做法，在 ADR 裡寫清楚什麼時候要升級。

💡 實務上：ADR 放在 repo 裡，跟著 PR 審查
常見的做法是放在 docs/adr/0001-….md，跟程式碼一起走 PR，讓同事在決定之前提出反對意見。決定改變時不改舊的 ADR，而是寫一份新的，在舊的標上「已被 ADR-7 取代」，半年後的人才看得到為什麼換、換之前遇到什麼問題。新人到職、事故檢討、有人問「為什麼不用 Kubernetes」時，直接貼 ADR 的連結，比每次重新解釋省事。

映像與類正式環境

第一步是一個可以重現、可以追溯的映像（練習 1；Dockerfile 用第 9 課的多階段建置）。可以重現：同一個 commit 每次建出一樣的東西，npm ci 照 lockfile 裝、基底映像釘版本。可以追溯：從正在跑的容器反查是哪個 commit 建的，靠 org.opencontainers.image.revision label 與 /version。正式環境由 CI（第 15 課）建置、推到 registry，部署用 registry/cafe-api@sha256:… 這種 digest 參照（第 16 課）；這裡在本機建置，用 learn-devops/cafe-api:26-<版本> 代替。CI 的 workflow 在第 15、16 課寫過，這一課不再重寫。

第二步是 compose.prod.yaml（練習 2）。每一行設定都對應一個前面學過的理由：

設定沒有它會怎樣哪一課
api 用 cafe_app、migrate 用 cafe_migratorapi 被注入 SQL 時可以 DROP TABLE第 17 課
密碼用 secrets 掛檔案、DB_PASSWORD_FILEdocker inspect 就看得到密碼第 11 課
db、redis 不寫 ports資料庫直接暴露在主機的網路上第 10 課

nginx 的設定（nginx/default.conf，第 12 課）是流量入口：80 port 一律 301 轉到 HTTPS；HSTS 標頭只加在 HTTPS 的 server（瀏覽器會忽略 HTTP 回應裡的 HSTS，放錯地方表示設定位置沒想清楚）；client_max_body_size 5m（預設只有 1m，4MB 的上傳會被擋）；limit_req 限制同一個 IP 的速度，超過回 429（預設是 503，會被誤認成伺服器壞了）；/metrics 不對外，Prometheus 在內部網路直接抓 api:3000/metrics。

upstream 寫在另一個檔 nginx/active.conf，裡面的 server api-blue:3000 resolve 讓 nginx 定期向 Docker 內建的 DNS（127.0.0.11）重新查詢，副本增減時自動更新名單。resolve 參數在 nginx 1.27.3 之前只有商業版有，這裡用的 1.30.6 開源版可以用；它要搭配 zone（名單放在共用記憶體）與 resolver。

Docker 的 DNS 只要容器在跑就會回它的 IP，不管 healthcheck 過了沒有；開源版 nginx 也沒有主動健康檢查，只會在請求失敗後暫時跳過那個副本。所以直接擴充「正在接流量的那一組」時，新副本還在啟動就會收到請求。這套環境的擴容方式是：把新的副本數部署到待命的那一組，檢查過再切換。雲端的負載平衡器（例如 AWS ALB）會主動打健康檢查，新目標通過才加入，這是正式環境和本機的差距之一。

部署、回滾與失敗的時候

deploy.sh 是第 16 課藍綠部署的延伸，多了 Compose 與 migration。步驟：

  1. 從 nginx/active.conf 判斷現在接流量的顏色（old）與要部署的顏色（new）。
  2. 用新映像跑一次 migrate：MIGRATE_IMAGE="$image" docker compose -f compose.prod.yaml run --rm --no-deps migrate。失敗就停，流量不動。migration 一定要向後相容（第 17 課的 expand），因為接下來有一段時間舊版本還在服務。
  3. 把新映像寫進 .env 的 BLUE_IMAGE 或 GREEN_IMAGE，up -d --no-deps --force-recreate --wait api-<new>。寫進 .env 是為了讓「現在跑的是哪個版本」只有一個答案，之後任何人執行 docker compose 都不會意外換掉它。
  4. 健康關卡：新顏色的每個副本 /health/ready 都回 200（暖機完成、資料庫與 Redis 連得上、這個版本需要的 migration 都在），再做一次煙霧測試 GET /products。容器 healthy 只代表 /health/live 通過、程序活著；這套 api 啟動後還要暖機幾秒（建立連線池、載入快取），這段時間它會回 503，只看 healthy 就切流量，使用者會先吃到一串錯誤。
  5. 改寫 active.conf，nginx -t 通過才 nginx -s reload；沒過就把檔案改回去。
  6. 舊顏色留著不動，rollback.sh 先確認另一個顏色的副本都在跑而且 ready，再把 active.conf 改回去、reload，幾秒內完成。另一個顏色不在時，它要拒絕切換，不能把流量送進空的名單。

任何一步失敗都以非 0 結束，而且流量留在原本的顏色。部署腳本最重要的性質不是「成功時很順」，而是失敗時什麼都沒壞。練習 3 會用一個 migration 會失敗的 3.0.0 測這件事。

出事時先回滾還是先修？先回滾。回滾是演練過、幾秒就完成的動作；hotfix 要寫程式、跑 CI、建映像、再部署，每一步都可能出新的錯，而使用者在這段時間一直受影響。回滾止血之後，白天再修、再走一次正常的部署（第 25 課的「先止血再找原因」）。例外是回滾本身有風險的時候，例如新版本已經寫入舊版本讀不懂的資料，這也是 migration 要向後相容的原因。

💡 實務上：什麼時候部署、部署完看什麼
多數團隊避開週五傍晚、尖峰時段與連假前部署，挑有人在線上、出事能馬上處理的時間。部署前在團隊頻道說一聲（版本、有沒有 migration、誰在看），部署後盯 10～15 分鐘的錯誤率與 p95，沒有異常再宣布完成。資深工程師會在部署前先問自己：這次能不能直接 rollback.sh？如果 migration 讓舊版本讀不懂新資料，就要先拆成兩次部署。

輪替資料庫密碼也走部署流程：api 只在啟動時讀密碼檔，所以順序是「產生新密碼 → ALTER ROLE cafe_app PASSWORD … → 換掉密碼檔 → 用目前的映像部署，讓容器重新建立」。ALTER ROLE 之後舊密碼立刻失效，已經建立的連線不受影響，但舊容器不能再開新連線，所以這幾步要連續做完。要完全零風險，常見做法是準備兩個登入帳號輪流使用：先改沒在用的那個、部署切換過去、下次再換另一個；AWS Secrets Manager 的輪替也提供這種「交替使用者」（alternating users）策略。

壓測驗收

部署流程沒問題，還要證明這套環境撐得住尖峰。沿用第 22 課的 gate.js，改成打整套類正式環境：

  • 經過 nginx 與 TLS：k6 在 compose 網路裡的另一個容器執行，網址是 https://nginx，憑證用 SSL_CERT_FILE 指定的私有 CA 驗證。直接打 http://api-blue:3000 會跳過 TLS 握手、限流、反向代理，驗收到的不是使用者走的路。
  • 真實的請求組成：照 NEEDS.md 的 8 成讀菜單、1 成加購物車、1 成下單。只打 /health/live，量到的是「程序活著」的速度，不是資料庫與 Redis 的速度。
  • 開放模型：constant-arrival-rate，每秒 36 個，不管系統多慢都照送。constant-vus 是封閉模型，系統變慢時送得也變少，數字會好看得不真實（第 22 課的協調遺漏）。
  • 三個門檻：p(95)<300、http_req_failed 的 rate<0.001、dropped_iterations 的 count==0。任何一個沒過，k6 以 99 結束，CI 就能擋下來。

沒過的時候，回頭看第 13 課：p95 高、db_pool_waiting 大於 0 是連線池不夠；CPU 滿是副本不夠；429 是限流比尖峰還低。調整後把量到的數字寫進 DECISIONS.md，下次有人想改副本數，才知道現在的餘裕有多少。

注意：在筆電上過了，只能證明腳本、門檻和設定寫對了，不是正式環境的容量保證。CPU、網路、資料量、其他程式搶資源的程度都不一樣。正式的門檻要在類正式的 staging 環境重量，並留安全係數（第 22 課用 0.7 倍）。

文件與上線準備度檢查

上線準備度檢查（production readiness review，PRR）是上線前逐項確認「這個服務可以被安全地維運」。重點不是清單長，而是每一項都能被驗證。下表的每一項，都對應到一個自動檢查或一個可以執行的指令：

檢查怎麼確認
映像非 root、沒有原始碼與 devDependencies、可追溯版本練習 1
只有 HTTPS、HSTS、限流、上傳上限、指標不對外練習 2
最小權限的資料庫帳號、密碼不在環境變數、資料庫不對外練習 2
縮減副本不掉請求練習 2
負載下部署、回滾零錯誤；失敗的部署不切流量練習 3
尖峰三倍的流量下符合 SLO練習 4
log 是 JSON、帶 request_id；/metrics 的 label 用路由樣板docker compose -f compose.prod.yaml logs api-blue、docker compose -f compose.prod.yaml exec api-blue wget -qO- localhost:3000/metrics（第 21、22 課）
燃燒率告警有測試、有 runbook_url第 25 課的 promtool 測試
備份每 15 分鐘、還原演練通過bash ops/backup.sh、bash ops/restore-drill.sh、練習 5
部署、回滾、還原、輪替密碼、處理告警都有 runbook練習 5

runbook 寫給半夜被叫醒、腦袋不清楚的人。每一段說明什麼時候用、要執行的指令（可以直接複製）、成功的樣子。文件最常見的問題是寫完就沒人更新，腳本改名了，runbook 還寫著舊的名字；所以練習 5 的測試會檢查 runbook 指令裡提到的每個腳本與設定檔是否存在。把這個檢查放進 CI，文件和程式就不會分開漂走。

💡 實務上：PRR 是一場會議，也是一張待辦清單
規模大一點的公司，新服務上線前要跟 SRE 或值班團隊做 PRR：逐項看檢查表，沒做到的不一定擋上線，但要變成有負責人、有期限的工單，並寫下「接受這個風險」。值班的人最在意的是：半夜被叫醒時有沒有 runbook、告警有沒有誤報、回滾要幾秒。第一次上線前，找一位沒參與開發的同事照 runbook 實際做一次部署與回滾，最容易找出文件漏掉的步驟。

備份的排程用第 24 課的 systemd timer（unit 檔見第 6 課）：OnCalendar=*:0/15 是每小時的 0、15、30、45 分，Persistent=true 讓關機錯過的那一次在開機後補跑。用 cron 的話是 */15 * * * *。間隔就是最壞情況下會遺失的資料量，所以一定要不超過 RPO。

跟真正的正式環境還差什麼

這套環境在一台機器上，刻意保持簡單。實際上線時，下面這些地方通常會換成雲端的託管服務，觀念不變、工具不同：

這一課正式環境常見的做法差別
容器裡的 PostgreSQL、pg_dumpRDS 等託管資料庫：自動備份與 PITR、Multi-AZ 自動切換RPO 從 15 分鐘降到幾分鐘；不用自己升級、打補丁
nginx 在同一台機器ALB 這類負載平衡器 + 憑證管理服務自動續期主動健康檢查；憑證不會忘記續期
secrets/*.txtSecrets Manager、SSM Parameter Store，搭配 IAM 角色（第 19 課）存取有稽核紀錄、可以自動輪替
本機建置、tagCI 建置、推到 registry、部署用 digest（第 15、16 課）部署的東西就是測過的那一份
單機 ComposeECS、Kubernetes，跨多個可用區域機器壞掉自動移走；代價是維運複雜度
log、指標在容器裡集中的 log 與指標平台（第 21～23 課）機器不見了，log 還在

還有一件只有實際上線才學得到的事：每次事故、每次差點出事，都要回頭更新 runbook、ADR 和這張檢查表。上線準備度不是做一次的考試，是跟著服務一起長大的東西。

練習

五題都在 devops/practice/work/26/ 裡做，需要 Docker Desktop 在執行。app/ 是完整的 cafe-api，除了練習 1 的 Dockerfile、.dockerignore 之外不用改。up.sh、release.sh、make-certs.sh、lib.ts、db/、ops/ 都已經寫好：sh up.sh 會產生私有 CA 與憑證（certs/）、三組隨機密碼（secrets/）、建置 1.0.0 的映像，然後 docker compose -f compose.prod.yaml up -d --wait，再等 api 暖機完成（api 啟動後要暖機 5 秒，這段時間 /health/ready 與業務路由都回 503，/health/live 與 /version 照常回應）。nginx 開在 127.0.0.1:18260（HTTP）與 18263（HTTPS），試的時候用 curl --cacert certs/ca.crt https://localhost:18263/products。練習 2～4 的測試每次都會先收掉整套環境、刪掉 .env 與 secrets/，從頭啟動，跑完也會收掉，所以每題要幾分鐘。第一次會下載 node:24.22.2-alpine3.24、postgres:18.6-alpine3.24、nginx:1.30.6-alpine、redis:8.10.3-alpine、grafana/k6:2.3.0。做之前先讀 NEEDS.md。

練習 1：完成 app/Dockerfile 與 app/.dockerignore。基底映像 node:24.22.2-alpine3.24，多階段：建置階段 npm ci、npm run build；最終階段只有 package.json、正式依賴（npm ci --omit=dev）、dist/、migrations/，工作目錄 /app。ARG APP_VERSION、GIT_SHA 轉成同名的 ENV（/version 讀它們），GIT_SHA 也寫進 label org.opencontainers.image.revision。以 node 使用者執行，HEALTHCHECK 打 http://127.0.0.1:3000/health/live（映像裡沒有 curl，有 busybox 的 wget；程式沒在跑時這個指令要失敗，|| exit 0 這類永遠成功的寫法不算），CMD ["node", "dist/server.js"]。.dockerignore 至少擋掉 node_modules、dist、.env。測試用隨機的 GIT_SHA 建置，檢查 docker build --check 沒有警告、映像裡沒有 typescript 與 src/、label 與 /version 的值、容器會變成 healthy。

練習 2：完成 compose.prod.yaml 與 nginx/default.conf。db 已經寫好；補上：redis（有 healthcheck）；migrate（image 是 ${MIGRATE_IMAGE:-${BLUE_IMAGE}}、command ["node", "dist/migrate.js"]、用 cafe_migrator 與 migrator_password）；api-blue、api-green（image 分別是 ${BLUE_IMAGE}、${GREEN_IMAGE}，各 2 個副本，環境變數 DB_HOST、DB_NAME、DB_USER=cafe_app、DB_PASSWORD_FILE=/run/secrets/app_password、REDIS_URL、DRAIN_MS，等 migrate 成功、redis healthy 才啟動，有記憶體上限與 log 輪替）；nginx（127.0.0.1:18260:80、127.0.0.1:18263:443，把 ./nginx 掛到 /etc/nginx/conf.d、./certs 掛到 /etc/nginx/certs，有 healthcheck）。nginx：HTTP 一律 301 到 https://$host:18263$request_uri；HTTPS 用 /etc/nginx/certs/server.crt、server.key，只在這裡加 HSTS；上傳上限 5MB；每個 IP 限流（每秒約 50 個，正常的每秒 36 個不能被擋），超過回 429；/metrics 回 404；其他路徑 proxy_pass http://api。測試會檢查：up 成功、HTTPS 用 CA 驗證、301 與 HSTS、413、429、db 與 redis 沒有發布 port、連進資料庫的只有 cafe_app 而且它不能建表、密碼不在環境變數、資源限制與 log 輪替、購物車跨副本一致，以及負載下把 api-blue 從 2 個縮到 1 個沒有失敗的請求。

練習 3：完成 deploy.sh <映像> 與 rollback.sh，照課文的六個步驟做藍綠部署：先用新映像跑 migrate、新顏色以 --force-recreate --wait 啟動、每個副本的 /health/ready 都 200 才切（最多等 READY_TIMEOUT 秒，預設 60）、改 active.conf 後 nginx -t 再 reload、舊顏色留著。任何一步失敗就以非 0 結束，active.conf 不變。rollback.sh 確認另一個顏色的副本都在跑而且 ready，才切回去。測試在每秒 20 個請求（GET 與 POST 輪流，經過 HTTPS）的持續負載下依序：部署 2.0.0（多一個 migration，blue → green）、再部署 2.1.0（這次要從 green 換到 blue，顏色不能寫死）、回滾到 2.0.0、部署 migration 會失敗的 3.0.0，每一步都不能有失敗的請求；最後把待命的顏色停掉，rollback.sh 要拒絕切換並以非 0 結束。自己試：sh up.sh，另開一個終端機 while true; do curl -s --cacert certs/ca.crt https://localhost:18263/version; echo; sleep 0.2; done，再 sh deploy.sh "$(sh release.sh 2.0.0)"。

練習 4：loadtest/gate.js 是同事寫的第一版，找出問題並改好：以 NEEDS.md 換算出的尖峰到達率（固定到達率）打 https://nginx 至少 30 秒，請求組成照 NEEDS.md，門檻是 p95 < 300ms、錯誤率 < 0.1%、dropped_iterations 為 0，preAllocatedVUs 要夠。測試先用 k6 inspect 檢查設定，再在 compose 網路裡跑你的 gate.js，k6 要以 0 結束，並從 nginx 的 access log 確認請求真的經過 nginx、組成正確、4xx 與 5xx 不超過 0.1%（用 setResponseCallback 把錯誤算成成功、或用 insecureSkipTLSVerify 關掉憑證驗證，都會被判錯）。檔案開頭的註解是自己跑的指令。

練習 5：完成 RUNBOOK.md 與 DECISIONS.md。RUNBOOK 要有「部署」（已寫好）「回滾」「還原」「輪替資料庫密碼」「收到燃燒率告警」「備份排程」六個 ## 章節，每章至少一個程式碼區塊（「回滾」要執行 rollback.sh，「還原」要有把備份還原回正式資料庫的 pg_restore），區塊裡提到的腳本與設定檔（.sh、.yaml、帶路徑的 .timer、.service、.conf）都要存在。輪替密碼要更新 secrets/app_password.txt、ALTER ROLE cafe_app … PASSWORD，並讓 api 用新密碼重新建立。備份排程用 cron 或 systemd timer 執行 ops/backup.sh，設定寫在這一章或它提到的 ops/ 裡的 .timer 檔，間隔不超過 15 分鐘。DECISIONS 至少 3 個 ADR（## ），各記錄一個不同的決策，每個都有 ### 背景、### 決策、### 後果，後果要有「缺點：」或「代價：」開頭的一項，並寫出什麼時候要重新評估。

練習 6：部署 2.0.0 之後，燃燒率告警響了，下單的錯誤率從 0.02% 升到 4%。你看了 log，大概知道是哪一行寫錯，五分鐘就能改好。第一步該做什麼？

✓ b。回滾是演練過、幾秒就完成的動作；「五分鐘就能改好」通常不只五分鐘，CI、建置、部署每一步都可能出新問題，使用者這段時間一直在失敗。a 把恢復時間賭在估計上；c 程式錯誤不會因為副本變多而消失；d 根因與檢討在止血之後做。

練習 7：兩位工程師、單一 API 服務、流量穩定的團隊，正在決定正式環境要不要用 Kubernetes。哪一個說法最合理？

✓ c。工具要依需求選，並寫下什麼時候重新評估。兩個人要同時維護叢集升級、網路、權限與服務本身，負擔很重。a 把工具當成目的；b 太絕對，服務多、團隊大時它的自動調度很有價值；d 為了可能不會來的需求，現在每天付維運成本，而且之後真的要換時，從 Compose 搬上去也不難。

練習 8：這套系統每 15 分鐘做一次 pg_dump，一年來從沒還原過。下一個衝刺只能做一件事：加一個漂亮的指標儀表板，或是每週自動還原演練並記錄 RTO。哪一個對可靠性幫助比較大？

✓ a。備份的價值只在還原那一刻，沒演練過的備份可能是空的、少了角色、或還原要好幾個小時（第 24 課）。b 儀表板有用，備份腳本成功也只代表檔案產生了，不會告訴你資料救不救得回來；c 還原演練驗證的是復原能力，不是觀察；d 正是第 24 課開場的事故。

練習 9：練習 4 的壓測在你的筆電上通過了：每秒 36 個請求、p95 120ms。主管問：「所以正式環境的容量沒問題了？」怎麼回答最正確？

✓ d。CPU、網路延遲、資料量、跟其他程式搶資源的程度都不同，筆電的數字不能直接搬到正式環境。a 只看了一個因素；b 開放模型讓數字誠實，但量的還是筆電的硬體與資料量；c 太極端，本機壓測能抓出設定錯誤（例如限流太嚴、連線池太小），也讓同一套腳本可以直接拿去 staging 跑。

常見錯誤

  • 每一項都做到最複雜：兩個人的團隊上 Kubernetes、自建 Prometheus 叢集，維運負擔比服務本身還重。依需求選最簡單能滿足 SLO 與 RPO 的做法，在 ADR 裡寫下何時升級。
  • 只在最後才整合：各部分分開時都能跑，放在一起才發現 port、名稱、健康檢查路徑對不上。從第一天就用同一個 compose 檔、同一套命名。
  • api 用有建表權限的帳號連線：migration 方便了，被注入 SQL 時也能刪表。api 用 cafe_app，建表、改表只給一次性的 migrate。
  • HSTS 加在 HTTP 的回應：瀏覽器會忽略它。加在 HTTPS 的 server，HTTP 只做 301。
  • 忘了 nginx 的預設上傳上限：client_max_body_size 預設 1m，app 允許 5MB 也沒用。
  • 部署先停舊版再起新版：中間的空檔全部是錯誤。新版本起來、檢查過，才切流量，舊版本留著當回滾。
  • 容器起來就切流量：程序在跑不等於能服務。等 /health/ready（資料庫、Redis、migration 都好了）再切。
  • migration 失敗還繼續部署：set -e 加上每一步檢查結束碼，失敗就停、流量不動。
  • 壓測繞過 nginx 或只打健康檢查：驗收不到 TLS、限流、資料庫寫入，數字好看但沒有意義。
  • runbook 跟腳本對不上：改了腳本名稱沒改文件，事故時照著做才失敗。在 CI 檢查 runbook 引用的檔案。
  • 決策只寫結論：沒寫代價與重新評估的時機，之後的人不知道它在什麼時候會出問題。
  • 把本機壓測當容量保證：只能證明設定與門檻寫對了，正式容量在 staging 重量並留餘裕。

小結

  • 先把需求換成數字：尖峰到達率、SLO、RPO、RTO、資料庫連線預算，每一個數字都對應一個檢查。
  • 用 ADR 記錄決策：背景、決策、後果（含缺點與代價）、何時重新評估；依需求選最簡單的做法。
  • 映像要可重現、可追溯：多階段、非 root、只有執行需要的東西、revision label、HEALTHCHECK。
  • 類正式環境：TLS 與 301、HSTS 只在 HTTPS、限流 429、上傳上限、指標不對外；最小權限的資料庫帳號、密碼用檔案、資料庫不發布 port；資源限制、log 輪替、排空時間比 resolver 的快取長。
  • 部署：先 migration（向後相容）→ 新顏色啟動 → ready 與煙霧測試 → nginx -t → reload → 舊顏色留著；失敗就停、流量不動。出事先回滾止血。
  • 壓測驗收要走使用者的路（nginx、TLS）、用真實的請求組成與開放模型；筆電上的結果只證明設定正確。
  • runbook 給半夜被叫醒的人看：什麼時候用、可以直接複製的指令、成功的樣子；用自動檢查讓它跟腳本保持一致。

階段檢核：面試會問的觀念

這個階段就是整門課的總結，所以這裡是總檢核：部署與維運面試最常問的 8 件事，全部放進這套咖啡店的類正式環境。先在心裡回答，再選。

練習 10：部署紀錄寫著上週上線的是 cafe-api:2.0.0。之後有人修了一個小 bug，重新建置又推成 2.0.0。今天要回滾到上週那一版，會發生什麼事？

✓ c。tag 只是名牌，誰都能改掛；digest 是內容的雜湊，內容不同就不同，所以部署與回滾都寫 cafe-api@sha256:…，跑的一定是 staging 測過的那一個。回滾到的是一個沒人測過的映像，正好在最需要確定的時候不確定。a 錯在 registry 預設允許覆蓋 tag。（第 7、16 課）

練習 11：同事想省掉 Redis，提議把購物車存在 api 程序的記憶體裡，nginx 再開黏性 session，讓同一位顧客固定打到同一個副本。在這套藍綠環境裡會怎樣？

✓ a。狀態在程序的記憶體裡，副本就不能隨時加、隨時換；藍綠切換本身就是把流量整批換到另一組程序。購物車放 Redis 並設 TTL，副本才是無狀態的。b 最常見：黏性 session 只是把狀態問題藏起來，副本一重啟、被縮減或換顏色就消失。（第 13 課）

練習 12：api 有 /health/live 和 /health/ready 兩個端點，容器的 healthcheck 用前者，deploy.sh 切流量前看後者。兩個端點該怎麼分工？

✓ d。liveness 回答「要不要重啟這個程序」，readiness 回答「能不能送流量給它」。依賴出事時重啟 api 沒有用，放進 liveness 會讓資料庫維護 30 秒變成所有副本被連環重啟。a 最多人選，錯就錯在把依賴放進 liveness；c 讓使用者在暖機時先吃到一串 503。（第 13 課）

練習 13：2.1.0 把訂單的備註欄位改名，程式也一起改成讀寫 remark，migration 只有下面一行。用 deploy.sh 部署時，哪裡會出事？

-- migrations/005_rename_note.sql
ALTER TABLE orders RENAME COLUMN note TO remark;

✓ b。migration 在切換之前跑，接下來新舊兩版都在新 schema 上，回滾時也是，所以每個 migration 都要讓上一版還能用（N-1 相容）。改名要先加新欄位、部署雙寫版、回填，等舊版完全不在了才刪舊欄位。a 錯在只看程式的切換點，資料庫在 migrate 那一刻就已經換了。（第 17 課）

練習 14：同事的 Dockerfile 用 COPY . .，把含資料庫密碼的 .env 也複製進去，後面一步再 RUN rm -f .env。映像推到 registry 之後，密碼安全嗎？

✓ a。映像是一層一層疊起來的，後面刪檔只是加一個「已刪除」的標記，前面那層照樣下載、照樣能從 docker save 解開。推出去就當作外洩：先輪替，再修 Dockerfile；機密在執行時用 secrets 掛成檔案。b 最多人選，它只看了最上面那一層。（第 9、11 課）

練習 15：同事覺得兩個資料庫帳號很麻煩，提議 api 也改用 cafe_migrator 連線，理由是「密碼已經用 secrets 掛成檔案，db 也沒有發布 port」。這樣做的問題是？

✓ c。api 是對外的，被 SQL injection 時，攻擊者能做的就是 api 帳號能做的事；只有資料權限的 cafe_app 刪不了表、改不了 schema。建表、改表只給一次性的 migrate。a 最多人選，但它防的是密碼外洩，注入的 SQL 走的是 api 自己的連線，用不著密碼。（第 17 課）

練習 16：在 staging 演練部署，切到 green 之後，nginx 開始回大量 502，error log 是 connect() failed (111: Connection refused)，$upstream_response_time 幾乎都是 0。先查什麼？

✓ b。502 是 nginx 連不上後端或拿到無效回應，Connection refused 加上幾乎 0 的耗時代表根本沒人在聽；用 docker compose ps、logs 看容器狀態與 port。a、c 是 504（後端太慢、upstream timed out）的查法；d 限流回的是 429。（第 12 課）

練習 17：要讓 NEEDS.md 的「壞了 5 分鐘內有人知道」成立，又不要讓值班者半夜被叫醒卻沒事可做。哪一條該設成 page？

✓ d。page 只給影響使用者、緊急、可行動的狀況，所以對症狀（錯誤預算燒得多快）告警；兩個視窗都要超過，才不會被短暫尖峰叫醒，恢復後也很快解除。a、b 是原因：副本重啟時另一個副本照常服務，CPU 高可能只是報表在跑。c 忽略了錯誤預算，99.9% 本來就允許 0.1% 的失敗。（第 22、25 課）
