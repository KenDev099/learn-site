階段 6：可觀測性與可靠性 · 第 25 課

告警、值班與事故處理

週六中午，咖啡店的線上點餐從 11:40 開始一直失敗。店長 12:30 打電話給你，你才知道出事了。打開手機一看，監控系統其實每五分鐘就發一封「CPU 超過 80%」的信，已經連續發了三個月，大家早就把它設成自動封存。真正的問題（新版本讓下單回 500）反而沒有任何告警。接起電話之後也很混亂：三個工程師同時在改不同的東西，沒人回覆店長，有人想先找出根本原因，有人想直接回滾，可是回滾會把昨天上的安全修正一起退掉。

這一課處理「出事之後」的事：從告警響起、接手處理，到事後檢討，每一步都有固定的做法，不靠當下臨場發揮。

這課的路線：
  1. 好的告警長什麼樣子：哪些事值得半夜叫醒人，哪些開一張工單就好，為什麼「CPU 超過 80%」不該叫醒人。
  2. 用燃燒率告警與測試告警：把錯誤預算的消耗速度寫成 Prometheus 告警規則，再用 promtool 證明該響時會響、不該響時不響。
  3. Alertmanager 與值班：告警怎麼分組、靜音、送到對的人手上，值班前要先講好哪些事。
  4. 事故處理流程：誰指揮、誰回覆店長，先止血再找原因，止血方式要對症（例如不要為了一個功能回滾掉安全修正）。
  5. 事後檢討：寫一份不究責的檢討，把「誰犯了錯」換成「系統為什麼允許這個錯」，讓同樣的事不再發生。
這課會用到：
  • 第 22 課的 SLO、錯誤預算與 PromQL：SLO 99.9% 代表 30 天內允許 0.1% 的請求失敗，這個額度就是錯誤預算；PromQL 從指標算出錯誤率，recording rule 把常用的查詢先算好存起來，promtool 用來測試規則。
  • 第 16 課的回滾與功能旗標：回滾是切回上一版映像；功能旗標讓已經部署的功能用設定決定開不開。

好的告警長什麼樣子

告警（alert）是系統自動通知人的訊號。它分成兩種：

  • page：要立刻處理，會打電話、推播把值班者叫醒。
  • ticket：開一張工單，上班時間處理就好。

一個值得 page 的告警要同時滿足四件事：影響使用者（或很快就會）、緊急（等到明天早上會更糟）、可行動（收到的人有事可做）、有 runbook（處理手冊，寫好收到這個告警時一步一步怎麼查、怎麼止血）。少了任何一項，它應該是 ticket、儀表板上的一張圖，或乾脆刪掉。

關鍵的區分是症狀與原因。症狀告警看使用者感受到的問題（下單失敗、很慢）；原因告警看可能造成問題的內部狀態（CPU 高、磁碟快滿、某個副本重啟）。

狀況類型怎麼處理
錯誤預算燒得很快（1 小時內燒掉 30 天預算的 2%）症狀page
p95 延遲持續超過 SLO症狀page 或 ticket，看燃燒多快
CPU 80%原因不告警，放儀表板；使用者沒感覺就沒事
磁碟 4 小時內會滿原因，但一定會變成症狀page（少數例外：可預測、必然出事）
一個副本重啟，其他副本接住了原因ticket 或不告警
最近一次成功備份超過 26 小時（第 24 課）原因，影響 RPOticket；超過 48 小時升成 page

原因告警的問題是：原因有一百種，你永遠列不完，而且大部分原因不會讓使用者受影響。CPU 80% 可能只是報表在跑。半夜為它被叫醒三次之後，值班者學到的是「告警不用理」。這叫告警疲勞（alert fatigue）：告警太多太吵，大家開始靜音、封存，真正的告警也被一起忽略。開場的故事就是這樣發生的。症狀告警只有幾條，卻涵蓋所有會讓使用者痛的原因，包括你沒想到的那些；原因交給儀表板，事故發生時用來縮小範圍。

💡 實務上：接手專案時，先盤點現有的告警
加入新團隊或接手一個服務，常看到幾十條從沒人調過的 CPU、記憶體告警，和一個沒人在看的告警頻道。資深工程師會先拉出過去一個月每條告警響了幾次、有幾次真的有人處理，再對每一條問：「它響的時候，我要做什麼？」答不出來的降成 ticket 或刪掉；缺的症狀告警（下單成功率、結帳延遲）補上。刪告警前跟維運和 PM 對一下 SLO，大家同意「什麼程度才值得半夜叫人」，告警才有共識。

用燃燒率告警

第 22 課教過燃燒率：觀察視窗內的錯誤率 ÷ (1 − SLO)。SLO 99.9% 時允許的錯誤率是 0.001，燃燒率 1 代表預算剛好在 30 天用完，燃燒率 14.4 代表 30 ÷ 14.4 ≈ 2 天就用完。

最直覺的告警是「5 分鐘錯誤率超過某個值就響」，問題是短視窗很吵：一個 4 分鐘的尖峰燒掉的預算微不足道，卻會把人叫醒。只看 1 小時的長視窗又有反方向的問題：事故在 10:00 修好了，1 小時視窗裡還留著修好前的錯誤；錯誤率越高，告警在恢復後響得越久（全面停機時接近 1 小時），值班者分不清「還在壞」還是「剛修好」。

Google 的 SRE workbook 建議多視窗多燃燒率告警（multiwindow multi-burn-rate alert）：每個告警同時看長、短兩個視窗，兩個都超過門檻才響。長視窗確認「真的燒掉了一定比例的預算」，短視窗（長視窗的 1/12）確認「現在還在燒」，所以恢復後幾分鐘就解除。SLO 99.9%、30 天的建議值：

燃燒率長視窗短視窗門檻（錯誤比例）響的時候已經燒掉處理
14.41 小時5 分鐘14.4 × 0.001 = 1.44%30 天預算的 2%page
66 小時30 分鐘6 × 0.001 = 0.6%5%page
13 天6 小時1 × 0.001 = 0.1%10%ticket

寫成 Prometheus 的告警規則（alerting rule）。先用 recording rule（第 22 課）把每個視窗的錯誤比例算好，告警直接讀：

groups:
  - name: cafe-api-slo-alerts
    rules:
      - alert: CafeApiErrorBudgetBurnFast
        expr: |
          job:slo_errors_per_request:ratio_rate1h{job="cafe-api"} > (14.4 * 0.001)
          and
          job:slo_errors_per_request:ratio_rate5m{job="cafe-api"} > (14.4 * 0.001)
        labels:
          severity: page
        annotations:
          summary: "cafe-api 錯誤預算快速燃燒：1 小時錯誤比例 {{ $value | humanizePercentage }}"
          runbook_url: https://runbooks.cafe.test/cafe-api/error-budget-burn
  • expr 有結果（至少一條序列）時告警成立。and 只留下兩邊 label 都對得上的序列，所以兩個視窗都要超過門檻。
  • labels 加在告警上，Alertmanager 依它決定送給誰；severity 是最常見的一個。
  • annotations 是給人看的說明，可以用 {{ $labels.job }}、{{ $value }} 這類樣板。runbook_url 讓半夜被叫醒的人點一下就知道下一步。
  • for: 5m：條件要持續 5 分鐘才從 pending（待定）變成 firing（觸發）。它能過濾一兩次評估的抖動，代價是至少晚 5 分鐘才響。別拿很長的 for 取代長視窗：for: 1h 代表事故開始後至少一小時才有人知道，而短暫的抖動一中斷，計時就從零開始。燃燒率告警本身已經用長視窗過濾雜訊，通常不需要 for，或只用幾分鐘。
  • 門檻用小數：SLO 寫成 0.999，允許的錯誤比例是 0.001。寫成 14.4 * (1 - 99.9) 會得到負數，告警永遠在響。
流量很低的服務（例如半夜每分鐘只有幾個請求），一個錯誤就是很高的錯誤率，燃燒率告警會很吵。常見的做法是加上最低請求數的條件，或把幾個小服務合起來算 SLO。

測試你的告警

告警規則寫錯時 Prometheus 不會報錯：門檻多一個零，它就永遠不響，你要到出事那天才發現。所以告警跟 recording rule 一樣要用 promtool test rules 測。除了第 22 課的 promql_expr_test，還有專門給告警的 alert_rule_test：在某個時間點，列出應該在響的告警（含 label 與 annotations）；列表留空代表「這時候不應該響」。

rule_files: [slo-rules.yml, alerts.yml]
evaluation_interval: 1m
tests:
  - interval: 1m
    input_series:
      # 每分鐘 10,000 個請求，前 120 分鐘錯誤 0.05%，之後 60 分鐘錯誤 2%
      - series: 'http_requests_total{job="cafe-api",status="500"}'
        values: '0+5x120 800+200x59'
      - series: 'http_requests_total{job="cafe-api",status="200"}'
        values: '0+9995x120 1209200+9800x59'
    alert_rule_test:
      - eval_time: 100m                       # 平常：不應該響
        alertname: CafeApiErrorBudgetBurnFast
        exp_alerts: []
      - eval_time: 170m                       # 燒了 50 分鐘：應該在響
        alertname: CafeApiErrorBudgetBurnFast
        exp_alerts:
          - exp_labels: { severity: page, job: cafe-api }
            exp_annotations:
              summary: "…"                    # 要跟展開後的文字完全一樣
              runbook_url: https://runbooks.cafe.test/cafe-api/error-budget-burn

一組好的告警測試至少涵蓋：平常不響、持續燃燒會響、短暫尖峰不響、恢復後解除、慢性問題由慢的告警接住。exp_annotations 要完全相符，含 $value 的文字不好寫死；這時可以改用 promql_expr_test 查 ALERTS{alertname="…", alertstate="firing"}，Prometheus 替每個 pending、firing 的告警產生這條序列。練習 1 的測試就是這樣做的。

Prometheus 3 的範圍選擇器是左開右閉：[5m] 在第 10 分鐘取的是 5 分（不含）到 10 分（含）的樣本，剛好落在邊界上的點不算。測試的時間點不要剛好卡在門檻跨過的那一分鐘，留一兩個評估間隔的餘裕。

告警送到哪：Alertmanager

Prometheus 只負責判斷告警成不成立，然後把它交給 Alertmanager：負責分組、抑制、靜音、路由的服務。

  • 分組（grouping）：資料庫掛了，20 個依賴它的告警同時響。group_by 把相同 label 的告警合成一則通知；group_wait（預設 30 秒）等一下，讓同一組的告警一起送出。
  • 抑制（inhibition）：某個告警在響時，暫時不送另一些。例如「整個 region 斷線」在響時，不再送每個服務各自的錯誤告警。
  • 靜音（silence）：維護期間手動暫停特定告警，有開始與結束時間。靜音一定要設期限，永久靜音等於刪掉告警。
  • 路由（routing）：依 label 決定送到哪裡：page 送值班系統（例如 PagerDuty、Opsgenie 這類會打電話、會升級的服務），ticket 送 Slack 頻道或開工單。
route:
  receiver: team-slack                 # 沒對到下面任何一條就送這裡
  group_by: [alertname, job]
  routes:
    - matchers: [ severity="page" ]
      receiver: oncall-pager
inhibit_rules:
  - source_matchers: [ alertname="CafeApiDown" ]
    target_matchers: [ severity="page" ]
    equal: [ job ]                     # 同一個 job 才抑制
receivers:
  - name: team-slack
    slack_configs: [ { channel: "#cafe-alerts", api_url_file: /run/secrets/slack_webhook } ]
  - name: oncall-pager
    pagerduty_configs: [ { routing_key_file: /run/secrets/pagerduty_key } ]

還有一個問題：監控系統自己掛了，所有告警都不會響，大家以為天下太平。解法是死人開關（dead man's switch，第 24 課教過同樣的概念）：寫一條永遠成立的告警（例如 expr: vector(1)，常取名 Watchdog），讓它一直送到外部的監控服務；那個服務「一段時間沒收到」才通知你。備份的新鮮度告警（最後一次成功備份距今多久）也是同樣的思路：檢查「該發生的事有沒有發生」，而不是等錯誤訊息。

值班

值班（on-call）是在一段時間內負責接 page 的人。幾個要先講好的事：

  • 輪值表：通常一人一週，至少兩人一組（主要、備援）。主要值班者在幾分鐘內沒有回應，就自動升級（escalation）給備援，再沒有回應就給主管。
  • 交接（handoff）：換班時留下紀錄：這週響了哪些告警、哪些事還沒處理完、有什麼正在進行的變更或靜音。下一位不用從零開始。
  • 可持續的負荷：Google SRE 的做法是每次值班的事故數量要有上限（例如每 12 小時班平均不超過兩件），超過就代表告警或系統該修了，而不是叫人更努力。半夜被叫醒的時間要有補償（補休或加給）。
  • 每個 page 都要檢討：這次的 page 有沒有必要？不必要的告警降級成 ticket 或刪掉。這是對付告警疲勞最有效的方式。
💡 實務上：第一次排進值班表之前
確認幾件事：手機上的值班 App 會不會在靜音、勿擾模式下響；筆電、VPN、正式環境的權限在家裡能不能用；每個會 page 的告警都打得開 runbook。很多團隊讓新人先當一輪「影子值班」：跟著資深的人一起接 page，不負主責。交接時把「這週響過什麼、哪些靜音還在、有什麼變更正在進行」寫下來，比口頭說可靠。

事故處理流程

事故（incident）是需要協調處理、影響使用者的意外狀況。用嚴重度（severity）分級，決定要叫多少人、多常更新：

等級咖啡店的例子處理
SEV1所有人都不能下單，或資料外洩立刻集合所有相關的人，每 15～30 分鐘對外更新
SEV2部分功能壞掉（下單失敗率 25%），或有替代方案值班者加上相關的人，定期更新
SEV3小問題，大部分使用者沒感覺上班時間處理

宣告：覺得可能是事故就宣告，事後降級很便宜，太晚宣告很貴。宣告之後開一個專用頻道，指派角色：

  • 事故指揮官（incident commander，IC）：統籌、做決定、指派工作，是唯一的資訊來源。IC 不親自修：一頭栽進 log 裡的人，沒辦法同時注意全局、決定要不要回滾、記得該更新狀態頁。
  • 記錄員（scribe）：記下時間線、每個決策和原因，事後檢討直接用。
  • 對外溝通：固定頻率（例如每 30 分鐘，就算沒有進展也說「還在處理」）更新狀態頁（status page，對使用者公告服務狀態的頁面）、回覆店長與客服。
  • 處理者：實際查問題、執行止血的工程師，由 IC 分派。

小團隊一個人可能身兼數職，但「誰在指揮」一定要講清楚。開場的故事裡三個人同時改東西，誰也不知道系統現在是哪個狀態，這比單一問題更危險。

先問「最近改了什麼」

大部分事故是變更造成的：部署、設定、旗標、資料庫 migration、流量突然變大。所以排查的第一步是把出事時間跟變更紀錄對起來（部署紀錄、git log、旗標的修改紀錄），再用可觀測性的三種工具縮小範圍：

  1. 指標（第 22 課）：哪個路由、哪個副本、從幾點開始？錯誤率還是延遲？
  2. log（第 21 課）：挑幾個失敗請求的 request_id，看錯誤訊息和 stack。
  3. trace（第 23 課）：慢的話，慢在哪個服務、哪一段。

這就是 NestJS 課第 25 課的除錯步驟（重現 → 讀錯誤 → 假設 → 縮小範圍 → 驗證），只是在正式環境、有時間壓力下做。每個假設和證據都告訴記錄員。

先止血，再找根本原因

止血（mitigation）是先讓影響停止；解決（resolution）是處理根本原因。事故當下的第一優先是止血：使用者在乎的是能不能下單，不是你有沒有找到那一行 bug。止血的方式要對症：

問題止血不要做
新版本的程式壞了用部署腳本回滾到上一個正常的映像（第 16 課），之後再 git revert（第 14 課）在正式環境 hotfix、進容器改檔案
旗標打開的新功能壞了只關那個旗標，讓程式重新載入設定回滾整個版本：同一版裡的其他修正（例如安全修正）會被一起退掉
流量超過容量擴充副本、限流擴充副本去掩蓋程式錯誤：壞掉的路徑還是壞的
資料庫連線池用完、延遲飆高找出占用連線的查詢或剛上線的變更，回滾或關掉只重啟：幾分鐘後又滿了

止血要留下紀錄、可以重現：用部署腳本、改設定檔、送訊號，不要 docker exec 進容器手動改檔。手動改的東西沒有 review、下次部署就消失，也沒人知道系統現在跑的是什麼。

💡 實務上：對外更新寫「已知什麼、在做什麼、下次幾點更新」
店長、客服、老闆在事故中最怕的是沒有消息。對外的訊息不寫技術細節和猜測的原因，只寫：影響範圍（「線上點餐無法下單，門市不受影響」）、正在做什麼（「已找到相關的變更，正在處理」）、下一次更新的時間。止血後也要發一則「已恢復」，並說明事後檢討會在幾天內提供。這個角色常由 IC 指派給非工程師（例如客服主管），工程師才能專心處理。
資安事故（金鑰外洩、資料外洩、帳號被盜）另有額外步驟：保全證據、撤銷與輪替憑證、評估通報義務，依 Auth 課第 25 課的劇本處理。這一課處理的是可用性事故。

MTTD（mean time to detect，平均偵測時間）是從問題開始到有人知道；MTTR（mean time to recovery，平均復原時間）是到服務恢復。好的症狀告警縮短 MTTD，好的 runbook、旗標、一鍵回滾縮短 MTTR。

事後檢討

事後檢討（postmortem）是事故結束後寫下的文件：發生了什麼、為什麼、怎麼避免再發生。Google SRE 的觸發條件是：使用者可見的停機或品質下降超過某個門檻、任何資料遺失、需要值班者介入（回滾、切換流量）、處理時間超過門檻、監控沒抓到而是人發現的。事先講好門檻，不用每次討論要不要寫。

事後檢討要不究責（blameless）：假設每個人都是根據當時手上的資訊做出合理的決定，問題要問「為什麼系統允許這個錯誤發生」。寫「原因：某工程師操作錯誤」，大家學到的是下次出錯要藏起來，而真正的問題（為什麼一個指令就能刪掉正式資料庫？為什麼沒有測試？為什麼沒有二次確認？）沒人修。範本：

  • 摘要：兩三句話說清楚發生了什麼、怎麼結束的。
  • 影響：持續多久、多少比例的請求或使用者受影響、用掉多少錯誤預算。
  • 時間線：用 UTC 的 ISO 時間（2026-11-01T01:29:47Z），每筆一行，從變更開始到解除。UTC 讓不同時區的人讀不會誤會，也能直接跟 log 對照。
  • 偵測：怎麼發現的？告警響了，還是客人打電話？
  • 促成因素：通常不只一個（程式的假設、缺少的測試、預設開啟的旗標、沒涵蓋到的煙霧測試）。避免只寫一個「根本原因」：複雜系統的事故很少只有一個原因。
  • 做得好的地方、可以更好的地方。
  • 改善項目：每項都有負責人、期限與類型（prevent 避免再發生、detect 更早發現、mitigate 更快止血），放進團隊的待辦清單追蹤。沒有負責人的改善項目不會被完成。

練習

練習 1～3 在 devops/practice 做（在 learn/ 執行 node check.mjs devops 25）。練習 1、2 需要 Docker 在跑，第一次會下載 prom/prometheus:v3.15.1 與 node:24.22.2-alpine3.24。練習 2 的測試每次會重新跑一次演練，大約 20 秒。

練習 1：在 alerts.yml 依 99.9% 的 SLO 寫三個告警：CafeApiErrorBudgetBurnFast（燃燒率 14.4，1 小時與 5 分鐘兩個視窗，severity: page）、CafeApiErrorBudgetBurnSlow（6 倍，6 小時與 30 分鐘，severity: page）、CafeApiErrorBudgetBurnTicket（1 倍，3 天與 6 小時，severity: ticket）。每個告警的 annotations 都要有 summary 與 runbook_url（http 或 https 網址）。slo-rules.yml 已經算好 job:slo_errors_per_request:ratio_rate5m、…30m、…1h、…6h、…3d，直接用。測試用 promtool 餵五種情境（每分鐘 10,000 個請求）：錯誤率穩定 0.05% 時三個都不響；2% 持續 1 小時時 Fast 在開始後 50 分鐘內響、恢復後 10 分鐘內解除；2% 只持續 4 分鐘時都不響；0.7% 持續 6.5 小時時 Slow 會響、Fast 不響，恢復後 40 分鐘內 Slow 解除；0.15% 持續 8 小時時只有 Ticket 響。

練習 2：事故演練。先執行 sh drill.sh：它建出 cafe-api 的 2.3.1 與 2.4.0，部署 2.3.1、送流量，再部署 2.4.0、送流量，然後告警響了。你是值班者：用 docker logs ld-25-api、curl localhost:18250/metrics、state/deploy.log、drill/CHANGELOG.md（需要時 diff 兩個版本的 drill/releases/*/server.mjs）找出問題，判斷該回滾（sh deploy.sh 2.3.1）還是只關掉某個旗標（改 state/flags.json，再 docker kill --signal HUP ld-25-api 讓 api 重新讀取）。把止血的指令寫進 mitigate.sh（drill.sh、deploy.sh、drill/ 不要改）。再填 incident.json：problem_type（"code" 或 "flag"）、bad_version、detected_at 與 mitigated_at（UTC ISO，例如 2026-11-01T01:29:47Z，止血晚於偵測）、mitigation（"rollback" 或 "flag-off"）、evidence：至少 3 筆，log 與指標各至少一筆，格式是 {"kind":"log","request_id":"…"}（從 log 複製一個失敗請求的 ID）或 {"kind":"metric","name":"完整的序列，含 label","value":當時的數值}。測試重新執行 drill.sh、記下當時的 log 與 /metrics，執行你的 mitigate.sh，然後送 200 個請求：錯誤率要低於 0.1%、p95 低於 300ms；同時檢查同一版裡的安全修正還在、只動了該動的旗標、容器由 deploy.sh 建立、docker diff 是空的（沒有進容器手動改檔），以及每筆證據都對得上。

練習 3：依範本為練習 2 的演練寫一份不究責的事後檢討 postmortem.md。八個 ## 章節都要有內容：摘要、影響、時間線、偵測、促成因素、做得好的地方、可以更好的地方、改善項目。時間線至少 5 筆，每筆一行，開頭是 UTC 的 ISO 時間（- 2026-11-01T01:29:47Z …），依時間遞增。影響要寫出持續幾分鐘（「12 分鐘」）與受影響請求的比例（「25%」）。改善項目用範本的表格，至少 3 項，每項有類型（prevent、detect、mitigate）、負責人和 YYYY-MM-DD 的期限。促成因素不能歸咎個人（「粗心」「人為疏失」「操作錯誤」「沒注意」這類字眼都不行）。

練習 4：半夜三點，api 的 CPU 到了 90%，錯誤率、延遲都在 SLO 之內。這時應該 page 值班者嗎？

✓ c。CPU 高是原因，不是症狀：可能只是報表或流量高峰，系統照樣好好服務。page 只留給影響使用者、緊急、可行動的狀況。a、b 都是原因告警，門檻調多高都一樣：它們會在使用者沒事時把人叫醒，久了造成告警疲勞，真正的告警也被忽略。CPU 長期偏高是容量規劃的問題，開 ticket 白天處理。

練習 5：同事提議把「5 分鐘錯誤率超過 1.44%」的告警加上 for: 1h，理由是「比較不吵」。主要的代價是什麼？

✓ a。for 要求條件「連續」成立這麼久，所以一小時內都在 pending，一次抖動就從零開始。多視窗燃燒率用 1 小時的長視窗過濾雜訊，同時在預算燒掉 2% 時就響（錯誤率 2% 時約 43 分鐘，錯誤率越高越快），恢復後又能很快解除。b 忽略了延遲偵測的成本：多一小時的 MTTD 就是多燒一小時的錯誤預算。c 不對，for 只是在記憶體裡記住告警從什麼時候開始 pending。

練習 6：剛部署的版本讓 25% 的下單失敗，你還不知道是哪一行程式造成的。第一優先是什麼？

✓ b。使用者在乎的是能不能下單。止血通常比找根因快得多（回滾或關旗標只要幾分鐘），而且不需要先知道是哪一行壞掉，只需要知道「跟這次的變更有關」。a 讓使用者在你讀程式碼的期間繼續失敗。c 是記錄員在處理過程中持續做的事，不是值班者的第一優先，也不能拖慢止血。

練習 7：事後檢討寫「根本原因：工程師阿哲操作錯誤，誤刪了正式環境的資料表」。這樣寫有什麼問題？

✓ c。換一個人在同樣的情境下也可能犯同樣的錯，系統讓這件事可能發生才是要修的地方：權限分離、刪除前的確認、備份與還原演練（第 24 課）。歸咎個人的結果是下次大家把錯誤藏起來，事故更晚被發現。a 的「以後小心」不是能追蹤的改善項目。b 只是換了主詞，還是在找該怪的人。

常見錯誤

  • 對原因告警，而不是對症狀告警：CPU、記憶體、重啟次數的告警會在使用者沒事時把人叫醒，又漏掉沒想到的原因。page 用 SLO 燃燒率，原因放儀表板。
  • 沒有 runbook 的告警：半夜被叫醒的人不知道下一步。每個告警的 runbook_url 都要指向一份寫好查法與止血指令的文件。
  • 告警太多，大家開始靜音：每個 page 事後都要問「有必要嗎」，不必要的降級成 ticket 或刪掉；靜音一定要設期限。
  • 只用短視窗或只用長視窗：只看 5 分鐘會被尖峰吵醒；只看 1 小時會在恢復後繼續響。兩個視窗同時成立才響。
  • 用很長的 for 代替長視窗：至少晚那麼久才響，抖動一次就重新計時。
  • 門檻用百分比的數字算：SLO 寫成 0.999，允許的錯誤比例是 0.001，不是 99.9 或 0.1。
  • 告警規則沒有測試：寫錯不會報錯，只會永遠不響。用 promtool 測「該響、不該響、恢復後解除」。
  • 事故時大家都在修，沒有人指揮與對外溝通：宣告事故後先指定 IC；IC 不親自修，負責決策、分派與固定頻率的更新。
  • 先找根因、晚止血：先回滾或關旗標讓使用者恢復，根因白天再查。
  • 止血方式不對症：旗標問題回滾整個版本，會把同一版的安全修正一起退掉；程式錯誤用擴充或重啟掩蓋，問題還在。
  • 進容器手動改檔案：沒有紀錄、下次部署就消失。改設定檔、送訊號、用部署腳本換版本。
  • 事後檢討歸咎個人：寫促成因素（缺了什麼測試、檢查、預設值），不寫誰不小心。
  • 改善項目沒有負責人，也沒人追蹤：每項要有負責人、期限與類型，放進待辦清單定期檢查。
  • 監控系統自己掛了也沒人知道：用一直在響的 Watchdog 告警搭配外部的死人開關。

小結

  • page 只給影響使用者、緊急、可行動、有 runbook 的狀況；其他用 ticket 或儀表板。對症狀告警，原因留給排查時用。
  • 多視窗多燃燒率：14.4 倍（1 小時＋5 分鐘）與 6 倍（6 小時＋30 分鐘）page，1 倍（3 天＋6 小時）ticket；短視窗讓告警恢復後很快解除。門檻是燃燒率 × (1 − SLO)。
  • 告警規則用 promtool 測：平常不響、持續燃燒會響、尖峰不響、恢復後解除。
  • Alertmanager 負責分組、抑制、靜音與路由；用 Watchdog 加死人開關確認監控本身還活著。
  • 值班要有輪值表、交接、升級路徑、負荷上限與補償，每個 page 都要檢討必要性。
  • 事故流程：偵測 → 宣告 → 分級 → 止血 → 解決 → 事後檢討。IC 指揮不親自修，記錄員記時間線，固定頻率對外更新；先問最近改了什麼，先止血再找根因，止血方式要對症（程式問題回滾、旗標問題只關旗標）。
  • 不究責的事後檢討：影響、UTC 時間線、怎麼發現的、促成因素、有負責人與期限的改善項目。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：結帳失敗的 error log 會把整個請求標頭記下來，authorization 也在裡面。同事說：「在 Alloy 加一條規則，把這個欄位刪掉再送到 Loki 就好，app 不用改。」這樣做的問題是？

✓ 遮蔽要在程式寫出之前做：在 pino 設定 redact，收集器的過濾只當第二道防線。已經寫出去的 token 要當成外洩處理，撤銷並換新。a 只看了集中後的查詢介面，忘了 log 在送出之前就已經存在主機上。（第 21 課）

練習 9：cafe-api 儀表板上的平均延遲一直在 90ms 左右，客服卻接到不少「結帳要轉好幾秒」的抱怨。最可能的解釋是？

✓ 98% 的請求 30ms、2% 的請求 3 秒，平均約 90ms，p99 卻是 3 秒。延遲用 histogram 記錄，看 p95、p99。c 的結論要先看過 p99 才能下：p99 也正常，才輪到懷疑網路。（第 22 課）

練習 10：SLO 是「30 天內 99.9% 的請求不是 5xx」。過去 1 小時的錯誤率是 1%，同事說：「99% 都成功了，明天再看。」用錯誤預算來看，這代表什麼？

✓ 燃燒率 ＝ 錯誤率 ÷ (1 − SLO) ＝ 0.01 ÷ 0.001 ＝ 10。99.9% 允許的錯誤率是 0.1%，1% 是它的 10 倍，再拖一天就燒掉三分之一的預算。a 錯在分母是允許的錯誤率，跟觀察視窗多長無關，1 小時的資料就算得出來。（第 22 課）

練習 11：api 和 kitchen 都裝了 OpenTelemetry，在 Jaeger 裡一筆下單卻變成兩條 trace：api 一條、kitchen 一條，trace_id 不同。最先檢查什麼？

✓ trace_id 靠 traceparent 一路傳下去：CLIENT span 要 inject，SERVER span 要在 extract 回來的情境下建立；少了任何一步，kitchen 找不到父 span，只好開新的 trace。佇列訊息也一樣要帶。b 錯在取樣只決定這條 trace 留不留，不會換 trace_id，而且 ParentBased 會照上游的 sampled 旗標走。（第 23 課）

練習 12：這支備份腳本跑了半年，每天都以 exit 0 結束。哪裡會出事？

#!/usr/bin/env bash
set -eu
name=cafe-$(date -u +%Y%m%dT%H%M%SZ)
docker exec ld-24-db pg_dump -U postgres -d cafe \
  | gzip > "/backup/$name.sql.gz"
echo "$name" > /backup/LATEST

✓ 管線的結束碼只看最後一段，pg_dump 連不上資料庫時，gzip 照樣壓縮了「什麼都沒有」。開頭改成 set -euo pipefail，寫到暫存檔、驗證過才 mv 成正式檔名，最後才更新 LATEST；能不能還原，還是要靠定期的還原演練證明。a 錯在保留政策本來就該用 UTC 算，混用時區才會歸錯天。（第 24 課）

練習 13：老闆說訂單最多只能丟 5 分鐘（RPO 5 分鐘）。目前每天 03:00 用 pg_dump 備份一次，該怎麼改？

✓ RPO 由兩次備份的間隔決定，每天一次的 pg_dump 最壞丟將近 24 小時；WAL 封存持續保存交易紀錄，可以重播到誤刪前一刻。代價是儲存費和維護，要跟老闆講清楚。b 錯在誤刪的 DELETE 一秒內就複寫過去：replica 解決機器壞了，不解決資料壞了。（第 24 課）

練習 14：同事只寫了一個告警：「1 小時錯誤率超過 1.44% 就 page」。10:00 錯誤率升到 10%，10:30 回滾後 5 分鐘錯誤率已經回到 0.05%，告警卻一直響到 11:20。為什麼？

✓ 長視窗確認燒掉的預算夠多，但恢復後要等錯誤滑出視窗，值班者分不清還在壞還是剛修好。再加一個長視窗 1/12 的短視窗（5 分鐘），兩個都超過才響，恢復後幾分鐘就解除。b 錯在 for 只會延後觸發，不會讓告警提早解除。（第 25 課）

練習 15：2.6.0 同時包含一個安全修正，和預設開啟的新功能旗標 points_v2（新的集點計算）。部署後 20% 的下單失敗，log 裡的錯誤都出在集點計算。該怎麼止血？

✓ 止血要對症：問題出在旗標打開的功能，關掉旗標就停止影響，根本原因白天再修。a 是最多人的直覺，但會把安全修正一起退掉，等於重新打開那個漏洞；程式本身壞了才回滾。c 只是掩蓋，壞掉的路徑還是壞的。（第 25 課）
