階段 6：可觀測性與可靠性 · 第 23 課

分散式追蹤：OpenTelemetry

儀表板顯示 POST /orders 的 p99 從 300ms 跳到 2.4 秒（第 22 課的指標）。你知道「有問題」，可是一個下單請求會經過 cafe-api、資料庫、kitchen 服務、kitchen 的資料庫，最後送進出單佇列。到底是哪一段變慢？log 裡每個服務各自寫著自己的耗時，你得用 request_id 一個服務一個服務地對時間，還不一定對得上。

分散式追蹤（distributed tracing）就是為這個問題設計的。這一課用 OpenTelemetry 替 cafe-api 和 kitchen 加上追蹤，並把 trace_id 放進 log，讓 log、指標、trace 三者互相連得起來。

這課的路線：
  1. trace 與 span：把一個請求在所有服務裡做的工作連成一棵樹、畫成瀑布圖，一眼看出慢在哪一段（開場問題的最小答案）。
  2. traceparent：kitchen 怎麼知道收到的請求屬於哪一條 trace，自己動手解析這個標頭。
  3. OpenTelemetry 的元件、手動與自動埋點：SDK、exporter、Collector 各做什麼，怎麼替 cafe-api 和 kitchen 加上追蹤。
  4. 取樣與成本：流量大時不能每個 span 都留，該留哪些。
  5. 把 log 和 trace 連起來：log 帶上 trace_id，值班時從一行錯誤 log 直接跳到整條 trace。
這課會用到：
  • 第 21 課的集中式 log：所有服務的 log 收到同一個地方，用 request_id 找出同一個請求的每一行。
  • 第 22 課的百分位數：p99 是「99% 的請求比這個值快」，代表最慢那群人的感受。
  • Node 課第 19 課的 AsyncLocalStorage：在一連串 await 之間保留「目前是哪個請求」，不必一層層傳參數。

一個慢請求到底慢在哪：trace 與 span

一條 trace（追蹤）是一個請求在所有服務裡經過的完整路徑。它由很多個 span（區段）組成：每個 span 是一段有開始、有結束的工作，例如「處理 POST /orders」「查資料庫」「呼叫 kitchen」。span 記得自己的父 span（parent），所以整條 trace 是一棵樹；沒有父 span 的第一段叫 root span。

一個 span 有這些欄位：

欄位是什麼例子
trace_id整條 trace 的編號，16 bytes，寫成 32 個 hex 字元；同一個請求的所有 span 都一樣4bf92f3577b34da6a3ce929d0e0e4736
span_id這個 span 的編號，8 bytes，16 個 hex 字元00f067aa0ba902b7
parent_span_id父 span 的編號；root span 沒有
name這段工作叫什麼。要是低基數的：路由樣板，不是原始網址POST /orders、GET /orders/:id
kindspan kind：這段工作的角色。SERVER 處理收到的請求；CLIENT 呼叫別的服務；PRODUCER 送出佇列訊息；CONSUMER 處理佇列訊息；INTERNAL 程序內部的工作SERVER
開始、結束時間相減就是耗時
屬性（attributes）描述這段工作的鍵值http.route=/orders
事件（events）span 期間某個時間點發生的事，最常見的是例外exception
狀態（status）UNSET（預設）、OK、ERRORERROR

span 跟 log 的差別在結構：log 是一個時間點上的一句話；span 是一段時間區間，而且知道自己的父親是誰，所以能組成樹、算出每一段佔了多少時間、知道誰在等誰。第 22 課說過三者的分工：指標告訴你「有問題」，trace 告訴你「在哪裡」，log 告訴你「為什麼」。

傳遞情境：traceparent

kitchen 怎麼知道自己收到的請求屬於哪一條 trace？呼叫的一方要把 trace 資訊放進請求裡帶過去，這叫情境傳遞（context propagation）。HTTP 用的格式是 W3C 的標準 Trace Context（Level 1，2021 年 11 月成為正式建議），定義了兩個標頭：traceparent 帶 trace 的身分，tracestate 讓各家廠商附加自己的資料。

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  trace-id（32 個 hex）             parent-id（16）    flags（2）
             version（2）
  • version：目前是 00。ff 明訂為無效。
  • trace-id：整條 trace 的編號。parent-id：送出這個請求的那個 span 的編號，收到的一方拿它當自己的父 span。
  • flags：最低的位元是 sampled：01 表示上游決定要記錄這條 trace，00 表示不記錄。其他位元保留，目前要設成 0。
  • 所有 hex 都要小寫。trace-id 全是 0、parent-id 全是 0 都是無效值。

收到無效的 traceparent 時，規格要求忽略它、開一條新的 trace，並丟掉 tracestate。這不只是格式潔癖：traceparent 來自外部，可能是壞掉的客戶端，也可能是有人故意塞的，照單全收會讓不相干的請求被串成同一條 trace。練習 1 你要自己寫這段解析。

每經過一個服務，trace-id 不變，parent-id 換成新的 span 的編號，sampled 照上游的決定往下傳：

瀏覽器 → api      traceparent: 00-4bf9…4736-00f067aa0ba902b7-01    （api 的 SERVER span 的父親）
api → kitchen     traceparent: 00-4bf9…4736-b7ad6b7169203331-01    （api 的 CLIENT span 的編號）

情境不只走 HTTP。訊息送進佇列（例如 NestJS 課第 20 課的 BullMQ），也要把 traceparent 一起放進訊息，否則 worker 處理訂單的那一段就跟原本的請求斷開了：

// 送出（PRODUCER）：把目前的情境寫進一個普通物件，跟著 job 一起存
const otel: Record<string, string> = {}
propagation.inject(context.active(), otel)          // otel = { traceparent: '00-…-01' }
await queue.add('print-ticket', { orderId, otel })

// 處理（CONSUMER）：從 job 取回情境，在它底下建立 span
const parent = propagation.extract(ROOT_CONTEXT, job.data.otel)
await tracer.startActiveSpan('process print-ticket', { kind: SpanKind.CONSUMER }, parent, async span => { … })

一次批次處理很多則訊息時，一個 span 沒辦法有好幾個父親，這時用 span link（連結）指向每一則訊息原本的 trace。

💡 實務上：trace 的邊界要自己決定
咖啡店的公開 API 會收到瀏覽器、合作夥伴、甚至攻擊者送來的 traceparent。常見的做法是：內部服務之間照單延續；從外部進來的請求，在入口（外部請求最先進到的那一層，例如反向代理後的第一個服務）開一條新的 trace，需要時用 span link 指回對方給的 trace。前端的 Vue 頁面若要送 traceparent，它是自訂標頭，跨網域時會觸發 CORS 預檢，後端要在 Access-Control-Allow-Headers 放行。設計時要問：哪些入口信任上游、哪些重開，寫進團隊的文件，不然每個服務各做各的。

OpenTelemetry 的元件

OpenTelemetry（簡稱 OTel）是 CNCF 的開放標準與工具組，涵蓋 trace、指標、log：定義資料長什麼樣、怎麼傳、各語言的程式庫怎麼寫。它不負責儲存與畫圖，那是 Jaeger、Grafana Tempo 這類後端，或各家 SaaS 的事。好處是你只埋點一次，後端可以換。

  • API 與 SDK 分開：@opentelemetry/api 只有介面。沒有註冊 SDK 時，它的每個呼叫都是什麼都不做的 no-op，幾乎沒有成本。所以函式庫只依賴 API：裝了它的應用程式不想要追蹤，就不用付代價；要追蹤，由應用程式自己裝 SDK、決定送去哪裡。函式庫要是自帶 SDK，就會跟應用程式的 SDK 版本衝突、各送各的。
  • SDK：TracerProvider 產生 span、做取樣、附上 resource（這個程序是誰：service.name、版本、環境）；span processor 在 span 結束時接手，BatchSpanProcessor 先放進佇列，攢一批（預設每 5 秒）再送，不會每個 span 一個網路請求。
  • exporter：把 span 轉成某種格式送出。標準格式是 OTLP（OpenTelemetry Protocol），gRPC 用 4317 port，HTTP 用 4318 port。OTLPTraceExporter（@opentelemetry/exporter-trace-otlp-http）預設送 JSON 到 http://localhost:4318/v1/traces，設了環境變數 OTEL_EXPORTER_OTLP_ENDPOINT 就改送到那個位址（自動接上 /v1/traces）。
  • Collector：接收、處理、轉送遙測資料的獨立服務。程式只送到附近的 Collector，由它批次、重試、遮蔽敏感屬性、取樣，再轉送到一個或多個後端。換後端只改 Collector 的設定。
  • 語意慣例（semantic conventions）：大家同意的屬性名稱，例如 http.request.method、http.route、http.response.status_code、url.full、service.name。名稱一致，後端才能自動畫出服務地圖、算出錯誤率。@opentelemetry/semantic-conventions 提供常數，例如 ATTR_HTTP_ROUTE。慣例也規定 HTTP span 的名稱：SERVER 是「方法 路由樣板」，CLIENT 只用方法。
版本注意：OpenTelemetry JS 3.0.0（2026-10-20）把 sdk-trace-base、sdk-trace-node、sdk-trace-web 合併成 @opentelemetry/sdk-trace，最低需要 Node 22.15.0，實驗性的套件（例如 exporter）要搭配 0.300.0；AsyncHooksContextManager 被移除，改用 AsyncLocalStorageContextManager；也不能再 import 套件內部的深層路徑。BatchSpanProcessor 的參數改成一個物件：new BatchSpanProcessor({ exporter })。npm 上的 sdk-trace-node 停在 2.x，網路上多數教學還是 2.x 的寫法，照抄會裝到舊套件。這門課用 sdk-trace 3.0.0、api 1.10.0、semantic-conventions 1.44.0。

手動埋點

埋點（instrumentation）是在程式裡加上產生遙測資料的程式碼。先設定 SDK，這一段每個服務啟動時跑一次：

import { context, propagation, trace } from '@opentelemetry/api'
import { AsyncLocalStorageContextManager } from '@opentelemetry/context-async-hooks'
import { W3CTraceContextPropagator } from '@opentelemetry/core'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http'
import { resourceFromAttributes } from '@opentelemetry/resources'
import { BatchSpanProcessor, TracerProvider } from '@opentelemetry/sdk-trace'
import { ATTR_SERVICE_NAME } from '@opentelemetry/semantic-conventions'

context.setGlobalContextManager(new AsyncLocalStorageContextManager())   // ① 記住「現在的 span」
propagation.setGlobalPropagator(new W3CTraceContextPropagator())          // ② 用 traceparent 跨服務
const provider = new TracerProvider({
  resource: resourceFromAttributes({ [ATTR_SERVICE_NAME]: 'cafe-api' }),  // ③ 我是誰
  spanProcessors: [new BatchSpanProcessor({ exporter: new OTLPTraceExporter() })],   // ④ 分批送出
})
trace.setGlobalTracerProvider(provider)

① 是關鍵。await 之後，程式怎麼知道「現在」屬於哪個請求的哪個 span？跟 Node 課第 19 課放 request id 的方法一樣：AsyncLocalStorage。context manager 把目前的情境（裡面有 active span）放在 AsyncLocalStorage 裡，每個非同步流程各自一份，同時處理 20 個請求也不會混在一起。

接著在處理請求的地方建立 span。tracer.startActiveSpan(名稱, 選項, 父情境, fn) 建立 span、在 fn 執行期間把它設成 active span，fn 裡建立的 span 自動成為它的子 span：

const tracer = trace.getTracer('cafe-api')

// 收到請求：從標頭取出上游的情境，在它底下建立 SERVER span
const parent = propagation.extract(context.active(), req.headers)
await tracer.startActiveSpan('POST /orders', {
  kind: SpanKind.SERVER,
  attributes: { [ATTR_HTTP_REQUEST_METHOD]: 'POST', [ATTR_HTTP_ROUTE]: '/orders' },
}, parent, async span => {
  try {
    await createOrder(req, res)
  } finally {
    span.setAttribute(ATTR_HTTP_RESPONSE_STATUS_CODE, res.statusCode)
    if (res.statusCode >= 500) span.setStatus({ code: SpanStatusCode.ERROR })
    span.end()                                   // 沒有 end 的 span 永遠不會送出
  }
})

呼叫 kitchen 時建立 CLIENT span，並且在它是 active span 的時候把情境 inject（寫入）到要送出的標頭：

await tracer.startActiveSpan('POST', { kind: SpanKind.CLIENT, attributes: { … } }, async span => {
  try {
    const headers: Record<string, string> = { 'content-type': 'application/json' }
    propagation.inject(context.active(), headers)          // headers.traceparent = '00-…-<這個 CLIENT span 的 id>-01'
    const res = await fetch(url, { method: 'POST', headers, body })
    if (!res.ok) throw new Error(`kitchen responded ${res.status}`)
  } catch (err) {
    span.recordException(err as Error)                      // 記成 exception 事件，含 stack
    span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).message })
    throw err
  } finally {
    span.end()
  }
})

還有一件常被忘記的事：BatchSpanProcessor 的 span 先放在記憶體裡。部署時容器收到 SIGTERM（第 3 課）就 process.exit，最後幾秒的 span 全部消失，偏偏出事的往往就是那幾秒。結束前要 await provider.shutdown()，它會把佇列裡的 span 送完再關掉 exporter。

屬性裡不要放個資與機密：email、電話、token、整個請求 body。trace 後端的保存與權限通常比資料庫寬鬆，第 21 課對 log 的規則一樣適用；Collector 也可以再遮蔽一次，當作第二道防線。

💡 實務上：值班時 trace 怎麼用
告警通知 POST /orders 的 p99 超標（第 22 課）。值班的人先在 trace 後端篩出這段時間、這個路由、耗時超過 1 秒或狀態 ERROR 的 trace，打開其中幾條看瀑布圖：哪個子 span 最長、是不是一直在同一段（同一個下游、同一句 SQL）。找到那一段，再用 trace_id 跳到那段時間的 log 看錯誤訊息。所以埋點時要先想好之後會用什麼篩選：路由、狀態碼、下游服務名稱都要是屬性，不然 trace 存了也撈不出來。

自動埋點與 ESM

每個 HTTP 請求、每次查詢都手寫 span 很累。自動埋點（auto-instrumentation）是不改業務程式碼，替常用函式庫（http、undici／fetch、pg、ioredis、Express、NestJS…）自動產生 span、自動 inject／extract。Node 的入口是 @opentelemetry/auto-instrumentations-node，它的做法是在模組載入時修改（patch）那些函式庫。

問題在 ESM（ECMAScript modules，import 語法）。CommonJS 的 require 可以攔截，ESM 的載入流程不同，要多掛一個 loader hook，官方文件寫的啟動方式是：

node --experimental-loader=@opentelemetry/instrumentation/hook.mjs \
     --import @opentelemetry/auto-instrumentations-node/register app.js

沒有 hook，程式照樣跑、一個錯誤都沒有，就是沒有 span。OpenTelemetry 的文件也說 ESM 的支援仍在進行中，結果可能不一致。NestJS 12 以 ESM 發布，一樣需要這個 hook。另一個細節是順序：SDK 必須在被埋點的函式庫載入之前啟動，所以用 --import 先載入設定，不是在 main.ts 裡面 import。

實務上兩者並用：自動埋點涵蓋框架與資料庫，手動 span 補上業務上重要的步驟（「計算折扣」「保留庫存」），再把業務屬性（訂單的商品數、付款方式）加到 active span 上。這一課的練習全部手動，是為了讓你看清楚自動埋點替你做了哪些事。

取樣與成本

每個 span 都要花 CPU 產生、花網路送、花錢存。每秒 500 個請求、每個請求 8 個 span，一天就是 3.5 億個 span。所以流量大時不會全部留下，而是取樣（sampling）：

方式在哪裡、什麼時候決定優點代價
head-based：例如 TraceIdRatioBasedSampler(0.1) 留 10%root span 開始時，在 SDK便宜：沒被選中的 span 根本不產生、不送決定時還不知道結果。罕見的錯誤、慢請求很可能剛好沒被選中
parent-based：ParentBasedSampler有上游時跟著 traceparent 的 sampled 旗標同一條 trace 在每個服務的決定一致，不會只剩半條只是跟隨，root 的決定還是要另外設
tail-based在 Collector，等整條 trace 的 span 到齊之後可以「錯誤與超過 1 秒的全留、其他留 5%」Collector 要把所有 span 暫存在記憶體裡等；同一條 trace 的 span 必須送到同一台 Collector

sdk-trace 3.0 沒設 sampler 時用的是 ParentBasedSampler({ root: new AlwaysOnSampler() })：自己是 root 就全留，有上游就照上游的 sampled 旗標。所以上游送來 -00 時，你的服務不會記錄這個請求。常見的正式設定是 SDK 用 ParentBased + 比例取樣控制總量，Collector 再用 tail sampling 把錯誤與慢的 trace 撈回來。TraceIdRatioBasedSampler 用 trace id 算決定，同一條 trace 在不同服務算出來的結果一樣。

取樣只影響 trace。指標（第 22 課）要從全部請求算，錯誤率、p99 才準；不要拿取樣後的 trace 去算錯誤率。

💡 實務上：取樣率是成本決策，要跟人討論
trace 的費用通常照 span 數或資料量計價，取樣率直接影響帳單，所以會跟維運、主管一起決定。常見的起點：流量小的服務先全留；流量大的用比例取樣，錯誤與慢請求靠 tail sampling 留下；上線新功能那幾天暫時調高。也要讓團隊知道 trace 不是完整紀錄：客服回報某一筆訂單很慢時，那筆不一定有 trace，要先查 log。

把 log 和 trace 連起來

第 21 課的 log 欄位裡有 trace_id。有了它，在 Grafana 看 trace 時可以一鍵跳到這條 trace 的所有 log，反過來看到一行錯誤 log 也能跳到它的 trace。做法是讓 logger 每寫一行都去問「現在的 active span 是誰」。pino 的 mixin 選項是一個函式，每寫一行 log 都會呼叫，回傳的物件併進那一行：

pino({
  mixin() {
    const span = trace.getActiveSpan()          // 從 AsyncLocalStorage 拿「這個請求」的 span
    if (!span) return {}                        // 請求以外（啟動、排程）不帶
    const { traceId, spanId } = span.spanContext()
    return { trace_id: traceId, span_id: spanId }
  },
})

兩個看起來也行、其實會錯的做法：只在 api 從 traceparent 標頭讀出 trace id 塞進 log，kitchen 那邊就沒有；用一個全域變數存「目前的 trace id」，第二個請求進來就把第一個的蓋掉，併發時 log 會掛到別人的 trace 上。練習 3 的測試會同時送 20 個請求抓這兩種錯。

  cr.jaegertracing.io/jaegertracing/jaeger:2.22.0
cd devops/practice/work/23

OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:18238 PORT=3000 KITCHEN_URL=http://localhost:3001 node api.ts
# 送幾個請求後打開 http://localhost:18236，選 cafe-api；看完 docker stop ld-23-jaeger

練習

練習 1 在頁面上做。練習 2、3 在 devops/practice 做，不需要 Docker：測試會在 127.0.0.1 的隨機 port 開一個假的 OTLP/HTTP 接收器，用 OTEL_EXPORTER_OTLP_ENDPOINT 指向它，啟動 kitchen.ts 與 api.ts，送請求、送 SIGTERM，再檢查收到的 span 與兩個服務印出的 log。testkit.ts 是測試用的工具，不用改。

練習 1：實作 traceparent 的解析與產生。這題只處理版本 00，其他版本一律當成無效。parseTraceparent(header)：格式完全正確時回傳 { version, traceId, parentId, sampled }，否則回 null。無效的情況包括：大寫 hex、任何一段長度不對、非 hex 字元、trace-id 或 parent-id 全是 0、版本不是 00（包括 ff）、多出來的 - 或內容、前後有空白。sampled 只看 flags 的最低位元。childTraceparent(parent, newSpanId)：產生要送給下游的 traceparent，trace-id 不變、parent-id 換成新的 span id、只保留 sampled 旗標（其他位元歸 0）。newRootTraceparent(traceIdHex, spanIdHex, sampled)：開一條新的 trace。這兩個產生的函式收到不合格的 id（長度不對、大寫、全是 0）時要丟出錯誤。

練習 2：把 api 與 kitchen 串成一條 trace。在 tracing.ts 完成 setupTracing(serviceName)：AsyncLocalStorageContextManager、W3CTraceContextPropagator、TracerProvider（resource 的 service.name、BatchSpanProcessor 接 OTLPTraceExporter），註冊成全域。在 api.ts：每個請求從標頭 extract 上游情境、建立 SERVER span（名稱 POST /orders，不是 req.url；屬性 http.request.method、http.route，結束前寫上 http.response.status_code，5xx 時狀態 ERROR）；callKitchen 包一個 CLIENT span（名稱 POST；屬性 http.request.method、url.full、http.response.status_code），送出前 inject 標頭，失敗時 recordException 並設成 ERROR。在 kitchen.ts：extract 後在那個情境下建立 SERVER span（POST /tickets，同樣的屬性），出錯時 recordException、設成 ERROR。每個 span 都在 finally 裡 end；兩個服務收到 SIGTERM 時都要先 await provider.shutdown() 再結束。測試會檢查：三個 span 都在傳入的 trace 裡、父子關係正確、名稱與屬性、kitchen 回 500 時三個 span 都是 ERROR、送完 10 個請求立刻 SIGTERM 時 30 個 span 一個都不少，而且是分批送出（不是每個 span 送一次）。手動試的指令寫在 api.ts 開頭。

練習 3：先完成練習 2。兩個服務都用 logger.ts 的 createLogger，請求期間會印出 order received、kitchen accepted、request（api）與 ticket received、ticket printed（kitchen）。在 logger.ts 讓請求期間的每一行 log 都帶上目前的 trace_id 與 span_id，請求以外的 log（例如 listening）不帶這兩個欄位。只能改 logger.ts。測試會同時送 20 個帶不同 traceparent 的請求，用 request_id 對出每一行屬於哪個請求，檢查 trace_id 是那個請求的、span_id 是這個服務在那個請求裡的某個 span。

練習 4：團隊在寫一個共用的資料庫存取套件 @cafe/db，想讓每個查詢都有 span。同事提議：「套件裡直接裝好 @opentelemetry/sdk-trace 和 OTLP exporter，誰用了就自動有追蹤。」比較好的做法是？

✓ b。API 在沒有註冊 SDK 時是 no-op，不想追蹤的應用程式幾乎不付代價；要追蹤的應用程式裝自己的 SDK，函式庫的 span 自動接到它的 trace 裡。a 函式庫自帶 SDK 會跟應用程式的 SDK 版本衝突、各自決定送去哪裡、取樣不一致；c 查詢這一段正是 trace 最想看到的；d console.log 沒有父子關係，也接不上 trace。

練習 5：為了省錢，SDK 改成 ParentBasedSampler({ root: new TraceIdRatioBasedSampler(0.1) })，只留 10% 的 trace。這樣會漏掉什麼？

✓ c。head-based 取樣在 root span 開始時決定，那時還不知道這個請求會不會出錯、會不會慢。tail sampling 等整條 trace 到齊再決定，可以「錯誤與慢的全留、其他抽樣」，代價是 Collector 要暫存 span。b ParentBased 讓下游跟著 root 的決定，一條 trace 是整條留或整條丟；d 指標是另外算的，跟 trace 取樣無關，也不應該從取樣後的 trace 算。

練習 6：同事說：「span 就是有時間戳的 log，我們已經有結構化 log 加 request_id，不需要 trace。」哪個說法正確？

✓ a。結構化 log 加 request_id 可以找出同一個請求的所有行，但看不出巢狀關係、哪幾段同時進行、哪一段在等哪一段。b 少了區間與父子關係；c 兩者互補：trace 告訴你在哪裡，log 告訴你為什麼，所以要用 trace_id 把兩者連起來；d trace 通常比 log 貴，所以才要取樣。

常見錯誤

  • 沒有傳遞情境：呼叫下游時沒有 inject，或收到時沒有 extract，每個服務各自一條 trace，瀑布圖斷成好幾段。CLIENT span 要 inject，SERVER span 要在 extract 回來的情境下建立。
  • 佇列訊息裡忘了帶 traceparent：worker 那一段變成獨立的 trace。送出時 inject 到訊息資料，處理時 extract。
  • 用原始網址當 span 名稱：POST /orders/1155?source=pos 每張訂單一個名稱，後端無法彙總。名稱用「方法 路由樣板」，id 放屬性。
  • 忘了 end span、關機時沒有 flush：沒 end 的 span 永遠不會送出；BatchSpanProcessor 記憶體裡的 span 會在 process.exit 時消失。end 寫在 finally，SIGTERM 時先 await provider.shutdown()。
  • 把個資放進 span 屬性：email、token、整個 body 進到 trace 後端，保存期與權限都管不住。只放除錯需要的、低敏感的欄位，Collector 再遮蔽一次。
  • 高流量下 100% 取樣：網路、儲存費用跟著流量線性長。用 ParentBased + 比例取樣，錯誤與慢的 trace 交給 tail sampling。
  • ESM 專案以為裝了自動埋點就會生效：沒有 --experimental-loader=@opentelemetry/instrumentation/hook.mjs，不會報錯，只是沒有 span；SDK 也要用 --import 在函式庫載入前啟動。
  • 照 2.x 教學寫 3.0：sdk-trace-node、new BatchSpanProcessor(exporter)、深層 import 在 3.0 都不能用。看套件的版本，查對應版本的 README。

小結

  • trace 是一個請求在所有服務的完整路徑，由 span 組成；span 有 trace_id、span_id、父 span、名稱、kind、時間區間、屬性、事件與狀態。
  • W3C traceparent：00-trace-id-parent-id-flags，小寫 hex、全 0 與版本 ff 無效、sampled 是最低位元；無效就開新的 trace。HTTP 標頭與佇列訊息都要傳。
  • 函式庫只依賴 API，應用程式裝 SDK：TracerProvider（resource、sampler）→ BatchSpanProcessor → OTLP exporter（:4318/v1/traces）→ Collector → Jaeger／Tempo。OTel JS 3.0 合併成 @opentelemetry/sdk-trace。
  • 手動埋點：startActiveSpan、extract／inject、recordException、ERROR 狀態、finally 裡 end、SIGTERM 時 shutdown；AsyncLocalStorage 讓併發的請求各自有自己的 active span。
  • 自動埋點在 ESM 需要 loader hook；取樣要在成本與留下罕見錯誤之間取捨，head、parent-based、tail 各有位置。
  • log 的每一行帶 trace_id、span_id（pino 的 mixin），log、指標、trace 才能互相跳轉。
