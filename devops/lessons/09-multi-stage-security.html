階段 2：容器化 · 第 9 課

多階段建置與映像安全

第 8 課的映像能跑，但打開來看：裡面有 TypeScript 編譯器、所有 .ts 原始碼、@types、npm 的快取。哪天 API 有漏洞被人拿到 shell，這些都是現成的工具。更糟的是，同事為了裝公司的私有套件，在 Dockerfile 加了 ARG NPM_TOKEN，映像推上 registry 之後，任何能拉映像的人用 docker history 就看得到那個 token。

這一課把映像變小、變乾淨，並讓容器用最少的權限執行。

這課的路線：
  1. 單一階段的映像與多階段建置：第 8 課的映像為什麼帶著編譯器和原始碼，怎麼只把執行需要的東西留在最終映像。
  2. 選擇基底映像：Alpine、slim、distroless 各留下什麼，沒有 shell 的映像出事怎麼查。
  3. 機密不能進映像：ARG NPM_TOKEN 為什麼用 docker history 就看得到，怎麼讓機密在建置時用完就消失。
  4. 釘版本、掃描與跨架構建置：釘住基底映像又不漏掉安全更新，在 Mac 上替 amd64 的伺服器建置映像。
  5. 執行期加固：就算 API 被人拿到 shell，讓攻擊者能做的事越少越好。
這課會用到：
  • 第 7 課的映像：由好幾層疊成，每一層都留在映像裡；tag 會移動、digest 不會；映像要符合主機的 CPU 架構（平台）。
  • 第 8 課的單一階段 Dockerfile：先複製 lockfile 再 npm ci 以重用層快取，USER node 不用 root 執行，docker build --check 檢查常見錯誤。
  • Node 課第 3 課的依賴分類：dependencies 是執行時要的套件，devDependencies 只在開發和建置時用。

單一階段的映像裡有什麼

先量一下第 8 課那種寫法。用 docker history 看每一層多大（由新到舊，最下面幾層是基底映像 node:24.22.2-alpine3.24）：

docker history <第 8 課建出的映像>
CREATED BY                                   SIZE
CMD ["node" "dist/server.js"]                0B
…
RUN /bin/sh -c npm run build                 6.65kB
COPY src ./src                               2.97kB
RUN /bin/sh -c npm ci                        44.6MB   ← 這一層最大
COPY package.json package-lock.json ./       18.7kB
…（以下是基底映像的層，約 167MB）

44.6MB 的 npm ci 那層裡，執行時真正需要的只有 pino 和它的幾個依賴，大約 1MB。其餘是：

  • TypeScript 7 的原生編譯器（@typescript/typescript-linux-arm64，二十幾 MB）和 typescript 本身
  • @types/node 等型別定義：只有編譯時要用
  • /root/.npm：npm 下載套件時留下的快取

再加上 src/ 裡的原始碼和 tsconfig.json。這些東西有三個代價：映像大，部署和擴展時拉得慢；裡面的套件越多，被發現漏洞的機會越多；攻擊者進到容器之後，能利用的工具越多。最後這點叫攻擊面（attack surface）：攻擊者能拿來利用的東西總和，包括多餘的套件、shell、編譯器、套件管理器。

在同一個 Dockerfile 最後加一行 RUN npm prune --omit=dev && rm -rf src /root/.npm 沒有用。第 7 課說過，映像是一層一層疊起來的，後面的層刪檔案只是加上一個「這個檔案被刪了」的標記，前面那層的 44.6MB 還在映像裡，照樣要下載，也照樣能從那一層把檔案拿出來。

多階段建置

多階段建置（multi-stage build）：一個 Dockerfile 寫好幾個 FROM，每個 FROM 開始一個新的階段（stage），各自從乾淨的基底開始。最後一個階段就是產出的映像，前面的階段只是工作區，用 COPY --from=階段名稱 把需要的成果複製過來，其他東西都不會進最終映像。

# syntax=docker/dockerfile:1

# 階段 1：編譯。需要 devDependencies
FROM node:24.22.2-alpine3.24 AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY tsconfig.json ./
COPY src ./src
RUN npm run build

# 階段 2：只裝正式依賴
FROM node:24.22.2-alpine3.24 AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

# 階段 3：最終映像
FROM node:24.22.2-alpine3.24
ENV NODE_ENV=production
WORKDIR /app
COPY package.json ./
COPY --from=deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
EXPOSE 3000
USER node
HEALTHCHECK …（同第 8 課）
CMD ["node", "dist/server.js"]

逐行看重點：

  • AS build 幫階段取名字，COPY --from=build 用名字指定從哪個階段複製。名字要小寫（build check 的 StageNameCasing 規則）。
  • 為什麼要另外一個 deps 階段，而不是在 build 階段 npm prune 後整包複製？兩種都可以；分開的好處是 deps 階段只跟 package*.json 有關，改原始碼時它整個走快取。不能直接複製 build 階段的 node_modules，那裡面有 typescript。
  • package.json 一定要帶：它的 "type": "module" 告訴 Node 用 ES module 載入 dist/*.js，少了它程式會直接出錯。
  • USER、ENV、HEALTHCHECK 只對寫在它的那個階段有效。最終階段是新的開始，前面階段寫過的設定都要重寫。
  • BuildKit 會分析階段之間的依賴，build 和 deps 兩個階段互不相關，會同時建置。

結果：最終映像只比基底多 1MB 左右，裡面沒有編譯器、沒有原始碼、沒有 npm 快取。

docker build --target build -t cafe-api:build . 只建到指定的階段為止。用途是：在 CI 裡用 build 階段跑測試（它有 devDependencies），或另外做一個帶 migration 工具的映像（第 17 課）。

選擇基底映像

最終階段 FROM 的那個映像決定了你的映像裡還剩什麼。Node 常見的選擇：

基底C 函式庫shell、套件管理器特色除錯
node:24.22.2-alpine3.24musl有（busybox sh、apk）小（arm64 約 167MB，大部分是 Node 本身）docker exec … sh
node:24-bookworm-slim／node:24-trixie-slimglibc有（bash、apt）Debian 精簡版，相容性最好docker exec … bash，可以臨時 apt-get install
gcr.io/distroless/nodejs24-debian13glibc沒有Google 維護，只有 Node 和執行需要的檔案；:nonroot 版本預設以 uid 65532 執行看 log、共用命名空間的除錯容器，或 :debug 版本
Docker Hardened Images（dhi.io/node）依版本（Alpine 或 Debian）runtime 版沒有，-dev 版有Docker 維護、以低 CVE 為目標；2025-12-17 起以 Apache 2.0 免費提供，拉取要先 docker login dhi.io同 distroless；建置階段用 -dev 版

幾個名詞：

  • musl／glibc：Linux 程式都會用到一個 C 標準函式庫。Debian、Ubuntu 用 glibc；Alpine 用 musl，比較小，但行為有些差異。純 JavaScript 的套件不受影響；有原生模組的套件（例如 bcrypt、sharp）要有對應 musl 的預先編譯版本，否則要在映像裡自己編譯，或者乾脆不能用。
  • distroless：「沒有發行版」的映像，裡面沒有 shell、沒有套件管理器，只有執行環境。攻擊者就算能執行程式碼，也沒有 sh、wget 可以用。代價是你也沒有。注意它的 ENTRYPOINT 已經是 node，所以 CMD 只寫 ["dist/server.js"]，HEALTHCHECK 也不能用 CMD-SHELL。
  • CVE（Common Vulnerabilities and Exposures）：公開漏洞的編號，例如 CVE-2026-33634。映像裡的套件越多，對到的 CVE 通常越多，但「數量」不等於「風險」：沒有被執行到的套件，漏洞也很難被利用。

沒有 shell 的映像出問題怎麼查？先看 docker logs。還不夠，就開一個有工具的除錯容器，讓它加入目標容器的網路和程序命名空間（第 7 課）：

# 借用 ld-09-app 的網路與程序命名空間：看到的 localhost、程序清單都是它的
docker run --rm -it --network container:ld-09-app --pid container:ld-09-app alpine:3.24 sh
/ # ps                       # 看得到 ld-09-app 裡的 node（PID 1）
/ # wget -qO- http://localhost:3000/health/live

除錯工具在另一個容器裡，用完就丟，正式的映像一直保持乾淨。

這門課選 node:24.22.2-alpine3.24：小、有 shell 方便學習時進去看，cafe-api 只有純 JS 的依賴，不受 musl 影響。正式環境要更嚴格時，最終階段換成 distroless 或 DHI，建置階段不用改。原則是：先確定依賴在那個 libc 上能跑、團隊會用除錯容器，再追求更小。

機密不能進映像

咖啡店有一個私有套件 @cafe/loyalty，放在公司的私有 npm registry，下載要帶 token。建置時需要 token，執行時不需要。常見的三種寫法都會外洩：

寫法token 留在哪裡怎麼看到
ARG NPM_TOKEN ＋ --build-arg NPM_TOKEN=…映像的建置紀錄：用到它的每一個 RUN 都記著值docker history --no-trunc 出現 RUN |1 NPM_TOKEN=npm_… /bin/sh -c …
ENV NPM_TOKEN=…映像設定，而且每個容器執行時都有這個環境變數docker image inspect 的 Env；容器裡 env
COPY .npmrc，用完 RUN rm .npmrcCOPY 那一層的檔案內容docker save 匯出後解開那一層

自己驗證第一種（token 是假的）：

docker build --build-arg NPM_TOKEN=npm_FAKE123 -f Dockerfile.private -t demo .
docker history --no-trunc --format '{{.CreatedBy}}' demo | grep FAKE
RUN |1 NPM_TOKEN=npm_FAKE123 /bin/sh -c node scripts/fetch-private.mjs # buildkit
ARG NPM_TOKEN=npm_FAKE123

映像推到 registry 之後，任何拉得到映像的人（同事、CI、外包、駭進 registry 的人）都能看到。Docker 官方文件也明說 build arg 和環境變數不適合傳機密，因為它們會留在最終映像裡。

正確做法是 build secret：只在某一個 RUN 執行期間掛進去、不寫進任何一層的機密。

# Dockerfile
RUN --mount=type=secret,id=npm_token,env=NPM_TOKEN node scripts/fetch-private.mjs

# 建置指令：把目前 shell 的環境變數 NPM_TOKEN 當成 id=npm_token 的 secret 交給 BuildKit
docker build --secret id=npm_token,env=NPM_TOKEN -f Dockerfile.private .
  • --mount=type=secret 預設把 secret 掛成檔案 /run/secrets/<id>；加 env=NPM_TOKEN 改成這一步的環境變數（Dockerfile 語法 1.10 起）。檔案形式也可以用 target=/root/.npmrc 指定位置，npm 會直接讀它。
  • --secret 的來源可以是 env=變數名 或 src=檔案路徑。
  • secret 的值不算在層快取裡：換了 token，那一步照樣走快取。Docker 文件建議的做法是另外加一個不是機密的 ARG CACHEBUST，換 token 時一起改它的值。
  • 它只保證「不進映像」。你自己在那一步把 token 寫進檔案（例如 echo … > .npmrc 卻沒刪），一樣會進那一層。

docker build --check 會用 SecretsUsedInArgOrEnv 規則擋下名稱看起來像機密的 ARG、ENV（TOKEN、PASSWORD、SECRET、KEY 之類）：

WARNING: SecretsUsedInArgOrEnv - …
Do not use ARG or ENV instructions for sensitive data (ARG "NPM_TOKEN")
多階段建置不能當成機密的防護：把 ARG NPM_TOKEN 放在建置階段，最終映像的 history 確實看不到，但 token 還在建置快取、--target 建出的中間映像、CI 的 log 裡，而且 build check 照樣會警告。一律用 secret mount。執行期才需要的機密（資料庫密碼）根本不該在建置時出現，第 11 課在執行時注入。

token 一旦進過映像，就當作已經外洩：撤銷、換新，再重建。刪掉映像不夠，你不知道誰已經拉過。

💡 實務上：外洩的 token 通常在 code review 時就該被擋下
真實的事故常是「某個舊映像的 history 裡有 token」，被資安掃描或外部回報才發現。資深工程師 review Dockerfile 時會先看三件事：有沒有 ARG／ENV 的名字像機密、有沒有 COPY 進 .npmrc、.env 這類檔案、.dockerignore 有沒有排除它們。再把 docker build --check 放進 CI，讓規則自動把關。發現外洩時先撤銷 token，再追查誰拉過映像，順序不能反。

釘版本、重建與掃描

第 7 課講過，tag 可以被移動，digest 不會。基底映像可以寫成：

FROM node:24.22.2-alpine3.24@sha256:<index digest>

tag 給人看，digest 保證每次建置用的是同一份內容。但釘死之後，基底映像出了安全更新你也不會拿到，所以要搭配自動更新工具：Dependabot（GitHub 內建）或 Renovate，它們會定期檢查 Dockerfile 的 FROM、package.json，有新版本就開 PR 改 digest，CI 跑過再合併（第 15 課）。

映像掃描（image scanning）：把映像裡每個套件的版本拿去跟漏洞資料庫比對，列出已知的 CVE。常用工具：

  • docker scout cves 映像：Docker 內建，要先登入 Docker 帳號；加 --exit-code 時發現漏洞會以結束碼 2 結束，可以讓 CI 失敗；--only-severity critical,high、--only-fixed 過濾。
  • Trivy（Aqua Security 的開源工具）：trivy image 映像，不用帳號。

兩個資深工程師要知道的事：

  • 掃描結果每天都會變。映像內容沒變，但漏洞資料庫每天新增 CVE，今天 0 個 critical，下個月可能有 3 個。所以要定期（例如每週）重新掃描已部署的映像，並定期重建，讓基底的更新進來。也因為結果會變，這一課的練習不拿掃描結果判分。
  • 掃描工具本身也是供應鏈的一環。供應鏈攻擊（supply chain attack）是不直接攻擊你，而是從你依賴的套件、映像、工具下手（npm 套件的例子見 Node 課第 25 課）。2026-03-19，aquasecurity/trivy-action 的 77 個版本 tag 有 76 個被改指向竊取 CI 機密的程式，還發布了惡意的 Trivy v0.69.4；2026-03-22 Docker Hub 上又出現惡意的 v0.69.5、v0.69.6 和 latest（CVE-2026-33634）。用 tag 或 latest 引用掃描工具的 CI，就在跑竊密程式。掃描工具一樣要釘 digest 或 commit SHA。

兩種描述「映像是什麼、怎麼來的」的資料，BuildKit 可以在建置時產生，附在映像上，統稱 attestation：

  • SBOM（Software Bill of Materials，軟體物料清單）：映像裡所有套件與版本的清單。下次又有像 log4j 那樣的漏洞公布，你查 SBOM 就知道哪些映像受影響，不用一個個打開。
  • provenance（建置來源證明）：記錄映像從哪個 repo、哪個 commit、用什麼建置流程產生。部署前可以驗證「這個映像真的是我們的 CI 建出來的」。
docker buildx build --sbom=true --provenance=mode=max -t registry.example.com/cafe-api:1.4.0 --push .

attestation 掛在映像的 index（一個映像名稱底下的清單，列出各平台的映像和附加資料）上。傳統的映像儲存放不下 index：這台 Mac 的 docker info 顯示 Storage Driver 是 overlay2，就是傳統儲存，這時預設的建置器加上 --sbom／--provenance 會直接失敗。解法是在 Docker Desktop 開啟 containerd 映像儲存，或用 docker buildx create --driver docker-container 建一個獨立的建置器再 --push 到 registry。實務上這件事在 CI 裡做（第 15、16 課）。另外 mode=max 的 provenance 會記下 build arg 的值（secret mount 不會），又是一個不能用 ARG 傳機密的理由。

💡 實務上：資安問卷和漏洞公告都會來找你要清單
大客戶的資安問卷常問「你們怎麼管理第三方元件的漏洞」，新的重大漏洞公告出來時，主管會問「我們有沒有受影響」。有 SBOM、有定期掃描的紀錄，這些問題十分鐘答得出來；沒有的話要一個個映像打開翻。資深工程師會先決定門檻：critical／high 而且有修正版的才擋 CI，其他排進待辦，否則團隊很快就學會忽略掃描結果。

為伺服器的架構建置

你的 Mac 是 arm64，很多雲端主機是 amd64（x86_64）。在 Mac 上直接 docker build，產出的是 arm64 映像，放到 amd64 主機上會出現 exec format error。

指定目標平台：docker build --platform linux/amd64 …。Mac 上沒有 amd64 的 CPU，Docker Desktop 用模擬（emulation，QEMU 或 Rosetta）一條條翻譯 amd64 指令來執行，結果正確，但慢很多。於是整個建置（npm ci、tsc）都在模擬裡跑。

BuildKit 自動提供兩個 build arg：

  • BUILDPLATFORM：執行建置的機器的平台，這台 Mac 是 linux/arm64。
  • TARGETPLATFORM：要產出的平台，就是 --platform 給的值；沒給就等於 BUILDPLATFORM。

TypeScript 編譯出來的 JavaScript 跟 CPU 架構無關，所以編譯可以在 Mac 原生的架構上做，只有最終階段要是 amd64：

FROM --platform=$BUILDPLATFORM node:24.22.2-alpine3.24 AS build   # 原生 arm64，不用模擬
…
FROM --platform=$BUILDPLATFORM node:24.22.2-alpine3.24 AS deps    # pino 是純 JS，也可以
…
FROM node:24.22.2-alpine3.24                                      # 沒寫 = TARGETPLATFORM
COPY --from=deps …
COPY --from=build …
  • 最終階段只有 COPY，沒有 RUN，所以完全不需要模擬，只是下載 amd64 的基底映像。
  • 有原生模組的依賴（bcrypt、sharp）不能這樣做：在 arm64 上裝出來的是 arm64 的二進位檔。這時 deps 階段不要加 --platform，讓它在目標平台（模擬）裡安裝。
  • 不要在 Dockerfile 寫死 FROM --platform=linux/amd64：這個 Dockerfile 就只能產出 amd64，build check 會報 FromPlatformFlagConstDisallowed。平台寫在建置指令上。

同時產出兩種架構：docker buildx build --platform linux/amd64,linux/arm64 -t … --push .，結果是一個 multi-platform index，主機拉取時自動選自己的架構。跟 attestation 一樣要 index：傳統映像儲存的預設建置器會回 Multi-platform build is not supported for the docker driver，要開 containerd 映像儲存或改用 docker-container 建置器。

💡 實務上：「我電腦上好好的」常常是架構不同
團隊裡有人用 Apple Silicon、有人用 Intel，CI 和正式主機又是另一種，新同事最常遇到的部署事故就是 exec format error。資深的做法是讓 CI 統一建置與推送映像，而且寫明要哪些平台；本機建的映像只拿來開發，不推到正式的 registry。換成 AWS Graviton 這類 arm64 主機省成本時，有 multi-platform 映像就只是改機型，不用改建置流程。

執行期加固

映像乾淨了，執行方式也要收緊：就算 API 有漏洞讓攻擊者能執行程式碼，他能做的事也越少越好。

capability：Linux 把 root 的權限拆成幾十項，例如 CHOWN（改檔案擁有者）、NET_BIND_SERVICE（聽 1024 以下的 port）、NET_RAW（送任意封包）。Docker 預設給容器 14 項：

docker run --rm alpine:3.24 grep CapEff /proc/self/status
CapEff:	00000000a80425fb        # 預設的 14 項
docker run --rm --cap-drop ALL alpine:3.24 grep CapEff /proc/self/status
CapEff:	0000000000000000        # 全部拿掉
docker run --rm --cap-drop ALL alpine:3.24 chown nobody /etc/hostname
chown: /etc/hostname: Operation not permitted

cafe-api 聽 3000 port、不改檔案擁有者，一項都不需要。加固的四個選項：

選項作用擋下什麼
--read-only唯讀根檔案系統：容器不能修改映像裡的任何檔案攻擊者改程式碼、放後門、寫入 crontab
--tmpfs /tmp在 /tmp 掛一個記憶體裡的可寫目錄（預設 noexec，放進去的檔案不能執行）讓需要暫存檔的程式能動，又不打開整個檔案系統
--cap-drop ALL拿掉所有 capability；真的需要才用 --cap-add 加回一項即使是 root，也做不了 chown、送原始封包等事
--security-opt no-new-privileges程序和它的子程序不能再取得更多權限透過 setuid 程式（執行時自動取得檔案擁有者權限的程式，例如 su）從 node 使用者變成 root

加上映像裡的 USER node（不要在執行時用 --user 0 蓋掉），就是一般 Web API 該有的基本設定。Docker 預設還會套用一份 seccomp 設定檔，擋掉一般程式用不到的系統呼叫（程式向 Linux 核心要求服務的入口），不要為了省事加 --security-opt seccomp=unconfined 把它關掉。另外兩個常見的錯誤方向：遇到權限錯誤就加 --privileged，它會給容器幾乎全部的主機權限，包括存取主機的裝置；或者乾脆不用 --read-only。正確的做法是找出程式要寫哪裡，只給那裡可寫。

cafe-api 的 POST /uploads 會先把檔案寫到 TMP_DIR（預設 /home/node/uploads）再處理。開了 --read-only 之後那裡寫不進去，回 500。修法是 --tmpfs /tmp 加上 -e TMP_DIR=/tmp：兩個都要，只有 tmpfs 程式還是寫原本的地方，只有環境變數則 /tmp 也是唯讀的。

💡 實務上：加固設定最好在第一次部署就定下來
服務上線後才補 --read-only，常會發現某個功能偷偷寫入本機檔案（上傳暫存、快取、log 檔），要回頭改程式。所以新服務一開始就用唯讀加 tmpfs 跑，寫入位置都用環境變數設定。資安稽核和容器平台的安全政策（例如不允許 privileged、要求非 root）也會檢查這幾項，早點做好，之後搬平台不必重來。

第 10 課用 Compose 時，對應的寫法是 read_only: true、tmpfs: [/tmp]、cap_drop: [ALL]、security_opt: [no-new-privileges:true]。

練習

四題都在 devops/practice/work/09/ 裡做，需要 Docker Desktop 在執行，第一次建置要連網路下載 npm 套件。app/ 是精簡版的 cafe-api，app/Dockerfile 是第 8 課的單一階段寫法。用到的 port 是 127.0.0.1:18090～18094。練習 3 第一次會下載 amd64 的 node 映像。

練習 1：把 app/Dockerfile 改成多階段建置。最終階段 FROM node:24.22.2-alpine3.24，只放 package.json、正式依賴（node_modules 裡不能有 typescript、@types）和 dist/，不能有 .ts 原始碼；仍然以 node 使用者執行、保有 HEALTHCHECK。測試建置 learn-devops/cafe-api:09-1，用 docker history 算出你在基底上加了多少（上限 20MB），在映像裡檢查檔案，啟動容器確認 /health/live、uid 不是 0、狀態變成 healthy，另外用 docker save 匯出映像，檢查每一層（不只最後看到的檔案）都沒有 .ts 原始碼和 typescript，並要求 docker build --check 沒有警告。自己試：docker build -t learn-devops/cafe-api:09-1 app && docker history learn-devops/cafe-api:09-1。

練習 2：app/Dockerfile.private 建置時執行 scripts/fetch-private.mjs 下載私有套件，它從環境變數 NPM_TOKEN（或檔案 /run/secrets/npm_token）讀 token。現在的 build-secret.sh 用 build arg 傳 token。改這兩個檔案，改用 build secret（腳本不能再有 --build-arg，換個名字或放到建置階段都一樣會留下痕跡）。測試每次產生一個隨機 token，放在環境變數 NPM_TOKEN 執行 sh build-secret.sh，確認私有套件有下載到，再到 docker history --no-trunc、docker image inspect、docker save 匯出的每一層裡找這個 token，一處都不能有；docker build --check -f app/Dockerfile.private app 也不能有警告。先執行一次起始版本，自己用 docker history --no-trunc learn-devops/cafe-api:09-private 找到 token。

練習 3：咖啡店的正式伺服器是 amd64。調整 app/Dockerfile，讓編譯 TypeScript 的階段用 FROM --platform=$BUILDPLATFORM 在原生架構上執行，再完成 build-amd64.sh，產出 linux/amd64 的 learn-devops/cafe-api:09-amd64。測試執行腳本，確認映像的架構是 amd64、以 --platform linux/amd64 執行時 node -p process.arch 印出 x64、/health/live 回 200，而且 build check 沒有警告（不能把平台寫死在 Dockerfile）。練習 1 也會用這個 Dockerfile，改完兩題都要通過。

練習 4：改 run-hardened.sh，在背景執行 learn-devops/cafe-api:09-1（名稱 ld-09-hardened，發布在 127.0.0.1:18094）：唯讀根檔案系統、只有 /tmp 是 tmpfs、拿掉所有 capability、禁止取得新權限，並設定讓上傳功能正常運作。測試先用你的 app/Dockerfile 建置映像，執行腳本後用 docker inspect 檢查設定，確認程式不是以 root 執行、沒有 --privileged、沒有加回 capability、沒有另外掛可寫的目錄、沒有關掉 seccomp，最後實際上傳一個隨機大小的檔案到 POST /uploads。自己試：curl -X POST --data-binary @app/package-lock.json http://localhost:18094/uploads。

練習 5：Dockerfile 用 ARG NPM_TOKEN 接收 token，裝完私有套件後，最後一步 RUN rm -f .npmrc && unset NPM_TOKEN。映像推到 registry 之後，token 安全嗎？

✓ b。docker history --no-trunc 直接看得到 RUN |1 NPM_TOKEN=…；後面的 rm 只在新的一層加上刪除標記，前面那層的檔案還在。a 誤解了層的運作；c 說的是容器的環境變數，但 token 是從映像的 metadata 和層外洩的；d 忽略了所有能拉映像的人和 CI，私有不等於只有你看得到。

練習 6：正式環境改用 distroless 映像後，某個容器開始回 502，docker exec ld-09-app sh 回應找不到 sh。最合適的下一步是？

✓ c。除錯容器共用目標的網路和程序命名空間，看得到它的 localhost 和程序，工具不必放進正式映像。a 為了除錯放棄了攻擊面的好處，而且重新部署可能讓問題消失、查不到原因；b 不對，還有 log 和除錯容器；d 改動了正在出問題的容器，加了唯讀檔案系統時也做不到。

練習 7：CI 每次建置都用 docker scout cves --exit-code --only-severity critical 掃描，上個月建的 cafe-api:1.4.0 當時是 0 個 critical，一直沒改程式所以沒有重建。現在這個映像？

✓ a。映像內容確實沒變，但「已知的漏洞」一直在增加，同一個套件版本今天沒事、明天就可能有 CVE。b 把掃描當成一次性的；c 正好相反，釘 digest 讓建置可重現，但也代表沒有自動拿到安全更新，要靠 Dependabot／Renovate 和定期重建。

練習 8：團隊討論基底映像，有人說「Alpine 最小，所以所有服務都換成 Alpine」。你的看法？

✓ d。大小只是其中一個因素，相容性、除錯、維護成本也是。a 忽略了 musl 相容性，而且映像的攻擊面要看裡面有什麼（shell、套件管理器、是否 root），不只看大小；b 沒有根據，CVE 數量依版本與內容而定；c 無法對 Alpine 本身做到，要沒有 shell 應該選 distroless 或 DHI。

常見錯誤

  • 用 rm 刪掉機密或大檔案，以為就沒了：前面的層還在。機密用 secret mount，大檔案用多階段建置留在建置階段。
  • 把建置階段整包 node_modules 複製到最終階段：typescript、@types 全部跟著進去。另外用 npm ci --omit=dev 準備正式依賴。
  • 最終階段忘了 USER node、HEALTHCHECK：每個階段的設定互相獨立，最終階段要重寫。
  • 只看映像大小，不看裡面有什麼：有沒有 shell、套件管理器、以不以 root 執行，比少幾 MB 重要。docker history、在容器裡 ls 看一次。
  • 在 Dockerfile 寫死 --platform=linux/amd64：只能產出一種架構，check 會警告。平台寫在建置指令上，建置階段用 $BUILDPLATFORM。
  • 有原生模組的依賴也在 $BUILDPLATFORM 上安裝：產出 arm64 的二進位檔，amd64 主機一載入就失敗。這類依賴要在目標平台的階段安裝。
  • 掃描工具和 CI action 用 tag 或 latest：2026-03 的 Trivy 事件裡，tag 被改指向竊密程式。釘 digest 或 commit SHA。
  • 只在第一次建置時掃描：CVE 每天在增加，要定期重新掃描與重建。
  • 容器出現權限錯誤就加 --privileged 或改用 root：找出程式真正需要寫的目錄或 capability，只開那一項。

小結

  • 單一階段的映像帶著編譯器、原始碼、npm 快取；後面的層刪檔案不會讓映像變小。
  • 多階段建置：build 階段編譯、deps 階段裝正式依賴，最終階段從乾淨的基底 COPY --from 需要的東西，並重寫 USER、HEALTHCHECK。
  • 基底映像在大小、libc 相容性、除錯方便和攻擊面之間取捨；沒有 shell 的映像用共用命名空間的除錯容器查問題。
  • ARG、ENV、COPY 後再刪都會讓機密留在映像裡；用 RUN --mount=type=secret 和 --secret，build check 的 SecretsUsedInArgOrEnv 幫你把關。
  • 基底映像釘 digest、用 Dependabot／Renovate 更新、定期重建與掃描；掃描工具也要釘版本；SBOM 和 provenance 要推到 registry 才保留得住。
  • 為 amd64 建置：--platform 寫在指令上，純 JS 的階段用 $BUILDPLATFORM 避免模擬。
  • 執行時用 --read-only、--tmpfs、--cap-drop ALL、no-new-privileges 和非 root 使用者，把被入侵時的損害降到最小。
