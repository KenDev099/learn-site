階段 2：容器化 · 第 7 課

容器是什麼：映像、容器與隔離

在 NestJS 課第 12 課你已經用 docker compose up 跑過 PostgreSQL，第 1 課也開過用完即丟的 ubuntu 容器。指令會打了，可是幾個問題還沒有答案：容器是一台小虛擬機嗎？為什麼刪掉容器資料就不見？同一個 node:24-alpine，為什麼今天和下個月拉到的不一樣？為什麼在 Mac 上好好的映像，放到雲端主機就跑不起來？

這一課把容器拆開來看：它其實是一個被隔離的普通程序。

這課的路線：
  1. 容器和虛擬機、namespace 與 cgroup：容器是不是一台小虛擬機，核心怎麼讓一個普通程序以為自己獨占一台機器（開場問題的最小答案）。
  2. 映像、層與 multi-arch index：映像和容器差在哪，同一個 tag 為什麼下個月拉到的不一樣、要怎麼用 digest 釘住，Mac 上好好的映像為什麼到雲端主機跑不起來。
  3. 容器的一生：啟動、停止、刪除各做了什麼，一個容器壞掉時先看哪幾個欄位。
  4. 資料放哪：刪掉容器資料為什麼就不見，資料庫的資料該放在 volume 還是 bind mount。
  5. 資源限制：替容器設記憶體和 CPU 上限，讓一個洩漏的服務拖不垮整台主機。
這課會用到：
  • 第 1 課的 docker run：--rm 結束就刪、-d 背景執行、--name 取名字、-p 127.0.0.1:主機 port:容器 port 發布 port。
  • 第 3 課的程序與結束碼：容器裡第一個程式是 PID 1；記憶體超過上限時核心送 SIGKILL，結束碼 137、OOMKilled 是 true。

容器和虛擬機差在哪

虛擬機（VM）用軟體模擬整台電腦，每台 VM 都開機跑自己的作業系統核心（kernel，管理 CPU、記憶體、檔案、網路的那一層）。容器（container）沒有自己的核心：它是主機核心上的一個普通程序，只是核心替它做了隔離，讓它以為自己獨占一台機器。

所以容器啟動只要幾百毫秒（不用開機）、多開幾個也只多幾個程序。代價是：容器一定要用主機的核心。Linux 容器需要 Linux 核心，這就是 Mac 上要有 Docker Desktop 的原因：它開一台 Linux VM，容器全跑在那台 VM 的核心上（第 1 課 docker version 的 Server 是 linux/arm64）。雲端的 Linux 主機就不需要這一層，容器直接跑在主機核心上。

所以開場第一個問題的答案是「不是」：容器是主機核心上被隔離的普通程序。其他三個問題的最小答案也從這裡來：容器裡寫的檔案只放在那個容器自己的一層，刪掉容器就跟著消失（細節在後面的〈資料放哪〉）；tag 只是一個會被維護者移到新版本的名字，要固定內容得用 digest（〈映像、層與 registry〉）；映像裡是編譯好的程式，CPU 架構要跟主機一致（〈一個 tag，好幾種 CPU〉）。

隔離怎麼做到：namespace 與 cgroup

Linux 核心提供兩種機制，Docker 把它們組合起來：

  • namespace（命名空間）：控制程序看得到什麼。PID namespace 讓容器只看到自己的程序、mount namespace 讓它只看到自己的檔案系統、network namespace 給它自己的網路介面和 port、UTS namespace 給它自己的主機名稱。
  • cgroup（control group，控制群組）：控制程序能用多少。CPU、記憶體、可以開幾個程序，都能設上限。

直接看。這台 Mac 上執行：

docker run --rm --memory 64m --cpus 0.5 alpine:3.24 \
  sh -c 'ps; hostname; cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max'
PID   USER     TIME  COMMAND
    1 root      0:00 sh -c ps; hostname; cat …
    7 root      0:00 ps
7e54ba0a0f05
67108864
50000 100000
  • ps 只看到兩個程序，而且 sh 是 PID 1：PID namespace 讓它看不到 VM 裡其他上百個程序。第 3 課講過 PID 1 的特殊之處，容器裡的主程式就是 PID 1。
  • hostname 是容器 ID 的前 12 碼，不是 VM 的名字：UTS namespace。
  • memory.max 是 67108864 byte＝64 MB；cpu.max 的「50000 100000」意思是每 100 毫秒最多用 50 毫秒的 CPU，也就是半顆。這兩個檔案就是 cgroup 的設定，--memory 和 --cpus 只是幫你寫進去。
容器共用主機核心，所以隔離不如 VM 徹底：核心有漏洞、容器用 root 跑又開了 --privileged、把 Docker 的 socket 掛進容器，都可能讓容器裡的程式碰到主機。容器是好用的打包和資源隔離工具，不是萬無一失的安全邊界。第 9 課會教怎麼縮小風險（不用 root、唯讀檔案系統、拿掉多餘的能力）。

映像、層與 registry

映像（image）是唯讀的檔案系統快照加上啟動設定（要執行什麼程式、預設的環境變數、工作目錄）。容器是用映像啟動的程序。用前端的話說：映像像 class，容器像 new 出來的 instance，同一個映像可以同時開很多個容器。

映像由好幾層（layer）疊成，每一層記錄「這一步加了、改了、刪了哪些檔案」。docker history 看得到每一層是怎麼來的：

docker history alpine:3.24
CREATED BY                                        SIZE
CMD ["/bin/sh"]                                   0B
ADD alpine-minirootfs-3.24.3-aarch64.tar.gz …     8.66MB

相同的層只下載、只存一次，所以十個 Node 服務的映像不會占十倍的空間。第 8 課寫 Dockerfile 時，層的順序還決定了建置快取能不能用上。

映像存在 registry（映像倉庫）：Docker Hub、GitHub 的 GHCR、AWS 的 ECR 都是。一個映像的完整名稱是 registry/repository:tag，postgres:18.6-alpine3.24 省略了 registry（預設 Docker Hub 的 docker.io/library/）。只有一段名稱的（node、postgres、nginx）是 Docker Hub 的官方映像（Docker Official Images），由 Docker 和各專案的維護者一起維護、定期為安全更新重建。

tag 會移動，digest 不會

tag 是人取的名字，像 git 的分支：維護者隨時可以把它指到新的映像。node:24-alpine 今天是 Node 24.22.2，下個月可能是 24.23.0；就連寫到最細的 node:24.22.2-alpine3.24，也會在 Alpine 出安全修補時被重建、指到新內容。

digest 是映像內容的 SHA-256 指紋，寫成 sha256: 加 64 個十六進位字元。內容改一個 byte，digest 就不同；反過來，同一個 digest 永遠拿到同樣的內容。部署時把映像寫成 名稱:tag@sha256:…，Docker 只看 digest，tag 留著給人讀：

docker pull postgres:18.6-alpine3.24@sha256:10a5c69a83035ab5239f5620d708520e8b28f5aa1f2b20143e6024532edadfb5

這樣 staging 驗過的，跟正式環境跑的，保證是同一個東西。代價是安全更新不會自動進來，要定期（或交給 Renovate、Dependabot 這類工具）更新 digest。

💡 實務上：registry 也是正式環境的一部分
部署、擴展、機器重開，都要從 registry 下載映像；registry 連不上，新的副本就開不起來。Docker Hub 對匿名下載有次數限制，很多台機器或 CI 共用同一個對外 IP 時特別容易撞到。所以團隊通常把自己的映像放在雲端廠商的 registry（例如 AWS ECR、GitHub Container Registry），常用的基底映像也複製一份過去，部署時只依賴自己控制的 registry。

一個 tag，好幾種 CPU：multi-arch index

第 1 課說過：M 系列 Mac 是 arm64，很多雲端主機是 amd64。映像裡裝的是編譯好的程式，arm64 的程式不能在 amd64 的 CPU 上執行。平台（platform）就是「作業系統／CPU 架構」這個組合，例如 linux/arm64、linux/amd64。

那為什麼同一個 postgres:18.6-alpine3.24 在 Mac 和 EC2 上都能用？因為官方映像的 tag 指向的不是一個映像，而是一份 multi-arch index（又叫 manifest list）：一張清單，列出每個平台各自的映像。docker pull 時，Docker 依自己的平台挑對的那個。

docker buildx imagetools inspect postgres:18.6-alpine3.24
Name:      docker.io/library/postgres:18.6-alpine3.24
MediaType: application/vnd.oci.image.index.v1+json
Digest:    sha256:10a5c69a…adfb5          ← index 的 digest
Manifests:
  Name:      …@sha256:3b0ef735…           ← linux/amd64 的映像
  Platform:  linux/amd64
  …
  Name:      …@sha256:b1c1673a…           ← linux/arm64 的映像
  Platform:  linux/arm64/v8
  …

清單裡還有 Platform 是 unknown/unknown 的幾筆，那是附帶的證明資料（attestation，例如建置來源紀錄），不是能跑的映像。

釘 digest 要釘最上面那個 index 的 digest。如果你從 docker image inspect 或 Manifests 底下抄了 arm64 那一個，Mac 上一切正常，到了 amd64 的主機就拉到一個跑不動的映像。

跑錯架構時，Linux 主機上容器一啟動就結束，log 只有一行：exec format error，意思是「核心看不懂這個執行檔的格式」。Docker Desktop 會用模擬執行 amd64 映像（docker run --platform linux/amd64 alpine:3.24 uname -m 在這台 Mac 印出 x86_64），所以這個錯誤通常在你的 Mac 上看不到，要到伺服器才爆。自己建置的映像怎麼同時產生兩個平台，是第 9 課的 --platform。

容器的一生

容器的主程序結束，容器就結束。最常用的指令：

指令做什麼
docker ps／docker ps -a列出執行中的容器；加 -a 連已結束的也列出（STATUS 會寫 Exited (137) 這類結束碼）
docker logs [-f] 名稱看容器主程序寫到 stdout、stderr 的內容；-f 持續追蹤。容器結束後還看得到
docker exec -it 名稱 sh在執行中的容器裡多開一個程序，用來查看狀況
docker inspect 名稱容器的完整設定與狀態（JSON）；-f '{{.State.ExitCode}}' 只取一個欄位
docker stop 名稱先送 SIGTERM，等一段時間（預設 10 秒，-t 可改）還沒結束就送 SIGKILL；第 3 課的優雅關機就是在這段時間內完成
docker kill 名稱直接送 SIGKILL，不給收尾的機會
docker rm [-f] 名稱刪除已結束的容器；-f 連執行中的也強制刪

除錯時最有用的是 inspect 的這幾個欄位：

docker inspect -f '{{.State.Status}} {{.State.ExitCode}} {{.State.OOMKilled}}' ld-07-a
exited 137 true
docker inspect -f '{{.HostConfig.Memory}}' ld-07-a        # 記憶體上限（byte），0 是沒限制
docker inspect -f '{{json .HostConfig.PortBindings}}' ld-07-a
docker inspect -f '{{json .Config.Env}}' ld-07-a          # 環境變數（注意：密碼也會出現在這裡）

重啟策略

重啟策略（restart policy）用 --restart 設定，決定容器結束時 Docker daemon 要不要自動重開它（依 Docker 文件）：

策略程序出錯結束（結束碼非 0）你手動 stop 之後，daemon 重啟時適合
no（預設）不重開不重開一次性的工作
on-failure[:次數]重開，可限制次數不重開會因為暫時錯誤失敗的工作
always重開（結束碼 0 也重開）重開一定要一直跑的服務
unless-stopped重開（結束碼 0 也重開）不重開一般的長駐服務：當機會回來，你停掉的不會自己冒出來

容器要先跑滿 10 秒，重啟策略才開始生效，而且每次重開之間的等待會加倍，避免一個一啟動就掛的容器瘋狂重開。這和第 6 課 systemd 的 Restart=on-failure 是同一件事，只是換 Docker daemon 來看管。

💡 實務上：自動重啟會把問題藏起來
設了重啟策略之後，程式一當掉就被拉起來，docker ps 看起來一直是 Up，客人卻每隔幾分鐘遇到一次錯誤。要看的是重啟次數：docker inspect -f '{{.RestartCount}}' 名稱，數字一直增加就代表有東西反覆崩潰。正式環境會把重啟次數做成指標和告警（第 22 課、第 25 課）：重啟策略讓服務撐住，不能取代找出原因。

資料放哪：可寫層、具名 volume、bind mount

容器裡寫的檔案，預設寫在那個容器的可寫層（writable layer）。docker stop 再 start 還在，可是 docker rm 後就沒了；而升級映像的方法就是刪掉舊容器、用新映像開新容器。所以資料庫的資料絕不能留在可寫層。

  • 具名 volume（named volume）：-v ld-07-pgdata:/var/lib/postgresql。冒號左邊是名稱，Docker 在 VM 裡替你管一塊空間；第一次用時自動建立，刪容器還在。資料庫用這個。
  • bind mount：-v "$(pwd)":/w:ro（$(pwd) 換成目前資料夾的路徑，第 2 課）。冒號左邊是路徑（以 / 或 . 開頭），把主機的資料夾直接掛進去，第 3 課練習就是這樣把 eat-memory.mjs 給容器用。適合開發時的原始碼、設定檔；:ro 代表唯讀。
  • 匿名 volume：只寫 -v /var/lib/postgresql，或映像自己宣告了 VOLUME 而你沒掛東西上去，Docker 會建一個用一長串亂碼命名的 volume。它不跟可寫層一起，但很難找回來，而且下面兩個清理指令會刪掉它。

postgres 18 換了掛載路徑

網路上大部分教學寫的是 -v pgdata:/var/lib/postgresql/data。這是 17 版以前的寫法。官方 postgres 映像從 18 起把資料放在 /var/lib/postgresql/18/docker（看 docker image inspect 的 PGDATA），映像宣告的 VOLUME 也改成 /var/lib/postgresql，所以要掛上一層：

docker run -d --name ld-07-db \
  -e POSTGRES_PASSWORD="$PGPASS" \
  -v ld-07-pgdata:/var/lib/postgresql \
  -p 127.0.0.1:18070:5432 \
  postgres:18.6-alpine3.24

照舊教學掛到 /var/lib/postgresql/data，postgres:18.6-alpine3.24 會拒絕啟動，log 開頭是 Error: in 18+, these Docker images are configured to store database data in a format which is compatible with "pg_ctlcluster"，並建議改成在 /var/lib/postgresql 掛一個 volume。看到這段就知道是路徑寫錯，不是資料壞了。

-e POSTGRES_PASSWORD="$PGPASS" 把你 shell 裡的環境變數 PGPASS 傳給容器，密碼不寫在腳本裡，腳本可以放心進 git。這只是第一步：密碼還是看得到（docker inspect 的 Env），更好的做法在第 11 課。

清理：哪些指令會刪資料

映像、停掉的容器、volume 會慢慢塞滿磁碟，Docker Desktop 的 VM 磁碟滿了，所有容器都會出怪錯。先看用了多少，再決定刪什麼：

指令刪什麼風險
docker system df不刪，只列出各類占多少、多少可回收無
docker image prune沒有名字的懸空映像（dangling）低
docker image prune -a所有沒被容器用到的映像下次要重新下載
docker rm -v 名稱容器，加上它的匿名 volume；具名 volume 保留匿名 volume 的資料沒了
docker volume prune沒被容器用到的匿名 volume同上
docker volume prune -a、docker volume rm 名稱連具名 volume 一起刪資料庫的資料直接消失

「沒被容器用到」包含容器已經被你刪了的情況：你 docker rm 了資料庫容器、打算等一下用新版映像重建，這時跑 volume prune -a，資料就沒了。刪 volume 前先 docker volume ls 看清楚名字。

資源限制

不設限制時，一個容器能用光整台主機的記憶體和 CPU：一個記憶體洩漏的服務，可以拖垮同一台機器上的資料庫。--memory 設記憶體上限，--cpus 設最多用幾顆 CPU。超過記憶體上限時，核心的 OOM killer 會用 SIGKILL 殺掉容器裡的程序，結果就是第 3 課看過的結束碼 137、OOMKilled: true。

加 --memory-swap 並設成跟 --memory 一樣，代表不准用 swap；沒寫的話，容器還可以另外用跟上限一樣多的 swap，變慢而不是被殺，問題更難發現。CPU 超過 --cpus 則不會被殺，只會被限速，表現是變慢。

Node 會看 cgroup 的記憶體上限來決定 V8 heap 的上限。在這台 Mac 上用 node -p "require('v8').getHeapStatistics().heap_size_limit/1048576" 實測 node:24.22.2-alpine3.24：

--memoryheap 上限（MB）
256m259
512m259
2g1120
不設（VM 約 7.6 GB）2240

大約是上限的一半，但有下限：256 MB 的容器 heap 上限就跟容器上限差不多大，heap 還沒用滿，整個程序就先被 OOM kill，你只看到 137，看不到 Node 的 heap out of memory 訊息。小容器要自己用 NODE_OPTIONS=--max-old-space-size=… 把 heap 設得比容器上限小，留空間給 Buffer 和 Node 本身。

練習

練習 1：在 db-up.sh 寫一行 docker run，用 postgres:18.6-alpine3.24 在背景啟動 ld-07-db：超級使用者的密碼從環境變數 PGPASS 帶入、資料放在具名 volume ld-07-pgdata、5432 只發布在 127.0.0.1:18070。測試會設一個隨機的 PGPASS 執行你的腳本、用這個密碼連進去寫一筆資料（也會確認錯的密碼連不進去），接著 docker rm -f -v ld-07-db、再執行一次腳本，資料必須還在。自己試的時候先 export PGPASS=任意字串，試完 docker rm -f ld-07-db。

練習 2：在 images.lock 替 node:24.22.2-alpine3.24、postgres:18.6-alpine3.24、nginx:1.30.6-alpine 各寫一行 名稱:tag@sha256:digest。digest 要是同時包含 linux/arm64 和 linux/amd64 的 index，用 docker buildx imagetools inspect 查。測試會用你寫的 digest 去 registry 查、真的拉下來，並確認映像裡的版本跟 tag 一致（官方映像會為安全更新重建，所以不要求等於 tag 現在的 digest；你查到的就算數）。

練習 3：測試會啟動 ld-07-a、ld-07-b、ld-07-c 三個壞掉的容器，一個被 OOM kill、一個缺環境變數、一個程式聽的 port 跟發布的不一樣；哪個是哪個、記憶體上限、缺的變數名稱、聽的 port，每次都隨機。在 diagnose.sh 用 docker inspect 和 docker logs 判斷每個容器的問題，每個印一行 名稱 原因 數值（檔案開頭的註解有格式和提示）。想先手動看看，就先跑一次 node check.mjs devops 07，測試結束會清掉容器，可以照 ex3.test.ts 裡的 docker run 自己開一組來觀察。

練習 4：你 docker exec -it ld-07-web sh 進到容器裡，apk add curl 裝了 curl。接著 docker rm -f ld-07-web，用同一個映像、同樣的指令再開一個容器。curl 還在嗎？

✓ 容器的改動都寫在它自己的可寫層，映像是唯讀的、不會被改。新容器從同一個映像開始，看不到舊容器做過的事。需要的工具要寫進 Dockerfile（第 8 課）做成新映像；需要保存的資料放 volume。進容器手動改東西，下次重建就全部消失，正式環境也沒人知道你改過什麼。

練習 5：你在 M 系列 Mac 上建置了 cafe-api 的映像，推上 registry，在 amd64 的 EC2 上執行，容器馬上結束，log 只有 exec /usr/local/bin/docker-entrypoint.sh: exec format error。最可能的原因？

✓ exec format error 是核心說「這個執行檔的格式我不認得」，典型原因就是 CPU 架構不合。在 Mac 上預設只建出 arm64 的映像，而 Docker Desktop 能模擬 amd64，所以在 Mac 上測不出來。映像不是到處都能跑：它跟 CPU 架構綁在一起，要建成同時含兩個平台的 multi-arch index（第 9 課）。沒有執行權限的錯誤是 permission denied；網路問題會在拉映像時失敗，而不是啟動時。

練習 6：容器和虛擬機最大的差別是什麼？

✓ 容器沒有自己的核心，所以啟動快、占用少，也所以 Linux 容器一定要跑在 Linux 核心上（Mac 要靠 Docker Desktop 的 VM），隔離程度也不如 VM。映像裡的 alpine、ubuntu 只是使用者空間的檔案（shell、套件管理器、函式庫），不含核心。容器可以有多個程序，只是習慣上一個容器放一個服務。

常見錯誤

  • 資料寫在容器的可寫層：docker rm 或換新映像時資料就沒了。資料庫一律掛具名 volume，而且掛對路徑。
  • postgres 18 還照舊教學掛 /var/lib/postgresql/data：18 起要掛 /var/lib/postgresql；用 docker image inspect 看 PGDATA 和 Volumes 確認，不要照抄舊文章。
  • 部署用 latest 或只寫 tag：tag 會移動，同一份設定今天和明天拉到不同的東西。正式環境釘 index 的 digest，並安排定期更新。
  • 釘了單一平台的 digest：從 docker image inspect 或 Manifests 底下抄 digest，換到另一種 CPU 的主機就跑不了。釘 imagetools inspect 最上面那個 index 的 digest。
  • 隨手 docker volume prune -a、docker volume rm：容器已經刪掉的資料庫 volume 也算「沒被用到」。刪之前先 docker volume ls，確定名字。
  • 把容器當 VM：進去 apk add、改設定檔，下次重建全部消失，也沒有紀錄。要改就改 Dockerfile 或啟動參數，重建容器。
  • 不設記憶體上限：一個洩漏的服務拖垮整台機器。設 --memory（和一樣大的 --memory-swap），Node 再用 --max-old-space-size 把 heap 設得比上限小。
  • 容器起不來就猜原因：先 docker ps -a 看結束碼，docker logs 看程式說了什麼，docker inspect 看 OOMKilled、記憶體上限、環境變數、port 對應。證據都在這三個指令裡。

小結

  • 容器是共用主機核心、被 namespace（看得到什麼）和 cgroup（能用多少）隔離的程序；VM 有自己的核心。Mac 上的容器跑在 Docker Desktop 的 Linux VM 裡。
  • 映像是唯讀的層加上啟動設定，層可以共用；容器在映像上多一層可寫層，刪容器就沒了。
  • tag 會移動，digest 是內容的指紋；部署寫 名稱:tag@sha256:…，釘 multi-arch index 的 digest。
  • 容器的一生：created → running → exited → 刪除；用 ps -a、logs、inspect、exec 查狀況，stop 先 SIGTERM 再 SIGKILL；長駐服務用 --restart unless-stopped。
  • 資料放具名 volume 或 bind mount；postgres 18 掛 /var/lib/postgresql。rm -v、volume prune 刪匿名 volume，volume prune -a、volume rm 連具名的也刪。
  • 用 --memory、--cpus 設上限；超過記憶體上限是結束碼 137、OOMKilled。
  • 映像綁 CPU 架構，跑錯是 exec format error；Mac 會模擬 amd64，所以要到伺服器才看得到。
