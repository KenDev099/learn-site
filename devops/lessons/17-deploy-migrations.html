階段 4：自動化交付 · 第 17 課

部署時的資料庫 migration

第 16 課的藍綠部署有一個前提：出事時切回舊版就好。可是程式可以換回舊映像，資料庫不行。咖啡店把 customers.phone 改名為 mobile，migration 一跑完，還在線上的舊版程式就開始回 500：column "phone" does not exist。這時「切回舊版」也沒用，舊版要的欄位已經不在了。

這一課把 migration 放進部署流程，讓新舊版本同時在線、甚至回滾的時候，資料庫都不出錯。

這課的路線：
  1. migration 在哪一步跑：由部署流程裡的一次性 job 執行，成功才換程式，失敗就停，線上的舊版不受影響。
  2. 新舊版本共存與 expand／contract：為什麼改個欄位名稱就讓舊版回 500，怎麼把不相容的改動拆成幾次部署。
  3. 鎖的連鎖反應與長時間回填：一個「瞬間完成」的 ALTER 怎麼卡住整個網站，幾千萬列的舊資料怎麼補進新欄位。
  4. 權限分離與失敗的時候：migration 和 app 為什麼用不同的資料庫帳號，migration 跑到一半失敗時怎麼收拾。
這課會用到：
  • 第 16 課的藍綠部署與回滾：新版在另一組容器啟動好才切流量，出事就切回舊版。
  • PostgreSQL 課第 22 課的 migration：schema 變更寫成有順序的檔案，每個環境照順序套用，套用過的記錄在資料庫裡；lock_timeout 限制等鎖的時間。
  • PostgreSQL 課第 34 課的零停機 migration：expand／contract 先加新的、搬資料，最後才移除舊的；大量資料分批回填。

migration 在部署流程的哪一步跑

migration job 是部署流程裡專門套用 migration 的一次性步驟：用新版的映像啟動一個容器，執行 node dist/migrate.js，跑完就結束。它成功了，部署才繼續換程式；它失敗了，部署停下來，線上的舊版完全不受影響。第 10 課的一次性服務 migrate 就是它在 Compose 裡的樣子。

還有兩個常見的位置，各有問題：

在哪裡跑問題
app 啟動時（sh -c "migrate && server"）三個副本同時搶著跑；migration 很慢時，app 遲遲不聽 port，健康檢查失敗、被重啟、又從頭跑；app 的帳號必須有改 schema 的權限；migration 失敗時所有副本一起起不來
每個副本的 init container（Kubernetes 的 initContainers：每個 Pod 啟動前先跑完的容器）比上一種好一點，app 本身不用 DDL 權限，但每個副本還是各跑一次；擴展到 10 份就是 10 個程序搶同一把鎖。第 10 課 Compose 的 pre_start 對整個服務只跑一次，沒有這個問題，但它跟著服務啟動走，沒辦法在換程式之前單獨執行、單獨擋下部署
部署前的一次性 job（本課的做法）只跑一次、失敗時擋下整個部署、權限只給這一步。代價是部署流程要多一步，並等它結束

「多個副本同時跑」為什麼通常不會把 schema 弄壞？因為 migration 工具會先拿一把 advisory lock（建議鎖）：PostgreSQL 提供、由程式自己約定意義的鎖（PostgreSQL 課第 33 課），拿到的人才能套用。node-pg-migrate 9.0.0 預設就會拿，拿不到時的行為由 --advisory-lock-mode 決定，預設 fail（直接失敗），可以改成 wait（等前一個做完）。Prisma 7 的 prisma migrate deploy 也有 advisory lock，逾時固定 10 秒、不能調整。有鎖只是不會「同時套用兩次」，上面表格裡的其他問題（慢啟動、權限、一起崩潰）鎖解決不了。

在 Kubernetes 上，做法一樣：先跑一個 Job（跑到完成就結束的工作）套用 migration，成功之後才更新 Deployment（管理一組相同副本的設定）的映像。

💡 實務上：正式環境的 migration 只由部署流程執行
在第 16 課的 CD 流程裡，它通常是 deploy 之前的一個 job：用剛推上 registry 的 cafe-api:<SHA> 執行 node dist/migrate.js，結束碼是 0 才往下走。migration 帳號的連線字串放在部署流程的 secret（第 11 課），工程師不從自己的電腦連正式資料庫跑 migration，每次套用了什麼都留在部署紀錄裡。PR 裡有 migration 時，資深工程師會在 PR 描述寫出三件事：這個 migration 拿什麼鎖、在正式環境的資料量下大概跑多久、上線後能不能回滾到上一版程式，review 時特別看這一段。

新舊版本共存的那段時間

migration job 跑完到程式換完之間，線上跑的是舊版程式配新版 schema。滾動更新一台一台換，藍綠部署切換前後也有一段排空時間，這段期間新舊兩版同時讀寫同一個資料庫。出事要回滾時，又變回舊版程式配新版 schema。

所以每個 migration 都要 N-1 相容（backward compatible）：新的 schema 要讓上一版程式也能正常運作。逐一檢查常見的改動：

改動能跟程式一起上嗎原因與做法
加一個可以是 NULL 的欄位✓舊版不知道它存在。INSERT 要寫出欄位名稱（cafe-api 都有寫），SELECT * 會多拿到一欄
加新表、加索引✓索引在正式環境要用 CREATE INDEX CONCURRENTLY，下一節講
改欄位名稱、改表名✗舊版立刻找不到欄位。拆成 expand／contract，下一節
刪欄位、刪表✗等所有還在用它的版本都下線、而且確定不會回滾，才在之後的部署刪
把欄位改成 NOT NULL✗舊版的 INSERT 沒寫這欄就失敗；既有的 NULL 也會讓 ALTER 失敗。先讓程式一律寫入、回填，再加約束
改型別（integer → bigint）✗大部分會重寫整張表，期間鎖住所有讀寫。加新欄位、雙寫、回填、切換讀取

換個角度：一次部署只做一種不相容的事。schema 先改成「新舊都能用」，程式再換；程式穩定了，下一次部署才把舊的東西收掉。

expand／contract 排進部署

expand／contract（先擴充、再收斂）是 PostgreSQL 課第 22、34 課講過的模式：先加新的（新舊並存）、搬資料、最後移除舊的。第 34 課用 trigger 在資料庫裡同步兩欄；這一課換成由程式雙寫（dual write，同時寫新舊兩欄），重點放在「每一步要部署什麼、什麼時候能部署」。把 phone 改名為 mobile，要三個版本的程式：

  • v1：只讀寫 phone（現在線上的版本）。
  • v2：寫入時兩欄都寫；讀取時優先讀 mobile，還沒回填的列退回去讀 phone：coalesce(mobile, phone)。
  • v3：只讀寫 mobile。
步驟做什麼線上的版本為什麼排在這裡
① migrate 002（expand）ADD COLUMN mobile textv1v1 不知道新欄位，照常運作
② deploy v2換成雙寫的版本v1 → v2從這之後，每一筆新資料兩欄都有值
③ backfill把舊資料的 phone 分批補到 mobilev2v1 已經下線，不會再有只寫 phone 的新資料
④ deploy v3只讀寫 mobilev2 → v3所有列的 mobile 都有值了
⑤ migrate 003（contract）DROP COLUMN phonev3已經沒有任何版本讀寫 phone

換掉任何兩步的順序都會出事。回填排在 ② 之前：回填完到 v1 下線之間，v1 新增的顧客只有 phone，v3 上線後讀到 NULL。③ 排在 ④ 之後：v3 讀到還沒回填的列，一樣是 NULL。⑤ 排在 ④ 之前：v2 還在寫 phone，立刻報錯。

這也決定了回滾的範圍。②、④ 之後都還能回滾到上一版，因為 schema 還留著舊欄位。⑤ 一做下去，v2 以前的版本就回不去了，所以 contract 不要急：等 v3 在正式環境穩定跑過一段時間（例如一週），再排進之後的某一次部署。

💡 實務上：改一個欄位名稱，要跨好幾次部署
PM 會問「改個名字為什麼要兩週」：因為中間隔著三次部署，回填和 contract 之前還要等新版穩定。資深工程師會在需求單上列出每一步、在哪一次部署做、contract 預計哪一天做，並開一張「收掉 phone」的待辦。沒有這張待辦，雙寫的程式和舊欄位常常就永遠留著，下一個人看不懂為什麼有兩個電話欄位。很多時候結論是：名字沒那麼礙事，就不改了。
雙寫還是 trigger？trigger 讓資料庫自己同步兩欄，回填可以早一點做，程式也少一個過渡版本；代價是多一段藏在資料庫裡的邏輯，要記得在 contract 時一起刪掉。雙寫把邏輯留在程式裡、容易測試，但多一次部署。兩種都要遵守同一件事：同一時間在線的所有版本，看到的資料都要對。

擋住鎖的連鎖反應

N-1 相容只解決「改了之後」的問題，改的那一瞬間還有另一個風險。ALTER TABLE 幾乎都要拿 ACCESS EXCLUSIVE 鎖，跟所有讀寫都衝突。ADD COLUMN mobile text 只改中繼資料、瞬間完成，可是如果有一個跑了很久的報表正讀著這張表，ALTER 就得排隊等它；更糟的是，ALTER 後面的所有查詢都排在 ALTER 後面。這叫鎖排隊（lock queue），PostgreSQL 課第 32 課實際看過：一個「瞬間完成」的 DDL，能讓整個網站卡到報表結束為止。

正式環境的每個 migration 都要設兩個逾時：

  • lock_timeout：等鎖最多等多久，等不到就放棄（錯誤是 canceling statement due to lock timeout，SQLSTATE 55P03）。最壞情況下，app 的查詢多等這麼久。常見 1～5 秒。
  • statement_timeout：單一 SQL 最多跑多久，防止 migration 意外掃全表、重寫表跑上半小時。它要比 migration 裡最慢的那一句還長，不然永遠不會成功。PostgreSQL 18 文件提醒：statement_timeout 不是 0 時，lock_timeout 設得跟它一樣長或更長沒有意義，因為 statement_timeout 會先觸發。

兩種設定方式：寫在 migration 檔開頭（SET lock_timeout = '3s';），或在執行 migration 的那個程序設定連線參數。PGOPTIONS 環境變數是連線時送給 PostgreSQL 的參數，pg 8.23.1（node-pg-migrate 用它連線）會讀它，只影響這個程序的連線：

PGOPTIONS='-c lock_timeout=3s -c statement_timeout=60s' npx node-pg-migrate up -m migrations

等不到鎖就放棄，接下來要重試：那個報表遲早會結束。重試要有兩個限制：

  • 退避（backoff）：每次失敗後等久一點再試（1、2、4、8 秒），給卡住的交易時間結束。不等就立刻重試，等於一直插隊，每次又讓 app 的查詢多等一個 lock_timeout。
  • 次數上限：試 5 次還不行，就以非 0 結束，讓部署停下來、通知人去查是誰拿著鎖（第 32 課的 pg_locks、pg_stat_activity）。無限重試會讓部署永遠卡在這一步，也沒有人知道。

幾個跟版本有關、寫 migration 時要知道的事（PostgreSQL 18 文件與 18.6 實測）：

  • ADD COLUMN status text NOT NULL DEFAULT 'new' 不會重寫整張表：常數（和 now() 這種非 volatile）預設值只寫進中繼資料。volatile（易變）是指函式每次呼叫的結果都可能不同，同一句 SQL 裡也一樣，所以每一列都要真的算一次：clock_timestamp() 這種 volatile 預設值、stored generated column、identity 欄位會重寫整張表和索引。在 18.6 上看 pg_relation_filenode('t')：加 DEFAULT 'new' 前後不變，加 DEFAULT clock_timestamp() 之後變了（表被重寫成新檔案）。
  • 一般的 CREATE INDEX 在建好之前擋住所有寫入；CREATE INDEX CONCURRENTLY 不擋，但不能在交易區塊裡執行，失敗時會留下一個 INVALID 索引，要先 DROP INDEX 再重建。node-pg-migrate 9.0.0 的 SQL migration 檔一律包在交易裡（看它的原始碼，SQL 檔沒有關閉交易的寫法），需要 CONCURRENTLY 的那一個要改寫成 JS／TS migration，在裡面呼叫 pgm.noTransaction()。
  • 一個 migration 只放一個會拿重鎖的 DDL：同一個交易裡，前面拿到的鎖會一直拿到 COMMIT。node-pg-migrate 9.0.0 的 CLI 預設 --single-transaction，把這次所有要套用的 migration 包在同一個交易；在程式裡呼叫 runner()（cafe-api 的 migrate.ts）沒有傳 singleTransaction 時，每個 migration 各自一個交易。
💡 實務上：部署 DDL 前先看有沒有長交易
鎖排隊的元兇多半是跑很久的交易：月底的營收報表、資料匯出、某人開著沒關的 psql。動大表之前先查一次：SELECT pid, now() - xact_start AS age, state, left(query, 60) FROM pg_stat_activity WHERE xact_start < now() - interval '1 minute';。有的話先問是誰在跑，或換到離峰時段部署。部署時看到 lock timeout 不是壞事，代表保護生效了，網站沒有被拖住；要擔心的是重試 5 次都失敗，那就是有人一直拿著鎖。大表的 migration 先在 staging 用接近正式環境的資料量跑一次，量出要多久。

長時間的回填是另一個工作

回填（backfill）是把既有資料補到新欄位。第 34 課說明過為什麼不能一句 UPDATE customers SET mobile = phone 做完：一個很長的交易、拿著幾千萬列的列鎖、大量死版本與 WAL。放到部署流程裡，還要多想三件事：

  • 不放在 migration 裡。migration 要快、要在換程式前完成，而且在交易裡。回填可能跑好幾個小時，它是 expand 部署之後、由獨立的工作執行（一個一次性容器或排程工作），不擋部署。
  • 可續跑：跑到一半被殺掉（部署、主機重開、你按了 Ctrl-C），重跑要接著做，不會重做已經完成的部分，也不會把資料弄亂。條件裡加上 mobile IS NULL，已經補好的列不會再被選到。
  • 看得到進度：每批印一行「到哪個 id、這批幾列、累計幾列」。卡住時才知道卡在哪。
  • 先記下終點：開始時查一次 max(id)，只回填到那裡。回填期間線上的 v2 一直在新增顧客，這些新列本來就兩欄都寫；不設終點的話，迴圈每批都會撿到幾筆剛新增的列，永遠等不到「沒有下一批」，回填就停不下來。
// 開始時記下終點：之後新增的列由 v2 雙寫，不需要回填
const { rows: [{ end_id }] } = await client.query('SELECT coalesce(max(id), 0) AS end_id FROM customers')
// 依主鍵往後走一段，每批一句 UPDATE（自己一個交易），做完休息一下
const { rows } = await client.query(
  `WITH batch AS (SELECT id FROM customers WHERE id > $1 AND id <= $3 ORDER BY id LIMIT $2),
        done  AS (UPDATE customers c SET mobile = c.phone FROM batch
                  WHERE c.id = batch.id AND c.mobile IS NULL RETURNING 1)
   SELECT (SELECT max(id) FROM batch) AS last_id, (SELECT count(*) FROM done)::int AS updated`,
  [lastId, batchSize, end_id])

批次大小（BATCH_SIZE）用環境變數決定，不寫死：資料庫忙的時候調小，深夜調大，不必改程式重新部署。

權限分離：migration 角色與 app 角色

cafe-api 到第 10 課為止都用同一個帳號 cafe，它是資料庫的擁有者，能建表、刪表。正式環境要拆成兩個（角色與 GRANT 見 PostgreSQL 課第 24 課）：

  • migration 角色（cafe_migrator）：擁有 schema，能 CREATE、ALTER、DROP。只有 migration job 用它。
  • app 角色（cafe_app）：只有 SELECT、INSERT、UPDATE、DELETE。api 的每個副本用它。

為什麼值得多一個帳號：api 是對外的，被 SQL injection（把惡意 SQL 混進輸入）時，攻擊者能做的事就是 api 帳號能做的事。只有資料權限時，他刪不了表、加不了 trigger、改不了 schema。工程師在除錯時用 app 的連線字串手滑下了 DROP，也只會得到 permission denied。

難的地方是：表是之後 migration 才建的，現在對「還不存在的表」授權，要用 預設權限（default privileges）：

-- 以後 cafe_migrator 在 public 建的表、序列，自動給 cafe_app 這些權限
ALTER DEFAULT PRIVILEGES FOR ROLE cafe_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO cafe_app;
ALTER DEFAULT PRIVILEGES FOR ROLE cafe_migrator IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO cafe_app;
  • 常見的錯是寫 GRANT … ON ALL TABLES IN SCHEMA public：它只影響現在已經存在的表，下一個 migration 建的新表 app 又沒權限了。
  • 序列那一行給的是 serial 欄位和 nextval() 用的：沒有序列的 USAGE，新增資料時會 permission denied。GENERATED … AS IDENTITY 欄位（cafe-api 的 orders）自動取號不檢查序列權限，在 18.6 上只有 INSERT 權限也能新增；兩行都寫，之後不管 migration 用哪一種都不會出錯。
  • FOR ROLE cafe_migrator 不能省：預設權限是跟著「建表的人」走的。migration 如果改用超級使用者 postgres 跑，建出來的表就不套用這條規則。
  • 不要圖方便寫 ALL：對表的 ALL 還包含 TRUNCATE、TRIGGER、REFERENCES，PostgreSQL 17 起還有 MAINTAIN（VACUUM、REINDEX 等維護操作）；GRANT ALL ON SCHEMA public 給了建表權限，等於沒分。
  • PostgreSQL 15 起，public schema 的擁有者是 pg_database_owner（也就是資料庫擁有者），其他人預設只有 USAGE、沒有 CREATE。在 18.6 上查 pg_namespace：{pg_database_owner=UC/pg_database_owner,=U/pg_database_owner}。所以把資料庫擁有者設成 cafe_migrator，它就能在 public 建表，cafe_app 不行。從 14 以前升級上來的資料庫還保留舊的設定，要自己 REVOKE CREATE ON SCHEMA public FROM PUBLIC。

代管資料庫（雲端廠商幫你維運的資料庫，例如第 18 課會介紹的 AWS RDS）也一樣：建立時拿到的主帳號只給 migration 和管理用，app 另外建只有資料權限的角色。

失敗的時候

PostgreSQL 的 DDL 可以放在交易裡：migration 中途出錯，整個交易 ROLLBACK，schema 回到套用前的樣子，pgmigrations 也不會多一筆。例外是不能在交易裡跑的東西（CREATE INDEX CONCURRENTLY），它失敗會留下 INVALID 索引要手動清。

migration job 失敗之後：

  1. 停止部署。migration 沒成功，新版程式就不該上線；這正是把它放在換程式之前的原因。
  2. 看錯誤：等不到鎖（找出拿著鎖的人，換個時間再部署）、逾時、資料不符合新約束（例如還有 NULL，先回填）。
  3. 往前修（roll forward）：寫一個新的 migration 修正，再部署一次。已經套用到任何環境的 migration 檔絕不修改：pgmigrations 只記檔名，改了內容，正式環境不會重跑，跟 staging、同事的資料庫從此不一樣。node-pg-migrate 會檢查順序（checkOrder），晚加進來、檔名卻排在已套用的檔案前面，會直接報錯 Not run migration … is preceding already run migration …。

漂移（drift）是資料庫實際的 schema 和 migration 紀錄對不上：有人在正式環境手動 ALTER 救火、改了已套用的檔案、某個環境漏跑一個 migration。漂移會讓「在 staging 測過」失去意義。偵測方式：在 CI 用全新的資料庫跑完全部 migration，用 pg_dump --schema-only 匯出，跟正式環境匯出的 schema 比對，有差異就提醒。Prisma 7 的 prisma migrate deploy 不偵測漂移（官方文件寫明），migrate dev 會，但它是開發用指令，不能對正式環境執行。手動救火之後，一定要補一個 migration 把同樣的變更寫進紀錄。

會刪資料、改大量資料的 migration（contract、型別轉換），跑之前先確認有能還原的備份（第 24 課會教備份與還原）。DROP 掉的欄位，down migration 只能把空欄位加回來，值回不來。

工具部署時用的指令同時只跑一個
node-pg-migrate 9.0.0（本課）node-pg-migrate up（或程式裡呼叫 runner()）advisory lock，預設 fail，可改 wait；--no-lock 關閉
Prisma 7.10.1（NestJS 課第 13 課）prisma migrate deploy，官方建議在 CI/CD 執行advisory lock，逾時固定 10 秒
Prisma 8（預發行，npm 的 latest 標籤是 8.0.0-rc.29）改名為 prisma db migrate以正式版文件為準

工具不同，原則一樣：部署前跑一次、用專門的帳號、每個變更 N-1 相容、設逾時、失敗就停、不改舊檔。

練習

三題都在 devops/practice/work/17/ 裡做，需要 Docker 在跑。練習 1 用 Compose 啟動 cafe-api 和 PostgreSQL（api 發布在 127.0.0.1:18170，第一次要建置映像）；練習 2、3 的測試會自己開一個練習用的 PostgreSQL 容器 ld-17-pg（發布在 127.0.0.1，port 由 Docker 挑），每個測試建自己的資料庫，跑完就刪掉。練習 2、3 的程式在你的電腦上用 Node 24 執行，pg、node-pg-migrate 已經裝在 devops/practice/node_modules。

練習 1：把 migration 變成部署前的一步，並分開權限。db/01-roles.sql 已經建好兩個帳號：cafe_migrator（資料庫擁有者）和 cafe_app（還沒有任何權限）。在 db/02-grants.sql 讓 cafe_app 對「之後 cafe_migrator 建的表」只有 SELECT、INSERT、UPDATE、DELETE（序列要能用）。在 compose.yaml 加兩個服務，都從 ./app 建置、映像叫 learn-devops/cafe-api:17：migrate 是一次性服務，用 cafe_migrator（密碼 ${MIGRATOR_PASS}）執行 node dist/migrate.js；api 用 cafe_app（密碼 ${APP_PASS}）連 db，設 DEBUG_ENDPOINTS: "1"，只發布在 127.0.0.1:18170:3000，等 migrate 成功結束才啟動。測試執行 up --wait --build，檢查：pgmigrations 有 2 筆、POST /orders 回 201、GET /debug/db-user 回 cafe_app、表的擁有者是 cafe_migrator、cafe_app 建表會 permission denied、沒有 TRUNCATE 這類多餘的權限、對 orders 的序列有 USAGE；docker compose run --rm migrate 再跑一次不做任何事；在全新的資料庫上同時跑兩個 migrate，兩個都成功、每個 migration 只套用一次。自己試之前 export PGPASS=… MIGRATOR_PASS=… APP_PASS=…，收掉用 docker compose -p ld-17 down -v（init 腳本只在資料目錄是空的時候執行，改了 02-grants.sql 要 -v 重建）。

練習 2：不停機把 customers.phone 改名為 mobile。rename/apps/ 是三個版本的程式（v1 只用 phone；v2 兩欄都寫、優先讀 mobile；v3 只用 mobile），不要改。你要寫：002_add_mobile.sql（expand）、003_drop_phone.sql（contract），兩個都要先設 lock_timeout（測試會讓一個交易拿著 customers 的鎖，你的 migration 要在 10 秒內因等鎖逾時而失敗，例如設 '3s'）；backfill.ts：從 DATABASE_URL 連線，每批最多 BATCH_SIZE（環境變數）列、每批自己一個交易、每批印一行進度、批次之間休息一下（例如 50 毫秒，測試要求相鄰兩批的間隔中位數至少 20 毫秒）、重跑時跳過已經補好的列、只回填到開始時的最大 id（回填期間線上一直有新顧客），做完以 exit 0 結束；plan.json：把 "migrate 002"、"deploy v2"、"backfill"、"deploy v3"、"migrate 003" 排成正確的順序。測試先灌 5000 位顧客，照你的 plan 逐步執行，每一步期間讓當時在線的版本持續新增、讀取顧客（deploy 時新舊版本同時跑一段時間）；任何一個版本出錯、讀到錯的電話，或最後有人的 mobile 不對，就算失敗。另外用 BATCH_SIZE=100 回填 5000 列：印出 10 行進度時會被 SIGKILL，重跑要能做完，而且每句 UPDATE 不超過 100 列、至少 50 個交易、合計更新不超過 5000 列；照 plan 執行時用的是 BATCH_SIZE=500，批次大小寫死會被抓到。自己試：DATABASE_URL=postgres://… BATCH_SIZE=100 node backfill.ts。

練習 3：等不到鎖就放棄並重試。locks/migrations/002_orders_note.sql 會先跑約 2 秒，再對 orders 加一個欄位（不要改）。改寫 locks/migrate.sh（用 sh 執行，從 DATABASE_URL 連線，用 npx node-pg-migrate up -m migrations 套用）：每次最多等鎖 3 秒；statement_timeout 不能短到讓 migration 本身跑不完；失敗就用 sleep 等一下再試，等待時間越來越長（例如 1、2、4、8 秒），最多試 5 次，都失敗就以非 0 結束。測試先開一個讀著 orders 不結束的交易，同時每 100 毫秒查一次訂單（模擬 app 的 GET /orders/:id），再執行你的腳本：app 的請求最久不能等超過 4 秒、PostgreSQL 的 log 要看到至少一次 lock timeout、報表結束後 migration 要成功、腳本 exit 0。第二個測試讓鎖一直拿不到：腳本要在 5 次以內放棄、以非 0 結束，而且每次 sleep 的秒數越來越長。

練習 4：同事提議：「讓每個 api 副本啟動時自動跑 migration，node-pg-migrate 有 advisory lock，不會重複套用，很安全。」這個做法真正的問題是？

✓ c。鎖解決的是「重複套用」，其他問題都還在：副本互相等鎖、慢的 migration 讓 app 遲遲不聽 port 而被重啟、migration 一失敗，每個新副本都起不來，部署卡在一半。改成部署前的一次性 job。a 錯在只看到重複套用這一件事。b 錯：advisory lock 是資料庫層級的，所有連到同一個資料庫的程序都看得到；d 錯：PostgreSQL 的 DDL 大多可以放在交易裡，失敗會整個回滾。

練習 5：v2 上線時一起跑了刪掉 phone 的 migration。一小時後發現 v2 有 bug，要回滾到 v1。怎麼辦？

✓ b。程式能回滾的前提是 schema 還相容於舊版。a 是最常見的誤解：v1 一上線就會 column "phone" does not exist。c 只能把空欄位加回來，刪掉的值回不來，而且這一小時 v2 寫入的資料只在 mobile 裡。

練習 6：在 PostgreSQL 18 對一張 5000 萬列的表執行 ALTER TABLE orders ADD COLUMN status text NOT NULL DEFAULT 'new'，會重寫整張表嗎？

✓ a。PostgreSQL 11 起，非 volatile 的預設值存在中繼資料，讀到舊列時直接補上。NOT NULL 不會讓它改成逐列寫入（b 錯），既有的列讀出來就是預設值。c 是 PostgreSQL 10 以前的行為。不重寫不代表不用鎖：它仍要拿 ACCESS EXCLUSIVE 鎖，等鎖的那段時間一樣會造成鎖排隊，所以照樣要設 lock_timeout。

練習 7：004_add_loyalty.sql 已經套用到 staging 和 production，現在發現少加了一個索引。怎麼辦？

✓ d。已套用的 migration 只記檔名，a 改了內容也不會重跑，各環境從此不一致；b 造成漂移，staging 和新同事的資料庫都沒有這個索引；c 會讓 004 的其他內容再執行一次（例如重複加欄位而失敗）。往前修：新的檔案、新的部署。大表上建索引記得用 CONCURRENTLY（node-pg-migrate 要寫成 JS／TS migration 並呼叫 pgm.noTransaction()）。

常見錯誤

  • 在 app 啟動時跑 migration：每個副本都跑、慢啟動導致健康檢查失敗、app 需要 DDL 權限、失敗時全部起不來。改成部署前的一次性 job，失敗就停止部署。
  • 同一次部署改了 schema 又改程式，兩者不相容：舊版在新 schema 上出錯，也回滾不了。每個 migration 都要 N-1 相容，改名、刪欄位拆成 expand／contract 分次部署。
  • 忘了 lock_timeout：DDL 排在長交易後面，所有查詢跟著排隊，網站卡住。每個 migration 先設 lock_timeout，等不到就放棄、退避重試、有次數上限。
  • statement_timeout 設得比 migration 需要的還短：永遠不會成功。要比最慢的那一句長，而且 lock_timeout 要比它短。
  • 把 CREATE INDEX CONCURRENTLY 放在交易裡：直接報錯；node-pg-migrate 的 SQL 檔一定在交易裡，要寫成 JS／TS migration 並 pgm.noTransaction()。失敗留下的 INVALID 索引要先刪掉再重建。
  • 一個 UPDATE 回填上千萬列：長交易、大量列鎖、WAL 暴增、中途失敗全部重來。分批、每批一個交易、可續跑、印進度，在部署之後以獨立工作執行。
  • app 用資料庫擁有者的帳號連線：被 SQL injection 時整個 schema 都能被改。app 只給資料權限，用 ALTER DEFAULT PRIVILEGES FOR ROLE 讓之後建的表自動授權。
  • 修改已經套用的 migration 檔：已套用的環境不會重跑，從此跟紀錄對不上。寫新的 migration 往前修。
  • 新版穩定前就做 contract：刪掉舊欄位之後就回不去了。contract 排在之後的部署，而且先確認有備份。

小結

  • migration 是部署前的一次性 job：用這次要上線的映像跑一次，成功才換程式，失敗就停止部署。工具的 advisory lock 只防止重複套用。
  • 新舊程式會同時在新 schema 上跑，回滾時也是，所以每個 migration 都要 N-1 相容；不相容的改動拆成 expand → 部署雙寫版 → 回填 → 部署新版 → contract。
  • 每個 DDL 都設 lock_timeout，等不到就放棄、退避重試、有次數上限；statement_timeout 要比 migration 需要的長。常數預設值的 ADD COLUMN 不重寫表；CONCURRENTLY 不能在交易裡。
  • 回填是獨立的工作：分批、每批一個交易、可續跑、印進度、批次大小可調，開始時先記下終點。
  • migration 角色擁有 schema，app 角色只有 SELECT／INSERT／UPDATE／DELETE，用預設權限涵蓋之後建的表。
  • 失敗時停止部署、往前修，不改已套用的檔案；用 schema 比對偵測漂移，高風險的 migration 前先確認備份。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：同事昨天在你的 PR 分支上推了一個修測試的 commit，你沒拉下來，在本機 rebase 到最新的 main 後執行 git push --force。結果會怎樣？

✓ --force 不檢查遠端，直接用你本機的分支蓋掉，你本機沒有的 commit 就不在分支上了。別人已經拿到或推過的分支不改寫：把 main merge 進來；分支真的只有你在推，才 rebase 再 --force-with-lease。a 是一般 git push 的行為，加了 --force 就跳過這個檢查。（第 14 課）

練習 9：同事想讓 fork 來的 PR 跑測試時也拿得到 NPM_TOKEN，把 workflow 改成這樣。哪裡會出事？

on: pull_request_target
jobs:
  test:
    steps:
      - uses: actions/checkout@… # v7
        with:
          ref: ${{ github.event.pull_request.head.sha }}
          allow-unsafe-pr-checkout: true
      - run: npm ci && npm test
        env: { NPM_TOKEN: "${{ secrets.NPM_TOKEN }}" }

✓ pull_request_target 帶著可寫的權杖和機密，是給加標籤、留言這種不碰 PR 程式碼的工作；在裡面跑 PR 的測試和套件腳本，等於把它們交給陌生人。測 PR 用 pull_request，fork 的 PR 本來就拿不到機密。b 錯在 permissions 只管 GITHUB_TOKEN，NPM_TOKEN 還是在環境變數裡被讀走。（第 15 課）

練習 10：週五晚上 production 自動擴容多開了一台，新的那台結帳一直出錯，它的 /version 跟另外三台不一樣。部署設定寫的是 image: ghcr.io/cafe/cafe-api:latest，為什麼？

✓ tag 是會移動的名牌，latest 每次推送都換指向；誰在什麼時候拉，就拿到當下那一個。部署和回滾一律用 digest，伺服器跑的一定是指名的那個映像，也查得到它是哪個 commit。b 剛好反過來：每次都拉最新的 latest，副本之間只會更不一致。（第 16 課）

練習 11：下午 3 點藍綠部署 v2 之後，結帳錯誤率從 0.1% 跳到 8%。這次沒有 migration，舊顏色的 v1 還在跑。值班的你第一步做什麼？

✓ 出事的預設動作是先回滾：它快，而且不需要先搞懂 bug 在哪。能這樣做的前提是 schema 還相容舊版，這次沒有 migration，切回去 v1 就能正常跑。a 是往前修，適合問題很小、修正很明確或不能回滾時，在壓力下現場寫修正，錯誤率要等整個 CI 和部署跑完才會降。（第 16 課）

練習 12：部署 workflow 裡 migration 和部署這樣寫（省略 runs-on 與 IMAGE 的設定）。哪裡會出事？

  migrate:
    needs: build
    steps:
      - run: docker run --rm "$IMAGE" node dist/migrate.js
  deploy:
    needs: build
    steps:
      - run: sh deploy.sh "$IMAGE"

✓ job 預設平行，needs 只保證排在 build 之後，不保證 migrate 先於 deploy。改成 deploy 寫 needs: [build, migrate]：migration 成功才換程式，失敗就停止部署。a 是最多人漏看的：兩個都等 build，彼此之間卻沒有順序。（第 15、17 課）

練習 13：要把 customers.phone 改名為 mobile，同事排的順序是：① 加 mobile 欄位 → ② 把 phone 回填到 mobile → ③ 部署雙寫的 v2 → ④ 部署只用 mobile 的 v3 → ⑤ 刪掉 phone。哪裡會出事？

✓ 回填要排在雙寫的 v2 上線之後，那時才不會再有只寫 phone 的新資料：expand → 部署 v2 → 回填 → 部署 v3 → contract。b 錯在加一個可以是 NULL 的欄位是 N-1 相容的，v1 的 INSERT 有寫出欄位名稱，不知道新欄位也照常運作。（第 17 課）

練習 14：migration 是 ALTER TABLE orders ADD COLUMN note text，平常一瞬間就完成。這次部署時，所有讀寫 orders 的 API 都卡了 4 分鐘，剛好等於財務報表跑完的時間，其他 API 正常。為什麼？

✓ ALTER TABLE 要拿 ACCESS EXCLUSIVE 鎖，得等報表的交易結束；它排隊的期間，後面的查詢也排在它後面，這就是鎖排隊。每個 migration 設 lock_timeout，等不到就放棄、退避重試、有次數上限。a 錯在可以是 NULL、沒有預設值的欄位只改中繼資料，不重寫表；慢的不是 ALTER 本身，是等鎖。（第 17 課）

練習 15：expand 的 migration 裡，同事在加完 mobile 之後直接寫了 UPDATE customers SET mobile = phone;，customers 有 800 萬列。哪裡會出事？

✓ 回填可能跑好幾個小時，不能放在必須快速完成、而且在交易裡的 migration；中途失敗就全部重來。改成部署之後的獨立工作：分批、每批一個交易、可續跑、印進度。a 錯在 UPDATE 拿的是列鎖，只擋同一列的寫入，讀取照常。（第 17 課）
