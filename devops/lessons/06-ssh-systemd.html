階段 1：伺服器基本功 · 第 6 課

在伺服器上跑服務：SSH 與 systemd

咖啡店租了一台雲端主機，要把 API 放上去。第一個問題是怎麼「進去」：主機在機房裡，你只有它的 IP。第二個問題是怎麼讓 API 一直活著：你在終端機打 node server.mjs，關掉視窗程式就跟著結束；半夜程式當掉沒人重開；主機重開機後也不會自己起來。

這一課解決這兩件事：SSH 讓你安全地登入伺服器、傳檔、連到伺服器內部的服務；systemd 負責啟動服務、掛了自動重啟、收集 log、開機自動執行。

這課的路線：
  1. SSH 金鑰登入與 ssh config：怎麼安全地「進去」一台只知道 IP 的主機，為什麼正式環境不用密碼登入。
  2. known_hosts 與加固 SSH：看到「主機身分改變」警告時怎麼判斷，22 port 開在網路上要先關掉哪些設定。
  3. systemd：寫一份 unit 檔，讓 API 掛了自動重啟、開機自動起來。
  4. 操作與除錯：部署新版後為什麼還在跑舊程式碼，服務起不來時用 systemctl、journalctl 找原因。
  5. systemd、pm2 與容器：各適合什麼情況，為什麼下一階段改用容器。
這課會用到：
  • 第 2 課的權限：chmod 600 只有擁有者能讀寫；服務用專屬的一般使用者跑，需要管理權限時才用 sudo。
  • 第 3 課的停止流程：先送 SIGTERM 讓程式收尾，等太久才送不能攔截的 SIGKILL。
  • 第 5 課的身分驗證：對方用私鑰簽名、你用公鑰驗證，確認連到的是真的伺服器而不是冒充者。

SSH 與金鑰登入

SSH（Secure Shell）是一個加密的遠端連線協定：你在 Mac 上打指令，指令透過加密的 TCP 連線（預設 22 port）送到伺服器執行，結果再傳回來。伺服器上負責接聽的程式叫 sshd（d 是 daemon，背景服務的意思）。

登入可以用密碼，但正式環境一律用金鑰對（key pair）：一把私鑰（private key）留在你的電腦，一把公鑰（public key）放到伺服器。登入時伺服器出一道題，只有持有私鑰的人答得出來，私鑰本身從頭到尾不離開你的電腦。密碼會被猜、被釣魚、會在很多地方重複使用；私鑰猜不到，也不會在網路上傳。

產生金鑰用 ssh-keygen。ed25519 是一種橢圓曲線簽章演算法，金鑰短、快、安全，OpenSSH 9.5 起 ssh-keygen 不加 -t 時預設就產生這種（macOS 與 Ubuntu 24.04 都已是 9.5 以上），這裡還是明確寫出來：

ssh-keygen -t ed25519 -C "ken@cafe-laptop"     # -C 是註解，放在公鑰最後，方便辨認是誰的
# 產生 ~/.ssh/id_ed25519（私鑰）和 ~/.ssh/id_ed25519.pub（公鑰）
cat ~/.ssh/id_ed25519.pub
# ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA… ken@cafe-laptop

公鑰只有一行，可以公開貼給任何人。要讓伺服器接受它，就把這一行加進伺服器上該使用者的 ~/.ssh/authorized_keys（一行一把公鑰），ssh-copy-id 指令就是在做這件事。

私鑰的權限必須是 600（只有自己能讀寫，第 2 課）。權限太寬時 ssh 會直接拒絕使用，顯示 WARNING: UNPROTECTED PRIVATE KEY FILE!：別人讀得到的私鑰，等於已經外洩。

產生金鑰時 ssh-keygen 會問 passphrase：用來加密私鑰檔的密碼，私鑰檔被偷走也打不開。每次輸入很煩，所以有 ssh-agent：一個背景程式，解鎖一次之後替你保管私鑰。macOS 可以用 ssh-add --apple-use-keychain ~/.ssh/id_ed25519 把 passphrase 存進鑰匙圈。

在 AWS 建立 EC2 主機時下載的 .pem 檔就是私鑰，AWS 只把公鑰放進主機。它只能下載一次，下載後先 chmod 400 cafe.pem（只有自己能讀），用 ssh -i cafe.pem ubuntu@<IP> 登入；Ubuntu 映像的預設使用者是 ubuntu。這個檔案不能放進 git、不能傳到伺服器上、不能貼到聊天室。
💡 實務上：一人一把金鑰，離職時才撤銷得掉
咖啡店請了第二位工程師，最省事的做法是把建主機時下載的 cafe.pem 傳給他。問題在之後：有人離職時你沒辦法只撤銷他，只能換掉整把金鑰、通知每個人。正確做法是每個人用自己的金鑰，公鑰各占 authorized_keys 一行，-C 寫上名字；離職時刪掉那一行。資安稽核會問「誰能登入正式主機、怎麼撤銷」，人數變多後改用下面會講的 SSM Session Manager，把權限交給帳號系統管。

第一次連線：TOFU

第一次連到一台伺服器，ssh 會顯示對方主機金鑰的指紋（fingerprint）：把公鑰算成雜湊值（hash，固定長度的摘要，內容差一個位元結果就完全不同），方便人用眼睛比對並問你要不要相信：

The authenticity of host '[127.0.0.1]:18060' can't be established.
ED25519 key fingerprint is SHA256:QUdOi0rSLaQ/4xTpfhn8vnAa4lkfkyL0QkBKIU611kQ.
Are you sure you want to continue connecting (yes/no/[fingerprint])?

回答 yes 之後，主機公鑰被寫進 ~/.ssh/known_hosts，之後每次連線都會比對。這種「第一次相信並記住，之後對不上就警告」的做法叫 TOFU（trust on first use）。它的弱點在第一次：如果那一刻有人在中間冒充伺服器（第 5 課的中間人攻擊），你記住的就是冒牌貨。SSH 沒有 TLS 那種 CA 替你背書，所以要自己用另一個管道確認指紋：雲端主控台的系統 log、建立主機時的輸出，或請已經登入的同事在伺服器上執行

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
# 256 SHA256:QUdOi0rSLaQ/4xTpfhn8vnAa4lkfkyL0QkBKIU611kQ root@cafe-server (ED25519)

兩邊一樣才回答 yes。自動化腳本沒有人能回答，常見的做法是先用 ssh-keyscan 從網路取得主機金鑰、跟可信的指紋比對後才寫進 known_hosts，練習 1 就是這樣做。

ssh config 與日常操作

每次打 ssh -i ~/.ssh/cafe.pem -p 2222 ubuntu@203.0.113.10 又長又容易錯。ssh config（~/.ssh/config）替主機取別名，把這些參數記起來：

Host cafe
  HostName 203.0.113.10
  User ubuntu
  Port 22
  IdentityFile ~/.ssh/cafe.pem
  IdentitiesOnly yes

之後 ssh cafe 就好。IdentitiesOnly yes 讓 ssh 只用 IdentityFile 指定的金鑰；沒有它，ssh 會把 agent 裡的每把金鑰都拿去試，金鑰一多就會在試到對的之前被伺服器以「嘗試次數太多」斷線。ssh -G cafe 印出 ssh 最後採用的所有設定，設定不如預期時用它查。

日常操作：

ssh cafe                              # 登入，得到伺服器上的 shell
ssh cafe 'uptime && df -h /'          # 不登入，直接在伺服器上執行指令，結果印在本機
scp app.tar.gz cafe:/tmp/             # 複製檔案過去（也可以反過來）
rsync -a --delete app/ cafe:/opt/cafe-api/   # 同步資料夾：只傳有變的部分，--delete 刪掉對方多出來的檔案

scp 每次都整份複製；rsync 先比對兩邊，只傳差異，大資料夾第二次同步幾乎是瞬間。兩者都走 SSH，所以 ssh config 的別名和金鑰設定都適用。注意 rsync 的來源路徑結尾有沒有 / 意思不同：app/ 是「app 裡面的東西」，app 是「app 這個資料夾本身」。

SSH 通道：連到只在伺服器內部開放的服務

資料庫、管理介面這類服務只該聽 127.0.0.1 或內網，從網路上連不到（第 4 課）。那你自己要怎麼連？用 SSH 的通道（port forwarding）：

ssh -L 15432:db.internal:5432 cafe
#      ↑本機 port  ↑從伺服器的角度看的目的地

ssh 在你的 Mac 上聽 15432；連到 localhost:15432 的流量，透過加密的 SSH 連線送到伺服器，再由伺服器連到 db.internal:5432。目的地是「從伺服器的角度」解析的，所以 127.0.0.1:9000 指的是伺服器自己的 9000 port。正式環境常見的架構是跳板機（bastion host）：整個網路只有它對外開 SSH，資料庫和應用程式主機都只能從它連。第 18 課連 RDS 資料庫就是這樣做。

在腳本裡開通道有兩個陷阱：通道還沒建好就去連，以及腳本結束後通道沒關、背景留下一個 ssh 程序。常見的錯誤寫法是 ssh -N -L … & sleep 2：用 sleep 猜時間，port 被占用時 ssh 只印警告、繼續執行，你連到的是別人的服務。正確的寫法：

ssh -f -N -M -S ./tunnel.sock -o ExitOnForwardFailure=yes -L 18061:127.0.0.1:9000 cafe
trap 'ssh -S ./tunnel.sock -O exit cafe' EXIT
curl -fsS http://localhost:18061/stats
選項作用
-N不執行遠端指令，只做轉送
-f連線和驗證完成後才進背景，ssh 指令返回時通道已經可以用
-o ExitOnForwardFailure=yes轉送建立不起來就以非 0 結束，而不是只印警告
-M -S ./tunnel.sock這條連線當主連線（ControlMaster），開一個控制 socket（ControlPath）
-S ./tunnel.sock -O exit透過控制 socket 叫那條背景連線結束，不必去找它的 PID

trap … EXIT（第 2 課）保證腳本不論成功或失敗都會關掉通道。

💡 實務上：用通道查正式資料庫的規矩
客服回報某筆訂單金額不對，要查正式資料庫：開通道（第 18 課經過跳板機連 RDS）、用唯讀帳號、查完馬上關。通道開著時，你電腦上任何程式都能透過 localhost:15432 連到正式資料庫。-L 預設只聽本機的 localhost，不要改成 -L 0.0.0.0:15432:…，否則同一個 Wi-Fi 的人也連得到。很多團隊要求連正式資料庫前在頻道說一聲要查什麼，事後才查得到是誰、為什麼連。

known_hosts 與「主機身分改變」警告

有一天連線時看到：

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
…
Offending ED25519 key in /Users/ken/.ssh/known_hosts:12
Host key verification failed.

意思是：這個位址現在出示的主機金鑰，跟你 known_hosts 第 12 行記住的不一樣。可能是伺服器重建了（新主機產生了新的主機金鑰，雲端上換機器、重灌、同一個 IP 被分配給別台機器都會這樣），也可能是有人在冒充。ssh 分不出來，所以拒絕連線。

處理順序：先問「這台機器最近有沒有重建？」並用另一個管道比對新指紋。確認是合法的變更之後，只刪掉那一台的舊紀錄：

ssh-keygen -R 203.0.113.10            # 刪掉這個主機的舊紀錄
ssh-keygen -R '[127.0.0.1]:18060'     # 非 22 port 的主機在 known_hosts 裡寫成 [主機]:port

不要刪整個 known_hosts（其他主機的紀錄也一起丟了，下次全部要重新 TOFU），更不要在 ssh config 裡寫 StrictHostKeyChecking no：那等於永遠不檢查對方是誰，所有中間人攻擊都會成功。自動化流程要信任新主機，用 StrictHostKeyChecking accept-new（新主機自動記住，已知主機的金鑰改變時照樣拒絕），或像練習 1 一樣先比對再寫入。

版本差異：OpenSSH 10.1（2025-10-06）起，連線協商到不是後量子（post-quantum）的金鑰交換演算法時，ssh 會印出警告（由 WarnWeakCrypto 控制，預設開啟），提醒你那台伺服器的 OpenSSH 太舊。同一版也把 ssh-agent 的 socket 從 /tmp 移到 ~/.ssh/agent。練習伺服器是 Ubuntu 24.04 的 OpenSSH 9.6p1，支援後量子金鑰交換，所以不會出現這個警告。

讓 SSH 更安全

只要 22 port 對整個網路開放，幾分鐘內就會有自動化程式來試帳號密碼。伺服器上的 /etc/ssh/sshd_config（Ubuntu 建議放在 /etc/ssh/sshd_config.d/*.conf）至少要有：

PasswordAuthentication no          # 不接受密碼登入
KbdInteractiveAuthentication no    # 也不接受「鍵盤互動」這種變相的密碼登入
PermitRootLogin no                 # 不准用 root 直接登入：先用一般使用者登入，需要時 sudo

改完先用 sudo sshd -t 檢查語法，用 sudo sshd -T | grep -i passwordauth 看實際生效的值（同一個設定寫在好幾個檔案時，先讀到的那個生效；雲端主機第一次開機時套用設定的 cloud-init 常會放一個 50-cloud-init.conf，裡面可能寫著 PasswordAuthentication yes），再 sudo systemctl restart ssh。保留目前的連線，另開一個視窗確認新設定能登入，再關掉舊的：設定寫錯時，舊連線是你唯一的救生索。

網路層再加三道：

  • 限制來源：雲端的安全群組（security group，主機外面的防火牆）只允許你的 IP 連 22 port，第 18 課會設定。
  • fail2ban：一個讀 sshd log 的服務，同一個 IP 失敗太多次就用防火牆暫時封鎖。已經關掉密碼登入時它主要是減少 log 噪音。
  • 完全不開 22 port：AWS 的 SSM Session Manager 由主機上的 agent 主動連出去，你透過 AWS 的權限系統（第 19 課）登入，每次登入都有稽核紀錄。團隊規模變大時這比管理一堆 authorized_keys 好。

systemd：讓服務一直活著

程式要在伺服器上長期執行，需要有人負責：開機時啟動它、它掛了重新啟動、收集它的輸出、關機時通知它結束。大多數 Linux 發行版（包括 Ubuntu）由 systemd 做這件事，它是開機後第一個程序（PID 1），其他所有服務都由它啟動和看管。

用 nohup node server.mjs & 讓程式在登出後繼續跑，看起來也可以，但：程式當掉沒人重開、重開機後不會起來、log 寫到哪個檔案沒人管、要停掉它得自己找 PID。systemd 把這些都處理了。

每個服務用一個 unit 檔描述，放在 /etc/systemd/system/<名稱>.service。咖啡店 API 的 unit：

[Unit]
Description=Cafe API
Wants=network-online.target
After=network-online.target

[Service]
Type=exec
User=cafe
Group=cafe
WorkingDirectory=/opt/cafe-api
EnvironmentFile=/etc/cafe-api.env
ExecStart=/usr/bin/node server.mjs
Restart=on-failure
RestartSec=2
TimeoutStopSec=20
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes

[Install]
WantedBy=multi-user.target
設定意思
Wants=／After=network-online.target等網路設定好之後才啟動。After 只管順序，Wants 才會真的把網路那個 target 拉起來，所以兩個都要寫
Type=execnode 執行起來就算啟動成功。預設的 simple 在 fork 之後就算成功，連程式路徑打錯都不會讓 start 失敗；exec 會。forking 是給會自己 fork 到背景、讓前景程序結束的老式 daemon 用的，Node 不會這樣做，用了 systemd 會一直等到啟動逾時
User=cafe用專屬的一般使用者執行。沒寫就是 root：程式被入侵時，攻擊者直接拿到整台機器
WorkingDirectory程式的目前資料夾，ExecStart 裡的相對路徑以它為準
EnvironmentFile從檔案載入環境變數（每行 KEY=value，程式用 process.env 讀，Node 課第 2 課）。密碼放這裡，檔案擁有者 root、權限 600。不要寫成 Environment=DB_PASSWORD=…：unit 檔任何使用者都能用 systemctl cat、systemctl show 看到
ExecStart要執行的指令，程式要寫絕對路徑
Restart=on-failure非 0 結束、被訊號殺掉（SIGTERM、SIGINT 這類正常停止的訊號除外，例如 kill -9 會重啟）、逾時時重新啟動。預設是 no：掛了就不管
RestartSec=2等 2 秒再重啟（預設 100ms），避免依賴的服務還沒好就一直撞
TimeoutStopSec=20stop 時先送 SIGTERM，20 秒內沒結束就送 SIGKILL（預設 90 秒）。設成比程式的優雅關機時間稍長
NoNewPrivileges、ProtectSystem=strict、ProtectHome、PrivateTmp沙箱：不能透過 setuid 程式（像 sudo 這種一執行就以擁有者身分、通常是 root 執行的程式）提權、整個檔案系統唯讀（要寫的地方用 ReadWritePaths= 開放）、看不到 /home、有自己的 /tmp
WantedBy=multi-user.targettarget 是一組 unit 的集合點，代表開機的某個階段；multi-user.target 是一般伺服器開機完成的狀態。systemctl enable 時把服務掛進這個階段。沒有 [Install] 段落就無法 enable

以上預設值以 Ubuntu 24.04 的 systemd 255 為準（freedesktop.org 的 systemd.service 說明，並在練習伺服器上用 systemctl show 確認過）。

程式收到 SIGTERM 時要自己優雅關機（Node 課第 21 課）：systemctl stop 送的就是 SIGTERM，跟 第 3 課的 docker stop 一樣。

操作與除錯

sudo systemctl daemon-reload             # 新增或修改 unit 檔之後：讓 systemd 重新讀取
sudo systemctl enable cafe-api           # 開機自動啟動（建立 multi-user.target.wants/ 裡的連結）
sudo systemctl enable --now cafe-api     # enable 並且馬上 start
sudo systemctl restart cafe-api          # 停掉再啟動：部署新程式碼後用這個
systemctl status cafe-api                # 狀態、MainPID、最近幾行 log
systemctl is-active cafe-api             # 只印 active／inactive／failed，腳本好用
systemctl show -p MainPID,NRestarts,Result cafe-api

兩個容易搞混的地方：start 只是現在啟動，重開機後不會起來，要 enable；enable --now 對已經在跑的服務什麼都不做，所以部署新版本時要 restart，不然跑的還是舊程式碼。

systemd 會收集每個服務的 stdout 和 stderr，交給 journald 存起來，用 journalctl 查：

journalctl -u cafe-api -f                 # 持續顯示新的 log，像 tail -f
journalctl -u cafe-api --since "10 min ago"
journalctl -u cafe-api -n 50 --no-pager   # 最後 50 行
journalctl -u cafe-api -p err             # 只看 error 以上

程式不用自己寫 log 檔，印到 stdout 就好（第 21 課再談集中 log）。

崩潰迴圈

如果程式一啟動就掛（例如設定檔少了一個變數），Restart= 會一直重啟它。systemd 有啟動頻率限制：預設 10 秒內啟動超過 5 次就放棄，服務變成 failed，log 出現 Start request repeated too quickly。這時重開沒用，要先看 journalctl -u cafe-api -n 50 找出程式為什麼掛，修好之後 systemctl reset-failed cafe-api 清掉計數再啟動。Restart=always 一樣受這個限制。

限制算的是「10 秒內啟動了幾次」，所以 RestartSec 越長越撞不到：上面的 unit 用 RestartSec=2，10 秒內最多啟動 5 次，不會超過，服務會每 2 秒重啟一次、永遠停不下來（在練習伺服器的 systemd 255 上實測：RestartSec=2 的服務 25 秒內重啟 9 次仍在重啟，預設 100ms 的早已變成 failed）。所以不能只看 status 是不是 active：systemctl show -p NRestarts 是服務被自動重啟過的次數，這個數字一直漲就是崩潰迴圈。

除錯的順序：systemctl status 看狀態和最後幾行 log → journalctl -u 看完整 log → systemctl cat 確認 systemd 讀到的 unit 跟你以為的一樣（忘了 daemon-reload 時，這裡還是舊的，status 也會提示 changed on disk）→ 用 unit 裡的身分手動跑一次：sudo -u cafe node /opt/cafe-api/server.mjs。

💡 實務上：半夜 API 掛了，先恢復再找原因
告警說 API 沒回應，SSH 上去先 systemctl status cafe-api：failed（放棄了）還是 activating（還在重啟）？接著 journalctl -u cafe-api --since "30 min ago" 往上找第一個錯誤，崩潰迴圈最後幾行通常只是同一個錯誤一直重複。再對時間：掛掉的時間點是不是剛好有人部署、改了 env 檔？是的話先把上一版放回去 restart，讓客人能點餐，再慢慢查根因。事後在事故紀錄寫下時間軸和指令，下次值班的人才有東西可以照著做（第 25 課）。

systemd、pm2 與容器

Node 世界裡也常見 pm2：一個用 Node 寫的程序管理工具，負責重啟和 log。它本身也需要有人在開機時啟動它，pm2 startup 做的就是產生一個 systemd unit。

systemdpm2容器（下一階段）
誰負責重啟systemd（PID 1）pm2 的背景程序Docker 的 restart policy、Kubernetes
log 去哪journaldpm2 自己的 log 檔容器的 stdout，由平台收集
隔離可以加沙箱設定，但共用主機的 Node 版本和套件幾乎沒有自己的檔案系統、Node 版本、網路
怎麼部署rsync 程式碼、在主機上裝套件、restart同左，或 pm2 deploy建一個映像，到哪台主機都一樣

systemd 適合一兩台主機、一兩個服務。問題在「在主機上裝套件」：每台主機的 Node 版本、系統函式庫可能不一樣，正式環境和你的電腦也不一樣，部署變成在每台主機上重做一遍安裝。下一階段改用容器，就是把程式和它需要的一切打包成一個映像。即使用了容器，主機上的 Docker 本身還是由 systemd 啟動的，這一課的知識不會白學。

練習

練習在一台「伺服器」容器裡做：Ubuntu 24.04、systemd 是 PID 1、sshd 只接受金鑰登入，SSH 發布在 127.0.0.1:18060，使用者 ubuntu 可以免密碼 sudo（雲端主機的預設也是這樣），系統使用者 cafe 已經建好。先在 learn 資料夾執行一次 node check.mjs devops 06，起始檔會複製到 devops/practice/work/06/。第一次會建置伺服器的映像，大約一分鐘。三題都在 work/06 裡做，練習 2、3 會用到練習 1 的金鑰和 ssh_config。想自己動手試：

cd devops/practice/work/06
sh keygen.sh && sh server/up.sh && sh trust-host.sh
ssh -F ssh_config cafe-server          # 登入練習伺服器，exit 離開
docker rm -f ld-06-server              # 用完關掉

-F ssh_config 讓 ssh 只讀這個資料夾的設定，不碰你自己的 ~/.ssh/config。

練習 1：金鑰登入。（1）完成 keygen.sh：在 keys/id_ed25519 產生 ed25519 金鑰（已經有就不重產，私鑰權限 600），把公鑰複製成 authorized_keys（server/up.sh 會把它裝到伺服器上）。（2）在 ssh_config 寫好 Host cafe-server：127.0.0.1 的 18060 port、使用者 ubuntu、只用 ./keys/id_ed25519、主機金鑰記在 ./known_hosts。（3）完成 trust-host.sh：用 ssh-keyscan 取得伺服器的主機金鑰，跟 docker exec ld-06-server ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub 的指紋比對，一樣才寫進 known_hosts，不一樣就以非 0 結束、known_hosts 保持原樣。測試會放一台用不同主機金鑰的冒牌伺服器占住 18060，你的腳本要拒絕它；再換回真的伺服器，最後執行 ssh -F ssh_config cafe-server whoami，要得到 ubuntu。提示：ssh-keygen -lf 檔案 | awk '{print $2}' 取出指紋。

練習 2：部署並交給 systemd 看管。app/server.mjs 是只用 Node 內建模組的咖啡店 API（伺服器上已經有 /usr/bin/node），從環境變數讀 PORT、APP_ENV、DB_PASSWORD；設定在 cafe-api.env。（1）完成 cafe-api.service。（2）完成 deploy.sh：把 app/ 同步到伺服器的 /opt/cafe-api/，用 sudo 把 unit 裝到 /etc/systemd/system/cafe-api.service、env 檔裝到 /etc/cafe-api.env（擁有者 root、權限 600；sudo install -o root -g root -m 600 來源 目的地 一次做完），讓 systemd 讀到新的 unit、設成開機啟動，並用新的程式碼（重新）啟動。所有操作都透過 cafe-server 這個 SSH 別名，跟操作真的雲端主機一樣：測試執行 deploy.sh 時 docker 指令不能用。測試會執行 deploy.sh 兩次（中間把伺服器上 systemd 載入的 unit 換成「上一版」），然後檢查：服務 active 且 enabled、第二次部署後 systemd 用的是新的 unit、主程序換了一個、主程序的使用者是 cafe、unit 檔裡沒有密碼、改了 /etc/cafe-api.env 並 restart 後程式讀到新值、kill -9 主程序後 5 秒內自動回來、systemctl stop 後 journal 有 shutdown complete 且 Result 是 success。

練習 3：用 SSH 通道連內部服務。伺服器上有一個 admin 服務只聽 127.0.0.1:9000，GET /stats 回傳 JSON，裡面的 token 每次伺服器啟動都不一樣。完成 tunnel.sh：開一條本機 18061 → 伺服器 127.0.0.1:9000 的背景通道，確定建立成功之後才抓 http://localhost:18061/stats 存成 stats.json，結束前（不論成功或失敗）關掉通道。測試會檢查 token、結束後沒有留下 ssh 程序、伺服器只發布了 22 port；然後先占用 18061 再執行一次，這時必須以非 0 結束而且不留下 ssh 程序；最後連續執行 5 次都要成功。

練習 4：第一次 SSH 到新建的雲端主機，ssh 顯示指紋並問你要不要繼續連線。正確的做法是？

✓ c：TOFU 的弱點在第一次，這一刻如果有人冒充，你記住的就是冒牌貨，所以要用網路以外的管道確認指紋。a 是大多數人的習慣，等於不檢查；b 讓之後每次連線都不檢查，連「主機身分改變」的警告也看不到；d 用密碼登入一樣是連到同一台（可能是冒牌的）主機，密碼還會直接交給對方。

練習 5：今天 SSH 到 cafe 時出現 WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!，應該怎麼做？

✓ b：警告代表「這個位址出示的主機金鑰跟上次不同」，可能是重建也可能是冒充，要先確認原因。a 把其他主機的紀錄也丟了，而且一樣沒確認；c 正是攻擊者希望你做的事，你的操作和輸入都會被對方看到；d 搞錯方向，這個警告是關於伺服器的主機金鑰，跟你的金鑰無關。

練習 6：cafe-api 設定了 Restart=always，部署後程式一啟動就因為缺少環境變數而結束。幾秒後 systemctl status 顯示 failed，不再重啟。為什麼？

✓ a：崩潰迴圈會撞到 StartLimitIntervalSec／StartLimitBurst（預設 10 秒、5 次），log 有 Start request repeated too quickly。修好原因後用 systemctl reset-failed 清掉計數。b 說的接近 on-abnormal，always 連正常結束也重啟；c 沒寫時用預設 100ms；d systemd 不解讀 log 內容。

練習 7：同事說「API 要聽 80 port，非 root 不能開 1024 以下的 port，所以 unit 檔不能寫 User=cafe」。比較好的回應是？

✓ d：用 root 跑應用程式，程式被入侵時影響範圍是整台主機。正式環境的 API 前面本來就有反向代理處理 TLS 和流量（第 12 課），API 自己聽高 port 就好。a 不正確，還有反向代理或只給特定權限（AmbientCapabilities=CAP_NET_BIND_SERVICE）的做法；b 防火牆擋不住從 80 port 合法進來、利用程式漏洞的攻擊；c sudo 群組是讓人執行 sudo 指令，不會讓程式自動有 root 權限，而且一樣擴大了權限。

常見錯誤

  • 私鑰權限太寬：ssh 顯示 UNPROTECTED PRIVATE KEY FILE 並拒絕使用。chmod 600（AWS 的 .pem 用 400）。
  • 為了方便設 StrictHostKeyChecking no：從此不檢查伺服器身分。自動化用 accept-new，或先比對指紋再寫入 known_hosts。
  • 把私鑰複製到伺服器上或放進 repo：私鑰只放在用它登入的那台電腦。要從伺服器 A 連到 B，用跳板設定（ProxyJump）或各自的金鑰。
  • 在 unit 檔裡寫密碼：任何使用者都能 systemctl cat。放 EnvironmentFile，檔案 root 擁有、權限 600。
  • 改完 unit 檔忘了 daemon-reload：systemd 還在用舊設定，status 會提示 changed on disk。
  • 只 start 沒有 enable：重開機後服務沒起來。用 enable 並確認 [Install] WantedBy=multi-user.target。
  • 部署時用 enable --now 以為會換新版：服務已經在跑時它什麼都不做，部署要 restart。
  • 用 nohup node & 取代 systemd：掛了不重啟、開機不啟動、log 沒人管。
  • 22 port 對全世界開放：安全群組只開給自己的 IP，或改用 SSM Session Manager 完全不開。
  • 腳本裡用 sleep 等通道建立：太短會失敗，port 被占用時還會連到別人的服務。用 -f 加 ExitOnForwardFailure=yes，結束時用 -O exit 關掉。

小結

  • SSH 是雙向驗證：伺服器用 authorized_keys 裡的公鑰驗證你，你用 known_hosts 驗證伺服器。私鑰權限 600、永遠不離開你的電腦。
  • 第一次連線是 TOFU，要從另一個管道比對指紋；「主機身分改變」的警告先查原因，確認後才 ssh-keygen -R 那一筆。
  • ssh config 替主機取別名；scp 整份複製、rsync 只傳差異；ssh -L 把只在伺服器內部開放的服務接到本機，腳本裡用 -f、ExitOnForwardFailure=yes、控制 socket 開關通道。
  • sshd 關掉密碼與 root 登入，sshd -t 檢查後再重啟，保留舊連線；網路層限制來源 IP。
  • systemd unit：專屬使用者、EnvironmentFile 放 secret、Type=exec、Restart=on-failure、合理的 TimeoutStopSec、沙箱設定、WantedBy=multi-user.target。
  • 改 unit 要 daemon-reload，開機啟動要 enable，部署新版要 restart；看 log 用 journalctl -u；崩潰迴圈會撞到 10 秒 5 次的限制。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：咖啡店的流程是 merge 後 CI 建置映像、部署到 staging；測過之後，正式環境的 pipeline 從同一個 commit 再 docker build 一次才部署。staging 全部通過，正式環境卻出錯。問題最可能出在哪？

✓ 映像只建置一次，staging 和正式環境跑同一個映像、只換設定；回滾也是把上一個映像再部署一次。每個環境各建一次，套件和基底映像都可能在兩次建置之間變了，staging 的驗證就不算數。a 錯在同一份程式碼不保證同一份產物，這正是「只建置一次」要避免的。（第 1 課）

練習 9：這支備份腳本每晚由排程執行，$1 是設定資料夾。哪裡會出事？

#!/usr/bin/env bash
set -euo pipefail
src="${1:?需要來源資料夾}"
out="/backup/cafe-config.tar.gz"
tar -cz -C "$src" . > "$out"

✓ 重新導向先清空再寫，tar 讀到一半失敗，留下的是壞掉的檔案，前一晚的好備份也被蓋掉。改成寫到輸出檔旁邊的 mktemp 暫存檔，成功才 mv 換上去，trap 清掉暫存檔。a 錯在 tar 是單獨一個指令，失敗時 set -e 會讓腳本停下並回非 0，問題是停下時舊備份已經被清空了。（第 2 課）

練習 10：午餐尖峰時咖啡店 API 的容器自己結束了，結束碼 137，那段時間沒有人部署或執行 docker stop。第一步該做什麼？

✓ 137 是被 SIGKILL 殺掉（128+9），來源只有兩種：記憶體超過上限被核心殺掉，或收到 SIGTERM 停不下來、逾時後被殺。沒有人送停止訊號，就先查 OOMKilled，是 true 再去找記憶體用量。b 修的是「docker stop 等滿逾時」那一種，這次沒有人叫它停。（第 3 課）

練習 11：新機器上的 cafe-api 連資料庫，立刻得到 connect ECONNREFUSED 10.0.2.15:5432。同事說「是安全群組沒開 5432」。你先查什麼？

✓ refused 是封包到了對方主機、對方回 RST：那個位址的 port 沒人在聽。去主機上用 ss -ltnp 看程式有沒有跑、聽在哪個位址。被安全群組或防火牆擋掉時封包會被丟掉，看到的是等很久之後 timeout，所以 a 查錯了層，還把資料庫開給全世界。（第 4 課）

練習 12：本機開發時，API 要呼叫一個用公司自建 CA 簽發憑證的內部服務，Node 回報不信任的簽發者。該怎麼處理？

✓ 錯誤說的是「不信任簽發者」，就把那個 CA 加進信任清單，身分驗證保持開著。b 是關掉身分驗證：還是有加密，但對面是誰都接受，中間人直接成功；這種設定最常見的下場是一路被複製到正式環境。c 錯在問題出在信任，不是名稱。（第 5 課）

練習 13：certbot 前天自動續期成功，伺服器上的 fullchain.pem 用 openssl 看還有 80 天，今天客人卻開始看到憑證過期的錯誤。最可能的原因是？

✓ 伺服器啟動時把憑證讀進記憶體，續期只換了磁碟上的檔案，要 reload 才生效。所以到期監控要連線讀伺服器實際送出的憑證，不能只看檔案。b 缺中繼憑證的錯誤是「不信任的簽發者」，而且瀏覽器通常會自己補，不會報成過期。（第 5 課）

練習 14：部署腳本用 rsync 傳了新程式碼、改了 unit 檔（加上 EnvironmentFile），最後執行 sudo systemctl enable --now cafe-api。服務是 active，但 API 還是舊版的行為，也沒讀到新設定。原因是？

✓ 改 unit 要 daemon-reload，部署新版要 restart；enable 只管開機啟動。systemctl cat 和 status 的 changed on disk 提示可以確認 systemd 讀到的是哪一版。c 錯在 env 檔是 systemd 用 root 讀的，讀完才切換成 cafe 啟動程式，root 擁有、600 正是建議的設法。（第 6 課）

練習 15：咖啡店請了第二位工程師，他需要 SSH 到正式主機部署。怎麼給他權限？

✓ 伺服器只需要公鑰，私鑰永遠不離開持有人的電腦。一人一把、公鑰各占 authorized_keys 一行，有人離職時刪掉那一行就撤銷了他。a 是最常見的做法：之後沒辦法只撤銷一個人，只能換掉整把金鑰、通知每個人。（第 6 課）
