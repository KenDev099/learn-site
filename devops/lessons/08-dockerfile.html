階段 2：容器化 · 第 8 課

Dockerfile：把咖啡店 API 裝進映像

第 7 課用的都是別人做好的映像：nginx、postgres。咖啡店 API 是你自己寫的 TypeScript 程式，要放進容器，就得自己做映像。同事照著「在新主機上手動部署」的步驟寫了一份 Dockerfile，結果建置失敗；修到能建置之後，每改一行程式要等很久，docker stop 時訂單寫到一半，容器還是用 root 在跑。

這一課從手動部署的步驟開始，一行一行寫出能上線的 Dockerfile。

這課的路線：
  1. 從手動步驟到 Dockerfile、建置情境：把「在新主機上手動部署」的步驟翻成 Dockerfile，並且不把 Mac 上的 node_modules、.env 帶進映像。
  2. 層快取：為什麼改一行程式要等很久，指令怎麼排才能重用上次的結果。
  3. CMD、PID 1、執行身分與 NODE_ENV：docker stop 時訂單為什麼寫到一半、怎麼不用 root 跑，NODE_ENV 放錯位置為什麼讓建置失敗。
  4. HEALTHCHECK：容器在跑不代表程式能回應，讓 Docker 定期檢查。
  5. 版本資訊與檢查：半夜告警時怎麼知道線上跑的是哪一版，用 build check 在 CI 抓出 Dockerfile 的常見錯誤。
這課會用到：
  • Node 課第 3 課的 npm：npm ci 完全照 lockfile 安裝；dependencies 是執行時要的套件，devDependencies 只在開發和建置時用。
  • Node 課第 5 課的 tsc：把 TypeScript 編成 JavaScript，Node 執行的是編出來的檔案。
  • 第 3 課的 PID 1 與訊號：docker stop 先送 SIGTERM 給 PID 1，10 秒內沒結束就送 SIGKILL，結束碼 137。
  • 第 7 課的映像與層：映像由好幾層疊成，每層記錄這一步改了哪些檔案；用 docker inspect 看容器的狀態。

從手動步驟到 Dockerfile

假設你拿到一台全新的 Linux 主機，要把 cafe-api 跑起來，大概會這樣做：

手動步驟Dockerfile 指令說明
裝好 Node 24FROM node:24.22.2-alpine3.24從官方的 Node 映像開始，Node 和 npm 都裝好了
mkdir /app && cd /appWORKDIR /app之後的指令都在 /app 裡執行；資料夾不存在會自動建立
把程式碼複製過去COPY 來源 目的地從你電腦上的建置情境（下一節）複製到映像裡
npm ci、npm run buildRUN 指令在建置過程中執行一個指令，結果存成新的一層
設定環境變數ENV 名稱=值會留在映像裡，容器執行時也看得到
開防火牆的 3000 portEXPOSE 3000只是說明「這個程式聽 3000」，不會真的開 port；開 port 還是靠 docker run -p
建一個一般使用者來跑服務USER node之後的 RUN 和容器裡的程式都用這個使用者
node dist/server.jsCMD ["node", "dist/server.js"]容器啟動時預設執行的指令；只是記在映像裡，建置時不會執行

Dockerfile 就是把這些步驟寫成檔案：一行一個指令，從上往下執行，每個 RUN、COPY 都會產生一層（第 7 課講過層）。照著表格寫出來，這一課的目標版本長這樣：

# syntax=docker/dockerfile:1
FROM node:24.22.2-alpine3.24
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci

COPY . .
RUN npm run build

ENV NODE_ENV=production
EXPOSE 3000
USER node
HEALTHCHECK …（後面講）
CMD ["node", "dist/server.js"]

第一行 # syntax=docker/dockerfile:1 不是一般的註解，而是解析器指示（parser directive）：告訴建置引擎用最新的 1.x 版 Dockerfile 語法，這樣新功能和下面的 build check 都能用。它一定要寫在檔案最前面。

在 app/ 資料夾裡執行 docker build -t learn-devops/cafe-api:dev . 就會建出映像。-t 給映像取名字和 tag；最後那個 . 很重要，下一節講。負責建置的程式叫 BuildKit：Docker 目前的建置引擎，會快取每一步的結果、能同時執行互不相關的步驟，也支援建置時用的 secret（第 9 課）。

建置情境與 .dockerignore

docker build . 的那個 . 是建置情境（build context）：Docker 會把這個資料夾裡的檔案打包送給 BuildKit，COPY 只能複製建置情境裡的東西。所以 COPY . . 的意思是「把建置情境的全部複製到 WORKDIR」，你資料夾裡有什麼，映像裡就有什麼。

問題是開發用的資料夾裡通常有這些：

  • node_modules/：在 Mac 上 npm install 裝的。有些套件會依平台安裝不同的檔案，例如 TypeScript 7.0.2 的編譯器是原生程式，npm 依作業系統和 CPU 從 optionalDependencies 挑一個：Mac 上裝的是 @typescript/typescript-darwin-arm64，Linux 容器裡需要的是 @typescript/typescript-linux-arm64。把 Mac 的 node_modules 複製進去，輕則多幾百 MB，重則在 Linux 上跑不起來。
  • .env：本機的資料庫密碼。進了映像，任何能拉這個映像的人都拿得到。
  • .git/：整個版本歷史，包括曾經 commit 過又刪掉的機密。

.dockerignore 放在建置情境的根目錄，列出不要送進去的檔案，語法跟 .gitignore 很像：

# 在 Mac 上裝的套件不能進 Linux 映像，映像裡由 npm ci 重新安裝
node_modules
# 編譯結果在映像裡重新產生
dist
# 機密與版本控制
.env
.env.*
.git

被排除的檔案根本不會送到 BuildKit，所以 COPY . . 也複製不到它們。建置輸出裡 load build context 那一步的 transferring context: 21.65kB 就是這次送了多少（cafe-api 的原始碼只有這麼多）；如果看到幾百 MB，先檢查 .dockerignore。

.dockerignore 只擋建置情境，不擋你明確寫出來的東西。.env 被排除後，Dockerfile 裡寫 COPY .env . 會直接建置失敗，這是好事；設定和機密應該在執行時給（第 11 課），不是燒進映像。
💡 實務上：.dockerignore 是資安檢查的一環
映像常被推到公司的 registry，甚至公開的 Docker Hub；裡面有 .env 就等於把資料庫密碼發給每個能拉映像的人。資安稽核和 code review 會看 .dockerignore 有沒有擋 .env*、.git、金鑰檔。新專案先寫好它；接手舊專案時，用 docker run --rm -it --entrypoint sh 映像 進去 ls -a 確認一次。RUN rm .env 不算修好：檔案還在 COPY 那一層，拿到映像就拆得出來。

層快取：指令的順序決定建置要多久

BuildKit 執行每一步之前，會先看層快取（layer cache）：如果這一步的指令一樣、用到的輸入（COPY 的檔案內容、前一層）也一樣，就直接拿上次的結果，不再執行，建置輸出會標示 CACHED。只要有一步的輸入變了，這一步和它後面所有步驟都要重新執行，因為每一層都疊在前一層上面。

原始碼每天改好幾次，套件清單偶爾才改，所以原則是：越少變的放越前面。先只 COPY package.json package-lock.json ./、RUN npm ci，再 COPY . .。兩個檔案都要複製：npm ci 照 lockfile 安裝，沒有 lockfile 會直接失敗。

用 --progress=plain 可以看到每一步有沒有用快取（輸出在 stderr）。在這台 Mac 上第一次建置時，npm ci 花了 20.3 秒；改一行 routes.ts 後重新建置，順序 B 的輸出：

docker build --progress=plain -t learn-devops/cafe-api:dev .
#9 [3/6] COPY package.json package-lock.json ./
#9 CACHED
#10 [4/6] RUN npm ci
#10 CACHED
#11 [5/6] COPY . .
#11 DONE 0.6s
#12 [6/6] RUN npm run build
#12 DONE 10.7s

同樣的修改，順序 A 每次都要再花 20 秒重新下載、安裝所有套件。專案的依賴越多差越多；CI 每個 PR 都要建置（第 15 課），差距會乘上每天的建置次數。

不要用 docker build --no-cache 或改成 npm install 來「解決」奇怪的建置問題。--no-cache 讓每次都從頭來；npm install 可能更新 lockfile，裝到的版本跟你測過的不一樣。快取有問題時，先用 --progress=plain 看是哪一步失效、為什麼。

CMD、PID 1 與執行身分

CMD 有兩種寫法：

exec 形式shell 形式
寫法CMD ["node", "dist/server.js"]CMD node dist/server.js
實際執行直接執行 node/bin/sh -c "node dist/server.js"
PID 1nodesh（見下面的例外）
能用 $VAR、&&不能（沒有 shell 幫你展開）能

第 3 課講過，docker stop 把 SIGTERM 送給 PID 1，sh 當 PID 1 時不會轉送訊號，10 秒後 Docker 送 SIGKILL，結束碼 137，優雅關機（Node 課第 21 課）一行都沒跑。在 node:24.22.2-alpine3.24 實測 sh -c 'node dist/server.js; echo bye'：PID 1 是 sh，docker stop 花了 10.5 秒、結束碼 137。

例外是：alpine 的 sh（BusyBox）遇到只有一個指令的 -c，會直接用那個指令取代自己，實測 CMD node dist/server.js 的 PID 1 是 node。但這是 shell 的實作細節，換一個基底映像、或哪天加了 &&，就會變回 sh。一律寫 exec 形式，build check 的 JSONArgsRecommended 規則也會對 shell 形式的 CMD 提出警告。

CMD ["npm", "start"] 也不好。實測 PID 1 是 npm，node 是它的子程序。npm 11.19.1 會把 SIGTERM 轉給 node，docker stop 1.5 秒就結束；但多了一個常駐的程序吃記憶體，啟動時 npm 還會連 registry 檢查新版、在 log 印出 npm notice New major version of npm available!。npm 只是幫你跑一行指令，直接寫那一行就好。

ENTRYPOINT 與 CMD：ENTRYPOINT 是固定要執行的程式，CMD 是給它的預設參數；兩個都有時，實際執行的是「ENTRYPOINT + CMD」。docker run 映像 其他參數 會換掉 CMD，--entrypoint 才換得掉 ENTRYPOINT。一般的 API 服務只寫 CMD 就夠，docker run … sh 就能直接進去看；把映像做成一個指令列工具（例如 ENTRYPOINT ["tofu"]）時才用 ENTRYPOINT。

不要用 root 執行

沒寫 USER 時，容器裡的程式是 root（uid 0）。容器的隔離不是萬無一失（第 7 課），程式有漏洞被拿到 shell 時，root 能改映像裡的任何檔案、能裝工具，遇到核心或設定的漏洞時離主機也更近。官方 Node 映像內建一個 uid 1000 的使用者 node，在 CMD 前面加 USER node 就好。

注意 COPY 進來的檔案擁有者是 root，node 使用者只能讀、不能寫。cafe-api 只讀程式碼，這樣反而安全；如果程式需要寫某個資料夾，用 COPY --chown=node:node 或 RUN mkdir … && chown node:node … 只開放那個資料夾。

💡 實務上：上線前先看 Dockerfile 的最後三行
接手別人的服務或審 PR 時，資深工程師通常先看結尾：有沒有 USER、CMD 是不是 exec 形式、有沒有 HEALTHCHECK。這三件事出錯都不會讓建置失敗，要到正式環境才出事：部署時每個容器多等 10 秒被 SIGKILL、訂單寫到一半中斷；被入侵時對方直接是 root。shell 形式的 CMD 可以在 CI 用 docker build --check 擋下；漏了 USER、HEALTHCHECK 它不會報，要寫進團隊的 PR 檢查清單。

NODE_ENV 要放在哪裡

同事的 Dockerfile 第二行就是 ENV NODE_ENV=production，接著 RUN npm install、RUN npm run build，結果：

> cafe-api@1.4.2 build
> tsc
sh: tsc: not found
ERROR: failed to build: … "/bin/sh -c npm run build" did not complete successfully: exit code: 127

ENV 從那一行之後對每個 RUN 都有效。npm 看到 NODE_ENV=production 時預設不安裝 devDependencies（npm 11 的文件：npm install、npm ci 都一樣），而 typescript 正是 devDependency，所以 tsc 找不到，127 是「找不到指令」的結束碼。NODE_ENV 不只影響執行期，也影響安裝。把 ENV NODE_ENV=production 移到 npm run build 之後：建置時有完整的工具，執行時是 production 模式。

這樣做的代價是映像裡還留著 TypeScript 和型別定義，第 9 課用多階段建置把它們拿掉。

HEALTHCHECK：讓 Docker 知道程式還好不好

容器在執行，不代表程式能回應：可能卡在無窮迴圈、事件迴圈被擋住、連線用光。HEALTHCHECK 讓 Docker 定期在容器裡執行一個指令，結束碼 0 是健康，1 是不健康：

HEALTHCHECK --interval=10s --timeout=3s --start-period=10s --start-interval=1s --retries=3 \
  CMD ["node", "-e", "fetch('http://127.0.0.1:3000/health/live').then(r => process.exit(r.ok ? 0 : 1), () => process.exit(1))"]
參數預設意思
--interval30s每隔多久檢查一次
--timeout30s一次檢查超過這個時間就算失敗
--start-period0s啟動的寬限期：這段時間內失敗不算數，成功一次就結束寬限期
--start-interval5s寬限期內的檢查間隔（Docker Engine 25 起支援）
--retries3連續失敗幾次才算 unhealthy

健康狀態一開始是 starting，檢查成功一次變成 healthy，連續失敗 retries 次變成 unhealthy。docker ps 的 STATUS 欄會顯示，詳細紀錄（每次檢查的輸出和結束碼）用 docker inspect --format '{{json .State.Health}}' 容器 看。

檢查指令要用映像裡有的程式。網路上的範例常寫 curl -f http://localhost:3000/ || exit 1，但 alpine 映像沒有 curl，每次檢查都是「找不到指令」，容器永遠 unhealthy；alpine 只有 BusyBox 的精簡版 wget，slim 系列的 Debian 映像連 wget 都沒有。Node 映像裡一定有 node，Node 24 內建 fetch，用 node -e 最可靠。網址寫 127.0.0.1：檢查在容器裡面執行，連的是容器自己。

檢查的是 liveness 端點 /health/live：只回答「程序還活著、能處理請求」，不檢查資料庫。另一種是 readiness /health/ready：「準備好接流量了嗎」，資料庫斷線或正在關機時回 503，讓負載平衡器先別送請求過來。兩者的差別和用法在第 13 課細講；這裡只要記住，資料庫掛了不代表 API 程序要重啟。

容器變成 unhealthy 之後，單純的 docker run 和 Docker Compose 不會重啟它。重啟策略（--restart）只看程序有沒有結束，unhealthy 只是一個狀態標記。會根據健康狀態換掉容器的是編排器，例如 Swarm、Kubernetes（Kubernetes 用自己的 probe，不看 Dockerfile 的 HEALTHCHECK）。Compose 會用健康狀態決定啟動順序（第 10 課）。

ARG、ENV 與版本資訊

半夜收到告警，第一個問題是「線上跑的是哪一版？」。答案應該寫在映像裡。git 用 commit SHA 識別每一個 commit：40 個十六進位字元，git rev-parse HEAD 可以取得目前的（第 14 課細講）。

建置時從外面傳值進來，用 ARG：

# 有預設值
ARG APP_VERSION=dev
# 沒給就是空字串
ARG GIT_SHA

docker build --build-arg GIT_SHA=$(git rev-parse HEAD) --build-arg APP_VERSION=1.4.2 -t learn-devops/cafe-api:1.4.2 .

Dockerfile 的註解一定要自己一行：# 寫在指令後面不算註解。實測 ARG GIT_SHA # 註解 會被當成宣告了 GIT_SHA、#、註解 三個 ARG。

ARGENV
在哪裡有值只在建置時，宣告之後的指令建置時和容器執行時都有
從外面改docker build --build-argdocker run -e
會留在映像的設定裡不會會（docker inspect 看得到）

只寫 ARG GIT_SHA，程式執行時 process.env.GIT_SHA 是 undefined。要用 ENV GIT_SHA=$GIT_SHA 把建置時的值留給執行期。另外加上 OCI label：寫在映像上的標準中繼資料（OCI 是制定容器映像格式的組織），不用啟動容器就查得到：

ENV APP_VERSION=$APP_VERSION \
    GIT_SHA=$GIT_SHA
LABEL org.opencontainers.image.version=$APP_VERSION \
      org.opencontainers.image.revision=$GIT_SHA

docker image inspect --format '{{json .Config.Labels}}' learn-devops/cafe-api:1.4.2

ARG 放的位置會影響快取

Dockerfile 參考文件寫明：ARG 之後的每個 RUN 都會把它當成環境變數，值改變時，宣告之後第一個用到它的指令就會快取失效，而所有 RUN 都算用到。GIT_SHA 每個 commit 都不同，如果把 ARG GIT_SHA 寫在 RUN npm ci 前面，每次建置 npm ci 都要重跑，前一節的順序就白排了。版本資訊放在最後，npm run build 之後。

💡 實務上：事故時先問「現在跑的是哪個 commit」
客服回報結帳壞了，第一步是確認線上版本：curl https://api…/version 或 docker image inspect 看 label，拿 SHA 去 git log 找這次部署多了哪些 commit。版本號由 CI 在建置時自動帶入（第 15 課），不要手動改；映像的 tag 也用同一個 SHA，回滾時才知道要退回哪一個（第 16 課）。
ARG 和 ENV 都不能拿來傳密碼或 token：ENV 留在映像設定裡，ARG 的值會出現在 docker history。第 9 課示範並教正確的做法（build secret）。

檢查與除錯

build check：BuildKit 內建一組 Dockerfile 常見錯誤的規則（需要 Dockerfile 語法 1.8、Buildx 0.15 以上），docker build --check . 只檢查、不建置，有違規時結束碼不是 0：

docker build --check .
JSON arguments recommended for CMD to prevent unintended behavior related to OS signals
Dockerfile:10
  10 | >>> CMD npm start
…
docker build --check .          # 修好之後
Check complete, no warnings found.

一般的 docker build 也會跑這些規則，但只印警告、照樣成功。在 Dockerfile 開頭加 # check=error=true，違規就讓建置失敗，適合放進 CI。其他常見規則：SecretsUsedInArgOrEnv（名稱像密碼的 ARG／ENV）、UndefinedVar（用了沒定義的變數）、CopyIgnoredFile（COPY 了被 .dockerignore 排除的檔案）。

看映像的每一層是哪個指令產生、多大：

docker history --format '{{.CreatedBy}}\t{{.Size}}' learn-devops/cafe-api:dev
CMD ["node" "dist/server.js"]                   0B
HEALTHCHECK {Test:[CMD node -e fetch('http:/…   0B
USER node                                       0B
…
RUN /bin/sh -c npm run build # buildkit         5.94kB
COPY . . # buildkit                             21.4kB
RUN /bin/sh -c npm ci # buildkit                44.6MB
COPY package.json package-lock.json ./ # bui…   18.7kB
WORKDIR /app                                    0B
CMD ["node"]                                    0B     ← 從這裡往下是基底映像的層

只改設定的指令（ENV、USER、CMD）大小是 0，真正占空間的是 npm ci 那一層，第 9 課會處理它。

進去看映像裡到底有什麼，用 --entrypoint 換掉原本的指令，開一個 shell：

docker run --rm -it --entrypoint sh learn-devops/cafe-api:dev
/app $ ls -a              # 有沒有 .env、node_modules 是不是 Linux 版
/app $ id                 # uid=1000(node)

Docker Desktop 另有 docker debug，可以進到沒有 shell 的映像，但它是 Docker Desktop 的功能，能不能用要看帳號方案；第 9 課改用自己的除錯容器，在哪裡都能用。

如果需要在 alpine 映像裡裝系統套件，寫 RUN apk add --no-cache 套件：不加 --no-cache 的話，apk 下載的套件索引會留在那一層，映像平白變大。

練習

三題都在 devops/practice/work/08/app/ 裡做，需要 Docker Desktop 在執行，第一次建置要連網路下載 npm 套件。app/ 是精簡版的 cafe-api：src/server.ts 聽 0.0.0.0:3000（容器裡要聽 0.0.0.0，外面才連得到，第 4 課）、用 pino 印 JSON log、收到 SIGTERM 等 DRAIN_MS 毫秒後關機並印出 shutdown complete；src/routes.ts 有 /health/live、/health/ready、/version、/products。app/Dockerfile 是同事寫的版本，三題都改這個檔案。

測試會把 app/ 複製到暫存資料夾再建置，不會動到你的檔案；映像名稱是 learn-devops/cafe-api:08-*，容器名稱 ld-08-*，port 用 127.0.0.1:18080～18083，測試結束會刪掉容器。自己試的時候：

cd devops/practice/work/08/app
docker build -t learn-devops/cafe-api:dev .
docker run --rm -d --name ld-08-try -p 127.0.0.1:18089:3000 learn-devops/cafe-api:dev
curl http://localhost:18089/version
docker stop ld-08-try

練習 1：把 app/Dockerfile 和 app/.dockerignore 改到能直接上線。測試會先在建置情境裡放三個陷阱：node_modules/SHOULD_NOT_COPY（模擬 Mac 上裝的套件）、含隨機密碼的 .env、.git/，然後建置並以 -e DRAIN_MS=500 --health-interval 2s 啟動。要做到：建置成功；docker build --check 沒有警告；工作目錄是 /app，裡面沒有那三個陷阱；.dockerignore 讓三個陷阱根本不送進建置情境（在 Dockerfile 裡 rm 不算）；有 HEALTHCHECK，30 秒內變成 healthy，而且 app 沒有回應時檢查要失敗；不是用 root 執行；PID 1 是 node；docker stop 在 5 秒內結束、結束碼 0、log 有 shutdown complete。

練習 2：讓快取發揮作用。測試用 --progress=plain 建置三次：第一次照原樣；第二次在 src/routes.ts 加一行註解，這時 RUN npm ci 那一步必須是 CACHED；第三次在 package.json 改 description，這時 npm ci 必須重新執行。後兩次的映像都要能回應 /health/live。安裝依賴要用 npm ci。

練習 3：把版本資訊放進映像。用 ARG 接收 GIT_SHA 和 APP_VERSION（APP_VERSION 預設 dev），讓 /version 回傳這兩個值（app 讀的是同名的環境變數），並加上 label org.opencontainers.image.revision 和 org.opencontainers.image.version。測試會用隨機的 40 位 SHA 和 APP_VERSION=1.4.2 建置，比對 /version 和 label；不給 build-arg 時 version 要是 dev；換一個 SHA 再建置一次，npm ci 仍然要用快取。

練習 4：同事說：「我只改了一行程式碼，為什麼每次建置都要重跑好幾分鐘的 npm ci？Docker 的快取好像很隨機。」他的 Dockerfile 是 COPY . . 接著 RUN npm ci。原因是什麼？

✓ c。快取是確定的：某一步的指令或輸入變了，它和後面每一步都要重跑。原始碼放在 npm ci 前面複製，任何程式改動都讓 npm ci 失效；先只複製 package.json 和 package-lock.json 再 npm ci 就好。a 錯在快取不會隨機失效，只有被清掉（docker builder prune，或磁碟空間不夠時自動回收）才會不見；b 錯在 npm ci 刪除 node_modules 是在執行時，快取命中時根本不會執行；d 錯在 BuildKit 預設就有快取。

練習 5：Dockerfile 把 ENV NODE_ENV=production 寫在 RUN npm ci 前面，RUN npm run build（tsc）會怎樣？

✓ b。ENV 從宣告那一行起對之後的每個 RUN 都有效，npm 看到 NODE_ENV=production 就預設略過 devDependencies，typescript 沒裝，sh: tsc: not found，結束碼 127。a 是最常見的誤解：NODE_ENV 也影響安裝；c 錯在 tsc 不看 NODE_ENV。把 ENV 移到 build 之後即可。

練習 6：用 docker run -d --restart unless-stopped 啟動 cafe-api，事件迴圈卡住，HEALTHCHECK 連續失敗，容器變成 unhealthy。接下來會發生什麼？

✓ a。重啟策略只在程序結束時作用，unhealthy 只是標記；要靠 Swarm、Kubernetes 這類編排器，或自己的監控（第 25 課）去處理。b、c 是常見誤解；d 錯在單純的 Docker 不做負載平衡，-p 發布的 port 照樣把連線送進去。

常見錯誤

  • 沒有 .dockerignore：Mac 的 node_modules、.env、.git 都被 COPY . . 複製進映像。建置情境要排除它們。
  • COPY . . 放在 npm ci 前面：改一行程式就重裝所有套件。先複製 package.json 和 package-lock.json，npm ci 之後再複製其他檔案。
  • shell 形式的 CMD 或 CMD ["npm", "start"]：PID 1 不是 node，訊號可能送不到、多一個程序。寫 CMD ["node", "dist/server.js"]。
  • 沒寫 USER：程式用 root 執行。官方 Node 映像有 node 使用者，CMD 前加 USER node。
  • HEALTHCHECK 呼叫映像裡沒有的 curl：容器永遠 unhealthy。用 node -e 搭配 fetch，並用 docker inspect 看 .State.Health 確認。
  • ENV NODE_ENV=production 放太早：devDependencies 沒裝，tsc 找不到。放在 build 之後。
  • 把建置期的 ARG 當成執行期設定：容器裡讀不到。要留到執行期就轉成 ENV；會因環境而不同的設定則在 docker run -e 時給（第 11 課）。
  • 每次都變的 ARG 放在前面：GIT_SHA 讓後面所有 RUN 快取失效。放在最後。
  • apk add 沒加 --no-cache：套件索引留在映像裡。

小結

  • Dockerfile 是手動部署步驟的檔案版：FROM、WORKDIR、COPY、RUN、ENV、EXPOSE、USER、HEALTHCHECK、CMD。
  • docker build . 的 . 是建置情境，用 .dockerignore 擋掉 node_modules、.env、.git。
  • 層快取從第一個變動的步驟開始失效：少變的放前面，先 package*.json → npm ci，再複製原始碼；用 --progress=plain 看 CACHED。
  • exec 形式的 CMD 讓 node 當 PID 1、直接收到 SIGTERM；USER node 不用 root。
  • HEALTHCHECK 用映像裡一定有的 node 檢查 liveness；unhealthy 不會自動重啟。
  • ARG 只活在建置時，要給程式用就轉成 ENV；版本資訊放最後，避免讓快取失效；docker build --check 和 docker history 幫你檢查結果。
