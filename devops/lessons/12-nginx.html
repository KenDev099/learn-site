階段 3：流量與擴展 · 第 12 課

Nginx 反向代理：流量的入口

咖啡店的 API 已經能用 Compose 跑起來（第 10 課），但它直接把 3000 port 開給外面：Node 自己處理 HTTPS、自己送前端的 Vue 檔案、誰都能一秒打幾百次 /api/products、上傳一個 500MB 的檔案也照收。某天行銷活動帶來一波流量，一個爬蟲同時把 API 打到記憶體用光，所有客人都點不了餐。

這一課在 API 前面放一台 nginx，讓它成為唯一的對外入口。

這課的路線：
  1. 反向代理與設定的結構：nginx 站在 API 前面替它做哪些事，設定檔一層層的區塊怎麼讀。
  2. proxy_pass 與轉送標頭：/api/ 怎麼轉給後端，網址結尾一個斜線為什麼決定路由對不對，後端怎麼知道客人真正的 IP。
  3. 終結 TLS 與保護後端：HTTPS 在入口解開，擋掉 500MB 的上傳和一秒幾百次的爬蟲。
  4. 靜態檔案與快取標頭：Vue 建置出來的檔案怎麼快取，發版後客人才拿得到新版。
  5. 驗證、重新載入與 log：改設定時怎麼不讓入口掛掉，出現 502、504 時去哪裡查。
這課會用到：
  • Node 課第 12 課的 HTTP：請求和回應都帶標頭（例如 Host），回應的狀態碼 4xx 是客戶端的錯、5xx 是伺服器的錯。
  • 第 5 課的 HTTPS：伺服器拿憑證和私鑰做 TLS，80 port 用 301 轉到 HTTPS，HSTS 讓瀏覽器之後只走 HTTPS。
  • 第 10 課的 Compose：同一個專案的容器用服務名稱（例如 api）互連，healthcheck 加 up --wait 等服務準備好。

為什麼要有反向代理

代理（proxy）是替別人轉送請求的程式。依它替誰服務分兩種：

  • 正向代理（forward proxy）：站在用戶端這邊，替用戶端向外連線。公司的上網代理就是：員工的請求都經過它出去，外面的網站只看到代理。
  • 反向代理（reverse proxy）：站在伺服器這邊，替後端接收請求。客人以為自己在跟咖啡店的網站說話，其實是 nginx 收下請求，再轉給後面的 app。

nginx 轉送過去的後端叫 upstream（上游）。這一課的 upstream 是 Compose 網路裡的 api:3000，它不發布 port，外面連不到，只有 nginx 連得到。

為什麼不讓 Node 自己做這些事？

工作交給 nginx 的理由
TLS 終結憑證只放在一個地方，續期後 reload 一台就好；後面有好幾個 app 副本時也不用每個都裝憑證
靜態檔案nginx 用很少的記憶體就能送大量檔案，Node 的事件迴圈留給 API
緩衝客人網路很慢時，nginx 先把整個請求收完、再把回應收下來慢慢送，app 不會被慢連線占住
限制過大的請求、過密的請求在入口就擋掉，不消耗 app 的資源
路由同一個網域底下，/api/ 給 API、其他給前端；之後要拆服務、加副本，只改入口

代價是多了一個要維護、要監控的元件，也多了一個可能出錯的地方：出事時要能分辨是 nginx 擋的，還是後端掛的。雲端上這個角色常由負載平衡器（AWS ALB，第 18 課）擔任，概念完全相同。

nginx 設定的結構

nginx 的設定是一層層的區塊，每一行指令以分號結尾：

http {                         # 所有 HTTP 相關設定（官方映像寫在 /etc/nginx/nginx.conf）
    server {                   # 一個網站：用 listen 的 port 與 server_name 的主機名稱分辨
        listen 80;
        server_name localhost;

        location /api/ {       # 依網址路徑決定怎麼處理
            proxy_pass http://api:3000/;
        }
        location / {
            root /srv/static;  # 回 /srv/static 底下的檔案
        }
    }
}

官方映像的 nginx.conf 在 http 區塊最後寫了 include /etc/nginx/conf.d/*.conf;，所以我們只要把自己的 server 區塊掛成 /etc/nginx/conf.d/default.conf，不用改主設定。外層寫的指令大多會被內層繼承，內層寫了同一個指令就蓋過外層。

location 依路徑選出一個區塊處理請求。一個請求只會進一個 location，選法不是「由上到下第一個符合」，而是有固定的優先順序：

寫法意思優先順序
location = /health精確比對，路徑完全相同才算1：符合就直接用，不再找
location ^~ /static/前綴比對，而且選中後不再檢查正規表示式2：它是最長的前綴時直接用
location ~ \.php$、~*（不分大小寫）正規表示式3：照設定檔裡的順序，第一個符合的勝出
location /api/一般前綴比對4：先記住最長的那個；沒有正規表示式符合時才用它

用 nginx:1.30.6-alpine 實際測過：同時有 location /images/ 和 location ~* \.(png|jpg)$ 時，/images/a.png 進的是正規表示式那個，/images/a.txt 才進 /images/；把前綴改成 ^~ /images/，.png 就不會被正規表示式搶走。location / 會符合所有路徑，所以它是最後的預設。

設定被 include 拆成好幾個檔案之後，很難看出最後到底生效了什麼。nginx -T 先檢查語法，再把所有檔案合併印出來：

docker compose exec nginx nginx -T | less
同一份設定要跑在 staging 和 production、只有網域不同時，官方映像有 templates 功能：把檔案放在 /etc/nginx/templates/default.conf.template，容器啟動時會用 envsubst（把文字裡的 ${VAR} 換成環境變數值的工具）產生 /etc/nginx/conf.d/default.conf。它只替換容器裡有定義的環境變數，所以 $host 這類 nginx 自己的變數不會被清空。這就是第 11 課「同一個映像，部署時才給設定」在 nginx 上的做法。

proxy_pass 與轉送標頭

proxy_pass 把請求轉給 upstream。最常出錯的是網址結尾那個斜線：

設定客人請求 /api/products，後端收到
location /api/ { proxy_pass http://api:3000; }/api/products：沒有 URI，原樣轉送
location /api/ { proxy_pass http://api:3000/; }/products：有 URI（就是那個 /），比對到的 /api/ 被換成 /
location /api/ { proxy_pass http://api:3000/v2/; }/v2/products

規則只有一條：proxy_pass 的位址後面有沒有路徑。有，就把 location 比對到的部分換成那個路徑；沒有，就原封不動。所以要先決定後端的路由長什麼樣子：cafe-api 的路由是 /products，就要寫有斜線的版本。

經過代理之後，後端看到的連線是 nginx 發出來的，原本的資訊都不見了。要用 proxy_set_header 補回去：

location /api/ {
    proxy_pass http://api:3000/;
    proxy_set_header Host $host;                                   # 客人連的主機名稱
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # 客人的 IP
    proxy_set_header X-Forwarded-Proto $scheme;                    # http 還是 https
    proxy_set_header X-Request-ID $request_id;                     # 這個請求的 ID
}
  • Host：nginx 預設送的是 $proxy_host，也就是 api:3000。後端要產生絕對網址（重設密碼信裡的連結、Location 轉址）時會拿到錯的主機名稱。$host 是客人請求裡的主機名稱。
  • X-Forwarded-For：轉送鏈上每一站附加的用戶端 IP 清單，用逗號分隔。$proxy_add_x_forwarded_for 是「客人送來的 X-Forwarded-For，再加上 nginx 看到的連線位址 $remote_addr」。
  • X-Forwarded-Proto：原始請求是 http 還是 https。TLS 在 nginx 就解開了，後端收到的永遠是 HTTP；沒有這個標頭，Express 這類框架會以為請求不安全，不肯送出 Secure cookie（Auth 課第 4 課），或把使用者轉到 http 的網址。
  • X-Request-ID：$request_id 是 nginx 為每個請求產生的 32 個十六進位字元。nginx 的 access log 和 app 的 log 都記下它，出事時就能把同一個請求在兩邊的紀錄對起來（第 21 課）。
X-Forwarded-For 不能全信。它只是一個標頭，客人可以自己帶 X-Forwarded-For: 1.2.3.4，nginx 會把真的位址接在後面，後端收到 1.2.3.4, 172.18.0.1。拿第一個當使用者 IP 去限流、記稽核紀錄，攻擊者想當誰就當誰。正確做法叫 trust proxy：後端只相信「來自自己的代理」加上的那一段，也就是從右邊數過來、自己代理的那幾站。Express 的 app.set('trust proxy', 1) 就是「只信任前面一層代理」。而且後端只該接受來自代理的連線，這一課的 api 不發布 port 就是為了這點。

連線重用（upstream keepalive）：nginx 把和後端的 TCP 連線留著給下一個請求用，省下每次重新連線的時間。nginx 1.29.7 起，轉送預設用 HTTP/1.1、不再送 Connection: close，而且 upstream 區塊預設就開著連線重用。upstream 區塊是替一組後端取名字的寫法，第 13 課放好幾個副本時會用到：

upstream cafe_api {
    server api:3000;           # 1.29.7 起預設等於多寫了 keepalive 32 local;
}
server {
    location /api/ { proxy_pass http://cafe_api/; }
}

像這一課直接寫 proxy_pass http://api:3000/;（沒有 upstream 區塊）時，在 1.30.6 實際觀察，每個請求仍然開一條新連線、用完就關。所以舊教學裡的 proxy_http_version 1.1; 與 proxy_set_header Connection ""; 在 1.29.7 以後是多餘的，但無害。

連線重用帶來一個不好查的問題：兩端都會關掉閒置太久的連線，nginx 的 upstream keepalive_timeout 預設 60 秒，Node 的 server.keepAliveTimeout 實際預設只有 5 秒（Node 課第 13 課量過）。第 5 秒 Node 正要關掉某條閒置連線，nginx 剛好把新請求寫進去，結果就是一個 502，error log 寫 upstream prematurely closed connection。流量越小越容易遇到，因為閒置連線越多。修法是讓後面的閒置逾時比前面長：app 的 keepAliveTimeout 設得比 nginx（或 ALB）的長，例如 65 秒；或把 nginx 的調到比 app 短。這一課練習裡的後端 api/server.mjs 就設了 keepAliveTimeout = 65_000，下一課換成 upstream 區塊時就不會踩到。

WebSocket 是另一個例外：它要靠 Upgrade 機制把 HTTP 連線換成雙向通道，nginx 不會自動轉送這兩個標頭，要自己寫 proxy_set_header Upgrade $http_upgrade; 和 proxy_set_header Connection "upgrade";。

在 nginx 終結 TLS

TLS 終結（TLS termination）是在入口把 HTTPS 解開，後面走內部網路的 HTTP。第 5 課讓 Node 自己做 HTTPS、HTTP 轉址與 HSTS，這裡把同樣的三件事搬到 nginx：

server {
    listen 80;
    server_name cafe.example.tw;
    return 301 https://$host$request_uri;      # 保留路徑與查詢字串；這裡不送 HSTS
}

server {
    listen 443 ssl;
    server_name cafe.example.tw;

    ssl_certificate     /etc/nginx/certs/fullchain.pem;   # 含中繼憑證的完整鏈（第 5 課）
    ssl_certificate_key /etc/nginx/certs/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;                  # TLS 1.0、1.1 已經不安全

    add_header Strict-Transport-Security "max-age=31536000" always;

    location /api/ { … 跟上一節一樣，X-Forwarded-Proto 會是 https … }
}
  • $request_uri 是客人請求的原始路徑加查詢字串。只寫 return 301 https://$host;，客人點 http://…/orders?id=7 會被丟回首頁。
  • add_header 預設只加在 200、201、204、206、301、302、303、304、307、308 這些回應上。404、500、502 就沒有 HSTS。加 always 才是每個回應都有。
  • HSTS 只寫在 443 的 server：瀏覽器會忽略 HTTP 回應裡的 HSTS，規格也要求不要送（第 5 課）。max-age 一樣先短再長。
  • 私鑰用唯讀方式掛進容器（./certs:/etc/nginx/certs:ro），不要 COPY 進映像；續期後 reload nginx 才會讀到新憑證。
💡 實務上：憑證過期是最常見的「全站掛掉」
憑證會自動續期，但 nginx 要 reload 才會用新的；續期腳本成功、nginx 沒 reload，到期那天所有客人都看到憑證錯誤。資深工程師會把「續期後 reload」寫進同一個自動化流程，再另外監控對外憑證的到期日（第 25 課的告警），不只相信續期有跑。

保護後端

入口的另一個工作是把明顯不該進來的請求擋在外面。

請求大小：client_max_body_size 預設 1m，超過就回 413 Payload Too Large（請求內容超過上限）。上傳頭像需要 2MB 時，只在那個 location 調大，其他路徑維持 1MB：

location = /api/uploads {
    client_max_body_size 2m;
    proxy_pass http://api:3000/uploads;
}

在 http 或 server 層一次調大，等於所有 API 都收 2MB 的 JSON，解析它們的是 Node 的單一執行緒。

逾時：proxy_connect_timeout（連上後端）與 proxy_read_timeout（兩次從後端讀到資料之間）預設都是 60 秒。一般 API 夠用；但 SSE（Server-Sent Events）、WebSocket 這種長連線會在 60 秒沒有資料時被 nginx 切斷，要在那個 location 調高 proxy_read_timeout，或讓後端定期送心跳。

限流（rate limiting）：限制每個用戶端的請求速率。nginx 的 limit_req 用 leaky bucket（漏桶）演算法：每個用戶端有一個桶子，請求倒進去，桶底以固定速率漏出（處理）；桶子滿了，新的請求就被拒絕。

# 寫在 http 層（conf.d/*.conf 本來就在 http 裡）：定義一個叫 api 的區域
limit_req_zone $binary_remote_addr zone=api:10m rate=5r/s;

server {
    limit_req_status 429;                     # 預設是 503
    location /api/ {
        limit_req zone=api burst=10 nodelay;
        proxy_pass http://api:3000/;
    }
}
  • key 決定「誰」是同一個用戶端。$binary_remote_addr 是 nginx 自己看到的連線位址（二進位格式，IPv4 只占 4 bytes）。用 $http_x_forwarded_for 的話，攻擊者每個請求換一個值就繞過了。
  • 10m 是共享記憶體的大小。官方文件說 1MB 大約存 16,000 個狀態，10m 大約 16 萬個 IP。
  • rate=5r/s 是每 200 毫秒漏出一個。burst=10 是桶子的容量，允許短時間多來 10 個。
  • nodelay：沒有它，burst 裡的請求會排隊、照 200 毫秒一個慢慢放行，前端會覺得很卡；有它就立刻處理，只是桶子的位置要照速率慢慢空出來。同時打 30 個請求，大約 11 個（1＋burst 10）馬上通過，其餘被拒。
  • limit_req_status 429：被拒絕的請求預設回 503 Service Unavailable，監控會以為服務掛了，客戶端也不知道該等一下再試。429 Too Many Requests（被限流）才說對了原因。

一個請求只會進一個 location，所以上一段的 location = /api/uploads 拿不到寫在 location /api/ 裡的 limit_req：上傳這條最吃資源的路徑反而沒有限流。要嘛在那個 location 裡再寫一次，要嘛把 limit_req 寫在 server 層，讓沒有自己寫 limit_req 的 location 都繼承它。

另一個工具 limit_conn 限制的是「同時開著的連線數」，適合擋一個 IP 開幾百條下載連線；寫法類似，limit_conn_zone $binary_remote_addr zone=addr:10m; 加 limit_conn addr 10;，被拒絕的預設狀態碼也是 503，用 limit_conn_status 改。

💡 實務上：限流的數字要從實際流量來
先數一數咖啡店首頁載入時同時打幾支 API；辦公室或學校的客人可能共用同一個對外 IP，一間公司一起訂下午茶就會撞到上限。先用寬鬆的值上線、看 log 裡的 429 次數再收緊，前端也要處理 429（稍後重試、提示客人），這要先跟前端和 PM 講好。只靠 IP 的限流擋不住分散在大量 IP 的攻擊，那要靠 CDN 或雲端的 WAF；登入這類路徑還要在 app 裡依帳號限制（Auth 課第 16 課）。nginx 限流計數存在單一台 nginx 的記憶體裡，入口有好幾台時每台各算各的。

靜態檔案與快取標頭

Vite 建置出來的前端分兩種檔案，要用不同的快取策略（Node 課第 15 課）：

檔案特性Cache-Control
index.html檔名固定，每次發版內容都變no-cache：可以存，但每次用之前都要回伺服器確認（ETag 沒變就回 304，很便宜）
/assets/app.3f9a1c.js檔名含內容的雜湊，內容一改檔名就變public, max-age=31536000, immutable：快取一年，連重新整理都不用確認
root /srv/static;

location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location / {
    add_header Cache-Control "no-cache";
}

如果 index.html 也快取一年，發版之後客人的瀏覽器一年內都不會來拿新的 index.html，也就永遠不知道有新的 app.xxxx.js。前面再加一層 CDN（內容傳遞網路，把靜態檔快取在離使用者近的伺服器，第 18 課的 CloudFront）時，CDN 通常也照這個 Cache-Control 決定要存多久，所以這兩行同時管瀏覽器和 CDN。

壓縮：官方映像的 nginx.conf 裡 gzip on; 是被註解掉的。打開時記得 gzip_types 預設只有 text/html，JSON、CSS、JS 要自己加：gzip_types application/json text/css application/javascript;。

add_header 的繼承規則：只有在目前這一層完全沒有 add_header 時，才會繼承上一層的。在 server 層加了 HSTS、X-Frame-Options，又在 location /assets/ 加一行 Cache-Control，/assets/ 的回應就只剩 Cache-Control，安全標頭全部不見，而且不會有任何錯誤訊息。傳統解法是在每個有 add_header 的 location 裡重寫一次（常用 include 共用片段）；nginx 1.29.3 起可以在 location 裡寫 add_header_inherit merge;，把上層的標頭一起帶上。用 1.30.6 測過，兩種行為都和上面描述的一樣。

驗證、重新載入與 log

改設定最怕的是打錯一個分號，整個入口起不來，所有客人都連不上。正確順序是先檢查，再重新載入（reload）：

docker compose exec nginx nginx -t           # 只檢查語法與檔案，不影響正在跑的 nginx
docker compose exec nginx nginx -s reload    # 套用新設定

reload 時，nginx 的主程序讀新設定；成功的話開新的 worker 程序接新請求，舊 worker 把手上的請求處理完才結束，現有連線不中斷。新設定有錯時主程序會繼續用舊設定。restart（docker compose restart nginx、systemctl restart nginx）則是整個停掉再啟動：連線全部斷開，設定有錯的話就起不來，入口直接掛掉。所以 nginx -t 一定先跑，部署流程也應該在 nginx -t 失敗時停下來。

log：官方映像把 access log 和 error log 導到容器的 stdout、stderr，用 docker compose logs nginx 看。預設格式沒有 request ID 與後端花的時間，正式環境建議自己定義：

log_format main_ext '$remote_addr "$request" $status $body_bytes_sent '
                    'rid=$request_id rt=$request_time urt=$upstream_response_time';
access_log /var/log/nginx/access.log main_ext;

$request_time 是 nginx 處理整個請求的時間，$upstream_response_time 是等後端的時間。兩個差很多，代表時間花在客人的慢網路或 nginx 自己；兩個都大，就是後端慢。

入口出錯時，狀態碼本身就告訴你方向：

狀態碼意思error log 常見的訊息先查什麼
502 Bad Gateway連不上後端，或拿到無效的回應connect() failed (111: Connection refused)、upstream prematurely closed connection後端有沒有在跑、port 對不對、是不是剛重啟；偶發的話看 keepAliveTimeout

💡 實務上：客服說「點餐一直轉圈然後錯誤」時
先問狀態碼，再分頭查：502 看 api 容器是不是剛重啟或一直重啟（docker compose ps），504 看資料庫的慢查詢，429 看是不是同一個 IP 打太多。拿 log 裡的 rid= 去 app 的 log 搜同一個 request ID，就能知道那個請求在後端做了什麼。回報時寫清楚「幾點到幾點、哪個路徑、什麼狀態碼、多少比例」，比「網站壞了」有用得多。

還有一個 Docker 才有的 502：nginx 在啟動時把 api 解析成 IP 後就一直用它。api 容器重建後拿到新 IP，nginx 還在連舊的。暫時的解法是 reload nginx；第 13 課用 upstream 的 resolve 參數讓 nginx 自己跟上。

練習

練習在 devops/practice 做，需要 Docker 在跑。compose.yaml 已經寫好：api 是一個只回答測試需要的路徑的小型 Node 伺服器（api/server.mjs，不發布 port，GET /api/debug/headers 會把它收到的標頭原樣回傳），nginx 用 nginx:1.30.6-alpine，發布在 127.0.0.1:18120（HTTP）與 127.0.0.1:18121（HTTPS）。三題各改一個設定檔，用 CONF 選要掛哪一個：CONF=ex2.conf docker compose up -d --wait。測試每次都會先收掉 ld-12 再重新啟動，跑完也會收掉。

練習 1：完成 nginx/ex1.conf：/api/ 開頭的請求轉給 api:3000 並去掉 /api 前綴（/api/products → /products），轉送 Host、X-Forwarded-For、X-Forwarded-Proto、X-Request-ID；/ 提供 /srv/static/index.html，Cache-Control: no-cache；/assets/ 提供雜湊檔名的檔案，快取一年而且 immutable。測試會先跑 nginx -t，再檢查 /api/products、後端看到的標頭（也會自己帶一個假的 X-Forwarded-For，確認最後一段仍是 nginx 看到的位址）、兩種靜態檔的 Cache-Control。自己試：docker compose up -d --wait，curl -s http://localhost:18120/api/debug/headers、curl -I http://localhost:18120/。

練習 2：完成 nginx/ex2.conf，在 nginx 終結 TLS。443：只允許 TLS 1.2 與 1.3，/api/ 跟練習 1 一樣轉給 api，後端要看到 X-Forwarded-Proto: https，所有 HTTPS 回應（包含 404）都帶 Strict-Transport-Security: max-age=31536000。80：任何路徑都 301 到 https://localhost:18121，保留路徑與查詢字串，不帶 HSTS。容器裡是 80／443、主機上是 18120／18121，所以轉址網址要寫主機上的 port。憑證由 make-certs.sh 用第 5 課的私有 CA 做法產生在 certs/，測試每次會先執行它，再用 ca.crt 驗證連線（不關掉驗證），並用 TLS 1.1、1.0 試連。自己試：sh make-certs.sh，CONF=ex2.conf docker compose up -d --wait，curl --cacert certs/ca.crt -i https://localhost:18121/api/products、curl -i 'http://localhost:18120/orders?id=7'。

練習 3：完成 nginx/ex3.conf，保護後端。只有 /api/uploads（後端路徑 /uploads）接受最大 2MB 的請求內容，其他路徑維持預設的 1MB；/api/ 底下（包含 /api/uploads）以用戶端 IP 限流：每秒 5 個、burst 10、nodelay，被拒絕時回 429。測試會 POST 1.5MB 與 3MB 到 /api/uploads、1.5MB 到 /api/orders；同時送 30 個 GET /api/products（大約 11 個馬上通過、其餘 429、不能有 503，而且沒有請求被排隊延後），並用 nginx -T 確認速率；等 3 秒確認恢復；再送 30 個每個都帶不同 X-Forwarded-For 的請求，以及 30 個小的 POST /api/uploads，都要被限流。

練習 4：location /api/ { proxy_pass http://api:3000; } 和 location /api/ { proxy_pass http://api:3000/; }，客人請求 /api/products 時有什麼不同？

✓ c。proxy_pass 的位址後面有路徑（哪怕只是一個 /）時，location 比對到的部分會被換成那個路徑；沒有路徑就原封不動轉送。a 不對，nginx 不會猜你的意思，這正是後端回 404 的常見原因；b 剛好說反；d 兩種都是合法設定。

練習 5：流量不大的時段偶爾出現 502，大部分請求都正常。nginx 的 error log 寫 upstream prematurely closed connection，cafe-api 沒有設定 keepAliveTimeout（Node 預設 5 秒），nginx 是 1.30.6，用 upstream cafe_api { server api:3000; } 轉送。最可能的原因與修法？

✓ b。nginx 1.29.7 起 upstream 區塊預設重用連線、閒置 60 秒才關，Node 5 秒就關，兩者交界時請求會寫進正在關閉的連線。流量越小、閒置連線越多，越容易遇到。a 逾時會是 504 和 upstream timed out；c 撐不住通常是逾時或連線被拒，而且不會只在流量小時發生；d 限流是 429（或預設的 503），不是 502。

練習 6：同事說：「nginx 回 502 和 504 都代表後端當機了，重啟 api 就好。」哪一個說法最正確？

✓ d。兩個狀態碼都是 nginx 產生的，描述的是「nginx 和後端之間」出了什麼事。502 先查後端有沒有在跑、port 與 keepalive；504 先查後端為什麼慢。a 忽略了慢和死的差別；b nginx 自己當機的話客人連 502 都收不到；c 剛好說反。

練習 7：cafe-api 在 nginx 後面，想記錄每個請求的使用者 IP 給風控用。後端直接取 X-Forwarded-For 的第一個 IP，安全嗎？

✓ a。$proxy_add_x_forwarded_for 是「客人送來的值，再加上 $remote_addr」，第一個 IP 完全由客人決定。b 忽略了客人送來的部分會被保留；c HTTPS 防的是中間人，防不了客人自己寫標頭；d 在代理後面，remoteAddress 永遠是 nginx 的位址，所有人都會變成同一個 IP。

常見錯誤

  • proxy_pass 的結尾斜線用錯：後端收到 /api/products 而回 404，或多一層、少一層路徑。先決定後端路由，再照「有路徑就替換」的規則寫，用 /api/debug/headers 這類回傳路徑的端點確認。
  • 把 X-Forwarded-For 當成可信：第一個 IP 是客人自己寫的。後端只信自己代理加的那一段；限流的 key 用 $binary_remote_addr。
  • 忘了轉送 Host 與 X-Forwarded-Proto：後端產生的網址變成 http://api:3000/…，Secure cookie 送不出去。
  • 改完設定直接 restart：設定有錯時入口就起不來。先 nginx -t，再 nginx -s reload。
  • limit_req 沒改狀態碼：預設 503 會被監控當成服務故障，客戶端也不知道要稍後重試。加 limit_req_status 429;。
  • 在 http 層把 client_max_body_size 全部調大：只在需要的 location 放寬。
  • SSE、WebSocket 每 60 秒斷一次：proxy_read_timeout 預設 60 秒。在那個 location 調高，或讓後端送心跳；WebSocket 還要轉送 Upgrade、Connection。
  • 在 location 裡加一個 add_header，上層的安全標頭全不見：每一層都要寫齊，或用 1.29.3 起的 add_header_inherit merge;。HSTS 記得 always。
  • index.html 也設長快取：發版後客人拿不到新版前端。只有檔名含雜湊的檔案能快取一年。
  • app 的 keepAliveTimeout 比前面代理的短：偶發 502。後面要比前面長。
  • api 容器重建後一直 502：nginx 還連著舊 IP。reload nginx，或用第 13 課的 resolve。

小結

  • 反向代理站在伺服器這邊替後端接請求，讓整套服務只有一個對外入口，負責 TLS 終結、路由、靜態檔、壓縮、緩衝、逾時與限制；後端不發布 port。
  • 設定是 http → server → location；location 的優先順序是 =、^~、正規表示式（依順序）、最長前綴；nginx -T 看合併後的完整設定。
  • proxy_pass 後面有路徑就替換比對到的部分，沒有就原樣轉送；轉送 Host、X-Forwarded-For、X-Forwarded-Proto、X-Request-ID，後端只信自己代理加上的轉送標頭。
  • 1.29.7 起 upstream 區塊預設重用連線；閒置逾時要前短後長，app 的 keepAliveTimeout 大於 nginx 或 ALB 的。
  • TLS 在 443 終結，只開 TLS 1.2／1.3；80 用 $request_uri 301 到 HTTPS；HSTS 只在 HTTPS 並加 always。
  • client_max_body_size 只在需要的地方放寬；limit_req 以 $binary_remote_addr 為 key、回 429；長連線要調高 proxy_read_timeout。
  • index.html 用 no-cache，雜湊檔名用一年加 immutable；子層有 add_header 就不繼承上層。
  • 先 nginx -t 再 reload；log 加上 $request_id 和 $upstream_response_time；502 是連不上或回應無效，504 是後端太慢。
