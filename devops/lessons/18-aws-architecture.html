階段 5：雲端與基礎設施即程式碼 · 第 18 課

雲端與 AWS 核心服務：VPC、EC2、RDS、S3

咖啡店的 cafe-api 目前跑在一台租來的主機上：Compose 起 api、PostgreSQL、nginx，備份靠每晚的 cron。這台主機所在的機房停電兩小時，那兩小時沒有人點得到餐；更糟的是資料庫的磁碟跟著壞了，最近一次能用的備份是三天前。老闆問：「搬到 AWS 是不是就不會這樣？」答案是：不會自動變好。放在同一個機房裡的東西照樣一起掛，資料庫開在公開網路上照樣被掃，而且月底多了一張看不懂的帳單。

這一課把雲端的基本元件講清楚，並學會看懂帳單。練習全部在瀏覽器裡做，不需要 AWS 帳號，也不會產生費用。

這課的路線：
  1. 雲端是什麼、要選哪一種：租機器、租容器平台還是租整個執行環境，各自要自己管多少。
  2. region 與可用區：服務和資料要怎麼擺，才撐得過一個機房停電（開場問題的最小答案）。
  3. 網路：VPC、子網路與安全群組：怎麼讓資料庫只有 app 連得到，不暴露在公開網路上。
  4. 運算與資料：EC2、ECS Fargate、RDS、S3 各管什麼，cafe-api 搬上 AWS 長什麼樣子，修補又是誰的責任。
  5. 成本：把帳單拆開看錢花在哪、設好預算警示，上線前估價和月底對帳都用得到。
這課會用到：
  • 第 4 課的網路基礎：CIDR 用 10.0.0.0/16 這種寫法表示一段 IP；私有網路的位址外面連不進來，要出去上網得經過 NAT。
  • 第 12 課的反向代理與 TLS 終結：入口接下所有請求、在這裡解開 HTTPS，再轉給後面的 app。
  • 第 13 課的無狀態與多副本：app 不在自己身上存狀態，才能開好幾份，前面靠健康檢查決定把請求送給誰。

雲端是什麼、要選哪一種

雲端（cloud）是按用量租用運算、儲存、網路資源：要一台機器，幾分鐘就開好，不用了就關掉，按小時或按請求計費。差別在於你租到哪一層，越往上租，自己要管的越少，能控制的也越少：

模型你租到的你還要管AWS 的例子
IaaS（Infrastructure as a Service）虛擬機、磁碟、網路作業系統、更新、執行環境、程式、擴展EC2、EBS、VPC
容器平台能跑容器的地方映像、設定、擴展規則ECS on Fargate、EKS
PaaS（Platform as a Service）執行環境：丟程式碼或映像上去就跑程式與設定App Runner、Elastic Beanstalk
serverless函式：有請求才執行，依請求與執行時間計費函式本身；冷啟動、執行時間上限都要遷就平台Lambda
SaaS（Software as a Service）整套軟體帳號與資料Gmail、Slack 這類

另一個常見的詞是託管服務（managed service）：由雲端供應商幫你維運的服務。RDS 是託管的 PostgreSQL，你不用自己裝、自己修補、自己排備份。代價是能調的東西變少（例如不能裝任意的 extension），也比自己在 EC2 上跑貴。

咖啡店 API 有幾條路可以走：

做法適合代價
一台 EC2 跑 Compose（就是前面幾課做的事）一兩個人、流量小、想先上線單點故障；作業系統更新、磁碟、備份全是自己的事
ECS Fargate 跑容器＋RDS小團隊、要多副本與零停機部署，但不想管機器要懂 task definition、IAM、VPC；單位運算比 EC2 貴
EKS（託管 Kubernetes，第 13 課最後一節）服務和團隊很多，已經有人懂 Kubernetes學習與維運成本最高，控制平面本身也收費
PaaS只想交出映像，網路與擴展都交給平台網路、規模、價格的彈性最少；換平台時要改的東西多
Lambda流量很不規則、大部分時間閒置冷啟動、執行時間上限；資料庫連線要另外處理（每次執行都可能開新連線）

判斷的順序：團隊有幾個人、誰半夜起來處理；流量是穩定還是暴衝；預算多少；能不能接受被某家雲端綁定（lock-in，換供應商時要重寫的東西）。這一課以「ECS Fargate＋RDS＋S3」為主線，因為它把前面學過的東西（映像、多副本、健康檢查、反向代理）一一對應到 AWS 的服務，同時也會講 EC2，因為它是其他服務的底層。

Region 與可用區

region（區域）是一個地理位置上的一群資料中心，例如東京 ap-northeast-1、台北 ap-east-2。台北 region 在 2025-06-05 開放，有 3 個可用區，屬於需要手動啟用（opt-in）的 region：帳號預設看不到，要先在帳號設定裡啟用。選 region 看三件事：離使用者近（延遲低）、法規要求資料放在哪裡、需要的服務在那個 region 有沒有提供。

一個 region 裡有好幾個可用區（Availability Zone，AZ）：彼此獨立供電、獨立網路的資料中心，相距夠遠，不會因為同一場停電一起掛，又夠近，彼此之間的延遲很低。AZ 是你設計高可用時的故障單位：一個 AZ 停擺時，所有只放在那個 AZ 的東西都會停。

「上雲」不會自動帶來高可用。一台 EC2 只存在於一個 AZ，那個 AZ 出事它就停。要撐過 AZ 故障，每一層都要跨 AZ：負載平衡器本身跨 AZ、app 副本分散在至少兩個 AZ（第 13 課的無狀態讓這件事成立）、資料庫有另一個 AZ 的備援。整個 region 掛掉的機率小得多，要防就得做跨 region 的備份或複寫，成本也高很多，第 24 課再談。

網路：VPC、子網路與安全群組

VPC（Virtual Private Cloud）是你在 AWS 裡的私有網路，建立時指定一段私有 CIDR，例如 10.20.0.0/16（第 4 課教過 CIDR 的寫法）。VPC 再切成子網路（subnet）：每個子網路是 VPC 裡的一小段 CIDR，而且只屬於一個 AZ。AWS 每個子網路保留 5 個位址（網段開頭、VPC 路由器、DNS、保留給未來、廣播位址），子網路大小只能在 /16 到 /28 之間，所以一個 /24 實際能用 251 個。

子網路分成兩種，差別只在路由表：

  • 公有子網路：路由表有一條 0.0.0.0/0 → internet gateway。internet gateway（IGW）讓 VPC 和網際網路直接互通，裡面有公開 IP 的機器可以被外面連到。只放 ALB 和 NAT gateway。
  • 私有子網路：沒有通往 IGW 的路由，外面連不進來。app 和資料庫放這裡。app 要呼叫外部 API、下載套件時，路由指向 NAT gateway：它在公有子網路裡，替私有子網路的機器主動連外，回應可以回來，但外面不能主動連進來（就是第 4 課家用路由器的 NAT）。NAT gateway 按小時、也按處理的 GB 收費，等一下算帳單會看到它的份量。
💡 實務上：VPC 的 CIDR 開了就改不了大小，先問「以後要跟誰連」
已經建立的 CIDR 不能放大或縮小，只能另外加一段次要 CIDR；兩個 VPC 的 CIDR 只要重疊，就不能用 VPC peering 互連。最常見的狀況是開發、測試、正式環境都用預設的 10.0.0.0/16，一年後要把它們接起來、或接公司的 VPN，才發現全部撞在一起，只能重建網路。資深工程師開 VPC 前會先問網路或維運的同事：公司辦公室、VPN、其他 VPC 用了哪些網段，再替每個環境挑一段不重疊的 /16，記在團隊的文件裡；子網路也留空位（例如 app 用 10.20.10.x、10.20.11.x，中間的號碼留給以後的第三個 AZ）。

路由決定「有沒有路」，安全群組（security group，SG）決定「門開不開」。安全群組是掛在網卡上的防火牆規則，只寫允許、不寫拒絕，沒寫到的就不通。它是有狀態的：允許了進來的連線，回應自動放行，不用另外寫一條。規則的來源可以是 CIDR，也可以是另一個安全群組，意思是「掛著那個安全群組的機器都可以」。後者是關鍵：Fargate task 換了 IP、多開了副本，規則都不用改。

安全群組允許進來的為什麼
alb-sg443，來源 0.0.0.0/0顧客從任何地方連進來
app-sg3000，來源 alb-sg只有 ALB 能把請求送給 app
db-sg5432，來源 app-sg只有 app 能連資料庫；同一個 VPC 裡的其他機器也不行

還有一層 network ACL：掛在子網路上、無狀態的規則（回應的流量也要另外允許，通常是 1024–65535 的臨時 port），可以寫拒絕。大部分團隊保留預設的「全部允許」，只用安全群組；要封鎖某段 IP 時才動它。

那要怎麼登入私有子網路裡的機器？第 6 課的做法是跳板機（bastion）：放在公有子網路、開 22 給辦公室的 IP，再從它 SSH 進去。AWS 上更好的做法是 SSM Session Manager：機器上的 agent 主動往外連 AWS，你透過 AWS 的權限開 shell，完全不必開 22 port，每次連線還會留下紀錄（權限怎麼給在第 19 課）。Fargate 的容器則用 ECS Exec，背後是同一套機制。

對外的入口還有三個服務：Route 53 是 AWS 的 DNS，把 api.brew.example.tw 指到 ALB；ACM（AWS Certificate Manager）免費申請並自動續期憑證，掛在 ALB 上做 TLS 終結（第 5 課、第 12 課）；CloudFront 是 AWS 的 CDN，把菜單圖片這類靜態檔快取在離使用者近的地方。

運算：EC2 與 ECS Fargate

EC2 是 AWS 的虛擬機。開一台要選幾樣東西：

  • AMI（Amazon Machine Image）：開機映像，決定作業系統，例如 Ubuntu 24.04 或 Amazon Linux。
  • instance type（機型）：CPU、記憶體的組合，例如 t4g.small（t 系列、第 4 代、g 代表 Graviton 的 ARM 處理器、small 是大小）。ARM 的機型要配 ARM 的映像（第 9 課的多平台建置）。
  • EBS（Elastic Block Store）：掛在機器上的網路磁碟，機器關掉資料還在，可以做快照。
  • user data：第一次開機時執行的腳本，用來安裝 Docker、拉映像、啟動服務。

t 系列是可爆發（burstable）機型：平常只保證一部分 CPU（基準線），用不到的部分累積成 CPU credit，忙的時候拿來衝高。T3、T4g 預設是 unlimited 模式：credit 用完還能繼續衝，但 24 小時平均超過基準線的部分另外收費。改成 standard 模式就不會多收錢，代價是 credit 用完後 CPU 被壓回基準線，API 忽然變慢卻查不到原因。CPU 長期很忙的服務，改用 m 系列這種固定效能的機型比較划算。

容器版的對應關係，和前面學過的東西一一對上：

前面學過的AWS 上的對應
映像倉庫（第 16 課的 registry）ECR（Elastic Container Registry）
compose 裡的一個 service 定義：映像、環境變數、port、資源限制ECS task definition
docker compose up --scale api=3ECS service：維持 N 個 task，掛掉的自動補上
自己的主機Fargate：不用管機器，按 task 的 vCPU 與記憶體計費
nginx 反向代理與 upstream（第 12 課、第 13 課）ALB（Application Load Balancer）與目標群組（target group）
log 與指標CloudWatch（Logs、Metrics、Alarms）

ALB 的設定和第 12 課、第 13 課的 nginx 是同一套概念，名字和預設值不同：

  • 目標群組的健康檢查打 /health/ready：沒過的 task 不會收到流量。
  • deregistration delay：把目標移出目標群組時，先等進行中的請求做完，預設 300 秒，就是第 13 課的排空。這段時間要配合 task 的停止期限（收到 SIGTERM 到被強制停止的時間），兩邊對不上就會掉請求或拖慢部署。
  • ALB 的閒置逾時預設 60 秒。第 12 課說過「後面的閒置逾時要比前面長」，所以 app 的 keepAliveTimeout 要大於 60 秒，例如 65 秒，否則會出現偶發的 502。

資料：RDS 與 S3

RDS 是託管的資料庫，咖啡店用 RDS for PostgreSQL。它幫你做的事：

  • 自動備份：每天的快照加上交易紀錄，可以還原到保留期間內的任何一秒（point-in-time recovery，PITR，概念在 PostgreSQL 課第 37 課）。還原出來的是一個新的資料庫，不是覆蓋原本那個。
  • Multi-AZ：在另一個 AZ 維持一個同步複寫的備援。主資料庫出事時自動切換，AWS 文件寫的切換時間通常是 60–120 秒。備援平常不能讀，它是為了可用性，不是為了分擔讀取（要分擔讀取用 read replica）。費用大約是兩份。
  • 參數群組（parameter group）：postgresql.conf 的設定都改在這裡，例如 log_min_duration_statement。

切換時 AWS 把資料庫的 DNS 名稱改指向備援，既有的連線全部斷掉。app 要能自己重連：連線池遇到斷線要丟掉壞的連線、重新解析 DNS，正在進行的交易要在 app 層重試（只重試冪等的操作，也就是重做一次結果不變的操作）。另外兩件事：資料庫放私有 DB 子網路、不要開「公開存取」；副本數 × 連線池大小不能超過資料庫的 max_connections（第 13 課算過），RDS 的預設值跟機型的記憶體有關，小機型很快就到頂。

💡 實務上：Multi-AZ 要在上線前演練一次切換
付了兩份錢買 Multi-AZ，但 app 的重連沒寫好，真的切換時照樣停擺。RDS 可以手動觸發切換：在測試環境執行 aws rds reboot-db-instance --db-instance-identifier cafe-db-staging --force-failover（只對 Multi-AZ 的執行個體有效），同時對 API 持續送請求，記下錯誤持續多久、連線池有沒有自己恢復、有沒有訂單寫到一半。這個演練通常排在上線前的檢查清單裡，也是向 PM 說明「維護時段會中斷多久」的依據。

S3（Simple Storage Service）是物件儲存：bucket 是一個容器，裡面每個物件用 key（像 menu/latte.jpg 這樣的名稱）存取，容量不用預先規劃。第 13 課說上傳的檔案不能存在副本的磁碟上，就是要放這裡。

  • 預設封鎖公開存取：新的 bucket 和物件預設不允許公開存取，Block Public Access 有四個開關。不要為了方便全部關掉；要公開的靜態檔用 CloudFront 提供。
  • presigned URL：有時效的簽名網址。cafe-api 用自己的權限簽一個「這個 key、PUT、10 分鐘內有效」的網址交給前端，前端直接把檔案傳到 S3，大檔案不經過 API（NestJS 課第 22 課）。網址的權限等於簽它的人的權限，拿到的人都能用，所以時效要短；用 CLI 或 SDK 簽最長 7 天，用角色的臨時憑證簽的網址會在憑證過期時一起失效。
  • 版本控制（versioning）：覆蓋或刪除時保留舊版本，誤刪可以救回來。
  • 生命週期規則（lifecycle）：多久之後轉到更便宜的儲存類別、多久之後刪除，例如舊的 log 匯出檔。

責任共擔：誰負責修補

AWS 的責任共擔模型（shared responsibility model）：AWS 負責「雲端本身」的安全（機房、硬體、虛擬化層、託管服務的底層），你負責「放進雲端的東西」。託管程度越高，你的責任越少，但永遠不會是零：

工作EC2FargateRDS
作業系統的安全更新你AWSAWS（在你設定的維護時段）
資料庫引擎的小版本修補你（如果自己裝）—AWS 套用；要不要自動升級由你設定
映像裡的套件漏洞你你（第 9 課的掃描）—
安全群組、公開存取、加密設定你你你
IAM 權限、金鑰保管（第 19 課）你你你
資料本身、備份有沒有還原過（第 24 課）你你你

有帳號的話，可以用 AWS CLI（這台 Mac 裝的是 aws-cli 2.36.37）唯讀地看看現況。下面的指令都只讀不寫；--profile 選用哪組設定、--region 選 region。不要把 access key 寫進程式或 repo，用角色與臨時憑證的做法在第 19 課。

成本：看不見的帳單

AWS 的帳單是一行一行的用量乘以單價。小流量服務最容易被低估的，是按小時計費、不管有沒有流量都在跑的固定費用：

  • RDS：Multi-AZ 是兩份執行個體與兩份儲存，常常是整張帳單最大的一項。
  • NAT gateway：每個每小時收費，每個 AZ 一個就是兩倍；另外每處理 1 GB 再收一次。私有子網路經過 NAT 存取同一個 region 的 S3 也照收。改用 S3 的 gateway endpoint（加一條路由，讓私有子網路直接到 S3）不收小時費也不收處理費。
  • ALB：每小時收費，再加上依流量計算的單位費。
  • 公開 IPv4 位址：從 2024-02-01 起，每個公開 IPv4（不論使用中或閒置）每小時 0.005 美元。ALB 每個 AZ 一個、NAT gateway 每個一個，都算。
  • 資料傳輸費（data transfer）：流量離開 AWS 到網際網路時按 GB 計費，進入 AWS 通常不收。流量大了才會成為主角。
  • CloudWatch Logs：寫入按 GB 收，保存也按 GB 收。log group 預設永久保存（Never Expire），每個月的 log 都疊上去，保存費每月成長。建立 log group 時就設保存天數。
  • 閒置資源：測試完沒刪的機器、沒掛載的 EBS、舊快照。

💡 實務上：資源一建立就打 tag，帳單才分得出是誰花的
帳單只會告訴你「RDS 花了 300 美元」，分不出是正式環境、測試環境，還是某個同事開來試的。團隊通常規定每個資源都要有 Project、Environment 這類 tag，再到 Billing 主控台把它們啟用成成本分配標籤（cost allocation tag）；啟用前產生的費用不會補上 tag，所以要一開始就做。之後每個月用 Cost Explorer 依 tag 和服務分組看一次，先找出閒置資源和沒人認領的機器。老闆或財務問「雲端費用為什麼漲了」時，這張分組表就是答案。

開帳號後的第一件事是設 AWS Budgets：設一個每月的成本預算，加上警示。幾件要知道的事：

  • 警示分兩種：實際（actual）是已經花到門檻才通知；預測（forecasted）是預估月底會超過就先通知。只設「實際 100%」，收到通知時錢已經花掉了。常見組合是實際 80%、實際 100%、預測 100%。
  • 每個警示最多通知 10 個 email 加一個 SNS topic（SNS 再轉到 Slack 或值班系統）。
  • 帳單資料每天至少更新一次，警示會延遲；實際警示每個預算週期只在第一次達到門檻時送一次；預測需要大約 5 週的使用紀錄才會觸發。
  • 預算只通知，不會停掉任何資源。要自動動作得另外設定 budget action。沒有 action 的預算免費。
  • 2025-07-15 之後建立的帳號，註冊時拿到 100 美元 credit，完成指定任務最多再拿 100 美元，可以選 Free plan 或 Paid plan。credit 會用完，Budgets 一樣要設。

用 CLI 建預算時，aws budgets create-budget 要三個參數：帳號 ID、--budget、--notifications-with-subscribers，後兩個是 JSON。練習 4 要你寫產生這兩段 JSON 的函式（只產生，不執行）：

aws budgets create-budget --account-id 123456789012 \
  --budget file://budget.json \
  --notifications-with-subscribers file://notifications.json

練習

練習 3、4 的價格都是範例參數，由測試傳入，不是 AWS 的實際報價。

練習 1：CIDR 計算與子網路規劃。實作 ipToInt（IPv4 轉成 0 到 2³² − 1 的無號整數）、inCidr(ip, cidr)、cidrSize(cidr)（位址總數）、usableInAws(cidr)（扣掉 AWS 保留的 5 個；不是 /16 到 /28 時丟錯）、overlaps(a, b)（兩段 CIDR 有沒有重疊）。再把 plan 填完：VPC 10.20.0.0/16 裡，兩個 AZ（a、b）各一個 public、app、db 子網路，全部是 /24、不重疊。測試會用 /0、/32、255.255.255.255 這些邊界。

練習 2：安全群組檢查器。實作 canReach(arch, from, to, port)：目的地掛的任何一個安全群組裡，有一條規則的 port 符合（單一 port 或含兩端的範圍），而且來源符合（CIDR 包含來源的 IP，或來源掛著 sg: 指定的安全群組），就回傳 true。然後修好 arch 的規則：現在資料庫的 5432、app 的 3000 和 SSH 都對全世界開放。修好後網際網路只能連 ALB 的 443，ALB 能連 app 的 3000，只有 app 能連資料庫，同一個 VPC 裡的 bastion 也不能直接連 app 或資料庫，任何機器的 22 都不對網際網路開放。只改 arch.sgs，不要改 nodes。

練習 3：每月成本估算。完成 lineItems(deploy, prices)，依序回傳 compute、alb、rds、storage、nat、publicIpv4、dataTransfer、logs 八項的每月金額（算法見上面的帳單表；Multi-AZ 的執行個體與儲存都算兩份；logs 是「寫入 GB × 寫入單價」加上「保存中的 GB × 保存單價」，永久保存時保存中的是 monthsRunning 個月的寫入量，有保存天數時最多是 retentionDays ÷ 30 個月）。再寫 topCostDrivers(items, n) 依金額由大到小取前 n 項（同額保持原順序、不能改動傳入的陣列），以及 cheaperS3Path(s3Gb, prices)：每月 s3Gb 的 S3 流量改走 gateway endpoint 能省多少。價格一律從 prices 讀，測試會換一組價目表。

練習 4：預算警示。改寫 budgetFor({ monthlyEstimate, emails, snsTopicArn })，回傳 aws budgets create-budget 要的 Budget 與 NotificationsWithSubscribers：每月的 COST 預算，金額是估算值無條件進位到整數美元（API 要的是字串）；三個通知：實際 80%、實際 100%、預測 100%，都是 GREATER_THAN、PERCENTAGE；每個通知都帶全部 email 訂閱者，snsTopicArn 不是 null 時再加一個 SNS 訂閱者。email 超過 10 個，或 email 和 SNS 都沒有時，要丟錯。

練習 5：同事想用自己電腦上的 GUI 工具直接查正式資料庫，提議：「把 RDS 開公開存取、安全群組開 5432 給 0.0.0.0/0，反正密碼有 32 個字元。」你怎麼回？

✓ c。資料庫對網際網路開放，攻擊面不只密碼：PostgreSQL 本身的漏洞、設定錯誤的角色、外洩的密碼，任何一個出問題就直接暴露（a 錯）。b 縮小了來源，但資料庫仍有公開 IP、仍在公有子網路：辦公室的 IP 會變，規則也容易被下一個人為了方便放寬，安全只剩安全群組這一層。d 換 port 擋不住掃描器，掃描器會掃所有 port。正確的做法是資料庫沒有任何對外的路，需要人工查詢時走 SSM 或 SSH 通道（第 6 課），而且最好連唯讀的角色。

練習 6：cafe-api 跑在 ap-northeast-1a 的一台 EC2 上（Compose 跑 api 和 PostgreSQL，EBS 每天快照）。這個 AZ 發生電力故障，會怎樣？

✓ b。一台 EC2 只存在於一個 AZ，AWS 不會替你把它搬走（a、c 錯）。api 和資料庫在同一台機器上，一起停（d 錯）。快照能讓你在別的 AZ 重建，但那是手動復原，而且會丟掉最後一次快照之後的資料。高可用要自己設計：每一層都跨 AZ。

練習 7：咖啡店 API 每天只有幾千個請求，第一個月的 AWS 帳單卻比預期高很多。最該先查哪幾項？

✓ d。流量小時，對外流量和 S3 儲存都只有幾塊錢（a、b 錯）。Fargate 可能可以調小，但通常不是最大項（c）。真正的大頭是 24 小時都在計費的資源：Multi-AZ 的 RDS 是兩份、NAT gateway 有小時費加處理費、ALB 與每個公開 IPv4 都按小時收費；log 永久保存則讓保存費每月往上疊。打開 Cost Explorer 依服務分組看，就能確認是哪幾項。

練習 8：cafe-api 有兩種部署方式：EC2 上跑 Compose，或 ECS Fargate。OpenSSL 公布了一個漏洞，哪些修補是你的責任？

✓ a。責任共擔模型裡，EC2 的作業系統（guest OS）更新是你的事；Fargate 把主機交給 AWS，但映像是你建的，裡面的套件漏洞只有你能修（第 9 課的掃描與重建）。b、c 把責任方向弄反了。d 錯在容器帶著自己的使用者空間函式庫，修主機的 OpenSSL 不會改到映像裡的那一份。

常見錯誤

  • 資料庫放公有子網路、安全群組開 0.0.0.0/0：資料庫直接暴露在網際網路上。放私有 DB 子網路，來源只寫 app 的安全群組。
  • 安全群組的來源寫整個 VPC 的 CIDR：VPC 裡任何一台被入侵的機器都能連資料庫。來源寫安全群組，只放行真的需要的那一層。
  • SSH 對全世界開放：每天被掃描、被暴力破解。用 SSM Session Manager，不開 22。
  • 所有資源都放在同一個 AZ：一個機房出事就全停。副本跨 AZ、資料庫 Multi-AZ。
  • 以為上雲就自動高可用、自動修補：EC2 的作業系統、映像裡的套件、安全群組、備份還原都是你的責任。
  • 忘了 NAT gateway 與流量費：NAT 有小時費加每 GB 處理費，連同區的 S3 也算。S3 走 gateway endpoint。
  • 每台機器一個公開 IP：每個公開 IPv4 每小時收費，而且多了被直接連線的入口。機器放私有子網路，對外只留 ALB。
  • 為了方便關掉 S3 的 Block Public Access：一個設定錯誤就讓整個 bucket 公開。要公開的檔案用 CloudFront，上傳用 presigned URL。
  • 沒設 Budgets，或只設實際花費 100%：超支後才知道。實際 80%、實際 100%、預測 100% 一起設。
  • 以為 Budgets 會即時通知、會自動停掉資源：帳單資料每天約更新一次，預算只通知；要自動動作得另外設 budget action。
  • CloudWatch Logs 保持預設的永久保存：保存費每個月往上疊。每個 log group 都設保存天數。
  • RDS 切換後 app 一直連不上：連線池拿著斷掉的連線、DNS 被快取。斷線要丟掉連線、重新解析、重試冪等的操作。
  • 用 root 帳號做日常操作：root 什麼都能做、不能被權限限制。第 19 課會把它鎖起來。

小結

  • IaaS、容器平台、PaaS、serverless 是同一條線上的不同位置：越往上管得越少、控制也越少。依團隊人數、流量型態、維運能力、預算與綁定的程度來選；咖啡店的主線是 ECS Fargate＋RDS＋S3。
  • region 是地理位置，AZ 是獨立供電與網路的資料中心，也是設計高可用時的故障單位。每一層都要跨至少兩個 AZ。
  • VPC 切成公有與私有子網路，差別只在路由表有沒有 IGW。ALB、NAT 在公有子網路；app、資料庫在私有子網路。安全群組有狀態、只寫允許，來源寫另一個安全群組；SSH 改用 SSM Session Manager。
  • EC2 是虛擬機（AMI、instance type、EBS、user data），t 系列有 CPU credit；容器版是 ECR → task definition → ECS service on Fargate，前面是 ALB 與目標群組（健康檢查、deregistration delay 300 秒、閒置逾時 60 秒）。
  • RDS：自動備份與 PITR、Multi-AZ 切換約 60–120 秒且連線會斷、不開公開存取。S3：預設封鎖公開、presigned URL 讓前端直接上傳、版本控制、生命週期。
  • 責任共擔：AWS 負責雲端本身，你負責放進去的東西；EC2 的作業系統更新、映像裡的套件都是你的事。
  • 帳單拆成明細看：小流量時最貴的是按小時計費的固定費用（RDS Multi-AZ、NAT、ALB、公開 IPv4），log 要設保存天數。開帳號第一件事設 Budgets：實際 80%、實際 100%、預測 100%。
