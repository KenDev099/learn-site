階段 1：伺服器基本功 · 第 5 課

HTTPS 與 TLS：憑證是怎麼被信任的

星期一早上，客服說好幾位客人打不開咖啡店的點餐網站，瀏覽器顯示「你的連線不是私人連線」。API 沒有改版、伺服器也活著，原因是憑證三天前過期了，沒有人收到通知。另一天，新同事為了讓測試通過，在呼叫金流的程式裡加了 rejectUnauthorized: false，從此任何人都能冒充金流商。

這一課把 HTTPS 拆開來看，你會自己當一次憑證機構、用 Node 跑 HTTPS 伺服器，最後寫一支監控程式，在憑證快過期前提醒你。

這課的路線：
  1. 沒有 TLS 會怎樣：在公共 Wi-Fi 送出的登入請求誰看得到、改得了，TLS 保證了哪三件事。
  2. 憑證、CA 與憑證鏈：瀏覽器憑什麼相信這把公鑰真的屬於 cafe.example.com。
  3. TLS 1.3 握手：連線時交換了什麼，憑證驗證失敗最常見的三個原因。
  4. 自己當 CA：本機跑 HTTPS 時，怎麼讓客戶端信任你的憑證，而不是用 rejectUnauthorized: false 把驗證關掉。
  5. Let's Encrypt、HTTP→HTTPS 與 HSTS：正式環境的憑證怎麼自動續期、怎麼監控才不會過期沒人知道，使用者只打網域時怎麼安全地轉到 HTTPS。
這課會用到：
  • Auth 課第 8 課的簽章：私鑰簽名、公鑰驗證，拿得到公鑰的人都能驗，只有持有私鑰的人簽得出來。
  • Node 課第 13 課的 node:http 伺服器：createServer 收請求、listen 聽 port。
  • 第 4 課的連線過程：先用 DNS 查 IP、再建立 TCP 連線，curl -v 依序印出每一段。

沒有 TLS 會怎樣

你在咖啡店連公共 Wi-Fi 送出 POST /login，封包會經過基地台、店家的路由器、網路業者的設備才到伺服器。用 HTTP 傳的話，路上每一台設備都看得到內容，也改得了內容。坐在隔壁、開了同名 Wi-Fi 的人，可以把自己放在你和伺服器中間，這叫中間人攻擊（man-in-the-middle）：你以為在跟伺服器說話，其實每個封包都先經過他。

TLS（Transport Layer Security）是加在 TCP 之上的一層協定，HTTPS 就是「HTTP 跑在 TLS 裡」，預設 port 443。TLS 給你三件事：

保證意思沒有它會怎樣
加密（confidentiality）路上的人看不懂內容密碼、session cookie 被偷看
完整性（integrity）內容被改過會被發現回應裡被插入廣告或惡意程式
驗證伺服器身分（authentication）你連到的真的是 cafe.example.com加密了，但對面是攻擊者

第三件最容易被忽略，也最常被關掉。只有加密、沒有驗證身分，等於跟一個陌生人講悄悄話。這一課大部分的內容，都在講第三件事怎麼做到。

TLS 只保護「傳輸過程」。網址列有鎖頭，不代表網站本身可信：釣魚網站一樣能申請到憑證，伺服器上的 SQL injection、資料外洩也跟 TLS 無關。

憑證裡有什麼

驗證身分靠的是公鑰／私鑰（public/private key）：私鑰只有伺服器自己有，用它簽名；公鑰公開，任何人都能用它驗證簽名，跟 Auth 課第 8 課 JWT 的 RS256 簽章是同一件事。問題是：你怎麼知道手上這把公鑰真的屬於 cafe.example.com？

答案是憑證（certificate，格式叫 X.509）：一份寫著「這把公鑰屬於這些網域」的文件，由憑證機構（CA，Certificate Authority）用 CA 自己的私鑰簽名。主要欄位：

欄位內容用途
SubjectCN=cafe.example.com憑證發給誰。CN（Common Name）是舊式放網域的地方，瀏覽器已經不看
Subject Alternative Name（SAN）DNS:cafe.example.com, DNS:www.cafe.example.com憑證適用的網域與 IP 清單，現代瀏覽器只比對這裡
IssuerCN=YR1, O=Let's Encrypt誰簽發的
ValidityNot Before／Not After有效期，超過就不能用
Public KeyRSA 2048 或 EC P-256伺服器的公鑰
Basic ConstraintsCA:FALSE這張能不能再去簽別的憑證。只有 CA 憑證是 CA:TRUE

拿一張真的憑證來看。先確認你用的是哪一套 openssl：macOS 內建的 /usr/bin/openssl 是 LibreSSL，用 Homebrew 裝的是 OpenSSL 3。建立憑證的指令兩套都能跑；只有 x509 -ext（只印某個擴充欄位）是 OpenSSL 3 才有，LibreSSL 要改用 -text 再找 X509v3 Subject Alternative Name 那一段。

openssl version          # OpenSSL 3.5.2 …（Homebrew）或 LibreSSL 3.3.6（macOS 內建）

# 連上網站、取得它送來的憑證，再解讀成文字（-servername 是告訴伺服器要哪個網域，叫 SNI，握手那一節會講）
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

x509 -text -noout 會印出全部欄位，用 -subject、-dates、-ext 只挑需要的（s_client 是 openssl 內建的 TLS 客戶端，只負責連線和印出伺服器送來的東西）。</dev/null 讓 s_client 拿到憑證就結束，不會停在那邊等你輸入。

誰來保證：CA 與憑證鏈

CA 用私鑰幫伺服器憑證簽名，但你又憑什麼相信 CA？因為作業系統和瀏覽器出廠時就內建了一份根 CA（root CA）的清單，叫信任庫（trust store）。macOS 的在「鑰匙圈存取」，Debian 的在 /etc/ssl/certs，Node 自己也帶一份。

根 CA 的私鑰非常珍貴，平常鎖在離線的設備裡，不直接簽網站憑證，而是先簽一張中繼 CA（intermediate CA）憑證，由中繼 CA 去簽網站。驗證時一路往上，這條路叫憑證鏈（certificate chain）：

重點是：伺服器必須送出中繼憑證。設定 nginx 時要用「完整鏈」檔案（Let's Encrypt 的 fullchain.pem），不是只有自己那張的 cert.pem。

只裝了自己那張的時候，會出現很難查的現象：Chrome 打得開，curl 和 Node 卻說 unable to get local issuer certificate。原因是瀏覽器會用憑證裡的網址自己去下載缺的中繼憑證，或者之前逛別的網站時已經快取過；curl、Node、手機 App 不會幫你補。看到這個錯誤，先用 openssl s_client -showcerts 數一數伺服器送了幾張。

💡 實務上：替每張憑證建一份清單
憑證事故很少是密碼學出錯，多半是「沒人知道這張憑證在哪」：同一張憑證放在 CDN、負載平衡器和 nginx 三個地方，只更新了其中一個；續期通知寄到離職同事的信箱；網域登記在另一個部門的帳號下。資深工程師會維護一份清單：網域、放在哪裡、怎麼續期、誰負責、到期監控在哪。新增子網域或換一家 CDN 時，順手更新它。

TLS 1.3 握手

TCP 連上之後（第 4 課的三向交握），雙方先做 TLS 握手（handshake），談好加密方式、交換金鑰、驗證身分，才開始傳 HTTP。TLS 1.3 只要一個來回：

  • ClientHello：客戶端列出支援的加密演算法，附上自己那一半的金鑰交換資料（key share）。裡面還有 SNI（Server Name Indication）：「我要連 cafe.example.com」。一台伺服器（一個 IP）常常同時服務好幾個網域，SNI 讓它在還沒加密前就知道該送哪一張憑證。
  • ServerHello：伺服器選好演算法、送回自己那一半的金鑰交換資料。到這裡雙方各自算出同一把對稱金鑰（加密和解密用同一把，比公鑰運算快很多），後面的訊息全部用它加密。這把金鑰本身從來沒有在網路上傳過。
  • Certificate／CertificateVerify：伺服器送出憑證鏈，再用私鑰對到目前為止的握手內容簽名，證明「私鑰在我手上」，不是只抄了一份公開的憑證。
  • Finished：雙方確認握手內容沒被竄改，接著就是 HTTP。

客戶端驗證憑證時，失敗的原因幾乎都是這三個：

原因curl／Node 的錯誤常見情境
名稱不符no alternative certificate subject name matches／ERR_TLS_CERT_ALTNAME_INVALID憑證沒有這個網域的 SAN、只有 CN、用 IP 連但 SAN 沒有 IP
過期certificate has expired／CERT_HAS_EXPIRED續期沒跑、續期了但伺服器沒 reload
不信任的簽發者unable to get local issuer certificate、self-signed certificate缺中繼憑證、自簽憑證、公司內部 CA 沒裝進信任庫

curl -v https://… 會把握手的每一步印出來（第 4 課看過），curl -w '%{time_appconnect}' 是從請求開始到 TLS 握手完成的秒數（含 DNS 和 TCP），減掉 time_connect 就是 TLS 握手本身。

SNI 是明文的。TLS 1.3 把憑證也加密了，但 ClientHello 裡的網域名稱路上的人還是看得到。把它也加密的擴充叫 ECH（Encrypted Client Hello），還沒有普及。

自己當 CA：本機的 HTTPS

開發和測試時沒辦法跟公開 CA 申請 localhost 的憑證（公開 CA 只發給你能證明擁有的網域）。做法是自己當一個私有 CA，簽發憑證，再讓客戶端信任這個 CA。這也是公司內部服務常見的做法。

步驟一：做 CA。req -x509 產生一張自簽憑證，加上 CA:TRUE：

openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -days 365 \
  -subj "/CN=Cafe Dev CA" \
  -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign"

-newkey rsa:2048 同時產生新的私鑰，-nodes 是私鑰不加密碼（腳本裡沒人能輸入；OpenSSL 3 也接受新名字 -noenc，LibreSSL 不認得）。

步驟二：伺服器的私鑰和憑證簽署請求（CSR，Certificate Signing Request）。CSR 是「請幫我這把公鑰簽一張憑證」的申請書，裡面有公鑰，沒有私鑰：私鑰從頭到尾不離開伺服器。

openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj "/CN=localhost"

步驟三：CA 簽發，並加上 SAN。擴充欄位寫在一個檔案裡，簽發時用 -extfile 帶進去：

printf '%s\n' 'basicConstraints = CA:FALSE' \
  'subjectAltName = DNS:localhost, IP:127.0.0.1' 'extendedKeyUsage = serverAuth' > server.ext
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -days 90 -extfile server.ext -out server.crt
openssl x509 -in server.crt -noout -ext subjectAltName   # 確認 SAN 真的在（LibreSSL：-text 再找 Subject Alternative Name）

用瀏覽器打 https://localhost 比對的是 DNS:localhost，打 https://127.0.0.1 比對的是 IP:127.0.0.1，兩個要分開寫。只寫 CN=localhost 的憑證，Chrome 從 58 版（2017 年）起就不接受。要注意的是 Node 的 X509Certificate.checkHost() 預設 subject: 'default'，沒有 DNS SAN 時還會看 CN；要模擬瀏覽器的規則得傳 { subject: 'never' }（Node 24 文件）。

步驟四：用 Node 提供 HTTPS。node:https 的 createServer 跟 node:http 幾乎一樣，多一個放金鑰和憑證的參數：

import https from 'node:https'
import { readFileSync } from 'node:fs'

https.createServer(
  { key: readFileSync('server.key'), cert: readFileSync('server.crt') },
  (req, res) => res.end('ok'),
).listen(18050, '127.0.0.1')

Node 24 的 tls.DEFAULT_MIN_VERSION 是 TLSv1.2：TLS 1.0、1.1 有已知弱點，預設就會被拒絕。不要為了遷就舊客戶端把 minVersion 調低。

步驟五：讓客戶端信任你的 CA，而不是關掉驗證：

curl --cacert ca.crt https://localhost:18050/health/live            # 只信任這個 CA
NODE_EXTRA_CA_CERTS=ca.crt node client.ts                          # Node：在內建清單之外多信任這個 CA
https.get({ host: 'localhost', port: 18050, ca: readFileSync('ca.crt') }, …)   # 只對這個請求

NODE_EXTRA_CA_CERTS 只在 Node 啟動時讀一次，要在指令前面設；在程式裡改 process.env 沒有用。給了 ca 選項時，內建清單和這個環境變數都不會用（Node 24 文件）。

curl -k、rejectUnauthorized: false、NODE_TLS_REJECT_UNAUTHORIZED=0 都是「不驗證身分」：還是有加密，但對面是誰都接受，中間人攻擊直接成功。開發時信任你自己的 CA；正式環境出現驗證錯誤，就去修憑證。這種程式碼最常見的下場是從測試一路被複製到正式環境。

產生的 ca.key、server.key 是私鑰，不能進 git，也不能 COPY 進映像（第 9 課、第 11 課）。ca.key 尤其要小心：拿到它的人可以替任何網域簽出你的電腦會信任的憑證。

正式環境：Let's Encrypt 與自動續期

公開網站用公開 CA 的憑證。Let's Encrypt 是免費的公開 CA，透過 ACME 協定讓程式自動申請、續期。CA 要先確認你真的控制這個網域，常用兩種驗證：

驗證方式怎麼證明適合
HTTP-01CA 去抓 http://網域/.well-known/acme-challenge/…，內容要對一般網站；80 port 要能從網際網路連到
DNS-01在 DNS 加一筆 _acme-challenge 的 TXT 紀錄萬用字元憑證（*.cafe.example.com）、伺服器不對外開放；需要 DNS 服務商的 API 權限

實際上很少自己寫 ACME：certbot 申請並排程續期，再 reload nginx；Caddy 這類伺服器內建 ACME，設好網域就自動處理；雲端的負載平衡器（例如 AWS 的 ALB 搭配憑證服務 ACM，第 18 課）由雲端代管。不論哪一種，續期後伺服器要重新載入憑證才會生效。

憑證的有效期正在變短。CA/Browser Forum（CA 和瀏覽器廠商一起訂規則的組織）2025 年通過的 SC-081v3：

從哪天起簽發的公開憑證最長有效期
2026-03-15200 天
2027-03-15100 天
2029-03-1547 天

Let's Encrypt 原本就是 90 天，預設的 classic 設定檔會在 2027-02-10 改成 64 天、2028-02-16 改成 45 天；選用的 tlsserver 設定檔從 2026-05-13 起就是 45 天。為什麼要越來越短？私鑰外洩或 CA 誤發時，壞憑證能被濫用的時間變短；撤銷（revocation，CA 宣告某張憑證提前作廢）在實務上不可靠：很多客戶端不檢查或查不到就放行，讓它自然過期比較確實。另一個目的是逼大家全面自動化：45 天的憑證，沒人能靠手動續期活下去。

這對你的意思是：

  • 續期時間不要寫死。「每 60 天續一次」在 45 天的憑證上會直接過期。用 ACME 客戶端的預設行為，或支援 ARI（ACME Renewal Information）的客戶端：由 CA 告訴你什麼時候該續，CA 需要大量撤銷時也能叫你提早續。Let's Encrypt 建議用 ARI。
  • 到期監控要自己做。Let's Encrypt 從 2025-06-04 起不再寄到期通知信。監控要連到線上的伺服器讀它實際送出的憑證：磁碟上的檔案續期了，不代表伺服器 reload 過。剩餘天數低於門檻就告警（第 25 課），練習 3 就是寫這支檢查程式。
# 線上伺服器實際送出的憑證什麼時候到期
openssl s_client -connect cafe.example.com:443 -servername cafe.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -enddate

HTTP→HTTPS 與 HSTS

使用者在網址列只打 cafe.example.com，瀏覽器第一次會用 HTTP 連 80 port。伺服器在 80 port 只做一件事：301 永久轉址到 HTTPS，而且保留原本的路徑和查詢字串，不然從舊連結點進來的人都會被丟到首頁：

http://cafe.example.com/orders?id=7   →   301   Location: https://cafe.example.com/orders?id=7

轉址的網址要用你設定好的網域組出來，不要直接拿請求的 Host 標頭：那是客戶端填的，可以是任何值，也可能帶著錯的 port。

轉址還留一個洞：第一個 HTTP 請求本身沒有加密，中間人可以攔下它，不讓你被轉到 HTTPS。HSTS（HTTP Strict Transport Security）補這個洞：HTTPS 回應帶上

Strict-Transport-Security: max-age=31536000

瀏覽器記住「接下來 max-age 秒內，這個網域只用 HTTPS」，之後使用者打 http:// 也會在瀏覽器裡直接改成 HTTPS，不送出明文請求。規則（RFC 6797）：

  • 只在 HTTPS 回應裡有效。從 HTTP 收到的 HSTS，瀏覽器必須忽略，因為攻擊者可以偽造 HTTP 回應；規格也要求伺服器不要在 HTTP 回應裡送。
  • max-age 先短再長。HSTS 一送出去就收不回來：在 max-age 到期前，瀏覽器不會再用 HTTP 連。先設 300 秒，確認所有頁面、API、圖片都走得了 HTTPS，再逐步拉到一年。
  • includeSubDomains 和 preload 有風險。includeSubDomains 讓所有子網域也只能用 HTTPS，還沒有憑證的 intranet.cafe.example.com 會立刻打不開。preload 是申請把網域寫進瀏覽器內建的清單，第一次連線就強制 HTTPS，要求 max-age 至少一年並加上 includeSubDomains，移除要等瀏覽器改版，以月計。

HSTS 和 Auth 課第 4 課的 Cookie Secure 屬性是一組的：Secure 讓 session cookie 只在 HTTPS 上送出，HSTS 讓瀏覽器根本不走 HTTP。

正式環境通常不讓 Node 自己處理 TLS，而是由前面的 nginx 或負載平衡器解密，後面走內部網路，這叫 TLS 終結（TLS termination），在第 12 課做。有些服務之間還會要求雙方都出示憑證，伺服器也驗證客戶端，這叫 mTLS（雙向 TLS），常見於內部服務和金流 API。這一課讓 Node 自己跑 HTTPS，是為了把每一步看清楚。
💡 實務上：「只有在公司連不上」可能是對方的網路在攔截
有些公司網路會解開員工的 HTTPS 流量做檢查，做法是在員工電腦裝一張公司自己的根憑證，再用它替每個網站臨時簽一張憑證。瀏覽器信任那張根憑證所以沒事，但 Node 預設用自己內建的信任清單，就會出現憑證錯誤。遇到這種回報，請對方提供看到的憑證簽發者；Node 程式真的需要信任公司的 CA 時，用環境變數 NODE_EXTRA_CA_CERTS 指向那張憑證，不要關掉驗證。

練習

三題都在 devops/practice/work/05/ 裡做，不需要 Docker，但需要 openssl（macOS 內建的 LibreSSL 或 Homebrew 的 OpenSSL 3 都可以）。練習 2 會用到練習 1 產生的憑證。

練習 1：完成 make-certs.sh：在它所在的資料夾產生 ca.key、ca.crt（CA 憑證，CA:TRUE）、server.key、server.crt。server.crt 要由 ca.crt 簽發、不是 CA、SAN 包含 DNS:localhost 和 IP:127.0.0.1、有效期不超過 200 天。測試會先刪掉舊的 ca.crt、server.crt、server.key，執行 sh make-certs.sh，再用 Node 的 X509Certificate 檢查：簽發者與簽章、SAN（用瀏覽器的規則，不看 CN）、有效期、私鑰和憑證是不是一對。

練習 2：把 https-server.ts 的 HTTP 伺服器改成 HTTPS：用 server.key、server.crt 在 127.0.0.1:18050 提供 GET /health/live（回 200），每個 HTTPS 回應都帶 Strict-Transport-Security: max-age=300。再開一台 HTTP 伺服器在 127.0.0.1:18051，任何路徑都 301 轉到 https://localhost:18050，保留路徑和查詢字串，不帶 HSTS。測試會先執行你的 make-certs.sh，再啟動 node https-server.ts，用 ca.crt 驗證連線（不關掉驗證），對 HTTP 發幾個不同路徑的請求（包括 /health/live），還會用 TLS 1.1 連線確認被拒絕。自己試：curl --cacert ca.crt -i https://localhost:18050/health/live、curl -i 'http://localhost:18051/orders?id=7'。

練習 3：完成 cert-days-left.ts <host> <port>：用 tls.connect 連上線上的伺服器，讀它實際送出的憑證（getPeerX509Certificate()），只印出一個整數：剩餘天數，無條件捨去。剩不到 14 天以 1 結束；連不上或 TLS 握手失敗（包括憑證不被信任）以 2 結束；其他以 0 結束。用網域名稱連線時要送 SNI（tls.connect 預設不送；IP 不能當 SNI）。不要關掉驗證，信任測試用的 CA 交給 NODE_EXTRA_CA_CERTS。測試會當場產生 5 天、15 天、60 天到期和自簽的憑證，各開一台 TLS 伺服器，其中一台只在收到 SNI 時才送正確的憑證；還會連一個沒人聽的 port。自己試：先執行練習 2 的伺服器，再 NODE_EXTRA_CA_CERTS=ca.crt node cert-days-left.ts localhost 18050。

練習 4：api.cafe.test 的憑證 Subject 是 CN=api.cafe.test，但沒有 SAN。用 Chrome 打開 https://api.cafe.test 會怎樣？

✓ c。Chrome 從 58 版起只比對 SAN，不看 CN，沒有 SAN 就等於沒有任何名稱，會顯示 NET::ERR_CERT_COMMON_NAME_INVALID。a 是十年前的規則；不會「打開但警告」；名稱比對跟誰簽發的無關，公開 CA 現在也一定會放 SAN。

練習 5：新上線的 https://cafe.example.com 用 Chrome 打開正常，但 curl 和 Node 都回 unable to get local issuer certificate。最可能的原因是？

✓ b。瀏覽器會自己下載或從快取補上缺的中繼憑證，curl 和 Node 不會，所以只有它們失敗。修法是設定完整鏈（例如 fullchain.pem）。a 的 -k 是關掉驗證，等於放棄身分驗證；過期和名稱不符在 Chrome 上也會失敗，而且錯誤訊息不同。

練習 6：同事建議「HSTS 越早送越好，連 80 port 的 HTTP 轉址回應也加上 Strict-Transport-Security」。這樣有用嗎？

✓ a。HTTP 回應可以被中間人偽造或刪掉，如果瀏覽器採信它，攻擊者就能送 max-age=0 關掉保護，所以 RFC 6797 規定只認 HTTPS 回應裡的 HSTS。要讓第一次連線就強制 HTTPS，靠的是 preload 清單，不是在 HTTP 上送標頭。

練習 7：公開憑證的最長有效期從 398 天一路縮到 2029 年的 47 天，主要原因是？

✓ d。撤銷在實務上不可靠，讓憑證早點自然失效最確實；短到人工續期做不到，自動化就成了唯一選項。a 不成立：Let's Encrypt 免費，而且推動縮短的是瀏覽器廠商；加密強度由演算法和金鑰長度決定，跟有效期無關；效能也無關。

常見錯誤

  • 用 curl -k 或 rejectUnauthorized: false 讓錯誤消失：驗證被關掉，誰都能冒充伺服器。開發時用 --cacert、ca 或 NODE_EXTRA_CA_CERTS 信任自己的 CA；正式環境修憑證。
  • 只裝了伺服器憑證，沒有中繼憑證：瀏覽器正常、API 客戶端失敗。設定完整鏈，用 openssl s_client -showcerts 確認送了幾張。
  • 只寫 CN、沒有 SAN：現代瀏覽器直接拒絕。用 IP 連線的話，SAN 還要有 IP: 這一筆。
  • 私鑰進了 git 或映像：要當成已外洩，撤銷並重新簽發。私鑰在部署時才掛進去（第 9、11 課）。
  • 續期排程寫死 60 或 90 天：有效期縮短後就會過期。用 ACME 客戶端的預設行為或 ARI，續期後記得 reload。
  • 只檢查磁碟上的憑證檔：檔案續期了，伺服器可能還在用舊的。監控要連線讀線上的憑證。
  • 一開始就把 HSTS 設成一年又加 includeSubDomains：還沒有 HTTPS 的子網域會打不開，而且收不回來。先用 300 秒。
  • 轉址用 Host 標頭組網址或丟掉查詢字串：被帶到錯的地方，或舊連結失效。用固定的網域加 req.url。
  • 以為有鎖頭就代表網站安全：TLS 只保護傳輸過程，不保證對面是好人，也不保證伺服器沒有漏洞。

小結

  • TLS 提供加密、完整性和伺服器身分驗證；HTTPS＝HTTP 跑在 TLS 上。身分驗證最常被關掉，也最不能關。
  • 憑證把網域（SAN）和公鑰綁在一起，由 CA 簽名；客戶端沿著憑證鏈一路驗到信任庫裡的根 CA。伺服器要送中繼憑證。
  • TLS 1.3 一個來回完成握手：ClientHello 帶 SNI 和 key share，伺服器回憑證並用私鑰簽名證明身分。失敗多半是名稱不符、過期、不信任的簽發者。
  • 本機用 openssl 自建 CA、簽發帶 SAN 的憑證；客戶端用 --cacert、ca、NODE_EXTRA_CA_CERTS 信任它，不關驗證。
  • 公開憑證用 ACME 自動申請與續期；有效期一路縮到 47 天，續期不能寫死天數，到期監控要讀線上的憑證。
  • HTTP 只做 301 轉址並保留路徑；HSTS 只放在 HTTPS 回應，max-age 先短再長。
