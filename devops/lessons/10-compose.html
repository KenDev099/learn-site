階段 2：容器化 · 第 10 課

Docker Compose：一次啟動整套服務

咖啡店 API 現在有了乾淨的映像（第 9 課），可是它一個人跑不起來：要先有 PostgreSQL，資料庫要先建好表，API 還得知道資料庫在哪裡。用第 7 課的 docker run 一個一個開，要記住一長串參數、開的順序、哪個容器接到哪個網路。新同事照著 README 打指令，漏了一個 -v，資料就留在容器的可寫層，隔天重開就不見了。

這一課把整套服務寫進一個 compose.yaml，新同事只要設好密碼這類變數，一個指令就能把整套服務按正確順序開起來，資料也留在 volume 裡。

這課的路線：
  1. 從一長串 docker run 到一個檔案：參數、開啟順序怎麼寫成一份可以 code review、進 git 的 compose.yaml。
  2. 網路與服務名稱：api 怎麼找到資料庫，為什麼在容器裡連 localhost:5432 會失敗。
  3. 啟動順序、健康檢查與 migration：資料庫真的準備好才啟動 API，表建好了才開始接請求。
  4. 操作整套服務、資源與 log 輪替：日常的 up、logs、down 怎麼下才不會誤刪資料，重啟策略和不會塞爆磁碟的 log。
  5. 開發和類正式環境：同一份 compose.yaml 怎麼疊上覆蓋檔，分出開發用和伺服器用。
這課會用到：
  • NestJS 課第 12 課的 compose 檔：services 底下每個服務寫映像、port、volume，up --wait 啟動並等到健康，down -v 連資料一起刪。
  • 第 7 課的容器設定：資料放具名 volume 才不會跟著容器消失，--restart 決定掛了要不要重開，--memory 設記憶體上限。
  • PostgreSQL 課第 25 課的連線字串與連線池：postgres://使用者:密碼@主機:port/資料庫，連線池重複使用幾條連線給所有請求。

從一長串 docker run 到一個檔案

不用 Compose，啟動咖啡店要這樣：

docker network create cafe-net
docker volume create cafe-pgdata
docker run -d --name cafe-db --network cafe-net \
  -e POSTGRES_USER=cafe -e POSTGRES_DB=cafe -e POSTGRES_PASSWORD="$PGPASS" \
  -v cafe-pgdata:/var/lib/postgresql postgres:18.6-alpine3.24
# 手動等資料庫好了……
docker build -t learn-devops/cafe-api:10 app
docker run -d --name cafe-api --network cafe-net -p 127.0.0.1:18100:3000 \
  -e DATABASE_URL="postgres://cafe:$PGPASS@cafe-db:5432/cafe" learn-devops/cafe-api:10

步驟有順序、有等待，改一個參數要記得把容器刪掉重開。Compose 是用一個 YAML 檔描述好幾個容器、再一次啟動它們的工具（指令是 docker compose）。你寫「最後要長什麼樣子」，它負責算出要建立、重建或刪除哪些東西，這種寫法叫宣告式（declarative）。同一份檔案本身就是說明，可以 code review、可以進 git。

services:
  db:
    image: postgres:18.6-alpine3.24
    environment:
      POSTGRES_USER: cafe
      POSTGRES_DB: cafe
      POSTGRES_PASSWORD: ${PGPASS}
    volumes:
      - pgdata:/var/lib/postgresql

  api:
    build: ./app
    environment:
      DATABASE_URL: postgres://cafe:${PGPASS}@db:5432/cafe
    ports:
      - "127.0.0.1:18100:3000"

volumes:
  pgdata:

逐段看：

  • services：每個服務（service）是一種容器的設定。db、api 是你取的服務名稱，之後也是網路上的主機名稱。一個服務可以跑好幾份容器（第 13 課的水平擴展）。
  • image 直接用現成映像；build: ./app 用那個資料夾的 Dockerfile 建置。兩個都寫時，建好的映像取 image 的名字。
  • environment：容器的環境變數（程式用 process.env 讀，Node 課第 2 課）。${PGPASS} 是變數替換（interpolation）：Compose 讀檔時，把它換成你 shell 裡（或同資料夾 .env 檔裡）的 PGPASS。寫成 ${PGPASS:?先 export PGPASS}，沒設定時直接報錯並印出後面那句話，不會默默變成空字串。
  • volumes：服務裡的 pgdata:/var/lib/postgresql 跟第 7 課的 -v 一樣；檔案最下面的頂層 volumes: 宣告這個具名 volume。

Compose 把這些資源歸成一個專案（project）。專案名稱預設是資料夾名稱，可以在檔案開頭寫 name: ld-10，或用 -p ld-10 指定；它會變成所有資源的前綴：容器 ld-10-api-1、網路 ld-10_default、volume ld-10_pgdata。同一台機器上兩個資料夾剛好同名，就會互相蓋掉對方的容器，所以練習一律指定專案名稱。

網路上很多範例第一行是 version: "3.8"。這個欄位已經過時，Compose 一律用最新的規格檢查。這台 Mac 的 Compose v5.3.1 看到它會印出 the attribute `version` is obsolete, it will be ignored，直接刪掉。Compose 的版本號從 2.x 直接跳到 v5，就是為了不跟舊的「3.x 檔案格式」搞混。

YAML 速成

YAML 是用縮排表示結構的設定檔格式，Compose、GitHub Actions（第 15 課）、Kubernetes 都用它。跟 JSON 對照：

YAML等於 JSON說明
image: nginx{"image": "nginx"}物件：key: value，冒號後面要有空白
ports:
  - "80:80"		{"ports": ["80:80"]}清單：每一項以 - 開頭
cap_drop: [ALL]{"cap_drop": ["ALL"]}也可以寫成 JSON 的樣子
run: |
  npm ci
  npm test		"npm ci\nnpm test\n"| 保留換行；> 把換行折成空白

三個常踩的地方：

  • 縮排只能用空白，不能用 Tab；同一層的 key 要對齊。縮錯一格，ports 就變成上一層的東西，或直接報錯。
  • 看起來像數字或布林的值會被轉型。在這台的 Compose v5.3.1 實測，MODE: 0755 被讀成八進位，變成 "493"。no、on、yes 在舊的 YAML 1.1 解析器（舊版 docker-compose、很多 Python 工具）會變成布林值；Compose v5 雖然把它們當字串，換個工具就不一定。所以 restart: "no"、"0755"、版本號、port 對應一律加引號。
  • 含 : 或 # 的值要加引號："127.0.0.1:18100:3000"；不加引號時， # 後面會被當成註解。

不確定 Compose 怎麼理解你的檔案時，執行 docker compose config：它印出解析、替換、合併之後的最終結果，不會啟動任何東西。注意輸出裡有替換進去的密碼，不要貼到聊天室或 issue。

網路與服務名稱

Compose 會替每個專案建一個使用者自訂網路（user-defined network），名稱是 專案_default，所有服務都接上去。同一個網路裡的容器可以用服務名稱找到彼此：Docker 在每個容器裡提供內建 DNS（embedded DNS），位址是 127.0.0.11，查 db 會拿到 db 容器在這個網路上的 IP。第 4 課的 DNS 查詢流程在這裡一樣適用，只是回答的人換成 Docker。

所以 api 的 DATABASE_URL 寫 postgres://cafe:…@db:5432/cafe。最常見的錯是寫 localhost:5432：每個容器有自己的網路命名空間（第 7 課），api 容器裡的 localhost 是 api 自己，那裡沒有 PostgreSQL，結果是 ECONNREFUSED 127.0.0.1:5432。在你的 Mac 上用 localhost 連得到，是因為那時你在主機上、連的是發布出來的 port，兩件事不一樣。

容器之間互連不需要發布任何 port，ports 只管「主機怎麼連進來」。資料庫只給 api 用，就不要寫 ports。第 4 課說過，在 Linux 伺服器上，Docker 發布的 port 走的 iptables 規則排在 ufw 之前，"5432:5432" 等於把資料庫開給全世界，ufw 擋不住。真的要從主機查資料，用 docker compose exec db psql -U cafe 進容器裡查。api 要給主機上的 Nginx（第 12 課）或你自己測試，就發布在 127.0.0.1。

💡 實務上：上線前先查「誰發布了 port」
咖啡店第一次把整套服務搬上 EC2 之前，在伺服器上跑 docker ps --format '{{.Names}} {{.Ports}}'，逐一看每個容器發布了什麼：看到 0.0.0.0: 開頭、而且不是 Nginx 的 80／443，就要問為什麼。資料庫、Redis 這類服務直接暴露在網路上，會被自動掃描的機器人找到並嘗試登入。真的要用桌面工具看正式資料庫，用第 6 課的 ssh -L 通道連進去，不要把 port 開出去。資安檢查、上線審查會問的就是這一題。

啟動順序與健康檢查

加上 depends_on: [db]，Compose 會先建立 db 再建立 api，可是它只等 db 的容器「啟動」，不等 PostgreSQL「準備好接受連線」。PostgreSQL 第一次啟動要初始化資料目錄，需要好幾秒；api 這時去連，就會拿到 ECONNREFUSED。程式如果在啟動時就去連資料庫、失敗就結束，容器會一直重啟，有時候成功有時候失敗，這種看時機的錯叫競態（race condition）。

解法是讓 db 能回報「我好了」，再讓 api 等這個訊號。第 8 課在 Dockerfile 寫過 HEALTHCHECK，Compose 的 healthcheck 是同一件事，寫在服務上：

  db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 10s        # 健康之後每 10 秒查一次
      timeout: 5s
      retries: 5           # 連續失敗 5 次才算 unhealthy
      start_period: 30s    # 啟動後 30 秒內的失敗不算數
      start_interval: 1s   # 這 30 秒內每 1 秒查一次，好了就能早點放行

  api:
    depends_on:
      db:
        condition: service_healthy
        restart: true

depends_on 條件有三種：

條件等到什麼時候用在
service_started（只寫名稱時的預設）容器啟動對方不需要準備時間，或你的程式自己會重試
service_healthyhealthcheck 回報 healthy；對方沒有 healthcheck 會直接報錯資料庫、Redis 這類要時間準備的依賴
service_completed_successfully容器跑完而且結束碼是 0migration 這類一次性工作

restart: true 是另一件事：你用 Compose 重啟或更新 db 時（例如 docker compose restart db），api 也跟著重啟，重新建立連線。

上面那行 test 有兩個細節，都是在這台 Mac 實際踩過的：

  • $$：Compose 讀檔時會替換所有 $VAR，用的是主機的環境變數。寫 $POSTGRES_USER，主機上沒有這個變數，Compose 印出 The "POSTGRES_USER" variable is not set. Defaulting to a blank string.，容器收到的指令變成 pg_isready -h 127.0.0.1 -U -d 。pg_isready 只看伺服器接不接受連線，所以照樣 healthy，可是 PostgreSQL 的 log 每次檢查都多一行 FATAL: role "-d" does not exist，真正的錯誤被淹沒。寫 $$，Compose 會留下一個 $，由容器裡的 shell 用容器的環境變數展開。用 docker inspect 容器 --format '{{json .Config.Healthcheck.Test}}' 可以看到容器實際收到什麼。
  • -h 127.0.0.1：Docker 官方文件的範例沒有這個參數。postgres 映像第一次啟動時，會先開一個只聽 Unix socket 的暫時伺服器跑初始化，跑完關掉，再正式啟動。不加 -h 時 pg_isready 走 socket，在暫時伺服器那段就回報成功，api 或 migration 衝進來剛好遇到它關機。這台 Mac 用 start_interval: 1s 試了三次，三次都是 migration 拿到 ECONNREFUSED。加上 -h 127.0.0.1 改走 TCP，暫時伺服器不聽 TCP，就不會誤判。
寫了 start_interval 就一定要寫 start_period，否則 up 直接失敗：healthcheck.start_interval requires healthcheck.start_period to be set。start_interval 需要 Docker Engine 25 以上。

depends_on 只管 Compose 啟動的那一刻。正式環境裡資料庫也會重啟、切換，所以程式本身仍要能處理連不上：連線池用逾時（cafe-api 設 connectionTimeoutMillis: 2000），/health/ready 連不上就回 503，等資料庫回來就自然恢復，不要一連不上就讓程序結束。

一次性步驟：migration 與 pre_start

資料庫好了，可是裡面還沒有表。建表、改欄位的 SQL 放在 migration 檔（app/migrations/），由 node dist/migrate.js 依序套用沒跑過的，跑完就結束；套用紀錄寫在 pgmigrations 表（node-pg-migrate 9.0.0 的預設）。它要在 api 開始接請求之前跑完。

做法一：一次性服務（one-shot service），跑完就結束的服務。

  migrate:
    build: ./app
    image: learn-devops/cafe-api:10      # 跟 api 同一個映像
    command: ["node", "dist/migrate.js"]
    environment:
      DATABASE_URL: postgres://cafe:${PGPASS}@db:5432/cafe
    depends_on:
      db:
        condition: service_healthy
    restart: "no"

  api:
    depends_on:
      migrate:
        condition: service_completed_successfully

restart: "no" 是預設值，寫出來是提醒自己。千萬不要因為「其他服務都寫了」就順手改成 unless-stopped：migration 結束（exit 0）之後 Docker 會把它重開，跑完又重開，api 永遠等不到它「完成」，這台 Mac 上 up --wait 等到逾時，印出 timeout waiting for dependencies。

條件也不能寫 service_started。cafe-api 的第 2 個 migration 建了索引、模擬要跑 2 秒（正式環境建索引、回填資料常常要好幾分鐘）。實測時 api 在 migration 結束前 2 秒就啟動了，這段期間的 POST /orders 會遇到還沒建好的表。

做法二：Compose 5.3.0 起的 pre_start（init container），把步驟掛在服務底下：

  api:
    build: ./app
    depends_on:
      db:
        condition: service_healthy
    pre_start:
      - command: ["node", "dist/migrate.js"]

每一步在臨時容器裡執行，預設用服務自己的映像、接上同樣的網路和 volume，依序跑、每一步都要 exit 0，服務的容器才會啟動。跑完的步驟不會出現在 docker compose ps；之後的 up，如果上次成功、定義也沒變，就跳過。服務擴展成好幾份時，pre_start 對整個服務只跑一次，不是每一份各跑一次（Compose 5.3 還不支援 per_replica: true），所以不會有多份同時搶著跑 migration 的問題。怎麼選：

  • 只屬於某個服務的準備工作（api 的 migration、修 volume 權限）：pre_start，比較簡潔。
  • 好幾個服務共用、或想單獨執行它（docker compose run --rm migrate）：一次性服務。

兩種都不要做成「api 的啟動指令裡先跑 migration」：sh -c "node dist/migrate.js && node dist/server.js"。api 擴展成三份時，三份同時搶著跑 migration；migration 失敗時 api 會一直重啟，看起來像 api 壞了。migration 跟部署怎麼搭配（先 migration 還是先部署、新舊版本同時在跑怎麼辦）在第 17 課。

💡 實務上：migration 失敗時先看兩個地方
部署後 up --wait 失敗、api 沒起來，先 docker compose ps -a 看 migrate 的結束碼，再 docker compose logs migrate 看是哪一句 SQL 出錯。api 沒啟動正是你要的結果：寧可新版沒上線，也不要新程式跑在不對的資料表上。資深工程師會在 PR 階段就讓 CI 對一份全新的資料庫跑一次全部 migration（第 15 課），並先估大表建索引、回填資料要多久，因為它擋住的是整個部署。

操作整套服務

指令做什麼
docker compose up -d建立或更新整套服務，在背景執行。設定改過的服務會重建，沒改的不動
docker compose up -d --wait --build先重新建置映像，並等到每個服務 running（有 healthcheck 的要 healthy）才結束，失敗時結束碼非 0。--wait 本身就隱含 -d。腳本和 CI 用這個
docker compose ps -a列出這個專案的容器、狀態、健康、port；-a 連已結束的（例如 migrate）一起列
docker compose logs -f --tail 50 api看 api 最後 50 行並持續跟著看；不寫服務名稱就是全部混在一起
docker compose exec db psql -U cafe在執行中的容器裡跑指令
docker compose run --rm migrate用服務的設定另外開一個容器跑一次，跑完刪掉
docker compose restart api重啟容器。注意：不會套用 compose.yaml 的修改，改了設定要用 up -d
docker compose down停止並刪除容器和網路，具名 volume 保留
docker compose down -v連 volume 一起刪：資料庫的資料就沒了
docker compose config印出最終設定，不啟動

所有指令都要在 compose.yaml 所在的資料夾執行，或用 -f 指定檔案；專案名稱要跟 up 時一樣，不然 Compose 找不到那些容器。

-v 在很多指令代表「詳細輸出」（verbose），在 down 是 volumes。開發時想重置資料庫可以用；在伺服器上打 down -v，就是把正式資料庫刪掉。在伺服器上執行前先 docker compose config --volumes 看清楚會影響哪些 volume，而且要有還原過的備份（第 24 課）。

資源、重啟與 log 輪替

第 7 課的 --memory、--restart 在 Compose 裡這樣寫：

  api:
    deploy:
      resources:
        limits:
          memory: 256m      # 超過就被 OOM kill（結束碼 137）
          cpus: "1"         # 最多用一顆 CPU，超過只會變慢
    restart: unless-stopped
    stop_grace_period: 10s  # docker compose stop 送 SIGTERM 後等多久才 SIGKILL（預設 10 秒）
    logging:
      driver: local
      options:
        max-size: 10m
        max-file: "3"

restart: unless-stopped：程序結束或 Docker 重啟後自動拉起來，除非你手動停掉它。這就是第 6 課 systemd 的 Restart=，交給 Docker 管。stop_grace_period 要比程式排空請求的時間長（第 3 課的 SIGTERM 處理），否則還沒處理完就被 SIGKILL。

log 輪替：容器印到 stdout 的 log，Docker 會存成檔案。預設的 json-file driver 不輪替，max-size 預設是無上限，一個很吵的服務能把伺服器的磁碟寫滿，資料庫跟著寫不進去。Docker 官方建議改用 local driver：預設每個檔案 20MB、最多 5 個、壓縮舊檔。要繼續用 json-file，就一定要加 max-size（max-file 只有在設了 max-size 時才有作用）。logging 是每個服務各自設定的，db 也要寫；或在伺服器的 daemon.json 把預設改成 local，但那只影響之後新建的容器。

💡 實務上：「磁碟滿了」常常是 log 和舊映像
Linux 伺服器上 df -h（第 3 課）看到根目錄 100%，資料庫寫不進去、api 開始回 500。先用 docker system df 看映像、容器、volume、建置快取各占多少，再 sudo du -sh /var/lib/docker/containers/* 找出 log 最大的容器。舊映像可以 docker image prune 清，volume 不要跟著亂清，那是資料。預防靠兩件事：每個服務都設 log 輪替，再加上磁碟使用率的告警（第 25 課）。

第 9 課的執行期加固，在 Compose 裡寫成 read_only: true、tmpfs: [/tmp]、cap_drop: [ALL]、security_opt: [no-new-privileges:true]，跟上面這些設定放在同一個服務底下。

開發和類正式環境

開發時想改了程式馬上生效、多開一個看資料庫的網頁工具（下面的 Adminer）；伺服器上要的是固定的映像、不掛原始碼。同一份 compose.yaml 塞不下兩種需求，Compose 的做法是疊檔案：

  • compose.yaml：類正式環境的設定，伺服器上就用它。
  • 覆蓋檔（override file）compose.override.yaml：放在同一個資料夾，docker compose up 會自動讀進來疊在主檔上。只放開發要改的地方。
# compose.override.yaml（只在開發機上）
services:
  api:
    command: ["node", "--watch", "dist/server.js"]   # 檔案一改就重新啟動
    volumes:
      - ./app/dist:/app/dist                          # bind mount 本機編譯的結果
    environment:
      LOG_LEVEL: debug

  adminer:
    image: adminer:5.4.1
    profiles: [tools]
    ports:
      - "127.0.0.1:18108:8080"

合併規則：單一值（command、image）由後面的檔案取代；environment 逐個 key 合併；ports 這種清單會加在後面。要在覆蓋檔裡拿掉主檔發布的 port，得明確寫 ports: !reset []（!reset 是 Compose 的 YAML 標記，把這個欄位清回預設值；這台的 v5.3.1 實測可用）；不寫就只會越疊越多。用 docker compose config 可以看合併後的結果。伺服器上要確定不讀覆蓋檔，就明確寫 docker compose -f compose.yaml up -d。

profile：有寫 profiles 的服務，平常不會啟動，只有 docker compose --profile tools up -d 指定時才會。適合放資料庫管理工具、壓測工具、只在除錯時用的服務。

💡 實務上：Compose 適合到哪裡
團隊裡最常見的用法是開發環境：新同事 clone 專案後一行 docker compose up，資料庫、Redis、api 都有了，不用照著 README 裝半天。流量不大的服務也常直接在一台 EC2 上用 Compose 上線，期末專題也是在一台機器上用 Compose 跑整套。它的極限是「只有一台主機」：主機掛了整套都停，也不會自動把容器搬到別台。需要好幾台、自動擴縮時才換 ECS 或 Kubernetes（第 13 課談取捨），代價是更多的維運工作。

同一個資料夾的 .env 檔只拿來替換 compose.yaml 裡的 ${VAR}，不會自動變成容器的環境變數；容器拿到什麼，只看 environment 和 env_file。這兩者的差別、密碼為什麼不該放環境變數，是第 11 課的主題。

練習

三題都在 devops/practice/work/10/ 裡做，需要 Docker Desktop 在執行，第一次建置要連網路下載 npm 套件。app/ 是連 PostgreSQL 的精簡版 cafe-api：GET /health/ready 用 SELECT 1 檢查資料庫，POST /orders 需要 migration 建好的表，node dist/migrate.js 套用 app/migrations/。測試每次用隨機的 PGPASS；自己試之前先 export PGPASS=任意字串。用到的 port 是 127.0.0.1:18100～18109。

練習 1：完成 compose.yaml。db 用 postgres:18.6-alpine3.24，使用者和資料庫都叫 cafe、密碼用 ${PGPASS}（不能寫死），資料放在具名 volume，有用 pg_isready -h 127.0.0.1 的 healthcheck（容器裡的變數記得用 $$），不發布任何 port。api 從 ./app 建置，用服務名稱連資料庫（環境變數 DATABASE_URL），只發布在 127.0.0.1:18100，等 db healthy 才啟動，有記憶體上限、restart: unless-stopped、會輪替的 log。測試執行 docker compose -p ld-10 up -d --wait --build，確認 /health/ready 回 200，用 docker inspect 檢查 port、volume、資源與 log 設定，再寫一筆資料、down（不加 -v）、重新 up，資料要還在。自己試完用 docker compose -p ld-10 down -v 收掉。

練習 2：在同一個 compose.yaml 讓 migration 先跑完：用跟 api 同一個映像執行 node dist/migrate.js，可以做成一次性服務，也可以寫在 api 的 pre_start。api 要等它成功結束才啟動。測試 up --wait 之後確認 pgmigrations 有 2 筆、POST /orders 回 201；用一次性服務時，它要是 exited、結束碼 0、沒被重啟過，而且 api 的啟動時間晚於它的結束時間；不管哪種做法，api 都要在最後一個 migration 套用之後才啟動。migration 不能塞在 api 的 command 裡。看結果：docker compose -p ld-10 ps -a、docker compose -p ld-10 logs migrate。

練習 3：同事留下的 broken/compose.yaml 起不來，裡面有四個問題。在 broken/ 裡執行 docker compose -p ld-10b up -d --wait --build，照錯誤訊息和 docker compose -p ld-10b logs 一個一個修，直到 http://localhost:18102/health/ready 回 200。測試會先占用主機的 127.0.0.1:18105，模擬你的電腦上已經裝了一個資料庫。不能用刪掉 healthcheck（或換成 true）、拿掉 depends_on、把資料庫換個 port 繼續發布的方式「修好」；db 的 log 也不能出現 role "…" does not exist。

練習 4：compose.yaml 裡 api 的 DATABASE_URL 寫 postgres://cafe:…@localhost:5432/cafe，db 服務也在同一個檔案裡，api 卻一直回 ECONNREFUSED 127.0.0.1:5432。原因是？

✓ b。Compose 把服務放在同一個網路，但每個容器仍有自己的 localhost，服務之間靠內建 DNS 用名稱找到對方。a 把「同一個專案」誤解成「同一台機器的 localhost」；c 發布 port 是給主機連的，容器之間不需要，而且會把資料庫暴露出去；d 密碼錯誤會是 password authentication failed，不是連線被拒。

練習 5：同事想清掉占空間的東西，在伺服器上執行 docker compose down -v。會發生什麼事？

✓ c。在 down 這裡 -v 是 --volumes，不是 verbose。不加 -v 時具名 volume 會保留，下次 up 資料還在。b 說反了：down 預設不刪映像，-v 刪的正好是 volume。在伺服器上執行任何會刪 volume 的指令前，先確認有還原過的備份。

練習 6：api 寫了 depends_on: [db]，db 沒有 healthcheck。docker compose up 時，api 啟動的那一刻，PostgreSQL 保證能接受連線嗎？

✓ a。Compose 不知道「就緒」對每個程式是什麼意思，只有 healthcheck 能告訴它。PostgreSQL 第一次啟動要初始化，中間還會重啟一次，這段時間連線會被拒絕（c 錯）。就算有 healthcheck，程式本身也要能處理資料庫暫時連不上，因為正式環境裡資料庫也會重啟。

練習 7：db 的 healthcheck 寫成 test: ["CMD-SHELL", "pg_isready -U $POSTGRES_USER -d $POSTGRES_DB"]，environment 也設了 POSTGRES_USER: cafe。up 時 Compose 印出 The "POSTGRES_USER" variable is not set。為什麼？

✓ d。變數替換發生在 Compose 解析檔案的時候，用的是你 shell 和 .env 的值，跟容器的 environment 無關。c 是最危險的誤解：容器實際收到 pg_isready -U -d ，因為 pg_isready 只看伺服器接不接受連線，狀態仍然是 healthy，但 PostgreSQL 的 log 每次檢查都多一行 FATAL: role "-d" does not exist。b 剛好相反，CMD-SHELL 才會經過 shell 展開；a 不對，environment 設的變數容器裡看得到。

常見錯誤

  • 用 localhost 連其他服務：容器的 localhost 是自己。用服務名稱，例如 db:5432。
  • 發布資料庫的 port：容器之間互連不需要 ports；在伺服器上發布的 port 還會繞過 ufw。要查資料用 docker compose exec db psql。
  • 隨手 down -v：-v 刪的是 volume，資料庫資料直接消失。只有確定要重置資料時才用。
  • depends_on 沒寫條件：只等容器啟動，不等就緒。資料庫要配 healthcheck 和 service_healthy。
  • 一次性工作設了 restart: always 或 unless-stopped：跑完又被重開，等它完成的服務永遠起不來。用 restart: "no"（加引號）或 pre_start。
  • healthcheck 的 $ 沒有跳脫：被 Compose 換成主機的值。容器裡的變數寫 $$，用 docker inspect 看容器收到的指令。
  • pg_isready 沒加 -h 127.0.0.1：初始化時的暫時伺服器只聽 socket，healthcheck 太早變成 healthy，後面的服務剛好撞上它關機。
  • 沒設定 log 輪替：預設的 json-file 不限大小，磁碟遲早被塞滿。用 local driver，或 json-file 加 max-size。
  • 還在寫 version: "3.8"：已過時，Compose 會警告並忽略它。
  • YAML 的值沒加引號：0755 變成 493、no／on 在別的工具裡變成布林值、 # 後面變註解。有疑問就加引號，再用 docker compose config 確認。
  • 改了 compose.yaml 卻用 restart：restart 只重開舊容器，不讀新設定。用 up -d。

小結

  • compose.yaml 宣告服務、映像或建置、環境變數、port、volume；專案名稱是所有資源的前綴，練習和伺服器上都明確指定。
  • 同一個專案網路裡用服務名稱互連（內建 DNS 127.0.0.11）；只有真的要給主機連的服務才發布 port，而且發布在 127.0.0.1。
  • depends_on 預設只等啟動；資料庫配 healthcheck（$$ 跳脫、-h 127.0.0.1）和 service_healthy，migration 用 service_completed_successfully 或 pre_start。
  • up -d --wait --build 適合腳本和 CI；down 保留 volume，down -v 會刪資料；config 看最終設定。
  • 每個服務設記憶體上限、重啟策略、log 輪替（local driver），stop_grace_period 配合程式的排空時間。
  • 主檔是類正式環境，compose.override.yaml 放開發用的修改，profile 放平常不開的工具。
