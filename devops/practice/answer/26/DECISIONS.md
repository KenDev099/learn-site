# 架構決策紀錄（ADR）

## ADR-1：用單機 Docker Compose，不用 Kubernetes

### 背景

咖啡店只有一個 API 服務，尖峰每秒 36 個請求（NEEDS.md），團隊兩位工程師，沒有人有 Kubernetes 的維運經驗。
需要零停機部署、兩個以上的副本，以及部署失敗時能立即回滾。

### 決策

在一台虛擬機上用 Docker Compose 執行整套服務（compose.prod.yaml），nginx 做 TLS 終結與藍綠切換，api 每個顏色 2 個副本。

### 後果

- 好處：只要會 Docker 與 Compose 就能維運，整套設定在一個檔案裡，本機和正式環境幾乎一樣。
- 缺點：單機就是單點故障，機器掛了服務就停（只能靠備份在另一台機器重建，RTO 以小時計）。
- 缺點：沒有自動調度與自動擴展，副本數要手動改。

重新評估的時機：可用性 SLO 要提高到 99.95% 以上、服務數量超過三個，或尖峰流量超過一台機器的容量時，評估 ECS 或 Kubernetes。

## ADR-2：藍綠部署，不用滾動更新

### 背景

營業時間也要能部署（NEEDS.md），出問題時要能在一分鐘內退回上一版。

### 決策

blue、green 兩組 api 同時存在。新版本部署到沒接流量的那組，/health/ready 通過後改 nginx/active.conf 並 reload；舊的那組留著，rollback.sh 直接切回去。

### 後果

- 好處：切換與回滾都只是 nginx reload，幾秒內完成；切換前新版本已經完整啟動、檢查過。
- 缺點：要準備兩倍的 api 資源（4 個副本，只有 2 個接流量）。
- 代價：新舊版本共用同一個資料庫，migration 一定要向後相容（expand／contract，第 17 課），刪欄位要分兩次部署。

重新評估的時機：機器資源吃緊，或需要先讓一小部分使用者試用新版本時，改成滾動更新或金絲雀（第 16 課）。

## ADR-3：每 15 分鐘 pg_dump，不做 PITR

### 背景

RPO 15 分鐘、RTO 1 小時（NEEDS.md）。資料庫只有幾百 MB，跑在自己管理的容器裡。

### 決策

systemd timer 每 15 分鐘執行 ops/backup.sh（pg_dump -Fc、校驗和、異地保存），每週跑一次 ops/restore-drill.sh 量 RTO。

### 後果

- 好處：只用 pg_dump，任何人都看得懂，還原演練容易自動化。
- 缺點：最壞會遺失 15 分鐘的訂單；資料變大後 pg_dump 會越跑越久，也會增加資料庫的負載。
- 缺點：只能還原到某次備份的時間點，不能還原到「誤刪之前的那一秒」。

重新評估的時機：資料庫超過 10GB、pg_dump 超過 5 分鐘，或 RPO 要求低於 15 分鐘時，改用 WAL 封存與 PITR，或搬到 RDS 的自動備份（第 24 課）。

## ADR-4：購物車放 Redis，不放 api 的記憶體

### 背景

api 有多個副本，nginx 輪流分配請求；部署時整組副本會換掉。

### 決策

購物車以 cookie sid 為 key 存在 Redis（24 小時過期），api 本身不保存狀態。

### 後果

- 好處：請求打到哪個副本都看到同一台購物車，部署、縮放不會讓購物車消失。
- 缺點：多一個要維運的服務；Redis 掛掉時購物車功能跟著掛（readiness 會變 503）。
- 代價：Redis 沒有開持久化，重啟會清空購物車；這是刻意接受的，購物車可以重來，訂單不行。

重新評估的時機：購物車需要跨裝置保存，或 Redis 故障造成的影響超過錯誤預算時，改存資料庫或加上 Redis 的持久化與備援。
