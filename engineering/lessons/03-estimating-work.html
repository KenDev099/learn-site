階段 1：從需求到交付：釐清、驗收、估計與溝通 · 第 3 課

估工：拆解工作、估區間與處理不確定性

店長問：「集點兌換要多久？」工程師想了一下兌換 API 的程式，回答「兩天」。兩週後還沒上線：資料表的 migration（修改資料庫結構的腳本，PostgreSQL 課第 22 課）寫了一天、測試和 code review 的修改又花了兩天、會計遲遲沒回覆兌換的飲料怎麼記帳、串接會計系統時才發現對方沒有文件。更麻煩的是，店長把「兩天」記成了承諾，海報已經印好了。

這一課學的是估工（estimation）：預估完成一件工作需要多少時間。系統設計課第 2 課的「估算」估的是流量、儲存空間、機器數量；這課估的是人完成工作的時間，是另一件事。

這課的路線：
  1. 「兩天」為什麼變成兩週：開場的估計錯在哪三個地方，「要多久」該怎麼回答（開場問題的最小答案）。
  2. 拆解：把功能拆成每項不超過兩天的工作，而且不漏掉測試、review、migration、部署、等別人回覆。
  3. 三點估計與 PERT：每一項給樂觀、最可能、悲觀三個數字，算出期望值與區間；後面兩節選讀解釋區間怎麼正確加總、怎麼用模擬算出 P85。
  4. 溝通估計：怎麼用「區間＋信心水準＋前提」回答店長，被要求「只能給你 10 天」時能談什麼。
  5. 降低不確定性：找出最不確定的那一項，先花一天做 spike 縮小它。
這課會用到：
  • 第 2 課的垂直切片：每一片從畫面到資料庫都做完、能單獨上線；切得小才估得準。

「兩天」為什麼變成兩週

回頭看開場的「兩天」，錯在三個地方：

  • 只算了寫程式：工程師心裡想的是「兌換 API 寫好」，但功能上線還要建資料表、寫測試、等 review、改 review 意見、部署、上線後確認。這些加起來常常比寫程式本身還多。
  • 只給一個數字：兩天是「一切順利」時的時間。工作總有不確定的部分（會計系統有沒有文件？），一個數字沒辦法表達「可能 2 天，也可能 8 天」。
  • 估計被聽成承諾：工程師說的「兩天」是猜測，店長聽到的是「後天可以上線」。兩個人對同一個數字的理解不一樣，卻沒有人發現。

所以「要多久」最小的答案是：先拆開再估，給區間和前提，不給單一數字，例如「大約 11 到 15 天，前提是會計這週回覆記帳方式；這是估計，不是承諾」。細節在後面的〈溝通估計：區間、信心水準與前提〉。這課依序解決這三件事：先拆解、把漏掉的工作補齊；再對每一項估區間、正確地加總；最後把結果說成對方能拿來做決定的形式。

先分清楚兩個詞。估計（estimate）是對未來的預測，本質上是一個機率分布：「大概 13 天，有 85% 的機會 17 天內做完」。承諾（commitment）是你從那個分布裡選一個點答應對方：「我們答應 11/27 上線」。估計不會因為別人希望它變小而變小；承諾要選多保守的點，是可以討論的商業決定。

拆解：每一項不超過兩天

工作拆解（work breakdown）是把一個大工作拆成可以單獨估計、單獨追蹤的小工作。為什麼要拆？因為人對大工作的直覺非常不準：「集點兌換」聽起來像一週，拆開才看得到裡面有八件事。拆到多小？這課用一個實用的上限：每一項的最可能值不超過 2 個工作天。超過兩天的工作，通常是你還說不清楚裡面要做什麼，這時候估出來的數字只是猜。

拆的方法沿用第 2 課：先依垂直切片切（櫃檯手動加點、兌換、查點數），每一片再拆成具體的工作。拆完之後，用這張清單逐項檢查有沒有漏掉：

常被漏掉的工作咖啡店集點兌換的例子為什麼會漏
測試兌換規則的單元測試、點數不足與非會員的情境、API 的整合測試心裡把「寫程式」和「寫好、有測試」當成同一件事
code review 與修改等同事 review、依意見修改、再次 reviewreview 的時間不在自己手上，容易當成零
migration 與回填新增點數紀錄資料表；舊訂單要不要補發點數資料表「加一張就好」，但正式環境要排時間執行、要能回復
部署與上線後驗證部署到 staging 讓店員試、部署到正式環境、上線後看錯誤率與第一筆兌換以為按一個鈕就好
文件給店員的兌換操作說明、給會計的報表欄位說明做完才想到，或乾脆不寫
等待別人等會計確認兌換的飲料怎麼記帳、等店長決定點數要不要過期不是自己在做事，所以覺得不算時間；但它會推遲上線日
整合與修 bug前端和 API 接起來才發現欄位名稱不一致每個人都假設自己那一塊接上去就會動

拆完的集點兌換，這課後面的例子都用這份清單（單位：工作天；a、m、b 下一節解釋）：

id工作a 樂觀m 最可能b 悲觀
ledger-migration建立點數紀錄資料表與 migration0.512
earn-api結帳時加點 API11.53
redeem-api兌換 API（含點數不足、非會員）124
counter-ui櫃檯畫面：查點數與兌換11.53
accounting-sync串接會計系統（沒有文件）128

deploy部署與上線後驗證0.50.51.5
wait-accounting等會計確認點數規則0.513

最可能值加起來是 11 天，已經是「兩天」的五倍多，而這還沒考慮不確定性。

「工作天」指一個人專心做這件事的一天，不是日曆上的一天。實際上每天還有會議、支援、別的案子，所以換成上線日期時要再打折扣（例如一週只有 3～4 個工作天能用在這件事上）。「等待」不是工作量而是經過的時間，這課為了簡單把它當成跟其他工作串在一起；如果等待期間你能同時做別的工作，它對上線日的影響會比較小。
💡 實務上：拆解的結果會直接變成 ticket
在團隊裡，這份清單通常會變成 Jira、Linear 或 GitHub Issues 上的一張張 ticket，PM 和你自己都靠它追進度。很多團隊以 sprint（通常一到兩週的工作週期）排工作，在 sprint 開始前的規劃會議用 story point（相對大小的點數）而不是天數估，但「切小、補齊漏掉的工作」的原則一樣；剛加入團隊時先問清楚大家用哪一種，跟著用，不要自創一套。「等會計確認」這種等待也要開成 ticket 並標明在等誰，站會時才看得到卡在哪裡。資深工程師看到一張估「5 天」的 ticket，第一個反應通常是問：「這裡面有哪幾件事？能不能再拆？」

三點估計與 PERT

對每一項工作，不要只給一個數字，給三個：

  • a 樂觀值：一切順利時的時間。不是「不可能更快」，而是「很少會比這更快」。
  • m 最可能值：如果做很多次同樣的工作，最常出現的時間。
  • b 悲觀值：遇到常見的麻煩（文件缺漏、規則要改、環境出問題）時的時間。不是「隕石砸到機房」。

這叫三點估計（three-point estimate）。注意 accounting-sync 的三個數字是 1、2、8：最可能值離樂觀值只有 1 天，離悲觀值卻有 6 天。工作時間的分布通常是右偏的（長尾在右邊）：能省的時間有限，最多就是全部順利；能多花的時間沒有上限，一個沒文件的 API 可以讓你卡好幾天。

PERT（Program Evaluation and Review Technique，美國海軍在 1950 年代為專案排程發展的方法）用三個數字算出一項工作的期望值 E 與標準差 SD：

E  = (a + 4m + b) / 6
SD = (b − a) / 6

E 是加權平均，最可能值的權重是 4，兩端各 1。標準差（standard deviation）描述結果有多分散：SD 小代表結果大多落在 E 附近，SD 大代表可能差很多。PERT 的 SD 用「樂觀到悲觀的距離除以 6」來近似。標準差的平方叫變異數（variance），下一節加總時會用到。跑跑看每一項的 E 與 SD：

每一項的 E 都大於或等於 m：右偏的工作，平均會比「最常發生」的時間長。accounting-sync 的 SD 是 1.17 天，是其他工作的兩倍以上。

三個數字要真的反映你的不確定性。常見的偷懶寫法是 a、m、b 一律寫成 m 的 0.8 倍、1 倍、1.2 倍：看起來有區間，其實什麼也沒說。問自己：「什麼事會讓它變成兩倍？」想得出具體原因的，b 就該拉開；想不出來的，區間才窄。

整個功能加總時，期望值可以直接相加：ΣE = 13.0 天。標準差不能直接相加；工作彼此獨立時，要把每一項的變異數加起來再開根號：總 SD = √(Σ SD²) ≈ 1.49 天。再用 E ± 1.645 × SD 得到大約 90% 的區間：13.0 ± 1.645 × 1.49，約 10.6～15.4 天，下限不能小於所有樂觀值的總和 Σa。練習 2 會把這幾個公式寫成函式；為什麼這樣算、什麼時候不成立，在下一節（選讀）。

加總：變異數相加，標準差不能直接加（選讀）

這節是選讀：上一節最後的公式已經夠你算出 PERT 區間；想知道標準差為什麼不能直接加、工作之間有共同風險時區間會差多少，或要跟同事解釋這些數字時再回來看。跳過不影響後面的課。

每一項有了 E 和 SD，整個功能呢？期望值可以直接相加，標準差不行。如果每一項工作彼此獨立（一項變慢不會讓另一項也變慢），統計上成立的是變異數相加：

總期望值 = Σ E
總標準差 = √(Σ SD²)

直覺是：八項工作同時都落在最壞的情況，機率非常低；有的慢、有的快，會互相抵消一部分。把幾種常見的「加總」放在一起比：

算法結果（天）問題
只加最可能值 Σm11忽略右偏，嚴重低估：每一項的平均都比 m 長
加總期望值 ΣE13.0這才是平均會花的時間，但還沒有區間
標準差直接相加 ΣSD3.5高估分散程度：假設每一項同時往同一邊偏
變異數相加後開根號 √ΣSD²1.49獨立工作的正確總標準差
悲觀值相加 Σb27.5每一項同時最壞，幾乎不會發生；當成「保險的估計」太悲觀，也沒有機率意義

有了總期望值與總標準差，可以用常態分布（normal distribution）近似算出一個區間。常態分布就是常見的鐘形曲線：大部分結果集中在平均附近、兩邊對稱地變少；很多獨立的小誤差加在一起時，總和會接近這個形狀。在常態分布下，E ± 1.645 × SD 大約涵蓋 90%（左右各留 5%）。咖啡店的例子是 13.0 ± 1.645 × 1.49，大約 10.6～15.4 天。這個近似有兩個前提，要知道它們什麼時候不成立：

  • 工作的項數要夠多：加總的結果要接近常態分布，通常要 20～30 項；只有 8 項時只能當粗略參考。區間的下限也不應該小於所有樂觀值的總和 Σa（不可能每一項都比樂觀值更快），練習 2 會處理這件事。
  • 工作要彼此獨立：實際上常常不是。同一個人做、同一個未知因素（會計系統很難串）會讓好幾項一起變慢。

不獨立的影響有多大？用一個極端的例子算給你看：五項工作，每一項都是「一半機會 1 天、一半機會 3 天」。

平均都是 10 天。獨立時總標準差是 √5 ≈ 2.24，全部變慢的機率只有 3.1%；完全相關時標準差是 5（等於直接相加），全部變慢的機率是 50%。真實的工作介在兩者之間：√ΣSD² 是在「獨立」假設下的結果，工作之間有共同的風險時，實際的分散會更大。處理方式是把共同的未知因素找出來，單獨列成一項（例如「確認會計系統的 API」），而不是假裝它不存在。

Monte Carlo：讓電腦模擬一萬次（選讀）

這節是選讀：PERT 區間已經夠你回答「要多久」；要算出 P85 這種「有 85% 把握」的數字、工作的長尾很明顯，或專案跨好幾週、日期會牽動別人時再回來看。練習 3 是這節的實作。跳過不影響後面的課。

PERT 的常態近似在工作項數少、分布右偏時不太準。另一個方法是 Monte Carlo 模擬：用亂數把整個專案「做」很多次，每次每一項工作抽一個可能的時間、加總，重複一萬次，看這一萬個總天數的分布。不需要常態假設，也能看到右偏的長尾。

每一項工作的時間從三角分布（triangular distribution）抽樣：最低 a、最高 b、最可能 m，機率密度畫出來就是上一節那個三角形。抽樣用逆轉換法：先拿一個 0 到 1 之間的均勻亂數 u，再用這個公式換成天數：

如果 u < (m − a) / (b − a)：x = a + √(u × (b − a) × (m − a))
否則：                      x = b − √((1 − u) × (b − a) × (b − m))

(m − a) / (b − a) 是「比 m 快」的機率，也就是三角形左半邊的面積。u 落在左半邊時得到 a 到 m 之間的值，落在右半邊時得到 m 到 b 之間的值。a = b（完全沒有不確定性）時分母是 0，要直接回傳 a。

亂數要能重現：同樣的輸入，每次跑出同樣的 P85，才能寫測試、才能跟同事對答案。做法是不在函式裡呼叫 Math.random()，而是讓函式接收一個 random: () => number 參數，由呼叫端決定亂數從哪裡來。這課用 mulberry32：給它一個 seed（種子），它就產生一串固定的「看起來隨機」的數字，seed 一樣、數列就一樣。下面先只抽 accounting-sync 這一項，畫出直方圖（把 seed 或 runs 改掉再執行看看）：

最高的柱子在 2 天附近，右邊拖著一條長尾巴，跟圖一樣。對整個功能做模擬時，每一次模擬把八項各抽一次、加起來，就得到一個「這次專案花了幾天」；一萬次之後排序，用 nearest-rank 取百分位數（系統設計課第 3 課教過，那裡的 p 寫成 0～100；這課寫成 0～1）：

排序後的第 ceil(p × n) − 1 個元素（從 0 開始數）
P50：p = 0.5，有一半的模擬在這個天數內完成
P85：p = 0.85，有 85% 的模擬在這個天數內完成

用 seed 42 跑 10,000 次，咖啡店的結果是 P50 約 14.9 天、P85 約 17.1 天（練習 3 寫完可以自己重現）。這比 PERT 的 13.0 天高，原因是三角分布比 PERT 更看重兩端：三角分布一項的平均是 (a + m + b) / 3，PERT 是 (a + 4m + b) / 6。兩種模型都是近似，哪一個比較貼近你的團隊，要靠記錄實際天數回頭比對（最後一節）。它們一致的訊息是：遠比 Σm 的 11 天長，更遠比「兩天」長。

什麼時候用哪一個？工作項數少、想快速得到一個數字，用 PERT；想知道 P85、工作有右偏的長尾、或之後要加上「某幾項會一起變慢」這種關聯，用 Monte Carlo。兩者的輸入一樣是每一項的 a、m、b，品質都取決於這三個數字估得好不好。
💡 實務上：大部分的 ticket 不需要跑模擬
日常一兩天的小工作，心裡想一下 a、m、b，回答「1 到 2 天，卡住的話可能 3 天」就夠了。值得認真拆解、跑 PERT 或 Monte Carlo 的，是要跨好幾週、日期會牽動別人的工作：配合行銷活動上線、跟外部廠商串接、要排進季度規劃的功能。工具不用多，一張試算表或這課練習裡那種幾十行的程式就能做。要注意的是別讓數學製造出「很精準」的錯覺：輸入的 a、m、b 是猜的，結果寫成「P85 約 17 天」，不要寫成「17.13 天」。

溝通估計：區間、信心水準與前提

下面用 P50、P85 表達區間：P50 是有一半的機會在這個天數內做完，P85 是有 85% 的機會。咖啡店的 P50 約 15 天、P85 約 17 天，是選讀的 Monte Carlo 一節模擬出來的，比 PERT 區間偏右（原因在那一節）。沒讀那一節的話，用 PERT 區間講也可以，例如「大約 11 到 15 天，有九成把握」；說法的原則一樣。

算出分布之後，回答「要多久」時要說出三件事：

  1. 區間與信心水準：「一半的機會 15 天內，85% 的機會 17 天內」，而不是「15 天」。
  2. 前提：這個估計成立需要哪些事：「前提是會計在週三前回覆記帳方式；不含 LINE 推播」。
  3. 什麼時候會更新：「串接會計系統的 spike 做完後（週二），我會更新一次估計」。

給店長的版本可以是這樣：

集點兌換的估計：P50 15 個工作天、P85 17 個工作天。
前提：會計在 11/11（三）前確認兌換的記帳方式；範圍是櫃檯兌換與查點數，不含 LINE 推播。
最大的不確定是會計系統沒有文件，我下週二先花一天確認，之後會更新這個估計。
如果要訂上線日，我建議用 P85 加上每週實際可用的天數去排。

幾個實務上的判斷：

  • 對外承諾用 P85，不用 P50。P50 代表有一半的機會延誤；對外宣布的日期（印海報、通知客人）延誤成本高，選保守的點。團隊內部規劃可以看 P50。
  • 不要回答「最快多久」。被問到時，回答「順利的話 13 天左右，但機率不高（模擬裡大約 15%）；85% 的把握是 17 天」。只講樂觀值，對方記住的只會是那個數字。
  • 前提改變就重新估。會計晚一週回覆、店長追加「點數要過期」，原本的估計就不成立了。主動說「前提變了，我明天給新的估計」，比默默延誤好得多。
  • 被要求「只能給你 10 天」時，不要砍估計。估計反映的是工作量與不確定性，不會因為被要求就變小；能談的是範圍（先做櫃檯手動加點，兌換下一期）、時程與資源。第 4 課會練習怎麼談。

降低不確定性：找出最大的那一項，先做 spike

區間太寬（P50 15 天、P85 17 天，再往上還有尾巴）時，與其一直解釋，不如把不確定性變小。先找出誰貢獻了最多的不確定性：每一項的變異數 SD² 佔總變異數的比例。咖啡店的總變異數是 2.21，accounting-sync 一項就佔 1.36，也就是 62%。注意比的是變異數：它的最可能值 2 天和 redeem-api 一樣，工作量不是最大的，但區間最寬。

找到之後，做一個 spike：限定時間的探索工作，目的是回答問題、縮小區間，不是交付功能。好的 spike 有三個要素：

  • 限定時間（timebox）：「最多 1 天」，時間到就停，就算沒有完全回答也要帶著發現回來。
  • 要回答的問題：「會計系統有沒有可以寫入兌換紀錄的 API？認證方式是什麼？測試環境能不能用？」
  • 產出：問題的答案、一段能動的最小程式（可以丟掉）、更新後的 a、m、b。

假設 spike 發現會計系統有 API、只是沒文件，accounting-sync 的估計從 1／2／8 縮成 1／1.5／2.5。多花了 spike 的 1 天，Monte Carlo 的結果從 P50 14.9、P85 17.1 變成 P50 14.0、P85 15.3：多做一天，P85 反而提早將近兩天，而且 P50 到 P85 的距離從 2.2 天縮成 1.3 天。如果 spike 發現情況很糟（根本沒有 API），你也是在第一週就知道，而不是第三週。

這是不確定性錐（cone of uncertainty）的實際應用。這個概念最早來自 1958 年美國成本工程師協會（今 AACE International）對化工與營建估價的研究；Barry Boehm 在 1981 年的《Software Engineering Economics》把它帶進軟體業，Steve McConnell 在 1997 年的《Software Project Survival Guide》叫它 cone of uncertainty。它說的是：專案越早期，估計的誤差範圍越大；還沒釐清需求時，實際花費可能是估計的 4 倍，也可能只有 1/4。錐形不會自己變窄，是靠釐清需求（第 1 課）、切小（第 2 課）、做 spike 這些行動讓它變窄。

💡 實務上：spike 也是一張 ticket，做完要交代
全端工作常見的 spike 題目有：第三方金流或物流 API 怎麼串、新套件能不能滿足需求、舊系統的某個查詢為什麼慢。實務上它會像一般工作一樣排進 sprint，例如「spike：確認會計系統 API（1 天）」，讓 PM 知道這一天花在哪裡、換到了什麼。最常見的坑是把 spike 寫的實驗程式直接改一改就上線：它沒有測試、沒考慮錯誤處理，應該重寫。結束時用幾行文字寫下發現和更新後的估計，貼在 ticket 上，比口頭說一聲可靠。

資深視角

  • 估計是給決策用的，不是考試。店長要用它決定海報什麼時候印、要不要先砍範圍。夠讓對方做決定的精確度就好；為了把估計弄得很準而花三天開會，通常不值得。
  • 記錄估計與實際，回頭校準。每一項做完時記下實際天數。累積一段時間後看：實際天數落在自己 P85 以內的比例接近 85% 嗎？如果只有 50%，代表你的 b 估得太樂觀，下次要拉開。不記錄的人，估計永遠不會變準。
  • 切小比估準更有效。兩天以內的工作，誤差最多也就差幾天；兩週的工作，誤差可能是兩週。估不準的時候，先回頭看能不能切得更小。
  • 估計的是團隊，不是你自己的手速。新人來做、要等 review、同時在支援另一個案子，都會改變數字。說清楚「這是我做的估計，換人做要重估」。
  • 別人逼你砍數字時，談範圍。改小估計只是把風險藏起來，延誤一樣會發生，只是更晚才被發現。

練習

練習 1～4 用的都是這課的咖啡店集點兌換。數字的單位是工作天；比對小數時容許 1e-9 的誤差（浮點數運算會有極小的誤差，見 TypeScript 課第 5 課）。練習 3 不能用 Math.random()：亂數一律從參數 random 來（測試期間呼叫 Math.random() 會丟錯）。

練習 1：替「集點兌換」做工作拆解，填進 tasks。這個功能要新增一張點數紀錄資料表、寫兌換 API 與櫃檯畫面，而且要等會計確認兌換的飲料怎麼記帳。要求：至少 6 項；id 不重複；kind 一定要涵蓋 test、review、migration、deploy、waiting 這五種；每一項 0 < a ≤ m ≤ b，而且 m ≤ 2（超過就再拆）；至少一半的工作 b > m（承認不確定性）；title 2～60 個字。

練習 2：寫 pert(tasks)，回傳整個功能的 PERT 估計：mean 是各項 E = (a + 4m + b) / 6 的總和；sd 是 √(Σ SD²)，SD = (b − a) / 6；low、high 是 mean ∓ 1.645 × sd（約 90% 區間），但 low 不能小於所有 a 的總和 Σa。空陣列回傳四個 0。

練習 3（選讀，對應「Monte Carlo」一節）：寫 simulate(tasks, runs, random)，用 Monte Carlo 算出 P50 與 P85。規則（測試會用固定 seed 的 mulberry32 比對，順序不同結果就不同）：

  • 外層跑 runs 次模擬；每次模擬依 tasks 陣列的順序，每一項呼叫一次 random() 得到 u，用課文的三角分布公式換成天數，加總。
  • a = b 的工作仍然要呼叫一次 random()（讓後面的工作拿到的亂數不受影響），但直接用 a，不能產生 NaN。
  • 全部跑完後排序，用 nearest-rank（系統設計課第 3 課）取值：P50 是排序後第 Math.ceil(0.5 * runs) - 1 個，P85 是第 Math.ceil(0.85 * runs) - 1 個（從 0 開始）。

練習 4：寫 spikeTarget(tasks)，找出最該先做 spike 的工作：每一項的變異數是 ((b − a) / 6)²，回傳變異數佔總變異數比例最大的那一項的 id 與比例 share（0～1）。比例一樣時取先出現的；總變異數是 0（全部 a = b）或空陣列時回傳 { id: '', share: 0 }。

練習 5：五項獨立的工作，每一項的 SD 都是 1 天。整體的 SD 大約是多少？

✓ 獨立的工作是變異數相加：5 × 1² = 5，開根號約 2.2 天。直接把 SD 相加得到 5 天，等於假設每一項同時往同一邊偏，會高估；1 天和 0.2 天是把「平均」的概念誤用在分散程度上。不過如果五項有共同的風險（同一個未知因素），實際的分散會比 2.2 天大，最極端時接近 5 天。

練習 6：主管問：「最快多久可以做完？」你回答「樂觀的話 5 天」。最大的問題是什麼？

✓ 單一數字會被聽成承諾，而樂觀值是「一切順利」才會發生的時間。回答「順利的話 5 天，但機率不高；85% 的把握是 9 天，前提是…」，讓對方依風險做決定。只給悲觀值一樣是單一數字，而且沒有機率意義；拒絕回答則讓對方沒有任何資訊可以規劃，可以先給一個寬的區間，說明什麼時候會更新。

練習 7：你的估計是 P50 8 天、P85 11 天。老闆說：「只能給你 6 天。」資深工程師的回應是？

✓ 估計反映的是工作量與不確定性，不會因為被要求就變小；能談的是範圍、時程與資源（第 4 課）。改數字只是把風險藏起來，延誤一樣會發生，只是更晚才被發現；加班趕工通常以品質為代價；拒絕討論則沒有幫對方解決問題。

練習 8：下面哪一項最適合先做 spike？

✓ spike 的目的是降低不確定性，區間最寬、變異數佔比最大的工作效益最高：1～8 天的 SD 約 1.17，變異數是其他工作的十倍以上。3～4 天的畫面工作量大，但區間只有 1 天，做 spike 也縮不了多少；0.5 天的文件與 2～3 天的 migration 都已經很確定。

常見錯誤

  • 只估寫程式的時間：測試、code review 與修改、migration、部署與驗證、文件、等待別人回覆都要列進去。拆完用「常被漏掉的工作」清單逐項檢查。
  • 給單一數字：一個數字會被聽成承諾。給三點估計，對外說 P50／P85 與前提。
  • 把悲觀值加總當成「保險的估計」：每一項同時最壞幾乎不會發生，Σb 太悲觀，也說不出有多少把握。用 PERT 或 Monte Carlo 算出有信心水準的數字。
  • 把標準差直接相加：獨立的工作要把變異數相加再開根號；但也要記得工作有共同風險時，實際分散比 √ΣSD² 更大，把共同的未知因素單獨列出來處理。
  • 被要求砍時間就砍估計：估計不會因為被要求而變小。談範圍、時程與資源，把選項攤開讓對方決定。
  • 從不回頭比較估計與實際：記下每一項的實際天數，看實際落在 P85 以內的比例是不是接近 85%，不是的話調整自己的 b。

小結

  • 估計是機率分布，承諾是從中選的一個點；對外承諾選 P85，並寫出前提。
  • 把工作拆到每項最可能值不超過 2 天，用清單補上測試、review、migration、部署、文件、等待。
  • 三點估計 a、m、b；PERT：E = (a + 4m + b) / 6、SD = (b − a) / 6。工作時間右偏，E 通常大於 m。
  • 獨立的工作加總時變異數相加：總 SD = √ΣSD²；只加 m 會低估，加 SD 或加 b 會高估；有共同風險時實際更分散。
  • （選讀）Monte Carlo：每項從三角分布抽樣、加總、重複上萬次，用 nearest-rank 取 P50、P85；亂數用注入的 random，結果才能重現。
  • 變異數佔比最大的工作先做限時的 spike；不確定性錐靠釐清、切小、spike 變窄。記錄估計與實際，持續校準。
