階段 3：放大影響力：寫作、帶人與 AI 輔助 · 第 7 課

技術寫作：提案摘要、操作手冊與交接文件

週六晚上十一點，咖啡店的出單印表機停了，櫃檯的訂單一直排在佇列裡。值班的是新進工程師小林。他打開 wiki，找到一頁「出單問題處理」，內容只有一行：「重啟 worker 就好」。他重啟了，佇列沒有動。接下來該做什麼、能不能清掉卡住的訂單、清掉之後還能不能救回來，文件都沒寫。他只好打電話把已經睡了的阿哲叫起來。同一個月，阿哲提案「讓 POS 自動加點」，寫了三頁背景，店長看到第二頁就放下了，提案擱了三週。

兩件事的原因一樣：文件沒有替讀者著想。這一課學三種最常寫的文件：讓決策者幾分鐘內做決定的提案摘要、凌晨三點也能照著做的操作手冊、讓接手的人不用再問你的交接文件。

這課的路線：
  1. 先問讀者是誰：同一件事，給店長、值班者、接手的人看，要寫成哪一種文件。
  2. 提案摘要：阿哲那份三頁的提案該怎麼改成一頁，數字、替代方案、決定期限放哪裡，店長五分鐘內就能點頭或拒絕。
  3. 操作手冊、用模擬器演練：小林那天晚上需要的手冊長什麼樣，每個動作都有驗證、失敗有回滾或升級、中斷後可以重跑，寫完怎麼先演練一次。
  4. 交接文件：讓接手的人能自己回答「系統正常嗎、壞了怎麼辦、要找誰」，而且不寫進任何秘密值。
這課會用到：
  • 第 4 課的結論先行（BLUF）：第一句就寫結論，以及「需要誰在什麼時候前做什麼決定」。
  • TypeScript 課第 15 課的字面值聯合：'action' | 'verify' 這種型別，值只能是列出來的其中一個；練習的手冊步驟用它表示種類。

先問：讀者是誰、讀完要做什麼

同一件事「出單佇列」，會有三種讀者，需要的文件完全不同：

讀者他的處境讀完要能文件
店長很忙，不懂技術，要決定花不花錢五分鐘內做決定提案摘要（one-pager）
值班的人凌晨被叫醒，壓力大，不一定熟這個系統照著一步步做，不用思考操作手冊（runbook）
接手的工程師原本的人調走或離職，沒人可以問獨立維運這個系統交接文件（handover doc）

寫之前先回答兩個問題：誰會讀、讀完要做什麼。答不出來，通常會寫成一份什麼都有、誰都用不上的文件。

文件分類有一個常用的框架叫 Diátaxis，它把文件依讀者的需求分成四類，用兩個問題區分：這份文件是告訴讀者做什麼（動作）還是知道什麼（知識）？讀者是在學習還是在工作？

類型讀者需要咖啡店的例子
教學（tutorial）學習中、要動手：帶著新手做一次，建立能力「第一天：在本機跑起集點服務，完成一筆加點」
操作指南（how-to guide）工作中、要動手：已經會基本操作，要完成一件具體的事「出單佇列卡住時的處理步驟」（runbook 屬於這類）
參考（reference）工作中、要查事實：準確、完整、不帶意見API 欄位表、環境變數清單、排程表
說明（explanation）學習中、要理解：為什麼這樣設計「為什麼點數用佇列非同步加，而不是結帳時直接寫」

分類的用處是避免混在一起：值班的人在照步驟處理事故時，不需要讀三段設計理由；設計理由放在說明文件，手冊裡一句連結過去就好。比較長的設計討論與決定，用系統設計課第 18 課的設計文件與 ADR，這課不重複。

提案摘要：讓決策者五分鐘內做決定

提案摘要（one-pager）是一頁以內的短文件，讀者是要做決定的人。阿哲那份三頁的提案，問題在結構：先寫背景，再寫技術細節，最後一頁才寫「所以想請店長同意」。店長讀不到最後一頁。提案摘要的結構固定，照順序寫：

段落寫什麼常見的錯
一句話結論建議做什麼、要多久、要對方決定什麼（第 4 課的結論先行）第一句是背景介紹
問題現在發生什麼事，有數字：多常發生、每次多久、影響多少人「很花時間」「常常出錯」
建議打算怎麼做，用讀者聽得懂的話只寫技術名詞
替代方案考慮過的其他做法，包含什麼都不做，每個寫為什麼不選只有一個方案，或沒寫不選的理由
成本與時程區間，例如 3～5 天（第 3 課）一個數字「5 天」
風險可能出錯的地方與因應不寫，等出事才說
需要的決定與期限一個能回答的問題，加上最晚什麼時候要答案「請店長參考」：沒有問題就沒有決定

為什麼一定要有「什麼都不做」？它是比較的基準。不做的成本算出來，決策者才能判斷建議值不值得。如果不做的成本很低，最好的決定可能真的是不做，這也是一個好結果。用集點的手動補點算一次：

有了數字，提案的第一句就能寫成：

✗ 集點目前由櫃檯手動補登，常常出錯，造成店員與顧客的困擾，因此我們評估了幾種做法……

✓ 建議讓 POS 結帳時自動加點，3～5 天完成，約 10 個月內回本；
  請店長 11/20 前決定是否在 12 月開始。

「需要的決定」要寫成一個問題，例如「是否同意 12 月開始導入自動加點？」。寫成「請店長參考」，店長讀完不知道要回答什麼，提案就會一直擱著。期限要早於你需要開工的日子，跟第 4 課升級時的期限一樣往回推。決定之後，在提案最上面補一行「2026-11-18 店長同意，12/1 開工」，口頭說好的事兩週後每個人記得的會不一樣。

提案摘要只有一頁，放不下的設計細節（資料表、API、重試策略、方案比較矩陣）寫進設計文件，摘要裡放一個連結。讀者不同：摘要給做決定的人，設計文件給要審查技術的人。
💡 實務上：小決定不用寫一頁，但結構一樣
工作中大部分的決定沒有大到要寫提案，例如「要不要升級套件的大版本」「這個需求要不要延到下個版本」，通常是在 Slack 或 issue 裡問一句。這時把同樣的結構壓成三四行：建議、兩個選項各自的代價、需要誰在什麼時候前回答。常見的坑是主管在私訊裡回一句「好」，其他人找不到這個決定；請他回在原本的討論串，或你自己補一句「已確認：12/1 開工」。要花錢、影響其他團隊、或做了很難退回的決定，才值得寫成正式的提案摘要。

操作手冊：凌晨三點也能照著做

操作手冊（runbook）是處理一個特定操作或告警的逐步指令，也有人叫 playbook。它的讀者是壓力最大、最不熟這個系統的人：凌晨被告警叫醒的值班者。所以它的標準是：不需要思考就能照著做。Google 的《Site Reliability Engineering》導論寫到，事先想好並記錄在 playbook 裡的做法，跟臨場即興相比，平均修復時間（MTTR，mean time to repair）大約改善 3 倍。

一份手冊由五種步驟組成：

  • 觸發條件：什麼時候用這份手冊。寫成看得到的訊號，例如「告警 PrintQueueStuck：出單佇列超過 50 筆且 5 分鐘沒有減少」。
  • 前置檢查（pre-check）：做動作之前確認條件成立。確認真的是這個問題（不是別的告警），確認現在的狀態（worker 是不是已經被暫停），以及在破壞性動作之前確認有備份。
  • 動作（action）：改變系統的指令，一步只做一件事。
  • 驗證（verification）：每個動作之後確認結果符合預期，例如「佇列在 5 分鐘內降到 10 筆以下」。沒有驗證的動作，你不知道它有沒有用。
  • 回滾（rollback）或升級（escalation）：驗證失敗時怎麼辦。回滾是把系統恢復到動作之前的狀態；升級是交給更懂的人（呼叫第二線值班）。兩個常常一起：先回滾到安全的狀態，再升級。

下面是「出單佇列卡住」的手冊片段。printq 是咖啡店自己寫的管理指令。注意每一步都是可以直接複製貼上的指令，加上預期的輸出：值班的人不用猜指令怎麼拼，也能一眼看出結果對不對。

## 出單佇列卡住（告警 PrintQueueStuck）
觸發：出單佇列超過 50 筆，且 5 分鐘沒有減少。

1. 前置檢查：確認佇列真的卡住
   $ printq status
   預期：depth 大於 50、worker: down 或 depth 持續不變。不符合 → 停止，這不是這份手冊的問題。

2. 前置檢查：worker 是否已經暫停（上一位值班可能做到一半）
   $ printq status
   worker: paused → 跳到第 4 步；worker: running 或 down → 繼續第 3 步。

3. 動作：暫停 worker      $ printq pause
   驗證：printq status 顯示 worker: paused。否則 → 第 10 步升級。

4. 動作：備份佇列         $ printq snapshot
   驗證：輸出 snapshot saved: snap-20261121-2310。否則 → 第 10 步升級（沒有備份不能清除）。

5. 動作：清除卡住的訊息   $ printq purge-stuck
   驗證：printq status 顯示 stuck: 0。否則 → 第 8 步回滾。
……
8. 回滾：還原備份          $ printq restore snap-20261121-2310
9. 回滾：恢復 worker      $ printq resume
10. 升級：呼叫第二線值班（PagerDuty「POS 出單」），貼上這次執行到第幾步、每步的輸出。

這份手冊有三個設計：

  • 破壞性動作前一定先備份：purge-stuck 會丟掉卡住的訊息，那些是客人的訂單。先 snapshot，清錯了還能還原（DevOps 課第 24 課：沒還原過的備份不算備份）。
  • 可以重複執行：上一位值班做到第 3 步就被叫去處理別的事，下一位從頭照做，第 3 步的 pause 會因為「已經暫停」而失敗。第 2 步先檢查狀態、已經暫停就跳過，手冊就能安全地重跑。這就是系統設計課第 9 課的冪等（idempotent）用在手冊上：同一份手冊中斷後重跑，不會出錯。
  • 沒修好就恢復原狀再升級：清除之後重啟仍然沒用，代表問題不在那幾筆訊息。把它們還原、讓 worker 回到正常狀態，再交給第二線。不要留下一個被暫停的 worker 和少了幾筆訂單的佇列，讓下一個人花時間猜你做過什麼。

沒有驗證的手冊會出什麼事？用一個最小的例子看：同一份「重啟就好」的手冊，在重啟有用和沒用的兩種情況下，都回報「完成」：

沒有驗證的版本，在重啟沒用時也說「完成」。值班的人回去睡覺，早上店員發現十幾張單沒出。

💡 實務上：你寫的第一份手冊，多半不是事故處理
新人最常寫到的手冊是例行操作：部署與回滾、上線前跑資料庫 migration、更換快到期的憑證或金鑰、幫客服手動補資料。這些事幾個月才做一次，每次都靠記憶就容易漏步驟。寫的時候每一步標清楚在哪個環境執行、需要什麼權限，同一個指令打到正式環境和測試環境，後果完全不同。資深的人審手冊會先看三件事：破壞性的步驟前有沒有備份、每個動作後有沒有驗證、做到一半中斷能不能從頭重跑。

把手冊寫成資料，用模擬器演練

手冊寫完，怎麼知道它真的能用？最可靠的方法是演練：在測試環境照著做一次，最好由沒寫過這份手冊的人來做。手冊第一次被執行就在真實事故中，是最常見的失敗方式：指令打錯、步驟順序不對、某個情況沒想到。Google SRE 也是把 playbook 和定期的角色演練一起用。

這課的練習把演練縮小成程式：手冊的每一步寫成一筆資料，交給一個模擬器，在幾種情境下執行，看最後的狀態對不對。每一步長這樣：

{ id: 'pause', kind: 'action', command: { type: 'pause-worker' } }
{ id: 'v-pause', kind: 'verify', command: { type: 'expect', metric: 'workerPaused', op: '=', value: 1 }, onFail: 'page' }

kind 是步驟的種類：check（前置檢查）、action（動作）、verify（驗證）、rollback（回滾）、escalate（升級）。onFail 是這一步失敗時要跳去的步驟 id，對應紙本手冊裡的「否則 → 第 10 步」。模擬器的規則：

  • 從第一步依序執行。某一步失敗（expect 的條件不成立，或指令本身失敗）：有 onFail 就跳到那一步；沒有就中止，結果是 aborted。
  • 正常流程走到第一個 rollback 或 escalate 步驟就結束，結果是 done：失敗處理放在手冊最後面，只有 onFail 會跳進去。跳進去之後依序往下執行。
  • 執行到 page-oncall 就結束，結果是 escalated。走完最後一步也是 done。
  • 最多執行 100 步。onFail 互相指向形成無窮迴圈（例如「重啟 → 驗證失敗 → 重啟」），結果是 too-many-steps。真實世界裡，這就是值班的人在凌晨重啟了二十次。

模擬的系統有五個可以檢查的數值（metric）：

metric意思
queueDepth佇列裡的訊息數
stuckCount卡住的訊息數（格式壞掉、讓 worker 一讀就當掉的訂單）
workerPausedworker 是否被暫停（1／0）
workerUpworker 程序是否在執行（1／0）
snapshotSaved是否已經備份過佇列（1／0）

以及八種指令：

command.type效果什麼時候失敗
expect檢查 metric op value（op 是 <、>、=），不改變系統條件不成立
snapshot-queue備份佇列目前的內容，snapshotSaved 變 1不會失敗
pause-worker暫停 worker已經暫停
resume-worker取消暫停不會失敗
restart-worker重新啟動 worker 程序不會失敗
purge-stuck丟掉卡住的訊息（佇列少 stuckCount 筆）worker 沒有暫停（避免同時在讀）
restore-snapshot把佇列還原成備份的內容沒有備份
page-oncall呼叫第二線值班，手冊結束不會失敗

除了 expect，每個指令成功之後，如果 worker 在執行而且沒有暫停：佇列裡還有卡住的訊息，worker 一讀就當掉（workerUp 變 0）；沒有卡住的訊息，而且問題真的只是那幾筆訊息，佇列就會被消化完（queueDepth 變 0）。

注意模擬器不會阻止你在沒有備份時清除訊息，就像真的系統不會阻止你一樣。擋住這種錯誤是手冊的工作。練習 2 的起始程式附上這個模擬器的完整程式碼，你可以直接執行、改情境、看每一步的結果。

交接文件：讓接手的人不用再問你

交接文件（handover doc）的讀者是要接手維運一個系統的人。目標是讓他在你不在的時候，能獨立回答「這個系統正常嗎？壞了怎麼辦？要找誰？」。第 5 課你從接手的那一邊學了怎麼讀懂舊系統；這一節換到交出去的那一邊，讓下一個人不用從頭追一次。

交接文件的清單：

項目寫什麼為什麼
系統做什麼兩三句話：誰用它、做什麼事、停了會怎樣判斷事情有多急
架構圖它跟誰溝通：POS、資料庫、簡訊服務出事時知道往哪查
怎麼確認健康儀表板的名稱、健康檢查的網址、正常值是多少「正常」要有數字，不然看了也不知道
排程工作名稱、什麼時候跑、失敗了會怎樣、要做什麼排程最容易被忘記，常常一個月才跑一次
外部依賴與聯絡人廠商、窗口、電話或信箱出事時不用翻舊信找人
秘密的位置名稱與存放位置，從不寫值見下方
部署與回滾怎麼部署、怎麼退回上一版，或連到對應的手冊接手第一週通常就要部署
已知問題已知的 bug 與怪行為，附 issue 編號不用再花時間重新發現
負責人交接之後誰負責、備援是誰沒有名字的系統，出事時每個人都以為別人在看

秘密（secret）是 API 金鑰、資料庫密碼、token 這類拿到就能操作系統的值。交接文件只寫它的名稱與存放位置，例如「POS_API_KEY：AWS SSM Parameter Store 的 /cafe/prod/pos-api-key，有權限的是工程群組」。不寫值的原因：文件會被複製、轉寄、貼進聊天、被搜尋引擎索引，你控制不了它會去哪裡；秘密要放在有權限控管、有存取紀錄、能更換的秘密管理系統（Auth 課第 23 課）。base64 編碼不是加密，任何人都能解回來。完全不提也不對，接手的人會找不到。

已經寫進文件或聊天的秘密，要當成已經外洩：到服務商那邊撤銷、產生新的、更新秘密管理系統裡的值，刪掉文件裡那一行不夠（版本紀錄還在）。寫完文件後掃一次常見的秘密格式，是很便宜的保險：

程式碼不用自己寫這種掃描：GitHub 的 secret scanning push protection 會在推送含秘密的程式時擋下來（個人帳號推到公開 repo 時預設開啟；repo 層級要管理者自己開）。但它管不到 wiki、聊天和文件，寫的人自己要有這個習慣。

💡 實務上：交接最常漏的是權限和帳號，不是文件
離職、調部門、外包結案都會交接，文件寫得再完整，接手的人沒有權限一樣動不了。常見的坑：廠商後台用前任的個人信箱註冊、雙重驗證綁在他的手機、雲端帳單的通知只寄給他一個人，人走了才發現登不進去。交接清單裡要列出每個帳號的擁有者，換成團隊信箱或共用的管理帳號。最有效的驗收是趁你還在的時候，讓接手的人自己部署一次、照手冊處理一次告警，卡住的地方當場補進文件。

寫作技巧：每一種文件都適用

  • 結論先行：第一句就是讀者最需要的東西：提案是建議與決定，手冊是觸發條件，交接文件是「這個系統做什麼、停了會怎樣」。
  • 一段一件事：一段話混了問題、方案和風險，讀者要自己拆。分段，每段第一句說這段在講什麼。
  • 數字取代形容詞：「很慢」→「p95 1.8 秒」；「常常出錯」→「上個月 12 次，其中 2 次補錯點數」；「盡快」→「11/20 前」。形容詞讓每個讀者想像不同的東西。
  • 能列表就列表，能做表就做表：步驟用編號清單，比較用表格。值班的人在找第幾步，不是在讀文章。
  • 寫具體的指令與值：「重啟服務」→「printq restart」；「檢查佇列」→「printq status，預期 depth 小於 10」。
  • 請目標讀者照著做一次：寫手冊的人看不出缺了什麼，因為缺的東西在他腦袋裡。請新人照交接文件在本機跑起來、請另一位值班照手冊演練，卡住的地方就是要補的地方。

資深視角：文件也要維護

過時的文件比沒有文件更危險：沒有文件，讀者知道要去問；過時的文件，讀者會照著做錯的事，而且很有信心。手冊裡的指令改名了、交接文件裡的負責人離職了，下一次出事時才會被發現。讓文件跟著系統一起變的做法：

  • 放在程式旁邊：手冊與交接文件放在專案的 docs/ 或 RUNBOOK.md，用 Markdown，跟程式一起進版本控制。改了指令的 PR，同一個 PR 更新手冊；code review 時一起看（系統設計課第 20 課）。
  • 告警連到手冊：每個會叫醒人的告警，訊息裡附上對應手冊的連結（DevOps 課第 25 課）。沒有手冊的告警，值班的人只能即興。
  • 事故之後更新：照手冊處理時發現少了一步、指令錯了，事後檢討的待辦就包含修手冊（系統設計課第 21 課）。
  • 寫上負責人與最後確認日：文件開頭寫「負責人：你；最後演練：2026-11-21」。超過一季沒確認的，排進下次的演練。

不是每件事都要寫文件。會重複發生的操作、會叫醒人的告警、要交給別人的系統，值得寫；一次性的操作，在 PR 或 issue 裡寫清楚就夠了。判斷標準是：下一次做這件事的人，是不是可能不是你。

練習

練習 1～3 是寫函式或填資料，起始程式已經宣告好型別。不能用 Date.now() 或 Math.random()。

練習 1：寫 lintProposal(p)，檢查提案摘要的結構，回傳違規代碼的陣列，依下面的順序，沒有違規就回傳空陣列：

  1. 'no-number-in-problem'：problem 裡沒有任何半形阿拉伯數字 0～9。
  2. 'no-do-nothing'：沒有任何一個替代方案的 name 包含「不做」兩個字（「什麼都不做」「先不做」都算）。
  3. 'alt-without-reason'：有替代方案的 whyNot 去掉前後空白後是空字串。
  4. 'cost-not-range'：cost.lowDays 大於或等於 cost.highDays（不是區間）。
  5. 'no-risks'：risks 是空陣列，或每一項去掉前後空白後都是空字串。
  6. 'decision-not-question'：decision.question 去掉前後空白後，不是以全形問號「？」結尾。
  7. 'summary-too-long'：summary 的長度（.length）超過 80。

寫好之後，修好阿哲的草稿：填 fixed，讓 lintProposal(fixed) 回傳空陣列。問題用課文的數字（每週約 3 次、每次約 20 分鐘）；除了「什麼都不做」，至少再寫一個真的考慮過的替代方案；decision.by 是 'YYYY-MM-DD' 格式的真實日期。

練習 2：替「出單佇列卡住」寫操作手冊 runbook，用上面的模擬器規則與八種指令。手冊要在三個情境都得到正確結果：

  • 情境 A：佇列 120 筆、其中 1 筆卡住，worker 已經當掉。清掉卡住的訊息、恢復並重啟 worker 後，佇列會被消化完。結果要是 done，queueDepth 是 0，worker 沒有被暫停。
  • 情境 B：跟 A 一樣，但問題不在那筆訊息，做完同樣的動作佇列還是不會動。結果要是 escalated，而且在升級之前已經成功 restore-snapshot（把清掉的訂單放回去）、worker 不是暫停狀態。
  • 情境 C：上一位值班做到一半：worker 已經暫停、已經備份過。你的手冊從頭重跑，結果仍要是 done、queueDepth 是 0。
  • 情境 D：告警誤報：佇列只有 20 筆、沒有卡住的訊息、worker 正常在跑。前置檢查要擋下來：結果是 aborted，而且沒有執行任何動作。

另外要符合這些規則：第一步是 check；check、verify 用 expect，其他種類不用；escalate 步驟用 page-oncall；每個 action 的下一步都是 verify；每個 verify 都有 onFail，而且指向存在的 id；id 不重複；執行 purge-stuck 時一定已經備份過；最多 20 步。起始程式最下面有模擬器，按「執行」會印出四個情境的結果。

練習 3：阿哲下週調到別的專案，集點服務交給你。他留下一份很亂的筆記（在起始程式的註解裡）。整理成 handover：

  • jobs：筆記裡的每一個排程都要列出，name 用筆記裡的名稱，schedule 與 ifFails（失敗時要做什麼）不能空。
  • dependencies：兩個外部依賴，name 包含筆記裡的名稱（「POS 廠商」「SMSGo」），一個依賴一筆；contact 照筆記寫電話或信箱。
  • secrets：三個秘密，name 用筆記裡的名稱；location 寫筆記裡的正式存放位置，以 'aws-ssm:' 或 '1password:' 開頭，例如 'aws-ssm:/cafe/prod/xxx'、'1password:保險庫名稱'。整份 handover 裡不能出現任何秘密值。
  • healthChecks 至少兩項（看什麼、怎麼看），筆記裡的儀表板與健康檢查網址都要有；knownIssues 列出筆記裡的已知問題（附 issue 編號）；purpose 不能空；owner 寫交接後的負責人。

練習 4：操作手冊的動作是「重啟出單 worker」。下一步最應該寫什麼？

✓ 每個動作之後都要有驗證，以及驗證失敗時的出路；沒有驗證，重啟沒用時手冊也會回報「完成」。重啟資料庫是另一個沒有根據的破壞性動作，會擴大影響；通知店長可以做，但不能取代確認系統是否恢復。

練習 5：交接文件要記錄金流 API 的金鑰，正確的寫法是？

✓ 文件會被複製、轉寄、搜尋，秘密只能放在有權限控管與存取紀錄的秘密管理系統，文件寫位置就好。base64 是編碼不是加密，任何人都能解回來；完全不提，接手的人找不到金鑰，最後只能到處問，秘密反而更容易被貼進聊天。

練習 6：提案的替代方案為什麼要包含「什麼都不做」？

✓ 不做的成本是比較的基準：一年 52 小時對上 3～5 天的開發，決策者才能判斷。如果不做的成本很低，最好的決定可能真的是不做，這也是提案的好結果。決策者通常不知道問題發生的頻率與代價，所以要寫出來。

練習 7：新進工程師小林第一天要在本機把集點服務跑起來、完成第一筆加點。依 Diátaxis，最適合給他哪一種文件？

✓ 小林在學習、要動手，需要的是教學：有人替他安排好順序，做完就有能力。參考文件適合已經會的人查事實；說明文件回答為什麼，適合之後想理解設計時讀；runbook 是給已經熟悉基本操作、要完成特定任務的人。這些他之後都會用到，但第一天不是。

常見錯誤

  • 提案先寫背景，結論在最後一頁：決策者讀不到最後。第一句寫建議、時程與要對方決定什麼，細節放後面或連到設計文件。
  • 問題沒有數字、沒有「什麼都不做」：「很花時間」沒辦法跟開發成本比較。寫出頻率與每次的代價，把不做當成一個替代方案。
  • 操作手冊只有動作：沒有驗證，就不知道動作有沒有用；沒有回滾或升級，驗證失敗時值班的人只能即興。每個動作後面接驗證，驗證失敗走向回滾或升級。
  • 破壞性動作前沒有備份：清除、刪除、覆寫之前先備份並確認備份成功，清錯了才救得回來。
  • 手冊沒演練過：第一次執行就在事故中，指令打錯、步驟少一步都在凌晨才發現。請沒寫過的人在測試環境照做一次。
  • 把秘密值寫進文件或聊天：只寫名稱與位置。已經寫出去的秘密當成外洩，撤銷並更換。
  • 文件寫完就不更新：過時的文件讓人很有信心地做錯事。文件放在程式旁邊，改程式的 PR 一起改文件，事故後更新手冊。

小結

  • 寫之前先回答：誰會讀、讀完要做什麼。Diátaxis 把文件分成教學、操作指南、參考、說明；runbook 是操作指南。長的設計與決定用設計文件與 ADR。
  • 提案摘要一頁以內：一句話結論、有數字的問題、建議、包含什麼都不做的替代方案、成本區間、風險、一個能回答的決定問題與期限。
  • 操作手冊：觸發條件 → 前置檢查 → 動作 → 驗證 → 失敗時回滾或升級；每一步是可以複製的指令加預期輸出；破壞性動作前先備份；先檢查狀態讓手冊可以重跑。
  • 手冊要演練：用模擬器或測試環境跑正常、動作沒用、做到一半三種情況。
  • 交接文件：系統做什麼、怎麼確認健康、排程與失敗時怎麼辦、外部依賴與聯絡人、秘密的位置（從不寫值）、部署與回滾、已知問題、負責人。
  • 文件跟程式一起維護：放在專案裡、跟 PR 一起更新、告警連到手冊、寫上負責人與最後確認日。
