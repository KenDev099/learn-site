階段 2：接手舊程式：讀懂、鎖住、安全修改 · 第 5 課

接手既有系統：讀程式、追資料流、確認實際行為

店長說：「下個月想在結帳加生日折扣。」要改的是三年前外包寫的結帳程式：寫的人早就離職，沒有任何測試，README 最後一次更新是 2023 年。打開檔案，裡面有你看不懂的條件、跟程式對不上的註解，還有一個大家都說「不要碰」的函式。這種時候最容易出事的做法，是找到看起來像的地方直接改。

這一課學的是動手改之前的那一段：先把舊程式實際怎麼運作弄清楚。第 6 課接著把讀懂的行為用測試鎖住，再小步修改。

這課的路線：
  1. 接手第一天：程式、註解、README 三種資訊各能信幾分，為什麼先不要改任何一行。
  2. 從入口追：從一個入口出發，追出實際的呼叫順序與資料流，找出哪裡算錢、哪裡寫資料。
  3. 影響分析：改一個共用函式之前，怎麼用依賴圖找出所有會受影響的呼叫者。
  4. 用實驗確認、文件與程式不一致時：註解說「滿 500」、程式寫「超過 500」，怎麼用實驗確認實際行為，決定以哪一邊為準、要問誰。
  5. 其他線索：用 git 歷史、PR 與還在的同事，找出程式「為什麼」這樣寫。
這課會用到：
  • TypeScript 課第 14 課的 Record：Record<string, string[]> 是鍵為字串、值為字串陣列的物件，這課用它表示「誰呼叫誰」。
  • TypeScript 課第 2 課的 Set／Map：Set 存不重複的值，Map 存鍵值對；追呼叫關係時用來記住走過的函式。

接手第一天：先不要改任何一行

舊系統（legacy code）不一定很老。Michael Feathers 在《Working Effectively with Legacy Code》（2004）裡的定義是：沒有測試的程式。沒有測試，你改了一行之後，沒有任何東西會告訴你哪裡壞了；常見的結果是上線三天後，會計發現報表對不上。

接手時手上通常有三種資訊，可信度不一樣：

來源它告訴你的可信度
註解、README、交接文件某人在某個時間點以為程式怎麼做最低：改程式的人常常忘了改文件
程式碼程式應該怎麼執行中：要配合設定、資料、執行環境才是完整的答案
實際執行的結果（本機、staging、正式環境的 log 與資料）。staging 是第 2 課提過的預備環境（設定和正式環境一樣、用測試資料）程式實際做了什麼最高：這就是使用者每天看到的行為

所以接手的前幾天，目標是建立一張地圖，而不是開始寫功能：

  • 有哪些入口（entry point）：外部觸發程式的地方，例如 API 路由的處理器（handler）、排程工作（cron job）、佇列的消費者、按鈕的事件處理。
  • 從這次要改的入口出發，呼叫了哪些函式、金額在哪裡被算、在哪裡被四捨五入、在哪裡被存起來。
  • 哪些函式有副作用（side effect）：除了回傳值以外，還改變了外界，例如寫資料庫、送訊息、呼叫外部 API、寫檔案。副作用是改程式時最危險的地方，也是做實驗時要小心的地方。沒有副作用、同樣的輸入永遠回傳同樣結果的函式叫純函式（pure function），例如只算金額的函式，可以放心反覆執行。
  • 一份「我還不知道的事」清單。每讀懂一件事就劃掉一條，每冒出一個疑問就加一條。
💡 實務上：接手第一週，交出地圖和問題清單
剛到職或剛被指派一個舊專案時，主管通常不會期待你第一週就改功能，但會期待你知道自己卡在哪。第一天先確認幾件事：本機怎麼跑起來、有沒有 staging、誰能給你唯讀的資料庫和 log 權限、出事時找誰。把地圖和「我還不知道的事」清單在週會上給主管或前任看一次，錯的地方當場會被糾正。先讀懂再改，看起來比較慢，但比改完才發現弄壞報表、回頭收拾快得多。

從入口追：呼叫鏈與資料流

呼叫鏈（call chain）是從入口開始，函式一層一層呼叫下去的路徑。資料流（data flow）是一個值從輸入到輸出經過了哪些轉換和儲存，例如「訂單金額從資料庫讀出來 → 乘上退款比例 → 四捨五入 → 存進退款紀錄」。兩者要一起看：呼叫鏈告訴你「誰叫了誰」，資料流告訴你「錢在哪裡變了」。

追的方法很固定：

  1. 找入口：從網址或按鈕找。在專案裡全文搜尋路由字串（例如 '/refund'）找到處理器；前端按鈕就從 @click 綁的函式找到它呼叫的 API。
  2. 一層一層往下：編輯器的「前往定義（Go to Definition）」跳到被呼叫的函式，「尋找所有參考（Find All References）」看一個函式被誰用。兩個指令在 VS Code 的右鍵選單裡都有。
  3. 記下順序，而且是執行順序：程式碼裡先寫到的不一定先執行。f(g(x)) 字面上 f 在前，但 g 先跑完，結果才傳給 f。
  4. 標出算錢與寫入的地方：哪一行改變了金額、哪一行寫了資料。
  5. 不確定就執行一次：在本機設中斷點逐步執行（Node 課第 6 課），或在函式開頭暫時加一行 log，看實際的順序。

影響分析：改一個函式，誰會受影響

假設你為了生日折扣，想把 roundPrice 從四捨五入改成無條件捨去。這個函式不只結帳在用。影響分析（impact analysis）是在改動之前找出它會影響到的程式與功能。做法是把「誰呼叫誰」寫成依賴圖，再反方向找：誰呼叫了 roundPrice？誰又呼叫了那些呼叫者？

只看直接呼叫者，會漏掉 handleCheckout：它透過 priceCart 間接用到 roundPrice。把三個入口翻成功能，改 roundPrice 會影響結帳金額、退款金額、日報表三個地方。前兩個顧客會直接看到，第三個會計每天在用。這就是為什麼小改動也要先查呼叫者：你只打算改結帳，結果會計的報表跟著變了。

找出受影響的地方之後，每一個都要回答：這裡的預期行為是什麼？改了之後還對嗎？常見的結論有三種：

  • 全部都該跟著改：照改，並在每個地方補驗證（第 6 課的特徵測試）。
  • 只有一個地方要改：不改共用函式，在那個呼叫者裡處理差異，或新增一個名稱清楚的函式（例如 floorBirthdayPrice）給它用。
  • 不知道：寫進問題清單，問業務方。
工具找不到的呼叫者最危險。「尋找所有參考」只看得到寫死在程式裡的呼叫，下面這些都看不到：用字串動態查表（handlers[name]()）、當成參數傳出去的 callback、設定檔裡用名稱指定的排程工作、其他服務透過 API 呼叫你。所以除了編輯器的參考，也要全文搜尋函式名稱和路由字串，並看排程設定與 API 的存取 log。

把「找所有間接呼叫者」拆成步驟，就是在圖上走一遍：

  1. 先把圖反過來：calls 是「a 呼叫了誰」，影響分析要問的是「誰呼叫了 b」。掃過 calls 的每一組 a → b，建一張 callers 表（Map<string, string[]>）：callers.get('roundPrice') 是 ['priceCart', 'handleRefund', 'dailyReport']。之後每次查直接呼叫者，都是查表，不用重掃整張圖。
  2. 準備一個待查清單：一開始只放 changed。
  3. 重複：從清單拿出一個名稱，查它的直接呼叫者。沒看過的呼叫者記進「已看過」（Set），也放進待查清單，因為它的呼叫者也會受影響。
  4. 清單空了就結束，「已看過」就是答案（記得拿掉 changed 本身，再排序）。

用 roundPrice 走一次：查到 priceCart、handleRefund、dailyReport，三個都放進清單；查 priceCart 得到 handleCheckout；其他幾個沒有呼叫者，清單空了。「已看過」是擋住循環的關鍵：查 saveOrder 會找到 retrySave，查 retrySave 又找回 saveOrder；沒有「已看過」就會一直繞下去，用遞迴寫會在幾毫秒內把呼叫堆疊撐爆（RangeError: Maximum call stack size exceeded）。真實專案的依賴圖裡循環很常見（重試、互相遞迴、模組互相 import），所以這一步不能省。

💡 實務上：影響範圍寫進 PR 描述
改共用函式的 PR，描述裡加一段「影響範圍」：列出受影響的功能（結帳、退款、日報表），以及每個地方怎麼驗證過。reviewer 和 QA 會照這份清單做回歸測試（重新確認原本正常的功能沒被改壞），會計也知道上線後要看哪張報表。清單很長的時候，通常代表這次改動太大，先問自己能不能只改一個呼叫者。資深工程師 review 這種 PR，第一個問題常常就是「還有誰在用這個函式？」

確認行為不能靠挑幾個順手的例子。系統性的做法（也就是系統設計課第 21 課的「假設 → 實驗 → 縮小範圍」）是：

  1. 列出每個分支：每個 if 成立和不成立各算一個分支。測試或實驗走過了哪些分支，叫做分支涵蓋（branch coverage）；只走過「成立」那一邊，「不成立」那一邊的行為就還是猜的。
  2. 每個分支設計一個會走到它的輸入，門檻的地方加上兩側：500 和 501、可頌 2 個和 3 個、週五和週六。
  3. 執行並記錄真實的輸出，跟註解、README 寫的並排。不一樣的地方就是下一節要處理的差異。

在哪裡做實驗也有規矩。只讀資料的路徑（計算金額的函式、查詢）可以在本機隨便跑；會寫入資料的路徑，只在本機或 staging 用測試資料執行，絕對不在正式環境實驗。在正式環境下一張測試訂單，會進到會計的報表、觸發廚房出單、可能還寄出發票。正式環境的資訊用唯讀的方式取得：查 log、用唯讀帳號查資料庫（例如統計過去 90 天有多少訂單金額剛好是 500 元，判斷這個邊界影響多少人）。

只讀程式碼也會漏掉執行時才知道的事：設定檔把某個優惠關掉了、資料庫裡有程式沒預期到的舊資料、環境變數讓程式走了另一條路。實驗的結果加上唯讀的正式環境資料，才是完整的答案。

文件與程式不一致時

你發現註解寫「滿 500」、程式是「超過 500」，而且這段程式已經在正式環境跑了三年。直覺會想順手把 > 改成 >=，讓程式符合註解。先不要。

正式環境的行為就是現在的事實。三年來每一筆 500 元的訂單都沒打折，會計的報表、對帳的規則、甚至店員跟客人說的話，都可能已經建立在這個行為上。Google 工程師 Hyrum Wright 的觀察（後來被稱為 Hyrum's Law）是：使用者夠多的時候，系統所有看得到的行為都會有人依賴，不管文件怎麼寫。你「修正」它，對某些人來說就是新的 bug。

處理差異的步驟：

  1. 記錄差異：文件怎麼寫、程式實際怎麼做、用什麼輸入確認的。
  2. 判斷要不要問人：
    • 影響金額、點數、顧客看到的結果（門檻、取整、誰能拿優惠）：問有權決定的人。金額和帳務規則問會計，優惠政策問店長。
    • 純粹是文件過時（指令改名、檔案搬家、欄位改名），程式的行為沒有爭議：不用問，直接更新文件。
  3. 決定之前不改行為，並用測試把目前的行為鎖住（第 6 課）。業務方決定要改，那是一個獨立的需求變更，有自己的驗收條件，不混在重構或別的功能裡。

問的時候帶著具體的例子和影響，對方才答得出來：

README 寫「滿 500 元（含）打 9 折」，程式實際是「超過 500 元才打折」，剛好 500 元不打折。
這個行為從 2023 年上線至今沒變過；過去 90 天有 37 筆訂單剛好 500 元（唯讀查詢）。
請問哪一個是正確的規則？
  A. 維持現狀（超過 500）：只改 README
  B. 改成含 500：之後剛好 500 元的訂單會少收 50 元，過去的訂單不追溯

💡 實務上：「修正」舊行為，前端和 App 也算使用者
Hyrum's Law 在 API 上最常見：後端把列表的排序「修正」成正確的順序、把錯誤訊息改得更清楚、把空陣列改成 null，結果前端或已經上架的 App 因為依賴舊的樣子而壞掉。App 的舊版本會在使用者手機上留很久，不是你部署就能更新。所以改任何看得到的行為（API 回應、匯出的 CSV 欄位、通知內容）之前，先問：誰在讀它？要不要先通知 PM 和前端？不確定時，維持現狀並寫進問題清單，比順手修正安全。

其他線索：git 歷史、PR 與還在的人

讀程式只能知道「做了什麼」，不知道「為什麼」。> 500 可能是當初打錯字，也可能是會計特別要求的。為什麼的答案通常在歷史紀錄裡。

DevOps 課第 14 課的 git log、diff 看的是整個 repo 的變動；接手時更常用的是從一行程式往回追。git blame 在每一行前面標出最後改這一行的 commit、作者和時間。檔案很長時用 -L 只看一段：

git blame -L 40,52 src/checkout.ts       # 只看第 40～52 行
git blame -L :applyPromos src/checkout.ts # 只看 applyPromos 這個函式
git blame -w src/checkout.ts             # 忽略空白的變動，排版過的行不會蓋掉真正的作者

# 輸出長這樣：commit、作者、時間、行號、內容
a1b2c3d4 (林小華 2023-04-12 14:03:11 +0800 47)   if (amount > 500) amount = amount * 0.9

blame 只告訴你最後一次改這行的人。如果那次 commit 只是整理格式，就要往前追。兩個常用的工具：

git log -L :applyPromos:src/checkout.ts  # 列出改過 applyPromos 的每一個 commit 與 diff，從新到舊
git log -S'> 500' -- src/checkout.ts      # 找出「> 500」這個字串出現或消失的 commit
git show a1b2c3d4                        # 看那個 commit 的完整內容與訊息

git log -L 追的是一個函式（或一段行數）的完整演變，比一行一行 blame 快得多。-S 找的是某個字串的數量有變的 commit，適合回答「這個條件是什麼時候加的」。專案用大規模格式化（例如導入 Prettier）的 commit，可以用 git blame --ignore-rev <commit> 跳過它。以上選項都可以在 git help blame、git help log 查到（本課以 Git 2.51 的說明為準）。

找到 commit 之後，線索通常會延伸出去：

  • commit 訊息與 PR：訊息裡的 issue 編號、PR 的討論，常常直接寫了原因（「會計要求滿額不含 500」）。
  • 正式環境的 log 與資料：用唯讀的方式看真實的分布，判斷一個怪行為影響多少人。
  • 還在職的人：帶著具體的問題去問。「這段在幹嘛？」很難回答；「2023-04 的 a1b2c3d4 把 >= 500 改成 > 500，commit 訊息寫『修正會計問題』，你記得是什麼問題嗎？」對方幾秒就能想起來或告訴你該問誰。
💡 實務上：今天的 commit 訊息，是明天的接手線索
追過一次 blame 就會發現，「fix」「update」這種 commit 訊息什麼都沒說。輪到你寫的時候，訊息寫「為什麼」，並附上 issue 或 PR 編號，例如「結帳滿額改成不含 500（會計要求，#128）」。團隊用 squash merge 時，整個 PR 會被壓成主線上的一個 commit，訊息通常取自 PR 的標題和描述，所以 PR 描述同樣要寫清楚原因。三個月後追這段程式的人，可能就是你自己。

最後一步：把讀懂的東西寫下來。入口、呼叫鏈、副作用、文件與程式的差異、還沒解決的問題，寫成一份簡短的筆記放進專案。下一個接手的人（包括三個月後的你）不用從頭再追一次。第 7 課會教交接文件的寫法。

練習

練習 1、3、4 用同一份舊結帳模組 checkout.ts，完整程式在練習 1 的編輯器裡。商品 id：1 美式咖啡 80、2 拿鐵 110、3 卡布奇諾 110、4 伯爵紅茶 90、5 可頌 70、6 起司蛋糕 120。weekday 是 1＝週一…7＝週日，程式不讀系統時間。

練習 1：追出結帳入口 handleCheckout（POST /checkout 的處理器），填 map：chain 是執行 handleCheckout 時，依實際執行順序列出被呼叫的模組內函式（包含間接呼叫，例如某個函式裡面再呼叫的函式；不含 handleCheckout 本身與 Math.round 這類內建函式）；totalComputedIn 是 handleCheckout 裡的 total 由哪個函式回傳；roundedIn 是金額在哪個函式被四捨五入成整數；pointsBasedOn 是點數依哪個金額計算（'subtotal' 原價小計、'afterPromo' 套完優惠還沒取整、'afterRound' 取整後）；sideEffects 是有副作用的函式。不確定就照課文的方法加 log 執行一次。

練習 2：寫 impacted(calls, changed)：calls[a] 是 a 直接呼叫的函式清單；回傳所有直接或間接呼叫 changed 的函式，不含 changed 本身，用陣列預設的 sort() 排序。要處理循環呼叫（例如 saveOrder ↔ retrySave）；changed 沒有出現在圖裡時回傳空陣列。不要改動傳進來的 calls。

練習 3：用實驗確認 priceCart 的實際行為。下面的程式在 applyPromos 裡標出了 7 個分支（B1～B7）。填 probes：每個探針是一個輸入和你實際執行 priceCart(input) 得到的 observed。要求：7 個分支都至少走過一次；最多 12 個探針；輸入要是合法的購物車（至少一個品項、商品 id 1～6、數量是 1～50 的整數）；至少要有一個探針剛好落在滿額門檻上。先寫 input、把 observed 填 0，按執行看印出的實際值，再填回去。

練習 4：下面是結帳模組 README 的 8 條說明（d1～d8）和目前 package.json 的 scripts。對照練習 1 的 checkout.ts，把實際行為跟說明不一致的條目填進 discrepancies：actual 用一句話寫程式實際怎麼做（最多 120 字）；askWho 是要問誰：影響金額或點數的差異問 'accounting'（會計）或 'owner'（店長），純粹是文件過時、行為沒有爭議的填 'none'（直接更新文件）。一致的條目不要列。

練習 5：註解寫「滿 500 打 9 折」，程式寫 if (total > 500)，正式環境已經跑了三年。你應該？

✓ c：現在的行為是事實，會計的報表、對帳規則可能已經依賴它。a 等於自己替業務做了決定，可能造成另一個 bug；b 也是自己做了決定（只是選了另一邊），萬一註解才是對的，三年來少收的錢沒人知道；d 讓下一個人再踩一次。

練習 6：要改共用的 roundPrice，第一步應該做什麼？

✓ b：共用函式的改動會影響所有呼叫者（結帳、退款、日報表）。a 只驗證了一個呼叫者；c 在確認之前就分叉，兩套規則之後越差越遠，而且也許其他地方本來就該一起改；d 只找得到靜態的直接呼叫，找不到動態呼叫與間接受影響的入口，還會讓程式暫時壞掉。

練習 7：想確認某段會寫入資料庫的程式實際怎麼運作，哪個做法最安全？

✓ c：會寫入的路徑不能在正式環境實驗，測試訂單會進報表、觸發廚房出單，刪掉也收不回已經發生的副作用（a、d）。只讀程式（b）會漏掉執行時才知道的事：設定、舊資料、環境變數。唯讀查詢與 log 補上真實資料的分布。

常見錯誤

  • 還沒讀懂就開始改：找到「看起來像」的那一行就動手，漏掉同一條資料流上的其他計算。先從入口追完呼叫鏈與資料流，標出算錢和寫入的地方再動手。
  • 相信註解與 README：文件是某人某時以為的行為。用會走過每個分支的輸入實際執行，記錄真實輸出。
  • 照程式碼出現的位置當成執行順序：f(g(x)) 先執行 g。不確定就加 log 或設中斷點跑一次。
  • 改共用函式前沒查呼叫者：只看直接呼叫者也不夠，要往上找到入口，翻成「哪些功能會受影響」；動態呼叫要用全文搜尋和設定檔補。
  • 順手修正文件與程式的差異：正式環境的行為有人依賴。記錄差異、問有權決定的人，決定前用測試鎖住現狀。
  • 在正式環境做會寫入資料的實驗：在本機或 staging 用測試資料，正式環境只做唯讀查詢與看 log。
  • 讀懂的東西沒寫下來：下一個人（包括三個月後的你）要從頭再追一次。把地圖、差異和未解的問題寫進專案。

小結

  • 舊系統是沒有測試的程式。接手的前幾天先建立地圖：入口、呼叫鏈、副作用，以及「我還不知道的事」。
  • 呼叫鏈看誰叫了誰（照執行順序），資料流看值在哪裡被轉換、取整、儲存。兩者一起看才找得到跨函式的不一致。
  • 影響分析是在依賴圖上反方向找所有直接與間接的呼叫者，再翻成受影響的功能；工具找不到的動態呼叫要另外搜尋。
  • 確認行為用實驗：每個分支設計一個輸入、門檻兩側都測、記錄真實輸出。寫入資料的路徑只在本機或 staging 實驗。
  • 文件和程式不一致時，正式環境的行為是事實：記錄差異，影響金額的問業務方，純文件過時就直接更新文件。
  • git blame -L、git log -L、git log -S 找出「為什麼」，再帶著具體的 commit 去問人。
