階段 3：放大影響力：寫作、帶人與 AI 輔助 · 第 8 課

帶人與知識傳承：onboarding、可執行的回饋、在 code review 裡教人

新進工程師小林第一天報到，拿到一張寫著正式資料庫密碼的便利貼；第三天還在跟開發環境奮鬥，因為 README 寫的 Node 版本跟專案實際用的不一樣；第五天被分到「會員集點跨 POS、後台、對帳三個服務的串接」，一週結束時一行程式都沒合併。他開始懷疑自己是不是不適合這份工作。問題不在小林，在帶他的方式。

當你變資深，你的產出不只是自己寫的程式，還包括你讓身邊的人能做到什麼。這一課學怎麼帶新人：排第一週、給回饋、在 code review 裡教人。

這課的路線：
  1. 小林的第一週、onboarding 計畫：同一個新人，兩種帶法的第一週差在哪，怎麼依依賴順序排計畫，讓他第三天就上線一個小改動。
  2. 可執行的回饋：「你很粗心」怎麼改寫成情境、行為、影響、請求，讓對方聽完知道下次怎麼做。
  3. 在 code review 裡教人：新人的 PR 有十幾個問題時，留哪幾則、怎麼寫，他下次才會寫得更好，而不是被幾十則意見淹沒。
  4. 調整支援的程度：依對方對這件任務的熟悉度（不是年資）決定你要示範、一起做、他做你 review，還是放手。
這課會用到：
  • 第 7 課的交接文件：讓接手的人能自己回答「系統正常嗎、壞了怎麼辦、要找誰」；它就是 onboarding 的教材。
  • 系統設計課第 20 課的 Conventional Comments：review 意見前加標籤（praise、nitpick、suggestion、issue、question），並標明 blocking（不改不能合併）或 non-blocking；這課不重教，只談怎麼在 review 裡教人。
  • TypeScript 課第 15 課的字面值聯合：'praise' | 'nitpick' 這種型別，值只能是列出來的其中一個。

新人小林的第一週：兩個版本

onboarding（到職引導）指的是讓新成員從「什麼都不知道」到「能獨立貢獻」的過程。它不是第一天的歡迎會，而是一段有順序、有檢查點的計畫。比較小林的兩種第一週：

天反例正例
1拿到正式資料庫密碼；自己照 README 裝環境開好 repo 權限；buddy 陪他把開發環境跑起來，跑通測試
2環境還裝不起來，不好意思一直問讀交接文件與架構圖；下午跟 buddy 配對，一起改一個小地方
3還在裝環境自己做 good first issue：收據底部加一行「集點請出示會員條碼」，走完 PR、review、部署，上線
4–5被分到跨三個服務的功能，一週沒合併任何東西完成資安訓練；拿到正式環境的唯讀權限；把裝環境時踩到的坑寫回文件，這是他的第二個 PR

正例裡有幾個名詞：

  • buddy（夥伴）：新人第一個月固定可以問問題的人，通常不是主管。新人最大的障礙常常不是技術，而是「不知道該問誰、怕問太多」。指定一個人，等於告訴他「問這個人，不會被嫌煩」。
  • 結對程式設計（pair programming）：兩個人一起寫同一段程式，一人打字（driver），一人看著、思考方向、指出問題（navigator），隔一段時間交換。帶新人時，讓新人打字、你當 navigator，他學得最快：手有動到，卡住時你馬上在旁邊。
  • good first issue：範圍小、風險低、不需要懂整個系統、但要走完完整交付流程的任務。開源專案常用這個標籤標出適合新貢獻者的 issue，團隊內部也可以平常就收集幾個備用。

第一個任務的目的不是產出功能，而是讓新人走完一次從拉分支、寫程式、跑測試、開 PR、回應 review、合併到部署的流程。走過一次，他就知道每一關在哪、卡住時該找誰；之後的任務只是內容變大，流程已經熟了。「改收據文字」很小，但它碰到的流程跟「做會員集點」一樣多。

onboarding 計畫：依賴順序與「完成的樣子」

排計畫時，把每一項想成有依賴（dependency）的工作：沒有帳號就裝不了環境，環境沒好就沒辦法配對寫程式，沒配對過就自己上線風險太高。常見的順序：

三個原則：

  • 權限隨需要逐步開通：這是 Auth 課第 18 課的最小權限（least privilege）用在人身上。第一天只需要 repo；要部署到 staging（預備環境：設定跟正式環境一樣、但用測試資料，第 5 課提過）時再開 staging；正式環境的唯讀權限要等資安訓練完成、而且他已經在正常流程下上線過一次。正式環境的寫入權限不在第一週的計畫裡。第一天就給正式資料庫密碼，新人不小心連錯資料庫跑一句 DELETE，責任在給權限的人。
  • 每一步寫出「完成的樣子」：「熟悉環境」沒辦法判斷做完沒；「npm test 全部通過、本機打開 localhost:3000 看到菜單」可以。新人自己就能確認進度，不用一直問「這樣算好了嗎」。
  • 第 3 天前交付一個小改動：越晚有第一次交付，新人越焦慮，你也越晚發現他卡在哪。第一週結束還沒合併過任何東西，通常代表環境、權限或任務大小有問題，要回頭檢查計畫，而不是怪新人。

💡 實務上：新人報到前一週就要開始準備
帳號與權限申請常要等 IT 或主管簽核，新人到了才申請，第一天就只能乾坐。資深的人會在報到前確認：筆電和帳號申請送出了沒、buddy 這週的行程有沒有空出時間、手邊有沒有一兩個 good first issue 可以給。報到前也自己照著文件，在乾淨的環境把開發環境從頭裝一次：文件過時的地方先修掉，新人第一天才不會卡在你早就知道的坑。

可執行的回饋：情境、行為、影響、請求

小林的 PR 上線後，有一次 migration（資料庫結構變更的腳本）失敗，你半夜手動修了資料。隔天你想跟他說這件事。比較兩種說法：

✗ 你最近有點粗心，migration 要小心一點。

✓ 11/3 #42 的 PR（情境），migration 只有往前的腳本、沒有回滾腳本（行為），
  上線失敗時只能手動修資料，集點停了 30 分鐘（影響）。
  下次在 PR 說明裡加上回滾步驟，並在 staging 跑一次回滾（請求）。

第一種說法的問題：「粗心」是對人的評價（label），不是對方做了什麼。小林聽完只知道你對他不滿，不知道指的是哪件事，也不知道下次具體要做什麼；「要小心一點」不是一個可以執行的動作。被貼標籤的人通常會防衛（「我哪有粗心」），對話就變成爭論個性，而不是解決問題。

可執行的回饋（actionable feedback）是對方聽完知道下一次具體要怎麼做的回饋。常用的結構是 SBI 回饋模型，由 Center for Creative Leadership（CCL）提出：

部分寫什麼檢查方式
Situation（情境）什麼時候、哪件事有日期、星期、「昨天」這類時間，或 PR 編號。對方能馬上想起是哪一次
Behavior（行為）你觀察到、攝影機拍得到的行為沒有評價詞：粗心、懶、態度、很差；也沒有「總是」「從不」這種誇大
Impact（影響）這個行為造成了什麼結果具體的結果：要手動修資料、停了 30 分鐘、別人不敢改
Request（請求）希望下一步怎麼做（這門課加上的第四部分）以動作開頭：加上、改成、先、在、請、下次……；不是「小心」「注意」「加油」

為什麼「總是」「從不」也算評價？因為它們幾乎都不是事實（「你總是不寫測試」，但上個月的 PR 有寫），對方只要舉出一個反例，你的整則回饋就被否定了。說具體那一次就好。

CCL 後來的延伸版本在影響之後加上 Intent（意圖）：問對方「當時你的想法是什麼？」也許小林知道要寫回滾，只是不知道 staging 可以演練。回饋是對話，不是宣判；你可能也漏看了什麼。

什麼時候、在哪裡說：

  • 私下說：改進的回饋一對一講，不在站立會議、團隊頻道裡講。稱讚可以公開。
  • 及時說：事情發生後一兩天內，細節大家都還記得。累積到半年一次的考核才說，對方已經用錯的方式做了半年。
  • 好的也要說：「#45 你主動補了退款的測試，review 時我一看就知道邊界有顧到」也是 SBI。說出具體哪裡好，對方才知道要繼續做什麼。

回饋也可以寫成資料，用程式做最基本的檢查（練習 2 會寫這個 lint）。它抓不出回饋寫得好不好，但抓得出最常見的四個問題：沒有情境、用標籤代替行為、沒有影響、請求不能執行。

💡 實務上：SBI 不只用在帶新人
最常用到的地方是每週或隔週的一對一會議（1:1），以及考核季要替同事寫的同儕回饋；跟 PM、設計師、甚至主管反映問題時，同一個結構一樣好用（「昨天的需求在上線前一小時才改，QA 來不及測，下次能不能在前一天中午前定案？」）。改進的回饋盡量當面或視訊說，文字訊息少了語氣，很容易被讀成指責。寫進考核的內容，平常就應該說過；對方在考核上第一次聽到問題，代表你平常沒有給回饋。

在 code review 裡教人

系統設計課第 20 課談 review 看什麼、依什麼順序、用標籤分輕重。對新人的 PR，review 還有另一個目的：他看完你的意見，下一次會寫得更好。Google 的〈How to write code review comments〉把它列為次要目標：主要目標是讓這個改動盡可能好，其次是提升開發者的能力。下面是小林兌換點數的 PR：

 1  import { Router } from 'express'
 2  import { logger } from './logger.js'
 3  import { db } from './db.js'
 4
 5  export const redeem_router = Router()
 6
 7  // 10 點換一杯中杯飲料（中杯以下的品項）
 8  redeem_router.post('/cards/:id/redeem', async (req, res) => {
 9    const card_id = Number(req.params.id)
10    const product_id = Number(req.body.productId)
11    if (!Number.isInteger(card_id) || !Number.isInteger(product_id)) {
12      return res.status(400).json({ error: 'bad request' })
13    }
14
15    const card = await db.query('SELECT balance FROM cards WHERE id = $1', [card_id])
16    if (card.rows.length === 0) {
17      return res.status(404).json({ error: '找不到這張點數卡' })
18    }
19    const current_balance = card.rows[0].balance
20    if (current_balance < 10) {
21      return res.status(409).json({ error: '點數不足，還差 ' + (10 - current_balance) + ' 點' })
22    }
23
24    db.query('UPDATE cards SET balance = balance - 10 WHERE id = $1', [card_id])
25    db.query(
26      'INSERT INTO point_ledger (card_id, delta, reason) VALUES ($1, $2, $3)',
27      [card_id, -10, 'redeem:' + product_id],
28    )
29    logger.info('redeem ' + card_id + ' ' + product_id)
30
31    const new_balance = current_balance - 10
32    return res.json({ ok: true, balance: new_balance })
33  })

你看完寫了 14 則草稿：變數用 snake_case（專案慣例是 camelCase）在第 5、9、10、19、31 行各一則；第 24、25 行的 db.query 沒有 await；數字 10 寫死在好幾處；還有 import 順序、log 格式、註解用字。直接全部送出，小林會收到 14 則通知，其中 5 則講同一件事，真正會讓客人拿到飲料卻沒扣點的 await 問題被埋在中間。教人的 review 這樣整理：

  • blocking 的意見說明為什麼，並附參考：只寫「這裡要 await」，小林會改這一行，下次在別的地方再犯。寫成「沒有 await，回應送出時扣點可能還沒完成，扣點失敗也不會進到錯誤處理：客人拿到飲料，點數卻沒扣」，再附上 async／await 的說明，他學到的是規則，不是這一行。
  • 同一種問題只留一則：snake_case 出現 5 次，留一則說明慣例與原因、列出所有行號、附上 style guide 連結。重點清楚，也教到背後的規則。
  • nitpick 最多留 3 則：小地方太多時只留最重要的 3 則，其餘改成「要不要找 15 分鐘一起看？」私下一起看比一則一則寫快，也不會讓 PR 看起來滿江紅。
  • 用問題引導：第 19～24 行先讀餘額、判斷、再扣點。與其直接寫答案，可以問「如果同一張卡的兩個兌換請求同時進來，兩邊都讀到 12 點，會發生什麼事？」讓他自己想到這是競態（race condition）：結果取決於兩個請求誰先執行到哪一行，兩邊都通過「點數夠」的檢查，各扣 10 點，卡片變成 −8 點（PostgreSQL 課第 19 課教怎麼用鎖避免）。自己想到的，印象比你告訴他深。但問題要有方向；他想不到時，下一則就直接給答案與連結，不要讓人猜謎。
  • 每次至少一則具體的稱讚：第 11～12 行在一開始就擋下非整數的輸入，壞資料進不到資料庫。說出來，他就知道這個習慣是對的。Google 的指南也提醒：人會從「做對的地方被肯定」學到東西，不只從被指正學到。

留意見時對事不對人：寫「這段程式在兩個請求同時進來時會超額兌換」，不寫「你沒想到並發」。也不要直接幫他把程式改好推上去：Google 的指南寫明修好 PR 是作者的責任；你改了，他下次還是不會。例外是他卡住很久、或時程真的不允許，這時跟他配對一起改，邊改邊講。

nitpick 永遠是 non-blocking。不小心把命名問題標成 blocking，新人會以為命名跟資料錯誤一樣嚴重，也會讓 PR 卡在不重要的爭論上。整理意見時，標籤是 nitpick 的就一律改成 non-blocking。

調整支援的程度：看熟悉度，不看年資

同一個人，碰不同的任務需要不同的支援。帶人時常用的四個階段：

階段你做什麼什麼時候用
示範（demo）你做，他看，你邊做邊講為什麼他從沒做過這類任務
一起做（together）配對，他打字，你在旁邊做過一次
他做、你 review（review）他獨立完成，你仔細 review做過兩次以上，但最近一次還有必須修改的問題
放手（delegate）他自己決定、自己完成，事後一起回顧做過兩次以上，最近一次沒有必須修改的問題

判斷依據是對這件任務的熟悉度，不是年資。阿哲有 8 年經驗，剛加入咖啡店團隊，第一次碰 POS 對帳的排程：他會寫程式，但不知道這套系統的對帳規則和怪行為。直接放手，他可能用很漂亮的程式做錯業務規則。反過來，小林雖然才來兩個月，但已經寫過三次 migration、最近一次乾淨：這件事可以放手，事後花 10 分鐘一起回顧就好。

兩種常見的錯：一直停在示範（「我自己做比較快」），新人永遠學不會，你永遠是瓶頸；太早放手，新人在沒人看的地方做錯，事後要花更多時間修。放手之後的事後回顧不能省：問他「哪裡卡住？下次會怎麼做？」，他講得出來才是真的會了。

💡 實務上：帶人的時間要算進排程
示範和配對會讓你這週自己的產出變少，估工時沒把它算進去，最後常常變成「沒空帶，叫他自己看文件」。跟主管或 PM 排工作時，直接說明「這兩週我約有三成時間在帶新人」，並把新人的任務也排進 sprint，讓這件事被看見。反過來，你是被帶的一方時，也可以主動說「這類任務我只做過一次，可以先配對嗎？」，比硬著頭皮做錯再重來省時間。

資深視角：讓知識不只在你腦中

  • 你的產出包含團隊的產出：花一小時讓新人能自己處理對帳問題，之後每週省下你兩小時。資深工程師的影響力，來自讓別人變強，而不是自己做完所有事。
  • 同一個問題回答第三次，就寫成文件：「staging 的測試帳號在哪」被問了三次，代表下一位新人也會問。寫進 第 7 課的交接文件或 README，下次直接給連結。
  • 讓 onboarding 本身被改進：每位新人第一週結束時問兩個問題：「哪裡最卡？」「文件哪裡跟實際不一樣？」答案就是下一版 onboarding 的修改清單。
  • 建立安全的提問環境：你自己也公開問問題、承認不知道。新人看到資深的人也會問，才敢在卡住 30 分鐘時就開口，而不是自己默默卡兩天。

練習

練習 1～4 是寫函式或填資料，起始程式已經宣告好型別。不能用 Date.now() 或 Math.random()。

練習 1：填 plan，排出小林第一週的 onboarding 計畫。檢查規則：id 不重複、總共不超過 15 項；每項 needs 裡的 id 都要存在，而且被依賴的項在更早的天，或同一天但在陣列中排在前面；第 1 天要有 setup；至少一項 pair；至少一項 ship，第一個 ship（天數最小、同一天取陣列中較前面的）在第 3 天以前，而且它的依賴鏈上（直接或間接）有 setup 與 pair；有 grants: 'prod-readonly' 的那一項，依賴鏈上要有 training，而且天數晚於第一個 ship。

練習 2：寫 lintFeedback(f)，依下列順序回傳找到的問題代碼：'no-situation-anchor'：situation 裡沒有任何一種時間或事件錨點（YYYY-MM-DD 或 M/D 日期、「週一～週日」或「星期一～星期日」、「昨天」「今天」「上週」、#數字 的 PR 編號）；'label-not-behavior'：behavior 含評價詞 LABELS 任一個；'no-impact'：impact 去掉前後空白後是空的；'request-not-actionable'：request 去掉前後空白後不是以 VERBS 任一個開頭，或含 VAGUE 任一個。再把 original 的三則改寫成 rewritten（順序對應），三則 lint 都要是空陣列，而且 behavior 保留原本的主題：第一則提到 migration、第二則提到「測試」、第三則提到「卡住」。

練習 3：寫 shapeReview(drafts)，把上面那份 PR 的 14 則草稿整理成要送出的意見。規則：同一個 pattern 合併成一則：label、why（取 rationale）、ref（取 link）都取該 pattern 的第一則；lines 由小到大、不重複；任一則 blocking 就是 blocking，但 nitpick 一律不是 blocking。合併後 nitpick 超過 3 則時，只保留 lines[0] 最小的 3 則（同一行時保留先出現的），並在最後加一則 { lines: [], label: 'question', blocking: false, why: ONE_ON_ONE, ref: '' }。合併後沒有任何 praise 時，用第一則 good 不是空字串的草稿產生 { lines: [它的 line], label: 'praise', blocking: false, why: 它的 good, ref: '' }。輸出依 lines[0] 由小到大排序（同一行時維持先出現的順序；產生的 praise 算在所有合併意見之後出現），加上的 question 永遠放最後。

練習 4：寫 supportFor(person, taskType, history)，決定這次給多少支援。只看 history 裡這個人做這類任務的紀錄（date 是 'YYYY-MM-DD'，陣列沒有排序）：0 次 → 'demo'；1 次 → 'together'；2 次以上時看日期最晚的那一次：blockingIssues > 0 → 'review'，否則 → 'delegate'。years（年資）不影響結果。

練習 5：新人第一週最好的第一個任務是？

✓ 第一個任務的目的是走完一次交付流程、建立信心，所以要小、風險低、但流程完整。重寫結帳模組太大太危險，一週都不會有完成感；讀完整個 codebase 沒有終點，也沒有實際練到流程；值夜班需要他還沒有的系統知識與正式環境權限。

練習 6：哪一則是可以執行的回饋？

✓ c 有具體情境（週二、#57）、觀察到的行為、影響與下一步。a、b 是對人的評價，對方不知道指的是哪件事、要改什麼；d 是空泛的鼓勵，沒有可以執行的動作。

練習 7：新人的 PR 有 12 處同樣的命名問題，資深的處理方式是？

✓ 合併成一則讓重點清楚，也教到背後的規則。12 則會淹沒真正重要的意見；直接幫他改，他下次還是不知道慣例（修好 PR 是作者的責任）；不提，問題會一直出現在之後的 PR 裡。

練習 8：小林在今天的站立會議上，說他的 PR「應該沒問題」，但你知道裡面的 migration 沒有回滾腳本。什麼時候、怎麼說最好？

✓ 改進的回饋私下、及時說，並用情境、行為、影響、請求的結構。當眾指出會讓他防衛，焦點從問題變成面子；等到考核，他已經用錯的方式做了好幾個月；不點名的提醒內容空泛（「要小心」不是動作），他也不一定知道在說他。

常見錯誤

  • 第一天就給新人正式環境的權限：權限隨需要逐步開通，正式環境唯讀權限要等資安訓練完成、而且他已經在正常流程下上線過一次；寫入權限不在第一週。
  • 新人的第一個任務太大：一週都沒有完成的感覺，你也看不出他卡在哪。第一個任務要能在第 3 天前上線，重點是走完流程。
  • 回饋是評價而不是行為：「粗心」「態度不好」「總是」讓對方防衛，也不知道要改什麼。說哪一次、做了什麼、造成什麼、下次怎麼做。
  • review 留下幾十則 nitpick：真正重要的 blocking 意見被淹沒。同一種問題合併成一則，nitpick 最多 3 則，其餘私下一起看。
  • blocking 意見只說「改掉」：新人改了這一行，下次在別處再犯。說明為什麼，附上參考。
  • 只指出問題，從不說哪裡做得好：對方不知道哪些習慣該保留。每次 review 至少一則具體的稱讚，並說明好在哪裡。
  • 用年資決定放不放手：資深的新成員一樣不熟這套系統的業務規則。看他做過這類任務幾次、最近一次的結果。

小結

  • onboarding 是有依賴順序的計畫：帳號與環境 → 讀交接文件 → 跟 buddy 配對 → good first issue 上線，每一步寫出完成的樣子；第 3 天前交付一個小改動。
  • 權限照最小權限逐步開通：正式環境只開唯讀，而且在資安訓練與第一次上線之後。
  • 可執行的回饋用 SBI 加上請求：情境有時間或 PR 編號、行為不貼標籤、說出影響、請求是可以執行的動作；私下說、及時說，好的也要說。
  • 在 review 裡教人：blocking 意見說明為什麼並附參考，同一種問題合併成一則，nitpick 最多 3 則，用問題引導，每次至少一則具體的稱讚。
  • 支援程度從示範、一起做、他做你 review 到放手並事後回顧，依對這件任務的熟悉度決定，不看年資。
  • 你的產出包含團隊的產出：重複回答的問題寫成文件，讓新人改進 onboarding 文件。
