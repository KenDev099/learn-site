階段 4：期末專題 · 第 10 課

期末專題：接手咖啡店舊專案的一個需求變更，從釐清需求到交付

2026 年 2 月 11 日（三），店長在群組丟了一句：「會員生日當月，飲料打 85 折，點數加倍。3 月 1 日開始。」要改的是第 5、6 課那份三年前外包寫的結帳程式：沒有測試、註解跟程式對不上、星期幾和時區都藏在裡面。這句話聽起來半天就能做完，實際上它碰到了金額、點數、時間、舊程式和上線，每一個都可能在 3 月 1 日凌晨出事。

這一課是期末專題。你會把前九課的方法依序用在同一個需求變更（change request）上：需求變更是對既有系統行為的修改要求，跟從零做新功能不同的地方是，你必須同時保證「該變的變了」和「不該變的沒變」。專題分成六步，每一步都留下可以交給別人檢查的產出，下一步拿上一步的產出繼續做。練習 1～6 就是這六步，判分方式跟前面各課相同。

這課的路線：
  1. 專題的六個步驟：每一步產出什麼、交給下一步什麼，為什麼順序不能跳。
  2. 步驟 1～3：把店長的一句話拆成規則與待確認問題，寫成可執行的驗收條件，再估時程、列風險。
  3. 步驟 4～5：在沒有測試的結帳程式上，先用特徵測試鎖住舊行為、重構，再加生日規則，確保「不該變的沒變」。
  4. 步驟 6：用功能旗標先部署、3 月 1 日再照操作手冊逐步打開，並寫一份給店長的紅黃綠回報。
  5. 回顧：真實工作裡最常被跳過的步驟，跳過的代價是什麼。
這課會用到：
  • 第 1 課與第 2 課：把一句話拆成有編號的業務規則、用八個類別找例外情境，再把規則寫成能抓到錯誤實作的驗收條件。
  • 第 3 課與第 4 課：工作拆解與 PERT 區間；每一項都有負責人、觸發條件、因應的風險表，以及由規則決定的紅黃綠燈號。
  • 第 5 課與第 6 課：先用實驗確認舊程式實際怎麼做，再用特徵測試鎖住、用變異測試確認測試有效，加時間接縫，重構與改需求分開提交。
  • 第 7 課的操作手冊：每一步是 check／action／verify／rollback／escalate 其中一種，失敗時照 onFail 處理，可以用模擬器演練；這課的格式多了一種步驟，會完整寫出來。

專題的六個步驟

先看全貌。每一步的產出都是有型別的資料或程式，不是「心裡有數」：

順序有理由：沒釐清就寫驗收條件，條件會照著你的猜測寫；沒有驗收條件就估計，不知道「做完」長什麼樣；沒鎖住舊行為就改程式，改壞了也不知道。真實工作裡常常有人壓時程要你跳步，這課最後一節會整理跳過每一步的代價。

步驟 1：釐清，從一句話到規則與問題

先用第 1 課的方法拆。店長那句話裡有幾條獨立的業務規則，各自編號，之後的驗收條件、程式註解、問題都用編號指回來：

編號規則目前不清楚的地方
b1會員在生日當月結帳才適用「當月」用哪個時區？2/29 生日？沒填生日？
b2飲料打 85 折哪些算飲料？每項打折還是整筆打折？怎麼取整？
b3點數加倍依折扣前還是折扣後的金額？退款怎麼扣回？
b4跟既有優惠的關係（店長沒提，但舊程式有滿額 9 折、會員 95 折、可頌買二送一）能不能疊加？滿額門檻用哪個金額？

b4 是你從舊程式讀出來的，店長根本不會想到。這是接手舊系統時釐清的重點：新規則一定會跟舊規則相遇，交會的地方要主動問。

接著用 Example Mapping 的綠卡，每條規則至少寫兩個具體例子，一個成立、一個不成立，邊界才看得出來。再用第 1 課的八個類別（邊界、退款、折扣、重複、失敗、時間、身分、缺資料）逐一掃過，找例外情境。這次有兩個跟時間有關的坑，先執行看看：

第一個坑：3 月生日的會員在 3/1 凌晨結帳，用 UTC 判斷還是 2 月，不會打折；反過來，2 月生日的會員在同一個時間結帳，UTC 還是 2 月，反而拿到不該有的折扣。程式裡先把時間加 8 小時、再用 getUTCMonth() 這類 getUTC* 方法讀，是因為 getMonth()、getDay() 讀的是執行環境的時區：你的電腦設在台北，測試全過；部署到時區是 UTC 的伺服器，結果就變了。台灣沒有日光節約時間，固定加 8 小時是正確的。第二個坑：Date.UTC 遇到不存在的日期會往後進位，這是 JavaScript 規格定義的行為，不會丟錯。如果有人寫「把生日換成今年的日期再比月份」，2/29 生日的會員在非閏年的 2 月拿不到優惠，3 月卻拿到了。這兩個坑都不是寫程式的人粗心，而是規則沒講清楚：「當月」是誰的當月？2/29 的人在非閏年算哪個月？

這些問題整理好，照第 1 課的格式（問句、附上選項與影響、期限）送給店長。店長回覆了，這份回覆就是後面每一步的規格：

店長回覆（2026-02-12）：
1. 「當月」以台北時間判斷。2/29 生日的會員，非閏年一樣算 2 月。沒填生日的不適用。
2. 飲料是美式、拿鐵、卡布奇諾、伯爵紅茶；可頌、起司蛋糕不打折。
   每一項飲料的小計（單價 × 數量）各自打 85 折後四捨五入到元。
3. 生日折扣可以跟原本的優惠疊加：先算生日折扣，再照原本的方式扣可頌、套滿額 9 折與會員 95 折，最後四捨五入。
   滿額 9 折的門檻照舊判斷，用「沒有生日折扣時」的金額，不能因為打了生日折扣反而失去滿額優惠。

練習 1 要你把規則、例子和例外情境寫成資料。

步驟 2～3：驗收條件、估計與風險

店長的回覆是文字，驗收條件把它變成可以執行的例子。格式跟第 2 課一樣是 Given／Then，只是 Given 變成「生日、結帳時間、是不是會員、購物車」，Then 是應付金額與點數。條件好不好，用同一個方法判斷：拿去跑正確的實作要全部通過，跑每一個有 bug 的實作至少有一條失敗。

手算一條給你看。生日 3 月的會員在 3/4 買一杯拿鐵：

  1. b2：拿鐵 110 × 85 / 100 = 93.5，四捨五入成 94。
  2. 可頌優惠：沒有可頌，不扣。滿額門檻用沒有生日折扣時的金額 110，沒超過 500，不打 9 折。
  3. 會員 95 折：94 × 0.95 = 89.3，四捨五入成 89 元。
  4. b3：89 / 50 = 1.78，四捨五入成 2 點，再乘 2，得 4 點。

寫成條件，再拿兩個實作跑跑看：

只有第一條的話，兩個實作都通過，條件抓不到時區的 bug。加上「台北 3/1 00:30」這一條，UTC 版本就失敗了。每一個例外情境都要變成至少一條條件，這是練習 2 的重點。

有了條件，才知道「做完」包含什麼，接著照第 3 課拆工作、估三點、算 PERT 區間。這次的拆解跟做新功能不一樣的地方是：讀舊程式、寫特徵測試、重構都要列成工作項目並估進去。不列，它們還是要做，只是變成「為什麼延期」的理由。風險表照第 4 課：每一筆都要有負責人、觸發條件和因應做法；這次最大的未知數是舊程式，至少要有一筆風險的觸發條件跟它有關。

💡 實務上：碰到舊程式，先要半天探查再給時程
PM 或店長問「這要多久」時，如果要改的是沒看過的舊程式，可以回：「給我半天看結帳程式，明天中午給你一個區間。」這就是第 3 課的 spike（有時間上限的探查），讀舊程式（第 5 課）正好拿來當探查的內容；看懂範圍再估重構和特徵測試，會準很多。時間上限要守住：半天看不完，這件事本身就是一筆風險，直接寫進風險表回報，不要默默看三天。改的是你熟悉的程式，就不必多這一步，直接估。

步驟 4～5：鎖住舊行為，先重構，再加規則

這是這次要改的 legacyCheckout。它跟第 5 課的 priceCart、awardPoints 是同一段邏輯，前人已經照第 6 課的方法加上了時間接縫 now，星期幾從台北時間算：

// 舊結帳程式（2023 年外包版）。第 6 課的方法已經替它加上時間接縫 now
function legacyCheckout(input: CheckoutInput, now: () => number): Result {
  const taipei = new Date(now() + 8 * 60 * 60 * 1000)   // 台北時間 = UTC + 8
  let weekday = taipei.getUTCDay()
  if (weekday === 0) weekday = 7                        // 1＝週一 … 7＝週日
  let subtotal = 0
  for (const i of input.items) subtotal += PRICES[i.productId] * i.qty
  let amount = subtotal
  // 可頌買二送一，限平日
  let croissants = 0
  for (const i of input.items) if (i.productId === 5) croissants += i.qty
  if (croissants >= 3) {
    if (weekday <= 5) amount -= Math.floor(croissants / 3) * PRICES[5]
  }
  // 滿 500 打 9 折
  if (amount > 500) amount = amount * 0.9
  // 會員 95 折
  if (input.memberId !== null) amount = amount * 0.95
  const total = Math.round(amount)
  // 會員每滿 50 元 1 點
  const points = input.memberId === null ? 0 : Math.round(total / 50)
  return { total, points }
}

生日規則要插進這段程式的中間：打折要在扣可頌之前、滿額門檻要用沒打生日折扣的金額、點數要乘 2。每一處都碰到舊行為。所以動手前先做第 6 課的三件事：

  1. 特徵測試：每個分支與邊界兩側挑一個輸入，記錄實際輸出。這份程式的分支有：可頌 3 個、4 個、6 個；平日和週末；台北和 UTC 的星期幾不同的凌晨；剛好 500 元；扣可頌之前超過 500、扣完沒超過；會員與非會員；四捨五入在 .5 上；點數在 .5 上；空購物車。
  2. 變異測試：用變異體確認測試真的抓得到改動。練習 4 的隱藏測試有 12 個變異體，例如「滿額門檻改成 >= 500」「星期幾改用 UTC」「空購物車改成丟錯」。
  3. 分開提交：測試、重構、新規則各自一個 PR。

重構時最容易不小心改到行為的，是計算的順序。乘法可以交換順序，但「滿額門檻」是一個判斷：先打會員 95 折，金額變小，門檻的結果就可能不同。下面是一個「看起來更整齊」的重構：用差異測試（第 6 課：大量固定種子的輸入，比對新舊版本）跑一次：

只有「會員、原價剛好超過 500 一點點」的訂單會不同，人工測幾筆很可能都沒碰到；差異測試幾秒鐘就找出來。這也說明為什麼「先重構、再加規則」：重構 PR 裡差異測試要是 0 筆不同，特徵測試的預期值一條都不改；加規則的 PR 裡，只有生日訂單的結果改變。兩件事混在一起，非生日訂單出現 1 元差異時，你分不出是重構弄壞的，還是新規則本來就該這樣。

三個提交的內容與 review 時看什麼：

提交內容reviewer 檢查
1. 鎖住行為只加特徵測試，程式不動案例在舊程式上全過；變異測試沒有存活的變異體
2. 重構拆成具名函式（台北時間、星期幾、可頌優惠…），行為不變特徵測試一條都沒改；差異測試 0 筆不同
3. 生日規則加 b1～b4，包在功能旗標後面；驗收條件變成測試驗收條件全過；非生日訂單的特徵測試仍然全過

第 3 個提交裡的功能旗標，實際程式會長這樣（isEnabled 是系統設計課第 19 課寫過的穩定分桶）：const birthday = isMember && isBirthdayMonth(...) && isEnabled('birthday-promo', memberId)。旗標關著的時候，新程式的行為跟舊程式完全相同，所以可以先部署、再慢慢打開。練習 5 為了專注在規則本身，省略旗標這個參數。

時間一律從 now 參數拿，不要在新程式裡寫 Date.now()。寫了，測試就沒辦法固定在「台北 3/1 00:30」這種時間點，時區的 bug 只會在真的 3 月 1 日凌晨出現。

步驟 6：用功能旗標上線、回報進度

前五步讓程式準備好了，最後一步是安全地上線。功能旗標（feature flag）是不重新部署就能開關功能的設定（系統設計課第 19 課、DevOps 課第 16 課）。它讓「部署」和「發布」分開：程式 2/26 就部署上去，旗標關著；3/1 再依操作手冊逐步打開。放量的意思是旗標不是只有開和關，而是「對百分之幾的會員開」：先 10%，觀察錯誤率沒問題，再 50%、100%。出問題時把旗標設回 0，幾秒鐘就止血，不用等重新部署。

操作手冊照第 7 課的做法寫成步驟資料，再用模擬器跑幾個情境，確認它在正常、出錯、重跑時都會做對的事。這次的步驟格式：

kind指令執行結果
checkexpect：讀一個指標跟門檻比較通過就下一步；沒過跳到 onFail，沒寫 onFail 就中止（aborted）
actionset-flag：把旗標設成某個百分比下一步一定要是檢查錯誤率的 verify
verifyexpect跟 check 一樣，但一定要有 onFail：動作之後的驗證沒過，要知道去哪
rollbackset-flag回滾：把旗標設回 0。唯一可以把旗標調降的步驟
escalatepage-oncall呼叫值班的人，手冊結束（escalated）
finishnotify-owner通知店長完成，手冊結束（done）。回滾的步驟放在它後面，正常流程不會走到

跟第 7 課的模擬器比，有兩點不同：多了 finish；而且正常流程走到 rollback 不會自動結束，會照樣執行。所以正常流程的終點要用 finish 明確寫出來，否則走完放量會接著執行回滾，把旗標關掉。

指標有三個：checkoutErrorRate（結帳錯誤率，%；平常約 0.2）、birthdayOrders（套用生日優惠的訂單數）、flagPercent（旗標目前的百分比）。

三個情境要想清楚：

  • 正常：10% → 驗證 → 50% → 驗證 → 100% → 驗證有生日訂單 → 通知店長。每次調升最多 50 個百分點，從 0 直接開到 100 等於沒有放量。
  • 10% 時錯誤率上升：先止血（旗標設回 0），驗證錯誤率恢復，再呼叫值班的人調查。順序反了，等人的這段時間顧客一直結帳失敗。
  • 重跑：上次放到 50% 時網路斷了，你重新從頭照手冊做。如果第一步是「設成 10%」，50% 裡已經拿到優惠的顧客會突然沒有，櫃檯會被問「剛剛不是打折嗎」。做法是每次放量前先 check flagPercent < 目標，已經達到就用 onFail 跳過，讓手冊可以安全地重跑（這跟系統設計課第 9 課的冪等是同一個想法）。
💡 實務上：上線也要通知不寫程式的人
放量的時間要選有人盯得住的時段：2026 年 3 月 1 日是星期日，要先排好那天誰照手冊放量、誰值班，出事時找得到人回滾；週五晚上或連假前開新功能，通常也會被資深同事擋下。上線前也要通知會被影響的人：櫃檯要知道收據上的折扣長什麼樣、顧客問「為什麼我沒打折」怎麼回答（例如沒填生日、可頌不打折）；會計要知道從哪天起報表會出現生日折扣。這些不寫在程式裡，但漏掉的話，第一天的客訴會先打到店長那裡。

上線前還有一件事：回報。2/18 你的 P85 預測完成日是 3/3，比 2/27 的期限晚，原因是等會計確認折扣怎麼記帳等了兩天。照第 4 課的規則，這是紅燈：預測晚於期限就是紅燈，不管你覺得「應該趕得上」。紅燈的回報一定要附上需要誰在什麼時候做什麼決定，而且決定的期限要來得及調整，例如請店長在 2/20 前決定「3 月生日優惠延到 3/4 開始」或「2/27 先上線、點數加倍晚一週」。練習 6 會把操作手冊和這份回報一起寫出來。

回顧：最常被跳過的步驟

六步做完，對照前九課。真實工作裡每一步都有人跳過，理由通常是「趕時間」；下表是跳過的代價：

步驟出處常見的跳過方式代價
釐清第 1 課聽完就開始寫時區、2/29 在 3/1 凌晨被顧客發現；重做的成本比問一句高得多
驗收條件第 2 課「做完給店長看」雙方對「做完」的認知不同，上線前一天才吵
估計與風險第 3、4 課只給一個數字、不列風險延期時只能道歉，沒有選項可以談
鎖住舊行為第 5、6 課「改一點點而已」非生日訂單的金額悄悄變了，月底會計對帳才發現
分開提交第 6 課重構和新規則一起送出問題分不出原因，只能整包回滾
操作手冊與回報第 4、7 課一次全開、做完才報出事時臨場想怎麼回滾；店長最後一天才知道會延

工作要交給別人時，同一份產出也是交接文件（第 7 課）：規則與店長的回覆、驗收條件、特徵測試、操作手冊，下一個人不用問你就能接手。帶新人時（第 8 課），這六步也是很好的第一個任務：小、有明確的完成標準、每一步都能給具體的回饋。用 AI 加速時（第 9 課），它可以幫你起草特徵測試的案例或重構，但驗收條件來自店長的回覆，不是來自 AI 寫的實作；差異測試與變異測試是你驗證它的工具。

💡 實務上：六步的份量看風險調整
不是每個需求變更都要把六步做滿。改按鈕文案、調整顏色，釐清一句、PR 附截圖就夠了；碰到金額、點數、權限、時間或舊程式，像這次的生日優惠，才值得每一步都留下產出。資深工程師拿到需求會先問：「做錯了，誰會發現？要多久才發現？」顧客當場就會發現的，風險反而小；要等月底對帳才發現的，就要鎖住舊行為、逐步放量。這個判斷也是跟主管談時程的依據：說得出為什麼這個需求要多花兩天，比較容易被接受。

練習

練習 1～6 依序是專題的六個步驟。每題開頭先寫「做完的樣子」，再拆成編號的小步驟，每一步標出要看哪一節；用到前面課的格式，直接附在題目裡（點開灰色的「格式速查」「提示」），不用翻回去。建議一次做一步、按一次「執行」看輸出，全部做完再按「檢查答案」。

共用的資料：商品 id 1 美式咖啡 80、2 拿鐵 110、3 卡布奇諾 110、4 伯爵紅茶 90（以上是飲料）、5 可頌 70、6 起司蛋糕 120。時間一律寫成台北時間加時區，例如 '2026-03-04T15:00+08:00'；程式不能用 Date.now()，時間從參數來。日曆：2026-11-04 週三、11-07 週六、11-08 週日、11-09 週一；2026-03-01 週日、03-04 週三。

結帳的計算順序（店長回覆寫成步驟，練習 2、4、5 都照這個算）：
  1. 判斷有沒有生日優惠：會員、birthday 不是 null、生日的月份（'1990-03-15' 的 03）等於台北時間結帳的月份。2/29 生日一律算 2 月。
  2. 每一項的小計 = 單價 × 數量。有生日優惠時，飲料（id 1～4）的小計 × 85 / 100 後 Math.round；食物不變。
  3. 台北時間週一到週五，可頌每 3 個扣一個的錢：Math.floor(可頌數 / 3) × 70。
  4. 滿額：用沒有生日折扣時的金額（原價小計扣掉可頌優惠）判斷，> 500 就 × 0.9。
  5. 會員再 × 0.95，最後 Math.round 得到 total。
  6. 點數：非會員 0；會員 Math.round(total / 50)，有生日優惠再 × 2。
沒有生日優惠時，第 2 步什麼都不打折，結果就是舊程式 legacyCheckout。

練習 1（步驟 1：釐清）：填 rules 與 edgeCases。

做完的樣子：按執行印出 b1～b4 四條規則、每條「2 個例子」以上，最後一行「例外情境 6 個」以上，而且下面表格裡 5 個一定要問的情境都在。這題是站在店長還沒回覆的時間點，不知道答案的就寫成問題。

  1. 規則（看「步驟 1」一節的 b1～b4 表）：起始程式已有 b1，照樣補 b2 飲料 85 折、b3 點數加倍、b4 與既有折扣的關係，各剛好一條，text 一句話（4～80 字）。
  2. 例子（Example Mapping 的綠卡）：每條至少 2 個，最好一個成立、一個不成立，同一條的 given 不能重複。答案還不知道的，expected 照實寫「要問：…」，b4 多半是這種。
  3. 5 個一定要問的例外情境：category、ruleId 要完全對上，scenario 或 question 要寫到右欄的字眼：
    情境category＋ruleId要寫到
    台北 3/1 凌晨，UTC 還是 2 月time＋b1UTC、時區或台北
    2/29 生日，今年不是閏年boundary＋b12/29 或閏年
    生日折扣跟滿額 9 折疊加discount＋b4滿額、500 或 9 折
    退款時加倍的點數怎麼扣回refund＋b3退（退款、退貨）
    會員沒填生日missing-data＋b1沒填、沒有生日、缺或空
  4. 再補到至少 6 個：用八個類別對著 b1～b4 再掃一次，挑一個上面沒有的（例如非會員說今天生日、同一天結帳很多筆）。
格式速查：EdgeCase 的欄位與八個類別（出自第 1 課「例外情境清單：八個類別逐一問」一節）
  • scenario：具體的情況，6～80 字，彼此不重複。
  • question：要問店長的問句，5～80 字，以「？」結尾，彼此不重複。能用是／否或一個數字回答的最好，例如「退款時要扣回加倍後的點數，還是只扣原本的點數？」。
  • category 只能是這八個值：boundary 邊界值（剛好等於門檻、0、最大值）、refund 退款、discount 折扣與優惠疊加、duplicate 重複送出或重複享用、failure 離線與失敗、time 時間（跨日、跨月、時區）、identity 身分（非會員、員工、改資料）、missing-data 資料缺漏（欄位沒填）。

練習 2（步驟 2：驗收條件）：依店長的回覆寫 criteria。

做完的樣子：最多 14 條、name 不重複；每一條在正確的實作上都通過，下面 6 個有 bug 的實作，每一個都至少被一條條件抓到（算出不同的金額或點數）。

  1. 先寫課文算過的那一條（「步驟 2～3」一節的手算）：生日 '1990-03-15' 的會員在 '2026-03-04T15:00+08:00' 買一杯拿鐵，then 是 89 元、4 點。格式照起始程式的 Criterion：now 要帶時區，birthday 是 'YYYY-MM-DD' 或 null，購物車至少一個品項。
  2. 每個 bug 設計一條抓得到它的條件：問自己「什麼樣的 Given，對的實作和這個 bug 會算出不同的結果？」
    • 用 UTC 判斷月份
    • 2/29 生日在非閏年不算（把生日放進今年的日期，2026 年的 2/29 會變成 3/1）
    • 食物也打 85 折
    • 滿額門檻改用生日折扣後的金額判斷
    • 點數沒有加倍
    • 非會員也打折
  3. 手算預期值：照練習一開頭的「結帳的計算順序」一步一步算，不要拿自己寫的程式算（程式寫錯，條件就跟著錯）。
  4. 按執行對照：非生日的條件（非會員、非生日月、沒填生日），你的預期要跟印出的「舊程式」相同；生日的條件跟舊程式不同是正常的。
提示：每個 bug 用什麼 Given 抓
  • UTC：3 月生日，台北 3/1 00:00～07:59 結帳（UTC 還是 2/28）。
  • 2/29：生日 '2000-02-29'，在 2026 年 2 月結帳。
  • 食物：生日月的購物車裡放可頌或起司蛋糕。
  • 滿額門檻：原價超過 500、打完生日折扣後不到 500 的購物車，例如 5 杯拿鐵（原價 550）。
  • 點數沒加倍：任何一條生日月、會得到點數的會員條件都抓得到。
  • 非會員：isMember: false，但生日在當月。

練習 3（步驟 3：估計與風險）：填 tasks、estimate、risks。

做完的樣子：按執行印出一個 low 小於 high 的區間，下面每一筆風險都印出分數和負責人。

  1. 拆工作 tasks（「步驟 2～3」一節最後一段）：至少 6 項，把讀舊程式、特徵測試、重構都列進去。kind 至少要有 code、test、review、deploy 四種，而且有一項 kind: 'test' 的 title 寫到「特徵」。
  2. 估三點：每一項 0 < a ≤ m ≤ b，m 最多 2（超過就再拆）；至少一半的工作 b > m（承認不確定性）。
  3. 算區間：直接寫 const estimate = pert(tasks)，起始程式已經附了 pert，不要手填數字。
  4. 列風險 risks：至少 3 筆，id 不重複；其中至少一筆的 trigger 寫到「舊程式」或 legacy（這次最大的未知數）。
格式速查：工作與風險的欄位（出自第 3 課「拆解：每一項不超過兩天」、第 4 課「風險表：每一項都要能行動」）
  • Task：id 不重複；title 2～60 字；a、m、b 是工作天（一個人專心做的一天）。kind 的值：code 寫程式、test 測試、review code review 與修改、migration 資料表變更、deploy 部署與上線後驗證、docs 文件、waiting 等別人、spike 有時間上限的探查（例如花半天讀舊程式）。
  • Risk：probability、impact 是 1～5 的整數（分數 = 兩者相乘）；owner 一個人的名字；trigger 看到什麼訊號就代表風險正在發生，最好有日期；mitigation 現在就做什麼來降低機率或影響；dueDate 是 'YYYY-MM-DD' 格式的檢查日。owner、trigger、mitigation 都不能是空白。
  • 風險的例子：{ id: 'accounting', title: '會計還沒確認生日折扣怎麼記帳', probability: 3, impact: 4, owner: '你', trigger: '2/16 前會計還沒回覆', mitigation: '先照一般折扣記帳寫，報表欄位留到確認後再調整', dueDate: '2026-02-16' }

練習 4（步驟 4：鎖住舊行為）：替 legacyCheckout 寫特徵測試 lockCases。

做完的樣子：最多 15 個案例、name 不重複，按執行每一行都是 ✓；隱藏測試的 12 個變異體（把舊程式改壞一處的版本），每一個都至少被一個案例抓到。

  1. 列分支：照「步驟 4～5」一節第 1 點的清單，每個分支或邊界寫一個案例，name 寫它鎖住什麼（例如「剛好 500 元不打 9 折」）。下面的提示列出每個變異體改了哪裡、要什麼樣的輸入。
  2. 先空著預期值、按執行：expected 先填 { total: 0, points: 0 }，按執行，把印出的「實際」抄進 expected。特徵測試記錄的是程式實際怎麼做，不是註解說的或你覺得對的（第 6 課「特徵測試：手選案例，記錄實際輸出」）。
  3. 時間 at：照練習一開頭的日曆挑平日、週六、週日；要讓台北和 UTC 的星期幾不同，挑台北凌晨 0～8 點。
提示：12 個變異體與抓它的輸入

滿額門檻 > 500 改成 >= 500金額剛好 500 元

可頌優惠不看星期幾週日買 3 個可頌

練習 5（步驟 5：實作）：改寫 checkout(input, now)，先重構、再加生日規則。

做完的樣子：按執行，前兩筆（非生日訂單）「新」和「舊」完全相同，第三筆生日月一杯拿鐵是 89 元、4 點。

  1. 重構，行為不變（「步驟 4～5」一節的提交 2）：把 checkout 拆出幾個具名的小函式或變數，例如台北時間、星期幾、可頌優惠。拆完按執行，三筆的「新」都要跟「舊」相同（生日規則還沒加）。
  2. 判斷生日月（計算順序第 1 步）：會員、birthday 不是 null、生日的月份等於台北時間的月份。月份直接從字串取，不要把生日組成今年的日期（2/29 會進位成 3/1，「步驟 1」一節的坑 2）。
  3. 飲料打折（第 2 步）：迴圈裡另外累加一個「要付的小計」，飲料（id 1～4）在生日月 Math.round(小計 × 85 / 100)；原價小計照舊累加，留給滿額門檻用。
  4. 扣可頌、滿額、會員折扣（第 3～5 步）：從「要付的小計」扣可頌優惠再打折；滿額門檻用「原價小計 − 可頌優惠」判斷。
  5. 點數加倍（第 6 步）：生日月的會員 Math.round(total / 50) × 2。按執行，第三筆應該是 89 元、4 點。
提示：取月份的寫法

台北時間的月份：new Date(now() + 8 * 60 * 60 * 1000).getUTCMonth() + 1（getUTCMonth() 從 0 起算）。生日的月份：Number(input.birthday.slice(5, 7))。不要用 getMonth()：它讀的是執行環境的時區，判分時會直接報錯。

判分：2,000 筆固定種子的隨機訂單，沒有生日優惠的（非會員、非生日月、沒填生日）要跟舊程式完全相同，生日月的要跟參考實作相同；另外跑一組跟練習 2 同類的條件。不能呼叫 Date.now()，也不能用 getMonth()、getDay() 這類讀執行環境時區的方法（用 getUTC*）；不要修改 legacyCheckout（判分用的是隱藏的舊程式副本）。

練習 6（步驟 6：上線）：填 releaseRunbook（放量的操作手冊）與 statusUpdate（給店長的回報）。起始程式附了模擬器 simulate，按執行會跑三個情境並印出每一步。

做完的樣子：按執行，三個情境的第一行分別是 A 正常 → done 旗標 100% []、B 10% 時錯誤率上升 → escalated 旗標 0% []、C 重跑（旗標已經 50%） → done 旗標 100% []（最後的 [] 代表沒有格式問題），最後一行印出以「紅燈」「黃燈」或「綠燈」開頭的 headline。另外 A 的旗標要依序走過 10、50、100，B 只開到 10，C 不能調降旗標。

A. 操作手冊（步驟的 kind 與指令見「步驟 6」一節的表；這裡的模擬器跟第 7 課不同，走到 rollback 不會自動結束，正常流程的終點要寫 finish）

  1. 先讓情境 A 通過：照順序寫 設成 10% → 驗證錯誤率 → 設成 50% → 驗證 → 設成 100% → 驗證 → 驗證 birthdayOrders > 0 → finish。每個 set-flag 的下一步一定要是檢查 checkoutErrorRate 的 verify，每次最多調升 50 個百分點。
  2. 再讓情境 B 通過：在 finish 後面接失敗處理：rollback 把旗標設成 0 → verify 錯誤率恢復 → escalate。每個 verify 一定要有 onFail，放量的驗證沒過就跳到 rollback。
  3. 最後讓情境 C 通過（「步驟 6」一節的「重跑」）：每段放量前加一個 check flagPercent < 目標，已經達到就用 onFail 跳過這一段。全部最多 20 步。
格式速查：步驟的寫法與模擬器怎麼跑 
{ id: 'open-10', kind: 'action', command: { type: 'set-flag', flag: 'birthday-promo', percent: 10 } }
{ id: 'verify-10', kind: 'verify', command: { type: 'expect', metric: 'checkoutErrorRate', op: '<', value: 1 }, onFail: 'rollback' }
  • 從第一步依序執行。expect 成立就到下一步；不成立時，有 onFail 就跳到那個 id，沒有就中止（aborted）。
  • 執行到 page-oncall 結束（escalated）；執行到 notify-owner 或走完最後一步結束（done）。
  • 模擬的指標：checkoutErrorRate 平常是 0.2，情境 B 只要旗標大於 0 就是 3.5；birthdayOrders 旗標大於 0 時是 12，否則 0；flagPercent 是旗標目前的百分比。
  • rollback 的 percent 一定要是 0，而且它是唯一可以把旗標調降的步驟。
提示：情境 C 的跳法

旗標已經 50% 時：「flagPercent < 10」不成立 → onFail 跳到 50% 那一段的檢查；「flagPercent < 50」也不成立 → 跳到 100% 那一段的檢查；「flagPercent < 100」成立 → 設成 100%。100% 那一段的檢查不成立時（旗標已經 100%），跳到驗證 birthdayOrders 的那一步。

B. 狀態回報（第 4 課「紅黃綠：燈號由規則決定」「進度回報：第一句就是結論」；「步驟 6」一節最後一段就是這次的狀況）

  1. 決定燈號 status：用 project 的資料照規則判斷：forecastP85 晚於 deadline → 'red'；否則緩衝用掉超過一半（bufferUsedDays > bufferDays / 2），或有阻擋從 since 到 today 超過 2 天 → 'yellow'；否則 'green'。
  2. 寫 headline：以「紅燈」「黃燈」或「綠燈」開頭（跟 status 一致），寫出預測完成日 2026-03-03，最多 60 字。
  3. 寫 done、next：各至少一項，不能是空字串。
  4. 寫 asks：不是綠燈時至少一項 { who, decision, by }：需要誰、決定什麼、最晚哪天（'YYYY-MM-DD'，在今天 2026-02-18 到期限 2026-02-27 之間，晚了就來不及調整）。

練習 7：台北時間 3 月 1 日 00:30，生日 3 月的會員結帳，伺服器用 UTC 判斷月份。會發生什麼？

✓ b。台北是 UTC+8，凌晨 0～8 點的 UTC 日期是前一天，月初那幾個小時的月份也是上個月。店長說的「當月」是台北時間，所以要先換算再取月份。a 忽略了時差；c、d 都不會發生：程式照樣算出一個金額，只是錯的，這種 bug 沒有錯誤訊息，只有顧客抱怨。

練習 8：專題的實作步驟為什麼要先重構、再加生日規則，而且分成不同的提交？

✓ b。分開讓每一步都能被驗證：重構的驗證標準是「什麼都沒變」，加規則的驗證標準是「只有該變的變了」。混在一起時，非生日訂單出現差異，分不出是重構弄壞的還是規則本來就該這樣。a 只說了附帶的好處；c 省下的時間會在除錯時加倍還回去；d 不是事實。

練習 9：功能旗標放到 10% 時，結帳錯誤率從 0.2% 升到 3.5%。正確的第一步是？

✓ b。旗標的價值就是不用重新部署、幾秒鐘就能止血；先止血再調查。a 把影響擴大五倍；c 也能止血，但比關旗標慢得多，而且會連帶撤掉同一版的其他改動；d 讓顧客在你查原因的這段時間一直結帳失敗。

常見錯誤

  • 跳過釐清直接寫：時區和 2/29 在 3/1 凌晨才被顧客發現。新規則跟舊規則交會的地方（滿額門檻、會員折扣、可頌）要主動問，業務方不會想到。
  • 驗收條件只寫快樂路徑：「生日月買一杯拿鐵」抓不到任何時區或門檻的 bug。每個例外情境都要變成至少一條條件，並用有 bug 的實作確認抓得到。
  • 估計沒有列讀舊程式、特徵測試、重構：這些工作一樣要做，只是沒被估進去，最後變成延期的理由。
  • 沒有特徵測試就改舊程式：改壞了非生日訂單的金額，月底對帳才發現。先鎖住行為，用變異測試確認測試有效。
  • 重構與新規則混在同一個提交：出問題分不出原因，只能整包回滾。重構的 PR 測試一條都不改。
  • 新程式裡寫 Date.now()：測試沒辦法固定在月初凌晨這種時間點。時間從參數 now 來。
  • 上線一次開到 100%、沒有回滾步驟：出事時臨場想辦法。依操作手冊逐步放量，每一步之後驗證，失敗就關旗標。
  • 做完了才第一次回報、或報喜不報憂：預測晚於期限就是紅燈，附上需要誰在什麼時候做什麼決定。

小結

  • 需求變更要同時保證「該變的變了」和「不該變的沒變」；六個步驟依序是：釐清 → 驗收條件 → 估計與風險 → 鎖住舊行為 → 先重構再加規則 → 用功能旗標上線並回報。
  • 釐清時特別注意新規則跟舊規則交會的地方，以及時間：「當月」「今天」都要問是誰的時區。不阻擋的問題附上預設值先做。
  • 驗收條件拿去跑正確與有 bug 的實作；特徵測試拿去跑原程式與變異體。兩者都要「對的全過、錯的抓得到」。
  • 重構用差異測試證明 0 筆不同，再加規則；三個提交各自可以 review、可以回滾。
  • 功能旗標把部署和發布分開：逐步放量、每步驗證、出事關旗標；操作手冊要能安全地重跑。
  • 每一步的產出都是可以交給別人檢查的東西，合起來就是這次變更的交接文件。
