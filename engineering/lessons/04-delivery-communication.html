階段 1：從需求到交付：釐清、驗收、估計與溝通 · 第 4 課

交付溝通：進度回報、風險升級與範圍協商

會員集點預計 11/27（五）上線。店長已經印好海報、排好店員教育訓練。11/26（四）晚上，工程師傳訊息：「POS 那邊的 API 還沒好，大概還要兩天。」店長只剩一個選擇：把海報撕掉。如果這句話在 11/18 就說出來，店長還有好幾條路：先上一個櫃檯手動加點的版本、改海報日期、找 POS 廠商的業務施壓。壞消息本身沒變，變的是還剩多少選項。

這一課學的是開工之後的溝通：怎麼及早發現延誤、怎麼報告進度、時程不夠時怎麼談。

這課的路線：
  1. 壞消息越晚說，選項越少：同一個延誤，早一週說和前一天說，需求方手上剩下的選項差多少。
  2. 風險表、紅黃綠：怎麼把還沒發生的延誤列成每一項都能行動的清單，燈號怎麼由規則決定，不靠「應該趕得上」的感覺。
  3. 進度回報：第一句就寫燈號與預計完成日，忙碌的店長只讀一句也知道要不要介入。
  4. 範圍協商、升級：時程不夠時保留 Must、依價值取捨其他功能；超出你權限的問題，帶著選項找能決定的人，並說清楚要他在什麼時候前決定什麼。
這課會用到：
  • 第 2 課的 MoSCoW 與垂直切片：功能分成 Must／Should／Could／Won't，每一片都能單獨上線；它們是範圍協商時拿來增減的單位。
  • 第 3 課的 P50／P85 與前提：P85 是有 85% 的機會在這天前做完；前提變了，估計就要重算。
  • TypeScript 課第 15 課的字面值聯合：'green' | 'yellow' | 'red' 這種型別，值只能是列出來的其中一個。

壞消息越晚說，選項越少

延誤幾乎不會在最後一天才「突然」發生。POS 廠商的 API 晚交，通常在約定日前幾天就有跡象：測試帳號一直沒寄來、對方回信越來越慢。工程師沒說，多半是因為想「再拚一下也許趕得上」，或不想讓人失望。結果是需求方失去了調整的時間。

所以這課的重點不是「講話技巧」，而是三個機制：用風險表提早看到可能出事的地方；用規則決定燈號，讓延誤在變成事實前就被報出來；延誤確定時，帶著選項去找有權決定的人。

風險表：每一項都要能行動

風險（risk）是還沒發生、可能發生、發生了會影響交付的事。已經發生的叫問題（issue）。「唯一懂舊結帳程式的同事下週休假」是風險（還沒發生，可以先安排交接）；「POS 廠商今天通知 API 延後」是問題（已經發生，要處理）。分清楚的原因是處理方式不同：風險要事先準備，問題要立刻決定怎麼辦。

風險表（risk register）是把風險列成一張清單，每一項有這些欄位：

欄位寫什麼咖啡店的例子
機率（probability）1～5，5 是幾乎一定發生4
影響（impact）1～5，5 是上不了線5
負責人（owner）一個人的名字，負責盯這個風險你
觸發條件（trigger）看到什麼訊號，就代表風險正在發生、要啟動因應11/20 前還沒拿到 POS 測試環境帳號
因應（mitigation）現在就做什麼來降低機率或影響先做櫃檯手動加點的切片，API 晚到也能上線
檢查日（dueDate）最晚哪天要再看一次2026-11-20

排序用分數 = 機率 × 影響，分數高的先處理。這不是精確的計算，1～5 是大家討論出來的粗略值；它的用途是讓團隊對「先顧哪個」有共識，而不是每個人憑印象。同分時，檢查日早的先看，因為它最快需要行動。

三個欄位最常被省略，也最不能省略：

  • 負責人：沒有名字的風險，每個人都以為別人在看。寫「團隊」等於沒寫；空白字串也一樣。
  • 觸發條件：沒有觸發條件，風險會一直停在「有點擔心」，直到變成問題。觸發條件要是一個看得到的訊號，最好有日期。
  • 因應：只寫標題、不寫要做什麼，風險表就只是一張擔心清單。

💡 實務上：風險表不用另開系統，放在團隊每週會看的地方
實際工作中，風險表常是專案頁面（Notion、Confluence）裡的一張表，或 Jira 上標了「風險」的票，重點是每週回報前真的會被打開。兩三天就做完的小任務不需要正式的表，在票或 PR 說明寫一句「依賴會計確認入帳方式，11/19 沒回覆就先照 X 做」就夠了。接手專案時，資深工程師會先問：「現在最大的三個風險是什麼？誰在盯？」答不出來，代表還沒人在管。另一個常見的坑是表越寫越長、從來不關：已經解除的項目要關掉，表才會一直反映現況。

紅黃綠：燈號由規則決定

進度回報常用紅黃綠燈表示狀態。問題是燈號常常憑感覺：工程師覺得「應該趕得上」就報綠燈。這種外面綠、裡面紅的報告叫西瓜報告（watermelon reporting）：每週都是綠燈，最後一週突然變紅。需求方從來沒收到提早調整的訊號。

解法是把燈號寫成規則，讓資料決定，不讓心情決定。這門課用的規則：

條件燈號意思
預測完成日（第 3 課的 P85）晚於期限紅燈照現在的範圍與人力，大概做不完，需要有人做決定
沒有紅燈，但已用掉的緩衝（buffer）超過一半，或有阻擋（blocker）超過 2 天黃燈還能如期，但安全空間在變小，需要注意或協助
其他綠燈照計畫進行

緩衝是計畫裡為不確定性保留的時間。集點專案的 P85 預測是 11/23，期限是 11/27，中間的 4 天就是緩衝。用掉超過一半（3 天以上），代表剩下的不確定性只剩很少的空間可以吸收。

阻擋（blocker）是讓工作停下來、要等別人才能繼續的事，例如等會計回覆入帳規則。「超過 2 天」用日曆天算，等待天數是今天減掉開始等的那天：11/16 開始等，到 11/18 等了 2 天，還不算超過；到 11/19 等了 3 天，變黃燈。界線要寫清楚，否則每個人算出來的燈號不同。

紅燈不是指責，它的意思是「需要有人做決定」。資深工程師的價值不在於永遠綠燈，而在於燈號準：說綠燈就是真的綠，說黃燈時還來得及處理。信任來自預測準確，不是永遠準時。

進度回報：第一句就是結論

需求方很忙，常常只讀第一句。所以回報用 BLUF（bottom line up front，結論先行）的寫法：第一句是燈號與預計完成日，細節放後面。比較兩個版本：

✗ 本週完成了會員註冊的 API 與畫面，也處理了手機號碼格式的驗證。POS 廠商的 API 文件
  還沒收到，我們有先寄信詢問。下週會繼續做兌換功能……（第五句才提到可能延後）

✓ 黃燈：預計 2026-11-26 完成，仍在 11/27 期限內，但緩衝已用掉 3 天。
  本週完成：會員註冊、手機號碼驗證。
  下週計畫：兌換功能、櫃檯加點畫面。
  風險：POS 廠商 API 尚未交付（11/20 前沒拿到測試帳號就啟動手動加點方案）。
  需要決定：店長，11/20 前決定若 API 延後，是否先上櫃檯手動加點版本。

固定的五段：燈號＋預計完成日、本週完成、下週計畫、風險、需要誰做什麼決定、什麼時候之前。最後一段最常被漏掉，卻是黃燈、紅燈回報的重點：只說「有風險」，對方不知道要做什麼。「需要決定」要寫出人、決定的內容、期限；期限一定要在交付日之前，否則決定了也來不及。

同一個狀態，給不同的人寫法不同：

讀者他關心寫法
店長（需求方）能不能如期、客人看到什麼、要他決定什麼用功能描述（「櫃檯可以手動加點」），不講 API、migration
工程主管（tech lead）技術風險、要不要調人、會不會影響其他系統可以講技術細節：哪個 API、卡在哪、估計的前提

兩個版本的燈號與日期必須一樣。給老闆報綠燈、給主管報黃燈，等於兩份報告裡有一份在說謊。

💡 實務上：每天的站會也是結論先行
大部分團隊有每日站會（daily standup）或在 Slack 頻道貼文字進度。同樣的原則：先說「照計畫」或「卡住了，需要誰」，不要從昨天做了什麼開始流水帳。卡住的事要點名對方、說清楚需要他什麼，例如「@會計 兌換的入帳方式，我週四前需要答案」，而不是「還在等會計」。重要的決定不要只在私訊裡講，貼在專案頻道或票上，之後的人才找得到。新人最常犯的錯是卡住一兩天都不說，以為自己解決才算能幹；早點說出「我卡在 X」通常是讓主管最放心的事。

範圍協商：四個變數，品質不在桌上

時程不夠時，可以動的變數有四個：時間（延後上線）、範圍（少做一些）、資源（加人）、品質（少測試、跳過 review）。跟需求方討論要動哪個，叫範圍協商（scope negotiation）。

  • 品質不是選項：不寫測試、跳過 code review 省下的時間，會在上線後以 bug、事故、加班還回來，而且通常更多。集點算錯點數，要人工補點、跟客人道歉。工程師不應該把它放進選項裡讓需求方選，因為需求方看不到它的代價。
  • 加人通常更慢：新人要時間上手，原本的人要花時間教他、跟他溝通。Fred Brooks 在《人月神話》（The Mythical Man-Month，1975）寫下這個現象：在已經延誤的軟體專案加人，會讓它更晚（後人稱為 Brooks 定律）。例外是工作能清楚切開、新人已經熟悉這套技術的時候。
  • 時間：延期是合理的選項，但有成本（海報、教育訓練、行銷檔期），由需求方評估。
  • 範圍：通常是最好的槓桿。用第 2 課的 MoSCoW：Must 全部保留，剩下的時間分給 Should，再分給 Could。

Should 和 Could 裡面怎麼選？不是挑價值最高的，而是挑每一天換到最多價值的：價值 ÷ 天數。價值是跟需求方一起打的相對分數（例如 1～10）。看這個例子，剩 3 天：

提出選項時，準備 2～3 個，並說出你的建議。只給一個選項是通知，不是協商；給五個以上，對方很難比較。每個選項寫清楚：做什麼、不做什麼、新的日期、代價。

選項 A（建議）：11/27 如期上線，先上櫃檯手動加點與兌換；POS 自動加點延到 12/4。
                代價：店員每筆要多按一次，約 5 秒。
選項 B：延到 12/1 上線，功能完整。代價：海報要重印、教育訓練要改期。
不建議：砍掉測試趕 11/27。點數算錯要人工補點、跟客人道歉，風險由所有人承擔。

協商的結果一定要寫下來：哪些功能這次不做、延到什麼時候、是誰在哪天決定的。口頭說好的範圍，兩週後每個人記得的不一樣（第 7 課會練怎麼寫；比較大的決定寫進系統設計課第 18 課的設計文件或決策紀錄）。也不要因為被要求「估短一點」就把估計砍掉；估計是機率分布，可以談的是範圍，不是數字（第 3 課）。

💡 實務上：「順便加一下」也是範圍協商
範圍協商最常出現的場合不是延誤會議，而是開發途中 PM 或店長說：「集點畫面順便加個生日優惠，應該很快吧？」答應不是錯，但要把交換條件說出來：「可以，大約要 2 天，那月報表要延到下一版，或上線日往後兩天，你選哪個？」每次都默默吸收，緩衝會在沒人知道的情況下被吃光，最後變成西瓜報告。真的是 Must 的新需求，就用上面的四個變數重新談：拿掉哪個 Should、或日期往後，而不是擠進原本的日期。

升級：帶著選項，找能決定的人

升級（escalation）是把超出你權限或能力的問題，帶著選項交給能決定的人。很多人把升級想成告狀或認輸，其實相反：它讓問題在還能處理的時候，被有權處理的人看到。

什麼時候升級（符合任一個）：

  • 需要的決定超出你的權限：改上線日、砍功能、花錢買服務。
  • 會影響已經答應別人的日期：燈號變紅。
  • 阻擋超過約定的時間：例如等別人回覆超過 2 天，催過也沒有進展。

升級給誰：給有權做這個決定的人。上線日是店長對客人、對海報的承諾，所以是店長；技術主管要知道（副本），但他不能替店長決定。POS 廠商是問題的來源，你要繼續追他的交付日，但他無權決定咖啡店什麼時候上線。

怎麼說：六個部分，跟進度回報一樣結論先行。

部分內容例子
現況發生了什麼，事實POS 廠商今天（11/19）通知，點數 API 從 11/19 延到 11/27 交付
影響對交付的影響，具體到天數串接與測試要 4 天，最快 12/1 完成。原本 4 天的緩衝全部用掉還不夠，上線會從 11/27 延到 12/1，晚 4 天
選項2～3 個，每個有新日期A：如期、先手動加點；B：延到 12/1
建議你選哪個、為什麼建議 A：海報不用改，自動加點晚一週影響小
需要的決定要對方決定什麼選 A 或 B
期限最晚什麼時候要答案，而且要早於交付日11/20 前，才來得及調整教育訓練

決定的期限要往回推：如果選 A，店員訓練要改成手動加點的流程，需要幾天準備，所以期限是 11/20，不是 11/26。期限訂在上線日之後，等於沒問。

💡 實務上：跨團隊卡住時，先找窗口，再一起往上
工作中最常見的升級，是等另一個團隊或外部廠商：後端 API、設計稿、資安審查。順序通常是：先直接找對方的負責人，問清楚卡在哪、什麼時候能給；約定時間過了仍沒進展，再請你的主管和對方的主管談，並先跟對方說一聲「這會影響我們的上線日，我會請主管一起看」。直接越級寄信給對方老闆而沒先打招呼，問題可能解決，但合作關係會受傷。資深工程師升級前會先確認：我手上的事實和日期是不是都對、選項是不是準備好了。
升級不是把問題丟出去就結束。對方做了決定之後，把決定寫下來、更新風險表與計畫、通知相關的人。如果你沒有收到回覆，在期限前再問一次，並說明「沒有回覆的話，我會照建議的選項 A 進行」。

練習

練習 1～4 是寫函式或填資料，起始程式已經宣告好型別。日期一律是 'YYYY-MM-DD' 字串，同樣格式的字串可以直接用 <、> 比較先後。不能用 Date.now() 或 Math.random()：需要今天的日期時，從參數來。

練習 1：寫 prioritizeRisks(risks)。owner、trigger、mitigation 任何一個去掉前後空白後是空字串，這個風險就不能行動：把它的 id 放進 invalid（照輸入的順序），不參與排序。其餘的依分數（probability × impact）由大到小排進 ranked；同分時 dueDate 早的在前；再同分依 id 的字串順序。不能修改傳進來的陣列。

練習 2：寫 statusOf(p) 和 report(p, done, next, asks)。statusOf 照「紅黃綠」一節的規則：forecastP85 晚於 deadline → 'red'；否則 bufferUsedDays > bufferDays / 2，或有任何 blocker 從 since 到 today 超過 2 個日曆天（daysBetween(since, today) > 2）→ 'yellow'；否則 'green'。report 回傳 { headline, status, done, next, asks }：status 用 statusOf 算；headline 以「綠燈」「黃燈」或「紅燈」開頭（跟 status 一致），並包含 forecastP85 的日期；done、next、asks 照傳入的回傳。兩種情況要 throw new Error(…)：status 不是 green 而 asks 是空的（黃燈、紅燈一定要說需要誰做什麼決定）；任何 ask 的 by 晚於 deadline（決定來不及）。

練習 3：寫 negotiate(items, capacityDays)，算出時程不夠時的範圍建議。規則：must 一定保留；剩下的天數先分給 should，再分給 could；同一級裡依 value / days 由大到小（同值依 id 的字串順序）逐一檢查，放得進剩下的天數就保留，放不進就砍掉、繼續看下一個。如果 must 的總天數本身就超過 capacityDays：fits 是 false，keep 只有 must，其他全部 cut（這時要回去談時間，不是砍 must）。其他情況 fits 是 true。keep、cut 的順序不限，每個 id 剛好出現在其中一邊。

練習 4：今天是 2026-11-19（四），集點原本 2026-11-27（五）上線。POS 廠商剛通知：點數 API 從今天延到 11/27 交付，串接與測試還要 4 天，照原本的範圍最快 12/1 才能上線。照「升級」一節的六個部分填 escalation：to 填有權決定上線日的人；impactDays 是會晚幾天；至少 2 個選項（id 不重複），其中至少一個縮小範圍、維持原上線日，至少一個延後；recommendation 是你建議的選項 id；decisionBy 是最晚要拿到決定的日期，要來得及在上線前調整。所有日期是合法的 'YYYY-MM-DD'，不能早於今天。

練習 5：進度回報寫「綠燈」，但預測完成日已經比期限晚 2 天，理由是「應該趕得上」。這是什麼問題？

✓ 燈號的用途是讓別人提早決策；報綠燈會讓需求方錯過調整的時機，最後一週才變紅。改成黃燈仍然不符合規則（預測已經晚於期限），只是換一種方式隱瞞；不寫預測日期，對方就沒辦法判斷燈號對不對。

練習 6：時程不夠時，下面哪一個不應該放進給需求方的選項？

✓ 品質不是可以交易的變數：省下的時間會在上線後以 bug、事故與加班加倍還回來，而需求方看不到這個代價，沒辦法替你做這個取捨。延期、砍 Could、先上小切片都是合理的選項，由需求方依代價選擇。

練習 7：風險「唯一懂舊結帳程式的同事下週休假」，最好的寫法是？

✓ 風險表的每一項都要能行動：誰負責盯、看到什麼訊號就啟動、要做什麼。只寫標題的風險沒人會處理。休假還沒發生，同事還在，現在安排交接就能降低影響，所以是風險；等他已經休假、你卡住了，才是問題。

練習 8：專案落後，主管提議再加兩個人。最可能的結果是？

✓ 新人要時間熟悉程式與需求，原本的人要花時間教他、跟他協調，越接近期限加人效果越差（Brooks 在《人月神話》寫下的現象）。但不是絕對：工作能清楚切開、新人熟悉這套技術時可能有幫助，所以「一定提早」「沒有影響」「品質一定變差」都太絕對。

常見錯誤

  • 最後一刻才說延誤：越晚說，需求方能選的路越少。看到風險的觸發條件成立，或燈號變黃，當天就說。
  • 燈號憑感覺：預測已經晚於期限仍報綠燈，就是西瓜報告。燈號寫成規則，由預測日、緩衝、阻擋天數決定。
  • 風險只寫標題：沒有負責人、觸發條件、因應的風險不會有人處理。負責人寫一個人的名字，觸發條件寫看得到的訊號與日期。
  • 升級時只丟問題：只說「API 延後了怎麼辦」，等於把思考也丟給對方。帶著現況、影響、2～3 個選項、你的建議、需要的決定與期限。
  • 用砍測試換時程：品質不是選項。可以談的是範圍、時間、資源。
  • 協商結果只在口頭上：寫下這次不做的功能、延到什麼時候、誰在哪天決定的，傳給相關的人，之後才不會各自記得不同的範圍。

小結

  • 風險是還沒發生的事，問題是已經發生的事；風險表每一項都有機率、影響、負責人、觸發條件、因應，依機率 × 影響排序。
  • 燈號由規則決定：預測晚於期限是紅燈；緩衝用掉超過一半或阻擋超過 2 天是黃燈；其他是綠燈。燈號準比永遠綠燈重要。
  • 進度回報結論先行：燈號＋預計完成日、本週完成、下週計畫、風險、需要誰在什麼時候前做什麼決定。給不同讀者換寫法，但燈號與日期一致。
  • 範圍協商的四個變數是時間、範圍、資源、品質；品質不是選項，加人通常更慢。Must 全部保留，其他依價值 ÷ 天數取捨。
  • 超出權限、影響期限、阻擋超過約定時間就升級：找有權決定的人，帶著現況、影響、選項、建議、需要的決定與期限，並把結果寫下來。
