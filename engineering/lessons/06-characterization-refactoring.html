階段 2：接手舊程式：讀懂、鎖住、安全修改 · 第 6 課

特徵測試與安全重構：先鎖住行為再小步修改

咖啡店的集點程式 calcPoints 是三年前外包寫的，一層包一層的 if，沒有測試。上個月有人覺得「點數用四捨五入很怪」，把一個 Math.round 改成 Math.floor，順便整理了縮排。程式跑起來沒有錯誤，三天後會計對帳才發現：這三天的會員點數比過去平均少了兩成，客人在櫃檯抱怨。改的人說「我只是整理一下」。問題不在他技術不好，而在他沒有任何方法知道自己改變了行為。

這一課教你在動舊程式之前先把行為鎖住，在測試保護下小步修改。

這課的路線：
  1. 不敢改的程式、特徵測試：沒有測試的 calcPoints 怎麼改才知道自己有沒有改變行為：先挑會走過每個分支與邊界的輸入，把現在的實際輸出記成測試。
  2. 變異測試：故意把程式改壞一點，看測試抓不抓得到，證明這些測試真的有用，而不是只有覆蓋率好看。
  3. 加接縫：「現在幾點」寫死在程式裡的函式，怎麼改成可以在測試裡指定時間，週五 16:59 也測得到。
  4. 小步重構、重構與改需求分開：每一步只做一種改動、立刻比對，重構完成後才改需求，兩者分開提交，reviewer 才看得出哪裡改了行為。
這課會用到：
  • 第 5 課的確認實際行為：列出分支與邊界、設計會走過它們的輸入、記錄實際輸出；這課把那些紀錄變成測試。
  • 系統設計課第 20 課的特徵測試與重構：特徵測試記錄程式現在的行為而不判斷對錯，重構是不改外部行為地改善結構；這課不重教定義，往下練手選案例、變異測試、接縫。

不敢改的程式長什麼樣

先看這次要動的程式。註解是當年寫的，程式是現在正式環境在跑的版本：

// productId：1 美式咖啡、2 拿鐵、3 卡布奇諾、4 伯爵紅茶、5 可頌、6 起司蛋糕
const CROISSANT = 5

// 集點規則（2023 年外包版）：
//   每滿 50 元 1 點；會員在平日點數加倍；平日買 2 個以上可頌多送 1 點
function calcPoints(order: Order): number {
  let points = 0
  if (order.total >= 50) {
    points = Math.round(order.total / 50)
    if (order.isMember) {
      if (order.weekday <= 5) {
        points = points * 2
      }
    }
  }
  let croissants = 0
  for (const item of order.items) {
    if (item.productId === CROISSANT) {
      croissants = croissants + item.qty
    }
  }
  if (croissants >= 3) {
    if (order.weekday <= 5) {
      points = points + 1
    }
  }
  return points
}

weekday 是 1～7，1 是週一、7 是週日，所以 weekday <= 5 是平日。仔細對照會發現兩處跟註解不一致：

  • 註解說「每滿 50 元 1 點」，程式卻是 Math.round(total / 50)（四捨五入，TypeScript 課第 5 課）：75 元得 2 點，不是 1 點。
  • 註解說「2 個以上可頌」，程式寫 croissants >= 3。

哪一邊才對？現在不知道。第 5 課說過：正式環境的行為就是現在的事實，客人已經依照它拿了三年的點數，會計的報表也照它對帳。開頭那位同事的錯，不是他覺得 Math.round 怪，而是他在「整理」的時候順手改了行為，而且沒有任何東西告訴他。

這一課的流程只有四步，每一步都是一個獨立的提交：

特徵測試：手選案例，記錄實際輸出

系統設計課第 20 課介紹過特徵測試（characterization test），又稱 golden master：不判斷程式對不對，只記錄它現在實際做了什麼，之後的改動不能讓這些紀錄改變。那一課的做法是丟一大批輸入、存下所有輸出。這一課練的是另一種寫法：手選少數案例，每一個都有名字、說得出它在鎖哪一條分支或哪一個邊界。手選的案例讀得懂，能當成文件，之後也容易換成描述業務規則的測試。

步驟：

  1. 列出分支與邊界（第 5 課的做法）。calcPoints 有：total >= 50（邊界是 49 和 50）、Math.round（餘數 25 以上會進位，例如 75）、會員、平日（邊界是週五 5 和週六 6，也要有週日 7）、可頌數量（邊界是 2 和 3）、可頌的平日條件、可頌加點與會員加倍的先後順序。
  2. 每個分支、每個邊界兩側各挑一個輸入。挑讓結果容易看出差別的值：會員加倍要用基本點數不是 0 的金額，不然加不加倍都是 0。
  3. 執行，把實際輸出寫成預期值。不是用心算、不是照註解推。下面的範例就是這一步：先跑，再抄。
  4. 看起來像 bug 的也照記，在案例名稱標註「疑似 bug，已開 issue #123」。修不修是另一件事，要問店長和會計，確定後用獨立的提交修，同時改那一條預期值。

75 元得 2 點、2 個可頌沒加點，都跟註解不同。特徵測試照實際寫 2 和 3，名稱標上「疑似 bug」。寫成資料表最容易讀，審查的人一眼看得出漏了哪個邊界：

const cases = [
  { name: '剛好 50 元：1 點（邊界）', input: { total: 50, isMember: false, items: [], weekday: 1 }, expected: 1 },
  { name: '49 元：0 點（邊界）', input: { total: 49, isMember: false, items: [], weekday: 1 }, expected: 0 },
  { name: '75 元：2 點（疑似 bug，註解說 1 點，issue #123）', input: { total: 75, … }, expected: 2 },
  …
]

資料表適合「輸入 → 一個回傳值」的函式。如果要檢查的不只一個值、或想在不符時給出清楚的訊息，就寫成一個測試函式：呼叫、比較、不符就 throw。練習 2 會用這種寫法。不管哪一種，一定要比較結果；只呼叫、不比較的測試永遠會通過。

特徵測試只能在本機或測試環境跑。第 5 課說過，會寫入資料的路徑絕對不要拿正式環境做實驗；像 calcPoints 這種只算數字、沒有副作用的純函式最好鎖，有寫入的程式要先用接縫把寫入換掉（下面會講）。
💡 實務上：快照測試是最快的特徵測試，也最容易被養壞
Jest、Vitest 都有 toMatchSnapshot()：第一次執行把輸出存成檔案，之後每次比對。接手 API 回應格式、報表匯出、Email 範本這類輸出很長的程式時，幾分鐘就能鎖住。常見的坑是快照一紅就直接加 -u 更新，等於把測試關掉；審查時要把快照檔的 diff 當成程式碼看。時間戳記、隨機 ID 這類每次都會變的欄位要先固定或遮掉再存。下週就要整段刪掉重寫的程式，不值得花時間鎖。

測試有沒有用：變異測試

寫完測試，怎麼知道它真的抓得到改動？最常見的答案是看覆蓋率（coverage）：測試執行到了幾成的程式。但覆蓋率只看「有沒有執行到」，不看「有沒有檢查結果」。一個只呼叫 calcPoints、什麼都不比較的測試，覆蓋率可以是 100%。

變異測試（mutation testing）直接回答「改了會不會被發現」：故意對程式做一個小改動，產生變異體（mutant），例如把 >= 改成 >、把 * 2 拿掉、把 Math.round 換成 Math.floor，然後拿你的測試去跑（第 2 課拿驗收條件去跑有 bug 的實作，就是同一個想法，這裡做成有系統的方法）：

結果名稱代表什麼
至少一個測試失敗被殺掉（killed）測試抓得到這種改動，這是你要的結果
測試全部通過存活（survived）有人這樣改，測試不會發現；缺一個案例或斷言
沒有任何測試執行到那一行沒有涵蓋（no coverage）當成存活
測試跑不完（例如變成無窮迴圈）逾時（timeout）當成偵測到

開頭那位同事的改動，就是一個「Math.round 換成 Math.floor」的變異體。如果當時有測試能殺掉它，他改完就會看到紅燈。下面示範：只有一個快樂路徑案例時，「>= 50 改成 > 50」的變異體活得好好的；補上剛好 50 元的邊界案例，它才被殺掉。

第一次只殺掉一個：100 元除以 50 剛好是 2，round 和 floor 一樣；100 也比 50 大，> 和 >= 沒差。補上 50 和 75 兩個值之後三個都殺掉了。這就是邊界值的用處：好的案例要放在「改一點就會不同」的位置。

變異測試的成績叫 mutation score。依 StrykerJS 文件的定義：被偵測到的（killed＋timeout）除以有效的（被偵測到的＋survived＋no coverage），乘以 100。編譯不過或執行時直接當掉的變異體不算進去。

等價變異體：殺不掉也沒關係

有些變異體跟原程式在任何輸入下行為都一樣，例如把 x * 1 改成 x / 1，或把迴圈的 i < arr.length 改成 i !== arr.length（i 從 0 加到長度，兩者一樣）。這叫等價變異體（equivalent mutant）：它存活不代表測試不足，任何測試都殺不掉它。確認是等價的就標記排除，不要為了 100 分硬寫奇怪的測試。

在真實專案裡

這課的練習由隱藏測試手寫變異體。真實專案用工具自動產生，JavaScript／TypeScript 常用的是 StrykerJS：它把程式裡的運算子、條件、回傳值一個一個改掉，對每個變異體跑一次你的測試，最後給出 HTML 報告，標出哪一行的哪種改動存活。它很慢（變異體數量 × 測試時間），實務上只對這次要改的檔案跑，或在 CI 只跑改動過的程式。這一課只要懂觀念，不用安裝。

加接縫：讓依賴時間的程式可以測

有些程式根本沒辦法寫特徵測試。看這個下午茶時段的判斷：

// 正式機的時區設定成 Asia/Taipei，所以 getHours() 拿到的是台北時間
function isHappyHour(): boolean {
  const d = new Date()
  const day = d.getDay()      // 0＝週日 … 6＝週六
  const hour = d.getHours()
  return day >= 1 && day <= 5 && hour >= 14 && hour < 17
}

它沒有參數，結果取決於你什麼時候執行。上午跑測試永遠是 false，你沒辦法測「週五 16:59」。而且它還藏了第二個外部因素：機器的時區。getHours()、getDay() 讀的是執行環境的時區。正式機設成台北所以正確；CI 機器通常是 UTC，同一個時刻 getHours() 少 8 小時，測試在你的筆電上過、在 CI 上壞，或者反過來。

接縫（seam）是 Feathers 的用詞：一個不用修改那段程式本身、就能替換行為的地方。最常見的接縫就是 Node 課第 22 課教過的「依賴從參數傳進來」：

const TAIPEI_OFFSET_MS = 8 * 60 * 60 * 1000

function isHappyHour(now: () => number = Date.now): boolean {
  const d = new Date(now() + TAIPEI_OFFSET_MS)   // 往後推 8 小時，再用 getUTC* 讀，就是台北的牆上時間
  const day = d.getUTCDay()
  const hour = d.getUTCHours()
  return day >= 1 && day <= 5 && hour >= 14 && hour < 17
}

三個決定：

  • 參數有預設值 Date.now。正式環境的呼叫端還是寫 isHappyHour()，一行都不用改；只有測試傳入固定的時間。拿掉預設值，就得同時改所有呼叫端，一個「讓它可測」的小改動變成大改動。
  • 傳函式 () => number，不是傳數字。呼叫端不用自己先取時間；需要時間時才呼叫，跟原本 new Date() 的時機相同。
  • 把時區寫死成 UTC+8。台北沒有夏令時間，固定加 8 小時就是台北時間。也可以用 Intl.DateTimeFormat 指定 timeZone: 'Asia/Taipei'。這兩種寫法在正式機（台北時區）上跟原程式結果相同，所以行為沒變；差別是現在換到任何時區的機器結果都一樣。

加接縫是一個獨立的提交，只做這一件事。它本身也是修改，但小到可以逐行審查：簽章多一個有預設值的參數、取時間的地方換成 now()。改完立刻替它寫特徵測試，邊界放在 13:59、14:00、16:59、17:00 和週末。

其他常見的接縫：亂數改成傳入 random()；寫資料庫、寄信、呼叫外部 API 改成傳入一個物件（測試時換成記錄呼叫的假物件）；讀環境變數改成傳入設定。原則一樣：預設值保留原本的行為，測試才傳替身。

💡 實務上：「本機過、CI 壞」常常是時間和時區
CI 機器多半設成 UTC，跟你的筆電差 8 小時。典型情境：測試只在月底、跨年，或台灣早上 8 點前（UTC 還是前一天）失敗，平常都是綠燈，大家以為是偶發。看到測試結果跟執行時間有關，第一個懷疑直接讀 new Date()、Math.random()、環境變數的地方。測試框架也有假時鐘（例如 Vitest 的 vi.useFakeTimers() 搭配 vi.setSystemTime()），不改程式就能固定時間；但它是全域替換，忘記還原會影響其他測試，能用參數接縫就優先用參數。Code review 看到新程式直接讀時間，可以順口問一句「這個要怎麼測？」。

小步重構，每一步都比對

有特徵測試之後才開始重構（refactoring）：不改變外部行為地改善結構。每一步只做一種改動，做完立刻跑測試：

一步例子
改名points 改成 basePoints，讓名字說出它是什麼
合併巢狀條件if (isMember) { if (weekday <= 5) … } 合成 if (isMember && weekday <= 5)
抽函式把「算可頌數量」抽成 croissantBonus(items)
提早 return不滿 50 元的情況先處理掉，主流程少一層縮排
具名常數50 改成 POINT_UNIT、3 改成 CROISSANT_MIN

為什麼要這麼碎？測試失敗時，你只要看最後一步：一次改五樣，失敗了不知道是哪一樣。每一步通過就提交（或至少存一個能回去的點），出錯時退回上一步重做，比除錯快。

手選的特徵測試只有十幾個案例，重構時再加一層保險：差異測試（differential testing），把同一批大量輸入同時丟給新舊兩個版本，比較輸出。就是系統設計課第 20 課 golden master 的做法，用固定種子的亂數產生輸入，每次結果都一樣。下面示範一步「合併巢狀條件」，以及一個「順手」把 round 換成 floor 的版本：

差異測試抓的是「整體行為有沒有變」，手選的特徵測試告訴你「是哪一條規則變了」，兩者互補。差異測試要注意兩件事：輸入的分布要涵蓋邊界（只產生 0～40 元的訂單，滿額的分支一次都不會走到），以及舊版本必須保留到比對完成，所以通常先把舊函式改名為 calcPointsLegacy 留在測試裡，重構完成、上線穩定後再刪掉。

💡 實務上：能交給編輯器的重構就不要手改
VS Code 對 TypeScript 的 Rename Symbol（F2）會一起改掉所有引用，Extract to function 也會自動整理參數和回傳值，比搜尋取代安全。但編輯器看不到字串裡的名字：obj[key] 這種動態存取、序列化成 JSON 的欄位名、對應資料庫欄位的名字，改名後要另外搜尋一次。實務上另一個常見問題是「重構順便升級套件、順便改格式化設定」，diff 一大就失去小步的意義；格式化這種整個檔案都變的改動，自己獨立成一個提交。

重構與改需求分開

上一節的重構完成了，現在才輪到需求。系統設計課第 20 課講過：重構 PR 和行為變更 PR 要分開。這裡實際走一次。店長的新需求：

起司蛋糕每買 1 個多送 1 點，不受會員加倍影響。

順序是：

  1. V2：只重構。把 calcPoints 拆成三個具名函式：basePoints(total)（滿額點數）、memberMultiplier(isMember, weekday)（2 或 1）、croissantBonus(items)（可頌加點），主函式只剩組合。特徵測試一條都不改，全部通過；差異測試 0 筆不同。這個 PR 的審查者只需要確認「結構變清楚、行為沒變」。
  2. V3：只改需求。在 V2 的結構上加一行起司蛋糕加點。這時特徵測試裡只有含起司蛋糕的案例預期值要改，其他案例照舊通過。審查者看 diff：程式多一行、測試改了哪幾個預期值、新增了哪幾個案例，一目了然。

如果兩件事混在一個 PR，審查者看到 15 個預期值改變，分不出哪些是「新需求本來就該變」、哪些是「重構不小心改到」。上線後點數出錯，也不知道該退哪一段。V2 先上線跑幾天沒問題，V3 出事時只要退 V3。

重構還有一個好處：需求變更變簡單了。在原本巢狀 if 的版本裡，起司蛋糕的點數該加在加倍之前還是之後、要不要包在 total >= 50 裡，每一個位置的行為都不同；拆成具名函式後，「不乘會員倍數」就是寫在乘法外面。

前面那兩個疑似 bug（75 元得 2 點、2 個可頌不加點）也是同樣的處理：問清楚之後，各自一個小 PR 修，修的時候改對應的特徵測試預期值，PR 說明寫上 issue 編號與店長的決定。

資深視角：鎖多少、什麼時候換掉

  • 不用先替整個系統補測試。只鎖住這次要改的範圍：要改 calcPoints，就鎖 calcPoints 和直接呼叫它的地方（第 5 課的影響分析）。想先把整個專案的覆蓋率補到 80% 再開工，需求會等不到。
  • 特徵測試是鷹架，不是終點。它鎖住的是「現在的行為」，包含 bug。疑似 bug 確認後，那條測試要改成描述業務規則的名字與預期值，例如「75 元得 1 點（店長 2026-11 確認每滿 50 元 1 點）」。慢慢地，特徵測試會被規則測試取代。
  • 用變異測試檢查重要的測試，不是全部。金額、點數、權限這類出錯會造成損失的程式值得跑；格式化顯示文字的程式不值得花那個時間。
  • 接縫越小越好。不要為了測試先導入一套依賴注入框架。一個有預設值的參數就能解決，就用參數。
  • 說得出「為什麼這樣改是安全的」。PR 說明寫：哪些特徵測試保護了這次改動、差異測試跑了幾筆、哪些行為刻意沒動。這是資深工程師跟「我覺得應該沒問題」的差別。

練習

練習 1：替舊的 calcPoints 寫特徵測試 cases。規則：

  • expected 寫的是程式實際的輸出，不是註解說的、也不是你覺得應該的。先用「執行」把案例跑一次，看印出來的實際值。
  • 最多 15 個案例，name 不能重複。不要改 calcPoints：判分用的是隱藏的原始版本。
  • 隱藏測試先用原程式跑你的所有案例（必須全過），再拿 10 個變異體逐一跑（比較符號改了、某個條件拿掉、捨入方式換了、可頌怎麼算改了……，都已確認不是等價變異體），每一個都要至少有一個案例失敗。沒通過時會告訴你哪一種變異體存活。

練習 2：收據最下面的問候語由 legacyGreeting 產生。這次不寫資料表，寫一個測試函式 characterize(fn)：

  • 呼叫 fn 至少 3 次，把每次的結果跟你寫死的字串比較，不符時 throw new Error(…)，訊息寫出是哪個情境。
  • characterize(原程式) 不能丟錯；隱藏測試另有 6 個變異體（時段邊界、生日怎麼比、名字的空白、沒填生日的處理……），characterize(每個變異體) 都要丟錯。
  • 跑變異體時，隱藏測試也會把全域的 legacyGreeting 換成同一個變異體：在函式裡拿 legacyGreeting(…) 當預期值，等於自己跟自己比，抓不到任何東西。

練習 3：替 isHappyHour 加接縫。

  • 改成 isHappyHour(now: () => number = Date.now): boolean：now() 回傳毫秒時間戳。規則不變：台北時間週一到週五、14:00～16:59 是 true。
  • 不要依賴執行環境的時區：判分時會模擬一台時區設成美國紐約的機器（getHours、getDay、沒指定 timeZone 的 toLocaleString 與 Intl.DateTimeFormat 都會是紐約時間），在 500 個時間點上跟正確答案比較。用 UTC 加 8 小時，或 Intl.DateTimeFormat 指定 timeZone: 'Asia/Taipei' 都可以。不要把 toLocaleString 的結果再丟回 new Date() 解析：那種字串的格式沒有標準保證，解析時又會套用執行環境的時區。
  • 保留預設值：不帶參數呼叫 isHappyHour() 要能用（判分時會把 Date.now 換成回傳固定時間的函式）。Date.now 只能出現在預設值。
  • 填 happyCases：at 是含時區的 ISO 字串（例如 '2026-11-02T14:00:00+08:00'）。必須包含平日台北時間 13:59、14:00、16:59、17:00，以及一個週六，expected 要正確。2026-11-02 是週一，2026-11-07 是週六。

練習 4：先重構、再改需求，分成兩個版本。

  • V2（只重構）：寫三個具名函式，calcPointsV2 只負責組合它們，行為跟 calcPoints 完全相同（包含疑似 bug 的 Math.round 與「3 個以上」）。
    • basePoints(total)：滿額點數，還沒乘會員倍數。
    • memberMultiplier(isMember, weekday)：會員且平日回傳 2，否則 1。
    • croissantBonus(items)：可頌數量合計 3 個以上回傳 1，否則 0；不看星期幾，平日條件寫在 calcPointsV2。
  • V3（只改需求）：起司蛋糕（productId 6）每個多送 1 點，不乘會員倍數，也不受星期幾、滿額門檻影響。

判分：用固定種子產生 2,000 筆訂單，V2 要跟 calcPoints 每一筆都相同、三個函式各自跟參考實作相同；V3 在不含起司蛋糕的訂單上要跟 V2 相同，含起司蛋糕的要剛好等於 V2 加上起司蛋糕的數量。判分也會把三個函式暫時換成「結果多 1」的版本，確認 V2 真的用到它們、V3 建立在 V2 上（所以保持起始程式的 function 宣告，不要直接呼叫舊的 calcPoints）；計算時不能修改傳進來的訂單。

練習 5：寫特徵測試時，發現舊程式在 total 為 0 時回傳 1 點，看起來是 bug。你應該？

✓ b。特徵測試記錄的是現在的事實；修 bug 是行為變更，要先問清楚（說不定有客人或報表依賴它），再用獨立的提交修，同時改這一條預期值。a 把修 bug 混進鎖行為的步驟，之後出事分不出原因；c 讓這個行為沒有任何保護，重構時被改掉也沒人知道；d 是在不知道後果的情況下改行為。

練習 6：你的測試全部通過、覆蓋率 100%，但變異測試顯示 6 個變異體存活。這代表？

✓ b。覆蓋率只看「有沒有執行到」，不看「有沒有檢查結果」，一個沒有斷言的測試也能有 100% 覆蓋率。存活的變異體指出「這裡改了測試不會發現」，通常是缺邊界值或缺斷言。a 正是混淆了兩者；c 沒有根據；d 也不對：變異體是故意改壞的程式，它存活說的是測試沒抓到這個改動，量的是測試的品質，不是原程式對不對。

練習 7：替 isHappyHour 加接縫時，為什麼寫成 isHappyHour(now: () => number = Date.now)，而不是 isHappyHour(now: () => number)？

✓ b。接縫的目的是在不改行為、不擴大改動範圍的前提下讓程式可測。拿掉預設值，每個呼叫 isHappyHour() 的地方都要跟著改，變成一個大改動，審查和出錯的範圍都變大。a、c 都不是事實；d 錯在忽略了呼叫端。

練習 8：變異測試報告裡，有一個變異體把 price * 1 改成 price / 1，你怎麼補測試都殺不掉。應該怎麼處理？

✓ c。等價變異體跟原程式在任何輸入下結果都一樣，殺不掉不代表測試不足。a 會浪費時間，而且做不到；b 為了分數改程式，本末倒置（雖然 * 1 本身多餘，要清掉也該是另一個重構提交）；d 毫無根據。

常見錯誤

  • 照註解或「應該的行為」寫預期值：特徵測試在原程式上就不通過，或者鎖住了一個不存在的行為。先執行，再把實際輸出抄成預期值。
  • 測試只呼叫、不檢查結果：覆蓋率很高，什麼都抓不到。每個案例都要比較結果；用變異測試確認它真的抓得到改動。
  • 只挑「好算」的輸入：100 元、週三，讓 > 和 >=、round 和 floor 都算出一樣的值。輸入要放在邊界上：50 和 49、週五和週六、2 個和 3 個。
  • 重構時順手修 bug：行為變了卻說是重構，出事時分不出原因。疑似 bug 開 issue，另一個提交修。
  • 一次改太多：測試失敗時不知道是哪一步。每一步只做一種改動，通過就提交。
  • 加接縫時移除預設值：所有呼叫端都要改，小改動變大改動。預設值保留原本的行為。
  • 忘了時區也是外部因素：getHours()、getDay() 讀機器的時區，筆電上過、CI 上壞。把時區寫死（台北 UTC+8）或用 Intl.DateTimeFormat 指定 timeZone。

小結

  • 改舊程式的順序：鎖住行為 → 加接縫 → 小步重構 → 改需求，每一步一個提交；只有最後一步改變行為。
  • 特徵測試記錄實際輸出，連疑似 bug 也照記並標註；手選案例放在每個分支與邊界的兩側，寫成有名字的資料表最好讀。
  • 覆蓋率只說明「有執行到」；變異測試說明「改了會不會被發現」。killed 是好事，survived 代表缺案例或斷言；等價變異體排除即可。mutation score =（killed＋timeout）÷ 有效變異體 × 100。
  • 接縫是不改那段程式就能替換行為的地方；最小的接縫是有預設值的參數，呼叫端不用改。時間、亂數、時區、寫入外部系統都要考慮。
  • 重構時用差異測試在大量固定種子的輸入上比對新舊版本；重構 PR 測試一條都不改，需求 PR 只改受影響的預期值。
  • 只鎖住這次要改的範圍；特徵測試完成任務後，逐步換成描述業務規則的測試。
