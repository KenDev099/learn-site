沒有測試的程式先讀懂、再鎖住。從入口追出實際行為，用特徵測試記錄下來；在測試保護下小步重構，最後才改需求。[回 資深工程師的工作方法 學習地圖](../index.html)

## A 接手時三種資訊誰可信
| 來源 | 告訴你 | 可信度 |
|---|---|---|
| 註解、README、交接文件 | 某人某時以為程式怎麼做 | no 最低：改程式的人常忘了改文件 |
| 程式碼 | 程式應該怎麼執行 | warn 中：要配合設定、資料、環境 |
| 實際執行結果與正式環境的 log、資料 | 程式實際做了什麼 | ok 最高：使用者每天看到的行為 |

接手前幾天先建立地圖：入口（路由處理器、排程、佇列消費者、按鈕事件）、呼叫鏈、副作用，以及一份「我還不知道的事」清單。Feathers 的定義：舊系統就是沒有測試的程式。

## B 從入口追：呼叫鏈和資料流一起看 {span=2}
```flow LR
(POST /orders/41/refund) -> handleRefund
handleRefund -> [① findOrder 讀出 total 437]
[① findOrder 讀出 total 437] -> [② roundPrice 437 × 0.5 = 218.5 → 219]
[② roundPrice 437 × 0.5 = 218.5 → 219] -> *[③ saveRefund 寫入 219 元、扣 4 點]: 唯一有副作用
```
這課的示範：`saveRefund(order, roundPrice(...))` 字面上 saveRefund 在前，實際 roundPrice 先執行。追完資料流才看到疑點。這筆 437 元訂單給了 9 點，給點看起來是四捨五入；退款扣點卻用 `Math.floor`，全額退款會留 1 點沒扣回；是不是 bug 要先寫進問題清單。不確定順序就設中斷點或暫時加 log，trace 不要 commit。

## C 影響分析：改共用函式誰會受影響
```flow BT
roundPrice
priceCart -> roundPrice
handleRefund -> roundPrice
dailyReport -> roundPrice
handleCheckout -> priceCart
```
這課的示範：改 `roundPrice` 會影響結帳、退款、日報表三個功能；只看直接呼叫者會漏掉 handleCheckout。

- 把 calls 反過來建 callers 表，從被改的函式往上找，用「已看過」的 Set 擋住互相呼叫（saveOrder ↔ retrySave）。
- 每個受影響的地方回答：全部跟著改、只改那個呼叫者，或寫進問題清單問業務方。
- 「尋找所有參考」看不到動態查表、callback、設定檔裡的排程、其他服務的 API 呼叫，要全文搜尋並看排程設定與存取 log。

## D 用實驗確認實際行為
- 列出每個 if 成立與不成立的分支，每個分支設計一個會走到它的輸入。
- 門檻兩側都測：500 和 501、可頌 2 個和 3 個、週五和週六。
- 記錄真實輸出，跟註解並排；示範中註解寫「滿 500 打 9 折」，程式是 `amount > 500`，剛好 500 元沒打折。

```callout err 會寫入的路徑不在正式環境實驗
只在本機或 staging 用測試資料執行。正式環境只用唯讀方式：查 log、用唯讀帳號查資料庫。測試訂單會進報表、觸發出單，刪掉也收不回副作用。
```

## E 文件和程式不一致：現在的行為是事實
| 差異 | 怎麼處理 |
|---|---|
| 影響金額、點數、顧客看到的結果 | warn 問有權決定的人：帳務問會計，優惠政策問店長 |
| 純粹文件過時，行為沒有爭議 | ok 直接更新文件 |

決定之前不改行為，用測試鎖住現狀；要改就是獨立的需求變更。Hyrum's Law：使用者夠多時，所有看得到的行為都會有人依賴。

```kv cols=1
git blame -L :applyPromos: 只看一個函式每一行最後改的 commit
git blame -w: 忽略空白變動
git log -L :函式:檔案: 一個函式的完整演變
git log -S'> 500': 找出某個字串出現或消失的 commit
```
找到 commit 後看訊息、PR 討論，再帶著具體的 commit 去問還在的人。

## F 改舊程式的四步，每步一個提交 {span=2}
```flow LR
(1 鎖住行為 提交 A) -> [2 加接縫 提交 B]
[2 加接縫 提交 B] -> [3 小步重構 提交 C 可拆成好幾個]
[3 小步重構 提交 C 可拆成好幾個] -> *[4 改需求 提交 D]
```
1～3 行為都不變，只有第 4 步改變行為；出問題時看是哪個提交就知道原因。只鎖這次要改的範圍，不必先替整個系統補測試；特徵測試完成任務後，逐步換成描述業務規則的測試。

特徵測試（golden master）只記錄程式現在實際做了什麼：
- 先執行，再把實際輸出抄成預期值，不照註解、不靠心算。
- 每個分支、每個邊界兩側各一個有名字的案例：49 和 50 元、75 元（`Math.round` 進位）、週五和週六、2 和 3 個可頌。
- 看起來像 bug 也照記，名稱標「疑似 bug」並開 issue，確認後另一個提交修。
- 快照測試一紅就加 `-u` 等於關掉測試，快照檔的 diff 要當程式碼審。

## G 變異測試：改了會不會被發現
| 結果 | 名稱 | 意思 |
|---|---|---|
| 至少一個測試失敗 | ok killed | 測試抓得到這種改動 |
| 測試全部通過 | no survived | 缺案例或斷言 |
| 沒有測試執行到那一行 | no no coverage | 當成存活 |
| 測試跑不完 | ok timeout | 當成偵測到 |

覆蓋率只看「有沒有執行到」，沒有斷言的測試也能 100%。mutation score =（killed＋timeout）÷ 有效變異體 × 100。等價變異體（`x * 1` 改成 `x / 1`）殺不掉，確認後標記排除。

## H 接縫與小步重構
```ts
function isHappyHour(now: () => number = Date.now): boolean
```
- 接縫：不改那段程式本身就能替換行為的地方；最小的是有預設值的參數，呼叫端一行都不用改。時間、亂數、時區、寫入外部系統都要考慮。
- 時區也是外部因素：`getHours()` 讀機器時區，CI 多半是 UTC；寫死 UTC+8 或用 `Intl.DateTimeFormat` 指定 `timeZone: 'Asia/Taipei'`。
- 重構每步只做一種改動：改名、合併巢狀條件、抽函式、提早 return、具名常數，通過就提交。
- 差異測試：固定種子的大量輸入同時丟給新舊版本比對，舊函式先改名 `calcPointsLegacy` 留著。
- 重構 PR 測試一條都不改；需求 PR 只改受影響的預期值。
