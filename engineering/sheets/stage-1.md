開工前把需求問清楚、把「做完」寫成可以檢查的條件、切成能上線的小片；估計給區間和前提，開工後讓燈號由規則決定，延誤時帶著選項找有權決定的人。[回 資深工程師的工作方法 學習地圖](../index.html)

## A 一句模糊的需求怎麼變成能開工的紀錄 {span=2}
```flow LR
(店長的一句話) -> [問為了什麼]: 避免 XY 問題
[問為了什麼] -> [整理成五類]
[整理成五類] -> [規則配例子]: Example Mapping
[規則配例子] -> [八類例外逐條問]
[八類例外逐條問] -> {兩條規則矛盾?}
{兩條規則矛盾?} -> [寫成指名決定者的問題]: 範圍重疊且結果不同
{兩條規則矛盾?} -> *寫下來給對方確認: 沒有
[寫成指名決定者的問題] -> *寫下來給對方確認
```
| 分類 | 是什麼 | 怎麼處理 |
|---|---|---|
| goal 目標 | 為什麼要做、成功的樣子 | 放最上面，取捨時回頭看 |
| rule 業務規則 | 能用具體例子檢查的規定 | 每條至少兩個例子，最好一個剛好成立、一個剛好不成立 |
| assumption 假設 | 還沒確認、先當成立的事 | 寫下來才會被確認 |
| question 問題 | 現場沒人答得出來 | 指名誰回答、附預設值與期限 |
| solution 解法 | 對方想好的做法 | 問出背後的目標，當成選項之一 |

例外情境用固定的八類找：邊界值、退款、折扣、重複送出、離線與失敗、時間、身分、資料缺漏。Example Mapping 一個 story 25 分鐘整理不完，代表太大或太不確定。

## B 哪些問題要等答案
| 改變資料結構或金額？ | 有安全預設？ | 結果 |
|---|---|---|
| 是 | 否 | no 阻擋：先問，等答案（點數算折前或折後） |
| 是 | 是 | ok 先用預設值（員工先不能集點） |
| 否 | 不論 | ok 先用預設值（兌換成功的提示文字） |

安全預設：之後改回來不用修資料。可以預設的問題寫明「沒人回答時的預設」和「最晚什麼時候確認」。

```callout warn 矛盾不要自己選一邊
寫成問題：決定者、選項與影響、建議預設、回覆期限。預設選之後容易改回來的那一邊；不要兩種都做成設定讓對方切換。
```

## C 驗收條件：讓錯的實作失敗
```gherkin
Scenario: 點數不足不能兌換
  Given 陳美華是會員，有 9 點
  When 櫃檯幫她兌換一杯中杯拿鐵
  Then 畫面顯示「點數不足」
  And 陳美華的點數仍是 9
```
- Given 寫具體的值，When 一個動作，Then 寫外部看得到的結果，不寫資料表。
- 一條條件驗一件事；同一條規則多組值用 Scenario Outline 加 Examples 表格。
- 好條件：正確實作全過、錯誤實作至少一條失敗。邊界值（49／50、9／10）抓得到 `>` 和 `>=` 寫錯。
- 模糊說法補上指標、門檻、怎麼量；指標要配得上那句話擔心的事，門檻要做得到。課文的例子：「兌換要快」→ 兌換 API 的 p95 < 300 ms，上線前壓力測試；數字不必完美，但要寫出來。
- 驗收條件管這個功能，DoD 管所有工作，兩者都要滿足才算做完。

## D 切片與 MVP：先做哪一塊
| 排法 | 第一次被使用者看到 | 結果 |
|---|---|---|
| 水平切分：資料庫 → API → 畫面 | 最後一層做完 | no 回饋晚、進度看不出來、不能提早停 |
| 垂直切片：每片穿過畫面、API、資料庫 | 第一片做完 | ok 示範：櫃檯手動加點＋查點數，三天後給店員試用 |

| MoSCoW | 意思 |
|---|---|
| Must | 沒有它這版沒意義；MVP 由 Must 的切片組成 |
| Should | 重要，但沒有它還能上線 |
| Could | 有更好，沒有也沒關係；排在 Must 之後，不跟 Must 擠同一片 |
| Won't | 一定寫下來，否則 MVP 越做越大 |

用 INVEST 檢查 story：獨立、可協商、有價值、可估計、夠小、可測試。

## E 估計：拆小，再給區間
拆到每項最可能值不超過 2 個工作天，再補上常被漏掉的：測試、code review 與修改、migration、部署與驗證、文件、等待別人、整合。每項給三點估計 a、m、b：
```kv cols=1
E: (a + 4m + b) / 6，工作時間右偏，E 通常大於 m
SD: (b − a) / 6
總期望值: Σ E，直接相加
總 SD: √(Σ SD²)，標準差不能直接加（為什麼：選讀）；前提是工作彼此獨立，有共同風險時實際更分散
約 90% 區間: ΣE ± 1.645 × 總 SD，下限不小於 Σa
```
| 這課示範的集點兌換 | 天 | |
|---|---|---|
| 只加最可能值 Σm | 11 | no 低估 |
| 加總期望值 ΣE | 13.0 | ok 平均會花的時間 |
| 標準差直接相加 ΣSD | 3.5 | no 高估分散 |
| √ΣSD² | 1.49 | ok 獨立工作的總 SD；13.0 ± 1.645 × 1.49，約 10.6～15.4 天 |
| 悲觀值相加 Σb | 27.5 | no 太悲觀，沒有機率意義 |

Monte Carlo（選讀）：PERT 區間已夠回答「要多久」；要 P85 這類數字時再看。每項從三角分布抽樣、加總、重複上萬次，用 nearest-rank 取 P50、P85；亂數用注入的 `random`，結果才能重現。

## F 回答「要多久」
估計是機率分布，承諾是從中選的一個點。
- 說區間與信心水準，不說單一數字。主線用 PERT 區間：「大約 11 到 15 天，有九成把握」。選讀的 Monte Carlo（seed 42 跑一萬次）：P50 約 14.9 天、P85 約 17.1 天，可說「P50 15 個工作天、P85 17 個工作天」。
- 寫前提：會計在期限前回覆、不含 LINE 推播；前提變了就重新估。
- 對外承諾用高信心的數字（P85 或區間上緣）；不要只回答「最快多久」。
- 被要求「只能給 10 天」時不砍估計，談範圍、時程與資源。
- 記錄估計與實際，看實際落在 P85 以內的比例是否接近 85%，持續校準。

```callout info 先對最不確定的那一項做 spike
看每項 SD² 佔總變異數的比例；示範中串接會計系統佔 62%。spike 限定時間、寫清楚要回答的問題、產出答案和更新後的 a、m、b。不確定性錐靠釐清、切小、spike 變窄。
```

## G 燈號由規則決定，不由心情 {span=2}
```flow LR
(本週狀態) -> {P85 預測晚於期限?}
{P85 預測晚於期限?} -> [紅燈 需要有人做決定]: 是
{P85 預測晚於期限?} -> {緩衝用掉超過一半\n或阻擋超過 2 天?}: 否
{緩衝用掉超過一半\n或阻擋超過 2 天?} -> [黃燈 安全空間在變小]: 是
{緩衝用掉超過一半\n或阻擋超過 2 天?} -> *綠燈: 否
```
每週都報綠、最後一週突然變紅叫西瓜報告。進度回報結論先行（BLUF）：燈號＋預計完成日、本週完成、下週計畫、風險、需要誰在什麼時候前做什麼決定；決定期限要早於交付日。給店長和工程主管寫法不同，燈號與日期一致。

風險表每一項要有機率、影響、負責人（一個人的名字）、觸發條件、因應、檢查日，依機率 × 影響排序。風險還沒發生，問題已經發生。

## H 時程不夠：協商與升級
| 變數 | 能不能談 |
|---|---|
| 範圍 | ok 通常最好的槓桿：Must 全留，其他依價值 ÷ 天數取捨 |
| 時間 | ok 合理，成本由需求方評估 |
| 資源 | warn 加人通常更慢（Brooks 定律） |
| 品質 | no 不放進選項：少測試、跳過 review 會以 bug 和事故還回來 |

提出 2～3 個選項並說出建議。升級的時機：超出權限、燈號變紅、阻擋超過約定時間。找有權決定的人，結論先行講六件事：現況、影響、選項、建議、需要的決定、期限；結果寫下來並更新風險表。
