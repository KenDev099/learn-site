## A 先問：讀者是誰、讀完要做什麼
| 讀者 | 處境 | 文件 |
|---|---|---|
| 店長 | 很忙、要決定花不花錢 | 提案摘要（one-pager），五分鐘內做決定 |
| 值班的人 | 凌晨被叫醒、不一定熟系統 | 操作手冊（runbook），照著做不用思考 |
| 接手的工程師 | 沒人可以問 | 交接文件，能獨立維運 |

Diátaxis 四類：教學（學習中要動手）、操作指南（工作中要動手，runbook 屬於這類）、參考（查事實）、說明（理解為什麼）。長的設計討論用設計文件與 ADR。

## B 提案摘要：一頁讓人做決定
```kv cols=1
一句話結論: 建議做什麼、要多久、要對方決定什麼
問題: 有數字，多常發生、每次多久、影響多少人
建議: 用讀者聽得懂的話
替代方案: 包含「什麼都不做」，每個寫為什麼不選
成本與時程: 區間，例如 3～5 天
風險: 可能出錯的地方與因應
需要的決定: 一個能回答的問題加上期限，不寫「請店長參考」
```
「什麼都不做」是比較的基準：不做的成本很低時，不做也是好結果。決定後在最上面補一行誰在哪天同意。

## C 操作手冊：每個動作接一個驗證 {span=2}
```flow LR
(觸發條件) -> [前置檢查]
[前置檢查] -> [動作]: 通過
[前置檢查] -> [停下來 改用別的手冊或升級]: 不是這個問題
[動作] -> {驗證}
{驗證} -> *完成: 通過
{驗證} -> [動作]: 通過，還有下一個動作
{驗證} -> [回滾]: 失敗
[回滾] -> [升級 呼叫第二線值班]
```
- 每一步是可以複製的指令加預期輸出，例如 `printq status`。
- 破壞性動作前先備份並確認備份成功（purge-stuck 之前 snapshot）。
- 先檢查狀態再動作，做到一半中斷也能從頭重跑，這是冪等用在手冊上。
- 沒修好就恢復原狀再升級；手冊要演練：正常、動作沒用、做到一半三種情況。

## D 交接文件與秘密
交接清單：
- 系統做什麼、架構圖、怎麼確認健康（正常值要有數字）
- 排程與失敗時怎麼辦、外部依賴與聯絡人
- 秘密的位置、部署與回滾
- 已知問題（附 issue 編號）、負責人

```callout err 秘密只寫名稱與位置，從不寫值
例如 `POS_API_KEY`：AWS SSM 的 `/cafe/prod/pos-api-key`。base64 不是加密。已經寫進文件或聊天的秘密當成外洩：撤銷、產生新的、更新秘密管理系統。
```
文件放在程式旁邊、跟 PR 一起更新、告警連到手冊、寫上負責人與最後確認日。過時的文件比沒有文件更危險。

## E 新人 onboarding：第 3 天前上線一個小改動 {span=2}
```flow LR
(帳號與 repo) -> [開發環境 測試跑得過]
[開發環境 測試跑得過] -> [讀交接文件 畫得出資料流]
[讀交接文件 畫得出資料流] -> [跟 buddy 配對 一起改一處]
[跟 buddy 配對 一起改一處] -> *[小改動上線 第 3 天前]
[小改動上線 第 3 天前] -> [正式環境唯讀權限]
[資安訓練] -> [正式環境唯讀權限]
```
每一步寫出「完成的樣子」，例如 `npm test` 全部通過。good first issue 要小、風險低、但走完 PR、review、部署的完整流程。權限照最小權限逐步開通，正式環境寫入權限不在第一週。

| 支援程度 | 什麼時候 |
|---|---|
| 示範：你做他看 | 從沒做過這類任務 |
| 一起做：配對，他打字 | 做過一次 |
| 他做、你 review | 兩次以上，最近一次還有必須修改的問題 |
| 放手，事後回顧 | 兩次以上，最近一次沒有必須修改的問題 |

看對這件任務的熟悉度，不看年資。你的產出包含團隊產出：重複回答的問題寫成文件，請新人回報 onboarding 文件哪裡跟實際不同。

## F 回饋與 code review：讓對方知道下次怎麼做
| 部分 | 寫什麼 |
|---|---|
| 情境 Situation | 日期、星期或 PR 編號 |
| 行為 Behavior | 攝影機拍得到的事，不寫「粗心」「總是」 |
| 影響 Impact | 具體結果，例如集點停了 30 分鐘 |
| 請求 Request | 以動作開頭，不寫「小心」「加油」 |

改進的回饋私下、及時說；好的也要說。

在新人的 PR 裡教人：
- blocking 意見說明為什麼並附參考。
- 同一種問題只留一則，列出所有行號。
- nitpick 最多 3 則，永遠 non-blocking，其餘找時間一起看。
- 用有方向的問題引導；每次至少一則具體的稱讚。
- 不直接幫他改好推上去。

## G 審查 AI 產生的程式
你提交的程式就是你的程式。LLM 產生的是看起來合理的內容，說錯時語氣一樣。審查要比同事 PR 更嚴，原因有三：它不標出沒把握之處、不知道團隊規則、容易一次改很多。

| 類別 | 看什麼 |
|---|---|
| injection | 輸入拼進 SQL，改用 `WHERE id = $1` |
| authz | 有登入，但沒比對擁有者 |
| secret | 密碼寫死在程式碼裡 |
| hallucinated-package | import 的套件不存在 |
| money-float | 示範：0.1 累加 10 次是 0.9999999999999999 |
| missing-await | 回應送出時扣點還沒完成 |
| swallowed-error | catch 後照樣回成功 |
| business-rule | 示範：規則只能換中杯，程式沒檢查 |

清單之外還要看過時或不存在的 API：照專案 lockfile 的實際版本查官方文件。規則先寫成測試再讓 AI 寫實作；AI 同時寫的程式和測試只代表彼此一致。測試要檢查回應與狀態，每個情境用新資料，try/catch 只包住被測的呼叫。

## H AI 工具的資料與權限風險
| 風險 | 做法 |
|---|---|
| 秘密與個資送進 AI（LLM02） | warn 只貼需要的幾行，先遮罩；連線字串只遮密碼，訂單編號不能誤遮；公司政策優先；push protection 管不到聊天視窗 |
| 套件幻覺與 slopsquatting（LLM03） | warn 安裝前確認存在、名稱不是熱門套件的變形（編輯距離）、發布時間、下載量、repo；裝完提交 lockfile，CI 用 `npm ci` |
| 提示注入（LLM01）與權限過大（LLM06） | warn 外部內容是資料不是指令；只給最小權限，危險動作要人確認 |

```callout info 適不適合交給 AI
看你能不能有效驗證它的產出。樣板程式、測試草稿、解釋陌生程式、改寫文件適合；不熟又沒測試的領域、需要內部規則的業務邏輯、安全決定、正式環境秘密與客戶資料要小心。
```
