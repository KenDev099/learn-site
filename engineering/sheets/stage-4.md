需求變更要同時保證「該變的變了」和「不該變的沒變」。每一步都留下別人能檢查的產出，下一步拿它繼續做。[回 資深工程師的工作方法 學習地圖](../index.html)

## A 專題的六個步驟 {span=2}
```flow LR
(① 釐清) -> [② 驗收條件]: 規則與店長回覆
[② 驗收條件] -> [③ 估計與風險]: 知道做完長什麼樣
[③ 估計與風險] -> [④ 鎖住舊行為]: PERT 區間與風險表
[④ 鎖住舊行為] -> [⑤ 先重構再加規則]
[⑤ 先重構再加規則] -> *⑥ 旗標放量上線並回報
[② 驗收條件] --> [⑤ 先重構再加規則]: 條件也是測試
```
店長說：「會員生日當月，飲料打 85 折，點數加倍。3 月 1 日開始。」要改第 5、6 課那份沒有測試、三年前外包寫的結帳程式。這個變更碰到金額、點數、時間、舊程式和上線。

## B 步驟 1：釐清，新舊規則交會處要主動問
| 編號 | 規則 | 店長回覆 |
|---|---|---|
| b1 | 生日當月才適用 | 以台北時間判斷；2/29 生日非閏年算 2 月；沒填生日不適用 |
| b2 | 飲料打 85 折 | 美式、拿鐵、卡布奇諾、伯爵紅茶；每項小計各自打折後四捨五入 |
| b3 | 點數加倍 | 用最後金額照原規則算，再乘 2 |
| b4 | 跟舊優惠的關係 | 可疊加；滿額門檻用沒有生日折扣時的金額 |

b4 是從舊程式讀出來的，店長不會想到。

```callout warn 兩個時間的坑
台北 3/1 凌晨用 UTC 判斷還是 2 月。`getMonth()` 讀執行環境的時區，所以先加 8 小時再用 `getUTC*` 讀。`Date.UTC` 遇到不存在的日期會往後進位，2/29 生日換成非閏年日期會跑到 3 月。
```
退款扣點不影響結帳金額，可以先上線；時區直接影響每筆金額，要先問到。

## C 步驟 2～3：驗收條件、估計與風險
這課的示範：生日 3 月的會員在 3/4 買一杯拿鐵。
```kv cols=1
b2: 110 × 85 / 100 = 93.5 → 94
滿額門檻: 用沒有生日折扣的 110 判斷，沒超過 500
會員 95 折: 94 × 0.95 = 89.3 → 89 元
b3: 89 / 50 = 1.78 → 2 點，乘 2 得 4 點
```
只有這一條，UTC 版本的 bug 抓不到；加上「台北 3/1 00:30」才會失敗。每個例外情境至少變成一條條件。

估計時把讀舊程式、特徵測試、重構都列成要估的工作；不列，它們會變成延期的理由。風險表至少一筆的觸發條件跟舊程式有關。要改沒看過的舊程式時，可以先要半天 spike（有時間上限的探查）讀程式，再給區間；半天看不完就寫進風險表回報。熟悉的程式不必多這一步。

## D 步驟 4～5：鎖住、重構、加規則各一個提交
| 提交 | 內容 | reviewer 檢查 |
|---|---|---|
| 1 鎖住行為 | 只加特徵測試，程式不動 | 舊程式上全過；沒有存活的變異體 |
| 2 重構 | 拆成具名函式，行為不變 | 特徵測試一條沒改；差異測試 0 筆不同 |
| 3 生日規則 | 加 b1～b4，包在功能旗標後面 | 驗收條件全過；非生日訂單的特徵測試仍全過 |

要鎖的分支與邊界：
- 可頌 3／4／6 個、平日與週末、台北與 UTC 星期幾不同的凌晨
- 剛好 500 元、扣可頌前超過 500 但扣完沒超過
- 會員與非會員、金額與點數取整在 .5、空購物車

示範中「先打會員 95 折」的整齊重構，只有原價剛好超過 500 的會員訂單會不同，差異測試幾秒就找出來。新程式時間一律從 `now` 參數拿，不寫 `Date.now()`。

## E 步驟 6：功能旗標逐步放量 {span=2}
```flow LR
(check 旗標低於 10%) -> [set-flag 10%]
[set-flag 10%] -> {verify 錯誤率}
{verify 錯誤率} -> [50%、100% 每步都 verify]: 正常
[50%、100% 每步都 verify] -> [verify 有生日訂單]
[verify 有生日訂單] -> *[finish 通知店長]
{verify 錯誤率} -> [rollback 旗標設回 0]: 上升
[rollback 旗標設回 0] -> [verify 錯誤率恢復]
[verify 錯誤率恢復] -> [escalate 呼叫值班]
```
- 旗標把部署和發布分開：先部署、旗標關著，再依手冊打開；每次調升最多 50 個百分點。
- 錯誤率上升先止血再調查，順序反了顧客會一直結帳失敗。
- 每次放量前先 check `flagPercent` 是否低於目標，已達到就跳過，中斷後重跑不會把旗標調降。
- 正常流程要用 finish 明確結束，否則會接著執行回滾。
- 上線前通知櫃檯和會計；示範中 P85 預測 3/3 晚於 2/27 期限，就是紅燈，附上需要店長在 2/20 前做的決定。

## F 回顧：跳過每一步的代價
| 步驟 | 常見的跳過方式 | 代價 |
|---|---|---|
| 釐清 | 聽完就開始寫 | no 時區、2/29 在 3/1 凌晨被顧客發現 |
| 驗收條件 | 「做完給店長看」 | no 上線前一天才吵什麼叫做完 |
| 估計與風險 | 只給一個數字 | no 延期時沒有選項可以談 |
| 鎖住舊行為 | 「改一點點而已」 | no 非生日訂單金額悄悄變了，月底對帳才發現 |
| 分開提交 | 重構和新規則一起送 | no 分不出原因，只能整包回滾 |
| 手冊與回報 | 一次全開、做完才報 | no 臨場想怎麼回滾，店長最後一天才知道會延 |

驗收條件拿去跑正確與有 bug 的實作，特徵測試拿去跑原程式與變異體；兩者都要對的全過、錯的抓得到。每一步的產出合起來就是這次變更的交接文件。

```callout ok 份量看風險調整
改文案、調顏色，釐清一句、PR 附截圖就夠。碰到金額、點數、權限、時間或舊程式才每一步都留下產出。先問：做錯了，誰會發現？要多久才發現？
```
