階段 2：修問題 · 第 7 課

審查別人的 PR：找出缺陷並寫出可執行的 review 意見

阿哲的 PR-58「優惠券」掛了你的名字當審查者。CI 三個步驟全綠，PR 說明寫著「本機測過 ✓」，最後一行是「行銷週五要發分享連結，希望今天能合併 🙏」。你打開 diff，三百多行。

這一課練的是另一邊的工作：審查別人的程式。CI 綠了只代表「現有的檢查都過了」，它不知道折扣金額該由誰算、兩個人同時用最後一張券會怎樣、顯示的文字裡藏著 HTML 會發生什麼事。這些要靠審查的人看出來。

這課的路線：
  1. 讀 diff、決定先看哪裡：三百多行的 PR，照什麼順序看，最容易先抓到嚴重的問題。
  2. 寫第一條意見、嚴重程度：意見要寫到作者不用再問就能照著改，並讓他知道哪一條非改不可。
  3. 並發與安全：「先查再寫」為什麼會讓優惠券被超用、v-html 為什麼能讓別人在顧客的瀏覽器裡執行程式，這兩種是 CI 抓不到、審查最常漏的問題。
  4. 用測試說服：作者回「不太可能剛好同時吧」時，怎麼在他的程式上跑一個會失敗的測試給他看。
  5. 再審：作者說「都改好了」，為什麼要對照程式而不是對照回覆。
這課會用到：
  • 系統設計課第 20 課的 code review：審查是為了在合併前找出正確性、安全、可維護性的問題，不是挑風格。
  • NestJS 課第 15 課的並發：兩個請求同時「先查再寫」會都通過檢查；第 3 課的時段名額用條件式更新把檢查和寫入合成一句 SQL 解決。
  • Auth 課第 7 課的 XSS：使用者能控制的文字被當成 HTML 放進頁面，裡面的程式就會在別人的瀏覽器執行；Vue 的 v-html 不做任何過濾。

先拿到這一課的程式

在 learn/ 執行 node check.mjs delivery 07，會建立 delivery/practice/work/07/。它是第 6 課修好 CI 之後的專案，加上這個 PR：

檔案是什麼

reviews/PR-58/README.mdPR 說明：作者寫的「做了什麼、怎麼測的」

真實團隊裡這些都在 GitHub 或 GitLab 的 PR 頁面上：說明在最上面、diff 在 Files changed 分頁、意見直接留在某一行旁邊。這裡把它們變成檔案，做法完全一樣。

讀 diff，再決定先看哪裡

diff 是「改了什麼」的標準格式。打開 pr.diff，每個檔案一段：

--- a/api/src/orders/orders.service.ts     ← a/ 是改之前（main）
+++ b/api/src/orders/orders.service.ts     ← b/ 是改之後（這個 PR）
@@ -35,19 +37,29 @@                         ← 原本從第 35 行起 19 行，變成從第 37 行起 29 行
       unitPrice: byId.get(i.productId)!.price,       ← 開頭是空白：沒改，給你看前後文
-    const total = items.reduce(…)                   ← 開頭是 -：刪掉的行
+    const subtotal = items.reduce(…)                ← 開頭是 +：新增的行

diff 只給你改到的那幾行和前後 3 行。很多 bug 藏在「改的這一行」和「沒改的那一行」的關係裡，所以要看前後文時，打開 tree/ 裡的完整檔案。意見的行號一律用 tree/ 裡檔案的行號（編輯器左邊那一欄），也就是 PR 頁面上新版的行號。

三百行不可能每行都同樣仔細看。審查的時間有限，要把它花在出事代價最高的地方。固定的順序，由重到輕：

順序看什麼在這個 PR 裡要問的問題
1. 說明與需求PR 做的事跟需求單一致嗎？有沒有漏、有沒有多做？CAFE-29 說 VIP50 只有 1 張、折扣無條件捨去到元
2. 金額與信任邊界錢怎麼算？哪些資料來自使用者，伺服器有沒有自己檢查？訂單金額由誰決定？
3. 並發兩個請求同時進來，結果還對嗎？兩個人同時用最後一張券？
4. 安全使用者輸入會不會被當成程式執行、會不會看到不該看的資料？畫面上顯示的文字從哪裡來？
5. 測試新的行為有沒有測試？測的是對的東西嗎？優惠券有沒有任何測試？
6. 風格命名、格式、可讀性最後才看，而且多半標 nit

順序的理由很實際：從風格開始看的人，常常在第二十個「這裡可以少一個空行」之後就沒力氣了，真正會讓店家賠錢的那一行反而沒看到。風格的問題盡量交給工具：formatter（自動排版的工具，例如 Prettier）和 linter（找出可疑寫法的工具，例如 ESLint）在 CI 裡就能擋下，人只看工具看不出來的東西。

第 2 步的關鍵詞是第 5 課提過的信任邊界（trust boundary）：資料從不可信的來源進入系統的地方。對 API 來說，瀏覽器送來的一切（body、query、header、cookie）都在邊界外：前端的程式碼使用者看得到、改得了，也可以完全不用你的前端，直接用 curl 送請求（Auth 課第 19 課講過同一件事：不要相信客戶端送來的資料）。所以伺服器拿到的每個值都要問一句：「如果使用者亂填，會怎樣？」

第 1 步常被跳過，卻最能看出「少做了什麼」：diff 裡不會出現沒寫的程式。先讀需求單和 PR 說明，想一下「如果是我會怎麼做、哪裡最容易錯」，再打開 diff。PR 說明的「怎麼測的」也要看：這次只有手動點過兩次，沒有任何新的自動測試，這本身就值得一條 major 意見。PR 太大、混了好幾件事時，請作者拆開也是正當的意見。

跟著做：寫第一條意見

照順序，第 2 步看金額。打開 tree/api/src/orders/orders.service.ts，第 42、43 行：

    // CAFE-29：折扣金額結帳頁已經算好了，直接用
    const discount = dto.couponCode ? dto.discount ?? 0 : 0

dto 是請求的 body，也就是瀏覽器送來的資料。再看 shared/contract.ts，契約真的多了一個 discount 欄位，結帳頁把算好的折扣塞進去送出。問那一句：「如果使用者亂填？」任何人都可以不用結帳頁，自己送這個請求：

curl -X POST http://localhost:3100/orders \
  -H 'Content-Type: application/json' \
  -d '{"customerId":1,"items":[{"productId":2,"quantity":1}],"couponCode":"OPEN10","discount":999}'

一杯 110 元的拿鐵，訂單金額變成 110 − 999 = −889 元。用的還是一張合法的券，用量也照常扣。這就是信任邊界的問題：折扣是錢，錢一定由伺服器算，前端算的只能拿來預覽。

現在把它寫成意見。差的意見和可執行的意見差在哪：

意見作者讀完的反應
「這段寫得不太好」哪裡不好？要改成怎樣？
「折扣應該在後端算吧？」是建議還是一定要改？前端算有什麼問題？
「orders.service.ts:43 直接用客戶端送的 discount，任何人送 discount: 999 就能讓訂單變負數。請改成伺服器依 coupon.percentOff 計算，並從契約拿掉 discount；加一個送 discount: 999 的測試，金額要還是正確的」知道在哪、為什麼一定要改、怎麼改、怎麼確認改好了

可執行的意見（actionable comment）是讀的人不用再問就知道要改什麼、怎麼確認改好了（工程實務課第 8 課的可執行回饋）。固定包含四件事：位置（檔案與行號）、後果（誰做什麼會發生什麼事，不是「不好」「怪怪的」）、修法、驗證方式，再加上嚴重程度，讓作者知道這條是不是擋住合併。這一課的 review.json 就是這個格式。打開 reviews/PR-58/review.json，把範本裡那一條改成：

{
  "verdict": "TODO：approve、request-changes 或 comment",
  "comments": [
    {
      "file": "api/src/orders/orders.service.ts",
      "line": 43,
      "severity": "blocker",
      "problem": "折扣金額直接用客戶端送來的 dto.discount。任何人用 curl 送 discount: 999，訂單就變成負數。",
      "suggestion": "伺服器依 coupon.percentOff 計算 Math.floor(subtotal * percentOff / 100)，契約拿掉 discount。加一個送 discount: 999 的測試：190 元打 9 折，金額仍是 171 元。"
    }
  ]
}

file 寫 tree/ 底下的路徑，line 寫你指的那一行。意見指的是同一個問題時，指到問題發生的地方就好，不用每個相關的行都留一條。

嚴重程度：讓作者知道先改哪一條

嚴重程度（severity）告訴作者這條意見有多重要。團隊用的詞不完全一樣，這門課用四級：

等級意思什麼時候用
blocker不改不能合併錢算錯、資料會錯或遺失、安全漏洞、跟需求相反
major應該在這個 PR 改缺少重要的測試、錯誤處理不完整、之後很難改的設計
minor可以另開工作處理小的重複、可以更清楚但不影響正確性的寫法
nit風格小事，作者可以不改命名偏好、排版、用字（nitpick：挑小毛病）

最常見的兩種錯：每件事都標 blocker，作者分不出哪條真的重要，最後全部當成意見參考；什麼都不標，作者只好每條都改，或自己猜。標等級也是對自己的檢查：寫 blocker 之前，要說得出「不改會發生什麼事」。

整個 review 最後還有一個結論（verdict），GitHub 的三個選項：approve（可以合併）、request-changes（要改完才能合併）、comment（只留意見，不表態）。只要有一條 blocker，結論就是 request-changes；只有 nit 的時候可以 approve，讓作者自己決定要不要改。

💡 實務上：意見寫給程式，不是寫給人
review 是團隊裡最常見的衝突來源。幾個讓意見好被接受的寫法：講程式不講人（「這段會讓訂單變負數」，不是「你忘了檢查」）；不確定時用問句（「這裡有沒有可能同時被呼叫？」）；在意見開頭標等級（很多團隊用 nit:、blocker: 前綴）；看到寫得好的地方也說一聲。在 review 裡教人時，附上原因和連結（例如「同一個檔案第 71 行的時段名額就是這個寫法」），下次他就會自己想到。作者趕時間時，blocker 不能因為「週五要上」就放過，但可以幫他把 blocker 以外的意見標成另開工作，縮小這次要改的範圍。

並發：先讀再寫，兩個人會同時通過檢查

第 3 步看並發。同一個檔案第 52～56 行：

    // CAFE-29：有輸入優惠券就先確認還能用
    const coupon = dto.couponCode ? await this.coupons.find(dto.couponCode) : null
    if (coupon && coupon.usedCount >= coupon.maxUses) {
      throw new ConflictException({ code: 'COUPON_USED_UP', message: '這張優惠券已經用完了' })
    }

再往下到第 76 行，訂單建好之後才扣用量：

        await tx.coupon.update({ where: { code: coupon.code }, data: { usedCount: coupon.usedCount + 1 } })

讀的時候只有一個請求，邏輯沒錯。但 API 同時會處理很多請求。VIP50 只有 1 張，兩位顧客幾乎同時按下送出：

時間顧客 A 的請求顧客 B 的請求資料庫裡的 used_count
1讀到 usedCount = 0，0 < 1，通過0
2讀到 usedCount = 0，0 < 1，通過0
3建立訂單，寫入 0 + 11
4建立訂單，寫入 0 + 11

兩張半價訂單都成功了，而且 used_count 是 1，資料上看起來一切正常。這有兩個問題疊在一起：先查再寫（check-then-act），檢查和寫入之間有空檔，別人可以插進來；以及遺失更新（lost update），用自己讀到的舊值算出新值寫回去，蓋掉了別人的修改。

CI 抓不到它，因為測試一次只送一個請求。阿哲手動測的「VIP50 用一次之後再用回 409」也是依序的。並發的 bug 只有在同時發生時才出現：開幕週發了分享連結，尖峰時段很多人同時下單，正是它出現的時候。

正確的做法你在第 3 課寫過，而且就在同一個檔案的第 71 行：時段名額用條件式更新，把「檢查」和「寫入」合成一句 SQL：

UPDATE coupons SET used_count = used_count + 1
WHERE code = $1 AND used_count < max_uses     -- 影響 0 列＝用完了，丟 409

PostgreSQL 的 UPDATE 會鎖住那一列；第二個交易要等第一個提交，之後會用最新的 used_count 重新檢查 WHERE（PostgreSQL 18 文件 13.2.1 節），所以只會有一個人成功。

安全：v-html 顯示了使用者能控制的文字

第 4 步看安全。PR 說明寫著「行銷要粗體，所以用 v-html」，打開 tree/web/src/components/CouponBanner.vue：

<p class="coupon" v-html="message" />

Vue 的 {{ }} 會把內容當純文字顯示，裡面的 < 會變成 &lt;。v-html 則把字串直接當 HTML 放進頁面，Vue 不做任何過濾（Vue 3.5 文件：只能用在可信的內容，不能用在使用者提供的內容）。所以要問：message 從哪裡來？看 CheckoutPage.vue 的 applyCoupon()：

  • 查到券時，是資料庫裡的 description（行銷填的）。
  • 查不到時，是 API 的錯誤訊息 找不到優惠券「${code}」，而 code 是使用者輸入的。
  • code 還會從網址的 ?coupon= 自動帶入。

串起來：有人在社群貼出 /checkout?coupon=<img src=x onerror=…>，點開的人進到結帳頁，API 回「找不到優惠券「<img …>」」，v-html 把它當 HTML 放進頁面，onerror 裡的程式就在受害者的瀏覽器執行。這就是 XSS（跨站腳本）：攻擊者的程式以受害者的身分在你的網站上執行，可以讀取頁面上的資料、用他的身分送出請求（Auth 課第 7 課）。這是 blocker。

修法：改用 {{ message }}。真的需要粗體時，不要把 HTML 存進資料庫，改成結構化的欄位（例如「強調的字」和「其他文字」兩段），由模板決定怎麼排版。非要顯示 HTML 不可時，要先用 DOMPurify 這類函式庫過濾。

用測試說服：在 PR 的程式上跑給作者看

「兩個人同時用會超用」這種意見，作者常常回「不太可能剛好同時吧」。最有效的回答是一個測試：在他的程式上跑，失敗給他看。這跟第 5 課先寫重現 bug 的測試是同一個想法。

測試的骨架已經在 tree/api/src/coupons/coupons.race.spec.ts：每次執行先準備一張只能用 1 次、還沒被用過的券 RACE1，order() 送出一個用這張券的訂單。你要寫的是最後兩件事：

  • 同時送出 10 個請求。for 迴圈裡 await 是一個等一個，永遠不會撞在一起；要先把 10 個請求都發出去，再用 Promise.all 等它們全部回來：await Promise.all(Array.from({ length: 10 }, order))。
  • 斷言成功的訂單數恰好是 1（其他是 409）。不要只檢查資料庫的 used_count：上面的時間表裡，遺失更新讓它停在 1，看起來完全正常。

骨架裡還有兩個讓請求真的同時發生的細節：app.listen(0) 先開好 server，以及送出前的「暖機」：先打 10 次 GET /products，讓資料庫連線池把連線建好。沒有暖機時，第一批請求會排隊等連線建立，有時剛好一個接一個完成，測試就時好時壞。

寫好之後在 work/07 執行（它會把 PR 的程式組到 reviews/PR-58/.run/pr/，用另一個資料庫 cafe_pr，不動你開發用的 cafe）：

npm run review:race

▶ 在 PR-58 第一版的程式上跑 api/src/coupons/coupons.race.spec.ts
 FAIL  api/src/coupons/coupons.race.spec.ts > PR-58 優惠券的使用次數上限 > 10 個人同時用只能用 1 次的券，只有 1 張訂單成功
AssertionError: 成功的訂單數：201, 201, 201, 201, 201, 201, 201, 201, 201, 409: expected [ 201, 201, 201, 201, 201, 201, …(3) ] to have a length of 1 but got 9
…
結果：失敗（你的測試在這一版上抓到問題了）

只能用 1 次的券，9 張訂單成功。成功的數量每次跑可能不同（看請求撞在一起的時機），只要超過 1 就證明了超用。把這段輸出貼在意見裡，比任何解釋都有說服力。還沒寫斷言時跑一次，結果會是「通過」：沒有斷言的測試什麼都證明不了。

💡 實務上：並發的測試有機率成分，要讓它「幾乎一定」重現
並發 bug 要靠時機撞在一起，同一個測試跑十次可能只失敗八次。讓它穩定的方法：請求數量夠多、送出前先暖機（讓連線池先建好連線）、讓所有請求在同一時間出發。測試通過一次，不代表程式沒有並發問題；失敗一次就足以證明有。資深的審查者看到「先讀、檢查、再寫」的程式碼，就會直接問「兩個同時進來會怎樣」，不用等測試；測試是拿來說服別人、以及修好之後防止有人改回去。

再審：逐條對照程式，不是對照回覆

作者看完意見會推新的版本，回覆「都改好了」。再審（re-review）是逐條確認每一條意見的處理結果。原則只有一個：看程式，不看回覆。回覆說的是作者以為自己做了什麼，程式才是實際做了什麼。

練習 3 的 round2.md 是阿哲的回覆，round2.patch 是第二版改了什麼（a/ 是第一版、b/ 是第二版），round2/ 是改過的檔案。對每一條意見問兩件事：程式真的改了嗎？原本的情境（送 discount: 999、10 個人同時用、網址帶 HTML）在新版上還會發生嗎？能用測試確認的就跑測試：

npm run review:race -- round2

這次要特別小心的是並發那一條。阿哲說「查用量、檢查、扣用量都包進 $transaction 了，同一個交易裡就不會超用」。這是很常見的誤解：交易保證的是「一起成功或一起失敗」，不保證「同時只有一個人在做」。PostgreSQL 預設的隔離等級是 READ COMMITTED（PostgreSQL 課第 31 課）：每一句 SQL 看到的是它開始時已經提交的資料。兩個交易同時開始，都讀到 used_count = 0，都通過檢查，上面那張時間表照樣發生，只是包在兩個交易裡。Prisma 的 $transaction 也不會自動鎖住讀到的列，它用的就是資料庫的預設隔離等級。

阿哲還把 usedCount + 1 改成了 increment（由資料庫在目前的值上加 1，不再用讀到的舊值）。這修好了遺失更新：used_count 會正確地變成 2、3…，但檢查已經在前面用舊的值通過了，超用還在。這種「改對了一半」最容易在再審時被放過。真正的修法有三種：條件式更新（最簡單，這裡推薦）、SELECT … FOR UPDATE 先鎖住那一列再檢查、或把隔離等級設成 SERIALIZABLE 並在衝突時重試。

其他沒改的意見也要處理：阿哲說 getCpnInfo 的命名之後再改。那是 nit，本來就讓作者決定，不用再爭。只要還有一條 blocker 沒解決，結論就還是 request-changes，並在那一條底下說明為什麼還沒解決、附上測試結果。

💡 實務上：再審時把已解決的意見關掉，只留下還沒解決的
PR 頁面上每條意見是一個討論串（thread）。再審時，確認改好的就標 resolved，沒改好的回覆在同一串裡說明原因（「包進交易還是會超用，race spec 在第二版上仍然不只 1 個成功，輸出如下」），作者一眼就知道剩下什麼。不要在第二輪提出第一輪就該提的新意見，除非是新的程式帶進來的問題；一直加新要求會讓 PR 永遠合併不了。如果來回三輪還談不攏，改成當面或視訊討論十分鐘，通常比再寫五條留言快。

練習 1：照審查順序看完 PR-58，填 reviews/PR-58/review.json。「跟著做」的那一條可以直接放進去。

  • 格式：{ verdict, comments: [{ file, line, severity, problem, suggestion }] }。file 是 tree/ 底下的路徑，severity 是 blocker、major、minor 或 nit，verdict 是 approve、request-changes 或 comment。
  • 判分：會讓店家損失或出事的缺陷都要有意見（指到同一個檔案、行號差 3 行以內）並標 blocker；只是命名風格的地方如果有意見，要標 nit；有 blocker 時 verdict 是 request-changes；意見最多 8 條，每條都要寫出 problem 與 suggestion（不留 TODO）。不評文筆。

練習 2：寫完 coupons.race.spec.ts，證明「同時用只能用 1 次的券會超用」。用 npm run review:race 在 PR 的程式上跑，要看到它失敗。

  • 同時送出至少 10 個用 RACE1 的訂單，斷言恰好 1 個成功（201）、其他被拒絕（409）。
  • 判分：你的 spec 會在四份程式上跑：PR-58 第一版和第二版（只包進 $transaction）要失敗；題目附的兩份修正版（條件式 UPDATE、SELECT … FOR UPDATE）要通過。依序送出、只檢查 used_count、只測折扣金額、讀原始碼找特定寫法、把 Prisma 換成假物件，都會在其中一份被判錯。

練習 4：下列哪一條是可執行的 review 意見？

✓ d。它指到位置、說出後果、給了修法和驗證方式，作者不用回頭追問。a、c 沒有位置也沒有後果，作者只能猜；b（Looks Good To Me）是核准，不是意見，在有問題的 PR 上等於沒看。

練習 5：作者說「我把用量檢查包進 $transaction 了」。這樣解決並發超用了嗎？

練習 6：同事的 PR 有一個變數命名你不喜歡，程式行為沒有問題。這條意見的嚴重程度應該是？

✓ c。風格偏好標 nit，作者可以不改。a、b 把小事標高，會跟真正的 blocker 搶注意力，也拖慢合併。d：完全不提也可以，但提了就要標清楚等級；因為怕傷感情而不提的習慣，遲早會讓重要的意見也不敢提。

常見錯誤

  • 從風格開始看：時間花完了還沒看到金額與並發。照順序：需求 → 金額與信任邊界 → 並發 → 安全 → 測試 → 風格。
  • CI 綠了就以為沒問題：CI 只跑現有的檢查。新功能沒有測試、並發與信任邊界的問題，CI 都看不到。
  • 意見只描述感覺：「怪怪的」「不太好」讓作者只能猜。寫出位置、後果、修法、驗證方式。
  • 每件事都標 blocker，或什麼都不標：作者分不出輕重。blocker 只給錢、資料、安全、跟需求相反的問題；風格標 nit。
  • 相信前端已經檢查過：瀏覽器送來的一切都能被改。金額、價格、折扣、身分，一律由伺服器決定。
  • 用依序的請求測並發：一個等一個永遠撞不在一起。用 Promise.all 同時送出，斷言成功的數量，而不是只看計數欄位。
  • 看到 $transaction 就放行：交易不等於互斥。先讀再寫在 READ COMMITTED 下照樣會超用。
  • 再審時只讀作者的回覆：對照第二版的程式，能跑測試就跑測試。

小結

  • 審查要用固定的順序，由重到輕：需求、金額與信任邊界、並發、安全、測試，最後才是風格。
  • 信任邊界之外（瀏覽器）送來的值都可能被改。錢一律由伺服器算，前端算的只是預覽。
  • 可執行的意見包含位置、後果、修法、驗證方式，並標出嚴重程度；有 blocker 時結論是 request-changes。
  • 「先讀、檢查、再寫」在並發下會讓兩個人同時通過檢查；用條件式更新把檢查和寫入合成一句。
  • v-html 不做任何過濾，顯示的內容只要有一部分來自使用者就是 XSS。用 {{ }}。
  • 最嚴重的問題用一個在 PR 程式上會失敗的測試證明；再審時對照程式與測試，不是對照回覆。交易不等於互斥。
