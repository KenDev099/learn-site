階段 1：接手與第一個需求 · 第 4 課

前後端契約與不同步發布：新增欄位的相容順序、共用型別、舊版前端仍在線上

新需求單 CAFE-18：店長要把結帳頁的「備註」改名為「顧客備註」，API 欄位也從 note 改成 customerNote。改名在自己的電腦上只要五分鐘：前後端一起改、一起測、一起上線。上線後客服卻收到「我明明寫了不要冰，送來的是冰的」。

原因是正式環境裡的前端和 API 從來不會在同一瞬間更新。

這課的路線：
  1. 直接改名會發生什麼事：本機好好的，為什麼上線後備註會不見、而且沒有任何錯誤（開場問題的最小答案）。
  2. 共用契約：前後端的請求、回應、錯誤格式寫在同一份 zod schema，一邊改了另一邊沒跟上，型別檢查就先報錯。
  3. 同時支援新舊（expand）：改名期間 API 怎麼同時收新舊欄位，怎麼知道還有誰在用舊的。
  4. 發布順序：API、前台、移除舊欄位要照什麼順序部署，才能讓每個中間狀態和每次回滾都安全；加欄位、刪欄位也是同一套。
這課會用到：
  • 系統設計課第 19 課的 expand → migrate → contract：先讓新舊格式並存，再讓客戶端換到新的，確認沒人用舊的才移除。
  • TypeScript 課第 26 課的 zod：一份 schema 同時給出型別（z.infer）和執行時檢查；safeParse 不丟例外，回傳成功或失敗的結果。
  • NestJS 課第 7 課的 Standard Schema 驗證：controller 寫 @Body({ schema })，StandardSchemaValidationPipe 就用那份 zod schema 檢查請求。
  • DevOps 課第 16 課的部署與回滾：每次部署是一個版本，出問題就退回上一個版本，前台和 API 各自部署、各自回滾。

直接改名會發生什麼事

假設 API 和前台都直接把 note 改成 customerNote，同一個時間部署。部署前就打開點餐頁的顧客，瀏覽器裡跑的還是舊的 JavaScript，送出的請求長這樣：

curl -X POST http://localhost:3100/orders -H 'Content-Type: application/json' \
  -d '{"customerId":1,"items":[{"productId":1,"quantity":1}],"note":"少冰"}'
{"id":16,"status":"pending","total":80,"customerNote":null,…}

沒有錯誤，回 201，訂單也建立了，只是備註不見了。新的 API 用 zod 的 z.object 驗證，它的預設行為是把沒宣告的欄位丟掉，不報錯（zod 4.6.7）。note 已經不在 schema 裡，就被默默拿掉。這種錯不會出現在錯誤率的圖表上，只會出現在客訴裡。

為什麼前端和 API 不會同時更新

不同步發布（non-atomic release）是指 API 與前端不會在同一瞬間更新，中間一定有一段時間新舊版本混著用。原因有三個：

  • 已經開著的分頁：Vue 做的單頁應用（SPA）只在打開頁面時下載一次 JavaScript，之後切換頁面都不會重新下載。顧客整天開著點餐頁，跑的就是早上的版本。這種已經載入在使用者瀏覽器裡、還沒重新整理的前端程式，叫舊版客戶端（legacy client）。CAFE-18 的工程備註也寫了：顧客常常整天不重新整理。
  • 快取：前台的檔案通常放在 CDN（把靜態檔案快取在離使用者近的伺服器上）。index.html 被快取的話，新部署之後還會有人拿到舊版。
  • 分開部署、分開回滾：正式環境前台和 API 是兩條部署流程。API 出問題時會單獨回滾（DevOps 課第 16 課），這時線上是「新前端＋舊 API」。

所以任何改動都要問：新 API 遇到舊前端、舊 API 遇到新前端，各會怎樣？這兩個組合都安全，才可以上線。

共用契約：shared/contract.ts

契約（contract）是前後端約定的請求、回應與錯誤格式。現在這份約定散在三個地方：API 的 CreateOrderDto（class-validator）、前台 API 層（Vue 課第 16 課）web/src/api/orders.ts 裡手寫的 OrderRequest 和 Order interface，以及 api<Order>() 這個型別斷言。手寫的 interface 只是「前端以為 API 會回這樣」，API 改了欄位，前端的型別檢查照樣通過，執行時才拿到 undefined。

把格式寫成一份 zod schema 放在 shared/，兩邊都從這裡 import：

  • API 用它驗證收到的請求（@Body({ schema })），不合格回 422。
  • 前台用它的型別寫程式，並用 safeParse 在執行時檢查收到的回應。
  • 改契約就是改 API：欄位改名後，vue-tsc 會直接指出前台哪一行還在用舊名字。

跟著做：寫 OrderResponse

打開 shared/contract.ts，加上下單回應的 schema。同一個名字同時匯出 schema（執行時用）和型別（z.infer 從 schema 推出來，寫程式時用），import 一個名字兩種都拿得到：

// POST /orders、GET /orders/:id 的回應。時間在 JSON 裡是 UTC 的 ISO 字串
export const OrderResponse = z.object({
  id: z.int(),
  status: z.string(),
  total: z.int(),
  note: z.string().nullable(),
  orderedAt: z.iso.datetime(),
  pickupAt: z.iso.datetime().nullable(),
  items: z.array(z.object({ productId: z.int(), quantity: z.int(), unitPrice: z.int() })),
})
export type OrderResponse = z.infer<typeof OrderResponse>
  • z.int() 是整數（zod 4 的寫法，等於 z.number().int()）。
  • .nullable()：資料庫裡可以是 NULL 的欄位，JSON 裡是 null。
  • z.iso.datetime() 預設只接受 Z 結尾的 ISO 時間；API 的 Date 轉成 JSON 就是這種格式。請求裡的 pickupAt 要接受 +08:00，那裡要寫 z.iso.datetime({ offset: true })，沒有位移的 2026-11-03T08:30:00 兩種寫法都不接受（zod 4.6.7 文件）。

前台用它取代手寫的 Order。web/src/api/orders.ts 在 web/src/api/ 裡，往上三層才到專案根目錄，所以路徑是 ../../../shared/contract.ts（前台的 import 都寫 .ts）。回應先過 safeParse 再回傳：

import { OrderResponse } from '../../../shared/contract.ts'
import { api } from './client.ts'

// 回應先過契約再交給畫面：格式不對就在這裡丟錯，不讓錯的資料流進畫面
function toOrder(body: unknown): OrderResponse {
  const result = OrderResponse.safeParse(body)
  if (!result.success) throw new Error('訂單資料的格式跟預期不同，請重新整理頁面')
  return result.data
}

export async function getOrder(id: number) {
  return toOrder(await api<unknown>(`/orders/${id}`))
}

safeParse 不會丟例外，回傳 { success: true, data } 或 { success: false, error }。api<unknown> 是故意的：在檢查之前，我們不知道它是什麼。對照原本的 api<Order>(…)，那是型別斷言，TypeScript 相信你，執行時什麼都沒檢查。OrderStatusPage.vue 改用 import type { OrderResponse } from '../../../shared/contract.ts'，再刪掉 orders.ts 裡的 interface Order。

API 端：import 路徑和 @Body({ schema })

API 用 nodenext 模組解析，import 要寫編譯後的副檔名 .js：從 api/src/orders/ 往上三層，'../../../shared/contract.js'。shared/ 在 api/ 外面，所以團隊已經改好設定：api/tsconfig.json 的 rootDir 改成 ..、include 加上 ../shared（不然 tsc 會說檔案不在 rootDir 裡）；編譯結果變成 dist/api/src/main.js 和 dist/shared/contract.js，所以 nest-cli.json 的 entryFile 改成 api/src/main。前台的 Vite 本來就讀得到專案裡的其他資料夾，不用改。

controller 的參數改成 @Body({ schema: OrderRequest }) body: OrderRequest。AppModule 已經登記了 StandardSchemaValidationPipe（NestJS 課第 7 課），有寫 schema 的參數由它驗證；沒寫的參數它直接放行，交給原本的 class-validator ValidationPipe。驗證失敗時，它用我們給的 exceptionFactory 丟出 422：

curl -s -X POST http://localhost:3100/orders -H 'Content-Type: application/json' \
  -d '{"customerId":1,"items":[{"productId":1,"quantity":0}]}'
{"code":"VALIDATION_FAILED","message":"items.0.quantity: Too small: expected number to be >=1"}

這是第 1 課記在 KNOWN_ISSUES.md 的「數量 0 被接受」，在契約寫 quantity: z.int().min(1) 就修好了；只寫 z.number() 的話 0、-1、1.5 都會通過。

錯誤也是契約的一部分

前台要靠 code 分辨錯誤（第 3 課的 ApiError 與 409 SLOT_FULL），所以錯誤的 body 也寫進契約：ApiErrorBody = z.object({ code: z.string(), message: z.string() })。前台已經有一個叫 ApiError 的錯誤類別（第 3 課），schema 取名 ApiErrorBody 避免撞名。

檢查一下現有的錯誤：422 和 409 已經是 { code, message }，但 OrdersService 的三個 NotFoundException 傳的都是字串，例如 NotFoundException('找不到商品')，Nest 會回 {"message":"找不到商品","error":"Not Found","statusCode":404}，沒有 code。改成傳物件，Nest 就把整個物件當成 body：new NotFoundException({ code: 'PRODUCT_NOT_FOUND', message: '找不到商品' })。client.ts 讀錯誤時也可以改用 ApiErrorBody.safeParse(body)，不符合（例如 Proxy 回的 502 頁面）就只用狀態碼。

💡 實務上：契約放在一份檔案，review 時一眼就看得到「API 變了」
前後端在同一個 repo（monorepo）時，共用 schema 是最省事的做法；前後端分開的團隊，常改用 OpenAPI 文件產生雙方的型別，道理一樣：只有一份來源。資深工程師 review 時看到 shared/contract.ts 有改動，會先問「舊的客戶端送這個／讀這個會怎樣」，而不是只看新程式對不對。前端那邊，回應不符合契約時要明確丟錯並記錄下來，比讓 undefined 一路流到畫面上、變成「價格顯示 NaN」好查得多。

同時支援新舊（expand）

改名的安全做法是擴充—遷移—收斂（expand／migrate／contract）：先讓 API 同時支援新舊格式（expand）、讓客戶端換到新格式（migrate）、確認沒人用舊的再移除（contract）。系統設計課第 19 課講過原則，這裡把第一步寫出來。

契約只寫新名字。shared/contract.ts 的 OrderRequest、OrderResponse 把 note 換成 customerNote：新前台只能送、只能讀新欄位，CheckoutPage.vue 還在送 note 的話，型別檢查會直接報錯。舊名字只留在 API 的相容程式裡，在 controller 用 .extend() 多接受一個欄位：

// CAFE-18 相容期：舊前端還會送 note、讀 note。
// 移除條件：warn log「legacy field note」連續 14 天是 0 之後，刪掉 LegacyOrderRequest、回應的 note 與這段註解
const LegacyOrderRequest = OrderRequest.extend({ note: z.string().max(200).optional() })
type LegacyOrderRequest = z.infer<typeof LegacyOrderRequest>

收到請求之後有四種情況：

送來的欄位處理
只有 customerNote（新前台）照常下單
只有 note（舊分頁）當成 customerNote，加 Deprecation 標頭、寫一行 warn log
兩個都有而且相同照常下單（一樣要標頭和 log，因為它送了舊欄位）
兩個都有而且不同422 { code: 'FIELD_CONFLICT' }。默默挑一個，另一個就不見了；寧可明確失敗

資料庫欄位不用改名。API 的欄位名和資料庫的欄位名可以不同：orders.note 留著，在 API 邊界對應一次。改資料庫欄位名本身又是一次需要好幾步部署的 migration（DevOps 課第 17 課），沒有必要就不做。回應也要兩個都回，因為舊分頁的畫面讀的是 note：

// 資料庫的 note 欄位 → API 的 customerNote；名字可以不同，對應只寫在這裡
function toResponse(order: Order): OrderResponse & { note: string | null } {
  return {
    id: order.id,
    …,
    customerNote: order.note,
    note: order.note,   // 相容期：給還沒更新的舊前端
    orderedAt: order.orderedAt.toISOString(),
    pickupAt: order.pickupAt?.toISOString() ?? null,
    …
  }
}

type Order = Awaited<ReturnType<OrdersService['findOne']>> 可以拿到 service 回傳的型別，不用另外 import Prisma 的型別。POST 和 GET /orders/:id 都經過 toResponse。

Deprecation 標頭與 warn log

Deprecation 標頭是回應裡告訴客戶端「這個用法即將移除」的 HTTP 標頭，RFC 9745（2025）規定它的值是 @ 加 Unix 秒數，代表從什麼時候起不建議使用，例如 @1793923200 是 2026-11-06 00:00 UTC（Date.parse('2026-11-06T00:00:00Z') / 1000）。它只是通知，請求照常成功。標頭說的是「這個 API 有用法要淘汰」，說不出是哪個欄位，所以只在請求真的送了 note 時才加，細節寫在 API 文件或需求單裡。要設標頭，handler 多拿一個 @Res({ passthrough: true }) res: Response（Response 從 express import 型別）：passthrough 讓你可以設標頭，回傳值仍由 Nest 送出。

標頭給客戶端的開發者看，warn log 給自己看：之後要靠它數「還有多少舊分頁在送 note」，決定什麼時候可以移除。用 Nest 的 Logger，訊息裡放一段固定、好搜尋的文字：

private readonly logger = new Logger(OrdersController.name)
…
this.logger.warn(`legacy field note customerId=${input.customerId}`)

做完之後，用舊格式送一次（-i 會印出回應標頭）：

curl -si -X POST http://localhost:3100/orders -H 'Content-Type: application/json' \
  -d '{"customerId":1,"items":[{"productId":1,"quantity":1}],"note":"少冰"}'
HTTP/1.1 201 Created
Deprecation: @1793923200
…
{"id":14,"status":"pending","total":80,"customerNote":"少冰","note":"少冰","orderedAt":"2026-11-02T08:22:35.507Z","pickupAt":null,"items":[{"productId":1,"quantity":1,"unitPrice":80}]}

API 的終端機會多一行：

[Nest] 797  - 11/02/2026, 4:22:34 PM    WARN [OrdersController] legacy field note customerId=1

兩個都送而且不同時：

{"code":"FIELD_CONFLICT","message":"note 與 customerNote 不同；請只送 customerNote"}
💡 實務上：相容程式一定要附移除條件
「先兩個都支援」很容易，難的是記得收。沒寫移除條件的相容程式會永遠留下來，下一個人不敢刪，因為不知道還有沒有人在用。資深工程師會在相容程式旁邊寫清楚「看哪一行 log、連續幾天是 0 就刪」，並在需求單開一張後續的單（例如 CAFE-19 移除 note），排進下一個月。對外的 API、手機 App 這種使用者不一定會更新的客戶端，等待期要用月來算，還要加上 Sunset 標頭公告停止日期。

發布順序：每個中間狀態都要安全

改名拆成四步，每一步都是一次獨立的部署，中間可以隔幾天：

步驟做什麼線上會出現的組合，為什麼安全
1. deploy-api-both上線同時支援新舊的 API舊前台＋新 API：送 note、讀 note 都照舊。這一版出問題可以回滾，前台還是舊的
2. deploy-web-new上線送 customerNote 的前台新前台＋新 API：沒問題。舊分頁＋新 API：步驟 1 已經處理。前台要回滾也安全，API 兩種都懂
3. wait-old-field-zero看 warn log，等它連續一段時間是 0什麼都不改。舊分頁只能用資料判斷有沒有消失
4. remove-old-fieldAPI 刪掉 note 的相容程式已經確認沒有人在送 note；資料庫不動

把順序反過來看就知道為什麼不行：

  • 前台先上：新前台送 customerNote 給還是舊版的 API，舊 API 不認得，備註被丟掉（跟這一課開頭一樣，只是方向反過來）。
  • 新前台上線後，API 回滾到步驟 1 之前的版本：同樣是「新前台＋舊 API」。所以步驟 2 之後，API 的回滾目標最舊只能到步驟 1 的版本。這也是步驟 1 要先單獨上線、觀察一陣子的原因。
  • 沒等就移除：還開著的舊分頁又回到「備註消失」。上線當天舊分頁最多。

等多久？不是靠感覺，而是看 log：在 log 系統裡搜尋 legacy field note，每天的筆數降到 0，並且連續維持一段時間（例如 14 天，要長過顧客最長不重新整理的時間，再加上一個週末）。本機開發時，就是在 API 的終端機輸出裡找這一行。

💡 實務上：加欄位、改名、刪欄位都是同一套順序
只「加」一個選填的欄位最簡單：API 先上，前台再用，舊前台不送也沒事。「改名」＝加新的＋之後刪舊的，「刪欄位」＝先讓所有人不再依賴它、再刪。資料庫的 migration 也一樣（DevOps 課第 17 課）：先加新欄位、程式兩邊都寫、回填、最後才刪舊欄位。PR 說明的「風險與回滾」段（第 2 課）要寫出這一版跟上一版、下一版混用時會怎樣，以及回滾的目標版本。

練習

三題都在 delivery/practice/work/04 裡寫，寫完回到 learn/ 執行 node check.mjs delivery 04。判分會先跑 tsc 與 vue-tsc（任何型別錯誤都會停在這裡），再重建判分用的資料庫、用 supertest 打 API，前台的 fetch 會換成假的。想手動試，可以 npm run dev 再照上面的 curl 送。

練習 1：建立共用契約，讓 API 和前台都改用它。

  • 先完成「跟著做」的 OrderResponse，再寫 OrderRequest（customerId 正整數、items 至少一項，每項 productId 正整數、quantity 至少 1 的整數；note 選填、最多 200 字；pickupAt 選填、要帶時區位移）與 ApiErrorBody（code、message 都是必填字串）。每一個都同時匯出 schema 和同名型別。
  • OrdersController 的下單改用 @Body({ schema: OrderRequest })，不再用 CreateOrderDto；OrdersService.create 的參數型別改成契約的 OrderRequest。POST /orders 和 GET /orders/:id 回傳符合 OrderResponse 的物件（orderedAt 等時間是 ISO 字串）。三個 NotFoundException 都改成 { code, message }。改完刪掉用不到的 create-order.dto.ts，並把 docs/KNOWN_ISSUES.md 的「數量 0」一節拿掉（已經修好了）。
  • 前台：web/src/api/orders.ts 從 shared/contract.ts import，createOrder、getOrder 都用 safeParse 檢查回應，不符合就丟錯。刪掉 web/src 裡手寫的 Order、OrderRequest（只多 import 契約、留著自己的 interface 不算）。
  • 判分：quantity 是 0、-1、1.5 都要 422，body 符合 ApiErrorBody；假的 fetch 回傳 total: "160" 時 createOrder 要丟錯。

練習 2：把 note 改名為 customerNote，做「同時支援新舊」這一步。

  • 契約的 OrderRequest、OrderResponse 改成 customerNote，OrderRequest 裡不能再有 note。結帳頁的欄位改叫「顧客備註」，送 customerNote（型別檢查會告訴你要改哪裡）。
  • API 用 OrderRequest.extend(…) 另外接受 note（一樣最多 200 字）。只送其中一個、或兩個相同都能下單，備註存進 orders.note；兩個都送而且不同回 422 { code: 'FIELD_CONFLICT', message }，不建立訂單。
  • 請求裡有 note（包括兩個相同時）回應加 Deprecation 標頭（@ 加 Unix 秒數），並寫一行含 note 的 warn log；只送 customerNote 時兩者都不能有。
  • POST /orders 與 GET /orders/:id 的回應同時有 customerNote 與 note；在相容程式旁邊用註解寫上移除條件（判分會找含「移除」的註解）。

練習 3：在 release-plan.json 排出 CAFE-18 的發布計畫。

  • steps：把 deploy-api-both、deploy-web-new、wait-old-field-zero、remove-old-field 排成正確的順序，每一步的 safeBecause 用一兩句說明這一步上線後，線上的新舊組合為什麼不會出事（判分只檢查有沒有填）。
  • watchLog：等待時要搜尋的那段文字，從練習 2 的 logger.warn(…) 複製一段固定的部分，至少 8 個字、含 note，不含 ${…} 的動態值（判分會在 api/src 的 warn( 呼叫裡找它）。只寫 note 的話，搜尋結果會混進一堆無關的 log。quietDays：log 連續幾天是 0 才移除，正整數。

練習 4：你把 API 的 note 直接改名為 customerNote，新前台也在同一分鐘上線。誰會出問題？

✓ a。部署只換掉伺服器上的檔案，已經載入的 SPA 會繼續用舊格式呼叫 API，直到顧客重新整理；而且 z.object 會默默丟掉 note，連錯誤都沒有。b：前後端不會在同一瞬間更新，快取和開著的分頁都會造成混用。c、d：問題跟裝置和新舊顧客無關，只跟瀏覽器裡跑的是哪一版程式有關。

練習 5：什麼時候可以移除 API 對 note 的支援？

✓ d。要用資料判斷舊客戶端是不是已經消失。a：上線當天正是舊分頁最多的時候。b、c：這些是流程上的時間點，跟還有沒有人在送 note 無關。

練習 6：前後端共用同一份 zod schema，主要的好處是什麼？

✓ b。型別（z.infer）和執行時檢查（safeParse）來自同一份定義，不會一邊改了另一邊沒跟上。a：它只保證格式，不保證畫面與流程正確，測試照樣要寫。c、d：跟打包大小和效能無關，前台反而多帶了 zod。

常見錯誤

  • 以為前後端會同時更新：開著的分頁、快取、單獨回滾都會造成新舊混用。每次改契約都問「新 API＋舊前端」和「舊 API＋新前端」各會怎樣。
  • 前端用型別斷言假裝回應一定符合：api<OrderResponse>() 或 as 只騙過編譯器。用 safeParse 檢查，不符合就明確丟錯。
  • 直接改名，以為 422 會擋下舊請求：z.object 預設丟掉不認得的欄位，舊前端得到 201，資料卻不見了。改名先 expand，舊欄位在相容期間照樣接受。
  • 兩個欄位都送時默默挑一個：另一個值消失，沒人知道。不同就回 422 FIELD_CONFLICT。
  • 相容程式沒寫移除條件：永遠留在程式裡，沒人敢刪。寫清楚看哪一行 log、連續幾天是 0 就刪，並開一張後續的單。
  • 沒有量測舊欄位的使用量：只能靠感覺決定何時移除。收到舊欄位就寫一行固定格式的 warn log。

小結

  • 前端和 API 不會同時更新：開著的分頁、CDN 快取、單獨回滾，都會讓新舊版本混用一段時間。
  • 把請求、回應、錯誤寫成 shared/contract.ts 的 zod schema：API 用 @Body({ schema }) 驗證，前台用 z.infer 的型別寫程式、用 safeParse 檢查回應；錯誤一律是 { code, message }。
  • z.object 會默默丟掉不認得的欄位，所以直接改名會讓舊前端的資料消失而且不報錯。
  • 改名用 expand → migrate → contract：API 先同時接受新舊、回應兩個都回、收到舊欄位加 Deprecation 標頭和 warn log；資料庫欄位不用跟著改名。
  • 發布順序：API（同時支援）→ 前台（送新欄位）→ 等 warn log 連續一段時間為 0 → 移除舊欄位。每一步都要說得出線上的新舊組合為什麼安全，以及回滾能退到哪一版。

這個階段的重點整理成一頁圖解。
