階段 2：修問題 · 第 5 課

沒有重現步驟的 bug：從使用者回報與 log 找證據、重現、修復、補回歸測試

中午客服轉來 BUG-31：「有客人說結帳一直失敗，可是我們自己試都正常。」沒有訂單內容、沒有截圖，只知道「大概十點多」。最省事的回覆是「無法重現，先結案」。但客人是真的付不了錢，而且明天還會有下一位。

這一課照順序走一次真實的除錯流程，從客訴一路做到修復紀錄。

這課的路線：
  1. 「我試過了，沒問題」不是結論：自己試不出來代表什麼，下一步該去哪裡找證據（開場問題的最小答案）。
  2. 收集證據、影響範圍：用 jq 從一天份的 log 找出失敗請求的共同點，算出影響幾筆、幾個人，決定這張單有多急。
  3. 假設要寫到能被推翻：從「哪一行壞了」走到「什麼條件下會壞」，再拿證據去對。
  4. 先寫會失敗的測試、修 API：怎麼證明你重現的就是這個 bug，修完又有證據可以給 PR 的審查者看。
  5. 修復紀錄：寫下什麼，下一個人遇到才不用重查一次。
這課會用到：
  • 系統設計課第 21 課的除錯方法：觀察、提出假設、做實驗驗證、逐步縮小範圍，不靠猜。
  • DevOps 課第 21 課的 JSON log：一行一個 JSON，用 jq 篩選、統計；同一個請求的每一行都帶同一個 requestId（jq 的基本語法在 DevOps 課第 2 課）。
  • 工程實務課第 6 課的「先用測試鎖住行為」：改程式之前先寫測試記錄現在的行為，改完再跑一次，才知道改到了什麼。

「我試過了，沒問題」不是結論

重現步驟（steps to reproduce）是「照著做一定會看到這個錯誤」的操作順序。客訴幾乎不會附上它：客人不知道哪個細節重要，客服也只能轉述。客服用店裡的平板點拿鐵和可頌，結帳成功，於是說「我們試都正常」。

這只證明了一件事：客服的條件跟客人不同。可能不同的地方很多：購物車裡的商品、哪一位顧客、什麼時間、頁面開了多久、用的是哪一版前端。猜下去沒有盡頭，所以下一步不是再試一次，而是去看客人當時真正送出了什麼。那份紀錄就在 log 裡。

也先翻一下團隊已經知道的問題。docs/KNOWN_ISSUES.md 裡有第 1 課記下的「下架商品會 500」。它可能就是 BUG-31，但現在還只是猜測：客人說的「失敗」也可能是格式錯誤、時段額滿，或別的事。要用證據確認，不能直接套用。

收集證據：從 log 找出失敗的請求

log 檔是 NDJSON（newline-delimited JSON）：一行一個完整的 JSON 物件。這是 Nest 的 ConsoleLogger 開了 json: true 之後的格式（NestJS 12.3.2，見 NestJS 課第 24 課），main.ts 已經改成這樣。每個請求結束時，request-log middleware 會寫一行 context 是 HTTP 的 log：

{"level":"log","pid":1,"timestamp":1793585561227,"message":{"requestId":"a5dbfc84-…","method":"POST","path":"/orders","status":500,"durationMs":12,"customerId":2,"productIds":[2,6]},"context":"HTTP"}
  • timestamp 是 Unix 毫秒，一律是 UTC。台北時間要加 8 小時。
  • message 是 middleware 傳給 logger 的物件，所以可以直接查 .message.status。
  • requestId 同時放在回應標頭 x-request-id：客人或前端回報這個值，就能直接找到那一行。

跟著做：先看整體，再縮小

macOS 內建 jq（/usr/bin/jq，jq 1.7.1）。第一步先看每種狀態碼各有幾個，知道有哪些錯誤：

jq -r 'select(.context == "HTTP") | .message.status' logs/api-2026-11-02.ndjson | sort | uniq -c
 302 200
  99 201
   1 404
   3 422
   6 500

select(條件) 只留下符合的行；-r 印出不帶引號的原始值；sort | uniq -c 數每個值出現幾次。今天有三種錯誤。把它們的時間列出來，.timestamp / 1000 | todate 把毫秒轉成秒，再轉成 ISO 8601 的 UTC 時間：

jq -c 'select(.context == "HTTP" and .message.status >= 400) | {time: (.timestamp / 1000 | todate), status: .message.status, path: .message.path}' logs/api-2026-11-02.ndjson
{"time":"2026-11-02T01:37:40Z","status":404,"path":"/orders"}
{"time":"2026-11-02T02:12:41Z","status":500,"path":"/orders"}
{"time":"2026-11-02T02:12:58Z","status":500,"path":"/orders"}
{"time":"2026-11-02T02:13:30Z","status":500,"path":"/orders"}
{"time":"2026-11-02T02:20:05Z","status":422,"path":"/orders"}
{"time":"2026-11-02T02:47:05Z","status":500,"path":"/orders"}
{"time":"2026-11-02T02:47:19Z","status":500,"path":"/orders"}
{"time":"2026-11-02T03:05:44Z","status":422,"path":"/orders"}
{"time":"2026-11-02T03:31:52Z","status":500,"path":"/orders"}
{"time":"2026-11-02T03:40:10Z","status":422,"path":"/orders"}

02:12:41Z 是台北的 10:12:41，跟客人說的「十點多」對得上。這段時間裡 500 和 422 混在一起，但它們不是同一種問題：422 是請求格式不對（例如數量 0，第 4 課的契約擋下來的），系統有正確地拒絕；500 是伺服器自己出錯。把不同的錯誤混在一起分析，找到的「共同點」就會是錯的，所以接下來只看 500。

錯誤特徵：這 6 個 500 是同一個問題嗎

500 的時候，Nest 內建的例外處理（ExceptionsHandler）會寫一行 level 是 error 的 log，裡面有錯誤名稱、訊息和 stack（Nest 預設怎麼處理沒接住的例外見 NestJS 課第 8 課，stack 怎麼讀見 NestJS 課第 25 課）。錯誤特徵（error signature）是把同一類錯誤歸在一起的特徵，最常用的是「錯誤類型＋訊息＋丟出錯誤的程式位置（stack 的第一行）」。把每一個 500 的特徵印出來數一數：

jq -r 'select(.level == "error") | "\(.error.name): \(.error.message) @ \(.error.stack | split("\n")[1] | ltrimstr("    at "))"' logs/api-2026-11-02.ndjson | sort | uniq -c
   6 TypeError: Cannot read properties of undefined (reading 'price') @ file:///srv/cafe/api/src/orders/orders.service.ts:27:41

6 個都一樣：同一個錯誤、同一行程式。如果這裡出現兩三種特徵，就代表有兩三個 bug，要分開處理、分開算影響。正式機用 node --enable-source-maps 啟動，所以 stack 指到的是 TypeScript 原始檔的行號，不是編譯後的 .js。

影響範圍：幾筆、幾個人、從什麼時候開始

影響範圍（blast radius）是這個問題影響了多少請求、多少顧客、在哪一段時間。它決定這張單有多急，也決定修好之後要不要通知誰、要不要補償。要分清楚兩個數字：

  • 失敗請求數：500 出現幾次。
  • 受影響顧客數：有幾個不同的 customerId。客人遇到錯誤會再按一次、再按一次，同一個人可能貢獻好幾筆。用請求數當人數，會把問題講得比實際嚴重，也會讓之後的補償名單出錯。

算「有幾個不同的值」要把所有行收進同一個陣列：jq -s（slurp）把整個檔案讀成一個陣列，之後就能用 map(…) 取出每一行的欄位、unique 去掉重複並排序、length 數個數。例如今天有幾種不同的 HTTP 方法：

jq -s 'map(select(.context == "HTTP") | .message.method) | unique' logs/api-2026-11-02.ndjson
[
  "GET",
  "POST"
]

時間要寫清楚時區。todate 印出的 2026-11-02T02:12:41Z 結尾的 Z 代表 UTC；把它當成台北時間，或把台北時間 10:12:41 後面加上 Z，都差了 8 小時。給人看的報告可以寫台北時間，但要標明；給程式讀的欄位用帶 Z 或 +08:00 的 ISO 8601。

假設要寫到能被推翻

知道「哪裡壞」（第 27 行讀 .price）還不夠，要知道「什麼條件下會壞」，才能重現，也才能判斷修法對不對。這一步要提出假設。可推翻的假設（falsifiable hypothesis）是寫得夠具體、可以拿證據證明它錯的假設：

假設能不能推翻
「應該是網路不穩」不能。不管 log 長怎樣都說得通，等於沒說
「2 號顧客的帳號有問題」能，而且被推翻了：失敗的有 2、4、5 號三個人
「只要訂單裡有起司蛋糕（6）就會 500」能，而且被推翻了：上午 08:52、09:58（台北）兩筆含 6 的訂單都是 201
「購物車裡有已下架的商品就會 500」能。預測：失敗的請求都含同一個下架商品、都發生在它下架之後；同一位顧客拿掉它就會成功

拿最後一個去對證據。data/product-changes.json 記著起司蛋糕在 10:05（台北）因為售完被店員下架；6 筆 500 全部含 6、全部在 10:05 之後；4 號顧客 10:47 兩次失敗，10:49 只點可頌（5）就成功了。每一個預測都對得上，而且跟第 1 課記的已知問題一致：菜單已經不顯示下架商品，但頁面開著沒重新整理的顧客，購物車裡還留著它。客服用的平板剛打開頁面，購物車裡沒有下架商品，所以「試都正常」。

💡 實務上：先寫下假設，再去查
除錯卡住時，通常是在沒有假設的情況下到處翻 log。資深工程師會在 bug 單上先寫一句「我認為是 X，因為 Y；如果是 X，應該會看到 Z」，然後只去查 Z。查到 Z 不成立就劃掉換下一個。這樣同事接手時知道哪些方向已經排除，自己也不會在同一個死胡同繞兩次。

先寫一個會失敗的測試

現在知道條件了，在本機用 curl 就能重現（第 1 課的那一行，7 號桂花烏龍在種子資料裡就是下架的）。但先別急著改程式，先把重現寫成測試。回歸測試（regression test）是重現過去某個 bug 的測試：bug 修好後它會通過，之後有人改壞同一個地方，它會再失敗。先寫、而且要先看到它失敗，原因有兩個：

  • 證明你重現的就是這個 bug。測試在有 bug 的程式上失敗、失敗的原因跟 log 一樣（500），才代表它抓到的是同一件事。一個一開始就通過的測試，什麼都證明不了。
  • 修完有證據。同一個測試從失敗變成通過，就是「真的修到了」的證據，PR 上也可以直接指著它說。

範本 api/src/orders/orders.unavailable.spec.ts 已經寫好啟動 app 的部分：用 Test.createTestingModule 建出整個 AppModule、關掉 log、跑完關閉，跟 NestJS 課第 10 課的 e2e 測試一樣。裡面的 it.todo('TODO') 是「還沒寫的測試」佔位，執行時只列成 todo、不算通過也不算失敗。你要寫的是 it(…) 本身：用 supertest 送出含下架商品的訂單，斷言修好之後應該看到的結果。斷言要寫得夠精確：只寫 expect(res.status).not.toBe(201) 的話，現在的 500 也符合，測試在有 bug 的版本就會通過，等於沒重現。

寫好之後執行 npm test，應該看到它失敗，而且失敗的原因是 500：

npm test

 ❯ api/src/orders/orders.unavailable.spec.ts (1 test | 1 failed) 354ms
   ❯ BUG-31 購物車裡有下架商品 (1)
     × 含下架商品的訂單回 409 PRODUCT_UNAVAILABLE 並列出商品 id 140ms

AssertionError: expected 500 to be 409 // Object.is equality

如果它失敗在別的地方（例如 Cannot find module 或連不上資料庫），那是測試本身還沒寫好，不算重現。npm test 用的是 api/.env 的開發資料庫 cafe，所以要先 npm run db:setup 過（第 1 課做過就不用再做）。

修 API：下架商品回 409 PRODUCT_UNAVAILABLE

先決定 API 應該回什麼，再寫程式：

  • 狀態碼 409 Conflict：請求格式沒錯（不是 422），商品也存在（不是 404），是商品現在的狀態不允許這個操作。跟第 3 課的時段額滿 SLOT_FULL 同一類。
  • body 照第 4 課的錯誤契約：{ code: 'PRODUCT_UNAVAILABLE', message, details: { productIds } }。code 給程式判斷，message 給人看；多帶的 details.productIds 讓前台之後可以標出要移除哪幾項。契約的 ApiErrorBody 只有 code、message，z.object 解析時會略過多的欄位，所以舊前台不受影響；前台真的要用 details 時再加進契約。
  • 列出全部下架的商品，不是只回第一個。顧客移除一項、送出、又被擋下一次，體驗比一次說完差很多。
  • 不要默默略過下架商品照樣建立訂單。顧客以為點了蛋糕，到櫃台才發現沒有，這比錯誤訊息更糟。

程式的改法：把「先數有幾個商品存在、再只查 available: true」改成查一次購物車裡所有的商品，存在性與上下架都從這份結果判斷。NotFoundException 的那一行保留（不存在的商品仍然是 404），接著挑出 available 是 false 的，有的話丟 ConflictException。跟第 4 課一樣，傳物件給例外，Nest 就把整個物件當成回應 body。修好後送同一個請求：

curl -s -X POST http://localhost:3100/orders -H 'Content-Type: application/json' \
  -d '{"customerId":1,"items":[{"productId":1,"quantity":1},{"productId":7,"quantity":1}]}'
{"code":"PRODUCT_UNAVAILABLE","message":"桂花烏龍（季節限定） 已下架，請從購物車移除後再送出","details":{"productIds":[7]}}

前台不用改就會變好：第 4 課的 api() 會用 ApiErrorBody 解析錯誤，結帳頁顯示 message。原本的 500 body 是 Nest 預設的 {"statusCode":500,"message":"Internal server error"}，沒有 code，所以畫面只顯示 HTTP 500，就是客人說的「一行英文」。再跑一次 npm test，同一個測試變成通過。

💡 實務上：API 是信任邊界，前端的檢查只是體驗
信任邊界（trust boundary）是外部資料進入系統的地方，過了這裡的資料都要自己檢查，第 7 課審查 PR 時會再用到。常見的提議是「前端送出前比對一下菜單就好」。這可以讓體驗更好，但擋不住問題：開著的舊分頁、別的客戶端（店內 POS、之後的 App）、「檢查完的那一秒剛好被下架」，請求都還是會到 API。API 對任何輸入都要回明確的 4xx，而不是 500。一個 500 在監控上代表「伺服器壞了」，值班的人會被叫起來；一個有 code 的 409 代表「系統照規則拒絕了」，前端也能做對應的處理。

修復紀錄：讓下一個人不用重查一次

修完之後寫一份短短的紀錄，放在 docs/bugs/BUG-31.md，PR 說明也可以直接連過去。範本有五節，每節幾行「- 欄位：值」：

  • 現象：顧客看到什麼、錯誤特徵是什麼（下次在 log 看到同樣的特徵，就知道查這份）。
  • 影響範圍：時間、失敗請求數、受影響顧客數，都寫數字。「少數使用者」沒辦法讓 PM 判斷要不要聯絡客人。
  • 根因：檔案:行號，加上一兩句為什麼會出錯。行號寫有 bug 的版本（start 版本）裡的那一行，也就是 stack 指到的那一行；修完之後行號會變，所以要說清楚是哪一版。
  • 修正：改了什麼行為（回 409、列出全部、不建立訂單），不是貼程式碼。
  • 預防：回歸測試的名稱（一字不差，別人才搜得到），以及其他可以更早發現的做法。「加強測試」不算，沒有人能檢查它做了沒有。

修好之後，記得把 docs/KNOWN_ISSUES.md 的「下架商品」一節拿掉，改成指到這份紀錄。

💡 實務上：修好之後還要回覆客服
bug 單不是程式合併就結束。回覆客服時用他們看得懂的話說明原因（「早上起司蛋糕售完下架，購物車裡還放著它的客人會送不出訂單」）、哪一天上線修正、受影響的是哪幾位顧客。影響範圍算出了 3 位顧客、時間點也有，客服或店長就能決定要不要主動聯絡、送一張折價券。這也是影響範圍要算人數而不是請求數的原因。

練習

三題都在 delivery/practice/work/05 裡做，寫完回到 learn/ 執行 node check.mjs delivery 05。判分會先跑 tsc 與 vue-tsc，再重建判分用的資料庫。練習 2 會把你的 spec 跑兩次：一次在 start 版本（有 bug）、一次在你修好的版本。

練習 1：分析 logs/api-2026-11-02.ndjson，填好 evidence.json。

  • requestIds：所有 POST /orders 回 500 的 requestId（字串陣列）。不要混進同時段的 422 和 404。
  • firstSeen、lastSeen：第一筆與最後一筆 500 的時間，ISO 8601 字串，帶 Z 或 +08:00（毫秒可以省略）。todate 印出來的直接貼上就對。
  • affectedCustomers：受影響的不同顧客有幾位（數字）。提示：jq -s 加上 map、unique、length。
  • productIds：每一筆失敗請求都含有的商品 id（數字陣列）。只出現在部分請求裡的不算共同點。

常見錯誤

  • 自己試一次正常就說無法重現：只證明了你的條件跟客人不同。去 log 找客人當時送出的請求。
  • 把所有錯誤混在一起分析：同時段的 422 是格式錯誤、系統有正確拒絕，混進來會找錯共同點。先按狀態碼與錯誤特徵分組，一次只看一組。
  • 用請求數當影響人數：同一位顧客會重試好幾次。人數要算不同的 customerId。
  • 時間沒寫時區：log 的時間是 UTC，客人說的是台北時間。寫 10:12:41Z 會差 8 小時。
  • 假設說不出怎麼推翻：「網路不穩」「偶發」什麼都解釋得通，也就什麼都沒解釋。寫成「如果是 X，就會看到 Z」。
  • 測試的斷言太寬：not.toBe(201) 在有 bug 的版本也會通過。斷言修好之後才成立的結果，並親眼看它先失敗一次。
  • 修了 bug 沒補回歸測試：下次有人重構 create()，同一個 500 會再回來，而且沒有人知道。
  • 把下架商品默默略過：訂單成立了，顧客要的東西卻不在裡面。明確拒絕，並告訴他是哪幾項。

小結

  • 沒有重現步驟時，從客人當時的請求找條件：先按狀態碼分組，再看錯誤特徵（類型＋訊息＋stack 第一行），確認是一個問題還是好幾個。
  • 影響範圍要有數字：失敗請求數、不同顧客數、帶時區的時間區間。人數和請求數不一樣。
  • 假設要寫到能被證據推翻，再拿證據去對：只有含 6 不夠，要在下架之後、拿掉就成功，三點都成立。
  • 先寫在有 bug 的程式上會失敗的回歸測試，看它因為同一個原因失敗，再修；修完它通過就是證據。
  • API 是信任邊界：下架商品回 409 PRODUCT_UNAVAILABLE，列出全部下架的品項，不建立訂單，不回 500。
  • 修復紀錄寫現象、影響範圍、根因（檔案:行號）、修正、預防（回歸測試的名稱），讓下一個人不用重查一次。
