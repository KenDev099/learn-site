階段 4：上線與維運 · 第 13 課

期末專題：獨立交付一個跨層需求，附驗收報告與自評

店長開了一張新的需求單 CAFE-50：客人付完款，可以在訂單頁自己取消，錢自動退回。聽起來只是「加一個按鈕」，實際上它同時碰到前面每一課處理過的難題：取消要退款（第 8 課的冪等與結果不明）、付款送的點數要扣回（第 9 課的補償紀錄）、預約的時段要空出名額（第 3 課的容量）、只能取消自己的訂單（第 12 課的擁有者檢查），還要跟吧台的「開始製作」搶同一張訂單。

這一課沒有新的大觀念。你要一個人把這張單從規則做到畫面，最後交一份驗收報告：做了什麼、用什麼證明、還有什麼風險，加上一份有證據的自評。這是資深工程師每次交付都在做的事：不是「我寫完了」，而是「這是它可以上線的證據」。

這課的路線：
  1. 先把規則變成例子、交付清單：開工前怎麼把會議紀錄寫成能直接變成測試的例子，整張單照什麼順序做。
  2. 取消的核心：客人按取消、吧台按開始製作同時發生時，怎麼保證只有一邊成功。
  3. 退款、點數與時段：退款為什麼放在交易外面、用固定的冪等鍵；送出的點數和佔掉的名額怎麼用補償還回去。
  4. 畫面：取消按鈕什麼時候出現，確認視窗為什麼用原生的 <dialog>。
  5. 驗收報告、自評與提交前自審：交付時怎麼拿出「它可以上線」的證據，再用審查別人的順序審自己。
這課會用到：
  • 第 3 課的條件式更新：把「現在的狀態」寫進 UPDATE 的 WHERE，看改到幾列判斷誰先搶到；時段名額記在 pickup_slots。
  • 第 8 課的冪等鍵與「結果不明」：同一把 key 的請求 CafePay 只處理一次；逾時、斷線不等於失敗，要當成結果不明處理。
  • 第 9 課的補償紀錄：point_entries 只新增、不修改，扣回點數是寫一筆負數紀錄，用 reversal_of 指向被抵銷的那一筆。
  • 第 12 課的 SEC-7（BOLA 修正）：先確認有登入（沒登入回 401），再檢查訂單是不是本人的，別人的訂單回 404。

先把規則變成例子，再寫程式

最常見的失敗是一讀完需求單就開始寫 controller。寫到一半才發現「製作中的單能不能取消？」「按兩次會不會退兩次？」，只好邊寫邊猜。第 2 課的做法是先把規則寫成可執行的驗收條件：每一條 Given／When／Then 都附上具體的例子，例子能直接變成測試。

會議紀錄的規則可以濃縮成兩個輸入：訂單的狀態（status）和按取消的顧客是不是下單的本人（actorIsOwner；false 指另一位顧客。會議紀錄第 1 條的「店員代取消」沿用同一個端點，這次不寫成例子），結果只有四種：

expect意思API 的樣子
refund取消成功並全額退款、扣回點數、釋放時段200，回取消後的訂單
not_cancellable不能取消（吧台已經開始做、還沒付款）409 ORDER_NOT_CANCELLABLE
not_found不是自己的訂單：就像它不存在404
already_cancelled已經取消過了：不是錯誤，也不再退款200，回目前的訂單

這張表就是判分用的「標準答案函式」：給它 { status, actorIsOwner }，它照會議紀錄算出結果。你寫的每個例子都會丟進去比對，對不上就代表你對規則的理解跟店長不同，這正是要在寫程式之前抓到的。

交付清單：每一步都在前面做過

例子定好之後，整張單照下面的順序做。整個交付流程在工程實務課第 10 課走過一次，這次是在真的程式庫上做：

順序交付物用到哪一課

2POST /orders/:id/cancel 與它的測試第 3 課（條件式更新、時段）、第 8 課（冪等鍵）、第 9 課（補償紀錄）、第 12 課（擁有者檢查）

取消的核心：一次條件式更新決定誰先

會議紀錄第 6 條：客人按取消和吧台按開始製作同時發生，只能有一個成功。直覺的寫法是「先查、再改」（findVisible 是 src/orders/orders.service.ts 裡現成的方法：照登入者讀一張訂單，店員看得到全部，顧客讀到別人的訂單回 404）：

const order = await this.findVisible(id, account)
if (order.status !== 'paid') throw new ConflictException(…)   // ① 檢查：是 paid
await this.refund(id)                                          // ② 呼叫 CafePay，花幾百毫秒
await this.prisma.order.update({ where: { id }, data: { status: 'cancelled' } })   // ③ 改狀態

問題在 ① 和 ③ 之間。吧台的「開始製作」（kitchen.module.ts 的 start()）在這段時間把訂單改成 preparing，兩邊都回 200：吧台在做一杯已經退款的拿鐵。這跟第 7 課審查優惠券時看到的「先查再寫」是同一種問題，中間還夾了一個網路呼叫，時間窗更大。

正確的做法跟吧台的 start() 一樣，用條件式更新：updateMany({ where: { id, status: 'paid' }, data: { status: 'cancelled' } })，回傳的 count 是改了幾列。是 1 代表你贏了；是 0 代表狀態已經不是 paid，再讀一次訂單看它現在是什麼：cancelled 就回目前的訂單（重複取消），其他狀態回 409。第 3 課佔時段名額也是這個寫法。

贏了之後要做的事（寫補償點數、釋放時段）跟狀態改變放在同一個交易：其中一步失敗就整個回滾，不會有「狀態改了、點數沒扣」的半套結果。

退款：在交易外面，用固定的冪等鍵

退款是呼叫外部服務，不能放在資料庫交易裡：交易回滾收不回已經退出去的錢，而且等網路回應的時間會一直占著鎖。所以順序是：先在交易裡把狀態改成 cancelled，提交之後再退款。

這帶來兩個情境，都靠第 8 課的冪等鍵（Idempotency-Key）處理：同一把 key 的請求，CafePay 只會處理一次，之後回傳第一次的結果。

  • 客人連按兩次、或同時送出好幾次：只有一個請求贏得條件式更新，其他的看到 cancelled。如果它們也呼叫退款，只要 key 相同，CafePay 也只退一次。
  • 退款結果不明（逾時、5xx）：可能已經退了，也可能沒有。不能當作失敗再換一把 key 退，也不能當作成功。付款維持 paid，客人再按一次取消時，看到訂單已經 cancelled、付款還沒退，就用同一把 key 再問一次，CafePay 會回第一次的結果。

所以 key 必須從業務資料推出來，例如 refund:${orderId}（一張訂單只會全額退一次）。用 randomUUID() 或時間當 key，每次重試都是一筆新的退款。退成功之後把付款標成 refunded，之後就不會再呼叫。

💡 實務上：先改狀態再退款，要想清楚中間斷掉怎麼辦
「資料庫改了，外部呼叫沒成功」是每個金流、寄信、通知功能都會遇到的問題。資深工程師會先寫下每個中斷點的狀態：狀態是 cancelled、付款是 paid，就代表「該退還沒退」，這個組合本身就是待辦清單。這次靠客人再按一次重試；正式上線前通常會讓排程（像 npm run reconcile）定期找出這種訂單補退款，並在每日對帳裡檢查。做不完的部分不要藏起來，寫進驗收報告的「已知限制」。

點數與時段：補償，不是刪除

點數：付款成功時寫了一筆 order_paid（每 10 元 1 點，110 元送 11 點）。取消時不能刪掉或改掉它：point_entries 只新增、不修改，這是第 9 課建立的規則，刪掉就看不出「曾經送過、後來因為取消扣回」。做法是寫一筆補償紀錄：

{ customerId, orderId, points: -11, reason: 'order_cancelled', reversalOf: <order_paid 那一筆的 id> }

reversal_of 有唯一限制，一筆紀錄最多被抵銷一次：就算程式哪裡寫錯、跑了兩次，資料庫也會擋下第二筆。顧客如果已經在櫃台把點數兌換掉，扣回後可能變成負數，會議紀錄沒有規定，這種問題就寫進已知限制，讓店長之後決定。

時段：有 pickupAt 的訂單，在同一個交易裡把 pickup_slots 那一列的 orders 減 1（加上 AND orders > 0，避免變成負數）。忘了這一步，那個時段會永遠少一個名額，而且沒有任何錯誤訊息。

擁有者檢查：端點加 @UseGuards(LoginGuard)（LoginGuard 定義在 src/auth/auth.module.ts：讀 cookie 找出現在是誰，沒登入回 401，GET /orders/:id 已經在用），用 findVisible(id, account) 讀訂單：別人的訂單回 404，跟 GET /orders/:id 同一套規則（第 12 課的 SEC-7）。用 findOne 就會讓任何登入的人取消別人的訂單。

畫面：按鈕只在可以取消時出現，先確認再送出

前台三件事：web/src/api/orders.ts 加 cancelOrder(id)（API 回的是訂單，跟 getOrder 一樣先過契約）；OrderStatusPage.vue 只在 status === 'paid' 時顯示「取消訂單」；按下去先開確認視窗。

確認視窗用原生的 <dialog>，呼叫 showModal() 打開。瀏覽器會幫你做好無障礙需要的事：焦點移進視窗、視窗外的內容不能操作（inert）、按 Esc 關閉，螢幕閱讀器把它當成對話框（MDN 的 dialog 文件）。不要用 window.confirm()：它會擋住整個頁面、樣式改不了，也沒辦法寫清楚「會全額退款 110 元」。

<button v-if="order.status === 'paid'" type="button" @click="confirmDialog?.showModal()">取消訂單</button>
<dialog ref="confirm" aria-labelledby="cancel-title">
  <h2 id="cancel-title">確定要取消訂單嗎？</h2>
  …
</dialog>

confirmDialog 用 Vue 3.5 的 useTemplateRef<HTMLDialogElement>('confirm') 拿到。剩下的你自己寫：「確定取消」送出請求、「先不要」關掉視窗；成功後用 API 回傳的訂單更新畫面，顯示「已取消，款項將退回」；409 時把 API 的 message 顯示出來，並重新讀一次訂單，讓按鈕跟著新狀態消失。

💡 實務上：前端隱藏按鈕不等於安全
「製作中不顯示取消按鈕」是為了使用者體驗，不是規則的執行點。客人的頁面可能開了十分鐘沒重新整理，按鈕還在，吧台早就開始做了；也有人會直接用 curl 打 API。規則一定在後端（條件式更新）執行一次，前端只負責把後端的答案（409 與原因）好好地顯示出來。審查前端 PR 時看到「用 v-if 擋住就好」，要問後端有沒有同樣的檢查。

驗收報告與誠實的自評

驗收報告（acceptance report）是交付時給審查者、PM 看的文件：做了什麼、怎麼證明、還有什麼風險。report.md 的範本有四段：

  • 範圍：做了什麼（API、畫面、測試），以及明確不做什麼（會議紀錄的「先不做」）。寫出不做的事，審查者才不會以為你漏了。
  • 測試證據：每一條驗收條件對到一個測試名稱。判分會真的跑你的 npm test，名稱要跟 it('…') 一字不差，而且通過。「我有測」不是證據，「AC2 對到這個通過的測試」才是。
  • 已知限制：還沒處理的狀況與原因，例如退款結果不明時誰來補。
  • 自評：用固定的自評量表（self-assessment rubric），三個面向各給 1–4 分並附證據。
分數意思
1沒做完
2做完，但缺測試證據
3做完，每條驗收條件都有通過的測試
43 之外，並發、重試、失敗的情境也有測試證明

三個面向：範圍（會議紀錄的規則都做到了嗎）、測試證據（每條規則都有測試證明嗎）、上線風險（上線後可能出什麼事、有沒有處理）。判分會另外跑一次隱藏的並發檢查（同時取消 10 次、取消與開始製作同時送出）：沒通過卻給了 4 分，練習 4 就不會過。自評的價值在於讓審查者快速判斷可以信任到什麼程度：有證據的 3 分，比沒有證據的 4 分有用得多；誠實寫出的限制，是上線前就能處理的風險。

💡 實務上：報告寫給沒參與的人看
PM 要知道能不能跟店長說「可以上線了」，客服要知道客人問「錢什麼時候退」怎麼回，下一個接手的人要知道哪裡還沒做完。報告裡的每一句都指到可以查證的東西（測試名稱、檔案、指令），半年後有人問「當初為什麼退款結果不明時不自動重試」，答案就在已知限制裡。很多團隊把這份報告直接貼在 PR 說明（第 2 課的五段範本）的「如何驗證」與「風險與回滾」兩段。

提交前：用審查別人的順序審自己

送出之前，把自己的 diff 當成別人的 PR，照第 7 課的順序看一遍：

  1. 需求：會議紀錄的 7 條決定都做到了嗎？有沒有順手改了不相關的東西（例如格式化了整個檔案）？有的話拆出去。
  2. 金額與信任邊界：退款金額來自付款紀錄，不是請求送來的值嗎？退款的 key 是固定的嗎？
  3. 並發：每個改狀態的地方是不是條件式更新？交易包住了所有該一起成功的寫入嗎？
  4. 安全：端點有 LoginGuard 嗎？讀訂單用的是 findVisible 嗎？畫面有沒有用 v-html 顯示 API 的文字？
  5. 測試：每條驗收條件都有測試、名稱以 AC 開頭嗎？並發和逾時有測嗎？先看過它們失敗嗎？

風格最後才看，自己的程式也一樣。

練習 5：顧客按取消的同時，吧台按了開始製作。正確的結果是？

✓ c。兩個動作改的是同一筆訂單的狀態，要在資料庫裡原子地決定（WHERE status = 'paid'，看影響了幾列）。a 會讓吧台做一杯已經退款的飲料；b「最後寫入為準」一樣會兩邊都以為成功；d 不符合店長的規則：吧台已經開始做，就不能取消。

練習 6：顧客連按兩次「取消訂單」。正確的結果是？

練習 7：自評時，哪一種寫法最有價值？

✓ d。自評的目的是讓審查者快速判斷交付的可信度：有證據且誠實的低分，比沒有證據的高分有用。a 和 b 會讓審查者不再相信你的報告；c 沒有固定的標準，沒辦法跟上一次比較，也看不出風險在哪裡。

常見錯誤

  • 一開始就寫程式：沒先把規則寫成例子，邊寫邊猜「製作中能不能取消」。先完成驗收條件，例子對過會議紀錄再動手。
  • 先查狀態再更新：檢查和修改之間（尤其中間夾了退款呼叫）吧台已經開始做，兩邊都成功。用條件式更新，看影響了幾列。
  • 退款放在資料庫交易裡：交易回滾收不回已經退的錢，等網路的時間還占著鎖。先提交狀態，再退款。
  • 退款的 key 每次都不一樣：重複點擊或重試時退兩次款。key 從訂單 id 推出來。
  • 退款結果不明就回 500 或當作失敗：客人以為沒取消，或之後換一把 key 又退一次。付款維持原狀，用同一把 key 重試。
  • 刪掉點數紀錄：看不出曾經送過、為什麼扣回，對帳也對不起來。寫一筆負的補償紀錄，reversalOf 指向原本那一筆。
  • 忘了釋放時段名額：那個時段永遠少一個位置，沒有任何錯誤訊息。在同一個交易裡減 1。
  • 用 findOne 讀訂單：任何登入的人都能取消別人的訂單。用 findVisible。
  • 只靠前端隱藏按鈕：頁面開著沒重新整理、或直接打 API，就繞過去了。規則在後端，前端顯示後端的答案。
  • 自評沒有證據，或跟實際結果不符：給 4 分但並發測試沒過。分數附測試名稱，沒做到的寫進已知限制。

小結

  • 交付一張跨層需求單的順序：規則寫成例子（驗收條件）→ API 與測試 → 畫面 → 驗收報告。每條驗收條件都對到一個通過的測試。
  • 改狀態用條件式更新，讓資料庫決定誰先；跟狀態一起成功的寫入（補償點數、釋放時段）放在同一個交易。
  • 外部呼叫（退款）放在交易提交之後，用由訂單決定的冪等鍵；結果不明時保留「該退還沒退」的狀態，用同一把 key 重試。
  • 點數只新增、不刪除，用補償紀錄抵銷；擁有者檢查沿用 findVisible；前端只在可以取消時顯示按鈕，用原生 <dialog> 確認，並顯示後端的錯誤。
  • 驗收報告寫範圍、測試證據、已知限制、自評；自評的每個分數都附證據，誠實比高分有用。
