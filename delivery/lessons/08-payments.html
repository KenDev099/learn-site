階段 3：錢與資料 · 第 8 課

串接付款服務：結果不明、重複通知與漏通知、對帳與補單

線上付款上線一週，會計美玲開了 tickets/CAFE-35.md：有客人被扣了兩次款，畫面卻顯示過「付款失敗」；有客人的點數加了兩次；有客人付了錢，訂單卻一直停在「待付款」；還有一筆已付款的訂單，付款紀錄後來又變成 failed。四件事都跟 CafePay（我們串接的金流商）有關，但 CafePay 每一件都照它的文件在做，問題出在我們的程式。

這一課處理串接外部付款服務最常出事的三個地方：呼叫對方時沒拿到回應、對方的通知重複或亂序、對方的通知根本沒來。串接其他外部服務（物流、簡訊、電子發票）也是同樣三個問題。

這課的路線：
  1. 付款有四種狀態：呼叫逾時或斷線時，為什麼不能當成「付款失敗」，「結果不明」要怎麼記。
  2. 冪等鍵：重試扣款時，怎麼讓金流商認出是同一筆、不會扣第二次。
  3. webhook：同一個通知來好幾次、晚到的舊通知想蓋掉新狀態，怎麼讓它只算一次。
  4. 漏通知：通知根本沒來時，補單程式怎麼主動去問，把卡住的付款救回來。
這課會用到：
  • 系統設計課第 8 課的逾時與重試：等太久就放棄這次呼叫；逾時不代表對方沒做，所以只有冪等的操作才能放心重試。
  • 系統設計課第 9 課的冪等鍵：同一把 key 的請求，對方只處理第一次，之後都回傳第一次的結果。
  • 系統設計課第 16 課的 webhook：對方主動打你的 API 通知事件；同一個事件可能送好幾次，順序也不保證。
  • NestJS 課第 15 課的交易與條件式更新：$transaction 裡的寫入一起成功或一起取消；updateMany 把目前狀態寫進 where，看改到幾列判斷有沒有搶到。

付款有四種狀態，「不知道」是其中一種

打開 payments.service.ts 的 pay()。它在資料庫建一筆 payments，呼叫 CafePay 扣款，成功就把訂單改成 paid。問題在 catch：

    } catch (e) {
      if (e instanceof HttpException) throw e
      // 沒成功就是失敗：請客人重新付款
      await this.applyPaymentResult(orderId, 'failed')
      throw new BadGatewayException({ code: 'PAYMENT_FAILED', message: '付款失敗，請重新付款' })
    }

什麼時候會進到這裡？看 cafepay.ts 的 send()：等超過 CAFEPAY_TIMEOUT_MS（預設 5 秒）還沒回應時，AbortSignal.timeout() 讓 fetch 丟出 TimeoutError；連線中斷、CafePay 回 5xx 也一樣。client 把這些都包成 CafePayUnknownError，名字已經說明了它的意思。

想一下「沒拿到回應」的時候，CafePay 那邊可能發生了什麼：

  • 請求在路上就丟了，CafePay 根本沒收到：沒有扣款。
  • CafePay 收到了，扣款成功，但回應在回來的路上丟了，或是它處理得比 5 秒久：已經扣款。

從我們這邊看，兩種情況一模一樣，都是「等了 5 秒什麼都沒拿到」。這就是結果不明（unknown）：送出了請求，但不知道對方有沒有處理。把它當成失敗，就會發生 CAFE-35 的第一件事：王小明的錢已經被扣了，畫面卻叫他重新付款，他再按一次，又扣一次。反過來把它當成成功也不行：沒付錢的訂單會被出餐。唯一誠實的答案是「還不知道」，之後再用別的方式確定。

對應到 API：卡片被拒絕是 CafePay 明確回答的，是真的失敗，回 402 CARD_DECLINED；結果不明時回 202 Accepted（「收到了，還在處理」）和 { status: 'unknown' }，controller 已經寫好這段。前台看到 unknown 顯示「付款確認中，請勿重新付款」，過幾秒重新查詢訂單狀態，不給客人「重新付款」的按鈕。

💡 實務上：呼叫外部服務，先把每一種結果分成三類
不只付款，寄簡訊、開發票、叫外送，凡是「對方會做一件改不回來的事」的 API 都一樣。接之前先列出對方會回的每一種結果，分成三類：確定成功、確定失敗（例如 4xx、明確的拒絕碼）、不知道（逾時、斷線、5xx、回應格式看不懂）。程式裡每一類各有一條路，不要用一個 catch 全部吃掉。逾時要設，而且要比前台等待的時間短；沒設逾時，一個卡住的金流請求會一直占住連線。上線後在監控上看 unknown 的比例，突然變多通常代表對方出事了，比客訴早知道。

冪等鍵：重試時讓 CafePay 認出是同一筆

不知道結果，就要再問一次。最直接的問法是用同一個請求再扣一次款，前提是 CafePay 能認出「這是剛剛那一筆」，不要真的扣第二次。這就是冪等鍵（idempotency key）：在請求標頭帶一個字串 Idempotency-Key，同一把 key 的請求，對方只處理第一次，之後都回傳第一次的結果（系統設計課第 9 課站在提供 API 的一方實作過）。CafePay 的 API 支援它，現在的程式也有傳，但傳的是：

      // 每次付款都用一把新的 key，免得跟上一次撞到
      const result = await this.cafepay.charge({ orderId, amount: payment.amount, cardToken }, randomUUID())

每次呼叫都產生新的 key，等於每次都告訴 CafePay「這是新的一筆」。冪等鍵有用的前提是：同一個意圖，不管重試幾次，key 都一樣。在這裡「意圖」是「付這張訂單的錢」，所以 key 要從訂單推出來，例如 payment:1042。

跟著做：用 curl 看 CafePay 怎麼處理同一把 key

在 work/08 執行 npm run dev（或只開假 CafePay：node cafepay/server.mjs），另開一個終端機，用同一把 key 扣款兩次：

curl -i -X POST http://localhost:3190/v1/payments \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: payment:12' \
  -d '{"orderId":12,"amount":110,"cardToken":"tok_visa"}'

兩次的回應：

HTTP/1.1 201 Created
{"id":"pay_0414a44e7791","orderId":12,"amount":110,"status":"succeeded"}
HTTP/1.1 201 Created
{"id":"pay_0414a44e7791","orderId":12,"amount":110,"status":"succeeded"}

同一個 id（你的會是別的亂碼）。CafePay 的 log 寫得很清楚：

[CafePay] 扣款 pay_0414a44e7791 訂單 12 110 元（key payment:12）
[CafePay] 重試 payment:12：回傳第一次的結果 pay_0414a44e7791（沒有再扣款）

把 key 換成一個新的 UUID 再送一次，log 會出現第二行「扣款」，id 也不一樣：同一張訂單被扣了兩次。這就是 CAFE-35 第一件事在 CafePay 那邊看到的樣子。

key 怎麼產生，三種常見寫法的差別：

key重試同一張訂單兩張不同的訂單
randomUUID()、`payment:${orderId}:${Date.now()}`每次不同，CafePay 當成新的付款，重複扣款不同，正常
固定字串 'payment'相同，正常相同，CafePay 回 422 idempotency_key_reused（同一把 key 用在金額或訂單不同的請求上）
`payment:${orderId}`相同，只扣一次不同，各扣各的

key 要從「代表這個意圖、而且重試時不會變」的資料算出來。訂單 id 存在資料庫裡，第二次呼叫 pay() 時還拿得到；UUID 或時間只活在那一次的函式呼叫裡，下一次就不見了。

把兩件事合起來，pay() 的流程是：

  1. 已經 paid：直接回 paid，不再呼叫 CafePay。已經 failed（卡片被拒絕過）：回 402，不再扣款。
  2. 還沒有付款紀錄就建一筆 pending；已經有一筆 pending 或 unknown（上次不知道結果）就沿用。
  3. 用 payment:<訂單 id> 呼叫 CafePay。拿到回答就照回答套用（applyPaymentResult）；丟出 CafePayUnknownError 就把付款標成 unknown，回 { status: 'unknown' }。其他錯誤（例如我們送錯了參數）照樣丟出。

第 2 步讓「重試」自然成立：前台顯示「付款確認中」時再呼叫一次 POST /orders/:id/pay，就是用同一把 key 問 CafePay「剛剛那筆怎麼了」。上次其實已經扣款的話，CafePay 回傳第一次的結果，訂單變 paid，只扣一次。

想親眼看 bug：在 npm run dev 開著時，先打開故障開關，讓下一筆扣款「已扣款但不回應」，而且不送 webhook（不然 1 秒後到的通知會先把結果告訴我們，看不到重試的效果）：

curl -X POST http://localhost:3190/_faults -d '{"timeoutAfterCharge":1,"dropWebhooks":1}'

接著下一張單、付款，回應裡的 id 就是訂單 id：

curl localhost:3100/orders --json '{"customerId":1,"items":[{"productId":2,"quantity":1}]}'
curl -X POST localhost:3100/orders/<訂單 id>/pay --json '{"cardToken":"tok_visa"}'

現在的程式等 5 秒後回 502「付款失敗，請重新付款」，再付一次回 200，CafePay 的 log 裡有兩行「扣款」。修好之後，第一次回 202 unknown，再付一次回 200 paid，log 只多一行「重試 … 沒有再扣款」。

卡片被拒絕後，在我們的 API 換一張卡重付，是客人的新意圖，要用新的 key（例如 payment:1042:2，第幾次嘗試存在資料庫）。沿用舊 key，CafePay 會一直回傳第一次的「被拒絕」。這一課的咖啡店規定被拒絕就到櫃台結帳，所以 API 不做換卡；遇到要做的時候記得這件事。

webhook：同一個通知會來好幾次，順序也不保證

扣款之後，CafePay 會主動呼叫我們的 POST /webhooks/cafepay 通知結果，這就是 webhook。它是「結果不明」的另一條出路：就算扣款的回應丟了，通知還是會來。CafePay 的文件（跟大多數金流商一樣）寫明了兩件事：

  • 至少一次送達（at-least-once delivery）：我們沒在時間內回 2xx，它就會重送；網路抖一下，我們處理完了它卻沒收到 200，也會重送。所以同一個通知可能來好幾次，接收端要自己去重。每個通知有一個事件編號 id（例如 evt_21b6ed1ba266），重送時不變。
  • 不保證順序：先發生的事件可能比較晚到。CAFE-35 第四件事就是這樣：客人在 CafePay 的付款頁面上第一張卡被拒絕、換一張卡成功，被拒絕的 payment.failed 在 payment.succeeded 之後才送到。

現在的 handleEvent() 收到什麼就照做：applyPaymentResult() 直接把狀態改掉、加點數，三個寫入各自獨立。同一個 succeeded 來兩次，點數加兩次（第二件事）；晚到的 failed 蓋掉 paid（第四件事）。要擋下這兩種情況，需要兩道檢查，各擋一種：

情況哪一道擋怎麼做
同一個事件（同一個 id）來第二次事件去重processed_events 的主鍵是 event_id，第二次寫不進去，整個略過
不同的事件、不同的路徑在講同一筆付款：晚到的舊 failed、webhook 和補單都說成功狀態只往前走條件式更新：只有從允許的狀態才能改，paid 不會再變

兩道都要：只有狀態檢查時，像「部分退款」這種本來就可以發生好幾次的事件，狀態分不出重複；只有事件去重時，晚到的舊事件 id 是新的，照樣會被處理，補單也沒有事件 id。

第一道：用資料庫的唯一約束去重，而且要在同一個交易裡

直覺的寫法是「先查有沒有處理過，沒有再處理」。第 7 課的優惠券已經看過它的下場：兩個請求同時查，都查到「沒有」，都往下做。webhook 的重送常常就是同時到的（CafePay 逾時重送時，第一個請求可能還在處理）。把它記在記憶體的 Set 也不行：正式環境有兩台以上的 API，各有各的記憶體，重啟之後也全部忘光。

要讓資料庫判斷：直接插入，撞到主鍵就什麼都不做，看影響了幾列。

const inserted = await tx.$executeRaw`INSERT INTO processed_events (event_id, type)
  VALUES (${event.id}, ${event.type}) ON CONFLICT (event_id) DO NOTHING`
if (inserted === 0) return false   // 處理過了

$executeRaw 回傳影響的列數（第 3 課的時段名額用過）。兩個請求同時插入同一個 event_id 時，後到的會等先到的交易結束：先到的提交了，後到的看到衝突，影響 0 列；先到的回滾了，後到的就插得進去，由它來處理。

接著是交易。「記下處理過」「改付款狀態」「改訂單狀態」「加點數」要在同一個 this.prisma.$transaction(async tx => { … }) 裡，全部用 tx。想想不在同一個交易時，中途失敗會怎樣：

  • 先記了 processed_events，加點數時資料庫出錯：我們回 500，CafePay 重送，但事件已經記成「處理過」，被略過，這筆付款永遠停在 unknown。
  • 狀態改成 paid 了，點數沒加：重送時狀態已經是 paid，點數再也補不回來。

在同一個交易裡，任何一步失敗就全部回滾，像這個通知從來沒來過；回 5xx 讓 CafePay 重送，重送時從頭再做一次。這也決定了回應碼：處理過的重複通知回 2xx（對 CafePay 來說「我收到了」就是成功，回錯誤它只會一直重送），真的處理失敗才回 5xx。

第二道：狀態只往前走

這是第 3 課時段名額、第 7 課優惠券用過的條件式更新：把「現在是什麼狀態」寫進 WHERE，看改到幾列。

const from = result === 'paid' ? ['pending', 'unknown', 'failed'] : ['pending', 'unknown']
const { count } = await tx.payment.updateMany({ where: { orderId, status: { in: from } }, data: { status: result } })

count 是 0 就代表不用做事：要改成 failed，但已經是 paid（晚到的舊事件）；要改成 paid，但已經是 paid（另一個事件、或補單已經做過）。count 是 1 而且結果是 paid，才改訂單狀態、加點數。因為是同一列的條件式更新，兩個交易同時改時，PostgreSQL 讓後到的等先到的提交，再用新的狀態重新檢查 WHERE，所以點數只會加一次。

為什麼 failed 可以變成 paid？我們的 failed 有可能是錯的（像王小明那筆，就是逾時被誤標的）。錢在 CafePay 那邊，CafePay 說成功就是成功，我們跟著改；反過來，paid 之後的任何 failed 都只是舊消息。

💡 實務上：webhook 的處理要快，而且每一步都假設會重來
金流商等 webhook 回應的時間有限（各家文件會寫，超過就算失敗、排入重送），所以 webhook 裡只做「驗簽、去重、改狀態」這種快的事；寄信、通知廚房這類慢的事，寫進資料庫讓背景工作去做（例如 NestJS 課第 21 課的佇列）。上線前一定要測三件事：同一個通知同時送兩次、舊的通知晚到、處理到一半出錯。金流商的測試環境大多有「重送這個事件」的按鈕，用它試。processed_events 也是客服查案的依據：CafePay 說「我們 10:03 送了 evt_xxx」，查這張表就知道我們有沒有收到、什麼時候收到。

漏通知：補單主動去問

第三件事：CafePay 的通知系統故障了一小時，「漏掉的通知不會補送」。webhook 是對方主動送來的，我們沒辦法保證它一定會來。如果 pay() 那次也剛好逾時，這筆付款就永遠停在 unknown，客人付了錢，訂單卻沒人處理。

解法是不要只等對方，自己定期去問。這叫補單（reconciliation job）：找出等太久還沒有結果的付款，向 CafePay 查詢（GET /v1/payments?orderId=，client 的 findByOrder()），再套用結果。reconcilePayments() 現在是空的，要做的事：

  1. 找出等太久的付款：狀態是 pending 或 unknown，而且 createdAt 早於「現在 − 10 分鐘」。「現在」一律從 this.clock.now() 拿（第 3 課的可注入時鐘），測試才能把時間撥快。為什麼要等 10 分鐘：剛送出的付款，webhook 多半還在路上，現在去查只是多打一次 CafePay；正常情況下通知幾秒內就到，等 10 分鐘還沒來，才值得主動查。
  2. 一筆一筆查：CafePay 說 succeeded 就是 paid；說 failed 就是 failed；查無這筆付款（404，status: 'not_found'）代表請求根本沒到 CafePay，沒有扣款，也標 failed（過了 10 分鐘還查不到，就不會再出現了）。
  3. 交給 applyPaymentResult()：跟 webhook 同一個函式。如果補單自己寫一份「改狀態、改訂單」，很快就會跟 webhook 那份分岔：忘了加點數，或忘了狀態只能往前走，補單和晚到的 webhook 就會各加一次點數。規則只寫一次，兩條路都走它。
  4. 一筆失敗不影響其他筆：查詢時 CafePay 沒回應，記一行 log、跳過，下一輪再查。回傳 { checked, updated } 方便看執行結果。

補單可以重複執行：已經 paid 的不會再被找出來；就算同時有 webhook 在處理同一筆，狀態檢查也只會讓其中一個加點數。手動執行：

npm run reconcile

npm run reconcile 會先 nest build，再用 api/src/reconcile.ts 建立 Nest 的應用程式內容（不開 HTTP port），拿到 PaymentsService 呼叫一次。正式環境會用排程（cron，或 NestJS 課第 21 課的 @Cron）每幾分鐘執行一次，這一課不做排程。

💡 實務上：補單之外，還有每天的對帳
補單處理的是「某一筆不知道結果」。另一件會計會要的事是對帳：金流商每天提供前一天的交易明細（對帳檔或報表 API），跟我們的 payments 逐筆比對金額與狀態，列出對不起來的。它抓得到補單抓不到的東西：我們以為 paid、對方其實退款了；對方有扣款、我們連 payments 都沒有（像王小明的第一次扣款）。對帳的結果是一張「差異清單」給人處理，不要自動改資料。補單和對帳都要有監控：補單每次 updated 都不是 0、或差異清單突然變長，代表 webhook 或程式出問題了，要有人去看。

練習

三題都在 delivery/practice/work/08 的 api/src/payments/payments.service.ts 裡做，寫完回到 learn/ 執行 node check.mjs delivery 08。判分會開自己的假 CafePay（隨機 port、逾時設成 300 毫秒）和兩台 API，直接看資料庫的結果。

練習 1：修正 pay()：結果不明時標 unknown，重試沿用同一把 Idempotency-Key。

  • CafePay 扣款後沒有回應（CafePayUnknownError）：付款標成 unknown，回傳 { orderId, status: 'unknown' }（controller 會回 202）。不能標 failed。
  • key 從訂單推出來（payment:<訂單 id>）。同一張訂單再呼叫一次 pay()：付款還是 pending／unknown 就用同一把 key 再問 CafePay，拿到成功就變 paid；已經 paid 直接回 paid；已經 failed 回 402，不再扣款。
  • 卡片被拒絕仍然回 402 CARD_DECLINED、付款標 failed。
  • 判分：逾時後回 202、付款 unknown；重試時真的再呼叫 CafePay，CafePay 只有一筆扣款、收到的 key 都相同、訂單 paid；同一位客人的兩張訂單 key 不同、各扣一次；被拒絕的付款是 failed。

練習 2：讓 webhook 冪等、不怕亂序：改 handleEvent() 與 applyPaymentResult()。

  • webhook 處理的事件記進 processed_events，同一個事件第二次來直接略過（回 2xx）。去重要靠資料庫，不能先查再寫，也不能記在記憶體。
  • 狀態只往前走：paid 不會被任何 failed 改掉；只有真的從別的狀態變成 paid 的那一次才改訂單、加點數。
  • 記錄事件、改付款、改訂單、加點數在同一個交易裡：中途出錯就全部回滾，回 5xx。
  • 判分：同一個 payment.succeeded 同時送 6 次（分給兩台 API）都回 2xx、點數只有一筆、processed_events 一筆；之後送一個較舊的 payment.failed，付款仍是 paid；兩個不同事件都說成功，點數仍一筆；用 trigger 讓寫點數失敗時，付款、訂單、processed_events 都沒有變，重送之後才完成。

練習 3：實作 reconcilePayments()：找出 pending／unknown 超過 10 分鐘的付款，向 CafePay 查詢，結果交給 applyPaymentResult()。

  • 「現在」用 this.clock.now()；成功→paid、失敗或查無付款→failed；一筆查詢出錯不影響其他筆；回傳 { checked, updated }。
  • 判分：把時間撥到 11 分鐘後執行一次，CafePay 已扣款但 webhook 沒來的付款變 paid、點數一筆；只等了 9 分鐘的付款沒有被查詢；再執行一次、或之後才收到 webhook，點數仍是一筆；pending 而且查無付款的標 failed；一筆查詢丟出錯誤時，其他筆照樣補上、出錯的那筆維持 unknown；最後真的執行一次 npm run reconcile（會 nest build，要等十幾秒）。

練習 4：呼叫金流商建立付款時逾時了。這筆付款應該標成什麼？

✓ a。逾時只代表「沒拿到回應」，對方可能已經扣款。b 會讓已經被扣款的客人再付一次（CAFE-35 的第一件事）；c 會讓沒付錢的訂單出餐；d 刪掉之後，如果其實已經扣款，連對帳的線索都沒了。

練習 5：webhook 去重最可靠的做法是？

✓ d。唯一約束讓資料庫決定誰是第一個，跟處理放在同一個交易，失敗時也一起回滾，重送時能再處理。a 在兩台以上的 API 或重啟之後就失效；b 在同時送達時兩個請求都查到「沒有」；c：至少一次送達是金流商的保證，不是可以關掉的選項，沒有重送反而會漏通知。

練習 6：webhook 漏送了，補單查到這筆付款其實成功了。應該怎麼套用結果？

✓ b。兩條路各寫一份，行為會慢慢分岔：a 很容易忘了加點數，或忘了「狀態只往前走」，之後晚到的 webhook 會再加一次點數。c 讓付了錢的客人拿不到餐；d 會重複扣款（就算用同一把 key，也是多此一舉，查詢就夠了）。

常見錯誤

  • 把逾時當失敗：對方可能已經處理了。分成成功、失敗、不知道三種，不知道就標 unknown，之後確定。
  • 每次重試產生新的冪等鍵：randomUUID()、時間戳記都會讓對方當成新的請求。key 從代表意圖、重試時不變的資料推出來，例如訂單 id。
  • 所有請求共用一把 key：第二張訂單會被對方拒絕，或拿到第一張的結果。一個意圖一把 key。
  • 去重放在記憶體，或先查再寫：多台主機、重啟、同時送達都會讓它失效。用唯一約束，插不進去就略過。
  • 記錄事件、改狀態、加點數分開寫：中途失敗會留下一半的資料，重送也救不回來。全部放在同一個交易。
  • 收到什麼就照改：晚到的舊事件會蓋掉新狀態。用條件式更新讓狀態只往前走，paid 是終點。
  • 重複的通知回錯誤碼：對金流商來說那代表沒收到，它會一直重送。處理過的就回 2xx。
  • 只靠 webhook：通知會漏。補單定期查詢等太久的付款。
  • 補單自己寫一份更新邏輯：跟 webhook 分岔，點數重複或沒加。兩條路共用 applyPaymentResult()。

小結

  • 呼叫外部服務的結果有三種：成功、失敗、不知道。逾時、斷線、5xx 是「不知道」，付款標 unknown、回 202，不能叫客人重付。
  • 冪等鍵讓重試被認成同一筆：key 從訂單推出來（payment:<訂單 id>），重試時用同一把，對方只扣一次款。
  • webhook 是至少一次送達、不保證順序。用兩道檢查：processed_events 的唯一約束擋同一個事件，條件式更新讓狀態只往前走、擋舊事件與重複的路徑。
  • 記錄事件、改狀態、加點數放在同一個交易：失敗就全部回滾、回 5xx，讓對方重送；重複的回 2xx。
  • 通知會漏，所以要補單：定期查等超過一段時間（這裡 10 分鐘）的付款，結果交給跟 webhook 同一個函式。
