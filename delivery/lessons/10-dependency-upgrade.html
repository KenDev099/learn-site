階段 3：錢與資料 · 第 10 課

依賴升級：讀 changelog、處理破壞性變更、分批上線

CafePay 寄來一封信：官方 SDK 2.0.0 已經發布，1.x 只支援到 2027-02-01，之後 API 的 /v1 端點停止服務。我們的付款程式用的是 cafepay-sdk 1.4.2。三個月後不升級，線上付款就會全部失敗。

升級套件最常見的做法是改版號、跑一下測試、看起來沒壞就上線。這次那樣做會出事：2.0 改了金額的單位，110 元的拿鐵如果照舊送 110，CafePay 收到的是 1.10 元。這一課照資深工程師升級重要依賴的順序做一次。

這課的路線：
  1. 先讀 changelog、找出每一個影響點：主版號升級時哪些東西會壞，怎麼用 grep 列出程式裡每個受影響的位置，而不是憑印象。
  2. 轉接層：怎麼讓新舊兩版 SDK 同時存在，業務邏輯不用知道底下是哪一版。
  3. 功能旗標：不重新部署，就讓 1% 的訂單先走新版，出事時改一筆資料就退回。
  4. 分批上線計畫：每放大一步要看哪些數字、看到什麼就退，寫到值班的同事也能照著做。
這課會用到：
  • 第 8 課的付款流程：逾時、斷線算「結果不明」（unknown，API 回 202）；重試時用同一把冪等鍵（例如 payment:1042）；補單程式定期向 CafePay 查詢沒有結果的付款。
  • 系統設計課第 19 課的功能旗標：程式執行時才決定走哪條路徑的開關，讓「部署程式」和「開放給使用者」分成兩件事。

為什麼用 imports，不是 npm install？正式專案會執行 npm install cafepay-sdk@2.0.0。要兩版並存時，npm 支援別名（alias）：npm install cafepay-sdk-v2@npm:cafepay-sdk@2.0.0，package.json 會出現 "cafepay-sdk-v2": "npm:cafepay-sdk@2.0.0"，程式用 import … from 'cafepay-sdk-v2'（npm 11 的文件：別名可以讓同一個套件的不同版本並存）。這門課的練習沒有網路、所有專案共用同一份 node_modules，所以改用 Node 的子路徑匯入（subpath imports）：package.json 的 "imports" 欄位，名稱一定要用 # 開頭，指到專案裡的檔案。程式碼的寫法和用別名時一樣，只差在名稱的開頭。

先讀 changelog：主版號增加代表有東西會壞

套件的版本號是 semver（Node 課第 3 課）：主版號.次版號.修訂號。修訂號（1.4.1 → 1.4.2）只修 bug；次版號（1.3 → 1.4）加功能，舊的寫法照樣能用；主版號（1.x → 2.0）代表有破壞性變更（breaking change）：原本的程式不改就會壞。所以 1.4.2 → 2.0.0 不是改個數字的事，要先知道「壞」在哪裡。

答案寫在 changelog：套件每一版改了什麼的紀錄，通常是 repo 根目錄的 CHANGELOG.md，或 GitHub 的 Releases 頁面。主版本的 changelog 常附一段遷移指南（migration guide）：作者告訴你舊的寫法要怎麼改成新的。打開 vendor/cafepay-sdk-2.0.0/CHANGELOG.md，讀的順序：

  1. 從你現在的版本讀到目標版本，中間每一版都要看：1.4.2 → 2.0.0 只隔一版，跨好幾個主版本時，每一版的破壞性變更都要處理。
  2. 先找 BREAKING CHANGES：每一條都要能回答「我們的程式哪裡用到它」。
  3. 看支援期限：決定排程。這裡是 2027-02-01，現在動手有三個月，夠分批上線。
  4. Features、Bug Fixes：看有沒有我們正在繞路處理的問題已經被修好。

2.0.0 有三個破壞性變更，這一課用三個代號稱呼它們：

代號1.4.22.0.0不改會怎樣
amount-unit金額是元：110金額是最小貨幣單位（分）的整數：11000型別都是 number，編譯會過，測試若只看「有沒有成功」也會過，CafePay 只扣 1.10 元
create-apicreatePayment(input, { idempotencyKey })payments.create({ ...input, idempotencyKey })TypeScript 直接報錯，最容易發現
error-throw回傳 { ok: true, payment } 或 { ok: false, error }成功直接回傳 Payment，失敗丟出 CafePayError沒有 try/catch 的地方，卡片被拒絕變成 500；逾時不再是「結果不明」

三個變更的危險程度不一樣：編譯器會幫你抓 create-api，另外兩個要靠你自己找。最危險的是 amount-unit：它不會報錯，只會收錯錢。這就是為什麼「改版號、跑測試、沒紅就上線」不夠：測試只會抓到測試想到的事。

跟著做：找出每一個影響點

影響點是「程式裡用到這個變更的每一行」。用 grep 找，不要憑印象。先找 create-api：搜尋 SDK 的方法名稱，範圍是 API 的原始碼和腳本。在 work/10 執行：

grep -rn "createPayment\|findPayment" --include='*.ts' api/src scripts

輸出（-r 往下找每個資料夾，-n 印行號，\| 是「或」；--include 的 *.ts 加引號，zsh 才不會先把它展開）：

api/src/payments/cafepay-v2.ts:24:    // 練習 2：TODO 用 this.sdk.findPayment(…)，回傳的結果跟 CafePayClient.findByOrder() 一樣
api/src/payments/cafepay.ts:26:    const r = await this.sdk.createPayment({ orderId: input.orderId, amount: input.amount, cardToken: input.cardToken }, { idempotencyKey })
api/src/payments/cafepay.ts:34:    const r = await this.sdk.findPayment(orderId)
scripts/daily-check.ts:22:    const r = await cafepay.findPayment(p.order_id)

（檔案的順序依作業系統列出資料夾的順序，你的電腦上可能不一樣。）三處真的呼叫：第一行是練習 2 空殼裡的註解，而且那個檔案用的是 2.0，不算。createPayment 只有 cafepay.ts:26 一處，這就是 create-api 的全部影響點。但結果也告訴你另一件事：用到 SDK 的不只 cafepay.ts。scripts/daily-check.ts 沒有經過 CafePayClient，自己 new 了一個 SDK。只看第一個搜尋結果、或只打開「看起來是付款的檔案」，就會漏掉它。

要確認「有哪些檔案用到這個套件」，搜尋 import 最可靠：

grep -rln "cafepay-sdk-v1" api/src scripts
api/src/payments/cafepay.ts
scripts/daily-check.ts

（-l 只印檔名。）兩個檔案就是全部的範圍。接著在這兩個檔案裡，各找另外兩個變更的特徵：

  • amount-unit：送進 SDK 的金額、從 SDK 拿回來的金額。看每一個 amount，問「這個數字的單位是誰決定的」。我們自己的型別（例如 charge(input: { amount: number })）是元，不受影響；傳給 SDK 的參數、讀 r.payment.amount 的地方才受影響。
  • error-throw：讀 { ok, error } 的地方。搜尋 .ok。

練習 1 讓你自己找出這兩個變更的位置，寫進 upgrade-notes.json。這份清單不只是作業：它是升級 PR 的檢查清單，審查的人照著它一行一行對，也是之後「移除 1.x」那一步要改的地方。

💡 實務上：升級前先把影響範圍寫下來
Dependabot、Renovate 這類工具會自動開升級的 PR，修訂號和次版號通常 CI 綠了就能合併；主版號的 PR 不要直接合併。資深工程師會先開一張單，寫下：changelog 的每一條破壞性變更、在我們的程式裡的位置（就是練習 1 的清單）、有沒有測試涵蓋、怎麼上線、怎麼退回。範圍大的升級（例如框架的主版本）常常先開一個「只修相容問題、不升級」的 PR，把要改的寫法先改成兩版都能用，真正升級的 PR 就很小。搜尋時記得 repo 裡的腳本、排程、測試、別的服務也算：它們常常繞過共用的包裝直接用套件。

轉接層：讓新舊兩版並存

最直接的升級方式是把 cafepay.ts 改成 2.0 的寫法，一次部署。問題是付款出錯沒有試錯的空間：2.0 有任何我們沒想到的差異（例如某種錯誤碼的意思變了），所有客人同時受影響，退回要重新部署舊版：等部署跑完的這段時間，每一筆付款都還在走有問題的新版。比較安全的做法是讓兩版同時存在，先讓一小部分訂單走新版，確定沒問題再放大。

要讓兩版並存，業務邏輯不能直接碰 SDK。第 8 課的 CafePayClient 其實已經在做這件事：PaymentsService 只呼叫 charge() 和 findByOrder()，拿到的是我們自己定義的結果（金額是元、結果分成成功／失敗／丟出 CafePayUnknownError），不知道底下是 fetch 還是 SDK。這一課把這個形狀寫成介面：

export interface PaymentGateway {
  // 扣款。卡片被拒絕回 failed；結果不明丟 CafePayUnknownError
  charge(input: { orderId: number, amount: number, cardToken: string }, idempotencyKey: string): Promise<ChargeResult>
  // 查詢某張訂單的付款（補單用）
  findByOrder(orderId: number): Promise<LookupResult>
}

把外部套件包在自己的介面後面，換版本時只改包裝的那一層，這層叫轉接層（adapter）。1.4.2 的實作是 CafePayClient，2.0.0 的實作是 CafePayV2Client，兩個都是 Nest 的 provider（NestJS 課第 3 課），PaymentsService 注入兩個，依每筆付款決定用哪一個。

CafePayV2Client 要做的，就是把三個破壞性變更換回介面的形狀：

2.0.0 的行為換成
payments.create({ orderId, amount, cardToken, idempotencyKey })，amount 是分呼叫前用 toMinor(input.amount) 把元換成分
成功：回傳 Payment{ id: payment.id, status: payment.status }
丟出 CafePayError，code: 'card_declined'回傳 { id: e.paymentId ?? null, status: 'failed' }（確定沒扣款，PaymentsService 會回 402）
code: 'network' 或 'server'丟出 CafePayUnknownError（第 8 課的「結果不明」，API 回 202）
findPayment() 丟出 code: 'not_found'回傳 { id: null, status: 'not_found' }（補單會標 failed）
其他 CafePayError、不是 CafePayError 的錯誤丟出一般的 Error：我們送錯了或程式有 bug，回 500 讓人去查

判斷錯誤種類用 e instanceof CafePayError 再看 e.code，不要比對 e.message 的文字：訊息是給人看的，套件改個措辭就對不上了。

轉接層只在並存期間需要。全部切到 2.0、移除 1.4.2 那天，PaymentGateway 介面、CafePayClient、payments.sdk 的分流一起刪掉，CafePayV2Client 就是唯一的實作。不要為了「以後也許會換金流商」把它留著。

金額換算：集中在一個函式，結果一定要是整數

元換成分是乘以 100。我們的價格都是整數元，110 * 100 是精確的 11000。但 JavaScript 的 number 是二進位的浮點數，0.1、19.9 這種小數存不精確：

19.9 * 100     // 1989.9999999999998
0.07 * 100     // 7.000000000000001
0.1 + 0.2      // 0.30000000000000004

今天沒有小數的元，下個月店長加一個「9 折」，99.5 元就出現了。金額換算的規則：

  • 集中在一個函式（toMinor()），不要在每個呼叫的地方各寫 * 100：之後要改、要加檢查，只有一個地方。
  • 乘完四捨五入成整數：Math.round(yuan * 100)。19.9 * 100 離 1990 只差一點點，四捨五入就對了。
  • 結果不是整數就是 bug：元有三位小數（例如 1.005 元）時，換不成整數的分，要丟錯誤，不要默默送一個奇怪的數字。
  • 測試要包含小數：110、1990 這種整數測不出問題，要加 19.9、0.07。
把錢存成「元的小數」（例如資料庫用 float）是更深的坑：加總、比較都會差一點點。資料庫的金額用整數（最小單位）或 PostgreSQL 的 numeric，程式裡用整數算。我們的 orders.total 是整數元，這一課的換算只發生在呼叫 CafePay 的那一刻。

功能旗標：不用部署就能切換、也能退回

功能旗標（feature flag）是程式執行時才決定走哪條路徑的開關。這一課的旗標 payments.sdk_v2 不只是開或關，而是一個百分比：開給幾 % 的訂單。它存在 feature_flags 表（migration 已經建好）：

CREATE TABLE "feature_flags" (
    "key" TEXT NOT NULL,                        -- 旗標的名稱，例如 payments.sdk_v2
    "percent" INTEGER NOT NULL DEFAULT 0,       -- 開給幾 %（CHECK 0～100）
    "updated_at" TIMESTAMPTZ(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    ...
);

種子資料放了 ('payments.sdk_v2', 0)。改它用 npm run flag：

$ npm run flag -- payments.sdk_v2 10
payments.sdk_v2：0% → 10%
┌─────────┬───────────────────┬─────────┬────────────────────┐
│ (index) │ key               │ percent │ updated            │
├─────────┼───────────────────┼─────────┼────────────────────┤
│ 0       │ 'payments.sdk_v2' │ 10      │ '2026-11-02 19:17' │
└─────────┴───────────────────┴─────────┴────────────────────┘

為什麼放資料庫，不放環境變數（PAYMENTS_SDK_V2=10）？環境變數在程序啟動時讀進來，要改就要改設定、重新部署或重啟所有的 API。正式環境出事時，退回的速度就是損失的大小：改一筆資料，下一個請求就生效，比等一次部署快得多。FeatureFlags.percent() 每次付款都查一次資料庫（主鍵查詢，很便宜）；不要在程式啟動時讀一次就記住，那等於又變回「要重啟才生效」。

依訂單 id 穩定分流

開給 10%，要怎麼決定「這筆訂單在不在 10% 裡」？直覺的寫法是：

const useV2 = Math.random() * 100 < percent   // 不要這樣寫

想想第 8 課的重試：付款逾時（unknown），客人過幾秒再按一次，pay() 用同一把冪等鍵 payment:1042 再問一次 CafePay。第一次擲骰子走 v2，送出 amount: 11000；第二次擲骰子走 v1，同一把 key 送出 amount: 110。CafePay 看到同一把 key 的金額不一樣，回 422 idempotency_key_reused：重試失敗，客人卡在「付款確認中」。換一個金流商，甚至可能被當成兩筆付款。

分流要穩定：同一筆訂單不管問幾次，答案都一樣。這叫穩定雜湊分流（sticky bucketing）：把「旗標名稱＋訂單 id」做雜湊，算出 0～99 的桶子編號，桶子編號小於 percent 就在裡面。

import { createHash } from 'node:crypto'

const bucket = createHash('sha256').update(`${key}:${id}`).digest().readUInt32BE(0) % 100
return bucket < percent

createHash('sha256') 對同樣的輸入永遠算出同樣的結果，而且結果看起來是亂的，所以 0～99 每個桶子分到的訂單差不多一樣多。digest() 回傳 32 個位元組，readUInt32BE(0) 取前 4 個當成一個整數，% 100 變成 0～99。幾筆訂單實際算出來的桶子：

訂單 id104110421043104410451046
桶子34455824016
10% 時v1v1v2v1v1v1
50% 時v2v2v2v1v2v2

從表上看得到兩個性質：

  • 調高百分比時，原本在裡面的不會被移出去：1043 的桶子是 5，10% 時在裡面，50% 時也在。用「桶子 < percent」才有這個性質，放大時只有新的訂單加入新版，不會有人在兩版之間跳來跳去。
  • 旗標名稱也放進雜湊：只用訂單 id 的話，每個旗標的「前 10%」都是同一批訂單，這批客人永遠先吃到每一個新功能的 bug。

實務上分流的單位要選「會一起重試、一起被看見的那個東西」：付款用訂單 id；改畫面的功能常用使用者 id，免得同一個人重新整理一次畫面就變了樣。

已經開始的付款，跟著它自己的版本走

穩定雜湊解決了「同樣的 percent 問兩次」，但還有一種情況：旗標本身變了。10% 時訂單 1043 走 v2，逾時變 unknown；這時你發現 v2 有問題，把旗標改回 0。客人重試時再算一次，1043 變成 v1，又是同一把 key、不同的金額。

所以分流的結果要記下來：建立付款時決定一次版本，寫進 payments.sdk；之後這筆付款的重試、補單都照 payments.sdk，不再看旗標。旗標只決定新的付款走哪一版。pay() 的流程變成：

  1. 已經有付款紀錄：sdk 用紀錄上的。沒有：await this.flags.enabledFor('payments.sdk_v2', orderId) 決定，建立付款時一起寫進 sdk。
  2. 依 sdk 選 CafePayClient 或 CafePayV2Client，其他照第 8 課（同一把冪等鍵、unknown 回 202）。

reconcilePayments() 也一樣：查詢時用 p.sdk 選轉接層。這個欄位還有第三個用途：上線時依 sdk 分組看成功率，下一節會用到。

💡 實務上：旗標是暫時的，要記得拆
功能旗標方便，但每多一個，程式就多一條分岔要測、要懂。這種「切換版本用」的旗標，在計畫裡就寫好拆除的時間：100% 跑穩一兩週後，開一個 PR 刪掉旗標、舊的路徑和轉接層。忘了拆，半年後沒人敢動，還會有人誤把它改回 0。旗標多的團隊會用專門的服務（例如 LaunchDarkly、Unleash 這類），有權限控管、修改紀錄和「誰在什麼時候改了什麼」；只有幾個旗標時，一張資料表加上修改腳本就夠了，改旗標的人和時間記在需求單或頻道裡。

分批上線計畫：每一步看什麼、什麼時候退

功能旗標讓你可以像 DevOps 課第 16 課的金絲雀發布一樣，先讓一小部分流量走新版。差別是金絲雀切的是「哪台機器跑新版程式」，旗標切的是「同一份程式裡走哪條路徑」，退回只要改一筆資料。計畫要在動手前寫好，內容是：

  • 階段：例如 1% → 10% → 50% → 100%。第一步要小（≤ 5%），出問題時只影響少數訂單；也要大到有足夠的付款可以看，咖啡店一天幾百筆，1% 就要看一整天。
  • 每一階段看什麼：一句可以直接執行的 SQL，依 sdk 分組比較新舊兩版。只看整體的成功率，10% 的 v2 壞掉只會讓整體掉一點點，被 90% 的 v1 稀釋掉。
  • 退回條件：寫成數字，例如「v2 的成功率比 v1 低 2 個百分點以上」「v2 出現 unknown 超過 10 分鐘」。「看起來怪怪的就退」到了半夜沒有人能判斷。
  • 怎麼退回：一行可以直接執行的指令：npm run flag -- payments.sdk_v2 0。不需要部署。

檢查用的 SQL。在 work/10 執行 docker compose exec postgres psql -U learn -d cafe 連進開發資料庫（第 9 課用過），貼上：

SELECT sdk,
       count(*) AS payments,
       round(100.0 * count(*) FILTER (WHERE status = 'paid') / count(*), 1) AS paid_pct,
       count(*) FILTER (WHERE status = 'unknown') AS unknown
FROM payments
WHERE created_at > now() - interval '1 hour'
GROUP BY sdk
ORDER BY sdk;
 sdk | payments | paid_pct | unknown
-----+----------+----------+---------
 v1  |       32 |     93.8 |       2
 v2  |        8 |     50.0 |       0

（這是在判分資料庫裡放的假資料。）count(*) FILTER (WHERE …) 只數符合條件的列；100.0 寫成小數，除法才不會被當成整數除法。看到這種結果：v2 只有 8 筆，成功率卻比 v1 低很多，先退回（設成 0），再去查 v2 失敗的那幾筆（WHERE sdk = 'v2' AND status = 'failed'）是卡片真的被拒絕，還是我們送錯了。注意 failed 也包括客人的卡被拒絕這種正常情況，所以要比的是兩版的差距，不是看成功率是不是 100%。

到 100% 之後計畫還沒結束：再跑一段時間，然後移除 1.4.2：練習 1 的清單裡每一個位置都改完（包括 daily-check.ts），刪掉 CafePayClient、介面、分流和 vendor/cafepay-sdk-1.4.2。在 1.x 停止支援之前完成，這次升級才算做完。

💡 實務上：上線計畫要讓別人也能執行
分批上線常常跨好幾天，中間可能是值班的同事在看。計畫寫在需求單或 PR 裡：每一階段的時間、要看的查詢或監控圖表、門檻、退回指令、通知誰（付款相關要讓會計和客服知道，他們最先接到客訴）。放大到下一階段之前，貼一次查詢結果。退回之後不要馬上重來：先找到原因、補上測試，再從 1% 開始。需要改資料庫結構的升級，記得旗標退得回去、migration 不一定退得回去（第 9 課的回填順序），所以 migration 要先單獨部署、而且新舊兩版程式都能用。

練習

三題都在 delivery/practice/work/10 裡做，寫完回到 learn/ 執行 node check.mjs delivery 10。判分會開自己的假 CafePay（隨機 port、逾時 300 毫秒），直接改判分資料庫的 feature_flags。先做練習 1 再改程式：練習 1 的行號以起始版本為準。

練習 1：讀 vendor/cafepay-sdk-2.0.0/CHANGELOG.md，在 upgrade-notes.json 列出三個破壞性變更各自影響到的程式位置。

  • 格式：[{ "change": "amount-unit", "locations": [{ "file": "api/src/payments/cafepay.ts", "line": 26 }] }, …]，file 是相對於專案根目錄（work/10）的路徑。
  • 範圍是 api/src 和 scripts 裡用到 1.x SDK 的檔案。amount-unit：送進 SDK 或從 SDK 拿回來的金額；create-api：呼叫 createPayment 的地方；error-throw：讀 { ok, error } 的地方。
  • 判分：每個變更都要涵蓋起始程式裡的每一個位置（行號差 2 行以內算對），跟這個變更無關的位置最多 1 個；檔案要存在、行號在範圍內。

練習 2：實作 2.0 的轉接層，並用旗標 payments.sdk_v2 依訂單 id 穩定分流。

  • cafepay-v2.ts：toMinor() 把元換成分（結果是精確的整數，19.9 → 1990；1.005 這種換不成整數分的要丟錯誤）；CafePayV2Client 的 charge()、findByOrder() 照上面的對照表，回傳跟 CafePayClient 一樣的結果。
  • feature-flags.ts：inRollout(key, id, percent)：同樣的輸入每次答案一樣；0% 全部 false、100% 全部 true；調高 percent 時原本 true 的不會變 false；旗標名稱也要算進去（不同旗標挑到的不是同一批）。
  • payments.service.ts：新的付款用 this.flags.enabledFor('payments.sdk_v2', orderId) 決定版本、寫進 payments.sdk；已經有的付款照它的 sdk；pay() 和 reconcilePayments() 依 sdk 選 CafePayClient 或 CafePayV2Client（兩個都已經在 PaymentsModule 裡，直接注入）。
  • 判分：旗標 0% 全部打 /v1（金額仍是元：110）、100% 全部打 /v2；v2 收到的 amount 是 11000、199000（110、1990 元）；v2 卡片被拒絕回 402；改旗標後下一個請求就照新的值；30% 時每筆訂單的版本跟 inRollout 一致，1000 筆裡 25%～35% 在裡面、問 5 次答案都一樣；v2 逾時後把旗標改回 0，重試仍走 v2、只扣一次款；補單照 sdk 查詢，v2 查無付款的標 failed。

練習 3：填 rollout-plan.json：{ stages: [{ percent, checkSql, rollbackIf }], rollback: { action, needsDeploy } }。

  • percent 是數字，第一階段 ≤ 5，每一階段比前一階段大，最後是 100，至少三個階段。
  • checkSql 是可以直接執行的唯讀查詢，要依 payments.sdk 分開看；rollbackIf 寫出有數字的退回門檻。
  • rollback.action 是可以直接執行的退回指令（npm run …），needsDeploy 是布林值。
  • 判分：每個 checkSql 在判分資料庫的唯讀交易裡執行得了，而且執行計畫裡真的讀了 payments.sdk（寫在註解裡不算）；指令用到的 npm script 存在、旗標名稱與百分比正確。

練習 4：分批上線用 Math.random() < 0.1 決定這次付款走不走新版，問題在哪？

✓ b。分流要對同一筆訂單穩定：用旗標名稱＋訂單 id 的雜湊算桶子，而且建立付款時把版本記在 payments.sdk，重試照它走。a 只看了比例，沒看同一筆訂單的一致性；c、d 不是重點，速度和亂數品質都夠用。

練習 5：為什麼這個功能旗標放在資料庫，而不是環境變數？

✓ c。退回的速度就是損失的大小。a、d 是錯的（環境變數是字串，轉成數字就好；NestJS 當然讀得到）；b 跟這個決定無關。也要注意程式每次都要讀資料庫，啟動時讀一次記住就又變回要重啟。

練習 6：新版 SDK 把金額改成最小單位的整數（110 元 → 11000）。最安全的換算方式是？

✓ a。19.9 * 100 是 1989.9999999999998，四捨五入才是 1990；集中在一個函式，之後要加檢查只有一個地方。b 今天剛好沒事，第一個有小數的價格就出錯，而且散在各處很難一起改；c：SDK 沒辦法知道 110 是 110 元還是 1.10 元；d：金額不能相信客戶端送來的值（第 7 課的優惠券）。

常見錯誤

  • 只改版號、跑一下測試就上線：金額單位這種變更型別檢查和一般測試都抓不到。先讀 changelog 的每一條破壞性變更，列出影響點，針對每一條補測試。
  • 只看第一個搜尋結果：腳本、排程、測試常常繞過共用的包裝直接用套件。先搜尋 import 找出所有用到套件的檔案，再逐一檢查。
  • 一次切換全部流量：有沒想到的差異時，所有客人同時受影響，退回要重新部署。用轉接層讓兩版並存，先開一小部分。
  • 用隨機數分流：同一筆訂單的重試會跑到不同版本。依旗標名稱＋訂單 id 的雜湊穩定分流，建立時把版本記下來，重試和補單照記下來的版本。
  • 旗標放在要重新部署才能改的地方：環境變數、設定檔，或只在啟動時讀一次。放資料庫，每次讀。
  • 金額換算用浮點數直接乘：19.9 * 100 不是 1990。集中在一個函式，四捨五入成整數，換不成整數就丟錯誤。
  • 比對錯誤訊息的文字判斷錯誤種類：訊息會改。用 instanceof 和錯誤碼。
  • 只看整體成功率：新版的問題被舊版的流量稀釋。依 sdk 分組比較。
  • 切到 100% 就結束：舊版、轉接層和旗標留著沒人敢刪。計畫裡寫好移除的時間，在舊版停止支援前完成。

小結

  • semver 的主版號增加代表有破壞性變更。升級前讀 changelog，從目前的版本讀到目標版本，每一條破壞性變更都找出程式裡的位置（搜尋 import 確定範圍，再搜尋特徵），寫成清單。
  • 不會報錯的變更最危險（金額單位）：型別和一般測試抓不到，要針對它寫測試。
  • 新舊兩版並存時，用轉接層把外部套件包在自己的介面後面：金額單位、錯誤的形狀在這一層換成同一種，業務邏輯不用知道版本。並存結束就把轉接層收掉。
  • 功能旗標放資料庫、每次讀，退回只要改一筆資料。依「旗標名稱＋訂單 id」的雜湊穩定分流，建立付款時把版本記在 payments.sdk，重試和補單照它走。
  • 分批上線計畫：小的第一步（≤ 5%）、逐步放大到 100%；每一步依版本分組看指標、有數字的退回條件、一行就能執行的退回指令；最後移除舊版。

這個階段的重點整理成一頁圖解。
