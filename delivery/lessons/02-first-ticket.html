階段 1：接手與第一個需求 · 第 2 課

第一張需求單：釐清、驗收條件、切任務、寫 PR 說明

接手第二天，主管指派給你第一張需求單：CAFE-12 預約取餐。內容只有一句話：「外帶客人想先點好、指定時間來拿。」看起來很簡單，加一個時間欄位就好。但只要你問自己「顧客可以選幾點？」，就會發現這句話沒有回答任何一個細節。

這一課在寫任何程式之前，把這張單變成可以開工的東西，最後幫同事的另一張單開 PR。下一課就照這一課的結果寫程式。

這課的路線：
  1. 一句話的需求單會在哪裡翻車：不問清楚就開工，時區、營業時間、一個時段接幾單，最後是誰決定的（開場問題的最小答案）。
  2. 好問題的形狀、可執行的驗收條件：怎麼問店長才能一次拿到答案，回覆怎麼寫成能直接變成測試的條件。
  3. 切任務：第一片要做多少，為什麼要從資料庫一路做到畫面。
  4. PR 說明：審查者、以及半年後用 git blame 追到這裡的人，需要從說明裡知道什麼。
  5. 把 CAFE-15 推成 PR 分支：main 已經往前時怎麼 rebase、解衝突、推上去，這是每天都在走的流程。
這課會用到：
  • 工程實務課第 1 課的需求釐清：開工前把需求問清楚，每條規則配上具體例子，答不出來的問題另外列出來。
  • 工程實務課第 2 課的驗收條件與垂直切片：驗收條件用 Given／When／Then 寫出前提、動作、結果；垂直切片是每一片都從資料庫做到畫面，做完就能交付。
  • DevOps 課第 14 課的 Git 協作：在自己的分支上 commit、推到遠端開 PR；rebase 把你的 commit 重新接到最新的 main 後面。

一句話的需求單會在哪裡翻車

需求單（ticket）是團隊追蹤工作的單位，每張有編號（這門課用 CAFE-編號）、提出的人、優先序和說明。PR、commit、測試都會寫上編號，日後才找得回「當初為什麼這樣做」。

打開 tickets/CAFE-12.md，說明只有「外帶客人想先點好、指定時間來拿」。如果直接開工，你會在寫程式時自己決定這些事，而且大多是在不知不覺中決定的：

  • 時區：顧客選「08:30」，存進資料庫的是什麼？正式機跑在 UTC（世界協調時間，比台灣慢 8 小時）。用伺服器時區算，店員看到的可能是 00:30。
  • 營業時間：可以選 06:00 嗎？19:00 打烊，能選 19:00 嗎？
  • 最快多久：顧客 08:02 送出，可以選 08:05 嗎？店裡來得及做嗎？時間可以選到分鐘，還是一格一格？
  • 一個時段能接幾單：如果 50 個人都選 08:30，吧台做不完。

你不問，程式還是會有答案：你寫程式時隨手決定的那個。上線後才發現「怎麼可以選 19:00」，要改的就包括已經存進去的資料和已經答應顧客的時間。所以開工前要先把這些問題拿去問店長，而且要問成他能直接回答的樣子，細節在下一節〈好問題的形狀〉。

好問題的形狀：附上你的預設答案

問題問得好不好，看對方能不能用一個字回答。比較這兩種問法：

開放式附預設答案
「最快可以多久後取？」「取餐時間至少要在送出的 15 分鐘後，時段 15 分鐘一格，例如 08:02 送出最早選 08:30，對嗎？」
「時間要怎麼處理？」「所有時間都照台灣時間（+08:00）算，跟伺服器在哪裡無關，對嗎？」

開放式的問題常常換來另一個模糊的回答（「大概 15 分鐘吧」），你還得再問一輪。附上你的預設答案和一個具體例子，店長只要說「對」或「不對，改成 20 分鐘」。就算他沒空回，你也已經寫下了假設，之後有爭議時大家知道你是照什麼做的。

跟著做：打開 questions.json，把範本那一題改成「時區」這一題。每一題三個欄位：topic（分類，從 time-zone、business-hours、lead-time、slot-capacity、cancellation、payment-timing 選）、question（問句）、myDefault（你的預設答案）：

[
  {
    "topic": "time-zone",
    "question": "所有時間都照台灣時間（Asia/Taipei，+08:00）算，跟伺服器在哪裡無關，對嗎？",
    "myDefault": "是：顧客選的、畫面顯示的、規則判斷的時間都是台灣時間"
  }
]

剩下的問題在練習 1 自己寫。寫的時候想著第 1 課學到的：先找證據再問。像「營業時間幾點」這種店長一定知道、程式裡找不到的事，才值得問。

💡 實務上：問題一次整理好，用文字送出
零碎地在聊天室問五次，對方會漏回、你也會漏記。把問題整理成一份清單（每題附預設答案），貼在需求單的留言裡，回覆就跟需求單綁在一起，之後誰接手都看得到。對方回完，把結論整理成會議紀錄或更新需求單說明，請他再確認一次。會阻擋開工的問題（時區、營業時間）先問；不阻擋的（例如畫面文案）可以邊做邊等。

把回覆寫成可執行的驗收條件

店長回覆後，你整理成了 docs/meeting-notes-02.md。打開看一下：時區、營業時間、最快 15 分鐘、時段對齊、只能今天、每時段 10 單，取消和付款先不做。

接下來把規則寫成驗收條件（acceptance criteria）：說明「怎樣才算做完」的條件，用 Given（前提）／When（動作）／Then（結果）三段寫。這門課要求更進一步：可執行的驗收條件（executable acceptance criteria），每條都附上具體的輸入和預期結果，可以直接變成測試，不留解讀空間。

例子怎麼挑？每條規則至少要有一個接受、一個拒絕，以及一個邊界案例（boundary case）：剛好落在規則分界上的例子。程式最常錯在分界上：>= 寫成 >、<= 18:45 寫成 < 18:45，只用「08:00 選 10:00」這種離分界很遠的例子，永遠測不出來。

時間一律寫成帶時區位移的 ISO 8601

例子裡的時間寫成 2026-11-03T08:15:00+08:00：日期、T、時間，最後的 +08:00 是時區位移（offset），表示「這是比 UTC 快 8 小時的地方的 08:15」。這種格式叫 ISO 8601。少了位移，每台機器會照自己的時區解讀。用 Node 試一次（TZ 環境變數設定程序的時區）：

node -e "console.log(new Date('2026-11-03T08:15:00+08:00').toISOString())"
2026-11-03T00:15:00.000Z

TZ=UTC node -e "console.log(new Date('2026-11-03T08:15:00').toISOString())"
2026-11-03T08:15:00.000Z

同一個沒有位移的字串，在 UTC 的機器上是 08:15Z，在台北的機器上會是 00:15Z，差了 8 小時。結尾的 Z 就是 +00:00（UTC）。所以 2026-11-03T07:00:00Z 是台北時間 15:00，不是 07:00。台灣沒有日光節約時間，Asia/Taipei 全年都是 +08:00。

跟著做：寫出「至少 15 分鐘後」這一條

acceptance.json 每一條是 { id, given, when, then, examples }，每個例子是 { now, pickupAt, ordersInSlot, expect }：now 是顧客送出的時間、pickupAt 是選的取餐時間、ordersInSlot 是這一單送出前那個時段已經有幾單、expect 是 "accepted" 或 "rejected"。規則「至少 15 分鐘後，剛好 15 分鐘可以」寫成：

{
  "id": "AC2",
  "given": "顧客在台北時間 08:00 或 08:01 送出訂單",
  "when": "取餐時間離送出至少 15 分鐘",
  "then": "接受；不到 15 分鐘拒絕，剛好 15 分鐘接受",
  "examples": [
    { "now": "2026-11-03T08:00:00+08:00", "pickupAt": "2026-11-03T08:15:00+08:00", "ordersInSlot": 0, "expect": "accepted" },
    { "now": "2026-11-03T08:01:00+08:00", "pickupAt": "2026-11-03T08:15:00+08:00", "ordersInSlot": 0, "expect": "rejected" },
    { "now": "2026-11-03T08:02:00+08:00", "pickupAt": "2026-11-03T08:30:00+08:00", "ordersInSlot": 0, "expect": "accepted" }
  ]
}

注意第二個例子：要測「只差 14 分鐘被拒絕」，其他規則都要符合（08:15 有對齊、在營業時間內、今天、沒額滿），只讓這一條落在分界上。如果你選 08:01 送出、08:14 取餐，它被拒絕的原因可能是「沒對齊」，這個例子就測不到 15 分鐘的規則。第三個是店長給的例子，直接拿來用，等於讓他確認過。

💡 實務上：驗收條件的例子就是下一課的測試資料
寫好的例子會直接變成測試：下一課你會把「現在」固定在 08:01，確認 08:15 被拒絕。PM 和店長看得懂例子、不一定看得懂程式，所以例子是你們之間的合約：有爭議時拿例子對，不拿程式對。資深工程師寫驗收條件時會特別問「分界那一分鐘算哪邊」「跨日怎麼算」「UTC 寫的時間換成台北是哪一天」，這三種地方最常出 bug。

切任務：第一片從資料庫做到畫面

規則清楚了，下一步是決定先做哪一塊。常見的錯誤是按技術分層切：先做資料表、再做 API、最後做畫面。每一片單獨都不能給使用者用，要到最後一片才知道接不接得起來。

垂直切片（vertical slice）是反過來：每一片都從資料庫做到畫面，只做一小部分功能，但做完就能上線讓人用。

CAFE-12 的第一片：不指定＝現點現做、可以選今天的時段、每個時段最多 10 單。要碰的東西是 orders 加一個取餐時間欄位、API 驗證規則、結帳頁加時段選擇。取消預約放第二片（會議紀錄已經說先不做）。

為什麼容量不能放到第二片？判斷標準是「這一片上線後會不會造成傷害」。沒有容量上限，50 個人選同一個時段，吧台就爆了，這一片不能單獨上線；取消功能晚一點來，顧客打電話也能處理。切片要小，但每一片都要能安全地交出去。

切好之後，每一片再估一個區間（例如第一片「2–4 天，時區處理最不確定」，工程實務課第 3 課）。這一課不交切片的檔案，下一課直接照這個切法做第一片。

PR 說明：五段範本

功能做完要開 PR（pull request，合併請求），請同事審查後合併。PR 說明（pull request description）是給審查者看的變更說明，也是半年後有人用 git blame（列出每一行最後是哪個 commit 改的）追到這次修改時，唯一能告訴他「為什麼這樣改」的紀錄。這門課固定用五段：

標題寫什麼
目的需求單編號，一兩句講為什麼要做（先講結論，見工程實務課第 7 課）
變更內容資料庫、API、畫面各改了什麼，條列。審查者靠它決定先看哪個檔案
驗收條件對照需求單的每一條（AC1、AC2…）怎麼確認做到了
如何驗證審查者複製貼上就能跑的指令，放在 ``` 區塊裡。「本機測過了」不算
風險與回滾哪裡可能出事、出事怎麼退

跟著做：讀同事的 patch

阿哲把 CAFE-15（商品可以標「已售完」）做好了，放在 changes/CAFE-15.patch，請你開 PR。patch 是用文字記錄的程式差異：- 開頭是刪掉的行、+ 開頭是新增的行。每個檔案的差異從 +++ b/檔名 那一行開始，先用它列出改了哪些檔案（在 work/02 執行）：

grep '^+++ ' changes/CAFE-15.patch
+++ b/api/prisma/migrations/20261104000000_sold_out/migration.sql
+++ b/api/prisma/schema.prisma
+++ b/api/prisma/seed.sql
+++ b/api/src/products/products.module.ts
+++ b/web/src/api/products.ts
+++ b/web/src/pages/MenuPage.vue

資料庫（migration、schema、種子資料）、API、畫面都有改，「變更內容」就照這三層條列。

有 migration 的 PR，第一件事是看 SQL：

grep -n "DROP\|ADD COLUMN" changes/CAFE-15.patch
16:+ALTER TABLE "products" DROP COLUMN "legacy_sku",
17:+ADD COLUMN     "sold_out" BOOLEAN NOT NULL DEFAULT false;

新增 sold_out 是需求要的。但同一個 migration 還「順便」刪掉了 legacy_sku，patch 開頭的說明寫著「已經沒有程式在讀」。這就是風險段要寫的東西。

會刪欄位的 migration：revert 救不回資料

回滾（rollback）是上線出問題時退回上一個能用的狀態。程式可以用 git revert（新增一個抵銷修改的 commit）退回去，但資料庫不會跟著退：DROP COLUMN 執行後，那一欄的資料就沒了，退回舊版程式也只會看到一個不存在的欄位。Prisma 7 也沒有「往回」的 migration 指令；官方文件的做法是再寫一個新的 migration 把欄位加回來，但加回來的是空欄位，資料救不回來（DevOps 課第 17 課講過同樣的事）。

所以有刪欄位的 PR，風險段至少要寫出一種保護資料的做法：

  • 先備份：上線前把那一欄存一份。例如 pg_dump -t products --data-only（-t 只匯出指定的表，PostgreSQL 18 文件），或在資料庫裡 CREATE TABLE products_legacy_sku_backup AS SELECT id, legacy_sku FROM products;。出事時從備份補回。
  • 先停用、下一版再刪：這個 PR 只加 sold_out；legacy_sku 先確認沒有程式、報表在讀，觀察一段時間，下一版再刪。這就是 DevOps 課第 17 課的 expand／contract：新增和刪除拆成不同次部署。

只新增欄位、有預設值的部分（sold_out）風險低：舊版程式不讀它，revert 程式就能退。把「哪部分退得回來、哪部分退不回來」分開寫，審查者一眼就知道要盯哪裡。

💡 實務上：「順便」是 PR 最常見的風險來源
一個 PR 混了需求和順手的清理（像這裡的刪欄位），審查者容易只看需求那部分；出事要退時，也沒辦法只退一半。看到這種情況，資深工程師會在 PR 留言建議拆開：「sold_out 先合併，legacy_sku 另開一個 PR，先問會計還有沒有在對帳時用到」。刪欄位、改型別、刪資料表這類不可逆的變更，最好單獨一個 PR，說明裡寫出備份位置和復原步驟。

把 CAFE-15 推成 PR 分支：每天都在走的 Git 流程

PR 說明寫好了，還要有一個推上遠端的分支才能開 PR。阿哲的 patch 是照昨天的 main 做的；這段時間小芸已經把 CAFE-14（菜單 API 回傳商品分類）合併進 main，而且她改到了同樣的檔案。這是團隊開發最常見的狀況：你開始做的時候 main 是一個樣子，要開 PR 時 main 已經往前了。以下每一步都在 work/02 執行，先 git status、git log --oneline 看一下：你在 main 上，只有一個 commit，工作目錄是乾淨的。

1. 開分支：名稱照團隊慣例

不在 main 上直接 commit：main 是大家共用、隨時可以部署的版本，只能透過審查過的 PR 合併進來。這個團隊的分支名稱是 類型/單號-英文短描述，類型跟 commit 訊息一樣（feat、fix…），例如 feat/CAFE-15-sold-out。從名稱就看得出是哪張單，PR 列表、CI 紀錄也好找。用 git switch -c 分支名稱 建立並切過去。

2. 完成需求、commit：訊息照 Conventional Commits

這張單的程式阿哲寫好了，用 git apply changes/CAFE-15.patch 套到工作目錄（patch 開頭的說明文字會被略過）。套完先 git status：改過的檔案是 M，新的 migration 資料夾是 ??（untracked，git 還沒追蹤）。新檔案不 add 就不會進 commit，只用 git add -u 或 git commit -a 會漏掉它，PR 合併後部署才發現 migration 不見了。這個 repo 用 git add -A 是安全的：課程的檔案已經排除在外。

commit 訊息照 DevOps 課第 14 課的 Conventional Commits：第一行 類型(範圍): 描述，72 字以內；空一行寫內文（為什麼、怎麼做）；最後一行寫 Refs: CAFE-15，半年後有人 git blame 追到這一行，才找得回需求單。程式是阿哲寫的，內文可以註明。git commit 會開編輯器讓你寫多行；也可以用好幾個 -m，每個 -m 是一段。

feat(products): 商品可以標記已售完

店員用 PATCH /products/:id/sold-out 標記，菜單仍列出售完的商品。

Refs: CAFE-15

3. 推之前先同步：main 已經往前了

你的 origin/main 還停在上次同步的位置，不會自己更新。git fetch origin 把遠端的新 commit 拿下來（不會動你的分支），再用 git log --oneline --graph --all 看整張圖：

* 1c2d3e4 (HEAD -> feat/CAFE-15-sold-out) feat(products): 商品可以標記已售完
| * 9f8e7d6 (origin/main) feat(products): 菜單 API 回傳商品分類
|/
* 5a6b7c8 (main) chore: 咖啡店點餐系統（11/2 的版本）

兩條線分岔了。先搞清楚對方做了什麼：git show origin/main --stat 看小芸改了哪些檔案、commit 訊息怎麼說，等一下解衝突要知道兩邊各自的意圖。（雜湊值每台電腦不同。）

4. rebase 到最新的 main，解衝突

這個分支還只有你在用，還沒開 PR，所以用 rebase：把你的 commit 重新套到 origin/main 後面，歷史是一直線，審查者看到的 diff 就是「最新的 main 加上你的改動」。rebase 之前先執行一次 git config merge.conflictStyle zdiff3（只對這個 repo 生效）：衝突標記會多顯示原本的版本，你才看得出兩邊各自「改了什麼」，而不只是「現在長怎樣」。然後 git rebase origin/main：

CONFLICT (content): Merge conflict in api/prisma/schema.prisma
CONFLICT (content): Merge conflict in api/prisma/seed.sql
CONFLICT (content): Merge conflict in api/src/products/products.module.ts
error: could not apply 1c2d3e4... feat(products): 商品可以標記已售完

三個檔案衝突。打開 schema.prisma：

<<<<<<< HEAD
  legacySku  String?     @map("legacy_sku") // 舊 POS 系統的商品代碼…
  category   String      @default("drink") // 菜單分類：drink（飲料）、food（餐點）
||||||| parent of 1c2d3e4 (feat(products): 商品可以標記已售完)
  legacySku  String?     @map("legacy_sku") // 舊 POS 系統的商品代碼…
=======
  soldOut    Boolean     @default(false) @map("sold_out") // true＝今天賣完…
>>>>>>> 1c2d3e4 (feat(products): 商品可以標記已售完)

三段分別是：HEAD（rebase 時是 main，也就是小芸那邊）、||||||| 後面的原本版本、======= 後面你的 commit。拿原本版本跟兩邊比，就看得出各自的改動：小芸新增了 category；你的 commit 刪掉 legacySku、新增 soldOut。正確的結果是兩邊的改動都做到：有 category、有 soldOut、沒有 legacySku。

最常見的錯是「兩段都留下」：legacySku 就被加回來了。這種錯不會讓 rebase 失敗，但 schema 說有這一欄，CAFE-15 的 migration 卻把它刪了，程式和資料庫對不上。seed.sql 是同一種狀況，products.module.ts 則是兩邊改了同一行，要合成一行。每個檔案都先回答「兩邊各想做什麼」，再寫出兩件事都成立的版本。

解完一個檔案就 git add 它；git status 會列出還沒解完的（UU）。全部 add 之前，git diff --cached --check 可以抓出忘了刪的衝突標記；在 learn/ 執行 node check.mjs delivery 02 會跑 prisma generate、型別檢查、migration 和 seed，衝突解錯通常在這一步就現形（這時練習 4 還會顯示 rebase 沒結束，正常）。都過了再 git rebase --continue：它會開編輯器讓你確認 commit 訊息，直接存檔離開就沿用原本的。弄亂了想重來：git rebase --abort 回到 rebase 之前。

5. 推上去、開 PR

git push -u origin 分支名稱：-u 讓本機分支記住它對應的遠端分支，之後只要打 git push。如果你在 rebase 之前就推過，rebase 換掉了 commit，一般的 push 會被拒絕；這時要用 git push --force-with-lease，不要先 git pull（會把舊的 commit 合併回來，同樣的改動出現兩次）。推上去之後，用練習 3 的 pr.md 開 PR。

💡 實務上：開 PR 之前同步一次，合併之前再同步一次
main 越晚同步，衝突越大、越難看懂。習慣是開工前 git fetch 一次，開 PR 前 rebase 一次；PR 開著時 main 又往前、出現衝突，再 rebase 一次並 --force-with-lease，在 PR 留一句「已 rebase 到最新 main，解了 schema.prisma 的衝突」，審查者才知道要重看哪裡。衝突的另一邊是同事的工作：看不懂對方為什麼這樣改，直接問他，不要猜著把它蓋掉。

練習 8：你昨天把 feat/CAFE-15-sold-out 推上去了，今天 rebase 到最新的 main 之後再 git push，被拒絕（rejected, non-fast-forward）。這個分支只有你在推。接下來怎麼做？

✓ c。rebase 換掉了 commit，遠端那份是舊的，覆蓋它是對的；--force-with-lease 在有人另外推了 commit 時會拒絕，不會在不知情下蓋掉別人的工作。a：遠端是 rebase 之前的舊 commit，pull 會把新舊兩套合在一起，同樣的改動出現兩次，還多一個 merge commit。b：結果一樣能推上去，但有人在你的分支推過東西時會被直接蓋掉。d：PR 綁著分支，刪掉分支可能讓 PR 被關閉。

常見錯誤

  • 拿到需求單就開工：做到一半才發現時區、營業時間沒講清楚，已經寫好的程式和存進去的資料都要改。開工前先列問題，會阻擋開工的先問。
  • 只丟開放式問句：「時間要怎麼處理？」換來另一個模糊回答。每題附上預設答案和具體例子。
  • 驗收條件只有快樂路徑：「08:00 選 10:00 可以」測不出任何 bug。每條規則要有接受、拒絕和剛好在分界上的例子。
  • 邊界例子同時違反好幾條規則：08:01 送出、選 08:14，被拒絕的原因是沒對齊，測不到 15 分鐘的規則。邊界例子只讓一條規則落在分界上。
  • 時間沒寫位移，或把 Z 當成台北時間：07:00Z 是台北 15:00。例子一律寫 +08:00，看到 Z 先換算。
  • PR 說明只寫做了什麼：沒寫怎麼驗證、出事怎麼退，審查者只能猜。照五段範本寫，如何驗證要有可以照貼的指令。
  • 以為 revert 能救回刪掉的欄位：revert 只還原程式。刪欄位前先備份，或先停用、下一版再刪。
  • 解衝突時兩段都留下：一邊刪掉的東西（這課的 legacySku）就被加回來了。先用 zdiff3 看原本的版本，弄清楚兩邊各改了什麼，再寫出兩邊改動都成立的結果。
  • 新檔案沒有 add：git add -u、git commit -a 只收已經追蹤的檔案，新的 migration 會留在你的電腦上。commit 前看一次 git status，不能有 ??。
  • rebase 之後 push 被拒絕就 git pull：舊的 commit 被合併回來，同樣的改動出現兩次。只有你在用的分支，用 --force-with-lease。

小結

  • 一句話的需求單藏著很多決定。開工前列出問題，每題附上你的預設答案和具體例子，讓對方只要回對或不對。
  • 可執行的驗收條件：Given/When/Then 加具體例子，例子要有接受、拒絕和邊界；邊界例子只讓一條規則落在分界上。
  • 時間一律寫成帶位移的 ISO 8601（2026-11-03T08:15:00+08:00），Z 是 UTC。
  • 垂直切片：每一片從資料庫做到畫面、做完就能安全上線。CAFE-12 第一片是「今天的時段＋每時段 10 單」。
  • PR 說明五段：目的、變更內容、驗收條件對照、如何驗證、風險與回滾。會刪欄位的 migration 要寫出 revert 救不回資料，以及備份或分兩版刪的做法。
  • 每天的 Git 流程：照慣例開分支 → commit（Conventional Commits，寫出單號）→ git fetch → git rebase origin/main 解衝突 → 推上去開 PR。解衝突是讓兩邊的改動都成立，不是兩段都留下；推過的分支 rebase 後用 --force-with-lease。
