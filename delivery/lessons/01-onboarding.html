階段 1：接手與第一個需求 · 第 1 課

接手專案：把系統跑起來、讀 README、追一筆訂單從畫面到資料庫

第一天報到。主管丟給你一個資料夾：「這是咖啡店的點餐系統，先跑起來，下午開始接需求單。」系統已經在線上用了一段時間，寫它的人有的已經離職，README 也很久沒人更新。這種已經在運作、帶著歷史包袱的系統叫棕地專案（brownfield）；從零開始寫的叫綠地專案（greenfield）。工作中你碰到的幾乎都是棕地。

這門課接下來 12 課都在同一個程式庫上做，所以這一課也是在認識你之後每天要用的專案。

這課的路線：
  1. 系統地圖：這個專案有哪幾個程式在跑，一筆請求怎麼從瀏覽器走到資料庫。
  2. README 不可信時、照 README 跑一次：照文件跑不起來時去程式哪裡找證據，再把 README 修對（新人的第一個 PR 常常就是這個）。
  3. 追一筆訂單：一個功能經過哪些檔案和資料表；客服轉來 bug 時，怎麼找到那一次請求。
  4. 確認實際行為：用 curl 送邊界輸入看系統現在怎麼反應，覺得是 bug 也先記下來，不順手修。
  5. 接手第一週該問的問題：哪些答案程式裡找不到，卡多久該去問人。
這課會用到：
  • NestJS 課第 12 課的 docker compose up -d --wait：照 compose.yaml 在背景啟動容器，等每個服務都 healthy 才結束。
  • NestJS 課第 13 課的 migration 與種子資料：prisma migrate deploy 把 migration 檔套到資料庫建出資料表，seed 再放進讓系統能動的初始資料。
  • Node 課第 2 課的環境變數：程式用 process.env.X 讀設定，開發時寫在 .env 檔裡。
  • Vue 課第 16 課的 API 層：元件不直接寫 fetch，而是呼叫 API 模組裡的函式，由它統一送請求、處理錯誤。

先拿到程式

這門課的程式庫叫 cafe。在 learn/ 資料夾執行：

node check.mjs delivery 01

第一次執行會建立 delivery/practice/work/01/，這就是你接手的專案，順便把 api/.env.example 複製成 api/.env。資料庫還沒啟動，所以你會看到這段訊息，先不用管它：

這一題要用 PostgreSQL，但 127.0.0.1:5436 沒有回應：課程的資料庫容器還沒啟動。

套件已經裝在 delivery/practice/node_modules（所有課號共用一份），所以這門課不用在專案裡 npm install。之後的指令都在 work/01 裡執行：

cd delivery/practice/work/01

系統地圖：一筆請求會經過哪些程式

讀程式之前，先知道有幾個程式在跑、彼此怎麼連。這個專案有三個：

  • Vite（web/）：開發用的前台伺服器。瀏覽器打 /api/… 時，Vite 把請求轉給 API 並拿掉 /api，這叫 proxy（代理），設定在 web/vite.config.ts。
  • NestJS API（api/）：處理請求、讀寫資料庫。每個請求結束時在終端機印一行 log，例如 {"requestId":"…","method":"POST","path":"/orders","status":201,"durationMs":233}。
  • PostgreSQL：用 compose.yaml 在 Docker 裡跑。容器裡是 5432，對應到你電腦的 5436，避開其他課的資料庫（port 對應的寫法見 DevOps 課第 10 課）。

log 會印在執行 npm run dev 的那個終端機。出問題時第一個要看的就是它。

README 不可信時，去哪裡找答案

新人報到時看的說明叫入職文件（onboarding doc），通常就是 README 的「快速開始」。它最容易過時：程式改了，沒人回頭改文件。照著做失敗時，不要一直重做同樣的步驟，去找程式裡的證據。程式是真的在跑的東西，文件只是某個人某天的描述。接手既有系統的整套方法在工程實務課第 5 課，這一課在真的程式庫上做一次。

想知道去看
有哪些指令可以跑根目錄的 package.json 的 scripts
要設定哪些環境變數api/.env.example，以及程式裡讀 process.env.X 的地方
API 開在哪個 portapi/src/main.ts 的 listen(…)，和啟動時的 log
前台開在哪個 portweb/vite.config.ts 的 server.port
資料庫在哪compose.yaml 的 ports

找到正確答案後，以程式為準修文件，不是改程式去配合文件。下一個新人才不會再卡一次。

💡 實務上：新人的第一個 PR 常常就是修 README
你是團隊裡唯一「完全照文件做」的人，文件哪裡錯只有你看得最清楚。邊做邊把卡住的地方、真正的指令和錯誤訊息記下來，當天就開一個只改 README 的小 PR。它風險低、review 很快，還能順便認識 review 的流程和團隊的人。只改文件，不要夾帶程式修改。

跟著做：照 README 跑一次，修好第一個卡點

先打開 README.md，照「快速開始」做。第一步啟動資料庫：

docker compose up -d --wait

你應該看到（第一次會先下載映像，比較久）：

 Container learn-delivery-postgres Created
 Container learn-delivery-postgres Starting
 Container learn-delivery-postgres Started
 Container learn-delivery-postgres Waiting
 Container learn-delivery-postgres Healthy

接著照 README 設 DB_HOST、執行 npm run dev。等終端機出現 Nest application successfully started，用 README 寫的網址測試：

curl http://localhost:3000/health
curl: (7) Failed to connect to localhost port 3000 after 1 ms: Couldn't connect to server

連不上。這是第一個卡點。不要重做，去找 API 真正開在哪裡。另開一個終端機（npm run dev 那個要一直開著），在 work/01 執行：

grep -n listen api/src/main.ts
8:await app.listen(process.env.PORT ?? 3100)

cat api/.env
PORT=3100
DATABASE_URL=postgresql://learn:learn@127.0.0.1:5436/cafe

process.env.PORT ?? 3100 的意思是：有 PORT 這個環境變數就用它，沒有就用 3100。.env 也寫 3100。所以 API 在 3100：

curl http://localhost:3100/health
{"status":"ok"}

第一個卡點解決了：README 的 3000 是錯的。順便注意 .env 裡沒有 DB_HOST，連線設定是整串的 DATABASE_URL（api/src/common/prisma.service.ts 讀的就是它）。README 說的 DB_HOST 從頭到尾沒有作用。

還有第三個問題要你自己找：打開 http://localhost:5174，菜單出現 Internal server error。回去看跑 npm run dev 的終端機，紅色的 ERROR 裡有這一行：

Database `cafe` does not exist on the database server

資料庫容器起來了，但裡面還沒有這個專案的資料庫和資料表。看 package.json 的 scripts，哪一個指令在做「建表＋種子資料」？（種子資料（seed）是讓系統能動的初始資料，這裡是菜單和顧客。）跑完它、重新整理頁面，就會看到 6 個商品。這就是練習 1 要寫進 README 的步驟。

想「整個重來」時，不要用 docker compose down -v：-v 會連資料庫的 volume 一起刪掉，所有資料都不見。只是要停掉容器，用 docker compose stop 或 down（不加 -v）。

追一筆訂單：從按鈕到資料表

系統跑起來後，下一件事是知道「一個功能」在程式裡怎麼走。沿著一個請求經過的每一層，找出它在哪個檔案、哪個函式被處理，這叫請求追蹤（request tracing）。以「送出訂單」為例，在畫面上加兩樣商品、到購物車按「送出訂單」，然後一站一站找：

  1. 畫面：按鈕在 web/src/pages/CheckoutPage.vue，<form @submit.prevent="submit"> 呼叫的是 submit 函式。
  2. 前端 API 模組：submit 呼叫 createOrder(…)，從 import 看出它在 web/src/api/orders.ts；它再呼叫 web/src/api/client.ts 的 api()，那裡才真的 fetch('/api' + path)。
  3. 網路：打開瀏覽器的開發者工具 → Network，再送一次，會看到 POST /api/orders，狀態 201。點進去看 Response Headers 的 x-request-id，它跟 API 終端機裡那一行 log 的 requestId 一樣：這是把「這一次點擊」跟「那一行 log」對起來的線索。
  4. API 的入口：用路由字串全域搜尋，比一個一個打開檔案快： 
    grep -rn "Controller('orders')" api/src
api/src/orders/orders.controller.ts:5:@Controller('orders')
    @Controller('orders') 加上 @Post()，就是 POST /orders，交給 OrdersController 的 create 方法。
  5. 商業邏輯：controller 只是把 body 交給 OrdersService.create（api/src/orders/orders.service.ts）。這裡查顧客、查商品價格、算總價，最後 prisma.order.create。
  6. 資料表：prisma.order.create 用的是 api/prisma/schema.prisma 的 model Order（對應 orders 表），裡面 items: { create: … } 是巢狀寫入，同時寫 OrderItem（order_items 表）。Prisma 會把兩張表的寫入包在同一個交易裡，不會只寫一半。

最後到資料庫確認剛剛那筆真的寫進去了：

docker compose exec postgres psql -U learn -d cafe -c 'SELECT id, customer_id, status, total FROM orders ORDER BY id DESC LIMIT 1;'
 id | customer_id | status  | total
----+-------------+---------+-------
  1 |           1 | pending |   250
(1 row)

你的 id 和 total 會依你點的東西不同。products 表在這個請求裡只被讀（查價格），沒有被寫入。分清楚「讀」和「寫」很重要：之後改這個功能時，會被影響的是寫入的那幾張表。

💡 實務上：客服轉來的 bug，第一步是找到那一次請求
顧客說「剛剛送出失敗」，你要找的是 API log 裡屬於他的那一行。如果前端在錯誤畫面上顯示（或回報時附上）x-request-id，用它搜尋 log 就能直接找到，不用靠「大概幾點」去猜。正式環境的 log 通常集中在一個查詢介面（例如雲端服務的 log 平台），查法一樣是搜尋 requestId。接手時順便確認：這個專案的 log 存在哪、留幾天、能不能用 requestId 查。

確認實際行為：先記錄，不要順手修

文件、規格、你的猜測都可能跟系統不一樣。系統現在真正的反應叫實際行為（actual behavior），要改任何東西之前都先確認它。最直接的方法是送幾個邊界輸入，看回什麼。示範一個：送一個不存在的商品 id 999。

curl -i -X POST http://localhost:3100/orders -H 'Content-Type: application/json' -d '{"customerId":1,"items":[{"productId":999,"quantity":1}]}'
HTTP/1.1 404 Not Found
x-request-id: 6aa10907-…
…
{"message":"找不到商品","error":"Not Found","statusCode":404}

-i 讓 curl 印出狀態行和標頭，第一行的 404 就是狀態碼。-d 後面是 JSON body，用單引號包起來，裡面的雙引號才不會被 shell 吃掉。-H 'Content-Type: application/json' 告訴 API「body 是 JSON」；少了它，curl 會當成表單送出，API 讀不到欄位，只會回 422。

接著你會自己試另外兩個：下架的商品（菜單上看不到的 7 號「桂花烏龍」）和數量 0。其中有的結果會讓你覺得「這是 bug」。接手第一週的目標是理解，不是修：

  • 你還不知道有沒有人依賴這個行為。例如店員可能用某種奇怪的單做招待。
  • 順手修的東西會混進你的第一個 PR，review 的人分不清哪些是需求、哪些是你的判斷。
  • 修 bug 要有測試、要排優先序，那是團隊的決定。

所以把它寫進 docs/KNOWN_ISSUES.md：一個問題一節，固定三行：重現指令（別人複製貼上就能看到同樣的結果）、影響（誰會遇到、會發生什麼事）、優先序（P1 最急，P3 可以排後面）。這兩個問題在第 4、5 課會修掉。

💡 實務上：優先序看「誰會遇到、多常遇到、有沒有替代做法」
一般顧客在正常操作下就會碰到、而且沒有替代做法的（例如送不出訂單），通常排 P1；只有直接打 API 才會發生、或有簡單替代做法的，排 P2、P3。你提的是建議，最後由團隊（常常是 PM 或技術主管）決定。真實團隊多半記在 issue 系統（GitHub Issues、Jira）而不是 Markdown 檔，但內容一樣：別人能照著重現、知道影響多大，才排得出優先序。

接手第一週該問的問題

有些答案程式裡找不到，只能問人。第一週就問，比出事時才問好：

  • 怎麼部署？誰可以部署？出事時怎麼回滾？
  • 正式環境的 log、錯誤通知在哪裡看？
  • 哪些地方不能碰（例如付款、會影響帳務的資料表）？要改時找誰？
  • 測試怎麼跑？CI 在哪裡？

自己找證據跟問人不衝突。原則是：先花一點時間找（看程式、看 log、搜尋），卡了大約 30 分鐘還沒有新線索就問，而且帶著你已經查到的東西去問（「我看到 main.ts 是 3100，但 README 寫 3000，哪個是對的？」），對方幾秒就能回答。

練習

前面的「跟著做」都在 delivery/practice/work/01 裡。寫完任何一題，回到 learn/ 執行 node check.mjs delivery 01 判分。判分用的是另一個專用的資料庫（每次重建），不會動到你 npm run dev 用的 cafe。

練習 1：修好 README 的「## 快速開始」，讓下一個新同事照著做就能成功。

  • 快速開始的 code block 依序要有：啟動資料庫（docker compose up -d --wait）、建表與種子資料（是 package.json 裡的哪個 script？）、npm run dev。可以加註解或其他行，順序不能錯。
  • 寫到的每個 npm run … 都要真的存在於 package.json。
  • 整份 README 不能再出現 DB_HOST 和 3000，改成正確的說法：寫出 API 真正的網址（http://localhost: 加上正確的 port），「## 設定」那一段寫出 API 真正讀的連線設定 DATABASE_URL。
  • 填 onboarding.json：apiPort（API 的 port）、webPort（前台的 port）、healthPath（API 的健康檢查路徑）。數字不加引號。

判分會把 port 跟 main.ts、vite.config.ts 比對，並實際打一次 healthPath（要回 {"status":"ok"}）。

練習 2：把「送出訂單」經過的站依序寫進 trace.json。

  • steps 每一站是 { "layer": "web" | "api" | "db", "file": "從專案根目錄算的路徑", "symbol": "名稱" }。函式寫名字（submit），類別的方法寫成 類別.方法，資料表寫 Prisma 的 model 名稱。
  • 至少要依序包含：畫面的送出函式 → 前端 API 模組的函式 → controller 的方法 → service 的方法 → schema 裡的 model。中間可以多列（例如 client.ts 的 api），順序不能顛倒，每一站都要真的存在。
  • tables：這個請求寫入的資料表名稱（資料庫裡的表名，不是 model 名稱），例如 ["xxx", "yyy"]。

判分會實際下一單，比對前後筆數有變的表。

練習 3：確認實際行為，記錄問題。只記錄，不修程式。

  • 仿照示範的 curl，對 POST /orders 送出三個請求：下架商品（productId 7）、數量 0（productId 1，quantity 0）、不存在的商品（productId 999）。把三個狀態碼填進 observed.json 的 offlineProduct、zeroQuantity、unknownProduct。要填實際看到的，不是 README 寫的。
  • 在 docs/KNOWN_ISSUES.md 把「下架商品」和「數量 0」兩節的 TODO 填好：重現指令 寫一行完整的 curl（含 http://localhost:3100/…、-H 'Content-Type: application/json' 與 -d '…'，直接複製你剛剛成功的那一行最保險；body 要真的帶著那個問題的輸入），影響 寫誰會遇到、會怎樣，優先序 寫 P1、P2 或 P3。

判分會照你的重現指令真的送一次，看能不能重現；也會確認訂單程式還是接手時的樣子。

練習 4：README 說 API 在 3000 port，但你怎麼連都連不到。最可靠的下一步是？

✓ c。程式和啟動 log 是系統真正的狀態，README 可能過時。a：同樣的步驟不會帶來新資訊。b：問人不是錯，但先花幾分鐘找證據，問題會小很多，通常也就不用問了。d：為了配合文件改程式是本末倒置，其他依賴 3100 的設定（例如 Vite 的 proxy）會跟著壞。

練習 5：接手第一週，你發現數量 0 的訂單會被接受。最恰當的做法是？

✓ a。先記錄、附證據，讓團隊決定什麼時候修。b：你還不知道有沒有人依賴這個行為，而且一個 PR 混兩件事，review 和回滾都變難。c：沒記下來的問題會被忘掉，直到出事。d：還沒評估影響就公告，只會造成恐慌；有證據的紀錄才能讓人做決定。

練習 6：顧客說「我剛剛送出訂單失敗」。哪個線索最能把他那一次點擊和 API 的某一行 log 對起來？

✓ d。requestId 是每個請求唯一的識別碼，就是為了串起同一個請求而設計的。a：同一秒可能有很多請求。b、c：不唯一（很多人點一樣的東西），而且姓名是個資，不應該出現在 log 裡。

常見錯誤

  • API 啟動時出現 EADDRINUSE（3100 被佔用）：通常是別的終端機還開著另一個 API（例如 NestJS 課的 API，它也用 3100）。到那個終端機按 Ctrl-C 關掉再啟動。
  • 照著過時的 README 反覆重試：同樣的步驟不會有不同結果。去看 package.json、.env.example、main.ts 和啟動 log。
  • 只讀程式不執行，用猜的：「看起來應該回 404」不算數。送一次請求，看實際的狀態碼。
  • 一邊接手一邊順手修 bug：第一個 PR 混了好幾件事，也可能破壞別人依賴的行為。記進 KNOWN_ISSUES，交給團隊排。
  • 用 docker compose down -v 重來：-v 會刪掉資料庫的 volume。只想停容器用 stop 或不加 -v 的 down。
  • 修好了卻沒改文件：你花半小時找到的答案，下一個新人還要再找一次。以程式為準，把 README 改對。

小結

  • 棕地專案的文件常常過時。照著做失敗時，去程式裡找證據（scripts、.env.example、listen、log），再以程式為準修文件。
  • 這個專案有三個程式：Vite（5174）、NestJS API（3100）、PostgreSQL（5436）。啟動順序是 docker compose up -d --wait → npm run db:setup → npm run dev。
  • 追一個功能：畫面的函式 → 前端 API 模組 → controller → service → Prisma model／資料表。用路由字串搜尋、Network 面板、psql 確認每一站。
  • x-request-id 把一次點擊和一行 log 對起來。
  • 改東西之前先確認實際行為；接手第一週發現的問題先記錄（重現指令、影響、優先序），不要順手修。
