階段 1：接手與第一個需求 · 第 3 課

跨層功能：從資料表、API 到 Vue 畫面（預約取餐時間）

上一課把 CAFE-12 預約取餐問清楚了，也決定好第一片：不指定＝現點現做、可以選今天的時段、每個時段最多 10 單。這一課把這一片做出來，從資料表一路做到結帳頁。

看起來只是多一個時間欄位，實際上會踩到三個常見的坑：不同時區的機器算出不同結果、測試依賴「現在幾點」、很多人同時搶最後幾個名額時超賣。

這課的路線：
  1. 資料表加上 pickup_at：取餐時間該用什麼型別存、為什麼可以是 NULL、migration 怎麼產生。
  2. 可注入的時鐘與 Asia/Taipei：同一段程式為什麼在台北和 UTC 的機器上算出不同結果，測試怎麼把「現在」固定住。
  3. GET /pickup-slots：今天有哪些時段能選、各剩幾個名額，規則怎麼只寫一次。
  4. 容量與並發：很多人同時搶最後幾個名額時怎麼不超賣；搶票、限量商品、庫存都是同一種問題。
  5. Vue 結帳頁：額滿的時段選不到，送出時被別人搶走要怎麼告訴顧客。
這課會用到：
  • NestJS 課第 3 課的 provider 注入：需要的物件寫在 constructor，由 Nest 建立後注入；測試用 overrideProvider 換成假的。
  • NestJS 課第 7 課的 DTO 驗證：用裝飾器（例如 @IsOptional()）寫出 body 的規則，全域 ValidationPipe 在進 handler 之前擋下不合格的請求。
  • NestJS 課第 15 課的交易與並發：$transaction 裡的寫入一起成功或一起取消；兩個請求同時「先查再寫」會都通過檢查，要改成條件式更新或 SELECT … FOR UPDATE。
  • Vue 課第 16 課的 API 層：元件不直接寫 fetch，而是呼叫 client.ts 這類模組，由它統一送請求、把錯誤丟出來。

第一步：資料表加上 pickup_at

垂直切片從最底層開始：訂單要記住顧客選的取餐時間。在 orders 加一個欄位 pickup_at，型別有兩個決定要做。

用 timestamptz，不用 timestamp 或字串。PostgreSQL 的 timestamp with time zone（簡寫 timestamptz）存的是一個絕對的時間點：寫入 2026-11-03T08:30:00+08:00 和 2026-11-03T00:30:00Z 是同一個值。timestamp without time zone 只存「牆上的鐘幾點」，不知道是哪裡的幾點，UTC 的機器寫入、台北的電腦讀出就差 8 小時。存成「08:30」字串更糟：不能比大小，跨日也算不出來。

可以是 NULL。表裡已經有訂單，它們沒有取餐時間；現點現做的新訂單也沒有。NULL 就是「沒有指定」。如果規定 NOT NULL，migration 要幫所有舊訂單編一個時間，編出來的值是假資料。

跟著做：改 schema、產生 migration

打開 api/prisma/schema.prisma，在 model Order 的 orderedAt 下面加一行。DateTime? 的 ? 表示可以是 NULL，@db.Timestamptz(3) 指定資料庫型別（(3) 是存到毫秒，跟 ordered_at 一樣）：

  orderedAt  DateTime    @default(now()) @map("ordered_at") @db.Timestamptz(3)
  pickupAt   DateTime?   @map("pickup_at") @db.Timestamptz(3) // 預約的取餐時間；NULL＝現點現做

migration 是一個 SQL 檔，記錄「資料庫從上一版變成這一版要執行什麼」，跟程式一起進 git，每個環境照順序套用（PostgreSQL 課第 22 課）。開發時用 migrate dev 比對 schema 和資料庫，自動寫出這個檔並套用到開發資料庫（api/.env 的 cafe）。在 work/03/api 執行：

已經 commit 或套用過的 migration 檔不要改：資料庫記錄了哪些 migration 跑過，改了舊檔也不會再跑，只會讓各環境的資料庫不一樣。要再改就開新的 migration。如果 migrate dev 說偵測到 drift（資料庫和 migration 記錄對不起來，通常是手動改過表）並問要不要 reset，開發資料庫可以回答 y 重建，再 npm run db:setup 補種子資料；正式環境不用 migrate dev。
💡 實務上：加「可以是 NULL、沒有預設值」的欄位最安全
PostgreSQL 加這種欄位只改表的定義，不用改寫既有的每一列，大表也很快；舊版程式不讀這個欄位，回滾程式也不受影響。要 NOT NULL 的欄位，資深工程師會拆成幾次部署：先加可為 NULL 的欄位、程式開始寫入、回填舊資料、最後才加 NOT NULL（DevOps 課第 17 課的 expand／contract）。PR 說明裡寫清楚「舊資料的這一欄會是什麼」，報表和客服才知道 NULL 代表什麼。

時間：可注入的時鐘與 Asia/Taipei

規則幾乎都跟「現在」有關：至少 15 分鐘後、只能選今天。這裡有兩個問題。

問題一：機器的時區會改變結果

正式機跑在 UTC，你的 Mac 跑在台北（時區與 Intl 的基礎在 TypeScript 課第 6 課）。Date 的 getHours()、沒指定 timeZone 的 toLocaleTimeString() 都用程序所在的時區。用 TZ 環境變數模擬兩台機器，各執行一次同一段程式：

TZ=UTC node -e "const d = new Date('2026-11-03T08:30:00+08:00'); console.log(d.getHours(), d.toLocaleTimeString('zh-TW'), new Intl.DateTimeFormat('zh-TW', { timeZone: 'Asia/Taipei', hour: '2-digit', minute: '2-digit', hourCycle: 'h23' }).format(d))"
0 上午12:30:00 08:30

TZ=Asia/Taipei node -e "…同一段…"
8 上午8:30:00 08:30

前兩個結果跟著機器變，只有指定了 timeZone: 'Asia/Taipei' 的 Intl.DateTimeFormat 兩邊都是 08:30。在台北的 Mac 上開發時，錯的寫法也會顯示正確，上線才差 8 小時，這就是這種 bug 難發現的原因。這門課的判分程序固定跑在 TZ=UTC，跟正式機一樣，錯的寫法在這裡就會現形。

「今天是幾號」也一樣。台北 11/3 早上 07:00 是 UTC 11/2 23:00：

TZ=UTC node -e "const d = new Date('2026-11-02T23:00:00Z'); console.log(d.toISOString().slice(0, 10), new Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Taipei' }).format(d))"
2026-11-02 2026-11-03

用 toISOString() 取日期拿到的是 UTC 的日期，早上 8 點以前會算成昨天。en-CA 這個語系的日期格式剛好是 YYYY-MM-DD，加上 timeZone 就是台北的今天。

拿到台北的日期字串後，「台北今天 07:30」就是 new Date(`${today}T07:30:00+08:00`)。直接寫 +08:00 是因為台灣沒有日光節約時間，全年都是 +08:00；有日光節約時間的地區（例如美國）不能這樣寫死，要用 Temporal 或時區函式庫算位移。

問題二：測試不能依賴真的「現在」

如果程式直接 new Date()，測試「08:01 送出、選 08:15 要被拒絕」就只能在早上 8:01 跑。可注入的時鐘（injectable clock）是把「現在幾點」也當成一個依賴：程式向 Nest 要一個 Clock，正式執行時拿到真的時間，測試時換成固定的時間。打開 api/src/common/clock.ts：

export abstract class Clock {
  abstract now(): Date
}

class SystemClock extends Clock {
  now() {
    return new Date()
  }
}

@Global()
@Module({ providers: [{ provide: Clock, useClass: SystemClock }], exports: [Clock] })
export class ClockModule {}

抽象類別 Clock 同時是型別和注入用的 token，所以用的時候跟注入 PrismaService 一樣寫在 constructor：constructor(private readonly clock: Clock) {}，要現在時間就 this.clock.now()。測試用 overrideProvider 換掉它（NestJS 課第 3 課用 CLOCK token 做過同樣的事）：

const clock = { t: Date.parse('2026-11-03T08:02:00+08:00'), now() { return new Date(this.t) } }
const app = await createTestApp(AppModule, { override: b => b.overrideProvider(Clock).useValue(clock) })

規則本身寫成純函式：todaySlots(now) 收「現在」當參數、回傳今天還能選的時段，不碰資料庫也不自己取時間。這樣同一個函式可以給 GET /pickup-slots 列時段，也可以給 POST /orders 驗證：「合法的取餐時間」就是「todaySlots(now) 裡的某一個」，規則只寫一次。

💡 實務上：時間的 bug 都出現在分界上
跨日（台北 00:00–08:00 是 UTC 的前一天）、營業時間的最後一格、剛好 15 分鐘，這些地方的 bug 在一般時段測不出來。有了可注入的時鐘，上一課 acceptance.json 的每個邊界例子都能直接寫成測試。資深工程師看到程式裡的 new Date()、Date.now()、getHours() 會在 review 時標出來；排程、優惠到期、營業時間、帳務結算都是同一類問題。

GET /pickup-slots：列出今天能選的時段

時段（slot）是每 15 分鐘一格的取餐時間，用開始時間代表。前台需要知道今天有哪些時段、每格還剩幾個名額。回應長這樣（台北 08:02 時）：

[
  { "start": "2026-11-03T00:30:00.000Z", "label": "08:30", "remaining": 10 },
  { "start": "2026-11-03T00:45:00.000Z", "label": "08:45", "remaining": 0 },
  …
  { "start": "2026-11-03T10:45:00.000Z", "label": "18:45", "remaining": 10 }
]
  • start：Date 在 JSON 裡會變成 UTC 的 ISO 字串。前台送出訂單時把它原封不動當 pickupAt 送回來，不用自己組時間。
  • label：台北時間 HH:mm，由 API 用 Intl.DateTimeFormat 產生。時區是店的業務規則，放在後端算一次，前台只負責顯示。
  • remaining：還能接幾單。額滿的時段也要列出來（remaining: 0），畫面才能顯示成「已滿、不能選」，而不是讓顧客以為那個時段不存在。

每個時段接了幾單記在另一張表 pickup_slots：slot_start（時段開始時間，主鍵）、orders（已接的單數，預設 0）。第一次有人選某個時段時才建立那一列，沒有那一列就是 0 單。為什麼不直接數 orders 表？下一節會看到：搶名額時要有「一列」可以條件式更新。

算 remaining 時用一次查詢拿回今天這些時段的列（where: { slotStart: { in: slots } }），再用 Map 對應，不要每個時段各查一次。比對 Date 要用 getTime()：兩個 Date 物件用 === 永遠不相等。

容量與並發：每個時段最多 10 單

最直覺的寫法是先查、再寫：

const [row] = await tx.$queryRaw`SELECT orders FROM pickup_slots WHERE slot_start = …`
if (row.orders >= 10) throw new ConflictException(…)
await tx.$executeRaw`UPDATE pickup_slots SET orders = orders + 1 WHERE slot_start = …`

一次一個人點的時候它完全正確。問題在兩個請求同時進來：

放在交易裡也一樣：PostgreSQL 預設的 READ COMMITTED 隔離層級下，SELECT 不會鎖住那一列，兩個交易都讀得到 9（NestJS 課第 15 課）。用練習 2 的測試跑這個版本（20 個請求同時搶同一個時段），三次分別成功了 17、18、19 個，上限 10。

修法：條件式更新，看影響了幾列

容量控制（capacity control）是在並發下確保總量不超過上限。關鍵是把「檢查」和「寫入」合成同一個 SQL：

UPDATE pickup_slots SET orders = orders + 1
WHERE slot_start = '2026-11-03T09:00:00+08:00' AND orders < 10;

PostgreSQL 更新一列之前會先鎖住它。第二個交易要改同一列時會等第一個提交，然後用最新的值重新檢查 WHERE：第一個把 9 改成 10 之後，第二個再檢查 orders < 10 不成立，就一列都不改。所以只要看「影響了幾列」：1 是搶到了，0 是額滿。Prisma 的 $executeRaw 回傳的就是影響的列數。

完整的佔名額寫在 OrdersService.create 裡，跟建立訂單放在同一個交易：

return this.prisma.$transaction(async tx => {
  const order = await tx.order.create({ data: { …, pickupAt }, include: { items: true } })
  if (pickupAt) {
    const slot = pickupAt.toISOString()
    // 第一次有人選這個時段時建立那一列；已經有了就什麼都不做
    await tx.$executeRaw`INSERT INTO pickup_slots (slot_start) VALUES (${slot}::timestamptz) ON CONFLICT (slot_start) DO NOTHING`
    const updated = await tx.$executeRaw`UPDATE pickup_slots SET orders = orders + 1 WHERE slot_start = ${slot}::timestamptz AND orders < ${SLOT_CAPACITY}`
    if (updated === 0) throw new ConflictException({ code: 'SLOT_FULL', message: '這個時段已額滿，請改選其他時段' })
  }
  return order
})
  • 同一個交易、都用 tx：$transaction(async tx => …) 裡丟出例外，整個交易回滾。額滿時剛建立的訂單一起消失；訂單寫入失敗時，名額也不會白白被佔掉。用 this.prisma 而不是 tx 執行的那一句不在交易裡。
  • 搶鎖的步驟放最後：從 INSERT／UPDATE 那一刻起，這一列被鎖到交易結束，其他人都在排隊。先建立訂單、最後才搶名額，鎖住的時間最短。Prisma 7.10.1 的互動式交易預設 5 秒逾時，排隊太久會變成 500。
  • ${slot}::timestamptz：$executeRaw 的 ${} 會變成參數，不是字串拼接，不會有 SQL injection；傳 ISO 字串並明確轉型，資料庫就不用猜這個時間是哪個時區。
  • 409 和 422 分開：422 是「這個時間本來就不能選」（顧客或前端的錯）；409 Conflict 是「時間沒問題，但被別人搶走了」，前台要重新載入時段。丟物件給 ConflictException，Nest 會把整個物件當成回應的 body，前台就能讀 code。
做法守得住嗎說明
條件式更新（本課）可以一句 SQL，影響 0 列就是額滿。最簡單
SELECT … FOR UPDATE 再判斷可以先鎖住那一列，其他交易的 FOR UPDATE 要排隊。判斷邏輯複雜、一句 SQL 寫不完時用
SERIALIZABLE 交易＋重試可以衝突時資料庫讓其中一個失敗（40001），程式要重試。寫起來最麻煩
API 記憶體裡的計數器不行每台 API 各記各的，重啟就歸零；正式環境通常不只一台
💡 實務上：「剩下 N 個」的東西都要問同一個問題
時段名額、限量商品、優惠券張數、座位、庫存，都是「先查再寫」會超賣的形狀。資深工程師在 review 看到 if (count < limit) 後面接一個寫入，會先問：「兩個請求同時進來會怎樣？」並要求一個並發測試（像練習 2 的 20 個同時送出），而不是只在本機點一下。上線後超賣，代價是店長要打電話跟顧客道歉。

Vue：結帳頁選時段

API 守住了名額，最後是畫面。結帳頁要做三件事：列出時段讓顧客選、額滿的不能選、送出時被搶走要好好告訴顧客（表單與 v-model 的基礎在 Vue 課第 18 課）。

用原生的 radio。「從幾個選項選一個」就是 <input type="radio">：鍵盤可以用方向鍵切換，螢幕閱讀器會念出這是一組選項中的哪一個，disabled 的選項點不到也送不出去。用 div 加 @click 自己做，這些全部都沒有，只改顏色的「額滿」也還是點得到。第一個選項是「現點現做」（值是空字串），所以不選時段就是現在的行為：

<fieldset>
  <legend>取餐時間</legend>
  <label><input v-model="pickupAt" type="radio" name="pickup" value=""> 現點現做</label>
  <label v-for="s in slots" :key="s.start">
    <input v-model="pickupAt" type="radio" name="pickup" :value="s.start" :disabled="s.remaining === 0">
    {{ s.label }}
  </label>
</fieldset>

送出時 pickupAt: pickupAt.value || undefined：空字串變成 undefined，JSON.stringify 會把它拿掉，API 收到的就是沒有 pickupAt。

把錯誤碼帶到畫面：ApiError

現在的 web/src/api/client.ts 遇到錯誤只丟 new Error(message)，狀態碼和 code 都丟掉了，畫面分不出「額滿」和其他錯誤。改成丟一個帶著這些資訊的錯誤類別（Vue 課第 16 課的做法）：

export class ApiError extends Error {
  constructor(message: string, readonly status: number, readonly code?: string) {
    super(message)
  }
}

// api() 裡：
if (!res.ok) throw new ApiError(String(body?.message ?? `HTTP ${res.status}`), res.status, body?.code)

結帳頁的 catch 就能分辨：e instanceof ApiError && e.code === 'SLOT_FULL' 時，顯示「這個時段已額滿，請改選其他時段」、把選擇清回現點現做、重新呼叫 listPickupSlots()（剛額滿的時段就會變成 disabled），購物車不動。額滿不是顧客的錯，清空購物車等於叫他從頭再點一次。錯誤訊息放在已經有的 <p role="alert"> 裡，螢幕閱讀器會主動念出來。web/src/api/orders.ts 的 OrderRequest 也要加上 pickupAt?: string，型別檢查才會過。

練習

三題都在 delivery/practice/work/03 裡寫，寫完回到 learn/ 執行 node check.mjs delivery 03。判分會用 migration 重建一個判分專用的資料庫、把時鐘固定在幾個時間、在 TZ=UTC 下跑，不會動到你的開發資料庫 cafe。改了 schema.prisma 一定要用 migrate dev 產生 migration 檔，判分只看 migration。

練習 1：先完成「跟著做」的 pickup_at，再仿照它做 pickup_slots，最後實作 GET /pickup-slots。

  • 在 schema.prisma 加 model PickupSlot：slotStart（DateTime @id，對應 slot_start，@db.Timestamptz(3)）、orders（Int @default(0)），用 @@map("pickup_slots")。執行 npx prisma migrate dev --name pickup-slots，再 npx prisma generate。既有的 migration 檔不能改。
  • pickup-slots.ts：todaySlots(now) 回傳台北時間「今天」07:30–18:45 之間、離 now 至少 15 分鐘、每 15 分鐘一格的時段（Date[]，由早到晚）；slotLabel(start) 回傳台北時間 HH:mm。用 Intl.DateTimeFormat 指定 timeZone: 'Asia/Taipei'，不能用 getHours()、toISOString() 取日期。
  • PickupService.availableSlots()：用 this.clock.now() 取現在時間，回傳 [{ start, label, remaining }]；remaining 是 10 減掉 pickup_slots.orders，額滿的也要列出來。
  • 判分會把時鐘固定在台北 08:02（第一個時段要是 08:30）、07:00（UTC 還是前一天）、2026-12-25 10:00（換一天、剛好差 15 分鐘的 10:15 要列出來）、18:40（沒有時段），並在 pickup_slots 放幾列資料檢查 remaining，其中有一列是昨天同一個 HH:mm 的時段，所以要用時間點對應，不能用標籤。

練習 2：POST /orders 接受 pickupAt（可以省略），照驗收條件驗證，並守住每個時段 10 單。

  • DTO 加 pickupAt?: string，用 @IsOptional() 和 @IsRFC3339()：RFC 3339 是 ISO 8601 的子集，一定要有 Z 或 +08:00 這種位移，沒有位移的 2026-11-03T08:30:00 直接 422。
  • OrdersService 注入 Clock。pickupAt 不是 todaySlots(this.clock.now()) 其中一個時，丟 UnprocessableEntityException（422），不能寫入任何東西。
  • 建立訂單和佔名額放在同一個 $transaction，用條件式更新；額滿回 409，body 是 { code: 'SLOT_FULL', message }。省略 pickupAt 時照常下單，pickup_at 是 NULL。
  • 判分會開兩個 API 實例、同時送 20 個同一時段的訂單，成功要正好 10 個；也會在 pickup_slots 先放 7 單，再送 20 個，只能成功 3 個；還會送一筆一定寫入失敗的訂單，確認名額有回滾。

練習 3：結帳頁加上取餐時間的選擇。

  • 一打開就呼叫 listPickupSlots()。每個時段是一個原生 radio，包在含 label 文字的 <label> 裡；第一個選項是「現點現做」。remaining 是 0 的 radio 要 disabled。
  • 選了時段，POST /orders 的 pickupAt 是那個時段的 start；沒選、或選了又改回「現點現做」，就不送 pickupAt。
  • client.ts 改成丟 ApiError（帶 status、code）。收到 409 SLOT_FULL 時，在 role="alert" 顯示含「已額滿」的訊息、重新載入時段、購物車的品項留著、留在結帳頁。其他錯誤（例如 422）照原本顯示 API 的訊息，不能說成已額滿。
  • 判分是元件測試（Vue 課第 22 課）：fetch 換成假的，不需要 API 在跑。

練習 4：為什麼「現在幾點」要透過 Clock provider 取得，而不是在程式裡直接 new Date()？

✓ d。可注入的時鐘讓「08:01 選 08:15 要被拒絕」這種邊界測試不管什麼時候跑都一樣。a、b：效能和框架限制都不是原因。c：時區要靠格式化時指定 timeZone 處理，跟時間從哪裡取得無關。

練習 5：20 個人同時搶同一個時段，最後超賣了。下列哪個做法無法解決？

✓ b。記憶體裡的計數器只在一個程序裡有效：開兩台 API 就各記各的，重啟就歸零。a、c、d 都讓資料庫保證同一時間只有一個交易能把名額加上去。

練習 6：時段標籤在你的 Mac 上顯示 08:30，在正式機（UTC）顯示 00:30。應該怎麼修？

✓ b。指定 timeZone 後，結果不受機器時區影響。a：把問題藏起來，換一台機器、一個容器映像就又壞了。c：加 8 小時後的 Date 代表的是另一個時間點，存進資料庫或跟別的時間比較時就錯了，日期也容易算錯。d：顧客要的是台北時間。

常見錯誤

  • 存台北時間字串，或用 timestamp without time zone：不同時區的機器讀出不同的時間，也不能比較大小。用 timestamptz，存絕對的時間點。
  • 直接改已經套用過的 migration：其他環境不會再跑一次，各環境的資料庫從此不一樣。新的變更一律開新的 migration。
  • 用本機時區格式化：getHours()、沒指定 timeZone 的 toLocaleTimeString()、用 toISOString() 取日期。開發機剛好在台北所以沒發現，上線差 8 小時。
  • 程式裡直接 new Date()：測試只能在特定時間跑。「現在」從 Clock 拿，規則寫成收 now 參數的純函式。
  • 先查剩幾單再寫入：並發下兩個請求讀到同一個數字，一起超賣。把檢查放進 UPDATE … WHERE orders < 10，看影響的列數。
  • 佔名額和建立訂單不在同一個交易：其中一步失敗時，名額被白佔或超出。兩步都用 tx，放在同一個 $transaction。
  • 額滿時清空購物車、或只把選項變灰：顧客要重點一次，或點了變灰的選項還是送得出去。保留購物車、用 disabled、重新載入時段。

小結

  • 跨層功能從資料表往上做：migration（pickup_at timestamptz，可為 NULL）→ API 規則與驗證 → 畫面。已經套用的 migration 不改，Prisma 7 改完 schema 要自己 prisma generate。
  • 時間存成 timestamptz，顯示和判斷「今天」一律用 Intl.DateTimeFormat 指定 timeZone: 'Asia/Taipei'，不依賴機器時區。
  • 「現在」從可注入的 Clock 取得，規則寫成純函式 todaySlots(now)，列時段和驗證共用同一份規則，測試可以固定在任何邊界時間。
  • 容量用條件式更新守住：UPDATE … SET orders = orders + 1 WHERE … AND orders < 10，影響 0 列就是額滿；和建立訂單放在同一個交易，搶鎖的步驟放最後。
  • 422 是不能選的時間，409 SLOT_FULL 是被搶走了；前台用 ApiError 讀到 code，顯示已額滿、重新載入時段、保留購物車。
