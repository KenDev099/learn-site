階段 4：上線與維運 · 第 12 課

線上事故演練：定位、止血、復原、事後檢討

星期一早上 7:40，你的手機響了。監控系統的告警：「POST /orders 最近 5 分鐘的 p95 > 1 s（目前 1.9 s）」。這是一天最忙的時段，客人在門口排隊用手機點餐，送出訂單要轉好幾秒，有些直接失敗。你是這週的值班工程師。

這時候最常見的錯誤是一頭栽進程式碼找 bug。這一課用一份固定的事故現場（log、部署紀錄、資料庫指標），照資深工程師的順序把整個流程走一次。

這課的路線：
  1. 事故的前五分鐘：為什麼第一件事是分工和記下時間，而不是打開程式碼。
  2. 定位：用 log 和部署紀錄找出從什麼時候開始、哪個路由在拖累其他人、跟哪次變更有關。
  3. 止血：關旗標、整版回滾、重啟 API 該選哪一個，為什麼回滾可能把安全修正一起丟掉。
  4. 修根因：用 EXPLAIN 看出搜尋為什麼掃整張表，用 pg_trgm 的 GIN 索引修好，再確認真的復原。
  5. 不究責的事後檢討：怎麼寫才能排出改善項目，而不是找戰犯。
這課會用到：
  • 第 5 課用 jq 查 log：一行一個 JSON，用 select 篩選、-s 把整個檔案收成陣列再分組統計。
  • 第 10 課的功能旗標：存在 feature_flags 表、程式執行時才讀的開關，用 npm run flag 修改，不用重新部署就能關掉一條路徑。
  • 第 11 課的 EXPLAIN 與索引：EXPLAIN ANALYZE 看資料庫是掃整張表（Seq Scan）還是走索引；正式表上建索引用 CREATE INDEX CONCURRENTLY，才不會擋住寫入。

事故的前五分鐘：先分工，先記時間

事故（incident）是「線上服務出問題、影響到使用者，需要立刻處理」的狀況。處理事故有三件事同時在進行：查原因、動手操作、對外說明。全部壓在一個人身上，最先被犧牲的是溝通，接著是判斷。所以就算只有兩個人，第一件事也是分工（DevOps 課第 25 課有完整的流程）：

角色做什麼這次是誰
事故指揮（incident commander）決定要做什麼、指派工作、決定什麼時候算結束。自己不動手查值班工程師（你）
溝通（communications）固定時間對店長、客服發更新，讓他們不用一直來問後端 tech lead
操作（operations）查 log、改旗標、跑 migration，做之前先說、做完回報你（人少時指揮兼操作，但溝通一定要交出去）

接著開一份共用的時間線，每做一件事、每看到一個現象，當下寫一行時間：「07:40 告警」「07:44 確認下單 p95 1.9 s」「07:48 關閉旗標 orders.search」。事後憑記憶補寫的時間線一定不準，而事後檢討的品質取決於它。對外的更新用固定格式，第一則在 10 分鐘內發出，之後固定間隔更新（例如每 15 分鐘），就算沒有進展也發：

【處理中】07:45 點餐系統下單變慢
影響：07:35 起顧客送出訂單要等好幾秒，部分失敗；查訂單、菜單也變慢
現在在做：工程師正在處理，優先讓下單恢復正常
下一次更新：08:00 前

注意這則更新沒有猜原因（07:45 還沒有證據），也沒有承諾修好的時間。說「影響是什麼、正在做什麼、下次什麼時候更新」就夠了。

💡 實務上：店長在乎的是「現在能不能點」
事故中最常被打斷的是指揮的人：店長、客服、主管輪流私訊問「好了沒」。固定頻道、固定時間、固定格式的更新能把這些問題擋掉，讓查問題的人專心。客服拿到更新後才能回覆顧客（例如「請先到櫃台點餐」）。很多團隊把狀態更新的範本和角色分工寫在 runbook（處理手冊：常見狀況一步一步怎麼處理）裡，值班第一天就要知道它在哪。

定位一：從什麼時候開始

手上有三份資料：API log、部署紀錄、資料庫指標。先看 log（JSON log 與集中查詢見 DevOps 課第 21 課）。每個請求一行，context 是 "HTTP"，message 裡有路徑、狀態碼和花了幾毫秒（durationMs），timestamp 是 Unix 毫秒（UTC）：

{"level":"log","pid":1,"timestamp":1794785580000,"message":{"requestId":"…","method":"POST","path":"/orders","status":201,"durationMs":23,"customerId":4,"productIds":[2]},"context":"HTTP"}

先回答「從什麼時候開始變慢」：依分鐘分組，算每分鐘的請求數、平均和最大的 durationMs。在 work/12 執行：

$ jq -rs '[.[] | select(.context == "HTTP")]
  | group_by(.timestamp / 60000 | floor)
  | .[]
  | [(.[0].timestamp / 1000 + 8 * 3600 | strftime("%H:%M")), length,
     (map(.message.durationMs) | add / length | round), (map(.message.durationMs) | max)]
  | @tsv' logs/incident.ndjson

拆開來看：-s 把整個檔案讀成一個陣列；group_by(.timestamp / 60000 | floor) 把同一分鐘的請求放在一組；+ 8 * 3600 再 strftime("%H:%M") 把 UTC 轉成台北時間；@tsv 用 Tab 分隔印出。輸出（只列 07:28 之後，欄位是：分鐘、請求數、平均 ms、最大 ms）：

07:32 以前每分鐘平均 20 ms 以內，07:33 突然出現 1.7 秒的請求，之後一分鐘比一分鐘慢。這張表回答了「從什麼時候開始有異狀」，但告警看的是另一個指標：下單（POST /orders）每分鐘的 p95。p95 是把請求依花費的時間由快到慢排好，排在第 95% 位置的那個：100 個請求裡有 95 個不超過它（第 11 課）；平均會被大量很快的請求拉低，也會被少數極慢的請求拉高，兩個方向都會騙人。事故的開始影響時間要用跟告警同一個指標算：下單 p95 第一次超過 1 秒的那一分鐘。它可能比第一個慢的請求晚幾分鐘，因為一開始只有新功能自己慢，壓力還沒傳到下單。這是練習 1 要你自己算的。

定位二：哪個路由、跟哪次變更有關

接著把 07:33 之後的請求依路由分組。log 裡的 path 是實際的網址，/orders/58231 和 /orders/58232 是同一個路由，/orders/search?q=… 每次的 q 也不一樣，所以先正規化：split("?")[0] 去掉查詢字串，gsub("/[0-9]+"; "/:id") 把數字換成 :id：

$ jq -rs '[.[] | select(.context == "HTTP")
    | select((.timestamp / 1000 + 8 * 3600 | strftime("%H:%M")) >= "07:33")
    | {route: (.message.method + " " + (.message.path | split("?")[0] | gsub("/[0-9]+"; "/:id"))),
       ms: .message.durationMs}]
  | group_by(.route)
  | map([.[0].route, length, (map(.ms) | add / length | round), (map(.ms) | max)])
  | sort_by(-.[2])
  | .[] | @tsv' logs/incident.ndjson

POST /orders	108	1382	5049

最後看資料庫指標 ops/db-metrics.csv：07:35 起 CPU 95–99%，連線 10/10（連線池滿了），07:38 開始出現 timeout exceeded when trying to connect：下單等不到連線，直接失敗。這時候很容易下結論「CPU 不夠」「連線池太小」，但它們是症狀，不是原因。一路問「為什麼」往下追：

如果把 CPU 加倍或連線池調大，只會讓更多全表掃描同時壓在資料庫上，下單照樣排隊。只看一個指標就下結論是事故中最常見的誤判；要把 log、部署紀錄、指標三份資料的時間對在一起。

止血：選影響最小的手段

止血（mitigation）是先讓影響停止擴大，不一定修好根因。復原（recovery）是回到正常、而且資料一致的狀態。止血優先，因為每多一分鐘，就有更多客人點不到餐；根因可以等止血之後慢慢修（「先止血，再找原因」見系統設計課第 21 課）。現在有幾個選項：

手段效果代價
關閉旗標 orders.search幾秒內生效（每個請求都讀旗標），搜尋停止送查詢店員暫時不能搜尋，改用訂單編號找單。其他功能完全不受影響
整版回滾到 v2.7.2搜尋消失SEC-7 的修正也一起消失：任何人改網址上的訂單 id 就能看別人的訂單。用一個問題換回另一個更糟的問題
重啟 API連線暫時清空，數字可能短暫恢復店員一搜尋又會回來。只是把問題延後，還會中斷進行中的請求
加大連線池、升級資料庫不確定對準的是症狀；更多連線＝更多全表掃描同時跑，資料庫可能更慢

SEC-7 修的是 BOLA（Broken Object Level Authorization，物件層級授權失效）：API 只檢查「你有沒有登入」，沒有檢查「這筆資料是不是你的」，所以改 id 就能讀到別人的資料（Auth 課第 19 課）。v2.7.x 連登入都沒有，回滾等於把每位顧客的訂單、備註重新公開。所以這次的答案很明確：關旗標。這也是 v2.8.0 把新功能放在旗標後面的原因：出問題時只關掉那一個功能，不動同一版裡的其他變更。

動手前在時間線寫一行「07:48 指揮決定關閉 orders.search」，然後執行（在開發環境演練，指令跟正式環境一樣）：

💡 實務上：讓每個變更都能單獨關掉
這次能在幾秒內止血，是因為新功能有旗標。資深工程師在設計發布時就會問：「出問題時，最小的關閉單位是什麼？」新功能放在旗標後面、先開 10% 觀察（第 10 課）；安全修正和新功能最好分成兩次部署，回滾時才不用二選一；也避開尖峰時段部署。事故中想回滾之前，先看那一版還帶了什麼，特別是安全修正和資料庫 migration（新版已經寫進去的資料，舊版程式不一定讀得懂）。

修根因：EXPLAIN 與 pg_trgm 的 GIN 索引

止血之後，壓力解除了，可以好好查原因。搜尋的程式在 orders.service.ts：

this.prisma.order.findMany({
  where: { note: { contains: keyword, mode: 'insensitive' } },   // → note ILIKE '%關鍵字%'
  orderBy: [{ orderedAt: 'desc' }, { id: 'desc' }],
  take: 20,
})

Prisma 的 contains 加上 mode: 'insensitive'，在 PostgreSQL 會變成 ILIKE '%關鍵字%'（不分大小寫的「包含」）。用 EXPLAIN ANALYZE 看資料庫怎麼找（慢查詢的讀法見 PostgreSQL 課第 29 課；docker compose exec postgres psql -U learn -d cafe）：

cafe=# EXPLAIN ANALYZE SELECT * FROM orders WHERE note ILIKE '%燕麥奶%' ORDER BY ordered_at DESC LIMIT 20;
 Limit  (actual time=40.045..41.846 rows=0.00 loops=1)
   ->  Gather Merge  (actual time=40.043..41.844 rows=0.00 loops=1)
         Workers Planned: 1
         ->  Sort  (actual time=38.548..38.548 rows=0.00 loops=2)
               Sort Key: ordered_at DESC
               ->  Parallel Seq Scan on orders  (actual time=38.502..38.502 rows=0.00 loops=2)
                     Filter: (note ~~* '%燕麥奶%'::text)
                     Rows Removed by Filter: 100100
 Execution Time: 41.888 ms

（cost 等欄位省略；~~* 就是 ILIKE。）Seq Scan：整張表掃描，20 萬列每一列都拿來比對一次。Parallel 是 PostgreSQL 把掃描分給 2 個程序一起做（loops=2），所以每個程序各丟掉約 10 萬列。在沒有別人使用的筆電上 40 ms；尖峰時店員每打一個字就送一次，好幾個全表掃描同時跑，還要和下單搶 CPU 與連線，就變成 log 裡的 4 秒。

為什麼不加一般的索引就好？一般的 B-tree 索引是把值排序存起來，像字典一樣只能從開頭找：LIKE '燕麥%'（開頭是燕麥）用得上，'%燕麥奶%'（中間任何位置）用不上，因為不知道從哪裡開始翻。這種「包含」的搜尋要用 pg_trgm（PostgreSQL 課第 28 課）：它把文字切成每 3 個字一組的 trigram，例如 oat milk 會切出 oat、mil、ilk 等，存進 GIN 索引（反向索引：記錄「每一組字出現在哪些列」）。查 '%燕麥奶%' 時，先用索引找出含有這些組合的列，再逐列確認，不用讀整張表。pg_trgm 是 PostgreSQL 內建的擴充功能（官方 postgres 映像就有），CREATE EXTENSION 之後就能用。

兩個限制要知道：關鍵字少於 3 個字切不出完整的一組，索引沒辦法縮小範圍：實測 '%燕麥%' 的計畫裡雖然有 Bitmap Index Scan，但索引回傳了全部 20 萬列，Rows Removed by Index Recheck 將近 20 萬，等於還是全部讀一遍。所以 v2.8.0 的 API 要求 q 至少 3 個字（「計畫裡有索引」不等於「索引有幫上忙」，要看 ANALYZE 的列數）；GIN 索引讓寫入多一點成本，orders 每次新增都要更新它，對咖啡店的下單量來說可以接受。

修法跟第 11 課一樣是兩步：

  1. api/prisma/schema.prisma 的 model Order 加一行： 
    @@index([note(ops: raw("gin_trgm_ops"))], type: Gin)
    type: Gin 指定索引種類，ops: raw("gin_trgm_ops") 指定用 pg_trgm 的比對方式。Prisma 會把它命名為 orders_note_idx。
  2. 新增 migration 資料夾 api/prisma/migrations/20261116000000_orders_note_trgm/migration.sql：先建擴充功能，再用 CREATE INDEX CONCURRENTLY 建索引。事故剛發生，現在最不能做的就是用一般的 CREATE INDEX 把 orders 的寫入擋住，等於再停一次下單。索引的寫法：CREATE INDEX CONCURRENTLY "orders_note_idx" ON "orders" USING GIN ("note" gin_trgm_ops);（本課程在 Prisma 7.10.1＋PostgreSQL 18 實測過：migrate deploy 不會把檔案包進交易，兩句放在同一個檔案可以執行）。

npm run db:setup 套用之後，同一句 EXPLAIN：

 Limit  (actual time=0.151..0.151 rows=0.00 loops=1)
   ->  Sort  (actual time=0.150..0.150 rows=0.00 loops=1)
         Sort Key: ordered_at DESC
         ->  Bitmap Heap Scan on orders  (actual time=0.084..0.084 rows=0.00 loops=1)
               Recheck Cond: (note ~~* '%燕麥奶%'::text)
               ->  Bitmap Index Scan on orders_note_idx  (actual time=0.008..0.008 rows=0.00 loops=1)
                     Index Cond: (note ~~* '%燕麥奶%'::text)
 Execution Time: 0.272 ms

從 42 ms 到 0.3 ms。Bitmap Index Scan on orders_note_idx 先從索引找出可能的列，Bitmap Heap Scan 再去讀那幾列、用 Recheck Cond 確認。正式環境的部署會跑同一個 migration；索引建好（pg_index.indisvalid 是 true）之後，才把旗標打開：

$ npm run flag -- orders.search on
orders.search：0% → 100%（記在 ops/flag-changes.log）

打開之後繼續看指標 15–30 分鐘，下單 p95 和 CPU 都維持正常，才算復原。這次也要檢查資料：07:38 之後有一些下單逾時失敗（500）。訂單是在交易裡建立的（第 3 課），失敗就整筆回滾，不會留下半張單或白佔的取餐名額，但這些客人可能沒拿到餐。客服需要失敗的時間與顧客清單（log 裡 status 500 的 customerId），主動聯絡他們。

不究責的事後檢討

事故結束後幾天內，團隊一起寫事後檢討（postmortem）。目的不是交代，而是找出「系統和流程哪裡讓這件事有機會發生」，並排出改善項目。它必須是不究責的（blameless）：檢討系統與流程為什麼允許錯誤發生，而不是找戰犯。理由很實際：如果寫出來會被點名，下次大家會隱藏問題、晚一點才說，事故只會更大；而且「某某人不小心」沒有任何可以執行的改善。

同一件事，兩種寫法：

找戰犯找系統原因
某某工程師上線前沒有測試效能測試資料只有幾筆訂單，全表掃描在測試環境看不出來；PR 審查沒有要求附新查詢的 EXPLAIN
某某在尖峰時段部署部署流程沒有禁止尖峰時段；新功能的旗標預設直接 100%，沒有先開一小部分觀察
店員一直按搜尋搜尋框每打一個字就送請求，沒有 debounce（停止輸入一段時間才送）

需要指人的地方寫角色（「部署的工程師」「值班工程師」），不寫名字。postmortem.md 的範本有四段：

  • 摘要：兩三句話，發生什麼事、影響誰、多久、怎麼解決。沒參與的人看完這段就知道全貌。
  • 時間線：開始影響、偵測、止血、復原的時間。偵測減開始影響是「多久才發現」，止血減偵測是「發現後多久擋住」，這兩個數字是改善的目標。
  • 根因：技術上的原因（哪個端點、做了什麼），加上流程上為什麼沒有在上線前擋下來。
  • 行動項目：每一項要具體、可驗收，有負責的角色。分兩類：prevent（避免再發生，例如「PR 範本加一項：新查詢要附 20 萬筆資料下的 EXPLAIN」）和 detect（更早發現，例如「每個路由分開告警，任何路由 p95 > 1 s 持續 3 分鐘就通知」）。只寫 prevent，下次換一種原因時還是要等到下單變慢才知道；「加強測試」「大家多注意」這種寫法沒辦法驗收，等於沒寫。
💡 實務上：行動項目要有人追
事後檢討最常見的結局是寫完就放著，三個月後同樣的事故再發生一次。行動項目要開成工作單、排進 sprint，檢討會議的最後確認每一項的負責角色和期限，下一次例會追進度。檢討文件分享給相關的人（PM、客服、維運）：客服知道下次怎麼應對，PM 知道新功能為什麼要先開小比例。寫的時候把時間、數字、指令都寫具體，讓半年後接手的人也看得懂。

練習

三題都在 delivery/practice/work/12 裡做，寫完回到 learn/ 執行 node check.mjs delivery 12。練習 1、3 只檢查你填的值和格式，練習 2 會在判分資料庫放 20 萬張訂單、用 EXPLAIN 確認索引真的有用到。

練習 1：從 log 與部署紀錄定位事故，填 incident.json。

  • startedAt：下單（POST /orders）每分鐘的 p95 第一次超過 1 秒的那一分鐘，ISO 8601 加上時區，例如 2026-11-16T07:00:00+08:00。p95 用排序後第 ceil(0.95 × 筆數) 個（從 1 數起）。從上面「依分鐘統計」的 jq 改：select 只留 POST /orders，把平均換成 p95（map(.message.durationMs) | sort | .[(length * 0.95 | ceil) - 1]）。
  • slowRoute：拖慢系統的路由，格式「方法 路徑」，不含查詢字串。
  • deploy：跟事故有關的部署版本（ops/deploys.log）。
  • rootCause：missing-index、cpu-high、pool-too-small、bad-network 選一個：原因，不是症狀。
  • 判分：startedAt 帶時區，而且落在從 log 算出來的那一分鐘裡（07:xx:00～07:xx:59）；其他三個欄位正確。

練習 2：止血，修根因，再把功能打開。

  • 先 npm run flag -- orders.search off（會自動記在 ops/flag-changes.log），用 curl 確認搜尋回 404、顧客還是看不到別人的訂單。不要整版回滾，orders.controller.ts 與 auth 模組都不用改。
  • 新增 api/prisma/migrations/20261116000000_orders_note_trgm/migration.sql：CREATE EXTENSION IF NOT EXISTS pg_trgm，再用 CREATE INDEX CONCURRENTLY 建 orders(note) 的 GIN（gin_trgm_ops）索引。既有的 migration 不要改。
  • schema.prisma 的 model Order 宣告同一個索引，讓 schema 跟資料庫一致。
  • npm run db:setup 套用、EXPLAIN 確認用到索引之後，npm run flag -- orders.search on。
  • 判分：沒登入查訂單 401、顧客查別人的訂單 404；旗標關閉時搜尋 404、打開時正常；migration 有 pg_trgm、gin_trgm_ops 與 CONCURRENTLY；prisma migrate diff 比對 schema 與資料庫沒有差異；20 萬張訂單時搜尋的 EXPLAIN 用到這個索引、沒有 Seq Scan；ops/flag-changes.log 在部署之後有關閉、之後再打開，最後是開的。

練習 3：寫不究責的事後檢討 postmortem.md。

  • 四段都填：摘要、時間線、根因、行動項目。標題和 - 欄位： 的格式不要改，範本的 TODO 全部換掉。
  • 時間線用 HH:MM（台北時間）：開始影響跟練習 1 同一分鐘；偵測是告警的時間（ops/alerts.log）；止血、復原照你演練的順序寫（止血晚於偵測，復原不早於止血）。
  • 根因寫出端點與缺少的索引；行動項目至少 2 項，類型同時有 prevent 與 detect，每項寫負責角色。
  • 判分：上面每一點（開始影響要跟練習 1 同一分鐘；根因要同時有 /orders/search 和「索引」），加上全文不能出現 ops/deploys.log 裡任何部署者的名字，只寫名不寫姓也不行。

練習 4：事故中你已經找到可疑的部署，但同一個版本也帶了一個安全修正。最好的止血方式通常是？

✓ a。止血要快、副作用小。b 會把安全漏洞（這次是 BOLA）重新打開，用一個問題換另一個問題；c 繞過審查和測試，很容易造成第二個事故，也沒有紀錄；d 代表影響在修好之前一直持續擴大。

練習 5：重啟 API 之後，下單的 p95 恢復正常了。可以宣告事故結束嗎？

✓ b。重啟只是清掉當下排隊的請求，造成問題的查詢還在，負載回來就會重演。結束的條件是原因已經被處理、指標穩定一段時間、資料一致。d 把兩件事混在一起：事故結束後才寫事後檢討。

練習 6：事後檢討的根因寫「工程師上線前沒有測試」。哪裡不好？

✓ c。不究責的檢討著重系統與流程：歸咎個人會讓大家以後隱藏問題，也產生不了可以執行的改善。寫成流程的缺口，才會有「PR 範本加 EXPLAIN」「旗標先開 10%」這種可以驗收的行動項目。a、b 都不是重點。

常見錯誤

  • 一開始就埋頭找根因：沒有分工、沒有對外更新，客人持續點不到餐。先止血、先溝通，根因在止血之後查。
  • 只看一個指標就下結論：看到 CPU 99% 就升級資料庫、看到連線池滿就調大。把 log、部署紀錄、指標的時間對在一起，一路問「為什麼」到原因。
  • 平均值和全部請求混在一起看：慢的路由被快的稀釋。依路由分組（先去掉查詢字串、把 id 換成 :id），開始時間用跟告警同一個指標算。
  • 整版回滾：連同版本裡的安全修正一起丟掉。先找最小的關閉單位（功能旗標），回滾前看清楚那一版還帶了什麼。
  • 止血後不驗證：改完旗標就宣布好了。確認問題停了，也確認該保留的行為（這次是 SEC-7）還在。
  • 旗標關了就不再打開：功能永遠消失，也沒人記得為什麼。修好根因、確認索引有效之後打開，並記在時間線上。
  • 事故中用一般的 CREATE INDEX：建索引的整段時間擋住下單，等於第二次事故。用 CONCURRENTLY，建完確認不是 INVALID。
  • 時間線事後憑記憶補寫：時間對不上，算不出偵測和止血花了多久。事故中當下記，也善用會自動記時間的工具（像 ops/flag-changes.log）。
  • 事後檢討變成找戰犯：寫人名、寫「某某疏忽」。寫角色和流程的缺口，行動項目同時有 prevent 和 detect，而且可以驗收。

小結

  • 事故一開始先分工（指揮、溝通、操作），開時間線當下記錄，對外更新用固定格式和固定頻率。
  • 定位靠三份資料對時間：log 依分鐘找出開始的時間、依路由找出拖累別人的那一個，部署紀錄找出相關的變更，指標分清楚症狀和原因。
  • 止血選影響最小、副作用最小的手段（關功能旗標），不要用整版回滾丟掉同一版的安全修正；止血後驗證問題停了、該保留的還在。
  • 修根因要有證據：EXPLAIN 看到 ILIKE '%…%' 全表掃描，用 pg_trgm 的 GIN 索引修，正式表上用 CREATE INDEX CONCURRENTLY，schema 同步宣告；確認之後才把功能打開，觀察穩定才算復原。
  • 事後檢討不究責：摘要、時間線、根因、行動項目；寫系統與流程的缺口，行動項目分 prevent 和 detect，有負責角色。
