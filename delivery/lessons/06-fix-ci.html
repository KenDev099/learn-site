階段 2：修問題 · 第 6 課

修好失敗的 CI：型別錯誤、flaky test、lockfile 與環境差異

團隊這週把 CI 接上了：每個 PR、每次推到 main，都會自動跑一次檢查。第一次跑就紅了，三個步驟全部失敗。群組裡同事說「那個測試本來就時好時壞，重跑幾次就過了」。技術主管重跑了三次，三次失敗的測試都不一樣。

這一課把這次 CI 修綠，而且每一個都修到根因。每種失敗都有一條「讓它變綠」的捷徑，這課也會說明為什麼不能走。

這課的路線：
  1. 讀 CI log：CI 紅了為什麼不能重跑到綠，那麼長的 log 要從哪裡讀起（開場問題的最小答案）。
  2. lockfile 不同步：npm ci 為什麼失敗、該改哪一個檔案，為什麼不能把 CI 改成 npm install。
  3. 型別錯誤：畫面明明正常，為什麼型別檢查不過；報錯的那一行為什麼不一定是要改的地方。
  4. 只在 CI 失敗的時區 bug：「我本機會過」的時候，為什麼 CI 反而是最接近正式機的環境。
  5. flaky test：每次失敗的測試都不一樣，怎麼找出測試之間共用的狀態，而不是加 retry。
這課會用到：
  • DevOps 課第 15 課的 CI：每次推程式就在乾淨的機器上依序跑幾個步驟（安裝、型別檢查、測試），任何一步失敗整條就是紅的。
  • Node 課第 3 課的 semver 與 lockfile：package.json 寫可以接受的版本範圍，package-lock.json 記下實際裝的確切版本。
  • Vue 課第 14 課的型別化元件：defineProps<{ … }>() 宣告 prop 的型別，vue-tsc 檢查 .vue 檔裡傳進去的值對不對。
  • 第 4 課的共用契約：shared/contract.ts 用 zod 寫出請求和回應的格式，前後端都從這裡拿型別。

讀 CI log：從第一個失敗開始

CI（continuous integration，持續整合）是每次有人推程式，就由一台乾淨的機器自動安裝、檢查、測試。它存在的目的只有一個：紅燈要可信。CI 紅了就代表程式真的有問題，綠了就可以放心合併。所以「重跑到綠」是最糟的反應：它讓紅燈變成「可能沒事」，下次真的有問題，也沒人會認真看。

打開 ci-log/run-1873.txt。CI log 很長，讀的順序是固定的：

  1. 找第一個失敗的步驟。這裡是 deps（✗ deps（exit code 1））。
  2. 在那個步驟裡找第一個錯誤訊息，不是最後一行。最後一行常常只是「exit code 1」或一大段用法說明；npm ci 失敗時，後面還印了 90 行左右的用法說明，真正的原因在前面的 Invalid: lock file's zod@4.6.7 does not satisfy zod@4.6.6。前面的錯誤也常常是後面錯誤的原因，先修前面的，後面的可能跟著消失。
  3. 再往下看其他失敗的步驟。這條 CI 的三個步驟各自獨立，所以一次看得到三種問題：typecheck 的 TS2322，以及 test 的兩個測試檔。

接著在自己的電腦重現。CI 跑的是 ci.mjs，本機用 npm run ci 跑同一個檔案，結果寫在 ci-report.json：

npm run ci
…
結果：✗ deps  ✗ typecheck  ✗ test（ci-report.json）

本機也紅，而且紅在同樣的地方，接下來就能在本機改、在本機驗證，不用每改一行就推上去等 CI。這是修 CI 的第一個原則：先在本機重現，再動手。ci.mjs 本身不要改：它是團隊對「可以合併」的共同定義，為了讓它變綠去拿掉一個步驟，等於把檢查關掉。

跟著做：lockfile 不同步

lockfile（package-lock.json）記錄這個專案實際裝了哪些套件的哪個確切版本，連套件依賴的套件都記。package.json 寫「我要什麼」，lockfile 寫「實際裝的是什麼」。CI 用的安裝指令是 npm ci，它跟 npm install 的差別：

npm installnpm ci
用在哪開發時加套件、改版本CI、部署：要裝出跟 lockfile 一模一樣的東西
package.json 與 lockfile 不一致時照 package.json 重新解析，改寫 lockfile直接失敗，不改任何檔案
node_modules在原本的上面調整先整個刪掉再裝

lockfile 不同步就是兩個檔案說的不一樣。在 npm 11，npm ci 遇到這種情況會用 EUSAGE 結束，訊息就是 log 裡那段（這段是在 npm 11.19.1 實際跑出來的）：

npm error code EUSAGE
npm error
npm error `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync. Please update your lock file with `npm install` before continuing.
npm error
npm error Invalid: lock file's zod@4.6.7 does not satisfy zod@4.6.6

意思是：lockfile 鎖的是 zod 4.6.7，package.json 卻要 4.6.6。先找出是怎麼發生的，才知道該往哪邊改。CAFE-26 說阿哲合併 main 時解過 package.json 的衝突：main 前幾天把 zod 升到 4.6.7（package.json 與 lockfile 一起改），阿哲的分支還是 4.6.6；他解衝突時 package.json 留了自己那邊，lockfile 用了 main 的。所以「正確」的版本是 main 決定的 4.6.7，該改的是 package.json。

動手。打開 package.json，把 "zod": "4.6.6" 改成 "zod": "4.6.7"，再跑一次：

npm run ci

▶ deps
26 個套件的版本都跟 lockfile 一致
✓ deps
…
結果：✓ deps  ✗ typecheck  ✗ test（ci-report.json）

第一個步驟綠了。這門課的所有專案共用 delivery/practice/ 的安裝，ci.mjs 的 deps 步驟拿你的 package.json 跟那裡的 lockfile 比對，規則和 npm ci 一樣。不要在 work/06 裡執行 npm install：它會在這裡另外裝一份 node_modules、寫一份新的 lockfile。

反過來的情況也常見：有人真的要升版本，在本機 npm install zod@新版本，卻只 commit 了 package.json。那就是在本機重新 npm install、把更新後的 lockfile 一起 commit。判斷方式一樣：先弄清楚哪一邊才是團隊想要的版本。

💡 實務上：不要把 CI 的 npm ci 改成 npm install
這是最常見的「修法」，CI 會立刻變綠，因為 npm install 會自己改寫 lockfile。代價是 CI 裝的版本不再等於 lockfile 記的版本，每次建置都可能裝到不一樣的東西：昨天測過的程式，今天部署上去用的是另一組套件。lockfile 衝突在 code review 時很容易被略過（diff 太長），所以很多團隊會讓 CI 專門檢查這件事，就像這裡的 deps 步驟。升級套件要開自己的 PR，跟功能分開，第 10 課會完整做一次。

型別錯誤：報錯的那一行，不一定是要改的地方

typecheck 步驟的錯誤：

web/src/pages/OrderStatusPage.vue(26,48): error TS2322: Type 'string' is not assignable to type 'Date'.

先解釋一個疑問：阿哲說畫面明明正常。因為 Vite 開發伺服器和 Vitest（測試的寫法見 NestJS 課第 5 課）都只把 TypeScript 轉成 JavaScript，不做型別檢查（速度快的原因就在這裡）。型別錯了，程式照樣跑；只有 tsc、vue-tsc 會抓到，這就是 CI 要有 typecheck 步驟的原因。

錯誤指在 OrderStatusPage.vue 第 26 行：<PickupTime :at="order.pickupAt" />。order 的型別是契約的 OrderResponse，pickupAt 是 string（v-if 已經排除了 null）；而 PickupTime.vue 宣告 defineProps<{ at: Date }>()。兩邊不一致，TypeScript 把錯誤報在「把值傳進去」的地方，但哪一邊錯了要自己判斷：

  • 契約是對的。API 回的是 JSON，JSON 裡沒有 Date，時間一定是字串（"2026-11-03T23:30:00.000Z"）。前台收到的就是字串，getOrder() 也用契約檢查過。
  • 元件的型別是錯的。它宣告收 Date，實際收到的是字串。看註解：「一開始寫 taipei.format(props.at) 畫面會壞掉，包一層 new Date() 就好了」。作者在執行時撞到了「它其實是字串」，卻只在程式裡繞過去，沒有改型別。

所以要改的是 PickupTime.vue：讓 prop 的型別跟真正收到的資料一致。也可以在訂單頁先 new Date(order.pickupAt) 再傳進去，型別檢查一樣會過，但之後每個用到這個元件的頁面都要記得先轉換；元件直接收契約的字串，轉換只寫在元件裡一次。這種「型別說 A、實際是 B」的狀況最危險：之後有人相信型別寫了 props.at.getTime()，畫面就真的壞了。

三種「讓它過」的捷徑都不行：

  • 把契約改成 z.date()：型別檢查也許會過，但契約描述的是 JSON，z.date() 只接受 Date 物件。前台用它檢查 API 回應時，每一筆有取餐時間的訂單都會被判成格式錯誤。
  • as any、@ts-ignore：錯誤沒有消失，只是不再顯示。型別說謊的問題還在。
  • 把 tsconfig 的 strict 關掉、或從 ci.mjs 拿掉 typecheck：整個專案一起失去保護。

只在 CI 失敗的時區 bug，其實是正式環境的 bug

test 步驟裡，pickup-label.spec.ts 的三個測試全部失敗：

AssertionError: expected '11/04 00:15' to be '11/04 08:15'
AssertionError: expected '11/03 23:30' to be '11/04 07:30'

每個都剛好差 8 小時。阿哲說「我的 Mac 上明明會過」，他說的是真的：在本機跑 npm test，這三個測試都通過。環境差異（environment drift）是本機和 CI／正式環境在時區、環境變數、Node 版本、作業系統、檔案系統（例如大小寫）上的不同。這裡的差異是時區：

  • 你的 Mac 設在台北，Node 程序的時區是 Asia/Taipei。
  • CI 的 Linux 機器沒有設定時區，預設是 UTC。ci.mjs 也明確用 TZ=UTC 跑測試。

在本機重現只要一個環境變數。TZ 決定 Node 程序的時區，放在指令前面只影響這一次執行：

TZ=UTC npm test -- api/src/pickup

（npm test -- 參數：-- 後面的東西會接在 vitest run 後面；api/src/pickup 是只跑路徑含這段的測試檔。）三個測試都失敗了，跟 CI 一樣。

原因在 pickup-label.ts：getMonth()、getDate()、getHours() 回傳的是程序所在時區的月、日、時。同一個時間點 2026-11-03T23:30:00Z，在台北的程序裡是 11/04 07:30，在 UTC 的程序裡是 11/03 23:30。

關鍵的判斷：正式機也跑在 UTC（雲端機器幾乎都是）。所以 CI 不是「環境比較怪」，它是三個環境裡最接近正式機的一個。這個 bug 早就在線上了：CAFE-26 裡店長說「小票上的取餐時間跟客人說的差很多，是不是印表機的時鐘壞了」，就是它。顧客選了 08:15 取餐，小票印 00:15。

修法跟第 3 課的 slotLabel 一樣：用 Intl.DateTimeFormat（TypeScript 課第 6 課）的 timeZone: 'Asia/Taipei' 指定「要哪裡的時間」。結果只看傳進來的時間點，跟程序的時區無關。不過這裡多一個坑，因為格式裡同時有日期和時間：

const taipei = new Intl.DateTimeFormat('zh-TW', {
  timeZone: 'Asia/Taipei', month: '2-digit', day: '2-digit', hour: '2-digit', minute: '2-digit', hourCycle: 'h23',   // h23：0–23 時制
})
taipei.format(new Date('2026-11-03T23:30:00Z'))   // '11/04 07:30'，但中間不是一般的空白

在 Node 24.22.1 實際印出每個字元的編碼，日期和時間之間是 U+2009（窄空白），不是一般空白 U+0020。畫面上看起來一模一樣，toBe('11/04 07:30') 卻比對不過，送到印表機也可能印成亂碼。format() 的標點、空白由 Node 內建的國際化資料（ICU）決定，Node 升級時也可能改變。要固定的格式，就用 formatToParts()：它回傳 [{ type: 'month', value: '11' }, { type: 'literal', value: '/' }, …]，取出月、日、時、分，自己組成字串。

三種常見的錯誤修法：

  • 在 CI 設 TZ=Asia/Taipei，或在程式開頭寫 process.env.TZ = 'Asia/Taipei'：測試會過，但前者讓正式機的 bug 留著；後者改掉整個程序的時區，其他用到時間的程式（log、資料庫參數）全部跟著變，而且只是把問題藏起來。
  • 手動加 8 小時（(getUTCHours() + 8) % 24）：小時對了，日期還是 UTC 的，23:30Z 會印成 11/03 07:30。
  • 把測試的期待值改成 UTC 的結果：等於宣告「小票印錯的時間是對的」。
💡 實務上：「只在 CI 壞」先問它跟正式機哪裡一樣
遇到「我本機會過、CI 不過」，第一個問題不是「CI 哪裡怪」，而是「CI 和正式機在這一點上是不是一樣」。常見的差異：時區（雲端機器多半是 UTC）、檔案名稱大小寫（macOS 預設不分大小寫，Linux 分：import './Foo' 指向 foo.ts 在 Mac 上會過）、沒有設定的環境變數、Node 版本、測試平行執行的程度。資深工程師會讓本機盡量貼近正式機（例如 .nvmrc 固定 Node 版本、測試指令固定 TZ=UTC），讓差異在寫程式的時候就出現，而不是在 CI 或線上。

flaky test：找出共用的狀態，不要用 retry 蓋掉

flaky test（不穩定的測試）是程式沒變，有時過、有時不過的測試。它比一直失敗的測試更傷：大家學會「紅了就重跑」，真正的問題混在裡面也被重跑掉。

log 裡 order-number.spec.ts 失敗的是「第一張是 A001」，而且旁邊寫著 (retry x3)：這個測試跑了 4 次（1 次加 3 次重試），拿到的是 A002、A003、A004、A005。看 ci.mjs 的 test 步驟，它用 --sequence.shuffle 讓測試每次用隨機順序跑，順序由 seed（隨機種子）決定，log 開頭印著 Running tests with seed "1873"。同一個 seed 一定排出同一個順序，所以可以重現（Vitest 5.0.5）：

npm test -- api/src/orders/order-number.spec.ts --sequence.shuffle --sequence.seed=1873 --retry=0

--retry=0 暫時關掉設定裡的重試，看最原始的結果。換幾個 seed 跑跑看，失敗的測試會跟著變，這就是「每次重跑失敗的都不一樣」。

原因在 order-number.ts：號碼存在模組層級的變數 let last = 0。同一個測試檔裡的所有測試共用這一個變數，誰先跑、拿走了幾個號碼，都會影響下一個測試：

執行順序結果
A001 → A002 → 回到 A001 → 歸零（檔案裡的順序）全部通過，所以作者沒發現
「下一張是 A002」先跑它拿到 A001，失敗；重試一次拿到 A002，通過
「第一張是 A001」不是第一個跑拿到 A002，重試拿到 A003、A004、A005，永遠失敗

第二列就是 retry 的問題：它讓一個依賴執行順序的測試「重試到剛好過」。測試沒有變好，只是 CI 看不到它壞了。測試隔離（test isolation）是每個測試都不依賴其他測試留下的狀態與執行順序，單獨跑、任意順序跑，結果都一樣。

修法是讓每個測試自己建立需要的狀態，這需要程式配合：狀態藏在模組裡，測試就只能共用它。把它改成工廠函式：createOrderNumbers() 每呼叫一次，就回傳一組新的、獨立的號碼（裡面用閉包記住自己的 last：函式記得它被建立時的變數），提供 next() 與 reset()。每個測試開頭 const numbers = createOrderNumbers()，彼此就不會互相影響。修好之後，把 vitest.config.ts 的 retry: 3 拿掉。

兩個看起來像修好、其實沒有的做法：

  • 在 beforeAll 建立或重置一次：beforeAll 在所有測試之前只跑一次，之後所有測試還是共用同一份狀態，換個順序照樣失敗。每個測試都要有自己的一份（寫在測試裡，或用 beforeEach）。
  • 把會失敗的測試 skip 掉：CI 綠了，但「第一張是 A001」這個需求從此沒有人檢查。
💡 實務上：看到 flaky test，先找三種東西
flaky 幾乎都來自三種原因：共用狀態（模組變數、同一個資料庫裡別的測試留下的資料）、時間（真的時鐘、setTimeout 的長短，用假時鐘解決）、外部依賴（網路、真的第三方服務）。重現的工具是固定 seed 的隨機順序，以及 Vitest 的 --repeats <n>（每個測試不論結果都重複跑 n 次）。修不完的時候，正確的暫時處理是開一張單、標記並指派負責人，而不是默默加 retry。另外，這個號碼產生器真的接到下單流程時，號碼要存在資料庫：記憶體裡的變數在 API 重啟時會歸零，開兩台 API 時也會發出重複的號碼。

  • package.json 的版本要跟 lockfile 一致（不要刪套件）。
  • 讓 PickupTime.vue 的 prop 型別跟它實際收到的資料（契約的 pickupAt）一致，訂單頁照樣用 <PickupTime> 顯示台北時間。前台只改這個檔案。
  • 判分：執行 ci.mjs，deps 與 typecheck 都要 ✓；ci.mjs、兩個 tsconfig.json、shared/contract.ts 與 web/src 裡其他檔案要跟題目一樣；PickupTime.vue 不能有 any、as unknown、@ts- 註解、defineProps(['at'])，prop 型別裡也不能留著 Date（例如 Date | string）。

練習 2：修好 pickupLabel 的時區 bug，讓小票在任何伺服器時區下都印台北時間，格式 MM/DD HH:mm（例如 11/04 07:30，中間是一般空白）。

  • 先用 TZ=UTC npm test -- api/src/pickup 看它失敗，修好之後同一個指令要通過，不加 TZ=UTC 也要通過。
  • 判分：分別在 TZ=UTC、America/New_York、Asia/Taipei 的程序裡執行同一組時間（含 UTC 前一天 23:30、跨年，以及一整年裡上千個時間點），結果要全部正確；不能改程序的時區（process.env.TZ）。

練習 3：修好時好時壞的 order-number.spec.ts，並拿掉 vitest.config.ts 的 retry。

  • 把 order-number.ts 改成 export createOrderNumbers()：每次呼叫回傳一組獨立的號碼 { next(), reset() }，號碼規則不變（A001…A999，之後回到 A001；reset() 之後從 A001 開始）。
  • 改寫 spec，讓每個測試自己建立號碼產生器。原本的 4 個測試都留著，用 npm test -- api/src/orders/order-number.spec.ts --sequence.shuffle --sequence.seed=任意數字 試幾個 seed。
  • 判分：用 10 個不同的 seed 隨機排序跑你的 spec，每次都全部通過；設定裡沒有 retry，沒有 skip、todo、only；你的 spec 要能抓到「沒有補零」「超過 999 沒有回到 A001」「reset() 沒有歸零」的號碼產生器。

練習 4：CI 上有個測試偶爾失敗，重跑就過。最好的處理是？

✓ b。偶爾失敗代表測試或程式有隱藏的依賴（順序、時間、外部服務），找到它才算修好。a：retry 讓 CI 失去警示能力，這課的「下一張是 A002」就是重試到剛好過。c：移除等於放棄這個保護。d：程式沒變它就不會自己好，大家只會習慣重跑。

練習 5：時段標籤的測試在 CI（TZ=UTC）失敗、在你的 Mac 通過。應該改什麼？

✓ c。CI 在這一點上跟正式機一樣，它抓到的是線上真的 bug。a 讓 CI 不再像正式機，bug 留在線上。b 把錯的結果當成規格。d 改的是測試的環境，程式在正式機照樣印錯。

練習 6：npm ci 失敗，說 package.json 與 lockfile 不同步。CI 應該改用 npm install 嗎？

✓ a。npm ci 的嚴格是為了每次建置都裝出同一組版本。b：它在 CI 機器上改寫的 lockfile 不會回到 repo，問題還在，而且每次可能裝到不同版本。c：「之後再改回來」通常不會發生。d：不一致時 npm install 會照 package.json 重新解析，結果可能跟 lockfile 不同。

常見錯誤

  • 只看 log 最後一行：最後一行常常只是 exit code 或用法說明。從第一個失敗的步驟、第一個錯誤訊息開始讀。
  • 不在本機重現就開始改：每改一行推一次等 CI，又慢又容易猜錯。先用 npm run ci、TZ=UTC、固定 seed 在本機看到同樣的失敗。
  • 在 CI 改用 npm install：lockfile 的檢查被繞過，每次建置可能裝到不同版本。在 PR 裡讓 package.json 與 lockfile 一致。
  • 放寬型別或契約讓型別檢查通過：as any、z.date()、關掉 strict 都只是讓錯誤不顯示。讓型別跟真正的資料一致。
  • 在 CI 或程式裡設時區讓測試通過：正式機的 bug 還在。用 Intl 的 timeZone 明確指定要哪裡的時間。
  • 用 format() 組要比對或列印的字串：Intl 的標點與空白可能是特殊字元。固定格式用 formatToParts()。
  • 用 retry 掩蓋 flaky test：依賴順序的測試會「重試到剛好過」。找出共用狀態，讓每個測試自己建立。
  • 在 beforeAll 重置一次就以為隔離了：之後的測試還是共用同一份狀態。每個測試各自一份。

小結

  • CI 的價值在於紅燈可信。讀 log 從第一個失敗的步驟、第一個錯誤開始，先在本機用 npm run ci 重現，再修；不改 CI 的檢查。
  • npm ci 要求 package.json 與 lockfile 一致，不一致就失敗、不改檔案。先查清楚哪一邊是團隊要的版本，在 PR 裡修正。
  • Vite 與 Vitest 不做型別檢查，型別錯誤只有 tsc／vue-tsc 抓得到。錯誤報在哪一行，不等於哪一邊錯；JSON 裡的時間就是字串。
  • getHours() 這類方法跟著程序的時區走。CI 和正式機都是 UTC，只在 CI 壞的時區 bug 就是線上的 bug；用 Intl.DateTimeFormat 的 timeZone 與 formatToParts() 修。
  • flaky test 用固定 seed 的隨機順序重現；根因常是共用狀態。讓每個測試自己建立狀態（程式改成工廠函式），拿掉 retry。
