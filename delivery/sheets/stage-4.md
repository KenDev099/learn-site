上線前用量測證明撐得住，出事時先止血再找根因，交付時附上證據。每個結論都要有條件、數字和原因。[回 產品交付實戰 學習地圖](../index.html)

## A 先把「撐得住」寫成數字 {span=2}
| 端點 | 平常尖峰（每秒） | 活動（每秒） | 說明 |
|---|---|---|---|
| GET /products | 4 | 20 | × 5 |
| POST /orders | 0.8 | 4 | × 5 |
| GET /orders/:id | 2 | 10 | × 5 |
| GET /kitchen/board | 3 | 3 | warn 請求數不變，每次要列的單從 40 張變 200 張 |

CAFE-38 的目標：每個 API 的 p95 < 300 ms、錯誤率 < 1%。每個端點分開算流量，也要估每個請求處理多少資料。準備跟那天一樣多的資料，只用種子資料的 6 張訂單看不出問題。

## B 尖峰用開放模型
| 模型 | 系統變慢時 |
|---|---|
| 開放：`ramping-arrival-rate` | ok 每秒送的請求數固定，延遲照實呈現 |
| 封閉：`constant-vus` | no 每個 VU 等回應才送下一個，請求變少，問題被藏起來 |

先確認 `dropped_iterations` 是 0，數字才可信。每個請求帶 `name` 標籤，每個端點分開算 p95，慢的才不會被快的稀釋。

## C 找原因靠證據，再用同一個腳本重測 {span=2}
| 證據 | 看到什麼 | 修法 |
|---|---|---|
| `DEBUG_SQL=1` 數查詢數 | 查詢數跟著筆數成長：1 + 200 × 2 ＝ 401，就是 N+1 | `include` 或 `IN` 一次查完，查詢數固定；回應形狀不能變 |
| `EXPLAIN ANALYZE` | Seq Scan 讀 20 萬列只留 200 列 | 等號篩選在前、排序在後：`(status, ordered_at)`；順序反過來 PostgreSQL 不用它 |
| 建索引的 migration | 一般 `CREATE INDEX` 整段時間擋寫入 | `CREATE INDEX CONCURRENTLY` 單獨一個 migration，schema.prisma 同步宣告 `@@index` |

這課在作者的 Mac 上量到：kitchen-board 的 p95 從 343 ms 降到 18 ms。前後要用同一個腳本、同樣的資料、同一台機器才能比。連線池滿通常是症狀，先找占著連線的查詢，不是先調大池子或加快取。

## D 事故的前五分鐘
| 角色 | 做什麼 |
|---|---|
| 事故指揮 | 決定做什麼、指派、決定何時結束，自己不動手查 |
| 溝通 | 固定時間對店長、客服發更新 |
| 操作 | 查 log、改旗標、跑 migration，做之前先說 |

開共用時間線，當下記每一件事。對外更新第一則 10 分鐘內發，之後固定間隔發，沒進展也發。內容寫影響、正在做什麼、下次更新時間，不猜原因、不承諾修好的時間。

## E 定位：三份資料對時間，分清症狀和原因 {span=2}
```flow LR
[07:32 v2.8.0 上線，搜尋旗標直接 100%] -> *[根因 缺索引]: ILIKE 包含搜尋每次掃整張表
*[根因 缺索引] -> [CPU 99%]
[CPU 99%] -> [連線池 10/10]: 慢查詢占住連線
[連線池 10/10] -> [下單排隊等連線，07:38 起部分逾時]
[下單排隊等連線，07:38 起部分逾時] -> [下單 p95 超過 1 s，07:40 告警]
```
上圖是這課的事故現場。log 依分鐘找出開始時間。依路由分組（去掉查詢字串、id 換成 `:id`）找出拖累別人的 `GET /orders/search`，部署紀錄對到 v2.8.0。CPU 加倍或連線池調大，只會讓更多全表掃描同時跑。根因用 pg_trgm 的 GIN 索引修，`CREATE INDEX CONCURRENTLY` 建好、schema 同步宣告、EXPLAIN 確認之後才打開旗標，觀察穩定才算復原。

## F 止血：選影響最小的手段
| 手段 | 結果 |
|---|---|
| 關閉旗標 `orders.search` | ok 幾秒生效，只有搜尋暫停 |
| 整版回滾到 v2.7.2 | no SEC-7 的 BOLA 修正一起消失 |
| 重啟 API | warn 店員一搜尋又會回來 |
| 加大連線池、升級資料庫 | no 對準的是症狀 |

止血後驗證問題停了、該保留的還在。事後檢討不究責：寫角色和流程的缺口，不寫人名。每個改善行動都要可驗收、有負責角色，而且 prevent 和 detect 兩類都要有。

## G 期末專題：取消訂單的順序 {span=2}
```sequence
participants: 顧客, API, 資料庫, 吧台, CafePay
顧客 -> API: POST /orders/:id/cancel，LoginGuard 加 findVisible
API -> 資料庫: 交易內 updateMany WHERE status = 'paid' → cancelled
吧台 -> 資料庫: start 也是 WHERE status = 'paid'
資料庫 --> API: count 1：同一個交易寫補償點數、時段名額減 1，提交
資料庫 --> 吧台: count 0，409
API -> CafePay: 交易提交後退款，key 是 refund:訂單 id
CafePay --> API: 成功：付款標 refunded
note API, CafePay: 結果不明：付款維持 paid，再按取消用同一把 key 重試
```
先把規則寫成例子再寫程式。別人的訂單 404；已取消再取消回 200 與目前的訂單，不再退款；製作中或還沒付款回 409 `ORDER_NOT_CANCELLABLE`。點數寫一筆 `order_cancelled` 補償紀錄，`reversalOf` 指向原本那一筆。前端只在 paid 時顯示按鈕、用原生 `<dialog>` 確認，規則在後端執行。

## H 驗收報告與自評
```kv cols=1
範圍: 做了什麼，也寫明不做什麼
測試證據: 每條驗收條件對到一個通過的測試，名稱以 AC 編號開頭
已知限制: 還沒處理的狀況與原因
自評: 範圍、測試證據、上線風險各 1～4 分並附證據
```
| 分數 | 意思 |
|---|---|
| 3 | 每條驗收條件都有通過的測試 |
| 4 | 再加上並發、重試、失敗情境的測試證明 |

有證據的 3 分比沒有證據的 4 分有用。交件前照第 7 課的審查順序審自己的 diff，跑 `npm run ci` 全綠再交。
