修問題要先拿到證據，再找根因，最後用一個先失敗、修完才通過的測試證明。不要重跑、放寬檢查或相信回覆。[回 產品交付實戰 學習地圖](../index.html)

## A 沒有重現步驟：從 log 找條件 {span=2}
```flow LR
(客訴 BUG-31) -> [按狀態碼分組]: jq 加 sort、uniq -c
[按狀態碼分組] -> [只看 500]: 422 是系統正確拒絕，不混進來
[只看 500] -> [錯誤特徵]: 類型、訊息、stack 第一行
[錯誤特徵] -> [影響範圍]: 請求數、不同顧客數、帶時區的時間
[影響範圍] -> *[可推翻的假設]
[可推翻的假設] -> [先失敗的回歸測試] -> [修 API] -> (修復紀錄)
```
「我試過了沒問題」只證明你的條件跟客人不同。log 是 NDJSON，`timestamp` 是 Unix 毫秒、一律 UTC。這課的示範資料：6 個 500 是同一個特徵，失敗的顧客是 2、4、5 號三位；同一個人會重試，人數要算不同的 `customerId`。

## B 假設要寫到能被推翻
| 假設 | 結果 |
|---|---|
| 「應該是網路不穩」 | no 什麼都說得通，等於沒說 |
| 「2 號顧客的帳號有問題」 | no 被推翻：失敗的有三個人 |
| 「有起司蛋糕就會 500」 | no 被推翻：下架前含 6 的訂單是 201 |
| 「購物車裡有已下架的商品就會 500」 | ok 都在下架之後、都含 6、拿掉就成功 |

先寫「我認為是 X，因為 Y；如果是 X，應該會看到 Z」，再只去查 Z。

## C 修 API 與修復紀錄
```callout ok API 是信任邊界
下架商品回 409 `PRODUCT_UNAVAILABLE`，`details.productIds` 列出全部下架的品項，不建立訂單；不存在的商品維持 404。前端比對菜單只是體驗，擋不住舊分頁和別的客戶端。
```
回歸測試先在有 bug 的程式上因為 500 失敗，修完才通過。`not.toBe(201)` 太寬，有 bug 時也會通過。修復紀錄五節：現象、影響範圍（寫數字）、根因（檔案:行號）、修正、預防（回歸測試的名稱）。

## D 讀 CI log：先在本機重現
```kv cols=1
紅燈要可信: 重跑到綠，紅燈就變成「可能沒事」
讀的順序: 第一個失敗的步驟 → 那一步的第一個錯誤訊息，不是最後一行
本機重現: `npm run ci`、`TZ=UTC`、固定 seed，看到同樣的失敗再改
不改 ci.mjs: 它是團隊對「可以合併」的定義
```
| | `npm install` | `npm ci` |
|---|---|---|
| 不一致時 | 改寫 lockfile | 直接失敗，不改檔案 |
| 用在 | 開發時加套件 | CI、部署 |

## E 四種 CI 失敗：根因與捷徑 {span=2}
| 失敗 | 根因修法 | 看似修好、其實沒有 |
|---|---|---|
| lockfile 不同步 | ok 查清楚哪一邊是團隊要的版本，在 PR 裡讓兩邊一致 | no CI 改用 `npm install` |
| 型別錯誤 TS2322 | ok 讓型別跟真正的資料一致：JSON 裡的時間是字串 | no `as any`、`@ts-ignore`、契約改 `z.date()`、關 strict |
| 只在 CI 錯的時區 | ok `Intl.DateTimeFormat` 指定 `timeZone: 'Asia/Taipei'`，固定格式用 `formatToParts()` | no CI 設 `TZ=Asia/Taipei`、手動加 8 小時、期待值改成 UTC |
| flaky test | ok 固定 seed 重現，找出共用狀態，程式改成工廠函式，每個測試自己建立 | no 加 retry、skip、只在 `beforeAll` 重置一次 |

Vite 和 Vitest 不做型別檢查，只有 tsc、vue-tsc 抓得到。CI 和正式機都是 UTC：只在 CI 壞的時區 bug 就是線上的 bug。

## F 審查順序：由重到輕
| 順序 | 要問 |
|---|---|
| 1 說明與需求 | 跟需求單一致嗎？少做什麼？ |
| 2 金額與信任邊界 | 錢由誰算？使用者亂填會怎樣？ |
| 3 並發 | 兩個請求同時進來？ |
| 4 安全 | 使用者輸入會被當成程式執行嗎？ |
| 5 測試 | 新行為有測試嗎？ |
| 6 風格 | 最後看，多半標 nit |

CI 綠了只代表現有的檢查都過了。

## G 可執行的意見與嚴重程度
一條意見寫出位置（檔案與行號）、後果、修法、驗證方式，再標嚴重程度。

| 等級 | 意思：什麼時候用 |
|---|---|
| blocker | 不改不能合併：錢算錯、資料錯或遺失、安全漏洞、跟需求相反 |
| major | 應該在這個 PR 改：缺重要測試、錯誤處理不完整 |
| minor | 可以另開工作處理：小的重複、不影響正確性的寫法 |
| nit | 作者可以不改：命名偏好、排版、用字 |

有 blocker 時結論是 request-changes。PR-58 的例子：折扣用客戶端送的 `discount`，錢一律由伺服器算；`v-html` 顯示含使用者輸入的文字是 XSS，改用 `{{ }}`。

## H 並發超用：用測試證明，再審看程式 {span=2}
```sequence
participants: 顧客 A, coupons, 顧客 B
顧客 A -> coupons: 讀 usedCount = 0，通過
顧客 B -> coupons: 讀 usedCount = 0，通過
顧客 A -> coupons: 寫入 0 + 1
顧客 B -> coupons: 寫入 0 + 1
note 顧客 A, 顧客 B: 只有 1 張的券用了兩次，used_count 卻是 1
== 第二版：包進 $transaction，改用 increment ==
note 顧客 A, 顧客 B: READ COMMITTED 下兩個交易仍都讀到 0、都通過；increment 只修好遺失更新
== 修法 ==
顧客 A -> coupons: UPDATE … WHERE code = $1 AND used_count < max_uses
coupons --> 顧客 B: 影響 0 列，409
```
race spec 用 `Promise.all` 同時送出至少 10 個請求，斷言恰好 1 個 201；只看 `used_count` 抓不到。這課的示範輸出：第一版有 9 張訂單成功。再審逐條對照第二版的程式與測試，不看作者的回覆；交易不等於互斥。
