階段 5：契約與整合架構 · 第 11 課

API gateway、BFF 與把 gRPC 開放給瀏覽器（資深）

前面幾課各自做了一個零件：GraphQL 伺服器（第 2–7 課）、gRPC 庫存服務（第 8–9 課）、契約檢查（第 10 課）。真的上線時，問題變成這些零件怎麼接在一起：App 要先連到誰？認證在哪裡檢查？菜單頁同時需要菜單與庫存，庫存服務掛掉時菜單還能不能顯示？瀏覽器能不能直接呼叫 gRPC？

這課的路線：
  1. 示範問題與 API gateway：每個前端直接呼叫每個服務會出什麼事，入口統一處理哪些事，商業邏輯和物件授權為什麼不放進去（開場問題的最小答案）。
  2. BFF 與聚合的可靠性：菜單頁同時要菜單與庫存，怎麼並行呼叫、共用 deadline 預算，庫存服務掛掉時菜單照樣顯示。
  3. metadata：request id 一層一層往下傳，客服回報問題時能把三個服務的 log 串起來。
  4. 瀏覽器怎麼呼叫 gRPC：原生 gRPC 為什麼不行，gRPC-Web、Connect 協定各怎麼解決。
  5. federation 與 ADR：團隊變多後 GraphQL 怎麼拆，把咖啡店的架構決定寫成文件。
這課會用到：
  • 第 9 課的 gRPC client：用 timeoutMs 設 deadline，metadata 就是標頭，失敗時用狀態碼（例如 UNAVAILABLE）表示原因。
  • 系統設計課第 8 課的 deadline 預算：整個請求只有固定的時間，每往下呼叫一層，要扣掉已經用掉的時間。
  • 第 3 課的部分成功：可為 null 的欄位出錯時只有它變成 null，錯誤放進 errors，其他欄位照常回傳。

示範問題：每個前端直接呼叫每個服務

咖啡店長大了。客戶端有四種：顧客的 App、官網、店內的 POS（收銀機）、外送平台這類外部合作夥伴。後端拆成三個服務：訂單、庫存、會員。最直覺的做法是讓每個客戶端直接呼叫需要的服務。半年後會出現這些狀況：

  • 認證做了三次：訂單、庫存、會員各自驗 JWT、各自設 CORS、各自限流，三份程式碼的行為慢慢不一樣。
  • 前端知道內部拓樸：App 寫死 inventory.coffee.tw。庫存服務想拆成兩個、想換網址，要等所有使用者更新 App，行動 App 的舊版本會在手機上活好幾個月。
  • 行動網路往返太多：菜單頁要先拿菜單、再拿庫存、再拿會員點數，三次往返在 4G 上每次 100–300 ms。
  • 每個前端要的形狀不同：App 只要名字、價格、還剩幾份；POS 要條碼、成本、今天賣了幾份。同一支 API 想同時滿足兩邊，欄位越長越多。

解法是在客戶端和服務之間加兩層：入口統一的 API gateway，以及依前端分開的 BFF。

開場的問題先給最小答案：App 只連 API gateway，認證的第一道檢查在 gateway，「這張訂單是不是你的」仍由擁有資料的服務判斷；菜單頁由 BFF 同時呼叫菜單與庫存，庫存服務掛掉時菜單照樣回傳，只有「還剩幾份」是 null；瀏覽器不能直接呼叫原生 gRPC，要改用 gRPC-Web 或 Connect 協定。細節在後面的〈聚合的可靠性〉與〈瀏覽器怎麼呼叫 gRPC〉。

API gateway：入口做什麼、不做什麼

API gateway 是所有外部請求的入口，處理每個請求都需要、但跟商業規則無關的事，這類需求叫橫切關注（cross-cutting concerns）。DevOps 課第 12 課的 Nginx 反向代理就是最小的 gateway：收 HTTPS、依路徑轉給後面的服務。常見的選擇還有 Envoy、Kong，以及雲端的 AWS API Gateway。

gateway 該做為什麼放這裡
TLS 終止、HTTP/2憑證只管一個地方；內部服務可以跑明文或內部憑證
路由：/graphql → BFF、/api/v1 → 公開 REST客戶端只認一個網域，內部怎麼拆可以自由改
認證的第一道檢查：token 簽章、有效期限沒登入、偽造的請求在入口就擋掉，不消耗後面的資源
限流（系統設計課第 10 課）、請求大小上限依 IP、API key 計數，一個地方算得準
產生 request id、存取 log、延遲與錯誤率指標每個請求從入口就有編號，之後每個服務的 log 都帶著它

不該做的是商業邏輯：「會員日拿鐵打九折」「庫存少於 3 份不讓外送平台下單」。寫在 gateway 的規則很難測試（要起整個 gateway）、很難部署（改一個規則要動全公司的入口），而且每個服務都被它綁住。規則放在擁有那份資料的服務裡。

授權也不能只放在 gateway。gateway 驗完 JWT，只知道「這是王小明」（認證）。「訂單 1042 是不是王小明的」需要查訂單資料，只有訂單服務知道（第 6 課、Auth 課第 19 課的物件層級授權）。內部的批次程式、其他服務也可能不經過 gateway 直接呼叫訂單服務。gateway 擋掉明顯的壞請求，服務自己做最後的判斷。

request id 由 gateway 產生或覆蓋：客戶端送來的 X-Request-Id 不可信（可能很長、可能故意重複別人的 id 混淆 log）。Nginx 的寫法是 proxy_set_header X-Request-Id $request_id;，$request_id 是 Nginx 為每個請求產生的隨機 16 bytes 十六進位字串。

💡 實務上：先分清楚錯誤是 gateway 回的，還是服務回的
前端最常碰到 gateway 的時候，是收到 401（沒登入）、413（請求太大）、429（太頻繁）、502／504（後面的服務連不上或逾時），卻在服務的 log 裡找不到這個請求：那通常是 gateway 在入口就擋掉或等不到後面的服務。先看回應 body 的格式（gateway 的錯誤多半是一頁 HTML 或固定文字，跟服務回的 JSON 長得不一樣），再拿 request id 去 gateway 的存取 log 找。gateway 多半由維運或平台團隊管，要加路由、調請求大小上限或限流門檻，是開單請他們改，不是自己改設定。資深會先問一句：「這條規則是每個請求都要的，還是只跟某個商業情境有關？」後者就該回到服務裡做。

BFF：為某一種前端服務的後端

gateway 處理的是每個請求都一樣的事；每一種前端要的資料形狀不同，交給下一層。BFF（backend-for-frontend）是專門服務某一種前端的後端層。給 App 的 BFF 回傳 App 畫面要的形狀，給 POS 的 BFF 回傳店員要的形狀。它做的事主要是聚合（aggregation）：一個請求進來，在伺服器端呼叫多個下游、組合結果。App 只要一次往返，伺服器之間的呼叫在同一個資料中心裡，每次只要幾毫秒。

你在第 2–7 課寫的 GraphQL 伺服器就是一個 BFF：前端用查詢決定形狀，resolver 去各個下游拿資料。BFF 通常由前端團隊擁有：前端要改畫面時，不用排隊等後端團隊改 API。

BFF 有兩個常見的風險：

  • 長出商業邏輯：「九折」寫在 App 的 BFF，POS 的 BFF 沒寫，兩邊價格不一樣。BFF 只做組合與轉換，規則留在下游服務。
  • BFF 太多：每個畫面一個 BFF，重複的程式碼與維運成本跟著變多。依「使用者體驗差很多的客戶端」分，常見是 App／官網共用一個、POS 一個；差不多的前端共用。

什麼時候不需要 BFF：只有一個前端、後端只有一個服務時，前端直接呼叫那個服務就好，多一層只是多一個要部署、要監控的東西。

💡 實務上：前端團隊擁有 BFF，也要負責它半夜壞掉
工作上的 BFF 不一定叫這個名字：Next.js 的 Route Handler、Nuxt 的 server routes、一個專門給 App 用的 Node 服務，常常就是在做 BFF 的事。好處是改畫面不用等後端排進時程；代價是它變成正式的後端服務，要有 log、監控、告警，壞掉時前端團隊要能自己查、自己修。接手或提議加 BFF 前，先確認三件事：誰會被告警叫醒、它呼叫哪些下游、有沒有人偷偷把折扣或權限判斷寫在裡面。如果答不出來，先別再加一層。

聚合的可靠性：並行、預算與部分失敗

App 的菜單頁要的是「菜單加上每個商品還剩幾份」。菜單來自菜單服務（約 40 ms），庫存來自第 9 課的 gRPC 庫存服務（約 30 ms）。BFF 的 GraphQL 欄位：

type Query {
  menuWithStock: [MenuItem!]!
}
type MenuItem {
  id: ID!
  name: String!
  price: Int!
  available: Int        # 為什麼可以是 null，下面會說
}

練習的起始程式（bff.ts）是最直覺的寫法，它有三個問題：

const products = await ctx.menu.list(ctx.signal)                       // 先等菜單
const stock = await ctx.inventory.listStock({}, { timeoutMs: 1000 })  // 再查庫存，逾時寫死
return products.map(p => ({ ...p, available: stock.levels[p.id]?.available ?? null }))

問題 1：依序呼叫，延遲相加

先 await 菜單再呼叫庫存，總時間是 40 + 30 = 70 ms。兩個呼叫彼此不需要對方的結果，可以同時出發，總時間是較慢的那個：40 ms。下游越多差越多。寫法是先呼叫拿到兩個 Promise，再一起等：

const menuCall = ctx.menu.list(ctx.signal)        // 呼叫就出發了，還沒 await
const stockCall = ctx.inventory.listStock({}, …)  // 也出發了
const [menu, stock] = await Promise.allSettled([menuCall, stockCall])

能不能並行取決於資料的依賴：如果庫存服務只有 GetStock(product_ids)，要先知道菜單有哪些商品才能查，就只能依序。所以這一課的 proto 比第 9 課多一個 ListStock：「列出所有商品的庫存」，不需要先知道商品 id。設計下游 API 時，想一下呼叫端能不能跟別的呼叫同時發；加一個 RPC 是安全的變更（第 10 課）。

問題 2：一個下游失敗，整個畫面失敗

Promise.all 只要一個失敗就整個失敗；Promise.allSettled 等所有 Promise 都結束，回傳每一個的結果：{ status: 'fulfilled', value } 或 { status: 'rejected', reason }。

BFF 要分清楚哪個下游是必要的：沒有菜單，菜單頁沒有意義，菜單失敗就整個失敗；庫存是附加資訊，拿不到時菜單照樣顯示，只是「還剩幾份」變成「庫存資訊暫時無法取得」。多個下游中只有一部分失敗叫部分失敗（partial failure），讓不必要的部分降級、其餘照常運作叫優雅降級（graceful degradation）。

GraphQL 本身就能表達部分成功（第 3 課）：available 的 resolver 丟出錯誤，這個欄位變成 null，errors 多一筆帶著路徑的錯誤，其他欄位照常回傳。兩個細節：

  • 欄位要可為 null：如果寫成 available: Int!，null 會往上傳染，整個 MenuItem 變 null；而列表是 [MenuItem!]!，再往上傳染，最後 data 整個是 null，等於整個失敗。附加資料的欄位宣告成可為 null。
  • 錯誤訊息不寫內部細節：庫存服務的錯誤可能是「inventory-db-3.internal 連線被拒」，那是內部拓樸，前端看了也沒用。給前端固定的訊息與錯誤代碼（INVENTORY_UNAVAILABLE，放在第 5 課的 extensions.code，前端依代碼決定顯示什麼），原始錯誤寫進 log。

在 work/11 執行 node examples/bff.ts（做完練習 1 之後），它開一個庫存服務和 BFF。用 INVENTORY=down node examples/bff.ts 讓庫存服務一律回 UNAVAILABLE，再查一次：

curl -s localhost:4000/graphql -H 'content-type: application/json' \
  -d '{"query":"{ menuWithStock { name available } }"}'

{"errors":[{"message":"庫存資訊暫時無法取得","path":["menuWithStock",0,"available"],
            "extensions":{"code":"INVENTORY_UNAVAILABLE"}}, …每個商品一筆…],
 "data":{"menuWithStock":[{"name":"美式咖啡","available":null},{"name":"拿鐵","available":null}, …]}}

HTTP 狀態仍是 200：執行階段的錯誤放在 errors，跟第 5 課一樣。INVENTORY=slow 讓庫存服務卡住不回應，BFF 在 300 ms 的預算內放棄，回傳一樣的結果。

💡 實務上：「哪些下游是必要的」要在開發前跟 PM、設計講好
部分失敗不只是後端的寫法，畫面也要跟著設計：庫存拿不到時，「加入購物車」按鈕要不要停用？顯示「庫存資訊暫時無法取得」還是乾脆不顯示數字？這些是產品決定，不該等上線出事才由工程師臨時決定。實務上會在需求討論時列出每個區塊的資料來源，逐一標「必要」或「可降級」，並確認設計稿有降級狀態。前端的元件也要真的處理 available 為 null 加上 errors 的情況，不能只寫拿得到資料的路徑。

問題 3：逾時寫死，不看剩下多少時間

App 對 BFF 的請求有一個總預算，例如 500 ms（系統設計課第 8 課的 deadline 預算）。BFF 開始處理時記下 deadline = now() + 500，之後每呼叫一個下游，就用「剩下的時間」當它的逾時：

timeoutMs = ctx.deadline − ctx.now() − 20

扣掉的 20 ms 留給 BFF 自己組回應、送回客戶端。寫死 1000 ms 的問題是：客戶端只願意等 500 ms，BFF 卻等庫存等到 1000 ms，客戶端早就放棄了，這段時間的工作全部白做，還佔著連線。

剩下的時間不夠時（算出來 <= 0）就不要呼叫，直接當成庫存失敗。注意 Connect 的 CallOptions.timeoutMs 設成 0 或負數代表「不設逾時」（@connectrpc/connect 2.3.0 的型別註解：Set to <= 0 to disable the default timeout），直接把負數傳下去會變成永遠等。

測試裡的時間一律用注入的 ctx.now()：測試把時鐘停住，剩餘預算才會是精確的數字，跟機器快慢無關。

還有一層防護：庫存服務持續掛掉時，每個菜單請求都還是會試一次、等到逾時。斷路器（circuit breaker）（系統設計課第 11 課）在連續失敗後暫時不呼叫，直接走降級，等一段時間再試。這一課只做 deadline，斷路器第 12 課的專題可以加。BFF 也不要自己重試到超過預算：重試的次數與間隔都要從同一個預算裡扣。

metadata：request id 與標頭往下傳

一個 App 請求會經過 gateway、BFF、庫存服務，每一層都寫 log。出事時要把同一個請求在三個服務的 log 串起來，靠的是 request id：每一層都把收到的 id 帶給下一層，log 裡也印出它（DevOps 課第 21 課；分散式追蹤用的 trace context 是同一個做法的進階版）。gRPC 的 metadata 就是 HTTP 標頭（第 9 課）：Connect 的 client 用 CallOptions.headers 送，伺服器的 handler 從 ctx.requestHeader 讀。

BFF 往下傳什麼要用白名單：

標頭轉送？原因
x-request-id要串 log。進來有就沿用；沒有就產生一個，同一個請求只產生一次，這個請求的每個下游呼叫共用
authorization要（原樣）下游服務自己做授權時要知道是誰（gateway 只做第一道檢查）
cookie不要裡面可能有 session 等憑證，送進內部服務就可能被印進 log、被別的程式讀到
content-type、content-length、host…不要描述的是「客戶端到 BFF」那個請求；整包轉送會蓋掉 gRPC 請求自己的值，呼叫直接壞掉

「每次下游呼叫各自產生新的 id」是常見的錯誤：同一個 GraphQL 請求的兩次庫存呼叫拿到兩個不同的 id，log 就串不起來。把 id 存在這個請求的 context 上（ctx.requestId ??= …，??= 是「左邊是 null 或 undefined 才指定」），之後的呼叫沿用。練習 2 把練習 1 的 timeoutMs 計算也收進同一個函式，BFF 每次呼叫下游都用它。

💡 實務上：把 request id 給到客服手上
客服轉來「早上 10 點點拿鐵失敗」，沒有 request id 時只能靠時間與使用者去翻好幾個服務的 log，常常對不起來。常見的做法是錯誤畫面或錯誤回應裡帶上 request id（例如「查詢編號：a1b2c3」，別跟 INVENTORY_UNAVAILABLE 這種錯誤代碼混在一起），使用者截圖給客服，工程師拿它一次查出 gateway、BFF、庫存服務各自發生了什麼。上線前可以自己測一次：故意讓下游失敗，看能不能只用畫面上的 id 在 log 系統裡把整條路串起來。request id 只是用來查 log 的隨機編號，不要放使用者資料進去。

瀏覽器怎麼呼叫 gRPC

POS 是一個網頁，要直接查庫存。瀏覽器支援 HTTP/2，但原生 gRPC 還是用不了：gRPC 把呼叫結果的狀態碼放在 HTTP trailers（回應 body 之後才送的標頭），瀏覽器的 fetch 讀不到 trailers，也不讓網頁控制 HTTP/2 的細節。所以要換一種瀏覽器可以用的協定：

做法怎麼運作代價
gRPC-WebgRPC 的變體，把狀態碼移到回應 body 的最後；瀏覽器用 gRPC-Web 的 client 呼叫多數 gRPC 伺服器不直接支援，要在前面放 Envoy 之類的代理轉換；請求是二進位，curl 不好測
Connect 協定Buf 定義的 HTTP 協定，unary 就是一般的 POST + JSON（或二進位 protobuf）；Connect 的伺服器同時接受 Connect、gRPC、gRPC-Web 三種協定伺服器要用 Connect 的實作（Node、Go、Swift、Kotlin…）；別的語言的 gRPC 伺服器要換或加代理
grpc-gatewayGo 生態的工具：在 proto 寫 google.api.http 註解（例如 get: "/v1/stock/{product_id}"），產生 REST/JSON 的反向代理要 Go 與多一個程序；適合對外提供「看起來像 REST」的 API

這門課的庫存服務是用 Connect 寫的，connectNodeAdapter 開在 HTTP/2 時三種協定都收；開在一般的 HTTP/1.1（http.createServer）時，gRPC 協定不能用，Connect 與 gRPC-Web 可以（Connect 官方文件 Node 伺服器頁的相容性表，@connectrpc/connect-node 2.3.0）。在 work/11 執行 node examples/serve-json.ts，用 curl 呼叫看看：

curl -s localhost:4000/coffee.inventory.v1.InventoryService/GetStock \
  -H 'content-type: application/json' -d '{"productIds":["1","5"]}'
{"levels":{"1":{"productId":"1","available":12},"5":{"productId":"5"}}}

curl -s -i localhost:4000/coffee.inventory.v1.InventoryService/GetStock \
  -H 'content-type: application/json' -d '{"productIds":["99"]}'
HTTP/1.1 404 Not Found
content-type: application/json

{"code":"not_found","message":"找不到商品 99"}

從輸出可以讀出 Connect 協定 unary 的規則（connectrpc.com/docs/protocol）：

  • 路徑是 /<package>.<Service>/<Method>，大小寫要一樣，不是 REST 風格的 /stock。方法一律 POST，Content-Type 是 application/json 或 application/proto。建議加 Connect-Protocol-Version: 1：伺服器可以設定成沒帶就拒絕（Connect 的 requireConnectProtocolHeader 選項，預設不要求）。
  • JSON 欄位名是 proto 欄位名的小駝峰（product_ids → productIds），伺服器兩種都接受。預設值會被省略：可頌的庫存是 0，回應裡就沒有 available（proto3 的 JSON 對應不輸出預設值），讀的時候要把「沒有」當成 0。
  • 錯誤是非 200 的 HTTP 狀態加上 JSON body { "code", "message" }，code 是小寫蛇形（not_found、unavailable）。錯誤的種類要讀 code：HTTP 狀態碼是好幾個 code 共用的，400 可能是 invalid_argument、failed_precondition 或 out_of_range，500 可能是 internal、unknown 或 data_loss。

實際的 Vue 專案不會手寫 fetch，而是用 @connectrpc/connect-web（2.3.0）的 transport 加上 buf 產生的程式碼，拿到跟第 9 課一樣有型別的 client（這門課的練習資料夾沒有安裝它，這裡只看寫法）：

import { createClient } from '@connectrpc/connect'
import { createConnectTransport } from '@connectrpc/connect-web'
import { InventoryService } from './gen/coffee/inventory/v1/inventory_pb.js'

const transport = createConnectTransport({ baseUrl: 'https://pos-api.coffee.tw' })
const inventory = createClient(InventoryService, transport)
const { levels } = await inventory.getStock({ productIds: ['1', '5'] })   // levels['5'].available 是 0，已經幫你補好

練習 3 刻意不用它，只用 fetch：證明瀏覽器不需要任何 gRPC 的東西，也看清楚線路上傳的是什麼。網頁和 API 不同網域時還要設 CORS（Auth 課第 5 課）：Content-Type: application/json 與 Connect-Protocol-Version 都會觸發預檢請求，@connectrpc/connect 匯出的 cors.allowedMethods、cors.allowedHeaders、cors.exposedHeaders 列好了要允許的值，加進你的 CORS 設定就好。

為咖啡店選：POS 是自己的網頁、庫存服務已經用 Connect 寫，選 Connect 協定，不用多一個代理。如果庫存服務是別的語言的原生 gRPC 伺服器、又不能換，才考慮 gRPC-Web 加 Envoy；要給外部合作夥伴 REST，可以考慮 grpc-gateway 或另外寫公開 REST。

GraphQL federation（概念）

公司再長大，一個 GraphQL BFF 由很多團隊一起改：訂單團隊改訂單的型別、會員團隊改會員的型別，大家擠在同一個 repo、同一個部署流程。GraphQL federation 讓每個團隊各自擁有一個子圖（subgraph）：一個獨立部署的 GraphQL 服務，只定義自己負責的型別與欄位。前面放一個 router（例如 Apollo Router、Hive Gateway）把所有子圖組成一個完整的 schema；查詢進來時，router 算出要問哪些子圖、依什麼順序，再把結果合起來。

它解決的是組織的問題（很多團隊、各自部署），不是效能問題。代價：

  • 多一個 router 要部署、監控、升級，而且它是所有流量的必經之路。
  • 跨子圖的查詢會被拆成好幾次子圖呼叫，延遲與 N+1 的問題（第 4 課）跨服務出現，比較難查。
  • 子圖之間的型別要協調（誰擁有 Product、誰只是擴充它），要搭配 schema registry 與組合檢查（第 10 課）。

咖啡店只有一個前端團隊、一個 BFF，不需要 federation。判斷的訊號是：好幾個團隊頻繁因為同一個 GraphQL 服務互相等待、互相卡部署。

決策：咖啡店的架構寫成 ADR

把這一課的決定寫成 ADR（架構決策紀錄，第 1 課與系統設計課第 18 課），一年後有人問「為什麼 POS 不經過 BFF」，答案在文件裡：

# ADR-007：對外入口與前端整合方式

## 情境
四種客戶端（App、官網、POS、外送平台）；三個服務（訂單、庫存 gRPC、會員）。
認證、CORS、限流在每個服務各做一次；App 菜單頁要三次往返。

## 決定
1. Nginx 當 API gateway：TLS、路由、JWT 驗簽、依 IP 與 API key 限流、產生 X-Request-Id。
   不放商業規則；物件層級授權留在各服務。
2. App 與官網共用一個 GraphQL BFF（前端團隊擁有）：並行呼叫下游、500 ms 預算、
   庫存失敗時 available 為 null 並帶 INVENTORY_UNAVAILABLE。只轉送 x-request-id 與 authorization。
3. POS 用 Connect 協定直接呼叫庫存服務（同一個伺服器，不加代理）。
4. 外送平台用公開 REST + webhook（第 1 課），有版本號。

## 不選的
- 每個前端直接呼叫每個服務：認證重複、前端綁死內部拓樸。
- gRPC-Web + Envoy：庫存服務已經是 Connect，多一個代理沒有好處。
- GraphQL federation：只有一個前端團隊，router 的維運換不到好處。團隊超過三個、常互相卡部署時再評估。

## 後果
gateway 是單點：至少兩個實例。BFF 要監控每個下游的錯誤率與延遲。

練習

在 learn/ 執行 node check.mjs api-styles 11，三題都在 api-styles/practice/work/11/（還沒安裝套件的話，先照第 2 課開頭的步驟 npm install）。inventory.ts（第 9 課的庫存服務加上 ListStock）與 server.ts（用你的 resolver 建立 BFF）是課程提供的，不用改；gen/ 每次跑測試前會依 proto/ 重新產生。三題的測試各自獨立，可以不按順序做。

練習 1：改寫 bff.ts 的 Query.menuWithStock，並修改 schema.graphql。要求：菜單（ctx.menu.list(ctx.signal)）與庫存（ctx.inventory.listStock）同時出發；庫存的 timeoutMs 是 ctx.deadline − ctx.now() − MIN_BUDGET_MS，算出來 <= 0 時不呼叫、直接當成失敗；庫存失敗（錯誤、逾時、預算不夠）時菜單照常回傳，每個商品的 available 放 inventoryUnavailable()（課程寫好的 MenuItem.available resolver 會把它丟出來，GraphQL 把欄位設成 null 並記下路徑）；菜單失敗時整個欄位失敗。測試用真的 Connect 庫存服務：每次菜單順序、價格、庫存數字都不同；會檢查兩個下游在任何一個完成前都已經出發、送出的逾時剛好是剩餘預算減 20、庫存服務卡住或回 UNAVAILABLE 時的 data 與 errors、菜單服務失敗時整個欄位失敗（不是回空陣列），以及錯誤細節沒有洩漏到回應。

練習 2：完成 metadata.ts。downstreamOptions(ctx, now) 回傳 BFF 呼叫庫存服務用的 CallOptions：timeoutMs 是 ctx.deadline − now() − MIN_BUDGET_MS；headers 只放 x-request-id（沿用 ctx.headers 裡的；沒有時呼叫 ctx.newId()，同一個請求只產生一次並存在 ctx.requestId）與 authorization（有才放，原樣轉送）。callerOf(ctx) 在庫存服務端從 ctx.requestHeader 讀回 { requestId, hasAuth }。測試的 BFF 每個 GraphQL 請求呼叫庫存服務兩次，會送 cookie 與其他標頭，檢查庫存服務收到什麼。

練習 3：完成 connect-json.ts。createJsonServer(stock) 用 http.createServer（HTTP/1.1）加 connectNodeAdapter 開出 inventory.ts 的 inventoryRoutes。fetchStockJson(baseUrl, ids) 只用 fetch，以 Connect 協定呼叫 GetStock：成功回傳 { levels: { 商品 id: 剩幾份 } }（庫存 0 的商品也要有，值是 0）；失敗回傳 { code }，code 是錯誤 JSON 裡的值。測試會檢查請求的方法、路徑與 Content-Type，用跟別的 code 共用 HTTP 狀態碼的錯誤測試 code，並確認檔案裡沒有用任何 Connect 的 client 或 transport。

練習 4：gateway 已經驗證了 JWT，訂單服務還要檢查「這張訂單屬於這位顧客」嗎？

✓ gateway 適合做認證與粗粒度的檢查。物件層級授權（BOLA，Auth 課第 19 課）需要資料，必須在擁有資料的服務裡做；內部的程式也可能不經過 gateway 直接呼叫。前端隱藏擋不住直接送請求的人（c 錯）；讀取一樣會洩漏資料（d 錯）。

練習 5：BFF 同時需要菜單與庫存。庫存服務掛了，最好的行為是？

✓ 不必要的下游失敗不該拖垮整個畫面。GraphQL 的部分成功與可為 null 的欄位正好表達這件事。a 讓顧客連菜單都看不到；c 會超過客戶端願意等的時間，還加重庫存服務的負擔；d 可能讓顧客點到已經賣完的商品，要用舊資料就要明確標示時間。

練習 6：瀏覽器為什麼不能用 fetch 直接呼叫原生 gRPC？

✓ 瀏覽器支援 HTTP/2，fetch 也能收送二進位（ArrayBuffer），問題在讀不到 trailers。gRPC-Web 把狀態移到回應 body；Connect 協定的 unary 就是普通的 POST，錯誤用 HTTP 狀態加 JSON。CORS 允許 POST，只是需要正確的預檢回應（d 錯）。

常見錯誤

  • 把商業邏輯放進 gateway：難測試、難部署，所有服務被它綁住。gateway 只做橫切關注，規則放在擁有資料的服務。
  • 只在 gateway 做授權：gateway 不知道資料屬於誰，內部呼叫也可能繞過它。服務自己做物件層級授權。
  • BFF 依序呼叫互不依賴的下游：延遲相加。先發出所有呼叫，再用 Promise.allSettled 一起等。
  • 一個下游失敗就整個失敗：分清楚必要與附加的下游；附加資料的欄位宣告成可為 null，失敗時回 null 並帶錯誤代碼。
  • 欄位宣告成非 null 卻可能失敗：null 往上傳染，整個列表、甚至整個 data 變 null。
  • 下游逾時寫死：客戶端早就放棄了，BFF 還在等。每個下游用「剩餘預算 − 保留時間」，算出來 <= 0 就不呼叫（Connect 的 timeoutMs <= 0 代表不設逾時）。
  • 把下游的錯誤訊息原樣給前端：洩漏內部主機名稱與架構。給固定訊息與錯誤代碼，細節寫 log。
  • 把進來的標頭整包轉給下游：cookie 流進內部服務與 log，content-type 之類的還會弄壞請求。用白名單，只轉送 request id、authorization。
  • 每次下游呼叫各自產生 request id：同一個請求的 log 串不起來。一個請求只產生一次。
  • 每個前端團隊一個 BFF，各自實作同一套規則：價格、折扣在兩個 BFF 算出不同結果。規則放在下游服務。
  • Connect 錯誤只看 HTTP 狀態碼：好幾個 code 共用一個狀態碼。讀 body 的 code。
  • 小團隊導入 federation：多一個 router 要維運，換不到好處。

小結

  • API gateway 是外部流量的入口：TLS、路由、認證的第一道檢查、限流、request id、log 與指標；不放商業邏輯，物件層級授權留在服務裡。
  • BFF 為某一種前端聚合多個下游，由前端團隊擁有；GraphQL 伺服器常扮演這個角色。BFF 只做組合與轉換，規則留在下游。
  • 可靠的聚合：互不依賴的下游並行呼叫；每個下游的逾時從同一個 deadline 預算計算，不夠就不呼叫；附加資料失敗時降級（欄位可為 null、錯誤代碼、不洩漏細節）。
  • 往下游只轉送需要的標頭：request id 一個請求只產生一次並共用，authorization 原樣轉送，cookie 不轉送。
  • 瀏覽器讀不到 HTTP trailers，不能直接呼叫原生 gRPC。可以用 gRPC-Web（通常要代理）、Connect 協定（POST + JSON，路徑 /package.Service/Method，錯誤是 { code, message }，預設值會被省略），或用 grpc-gateway 產生 REST。
  • GraphQL federation 解決多團隊共用一個 graph 的組織問題，代價是 router 的維運與跨子圖的複雜度；團隊少時不需要。
