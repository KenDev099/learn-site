階段 3：GraphQL 上線：防護與客戶端 · 第 6 課

授權與防護：欄位層級授權、深度與成本限制、persisted operations（資深）

REST 的每支端點各自檢查權限：GET /orders/42 檢查一次就完了。GraphQL 只有一個 /graphql，而且型別彼此連通：訂單連到顧客、顧客連到訂單、商品連到買過它的訂單。入口欄位檢查得再仔細，換一條路徑還是可能拿到同一張訂單。另一個問題是查詢由客戶端決定：一份兩三百字的查詢，可以要伺服器組出幾十萬個物件。

這課的路線：
  1. 示範問題與授權放在哪：入口檢查過了，為什麼換一條路徑還拿得到別人的訂單，規則放在哪才每條路都會經過。
  2. 示範問題二與深度限制：兩三百字的查詢怎麼讓伺服器組出幾十萬個物件，先擋住巢狀太深的查詢。
  3. 成本計算：執行前估算一份查詢要做多少事，太貴就拒絕，也能拿來依成本限流（GitHub 的公開 API 就這樣做）。
  4. persisted operations：自家 App 和官網只執行事先登記的查詢，比深度、成本限制更徹底。
  5. 其他設定：CSRF、內省、批次請求、錯誤建議，上線前要檢查、面試也常問的項目。
這課會用到：
  • Auth 課第 19 課的 BOLA 與 BOPLA：BOLA 是換個 id 就拿到別人的物件；BOPLA 是物件可以存取，個別欄位卻沒管好，多回了不該看的欄位或改了不該改的欄位。
  • 第 3 課的 resolver 與 context：每個欄位一個函式，四個參數裡的 parent 是上一層的回傳值，context 放這個請求的登入者。

示範問題：換一條路就拿到別人的訂單

在 learn/ 執行 node check.mjs api-styles 06，建立 api-styles/practice/work/06/（還沒裝套件的話，先照第 2 課的步驟 npm install）。schema.graphql 是咖啡店的顧客、訂單、商品：

type Query {
  me: Customer
  menu: [Product!]!
  product(id: ID!): Product
  customer(id: ID!): Customer     # 公開的顧客資料（評論區顯示名字）
  order(id: ID!): Order
}
type Product  { id: ID!  name: String!  price: Int!  orders: [Order!]! }
type Customer { id: ID!  name: String!  email: String  orders: [Order!]! }
type Order    { id: ID!  total: Int!  internalNote: String  customer: Customer!  items: [OrderItem!]! }
type OrderItem { quantity: Int!  product: Product! }

起始的 resolvers.ts 在 Query.order 檢查「訂單是不是你的」，其他地方都沒檢查。登入方式是 Authorization: Bearer <token>，伺服器用 token 查自己保存的 session，得到 viewer（{ id, role }，role 是 CUSTOMER 或 STAFF，角色的設計見 Auth 課第 18 課）。在 work/06 執行 node examples/leak.ts，用王小明的身分走三條路徑：

路徑 1：Query.order
{"errors":[{"message":"沒有權限查看這張訂單", … "extensions":{"code":"FORBIDDEN"}}],"data":{"order":null}}

路徑 2：Product.orders
{"data":{"product":{"orders":[{"id":"107","internalNote":"曾經付款失敗兩次","customer":{"name":"張雅婷","email":"guest4-7027@example.tw"}}, …

路徑 3：Customer.orders
{"data":{"customer":{"name":"陳美華","email":"guest2-5034@example.tw","orders":[{"id":"101","total":270}, …

入口擋住了，但 product { orders } 和 customer(id) { orders } 把別人的訂單、店員之間的備註和 email 全部交出來。這就是 Auth 課第 19 課的兩種漏洞在 GraphQL 裡的樣子：

  • BOLA（Broken Object Level Authorization，物件層級授權失效）：拿得到不屬於你的物件（別人的訂單）。
  • BOPLA（Broken Object Property Level Authorization，物件屬性層級授權失效）：物件可以看，但其中某些欄位不該給你（email、internalNote）。

授權放在哪：每條路徑都要經過同一套規則

GraphQL 規格不管授權，交給你的程式。實務上有兩個放法，都比「在入口檢查」可靠：

  • 資料存取層：查訂單的函式本身就要求 viewer，例如 orderRepository.findVisible(viewer, …)，只回傳這個人看得到的資料。resolver 不管怎麼寫，都拿不到看不到的東西。專案大、多人維護時最穩。
  • 型別與欄位的 resolver：把規則寫成幾個小函式集中在一個檔案（這一課的 visibility.ts），每個能拿到訂單、敏感欄位的 resolver 都呼叫它。規則只有一份，改規則只改一個地方。

無論哪一種，規則要先講清楚。咖啡店的規則（錯誤代碼放在 extensions.code，見第 5 課）：

情況處理原因
直接要求一張訂單（order(id)），沒登入錯誤 UNAUTHENTICATED客戶端可以據此導去登入頁
直接要求別人的訂單錯誤 FORBIDDEN，order 是 null使用者明確要求這一筆，要讓他知道為什麼沒有
列表裡有看不到的訂單（Product.orders、Customer.orders）濾掉，不報錯一筆看不到就讓整個列表失敗，畫面會整塊壞掉
非店員查 email、internalNote回 null欄位層級的拒絕，不影響同一個物件的其他欄位

欄位層級的規則要寫在那個欄位的 resolver，不是寫在回傳物件的地方。如果只在 Query.customer 裡把 email 清掉，Order.customer 回傳的 Customer 物件走預設 resolver，email 照樣出去：

Customer: {
  // 不論 Customer 物件從哪條路徑來（customer、me、Order.customer），email 都經過這裡
  email: (customer, _args, ctx) => staffOnly(ctx.viewer, customer.email),
},
  • 欄位要能是 null：email: String 沒有 !。如果宣告成 String! 又回 null，null 會往上傳染，整個 Customer 變 null（第 3 課）。設計 schema 時，有權限限制的欄位一律可為 null。
  • 回 null 還是 FORBIDDEN：直接要求的單一物件常回 FORBIDDEN；也有團隊回 null（假裝不存在），讓攻擊者無法用 id 猜出「這張訂單存在」。咖啡店的訂單 id 是連號，存在與否本來就猜得到，所以選 FORBIDDEN，讓前端顯示清楚的訊息。
  • 角色從伺服器端來：viewer.role 是伺服器用 session 查到的。客戶端送 x-role: STAFF 這種標頭，伺服器一律不看（Auth 課第 21 課）。
  • DataLoader 與授權：第 4 課的 loader 每個請求一份，快取的是資料庫的原始資料，授權在 resolver 拿到資料後才判斷，所以不同使用者不會互相影響。不要把「已經依某位使用者過濾過」的結果放進跨請求的快取，下一個人會拿到上一個人的權限範圍。
💡 實務上：授權漏洞多半出在「後來新增的欄位」
上線第一版通常都檢查過，出事的常是幾個月後有人加了 Product.orders 給後台報表用，忘了這條路也開給了顧客。資深工程師的做法是把授權寫成測試矩陣：每個角色（未登入、顧客本人、別的顧客、店員）× 每條能拿到訂單或敏感欄位的路徑，放進 CI，就像練習 1 的測試。review 時看到 schema 新增「回傳 Order、Customer 或清單」的欄位，先問：它經過 visibility 的哪個函式？新增敏感欄位（電話、地址）時也要找資安或 PM 確認誰能看。

示範問題二：一份小查詢讓伺服器做幾十萬次工作

授權擋的是「看不該看的」；另一類攻擊是「讓伺服器做太多事」，OWASP API Top 10 的 API4（資源耗用不受限制，Auth 課第 24 課）。查詢由客戶端寫，常見的四種形式：

  • 深層巢狀：schema 有環（Order → customer → orders → items → product → orders …），查詢可以一直往下繞，每多一層，資料量乘一次。
  • 大量清單：menu(first: 50) { orders(first: 50) { items(first: 50) { quantity } } } 只有三層，最多是 50 × 50 × 50 = 125,000 個 item。
  • 別名放大（alias amplification）：{ a1: menu { name } a2: menu { name } … a500: menu { name } }，用別名把同一個欄位查 500 次。深度只有 1。
  • 批次請求（batching）：一個 HTTP 請求帶一個陣列、裡面 100 份操作，讓「每分鐘 60 個請求」的限流變成 6,000 份操作。

這些查詢都合法、都通過第 2 課的驗證。要擋，就在執行前多加檢查。

深度限制：@envelop/depth-limit

深度限制（depth limit）限制查詢巢狀幾層。Yoga 建立在 envelop 的 plugin 系統上，@envelop/depth-limit 8.0.0（相容 Yoga 6、graphql 17）在驗證階段加一條規則：

import { useDepthLimit } from '@envelop/depth-limit'

createYoga({
  schema,
  plugins: [useDepthLimit({ maxDepth: 6 })],
})

它的算法（看套件原始碼，內部用 graphql-depth-limit 1.1.0）：最外層的欄位是第 0 層，往內每一層 +1；有欄位在第 7 層（超過 maxDepth）就回錯誤。fragment 會展開來算；名稱以 __ 開頭的欄位（__schema、__type）不算，所以 GraphiQL 的內省查詢不會被擋。被擋時的回應：

HTTP 400
{"errors":[{"message":"'Deep' exceeds maximum operation depth of 6","extensions":{"code":"GRAPHQL_VALIDATION_FAILED"}}]}

它是驗證錯誤，所以跟第 2 課的拼錯欄位一樣：整份查詢不執行，一個 resolver 都不會被呼叫。上限怎麼定：把自己前端最深的操作量出來，再多留一兩層。

深度限制不夠用。上面的「大量清單」只有 3 層、「別名放大」只有 1 層，都在上限內。深度限制是便宜的第一道門，真正衡量工作量的是下一節的成本。

成本計算：自己寫一條 ValidationRule

查詢成本（query cost／complexity）是在執行前估算一份查詢大約要做多少事。常見的現成套件（例如 graphql-armor 3.2.0）目前只支援 graphql 16 與 envelop 5，不能跟 Yoga 6、graphql 17 一起用，所以這一課自己寫。規則不必精準，只要「越貴的查詢分數越高」並且繞不過去。這門課的定義：

  • 每個欄位 1 分（包括 __typename）。
  • 有 first 參數的欄位會回傳一串資料：「這個欄位自己 1 分＋底下所有欄位」整個乘以 first。沒寫 first 就用 schema 的預設值（orders(first: Int = 10)）。
  • 巢狀相乘；別名各算各的；fragment 與 inline fragment 展開來算。

用練習 3 的 schema（menu(first: Int = 20)、orders(first: Int = 10)、items(first: Int = 5)）：

查詢計算成本
{ order(id: "1") { total customer { name } } }1 × (1 + 1 + 1 × (1 + 1))4
{ menu(first: 20) { name price } }20 × (1 + 2)60
{ menu { name } orders { id } }20 × 2 + 10 × 2（預設值）60
{ orders(first: 50) { items(first: 10) { product { name } } } }50 × (1 + 10 × (1 + 2))1,550
500 個別名的 menu(first: 20) { name }500 × 20 × 220,000

ValidationRule 是 graphql-js 在執行前對查詢文件做的一項檢查，第 2 課看到的「欄位不存在」就是內建規則回報的。它的型別是 (context: ValidationContext) => ASTVisitor：拿到 context，回傳一個「遇到哪種節點要做什麼」的物件。成本規則在每個操作（OperationDefinition）上算一次：

export function costLimitRule(max: number, variables = {}): ValidationRule {
  return context => ({
    OperationDefinition(op) {
      const cost = …                                    // 從 op.selectionSet 遞迴算
      if (cost > max) context.reportError(new GraphQLError(`查詢成本 ${cost} 超過上限 ${max}`,
        { nodes: op, extensions: { code: 'QUERY_TOO_COMPLEX', cost } }))
    },
  })
}

遞迴時會遇到三種 selection，每一種都要處理，漏掉任何一種就有人能繞過：

  • Kind.FIELD：欄位。用目前型別的 getFields()[名稱] 找到定義，getNamedType(def.type) 是往下一層的型別。
  • Kind.INLINE_FRAGMENT（... on Order { … }）：直接算它的 selectionSet。
  • Kind.FRAGMENT_SPREAD（...O）：用 context.getFragment('O') 找到 fragment 定義再算。fragment 可能互相引用（A 用 B、B 用 A），graphql 的內建規則會回報錯誤，但你的遞迴會先停不下來，所以要記住這條路徑上展開過哪些 fragment。

變數最容易被忽略。query ($n: Int) { menu(first: $n) { … } } 的查詢文字裡沒有數字，實際的值在請求的 variables。graphql 17 有兩個函式處理所有情況（寫在查詢裡、用變數、變數自己的預設值、schema 的預設值）：

const { variableValues } = getVariableValues(schema, op.variableDefinitions ?? [], variables)
getArgumentValues(fieldDef, fieldNode, variableValues).first    // 例如 50

練習 3 的 listSize() 已經包好這一步。注意 graphql 17 從 SDL 建立的參數，預設值放在 arg.default（舊的 arg.defaultValue 是 undefined，v18 會移除），自己去讀很容易讀錯，交給 getArgumentValues 最穩。

接上 Yoga 時有一個陷阱：Yoga 會快取驗證結果，鍵是「查詢文件＋規則名稱」，不含 variables（套件原始碼 use-parser-and-validation-cache.js，實測確認）。如果在 onValidate 用 addValidationRule 加成本規則，同一份查詢先用 n = 5 通過，之後 n = 5000 會直接拿到快取的「通過」。所以練習 3 給的 cost-plugin.ts 在 onExecute（每次執行前、已經拿到這次的 variables）呼叫 validate(schema, document, [costLimitRule(max, variables)])，超過就用 setResultAndStopExecution 回錯誤。

成本還能跟限流結合（系統設計課第 10 課）：token bucket 不是每個請求扣 1，而是扣這份查詢的成本，例如每位使用者每分鐘 10,000 分。GitHub 的公開 GraphQL API 就是用這種「點數」限流。這樣便宜的查詢可以多發，昂貴的查詢很快用完額度，比單純數請求次數公平。

💡 實務上：成本上限先「只記錄」，看過真實數字再擋
一開始就設上限，很容易擋到自己前端的正常畫面。比較穩的上線順序：先讓規則只把每個操作的名稱和成本寫進 log、不拒絕，跑一兩週，找出自己前端最貴的操作，上限定在它之上再留餘裕；之後才改成拒絕。錯誤的 extensions 帶 cost，前端工程師看到 QUERY_TOO_COMPLEX 就知道要拆查詢或縮小 first。上限和每分鐘可用的分數要寫進 API 文件，公開 API 的使用者才知道怎麼估算。

persisted operations：伺服器只執行登記過的查詢

深度和成本都是在「誰都能送任何查詢」的前提下盡量擋。如果客戶端只有自己的 App 和官網，可以換個想法：前端用到的查詢在建置時就決定了，伺服器只執行這些，其他一律拒絕。這叫 persisted operations（持久化操作，也常叫 trusted documents 或白名單）：

  1. 前端建置時，把每個操作的文字算出 sha256 雜湊，產生 { 雜湊: 查詢文字 } 清單（第 7 課的 codegen 可以自動輸出）。清單隨伺服器部署。
  2. 客戶端只送雜湊：{"extensions":{"persistedQuery":{"version":1,"sha256Hash":"0b88…"}}}，變數照常放 variables。
  3. 伺服器用雜湊查出查詢文字再執行；查不到、或送來的是查詢文字，就拒絕。
import { usePersistedOperations } from '@graphql-yoga/plugin-persisted-operations'

const manifest = new Map(Object.entries(operations))
createYoga({
  schema,
  plugins: [
    usePersistedOperations({
      getPersistedOperation: key => manifest.get(key) ?? null,
      allowArbitraryOperations: dev,       // 只有開發模式允許任意查詢
    }),
  ],
})

@graphql-yoga/plugin-persisted-operations 4.0.1 的行為（看套件原始碼）：allowArbitraryOperations 預設 false；送查詢文字會得到 PersistedQueryOnly（代碼 CANNOT_SEND_PQ_ID_AND_BODY）；雜湊不在清單得到 PersistedQueryNotFound（代碼 PERSISTED_QUERY_NOT_IN_LIST）。allowArbitraryOperations 也可以傳函式 (request) => boolean，但決定權只能在伺服器（環境設定、內部網路），不能看請求帶的標頭，任何人都能加標頭。查清單用 Map：一般物件的 operations['toString'] 會查到原型上的函式。

在 work/06 執行 node examples/manifest.ts（做完練習 4 之後），它印出清單並用 4000 port 開啟練習 4 的伺服器：

# 用雜湊：執行
curl -s localhost:4000/graphql -H 'content-type: application/json' \
  -d '{"extensions":{"persistedQuery":{"version":1,"sha256Hash":"（印出來的第一個雜湊）"}}}'

# 送查詢文字：拒絕
curl -s localhost:4000/graphql -H 'content-type: application/json' -d '{"query":"{ menu { name } }"}'
{"errors":[{"message":"PersistedQueryOnly","extensions":{"code":"CANNOT_SEND_PQ_ID_AND_BODY"}}]}

取捨：

  • 第一方客戶端（自己的 App、官網）：開白名單是最強的防護。攻擊者看得到你的 schema 也沒用，伺服器根本不執行他寫的查詢。代價是部署流程：新版前端的清單要先部署到伺服器，舊版 App 的雜湊也要保留到沒人使用。
  • 公開 API（給第三方開發者）：不能用白名單，對方的查詢你事先不知道。只能靠深度、成本限制加上依成本限流。
  • 附帶好處：請求只帶雜湊，可以改用 GET，網址固定，CDN 能快取公開資料（第 7 課）。
💡 實務上：白名單最常出事的是部署順序
前端先上線、清單還沒部署到伺服器，新畫面的每個查詢都會得到 PersistedQueryNotFound。所以 CI 要先把新清單送到伺服器（或伺服器讀取的儲存位置），再發布前端。手機 App 更麻煩：舊版會在使用者手機上留很久，舊雜湊只能加、不能刪，要等統計顯示舊版沒人用了才清。從「任意查詢」切換到白名單時，也可以先記錄「不在清單裡的查詢」一段時間，確認都是攻擊或測試流量再開啟強制。

其他設定：CSRF、內省、批次請求、錯誤建議

  • CSRF：瀏覽器的「簡單請求」（GET，或 POST 用 text/plain、表單格式）跨站送出時不會先發 preflight（Auth 課第 6 課），帶著 Cookie 登入的使用者點了惡意網站，就可能替攻擊者執行操作。@graphql-yoga/plugin-csrf-prevention 4.0.1 的 useCSRFPrevention({ requestHeaders: ['x-graphql-yoga-csrf'] }) 要求這類請求帶一個自訂標頭，沒帶回 403；content-type: application/json 的 POST 本來就會 preflight，不受影響。開了 persisted operations 改用 GET 的話，CSRF 防護一定要開。
  • 正式環境要不要關內省：關掉（graphql 的 NoSchemaIntrospectionCustomRule）只是讓攻擊者猜 schema 麻煩一點，schema 從前端程式碼、網路請求都看得出來。它不是安全邊界，白名單和成本限制才是。公開 API 通常保留內省，方便第三方使用工具。
  • 批次請求：Yoga 6 預設不接受陣列形式的批次請求；開啟 batching: true 時預設上限 10 份，可以用 batching: { limit } 調整。開了就要把每份操作都算進限流與成本。
  • 錯誤建議：驗證錯誤的 Did you mean "email"? 會透露欄位名稱，關了內省也一樣。graphql 17 的 validate 有 hideSuggestions 選項；開了白名單就不太需要在意，因為未登記的查詢連驗證都不會跑。

練習

在 learn/ 執行 node check.mjs api-styles 06，四題都在 api-styles/practice/work/06/。每一題的測試各自獨立，可以不按順序做。練習 2 用 schema.graphql 但自帶 resolver，跟練習 1 的修改無關。

練習 1：修補授權。在 visibility.ts 完成四個函式（檔案開頭寫了規則）：canSeeOrder（本人或店員才看得到）、visibleOrders（濾掉看不到的）、requireOrder（沒登入丟 unauthenticated()、看不到丟 forbidden()、找不到回 null）、staffOnly（店員拿到值，其他人 null）。再改 resolvers.ts，讓 Query.order、Product.orders、Customer.orders 都經過這些函式，並替 Customer.email 與 Order.internalNote 寫 resolver。測試用王小明、陳美華、店員、沒登入四種身分跑每一條路徑，也會偷加 x-role: STAFF 標頭；訂單、email、備註每次都隨機產生。

練習 2：在 depth.ts 用 @envelop/depth-limit 把深度上限設為 6，加進 createYoga 的 plugins。測試確認：深度 6 的查詢照常執行；深度 7 的查詢（包括用別名、拆進 fragment 的寫法）在執行前就被擋，resolver 一次都沒被呼叫；GraphiQL 用的內省查詢不會被誤擋。

練習 3：完成 cost.ts 的 costLimitRule(max, variables)，照這一課的成本定義計算：有 first 的欄位整個乘以 first（用給好的 listSize，並傳入由 getVariableValues 算出的 variableValues）、巢狀相乘、別名各算各的、fragment 與 inline fragment 展開、互相引用的 fragment 不能讓規則當掉。超過 max 時回報 GraphQLError，extensions 是 { code: 'QUERY_TOO_COMPLEX', cost }（起始程式已經寫好這部分）。測試用隨機的 first 值比對成本是否剛好等於定義算出來的數字，最後再透過 cost-plugin.ts 接上 Yoga 確認變數傳入的大 first 會被擋。

練習 4：在 persisted.ts 的 createApp({ operations, dev }) 加上兩個 plugin：usePersistedOperations（只執行 operations 清單裡的雜湊；只有 dev 為 true 時允許任意查詢文字；查不到回 null）與 useCSRFPrevention（要求標頭 x-graphql-yoga-csrf）。測試用每次都不同的清單，檢查：雜湊能執行（含變數）、正式環境送查詢文字或未知雜湊（包括 toString、__proto__）被拒、帶什麼標頭都不能讓正式環境接受任意查詢、開發模式可以送任意查詢、沒帶 CSRF 標頭的 GET 回 403。

練習 5：Query.order(id) 已經檢查訂單屬於目前使用者。還需要在其他地方檢查嗎？

✓ 這就是 GraphQL 版的 BOLA。最穩的做法是讓授權發生在資料存取層或型別、欄位的 resolver，不論從哪條路徑進來都會經過。讀取一樣會洩漏資料（c 錯）；前端隱藏擋不住直接送查詢的人（d 錯）。

練習 6：已經設定深度上限 6，還需要成本限制嗎？

✓ 深度只限制巢狀層數。first: 50 巢狀三層是 125,000 筆，500 個別名只有 1 層，都在深度限制內。第一方 App 如果開了白名單，可以不靠成本限制；沒開就一樣需要（c 錯）。關掉內省不會讓查詢變便宜（d 錯）。

練習 7：咖啡店的 App 與官網是唯一的客戶端。哪一項防護最能防止攻擊者送任意查詢？

✓ 白名單讓伺服器根本不執行未登記的查詢。關掉內省只是讓攻擊者猜 schema 麻煩一點，schema 從前端程式碼就看得出來；改網址、加密回應都不影響伺服器執行什麼。開放給第三方的 API 不能用白名單，就要靠成本限制與限流。

練習 8：非店員查 Customer.email，最常見且合理的處理是？

✓ 欄位層級的拒絕常用 null，一個欄位不讓整個物件失敗。a 讓名字、訂單也一起看不到；c 的空字串會被前端當成「這個人沒有 email」，跟「你沒權限」分不出來；d 的 String! 回 null 會變成錯誤並往上傳染，整個 Customer 變 null（第 3 課）。

常見錯誤

  • 只在入口欄位檢查授權：圖是連通的，每條路徑都可能拿到同一個物件。把規則放在資料存取層或每個型別的 resolver。
  • 欄位權限寫在回傳物件的地方：只在 Query.customer 清掉 email，Order.customer 走預設 resolver 照樣洩漏。寫在欄位自己的 resolver。
  • 列表遇到看不到的就丟錯：整個列表失敗、畫面整塊壞掉。列表過濾，單一物件才報錯。
  • 相信客戶端傳來的角色：x-role 標頭、request body 裡的 role 誰都能改。角色一律從伺服器端的 session 或驗證過的 token 取得。
  • 以為關掉內省就安全：schema 不是秘密。白名單和成本限制才是防護。
  • 只有深度限制：別名與大清單都在深度限制內。加上成本計算。
  • 成本計算漏掉 fragment、別名或變數：最容易被繞過的三個地方。變數還要注意 Yoga 的驗證快取不看 variables。
  • 白名單的開關看請求：「帶某個標頭就允許任意查詢」等於沒有白名單。只看伺服器自己的設定。
  • 公開 API 用白名單：第三方沒辦法用。第一方用白名單，公開 API 用成本限制加依成本限流。

小結

  • GraphQL 的型別互相連通，授權要在每條路徑都生效：放在資料存取層，或集中成幾個函式、由每個型別與欄位的 resolver 呼叫。
  • 直接要求的單一物件回 UNAUTHENTICATED／FORBIDDEN；列表把看不到的濾掉；敏感欄位可為 null，沒權限回 null。角色只看伺服器端的 viewer。
  • 深度限制（useDepthLimit({ maxDepth })）在驗證階段擋下過深的查詢，但擋不住寬而淺的查詢。
  • 成本計算是自己寫的 ValidationRule：欄位 1 分、清單乘 first、巢狀相乘、展開 fragment、別名各算、用請求的 variables；可以拿成本來限流。
  • 第一方客戶端用 persisted operations 白名單，伺服器只執行登記過的雜湊；公開 API 靠成本限制與限流。
  • CSRF 防護要求簡單請求帶自訂標頭；關內省不是安全邊界；開了批次請求要設上限。
