階段 2：GraphQL 基礎 · 第 4 課

N+1 與 DataLoader：一次請求不能發出一百句 SQL（資深）

上一課把每個欄位寫成一個 resolver，程式很乾淨：Order.customer 用 customer_id 查顧客、OrderItem.product 用 product_id 查商品。可是前端查「最近 20 張訂單，每張的顧客與品項」時，這些 resolver 會被呼叫幾十次，每次各發一句 SQL。本機資料少看不出來，上線後訂單一多，一個畫面就讓資料庫收到上百句查詢。

這課的路線：
  1. 示範問題與成因：查 5 張訂單為什麼發出 18 句 SQL，GraphQL 為什麼比 REST 更容易踩到。
  2. 自己做迷你版：怎麼把 20 次「查一個顧客」收成一句 WHERE id = ANY($1)。
  3. dataloader 套件：batch 函式的三條規則，為什麼每個請求要建一份 loader、改了資料要清快取。
  4. 什麼時候不用 DataLoader：每組只取前 3 筆、後台匯出報表這類形狀固定的查詢，改寫一句 JOIN。
  5. 上線後怎麼發現 N+1：開發機看不出來，正式環境靠測試、log 和追蹤把它抓出來。
這課會用到：
  • 第 3 課的 resolver：每個欄位一個函式，parent 是上一層的回傳值；context 每個請求建立一份。
  • TypeScript 課第 7 課的微任務：Promise 的後續工作排在目前的同步程式跑完之後、下一個計時器之前執行。
  • PostgreSQL 課第 9 課的 JOIN：依關聯欄位把兩張表的列配在一起，一句 SQL 查出訂單和它的顧客。

示範問題：查 5 張訂單，發出 18 句 SQL

在 learn/ 執行 node check.mjs api-styles 04，會建立 api-styles/practice/work/04/（還沒安裝套件的話，先照第 2 課開頭的步驟 npm install）。這一課的資料庫是真的 PostgreSQL 18.6：用 PGlite 0.5.13 在 Node 程序裡執行，不需要 Docker。helpers/db.ts 的 createDb() 建一個記憶體資料庫，裡面是咖啡店的資料；它回傳的 db.query(sql, params) 每執行一句，就把 SQL 文字推進 db.log 陣列。數 db.log 的長度，就知道發了幾句。

naive.ts 是沒有優化的 resolver，寫法跟上一課一樣，每個欄位各查各的：

// naive.ts（節錄）
Order: {
  customer: (order, _, ctx) =>
    first(ctx.db.query('SELECT id, name FROM customers WHERE id = $1', [order.customer_id])),
  items: (order, _, ctx) =>
    ctx.db.query('SELECT … FROM order_items WHERE order_id = $1 ORDER BY product_id', [order.id]),
},
OrderItem: {
  product: (item, _, ctx) =>
    first(ctx.db.query('SELECT id, name, price, category FROM products WHERE id = $1', [item.product_id])),
},

在 work/04 執行 node examples/measure.ts 5，它用 naive.ts 執行 { orders(last: 5) { id total customer { name } items { quantity product { name price } } } }，再把 db.log 依 SQL 文字分組：

naive.ts：這次請求一共 18 句 SQL
   1 次  SELECT id, customer_id, ordered_at, total FROM orders ORDER BY ordered_at DESC, id DESC LIMIT $1
   5 次  SELECT id, name FROM customers WHERE id = $1
   5 次  SELECT order_id, product_id, quantity, unit_price FROM order_items WHERE order_id = $1 ORDER BY product_id
   7 次  SELECT id, name, price, category FROM products WHERE id = $1

這就是 N+1 問題：先用 1 句查出 N 筆，再對每一筆各查 1 句，總共 N+1 句。這裡還疊了兩層：訂單 1 句，顧客 N 句，品項 N 句，商品每個品項 1 句。所以句數是 1 + N + N + 品項數。查 20 張訂單、平均每張 3 個品項，就是 1 + 20 + 20 + 60 = 101 句。咖啡店只有 6 種商品，商品卻被查了 7 次：同一個商品被不同訂單重複查。

💡 實務上：「列表頁很慢」常常不是 SQL 慢，而是 SQL 太多
常見的回報是：咖啡店後台的訂單列表本機很快、上線後要好幾秒，可是慢查詢 log（資料庫記錄執行太久的 SQL 的地方）裡找不到任何一句慢的 SQL。每一句都很快，只是有一百句，每句還要走一次到資料庫的網路來回。查這類問題時，先看「這個請求發了幾句 SQL」，再看「哪一句最慢」。資料量越大越慢、而且跟清單長度成正比，是 N+1 的典型特徵；換成分頁只能減輕，不會根治。

為什麼 GraphQL 特別容易 N+1

REST 的一支端點由後端決定回傳什麼，寫 handler 的人看得到整個形狀，自然會寫一句 JOIN 一次查完。GraphQL 把形狀交給客戶端，伺服器把每個欄位拆成獨立的 resolver：Order.customer 只拿到自己那張訂單（parent），不知道旁邊還有 19 張訂單也在查顧客。每個 resolver 單獨看都對，合起來就是 N+1。

REST handlerGraphQL resolver
誰決定回傳哪些欄位後端客戶端的查詢
寫程式時看得到什麼整個回應只有自己的 parent 和參數
常見寫法一句 JOIN每個關聯欄位各查一次
N+1 何時出現ORM 延遲載入時（NestJS 課第 16 課）只要清單底下有關聯欄位

不能叫前端別查巢狀欄位，那等於放棄 GraphQL。要做的是讓同一層的兄弟 resolver 把各自要的 id 交給同一個地方，由它合成一句 SQL。這個動作叫批次（batching）：把很多個小請求合成一個。

原理：自己做一個 30 行的迷你版

關鍵在時機。GraphQL 執行到 Order.customer 這一層時，會在同一段同步程式裡把 20 張訂單的 resolver 依序呼叫完，才輪到下一個工作。所以只要讓 resolver 先「登記」要哪個 id、拿回一個 Promise，等這段同步程式跑完再一次查，就能把 20 個 id 收成一批。examples/mini-loader.ts：

// examples/mini-loader.ts（節錄）
function createMiniLoader<K, V>(batch: (keys: K[]) => Promise<V[]>) {
  let queue: Job<K, V>[] = []
  async function dispatch() {
    const jobs = queue
    queue = []                                   // 之後的 load 進下一批
    try {
      const values = await batch(jobs.map(j => j.key))
      jobs.forEach((job, i) => job.resolve(values[i]))   // 第 i 個 key 拿第 i 個值
    } catch (error) {
      jobs.forEach(job => job.reject(error))
    }
  }
  return {
    load(key: K): Promise<V> {
      return new Promise<V>((resolve, reject) => {
        queue.push({ key, resolve, reject })
        if (queue.length === 1) queueMicrotask(dispatch)   // 這一批的第一個 key：排定「目前的同步程式跑完後」送出
      })
    },
  }
}

執行 node examples/mini-loader.ts：

batch 收到 keys： [ 2, 1, 2 ]
第一批結果： [ '陳美華', '王小明', '陳美華' ]
batch 收到 keys： [ 3 ]
第二批結果： 林志豪
  • load(key) 不馬上查，只把 key 放進佇列、回傳 Promise。
  • 第一個 key 進佇列時，用 queueMicrotask 排定 dispatch。微任務在目前的同步程式跑完後才執行（TypeScript 課第 7 課），所以同一段程式裡的三次 load 都進了同一批。
  • batch 收到一組 key，回傳一組值，第 i 個值對應第 i 個 key。這個約定是整個機制的核心，下一節的三條規則都從它來。
  • 等過一次之後才 load(3)，那時第一批已經送出，所以它自成一批。批次只合併「同一個時機」的 load。

正式的 DataLoader（Facebook 開源、現在放在 GitHub 的 graphql 組織下維護的 dataloader 套件，本課用 2.2.3）做的是同一件事，送出的時機再晚一點：dataloader 2.2.3 的原始碼裡，在 Node 上是先等目前排入的 Promise 工作跑完，再用 process.nextTick（Node 課第 7 課）送出。這樣 resolver 裡多一層 await 才呼叫的 load 也能趕上同一批。另外它多了快取（同一個 key 只查一次）、maxBatchSize（一批最多幾個 key）和錯誤處理。

用 dataloader 套件：batch 函式的三條規則

建立一個 loader 只要給它一個 batch 函式（batch function）：收到一組 key，一次回傳對應的一組值。

import DataLoader from 'dataloader'

const customerById = new DataLoader<number, CustomerRow | null>(async ids => {
  const rows = await db.query<CustomerRow>('SELECT id, name FROM customers WHERE id = ANY($1)', [ids])
  const byId = new Map(rows.map(r => [r.id, r]))
  return ids.map(id => byId.get(id) ?? null)
})

// resolver 裡
customer: (order, _, ctx) => ctx.loaders.customerById.load(order.customer_id)

WHERE id = ANY($1) 是 PostgreSQL 用一個陣列參數（PostgreSQL 課第 14 課）一次比對多個值的寫法：$1 傳 JS 陣列 [3, 1, 5]，等於 id IN (3, 1, 5)，但不管幾個 id 都是同一句 SQL。PGlite 會把 JS 的數字陣列當成整數陣列，不用另外轉型。id 是主鍵，本來就有索引；用別的欄位批次查時（例如 order_items.order_id），那個欄位要有索引（PostgreSQL 課第 20 課），否則一句查詢會掃整張表（PostgreSQL 課第 20 課）。

batch 函式的回傳有三條規則，違反任何一條，結果就會錯或整批失敗：

  1. 長度相同：回傳陣列的長度要等於 keys。長度不同時，DataLoader 會讓這一批的每個 load 都失敗（錯誤訊息是 …not return a Promise of an Array of the same length as the Array of keys）。
  2. 順序相同：第 i 個值對應第 i 個 key。SQL 沒寫 ORDER BY 時，資料庫不保證回傳順序；就算寫了 ORDER BY id，順序也是 id 由小到大，不是 keys 的順序。所以一律先放進 Map，再用 ids.map(…) 依 keys 的順序取出。
  3. 找不到放 null：不能把找不到的過濾掉，那會讓長度不同。也可以放一個 Error 物件，只讓那一個 load 失敗。

直接回傳 rows 是最常見的錯：本機測試資料剛好每個 id 都有、順序也剛好一樣，就會一直通過。keys 是 [3, 1, 9]、資料庫只有 1 和 3 時，正確回傳是 [row3, row1, null]。

一對多的關聯（一張訂單有多個品項）也一樣，只是每個 key 對應一個陣列，回傳陣列的陣列：

const itemsByOrderId = new DataLoader<number, ItemRow[]>(async orderIds => {
  const rows = await db.query<ItemRow>(
    'SELECT order_id, product_id, quantity, unit_price FROM order_items WHERE order_id = ANY($1) ORDER BY order_id, product_id',
    [orderIds])
  const byOrder = Map.groupBy(rows, r => r.order_id)     // Map<order_id, ItemRow[]>
  return orderIds.map(id => byOrder.get(id) ?? [])          // 沒有品項：空陣列
})
// orderIds [7, 2, 99] → [[品項…], [品項…], []]

Map.groupBy(陣列, 取 key 的函式) 是 ES2024 加入的內建函式（Node 21 起可用），把陣列依 key 分組成 Map。改用 loader 之後再跑一次 node examples/measure.ts mine（練習 2 做完才會成功），不管查幾張訂單都是 4 句：

resolvers.ts：這次請求一共 4 句 SQL
   1 次  SELECT id, customer_id, ordered_at, total FROM orders ORDER BY ordered_at DESC, id DESC LIMIT $1
   1 次  SELECT id, name FROM customers WHERE id = ANY($1)
   1 次  SELECT order_id, product_id, quantity, unit_price FROM order_items WHERE order_id = ANY($1) ORDER BY order_id, product_id
   1 次  SELECT id, name, price, category FROM products WHERE id = ANY($1)
key 的型別要一致。DataLoader 的快取用 Map 比對 key，'1' 和 1 是兩個不同的 key。GraphQL 的 ID 參數進來是字串，資料庫的 customer_id 是數字：在 resolver 裡統一轉成數字（Number(args.id)）再 load。

每個請求一份 loader；改了資料要清快取

DataLoader 的快取是每個請求的快取（per-request cache）：同一個請求裡 load 過的 key，第二次直接拿同一個 Promise，不再查資料庫。它沒有過期時間，也不知道誰有權限看什麼。所以 loader 一定要在 context 裡每個請求建立一份：

// context.ts
export function createContext(db: Db): Context {
  return { db, loaders: createLoaders(db) }   // 每個請求一份新的；請求結束就跟著回收
}

把 loader 存在模組變數裡「省下建立的成本」，會出這些事：

  • 權限外洩：王小明的請求載入了他的訂單；接著陳美華的請求用同一個 loader 查同一個 id，直接從快取拿到，權限檢查如果寫在批次查詢裡就被跳過了。
  • 讀到過期資料：店長改了拿鐵的價格，之後每個請求都還拿到快取裡的舊價格，直到程序重啟。
  • 記憶體只增不減：快取永遠不清，載入過的每一列都留在記憶體裡。

建立 loader 的成本只是幾個物件，可以忽略。跨請求的快取要用真的快取層，並且設計失效機制（NestJS 課第 19 課的 Redis）。

同一個請求裡也會過期：mutation 先 load 了商品確認它存在，接著 UPDATE 改價，再 load 一次回傳結果。第二次 load 會拿到快取裡的舊價格。改完資料要處理快取：

const [row] = await ctx.db.query('UPDATE products SET price = $2 WHERE id = $1 RETURNING id, name, price, category', [id, args.price])
ctx.loaders.productById.clear(id).prime(id, row)   // 清掉舊值，放入新的那一列
return ctx.loaders.productById.load(id)

clear(key) 清掉一個 key 的快取，下次 load 會重新查；prime(key, value) 把已知的值直接放進快取（key 已經有值時 prime 不會覆蓋，所以先 clear）；clearAll() 清掉全部。只 clear 不 prime 也對，代價是多一句 SELECT。不要用 new DataLoader(fn, { cache: false }) 來「修」：那樣同一個請求裡重複的 id 又會被查很多次。

💡 實務上：review 時檢查 loader 在哪裡建立、結果會不會因人而異
新增 DataLoader 的 PR，資深工程師會先問三件事：loader 是不是在 context 裡每個請求建立；batch 函式的結果會不會因為「誰在看」而不同（例如顧客只能看自己的訂單），會的話權限條件要跟著這個請求的使用者一起放進 batch 的 SQL；這個欄位會被 mutation 改到嗎，改到之後有沒有 clear。跨請求共用的錯誤在單一請求的測試裡看不出來，要送兩個請求來驗證：像練習 3 在兩個請求之間改資料，或用兩個不同使用者各查一次，確認第二個請求拿到的是自己的結果。

什麼時候不用 DataLoader

DataLoader 解決的是「同一層的兄弟各自要一筆關聯資料」。它不是萬用的：

  • 每一層仍至少一句：它把同一層合併，不會把不同層合併。查詢有 3 層關聯，就至少 3 句（加上最上層）。這通常可以接受，因為句數跟資料量無關了。
  • 每個父項各自要 LIMIT：「每張訂單只顯示金額最高的 3 個品項」。批次之後在同一句 SQL 加 LIMIT 3，LIMIT 作用在整句查詢上：
SELECT order_id, product_id FROM order_items WHERE order_id = ANY($1) LIMIT 3
-- 傳 [1, 2, 3, 4]，只回 3 列：(1,1) (1,2) (2,2)，訂單 3、4 一個品項都沒有

要每組各取 3 筆，用 LATERAL JOIN（PostgreSQL 課第 29 課）或視窗函式 ROW_NUMBER() OVER (PARTITION BY order_id …)（PostgreSQL 課第 17 課）。這句 SQL 也可以放在 batch 函式裡，重點是每組各自排序、各自 LIMIT：

SELECT o.id AS order_id, i.product_id, i.quantity, i.unit_price
FROM unnest($1::int[]) AS o(id)
CROSS JOIN LATERAL (
  SELECT product_id, quantity, unit_price FROM order_items
  WHERE order_id = o.id
  ORDER BY quantity * unit_price DESC, product_id
  LIMIT 3
) AS i
  • 形狀固定、每次都要全部資料：後台的訂單詳情、匯出報表，每次都要訂單＋顧客＋全部品項＋商品名稱。這種不是由客戶端決定形狀的地方，在一個地方寫一句 JOIN 最直接。
  • 看 info 決定要不要 JOIN：resolver 的第四個參數 info 帶著這次查詢選了哪些欄位，可以在父 resolver 先看「有沒有選 customer」再決定要不要 JOIN（叫 lookahead）。這是進階手段，程式會跟查詢形狀綁在一起，多數時候 DataLoader 就夠了。

練習 4 會用到下面這張表。每一題選一種做法，再選一個理由代碼：

理由代碼意思
optional-field要不要查這個關聯由客戶端決定，同一層很多兄弟各要一筆；只在真的被查時才批次載入
per-parent-limit每個父項要各自排序、各自取前幾筆，一句 LIMIT 做不到
fixed-shape形狀固定、每次都要全部資料，一句 JOIN 一次查完

less-code程式比較短
shared-cache快取可以讓所有請求共用

後三個是常見但不成立的理由：JOIN 在一對多時會讓父列重複很多次，不一定比較快；程式長短不是選擇的依據；DataLoader 的快取不能跨請求。

上線後怎麼發現 N+1

N+1 在開發機上幾乎看不出來：資料少、資料庫在本機，100 句也只要幾毫秒。上線後資料變多、資料庫在另一台機器，每句多一次網路來回，才變慢。所以要主動量：

  • 在測試裡斷言 SQL 句數：本課練習的做法。重要的查詢寫一個測試：「不管幾張訂單，都是 4 句」。有人把 resolver 改回直接查詢，測試會擋下來。
  • 每個請求記錄 SQL 數量：用 request context（Node 課第 19 課）在每個請求結束時把句數寫進 log，查「句數最多的操作名稱」。
  • tracing 的 span 數：分散式追蹤（DevOps 課第 23 課）會把每句 SQL 畫成一個 span，一個請求底下排了幾十條一樣的 span 就是 N+1。
💡 實務上：句數多的操作，先修流量大的
log 排出「句數最多的操作」之後，不用一次全部修完：先修顧客天天在點的畫面（例如咖啡店 App 的訂單紀錄），後台一天只跑幾次的報表可以排後面。修完補一個句數測試，放進每次 push 都會自動跑的測試（CI）。要注意測試只擋得住你寫進去的查詢：前端在查詢裡多加一個巢狀欄位，就是新的查詢形狀，要把它也加進測試，或在 code review 時問一句「這個欄位底下有沒有用 loader」。

練習 5：DataLoader 怎麼知道「該送出這一批了」？

✓ dataloader 2.2.3 在 Node 上先等排入的 Promise 工作跑完，再用 process.nextTick 送出。GraphQL 在同一段程式裡呼叫完同一層的兄弟 resolver，所以它們的 load 會合在一起。用計時器（a）會讓每個請求白白多等；數量門檻（c）在 key 不夠多時會一直等；立刻送（d）就回到 N+1。要改時機可以用 batchScheduleFn 選項，很少需要。

練習 6：batch 函式收到 keys [3, 1, 9]，資料庫只有 id 1 和 3。正確的回傳是？

✓ 回傳要跟 keys 一樣長、一樣順序，找不到的放 null（或放 Error 物件，只讓那一個 load 失敗）。a 長度不同，整批都會失敗；c 長度對但順序是資料庫的順序，3 號會拿到 1 號的資料；d 讓同一批的其他 load 也一起失敗。

練習 7：把 DataLoader 建在模組層級、讓所有請求共用，會怎樣？

✓ DataLoader 的快取只是記憶化（memoization）：同一個 key 給同一個 Promise，沒有過期、沒有權限的概念，設計上就是每個請求一份。它不會報錯（b），批次也照常運作（d），所以這個錯誤在測試裡常常看不出來。跨請求的快取要用專門的快取層並設計失效。

練習 8：「每張訂單只顯示金額最高的 3 個品項」，用 DataLoader 批次 orderId，batch 函式的 SQL 加上 LIMIT 3，結果是？

✓ LIMIT 作用在整句查詢上，不知道 order_id 的分組。要每組各取 3 筆，用 LATERAL JOIN 或 ROW_NUMBER() OVER (PARTITION BY order_id …)，batch 函式再依 order_id 分組。DataLoader 只負責收集 key，不會改你的 SQL（d）。

常見錯誤

  • batch 函式直接回傳 rows：順序是資料庫的順序，找不到的 id 也不見了。先放進 Map，再用 keys.map(…) 對回去，找不到放 null。
  • 在 batch 函式裡逐筆查詢：Promise.all(ids.map(id => db.query(… = $1))) 還是 N+1，只是包在 DataLoader 裡。要一句 WHERE id = ANY($1)。
  • 一對多回傳扁平陣列：itemsByOrderId 的每個 key 要對應一個陣列，回傳陣列的陣列；沒有品項的放 []。
  • loader 建在模組層級：快取跨請求，會洩漏權限、讀到舊資料。在 context 裡每個請求建立。
  • mutation 之後沒清快取：同一個請求後面的讀取拿到舊值。改完用 clear(id)，需要時再 prime(id, 新值)（只 prime 不 clear 不會覆蓋舊值）；只回傳 UPDATE 的結果、不動快取也不對，後面的讀取還是舊值；不要用 cache: false 繞過。
  • key 的型別不一致：字串 '1' 和數字 1 是不同的 key，同一個商品會被查兩次。進 loader 前統一型別。
  • 以為 DataLoader 讓查詢只剩 1 句：它合併同一層，每一層仍至少一句；每組各取前幾筆要用 LATERAL 或視窗函式。
  • 沒有量測：本機資料少看不出 N+1。重要查詢在測試裡斷言 SQL 句數，上線後記錄每個請求的句數。

小結

  • N+1：先 1 句查出 N 筆，再對每筆各查 1 句。GraphQL 的 resolver 各自獨立，只要清單底下有關聯欄位就會發生。句數可以從 SQL 記錄算出來：1 + N + N + 品項數。
  • DataLoader 在同一個時機收集所有 load(key)，一次呼叫 batch 函式，再依順序把結果分回去；同一個請求裡相同的 key 只查一次。
  • batch 函式三條規則：長度相同、順序相同、找不到放 null；一對多回傳陣列的陣列；SQL 用 WHERE … = ANY($1) 一句查完，欄位要有索引。
  • loader 每個請求一份，在 context 建立；改了資料用 clear／prime 更新快取。
  • 每組各取前幾筆用 LATERAL 或視窗函式；形狀固定的地方直接 JOIN；用測試斷言句數，上線後記錄每個請求的句數。
