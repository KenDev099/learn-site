階段 5：契約與整合架構 · 第 12 課

期末專題：咖啡店的 GraphQL 菜單與訂單歷史、gRPC 庫存服務與契約測試

前面十一課各練一塊：schema、resolver、DataLoader、分頁、授權、防護、codegen、protobuf、gRPC、契約、BFF。上線的系統不會一次只出一種問題：訂單歷史慢，是因為某個欄位繞過了 loader；下單重複扣庫存，是因為逾時後重試；前端突然壞掉，是因為後端改了一個欄位名。這一課把它們組成一條完整的路徑：App → GraphQL（菜單、訂單歷史、下單）→ gRPC 庫存服務，資料在 PGlite。

起始專案「功能都有」，但每個上線會出事的地方都還沒處理。你要照需求一塊一塊修好。做完之後，你會有一個能拿來說明「我怎麼設計一個 API」的完整專案。

這課的路線：
  1. 需求與架構：產品經理只給畫面，工程師怎麼補上效能、可靠性、安全的具體數字，起始專案哪些檔案歸你寫。
  2. 驗收測試與 GraphQL 這一側：測試怎麼判分、從哪裡開始修；DataLoader、分頁、授權接起來後，訂單歷史為什麼最多 6 句 SQL。
  3. 防護與下單：白名單、深度、成本、錯誤遮罩一次設好；逾時重試時怎麼不重複扣庫存，庫存服務掛掉時菜單照樣顯示。
  4. 契約檢查：一個指令在合併前擋下 schema、proto、App 契約的破壞性變更。
  5. ADR 與回顧：把設計決定寫成一頁文件，面試時拿它說明取捨，並列出上線前還缺什麼。
這課會用到：
  • 第 4 課的 DataLoader：同一層的 load() 合成一句 WHERE id = ANY($1)，loader 每個請求建立一份；測試靠 SQL 記錄數句數。
  • 第 6 課的授權與防護：每條拿得到訂單的路徑都檢查擁有者，敏感欄位只給店員；深度、成本限制與 persisted operations 白名單擋住惡意查詢。
  • 第 9 課的 deadline 與狀態碼：呼叫庫存服務一定設 deadline；庫存不足回 FAILED_PRECONDITION，暫時連不上回 UNAVAILABLE。
  • 系統設計課第 9 課的冪等：請求帶一個唯一的 key，同一個 key 送幾次都只生效一次，逾時後重試才安全。

需求：三個畫面、一個店員後台、六條非功能需求

產品經理給的需求只有畫面。工程師要自己補上「怎樣才算做好」，也就是非功能需求：效能、可靠性、安全的具體數字。沒有數字就沒辦法驗收，也沒辦法在設計時取捨。

驗收測試怎麼判分，建議的順序

驗收測試（acceptance test）從系統外面確認需求有沒有被滿足：它只看 HTTP 與 gRPC 的回應、資料庫裡的 SQL 記錄、庫存數字、pact 檔、指令的結束碼，不管你的函式怎麼拆。跟單元測試的差別是：單元測試告訴你「這個函式對不對」，驗收測試告訴你「這個需求做到了沒」。內部怎麼寫由你決定，只要外部行為對。

每次執行都換資料：300 張訂單用不同的亂數種子產生，價格、庫存、備註也隨機，所以寫死答案不會過。建議照這個順序做，每完成一塊就跑一次 node check.mjs api-styles 12，不要全部寫完才跑：

  1. 練習 1：菜單（起始就能跑）→ 訂單歷史改 keyset → DataLoader → 授權。
  2. 練習 2：深度、成本 → 白名單 → 錯誤遮罩。
  3. 練習 3：庫存服務的冪等 → BFF 的 deadline 與降級 → 下單流程的順序與交易 → schema 加 InventoryUnavailable。
  4. 練習 4：契約檢查（provider 用正式模式，需要練習 2 的白名單）。
  5. 練習 5：ADR。

GraphQL 這一側：把第 4–6 課接起來

SQL 上限 6 句是怎麼算出來的：GraphQL 一層一層執行，DataLoader 把同一層的 load() 合成一句，所以句數跟「資料有幾筆」無關，只跟「查詢有幾層關聯」有關。

層欄位SQL
1mecustomers WHERE id = ANY($1)（customerById）
2orders(first: 20)一句 keyset 查詢，LIMIT 21
320 張訂單的 items、customeritemsByOrderId 一句；customer 都是第 1 層載入過的同一位顧客，loader 的快取直接回傳，不發 SQL
4所有品項的 productproductById 一句

合計 4 句（實測）。店員查好幾位顧客的訂單時，第 3 層的 customerById 才會真的發一句，變成 5 句；上限 6 留了餘裕。超過 6 句幾乎都是兩種原因：某個關聯欄位直接 ctx.db.query、沒走 loader；或 batch 函式裡用 Promise.all(ids.map(…)) 每個 id 各查一次（看起來用了 DataLoader，其實還是 N 句）。查法：印出 log，找重複出現、只差參數的句子。

loader 要每個請求一份（app.ts 在 context 裡呼叫 createLoaders(db)）。放在模組層級共用，第一個請求載入的資料會一直留在快取裡，資料改了也看不到，而且不同使用者會共用快取。

授權照第 6 課的原則：每條拿得到訂單的路徑都要經過 auth.ts。這個 schema 有四條：

  • order(id)：單一物件，用 requireOrder（沒登入 UNAUTHENTICATED、別人的 FORBIDDEN）。
  • me.orders、customer(id).orders：都是 Customer.orders，用 canSeeOrdersOf，看不到就回空的 connection（EMPTY）。
  • Product.orders：最容易漏掉。顧客只能看到自己的，條件要寫進 SQL（AND o.customer_id = $2），不要先查出全部再在 JavaScript 濾掉：先查再濾，first: 10 濾完可能只剩 2 筆，還多讀了別人的資料。
  • Order.customer.orders：訂單看得到，代表你是本人或店員，所以這條自然安全。

個資欄位 Customer.email、Order.internalNote 寫在欄位自己的 resolver（staffOnly），不論 Customer 從哪條路徑來都會經過。

💡 實務上：GraphQL 的資料外洩多半出在「另一條路徑」
資安回報的 GraphQL 漏洞，常見的不是主要查詢沒擋，而是從關聯欄位繞進去（例如從商品查到所有人的訂單）。新增任何回傳 Customer 或 Order 的欄位時，code review 要先問：「這條路徑誰能走到？授權寫在哪？」授權放在欄位或資料層，而不是只放在最上層的 query，新路徑才會自動受保護。資深的做法是每加一條路徑就補一個「別人的資料拿不到」的測試，像練習 1 那樣。

防護：protect.ts 回傳給 createYoga 的設定

app.ts 把 protect({ dev, operations, logger }) 的回傳值展開進 createYoga。你要回傳 { plugins, maskedErrors }：

plugins: [
  usePersistedOperations({ getPersistedOperation: key => …, allowArbitraryOperations: dev }),
  useCSRFPrevention({ requestHeaders: ['x-graphql-yoga-csrf'] }),
  useDepthLimit({ maxDepth: MAX_DEPTH }),
  useCostLimit(MAX_COST),          // cost-plugin.ts：用這次請求的 variables 算成本
],
maskedErrors: { maskError(error, message, isDev) { … } },

白名單從哪來（第 7 課）：codegen.ts 設了 persistedDocuments: true，codegen 會把 app/ 底下每個操作寫進 app/gql/persisted-documents.json，鍵是 "sha256:<雜湊>"。App 送出的 sha256Hash 只有 <雜湊> 那段，所以 app.ts 的 loadOperations() 讀檔時已經去掉前綴，交給你的是 Map<雜湊, 查詢文字>。用 Map 查，不要用一般物件（operations['toString'] 會拿到原型上的函式）。

在 Yoga 6.0.1 實測，正式模式（allowArbitraryOperations: false）送查詢文字會得到 PersistedQueryOnly，送不在清單裡的雜湊得到 PersistedQueryNotFound，兩者都不會執行任何 resolver。allowArbitraryOperations 只能看伺服器自己的設定（dev），不能看請求帶了什麼標頭。

錯誤遮罩沿用第 5 課：用 graphql-yoga 匯出的 maskError 包一層，回傳值跟原本的 error 不是同一個，就代表被遮罩了，把原錯誤（GraphQLError 的話取 originalError）交給 logger.error。Yoga 遮罩後的錯誤是 message: "Unexpected error."、extensions.code: "INTERNAL_SERVER_ERROR"；你刻意丟的 GraphQLError（FORBIDDEN、BAD_USER_INPUT）保留原訊息。

下單：先預留庫存，成功才建立訂單

下單牽涉兩個系統：庫存服務（記憶體裡的數字）和資料庫（訂單）。兩邊沒有共用的交易，所以順序決定了「失敗時留下什麼」。

順序庫存服務掛掉時資料庫寫入失敗時
✗ 先建訂單，再 Reserve資料庫多一張沒有庫存的訂單，店員會照單做沒事
✓ 先 Reserve，成功再建訂單什麼都沒留下，回 InventoryUnavailable庫存被扣了但沒有訂單（少賣幾杯）

第二種的失敗代價小（少賣不會做錯單），而且可以補救：資料庫寫入失敗時呼叫一個「釋放預留」的 RPC，或讓預留在一段時間後自動過期。這就是 saga 的補償動作（系統設計課第 13 課）。這個專題刻意不做補償，在 ADR 和回顧裡寫出來就好。完整流程：

  1. 驗證：要登入的顧客；數量 1–20（不對回 InvalidQuantity）；商品存在（不存在丟 BAD_USER_INPUT）。起始程式已經寫好。
  2. 重送檢查：SELECT … FROM orders WHERE customer_id = $1 AND client_order_id = $2，有就直接回那張訂單，不再扣庫存。
  3. Reserve：reserveFor(ctx, `${顧客 id}:${clientOrderId}`, lines)。key 加上顧客 id，兩位顧客的 App 剛好產生同一個 clientOrderId 也不會互相影響。
  4. 交易裡建立訂單與品項：ctx.db.transaction(async tx => …)，訂單和品項一起成功或一起失敗。

clientOrderId 是 App 按下「下單」時產生的唯一編號（例如 crypto.randomUUID()）。網路斷掉、App 重試時帶同一個值，伺服器就知道「這是同一筆」。冪等要做在三層，因為重試可能來自任何一層（系統設計課第 9 課）：

  • 庫存服務：記住做過的 idempotency_key 與第一次的回應，同一個 key 再來時不扣，直接回第一次的回應。BFF 呼叫 Reserve 逾時，不代表庫存服務沒扣，重試時就靠這一層。
  • BFF：第 2 步的重送檢查。
  • 資料庫：UNIQUE (customer_id, client_order_id)。同一個 clientOrderId 同時送兩次，兩個請求都通過第 2 步，最後一道防線是唯一約束（PostgreSQL 課第 12 課）：INSERT … ON CONFLICT (customer_id, client_order_id) DO NOTHING RETURNING …，沒插入（回傳 0 列）就查出已存在的那張。

不能超賣靠庫存服務：Reserve 先檢查全部品項、再全部扣，中間沒有 await。Node 是單執行緒，一個 handler 在沒有 await 的區段裡不會被別的請求插隊，所以 30 個請求同時搶 10 杯拿鐵，恰好 10 個成功。換成資料庫或多個程序時要改用交易與列鎖（PostgreSQL 課第 19 課）。

💡 實務上：跨系統的寫入，先問「中途失敗會留下什麼」
下單、付款、寄送通知這類跨兩個系統的動作，客服最常收到的回報是「扣款了但沒有訂單」或「同一筆被建立兩次」。設計時逐一列出每一步失敗後的狀態，選留下的爛攤子最小、最容易補救的順序。補償動作本身也可能失敗，所以實務上常再加一個定期對帳的排程：比對兩邊的資料，找出「庫存扣了卻沒有訂單」這類不一致，再釋放或通知人處理。PM 關心的是「使用者會不會被多扣、店員會不會做錯單」，用這個語言跟他說明取捨。

庫存不夠：用錯誤細節帶出是哪個商品

第 9 課說過，庫存不夠回 FAILED_PRECONDITION。但 App 要顯示「拿鐵只剩 2 杯」，只有狀態碼和一段訊息不夠，訊息是給人看的，程式不該去解析它。gRPC 的做法是錯誤細節（error details）：錯誤可以附帶任意個 protobuf 訊息，放在回應的 trailer（grpc-status-details-bin）裡。這個專案的 proto 定義了 OutOfStockDetail { product_id, available }，庫存服務這樣丟（起始程式已經寫好）：

throw new ConnectError(`庫存不足：…`, Code.FailedPrecondition, undefined,
  [{ desc: OutOfStockDetailSchema, value: { productId, available } }])

呼叫端用 findDetails 取出（@connectrpc/connect 2.3.0 的 ConnectError：第三個參數是 metadata、第四個是要送出的細節）：

const err = ConnectError.from(e)
const [detail] = err.findDetails(OutOfStockDetailSchema)   // 沒有這種細節時是空陣列
if (detail) return { ok: false, outOfStock: { productId: detail.productId, available: detail.available } }

deadline 預算與降級

context 裡有兩個欄位：deadline（收到請求時的 now() + 500）和 now（測試會換成假的時鐘）。每次呼叫庫存服務時算一次：

const timeoutMs = ctx.deadline - ctx.now() - MARGIN_MS   // 留 20 ms 給之後寫資料庫、回應
if (timeoutMs < MIN_CALL_MS) → 不呼叫，直接當成逾時
await ctx.inventory.reserve(req, { timeoutMs })

剩不到 20 ms 還呼叫，庫存服務幾乎一定來不及，還白白占用它的資源，不如直接回 TIMEOUT。錯誤怎麼對應：

情況stockFor（菜單）reserveFor（下單）
成功Map（商品 id → 剩幾份）{ ok: true }
FAILED_PRECONDITION 帶 OutOfStockDetail—{ ok: false, outOfStock } → OutOfStock
DEADLINE_EXCEEDED，或預算不夠沒呼叫nullfailure: 'TIMEOUT'
其他錯誤（連不上是 UNAVAILABLE）nullfailure: 'DOWN'

stockFor 回 null 時，MenuItem.available 的 resolver（給好的）丟 INVENTORY_UNAVAILABLE，因為 available 是可為 null 的欄位，錯誤只讓這個欄位變 null，菜單其他欄位照常回傳（第 3 課的 null 傳播）。降級時一定要 ctx.logger.error(err)：使用者看不出問題，監控也看不到的話，庫存服務掛一整天都沒人發現。持續失敗時應該加斷路器（系統設計課第 11 課）直接跳過呼叫，這個專題不判分。

schema 要加上這個結果，App 才分得出「庫存不夠」和「暫時不能下單」：

enum InventoryFailure { TIMEOUT DOWN }
type InventoryUnavailable { reason: InventoryFailure! }
union PlaceOrderResult = OrderPlaced | OutOfStock | InvalidQuantity | InventoryUnavailable

union 多一個成員對舊的 App 不是破壞性變更，但有風險：舊 App 的 PlaceOrder 沒選 ... on InventoryUnavailable，只拿得到 __typename。所以 app/placeOrder.graphql 一開始就選了 __typename，不認識的結果一律顯示「暫時無法下單」。

契約檢查：一個指令跑完四步

node contracts/run.ts 是 CI 在每次合併前要跑的指令，把第 8 課與第 10 課的檢查串在一起。四步各守一條邊界：

步驟守什麼怎麼做
graphql-schema所有 GraphQL 客戶端findSchemaChanges(baseline, 目前)（graphql 17）
buf-breaking呼叫庫存服務的所有服務buf breaking --against contracts/baseline/proto
pact-consumer產生 App 的契約node --test contracts/consumer.ts
pact-provider真的伺服器滿足 App 的契約node --test contracts/provider.ts

baseline 是線上正在被使用的版本（contracts/baseline/），由發布流程在部署後更新；實務上常取 main 分支或 schema registry 上的最新版本。檢查時只讀不寫。每次先用目前的 schema 重新產生 baseline，就永遠是自己跟自己比，永遠不會失敗。

findSchemaChanges 回傳每一個變更的 { type, description }。type 屬於 BreakingChangeType（例如 FIELD_REMOVED）就失敗；其他的（例如 TYPE_ADDED_TO_UNION 屬於 dangerous）印出來提醒就好：

const breaking = new Set<string>(Object.values(BreakingChangeType))
const changes = findSchemaChanges(buildSchema(baseline), buildSchema(current))
const bad = changes.filter(c => breaking.has(c.type))

schema 檢查只知道「型別變了」，不知道哪個客戶端在用哪個欄位；Pact 補上這一塊。consumer 測試（App 這一方）描述「我送什麼、期待什麼形狀的回應」，用 App 真正的 fetchOrderHistory 打 Pact 開的 mock server，通過後寫出 pact 檔。provider 驗證（伺服器這一方）開一個真的 GraphQL 伺服器，Pact 把 pact 檔裡的請求重播一次、比對回應。對著 mock 驗證永遠會通過，等於沒驗。用的 API（@pact-foundation/pact 17.1.4 的 V4）：

await new PactV4({ consumer: 'coffee-app', provider: 'coffee-graphql', dir })
  .addInteraction()
  .given('顧客 1 已登入且有訂單')                 // provider state：provider 驗證前要準備好的前提
  .uponReceiving('App 查詢我的訂單第一頁')
  .withRequest('POST', '/graphql', b => b.headers({ … }).jsonBody({ … }))
  .willRespondWith(200, b => b.jsonBody({ data: { me: { id: like('1'), orders: { edges: eachLike({ … }) } } } }))
  .executeTest(async server => { await fetchOrderHistory(server.url, 'pact-customer-1', { first: 2 }) })

await new Verifier({ provider: 'coffee-graphql', providerBaseUrl: url, pactUrls: [pact 檔的絕對路徑],
  stateHandlers: { '顧客 1 已登入且有訂單': async () => { /* 登記 session */ } } }).verifyProvider()

回應用 matcher（MatchersV3 的 like、eachLike、integer、boolean）描述形狀與型別，不要寫死值：provider 的資料不會跟範例一模一樣。請求 body 是 App 會送的內容，正式環境只送雜湊（ORDER_HISTORY_HASH），所以 provider 也要用正式模式（dev: false）驗證，跟上線的設定一致。

結束碼是 CI 唯一看得懂的訊號：任何一步失敗都要讓 node contracts/run.ts 以非 0 結束（process.exitCode = 1），並停止後面的步驟。起始程式 catch 了錯誤卻什麼都沒做，CI 會顯示綠燈。

💡 實務上：契約檢查擋的是「舊版 App 還在用」的欄位
App 已經上架、使用者不一定會更新，後端刪掉一個欄位，舊版 App 就壞了，而且沒辦法馬上修好。所以檢查要在合併前擋下（通常設定成 CI 沒過就不能合併），而不是上線後才看錯誤率。真的要移除欄位時，先標 @deprecated、從監控確認沒有舊版在用，再刪。確定要做破壞性變更時，資深的做法是在 PR 寫清楚影響哪些客戶端、讓 reviewer 同意，而不是把那一步關掉或連 baseline 一起改掉。

ADR：把決定和理由寫下來

ADR（Architecture Decision Record，架構決策紀錄，系統設計課第 18 課）是一頁短文件：當時的狀況、決定了什麼、考慮過哪些替代方案、要付出什麼代價。一年後新同事問「為什麼庫存用 gRPC」時，答案在這裡，不在某個離職同事的腦袋裡。adr.md 的範本有五個章節：狀態、背景、決定、替代方案、後果。寫完用這份清單自我檢查：

  • 背景有具體的數字或限制（客戶端種類、500 ms 預算、團隊大小），不是「為了更好的架構」。
  • 決定說了 App、服務之間、外部合作夥伴各用什麼，以及各自的理由。
  • 替代方案至少兩個，每個寫出為什麼不選；沒有替代方案的決定，讀的人無法判斷你有沒有想過。
  • 後果同時有好處與代價：要維運三套工具、學習曲線、GraphQL 的 HTTP 快取比較難、BFF 多一跳。只寫優點的 ADR 不可信。
  • 寫出演進方式：欄位怎麼淘汰（@deprecated、proto 的 reserved）、誰更新 baseline。

測試只檢查結構（章節、三種風格、替代方案數量、後果有沒有提到代價、400–2000 字），內容好不好要自己對照清單。參考答案在 answer/12/adr.md，也可以在練習 5 按「看答案」。

交付後的回顧：刻意的簡化與上線前還缺什麼

專題為了在一台電腦、一分鐘內跑完，做了幾個刻意的簡化。資深工程師交付時會把它們寫出來，而不是假裝沒有：

  • 單一程序、記憶體裡的庫存與冪等紀錄：重啟就消失、不能開多台。正式環境放資料庫（冪等紀錄設保存期限），扣庫存用交易與列鎖。
  • 沒有補償：Reserve 成功但訂單寫入失敗時，庫存不會還回去。要加釋放預留的 RPC 或預留過期。
  • 沒有斷路器：庫存服務持續掛掉時，每個請求還是會試一次。
  • 沒有 Pact Broker 與 schema registry：pact 檔與 baseline 放在 repo 裡。團隊多了以後，用 broker 管理「哪個版本的 consumer 部署在哪裡」，provider 才知道要驗證哪些契約。
  • 觀測：上線前要有跨 GraphQL 與 gRPC 的分散式追蹤，把 trace context 從 Yoga 傳到 gRPC 的 metadata（DevOps 課第 23 課），一個慢請求才查得到慢在哪一段。

練習

五題都在同一個專案裡，測試每次建立新的資料庫與伺服器。練習 4 需要練習 2 完成（provider 用正式模式驗證，要有白名單），也會用到練習 1、3 的程式。

練習 1：GraphQL 菜單與訂單歷史。在 loaders.ts 寫三個 DataLoader（customerById、productById、itemsByOrderId，每個 batch 函式一句 SQL）；把 orders.ts 的 OFFSET 分頁改成 keyset（用 cursor.ts）；改 resolvers.ts：關聯欄位走 ctx.loaders，order、Customer.orders、Product.orders 都經過 auth.ts，email、internalNote 只給店員。測試確認：菜單 6 筆含庫存、價格來自資料庫；一位顧客的訂單逐頁走完不重複不遺漏（翻頁途中會插入新訂單）；最深的訂單歷史查詢最多 6 句 SQL；顧客從任何路徑都看不到別人的訂單、email 與備註，Product.orders(first: k) 拿得到自己的前 k 張（條件寫在 SQL，不是查完再濾）；資料改了，下一個請求看得到（loader 不跨請求）。

練習 2：防護。在 protect.ts 回傳 { plugins, maskedErrors }：深度上限 6、成本上限 1000（useCostLimit）、persisted operations（只有 dev 為 true 時允許任意查詢）、CSRF 防護、錯誤遮罩並把原錯誤交給 logger.error。測試確認：App 的 OrderHistory（深度 6）可以執行、深度 7 在執行前被擋（一句 SQL 都沒有）；成本剛好 1000 可以執行、1001 被擋；正式模式送查詢文字或未知雜湊被拒、送 codegen 白名單裡的雜湊成功；沒帶 CSRF 標頭的 GET 回 403；資料庫錯誤對外只顯示 Unexpected error. 並被記錄，UNAUTHENTICATED 這類刻意的錯誤保留代碼。

練習 3：庫存 gRPC 與下單。inventory/server.ts 的 Reserve 加上冪等（同一個 key 回第一次的回應、不再扣）；inventory.ts 的 stockFor、reserveFor 用剩餘預算當 deadline、預算不夠不呼叫、失敗時降級並記錄；place-order.ts 改成「重送檢查 → Reserve → 交易裡建立訂單」，Reserve 失敗回 OutOfStock 或 InventoryUnavailable；schema.graphql 加上 InventoryFailure 與 InventoryUnavailable。測試確認：直接對庫存服務重送同一個 key 只扣一次；30 張訂單搶最後幾杯拿鐵恰好成功那幾張、不超賣；同一個 clientOrderId（依序或同時）只建立一張訂單；兩位顧客剛好用了同一個 clientOrderId 時各扣各的庫存；品項寫入失敗時訂單跟著回滾；庫存服務不回應時在預算內回 TIMEOUT、grpc-timeout 等於預算減 20 ms、不留訂單；預算不夠時不呼叫；庫存服務掛掉時菜單照常、下單回 DOWN。

練習 4：契約檢查。完成 run.ts（四個步驟，名稱照檔案開頭的說明；成功印 ✓ 名稱、失敗印 ✗ 名稱、停止後面的步驟並以非 0 結束）、consumer.ts（App 的 OrderHistory 互動，回應用 matcher）、provider.ts（對著真的 GraphQL 伺服器驗證，正式模式）。自己在 work/12 執行 node contracts/run.ts 看輸出。測試先確認目前的程式四步都通過、pact 檔存在且用了 matcher；再複製一份專案，分別注入三種破壞：移除 Order.total、proto 改欄位編號、把 total 改名並連 baseline 一起改，確認各自在對的步驟失敗、結束碼非 0。

練習 5：照範本寫 adr.md：選 GraphQL 給 App、gRPC 給庫存、REST 加 webhook 給合作夥伴的決定，考慮過的替代方案（至少兩個，列點）、取捨、後果與演進方式。測試檢查五個章節都有內容、「決定」提到三種風格、「後果」寫到代價（例如出現代價、成本、風險、維運、複雜、學習曲線其中一個詞）、全文 400 到 2000 字（不含空白與註解）。寫完用上面的清單自我檢查。

練習 6：驗收測試要求訂單歷史查詢最多 6 句 SQL，你的實作發出 25 句。最可能的原因是？

✓ 每一層關聯一句 SQL 是正常的，句數跟資料筆數成正比就代表有地方在逐筆查。印出 SQL 記錄，找只差參數、重複出現的句子。keyset 和 OFFSET 都是一句（a 錯）；成本限制與白名單在執行前判斷，不會增加 SQL（c、d 錯）。

練習 7：placeOrder 呼叫 Reserve 逾時，App 用同一個 clientOrderId 重送。正確的系統行為是？

✓ 逾時只代表呼叫端沒等到回應，庫存服務可能已經扣了。冪等 key 讓重試安全，資料庫的唯一約束是最後一道防線。a 會重複扣；c 讓使用者重下一張，可能變成兩張訂單；d 把問題丟給前端，前端一樣不知道到底扣了沒有。

練習 8：同事的契約檢查每次先用目前的 schema 產生 baseline，再拿目前的 schema 跟它比。問題是？

✓ 相容性檢查的意義是跟正在被客戶端使用的版本比。Pact 只涵蓋寫了契約的客戶端與互動，其他客戶端靠 schema 檢查（c 錯）。比對兩份一樣的 schema 不會報錯，只會回傳空陣列（d 錯），這正是問題所在。

常見錯誤

  • 先寫完全部程式才跑驗收測試：一次冒出十幾個失敗，分不出哪裡壞。照建議的順序，每完成一塊就跑。
  • 為了 SQL 句數寫一個 JOIN 所有關聯的大查詢：客戶端沒選的欄位也被查出來，查詢越長越難維護。DataLoader 只查被選到的那一層。
  • 授權只做在入口或只做在 Customer.orders：Product.orders 也拿得到訂單。每條路徑都要經過同一套規則。
  • 冪等只做在 GraphQL 層：BFF 呼叫 Reserve 逾時後重試，GraphQL 層看不到資料庫有訂單，只能靠庫存服務認得 key。重試可能來自任何一層。
  • 先建訂單再預留庫存：庫存服務掛掉時留下一張沒有庫存的訂單。先 Reserve，成功才寫資料庫。
  • deadline 寫死：timeoutMs: 1000 不管請求已經用掉多少時間，整條路徑就超過 500 ms 的預算。每次從 ctx.deadline − ctx.now() 算。
  • 降級時不記錄：菜單照常顯示，但庫存服務掛了一整天沒人知道。
  • 契約檢查失敗仍以 0 結束：CI 只看結束碼。catch 之後要設 process.exitCode。
  • provider 驗證對著 mock：mock 就是照 pact 檔寫的，永遠會通過。要開真的伺服器。
  • ADR 只寫優點：讀的人無法判斷代價能不能接受，之後條件改變時也不知道該不該重新決定。

小結

  • 非功能需求要寫成數字（SQL 句數、深度、成本、延遲預算），才能設計、才能驗收。
  • GraphQL 的 SQL 句數跟查詢的層數有關、跟資料筆數無關：關聯一律走每個請求一份的 DataLoader。
  • 授權放在每條路徑都會經過的地方；列表濾掉、單一物件報錯、個資欄位回 null。
  • 上線的 GraphQL 要有深度與成本限制、只接受白名單、遮罩非預期錯誤並記錄。
  • 跨系統的寫入，順序決定失敗時留下什麼：先預留、再寫入；冪等做在每一層，資料庫唯一約束是最後一道防線。
  • 每次呼叫下游都用剩餘預算當 deadline；非必要的下游失敗時降級並記錄。
  • 契約檢查跟線上版本比：GraphQL schema、proto、Pact 各守一條邊界，失敗要讓 CI 看得到（非 0 結束）。
  • ADR 寫下背景、決定、替代方案與代價，讓之後的人知道為什麼、何時該重新決定。

階段檢核：面試會問的觀念

這個階段與整門課一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：App 與店員後台都改查新欄位 Order.totalTwd，舊的 Order.total 已經加上 @deprecated(reason: "改用 totalTwd")。什麼時候可以把 total 從 schema 刪掉？

✓ 刪欄位是破壞性變更，還在查它的客戶端整個查詢會在驗證階段失敗。新版上架不代表舊版消失，使用者手機上的舊 App 可能好幾個月才更新，所以用使用量決定，不用日期猜。a 錯在只看到自己部署得了的程式，商店裡的舊版 App 照樣會送出查 total 的查詢。（第 10 課）

練習 10：一個 PR 改了 schema.graphql，contracts/run.ts 的 graphql-schema 步驟用 findSchemaChanges 跟 baseline 比對。下面哪一個改動應該讓這一步失敗？

✓ 輸入多一個必填欄位是 breaking：舊 App 的 PlaceOrder 沒帶 storeId，請求直接被拒。union 與 enum 多一個成員是 dangerous，CI 提醒、通知前端就好；新增輸出欄位是 safe。b 最多人選，但它不會讓舊查詢失敗，App 有選 __typename，不認識的結果一律顯示「暫時無法下單」；把它擋下，團隊只會想辦法繞過檢查。（第 10、12 課）

練習 11：官網要做自己的 BFF，App 的 BFF 就是這個專題的 GraphQL 伺服器。新規則「會員第二杯半價」該寫在哪裡？

✓ 價格是商業規則，放在擁有資料的服務，每個前端算出來才會一樣；BFF 只做組合與轉換，gateway 只做 TLS、路由、認證、限流這類橫切的事。a 最常見，兩份實作遲早算出不同的價錢。c 的金額任何人都能改掉再送出。（第 11 課）

練習 12：同事覺得「庫存一定有數字」，把 MenuItem.available 從 Int 改成 Int!，schema 檢查也放行了。之後庫存服務掛掉，available 的 resolver 丟出 INVENTORY_UNAVAILABLE，App 會收到什麼？

type Query { menuWithStock: [MenuItem!]! }
type MenuItem { product: Product!  available: Int! }

✓ 非空欄位放不進 null，只能讓父物件變 null；MenuItem 在 [MenuItem!]! 裡也不能是 null，一路傳到根，降級變成整個失敗。附加資料的欄位要宣告成可為 null。a 是 Int 才有的結果；輸出欄位變非空對舊客戶端是 safe，所以 schema 檢查擋不住這個錯。（第 3、11 課）

練習 13：placeOrder 要呼叫庫存服務的 Reserve，也要在資料庫建立訂單，兩邊沒有共用的交易。哪個寫法中途失敗時留下的問題最小？

✓ 順序決定失敗時留下什麼。先 Reserve：庫存服務掛掉時什麼都沒留下；資料庫寫入失敗時只是庫存被扣、少賣幾杯，可以用釋放預留的補償動作或預留過期補救。a 最多人選，但庫存服務掛掉時資料庫已經多一張沒有庫存的訂單，店員會照單做。（第 12 課）

練習 14：「我的訂單」要在每張訂單旁顯示總杯數，同事在 resolvers.ts 加了 Order.itemCount。哪裡會出事？

Order: {
  itemCount: async (order, _args, ctx) => {
    const { rows } = await ctx.db.query(
      'SELECT quantity FROM order_items WHERE order_id = $1', [order.id])
    return rows.reduce((sum, r) => sum + r.quantity, 0)
  },
},

✓ GraphQL 對每張訂單各呼叫一次 resolver，不會幫你合併，這就是搬到伺服器上的 N+1。改成 ctx.loaders.itemsByOrderId.load(order.id) 再加總：同一層合成一句，跟 items 一起查時還會命中快取、不多發 SQL。b 就是「GraphQL 解決了 N+1」的誤解。（第 4、12 課）

練習 15：下單的預算是 500 ms，呼叫庫存服務要保留 20 ms 給寫資料庫與回應。這次資料庫很慢，驗證與重送檢查就用掉 490 ms，接下來的 Reserve 該怎麼處理？

✓ deadline 是整條呼叫鏈的剩餘預算，算出來不夠就不呼叫：App 快要放棄了，這時才去扣庫存，只是白占庫存服務的資源。a 最多人選，但 Connect 的 timeoutMs 小於等於 0 代表不設逾時，結果跟 c 一樣，庫存服務會一直做下去。b 讓整個請求超過 500 ms，App 早就放棄了，伺服器還在扣庫存。（第 9、11、12 課）

練習 16：同事整理 inventory.proto，把 StockLevel 的 int32 available = 2; 改成 = 3。庫存服務先部署了，BFF 還是舊版、用二進位格式呼叫。菜單會怎樣？

✓ 二進位裡只有編號、沒有名稱，改編號等於刪掉舊欄位再新增一個。舊 BFF 跳過不認得的編號 3，編號 2 沒送，proto3 就給預設值 0：不報錯、不降級，看起來像全部賣完。c 錯在不認得的編號會被跳過、不會丟錯，所以這種改動只能靠 CI 的 buf breaking 在合併前擋下。（第 8、10 課）
