階段 4：gRPC 與 Protobuf · 第 8 課

Protobuf：訊息、程式碼產生與相容規則

咖啡店的訂單服務下單前要問庫存服務「拿鐵還有幾杯」。兩個服務由不同團隊維護，一邊用 Node，另一邊可能是 Go。雙方要對「請求長什麼樣、回應有哪些欄位、數字是整數還是小數」有一份共同、不會各自理解錯的約定。gRPC 用的約定叫 Protocol Buffers（簡稱 protobuf）：在 .proto 檔寫下訊息的結構，兩邊的程式碼都從它產生，傳送時編成很小的二進位格式。

這一課先不碰 gRPC 服務（下一課），只學它底下的 protobuf 這一層。

這課的路線：
  1. 一份 .proto 與第一個 message：Node 和 Go 兩個團隊怎麼共用同一份約定，欄位後面的編號是做什麼的。
  2. 型別與預設值：repeated、map、enum、oneof 各用在哪，為什麼收到 0 分不出「庫存是 0」還是「沒給」。
  3. buf：檢查 .proto 的寫法、產生 TypeScript 程式碼，改 .proto 時天天用到的工具。
  4. 線上格式：7 個位元組怎麼拆，為什麼欄位編號不能改、名稱可以改。
  5. 相容規則：哪些改動會讓還沒更新的服務讀錯資料，每次改 .proto 都要做的判斷。
這課會用到：
  • Node 課第 11 課的 Buffer：一串位元組，每個位元組 0～255，常寫成兩位十六進位（6e 就是 110）。
  • 系統設計課第 19 課的 API 相容性：新舊版本會同時在線上，加欄位通常安全，刪欄位、改語意會弄壞還沒更新的一方。

在 learn/ 執行 node check.mjs api-styles 08，會建立 api-styles/practice/work/08/（還沒安裝套件的話，先照第 2 課開頭的步驟 npm install）。裡面有：

  • buf.yaml、buf.gen.yaml：buf 的設定（不用改，下面會逐行說明）。
  • proto/coffee/demo/v1/order.proto：這一頁範例用的訂單訊息（不用改）。
  • proto/coffee/inventory/v1/inventory.proto（練習 1）、codec.ts（練習 2）、evolve/ 與 compat.md（練習 3）。
  • gen/：每次執行 check.mjs 都會先自動執行 buf generate，把 proto/ 產生成這裡的 .js 與 .d.ts。不要手改，下次就被蓋掉。
  • examples/：這一頁的範例，在 work/08 執行（要先跑過一次 check.mjs，gen/ 才存在）。

一份 .proto，兩邊產生程式碼

REST 的 JSON 沒有強制的格式說明：後端回傳 {"available": "3"}（字串）還是 {"available": 3}（數字），前端要等到執行時才知道。OpenAPI 能補上說明，但它是另外寫的規格，可能跟程式不一致。

protobuf 反過來：先寫介面定義語言（IDL，Interface Definition Language）檔，也就是 .proto，再由程式碼產生器為每個語言產生型別與編碼、解碼的程式。兩邊的型別都來自同一份檔案，不會各寫各的。第 7 課從 GraphQL schema 產生前端型別（codegen）是同一個想法。

現在常用的語法版本是 proto3，這門課都用它。protobuf 另有較新的 editions 語法（用設定取代 proto2／proto3 的差異），新專案還不多，本課不用。

第一個 .proto：package、message、欄位編號

知道 .proto 是兩邊共用的型別來源後，先看一份最小的檔案長什麼樣：庫存服務回報某個商品還剩幾份。看的時候注意三個地方：開頭的 package、message 裡的欄位，以及每個欄位後面的編號。

syntax = "proto3";

package coffee.inventory.v1;

message StockLevel {
  string product_id = 1;
  int32 available = 2;
}
  • syntax = "proto3";：第一行，宣告語法版本。
  • package coffee.inventory.v1;：命名空間，避免跟別的團隊的 StockLevel 撞名。最後一段 v1 是版本：哪天真的要做不相容的大改，就開 coffee.inventory.v2，兩版並存一段時間，舊的呼叫端慢慢搬。沒有版本的 package 之後沒地方放 v2。
  • 檔案路徑跟 package 對應：coffee.inventory.v1 放在 coffee/inventory/v1/ 底下。buf lint 會檢查這兩件事。
  • message：一種資料結構，像 TypeScript 的物件型別。欄位寫成「型別 名稱 = 編號;」，名稱用 lower_snake_case，產生的 TypeScript 會轉成 camelCase（product_id → productId）。

最重要的是 = 1、= 2：欄位編號（field number）。它不是預設值，也不是順序，而是這個欄位在線上格式（wire format，實際在網路上傳的位元組）裡的身分。二進位資料裡只有編號，沒有欄位名稱。所以：

  • 同一個 message 裡編號不能重複；編號一旦上線就不能改。
  • 編號 1 到 15 編碼只要 1 個位元組，16 到 2047 要 2 個：常用的欄位用小編號。
  • 19000 到 19999 保留給 protobuf 自己用，不能用。

型別：純量、repeated、map、enum、oneof

這一頁範例用的 proto/coffee/demo/v1/order.proto：

import "google/protobuf/timestamp.proto";

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;
  ORDER_STATUS_PENDING = 1;
  ORDER_STATUS_READY = 2;
}

message OrderItem {
  string product_id = 1;
  int32 quantity = 2;
  int32 unit_price_twd = 3;
}

message Order {
  string id = 1;
  OrderStatus status = 2;
  repeated OrderItem items = 3;              // 清單
  int32 total_twd = 4;
  optional int32 discount_twd = 5;           // 分得出「沒折扣」和「折扣 0 元」，下一節講
  map<string, string> notes = 6;             // key → value
  google.protobuf.Timestamp ordered_at = 7;  // 時間點，protobuf 內建的訊息型別
  oneof pickup {                             // 內用桌號或外帶名字，最多一個有值
    int32 table_no = 8;
    string takeaway_name = 9;
  }
  int64 loyalty_points = 10;
}
proto 型別產生的 TypeScript 型別（protobuf-es 2.16）咖啡店用在哪
stringstring商品 id、名稱
boolboolean是否上架
int32number數量、新台幣整數元
int64bigint真的會超過 21 億的數字：累積點數、以「分」計的大金額
float、doublenumber溫度、座標；不要用在金額，理由跟 TypeScript 課第 5 課一樣
bytesUint8Array圖片縮圖、雜湊值
repeated TT[]訂單品項
map<K, V>{ [key: K]: V }以商品 id 查庫存
enumTypeScript enum（值是數字）訂單狀態、商品分類
message產生的訊息型別，沒設定時是 undefined品項、時間
  • int64 在 JS 是 bigint：number 只能精確表示到 253 − 1（TypeScript 課第 5 課），所以 protobuf-es 用 bigint。bigint 不能直接 JSON.stringify、不能跟 number 相加。數量、價格用 int32 就好（上限約 21 億）；用不用 int64、金額用「元」還是「分」，整個團隊要一致。
  • enum 的第一個值一定是 0，而且慣例命名為 XXX_UNSPECIFIED：下一節會看到，沒設定的 enum 欄位讀出來就是 0，0 要代表「沒設定」，不能代表真的分類。每個值加上 enum 名稱當前綴（ORDER_STATUS_PENDING），因為 proto 的 enum 值跟 enum 本身在同一個命名空間，兩個 enum 都有 PENDING 會撞名。產生的 TypeScript 會把前綴拿掉：OrderStatus.PENDING。
  • oneof：幾個欄位中最多只有一個有值，設了 table_no 就自動清掉 takeaway_name。產生的程式碼是可辨識聯合：{ case: 'tableNo', value: 5 }，跟 TypeScript 課第 16 課的型別縮小一樣用 case 判斷。
  • 巢狀訊息：欄位型別可以是另一個 message（OrderItem），也可以把 message 宣告在另一個 message 裡面。google.protobuf.Timestamp 這類常用型別叫 well-known types，import 進來就能用。

預設值不會被送出：0 和「沒給」分不出來

proto3 為了省空間，值等於預設值的欄位不寫進位元組：數字是 0、字串是空字串、bool 是 false、enum 是 0。接收端沒讀到欄位，就填預設值。執行 node examples/wire.ts：

拿鐵 3 杯：      0a 01 32 10 03 18 6e
單價 300：       0a 01 32 10 03 18 ac 02
數量 0：         0a 01 32 18 6e
什麼都沒給：     （0 個位元組）
沒有折扣：       0a 01 37  discountTwd = undefined  isFieldSet = false
折扣 0 元：      0a 01 37 28 00  discountTwd = 0  isFieldSet = true

「數量 0」那一行少了 10 03（數量欄位）。接收端讀到的 quantity 是 0，但它沒辦法知道對方是「明確說 0」還是「根本沒填這個欄位」（例如對方還是不認得這個欄位的舊版本）。

多數欄位這樣沒問題：沒給的數量當成 0 合理。但有些欄位的 0 有意義：庫存的「補貨點」（庫存低於多少要叫貨）設成 0 代表「賣完才補」，沒設定代表「這個商品不自動補貨」。把兩者當成一樣，就會在不該叫貨時叫貨。這種欄位加上 optional：

  • optional int32 discount_twd = 5; 讓欄位有存在性（presence）：只要設了值，就算是 0 也會送出（上面的 28 00）。
  • 產生的 TypeScript 型別是 discountTwd?: number，沒設定時是 undefined；也可以用 isFieldSet(msg, OrderSchema.field.discountTwd) 檢查。
  • 另一個做法是包裝型別（google.protobuf.Int32Value），它是一個 message，沒設定時就是 undefined。proto3 加入 optional 之後，新寫的 schema 用 optional 比較直接。
  • message 型別的欄位本來就有存在性，不用加 optional；repeated 與 map 不能加。
「讀到 0」不等於「對方說 0」。設計每個數字、bool、enum 欄位時都問一次：0／false 跟「沒給」意思一樣嗎？不一樣就加 optional。上線之後再補 optional，舊程式送來的資料仍然分不出來。
💡 實務上：「只改有給的欄位」的更新 API 最常踩到預設值
後台要做「修改商品」：店長只改價格，其他欄位不動。如果請求是整個 Product 訊息，伺服器分不出 name 是空字串是「改成空的」還是「沒給」，照單全收就把商品名稱清空了。常見做法是請求多帶一個 google.protobuf.FieldMask update_mask，列出這次要改的欄位路徑（例如 ["price_twd"]），伺服器只更新清單裡的欄位；Google 的 API 設計指南（AIP-134）就是這樣規定。欄位不多時，把可以部分更新的欄位都標成 optional 也行。設計更新 API 時先跟前端講好用哪一種。

buf：lint 與產生程式碼

buf 是 protobuf 的工具鏈：buf lint 檢查寫法、buf generate 產生程式碼、buf breaking 檢查相容性。它以 npm 套件 @bufbuild/buf（這門課鎖 1.75.0）安裝，套件裡帶著你電腦平台的執行檔，不用另外裝 Google 的 protoc 編譯器。work/08/buf.yaml：

version: v2
modules:
  - path: proto        # .proto 的根目錄：import 與 package 路徑從這裡算
lint:
  use:
    - STANDARD         # buf 建議的整套規則

在 work/08 執行 npx buf lint，起始的 inventory.proto 會出現這類訊息，格式是「檔名:行:欄:說明」：

proto/coffee/inventory/v1/inventory.proto:4:1:Package name "coffee.inventory" should be suffixed with a correctly formed version, such as "coffee.inventory.v1".
proto/coffee/inventory/v1/inventory.proto:7:3:Enum zero value name "COFFEE" should be suffixed with "_UNSPECIFIED".
proto/coffee/inventory/v1/inventory.proto:8:3:Enum value name "TEA" should be prefixed with "CATEGORY_".

這些就是前面講的慣例（package 要有版本、路徑要對應、enum 的 0 是 _UNSPECIFIED、enum 值加前綴、欄位用 lower_snake_case）。lint 讓整個公司的 .proto 長得一樣，也擋下之後才會痛的設計（沒有版本的 package）。

產生程式碼的設定 buf.gen.yaml：

version: v2
clean: true                   # 產生前先清掉 gen/，刪掉的 .proto 不會留下舊檔
plugins:
  - local: protoc-gen-es      # 用 node_modules 裡的 @bufbuild/protoc-gen-es（2.16.0）
    out: gen
    opt:
      - target=js+dts         # 產生 .js 與 .d.ts
      - import_extension=js   # 產生的 import 寫 './x_pb.js'，Node 才找得到

為什麼不用預設的 target=ts？它產生 .ts 檔，裡面的 proto enum 會變成 TypeScript 的 enum。這門課直接用 Node 執行 .ts（type stripping），只能執行可以直接抹掉的型別語法，enum 會產生執行時的程式，跑不動。js+dts 把執行的程式放在 .js、型別放在 .d.ts（TypeScript 課第 25 課），執行與型別檢查都沒問題。@bufbuild/protobuf（執行時套件）與 @bufbuild/protoc-gen-es（產生器）的版本要相同。

npx buf generate 之後，proto/coffee/demo/v1/order.proto 變成 gen/coffee/demo/v1/order_pb.js 與 order_pb.d.ts。每個 message 產生兩樣東西：型別 Order，和描述它的 OrderSchema（欄位、編號、型別的完整資訊）。所有操作都是「函式 + Schema」：

// examples/encode.ts（節錄）
import { create, fromBinary, toBinary, toJson } from '@bufbuild/protobuf'
import { OrderSchema, OrderStatus } from '../gen/coffee/demo/v1/order_pb.js'

const order = create(OrderSchema, {          // 沒給的欄位填預設值
  id: '42',
  status: OrderStatus.PENDING,
  items: [{ productId: '2', quantity: 2, unitPriceTwd: 110 }, …],
  pickup: { case: 'tableNo', value: 5 },
  loyaltyPoints: 1200n,
})
const bytes = toBinary(OrderSchema, order)   // Uint8Array
const back = fromBinary(OrderSchema, bytes)  // 解回訊息；位元組壞掉會丟錯
toJson(OrderSchema, back)                    // protobuf 規定的 JSON 格式

執行 node examples/encode.ts：

protobuf： 52 位元組
JSON：     259 位元組
解回來的 status： 1 = PENDING
解回來的 pickup： { case: 'tableNo', value: 5 }
loyaltyPoints 的型別： bigint
toJson： {
  id: '42',
  status: 'ORDER_STATUS_PENDING',
  items: [ … ],
  totalTwd: 290,
  notes: { cup: 'own' },
  orderedAt: '2026-10-01T08:30:00Z',
  tableNo: 5,
  loyaltyPoints: '1200'
}
直接 JSON.stringify 訊息： Do not know how to serialize a BigInt
  • 同樣的資料，二進位是 52 位元組，JSON 是 259：沒有欄位名稱、數字用可變長度編碼。
  • toJson 的格式有規定（proto3 JSON mapping）：欄位名稱轉成 lowerCamelCase、enum 用名稱字串、int64 用字串、Timestamp 用 RFC 3339 字串、值等於預設值的欄位省略。要給瀏覽器或記錄 log 時用它，不要自己 JSON.stringify 訊息（bigint 會丟錯，enum 只會是數字）。
  • 反過來，toJson 的結果不適合在程式裡繼續用：available: 0 被省略了、int64 變成字串。程式之間傳資料用訊息物件本身。
💡 實務上：.proto 放在哪裡、產生的程式碼要不要進 git
兩個團隊要共用同一份 .proto，不能各自複製一份再各改各的。常見做法是把所有 .proto 放在一個共用的 repo（或 monorepo 裡的一個資料夾），CI 跑 buf lint 與 buf breaking，各服務從那裡產生程式碼。gen/ 進不進 git 是團隊要定的事：不進 git，每次 build 都要先 buf generate，產生器版本要鎖死；進 git，code review 看得到產生的程式碼改了什麼，但要有人記得重產（CI 可以重產一次，跟 commit 的比對，不同就失敗）。不論哪種，@bufbuild/protobuf 與 @bufbuild/protoc-gen-es 要一起升級。

線上格式：為什麼編號不能改、名稱可以改

拆開 OrderItem { product_id: "2", quantity: 3, unit_price_twd: 110 } 的 7 個位元組 0a 01 32 10 03 18 6e。每個欄位都是「tag + 值」，tag = 欄位編號 << 3 | wire type，wire type 告訴解碼器值有多長：

wire type值的格式用在
0（VARINT）varintint32、int64、bool、enum
1（I64）固定 8 位元組double、fixed64
2（LEN）varint 長度 + 那麼多位元組string、bytes、message、repeated 的數字（packed）
5（I32）固定 4 位元組float、fixed32

varint 是可變長度的整數編碼：每個位元組用低 7 位元放數字，最高位元是 1 代表「後面還有」。110 小於 128，一個位元組 6e；300 要兩個：300 的二進位是 10 0101100，先放低 7 位元 0101100 並把最高位元設 1 得到 ac，再放剩下的 10 得到 02，所以是 ac 02（上面「單價 300」那一行）。小的數字只佔一個位元組，這是 protobuf 小的主要原因。

解碼器讀到 tag，用編號找欄位。找不到（舊程式不認得新欄位）就依 wire type 跳過那段位元組，protobuf-es 會把它留在訊息的 $unknown，重新編碼時原樣送出。從這裡可以推出相容規則的核心：

  • 名稱不在線上：二進位格式下改欄位名稱，舊程式照樣讀得到。
  • 編號就是身分：改編號等於刪掉舊欄位、新增一個欄位；把舊編號拿給別的欄位用，舊程式送來的資料會被當成新欄位的值。
  • wire type 要一樣：int32 改成 string，wire type 從 0 變成 2，舊程式解不開或讀錯。

相容規則：哪些改動會弄壞還沒更新的服務

庫存服務改了 .proto 重新部署，訂單服務可能下週才更新，行動 App 的舊版本會在使用者手機上活好幾個月。所以每個改動都要問兩件事：新程式讀得懂舊資料嗎？舊程式讀得懂新資料嗎？還要分清楚對方用哪種格式：只用二進位，還是也有人用 JSON（例如瀏覽器透過 gateway 呼叫，第 11 課），或是共用產生的程式碼。

改動二進位JSON／產生的程式碼正確做法
新增欄位（新編號）安全：舊程式跳過安全直接加；舊程式送來的資料沒有這個欄位，新程式要能處理預設值
刪除欄位當下安全當下安全一定要 reserved 編號與名稱，否則之後有人重用編號，舊資料會被解讀成新欄位
改名（編號不變）安全壞：JSON 用名稱，產生的程式碼屬性名稱也變了新增新名稱的欄位（新編號），舊欄位加 [deprecated = true]，過渡期兩個都填
改型別多數壞（wire type 不同就一定壞）壞新增新欄位
改編號壞壞不要做
enum 新增值安全，但舊程式會讀到不認得的數字安全（buf 各類別都放行），但舊程式解析 JSON 時預設不接受不認得的名稱：protobuf-es 的 fromJson 會丟錯，要加 { ignoreUnknownFields: true }程式要處理不認得的值（例如當成 UNSPECIFIED）；讀 JSON 的一方先加上 ignoreUnknownFields
加上 optional安全：位元組一樣JSON 安全；產生的程式碼型別從 number 變成 number | undefined（buf 的 WIRE、WIRE_JSON 放行，FILE、PACKAGE 擋）可以加，但舊程式不送 0，所以舊資料的 0 仍然分不出來
加上或拿掉 repeated、移進 oneof多數壞壞新增新欄位

刪除欄位的寫法：

message Product {
  reserved 4;              // 編號，也可以寫範圍：reserved 4, 9 to 11;
  reserved "price_twd";    // 名稱：JSON 用名稱，名稱也要保留
  string id = 1;
  string name = 2;
  Category category = 3;
}

之後有人寫 string note = 4;，編譯就失敗。不要把後面的欄位編號往前移來「補洞」，那等於改了每個欄位的編號。

「改名」的正確做法是一段過渡期：加 int32 on_hand = 3;，舊的 available 加 [deprecated = true]（產生的程式碼會標成 @deprecated，編輯器畫刪除線），伺服器兩個欄位都填同樣的值，讀的人慢慢改用 on_hand；確認沒有人讀 available 之後，再刪除並 reserved。第 10 課會講怎麼「確認沒有人用」。

人工檢查一定會漏，所以交給 buf breaking：拿新的 .proto 跟上一版（例如 main 分支）比對。它有四個類別，從嚴到鬆：

類別擋下什麼適合
FILE（buf 1.75 的預設）跟 PACKAGE 一樣，再加上檔案層級的改動（把型別搬到別的檔案）產生的程式碼被很多專案 import，而且有語言以檔案為單位產生程式碼
PACKAGE產生的程式碼要相容：刪除任何欄位、message、enum 值都擋（就算 reserved 了，程式碼裡的屬性還是不見），型別要完全相同產生的程式碼被別的團隊直接使用
WIRE_JSON二進位與 JSON 不相容的改動：改名擋；刪欄位只要 reserved 編號與名稱就放行有人用 JSON 呼叫（gateway、Connect 的 JSON）
WIRE只擋二進位不相容的改動：改名放行；刪欄位要 reserved 編號確定只用二進位、而且不共用產生的程式碼

練習 3 的 evolve/new/buf.yaml 設定 breaking: use: [WIRE_JSON]。在 work/08 執行 npx buf breaking evolve/new --against evolve/old，直接把 available 改名成 on_hand、刪掉 price_twd 會得到：

evolve/new/inventory.proto:6:1:Previously present field "3" with name "price_twd" on message "Product" was deleted without reserving the name "price_twd".
evolve/new/inventory.proto:6:1:Previously present field "3" with name "price_twd" on message "Product" was deleted without reserving the number "3".
evolve/new/inventory.proto:13:3:Field "2" with name "on_hand" on message "StockLevel" changed option "json_name" from "available" to "onHand".
evolve/new/inventory.proto:13:9:Field "2" on message "StockLevel" changed name from "available" to "on_hand".

改成 WIRE 時，改名的兩行就不會出現，刪除沒 reserved 的仍然會。反過來，用預設的 FILE 時，就算 reserved 了，刪除欄位還是會被擋（was deleted）：用 FILE／PACKAGE 的團隊通常只把欄位標成 deprecated、不刪，等開 v2 package 時才拿掉。不確定選哪個時用嚴的：放寬一個規則很容易，事故發生後才收緊就晚了。第 10 課把 buf breaking 放進 CI，每個 PR 自動跟 main 比對。

資深視角：相容性檢查只看結構，看不到語意。把 price_twd 從「含稅」改成「未稅」，編號、型別都沒變，buf 不會報錯，但每個呼叫端都算錯錢。改語意就新增一個名稱說清楚的新欄位（price_twd_excl_tax），跟改名走一樣的過渡流程。
💡 實務上：審 .proto 的 PR 時先問這幾件事
改到 .proto 的 PR 影響的不只這個服務。審查時逐一問：有沒有改到既有欄位的編號或型別？刪掉的欄位有沒有 reserved 編號與名稱？新欄位的 0／空字串是不是一個合理的「沒給」？新的 enum 值，舊的呼叫端讀到會怎樣？語意有沒有變（例如金額從元改成分）？還要想部署順序：新欄位要「讀的一方」先能處理再讓「寫的一方」開始填，不然先送出去的資料沒人看；反過來要停用欄位，先讓所有讀的人不再依賴它，最後才停止填值。

練習

練習 1：改寫 inventory.proto，讓它通過 npx buf lint（STANDARD），並符合：package 是 coffee.inventory.v1；enum Category 依序是 CATEGORY_UNSPECIFIED = 0、CATEGORY_COFFEE = 1、CATEGORY_TEA = 2、CATEGORY_FOOD = 3；Product 有 id（string，1）、name（string，2）、category（Category，3）、price_twd（新台幣整數元，4）；StockLevel 有 product_id（string，1）、available（int32，2）、reorder_point（int32，3，要分得出「沒設定」和 0）；GetStockRequest 的 product_ids（1）一次可以放好幾個商品 id；GetStockResponse 的 levels（1）以商品 id 為 key、值是 StockLevel。括號裡的數字是欄位編號。測試先跑 buf lint，再讀產生的程式碼裡的描述，逐一檢查每個欄位的編號、型別與存在性。

練習 2：在 codec.ts 用練習 1 產生的 StockLevelSchema、GetStockResponseSchema（從 ./gen/coffee/inventory/v1/inventory_pb.js import；練習 1 沒完成時這兩個不存在）寫三個函式。encodeStock(levels)：把陣列編成一個 GetStockResponse 的位元組，levels 的 key 是每筆的 productId。decodeStock(bytes)：解回 { productId, available, reorderPoint? } 陣列（順序不限），沒設定補貨點的那筆不能出現 reorderPoint: 0，位元組壞掉要丟錯。toWireHex(level)：把一筆 StockLevel 編成位元組，回傳小寫十六進位字串。測試每次換資料，並用手算的 tag 與 varint 逐位元組比對 toWireHex。

練習 3：evolve/old/inventory.proto 是已經上線的版本（不要改），把 evolve/new/inventory.proto 改成下一版：刪除 Product.price_twd；StockLevel 新增 warehouse_id（string）；把 available「改名」為 on_hand（int32）。只能用相容的方式完成，要通過 buf breaking（WIRE_JSON），而且舊版程式解新版的位元組時，available 的值要正確。另外在 compat.md 每一行填上：如果「直接」做那個改動（不用 reserved、不用新欄位），它屬於 safe、needs-reserved（線上安全，但刪除要 reserved）、wire-only-safe（二進位安全，JSON 與產生的程式碼會壞）、breaking 哪一類。

練習 4：把 int32 available = 2; 改名成 int32 on_hand = 2;，用二進位格式通訊、還沒更新的舊 client 會怎樣？

✓ 二進位只有編號 2，沒有名稱，所以舊 client 照樣讀到（a、c、d 錯）。JSON 用欄位名稱識別，available 變成 onHand，舊的 JSON 呼叫端讀不到；重新產生的程式碼屬性名稱也變了，用到 available 的程式編譯失敗。所以 buf 的 WIRE 類別放行、WIRE_JSON 擋下。

練習 5：庫存服務回傳的 StockLevel 裡，int32 available（沒有 optional）讀出來是 0。訂單服務能確定「庫存是 0」嗎？

✓ proto3 沒有存在性的純量欄位，等於預設值時不寫進位元組，接收端補預設值，所以 0 和「沒填」在線上一模一樣（a 錯）。protobuf 沒有 null，也不會因為少欄位丟錯（c、d 錯）。如果 0 和「沒填」意思不同，欄位要加 optional。

練習 6：Product 的 int32 price_twd = 4; 不再需要，同事刪掉它之後，下一步最該做什麼？

✓ 刪除當下是相容的，但半年後有人新增 string note = 4;，舊 client 送來的價格（varint）就會被當成 note 解讀，這種錯誤很難發現。reserved 讓編譯器擋下重用（a 錯）。移動編號等於改每個欄位的身分，最嚴重（b 錯）。刪一個欄位不需要開新的 package 版本（d 錯）。

常見錯誤

  • 改欄位編號或重新排列編號：線上格式只認編號，舊程式會把資料放進錯的欄位。編號上線後就固定。
  • 刪除欄位沒有 reserved：之後有人重用編號，舊資料被解讀成新欄位。刪除時一起 reserved 編號與名稱。
  • 0 有意義卻沒有 optional：補貨點 0、折扣 0、評分 0 都跟「沒給」分不出來。設計時就加 optional。
  • enum 的 0 拿來代表真的值：沒設定的欄位讀出來也是那個值。第一個值固定是 XXX_UNSPECIFIED = 0。
  • 金額用 float／double：有誤差。用整數（int32 的元，或 int64 的分），全公司統一。
  • 數量用 int64：在 JS 變成 bigint，JSON.stringify 丟錯、不能跟 number 運算。用不到 21 億就用 int32。
  • package 沒有版本：哪天必須做不相容的修改時，沒有 v2 可以並存。從第一天就寫 .v1。
  • 直接改名：二進位沒事，JSON 與產生的程式碼壞掉。新增欄位、舊欄位 deprecated、過渡期兩個都填。
  • 自己 JSON.stringify 訊息或用 toJson 的結果做計算：bigint 丟錯、預設值被省略。程式之間用訊息物件，要 JSON 時用 toJson。
  • 用 target=ts 產生程式碼再用 Node 直接執行：產生的 enum 不是可抹除的語法。用 target=js+dts。
  • 手改 gen/ 裡的檔案：下次產生就被蓋掉。改 .proto，再產生一次。

小結

  • .proto 是服務之間唯一的契約，各語言的型別與編解碼程式都從它產生。
  • package 帶版本（coffee.inventory.v1），檔案路徑跟 package 對應；欄位名稱 lower_snake_case，產生的 TypeScript 是 camelCase。
  • 欄位編號是線上格式的身分，名稱不在線上；tag = 編號 << 3 | wire type，數字用 varint。
  • proto3 不送預設值，0 和「沒給」分不出來；0 有意義的欄位加 optional。enum 的 0 是 _UNSPECIFIED。
  • int64 在 JS 是 bigint；金額用整數，不用 float。
  • buf：buf lint 統一寫法、buf generate 用 protoc-gen-es 產生 .js + .d.ts、buf breaking 比對上一版。
  • protobuf-es 的操作都是「函式 + Schema」：create、toBinary、fromBinary、toJson、isFieldSet。
  • 加欄位安全；刪欄位要 reserved；改名在二進位安全但 JSON 與程式碼會壞，用新欄位 + deprecated 過渡；改型別、改編號不安全。
