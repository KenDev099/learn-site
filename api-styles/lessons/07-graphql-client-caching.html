階段 3：GraphQL 上線：防護與客戶端 · 第 7 課

從 Vue 使用 GraphQL：codegen、客戶端快取與 HTTP 快取的難題

前面六課都站在伺服器這一邊。這一課換到你熟悉的那一邊：Vue 的「我的訂單」頁面要呼叫 GraphQL。用 fetch 就能呼叫，但很快會遇到三個問題：回應沒有型別，schema 改了前端照樣編譯通過；同一份資料每次切頁都重新查；顧客剛下單，訂單列表卻沒有出現新訂單。

這課的路線：
  1. 最小的客戶端：fetch 十行就能呼叫 GraphQL，少了型別、快取、錯誤處理三樣東西，各由哪一節補上（開場問題的最小答案）。
  2. codegen：從 schema 和查詢產生 TypeScript 型別，後端改了欄位名稱，前端編譯時就失敗。
  3. urql 與 document cache：切頁要不要重查由誰決定，下單之後列表為什麼沒更新、怎麼修。
  4. 正規化快取：同一張訂單只存一份，改一處所有畫面一起更新，代價是什麼。
  5. HTTP 快取與即時更新：菜單怎麼讓 CDN 快取，伺服器端的回應快取怎麼才不會把王小明的資料給陳美華，什麼時候用 subscription。
這課會用到：
  • Vue 課第 17 課的非同步資料：自己管理載入狀態、處理競態（舊的回應晚到不能蓋掉新的）、把查過的結果快取起來。
  • Node 課第 15 課的 HTTP 快取：Cache-Control 決定瀏覽器和 CDN 能不能存、存多久，public 誰都能存，private 只有使用者的瀏覽器能存。
  • 第 5 課的 connection：分頁欄位回傳 edges（每筆資料與它的游標）和 pageInfo（還有沒有下一頁、最後一筆的游標）。

在 learn/ 執行 node check.mjs api-styles 07，會建立 api-styles/practice/work/07/（還沒安裝套件的話，先照第 2 課開頭的步驟 npm install）。裡面有：

  • schema.graphql、server.ts：咖啡店的 GraphQL 伺服器，資料放在記憶體（不用改）。Customer.orders 是第 5 課的 connection 形狀。
  • src/：前端的程式。src/*.graphql 是前端要送的操作，client.ts、normalized.ts 是練習 2、3 要寫的檔案。
  • codegen.ts（練習 1）、cache.ts（練習 4，伺服器端）。
  • examples/：這一頁的範例，在 work/07 執行。除了 fetch-client.ts，其他範例要先做完練習 1。

最小的客戶端：fetch 就能用

GraphQL 在 HTTP 上只是一個 POST：body 是 { query, variables } 的 JSON，回應是 { data, errors }。所以不用任何套件，十行就能寫一個客戶端。執行 node examples/fetch-client.ts：

// examples/fetch-client.ts（節錄）
async function gql(query: string, variables?: Record<string, unknown>) {
  const res = await fetch('http://localhost:4000/graphql', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ query, variables }),
  })
  return res.json()   // 型別是 any
}
{"data":{"menu":[{"name":"美式咖啡","price":80},…]}}
{"errors":[{"message":"Cannot query field \"nmae\" on type \"Product\". Did you mean \"name\"?",…}]}

能用，但少了三樣東西：

  • 型別：res.json() 是 any。nmae 拼錯要等到執行才知道；後端把 price 改名，前端照樣編譯通過，上線才壞。
  • 快取：每次進「我的訂單」都重新查。自己寫快取就要回答「鍵是什麼」「什麼時候過期」「下單後要清掉哪些」。
  • 錯誤處理：GraphQL 的錯誤在 200 回應的 errors 裡，res.ok 是 true 也可能有錯；網路錯誤又是另一種。Vue 課第 16 課的 API 層包法照用：把兩種錯誤都轉成同一個回傳格式。

接下來三節依序解決這三件事。開場的「下單後列表沒出現新訂單」也是快取的問題：客戶端快取還存著下單前的結果，不知道它已經過期；要讓快取知道這份查詢跟訂單有關，下單後才會重查。細節在後面的〈document cache：下單之後，列表為什麼沒更新〉。

codegen：從 schema 和查詢產生型別

codegen（code generation，程式碼產生）是讀 schema 和你寫的查詢，自動產生 TypeScript 型別的工具。schema 已經說清楚每個欄位的型別，查詢說清楚選了哪些欄位，兩者合起來就能算出回應的確切形狀，不需要手寫。GraphQL 生態系最常用的是 GraphQL Code Generator（@graphql-codegen/cli 7.4.6），搭配 client preset（@graphql-codegen/client-preset 6.2.3）：preset 是一組預先搭配好的外掛，專門產生前端要用的東西。

設定寫在 codegen.ts：

import type { CodegenConfig } from '@graphql-codegen/cli'

const config: CodegenConfig = {
  schema: 'schema.graphql',             // 也可以是伺服器網址，codegen 會用內省查 schema
  documents: ['src/**/*.graphql'],      // 前端的操作放在哪裡
  generates: {
    'src/gql/': {                       // 輸出資料夾
      preset: 'client',
      presetConfig: { persistedDocuments: true },
      config: { … },                    // 見下方表格
    },
  },
}
export default config

操作寫在 .graphql 檔，例如 src/placeOrder.graphql：

mutation PlaceOrder($input: PlaceOrderInput!) {
  placeOrder(input: $input) { id orderedAt total status }
}

執行 npx graphql-codegen --config codegen.ts（node check.mjs 每次跑測試前也會自動執行），src/gql/graphql.ts 會出現：

export type OrderStatus = 'PREPARING' | 'READY' | 'PICKED_UP'
export type PlaceOrderMutationVariables = Exact<{ input: PlaceOrderInput }>
export type PlaceOrderMutation = { placeOrder: { id: string, orderedAt: string, total: number, status: OrderStatus } }
export const PlaceOrderDocument = {"kind":"Document", …} as unknown as DocumentNode<PlaceOrderMutation, PlaceOrderMutationVariables>

PlaceOrderDocument 是一個 TypedDocumentNode：執行時它是解析好的查詢（AST，抽象語法樹：把查詢文字拆成樹狀物件，客戶端不用每次重新解析），型別上它還帶著「結果是什麼」「變數是什麼」兩個型別參數。urql、Apollo 這些客戶端看到它，就會自動推導出 data 與 variables 的型別，你不用再寫任何泛型：

const result = await client.mutation(PlaceOrderDocument, { input }).toPromise()
result.data?.placeOrder.total      // number
client.mutation(PlaceOrderDocument, { input: { customerId: '1' } })   // ✗ 編譯錯誤：少了 lines

改了 schema（例如把 total 改名）再跑一次 codegen，所有用到舊欄位的 .graphql 會讓 codegen 直接失敗，用到舊型別的 .ts 會讓型別檢查失敗。這就是 codegen 的價值：前後端對不上的問題在建置時抓到，不是上線後。第 10 課會把這個檢查放進 CI。

這門課的練習在 Node 直接執行 .ts（type stripping），所以 config 要多設兩個選項（實測 7.4.6／6.2.3）：

選項預設會產生為什麼要改
importExtension: '.ts'import * as types from './graphql'Node 執行 .ts 時，相對 import 一定要寫副檔名
useTypeImports: trueimport { TypedDocumentNode } from '@graphql-typed-document-node/core'那個套件只有型別、沒有 JavaScript。寫成 import type，執行時整行消失；不改的話 Node 會去載入它而失敗

schema 的 enum OrderStatus 在 client preset 6.2.3 預設就產生成字串聯集 'PREPARING' | 'READY' | 'PICKED_UP'，不是 TypeScript 的 enum（type stripping 不支援 enum），所以不用另外設定。用 Vite 建置的 Vue 專案由 Vite 處理副檔名，上面兩項不是必要。

產生的變數型別裡，ID! 的輸入是 string | number：GraphQL 規格允許 ID 的輸入是字串或整數，輸出一律是字串。所以從 URL 拿到的 '42' 和程式裡的數字都能傳。

presetConfig: { persistedDocuments: true } 另外輸出 persisted-documents.json：{ "sha256:6f61…": "query OrderHistory(…) { … }" }。這就是第 6 課 persisted operations 需要的白名單，建置前端時產生、部署時交給伺服器。每個產生的 Document 也帶著 __meta__.hash，客戶端可以只送雜湊。

client preset 還會產生 graphql() 函式，讓你把查詢直接寫在 .ts 或 .vue 裡：const Q = graphql(`query OrderHistory … `)，codegen 掃描這些呼叫並產生對應的型別（這時 documents 要指向 src/**/*.{ts,vue}）。兩種寫法都常見；這一課用 .graphql 檔，Node 直接 import 產生的 XxxDocument。

💡 實務上：前端拿到的 schema 要跟後端部署的是同一份
codegen 的型別只跟它讀到的 schema 一樣準。常見做法是後端把 schema.graphql 放進 git（或發布到 schema registry，第 10 課），前端的 codegen 讀這份，不要讀某位同事電腦上的開發伺服器。產生的 src/gql/ 進不進 git 各團隊不同；進 git 的話，CI 要重跑 codegen 並確認沒有差異，免得有人改了 .graphql 卻忘了重產。後端要改名或刪欄位時，前端 CI 的 codegen 失敗就是提醒：先在 schema 標 @deprecated、等前端換掉再刪（第 10 課）。

urql：client、exchange 與 requestPolicy

urql 是一個 GraphQL 客戶端。@urql/core（6.0.3）是跟框架無關的核心；@urql/vue（2.1.1）在它上面提供 Vue 的 composable（Vue 課第 12 課）。所以這一課的練習直接測 @urql/core（不需要瀏覽器），學到的設定在 Vue 裡完全一樣。

import { cacheExchange, createClient, fetchExchange } from '@urql/core'

const client = createClient({
  url: 'https://api.brew.example.tw/graphql',
  exchanges: [cacheExchange, fetchExchange],
  requestPolicy: 'cache-first',     // 預設值
  fetchOptions: () => ({ headers: { authorization: `Bearer ${token()}` } }),
})

exchange 是 urql 處理每個操作的一段段管線，依陣列順序執行：cacheExchange 先看快取有沒有，沒有才交給 fetchExchange 送 HTTP 請求，回應再往回經過 cacheExchange 存起來。換快取、加重試、加認證，都是換或加 exchange。

在 Vue 裡，整個 App 只建立一個 client，用 app.use(urql, client) 提供給所有元件（底層就是 provide／inject），元件裡用 useQuery：

<script setup lang="ts">
import { useQuery } from '@urql/vue'
import { OrderHistoryDocument } from '@/gql/graphql'

const props = defineProps<{ customerId: string }>()
const { data, fetching, error } = useQuery({
  query: OrderHistoryDocument,
  variables: () => ({ customerId: props.customerId, first: 10 }),   // getter：props 改變就自動重查
  requestPolicy: 'cache-and-network',
})
</script>

<template>
  <p v-if="error">載入失敗：{{ error.message }}</p>
  <ul v-else-if="data?.customer">
    <li v-for="{ node } in data.customer.orders.edges" :key="node.id">{{ node.orderedAt }}　{{ node.total }} 元</li>
  </ul>
  <p v-if="fetching">更新中…</p>
</template>

data、fetching、error 都是 ref，data 的型別由 OrderHistoryDocument 推導出來。Vue 課第 17 課自己處理的載入狀態、競態（變數變了，舊的回應晚到不能蓋掉新的），urql 都處理好了。

requestPolicy 決定一個查詢先讀快取還是先問伺服器：

requestPolicy快取有資料時快取沒有時適合
cache-first（預設）直接用快取，不送請求送請求不常變的資料、靠失效機制保持新鮮
cache-and-network先給快取（stale: true），同時在背景重查，回來再更新一次送請求列表頁：畫面立刻有東西，又不會一直舊
network-only一律送請求，結果還是會存進快取送請求「重新整理」按鈕、一定要最新的畫面
cache-only用快取不送請求，data 是空的確定已經查過、離線

兩個實測（@urql/core 6.0.3 原始碼）會影響你怎麼寫程式：

  • client.query(…).toPromise() 會跳過 stale 的結果，只回傳第一個新鮮的結果。所以 cache-and-network 加上 toPromise() 一定會等網路；要「先顯示快取」得用訂閱（useQuery 就是訂閱）。
  • 查詢預設用 GET（preferGetMethod 預設 'within-url-limit'：網址不超過 2048 字元就用 GET，查詢和變數放在網址參數）；mutation 一律 POST。在瀏覽器的 Network 面板看到 GET 不用意外，伺服器要接受 GET 查詢（Yoga 預設接受）。
Apollo Client 是另一個常見選擇，概念相同（它預設就是正規化快取）。版本要注意：Apollo Client 4.3.5 支援 graphql 17，但 Vue 的整合套件 @vue/apollo-composable 4.2.2 的 peer 仍是 @apollo/client ^3。新的 Vue 專案選 Apollo 時，要先確認這個落差能不能接受。

document cache：下單之後，列表為什麼沒更新

urql 預設的 cacheExchange 是 document cache：用「查詢文字 + 變數」算出一個鍵，整份回應存在這個鍵底下。OrderHistory({ customerId: '1', first: 10 }) 和 first: 5 是兩個不同的鍵，各存一份。它很簡單：不用設定、不用懂 schema。

難題是 mutation。顧客下單後，document cache 怎麼知道哪些查詢過期了？它不知道 placeOrder 的意思，只能用一個粗略的規則：每份查詢結果存起來時，記下裡面出現過哪些 __typename；mutation 的結果回來時，看它含哪些型別，讓含有同樣型別的查詢全部失效（正在畫面上的查詢會自動重查，其他的下次讀取時重查）。urql 會自動在每個選擇集加上 __typename，所以這件事不用你做。

執行 node examples/document-cache.ts，兩位還沒有訂單的顧客各下一張單：

context = {}：下單前 0 張、下單後 0 張，共 2 個請求
context = {"additionalTypenames":["Order"]}：下單前 0 張、下單後 1 張，共 3 個請求

第一位顧客下單後的查詢直接拿了快取（只有查詢、下單兩個請求），畫面停在「沒有訂單」。修法是在查詢的 context 加上 additionalTypenames，主動登記這份查詢跟哪些型別有關：

client.query(OrderHistoryDocument, { customerId, first }, { additionalTypenames: ['Order'] })
// Vue：useQuery({ query: OrderHistoryDocument, variables, context: { additionalTypenames: ['Order'] } })

代價是範圍粗：任何回傳 Order 的 mutation（包括店員改了別人訂單的狀態），都會讓所有顧客的歷史重查。多數 App 這樣就夠了，因為重查一次的成本很低。

💡 實務上：「下單後列表沒更新」與「登出後還看到上一個人的訂單」
客服回報畫面沒更新時，先開瀏覽器的 Network 面板重現：mutation 之後如果沒有再送一次 OrderHistory，就是快取失效的問題，不是伺服器沒寫入；最常見的原因就是上面那種列表結果裡沒有 Order，補上 additionalTypenames。另一個常見事故在登出：快取跟著 client 存在記憶體裡，換一個人登入時畫面可能先閃出前一個人的訂單。urql 官方文件的建議是登入狀態改變時建立新的 client（舊快取整個丟掉）；在 Vue 裡最簡單的做法是登出後整頁重新載入（例如 location.assign('/login')），記憶體裡的 client 和快取就一起消失。共用電腦（店內點餐平板）上這點特別要測。

正規化快取：同一個物件只存一份

正規化快取（normalized cache）把回應拆開：每個有 __typename 和 id 的物件，用 Order:42 這樣的鍵各存一份；查詢結果只記「這裡指向 Order:42」。urql 的正規化快取是 @urql/exchange-graphcache（9.0.2），把 cacheExchange 換掉就好。

執行 node examples/graphcache.ts：

第一次查： Order:42=PREPARING Order:41=PREPARING （1 個請求）
改狀態後： Order:42=READY Order:41=PREPARING （2 個請求：mutation 那一個，歷史沒有重新查）

店員把 42 號改成「可取餐」，mutation 回傳 { id, status }，graphcache 把新的 status 寫進 Order:42，所有用到它的查詢立刻更新，不用重查。document cache 在同樣情況會讓整份歷史失效、重新查一次。

它解決不了的是新增：新訂單 Order:43 存進快取了，但「顧客 2 的 orders 列表」是另一筆記錄，裡面只有原本那些連結，graphcache 不知道 43 號該不該放進去、放在第幾個。這要你在 updates 裡寫：

import { cacheExchange } from '@urql/exchange-graphcache'

cacheExchange({
  updates: {
    Mutation: {
      // placeOrder 的結果寫進快取時呼叫：(結果, 參數, cache, info)
      placeOrder(result, args, cache) {
        const customer = { __typename: 'Customer', id: args.input.customerId }
        for (const field of cache.inspectFields(customer)) {        // 快取裡這位顧客有哪些欄位
          if (field.fieldName === 'orders') cache.invalidate(customer, 'orders', field.arguments)
        }
      },
    },
  },
})
  • cache.inspectFields(物件) 列出快取裡這個物件存了哪些欄位，每一筆有 fieldName 和 arguments。orders(first: 10) 和 orders(first: 5) 是兩筆，所以要用迴圈，invalidate 時帶上那一筆的 arguments。
  • cache.invalidate 讓欄位失效，用到它的查詢會重新向伺服器查。另一種做法是 cache.updateQuery 直接把新訂單插進列表，省一次請求，但你要自己處理排序、分頁游標，容易跟伺服器不一致。先用 invalidate，有效能需要再改。
  • 沒有 id 的物件 graphcache 沒辦法正規化，只能嵌在父物件裡，並用 console.warn 提醒（Invalid key）。名稱是 PageInfo、或以 Connection、Edge 結尾的型別不會警告（9.0.2 原始碼直接略過這些 Relay 慣用名稱），所以這個 schema 不用設定。其他沒有 id 的型別，在 keys 設 { Money: () => null } 表示「我知道，直接嵌入」；鍵不叫 id 的，回傳要當鍵的值，例如 { Product: p => p.sku }。這也是 schema 設計的影響：會被多個畫面共用的物件，要給穩定的 id。

正規化快取還能做樂觀更新（optimistic update）：伺服器回應前，先假設 mutation 成功、把預期的結果寫進快取，按下按鈕畫面立刻變；伺服器回應後再用真的結果取代，失敗就還原。graphcache 用 optimistic 選項設定。按讚、改狀態這種幾乎不會失敗的操作很適合；下單這種可能庫存不足的，不要假裝成功。

HTTP 快取的難題

REST 的 GET /menu 可以加 Cache-Control: public, max-age=60，讓瀏覽器和 CDN（內容傳遞網路，放在使用者附近的快取伺服器）直接回應（Node 課第 15 課）。GraphQL 很難這樣做：

  • 傳統的用法是 POST，CDN 和瀏覽器不快取 POST。
  • 所有操作都打同一個網址 /graphql，查詢在 body 裡；就算改成 GET，查詢文字很長，每個客戶端寫法稍有不同就是不同的網址，命中率很低。
  • 同一個網址的回應常常依使用者不同（me、我的訂單）。這種回應放進公開快取，就是把一個人的資料給另一個人。

做法是結合第 6 課的 persisted operations：客戶端用 GET，網址只帶操作的雜湊和變數（/graphql?extensions={"persistedQuery":{"version":1,"sha256Hash":"…"}}&variables=…，這是 Yoga 的 persisted operations 外掛預設讀取的格式）。同一份操作、同樣的變數就是同一個短網址，CDN 能快取；再由伺服器只對公開資料的操作設 Cache-Control: public，其他一律 private, no-store。執行 node examples/http-cache.ts：

GET Menu  200  cache-control: public, max-age=60
   {"data":{"menu":[{"id":"1","name":"美式咖啡","price":80},…

菜單用 GET 加雜湊取得、可以公開快取；訂單歷史不在公開清單裡（這裡故意沒帶變數，順便看到錯誤回應也是 no-store）；不在白名單的任意查詢直接被拒絕。Cache-Control 由伺服器依「操作是否公開」決定，不是由客戶端決定。

不要為了讓 CDN 命中，把個人資料設成 public。CDN 的快取鍵預設只有網址，Authorization 標頭不同它也會回傳同一份；Vary: Authorization 能分開，但每個使用者一份，命中率趨近於零，等於沒快取。個人資料用 private（只有瀏覽器自己能存）或 no-store，交給客戶端快取。

另一層是伺服器端的回應快取（response cache，快取與失效的基本觀念見 NestJS 課第 19 課、系統設計課第 5 課）：伺服器把「查詢 + 變數 + 使用者」對應的整份回應存起來，下次同樣的請求直接回傳，resolver 完全不執行。Yoga 用 @graphql-yoga/plugin-response-cache（4.0.1）：

useResponseCache({
  session: request => request.headers.get('x-customer-id'),   // 快取鍵的使用者部分；null 代表沒登入
  ttl: 0,                                  // 預設不快取
  ttlPerSchemaCoordinate: {                // schema coordinate：「型別.欄位」
    'Query.menu': 60_000,                  // 毫秒
    'Query.me': 10_000,
  },
  invalidateViaMutation: true,             // 預設 true
})

這幾個選項各自對應一個正式環境的事故（以下行為讀過 4.0.1 與底層 @envelop/response-cache 10.0.0 的原始碼）：

  • session 一定會被併進快取鍵。回傳固定字串或 null，就等於「所有人共用一份」：王小明查過 me，陳美華拿到的是王小明。session 要從驗證過的身分取，不是信任任意標頭（這裡為了練習簡化）。
  • ttl 不設時預設是 Infinity：所有查詢都存、永遠不過期。ttl: 0 讓預設是不存，再用 ttlPerSchemaCoordinate 白名單列出要存的欄位。一份查詢同時含好幾個有設定的欄位時，用最小的 ttl。
  • invalidateViaMutation：快取每份回應時記下裡面的物件（Product:3），mutation 回傳的物件會讓含有它的快取失效。前提是 mutation 有回傳那個物件和它的 id；只回傳 Boolean 的 mutation 讓不了任何東西失效。
  • 有錯誤的回應預設不存。外掛也會在回應加上 ETag，客戶端帶 If-None-Match 回來時可以得到 304。
💡 實務上：開回應快取前先問「誰會改這份資料」
invalidateViaMutation 只看得到經過這台 GraphQL 伺服器的 mutation。後台用另一個服務、排程或直接改資料庫調價時，快取不會知道，ttl 到期前顧客看到的都是舊價格。預設的快取（createInMemoryCache()）存在每台伺服器自己的記憶體：伺服器有好幾台時，A 台失效了 B 台還是舊的，其他服務也碰不到它。要共用就換 @envelop/response-cache-redis 的 createRedisCache，其他服務改完資料後也能對同一個 Redis 呼叫 cache.invalidate([{ typename: 'Product', id: '3' }])。上線前跟 PM 確認「看到幾秒前的資料可以接受」（菜單舊 60 秒通常可以，結帳時價格與庫存一律重新查），那就是 ttl 的上限。
TTL 由外掛內部的 lru-cache 套件用 performance.now() 計時，node:test 的假時鐘控制不到。所以練習 4 不等時間過去，而是包一層記錄的 cache，檢查寫入時的 ttl。

即時更新與怎麼選

訂單狀態變成「可取餐」時，想讓顧客的畫面自己更新，GraphQL 有 subscription（第三種操作，subscription { orderStatusChanged(id: "42") { id status } }），伺服器有事件就推一筆結果。Yoga 內建用 SSE（Server-Sent Events）傳送，不需要另外架 WebSocket 伺服器；Vue 端用 @urql/vue 的 useSubscription，推來的 Order 一樣會寫進正規化快取。規模化的問題跟 系統設計課第 17 課相同：每個顧客一條長連線、斷線重連時漏掉的事件、多台伺服器之間怎麼廣播。這一課不出練習；很多時候輪詢（cache-and-network 加上每 15 秒重查）就夠了。

資深工程師的判斷：

情況選擇
多數後台、表單、列表頁document cache + 適當的 requestPolicy（列表 cache-and-network），mutation 後用 additionalTypenames 或重查
同一批物件出現在很多畫面，改一個地方其他畫面要同步（購物車、訂單看板）正規化快取。代價：每種新增／刪除都要寫 updates、沒有 id 的型別要設 keys、樂觀更新與快取清理要自己想
公開、每個人都一樣的資料（菜單）persisted operation + GET + Cache-Control: public，交給 CDN
算起來很貴、短時間內很多人查同樣東西伺服器端回應快取：白名單、短 ttl、session 一定要對、mutation 回傳 id

不要一開始就上正規化快取。先用 document cache，等你發現自己在很多地方手動重查同一批資料，才是換的時機。

練習

四題都在 api-styles/practice/work/07/，執行 node check.mjs api-styles 07。練習 2、3 用練習 1 產生的 src/gql/graphql.ts，要先做完練習 1；練習 4 是伺服器端，可以獨立做。測試每次用不同的訂單、價格，寫死答案不會過。

練習 1：寫 codegen.ts：schema 是 schema.graphql；documents 涵蓋 src 底下（含子資料夾）所有的 .graphql；用 client preset 輸出到 src/gql/，presetConfig 開 persistedDocuments，config 設 importExtension: '.ts'、useTypeImports: true。再把 src/orderHistory.graphql 補完：操作名稱 OrderHistory，變數 $customerId: ID!、$first: Int，選 customer(id: $customerId) 的 id、name，以及 orders(first: $first) 的 edges { cursor node { id orderedAt total status } } 和 pageInfo { hasNextPage endCursor }。測試會自己執行 codegen（離線，每次幾秒），用 Node 載入產生的檔案，用 TypeScript 編譯一段型別檢查（例如 node.total 必須是 number、first 必須是 number | null | undefined），核對 persisted-documents.json 的雜湊，並在暫存資料夾加一個欄位拼錯的 src/extra/typo.graphql，確認 codegen 會失敗。

練習 2：在 src/client.ts 用 @urql/core 的 document cache：createHistoryClient(fetch) 建立 client（url 用 'http://localhost:4000/graphql'、fetch 用參數、requestPolicy: 'cache-first'）；loadHistory(client, customerId, first) 用產生的 OrderHistoryDocument 查詢；placeOrder(client, input) 用 PlaceOrderDocument。兩個函式都回傳 { data, error }，不丟例外。測試注入一個轉給 yoga.fetch 的假 fetch，記下每個請求，檢查：同一個 client 第二次查同一份歷史不送請求；一位還沒有訂單的顧客下單後，再查歷史會重新查詢並看到新訂單；伺服器回 errors 時 error 保留訊息、data 保留部分結果；網路錯誤時回傳 error.networkError；查詢只寫在 .graphql 檔，client.ts 從 ./gql/graphql.ts import。

練習 3：在 src/normalized.ts 寫 createNormalizedClient(fetch)，改用 @urql/exchange-graphcache 的 cacheExchange（requestPolicy: 'cache-first'），在 updates.Mutation.placeOrder 讓下單顧客的 orders 欄位（每一組參數）失效。測試檢查：改訂單狀態後，歷史顯示新狀態而且沒有重新查詢；下單後，同一位顧客 first 不同的兩份歷史都出現新訂單（而且兩份各重查一次），別位顧客的歷史仍然直接用快取。所以不要用 cache.invalidate('Query') 把整個快取清掉。

練習 4：在 cache.ts 的 cachePlugin({ cache }) 回傳 useResponseCache，修好起始檔的危險設定：用傳進來的 cache（正式程式會傳 createInMemoryCache() 或 Redis）；預設不快取；Query.menu 存 60 秒、Query.me 存 10 秒；session 用 x-customer-id 標頭（沒有時是 null）；updatePrice 之後含那個商品的快取失效。測試把 cache 包一層記錄每次寫入的 ttl，並用 resolver 的呼叫次數判斷有沒有命中：兩位顧客先後查 me 要各自拿到自己的資料、沒列出的查詢不能被寫入快取、改價後 menu 要是新價格。

練習 5：「我的訂單」用 document cache（cache-first）。一位還沒有訂單的顧客下單成功，回到「我的訂單」還是顯示「沒有訂單」。最可能的原因？

✓ document cache 不懂 placeOrder 的意思，只能比對型別名稱；空列表沒有 Order 可以比對。加上 additionalTypenames: ['Order']、在 mutation 後重查，或用正規化快取寫 updates。伺服器有寫入（a），重新整理頁面就看得到；mutation 當然可以新增（c）；cache-only 永遠不問伺服器，只會更舊（d）。

練習 6：為了讓 GraphQL 的回應能放進 CDN，下列做法哪一個對？

✓ CDN 依網址快取 GET，所以要讓「同一份查詢 + 變數」對應固定、短的 GET 網址，而且只對每個人都一樣的資料用 public。a 會把某位顧客的 me、訂單給所有人；CDN 預設不快取 POST（b）；內省跟快取無關（d）。

練習 7：正規化快取（graphcache）以什麼當物件的鍵？店員改了 Order:42 的狀態後會發生什麼事？

✓ 正規化快取把物件拆開存，同一個物件全部畫面共用一份，所以修改已存在的物件自動反映。a 是 document cache 的行為；c 是 HTTP 快取；d 錯在新增：新物件不在任何列表的連結裡，graphcache 不知道它屬於哪個列表、排在哪裡，要寫 updates。

常見錯誤

  • 手寫回應型別：res.json() as History 只是你說了算，schema 改名後照樣編譯通過。用 codegen 產生的 TypedDocumentNode，schema 一改型別檢查就會報錯。
  • documents 的路徑沒涵蓋全部的操作：例如只列幾個檔名，新加的 .graphql 不會被驗證、也沒有型別。用 src/**/*.graphql 這種 glob。
  • 每次查詢都建立新的 client：在元件或函式裡呼叫 createClient，快取跟著 client 一起丟掉。整個 App 一個 client。
  • 以為 mutation 後快取會自動更新列表：document cache 依型別名稱失效，空列表就漏掉；正規化快取只更新已存在的物件，新增、刪除都要寫 updates。
  • 把錯誤吞掉：只回傳 data，畫面不知道為什麼是空的。error 一起回傳；GraphQL 錯誤時 data 可能還有部分內容。
  • 伺服器回應快取的 session 回傳固定值：所有人共用一份快取，一個人的資料被另一個人看到。session 從驗證過的身分取。
  • 回應快取不設 ttl：預設 Infinity，連個人資料、訂單都永遠快取。ttl: 0 再用白名單開。
  • 為了 CDN 命中把個人資料設成 public：CDN 只看網址。個人資料用 private 或 no-store。
  • 一開始就上正規化快取：每種 mutation 都要想 updates，複雜度很高。多數畫面 document cache 加上適當的 requestPolicy 就夠。

小結

  • GraphQL 用 fetch POST 就能呼叫；正式專案要補上型別、快取與一致的錯誤處理。
  • codegen 從 schema 和 .graphql 產生 TypedDocumentNode，客戶端自動推導 data 與變數的型別；schema 改了，前端在建置時就報錯。client preset 也能輸出 persisted operations 白名單。
  • urql：一個 App 一個 client，exchange 是處理操作的管線；requestPolicy 決定先讀快取還是先問伺服器。toPromise() 跳過 stale 結果；查詢預設用 GET。
  • document cache 以「查詢 + 變數」為鍵，mutation 依 __typename 讓查詢失效；空列表要用 additionalTypenames。
  • 正規化快取以 __typename:id 為鍵，修改已存在的物件自動反映；新增要寫 updates；物件要有穩定的 id。
  • GraphQL 難用 HTTP 快取：POST、同一個網址、回應依使用者不同。公開資料用 persisted operation + GET + Cache-Control: public；伺服器回應快取要白名單、session 正確、mutation 回傳 id。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 8：同事把「只有店員看得到 email」寫在 Query.customer 裡，其他地方沒有另外寫 resolver。這樣寫哪裡會出事？

Query: {
  customer: async (_parent, { id }, ctx) => {
    const c = await db.findCustomer(id)
    return ctx.viewer?.role === 'STAFF' ? c : { ...c, email: null }
  },
},

✓ GraphQL 的型別互相連通，Order.customer、me 回傳的 Customer 不經過 Query.customer，email 走預設 resolver 直接回傳。規則要寫在 Customer.email 自己的 resolver，不論從哪條路徑來都會經過。a 錯在把「入口檢查過」當成「每條路徑都檢查過」，這就是 GraphQL 版的 BOPLA。（第 6 課）

練習 9：咖啡店的 GraphQL 有深度上限 6，限流是每位使用者每分鐘 60 個請求，資料庫還是被少數請求打到滿載。log 裡這些查詢都只有一兩層，最可能缺了什麼？

✓ 深度只限制巢狀層數：500 個別名只有 1 層，三層各 first: 50 就是 125,000 筆。成本計算讓清單乘 first、別名各算，限流扣每份查詢的成本而不是請求數。b 錯在深度限制本來就會展開 fragment；問題是查詢太寬，不是太深。（第 6 課）

練習 10：自家 App 已經用 persisted operations 白名單。現在要開放 GraphQL 給外送平台串接，查詢由對方自己寫。對外的入口該怎麼防？

✓ 白名單只適合第一方客戶端：查詢在建置時就知道。第三方的查詢事先不知道，只能讓它執行，再用深度、成本限制與依成本限流控制工作量。b 錯在標頭誰都能加，「帶標頭就放行」等於沒有白名單；開不開任意查詢只能看伺服器自己的設定。（第 6 課）

練習 11：同事替 Yoga 開了回應快取，想讓菜單存 60 秒。這段設定上線後哪裡會出事？

useResponseCache({
  session: () => null,
  ttlPerSchemaCoordinate: { 'Query.menu': 60_000 },
})

✓ ttl 預設是 Infinity，沒列在白名單的查詢也會永遠存著；session 會併進快取鍵，固定回傳 null 就是所有人共用一份。修法是 ttl: 0 再用 ttlPerSchemaCoordinate 開白名單，session 從驗證過的身分取。a 錯在以為沒列的欄位不會被存，預設剛好相反。（第 7 課）

練習 12：店員的訂單看板改用 graphcache。按「可取餐」呼叫 markReady(id: ID!): Boolean!，伺服器已經改好，看板和訂單詳細頁卻都還顯示「準備中」。原因是？

✓ 正規化快取靠 mutation 回傳的物件更新：回傳 Order { id status }，新的 status 寫進 Order:42，所有畫面一起更新、不用重查。只回傳 Boolean，快取沒有東西可以寫。b 剛好說反了：修改既有物件是自動的，新增才要寫 updates。（第 7 課）

練習 13：後端把 Order.total 改名成 amount 並部署。下列哪一種前端寫法，會在建置時就失敗，而不是上線後畫面才出錯？

✓ codegen 用 schema 驗證每個 .graphql 操作，欄位不存在就直接失敗；產生的型別也讓用到 total 的程式碼型別檢查失敗。前提是 codegen 讀的是後端實際部署的那份 schema。b 錯在 as 只是你說了算，schema 改了照樣編譯通過。（第 7 課）
