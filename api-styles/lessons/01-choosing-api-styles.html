階段 1：選擇 API 風格 · 第 1 課

同一間咖啡店，四種 API：REST、GraphQL、gRPC 與事件

咖啡店 App 的「我的訂單」畫面要顯示：最近幾筆訂單、每筆訂單的品項名稱與價格、目前的會員點數。後端現有的 REST API 是照資源切的：訂單列表一支、每張訂單的品項一支、會員一支。結果 App 要先拿列表，再對每一張訂單各打一次品項，再打一次會員。8 筆訂單就是 10 個請求；手機在捷運上每個請求要 200 ms，一個一個打要等 2 秒。

同一間咖啡店裡還有別的溝通：訂單服務下單前要問庫存服務「拿鐵還有沒有」，要立刻知道答案；出貨之後要通知會計、點數、推播，但下單的人不需要等它們做完。這三種需求適合不同的 API 風格（API style）：客戶端和伺服器約定「怎麼問、怎麼回」的整套方式。這一課比較四種最常見的風格：REST、GraphQL、gRPC 和事件，學完你能為一個情境選出風格、說出理由和代價。後面的課再一種一種動手做。

這課的路線：
  1. REST：照資源切的 API 碰上「我的訂單」這種畫面，為什麼變成 10 個請求、一個等一個。
  2. GraphQL 與 gRPC：前端一次說清楚要哪些欄位，一個請求拿齊；內部服務問庫存，像呼叫函式一樣快、有型別。
  3. 事件：出貨後通知會計、點數、推播，為什麼不讓下單的人等，對方掛掉時誰受影響。
  4. 並排比較與決策表：用五個問題替一個情境選風格，寫成 ADR，面試時也講得出理由和代價。
這課會用到：
  • Node 課第 12 課的 HTTP：方法（GET 讀、POST 寫）、狀態碼表示結果、標頭帶附加資訊。
  • Node 課第 14 課的 REST 設計：URL 代表資源（/orders/42），HTTP 方法代表動作。
  • 系統設計課第 16 課的事件與 webhook：發生了什麼事就發出通知，訂閱的人各自處理；webhook 是主動 POST 到對方給的網址。

REST：照資源切，畫面卻不照資源長

REST 你在 Node 課第 14 課做過：用 URL 代表資源（/orders/42），用 HTTP 方法表達動作（GET 讀、POST 建立、PATCH 修改），用狀態碼表達結果。這種設計叫資源導向（resource-oriented）。咖啡店現有的端點：

端點回傳
GET /orders?customer=1這位顧客的訂單列表：每筆只有 id、total、orderedAt
GET /orders/:id/items一張訂單的品項：productId、quantity、unitPrice
GET /products/:id一個商品：id、name、price、category、description
GET /members/:id會員：name、phone、email、points、birthday…

REST 的優點很實在：人人看得懂，curl 就能測；GET 有固定 URL，瀏覽器快取和 CDN（內容傳遞網路，把回應存在離使用者近的機器上；HTTP 快取見 Node 課第 15 課）照 HTTP 規則直接可用；工具、閘道、監控都支援。它的契約（雙方都同意的請求與回應格式）通常寫成 OpenAPI 文件（NestJS 課第 23 課）。

問題出在畫面跟資源不一一對應，分成兩種：

  • 拿太多（over-fetching）：畫面只要會員點數，GET /members/1 卻回了電話、email、生日。浪費流量，也把畫面用不到的個人資料送到手機上。
  • 拿不夠（under-fetching）：一支端點湊不齊畫面要的資料，要再打好幾支。後面的請求要用到前面的結果（先有訂單 id 才能查品項），只能等前一批回來，這叫瀑布式請求（request waterfall）。

3 筆訂單是 5 個請求、要兩輪（約 400 ms）。這裡有兩個數字要分開看：

  • 請求次數：1（列表）＋ N（每張訂單的品項）＋ 1（會員）。N 越大越多，手機每個請求都要耗電、佔連線。
  • 瀑布深度：最長的「必須依序」鏈有幾段。品項要等列表，所以是 2。N 個品項請求可以同時送，不會讓深度變成 N。等待時間大約是「深度 × 單次延遲」。如果程式寫成 for 迴圈一個一個 await，深度才會變成 N + 1，這是寫法的問題，不是 REST 的問題。

品項只有 productId，畫面要商品名稱，就得再查 /products/:id，深度變成 3。這就是練習 1。

💡 實務上：先打開 Network 面板數一數，再決定要不要換風格
客服或 PM 回報「App 的我的訂單很慢」時，先在 Chrome DevTools 的 Network 面板把網路節流設成 Slow 4G，重新整理那個畫面，看瀑布圖：有幾個請求、幾段必須依序。很多時候問題是程式用 for 迴圈一個一個 await，改成 Promise.all 就好；或是在 REST 加一支專給這個畫面的端點（例如 GET /me/order-summary），不用整套換掉。只有當好幾個畫面、好幾種前端都在重複遇到這件事，才值得考慮 GraphQL。

GraphQL：客戶端說要哪些欄位

REST 的問題出在資源的形狀由伺服器決定，畫面要什麼卻是前端最清楚。GraphQL 把決定權交給前端。它是一種 API 的查詢語言（query language）：伺服器公開一份 schema（有哪些型別、每個型別有哪些欄位），客戶端在一次請求裡送出一份查詢文件，寫出這個畫面要哪些欄位，伺服器照這個形狀回傳。「我的訂單」畫面只要一個請求：

query MyOrders {
  me {
    points
    orders(first: 8) {
      id
      total
      items {
        quantity
        product { name price }
      }
    }
  }
}
{ "data": { "me": { "points": 320, "orders": [
  { "id": "11", "total": 190, "items": [
    { "quantity": 1, "product": { "name": "拿鐵", "price": 110 } },
    { "quantity": 1, "product": { "name": "美式咖啡", "price": 80 } } ] } ] } } }

回應的形狀跟查詢一模一樣：沒選 phone 就不會回 phone，拿太多和拿不夠一次解決。適合的情況：有好幾種前端（App、網頁、店內平板）各要不同的欄位組合、畫面改得快、資料彼此關聯很深。

代價要一起記住：

  • HTTP 快取幾乎用不上。GraphQL over HTTP 規格要求伺服器一定支援 POST，GET 是選用（而且 mutation 不能用 GET）；實務上幾乎都是 POST 到同一個 /graphql，CDN 沒有可用的快取鍵。要接近 REST 的快取，得用 persisted operations（事先登記好的查詢，客戶端只送查詢的 id）搭配 GET（第 6、7 課）。
  • N+1 從前端搬到後端。前端只發一個請求，但伺服器替每張訂單各查一次品項，資料庫還是收到 N+1 句 SQL（第 4 課用 DataLoader 解決）。
  • 要防惡意查詢。客戶端可以寫很深、很大的查詢，伺服器要限制深度與成本（第 6 課）。
  • GraphQL 不是資料庫查詢語言。它只描述 API 的形狀，資料從哪裡來、怎麼查，全由伺服器上你寫的程式（resolver）決定。
💡 實務上：GraphQL 上線後，監控與 log 要跟著改
REST 的監控習慣用「URL ＋ 狀態碼」分組；GraphQL 所有請求都是 POST /graphql，而且欄位出錯時常常還是回 HTTP 200，錯誤放在回應的 errors 裡（第 5 課）。如果只看 URL 和狀態碼，儀表板會一片綠，實際上「我的訂單」查詢一直在失敗。導入時要先跟維運約定：每份查詢都要有名稱（例如上面的 MyOrders），log 與監控用查詢名稱分組，並把 errors 的數量記下來。這是評估要不要導入 GraphQL 時常被漏掉的成本。

gRPC：像呼叫函式一樣呼叫別台機器

REST 和 GraphQL 主要服務前端；開場第二種需求是訂單服務問庫存服務，兩邊都是自己人寫的後端。RPC（remote procedure call，遠端程序呼叫）的想法是：呼叫別台機器上的程式，寫起來像呼叫本地的函式。gRPC 是 Google 開源的 RPC 框架。先用 .proto 檔定義服務與訊息，這份檔就是契約：

syntax = "proto3";
package coffee.inventory.v1;

service InventoryService {
  rpc CheckStock(CheckStockRequest) returns (CheckStockResponse);
}

message CheckStockRequest {
  string product_id = 1;
  int32 quantity = 2;
}

message CheckStockResponse {
  bool available = 1;
  int32 remaining = 2;
}

再用工具從 .proto 產生兩邊的程式碼，訂單服務（服務為什麼拆開、互相呼叫，見系統設計課第 15 課）呼叫時就像 await inventory.checkStock({ productId: '2', quantity: 1 })，參數和回傳都有型別。訊息用 Protobuf（Protocol Buffers，.proto 定義的資料格式）編成二進位（比 JSON 小、解析快），走 HTTP/2，內建 deadline（「最晚幾點前要回來，過了就放棄」）和串流（一個呼叫連續送多筆資料）。適合服務之間的內部呼叫：要低延遲、呼叫量大、團隊用多種程式語言但要共用同一份契約。

代價：

  • 瀏覽器不能直接呼叫原生 gRPC。gRPC 直接控制 HTTP/2 的資料框（frame，HTTP/2 把請求切成的小塊）並依賴 trailers（回應主體之後才送的標頭，gRPC 把狀態碼放在這裡），瀏覽器的 fetch 都拿不到。瀏覽器要改用 gRPC-Web 或 Connect 協定：原生 gRPC 伺服器前面要放一個代理（例如 Envoy）把 gRPC-Web 轉成 gRPC；用 Connect 函式庫寫的伺服器本身就能同時接受 gRPC、gRPC-Web 和 Connect，不用代理（第 11 課）。
  • 除錯沒那麼方便。二進位內容不能直接看，curl 不夠用，要 grpcurl、buf curl 這類工具。
  • CDN 不快取（每個呼叫都是 HTTP/2 POST），也不適合給外部合作夥伴：對方要先拿你的 .proto 產生程式碼。
💡 實務上：gRPC 的負載平衡要先跟維運確認
gRPC 會跟對方開一條 HTTP/2 長連線，之後的呼叫都在這條連線上跑。如果負載平衡器只在「建立連線」時決定送去哪一台（常聽到的 L4 負載平衡），訂單服務的所有呼叫會一直落在同一台庫存服務上，其他台閒著。解法是改用看得懂 HTTP/2、每個請求各自分配的負載平衡器（L7），或讓客戶端自己在多台之間輪流（client-side load balancing）。提議用 gRPC 時，設計審查就要問維運：現有的負載平衡器是哪一種？不要等上線後才發現某一台 CPU 特別高。

事件：發出去就繼續，誰有興趣誰處理

前面三種都是同步呼叫（synchronous call）：呼叫端送出請求，等對方回應才繼續。事件（event）是非同步（asynchronous）的：訂單服務出貨後發一個 OrderShipped 到佇列，然後就繼續做自己的事；會計、點數、推播服務各自訂閱、各自處理。外部合作夥伴收通知常用 webhook（你主動 POST 到對方給的網址），在這一課的比較裡也算事件。

事件讓服務彼此不用同時活著，代價是：

  • 最終一致（eventual consistency）：出貨那一刻會計帳還沒記上，過一陣子才一致。畫面要能接受這段落差。
  • 除錯困難：一件事散在好幾個服務、好幾個時間點，要靠關聯 ID（correlation ID：同一件事在每個服務的 log 裡都帶同一個 ID）和集中的 log 才串得起來。事件會重複、會亂序，消費者要能處理（系統設計課第 12 課、第 16 課）。
  • 不適合需要立刻回應的請求。用事件問「還有沒有拿鐵」再等另一個事件回來，等於自己重做一套同步呼叫：要配對請求與回應、處理逾時，還多了佇列這個會壞的地方。
💡 實務上：改用事件之前，先跟 PM 和維運講好「延遲」和「卡住」
點數改成收 OrderShipped 事件後，顧客一出貨就打開 App，可能看到點數還沒加上，客服就會接到「點數沒入帳」。所以要先跟 PM 談畫面怎麼呈現，例如顯示「點數處理中」，而不是讓顧客以為沒拿到。資深工程師還會先問兩件事：消費者一直處理失敗、事件在佇列裡越堆越多時，誰會收到告警？事件格式也是契約，改欄位前要知道有哪些服務在訂閱。如果只有一個接收者、而且就在同一個服務裡，直接呼叫函式就好，不必為了「解耦」多養一個佇列。

決策表：用五個問題選風格

選風格時依序問這五個問題：

  1. 誰呼叫？瀏覽器或 App（前端）、內部服務、外部合作夥伴。
  2. 要不要立刻拿到結果？呼叫端要等答案才能繼續，還是發出去就好。
  3. 資料形狀由誰決定？不同畫面各要不同欄位組合，還是每次都一樣。
  4. 要不要 CDN／HTTP 快取？同一份資料被大量重複讀取。
  5. 團隊熟悉度與工具：沒人會維運的技術，再適合也會出事。這一條沒辦法用程式判斷，但要寫進決定的理由裡。

前四個問題整理成下面這張表。由上往下看，第一個符合的列就是答案；每一列也規定了理由要寫哪些代碼（練習 3 用）：

#條件風格理由代碼
1不需要立刻拿到結果（不管誰呼叫）eventfire-and-forget
2呼叫端是外部合作夥伴restexternal-partner
3呼叫端是內部服務（本課假設：呼叫量大、要低延遲）grpcinternal-low-latency
4前端，需要 CDN／HTTP 快取restbrowser-caller、needs-cdn-cache

幾個順序上的理由：「不用等結果」放第一，因為不管誰呼叫，同步呼叫都會讓對方掛掉時連帶失敗。外部合作夥伴放在內部服務前面，因為對方的語言、工具你管不到，REST 加 OpenAPI 是最低門檻（要通知他們就用 webhook，落在第 1 列）。前端同時需要快取和自選欄位時選 REST，因為快取省下的是整台伺服器的負載，第 4 列比第 5 列優先。第 3 列寫的是咖啡店的前提，不是通則：內部服務之間用 REST／JSON 也很常見，gRPC 通常在講求效能、需要串流、或多種語言要共用同一份契約時才選；團隊沒人熟 gRPC 時，第 5 個問題可以推翻這一列。這是課程為了練習做的簡化版，真實決定還要加上第 5 個問題；前後端同 repo、全是 TypeScript、只有自己的前端時，也可以考慮 tRPC。

一個系統通常混用好幾種

咖啡店照這張表走完，最後的架構長這樣：

資深視角：選風格是選取捨，不是選流行

  • 先量測再換。「gRPC 比較快」要先問延遲花在哪裡（系統設計課第 3 課）。多數 API 的時間花在資料庫和網路往返，JSON 換成二進位省下的通常不多。
  • 換風格的成本主要在契約與工具：程式碼產生、測試、監控、閘道、文件、團隊學習。改寫 handler 反而是最小的部分。
  • 把決定寫成 ADR（系統設計課第 18 課）：情境、考慮過的選項、選了什麼、放棄了什麼。一年後有人問「為什麼這裡不是 REST」，答案在文件裡。

練習

練習 1：寫 countRequests(screen, style)，算出一個「我的訂單」畫面要幾個 HTTP 請求（requests），以及最長的「必須依序」鏈有幾段（depth，瀑布深度）。規則：

  • 'rest' 用本課的 REST 端點表：列表一定要打 1 次。withItems 時每張訂單打一次品項；withProductNames 時每個品項各打一次 /products/:id（不合併重複的商品）。withPoints 時多打 1 次會員，它和列表同時送。能同時送的一律同時送。
  • 訂單是 0 筆時，不用查品項，也不用查商品。
  • 'graphql'：不管要幾個欄位都是一份查詢，1 個請求、深度 1。
  • withProductNames 為 true 時，withItems 一定也是 true。

練習 2：寫一個迷你版的「GraphQL 選欄位」pickFields(data, selection)。selection 是巢狀物件，true 表示要這個欄位的值，物件表示要往下再選，例如 { id: true, items: { quantity: true } }。規則：

  • 回傳的資料只含選到的欄位，順序照 selection。
  • 資料是陣列時，逐筆套用同一個 selection。
  • 資料是 null（例如沒有用優惠券的訂單，coupon 是 null）時，直接回傳 null，不要往下選。
  • 選了資料裡沒有的欄位，丟出 new FieldError(欄位名稱)。
  • 不能修改傳進來的 data。

練習 3：照本課的決策表寫 chooseStyle(scenario)，回傳 { style, reasons }。reasons 要剛好是表上那一列的理由代碼（順序不限），不能多也不能少。練習裡的內部服務都符合第 3 列的前提（呼叫量大、要低延遲）。下面印出四個情境，隱藏測試另有其他情境，涵蓋表上每一列。

練習 4：咖啡店的菜單一天只改一次，全台灣的 App 都要讀。哪種風格最容易用 CDN 快取？

✓ REST 的 GET 有固定 URL，CDN 與瀏覽器快取照 HTTP 規則運作（Cache-Control、ETag）。GraphQL 實務上幾乎都 POST 到同一個 URL，要做 persisted operations 搭配 GET 才能接近（第 6、7 課）；gRPC 每個呼叫都是 HTTP/2 POST，CDN 不快取；事件是通知，不是讓人讀資料的方式。

練習 5：「GraphQL 解決了 N+1 問題」這句話對嗎？

✓ GraphQL 把「湊資料」從前端搬到伺服器。伺服器替每張訂單各查一次品項，N 筆訂單就是 N 次查詢；第 4 課用 DataLoader 批次處理。GraphQL 不會產生 SQL（資料怎麼查由你寫的 resolver 決定），也不一定比較慢。

練習 6：團隊說「我們改用 gRPC，因為它比較快」。資深工程師第一個該問的是？

✓ 換風格前先量測：多數延遲在資料庫和網路往返，JSON 換二進位省下的通常不多。也要確認呼叫端：瀏覽器、外部合作夥伴不能直接呼叫原生 gRPC。a、c、d 都是決定要換之後才需要回答的問題。

常見錯誤

  • 因為流行就換風格：沒有量測、沒有寫下取捨，換完多了一套工具和維運成本。先找出真正的問題（請求太多？欄位太多？延遲在哪？），再寫 ADR。
  • 以為 GraphQL 是資料庫查詢語言：它只描述 API 的形狀。資料從哪裡來、要查幾次資料庫，全由伺服器上的程式決定。
  • 以為瀏覽器可以直接呼叫 gRPC 服務：原生 gRPC 依賴 HTTP/2 的資料框與 trailers，瀏覽器的 fetch 拿不到。要透過 gRPC-Web、Connect 或閘道。
  • 用事件做需要立刻回應的請求：等於自己重做一套同步呼叫，還多了佇列這個故障點。要立刻知道答案就用同步呼叫並設逾時。
  • 把瀑布深度當成請求次數：N 個彼此不相依的請求可以同時送，深度不會變成 N。等待時間看深度，耗電與伺服器負載看次數；兩個都要算。
  • 以為一個系統只能選一種：常見的是對外 REST／GraphQL、內部 gRPC、跨團隊通知用事件，各用在合適的地方。

小結

  • REST 照資源切，HTTP 快取與工具最完整；畫面跟資源對不上時會拿太多或拿不夠，造成多個請求和瀑布。
  • GraphQL 讓客戶端用一份查詢選欄位，一個請求拿齊；代價是 HTTP 快取難做、N+1 搬到伺服器、要防惡意查詢。
  • gRPC 先寫 .proto 再產生程式碼，二進位、HTTP/2、有 deadline 與串流，適合講求效能、需要串流或多語言共用契約的內部服務；瀏覽器不能直接呼叫。
  • 事件發出去就繼續，對方掛掉不影響發送端；代價是最終一致與除錯困難，不適合要立刻回應的請求。
  • 依序問：誰呼叫、要不要立刻拿到結果、資料形狀誰決定、要不要快取、團隊熟不熟。一個系統混用多種風格是常態，決定要寫成 ADR。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 5 件事。先在心裡回答，再選。

練習 7：「我的訂單」顧客有 10 張訂單，在 Slow 4G 下要等很久，同事提議整套改成 GraphQL。程式長這樣，第一步該做什麼？

const orders = await api.get('/orders?customer=1')
const member = await api.get('/members/1')
for (const o of orders) {
  o.items = await api.get(`/orders/${o.id}/items`)
}

✓ 等待時間看瀑布深度。這段程式每個請求都等上一個，12 個請求排成 12 段；彼此不相依的同時送，深度只剩 2。先在 Network 面板量測、改寫法，好幾個畫面都重複遇到才值得換 GraphQL。a 錯在問題是寫法造成的，不是 REST 本身，換風格的成本也高得多。（第 1 課）

練習 8：GraphQL 上線後，用「URL ＋ 狀態碼」分組的儀表板顯示 POST /graphql 全部 2xx，客服卻一直接到「我的訂單打不開」。最可能的原因是？

✓ GraphQL 所有請求都打同一個 URL，欄位失敗也常回 200，只看 URL 和狀態碼會一片綠。修法是每份查詢取名稱，log 與監控用查詢名稱分組，並記下 errors 的數量。b 錯在 GraphQL 實務上都是 POST，CDN 本來就不快取。（第 1 課）

練習 9：訂單服務用 gRPC 呼叫 3 台庫存服務，中間是只在建立連線時分配的 L4 負載平衡器。上線後一台 CPU 90%，另外兩台幾乎閒著，為什麼？

✓ gRPC 跟對方開一條長連線，之後的呼叫都在上面跑；L4 只在建連線時決定送去哪台，所以全部打到同一台。改用每個請求各自分配的 L7 負載平衡器，或 client-side load balancing。c 錯在加機器也一樣閒著，新的台分不到既有連線上的呼叫。（第 1 課）

練習 10：出貨時，shipOrder 依序同步呼叫會計、點數、推播三個服務。會計服務維護 10 分鐘，這段時間出貨全部失敗，該怎麼改？

✓ 出貨不需要立刻拿到會計的結果，同步呼叫只會讓對方掛掉時連帶失敗。改成事件後，會計恢復再處理堆著的事件；代價是點數晚一點入帳，要先跟 PM 談畫面怎麼呈現。a 錯在維護 10 分鐘，重試三次一樣失敗，出貨還是被擋住。（第 1 課）

練習 11：外送平台要查咖啡店的訂單狀態，也想在出貨時馬上收到通知。咖啡店內部服務之間已經全用 gRPC，該怎麼提供？

✓ 外部合作夥伴的語言和工具你管不到，REST 加 OpenAPI 門檻最低；要通知就用 webhook，POST 到對方給的網址。一個系統對外 REST、內部 gRPC、通知用事件是常態。a 錯在對方得先拿 .proto 產生程式碼，內部契約也變成改不動的對外承諾。（第 1 課）
