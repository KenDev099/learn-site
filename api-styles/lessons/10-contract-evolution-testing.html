階段 5：契約與整合架構 · 第 10 課

契約演進與契約測試：deprecation、破壞性變更檢查、Pact 與 schema registry（資深）

後端同事覺得 Product.price 這個名字不夠清楚，改成 priceTwd。他自己的測試全部通過，前端的測試也全部通過，因為前端用的是自己寫的假資料（mock），假資料裡還是 price。上線十分鐘後，App 的菜單頁一片空白：GraphQL 在驗證階段就拒絕了整個查詢，因為 price 這個欄位已經不存在。

這課的路線：
  1. 示範問題：前後端的測試都通過，為什麼後端改一個欄位名稱，上線後菜單頁還是一片空白。
  2. GraphQL 的演進與 findSchemaChanges：改名要分四步走，CI 怎麼自動擋下直接刪欄位的 PR。
  3. proto 的 buf breaking：同樣的檢查放進 CI，每個 PR 都跟 main 分支比對。
  4. 契約測試與 Pact：前端對後端的假設寫成契約，在後端的 CI 裡重播驗證。
  5. Broker、schema registry 與取捨：團隊多大才需要這些工具，契約測試擋不住什麼。
這課會用到：
  • 第 2 課的先驗證再執行：查詢裡只要有一個欄位不在 schema 裡，整份查詢在驗證階段就被拒絕，一個欄位都不回。
  • 系統設計課第 19 課的 expand → migrate → contract：先加新的、讓使用者搬過去，確認沒人用了才刪舊的。

示範問題：兩邊的測試都過，上線還是壞

回頭看那次事故，每一方都「測過了」：

  • 後端的測試查的是新的 priceTwd，當然通過。後端的測試不知道前端用了哪些欄位。
  • 前端的測試用 mock（Node 課第 22 課的測試替身）回傳 { price: 110 }。mock 是前端對後端的假設，後端改了，假設不會跟著改。
  • 端對端測試（end-to-end，把前端、後端、資料庫全部起起來，用瀏覽器點一遍）抓得到，但它慢、容易因為無關的原因失敗（網路、資料、時間），通常只在部署前跑一次，問題發現得太晚，也很難看出是哪一方改壞的。

破壞性變更（breaking change）是指讓現有客戶端壞掉的變更：刪欄位、改名、改型別、參數改成必填。這一課的工具都在回答同一個問題：這次改動，在合併之前，會不會弄壞某個正在使用的人？

GraphQL 的演進：新增 → deprecate → 確認沒人用 → 移除

REST 常用 /v1/、/v2/ 做版本（NestJS 課第 23 課）。GraphQL 通常不這樣做，原因是客戶端只拿自己選的欄位：伺服器多一個欄位，沒有任何既有查詢會受影響。所以改名不是「改」，而是分四步：

type Product {
  id: ID!
  name: String!
  priceTwd: Int!
  price: Int! @deprecated(reason: "改用 priceTwd")
}
  • @deprecated 是 GraphQL 規格內建的指令（directive），標記「這個欄位即將移除」。它不改變任何行為：舊查詢照常執行、照常拿到值。它的作用是讓工具看得到：內省（introspection）會回傳 isDeprecated 與 deprecationReason，GraphiQL 的文件面板會標示它，graphql-js 也有 NoDeprecatedCustomRule 驗證規則，可以在前端的 CI 裡讓「用到 deprecated 欄位」的查詢報錯。
  • reason 要寫替代方案。只寫 @deprecated 時，reason 是預設的 No longer supported，前端看了不知道該改用什麼。
  • 舊欄位 resolver 照舊，新欄位從同一份資料算出來。資料庫欄位叫什麼跟 API 欄位叫什麼是兩件事：資料庫還是 price，API 多一個 priceTwd 的 resolver 回傳 row.price。

改型別也是同樣的流程。Order.status 原本是 String（回傳 "preparing"），想改成 enum。直接改成 status: OrderStatus! 會讓舊客戶端壞掉：舊查詢還能通過驗證，但回傳的值變成 "PREPARING"，舊版 App 拿 status === 'preparing' 判斷就全錯了；在 TypeScript 裡用 codegen 產生的型別也會變。正確做法是新增 state: OrderStatus!，把 status 標成 deprecated。

「確認沒人用」靠資料，不靠感覺。網頁前端每次部署就全部換新，但行動 App 的舊版本會在使用者手機上活好幾個月，有人就是不更新。所以要有欄位使用量：GraphQL 的 schema registry（Hive、Apollo GraphOS）可以讓伺服器回報「哪個操作、哪個客戶端版本用了哪些欄位」，看到 Product.price 過去 30 天的使用量是 0 才移除。沒有這種工具時，至少在 resolver 裡記 log 或指標（DevOps 課第 22 課）：舊欄位被查一次就加一。

💡 實務上：移除欄位是一份有日期的計畫，不是一個 PR
咖啡店的 App 有 iOS、Android 好幾個舊版本，合作的外送平台也在呼叫菜單 API。要移除 price 之前，資深工程師會先問：誰在用（哪些客戶端、哪些版本）？使用量多少？哪一天移除？誰負責通知？行動 App 常搭配「最低支援版本」：低於某版就提示使用者更新，舊版本才真的會消失。對外部合作夥伴，使用量歸零之前就要公告時程（changelog、email），不能只等數字。REST API 也有標準的做法：回應加上 Deprecation header（RFC 9745，2025 年發布）標記已棄用，搭配 Sunset header（RFC 8594）告訴呼叫端哪一天停止回應。

在 CI 自動檢查 schema：findSchemaChanges

「記得不要直接改名」靠人一定會漏，要交給 CI。graphql 17 提供 findSchemaChanges(oldSchema, newSchema)，比較兩份 schema，回傳每一項變更的 { type, description }。type 屬於三個分類之一，三個分類都由 graphql 匯出：

分類例子（type）CI 怎麼處理
BreakingChangeType
破壞性		FIELD_REMOVED、FIELD_CHANGED_KIND（改型別）、REQUIRED_ARG_ADDED、ARG_CHANGED_KIND（例如 Int → Int!）、VALUE_REMOVED_FROM_ENUM、TYPE_REMOVED擋下 PR
DangerousChangeType
危險		VALUE_ADDED_TO_ENUM、OPTIONAL_ARG_ADDED、ARG_DEFAULT_VALUE_CHANGE、TYPE_ADDED_TO_UNION不擋，但在 PR 上提醒
SafeChangeType
安全		FIELD_ADDED、TYPE_ADDED、DESCRIPTION_CHANGED、FIELD_CHANGED_KIND_SAFE（輸出欄位從可為 null 變成非空）放行

危險變更（dangerous change）是不一定壞、但可能改變客戶端行為的變更。enum 多一個 CANCELLED：舊 App 的 switch 沒有這個分支，可能顯示空白或丟錯。所以前端處理 enum 時要有「不認得的值」的預設分支，後端加 enum 值時要先通知前端。

輸出欄位和輸入參數的方向相反：輸出欄位從 String 變成 String! 是安全的（客戶端本來就要處理 null，現在只是不會出現）；參數從 Int 變成 Int! 是破壞性的（舊查詢沒傳這個參數，會被驗證擋下）。這種判斷交給函式，不要自己用文字比對 SDL。另外，加上 @deprecated 不會產生任何變更，因為它不影響任何查詢。

import { buildSchema, findSchemaChanges, BreakingChangeType } from 'graphql'

const BREAKING = new Set<string>(Object.values(BreakingChangeType))
const changes = findSchemaChanges(buildSchema(mainSdl), buildSchema(prSdl))
const breaking = changes.filter(c => BREAKING.has(c.type))
// [{ type: 'FIELD_REMOVED', description: 'Field Product.price was removed.' }]

v17 以前用的 findBreakingChanges、findDangerousChanges 在 graphql 17 已標成 deprecated，預定 v18 移除，新程式用 findSchemaChanges。

更進一步：只擋「有人在用」的移除。走完 deprecation 流程、確認沒人用之後，移除欄位在 findSchemaChanges 眼中仍然是 FIELD_REMOVED。如果手上有前端實際在用的操作清單（第 7 課的 .graphql 檔與 codegen，或 persisted operations 的清單），就能把規則改成「被移除的欄位只要沒有任何操作在用，就不擋」。要知道一份操作用了哪些欄位，用 graphql 的 visit 走過語法樹，搭配 TypeInfo：走到每個欄位時，typeInfo.getParentType() 告訴你它屬於哪個型別，就能記下 Product.price 這樣的座標。

const typeInfo = new TypeInfo(oldSchema)
visit(parse(operation), visitWithTypeInfo(typeInfo, {
  Field() {
    const parent = typeInfo.getParentType(), field = typeInfo.getFieldDef()
    if (parent && field) used.add(`${parent.name}.${field.name}`)
  },
}))

fragment 定義也在同一份文件裡，整份文件走過一遍就會一起記到。input 物件的欄位是例外：它們出現在 variables 的 JSON 裡，從操作文字看不出誰在用，移除一律當成破壞性。

放進 CI（GitHub Actions，見 DevOps 課第 15 課）時，舊 schema 從 main 分支取得。schema 是程式碼產生的話，先在 CI 裡把它印成 SDL 檔（printSchema(schema)）並 commit 進 repo，PR 的 diff 也看得到 schema 的變化：

# .github/workflows/api.yml 的一個步驟（actions/checkout 要設 fetch-depth: 0 才拿得到 main）
- run: git show origin/main:schema.graphql > /tmp/schema-main.graphql
- run: node scripts/check-schema.ts /tmp/schema-main.graphql schema.graphql   # 有破壞性變更就以非 0 結束
💡 實務上：檢查擋下 PR 時，不要直接改 CI 設定繞過去
總有真的需要破壞性變更的時候，例如發現某個欄位把顧客的手機號碼回傳給所有人，必須立刻拿掉。這時該做的是讓例外看得見：PR 說明寫清楚為什麼、影響哪些客戶端，由 API 的負責人核准，寫進 changelog 並通知前端與 App 團隊。常見做法是讓檢查可以被一個需要核准的 PR 標籤略過，而不是有人順手把檢查步驟註解掉。另一個常見的坑是部署順序：前端要用新欄位，後端必須先上線，前端的 PR 才能合併部署。

proto 的自動檢查：buf breaking 放進 CI

第 8 課在本機用 buf breaking evolve/new --against evolve/old 比較兩個資料夾，也選過類別（FILE、PACKAGE、WIRE_JSON、WIRE）。放進 CI 時，改成跟 main 分支比對。--against 可以是本機的 git 倉庫（.git#branch=main），也可以是遠端 git 網址：

# 本機：跟自己的 main 分支比
npx buf breaking --against '.git#branch=main'

# CI（GitHub Actions）：跟遠端的 main 比，錯誤直接標在 PR 的那一行
- run: npx buf breaking --against "https://github.com/coffee/api.git#branch=main" --error-format github-actions

類別照第 8 課的判斷：服務之間只傳二進位、而且每個服務都會重新產生程式碼時，WIRE 就夠；有人用 JSON 呼叫（Connect 的 JSON、gateway 轉換）就要 WIRE_JSON；proto 被很多團隊共用、產生的程式碼被當成函式庫發布時用預設的 FILE，連改名都擋。

契約測試：把前端的假設交給後端驗證

schema 檢查只知道「schema 變了」，不知道「誰依賴什麼」，而且只適用於有 schema 的 API。REST 的 JSON、webhook 的內容（系統設計課第 16 課）、沒有寫好 OpenAPI 的服務，還是需要另一種方法。

契約測試（contract testing）把一方對另一方的期待寫成一份契約，然後兩方各自用這份契約測試：呼叫的一方叫 consumer（例如 App），被呼叫的一方叫 provider（例如菜單 API）。消費者驅動契約（consumer-driven contract，CDC）是指契約由 consumer 的測試產生：consumer 實際用到什麼，契約就寫什麼，一行不多。Pact 是最常用的 CDC 工具，契約叫 pact 檔，是一份 JSON。

它補上的正是示範問題的缺口：前端的 mock 不再是前端自己寫、自己相信的假資料，而是一份會被後端 CI 驗證的契約。後端把 priceTwd 改名，後端自己的 CI 就會失敗，問題在合併前被發現，而且很清楚是誰改壞了誰。

Pact consumer 測試：描述互動、呼叫真的 client

以下用 @pact-foundation/pact 17.1.4（這門課鎖的版本）。它的核心是 Rust 寫的原生程式，npm install 時依你的電腦下載（第 2 課裝過）。consumer 測試描述一個互動（interaction）：在什麼前提下、收到什麼請求、要回什麼回應。

import { MatchersV3, PactV4, SpecificationVersion } from '@pact-foundation/pact'
const { eachLike, like, integer } = MatchersV3

const pact = new PactV4({ consumer: 'CoffeeApp', provider: 'MenuAPI', dir, spec: SpecificationVersion.SPECIFICATION_VERSION_V4 })

await pact.addInteraction()
  .given('菜單有六個商品')                        // provider state
  .uponReceiving('查詢菜單')                       // 這個互動的名稱
  .withRequest('POST', '/graphql', b => b.jsonBody({ query: MENU_QUERY }))
  .willRespondWith(200, b => b.jsonBody({
    data: { menu: eachLike({ id: like('2'), name: like('拿鐵'), priceTwd: integer(110) }) },
  }))
  .executeTest(async server => {
    const menu = await fetchMenu(server.url)       // 真的 client 程式打 mock server
    assert.deepEqual(menu[0], { id: '2', name: '拿鐵', priceTwd: 110 })
  })
  • provider state：given('菜單有六個商品') 是一個前提的名稱。provider 驗證時，會先呼叫同名的處理函式把資料準備好，再重播請求。
  • GraphQL 就是 HTTP POST：請求寫成 POST /graphql 加 JSON body，跟第 2 課用 curl 送的一樣。Pact 另外有 GraphQL 專用的輔助類別，但它內部用自己的一份 graphql 16，跟我們的 graphql 17 混用容易出錯，這門課直接寫 HTTP 互動。
  • matcher：like(值) 表示「型別跟範例值一樣就好」，integer(值) 要求整數，eachLike(樣板) 表示「一個陣列，至少一筆，每一筆都長得像樣板」。範例值只用在 mock server 的回應裡。
  • executeTest：Pact 在 127.0.0.1 的隨機 port 開 mock server，把網址傳進來。測試裡一定要呼叫真的 client 程式（fetchMenu），並斷言它的回傳。自己另外寫一段 fetch 的話，契約描述的就是那段假程式，不是 App。測試結束時，Pact 檢查每個描述過的請求都真的收到了，然後把 pact 檔寫進 dir。

matcher 要多嚴是這裡最重要的判斷。全部寫死（priceTwd: 110），等於宣稱「App 依賴拿鐵賣 110 元」：店裡一漲價，provider 驗證就失敗，但 App 其實沒壞。用 like 包住整個物件則比較鬆：like 只比 JSON 型別，provider 把 priceTwd 回成字串 "110" 會被擋，回成小數 110.5 卻會通過。App 依賴的是「整數」（例如拿來算總價）時，就用 integer 寫清楚。原則：契約描述 consumer 依賴的事，型別與形狀用 matcher，只有真的依賴具體值時（例如 status 一定是幾個值之一）才寫死。

Pact provider 驗證：重播請求給真的伺服器

provider 端不用寫任何互動，只要把真的伺服器開起來，交給 Verifier：

import { Verifier } from '@pact-foundation/pact'

const { server, store } = createMenuApi()
const { url } = await listen(server)             // helpers/http.ts：listen(0)，結束時自動關
await new Verifier({
  provider: 'MenuAPI',
  providerBaseUrl: url,
  pactUrls: [pactFile],                          // 本機檔案；用 Broker 時改成 Broker 的設定
  stateHandlers: {
    '菜單有六個商品': async () => { store.products = PRODUCTS.map(p => ({ ...p })) },
  },
}).verifyProvider()                              // 有互動不符就 reject

Verifier 對每個互動：先呼叫名稱相同的 state handler，再把 pact 檔裡的請求送給 providerBaseUrl，用 matcher 規則比對回應，印出每一項的結果。名稱要一字不差，找不到 handler 時資料沒準備好，結果就跟預期不同。state handler 準備的是 provider 自己的測試資料（記憶體裡的 store、測試資料庫），不要指向正式環境。

把 provider 的 priceTwd 改名再跑一次，Verifier 會指出回應的商品少了 priceTwd，verifyProvider() reject，後端的 CI 失敗。這一步要讓它真的失敗：catch 起來印個 log 就等於沒有驗證。

Pact 執行時預設會送出匿名的使用統計。練習的起始程式已經設好 PACT_DO_NOT_TRACK=true；在公司專案裡，CI 的環境變數也要設。
💡 實務上：契約測試是兩個團隊之間的約定
工具裝好不代表導入成功。分工通常是：前端（consumer）寫 consumer 測試、維護契約；後端（provider）在自己的 CI 跑驗證、維護 state handler；provider state 的名稱兩邊一起定，當成共用的詞彙。驗證失敗時先看是哪一種：後端真的改壞了，還是契約寫得太嚴（寫死了值、要求了 App 根本沒用的欄位）。後者要回頭改 consumer 測試，不是讓後端遷就。導入時先挑一個最常出事的互動（例如菜單或結帳），讓 provider 端的驗證穩定跑起來，再慢慢擴大。

契約怎麼交換：Broker、can-i-deploy 與 schema registry

這一課的 pact 檔放在同一個資料夾，consumer 寫、provider 直接讀。前端與後端在不同 repo、各自部署時，pact 檔需要一個交換的地方：

  • Pact Broker（開源，自己架）／PactFlow（商業版）：consumer 的 CI 把 pact 檔連同版本號發布上去；provider 的 CI 從 Broker 取得「所有 consumer 的契約」來驗證，並把結果回報。consumer 發布新契約時，Broker 可以用 webhook 觸發 provider 的驗證。
  • can-i-deploy：Broker 提供的檢查，部署前問「我這個版本，跟正式環境上的每個對方版本都驗證過了嗎？」沒有就不部署。這解決了「各自部署」的順序問題：App 要用新欄位，必須等 provider 的新版先上線。
  • schema registry：集中存放 schema 的每個版本，發布時做相容性檢查，並記錄誰在用。GraphQL 有 Hive、Apollo GraphOS（加上欄位使用量回報，就能回答「price 還有沒有人用」）；protobuf 有 Buf Schema Registry（buf breaking --against-registry 直接跟 registry 上的版本比）；Kafka 這類事件系統有 Confluent Schema Registry，搭配 Avro 或 Protobuf，producer 送出不相容的事件格式時直接被拒絕（系統設計課第 16 課的事件也需要契約）。

什麼規模才需要：少數幾個人、單一 repo、前後端一起部署時，CI 裡跑 schema 比對（findSchemaChanges、buf breaking），pact 檔 commit 進 repo 就夠了，不用另外維運一套服務。多個 repo、多個團隊、服務各自部署，開始出現「我不知道誰在用這個欄位」「不知道能不能先部署」的問題時，才導入 Broker 或 registry。

取捨：契約測試不是什麼

  • 它不是功能測試：它只驗證「consumer 寫進契約的那些請求，provider 回應的形狀對不對」，不驗證價格算得對不對、庫存扣得對不對。那些是 provider 自己的測試的責任。
  • 它只涵蓋寫進契約的部分：App 有十個畫面，只為菜單寫了契約，其他九個畫面依賴的欄位照樣可能被改壞。契約的價值跟覆蓋率成正比，通常先從最重要、最常出事的互動開始。
  • GraphQL 已經有 schema：GraphQL 的大部分相容問題用「schema 比對 + 操作清單」就能抓到，Pact 在 GraphQL 上主要補的是 schema 看不到的語意（例如 provider state 下的資料形狀、錯誤回應）。REST、webhook 這類沒有強制 schema 的 API，Pact 的收益最大。
  • gRPC：Pact 要另外安裝 protobuf plugin（執行時下載）才能描述 gRPC 互動。這門課的 gRPC 用另一條路：共用同一份 .proto 產生兩邊的程式碼，加上 buf breaking 守住相容性。

練習

在 learn/ 執行 node check.mjs api-styles 10，四題都在 api-styles/practice/work/10/（第一次做這門課的練習，先照第 2 課安裝套件）。四題互相獨立。練習 3、4 的 Pact 測試一次要幾秒到十幾秒；檔名刻意沒有 .test，由 ex3.test.ts、ex4.test.ts 執行它們再檢查結果，你也可以在 work/10 自己執行 node --test pact-consumer.ts。

練習 1：schema-v1.graphql 是線上的版本（不要改），evolve.graphql 是下一版。需求：Product.price 改名為 priceTwd: Int!；Order.status 從字串改成 enum OrderStatus（PREPARING、READY、PICKED_UP），新欄位叫 state: OrderStatus!。用不破壞舊版 App 的方式完成：舊欄位的名稱與型別不變，加上 @deprecated，reason 要寫出替代的新欄位名稱。resolvers.ts 的資料列形狀不能改（資料裡只有 price 與小寫的 status），替新欄位寫 resolver。測試用 findSchemaChanges 確認沒有破壞性變更，拿舊版 App 的 10 個查詢在兩份 schema 上執行，結果要一模一樣，再查新欄位的值（資料每次隨機）。

練習 2：完成 schema-check.ts 的 checkSchema(oldSdl, newSdl, operations)，回傳 { ok, breaking, unusedRemovals }。物件型別被移除的欄位，用兩份 schema 的 getFields() 比對找出來（不要解析 description 字串）：沒有任何 operation 用到的，座標（'Product.description'）排序後放進 unusedRemovals，不影響 ok；有人在用的放進 breaking（字串要帶出座標）。其他變更用 findSchemaChanges 判斷，只有 BreakingChangeType 的放進 breaking（用它的 description 即可），危險與安全的都不擋。ok 是 breaking 為空。使用情況用 visit + visitWithTypeInfo 走過每份操作，fragment 裡用到的也算。測試用 9 組變更比對（包含不同型別上的同名欄位），被移除的欄位與操作順序每次不同。

練習 3：在 pact-consumer.ts 為 menuClient.ts 的 fetchMenu(baseUrl) 寫 Pact consumer 測試（menuClient.ts 不用改）。互動要有 provider state 菜單有六個商品，請求是 POST /graphql、body 是 { query: MENU_QUERY }；回應的 data.menu 用 eachLike，id、name 用 like，priceTwd 用 integer。在 executeTest 裡呼叫真的 fetchMenu(server.url)，並斷言它回傳的第一個商品。測試會檢查產生的 pacts/CoffeeApp-MenuAPI.json、確認請求是從 menuClient.ts 發出的，還會把 mock server 的回應換成空菜單再跑一次，那次你的測試要失敗。

練習 4：在 pact-provider.ts 用 Verifier 驗證 pacts/CoffeeApp-MenuAPI.json：用 provider.ts 的 createMenuApi() 建立 server 與 store（不用改它，store 一開始是空的），用 helpers/http.ts 的 listen(server) 啟動（port 0），providerBaseUrl 用它回傳的 url；stateHandlers 處理 菜單有六個商品，把 PRODUCTS 放進 store.products；驗證結束後關掉 server。測試會先寫入一份標準的 pact 檔（不依賴練習 3），執行你的驗證要通過；再把 provider 的 priceTwd 改名成 price 跑一次，那次要失敗；兩次程序都要自己結束。

練習 5：GraphQL API 通常不像 REST 那樣用 /v2/ 做版本，主要原因是？

✓ 回應的形狀由客戶端的查詢決定，所以加欄位永遠安全；真正會弄壞人的變更（刪除、改名、改型別）用「新增 → deprecate → 看使用量 → 移除」處理。URL 當然可以改（a 錯），只是沒有必要；客戶端不會自動適應，刪掉它在用的欄位，整個查詢在驗證階段就被拒絕（c 錯）；用 header 帶版本也不是 GraphQL 的慣例（d）。

練習 6：前端用 mock 測試、後端有自己的整合測試，都全部通過，上線還是壞了。契約測試補上的是哪一塊？

✓ mock 是 consumer 對 provider 的假設，沒有人驗證它。契約測試把假設寫成 pact 檔，交給 provider 用真的伺服器重播，假設錯了在合併前就失敗。它只驗證介面期待，不測畫面（a）、效能（c）或商業邏輯與資料正確性（d），那些仍然要各自的測試。

練習 7：Pact 的回應全部寫死成具體值（name: '拿鐵'、priceTwd: 110，不用 matcher），後果是？

✓ 契約描述「consumer 依賴什麼」。App 依賴的是「有一個整數的 priceTwd」，不是「拿鐵等於 110」。寫死會讓 provider 動不了資料，契約測試變成到處誤報，最後大家不信任它。Pact 允許寫死（c 錯），consumer 端也會通過（d 錯），問題出在 provider 驗證。

練習 8：小團隊、單一 repo、前後端同一批人一起部署。關於 API 相容性，最先該做的是？

✓ 工具的成本要配合規模。單一 repo 裡，CI 直接從 main 分支拿到舊 schema 比對；Broker 與 registry 解決的是「多 repo、各自部署時，誰在用、能不能先部署」，現在還沒有這個問題（a）。同一批人也會漏（c），而且行動 App 的舊版本不受「一起部署」影響。換成 gRPC 不會自動相容，改編號、改型別一樣會壞（d）。

常見錯誤

  • 直接改名或改型別：舊客戶端的查詢在驗證階段就失敗。先新增新欄位、舊欄位 deprecate，確認沒人用再移除。
  • deprecate 之後馬上刪：網頁前端換新了，但舊版 App 還在使用者手機上。用欄位使用量決定什麼時候刪，不要用日期猜。
  • @deprecated 不寫 reason：前端只看到 No longer supported，不知道該改用什麼。
  • 用文字比對 SDL 判斷相容性：分不出輸出欄位變非空（安全）和參數變必填（破壞性），也會把排版改動當成變更。用 findSchemaChanges。
  • 把危險變更當成破壞性變更擋下：enum 加值這類變更擋下，團隊就會想辦法繞過檢查。在 PR 上提醒、通知前端即可。
  • 只靠端對端測試確保相容：慢、不穩、太晚發現，而且看不出是誰改壞的。
  • Pact 回應全部寫死值：provider 一改資料就失敗。用 like、integer、eachLike。
  • Pact 測試裡沒呼叫真正的 client 程式：契約變成手寫的假資料，跟 App 實際送出的請求無關。
  • provider 驗證時 catch 掉錯誤：驗證永遠「通過」，契約形同虛設。
  • state handler 名稱跟 given(...) 對不上：資料沒準備好，驗證失敗的原因看起來像 provider 壞了。
  • 把契約測試當功能測試：它只驗證介面期待，不驗證計算結果。
  • 一開始就導入 Broker／registry：先在 CI 做 schema 比對，等到多 repo、各自部署時再加。

小結

  • 破壞性變更是讓現有客戶端壞掉的變更。GraphQL 不做 URL 版本，改名、改型別都走「新增 → @deprecated(reason) → 看使用量 → 移除」；行動 App 讓「確認沒人用」可能要好幾個月。
  • findSchemaChanges（graphql 17）把變更分成 breaking、dangerous、safe；CI 只擋 breaking。有前端的操作清單時，用 visit + TypeInfo 找出被使用的欄位，沒人用的欄位就能放心移除。
  • proto 用 buf breaking --against 跟 main 比對，類別依呼叫方式選（WIRE、WIRE_JSON、FILE）。
  • Pact：consumer 測試描述互動（provider state、請求、matcher 描述的回應），讓真的 client 打 mock server，產生 pact 檔；provider 用 Verifier 依 state 準備資料、重播請求、比對回應。matcher 描述依賴的形狀與型別，不寫死值。
  • Pact Broker、can-i-deploy、schema registry 解決多 repo、各自部署時的交換與部署順序問題；小團隊先從 CI 比對開始。
