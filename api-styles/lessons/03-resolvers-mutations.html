階段 2：GraphQL 基礎 · 第 3 課

Resolver 與 mutation：每個欄位都是一個函式

上一課的 schema 說明「有哪些欄位」，但資料從哪裡來？訂單資料表只存 customer_id，前端查的卻是 order { customer { name } }；資料庫欄位叫 unit_price，schema 叫 unitPrice；「目前登入的是誰」要從請求標頭讀出來。這些都由 resolver 處理：schema 裡的每個欄位背後都是一個函式，GraphQL 一層一層呼叫它們，把結果組成回應。

這課的路線：
  1. 執行模型與四個參數：resolver 怎麼由上往下被呼叫，customer_id 怎麼變成 customer { name }（開場問題的最小答案）。
  2. context：「目前登入的是誰」這種每個請求自己的資料放哪，放錯會讓使用者看到別人的資料。
  3. Mutation 與預期中的失敗：下單怎麼寫，「拿鐵賣完了」該丟錯、回 userErrors 還是用 union。
  4. 錯誤與 null 傳播：一個欄位出錯，為什麼可能讓整張訂單變成 null，schema 怎麼設計來控制範圍。
  5. 服務層與交易：下單邏輯放哪才能讓 REST 端點、排程共用，兩個人搶最後 3 杯拿鐵時怎麼不超賣。
這課會用到：
  • 第 2 課的 schema 與 Yoga：用 SDL 宣告型別和欄位，yoga.fetch 不開 port 就能送一個請求給伺服器。
  • TypeScript 課第 16 課的可辨識聯合：每個成員有一個共同欄位（例如 kind）標明自己是哪一種，判斷它就能縮小型別。
  • PostgreSQL 課第 18 課的交易：中間的修改一起生效或一起取消，失敗時回滾。

在 learn/ 執行 node check.mjs api-styles 03，會建立 api-styles/practice/work/03/（還沒安裝套件的話，先照第 2 課開頭的步驟 npm install）。裡面有：

  • db.ts：放在記憶體裡的咖啡店資料庫（不用改）。欄位照資料庫習慣用 snake_case（customer_id、unit_price），方法都是 async，跟真的資料庫一樣要 await。
  • schema.graphql、resolvers.ts、context.ts、orders.ts、nulls.ts：四題練習要改的檔案。server.ts 把它們組成 Yoga 伺服器（不用改）。
  • examples/：這一頁的範例，在 work/03 執行。

執行模型：由上往下，一個欄位呼叫一次

resolver 是負責算出一個欄位值的函式。Yoga 的 createSchema 收一個 resolvers 物件，結構是「型別名稱 → 欄位名稱 → 函式」。執行查詢時，GraphQL 從根型別開始，先呼叫 Query.order，拿到訂單後再呼叫 Order 底下被選到的欄位，拿到品項後再往下，直到每個欄位都是純量為止。執行 node examples/trace.ts：

// examples/trace.ts（節錄）
resolvers: {
  Query: {
    order: (_parent, args, ctx, info) => ctx.db.orderById(args.id),
  },
  Order: {
    items: (order, _args, ctx) => ctx.db.itemsByOrder(order.id),
  },
  OrderItem: {
    product: (item, _args, ctx) => ctx.db.productById(item.product_id),
  },
}
Query.order  path=["order"]  args = {"id":"1"}
Order.items  path=["order","items"]  parent = {"id":"1","customer_id":"1","ordered_at":"2026-10-01T08:30:00.000Z"}
OrderItem.product  path=["order","items",0,"product"]  parent.product_id = 1
OrderItem.product  path=["order","items",1,"product"]  parent.product_id = 5

Order.id、OrderItem.quantity、Product.name 沒有寫 resolver，GraphQL 用預設 resolver（default resolver）：直接回傳 parent[欄位名稱]，如果那是函式就呼叫它。所以資料庫的欄位名稱跟 schema 一樣時，什麼都不用寫；名稱不同（ordered_at 對 orderedAt）或要用別的資料查（customer_id 查出整個顧客），才自己寫。

resolver 可以回傳值，也可以回傳 Promise，GraphQL 會等它完成再往下。上面每張訂單的每個品項都各查一次商品：10 張訂單、每張 3 個品項就是 30 次查詢，這是下一課的 N+1 問題，這一課先把正確性做對。

四個參數：parent、args、context、info

每個 resolver 都收到同樣的四個參數（graphql 17 與 Yoga 6 相同）：

參數是什麼咖啡店的例子
parent（也叫 root、source）上一層 resolver 的回傳值Order.customer 收到訂單那一列，用 parent.customer_id 查顧客
args這個欄位在查詢裡收到的參數，已經依 schema 驗證、轉好型別Query.order 的 args.id
context同一個請求裡所有 resolver 共用的物件，每個請求一份{ db, viewer }：資料存取物件與目前登入的顧客
info這次執行的結構資訊：欄位名稱、父型別、路徑、選了哪些子欄位info.path（trace.ts 印出來的 path）

info 平常用不到，知道有它就好；第 4 課的取捨會提到用它看「前端選了哪些欄位」再決定要不要 JOIN。用不到的參數照慣例用底線開頭（_parent、_args），因為參數靠位置對應，後面的參數要用時前面的不能省略。

欄位不必等於資料庫的欄位。練習 1 的 schema：

type OrderItem {
  product: Product
  quantity: Int!
  unitPrice: Int!
}

type Order {
  id: ID!
  orderedAt: String!
  customer: Customer
  items: [OrderItem!]!
  total: Int!
}
  • 改名：orderedAt: (order) => order.ordered_at。GraphQL 慣例用 camelCase，資料庫慣例用 snake_case，在 resolver 轉換，不要為了少寫幾行把 snake_case 露在 API 上。
  • 關聯：customer: (order, _args, ctx) => ctx.db.customerById(order.customer_id)。回傳整個顧客物件，GraphQL 再往下用預設 resolver 取 name。回傳 order.customer_id（字串）是常見錯誤：GraphQL 會在字串上找 name，得到 undefined。
  • 計算出來的欄位：total 不存在資料表裡，由品項的 quantity × unit_price 加總。用 unit_price（下單當下的價格）而不是商品現在的 price：拿鐵下個月漲價，上個月的訂單金額不能跟著變。顯示用的欄位也可以這樣做，例如 priceLabel 用 Intl.NumberFormat 格式化成「NT$110」（TypeScript 課第 6 課）。

關聯欄位 customer、product 刻意沒有 !，原因在後面的「錯誤與 null 傳播」。

context：每個請求一份

context 放的是「這個請求」才有的東西：目前登入的使用者、資料存取物件、第 4 課的 DataLoader。Yoga 每收到一個請求就呼叫一次 context 函式，參數裡有標準的 Request（request）和解析好的 GraphQL 參數（params，含 query、variables），回傳值會和這兩個合併，交給這個請求的每個 resolver 當第三個參數：

// server.ts
export function buildYoga(db: Db) {
  return createYoga({ schema, context: ({ request }) => createContext(request, db), logging: false })
}

這門課用 x-customer-id 標頭當作假的登入（真正的認證在 auth 課）。起始的 context.ts 把顧客 id 存在模組變數：

// ✗ 模組變數：整個程序只有一份，所有請求共用
export let currentCustomerId: string | null = null

export async function createContext(request: Request, db: Db) {
  currentCustomerId = request.headers.get('x-customer-id')
  return { db }
}

// resolvers.ts
myOrders: async (_parent, _args, ctx) =>
  (await ctx.db.listOrders()).filter(o => o.customer_id === currentCustomerId),

一次只有一個請求時看起來正常。但 Node 在同一個程序裡同時處理很多請求（Node 課第 7 課）：

順序王小明的請求陳美華的請求currentCustomerId
1createContext 設成 11
2await listOrders()，等資料庫1
3createContext 設成 22
4資料回來，用 currentCustomerId 過濾2：王小明看到陳美華的訂單

只要 await 之後才讀模組變數，就可能讀到別人寫的值。這種 bug 在本機測不出來，上線後流量一大才偶爾出現，而且是個資外洩。修正方式是把使用者放進 context，resolver 只從 context 讀：

export async function createContext(request: Request, db: Db): Promise<Context> {
  const id = request.headers.get('x-customer-id')
  const viewer = id ? await db.customerById(id) : null
  return { db, viewer }
}

// resolvers.ts
me: (_parent, _args, ctx) => ctx.viewer,

沒登入時 viewer 是 null，me 回 null：沒登入是正常情況，不是錯誤。至於「沒登入不能看某些欄位」的授權規則，第 6 課再講。

不經過 resolver 參數、又想取得「目前這個請求」的資料（例如 log 裡的 request id），Node 用 AsyncLocalStorage（Node 課第 19 課）。GraphQL 的 resolver 本來就收 context，業務資料直接用 context 傳最清楚。
💡 實務上：review 時看到模組層級的 let 就要問「這是誰的資料」
這類 bug 在本機、在一次只送一個請求的測試裡都不會出現，上線後偶爾有客服回報「我看到別人的訂單」，又重現不出來。資深工程師在 code review 時會特別看模組最外層的 let、可變的 Map、單例物件的屬性：裡面放的如果是「某個使用者、某個請求」的資料，就要搬進 context。要驗證修好了，就像練習 2 的測試那樣，讓兩個不同使用者的請求故意交錯執行，而不是只送一個請求看結果。這類事件牽涉個資，發生時要通知資安評估影響範圍。

Mutation：input、payload，頂層欄位依序執行

前面的 resolver 都在讀資料，下單則要寫入。mutation 是會改變資料的操作，寫在根型別 Mutation 底下。語法跟查詢一樣，只是開頭寫 mutation：

input OrderLineInput {
  productId: ID!
  quantity: Int!
}

input PlaceOrderInput {
  items: [OrderLineInput!]!
}

type Mutation {
  placeOrder(input: PlaceOrderInput!): PlaceOrderResult!
}
  • 參數用一個 input 型別包起來（input: PlaceOrderInput!），之後要加欄位（例如外帶／內用）只要在 input 加一個可選欄位，不用改 mutation 的參數列，前端的舊程式也不會壞。
  • 回傳的是 payload：專門給這個 mutation 用的結果型別，而不是直接回傳 Order。結果裡可以放訂單，也可以放「為什麼失敗」，下一節說明。
  • 客戶端送 mutation PlaceOrder($input: PlaceOrderInput!) { placeOrder(input: $input) { … } }，變數 { "input": { "items": [{ "productId": "2", "quantity": 1 }] } }。

執行順序有一條規則：Query 的欄位可以同時執行，Mutation 的頂層欄位一定依序執行（GraphQL 規格規定；graphql 17 的執行器遇到 mutation 就改成逐一執行）。執行 node examples/serial.ts，同一個會等待的欄位，a 等 100 ms、b 等 10 ms：

query：
  開始 a
  開始 b
  結束 b
  結束 a
mutation：
  開始 a
  結束 a
  開始 b
  結束 b

所以同一份操作裡寫 a: placeOrder(…) b: placeOrder(…)，一定是 a 做完才做 b。但它們不在同一個交易裡：b 失敗時 a 已經寫入、不會回滾。需要「全部成功或全部失敗」，就設計成一個 mutation 收一整批資料，由伺服器在一個交易裡處理。

預期中的失敗：丟錯、userErrors，還是 union

下單會失敗：數量填 0、拿鐵賣完了。這些不是 bug，是預期中的失敗，App 要依情況顯示不同畫面（「拿鐵只剩 2 杯」）。常見三種做法：

做法回應長什麼樣子客戶端
A. 丟錯{ data: null, errors: [{ message: "庫存不足", extensions: { code: "OUT_OF_STOCK" } }] }要從 errors 裡找代碼、解析訊息字串；「還剩幾杯」只能塞進 extensions，沒有型別
B. userErrors 欄位{ placeOrder: { order: null, userErrors: [{ field: "items.1", code: "OUT_OF_STOCK", message: "…" }] } }錯誤在 schema 裡、有型別；但 order 和 userErrors 哪個有值要靠約定
C. union 結果型別{ placeOrder: { __typename: "OutOfStock", productId: "2", available: 2 } }用 __typename 分支，每種結果有自己的欄位；codegen 產生的型別會強迫處理每一種

做法 B 在 Shopify 等公開 API 很常見，也完全可行。這門課採用 C，因為它就是 TypeScript 課第 27 課的 Result（用回傳值表示預期中的失敗，不丟錯）：預期中的失敗是資料，放進 schema 才有型別、才能被檢查。errors 陣列留給非預期的錯誤（bug、資料庫連不上）和請求本身不合法（沒登入）。

union 表示「這個欄位會回傳這幾種物件型別之一」：

type OrderPlaced { order: Order! }
type OutOfStock { productId: ID!  available: Int! }
type InvalidQuantity { productId: ID!  quantity: Int! }

union PlaceOrderResult = OrderPlaced | OutOfStock | InvalidQuantity

union 的成員沒有共同欄位，客戶端要用 inline fragment（... on 型別）分別選，再加上每個物件都有的內建欄位 __typename（型別名稱）來判斷是哪一種，跟可辨識聯合用 kind 判斷一樣：

mutation PlaceOrder($input: PlaceOrderInput!) {
  placeOrder(input: $input) {
    __typename
    ... on OrderPlaced { order { id total } }
    ... on OutOfStock { productId available }
    ... on InvalidQuantity { productId quantity }
  }
}

伺服器那邊，GraphQL 也要知道 resolver 回傳的物件是哪個型別。兩種寫法擇一（graphql 17.0.2、Yoga 6.0.1）：

  • 物件自己帶 __typename：graphql-js 的預設型別判斷會讀它。服務層回傳 TypeScript 的可辨識聯合時最自然：{ __typename: 'OutOfStock', productId, available }。
  • 在 resolvers 寫 PlaceOrderResult: { __resolveType: (obj) => 'order' in obj ? 'OrderPlaced' : … }。

兩個都沒有時，執行到這個欄位會出錯：Abstract type "PlaceOrderResult" must resolve to an Object type at runtime …。另一種抽象型別 interface（有共同欄位的一組型別，例如 interface Node { id: ID! }）判斷方式相同，本課程用不到。

💡 實務上：錯誤怎麼回，要在第一支 mutation 就跟前端約定好
同一個 API 裡有的 mutation 丟錯、有的回 userErrors、有的回 union，前端每支都要寫不同的處理，很快就會漏。開始寫第一支 mutation 時，就跟前端（Vue、App）一起定下規則：預期中的失敗用哪種做法、型別怎麼命名（OutOfStock、InvalidQuantity）、哪些情況才進 errors，寫進團隊的 API 規範。另外要提醒前端：之後在 union 加一種新結果（例如 StoreClosed），graphql 17.0.2 的 findSchemaChanges 會把它列為 dangerous（不是 breaking）的變更，因為舊版 App 不認得新的 __typename；所以前端的 switch 一定要有預設分支（例如顯示「下單失敗，請稍後再試」）。schema 演進在第 10 課。

錯誤與 null 傳播

resolver 丟錯時，GraphQL 不會讓整個請求失敗：那個欄位變成 null，錯誤放進 errors，帶著完整的 path（從根到出錯欄位的路徑，清單用數字索引），其他欄位照常回傳。這叫部分成功（partial success）。執行 node examples/errors.ts：第二個品項的商品查不到、promo 連不上資料庫、banner 丟出 GraphQLError：

200 {
  "errors": [
    { "message": "Unexpected error.", "path": ["order", "items", 1, "product"], "extensions": { "code": "INTERNAL_SERVER_ERROR" } },
    { "message": "Unexpected error.", "path": ["promo"], "extensions": { "code": "INTERNAL_SERVER_ERROR" } },
    { "message": "今天的活動還沒開始", "path": ["banner"] }
  ],
  "data": {
    "order": { "id": "1", "items": [{ "quantity": 1, "product": { "name": "拿鐵" } }, { "quantity": 2, "product": null }] },
    "promo": null,
    "banner": null
  }
}

一般的 Error 被 Yoga 換成 Unexpected error.：這是 Yoga 預設的錯誤遮罩（masked errors），避免把 10.0.0.5:5432 這種內部資訊傳給客戶端，原本的錯誤記在伺服器 log。想讓客戶端看到的訊息用 graphql 的 GraphQLError 丟出。錯誤代碼與遮罩的細節在第 5 課。

上面的 product 可以是 null，所以錯誤只影響它自己。如果欄位是非空（!），GraphQL 不能放 null 進去，只好把它的父物件變成 null；父物件也是非空，就再往上，直到遇到可以是 null 的位置。這叫 null 傳播（null bubbling）。如果一路冒到根，整個 data 就是 null。

預測的步驟：找到丟錯的欄位 → 它可以是 null 嗎？可以就停；不行就換成它的父層再問一次。清單要多問一層：[OrderItem!] 的元素不能是 null，所以先換成整個清單；[Order] 的元素可以是 null，就停在那一格。path 一律指向丟錯的那個欄位，不是 null 停下來的位置。

設計上的結論：關聯欄位與「可能查不到」的欄位讓它可以是 null，錯誤就只影響局部；id、名稱這種跟物件同生共死的欄位才加 !。這也是第 2 課提醒「不確定就不加 !」的原因。

💡 實務上：「訂單頁整片空白」先看 errors 的 path
客服回報某位顧客的訂單頁一片空白、其他人正常，常見原因就是 null 傳播：那張訂單的某個商品已經下架、查不到，非空的 product 把整張訂單變成 null。查的時候先看伺服器 log 或回應裡 errors[].path，它直接指出出錯的欄位與清單索引，再對照 schema 找 null 停在哪裡。修法是把那個關聯改成可以是 null，但已上線的輸出欄位拿掉 !，graphql 17.0.2 的 findSchemaChanges 會列為 breaking（FIELD_CHANGED_KIND）：前端 codegen 的型別多出 null，舊程式可能直接讀 product.name 而出錯，要跟前端一起改。所以關聯在設計時就讓它可為 null 最省事。前端也要能顯示「部分資料＋這一格載入失敗」，不要一看到 errors 就整頁顯示錯誤。

resolver 只是入口：下單邏輯放在服務層、在交易裡

下單要做的事：檢查數量、檢查每個商品的庫存、扣庫存、寫訂單與品項。把這些全寫在 Mutation.placeOrder 裡，之後後台的 REST 端點或排程也要下單時，只能複製一份。照 NestJS 課第 18 課的分層：resolver 只負責轉接，商業邏輯放在服務層（orders.ts）：

// resolvers.ts
Mutation: {
  placeOrder: (_parent, args, ctx) => {
    if (!ctx.viewer) throw new GraphQLError('請先登入再下單', { extensions: { code: 'UNAUTHENTICATED' } })
    return placeOrder(ctx.db, ctx.viewer.id, args.input.items)
  },
},

服務層有三個容易做錯的地方：

  • 先全部檢查，再全部寫入。一行一行「檢查、扣庫存」，第二行庫存不足時第一行已經扣了。回傳 OutOfStock 是正常回傳，不是丟錯，交易照樣提交，所以檢查一定要放在任何寫入之前。
  • 同一個商品出現在兩行（先點 3 杯拿鐵、又加 2 杯）：數量要加總後再跟庫存比。
  • 檢查到寫入之間要在同一個交易裡。兩個人同時買最後 3 杯拿鐵：兩邊都查到「還有 3 杯」、都通過檢查、都扣 3 杯，就超賣了。db.ts 提供 db.transaction(async tx => …)：同一時間只執行一個交易，fn 丟錯時修改全部還原。真的 PostgreSQL 用 SELECT … FOR UPDATE 鎖住那幾列，或用 UPDATE … SET stock = stock - $1 WHERE stock >= $1 讓資料庫判斷（PostgreSQL 課第 18 課、第 19 課）。
// orders.ts（架構）
export type PlaceOrderResult =
  | { __typename: 'OrderPlaced', order: OrderRow }
  | { __typename: 'OutOfStock', productId: string, available: number }
  | { __typename: 'InvalidQuantity', productId: string, quantity: number }

export async function placeOrder(db: Db, customerId: string, lines: OrderLine[]): Promise<PlaceOrderResult> {

  return db.transaction(async tx => {
    // 2. 合計每個商品的數量，逐一跟 tx.stockOf() 比，不夠就 return OutOfStock
    // 3. 全部通過：tx.takeStock()、tx.insertOrder()，return OrderPlaced
  })
}

服務層回傳的是 TypeScript 的可辨識聯合，__typename 剛好就是 GraphQL 的型別名稱，resolver 直接把它交出去；同一個函式從 REST 端點呼叫時也能用 switch (result.__typename) 處理。

💡 實務上：庫存規則先跟 PM 問清楚，再寫交易
超賣通常不是平常出事，而是限量商品開賣、節日促銷這種很多人同時搶的時候。動手寫之前，先跟 PM 確認一件程式替不了的事：一張單裡只有一項不夠時，是整張單失敗，還是其他品項照常成立？這會決定 OutOfStock 要帶哪些欄位、前端要顯示什麼。review 時資深工程師會檢查兩點：「檢查庫存」和「扣庫存」是不是在同一個交易裡；有沒有像練習 3 那樣讓兩個請求同時搶最後幾份的測試。邏輯很短、只有 GraphQL 一個入口的小功能，不用急著拆服務層；但下單這種後台、排程也會用到的流程，一開始就該拆。

練習

四題都在 api-styles/practice/work/03/，執行 node check.mjs api-styles 03。每題的測試自己準備 context（隨機產生的訂單、顧客名稱、價格），所以可以不按順序做。想用 curl 試：node examples/serve.ts 會用範例資料開在 4000 port，curl -X POST http://localhost:4000/graphql -H 'content-type: application/json' -H 'x-customer-id: 1' -d '{"query":"{ me { name } myOrders { id total } }"}'。

練習 1：在 resolvers.ts 補完 Order 與 OrderItem 的 resolver：Order.orderedAt（資料表的 ordered_at）、Order.customer（用 customer_id 查出顧客物件）、Order.items（這張訂單的品項）、Order.total（Σ quantity × unit_price）、OrderItem.product、OrderItem.unitPrice。資料一律從 context.db 取得（方法列在 db.ts 的 Db 型別）。測試用隨機資料查出整棵訂單樹逐欄比對，而且在建好訂單之後把商品漲價：total 要用下單當下的 unit_price。

練習 2：修掉「目前顧客存在模組變數」的問題。context.ts 的 createContext(request, db) 從 x-customer-id 標頭查出顧客，回傳 { db, viewer }（記得更新 Context 型別）；resolvers.ts 的 Query.me 回傳 viewer、Query.myOrders 回傳這位顧客的訂單（db.ordersByCustomer），都只從 context 讀。沒帶標頭或顧客不存在時，me 是 null、myOrders 是 []，不要丟錯。測試會讓第一個請求在等資料庫時，第二位顧客的請求整個跑完，確認兩邊各自拿到自己的資料；也會把每位顧客的請求同時送出、再連續送不同顧客的請求。所以「在 resolver 一開始、await 之前先讀模組變數」也過不了：另一個請求的 createContext 可能在你的 resolver 執行前就改掉它。

練習 3：實作下單。schema.graphql 加上本頁的 OrderLineInput、PlaceOrderInput、OrderPlaced、OutOfStock、InvalidQuantity、union PlaceOrderResult 與 type Mutation { placeOrder(input: PlaceOrderInput!): PlaceOrderResult! }。orders.ts 的 placeOrder(db, customerId, lines)：任何一行的數量不是 1–20 的整數，回傳 InvalidQuantity（第一個有問題的那一行）；同一個商品的數量合計超過庫存，回傳 OutOfStock（available 是目前庫存）；全部通過才扣庫存、用商品目前的 price 當 unitPrice 寫入訂單，回傳 OrderPlaced。失敗時什麼都不能改；檢查與寫入放在同一個 db.transaction 裡，用 tx 操作。resolvers.ts 加上 Mutation.placeOrder：沒登入（viewer 是 null）先檢查、丟 GraphQLError（直接讀 ctx.viewer.id 會丟 TypeError，被遮罩成 Unexpected error.，前端看不出原因），其他交給 orders.ts。測試會檢查這些預期中的結果都在 data 裡、errors 是空的，並讓兩個請求同時搶最後的庫存。

練習 4：在 nulls.ts 寫出四個案例的預測：回應的 data，以及 errors[0].path。測試會真的執行這四份 schema 並比對。每個案例只有一個 resolver 丟錯：

練習 5：為什麼 context 要每個請求建立一份，而不是在模組裡放一個 let currentUser？

✓ Node 的一個程序同時服務很多請求；只要在 await 之後讀模組變數，就可能讀到另一個請求寫進去的值。每個請求自己的狀態放在 context（或 AsyncLocalStorage）。每次建立反而多做一點事，不是為了快（a）；規格沒有這種規定（c）；export let 是合法的 TypeScript（d）。

練習 6：schema 是 order(id: ID!): Order、items: [OrderItem!]!、product: Product!。其中一個品項的 OrderItem.product resolver 丟錯，結果最接近？

✓ 非空的位置不能放 null，null 往上找最近的可為 null 的位置：Product! → OrderItem!（清單元素）→ […]! → Order。a 是 product 可為 null 時的結果；b 要元素型別是 [OrderItem]。執行階段的錯誤是 200 加上 errors（帶完整 path），不是 500（d）。

練習 7：「庫存不足」用 union 的 OutOfStock 回傳，而不是丟錯，主要好處是？

✓ 跟 Result 型別一樣，預期中的失敗是資料，放進 schema 才有型別、能被檢查。errors 只有訊息字串和 extensions，而且一般 Error 還會被 Yoga 遮罩成 Unexpected error.。大小差不多（a）；丟錯只讓那個欄位變 null，伺服器不會當掉（c）；mutation 當然可以丟錯，例如沒登入（d）。

練習 8：同一份操作寫了 mutation { a: placeOrder(…) b: placeOrder(…) }，b 庫存不足。下列何者正確？

✓ 規格規定 Mutation 的頂層欄位依序執行（a 錯），但每個欄位各自執行，沒有共同的交易（c 錯）。兩個欄位都會執行（d 錯）。需要整批成功或整批失敗，就設計成一個 mutation 收整批資料。

常見錯誤

  • 用模組變數存目前的使用者：並行的請求互相覆蓋，看到別人的資料。放進每個請求的 context。
  • 關聯欄位回傳 id：customer: (o) => o.customer_id 讓 GraphQL 在字串上找 name。回傳整個物件。
  • 計算金額用商品現價：歷史訂單的金額會跟著漲價。用下單時記下的 unit_price。
  • 預期中的失敗只丟錯：客戶端只能解析訊息字串，訊息還可能被遮罩。用 union 或 userErrors。
  • 邊檢查邊寫入：第二行失敗時第一行已經改了；回傳失敗結果不是丟錯，交易不會回滾。先全部檢查，再全部寫入，整段放在交易裡。
  • 把商業邏輯寫在 resolver：其他入口（REST、排程）要用時只能複製。resolver 只做轉接，邏輯放服務層。
  • 關聯欄位全部加 !：一個關聯出錯，整個父物件跟著消失。讓關聯欄位可以是 null，把錯誤局部化。
  • 以為同一份操作裡的多個 mutation 是同一個交易：它們只是依序執行。需要原子性就設計成一個 mutation。
  • union 的物件沒有 __typename，也沒寫 __resolveType：執行時報 Abstract type must resolve to an Object type。擇一補上。

小結

  • schema 的每個欄位背後都是一個 resolver，GraphQL 由根往下逐層呼叫，上一層的回傳值是下一層的 parent；沒寫的欄位用預設 resolver 取 parent[欄位名稱]。
  • 四個參數：parent、args、context（每個請求一份，放使用者與資料存取物件）、info（結構資訊，少用）。
  • resolver 負責轉換：snake_case 轉 camelCase、用 id 查出關聯物件、算出不存在資料表裡的欄位。
  • mutation 用 input 型別收參數、回傳 payload；頂層欄位依序執行，但不共用交易。
  • 預期中的失敗設計成 union 結果型別（或 userErrors），用 __typename 區分；errors 陣列留給非預期的錯誤。
  • resolver 丟錯時該欄位變 null，非空欄位的 null 往上傳到最近的可為 null 的位置；關聯欄位可為 null，錯誤才局部化。
  • 下單邏輯放在服務層：先全部檢查、再全部寫入，檢查到寫入在同一個交易裡。
