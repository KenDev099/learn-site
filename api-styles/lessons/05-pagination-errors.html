階段 2：GraphQL 基礎 · 第 5 課

分頁與錯誤：cursor connection、錯誤遮罩與錯誤代碼

老顧客王小明在 App 裡打開「我的訂單」，往下滑載入更多。他有三百張訂單，一次全拿太慢，所以要分頁。用最直覺的「第幾頁」做法，他滑到第二頁時店裡剛好成立一張新訂單，結果第二頁的第一筆就是剛才看過的那一筆。另一個問題出在錯誤：資料庫欄位改名之後，查詢失敗的錯誤訊息連同表名、欄位名一起回到了 App 上。

這課的路線：
  1. OFFSET 的問題與 keyset 分頁：翻頁途中有新訂單時為什麼重複一筆，改成「從上一頁最後一筆之後開始」就不會。
  2. Relay Connection 與游標：GitHub、Shopify 都在用的分頁欄位形狀，游標為什麼要不透明、收到時要驗證。
  3. 錯誤分三類：哪些錯誤讓客戶端看到、哪些只寫進 log，為什麼出錯時 HTTP 還是 200。
  4. 錯誤遮罩與 extensions.code：SQL 錯誤不外流，前端依穩定的代碼決定畫面，客服回報時靠 request id 查 log。
這課會用到：
  • 第 3 課的部分成功：resolver 丟錯時那個欄位變成 null、錯誤放進 errors，其他欄位照常回傳；預期中的失敗放進 schema 的結果型別。
  • PostgreSQL 課第 5 課的 ORDER BY、LIMIT、OFFSET：先排序，跳過前幾筆，再取固定筆數。
  • PostgreSQL 課第 27 課的複合索引：索引照多個欄位依序排好，查詢的條件和排序對得上時，資料庫直接從某個位置往下讀。
  • Node 課第 18 課的兩種錯誤：可預期的錯誤（商品不存在、欄位填錯）是需求的一部分，要處理並回清楚的訊息；程式錯誤（bug）不該發生，要記下完整資訊去修。

示範問題：OFFSET 分頁遇到新訂單

offset 分頁就是 LIMIT 20 OFFSET 40：依排序跳過前 40 筆，取接下來 20 筆。第 N 頁的 OFFSET 是 (N - 1) × 每頁筆數，前端只要記住頁碼。在 learn/ 執行 node check.mjs api-styles 05 建立 work/05/（第一次做這門課的練習，先照第 2 課安裝套件），再到 work/05 執行 node examples/offset.ts：

// examples/offset.ts（節錄）：王小明的訂單，一頁 2 筆
const offsetPage = (offset: number) => db.query(
  'SELECT id, ordered_at FROM orders WHERE customer_id = 1 ORDER BY ordered_at DESC, id DESC LIMIT 2 OFFSET $1', [offset])
第 1 頁： #7 #3
…王小明又下了一張訂單…
OFFSET 2 的第 2 頁： #3 #1
keyset 的第 2 頁（從 #3 之後）： #1

反過來，翻頁途中刪掉前面的一筆，整串往前移一格，就會漏看一筆。另一個問題是效能：OFFSET 10000 時資料庫還是要先找出並丟掉前 10000 列，用 EXPLAIN 看得到掃過的列數隨頁數變多（PostgreSQL 課第 21 課）。

offset 分頁不是不能用：後台報表要「跳到第 37 頁」、資料幾乎不變、總筆數不多時，它最簡單。會一直新增的列表（訂單、動態、通知）和無限捲動，就用下一節的 keyset。

keyset 分頁：從上一頁最後一筆之後開始

keyset 分頁（也叫游標分頁，cursor pagination）不記「第幾筆」，而是記住上一頁最後一筆的排序鍵，下一頁從它之後開始。訂單由新到舊排序，第 1 頁最後一筆是 (ordered_at = 2026-10-21 09:00, id = 3)，第 2 頁就是：

SELECT id, customer_id, ordered_at, total FROM orders
WHERE customer_id = $1
  AND (ordered_at, id) < ($2, $3)        -- 上一頁最後一筆的 ordered_at 與 id
ORDER BY ordered_at DESC, id DESC
LIMIT $4                                 -- 每頁筆數 + 1
  • 為什麼要加 id：排序鍵必須唯一。同一秒可能成立好幾張訂單，只寫 WHERE ordered_at < $2，跟最後一筆同時間、還沒顯示的訂單會被 < 一起排除，永遠看不到。加上唯一的 id 當第二排序鍵，每一筆的位置就是唯一的。
  • (a, b) < (x, y) 是列比較（row comparison）：先比 a，相等時再比 b，等於 a < x OR (a = x AND b < y)。ORDER BY 的方向和比較符號要一致：DESC 用 <，ASC 用 >。
  • 多拿一筆判斷有沒有下一頁：一頁要 10 筆就 LIMIT 11，拿到 11 筆代表還有下一頁，只回傳前 10 筆。用「拿到的筆數等於 10」判斷的話，總數剛好是 10 的倍數時，最後會多一頁空白頁。
  • 索引：建 (customer_id, ordered_at DESC, id DESC) 的複合索引（PostgreSQL 課第 27 課），資料庫直接從游標的位置往下讀 11 筆，第 1 頁和第 1000 頁一樣快。

keyset 的代價：不能直接跳到第 37 頁、很難算「共幾頁」，排序方式要事先決定（每種排序都要有對應的索引）。手機的無限捲動本來就只需要「下一頁」，正好適合。

💡 實務上：分頁方式要在設計畫面時就跟 PM、前端講好
App 的「我的訂單」是無限捲動，用 keyset；後台的訂單管理常要「跳到第 37 頁」和「共 1,234 筆」，這是 offset 的長處。設計稿出來時先問：要頁碼還是「載入更多」？要不要總筆數？能依哪些欄位排序、篩選？每多一種排序就多一個索引，總筆數的 COUNT(*) 在大表上也不便宜。在 GraphQL 裡可以把總數做成獨立欄位（例如 totalCount），只有查詢有選這個欄位時它的 resolver 才會執行，App 不選就不用付這個成本。

Relay Connection：GraphQL 分頁的通用形狀

keyset 的查詢寫好了，接著決定 schema 裡的分頁欄位長什麼樣子。Relay 是 Meta 的 GraphQL 客戶端，它規定了一種分頁欄位的形狀，叫 Connection。這個慣例成了業界通用寫法，GitHub、Shopify 的 GraphQL API 都用它，前端的 Apollo、urql 也有對應的快取工具，就算不用 Relay 也照這個形狀設計：

type Customer {
  id: ID!
  name: String!
  orders(first: Int = 10, after: String): OrderConnection!
}

type OrderConnection {
  edges: [OrderEdge!]!
  pageInfo: PageInfo!
}

type OrderEdge {
  cursor: String!   # 這一筆的位置
  node: Order!      # 這一筆的資料
}

type PageInfo {
  hasNextPage: Boolean!
  endCursor: String  # 這一頁最後一筆的 cursor；沒有資料時是 null
}
  • edge（邊）：清單裡的一筆，包著資料 node 和它的位置 cursor。多包一層的好處是可以放「關係本身」的資訊，例如 FriendEdge.since。
  • first／after：「從 after 這個游標之後，取 first 筆」。第一頁不給 after。
  • pageInfo：hasNextPage 決定要不要顯示「載入更多」，endCursor 是下一次請求的 after。

前端的用法：

query MyOrders($id: ID!, $after: String) {
  customer(id: $id) {
    orders(first: 10, after: $after) {
      edges { cursor node { id orderedAt total } }
      pageInfo { hasNextPage endCursor }
    }
  }
}
# 第一次 variables: { "id": "1" }
# 載入更多 variables: { "id": "1", "after": 上一次的 pageInfo.endCursor }

first 一定要有上限，例如 50：沒有上限，有人送 first: 100000 就讓資料庫一次查十萬筆，等於阻斷服務。超過時回錯誤（下面的 BAD_USER_INPUT），不要默默改成 50，客戶端才知道自己拿到的不是要求的數量。巢狀的清單還會相乘，第 6 課的查詢成本限制會再處理。

完整的 Relay 規範裡，PageInfo 有四個欄位：hasNextPage、hasPreviousPage、startCursor、endCursor，參數還有往前翻的 last／before，做法是同一個 keyset 查詢把排序反過來。訂單歷史只需要往後翻，練習只做 first／after 和兩個 PageInfo 欄位；要給 Relay 客戶端用時，四個欄位都要補上（只往後翻時 hasPreviousPage 依規範可以回 false）。規範也允許 first: 0，只有負數要報錯。

游標要不透明，而且要驗證

游標（cursor）是代表「某一筆在排序中的位置」的字串。keyset 分頁的位置就是 (ordered_at, id)，所以游標把這兩個值編碼成一個字串：

encodeCursor({ orderedAt: '2026-10-21T01:00:00.000Z', id: '3' })
// JSON.stringify → '["2026-10-21T01:00:00.000Z","3"]'
// base64url     → 'WyIyMDI2LTEwLTIxVDAxOjAwOjAwLjAwMFoiLCIzIl0'

不透明游標（opaque cursor）的意思是：客戶端只能原樣傳回，不應該解析內容。base64url 不是加密，任何人都解得開，它的目的是讓客戶端不要依賴內容。這樣日後把排序改成 (total, id)、或游標裡多放一個欄位，客戶端都不用改。直接用訂單 id 當游標，前端很快就會開始寫 after: String(lastId)，之後就改不動了，而且只有 id 也做不了「時間相同時用 id 比」的 keyset 查詢。

用 base64url（Auth 課第 2 課）而不是 base64：base64 會出現 +、/、=，放進網址的查詢字串要再跳脫，+ 還會被當成空白。base64url 只用 A–Z a–z 0–9 - _，Node 寫成 Buffer.from(s).toString('base64url')。

游標來自客戶端，所以是不可信的輸入，解碼時要逐層檢查：

  1. 字元只能是 base64url 的字元。Buffer.from(s, 'base64url') 遇到不合法的字元會直接略過、不會丟錯，所以要先用正規表示式檢查。
  2. JSON.parse 會丟 SyntaxError，要 try/catch。
  3. 能 parse 不代表內容對：要是長度 2 的陣列，時間和 id 都是字串。
  4. 值要是資料庫一定接受的：這兩個值會放進 SQL，PostgreSQL 不接受的值會在 SQL 才出錯，變成 Unexpected error.。只用 Date.parse 檢查不夠：Date.parse('1') 是 2001 年、2 月 30 日會被轉成 3 月 2 日，PostgreSQL 卻會拒絕。所以時間要是 toISOString() 的格式（2026-10-21T01:00:00.000Z），而且 new Date(t).toISOString() === t；id 是數字組成的字串，而且不超過 orders.id（integer）的上限 2147483647。
  5. 任何一步失敗，都丟同一個錯誤：BAD_USER_INPUT，訊息只說「游標無效」，不帶出 JSON.parse 的內部訊息。
時間的精度：PostgreSQL 的 timestamptz 存到微秒（小數點後 6 位），JavaScript 的 Date 只到毫秒（3 位）。用 now() 寫入的 09:00:00.123456 變成游標時會被截成 09:00:00.123，下一頁的 (ordered_at, id) < (09:00:00.123, …) 就把同一微秒時間、id 較小的訂單排除掉了。寫入時就截到毫秒（DEFAULT date_trunc('milliseconds', now())），游標裡的時間才會和資料庫裡的一模一樣。練習的訂單時間都是毫秒，不會遇到。

游標裡不放任何跟權限有關的資料，例如 customer_id。伺服器仍然以目前登入的使用者決定能看哪些訂單：別人拿到王小明的游標，也只是在自己的訂單裡定位。這部分在第 6 課的授權會再談。

💡 實務上：游標會失效，前端要能從第一頁重來
游標只在「同一個排序、同一組篩選條件」下有意義。使用者把排序從「最新」切到「金額最高」、或改了篩選，前端要丟掉手上的 endCursor 從第一頁重新載入。後端改了游標格式（例如排序鍵多一個欄位）再部署時，還開著 App 的使用者會送來舊格式的游標，伺服器回 BAD_USER_INPUT，前端看到這個代碼就重新載入第一頁，使用者頂多感覺列表刷新了一次。改游標格式前，先跟前端確認這條路徑真的有做。

錯誤分三類，處理方式各不同

游標無效時要丟錯。丟哪一種錯、客戶端會看到什麼，要先把錯誤分類。第 3 課看過：resolver 丟錯時那個欄位變成 null、錯誤放進 errors，其他欄位照常回傳（部分成功）；一般的 Error 會被 Yoga 換成 Unexpected error.。這一課把錯誤整理成三類：

類別例子誰處理客戶端看到
請求錯誤（解析、驗證、變數型別）拼錯欄位、first: "abc"Yoga 在執行前擋下（第 2 課）只有 errors，沒有 data；application/graphql-response+json 時 HTTP 400（application/json 時是 200），驗證錯誤的 code 是 GRAPHQL_VALIDATION_FAILED
預期中的錯誤沒登入、沒權限、游標無效、first 超過上限；庫存不足你的程式：丟 GraphQLError 帶代碼，或像第 3 課放進 schema 的結果型別保留訊息與 extensions.code
非預期錯誤SQL 錯誤、程式 bug、下游服務掛了錯誤遮罩：對外換掉，原錯誤寫進 logUnexpected error.、code INTERNAL_SERVER_ERROR

「庫存不足」這種使用者能處理、畫面要有對應設計的結果，第 3 課放進 schema 的 union 裡，因為它是資料、有型別。GraphQLError 適合橫跨所有欄位的情況：沒登入、沒權限、參數不合法，任何一個欄位都可能遇到，前端用同一套程式處理。

執行階段的錯誤（後兩類）HTTP 狀態仍是 200：GraphQL over HTTP 規格（草案）規定，請求已經開始執行，回應裡就可能同時有 data 和 errors，所以用 200。前端不能只看狀態碼，要同時看 data 和 errors（第 7 課的客戶端也是如此）。

💡 實務上：只看 HTTP 5xx 的監控會漏掉 GraphQL 的錯誤
維運常用「5xx 比例」當告警，但 GraphQL 的執行錯誤是 200，資料庫整個掛掉時儀表板可能還是一片綠。接上 GraphQL 時要另外依 errors[].extensions.code 計數：INTERNAL_SERVER_ERROR 的比例拿來告警，UNAUTHENTICATED、BAD_USER_INPUT 只看趨勢（突然暴增可能是前端改壞了，或有人在亂試）。計數時同時記下操作名稱（operation name，例如上面的 query MyOrders 裡的 MyOrders），才知道是哪個畫面出問題。

錯誤遮罩：不要把 SQL 錯誤回給客戶端

錯誤遮罩（error masking）是不把內部錯誤的訊息（SQL、表名、檔案路徑、stack）回給客戶端。這些資訊對使用者沒用，對攻擊者卻是資料庫結構的地圖。graphql-yoga 6.0.1 預設開啟。執行 node examples/masking.ts：

// examples/masking.ts（節錄）
salesReport: () => { throw new Error('column "total" does not exist (SELECT sum(total) FROM orders)') },
myOrders: () => { throw new GraphQLError('請先登入', { extensions: { code: 'UNAUTHENTICATED' } }) },
200 {
  "errors": [
    { "message": "Unexpected error.", "path": ["salesReport"], "extensions": { "code": "INTERNAL_SERVER_ERROR" } },
    { "message": "請先登入", "path": ["myOrders"], "extensions": { "code": "UNAUTHENTICATED" } }
  ],
  "data": { "menu": ["美式咖啡", "拿鐵"], "salesReport": null, "myOrders": null }
}

Yoga 怎麼分辨？每個錯誤都會經過 maskError(error, message, isDev)：用 graphql 套件的 GraphQLError 丟出的錯誤原樣保留，其他錯誤換成新的 GraphQLError('Unexpected error.')，並加上 extensions.code: 'INTERNAL_SERVER_ERROR'。NODE_ENV=development 時，它會把原錯誤放進 extensions.originalError 方便開發，所以正式環境一定要設 NODE_ENV=production（或不設）。

被遮罩的錯誤一定要記錄下來，不然 bug 就消失了。Yoga 預設會用自己的 logger 記，但正式專案通常有自己的 logger（Node 課第 19 課的結構化 log，帶 request id）。做法是自訂 maskError，裡面呼叫 Yoga 匯出的 maskError 保留預設行為：

import { GraphQLError } from 'graphql'
import { createYoga, maskError } from 'graphql-yoga'

createYoga({
  schema,
  logging: false,                    // 關掉 Yoga 自己的 log，改用我們的 logger
  maskedErrors: {
    maskError(error, message, isDev) {
      const masked = maskError(error, message, isDev)
      if (masked !== error) {         // 被換掉了 → 非預期錯誤
        logger.error(error instanceof GraphQLError && error.originalError ? error.originalError : error)
      }
      return masked
    },
  },
})
  • resolver 丟出的錯誤到這裡時，已經被 graphql-js 包成帶 path 的 GraphQLError，原本的錯誤在 error.originalError。記錄原錯誤才有完整的 SQL 訊息和 stack。
  • 只記被遮罩的那些：沒登入、游標無效是預期中的情況，記成 error 會讓告警被雜訊淹沒。
  • maskedErrors: false 會把所有錯誤原樣回傳。不要為了除錯關掉它；除錯靠 log 和 tracing（devops 課），不靠回應內容。
💡 實務上：客服說「App 顯示發生錯誤」，靠 request id 找回原錯誤
遮罩之後，使用者和客服只看得到 Unexpected error.，真正的原因只在伺服器 log。所以每個請求要有一個 request id：寫進每一行 log（Node 課第 19 課），也放在回應標頭讓前端記錄或顯示在錯誤畫面上（例如「錯誤編號 7f3a…」）。客服回報時附上這個編號，工程師就能直接在 log 找到那一筆原錯誤、SQL 和 stack，不用重現。log 裡可能有個資與 SQL，誰能看 log 也要跟資安一起管。
不要在 resolver 裡 try { … } catch { return null } 吞掉錯誤。errors 是空的，客戶端以為「營業額沒有資料」，監控也看不到任何錯誤，問題要等到有人發現數字不對才會被注意到。讓錯誤丟出去，交給遮罩和 log 處理。

錯誤代碼：extensions.code

GraphQL 規範的錯誤物件只有 message、locations、path，另外保留一個 extensions 欄位讓伺服器放額外資訊。業界習慣在 extensions.code 放一個穩定的錯誤代碼，客戶端依代碼處理，不解析訊息文字：訊息會改寫、會翻譯，代碼不會變。

throw new GraphQLError('請先登入', { extensions: { code: 'UNAUTHENTICATED' } })
代碼意思前端通常怎麼做
UNAUTHENTICATED沒登入或 token 過期導到登入頁、或先換新 token 再重送
FORBIDDEN登入了，但沒有權限顯示「沒有權限」，不要重試
BAD_USER_INPUT參數的值不合法（型別對，但內容不行）顯示訊息；游標無效時從第一頁重新載入
INTERNAL_SERVER_ERROR非預期錯誤（被遮罩）顯示通用錯誤、可以讓使用者重試

這組代碼不是 GraphQL 規範定義的，是 Apollo Server 流傳開來的慣例，Yoga 的 INTERNAL_SERVER_ERROR、GRAPHQL_VALIDATION_FAILED 也沿用。團隊要把代碼清單寫進文件，當成契約的一部分：改代碼跟改欄位一樣，會弄壞依賴它的前端。代碼的取捨跟 REST 的狀態碼相同（Node 課第 14、18 課），只是放的位置不一樣。

練習

在 learn/ 執行 node check.mjs api-styles 05，三題都在 api-styles/practice/work/05/。練習 2、3 都 import 練習 1 的 cursor.ts，請先完成練習 1。每次執行測試都會產生不同的訂單與商品資料。

練習 1：完成 cursor.ts。encodeCursor({ orderedAt, id }) 把 [orderedAt, id] 用 JSON 再 base64url 編碼成字串；decodeCursor(s) 把它還原成 { orderedAt, id }。decodeCursor 遇到任何不合法的輸入（有 base64url 以外的字元、解碼後不是 JSON、不是長度 2 的陣列、時間不是 toISOString() 的格式或轉回去不一樣、id 不是數字組成的字串或超過 2147483647），都要丟 graphql 的 GraphQLError，extensions.code 是 BAD_USER_INPUT，訊息不能帶出 JSON.parse 的錯誤內容。測試會來回編解碼 200 組隨機值，再試十幾種壞掉的游標。

練習 2：把顧客的訂單歷史改成 keyset 分頁。schema.graphql：照本頁加上 OrderConnection、OrderEdge、PageInfo，把 Customer.orders 改成 orders(first: Int = 10, after: String): OrderConnection!。orders.ts 的 ordersConnection(db, customerId, { first, after })：依 ordered_at DESC, id DESC 排序；first 沒給時是 10，不是 0–50 的整數就丟 BAD_USER_INPUT；after 用練習 1 的 decodeCursor 解碼，從它之後開始；每一頁只能有一句查 orders 的 SQL，不能用 OFFSET；hasNextPage 用多拿一筆判斷；每個 edge 的 cursor 用 encodeCursor 產生，endCursor 是最後一筆的 cursor。server.ts 已經把 resolver 接好，不用改。測試讓每 3 張訂單同一個時間，逐頁翻完並在翻到一半時新增一筆訂單，檢查不重複、不遺漏、順序正確。

練習 3：修好 errors.ts 的錯誤處理。requireViewer 沒登入時丟 GraphQLError，code UNAUTHENTICATED；requireStaff 不是店員時丟 FORBIDDEN，兩個都保留給使用者看的訊息。createApp 的 maskedErrors 改成自訂的 maskError：呼叫 graphql-yoga 匯出的 maskError，被遮罩的錯誤呼叫一次 logger.error(原錯誤)，預期中的錯誤不記錄。測試把 orders.total 欄位改名讓 salesReport 的 SQL 失敗，檢查回應裡沒有任何 SQL 內容、是 Unexpected error.／INTERNAL_SERVER_ERROR、menu 仍然有資料，logger.error 只收到 SQL 錯誤一次；另外檢查沒登入、沒權限、壞游標各自的代碼。

練習 4：訂單歷史用 OFFSET 分頁，使用者翻頁時店裡持續成立新訂單。會發生什麼？

✓ OFFSET 依「第幾筆」定位，前面多一筆，整串就往後移一格，上一頁最後一筆變成下一頁第一筆；刪除時則反過來漏掉一筆。keyset 依「上一頁最後一筆的值」定位，不受新增、刪除影響。分頁的 SELECT 不會鎖表（c）；條件有 customer_id，不會看到別人的（d）。

練習 5：keyset 分頁只用 ORDER BY ordered_at DESC，下一頁的條件是 WHERE ordered_at < $1。會出什麼問題？

✓ ordered_at 不唯一。上一頁最後一筆是 09:00 的 #3，同樣 09:00 的 #2 還沒顯示，< 09:00 就把它排除了。排序鍵要加上唯一的 id，用 (ordered_at, id) < ($1, $2) 列比較，並建對應的複合索引。時間重複很常見（a 錯）；有索引時 keyset 比大 OFFSET 快（c 錯）；游標長度跟這個問題無關（d）。

練習 6：resolver 裡資料庫丟出含 SQL 與表名的一般 Error，graphql-yoga 用預設設定。客戶端看到的是？

✓ Yoga 預設開啟錯誤遮罩：不是 GraphQLError 的錯誤，訊息被換成 Unexpected error.，原錯誤記在伺服器端。執行階段的錯誤只讓那個欄位變 null（部分成功），HTTP 仍是 200（b 錯）。要讓客戶端看到訊息，就刻意用 GraphQLError 丟出並加上 extensions.code。

常見錯誤

  • 會一直新增的列表用 OFFSET：翻頁途中有新資料就重複，刪除就漏掉，頁數越後面越慢。用 keyset。
  • 排序鍵不唯一：只用 ordered_at，同時間的資料在換頁時被跳過。加上 id，用列比較 (ordered_at, id) < ($1, $2)。
  • 用「拿到的筆數等於 first」判斷有下一頁：總數剛好整除時多一頁空白頁。多拿一筆。
  • 游標是可猜的原始 id：客戶端開始依賴內容，之後改不了排序；也少了排序鍵。用不透明編碼，並把它當不可信的輸入驗證。
  • first 沒有上限：一個請求就能讓資料庫查十萬筆。設上限，超過回 BAD_USER_INPUT。
  • 用 base64 而不是 base64url：+ / = 放進網址要跳脫，+ 還會變成空白。
  • 關掉錯誤遮罩方便除錯，結果上線：SQL 與表名直接回到客戶端。用 log 和 tracing 除錯，不要靠回應。
  • 預期中的錯誤丟一般的 Error：被遮罩成 Unexpected error.，前端分不出是沒登入還是伺服器壞了。用 GraphQLError 加 extensions.code。
  • 在 resolver catch 所有錯誤回傳 null：客戶端以為沒資料，監控也看不到錯誤。
  • 每個錯誤都記成 error log：沒登入、參數錯誤是正常情況，混進去會讓真正的錯誤被淹沒。只記被遮罩的。

小結

  • OFFSET 依位置定位，資料一變動就重複或漏掉，而且越後面越慢；keyset 依上一頁最後一筆的排序鍵定位，排序鍵要唯一（加上 id），配合複合索引。
  • Relay Connection：edges { cursor node }、pageInfo { hasNextPage endCursor }、first／after；first 有上限，多拿一筆判斷下一頁。
  • 游標是不透明的 base64url 字串，客戶端原樣傳回；伺服器把它當不可信的輸入逐層驗證，壞掉時回 BAD_USER_INPUT。
  • 錯誤分三類：請求錯誤（Yoga 執行前擋下）、預期中的錯誤（GraphQLError ＋ extensions.code，或 schema 的結果型別）、非預期錯誤（遮罩成 Unexpected error.，原錯誤寫進 log）。
  • 執行階段的錯誤 HTTP 仍是 200，一個欄位失敗、其他欄位照常有資料；客戶端要同時看 data 和 errors，依代碼處理。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：前端部署新版後，菜單頁整頁空白。回應只有 errors，完全沒有 data 這個鍵。先查什麼？

✓ 沒有 data 代表根本沒進到執行：解析或驗證失敗，例如欄位拼錯、用了後端還沒上線的欄位、變數型別比參數寬鬆，任何 resolver 都沒被呼叫。a 錯在 resolver 丟錯屬於執行階段，回應會有 data，出錯的欄位是 null，旁邊是 errors。（第 2 課）

練習 8：新設計的訂單 schema 如下。商品下架後查不到，OrderItem.product 丟錯，那位顧客的訂單頁就整片空白。怎麼設計，其他品項才會照常顯示？

order(id: ID!): Order
type Order { items: [OrderItem!]! }
type OrderItem { product: Product! }

✓ resolver 出錯時那個欄位變 null，非空的位置放不下，就往上找最近可為 null 的位置。product 可為 null，錯誤就局部化在那一個品項，前端顯示「這一格載入失敗」。a 反而更糟：order 也不能是 null，null 冒到最上層，整個 data 變 null。已上線的輸出欄位拿掉 ! 是破壞性變更，所以關聯在設計時就讓它可為 null。（第 3 課）

練習 9：viewer 已經照第 3 課放進 context，loader 則為了「省下建立成本」在程式啟動時建一次。上線後會出什麼事？

const loaders = createLoaders(db)   // 程式啟動時建立一次

export async function createContext(request: Request): Promise<Context> {
  const id = request.headers.get('x-customer-id')
  const viewer = id ? await db.customerById(id) : null
  return { db, viewer, loaders }
}

✓ DataLoader 的快取只是記憶化：同一個 key 拿同一個 Promise，沒有過期、不認得使用者，設計上一個請求一份。改成在 createContext 裡呼叫 createLoaders(db)。b 是最常見的誤判：單一請求的測試全部通過，要送兩個請求、中間改資料才測得出來。（第 4 課）

練習 10：顧客一張單點了拿鐵和可頌，拿鐵庫存夠、可頌不夠。這段下單程式的結果是？

return db.transaction(async tx => {
  for (const line of lines) {
    const stock = await tx.stockOf(line.productId)
    if (stock < line.quantity) return { __typename: 'OutOfStock', productId: line.productId, available: stock }
    await tx.takeStock(line.productId, line.quantity)
  }
  return { __typename: 'OrderPlaced', order: await tx.insertOrder(customerId, lines) }
})

✓ 交易只有在函式丟錯時才還原；回傳 OutOfStock 是正常回傳，前面扣掉的拿鐵跟著提交。改成先把每一行都檢查完，全部通過才扣庫存、寫訂單，檢查和寫入仍在同一個交易裡。a 錯在把「回傳失敗結果」當成「丟錯」。（第 3 課）

練習 11：後台訂單列表本機很快，上線後要好幾秒，而且訂單越多越慢；慢查詢 log 裡卻找不到任何一句慢的 SQL。先查什麼？

✓ 每句都快、加起來卻慢，而且跟清單長度成正比，是 N+1 的典型特徵：每句還要走一次到資料庫的網路來回。先數句數，對照 1 + N + N + 品項數，再用 DataLoader 把每一層合成一句。a 查的是單句慢，慢查詢 log 已經排除了這個可能。（第 4 課）

練習 12：訂單列表用這個 loader 載入顧客名稱。哪裡會出事？

const customerById = new DataLoader<number, CustomerRow | null>(async ids => {
  return db.query<CustomerRow>('SELECT id, name FROM customers WHERE id = ANY($1)', [ids])
})

✓ DataLoader 依位置把結果分回去，回傳陣列要跟 keys 一樣長、一樣順序。先放進 Map，再用 ids.map(id => byId.get(id) ?? null) 對回去。本機資料剛好齊全、順序剛好一樣時會一直通過。a 是在 batch 函式裡逐筆查詢的寫法，這裡只有一句。（第 4 課）

練習 13：App 的「我的訂單」是無限捲動；後台的訂單管理要「跳到第 37 頁」和「共 1,234 筆」。分頁怎麼選？

✓ keyset 依上一頁最後一筆的排序鍵定位，新增、刪除都不影響，配合複合索引每頁一樣快，但不能直接跳頁。後台要頁碼就用 OFFSET，接受翻頁途中可能錯位。a 錯在去重只處理新增造成的重複，翻頁途中有訂單被刪除時，OFFSET 會漏掉一筆，去重救不回來。（第 5 課）

練習 14：requireViewer 寫成 if (!ctx.viewer) throw new Error('請先登入')。Vue 端看到 extensions.code 是 UNAUTHENTICATED 就導去登入頁，但沒登入的使用者卻看到「系統錯誤」。為什麼？

✓ 遮罩只放過 GraphQLError；預期中的錯誤要刻意用 GraphQLError 丟出並帶 extensions.code，客戶端才能依代碼處理。d 是最危險的「修法」：關掉遮罩會把 SQL 與表名也一起回給客戶端，除錯要靠 log。（第 5 課）
