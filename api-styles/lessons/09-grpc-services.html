階段 4：gRPC 與 Protobuf · 第 9 課

gRPC 服務：unary、串流、deadline 與狀態碼

上一課用 protobuf 定義了庫存的訊息。這一課讓它真的跑起來：訂單服務下單前要問庫存服務「拿鐵還有幾杯」「幫我保留 2 杯」，店內看板要即時看到庫存變化。這些是服務之間的同步呼叫，咖啡店選了 gRPC（第 1 課的決策表）。

寫出能回應的伺服器不難，難的是出事時的行為：庫存服務卡住時，訂單服務要等多久？使用者已經放棄了，庫存服務還在查資料庫嗎？錯誤要回什麼，呼叫端才知道該不該重試？

這課的路線：
  1. 定義服務與 Connect-ES：四種 RPC 各適合什麼情境，寫出庫存服務的伺服器與 client（開場問題的最小答案）。
  2. 狀態碼：庫存不足、服務重啟各回哪個碼，呼叫端的重試機制靠它決定要不要重試。
  3. deadline 與取消傳遞：訂單服務最多等多久，使用者放棄後怎麼讓庫存服務的查詢也停下來。
  4. 串流：店內看板即時看到庫存變化，client 斷線時怎麼把監聽清乾淨。
  5. metadata、interceptor 與互通：request id、憑證這種每個呼叫都要帶的資訊放哪，出問題時怎麼用 buf curl、grpc-js 除錯。
這課會用到：
  • 第 8 課的 protobuf：在 .proto 寫訊息，buf generate 產生 TypeScript 程式碼；proto3 不送等於預設值的欄位。
  • 系統設計課第 8 課的逾時與重試：每個呼叫都要有逾時，重試要退避加隨機；deadline 是整條呼叫鏈共用的時間預算。
  • TypeScript 課第 11 課的 AbortSignal：AbortController 發出取消，把 signal 交給 fetch 這類函式，它們收到 abort 就停下並丟錯。
  • TypeScript 課第 10 課的 async generator：async function* 每 yield 一次交出一個值，呼叫端用 for await 一個一個拿。

定義服務：四種 RPC

在 learn/ 執行 node check.mjs api-styles 09，會建立 api-styles/practice/work/09/（還沒安裝套件的話，先照第 2 課開頭的步驟 npm install），並先執行 buf generate 產生 gen/（每次跑測試前都會重產，改了 .proto 不用自己記得）。這一課的契約在 proto/coffee/inventory/v1/inventory.proto。上一課只有 message，這一課多了 service：

service InventoryService {
  rpc GetStock(GetStockRequest) returns (GetStockResponse);          // unary
  rpc Reserve(ReserveRequest) returns (ReserveResponse);             // unary
  rpc WatchStock(WatchStockRequest) returns (stream WatchStockResponse);  // server streaming
  rpc Restock(stream RestockRequest) returns (RestockResponse);      // client streaming
}

service 是一組方法，每個方法叫一個 RPC（remote procedure call，遠端程序呼叫）：呼叫端寫起來像呼叫本機函式，實際上請求經過網路送到另一個程序。stream 寫在哪一邊，決定了 RPC 的種類：

種類寫法意思咖啡店的例子
unary(A) returns (B)一個請求、一個回應，最常見查庫存、保留庫存
server streaming(A) returns (stream B)一個請求，伺服器陸續送多個回應店內看板訂閱拿鐵的庫存變化
client streaming(stream A) returns (B)客戶端陸續送多個請求，伺服器最後回一個倉庫掃描進貨，一箱送一筆，最後回總數
bidirectional streaming(stream A) returns (stream B)雙方同時陸續送，互不等待POS 與庫存服務即時同步（少用）

預設用 unary。串流適合「資料本來就是陸續產生的」情況；用串流傳一個大清單，通常不如分頁的 unary 好維護。另外注意命名：buf lint 的 STANDARD 規則要求每個 RPC 有自己的 XxxRequest／XxxResponse，所以串流回的是 WatchStockResponse，不是直接回 StockLevel。這樣之後要在串流訊息加欄位（例如變動原因），不會影響別的 RPC。

buf generate 除了 message，還會在 gen/coffee/inventory/v1/inventory_pb.js 產生 InventoryService：一個描述物件（descriptor），列出每個方法的名稱、種類、請求與回應的 schema。伺服器和 client 都拿它當輸入，型別也從它推出來。

伺服器與 client：Connect-ES

本課用 Connect（Buf 公司的 RPC 框架，JS 版叫 Connect-ES，本課用 @connectrpc/connect 與 @connectrpc/connect-node 2.3.0）。同一個 Connect 伺服器同時接受三種協定：gRPC、gRPC-Web 和 Connect 自己的協定（第 11 課會用到後兩種）。這一課只用 gRPC。

// server.ts（練習 1 的骨架）
import { Code, ConnectError, type ConnectRouter } from '@connectrpc/connect'
import { InventoryService } from './gen/coffee/inventory/v1/inventory_pb.js'

export function inventoryRoutes(stock: Map<string, number>) {
  return (router: ConnectRouter) => {
    router.service(InventoryService, {
      async getStock(req, ctx) {
        // req.productIds 是 string[]；回傳的物件形狀要符合 GetStockResponse
        return { levels: { '2': { productId: '2', available: stock.get('2') ?? 0 } } }
      },
      async reserve(req) { … },
    })
  }
}

// 開伺服器
import http2 from 'node:http2'
import { connectNodeAdapter } from '@connectrpc/connect-node'
http2.createServer(connectNodeAdapter({ routes: inventoryRoutes(stock) })).listen(4000)
  • router.service(描述, 實作)：實作是一個物件，方法名稱是 proto 的 RPC 名稱改成小寫開頭（GetStock → getStock）。沒實作的方法，呼叫時會收到 UNIMPLEMENTED。
  • 每個方法收到 req（已解碼的請求訊息，欄位名是 lowerCamelCase）和 ctx（這次呼叫的資訊，後面會用到 signal、timeoutMs()、requestHeader）。回傳普通物件就好，Connect 會依 schema 編碼。
  • connectNodeAdapter 把路由變成 Node 的請求處理函式。用 http2.createServer 是因為 gRPC 規定跑在 HTTP/2 上：一條 TCP 連線可以同時跑很多個請求（多工，multiplexing），串流也靠它。gRPC 的結果狀態放在回應最後的 trailers（標頭的一種，在 body 之後才送），這也是瀏覽器不能直接呼叫原生 gRPC 的原因（第 11 課）。

client 端：

import { createClient } from '@connectrpc/connect'
import { createGrpcTransport } from '@connectrpc/connect-node'

const transport = createGrpcTransport({ baseUrl: 'http://localhost:4000' })   // http:// = 不加密的 HTTP/2
const client = createClient(InventoryService, transport)
const res = await client.getStock({ productIds: ['1', '2'] })                  // 有型別：res.levels['1'].available

transport 決定用哪個協定、怎麼連線；createGrpcTransport 用 gRPC 協定，一律走 HTTP/2（Connect v2 移除了 httpVersion 選項）。換成 createConnectTransport，同一個 client 就改用 Connect 協定，呼叫的程式不用改。在 work/09 執行 node examples/tour.ts，它在同一個程序裡開伺服器和 client，依序示範這一課的每一種呼叫。前兩段：

1. unary
  [伺服器] getStock 協定=grpc x-request-id=tour-1 剩餘=998
   1:12 2:5
2. 錯誤是 ConnectError，帶狀態碼
  [伺服器] getStock 協定=grpc x-request-id=tour-2 剩餘=沒有 deadline
   code=5（NotFound） message=找不到商品 99

開場的三個問題，最小的答案在這裡：訂單服務要等多久，由它呼叫時設的 deadline 決定，gRPC 預設不設就會一直等；deadline 到了，取消會傳到庫存服務，它要把 signal 交給資料庫查詢，查詢才會停；錯誤用 gRPC 狀態碼表示，呼叫端依碼決定要不要重試。細節在後面的〈狀態碼〉與〈deadline 與取消傳遞〉。

狀態碼：選對碼，呼叫端才知道要不要重試

gRPC 不用 HTTP 狀態碼表示結果。成功或失敗都是 HTTP 200，真正的結果是 trailers 裡的 gRPC 狀態碼：一共 17 個，從 OK = 0 到 UNAUTHENTICATED = 16（grpc.io 的 Status codes 文件）。在 Connect 裡丟 new ConnectError(訊息, Code.X)，client 收到的也是 ConnectError，讀 err.code。handler 丟出不是 ConnectError 的錯誤（一般的 Error、TypeError），呼叫端會收到 INTERNAL 或 UNKNOWN，它沒辦法判斷該怎麼處理。

狀態碼（數字）什麼時候用呼叫端可以重試嗎
INVALID_ARGUMENT（3）請求本身不對，跟系統狀態無關：空的 id 清單、數量 0不行，改請求才有用
NOT_FOUND（5）要的東西不存在：商品 99不行
FAILED_PRECONDITION（9）系統目前的狀態不允許：庫存不夠狀態改變前不行
ABORTED（10）併發衝突，例如交易被中止從更高一層重做（重新讀、再寫）
RESOURCE_EXHAUSTED（8）配額用完、被限流等一段時間再試
UNAVAILABLE（14）服務暫時連不上、正在重啟可以，退避後重試（非冪等操作仍要小心）
DEADLINE_EXCEEDED（4）期限到了還沒完成要看操作是否冪等，下一節說明
PERMISSION_DENIED（7）／UNAUTHENTICATED（16）沒有權限／沒有或無效的憑證不行
INTERNAL（13）伺服器的 bug、違反了不該違反的條件通常不行，要有人去查

grpc.io 文件給的分法：呼叫端可以只重試這一個呼叫 → UNAVAILABLE；要從更高一層重做 → ABORTED；系統狀態被修正之前都不該重試 → FAILED_PRECONDITION。所以庫存不足不能回 UNAVAILABLE：呼叫端的重試機制會不停重送。

「庫存不足」也可以不當錯誤，改在回應裡放一個欄位（例如 ReserveResponse 加 oneof result）。取捨跟第 3 課 GraphQL 的 union 一樣：呼叫端一定要處理的業務結果，放回應裡比較不會被漏掉；呼叫端通常只是失敗的，用狀態碼。這一課用狀態碼。

💡 實務上：每個 RPC 會回哪些狀態碼，要寫進契約
訂單服務的工程師要寫重試與錯誤畫面，得先知道 Reserve 可能回什麼。常見做法是在 .proto 的 RPC 上方用註解列出「哪種情況回哪個碼」，這份註解會跟著 buf generate 出現在產生的程式碼裡，呼叫端在編輯器就看得到。監控也依狀態碼分開看：gRPC 失敗時 HTTP 仍是 200，只看 HTTP 5xx 的儀表板會漏掉；INTERNAL、UNKNOWN 拿來告警（代表有 bug），NOT_FOUND、FAILED_PRECONDITION 是正常業務結果，只看趨勢。之後把某個情況改回別的狀態碼，對呼叫端來說就是破壞性變更，要跟改欄位一樣先通知。

保留庫存要先檢查、再扣，失敗時庫存不能變。在單一個 Node 程序裡，只要檢查和扣之間沒有 await，別的請求就插不進來。換成資料庫時，兩個請求會同時通過檢查，要改成一句有條件的 UPDATE（… SET available = available - $1 WHERE id = $2 AND available >= $1）或交易（PostgreSQL 課第 18 課）。

deadline 與取消傳遞

deadline 是「這次呼叫最晚必須完成的時間點」。gRPC 預設沒有 deadline（grpc.io 的 Deadlines 文件）：沒設的話，下游卡住時，呼叫端就一直等。在 Connect 的 client 用 timeoutMs 設：

await client.getStock({ productIds: ['2'] }, { timeoutMs: 300 })   // 300 ms 內沒完成就丟 DEADLINE_EXCEEDED

client 會把它放進請求的 grpc-timeout 標頭（例如 300m，m 是毫秒）。送的是相對的「還剩多久」而不是絕對時間，兩台機器的時鐘不準也沒關係。伺服器這邊：

  • ctx.timeoutMs()：還剩幾毫秒；client 沒設 deadline 時是 undefined。
  • ctx.signal：一個 AbortSignal。deadline 到、client 取消、或這次 RPC 結束時都會 abort。

只設 deadline 還不夠。client 時間到就放棄了，但伺服器如果沒有把 ctx.signal 交給資料庫查詢和下游呼叫，那些工作會繼續跑完，結果沒人要。這就是取消傳遞（cancellation propagation）：上游放棄後，下游的工作也跟著停。尖峰時最需要它，沒人要的查詢還佔著資料庫連線，會讓更多請求逾時。

async getStock(req, ctx) {
  const left = ctx.timeoutMs()
  if (left !== undefined && left < 20) {                          // 剩這麼一點，開始查也來不及
    throw new ConnectError(`剩 ${left} ms`, Code.DeadlineExceeded)
  }
  const rows = await repo.fetchLevels(req.productIds, ctx.signal)  // 把 signal 交給下游
  …
}

下游收到 signal abort 時應該以 signal.reason 失敗。讓這個錯誤原樣往外丟，不要 catch 之後包成 INTERNAL：伺服器回給呼叫端的狀態碼，就是 handler 最後丟出的錯誤。tour 的第 5 段，client 只等 200 ms，伺服器的假下游一直等到 signal abort：

5. deadline：client 只等 200 ms
  [伺服器] getStock 協定=grpc x-request-id=tour-5 剩餘=199
   DeadlineExceeded，等了約 200 ms
  [伺服器] signal abort 了，原因：ConnectError: [deadline_exceeded] the operation timed out

多跑幾次，最後一行有時會是 http/2 stream closed with error code INTERNAL_ERROR：client 和伺服器各有一個計時器，client 先放棄時會關掉這個 HTTP/2 stream，伺服器就以「連線被關」為原因 abort。兩種情況 ctx.signal 都會 abort，這正是要用它而不是自己計時的原因。

從上游收到請求的服務，呼叫下游時用剩下的時間當 deadline：ctx.timeoutMs() 減掉自己處理回應需要的時間，不是每層各訂一個固定值。剩下太少就直接回 DEADLINE_EXCEEDED，不浪費下游的資源。

💡 實務上：deadline 從使用者願意等多久往回推，並設一個上限保底
先問 PM：App 按下「結帳」後，最多讓使用者等多久就該顯示錯誤？那就是最外層的預算，每一層往下傳剩下的。怕有人忘了設，Connect 2.3.0 的 transport 可以設 defaultTimeoutMs，呼叫沒帶 timeoutMs 時就用它；伺服器端的 connectNodeAdapter 可以設 maxTimeoutMs，呼叫端要求的時間比它長就拒絕（回 INVALID_ARGUMENT）。數字不要憑感覺訂：看下游正常時的回應時間分佈（例如 p99），留一點餘裕。一個服務的 DEADLINE_EXCEEDED 突然變多，通常是它的下游變慢了，沿著呼叫鏈一層層看下游的回應時間（下面 metadata 一節的 request id 能把同一個請求在各服務的 log 串起來）。
DEADLINE_EXCEEDED 只代表呼叫端沒在期限內拿到結果，不代表伺服器沒做。Reserve 可能已經扣完庫存，只是回應來不及送達。盲目重試會扣兩次。要能重試，Reserve 要帶 idempotency_key，伺服器對同一個 key 只扣一次（系統設計課第 9 課；第 12 課實作）。GetStock 這種只讀的呼叫，重試沒有副作用。

串流：async generator 與取消

server streaming 的 handler 寫成 async generator（async *方法名）：每 yield 一次，Connect 就送出一筆回應；generator 結束，串流就結束；丟錯，串流就以那個狀態碼結束。client 用 for await 一筆一筆收，中途 break 就是取消串流，伺服器的 ctx.signal 會 abort。tour 的第 3 段：

3. server streaming：收到 3 筆後 break
   收到 available=12
   收到 available=11
   收到 available=10
  [伺服器] watchStock 結束，signal.aborted=true

練習 3 的 watchStock 要在庫存變動時送出，變動來自一個 EventEmitter（Node 課第 8 課）的 'change' 事件。最常見的錯是用 changes.on(…) 加了監聽卻沒有移除：每個斷線的 client 都留下一個監聽，記憶體慢慢漲，Node 最後印出 MaxListenersExceededWarning。Node 內建的 events.on 正好解決這件事（Node 課第 8 課）：

import { on } from 'node:events'

const events = on(changes, 'change', { signal: ctx.signal })   // 呼叫的當下就開始監聽
yield { productId, available: current }                         // 先開始監聽，再送目前的值
for await (const [change] of events) {                          // 每次 emit 得到一個參數陣列
  …
  yield change
}
  • on() 回傳一個 async iterator，事件會先排進它自己的佇列，不會因為 client 還沒讀而漏掉。
  • 傳入 signal 後，signal abort 時它會移除監聽，並讓 for await 丟出 AbortError。這個錯誤不是 ConnectError，Connect 會把它當成 INTERNAL 送給呼叫端。所以要包一層 try/catch，在 signal 已經 abort 時改丟 ctx.signal.reason，deadline 到時 client 才會收到 DEADLINE_EXCEEDED。
  • 順序很重要：先開始監聽、再送目前的值。反過來的話，送出目前值到開始監聽之間的變動會漏掉。

串流不是無限的。長時間開著的串流會被中間的負載平衡器、代理伺服器因為閒置而切斷，所以要設 deadline 讓 client 定期重新訂閱，或定期送一筆心跳（heartbeat）訊息。串流的 deadline 涵蓋整個串流，不是每一筆。

💡 實務上：每次部署，所有串流都會斷一次
店內看板訂閱著庫存，庫存服務一重新部署，舊程序上的串流全部中斷，看板收到 UNAVAILABLE 或連線錯誤。所以訂閱端一定要寫「斷線後等一下再重新訂閱」，而且等待時間要退避加隨機（系統設計課第 8 課），不然幾十台看板會在同一秒一起重連。重新訂閱後伺服器先送目前的值（練習 3 的設計），看板就不會停在斷線前的舊數字。上線前跟維運確認：部署時舊程序會等多久才強制關閉、中間的代理對閒置連線的逾時是多少，心跳間隔要比它短。

client streaming 反過來：handler 收到的 req 是 async iterable，用 for await 讀完再回一個回應；client 傳一個 async generator 進去。tour 的第 4 段就是 Restock：

// 伺服器
async restock(requests) {
  let receivedItems = 0, totalQuantity = 0
  for await (const r of requests) { … receivedItems++; totalQuantity += r.quantity }
  return { receivedItems, totalQuantity }
}
// client
async function* deliveries() {
  yield { productId: '2', quantity: 10 }
  yield { productId: '6', quantity: 4 }
}
await client.restock(deliveries())

bidirectional streaming 的 handler 同時拿到 async iterable 也回傳 async generator。Connect 的 gRPC transport 在 Node 支援它，但需要雙方都用 HTTP/2，經過某些代理會不通，實務上少用。

metadata 與 interceptor

metadata 是 gRPC 的標頭：跟商業資料無關、但每個呼叫都需要的資訊，例如 authorization（誰在呼叫）和 x-request-id（把同一個請求在不同服務的 log 串起來）。Connect 用標準的 Headers：client 呼叫時傳 { headers: { 'x-request-id': id } }，伺服器讀 ctx.requestHeader.get('x-request-id')。

每個呼叫都要加的東西，不要在每個呼叫的地方各寫一次，用 interceptor（攔截器）統一處理。它包住每一次呼叫，可以改請求、看回應、量時間：

const requestId: Interceptor = next => async req => {
  req.header.set('x-request-id', crypto.randomUUID())
  return next(req)
}
createGrpcTransport({ baseUrl, interceptors: [requestId] })

tour 第 1 段印出的 x-request-id=tour-1 就是這樣來的。伺服器端也可以在 connectNodeAdapter({ routes, interceptors }) 加 interceptor，統一做驗證或記錄 log。

💡 實務上：interceptor 放橫切的事，不放商業邏輯
「橫切」指每個 RPC 都要做、跟哪個功能無關的事。咖啡店的各個服務通常共用同一組 interceptor：產生或沿用 x-request-id、驗證 authorization、記錄每個 RPC 的方法名、耗時和狀態碼。「拿鐵庫存不足就拒絕」這種規則不要放進去，它屬於 handler，放在 interceptor 裡別人讀程式時找不到。記 log 時不要整包印出 metadata 或請求內容，authorization 的 token 和顧客個資會跟著進 log 系統，資安會找上門。資深工程師會把這組 interceptor 做成各服務共用的套件，確保標頭名稱一致，request id 才串得起來。

互通與除錯：grpc-js、buf curl

Connect 實作的是真正的 gRPC 協定，任何 gRPC client 都能呼叫它。Node 官方的 gRPC 實作是 @grpc/grpc-js（本課 1.14.6），NestJS 的 gRPC microservice 用的也是它。它可以不產生程式碼，用 @grpc/proto-loader（0.8.1）在執行時讀 .proto：

import * as grpc from '@grpc/grpc-js'
import * as protoLoader from '@grpc/proto-loader'

const definition = protoLoader.loadSync(PROTO, { defaults: true })   // 預設 keepCase: false，欄位名轉成 productIds
const loaded = grpc.loadPackageDefinition(definition)                // 依 package 變成巢狀物件：loaded.coffee.inventory.v1.InventoryService
const client = new InventoryService('127.0.0.1:4000', grpc.credentials.createInsecure())   // 不加密

client.getStock({ productIds: ['2'] }, { deadline: Date.now() + 300 }, (err, res) => {
  client.close()                                     // 用完關掉連線
  if (err) console.log(grpc.status[err.code], err.details)   // err.code 是數字，grpc.status[5] 是 'NOT_FOUND'
  else console.log(res.levels)
})
  • grpc-js 的 deadline 是絕對時間點（Date 或毫秒時間戳），不是毫秒數。寫 { deadline: 300 } 等於「1970 年過 300 ms」，每個呼叫都立刻 DEADLINE_EXCEEDED。它送出前會換算成相對的 grpc-timeout。
  • defaults: true：proto3 不送預設值，庫存 0 在線上根本沒有那個欄位（第 8 課）。不設的話 proto-loader 讀出 undefined；Connect 產生的程式碼則一律補上 0。
  • grpc-js 是 callback 風格，自己包成 Promise。proto-loader 載入的 client 在 TypeScript 裡沒有型別，interop.ts 已經幫你寫好用得到的部分。

除錯時用 buf curl（像 curl，但懂 protobuf）。先 node examples/serve.ts 用你的 server.ts 開在 4000 port，另一個終端機在 work/09：

npx buf curl --protocol grpc --http2-prior-knowledge --schema proto \
  -d '{"productIds":["2","5"]}' \
  http://localhost:4000/coffee.inventory.v1.InventoryService/GetStock
{
  "levels": {
    "2": { "productId": "2", "available": 5 },
    "5": { "productId": "5" }
  }
}

--schema proto 讓它讀本機的 .proto 才知道怎麼把 JSON 轉成 protobuf；--http2-prior-knowledge 表示直接用不加密的 HTTP/2。商品 5 的庫存是 0，所以 JSON 裡沒有 available：又是「預設值不送」。失敗時它印出狀態碼（例如 "code": "not_found"）並以非 0 結束。另一個常見工具是 grpcurl。兩者都能改用伺服器反射（reflection）：伺服器多開一個服務，回答「我有哪些方法、訊息長什麼樣」，就不用帶 .proto。方便，但等於公開整份 API 的結構，正式環境通常只在內網或除錯時開。

練習

四題都在 api-styles/practice/work/09/，執行 node check.mjs api-styles 09。proto、gen/、examples/ 不用改。測試自己開伺服器（listen 0）、每次用不同的隨機庫存，四題互不相依，可以不按順序做。

練習 1：在 server.ts 完成 getStock 與 reserve，庫存在傳入的 stock Map。getStock 回傳 { levels: { [id]: { productId, available } } }；productIds 是空陣列回 INVALID_ARGUMENT，任何一個商品不存在回 NOT_FOUND（不要回 available 0）。reserve 扣掉 quantity 並回 { productId, remaining }；quantity 小於 1 回 INVALID_ARGUMENT，商品不存在回 NOT_FOUND，庫存不夠回 FAILED_PRECONDITION，而且失敗時庫存不能變。測試還會同時送 20 個 reserve 搶最後 5 份拿鐵，要剛好 5 個成功。

練習 2：在 deadline.ts 讓 deadline 與取消傳下去。伺服器的 getStock：ctx.timeoutMs() 有值且小於 MIN_BUDGET_MS（20）時直接丟 DEADLINE_EXCEEDED，不呼叫 repo；其他情況把這次 RPC 的 signal 傳給 repo.fetchLevels，repo 的錯誤原樣往外丟。client 的 getStockWithin(client, ids, budgetMs) 以 budgetMs 當這次呼叫的 deadline。測試的假 repo 永遠不會自己完成，只在收到的 signal abort 時失敗，所以結果跟電腦快慢無關。

練習 3：在 watch.ts 實作 server streaming 的 watchStock：商品不存在回 NOT_FOUND；先送目前庫存，之後每次 changes 發出 'change' 事件（參數是 { productId, available }）且是這個商品、數字跟上一筆送出的不同時，送一筆。client 取消或 deadline 到時要移除監聽，deadline 到時串流要以 DEADLINE_EXCEEDED 結束（不是 INTERNAL）。測試收到 3 筆後 break，再檢查 changes.listenerCount('change') 回到 0。

練習 4：在 interop.ts 用 @grpc/grpc-js 與 @grpc/proto-loader 載入 PROTO，完成 callWithGrpcJs(address, ids, ms)：以 ms 為預算設 deadline 呼叫 GetStock，成功回 { ok: true, levels: { [id]: 庫存數字 } }（庫存 0 也要是 0），失敗回 { ok: false, code, message }，code 是狀態碼的名稱（'NOT_FOUND'、'DEADLINE_EXCEEDED'），message 是伺服器給的訊息（err.details）。用完關掉 client。測試的目標是一個 Connect 伺服器。

練習 5：訂單服務收到 App 的請求時，預算是 300 ms；呼叫庫存服務之前已經用了 120 ms。呼叫庫存服務時的 deadline 應該是？

✓ deadline 是整條呼叫鏈共用的預算。每一層各給固定逾時（a、d），總時間會超過使用者願意等的時間，上游早就放棄了，下游還在做白工。不設（c）時，一個卡住的下游會讓請求永遠等。Connect 的 ctx.timeoutMs() 就是剩餘預算。

練習 6：Reserve（扣庫存）回 DEADLINE_EXCEEDED，可以直接重試嗎？

✓ 逾時只代表呼叫端沒在期限內拿到結果。非冪等的操作要先有冪等設計才能重試（系統設計課第 9 課）。只讀的 GetStock 重試沒有副作用，所以 c 太絕對。改狀態碼（d）不會改變「可能已經扣過」的事實，只是把問題藏起來。

練習 7：伺服器沒有把 ctx.signal 傳給資料庫查詢。client 的 deadline 到了之後會怎樣？

✓ client 有自己的計時器，時間到就放棄（d 錯）。伺服器那邊只有 ctx.signal 會 abort，沒交給查詢的話，查詢不知道已經沒人要（a 錯），也不會出錯（c 錯）。取消要一路傳下去才有效。

練習 8：顧客要買 3 杯拿鐵，庫存只剩 2 杯。Reserve 回哪個狀態碼最合適？

✓ 系統目前的狀態不允許這個操作，狀態改變（補貨）前重試也沒用。INTERNAL 代表伺服器有 bug，會觸發錯誤告警；UNAVAILABLE 會讓呼叫端的重試機制不停重送；NOT_FOUND 是商品不存在。也可以把「庫存不足」設計成回應欄位，取捨跟第 3 課相同。

常見錯誤

  • 沒設 deadline：gRPC 預設沒有逾時，一個卡住的下游會讓呼叫永遠等。每個呼叫都設 timeoutMs（grpc-js 是 deadline: Date.now() + ms）。
  • 每一層各自訂固定逾時：總時間超過上游願意等的時間。往下傳剩餘預算（ctx.timeoutMs()）。
  • 伺服器不傳遞取消：逾時後還在查資料庫。把 ctx.signal 交給每個下游；不要自己用 AbortSignal.timeout 另訂一個時間。
  • 所有錯誤都回 INTERNAL 或 UNKNOWN：呼叫端無法判斷要不要重試。丟 ConnectError 並選對狀態碼；deadline 造成的錯誤原樣往外丟，不要包成 INTERNAL。
  • 找不到時回傳空值或 0：「沒有這個商品」和「賣完了」是兩件事，前者回 NOT_FOUND。
  • DEADLINE_EXCEEDED 後盲目重試非冪等操作：伺服器可能已經做完。先加 idempotency key。
  • 串流沒有處理取消：emitter.on 之後沒有移除，每個斷線的 client 留下一個監聽。用 events.on(…, { signal: ctx.signal })。
  • grpc-js 的 deadline 傳毫秒數：它要的是絕對時間點，傳 300 等於 1970 年，每個呼叫都立刻逾時。
  • 把 gRPC 狀態碼當 HTTP 狀態碼：gRPC 的回應幾乎都是 HTTP 200，結果看 trailers 裡的 gRPC 狀態碼；5 是 NOT_FOUND，不是 404。
  • 以為前端可以直接呼叫這個 gRPC 伺服器：瀏覽器的 fetch 讀不到 HTTP/2 trailers，原生 gRPC 只適合服務之間。瀏覽器要改用 gRPC-Web 或 Connect 協定（第 11 課）。

小結

  • service 裡的 RPC 依 stream 的位置分成 unary、server streaming、client streaming、bidirectional；預設用 unary。
  • Connect-ES：router.service(描述, 實作) 加 http2.createServer(connectNodeAdapter(…)) 是伺服器；createClient(描述, createGrpcTransport({ baseUrl })) 是 client。gRPC 跑在 HTTP/2 上。
  • 錯誤用 ConnectError(訊息, Code.X)：參數錯 INVALID_ARGUMENT、不存在 NOT_FOUND、狀態不允許 FAILED_PRECONDITION、暫時不可用 UNAVAILABLE。狀態碼決定呼叫端會不會重試。
  • deadline 是整條呼叫鏈的剩餘預算：client 設 timeoutMs，伺服器用 ctx.timeoutMs() 看剩多少、把 ctx.signal 交給下游。逾時後重試非冪等操作要有 idempotency key。
  • server streaming 用 async generator；用 events.on 加 signal 監聽事件，先監聽再送目前值，取消時監聽會被移除。
  • metadata 放 request id、authorization，用 interceptor 統一加。grpc-js 能呼叫 Connect 伺服器（deadline 是絕對時間）；除錯用 buf curl。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 9：庫存服務要改 inventory.proto，訂單服務下週才更新，兩邊用二進位通訊。下面哪個改動，部署後舊的訂單服務仍然讀得對？

✓ 線上只有欄位編號沒有名稱，舊程式遇到不認得的編號 5 就依 wire type 跳過。a 改了每個欄位的身分，d 讓舊資料被當成 note 解讀。b 最容易漏：buf breaking 也會放行，但每個呼叫端都算錯錢，改語意要新增一個名稱說清楚的欄位。（第 8 課）

練習 10：後台的 UpdateProduct 收整個 Product 訊息，伺服器照收到的值整筆更新。店長只改了美式咖啡的價格，商品名稱卻變成空的，為什麼？

✓ proto3 不送等於預設值的欄位，接收端補預設值，所以伺服器分不出「沒給」和「改成空字串」。修法是請求帶 update_mask 列出這次要改的欄位，或把可部分更新的欄位標成 optional。b 錯在沒有存在性的 string 欄位讀出來是空字串，不是 undefined。（第 8 課）

練習 11：訂單服務用 createGrpcTransport 呼叫庫存服務，今天 Reserve 有三成失敗。監控只看 HTTP 5xx 的儀表板卻一直是 0，為什麼？

✓ gRPC 不用 HTTP 狀態碼表示結果，成功失敗都是 200，真正的結果是 trailers 裡的 gRPC 狀態碼。監控要依 gRPC 狀態碼分開看：INTERNAL、UNKNOWN 告警，NOT_FOUND、FAILED_PRECONDITION 看趨勢。c 錯在一般 Error 不會被吞掉，呼叫端會收到 INTERNAL 或 UNKNOWN。（第 9 課）

練習 12：訂單服務呼叫 GetStock 時設 timeoutMs: 200，庫存服務的 handler 這樣寫。尖峰時會出什麼事？

async getStock(req, ctx) {
  const signal = AbortSignal.timeout(500)
  const rows = await repo.fetchLevels(req.productIds, signal)
  …
}

✓ client 有自己的計時器，200 ms 就放棄；伺服器只有 ctx.signal 會在 deadline 到或 client 取消時 abort，自己訂的 signal 不知道已經沒人要了。改成把 ctx.signal 交給 repo，剩太少時直接回 DEADLINE_EXCEEDED。c 錯在 Connect 只 abort ctx.signal，管不到你另外建的 signal。（第 9 課）

練習 13：訂單服務的共用重試 interceptor 遇到 UNAVAILABLE 和 DEADLINE_EXCEEDED 都重試 3 次。庫存服務變慢那天，同一筆訂單的拿鐵被扣了兩三次，該怎麼修？

✓ DEADLINE_EXCEEDED 只代表呼叫端沒在期限內拿到結果，Reserve 可能已經扣完，盲目重試就扣兩次。非冪等操作要重試，先加 idempotency key。b 只是讓它少發生，下游再慢一點又會重複扣。（第 9 課）

練習 14：店內看板的庫存串流上線一週，庫存服務的記憶體一直漲，log 出現 MaxListenersExceededWarning。changes.listenerCount('change') 是在線看板數的好幾倍，最可能的原因？

✓ 每個斷線的看板都留下一個監聽，數字才會超過在線的看板數。改用 events.on(changes, 'change', { signal: ctx.signal })，取消或 deadline 到時監聽會被移除。a 錯在還連著的串流各只有一個監聽，數量會等於在線看板數，不會是好幾倍。（第 9 課）
