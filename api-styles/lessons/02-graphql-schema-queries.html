階段 2：GraphQL 基礎 · 第 2 課

GraphQL 入門：schema、SDL 與第一個查詢

App 的商品頁要顯示商品名稱、價格和說明；比較頁要並排兩個商品；菜單頁只要名稱和價格。用 REST 時，後端常要為每個畫面多開一支端點，或讓前端拿到一大包用不到的欄位。GraphQL 換一種做法：伺服器公開一份「有哪些資料、長什麼型別」的清單，前端在每次請求裡寫出這個畫面要哪些欄位，伺服器照著回傳，不多也不少。

這課的路線：
  1. 準備環境、執行第一個查詢：GraphQL 最少只要哪兩樣東西，在 Node 裡怎麼跑起來。
  2. 用 SDL 寫 schema：前後端的契約怎麼寫，哪些欄位該加 !，哪些不該。
  3. 寫查詢：參數、變數、別名、fragment，商品頁、比較頁、菜單頁各怎麼查，前端天天用到。
  4. 先驗證再執行、內省：查詢打錯欄位為什麼一筆資料都不查，前端工具怎麼知道有哪些欄位可查。
  5. graphql-yoga：把 schema 變成可以用 curl 呼叫的 HTTP 端點。
這課會用到：
  • 第 1 課的「拿太多、拿太少」（over-fetching／under-fetching）：REST 的回應形狀由伺服器決定，畫面常拿到用不到的欄位，或要多打幾支才拿齊。
  • Node 課第 13 課的 node:http：createServer 收到每個請求就呼叫你的處理函式，listen 開始在某個 port 等請求。

準備練習環境，執行第一個查詢

這門課從這一課起在你自己的電腦上練習，資料夾是 learn/api-styles/practice，需要 Node 24.20 以上（node -v 確認）。第一次先安裝套件：

cd learn/api-styles/practice
SCARF_ANALYTICS=false PACT_DO_NOT_TRACK=1 npm install

前面兩個環境變數關掉其中一個套件（第 10 課的 Pact）安裝時的匿名統計。npm 11 會印出 install-scripts 警告，說有幾個套件的安裝腳本沒有執行；這門課用不到那些腳本，忽略即可。接著回到 learn/ 執行 node check.mjs api-styles 02：第一次會建立 api-styles/practice/work/02/，裡面有這一課的範例（examples/）、菜單資料 data.ts 和三題練習的起始檔。測試一開始沒過是正常的。

GraphQL 最少只需要兩樣東西：一份 schema（伺服器提供的所有型別與欄位的完整清單），和一段客戶端送來的查詢文件（document，例如 { hello }）。graphql 套件（graphql-js，GraphQL 官方的 JavaScript 實作，本課用 17.0.2）可以直接在 Node 裡執行，不需要伺服器：

// examples/hello.ts
import { buildSchema, graphql } from 'graphql'

const schema = buildSchema(`
  type Query {
    hello: String
  }
`)
const rootValue = { hello: () => '歡迎光臨咖啡店' }

console.log(JSON.stringify(await graphql({ schema, source: '{ hello }', rootValue })))
console.log(JSON.stringify(await graphql({ schema, source: '{ helo }', rootValue })))

在 work/02 執行 node examples/hello.ts：

{"data":{"hello":"歡迎光臨咖啡店"}}
{"errors":[{"message":"Cannot query field \"helo\" on type \"Query\". Did you mean \"hello\"?","locations":[{"line":1,"column":3}]}]}
  • buildSchema 把一段文字讀成 schema 物件。type Query { hello: String } 的意思是：查詢的入口有一個欄位 hello，型別是字串。
  • rootValue 提供入口欄位的值。這裡是函式，查詢用到 hello 時才呼叫。這種「替一個欄位取得資料的函式」叫 resolver，本課後面講 graphql-yoga 時會換成正式寫法，下一課詳細講。
  • 回應永遠是同一個形狀：成功時有 data；出錯時有 errors 陣列，每個錯誤有 message 和出錯的位置 locations（第幾行第幾欄）。看結果時兩個都要看。

用 SDL 寫 schema：型別、純量、非空與清單

上面那段 type Query { … } 的語法叫 SDL（Schema Definition Language，schema 定義語言）。schema 就是前後端之間的契約：前端只能查 schema 裡有的欄位，後端承諾每個欄位回傳宣告的型別。以咖啡店的商品為例，一步一步長大：

enum Category {
  COFFEE
  TEA
  FOOD
}

type Product {
  id: ID!
  name: String!
  price: Int!
  category: Category!
  description: String
}

type Query {
  menu(category: Category): [Product!]!
  product(id: ID!): Product
}
  • 物件型別（object type）：type Product { … }，一組有名字的欄位，每個欄位有型別。
  • 純量（scalar）：最底層、不能再往下選的值。內建五種：Int（32 位元整數）、Float、String、Boolean、ID（識別碼，JSON 裡一律是字串，例如 "2"）。也可以自訂，例如日期時間的 DateTime。價格用 Int 存新台幣整數元，原因跟 TypeScript 課第 5 課一樣：Float 會有 0.1 + 0.2 的誤差。
  • enum：只能是固定幾個值之一。Category 對應到 TypeScript 的字面值聯合型別 'COFFEE' | 'TEA' | 'FOOD'（TypeScript 課第 15 課）：傳 DRINK 進來，GraphQL 在執行前就擋下。
  • 非空（non-null，!）：保證不是 null。description 沒有 !，因為有的商品沒有說明。
  • 參數（argument）：欄位可以帶參數，product(id: ID!) 的 id 必填，menu(category: Category) 的 category 可以不給。
  • 根型別（root type）：Query 是所有讀取的入口。另外兩個根型別 Mutation（寫入）在下一課、Subscription（訂閱，伺服器主動推送）本課程不練習。

清單用 [ ] 包起來，! 可以加在裡面、外面或兩邊，意思不同：

寫法清單本身可以是 null 嗎元素可以是 null 嗎可能的值
[Product]可以可以null、[]、[p, null]
[Product!]可以不行null、[]、[p, q]
[Product]!不行可以[]、[p, null]
[Product!]!不行不行[]、[p, q]

菜單用 [Product!]!：前端不用處理「菜單是 null」或「某一筆是 null」，空菜單就是 []。product(id) 回傳 Product（不加 !），因為 id 可能不存在，找不到時回 null 是正常結果，不是錯誤。

! 是對前端的承諾，加了就很難拿掉：把 String! 改回 String，所有假設它不是 null 的前端程式都可能壞掉（第 10 課的破壞性變更）。而且非空欄位真的取不到值時，null 會往上傳染到整個父物件（第 3 課）。只在「一定有值」時加 !，不確定就不加。

參數也可以是一整個物件，這時要用 input 型別宣告。input 只能當參數、不能當回傳值，欄位只能是純量、enum、其他 input，或這些型別的清單：

input MenuFilter {
  category: Category
  maxPrice: Int
}

type Query {
  search(filter: MenuFilter!): [Product!]!
}

下一課的下單 mutation 會用 input 傳整張訂單。

💡 實務上：改 schema 要像改 API 規格一樣走 review
在有 GraphQL 的團隊，schema 的改動通常會單獨開 PR，前端、後端、App 的人都會被找來看，因為欄位名稱和 ! 一上線就很難再改（第 10 課）。例如咖啡店要加「季節限定」欄位，review 時資深會先問：舊商品有沒有這個值？以後會不會有商品沒填？只要有一題答「會」，就不加 !。欄位名稱也要用畫面看得懂的業務語言（price、category），不要照搬資料表的欄位名稱，資料表之後改名，schema 不必跟著改。

寫查詢：選欄位、參數、變數、別名、fragment

examples/shop.ts 是上面的 schema 再加上訂單（Order）與品項（OrderItem）。examples/queries.ts 收錄了這一節的每個查詢，node examples/queries.ts fields 執行其中一個，不給名稱就全部執行。

選欄位：查詢的形狀就是回應的形狀。物件型別的欄位一定要繼續往下選到純量為止，所以不能只寫 { menu }：

{ menu { name price } }                     # fields：回傳 { "menu": [{ "name": "美式咖啡", "price": 80 }, …] }
{ order(id: "1") { customerName total items { quantity product { name price } } } }   # nested：訂單 → 品項 → 商品，一次拿齊

參數：{ menu(category: TEA) { name } product(id: "2") { name description } }（args）。enum 值直接寫 TEA，不加引號；一份查詢可以同時查好幾個入口欄位。product(id: "999") 查不到時得到 { "data": { "product": null } }，沒有 errors（missing）。

變數（variables）：把值寫死在查詢裡，每個 id 就是一份不同的查詢文字。正式寫法是在操作名稱後宣告變數，值另外用 JSON 傳：

query ProductById($id: ID!) {
  product(id: $id) { name price }
}
# 變數另外傳：{ "id": "4" }

query ProductById 這一整段叫一個操作（operation），ProductById 是操作名稱（operationName），在伺服器 log 和錯誤追蹤裡用它認出是哪個畫面發的查詢，正式專案的每個操作都要取名。變數型別要跟參數相容：參數是 ID!，變數就要宣告成 $id: ID!，寫 $id: ID 會在驗證時被擋下，因為變數可能是 null。

不要用字串拼接把使用者輸入放進查詢（`{ product(id: "${id}") { name } }`）。跟 SQL 拼字串是同一個問題：使用者可以輸入 "){ … } 這類內容改變查詢的結構；而且每個值都是不同的查詢文字，伺服器沒辦法快取解析結果，也做不了第 6 課的 persisted operations（伺服器只接受事先登記過的查詢）。值一律用變數傳。

別名（alias）：同一個欄位用不同參數查兩次，回應裡兩個都叫 product 會衝突，GraphQL 直接判為驗證錯誤。在欄位前面加上 名字:，結果就用這個名字：

{
  first: product(id: "1") { name price }
  second: product(id: "2") { name price }
}
# alias：{ "first": { "name": "美式咖啡", … }, "second": { "name": "拿鐵", … } }

fragment：可以重複使用的欄位片段，on Product 說明它用在哪個型別上，用 ...名稱 展開。比較頁的兩張商品卡片顯示一樣的欄位，寫一次就好；之後卡片要多顯示分類，只改 fragment：

query CompareTwo($a: ID!, $b: ID!) {
  first: product(id: $a) { ...ProductCard }
  second: product(id: $b) { ...ProductCard }
}

fragment ProductCard on Product { id name price }

前端專案常讓每個元件定義自己需要的 fragment，頁面的查詢把子元件的 fragment 組起來。第 7 課的 codegen（程式碼產生：讀 schema 和你寫的查詢，自動產生 TypeScript 型別）會用到這個習慣。

💡 實務上：操作名稱是除錯時最重要的線索
GraphQL 的請求全都打同一個 /graphql，打開瀏覽器 DevTools 的 Network 面板，會看到一整排名字都是 graphql 的請求。客服回報「商品頁價格錯了」時，你要點開請求的 payload，靠 operationName 找出 ProductById；後端在 log 裡查的也是同一個名字。沒取名的查詢在兩邊都只是一串看不出來源的文字。所以團隊通常會約定命名規則（例如「頁面＋用途」），並在 lint（例如 ESLint 的 GraphQL 外掛）擋掉沒取名的操作。

先驗證，再執行

查詢打錯一個欄位名稱，GraphQL 一筆資料都不會查，原因在它的處理順序。伺服器收到查詢後分三步處理：先解析（parse）文字，再對 schema 驗證（validate），最後才執行（execute），也就是呼叫函式取得資料。前兩步任何一步失敗，整份查詢都不執行。

examples/queries.ts 最後三個範例會印出入口函式被呼叫了幾次，三個都是 0：

範例查詢錯誤訊息（graphql 17.0.2）
typo{ menu { name prise } }Cannot query field "prise" on type "Product". Did you mean "price"?
missing-arg{ product { name } }Argument "Query.product(id:)" of type "ID!" is required, but it was not provided.
bad-variable$id: ID! 傳 { "x": 1 }Variable "$id" has invalid value: ID cannot represent value: { x: 1 }

這是 GraphQL 有型別系統的直接好處：拼錯、漏參數、型別不符都在執行前擋下，不會發生「扣了庫存才發現某個欄位不存在」這種只做一半的事。對前端來說也一樣，第 7 課的 codegen 會在 build 階段就用 schema 驗證你的查詢。

內省與 GraphiQL

前端怎麼知道 schema 有哪些欄位？GraphQL 內建內省（introspection）：用一般的查詢問伺服器自己的結構。以 __ 開頭的欄位是內建的，__schema 列出所有型別，__type(name:) 查一個型別：

{ __type(name: "Product") { name kind fields { name type { kind name ofType { kind name } } } } }

執行 node examples/introspect.ts，price 的型別是 { kind: "NON_NULL", ofType: { kind: "SCALAR", name: "Int" } }，也就是 Int!：非空是一層包在外面的型別。graphql-js 裡也一樣，String(field.type) 會印出 Int!、[Product!]! 這種寫法，練習 1 的測試就是這樣檢查的。

GraphiQL（瀏覽器裡的 GraphQL 編輯器）、IDE 的自動完成、第 7 課的 codegen 都靠內省運作。正式環境要不要關掉內省是安全上的取捨，留到第 6 課。

變成 HTTP 端點：graphql-yoga

graphql() 只是函式。要讓 App 透過網路呼叫，需要一個 HTTP 伺服器：收請求、取出查詢、執行、寫回應。本課程用 graphql-yoga 6.0.1（支援 graphql 17 的 GraphQL 伺服器）。它的 createSchema 把 SDL（typeDefs）和每個欄位怎麼取得資料（resolvers）合成一份 schema，createYoga 建立處理請求的物件 yoga，它可以直接交給 node:http 的 createServer：

// examples/yoga.ts（節錄）
import { createServer } from 'node:http'
import { createSchema, createYoga } from 'graphql-yoga'
import { menu } from '../data.ts'

const yoga = createYoga({
  schema: createSchema({
    typeDefs: /* GraphQL */ `
      type Product { id: ID! name: String! price: Int! }
      type Query { menu: [Product!]! }
    `,
    resolvers: {
      Query: {
        menu: () => menu,
      },
    },
  }),
})

createServer(yoga).listen(4000)

/* GraphQL */ 只是註解，讓編輯器的 GraphQL 外掛把這段字串當 SDL 上色，執行時沒有作用。resolvers 的結構跟 schema 對應：Query.menu 是 menu 欄位的函式。它的第一個參數是父物件，第二個參數是這個欄位收到的參數，例如 product: (_parent, args) => … 裡的 args.id，下一課詳細講。執行 node examples/yoga.ts，另開一個終端機：

curl -X POST http://localhost:4000/graphql \
  -H 'content-type: application/json' \
  -d '{"query":"{ menu { name price } }"}'
{"data":{"menu":[{"name":"美式咖啡","price":80},{"name":"拿鐵","price":110},…]}}
  • 端點只有一個：/graphql。body 是 JSON：query 是查詢文字，另外可以有 variables（物件）和 operationName（文件裡有多個操作時，指定執行哪一個）。
  • GET 也可以：/graphql?query=…（要 URL 編碼）。GET 能被 HTTP 快取，但查詢文字放在網址裡太長，第 7 課再談。
  • 用瀏覽器打開 http://localhost:4000/graphql 會看到 Yoga 內建的 GraphiQL，可以邊打邊自動完成、按執行。Yoga 6 預設開著，createYoga({ graphiql: false }) 關掉。
  • Yoga 6 預設每個請求在終端機印一段 INF Request processed log（含狀態碼與錯誤數），createYoga({ logging: false }) 可以關掉。

HTTP 狀態碼要特別注意。客戶端用 Accept 標頭說明它看得懂哪種回應格式，Yoga 依此決定驗證失敗時回什麼（graphql-yoga 6.0.1 本機實測）：

情況Accept: application/json 或沒給Accept: application/graphql-response+json
成功200200
拼錯欄位（驗證失敗）200 ＋ errors400 ＋ errors
變數型別不符400 ＋ errors400 ＋ errors
執行時出錯（下一課）200 ＋ data ＋ errors200 ＋ data ＋ errors

application/graphql-response+json 是 GraphQL over HTTP 規格（草案）定義的新格式，請求本身有問題時用 4xx（規格目前的草案對驗證失敗建議 422，Yoga 6.0.1 回 400，所以前端不要只靠某一個狀態碼判斷）。不管哪一種，200 不代表成功，前端一定要檢查 errors。

💡 實務上：監控只看狀態碼，會漏掉 GraphQL 的錯誤
從 REST 轉過來的團隊常踩這個坑：維運的儀表板照 HTTP 狀態碼統計錯誤率，全部是 200，看起來一切正常，其實使用者的菜單頁一直拿到 errors。前端的做法是把「檢查 errors」寫進共用的請求函式或 GraphQL client 的設定，而不是每個畫面自己判斷。後端與維運則要讓 log 和告警以 errors 的數量、依操作名稱分組來看。上線前資深會問一句：「回 200 但有 errors 時，我們看得到嗎？」

測試時不必真的開 port：yoga.fetch(url, init) 收一個標準的 Request 參數、回傳 Response，走的是跟真實 HTTP 請求相同的處理流程，這是 Yoga 官方建議的測試方式，練習 3 的測試就這樣用：

const res = await yoga.fetch('http://yoga/graphql', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ query: 'query ($id: ID!) { product(id: $id) { name } }', variables: { id: '2' } }),
})
console.log(res.status, await res.json())   // 200 { data: { product: { name: '拿鐵' } } }
這門課的寫法叫 schema-first：先寫 SDL，再寫 resolver（Yoga 的 createSchema、graphql-tools 的 makeExecutableSchema 都是）。另一派是 code-first：用程式碼（例如 Pothos，或 NestJS 的 @ObjectType() decorator）定義型別，由程式產生 schema。產生出來的 SDL 和概念完全相同；選哪一種看團隊：schema-first 讓前後端先對著 SDL 討論契約，code-first 讓型別和 resolver 寫在一起、比較不會不同步。

練習

在 learn/ 執行 node check.mjs api-styles 02，三題都在 api-styles/practice/work/02/。練習 2 的測試用的是自己的參考 schema（就是練習 1 的要求），所以可以不按順序做；練習 3 會讀你的 menu.graphql，要先完成練習 1。

練習 1：menu.graphql 現在的 schema 有好幾處不符合需求，改成：enum Category（COFFEE、TEA、FOOD）；type Product 有 id: ID!、name: String!、price: Int!、category: Category!、description: String 五個欄位；Query.menu 有一個可以不給的 category 參數，回傳清單本身和每個元素都不會是 null；Query.product 有必填的 id，找不到時能回 null。測試會逐一檢查每個欄位與參數的型別（包括 ! 和 [ ] 的位置），再用這份 schema 執行查詢。

練習 2：在 queries.graphql 寫三個具名操作。MenuNames：整份菜單，每個商品只要 name 和 price（現在的起始寫法選太多欄位了）。ProductById：用變數 $id 查一個商品，要有 name、price、description。CompareTwo：用變數 $a、$b 同時查兩個商品，結果分別叫 first、second，兩邊的欄位都用 fragment ProductCard on Product（選 id、name、price）。三個操作都要通過驗證；測試每次會用不同的商品資料和變數執行。

練習 3：完成 server.ts：用 createSchema 建立 schema（typeDefs 讀同資料夾的 menu.graphql，提示：readFileSync(new URL('./menu.graphql', import.meta.url), 'utf8')。import.meta.url 是 server.ts 自己的檔案網址，用它組出同資料夾的路徑，不管從哪個資料夾執行都讀得到；只寫 './menu.graphql' 會以執行指令時所在的資料夾為準），resolver 從 data.ts 的 menu 取資料，而且不能改動這個陣列（要排序先複製一份，sort() 會直接改原陣列）；再用 createYoga 建立 yoga，兩個都 export。menu(category) 給了分類就只回該分類（null 等於沒給），product(id) 用 id 找商品、找不到回 null（不是丟錯）。測試會比對你的 schema 跟 menu.graphql 是否一致（不要在 server.ts 另寫一份 SDL），也會換掉 data.ts 陣列的內容和順序，所以要在每次查詢時讀 menu。想用 curl 或 GraphiQL 試，執行 node examples/serve.ts，它會用 4000 port 開啟你的 yoga。

練習 4：欄位型別 [Product!]! 代表什麼？

✓ 外層的 ! 管清單本身，內層的 ! 管每個元素，兩個都有就是「一定是陣列、裡面沒有 null」。空陣列 [] 合法，GraphQL 沒有「至少一個」的型別，所以 c 錯。a 是 [Product!]，d 是 [Product]!。

練習 5：前端把查詢寫成 `{ product(id: "${id}") { name } }`，用字串拼接放入 id。最主要的問題是？

✓ 跟 SQL 一樣，值要用變數傳（query ($id: ID!) { product(id: $id) { … } }）。變數讓查詢文字固定：伺服器可以快取解析與驗證的結果、可以只允許事先登記的查詢（第 6 課），使用者輸入也只會被當成值。GraphQL 當然支援字串參數（a 錯）；c 沒有根據；d 忽略了插入攻擊和快取。

練習 6：查詢 { menu { name } product(id: "1") { nmae } } 送到伺服器，product 那段拼錯了欄位名稱。結果是？

✓ 解析和驗證是對整份文件做的，任何一處不合 schema，整份查詢都不執行，所以拼錯的欄位連帶讓 menu 也拿不到。「部分成功」（有 data 又有 errors，a 描述的情況）只發生在執行階段，是下一課的內容。GraphQL 不會靜默忽略錯誤（b）；狀態碼是 200 或 400（看 Accept），不是 500（d）。

常見錯誤

  • 每個欄位都加 !：之後某個欄位真的可能取不到值時，改成可為 null 會弄壞前端，而且一個 null 會往上傳染整個物件。只在一定有值時加。
  • 找不到資料時丟錯：product(id) 查不到是正常結果，回 null，回傳型別就不能加 !。錯誤留給真的出問題的情況。
  • 把值拼進查詢字串：無法快取、無法做 persisted operations，還可能被插入額外的查詢內容。用變數。
  • 變數型別比參數寬鬆：參數是 ID!，變數宣告成 $id: ID 會驗證失敗。變數型別照抄參數型別。
  • 金額用 Float：會有浮點誤差。用 Int 存整數元（或分）。
  • 看到 200 就當成功：GraphQL 的錯誤放在 body 的 errors，驗證失敗在 application/json 下也是 200。一律檢查 errors。
  • 每個請求重新建立 schema：讀檔、解析 SDL 都要時間。schema 和 yoga 在程式啟動時建一次，resolver 在每次查詢時讀資料。
  • 查詢沒有操作名稱：{ … } 能跑，但 log 和錯誤追蹤裡分不出是哪個畫面發的。正式程式一律寫 query 名稱(…)。

小結

  • schema 是前後端的契約，用 SDL 寫：物件型別、純量（Int、Float、String、Boolean、ID）、enum、input，入口是 Query。
  • ! 表示非空，[T!]! 是「一定是陣列、元素沒有 null」；找得到也可能找不到的欄位不要加 !。
  • 查詢的形狀就是回應的形狀；用變數傳值、用別名同時查同一個欄位兩次、用 fragment 重用欄位、每個操作都取名。
  • 伺服器先解析、再驗證、最後執行；前兩步失敗就只有 errors、沒有 data，任何函式都不會被呼叫。
  • 內省讓 GraphiQL、IDE、codegen 知道 schema；graphql-yoga 用 createSchema＋createYoga 把 schema 變成 /graphql 端點，測試用 yoga.fetch 不必開 port。
  • 回應永遠是 { data, errors }，HTTP 200 不代表沒有錯誤。
