伺服器替使用者發出連線、保存秘密、開放端點，每一樣都是攻擊面。用威脅模型和 OWASP 清單有系統地找問題，修根本原因，每個修補都留攻擊測試，出事時先止血再調查。[回 認證與資安 學習地圖](../index.html)

## A SSRF：出站請求的流程 {span=2}
```flow LR
(使用者給的網址) -> [new URL 正規化，只允許 https、443、沒有 userinfo] -> [解析一次 DNS，每一筆都要是公開位址] -> *[用驗證過的 IP 連線，保留 Host 與 SNI]
*[用驗證過的 IP 連線，保留 Host 與 SNI] -> {重導向?}
{重導向?} --> [new URL 正規化，只允許 https、443、沒有 userinfo]: 每一跳重新走一次，限制跳數
{重導向?} -> [邊讀邊限制大小、限制時間]: 否
[邊讀邊限制大小、限制時間] -> (錯誤訊息不透露細節)
```
SSRF（OWASP API7）：伺服器照著使用者給的網址發請求，攻擊者就能打到 metadata、本機管理介面、內網服務，或拿來掃描內網。不自動跟隨重導向。「先解析檢查、再 `fetch(url)`」不夠：fetch 連線前會自己再解析一次。攻擊者把網域的 TTL 設成 0，第二次回 127.0.0.1（DNS rebinding）。所以只解析一次，連線時直接用驗證過的 IP。

## B 位址判斷與其他防線
```kv cols=1
CIDR: IP 解析成位元組，前 N 個位元相同就是同一段
IPv4: 照 IANA 特殊用途位址表拒絕
IPv6: 預設拒絕，只允許 2000::/3 再排除特殊範圍；內嵌 IPv4 的位址取出來檢查（逐步檢查是選讀）
已知目的地: 用網域允許清單
網路層: 出站防火牆或代理、高風險功能放在沒有權限的獨立服務、AWS 只接受 IMDSv2、IAM 最小權限
```
第三方 API 的回應（OWASP API10）是不可信輸入。逐欄驗證、只取需要的欄位、網址檢查協定與完整 hostname、跨網域重導向不帶憑證、設逾時與斷路器。

## C 三種「加密」防的東西不一樣
| 種類 | 擋得住 |
|---|---|
| TLS 傳輸中加密 | 網路上被竊聽、被竄改 |
| 靜態加密 | 硬碟、快照、備份檔本身被拿走 |
| 應用層欄位加密 | 資料庫內容外流 |

```callout warn 三者都擋不住應用程式本身被入侵
合法的程式必須能解密。要原文就加密（TOTP 秘密、第三方 token、手機號碼），不需要原文就雜湊（密碼、重設 token）。
```

## D 欄位加密怎麼做 {span=2}
```flow LR
[KMS 的 HSM 裡的主金鑰 KEK] -> [資料金鑰 DEK 明文，加上加密過的 DEK]: 產生
[資料金鑰 DEK 明文，加上加密過的 DEK] -> [用 DEK 明文做 AES-256-GCM，明文用完就丟]
[用 DEK 明文做 AES-256-GCM，明文用完就丟] -> *[資料庫存加密過的 DEK 與密文]
```
信封加密：主金鑰留在 KMS 的 HSM 裡，只加密資料金鑰；解密時把加密過的 DEK 交給 KMS 解開，每次解密都有稽核紀錄。
| 部分 | 規則 |
|---|---|
| IV | 每次 12 bytes 隨機；同一把金鑰最多 2<sup>32</sup> 次 |
| AAD | 把密文綁在資料列上；解密失敗一定當錯誤處理 |
| 金鑰輪替 | 密文帶 kid（`v1.<kid>.<iv>.<密文>`）；寫入用 current、讀取依 kid；背景工作分批重新加密，全部完成才移除舊金鑰 |
| HKDF（選讀） | 從一把主金鑰衍生各用途的子金鑰 |
| blind index（選讀） | HMAC(索引金鑰, 正規化後的值)，讓加密欄位能做「等於」查詢；代價是洩漏重複與頻率 |

## E Secrets 與個資
```kv cols=1
Secrets: 不進 git、不進 log、不進前端
外洩時: 先部署新的、確認、再撤銷舊的，並查舊的有沒有被用過
資料最小化: 只收需要的，訂好保留期限
刪除: 涵蓋主資料庫、備份、log 與第三方副本；軟刪除不算刪除
log 遮罩: ****678、x***@example.com；走過整個物件、不分大小寫、不改到原物件
開發環境: 用合成資料或先遮罩的傾印
```

## F OWASP API Security Top 10（2023） {span=2}
| 編號 | 名稱 | 一句話 |
|---|---|---|
| API1 | BOLA | 少檢查這一筆 |
| API2 | 認證 | 登入、token 的機制有漏洞 |
| API3 | BOPLA | 少檢查這個欄位 |
| API4 | 資源耗用 | 分頁、body、上傳、昂貴操作、付費服務、時間都要有上限；超過回 429 加 `Retry-After` |
| API5 | BFLA | 少檢查這類動作 |
| API6 | 敏感業務流程 | 程式沒 bug 也會被濫用；累計限購、綁定付款卡或手機等是產品決策 |
| API7 | SSRF | 伺服器被騙去連不該連的地方 |
| API8 | 設定錯誤 | 錯誤回應只給通用訊息與 request id；檢查 CORS、安全標頭、debug 端點、TLS |
| API9 | 資產管理 | OpenAPI 文件就是清單，自動比對實際路由；舊版要有 sunset 日期 |
| API10 | 不安全地使用第三方 API | 外部回應是不可信輸入 |

安全審查：列端點 → 每個端點問同一組問題 → 依可能性 × 影響排序 → 修補並留攻擊測試；secret scanning、套件稽核、SAST／DAST、授權矩陣測試放進 CI。OWASP Top 10:2025 是另一份清單，要一併看。

## G 威脅建模、稽核紀錄與事故應變 {span=2}
威脅建模的四個問題：我們在做什麼、可能出什麼錯、要怎麼處理、做得夠好嗎。在設計時、架構改變時、事故之後做。畫 DFD（外部實體、程序、資料存放、資料流、信任邊界），對每個元件與跨邊界的資料流用 STRIDE 逐一問：
| STRIDE | 破壞的性質 |
|---|---|
| 偽冒 | 認證 |
| 竄改 | 完整性 |
| 否認 | 不可否認性 |
| 資訊洩漏 | 機密性 |
| 阻斷服務 | 可用性 |
| 權限提升 | 授權 |

風險 = 可能性 × 影響；每個威脅明確決定緩解、消除、轉移或接受，寫進設計文件。
```kv cols=1
稽核紀錄記: 安全事件與主體、目標、結果、IP、request id
稽核紀錄不記: 密碼、token、session ID、金鑰、連線字串；欄位名稱遮罩之外，再依秘密的格式掃字串值
防竄改: 資料庫權限只給 INSERT（每個專案都該做）；雜湊鏈（標準化 JSON、算進前一筆的雜湊）與外部錨定是選讀，用在稽核要求高的系統
偵測: 暴力破解看同一帳號的失敗次數，密碼噴灑看同一來源的不同帳號數，撞庫看整體成功率
```
```callout err 事故應變先止血再調查
金鑰外洩先換金鑰、資料庫外洩先讓憑證失效、帳號被盜要檢查 email 與 MFA、套件被植入要輪替 CI 的 secrets。最後寫不究責的事後檢討，回頭更新威脅模型。
```

## H 期末專題：強化咖啡店 API
```timeline v
步驟一 | 先畫威脅模型 | 畫出信任邊界，依可能性 × 影響排序
步驟二 | 逐項修補 | 修根本原因而不是症狀
步驟三 | 事故演練 | 外洩的秘密要輪替，被擋下的攻擊也是事故
```
- 門市範圍的檢查放在共用的函式並寫進查詢條件；全域拒絕多餘欄位；回應用允許清單。
- 每個修補都要有攻擊測試（證明擋住、以後也不會回來）與功能測試（證明沒改壞），再加一段決策紀錄。
- JWT 固定演算法與 aud；refresh 重用要撤銷整個家族；重設密碼 token 雜湊、短期限、單次、讓舊 token 全部失效；登入限流分帳號與 IP。
