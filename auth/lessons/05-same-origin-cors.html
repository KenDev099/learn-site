階段 2：瀏覽器裡的登入狀態：Cookie、Session 與跨站攻擊 · 第 5 課

同源政策與 CORS：誰可以讀回應

咖啡店的 Vue 前台部署在 https://shop.coffee.example，API 在 https://api.coffee.example。上線前一天，前台一呼叫 API 取訂單，Console 就跳出紅字，說請求被 CORS 擋了；可是用 Postman 打同一個 API 完全正常。網路上搜到的解法通常有兩種：「把 Access-Control-Allow-Origin 設成 *」，或「請求的 Origin 是什麼就回什麼」。第一種在前台要帶 cookie 時根本不能用；第二種能讓紅字消失，但也讓任何網站都能讀你使用者的訂單。

這一課的任務：讓咖啡店的前台和店長後台讀得到 API 的回應，而且不替其他網站開門。要做到這件事，得先知道瀏覽器到底在擋什麼、為什麼要擋，再看 CORS 怎麼在不開洞的前提下放行。學完你能寫出正式環境的 CORS 設定，也能在 Console 跳紅字時，從 Network 面板找到真正的原因。

這課的路線：
  1. 為什麼前台讀不到自己 API 的回應：瀏覽器讓別的來源「送」請求，但不讓它的 JavaScript「讀」回應；前台和 API 不同來源，所以要 API 明確同意（開場問題的最小答案）。
  2. shop 和 api 為什麼算不同來源：「來源」和「站」兩種判斷方式，各用在哪裡。
  3. API 怎麼同意、瀏覽器怎麼檢查：CORS 的回應標頭；取訂單的 GET 直接送，改訂單的 JSON PATCH 為什麼要先送一個 OPTIONS 預檢。
  4. 開了 CORS 之後要守住什麼：CORS 不是存取控制；允許清單哪些比對寫法會開洞；咖啡店最後的設定。
  5. 設好了還是跳紅字怎麼查：到 Network 面板看哪幾個地方，為什麼 CORS 錯誤常常只是表象。
這課會用到：
  • Node 課第 12 課的 HTTP 方法與標頭：除了 GET、POST，還有用來詢問伺服器的 OPTIONS；請求和回應都帶「名稱: 值」的標頭。Node 課沒有教 CORS，這課從頭講。
  • 第 4 課的 cookie：符合條件的請求會自動帶上 cookie，所以「送出請求」本身就帶著使用者的身分。

為什麼前台讀不到自己 API 的回應？

先看那行紅字實際發生了什麼。前台執行 fetch('https://api.coffee.example/orders', { credentials: 'include' })，JS 拿到的不是回應，而是一個 TypeError。可是去看 API 的 log，這個請求確實進來了，也回了訂單資料。資料已經回到瀏覽器，是瀏覽器自己不肯交給 JS。

瀏覽器不知道 shop 和 api 是同一家咖啡店的，它只比對兩件事：發請求的頁面從哪裡來、回應從哪裡來。兩邊不一樣，它就把回應藏起來。要理解這條規則為什麼存在，最好的方法是想像沒有它的世界。

你登入了咖啡店，session cookie 存在瀏覽器裡。接著你在另一個分頁打開 https://evil.example。這個網站的 JavaScript 呼叫 fetch('https://api.coffee.example/orders', { credentials: 'include' })，會發生什麼事？

  • 請求送得出去。會不會帶著你的 cookie，看 cookie 的 SameSite（第 4 課）：SameSite=None 的 cookie 跨站也會附帶，不管是哪個網頁發的；Lax、Strict 的不會（細節在第 6 課）。這一節假設是 None。
  • 回應讀不回來。瀏覽器收到回應後，發現發請求的頁面來自另一個來源，伺服器也沒有說「這個來源可以讀」，就把回應藏起來，fetch 丟出 TypeError。

如果瀏覽器把這份回應交給 evil.example 的 JS，對方就能用你的登入狀態讀你的訂單、地址、電話，再傳回自己的伺服器。你只是打開了一個頁面，什麼都沒點。瀏覽器為了防這件事定了一條規則，叫同源政策（same-origin policy，SOP）：一個來源的 JavaScript 不能讀另一個來源的回應。

注意它擋的是「讀」，不是「送」。網頁從一開始就能用表單、<img>、<script> 對別的網站發請求，這是網站互相連結的基礎，全部擋掉會讓大量既有網站壞掉。瀏覽器能做到的，是讓別人拿不到結果。

用一段模擬確認這件事。coffeeApi 代表伺服器，browserFetch 代表瀏覽器：先把請求交給伺服器，再看回應標頭決定 JS 能不能讀。執行後看兩行輸出：evil 的 JS 拿到什麼，伺服器上的訂單有沒有成立。

JS 讀不到回應，但伺服器上的訂單已經成立。同源政策保護的是回應的內容，不保護伺服器不收到請求。攻擊者常常根本不需要讀回應，只要請求被執行就夠了，這種攻擊叫跨站請求偽造（CSRF），是下一課的主題。這課先記住：被同源政策擋下，不代表請求沒有執行。

回到咖啡店。前台被擋的原因和 evil.example 一模一樣：在瀏覽器眼中，shop.coffee.example 也是「別的來源」。要讓它讀得到，只有一個辦法：API 在回應裡明確說「這個來源可以讀」，這就是後面要講的 CORS。不過在設定之前，要先弄清楚瀏覽器怎麼判斷「別的來源」：shop 和 api 都在 coffee.example 底下，為什麼不算自己人？

shop 和 api 為什麼算不同來源？

「同一個網站」在瀏覽器裡有兩種定義，嚴格程度不同，用在不同地方：同源政策和 CORS 用嚴格的來源，第 4 課的 SameSite cookie 用寬鬆的站。這兩個很容易混在一起，混了就會在第 6 課的 CSRF 防護上出錯，所以分開講。

來源（origin）由三樣東西組成：scheme（https 或 http）、host（網域名稱）、port。例如 https://shop.coffee.example 的來源是 (https, shop.coffee.example, 443)。https 沒寫 port 就是 443，http 是 80。三樣都相同才是同源，路徑和查詢字串都不算。shop.coffee.example 和 api.coffee.example 的 host 不同，所以不同源，這就是前台被擋的直接原因。

站（site）寬鬆得多，它只看 scheme 和「可註冊網域」。要知道可註冊網域是什麼，得先知道哪些網域字尾是「公共的」。com、com.tw、github.io 這類字尾底下，每個人都能各自註冊自己的網域，它們叫公共字尾，瀏覽器用一份公共字尾清單（Public Suffix List）判斷。公共字尾再往左加一段，就是可註冊網域（registrable domain，也叫 eTLD+1），也就是一個擁有者能控制的範圍：

  • shop.coffee.example 和 api.coffee.example 的可註冊網域都是 coffee.example，所以它們同站（same-site）；不同站就是跨站（cross-site）。
  • coffee.com.tw 是可註冊網域，com.tw 不是。第 4 課提過 cookie 的 Domain 不能設成 com.tw，用的也是這份清單。
  • alice.github.io 和 bob.github.io 是兩個不同的人的網站，因為 github.io 是公共字尾，它們彼此跨站。

site 不看 port，但看 scheme（HTML Standard 的定義）。下表把兩種判斷放在一起比較，第二列就是咖啡店的情況：

網址 A網址 B同源？同站？

第四列也是你開發時會遇到的：Vite 在 5173 port、NestJS 在 3000 port，port 不同就不同源，所以本機開發也會碰到同一個紅字。

前兩行的大寫和 :443、:80 都被正規化掉了，第三行的 5173 不是預設 port，所以保留。最後一行的 data: 網址，來源是字串 null：它沒有可以比較的來源，稱為不透明來源（opaque origin）。沙箱 iframe 裡的頁面發出的請求也會帶 Origin: null。只看到字串 null，分不出是哪一個頁面，所以比對時一律當成不同源；等一下設定 CORS 時也絕對不能信任 null。

同站不等於同源。前台和 API 同站但跨來源，所以前台要讀 API 的回應需要 CORS。反過來，任何一個子網域（例如被遺忘的 promo.coffee.example）發出的請求對 API 來說都是「同站」，SameSite cookie 擋不住它（第 6 課）。
💡 實務上：能同源就先同源，很多團隊根本不用設 CORS
開發時最常見的做法是 Vite 的 server.proxy：前台呼叫 /api/orders，由 Vite 轉給 localhost:3000，瀏覽器只看到一個來源。正式環境也常用 Nginx 或 CDN 把 shop.coffee.example/api 轉到後端，前後端同源，cookie 和 CORS 都單純很多。需要 CORS 的通常是 API 要給好幾個前台共用（前台、店長後台、合作夥伴的網頁）的情況。咖啡店的 API 要同時給前台和店長後台用，所以這課走 CORS 這條路。資深的人遇到 CORS 問題，第一個問題常常是「這裡真的需要跨來源嗎？」，而不是先去改標頭。

現在知道咖啡店的前台和 API 為什麼是不同來源了。下一步是讓 API 告訴瀏覽器：shop.coffee.example 可以讀我的回應。

API 要怎麼告訴瀏覽器「前台可以讀」？

同源政策對咖啡店太嚴了：它擋住 evil.example，也擋住自己的前台。CORS（Cross-Origin Resource Sharing，跨來源資源共用）就是用來開例外的：伺服器在回應標頭裡寫「這些來源可以讀我的回應」，瀏覽器看到了就把回應交給 JS。它是放寬同源政策的機制，不是額外加上的保護。這一點後面會一再用到：CORS 設定只能讓瀏覽器少擋一點，不能讓它多擋任何東西。

這個對話怎麼進行？瀏覽器發跨來源請求時，會自動加上 Origin: https://shop.coffee.example，告訴伺服器「是哪個來源的頁面發的」。這個標頭 JS 改不了，所以伺服器可以拿它來判斷。這只對瀏覽器成立：curl 之類不經瀏覽器的工具可以隨便填 Origin，所以它只能拿來決定要不要回 CORS 標頭，不能當作身分驗證（後面「開了 CORS，API 就安全了嗎？」會講）。伺服器如果同意，就在回應加上 Access-Control-Allow-Origin: https://shop.coffee.example。

至於瀏覽器什麼時候檢查這個標頭，要看請求屬於哪一種。先看最單純、也是咖啡店取訂單用的那一種。

取訂單的 GET：直接送，回來再檢查

有一部分請求，HTML 表單和 <img> 這類標籤本來就送得出去，伺服器也一直都會收到它們。瀏覽器對這類請求不另外詢問，直接送出，等回應回來再決定 JS 能不能讀。Fetch 標準用一份安全清單（CORS-safelisted）定義它們，方法和標頭都在清單裡的請求叫簡單請求（simple request）：

項目安全清單
方法GET、HEAD、POST
標頭名稱（不分大小寫）Accept、Accept-Language、Content-Language、Content-Type、Range
Content-Type 的值只能是 application/x-www-form-urlencoded、multipart/form-data、text/plain，後面的 ;charset=UTF-8 這類參數不影響

這三列是判斷時最常用到的。Range 的格式、字元和長度另有限制，完整規則見課末「補充與查表」。前台取訂單的 GET /orders 沒有自訂標頭，是簡單請求。

回應回來後，瀏覽器做 CORS 檢查，依序看：

  1. 沒有 Access-Control-Allow-Origin → 失敗。
  2. 請求沒帶 cookie，而值是 * → 通過。
  3. 值必須剛好等於請求的來源（逐字比對，多一個結尾的 / 都不行）。
  4. 請求有帶 cookie（credentials: 'include'）時，還要有 Access-Control-Allow-Credentials: true。

注意第 2 點的前提：帶 cookie 的請求，* 不算數。帶 cookie 的回應是某一個使用者的資料，* 的意思是任何網站都能讀，兩者放在一起就等於沒有同源政策，所以瀏覽器不准這種組合。這也是開場第一種解法對咖啡店無效的原因：前台要帶 session cookie，API 必須回明確的來源，再加上 Allow-Credentials: true。

簡單請求一定會抵達伺服器，伺服器也會執行它。CORS 檢查發生在回應回來之後。一個跨站的 POST，Content-Type: text/plain，就算 Console 顯示 CORS 錯誤，伺服器那邊的訂單早就建立了。

取訂單解決了，但前台不只讀資料。顧客修改訂單（例如改杯型）時，前台送的是 PATCH，body 是 JSON，還帶了一個 X-CSRF-Token 標頭。X-CSRF-Token 是前台每次改資料都附上的一串隨機值，用來防第 6 課的 CSRF，這課只需要知道它是一個自訂標頭。這三樣都不在安全清單裡，瀏覽器就不能「先送再說」了。

改訂單的 PATCH，瀏覽器為什麼先多送一個 OPTIONS？

不在安全清單的請求，在 CORS 出現以前，網頁根本送不到別的來源。有些伺服器因此預設這類請求只會來自自己的頁面。如果瀏覽器直接送，等於替這些伺服器開了一個以前不存在的入口，所以瀏覽器改成先問一聲，等伺服器同意了才送。

這一聲詢問叫預檢請求（preflight）：方法是 OPTIONS，用 Access-Control-Request-Method 說「我等一下要用什麼方法」，用 Access-Control-Request-Headers 說「我會帶哪些標頭」。預檢不帶 cookie，也不帶 Authorization，它只是在問規則，不是真正的操作。像 PATCH、Content-Type: application/json、帶 Authorization 或 X-CSRF-Token 的請求，都會觸發預檢。前台改訂單的流程如下：

第 ③ 步，瀏覽器判斷預檢通過的條件（Fetch 標準的 CORS-preflight fetch）：

  • 狀態碼是 200～299（3xx 轉址也算失敗），而且通過上一節那個 CORS 檢查。
  • 方法不是 GET／HEAD／POST 時，要列在 Access-Control-Allow-Methods。方法的比對分大小寫，method: 'patch' 這種寫法會出事，原因見課末「補充與查表」。
  • 每個不在安全清單的標頭都要列在 Access-Control-Allow-Headers（不分大小寫）。咖啡店的 Content-Type（值是 JSON 時）和 X-CSRF-Token 都要列。
  • * 在這兩個標頭裡代表「全部」，但有兩個例外：帶 cookie 的請求 * 不算萬用字元；Authorization 不吃萬用字元，一定要明列。

每次改訂單都先問一次很浪費，所以伺服器可以用 Access-Control-Max-Age 告訴瀏覽器「這次的答案可以快取幾秒」，這段時間內同樣的請求就不再預檢。預設值和上限見課末。

預檢有一個重要的副作用：瀏覽器只在預檢通過後才送出真正的請求，所以「需要預檢」的請求，在 CORS 沒允許時根本到不了伺服器。這和上一節的簡單請求正好相反，也是第 6 課一種 CSRF 防護（要求 JSON 或自訂標頭）的基礎。

💡 實務上：預檢是一次額外的往返，但不要為了省它改寫請求
咖啡店前台每個 application/json 的 PATCH、帶 Authorization 的請求都會先送 OPTIONS，在網路慢的手機上會感覺得到。常見的處理是設合理的 Access-Control-Max-Age，或讓前後端同源，就完全沒有預檢。不要為了避開預檢，把 JSON 改用 text/plain 送、拿掉自訂標頭：這等於讓其他來源的請求不經預檢就直接打到伺服器，也拆掉了下一課 CSRF 防護的基礎。效能優化前先在 Network 面板確認預檢真的是瓶頸。

到這裡，前台讀訂單、改訂單都通了。這時很容易冒出一個想法：既然 CORS 只放 shop 讀，API 是不是就安全了？

開了 CORS，API 就安全了嗎？

不是。CORS 只是伺服器寫給瀏覽器看的標頭，執行規則的也是瀏覽器，沒有瀏覽器在場，這些標頭就沒人理：

  • curl、Postman、手機 App、另一台伺服器，都不看 CORS 標頭，想打哪個 API 就打哪個，想讀什麼就讀什麼。這也是開場時 Postman 打得通、前台打不通的原因。
  • 就算是瀏覽器，簡單請求也照樣送到伺服器並執行。

所以 API 的保護永遠靠第 1 課的認證與授權：這個請求是誰、他能不能做這件事。CORS 設得再嚴，也不能省掉 token 或 session 的驗證。

那 CORS 設錯的危險在哪？在於它打開了同源政策。回想第一節 evil.example 的情境：同源政策是唯一擋住它讀回應的東西。如果 API 允許 evil.example 讀帶 cookie 的回應，使用者只要打開 evil 的頁面，對方的 JS 就能用使用者的 session 讀他的個資、訂單、CSRF token（第 6 課），等於沒有同源政策。

💡 實務上：有人要求「幫我們開 CORS」時先問清楚
合作廠商或另一個團隊說串接被 CORS 擋，先問：是從瀏覽器呼叫，還是從他們的伺服器呼叫？從伺服器呼叫根本不受 CORS 影響，問題在別的地方（網路、認證、防火牆）。真的是瀏覽器呼叫，再問完整的來源是什麼、需不需要帶 cookie，只把那個來源加進清單，不要為了讓對方先動起來，就改成「請求帶什麼 Origin 就回什麼」（反射 Origin，下一節會看到它的問題）。資安掃描或滲透測試通常會檢查 CORS 設定，反射 Origin 再加上允許帶 cookie，是常被標成高風險的項目。

所以 CORS 設定要守住的只有一件事：只對該讀的來源打開。這聽起來簡單，實際上最常出事的，就是判斷「這個 Origin 在不在允許清單裡」的那幾行程式碼。

允許清單怎麼比對，才不會替攻擊者開門？

允許清單比對寫錯，是 CORS 最常見的漏洞。攻擊者能控制的是自己網頁的來源：他可以買任何沒人註冊的網域、在自己的網域下開任意子網域。所以每一種比對寫法都要用一個問題檢查：攻擊者能不能弄出一個通過比對的來源？下面每一種都在真實系統出現過：

寫法攻擊者用什麼來源通過
反射 Origin：請求帶什麼就回什麼，再加上 Allow-Credentials: true任何網站。等於沒有同源政策
origin.endsWith('coffee.example')https://evilcoffee.example（買一個網域就好）
origin.startsWith('https://shop.coffee.example') 或 includeshttps://shop.coffee.example.evil.example
沒有 ^…$ 錨定的正規表示式 /https:\/\/shop\.coffee\.example/同上；另外 . 沒跳脫時連 shopxcoffee.example 都會過
允許 null沙箱 iframe（<iframe sandbox="allow-scripts">）裡的頁面，送的就是 Origin: null
允許所有子網域 *.coffee.example任何一個子網域被入侵；有 XSS 漏洞，讓攻擊者能在那個頁面執行自己的 JS（第 7 課）；或 DNS 還指向已經退租的雲端服務，被別人接手（子網域接管，subdomain takeover）
忘了 Vary: Origin不用攻擊：CDN 或瀏覽器快取把給 A 來源的回應（或沒有 Allow-Origin 的回應）拿給 B 來源，前台時好時壞

第二列看起來最無害，也最常見：「只要是 coffee.example 結尾的就放行」。用 URL 取出 hostname 再比，看起來已經比切字串嚴謹。執行後看四個來源各得到什麼結果：

四個全部放行：

  • evilcoffee.example 是陌生人的網域，字串結尾剛好相同。
  • http://shop.coffee.example 降級成 http。http 沒有加密，和使用者連到同一個 Wi-Fi 的人可以改寫傳輸中的頁面、塞進自己的 JS，這種攻擊叫中間人攻擊；被改寫的頁面就能用這個來源讀 API。
  • :8443 是同一台主機上另一個 port 的服務，可能根本不是前台。

正確的做法只有一種：把允許的來源完整寫出來，逐字比對。瀏覽器送的 Origin 已經是正規化過的格式（小寫、沒有預設 port、沒有結尾 /），清單照這個格式寫就能直接比對，不需要任何字串技巧。

表格最後一列的 Vary 不是攻擊，而是快取造成的錯誤。Node 課第 15 課講過，回應會因為某個請求標頭而不同時，要用 Vary 告訴快取。CORS 的回應正是這樣：同一個 GET /menu，給前台的回應帶 Allow-Origin: https://shop.coffee.example，給店長後台的帶 https://admin.coffee.example。如果 CDN 只用網址當快取的鍵，就可能把給前台的那份拿去回應店長後台，瀏覽器比對來源不符，店長後台就讀不到。Vary: Origin 告訴快取「Origin 不同，要分開存」。Fetch 標準規定，Allow-Origin 不是固定值（不是 * 也不是單一來源）時要用 Vary: Origin。它舉的例子正是沒有 Allow-Origin 的回應被快取起來，再拿去回應允許的來源。所以每個回應都加，包括拒絕的那些。

知道哪些寫法會出事之後，回到咖啡店的 NestJS API，把設定寫出來。

咖啡店的 API 最後怎麼設？

你在 NestJS 課第 6 課寫過 app.enableCors({ origin: [...] })。NestJS 在 Express 平台底下用的是 cors 套件，選項就是它的選項。動手前先看它的預設值，因為沒明寫的選項就會落到這些預設，而其中幾個正是上一節表格裡的寫法：

  • 不給 origin：回 Access-Control-Allow-Origin: *。
  • origin: true：反射請求的 Origin。再加上 credentials: true 就是上一節表格的第一列。
  • origin 給陣列：字串逐字比對、RegExp 用 test()，RegExp 沒錨定一樣會出事。
  • 不給 allowedHeaders：直接反射預檢的 Access-Control-Request-Headers，要什麼給什麼。
  • 預設自己回應預檢（204），不會把 OPTIONS 交給後面的路由。

所以正式環境一律明寫 origin 陣列（純字串）、methods、allowedHeaders。咖啡店的情況是：前台 https://shop.coffee.example、店長後台 https://admin.coffee.example，API 在 https://api.coffee.example。它們同站、跨來源，所以要 CORS，而且前台用 session cookie，要帶 credentials：

app.enableCors({
  origin: config.corsOrigins,            // ['https://shop.coffee.example', 'https://admin.coffee.example']
  credentials: true,
  methods: ['GET', 'POST', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'X-CSRF-Token'],
  maxAge: 600,
})

每一行對應前面講過的一件事：

  • origin：兩個完整的來源字串，逐字比對，對應上一節「把允許的來源完整寫出來」。不用萬用字元、不允許所有子網域，新增一個前台就加一行。
  • credentials: true：回 Access-Control-Allow-Credentials: true，前台帶 session cookie 的請求才讀得到回應。
  • methods、allowedHeaders：預檢時回的 Allow-Methods、Allow-Headers，只列前台真的會用的。前台改訂單用 PATCH、帶 JSON 和 X-CSRF-Token，所以這幾個都在清單裡。
  • maxAge: 600：預檢結果快取 600 秒，減少改訂單時的額外往返。

允許清單從設定讀（NestJS 課第 11 課），因為開發和正式環境的清單不一樣。開發時 Vite 在 http://localhost:5173，只放在開發環境的設定裡；正式環境的清單不能有 localhost：任何人在自己電腦上開 5173 port 的頁面，就能讀到正式 API 的回應。

最後別忘了上上節的結論：CORS 只決定「誰能讀」，每個路由照樣要驗 session 和權限。設定寫好、部署上去之後，前台還是可能跳紅字，這時要知道去哪裡找原因。

設好了還是跳 CORS 錯誤，要從哪裡查？

先知道為什麼不能只看 Console。Console 只會告訴你請求被 CORS 擋了，附一句原因；JS 拿到的只有一個 TypeError，看不到狀態碼。這是刻意的：連「失敗的原因」都可能洩漏跨來源的資訊，例如 evil.example 可以從狀態碼猜出使用者有沒有登入。真正的線索在 DevTools 的 Network 面板，照請求發生的順序查：

  1. 找有沒有 OPTIONS 預檢（Chrome 會把它和真正的請求分成兩列，Type 欄寫 preflight）。有的話先看它：狀態碼是不是 2xx？回應有沒有 Access-Control-Allow-Origin？Allow-Methods、Allow-Headers 有沒有列到你用的方法和標頭？
  2. 預檢沒問題，再看真正的請求：回應有沒有 Allow-Origin？帶 cookie 時有沒有 Allow-Credentials: true？
  3. 用 Origin 標頭重放一次確認：curl -i -X OPTIONS https://api.coffee.example/orders -H 'Origin: https://shop.coffee.example' -H 'Access-Control-Request-Method: PATCH' -H 'Access-Control-Request-Headers: content-type'

第 3 步用 curl 是因為它不執行 CORS，會把伺服器回的標頭原樣印出來，你能看到瀏覽器看到的東西。下表是查的時候最常遇到的情況，看到現象再對照，不用背：

看到的現象原因改哪裡
預檢回 401認證檢查跑在 CORS 之前（自己寫的認證 middleware 排在 cors 前面，或擋在 API 前面統一驗 token 的 API gateway）。預檢不帶 cookie 也不帶 Authorization，當然認證失敗CORS 要排在認證前面；OPTIONS 預檢不需要認證
預檢回 2xx，但帶 Authorization 的請求被擋Allow-Headers: *，以為包含 AuthorizationAllow-Headers 明列 Authorization
不帶 cookie 時正常，加上 credentials: 'include' 就壞Allow-Origin 是 *，或少了 Allow-Credentials: true回明確的來源，加上 Allow-Credentials
Allow-Origin 看起來對，還是被擋值多了結尾的 /、大小寫不同，或回了兩個值允許清單照 new URL(x).origin 的格式寫
改了伺服器設定還是失敗，過一陣子才好預檢結果被快取（Access-Control-Max-Age）等快取過期，或在 DevTools 勾 Disable cache 再測
沒有 Allow-Origin，但狀態碼是 500伺服器出錯，錯誤處理的回應沒經過 CORS middleware先修 500；錯誤回應也要帶 CORS 標頭，前台才讀得到錯誤訊息

最後一列提醒一件事：CORS 錯誤常常只是表象。伺服器出錯、認證擋到預檢，瀏覽器顯示的都是 CORS 錯誤。看到它先別急著改 CORS 設定，更不要改成反射 Origin 讓紅字消失；先看伺服器實際回了什麼狀態碼。

補充與查表

主線用不到、但判斷請求會不會預檢、或寫練習 2、4 時會查的細節。查表用，不用背。

簡單請求的完整安全清單

項目安全清單
方法GET、HEAD、POST
標頭名稱（不分大小寫）Accept、Accept-Language、Content-Language、Content-Type、Range
Content-Type 的值分號前的 MIME 類型（叫 essence，下面寫成「MIME 本體」）只能是 application/x-www-form-urlencoded、multipart/form-data、text/plain，後面的 ;charset=UTF-8 這類參數不影響
Range 的值只有 bytes=開始- 或 bytes=開始-結束（開始不能大於結束）；bytes=-500 這種只寫結尾的不算
字元Accept、Content-Type 的值不能有 " ( ) : < > ? @ [ \ ] { } 和控制字元；Accept-Language、Content-Language 只能有英數字、空白和 * , - . ; =
長度每個值不超過 128 bytes，安全標頭的值加起來不超過 1024 bytes

預檢的兩個細節

  • 方法名稱分大小寫：fetch 只會把 delete、get、head、options、post、put 自動轉大寫，寫成 method: 'patch' 送出去的就是小寫的 patch，對不上 Allow-Methods: PATCH。
  • Access-Control-Max-Age：預檢結果可以快取幾秒，沒寫時是 5 秒；瀏覽器另有自己的上限。

練習

練習 1：寫三個函式。sameOrigin(a, b)：兩個網址同源嗎？來源是 'null' 的（例如 data: 網址）一律不同源。siteOf(url, publicSuffixes)：回傳 scheme + 可註冊網域，格式像 https://coffee.example。公共字尾取清單裡最長的那個；清單裡都沒有時，把最後一段當公共字尾（公共字尾清單的預設規則）；主機本身就是公共字尾（例如 localhost）或是 IP 位址時，用主機本身。sameSite(a, b, publicSuffixes)：兩個網址同站嗎？用 URL 解析，不要自己切字串。

練習 2：寫 needsPreflight(req)，依 Fetch 標準判斷瀏覽器會不會先送預檢。要預檢的情況：方法不是 GET／HEAD／POST（先轉大寫再比）；或有任何一個標頭不在安全清單裡。安全清單照上面的表：標頭名稱不分大小寫；Content-Type 取分號前的 MIME 本體（去掉空白、轉小寫）比對三種之一；Range 要符合 bytes=數字- 或 bytes=數字-數字，而且開始不大於結束；任何一個值超過 128 bytes 就不安全（用 TextEncoder 算 bytes）。這題不處理字元限制和 1024 bytes 的總和限制。

練習 3：寫 API 端的 corsHeaders(req, config)，回傳要加在回應上的 CORS 標頭。規則：

  • 每個回應都有 'Vary': 'Origin'，不論允不允許。
  • 只有 req.origin 逐字等於 config.allowedOrigins 其中一個時才允許：加 'Access-Control-Allow-Origin'，值就是那個來源（不用 *）；config.allowCredentials 時再加 'Access-Control-Allow-Credentials': 'true'。
  • 允許、而且是預檢（req.method === 'OPTIONS'）時，加 'Access-Control-Allow-Methods' 和 'Access-Control-Allow-Headers'，值是設定裡的清單用 ', ' 接起來。不要反射 req.requestHeaders。
  • 不允許時只有 Vary，不要有其他 CORS 標頭。

練習 4：前台的請求被 CORS 擋了，你拿到 Network 面板上的預檢與回應。寫 explainCorsFailure(req, preflight, response)，照下面的順序找出第一個失敗的原因，全部通過回 null。回應標頭的名稱不分大小寫；方法名稱照原樣逐字比對（分大小寫）。

  1. 需要預檢時（用已經寫好的 needsPreflight 判斷；需要時 preflight 一定有給）檢查 preflight：狀態不是 200～299 → status（標準只要求兩者都成立，沒規定先後；這題先看狀態碼，因為 Network 面板上最先看到的就是它）；CORS 檢查失敗 → allow_origin 或 credentials；方法不是 GET／HEAD／POST、不在 Allow-Methods 裡，而且（帶 credentials 或 Allow-Methods 沒有 *）→ method；請求有 Authorization 而 Allow-Headers 沒有明列 → headers；其他不安全的標頭不在 Allow-Headers 裡，而且（帶 credentials 或 Allow-Headers 沒有 *）→ headers。這幾項的 phase 都是 'preflight'。
  2. 最後對 response 做 CORS 檢查，失敗時 phase 是 'response'。

CORS 檢查：沒有 Allow-Origin → allow_origin；不帶 credentials 而值是 * → 通過；值不是逐字等於 req.origin → allow_origin；帶 credentials 而 Allow-Credentials 不是逐字的 true → credentials。Allow-Methods、Allow-Headers 的值用逗號分隔，去掉空白；Allow-Headers 比對不分大小寫。

練習 5：API 完全沒設 CORS 標頭。使用者登入咖啡店後打開 evil.example，它的 JS 執行 fetch('https://api.coffee.example/orders', { method: 'POST', credentials: 'include', headers: { 'Content-Type': 'text/plain' }, body: '{"productId":2}' })。session cookie 設了 SameSite=None; Secure，瀏覽器也沒有封鎖第三方 cookie，API 只檢查這個 cookie，而且不管 Content-Type 都把 body 當 JSON 解析。結果是？

✓ POST 加上 text/plain 是簡單請求，不預檢，直接帶著 cookie 送出（SameSite=None 允許跨站送 cookie，第 6 課詳講。Safari、Firefox 預設會封鎖或分隔第三方 cookie，但伺服器不能靠使用者的瀏覽器設定保護自己）。CORS 檢查發生在回應回來之後，只決定 JS 能不能讀。a 是最常見的誤解：CORS 錯誤不代表請求沒送到。b 錯在 text/plain 不需要預檢。d 錯在 credentials: 'include' 正是要瀏覽器帶 cookie。這就是第 6 課的 CSRF。

練習 6：同事說：「我們的 CORS 只允許 shop.coffee.example，所以內部用的 GET /admin/sales 不用驗 token，反正別的網站讀不到。」錯在哪？

✓ CORS 是伺服器寫給瀏覽器看的標頭，由瀏覽器執行。攻擊者在自己電腦上用 curl 打 API，根本沒有瀏覽器在檢查。CORS 放寬的是瀏覽器的同源政策，不是 API 的門鎖；每個路由都要認證與授權（第 1 課）。c、d 都還是在調整 CORS，問題沒解決。

練習 7：https://shop.coffee.example 和 https://api.coffee.example 是什麼關係？

✓ 來源看 scheme + host + port，兩者 host 不同，所以跨來源，前台要讀 API 需要 CORS。站看 scheme + 可註冊網域，兩者都是 https 和 coffee.example，所以同站，SameSite cookie 會照常送出。不可能「同源但跨站」：同源一定同站。

常見錯誤

  • 以為 CORS 能擋 curl 或其他伺服器：CORS 只有瀏覽器執行。API 的保護靠認證與授權。
  • 以為 CORS 錯誤代表伺服器沒執行：簡單請求一定會抵達伺服器並執行，CORS 只決定 JS 能不能讀回應。
  • 反射 Origin，或用 endsWith、includes、沒錨定的正規表示式比對：攻擊者買一個 evilcoffee.example 或註冊 shop.coffee.example.evil.example 就通過。把允許的來源完整列出、逐字比對。
  • 允許 null：任何網站都能用沙箱 iframe 送出 Origin: null。
  • 忘了 Vary: Origin，或只在允許時才加：快取會把一個來源的回應拿給另一個來源。
  • 正式環境的允許清單留著 http://localhost:5173：開發用的來源只放在開發環境的設定。
  • 把同站當成同源：子網域彼此同站，SameSite cookie 擋不住子網域發的請求；但它們跨來源，讀回應要 CORS。
  • 認證擋到 OPTIONS 預檢：預檢不帶 cookie 也不帶 token，被擋成 401 後，瀏覽器顯示的是 CORS 錯誤，容易查錯方向。CORS 要在認證之前處理。
  • Access-Control-Allow-Headers: * 以為包含 Authorization：Authorization 一定要明列；帶 credentials 時 * 完全不算萬用字元。

小結

  • 前台讀不到 API 的回應，是因為同源政策：一個來源的 JS 不能讀另一個來源的回應。它擋的是「讀回應」，不是「送請求」；跨站請求照樣帶著 cookie 送到伺服器並執行，這是 CSRF 存在的原因。
  • 來源 = scheme + host + port；站 = scheme + 可註冊網域（看公共字尾清單）。shop 和 api 同站但跨來源。同源一定同站，同站不一定同源。
  • CORS 是伺服器放寬同源政策的方式，由瀏覽器執行。簡單請求（GET／HEAD／POST、安全清單內的標頭）直接送出，回來再檢查；其他請求先送 OPTIONS 預檢，通過才送真正的請求。
  • CORS 不是 API 的存取控制：curl、Postman、其他伺服器都不理它，每個路由照樣要認證與授權。
  • 安全的設定：允許清單逐字比對、回明確的來源、每個回應都加 Vary: Origin、帶 cookie 時不能用 *、不信任 null、Allow-Headers 明列 Authorization、正式環境不留 localhost。NestJS 的 enableCors 要明寫 origin、methods、allowedHeaders。
  • 查 CORS 錯誤看 Network 面板：先看預檢的狀態碼和標頭，再看真正的回應；CORS 錯誤常常只是 401 或 500 的表象。
