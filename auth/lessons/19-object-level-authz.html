階段 5：授權：能做什麼、能看哪些資料 · 第 19 課

物件與欄位層級授權：BOLA、BOPLA 與 ABAC

星期一早上，客服轉來一封信。王小明寫道：「我打開『我的訂單』，網址是 /orders/1042。我好奇把 1042 改成 1043，結果看到另一位客人的訂單，有她買了什麼、在哪間門市取餐、還有手機號碼。」那位客人是陳美華。小明的帳號沒有被盜，他也沒有用任何駭客工具，只是改了網址上的一個數字。

上一課的 RBAC 在這裡全部通過了：小明有登入，他的角色也確實有 order:read。問題是 order:read 只回答「這個人能不能使用『看訂單』這個功能」，沒有回答「訂單 1043 是不是他的」。這課的任務就是修好這個洞，並且順著它把咖啡店 API 查一遍：每個請求除了問「能不能做這類事」，還要問「能不能碰這一筆」，以及「這一筆裡的哪些欄位」能改、能看。學完你能在資料存取層把擁有者條件寫成每條路徑都得經過的函式，把「同門市、值班中、金額上限」這類規則寫成可測試的政策函式，並擋下多送欄位改權限、回應夾帶密碼雜湊這兩種常見外洩。

這課的路線：
  1. 小明為什麼看得到美華的訂單，修法要放在哪裡：在查詢本身就帶上擁有者條件，查不到與沒權限一律 404（開場問題的最小答案），再把同一個條件推到改、刪、列表、匯出。
  2. 有人提議「把 ID 換成 UUID 就猜不到了」：為什麼這不能取代擁有者條件。
  3. 店員那一側的規則比「是不是你的」多：上一課老闆的第三個需求「店員只能退自己門市的單」，再加上值班中、金額上限，怎麼寫成一個好測試的政策函式（ABAC）。
  4. 就算是自己的那一筆，也不是每個欄位都能改、都能看：多送 role 把自己升成店長、回應夾帶 passwordHash，兩種欄位層級的漏洞怎麼擋（BOPLA）。
  5. 規則變成「誰跟哪筆資料有什麼關係」時（團購單共同編輯、加盟主看旗下門市），什麼時候該換成 ReBAC。
這課會用到：
  • 第 18 課的 can(user, permission)：問「這個人有沒有 order:refund 這類權限」，只管能不能做這類動作。
  • TypeScript 課第 17 課的 unknown 與型別守衛：不確定形狀的資料先當成 unknown，逐欄檢查過才當成某個型別用。
  • TypeScript 課第 21 課的 Pick、Omit：從既有型別挑出幾個欄位，或去掉幾個欄位。
  • NestJS 課第 7 課的 DTO 與 ValidationPipe：用類別宣告請求 body 的欄位，pipe 在進 controller 前驗證。

小明有 order:read，為什麼看得到美華的訂單？

先把小明的請求從頭走一遍，看它經過哪些檢查。請求帶著小明的 token 打 GET /orders/1043。第一關是認證：guard 驗證 token 的簽章與期限，確認「這是王小明」。第二關是上一課的功能層級授權：小明的角色有 order:read，通過。接著 service 拿 1043 去資料庫查 WHERE id = 1043，查到了，回 200。

每一關都照設計運作，缺的是一個沒有人負責的問題：「訂單 1043 屬於誰？」這類漏洞叫做 BOLA（Broken Object Level Authorization，物件層級授權失效）。這裡的「物件」指的是一筆具體的資料，例如訂單 1043；「物件層級授權」就是針對這一筆檢查「你能不能碰它」，跟上一課針對「一類動作」檢查的功能層級授權是兩件事。BOLA 較早、也很常見的名稱是 IDOR（Insecure Direct Object Reference，不安全的直接物件參照）：API 直接拿請求裡的 ID 去找資料，沒有確認這個 ID 是不是請求者可以碰的。不論 ID 放在網址、query 還是 body，改掉它就能存取別人的資料。

OWASP 是整理網站安全風險的非營利組織，它的 API Security Top 10（2023 版）列出 API 最常見的十類漏洞，BOLA 排第一（API1）。這課後半會遇到的「改到不該改、看到不該看的欄位」排第三（API3）。

BOLA 這麼常見，原因在於分工。認證是通用問題，框架與套件幫你做好了；上一課的權限表也是通用結構，一個 guard 就能套到所有路由。但「訂單 1043 的 customer_id 是 2」是你的業務資料，只有你的程式知道訂單屬於顧客、外帶單屬於門市、發票屬於訂單，沒有框架能替你猜出這些關係。所以這個檢查框架沒辦法替你自動套用，每個帶 ID 的端點都得經過你寫的檢查；每多一個端點，就多一個可能忘記的地方，忘一個就是一個洞。

下面重現小明遇到的情況。Principal 代表「發出這個請求的人」（主體，principal），這裡先只有顧客一種。執行後比較兩行輸出：兩次都回 200。

getOrderBad 只檢查了 order:read，所以小明和美華在它眼裡沒有差別。要修，得讓「這筆訂單是誰的」進到判斷裡。問題是這個判斷要放在哪裡：查出來之後再比對，還是查的時候就帶上？

擁有者條件要放在哪裡：查完再比對，還是查詢時就帶上？

把「這筆是不是你的」這個條件稱為擁有者條件：顧客的訂單屬於下單的顧客，所以條件是 customer_id 等於請求者；店員管的是門市，條件是 store_id 等於他的門市。它有兩種寫法。

第一種是先查再比對：用 id 把訂單查出來，再用 if 比對 order.customerId === principal.id，不符合就拒絕。第二種是查詢時就帶上：把擁有者條件直接寫進 WHERE，別人的訂單根本查不出來。

-- 先查再比對：資料已經進到程式裡，判斷寫錯或忘了寫就外洩
SELECT * FROM orders WHERE id = $1;

-- 查詢時就加條件：別人的訂單根本不會被讀出來
SELECT * FROM orders WHERE id = $1 AND customer_id = $2;

-- 列表、匯出也一樣
SELECT * FROM orders WHERE customer_id = $1 ORDER BY ordered_at DESC;

兩種寫法在小明這個請求上都會擋下來，差別在出錯時會怎樣。這課採用第二種，理由有三個，每一個都對應一種真實的事故：

  • 別人的資料從來沒進到記憶體。先查再比對時，美華的訂單已經在你的程式裡了，接下來是否外洩，全看那個 if 有沒有寫、有沒有寫對。後來有人重構、加了快取、在比對之前先寫了一行 log，資料就可能從那些地方漏出去。查詢時就帶條件，資料庫回給你的本來就只有能看的資料，沒有東西可以漏。
  • 「查不到」和「沒權限」自然變成同一個結果。先查再比對時，程式知道「1043 存在、但不是你的」，很容易回 403。這個 403 本身就是情報：攻擊者把 1 到 99999 都打一遍，回 403 的就是存在的訂單，回 404 的就是不存在，訂單量、編號規則都被摸清楚了，這就是第 1 課講的列舉。查詢時就帶條件，別人的訂單和不存在的訂單一樣查不到，都回同一個 404，什麼都沒透露。
  • 條件只寫一次，所有路徑共用。把它放進資料存取層的一個函式，讀單筆、列表、取消、匯出都呼叫它，就不會有哪條路徑「剛好忘了比對」。

第三點最好直接寫在函式的形狀上：資料存取函式叫 findOrderFor(principal, id)，而不是 findOrder(id)。沒有傳入主體就呼叫不了，「查訂單一定要說是誰在查」變成函式簽章的一部分，呼叫 findOrderFor 時忘了傳主體，編譯就會報錯；至於有沒有人繞過它另外寫查詢，就要靠下面的 review 清單。

下面的範例把顧客和店員都放進來。ownedBy 依主體的種類回傳一個判斷函式，等同 SQL 裡的 WHERE customer_id = $2 或 WHERE store_id = $2；findOrderFor 與 listOrdersFor 都用它。執行後看三行輸出：小明查 1043 得到 undefined（跟訂單不存在一樣），列表只剩自己的，門市 2 的店員只看到門市 2 的訂單。

修好 GET /orders/:id 之後，事情還沒完。BOLA 最常在「大家只修了讀取」的時候再出事，因為同一個 ID 出現在很多端點上，每一個都要經過同一個擁有者條件。下表是 code review 時要逐一確認的路徑（查表用，不用背）：

路徑容易漏掉的原因
PATCH、DELETE /orders/:id、POST /orders/:id/cancel寫入端點常被認為「前端只會對自己的訂單顯示按鈕」
GET /orders、搜尋、分頁列表沒過濾，一次外洩全部
匯出 CSV、報表常另外寫一支查詢，沒經過 repository（NestJS 課第 18 課：專門讀寫資料的那一層）
附件、發票 PDF、圖片下載檔案路徑或下載連結本身被當成授權
巢狀資源 /orders/:id/items/:itemId只檢查 item 存在，沒檢查它屬於這張訂單、訂單屬於你
GraphQL、批次 API一次帶很多 ID，只檢查了第一個

這張表的共同點是：每一列都是「另外寫了一支查詢」或「以為別的東西替你擋了」。前者靠 findOrderFor 收斂，後者靠一個認知：前端只對自己的訂單顯示按鈕、下載連結很長、只檢查了第一個 ID，這些都不是授權。資料庫還可以再加一道防線，讓程式漏了條件時也查不出別人的資料，細節見課末「補充與查表」。

💡 實務上：每個帶 ID 的新端點，review 時都問一句「換個帳號打會怎樣」
咖啡店後台加了「訂單發票下載」，code review 時資深工程師第一個問題通常是：這支查詢有沒有經過 findOrderFor，還是另外寫了一支只用 id 查的新查詢？測試也照這個思路寫：準備小明和美華兩個帳號，用小明的 token 打美華的訂單，斷言回 404，讀、改、刪、匯出各一條。這種測試很便宜，卻能擋下最常見的外洩；資安檢測或滲透測試報告裡，IDOR 也幾乎是固定出現的項目。前端工程師也要有這個意識：前端隱藏按鈕只是體驗，不是保護。

修補的 PR 送出後，有同事在討論串提議另一種做法：「把訂單 ID 從 1042 這種連號改成 UUID，小明就猜不到 1043 了，不是比較省事嗎？」

把 ID 換成 UUID，可以不寫擁有者條件嗎？

UUID 是一串 128 位元、通常隨機產生的識別碼，長得像 3f2a9c1e-…。換成它之後，小明確實沒辦法把最後一位加一就得到下一張訂單。但這只解決了「猜」這一種拿到 ID 的方式。實際上 ID 會出現在很多地方，攻擊者多半是撿到，不是猜到：

  • 網址列、瀏覽紀錄、截圖、客服對話
  • 伺服器和代理的 access log、錯誤追蹤系統
  • 分享連結，以及 Referer 標頭：點連結跳到別的網站時，瀏覽器會在 Referer 標頭附上原本的網址，訂單 ID 就跟著送出去
  • 其他 API 的回應：例如「同桌點餐」列出所有人的訂單 ID

只要 ID 外洩一次，沒有擁有者檢查的 API 就照樣回資料。反過來，有擁有者條件的 API，就算 ID 完全公開也不會出事，因為 findOrderFor 根本不看「你知不知道 ID」，只看「這筆是不是你的」。所以兩者的角色不同：隨機 ID 的真正價值是擋列舉，外人看不出你有幾張訂單、每天賣多少；授權仍然要靠擁有者條件。UUID 可以加，但它是額外的一層，擁有者條件一樣要寫。

有一種情況是你故意讓「拿到連結的人就能看」，例如讓小明把電子收據分享給同事報帳。這時連結本身就是通行證，要把它當成另一種憑證來設計：用密碼學安全的亂數產生器（CSPRNG，第 2 課的 crypto.getRandomValues）產生夠長的 token、有期限、能撤銷、只給看收據不給改，而不是把訂單 ID 直接公開。

到這裡，顧客這一側的規則只有一條：「訂單是不是你的」。但同一張訂單，門市的班長也會碰到，例如幫客人退款。班長的規則就不是一句「是不是你的」說得完了。

班長只能退自己門市、值班中、金額上限內的單：角色表得出來嗎？

咖啡店的退款規則是這樣：

  • 要有 order:refund 權限。這條上一課的 RBAC 管得到。
  • 只能退自己門市的單（上一課老闆的第三個需求），而且要在值班時間內。這條 RBAC 管不到：大家的角色都是「班長」，但每個人的門市與班表各不相同。
  • 訂單狀態要是已付款或已完成；退款金額不能超過訂單總額；超過 2000 元要有大額權限。這些條件取決於這一筆訂單和這一次請求的內容。

如果硬用角色表達，就得開出 shift_lead_store1_morning、shift_lead_store2_evening 這種角色，每間門市乘上每個班別各一個，排班一改就要改角色，這就是上一課說的角色爆炸。而且「金額不超過訂單總額」根本不是角色能表達的，它是兩個數字的比較。

這些規則有一個共同的形狀：拿請求者的某個特徵，和訂單的某個特徵、或現在的時間比較。這些「特徵」就叫做屬性（attribute），依屬性做判斷的模型叫 ABAC（Attribute-Based Access Control，以屬性為基礎的存取控制）。屬性分四類，一個判斷通常會同時用到好幾類：

類別咖啡店的例子
主體（subject）：誰在做權限、所屬門市、班表
資源（resource）：對什麼做訂單的門市、總額、狀態
動作（action）：做什麼退款、改狀態、取消
環境（environment）：在什麼情況下現在時間、請求來源

ABAC 不是用來取代 RBAC 的。權限仍然是第一個條件（沒有 order:refund 就不用往下看），ABAC 在它之上再加屬性條件。前面的擁有者條件其實也是 ABAC 的一個特例：比對主體的 id 和資源的 customerId。

規則一多，最重要的是能測。所以政策要寫成純函式：輸入四類屬性，輸出允許，或拒絕加上原因；函式裡不讀資料庫、不讀時鐘。為什麼連時鐘都不讀？如果函式裡直接呼叫 Date.now()，「班表結束那一刻算不算下班」這種測試就只能等到真的那個時間才跑得出來。把 now 當成參數傳進來，測試想測哪個時間點就傳哪個時間點，每種組合都能直接寫成一條斷言。

政策寫成函式之後，程式裡會出現兩種角色，先給它們名字，後面會一直用到：

  • 政策決策點（PDP，Policy Decision Point）：負責「判斷可不可以」的地方，例如 canRefund(…)。它只回答問題，不碰請求、不改資料。
  • 政策執行點（PEP，Policy Enforcement Point）：拿到判斷結果、實際把請求擋下來或放行的地方，例如 controller、service、guard。

分開的理由是規則要集中。PEP 只做三件事：先查出資料、呼叫 PDP、照結果處理；所有規則都在 PDP 裡。稽核時有一個地方能列出全部規則；規則散在二十個 controller 的 if 裡，沒人能回答「店員到底能做什麼」，改規則時也一定會漏掉某一個。

下面先用比較短的「把訂單標成完成」示範這個結構，它只有三個條件：權限、同門市、值班中；完整的退款規則留給練習 2。執行後看三行輸出：值班中的同門市訂單 200、別間門市 404、下班後 403。

為什麼 other_store 回 404、off_shift 回 403？這是 PEP 的決定，跟前一節同一個道理。別間門市的訂單，這位店員平常在列表裡就看不到，對他來說它「不存在」，回 403 等於告訴他「這張單存在，只是不歸你管」。off_shift 不一樣：訂單是自己門市的，他本來就看得到，回 403 說「你現在不能改」沒有透露任何新資訊。PDP 只給出原因，要回哪個狀態碼由 PEP 依「對方本來看不看得到」決定。

時間區間寫成「開始包含、結束不包含」（start <= now < end）。這樣 9:00～13:00 與 13:00～17:00 兩個班接在一起時，13:00 整只屬於下一班，不會兩邊都算或兩邊都不算。
💡 實務上：規則會一直變，集中在 PDP 才改得動
PM 常會來說「大額退款門檻從 2000 改成 3000」「代班的人也要能退款」。規則集中在 canRefund 裡，改一個地方、補幾條測試就上線；散在各個 controller 就得全專案搜尋，還怕漏一個。拒絕時把 reason 記進 log，客服接到「店員說按退款沒反應」時，查得到是 off_shift 還是 other_store。但回給前端的訊息要節制：該回 404 的情況不要在錯誤訊息裡透露「這是別間門市的單」。

到目前為止，所有檢查都在回答同一個問題：「這個人能不能碰這一筆？」可是通過了這一關，請求還是可能出事。小明改自己的個人資料，資料當然是他的，擁有者條件會放行，但他送進來的 body 裡，可能不只有暱稱。

資料是自己的，就每個欄位都能改嗎？

咖啡店 App 的「編輯個人資料」頁面只有一個暱稱輸入框，前端送出的 body 是 { "nickname": "小明" }。但 API 收到的是什麼，不由你的前端決定。任何人都能打開 DevTools 或用 curl，自己組一個請求：

PATCH /me
{ "nickname": "小明", "role": "manager", "points": 99999 }

如果後端的寫法是「把 body 整個合併進顧客資料」，這三個欄位就全部生效了。這種漏洞叫 mass assignment（大量指派）：程式把請求裡的欄位「一次全部」指派到資料物件上，沒有逐一確認每個欄位能不能被這個人改。它的成因通常是好意：寫 Object.assign(user, body) 或 { ...user, ...body } 很短，前端加了新欄位後端也不用改。代價是後端也不知道自己接受了哪些欄位。

下面的範例重現這個請求，而且多塞了一個 __proto__。執行後看三行輸出：JSON.parse 產生了哪些鍵、合併後的 role 與 points、以及 me.isAdmin。

前兩個結果很直接：role 變成店長、points 變成 99999。第三個結果比較隱蔽，要分兩步看：

  1. JSON.parse 把 "__proto__" 當成一個普通的自有鍵，所以第一行輸出的鍵清單裡有它。到這一步還沒有東西被改壞。
  2. Object.assign 把每個鍵用一般的賦值寫進 me。對一般物件寫入 __proto__ 會觸發它內建的 setter，效果不是新增一個叫 __proto__ 的欄位，而是把 me 的原型換成攻擊者給的物件 { isAdmin: true }。之後讀 me.isAdmin，在 me 自己身上找不到，就沿著原型找到 true。

這種「透過寫入 __proto__ 改到原型」的攻擊叫原型污染（prototype pollution）（Node 課第 25 課）。如果程式裡有某處寫 if (user.isAdmin)，這一行就被騙過了。用遞迴深合併時，影響會擴大到所有物件，細節見課末「補充與查表」。

修法是允許清單（allowlist）：每個端點明確列出「這裡可以改哪些欄位」，清單以外的鍵一律拒絕。為什麼不用黑名單，只擋掉 role？因為黑名單保護的是「寫黑名單那天已經存在的欄位」。下個月有人在顧客表加了 tenantId、emailVerified，沒有人會記得回來更新這個端點的黑名單，新欄位就默默變成可以改的了。允許清單剛好相反：新欄位預設改不了，要有人刻意加進清單才行，忘記的後果只是功能少了，而不是權限漏了。

具體做法有三步：

  • body 先當成 unknown，用 Object.keys 逐一檢查每個鍵都在清單裡。JSON.parse 產生的 __proto__ 是自有鍵，也會被列出來而擋下。
  • 值逐一驗證型別與範圍，全部通過後才組出新的物件。驗證到一半失敗時，原本的資料不能被改到一半。
  • 不同端點用不同的允許清單：顧客改自己的資料只能動 nickname；店長調整點數走另一個端點、另一個權限（stampcard:adjust）。

在 NestJS 裡，允許清單就是 DTO 加上 ValidationPipe 的兩個選項：whitelist: true 會移除 DTO 上沒有驗證裝飾器的屬性，forbidNonWhitelisted: true 把「移除」改成直接回 400。這裡有一個常見的誤會：它保證的只是「body 裡只有 DTO 上的欄位」。如果 DTO 本身就有 role，例如管理員和顧客共用同一個 UpdateUserDto，那 role 對 pipe 來說就是合法欄位，照樣通過、照樣被寫進去。所以每個端點要有自己的 DTO，DTO 上只放這個端點允許改的欄位；service 也不要把 DTO 整個展開進 prisma.user.update({ data: dto })，而是逐欄指定要更新哪些欄位。

寫入的方向擋住了。同一個顧客資料，從 API 回傳出去時也有一樣的問題，只是方向相反：不是收進太多欄位，而是送出太多欄位。

回應裡為什麼有 passwordHash？欄位要選進來，不是漏出去

「查看顧客資料」的 API 是這樣寫的：用 Prisma 把顧客那一列查出來，直接回傳。前端畫面只顯示暱稱，看起來沒問題。但那一列裡還有 passwordHash、mfaSecret、客服寫的內部備註，它們全部跟著 JSON 送到瀏覽器，打開 DevTools 的 Network 分頁就看得到。這叫過度資料暴露（excessive data exposure）：API 回傳的欄位比這個讀者需要的多。「前端沒顯示」不是保護，因為資料已經離開伺服器了。

前一節的 mass assignment 和這一節的過度資料暴露，在 OWASP 2019 年版是分開的兩項，2023 版把它們合併成同一項：BOPLA（Broken Object Property Level Authorization，物件屬性層級授權失效），也就是開場提到的 API3。「物件屬性」指的是一筆資料裡的欄位，BOPLA 的意思就是授權只做到「能不能碰這一筆」，沒有做到「這一筆裡的哪些欄位能改、能看」。兩個方向的修法也是同一個想法：允許清單。

回傳時的允許清單，是依「誰在看」決定要哪些欄位，並用型別把每種回應寫清楚。這裡要用 Pick（列出要哪些欄位，等於允許清單），不要用 Omit（列出不要哪些欄位，等於黑名單），理由跟上一節一樣：資料表新增 resetToken 欄位時，Omit 會自動把它帶出去，Pick 不會。下面的範例比較兩種寫法，執行後看兩行輸出各剩哪些鍵。

黑名單只刪了 passwordHash，mfaSecret 和 internalNote 照樣出去；允許清單只有 id 和 nickname。

有一個陷阱要特別注意：Pick 只管型別，不管執行時送出什麼。TypeScript 用的是結構型別，只要物件「至少有」型別要求的欄位就算符合，多出來的屬性不會報錯。所以 toPublicView 如果偷懶直接 return c，一樣能通過 PublicCustomer 的型別檢查，但執行時整列資料照樣全部送出。型別擋不住，一定要像上面那樣一個欄位一個欄位建立新物件。更早一步的做法是查詢時就用 Prisma 的 select 只拿需要的欄位（NestJS 課第 14 課），讓 passwordHash 根本不離開資料庫，跟前面「擁有者條件寫進查詢」是同一個思路。

「誰在看」也不只分「本人」和「外人」。同一個顧客的手機號碼：本人看到完整的；同門市的店員為了取餐時聯絡，看到遮罩後的 0912-***-678；其他人看不到。這也是授權，只是粒度細到欄位，練習 3 就是照這個規則寫回應。

💡 實務上：回應物件是 API 合約，欄位要「選進來」而不是「漏出去」
常見的事故是：後端為了省事直接回傳整列，後來有人在 customers 加了內部備註或重設密碼的 token，就默默出現在 API 回應裡，直到有人打開 Network 才發現。實務上會為每種讀者寫一個轉換函式或回應 DTO（顧客版、店員版、後台版），新增資料表欄位時預設不會出去，要有人刻意加進來。上線前可以實際用不同角色登入，看 DevTools Network 的回應內容，這是前端工程師最容易做的檢查。列表 API 特別要注意：一次回傳上百筆，多一個敏感欄位就是上百筆外洩。

回頭看這課修過的規則，「訂單是不是你的」「是不是同門市」「手機號碼給誰看」，都是拿主體的一個屬性和資料的一個屬性比對，一個函式就寫得完。但咖啡店接下來要做的功能，規則的形狀開始不一樣了。

規則變成「誰跟誰有關係」時：要不要換成 ReBAC？

看兩個即將上線的需求：

  • 小明開了一張團購單，分享給三個朋友，朋友可以加品項但不能結帳。
  • 咖啡店開放加盟，加盟主可以看旗下所有門市的報表；門市換了加盟主，權限要跟著換。

這兩條規則的關鍵不在某個屬性的值，而在「關係」：美華是不是這張團購單的編輯者？林志豪是不是門市 3 的加盟主？而且關係會一層接一層，加盟主之上還可能有區域經理、品牌總部。用 ABAC 硬寫，就得把「這張團購單分享給了誰」「這位加盟主有哪些門市」都變成屬性，每次判斷都要先把整串關係查出來，層級一多就很難維護。

ReBAC（Relationship-Based Access Control，以關係為基礎的存取控制）換一個角度：把權限存成一張「誰和哪筆資料有什麼關係」的關係圖，例如 團購單#7 的 owner 是 小明、團購單#7 的 editor 是 美華、門市#3 的 franchisee 是 林志豪；再另外定義規則，例如「editor 可以加品項」「門市的 franchisee 可以看該門市的報表」。判斷時沿著關係圖找路徑。門市換加盟主，只要改一筆關係，規則不用動。

一次判斷實際上這樣走：問「美華能不能在團購單#7 加品項」，系統找到 團購單#7 的 editor 是 美華，再套上規則「editor 可以加品項」，結果允許。問「林志豪能不能看門市 3 的報表」，就沿著 門市#3 的 franchisee 是 林志豪 判斷；之後公司多了區域經理，只是多一層關係（區域管門市、經理管區域），規則照樣沿著路徑走。反過來問「林志豪能看哪些門市」，就是從林志豪出發沿著關係列出所有門市，這正是列表 API 需要的查詢，也是下表說 ReBAC 擅長列表的原因。

這是 Google 在 Zanzibar 論文描述的模型，開源實作有 OpenFGA、SpiceDB 等。

三種模型不是互斥的，而是各自擅長回答不同的問題：

模型擅長代價
RBAC功能層級：誰能用退款功能表達不了「這一筆」；例外多就角色爆炸
ABAC依屬性的條件：同門市、值班中、金額上限規則多了難以一眼看懂；要確保屬性來源可信
ReBAC分享、組織階層、「我能看哪些東西」的列表多一套服務與資料要同步、要維運；查詢多一次網路往返

ReBAC 的代價寫在表的最後一格：它通常是一個獨立的授權服務，關係資料要和你的主資料庫保持同步，多一套服務要部署、監控，每次判斷也多一次網路往返。所以資深的判斷是：咖啡店的規則幾條 ABAC 函式就寫得完，就不要引入 ReBAC 服務。等到出現大量分享關係、多層組織，而且多個服務要共用同一套授權資料時，才值得付出同步與維運的成本。

補充與查表

主線用不到、但設計資料庫防線或查原型污染時會用到的細節。

資料庫層的第二道防線：Row Level Security

PostgreSQL 的 Row Level Security（RLS）讓「這個連線只看得到這些列」由資料庫強制（PostgreSQL 課第 24 課）。程式漏了一個擁有者條件，RLS 還在。這是縱深防禦，不是取代程式裡的條件；下一課會用它做租戶隔離。

深合併與 Object.prototype

主線的範例用的是 Object.assign，只換掉了 me 一個物件的原型。如果程式用遞迴的「深合併」把 body 合進設定或資料，攻擊者甚至能改到 Object.prototype，讓所有物件都多出這個屬性。這也是 body 要先用允許清單過濾、再組出新物件的原因之一。

練習

練習 1：OrderService 的三個方法都有 BOLA：只用 id 找訂單，列表也沒過濾。修好它：

  • 顧客只能碰自己的訂單（customerId 等於自己的 id）；店員只能碰自己門市的訂單（storeId 相同）。顧客與店員是兩張表，id 可能剛好一樣。
  • getOrder、cancelOrder：訂單不存在、或不是你能碰的，一律回同一個 { status: 404, body: { error: 'not_found' } }；沒權限時訂單不能被改到。
  • listOrders 只回你能碰的訂單。

建議把擁有者條件寫成一個私有方法，三個方法共用。

練習 2：寫 ABAC 政策 canRefund(subject, order, req, env)。照下面的順序檢查，第一個不符合的就回它的 reason：

  1. 主體沒有 order:refund → no_permission
  2. 主體的門市不是訂單的門市 → other_store
  3. env.now（毫秒）不在任何一個班表區間內 → off_shift（區間開始包含、結束不包含）
  4. 訂單狀態不是 paid 或 done → bad_status
  5. 退款金額不是正整數 → invalid_amount
  6. 退款金額超過訂單總額 → amount_exceeds_total
  7. 金額超過 2000 而且沒有 order:refund:large → needs_large_permission

全部通過回 { allow: true }。

練習 3：PATCH /me 與「查看顧客資料」都有 BOPLA。寫兩個函式：

applyProfileUpdate(user, body)：body 是 JSON.parse 的結果（unknown）。

  • body 不是一般物件（null、陣列、字串、數字）→ invalid_value。
  • 只允許 nickname（字串，1～20 個字元，用 [...s].length 算）與 favoriteDrink（MENU_IDS 裡的值）。有其他任何鍵 → unknown_field；鍵都合法但值不對 → invalid_value。
  • 成功時回傳新的顧客物件；不論成功或失敗，都不能改到傳入的 user。

toCustomerView(viewer, customer)：依「誰在看」回傳新物件，只能有下表的欄位：

誰在看欄位
本人（顧客，id 相同）id、nickname、name、phone（完整）、favoriteDrink、points
同門市的店員（storeId 相同）id、nickname、name、points、phone（遮罩：0912345678 → 0912-***-678）
其他人（別的顧客、別門市的店員）id、nickname

練習 4：訂單 ID 從連續數字改成隨機的 UUID 之後，GET /orders/:id 還需要檢查訂單是不是你的嗎？

✓ c。UUID 擋的是「一個一個猜」與列舉，不是授權：攻擊者通常不是猜到 ID，而是從別的地方拿到 ID（a 錯）。產生方式安全與否只影響能不能猜，不影響「拿到 ID 的人能不能看」（b 錯）。只檢查登入，任何登入的顧客拿到 ID 就能看，正是 BOLA（d 錯）。

練習 5：NestJS 全域開了 new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })。PATCH /me 用的是管理後台也在用的 UpdateUserDto，裡面有 nickname 和 role 兩個欄位（都有驗證裝飾器）。service 寫 prisma.user.update({ where: { id: me.id }, data: dto })。顧客送 { "role": "manager" } 會怎樣？

✓ b。whitelist 只移除「DTO 上沒有驗證裝飾器」的屬性，forbidNonWhitelisted 只是把移除改成回錯誤（a、c 錯）。它保證的是「body 不超出 DTO」，DTO 本身該不該有 role，是你的設計。修法：每個端點自己的 DTO（顧客的只有 nickname），service 逐欄指定要更新的欄位，不要把 DTO 整個交給 data。

練習 6：咖啡店開放加盟。需求是「加盟主可以看旗下所有門市的營收報表；門市換了加盟主，權限立刻跟著換」，而且之後還會有區域經理、品牌總部等層級。哪種模型最自然？

✓ c。這個需求的本質是多層的「關係」，而且關係會變動，ReBAC 改一筆關係就生效。a 是角色爆炸：每位加盟主一個角色、換門市要改角色定義。b 擋不住直接打 API。d 能做，但清單塞在 token 裡，換加盟主時舊 token 在過期前還有效（第 11 課的過期權限），層級一多清單也會失控。規則只有一兩條、沒有多層組織時，ABAC 函式查資料庫就夠了，不必引入 ReBAC 服務。

常見錯誤

  • 只在 GET 檢查擁有者：PATCH、DELETE、取消、匯出、附件下載、巢狀資源一樣要。把條件放進 findOrderFor(principal, id) 這類資料存取函式，讓每條路徑都得經過它。
  • 先查出資料再判斷，回 403：洩漏了資料存在與否，也讓資料先進了記憶體。查詢時就加條件，查不到一律 404。
  • 以為 UUID 就安全：隨機 ID 擋列舉，不擋外洩後的存取。擁有者檢查照寫。
  • 把 request body 直接展開或 Object.assign 進資料：攻擊者多塞 role、points、__proto__ 就改到了。用每個端點自己的允許清單，逐欄驗證後組出新物件。
  • 用黑名單擋欄位：新增的欄位不會自動被擋，不管是寫入（擋 role 漏 points）還是回傳（刪 passwordHash 漏 mfaSecret）。
  • 直接回傳 ORM entity：前端沒顯示不代表沒送出。依「誰在看」組出新的回應物件，或在查詢就用 select 只拿需要的欄位。
  • 授權規則散落在各個 controller：沒人能完整列出規則，也沒辦法測。規則集中在政策函式（PDP），controller、service 只負責執行（PEP）。

小結

這課從小明改網址看到美華的訂單開始，把咖啡店 API 的授權從「能不能做這類事」補到「能不能碰這一筆、這一筆的哪些欄位」：

  • BOLA（API1）：有功能權限不代表能碰每一筆。訂單屬於誰是業務資料，只有你的程式知道，框架幫不了。
  • 在查詢時就加上擁有者條件（WHERE id = $1 AND customer_id = $2），包成 findOrderFor(principal, id)，讀、改、刪、列表、匯出、附件全部走它；查不到與沒權限都回 404。RLS 是資料庫層的第二道防線。
  • UUID 不是授權，它只讓猜測與列舉變難；ID 外洩之後，擋住存取的仍是擁有者條件。
  • 班長的退款規則要比對主體、資源、動作、環境的屬性，這是 ABAC；政策寫成注入 now 的純函式（PDP），集中一處，由 controller、service 執行（PEP），並依「對方本來看不看得到」決定回 404 還是 403。
  • BOPLA（API3）：資料是自己的，也不是每個欄位都能改、都能看。寫入用允許清單擋 mass assignment（含 __proto__），驗證全部通過才組出新物件；回應依「誰在看」挑欄位，用 Pick 不用 Omit，並建立新物件。
  • RBAC 管功能、ABAC 管條件、ReBAC 管關係；規則少時用 ABAC 函式，關係多層又要跨服務共用時才考慮 ReBAC。
