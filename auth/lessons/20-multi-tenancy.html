階段 5：授權：能做什麼、能看哪些資料 · 第 20 課

多租戶隔離

咖啡店的點餐系統做得不錯，別的咖啡品牌也想用。你把它改成一套系統賣給很多品牌：山丘咖啡、巷口咖啡各自有門市、店員、顧客、訂單，共用同一個 API、同一個資料庫。上線第一週，山丘咖啡的店長打電話來：信義店（門市 1）今天的營收報表是 310 元，收銀機的帳只有 190 元；點開明細，多出來的那一筆是巷口咖啡中山店的訂單，上面還有對方顧客的名字。反過來，巷口咖啡的店長也看得到山丘咖啡的營收。對一套賣給很多品牌的系統，這種事故一次就可能讓所有客戶一起離開。

這一課的任務：找出這筆訂單為什麼會跑進別人的報表，然後把系統改成就算某個工程師忘了寫租戶條件，資料也不會漏到別的品牌。做完之後，你會知道每一層該擋哪一種錯：程式、資料庫、快取與背景工作，以及自家客服要跨品牌查資料時該怎麼留紀錄。

這課的路線：
  1. 為什麼山丘咖啡的報表多出巷口咖啡的訂單：每筆資料多了「屬於哪個租戶」這層歸屬，查詢沒用它就會漏（開場問題的最小答案）。接著決定資料要共用表、分 schema 還是分資料庫。
  2. 這個請求屬於哪個租戶：為什麼不能相信前端送的 X-Tenant-Id，租戶要從登入的身分決定。
  3. 幾百個查詢怎麼讓人忘不了加 tenant_id：repository 自動加條件、複合外鍵擋跨租戶參照、RLS 擋繞過程式的 SQL，以及連線池上的 SET LOCAL。
  4. 資料離開資料庫之後：快取 key、背景工作、檔案路徑這些 code review 常看不到的事故點。
  5. 跨租戶的合理需求與共用資源：客服怎麼查山丘咖啡的問題又留下紀錄，巷口咖啡跑大報表時怎麼不拖慢山丘咖啡。
這課會用到：
  • 第 19 課的物件層級授權：在查詢時就加上條件（WHERE id = $1 AND customer_id = $2），查不到一律 404。租戶條件是同一個想法，只是範圍更大。
  • PostgreSQL 課第 24 課的 RLS：表開啟後，資料庫依政策自動過濾每一列；政策可以用 current_setting 讀這條連線上用 set_config 設好的值。
  • Node 課第 19 課的 AsyncLocalStorage：讓同一個請求裡的所有函式拿到同一份上下文。

為什麼山丘咖啡的報表多出巷口咖啡的訂單？

先把現在的處境說清楚。原本的系統只服務一家咖啡店；現在你經營一套系統，很多品牌付月費共用它，品牌不用自己架伺服器，也不用自己維護程式。這種賣法叫 SaaS（Software as a Service，軟體即服務）。

共用這套系統、但資料必須跟別人分開的每一個客戶，叫做一個租戶（tenant）。在這裡，一個咖啡品牌就是一個租戶：山丘咖啡是租戶 1，巷口咖啡是租戶 2。一套系統同時服務多個租戶，叫多租戶（multi-tenancy）。多租戶系統對客戶最基本的承諾是租戶隔離（tenant isolation）：A 租戶永遠看不到、也改不到 B 租戶的資料。功能少一個、畫面醜一點，客戶都還能忍；隔離破一次，客戶失去的是營收數字和顧客名單，你失去的是所有客戶的信任。

看圖裡的門市編號。單一品牌的時代，「門市 1」全公司只有一間，storeId 就足以指出是哪間店。多租戶之後，山丘咖啡的信義店是門市 1，巷口咖啡的中山店也是門市 1：門市編號只在自己的租戶裡唯一。下面是單一品牌時代寫的營收函式，原封不動搬到多租戶系統上。執行後看第一行印出的營收：

第一行印出 310，把巷口咖啡門市 1 的 120 元也算進去了，這就是店長看到的那個數字。storeRevenue 只問「是不是門市 1」，從來沒問「是不是山丘咖啡的門市 1」，因為寫它的時候根本沒有第二個品牌。加上 tenantId 條件後，第二行回到正確的 190。

注意這個錯有多安靜：沒有例外、沒有錯誤訊息，數字只是「多了一點」。所以這類漏洞通常不是被測試或攻擊者發現，而是某天客戶打電話來問「為什麼報表上有我不認識的顧客」，那時資料已經漏出去了。

這就是開場問題的最小答案：多租戶之後，每一筆資料都多了一層歸屬，它屬於哪個租戶；每一次讀寫都要用目前請求的租戶加上條件，而這個租戶要從登入的身分決定。這跟第 19 課的「這張訂單是不是這位顧客的」是同一個想法，只是範圍從一個人擴大到一整個品牌。

加一個條件看起來很簡單。但在動手改幾百個查詢之前，要先決定一件更根本的事：所有品牌的資料，真的要放在同一張表裡嗎？

所有品牌的資料要放在同一張表嗎？

把租戶分開，有三種常見的做法，差別在「分開」發生在哪一層：同一張表裡用欄位分、同一個資料庫裡用 schema 分，或者乾脆每個租戶一個資料庫。

中間那種要先認識 schema。在 PostgreSQL 裡，schema 是資料庫裡放表的命名空間，像資料夾一樣：同一個資料庫可以有 tenant_hill.orders 和 tenant_alley.orders 兩張同名的表，各在自己的 schema 底下。SQL 裡只寫 orders 沒寫 schema 時，PostgreSQL 依連線上的 search_path 設定決定去哪些 schema 找（PostgreSQL 課第 26 課）。所以「每個租戶一個 schema」的做法，是請求進來時把連線的 search_path 切到那個租戶的 schema。

共用表，每列帶 tenant_id每個租戶一個 schema每個租戶一個資料庫
做法所有租戶的訂單都在同一張 orders，用 tenant_id 欄位區分同一個資料庫裡，每個租戶一個 schema：tenant_hill.orders、tenant_alley.orders每個租戶一個獨立的資料庫，甚至獨立的機器
隔離靠什麼每個查詢都要加 WHERE tenant_id = …；再加 RLS 當保險連線時切換 search_path；忘記切就會查到別人的連到哪個資料庫；連錯才會出事
成本最低：一套表、一套連線池中等：表的數量 ＝ 租戶數 × 表數最高：每個租戶一份資源、備份、監控
改 schema（migration）跑一次每個租戶跑一次，幾百個租戶時會有跑到一半失敗的問題每個資料庫跑一次，同上
跨租戶統計（平台營收）一個查詢要合併每個 schema要到每個資料庫拿再合併
適合大多數 SaaS 的起點；租戶多、每個不大租戶數量不多、需要比較強的隔離大客戶、法規要求資料分開存放、需要獨立的效能保證

從左到右，隔離越來越強，代價也越來越高。共用表最便宜，但隔離完全靠你的程式和資料庫設定，開場那種事故就是它的典型症狀。每租戶一個資料庫隔離最強，可是每多一個客戶就多一份要備份、監控、升級的資料庫；改一次表結構要對每個資料庫各跑一次 migration，幾百個租戶時，一定要處理「跑到一半某些租戶失敗」的情況。平台自己想算「全部品牌這個月的總營收」，也要到每個資料庫拿再合併。

實務上常見的路線是從共用表開始，等某個大客戶要求獨立的資料庫（或付得起），再把它搬出去，變成混合模式。這課的程式碼都以共用表為主：它最便宜，也最容易出錯，開場的事故就發生在它身上，值得把防線一層一層講清楚。

也不要以為選了分 schema、分資料庫就自動安全。程式裡的連線池、快取、背景工作一樣要知道「現在是哪個租戶」，只是忘記時的症狀不同：共用表是「多看到別人的幾列」，分開放是「整個連到別人那邊」。

💡 實務上：選隔離方式前，先問清楚客戶是誰
新的 B2B 產品（給店家、公司用的後台）幾乎都從共用表加 tenant_id 開始，第一天就把欄位放進每張表，比上線後再補容易太多。資深工程師會先問 PM 和業務：預計幾個租戶、有沒有大客戶在合約裡要求資料分開存放或指定機房、需不需要單獨還原某個租戶的資料。如果答案都是「沒有」，就不要一開始就做每租戶一個資料庫，維運成本會拖垮小團隊。反過來，只服務自己品牌的系統（像前幾課的單一咖啡店）根本不需要多租戶，有 store_id 就夠了。

不管選哪一種，程式都要先回答同一個問題：共用表要用租戶加條件，分 schema 要用它切 search_path，分資料庫要用它選連線。這個「現在是哪個租戶」的答案，要從哪裡來？

這個請求屬於哪個租戶？

每個請求進來，後端都要先回答「這個請求屬於哪個租戶」。這個答案叫租戶上下文（tenant context），後面的查詢、快取、背景工作都靠它。它錯了，後面每一層都會很認真地幫你查出別人的資料。

很多團隊第一個想到的做法是：Vue 前台本來就知道自己是哪個品牌，每個請求帶一個 X-Tenant-Id 標頭給後端。問題在第 1 課說過的：請求裡的任何東西都可以被偽造。山丘咖啡的店員打開 DevTools，把標頭裡的 1 改成 2，就換成了巷口咖啡。登入只證明「你是山丘咖啡的店員」，不證明「你可以看你送來的那個租戶」。

所以要逐一看每個候選來源，問同一個問題：這個值是伺服器自己確認過的，還是客戶端說了算？

來源能不能當依據原因
登入的主體（店員帳號屬於山丘咖啡）可以，這是唯一的依據伺服器自己查資料庫或驗過簽章得到的，客戶端改不了
子網域 hill.coffeepos.example只能當路由提示，要和主體一致網址是使用者輸入的，任何人都能打 alley.coffeepos.example
X-Tenant-Id 標頭、body 或 query 裡的 tenantId不行客戶端想送什麼就送什麼，打開 DevTools 改一個數字就換租戶

子網域和標頭不是完全沒用：前端可以送它們當提示，例如讓 API 回「你在錯的網址」，或決定登入頁要顯示哪個品牌的 logo。但決定查哪個租戶的資料時，後端只用主體的租戶。下面的 resolveTenant 就是這個規則：主體的租戶是答案，子網域只拿來比對，標頭完全不看。執行後看三行結果的 tenantId 和 status：

  • 同一位店員多帶了 x-tenant-id: 2：結果還是租戶 1，標頭被忽略。

那主體身上的租戶又是從哪來的？要看你用哪一種登入方式：

用 session（第 4 課）時，登入成功就把 tenantId 存進伺服器端的 session，或每次請求用 userId 去資料庫查。這兩種都是伺服器自己保存的資料，客戶端碰不到。

用 JWT（第 8、9 課）時，可以把 tenant_id 放進 payload，簽章保證它沒被改過。但第 11 課說過 token 裡的資料可能過期：店員被調到別的品牌，舊 token 在到期前仍然帶著舊租戶。重要操作時用資料庫的最新狀態。

還有一種情況要先想好：一個人屬於多個租戶，例如加盟顧問同時服務兩個品牌。這時登入後讓他選一個，伺服器檢查「他確實是這個租戶的成員」之後，把選擇存進 session，或發一個只帶這個租戶的 token。之後每次切換租戶，都等於再檢查一次成員資格，不能讓前端直接改。

用子網域區分品牌時，session cookie 的設定也會影響隔離，細節見課末「補充與查表」。

到這裡，租戶有了可靠的來源。回頭看開場的 storeRevenue：它的問題不是拿不到租戶，而是寫的人沒用它。系統有幾百個查詢，每個人寫新功能時都要記得加 tenant_id，總有一次會忘。怎麼讓「忘記」不再造成事故？

幾百個查詢，怎麼讓人忘不了加 tenant_id？

靠每個人記得，是把安全押在注意力上。資深的做法是改變結構，讓忘記變得很難，而且就算忘了也有別的東西擋住。這一節建立三道防線，每一道擋一種不同的錯：業務程式碼忘了加條件、資料指到別的租戶、有人繞過程式直接寫 SQL。最後再處理第三道防線在連線池上的一個陷阱。

第一道：業務程式碼忘了加條件，交給 repository 自動加

開場的 storeRevenue 自己寫了查詢邏輯，所以有機會漏掉條件。如果所有存取資料的程式都必須經過同一層，而那一層自己加條件，業務程式碼就根本沒機會忘記。這一層叫 repository：專門負責讀寫資料的那一層（NestJS 課第 18 課的分層）。業務程式碼呼叫 orders.findById(id)，repository 自己從上下文拿到目前的租戶，自己加上 tenant_id 條件。

接著的問題是：repository 怎麼知道「目前的租戶」？最直接的做法是從 controller 一路把 tenantId 當參數傳下去，經過 service、經過每個輔助函式，最後到 repository。這很囉唆，而且中間只要有一個函式沒傳，就又回到「有人忘記」的老問題。

Node 提供的解法是 AsyncLocalStorage（Node 課第 19 課）。它像一個「跟著這個請求走」的盒子：請求進來時用 run() 放進一份資料，這個請求之後所有的 await、callback 裡呼叫 getStore() 都拿得到同一份，就算同時有好幾個請求在跑也不會拿錯。在 run() 之外呼叫 getStore() 會得到 undefined（Node 24 文件）。下面是把租戶放進盒子、再從 repository 取出的寫法：

// Node.js（這段在瀏覽器的練習區不能執行，Worker 裡沒有 node:async_hooks）
import { AsyncLocalStorage } from 'node:async_hooks'

const tenantContext = new AsyncLocalStorage<{ tenantId: number }>()

// 認證之後的 middleware：租戶來自 principal，不是請求
app.use((req, res, next) => {
  tenantContext.run({ tenantId: req.principal.tenantId }, next)
})

// repository 拿租戶：沒有上下文就丟錯，絕不用預設值
export function currentTenantId(): number {
  const ctx = tenantContext.getStore()
  if (!ctx) throw new Error('沒有租戶上下文：這段程式不是在請求或工作裡執行的')
  return ctx.tenantId
}

注意最後那個 throw。getStore() 拿不到上下文，代表這段程式不是在某個請求或工作裡執行的，例如有人在啟動程式裡直接呼叫了 repository。這時有兩種選擇：退回一個「預設租戶」或乾脆不加條件，讓程式繼續跑；或者直接丟錯。這裡選後者，叫失敗關閉（fail closed）：找不到租戶時寧可整個請求出錯，也不要猜一個。退回預設值的程式碼平常都正常，因為平常都有上下文；一旦出事，就是全部租戶的資料混在一起，而且沒有任何錯誤提醒你。AsyncLocalStorage 有一個跟預設值有關的建構子選項，課末「補充與查表」說明為什麼不要用它設預設租戶。

讀取擋住了，寫入也一樣要擋。第 19 課的 mass assignment 是指把請求 body 整包寫進資料，讓客戶端有機會多塞一個不該由它決定的欄位。在多租戶系統裡它更危險：body 多塞一個 "tenantId": 2，資料就被寫進巷口咖啡。所以 tenantId 一律由上下文填入，不從 body 來；更新時也不能讓 body 改掉既有資料的 tenantId。練習 1 會實作這樣的 repository。

repository 管住了「查的是哪個租戶的資料」。但它管不住資料內容裡的參照：山丘咖啡的店員建立訂單時，送來的商品 id 如果是巷口咖啡的商品呢？

第二道：訂單指到別家的商品，交給複合外鍵擋

這種錯叫跨租戶參照（cross-tenant reference）：A 租戶的資料指到 B 租戶的資料。repository 會把訂單項目正確地存成租戶 1，可是項目裡的 product_id 指的是巷口咖啡的商品；之後報表一 join，山丘咖啡的訂單上就出現巷口咖啡的商品名稱和價格。

一般的單一欄位外鍵 product_id REFERENCES products(id) 擋不住，因為它只檢查「這個商品存在」，不管它屬於誰。解法是複合外鍵（composite foreign key）：用 (tenant_id, product_id) 兩個欄位一起參照，資料庫要找到「同一個租戶底下的這個商品」才放行。PostgreSQL 課第 38 課用 store_id 做過同樣的事：

CREATE TABLE products (
  tenant_id bigint NOT NULL,
  id        bigint NOT NULL,
  name      text   NOT NULL,
  price     integer NOT NULL,
  PRIMARY KEY (tenant_id, id)
);

CREATE TABLE order_items (
  tenant_id  bigint NOT NULL,
  order_id   bigint NOT NULL,
  product_id bigint NOT NULL,
  quantity   integer NOT NULL,
  FOREIGN KEY (tenant_id, product_id) REFERENCES products (tenant_id, id)
);

INSERT INTO products VALUES (1, 10, '拿鐵', 110), (2, 20, '美式咖啡', 80);
INSERT INTO order_items VALUES (1, 1, 10, 1);   -- 成功：租戶 1 的訂單、租戶 1 的商品
INSERT INTO order_items VALUES (1, 2, 20, 1);   -- 失敗：租戶 1 的訂單指到租戶 2 的商品
-- ERROR:  insert or update on table "order_items" violates foreign key constraint
--         "order_items_tenant_id_product_id_fkey"（SQLSTATE 23503）

上面的錯誤訊息是用 PGlite 0.5.13（PostgreSQL 18.6）實際跑出來的。資料庫只認 (1, 20) 這個組合，租戶 1 沒有商品 20，所以擋下來。這一招不需要任何應用程式的配合：不管是 repository、手寫的匯入腳本還是直接連進資料庫的人，都寫不進跨租戶的參照。

前兩道都有一個前提：讀資料的 SQL 是經過 repository 寫的。可是總有人會繞過它，例如為了趕報表直接寫一段 SQL。那段 SQL 忘了加 tenant_id，誰來擋？

第三道：有人繞過 repository，交給 RLS 擋

PostgreSQL 課第 24 課的 RLS（Row Level Security，列層級安全）在資料庫裡過濾：表開啟 RLS 之後，資料庫依你寫的政策自動過濾每一列。程式裡就算有一個查詢忘了加 tenant_id，資料庫也只回目前租戶的列。政策要知道「目前的租戶」，做法是讓應用程式在連線上設一個自訂變數 app.tenant_id，政策再用 current_setting 讀它：

ALTER TABLE products ENABLE ROW LEVEL SECURITY;
ALTER TABLE products FORCE ROW LEVEL SECURITY;   -- 表的擁有者預設會繞過 RLS，FORCE 讓它也受限

CREATE POLICY tenant_isolation ON products
  USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint);

這幾行有三個地方要看懂：

  • FORCE：表的擁有者預設會繞過 RLS。很多團隊的應用程式就是用建表的那個帳號連線，不加 FORCE，政策對它等於不存在。
  • 只寫 USING 也擋寫入：只寫 USING 的政策，PostgreSQL 18 會把同一個條件也當成 WITH CHECK。所以不只看不到別人的列，也不能 INSERT、UPDATE 出別的租戶的列（會報 new row violates row-level security policy）。
  • NULLIF(…, '')：current_setting('app.tenant_id', true) 的第二個參數 true 表示「沒有這個設定時回 NULL，不要報錯」。但實測在同一條連線上設定過一次、交易結束之後，它回的是空字串而不是 NULL，空字串轉 bigint 會報錯。所以用 NULLIF 把空字串也變成 NULL。NULL 跟任何值比較都不成立，沒設定租戶 ＝ 一列都看不到，這是資料庫層的失敗關閉。

還有一個前提：應用程式連資料庫的帳號不能是超級使用者，也不能有 BYPASSRLS 屬性，這兩種永遠繞過 RLS（PostgreSQL 課第 24 課）。測試環境常用超級使用者連線，RLS 在那裡永遠不會生效，所以要用正式環境同樣的角色測。

政策寫好了，但它讀的 app.tenant_id 是設在連線上的值。後端的連線會被很多請求輪流使用，上一個請求設的值，會不會留給下一個請求？

RLS 的變數會不會留給下一個請求？SET 和 SET LOCAL

後端不會每個請求都開一條新的資料庫連線，那樣太慢。它維護一個連線池（connection pool）：請求來了借一條、用完還回去，下一個請求很可能借到同一條（PostgreSQL 課第 36 課）。設在連線上的變數會跟著連線一起被下一個人借走，所以「設在哪一層、什麼時候消失」決定了會不會漏。

PostgreSQL 有兩種設法。依 PostgreSQL 18 文件：SET 作用在整個 session（也就是這條連線）上，直到連線關閉或被改掉；SET LOCAL 只到目前交易結束（COMMIT 或 ROLLBACK）為止，在交易外執行只會警告、沒有效果。set_config(name, value, true) 等同 SET LOCAL。下面用一個模擬的連線池看差別，執行後對照每個請求查到的資料：

  • 用 SET：請求 A 設了租戶 1，連線還回去之後值還在。請求 B 是一個忘了設定租戶的背景工作，借到同一條連線，就用租戶 1 的身分查到了山丘咖啡的資料。RLS 的失敗關閉在這裡失效了，因為對資料庫來說租戶「有設定」。
  • 交易裡用 SET LOCAL：COMMIT 之後值就消失，請求 D 沒設定，一列都看不到，回到失敗關閉。
  • 忘了 BEGIN 就用 SET LOCAL：只有一個警告，設定沒有生效，請求 E 查不到任何資料。這不會洩漏，但功能會壞，要在測試裡抓出來。

所以每個請求的模式是：借連線 → BEGIN → SELECT set_config('app.tenant_id', $1, true) → 查詢 → COMMIT → 還連線。租戶值用參數（$1）傳，不要字串拼接，否則又多一個 SQL injection（PostgreSQL 課第 25 課）的入口。如果前面還有 PgBouncer 這類 transaction 模式的連線池（PostgreSQL 課第 36 課），更要這樣做：同一個 session 的連續兩個交易可能跑在不同的伺服器連線上，session 層的設定根本不可靠。

回頭看三道防線各管什麼錯：repository 擋「業務程式碼忘了加條件」，複合外鍵擋「參照到別的租戶的資料」，RLS 擋「有人繞過 repository 直接寫 SQL」。少了 repository，每個查詢都要自己記得；少了 RLS，一個手寫的報表查詢就能洩漏全部租戶。開場那個 storeRevenue，現在不管是走 repository 還是被人改成手寫 SQL，都查不到巷口咖啡的訂單了。

可是這三道都只守在資料庫的路上。資料一旦被讀出來，存進快取、放進佇列、寫成檔案，就離開了 repository 和 RLS 的範圍。那些地方誰還記得租戶？

資料離開資料庫之後，誰還記得租戶？

資料庫查詢通常會被 code review 看到，真正的事故常發生在資料庫以外的地方。拿開場的門市 1 來說：菜單查詢很慢，有人加了快取，key 寫成 menu:${storeId}（快取見 NestJS 課第 19 課）。山丘咖啡的店員先開門市 1 的菜單，結果被存進 menu:1；巷口咖啡的店員接著開自己的門市 1，從快取拿到的是山丘咖啡的菜單。資料庫的每一道防線都正常運作，漏洞出在一個字串上。

同樣的事會發生在每個「資料離開請求」的地方。下表檔案那一列會用到簽名網址（presigned URL）：後端用物件儲存（例如 S3）的存取金鑰簽出的下載連結，網址裡帶著有效期限和簽章，過期或被改動就失效，所以可以讓瀏覽器直接下載檔案，又不用把整個儲存空間公開。

地方出事的樣子做法
快取 keymenu:${storeId}：兩個租戶都有門市 1，先查的那個租戶的菜單被另一個租戶讀到key 一定包含租戶，每一段跳脫（練習 2）
背景工作（NestJS 課第 20 課）job 只帶 storeId，worker 不知道租戶，就用「預設租戶」或乾脆不加條件job 資料帶 tenantId，worker 用它重建上下文，並檢查 job 裡的每個 id 都屬於這個租戶（練習 3）
檔案、物件儲存（S3）receipts/${orderId}.pdf：改網址的數字就下載到別人的收據路徑前綴 tenants/${tenantId}/…，下載前仍要做第 19 課的物件層級檢查，再發短期的簽名網址
搜尋索引全文搜尋的索引沒有租戶欄位，搜「拿鐵」出現別的品牌的商品每份文件帶 tenantId，查詢一律加過濾；或每個租戶一個索引
匯出、報表「匯出 CSV」是另外寫的 SQL，沒經過 repository一樣走 repository 或有 RLS 的連線；匯出檔放在租戶的路徑下
log、錯誤訊息錯誤訊息印出「商品 20 屬於租戶 2」，等於告訴攻擊者那個 id 存在對外一律 404（第 19 課）；log 記 tenantId 方便排查，但不記別的租戶的資料內容
webhook、email寄信的範本、寄件名稱用錯租戶，或通知送到別的租戶設定的網址發送時用 job 裡的 tenantId 讀設定，不用全域預設

這張表的每一列都是同一個模式：只要資料離開了「有租戶上下文的請求」，就要把 tenantId 明確帶著走，到了另一邊再用它重建上下文。快取 key 是字串、job 是 JSON、檔案路徑是字串，這些地方都沒有 RLS 幫你擋，AsyncLocalStorage 的盒子也不會跟著 job 跑到另一台機器上的 worker。背景工作還要多做一步：job 是在請求當下建立的，到 worker 執行時，裡面的 storeId 仍要檢查確實屬於 job 的租戶，因為門市編號只在租戶裡唯一。

練習 2 要修的就是菜單快取的 key。把租戶放進 key 之前，還有一個小陷阱要先看：用 : 串接不同的段，如果某一段本身就含有 :，兩組不同的值會組出同一個 key。執行後看第三行：

💡 實務上：用「兩個租戶」的測試資料抓漏洞
只有一個租戶的測試資料永遠抓不到跨租戶漏洞，因為根本沒有別人的資料可以漏，開場的 storeRevenue 在單一品牌的測試裡永遠是對的。常見做法是測試資料固定建兩個租戶，而且故意讓它們有相同的門市編號、相同的商品名稱，再用租戶 B 的帳號去打每個 API、拿租戶 A 的 id，預期一律 404。code review 時看到新的快取 key、job 資料、檔案路徑、匯出功能，資深的人會直接問一句「這裡的 tenantId 從哪來？」。上線前也可以請 QA（測試人員）開兩個測試租戶，交叉操作一輪。

到這裡防的都是「不小心」跨租戶。可是有一種跨租戶存取是公司自己需要的：山丘咖啡打電話來報案之後，你的客服得進去看山丘咖啡的資料，才查得出問題。

客服要查山丘咖啡的問題：怎麼跨租戶又不開後門？

你的公司經營這個平台，自己也需要跨租戶存取：客服要幫山丘咖啡查「為什麼這張訂單出現在我們的報表上」，工程師要排查只在某個租戶發生的錯誤。前面所有的防線都會擋住他們，因為客服帳號不屬於山丘咖啡。

最省事的做法是給客服一個「超級使用者」帳號，所有租戶條件都跳過。這等於在隔離牆上開了一扇沒人看管的門：那個帳號被盜、客服出於好奇亂看、離職員工的帳號沒停用，任何一種都會洩漏所有租戶的資料，而且事後查不出誰看了什麼。

比較好的做法是把跨租戶存取當成一個明確的、留下紀錄的動作。這裡的「紀錄」指稽核紀錄（audit log）：專門記錄「誰在什麼時候對什麼資料做了什麼」的紀錄，用來在事後回答責任問題，跟除錯用的一般 log 分開保存。整個設計包含這幾件事，每一件都對應一個超級帳號的風險：

  • 明確切換：客服帳號平常不屬於任何租戶，要看某個租戶時發起「進入租戶 1」，系統發一個只對租戶 1 有效的 session。它仍然經過同一套 repository 和 RLS，只是租戶上下文是切換來的，前面的三道防線一道都沒拆。
  • 填理由、關聯工單：例如「工單 #4821：報表多一筆別家的訂單」。沒有理由就不能進，事後也知道每一次存取是為了什麼。
  • 有時效：例如 1 小時後自動失效，不能永久掛著。忘了登出的 session 不會變成長期的後門。
  • 預設唯讀：查問題通常只需要看。要修改資料需要更高的權限，最好要第二個人核准。
  • 寫稽核紀錄：誰、什麼時候、進入哪個租戶、理由、看了哪些資料。稽核紀錄要跟一般 log 分開、不能被客服自己刪改（第 25 課會再談）。
  • 讓租戶知道：在租戶的管理頁面列出「平台人員的存取紀錄」，有些合約會要求事前同意。
💡 實務上：「以客戶身分登入」常是客服最想要的功能
很多 SaaS 後台都有「以這位使用者身分檢視」之類的按鈕，客服用它重現客戶看到的畫面，比叫客戶截圖快得多。PM 提這個需求時，要把它做成上面那種明確切換、會過期的租戶 session，而不是一個跳過所有檢查的後門。資安和法務通常會關心兩件事：客戶合約有沒有允許平台人員看資料、出事時能不能查出是誰看的。早期團隊可以先做最小版本（明確切換、唯讀、稽核紀錄），但稽核紀錄一定要從第一版就有，事後補不回已經發生的存取。

資料的隔離到這裡完整了：誰都看不到別人的資料，自家客服要看也有範圍和紀錄。但租戶共用的不只是資料，還有同一台資料庫的 CPU、同一個 API 的處理能力。

巷口咖啡跑大報表，山丘咖啡結帳卡住：怎麼分資源？

巷口咖啡的店長在月底按下「匯出三年訂單」，這個查詢讓資料庫 CPU 滿載；同一時間，山丘咖啡的店員在櫃台結帳，畫面一直轉圈。巷口咖啡沒有看到山丘咖啡的任何資料，但山丘咖啡一樣受害了。一個租戶用太多共用資源、拖慢其他租戶，叫雜訊鄰居（noisy neighbor），就像住公寓時樓上整晚施工。

它的成因跟資料隔離一樣：系統把所有租戶當成同一群使用者。解法也一樣，把「租戶」加進每個分配資源的地方：

  • 每個租戶各自的限流與配額：限流（rate limit）是規定一段時間內最多接受幾個請求，第 16 課用 IP 當 key 做過。這裡限流的 key 包含 tenantId（例如每租戶每分鐘 600 個請求），而不只是每 IP、每使用者：一個租戶有很多店員、很多 IP，只限每 IP 擋不住整個租戶的量。這是第 24 課 OWASP API4（Unrestricted Resource Consumption）的一部分。
  • 重的工作進佇列，按租戶公平排程：匯出三年訂單這種工作不在請求裡直接跑，而是放進佇列。排程時不要讓一個租戶塞進去的一萬個 job 排在所有人前面。
  • 大租戶搬出去：回到第二節的三種隔離方式，用量大的租戶換成獨立的資料庫，這也是一個常見的付費方案。
  • 監控也要分租戶：延遲、錯誤率、資料量都依 tenantId 分組。否則幾百個租戶的平均值看起來很正常，某個租戶其實一直出錯，就像開場的事故，要等客戶打電話來才知道。

回到這課的任務。開場那筆跑錯報表的訂單，現在要經過層層關卡才可能漏出去：租戶只從登入的主體來；repository 自動加條件，找不到租戶就失敗關閉；複合外鍵擋住跨租戶參照；RLS 擋住繞過程式的 SQL，變數用 SET LOCAL 不留給下一個請求；快取、背景工作、檔案都明確帶著租戶；客服跨租戶有範圍、有紀錄；資源也依租戶分配。接下來的練習 1–3 分別實作 repository、快取 key 和背景工作這三個最常出事的地方，練習 4–6 回頭檢查租戶來源、RLS 的必要性和客服存取的設計。

補充與查表

主線用不到、但實作上下文或設定子網域 cookie 時會查的細節。

AsyncLocalStorage 的 defaultValue

Node 24 的 AsyncLocalStorage 建構子有一個 defaultValue 選項，設了之後 run() 之外呼叫 getStore() 會回這個值，而不是 undefined。所以不要用它設「預設租戶」：它會讓主線裡 currentTenantId() 的失敗關閉永遠不會觸發，沒有上下文的程式會靜靜地查預設租戶的資料。

子網域與 session cookie

所有租戶共用 coffeepos.example 底下的子網域時，session cookie 不要設 Domain=coffeepos.example，否則它會被送到每個租戶的子網域。用第 4 課的 __Host- 前綴：它保證 cookie 是 host-only（只送回發出它的那個主機），別的子網域也沒辦法寫一個同名 cookie 蓋掉它；某個子網域有 XSS（第 7 課）時，影響才不會擴散到其他租戶。

練習

練習 1：實作會自動加上租戶條件的 TenantRepository<T>（泛型見 TypeScript 課第 19 課）。建構子收到 getTenantId（回傳目前請求的租戶，正式環境裡它會讀 AsyncLocalStorage）和所有租戶共用的 rows 陣列（模擬共用的資料表）。

  • findById(id)：只找得到目前租戶的資料，別的租戶的回 undefined。
  • list()：只回目前租戶的資料。
  • create(data)：tenantId 一律用 getTenantId() 的值，就算 data 在執行時多帶了 tenantId 也一樣；id 是 rows 裡最大的 id 加 1；放進 rows 並回傳。
  • update(id, patch)：別的租戶的資料找不到（回 undefined、不能改到）；patch 就算在執行時帶了 id 或 tenantId 也不能改掉它們。回傳更新後的資料。
  • delete(id)：只能刪目前租戶的資料，有刪到回 true。
  • 每次操作都重新呼叫 getTenantId()：同一個 repository 會被不同租戶的請求共用。

提示：組出新物件時 TypeScript 無法證明它是 T，可以寫 { … } as T；重點是 tenantId 放在哪裡。

練習 2：修好菜單快取。原本的 key 是 menu:${storeId}，兩個租戶都有門市 1，先查的那個租戶的菜單會被另一個租戶讀到。

  • 寫 cacheKey(ctx, ...parts)：回傳的 key 一定包含 ctx.tenantId，而且每一段（包括租戶）都先用 encodeURIComponent 跳脫再用 : 串起來，讓不同的組合不會組出同一個 key。
  • 把 getMenu 改用 cacheKey：快取有就直接回傳，沒有才呼叫 db.loadMenu 並存進快取。

練習 3：月報表是背景工作。店長按下「產生報表」時，API 呼叫 enqueueReport 把 job 放進佇列；之後 worker 從佇列拿出 job 呼叫 runReportJob。佇列存的是 JSON（像 Redis 裡的 BullMQ job），worker 那邊沒有請求的租戶上下文。

  • enqueueReport(ctx, params, queue)：job 一定帶 tenantId，而且取自 ctx；params 在執行時就算多帶了 tenantId 也不能用它。
  • runReportJob(job, deps)：
    • job.tenantId 不是正整數（沒有、字串、0）→ { ok: false, error: 'missing_tenant' }，不能用任何預設租戶。
    • 這個租戶沒有 job.storeId 這間門市 → { ok: false, error: 'store_not_in_tenant' }。注意門市編號只在租戶裡唯一：兩個租戶都可能有門市 1。
    • 否則回 { ok: true, report }：只算這個租戶、這間門市、orderedAt 以 job.month（例如 '2026-10'）開頭的訂單，orderCount 是筆數、revenue 是 total 的總和。

練習 4：前端工程師說：「Vue 前台本來就知道自己是哪個品牌，每個請求帶 X-Tenant-Id 標頭給 API，後端就用它查資料。登入也檢查過了，應該沒問題。」怎麼回應？

✓ 登入只證明「你是山丘咖啡的店員」，不證明「你可以看你送來的那個租戶」。用 DevTools 或 curl 改一個標頭不需要任何技術。a 誤以為使用者只會用你的前台，而且「登入了」不等於「能看每個租戶」，山丘咖啡的店員把標頭改成 2 就查到巷口咖啡；b 換了一個一樣能被改的來源：DNS 和憑證只保證你連到的是真的伺服器，不保證你是那個租戶的人，任何人都能打 alley.coffeepos.example。子網域可以用來決定要顯示哪個品牌的登入頁，但 API 要比對主體的租戶。

練習 5：團隊已經寫好 TenantRepository，每個查詢都自動加 tenant_id，有人說「再加 RLS 只是重複，還要處理 SET LOCAL 很麻煩」。資深工程師最好的理由是？

✓ 縱深防禦：兩層各自擋不同的錯。跨租戶洩漏的代價極高，多一層的成本（每個交易一次 set_config）很小。a 錯：repository 的 WHERE tenant_id = … 本來就在資料庫裡過濾，RLS 只是再加一個條件，不會讓查詢變快，條件寫不好反而會變慢；c 錯：拿掉應用層的條件後，RLS 的設定一出錯（例如用了有 BYPASSRLS 的帳號、表的擁有者沒加 FORCE）就沒有任何保護，而且程式在測試環境用超級使用者連線時根本看不出問題。

練習 6：平台客服常常要幫各品牌查問題，產品經理提議「給客服一個能看所有租戶的帳號，最方便」。比較好的設計是？

✓ 跨租戶存取是合理的需求，重點是讓它變成「明確、有範圍、有紀錄」的動作，而不是隱形的後門。b 減少了帳號被盜的機會，但仍然是永久、無範圍、沒紀錄的全部存取，事後查不出誰看了什麼；c 最糟：超級使用者繞過 RLS，也繞過應用程式所有的檢查與稽核。

常見錯誤

  • 從請求參數、標頭、子網域取得租戶：客戶端改一個值就換租戶。租戶從登入的主體來，其他來源只當提示，不一致就拒絕。
  • 每個查詢自己記得加 tenant_id：總有一次會忘。集中在 repository，從上下文自動加。
  • 找不到租戶上下文時退回預設租戶：平常看不出來，出事時資料全部混在一起。失敗關閉：丟錯，或一列都不回。
  • 寫入時用 body 裡的 tenantId，或展開 body 時順序錯了讓它蓋掉上下文的值：tenantId 一律最後由上下文填。
  • 快取 key、檔案路徑、搜尋索引、背景工作沒帶租戶：資料離開請求時，tenantId 要明確帶著走，另一邊再重建上下文並檢查每個 id 屬於這個租戶。
  • 連線池上用 SET 設定 RLS 變數：下一個借到這條連線的請求沿用上一個租戶。在交易裡用 SET LOCAL 或 set_config(…, true)。
  • RLS 用 current_setting('app.tenant_id')::bigint 而沒處理空值：沒設定時會報錯或變成空字串。用 NULLIF(current_setting('app.tenant_id', true), '')::bigint。
  • 應用程式用超級使用者或表的擁有者連資料庫：RLS 被繞過。用一般角色，表加 FORCE ROW LEVEL SECURITY。
  • 單欄外鍵：訂單可以參照到別的租戶的商品。用 (tenant_id, id) 複合外鍵。
  • 平台管理員帳號沒有範圍、沒有稽核紀錄：改成明確切換、限時、唯讀、寫稽核紀錄、讓租戶看得到。
  • 限流只看 IP 或使用者：一個租戶的大量請求拖垮其他租戶。限流與配額的 key 加上 tenantId。

小結

  • 多租戶系統最重要的保證是租戶隔離；漏掉時通常沒有錯誤訊息，只是「多看到一點別人的資料」，像開場報表多出的那 120 元。門市編號這類 id 只在租戶裡唯一。
  • 三種隔離方式：共用表＋tenant_id（便宜、靠程式與 RLS）、每租戶一個 schema、每租戶一個資料庫（隔離最強、維運最重）；多數從共用表開始，大客戶再搬出去。
  • 租戶上下文來自登入的主體；標頭、body、子網域都只是提示，不一致就回 404。
  • 三道防線各擋一種錯：repository 從上下文（AsyncLocalStorage）自動加條件、寫入時由上下文填 tenantId；複合外鍵擋跨租戶參照；RLS 擋繞過 repository 的查詢，變數在交易裡用 SET LOCAL，不留給借到同一條連線的下一個請求。找不到租戶一律失敗關閉。
  • 資料離開請求的地方（快取 key、背景工作、檔案路徑、搜尋、匯出、log）都要明確帶租戶，到另一邊再重建上下文。
  • 平台人員跨租戶存取要明確切換、填理由、限時、唯讀、寫稽核紀錄；資源也要依租戶限流與配額，避免雜訊鄰居。
