階段 2：瀏覽器裡的登入狀態：Cookie、Session 與跨站攻擊 · 第 4 課

Cookie 與 Session：伺服器怎麼記住你

王小明在咖啡店會員網站輸入帳密，按下登入，伺服器用第 3 課的方法驗證密碼通過。接著他點「我的訂單」，這是一個全新的 HTTP 請求。伺服器怎麼知道這個請求也是王小明？

這一課要替咖啡店會員網站做出完整的登入狀態：小明按下登入、之後每個請求都被認出來、一段時間沒用就過期、按下登出，或帳號被盜時由客服把他所有裝置登出。每走一步都問同一個問題：攻擊者能不能在這一步冒充小明？做完之後，你會知道 cookie 和 session 每個設定為什麼存在，看到「登入後一直被登出」這類回報時也知道從哪裡查。

這課的路線：
  1. 伺服器怎麼認出下一個請求也是小明：登入後發一個猜不到的 session ID，用 cookie 讓瀏覽器每次自動帶回來，伺服器查表就知道是誰（開場問題的最小答案）。
  2. 誰能拿走小明的號碼牌、cookie 會送到哪些網址：HttpOnly、Secure、SameSite 擋住三條偷取或借用的路，Path、Domain、__Host- 決定 cookie 送到哪裡，以及瀏覽器為什麼會默默拒收。
  3. 伺服器的名冊怎麼存、要有效多久：store 外洩了也不能拿來登入，開兩台伺服器也不會掉登入；閒置逾時和絕對逾時各擋什麼。
  4. 登入那一刻與登出那一刻：登入時為什麼一定要換新 ID，登出為什麼一定要刪伺服器端的 session，帳號被盜時怎麼登出所有裝置。
這課會用到：
  • Node 課第 12 課的標頭：請求和回應都帶一組「名稱: 值」的標頭；伺服器用 第 13 課的 res.setHeader 設定回應標頭。Node 課沒有教 cookie，這課從頭講。
  • 第 2 課的安全亂數與雜湊：crypto.getRandomValues 產生 32 bytes（256 bits）猜不到的 token；SHA-256 把它變成不能還原的指紋。

伺服器怎麼知道下一個請求也是王小明？

先看問題出在哪。HTTP 的每個請求都是獨立的：瀏覽器送出方法、網址、標頭和內容，伺服器回完就結束，不會留下「剛才是誰來過」的紀錄。這個性質叫無狀態（stateless）。對伺服器來說，小明登入用的 POST /auth/login 和下一秒的 GET /orders 是兩個互不相干的請求，第二個請求上沒有任何東西說「我就是剛剛登入的那個人」。所以「已登入」在 HTTP 裡不會自動延續，要我們自己把兩個請求連起來。

最直覺的兩個辦法都不行。看它們錯在哪，正好能看出正確做法要滿足什麼條件：

  • 每個請求都帶帳密：伺服器每次重新驗證，確實認得出人。但密碼會在每個請求裡跑來跑去，前端得一直保存明文密碼，任何一個環節外洩就是密碼外洩；而且每個請求都要跑一次第 3 課的慢雜湊（每次幾十到幾百毫秒），每支 API 都被拖慢。
  • 帶 userId=7：快，也不用碰密碼。但這個值是瀏覽器自己送的，任何人改成 8 就變成別人，伺服器分辨不出這個數字有沒有被改過。

所以要帶在請求上的東西必須同時滿足兩件事：不是密碼本身，外洩了可以單獨作廢；而且猜不到、改不了，不能像 userId 一樣改一個數字就變成別人。

實際的做法像咖啡店櫃台的取餐號碼牌。登入成功時，伺服器產生一個很長的隨機字串當號碼，在自己的名冊上記下「這個號碼是王小明、幾點登入」，再把號碼交給瀏覽器。之後瀏覽器每個請求都出示號碼，伺服器查名冊就知道是誰。號碼本身不含任何資訊，只有伺服器的名冊知道它代表誰；號碼又長又隨機，攻擊者猜不到別人的號碼。這套做法裡的三個角色，整課都用這三個名字：

  • 號碼叫 session ID（也叫 session token）。
  • 名冊上的那一筆資料（是誰、何時登入、最後一次活動時間）叫 session。
  • 存放所有 session 的地方叫 session store，可以是記憶體、Redis 或資料庫，後面「名冊怎麼存」那一節會比較。

還差一塊：號碼要放在瀏覽器裡，而且每次請求都要自動帶上，不能靠前端在每個 fetch 手動加。這是 cookie 的工作。cookie 是瀏覽器替某個網站保存的一小段「名稱=值」：伺服器在回應裡要求瀏覽器存下，之後瀏覽器對這個網站發請求時，自動把符合條件的 cookie 附上。對寫 Vue 的你來說，這代表 fetch('/orders') 什麼都不用加，號碼牌就跟著送出去了。

這張圖就是開場問題的最小答案：登入時伺服器發一個猜不到的 session ID，用 cookie 存在瀏覽器，之後每個請求自動帶回，伺服器查 session store 認人。②和⑤存、查的是 hash(sid) 而不是號碼本身，原因留到「名冊怎麼存」那一節。先看③和④這兩個標頭實際長什麼樣子。

兩個方向用不同的標頭，格式也不一樣：

  • Set-Cookie（回應）：伺服器要求瀏覽器存一個 cookie。一個 cookie 一行，後面用分號接屬性：Set-Cookie: sid=Zx9…; Path=/; HttpOnly。屬性是給瀏覽器的指示：什麼時候送、送到哪、誰能讀，下兩節逐一講。要設兩個 cookie 就送兩行 Set-Cookie，不能用逗號合併成一行（Expires 的日期裡本來就有逗號）。Node 裡寫成 res.setHeader('Set-Cookie', [a, b])。
  • Cookie（請求）：瀏覽器帶回符合條件的 cookie，只有名稱和值：Cookie: sid=Zx9…; theme=dark。屬性不會送回來，所以伺服器看不出某個 cookie 當初有沒有 Secure、何時到期、是哪個網域設的。

伺服器收到的 Cookie 標頭只是一串文字，要自己拆。下面的範例拆出所有 cookie，執行後看結果裡有兩個 sid：瀏覽器用（名稱、網域、路徑）三個一起分辨 cookie，不同 Path 的同名 cookie 會被當成兩個，一起送來，伺服器分不出哪個是哪個。後面「登出」那一節會看到這種情況怎麼發生。

寫伺服器時，這兩個標頭要能親眼看到。開 DevTools：Application → Cookies 列出這個網站存了哪些 cookie 和屬性；Network 點一個請求，看 Response Headers 的 Set-Cookie，被瀏覽器拒收的那一行旁邊會有警告圖示，滑鼠移上去會說原因。前端的 document.cookie 只看得到沒有 HttpOnly 的 cookie，下一節會說明這個差別。

到這裡，小明已經能被認出來，新的風險也跟著出現：session ID 就是小明的登入憑證。誰拿到這串字，誰就是王小明，不需要密碼。下一節看它會從哪些地方被拿走。

誰能拿走王小明的號碼牌？HttpOnly、Secure、SameSite

session ID 一路上會經過三個地方：它存在瀏覽器裡，頁面上的 JavaScript 可能讀得到；它跟著每個請求在網路上傳，路上的人可能看得到；而且瀏覽器會自動附上它，連別的網站發起的請求也可能帶著。Set-Cookie 的三個屬性正好各堵一條路。

頁面上的腳本：HttpOnly

前端的 document.cookie 可以讀寫這個網站的 cookie。如果網站有漏洞，讓攻擊者把自己的 JavaScript 塞進咖啡店的頁面執行，這種攻擊叫 XSS（跨站腳本，第 7 課詳講）。這段腳本跟你寫的 Vue 程式碼跑在同一個頁面，權限一樣，一行程式就能把 document.cookie 送到攻擊者的伺服器，攻擊者在自己的瀏覽器設好這個 cookie，就以小明的身分登入了。

HttpOnly 讓 JavaScript 讀不到這個 cookie：document.cookie 裡看不到它，但瀏覽器發請求時照樣附上。session cookie 本來就只給伺服器看，前端沒有理由讀它，所以一定要設。

要分清楚它擋住的範圍：HttpOnly 只擋「讀」。腳本還是能在你的頁面上用 fetch 發請求，瀏覽器照樣帶 cookie，攻擊者不用偷號碼也能以小明的身分操作。它把損害從「號碼被帶走、隨時隨地冒用」縮小到「只能趁受害者開著頁面時操作」，真正的修法是不讓 XSS 發生。練習 4 會考這個區別。

網路上的人：Secure

HTTP 本身是明文。HTTPS 在 HTTP 外面加一層 TLS 加密，路上的人看不到也改不了內容（部署課第 5 課）。在公共 Wi-Fi 上，攻擊者可以夾在你和伺服器之間，看所有沒加密的流量，這種位置的攻擊者叫中間人（man-in-the-middle）。

咖啡店全站都用 HTTPS 還不夠。沒有 Secure 的 cookie，在 http 請求上也會送出；中間人只要誘使瀏覽器對咖啡店發一個 http 請求，cookie 就跟著明文請求被看見，拿去冒用。這叫 session 劫持（session hijacking）。Secure 讓 cookie 只在 HTTPS 連線送出，這條路就斷了。

本機正常，部署到測試機就一直被登出。瀏覽器把 http://localhost 當成安全的來源，所以本機開發時 Secure cookie 也收得下來。換成 http://192.168.1.20 這種一般主機，帶 Secure 的 cookie 會被直接拒收。瀏覽器拒收時不會通知伺服器，伺服器以為設好了，只有 DevTools 的 Network 面板會標出原因。測試機也要上 HTTPS。

別的網站：SameSite

第三條路不是偷，而是借。沒有額外限制時，瀏覽器帶不帶 cookie 只看請求要送到哪個網站，不管是哪個網站的頁面發起的。小明開著咖啡店的分頁，又在另一個分頁打開惡意網站，那個網站的頁面對咖啡店送出一個請求，瀏覽器照樣附上小明的 cookie，伺服器看到的就是「已登入的小明」在操作。這種攻擊叫 CSRF（跨站請求偽造），第 6 課詳講。

從別的網站發出、目標是咖啡店的請求，叫跨站請求。SameSite 控制跨站請求帶不帶這個 cookie，值有三種：Strict、Lax、None，嚴格程度由高到低，差別第 6 課講，咖啡店的 session cookie 先用 Lax。SameSite=None 表示跨站也帶，這時必須同時有 Secure，否則整個 cookie 被拒收。

這個屬性一定要明寫。各瀏覽器沒寫時的行為不一樣：只有 Chromium 系列（Chrome、Edge）把沒寫當成 Lax，Firefox、Safari 沒有這個預設，靠預設就等於有些使用者沒受保護。各瀏覽器的版本見課末「補充與查表」。

這三個屬性處理了「誰拿得到、誰能借用」。另一類問題不是攻擊，而是 cookie 沒送到該送的地方，或送到了不該送的地方。這由 Path 和 Domain 決定。

cookie 會送到哪些網址？Path、Domain 與 __Host- 前綴

先看 Path。瀏覽器只在請求路徑落在這個路徑底下時才送：Path=/docs 會送到 /docs/a，不會送到 /docsets。沒寫時，預設是設定它的那個請求路徑的目錄。咖啡店的登入 API 是 /auth/login，它回的 cookie 沒寫 Path，就只會送到 /auth 底下；小明接著打開 /orders，請求沒帶 cookie，看起來就像「登入後馬上被登出」。所以 session cookie 要明寫 Path=/。另外，Path 只管送不送，不是安全邊界，同一個網站其他路徑上的程式一樣讀得到。

再看 Domain。不寫時是 host-only cookie：只送回設定它的那台主機，www.coffee.example 設的就只回 www.coffee.example。寫了 Domain=coffee.example，就會送到所有子網域，包括外包做的活動頁 promo.coffee.example。那個活動頁只要有一個漏洞，小明的 session ID 就會出現在它的伺服器上。Domain 只能設成自己或上層網域。有些網域字尾是任何人都能在底下註冊網域的，例如 com.tw，這種字尾叫公共字尾（public suffix，第 5 課），Domain 不能設成它，否則一個網站就能把 cookie 送給所有 .com.tw 網站。

結論是 session cookie 不寫 Domain。但光是咖啡店自己不寫還不夠：子網域也能寫 cookie。被攻破的 promo.coffee.example 可以設一個 Domain=coffee.example、名稱也叫 sid 的 cookie，瀏覽器會把它送到 www。第一節看過，Cookie 標頭只有名稱和值，伺服器分不出哪個 sid 是自己設的。後面的 session fixation 就會利用這一點。

要堵住它，靠 cookie 名稱的前綴：名稱以特定字串開頭時，瀏覽器會檢查屬性，不符合就拒收。

  • __Host-：必須 Secure、從 HTTPS 設定、Path=/、不能有 Domain。這保證它是 host-only，子網域沒辦法寫一個同名 cookie 蓋掉它：子網域要讓 cookie 送到 www，就一定得寫 Domain，而帶 Domain 的 __Host- cookie 會被瀏覽器直接拒收。session cookie 首選這個。
  • __Secure-：只要求 Secure、從 HTTPS 設定，不限 Path 和 Domain。Path 不是 / 的 cookie 只能用這個，例如第 10 課只送到 /auth/refresh 的 refresh cookie。

前綴比對不分大小寫，__host-sid 一樣要符合規則。還有要求 HttpOnly 的較新前綴，瀏覽器支援還不齊，本課用 __Host-，細節見課末。

兩節的屬性合起來，咖啡店會員網站的 session cookie 長這樣：

Set-Cookie: __Host-sid=Zx9…; Path=/; Secure; HttpOnly; SameSite=Lax

HttpOnly 擋腳本讀取，Secure 擋中間人，SameSite 擋跨站借用，Path=/ 讓所有 API 都收得到，不寫 Domain 加上 __Host- 擋子網域。每個屬性的「沒設或設錯會怎樣」整理在課末的屬性速查表。

這些規則有一個共同的麻煩：瀏覽器拒收 cookie 時不會告訴伺服器。伺服器回了 Set-Cookie，以為設好了，下一個請求卻沒帶 cookie，使用者看到的就是「登入後一直被登出」。能看到原因的只有 DevTools 的 Network 面板。練習 1 會把這節和上一節的規則寫成一個模擬瀏覽器的函式，同事回報這類問題時就能拿來對照。

💡 實務上：上線前打開 DevTools 看真正送出的 Set-Cookie
實際專案很少手寫 Set-Cookie，多半是在框架或 session 套件的設定裡填 httpOnly、secure、sameSite，而每個套件的預設值不一樣。所以 code review 時不要只看設定檔，要在測試機用 DevTools 的 Network 看回應裡實際送出的那一行，再到 Application → Cookies 確認瀏覽器真的收下了。前端和 API 放在不同網域（例如 www. 和 api.）時，還會牽涉到 SameSite 和 CORS，第 5、6 課會處理。資深工程師會把「session cookie 的屬性」寫進上線檢查清單，而不是靠每個人記得。

cookie 這一側設好了，號碼牌只會在對的時候送到對的地方。另一半在伺服器：名冊本身也會外洩，備份、log、被入侵的 Redis 都可能，那時候名冊上的東西能不能直接拿來登入？

伺服器的名冊怎麼存，外洩了也不能拿來登入？

名冊要安全，先要號碼本身猜不到，再要名冊上存的東西不能直接當號碼用。先看號碼。session ID 就是登入憑證，所以要符合第 2 課對 token 的要求：用 crypto.getRandomValues 產生 32 bytes（256 bits）。遞增數字不行，看到自己是 1007 就會去試 1006；用 userId 組出來不行，知道規則就能組出別人的；Math.random 不行，它不是為安全設計的亂數，輸出可能被推算出來。OWASP 要求至少 64 bits 熵，自己產生時建議 128 bits 以上。

號碼猜不到之後，再看名冊。最直接的存法是把 token 原樣當 key：sessions['Zx9…'] = { userId: 7 }。問題是名冊會外洩：資料庫或 Redis 的備份放錯地方、log 把整筆資料印出來、store 被入侵。原樣存的話，攻擊者拿到的就是一整疊有效的號碼牌，挑一個設進自己的 cookie 就登入了。

所以存的時候，key 用 token 的 SHA-256，不存原始 token。瀏覽器拿著原始 token；伺服器收到請求時，把 token 再算一次 SHA-256 去查。外洩的名冊裡只有雜湊，攻擊者要從雜湊反推出原始 token 才能放進 cookie，而 SHA-256 不能還原。

你可能會想到第 3 課：密碼要用慢雜湊，這裡為什麼 SHA-256 就夠？慢雜湊保護的是熵很低、猜得到的密碼，攻擊者可以拿常見密碼一個個算雜湊比對，慢雜湊讓每次猜測都變貴。256 bits 的隨機 token 根本猜不完，再快的雜湊也沒用；反過來，每個請求都要查一次 session，用慢雜湊會讓每支 API 多等幾十到幾百毫秒。

名冊的每一筆裡放什麼？放會用來判斷的最少資訊：userId、建立時間、最後活動時間、未登入時的購物車。如果網站有多因素認證，也就是除了密碼還要輸入手機上的驗證碼（第 14 課），session 要記下這次登入通過了沒有。不要把整份使用者資料或角色放進去：店長把小明的權限拿掉之後，session 裡的舊角色還在，要等他重新登入才會更新。權限每次從資料庫查（可以短暫快取），第 11 課會再談。

名冊存什麼決定了。還有一個問題要等網站變大才會出現：名冊放在哪一台機器上？

開了第二台伺服器之後，小明為什麼一直被登出？

名冊放在哪台機器上，也會影響登入狀態。如果 session 存在 Node 程序記憶體裡的一個 Map，一台伺服器時沒問題。流量變大、開了兩台之後，前面會放一個負載平衡器（load balancer）：它站在多台伺服器前面，把每個請求分給其中一台。小明在 A 台登入，session 記在 A 台的記憶體；下一個請求被分到 B 台，B 台的 Map 裡沒有這個號碼，小明就被登出了。兩種解法：

  • 黏性 session（sticky session）：讓負載平衡器把同一個使用者固定送到同一台。簡單，但那台重啟或縮減時，上面的人全部被登出，流量也分不平均。
  • 共用 store：所有伺服器都查同一個 Redis（或資料庫）。這是常見做法。Redis 可以替每個 key 設存活時間（TTL），時間到自動刪除（NestJS 課第 19 課），剛好對應下一節的閒置逾時。伺服器本身不存狀態，才能隨意增減，部署課第 13 課會完整講。
💡 實務上：session 交給成熟套件，store 用 Redis
Node 專案通常用 express-session 這類套件搭配 Redis store，不會從零寫；這課自己實作，是為了讓你看得懂它的設定、知道該檢查哪些項目。導入時先讀文件確認：cookie 的預設屬性、session ID 怎麼產生、過期資料怎麼清。Redis 放 session 之後就變成登入的關鍵依賴：它掛掉時所有需要登入的 API 都會失敗，被清空時所有人同時被登出，維運要把它納入監控和備援。只有一台伺服器的小型內部工具，先用資料庫存 session 也完全可以，不必為了「以後可能擴充」多架一套 Redis。

名冊存得安全、每台伺服器都查得到了。但名冊上的每一筆要有效多久？如果小明登入之後永遠有效，號碼牌一旦外洩，就永遠能用。

號碼牌要有效多久？閒置逾時與絕對逾時

session 永遠有效會出兩種事，對應兩種不同的期限。第一種：小明在網咖登入看訂單，走的時候忘了登出，下一個坐上那台電腦的人直接就是小明。第二種：小明的號碼牌被偷了，攻擊者拿著它想用多久就用多久。

對付第一種用閒置逾時（idle timeout）：一段時間沒有任何請求就失效。實作方式是滑動到期（sliding expiration）：每次使用就把期限往後延。小明一直在用，就一直有效；他離開網咖 30 分鐘沒動作，session 就失效，下一個人拿不到。

但滑動到期擋不住第二種。攻擊者拿到號碼後，只要每隔 20 分鐘用一次，期限就一直往後延，永遠不會過期。所以還要絕對逾時（absolute timeout）：從登入起算，不管多常使用，時間到就失效。號碼被偷了，最多也只能用到絕對逾時為止，之後小明重新登入拿到新號碼，偷來的那張就作廢了。

要多長？OWASP 給的例子：閒置逾時，高價值的應用（網路銀行）2～5 分鐘、一般應用 15～30 分鐘；絕對逾時 4～8 小時。咖啡店會員網站能看訂單、改地址，選閒置 30 分鐘、絕對 8 小時：一個工作天內不用重新登入。「記住我」是另一種設計：長效 session，但改密碼、退款這類敏感操作要重新驗證（第 14 課）。

實作時判斷順序很重要：先檢查，再更新最後活動時間。反過來的話，閒置了一整天的 session 會先被延期、再檢查，檢查時看到的是「剛剛才用過」，永遠不會過期。時間一律用注入的 now() 取得，不直接呼叫 Date.now()，測試才能直接把假時鐘推進 8 小時，不用真的等。下面的範例執行後看三行：29 分鐘還有效、31 分鐘因為閒置過期、一直在用的 session 在第 480 分鐘因為絕對逾時過期。

瀏覽器那一側也有期限，由 Max-Age（存活秒數）或 Expires（到期日期）決定，兩個都有時 Max-Age 優先，Max-Age=0 代表立刻刪除，登出時會用到。兩個都不寫，就是「瀏覽器關閉就消失」的 cookie（但「還原上次分頁」功能可能讓它留下來）。session cookie 通常不寫 Max-Age，真正的期限由伺服器判斷，因為 cookie 的期限存在使用者的瀏覽器裡，使用者可以自己改；伺服器的名冊說過期了，帶什麼 cookie 來都沒用。

💡 實務上：逾時長度是產品決定，前端要接住「被登出」
逾時太短，PM 和客服會收到「一直要重新登入」的抱怨；太長，資安會擔心。常見做法是分開設定：咖啡店會員網站寬鬆一點，能退款、改價格的店長後台嚴格一點。前端要處理 session 過期：API 回 401 時導到登入頁、記住原本的網址，登入後再導回去，必要時先把使用者填到一半的表單暫存起來。討論時資深工程師會先問「這個系統被冒用的後果多嚴重」，再決定數字，而不是直接套範例。

到這裡，一個 session 從發出到過期的規則都有了。還漏了一個時間點：號碼牌是什麼時候發的？很多網站在小明登入之前就已經發給他一張了。

登入那一刻為什麼一定要換新號碼？Session fixation

咖啡店允許沒登入的人先把拿鐵放進購物車，購物車存在 session 裡，所以小明一打開網站就拿到一張匿名的號碼牌。登入成功時，最順手的寫法是沿用這張號碼牌，只把 userId 填進名冊。問題是：登入之前就知道這個號碼的人，現在手上拿的是一張已登入的號碼牌。如果那個人是攻擊者，他根本不用偷，號碼是他事先塞給小明的。這種攻擊叫 session fixation（固定 session 攻擊）：攻擊者先讓受害者用一個攻擊者知道的 session ID，等受害者登入。按「下一步」看過程：

步驟攻擊者王小明的瀏覽器伺服器的 session
1打開網站，拿到 sid=TT：未登入
2從子網域寫入 sid=T存了 sid=TT：未登入
3登入成功T：王小明
4帶 sid=T 看訂單 → 成功T：王小明
✓帶 sid=T → 未登入收到新的 sid=T2T：已刪除
T2：王小明

第 2 步是攻擊的關鍵，也是上一節 Domain 和 __Host- 派上用場的地方：攻擊者要能把 sid=T 寫進小明的瀏覽器。用 __Host- 前綴，子網域寫不進同名 cookie；登入時換新 ID，就算 T 被塞進去了也沒用。兩道防線擋的是同一個攻擊的不同步驟，一起用。

換新 ID 的規則不只用在登入：權限改變時就換新 ID、刪掉舊的。包括登入成功、權限提升（例如店員切換成店長模式）、改密碼。換的時候，匿名 session 裡的購物車要搬到新 session，否則小明登入後發現購物車空了。session 存在資料庫時，「刪舊、建新」要放在同一個交易裡（PostgreSQL 課第 18 課），不能只成功一半。練習 3 會實作這個 login。

登入換號碼處理了 session 的開始。最後是結束：小明按下登出時，到底要刪掉什麼？

登出時要刪掉什麼？登出與登出所有裝置

登出要刪伺服器端的 session，清 cookie 只是順便。號碼有沒有效是名冊說了算：只清 cookie 的話，小明這台瀏覽器忘了號碼，但名冊上那一筆還在，號碼仍然有效。如果它早就被偷了（XSS 時沒設 HttpOnly、被裝了惡意擴充功能），攻擊者照樣用到絕對逾時為止。

清 cookie 的寫法是送一個同名稱、同 Path、同 Domain 的 cookie，加上逾時那一節講過的 Max-Age=0：

Set-Cookie: __Host-sid=; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=0

第一節說過，瀏覽器用（名稱、網域、路徑）三個一起當作 cookie 的身分。Path 或 Domain 寫得跟設定時不一樣，瀏覽器會當成另一個 cookie：多存一個空的，原本的還在。這就是第一節範例裡同一個 sid 出現兩次的由來。

有時候要登出的不只一台。登出所有裝置是依 userId 找出這個人所有的 session 全部刪掉，這些情況要做：

  • 使用者按「登出所有裝置」、發現帳號異常。
  • 改密碼、重設密碼：可能就是因為密碼外洩才改的，其他地方的 session 也要失效，通常保留目前這一個，免得使用者剛改完就被登出。
  • 帳號被停權：全部立即失效。

要依 userId 找 session，名冊就要能用 userId 查。前面說過名冊的 key 是 token 的雜湊，不是 userId，所以要另外準備查法：資料庫版的 session 表要在 user_id 上建索引（PostgreSQL 課第 20 課），不然每次都要掃整張表；Redis 版通常另外維護一個「userId → 這個人的 session key」的集合。練習 3 的 destroyAllForUser 會碰到這個限制。

到這裡，小明的登入狀態從發號碼牌、每次請求認人、過期、登入換號，到登出和全部登出，每一步都有對應的防線。

💡 實務上：帳號被盜時，客服第一步就是登出所有裝置
Google、GitHub 這類服務都有「目前登入的裝置」頁面，列出每個 session 的裝置、登入時間、最後活動時間，可以單獨登出某一個。要做這個功能，建立 session 時就要順便存 User-Agent（瀏覽器在請求標頭裡自報的瀏覽器和作業系統）和建立時間，事後補不回來。客服接到「我的帳號被盜」時，常見處理是讓該帳號所有 session 失效、要求重設密碼，所以後台最好有一個給客服用的按鈕，不要每次都請工程師手動刪資料。

Session cookie 屬性速查

查表用，不用背。

屬性作用與擋住什麼沒設或設錯會怎樣
HttpOnlyJavaScript（document.cookie）讀不到。網站被注入惡意腳本（XSS，第 7 課）時，腳本偷不走 session ID。XSS 一行程式就把 session ID 送到攻擊者手上。注意：設了也只擋「讀」，腳本還是能在你的頁面上發請求，瀏覽器照樣帶 cookie。
Secure只在 HTTPS 連線送出。HTTPS／TLS 是在 HTTP 外面加一層加密，路上的人看不到也改不了（部署課第 5 課）。在公共 Wi-Fi 上，中間人只要誘使瀏覽器發一個 http 請求，就能看到 cookie，拿去冒用，這叫 session 劫持。
SameSite控制跨站請求帶不帶這個 cookie：Strict、Lax、None。用來擋 CSRF（第 6 課）。只有 Chromium（Chrome 80+、Edge 86+）沒寫時預設 Lax；Firefox 預設沒開、Safari 沒有這個預設。所以一定要明寫。SameSite=None 必須搭配 Secure，否則整個 cookie 被拒收。
Path只有請求路徑在這個路徑底下才送。Path=/docs 會送到 /docs/a，不會送到 /docsets。沒寫時預設是設定它的那個請求路徑的目錄：/auth/login 回的 cookie 只會送到 /auth 底下，/orders 收不到，看起來像「登入後馬上被登出」。Path 不是安全邊界，同一個網站的其他路徑一樣讀得到。
Domain不寫時是 host-only cookie：只送回設定它的那台主機。寫了 Domain=coffee.example 就會送到所有子網域，包括外包做的活動頁 promo.coffee.example。只能設成自己或上層網域，不能是 com.tw 這種公共字尾（第 5 課）。
Max-Age／Expires存活秒數／到期日期，兩個都有時 Max-Age 優先；Max-Age=0 立刻刪除。都不寫是「瀏覽器關閉就消失」的 cookie（但「還原上次分頁」功能可能讓它留下來）。rfc6265bis 草案規定期限不超過 400 天，寫得更長會被壓成 400 天。

規則寫在哪裡、各瀏覽器的差異

瀏覽器的完整規則寫在 RFC 6265（現行標準）和它的修訂草案 rfc6265bis（draft-22，2025-12，已送審但尚未成為 RFC）。前綴、400 天上限、SameSite 這些規則都只寫在草案裡。

  • SameSite 沒寫時的預設：只有 Chromium（Chrome 80+、Edge 86+）預設 Lax；Firefox 預設沒開、Safari 沒有這個預設。
  • 期限上限：rfc6265bis 草案規定期限不超過 400 天，寫得更長會被壓成 400 天（練習 1 的 34560000 秒）。
  • 前綴不分大小寫：__host-sid 一樣要符合規則，這是 rfc6265bis 草案為了堵住大小寫繞過而規定的。
  • __Http-、__Host-Http- 前綴：另外要求 HttpOnly，保證只能由伺服器設定。Chrome／Edge 140+、Firefox 143+ 支援，Safari 還沒有，所以本課用 __Host-。

練習

練習 1：同事回報「登入後一直被登出」，你要寫一個除錯工具。checkSetCookie(header, requestUrl) 模擬瀏覽器收到一行 Set-Cookie（不含 Set-Cookie: 這幾個字）時收不收。依序檢查，第一個不符合的就回傳那個原因：

  1. 第一段沒有 =，或名稱是空的 → malformed（名稱、值前後的空白去掉）
  2. 名稱加值超過 4096 bytes（UTF-8，用 TextEncoder 算）→ too_large
  3. 有 Secure，但請求不是 https:，而且主機不是 localhost → secure_on_http
  4. 名稱以 __Secure- 開頭（不分大小寫）卻沒有 Secure → prefix_secure
  5. 名稱以 __Host- 開頭（不分大小寫），卻沒有 Secure、或 Path 不是 /、或有 Domain → prefix_host
  6. SameSite=None 沒有 Secure → samesite_none_insecure
  7. Domain（去掉開頭的 .、轉小寫）既不等於請求的主機，也不是它的上層網域 → domain_mismatch

屬性名稱與 SameSite 的值不分大小寫。接受時：沒寫 Domain 就是 host-only，domain 填請求的主機；沒寫 Path（或不是 / 開頭）就用請求路徑到最後一個 / 之前的部分，沒有剩下東西時是 /；Max-Age 超過 400 天（34560000 秒）就壓成 34560000，沒寫是 null（這題不處理 Expires）；沒寫 SameSite 記成 'unset'。

練習 2：實作 SessionStore。時間用建構子注入的 now()（毫秒），資料存在注入的 db。base64url、sha256 已經寫好（第 2 課）。

  • create(userId)：產生 32 bytes 的安全亂數 token（base64url），db 的 key 是 sha256(token)，回傳原始 token（要放進 cookie）。userId 是 null 代表還沒登入的匿名 session。
  • get(token)：找不到回 null；距離上次使用 ≥ 30 分鐘，或距離建立 ≥ 8 小時，就算過期：從 db 刪除並回 null；否則把 lastSeenAt 更新成現在，回傳 session。
  • destroy(token)：刪除這個 session（登出）。

練習 3：在練習 2 的 SessionStore（已經寫好）加上兩個方法：

  • login(currentToken, userId)：登入成功時呼叫。currentToken 是瀏覽器目前帶來的 session（可能是 null）。建立一個新的 session，如果舊的還有效就把它的 cart 搬過去，然後刪掉舊的，回傳新的 token。不能沿用舊的 token（session fixation）。
  • destroyAllForUser(userId, exceptToken?)：刪掉這位使用者所有的 session；有給 exceptToken 時保留那一個（改密碼時保留目前這台裝置）。注意 db 的 key 是雜湊。

練習 4：session cookie 設了 HttpOnly。網站有一個 XSS 漏洞，攻擊者的腳本在受害者的頁面上執行。下面哪一句正確？

✓ HttpOnly 只擋「讀取」：session ID 不會被偷走帶到別的地方用，這很有價值。但腳本就在你的網站上執行，它發的請求跟使用者自己發的一樣，cookie 照帶。所以 HttpOnly 是縮小損害，不是防 XSS；真正要做的是不讓 XSS 發生（第 7 課）。a 錯在把「偷不走」當成「用不了」；b 錯在 HttpOnly 正好讓 document.cookie 看不到這個 cookie。

練習 5：登出時，前端把 cookie 清掉、導回首頁，伺服器沒做任何事。這有什麼問題？

✓ 「登出」要讓那個 session ID 失效，而 ID 有沒有效是伺服器說了算。瀏覽器清掉 cookie 只影響這台瀏覽器；如果 ID 早就外洩（公用電腦、惡意擴充功能），攻擊者手上的那份還能用到絕對逾時。c 只看到了空間，沒看到安全問題。

練習 6：在 http://localhost:5173 開發時登入正常。部署到內網測試機 http://192.168.1.20 後，登入成功卻馬上被當成未登入，伺服器 log 也沒有錯誤。最可能的原因？

✓ 瀏覽器把 http://localhost 當成安全的來源，Secure cookie 照收；http://192.168.1.20 不是，帶 Secure 的 Set-Cookie 被直接丟掉，伺服器不會知道。打開 DevTools 的 Network 面板，看登入回應的 Set-Cookie 旁邊的警告就能確認。修法是讓測試機也走 HTTPS，而不是把 Secure 拿掉。b：store 壞了伺服器會有錯誤，而且瀏覽器根本沒存 cookie、請求就沒帶 sid，問題在 store 之前。c：CORS 擋住時登入請求本身就會在 console 報錯，前端拿不到「登入成功」。

常見錯誤

  • session ID 用遞增數字、userId 或 Math.random 組出來：猜得到就能冒用別人。用 crypto.getRandomValues 產生 128 bits 以上。
  • 登入後沿用同一個 session ID：session fixation。登入、權限提升、改密碼時都要換新 ID、刪掉舊的。
  • 登出只清 cookie：伺服器上的 session 還有效。登出要刪伺服器端的 session。
  • 只有滑動逾時：被偷的 session 可以一直續命。一定要加絕對逾時。
  • 在 session 裡快取角色或權限：降權之後要等重新登入才生效。session 只存 userId，權限從資料庫查。
  • cookie 設 Domain 到上層網域：所有子網域（活動頁、外包網站）都收得到，也寫得進同名 cookie。不寫 Domain，用 __Host- 前綴。
  • 不寫 SameSite，交給瀏覽器預設：只有 Chromium 預設 Lax，Firefox、Safari 沒有。明寫 SameSite=Lax 或 Strict。
  • session 存在單台機器的記憶體：部署兩台之後使用者一直被登出。放到 Redis 這類共用 store。
  • 沒寫 Path：/auth/login 設的 cookie 只會送到 /auth 底下，/orders 收不到。明寫 Path=/。
  • 清 cookie 時 Path 或 Domain 跟設定時不同：瀏覽器當成另一個 cookie，原本的沒被刪。用同樣的名稱、Path、Domain 送 Max-Age=0。

小結

  • HTTP 是無狀態的。登入後發一個猜不到的 session ID，伺服器在 session store 記下它代表誰；cookie 負責每次自動把 ID 帶回來。
  • Set-Cookie 一個 cookie 一行、帶屬性；Cookie 只有名稱和值。瀏覽器用（名稱、網域、路徑）分辨 cookie，拒收時不會通知伺服器，要看 DevTools。
  • session cookie：__Host-sid=…; Path=/; Secure; HttpOnly; SameSite=Lax，不設 Domain。HttpOnly 只擋讀取，Secure 擋中間人，SameSite 擋跨站，__Host- 擋子網域覆蓋。
  • session store 只存 token 的 SHA-256；256 bits 的隨機 token 不需要慢雜湊。session 只放判斷要用的最少資訊，權限從資料庫查；多台伺服器時放 Redis 這類共用 store。
  • 閒置逾時擋忘了登出，絕對逾時擋被偷的 ID 一直續命，兩個一起用；先檢查再延期；時間用注入的 now()。
  • 登入、權限提升、改密碼時換新 ID 並刪掉舊的；登出刪伺服器端的 session；改密碼時讓其他裝置的 session 全部失效。
