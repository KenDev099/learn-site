階段 1：地基：身分、信任與密碼學工具 · 第 1 課

認證與授權：誰在用、能做什麼

咖啡店的 API 上線第一週，客服轉來一封信。顧客小明登入後打開「我的訂單 #42」，順手把網址列的 42 改成 43，畫面上出現了陳美華的訂單：她點了什麼、在哪家門市取餐。沒有人入侵伺服器，小明也沒用任何駭客工具，他只改了一個數字。

回頭看那支 GET /orders/:id，它只做一件事：拿路徑上的編號去資料庫查，查到就回傳。它沒有問「這個請求是誰發的」，更沒有問「這個人能不能看這一筆」。這種改個編號就看到別人資料的漏洞，在 OWASP 整理的 API 安全風險裡排第一名。OWASP 是一個整理網站與 API 常見安全風險的非營利社群，它的清單是業界檢查 API 時最常拿來對照的依據。

這一課的任務：把 GET /orders/:id 修到正確，並弄懂它為什麼會漏。修的過程會碰到整門課的基本觀念：伺服器能相信什麼、認證和授權差在哪、檢查不通過時回哪個狀態碼、怎麼設計才不會在下一支 API 重蹈覆轍。課末的練習 1 就是親手寫出修好的版本。

這課的路線：
  1. #43 是怎麼流出去的：跟著請求走一趟，看伺服器從哪一條線之後就不能直接相信收到的資料。
  2. 伺服器該問哪幾個問題：識別、認證、授權是三個不同的步驟，#43 外流是因為少了授權（開場問題的最小答案）。
  3. 檢查不通過要回什麼：401、403、404 怎麼選，為什麼別人的訂單要回跟「不存在」一樣的 404。
  4. 能不能讓前端把 customerId 一起送來：請求的每個位元組都在使用者手上，身分只能來自認證步驟。
  5. 密碼被偷了怎麼辦、下一支 API 怎麼不再漏：認證因素與 MFA，以及預設拒絕、最小權限、縱深防禦。
這課會用到：
  • Node 課第 12 課的 HTTP：請求帶方法、路徑、標頭、body，回應帶狀態碼、標頭、body。
  • Node 課第 14 課的資源路徑：GET /orders/:id 用路徑參數指定要哪一筆資源。
  • TypeScript 課第 16 課的可辨識聯合：用共同欄位（這課是 status）區分幾種形狀，例如 { status: 200, … } | { status: 404, … }。

#43 是怎麼流出去的？

要知道漏洞在哪，先跟著「查看訂單 #42」的請求走一趟。下圖是修好之後應該有的樣子；出事的版本少了中間的①認證和②授權兩關，請求一進來就直接去查資料庫。

從最左邊看起。小明按下按鈕時，Vue 前台發出 GET /orders/42。這個請求是在小明的電腦上、由小明的瀏覽器組出來的。網址裡的 42 雖然是前端程式填的，但小明可以在網址列改它，也可以打開 DevTools 改掉請求的任何部分再送出。伺服器收到的只是一串位元組，它分辨不出這串位元組是 Vue 程式正常產生的，還是小明手動改過的。

圖上的虛線叫信任邊界（trust boundary）：資料從你控制不了的一方，進到你控制的一方的那條線。線的右邊是你的 API 程式和資料庫，程式怎麼跑由你決定；線的左邊是使用者的瀏覽器，最後送出什麼由使用者決定。第三方金流也在另一條線的外面：它的伺服器不歸你管，回應可能出錯，也可能被偽造。所以規則只有一條：跨過這條線的每個位元組，都要在你這一側重新檢查，不能因為「這是我們自己的前端送的」就相信。

出事的 handler 就是忘了這條線。它把路徑上的 43 當成「使用者想看、而且有資格看的訂單」，但 43 只代表「有人送來了 43」。前端畫面只列出小明自己的訂單，這件事發生在線的左邊，對伺服器沒有任何保證。

攻擊者從線的外面碰得到的所有入口，合起來叫攻擊面（attack surface）：每個 API、每個查詢參數、每個標頭、每個 cookie、每個上傳的檔案。GET /orders/:id 的路徑參數就是攻擊面的一部分，小明碰巧用它看到了別人的資料。多開一支 API，攻擊面就大一點，要檢查的入口也多一個。

漏洞不在前端，而在線的右邊：伺服器收到 43 之後什麼都沒問。下一步要弄清楚的是，伺服器到底該問哪幾個問題。

伺服器該問哪幾個問題？識別、認證、授權

伺服器在交出訂單之前，要依序完成三個步驟。這三個詞常被混用，但它們各自回答不同的問題，失敗時的處理也不同。用咖啡店櫃台比喻：

步驟櫃台API失敗時這門課在哪講
身分識別（identification）：宣稱「我是誰」報上會員手機號碼輸入 email——
認證（authentication，常縮寫 authn）：證明宣稱是真的出示會員卡並簽名驗證密碼、token401階段 1～4
授權（authorization，常縮寫 authz）：知道是誰之後，決定能不能做店員判斷這張卡能不能用員工價判斷能不能看 #42、能不能退款403 或 404階段 5

放回訂單的情境：小明登入時輸入 email，這是識別，他宣稱自己是這個帳號；接著輸入密碼，伺服器比對正確，這是認證，他的宣稱被證明了。之後他打 GET /orders/43，伺服器判斷「小明能不能看 #43」，這是授權。順序是固定的：沒有認證就不知道是誰，不知道是誰就沒辦法判斷他能做什麼。

認證要檢查的那樣東西，叫憑證（credential）：用來證明身分的東西，例如密碼、token、私鑰。憑證檢查通過之後，伺服器就認定「這個請求代表誰」，這個認定的結果叫主體（principal）。主體可能是顧客、店員，也可能是另一個服務（第 17 課）。這課的程式裡，req.principal 就是認證步驟算出來的結果，之後所有判斷都從它出發。

還有一個實際問題：小明只在登入時送一次密碼，之後每個請求不可能再送一次。所以登入成功後，伺服器會交給瀏覽器一樣東西，讓之後的請求帶著它來證明「我是剛剛登入的那個人」。常見的做法有兩種。一種是伺服器發一張號碼牌，自己記住號碼對應誰，叫 session（第 4 課）；另一種是發一張有簽章、上面自己寫著「我是誰」的通行證，叫 token（第 8 課）。現在先認得名字就好，這課只需要知道：認證步驟驗過 session 或 token 之後，會把結果放進 req.principal。

有了這三個詞，就能說清楚 #43 為什麼外流。出事的版本兩關都沒有，但只補上認證並不夠：小明本來就登入了，就算確認了請求來自小明，少了授權他照樣看得到 #43。所以真正的缺口是授權：沒有比對 #43 的 customerId 是不是小明。只做認證、不做授權，等於確認了來的人是會員，就讓他翻整本訂單簿。修法的最小版本，是在查到訂單之後多做一次比對：

principal = 認證步驟的結果       → 小明，id 1
order     = 資料庫裡的 #43       → customerId 2
order.customerId !== principal.id → 不是他的，不能看

存取了不屬於自己的資料，叫越權。要擋住越權，授權檢查必須針對「這一筆」資料做，光確認「有登入」不夠。第 19 課會專門處理這類逐筆的檢查。

用同樣的眼光看之前寫過的程式，也能看出它缺了什麼：

NestJS 課第 6 課的 AdminKeyGuard 只檢查標頭裡的金鑰對不對：它有認證（證明你拿到了金鑰），但沒有「你是誰」，所有人共用同一把，也就無法分辨誰做了什麼、無法只撤銷某個人。這門課會一步步把它換成真正的使用者登入。

知道要加授權檢查之後，下一個問題馬上出現：檢查不通過時要回什麼？沒登入、登入了但不是你的、訂單根本不存在，這三種情況該回同一個狀態碼嗎？

檢查不通過，該回 401、403 還是 404？

狀態碼不只是給人看的錯誤訊息。前端拿它決定下一步：把使用者送去登入頁，還是留在原頁顯示「沒有權限」。回錯了，前端就會做錯事。三個候選各自的意思是：

  • 401 Unauthorized：名字取錯了，它的意思其實是「還沒認證，或認證失敗」（unauthenticated）：沒帶 token、token 過期、簽章不對。對應的是三步驟裡的「認證」失敗。HTTP 規格 RFC 9110 §15.5.2 規定：回 401 時 MUST 帶 WWW-Authenticate 標頭，告訴客戶端該用什麼方式認證，下面的例子寫的是「請用 Bearer token」。前端收到 401 通常是導去登入頁。
  • 403 Forbidden：伺服器知道你是誰，但你沒有權限，對應的是「授權」失敗。用同一個帳號重新登入也沒用。例如店員想核准退款，但退款只有店長能做。
  • 404 Not Found：找不到，或者不願意透露它存不存在。RFC 9110 §15.5.4 明寫：想隱藏資源存在與否的伺服器，可以用 404 代替 403。
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="coffee"
Content-Type: application/json

{"error":"unauthenticated"}

Bearer 是「持有者」的意思：誰拿著這個 token 就能用，不再另外確認身分，所以 token 外洩就等於帳號外洩。客戶端在請求裡用 Authorization: Bearer <token> 帶上它，下一節的 curl 就是這樣帶的。realm 是伺服器自訂的保護範圍名稱，讓客戶端知道要拿哪一組憑證，這課照抄即可。

回到 #43。小明已經登入，所以不是 401；他沒權限看，照字面應該回 403。問題出在咖啡店的訂單編號是連續的。如果「別人的訂單」回 403、「不存在的訂單」回 404，攻擊者從 1 掃到 10000，看回應就知道哪些編號存在，等於知道這家店有多少訂單、每天賣多少。從回應的差異推測某個帳號或某筆資料存不存在，叫做列舉（enumeration）。防法是讓兩種情況的回應一模一樣：狀態碼相同、body 也相同，攻擊者就分辨不出來，列舉也就沒有用。所以 #43 要回 404，跟查不存在的 #99999 完全一樣。

同樣的道理也決定了檢查的順序：先檢查登入、再查資料。如果先查資料，沒登入的人查不存在的訂單會得到 404、查存在的訂單才走到登入檢查得到 401，一樣洩漏了存在與否。先認證的話，沒登入的人不管查哪一筆都只會得到同一個 401，伺服器還沒碰資料就拒絕了。

把這個順序寫成程式。執行後看五行輸出：沒登入的兩種情況都是 401；登入後，「別人的訂單」和「不存在的訂單」都是 404，只有自己的訂單是 200。

那 403 什麼時候用？當「這東西存在」本來就不是祕密：店員打 POST /orders/42/refund，退款功能人人都知道有，回 403 讓前端顯示「需要店長權限」，比假裝找不到更有用。判斷方式：回 403 會不會洩漏不該知道的事？會就回 404。

到這裡，#43 的修法已經完整：先認證，沒登入回 401；再查訂單並比對擁有者，不是他的或不存在都回同樣的 404。

💡 實務上：401／403 是前後端之間的約定
前端通常會在 axios 的攔截器裡統一處理狀態碼。攔截器是每個請求、回應都會經過的共用函式，用 fetch 的話就自己包一層。收到 401 清掉登入狀態、導去登入頁；收到 403 顯示「沒有權限」，不要把人登出。後端如果把「權限不足」也回成 401，使用者就會被莫名其妙登出、一直重新登入。所以新 API 開工前，前後端要先講好每個錯誤情況回什麼狀態碼和 body，寫進 API 文件。資深工程師 review 像 GET /orders/:id 這種 API 時，會實際打一次「別人的訂單」和「不存在的訂單」，把兩個回應的狀態碼和 body 並排比對。

能不能讓前端把 customerId 一起送來比對？

上一節的修法完全靠 req.principal。修 #43 的時候，團隊裡很可能有人提出一個看起來更省事的做法：「前端反正知道登入的是誰，讓它把 customerId 放進請求，後端拿來比對就好。」這個提議錯在哪，牽涉到前端工程師轉後端最需要調整的觀念：請求的每一個位元組都在使用者手上。

第一節說過，請求是在信任邊界的另一邊組出來的。你的 Vue 程式只是「其中一種」發請求的方式。任何人都能打開 DevTools 改 body，或在 Network 面板的請求上按右鍵「Copy as cURL」，把它複製成一行終端機指令，改完再送。

這個錯誤在「我的集點卡」這種 API 上最容易看清楚，所以接下來換它來示範。集點卡的網址是 GET /stamp-card，路徑上沒有任何 id，因為「我的」就是指目前登入的人；查誰的卡，答案只該由 principal 決定。下面是小明改過的請求：token 是他自己登入拿到的、是真的，但他另外加了一個自訂標頭宣稱自己是店長，又在 body 裡放了陳美華的 id：

curl -X GET 'https://api.coffee.example/stamp-card' \
  -H 'Authorization: Bearer eyJ…（小明自己的 token）' \
  -H 'X-User-Role: manager' \
  -H 'Content-Type: application/json' \
  -d '{"customerId": 2}'

這個請求裡，只有 Authorization 標頭的 token 是伺服器自己發出去、驗得了真假的，驗過之後就知道這是小明。X-User-Role 和 body 的 customerId 小明想寫什麼就寫什麼，伺服器沒有任何辦法確認。（GET 帶 body 是否合法，見課末「補充與查表」。）

由此得到第一條規則：伺服器只相信自己驗證過的東西。「這個請求是誰」只能來自認證步驟，也就是驗證過的 session 或 token 算出來的 principal；不能來自 body 的 customerId、自訂的 X-User-Role 標頭，也不能相信前端算好的 price、isAdmin。回頭看那個提議：讓前端送 customerId 來和訂單的擁有者比對，小明只要把 customerId 改成 2，查 #43 的比對就會通過。比對的一邊是小明自己填的值，這個檢查等於沒做。

第二條規則是反過來看前端：隱藏按鈕、Vue 的路由守衛只是使用者體驗，讓一般人不會點到用不了的功能。它擋不住直接打 API 的人，因為它們全都在信任邊界的另一邊。Vue 課第 20 課會再談前端權限的界線。

把上面那個請求丟給兩種 handler。下面的壞版本讓 body 的 customerId 優先。執行後比對兩行：同一個偽造的請求，壞的版本回傳 9 點（陳美華的），好的版本回傳 3 點（小明自己的）。

這種寫法通常來自好意：「前端反正知道使用者 id，順便傳過來比較方便」。結果是認證做得再好，授權還是被一個欄位繞過。

💡 實務上：自己動手試一次「換掉 id」
開發完一個 API，最便宜的安全測試就是：登入帳號 A，在 DevTools 用「Copy as cURL」複製請求，把網址或 body 裡的 id 換成帳號 B 的，再送一次。如果看得到或改得到 B 的資料，就是越權。這類問題沒人主動試，往往要等使用者回報才發現，就像開場那封客服信。Code review 時看到 handler 從 req.body、req.query 讀 userId、role、price 來做判斷，就該停下來問「這個值是誰給的？」。前端同事說「按鈕已經藏起來了」時，要能說清楚那只是畫面，API 一樣要擋。

如果小明的密碼被偷了呢？認證因素與 MFA

到目前為止，所有檢查都建立在一個前提上：principal 是真的。但認證只證明「發請求的人拿得出這個帳號的憑證」。假設陳美華在別的網站用了同一組密碼，那個網站外洩後，攻擊者拿這組密碼來登入咖啡店：認證通過，principal 是陳美華，授權也照規則放行她的訂單。每一道檢查都沒寫錯，資料還是被看光了。所以要另外問：認證本身能做到多可靠？

證明身分的方式可以分成三類，叫認證因素（authentication factor）：

類型例子弱點
你知道的密碼、PIN、安全問題的答案會被猜、被釣魚、被其他網站外洩後拿來試
你擁有的手機上的驗證器 App、安全金鑰、手機裡的 passkey會遺失，要有復原流程
你本人的特徵指紋、臉換不掉；所以不該送到伺服器

注意每一類的弱點：同一類的東西，往往會被同一種手法一起拿走。釣魚網站能騙走密碼，也能順便騙走安全問題的答案，因為兩者都是「你知道的」，都能被你親手打進假網站。多因素認證（MFA，multi-factor authentication）就是針對這點設計的：要求至少兩種不同類型的因素，攻擊者得同時用兩種不同的手法才能冒用。偷到陳美華密碼的人，手上並不會因此多出她的手機。所以判斷是不是 MFA，看的是「類型」，不是步驟數：

  • 密碼＋安全問題：兩個都是「知道的」，一起被釣魚網站騙走。不算 MFA，只是兩個步驟。
  • 密碼＋驗證器 App 的 6 位數字：知道的＋擁有的，算（第 14 課）。
  • 手機上的 passkey，用指紋解鎖：擁有的（手機裡的私鑰）＋本人特徵。指紋只在手機上解鎖私鑰，不會送到伺服器，伺服器只收到私鑰的簽章（第 15 課）。

指紋不送到伺服器的理由，就是表格裡的那個弱點：換不掉。密碼外洩了可以改，指紋外洩了一輩子都是那個指紋。所以生物特徵只留在使用者自己的裝置上，用來解鎖裝置裡的私鑰。

回到咖啡店：MFA 讓 principal 更可信，但它管的是「是不是本人」，管不到「本人能看什麼」。#43 外流是授權的問題，再強的 MFA 也修不好；反過來，授權寫得再嚴，也擋不住拿著真密碼登入的人。兩邊都要做。到這裡 GET /orders/:id 已經修好了，但咖啡店之後還會有幾十支 API，下一支要怎麼避免再犯同樣的錯？

下一支 API 怎麼不再漏？資安設計的基本原則

修好一支 API 靠的是那一次比對；讓幾十支 API 都不漏，靠的是設計原則：就算某個工程師某天忘了寫檢查，系統的預設行為也是安全的。這幾條原則會在整門課反覆出現，先各配一個咖啡店的例子：

  • 預設拒絕（default deny）：沒有明確允許的就拒絕；判斷過程出錯時也拒絕，這一半也叫 fail closed。開場那支 GET /orders/:id 正是預設允許：沒寫檢查，就全部放行。再看一個例子：新加了 GET /admin/export 卻忘了設權限，預設拒絕的系統會擋下來，預設允許的系統會把全部顧客資料給任何人。預設拒絕的寫法是列出「允許的」，其他一律拒絕，叫白名單；反過來的寫法叫黑名單：列出「不能做的」，其他都放行，漏列一條就是漏洞。練習 3 會親手寫一個預設拒絕的權限表。
  • 最小權限（least privilege）：只給完成工作需要的權限。吧台店員要能改訂單狀態，但不需要退款、不需要看營收報表。API 連資料庫用的帳號也一樣（PostgreSQL 課第 24 課）。
  • 縱深防禦（defense in depth）：多層防護，一層失守還有下一層。API 檢查訂單擁有者之外，資料庫再用 Row Level Security 限制每個連線看得到的列（PostgreSQL 課第 24 課），程式漏了一個檢查也不會整個失守。如果 #43 那時有這一層，就算 handler 忘了比對，資料庫也不會把陳美華的訂單交出來。
  • 不要自己發明密碼學：這門課會用 Web Crypto 親手做雜湊、簽章、TOTP，是為了理解原理、看懂錯在哪；正式環境用成熟、有人審查過的函式庫。
  • 安全與易用要取捨：每次結帳都要 MFA 最安全，但顧客會跑掉。資深工程師的工作是說清楚風險和代價，讓團隊做決定，例如「只有改密碼、大額退款時才要再驗證」。

預設拒絕最容易在「出錯時」被忘記。授權檢查不一定是程式裡的一個 if，系統變大之後，常常是去問另一個專門管權限的服務。那個服務逾時了，該放行還是拒絕？下面模擬權限服務掛掉，執行後看三行：fail open 的版本回 true，退款被放行；fail closed 的版本先印出失敗原因，再回 false。

fail open 等於：攻擊者只要想辦法讓權限服務變慢（例如灌大量請求），所有檢查就自動失效。拒絕會讓少數請求失敗，但那是看得到、會被告警抓到的問題；被偷偷放行是看不到的。

💡 實務上：哪些可以降級、哪些一定要拒絕
系統依賴的服務總會有掛掉的時候，要先分清楚哪些功能可以「降級照常營業」：推薦商品、熱門排行抓不到，顯示預設清單就好。但權限檢查、登入、付款、退款這類涉及身分和金錢的判斷，出錯時一律拒絕。拒絕時要記錄並觸發告警，讓維運知道該處理，而不是默默失敗。PM 問「權限服務掛了能不能先放行」時，資深工程師會把代價說清楚：放行的那段時間，任何人都可能做任何事，就像開場的 #43 一樣，而且事後也很難查出誰做了什麼。

補充與查表

GET 可以帶 body 嗎？

GET 帶 body 在 HTTP 規格 RFC 9110 §9.3.1 裡沒有定義的意義，正常的前端不會這樣送；但很多伺服器框架照樣解析，攻擊者就會試。所以上面 curl 例子裡的 -d 並不是假想情況：只要你的框架會解析它、handler 會讀它，它就是攻擊面的一部分。

練習

練習 1：寫 respond(req, orders)，處理 GET /orders/:id。req.principal 是認證步驟的結果（null 表示沒登入）。規則：

  • 沒登入：回 401，帶 WWW-Authenticate: Bearer realm="coffee"，而且不管訂單存不存在，回應都一模一樣。
  • 顧客只能看自己的訂單（customerId 等於自己的 id）。
  • 店員只能看自己門市的訂單（storeId 相同）。顧客和店員是兩張不同的表，id 可能剛好一樣。
  • 訂單不存在、或沒權限看：一律回同樣的 404。

練習 2：「查集點卡」的 handler 用 x-role 標頭判斷是不是店員、用 body 的 customerId 決定查誰，任何人都能冒用。改成只依 req.principal（認證步驟填好的）決定：

  • 顧客：只能查自己的卡（id 等於自己的 customerId）。query 帶了 customerId 就回 404，這個參數只給店員用。
  • 店員：用 query 的 customerId 指定顧客。它必須是正整數字串（例如 '2'，不接受 ''、'abc'、'1.5'、'02'），否則回 400。只能查自己門市的卡，別門市或沒有這張卡都回 404。
  • headers 和 body 完全不要用。

練習 3：寫預設拒絕的 authorize(principal, method, path, policy)。policy 的鍵是「方法 空白 路徑樣式」，值是 'public'（不用登入）或允許的角色清單。規則：

  • 先找規則：方法要完全相同（大小寫也要一樣，'post' 不等於 'POST'）；路徑用 / 切開後逐段比對，段數要一樣，:id 匹配任何一段非空的字串。找不到規則 → no_policy。
  • 'public' → 允許。其他規則：沒登入 → unauthenticated；角色在清單裡 → 允許；不在（包括資料庫裡出現程式不認得的角色、清單是空的）→ forbidden。

完成後試試：POST /orders/42/refund 不能因為「開頭是 POST /orders」就讓顧客通過；/orders//refund、/menu/ 都找不到規則。

練習 4：Vue 的路由守衛已經擋住非店長進入 /admin/reports，頁面上也沒有營收報表的按鈕給店員。後端的 GET /reports/revenue 還需要檢查角色嗎？

✓ b。路由守衛和隱藏按鈕只控制「Vue 前台畫面長什麼樣」，請求的每個位元組都在使用者手上：從 Network 面板複製請求、改網址再送就繞過了。API 網址也不是祕密，打包後的 JS 裡就看得到（c 錯）。前端的檢查是使用者體驗，後端的檢查才是安全機制（a 錯）。

練習 5：咖啡店會員登入時先輸入密碼，再回答安全問題「第一隻寵物的名字」。這算多因素認證（MFA）嗎？

✓ c。MFA 看的是因素的「類型」，不是步驟數（a 錯）。密碼和安全問題都是「知道的」，存在哪裡不影響類型（b 錯）。MFA 也不必用生物特徵：密碼＋驗證器 App 的 6 位數字（知道的＋擁有的）就是 MFA（d 錯）。

練習 6：小明已經登入，打 GET /orders/43，但 #43 是陳美華的訂單。訂單編號是連續的。哪個回應最好？

✓ c。401 的意思其實是「還沒認證或認證失敗」，小明已經登入了，回 401 前端會誤以為要重新登入（a 錯）。403 讓攻擊者把編號從頭掃一遍，就能分辨哪些訂單存在，這叫列舉；RFC 9110 允許用 404 隱藏資源是否存在（b 錯）。200 加空物件讓前端以為成功，錯誤處理全亂（d 錯）。

常見錯誤

  • 把 401 和 403 用反：401 是「不知道你是誰」，前端會導去登入頁；403 是「知道你是誰但不准」，重新登入也沒用。回 401 時要帶 WWW-Authenticate。
  • 相信前端送來的 userId、role、price、isAdmin：這些都在攻擊者手上。「是誰」只來自認證步驟，價格從資料庫查，角色從資料庫或驗證過的 token 讀。
  • 只在前端隱藏按鈕或路由：那是使用者體驗。每個 API 都要在伺服器端檢查。
  • 授權寫成黑名單：列出「不能做的」，其他都可以。新角色、新路由一出現就漏。改成白名單：列出允許的，其他一律拒絕。
  • 先查資料再檢查登入：沒登入的人能從 401 與 404 的差異推測資料存不存在。先認證，再碰資料。
  • 別人的資料回 403：當「存在與否」本身是祕密（訂單、帳號），回跟「不存在」一樣的 404。
  • 權限服務掛掉時先放行（fail open）：出錯就拒絕，並記錄、告警。

小結

  • #43 外流是因為伺服器相信了跨過信任邊界的資料：路徑上的編號、body、標頭都在使用者手上。前端的路由守衛和隱藏按鈕只是使用者體驗，不是安全機制。
  • 識別是宣稱身分、認證是證明身分（失敗回 401）、授權是決定能做什麼（失敗回 403 或 404）。認證的結果是 principal，之後的判斷只看它；只做認證、不做授權，就是改編號看別人訂單的 API。
  • 401 的意思是「沒認證」，必須帶 WWW-Authenticate；403 是知道你是誰但不准；別人的資料回跟「不存在」一樣的 404，擋住列舉。
  • 先檢查登入，再查資料。
  • MFA 是至少兩種「不同類型」的因素：知道的、擁有的、本人特徵。它讓 principal 更可信，但取代不了授權。
  • 預設拒絕（包括出錯時）、最小權限、縱深防禦，讓下一支 API 忘了寫檢查時也不會整個失守，是之後每一課的基本原則。
