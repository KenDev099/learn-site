階段 3：Token 與 JWT · 第 8 課

Token 與 JWT：結構、簽章與公鑰

咖啡店長大了，原本一個後端做完所有事，現在拆成三個服務：Auth 服務負責登入，訂單服務負責點餐與訂單，集點服務負責點數，之後還會有會員服務。王小明在 Vue 前端登入後，按下「我的訂單」，前端送出 GET /orders。訂單服務收到這個請求，第一個問題是：這是誰發的？

第 4 課的做法是 session：瀏覽器帶著一張號碼牌，伺服器每個請求都去 session store 查「這個號碼是誰」。拆成三個服務以後，訂單和集點每收到一個請求都要去問同一個 session store，它就變成每個請求都要經過的瓶頸，它一停機，三個服務一起停。這一課要解決的任務是：讓訂單服務不用問任何人，就能確定這個請求是 42 號顧客王小明發的，而且沒有人能冒充他。答案是 JWT。這課把它拆開來看，親手簽出和驗證簽章；驗證時每個欄位要怎麼檢查，是第 9 課的主題。

這課的路線：
  1. 訂單服務不想每次都問 session store，有什麼辦法？兩種 token 的差別，以及 bearer token 為什麼像現金。
  2. 一張 JWT 裡裝了什麼？Auth 服務該在 payload 寫哪些內容、時間怎麼寫？
  3. 怎麼讓 payload 改不了？先用 HS256 簽一次，再看它為什麼不適合三個服務。
  4. 怎麼讓訂單服務只能驗、不能簽？非對稱簽章，以及訂單服務怎麼用 JWK、JWKS、kid 拿到並選對公鑰。
  5. Auth 服務要換金鑰時怎麼不把所有人登出？最後整理 JWT 解決了什麼、沒解決什麼。
這課會用到：
  • 第 2 課的 base64url 與 HMAC：base64url 把位元組寫成網址安全的字串；HMAC 用共用金鑰算出標籤，用 crypto.subtle.verify 驗證。
  • 第 4 課的 session：伺服器存「這個 ID 是誰」，每個請求都查 store。這課一直拿它跟 JWT 對照。
  • TypeScript 課第 26 課的驗證外部資料：從 token 解出來的 JSON 先當成 unknown，用 第 16 課的 typeof、in 縮小型別後才使用。

訂單服務不想每次都問 session store，有什麼辦法？

先把「token」這個字講清楚。登入成功後，伺服器發給客戶端一串字，之後每個請求都帶著它，伺服器看這串字就知道是誰，不用每次重送密碼。這串字就叫 token。第 4 課的 session ID 也是一種 token。

token 依「它本身有沒有寫內容」分成兩種，差別正好對應訂單服務的困擾。

第一種是不透明 token（opaque token）：一串隨機字串，本身沒有任何意義，要拿去問發 token 的伺服器才知道代表誰。像咖啡店的取餐號碼牌，「37 號」本身什麼也沒說，要看櫃檯的紀錄。session ID 就是這種。它的好處是伺服器完全掌控：刪掉那筆紀錄，token 立刻失效。代價是每個請求都要查一次紀錄，這就是訂單服務現在的處境。

第二種是自包含 token（self-contained token）：token 本身就寫著「我是 42 號顧客，15 分鐘後到期」，再附上一個發行者的簽章。拿到的人只要驗過簽章，就能相信上面寫的內容，不用問任何人。像總店蓋了章的證明書，分店看印章就知道是真的，不用打電話回總店。訂單服務要的就是這個：Auth 服務在登入時寫好、簽好，訂單服務自己驗。JWT 是最常見的自包含 token 格式，這課接下來都在講它。

不管哪一種，token 在 HTTP 上通常都是 bearer token（持有者 token）。「bearer」是「持有的人」：前端把它放在 Authorization: Bearer <token> 標頭送出，伺服器只看「有沒有這張 token」，不問拿著它的是誰。RFC 6750 對它的定義就是：任何持有它的人都能使用它。所以 bearer token 像現金，掉了就是撿到的人的。它外洩的嚴重程度和密碼一樣，這一點會在整課反覆出現。

兩種 token 放在一起比，取捨就很清楚：

不透明 token（session ID）自包含 token（JWT）
驗證時要查資料庫嗎要，每個請求都查不用，驗簽章就好
能不能隨時撤銷能，刪掉那筆紀錄就失效難，簽出去的 token 到期前都有效（第 11 課）
大小固定，約 43 個字元幾百個字元起跳，內容越多越大
內容誰看得到只有伺服器任何拿到 token 的人
外洩的影響有效到被撤銷或逾時有效到 exp，通常只能等它過期
適合單一網站、要能立刻登出多個服務各自驗證、不想每次都查中央資料庫

JWT 用「不查資料庫」換來「很難撤銷」，這是整個階段 3 的主軸。第 10 課用很短的效期加上 refresh token 縮小風險，第 11 課再完整比較什麼時候該選哪一種。這一課先專心把 JWT 做對：它是自包含的，所以下一個問題是，它到底「包含」了什麼？

一張 JWT 裡裝了什麼？

JWT（JSON Web Token）的格式由 RFC 7519 定義。它是三段 base64url 字串，用 . 串起來：

base64url(header) . base64url(payload) . base64url(signature)

三段各有分工：

  • header：一個 JSON 物件，說明這張 token 本身，例如用什麼演算法簽（alg）、是什麼種類（typ）。
  • payload：一個 JSON 物件，放真正要傳達的內容。裡面的每個欄位叫一個 claim（宣告），因為它是發行者對某件事的聲明，例如 "sub": "42" 聲明「這張 token 的主體是使用者 42」。
  • signature：發行者對前兩段算出來的簽章。怎麼簽由另一份規格 JWS（JSON Web Signature）、RFC 7515 定義。兩份規格的分工是：JWT 規定內容長什麼樣，JWS 規定怎麼簽。

執行後看輸出的前兩行（原文）和最後一行，三件事要看清楚。

第一，payload 只是編碼，不是加密。上面的程式沒有用到任何金鑰，就把內容讀出來了。也就是說，任何拿到 token 的人：使用者自己、瀏覽器擴充功能、log 系統、中間經過的 proxy，都看得到 payload。王小明的 token 裡不能放密碼、手機號碼、地址、身分證字號這類資料。

第二，header 原文裡有 \r\n 和空白。RFC 刻意這樣寫，是為了提醒：簽章簽的是「base64url 之後的那串文字」，不是 JSON 物件。如果把 header 解碼成物件再 JSON.stringify 回去，會得到 {"typ":"JWT","alg":"HS256"}，換行和空白不見了，位元組不同，簽章就對不上。所以驗證時一定要用收到的原始字串，下一節會親眼看到這件事。

第三，解碼沒有驗證任何東西。攻擊者可以把 payload 的 sub 改成 "1"（店長的 ID）再編碼回去，解碼一樣成功。訂單服務如果只解碼就相信 sub，等於誰都能冒充任何人。只有驗過簽章，內容才可信。

不要把正式環境的 token 貼到線上的 JWT 解碼網站
除錯時很順手就會這樣做。但 bearer token 誰拿到誰就能用，貼出去等於把登入狀態交給那個網站，也可能留在瀏覽器歷史和剪貼簿同步裡。在本機解碼就好（練習 1 的 decodeJwt，或在終端機用 base64 指令），而且只看 header 和 payload。

簽章要保護的就是 payload 的內容，所以在學怎麼簽之前，先決定 Auth 服務要在王小明的 payload 裡寫什麼。

Auth 服務該在 payload 寫什麼？

從訂單服務的角度想，它收到一張 token，需要回答四個問題才敢處理 GET /orders：

  1. 這張 token 代表誰？訂單服務要用這個 ID 去查王小明的訂單。
  2. 是誰發的？訂單服務只信任自家的 Auth 服務，不信任別人發的 token。
  3. 是發給誰用的？如果 Auth 服務也發 token 給集點服務，一張「給集點用」的 token 不該拿來打訂單 API。
  4. 現在還能用嗎？token 外洩了也要在一段時間後自動失效。

RFC 7519 為這類常見需求定義了一組註冊 claim（registered claims）：名字固定、意思固定，大家寫的 token 就能互通。它們都是選用的，但用到時意思不能改；名字都只有三個字母，是為了讓 token 短一點。上面四個問題分別對應 sub（subject，代表誰）、iss（issuer，誰發的）、aud（audience，給誰用的）、exp（expiration time，何時到期）。完整的清單如下，查表用，不用背：

ississuer誰發的 token"https://auth.coffee.example"收到的 API 比對「我信任的發行者」

表裡最重要的是「誰檢查」那一欄。JWT 這個格式不會自己檢查任何東西：簽章正確只代表「這是發行者簽的、沒被改過」，至於 exp 過了沒、aud 是不是寫著自己，都要收 token 的那一方自己檢查。訂單服務漏掉 aud，給集點服務的 token 就能拿來讀訂單；漏掉 exp，外洩的 token 永遠有效。每一項漏掉的後果，第 9 課一個一個示範。

💡 實務上：前端可以讀 payload，但只拿來顯示
Vue 前端常把拿得到的 access token 解碼，看 exp 決定快到期時先換新 token（第 10 課），或用 sub 判斷畫面上現在是誰登入。這沒問題，但前端讀到的內容只能影響畫面，不能當成權限：使用者在 DevTools 改掉 token 或前端程式，就能讓畫面以為自己是店長，真正的檢查一定在後端。後端這邊常見的坑是把整串 token 印進 log 或錯誤回報系統，等於把能登入的憑證交給所有看得到 log 的人；記 sub（有 jti 的話也記）就夠查問題。Code review 看到 payload 新增欄位時，資深會先問：這個欄位前端真的需要嗎？被任何人看到可以嗎？

payload 的內容定好了。但上一節看過，任何人都能把 sub 改成店長的 ID 再編碼回去。下一步是讓訂單服務能確定：這些內容真的是 Auth 服務寫的，而且一個字都沒被改過。

怎麼讓 payload 改不了？先用 HS256 簽一次

防竄改的工具，第 2 課已經學過：HMAC。它用一把只有自己知道的秘密金鑰，對一段內容算出一個標籤；內容改一個字，標籤就完全不同，而沒有金鑰的人算不出正確的標籤。JWT 用 HMAC-SHA256 簽的方式叫 HS256，寫在 header 的 alg 欄位裡。

簽的是什麼？不是 payload 物件，而是一串叫簽章輸入（signing input）的文字：前兩段 base64url 字串用 . 接起來。這就是上一節說「簽的是文字，不是 JSON 物件」的意思：

簽章輸入 = base64url(header) + '.' + base64url(payload)    ← 這串 ASCII 文字的位元組
signature = 簽(金鑰, 簽章輸入)

header 也在簽章輸入裡，改 header 的任何欄位，簽章同樣對不上。前提是驗證端用對的方法驗；攻擊者想辦法讓驗證端換一種方法驗的手法，第 9 課會示範。所以驗證端要自己決定只接受哪個演算法，header 的 alg 和預期不同就直接拒絕，不能照著 alg 換驗法；演算法由伺服器決定，不由 token 決定，練習 2、3 都照這條寫。

現在用 RFC 7515 附錄 A.1 公布的金鑰，重算一次上一節那張範例 token 的簽章，看結果是不是跟 token 第三段一樣。程式裡的金鑰用 JSON 物件表示，這種格式叫 JWK，後面講公鑰時會詳細介紹；這裡只要知道 kty: 'oct' 表示這是一把對稱的秘密金鑰，k 是金鑰本身的 base64url。執行後比對「重算」和「原本」兩行，再看最後一行：

「重算」和「原本」完全相同，表示我們對原始的 header.payload 文字算 HMAC，結果和規格一致。最後一行是 false：把 header 和 payload 解碼成物件、再 JSON.stringify 回去，得到的文字和原本不同（少了換行和空白），拿它去算簽章一定對不上。這是自己寫驗證程式時最常犯的錯：驗證時一律從收到的 token 切出原始文字，不要重組。

HS256 的驗證方式就是：用同一把金鑰對收到的簽章輸入再算一次，交給 crypto.subtle.verify 比對。為什麼不自己算出簽章再用 === 比字串？第 2 課的時序攻擊說過：=== 遇到第一個不同的字元就回傳，回應時間會洩漏「前面猜對了幾個字元」，攻擊者能據此逐字元猜出簽章；crypto.subtle.verify 驗 HMAC 時用常數時間比較。下一節的 ES256 每次簽出來都不同，更是只能用 verify。練習 2 會親手寫出 signHS256 和 verifyHS256Signature。

金鑰本身也有要求。RFC 7518 要求 HS256 的金鑰至少和雜湊輸出一樣長，也就是 256 bits；RFC 8725 明確禁止直接拿人記得住的密碼當金鑰。原因是 HMAC 的安全性完全建立在「猜不到金鑰」上：

HS256 的金鑰要 32 bytes 以上的隨機值
網路上的範例常寫 secret、mysecret。攻擊者拿到任何一張你的 token，就能在自己的電腦上離線猜金鑰：每猜一個就算一次 HMAC、比對簽章，常見字串幾秒內就試完了。猜中之後他能簽任何 token。用第 2 課的 crypto.getRandomValues(new Uint8Array(32)) 產生，放在環境變數或 secrets 管理系統（第 23 課）。

HS256 寫起來最簡單，但回到這課的任務就會碰到問題。HMAC 的金鑰是對稱的：簽和驗用同一把，能驗證的人就能簽。訂單服務和集點服務都要驗 token，所以兩個服務都得拿到那把秘密金鑰，也就是兩個服務都能自己簽出一張「我是店長」的 token。三個服務裡任何一個被入侵、設定檔外洩，整個咖啡店的身分都能被偽造。HS256 只適合「簽的人和驗的人是同一個程式」的情況，例如只有一個後端的小網站。

咖啡店需要的是另一種簽章：Auth 服務簽得出來，訂單服務和集點服務只驗得了、簽不出來。

怎麼讓訂單服務只能驗、不能簽？非對稱簽章

HMAC 的問題出在「簽」和「驗」用同一把金鑰。非對稱密碼學（asymmetric cryptography）把這把金鑰拆成一對：私鑰（private key）由發行者自己留著，用來簽；公鑰（public key）可以公開給任何人，用來驗。兩把是一起產生的，數學上互相對應，但從公鑰算不出私鑰。用私鑰簽、公鑰驗的簽章叫數位簽章（digital signature），它證明兩件事：內容沒被改過，而且是持有私鑰的人簽的。

用咖啡店比喻：只有總店有店章（私鑰），每家分店都有一張印鑑卡（公鑰），能比對蓋在文件上的章是不是總店的，但看著印鑑卡刻不出店章。換成咖啡店的系統，就是下面這張圖：

輸出裡有三件事，對應到寫 ES256 程式時的三個規則：

  • 簽章是 64 bytes：ECDSA 的簽章由兩個數字 r 和 s 組成，P-256 各 32 bytes。Web Crypto 輸出的是 r 和 s 直接接起來（寫作 r||s），剛好就是 JWS 規定的 ES256 格式，不用轉換。所以驗證 ES256 的 token 時，簽章解碼後不是 64 bytes 就可以直接拒絕，練習 3 會用到。
  • 同一段內容每次簽出來都不一樣：ECDSA 每次簽都用一個新的隨機數。所以不能像 HMAC 那樣「重算簽章再比對字串」，一定要呼叫 verify。
  • 公鑰不能簽：CryptoKey 建立時就決定了用途，用錯會丟 InvalidAccessError。訂單服務手上只有公鑰，在程式層面就簽不出 token。

ES256 不是唯一的選擇。JWT 的 header 用 alg 寫出簽章演算法，最常見的四種如下：

alg演算法金鑰簽章大小
HS256HMAC-SHA256（第 2 課）一把共用的秘密金鑰，簽和驗都用它32 bytes
RS256RSA 簽章＋SHA-256一對金鑰：私鑰簽、公鑰驗；RFC 7518 要求至少 2048 bits256 bytes（2048 bits 金鑰）
ES256ECDSA，曲線 P-256，SHA-256一對金鑰64 bytes

RS256 也很常見，很多身分服務（例如第 13 課的 Google 登入）預設用它，缺點是金鑰和簽章都大，token 跟著變長。自己發 token 時，ES256 和 EdDSA 都是好選擇；驗別人發的 token 時，用對方公布的演算法。RS256 和 EdDSA 的細節見課末「補充與查表」。

💡 實務上：先問「誰簽、誰驗」，再選演算法
工作中很少從零寫簽章：多數團隊用 Auth0、Cognito、Supabase、Keycloak 這類身分服務簽 token，自己的後端只負責驗；就算自己簽，也是用 jose 這類成熟的函式庫，不會自己拼字串。選演算法時資深會先畫出「誰簽、誰驗」：只有一個後端自己簽自己驗，HS256 夠用；像咖啡店這樣有第二個服務或外部合作夥伴要驗，就改用 ES256 或 RS256，只把公鑰給出去。接著問私鑰放在哪裡、誰能讀到：放在程式碼庫或共用設定檔裡，前面的安全性就都不算數。

架構定下來了：Auth 服務用私鑰簽，訂單服務用公鑰驗。剩下一個實際問題：訂單服務要怎麼拿到那把公鑰？Auth 服務手上不只一把金鑰時，訂單服務又怎麼知道該用哪一把？

訂單服務怎麼拿到公鑰，又怎麼知道用哪一把？

公鑰需要一個大家都看得懂的交換格式。標準做法是 JWK（JSON Web Key），由 RFC 7517 定義：用一個 JSON 物件表示一把金鑰。上一節重算 HS256 時用過的 { kty: 'oct', k: … } 就是一個 JWK。把好幾個 JWK 放在 { "keys": [...] } 裡，叫 JWKS（JWK Set）。

Auth 服務把自己的 JWKS 放在一個公開的網址，常見的路徑是 /.well-known/jwks.json。訂單服務和集點服務去抓這個網址，就拿到了公鑰；公鑰本來就可以公開，所以這個網址不需要保護。支援 OpenID Connect 的身分服務（例如 Google）會在設定文件的 jwks_uri 欄位告訴你網址，第 13 課會用到。

下面把 ES256 的公鑰和私鑰都匯出成 JWK，比較兩者差在哪，最後組出 Auth 服務要公開的 JWKS：

EC 公鑰的 JWK 有四個主要欄位：

  • kty：金鑰種類。EC 是橢圓曲線，另外還有 RSA，以及 oct（對稱的秘密金鑰）。
  • crv：用哪條曲線，這裡是 P-256。
  • x、y：公鑰在曲線上的座標，也就是公鑰本身。

第二行輸出顯示私鑰多了一個 d，那就是秘密本身，絕對不能出現在 JWKS 裡。所以發布 JWKS 時用白名單挑出要公開的欄位，像上面的程式那樣一個一個寫出來，不要把 exportKey 的結果整個丟出去；哪天有人手滑匯出成私鑰，白名單也不會讓 d 跟著出去。JWKS 裡每把金鑰還加了三個欄位：kid（這把金鑰的名字）、alg（這把金鑰只用在哪種演算法）、use: 'sig'（用來驗簽章）。

kid 就是第二個問題的答案。JWKS 裡通常不只一把金鑰（這節最後會看到為什麼），驗證端要知道用哪一把。JWT 的 header 有一個 kid（key ID）欄位，寫著「我是用哪一把簽的」：

{ "alg": "ES256", "typ": "JWT", "kid": "2026-10" }

訂單服務收到 token，就在自己已經信任的 JWKS 裡找 kid 相同的那一把來驗。找不到就失敗，不要「每一把都試試看」：那等於讓攻擊者決定用哪把金鑰，也讓每個無效的 token 浪費好幾次驗證。還要記得 kid 是 token 裡的字，攻擊者能隨意改，它只能拿來在已知的集合裡查，不能拿去組檔案路徑或 SQL，第 9 課會示範被注入的後果。練習 3 會把這整條路串起來：Auth 服務用 ES256 簽、帶 kid，訂單服務用 JWKS 找鑰、驗證。

到這裡，訂單服務已經能自己驗證王小明的 token。但金鑰不會永遠不換：定期更換是好習慣，懷疑外洩時更是非換不可。JWKS 能放好幾把、header 用 kid 指定，正是為了讓換金鑰這件事做得到。

Auth 服務要換金鑰，怎麼不把所有人登出？

定期或在懷疑外洩時換掉簽章金鑰，叫金鑰輪替（key rotation）。難的不是產生新金鑰，而是換的那一刻，系統裡同時存在兩樣「舊的東西」：

  • 已經發出去、還沒過期的 token，是用舊私鑰簽的。
  • 訂單服務為了不每個請求都去抓 JWKS，會把它快取一段時間（例如幾分鐘到一小時），快取裡只有舊公鑰。

直覺的做法是一次換掉，兩種失敗都會發生。Auth 服務一換新私鑰就開始簽，還沒更新快取的訂單服務找不到新的 kid，剛登入的使用者突然收到 401；如果同時把舊公鑰從 JWKS 拿掉，所有人手上的舊 token 立刻驗不過，等於全站登出。

所以要分三步，讓新舊兩把在一段時間內並存：

  1. 先發布新公鑰：JWKS 同時有 k1 和 k2，簽章仍然用 k1。等所有驗證端的快取都更新，大家都認得 k2。
  2. 改用新私鑰簽：新 token 的 header 寫 kid: k2。用 k1 簽的舊 token 還在 JWKS 裡找得到公鑰，繼續有效。
  3. 舊 token 全部過期後才移除舊公鑰：access token 效期 15 分鐘，就至少等 15 分鐘（加上一點時鐘誤差）。

每一步等待的長度都對應一樣「舊的東西」：第一段等的是訂單服務的 JWKS 快取，第二段等的是舊 token 的效期。

私鑰外洩是例外。那時攻擊者手上的私鑰能簽出任何 token，舊公鑰多留一分鐘，偽造的 token 就多有效一分鐘，所以要立刻移除舊公鑰，接受所有人被登出。驗證端的函式庫通常會幫忙處理快取與「遇到不認得的 kid 就重抓 JWKS」，jose 的做法見課末「補充與查表」。

💡 實務上：輪替要寫成步驟，平常就跑過一次
金鑰輪替通常不是每天會做的事，所以最常見的失敗是「真的要換時，沒人記得怎麼換」。團隊會把三個步驟和每步要等多久寫進維運手冊，在測試環境或正式環境的離峰時段實際跑一次，確認沒有人被登出。換的當下要盯著 401 數量和「找不到 kid」的錯誤，有服務把 JWKS 寫死在設定檔、沒有去抓網址，就會在這時候出事。這類變更要先跟維運和客服說，萬一有人被登出，客服才知道怎麼回答。

到這裡，這課的任務完成了：訂單服務不用問任何人，就能確定 token 是 Auth 服務簽的、內容沒被改過，而且 Auth 服務換金鑰也不會中斷服務。但「驗得過簽章」和「這個請求可以放行」之間，還有一段距離。

JWT 解決了什麼、還沒解決什麼？

JWT 解決的是開場那個問題：每個服務自己驗簽章，不用每個請求都查中央的 session store。下面四件事是它沒有解決、卻常被誤以為解決了的，後面幾課會一一處理。

它不是加密。JWS 只簽章，第二節已經看過 payload 誰都能解開。真的要藏內容，有另一個格式 JWE（JSON Web Encryption），但大部分情況的答案是「不要把秘密放進 token」：王小明的手機號碼留在伺服器，前端需要時用 API 查。

它不是 session 的直接替代品。「JWT 不用存在伺服器」的另一面是「伺服器沒辦法讓它提早失效」。王小明按登出、改密碼、被停權，簽出去的 JWT 照樣能用到 exp。第 10 課用短效期加 refresh token 縮小這個窗口，第 11 課討論真的需要撤銷時怎麼辦。

它不是越大越好。每個請求都帶著它。payload 放了權限清單、個人資料，token 很容易長到幾 KB；放在 cookie 裡還會碰到單一 cookie 4096 bytes 的上限，超過時瀏覽器會整個忽略那個 cookie，使用者就莫名其妙地「沒登入」。

它不是「驗過簽章就安全」。簽章只回答「是誰簽的、有沒有被改」。過期了沒、是不是給訂單服務的、header 裡的演算法是不是伺服器允許的，都要另外檢查。這一課的練習只驗簽章，第 9 課把這些檢查補齊。

補充與查表

主線用不到、但選演算法、讀別人的 token 或設定驗證函式庫時會查的細節。

RS256 與 EdDSA

RS256 的金鑰大（2048 bits 起）、產生一把比 EC 金鑰慢得多（常要幾十到幾百毫秒）、簽章 256 bytes，token 也跟著變長。Ed25519（JWT 裡寫作 EdDSA）在 Chrome 的 Web Crypto 也能用，簽章同樣 64 bytes。

ECDSA 簽章的另一種編碼：DER

JWS 的 ES256 用 r||s（固定 64 bytes）。其他系統常用另一種叫 DER 的編碼（大約 70～72 bytes），第 15 課的 passkey 就會遇到。

jose 的 createRemoteJWKSet

成熟的函式庫會幫驗證端處理一部分輪替的細節，例如 jose 6.2 的 createRemoteJWKSet：依 header 的 alg 和 kid 在 JWKS 裡挑金鑰，快取預設 10 分鐘；遇到對不上的 kid 會重抓 JWKS，但距離上次成功抓取要超過冷卻時間（預設 30 秒），避免攻擊者用大量假 kid 讓你一直重抓。

練習

練習 1：寫 decodeJwt(token)：只解碼、不驗證，用來在本機除錯。規則：

  • 必須剛好三段（用 . 分開）。
  • 每一段都是沒有 = 的 base64url（只能有 A-Z a-z 0-9 - _，簽章那段也要能解碼）。
  • header 與 payload 用 UTF-8 解碼後是 JSON，中文要正確。
  • 任何一條不符合就回傳 null，不能丟出例外。解出來的值型別是 unknown，還沒驗證過，不能直接相信。

練習 2：用 HS256 簽與驗。

  • signHS256(payload, secret)：header 固定是 { alg: 'HS256', typ: 'JWT' }，回傳完整的 JWT。
  • verifyHS256Signature(token, secret)：只驗簽章（這課先不看 exp）。格式不對回 false；header 的 alg 必須是 'HS256'，否則不管簽章如何都回 false；對收到的原始「header.payload」文字用 crypto.subtle.verify 驗證。

header 解出來是 unknown：先確認它是物件、有 alg 欄位，才能讀 alg。

練習 3：咖啡店改成 Auth 服務用 ES256 簽，訂單服務用 JWKS 驗。

  • signES256(payload, privateKey, kid)：header 是 { alg: 'ES256', typ: 'JWT', kid }，用 ECDSA P-256＋SHA-256 簽。
  • verifyES256(token, jwks)：
    1. 格式要對，header 的 alg 必須是 'ES256'（演算法由你決定，不是由 token 決定）。
    2. header 要有字串 kid，在 jwks 裡找 kid 相同的那一把；找不到就失敗，不要逐一嘗試每一把金鑰。
    3. 找到的金鑰必須是 kty: 'EC'、crv: 'P-256'，否則失敗。
    4. 簽章必須剛好 64 bytes，再用 crypto.subtle.verify 驗證。

任何失敗都回 false，不能丟出例外。TypeScript 內建的 JsonWebKey 型別沒有 kid，所以題目自己定義了 PublicJwk。

練習 4：會員服務想讓前端少打一支 API，打算把顧客的手機號碼放進 JWT 的 payload。下面哪一句正確？

✓ JWS 的簽章只防竄改、不隱藏內容，不論 HS256 或 ES256 都一樣，所以 a、b 錯。d 錯，HttpOnly 只擋頁面上的 JavaScript 讀 cookie；使用者自己在 DevTools 就看得到，token 也會經過反向代理、出現在伺服器或除錯 log，任何一處拿到都能解開 payload。個資留在伺服器，前端需要時用 API 查。

練習 5：咖啡店的訂單服務和集點服務都要驗證 Auth 服務發的 token。同事說：「HS256 比較快，全部用 HS256，把秘密金鑰放進三個服務的環境變數就好。」主要的問題是什麼？

✓ HMAC 是對稱的：驗證的人和簽的人用同一把金鑰。金鑰分散在三個服務，攻擊面就變成三倍，而且任何一個被打穿都能簽出「我是店長」。ES256 讓只有 Auth 服務持有私鑰，其他服務只拿公開的公鑰。a 錯，HMAC 的確比較快，但差的是微秒，不是理由。c、d 錯，HS256 的簽章只有 32 bytes，放哪裡都一樣。

練習 6：簽 token 的程式寫了 exp: Date.now() + 15 * 60 * 1000。會發生什麼事？

✓ NumericDate 的單位是秒。Date.now() 是毫秒，數字大了 1000 倍，用秒去讀是好幾萬年後。這種錯誤不會報錯，看起來一切正常，只是 token 永遠不會過期，外洩後也一直有效。b 是反過來的錯誤（把秒當毫秒比較時才會發生）。c 錯，規格沒有這種自動判斷，函式庫照秒去讀。正確寫法是 Math.floor(Date.now() / 1000) + 15 * 60。

練習 7：Auth 服務要換 ES256 的簽章金鑰，驗證端會把 JWKS 快取 10 分鐘。下面哪個順序對？

✓ 驗證端只信任它快取裡的公鑰。a 和 b 都會讓還沒更新快取的服務看到不認得的 kid，使用者拿新 token 卻收到 401；a 還會讓手上的舊 token 立刻失效。d 是私鑰外洩時才不得不做的事，平常輪替不該把所有人登出。c 的兩段等待分別對應「JWKS 快取時間」與「token 的最長效期」。

常見錯誤

  • 以為 JWT 有加密：payload 是 base64url，任何人都能解。不要放密碼、個資、內部資訊。
  • 只解碼就相信 payload：解碼不需要金鑰，攻擊者能改成任何內容再編碼回去。驗過簽章之後才能用 sub。
  • 用 secret、mysecret 當 HS256 金鑰：拿到一張 token 就能離線猜出金鑰。用 32 bytes 以上的 CSPRNG 隨機值。
  • exp 用毫秒：NumericDate 是秒，用 Math.floor(Date.now() / 1000)。
  • 驗證時把 header、payload 重新 JSON.stringify 再算簽章：簽的是收到的原始文字，重新序列化後位元組不同。用 lastIndexOf('.') 切出原始的 header.payload。
  • 重算簽章後用 === 比對：有時序攻擊的風險，而且 ECDSA 每次簽都不同，根本比不起來。用 crypto.subtle.verify。
  • 照 header 的 alg 決定怎麼驗：header 是攻擊者能改的。演算法由伺服器設定決定，每把金鑰只配一種演算法（第 9 課）。
  • 每個服務都持有 HS256 的秘密金鑰：能驗就能簽。多個服務要驗證時用 ES256，只有 Auth 服務持有私鑰。
  • kid 找不到就逐一試每一把金鑰，或拿 kid 組檔案路徑、SQL：kid 是攻擊者的輸入，只能在已信任的集合裡查（第 9 課）。
  • JWKS 直接丟出 exportKey 的結果：私鑰的 JWK 有 d。用白名單挑 kty、crv、x、y、kid、alg、use。
  • 輪替時立刻移除舊公鑰或立刻用新私鑰簽：前者讓還沒過期的 token 全部失效，後者讓還沒更新快取的服務不認得新 kid。
  • 把正式環境的 token 貼到線上的 JWT 解碼網站：bearer token 誰拿到誰就能用，在本機解碼。

小結

  • 拆成多個服務後，每個請求都問 session store 會變成瓶頸。不透明 token 要問伺服器才知道代表誰，能隨時撤銷；自包含 token 自己寫著內容、驗簽章就能信，但很難提早失效。兩者通常都是 bearer token，誰拿到誰能用。
  • JWT 是三段 base64url 用 . 串起來：header、payload、signature。payload 只是編碼，任何人都看得到；解碼不等於驗證。
  • payload 用註冊 claim 回答訂單服務的問題：sub 代表誰、iss 誰發的、aud 給誰用、exp 何時到期（另有 nbf、iat、jti）。時間是秒；每一項都要收 token 的一方自己檢查。
  • 簽章簽的是原始的「header.payload」文字，驗證時用收到的那串，並用 crypto.subtle.verify。
  • HS256 對稱：能驗就能簽，只適合簽和驗是同一方；金鑰至少 256 bits 隨機值。ES256 非對稱：私鑰簽、公鑰驗，簽章 64 bytes（r||s），適合多個服務驗證。
  • 公鑰用 JWK 表示、放在 JWKS 公開，只挑白名單欄位；header 的 kid 只用來在已信任的集合裡選鑰。輪替：先發布新公鑰 → 等快取更新再用新私鑰簽 → 舊 token 都過期後才移除舊公鑰。
  • JWT 不是加密、不是 session 的直接替代品、不是越大越好，驗過簽章也還不夠：效期、對象、演算法都要另外檢查。
