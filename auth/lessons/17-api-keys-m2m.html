階段 4：更多登入方式：第三方、多因素與機器 · 第 17 課

機器對機器：API key、client credentials 與 webhook 簽章

王小明在外送 App 點了一杯拿鐵。從他按下「送出」，到這杯拿鐵變成他的會員點數、再變成當晚的營收報表，中間要經過三段呼叫，每一段都是伺服器呼叫伺服器：

  1. 外送平台的伺服器呼叫咖啡店的 POST /orders，替王小明建單。
  2. 王小明付款後，咖啡店的訂單系統把「新訂單」事件 POST 到會員系統，讓會員系統替他加點數。
  3. 半夜，咖啡店的報表服務向訂單服務要前一天的營收。

前面十幾課的登入，螢幕前都有一個人：他輸入密碼、按 passkey、點同意。這三段呼叫沒有人可以輸入密碼，也沒有瀏覽器可以放 cookie。可是每一段的接收方都必須知道「呼叫我的是誰、它能做什麼」：任何人都能對 POST /orders 送請求，任何人也都能對會員系統的網址 POST 一個假的「王小明買了 100 杯拿鐵」。

這種沒有人在螢幕前操作、服務與服務之間的認證，叫機器對機器（machine-to-machine，M2M）認證。這一課的任務：讓這杯拿鐵經過的三段呼叫都能證明「我是誰」，而且任何一把秘密外洩時，損害有上限、換得掉，外送單也不會因為換 key 而斷線。

這課的路線：
  1. 三段呼叫各用什麼證明身分：服務帳號是什麼，API key、webhook 簽章、client credentials 各對應哪一段，mTLS 放在哪裡（開場問題的最小答案）。
  2. 第一段，外送平台的 API key：格式怎麼設計才能讓外洩的 key 被找到，資料庫只存什麼，每個請求怎麼驗。
  3. key 要換、或懷疑外洩時，怎麼不讓外送單斷線；為什麼 key 不能放進 Vue 前台。
  4. 第二段，通知會員系統的 webhook：怎麼簽章讓對方確認是咖啡店送的，怎麼擋重放與重複加點數，secret 怎麼換。
  5. 第三段，內部的報表服務：都在內網為什麼還要認證，怎麼用 client credentials 換短效 token，不必每個服務發一把長期 key。
這課會用到：
  • 第 2 課的 SHA-256、HMAC 與熵：SHA-256 把資料變成不能反推的雜湊；HMAC 用一把共用的秘密金鑰算出簽章，沒有金鑰算不出來；熵是隨機值有多難猜，用 bits 計；CSPRNG（密碼學安全的亂數產生器，例如瀏覽器與 Node 都有的 crypto.getRandomValues）產生的值無法從先前的輸出預測，Math.random 則不保證這一點，不能用來產生秘密。
  • 第 12 課的 OAuth 角色：client（要拿 token 的程式）、授權伺服器（發 token）、資源伺服器（收 token、提供 API），以及換 token 的 token 端點。
  • 第 9 課的 JWT 驗證：驗完簽章還要檢查 iss（誰發的）、aud（發給誰）、exp（何時過期）。

三段呼叫，各用什麼證明「我是誰」？

人登入時，系統認的是帳號：一筆代表某個人的紀錄，綁著他的密碼與權限。機器也需要這樣一筆紀錄，叫服務帳號（service account）：代表一個程式而不是一個人的帳號。外送平台的伺服器是一個服務帳號，咖啡店的報表服務也是一個。

為什麼不乾脆借某位員工的帳號給機器用？員工會離職、會改密碼、會被要求開 MFA，而機器不會輸入驗證碼；員工的權限通常也比機器需要的大得多。服務帳號的權限只開它需要的部分：外送平台的帳號能建單、查單，不能退款，也不能匯出顧客資料。這種「這個身分被允許做哪些事」的清單叫 scope，每一項寫成像 orders:create 這樣的字串。

有了帳號，還要決定機器每次呼叫時，拿什麼證明「我就是這個帳號」。三段呼叫的情況不同，用的做法也不同：

呼叫做法怎麼運作適合代價
第一段：外送平台呼叫我們API key發一把長期的秘密字串，每個請求放在標頭裡給外部合作夥伴、開發者用的公開 API長期有效，外洩就一直能用到被撤銷；要自己做輪替、scope、到期
第二段：我們通知會員系統webhook 簽章方向相反：我們送出時用共用的 secret 算 HMAC，對方驗證我們主動通知別人接收方要正確實作驗證、防重放
第三段：報表服務呼叫訂單服務OAuth client credentials服務用自己的身分向授權伺服器換短效 access token，再拿 token 呼叫 API已經有授權伺服器、很多服務要互相呼叫多一台授權伺服器、多一次請求；token 要快取

第二段跟另外兩段方向相反。第一、三段是別人呼叫我們，我們是接收方，負責驗證對方；第二段是我們呼叫會員系統，換成我們要讓對方能驗證我們。所以 webhook 不是「會員系統發一把 key 給咖啡店」，而是咖啡店在每個送出的請求上用 secret 算出簽章，讓會員系統檢查。

表裡沒有列出的第四種做法是 mTLS（雙向 TLS）。一般 HTTPS 連線只有伺服器出示 TLS 憑證，證明「我是這個網域」；TLS 憑證是由憑證機構簽發、把公鑰和身分綁在一起的檔案（這裡的憑證是 certificate，跟第 1 課的憑證 credential 不同，只是中文同名）。mTLS 讓客戶端也出示自己的 TLS 憑證，伺服器驗證通過才接受連線。它適合自己管的內部基礎設施、金融機構之間，代價是要管憑證的簽發與更新，除錯也比較難。這一課的主線不實作它，第三段會再說明它和 client credentials 怎麼搭配。

這幾種做法不互斥：咖啡店對外送平台發 API key、對會員系統送有簽章的 webhook、內部服務用 client credentials，三種同時存在。開場的問題到這裡有了最小答案，接下來照拿鐵經過的順序一段一段做。第一段最直覺的做法，是產生一串亂數當 key 交給外送平台。這樣做在平常沒問題，出事的時候卻會沒人發現。

第一段：一串亂數當 key，外洩了為什麼沒人發現？

API key 是發給合作夥伴或服務的長期金鑰：咖啡店產生一串秘密字串交給外送平台，外送平台每次呼叫 POST /orders 都帶著它，咖啡店看到這串字就知道是外送平台。最簡單的做法是產生一串亂數就交出去。

問題出在外洩之後。key 外洩多半不是被駭，而是自己人不小心：工程師把 key 貼進 GitHub、寫進 log、截圖放進客服單。外洩擋不完，能做的是讓外洩的 key 盡快被發現。負責發現的是 secret scanning：自動掃描程式碼、log、聊天訊息，找出外洩金鑰的工具。

可是掃描工具要怎麼從大量程式碼裡認出「這是一把 key」？一串沒有特徵的亂數，跟 commit hash、檔案雜湊、隨機產生的 ID 長得差不多。掃描工具認不出它是 key，就沒人發現，這把 key 會一直有效，攻擊者可以一直用下去。

GitHub 為了讓掃描工具認得自家的 token，把 token 格式設計成有特徵的樣子（改格式的時間見課末「補充與查表」）。前兩個特徵：

  • 可辨識的前綴：ghp_ 是個人存取 token、gho_ 是 OAuth access token 等。看到前綴就知道是誰家、哪一種 key，該通知誰。
  • 底線分隔：key 的隨機部分是 base62，本身不含底線（標準 base64 也沒有底線，但 JWT 用的 base64url 有），隨機字串剛好長得像 key 的機會變小；在編輯器裡雙擊也會選到整串。

第三個特徵是最後 6 個字元的檢查碼（checksum）。檢查碼是從內容算出的短碼，用來偵測打錯或被截斷：內容改了一個字，算出來的檢查碼就不同。GitHub 用的是 CRC32，一種常見的檢查碼演算法，輸出 32 bits 的整數，zip、PNG 都用它。做法是對前面的內容算 CRC32，轉成 base62、左邊補 0 到 6 個字元，接在最後。

CRC32 不是密碼學工具，任何人都算得出來，所以它不負責保密。它的用途是讓掃描工具不必查資料庫就能排除假的 key：一串字符合前綴，可能只是文件裡的範例；重算檢查碼對得上，才幾乎一定是真的 key。符合前綴但檢查碼對不上的字串，一定不是真的 key。前綴讓掃描工具找得到候選，檢查碼讓它丟掉誤報。

key 做好了。交給外送平台之前，咖啡店自己得留一份紀錄，之後每個請求進來才能比對。最直接的做法是把 key 原封不動存進資料庫，但那樣資料庫一外洩，所有合作夥伴的 key 就一起外洩了。

伺服器要留什麼，才能驗 key、外洩也不能用？

跟 session token 一樣（第 4 課），資料庫只存 key 的 SHA-256 雜湊。驗證時，伺服器把請求帶來的 key 再算一次 SHA-256，拿結果去資料庫找。資料庫外洩時，攻擊者拿到的只是雜湊值：雜湊反推不回 key，而把雜湊值本身當成 key 送來，伺服器會再雜湊一次，找不到任何一筆。所以雜湊值不能直接拿來呼叫 API。

為什麼密碼要用 Argon2id 這類慢雜湊，key 用 SHA-256 就夠？第 2 課說過，雜湊不能反推、但可以猜。密碼是人想的，可能性少，攻擊者照常見密碼清單一個一個試，慢雜湊是為了讓每一次試都很貴（第 3 課）。key 是 CSPRNG 產生的 178 bits，就算每秒試一兆次，試完一半也要遠超過宇宙年齡的時間。猜不到的東西不需要讓「猜」變慢，而 API 每個請求都要驗證，用慢雜湊反而讓伺服器自己變慢。

只存雜湊，伺服器自己也看不到原始的 key，所以 key 只在建立時顯示一次：後台顯示「請現在複製，關掉之後就看不到了」，忘了就建一把新的。使用者要辨認「這是哪一把」，就另外存一段前綴給他看。

紀錄裡還要記這把 key 能做什麼，也就是開頭說過的 scope：一把 key 或一張 token 被允許做的事，例如 orders:create。外送平台的 key 只給 orders:create 和 orders:read，key 外洩時攻擊者也不能退款或匯出顧客資料。沒有 scope 的 key 等於全部權限。

把這些需求放在一起，一把 key 的紀錄長這樣：

欄位用途
id主鍵
owner_id屬於哪個服務帳號或合作夥伴
prefixkey 的前 14 個字元，例如 cafe_live_7Gx2，後台列表顯示用。14 個字元裡只有 4 個隨機字元，洩漏它不會讓 key 變好猜

紀錄存好了。外送平台尖峰時每秒有幾百個請求帶著 key 進來，每一個都要拿這份紀錄驗證；驗的順序，決定了它快不快、會不會被亂猜的 key 拖垮資料庫。

每秒幾百個請求，每個怎麼驗？

原則是便宜的檢查放前面，花資料庫的檢查放後面。亂猜或打錯的 key 越早被擋，資料庫越不會被它們拖累：

  1. 格式：符合 cafe_(live|test)_ 加 36 個 base62 字元，不符合直接拒絕。
  2. 檢查碼：對不上直接拒絕。亂猜的 key、打錯的 key 在這裡就擋掉，不會打到資料庫。這是上一節的檢查碼第二個用途：掃描工具用它排除誤報，伺服器用它保護資料庫。
  3. 雜湊查表：SHA-256 之後用 key_hash 查。用雜湊值查表，不是逐筆比對字串，也就沒有第 2 課的時序問題：攻擊者無法控制雜湊值的前幾個字元。
  4. 狀態：已撤銷、已過期、scope 不夠，各自拒絕。

驗證通過後要更新 last_used_at，但不要每個請求都寫資料庫：外送平台尖峰時每秒幾百個請求，每個都 UPDATE 同一列會變成熱點。常見做法是在記憶體記下「這把 key 用過了」，每分鐘批次寫一次；精確到分鐘就夠判斷 key 還有沒有人用。

最後要跟外送平台約定 key 放在請求的哪裡：用標頭（Authorization: Bearer cafe_live_… 或自訂的 X-API-Key），不要放在網址的 query。網址會被寫進伺服器的存取 log、Proxy 的 log、瀏覽器歷史紀錄，等於把 key 抄到一堆你管不到的地方，前面花力氣讓資料庫只存雜湊也就白費了。

💡 實務上：API key 管理頁是後台的標準配備
對外開放 API 的產品幾乎都有一頁「API 金鑰」：建立、命名、看前綴與最後使用時間、撤銷。key 要綁在服務帳號或合作夥伴上，不要綁在某個員工的個人帳號，否則他離職、帳號停用，外送平台的單就全斷了。建立和撤銷 key 都要寫進稽核紀錄（audit log），也就是記錄「誰、在什麼時間、做了什麼」的紀錄（第 25 課專門講）。資深工程師會先問：誰有權限建 key、能給哪些 scope、多久沒用要提醒。另外檢查 log 設定有沒有遮掉 Authorization 與 X-API-Key 標頭，key 最常外洩的地方就是自己的 log。

換 key 或懷疑外洩時，怎麼不讓外送單斷線？

驗證寫好之後，外送平台可以穩定下單，但這把 key 遲早要換：員工離職、合作夥伴換系統、定期更換，或者懷疑外洩了。如果一個合作夥伴同一時間只能有一把有效的 key，換 key 的流程就是「撤銷舊的 → 給新的 → 對方部署新的」，中間那段時間外送單全部失敗。結果是大家都不敢換，key 一用好幾年。

解法是允許輪替的重疊期：新舊 key 同時有效的一段時間。資料表的 revoked_at 可以設成未來的時間，就是為了這件事。

  1. 建立新 key，交給合作夥伴。舊 key 照常可用。
  2. 合作夥伴部署新 key。你從 last_used_at 看到新 key 開始被使用、舊 key 不再被使用。
  3. 撤銷舊 key。也可以在第 1 步就把舊 key 的 revoked_at 設成 7 天後，到時自動失效。

計畫中的輪替可以慢慢來，懷疑外洩時順序相反：先撤銷，再調查。多等一分鐘，攻擊者就多用一分鐘。調查靠的是上一節提到的稽核紀錄，加上 last_used_at。

  1. 立刻撤銷那把 key（revoked_at 設成現在），同時發一把新的給合作夥伴。服務中斷一小段時間，比資料被拿走好。
  2. 查 last_used_at 和稽核紀錄：外洩之後這把 key 做了什麼、從哪些 IP 來。
  3. 通知對方，找出外洩的來源（git 歷史、log、CI 設定），清掉，否則新 key 一樣會外洩。
💡 實務上：外洩應變要在出事前準備好
半夜收到 secret scanning 的通知時，沒人有空現想流程。上線前先確認三件事：撤銷一把 key 是後台按一個鈕，不是請 DBA 手動改資料庫；有一份寫好的應變步驟（誰負責、通知哪個合作夥伴窗口）；repo 開了 secret scanning，在 push 時就擋下含 key 的 commit。團隊內傳 key 也別貼在聊天群組或 .env 範例檔，改用密碼管理工具或雲端的 secret manager。

Vue 前台也要用 key：放進 .env 為什麼藏不住？

上一節的第 3 步要清掉外洩的來源。對前端工程師來說，最容易親手造成外洩的來源是前端程式碼本身。咖啡店官網要顯示門市地圖，最直覺的寫法是把地圖服務的 key 放在 .env：

VITE_MAP_API_KEY=sk_live_abc123

Vite 只把 VITE_ 開頭的變數提供給前端程式碼，打包時會把 import.meta.env.VITE_MAP_API_KEY 直接替換成字串寫進 JS 檔。任何人打開網站、在 DevTools 的 Sources 裡搜尋 sk_live 就找得到。Vite 文件（v8）明說：VITE_ 變數不應該放 API key 這類敏感資訊，秘密要放在後端或 serverless 函式。

這裡的迷思是把「環境變數」當成「秘密」。環境變數只代表值不寫在程式碼裡，不代表它是秘密；決定它是不是秘密的，是它最後跑在誰的電腦上。前端程式碼跑在每個訪客的瀏覽器裡，所以放進去的東西每個訪客都拿得到。手機 App 也一樣，安裝檔可以被解開、反組譯。

前端需要呼叫要 key 的第三方服務時，走後端代理：Vue 呼叫自己的 GET /api/map-tiles，後端用存在伺服器環境變數（Node 課第 2 課）裡的 key 呼叫地圖服務。後端還能順便加上限流與快取，key 外洩的風險只剩伺服器。有些服務提供專門給前端用的公開 key（限制來源網域、只能讀），那是服務商刻意設計成公開的，跟秘密 key 是兩回事，用之前看清楚文件。

到這裡，第一段完成了：外送平台帶著有前綴、有檢查碼的 key 呼叫咖啡店，咖啡店只存雜湊、依序驗證、換 key 不斷線。接著是第二段：王小明付款後，訂單系統要通知會員系統加點數。這次方向反過來，是咖啡店呼叫別人，要證明身分的換成了咖啡店。

第二段：通知會員系統加點數，對方怎麼確認是咖啡店送的？

webhook 是事件發生時，由我方主動 POST 到對方事先登記的網址。咖啡店有新訂單時，POST 到會員系統的 https://members.example.com/hooks/cafe，會員系統收到就替顧客加點數。這個網址是公開的，任何人都能 POST 一個假的「王小明買了 100 杯拿鐵」過去，所以接收方要能驗證三件事：

  • 來源與完整性：是咖啡店送的、內容沒被改過 → HMAC 簽章（第 2 課）。
  • 新鮮：不是攻擊者錄下一個真的請求、之後重送 → 時間戳。
  • 只處理一次：網路重試讓同一個事件送達兩次 → 事件 ID。

這一節先處理第一件：簽章。咖啡店和會員系統事先共用一把 secret，咖啡店送出時對內容算 HMAC，會員系統用同一把 secret 再算一次，對得上就代表內容出自持有 secret 的咖啡店、沒被改過。

簽什麼、簽章放在哪個標頭、怎麼編碼，每家服務商以前各做一套，接收方每串一家就要讀一份文件、寫一份驗證程式。Standard Webhooks 是一份公開的 webhook 規格，把這些細節統一下來；咖啡店照它設計，會員系統就可以直接用現成的函式庫驗證。規格定義了三個標頭：

標頭內容
webhook-id這個事件的唯一 ID，例如 msg_p5jXN8AQM9LWM0D4loKWxJek；重試時不變
webhook-timestamp送出時間，Unix 秒數
webhook-signaturev1, 加上 base64 的 HMAC-SHA256；可以有好幾個，用空白分隔

簽章怎麼算，規格也規定了：

  • 簽的內容是 id.timestamp.payload：三樣用 . 接起來。把 ID 和時間戳也簽進去，攻擊者就不能拿一個舊的簽章、換上新的時間戳。
  • secret 是 24～64 bytes 的隨機位元組，base64 之後加上 whsec_ 前綴交給對方。算 HMAC 時要先去掉前綴、base64 解碼，用解出來的位元組當金鑰，不是把整個字串當金鑰。
  • v1 是 HMAC-SHA256；規格另外定義了 v1a（Ed25519 公鑰簽章），接收方只存公鑰。看不懂的版本就跳過。

下面這格用規格的範例值算出簽章，再模擬一個常見的接收方寫法：先把 body 解析成物件，再轉回字串來驗。執行後比較最後兩行簽章。

第二個簽章對不上：簽章簽的是原始位元組。JSON.parse 再 JSON.stringify 會改掉空白、鍵的順序、數字的寫法（1.0 變 1），內容意思一樣，位元組不同。接收方必須拿到框架解析之前的原始 body 來驗證，NestJS 要開 rawBody: true（NestJS 課第 22 課）。驗證通過之後才解析 JSON。

簽章驗過，代表這個請求出自咖啡店、內容沒被改過。開頭列的三件事解決了第一件，會員系統現在就可以放心加點數了嗎？

簽章驗過了，為什麼還會重複加點數？

簽章只證明「這是咖啡店某個時候送的」，不證明「是剛剛送的」。攻擊者在中間（例如一台被入侵的 Proxy）錄下一個合法的 webhook，明天重送，簽章照樣通過，會員系統就再加一次點數。這叫重放攻擊（replay attack）。

不需要攻擊者也會重複：送出方沒收到回應就會重送，網路慢一點，同一個事件就可能到兩次。所以開頭列的第二、三件事都要做，兩道防線：

  • 時間戳容忍（timestamp tolerance）：只接受 webhook-timestamp 和現在相差一定範圍內的請求。Standard Webhooks 的 JavaScript 參考實作用 5 分鐘，太舊和太新（在未來）都拒絕。時間戳在簽章範圍內，攻擊者改不了。
  • 用 webhook-id 去重：處理過的 ID 記下來（例如 Redis，保存時間比容忍範圍長），同一個 ID 第二次來就直接回 200、不再處理。這也解決了正常的重試。webhook-id 在這裡就是冪等鍵（idempotency key）：讓同一個請求處理多次也只生效一次的識別碼（系統設計課第 9 課詳談）。

時間戳把重放的窗口縮到幾分鐘，webhook-id 把窗口內的重送也擋掉，兩道缺一不可。送出方這一端要做的重試、逾時與防 SSRF，見課末「補充與查表」。

💡 實務上：接 webhook 時先回 200，再慢慢處理
串金流、物流、LINE 這類服務時，你多半是接收方（NestJS 課第 22 課做過）。常見做法是驗完簽章、檢查時間戳，就把事件寫進資料庫或佇列並立刻回 200，加點數、寄信交給背景工作處理；在 handler 裡做太久，對方逾時就會重送，反而製造重複事件。去重最可靠的是在資料表對事件 ID 加 UNIQUE，不要只靠程式先查再寫。保留原始 body 也很有用：客服回報「點數沒加」時，查得到對方到底送了什麼。本機開發時，對方連不到你的 localhost，要用 ngrok 這類通道工具開一個臨時的公開網址，把 webhook 轉到自己電腦上測。

webhook 的 secret 要換時，怎麼不讓驗證全部失敗？

會員系統的接收端寫好後，還剩一件事：webhook 的 secret 跟 API key 一樣要能換。麻煩在於 secret 同時存在兩邊。咖啡店某一刻改用新 secret 簽章，會員系統如果還在用舊的，從那一刻起每個 webhook 都驗不過；兩家公司不可能在同一秒一起切換。

Standard Webhooks 的解法是允許 webhook-signature 帶多個簽章，用空白分隔：輪替期間，送出方用新舊兩把 secret 各簽一次，

webhook-signature: v1,新secret的簽章 v1,舊secret的簽章

接收方不論目前設定的是新的還是舊的 secret，都有一個簽章對得上。接收方的程式也要支援「設定兩把 secret、任一把通過即可」，這樣接收方先換、送出方後換也沒問題。只看第一個簽章的實作，輪替一開始就會全部失敗。這跟 API key 的重疊期是同一個想法：新舊秘密並存一段時間，兩邊各自換完再拿掉舊的。

第二段完成。最後是第三段：半夜，報表服務向訂單服務要前一天的營收。跟前兩段不同，這次呼叫的雙方都是咖啡店自己的程式，而且都在公司內網裡。

第三段：報表服務和訂單服務都在內網，還要認證嗎？

常見的想法是：「訂單服務只在內網，外面連不到，報表服務呼叫它不用認證。」問題是內網裡的東西比你以為的多：一台被入侵的伺服器或容器、一個設定錯誤對外開放的 port、一個帳號還沒停用、能從外面連進公司內網的離職員工，還有一個有 SSRF 漏洞的服務。SSRF（伺服器端請求偽造）是攻擊者讓你的伺服器替他去連某個網址，借你的伺服器進到內網，第 22 課詳講。只要攻擊者進到內網任何一個點，所有「內網就信任」的服務都敞開。

零信任（zero trust）的基本概念：不因為請求來自內網就信任，每個呼叫都要認證、都要檢查權限。具體做法就是這一課的工具：服務之間用 client credentials 的短效 token 或 mTLS，每個服務只拿到它需要的 scope。

所以報表服務呼叫訂單服務也要認證。最直接的想法是沿用第一段的 API key：給報表服務發一把。可是咖啡店內部有訂單、報表、會員、庫存幾個服務，互相呼叫起來，每一對都要發 key、存雜湊、排輪替，而且每把都是長期有效的秘密，散落在每個服務的設定裡。服務一多，這套就管不動了。

內部服務一多，怎麼不必每個都發一把長期 key？

咖啡店已經有一台授權伺服器（第 12 課的角色），而 OAuth 有專門給機器用的流程：client credentials grant。服務用自己的 client_id 和認證方式，直接向授權伺服器的 token 端點換 access token，再拿 token 呼叫 API。跟第 12 課的授權碼流程比，這裡沒有使用者、沒有轉址、沒有授權碼，因為要證明身分的就是服務自己。

第 ① 步的請求（RFC 6749 §4.4）：

POST /oauth/token
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&scope=orders:read

好處是長期的秘密只送到授權伺服器一個地方；訂單 API 只看到 10 分鐘就過期的 access token，外洩的損害有時間上限。這正是上一節的問題的解法：每個服務只需要一個身分，不必對每個要呼叫的服務各拿一把 key。

token 要限定 aud（只能用在訂單 API），scope 只給這個服務需要的。拿到 token 的 API 照第 9 課完整驗證，不能因為「是內部服務」就省略，理由就是上一節的零信任。RFC 6749 規定這個流程不應該發 refresh token：服務隨時可以用自己的身分再換一張，不需要續期。

授權伺服器這一端，驗證 client 的方式跟第一段驗 API key 很像：

  • client secret 只存雜湊：secret 是授權伺服器產生的高熵亂數，SHA-256 就夠，理由跟 API key 相同。
  • 不存在的 client 和錯的 secret 回同一個錯誤（invalid_client），否則攻擊者能試出哪些 client_id 存在，這是第 16 課帳號列舉的機器版本。
  • scope 只能是允許清單的子集：要求的 scope 只要有一個不在清單裡，整個請求就回 invalid_scope，不能「有一個對就給」。沒有指定 scope 時，給這個 client 預設的範圍（練習裡是全部允許的 scope）。

client secret 還有一個弱點：它是共用的秘密，授權伺服器和服務都知道它，每次換 token 都要傳過去。OAuth 的安全最佳實務建議改用非對稱的 client 認證，伺服器只存公鑰：private_key_jwt 讓服務用自己的私鑰簽一個短效 JWT 代替 secret；開頭提過的 mTLS 則用 TLS 憑證證明 client 身分。client secret 最容易上手，另外兩種更安全但要管金鑰或憑證，兩者的細節與取捨見課末「補充與查表」。

到這裡，王小明那杯拿鐵經過的三段呼叫都有了身分證明：外送平台帶 API key、咖啡店對會員系統簽 webhook、報表服務用 client credentials 換短效 token。還有一種情況這三段沒有涵蓋：服務要代表某個使用者往下呼叫另一個服務，標準做法 token exchange 也放在課末。

💡 實務上：先看自己有沒有授權伺服器
只有一個單體後端、加上一兩個排程工作的小團隊，為了 client credentials 自架授權伺服器多半不划算，一把有 scope 的 API key 就夠了。服務變多、已經在用 Keycloak、Auth0 這類身分平台時，client credentials 幾乎不用額外成本。最常見的坑是每個請求都去換一次 token，把授權伺服器打垮：token 要快取到快過期前再換。code review 時也注意有沒有人為了方便給服務「全部 scope」。

補充與查表

主線用不到、但設計 key 格式、選 client 認證方式、實作 webhook 送出端時會查的細節。

GitHub 的 token 格式

GitHub 在 2021 年 4 月改了自己的 token 格式（2023 年 5 月更新說明），讓 secret scanning 好認：可辨識的前綴（ghp_、gho_ 等）、底線分隔、最後 6 個字元是 CRC32 檢查碼。GitHub 預估光靠前綴就能把 secret scanning 的誤報率降到 0.5%，加上檢查碼則幾乎沒有誤報。

比 client secret 更好的認證方式

client secret 是共用的秘密：授權伺服器和服務都知道它，它還要在每次換 token 時傳過去。RFC 9700（OAuth 安全最佳實務，2025 年 1 月）建議改用非對稱的 client 認證，伺服器只存公鑰：

  • private_key_jwt（RFC 7523）：服務用自己的私鑰簽一個短效 JWT（iss 與 sub 是 client_id、aud 是 token 端點、帶 jti 和 exp），放在 client_assertion 參數送出。授權伺服器用登記的公鑰驗證（第 8 課的 ES256）。私鑰從不離開服務，授權伺服器外洩也沒有 secret 可偷。
  • mTLS（RFC 8705）：先認識 TLS 憑證（certificate）：由憑證機構簽發、把公鑰和網域（或客戶端身分）綁在一起的檔案。它跟第 1 課的「憑證（credential）」是不同的東西，只是中文同名（部署課第 5 課詳講）。一般 HTTPS 只有伺服器出示 TLS 憑證；mTLS（雙向 TLS）連客戶端也要出示，伺服器驗證通過才接受連線。RFC 8705 還能把 access token 綁定在客戶端的 TLS 憑證上，token 被偷了，沒有對應的私鑰也用不了。

取捨：client secret 最容易上手；private_key_jwt 要管金鑰對，但不需要改網路設定；mTLS 最強，但憑證的簽發、更新、撤銷要一整套流程，通常是有專門平台團隊管理憑證的組織才用。

webhook 送出方的其他責任

失敗要用指數退避（每次重試的間隔加倍，系統設計課第 8 課）重試好幾天、逾時設 15～30 秒、payload 盡量小（規格建議通常小於 20 KB），細節在系統設計課第 16 課。送出 webhook 等於讓你的伺服器去連一個別人給的網址，還要防 SSRF（伺服器端請求偽造：攻擊者登記一個內網網址，讓你的伺服器替他去連），那是第 22 課的主題。

代表使用者往下呼叫：token exchange

會員服務收到使用者的請求，要代表這個使用者呼叫訂單服務。直接把使用者的 access token 往下傳，那張 token 的 aud 是會員服務，訂單服務照第 9 課應該拒絕；改成用服務自己的 client credentials，又會失去「是哪個使用者」的資訊，訂單服務只能信任會員服務說的 user id。正式的做法是 token exchange（RFC 8693）：會員服務拿使用者的 token 向授權伺服器換一張新的，aud 是訂單服務、身分仍是那個使用者、scope 更小。這裡只需要知道有這個標準；第一次遇到時再查規格。

練習

練習 1：產生咖啡店的 API key。起始程式已經有 crc32、toBase62、sha256Hex，完成三個函式：

  • randomBase62(length)：用 crypto.getRandomValues 產生指定長度的 base62 字串。注意 256 不是 62 的倍數，直接 % 62 會讓前幾個字元出現得比較多：丟掉 248 以上的位元組（248 = 62 × 4）再取餘數。
  • createApiKey(env)：key 是 cafe_${env}_ 加 30 個隨機字元，再接 6 個字元的檢查碼：對前面整段（含前綴）算 CRC32，轉 base62，左邊補 0 到 6 個字元。回傳 { key, record }，record 只有 prefix（key 的前 14 個字元）和 keyHash（key 的 SHA-256 hex），不能有原始的 key。
  • hasValidChecksum(key)：格式不對或檢查碼對不上就回傳 false，不會丟錯。

練習 2：寫 verifyApiKey(key, requiredScope, records, now)。records 以 keyHash 為鍵；now、expiresAt、revokedAt 都是毫秒，null 代表沒設定。依序檢查，回傳第一個失敗的原因：

  1. 格式不符 → malformed；檢查碼不對 → bad_checksum。這兩步不能查表。
  2. 用 SHA-256 查表，找不到 → unknown。
  3. revokedAt 到了（revokedAt <= now）→ revoked；設在未來代表輪替中，還能用。
  4. expiresAt <= now → expired。
  5. scopes 沒有 requiredScope → insufficient_scope。

練習 3：依 Standard Webhooks 寫送出與接收兩端。起始程式有 base64 與位元組互轉的函式。

  • signWebhook(secret, msg)：secret 是 whsec_ 加 base64，先去掉前綴再解碼成金鑰；對 ${id}.${timestamp}.${payload} 算 HMAC-SHA256，回傳 v1,<base64>。
  • verifyWebhook(headers, rawBody, secrets, nowSeconds, toleranceSeconds = 300)：
    • webhook-id、webhook-timestamp、webhook-signature 少一個 → missing_headers。
    • 時間戳不是整數，或跟 nowSeconds 相差超過 toleranceSeconds（過去或未來都算）→ stale。
    • webhook-signature 可能有好幾個（空白分隔），secrets 可能有兩把（輪替中）：任一組合通過就是 { ok: true }，否則 bad_signature。不是 v1 的、base64 壞掉的簽章跳過，不能丟錯。
    • 比對用 crypto.subtle.verify，簽的是 rawBody 原本的字串。

練習 4：授權伺服器的 token 端點收到 client credentials 請求。寫 issueClientToken(clients, req)，決定能不能發 token、發哪些 scope（發 token 本身不用寫）：

  • clients 以 client_id 為鍵，secretHash 是 client secret 的 SHA-256 hex。把收到的 clientSecret 雜湊後，用起始程式的 timingSafeEqual 比對。
  • client 不存在、secret 錯，都回 invalid_client，不能丟錯或回不同的結果。
  • req.scope 是空白分隔的字串（可能有多餘的空白）。每一個都要在 allowedScopes 裡，否則回 invalid_scope。
  • 成功時回傳 { ok: true, scopes }：scopes 依 allowedScopes 的順序、不重複；scope 是空字串時給全部允許的 scope（要是新的陣列）。

練習 5：Vue 專案要顯示門市地圖，工程師把地圖服務的秘密 key 放在 .env 的 VITE_MAP_API_KEY，並且把 .env 加進 .gitignore。這樣安全嗎？

✓ Vite 會把 import.meta.env.VITE_* 替換成字串寫進打包後的 JS，Vite 文件明說不能放 API key。a、b 是同一個迷思：「環境變數」只代表值不寫在原始碼裡，最後跑在誰的電腦上才決定它是不是秘密，而前端程式碼跑在每個訪客的瀏覽器裡。d 錯：base64 是編碼，任何人都能解回來（第 2 課）。正確做法是讓後端拿 key 呼叫第三方，前端只呼叫自己的後端。

練習 6：會員系統接收咖啡店的「訂單完成」webhook，會依金額加點數。它驗證了 webhook-signature，但沒有檢查 webhook-timestamp，也沒有記錄處理過的 webhook-id。會出什麼事？

✓ 簽章只證明「咖啡店某個時候送過這個內容」，不證明「是剛剛送的、是第一次」。重送原封不動的請求，簽章照樣正確（a、d 錯）。檢查時間戳把重放的時間窗口縮到幾分鐘，用 webhook-id 去重把窗口內的重送也擋掉，同時處理了送出方正常的重試。c 錯：簽章一定涵蓋 body，改了金額簽章就對不上，攻擊者能做的只是原樣重送。

練習 7：外送平台來信：「工程師可能把我們的咖啡店 API key 貼到公開的 GitHub repo 了，但還不確定。」你先做什麼？

✓ 外洩的應變順序是先撤銷、再調查：每多等一分鐘，攻擊者就多一分鐘可以用。換 key 的中斷時間很短，資料被拿走卻收不回來。b 是迷思「先查清楚再撤銷」：查的期間 key 仍然有效，而且沒看到異常不代表沒被用。c 錯：公開過的內容可能已經被複製、被搜尋引擎或自動掃描工具抓走，改成私人的收不回來。d 錯：唯讀仍能讀到訂單與顧客資料。

常見錯誤

  • key 沒有前綴、沒有檢查碼：外洩了掃描工具認不出來。用 cafe_live_ 這種可辨識的前綴，最後加 CRC32 檢查碼。
  • API key 存明文，或用可逆的加密存：資料庫或備份外洩就等於 key 全部外洩。只存 SHA-256，原始 key 只在建立時顯示一次。
  • 對 API key 用慢雜湊：key 是 CSPRNG 產生的高熵亂數，猜不到，慢雜湊只會讓每個 API 請求變慢。慢雜湊是給人想的密碼用的。
  • key 沒有 scope：一把 key 等於全部權限，外洩時損害最大。依用途只給需要的 scope。
  • key 放在前端、放進 git、放在網址 query：VITE_ 變數會打包進 JS，git 歷史刪不乾淨，網址會進各種 log。前端需要時走後端代理，key 只放伺服器的環境變數，傳送時用標頭。
  • 同一時間只能有一把有效的 key：換 key 一定停機，所以大家都不換。允許新舊 key 並存的重疊期，舊 key 設定未來的失效時間。
  • 懷疑外洩時先調查再撤銷：調查期間 key 仍有效。先撤銷、發新的，再調查。
  • webhook 對 parse 後重新序列化的 JSON 驗證簽章：位元組不同，合法的請求全部失敗。用原始 body 驗證，通過之後才解析。
  • webhook 不檢查時間戳、不去重：錄下來的請求可以一直重送。時間戳限制在前後 5 分鐘，用 webhook-id 去重。
  • webhook 只看第一個簽章、只設定一把 secret：輪替一開始就全部失敗。逐一比對每個簽章與每把 secret。
  • 以為內網的服務互相呼叫不用認證：攻擊者進到內網任何一點就能呼叫所有服務。服務之間也要認證，只給需要的 scope。
  • client credentials 的錯誤訊息洩漏 client 是否存在：不存在與 secret 錯都回 invalid_client。
  • scope 只要有一個允許就整批通過：要求的每一個 scope 都要在允許清單裡，否則整個請求回 invalid_scope。

小結

  • 機器之間沒有人可以輸入密碼，呼叫方用服務帳號：外部夥伴呼叫我們用 API key、我們通知別人用 webhook 簽章、有授權伺服器的內部服務用 client credentials；mTLS 門檻最高，適合自己管的基礎設施。
  • API key 的格式：可辨識的前綴（區分 live／test）＋ 30 個 base62 隨機字元（約 178 bits）＋ CRC32 檢查碼，讓外洩的 key 被掃描工具找到、假的 key 不用查資料庫就排除。
  • 只存 SHA-256、只顯示一次；高熵的 key 不需要慢雜湊。驗證順序：格式 → 檢查碼 → 雜湊查表 → 撤銷、到期、scope。
  • 輪替靠新舊並存的重疊期；外洩時先撤銷再調查。秘密不能放在前端，VITE_ 變數會被打包進 JS。
  • Standard Webhooks：簽 id.timestamp.payload、v1, 加 base64 的 HMAC-SHA256、secret 去掉 whsec_ 後 base64 解碼、多個簽章支援輪替；接收方用原始 body 驗證、限制時間差、用 webhook-id 去重。
  • 不因為在內網就信任：服務之間也要認證。
  • client credentials 用服務的身分換短效、限定 aud 的 access token；授權伺服器只存 secret 的雜湊、不洩漏 client 是否存在、scope 只能是允許的子集。可以的話改用 private_key_jwt 或 mTLS；要代表使用者往下呼叫時用 token exchange。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：咖啡店的手機 App 要串外送平台，App 沒有後端代理，用 coffeeapp://oauth/callback 當 redirect_uri。該怎麼拿 token？

✓ App 是公開 client，打包後誰都拆得開，守不住 secret；任何 App 都能註冊同一個 scheme 攔下 code。PKCE 讓換 token 時必須送出只有發起者知道的 verifier，SHA-256 反推不回來，攔到 code 也沒用。a 是最常見的想法，但混淆只是拖時間，拆出來的 secret 對所有人都一樣。implicit 與密碼授權都被 RFC 9700 列為不應使用。（第 12 課）

練習 9：咖啡店後端收到 App 傳來的 Google ID token，簽章、iss、exp 都驗過了，但 aud 是另一個 App 的 client_id。該怎麼處理？

✓ ID token 是給特定 client 的登入證明，aud 必須有自己的 client_id、其他受眾也都要信任。任何 App 都能讓顧客用 Google 登入、拿到一張合法的 ID token，不驗 aud，別人的 App 拿到的 token 就能冒用顧客登入你的網站；access token 不能當登入證明也是同一個道理。a 錯在簽章只證明 Google 發過這張 token，不證明是發給你的。（第 13 課）

練習 10：陳美華用 email＋密碼註冊、累積了 800 點，今天第一次按「用 LINE 登入」，ID token 的 email 跟她的會員 email 相同。後端該怎麼做？

✓ 用 (iss, sub) 認人，不用 email；同 email 只是「可能已有帳號」的提示，連結要由已登入的本人確認。自動合併的話，攻擊者在不驗 email 的 OP 填上她的 email 就能永久接管帳號。b 錯在 email_verified 只代表 OP 某個時間點驗證過，仍然只能當提示；c 會讓她以為點數不見了，客服最常接到的就是這種案子。（第 13 課）

練習 11：滲透測試報告：拿登入第一步（密碼正確、還沒輸入驗證碼）拿到的 cookie，直接用 curl 呼叫 /api/orders，回 200。該怎麼修？

✓ MFA 必須是伺服器上的 session 狀態，不是前端的一個畫面：「待 MFA」只能呼叫驗證端點，通過後權限升級、換 session ID。b 是最多人的直覺，但攻擊者根本不經過前端，直接打 API 就跳過了路由守衛。d 只是縮短窗口，這 5 分鐘內照樣能讀訂單。（第 14 課）

練習 12：能退款的店長帳號已經開了 TOTP。上週有店長在仿冒網站輸入密碼和驗證碼，幾秒後帳號就被登入了。下一步加強哪個最有效？

✓ 驗證碼是可以照抄的字串，不知道自己被輸入在哪個網站，釣魚網站幾秒內轉送就能用。passkey 綁定 RP ID，瀏覽器在假網域根本不會列出它，clientDataJSON 的 origin 也由瀏覽器填，假網站拿到的東西在真網站無效。a 最多人選，但即時轉送只要幾秒，縮時間窗擋不住；簡訊同樣是可轉送的碼。（第 14、15 課）

練習 13：王小明覺得帳號被盜，用「忘記密碼」改了新密碼。隔天帳號又被下了一筆訂單，密碼沒有再被改過。重設流程最可能漏了什麼？

✓ 會來重設密碼，很可能就是帳號已經被別人登入；改密碼不會讓攻擊者手上的 session 失效，要在成功後呼叫 destroyAllForUser、撤銷 refresh token，並寄通知。b 錯在 token 是 32 bytes 的高熵亂數，SHA-256 猜不回來，而且用過就作廢。c 反了：重設後應該導回登入頁，自動登入是多一條跳過 MFA 的路。（第 16 課）

練習 14：設計 API key 的資料表時，同事說：「key 跟密碼一樣是秘密，應該用 Argon2id 存才安全。」怎麼回應？

✓ 慢雜湊是為了讓「照清單猜」變貴，對付的是人想的密碼；約 178 bits 的 key 每秒試一兆次也試不完，API 每個請求都要驗證，用慢雜湊只是讓自己變慢。存 SHA-256、用雜湊查表、原始 key 只在建立時顯示一次。a 是最常見的直覺，把「秘密」和「可猜的秘密」混為一談；c、d 都讓資料庫外洩等於 key 全部外洩。（第 17 課）

練習 15：會員系統的 webhook 接收端這樣寫，上線後咖啡店送來的合法 webhook 幾乎全部驗證失敗。為什麼？

// req.body 已被框架解析成物件
const payload = JSON.stringify(req.body)
const signed = `${headers['webhook-id']}.${headers['webhook-timestamp']}.${payload}`
if (!(await verifySignature(headers['webhook-signature'], signed))) {
  return res.status(401).end()
}

✓ 簽章簽的是原始位元組；JSON.parse 再 JSON.stringify 會改掉空白、鍵的順序、數字寫法，意思一樣、位元組不同。要拿框架解析之前的原始 body 驗證（NestJS 開 rawBody: true），通過後才解析。a 錯在時間戳是另一道檢查，用來擋重放，不影響簽章本身算不算得對。（第 17 課）
