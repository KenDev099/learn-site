階段 5：授權：能做什麼、能看哪些資料 · 第 18 課

RBAC：角色與權限

前面 17 課都在回答「你是誰」：密碼、session、JWT、OAuth、passkey、API key。從這一課開始回答第二個問題：知道你是誰之後，你能做什麼。這個問題叫授權（authorization），第 1 課區分過它和認證的差別，這個階段要把它真正寫成程式。

咖啡店後台的退款功能是半年前寫的。當時只有店長和老闆能退款，所以程式裡直接寫 if (user.role === 'manager' || user.role === 'owner')。現在老闆提了三個需求：

  1. 新增「副店長」：可以核准退款，但不能看營收報表。
  2. 退款要兩個人經手：吧台發起，班長核准，超過 2000 元要店長核准，避免有人自己退給自己。
  3. 明年開第二間門市，店員只能退自己門市的單。

這一課的任務：把「誰能做什麼」從散落各處的 if 整理成一套 RBAC（以角色為基礎的存取控制），讓前兩個需求改一張對照表、加幾行檢查就能完成，並且說得出第三個需求為什麼不該硬塞進角色裡。

這課的路線：
  1. 加一個副店長為什麼要翻遍整個專案：把角色和權限分開，程式只問權限（開場問題的最小答案）。
  2. 對照表裡放哪些權限、切多細，班長和店長為什麼不用把吧台的權限再寫一遍。
  3. 權限字串拼錯、資料庫裡的角色名稱壞掉時，怎麼讓錯誤早點出現，而且壞掉的結果是「拒絕」不是「放行」。
  4. 新路由忘了加檢查怎麼辦；有核准權限的人，怎麼不能自己核准自己發起的退款（第二個需求）。
  5. Vue 怎麼知道要不要顯示「核准退款」按鈕；第三個需求為什麼 RBAC 做不到，下一課接手。
這課會用到：
  • 第 1 課的預設拒絕與 401／403：沒有明確允許就拒絕；401 是「不知道你是誰」，403 是「知道你是誰，但你不能做」。
  • TypeScript 課第 20 課的 as const、typeof、satisfies：從一份清單推導出型別，清單改了型別跟著改。
  • TypeScript 課第 22 課的樣板字面值型別（template literal type）：`${string}:${string}` 代表「任意字串＋冒號＋任意字串」。那一課是選修，這課只需要知道這個意思。
  • NestJS 課第 6 課的 guard：在 controller 之前執行，回傳 false 就擋下請求。

加一個副店長，為什麼要翻遍整個專案？

先看現在的程式長什麼樣子。退款、看報表、改菜單這三個功能，各自在自己的 controller 裡判斷角色名稱：

// orders.controller.ts
if (user.role === 'manager' || user.role === 'owner') { /* 可以退款 */ }
// reports.controller.ts
if (user.role === 'manager' || user.role === 'owner') { /* 可以看報表 */ }
// menu.controller.ts
if (user.role === 'manager' || user.role === 'owner') { /* 可以改菜單 */ }

老闆的第一個需求是新增副店長，能退款、不能看報表。要做到這件事，你得找出程式裡每一個 'manager'，逐一判斷副店長該不該加進去。三個檔案還好，真實的後台可能有三十個。漏掉一個，副店長就少了一個該有的功能；多加一個，副店長就看到了不該看的報表。而且這兩種錯誤都不會有任何錯誤訊息，只會在某天有人抱怨時才被發現。

更麻煩的是，這種程式回答不了一個很基本的問題：「店長到底能做哪些事？」答案散在三十個檔案裡，要讀完全部程式才拼得出來。稽核或 PM 來問時，沒有一個地方可以指給他看。

問題的根源是：程式把兩件會各自變動的事綁在一起了。「退款這個功能需要什麼資格」跟著功能變，只有退款流程改了它才會變；「店長、副店長各能做什麼」跟著組織變，老闆調整人事就會變。把它們寫在同一行 if 裡，組織一調整，就得改功能的程式碼。

解法是在中間多放一層，把這兩件事拆開：

  • 權限（permission）：一個具體的動作，寫成「資源:動作」，例如 order:refund（核准退款）、report:read（看報表）。權限描述的是功能，跟誰在用無關。
  • 角色（role）：一組權限的名字，例如「店長 = 退款＋看報表＋改菜單」。角色描述的是組織裡的一種職務。
  • 使用者有角色，角色有權限。程式只檢查權限，不檢查角色名稱；角色到權限的對照集中寫在一個地方。

這就是 RBAC（role-based access control，以角色為基礎的存取控制）。名字裡有「角色」，但重點反而是程式碼裡不出現角色名稱：角色只出現在那張對照表裡。

下面把兩種寫法放在一起比。寫法 A 是現在的程式，寫法 B 多了一張對照表 ROLE_PERMS，新增副店長只在表裡加一行。執行後看三行輸出：同一個副店長，兩種寫法的答案各是什麼。

寫法 A 回答「副店長不能退款」，因為那行 if 根本不認得 assistant_manager，要改程式碼才能讓它認得。寫法 B 能退款、不能看報表，正好是老闆要的，而且 canB 這個函式一個字都沒改。（canB 裡用的 Object.hasOwn 是為了安全地查表，後面「資料庫裡的角色名稱不可信」那一節會解釋為什麼不直接寫 ROLE_PERMS[u.role]。）

這就是開場問題的最小答案：權限的名字跟著功能走，功能不變它就不變；角色跟著組織走，組織調整時只改對照表。新增角色時，程式碼一行都不用改。這張對照表同時也是一份文件，「店長能做什麼」有了一個可以直接讀的答案，稽核、新同事、PM 都看得懂。

不過上面的對照表是隨手寫的：店長和老闆的權限重複寫了兩遍，也還沒區分「發起退款」和「核准退款」。要支撐老闆的第二個需求，得先好好決定：表裡要放哪些權限，每個角色又該怎麼組。

對照表裡要放哪些權限？切多細、角色怎麼組？

設計權限從「系統有哪些動作」開始，不是從「公司有哪些職稱」開始。職稱會變，副店長今年有、明年可能就改名了；但「核准退款」這個動作只要功能還在就一直存在。所以先把每個資源能做的動作列出來，最後一欄才寫目前誰需要它：

權限意思誰需要
menu:read／menu:write看菜單／改品項與價格所有人／店長
order:create／order:read下單／看訂單顧客、吧台
order:update_status把訂單改成「製作中」「可取餐」吧台
order:refund_request發起退款（顧客在櫃台說咖啡做錯了）吧台
order:refund核准退款班長
order:refund:large核准超過 2000 元的退款店長
stampcard:adjust手動補點或扣點班長
report:read看營收報表店長
staff:manage新增員工、改員工的角色老闆

這張表一共 11 個權限。注意退款被拆成了三個：order:refund_request（發起）、order:refund（核准）、order:refund:large（核准大額）。這正是為了老闆的第二個需求：吧台要能發起但不能核准，班長能核准小額但不能核准大額。如果只有一個 order:refund，就沒辦法表達「能發起、不能核准」。

權限切多細沒有標準答案，但兩個極端都會出事。太粗，例如一個 order:write 包山包海，就沒辦法只給吧台改訂單狀態而不給他退款；太細，例如每個欄位一個權限，表會長到幾百列，沒人維護得動，最後大家乾脆每個角色都全勾。判斷的原則是：會有人需要「只能做 A、不能做 B」的，就拆開；沒有人需要分開的，就不拆。

接著組角色。看「誰需要」那一欄會發現一個規律：班長會做吧台做的所有事，再多一些；店長會做班長做的所有事，再多一些。如果每個角色都把權限從頭列一遍，吧台多一個權限時，就得記得同時加到班長、店長、老闆身上，又回到了「漏改一處」的老問題。

解法是角色繼承（role hierarchy）：一個角色可以宣告「我繼承某個角色」，它就擁有那個角色的全部權限，再加上自己額外的權限。每個角色只寫「自己多出來的」，其他靠繼承取得：

要算出一個角色的完整權限，就從它自己開始，沿著箭頭一路往左走，把經過的每個角色的權限收集起來。這個動作叫展開繼承，練習 1 的 permissionsOf 就是在做這件事。顧客不在這條鏈上：顧客能下單、看訂單，但不該因為「吧台也能下單」就跟吧台扯上關係，所以它是一個獨立的角色。

有了繼承，副店長也很好放：繼承班長，就拿到班長的核准退款等權限；再加上 order:refund:large，讓他能核准大額退款；report:read 不給，所以看不到營收報表。對照表多一列 assistant_manager: { permissions: ['order:refund:large'], inherits: ['shift_lead'] }，程式不用動。

繼承讓設定變短，代價是：要看完整條鏈才知道一個角色到底有什麼權限。鏈只有三層時還看得出來；繼承超過兩三層、或一個角色同時繼承好幾個角色時，最好提供一個「列出這個角色的完整權限」的工具或管理頁面，不然沒人說得清楚。

💡 實務上：權限跟著程式碼走，角色指派存在資料庫
團隊協作工具、電商後台這類產品幾乎都有一個「成員與權限」頁面，背後就是上面這種權限表加上角色對照。常見的分工是：權限清單寫在程式碼裡，因為每個權限都對應一段要檢查它的程式，新增權限一定伴隨部署；「誰是什麼角色」存在資料庫，由有 staff:manage 的人在後台調整。需求剛開始時先只做幾個固定角色，等真的有客戶要求「自訂角色」再做角色編輯器，它會帶來權限說明文字、預覽、設錯時怎麼復原等一整串工作。資深工程師接到新功能時會先問 PM：「誰能用？要不要拆成讀和寫兩個權限？」，在開發前就把答案寫進權限表。像這次的退款，就是在開工前先決定要拆成發起、核准、核准大額三個權限。

權限表定好了，但這 11 個權限在程式裡都只是字串。字串有一個老毛病：打錯了不會有人告訴你。

權限字串拼錯了，怎麼在存檔當下就知道？

想像退款 API 的檢查寫成 can(user, 'order:refnud')，u 和 n 對調了。JavaScript 不會報錯，因為對它來說這只是另一個字串。沒有任何角色擁有 order:refnud，所以這個檢查永遠回傳 false：上線後店長突然不能退款，要等客訴進來才發現。

反方向的拼錯更糟。後面「新路由忘了加」那一節會介紹政策表：記錄「每個路由需要什麼權限」的表。如果把 POST /orders/:id/refund 那一列的路由或權限打錯，這個路由等於沒有政策。系統若是「沒寫就放行」，結果就是任何登入的人都能退款。上一段的拼錯是「該能用的人不能用」，頂多有人來抱怨；這裡是「不該能用的人能用」，錢被退走了才會發現，所以更糟。不管哪一種，你都希望在打字的那一刻就看到紅線，而不是上線後才知道。

做法是讓 TypeScript 認得「合法的權限只有這 11 個」。手寫一個 type Permission = 'menu:read' | 'menu:write' | … 可以做到，但這樣權限就同時存在兩個地方：一份是執行時要用的陣列，一份是型別，新增權限時兩邊都要記得改，又是「漏改一處」。更好的做法是用 TypeScript 課第 20 課的技巧，只寫一份清單，型別從清單推導出來。這樣同一份清單同時是執行時的值和編譯時的型別：

  • as const 讓陣列的每個元素保留它的字面值型別，例如 'menu:read'，而不是被放寬成 string。
  • (typeof PERMISSIONS)[number] 意思是「這個陣列任何一個元素的型別」，結果就是所有權限組成的聯合型別。
  • satisfies 檢查值符合某個型別，但不改變推導出來的型別。這裡用它確認每個元素都長得像「資源:動作」。

下面的範例只放 3 個權限，方便看清楚。執行後看前兩行輸出：有的權限是 true，沒有的是 false；接著照註解拿掉 'order:refnud' 那行的註解，看編輯器怎麼標紅。

拼錯的 'order:refnud' 不在 Permission 這個聯合型別裡，所以 can 的參數型別不符，編譯就過不了。錯誤從「上線後的客訴」提前到「存檔當下的紅線」。新增權限時，只要在 PERMISSIONS 加一個字串，型別自動跟著變。

角色定義也用同樣的方式保護：ROLE_DEFS satisfies Record<Role, RoleDef<Role>> 會檢查三件事，每個角色都有寫、寫進去的權限都存在於 Permission、inherits 裡繼承的角色名字沒拼錯。因為用的是 satisfies 而不是型別註記，ROLE_DEFS 的型別還是保留它實際的內容。練習 1 的起始程式就是這樣寫的。

到這裡，你自己寫在程式碼裡的權限和角色都有編譯器把關了。但有一個值是編譯器看不到的：使用者身上的角色。

資料庫裡的角色名稱不可信，展開權限時要防什麼？

型別只保護你自己寫的程式。使用者的角色是從資料庫讀出來的 string：可能是舊版本留下的 'owner2'，也可能是有人手動改壞的值。這些值在執行時才出現，編譯器看不到，所以 permissionsOf(role: string) 的參數是 string，不是 Role，函式本身要處理不認得的角色。

換句話說，permissionsOf 是一個邊界：它把「外面來的、可能是任何值的字串」轉換成「一組權限」。邊界上的程式要假設輸入可能是壞的，而且壞的輸入必須得到最安全的結果。這一節處理三種壞輸入：不認得的角色、名字剛好撞到 JavaScript 內建屬性的角色、繼承繞成一圈的設定。

先決定不認得的角色該得到什麼。答案只能是「什麼權限都沒有」。給全部權限，或者「當作顧客處理」，都等於預設允許：資料壞掉的人反而拿到了權限。丟例外也不好，要看呼叫端有沒有接住，接不好就變成 500，或者在某個 try/catch 裡被吞掉而繞過檢查。這就是第 1 課的預設拒絕：沒有明確允許，就拒絕。

直覺的寫法是用 defs[role] 查表，查不到就回傳空集合。這裡有一個陷阱：JavaScript 的物件會從原型鏈繼承屬性。每個一般物件背後都連著 Object.prototype，上面有 toString、constructor 這些內建的東西，用 obj[key] 讀屬性時，物件自己沒有就會往原型鏈上找。所以就算 ROLE_DEFS 裡只寫了 barista，查 'toString' 也查得到東西。執行後看每一行中間的 typeof：哪些角色查到了不該查到的值。

結果分成三種：

  • 'barista'：查到物件，Object.hasOwn 也是 true，這是正常的角色。
  • 'owner2'：查到 undefined，if (!defs[role]) 擋得掉。
  • 'toString'、'constructor'：查到的是函式，if (!defs[role]) 擋不掉；接著讀 .permissions 得到 undefined，要逐一走訪它時程式就丟出例外。只有 Object.hasOwn 正確回答「這不是我們定義的角色」。

所以用不可信的字串查物件時，一律先用 Object.hasOwn(obj, key) 確認它是物件自己的屬性，或者改用 Map，Map 的 get 只看你放進去的 key。'__proto__' 是同一類的名字，練習 1 的測試會拿它來試。這也是第一節寫法 B 為什麼用 Object.hasOwn。

第三種壞輸入來自繼承。角色定義放進資料庫、可以在後台調整之後，就可能有人把 A 設成繼承 B、B 又繼承 A，或者讓一個角色繼承自己。展開繼承的程式如果只是「看到 inherits 就往下走」，就會在 A 和 B 之間來回走個不停：用迴圈寫是無窮迴圈，用遞迴寫是堆疊溢位，結果都是每個需要檢查權限的請求都卡住。防法是用一個 Set 記下已經處理過的角色，再遇到就跳過。繼承到一個不存在的角色，也照「不認得就沒有權限」處理，跳過即可。

練習 1 要你把這三件事寫進 permissionsOf，再用它寫出 can(user, permission)。到這裡，「這個人有沒有某個權限」有了一個可靠、壞輸入也只會得到拒絕的答案。但 can() 只有在被呼叫時才有用：如果某個路由根本沒呼叫它呢？

退款 API 有檢查了，下一個新路由忘了加怎麼辦？

先看這種漏洞在業界有多常見。OWASP 是一個整理 Web 安全問題的開放社群，它的 API Security Top 10（2023 版）列出 API 最常見的十類漏洞，第五名是 BFLA（Broken Function Level Authorization，功能層級授權失效）：一般使用者能呼叫只有管理者能用的功能。「功能層級」指的就是這一課在做的事：判斷這個人能不能使用某個功能，也就是某個路由。OWASP 列出的攻擊方式很樸素：

  • 直接猜管理功能的網址，例如 /api/admin/v1/users/all。
  • 把一個能用的請求換個方法，例如 GET /orders/42 改成 DELETE /orders/42。

你可能會想：前端沒有那個按鈕，使用者怎麼知道要打哪個網址？但前端沒有按鈕不代表 API 不存在。打包後的 JS 裡就看得到 API 的路徑，打開 DevTools 的 Network 分頁也看得到每一個請求，複製下來改一改再送出，不需要任何特殊工具。

咖啡店最可能出事的情境不是退款，而是下一個新功能。假設同事為了月底對帳，新增了 GET /admin/export，把所有訂單和顧客手機匯出成 CSV。功能寫好了、測試過了，就是忘了呼叫 can()。如果系統的規則是「有寫檢查才檢查，沒寫就放行」，任何登入的顧客都能下載全部顧客資料。退款 API 寫得再仔細也沒用，漏洞出在旁邊那個沒人想到的路由。

「每個人都記得加」不是可靠的機制，新人會忘、趕時程會忘、寫臨時工具時更會忘。要讓「忘記」這件事本身被系統擋下來。做法是把每個路由需要什麼權限寫成一張表，這張表叫政策表，表裡的每一列是一條政策（policy）：「POST /orders/:id/refund 需要 order:refund」、「GET /menu 公開」。有了這張表，可靠的做法是兩層：

  1. 執行時預設拒絕：授權判斷找不到這個路由的政策，就回 403，並記一筆錯誤 log。這樣新路由忘了寫政策，結果是「功能不能用」，同事自己測試時就會發現，而不是「所有人都能用」，上線後才被發現。
  2. 合併之前自動檢查：列出框架註冊的所有路由，跟政策表比對，有任何路由沒有政策就讓測試失敗。這個測試放在 CI 裡跑。CI（continuous integration，持續整合）是每次推送或合併程式碼前，自動安裝、建置、跑測試的流程，測試沒過就不能合併。這樣漏寫政策的路由在合併之前就被擋下來，不用等到有人打到它。同樣的比對也可以放在應用程式啟動時：有路由沒有政策，就讓啟動失敗。放在啟動時是部署當下擋下，放在 CI 則是合併之前就擋下。

第一層保證「漏了也不會放行」，第二層保證「漏了會被看到」。兩層缺一不可：只有第一層，漏寫的路由可能要到某個少用的功能被點開時才發現；只有第二層，測試哪天被關掉或沒涵蓋到動態註冊的路由，就又回到預設允許。

還有一個細節：公開的路由也要明寫 'public'，不能用「沒寫」代表公開。如果「沒寫」等於公開，就分不出「故意公開」和「忘了寫」，上面的兩層檢查都失效。明寫之後，政策表裡每一列都是有人決定過的，審查時看得到「這個路由故意公開」。練習 2 要你寫出這兩層：findUnprotectedRoutes 找出沒有政策的路由，authorizeRoute 依序回答沒有政策、公開、沒登入（401）、沒權限（403）。

第一層在 NestJS 裡的形狀是：一個全域的 guard 讀每個 handler 上宣告的權限，沒有宣告就拒絕。guard 的完整實作在第 21 課，這裡先看形狀：

@Post(':id/refund')
@RequirePermissions('order:refund')      // 宣告這個 handler 需要的權限
approveRefund(@Param('id') id: string) { … }

@Get('menu')
@Public()                                // 公開也要明寫
listMenu() { … }

// 全域的 PermissionsGuard：
//   有 @Public() → 放行
//   有 @RequirePermissions(...) → 用 can() 檢查
//   兩個都沒有 → 拒絕（預設拒絕）

guard 只做第一層。第二層是另一個測試：列出 Nest 註冊的所有 handler，檢查每個都有 @Public() 或 @RequirePermissions()，有任何一個兩者皆無就失敗。

注意這裡宣告的是權限 'order:refund'，不是角色。如果寫成「需要 manager 或 owner」，就又回到第一節的問題：新增副店長時要改每一個 decorator。第 1 課練習 3 的政策表寫的是角色，兩者的差別見課末。

💡 實務上：code review 先看新路由的權限，測試要有 403 的案例
審查新增 API 的 PR 時，第一個問題通常不是邏輯對不對，而是「這個端點要什麼權限？」。測試只寫「店長呼叫成功」不夠，至少再寫一個「吧台呼叫回 403」、一個「沒登入回 401」，否則權限檢查哪天被誤刪也不會有測試失敗。像上面的月底對帳匯出，資料匯出、批次修正這類「臨時內部工具」最常漏權限，因為寫的人心裡想的是「只有我會用」。資安或稽核來問「誰能匯出顧客資料」時，能直接拿出政策表回答，比翻程式碼可靠得多。

路由層現在擋得住沒有 order:refund 的人了。可是老闆第二個需求擔心的，偏偏是有這個權限的人。

有核准權限的人，怎麼不能自己核准自己的退款？

退款是咖啡店最容易出現內部舞弊的地方。假設班長自己發起一筆退款，說顧客的咖啡做錯了，再用自己的帳號核准，錢就從收銀機流出去，而且帳上看起來完全合規：發起的人有發起權限，核准的人有核准權限。問題在於發起和核准是同一個人，整個流程裡沒有第二雙眼睛。

這就是職責分離（separation of duties）要解決的事：把一件有風險的工作拆成幾個步驟，交給不同的人完成，讓舞弊至少需要兩個人串通。單人作弊很容易，兩個人串通的成本和被發現的機會都高得多。老闆的第二個需求寫成表格是這樣：

步驟誰需要的權限
發起退款吧台（或任何店員）order:refund_request
核准 2000 元以下班長，而且不是發起的人order:refund
核准超過 2000 元店長，而且不是發起的人order:refund＋order:refund:large

表格的「需要的權限」欄，RBAC 都處理得了，這就是第二節把退款拆成三個權限的用意。但「而且不是發起的人」這個條件不是權限，RBAC 寫不出來。原因是權限只看「這個人是誰、有什麼角色」，而這個條件要看「這一筆退款是誰發起的」，同一個店長面對自己發起的那筆要拒絕，面對別人發起的那筆要允許。角色對照表裡沒有任何一列能表達這件事。

所以這個條件必須在處理那筆退款的程式裡檢查：先從資料庫讀出這筆退款，拿 refund.initiatedBy 和核准者的 id 比對。練習 3 的 approveRefund 就是把這張表寫成程式，判斷順序是：沒有核准權限、自己核准自己、金額太大而沒有大額權限，都通過才核准。權限一律用 can() 問，不比對角色名稱。這種「要看這一筆資料才能決定」的條件，下一課會推廣成物件層級授權。

職責分離防的是一個人蓄意作弊。另一種風險是帳號本身被盜：班長的密碼外洩了，攻擊者拿到的就是班長的全部權限。這時能控制的是損失有多大，對應的原則叫最小權限（least privilege）：每個帳號只給它完成工作所需的最少權限。放到 RBAC 裡，具體是這幾件事：

  • 新員工給最小的角色，需要時再升級，不要「先給店長，比較方便」。副店長也是一樣：老闆可能會說「直接給他店長角色，叫他不要看報表就好」，但「不要去看」不是控制，該做的是照第二節開一個副店長角色。
  • 老闆的 owner 帳號平常不用。老闆日常巡店用店長角色的帳號，要新增員工時才登入 owner 帳號。日常帳號被盜，損失的是店長的權限，不是全部。
  • 定期檢查誰有什麼角色：調職、離職的人常常留著舊角色，那些權限沒人在用，卻一直在等著被盜用。

老闆出國、店長離職時，系統還是得有人能處理高權限的事，這時用的是平常鎖起來的「緊急存取帳號」，怎麼保管和監控見課末。

💡 實務上：職責分離與權限盤點在團隊裡隨處可見
你每天都會碰到職責分離：PR 要別人核准才能合併、正式環境的部署要另一個人按同意、改商品價格或大量退款要主管簽核。設計後台功能時，遇到「動到錢」「動到個資」「改別人權限」的動作，就該想一下要不要拆成發起與核准。權限盤點則常跟著離職流程走：HR 系統標記離職，就要有人（最好是自動化）停用帳號、移除角色。注意不要每個動作都要求兩人核准，流程太卡的話大家會共用一個高權限帳號來繞過，反而更危險。

後端的規則到這裡都齊了：路由層看權限，處理退款時再比對發起者。剩下前端：Vue 前台怎麼知道要不要把「核准退款」按鈕顯示給這個人？

Vue 前台怎麼知道要不要顯示「核准退款」按鈕？

班長打開後台的訂單頁，應該看到「核准退款」按鈕；吧台打開同一頁，按鈕應該藏起來，免得他按了才看到 403。前端需要知道「這個人能做什麼」。

最常見的做法是把使用者的角色傳給前端，前端再寫一份 if (role === 'manager')。這等於把第一節的問題原封不動搬到前端：角色到權限的對照現在有兩份，一份在後端、一份在 Vue。老闆新增副店長時，後端改了對照表，前端忘了改，就會出現「有權限卻找不到按鈕」；反過來前端改了、後端沒改，就是「按鈕看得到但按了 403」。

比較好的做法是讓對照表只存在後端。後端提供一個端點，回傳這個人展開繼承之後的完整權限清單：

GET /me/permissions

200 OK
{
  "role": "shift_lead",
  "permissions": ["menu:read", "order:create", "order:read", "order:update_status",
                  "order:refund_request", "order:refund", "stampcard:adjust"]
}

這份清單就是 permissionsOf('shift_lead') 的結果：班長自己的 2 個權限加上從吧台繼承的 5 個。前端不需要知道繼承怎麼運作，也不需要知道副店長存不存在，它只問「清單裡有沒有 order:refund」。Vue 端把清單存起來，寫一個 can('order:refund') 給 v-if 與路由守衛用（Vue 課第 20 課）。後端改了對照表，前端下次取清單時自然就拿到新的結果。

這個做法還有三件事要記得：

  • 前端的檢查只是使用者體驗。藏起按鈕擋不住任何人：上一節說過，攻擊者用 curl 或 DevTools 直接打 API。每個 API 照樣檢查權限，前端的 can() 只負責「不要顯示用不到的東西」。
  • 權限會變。店長把班長降回吧台，前端手上的清單還是舊的。API 回 403 時重新取得權限清單；切換頁面或重新整理時也重新取得。後端也不能依賴 token 裡的角色（第 11 課的過期權限），每次從資料庫讀。
  • 權限清單本身不是秘密，但不要順便回傳別的東西，例如所有角色的完整對照表，這會告訴攻擊者有哪些功能值得試。

老闆的前兩個需求都完成了：副店長只是對照表的一列，兩人核准是權限加一行比對，前端跟著權限清單走。剩下第三個需求：開第二間門市後，店員只能退自己門市的單。

「只能退自己門市的單」：為什麼角色做不到？

RBAC 回答的是「這個人能不能做這類動作」：能不能核准退款、能不能看報表。它看的只有人和角色，不看被操作的那一筆資料。老闆的第三個需求，跟下面這幾個需求是同一種：

  • 店員只能處理自己門市的訂單。
  • 顧客只能看自己的訂單。
  • 不能核准自己發起的退款（上一節已經遇到）。
  • 只有值班中的班長能核准退款。

它們的共同點是：答案取決於「這一筆資料」或「這個人當下的狀態」。同一個店員，面對自己門市的訂單要允許，面對別間門市的要拒絕。這些資訊不在角色對照表裡，RBAC 看不到。

硬要用角色表達會怎樣？最直覺的做法是開 barista_store1、barista_store2，再來是 shift_lead_store1_weekend……每開一間店、每多一個例外，角色數量就乘上去，最後角色比員工還多，沒人說得清誰能做什麼。這叫角色爆炸（role explosion）。它把第一節好不容易整理好的對照表又變回一團亂，而且門市 id 還是得在某處比對，角色並沒有真的解決問題。看到角色名稱裡出現門市、人名、時段，就是該換工具的訊號。

正確的分工是兩層：RBAC 決定「能不能呼叫這個功能」，在路由層檢查；再由處理那筆資料的程式，依「這筆資料」與「這個人的屬性」決定「能不能動這一筆」，例如比對店員的門市和訂單的門市。後者就是下一課的物件層級授權，以及依屬性決定權限的 ABAC。兩層都要有：只有 RBAC，店員就能退別間門市的單；只有物件層級，顧客就能呼叫到管理功能。

補充與查表

主線用不到、但設計帳號制度或回頭對照第 1 課時會查的細節。

緊急存取帳號（break-glass account）

老闆出國、店長離職，系統卻要有人處理高權限的事。準備一個平常鎖起來的高權限帳號，密碼與安全金鑰分開保管，每次登入都通知所有管理者、每個動作都寫進稽核紀錄（第 25 課），用完立刻換密碼。它跟最小權限不衝突：平常沒人用它，用的時候所有人都知道。

第 1 課的政策表與這一課的差別

第 1 課練習 3 的政策表寫的是「哪些角色可以呼叫」，這一課改成「需要哪個權限」。差別就是第一節的副店長問題：政策表寫角色，新增角色就要改每一列；寫權限，只改角色定義。

練習

練習 1：把咖啡店的權限表寫成有型別檢查的程式。要做三件事：

  • 讓 Permission 從 PERMISSIONS 推導成 11 個字面值的聯合（不能手寫一遍，也不能是 string）。完成後 can(u, 'order:fly') 要是編譯錯誤。
  • 寫 permissionsOf(role, defs)：回傳這個角色自己的權限加上所有繼承來的權限（一路往上，去掉重複）。role 是從資料庫讀出來的字串，不認得的角色回傳空集合，包括 'toString'、'__proto__' 這種名字；繼承繞成一圈、繼承自己、繼承不存在的角色，都要正常結束。每次呼叫都回傳一個新的 Set。
  • 寫 can(user, permission)：用 permissionsOf 判斷。

練習 2：寫兩個函式，擋下「新路由忘了加權限」。POLICIES 的 key 是「方法 空白 路徑樣式」，值是 'public' 或一個權限；matches 已經寫好。

  • findUnprotectedRoutes(routes, policies)：照 routes 的順序，回傳沒有對應政策的路由，格式是 'DELETE /orders/:id'。路由清單的 path 就是樣式本身，所以用 key 直接查，方法大小寫不同就是不同的 key。
  • authorizeRoute(user, method, path, policies)：依序判斷：找不到匹配的政策 → no_policy；'public' → 允許；沒登入（null）→ unauthenticated；can() 為真 → 允許，否則 forbidden。不要比對角色名稱。

練習 3：寫 approveRefund(refund, approver)，實作退款的職責分離。依序判斷：

  1. 核准者沒有 order:refund → forbidden。
  2. 核准者就是發起者（approver.id === refund.initiatedBy）→ self_approval。
  3. 金額超過 LARGE_REFUND（2000 元，剛好 2000 不算），而核准者沒有 order:refund:large → amount_too_large。
  4. 都通過 → { ok: true }。

權限一律用 can() 檢查。隱藏測試會在 ROLE_DEFS 加一個新角色，比對角色名稱的寫法會失敗。

練習 4：老闆要新增「副店長」：可以核准大額退款，但不能看營收報表。程式用的是這一課的 RBAC，最好的做法是什麼？

✓ c：程式只檢查權限，新增角色就是在對照表裡組合現有的權限。a 是第一節的反例，漏改一處就出錯；b 用「繼承再扣掉」，又把角色名稱寫回程式，下一個例外又要再加一行；d 違反最小權限，「不要去看」不是控制。

練習 5：Vue 前台已經依 GET /me/permissions 把「核准退款」按鈕藏起來了。POST /orders/:id/refund 還需要檢查 order:refund 嗎？

✓ b：請求的每個位元組都在使用者手上（第 1 課），伺服器只能相信自己驗證過的東西。a 與 d 都是「看不到就安全」的誤解：打包後的 JS 裡就有 API 路徑，OWASP 也把「猜管理功能的網址」列為 BFLA 的典型攻擊；c 讓開發與正式環境行為不同，測試就測不到真正的規則。

練習 6：需求是「店員只能處理自己門市的訂單」。用 RBAC 怎麼做？

✓ d：角色描述的是「能做哪類動作」，不認得「這一筆」資料。a 是角色爆炸，開新店就要改角色、改每個人的設定；b 的權限名稱寫了「自己門市」，但真正的比對還是得在程式裡做，權限只是換個名字；c 把會變的屬性放進 token，會遇到第 11 課的過期權限，也一樣要程式比對。

常見錯誤

  • 程式裡檢查角色名稱：新增或調整角色就要改散落各處的程式，漏一處就出錯。程式只檢查權限，角色到權限的對照集中在一個地方。
  • 為每個例外開新角色：角色爆炸。角色名稱裡出現門市、人名、時段時，改用物件層級授權或 ABAC。
  • 權限字串散落各處、拼錯沒人發現：用 as const 清單推導出 Permission 型別，政策表與 can() 都只接受這個型別。
  • 用 defs[role] 查資料庫來的角色：'toString'、'__proto__' 會查到原型鏈上的東西。用 Object.hasOwn 或 Map，不認得的角色一律沒有權限。
  • 展開繼承沒有記錄走過的角色：設定繞成一圈時無窮迴圈，所有請求卡住。用一個 Set 記下處理過的角色。
  • 新路由忘了加權限，系統預設允許：這就是 BFLA。授權判斷找不到政策時拒絕，再用測試自動比對「所有路由」與「政策表」，公開的路由也要明寫 public。
  • 允許自己核准自己：有核准權限的人就能自己發起、自己核准，職責分離失效。核准時比對發起者。
  • 日常使用 owner 帳號：被盜就是全部權限。老闆日常用低權限帳號，緊急存取帳號平常鎖起來，用了一定通知並留紀錄。
  • 前端另寫一份角色規則，或只有前端檢查：兩邊不一致，或攻擊者直接打 API。後端回傳展開後的權限清單給前端，API 照樣檢查。

小結

  • RBAC：使用者有角色、角色有權限，程式只檢查「資源:動作」形式的權限。權限跟著功能走，角色跟著組織走；新增副店長只改對照表。
  • 權限從系統的動作設計，需要「只能做 A 不能做 B」的就拆開，例如退款拆成發起、核准、核准大額；角色繼承讓設定變短，但要能列出一個角色的完整權限。
  • as const＋typeof 從清單推導 Permission，satisfies 檢查角色定義，拼錯就是編譯錯誤；資料庫來的角色仍要在執行時處理。
  • 展開繼承：不認得的角色沒有權限、用 Object.hasOwn 查表、記錄走過的角色防止繞圈。
  • 擋 BFLA（OWASP API5:2023）：每個路由都有政策、找不到政策就拒絕、自動檢查沒有政策的路由。
  • 職責分離：發起與核准分給不同權限，核准時比對發起者；最小權限：新員工給最小角色、owner 帳號平常不用、緊急存取帳號留紀錄。
  • 前端用 GET /me/permissions 拿展開後的權限決定顯示什麼，API 照樣檢查。
  • RBAC 只管「能不能做這類動作」，管不了「這一筆」；硬用角色表達會角色爆炸。
