階段 4：更多登入方式：第三方、多因素與機器 · 第 16 課

帳號流程：驗證信、重設密碼與防暴力破解

咖啡店的會員系統已經有安全的密碼儲存（第 3 課）、session（第 4 課）、MFA（第 14 課）和 passkey（第 15 課）。下週要上線登入頁旁邊那一排連結：「忘記密碼」「重寄驗證信」「更改 email」。同事寫好了第一版：忘記密碼查不到人就顯示「查無此 email」，重設信裡的連結用請求帶來的網域組出來，登入連續錯 5 次就永久鎖住帳號。每一項單獨看都合理，功能也都能動。

你負責上線前的審查。這課從頭到尾用同一個方法：假設有個攻擊者想拿走會員王小明帳號裡的儲值金。他手上有一份別的網站外洩的帳號密碼清單，但沒有王小明的手機，過不了 MFA。他不會去敲最堅固的那扇門，會挑最弱的入口。我們跟著他一步一步走，每走到一個入口，就看第一版會在哪裡被突破、要怎麼補。走完這課，你會有一份帳號流程的審查清單，也親手寫出三段程式：不洩漏帳號狀態的登入、重設密碼服務、登入限流。

這課的路線：
  1. 王小明的帳號有幾個入口：忘記密碼、改 email 為什麼跟登入一樣危險，審查每條路時要問的那一個問題（開場問題的最小答案）。
  2. 攻擊者怎麼先篩出誰是會員：錯誤訊息和回應時間怎麼洩漏帳號存不存在，怎麼改成不洩漏。
  3. 忘記密碼的連結、改 email：寄出去的連結怎麼不變成萬能鑰匙，拿到 session 的人為什麼還不能改 email。
  4. 直接猜密碼、擋不住的時候：限流怎麼設才不會讓攻擊者故意鎖住別人，防線漏掉時怎麼讓本人和你知道。
這課會用到：
  • 第 2 課的 randomToken 與 SHA-256：randomToken 用安全亂數產生 32 bytes、轉成 base64url 字串；SHA-256 把它變成存進資料庫的雜湊。
  • 第 3 課的 hashPassword／verifyPassword：用刻意算很慢的雜湊存密碼，登入時重算一次來比對。
  • 第 4 課的 destroyAllForUser：刪掉一位使用者所有的 session，每台裝置都要重新登入。
  • 第 14 課的 MFA 與 step-up：MFA 是密碼之外再驗一個因素；step-up 是做敏感操作前，要求使用者最近驗證過。

王小明的帳號有幾個入口？

先站在攻擊者的位置數一數。講到「拿到帳號」，大部分人只想到登入頁。但對攻擊者來說，任何一條「走完之後就能用這個帳號」的路都是入口。下面六條路的終點都一樣，都是「這個人能用王小明的帳號」：

這張圖要說的是：帳號的安全程度，等於這六條路裡最弱的那一條。我們在登入加了 MFA，攻擊者就不走登入。如果忘記密碼只要「收得到 email」就能改密碼、改完直接進去，MFA 就等於沒裝：攻擊者只要先拿到王小明的信箱，例如王小明的信箱密碼跟外洩清單裡那組一樣，就能從忘記密碼繞過第二個因素。客服是同一回事。客服在電話裡聽到正確的生日和 email 就幫忙改綁，等於把帳號交給任何知道這兩項資料的人，而這兩項資料在很多外洩事件裡都拿得到。

所以審查帳號流程時，每一條路都問同一個問題：這條路要使用者證明什麼？證明的強度有沒有比登入弱？這就是開場問題的最小答案。套回上面兩個例子：有開 MFA 的帳號，重設密碼後仍然要過 MFA，因為「收得到 email」只證明擁有信箱，取代不了第二個因素；客服的重設，最多只能觸發一封寄到已驗證 email 的重設信，不能在電話裡直接改資料。

接下來每一節都是這個問題的具體版本，順序照攻擊者會走的路。他手上的清單有一百萬組帳密，其中大部分的 email 根本不是咖啡店會員。動手之前，他要先回答一個問題：這份清單裡，誰是咖啡店的會員？

攻擊者怎麼先篩出誰是會員？

第一版的忘記密碼頁，輸入沒註冊的 email 會顯示「查無此 email」。這對真正的使用者很貼心，對攻擊者也一樣貼心：他寫一支程式，把一百萬個 email 逐一送進忘記密碼，看到「查無此 email」就跳過，剩下的就是會員名單。像這樣從錯誤訊息或回應時間判斷某個 email 有沒有註冊，叫做帳號列舉（account enumeration）。

拿到會員名單，對攻擊者有三個用處：

  • 撞庫更省力：第 3 課提過撞庫（credential stuffing），就是拿別的網站外洩的帳號密碼來試。只對確定存在的帳號試，請求量少很多，也不容易觸發警報。
  • 釣魚信更可信：「您在咖啡店的帳號異常」只寄給真的會員，收信的人更容易相信。
  • 「有註冊」本身就是隱私：有些網站光是被知道你是會員就會出事，例如診所、交友網站。

洩漏的地方不只忘記密碼頁。凡是會依照「這個 email 存不存在、帳號是什麼狀態」給出不同回應的端點，都是列舉的入口。把第一版裡會洩漏的地方和改法列出來：

流程會洩漏的寫法不洩漏的寫法
登入「這個 email 尚未註冊」／「密碼錯誤」一律「email 或密碼不正確」
忘記密碼「查無此 email」一律「如果這個 email 有註冊，我們已寄出重設信」
註冊「這個 email 已經被使用」一律「請到信箱完成驗證」；email 已存在時，改寄一封「你已經有帳號了，忘記密碼請點這裡」給本人
停用的帳號「帳號已停用」（密碼都還沒驗就說）跟密碼錯誤一樣回「email 或密碼不正確」

改法的原則是：畫面上的訊息一律寫成「不管帳號存不存在都成立」的句子，真正的結果改從只有本人收得到的管道送出。使用者體驗並沒有因此壞掉：忘記密碼的人如果有註冊，會收到重設信；用已註冊的 email 再註冊一次的人，會收到「你已經有帳號了」的信。答案只有信箱的主人看得到，攻擊者看到的永遠是同一句話。

停用帳號那一列容易被忽略。「帳號已停用」看起來沒在講帳號存不存在，但它一樣透露了「這個 email 有註冊」，而且第一版是在密碼都還沒驗之前就說，攻擊者連密碼都不用猜。所以停用的帳號也回「email 或密碼不正確」。

💡 實務上：註冊要不要洩漏，是跟 PM 一起決定的取捨
登入、忘記密碼不洩漏幾乎沒有代價，註冊卻有：上面「一律請到信箱驗證」的做法，使用者要多收一封信才知道結果，PM 常會擔心註冊轉換率下降。對咖啡店會員系統這是合理的取捨；如果產品決定直接顯示「email 已被使用」，至少要對註冊端點限流，讓大量查詢變貴。資深工程師會把這個決定和理由寫進規格，免得之後有人為了「優化體驗」，把登入或忘記密碼的訊息也改成會洩漏的寫法。

訊息統一之後，畫面上已經看不出差別。但攻擊者還有第二個觀察點：每個請求花了多久。

訊息都一樣了，回應時間還會洩漏嗎？

會。從處理時間的差異推出原本看不到的資訊，叫做時間側通道（timing side channel）。「側通道」指的是資訊不是從正式的輸出（回應內容）漏出去，而是從旁邊的副作用漏出去，處理時間是最常見的一種。

看第一版的登入程式：找不到使用者就立刻回傳，找到了才跑慢雜湊。第 3 課的慢雜湊故意讓驗證一次花上幾十到幾百毫秒，目的是讓偷到雜湊的人很難大量猜密碼。這個設計在這裡反過來害了我們：存在的帳號要多跑一次慢雜湊，差距大到用碼表都量得出來。按「執行」，看兩個 email 各花多久：

兩個回應的內容一模一樣，都是 invalid_credentials，但不存在的帳號幾乎 0 毫秒，存在的帳號要幾十毫秒。攻擊者不用看訊息，只要替每個請求計時，比較慢的就是會員。

修法是讓兩條路做一樣的事：使用者不存在時，也用一個固定的假雜湊（dummy hash）跑一次驗證，結果丟掉。這樣不管帳號存不存在，請求都花一次慢雜湊的時間。假雜湊要用跟真的雜湊同樣的演算法和參數產生，例如伺服器啟動時對一個隨機字串跑一次 hashPassword，把結果留在記憶體。參數不同，例如迭代次數比較少，驗證時間也會不同，又出現新的差距。還有一個細節：假雜湊驗證「通過」也不能算登入成功，判斷成功時要同時確認使用者真的存在。

慢雜湊是最明顯的時間差，但同樣的道理適用於每一個「只有帳號存在時才做」的動作。審查時要把這些分支找出來：

  • 寄信：忘記密碼時，存在的帳號要寄信，呼叫郵件服務要花幾百毫秒，不存在的不用寄。改法是把寄信放進佇列（NestJS 課第 20 課）：請求只負責把「寄這封信」記下來就回應，由背景的程式另外寄出。這樣兩條路都立刻回應。
  • 停用帳號、未驗證 email 的分支：未驗證 email 指的是註冊後還沒點驗證信的帳號，為什麼要驗證，後面改 email 那一節會講。這些檢查要放在密碼驗證之後，否則它們又是一條不跑雜湊的快速路徑。上一節說停用帳號要回同一句話，這裡再加一條：也要花同樣的時間。
時間一致是「讓差距小到量不出來」，不是完全相等：網路延遲本身就有幾毫秒的抖動。目標是消除慢雜湊、寄信這種幾十毫秒以上、一量就出來的差距。

練習 1 要把第一版的登入改成這個樣子：不存在、停用、密碼錯，每一種失敗都剛好驗證一次，回同一個錯誤。到這裡，攻擊者已經沒辦法從回應判斷誰是會員。但他對王小明本來就有興趣，不需要名單：他可以直接對王小明的 email 按「忘記密碼」，看看寄出去的那封信能不能為他所用。

忘記密碼寄出的連結，怎麼不變成萬能鑰匙？

先看忘記密碼的標準流程：使用者輸入 email → 伺服器產生一個一次性 token，把含有它的連結寄到這個 email → 使用者點連結、輸入新密碼 → 伺服器確認 token 有效，改掉密碼。這個流程拿「收得到這封信」當身分證明：只有信箱的主人收得到信，所以能出示 token 的人就被當成帳號主人。

這種寄到 email、點了就能完成某件事的一次性連結也叫 magic link。email 驗證、「免密碼登入」用的是同一套做法，所以這一節的規則也適用於它們。

從攻擊者的角度看，這個 token 就是一把臨時的密碼：誰拿到它，誰就能改王小明的密碼。他拿到 token 的方法有幾種：用猜的、從外洩的資料庫讀出來、翻到信箱裡的舊信、騙王小明把它送出去。下表每一條規則各擋其中一種，跟第 10 課的 refresh token 很像：

規則理由
用第 2 課的密碼學安全亂數產生器（CSPRNG），例如 crypto.getRandomValues，產生 32 bytes（256 bits）猜不到。The Copenhagen Book 的下限是 112 bits。
資料庫只存 SHA-256資料庫或備份外洩時，拿到的雜湊不能拿來重設任何人的密碼。token 是高熵亂數，不像密碼可以拿字典猜，所以快雜湊就夠，不用第 3 課的慢雜湊。
短期限：常見 15～60 分鐘（本課 30 分鐘）信箱裡的舊信、轉寄、被備份的郵件都可能外洩；期限越短，舊信越沒用。
單次使用用過就作廢，瀏覽器歷史紀錄裡的連結再打開也沒用。
新申請時，同一位使用者舊的 token 全部作廢使用者按了三次「忘記密碼」，只有最新那封信有效，外面流傳的舊連結都失效。
綁定一位使用者token 只能重設申請時的那個帳號。

第一版違反了其中幾條：把 token 原文直接存進資料庫，重新申請時也沒有作廢舊的。練習 2 會一起修掉。不過就算 token 本身做得完全正確，還有一個地方能把它送到攻擊者手上：信裡那個連結指向的網域。

信裡的連結會指向哪裡？

組信裡的連結時，很自然會寫 `https://${req.headers.host}/reset?token=…`，因為這樣開發、測試、正式環境都不用改設定，第一版就是這樣寫的。問題是 Host 標頭是客戶端送來的。瀏覽器會把網址列上的網域填進去，但攻擊者自己用程式發請求時，想填什麼都可以。利用這一點讓伺服器產生指向別的網域的內容，叫做 Host 標頭注入（host header injection）。看攻擊者怎麼替王小明申請重設：

王小明收到的是咖啡店真正寄出的信，寄件人、內容都正確，只有連結指向 evil.example。他一點，token 就送到攻擊者的伺服器上，攻擊者拿它到真網站重設密碼。前面那些 token 規則全都做對也沒用，因為 token 是王小明自己親手送出去的。

你可能會想：伺服器前面還有一層，不會擋嗎？很多部署會在應用程式前面放一台反向代理（reverse proxy），例如 Nginx 或雲端的負載平衡器。它先收下所有請求，再轉給後面的應用程式。但反向代理不一定會擋掉奇怪的 Host。代理還會用 X-Forwarded-Host 標頭轉告應用程式「原始請求的網域是什麼」，這個標頭客戶端也一樣能自己帶。所以規則很簡單：信裡的網址一律用設定檔的 APP_URL，部署時就決定好，跟請求內容無關。

王小明點開連結之後，還有哪些地方要守？

連結送對了地方，王小明點開重設頁、輸入新密碼。從打開頁面到改完密碼，還有六件事要做對，每一件都對應攻擊者的一個機會：

  • 重設頁加 Referrer-Policy: no-referrer：token 在網址裡。瀏覽器載入頁面上的圖片、腳本、或使用者點出去的連結時，會用 Referer 標頭告訴對方「我從哪一頁來」。現在瀏覽器的預設政策 strict-origin-when-cross-origin 對別的網域只送網域、不送路徑和查詢字串，但同網域的請求（例如自己的分析端點、存取紀錄）會帶完整網址，網站或框架也可能把政策改寬。no-referrer 讓這一頁完全不送，token 就不會出現在任何人的紀錄裡。
  • 先驗 token，再顯示表單；送出新密碼時再驗一次（token 仍然有效、沒被用過），然後才改密碼。新密碼一樣要過第 3 課的長度與外洩清單檢查。
  • 成功後讓這位使用者所有的 session 和 refresh token 失效（第 4 課的 destroyAllForUser、第 10 課的 refresh token 撤銷）：會來重設密碼，很可能就是因為帳號被別人登入了。不踢掉這些 session，已經在裡面的攻擊者會繼續用。
  • 不要自動登入：OWASP 建議重設完導回登入頁，讓使用者用新密碼走一次正常登入。正常登入流程會走 MFA、限流、新裝置通知；自動登入等於多一條跳過這些檢查的路，也就是第一節說的「比登入弱的入口」。
  • 寄通知信：「你的密碼剛剛被變更，如果不是你，請……」。信裡不要附密碼。
  • 忘記密碼的申請不能讓帳號被鎖：申請重設時舊密碼仍然有效，直到 token 被使用。否則任何人輸入你的 email 按「忘記密碼」，你就登不進去了。但「申請」本身要限流（每 email、每 IP），否則有人能用它對你的信箱轟炸。
💡 實務上：上線前用真的信箱走一遍重設流程
很多問題只有在真實寄信時才會出現。公司信箱的安全掃描常會先自動打開信裡的連結檢查，所以打開重設頁（GET）只能驗 token、不能把它用掉，真正作廢要等送出新密碼（POST）。郵件服務的「點擊追蹤」會把連結改寫成經過它們網域的轉址網址，token 就經過了第三方，驗證信和重設信這類交易信建議關掉追蹤。上線前用 Gmail、Outlook 和公司信箱各收一次，確認連結網域是 APP_URL、重設完再點同一個連結會失敗、舊信的連結已失效。

到這裡，忘記密碼這條路守住了：token 猜不到、偷不到、舊信沒用、連結只指向自己的網域、改完把所有人踢出去。但這整條路的安全都建立在一個前提上：重設信寄到的那個 email，真的是王小明的。如果攻擊者能把帳號上的 email 換成自己的，以後每一封重設信都會寄給他。

拿到 session 的人，能不能改 email 把帳號搶走？

假設攻擊者用某種方式拿到了王小明已登入的 session：王小明在門市的公用平板忘了登出，或是第 7 課的 XSS 讓攻擊者能借王小明的瀏覽器發請求。session 會過期，王小明重設密碼時也會把所有 session 踢掉（上一節的 destroyAllForUser），所以這個入口是暫時的。攻擊者想把暫時的權限變成永久的，最直接的做法就是改 email。email 是忘記密碼的終點，改成自己的信箱，等於拿到以後所有的重設權，王小明自己反而再也重設不回來。

第一版的改 email 只要已登入就能改，這正是攻擊者要的。正確的做法有三道關卡：

  1. 重新驗證（re-authentication）：要求使用者當場再證明一次自己是本人，再輸入一次密碼或用 passkey，有 MFA 的帳號要過 MFA（第 14 課的 step-up）。session 只能證明「這個瀏覽器之前登入過」，不能證明「現在坐在螢幕前的是本人」，所以只靠 session 不能做這種改不回來的事。
  2. 寄確認信到新 email：點了連結才真的改。證明使用者擁有新信箱，也避免打錯字把帳號綁到別人的信箱。
  3. 通知舊 email：「你的帳號 email 正在被改成 c***@example.com，如果不是你，請點這裡」。這個「不是我」的連結要能取消變更，並引導使用者重設密碼、登出所有裝置。

三道關卡各擋一件事：重新驗證擋住「只有 session」的攻擊者；確認新信箱擋住打錯字，也擋住把帳號綁到不屬於自己的信箱；通知舊信箱是最後一道保險，就算前兩關都被突破，真正的主人還有機會喊停。

改 email 不是唯一要這樣處理的操作。凡是「做了之後，攻擊者能長期佔住帳號、本人很難救回來」的操作，都要重新驗證並通知本人：改密碼（要輸入舊密碼）、關閉 MFA、新增或刪除 passkey、產生新的復原碼、加入新的付款方式。實作上可以在 session 記一個 reauthenticatedAt，敏感端點檢查它在最近幾分鐘內（例如 5～10 分鐘，這是本課的建議值，不是標準規定），過了就要求再驗一次。

email 為什麼要先驗證過才算數？

前面一直把「收得到信」當成身分證明，這有一個前提：帳號上的 email 確實屬於這個人。註冊時填的 email 只是使用者打的一串字，沒驗證過之前，不能當成「這個人擁有這個信箱」。不驗證會出兩種事：有人可以先用王小明的 email 註冊，等王小明本人來註冊時，帳號已經被占走；用第三方登入（第 13 課）合併帳號時，攻擊者也能拿一個沒驗證過的 email 去接上別人的帳號，所以合併時只能信任雙方都驗證過的 email。

email 驗證的做法：註冊後寄一封含 token 的信，點了才把 email_verified_at 填上。它也是一種 magic link，token 的做法跟重設密碼一樣（32 bytes、只存 SHA-256、單次、有期限、重寄時舊的作廢）。改 email 的第 2 道關卡「寄確認信到新 email」，其實就是對新信箱再做一次 email 驗證。

到這裡，旁門都上了鎖：列舉查不出會員，重設連結拿不到，email 改不掉。攻擊者剩下最直接的一條路：拿著那一百萬組外洩的帳密，直接打登入端點。

攻擊者直接猜密碼，怎麼擋又不誤傷會員？

對登入的猜測攻擊有三種，差別在「對幾個帳號、用什麼密碼」。先分清楚，因為每一種需要的防線不同：

攻擊做法只鎖帳號擋得住嗎只限 IP 擋得住嗎
暴力破解（brute force）對一個帳號試很多密碼擋得住攻擊者換 IP 就擋不住
密碼噴灑（password spraying）對很多帳號各試少數常見密碼（例如每個帳號只試 Password123），避開單一帳號的限制擋不住：每個帳號只錯一兩次來源集中時擋得住
撞庫（credential stuffing）拿別的網站外洩的 email＋密碼組合來試，每組只試一次擋不住：每個帳號只錯一次來源集中時擋得住

我們的攻擊者拿著外洩清單，做的是表中的撞庫。王小明開了 MFA，撞庫拿不下他；但同一份清單拿去打全站，沒開 MFA、又在別處用過同一組密碼的會員就會被拿下，所以登入端點仍然要擋。表格最後兩欄看得出來，帳號和 IP 兩種限制各有擋不住的攻擊，所以兩邊都要有。IP 限制的弱點在於攻擊者常用殭屍網路（botnet）：被控制的大量電腦、路由器、手機，可以從成千上萬個 IP 同時發請求，每個 IP 只送幾次。所以 IP 限流擋得住「一台電腦狂打」，擋不住分散的攻擊。反過來，同一個 IP 也可能是很多正常人，公司、學校、行動網路的出口常是好幾百人共用一個 IP，所以 IP 的上限不能設太低。

第一版的「錯 5 次永久鎖住」錯在哪？

失敗太多次就禁止登入，叫做帳號鎖定（account lockout）。直覺上最安全，但第一版「連續錯 5 次永久鎖住」會被反過來利用：攻擊者故意對每位會員各輸入 5 次錯密碼，全店的會員都登不進來，客服電話被打爆。這是一種阻斷服務（denial of service），讓正常使用者用不了服務的攻擊，而且攻擊者不需要知道任何密碼。前面說「只鎖帳號擋得住暴力破解」，代價就在這裡：它同時擋住了真正的主人。

比較好的做法是逐步延遲（progressive delay，也叫 backoff）：失敗越多次，下一次能嘗試的時間越晚，而且有上限。例如連續失敗 5 次後開始等 1 秒，之後每多一次加倍，最多 15 分鐘。正常使用者打錯幾次幾乎感覺不到；攻擊者對一個帳號一天只能試大約一百次，想鎖住別人的人，也只能讓對方最多等 15 分鐘。NIST SP 800-63B-4 也規定：同一個帳號連續失敗的次數上限不能超過 100 次，超過就要有限制。

要疊哪幾層？

沒有單一措施擋得住全部，要疊起來用，每一層擋前面那張表裡的一種攻擊：

  • 每帳號逐步延遲：擋暴力破解。登入成功一次就歸零。
  • 每 IP 限流：擋集中來源的噴灑與撞庫。上限設寬（例如 15 分鐘 100 次失敗）。登入成功不能重設 IP 的計數，否則攻擊者每試 99 次就用自己的帳號登入一次，計數歸零。
  • 全站異常偵測：整體失敗率突然上升（撞庫的特徵）時，提高門檻、要求額外驗證（第 25 課）。
  • 外洩密碼檢查（第 3 課）：註冊與改密碼時就擋掉別處外洩過的密碼，撞庫自然沒效。
  • MFA 與 passkey（第 14、15 課）：密碼猜對了也進不來。

失敗次數要怎麼算、算在哪裡？

「每 IP 限流」的意思是限制一段時間內的次數（rate limiting），要決定「一段時間」怎麼切。最簡單的演算法是固定視窗（fixed window）：從第一次失敗開始算 15 分鐘，視窗內每次失敗加 1，到上限就擋到視窗結束，視窗結束後重新計數。練習 3 的 IP 限流就用它。它有一個已知的缺點，其他演算法也各有取捨，細節見課末「補充與查表」。

計數要放在哪裡？咖啡店的 API 部署了三台伺服器時，如果計數存在各自的記憶體，每台各算各的，上限實際上變成三倍，而且重啟就歸零。所以計數要放在三台都讀得到的共用儲存，最常見的是 Redis：

INCR   login_fail:ip:203.0.113.7          # 加 1，回傳新的值；key 不存在時從 0 開始
EXPIRE login_fail:ip:203.0.113.7 900 NX   # 只在還沒設過期時間時設 900 秒（第一次失敗時）

INCR 是原子操作（atomic）：「讀出、加 1、寫回」一次完成，中間不會被別的請求插隊，所以三台伺服器同時加也不會少算。EXPIRE … NX 每次失敗都送也沒關係，只有第一次會生效，所以視窗從第一次失敗起算；就算某次 INCR 之後伺服器當掉、沒送到 EXPIRE，下一次失敗也會補上。NX 的版本需求，以及 NestJS 現成的限流套件在多台部署時要注意什麼，見課末「補充與查表」。

被擋下的請求要回什麼？

流程上，限流要包在密碼驗證外面：先問限流能不能試，能試才驗密碼，驗完再把結果記回去。被擋時回 HTTP 狀態碼 429 Too Many Requests（請求太多），並用 Retry-After 標頭告訴客戶端幾秒後再試：

check(email, ip)            → 被擋：回 429 Too Many Requests，Retry-After: 秒數，不驗密碼
verify password             → 錯：recordFailure(email, ip)，回「email 或密碼不正確」
                            → 對：recordSuccess(email, ip)，繼續 MFA、建立 session

被擋時回 429，會不會又讓攻擊者分辨出帳號存不存在，回到第二節的問題？不會。延遲是依「登入時輸入的帳號字串」計算，不管它存不存在，計數都一樣，被擋的時機也一樣。這也是練習 3 用 account 字串當 key 的原因。

💡 實務上：先看現有的工具已經擋了哪些
實務上很少全部自己寫：很多網站前面會擋一層 CDN 或雲端 WAF，WAF 是網站應用程式防火牆，專門過濾惡意的 HTTP 請求，Cloudflare、AWS WAF 都是。它們多半能對登入端點設限流，Auth0、Supabase Auth 這類身分服務也內建了一部分防護。資深工程師會先盤點「哪一層已經擋了什麼」，自己只補缺的那塊，例如每帳號的逐步延遲。上線前也要跟客服、維運講好：會員被擋住時客服看得到什麼、怎麼協助，被限流擋下的請求（上面的 HTTP 429）突然變多時誰會收到警報。公司或學校共用出口 IP 的大量正常使用者，是 IP 上限設太低時最先來客訴的人。

練習 3 會把帳號和 IP 兩層寫成 LoginThrottle。這幾層疊起來還是有漏的時候：沒開 MFA 的會員，密碼剛好在清單裡，攻擊者第一次就猜對，限流一次都不會觸發。最後一個問題是：漏掉的時候，誰會知道？

擋不住的時候，誰會知道？

前面每一節都在擋，這一節處理擋不住之後。目標是讓兩方盡快知道出事了：帳號的主人，和你。前面其實已經出現過幾次：重設密碼後的通知信、改 email 時寄給舊信箱的信。把它們整理成一套規則：

  • 通知本人：新裝置或新地點登入、密碼變更、email 變更（通知舊的）、MFA 或 passkey 新增移除。每封都附「不是我」的處理方式。這些通知常是使用者發現帳號被盜的唯一管道：王小明收到「新裝置登入」的信，比他下次想用儲值金時才發現被花光，早了好幾天。
  • 寫稽核紀錄（audit log）：稽核紀錄是一份事後查得到「誰在什麼時候做了什麼」的紀錄。登入成功與失敗、重設申請與完成、限流觸發，都記下時間、帳號、IP、User-Agent、結果。不要記密碼、token 原文。第 25 課會用這些紀錄做偵測與事故調查。

回到開場的審查。第一版的每一個問題，現在都有對應的修法：「查無此 email」改成一律相同的訊息、時間也對齊；重設連結的 token 只存雜湊、單次、短期限，網址用 APP_URL；改 email 要重新驗證、確認新信箱、通知舊信箱；永久鎖定改成逐步延遲加 IP 限流；擋不住的部分靠通知和紀錄補上。接下來的練習，把其中三段寫成程式。

固定視窗的缺點與其他演算法

固定視窗在視窗交界時，能在短時間內打出兩倍的量：前一個視窗的最後幾秒打滿上限，下一個視窗的頭幾秒又打滿一次。這個缺點和其他演算法的取捨，在系統設計課第 10 課。

Redis 的 EXPIRE … NX

EXPIRE 的 NX 選項要 Redis 7.0 以上。

@nestjs/throttler 在多台部署時

NestJS 課第 6 課用過的 @nestjs/throttler（6.7.1）預設的儲存 ThrottlerStorageService 就是單一程序的記憶體，官方說明它不能跨實例協調，部署多台時要換成共用的儲存（例如 Redis）。另外它用 req.ip 認人，在反向代理後面要設好 Express 的 trust proxy，否則所有人都是代理的那一個 IP。

練習

練習 1：讓登入的回應和時間不洩漏帳號狀態。完成 login(email, password, deps)：

  • 使用者不存在、帳號已停用（disabled: true）、密碼錯誤，都回 { ok: false, error: 'invalid_credentials' }。
  • 每一種情況都剛好呼叫一次 deps.hasher.verify：使用者不存在時用 DUMMY_HASH 驗證。
  • 密碼正確且帳號沒停用時回 { ok: true, userId }。

練習 2：完成 PasswordResetService。sha256、randomToken 已經寫好（第 2 課）。

  • request(email, hostHeader)：不管 email 存不存在，都回 { message: MESSAGE }。使用者存在時：作廢這位使用者其他還沒用過的 token，產生 32 bytes 的新 token，tokens 裡只存它的 SHA-256（key）和 { userId, expiresAt, usedAt: null }，期限 30 分鐘，然後寄信，內容包含 ${config.appUrl}/reset?token=…。hostHeader 是請求帶來的 Host，不能拿來組連結。
  • reset(token, newPassword)：token 不存在、用過、到期（now() >= expiresAt）都回 false。有效時：用 hasher.hash 存新密碼、把 token 標記為已使用、呼叫 sessions.destroyAllForUser(userId)，回 true。

練習 3：寫 LoginThrottle，登入流程在驗密碼前呼叫 check，驗完呼叫 recordFailure 或 recordSuccess。now() 回傳毫秒。規則：

  • 每帳號：連續失敗 n 次（n ≥ 5）後，要從最後一次失敗起等 2n−5 秒才能再試，最多 900 秒。也就是 5 次後等 1 秒、6 次後 2 秒、7 次後 4 秒……。這個帳號登入成功一次就歸零。
  • 每 IP：固定視窗，從這個 IP 視窗內的第一次失敗起算 15 分鐘，視窗內累積 100 次失敗就擋到視窗結束；視窗結束後重新計數。登入成功不會重設 IP 的計數。
  • check 被擋時回 { allowed: false, retryAfterSeconds }，秒數無條件進位；帳號和 IP 都被擋時取比較久的那個。

練習 4：產品經理說：「登入失敗時告訴使用者『這個 email 尚未註冊』，他就知道要去註冊，體驗比較好。」怎麼回應？

✓ 帳號列舉讓攻擊者只對確定存在的帳號撞庫、只對真的會員寄釣魚信。真正的使用者不需要在畫面上看到答案：忘記密碼會收到信、重複註冊會收到「你已經有帳號」的信。a 忽略了「有沒有註冊」本身就能被利用；b 只是換一個頁面洩漏，攻擊者會改打忘記密碼的端點。

練習 5：為了擋暴力破解，系統設成「同一個帳號連續輸錯 5 次就永久鎖住，要打電話給客服解鎖」。攻擊者最可能怎麼利用？

✓ 永久鎖定把「擋攻擊」變成「任何人都能讓別人登不進去」的阻斷服務。改用逐步延遲並設上限（例如最多 15 分鐘），再加上 IP 限流、MFA。a 只看到單一帳號的猜測，沒想到鎖定本身能被別人觸發；c 錯在鎖定是記在帳號上的，換 IP 一樣登不進去，這正是它擋得住暴力破解的地方，問題在它也擋住了真正的主人。

練習 6：重設密碼信裡的連結用 `https://${req.headers.host}/reset?token=${token}` 產生，伺服器在反向代理後面。問題在哪？

✓ 請求能到你的伺服器，是靠 DNS 和 IP，不是靠 Host 標頭的內容；很多代理和伺服器設定會把不認得的 Host 也轉進來，所以 b 錯。X-Forwarded-Host 一樣是客戶端能偽造的標頭，c 錯。信裡的網址要用設定好的 APP_URL。

常見錯誤

  • 錯誤訊息洩漏帳號是否存在：「查無此 email」「帳號已停用」。登入、忘記密碼、註冊都回一樣的訊息，細節寄到 email。
  • 回應時間洩漏帳號是否存在：使用者不存在時不跑慢雜湊、存在時同步寄信。用假雜湊跑一次驗證，寄信放進佇列。
  • 重設 token 存明文、可重複使用、期限太長、舊的不作廢：32 bytes CSPRNG、只存 SHA-256、單次、30 分鐘左右、新申請時作廢舊的。
  • 用 Host 或 X-Forwarded-Host 標頭產生信裡的連結：token 會被送到攻擊者的網域。用設定的 APP_URL。
  • 重設密碼後沒讓 session 失效：已經登入的攻擊者繼續用。呼叫 destroyAllForUser，撤銷 refresh token。
  • 重設後自動登入：多一條跳過 MFA 與登入檢查的路。導回登入頁。
  • 改 email 不需要重新驗證、也不通知舊 email：拿到 session 的人就能永久接管帳號。重新驗證、確認新信箱、通知舊信箱並附「不是我」。
  • 只做帳號鎖定：攻擊者能把所有人鎖住。逐步延遲加上限。
  • 只做 IP 限流：殭屍網路分散來源就擋不住。帳號與 IP 兩邊都要。
  • 登入成功時重設 IP 計數：攻擊者用自己的帳號登入一次就歸零。IP 計數只看時間視窗。
  • 登入嘗試計數只存在單台伺服器的記憶體：部署多台後每台各算各的，重啟就歸零。放在 Redis 這類共用儲存。
  • 客服重設流程沒有確認身分：冒充本人、編故事騙客服幫忙，這種手法叫社交工程（social engineering），最常走這條路。客服的重設要跟線上流程一樣強，例如只能觸發寄到已驗證 email 的重設信。

小結

  • 每個帳號流程都是一個登入入口，帳號的安全取決於最弱的那一條。審查每條路都問：它要使用者證明什麼、強度有沒有比登入弱；重設密碼、改 email、客服流程都不能低於登入。
  • 攻擊者第一步是篩出誰是會員。不洩漏帳號存在：訊息一致（細節寄到 email）、時間一致（不存在也跑假雜湊、停用檢查放在驗證之後、寄信進佇列）。
  • 重設連結是一把臨時密碼：32 bytes CSPRNG、只存 SHA-256、單次、短期限、新申請作廢舊的；連結用 APP_URL；重設頁 Referrer-Policy: no-referrer；成功後所有 session 失效、寄通知、不自動登入。
  • email 是重設的終點，所以要先驗證才算數；改 email、改密碼、關 MFA 要重新驗證，改 email 還要確認新信箱並通知舊信箱。
  • 擋猜測攻擊要疊加：每帳號逐步延遲（有上限，不永久鎖）、每 IP 限流（成功不重設）、異常偵測、外洩密碼檢查、MFA；NIST 要求連續失敗上限不超過 100 次；計數放在共用儲存。
  • 防線一定有漏的時候：重要變更都通知本人，登入與帳號事件寫進稽核紀錄。
