階段 4：更多登入方式：第三方、多因素與機器 · 第 15 課

Passkey：用公鑰取代密碼

第 14 課的 TOTP 擋得住「只拿到密碼」的攻擊者，擋不住釣魚：王小明在假的咖啡店登入頁輸入密碼和 6 位數驗證碼，假網站立刻把兩樣東西轉送到真網站，30 秒內就登入成功。問題出在密碼和驗證碼都是「一串可以照抄的字」，使用者分不出網址，字串也不知道自己被送到哪裡。

這課的任務是替咖啡店的會員系統加上 passkey 登入，讓同樣的釣魚對王小明無效。做法的核心是：王小明的裝置保管一把私鑰，登入時對「伺服器給的隨機值＋瀏覽器看到的網址」簽章，伺服器只存公鑰。整課一路推到最後一關：伺服器收到一個登入回應，要能判斷該不該讓這個人登入，練習 3 會讓你親手寫出這段驗證程式。

這課的路線：
  1. 為什麼密碼和 OTP 轉送得了、passkey 轉送了也沒用（第 1 節，開場問題的最小答案）。
  2. 註冊與登入兩個儀式：王小明的裝置、瀏覽器和咖啡店伺服器之間來回傳了什麼，伺服器要存什麼（第 2、3 節）。
  3. 讀懂登入回應並逐項檢查：authenticatorData 這串位元組怎麼拆、伺服器照什麼順序檢查、challenge 存在哪（第 4、5 節，對應練習 1–3）。
  4. 換手機、掉手機與上線順序：同步與裝置綁定的 passkey、帳號復原、既有會員怎麼逐步改用 passkey（第 6、7 節）。
這課會用到：
  • 第 8 課的 ECDSA P-256：私鑰簽、公鑰驗；Web Crypto 的簽章是 r、s 兩個數字各 32 bytes 接起來，共 64 bytes。
  • 第 2 課的 SHA-256 與 base64url：SHA-256 把任意資料變成 32 bytes 的雜湊；base64url 把位元組轉成能放進 JSON、網址的字串。
  • 第 4 課的 session：登入狀態存在伺服器、用 cookie 裡的 ID 找回來；這課的 challenge 也存在 session 裡。
  • Node 課第 11 課的位元組操作：大端序（big-endian，高位的 byte 放前面）、readUInt32BE 讀 32-bit 無號整數。

為什麼密碼和 OTP 轉送得了，什麼東西轉送了也沒用？

先看密碼和 OTP 為什麼會輸。伺服器驗證它們時只問一件事：「送來的字串對不對？」字串本身不記得自己是在哪個網站被輸入的，誰拿到誰就能用。假網站只要站在中間，把王小明輸入的東西原封不動轉給真網站，真網站看到的就是正確的密碼加上正確的驗證碼，沒有理由拒絕。整套防線最後只剩王小明自己看出網址不對，而做得逼真的釣魚頁面，正好讓這件事很難做到。

所以要擋釣魚，登入時送出的東西要同時滿足兩個條件：

  1. 不是可以照抄重用的秘密。這靠第 8 課的公鑰密碼學：私鑰簽章、公鑰驗章，只拿到公鑰簽不出任何東西。每次登入都對伺服器新給的隨機值簽章，就算某一次的簽章被錄下來，下一次也用不上。
  2. 帶著「這是在哪個網站產生的」，而且這個資訊不能由網頁自己說。網頁的 JavaScript 是假網站寫的，它想填什麼網址都可以；只有瀏覽器知道目前分頁真正的網址，所以要由瀏覽器把網址寫進要簽的資料。

把這兩個條件做成各家瀏覽器、作業系統都支援的標準，就是 passkey。往下讀之前，先認識會一直出現的四個名詞。

認證器（authenticator）是產生並保管私鑰、替使用者簽章的東西。它可以是手機或筆電內建的安全晶片（解鎖方式是 Touch ID、Windows Hello 這類），可以是插在 USB 上的安全金鑰，也可以是密碼管理工具。私鑰在認證器裡產生，之後網頁和伺服器都碰不到它。

passkey 是認證器裡為某一個網站產生的一組金鑰對（中文也譯作「通行密鑰」，Google 的中文介面稱「密碼金鑰」）。王小明在咖啡店建立 passkey，意思是他的 iPhone 為咖啡店產生一組金鑰對，私鑰留在 iPhone，公鑰交給咖啡店。

WebAuthn（Web Authentication API）是網頁使用 passkey 的瀏覽器 API，由 W3C 制定規格。前端只會用到兩個函式：navigator.credentials.create() 建立 passkey，navigator.credentials.get() 用 passkey 登入。這課寫到「§7.2」這類章節編號，指的都是 WebAuthn 規格（版本見課末「補充與查表」）。

RP（Relying Party，依賴方）是讓使用者用 passkey 登入的網站，叫「依賴方」是因為它依賴認證器的簽章來判斷來的人是誰。這課的 RP 就是咖啡店。每把 passkey 建立時都會記下一個 RP ID：這把 passkey 屬於哪個網域，例如 coffee.example。

有了這些名詞，passkey 怎麼滿足上面兩個條件，可以拆成三件事：

  1. 認證器只替對應的 RP ID 簽章：每把 passkey 建立時就記下 RP ID。王小明在 coffee-login.example 上按登入，瀏覽器只會找 RP ID 是 coffee-login.example（或它的上層網域）的 passkey，咖啡店的那把根本不會出現在選單裡。
    你可能會問：options 是假網站自己的 JavaScript 送出的，它不能直接把 rp.id 填成 coffee.example，把咖啡店那把 passkey 叫出來嗎？不行。RP ID 雖然由網頁在 options 裡指定，瀏覽器會先檢查它：必須等於目前網址的網域，或是它的上層網域（registrable domain suffix）。在 coffee-login.example 上指定 coffee.example，瀏覽器直接以 SecurityError 拒絕這次呼叫，根本不會去問認證器。所以這道關卡由瀏覽器守住，不靠網頁自律，和下一點「origin 由瀏覽器填」是同一個道理。
  2. 來源由瀏覽器寫進簽章資料：要簽的資料裡有一段 clientDataJSON，其中的 origin 是瀏覽器自己填的網址，網頁的 JavaScript 改不了。就算假網站想辦法拿到一個簽章，上面寫的也是假網站的來源，真網站驗證時會拒絕。
  3. 伺服器只存公鑰：公鑰只能驗章、不能簽章。資料庫外洩，攻擊者拿到的東西不能拿來登入，也沒有可以離線暴力破解的密碼雜湊。

這就是開場問題的最小答案：如果王小明用的是 passkey，假網站上根本叫不出咖啡店的那把；退一步說，就算假網站拿到一個簽章，裡面寫的網址也是它自己的，轉送到真網站只會被拒絕。整個過程不需要王小明看懂網址。

passkey 也是一種多因素認證：裝置是「你擁有的東西」，解鎖裝置用的指紋或 PIN 是「你本人」或「你知道的東西」。指紋只在裝置上比對，伺服器只收到「使用者已驗證」這一個位元，收不到任何生物特徵（WebAuthn §14.3）。

不過上面每一件事都還有「怎麼做到」：私鑰什麼時候產生、公鑰怎麼交到咖啡店手上、伺服器怎麼確定簽章是剛剛簽的而不是錄下來的。先從王小明第一次建立 passkey 開始看。

王小明第一次建立 passkey，發生了什麼？註冊儀式

王小明已經用密碼登入咖啡店，在帳號設定頁按下「新增 passkey」。從這一刻起，瀏覽器、認證器、伺服器三方會照固定的步驟一來一回，WebAuthn 把這種流程叫做儀式（ceremony）。儀式有兩種：註冊（registration）建立 passkey，驗證（authentication）用 passkey 登入。這一節講註冊，下一節講登入。

兩種儀式都從伺服器產生的 challenge 開始。challenge 是伺服器每次新產生的一次性隨機值。為什麼需要它？簽章只證明「有私鑰的人簽過這段資料」，不證明「是剛剛簽的」。如果每次要簽的資料都一樣，攻擊者只要錄下某一次的回應，之後原封不動重送就能過關，這種攻擊叫重放（replay）。讓認證器把伺服器這次新給的隨機值一起簽進去，伺服器再比對「回應裡的 challenge 是不是我剛剛發出去的那個」，錄下來的舊回應就失效了。challenge 要存在哪、什麼時候作廢，第 5 節會講。

圖裡的第 1 步，伺服器產生 challenge 存進王小明的 session，再回給前端一份 options；前端（例如 Vue 元件）把它原樣交給 navigator.credentials.create()。下面是這份 options 的 JSON 版本，二進位欄位用 base64url：

{
  "rp": { "id": "coffee.example", "name": "咖啡店" },
  "user": { "id": "隨機產生的 user handle（base64url）", "name": "amy@example.com", "displayName": "王小明" },
  "challenge": "32 bytes 隨機值（base64url）",
  "pubKeyCredParams": [
    { "type": "public-key", "alg": -7 },
    { "type": "public-key", "alg": -257 }
  ],
  "authenticatorSelection": { "residentKey": "required", "userVerification": "preferred" },
  "excludeCredentials": [{ "type": "public-key", "id": "這個人已經註冊過的 credential ID" }],
  "attestation": "none",
  "timeout": 300000
}

每個欄位都在回答一個設計問題，依序看：

  • rp：這把 passkey 屬於哪個網站。id 就是第 1 節的 RP ID，name 是顯示給使用者看的名稱。
  • user：這把 passkey 屬於哪個帳號。name、displayName 是讓王小明在選單裡認得出自己的帳號；user.id 則叫 user handle，會存在認證器裡，登入時跟著回應送回來，讓伺服器找到是哪個帳號。它最多 64 bytes，規格規定不能放 email、帳號這類個資（§5.4.3），因為它存在認證器裡，伺服器管不到它被誰看見。所以用隨機值，再在資料庫裡記下它對應哪個使用者。
  • challenge：上面講的一次性隨機值。
  • pubKeyCredParams：伺服器接受哪些簽章演算法。WebAuthn 傳遞金鑰和簽章用的是二進位格式，不是 JSON：CBOR 是一種結構類似 JSON、但用位元組表示的格式；COSE 是建立在 CBOR 上的標準，規定金鑰、簽章演算法怎麼表示。這裡的數字就是 COSE 的演算法編號：-7 是 ES256，也就是第 8 課的 ECDSA P-256 配 SHA-256；-257 是 RS256。註冊時拿到的公鑰同樣是 COSE 格式，解析交給函式庫（第 5 節）。
  • authenticatorSelection.residentKey: "required"：要求建立可探索憑證（discoverable credential）。一般的憑證要伺服器先知道使用者是誰、把他的 credential ID 列給瀏覽器，認證器才找得到對應的私鑰；可探索憑證則是認證器自己記得「這個網站有哪些帳號」，登入時使用者不用先輸入 email，直接從選單挑帳號。passkey 指的就是這種憑證。
  • excludeCredentials：王小明已經註冊過的 credential ID。認證器如果已經有其中一把，就不會再建一把，避免同一台裝置重複註冊。
  • attestation：認證器附上的出廠證明，用來證明自己是哪個廠牌、哪個型號。只有要限制「只能用公司發的安全金鑰」這類情況才需要；一般網站用預設的 "none"。
  • timeout：300,000 毫秒（5 分鐘）是規格建議的預設值（§15.1），challenge 的有效期也照這個長度。

第 3、4 步，王小明用指紋或 PIN 解鎖 iPhone，認證器產生金鑰對：私鑰留在 iPhone，公鑰和 credential ID 交給瀏覽器。credential ID 是認證器替這把 passkey 取的識別碼，之後每次登入都會一起送回來，伺服器靠它找到該用哪一把公鑰驗章。第 5、6 步，伺服器收到回應，確認 challenge、origin、RP ID 都對（跟登入時的檢查是同一套想法，第 5 節細講），通過後為這把 passkey 存一筆 credential 紀錄：

CREATE TABLE passkeys (
  id              bytea PRIMARY KEY,      -- credential ID（認證器給的）
  user_id         bigint NOT NULL REFERENCES users(id),
  public_key      bytea NOT NULL,         -- COSE 格式的公鑰
  sign_count      bigint NOT NULL,        -- 32-bit 無號整數，integer 裝不下
  transports      text[],                 -- usb、internal（內建）、hybrid（用手機掃 QR code）…，下次登入給瀏覽器當提示
  backup_eligible boolean NOT NULL,       -- 註冊當時的 BE，之後不會變
  backup_state    boolean NOT NULL,       -- 最近一次的 BS
  name            text,                   -- 讓使用者辨認：「iPhone」「辦公室的安全金鑰」
  created_at      timestamptz NOT NULL DEFAULT now(),
  last_used_at    timestamptz
);

一個使用者可以有很多把 passkey（手機、筆電、安全金鑰各一把），所以 users 對 passkeys 是一對多。帳號設定頁要列出它們，讓使用者能改名、刪除。sign_count、backup_eligible、backup_state 這三欄存的是認證器每次登入都會報上來的狀態，現在先記住欄位名稱；第 4 節拆開 authenticatorData 時，會講每一欄是什麼、為什麼要存。

💡 實務上：RP ID 一旦上線就很難改
RP ID 在註冊時就跟每一把 passkey 綁在一起。之後網站換網域（例如品牌改名，從 coffee.example 搬到別的網域），舊的 passkey 全部不能用，使用者只能先用別的方式登入再重新註冊。所以 RP ID 通常設成主網域 coffee.example，不是 login.coffee.example，這樣 app.、admin. 這些子網域都能共用同一把 passkey。staging 這類測試環境用自己的網域和 RP ID，不跟正式環境混用；本機開發可以直接用 localhost。資深工程師會在設計階段就問 PM 和維運：「之後有沒有換網域或拆子網域的計畫？」

公鑰存好了。下次王小明回來登入，伺服器手上只有這把公鑰，它要拿公鑰驗的到底是「什麼東西」？

下次登入，王小明的裝置簽了什麼？登入儀式

登入時伺服器再產生一個新的 challenge（註冊用的那個已經作廢），前端拿它呼叫 navigator.credentials.get()。瀏覽器列出 RP ID 符合目前網域的 passkey，王小明選了自己的帳號、用指紋解鎖（登入頁怎麼讓 passkey 直接出現在瀏覽器的自動填入選單，是前端的細節，見課末「補充與查表」）。接下來要簽的資料由瀏覽器和認證器各準備一半：

  1. 瀏覽器準備 clientDataJSON：一段 JSON，內容是 type（登入時是 "webauthn.get"，註冊時是 "webauthn.create"）、challenge、origin。這段由瀏覽器自己填，網頁的 JavaScript 改不了，第 1 節說的「來源由瀏覽器寫進簽章資料」就是在這裡發生。
  2. 認證器準備 authenticatorData：認證器自己產生的一串位元組，裡面有 RP ID 的 SHA-256、幾個旗標（例如使用者有沒有在場、有沒有驗證過本人）和一個簽章計數器。第 4 節會逐段拆開。
  3. 認證器簽章：簽的是 authenticatorData || SHA-256(clientDataJSON)。|| 是「把兩段位元組前後接起來」的寫法，所以要簽的是 authenticatorData 原文，後面接上 clientDataJSON 的雜湊，不是兩段原文直接接起來。

瀏覽器把 clientDataJSON、authenticatorData、signature 和 credential ID 交給前端，前端送到伺服器。伺服器用 credential ID 找出註冊時存的公鑰，再自己把 authenticatorData || SHA-256(clientDataJSON) 接一次來驗章。

現在可以回頭驗證第 1 節的說法：釣魚網站拿到的簽章，到了真網站到底會怎樣？練習區的程式跑在 Worker 裡，沒有 navigator.credentials，也沒有真的認證器，所以下面用 Web Crypto 模擬：產生金鑰對、組 clientDataJSON 與 authenticatorData、簽章，再讓伺服器端檢查四項。執行後比較兩行結果裡哪幾項是 false：

真網站四項都是 true。釣魚網站那一行，signature 也是 true：簽章本身有效，用的確實是王小明那把私鑰；challenge 也對，因為假網站可以先向真網站要一個 challenge 再交給受害者。會露出破綻的只有 origin 和 rpIdHash。所以只驗簽章不夠，伺服器的工作不是「驗一個簽章」，而是逐項比對回應裡的每個欄位。

其中 origin、challenge 在 clientDataJSON 裡，是 JSON，JSON.parse 就讀得到；rpIdHash 和旗標則在 authenticatorData 這串位元組裡，伺服器得先會拆它，才談得上檢查。

authenticatorData 這串位元組裡寫了什麼？

上一節模擬用的是最短的 authenticatorData：37 bytes，固定分成三段。伺服器要確認 RP ID、確認使用者在場、偵測金鑰被複製，資料都從這三段讀出來：

第一段 rpIdHash（位置 0～31）是 RP ID 的 SHA-256，記錄認證器是替哪個網站簽的。伺服器自己算一次 SHA-256('coffee.example') 來比對；上一節釣魚的例子，就是這一項對不上。

第二段 flags（位置 32）只有 1 個 byte，也就是 8 個 bit，每個 bit 回答一個是非題。登入時最常看的是 UP 和 UV；BE、BS 跟 passkey 能不能同步有關，第 6 節會用到；AT、ED 只在註冊或使用擴充功能時出現。下表查表用，不用背：

旗標位元意思
UP（User Present）bit 0（0x01）使用者在場：有人碰了裝置或按了確認。登入時一定要是 1。
UV（User Verified）bit 2（0x04）使用者驗證過身分：指紋、臉、PIN。要求 UV 時才檢查。
BE（Backup Eligible）bit 3（0x08）這把金鑰能被同步備份（例如存在 iCloud 鑰匙圈）。註冊後不會變。
BS（Backup State）bit 4（0x10）這把金鑰目前已經備份。BE 是 0 時 BS 不可能是 1。
AT（Attested credential data）bit 6（0x40）後面接著新金鑰的資料（註冊時）。
ED（Extension Data）bit 7（0x80）後面接著擴充功能的資料。

UP 和 UV 的差別要分清楚：UP 只代表「有人在裝置前面碰了一下」，UV 才代表「認證器確認了這個人是裝置的主人」。註冊時 options 裡的 userVerification 是伺服器的要求，實際有沒有驗，要看這次回應的 UV。

第三段 signCount（簽章計數器）（位置 33～36）是認證器每簽一次就增加的 32-bit 無號整數，用大端序存。它的用途是偵測金鑰被複製：正常情況下私鑰只存在一個認證器裡，數字只會往上加；萬一私鑰被複製到第二個認證器，兩邊各自從自己的數字往上加，伺服器每次記下收到的最新值，遲早會收到一個沒有比上次大的數字。會同步的 passkey 通常不實作計數器，一直回 0（規格寫明「沒有實作計數器的認證器固定給 0」），第 5 節的檢查規則必須照顧到這種情況。

讀這三段會用到兩個 JavaScript 細節：怎麼從 flags 取出某一個 bit，以及怎麼把 4 bytes 讀成一個數字。下面這格兩件事都做，執行後特別看最後兩行：同樣的 4 bytes，讀出兩個不同的數字。

前半段用到兩個位元運算子：1 << n（左移）把 1 往左移 n 位，得到「只有第 n 位是 1」的數字，例如 1 << 2 是 0b100（4）；a & b（位元 AND）只留下兩邊都是 1 的位元。所以 flags & 0x04 不是 0，就代表 bit 2 是 1。

後半段的差異來自 JavaScript 的位元運算一律先轉成有號 32-bit 整數，最高位元是 1 時結果就變成負數，所以用 << 和 | 組出來的計數器是負的。DataView.getUint32 讀的是無號整數，第二個參數不給就是大端序（第 14 課用過的 setBigUint64 也是）。計數器讀成負數，跟存的值比大小就全錯了。

練習 1 還會遇到第三個陷阱：Uint8Array 只是底層記憶體（buffer，一個 ArrayBuffer）的一個「視窗」。big.subarray(10, 47) 不複製資料，回傳的陣列和 big 共用同一個 buffer，只是從第 10 個 byte 開始看，這個起點記在 byteOffset。new DataView(bytes.buffer) 會從整個 buffer 的第 0 個 byte 開始讀，位置就錯了；要寫 new DataView(bytes.buffer, bytes.byteOffset, bytes.byteLength)。反過來，slice() 會複製出一份新的資料。

能從 authenticatorData 拆出 rpIdHash、旗標和 signCount，伺服器需要的原料就齊了。下一步是決定：這些欄位要照什麼順序檢查、每一項沒過代表什麼。

伺服器收到登入回應，要依序檢查哪幾件事？

第 3 節的釣魚例子說明了只驗簽章不夠，第 4 節讓我們讀得出每個欄位。WebAuthn Level 3 §7.2 把伺服器驗證登入回應的步驟寫成清單；去掉跟擴充功能、iframe 有關的部分，核心是下面這張表，順序照規格。讀的時候重點放在「擋什麼」那欄：每一項都對應一種具體的攻擊或錯誤，正式環境出問題時，你要能從「哪一項沒過」反推發生了什麼。

#檢查擋什麼
1credential ID 屬於這個帳號（可探索憑證：用回應裡的 user handle 找帳號，再確認那個帳號有這把 credential）拿別人的 passkey 登入自己的帳號，或反過來
2clientData.type === 'webauthn.get'拿註冊時的回應（webauthn.create）來登入
3clientData.challenge 等於伺服器存的 challenge重放錄下來的回應
4clientData.origin 完全等於預期的來源釣魚網站、別的子網域
5rpIdHash 等於 SHA-256(RP ID)別的網站的 passkey 產生的回應
6UP 是 1；要求 UV 時 UV 是 1沒人在場的簽章；只有「碰一下」卻當成驗證過身分
7BE 是 0 時 BS 也要是 0；有用備份狀態做判斷時，BE 要跟註冊時存的一樣不一致的認證器資料
8用存好的公鑰驗 authenticatorData || SHA-256(clientDataJSON) 的簽章偽造、竄改
9signCount：新值或舊值有一個不是 0，而且新值 ≤ 舊值 → 可能被複製被複製的金鑰
10全部通過後才更新存的 signCount、backup_state、last_used_at失敗的嘗試改到狀態

有兩項需要多說明。第 9 步接著第 4 節的計數器：規格只說倒退是「可能被複製的訊號，不是證明」，要拒絕、只記錄還是要求額外驗證，由網站自己的政策決定。新舊都是 0 時不比較，否則所有同步 passkey 都登不進來。本課的練習採嚴格政策：倒退就拒絕。

第 8 步有一個格式差異：WebAuthn 的 ES256 簽章是 DER 編碼，這是一種「型別、長度、內容」層層包起來的二進位格式，整個簽章大約 70～72 bytes；而 Web Crypto 只收第 8 課的 64 bytes r||s，所以驗章前要先轉換。第 3 節的模擬直接用 Web Crypto 簽，所以印出的是 64 bytes 的 r||s；真的認證器回傳的是 DER，伺服器收到後要先轉。忘記轉換的症狀是「每個人都登不進去」：直接拿 DER 去驗不會報錯，只會回 false。練習 3 會提供現成的 derToRaw；DER 長什麼樣、怎麼轉，見課末「補充與查表」。

這張表就是練習 3 的 verifyAssertion 要照順序實作的內容。正式環境不要自己解析 CBOR、COSE 和 attestation：格式多、邊界情況多，用維護良好的函式庫，例如 @simplewebauthn/server 搭配前端的 @simplewebauthn/browser（版本見課末）。同一張表在函式庫裡變成幾個參數：

// 伺服器（Node）：@simplewebauthn/server 14.0.3
const verification = await verifyAuthenticationResponse({
  response: body,                          // 前端 startAuthentication() 的結果
  expectedChallenge: session.challenge,    // 從 session 取出，用完就刪
  expectedOrigin: 'https://coffee.example',
  expectedRPID: 'coffee.example',
  credential: { id: passkey.id, publicKey: passkey.publicKey, counter: passkey.signCount, transports: passkey.transports },
  requireUserVerification: true,           // 預設就是 true
})
if (verification.verified) {
  // 更新 signCount 與 backup_state 是你的工作，函式庫不會幫你存
  await savePasskey(passkey.id, verification.authenticationInfo.newCounter, verification.authenticationInfo.credentialBackedUp)
}

對照表格看：expectedChallenge 對第 3 項、expectedOrigin 對第 4 項、expectedRPID 對第 5 項、requireUserVerification 對第 6 項，credential 裡的公鑰和計數器對第 8、9 項；第 10 項的「通過後更新」則留在 if 裡由你來做。函式庫處理格式與密碼學；你要負責的是這課講的部分：challenge 存在哪、怎麼作廢，資料表存什麼、登入後更新什麼，origin 和 RP ID 設什麼，以及復原流程。練習 3 讓你親手寫一次整張表的檢查順序，以後讀函式庫的設定和錯誤訊息，才知道它在做什麼。

第 3 項的「伺服器存的 challenge」存在哪、什麼時候作廢？

這幾個參數裡，expectedChallenge 是最容易做錯的一個，因為函式庫只負責比對，challenge 從哪來、存在哪是你的事。規格要求伺服器自己記住發出去的 challenge，不能相信客戶端送回來的值（§13.4.3），並建議至少 16 bytes、有效期跟 timeout 差不多。落到實作是四條規則，每一條都對應一種漏洞：

  • 用 CSPRNG 產生 32 bytes（第 2 課），讓人猜不到。存在這個 session 底下，不是全站共用的集合：如果只檢查「這個 challenge 是不是我發過的」，攻擊者可以拿別人 session 的 challenge 來用。
  • 5 分鐘後失效，跟 options 裡的 timeout 一致。
  • 用一次就刪，不論驗證成功或失敗，錄下來的回應才不能再送一次。同一個 session 重新開始登入時，舊的 challenge 作廢。
  • 多台伺服器時，challenge 跟 session 一樣放在共用的儲存（Redis、資料庫），不然發 challenge 的和收回應的可能是不同台。

練習 2 的 ChallengeStore 就是把這四條寫成程式。

💡 實務上：「大家都登不進去」先查設定
passkey 上線後，很多「登不進去」的回報不是攻擊，而是設定錯：預期的 origin 少了 port 或寫成 http、伺服器在反向代理後面，用請求的 Host 拼出 origin，結果拼成內部位址、多台伺服器的 challenge 各自存在記憶體裡。做法是 origin 和 RP ID 從每個環境的設定讀，不從請求內容推算。驗證失敗時在伺服器 log 記下是哪一項沒過（challenge、origin、rpIdHash、簽章），回給前端的只要一句「登入失敗」。這樣客服轉來「iPhone 登不進去」時，查 log 就分得出是設定問題還是使用者裝置的問題。

到這裡，王小明用同一支 iPhone 登入的流程已經完整。但表裡第 7、9 項都繞著一個還沒回答的問題：passkey 能不能跟著王小明換到新手機？

王小明換手機，passkey 會跟著走嗎？同步與裝置綁定

答案取決於私鑰能不能離開產生它的那台裝置。passkey 依這點分成兩種：

  • 同步 passkey：存在 iCloud 鑰匙圈、Google 密碼管理工具、1Password 這類服務，同一個雲端帳號的所有裝置都拿得到。BE 和 BS 都是 1，signCount 通常一直是 0。王小明換新 iPhone，登入同一個 Apple ID 後 passkey 就回來了。
  • 裝置綁定 passkey：私鑰鎖在那支安全金鑰或那台裝置的晶片裡，複製不出來。BE 是 0，通常有遞增的 signCount。裝置遺失，passkey 就沒了。

這也解釋了第 4 節的兩個現象：同步 passkey 的私鑰本來就會被「複製」到使用者的每台裝置，計數器沒有意義，所以固定給 0；裝置綁定的才有遞增的計數器，第 9 項的複製偵測只對它有用。兩種的取捨：

同步 passkey裝置綁定 passkey
方便新裝置自動可用每台裝置要各自註冊
遺失裝置從雲端帳號取回要靠別的 passkey 或復原流程
風險集中在雲端帳號（Apple ID、Google 帳號）被盜實體裝置被偷且 PIN 被破
複製偵測做不到（計數器是 0）signCount 倒退可以發現
適合一般顧客店長後台、能退款、能改權限的高權限帳號

BE、BS 可以拿來做政策，這就是資料表存 backup_eligible、backup_state 的原因。例如顧客只有一把 BS=0 的 passkey 時，提示他「再加一把，或開啟同步，以免換手機後登不進來」；高權限帳號要求 BE=0 的安全金鑰。一旦用備份狀態做判斷，認證器報上來的 BE 就必須可信，所以 §7.2 規定（表裡第 7 項）：每次登入的 BE 要和註冊時存的一樣。

💡 實務上：顧客用同步 passkey，安全金鑰留給高權限帳號
一般顧客用同步 passkey 就好：換手機不會掉帳號，客服負擔最小。要求實體安全金鑰（BE=0）通常只用在少數帳號，例如咖啡店的店長後台、工程師登入雲端主控台，而且要搭配發放、遺失補發的流程，每人至少兩支。決定之前先問：「這個帳號被盜，最壞會發生什麼事？」如果答案只是「看到自己的訂單紀錄」，強迫顧客買安全金鑰只會讓他們放棄註冊。

同步解決了換手機的問題。但如果王小明唯一的那支手機掉了、passkey 也沒同步，他要怎麼回到帳號？而這條「回到帳號」的路，正是攻擊者接下來會盯上的地方。

passkey 全丟了怎麼辦？帳號復原與導入順序

passkey 擋住了釣魚，攻擊者就會改打帳號復原：如果「忘記 passkey？輸入 email 收連結」就能重設，整個帳號的強度就等於那個 email 連結，前面做的一切都被繞過。所以復原流程的設計原則是不能比登入弱：

  • 鼓勵使用者註冊兩把以上的 passkey（例如手機加筆電），遺失一把還能用另一把登入。這是成本最低的復原方式，帳號設定頁的 passkey 列表就是為此存在。
  • 提供第 14 課的復原碼，只存雜湊、用一次就刪。
  • 復原後通知使用者，並讓其他 session 失效。復原流程本身的設計是第 16 課的主題。

復原流程解決的是已經在用 passkey 的人掉了裝置。同樣的「別把人鎖在門外」也適用在還沒用 passkey 的人：咖啡店既有的密碼會員要怎麼逐步換過來？他們的裝置不一定都支援 passkey，所以導入順序是：先在帳號設定加「新增 passkey」，登入頁同時支援密碼與 passkey；使用者用 passkey 登入過一陣子、確定他的裝置用得順之後，再提示他可以移除密碼。一次全部改掉，沒有支援裝置的使用者會被鎖在門外。

補充與查表

版本備註

  • WebAuthn Level 3 在 2026-08-25 成為正式的 W3C 推薦標準（Recommendation）。本課的章節編號（§5.4.3、§6.5.5、§7.2、§13.4.3、§14.3、§15.1）都指這一版。
  • @simplewebauthn/server：2026-10-31 的最新版是 14.0.3，本課的範例以這一版為準。

FIDO2 與 CTAP

看文件時常會遇到 FIDO2 這個詞：它是 WebAuthn 加上 CTAP 的總稱。CTAP 是「瀏覽器怎麼跟安全金鑰、手機溝通」的協定。寫伺服器的人只會直接碰到 WebAuthn 這一半。

登入頁的 passkey 自動填入

使用可探索憑證時，登入頁可以讓 passkey 出現在瀏覽器的自動填入選單：帳號輸入框寫 autocomplete="username webauthn"，頁面載入時就用 mediation: 'conditional' 呼叫 navigator.credentials.get()。使用者點帳號欄位就看得到「用 passkey 登入」，不用先輸入 email。

ES256 的簽章：DER 轉 r||s

正式環境由函式庫做這個轉換，練習 3 也直接提供 derToRaw。想知道 DER 長什麼樣、要自己處理二進位格式或讀懂函式庫原始碼時再看。

ECDSA 的簽章是兩個數字 r 和 s。第 8 課看過 Web Crypto 和 JWT 的格式：r、s 各補成 32 bytes 直接接起來，共 64 bytes。WebAuthn 不一樣：§6.5.5 規定 ES256 的簽章必須是 ASN.1 DER 編碼。ASN.1 是一套描述資料結構的標準（憑證、金鑰檔都用它），DER 是把它轉成位元組的規則之一。DER 是一種「型別、長度、內容」一層一層包起來的二進位格式：

30 <總長度>
   02 <r 的長度> <r 的位元組>
   02 <s 的長度> <s 的位元組>

30 代表 SEQUENCE（一串東西），02 代表 INTEGER（整數）。DER 的整數是有號的：最高位元是 1 時要在前面補一個 00，不然會被當成負數；前面的 00 又要省略。所以 r、s 的長度不固定（通常是 32 或 33 bytes，數字前面剛好是 0 時更短），整個簽章大約 70～72 bytes。驗章前要轉回 64 bytes 的 r||s：

練習

練習 1：寫 parseAuthenticatorData(bytes)，把 authenticatorData 拆成三個欄位：

  • 長度小於 37 bytes 回傳 null。
  • rpIdHash：前 32 bytes（複製一份）。
  • flags：第 33 個 byte 的 UP（bit 0）、UV（bit 2）、BE（bit 3）、BS（bit 4）、AT（bit 6）、ED（bit 7），每個是 boolean。
  • signCount：接下來 4 bytes，大端序、無號，結果不能是負數。
  • 傳進來的可能是某個大陣列的一段（subarray），byteOffset 不一定是 0。

練習 2：寫 ChallengeStore，管理登入用的 challenge。時間由建構子傳入的 now() 決定（毫秒）。

  • issue(sessionId)：用 CSPRNG 產生 32 bytes，回傳 base64url（43 個字元），綁在這個 session 上，5 分鐘內有效。同一個 session 再呼叫一次，舊的 challenge 作廢。
  • consume(sessionId, challenge)：challenge 必須是這個 session 目前的那一個、還沒過期、還沒用過，才回傳 true。用過就刪，不能用第二次；不論這次對不對都要刪，不然攻擊者可以一直猜。
  • 不同 session 的 challenge 互不影響。

練習 3：寫 verifyAssertion(response, ctx)，照 §7.2 驗證一個 passkey 登入回應。response 的三個欄位都是 base64url，signature 是 DER 編碼的 ES256 簽章。依序檢查，第一個不符合的就回傳對應的錯誤：

  1. 解碼失敗、clientDataJSON 讀不出 type／challenge／origin、authenticatorData 不到 37 bytes → malformed
  2. type 不是 'webauthn.get' → bad_type
  3. challenge 不等於 ctx.expectedChallenge → bad_challenge
  4. origin 不完全等於 ctx.expectedOrigin → bad_origin
  5. rpIdHash 不等於 SHA-256(ctx.rpId) → bad_rp
  6. UP 不是 1 → user_not_present；ctx.requireUV 而 UV 不是 1 → uv_required
  7. BE 是 0 但 BS 是 1，或這次的 BE 跟註冊時存的 backupEligible 不同 → bad_backup_flags
  8. DER 轉不成 r||s（用已經寫好的 derToRaw），或 authenticatorData || SHA-256(clientDataJSON) 的簽章驗不過 → bad_signature
  9. 新舊 signCount 有一個不是 0，而且新值 ≤ 存的值 → counter_regressed（本課的政策：拒絕）

全部通過回傳 { ok: true, newSignCount, backupState }，呼叫端再拿去更新資料庫。不能丟出例外。

練習 4：王小明點了簡訊裡的連結，打開釣魚網站 coffee-login.example，畫面跟咖啡店一模一樣。他按「用 passkey 登入」。會發生什麼事？

✓ passkey 綁定 RP ID，瀏覽器只會列出符合目前網域的 passkey，咖啡店那把在假網站上根本不會出現；簽章裡的 clientDataJSON 帶著瀏覽器填的 origin，伺服器比對不符就拒絕。a 是密碼和 OTP 的情況，不是 passkey。b 錯，防釣魚不靠使用者判斷網址，這正是它比 OTP 強的地方。d 錯，passkey 本身就同時是「擁有的裝置」加上「解鎖裝置的指紋或 PIN」。

練習 5：咖啡店的資料庫外洩，攻擊者拿到 passkeys 表的所有資料（credential ID、公鑰、signCount）。他能用這些登入顧客的帳號嗎？

✓ 這是公鑰密碼學的設計：從公鑰算出 P-256 私鑰在計算上不可行，所以 c 錯。a 錯在把公鑰當成秘密：密碼雜湊外洩後還能離線猜密碼，公鑰外洩沒有東西可猜。還是要處理外洩（其他欄位可能有個資、要查怎麼被入侵的），但不需要讓所有人重設 passkey。

練習 6：咖啡店發現大部分顧客的 passkey，signCount 每次登入都是 0。應該怎麼處理？

✓ WebAuthn 規格寫明，沒有實作計數器的認證器固定給 0，§7.2 也只在「新舊有一個不是 0」時才比較。b 會讓 iCloud 鑰匙圈、Google 密碼管理工具的使用者全部登不進來。c 沒有意義：計數器的用途是比對認證器報的數字，伺服器自己加 1 偵測不到任何複製。

練習 7：顧客問：「用指紋登入咖啡店，我的指紋資料會傳到你們的伺服器嗎？」正確答案是？

✓ 生物辨識在認證器本機進行（WebAuthn §14.3），通過後認證器才用私鑰簽章，並把 UV 設成 1。伺服器收到的是 authenticatorData、clientDataJSON 和簽章，裡面沒有任何生物特徵，也沒有它的雜湊，所以 a、b、c 都錯。伺服器也無從知道使用者用的是指紋、臉還是 PIN。

常見錯誤

  • 只驗簽章：釣魚網站或別的網站的 passkey 產生的簽章也是有效簽章。type、challenge、origin、rpIdHash、UP 每一項都要檢查。
  • origin 用 startsWith、includes 比對：https://coffee.example.evil.example 會通過。用完全相等，或在明確的允許清單裡查。
  • challenge 可以重複使用、沒綁 session、沒有期限：錄下來的回應就能重放。challenge 存在 session 底下，5 分鐘內有效，用一次就刪。
  • 簽章資料沒雜湊 clientDataJSON：簽的是 authenticatorData || SHA-256(clientDataJSON)，不是兩段原文接起來。
  • 用 << 組 32-bit 計數器：最高位元是 1 時會變負數。用 DataView.getUint32。
  • signCount 是 0 就當成錯誤：擋掉所有同步 passkey。新舊都是 0 時不比較。
  • 驗證失敗也更新 signCount：全部檢查通過後才更新 sign_count 和 backup_state。
  • 忘了 DER 轉換，或把 r||s 當 DER：WebAuthn 的 ES256 簽章是 DER，Web Crypto 要 64 bytes 的 r||s。忘了轉的症狀是所有人都登不進來。
  • user handle 放 email 或帳號：它會存在認證器裡，規格禁止放個資。用隨機值。
  • 自己解析 CBOR、COSE 和 attestation：格式多、邊界情況多。用 @simplewebauthn/server 這類維護良好的函式庫，自己負責 challenge、資料表和政策。
  • 復原流程只靠 email 重設：攻擊者改打最弱的入口。讓使用者註冊多把 passkey、提供復原碼，復原後通知並讓其他 session 失效。

小結

  • 密碼和 OTP 是可以照抄的字串，釣魚網站轉送就能用。passkey 是存在認證器裡的金鑰對：私鑰不離開裝置，伺服器只存公鑰，資料庫外洩也沒有能拿來登入的東西。
  • 防釣魚靠兩層：passkey 綁定 RP ID，瀏覽器只在對的網域列出它；簽章資料裡有瀏覽器填的 origin。
  • 兩個儀式都從伺服器的 challenge 開始，用來擋重放。註冊時伺服器存 credential ID、公鑰、signCount、BE／BS；登入時認證器簽 authenticatorData || SHA-256(clientDataJSON)。
  • authenticatorData：rpIdHash（32 bytes）、flags（UP bit 0、UV bit 2、BE bit 3、BS bit 4、AT bit 6、ED bit 7）、signCount（32-bit 大端序，用 DataView.getUint32 讀）。
  • 只驗簽章不夠。伺服器依 WebAuthn Level 3 §7.2 檢查：type、challenge、origin、rpIdHash、UP／UV、BE／BS、簽章（DER 轉 r||s）、signCount（新舊都是 0 不比較），全部通過才更新狀態。
  • challenge：32 bytes CSPRNG、綁 session、5 分鐘、用一次就刪。
  • 正式環境用 @simplewebauthn/server 這類函式庫做格式解析與驗章；你負責 challenge 存哪、怎麼作廢，資料表存什麼、登入後更新什麼，origin 和 RP ID 的設定，以及復原流程。
  • 同步 passkey 方便、不怕遺失，但風險在雲端帳號；裝置綁定的安全金鑰適合高權限帳號。復原流程不能比登入弱；導入時先讓密碼和 passkey 並存。
