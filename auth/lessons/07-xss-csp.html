階段 2：瀏覽器裡的登入狀態：Cookie、Session 與跨站攻擊 · 第 7 課

XSS 與 CSP：前端漏洞怎麼變成帳號被盜

咖啡店的商品頁可以留評論。某天客服轉來一則看起來很普通的評論：「拿鐵很好喝」，後面接著一段 <img src=x onerror=…>。從那天起，每個打開這個商品頁的顧客，瀏覽器都會執行 onerror 裡的 JavaScript。這段程式跑在 shop.coffee.example 的頁面裡，瀏覽器把它當成咖啡店自己的程式：它能讀頁面、讀 localStorage、用顧客的 cookie 呼叫 API。第 4 課做好的 cookie 設定、第 6 課的 CSRF token，在這裡全部擋不住。

這類漏洞叫 XSS。這一課的任務是處理這則評論：先弄清楚它為什麼能執行、執行後能拿走什麼，再把咖啡店改到它沒辦法得手。修法有兩層：第一層是在輸出資料的地方做對，讓評論永遠只被當成文字；第二層是 CSP，就算哪一處漏了，瀏覽器也拒絕執行塞進來的程式。

這課的路線：
  1. 一則評論為什麼能在別人的瀏覽器裡執行程式？它執行之後能拿走什麼，為什麼 HttpOnly 和 CSRF token 都擋不住？
  2. 評論要怎麼輸出，才只會被當成文字？依輸出位置編碼，Vue 的 {{ }} 幫你做了什麼、沒做什麼。
  3. HTML 編碼擋不住的網址要怎麼檢查？同一套做法也用在登入後的 next 導回。
  4. 店長的公告就是要有粗體和連結時，怎麼顯示才安全？
  5. 就算哪裡漏了，怎麼讓瀏覽器拒絕執行？CSP 與 Trusted Types，以及咖啡店的 Vite SPA 怎麼上線。
這課會用到：
  • 第 4 課的 HttpOnly cookie：JavaScript 讀不到，但瀏覽器發請求時照樣會帶上。
  • 第 5 課的來源（origin）：協定＋主機＋port。同源的程式可以讀回應，這課的攻擊就是讓惡意程式變成「同源」。
  • 第 2 課的安全亂數：crypto.getRandomValues 產生攻擊者猜不到的位元組，再編成 base64。CSP 的 nonce 要用它產生。

一則評論，為什麼能在別人的瀏覽器裡執行程式？

先重現事故。商品頁的後端從資料庫拿出評論，用字串拼接組成 HTML 交給瀏覽器。下面的 renderNaive 就是這段程式：它把評論用字串拼接組成 HTML，第二則評論是攻擊者留的。Worker 裡沒有 DOM，所以只印出產生的 HTML。執行後看第二行：

第二行裡有一個完整的 <img> 標籤。對程式來說，評論只是一段字串；但這段字串被拼進 HTML 之後，瀏覽器解析時看到的就是標籤。瀏覽器去載入 src=x，載入失敗，於是執行 onerror 屬性裡的程式，把 localStorage 裡的 token 送到 evil.example。攻擊者不需要入侵伺服器，只需要留一則評論。

問題的根源是：程式把資料（使用者輸入的文字）直接拼進程式碼（HTML、JavaScript、網址）。資料裡的 <、" 這類字元在 HTML 裡有特殊意義，拼進去之後，它們就不再是文字，而是變成程式結構的一部分。瀏覽器拿到的是一整份 HTML，沒有任何標記告訴它「從這裡到這裡是使用者寫的」，所以它分不出哪段是咖啡店寫的、哪段是攻擊者塞的。

這類漏洞叫 XSS，全名 cross-site scripting，中文是跨站腳本：讓攻擊者的 JavaScript 在你網站的頁面裡執行。名字裡的「跨站」是歷史因素，不用從字面理解。重點在結果：瀏覽器判斷一段程式有什麼權限，只看它在哪個來源的頁面裡執行。第 5 課的同源政策保護的是「別的網站讀不到你的資料」；惡意程式在 shop.coffee.example 的頁面裡執行，它就是 shop.coffee.example 自己，擁有這個來源的一切權限，同源政策對它完全不設防。

評論區只是其中一條路。資料從哪裡進來，決定了要去哪裡找漏洞、誰會中招，所以 XSS 依惡意內容的來源分成三種：

類型惡意內容在哪裡咖啡店的例子誰會中招
儲存型（stored）存進資料庫，之後每次顯示都帶出來商品評論存了 <img src=x onerror=…>，商品頁直接把評論拼進 HTML每個看到這則評論的人，包括後台審評論的店長
反射型（reflected）在網址裡，伺服器把它原樣放進回應搜尋頁 /search?q=… 回應「找不到 q 的內容」，攻擊者把惡意的 q 做成連結傳給顧客點了那個連結的人
DOM 型（DOM-based）前端程式自己把不可信的資料塞進危險 API，伺服器可能完全沒經手前端讀 location.hash，用 innerHTML 顯示「目前分類：…」點了那個連結的人

咖啡店這次是儲存型，也是最危險的一種：攻擊者只要留一次，每個看到的人都中招，不需要騙任何人點連結。

三種的共同點是：最後都有一段程式，把不可信的字串交給「會把字串當成 HTML 或程式碼解讀」的 API。這類 API 叫危險注入點，英文是 sink，意思是資料最後流進去的地方。找 XSS 的方法，就是找出這些注入點，再往回追「這個值是誰給的」。常見的有：innerHTML、outerHTML、insertAdjacentHTML、document.write、eval、new Function、setTimeout('字串')、location.href = …、<a href>。

寫 Vue 時很少直接碰這些 API，但它們會換個樣子出現。在 Vue 專案裡最常見的入口是：

  • v-html 綁使用者的內容（評論、自我介紹、後台編輯的公告）。
  • :href、:src 綁使用者給的網址（個人網站、商品連結）：javascript: 網址點下去就會執行。
  • 在元件裡直接操作 DOM：el.innerHTML = …。
  • 第三方腳本：分析工具、客服聊天、廣告。它們跟你的程式同源執行，供應商被入侵，你的網站就被入侵。
💡 實務上：接手 Vue 專案，先搜一遍危險注入點
接手一個前端專案，最快的 XSS 健檢是在整個專案搜 v-html、innerHTML、insertAdjacentHTML、:href，逐一問「這個值最早是誰輸入的？」。來自店長後台的公告也要算進去：後台帳號被盜或內部人員誤貼，一樣會打到所有顧客。Code review 時看到新增的 v-html，資深的人會要求在 PR 裡寫清楚內容來源和清理方式，也可以把 ESLint 的 vue/no-v-html 規則設成 error，讓它預設報錯，真的需要時再個別關掉。第三方腳本也要列清單：行銷想加一段追蹤碼，要先問誰在維護、能不能拿掉。

知道評論為什麼能執行之後，下一個問題是嚴重程度：咖啡店在第 4 課已經把 session 放進 HttpOnly cookie、第 6 課加了 CSRF token，這段程式到底還能拿走什麼？

程式跑起來之後能拿走什麼？HttpOnly 和 CSRF token 為什麼擋不住？

上一節說過，惡意程式在咖啡店的頁面裡執行，就跟咖啡店自己的前端程式完全同等：前端能做的事，它都能做。所以「登入狀態放在哪裡」只決定損害長什麼樣子，決定不了有沒有損害。三種情況分開看：

登入狀態放在XSS 能做什麼關掉分頁之後
localStorage 裡的 access tokenlocalStorage.getItem('token') 一行讀走，送到自己的伺服器攻擊者在自己的電腦上繼續用，直到 token 過期或被撤銷
HttpOnly cookie 裡的 session ID讀不到 cookie，但可以 fetch('/api/me/email', { method: 'PATCH', credentials: 'include', … })：瀏覽器自動帶 cookie，這是同源請求，CORS 和 CSRF 防護都不擋，回應也讀得到攻擊停止，但已經做的事（改 email、下單、讀個資）都做了
不論放哪裡在頁面上畫一個假的「登入逾時，請重新輸入密碼」對話框，騙走密碼；讀頁面上的 CSRF token 再發請求拿到密碼就是永久的

第二列最容易被誤會。HttpOnly 讓 JavaScript 讀不到 cookie，所以攻擊者沒辦法把 session ID 帶回自己的電腦用。但它不需要帶走：瀏覽器發同源請求時本來就會自動附上 cookie，惡意程式只要在受害者的瀏覽器裡直接呼叫 API，伺服器看到的就是一個帶著正確 cookie 的正常請求。這種不偷憑證、直接借用受害者瀏覽器替攻擊者發請求的做法，叫 session riding。

所以 HttpOnly 的作用是降低損害：token 不會被帶走、在受害者關掉分頁後繼續被使用。它不是防 XSS。第 6 課的 CSRF token 也一樣擋不住：CSRF 防護的前提是攻擊者的程式跑在別的網站，拿不到頁面上的 token；現在惡意程式就跑在咖啡店的頁面上，直接讀得到 token，發出的請求也是同源，Sec-Fetch-Site 是 same-origin。

既然 XSS 得手後能以使用者身分做任何事，最怕的是它把一次性的攻擊變成永久接管：例如先改 email，再用「忘記密碼」把重設信寄到攻擊者的信箱。所以敏感操作（改 email、改密碼、綁新的 passkey）要再確認一次身分，重新輸入密碼或做多因素認證（MFA，第 14 課、第 16 課）。這是縱深防禦：不依賴單一防線，XSS 得手了，攻擊者還差一步。

結論很直接：損害擋不住，只能讓惡意程式根本不要執行。這課的答案分兩層：第一層是輸出資料時依位置編碼，讓評論永遠只被當成文字；第二層是 CSP，萬一某處漏了，瀏覽器也拒絕執行。先回到 renderNaive，把第一層做對。

評論要怎麼輸出，才只會被當成文字？

renderNaive 的問題是評論裡的 < 被瀏覽器當成標籤的開頭。修法不是把 < 刪掉，而是換一種寫法，讓瀏覽器知道「這裡是一個小於符號的字，不是標籤」。HTML 本來就有這種寫法，叫字元實體：&lt; 在畫面上顯示成 <，但解析時不會開始一個標籤。把資料裡有特殊意義的字元，全部換成只代表字元本身的寫法，這個動作叫輸出編碼（output encoding），也常叫跳脫（escaping）。評論經過編碼後，顧客在畫面上看到的文字一模一樣，只是瀏覽器不會再把它當成程式。

& 一定要最先換，原因是其他四個字元換出來的結果都以 & 開頭。如果先把 < 換成 &lt;，最後才換 &，剛產生的 &lt; 會再被換成 &amp;lt;，畫面上就顯示成「&lt;」四個字。

第四個 payload 沒被改，是因為它根本沒有特殊字元。這指出編碼的關鍵：要依輸出的位置選編碼方式。同一段資料，放在 HTML 內容、屬性、網址、JavaScript 裡，瀏覽器用不同的規則解析，危險的字元也不同。< 在元素內容裡危險；在屬性值裡，真正能跳出去的是引號；在 href 裡，連一般字母組成的 javascript: 都會執行。

輸出位置例子怎麼做
HTML 元素內容<li>資料</li>編碼 & < >，& 要最先換
HTML 屬性值<li data-author="資料">屬性一定加引號，再編碼 & < > " '。沒加引號時空白就能結束屬性，編碼引號也沒用
網址屬性<a href="資料">HTML 編碼不夠：javascript:alert(1) 沒有任何特殊字元。要解析網址，只允許 http:、https:
<script> 裡const user = 資料不要拼。改放進 <script type="application/json"> 或 data-* 屬性，再用 JSON.parse 讀
事件屬性、styleonclick="…資料…"不要放使用者資料

範例最後一段對應表格的 <script> 那一列。後端有時想把資料直接放進頁面的 <script> 裡給前端讀，以為 JSON.stringify 就安全。但 HTML 解析器在 JavaScript 執行之前就先掃過整份文件，只要看到 script 的結束標籤就結束這個 <script>，不管它是不是在 JSON 字串裡。所以要把 < 換成 \u003c（JSON 字串裡 < 的 Unicode 跳脫寫法）：對 JSON 來說兩者是同一個字元，JSON.parse 讀回來一樣，但 HTML 解析器看不到結束標籤。

你可能會想：為什麼不在評論存進資料庫時就把 < > 過濾掉，一勞永逸？因為存進去的時候，還不知道之後會輸出到哪裡：

  • 同一則評論會出現在網頁、App、email、後台、匯出的 CSV，每個位置的危險字元不同。濾掉 < > 擋不住屬性裡的引號，也擋不住 javascript: 網址。
  • 會毀掉正常資料：「買 2 杯 < 3 杯的價格」被改壞。
  • 輸入驗證（長度、格式、允許的值）仍然要做，它是另一件事：擋掉不合理的資料。防 XSS 的責任在輸出的地方。

寫 Vue 的好消息是：大部分的編碼 Vue 已經替你做了。模板裡的 {{ }} 用瀏覽器的 textContent 寫入，內容一律當文字；:title 這類屬性綁定用 setAttribute，值跳不出屬性。所以咖啡店的前台只要用 {{ review.text }} 顯示評論，那則 <img onerror> 就只會顯示成一串文字。Vue 不會處理的有兩處：v-html 直接設 innerHTML，完全不跳脫；:href 會跳脫引號，但跳脫擋不住 javascript:。Vue 的安全指南建議使用者提供的網址在後端存進資料庫前就清理，這樣網頁、App 每個用戶端都受保護。

Vue 的自動跳脫只保護 Vue 輸出的地方，後端還有兩類輸出它管不到：

  • API 回應本身：回應 JSON 時，Content-Type 要是 application/json，並加上 X-Content-Type-Options: nosniff。如果標成 text/html，有人直接在瀏覽器打開 /api/reviews/7，瀏覽器會把 JSON 裡的 <img onerror> 當 HTML 執行。nosniff 叫瀏覽器照標頭寫的類型處理，不要自己猜內容是什麼。
  • 後端產生的 HTML：訂單確認信、匯出的 PDF、伺服器渲染的後台頁面。模板引擎要開自動跳脫，自己拼字串時用上面的編碼。後台特別危險：店長權限比顧客大，儲存型 XSS 打到後台，攻擊者拿到的是店長的權限。

評論的文字到這裡處理完了。但表格裡有一列 HTML 編碼擋不住：網址。咖啡店的評論旁邊會顯示作者在個人頁填的網站，那個連結要怎麼檢查？

使用者給的網址，要怎麼檢查？

作者的網站要顯示成 <a :href="author.website">。如果作者填的是 javascript:fetch(…)，顧客一點就執行。直覺的做法是檢查字串開頭是不是 javascript:，但這擋不住。瀏覽器解析網址時，協定不分大小寫、會去掉開頭結尾的空白與控制字元、刪掉中間的 tab 和換行，所以 JaVaScRiPt:、開頭多一個空白的 javascript:、java[tab]script: 全都會執行。你的字串規則跟瀏覽器的解析規則只要差一點，就是一個繞過的方法。

正確做法是讓瀏覽器自己的規則來判斷：用 new URL() 解析，它跟瀏覽器點連結時用的是同一套網址規範，解析後的 protocol 就是瀏覽器真正會用的協定。再用允許清單檢查，只放行 http:、https:。不要用黑名單：黑名單只擋 javascript:，data:text/html,… 就漏了，而你永遠列不完所有危險的協定。執行後看每一行的 protocol，前四個怎麼寫都會被正規化成 javascript: 或 data:：

同一個問題：登入後的 next 參數

咖啡店還有一個地方在用使用者給的網址，而且更容易被忽略：登入頁。顧客在訂單頁被要求登入時，網址會是 /login?next=/orders/42，登入完導回原本的頁面。next 是網址的一部分，任何人都能改。如果它可以是任意網址，這就是開放重導向（open redirect）：攻擊者寄出 https://shop.coffee.example/login?next=https://evil.example/fake-login，連結的網域是真的，顧客放心登入，登入後卻被帶到假網站，上面寫著「密碼錯誤，請再輸入一次」。在 OAuth 裡，開放重導向還能把授權碼帶走（第 12 課）。

這裡的規則跟作者網站不同：作者網站可以連到任何網站，只是協定要對；next 只能留在咖啡店自己的網站裡。常見的寫法是檢查 next.startsWith('/')，但它跟上面的字串檢查有同樣的問題：

  • //evil.example：開頭是 /，但兩個斜線開頭是「沿用目前協定的完整網址」，會跳到 evil.example。
  • /\evil.example：對 http、https 網址，瀏覽器把 \ 當成 /，結果同上。
  • startsWith('https://shop.coffee.example') 也不行：https://shop.coffee.example.evil.example 是攻擊者的網域。

做法一樣是交給 URL 解析器：用 new URL(next, 自己的來源) 解析，第二個參數是相對路徑的基準，/orders/42 會接在自己的來源後面。再比對解析後的 origin 跟自己的來源完全相等，只回傳路徑部分。還有一個細節：/.//evil.example 解析後還在自己的來源，但 pathname 是 //evil.example，原樣交給 Location 標頭又變成跳到別的網站，所以結果以 // 開頭時也要拒絕。執行後看每一行的 origin 是不是 https://shop.coffee.example，以及最後一行的路徑：

到這裡，評論的文字和作者的網址都能安全輸出。但咖啡店有一種內容不能跳脫：店長在後台寫的公告，本來就要有粗體和連結。

店長的公告就是要排版，怎麼顯示才安全？

前台用 {{ }} 顯示公告，<b> 會被跳脫成文字，畫面上出現一堆 &lt;b&gt;。要顯示格式，就得用 v-html 把 HTML 交給瀏覽器，這正是上一節說的危險注入點。這時候要做的不是編碼，而是清理（sanitize）：把 HTML 解析成一棵樹，只留下允許的標籤與屬性，其他全部移除，再把結果交給 v-html。

清理的難處在於「解析」要跟瀏覽器完全一致。瀏覽器的 HTML 解析器非常寬容：大小寫混寫、屬性中間換行、HTML 實體、SVG 和 MathML 裡的標籤，都會被解析成可執行的東西。所以：

  • 用成熟的函式庫，例如 DOMPurify（瀏覽器直接用；Node 要搭配 jsdom）。它用瀏覽器自己的解析器解析，處理了 SVG、MathML、各種解析怪癖。
  • 用允許清單：DOMPurify.sanitize(dirty, { ALLOWED_TAGS: ['b', 'i', 'a', 'p'], ALLOWED_ATTR: ['href'] })，只放需要的。黑名單（「去掉 script 和 on 開頭的屬性」）永遠列不完。
  • 不要自己寫正規表示式清理 HTML：<scr<script>ipt> 去掉一次中間的 <script> 後剛好拼出新的 <script>；<svg><animate onbegin=…>、大小寫、換行、HTML 實體的變化，正規表示式都追不上瀏覽器的解析規則。

如果需求允許，也可以不讓使用者寫 HTML，改寫 Markdown。但後端把 Markdown 轉成 HTML 之後一樣要清理，因為 Markdown 允許內嵌 HTML，也允許 [點我](javascript:…) 這種連結。反過來，如果真的要讓使用者寫任意 HTML、CSS，例如店家自訂的活動頁，清理就不適用了，要把它放在 <iframe sandbox> 裡，最好用另一個網域，讓它跟主站不同源，裡面的程式碼就算執行也碰不到主站。Vue 的安全指南也說，使用者提供的 HTML 除非在沙箱 iframe 裡，否則不能視為安全。

清理要在每次輸出前做，或在存入時做並記住「這欄是清理過的 HTML」。前者比較保險：DOMPurify 會修正新發現的繞過手法，輸出前清理的話，升級套件就等於重新清理了所有舊資料。

💡 實務上：PM 說「讓店長自己排版公告」時
這類需求通常會變成在後台裝一個富文字編輯器（rich text editor）。編輯器只管「輸入」，存進資料庫的 HTML 一樣可能被人直接打 API 塞進惡意內容，所以顯示端還是要用 DOMPurify 清理，不能因為「編輯器只做得出粗體」就信任它。先跟 PM 確認真正需要的格式：多數公告只要粗體、清單、連結，允許清單越短越好；要嵌 YouTube、自訂樣式的需求，就要另外談 iframe 沙箱。DOMPurify 這類套件要跟著安全性更新升級，交給 Dependabot 或 Renovate 這類工具自動開升級 PR，不要鎖在多年前的版本。

現在咖啡店的每一種輸出都有正確做法了。但這些做法的前提是：每一個輸出點、每一位同事、每一次改版都做對。大專案總有一處漏掉，例如某個新頁面用了 v-html 卻沒清理。能不能有一道網，在漏掉的時候也接住？

就算哪裡漏了，能不能叫瀏覽器拒絕執行？CSP

這道網叫 CSP（Content Security Policy，內容安全政策）。它是伺服器在回應標頭裡寫給瀏覽器的一份規則：「這個頁面只能執行這些腳本」。瀏覽器照著規則執行，不在規則裡的一律拒絕。回到那則評論：就算某個頁面漏了編碼，<img onerror> 真的進了 HTML，在嚴格的 CSP 下，瀏覽器也不會執行 onerror 裡的程式。CSP 是縱深防禦，不取代輸出編碼：它擋的是執行，HTML 還是被注入了，而且政策寫錯就形同虛設。

問題是瀏覽器怎麼分辨「咖啡店自己的腳本」和「攻擊者塞進來的腳本」？web.dev 建議的嚴格 CSP（strict CSP）用的方法是 nonce。nonce 是 number used once 的縮寫：伺服器每次回應都產生一個新的隨機值，同時寫在 CSP 標頭和這份 HTML 的每個 <script nonce="…"> 上。瀏覽器只執行 nonce 跟標頭相符的腳本。咖啡店自己的腳本是伺服器在同一個回應裡產生的，帶著正確的值；攻擊者的評論是幾天前存進資料庫的，不可能知道這一次的值。完整的政策長這樣：

Content-Security-Policy: script-src 'nonce-R4nd0mV4lu3xxxxxxxxxx==' 'strict-dynamic'; object-src 'none'; base-uri 'none'

每個指令各補一個洞：

指令作用
script-src 'nonce-…'只有帶著這次 nonce 的 script 標籤能執行。攻擊者注入的 <script> 不知道這次的值；onerror 這類事件屬性、javascript: 網址一律不執行
'strict-dynamic'被 nonce 信任的腳本，用 document.createElement('script') 動態載入的腳本也被信任。打包工具會動態載入分割出來的程式碼，有了它就不必列網域清單
object-src 'none'禁止 <object>、<embed> 這類外掛內容，它們能繞過 script 的限制
base-uri 'none'禁止 <base href>。攻擊者能注入 <base href="https://evil.example/"> 時，頁面上用相對路徑載入的 <script src="/app.js"> 就會從 evil.example 載入，nonce 照樣有效

nonce 的安全性完全來自「攻擊者猜不到這一次的值」，所以 web.dev 的規則是：用密碼學安全的亂數產生、128 bits 以上、base64 編碼、每個回應都新產生。寫死或所有回應共用，攻擊者打開一次自己的頁面就看到值，把它寫進注入的 <script nonce> 就能執行，等於沒有。下面的範例模擬兩個請求，執行後看兩次的 nonce 不同，而且同一個請求裡標頭和 script 標籤用的是同一個值：

為什麼不用網域允許清單？

你可能看過另一種 CSP：script-src 'self' https://cdn.jsdelivr.net，意思是「自己的網域和這個 CDN 的腳本可以執行」。它看起來更直覺，但信任的單位是「整個網域上的所有檔案」。jsdelivr 上有整個 npm 的所有套件，任何人都能發布套件，也有很多舊版函式庫能被利用，例如舊版 AngularJS 會執行頁面上的模板語法、JSONP 端點會執行網址指定的回呼函式。攻擊者注入 <script src="https://cdn.jsdelivr.net/npm/攻擊者的套件">，完全符合你的清單。web.dev 引用的研究指出，網域允許清單型的 CSP 在大多數設定下都能被繞過。nonce 型不管網域，只認這次回應的那個值。

也不要加 'unsafe-inline'：它允許所有 inline 腳本與事件屬性，正好就是 XSS 注入的東西，加了它，那則評論的 onerror 就能執行。（有一種舊瀏覽器相容的寫法會同時加它，見課末。）

怎麼上線才不會擋掉自己的功能？

政策寫好了，但直接上線，可能擋掉你沒注意到的 inline 腳本或第三方工具，正式環境的某個按鈕就默默失效。所以先改送 Content-Security-Policy-Report-Only 標頭：瀏覽器照政策檢查，但只回報違規（印在 console、送到設定的回報端點），不阻擋。觀察一段時間、修好誤擋的地方，再換成正式的 Content-Security-Policy。CSP 也可以寫在 <meta http-equiv> 裡，但限制較多，正式環境用標頭，細節見課末。

咖啡店的 Vite SPA 怎麼帶 nonce？

咖啡店前台是 Vite 打包的 Vue SPA，這裡有一個矛盾：nonce 要伺服器每次回應時產生，但 Vite 打包出來的 index.html 是一個靜態檔案。解法是讓 Vite 先在 HTML 裡留好位置，再由送出 index.html 的那一層填值：設定 Vite 的 html.cspNonce 放一個佔位字串，Vite 會把它加到產生的 <script>、<style>、<link> 上；回應 index.html 的那一層（Node 伺服器、Nginx）每個請求把佔位字串換成新的 nonce，並送出對應的標頭。代價是 index.html 不能直接交給 CDN 快取同一份，因為每個回應的內容都不同。

如果 index.html 一定要完全靜態、交給 CDN 快取，另一條路是用 hash 取代 nonce，做法和代價見課末。

NestJS 後端怎麼送出這些標頭？

NestJS、Express 通常用 helmet 一次加上 CSP 和其他安全標頭（第 21 課與期末專題會用）。要注意 helmet 8.3.0 預設的 CSP 是 script-src 'self' 這類網域清單型，還有 style-src 'self' https: 'unsafe-inline'：比沒有好，但不是這一節的嚴格 CSP。要用 nonce，就自己設定 script-src。helmet 加上的其他標頭各擋什麼，整理在課末的查表。

💡 實務上：CSP 最常卡在第三方腳本與行銷工具
導入 CSP 時，最常被擋的不是自己的程式，而是行銷透過 Google Tag Manager 加的追蹤碼、客服聊天外掛、A/B 測試工具：它們常在頁面插入沒有 nonce 的 inline 腳本或 onclick 這類事件屬性，嚴格 CSP 會直接擋掉（由已放行的腳本用程式載入的檔案，'strict-dynamic' 會放行，通常不是問題）。所以上線前要先列出頁面上所有第三方腳本，並跟行銷、PM 講好「新加工具要先經過工程確認」，不然某天加了一段碼，在正式環境卻默默沒作用。Report-Only 的回報裡會有不少瀏覽器擴充功能造成的雜訊，看報告時先過濾掉，專注在自己網域的頁面與腳本。回報端點要限制大小和頻率，不要讓它變成可以灌爆的公開 API。

CSP 擋的是「執行」這一步。但第一節的 DOM 型 XSS，源頭是前端程式把字串塞進 innerHTML，能不能在寫程式這一端就擋住？

能不能讓危險注入點根本收不到字串？Trusted Types

第一節說過，找 XSS 要從危險注入點往回追每一個值的來源。專案一大，innerHTML 散在幾十個地方，每一處都要追，審查很難做完。Trusted Types 換了一個方向：讓瀏覽器拒絕把普通字串直接塞進危險注入點，只接受經過你定義的 policy 產生的物件。policy 是一個你命名的轉換函式，例如「把輸入交給 DOMPurify 清理再回傳」；只有它產生的值，瀏覽器才認為可以塞進 innerHTML。它一樣用 CSP 指令開啟：

Content-Security-Policy: require-trusted-types-for 'script'; trusted-types review-html
// 開啟之後
el.innerHTML = review.text            // TypeError：字串不能直接塞進 innerHTML

// 必須經過 policy；trusted-types 指令列出允許建立的 policy 名稱
const policy = trustedTypes.createPolicy('review-html', {
  createHTML: (input) => DOMPurify.sanitize(input),
})
el.innerHTML = policy.createHTML(review.text)   // 可以

好處是審查的範圍變小：整個專案只有建立 policy 的那幾行能產生可以塞進 innerHTML 的值，搜尋 createPolicy 就找得到全部。它涵蓋 innerHTML、outerHTML、insertAdjacentHTML、document.write、eval、new Function、script.src 等。

不支援的瀏覽器會忽略這個指令（各瀏覽器的支援版本見課末），所以它跟 CSP 一樣是額外一層，不能取代清理。現有專案可以先用 Report-Only 開啟，看哪些地方還在塞字串。到這裡，咖啡店對那則評論有了三層防護：輸出時編碼或清理、CSP 拒絕執行、Trusted Types 讓注入點收不到字串。

其他安全標頭（查表用，不用背）

helmet 一次加上的標頭裡，除了 CSP，這幾個各擋一類問題：

標頭擋什麼建議值
X-Content-Type-Options瀏覽器自己猜內容類型，把 JSON 或上傳的檔案當 HTML／腳本執行nosniff
CSP 的 frame-ancestors點擊劫持（clickjacking）：別的網站把你的頁面放進透明 iframe，騙使用者點到「確認付款」。這個指令決定誰可以把你的頁面嵌進 iframe；舊的做法是 X-Frame-Optionsframe-ancestors 'none'（不讓任何網站嵌入）或 'self'
Referrer-Policy點連結離開時，完整網址（可能含 token、訂單編號）經 Referer 標頭送到別的網站strict-origin-when-cross-origin（現代瀏覽器的預設）；重設密碼頁用 no-referrer（第 16 課）
Strict-Transport-Security使用者打 http:// 時第一個請求被竊聽或竄改（部署課第 5 課）max-age=31536000; includeSubDomains

用 hash 取代 nonce

script-src 'sha256-…' 'strict-dynamic'，用 inline 腳本內容的 SHA-256 取代 nonce，HTML 可以完全靜態、可以快取。hash 認的是 inline 腳本，Vite 產生的是外部的 <script src>，所以要改成一小段 inline 載入程式（用 createElement('script') 載入打包檔，靠 'strict-dynamic' 放行），再算這一段的 hash。web.dev 建議靜態或要快取的頁面用 hash、伺服器渲染的頁面用 nonce。代價：腳本內容改一個空白，hash 就要重算，要放進建置流程。

'unsafe-inline' 當舊瀏覽器的退路

web.dev 提到可以把 'unsafe-inline' 當成給很舊的瀏覽器的退路，支援 nonce 的瀏覽器看到 nonce 時會忽略它；但這會讓讀設定的人誤會，咖啡店不需要支援那麼舊的瀏覽器，就不要加。

Report-Only 與 meta 標籤

Report-Only 只能用 HTTP 標頭，<meta http-equiv> 不支援；正式環境也建議用標頭而不是 meta。

Trusted Types 的支援度

練習

練習 1：寫 escapeHtml(s)，把五個字元換掉：& → &amp;、< → &lt;、> → &gt;、" → &quot;、' → &#39;。再寫 renderReview(review)，產生 <li data-author="作者">內容</li>：作者放在屬性裡、內容放在元素裡，兩個都要編碼。

練習 2：寫 safeLinkUrl(input)：顧客在個人頁填的網站，要顯示成 <a href>。用 new URL(input) 解析（不給 base，所以相對網址會解析失敗），只允許 protocol 是 http: 或 https:，回傳解析後的 url.href；解析失敗或其他協定回 null。再寫 safeRedirect(next, appOrigin)：登入後要導回的位置只能在自己的網站裡。用 new URL(next, appOrigin) 解析，origin 等於 appOrigin 時回傳 pathname + search + hash；origin 不同、解析失敗、或結果以 // 開頭時回 '/'。

練習 3：寫 newNonce()：用 CSPRNG 產生 16 bytes（128 bits），回傳標準 base64（有 + / = 的那種，CSP 的 nonce 用標準 base64）。再寫 cspHeader(nonce, opts)，回傳 [標頭名稱, 標頭值]：值必須是 script-src 'nonce-<nonce>' 'strict-dynamic'; object-src 'none'; base-uri 'none'，opts.reportOnly 為 true 時標頭名稱是 Content-Security-Policy-Report-Only，否則是 Content-Security-Policy。

練習 4：把 access token 從 localStorage 移到 HttpOnly cookie，XSS 就沒有威脅了嗎？

✓ HttpOnly 讓 token 不會被讀走、帶到攻擊者的電腦離線使用，這是降低損害。但惡意腳本跟你的前端同源，fetch('/api/…', { credentials: 'include' }) 會帶 cookie、讀得到回應，CSRF 防護也不擋（session riding）。HttpOnly 不影響腳本能不能執行；document.cookie 也確實讀不到 HttpOnly cookie，d 的理由錯了。防 XSS 靠輸出編碼、清理與 CSP。

練習 5：Vue 元件裡有三處顯示評論資料：{{ review.text }}、<div v-html="review.text">、<a :href="review.link">。哪些會被 XSS？

✓ {{ }} 用 textContent 寫入，內容一律當文字。v-html 直接設 innerHTML，Vue 不跳脫。:href 會跳脫引號，所以跳不出屬性，但 javascript:alert(1) 不需要任何特殊字元，點下去就執行，所以 c 錯：網址要解析並只允許 http／https（練習 2），Vue 建議在後端存入前就清理。

練習 6：網站送出 Content-Security-Policy: script-src 'self' https://cdn.jsdelivr.net，也確實沒有任何 inline 腳本。為什麼仍然可能被 XSS？

✓ 網域清單信任的是「整個網域上的所有檔案」。CDN 上有所有 npm 套件，也有舊版 AngularJS、JSONP 端點這類能執行任意程式的工具，攻擊者只要用標籤載入就符合政策。'self' 不允許 inline 腳本（那要 'unsafe-inline'），c 錯；CSP 不分 HTTP、HTTPS，b 錯。改用 nonce 加 'strict-dynamic'，只認這次回應的隨機值。

常見錯誤

  • 用 v-html 顯示使用者的內容：Vue 不會跳脫。用 {{ }}；真的要格式就用 DOMPurify 允許清單清理，或放進沙箱 iframe。
  • :href 直接綁使用者給的網址：javascript: 點下去就執行。用 new URL 解析，只允許 http:、https:，最好在後端存入前就檢查。
  • 自己寫正規表示式清理 HTML 或檢查網址：大小寫、空白、tab、巢狀標籤都能繞過。HTML 用 DOMPurify，網址用 URL 解析器。
  • 輸入時過濾 < > 就以為防住了：擋不住屬性與網址，還會弄壞正常資料。依輸出位置編碼。
  • 以為 HttpOnly 就不怕 XSS：它只讓 token 不被讀走，腳本照樣能以使用者身分發同源請求。
  • CSP 加 'unsafe-inline'，或把整個 CDN 加進允許清單：等於沒擋。用 nonce（或 hash）加 'strict-dynamic'，再加 object-src 'none'、base-uri 'none'。
  • nonce 寫死或所有回應共用：攻擊者看一次就知道。每個回應用 crypto.getRandomValues 產生 16 bytes 以上。
  • 直接上正式的 CSP：可能擋掉正常功能。先用 Content-Security-Policy-Report-Only 觀察。
  • 回應 JSON 卻標成 text/html，或沒有 nosniff：直接打開 API 網址就會執行 JSON 裡的 HTML。
  • 只有前端跳脫：後端產生的 email、PDF、後台頁面也輸出 HTML，模板引擎要開自動跳脫。
  • 登入後的 next 只檢查開頭是 /：//evil.example、/\evil.example 都會跳走。用 new URL(next, 自己的來源) 比對 origin，結果是 // 開頭也拒絕。

小結

  • XSS 是資料被拼進程式碼、讓攻擊者的程式以你網站的來源執行：儲存型在資料庫、反射型在網址、DOM 型是前端自己把不可信的資料塞進危險注入點。找漏洞就從危險注入點往回追值的來源。
  • XSS 得手後，localStorage 的 token 被讀走；HttpOnly cookie 讀不到，但腳本能直接發同源請求（session riding）。HttpOnly 降低損害，不防 XSS；CSRF 防護也擋不住。敏感操作要再確認身分。
  • 第一層防線在輸出：HTML 內容與屬性用 HTML 編碼（& 先換、屬性加引號），資料不要拼進 <script>。Vue 的 {{ }} 自動跳脫，v-html 與網址不會；後端的 JSON 要標對 Content-Type 加 nosniff，後端產生的 HTML 要開自動跳脫。
  • 網址用 new URL 解析並只允許 http／https；登入後的 next 用 new URL(next, 自己的來源) 解析，origin 完全相等才導回，結果以 // 開頭也拒絕。
  • 要顯示 HTML 時用 DOMPurify 允許清單清理，或放進沙箱 iframe；不要自己寫正規表示式。
  • 第二層是嚴格 CSP：script-src 'nonce-…' 'strict-dynamic'; object-src 'none'; base-uri 'none'，nonce 每個回應用 CSPRNG 產生 128 bits 以上；不用網域清單、不加 'unsafe-inline'；先用 Report-Only 上線。Vite 用 html.cspNonce 留位置，helmet 的預設 CSP 要自己改成嚴格版。
  • Trusted Types 讓危險注入點只接受 policy 產生的值，審查範圍縮到 createPolicy 那幾行。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：顧客逛菜單時就發了匿名 session（存購物車），登入的程式這樣寫。哪裡會出事？

async function login(req, res) {
  const user = await verifyPassword(req.body.email, req.body.password)
  if (!user) return res.status(401).end()
  const session = await store.get(req.cookies['__Host-sid'])
  session.userId = user.id
  await store.save(session)
  res.status(204).end()
}

✓ 這是 session fixation：攻擊者手上的 ID 在受害者登入後就升級成受害者的身分。修法是登入成功時建立新 session、刪掉舊的、把購物車搬過去；權限提升、改密碼時也一樣。d 錯在匿名 session 沒問題，問題是權限改變時沒有換 ID。（第 4 課）

練習 8：session cookie 目前是 sid=…; Domain=coffee.example; Path=/; Secure; HttpOnly; SameSite=Lax。行銷要把活動頁 promo.coffee.example 外包出去，怎麼改最能限制活動頁對登入狀態的影響？

✓ 寫了 Domain，cookie 會送到所有子網域，子網域也能寫同名 cookie 蓋掉它。__Host- 要求不能有 Domain、Path=/、Secure，瀏覽器保證子網域寫不進來。b 錯在 SameSite 看的是站，子網域彼此同站，Strict 照樣帶。（第 4 課）

練習 9：新前台 order.coffee.example 的「快速點單」用 fetch 送 POST，body 是 URLSearchParams，API 只檢查 session cookie，CORS 清單卻忘了加這個來源。console 出現 CORS 錯誤，顧客以為失敗又按了兩次，後台出現三筆訂單。為什麼？

✓ 同源政策擋的是讀回應，不是送請求。簡單請求直接送出，伺服器照常建立訂單，回應回來後瀏覽器才做 CORS 檢查，只是不交給 JS。修法是把新來源加進允許清單，並記得 CORS 錯誤不代表伺服器沒執行。b 是最常見的誤解。（第 5 課）

練習 10：API 的 CORS 這樣寫。哪裡會出事？

function corsHeaders(origin) {
  if (origin && origin.endsWith('coffee.example')) {
    return {
      'Access-Control-Allow-Origin': origin,
      'Access-Control-Allow-Credentials': 'true',
      'Vary': 'Origin',
    }
  }
  return { 'Vary': 'Origin' }
}

✓ endsWith 只比字尾，攻擊者買一個 evilcoffee.example 就通過，再加上 Allow-Credentials，等於讓它以使用者身分讀 API。修法是把允許的來源完整列出、逐字比對。a 正好相反：帶 credentials 時 * 不算數，一定要回明確的來源。（第 5 課）

練習 11：session cookie 明寫 SameSite=Strict，會改狀態的 API 都用 POST。同事提議拿掉伺服器端的 Fetch Metadata 檢查，理由是 Strict 已經擋住所有 CSRF。哪個情況會出事？

✓ SameSite 看的是站，子網域彼此同站，Strict 擋不住被入侵或被接管的子網域。Fetch Metadata 檢查會看到 Sec-Fetch-Site: same-site 並拒絕，所以 SameSite 是縱深防禦，伺服器端的檢查要留著。b 錯在 Strict 對任何跨站請求都不帶 cookie，頂層導覽也一樣。（第 6 課）

練習 12：咖啡店有綁 session 的 CSRF token、SameSite=Strict、HttpOnly。評論區被發現有儲存型 XSS，攻擊者能以看到評論的顧客身分取消訂單嗎？

✓ CSRF 防護擋的是別的網站；XSS 的腳本就跑在你的網站上，讀得到頁面上的 token，發的是同源請求，SameSite 也不擋。所以 XSS 會打敗所有 CSRF 防護，要靠輸出編碼、清理和 CSP 讓它不發生。a 錯在攻擊者不用猜，直接讀。（第 6、7 課）

練習 13：PM 要讓店長自己排版公告（粗體、清單、連結）。後台裝了富文字編輯器，前台用 v-html 顯示。顯示端該怎麼做？

✓ 要顯示格式就不能跳脫，要清理：用成熟的函式庫解析 HTML，只留允許清單上的標籤與屬性。b 錯在編輯器只管輸入，有人直接打 API 就能存進任何 HTML；a 的正規表示式追不上瀏覽器的解析規則；c 會把標籤原樣顯示出來。（第 7 課）

練習 14：伺服器渲染的菜單頁加了嚴格 CSP。同事為了省效能，nonce 在啟動時產生一次。哪裡會出事？

const NONCE = newNonce()  // 啟動時產生一次，所有請求共用

app.get('/menu', (req, res) => {
  res.setHeader('Content-Security-Policy',
    `script-src 'nonce-${NONCE}' 'strict-dynamic'; object-src 'none'; base-uri 'none'`)
  res.send(renderMenu(NONCE))
})

✓ nonce 的作用是攻擊者猜不到這一次的值；所有回應共用，看一次自己的頁面就拿到了，CSP 等於沒有。每個回應都要用 CSPRNG 產生 128 bits 以上的新值。d 錯在 'strict-dynamic' 只延伸信任給已被 nonce 放行的腳本，沒有正確 nonce 的注入腳本跑不起來；這裡的洞是 nonce 被知道了。（第 7 課）
