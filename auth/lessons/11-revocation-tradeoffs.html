階段 3：Token 與 JWT · 第 11 課

登出與撤銷：session 與 JWT 怎麼選

週六早上，咖啡店店長林志豪發現手機掉在捷運上。手機上的 POS App 還登入著他的帳號，而店長帳號可以退款。他用店裡的電腦改了密碼，再按下「登出所有裝置」，畫面顯示「已登出所有裝置」。

麻煩在於 POS App 用的是第 10 課的做法：短效的 access token（一張 JWT）加上 refresh token。手機上那張 access token 簽章有效，還有 12 分鐘才到 exp。第 9 課的 verifyAccessToken 只檢查簽章和 claim，不查資料庫，所以不管電腦上按了什麼，API 收到這張 token 都會放行。接下來 12 分鐘，撿到手機的人照樣能用店長的身分退款。

這一課的任務：讓「登出所有裝置」對手機上那張 token 真的生效，並且說得出它多快生效、每個請求要為此付出什麼代價。做完你會發現，JWT 最大的賣點「驗證不用查資料」被拿回去了一部分，這正是決定會員網站、POS App 各該用 session 還是 JWT 的依據。

這課的路線：
  1. 店長的手機掉了，哪些憑證要失效、要多快？為什麼 session 刪掉資料就生效，JWT 卻收不回來（開場問題的最小答案）。
  2. 前端刪掉 token、撤銷 refresh 家族夠不夠？不夠的話，伺服器端能改什麼：短效期、jti 黑名單、token 版本，各晚多久生效、要付什麼代價。
  3. 身分收回來了，權限呢：店長調回店員後，token 裡的 role 為什麼還是店長。
  4. 驗證又要查資料了，還要用 JWT 嗎：會員網站、POS App、合作夥伴 API 各選哪一種；瀏覽器一定要用 token 時，用 BFF 讓它碰不到 token。
  5. 把選擇寫成決策紀錄，半年後有人問「為什麼」時有答案。
這課會用到：
  • 第 4 課的 session store：每個請求都拿 session ID 去 store 查是誰；登出刪掉這一筆，destroyAllForUser 刪掉這個人的全部。
  • 第 9 課的 verifyAccessToken：只驗簽章和 exp、iss、aud 這些 claim，不查資料庫；jti 是每張 token 的唯一 ID，sub 是使用者。
  • 第 10 課的 refresh token 家族：同一次登入一路輪替出來的 refresh token 用 family_id 串起來，撤銷家族之後就換不到新的 access token。

店長的手機掉了：哪些憑證要失效、要多快？

先把要處理的東西叫清楚。憑證是請求用來證明「我是誰」的東西：session 架構下是 cookie 裡的 session ID，token 架構下是 access token 與 refresh token。每種憑證本來就有壽命，session 會閒置逾時，JWT 到 exp 就驗不過。撤銷（revocation）指的是在壽命結束之前，主動讓它提早失效。

為什麼需要撤銷？因為憑證的壽命是登入那一刻決定的，而風險是之後才出現的：手機掉了、密碼外洩、員工離職。「登出」只是其中最溫和的一種情況。不同事件要失效的範圍不同，能容忍的延遲也不同：

事件要失效的東西要多快生效
按「登出」這台裝置的 session，或這台的 access token＋refresh 家族這台立即；其他裝置不受影響
按「登出所有裝置」這個人所有裝置的憑證立即
改密碼、重設密碼其他所有裝置（可能就是因為外洩才改）；目前這台通常保留立即
停權（離職、帳號被盜）全部，而且之後發的也不能用立即
降權（店長調回店員）不用登出，但權限要馬上更新立即，至少高風險操作要立即
refresh token 被偷（第 10 課的重用偵測）整個 token 家族立即

表裡最右邊那一欄是設計時最常被跳過的問題。「多快」的意思是：從使用者按下按鈕，到 API 開始拒絕舊憑證，中間隔多久。這段時間裡，拿著舊憑證的人做什麼都會成功。有些系統可以接受「最多晚 5 分鐘生效」，例如只能查集點紀錄的會員 App；有些不行，例如能退款、能改別人權限的帳號。

套到林志豪身上：他同時觸發了兩列，改密碼和登出所有裝置。要失效的是手機上的全部憑證，店裡電腦這台要保留；店長帳號能退款，所以「立即」是硬需求，12 分鐘的空窗不能接受。下一個問題是：同樣的需求，為什麼 session 一刪就做到，JWT 卻卡住？

為什麼 session 刪掉就生效，JWT 卻收不回來？

回想第 4 課的 session：cookie 裡只有一個隨機的 session ID，本身不帶任何資訊。每個請求進來，伺服器都拿這個 ID 去 session store 查「這是誰、還有效嗎」。既然每次都要查，撤銷就等於刪資料：

  • 登出：刪掉這一筆 session。
  • 登出所有裝置、改密碼：destroyAllForUser(userId, exceptToken?)，第二個參數用來保留目前這台。
  • 停權：刪掉全部，並在登入時拒絕停權的帳號。

刪掉之後，手機下一個請求帶來的 session ID 在 store 裡查不到，立即被拒，不用額外設計。代價是每個請求都要查一次 store。放在 Redis 時一次查詢通常在 1 毫秒以內，跟 API 本身查資料庫的時間比起來很小。

這種「驗證時要查伺服器上的資料」的做法叫有狀態驗證（stateful）：憑證有沒有效，取決於伺服器現在存了什麼。JWT 走的是另一條路，叫無狀態驗證（stateless）：Auth 服務簽發時把 sub、exp 等資訊寫進 token 並簽章，API 只要有金鑰、看得到時鐘，就能自己判斷這張 token 有沒有效，不查任何資料。無狀態的好處是省下每次查詢、不依賴共用的 store，好幾個服務都能各自驗證。

壞處就是這一課的主題。一張 JWT 有沒有效，只由三樣東西決定：token 本身的內容、驗證用的金鑰、現在的時間。林志豪在電腦上改密碼、按登出，這三樣一樣都沒變：手機上的 token 一個位元都沒動，金鑰沒換，時間還沒到 exp。伺服器上沒有任何一筆資料是驗證會去看的，所以也沒有東西可刪。

這就是開場問題的最小答案。要讓手機上那張 JWT 在 12 分鐘內失效，只有兩條路：一是讓驗證多查一樣伺服器端的東西（例如「已撤銷的 token 清單」），等於在 JWT 上加回一點狀態；二是不多查，把 access token 的壽命縮短，接受撤銷最多晚一個壽命才生效。後面幾節就是把這兩條路各自展開。不過在那之前，要先排除一個很多 JWT 專案實際在用的「登出」：兩條路都沒走，只在前端把 token 刪掉。

前端刪掉 token，手機上那張就失效了嗎？

用 JWT 的 Vue 前台，常見的「登出」寫法是把記憶體或 localStorage 裡的 token 刪掉，再導回登入頁。從使用者的角度看，登出成功了。但這個動作只讓這個分頁以後不再送 token，token 本身沒有任何改變。林志豪的情況更明顯：他按登出的是店裡的電腦，電腦的前端刪掉自己的 token，對手機上那份完全沒有影響。同樣的道理也適用於任何被複製走的 token，例如透過 第 7 課的 XSS、惡意擴充功能、或寫進 log 外洩的那一份。

下面用第 9 課驗證的簡化版模擬：stolen 是早就被複製走的一份，代表手機上那張。執行後看最後四行：登出之後第 1、5、14、15 分鐘，攻擊者拿複本打 API 的結果。

前端的變數已經是 null，但複本在登出後 14 分鐘還是「200 通過」，要到第 15 分鐘 exp 到了才被擋。驗證函式從頭到尾只看 token 和時鐘，前端做了什麼它根本不知道。

那撤銷 refresh 家族呢？第 10 課的「登出所有裝置」會把這個人所有的 refresh 家族標成撤銷，手機之後就換不到新的 access token。這有用，它把攻擊者的時間上限定在「手上這張 access token 的剩餘壽命」，不會一直續命下去。但手上這張仍然能用到 exp，因為 access token 的驗證不查 refresh 表。

結論是：要讓登出真的生效，伺服器端一定要有東西改變，而且是驗證時會看的東西：刪 session、撤銷 refresh 家族、把 jti 放進黑名單，或調高 token 版本。前兩個在第 4、10 課做過，下一節的三種做法就是 JWT 版本的「伺服器端改變」。

💡 實務上：驗收登出時，拿舊 token 重打一次 API
測試登出最常見的漏洞是只看畫面：按下去跳回登入頁就算通過。比較可靠的驗收方式是登出前先在 DevTools 的 Network 對某個 API 請求按「Copy as cURL」，登出後在終端機再送一次，看伺服器是不是回 401。資安檢測常測這一項；改密碼、停權也用同樣方式各測一次。如果結果是「要等 access token 過期（例如最多 15 分鐘）才失效」，不一定是 bug，但要讓 PM 和資安知道並同意、寫進規格，而不是等檢測報告才發現。林志豪這個案例，就是這份規格該寫清楚的情境。

伺服器端能改什麼，讓手機上的 JWT 失效？

上一節確定了：光靠前端不行，伺服器端要有驗證會看的東西改變。JWT 常見的做法有三種，差別在「驗證時額外查什麼」。每一種都用同樣三個問題來看：多快生效、每個請求多付什麼成本、要存多少資料，最後再看它能不能解決林志豪的手機。

(a) 不多查：短效期＋撤銷 refresh 家族

這是第 10 課已經做好的部分：access token 只活 5～15 分鐘，登出時撤銷 refresh 家族。之後換不到新的 access token，舊的最多再用到過期。驗證不查任何資料，JWT 保持完全無狀態，代價是撤銷最多晚 N 分鐘生效，N 就是 access token 的壽命。

一般按「登出」通常可以接受這個延遲：使用者自己按登出，多半不是因為憑證外洩。停權、手機被偷就不一定。林志豪的手機正好是不能接受的那種：這個做法下，撿到手機的人還有最多 12 分鐘可以退款。要補上這個空窗，驗證就得多查一樣東西，接下來兩種做法查的東西不同。

(b) 撤銷某一張：jti 黑名單

第 9 課提過，每張 JWT 都有一個唯一 ID jti。黑名單（denylist）就是記錄「哪些 jti 已經撤銷」的清單。驗證流程變成：先照第 9 課驗簽章和 claim，通過之後再查一下黑名單，jti 在裡面就回 401。

黑名單要存多久？不用永遠存。每張 JWT 都有 exp，過期之後驗證本來就會失敗，黑名單再記著它也沒有意義，所以一筆紀錄只需要存到那張 token 的 exp 為止。Redis 剛好有現成的工具：替 key 設定 TTL（time to live，存活時間），到期時 Redis 自動刪掉它（NestJS 課第 19 課）。EXAT 是用「到期的 Unix 時間（秒）」來設定 TTL，正好可以直接填 token 的 exp：

SET deny:a-001 1 EXAT 1800000900     # 到 exp（Unix 秒）自動刪除，Redis 6.2 起支援 EXAT
EXISTS deny:a-001                    # 驗證時查：1 表示已撤銷

這裡有兩個常見的坑。第一，忘了設 TTL：每次登出都加一筆、永遠不刪，黑名單會一直長大。第二，單位：JWT 的 exp 是秒，JavaScript 的 Date.now() 是毫秒。拿毫秒的「現在」直接跟秒的 exp 比，現在永遠比較大，紀錄一加進去就被當成過期清掉；反過來把秒當毫秒設到期時間，紀錄就幾乎永遠不清。練習 1 會測這兩個坑。

黑名單擅長的是撤銷「一張」token，例如「登出這台裝置」：登出請求本身就帶著這台的 access token，伺服器知道它的 jti 和 exp，放進黑名單就好。但林志豪是在電腦上按「登出所有裝置」，請求裡帶的是電腦的 token，伺服器不知道手機那張的 jti，除非它把發出去的每一張都記下來。另外，黑名單讓每個請求都要查一次 Redis，JWT 又變回有狀態，成本跟 session 一樣。撤銷「某個人的全部」需要另一種做法。

(c) 撤銷某人的全部：token 版本

token 版本（token version）是資料庫裡每個使用者一個整數。Auth 服務簽發 JWT 時，把這個使用者當下的版本寫進 token（例如放在 ver claim）。要「撤銷這個人全部的 token」時，只要把資料庫裡的版本加 1。驗證時比對 claims.ver 和資料庫目前的版本，不一樣就代表是撤銷之前發的舊 token。

套到林志豪身上：手機那張 token 帶著 ver: 3。他改密碼時，伺服器把他的版本改成 4，再發一張帶 ver: 4 的新 token 給電腦。手機下一個請求進來，API 看到 3 不等於 4，立刻拒絕；電腦的新 token 照常使用。整個過程不需要知道手機那張的 jti，所以它正好補上黑名單做不到的「撤銷全部」。

代價是每個請求要多查一個小欄位。這個欄位可以快取幾秒（例如 5 秒），減輕資料庫負擔，代價是撤銷最多晚 5 秒生效；退款這類操作可以跳過快取，直接查資料庫。另外，順序很重要：先把版本加 1，再發新 token。反過來的話，新 token 帶的是舊版本，版本一加 1，剛發給電腦的新 token 也跟著失效。

你可能會想到另一種寫法：不存整數，而是存一個時間點，規則是「這個時間之前簽發的 token 都無效」（tokens valid after），驗證時拿 token 的 iat（簽發時間）來比。聽起來一樣，但 iat 只精確到秒，而改密碼的流程是「撤銷全部」後馬上發新 token 給電腦，兩件事常落在同一秒。下面把林志豪的情況放進同一秒內：手機的舊 token 在 12:00:00.100 簽發、改密碼在 .400、電腦的新 token 在 .700。執行後看「拒絕」「接受」後面有沒有打 ✗：

結果由上到下：

  • 三個時間換成秒之後完全一樣，原本的先後順序消失了。
  • 規則用 <：電腦的新 token 被接受，但手機的舊 token 也被放過。這正是我們要擋的那一張。
  • 規則用 <=：手機的舊 token 被擋住了，但電腦剛拿到的新 token 也被誤殺，林志豪改完密碼馬上被登出。
  • token 版本：舊的拒絕、新的接受，兩邊都對。

用時間點的話，同一秒內總有一邊錯，要另外處理，例如 validAfter 存毫秒、JWT 另外帶毫秒的簽發時間，或撤銷之後等到下一秒才發新 token。token 版本比的是整數，只有「相等」和「不相等」，沒有精度問題。

三種做法怎麼搭配？

把三種做法和第 4 課的 session 放在一起比較：

做法多快生效每個請求的成本儲存量適合
短效期＋撤銷 refresh最多晚一個 access token 的壽命不查只有 refresh token 表一般登出
jti 黑名單立即查一次 Redis每張被撤銷的 token 一筆，存到 exp撤銷某一張 token
token 版本立即（有快取時晚幾秒）查一個欄位，可快取每個使用者一個整數撤銷某人全部的 token
（對照）session立即查一次 store每個登入一筆全部

實務上很少只選一種，而是依事件搭配：短效 access token＋refresh 家族處理一般登出；token 版本處理改密碼與「登出所有裝置」；停權再加一個「使用者已停用」的檢查，因為停權要擋住的不只是現有的 token，還有之後任何流程誤發出來的新 token。林志豪的手機用這個組合就解決了：改密碼時版本加 1、撤銷手機的 refresh 家族，手機下一個請求立刻被拒，也換不到新的 token。練習 1、3 會把這套組合實際寫出來。

OAuth 也定義了撤銷 token 與查詢 token 狀態的標準端點，跟這節的做法相關，放在課末的補充。

💡 實務上：撤銷檢查集中在一處，並先決定 Redis 連不上時怎麼辦
黑名單、token 版本、停用檢查要寫在共用的驗證 middleware 或 guard 裡，讓每個路由自己檢查，一定會有漏掉的。加了這些檢查，Redis 或資料庫就成了每個請求的依賴，設計時要先回答：它連不上時，是全部拒絕（fail closed），還是先放行（fail open）？退款、改權限這類操作通常選拒絕；查集點紀錄這種低風險的讀取，可以跟 PM 討論要不要放行。資深工程師會把這個決定寫進文件、加上監控與告警，而不是讓它停在「碰到例外就回 500」的意外行為。

到這裡，「這張 token 是誰的、還算不算數」已經收得回來了。但 JWT 裡常常不只放身分，還放了「他能做什麼」，那一部分有另一個問題。

身分收回來了，權限呢？token 裡的角色會過時

JWT 的 payload 很方便塞資料，常見的是把角色、門市也放進去：{ sub: 'u-lin', role: 'manager', storeId: 2 }。API 讀 claim 就知道這個人能不能退款，連使用者表都不用查。問題在於 claim 是簽發當下的快照：Auth 服務簽名的那一刻他是店長，就寫店長；之後資料庫怎麼改，已經簽好的 token 都不會跟著改。token 裡的權限資訊落後資料庫，這種情況叫過期權限（stale claims）。

換一個跟手機無關、但同樣常見的情境來看：手機事件後，總部決定把林志豪調回店員。他早上 09:55 登入拿到 15 分鐘的 token，總部 10:00 在後台改了他的角色。執行後看兩行：用 token 判斷和用資料庫判斷，「能不能退款」的答案是否一致。

看 token 的答案是 true，看資料庫是 false。到 10:10 token 過期之前，他在 API 眼中都還是店長；如果 refresh 時 Auth 服務也照抄舊 token 的 role，而不是重新查資料庫，就會更久。這跟上一節是同一類問題：憑證的內容在簽發時就固定了，伺服器端的變化傳不進去。

修法的原則是：token 只代表「是誰」，「能做什麼」每次問資料庫。具體做法有三層：

  • token 只放身分（sub），角色、門市每次用 sub 從資料庫查。可以快取幾秒，降低負擔。
  • 退款、改權限、匯出個資這類高風險操作一定即時查，不走快取。
  • 降權時順便調高 token 版本，讓舊 token 失效、強迫換一張新的。

這不是 JWT 獨有的問題。第 4 課的 session 如果在 session 資料裡快取了角色，降權後一樣要等他重新登入才會更新。原則相同：憑證只代表「是誰」，「能做什麼」問資料庫。練習 2 就是把讀 role 的退款判斷改成查資料庫。

💡 實務上：後台的「改角色」按鈕要連帶處理舊 token
總部人事後台把店長調回店員、或停用離職員工時，PM 預期的是「按下去就生效」。實作這支 API 時，要在同一個流程裡更新角色、調高 token 版本（停用還要設停用旗標），並在後台畫面上寫清楚生效時間。code review 時搜尋直接拿 JWT payload 判斷權限的寫法（例如來自 token 的 req.user.role），確認授權用的是資料庫的值。這類操作也要留稽核紀錄（誰在什麼時候改了誰的權限），客服和資安事後追查時會用到。

把這兩節的修法加起來，POS 的每個請求現在都要查 token 版本、停用旗標和角色。這時候該回頭問一個問題：既然每個請求都在查資料，一開始為什麼選 JWT？

每個請求都要查資料了，那還要用 JWT 嗎？

加上撤銷檢查和權限查詢之後，POS 的 JWT 跟 session 的差別只剩兩點：token 自己帶著 claim，以及別的服務可以用公鑰驗證它，不必連到同一個 session store。這兩點值不值得付出撤銷、過期權限、refresh 流程的複雜度，要看情境。

先排除一個常見的錯誤理由：「JWT 才能水平擴展」。水平擴展是指流量變大時多開幾台 API 伺服器，由負載平衡器把請求分過去。如果 session 存在每台伺服器自己的記憶體裡，請求打到另一台就查不到，使用者會被莫名登出，這是這個迷思的來源。但修法不是換 JWT，而是把 session 放到所有伺服器共用的 store，例如第 4 課的 Redis。水平擴展只要求「狀態放在共用的地方」，不要求「沒有狀態」。

真正該問的是兩件事：誰要驗證（只有一個 API，還是很多服務）、撤銷要多快。看下面的表之前，先認識三個名詞。第一方（first-party）是自家團隊寫、自家掌控的程式，例如咖啡店自己的 Vue 會員網站；第三方（third-party）是別家公司寫的程式，例如想讀顧客訂單的外送平台。API 閘道（API gateway）是擋在所有後端服務前面的單一入口，統一做認證、限流、把請求轉給對的服務。

情境建議理由
第一方的 Vue 會員網站＋單一 API，同站session cookie最簡單、撤銷立即；HttpOnly cookie 讓 XSS 偷不走憑證。不需要 token。
店員 POS App（手機、平板）短效 access token＋refresh 輪替（第 10 課）App 不是瀏覽器，cookie 不方便；refresh 家族可撤銷，搭配 token 版本處理改密碼與停權。
多個內部服務都要驗證同一個使用者短效 JWT（ES256，用 JWKS 發布公鑰，第 8 課）每個服務用公鑰自己驗，不必都連 session store。常見做法是由 API 閘道驗證後往下傳。
第三方要存取使用者資料OAuth（第 12 課）第三方不能拿到使用者的密碼或 session；要有範圍、可撤銷的授權。

表裡只有第三列真正用上了 JWT「不連 store 也能驗」的好處。單一 API 選 JWT 的代價是：要處理撤銷（又變有狀態）、過期權限、token 放在哪（第 10 課），還要寫 refresh 流程；換到的好處在只有一個 API 的時候幾乎不存在。POS App 選 token 的理由也不是無狀態，而是 App 不方便用 cookie，所以這課前面為它加回的狀態是合理的代價。

表裡會員網站選 session 有一個前提：Vue 前端和 API 同站，API 是自己管的。如果前端非得呼叫一個只收 token 的 API 呢？

瀏覽器一定要用 token 時，怎麼讓它碰不到 token？

有些情況下，瀏覽器前端必須呼叫用 token 保護的 API，例如 API 由另一個團隊管理、只接受 access token，或 token 是由外部的登入服務發的。這時 token 若放在瀏覽器裡（記憶體或 localStorage），就回到第 7 課的風險：一次 XSS 就能把它讀走，帶到攻擊者自己的電腦上用到過期。

先補兩個第 12 課會正式講的 OAuth 名詞，這一節會用到。負責發 token 的一方叫授權伺服器（authorization server），咖啡店的 Auth 服務就是這個角色；拿 token 去呼叫 API 的程式叫 client。client 又分兩種：跑在伺服器上、能安全保管自己的秘密（client secret），並用它向授權伺服器證明身分的，叫機密 client（confidential client）；跑在瀏覽器或手機裡、程式碼誰都拿得到、藏不住秘密的，叫公開 client。

BFF（Backend for Frontend）的做法是：在前端旁邊放一個同站的小後端，由它當機密 client。瀏覽器只跟這個後端溝通，用的是第 4 課的 HttpOnly session cookie；access token 與 refresh token 只存在這個後端，由它代替前端帶著 token 去呼叫 API、負責 refresh 與撤銷。對瀏覽器來說，它只是在用一般的 session。

RFC 10017「OAuth 2.0 for Browser-Based Applications」（BCP 212，2026 年 8 月）把瀏覽器應用的架構依安全性排成三種，越前面越安全：

  1. BFF：token 只在後端。商業、敏感、處理個資的應用強烈建議用這個。
  2. token-mediating backend：後端負責取得 token，再交給瀏覽器去呼叫 API。refresh token 留在後端，但 access token 仍在瀏覽器裡。
  3. 純瀏覽器 OAuth client：整個 OAuth 流程與所有 token 都在瀏覽器裡。

BFF 不是讓 XSS 失效。惡意腳本仍然可以透過受害者的瀏覽器向 BFF 發請求，瀏覽器會自動帶上 cookie，所以使用者開著頁面的期間，攻擊者能以他的身分做事（第 7 課講過的情況）。差別在於瀏覽器裡沒有 token 可以偷：攻擊者拿不到能帶回自己電腦、在使用者關掉頁面後繼續用的憑證。他也沒辦法自己跑一次授權流程（向授權伺服器換 token 的步驟）拿新 token，因為那需要 BFF 保管的 client secret。損害被限制在「頁面開著的時候」，而且 BFF 這邊撤銷 session 就能立即切斷，跟本課前半的 session 一樣。

BFF 用的 cookie 就是整個架構的憑證，RFC 10017 對它的要求是：Secure、HttpOnly 是 MUST；SHOULD 用 SameSite=Strict、Path=/、不設 Domain，並用表示「只能由 HTTP 設定」的前綴，例如 __Host-Http-：

Set-Cookie: __Host-Http-sid=Zx9…; Path=/; Secure; HttpOnly; SameSite=Strict

__Host-Http- 除了第 4 課 __Host- 的規則，還要求 HttpOnly，所以 JavaScript 不能用 document.cookie 寫入同名 cookie。各瀏覽器的支援情況不一，見課末補充。另外，既然 BFF 靠 cookie 認人，它就跟所有 cookie 架構一樣 MUST 做 CSRF 防護；RFC 建議要求一個自訂標頭，再靠 CORS 擋掉跨站送這個標頭（第 5、6 課）。

到這裡，咖啡店三個前端各用什麼、為什麼，已經都有答案了。最後一步是把它寫下來。

怎麼讓半年後的同事知道為什麼這樣選？

這一課做的每個選擇都帶著代價：POS 接受一般登出最多晚 15 分鐘生效，會員網站接受每個請求查一次 Redis。半年後新同事問「為什麼 POS 不用 session」或「為什麼不全部換成 JWT」，如果答案只在某個已經離職的同事腦袋裡，團隊很可能把當初刻意付出的代價當成 bug「修掉」，或重新踩一次林志豪的坑。

決策紀錄（ADR，Architecture Decision Record）就是記下「當時為什麼這樣選」的短文件。格式與流程在系統設計課第 18 課詳談；這裡用最小的四段：背景（當時的情況與限制）、選項（考慮過哪些）、決定（選了哪個）、後果（得到什麼、付出什麼）。咖啡店三個前端的決策寫成：

會員網站（Vue）店員 POS App合作夥伴 API
背景第一方、和 API 同站；有個資與集點手機與平板，可能遺失；店員會離職、調職外送平台要讀顧客授權的訂單
選項session cookie／JWT 放 localStorage／BFFsession／短效 JWT＋refresh給 API key／OAuth
決定session cookie（__Host-、HttpOnly、SameSite=Lax）存 Redisaccess 15 分鐘＋refresh 輪替；token 帶 ver；權限每次查資料庫（快取 5 秒，退款不快取）OAuth 授權碼流程（第 12 課）
後果每個請求查一次 Redis；撤銷立即；Redis 停機時無法登入，要監控一般登出最多晚 15 分鐘；改密碼、停權靠 ver 與停用檢查立即生效；要維護 refresh 表要架授權伺服器或用現成服務；合作夥伴的權限可以單獨撤銷

POS 那一欄就是林志豪事件的答案：手機遺失時改密碼，靠 ver 立即生效；店員按一般登出，接受最多晚 15 分鐘。「後果」一定要寫代價，不是只寫優點。之後情況改變（例如會員網站要接第二個 API），就能對照背景，看出當初的前提是不是還成立、決定要不要重新討論。

補充與查表

主線用不到、但接觸 OAuth 授權伺服器或設定 BFF cookie 時會查的細節。

OAuth 的撤銷與 introspection 端點

OAuth（第 12 課）有兩個跟撤銷相關的標準端點，這裡先認識用途：token revocation（RFC 7009）讓 client 通知授權伺服器「這張 token 不要了」，對不認得或已失效的 token 也回 200；撤銷 refresh token 時，伺服器 SHOULD 一併讓同一次授權發出的 access token 失效（前提是它支援撤銷 access token）。token introspection（RFC 7662）讓 API 問授權伺服器「這張 token 現在還有效嗎」，回應裡一定有 active（布林值），呼叫的一方也要經過授權。introspection 就是把有狀態驗證集中到授權伺服器。

__Host-Http- 的瀏覽器支援

依 MDN 的相容性資料（2026-10），Chrome 140、Firefox 143 起支援，Safari 還不支援。Safari 遇到時只把它當成一般的 __Host- cookie，__Host- 的規則仍然有效，只是少了 HttpOnly 的強制檢查；需要一致行為時就用 __Host-。

練習

練習 1：實作 TokenRevocation，在 verifyAccessToken 驗過簽章與 exp 之後，再判斷 token 是不是已被撤銷。now() 回傳毫秒，claims 的 exp 是秒。

  • revokeJti(jti, exp)：把這張 token 放進黑名單，只記到 exp 為止。
  • revokeAllForUser(userId)：這位使用者的 tokenVersion 加 1。
  • disableUser(userId)：停用這位使用者。
  • isRevoked(claims)：先清掉黑名單裡已經到期（now() 到達 exp × 1000）的紀錄；接著 jti 在黑名單、使用者不存在或已停用、或 claims.ver 不等於目前的 tokenVersion，都回傳 true。

練習 2：下面的 canRefund 讀 token 裡的 role 決定能不能退款，林志豪被調回店員之後還能退款。改成只用 claims.sub 向 users 查使用者，以資料庫為準：使用者存在、沒有停權（suspended）、角色是 manager 才回傳 true。token 裡有沒有 role 都不影響結果。

練習 3：把撤銷組成完整的帳號流程。AccountSecurity 注入三樣東西：練習 1 的 TokenRevocation（已經寫好）、第 10 課的 refresh 家族操作 refresh，以及 issueAccessToken(userId)（依呼叫當下的 tokenVersion 發新的 access token claims）。實作：

  • logout(claims, familyId)：只登出這台裝置，這台的 access token 與 refresh 家族都失效，其他裝置照常。
  • logoutAll(userId)：所有裝置的 refresh 家族與 access token 都失效。
  • passwordChanged(userId, currentFamilyId)：其他裝置的 refresh 與 access 全部失效；目前這台保留 refresh 家族，舊的 access token 失效，回傳一張新的、有效的 access token。
  • suspended(userId)：所有 token 立刻失效，之後新發的也不能用。

想一想每一步的先後順序。

練習 4：咖啡店的會員網站是 Vue 前台＋單一 NestJS API，部署在同一個網域。團隊想改成「登入回傳 JWT、存 localStorage、每個請求放 Authorization 標頭」，理由是「比 session 現代，而且之後好擴展」。你的建議是？

✓ 第一方、同站、單一 API 正是 session cookie 最適合的情境：HttpOnly 讓腳本讀不到、刪掉 store 裡的資料就立即登出。a 是迷思：session 放 Redis 就能水平擴展。b 的 sessionStorage 一樣讀得到（XSS 能帶走），關分頁也沒有讓伺服器端的 token 失效。d 每個請求都查黑名單，等於用更複雜的方式重做 session，還多了 localStorage 被 XSS 讀走的風險。

練習 5：POS App 用 15 分鐘的 JWT access token。店員按「登出」，前端把記憶體裡的 access token 刪掉，也呼叫了撤銷 refresh 家族的 API。這張 access token 接下來還能用嗎？

✓ JWT 的簽章與 exp 都沒變，驗證不查資料就會通過。撤銷 refresh 家族只讓它換不到新的，手上這張仍能用到過期（a、c 錯：簽章是簽發時算好的，不會因為伺服器的資料改變而失效）。要立即失效就要讓驗證多查一樣東西：jti 黑名單（撤銷一張）或 token 版本（撤銷全部），d 錯在說沒辦法。代價是驗證又變有狀態；能接受晚 15 分鐘生效的話，只撤銷 refresh 也是合理的取捨。

練習 6：RFC 10017 依安全性把瀏覽器應用分成 BFF、token-mediating backend、純瀏覽器 OAuth client。網站已經有 XSS 漏洞時，為什麼 BFF 仍然比較好？

✓ RFC 10017 的說法：BFF 架構下沒有 token 可偷，攻擊者也無法自己跑授權流程（BFF 是機密 client），損害限制在使用者開著頁面的期間。b 錯：HttpOnly 只讓 JavaScript 讀不到 cookie，不影響腳本執行。c 錯：另外兩種架構裡 token 可以被偷走、在攻擊者的電腦上一直用到過期（或用 refresh token 續命）。d 錯：惡意腳本跑在你自己的網站上，它發的請求是同站的，SameSite 不擋。

常見錯誤

  • 以為前端刪掉 token 就是登出：token 本身沒有改變，複本仍能用到 exp。登出一定要在伺服器端改變驗證會看的東西：刪 session、撤銷 refresh 家族、黑名單或 token 版本。
  • 停權只撤銷 refresh token：access token 還能用到過期。停權要讓驗證拒絕這個使用者的所有 token，包括之後新發的。
  • 改密碼後沒讓其他裝置登出：密碼可能就是外洩才改的。撤銷其他裝置的 refresh 家族，並把 token 版本加 1。
  • 黑名單永遠不清：每次登出加一筆，Redis 越來越大。用 TTL 只存到 token 的 exp，注意 exp 是秒。
  • 改密碼時先發新 token 再把版本加 1：新 token 帶舊版本，一發出就失效。先撤銷，再發新的。
  • 「撤銷全部」用時間點判斷，卻沒處理同一秒：iat 只到秒，同一秒內不是放過舊 token 就是誤殺新 token。用 token 版本，或改用毫秒並另外處理。
  • JWT 裡放角色、權限、門市，改了以後不更新：降權後要等 token 過期才生效。token 只放 sub，權限從資料庫查；高風險操作即時查；降權時調高 token 版本。
  • 為了「無狀態」選 JWT，結果每個請求又查黑名單與使用者表：成本跟 session 一樣，複雜度更高。單一 API 的第一方網站直接用 session。
  • 沒有決策紀錄：半年後沒人記得為什麼這樣設計，前提改變了也沒人發現。用背景、選項、決定、後果四段寫下來。

小結

  • 撤銷是讓還沒過期的憑證提早失效。登出、改密碼、停權、降權、token 被偷，要失效的範圍和速度都不同；設計時每一種都要回答「多快」。
  • session 是有狀態驗證，天生可撤銷：刪掉 store 裡的資料就立即生效，代價是每個請求查一次。JWT 是無狀態驗證，伺服器沒有東西可刪，簽出去的 token 在 exp 前一直有效。
  • 前端刪 token 不算登出；撤銷 refresh 家族只讓它換不到新的。要讓手上那張立即失效，驗證必須多查一樣東西：jti 黑名單（撤銷一張，只存到 exp）或 token 版本（撤銷某人全部）。這也讓 JWT 變回有狀態。
  • 流程的順序：先撤銷、再發新 token；改密碼保留目前這台的 refresh 家族；停權要擋住之後新發的 token。林志豪的手機靠「版本加 1＋撤銷 refresh 家族」立即失效。
  • token 只代表「是誰」，「能做什麼」問資料庫，避免過期權限。
  • 水平擴展不是選 JWT 的理由。第一方同站用 session；手機 App 用短效 access＋refresh 輪替；多個內部服務用短效 JWT；第三方用 OAuth。瀏覽器需要 token 時用 BFF，讓 token 只在後端。
  • 把選擇寫成決策紀錄：背景、選項、決定、後果（含代價）。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：「我的訂單」API 這樣取得顧客 ID。哪裡會出事？

// jsonwebtoken
const { sub } = jwt.decode(token)
return db.orders.findMany({ where: { customerId: sub } })

✓ payload 只是 base64url，任何人都能解開、改寫、再編碼回去；擋住竄改的是簽章，而 decode 根本不看簽章。授權只能用驗證過的結果：verify 或 jwtVerify。a 錯在「改不了」要靠伺服器驗簽章才成立，這段程式沒有驗。（第 8、9 課）

練習 8：訂單 API 用 ES256 驗證，公鑰公開在 JWKS，私鑰沒有外洩。攻擊者卻做出了被接受的 role: admin token，header 寫的是 HS256，最可能的原因是？

✓ 這是演算法混淆：驗證端看到 HS256 就用「公鑰的位元組」算 HMAC，而公鑰人人拿得到。修法是允許清單寫在伺服器、每把金鑰綁一種演算法，header 的 alg 只拿來比對（RFC 8725 §3.1）。c 錯在重送的舊 token 是 Auth 服務簽的 ES256，header 不會是 HS256，payload 也不會是攻擊者寫的。（第 9 課）

練習 9：訂單 API 和集點 API 都驗證同一個 Auth 服務、同一把 ES256 金鑰簽的 access token。訂單 API 的設定如下，哪裡會出事？

JwtModule.register({
  publicKey: config.jwtPublicKey,
  verifyOptions: { algorithms: ['ES256'] },
})

✓ 簽章只證明「Auth 服務簽的」，不證明「給我用的」；jsonwebtoken 沒給 audience、issuer 就完全不檢查，同一把金鑰簽的別種 token 都能通過。補上 issuer、audience: 'orders-api'，自己發的 token 再檢查 typ。a 正好相反：jku 是攻擊者的輸入，JWKS 網址只能寫在設定裡。（第 9 課）

練習 10：店員 POS 是 Vue SPA，用 15 分鐘的 access token 加上 refresh token 輪替。兩種 token 該放哪裡？

✓ refresh token 活幾十天，最怕被讀走帶到別處用，所以放腳本讀不到的 HttpOnly cookie，只送到 refresh 端點；access token 短命，放記憶體，重新整理時呼叫一次 /auth/refresh 拿新的。c 把保護放反了：一次 XSS 或被汙染的 npm 套件就能讀走 refresh token，換 access token 換上幾十天。（第 10 課）

練習 11：同事改寫 refresh 流程：「用過的 refresh token 直接從資料表刪掉，表比較小，刪了也不能再用。」問題在哪？

✓ 重用偵測靠的是「這張已經用過」的紀錄：用過的又出現，代表有兩個人拿著它，要撤銷整個家族。刪掉之後，先拿偷來的 token 換到新 token 的攻擊者可以一直輪替下去，沒有人發現。留著 used_at，等家族過期再清。a 只看到「舊的不能用」，漏掉了它是偵測被偷的唯一線索。（第 10 課）

練習 12：POS 用 15 分鐘的 JWT access token 加 refresh 家族。店長要求：離職店員的帳號「按下停用就不能再呼叫任何 API」，該怎麼做？

✓ JWT 到 exp 前都驗得過，要立即失效，驗證就得多查一樣東西；停用旗標或 token 版本一次擋住這個人手上所有的 token，包括其他裝置的。檢查寫在共用的 middleware，才不會有路由漏掉。a 最常被選，但手上已經發出的 access token 還能用到過期，最多晚 15 分鐘。（第 10、11 課）

練習 13：退款 API 這樣判斷權限，req.user 是驗證過簽章、aud、exp 的 JWT claims。哪裡會出事？

@Post('orders/:id/refund')
refund(@Req() req) {
  if (req.user.role !== 'manager') throw new ForbiddenException()
  // …退款
}

✓ claim 是簽發時寫進去的，資料庫改了它不會跟著改，這叫過期權限。token 只代表「是誰」，用 sub 向資料庫查角色；退款這類高風險操作不走快取，降權時再調高 token 版本。c 錯在簽章只證明「簽發時是這樣」，不證明「現在還是這樣」。（第 11 課）

練習 14：會員網站的 session 存在每台 API 伺服器的記憶體裡，從 1 台擴展到 3 台後，使用者常被莫名登出。同事提議改用 JWT，你的看法？

✓ 被登出是因為請求打到沒有這筆 session 的那台；水平擴展只要求 session 放在共用的 store，不是選 JWT 的理由。換成 JWT 反而要另外處理撤銷、過期權限與 token 放哪裡。c 錯在簽章只證明 cookie 裡的 session ID 沒被改，資料還是只在建立它的那台記憶體裡。（第 4、11 課）
