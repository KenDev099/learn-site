階段 4：更多登入方式：第三方、多因素與機器 · 第 12 課

OAuth 2.0：授權碼流程與 PKCE

咖啡店想做一個新功能：「匯入你在外送平台點過的咖啡，自動幫你集點」。王小明常在外送平台點拿鐵，這些訂單存在外送平台的資料庫裡，咖啡店看不到。這一課的任務是：讓咖啡店讀得到王小明在外送平台的訂單，而且只讀得到訂單。先做網站版，再做手機 App 版。

最直覺的做法是請王小明在咖啡店網站輸入外送平台的帳號密碼，由咖啡店的伺服器代為登入去抓訂單。這課從這個做法錯在哪裡開始，一步一步做出業界標準的 OAuth 2.0 流程，並看攻擊者會從流程的哪些縫隙下手、每一道檢查擋住的是哪一種攻擊。學完你能自己串第三方平台的 API，也看得懂登入套件替你做了哪些檢查。

這課的路線：
  1. 為什麼不能直接要密碼？OAuth 的做法：王小明在外送平台自己的頁面同意，咖啡店拿到只能讀訂單、隨時可撤銷的 token（開場問題的最小答案）。
  2. token 怎麼交到咖啡店手上？授權碼流程的六個步驟，經過瀏覽器的前端通道與伺服器直連的後端通道各傳什麼。
  3. 授權碼會不會被送錯地方、會不會被別人塞進來？redirect_uri 一字不差的比對，以及 state、iss 兩個檢查。
  4. 手機 App 沒有 client secret 怎麼辦？PKCE 讓攔走授權碼的人換不到 token，以及授權伺服器那一端要守的規則。
  5. 新專案照哪張清單做？RFC 9700 的規則整理，以及咖啡店的 Vue 前台該選哪一種架構。
這課會用到：
  • 第 2 課的安全亂數、SHA-256、base64url：crypto.getRandomValues 產生猜不到的位元組，SHA-256 算出不能還原的指紋，base64url 把位元組寫成網址安全的字串。PKCE 三樣都用。
  • 第 4 課的 session：伺服器端存「這個瀏覽器是誰、帶著什麼資料」，用 cookie 裡的 ID 找回來。state 與 code_verifier 就存在這裡。
  • 第 6 課的 CSRF token：放一個綁定使用者 session、攻擊者猜不到的值，伺服器收到時比對。state 就是 OAuth 的 CSRF token。
  • 第 10 課的兩種 token：短命的 access token 拿去呼叫 API，長命的 refresh token 只用來換新的 access token。

為什麼不能直接請王小明給外送平台的密碼？

先把「給密碼」這個做法想清楚。咖啡店拿到密碼後，能做的事跟王小明本人一模一樣：讀訂單，也能改密碼、用他綁定的信用卡下單、刪掉帳號。咖啡店只需要「讀訂單」，卻拿到了全部權限。

權限也收不回來。王小明哪天不想讓咖啡店讀了，唯一的辦法是改外送平台的密碼，而改密碼會讓他其他用到這組密碼的裝置一起被登出。更糟的是風險跟著密碼搬家：咖啡店的資料庫只要被入侵一次，存在裡面的外送平台密碼就全部外洩，而外送平台對此完全無能為力。外送平台如果要求簡訊驗證或 passkey 這類只能在它自己頁面上完成的登入方式，咖啡店的伺服器根本登不進去。

所以咖啡店真正需要的是三件事：權限有範圍（只能讀訂單）、王小明隨時能收回、密碼從頭到尾不經過咖啡店。OAuth 2.0（RFC 6749）就是為這件事設計的框架。它的做法是：王小明在外送平台自己的頁面登入、按「同意」，外送平台發給咖啡店一張只能讀訂單、隨時可以撤銷的 token。咖啡店之後拿這張 token 呼叫外送平台的 API，不再需要密碼。

這就是開場問題的答案。接下來的所有細節，都在處理「這張 token 怎麼安全地交到咖啡店手上」。為了說清楚每一步是誰把什麼交給誰，OAuth 給參與的四方各取了名字：

角色是什麼咖啡店的例子
資源擁有者（resource owner）資料的主人，也就是使用者王小明
client想存取資料的程式咖啡店網站 shop.coffee.example
授權伺服器（authorization server，AS）讓使用者登入、同意，並發出 token 的服務外送平台的 auth.delivery.example
資源伺服器（resource server，RS）存放資料、接受 access token 的 API外送平台的 api.delivery.example

注意外送平台分成兩個角色：授權伺服器負責「讓王小明登入、問他同不同意、發 token」，資源伺服器負責「收 token、回訂單資料」。它們可能是同一家公司的兩台伺服器，也可能是同一台，但職責不同，後面講流程時要分開看。

咖啡店要的權限範圍叫 scope，是一個字串，例如 orders:read，每一家平台自己定義有哪些 scope。外送平台把它翻成人看得懂的同意頁：「咖啡店想要：讀取你的訂單紀錄」。王小明看得到咖啡店要了什麼，可以拒絕；外送平台發出的 access token 只能做 scope 允許的事，咖啡店拿它去下單會被資源伺服器擋下。王小明也能在外送平台的設定頁撤銷這次授權，咖啡店手上的 token 就失效，不用改密碼。

最後要分清楚 OAuth 回答的是什麼問題。它回答的是「咖啡店可以讀王小明的訂單嗎」，不是「現在操作的人是不是王小明」。access token 是發給資源伺服器看的，對咖啡店來說它是一串不透明的字（像第 8 課的不透明 token），OAuth 沒有規定咖啡店要怎麼從它知道使用者是誰。所以 OAuth 不能直接拿來做「用外送平台帳號登入」；那需要的身分資訊由 OpenID Connect 在 OAuth 之上補齊，是下一課的主題。這一課先把 OAuth 本身的流程和攻擊弄清楚，它們在 OpenID Connect 裡全部照用。

💡 實務上：你多半是 client，scope 要得越少越好
工作中最常遇到的是當 client：串 Google 日曆、LINE、GitHub、物流或外送平台的 API。scope 只要功能真正用得到的，同意頁列一長串權限，使用者會猶豫甚至取消；有些平台（例如 Google 的敏感 scope）還要額外送審。使用者隨時能在平台撤銷授權，所以呼叫 API 收到 401、refresh 也失敗時，要把這個連結標成失效，畫面上顯示「重新連結外送平台」，而不是一直重試或整頁出錯。資深工程師會先問：使用者不在線上時也要讀資料嗎？要才需要長期保存 refresh token；只是一次性匯入，用完就不必留 token。

方向定了：王小明在外送平台的頁面同意，外送平台發 token 給咖啡店。問題是王小明是在瀏覽器裡跟外送平台互動的，外送平台要把東西交給咖啡店，第一個能走的路就是瀏覽器，而瀏覽器並不是保管秘密的好地方。

token 怎麼交到咖啡店手上？授權碼流程一步一步

王小明在外送平台按下「同意」之後，外送平台能做的是把瀏覽器導回咖啡店的網站，要交給咖啡店的東西只能放在導回的網址裡。網址是很容易外流的地方：它會留在瀏覽器的歷史紀錄裡，會被寫進伺服器與中間代理的 access log，使用者離開頁面時會跟著 Referer 標頭送給下一個網站，也可能被瀏覽器擴充功能看到。如果外送平台直接把 access token 放在網址裡，這張 token 就散落在這些地方。

所以 OAuth 把資料的傳遞分成兩條路，並規定什麼東西能走哪一條：

  • 前端通道（front channel）：透過瀏覽器的導向與網址傳遞，也就是上面那些容易外流的地方。這裡只傳短效、一次性的東西，外流了也很快沒用。
  • 後端通道（back channel）：咖啡店的伺服器直接用 HTTPS 呼叫外送平台的伺服器，不經過瀏覽器，不會留在歷史紀錄或 Referer 裡。真正有價值的 token 只走這裡。

兩條通道之間要有一個交接物，就是授權碼（authorization code）。它像一張取貨單：從前端通道送到咖啡店手上，本身不能拿來呼叫 API；咖啡店要拿著它，從後端通道去外送平台換成真正的 token，而且它只能用一次、幾分鐘內有效。就算它從網址外流，撿到的人也很難在幾分鐘內、在咖啡店之前把它用掉（後面幾節會把「很難」變成「做不到」）。

OAuth 把「client 取得 token 的方式」叫做 grant，規格裡定義了好幾種。用上面這種「前端通道傳授權碼、後端通道換 token」的方式，叫授權碼流程（authorization code grant）；現在只要有使用者參與，一律用它。其他被淘汰或用在別處的 grant，最後一節和課末再整理。下圖是整個流程的全貌：

下面一步一步看。第 1 步會出現兩個隨機值：state 和 code_verifier。它們各自擋一種攻擊，為什麼需要，要等看過攻擊才講得清楚（state 在下一節、code_verifier 在 PKCE 那一節）；這一節先記住它們在流程中什麼時候產生、存在哪裡、什麼時候用掉。

1. client 準備並導向授權端點

王小明在咖啡店網站按「從外送平台匯入」。咖啡店後端先產生 state 與 code_verifier 兩個隨機值，存進王小明自己的 session（第 4 課），再把瀏覽器導向外送平台授權伺服器的授權端點：

GET https://auth.delivery.example/authorize
  ?response_type=code
  &client_id=coffee-shop
  &redirect_uri=https%3A%2F%2Fshop.coffee.example%2Foauth%2Fcallback
  &scope=orders%3Aread
  &state=Qm9xX0kE4vT1…
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256

每個參數的用途：

參數用途
response_type=code要授權碼流程
client_idclient 事先在外送平台註冊時拿到的識別碼，公開的，不是秘密
redirect_uri授權完要導回的網址，必須和註冊時一字不差
scope要的權限，多個用空白分隔
state一次性隨機值，確認回來的 callback 是自己發起的
code_challenge、code_challenge_methodPKCE：code_verifier 的 SHA-256，證明之後來換 token 的是同一個 client

client_id 是咖啡店事先在外送平台的開發者後台「註冊成一個 client」時拿到的。註冊時咖啡店也要填好授權完要導回的網址，也就是 redirect_uri；為什麼要事先填、比對為什麼要一字不差，是下一節的主題。

2. 使用者在授權伺服器登入、同意

這一步完全發生在 auth.delivery.example。王小明輸入密碼、做簡訊驗證、看同意頁，咖啡店都看不到，這正是開場要的「密碼不經過咖啡店」。王小明按「拒絕」時，授權伺服器一樣導回 redirect_uri，但帶的是 error=access_denied 而不是授權碼，咖啡店要能處理這個情況。

3. 導回 redirect_uri

王小明按下同意，授權伺服器用一個 302 導向把瀏覽器送回咖啡店的 callback，授權碼就放在網址裡：

HTTP/1.1 302 Found
Location: https://shop.coffee.example/oauth/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=Qm9xX0kE4vT1…&iss=https%3A%2F%2Fauth.delivery.example

網址裡有三個參數：code 是授權碼；state 是第 1 步咖啡店送出去的值，原樣帶回來；iss 是授權伺服器報上自己的名字（RFC 9207），咖啡店串了不只一家平台時才用得到，留到下一節最後再講。這個網址現在留在王小明的瀏覽器歷史紀錄和咖啡店的 access log 裡，這就是授權碼必須短效、一次性的原因。

4. client 檢查 callback

咖啡店後端收到 callback，先不要急著用 code。依序檢查：網址有沒有 error；state 是否等於 session 裡存的那個；iss 是否等於這次發起授權的那個授權伺服器。比對完就把 session 裡的 state 刪掉，讓它只能用一次。任何一項不符就停在這裡，不拿 code 去換 token。

5. 後端通道換 token

檢查都通過，咖啡店的伺服器直接呼叫授權伺服器的 token 端點，用授權碼換 token。這一步不經過瀏覽器：

POST https://auth.delivery.example/token
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Y29mZmVlLXNob3A6…（client_id:client_secret）

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fshop.coffee.example%2Foauth%2Fcallback
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

請求裡除了 code，還有兩樣東西。redirect_uri 要跟第 1 步送的完全相同，授權伺服器會核對這個 code 是不是發給這個網址的。Authorization: Basic 標頭裡是咖啡店的 client_id 和 client_secret，這叫 client 認證：咖啡店向授權伺服器證明「來換 token 的真的是 coffee-shop」。client_secret 是註冊時外送平台發給咖啡店的密碼，只有咖啡店知道。就算授權碼從網址外流，撿到的人沒有 client_secret，也換不到 token。

這道防線有個前提：client 要保管得住秘密。咖啡店後端跑在自己的伺服器上，程式碼和環境變數使用者都看不到，所以能保管 client_secret，這種 client 叫機密 client（confidential client）。另一種情況是程式碼在使用者手上：瀏覽器裡的 Vue SPA、手機 App。打包後的 JS 或 App 安裝檔誰都能拆開來看，放進去的任何秘密都等於公開（Vite 的 VITE_ 變數就會原樣出現在打包後的 JS 裡）。這種 client 叫公開 client（public client），它沒有 client_secret，換 token 時少了 client 認證這道防線。這個缺口要靠 PKCE 補上，咖啡店做手機 App 時就會碰到。client 認證還有一種不用共用密碼的做法，見課末「補充與查表」。

從工程的角度看，這一步就是一般的後端呼叫外部 API，要設逾時、處理 4xx／5xx（Node 課第 17 課）。授權伺服器拒絕時回 400 與 {"error":"invalid_grant"} 這類錯誤代碼，例如 code 過期或已經用過。

6. 拿到 token

{
  "access_token": "SlAV32hkKG…",
  "token_type": "Bearer",
  "expires_in": 900,
  "refresh_token": "8xLOxBtZp8…",
  "scope": "orders:read"
}

之後咖啡店用 Authorization: Bearer SlAV32hkKG… 呼叫外送平台 API 讀訂單；access token 過期就用 refresh token 換新的，規則跟第 10 課一樣。token 存在咖啡店後端（例如加密後存資料庫，第 23 課），不交給瀏覽器，這樣它就從頭到尾沒有出現在前端通道。注意回應裡的 scope：王小明可能只同意了一部分權限，咖啡店要以這個值為準，而不是以自己要求的為準。

把六步排在一起看：每一步經過哪條通道、帶了什麼，以及咖啡店 session 裡的兩個隨機值什麼時候存、什麼時候刪。

步驟通道誰 → 誰帶了什麼咖啡店 session 裡
1. 導向授權端點前端咖啡店後端 → 瀏覽器 → 授權伺服器client_id、redirect_uri、scope、state、code_challenge存進 state、code_verifier
2. 登入、同意只在授權伺服器王小明 ↔ 授權伺服器密碼、MFA、按「同意」（咖啡店看不到）不變
3. 導回前端授權伺服器 → 瀏覽器 → 咖啡店 callbackcode、state、iss不變
4. 檢查 callback咖啡店後端內部—比對 state、iss比對完刪掉 state
5. 換 token後端咖啡店後端 → 授權伺服器 /tokencode、redirect_uri、code_verifier、client 認證送出後刪掉 code_verifier
6. 拿到 token後端授權伺服器 → 咖啡店後端access_token、refresh_token、scopetoken 存在後端，不給瀏覽器

第 1 步的網址和第 3 步的 callback，都是咖啡店後端用程式組出來、拆開來的。下面用 URL 與 URLSearchParams 示範。執行後先看 redirect_uri：它自己帶著 ? 和 &，只有交給 URLSearchParams 編碼，授權伺服器讀到的才是完整的網址；用字串相加，&lang=zh-TW 會被當成授權網址自己的參數，redirect_uri 就斷掉了。最後一行的重複 state，等講到 state 那一節會用到。

流程走完了，但它整個建立在一個前提上：授權碼只會被送到咖啡店的 callback，而且送進 callback 的，就是王小明自己這一次的授權碼。決定送去哪裡的是第 1 步網址裡的 redirect_uri，而這個網址是放在瀏覽器裡、任何人都能改的。

授權碼會被送去哪裡？redirect_uri 為什麼要一字不差

想像攻擊者把第 1 步的網址複製下來，只改一個參數：把 redirect_uri 換成自己的網站，再把這個連結傳給王小明。王小明點下去，看到的是真正的外送平台登入頁、真正的同意頁，他按下同意，授權伺服器就把授權碼導向攻擊者的網站。王小明從頭到尾沒有做錯任何事。

所以授權伺服器不能相信網址裡的 redirect_uri。這就是註冊的用意：咖啡店事先在外送平台登記「我的 callback 是這幾個網址」，授權伺服器在 /authorize 收到請求時，檢查 redirect_uri 是不是登記過的其中一個，不是就直接顯示錯誤頁，不導向任何地方。

關鍵在「怎麼比對」。這課會一直引用 RFC 9700：它是 IETF 在 2025 年 1 月發布的《OAuth 2.0 安全最佳實務》，把 RFC 6749 之後十幾年累積的攻擊與修正整理成規則，最後一節會整理成一張表。RFC 9700 規定這個比對 MUST 是精確的字串比對：請求的值要跟登記的值每個字元都相同。原因是過去各家授權伺服器用過的寬鬆比對，每一種都被繞過過。表中會出現「開放重導向」，這是第 7 課講過的漏洞：網站上有個網址參數能把人導到任意外部網址，例如 /go?url=https://evil.example。code 只要先落在這樣的頁面，就會被轉送出去：

看到最後一個網址，可能會想：既然解析後跟登記的一樣，授權伺服器能不能「幫忙」正規化後再比對？答案是不要。大小寫、預設 port、結尾斜線、..，每多一條正規化規則，就多一個 client 端與授權伺服器端解析結果不一致的機會，上表的第二列就是這樣被繞過的。要支援多個環境，就登記多個完整的網址。

精確比對只有一個例外：手機與桌面 App 的 loopback 網址（http://127.0.0.1）。有些桌面 App 接 callback 的方式是在自己電腦上臨時開一個 port 等瀏覽器導回來，port 由作業系統分配，事先不知道是哪一個，所以 RFC 8252 §7.3 允許 loopback 網址的 port 每次不同，其餘部分仍要一字不差。

redirect_uri 指到的 callback 頁面本身也要乾淨，因為授權碼會在這個頁面的網址裡停留一下。這個頁面不要有開放重導向（上面寬鬆比對表講過的那種頁面），不要載入第三方腳本；處理完 code 後立刻用 302 導到不含 code 的網址，並設 Referrer-Policy: no-referrer，讓 code 不會經由 Referer 外洩。另外 RFC 9700 規定除了 loopback 以外，redirect_uri 不能用 http：明文傳輸時，同一個網路上的人就看得到網址裡的 code。

💡 實務上：redirect_uri_mismatch 是串接時最常見的錯誤
localhost、staging、正式站各註冊一個完整的 callback 網址；換網域、多一個結尾斜線、http 和 https 不同，授權頁都會直接顯示這個錯誤。每個 PR 一個網址的預覽部署沒辦法事先註冊（精確比對不接受萬用字元），常見做法是在預覽環境關掉第三方登入，第三方登入只在固定網址的 staging 測。callback 網址放在環境變數，平台後台註冊的值列進上線檢查清單，換網域時才不會漏改。測試用和正式站各註冊一組 client_id 與 client_secret，測試的 secret 外洩也不會波及正式站。

redirect_uri 確保授權碼只會被送到咖啡店。但反過來想：送進咖啡店 callback 的授權碼，一定是王小明自己按「匯入」換來的嗎？攻擊者不偷王小明的 code，而是把自己的 code 送進去，會怎樣？

callback 真的是王小明自己發起的嗎？用 state 擋授權碼注入

假設咖啡店沒有 state，callback 只要收到 code 就去換 token。攻擊者可以這樣做，而且不用偷任何東西：

  1. 攻擊者用自己的外送平台帳號，在咖啡店按「匯入」，走到第 3 步拿到 callback 網址，但不打開它。
  2. 攻擊者把這個網址做成一張圖片或連結，讓已登入咖啡店的王小明打開（第 6 課的 CSRF）。
  3. 咖啡店收到 callback，用攻擊者的 code 換到 token，把攻擊者的外送帳號連到王小明的咖啡店帳號。

後果看功能而定：攻擊者的外送訂單灌進王小明的集點卡還算小事；如果這個連結是「用外送平台帳號登入咖啡店」，攻擊者之後就能用自己的外送帳號登入王小明的咖啡店帳號。這叫授權碼注入：把自己的 code 塞給受害者的 client 去用。

這個攻擊會成功，是因為 callback 請求確實是王小明的瀏覽器送的，帶著王小明的 cookie，咖啡店分不出「這是王小明自己發起的授權回來了」還是「別人做好的網址被王小明打開了」。這跟第 6 課的 CSRF 是同一種問題，解法也一樣：發起時放一個只有這個使用者 session 知道的值，回來時比對。這個值就是 state。

具體做法：王小明按「匯入」時，咖啡店用 CSPRNG 產生一個隨機值（例如 32 bytes 的 base64url），存進王小明的 session，同時放進第 1 步的網址；callback 回來時比對網址上的 state 和 session 裡的是否相同，相同才繼續，比對完立刻刪掉。攻擊者做好的 callback 網址帶的是攻擊者那次的 state，跟王小明 session 裡的不同（王小明根本沒發起過，session 裡可能什麼都沒有），咖啡店就會拒絕。

有三個地方容易寫錯，它們都會讓 state 形同虛設。第一，state 要存在伺服器端的 session，比對完就刪；不要放在 localStorage，所有分頁共用同一份，又容易忘了刪，變成可以重複使用。第二，callback 沒有 state 也要拒絕，不能寫成「有帶才比對」，否則攻擊者只要把 state 拿掉就過關了。第三，state=a&state=b 這種重複參數也要拒絕：前面組網址的範例最後一行看過，get 只回第一個，而同一個請求經過的不同程式碼可能一個讀第一個、一個讀最後一個，檢查的和使用的就不是同一個值。

RFC 9700 §2.1 的規定比「一定要用 state」寬一點：client MUST 防 CSRF，而做法有三種。確認授權伺服器支援 PKCE 的 client，可以依賴 PKCE 防 CSRF（原因在後面的 PKCE 那一節）；OpenID Connect 另有一個叫 nonce 的隨機值：client 產生後存進 session，授權伺服器把它原樣放進 ID token，client 收到時比對，作用跟 state 一樣（下一課）；以上都沒有時，MUST 用綁定使用者、一次性的 state。實務上 state 很便宜，咖啡店照樣帶。

咖啡店再串第二家外送平台時：用 iss 擋 mix-up

咖啡店的匯入功能做得不錯，又串了另一個外送平台 B，現在畫面上有兩個按鈕：「從 A 匯入」「從 B 匯入」。這時出現一個新的縫隙。咖啡店在第 5 步要把 code 送到哪一家的 token 端點，靠的是自己記得「這次是向誰發起的」。mix-up 攻擊就是讓這個記憶跟實際發 code 的平台不一致。假設 B 是惡意的（或被攻擊者控制），用咖啡店的情境走一遍：

  1. 王小明按「從 B 匯入」。咖啡店在 session 記下「這次找 B」，把瀏覽器導向 B 的授權端點。
  2. 惡意的 B 不自己發 code，而是把瀏覽器轉到 A 的 /authorize，帶上咖啡店在 A 註冊的 client_id 和 callback。這兩個值本來就會出現在網址裡，不是秘密。
  3. 王小明看到的是 A 的真頁面、咖啡店的真名稱，按下同意。A 照規矩把 code 導回咖啡店登記過的 callback，redirect_uri 的精確比對完全擋不住，因為它本來就是對的。
  4. 咖啡店收到 code，照 session 的記錄以為這是 B 發的，就把 A 的 code 送到 B 的 token 端點。B 就拿到了 A 的 code。

問題出在第 4 步：咖啡店只靠自己的記憶決定 code 送去哪裡，沒有確認 code 實際是誰發的。如果 callback 帶著 iss=A，咖啡店在第 4 步之前拿它跟 session 記的 B 比對，就會發現不符而停下。

防法是 RFC 9207 定義的 iss 參數，也就是第 3 步 callback 網址裡的第三個參數：授權伺服器在 callback 裡帶上自己的識別，咖啡店發起授權時把「這次是向誰發起的」存在 session 裡，callback 回來時用簡單的字串比對確認兩者相同，不符就拒絕。這裡同樣不要正規化，多一個結尾斜線就算不同。

授權伺服器會不會帶 iss，寫在它的 metadata 裡。metadata 是授權伺服器公開的一份 JSON 設定檔，列出各端點的網址與支援的功能，格式由 RFC 8414 定義。metadata 宣告了 authorization_response_iss_parameter_supported: true 時，callback 缺少 iss 也 MUST 拒絕，否則攻擊者只要把它拿掉就繞過了。這門課的外送平台有宣告支援，所以練習 2 要求 iss 一定要出現。

到這裡，網站版的匯入功能擋住了「code 被送錯地方」和「別人的 code 被塞進來」。它還有最後一道防線：第 5 步換 token 要附 client_secret，就算 code 從 log 或歷史紀錄外流，沒有 secret 也換不到 token。接下來咖啡店要做手機 App 版，這道防線就沒了。

手機 App 沒有 client secret，被攔走的授權碼怎麼辦？PKCE

咖啡店的手機 App 也要有「從外送平台匯入」。第 5 步講過，App 安裝檔誰都能拆開，App 是公開 client，不能放 client_secret。這代表授權碼一旦落到別人手上，對方拿著它就能直接去 token 端點換 token，沒有任何東西能證明「來換的是咖啡店 App」。

而 App 的授權碼特別容易落到別人手上。App 常用自訂 URL scheme 當 redirect_uri，例如 coffeeapp://oauth/callback：手機系統看到這個開頭的網址，就交給註冊了這個 scheme 的 App 打開。問題是任何 App 都能註冊同一個 scheme。惡意 App 註冊了 coffeeapp://，外送平台導回的 callback 就可能被它攔下，授權碼到了它手上。除了 App，code 也可能從 access log、Referer、瀏覽器歷史漏出去。這些都叫授權碼攔截。

我們需要一個辦法證明「來換 token 的」就是「當初發起授權的」，但不能靠一個長期的秘密，因為 App 保管不住。PKCE（Proof Key for Code Exchange，RFC 7636，念作 pixy）的想法是：每次授權都臨時產生一個新的秘密，只用這一次。它分四步：

  1. client 產生 code_verifier：43～128 個 unreserved 字元（A-Z a-z 0-9 - . _ ~）的高熵隨機字串。RFC 7636 建議 32 bytes CSPRNG 隨機值，base64url 後剛好 43 個字元。自己留著，不送出去。
  2. 算出 code_challenge = BASE64URL(SHA-256(ASCII(code_verifier)))，放在授權請求（前端通道）裡，加上 code_challenge_method=S256。
  3. 授權伺服器把 challenge 和這個授權碼存在一起。
  4. 換 token 時（後端通道）client 送出 code_verifier；授權伺服器算一次 SHA-256，跟存的 challenge 比對。

關鍵在於兩個值走不同的通道。challenge 走前端通道，可能被看到；verifier 只在最後一步、從後端通道送出。攔截者在前端通道只看得到 code 和 challenge，而 SHA-256 反推不回 verifier，所以拿著 code 也換不到 token。對咖啡店 App 來說，verifier 就是一個「只活一次授權」的 client_secret。

寫 PKCE 時有三個地方最常出錯。第一，雜湊的是 verifier 這個 ASCII 字串本身，不是把它 base64url 解碼回 32 bytes 再雜湊。RFC 7636 的公式是 SHA256(ASCII(code_verifier))，上面的 challengeOf 就是用 TextEncoder 把字串編碼後直接雜湊。

第二，只用 S256。PKCE 還定義了另一個方法 plain，challenge 直接等於 verifier。這樣前端通道上看得到 challenge，就等於看得到 verifier，整個機制失效。RFC 9700 說 S256 是目前唯一不暴露 verifier 的方法。各家平台支援哪些方法不太一樣（見課末「補充與查表」），我們一律用 S256。

第三，verifier 用 CSPRNG 產生。它跟 session ID 一樣是讓人猜不到的秘密，用 Math.random 湊出來的字串長度夠但熵不夠，猜得到（第 2 課）。每次授權都產生新的，存在發起授權的那個 session 裡，換完 token 就刪掉。

PKCE 還順便擋住了上一節的授權碼注入。攻擊者塞進來的 code，綁的是攻擊者那次授權的 challenge；王小明的 client 換 token 時送出的是王小明 session 裡的 verifier，兩者對不上，換不到。這就是 RFC 9700 說「確認授權伺服器支援 PKCE 時，可以依賴它防 CSRF」的原因。也因為它能防注入，PKCE 不只給公開 client 用，有 client_secret 的機密 client 也建議用。

不過「確認授權伺服器支援」這個前提很重要：PKCE 的比對是在授權伺服器那一端做的，只要那一端的判斷有漏洞，client 這邊做得再對也沒用。

授權伺服器那一端：PKCE 降級

RFC 9700 規定：公開 client MUST 用 PKCE，機密 client 也 RECOMMENDED；授權伺服器 MUST 支援 PKCE。站在外送平台的位置，兌換授權碼時要看兩件事：當初授權時有沒有存 challenge、這次換 token 有沒有帶 verifier。組合起來有五種情況：

前三列很直觀，第四列最容易寫錯。一個看似合理的寫法是「當初沒有 challenge，就不看 verifier」，它會被 PKCE 降級攻擊利用：攻擊者自己發起一個不帶 code_challenge 的授權流程，拿到一個沒有綁定 challenge 的 code，塞給受害者的 client。受害者的 client 照常送出自己的 verifier，授權伺服器發現這個 code 當初沒有 challenge，就略過檢查，換成功了。PKCE 擋注入的效果就這樣消失。所以 RFC 9700 §2.1.1 要求授權伺服器只在授權請求帶了 code_challenge 時，才接受含 code_verifier 的 token 請求。

授權伺服器那一端：授權碼本身的規則

除了 PKCE，授權碼本身也要守三條規則，它們就是前面一直說的「短效、一次性」的具體寫法。

一次性：RFC 6749 §4.1.2 規定授權碼被用第二次時 MUST 拒絕，SHOULD 撤銷用這個授權碼發出的所有 token。同一個 code 出現第二次，代表它外洩了，而且授權伺服器分不出哪一次是正牌 client，所以連第一次發出去的 token 也撤銷。這跟第 10 課的 refresh token 重用偵測是同一個想法。

短效：RFC 6749 建議最多 10 分鐘。正常的 client 拿到 code 幾秒內就會換，有效期越短，外流的 code 能被利用的時間越短。

綁定：授權碼綁定發起授權的 client_id 和 redirect_uri，換 token 時兩者都要相同。這就是第 5 步要再送一次 redirect_uri 的原因。

練習 3 會把這些規則寫成外送平台的兌換程式，它的設計是：code 只要出現在 token 請求裡一次，不論這次成功或失敗都作廢。攻擊者拿偷來的 code 亂試一次，正牌 client 也換不到了，使用者要重新授權一次，但攻擊者也什麼都拿不到。寧可多讓使用者按一次，不給攻擊者重試的機會。

到這裡，網站版和 App 版的匯入功能都安全了。回頭看，這些規則分散在 RFC 6749、7636、8252、9207、9700 好幾份文件裡。下一次開新專案，要有一張清單一次對齊。

implicit grant 是早年為瀏覽器設計的捷徑：少了「用授權碼換 token」那一步，授權伺服器直接把 access token 放在網址裡導回。少掉的那一步，正是 token 不經過瀏覽器、能做 client 認證與 PKCE 比對的地方，所以它在今天的標準下站不住。密碼授權則就是開場那個「請王小明給密碼」的做法換了個名字。OAuth 的新版規格 OAuth 2.1 也拿掉了這兩種 grant，目前的狀態見課末「補充與查表」。

最後回到讀者最熟悉的地方：咖啡店的前台是 Vue SPA。如果 Vue 前台也要串外送平台，token 該放哪裡？RFC 10017（OAuth 2.0 for Browser-Based Applications，BCP 212，2026 年 8 月）依安全性由高到低列出三種架構：

  • BFF（第 11 課）：咖啡店後端當機密 client，跑整個授權碼流程，access token 與 refresh token 都只存在後端，瀏覽器只拿 session cookie。處理個資、付款的應用強烈建議用這個。這課一路做的網站版，就是這個架構。
  • token-mediating backend：後端一樣當機密 client 換 token、保管 refresh token，但把 access token 交給瀏覽器裡的 JS 直接呼叫 API。access token 仍在瀏覽器裡，XSS 偷得到。
  • 純瀏覽器 client：Vue 自己當公開 client，在 JS 裡產生 verifier、換 token、保管 token。

三種都用授權碼流程加 PKCE，差別在 verifier 和 token 放在哪裡。token 離瀏覽器越遠，一次 XSS 能拿走的東西就越少。

💡 實務上：流程交給成熟套件，設定由你負責
正式專案通常不會從零手寫這課的流程，Node 後端常用 openid-client 或框架的登入套件，它們內建 state、PKCE 的產生與檢查。但要哪些 scope、redirect_uri 註冊哪些、token 存在哪裡，套件不會替你決定。咖啡店已經有自己的後端，Vue 前台就直接選 BFF，token 不進瀏覽器；純瀏覽器 client 只適合沒有後端、資料不敏感的小工具。資深工程師 review 時會看：套件還有沒有在維護、PKCE 是否用 S256、callback 失敗時使用者看到的是清楚的訊息還是白畫面。

這課的任務完成了：咖啡店讀得到王小明在外送平台的訂單，只讀得到訂單，王小明隨時能收回，密碼從沒經過咖啡店；網站版靠 client_secret，App 版靠 PKCE，兩者都用 redirect_uri、state、iss 擋住 code 被送錯或被塞進來。

補充與查表

主線用不到、但串接平台或設計授權伺服器時會查的細節。

client 認證的另一種做法：private_key_jwt

第 5 步的 client_secret 是 client 和授權伺服器共用的密碼，兩邊都要存。RFC 9700 建議改用非對稱的方式，例如 client 用自己的私鑰簽一個短效 JWT 來證明身分（private_key_jwt），授權伺服器只存公鑰，外洩風險較小。

各平台的 PKCE 支援

LINE Login 只支援 S256；Google 的 discovery 文件同時列出 plain 與 S256（2026-10-31 查詢）。不管平台支援什麼，我們一律用 S256。

OAuth 2.1 的狀態

OAuth 2.1 是把 RFC 9700 這些規則整理成新版規格的草案，2026-10-31 的最新版是 draft-ietf-oauth-v2-1-17，還沒成為 RFC。內容跟 RFC 9700 的表一致（拿掉 implicit 與密碼授權、授權碼流程一律 PKCE），所以照 RFC 9700 做就對齊了。

還有哪些流程

  • client credentials：沒有使用者，服務代表自己呼叫 API（例如咖啡店的對帳排程呼叫金流 API）。第 17 課講。
  • PAR（Pushed Authorization Requests，RFC 9126）：client 先用後端通道把授權參數 POST 給授權伺服器，拿回一個 request_uri，導向時網址只帶它。參數不經過瀏覽器，也不能被竄改。金融等高安全要求的場合常用。
  • DPoP（RFC 9449）：client 每次用 token 時，用自己的私鑰簽一個證明，token 被偷了沒有私鑰也用不了。這就是 RFC 9700 說的 sender-constrained token。

PAR 與 DPoP 是進階強化，知道用途、遇到需求時再查規格就好。

練習

練習 1：寫 PKCE 的 client 端。createCodeVerifier()：用 CSPRNG 產生 32 bytes，回傳 base64url（43 個字元）。codeChallengeS256(verifier)：回傳 code_verifier 這個字串的 SHA-256 的 base64url。base64urlEncode 已經寫好（第 2 課練習 1 的答案）。

練習 2：寫 client 端的第 1 步與第 4 步。

  • buildAuthorizeUrl(config, p)：用 new URL(config.authorizeEndpoint) 與它的 searchParams 加上 response_type=code、client_id、redirect_uri、scope（陣列用一個空白連起來）、state、code_challenge、code_challenge_method=S256，回傳 href。授權端點本身可能已經有 query，要保留。
  • handleCallback(callbackUrl, saved)：依序檢查。① 有 error 參數 → authorization_error（就算同時帶了 code）；② state 必須剛好出現一次而且等於 saved.state，否則 state_mismatch；③ iss 必須剛好出現一次而且等於 saved.issuer（字串比對，不正規化），否則 issuer_mismatch；④ 沒有 code 或是空字串 → missing_code；都通過回傳 { ok: true, code }。

練習 3：換到授權伺服器這一端。

  • validateRedirectUri(registered, requested)：requested 跟 registered 裡某一個字串完全相等才回 true。唯一例外：註冊了 http://127.0.0.1/…（不寫 port）時，請求可以在 127.0.0.1 後面多一個 :port，其餘部分仍要一字不差。不要用 new URL 正規化後比對。
  • redeemCode(store, req)：兌換授權碼，失敗一律回 { ok: false, error: 'invalid_grant' }。規則：code 不存在 → 失敗；code 已經用過 → 失敗，並把它當初發出的 issuedTokenId（有的話）加進 store.revokedTokens；否則先把 code 標成用過（這次不論成敗都作廢），再檢查：req.now - createdAt 要小於 CODE_TTL_MS（10 分鐘，毫秒）；clientId、redirectUri 要跟授權時相同；PKCE 依上面那張表（存了 challenge 就必須有 verifier 而且 S256 相符；沒存 challenge 卻帶了 verifier 也拒絕）。全部通過時呼叫 store.issueToken(clientId) 取得 tokenId，記到 issuedTokenId，回傳 { ok: true, tokenId }。codeChallengeS256 已經寫好。

練習 4：咖啡店做「用外送平台帳號登入」：走完授權碼流程拿到 access token，呼叫外送平台的 /me 拿到使用者 ID，就當作這個人登入了。問題在哪裡？

✓ OAuth 回答「這個 client 能不能讀這些資料」，不是「現在操作的是誰」。access token 的受眾是資源伺服器；拿得到 /me 只代表「某個 client 拿到了這個使用者的授權」，可能是別的 App 拿到後被塞進你的流程（尤其是會把 token 放在網址裡的 implicit 流程），也沒有登入時間、nonce 可以綁回這次登入。OpenID Connect 加上 ID token：aud 是你的 client_id、有 nonce 與 auth_time（下一課）。state 是 client 自己產生的隨機值，不能放身分，b 錯；refresh token 也只是授權，d 錯。

練習 5：咖啡店已經用了 PKCE（S256），還需要 state 嗎？

✓ 攻擊者塞給受害者的 code 綁的是攻擊者的 code_challenge，受害者的 client 送出的是受害者 session 裡的 verifier，對不上就換不到 token，所以 PKCE 也擋得住授權碼注入（OAuth 的 CSRF），a 錯。前提是授權伺服器真的檢查 PKCE、也防降級，所以 RFC 9700 說「確認支援時」才可以只靠 PKCE。state 只是多一個比對，不會降低安全性，c 錯。HTTPS 只保護傳輸，攻擊者用的是自己合法取得的 code，d 錯。

練習 6：為什麼 implicit grant（授權伺服器直接把 access token 放在 redirect_uri 的 # 後面導回）被 RFC 9700 列為不應使用？

✓ implicit 少了「換 token」這一步，代價是真正有價值的 access token 直接出現在網址裡，沒有一次性、沒有 verifier、也沒有後端通道的 client 認證。少掉的那一步正是 token 不經過瀏覽器、能驗證 client 與 verifier 的地方，所以少一步不是優點，b 錯。fragment（# 後面）瀏覽器不會送給伺服器，所以不會進 access log，c 錯；但它仍在歷史紀錄裡，被導到別的頁面時也可能跟著過去。它當初正是為瀏覽器設計的，d 錯。現在瀏覽器 client 用授權碼＋PKCE，或更好的 BFF。

常見錯誤

  • 把 OAuth 當登入協定：只拿 access token 查 /me 就當作登入。要登入用 OpenID Connect 的 ID token（下一課）。
  • 不檢查 state，或「有帶才比對」：攻擊者就能把自己的授權碼塞給受害者。state 用 CSPRNG 產生、存在這個使用者的 session、沒帶也拒絕、用完就刪。
  • redirect_uri 用前綴、萬用字元或正規化後比對：callbackx、子網域、@、.. 都能繞過。精確字串比對，只有 loopback 的 port 例外。
  • PKCE 用 plain、verifier 太短、用 Math.random：用 32 bytes CSPRNG 的 base64url 當 verifier，只用 S256，對 verifier 字串本身做 SHA-256。
  • 授權伺服器沒存 challenge 就不看 verifier：PKCE 降級。沒有 challenge 卻收到 verifier 也要拒絕。
  • 把 client secret 放進 Vue 或手機 App：打包後的程式碼誰都拆得開，公開 client 沒有秘密。用 PKCE，或讓後端當 BFF。
  • 授權碼可以重複使用、有效期太長：一次性、最多 10 分鐘，重複出現時撤銷已發出的 token。
  • 還在用 implicit 或密碼授權：改用授權碼流程加 PKCE。
  • 串好幾個授權伺服器卻不看 iss：mix-up 攻擊把 code 送錯地方。記住這次是向誰發起的，callback 的 iss 字串比對。
  • 用字串相加組授權網址：redirect_uri、state 裡的 &、? 會把參數切斷。用 URL 與 URLSearchParams。

小結

  • 請使用者交出第三方密碼，client 會拿到全部權限、收不回來、外洩跟著搬家。OAuth 2.0 是授權框架：資源擁有者在授權伺服器自己的頁面同意，client 拿到有範圍（scope）、可撤銷的 access token 去呼叫資源伺服器。它回答「能不能讀」，不回答「你是誰」，不是登入協定。
  • 授權碼流程：導向 /authorize（前端通道）→ 登入同意 → 帶 code、state、iss 導回 → client 比對 → 後端通道 POST /token（code、redirect_uri、code_verifier、client 認證）→ 拿到 token。網址容易外流，所以前端通道只傳短效、一次性的授權碼，token 只走後端通道。
  • code 不能被送錯地方：redirect_uri 事先註冊、精確字串比對，只有 loopback 的 port 例外。code 不能被塞進來：state 綁定使用者 session、一次性、沒帶也拒絕，擋授權碼注入；串多家授權伺服器時用 iss 擋 mix-up。
  • 機密 client 能保管 client_secret，公開 client（Vue SPA、手機 App）不能。PKCE 讓每次授權有自己的一次性秘密：verifier 是 32 bytes CSPRNG 的 base64url，challenge = BASE64URL(SHA-256(verifier))，只用 S256。公開 client 必須用、機密 client 也建議用；它同時擋授權碼攔截與注入，授權伺服器要防降級。
  • 授權碼一次性、短效、綁定 client_id 與 redirect_uri；重複出現時撤銷已發出的 token。
  • 照 RFC 9700 做：不用 implicit、不用密碼授權、access token 限定 audience、公開 client 的 refresh token 要輪替。Vue 前台有後端時選 BFF，token 不進瀏覽器。
