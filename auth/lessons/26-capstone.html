階段 6：資深工程師的資安實務 · 第 26 課

期末專題：咖啡店 API 安全強化

咖啡店的 API 長大了：同一個平台上有兩個咖啡品牌，每個品牌有好幾間門市，顧客、店員、店長各自登入。功能都做好了，測試也都是綠的，下週就要上線。上線前，主管找你做一次安全審查，只給你一個線索：這份程式碼裡藏著 7 個漏洞，每一個都是前面某一課教過、在真實專案裡反覆出現的錯。

這課從頭到尾只做這一件事：在上線前把這 7 個漏洞找出來、決定先修哪個、修在根本原因上並留下證明，最後準備好上線後真的出事時怎麼應對。這課沒有新的技術，練的是資深工程師做安全審查的工作方式：從哪裡開始看、怎麼判斷輕重、怎麼修才不會再回來。

這課的路線：
  1. 要審的是什麼：專案有哪些租戶、門市、角色與端點；把它跑起來，用 curl 親眼看到第一個漏洞。
  2. 從哪裡開始找：為什麼不是從第一個檔案讀到最後一個，而是先畫威脅模型、盯住信任邊界，再排出先後（開場問題的最小答案）。
  3. 找到之後修在哪裡：從症狀追到根本原因，讓同一類的漏洞一次消失，並用回歸測試證明它不會回來。
  4. 七個漏洞怎麼一個一個修：每一題都照同一套步驟，修完還有不完美的地方怎麼留紀錄。
  5. 上線後出事怎麼辦、下一個專案怎麼審：事故演練的原則，以及把整門課濃縮成上線前檢查清單。
這課會用到：
  • 第 21 課的 NestJS 認證與授權：全域 guard 讓所有路由預設要登入，@Public() 標出例外；refresh token 每用一次就換新。起始專案沿用同樣的寫法，但授權用簡單的 @Roles() 角色檢查，不是第 21 課的權限表。
  • 第 19 課的物件與欄位授權、第 20 課的租戶隔離：查詢時就加上擁有者與租戶條件，回應只放允許的欄位。
  • 第 25 課的威脅建模與事故劇本：先畫資料流程圖、用 STRIDE 逐一問會出什麼錯；出事時照事先寫好的步驟處理。

要審的是什麼？先把專案跑起來，親眼看一次漏洞

審查之前要先回答一個問題：這個系統在保護什麼、替誰保護。不知道「誰不該看到什麼」，就無從判斷一段程式碼有沒有漏洞。起始專案在 nestjs/practice/start/auth26/，是 NestJS 12＋Prisma 7＋PostgreSQL，資料的關係是：

  • 租戶（Tenant）：一個咖啡品牌。豆香咖啡（id 1）與山嵐咖啡（id 2），彼此的資料絕對不能互相看到。
  • 門市（Store）：豆香信義店（1）、豆香大安店（2）、山嵐中山店（3）、山嵐板橋店（4）。
  • 使用者（User）：role 是 customer、barista（店員，有 storeId）或 manager（店長，管整個品牌）。還有 passwordHash、mfaSecret、points（集點）、tokenVersion。
  • 訂單、商品、refresh token、重設密碼紀錄：orders、products、refresh_tokens、password_resets。

從這份清單就能讀出這次審查要守住的幾條線。第一條是品牌之間：豆香和山嵐是兩家不同的公司，只是剛好用同一個平台，豆香的店長看到山嵐的訂單，就是一家公司的營業資料外洩給競爭對手。第二條是品牌之內：大安店的店員不該看信義店的訂單。第三條是欄位：passwordHash、mfaSecret 這種欄位誰都不該拿到，role、points 這種欄位不能讓使用者自己改。

資料是要保護的東西，端點是攻擊者碰得到它們的入口。下表的「誰能用」是這個系統應該做到的規則；審查要確認的，就是程式碼真的照這張表執行，而且沒有表上沒寫的後門：

端點誰能用做什麼
POST /auth/login、/auth/refresh、/auth/logout公開登入發 access token 與 __Secure-rt cookie、輪替、登出
GET /me、PATCH /me登入的人看自己的資料、改名字與手機
GET /stores/:storeId/orders、/orders/:orderId店員、店長門市的訂單
GET /stores/:storeId/customers店員、店長常來這間門市的顧客（集點、叫號）
POST /password-reset/request、/confirm公開忘記密碼：寄信、用信裡的 token 設新密碼
GET /products、POST /products登入的人／店長品牌的菜單、新增商品
POST /products/:id/image-from-url店長貼上圖片網址，伺服器下載後存到商品上

只讀表格和程式碼，很容易說服自己「這裡應該沒問題」。所以第一步是讓專案跑起來，用攻擊者的角度實際打一次。先把環境準備好（docker compose 的用法見 NestJS 課第 12 課）。第一次執行 check.mjs 會建立 work/auth26/，之後所有修改都在那裡做：

cd learn/nestjs/practice
docker compose up -d --wait          # PostgreSQL（NestJS 課第 12 課）
cd ../..
node check.mjs nestjs auth26         # 建立 work/auth26/，跑一次判分：現在每一題都沒過

cd nestjs/practice/work/auth26
npx prisma generate                  # 產生 Prisma Client（src/generated/）
npx prisma migrate deploy            # 在開發資料庫 nest_auth26 建表
npx prisma db seed                   # 灌入兩個品牌的資料，每個帳號的密碼都是 latte-art-2026
npm run start:dev                    # http://localhost:3100

種子資料準備了兩個品牌的店長、店員與顧客，完整的帳號列表在課末的「補充與查表」。現在用豆香的店長登入，拿到 access token，再去要山嵐中山店（門市 3）的訂單。照上面的規則，這個請求應該被拒絕：

TOKEN=$(curl -s localhost:3100/auth/login -H 'content-type: application/json' \
  -d '{"email":"manager@douxiang.example","password":"latte-art-2026"}' | node -pe 'JSON.parse(require("fs").readFileSync(0)).accessToken')
curl -s localhost:3100/stores/3/orders -H "Authorization: Bearer $TOKEN"    # 豆香的店長看到了山嵐的訂單

結果是山嵐的訂單整份回來了。原因藏在兩個地方：controller 上的 @Roles('barista', 'manager') 只確認「你是店員或店長」，沒有問「你是哪個品牌、哪間門市的」；service 收到了登入的使用者，查詢條件卻只用了網址上的 storeId。角色對了，範圍沒檢查，這就是第 19 課的物件層級授權漏洞。

修之前親眼看到攻擊成功，有兩個用處：確認你真的理解這個攻擊怎麼運作，而且修完之後可以拿同一個指令再打一次，看到它被擋下。判分測試在 work/auth26/ex1.test.ts～ex7.test.ts，做的就是同一件事的自動化版本，這點下兩節會再回來談。

第一個漏洞是照著端點表順手打出來的。剩下六個分散在認證、重設密碼、商品、全域設定各處，從第一個檔案讀到最後一個，讀完了也說不出哪裡最要緊。下一個問題是：該從哪裡開始找？

從哪裡開始找？先畫威脅模型，盯住信任邊界

回答「從哪裡開始找」，靠的是第 25 課的威脅建模：不先讀程式碼，先畫出資料從哪裡來、往哪裡去，再問每個地方可能出什麼錯。畫圖的目的，是找出圖上的信任邊界（trust boundary）。

信任邊界是資料從比較不可信的一側，進到比較可信的一側的那條線。在線的外面，資料是任何人都能捏造的：網址、body、標頭、cookie，攻擊者全都可以改。進到線的裡面之後，程式碼就開始把它當成事實來用，拿去查資料庫、組信件內容、發出連線。漏洞幾乎都出在這條線上，因為那裡是「外面的資料第一次被相信」的地方。剛才的 /stores/3/orders 就是例子：3 是攻擊者在網址上寫的，跨過邊界之後，程式碼直接把它當成「這個人有權看的門市」。

圖上有兩條邊界。左邊那條大家都會想到：網際網路進到 API。右邊那條比較容易忽略：API 把資料送到自己以外的系統時，送出去的東西如果混著使用者給的值，就可能讓那個系統做出我們沒打算讓它做的事。例如信裡的連結如果是用請求的標頭組出來的，攻擊者就能決定信裡的網址；伺服器如果照使用者給的網址去下載圖片，攻擊者就能讓伺服器替他連到內網。

有了邊界，接著對每個跨邊界的端點用 STRIDE 問六種錯：偽冒、竄改、否認、資訊洩漏、阻斷服務、權限提升。不需要每格都填滿，目標是替每個端點找出「它最可能出什麼錯」，這就是接下來讀程式碼時要盯的地方：

端點最該擔心的威脅要檢查什麼
/stores/:storeId/...資訊洩漏、權限提升路徑上的 id 是攻擊者給的：門市屬不屬於這個人、訂單在不在這間門市
PATCH /me、GET /me竄改、資訊洩漏body 能不能夾帶 role；回應是不是整筆資料列
/auth/*偽冒JWT 驗證的每一條規則、refresh 被偷時能不能發現、能不能無限猜密碼
/password-reset/*偽冒、資訊洩漏token 怎麼存、多久失效、能不能重用；回應會不會洩漏誰是會員
image-from-url權限提升（借伺服器的網路位置）伺服器會連到哪裡、DNS 與重導向
全域設定資訊洩漏錯誤回應、CORS、安全標頭

這張表把「讀整個專案」縮小成「讀六個地方、每個地方問一個具體問題」。這就是開場問題的答案：審查從威脅模型開始，因為它告訴你該讀哪裡、讀的時候要問什麼。

找到的漏洞不會一樣急。時間有限時，要用第 25 課的「可能性 × 影響」排順序：可能性看利用的門檻有多低，影響看出事時傷害有多大。不用登入、一個 curl 就能利用、影響所有租戶的，排在最前面；需要先偷到 token 才能利用的，往後排。剛才的跨品牌讀取只需要一個正常的店長帳號、一行 curl，影響兩個品牌的全部訂單，所以排在最前面。

💡 實務上：審查多半是一個 PR、一份設計，不是整個專案
工作中很少有人給你一整個專案從頭審，更常見的是「咖啡店要串外送平台，這份設計幫忙看一下」或一個新增端點的 PR。資深工程師會先問三件事：誰能呼叫它、哪些 id 或網址是使用者給的、它會連到我們以外的哪些系統，再決定細看哪裡。審查要有時間上限，找到的問題開成工單（ticket）、標上嚴重程度，跟 PM 講清楚哪些會擋上線、哪些可以排進下一版。不要想一個人全部修完：該由原作者修的就交回去，你負責確認修法打在根本原因上。

照著表讀程式碼，七個漏洞會一個一個浮出來。找到之後，最直覺的修法是在出事的那個 handler 加一個 if，測試就過了。下一節說明為什麼這樣修，下個月漏洞還會回來。

找到之後修在哪裡？從症狀追到根本原因

在出事的地方加一個 if，修掉的是症狀。症狀是你看到的那一個現象；根本原因（root cause）是讓這個現象發生的源頭，同一個源頭通常會在別的地方產生同樣的症狀。拿剛才的跨品牌讀取來說：

  • 症狀：剛才 curl 打的是列表 GET /stores/3/orders；同一個漏洞的單筆版本 GET /stores/3/orders/4 也讓豆香的店長看到山嵐的訂單。
  • 只修症狀：在 OrdersController.get 加一個 if。測試過了，但 GET /stores/3/orders（列表）和 GET /stores/3/customers 一樣能看，下個月新增的 /stores/:storeId/shifts 也會忘記檢查。
  • 根本原因：「這個人能不能碰這間門市」沒有一個固定的地方。修法是寫一個所有 /stores/:storeId/... 的 service 都會呼叫的函式，並且在查詢條件裡帶上範圍（where: { id: orderId, storeId }），讓「忘記檢查」變成很難犯的錯。

判斷自己找到的是不是根本原因，可以問：「如果明天有人新增一個類似的端點，他會不會犯同樣的錯？」如果會，你修的還是症狀。同樣的問法套到另外兩個漏洞：PATCH /me 能改 role 的根本原因不只在這個 handler，而是全域的 ValidationPipe（NestJS 課第 7 課）沒有拒絕多餘的欄位，所以每個接收 body 的端點都有同樣的風險；GET /me 外洩 passwordHash 的根本原因是「回傳整筆資料列」這個習慣，所以店員看的顧客名單也一樣外洩。這也是為什麼練習的題目只描述症狀，測試卻會打同一類的其他端點。

修在根本原因上，解決的是「同一類的漏洞現在都消失」。還有另一半要解決：「以後也不會再出現」。程式碼會被重構、會被別人改，半年後有人覺得那個共用函式多餘、把它拿掉，漏洞就悄悄回來了。擋住這件事的是回歸測試（regression test）：一個證明某個漏洞修好了、而且以後重構時會失敗提醒你的測試。它就是把開頭那行 curl 寫成程式，放進每次提交都會跑的 CI，有人把檢查拿掉時，CI 會變紅。

回歸測試只證明攻擊被擋下還不夠。如果只有攻擊測試，把端點改成「一律拒絕」也能通過，但店員從此看不到自己門市的訂單。所以每一題的判分測試都同時有兩種：功能測試確認正常使用者還能用，攻擊測試確認攻擊被擋下。這是測試設計的基本功，你自己替安全修補寫測試時也照這樣做。

根本原因、回歸測試、功能測試，是每一個修補都要做到的三件事。但這裡有七個漏洞，同時開工很容易改到一半分不清哪個修好了、哪個把別的改壞了。下一節把這三件事排成一套固定的步驟。

七個漏洞怎麼一個一個修，而不把別的改壞？

有了修補要達到的標準，接下來是執行的順序。每一題都照同樣的步驟做，不要一次改七個地方再看結果，否則測試一紅，你不知道是哪一處改動造成的：

  1. 重現：用 curl 或讀測試，親眼看到攻擊成功。
  2. 定位：從路由找到 controller、service，找出是哪一層少了什麼。用 grep -rn "findUnique\|origin: true\|headers.host" src 這類搜尋找同一個模式出現在哪些地方。
  3. 修在根本原因：能放在共用的地方就放在共用的地方。
  4. 跑全部的測試：node check.mjs nestjs auth26。只看這一題過了不夠，修補很容易把別的功能改壞（例如限流擋到正常登入、CORS 擋到前台）。
  5. 再當一次攻擊者：用剛才的 curl 確認真的擋下來了。

第 2 步的搜尋，就是上一節「同一個源頭會在別處產生同樣症狀」的實際做法：在 orders.service.ts 看到一個沒帶範圍的 findUnique，就搜尋整個 src 還有哪些查詢也是這樣寫的。第 4 步跑全部的測試，對應的是上一節的功能測試：你這一題的修補，可能讓另一題的正常使用者不能用。

七題都修完之後，專案還是會有不完美的地方，這是正常的。例如登入限流（練習 5 要寫完的 LoginThrottleService）的計數放在記憶體裡，部署三台時上限會變三倍（第 16 課）。審查的目標不是做出完美的系統，而是讓每個已知的弱點都有人知道、有人決定。在決策紀錄寫下「目前單台，多台時改用 Redis」，比假裝它不存在好。

💡 實務上：決策紀錄讓修法不會被「簡化」掉
修好一個漏洞之後，花兩分鐘寫下決策紀錄（ADR，系統設計課第 18 課）：問題是什麼、影響範圍、選了哪個修法、沒選的修法與原因。例如「租戶隔離：選擇在 service 層檢查、沒有用 PostgreSQL RLS，因為目前只有一個服務存取資料庫；第二個服務出現時重新評估」。半年後有人問「為什麼這樣寫」，答案在這裡，不在某個離職同事的腦袋裡。

到這裡，七個漏洞修完、測試全綠、紀錄寫好，專案可以上線了。但修好已知的漏洞，不代表上線後不會出事：token 可能被偷、秘密可能被不小心印進 log。下一節處理上線之後的事。

上線後出事怎麼辦？事故演練

審查擋得住的是已知的漏洞；上線後真正遇到的，常常是另一種狀況：防護正常運作，但有東西已經外洩了。練習 9、10 是兩個值班時真的會遇到的情境，用第 25 課的劇本回答。兩題背後是同一組原則，每一條都是在糾正一個值班時很自然、但會讓事情變糟的直覺：

  • 先止血，再調查：直覺是先搞清楚發生了什麼再動手，但查的過程中攻擊者還在用外洩的東西。所以先讓它失效（輪替金鑰、撤銷 token），再去查。
  • 「系統擋下來了」也是事故：直覺是「擋下來了，沒事」。但被擋下的攻擊告訴你有人拿到了不該有的東西，擋下的只是這一次，攻擊者可能已經在被擋之前用過它。
  • 刪掉證據不等於處理完：直覺是把外洩的 log 刪掉就好。但秘密一旦出現在 log、聊天室、git 歷史，就當作已經外洩，刪除只是避免更多人看到，已經拿到的人手上那份還在。
  • 留下紀錄、做事後檢討：時間軸、影響範圍、根本原因、改進事項（部署課第 25 課）。事後檢討找的根本原因，跟修漏洞時一樣，是「為什麼會發生、怎麼讓它不再發生」，而不是「誰犯的錯」。

這次審查和演練，處理的是咖啡店這一個專案。下一個專案、下一個 PR 進來時，不可能每次都從頭回想 26 課的內容。最後一節把整門課整理成一份可以重複使用的清單。

練習

所有修改都在 nestjs/practice/work/auth26/。每一題只描述症狀與攻擊方式，程式碼的位置要自己找；下面列的檔案是標準答案改過的地方，你的修法可以不同，也可以新增檔案（例如共用的檢查函式）。判分指令：在 learn/ 執行 node check.mjs nestjs auth26。不要改 ex*.test.ts 和 test-fixtures.ts。

練習 1：物件層級授權與租戶隔離（OWASP API1）。現在改網址裡的 storeId 或 orderId，就能看到別的品牌、別間門市的訂單。修到：店長只能看自己品牌所有門市、店員只能看自己的門市，而且訂單必須真的在路徑上的那間門市；範圍外與不存在的一律回一模一樣的 404。

測試會打 /stores/:storeId/orders/:orderId、訂單列表，以及有同樣問題的 /stores/:storeId/customers。只檢查「路徑的門市屬於我的品牌」不夠：/stores/1/orders/4 的訂單 4 在山嵐。回 403 也不行，它等於告訴對方這筆資料存在。

練習 2：欄位層級授權（OWASP API3）。顧客對 PATCH /me 送 {"role":"manager"}、points 或 tenantId 都會被寫進資料庫；GET /me、PATCH /me 與店員看的顧客名單會回傳 passwordHash、mfaSecret。修到：

  • 多餘的欄位回 400，資料庫完全不變（不是悄悄丟掉後回 200）。
  • GET /me 與 PATCH /me 只回 id、email、name、phone、role、points，自己看得到完整手機。
  • 顧客名單每一筆只有 id、name、phone、points，手機遮罩成前 4 碼＋***＋後 3 碼，例如 0912***678。

用允許清單（列出可以給的欄位），不要用排除清單：只排除 passwordHash，mfaSecret 和以後新增的欄位還是會外流。

練習 3：token 的設定（OWASP API2）。兩個問題：用同一把秘密簽、但 aud 是別的服務的 token，或用 HS512 簽的 token，都能呼叫 API；refresh token 用過就從資料庫刪掉，被偷的舊 token 再被拿來用時，系統認不出這是重用。修到：驗證時固定演算法、發行者（iss）與接收者（aud）；用過的 refresh token 標記為已使用，再被使用時回 401 並撤銷整個家族（同一次登入輪替出來的所有 token），其他裝置的登入不受影響。用一句原子（atomic）的 updateMany 判斷「這次是不是第一個用它的請求」：條件（usedAt 還是空的）和寫入在同一句 SQL 裡完成，兩個請求同時拿同一個 token 來，也只有一個的 count 是 1。先查再改的兩句寫法，兩個請求會同時看到「還沒用過」。

練習 4：忘記密碼。現在的流程：沒註冊的 email 回不同的訊息、token 原樣存在資料庫、不會過期、可以重複使用、信裡的連結用請求的 Host 標頭組成。全部照第 16 課修好：

  • 存在與不存在的 email 回應完全相同（存在的才寄信）。
  • 資料庫的 tokenHash 存 token 的 SHA-256（hex）。
  • 連結用設定裡的 APP_URL：${APP_URL}/reset-password?token=…。
  • 30 分鐘後失效、只能用一次（失敗回 400）。時間一律用注入的 CLOCK。
  • 重設成功後，這個人所有舊的 access token 與 refresh token 立刻失效。

只撤銷 refresh token 不夠：已經發出去的 access token 還能用到 15 分鐘後過期。想想第 11 課的 tokenVersion。

練習 5：防暴力破解。登入沒有任何次數限制。LoginThrottleService 只有空殼，也還沒接到登入流程。照第 16 課練習 3 的規則寫完並接上：

  • 每帳號（用輸入的 email 字串）：連續失敗 n 次（n ≥ 5）後，要從最後一次失敗起等 2n−5 秒，最多 900 秒；登入成功歸零。
  • 每 IP（req.ip，專案已經設好 trust proxy）：固定視窗 15 分鐘、100 次失敗；登入成功不重設 IP 的計數。
  • 被擋時不驗密碼，回 429 並帶 Retry-After（秒，無條件進位）。
  • 帳號不存在時也要跑一次密碼驗證（用一個假的 argon2id 雜湊），回應時間才不會洩漏帳號存不存在。

只用 @nestjs/throttler 限 IP 擋不住換 IP 猜同一個帳號；「失敗 5 次永久鎖住」會被拿來鎖住所有會員。

練習 6：SSRF（OWASP API7）。POST /products/:id/image-from-url 用 fetch 抓任何網址，包括 http://127.0.0.1:5432 與雲端 metadata 169.254.169.254。專案的 src/products/net.ts 已經有兩個 provider：DnsResolver.resolve(hostname) 回傳所有位址；HttpFetcher.get(url, ip, { maxBytes, timeoutMs }) 連到指定的 IP、不自己查 DNS、不跟隨重導向。改用它們，照第 22 課的規則：

  • 只接受 https、預設的 443 port、沒有帳號密碼的網址。
  • 解析出的每一個位址都必須是公開位址（包含 IPv6 與 ::ffff:127.0.0.1 這種寫法；可以用 Node 內建的 net.BlockList）。
  • 連線用剛驗證過的 IP；重導向（3xx）最多跟 3 次，每一跳都重新解析、重新驗證。
  • maxBytes 是 5 MB（5 * 1024 * 1024），timeoutMs 是 5000；不是 200 的圖片就拒絕。
  • 失敗一律回同一個 400 訊息，不透露是哪一步、連到了什麼。

測試會把兩個 provider 換成假的跑攻擊清單，另外在 127.0.0.1 開一個真的「內網服務」，確認它一個請求都沒收到。

練習 7：安全設定（OWASP API8）。三個問題：新增重複名稱的商品時，409 回應帶著 Prisma 的錯誤訊息（有資料表與欄位名稱）和 stack；CORS 用 origin: true 反射任何來源而且允許 credentials；沒有安全標頭。修到：

  • 一個處理所有錯誤的 exception filter：HttpException 照常回應；唯一鍵衝突（P2002）回 409 和你自己寫的訊息；其他錯誤回 500 與 requestId，細節只寫進 log。
  • CORS 只允許設定 CORS_ORIGINS 裡的來源（逗號分隔）：用 ConfigService 讀，不要把網址寫死在程式裡，測試會換成別的設定值。
  • 用 helmet（8.3.0，已安裝）加上預設的安全標頭。

練習 8：七個漏洞都找到了，但上線前只夠時間修三個。下面哪一種排序方式最合理？

✓ c：排序依據是風險，不是工作量。跨租戶讀取不需要特殊條件、影響所有品牌；SSRF 可能拿到雲端憑證；重設密碼的 Host 注入能接管帳號。這三個應該先修。a 用工作量排序，最危險的可能留到最後；b 的編號是整個業界的整體排名，不是你這個專案的風險；d 的測試數量只反映測試怎麼寫，不反映風險。暫時不修的要寫下來、讓負責人知道並接受，這叫風險接受，不是忘記。

練習 9：告警顯示：凌晨 3:12，王小明一個已經撤銷的 refresh token 家族又被拿來用了，API 回了 401。你要做什麼？

✓ b：被撤銷的家族還有人拿來用，代表有一份 token 在攻擊者手上（或在某個不該存 token 的地方，例如 log、外掛）。擋下的只是這一次請求，攻擊者可能已經在撤銷之前用過它。a 只看到這一次被擋，沒處理已經外洩的 token 與攻擊者可能做過的事；c 拆掉了偵測能力；d 讓真正的使用者不能用，而且沒有回答「怎麼外洩的」，下次還會發生。

練習 10：有人發現 CI 的 log 裡印出了正式環境的 JWT_SECRET，這份 log 已經公開三天。處理順序哪一個正確？

✓ d：拿到 HS256 秘密的人可以替任何人簽 token，包括店長。先止血（換金鑰並讓舊 token 失效），再調查與修根本原因。a 刪掉的只是證據，三天內任何人都可能已經拿到；b 調查期間攻擊者可以一直偽造；c 讓攻擊者手上的秘密繼續有效一個月，而且沒有查有沒有被偽造過。正常的金鑰輪替可以新舊並存一段時間，外洩時不行。

常見錯誤

  • 只修測試打到的那個端點：同樣的模式在其他端點還在。修之前先搜尋同一個寫法出現在哪裡，修在共用的地方。
  • 修補時把功能改壞：例如把所有非 GET 的請求都擋掉、限流把正常登入也擋住、CORS 把前台也擋掉。每一題都有功能測試，跑全部的測試，不是只跑這一題。
  • 回 403 而不是 404：對沒有權限的物件回 403，等於告訴攻擊者「這筆存在，只是你不能看」。範圍外與不存在要回完全相同的回應。
  • 用排除清單保護欄位：只拿掉 passwordHash，新加的 mfaSecret 就外流了。回應與可寫入的欄位都用允許清單。
  • 撤銷只做一半：重設密碼後只撤銷 refresh token，舊的 access token 還能用到過期；只加 tokenVersion，refresh token 還能換出新的 access token。兩個都要做。
  • SSRF 只擋字串：擋 localhost 與 127.0.0.1 字串，擋不住 2130706433、解析成內網的網域、重導向和 DNS rebinding。要檢查解析後的每一個 IP，並連到驗證過的那一個。
  • 只看測試、不讀程式碼：測試只涵蓋想得到的攻擊。修完再讀一次相關的程式碼，找測試沒打到的同類問題。
  • 修完沒有留下紀錄：沒有回歸測試，下次重構時漏洞會回來；沒有決策紀錄，下一個人不知道為什麼要這樣寫，可能把它「簡化」掉。

小結

  • 安全審查從威脅模型開始，不是從第一個檔案讀到最後一個：畫出信任邊界，對每個端點問最可能出什麼錯，再依「可能性 × 影響」排序。修之前先用 curl 親眼看到攻擊成功。
  • 修根本原因而不是症狀：門市範圍的檢查放在共用的函式並寫進查詢條件、全域拒絕多餘欄位、回應用允許清單。
  • 每個修補都要有攻擊測試（證明擋住、以後也不會回來）與功能測試（證明沒改壞），再加一段決策紀錄。
  • 認證流程的細節決定成敗：JWT 固定演算法與 aud、refresh 重用要撤銷整個家族、重設密碼 token 雜湊＋短期限＋單次＋讓舊 token 全部失效、登入限流分帳號與 IP。
  • 伺服器替使用者發出的連線要檢查解析後的 IP、連到驗證過的 IP、逐跳驗證重導向；錯誤回應不帶內部細節；CORS 只允許明確的來源。
  • 事故處理先止血再調查：外洩的秘密要輪替，被擋下的攻擊也是事故。
  • 七個漏洞一題一題修：重現、定位、修在根本原因、跑全部測試、再打一次；修完仍有的弱點寫進決策紀錄。下一個專案用上線前檢查清單補上威脅模型沒想到的類別，並把清單放進 PR 範本與 CI。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 11：外送平台登記 webhook 網址時，系統解析 DNS、確認每一個 IP 都是公開位址才存進資料庫；之後訂單改狀態就直接 fetch 這個網址。哪裡會出事？

✓ 檢查的是「連線當下的 IP」，不是登記時的名字：三個月後同一個網域可能已經解析到內網的 Redis。每次送出都走完整流程，並用驗證過的 IP 連線，否則 fetch 自己再解析一次又會被 rebinding 換掉。d 錯在不讀回應，請求還是打進了內網，照樣能敲管理介面、能拿來掃描。（第 22 課）

練習 12：咖啡店要存三樣東西：外送平台給的 API token、顧客的 TOTP 秘密、重設密碼 token。哪個組合正確？

✓ 只問一件事：以後要不要原文。呼叫外送平台要帶 API token，驗證 TOTP 要用秘密的原文算 HMAC，所以加密；重設 token 只需要比對，雜湊就好，夠長的隨機值不需要慢雜湊。b 錯在雜湊之後拿不回原文，API 呼叫和 TOTP 驗證直接壞掉。（第 23 課）

練習 13：手機號碼用 AES-256-GCM 加密，AAD 是 customers:<id>:phone。攻擊者能透過 SQL injection 執行 UPDATE，但沒有金鑰；他把王小明（42 號）的手機密文複製到自己（43 號）的欄位，再打開「我的資料」。結果是？

✓ GCM 的驗證標籤同時保護密文和 AAD，AAD 綁住「表、資料列 ID、欄位」，密文搬了位置就解不開。解密失敗不能吞掉回傳空字串，要記下 ID、發警報，原資料留著當證據。a 是沒有用 AAD 時才會發生的事：程式會替攻擊者解密別人的資料。（第 23 課）

練習 14：手機號碼的金鑰從 k1 換成 k2：current 已經是 k2，背景工作也把資料庫裡 v1.k1. 開頭的密文全部重新加密完了。什麼時候可以把 k1 從 keyring 移除？

✓ 讀取依密文上的 kid 選金鑰，只要還有地方存著 k1 的密文，k1 就得留著；備份最容易被忘記。先用 LIKE 'v1.k1.%' 確認資料庫歸零，再跟維運確認備份的保留期限，才排定移除日。a 錯在只看了資料庫，哪天要還原上個月的備份，所有手機號碼都解不開。（第 23 課）

練習 15：店員查訂單的 API，storeId 取自登入的 token。哪裡會出事？

const n = parseInt(req.query.limit, 10) || 20
const orders = await prisma.order.findMany({
  where: { storeId: req.user.storeId },
  take: n,
  orderBy: { id: 'desc' },
})

✓ 這是 API4 資源耗用：使用者能控制的數量都要有上限，否則一個請求就拖垮資料庫。先用規則驗證字串是正整數（parseInt('50abc') 會變成 50），再套上上限，不合法回 400。b 錯在 0 || 20 會得到 20，回的是預設的 20 筆。（第 24 課）

練習 16：公司在 CI 加了 SAST 和 DAST，報告是零個高風險。主管說：「這樣 BOLA 那類問題就不用再另外審了。」怎麼回應？

✓ SAST 找危險寫法，DAST 送攻擊請求，兩者都不知道「這筆訂單只有王小明看得到」，所以抓不到 BOLA 和 API6。授權要在設計審查時問，並用授權矩陣測試（每個端點 × 每種角色 × 自己的／別人的資料）放進 CI。b 錯在換了 orderId 拿到 200，對掃描工具來說就是一個正常的回應。（第 24 課）

練習 17：登入已經有「同一帳號連續失敗就逐步延遲」。今晚登入成功率正常，log 卻顯示同一個 IP 在一小時內對 3,000 個不同帳號各試了一次 Coffee2026!。怎麼判斷？

✓ 噴灑每個帳號只試一兩次，每帳號的限制永遠不會觸發；偵測規則要算「一個來源碰了多少不同帳號」。觸發後先告警、要求額外驗證，不要直接封鎖，公司的共用出口 IP 會誤報。a 錯在門檻調到 2 也不會觸發，只會誤傷打錯一次密碼的人。（第 25 課）

練習 18：威脅表裡有一條「錯誤回應帶出資料表名稱」，可能性 3、影響 1。修它要改整個錯誤格式，團隊決定這一季先不修。怎麼做才算處理了這個威脅？

✓ 每個威脅都要有明確的決定：緩解、消除、轉移或接受，寫進設計文件。接受要有人負責、有理由、有重新檢視的日期，否則「接受」就只是「忘了」。c 錯在排序決定的是先後，不是可以不決定；沒寫下來，下一個人不知道這是刻意留著的。（第 25 課）

這個階段的重點整理成一頁圖解。
