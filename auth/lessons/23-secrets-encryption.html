階段 6：資深工程師的資安實務 · 第 23 課

Secrets 管理與資料加密

咖啡店的 customers 表存著三種敏感資料：會員的手機號碼、TOTP 秘密，以及跟外送平台串接用的 API token。TOTP 秘密是第 14 課做兩步驟驗證時，每位會員各有一串、用來算驗證碼的值。上個月出了一件事：工程師為了查一個集點的 bug，把正式環境的資料庫傾印一份到自己的筆電，筆電後來在咖啡廳被偷了。傾印（dump）就是把整個資料庫匯出成一個檔案。大家第一個反應是「還好資料庫有開加密」，查下去才發現，那份傾印裡的手機號碼、TOTP 秘密、外送平台 token 全是明文。

這一課就是這件事的整改。先弄清楚為什麼開了加密，傾印還是明文；再在程式裡把敏感欄位加密，讓下一份外流的傾印只剩密文。加密做好之後，所有安全性都壓在金鑰上，所以接著處理金鑰：怎麼換、放哪裡、外洩了怎麼辦。金鑰也是一種 secret，而筆電事件後不久，還有人把 .env 推上 GitHub，所以也會處理 secrets 外洩時該照什麼順序收拾。最後回到根本：正式環境的會員資料，一開始就不該出現在那台筆電上。

這課的路線：
  1. 開了加密，傾印為什麼還是明文？customers 的哪幾欄該加密、哪幾欄該雜湊？（開場問題的最小答案）
  2. 在程式裡怎麼加密手機號碼，還能發現密文被改過（AES-256-GCM）；IV 不用保密，為什麼每次都要換新的。
  3. 換金鑰那天，幾十萬筆舊密文怎麼辦；金鑰本身要放哪裡（信封加密與 KMS）。選讀：加密之後，櫃檯怎麼還能用手機號碼找會員。
  4. 金鑰和其他 secrets 會從哪裡漏出去；.env 推上 GitHub 之後要照什麼順序處理。
  5. 回到那台筆電：會員資料該不該存、存多久、怎麼刪，log 和開發環境裡的個資怎麼辦。
這課會用到：
  • 第 2 課的 HMAC、安全亂數與 base64url：HMAC 用秘密金鑰算出別人算不出的值；crypto.getRandomValues 產生猜不到的位元組；base64url 把位元組轉成字串存進資料庫。
  • 第 3 課的雜湊與加密的差別：雜湊不能還原，加密有金鑰就能還原。
  • Node 課第 2 課的環境變數與部署課第 11 課的 secret 注入：設定和 secrets 由執行環境交給程式，不寫進程式碼。

資料庫明明有加密，偷走的傾印為什麼是明文？

先看「資料庫有開加密」指的是什麼。咖啡店的資料庫跑在 RDS 上，RDS 是 AWS 代管的資料庫服務（部署課第 18 課）。建立 RDS 時勾選的「加密」，是靜態加密（encryption at rest）：資料寫到磁碟時由儲存層加密，從磁碟讀出來時自動解密，金鑰由雲端那一側管理。資料庫本身、應用程式、用 SQL 查資料的人，全都感覺不到它的存在。它保護的情境很明確：有人拿走了實體硬碟、磁碟快照或備份檔本身，拿到的是一堆解不開的位元組。

再看那份傾印是怎麼來的。工程師用的是 pg_dump，PostgreSQL 匯出整個資料庫的指令。它跟應用程式一樣，用帳號密碼連上資料庫、執行查詢、把結果寫成檔案。資料從磁碟讀出來的那一刻已經被儲存層解密，所以 pg_dump 拿到的、寫進檔案的都是明文。靜態加密從頭到尾都在正常運作，只是它防的根本不是這條路徑。

同樣的道理，任何「以資料庫的身分讀到資料」的方式都看得到明文：SQL injection（PostgreSQL 課第 25 課）讓攻擊者借應用程式的連線執行自己的查詢；被盜的資料庫帳號；能連正式資料庫的資料庫管理員（DBA）或分析人員。這些情況需要的是另一種加密：在應用程式寫入資料庫之前就把欄位加密，金鑰放在資料庫以外的地方。資料庫裡從頭到尾只有密文，誰用 SQL 讀出來、整份傾印搬走，都解不開。這叫應用層欄位加密（application-level encryption）。

加上網路傳輸那一段，「我們的資料有加密」這句話至少有三種意思，各自擋住不同的外洩路徑：

種類在哪一層擋得住擋不住
傳輸中加密（encryption in transit）TLS，部署課第 5 課網路上被竊聽、被竄改資料到了伺服器之後的一切
靜態加密（encryption at rest）磁碟、RDS 的儲存與快照硬碟、快照檔、備份檔本身被拿走任何透過資料庫連線讀到的資料：SQL injection、被盜的資料庫帳號、pg_dump 出來的檔案，拿到的都是明文
應用層欄位加密（application-level encryption）程式寫入資料庫之前先加密資料庫被傾印、備份外流、有人直接用 SQL 查資料表、DBA 或分析人員看到不該看的欄位應用程式本身被入侵（程式手上有金鑰，攻擊者讓它解密就好）

表格最後一欄有一個共同點：三種都擋不住「應用程式被入侵」，因為合法的程式必須能解密。所以這三層不是「加了一層就安全」，而是縱深防禦（defense in depth）：每一層擋一條不同的外洩路徑，一層失守時，其他層還擋著其他路徑。開場那台筆電，就是缺了應用層這一層。

三層的成本差很多。TLS 和靜態加密幾乎沒有成本，開了就好。應用層加密有代價：資料庫只看得到密文，所以不能再對那個欄位做 WHERE、ORDER BY、LIKE，每次讀寫還要多一次加解密。所以它只用在真正敏感的欄位，整改的第一步就是挑出這些欄位。

💡 實務上：被問「資料有加密嗎」，先問是哪一種
企業客戶的資安問卷、合作廠商的審查、PM 轉來的客戶問題，常常只寫一句「資料是否加密」。只回答「有，RDS 有開加密」等於只講了靜態加密，對方真正擔心的往往是「你們的工程師或外包看不看得到我的資料」。資深工程師會反過來問：誰有正式資料庫的帳號、pg_dump 出來的檔案會放到哪裡、分析人員連的是不是同一個資料庫。應用層加密不要一口氣套到每個欄位，先列出「外洩會出大事」的那幾欄（TOTP 秘密、第三方 token、手機），其他欄位交給權限控管和前兩層。

customers 表的哪幾欄該加密、哪幾欄該雜湊？

挑出敏感欄位之後，下一步是決定每一欄用什麼方法藏起原文。第 3 課分過兩種方法：雜湊是單向的，算出來就回不去；加密是雙向的，有金鑰就能還原。判斷只看一個問題：系統以後需不需要拿回原文？

資料要原文嗎做法
會員密碼不用，登入時把輸入再算一次比對慢雜湊（Argon2id，第 3 課）
重設密碼 token、復原碼不用SHA-256（夠長的隨機值不需要慢雜湊，第 14 課、第 16 課）
TOTP 秘密要，每次驗證都用原文算 HMAC加密
外送平台的 API token、OAuth refresh token要，呼叫對方 API 時要帶加密
手機號碼要寄簡訊；也要能「用手機號碼找會員」加密；要查詢時另外存一個 blind index（後面的選讀節）

逐列看理由。密碼只需要「比對」：登入時把使用者輸入的密碼用同樣的參數再算一次雜湊，跟存的值一樣就通過，系統從來不需要知道原本的密碼是什麼。重設密碼 token 也一樣，只需要比對。TOTP 秘密就不同了：每次會員輸入 6 位數驗證碼，伺服器都要拿原本的秘密跟目前時間算一次 HMAC，看結果對不對得上；存成雜湊，伺服器就再也算不出驗證碼。外送平台的 token 要放進呼叫對方 API 的 header，手機號碼要拿去寄簡訊，都需要原文。

兩個方向都會出錯。用雜湊存 TOTP 秘密，功能直接壞掉，這種錯誤測試時就會發現。反方向比較危險：用加密存密碼，平常一切正常，但金鑰一外洩，所有會員的密碼都能還原，而密碼本來就不需要還原，等於平白多了一個風險。

這就是開場問題的最小答案：customers 表裡，TOTP 秘密、外送平台 token、手機號碼改成應用層加密，金鑰放在資料庫以外；密碼已經是 Argon2id、重設 token 已經是 SHA-256，不用動。下一個問題是：在程式裡，具體要怎麼加密一個欄位？

怎麼在程式裡加密手機號碼，還能發現密文被改過？

加密欄位用的是對稱加密（symmetric encryption）：同一把金鑰負責加密和解密。這正好符合我們的情境，寫入和讀取的都是同一個應用程式。最常用的對稱加密演算法是 AES，金鑰長度 256 bits 時叫 AES-256。

AES 本身一次只能處理 16 bytes。手機號碼、token 都比這長或長度不一，所以 AES 要搭配一種模式（mode），規定長資料怎麼切塊、每一塊怎麼跟金鑰組合。模式選錯，演算法再強也沒用，這是這一節的重點。

先想攻擊者能做什麼。他沒有金鑰，但可能透過 SQL injection 執行 UPDATE，直接改資料庫裡的密文。有些模式（例如 CBC、CTR）只負責「看不懂」，不負責「發現被改過」：密文被改了幾個 bit，解密照樣成功，只是吐出一份被改過的明文。攻擊者可以反覆改密文、觀察系統的反應（錯誤訊息不同、回應時間不同），一點一點推出內容。所以應用程式需要的是加密的同時也能驗證完整性的模式，這類做法叫認證加密（authenticated encryption）。

應用程式該用的模式是 GCM。它在加密時，除了密文，還會算出一個 16 bytes 的驗證標籤（authentication tag）附在密文後面。這個標籤只有持有金鑰的人算得出來。解密時先重算標籤，跟附上的比對，密文被改過一個 bit 就對不上，整個解密直接失敗，不會吐出任何明文。GCM 屬於認證加密裡的 AEAD（authenticated encryption with associated data），名字最後那段「associated data」指的是下面的 AAD。

用 GCM 加密時，除了金鑰和明文，還要給兩樣東西：

  • IV（initialization vector，初始化向量，也叫 nonce）：每次加密都必須不同的值。它不需要保密，跟密文存在一起，解密時拿出來用。NIST 的 GCM 規範（SP 800-38D）建議 IV 用 96 bits，也就是 12 bytes。用 crypto.getRandomValues 隨機產生時，同一把金鑰總共最多加密 232 次，超過就要換金鑰（規範的章節與修訂狀態見課末「補充與查表」）。為什麼一定要每次不同，下一節示範。
  • AAD（additional authenticated data，附加認證資料）：不加密、但跟密文綁在一起的資料。解密時要給一模一樣的 AAD，否則失敗。它防的攻擊，看完範例再講。

密文比明文多出的 16 bytes 就是驗證標籤。兩種失敗都丟 OperationError，而且不會告訴你是哪裡不對，這是刻意的：告訴攻擊者「標籤不對」或「AAD 不對」，等於幫他縮小範圍。對程式來說，解密失敗只有一種意思：這份資料不可信，可能被竄改、被搬過、或用錯金鑰。程式一定要把它當錯誤處理，不能吞掉、不能回傳空字串假裝成功；回傳空字串，畫面上顯示「沒有手機號碼」，被竄改的事就被掩蓋了。

現在回頭看 AAD 防的是什麼。攻擊者能寫資料庫，卻沒有金鑰。他沒辦法自己造出合法的密文，但可以把王小明的手機密文整段複製到自己帳號的欄位，然後在網站上點「查看我的手機號碼」，讓程式替他解密。這份密文本身沒被改過，標籤完全正確，沒有 AAD 的話解密會成功。用 customers:42:phone（表、資料列 ID、欄位）當 AAD，密文就跟「42 號會員的 phone 欄位」綁在一起，搬到 43 號會員，程式解密時給的 AAD 是 customers:43:phone，解密就失敗，範例的第三行就是這個情況。

AAD 要用不會變的值。資料列 ID 可以；email 這種會被會員修改的欄位不行，否則會員改了 email，原本的密文就再也解不開了。

範例裡的 IV 每次都用 crypto.getRandomValues 產生新的。同事看到可能會問：IV 又不用保密，跟密文明擺在一起，固定成一個值不是比較好除錯嗎？

IV 不用保密，為什麼每次都要換新的？

要回答這個問題，得先看 GCM 內部怎麼加密。GCM 用 AES、金鑰和 IV 產生一串跟明文一樣長的隨機外觀位元組，稱為金鑰流（keystream），再把明文和金鑰流做 XOR 得到密文。XOR（互斥或）是逐 bit 比較：兩個 bit 相同得 0、不同得 1。它有一個關鍵性質：同一個值 XOR 兩次會互相抵銷。所以 明文 XOR 金鑰流 = 密文，解密時 密文 XOR 金鑰流 又回到明文。

金鑰流只由金鑰和 IV 決定。同一把金鑰配同一個 IV，產生的金鑰流就一模一樣。這時把兩份密文 XOR 起來，兩邊的金鑰流互相抵銷，剩下的正好是兩份明文的 XOR，攻擊者完全不需要金鑰。下面固定用全 0 的 IV 加密兩支只差最後兩碼的手機，執行後比較「密文 XOR」和「明文 XOR」兩行：

兩行完全一樣。明文相同的位置 XOR 出來是 0，所以攻擊者一眼就看得出兩支手機前 8 碼相同。如果他還知道其中一份明文（例如他自己的手機號碼），另一份就能直接算出來。更糟的是，IV 重複時攻擊者還能推出 GCM 用來算驗證標籤的內部值，之後就能偽造通過驗證的密文，上一節靠標籤擋竄改的保護也沒了。

所以規則只有一條：每次加密都用新的 12 bytes 隨機 IV，來源一定是 crypto.getRandomValues。兩種看起來可行的替代做法都不行。Math.random() 不是密碼學安全的亂數，看到足夠多的輸出就能算出它的內部狀態、預測下一個值（第 2 課），NIST 對隨機 IV 的要求是來源必須是經過核准的密碼學亂數產生器。自己維護一個計數器，在多台伺服器、程式重新啟動、從備份還原時，很容易從同一個數字重來，IV 就重複了。

固定 IV 還有一個陷阱：全 0 的 IV 加解密完全正常，測試全部會過，問題不會自己現形，只有被攻擊時才知道。

隨機 IV 也有上限：同一把金鑰最多加密 232 次，超過之後隨機產生的 IV 撞在一起的機率就高到不能接受。咖啡店一天加密幾萬次，用不到這個上限，但上限的存在說明了一件事：金鑰不是用一輩子的，總有一天要換。問題是，換金鑰那天，資料庫裡已經存了幾十萬筆用舊金鑰加密的資料。

換金鑰那天，資料庫裡幾十萬筆舊密文怎麼辦？

除了加密次數上限，換金鑰的理由還有很多：定期輪替、知道金鑰的員工離職、懷疑金鑰外洩。換的那一刻，資料庫裡已經有幾十萬筆舊金鑰加密的資料，不可能一瞬間全部重新加密，總會有一段時間新舊密文並存。程式讀到一筆密文時，必須知道該用哪一把金鑰解。

做法是讓密文自己標記「我是哪一把金鑰加密的」。這個標記叫金鑰版本（key id，簡稱 kid），跟第 8 課 JWT header 裡的 kid 是同一個想法：JWT 用它告訴驗證端該拿哪一把公鑰，這裡用它告訴程式該拿哪一把金鑰解密。這一課的密文格式把 kid 和 IV 一起放進欄位的字串裡：

v1.k2.Hk3cQ2s9xV0pYq1L.p0bX…（base64url）
│  │  │                └ 密文（含 16 bytes 驗證標籤）
│  │  └ IV，12 bytes
│  └ kid：用哪一把金鑰
└ 格式版本：以後換演算法時改成 v2

最前面的 v1 是格式本身的版本。哪天要換演算法或改格式，新資料寫成 v2，程式看到 v1 就走舊的解法，跟 kid 是同一個道理，只是管的是「怎麼解」而不是「用哪把金鑰」。

程式裡用一個 keyring 保存所有還在用的金鑰，並標明哪一把是目前的：

{ current: 'k2', keys: { k1: 舊金鑰, k2: 新金鑰 } }

k1、k2 的位元組目前跟其他設定一樣，用環境變數交給程式（Node 課第 2 課），啟動時讀進來組成 keyring。

規則只有兩條：寫入一律用 current，讀取依密文上的 kid 選金鑰。有了這兩條，輪替就能分步驟、不停機地完成：

  1. 產生 k2，加進 keyring，部署到每一台伺服器。這時 current 還是 k1，因為有些機器可能還沒拿到 k2；如果某台機器先用 k2 寫入，還沒更新的機器讀到就解不開。
  2. 每台都有 k2 之後，把 current 改成 k2。新寫入的資料用 k2，舊資料讀取時仍依 kid 用 k1 解開。
  3. 重新加密（re-encryption）：背景工作每次撈一批 kid 是 k1 的資料列，解密、用 k2 加密、寫回（NestJS 課第 20 課的佇列很適合做這件事）。一次一小批，避免長時間鎖表。
  4. 確認資料庫和備份裡都沒有 k1 的密文了，才把 k1 從 keyring 移除。還有備份需要還原時，k1 要保留到那些備份過期為止。

重新加密時一定會遇到解密失敗的資料列。不要覆蓋它，也不要跳過就算了：它可能被竄改過、被搬過，這正是上一節說的「這份資料不可信」，也是要調查的證據。記下 ID、發警報，原封不動留著。

輪替解決了「怎麼換」，但還沒回答另一個問題：k1、k2 這些金鑰現在放在哪裡？

💡 實務上：kid 要在第一天就放進格式
最常見的情況不是不會輪替，而是第一版的密文沒有標 kid，等到員工離職或懷疑外洩要換金鑰時，程式分不出每筆資料該用哪一把解，只能每把輪流試，或停機一次全部重新加密。所以就算現在只有一把金鑰，格式也先留好 v1.k1.。重新加密的背景工作要能中斷後接著跑，跑完用一句 SELECT count(*) … WHERE 欄位 LIKE 'v1.k1.%' 確認歸零，再跟維運確認備份的保留期限，才排定移除 k1 的日子。

金鑰本身要放哪裡？信封加密與 KMS

上一節的 k1、k2 是從環境變數讀進來的。這樣問題沒有消失，只是換了位置：拿到環境變數的人，就能解開所有資料。環境變數會出現在部署設定、主機的程序資訊、偶爾還有錯誤回報裡，看得到的人比想像中多。我們需要一個地方，讓金鑰能被「使用」，卻不能被「拿走」。

這就是 KMS（key management service，金鑰管理服務）做的事。KMS 把最重要的金鑰放在 HSM（hardware security module，硬體安全模組）裡。HSM 是專門保管金鑰的硬體：金鑰在裡面產生、在裡面使用，不會以明文離開。應用程式要加解密時，把資料送進去，它把結果送出來，金鑰本身從頭到尾都不在應用程式手上。AWS KMS 的文件寫明，KMS 金鑰的明文金鑰材料不會離開 HSM，要用它只能呼叫 KMS 的 API。

可是每加密一個欄位就呼叫一次 KMS 太慢，每次都是一趟網路來回，而且 KMS 有請求次數限制和費用。解法是信封加密（envelope encryption），它用兩層金鑰：

  • 資料金鑰（DEK，data encryption key）：真正用來加密資料的 AES 金鑰，由應用程式在記憶體裡使用。
  • 主金鑰（KEK，key encryption key）：只用來加密資料金鑰，永遠留在 KMS 裡。

名字的由來是：資料金鑰被主金鑰「裝進信封」（加密），加密過的資料金鑰跟資料存在一起；要用時把信封交給 KMS 拆開。流程如下：

多繞這一圈，換到三個好處。第一，主金鑰不會外流。伺服器被入侵時，攻擊者能趁機解密（程式本來就能），也可能拿走當時在記憶體裡的資料金鑰明文，但帶不走主金鑰；入侵被清除後，他就解不開其他資料金鑰保護的資料。

第二，每次使用都有紀錄。每次 Decrypt 都是一次 API 呼叫，AWS 會記在 CloudTrail 裡。CloudTrail 是 AWS 的稽核服務，記錄帳號裡每一次 API 呼叫是誰、什麼時候、做了什麼。半夜有人大量解密，看得到。還可以用 IAM 限定只有哪個服務能呼叫 Decrypt；IAM 是 AWS 的權限系統，部署課第 19 課教過。環境變數裡的金鑰做不到這兩件事：誰讀了它、拿去解了什麼，沒有任何紀錄。

第三，輪替主金鑰不用重新加密資料。AWS KMS 的自動輪替保留舊的金鑰材料，舊的加密資料金鑰照樣解得開；就算改用另一把主金鑰，也只要把每把 32 bytes 的資料金鑰解開、用新主金鑰重新加密，資料本身不用動。這跟上一節不同：上一節換的是直接加密資料的金鑰，所以每一筆資料都得重新加密。但輪替主金鑰對已經外洩的資料金鑰沒有幫助，那種情況仍要換資料金鑰、重新加密它保護的資料（AWS 文件的說法見課末）。

代價是多一個外部相依：KMS 掛了或網路斷了，就無法解密。實務上會在記憶體快取解開的資料金鑰一段時間，在「呼叫 KMS 的次數」和「明文金鑰留在記憶體多久」之間取捨。

金鑰有了地方放，還有一件事要決定：要放幾把。咖啡店需要的金鑰不只欄位加密這一把，還有 CSRF token 的 HMAC（第 6 課）、JWT 簽章。一把金鑰只做一種用途。同一把金鑰同時拿去做 AES 和 HMAC，兩種演算法的輸出可能互相洩漏資訊；一處外洩就全部外洩；而且沒辦法只輪替其中一種用途。每種用途各自一把。各自保管很多把很麻煩，所以下一節（選讀）介紹怎麼從一把主金鑰衍生出各用途的子金鑰，以及加密後的手機號碼怎麼還能拿來查會員。

一把主金鑰怎麼分給多種用途？加密後還能用手機找會員嗎？（選讀）

這節是選讀：要做「用手機號碼找會員」這類加密欄位的查詢時再回來看。跳過不影響後面的課；練習 2、練習 8 對應這一節。這一節講兩件事：HKDF 子金鑰與 blind index。

HKDF：一把主金鑰，衍生不同用途的子金鑰

上一節的結論是每種用途各自一把金鑰。HKDF（HMAC-based key derivation function，RFC 5869）讓你只保管一把主金鑰，再依「用途字串」衍生出各用途的子金鑰。用途字串是 HKDF 的 info 參數，例如 'field-encryption'、'csrf'。它有三個性質：用途不同，子金鑰就完全不同；用途相同，每次都得到同一把，所以不用另外存子金鑰；知道其中一把子金鑰，推不回主金鑰，也推不出其他子金鑰。執行後看第二行和第四行：同樣是 blind-index:phone，衍生出的值一樣，其他用途則各不相同：

程式裡的 salt 給了空的位元組，這要解釋一下。HKDF 的 salt 是一個隨機值，用途是在輸入的金鑰材料不夠均勻時（例如某些位元容易猜到），先把它打散成均勻的狀態，再衍生子金鑰。我們的主金鑰是 crypto.getRandomValues 產生的 32 個隨機位元組，每個位元都猜不到，這種狀態叫高熵（high entropy）。輸入本來就均勻，就不需要 salt 再打散，所以 salt 可以給空的（RFC 5869 也允許不給 salt）。要從密碼這種低熵、人想出來的東西產生金鑰，用的是第 3 課的 PBKDF2 或 Argon2，不是 HKDF：HKDF 很快，拿來處理密碼等於讓攻擊者高速猜測。

加密之後還要能查：blind index

手機號碼加密之後，櫃檯「輸入手機號碼找會員」的功能就壞了。AES-GCM 每次用不同的 IV，同一支手機加密兩次結果不同，資料庫裡沒有任何值能拿來 WHERE phone = ...。

blind index（盲索引）的做法是另外存一欄 HMAC(索引金鑰, 正規化(手機))。HMAC 跟 AES-GCM 不同，同樣的輸入和金鑰一定算出同樣的結果，所以能拿來比對。查詢時對輸入算同樣的 HMAC，用它查那一欄；原本的加密欄位繼續負責顯示和寄簡訊：

customers
  id | phone_enc（AES-GCM，顯示、寄簡訊用） | phone_idx（HMAC，查詢用，建索引）
  42 | v1.k2.Hk3c….p0bX…                    | 6Qx0…

SELECT id FROM customers WHERE phone_idx = $1   -- $1 = HMAC(索引金鑰, '0912345678')

寫入和查詢之前都要先正規化（normalize），也就是把同一個值的不同寫法統一成一種格式。0912-345-678、0912 345 678、+886912345678 是同一支手機，但 HMAC 的輸入差一個字元結果就完全不同，不先統一，會員註冊時打了 -、櫃檯查詢時沒打，就找不到人。

為什麼一定要用 HMAC，不能直接存 SHA-256？因為手機號碼的可能值太少：09 開頭再 8 碼，大約一億種。沒有金鑰的雜湊，誰都能算，攻擊者拿到資料庫後把一億種全部算一遍、比對，就能還原每一支手機（第 2 課）。下面用一萬種可能示範，假設攻擊者已經知道前 6 碼，執行後看試了幾次、花了多少毫秒：

一萬種在瀏覽器裡一眨眼就算完，一億種在一般電腦上也只是時間問題。HMAC 沒有金鑰就算不出來，所以能擋住這種列舉。同樣的道理也說明了索引金鑰的地位：它要跟加密金鑰分開（用上面的 HKDF 衍生 blind-index:phone），而且一樣要保密。拿到索引金鑰的人，照樣能把一億種手機的 HMAC 全部算一遍、對回原文。

blind index 本身也洩漏一些資訊，這是用它換「能查詢」的代價：相同手機的索引一定相同，看資料庫的人雖然不知道號碼，但看得出「這兩個帳號用同一支手機」、「這個索引出現了 300 次」。所以 blind index 只用在真的需要精確查詢的欄位，而且只能做「等於」的查詢，不能做模糊搜尋或範圍查詢。

金鑰和其他 secrets 會從哪裡漏出去？

加密做完之後，整件事的安全性都壓在金鑰上：手機密文就算外流，只要金鑰沒外流就安全；金鑰一外流，加密就形同虛設。而金鑰只是咖啡店眾多「秘密」裡的一種。筆電事件後不久又出了一件事：有人把 .env 推到 GitHub，裡面有資料庫密碼和 JWT 簽章金鑰。這一節把金鑰和這些值放在一起處理。

Secret 是任何拿到就能冒充你的系統的值：資料庫密碼、加密主金鑰、JWT 簽章金鑰、第三方 API key、OAuth client secret、webhook 簽章 secret。拿到資料庫密碼就能以應用程式的身分查資料；拿到 JWT 簽章金鑰就能簽出任何會員的 token。每一個 secret 都要走過同一套生命週期，每個階段都有對應的做法：

階段怎麼做
產生crypto.getRandomValues，至少 32 bytes；不用人想的字、不用範例檔裡的值
存放環境變數，或 secrets manager（集中保管、控管誰能讀、記錄每次讀取、支援輪替的服務，例如 AWS Secrets Manager，部署課第 11 課）；主金鑰放 KMS
注入部署時注入成環境變數或檔案；不放進映像（image）、不寫死在程式碼裡
使用只有需要的服務拿得到；不印進 log（Node 課第 19 課的遮罩）、不回傳給前端
輪替定期換，也在人員異動、懷疑外洩時換；程式要能同時接受新舊兩把（keyring）
撤銷確認新的都在用之後，讓舊的失效

輪替那一列，就是前面 keyring 的做法套用到所有 secrets：新舊並存一段時間，確認新的在用了才撤銷舊的。實際外洩時，secrets 最常從三個地方漏出去。

第一是進了 git。.env 要寫在 .gitignore，repo 裡只放沒有真實值的 .env.example，讓新同事知道要設哪些變數。一旦 push 出去，就當成已經外洩：別人可能已經 clone 或 fork，公開 repo 會被自動掃描，刪 commit、force push 都收不回已經被拿走的副本。

第二是進了 log。常見的寫法是印出整個 config 物件、印出請求的 headers（裡面有 Authorization），或錯誤訊息裡帶著資料庫連線字串。log 系統能看的人通常比正式環境多，保存得也更久。

第三是進了前端，這是前端工程師最容易踩的。Vite 會把 VITE_ 開頭的環境變數打包進前端程式碼，任何人打開開發者工具都看得到。前端只能放本來就公開的值，例如 OAuth 的 client_id；secret 只能留在後端。

回到那個被推上 GitHub 的 .env。知道外洩之後，處理順序很重要：

外洩時的處理順序
1. 產生新的 secret，部署到所有用到它的地方。
2. 確認新的已經在用（服務正常、log 裡看得到用新的 kid）。
3. 撤銷舊的。
4. 查舊的 secret 在外洩期間有沒有被用過（雲端的稽核紀錄、第三方後台的 API 呼叫紀錄），被用過就照事故處理（第 25 課）。
順序反過來（先撤銷再換新）會讓自己的服務先掛掉。如果確定攻擊者正在使用，才考慮接受停機、先撤銷。

以 JWT 簽章金鑰為例：先撤銷舊金鑰，所有已發出的 token 立刻驗證失敗，全部會員被登出，新金鑰卻還沒部署好，連重新登入都不行。先部署新金鑰並讓驗證端同時接受新舊兩把，再撤銷舊的，會員最多只是重新登入一次。第 4 步也不能省：查舊金鑰在外洩期間有沒有被拿去簽出可疑的 token。

💡 實務上：外洩靠流程擋，不是靠大家小心
新專案建立時就把 .env 放進 .gitignore、附上 .env.example，再開 GitHub secret scanning 的推送保護（push protection，含 secret 的 commit 推送時就被擋下）或在 CI 跑 gitleaks 這類掃描工具。團隊另外要有一份「secrets 清單」：每一個 secret 在哪裡、誰能讀、誰負責換，外洩或有人離職時才不會花半天找。資深工程師 review 時會特別看兩種改動：新增 VITE_ 開頭的變數，和把整個 config 或 request 物件丟進 log 的那一行。

回到那台筆電：會員資料一開始為什麼會在那裡？

到這裡，手機號碼加密了、金鑰放進 KMS 了、secrets 也有了流程。但開場那件事還有一個問題沒處理：正式環境的會員資料，為什麼會出現在一台工程師的筆電上？就算傾印裡的手機都是密文，姓名、Email、消費紀錄還是明文。比「怎麼保護」更前面的問題是：這筆資料該不該存、要存多久、會被複製到哪裡。

個人資料（簡稱個資，英文常說 PII，personally identifiable information）是能直接或間接認出某一個人的資料：姓名、手機、Email、生日、地址、身分證字號，也包括單獨看認不出、跟別的資料合起來就認得出的，例如「會員編號＋每天早上 8 點在同一間門市點拿鐵」。個資跟 secrets 一樣有生命週期，每一個階段都可能外洩：

階段要問的問題咖啡店的做法
蒐集這個欄位拿來做什麼？少了它哪個功能會壞？集點只需要手機；生日只在要送生日優惠時才問，而且只問月份
使用誰需要看到原文？櫃檯畫面只顯示 ****678；客服要看完整號碼時另外授權並留紀錄
複製這份資料還會出現在哪裡？log、備份、分析用的資料庫、開發環境、寄給廠商的 CSV，每一份都要算進來
保存要留多久？依據是什麼？寫成保留政策（retention policy），每一類資料一個期限，由排程工作執行

資料最小化：不存就不會外洩

資料最小化（data minimization）是只蒐集、只保存完成目的需要的資料。這是成本最低的防護：沒存的欄位不用加密、不會出現在傾印裡、使用者要求刪除時也不用處理。「先多收一點，以後分析可能用得到」是最常見的反例，那些欄位多半沒人用，但每一份備份都帶著它們。

同一個原則也用在 log：記 customerId: 7，不記姓名和手機。真的要查是誰，拿 id 回資料庫查，那裡有權限控管和稽核紀錄；log 系統通常有更多人能看，保存得也更久。

保留期限與刪除

收了的資料總有不需要的一天，例如會員申請刪除帳號。說到刪除，先分清兩種：

  • 軟刪除（soft delete）：加一欄 deleted_at，查詢時過濾掉，資料其實還在。好處是刪錯了救得回來、外鍵不會斷。對個資來說它不算刪除：資料庫外洩時這些列一樣外洩。
  • 硬刪除（hard delete）：真的 DELETE 或把個資欄位改成 NULL。

兩種各有用處，所以會員申請刪除帳號時，常見的流程是先軟、後硬：

  1. 先軟刪除（停用帳號、不能登入），給一段反悔期，例如 14 天。
  2. 反悔期過後，排程工作把個資欄位清掉：UPDATE customers SET name = NULL, phone_enc = NULL, phone_idx = NULL, email = NULL WHERE id = 7。
  3. 法規或會計需要留的紀錄（訂單金額、日期）留著，只是不再連到認得出的人。要注意：剩下的資料如果跟別的資料一對照還是認得出是誰，它仍然是個資。
  4. 通知其他拿過這份資料的系統一起刪：寄簡訊的廠商、分析工具、客服系統。

主資料庫清掉了，備份是最難的一份。備份通常是不可變的（部署課第 24 課），沒辦法進去刪一列。有兩種做法：

  • 靠保留期限：備份只留 35 天，刪除請求最晚 35 天後隨著舊備份過期而消失。代價是：從舊備份還原時，要把還原點之後的刪除請求重新套用一次。所以刪除請求本身要記下來（記 customerId 和時間，不記個資）。
  • 加密抹除（crypto-shredding）：每位會員的個資用自己的資料金鑰加密（前面的信封加密），刪除時銷毀那把資料金鑰。備份裡的密文還在，但再也解不開。代價是金鑰管理變複雜，每次讀取都要先拿到那位會員的金鑰。

log 也有保留期限（部署課第 21 課），但它很難逐筆刪除，所以 log 的原則是一開始就不放原文，這是下一小節。

log 裡的個資要遮罩

Node 課第 19 課的遮蔽（redaction）把密碼、token 整個換成 [REDACTED]。個資通常不整個拿掉，而是部分遮罩（masking）：留下一小段，讓客服查「尾碼 678 的會員說沒集到點」時，還認得出是哪一筆，但看 log 的人拿不到完整號碼。

欄位原文遮罩後
手機0912-345-678****678
Emailxiaoming@example.comx***@example.com
卡號4111 1111 1111 1111****1111
密碼、token、Authorization任何值[REDACTED]

星號用固定個數，不照原文長度補，避免洩漏原本有幾碼。完整卡號本來就不該經過你的伺服器（交給金流商處理），會出現在 log 裡多半是有人把整個請求印出來。

遮罩要在哪裡做？結構化 logger（例如 pino）的 redact 用路徑指定欄位、區分大小寫、不會自動找任何深度的同名欄位（Node 課第 19 課）。log 裡的物件形狀一多，路徑很容易漏。另一種做法是寫一個函式，在交給 logger 之前走過整個物件。先看最直覺、只處理第一層的寫法漏了什麼，執行後看輸出裡哪些地方還是原文：

開發與測試環境不用正式資料

最後是開場那台筆電本身。開發、測試環境的權限、log、備份都比正式環境鬆，資料還會被複製到更多台筆電，或貼進錯誤追蹤、AI 工具這類第三方服務。正式環境的個資不應該出現在那裡。工程師要重現 bug 時，有兩種替代做法：

  • 種子資料或合成資料（seed data、synthetic data）：用腳本產生假資料。Email 用 example.com 這類保留給範例的網域（RFC 2606），不會寄到真人信箱。需要「很多會員」來重現效能問題，就產生同樣數量、同樣分布的假資料。
  • 遮罩過的傾印（masked dump）：真的需要正式資料的分布時，在正式環境那一側先把個資欄位換成格式正確的假值（例如 'user' || id || '@example.com'，保持唯一），再匯出。先匯出到筆電再遮罩是錯的順序：明文已經離開正式環境，存在傳輸過程、暫存檔和那台筆電上了。

開場那位工程師要查的集點 bug，用合成資料或正式環境那一側先遮罩的傾印就能重現。這兩種做法都在，筆電被偷的事件就只是掉了一台筆電。這些要求背後也有法律依據：台灣的《個人資料保護法》要求蒐集不得逾越目的之必要範圍、目的消失時要刪除，條文重點見課末「補充與查表」。

💡 實務上：新增欄位時，先問「為什麼要存」
個資問題多半在需求階段就決定了：PM 想在會員資料加「生日、地址、性別」，工程師最好在開需求單時就問「哪個功能會用到、要留多久」，而不是上線後再補刪除流程。review migration 時看到新的個資欄位，順便確認三件事：log 會不會印到、會員刪除帳號時有沒有清到、開發環境的種子資料有沒有對應的假值。客服或工程師說「要正式資料才能重現 bug」時，先試著用同樣條件產生假資料，真的不行才走遮罩過的傾印，並讓主管或資安知道。

練習

練習 1：寫欄位加密與解密。

  • encryptField(plaintext, keyring, aad)：用 keyring.current 那把金鑰做 AES-GCM，IV 每次 12 bytes 隨機，aad 用 UTF-8 轉成位元組當 additionalData。回傳 v1.<kid>.<iv>.<密文>，IV 和密文用 base64url。
  • decryptField(token, keyring, aad)：成功回傳 { ok: true, value }。格式不對（不是 4 段、不是 v1、base64url 解不開、IV 不是 12 bytes）回傳 malformed；keyring 裡沒有這個 kid 回傳 unknown_key；AES-GCM 解密失敗回傳 decrypt_failed。
  • kid 是從資料庫讀出來的字串，可能是任何值，包括 toString 這種物件原型上就有的名字。

練習 2（選讀）：寫子金鑰衍生與手機號碼的 blind index（對應選讀節「HKDF 子金鑰與 blind index」，跳過不影響其他練習）。

  • deriveSubkey(master, purpose)：HKDF-SHA256，salt 是空的位元組，info 是 purpose 的 UTF-8，輸出 32 bytes。
  • blindIndex(phone, indexKey)：先正規化（去掉所有空白和 -，再把開頭的 +886 換成 0），再用 indexKey 算 HMAC-SHA256，回傳 base64url。

練習 3：寫輪替用的背景工作 rotateBatch(rows, keyring, limit)。encryptField、decryptField 是練習 1 的答案，已經寫好。

  • 依陣列順序，找出 kid 不是 keyring.current 的資料列，最多處理前 limit 筆。
  • 每一筆用它原本的 AAD（customers:<id>:phone）解密，再用 current 重新加密，寫回 row.phoneEnc。
  • 解密失敗的列不要動，把 id 放進 failed。回傳 { rotated: 成功筆數, failed: 失敗的 id }。

練習 4：寫 log 的個資遮罩 maskPii(value)，在交給 logger 之前呼叫。

  • 走過整個值，不管在第幾層、在不在陣列裡；陣列遮完還是陣列。回傳新的值，不能改到傳入的物件（呼叫端等一下還要用原文寄簡訊）。
  • 欄位名稱不分大小寫：phone、mobile → **** 加上數字的最後 3 碼；cardNumber → **** 加上數字的最後 4 碼；email → 第一個字元、***、再接從最後一個 @ 開始的網域（沒有 @ 或 @ 在第一個字元就換成 [REDACTED]）；password、token、authorization → [REDACTED]。
  • 只比對完全相同的欄位名稱：emailVerified、phoneCount 不是個資，不能遮。
  • 上面這些欄位的值是 null 時保留 null（「沒有填」對除錯有用，也不是個資）；值不是字串（例如數字）時一律 [REDACTED]。其他欄位原樣保留，物件、陣列要繼續往裡面找。

練習 5：咖啡店的 RDS 開了靜態加密。攻擊者透過 SQL injection 執行 SELECT * FROM customers，拿到的手機號碼是什麼？

✓ b。靜態加密由儲存層透明處理，只要能透過資料庫連線讀到資料，看到的就是明文；它防的是硬碟、快照、備份檔被直接拿走。a、c 把靜態加密想成資料庫裡存的是密文。d 錯在靜態加密不做任何存取控制。要讓 SQL injection 拿到的也是密文，要在應用層加密欄位，金鑰放在資料庫以外。

練習 6：為了「方便除錯」，同事把 AES-GCM 的 IV 固定成 12 個 0。會發生什麼事？

✓ c。IV 公開沒關係，但每次都要不同。IV 重複時金鑰流也重複，兩份密文 XOR 之後金鑰流抵銷，剩下明文的 XOR；攻擊者還能推出驗證標籤用的內部值，進而偽造密文。a 混淆了「公開」與「可以重複」。b 錯在全 0 的 IV 照樣能加解密，所以這種錯誤不會在測試中自己現形。d 錯在速度不受影響。

練習 7：工程師把含有 JWT 簽章金鑰的 .env push 到公開的 GitHub repo，五分鐘後發現，馬上 force push 把那個 commit 蓋掉。接下來應該？

✓ a。push 出去之後，別人可能已經 clone、fork，公開 repo 也會被自動掃描，force push 和改成私人都收不回已經被拿走的副本（b、c）。d 的順序會讓所有使用者立刻被登出、服務先掛掉；除非確定攻擊者正在使用，否則先換新、確認、再撤銷。最後還要查外洩期間有沒有可疑的 token 被簽出來。

練習 8（選讀）：手機號碼用 AES-GCM 加密，另外存一欄 HMAC(索引金鑰, 正規化後的手機) 當 blind index。資料庫整份外洩、索引金鑰沒有外洩時，攻擊者能知道什麼？

✓ d。相同的輸入一定算出相同的 HMAC，所以重複與出現頻率會洩漏，這是換取「能查詢」的代價（a 錯）。b 要在攻擊者也拿到索引金鑰時才成立：沒有金鑰就算不出 HMAC，列舉不了；這也是索引金鑰要保密、跟加密金鑰分開的原因。c 錯在 HMAC 的輸出看不出輸入的任何部分。

練習 9：會員申請刪除帳號。工程師在 customers 加了 deleted_at，所有查詢都過濾掉有值的列，然後回覆會員「已刪除」。哪個說法對？

✓ b。軟刪除只是查詢時看不到，資料還在資料庫和每一份備份裡，資料庫外洩時一樣外洩（a 錯）。軟刪除可以當反悔期，期滿由排程工作清掉個資欄位，也要通知拿過資料的廠商一起刪。c 的成本與風險都太高，改動備份也破壞了備份不可變的意義；一般做法是讓備份照保留期限過期，還原時重新套用刪除請求，或用加密抹除。d 錯在金鑰還在，加密的資料隨時能解開；只有金鑰被銷毀（加密抹除），密文才等於刪除。

練習 10：測試環境要重現「會員很多時查詢變慢」。同事提議把正式資料庫整份 pg_dump 下來還原到 staging，理由是「staging 在公司內網，只有工程師看得到」。比較好的做法是？

✓ c。效能問題需要的是資料量和分布，不是真的手機號碼：遮罩是把個資欄位換成格式正確、不重複的假值，合成資料是用腳本產生同樣數量與分布的假會員。a 錯在 staging 的權限、log、備份都比正式環境鬆，看得到的人和工具更多，開場那台筆電就是這樣出事的。b 的順序錯了：還原之前，明文已經離開正式環境，存在傳輸過程、傾印檔和 staging 的磁碟與備份裡。d 會讓正式環境的使用者承擔測試造成的負載與風險。

常見錯誤

  • 以為開了靜態加密，資料庫的內容就是密文：靜態加密只防硬碟、快照、備份檔被拿走；透過資料庫連線讀到的（SQL injection、pg_dump）都是明文。敏感欄位要應用層加密，金鑰放在資料庫以外。
  • 用雜湊存需要還原的資料，或用加密存密碼：先問「以後要不要原文」。TOTP 秘密、第三方 token 加密；密碼用慢雜湊。
  • IV 固定、用 Math.random、用多台機器各自維護的計數器：IV 重複會洩漏明文並能偽造。每次用 crypto.getRandomValues(new Uint8Array(12))。
  • 解密失敗被吞掉：回傳空字串或預設值，等於接受了被竄改的資料。回傳明確的錯誤、記錄、發警報。
  • 不用 AAD：密文可以在資料列之間搬移，讓程式替攻擊者解密別人的資料。用「表:ID:欄位」這類不會變的值當 AAD。
  • 用 keys[kid] 判斷金鑰存不存在：kid 來自資料庫，'toString' 這種名字會拿到原型上的方法。用 Object.hasOwn 或 Map。
  • 一把金鑰多種用途：加密、HMAC、JWT 簽章共用同一把，一處外洩全部外洩，也沒辦法分開輪替。用 HKDF 依用途衍生。
  • 金鑰和密文放在一起：金鑰存在同一個資料庫、或寫在進了 repo 的 .env，加密就沒有意義。金鑰放 KMS、secrets manager 或部署時注入的環境變數。
  • 移除舊金鑰太早：還有資料或備份是舊金鑰加密的，就解不開了。全部重新加密、舊備份也過期後再移除。
  • secret 外洩後只刪 commit：一律輪替，順序是先部署新的、確認、再撤銷舊的。
  • 先多收一點個資，以後可能用得到：沒用到的欄位一樣要加密、備份、回應刪除請求，外洩時一起外洩。只收完成目的需要的。
  • 把軟刪除當成刪除：資料還在資料庫和備份裡。反悔期過後清掉個資欄位，備份靠保留期限或加密抹除。
  • log 遮罩只處理第一層、只認得小寫：customer.phone、陣列裡的 Mobile、header 的 Authorization 都會漏。走過整個物件、欄位名稱不分大小寫；個資也不要拼進訊息字串。
  • 把正式資料庫複製到開發或測試環境：那裡的權限和保存都更鬆。用合成資料，或在正式環境那一側先遮罩再匯出。

補充與查表

GCM 的 IV 長度與加密次數上限：規範出處

IV 用 96 bits（12 bytes）的建議出自 NIST SP 800-38D §5.2.1.1；用隨機 IV 時，同一把金鑰總共最多加密 232 次，出自 §8.3。NIST 已在 2024-03-06 宣布要修訂這份規範，目前仍以這個版本為準。

程式裡的 Uint8Array<ArrayBuffer>

TypeScript 5.7 起 Uint8Array 多了一個型別參數，標明底下是哪種記憶體。只寫 Uint8Array 代表也可能是共享記憶體 SharedArrayBuffer，Web Crypto 的參數不收，所以信封加密的範例寫明是一般的 ArrayBuffer。

AWS KMS 輪替主金鑰的範圍

AWS KMS 的自動輪替只換「目前用來加密的金鑰材料」，舊的材料保留，舊的加密資料金鑰照樣解得開。AWS 文件也提醒：輪替主金鑰不會換掉資料金鑰，對已經外洩的資料金鑰沒有幫助，那種情況要換資料金鑰、重新加密它保護的資料。

台灣的法規

台灣的《個人資料保護法》（個資法）規範個資的蒐集、處理與利用。全國法規資料庫的條文裡，跟個資那一節直接相關的幾點：第 2 條的「個人資料」包括姓名、出生年月日、聯絡方式、財務情況等，以及其他得以直接或間接方式識別該個人的資料；第 3 條列出當事人的權利，包括查詢或請求閱覽、請求製給複製本、請求補充或更正、請求停止蒐集處理或利用、請求刪除，而且不得預先拋棄或以特約限制；第 5 條要求蒐集、處理或利用不得逾越特定目的之必要範圍；第 11 條第 3 項規定特定目的消失或期限屆滿時，應主動或依當事人請求刪除、停止處理或利用（有但書）。

這部法律在民國 114 年（2025 年）11 月修正，撰寫時（2026 年 11 月）部分條文的施行日期還由行政院另定。這裡只是讓你知道工程上的刪除流程、最小化背後有法律要求，不是法律意見；實際的義務（例如保存年限、外洩時要通知誰）以全國法規資料庫的最新條文為準，並跟法務確認。

小結

  • 筆電上的傾印是明文，因為靜態加密只防儲存媒體被拿走，透過資料庫連線讀到的都已解密。TLS 防傳輸中、靜態加密防儲存媒體、應用層欄位加密防資料庫內容外流；三者都擋不住應用程式本身被入侵。
  • 要原文就加密（TOTP 秘密、第三方 token、手機號碼），不需要原文就雜湊（密碼、重設 token）。
  • AES-256-GCM 是認證加密：密文被改過就解密失敗。每次 12 bytes 隨機 IV、同一把金鑰最多 232 次；IV 重複會洩漏明文的 XOR 並能偽造。AAD 把密文綁在資料列上；解密失敗一定當錯誤處理。
  • 密文帶 kid（v1.<kid>.<iv>.<密文>）：寫入用 current、讀取依 kid；背景工作分批重新加密，全部完成、舊備份也過期才移除舊金鑰。
  • 信封加密：主金鑰留在 KMS 的 HSM 裡，只加密資料金鑰；每次解密都有稽核紀錄。一把金鑰只做一種用途（選讀：HKDF 從一把主金鑰衍生各用途的子金鑰）。
  • （選讀）blind index = HMAC(索引金鑰, 正規化後的值)，讓加密欄位能做「等於」查詢，代價是洩漏重複與頻率。
  • Secrets 不進 git、不進 log、不進前端；外洩時先部署新的、確認、再撤銷舊的，並查舊的有沒有被用過。
  • 個資的生命週期：只收需要的（資料最小化）、訂好保留期限、刪除要涵蓋主資料庫、備份、log 與第三方副本；軟刪除不算刪除。
  • log 裡的個資部分遮罩（****678、x***@example.com），遮罩要走過整個物件、不分大小寫、不改到原物件；開發環境用合成資料或在正式環境那一側先遮罩的傾印，正式資料不該出現在筆電上。
