階段 4：更多登入方式：第三方、多因素與機器 · 第 13 課

OpenID Connect：用 Google、LINE 登入

咖啡店的會員註冊頁，有一半的人填到密碼那一欄就走了。行銷部想加上「用 LINE 登入」：顧客按一下、在 LINE 的頁面同意，回到咖啡店時就已經登入。這一課要寫的是這個功能的後端：一支 GET /login/line 把顧客送去 LINE，一支 GET /callback/line 接住 LINE 送回來的結果，最後決定「這個人是誰、要不要發給他咖啡店的 session」。

callback 的最後幾行寫錯，後果很直接。沒把 LINE 給的 token 驗好，攻擊者自己造一張 token，就能登入任何人的帳號。用 email 把 LINE 帳號接到既有會員，攻擊者在別的服務註冊會員陳美華的 email，一登入就拿走她在咖啡店累積的 800 點。這課從頭到尾跟著這支 callback 走：它拿到什麼、怎麼確認是真的、怎麼對應到會員、最後交出什麼。

這課的路線：
  1. OAuth 只說「可以做什麼」，callback 怎麼知道「你是誰」：OpenID Connect（OIDC）在 OAuth 上多了什麼，整個登入流程的最小答案。
  2. ID token 裡寫了什麼、憑什麼相信它：每個欄位的意思，公鑰和演算法從哪裡來，JWKS 為什麼要快取。
  3. 驗證 ID token 的六步，以及有了 state 為什麼還要 nonce：每一步擋住哪一張偽造的 token。
  4. 驗完之後這是哪位會員：用 (iss, sub) 認人，陳美華第一次按 LINE 登入時怎麼不被接管。
  5. callback 最後交出什麼、什麼東西絕不能外流：換成咖啡店自己的 session，channel secret 只放後端；最後判斷要不要自己做這一切。
這課會用到：
  • 第 12 課的授權碼流程：把使用者導到授權伺服器登入同意，帶著 code 和 state 導回，後端再用 code 加 PKCE 的 verifier 換 token。這課的登入就是走這個流程。
  • 第 8 課的 JWT 簽章：HS256 用同一把共用金鑰簽和驗；ES256 用私鑰簽、公鑰驗，公鑰放在 JWKS 裡，用 header 的 kid 挑出是哪一把。
  • 第 9 課的驗證步驟：演算法由伺服器設定決定，依序檢查演算法、金鑰、簽章、exp、iss、aud。
  • 第 4 課的 session：伺服器端存「這個瀏覽器是誰」，登入成功時換一個新的 session ID、刪掉舊的。

OAuth 只說「可以做什麼」，callback 怎麼知道「你是誰」？

先看只用第 12 課的 OAuth 會卡在哪裡。授權碼流程走完，咖啡店後端拿到一張 access token。access token 回答的是「持有者可以做什麼」，它是給 LINE 的 API 看的：OAuth 沒有規定它的格式，可能只是一串咖啡店看不懂的不透明字串，裡面也不一定寫著「這是發給咖啡店的」。

有人會想：那就拿 access token 去呼叫 LINE 的 API 查「這是誰」，查到的使用者 ID 就是登入者。問題是咖啡店沒辦法確定手上這張 access token 是 LINE 為了這次登入發給咖啡店的。如果它其實是發給另一個 App、被那個 App 的經營者拿來冒用，LINE 的 API 照樣會回答「這是陳美華」，因為 access token 本來就只證明「持有者可以讀她的資料」，不證明「她剛剛在你這裡登入」。用授權的憑證做登入，就缺了「給誰的、為了哪一次登入」這兩件事。

OpenID Connect（OIDC）就是補上這兩件事的登入協定。它建立在 OAuth 2.0 上，流程照舊，只是多發一張專門用來證明身分的 token，上面寫明「誰、什麼時候、為了哪個網站登入」，並由發出它的一方簽章。

OIDC 的規格替兩個角色取了新名字，先對上：

  • 依賴方（relying party，RP）：用 OIDC 讓使用者登入的網站，這裡是咖啡店。它「依賴」別人告訴它使用者是誰。它就是第 12 課的 client，參數也還叫 client_id，所以這課沿用 client 這個叫法。
  • OpenID 提供者（OpenID Provider，OP）：負責確認使用者身分、簽發身分證明的一方，例如 Google、LINE。在 OAuth 裡它是授權伺服器。它簽的 token 會在 iss 欄位寫上自己，所以講到 iss 時也叫它發行者（第 8 課）。

OIDC 在 OAuth 上加的東西不多。下面這張表列出全部，後面各節會一樣一樣用到：

callback 拿到的 ID token 裡寫了什麼？

ID token 是一張 JWT（第 8 課），payload 解開就是一個 JSON 物件。下面是陳美華用 LINE 網頁登入時拿到的 ID token payload（數值是範例）。執行後看三行輸出：有效期間多長、哪兩個欄位組成穩定的識別、哪些欄位只是資料：

iss、exp、iat 是第 9 課看過的欄位：誰簽的、什麼時候到期、什麼時候簽的。ID token 新出現、而且這課會一直用到的是下面四個。

sub（subject）是使用者在這個發行者內的識別碼。sub 在這個發行者內唯一，而且不會重新分配給別人；對同一個 client 來說，同一個使用者的 sub 不會變，所以適合用來認人。（LINE 這類 pairwise 發行者，對不同 provider 底下的 client 會發不同的 sub，細節見課末。）但它只在發行者內部唯一：同一個陳美華，在 LINE 和 Google 的 sub 完全不同；兩個發行者也可能剛好發出同一個 sub 字串給兩個不同的人。這就是為什麼後面認人時要用 iss 和 sub 兩個一起。

aud（audience）寫的是這張 ID token 給哪個 client，值就是 client_id，在 LINE 叫 channel ID。它可以是字串，也可以是陣列。上一節說 access token 缺「給誰的」，aud 補的就是這一塊：別的網站拿到的 ID token，aud 是那個網站的 client_id，咖啡店一比對就知道不是給自己的。

nonce是只用一次的隨機值（number used once）。咖啡店在把顧客送去 LINE 時帶上它，LINE 原樣寫進 ID token、一起簽章。上一節說 access token 缺「為了哪一次登入」，nonce 補的就是這一塊。它怎麼用、跟第 12 課的 state 有什麼不同，驗證那一節後面會講。

範例裡沒列出、但 OP 給 email 時通常會一起給的 email_verified，是布林值，表示 OP 是否確認過這個 email 屬於這位使用者。payload 裡的 auth_time、amr 是登入方式的細節，這課用不到，所以不談。payload 裡的 name、email 是使用者的資料，不是識別：名字會改、email 會換，這件事到「這是哪位會員」那一節會變得很重要。

到這裡有一個根本的問題：這些欄位只是一段 JSON，任何人都寫得出 {"iss":"https://access.line.me","sub":"陳美華的 sub"}。咖啡店要相信它，得確認它真的是 LINE 簽的，而這需要知道 LINE 用什麼演算法、什麼金鑰簽。

憑什麼相信是 LINE 簽的？Discovery、演算法與 JWKS

驗簽章需要兩樣東西：演算法和金鑰。咖啡店要去哪裡知道 LINE 的這兩樣東西，連同 token 端點的網址？OIDC 的答案是 Discovery：每個 OP 在 發行者網址 + /.well-known/openid-configuration 放一份 JSON，列出自己的端點網址、公鑰清單（JWKS）的網址 jwks_uri、支援的簽章演算法。client 啟動時讀這份文件，就不用把網址寫死。下面是 2026-10-31 實際查詢 Google 和 LINE 的結果（節錄）：

// https://accounts.google.com/.well-known/openid-configuration
"issuer": "https://accounts.google.com",
"jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
"id_token_signing_alg_values_supported": ["RS256"],

// https://access.line.me/.well-known/openid-configuration
"issuer": "https://access.line.me",
"jwks_uri": "https://api.line.me/oauth2/v2.1/certs",
"id_token_signing_alg_values_supported": ["ES256"],
"subject_types_supported": ["pairwise"],
"code_challenge_methods_supported": ["S256"]

Google 的情況單純：ID token 只用 RS256，用 jwks_uri 裡的公鑰驗。要注意的是 iss：Google 的文件說它可能是 https://accounts.google.com，也可能是沒有 https:// 的 accounts.google.com，兩個都要接受；存進資料庫前統一成一種寫法，不然同一個人會變成兩個身分。

LINE 是這課的主角，也是最容易出事的地方。它的 discovery 只寫了 ES256，但 LINE Login v2.1 的文件寫得很清楚，簽法依整合方式而不同：

  • 網頁登入（咖啡店現在做的這種）拿到的 ID token 用 HS256，金鑰是你的 channel secret。channel secret 是 LINE Developers Console 發給你這個 LINE Login 頻道的秘密字串，它的 UTF-8 位元組直接當 HMAC 金鑰。HS256 是對稱的：LINE 用它簽，你用同一把驗。
  • 原生 App、LINE SDK、LIFF（在 LINE App 裡開的網頁）拿到的 ID token 才用 ES256，公鑰在 jwks_uri 的 JWKS 裡，依 header 的 kid 挑。

同一個 iss，兩種簽法。這代表演算法不能看 discovery 決定（它只列了一種），更不能看 token 自己 header 裡的 alg 決定（第 8 課的演算法混淆：攻擊者會挑對他有利的那種）。正確做法是依咖啡店實際用的整合方式，在設定裡寫死「這個發行者用 HS256、金鑰是 channel secret」。

用 ES256 時還有一個問題：JWKS 什麼時候去抓？兩個極端都不行。每個請求都抓，發行者會限流你，你的登入也跟著它的網路延遲一起變慢。抓一次就永遠不更新，發行者輪替金鑰（第 8 課）之後，新 token 的 kid 你都不認得，所有人都登入失敗。

做法是 JWKS 快取：抓來的公鑰存在記憶體，過了一段時間才重抓；遇到不認得的 kid，代表發行者可能剛換了金鑰，可以提早重抓，但要限制頻率。原因是 kid 是 token 裡的字，攻擊者可以每個請求填一個亂碼。如果每次看到不認得的 kid 就去抓，你等於替他對發行者發動攻擊，自己也被限流，連正常使用者都登入不了。另外兩件事也要顧到。快取剛過期時，很多請求會同時發現要重抓，只讓第一個去抓，其他請求等同一次結果，這叫 single-flight（第 10 課）；不這樣做，同一瞬間會對發行者發出幾十個請求。重抓失敗時，例如發行者暫時連不上，已知的 kid 繼續用快取裡的舊公鑰，不要讓所有登入一起失敗。成熟的函式庫都這樣做（jose 的預設值見課末「補充與查表」），練習 3 會自己寫一個。

有了演算法和金鑰，簽章就驗得了。但簽章只回答「是 LINE 簽的、沒被改過」。LINE 每天簽出無數張 ID token，給別的網站的、過期的、別人登入時的，每一張的簽章都是對的。所以驗簽章只是其中一步。

驗證 ID token：六步各擋哪一張偽造的 token？

OIDC Core 1.0（errata set 2）§3.1.3.7 規定了 client 驗 ID token 的步驟。跟第 9 課驗 access token 比，順序和精神一樣，差別有兩個：aud 要等於自己的 client_id，以及多了 nonce。把每一步都想成「它擋住的是哪一張 token」，就比較不會漏：

  1. iss 必須完全等於你設定的發行者網址。它擋的是「別的發行者簽的 token」：咖啡店只信任 LINE 和自家身分服務，其他人簽的一律不認。用 startsWith、includes 比對，https://access.line.me.evil.example 這種攻擊者自己架的發行者就混得進來。用 iss 查設定表時，用 Object.hasOwn 或 Map：一般物件上 issuers['constructor'] 會查到原型鏈上的函式，被當成一份設定。
  2. 簽章：它擋的是「內容被改過或自己捏造的 token」。規格說 alg 應該是預設的 RS256 或註冊時約定的演算法。實作上就是上一節的結論：每個發行者在設定裡寫死一種演算法和金鑰，header 的 alg 必須跟設定相同，再用設定的金鑰驗。LINE 同時有 HS256 與 ES256，這一步比第 8 課的例子更容易寫錯。
  3. aud 必須包含自己的 client_id，而且如果還有其他受眾，每一個都必須是你信任的；只要出現一個你不信任的，就整張拒絕。它擋的是「LINE 發給別的網站的 token」：攻擊者經營一個也接 LINE 登入的網站，收集來的 ID token 簽章、iss 都對，只有 aud 不是咖啡店。
  4. 現在時間必須早於 exp。它擋的是過期的 token，例如從舊的記錄檔裡翻出來的。
  5. iat 不能離現在太遠：可接受的範圍由 client 自己決定。它擋的是很久以前簽的 token。另一個用處：如果你的系統要防同一張 ID token 被重送（例如 App 直接 POST ID token、沒有 session 可刪的情況），就得記住已經用過的 nonce；iat 有上限，這份紀錄只要保留到那個上限就能清掉。
  6. 授權請求帶了 nonce，ID token 就必須有 nonce，而且相等。它擋的是「真的、沒過期、給咖啡店的，但不是這一次登入的 token」。ID token 沒有 nonce 時「略過不檢查」，等於沒驗。

任何一步失敗就拒絕，全部通過才用 (iss, sub) 找會員。順序也有意義：先確認 iss、驗完簽章，後面讀到的 aud、exp 才是可信的資料；還沒驗簽章就看內容，看到的是攻擊者想讓你看的東西。練習 1 會把六步完整寫一遍。

💡 實務上：直接從 token 端點拿到的 ID token，也一律驗簽章
規格允許一個例外：ID token 是後端直接透過 TLS 向 token 端點拿到的，可以用 TLS 的伺服器驗證代替驗簽章。Google 的文件也這樣說，但同時強調：只要 ID token 被轉交給其他元件，那些元件就一定要驗。咖啡店的 callback 符合這個例外，實務上仍然一律驗。驗簽章的成本很低，而程式碼總有一天會被重構成「前端把 ID token 傳上來」。LINE 的 App 與 LIFF 就是這種情況：ID token 在使用者的手機上，送到你的後端時，跟任何人隨手寫的字串沒有差別。

第 6 步的 nonce 還沒解釋清楚。它跟第 12 課的 state 一樣，都是登入前產生的隨機值；咖啡店的 callback 已經檢查 state 了，為什麼還要多一個？

已經有 state，為什麼還要 nonce？

state 和 nonce 都在顧客按「用 LINE 登入」時產生、存在顧客自己的 session 裡，差別在它們出現的位置，位置決定了誰檢查、擋得住什麼：

state 只保護「callback 這個請求」：它在網址上，不在 ID token 裡。只要 ID token 不是由你這一次的 code 換來的，state 就完全幫不上忙。兩種常見的情況：App 或 LIFF 把 ID token 直接 POST 到你的 API，中間根本沒有 callback；攻擊者拿到一張別人登入時的舊 ID token，想重送一次。這兩種 token 的簽章、iss、aud 都對。

nonce 在 OP 的簽章裡，攻擊者改不了。咖啡店在 session 裡存著這一次登入產生的 nonce，ID token 裡的值跟它相等，就證明「這張 ID token 是為了這個 session 剛剛發起的那次登入簽的」；舊 token 的 nonce 是舊登入的值，對不上。RFC 9700 也提到：OIDC 流程裡 nonce 提供 CSRF 保護。兩個都帶，各擋一層。

到這裡，callback 已經能確認手上的 ID token 是 LINE 為了這次登入、發給咖啡店的。接下來是第 ⑦ 步的第二件事：token 說這個人是 iss 為 https://access.line.me、sub 為某個字串的使用者，咖啡店要把它對應到哪一位會員？

驗完了，這是哪位會員？用 (iss, sub)，不是 email

payload 裡有 email，咖啡店的會員資料也有 email，直覺會想用 email 對應。OIDC Core §5.7 說得很直接：iss 加上 sub 是唯一能當穩定識別的組合；email、電話、使用者名稱、姓名都 MUST NOT 當唯一識別。原因有四個，前三個是 email 的問題，第四個是 sub 單獨使用的問題：

  • email 會變：使用者在 Google 改了主要 email，用 email 認人就變成另一個帳號，原本的點數和訂單都找不到。
  • email 會被回收：規格明說發行者可以在不同時間把同一個 email 給不同的人。公司信箱在員工離職後被收回、再發給新人，新人就會登入成舊人的帳號。
  • email 可能沒驗證過：有些 OP 讓使用者填任何 email，email_verified 是 false。
  • 只用 sub 也不夠：ID token 那一節說過，sub 只在同一個發行者內唯一，Google 的某個 sub 和你自家身分服務的某個 sub 可能是同一串字。

所以外部身分單獨一張表，用 (iss, sub) 當唯一鍵（PostgreSQL 課第 12 課的 UNIQUE 約束：同一組值只能出現一次）。一位咖啡店會員可以連著好幾個外部身分，例如陳美華同時連了 LINE 和 Google：

CREATE TABLE external_identities (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users(id),
  iss        text   NOT NULL,
  sub        text   NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (iss, sub)
);

callback 的查法就是：驗完 ID token，用 (iss, sub) 查這張表，查到就知道是哪位會員。LINE 的 sub 還有一個特性會影響這張表（同一個人在不同公司底下的 sub 不同），細節見課末「補充與查表」。

查不到的時候才是難題。陳美華原本用 email 加密碼註冊，累積了 800 點；今天她第一次按「用 LINE 登入」，external_identities 裡還沒有她的 LINE (iss, sub)。咖啡店要決定：這是新顧客，還是陳美華？

陳美華第一次按 LINE 登入：帳號連結怎麼不被接管？

把一個外部登入身分接到既有的會員帳號上，叫帳號連結（account linking）。陳美華這種情況就需要它：咖啡店得把她的 LINE (iss, sub) 寫進 external_identities、指向她原本的帳號，之後她按 LINE 登入才會回到有 800 點的那個帳號。

最直覺的寫法是「email 一樣就當成同一個人，自動接上」。看看攻擊者怎麼利用它。假設咖啡店除了 LINE，也接了一個不驗 email 的 OP「某論壇登入」。執行後看兩行輸出：攻擊者登入成了哪個使用者、拿到幾點，以及他的外部身分是不是已經永久接上：

這就是帳號接管（account takeover）：攻擊者取得了別人帳號的控制權。而且是永久的，因為他的 (iss, sub) 已經寫進陳美華的帳號，之後每次用「某論壇登入」都會直接進來，就算咖啡店後來修了程式也一樣。防守的規則有三條：

  • 不自動合併。找不到 (iss, sub)、但有同 email 的既有會員時，請使用者先用原本的方式（密碼，或已經連結的另一個 OP）登入，在已登入的狀態下確認「要把這個 LINE 帳號連到我的帳號嗎」，確認後才寫入 external_identities。攻擊者過不了「用原本的方式登入」這一關，因為他不知道陳美華的密碼。
  • 只有 email_verified === true 才把 email 當成有意義的資料，而且要是布林的 true。有些 OP 曾經回字串 "true"，你的程式不要猜，嚴格比對；字串 "false" 在 JavaScript 是 truthy，if (claims.email_verified) 會判成已驗證。
  • 即使 email_verified 是 true，也只代表「OP 在某個時間點驗證過」，不代表這個 OP 對 email 的管理跟你一樣嚴格。所以它仍然只是「提示可以連結」，不是「直接登入」。

練習 2 會把這段邏輯寫出來：查到 (iss, sub) 就登入，有同 email 的已驗證會員就要求確認連結，其他情況建立新會員。

💡 實務上：社群登入上線後，客服常接到「我的點數不見了」
多半是同一個人第一次按「用 LINE 登入」時被建成新帳號，他以為還是原本那個。上線前先跟 PM 把畫面談好：找到同 email 的既有會員時，提示「你可能已經有帳號，請先用原本的方式登入再連結」，不要默默建新帳號，也不要自動合併。會員設定頁要能看到、解除已連結的登入方式，但不能解除到一種都不剩。客服手動合併帳號也是一種帳號連結，要先確認是本人，不能只憑對方報上的 email。

找到會員之後，就剩第 ⑦ 步的最後一件事：callback 要交給瀏覽器什麼，之後顧客打咖啡店的 API 才算「已登入」？

找到會員之後，callback 交出什麼？

前端工程師常有的直覺是：ID token 也是一張 JWT，那就把它交給 Vue，之後放進 Authorization: Bearer 去打咖啡店的訂單 API。這行不通，原因在流程裡的兩種 token 用途完全不同：

ID tokenaccess token
給誰看給 client（咖啡店）自己看給 API（例如 LINE 的 UserInfo）看
aud咖啡店的 client_id那支 API
格式一定是 JWTOAuth 沒規定，可能是不透明字串
回答的問題「剛剛登入的是誰」「持有者可以做什麼」
能拿去打 API 嗎不行可以，只能打它的 aud

拿 ID token 打訂單 API，會撞上三個問題。第一，ID token 的 aud 是咖啡店網站的 client_id，不是訂單 API；訂單 API 照第 9 課的規則驗 aud，就該拒絕它。第二，ID token 沒有 scope、沒有權限，它只說「誰登入了」，訂單 API 從它看不出這個人能做什麼。第三，兩種 JWT 混用，API 很難分辨收到的是哪一種：RFC 9068 規定 JWT 格式的 access token 要在 header 寫 typ: "at+jwt"，就是為了讓 API 分得出 ID token 和 access token；RFC 8725 也建議不同種類的 JWT 用互斥的驗證規則。同樣的道理，LINE、Google 發的 access token 是用來呼叫 LINE、Google 的 API 的，也不能拿來打你的 API。

最常見、也最簡單的做法：callback 驗完 ID token、用 (iss, sub) 找到會員之後，建立咖啡店自己的 session（第 4 課），而且照第 4 課的規則換一個新的 session ID。之後前端打咖啡店 API 帶的是咖啡店自己的 session cookie，跟 LINE 的 token 再也沒有關係。ID token 完成了「證明這次是誰登入」的任務就可以丟掉。LINE 的 access token 如果之後還要用（例如查好友關係），存在後端，不給前端。

只在前端驗 ID token 沒有用。Vue 裡驗完簽章、再把「已驗證」的使用者 ID 傳給後端，後端收到的就只是一個任何人都能改的 ID。驗證一定在後端做，前端頂多解碼來顯示名字。

換成自己的 session 也決定了登出的樣子。登出有兩層：咖啡店的 session 和 LINE 的登入狀態。在咖啡店按登出，只會刪掉咖啡店的 session（第 4 課）；使用者在 LINE 還是登入的，下次按「用 LINE 登入」可能一秒就回來了。這通常是使用者想要的。店內共用的平板這種需要連 LINE 一起登出的情境，OIDC 有另一份規格，但 Google 和 LINE 都沒有支援，細節見課末「補充與查表」。

callback 的三件事都做完了。回頭看整個流程，有一樣東西撐著第 2 步的簽章驗證：LINE 網頁登入的 HS256 金鑰，也就是 channel secret。它如果外流，前面每一步都會失效。

channel secret 外流會怎樣？

LINE 網頁登入的 ID token 用 HS256 簽，金鑰是你的 channel secret。HMAC 是對稱的（第 8 課）：用來驗的那把金鑰，同時也能簽。所以拿到 channel secret 的人，不只能驗 token，還能自己簽出 LINE 會簽的 token。假設有人把 channel secret 寫進了前端的 .env，打包後誰都看得到。執行後看第一行：攻擊者自己簽、sub 填陳美華的 ID token，咖啡店驗出來是 true：

簽章、iss、aud 全部正確，因為從密碼學的角度，它就是一張有效的 token。channel secret 外洩，等於任何人都能用任何 LINE 使用者的身分登入你的網站。nonce 也擋不住：攻擊者自己在咖啡店發起登入，就知道自己 session 裡的 nonce，照填進去就好。

規則：channel secret、client secret 只放在後端的環境變數或 secrets 管理系統（第 23 課），絕不進前端的打包、不進 Git；懷疑外洩就到 LINE Developers Console 重新產生。這也解釋了 Discovery 那一節的「兩種簽法」：App 和 LIFF 拿到的是 ES256 的 token，因為 App 在使用者手上，放不了秘密，只能用公鑰驗。LINE 也提供一支由它替你驗 ID token 的 API，取捨見課末「補充與查表」。

💡 實務上：開發、測試、正式環境各用各的頻道和 secret
在同一個提供者底下為每個環境各開一個 LINE Login 頻道：sub 還是同一個，但測試環境（staging）的 secret 外洩不會波及正式站。每個 callback URL 都要先在 LINE Developers Console 登記，換網域或新增環境時忘了加，登入會直接失敗，這是上線當天很常見的狀況。Code review 看到 VITE_、NEXT_PUBLIC_ 這類前綴的變數裡放著 secret，直接擋下：這些變數會被打包進前端。

到這裡，「用 LINE 登入」的後端已經完整：產生 state、nonce、PKCE，驗六步，處理兩種簽章和 JWKS 快取，帳號連結，換成自己的 session，保管 channel secret。這是只接一個 OP 的工作量。最後一個問題是：這些要不要都自己做？

這麼多事，要自己做還是交給身分服務？

把剛才那份清單加上這門課後面幾課的內容：密碼儲存（第 3 課）、MFA（第 14 課）、passkey（第 15 課）、忘記密碼與防暴力破解（第 16 課），登入系統是一大塊工作。另一條路是交給身分服務（identity provider，IdP）：專門負責登入、MFA、帳號管理的系統。雲端代管的版本常叫 IDaaS（Identity as a Service）。例如 Keycloak（開源、自己架）、Amazon Cognito、Auth0（代管）。

身分服務跟咖啡店的整合方式，正是這一課學的 OIDC：它是 OP，咖啡店是 client。顧客在身分服務的頁面登入，咖啡店拿到它簽的 ID token，照這課的六步驗。差別在於 LINE、Google 這些登入方式改成接在身分服務後面，咖啡店只需要接一個 OP。兩條路的取捨：

考量自己做身分服務
上線速度慢：每個流程都要寫、要測快：社群登入、MFA、passkey 多半是設定就有
費用主要是人力與維護代管服務多半依每月活躍使用者計價，使用者多了費用跟著漲；自架 Keycloak 換成維運成本
資料放哪裡自己的資料庫代管服務在對方的雲上，要看個資與法規要求
客製流程想怎麼做都行，例如店員在 POS 用 4 位數 PIN 快速切換受限於服務提供的擴充點
被綁定的程度沒有使用者的密碼雜湊、MFA 設定在對方那裡，搬家時不一定匯得出來

判斷的方向：團隊小、時程緊、需要的是標準流程（email＋密碼、社群登入、MFA），用身分服務通常比較划算，也比自己第一次寫的安全。登入流程本身是產品的核心差異、有特殊的法規或資料落地要求、使用者規模大到計價很痛，才值得自己做。

不管選哪一種，下面這些都還是你的責任。身分服務只負責「你是誰」，這課後半段處理的事情大多落在它的範圍之外：

  • 授權：身分服務告訴你「這是陳美華」，「陳美華能不能看訂單 #42」是你的程式決定的（第 18～20 課）。
  • token 驗證：你的 API 要照這課的步驟驗身分服務發的 token，加上 JWKS 快取。設定錯一個 aud，身分服務再好也沒用。
  • session 與 token 的管理：登入之後的 session、登出、撤銷（第 10、11 課）。
  • 帳號流程的安全：帳號連結、改 email、客服重設帳號，這些業務流程寫錯，一樣會被接管。

補充與查表

主線用不到、但接 LINE、Google 或設定驗證函式庫時會查的細節。

azp（authorized party）

ID token 裡有時會看到 azp，意思是「這張 token 發給哪個 client」。OIDC Core 1.0 的 errata set 2（2023-12-15）把「多個 aud 時要檢查 azp」的規定拿掉了，現在只有用到擴充規格時才驗，一般情況可以忽略。練習 1 也不檢查它。

LINE 的 sub 是 pairwise

LINE 的 discovery 寫著 "subject_types_supported": ["pairwise"]。意思是：同一個 LINE 使用者，在 LINE Developers Console 裡不同「提供者（provider）」底下的 sub 不一樣；同一個提供者底下的各個頻道拿到的是同一個。提供者是管理頻道的單位，通常一間公司一個。這保護使用者隱私（不同公司無法用 sub 串起同一個人），也代表你把 LINE Login 頻道搬到另一個提供者底下時，external_identities 裡舊的 sub 就對不上了。前面「開發、測試、正式環境各用各的頻道」的建議，要在同一個提供者底下開，就是這個原因。

jose 的 JWKS 快取預設值

jose 6 的 createRemoteJWKSet 預設快取 10 分鐘（cacheMaxAge），遇到不認得的 kid 時，要距離上次成功抓取 30 秒（cooldownDuration）才會再抓。

LINE 的 ID token 驗證 API

LINE 提供一支驗證 API（POST https://api.line.me/oauth2/v2.1/verify，帶 id_token 與 client_id），由 LINE 替你驗。它省掉自己寫驗證，代價是每次登入多一個對外請求，而且 nonce 還是要自己負責比對（帶 nonce 參數讓它比對，或自己比）。

連 OP 一起登出：RP-Initiated Logout

需要連 OP 一起登出時（例如店內共用的平板），OIDC 有一份獨立的規格 RP-Initiated Logout：把使用者導到 OP 的 end_session_endpoint。不是每個 OP 都支援，Google 和 LINE 的 discovery 都沒有列這個端點，所以共用裝置的情境要另外處理，例如結帳後自動登出、提醒使用者。

練習

練習 1：咖啡店同時接了兩個發行者：LINE 網頁登入（HS256，金鑰是 channel secret）和自家的身分服務 https://login.coffee-auth.example（ES256，JWKS）。寫 validateIdToken(idToken, ctx)，依序檢查，遇到第一個失敗就回傳對應的錯誤：

  1. 用 decodeJwt 解碼；解不開、header 或 payload 不是物件、payload 的 iss 不是字串 → malformed。
  2. 用 iss 在 ctx.issuers 找設定，完全相等才算，用 Object.hasOwn（iss 是 'constructor' 也要找不到）→ 找不到是 unknown_issuer。
  3. header 的 alg 必須等於設定的 alg → 否則 alg_mismatch。
  4. 用設定的演算法與金鑰驗簽章 → 失敗是 bad_signature。HS256：secret 當 HMAC-SHA256 金鑰。ES256：header 的 kid 在設定的 jwks 找相同的那一把，必須是 kty: 'EC'、crv: 'P-256'，簽章剛好 64 bytes（第 8 課練習 3）。
  5. sub 是非空字串、exp 與 iat 是數字、aud 是字串或字串陣列 → 否則 malformed。
  6. aud 必須包含 clientId，其他值都必須在 otherTrustedAudiences 裡 → 否則 wrong_audience。不檢查 azp。
  7. now >= exp → expired（時間都是秒）。
  8. |now - iat| > maxIatAgeSeconds → iat_too_old。
  9. nonce 必須存在而且等於 expectedNonce → 否則 nonce_mismatch。

全部通過回 { ok: true, claims }。任何情況都不能丟出例外。

練習 2：ID token 驗證通過後，用 claims 找出（或建立）咖啡店的使用者。寫 linkOrCreateUser(db, claims)：

  1. 在 db.identities 用 (iss, sub) 兩個都相等找外部身分。找到 → { action: 'login', userId }。
  2. 找不到，而且 claims.email_verified === true（布林值）、claims.email 是字串、db.users 有同 email 的使用者 → 不要自動合併，也不要寫入任何東西，回 { action: 'require_link_confirmation', userId: 那位使用者的 id }，讓他先用原本的方式登入再確認。
  3. 其他情況 → 建立新使用者（id 是目前最大的 id + 1，沒有使用者時是 1），email 只有在 email_verified === true 而且是字串時才寫入，否則是 null；同時新增一筆外部身分。回 { action: 'created', userId }。

練習 3：咖啡店的 API 要驗自家身分服務發的 ES256 token，寫一個 JWKS 快取 createJwksCache(deps, opts)，回傳 { getKey(kid) }：

  • 第一次呼叫時抓 JWKS（deps.fetchJwks()）。
  • 距離上次成功抓取超過 maxAgeMs（>=）就重抓。
  • kid 找不到時，距離上次嘗試抓取已經 >= minRefetchIntervalMs 才重抓一次；還在間隔內就直接回 null。抓取失敗也算一次嘗試。
  • single-flight（第 10 課）：正在抓的時候，其他呼叫等同一次抓取的結果，不另外抓。
  • 抓取失敗（Promise reject 或直接 throw）時沿用手上的金鑰；手上沒有就回 null。getKey 不能丟出例外。

時間一律用 deps.now()（毫秒），不要用 Date.now()，也不要留下 setTimeout、setInterval。

練習 4：同事設計外部登入的資料表：users.email 設 UNIQUE，「用 Google 登入」時用 ID token 的 email 找使用者，找到就登入。理由是「email 是唯一的，而且 Google 驗證過」。最大的問題是什麼？

✓ OIDC Core §5.7 規定只有 iss 加 sub 能當穩定識別，email 這類欄位 MUST NOT 當唯一識別：使用者改 email 會變成另一個帳號；email 被回收給新人時，新人會登入成舊人的帳號。a 錯：email_verified 只代表 OP 在某個時間驗證過，不解決改名與回收，接了第二個 OP 後還有自動合併被接管的問題。b 不是重點。d 錯：sub 只在同一個發行者內唯一，不同發行者可能撞在一起，要搭配 iss。

練習 5：Vue 前端用 Google 登入後拿到了 ID token，同事想把它放進 Authorization: Bearer 去呼叫咖啡店的訂單 API，「反正都是 Google 簽的 JWT」。該怎麼回應？

✓ ID token 回答「誰登入了」，aud 是 client；API 照第 9 課驗 aud 就該拒絕它，RFC 9068 的 typ: at+jwt 也是為了區分兩者。a 錯在只看簽章，忽略了「給誰的」。c 錯：Google 的 access token 是給 Google 的 API 用的，aud 也不是你的訂單 API。d 不是原因。最簡單的做法是後端驗完 ID token、建立咖啡店自己的 session。

練習 6：咖啡店的 callback 已經檢查了 state。同事說「nonce 也是一個隨機值，有 state 就夠了，LINE 也說 nonce 是選填」。下面哪個說法正確？

✓ state 不在 ID token 裡，只保護「導回來的這個請求」。App、LIFF 把 ID token 直接送到 API，或攻擊者重送一張舊的 ID token 時，只有簽章裡的 nonce 能證明它屬於這次登入。b 錯：規格只在 implicit 流程把 nonce 定為必填、授權碼流程是選填，但 ID token 只要不是由你這次的 code 換來（App、LIFF 直接送上來），就只剩 nonce 能把它綁回這次登入。c 錯：LINE 規定 state 必填，而且 state 是在換 token 之前就擋下偽造的 callback。d 錯：OP 只是把收到的 nonce 原樣寫進 ID token，它不知道你的 session 裡存了什麼；比對一定是 client 自己做（LINE 的驗證 API 也要你把 nonce 傳給它才會比）。

練習 7：LINE 網頁登入的 ID token 用 HS256 簽。下面哪一句正確？

✓ HS256 是對稱的（第 8 課），LINE 和你共用 channel secret。a 錯：持有 channel secret 的你（以及偷到它的人）也簽得出來，「OP 簽的 token 只有 OP 能產生」只對非對稱簽章成立。b 錯得最嚴重：放到前端等於公開，而且前端驗證本來就沒有意義。c 錯：HS256 本身沒問題，問題在金鑰怎麼保管。channel secret 只放後端，外洩就到 LINE Developers Console 重新產生。

練習 8：團隊三個人，兩個月後要上線會員系統（email 登入、LINE 登入、MFA）。主管決定用代管的身分服務，並說「這樣安全就交給它了」。哪一句最準確？

✓ 小團隊、時程緊、需求是標準流程，身分服務能省下大量工作，也比第一次自己寫的更不容易出錯，所以 c 不對。但它只負責「你是誰」：「你能做什麼」、API 怎麼驗它發的 token、登入後的 session 與撤銷、帳號連結和客服流程都還是你的，a 錯。d 錯：OIDC 讓整合方式標準化，但使用者的密碼雜湊、MFA 設定存在對方那裡，不一定匯得出來，搬家成本是選擇時要算進去的代價。

常見錯誤

  • 依 header 的 alg 選演算法：LINE 同一個 iss 有 HS256 與 ES256，看 header 選就給了攻擊者選金鑰的機會。每個整合方式在設定裡寫死一種演算法和金鑰。
  • 每個請求都抓 JWKS，或 kid 找不到就無限重抓：慢、被發行者限流，還讓攻擊者用亂填的 kid 拖垮你。快取、限制重抓頻率、single-flight。
  • Google 的 iss 只接受一種寫法：Google 的 ID token 可能是 https://accounts.google.com 或 accounts.google.com。兩個都接受，存之前統一。
  • 不驗 aud，或用 includes 驗：別的 client 的 ID token、coffee-web-evil 都混得進來。統一成陣列，必須有自己、其他每個都要信任。
  • 沒送 nonce，或 token 沒有 nonce 時略過：ID token 沒有綁回這次登入，重放、注入都擋不住。每次登入都產生、存在 session、用過即刪。
  • 用 email 找使用者、自動合併帳號：攻擊者在不驗 email 的 OP 註冊受害者的 email，一登入就接管。用 (iss, sub) 認人；有同 email 的帳號時，要使用者先用原本的方式登入再確認連結。
  • 只用 sub、不搭配 iss：sub 只在同一個發行者內唯一。資料表用 UNIQUE (iss, sub)。
  • if (claims.email_verified)：字串 "false" 是 truthy。用 === true。
  • 只在前端驗 ID token：後端收到的「已驗證的使用者 ID」任何人都能改。在後端驗。
  • 把 ID token 當成 API 的 access token：aud 不對、沒有權限資訊。驗完換成自己的 session。
  • channel secret、client secret 放進前端或 Git：HS256 的 channel secret 外洩，任何人都能簽出 LINE 使用者的 ID token。只放在後端的環境變數或 secrets 管理系統。

小結

  • OAuth 的 access token 只說「持有者可以做什麼」，不說「給誰的、為了哪一次登入」，不能拿來做登入。OIDC = OAuth 2.0 授權碼流程 + openid scope + ID token + nonce + UserInfo + Discovery。client（規格叫 RP）是咖啡店，OP 是 Google、LINE。
  • callback 拿到 ID token 後做三件事：驗證、用 (iss, sub) 找會員、建立咖啡店自己的 session。
  • 簽章的演算法和金鑰寫死在設定裡，不看 discovery、不看 header。LINE：iss 是 https://access.line.me；網頁登入 HS256（金鑰是 channel secret），App／LIFF 用 ES256（JWKS）。Google：只用 RS256，iss 有兩種寫法。
  • JWKS 要快取：定時重抓、不認得的 kid 限頻率重抓、single-flight、抓不到時沿用舊鑰。
  • 驗 ID token（OIDC Core §3.1.3.7）：iss 完全相等 → 依設定的演算法驗簽章 → aud 有自己、沒有不信任的 → exp → iat → nonce。每一步擋一種 token，在後端做。
  • state 在網址上，保護 callback；nonce 在簽章裡，把 ID token 綁回這次登入。兩個都存在 session、用過即刪。
  • 用 (iss, sub) 認人，不用 email；帳號連結不自動合併，要使用者先用原本的方式登入再確認，只有 email_verified === true 才考慮 email。
  • ID token 是給 client 看的登入證明，不能拿去打 API；驗完換成自己的 session。channel secret 能驗就能簽，只放後端。
  • 身分服務能省下大量登入工作，但授權、token 驗證、session、帳號流程的安全仍是自己的責任；選擇時把費用、資料位置、客製需求、搬家成本算進去。
