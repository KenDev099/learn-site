階段 2：瀏覽器裡的登入狀態：Cookie、Session 與跨站攻擊 · 第 6 課

CSRF：借你的 Cookie 發請求

王小明登入咖啡店網站後，沒登出就去逛別的網站。其中一個標榜「免費拿鐵抽獎」的頁面藏了一個看不見的表單，頁面一載入就自動送出 POST https://api.coffee.example/orders/42/cancel。瀏覽器替這個請求附上咖啡店的 session cookie，API 看到合法的 session，就把王小明的訂單 #42 取消了。王小明什麼都沒點，惡意網站也從頭到尾沒碰到他的 cookie。

這叫跨站請求偽造（Cross-Site Request Forgery，CSRF）：惡意網站讓你的瀏覽器帶著你的 cookie，對你已登入的網站送出你沒打算送的請求。第 5 課說過，同源政策擋的是別的網站「讀」回應，不擋它「送」請求；CSRF 只需要「送」。

這一課從頭到尾處理同一件事：讓咖啡店的 POST /orders/42/cancel 只接受王小明在咖啡店網站上自己按下的取消，拒絕別的網站替他送出的請求。學完你能替一個用 cookie 登入的網站選出 CSRF 防線，並說得出每一層擋什麼、漏什麼。

這課的路線：
  1. 王小明什麼都沒點，訂單怎麼被取消的：重現攻擊，找出 CSRF 成立的三個條件，之後每一種防法各打破其中一個。
  2. 能不能叫瀏覽器跨站時別帶 cookie：SameSite。明寫 Lax 就擋得住開頭的表單，但它還有四個洞。
  3. 伺服器怎麼知道請求從哪個網站來：瀏覽器自己填、網頁改不掉的 Fetch Metadata 與 Origin 標頭，照 Go 1.25 的規則寫成伺服器端檢查。
  4. 能不能在請求裡放一個攻擊者拿不到的值：CSRF token，以及它為什麼一定要用 HMAC 綁到 session。
  5. Vue 前台只打 JSON API 時有沒有更省事的防法，防線畫好之後還有哪些地方會漏。
這課會用到：
  • 第 4 課的 session cookie 與 SameSite：瀏覽器會自動替請求附上目標網站的 cookie，SameSite 決定跨站時帶不帶。
  • 第 5 課的同源、同站與預檢：來源看 scheme＋host＋port，站看 scheme＋可註冊網域；表單這類簡單請求直接送出，帶自訂標頭的跨來源請求要先通過預檢。
  • 第 2 課的安全亂數與 HMAC：crypto.getRandomValues 產生猜不到的值；HMAC 用伺服器的金鑰算出標籤，用 crypto.subtle.verify 驗證。

王小明什麼都沒點，訂單怎麼被取消的？

先重現攻擊。攻擊者在 https://evil.example/win-a-free-latte 放了這段 HTML：

<form action="https://api.coffee.example/orders/42/cancel" method="POST">
  <input type="hidden" name="reason" value="不想要了">
</form>
<script>document.forms[0].submit()</script>

前三行是一個指向咖啡店 API 的表單，裡面只有一個隱藏欄位；最後一行在頁面載入時替使用者按下送出。使用者畫面上看到的，可能只是一張抽獎圖。

這段 HTML 能成功，靠的是瀏覽器兩個很老的行為。第一，任何網站都能對任何網址送出表單。表單送出是瀏覽器最古老的功能，跨網站送表單不需要 CORS 許可，也不會先預檢（第 5 課：表單屬於簡單請求）。第二，瀏覽器送請求時，附上的是「目標網站」的 cookie，不管這個請求是哪個網頁發起的。請求要送去 api.coffee.example，瀏覽器就附上 api.coffee.example 的 cookie，即使按下送出的是 evil.example 的頁面。

注意攻擊者從頭到尾讀不到任何東西：cookie 的值它不知道，⑤ 的回應受同源政策保護，evil.example 的程式也看不到。但它不需要讀，請求在 ④ 抵達伺服器時，取消訂單這件事已經發生了。所以 CSRF 傷害的是「會改變狀態」的請求：取消訂單、改 email、兌換集點、轉讓會員點數。只回傳資料的請求，攻擊者讀不到回應，沒有收穫。

把這次攻擊拆開，它要成立需要三個條件，缺一不可：

  1. 瀏覽器會自動帶憑證：cookie 會在請求裡自動附上，攻擊者不用知道它的值。HTTP Basic 認證、客戶端憑證也是瀏覽器自動帶的憑證，一樣適用。
  2. 伺服器只靠這個憑證判斷身分：API 看到合法的 session 就照做，不管請求從哪個網頁來。
  3. 請求裡沒有攻擊者猜不到的東西：取消訂單只需要訂單編號，攻擊者知道或猜得到所有參數。

這三個條件就是防禦的方向：打破任何一個，攻擊就不成立。接下來每一種防法，都是在打破其中一個。先從最外層的第一個條件開始：cookie 是瀏覽器自動帶的，那能不能叫瀏覽器在跨站的時候別帶？

能不能叫瀏覽器跨站時別帶 cookie？SameSite

可以，這就是 cookie 的 SameSite 屬性。第 4 課設 session cookie 時寫了 SameSite=Lax，當時只說它決定跨站時帶不帶；這一節看它怎麼決定。

瀏覽器先判斷請求是不是跨站。「站」是第 5 課的 site：scheme 加上可註冊網域。發起請求的頁面跟目標網址同站，SameSite 不管，cookie 照帶；不同站，才看 SameSite 的值。evil.example 跟 api.coffee.example 不同站，所以開頭的表單是跨站請求。

SameSite 的規則用到兩個名詞，先講清楚。安全方法（safe method）是 GET、HEAD、OPTIONS。依 HTTP 的語意，它們只讀不改（Node 課第 14 課），伺服器收到它們不應該改任何資料，所以放行它們被認為沒有風險。頂層導覽（top-level navigation）是整個分頁跳到另一個網址、網址列會跟著變的請求：點連結、送出表單、location.href = …。fetch、<img>、<script>、iframe 裡的跳轉都不是頂層導覽，它們是頁面在背景載入東西。送出表單算頂層導覽，因為送出後整個分頁會跳到回應的頁面。

有了這兩個名詞，SameSite 的三個值是：

  • SameSite=Strict：任何跨站請求都不帶。
  • SameSite=Lax：跨站時只有「頂層導覽，而且是安全方法」才帶。
  • SameSite=None：跨站也帶，必須同時有 Secure，否則瀏覽器整個拒收這個 cookie。

Lax 為什麼偏偏放行「頂層導覽的安全方法」？因為那正是使用者從別的網站點連結過來的情況。王小明在 Gmail 的信裡點了咖啡店的訂單連結，他期待看到自己已登入的訂單頁；這個請求是 GET、不改資料，帶 cookie 沒有風險。開頭的攻擊是跨站的 POST，不是安全方法，Lax 就不帶。各種情境對照如下：

情境（目標都是 api.coffee.example）StrictLaxNone; Secure
evil.example 自動送出的表單 POST（頂層導覽）不帶不帶帶
evil.example 用 fetch 送 POST（帶 credentials）不帶不帶帶
evil.example 的 <img src>、iframe不帶不帶帶
從 Gmail 網頁版的信裡點連結進來（GET 頂層導覽）不帶帶帶
marketing.coffee.example（同站的子網域）送出的 POST帶帶帶
shop.coffee.example 前台呼叫 API（同站）帶帶帶

表的第一列就是開場問題的最小答案：session cookie 明寫 SameSite=Lax，evil.example 自動送出的表單就不帶 cookie，API 看不到 session，回 401，訂單保住了。練習 1 會把這張表的判斷寫成函式。

那為什麼不直接用最嚴的 Strict？看表的第四列：Strict 連從別的網站點連結進來都不帶 cookie。王小明從 Gmail 點訂單連結，會看到「沒登入」，要在站內再點一次或重新整理才正常。為了避開這個體驗問題，session cookie 通常用 Lax。

但 Lax 只擋住了「跨站送 POST」這一種情況，它還有四個洞：

  1. 會改狀態的 GET：如果咖啡店有 GET /orders/42/cancel、GET /logout、GET /rewards/redeem?item=latte 這類 API，攻擊者只要讓你點一個連結，或在頁面裡寫 location.href = …，就是頂層 GET 導覽，Lax 照帶。有些框架支援「方法覆寫」：GET 請求帶一個參數（例如 GET …?_method=POST），伺服器就當成 POST 處理。開著它，效果一樣。
  2. 同站的子網域：SameSite 只看 site，marketing.coffee.example 跟 api.coffee.example 同站。這個子網域一旦被攻擊者掌控，它發出的請求連 Strict cookie 都會帶。常見的掌控方式有兩種。一種是外包的活動頁有 XSS 漏洞：攻擊者的程式碼跑進了那個網頁（第 7 課）。另一種叫子網域接管（subdomain takeover）：某個子網域的 DNS 還指向已經刪掉的雲端資源，別人把那個資源申請下來，就接管了這個子網域。
  3. 沒寫 SameSite 時，各家瀏覽器不一樣：只有 Chromium（Chrome 80+、Edge 86+）把沒寫的當成 Lax，Firefox 預設沒開，Safari 沒有這個預設，當成 None 處理。第 4 課說過：一定要明寫。
  4. Chrome 的 2 分鐘例外：Lax 是「預設套用」（cookie 沒寫 SameSite）時，瀏覽器用比較寬鬆的版本：cookie 設定後 2 分鐘內，跨站的頂層 POST 也會帶。這是為了不弄壞舊的單一登入流程。明寫 SameSite=Lax 就沒有這個例外。規格出處見課末「補充與查表」。

四個洞有同一個根源：SameSite 是瀏覽器端的規則。伺服器只能希望使用者的瀏覽器照做、每個 cookie 的設定都沒寫錯、所有同站的子網域都可信。所以要疊好幾層各自獨立的防護，一層失守還有下一層，這種做法叫縱深防禦（defense in depth）。OWASP CSRF Prevention Cheat Sheet 的結論也是：SameSite 是縱深防禦，不是唯一防線。咖啡店的 session cookie 明寫 SameSite=Lax（或 Strict），伺服器端還要自己檢查。另外，Safari、Firefox 對第三方 cookie 的限制也不能當成 CSRF 防護，原因見課末。

💡 實務上：有人要把 cookie 改成 SameSite=None 時，先問為什麼
最常見的理由是「要嵌進別人的網站」：例如咖啡店的訂位小工具用 iframe 放在合作商場的頁面上，iframe 裡要維持登入，Lax 就不帶了；而且就算改成 None，Safari、Firefox 會封鎖第三方 cookie（見課末），這種登入本來就不可靠。改成 None 之後，evil.example 的表單、fetch 都會帶這個 cookie，開頭的攻擊又能成立，伺服器端的 CSRF 檢查就從「多一層保險」變成唯一防線。資深工程師會先問能不能不用 cookie（例如小工具改用短效 token），真的要改，就只讓那個用途用一個獨立的 cookie，主站的 session cookie 維持 Lax。上線前在 DevTools 的 Application → Cookies 確認每個 cookie 的 SameSite、Secure 都是明寫的。

伺服器端要檢查什麼？四個洞的共通點是：伺服器看到 cookie 就照做，不知道請求是從哪個網站發起的。下一節就讓伺服器自己看出來。

伺服器怎麼知道請求是從哪個網站發起的？

上一節的洞，都出在第二個條件：伺服器只靠 cookie 判斷身分。如果伺服器能自己看出請求從哪個網站來，就能直接拒絕 evil.example 和不可信的子網域，不用指望 cookie 的設定。問題是：請求裡有什麼東西是攻擊者偽造不了的？

大部分的請求標頭，網頁的 JavaScript 都能用 fetch 自己設定，攻擊者的頁面也能，拿來判斷來源沒有意義。但有一群標頭不一樣：瀏覽器規定網頁的 JavaScript 不能設定或修改它們，只有瀏覽器自己會填，這群標頭叫禁止的請求標頭（forbidden request header）。名稱以 Sec- 開頭的標頭就屬於這一類。攻擊者的頁面改不了它們，伺服器才能相信它們的內容。

現代瀏覽器會在每個請求加上一組這樣的標頭，說明這個請求的來歷，叫 Fetch Metadata。防 CSRF 只需要其中的 Sec-Fetch-Site：發起請求的頁面跟目標網址是什麼關係。它有四個值：

  • same-origin：同源，例如 api.coffee.example 自己的頁面。
  • same-site：同站不同源，例如 shop.coffee.example 或 marketing.coffee.example 的頁面呼叫 api.coffee.example。
  • cross-site：跨站，例如 evil.example。
  • none：不是由網頁發起，而是使用者自己在網址列打網址、開書籤。

所以 evil.example 不管用表單還是 fetch，送到咖啡店 API 的請求都帶著 Sec-Fetch-Site: cross-site，它改不掉。curl 當然可以隨便填這個標頭，但 curl 沒有受害者的 cookie，發出的請求用的是攻擊者自己的身分，不是 CSRF。另外兩個 Fetch Metadata 標頭（Sec-Fetch-Mode、Sec-Fetch-Dest）這課用不到，列在課末查表。

另一個訊號是 Origin 標頭：瀏覽器在跨來源請求與 POST 上註明請求來自哪個來源，例如 Origin: https://evil.example。它也是禁止的請求標頭。有一個值要特別小心：沙箱 iframe、file: 頁面、某些跳轉後的請求會送 Origin: null。null 不是「同源」，而是「來源不明」，要當成不可信。

伺服器端的規則就是把這兩個訊號組起來。Go 1.25 的標準函式庫內建了一個這樣的檢查，叫 net/http.CrossOriginProtection，這課照它的規則走。一共四條，由上往下判斷：

  1. GET、HEAD、OPTIONS 一律放行：安全方法依語意不改資料，不需要防。前提是你的 GET 真的不改狀態；這條規則把「GET 不能改狀態」從建議變成安全要求，上一節的第一個洞在這裡一樣存在。
  2. 有 Sec-Fetch-Site：same-origin 或 none 放行，其他值拒絕。same-site 也拒絕：子網域不一定可信（外包活動頁、被接管的子網域），這正好補上 SameSite 的第二個洞。
  3. 沒有 Sec-Fetch-Site 時退回比對 Origin：Origin 的 host 等於請求的 Host 標頭才放行，null 或不相等就拒絕。
  4. 兩個都沒有就放行：瀏覽器送 POST 一定帶 Origin，兩個都沒有代表不是瀏覽器，例如手機 App、curl。它們不會自動帶受害者的 cookie，沒有 CSRF 的問題；這裡拒絕的話，手機 App 會全部壞掉。

回到咖啡店。前台在 https://shop.coffee.example，API 在 https://api.coffee.example：同站但不同源，前台呼叫 API 帶的是 Sec-Fetch-Site: same-site，照第 2 條會被拒絕。做法是把前台的來源加進信任清單（Go 的 AddTrustedOrigin，比對完整的 Origin 字串），只放行這一個子網域，marketing 子網域照樣擋下。信任清單在第 2、3 條都會查，Origin 完全等於清單裡的某一個就放行。練習 2 會實作這套規則；Go 原始碼裡的邊界情況（什麼時候沒有 Sec-Fetch-Site、比對 Origin 的盲點）整理在課末。

💡 實務上：加上檢查後前台突然全部 403，先看 Network 面板
打開 DevTools 的 Network 面板，看被擋的請求的 Request Headers：Sec-Fetch-Site 是什麼、Origin 是什麼，再對照伺服器的信任清單。常見原因是新增了一個前台網域（例如 https://www.coffee.example）卻忘了加進清單，或清單寫了結尾的 /、寫錯 port。信任清單要逐字比對完整的 Origin，加網域的人要知道有這份清單，新前台上線的檢查清單裡就該有這一項。

現在開頭的表單會被擋兩次：瀏覽器不帶 Lax cookie，就算帶了，伺服器也看到 cross-site 而拒絕。不過這兩層都靠瀏覽器提供的資訊。第三個條件還沒動過：請求裡的參數攻擊者全都知道。下一節從這裡下手。

能不能在請求裡放一個攻擊者拿不到的值？CSRF token

前兩節打破的是第一、第二個條件。第三個條件是：開頭的請求裡，訂單編號、取消原因這些參數攻擊者全都知道。如果每個會改狀態的請求都必須附上一個攻擊者拿不到的值，攻擊者的表單就湊不出合法的請求。這個值叫 CSRF token。伺服器渲染的表單（例如店長後台用傳統表單）、要支援不送 Fetch Metadata 的環境時，常用這個做法。

最傳統的版本叫同步器 token（synchronizer token），運作分三步：登入時產生一個 32 bytes 的安全亂數，存在 session 裡；伺服器產生頁面時，把它放在表單的隱藏欄位，或讓前端放進 X-CSRF-Token 標頭；伺服器收到請求時，拿請求裡的值跟 session 裡的比對，不一樣就拒絕。

攻擊者為什麼拿不到這個值？token 寫在咖啡店的頁面裡，要拿到它就得讀咖啡店頁面的內容。evil.example 可以叫瀏覽器去載入咖啡店的頁面，卻讀不到回應，這是第 5 課的同源政策。「能送不能讀」讓 CSRF 有機可乘，在這裡反過來幫了防守方。

同步器 token 的缺點是每個 session 要在伺服器多存一個值。session 存在 Redis 這類共用儲存時，每次發 token、驗 token 都要讀寫它；有些框架的 session 結構也不方便加欄位。能不能不存？

不存在伺服器：天真的 double submit 為什麼會被繞過

常見的偷懶版本叫「天真的 double submit」：產生一個亂數，同時放進 cookie 和表單欄位，伺服器不存任何東西，只檢查兩個值一樣。它的假設是「攻擊者讀不到 cookie，就不知道表單該填什麼」。

這個假設不成立，因為攻擊者不需要讀 cookie，只要能寫。把攻擊者選的值寫進受害者瀏覽器的 cookie，叫 cookie 注入（cookie tossing），常見的途徑有兩種：子網域可以寫 Domain=coffee.example 的 cookie，這種 cookie 會跟著送往所有 coffee.example 子網域的請求；網站還有 http（沒加密）的頁面時，網路上的攻擊者（例如同一個公共 Wi-Fi 上的人，這叫中間人攻擊）可以竄改這個頁面的回應，替它寫入同名 cookie。攻擊者寫進一個自己知道的值，再在表單裡填同一個值。下面模擬被接管的 marketing 子網域這麼做，執行後比較兩行的結果：

用 HMAC 把 token 綁到 session：簽章雙重提交

要回答「是不是伺服器為這個 session 發的」，又不想在伺服器存東西，可以用第 2 課的 HMAC：伺服器用只有自己知道的 secret，對「session ID 加上一個亂數」算出標籤，亂數和標籤一起當作 token。驗證時用同一個 secret 重算一次，對得上，就代表這個 token 是伺服器為這個 session 發的。這個做法叫簽章雙重提交 cookie（signed double-submit cookie），格式如下：

random = base64url(32 bytes 安全亂數)
token  = random + '.' + base64url(HMAC-SHA256(secret, `${sessionId.length}!${sessionId}!${random}`))

回到 cookie 注入。攻擊者寫進去的 token 必須是「為受害者的 session ID 算出的 HMAC」，沒有 secret 就算不出來；拿自己帳號的合法 token 也沒用，因為 session ID 不同。綁了 session 之後，攻擊者剩下的路是連 session cookie 一起蓋掉，換成自己帳號的 session，再配上自己帳號的合法 token。所以 session cookie 要用第 4 課的 __Host- 前綴（不能設 Domain），子網域就蓋不掉它。OWASP 建議 CSRF cookie 也用 __Host- 前綴，但綁 session 才是根本的解法。

token 放在哪裡、從哪裡讀，要分清楚。token 本身可以放在一個一般的 cookie（不設 HttpOnly，讓前端讀出來）或直接寫進頁面；前端送請求時，把它放進 X-CSRF-Token 標頭或表單欄位。伺服器檢查的是標頭或欄位裡的 token，絕對不能從 cookie 讀 token 再跟 cookie 比：cookie 是自動帶的，攻擊者的請求也會帶，等於沒檢查。

格式裡還有一個細節：HMAC 的訊息為什麼寫成 ${sessionId.length}!${sessionId}!${random}，不直接把 sessionId 和 random 接起來？因為直接接起來，不同的組合可能得到同一個字串。執行後比較每一行的 true／false：

簽章簽的是位元組，兩個訊息位元組一樣，簽章就一樣。'ab' + 'c' 和 'a' + 'bc' 都是 abc，簽章相同，伺服器就分不出這個 token 是發給哪個 session 的。訊息由多個欄位組成時，要讓每種組合都只對應一個字串：先寫長度再寫內容，或用固定長度的欄位。只加分隔符號不夠，因為欄位本身也可能含有分隔符號。這個原則在 JWT（第 8 課用 . 分隔 base64url，base64url 本身不含 .）、webhook 簽章（第 17 課）都會再出現。

最後是驗證。用 crypto.subtle.verify，它是常數時間比較（第 2 課）；不要 sign 一次再用 === 比。token 格式不對（沒有 .、多了 .、不是 base64url）一律回 false，不要讓例外變成 500。練習 3 會把簽發和驗證都寫出來。

💡 實務上：多半是框架幫你做，你要做的是「不要關掉它」
Django、Rails、Laravel 這類伺服器渲染的框架都內建 CSRF 檢查，在表單樣板加一個標籤（Django 的 {% csrf_token %}、Laravel 的 @csrf）或用 Rails 的表單 helper，就會放好隱藏欄位，平常你幾乎感覺不到它。真正會出事的時刻，是有人為了讓某個 403 消失，把整個中介軟體關掉，或把一整組路由加進排除清單，取消訂單的 API 就又能被開頭那個表單打到。code review 看到「停用 CSRF」的改動，要問清楚是哪個路由、為什麼、改用什麼方式驗證請求。自己用 HMAC 做 token，通常只發生在框架沒提供、或前後端分離要自己接的情況，這時本節的長度與分隔、常數時間比較就是檢查清單。

簽章雙重提交適合伺服器渲染的表單，也適合前後端分離時自己接。但咖啡店的前台是 Vue SPA，只打 JSON API，每個請求都要自己帶 token。這種架構有沒有更省事的做法？

Vue 前台只打 JSON API，有更省事的防法嗎？

有。咖啡店的前台是 Vue SPA，API 只收 JSON，這種架構可以要求每個會改狀態的請求帶 Content-Type: application/json 或一個自訂標頭（例如 X-Requested-With: coffee-shop）。不用 token，也不用在伺服器存東西。

為什麼這樣就擋得住？回想開頭的攻擊為什麼能送出：表單是簡單請求，不用預檢。但表單能做的事有限，它只能送三種 Content-Type（application/x-www-form-urlencoded、multipart/form-data、text/plain），而且不能加自訂標頭。攻擊者想送出帶 application/json 或自訂標頭的請求，只能改用 fetch；跨來源的 fetch 一旦帶了這些，就不是簡單請求，瀏覽器會先送預檢（第 5 課）。你的 CORS 設定沒有允許 evil.example，預檢失敗，真正的請求根本不會送出。結果是：表單送不出合格的請求，fetch 送得出合格的請求卻過不了預檢。它打破的是第三個條件的變形：合格的請求必須帶一個攻擊者的表單做不出來、fetch 又會被預檢擋下的東西（JSON 格式或自訂標頭）。

這個防法有三個前提，少一個就破：

  • CORS 沒有亂開：反射任意 Origin、允許 null、允許所有子網域（第 5 課的錯誤設定），等於替攻擊者通過預檢。
  • 伺服器真的拒絕其他格式：如果為了方便，body parser 也接受 text/plain 並當成 JSON 解析，攻擊者就能用 <form enctype="text/plain"> 湊出一個合法的 JSON body，不用預檢就送到。Content-Type 不是 application/json 的請求，回 415（Unsupported Media Type，不支援的格式）。
  • 允許清單裡的來源都可信：CORS 允許的來源本來就能讀寫你的 API。

這個做法也有標準文件背書。BFF（Backend for Frontend）是一種架構：前端只拿 session cookie，OAuth 登入拿到的 access token 留在後端，第 11 課會講。RFC 10017（OAuth 2.0 for Browser-Based Applications，BCP 212，2026 年 8 月）對 BFF 架構的建議就是用自訂標頭加 CORS 防 CSRF，並提醒子網域被接管時 SameSite 擋不住。

到這裡，咖啡店取消訂單的 API 有三層：cookie 明寫 SameSite、伺服器做 Fetch Metadata 檢查、API 只收 JSON。這是實務上最穩的組合，三層各擋不同的洞：SameSite 讓瀏覽器不帶 cookie，Fetch Metadata 讓伺服器拒絕別的網站，只收 JSON 讓表單送不出合格的請求。防線畫好了，剩下兩個問題：哪些情況其實不用防，哪些地方最容易漏掉？

哪些情況不用擔心，哪些地方最容易漏？

先看不用擔心的情況。token 放在 Authorization 標頭時不受 CSRF 影響。這打破的是第一個條件：瀏覽器不會自動帶這個標頭，前端要自己寫 headers: { Authorization: `Bearer ${token}` }，惡意網站沒有 token 就送不出。代價是 token 必須放在 JavaScript 讀得到的地方（記憶體、localStorage），一旦有 XSS，攻擊者直接把 token 偷走，拿到別的地方用到過期。CSRF 換成了 XSS 的風險，這個取捨在第 7 課和第 11 課詳談。

反過來，用 cookie 登入時，下面這些地方容易被忽略，都要防：

  • 登入表單（登入 CSRF，login CSRF）：攻擊者讓受害者的瀏覽器用攻擊者的帳密登入。受害者以為在用自己的帳號，之後加的信用卡、填的地址、搜尋紀錄全進了攻擊者的帳號。登入前還沒有 session，所以 CSRF token 要綁在登入前的匿名 session 上，或靠 Fetch Metadata 檢查（它不需要 session）。
  • 登出：GET /logout 讓任何網站一個 <a> 就能登出你。登出用 POST，也受同樣的檢查。
  • OAuth 的 callback：第 12 課的 state 與 PKCE 就是在防 OAuth 流程裡的 CSRF。
💡 實務上：金流導回來的請求本來就是跨站的
有些金流（例如綠界的付款結果頁）在付款完成後，讓使用者的瀏覽器用表單 POST 把人帶回你的網站。這是跨站的頂層 POST，跟開頭的攻擊長得一樣：Lax cookie 不會帶，Fetch Metadata 檢查會回 403，常見症狀是「付款成功了，回到網站卻顯示沒登入或錯誤頁」。正確的做法是讓這個端點不依賴 session，也不做任何改狀態的事，只用 303 轉到你站內的 GET 結果頁（頂層 GET 導覽，Lax cookie 會帶）；訂單狀態由金流的伺服器對伺服器通知更新，而且要驗金流的簽章。把這種端點從 CSRF 檢查排除時，要寫在文件裡，並確認它真的不靠 cookie 判斷身分。
XSS 會打敗所有 CSRF 防護。上面這些防護都有一個共同前提：攻擊者的程式碼跑在別的網站。同源的惡意腳本送出的請求是 Sec-Fetch-Site: same-origin，Origin 正確，可以讀頁面上的 CSRF token，也可以帶自訂標頭。程式碼一旦跑進你的網站，這個前提就沒了。所以下一課是 XSS。

Chrome 2 分鐘例外的出處

cookie 規格的草案（rfc6265bis-22，還沒成為正式 RFC）叫它 Lax-allowing-unsafe，MDN 說明只有在 Lax 是預設值時才有；明寫 SameSite=Lax 就沒有這個例外。

第三方 cookie 的封鎖不是 CSRF 防護

Safari、Firefox 另外會封鎖或分隔第三方 cookie（嵌在別人網站裡的 iframe、圖片拿不到你的 cookie），Chrome 則維持讓使用者自己選（Google 2025 年 10 月宣布）。這是隱私機制，規則跟各家的設定、使用者的選擇有關，而且頂層導覽通常不在封鎖範圍。不能把它當成 CSRF 防護。

Go 1.25 CrossOriginProtection 的邊界情況

以下照 release-branch.go1.25 的 src/net/http/csrf.go 原始碼整理，要自己實作或審查這類 middleware 時再看：

  • 什麼時候沒有 Sec-Fetch-Site：瀏覽器只在送往 potentially trustworthy 的網址（https、localhost）時才加 Fetch Metadata，另外很舊的瀏覽器也不送。Go 原始碼的註解說所有主流瀏覽器自 2023 年起都支援 Sec-Fetch-Site。
  • 比對 Origin 的盲點：Host 標頭不含 scheme，所以這一步分不出 http:// 頁面打 https:// API 的情況；Go 選擇放行，建議用 HSTS 補上。HSTS 是一個回應標頭，要求瀏覽器之後只用 https 連線到這個網站。
  • 信任清單在兩條路上都會查：Sec-Fetch-Site 不是 same-origin／none，或 Origin 跟 Host 不同時，Origin 完全等於清單裡的某一個就放行（咖啡店同站的前台就是靠這個）。

練習

練習 1：寫 cookieWouldBeSent(cookie, req, browser, publicSuffixes)，判斷瀏覽器送出請求時帶不帶這個 cookie。時間單位都是毫秒。依序檢查：

  1. cookie.secure 是 true，目標網址不是 https: → 不帶（真實瀏覽器對 localhost 另有例外，這題不處理）。
  2. sameSite 是 'None' 卻沒有 secure → 瀏覽器根本沒存，不帶。
  3. 頁面與目標同站（用已經寫好的 sameSite()，有比 scheme）→ 帶。
  4. 跨站：Strict 不帶；None 帶；Lax 只在頂層導覽（kind 是 'navigation'）而且方法是 GET 或 HEAD 時帶。
  5. 沒寫 SameSite（sameSite 是 undefined）：browser.laxByDefault 是 true 就照 Lax，另外頂層導覽在 cookie 設定後 2 分鐘內（now - createdAt <= 120000）任何方法都帶；laxByDefault 是 false 就照 None（這時不要求 Secure）。

練習 2：寫 crossOriginCheck(req, trustedOrigins)，照 Go 1.25 CrossOriginProtection 的規則判斷要不要放行。headers 的 key 一律小寫，沒有的標頭是 undefined：

  1. 方法是 GET、HEAD、OPTIONS → 放行。
  2. 有 sec-fetch-site：值是 same-origin 或 none → 放行；其他值（包含 same-site）→ 除非 origin 完全等於 trustedOrigins 的某一個，否則回 cross-site。
  3. 沒有 sec-fetch-site 也沒有 origin → 放行（不是瀏覽器）。
  4. 只有 origin：用 new URL() 解析，host（含 port）等於 req.host → 放行；解析失敗（例如 null）或不相等 → 除非 origin 在信任清單，否則回 origin-mismatch。

練習 3：做出簽章雙重提交的 CSRF token。

  • issueCsrfToken(sessionId, secret)：random 是 32 bytes 安全亂數的 base64url；回傳 random + '.' + base64url(HMAC-SHA256(secret, `${sessionId.length}!${sessionId}!${random}`))。
  • verifyCsrfToken(sessionId, token, secret)：用 crypto.subtle.verify 檢查。格式不對（不是剛好兩段、簽章不是 base64url）回 false，不能丟例外。

練習 4：咖啡店 API 全部改成用 Authorization: Bearer … 標頭帶 token，不再用 cookie。還需要 CSRF 防護嗎？

✓ CSRF 的第一個條件是「瀏覽器自動帶憑證」，Authorization 標頭要前端自己加，瀏覽器不會自動帶（a 錯）；表單也不能加自訂標頭，跨來源的 fetch 加了會先預檢（d 錯）。但風險沒有消失，只是換了一種：token 在 JavaScript 手上，XSS 可以把它讀走、拿到攻擊者的機器上一直用到過期（b 錯）。HttpOnly cookie 被 XSS 利用時，攻擊者至少要在受害者的瀏覽器裡操作。

練習 5：session cookie 設了 SameSite=Lax，取消訂單的 API 是 GET /orders/42/cancel。evil.example 能讓已登入的使用者取消訂單嗎？

✓ Lax 只擋跨站的「非安全方法」和「非頂層導覽」，頂層 GET 導覽照帶 cookie（a 錯）。2 分鐘例外是讓 POST 也能過，而且只適用沒寫 SameSite 的 cookie，GET 本來就會過（c 錯）。讀不到回應無關緊要：取消已經在伺服器上執行了（d 錯）。修法是把會改狀態的操作改成 POST，並在伺服器做 Fetch Metadata 檢查。

練習 6：同事實作了「cookie 裡的 csrf 值等於表單欄位 _csrf 就放行」，理由是「攻擊者讀不到我們的 cookie」。為什麼不夠？

✓ 天真的 double submit 只檢查「兩個值一樣」，不檢查「這個值是不是伺服器為這個 session 發的」。cookie 注入讓攻擊者自己決定 cookie 的值，兩邊都填同一個就通過，再長的亂數也沒用（c 錯）。同源政策讓別的網站讀不到你的 cookie（b 錯）。常數時間比較要做，但不是這裡的漏洞（d 錯）。修法是練習 3：用 HMAC 把 token 綁到 session。

常見錯誤

  • 用 GET 改狀態（/cancel、/logout、/redeem）：SameSite=Lax 和 Fetch Metadata 檢查都會放行 GET。會改狀態的操作一律用 POST、PUT、PATCH、DELETE，也不要開方法覆寫。
  • 只靠 SameSite，甚至不寫 SameSite：子網域、會改狀態的 GET、各家瀏覽器預設不同、Chrome 的 2 分鐘例外，都是洞。明寫 SameSite，伺服器端另外檢查。
  • 天真的 double submit：沒有綁 session、沒有簽章，cookie 注入就能繞過。用 HMAC 把 token 綁到 session ID，訊息要寫長度或分隔。
  • 伺服器從 cookie 讀 CSRF token 再跟 cookie 比：cookie 會自動帶，攻擊者的請求也有，等於沒檢查。token 要從標頭或表單欄位讀。
  • 只看 Referer，或把 Origin: null 當同源：Referer 可能被 Referrer-Policy 拿掉，也不是為這個用途設計的；null 代表來源不明。用 Sec-Fetch-Site，退回比對 Origin。
  • 為了方便，text/plain 或表單格式的 body 也當成 JSON 解析：表單不用預檢就能送出這些格式，「只收 JSON」的防護就沒了。不是 application/json 回 415。
  • 以為登入頁、登出不需要 CSRF 防護：登入 CSRF 會讓受害者用攻擊者的帳號，之後的個資、付款資料都進了攻擊者的帳號。登入、登出都要檢查。
  • 信任清單用 startsWith 或 endsWith 比對：https://shop.coffee.example.evil.example 會通過。完整的 Origin 字串完全相等才放行。

小結

  • CSRF 要三個條件：瀏覽器自動帶 cookie、伺服器只靠 cookie 判斷身分、請求裡沒有攻擊者猜不到的東西。攻擊者讀不到任何回應，但會改狀態的請求一送到就已經生效。每種防法打破其中一個條件。
  • SameSite 打破第一個條件：Strict 跨站都不帶；Lax 跨站只有頂層導覽的 GET／HEAD 帶，明寫 Lax 就擋得住開頭的跨站表單；None 一定要 Secure。Lax 擋不住會改狀態的 GET、同站子網域、沒寫 SameSite 時的瀏覽器差異與 2 分鐘例外。它是縱深防禦，不是唯一防線。
  • Fetch Metadata 打破第二個條件，伺服器看瀏覽器自己填、網頁改不掉的標頭（Go 1.25 的規則）：安全方法放行；Sec-Fetch-Site 是 same-origin 或 none 放行，其他（含 same-site）拒絕；沒有就比 Origin 與 Host；兩個都沒有是非瀏覽器，放行。同站的前台用信任清單放行。
  • CSRF token 打破第三個條件，而且要綁 session：random.HMAC(secret, 長度!sessionId!random)，用 crypto.subtle.verify 驗證，從標頭或表單欄位讀。只比 cookie 和欄位一樣不一樣，會被 cookie 注入繞過。
  • JSON API 可以靠「只收 application/json 或自訂標頭」加上正確的 CORS，打破的是第三個條件的變形：合格的請求必須帶表單做不出來、fetch 又過不了預檢的東西。前提是伺服器拒絕其他格式。咖啡店的組合：cookie 明寫 SameSite、伺服器做 Fetch Metadata 檢查、API 只收 JSON。
  • Authorization 標頭不受 CSRF 影響，但換成 XSS 偷 token 的風險；登入、登出也要防；XSS 會打敗所有 CSRF 防護。
