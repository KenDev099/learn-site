階段 1：地基：身分、信任與密碼學工具 · 第 3 課

密碼怎麼存：salt、慢雜湊與密碼政策

咖啡店的會員系統要讓顧客用 email 和密碼登入。你要在 customers 表加一個欄位存密碼，並寫好註冊與登入兩支 API。難的地方在這裡：伺服器必須能確認「這次輸入的密碼對不對」，卻不應該知道密碼本身，因為這張表總有一天會被整張拿走。

這課從頭到尾只做一件事：設計 customers.password_hash 這個欄位，從註冊時怎麼存、登入時怎麼驗，到註冊表單該擋哪些密碼。每一步都用同一個問題檢查：如果明天這張表外洩，攻擊者拿著它能做什麼？範例一路沿用王小明的密碼 latte2026。

這課的路線：
  1. 資料庫被整張拿走那天：明文的後果、為什麼不用加密而用雜湊，以及只存雜湊、登入時重算比對這個最小答案。
  2. salt 與慢雜湊：同一個密碼為什麼要存成不同結果；加了 salt 之後，為什麼還要讓每一次計算故意變慢。
  3. 選演算法、存成一個字串、參數升級：Argon2id、PBKDF2 該設多少，參數怎麼跟雜湊存在同一個欄位，參數調高後舊帳號怎麼跟上。
  4. 註冊時擋什麼（NIST SP 800-63B-4）：為什麼不再要求「大寫＋數字＋符號」和定期改密碼，以及怎麼查密碼外洩過沒有，又不把密碼送給第三方。
這課會用到：
  • 第 2 課的雜湊與安全亂數：SHA-256 把輸入變成固定長度、不能還原的指紋；crypto.getRandomValues 產生攻擊者猜不到的位元組，再用 base64url 寫成字串。
  • 第 2 課的 HMAC 與常數時間比較：HMAC 用金鑰算出標籤；比對秘密不用 ===，改用 timingSafeEqual，比對時間才不會洩漏前幾個字元對不對。

資料庫被整張拿走那天，密碼欄位該長什麼樣子？

先看最直覺的寫法：密碼直接存明文（plaintext），也就是使用者打什麼就存什麼。

email                 password
wang@example.com      latte2026
chen@example.com      MeiHua!0812

資料庫外洩比想像中常見。最常見的兩條路：資料庫備份檔被誤放在公開的雲端儲存空間；或 API 有 SQL injection 漏洞，攻擊者在輸入欄位塞進一段 SQL，讓伺服器把整張表查出來（PostgreSQL 課第 25 課講過怎麼防）。不管哪一條，結果都是整張 customers 表被傾印（dump）成檔案，落到攻擊者手上。

如果密碼是明文，第一層後果很直接：攻擊者拿王小明的 email 和 latte2026 就能登入咖啡店，看他的訂單、用他的點數。第二層後果更嚴重，而且不在你的網站上。很多人在不同網站用同一組密碼，攻擊者會把這份 email＋密碼清單拿去購物網站、銀行、信箱逐一試登入，這種攻擊叫撞庫（credential stuffing）。王小明如果在網路銀行也用 latte2026，咖啡店的外洩就變成他銀行帳戶的外洩。

所以設計目標要訂成：就算整個資料庫被拿走，攻擊者也很難從中得到密碼。注意這個目標假設外洩一定會發生。防外洩是另一件事（權限、網路隔離、修漏洞），密碼欄位的設計要在那些防線都失守之後，還能保護使用者。

第一個想法通常是加密：把密碼用金鑰加密再存，要用時解密。問題是加密的設計目的就是「能解開」。伺服器要能解密，就得隨時拿得到金鑰，而金鑰通常放在同一台機器、同一份設定檔或同一份備份裡。攻擊者拿走資料庫時，常常連金鑰一起拿走，加密就形同虛設。

更根本的是，伺服器其實不需要知道密碼是什麼。登入時它只要回答一個是非題：「這次輸入的，跟當初註冊時的一樣嗎？」第 2 課的雜湊剛好能回答這個問題：同樣的輸入一定得到同樣的雜湊，而雜湊不能還原成輸入。所以做法是：

  • 註冊時，存 hash(密碼)，不存密碼本身。
  • 登入時，算 hash(輸入)，跟存的值比對；一樣就是密碼正確。

這就是這課的最小答案：只存不能還原的雜湊，登入時重算比對。資料庫外洩時，攻擊者拿到的只是一串雜湊，沒有金鑰可以偷，也沒有東西可以「解開」。

但第 2 課也留下一個警告：「不能反推」不等於「猜不到」。攻擊者不需要從雜湊反推密碼，他可以拿常見密碼一個個算雜湊，跟資料庫裡的值比對，算出一樣的就猜中了。如果直接用 SHA-256，這個猜的過程有兩個漏洞可以鑽，下一節先處理第一個。

王小明和陳美華用同一個密碼，雜湊為什麼要不一樣？

上一節說攻擊者會用猜的。第一個漏洞是：用同一個雜湊函式時，相同的密碼一定得到相同的雜湊。這讓攻擊者可以先算好再來查。

做法是這樣：攻擊者還沒拿到任何資料庫之前，就先把幾億個常見密碼的 SHA-256 全部算好，存成一張「雜湊 → 密碼」的大型對照表。這種預先算好的表叫彩虹表（rainbow table）。等某天拿到咖啡店的資料庫，他不用再算任何東西，直接拿每一列的雜湊去表裡查，查到就知道密碼。這張表可以重複用在每一個用 SHA-256 存密碼的網站上，算一次、用很多年。

就算不查表，相同雜湊本身也會洩漏資訊。王小明和陳美華如果都用 latte2026，資料庫裡兩列的雜湊會一模一樣。攻擊者一眼就知道他們密碼相同，猜中一個就是兩個；某個雜湊出現上千次，也幾乎可以確定它是 123456 這種熱門密碼。

解法是 salt（鹽）：註冊時替每個使用者產生一個隨機值，跟密碼一起雜湊，再把這個 salt 存在雜湊旁邊。登入時從資料庫讀出這個人的 salt，跟輸入一起重算，就能比對。因為每個人的 salt 不同，同一個密碼會得到完全不同的雜湊。執行下面這格，比較兩組輸出：上面兩行沒加 salt，雜湊一樣；下面兩行各有隨機 salt，雜湊不一樣（每次執行也都不一樣）。

salt 為什麼能讓彩虹表失效？因為彩虹表的前提是「提前算好」。攻擊者事先不知道王小明的 salt 是什麼，就沒辦法提前算 hash(salt + latte2026)；要等拿到資料庫、看到 salt 之後才能開始算。而且王小明和陳美華的 salt 不同，替王小明算的結果對陳美華完全沒用，每個帳號都要分開從頭猜。

理解了這個作用，salt 的三條規則就很自然：

  • 不用保密。salt 的作用是讓「預先算好」失效、讓每個人要分開猜，靠的是每人不同、事先猜不到，不是靠藏起來。所以它直接跟雜湊存在同一列。
  • 每人一個，每次重新雜湊都換新的。如果全站共用一個 salt，攻擊者拿到資料庫後只要針對那一個 salt 做一張表，所有帳號又能一起查，回到原點。
  • 用 CSPRNG 產生，16 bytes 以上。CSPRNG 就是第 2 課的 crypto.getRandomValues 這類密碼學安全的亂數產生器。NIST 的下限是 32 bits，常見做法是 16 bytes。不要用 email 或使用者 ID 當 salt：它們可以預測，同一個 email 也會出現在其他網站，攻擊者可以預先為熱門 email 算好表，salt 就失去作用。

salt 之外還有一種叫 pepper 的額外保護，跟 salt 剛好相反，是要保密的；它不是必要的一層，細節見課末「補充與查表」。

加了 salt 之後，攻擊者不能查表了，只能拿到資料庫後，對每個帳號一個一個猜。但這裡還剩第二個漏洞：每猜一次，攻擊者只要算一次 SHA-256。如果一次 SHA-256 非常便宜，「一個一個猜」也不會花多少時間。下一節來量量看到底有多便宜。

有了 salt 還不夠：怎麼讓每一次猜測都變貴？

上一節留下的問題是：攻擊者雖然要逐人猜，但每猜一次的成本只有一次 SHA-256。SHA-256 是為了檢查檔案、簽章這類用途設計的，這些用途要求它越快越好。對存密碼來說，這個優點正好幫了攻擊者。

下面這格量兩件事：第 1 段在 0.3 秒內盡量多算 SHA-256，換算成每秒幾次；第 2 段用 PBKDF2 這種「故意算很慢」的做法算一個密碼，看要花多少毫秒。執行後比較兩行輸出的「每秒約幾次」。

兩行的差距是幾萬倍。而且這裡的 SHA-256 已經被拖慢了：每一次都要 await 一個 Promise，又只在一個 Worker 裡跑。攻擊者不會這樣算，他用一張高階 GPU 跑原生程式，每秒可以算上百億次 SHA-256。照這個速度，八位數的純數字密碼只有一億種組合，一秒內就全部試完；字典裡幾億個常見密碼，每個帳號也不到一秒。salt 讓他必須逐人猜，但逐人猜的每一個人都很快就猜完了。

第 2 段的 PBKDF2 展示了解法。它把 HMAC（第 2 課教過，帶金鑰的雜湊）連續重複算 600,000 次，前一次的結果當下一次的輸入，再把每一輪的結果 XOR 起來，得到要存的雜湊。每一次 HMAC 內部要算兩次 SHA-256，所以 600,000 次 HMAC 大約等於 120 萬次 SHA-256 運算。攻擊者想驗證一個猜測，也必須完整跑完這 600,000 次，沒有捷徑。

這筆帳對兩邊很不公平，而這正是重點。對正常使用者，登入時多等 70 ms 左右，完全感覺不到，而且他一次只登入一次。對攻擊者，他要試的是幾十億次，每一次猜測都貴了大約一百萬倍；原本不到一秒就試完的一億種組合，現在要好幾個小時；字典加上變形規則、動輒幾十億個猜測的攻擊，就要以天、甚至以月計。而這還只是一個帳號。這就是慢雜湊的想法：不是讓雜湊不能反推（它本來就不能），而是讓每一次猜測都變貴。

到這裡，密碼欄位的設計原則齊了：每人一個隨機 salt，加上故意很慢的雜湊。但「慢」要怎麼做、要多慢？PBKDF2 只是其中一種，下一節看有哪些演算法可以選、參數該設多少。

該選哪個演算法、參數設多少？

上一節的 PBKDF2 屬於一類專門用來存密碼的演算法，統稱密碼雜湊函式（password hashing function）。它們的共同點是故意算很慢，或故意吃很多記憶體。控制「有多慢」的那個參數叫工作因子（work factor），有些函式庫叫 cost，例如 PBKDF2 的工作因子就是重複次數 iterations。

你可能也會在文件裡看到 PBKDF2、scrypt、Argon2 被叫做金鑰衍生函式（key derivation function，KDF）。這是因為同一套計算也能把密碼變成加密用的金鑰；在這課的用途裡，把它當成密碼雜湊函式就好。

常見的四種，差別在於它們拿什麼讓攻擊者變貴：

  • PBKDF2：把 HMAC 重複算很多次，只吃 CPU。缺點是 GPU 有幾千個核心，可以同時算幾千個猜測，攻擊者的平行能力很強。
  • scrypt、Argon2id：每算一次都需要一大塊記憶體，這叫 memory-hard（記憶體密集）。GPU 核心雖然多，每個核心分到的記憶體卻只有一點點，沒辦法同時跑幾千個；攻擊者想平行，就得買大量記憶體，成本跟著上去。
  • bcrypt：1999 年的演算法，吃少量記憶體，現在仍可接受，但不是新系統的首選。它有一個 72 bytes 的長度限制，見課末。

參數該設多少，業界最常引用的是 OWASP Password Storage Cheat Sheet。下表是它的建議（2026-10-31 查），是最低值，查表用，不用背：

演算法建議參數（最低）備註
Argon2idm=19 MiB（19456 KiB）、t=2、p=1首選。m 是記憶體、t 是重複次數、p 是平行度；另有等效組合，見課末
scryptN=217（128 MiB）、r=8、p=1沒有 Argon2id 時用
bcryptcost ≥ 10只給舊系統。多數實作只吃前 72 bytes
PBKDF2-HMAC-SHA256600,000 次需要 FIPS-140（美國政府的密碼模組認證標準）時用
PBKDF2-HMAC-SHA512220,000 次舊文章常寫 210,000，已經更新

新系統選 Argon2id。這課的練習卻用 PBKDF2，原因只是環境限制：練習在瀏覽器裡跑，而瀏覽器的 Web Crypto 只提供 PBKDF2，沒有 Argon2、scrypt、bcrypt。原理完全一樣，換演算法只是換掉計算雜湊的那一步，salt、存法、驗證流程都不變。之後在 Node 裡會改用 Argon2id，版本細節見課末。

表上的數字是下限，不是答案。OWASP 自己也說沒有放諸四海皆準的值，要在你自己的伺服器上量。調參數時有三個力量互相拉扯：

  • 使用者體驗：驗證一次的時間控制在數百毫秒以內，OWASP 給的上限是一秒。
  • 伺服器成本：慢雜湊的 CPU 是你自己付的。估一下登入尖峰：每秒 50 個登入、每次 200 ms CPU，就要吃掉 10 顆 CPU 核心。
  • 被拿來攻擊：攻擊者不需要猜對密碼，只要一直送假的登入請求，每個請求都逼你的伺服器算一次慢雜湊，就能把 CPU 吃滿，讓正常顧客也登不進來。這叫阻斷服務攻擊（DoS）。參數越高，登入 API 越像 DoS 的放大器。所以登入 API 一定要搭配限流（rate limiting）：限制同一個來源在一段時間內最多能送幾次請求，超過就直接拒絕、不算雜湊。限流在第 16 課實作。
💡 實務上：你通常不會自己寫雜湊，而是檢查框架用了什麼
多數框架與認證套件都內建密碼雜湊（Django、Laravel、Rails、ASP.NET Identity、各語言的 argon2 套件），工作中直接呼叫它們的 hash／verify，不要自己拼演算法。你的工作是確認三件事：用的是哪個演算法、參數是不是還符合 OWASP 現在的建議、有沒有在正式環境的機器上量過登入要花多少 CPU。接手專案時，打開資料庫看一眼 password_hash 欄位的開頭（$argon2id$、$2b$、pbkdf2_sha256$），就知道它用什麼存。如果看到 32 個十六進位字元、沒有任何前綴，很可能是沒加鹽的 MD5，一種很舊的快速雜湊，這要當成資安問題回報，不是「之後再改」。

還有一個力量沒算進去：時間。硬體每年變快，今天的 600,000 次，幾年後對攻擊者就不夠貴了，參數得跟著調高。但只要一調，資料庫裡那些用舊參數算的雜湊怎麼辦？要回答這個問題，得先決定參數存在哪裡。

驗證時怎麼知道當初用了什麼參數？存成一個字串

上一節說參數會隨時間調高。這代表資料庫裡會同時存在用不同參數算出來的雜湊：三年前註冊的王小明是 600,000 次，明年註冊的新顧客可能是 800,000 次。登入時要重算雜湊比對，就一定要用當初雜湊時的參數，不然算出來的值不會一樣。所以參數必須跟雜湊存在一起，salt 也是。

業界慣例是把演算法、參數、salt、雜湊四樣東西串成一個字串，放在一個 text 欄位，例如 password_hash text NOT NULL。這課用類似 Django 的格式，用 $ 分隔：

pbkdf2_sha256$600000$<salt 的 base64url>$<雜湊的 base64url>

Argon2 的函式庫多半用一種叫 PHC 字串格式的寫法，概念一樣，只是參數更多：$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>。開頭寫清楚演算法，後面跟著這個演算法需要的參數。

為什麼不拆成 salt、iterations、hash 好幾個欄位，看起來比較「正規化」？因為每種演算法的參數都不同：PBKDF2 只有次數，Argon2id 有記憶體、次數、平行度三個。哪天從 PBKDF2 換成 Argon2id，拆開的欄位就得改 schema；存成一個字串，交給函式庫自己解讀，資料表完全不用動，新舊格式也能並存在同一個欄位。

有了這個格式，登入時的驗證流程是：

  1. 用 $ 切開，確認演算法認得、參數合法。看不懂的字串一律當作驗證失敗，不要丟例外，否則登入 API 會回 500。
  2. 用字串裡存的 iterations 和 salt，重算這次輸入的密碼。
  3. 用第 2 課的常數時間比較，跟存的雜湊比對。
  4. 如果密碼正確，但存的參數低於目前的政策，標記 needsRehash，表示這個雜湊該升級了。

第 2 步為什麼一定要讀存的參數？假設你偷懶，驗證時直接用「現在設定檔裡的」iterations。你把它從 600,000 調到 800,000 的那一刻，所有舊雜湊用 800,000 次重算都對不上，全部使用者同時登不進來。這是調參數時最常見的事故。

第 4 步的 needsRehash 只是一個標記，它還沒有真的升級任何東西。標記之後要怎麼把舊雜湊換成新參數？下一節處理。

參數調高之後，舊帳號的雜湊怎麼升級？

上一節的驗證流程會告訴你「王小明的雜湊用的是舊參數」。直覺的做法是寫一支批次程式，把所有舊雜湊用新參數重算一遍。但這做不到：重算雜湊需要明文密碼，而伺服器從頭到尾都沒有存明文，這正是整課的目的。

整個系統裡，唯一拿得到明文的時機，是使用者登入成功的那一刻：他剛剛送來密碼，你也剛剛驗證過它是對的。所以升級就在這時順便做：驗證通過、發現 needsRehash，就用新參數重新雜湊，UPDATE 回資料庫，然後照常發 session。這叫登入時重新雜湊（rehash on login）。使用者完全無感，只是這次登入多算了一次雜湊。

注意圖上不 ok 的那條路：回 401，而且回應要跟「查無此帳號」一模一樣，不讓攻擊者分辨帳號存不存在。這在第 16 課會細講。

rehash on login 有一個盲點：很久沒登入的帳號，會一直留著舊雜湊，永遠等不到升級的機會。OWASP 的建議是設一個期限，過了期限還沒登入的帳號，就讓舊雜湊失效，下次登入時走重設密碼流程（第 16 課）。

💡 實務上：接手一個用 MD5 存密碼的舊系統
等使用者登入再升級太慢，而逼所有人重設密碼又會被客服與 PM 擋下來。OWASP 提到的另一個做法是一次把所有舊雜湊整批包一層，存 Argon2id(舊的 MD5 值) 並標成另一種前綴（例如 argon2id_md5$…），驗證時先算 MD5 再走 Argon2id；使用者下次登入成功，再換成直接 Argon2id(密碼)。這樣上線當天資料庫裡就沒有裸露的 MD5，使用者也完全無感。上線前要確認舊的 MD5 欄位與含舊值的備份都清掉，不然等於沒升級。

到這裡，「怎麼存」已經完整了：salt、慢雜湊、存成一個字串、登入時升級。但還有一個漏洞，存法再好也補不了：如果王小明註冊時用的密碼是 123456，攻擊者第一個就會猜它，慢雜湊只是讓他多等 70 ms。所以註冊 API 也得把關：哪些密碼要擋下來？

註冊時該擋哪些密碼？NIST SP 800-63B-4

上一節說，太好猜的密碼，存法再好也救不回來。那什麼樣的密碼該擋？多數人的直覺是「至少 8 碼，要有大寫、數字、符號，每 90 天換一次」。這套規則用了二十幾年，現在的權威規範卻明文禁止其中大半。

這份規範是美國國家標準與技術研究院（NIST）的 SP 800-63B，數位身分認證最常被引用的規範。第 4 版（寫作 SP 800-63B-4）在 2025 年 7 月定稿，取代 2020 年的版本。規範裡的 SHALL 是「必須」、SHOULD 是「應該」，SHALL NOT 是「不得」。

先講它為什麼推翻組成規則，這是整份規範的核心想法。規定「要有大寫、數字、符號」時，大多數人不會因此寫出隨機的密碼，而是寫出 Latte2026! 這種可預測的變形：首字大寫、結尾加年份和驚嘆號。攻擊者的字典早就收錄了這些變形規則，所以組成規則讓密碼更難記，卻沒有更難猜。真正讓密碼難猜的是長度：morning latte with oat milk 這種長句好記，可能的組合數卻遠多於 8 碼的混合字元。定期強迫改密碼也一樣，結果是 Latte2026! 變 Latte2027!，攻擊者知道舊密碼就猜得到新的。

所以 NIST 的方向是：只要求夠長，再擋掉真正會被猜中的密碼（常用的、外洩過的），其他交給使用者和密碼管理器。下表是密碼相關的條文，查表用，不用背；練習 3 會用到前兩列和黑名單那一列：

規則NIST SP 800-63B-4
最短長度只靠密碼登入：至少 15 字元（SHALL）；密碼只是 MFA 的其中一個因素時（第 1 課的多因素認證，至少兩種不同類型的因素）：至少 8 字元（SHALL）
最長長度至少要允許 64 字元（SHOULD）
組成規則不得要求大小寫、數字、符號（SHALL NOT）
定期更換不得強迫定期改密碼；有外洩證據才要求改
黑名單必須比對常用、可預期、已外洩的密碼清單，比對整個密碼，不是子字串；拒絕時要告訴使用者原因
貼上與密碼管理器必須允許密碼管理器與自動填入；應該允許貼上
提示不得讓使用者存密碼提示
長度怎麼算每個 Unicode code point 算一個字元（SHALL）；比對與雜湊前應做 NFC 正規化（SHOULD）
連續失敗同一帳號連續失敗不得超過 100 次（SHALL，在 §3.2.2 限流一節，第 16 課）

表上「長度怎麼算」那一列看起來是細節，實作時卻最容易出錯。「至少 15 字元」的「字元」要怎麼數？JavaScript 的 s.length 數的不是字元，而且同一個字在位元組上可能有兩種寫法。

第一個問題是 code point。Unicode 給世界上每個字元一個編號，這個編號叫 code point。JavaScript 字串內部用 UTF-16 存，每個單位只裝得下 65535 以內的編號；🍰 這種編號更大的字元要用兩個單位，所以 '🍰'.length 是 2，但它只是一個 code point。用 [...s].length 展開字串，數到的才是 code point 數。用 length 檢查長度，8 個 🍰 會被當成 16 個字元，太短的密碼就這樣過關了。

第二個問題是 Unicode 正規化（normalization）。é 有兩種寫法：一個字元 U+00E9，或 e 加上一個組合重音符 U+0301。螢幕上看起來一樣，位元組卻不同，算出來的雜湊也不同。不同的作業系統、輸入法或複製來源可能產生不同寫法，結果是同一個人在 Mac 上註冊、換到 Windows 就登不進去。s.normalize('NFC') 會把這兩種寫法統一成同一串。

執行下面這格，依序看三件事：8 個 🍰 的 length 和 code point 數不一樣；兩種 café 直接比是不相等的；NFC 之後才相等。

結論是一個順序：收到密碼後先做 NFC，之後的每一步，包括算長度、比對黑名單、雜湊，都用 NFC 後的字串，長度用 code point 數。登入時也要先做 NFC 再驗證，兩邊才對得上。

💡 實務上：密碼規則常常來自舊的檢查表
PM、稽核或客戶的資安問卷常寫著「要有大寫、數字、符號，每 90 天更換」。資深工程師不會默默照做，而是引用 NIST SP 800-63B-4，提議改成長度下限加外洩清單比對，並把上面的表格當成溝通依據，而不是只說「我覺得」。前端也要配合：密碼欄位不要設太短的 maxlength、不要擋貼上、加上 autocomplete="new-password"／"current-password" 讓密碼管理器知道該填什麼。前端的檢查只是使用者體驗，真正的規則一定在後端再檢查一次。

表上的黑名單那一列還沒交代怎麼做。常用密碼清單可以下載回來自己比對，但「已外洩的密碼」數量龐大，而且每次新的外洩事件都會增加。最好的來源在第三方手上，問題是：怎麼拿使用者的密碼去問第三方，又不把密碼交出去？

怎麼查密碼有沒有外洩過，又不把密碼送出去？

上一節留下的問題是比對外洩密碼清單（breached password list）。最常用的來源是 Have I Been Pwned（HIBP）的 Pwned Passwords 服務，它收錄了歷年外洩事件裡出現過的密碼，以及每個密碼出現過幾次。但把使用者的密碼送給第三方查詢，本身就是一種外洩；就算只送完整的雜湊也一樣，雜湊對 HIBP 來說等於密碼，它手上有對照表。

HIBP 用一種叫 k-anonymity（k-匿名）的做法解決。k-anonymity 的意思是：你送出的查詢，同時符合至少 k 筆不同的資料，對方沒辦法知道你要的是其中哪一筆。HIBP 的具體做法分三步：

  1. 你的伺服器算出密碼的 SHA-1，寫成 40 個十六進位字元，只把前 5 個字元送給 HIBP。
  2. HIBP 回傳所有以這 5 碼開頭的雜湊，每個只給後 35 個字元和出現次數。同一個前綴通常對應幾百到上千個雜湊。
  3. 你的伺服器在回應裡找自己那後 35 碼：找到就是外洩過，次數就是出現幾次；找不到就是沒外洩過。

整個過程裡，HIBP 只看到 5 碼前綴，而這個前綴底下有幾百個可能的密碼，它不知道你查的是哪一個。比對在你自己的伺服器上做，密碼和完整雜湊都沒有離開。

實作時有四個細節，前三個練習 4 會用到：

  • 回應每一行是 後 35 碼:次數，用 CRLF（\r\n）分行。
  • 回應大小本身也可能洩漏資訊：每個前綴底下的雜湊數量不同，光看回應有多大，就可能猜出你查的是哪一組前綴。請求加上 Add-Padding: true 標頭，HIBP 會補上假的行讓回應大小差不多。補的行次數是 0，不代表外洩，比對時要排除。
  • 這裡用 SHA-1 沒問題，雖然第 2 課說過它不該再用。在這裡它只是查表的索引，不是用來保護密碼；存進資料庫的照樣是慢雜湊。
  • 查詢放在伺服器端，在註冊和改密碼時做。HIBP 連不上時怎麼辦是取捨：擋下註冊會影響營運，放行就少一層檢查；多數系統選擇放行並記錄。

補充與查表

主線用不到、但設計或審查密碼儲存時會查的細節。

pepper：存在資料庫以外的秘密

salt 不用保密；pepper 剛好相反。它是所有使用者共用、存在資料庫以外（環境變數、secrets 管理服務）的秘密，例如把慢雜湊的結果再用 pepper 當金鑰算一次 HMAC。只有資料庫外洩、伺服器設定沒外洩時，攻擊者沒有 pepper，連猜都沒辦法開始猜。代價是 pepper 一旦外洩就得換，而換 pepper 需要明文密碼，等於所有人都要重設密碼。它是 salt 之外的額外一層，不能取代 salt。第 23 課會講 secrets 怎麼管。

bcrypt 的 72 bytes

多數 bcrypt 實作只吃密碼的前 72 bytes，超過的部分直接被忽略。100 個字元的密碼，跟它前 72 bytes 一樣的任何密碼都能登入；中文一個字 3 bytes，24 個中文字就到上限。不要「先 SHA-256 再丟進 bcrypt」來繞過：雜湊結果可能含 0 byte，有的實作遇到 0 byte 就截斷；而且如果同一個使用者的未加鹽 SHA-256 在別處外洩過，攻擊者可以拿它去配對 bcrypt，這叫 password shucking。新系統直接用 Argon2id，沒有這個問題。

Argon2id 的等效參數

OWASP 對 Argon2id 除了 m=19 MiB、t=2、p=1，也列出等效組合，記憶體少就用更多次數補：m=46 MiB、t=1；m=12 MiB、t=3；m=9 MiB、t=4；m=7 MiB、t=5。

Web Crypto 與 Node 的版本備註

瀏覽器的 Web Crypto 沒有 Argon2、scrypt、bcrypt（Chrome 156 對 Argon2id 丟 NotSupportedError），所以這課的練習用 PBKDF2。第 21 課在 Node 24 用內建的 crypto.argon2()（v24.7.0 加入）。

練習

練習的 iterations 用 1,000 次，讓測試跑得快；正式環境照上面的表。每題開頭「已經寫好」的工具是第 2 課做過的。

練習 1：寫 pbkdf2Sha256 與 hashPassword。pbkdf2Sha256 用 Web Crypto 的 PBKDF2-HMAC-SHA256 算出 bytes 個位元組（importKey('raw', …, 'PBKDF2', false, ['deriveBits']) 再 deriveBits，長度單位是 bits）。hashPassword 先把密碼做 NFC，產生 16 bytes 的 CSPRNG salt，算出 32 bytes 雜湊，回傳 pbkdf2_sha256$<iterations>$<salt>$<hash>（salt 與 hash 用 base64url）。

練習 2：寫 verifyPassword。用 stored 裡存的 iterations 與 salt 重算（密碼一樣先做 NFC），用 timingSafeEqual 比對。格式不對、演算法不是 pbkdf2_sha256、iterations 不是正整數、base64url 解不開，一律回 { ok: false, needsRehash: false }，不能丟例外。密碼正確而且存的 iterations 低於 policy.iterations 時，needsRehash 為 true；密碼錯時一律是 false。

練習 3：寫註冊時的密碼檢查 checkNewPassword。先做 NFC，以 code point 計長度：沒有 MFA 至少 15、有 MFA 至少 8，不足回 too_short；超過 64 回 too_long（這是本課的約定，NIST 只要求至少要允許到 64）；長度合格後，整個密碼在 blocklist 裡就回 blocklisted（黑名單存的是 NFC 形式）。不檢查大小寫、數字、符號。

練習 4：寫 breachCount，用 k-anonymity 查密碼外洩過幾次。算密碼的 SHA-1，轉成大寫 hex，只把前 5 碼傳給 fetchRange（假的 HIBP，只呼叫一次）。回應每行是「後 35 碼:次數」，用 CRLF 分行，hex 可能是小寫，也可能有次數 0 的 padding 行。找到就回傳次數，找不到回 0。

練習 5：關於 salt，下面哪個說法正確？

✓ salt 的作用是讓預先算好的彩虹表失效、讓每個帳號要分開猜，靠的是「每人不同、無法預測」，不是保密，所以存在雜湊旁邊（a 錯）。全站共用時攻擊者只要針對那一個 salt 算一次表（b 錯）。email 可以預測，而且同一個 email 在其他網站也會出現，攻擊者可以預先為它算表（d 錯）。

練習 6：同事說「既然慢就是安全，PBKDF2 的 iterations 直接設一億次」。最主要的問題是什麼？

✓ 600,000 次約 67 ms，一億次就是十幾秒，而且全是你的伺服器在付 CPU。登入 API 變成 DoS 的放大器：攻擊者不用猜對，只要一直送請求。參數要在自己的伺服器上量，控制在數百毫秒內，搭配限流（d 錯）。PBKDF2 沒有 1,000,000 的上限，只要求大於 0（a 錯）；次數不影響碰撞機率（c 錯）。

練習 7：公司的密碼規定是「至少 8 碼、要有大小寫數字符號、每 90 天改一次、不能貼上」，帳號沒有 MFA。依 NIST SP 800-63B-4，哪些要改？

✓ SP 800-63B-4 規定只靠密碼時至少 15 字元、不得要求組成規則、不得強迫定期更換（有外洩證據才要求）、應允許貼上並必須允許密碼管理器，還要比對常用與外洩的密碼。組成規則只會讓人寫出 Latte2026! 這種可預測的變形（b 錯），a、c 都漏掉了其他規則。

常見錯誤

  • 用 MD5、SHA-1、SHA-256 存密碼，或全站共用一個 salt：快速雜湊讓攻擊者每秒試幾十億次，共用 salt 讓他只要做一張表就能查全部帳號。用 Argon2id（或 Web Crypto 環境下的 PBKDF2），每人一個隨機 salt。
  • 用 email 或使用者 ID 當 salt：可以預測，同一個 email 在別的網站也會出現，攻擊者能預先算表。用 CSPRNG 產生 16 bytes。
  • 驗證時用「現在的設定」重算：一調參數，全部人同時登不進來。參數要跟雜湊存在同一個字串，驗證時讀出來用。
  • bcrypt 之前先自己 SHA-256：0 byte 截斷與 password shucking 都會削弱它。新系統用 Argon2id；用 bcrypt 時就在註冊時把密碼限制在 72 bytes 內。
  • 用 s.length 算密碼長度，或在算長度前沒做 NFC：emoji 算兩個、組合字算兩個，同一個密碼換輸入法就得到不同結果。先 normalize('NFC')，再用 [...s].length。
  • 強制組成規則與定期改密碼：NIST SP 800-63B-4 已明文禁止，只會產生 Latte2026! 這種可預測的變形。改成長度下限加外洩清單比對。
  • 慢雜湊參數調太高，登入 API 又沒有限流：攻擊者不用猜對密碼，送假登入就能拖垮伺服器。在自己的伺服器上量過再調，並搭配第 16 課的限流。
  • 驗證失敗時把整個 request body 寫進 log：密碼就這樣以明文進了 log 系統，而 log 的權限通常比資料庫寬鬆得多，前面做的雜湊全白費。記錄時排除 password 這類欄位。

小結

  • 設計密碼欄位時假設資料庫一定會外洩。不存明文、不用可還原的加密，只存雜湊，登入時重算比對。
  • salt 讓相同密碼得到不同雜湊，彩虹表失效、每個帳號要分開猜：每人一個、用 CSPRNG 產生、跟雜湊存在一起、不用保密。pepper 存在資料庫以外，是額外的一層。
  • salt 不會讓猜測變慢，所以要用慢雜湊讓每一次猜測都變貴。OWASP 首選 Argon2id（m=19 MiB、t=2、p=1）；PBKDF2-HMAC-SHA256 要 600,000 次；bcrypt 只吃 72 bytes。參數在自己的伺服器上量，登入 API 要搭配限流。
  • 演算法、參數、salt、雜湊存成一個字串；驗證時用存的參數重算、常數時間比較；登入成功時發現參數過時，就用新參數重新雜湊，這是唯一拿得到明文的時機。
  • 註冊時依 NIST SP 800-63B-4 把關：只靠密碼至少 15 字元、搭配 MFA 至少 8；不設組成規則、不定期強迫改；比對常用與外洩密碼清單；先做 NFC、以 code point 計長度。
  • 查 HIBP 用 k-anonymity：只送 SHA-1 的前 5 碼，在自己的伺服器上比對後 35 碼，密碼和完整雜湊都不離開伺服器。

練習 8：查訂單的 handler 這樣寫，訂單編號是連續的。哪裡會出事？

async function getOrder(req) {
  const order = await db.findOrder(req.params.id)
  if (!order) return notFound()                  // 404
  if (!req.principal) return unauthorized()      // 401，帶 WWW-Authenticate
  if (order.customerId !== req.principal.id) return notFound()
  return ok(order)
}

✓ 先查資料才檢查登入：沒登入的人查存在的訂單得到 401、不存在的得到 404，掃一遍編號就知道哪些訂單存在。把 if (!req.principal) 移到最前面，先認證再碰資料。a 錯在別人的訂單回跟「不存在」一樣的 404，正是為了擋住列舉。（第 1 課）

練習 9：結帳 API 收到 { productId: 3, qty: 2, price: 55 }，handler 直接用 price * qty 算金額。同事說「價格是前端從商品 API 拿的，不會錯」。這樣寫會怎樣？

✓ 請求的每個位元組都在使用者手上，「Copy as cURL」改掉 price 再送就好。前端顯示的價格只是畫面，後端要用 productId 從資料庫查價格。b 錯在 HTTPS 防的是傳輸途中的第三者，改 body 的是使用者自己，送出前就改好了。（第 1 課）

練習 10：PM 問：「權限服務偶爾逾時，退款 API 能不能先放行，不要影響營業？」怎麼回最恰當？

✓ 放行（fail open）等於攻擊者只要灌請求讓權限服務變慢，所有檢查就自動失效，而且被偷偷放行是看不到的。權限、登入、付款、退款出錯一律拒絕，並記錄、告警。b 錯在角色標頭是客戶端送的，任何人都能填 manager。（第 1 課）

練習 11：同事想把顧客的手機號碼放進簽過 HMAC 的 cookie，說「有金鑰保護，別人改不了也看不到」。這句話哪裡不對？

✓ HMAC 保證值是伺服器發的、沒被改過，但內容照樣是明文，DevTools、log、任何拿到 cookie 的人都看得到。要保密就要加密，或只放不敏感的 ID、資料留在伺服器。a 錯在金鑰只用來算和驗證標籤，讀內容不需要金鑰。（第 2 課）

練習 12：重設密碼連結的 token 這樣產生：sha256Hex(email + Date.now())。同事說「經過 SHA-256，64 個 hex 字元看起來完全隨機」。問題在哪？

✓ 熵來自輸入，不是輸出長度：email 是公開的，Date.now() 只要試申請前後幾秒，幾千次就猜中。雜湊不增加熵，「看起來亂」不等於「猜不到」。改用 crypto.getRandomValues 產生 32 bytes。a 錯在不需要反推，攻擊者猜輸入、算一次、比對就好。（第 2 課）

練習 13：金流 webhook 的驗證這樣寫，金鑰用 CSPRNG 產生、放在環境變數。哪裡會出事？

const expected = await signB64url(key, rawBody)   // 重算 HMAC
if (req.headers['x-signature'] === expected) {
  await markOrderPaid(payload.orderId)
}

✓ 攻擊者對每個位置試 64 種字元、挑回應最慢的，一位一位猜出簽章，總共只要 64 × 長度次。改用 crypto.subtle.verify（內部常數時間比較）或 timingSafeEqual。c 錯在不必算出簽章，用時間差逐字元猜就夠了。（第 2 課）

練習 14：密碼存成 SHA-256(salt + 密碼)，salt 每人一個、用 CSPRNG 產生 16 bytes。資料庫整個外洩，這樣夠嗎？

✓ salt 讓彩虹表失效、每人要分開猜，但每猜一次仍然只是一次 SHA-256，常見密碼很快就試完。要用慢雜湊：Argon2id，或 PBKDF2-HMAC-SHA256 600,000 次，讓每一次猜測都變貴。a 錯在 salt 就存在雜湊旁邊，攻擊者拿到資料庫就能針對每個 salt 從頭猜。（第 3 課）

練習 15：驗證密碼這樣寫。上線一年後，把 policy.iterations 從 600,000 調到 800,000，會發生什麼事？

async function verifyPassword(password, stored) {
  const [, , salt, hash] = stored.split('$')
  const computed = await pbkdf2(password.normalize('NFC'), b64urlDecode(salt), policy.iterations)
  return timingSafeEqual(computed, b64urlDecode(hash))
}

✓ 用「現在的設定」重算，算出來的跟當初 600,000 次的雜湊對不上。要讀字串裡存的 iterations 重算；密碼正確而存的次數低於政策時，再重新雜湊並 UPDATE，這是唯一拿得到明文的時機。a 錯在升級的前提是先驗證成功，用錯次數就永遠不會成功。（第 3 課）
