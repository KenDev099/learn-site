階段 3：Token 與 JWT · 第 9 課

驗證 JWT：每個欄位都要檢查

咖啡店訂單 API 原本的驗證程式只做一件事：照 header 的 alg 用 Auth 服務的公鑰驗簽章，通過就相信 payload 的 sub，把對應顧客的訂單回給對方。資安同事拿四張 token 測試這支 API，四張都拿到了 7 號顧客的訂單：

  • 甲：7 號顧客兩個月前登入時拿到的 token，exp 早就過了。
  • 乙：Auth 服務發給集點 API 的 access token。
  • 丙：前端登入時拿到的 ID token。ID token 是 OpenID Connect（第 13 課）用來告訴前端「誰登入了」的 token，不是拿來呼叫 API 的。
  • 丁：攻擊者自己寫的 token，header 改成 alg: none，沒有任何簽章。

前三張的簽章都是真的，第四張根本沒有簽章。這四種情況在真實的系統裡都發生過，原因都一樣：驗證程式只檢查了一部分欄位。這一課的任務，是把訂單 API 的驗證改寫成 verifyAccessToken，讓這四張 token 一張都過不了、正常的 token 照樣通過，最後再決定驗證失敗時回給前端什麼、log 記什麼。

這課的路線：
  1. 簽章驗過了為什麼還不夠：簽章證明什麼、不證明什麼，伺服器要事先決定哪些設定，完整的驗證清單長什麼樣。
  2. 擋下丁：攻擊者改 header 的 alg 能做到什麼，同一個 header 裡的 kid、jku 為什麼也不能照單全收。
  3. 擋下甲：過期怎麼算才不會多給一秒，伺服器之間時鐘不一致時怎麼辦。
  4. 擋下乙和丙：同一把金鑰簽的 token，怎麼用 iss、aud、typ 分辨是不是給訂單 API 的。
  5. 交給函式庫與上線之後：jose、@nestjs/jwt 哪些選項不給就不檢查；失敗時回什麼、log 記什麼，401 突然變多時怎麼查。
這課會用到：
  • 第 8 課的 JWT：header、payload、簽章三段 base64url；HS256 用共用金鑰簽、ES256 用私鑰簽公鑰驗；header 的 kid 指出用哪一把金鑰。練習的起始程式已經放好第 8 課做過的解碼工具。
  • TypeScript 課第 27 課的 Result 型別：失敗不丟例外，回傳 { ok: true, … } | { ok: false, error }，呼叫端用 ok 分辨。
  • TypeScript 課第 16 課的型別縮小：用 typeof 檢查 unknown 值，通過後才能當成字串或數字用。來自 token 的值都先當成 unknown。

簽章驗過了，為什麼四張 token 還是進得來？

第 8 課驗的簽章，回答的是一個問題：「這串 header.payload 是不是握有私鑰的人簽的，簽完之後有沒有被改過」。對甲、乙、丙來說，答案都是「是」：它們確實是咖啡店的 Auth 服務用同一把私鑰簽的，一個字都沒被改過。

簽章不回答的問題有三個：這張 token 現在還能不能用（甲）、它是不是發給訂單 API 的（乙）、它是不是 access token 這種用途（丙）。這三個答案分別寫在 payload 的 exp、aud 和 header 的 typ 等欄位裡，驗證程式要一個一個去看。只驗簽章，等於只確認了「這是真的 token」，沒有確認「這是一張現在、給我用的 access token」。

丁是另一種情況。它根本沒有簽章，卻能通過，是因為驗證程式在決定「怎麼驗簽章」時，聽了 token 自己的話。JWT 的 header 和 payload 都只是 base64url 編碼的 JSON，任何人都能解開、改寫、再編回去。改完之後簽章會對不上，但前提是伺服器真的用正確的方法驗了簽章。如果「用哪個演算法、哪把金鑰」是從 header 讀來的，就等於讓寫 token 的人決定怎麼檢查他自己。

所以驗證程式的第一個原則是：怎麼驗由伺服器的設定決定，不由 token 決定。header 寫了什麼演算法、什麼 kid，都只是 token 的自我介紹；伺服器拿它跟自己的設定比對，對不上就拒絕。具體來說，訂單 API 啟動前要在設定裡寫好這幾件事：

  • 接受哪些演算法：例如只接受 ES256。這份清單叫演算法允許清單（algorithm allowlist），header 的 alg 不在清單裡就拒絕。
  • 信任哪些金鑰，每把綁一種演算法：金鑰表寫的是「kid → (演算法, 金鑰)」。RFC 8725 §3.1 要求函式庫讓呼叫者指定允許清單，而且每把金鑰只能用在一種演算法。為什麼要綁，下一節看到攻擊就會明白。
  • 發行者與接收者：issuer 是簽發 token 的一方，例如 https://auth.coffee.example；audience 是 token 要交給的對象，訂單 API 的名字叫 orders-api。token 的 iss、aud 要跟這兩個值比對，aud 不符就拒收，這叫 audience 限制。
  • 容許多少時鐘誤差：每台伺服器的時鐘不會完全同步，這種差距叫時鐘誤差（clock skew）。比對 exp、nbf 時容許的幾秒寬限叫 leeway。
  • 只收哪種 token：在 header 的 typ 標示這是哪一種 JWT，叫明確型別（explicit typing）。RFC 9068 規定 JWT 格式的 access token 必須寫 typ: "at+jwt"，訂單 API 只收這種。

對照開場的四張 token：丁在第 2 步被擋（none 不在允許清單），甲在第 8 步（過期），乙在第 11 步（aud 是集點 API），丙在第 6 步（typ 不是 at+jwt）。這張清單就是這課的答案。接下來幾節把每一步拆開，看它防的是什麼攻擊、少了它會怎樣。先從丁開始：它不需要偷任何東西，攻擊者自己就做得出來。

攻擊者改掉 header 的 alg，為什麼騙得過驗證？

JWT 的演算法規格 RFC 7518 定義了一個「演算法」叫 none：沒有簽章，token 的第三段是空的。它原本是給「已經有其他方式保證完整性」的場合用。問題出在早年好幾個函式庫的驗證函式是這樣寫的：讀 header 的 alg，照它說的方法驗。攻擊者把 header 改成 {"alg":"none"}、刪掉簽章，驗證函式就照著「不驗」，任何 payload 都會通過。這就是丁。

擋掉 none 還不夠，同一類錯誤有一個更隱密的版本，叫演算法混淆（algorithm confusion）。要看懂它，先回想第 8 課的兩種演算法：HS256 是對稱的，簽和驗用同一把秘密金鑰，安全性完全建立在這把秘密沒人知道；ES256 是非對稱的，私鑰簽、公鑰驗，公鑰本來就公開。混淆攻擊利用的是一個驗證函式同時支援兩種演算法、卻只收一個 key 參數的寫法。過程是這樣的：

  1. 伺服器用 ES256 驗證 token。公鑰本來就公開在 JWKS 端點（第 8 課），任何人都抓得到。
  2. 驗證函式的寫法是 verify(token, key)：照 header 的 alg 選演算法，key 一律傳「那把公鑰的位元組」。
  3. 攻擊者把 header 改成 HS256，拿公鑰的位元組當 HMAC 的秘密金鑰，自己簽一個 payload 寫 "sub": "1", "role": "admin" 的 token。
  4. 驗證函式看到 HS256，就用「公鑰位元組」當秘密算 HMAC。兩邊用的是同一串位元組，結果當然一樣，驗證通過。

關鍵在第 4 步：HMAC 需要的是只有簽發者知道的秘密，這裡被當成秘密的卻是人人都抓得到的公鑰。下面的範例重現兩種攻擊。天真的 naiveVerify 犯了兩個錯：照 header 選演算法、看到 none 直接放行。執行後先看前兩行是不是印出 true，再看修好的 strictVerify 是不是都變成 false：

修好的版本只改了一件事：不管 header 寫什麼，只接受 ES256。這對應 RFC 8725 §3.1 的兩層防護，正式的驗證程式兩層都要有：

  • 允許清單在伺服器：alg 不在清單裡就拒絕，none 永遠不在清單裡。比對要完全相等：None、NONE、es256 都不是 ES256。有函式庫曾經只擋小寫的 none，規格的修訂草案因此特別加了大小寫變形的檢查（見課末）。
  • 每把金鑰綁一種演算法：金鑰表裡寫的是「kid → (演算法, 金鑰)」。拿到金鑰之後，header 的 alg 必須等於這把金鑰綁定的演算法。這樣就算允許清單同時有 ES256 和 HS256（例如從 HS256 換到 ES256 的過渡期），ES256 的公鑰也不會被拿去當 HMAC 秘密。

你可能注意到，範例裡的攻擊者要先把公鑰「匯出成位元組」才做得到。這是 Web Crypto 的 CryptoKey 本身就綁定演算法的緣故，Node 的舊函式庫沒有這層保護，細節見課末。結論不變：用函式庫時一樣要明確給 algorithms，不要依賴它剛好擋得住。

💡 實務上：接手舊專案，先找每個驗證 token 的地方
你很少會從零寫 JWT 驗證，比較常遇到的是接手一個已經跑了幾年的後台。先全文搜尋 verify(、jwtVerify(，確認每個呼叫都有寫死 algorithms；再看 package.json 的 JWT 函式庫版本，跑一次 npm audit 檢查有沒有已知漏洞。要從 HS256 換到 ES256 時，新舊金鑰用不同的 kid，舊的那把等所有舊 token 過期後就從設定移除，不要讓「兩種都收」變成永久狀態。這類檢查適合寫進團隊的 code review 清單，而不是靠某個人記得。

第二層防護要靠金鑰表：先用 header 的 kid 查出金鑰，再看 alg 跟那把金鑰綁的演算法是否一致。但 kid 同樣寫在 header 裡，同樣是攻擊者能改的。查表這一步本身，會不會也被利用？

kid 也是攻擊者寫的，該怎麼拿它找金鑰？

kid（key ID）是 header 裡的一個字串，告訴伺服器「簽這張 token 用的是哪一把金鑰」。第 8 課講過為什麼需要它：Auth 服務會輪替金鑰，新舊兩把在一段時間內同時有效，驗證端要靠 kid 知道該拿哪一把。但用到 kid 的時候，簽章還沒驗，kid 跟丁的 alg 一樣，是攻擊者可以隨便寫的字串。把它當成可信的值拿去做事，就會出這幾種問題：

  • 拿 kid 組檔案路徑：readFile(`keys/${kid}.pem`)。kid 寫成 ../../../dev/null 就讀到空檔案，空字串當 HMAC 秘密，攻擊者也能用空字串簽。
  • 拿 kid 查資料庫：直接拼進 SQL 就是 SQL injection（PostgreSQL 課第 25 課）。
  • 拿 kid 組網址抓金鑰：https://keys.coffee.example/${kid}.json，kid 可以讓網址指到別的地方。
  • 用普通物件當金鑰表：keys[kid] 在 kid 是 constructor 或 __proto__ 時會拿到原型上的東西。用 Map，map.get(kid) 只會找到你自己放進去的。

這四種錯誤的共同點，是讓攻擊者寫的字串決定了「去哪裡拿金鑰」。正確用法只有一種：kid 只用來在「已經信任的金鑰集合」裡查，查不到就拒絕（unknown_kid），不要因此去別的地方找，也不要「每一把都試試看」。這個集合在程式啟動時從設定載入，放在 Map 裡，不會因為收到某張 token 而多出一把。

header 還可能有 jku 和 x5u 兩個欄位：jku（JWK Set URL）是金鑰集合的網址，x5u 是 X.509 憑證的網址。照著 token 裡的網址去抓金鑰，等於讓攻擊者決定「用哪一把金鑰驗我寫的 token」：他把網址指向自己架的 JWKS，裡面放他自己的公鑰，簽章當然通過。就算你只是去抓、最後沒採用，伺服器也已經對攻擊者指定的網址發了請求。伺服器照外部給的網址替攻擊者發出請求，這類漏洞叫 SSRF（server-side request forgery，第 22 課會完整講）。JWKS 的網址寫在伺服器設定裡，跟 issuer 一起決定，永遠不讀 token 裡的。

💡 實務上：多個發行者時，用 iss 查設定，不用 iss 組網址
咖啡店後來開放加盟，每家加盟店有自己的 Auth 服務，API 要收好幾個發行者的 token。容易寫錯的地方是「讀 token 的 iss，在後面接上 /.well-known/jwks.json 去抓金鑰」：這跟讀 jku 是同一個洞，攻擊者自己架一個發行者就能通過。正確做法是在設定裡維護「發行者 → JWKS 網址」的對照表，iss 只拿來查表，查不到就拒絕。新增一家加盟店時，要改的是這份設定，而且要經過 review。

到這裡，丁已經過不了：none 不在允許清單，改成 HS256 會跟金鑰綁定的演算法對不上，亂寫 kid 查不到金鑰。通過簽章驗證的 token，可以確定是 Auth 服務簽的、內容沒被改過。但甲也是 Auth 服務簽的、內容也沒被改過，只是兩個月前就過期了。下一步要讀 payload 裡的時間。

兩個月前的 token 簽章也是真的：過期要怎麼判斷？

第 8 課講過，payload 有三個時間 claim：exp、nbf、iat。它們都是 NumericDate：從 1970-01-01 UTC 起算的秒數，不是毫秒。JavaScript 的 Date.now() 回傳的是毫秒，直接拿來比，所有 token 都會被當成早就過期。三個 claim 的意思與拒絕條件（RFC 7519 §4.1.4、§4.1.5）：

claim意思拒絕的條件（含 leeway）
exp過期時間：這個時間點（含）以後不能用now >= exp + leeway
nbf生效時間：這個時間點以前不能用now < nbf - leeway
iat簽發時間規格不要求檢查；可以用來限制最長壽命：now - iat > 上限

先看沒有 leeway 時的邊界。exp 的意思是「這個時間點（含）以後不能用」，所以 now === exp 時已經過期，拒絕條件是 now >= exp。寫成 exp < now 看起來差不多，但 now 剛好等於 exp 的那一秒會被放行，等於多給一秒。練習 1 的測試會專門檢查這一秒。

再看為什麼需要 leeway。簽 token 的 Auth 服務和驗 token 的訂單 API 是不同的機器，各自的時鐘會差個幾秒。假設 Auth 服務的時鐘快了 10 秒，它簽出一張 nbf 等於自己「現在」的 token；訂單 API 馬上收到，但在它的時鐘看來，nbf 還在 10 秒後，於是拒絕了一張剛簽好的正常 token。leeway 就是為這種誤差保留的寬限：比對 exp 時往後多給 leeway 秒，比對 nbf 時往前多給 leeway 秒。RFC 7519 說 leeway「通常不超過幾分鐘」，實務上 30～60 秒就夠了。寬限放得越大，被偷的 token 也活得越久：leeway 設成一天，15 分鐘的 access token 就多活一天。

還有一個容易漏的地方：規格裡 exp 是選填的，所以函式庫遇到「沒有 exp」時通常直接略過檢查。對自己發的 access token，沒有 exp 就是「永遠有效」，被偷了也永遠能用，所以要把它列為必填，缺了就拒絕（missing_claim）。清單的第 7 步把 exp、iat、sub 都列為必填，就是為了不讓「缺欄位」變成「不檢查」。iat 必填，是因為要用它限制 token 的最長壽命（now - iat > 上限 就拒絕）：沒有 iat 就算不出 token 的年齡，所以後面函式庫一節用的 jose maxTokenAge 也會要求 iat 存在。sub 必填，是因為訂單 API 要靠它知道這是哪位顧客，缺了就無從判斷該回誰的訂單。

最後是一個設計決定：時間要從外面傳進來（now 參數），不要在驗證函式裡呼叫 Date.now()。如果函式自己讀時鐘，測試沒辦法讓它「停在 exp 那一秒」檢查邊界；把 now 當參數，測試就能停在任意時間點。下面的範例把時間檢查單獨拿出來，執行後對照上面的表看每一行的結果：

💡 實務上：「一直被登出」不是調大 leeway 的理由
上線後 PM 常會轉來客服回報：「使用者用到一半被登出」。直覺的修法是把 access token 改成一天、或把 leeway 調大，但這等於讓被偷的 token 多活一天。資深工程師會先分清楚是哪一種：時鐘不準就修時鐘、token 太短讓使用者體驗差就用 refresh token 換新的（第 10 課），而不是放寬驗證。exp 的長度是資安和體驗的取捨，值得跟 PM、資安一起訂下來寫進文件，不要散落在各服務的設定裡。

甲擋下了。剩下的乙和丙更難發現：它們沒過期、簽章是真的、出自同一個 Auth 服務，只是發給了別人，或是別種用途。

OpenID Connect 的 ID token（第 13 課）aud 是前端 App 的 client IDID token 是給前端「知道誰登入了」的，會被存在前端、傳來傳去；當成 access token 收就是把登入證明當通行證

把「發給 A 的 token 拿去打 B」叫做 token 替換（token substitution）。它不需要破解任何東西，攻擊者只要拿到一張在別處合法的 token。乙和丙都屬於這一類。擋它靠三個欄位，各自回答一個問題：

  • iss（issuer），「是誰簽的」：必須完全等於你信任的發行者，例如 https://auth.coffee.example。多個發行者時，每個發行者對應自己的金鑰，不能用 A 的金鑰驗 B 宣稱的 token（RFC 8725 §3.8）。
  • aud（audience），「是給誰的」：必須包含這個 API 自己的識別字（RFC 8725 §3.9）。aud 可以是字串，也可以是陣列，兩種都要處理；陣列要逐一完全比對，不能把陣列或字串拿來做子字串搜尋：'orders-api-admin'.includes('orders-api') 是 true。
  • typ，「是哪一種 token」：access token 是 at+jwt。ID token 不會有這個 typ，所以就算 aud 剛好設錯，也會被擋下（RFC 9068 加這條的目的就是這個）。RFC 8725 §3.12 的建議更進一步：不同用途的 JWT 用不同的金鑰，或互斥的驗證規則，讓一種 JWT 不可能通過另一種的驗證。typ 的其他寫法見課末。

對照開場：乙的 aud 是 loyalty-api，在第 11 步被擋。丙在第 6 步就被 typ 擋下；就算 typ 檢查漏了，它的 aud 是前端的 client ID，走到第 11 步還是過不了。丙被兩道檢查擋住，一道設定錯了，另一道還在。

💡 實務上：設計階段就決定每個 API 的 aud
新增一個服務（例如咖啡店的外送 API）時，設計審查會先問：它的 audience 叫什麼、誰能拿到這個 aud 的 token、驗證設定有沒有填 audience。另一個常見的坑是測試環境和正式環境共用同一個 issuer 和金鑰：測試機上隨手拿到的 token 就能打正式 API。各環境用不同的 issuer 與金鑰，aud 不對直接拒絕，這種「拿錯地方」的事故就不會發生。

四張 token 都擋下了，整張清單也走完了，練習 1 會讓你親手把它寫成 verifyAccessToken。不過自己寫一次是為了理解，正式環境不會自己維護這段程式。

改用 jose 或 @nestjs/jwt，哪些選項不給就等於沒檢查？

正式環境不要自己寫 JWT 驗證，用成熟的函式庫。這課自己做，是為了知道函式庫在做什麼：看得出它的每個選項對應清單的哪一步，也知道哪些步驟「不給設定就不會做」。這一點最容易出事，因為漏設的選項不會報錯，正常的 token 照樣通過，只有甲乙丙丁這類 token 送來時才會發現。下面兩段是設定範例（不能在這頁執行），用到的版本見課末。

jose 的 jwtVerify：

import { jwtVerify, createRemoteJWKSet } from 'jose'

// JWKS 的網址寫在設定裡，不從 token 讀
const JWKS = createRemoteJWKSet(new URL('https://auth.coffee.example/.well-known/jwks.json'))

const { payload } = await jwtVerify(token, JWKS, {
  algorithms: ['ES256'],                  // 允許清單
  issuer: 'https://auth.coffee.example',  // 有給才檢查 iss
  audience: 'orders-api',                 // 有給才檢查 aud（字串或陣列都會處理）
  typ: 'at+jwt',                          // 有給才檢查 header 的 typ
  clockTolerance: 30,                     // leeway，秒
  maxTokenAge: '1 hour',                  // 用 iat 限制最長壽命（會要求 iat 存在）
  requiredClaims: ['exp', 'sub'],         // 不寫的話，沒有 exp 的 token 不會被拒絕
})

jose 永遠不接受 alg: none；沒給 algorithms 時，接受「這把金鑰適用的所有演算法」。createRemoteJWKSet 會依 header 的 alg 和 kid 在 JWKS 裡挑金鑰，而且必須剛好一把符合，這就是上一節「kid 只在信任的集合裡查」的函式庫版本。

jsonwebtoken 是 NestJS 的 @nestjs/jwt 底層用的函式庫。它的預設比較寬鬆，對照清單，不給設定時這幾步不會照你期待的做：

  • 沒給 algorithms 時，依金鑰型別用預設清單：秘密字串是 HS256／HS384／HS512，EC 公鑰是 ES256／ES384／ES512。
  • audience、issuer 沒給就完全不檢查。
  • payload 沒有 exp 就不檢查過期；沒有檢查 typ 的選項，需要的話用 complete: true 拿到 header 自己比對。

所以在 NestJS 裡，要在 JwtModule 一次把這些選項設好，讓所有驗證都走同一份設定：

// NestJS：在 JwtModule 一次設定好（第 21 課會實際做）
JwtModule.register({
  publicKey: config.jwtPublicKey,
  verifyOptions: {
    algorithms: ['ES256'],
    issuer: 'https://auth.coffee.example',
    audience: 'orders-api',
    clockTolerance: 30,
    maxAge: '1h',
  },
})
函式庫的 decode() 只解碼、不驗證。它適合除錯時看內容，絕對不能拿它的結果做授權判斷。code review 時看到 jwt.decode(token).sub 出現在授權邏輯裡，就是漏洞。

不論自己寫還是用函式庫，驗證的結果都是「通過」或「失敗加一個原因」。剩下最後一個問題：失敗時，要讓前端知道多少？

驗證失敗時，回給前端什麼、log 記什麼？

失敗原因有兩個讀者：呼叫 API 的客戶端，和事後查問題的你自己。兩邊需要的內容不一樣，所以回應和 log 要分開寫。

先看回應。狀態碼照第 1 課：認證失敗回 401，而且一定要帶 WWW-Authenticate 標頭，告訴客戶端這個 API 要哪一種認證方式。RFC 6750（Bearer token 的使用方式）§3 規定：

情況狀態碼WWW-Authenticate
沒帶 token，或不是 Bearer401Bearer（不加錯誤代碼，§3.1）
token 過期、被竄改、aud 不對……401Bearer error="invalid_token"

RFC 6750 還定義了 invalid_request（請求格式錯誤，400）和 insufficient_scope（權限不夠，403）。這課的練習把格式錯誤的 Bearer 標頭也當成 invalid_token 處理，讓規則簡單一點。

回應不要寫出「簽章錯誤」「aud 不對」這些細節：攻擊者會用它們一步步調整偽造的 token，例如先試出哪個 alg 能過第 2 步，再試 kid。前端也不需要這些細節：不管哪一種原因，它能做的都一樣，就是換一張新的 token 或請使用者重新登入。

具體原因寫進 log，例如 auth.verify_failed reason=wrong_audience kid=es-2026 sub=7。log 裡不要記整個 token：access token 是 bearer token，誰拿到誰能用，log 系統的讀取權限通常比資料庫寬（第 25 課）。

這份 log 上線後就是除錯工具。正式環境突然出現大量 401 時，照 log 的原因代碼查：

原因先查什麼
expired、not_yet_valid 突然變多伺服器時間：比對簽發端與驗證端的時鐘，是不是有一台的 NTP 校時壞了
wrong_audience、wrong_issuer發 token 那一端的設定：新部署的環境是不是填錯 issuer 網址（例如 http 與 https、結尾斜線）
unknown_kid金鑰輪替：Auth 服務改用新金鑰簽了，但 API 快取的 JWKS 還是舊的（第 8 課的輪替順序、第 13 課的 JWKS 快取）
bad_signature 少量出現多半是有人在嘗試竄改；大量出現時檢查是不是各環境的金鑰混用

原因代碼能這樣查，前提是驗證程式每一步都回傳自己的代碼，這也是練習 1 要求固定順序、固定代碼的原因。下面三題就是這課的任務：練習 1 把清單寫成 verifyAccessToken，練習 2 是同事匆忙補過一輪、現在線上的 verify：它擋下了 alg: none，也會比對 exp，但還留著四個漏洞，請你 code review 並修好；練習 3 寫每個請求最前面的 authenticate，決定回什麼、記什麼。

練習

練習 1：實作訂單 API 的 verifyAccessToken(token, opts)。opts.keys 是信任的金鑰表（kid → 綁定的演算法與 CryptoKey），opts.now 與 opts.leeway（預設 0）的單位是秒。照下面的順序檢查，第一個不符合的就回傳那個錯誤代碼：

  1. 用已經寫好的 parseJwt 解析，失敗 → malformed
  2. header 的 alg 不是 'ES256' 或 'HS256'（完全相等）→ alg_not_allowed
  3. kid 不是字串，或不在 opts.keys 裡 → unknown_kid
  4. header 的 alg 不等於這把金鑰綁定的 alg → alg_not_allowed
  5. 用這把金鑰驗簽章：ES256 用 { name: 'ECDSA', hash: 'SHA-256' }、HS256 用 'HMAC'，失敗 → bad_signature
  6. header 的 typ 不是 'at+jwt' → wrong_typ
  7. exp、iat 不是數字，或 sub 不是字串 → missing_claim
  8. now >= exp + leeway → expired
  9. 有 nbf 時，nbf 不是數字或 now < nbf - leeway → not_yet_valid
  10. iss 不等於 opts.issuer → wrong_issuer
  11. aud（字串或字串陣列）不包含 opts.audience → wrong_audience

全部通過時回傳 { ok: true, claims: payload }。

練習 2：code review。下面的 verify 是訂單 API 現在在用的版本，正常的 token 都能通過，但它有四個漏洞：

  1. 照 header 的 alg 選演算法，HS256 時拿公鑰的 JSON 文字當 HMAC 秘密（演算法混淆）。
  2. 沒有檢查 aud：給集點 API 的 token 也能打訂單 API。
  3. exp 不存在時直接略過過期檢查。
  4. 用 kid 組網址，呼叫 deps.fetchKey 去抓金鑰：kid 寫成 ../../evil 或 http://evil.example，攻擊者就能決定用哪把公鑰驗他自己簽的 token。

改寫成只從 deps.trustedKeys（訂單 API 啟動時從設定載入的 ES256 公鑰，kid → 公鑰）取金鑰、只接受 ES256，四個漏洞都修好，完全不呼叫 fetchKey（這個參數留著是因為舊程式還會傳進來）。正常的 token 仍要通過。錯誤代碼自己選用 Result 裡最合適的。

練習 3：寫訂單 API 每個請求最前面的 authenticate(authorization, verify)。authorization 是 Authorization 標頭的值（沒帶時是 undefined），verify 是練習 1 那種驗證函式。規則：

  • 標頭格式是 <scheme> <token>：用第一個空白切開。scheme 不分大小寫（bearer、BEARER 都算 Bearer）。
  • 沒帶標頭 → logReason: 'missing_token'；scheme 不是 Bearer（例如 Basic …）→ 'not_bearer'。這兩種的 wwwAuthenticate 都是 'Bearer'，不加錯誤代碼。
  • token 必須符合 RFC 6750 的 b64token：一個以上的 A-Z a-z 0-9 - . _ ~ + /，後面可以接任意個 =。不符合（空的、含空白、含其他字元）→ logReason: 'malformed_header'，而且不呼叫 verify。
  • verify 失敗 → logReason 是它回傳的錯誤代碼。
  • malformed_header 與驗證失敗的 wwwAuthenticate 一律是 'Bearer error="invalid_token"'，不能透露具體原因。所有失敗的 status 都是 401。
  • 成功時回傳 { ok: true, claims }。

練習 4：訂單 API 用 Auth 服務的公鑰驗證 token，簽章驗證通過了。下面哪一句正確？

✓ 同一把私鑰可能簽出 ID token、給集點 API 的 access token、兩個月前就過期的 token，它們的簽章全都是對的。a 和 b 漏掉了用途與接收者的檢查，會被 token 替換利用。d 混淆了認證與授權：就算 token 完全有效，「7 號顧客能不能看 #42 訂單」還是要另外判斷（第 1 課、第 19 課）。

練習 5：一個 token 的 header 是 {"alg":"ES256","kid":"../../../dev/null"}。驗證程式該怎麼處理？

✓ header 的每個欄位都是攻擊者可以任意改寫的輸入，簽章在這個時候還沒驗。kid 只能當成查表的 key，查不到就拒絕。a 讓攻擊者決定讀哪個檔案：讀到空檔案、空字串當 HMAC 秘密，他就能自己簽 token。c 是黑名單思維，編碼變形、絕對路徑、其他特殊字元總有漏網之魚；正確的做法是根本不拿 kid 組路徑。

練習 6：前端用咖啡店的 Auth 服務登入，把拿到的 ID token 放進 Authorization: Bearer … 呼叫訂單 API。ID token 和 access token 是同一個 Auth 服務、同一把金鑰簽的。驗證程式靠哪個檢查擋下它？

✓ ID token 的 aud 是前端 App 的 client ID，不是訂單 API；而且它不會帶 typ: at+jwt（RFC 9068 加這個 typ 就是為了這種情況）。b、c 都會通過，因為發行者和金鑰都一樣。d 正是這題要破除的迷思：同一個發行者簽的不同種類 token，用途不同，要用互斥的規則驗證（RFC 8725 §3.12）。

常見錯誤

  • 依 token header 的 alg 決定怎麼驗：alg: none 和演算法混淆都從這裡來。允許清單寫在伺服器設定，每把金鑰綁一種演算法。
  • 只驗簽章，不驗 aud、iss、typ：發給別的 API、別種用途的 token 都能通過。函式庫的 audience、issuer 選項要明確給。
  • exp 不存在時當成永不過期：大多數函式庫預設就是這樣。自己發的 access token 把 exp 列為必填（jose 的 requiredClaims）。
  • leeway 設很大：設成一天，15 分鐘的 token 就多活一天。30～60 秒就夠，時間差更大要修的是 NTP 校時。
  • 用 decode（不驗證）的結果做授權判斷：decode 只能拿來除錯看內容。
  • 用 header 裡的 jku、x5u 網址或 kid 組網址抓金鑰：攻擊者決定用哪把金鑰驗他自己的 token，還會造成 SSRF。JWKS 網址寫在設定裡。
  • 回應告訴客戶端「簽章錯誤」「已過期」：回應只有 Bearer error="invalid_token"，原因寫進 log。
  • log 印出整個 token：讀得到 log 的人就能冒用。只記 kid、sub、jti（第 8 課的 token 唯一 ID）和原因代碼。
  • exp 用毫秒比較：Date.now() 是毫秒，NumericDate 是秒，比較前先除以 1000 取整數；更好的做法是把 now 當參數傳進驗證函式。

RFC 8725 的修訂草案

RFC 8725 的修訂草案（draft-ietf-oauth-rfc8725bis，2026-10-31 時已核准、還在 RFC Editor 佇列，尚未成為 RFC）特別加了 alg 大小寫變形的檢查，因為有函式庫曾經只擋小寫的 none。

為什麼範例要先把公鑰匯出成位元組

Web Crypto 的 CryptoKey 在匯入時就綁定了演算法：把 ECDSA 公鑰傳給 crypto.subtle.verify('HMAC', …) 會丟 InvalidAccessError，所以演算法混淆的範例必須先把公鑰「匯出成位元組」才做得到。Node 的舊函式庫收的是 PEM 字串或 Buffer，沒有這層保護，這就是當年演算法混淆能成功的原因。用函式庫時一樣要給 algorithms，不要依賴它剛好擋得住。

typ 的其他寫法

RFC 9068 也接受完整寫法 application/at+jwt，而且 media type 不分大小寫；這課的練習為了簡單只接受 at+jwt，jose 的 typ 選項則會把兩種寫法都當成相同。

小結

開場的四張 token，簽章驗證都擋不下來；擋下它們的是簽章以外的檢查：

  • 怎麼驗由伺服器決定：允許的演算法、信任的金鑰（每把綁一種演算法）、issuer、audience、leeway 都寫在設定裡，header 只拿來比對。
  • 順序：格式 → alg 允許清單 → kid 查表 → alg 與金鑰相符 → 簽章 → typ → 必要 claim → exp → nbf → iss → aud。簽章之前，payload 的內容一個字都不能信。
  • 丁：alg: none 與演算法混淆，都是「照 header 選演算法」造成的。kid、jku、x5u 也是攻擊者的輸入：kid 只在 Map 裡查，網址從不讀 token 的。
  • 甲：now >= exp + leeway 就是過期；exp 必填；leeway 幾十秒；時間用注入的 now。
  • 乙和丙：typ（at+jwt）、iss、aud 一起擋 token 替換；aud 可能是字串或陣列，要完全比對。
  • 函式庫的 issuer、audience、algorithms 不給就不檢查。
  • 失敗時回 401 與 WWW-Authenticate: Bearer error="invalid_token"（沒帶 token 時只回 Bearer），原因只進 log，log 不記整個 token。
