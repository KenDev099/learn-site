階段 6：資深工程師的資安實務 · 第 24 課

OWASP API Security Top 10（2023）總整理

咖啡店的 API 下個月要開放給加盟門市和外送平台。主管把端點清單交給你：「上線前做一次安全審查，交一份『先修哪些』的清單給我。」清單上有後台訂單列表 GET /orders?limit=20、每月的訂單匯出、會寄簡訊驗證碼的忘記密碼、下週開賣的聖誕限量咖啡豆，還有新舊兩版的訂單 API /v1/orders 與 /v2/orders。前面 23 課你一項一項學了密碼、session、JWT、OAuth、授權、SSRF、加密，可是面對一整份端點清單，問題變成：要照什麼順序問？怎麼知道自己沒漏掉某一類問題？

這一課用 OWASP 的 API Security Top 10 當審查的地圖，帶著這份端點清單逐項走過，把前面沒教過的四類問題補上，最後把找到的問題排好順序交出去。

這課的路線：
  1. 審查要拿什麼當清單：OWASP API Top 10 的十類問題、每一項對到這門課的哪一課，哪些還沒學過（開場問題的最小答案）。
  2. ?limit= 能被要到多大：沒有上限的查詢、上傳、付費簡訊怎麼把服務或帳單拖垮（API4）。
  3. 限量咖啡豆：每個請求都合法、程式沒有 bug，為什麼還是出事，要怎麼擋（API6）。
  4. 錯誤回應裡為什麼有 SQL、端點清單本身可不可信：設定錯誤（API8）與說好要下線卻還在線上的舊版 API（API9）。
  5. 清單外的問題與交出審查結果：注入、供應鏈去哪裡找，找到的問題怎麼排序、怎麼放進 CI。
這課會用到：
  • 第 18 課的 BFLA 與第 19 課的 BOLA、BOPLA：一般使用者呼叫到管理功能、看到別人的資料、改到或看到不該碰的欄位。
  • 第 16 課的限流：超過次數回 429，用 Retry-After 標頭告訴對方多久後再試。

審查要拿什麼當清單？

審查最怕的是靠靈感：今天想到 SQL injection 就查注入，明天想到限流就查限流，查完也說不出「還有哪一類沒看」。所以第一步是找一份公認的分類，讓每個端點都照同一份問題走一遍。API 領域最常用的那一份來自 OWASP。

OWASP（Open Worldwide Application Security Project）是一個非營利的應用程式安全社群，整理各種風險清單，也發布 Cheat Sheet，也就是針對單一主題的實作建議。這門課引用過好幾次它的密碼儲存與 SSRF 的 Cheat Sheet。它專門為 API 整理的那份叫 OWASP API Security Top 10，目前的版本在 2023 年發布，所以每一項的編號寫成 API1:2023 這種形式，平常簡稱 API1 到 API10。

這份清單要怎麼讀？它不是「十個要打勾的功能」，而是十類最常見、影響最大的問題。你不會「實作 API4」，而是拿 API4 去問每個端點：「這裡有沒有沒上限的東西？」清單的價值在於提醒你有哪些方向要問，讓審查不依賴當天想到什麼。

讀清單時會發現授權佔了很大比例：十項裡有三項是授權（API1、API3、API5），API2 則是認證。原因跟 API 的形狀有關。API 回傳的是結構化資料，資料的 ID 直接出現在網址上，例如 /orders/1043；攻擊者只要把 1043 改成 1044 就能試，不需要任何特殊工具。所以授權錯誤在 API 裡特別多，也特別容易被找到。下表是十項的整理，最後一欄是這門課在哪裡處理過它：

三項授權最容易混在一起，而分錯類的代價是修錯地方。分辨的方法是問「少檢查了什麼」：少檢查這一筆的擁有者是 API1，例如店員能看別人的訂單；少檢查這個欄位能不能讀或改是 API3，例如顧客能自己改點數；少檢查這類動作（整個端點）能不能用是 API5，例如吧台能刪菜單。同一個端點可能同時有好幾項。

到這裡，開場的問題有了最小答案：審查時拿這十項逐一問每個端點。表裡已經有一半在前面的課處理過，授權的三項有第 18、19 課的 guard 與物件檢查，API2 有密碼、JWT 與限流，API7、API10 有第 22 課的 SSRF 防護。剩下標著「本課」的 API4、API6、API8、API9 是還沒學過的。端點清單上的第一個 GET /orders?limit=20 正好就是 API4 的典型例子，從它開始。

?limit= 能被要到多大？

咖啡店的後台訂單列表是 GET /orders?limit=20，前端每次要 20 筆。審查時你試著把它改成 ?limit=1000000：資料庫掃了一百萬列，Node 把一百萬個物件放進記憶體、再序列化成一大串 JSON，這個請求跑了 40 秒，期間其他店員的請求全部變慢。

這不只是效能問題。效能問題是「正常使用時太慢」；這裡是任何人只要送一個請求，就能讓所有人用不了服務。讓服務無法回應正常使用者的攻擊叫阻斷服務（denial of service，DoS）。一般印象中的 DoS 是用大量流量淹沒伺服器，但 API 常常不用大量流量：只要找到一個沒有上限的參數，一個請求就夠了。OWASP 把這類問題列為 API4 資源耗用不受限：API 讓呼叫者決定要用多少資源，卻沒有限制上限。

先修眼前這一個。修法是伺服器端自己決定上限：沒給 limit 就用預設 20 筆，給了超過 100 就只回 100 筆。上限一定要在伺服器端，前端的下拉選單只有 20、50、100 不代表什麼，攻擊者不會用你的前端，他直接改網址。

伺服器端拿到的 limit 是查詢字串，也就是一個字串，要先轉成數字才能比大小。這一步很容易出錯，因為 JavaScript 的轉換函式各有各的寬鬆。執行後看每一列的三個結果，特別是 parseInt 和 Number 把哪些看起來不像數字的字串變成了數字：

parseInt('50abc') 是 50，因為 parseInt 從頭讀到不是數字的字元就停下，把前面讀到的當結果；Number('') 是 0，空字串被當成零；Number('1e3') 是 1000，因為科學記號也是合法的數字寫法。查詢字串來自使用者，寬鬆的轉換會把垃圾當成合法輸入，例如 '1e3' 繞過「只能寫數字」的直覺、'' 變成 0 筆。正確的順序是先驗證字串、再轉換：規則寫清楚只接受「1 到 9 開頭、後面全是數字」，通過了才轉成數字，再套上 100 的上限。在 NestJS 裡，這就是 DTO 上的驗證規則（NestJS 課第 7 課）。

limit 修好了，但它只是一種資源。API4 的「資源」指的是處理一個請求會用到的任何有限的東西，CPU 只是其中之一。拿端點清單一個一個看，會發現每一列都有類似的缺口：

資源怎麼被耗光上限放在哪裡
資料庫與記憶體?limit=1000000、沒有分頁的匯出伺服器端限制每頁筆數（預設 20、最多 100）
請求大小送 500 MB 的 JSON、陣列裡塞十萬個品項body 大小（框架預設值見課末，超過回 413）；字串長度、陣列元素數量寫進 DTO 驗證
上傳上傳 2 GB 的「商品圖片」檔案大小與數量（NestJS 課第 22 課）
昂貴的操作連按 50 次「匯出全年報表」每個使用者、每個租戶的配額；放進背景工作排隊
付費的第三方服務對忘記密碼端點送幾萬次請求，每次寄一封簡訊每個手機號碼、每個 IP 的次數上限；第三方的花費上限或帳單告警
時間一個查詢卡住，連線池被占滿每個請求、每個查詢、每個外部呼叫的逾時

最後兩列最常被忽略，因為它們不會讓伺服器變慢。端點清單上的忘記密碼就是付費服務那一列：每呼叫一次，咖啡店就付一封簡訊的錢。SMS pumping（簡訊灌量）是攻擊者大量觸發「寄驗證碼」，有時還搭配自己控制的高費率電話號碼，跟電信業者分潤。你沒有任何資料外洩，服務也照常運作，帳單卻多了幾十萬。OWASP 的 API4 頁面第一個例子就是忘記密碼的簡訊。防法分兩層：第一層是限流（第 16 課、系統設計課第 10 課），每個手機號碼、每個 IP 都限制次數；第二層是在簡訊供應商那邊設花費上限或帳單告警，當成程式出錯時的最後一道防線。時間那一列也類似：一個卡住的查詢本身不貴，但它佔住一條資料庫連線，連線池被佔滿後，所有請求都在排隊。

上限有了，接著要決定「上限是誰的」。如果月報匯出是全站共用「每小時 3 次」，一個加盟店連按三次，其他所有加盟店這一小時都匯不了，這就是第 20 課的「雜訊鄰居」。所以配額的 key 要跟著「誰在付錢、誰在被保護」走：匯出報表按租戶算，登入失敗按帳號與 IP 算，寄簡訊按手機號碼算。超過時回 429 Too Many Requests 加上 Retry-After，讓正常的客戶端知道多久後再試，而不是不停重試讓情況更糟。練習 1 會把分頁上限和按租戶計算的匯出配額實作出來。

💡 實務上：替已上線的 API 加上限，先觀察再擋
新端點一開始就帶上限最省事；難的是替跑了兩年的舊 API 補上限，因為你不知道誰正依賴「一次拿一萬筆」，可能是 POS 的夜間同步，或會計每月的匯出。常見做法是先只記錄「超過上限的請求」一兩週，看是哪些客戶端、多大的量，再決定數字並通知對方改用分頁。上限的數字要能說出來由，例如「門市一天的訂單量」，而不是隨手寫 1000。簡訊、Email 這類付費服務的告警要找維運或財務一起設，帳單異常時第一個收到通知的人不該只有你。

到這裡，GET /orders、匯出、忘記密碼都有了上限。但上限擋的都是「量」：一個請求太大、一個人送太多。端點清單上的下一項是聖誕限量咖啡豆，它的請求都很小，每個人也只買一次，上限一個都沒被碰到，卻還是出事了。

限量咖啡豆：每個請求都合法，怎麼還是出事？

去年的聖誕限量咖啡豆，每包 450 元，只有 300 包。開賣 10 秒就賣完，隔天全部出現在拍賣網站上，價格翻三倍。你檢查程式：庫存扣得正確、沒有超賣、每個請求都通過認證與授權，也沒有一個請求超過上限。程式沒有 bug，但老顧客一包都沒買到。今年的端點清單上又有這個活動，審查時要回答「這次會不會再發生」。

問題出在哪裡？「先搶先贏」這個流程是設計給人用的：人要開網頁、選數量、按結帳，至少要幾秒。攻擊者寫程式直接呼叫 API，同時用幾十個帳號在開賣的那一刻送出，速度和數量都是人比不上的。每一步都照規格執行，但整個流程被大量、快速地自動化之後，結果就不是產品原本想要的「讓顧客買到」。這類問題 OWASP 列為 API6 敏感業務流程存取不受限，白話說就是業務流程被濫用。「敏感」指的是這個流程被自動化濫用時，會有人受損，可能是公司的錢，也可能是其他顧客。咖啡店會遇到的：

  • 限量商品被機器人（bot），也就是自動執行的程式，掃光再轉賣。
  • 迎新點數：註冊送 50 點，有人寫程式註冊一萬個帳號，把點數集中換成咖啡。OWASP 的例子是叫車 App 的推薦獎勵。
  • 優惠碼被暴力猜：代碼只有 6 碼英數字，沒有次數限制。
  • 訂位：外帶預約時段被大量預訂再取消，正常顧客訂不到。

上一節的限流為什麼擋不住？限流計算的是「同一個 key 在一段時間內的次數」，它擋得住一台電腦狂打。但攻擊者用一萬個帳號、分散在很多 IP，每個帳號只買一次，每個 key 的次數都是 1，限流完全看不到異常。所以防禦要從業務規則下手：先問「這個流程被大量自動化的話，誰會受損」，再依受損的方式挑工具。每種手段擋的東西不同，代價也不同：

手段擋什麼代價
每人限購、累計上限同一個帳號重複買幾乎沒有；但開新帳號就能繞過
綁定難以大量取得的東西：付款卡、驗證過的手機開很多帳號要多收一些資料；共用一張卡的家人會被擋
帳號年齡、延遲發放（註冊 7 天、第一次消費後才給點數）註冊完立刻套利正常新顧客的體驗變差
人類驗證（CAPTCHA）、裝置指紋、行為偵測（加入購物車到結帳不到 1 秒）自動化腳本擋到正常使用者、要持續調整，攻擊者也在進步
抽籤、預約登記取代先搶先贏速度優勢改變產品設計，要 PM 同意
人工審核大額或異常的兌換規則沒想到的手法人力

這張表要從上往下讀，每往下一列，擋得越多，代價也越大。只做第一列「每人限購 2 包」，攻擊者多開帳號就繞過了；加上第二列「同一張付款卡也最多 2 包」，開帳號變得沒用，因為付款卡不能無限申請；再加上第三列「帳號要建立滿 24 小時」，開賣當天才註冊的帳號也買不到。三層疊起來，攻擊者的成本就從「寫一支程式」變成「準備很多張卡和提早養很多帳號」。練習 2 會用這三列寫出限量咖啡豆的購買檢查。

還要注意的是，這張表的每一列都是產品決策，不是工程師自己能決定的：要不要讓共用一張卡的家人買不到、要不要改成抽籤，影響的是顧客體驗和行銷目標。資深工程師的工作是在設計階段就問出「這個流程會不會被刷」，把風險和每種手段的代價講清楚，讓產品一起決定。

API4 和 API6 都是 API 的設計少了限制：一個少了用量上限，一個少了業務規則。審查時你在 staging 對 POST /users 送了一個重複的 email，想看註冊失敗的回應長什麼樣子，結果回應裡出現了一整段 SQL 錯誤。這次設計沒有問題，出事的是設定與預設行為。

錯誤回應裡為什麼有 SQL？

那段回應是這樣來的：資料庫拒絕了重複的 email，丟出一個錯誤，而全域的錯誤處理把這個錯誤原封不動回給了前端。開發時這麼寫很方便，前端畫面上直接就看得到錯在哪；上線後，看到的人就變成了攻擊者。執行後比較兩種對外回應，以及 log 裡留下了什麼：

攻擊者從第一個回應知道了這些事：

  • 資料庫是 PostgreSQL，有一張 users 表，email 有唯一索引。
  • 所以他能拿註冊來確認某個 email 有沒有註冊過，這就是第 16 課的帳號列舉。
  • stack 裡還有程式碼的檔案路徑，等於看到了伺服器內部的目錄結構。

沒有一項能直接拿來入侵，但每一項都讓下一步攻擊更容易。

那出錯時要怎麼查？第二種回應只給一個通用訊息和 request id。request id 是伺服器替每個請求產生的唯一編號，同一個請求寫出的每一筆 log 都帶著它（Node 課第 19 課）。使用者回報問題時給客服這個編號，你就能在 log 裡找到完整的錯誤訊息和 stack。細節只存在你看得到的地方，對外不必洩漏任何東西，除錯也不受影響。

如果用的是 NestJS，內建的 exception filter（NestJS 課第 8 課）遇到不認得的錯誤，已經會回 500 與「Internal server error」，不會洩漏訊息。出事通常是自己寫的全域 filter 為了除錯，把 exception.message 放了進去。OWASP 的建議是把錯誤回應也定義成 schema，只回 schema 裡有的欄位，這樣即使有人在錯誤物件上多掛了東西，也帶不出去。練習 3 會寫這樣一個全域錯誤處理函式：只有程式刻意丟給使用者看的錯誤才把訊息放進回應，其他一律通用訊息。

這個問題屬於 API8 安全設定錯誤。這一類的共同點是：每一行程式單獨看都沒寫錯，是某一層的設定或預設行為讓系統變得不安全。這裡的「某一層」可以是請求經過的任何一層：框架、反向代理、雲端服務、容器。錯誤處理只是最常見的一種，OWASP 列出的其他狀況對到咖啡店是這樣的：

狀況例子怎麼防

到目前為止，你都是照著主管給的端點清單一個一個查。但清單上的資訊本身可信嗎？如果清單把一個端點的狀態寫錯，或線上有一個端點根本不在清單上，前面所有的審查都碰不到它。

清單上的資訊本身可信嗎？

清單上有 /v1/orders 和 /v2/orders 兩版，背後有一段歷史。去年咖啡店推出 /v2/orders，加上「店員只能看自己門市的訂單」。舊版 /v1/orders 留著給舊 POS App 用，說好三個月後下線，後來大家都忘了；清單上 /v1 標著「已停用，只剩舊 POS」，實際上卻還能用。審查時你拿一般店員的帳號試 /v1/orders，看到了所有門市的訂單：新版的安全修補沒有回到舊版，而舊版還連著同一個資料庫。

這是 API9 資產管理不當：不知道自己對外有哪些 API、哪些版本、哪些主機。「資產」在這裡指的是所有對外開放、攻擊者碰得到的東西。你沒列管的東西，就不會被審查、不會被修補，也不會有人記得要關掉。它常見的有兩種形態。第一種是剛才的情況，已經宣布淘汰、卻還在線上的舊版，叫殭屍 API（zombie API）。第二種是線上有、但從來沒被列管的端點，叫影子 API（shadow API），例如同事為了除錯加的 POST /admin/debug，沒寫進文件，也沒人審查過；主管給你的清單上不會有它。

主機也是資產。staging.coffee.example 對外開放、還連著正式資料庫，限流卻只設在正式環境的閘道上，攻擊者就會去打 staging。OWASP 的 API9 例子就是這樣：研究者在 beta 主機上暴力猜 6 位數的重設密碼碼，因為限流只做在正式環境前面。

根本原因是清單靠人維護：有人加了端點忘了寫文件，有人說好下線忘了關。所以對策是讓清單變成自動維護、自動檢查的東西：

  • OpenAPI 文件就是清單（NestJS 課第 23 課）：從程式產生，跟著 CI 建置，不靠人手寫。
  • 自動比對「框架實際註冊的路由」和「文件」：多出來的是影子 API，文件有卻沒註冊的是文件過時。練習 4 寫這個比對。
  • 淘汰要有日期：舊版在 OpenAPI 標 deprecated: true，再寫下停止服務的日期。OpenAPI 本身只有 deprecated，日期常放在自訂的 x-sunset 欄位；對客戶端則用 HTTP 的 Deprecation 與 Sunset 兩個標準標頭通知（規格與格式見課末）。過了日期還在線上的，CI 直接報錯。
  • 每個對外的版本都套同樣的防護：授權、限流做在共用的 guard 或閘道，新版的安全修補要評估是否回補到舊版，不能回補就加快下線。
  • 非正式環境不放正式資料：真的需要時，用跟正式環境一樣的防護。
💡 實務上：下線舊版前，先看還有誰在用
接手一個系統時，很值得先花半天列出它對外的網域、閘道上的路由和各版本的流量。要關 /v1 前，先從存取 log 找出還在呼叫的客戶端（看 API key 或 User-Agent），逐一聯絡負責人、約好日期，而不是直接拔掉讓舊 POS 在尖峰時段壞掉。Deprecation 和 Sunset 標頭從宣布淘汰那天就開始送；一直聯絡不到的流量，可以在離峰時段先短暫停用舊版幾小時，看有沒有人來反應。淘汰日期要寫進 PM 的時程，只寫在工程師的備忘裡，三個月後就沒人記得。

到這裡，API Top 10 的十項都走過了：前面的課處理過六項，這課補上四項。但端點清單裡還有一個匯出 CSV 的功能，你懷疑它有注入問題，翻遍十項卻找不到對應的分類。

API Top 10 沒列到的，要去哪裡找？

找不到是正常的：Top 10 是「最常見的十類」，不是「全部」。清單上沒有 SQL injection，不代表 API 不會被注入。API 版只挑 API 特有、發生頻率最高的問題，所以把授權拆成三項，卻沒有注入。補上這個缺口的是 OWASP 另一份給網頁應用的 OWASP Top 10，它涵蓋整個應用程式，包括前端與建置流程。目前是 2025 版，下表把它的十項對到 API 版和這門課：

表中標著「API 清單沒有」的三列，正是只看 API 版會漏掉的：A03 供應鏈、A05 注入、A09 記錄與告警。匯出 CSV 的疑慮就落在 A05，它叫 CSV 公式注入（CSV injection）：顧客在姓名、備註這類欄位填入以 =、+、-、@ 開頭的內容，例如 =HYPERLINK("https://evil.example","點此查看")。管理員匯出 CSV、用 Excel 打開時，這段內容會被當成公式執行，可能被拿來外連或騙人點擊。攻擊者不需要能呼叫匯出端點，只要能把資料寫進欄位；受害的是打開檔案的人。防法是匯出時替這類開頭的值加上前綴（例如單引號）或跳脫，讓試算表把它當成文字。這三類常常是損害最大的，一個被植入的套件或一個字串拼接的 SQL，影響的是整個系統。所以審查 API 時兩份清單都要對照：API 版提醒你 API 特有的高頻問題，網頁版補上整個應用程式都會有的那幾類。

現在你手上有兩份清單，也已經記下一串問題：簡訊不限次數、錯誤回應帶 SQL、Swagger UI 對外、/v1/orders 沒有門市檢查、匯出 CSV 可能被注入。最後一步是把這些整理成主管要的那份「先修哪些」。

怎麼把審查做完，交出「先修哪些」？

回頭看這一課的過程，你其實已經在做安全審查（security review）：有系統地檢查設計與程式碼，找出安全問題。關鍵是「有系統」，照著同一份問題逐個端點走，而不是靠靈感想到什麼查什麼。把這一課的做法整理成可以重複的步驟：

  1. 列出所有端點：從 OpenAPI 產生，再跟實際註冊的路由比對（API9），不要直接相信別人給的清單。包含管理端點、webhook、內部服務呼叫的端點。
  2. 每個端點問同一組問題：下表把兩份清單濃縮成八個問題，右欄是對應的類別。
問題對應
誰能呼叫？沒登入呢？什麼角色？API2、API5
能碰哪些物件？查詢有沒有帶上擁有者、門市、租戶的條件？API1、第 20 課
能改哪些欄位？回應帶出哪些欄位？API3
一次最多能用多少資源？會不會觸發要花錢的服務？API4
被自動化大量呼叫的話，誰會受損？API6
會不會用使用者給的網址去連線？會不會相信第三方的資料？API7、API10
出錯時回應會洩漏什麼？有沒有記錄到 log？API8、A09
輸入有沒有拼進 SQL、命令、檔案路徑？A05
  1. 排序：每個問題估兩個分數。「可能性」是要什麼條件才能利用：不用登入？一般帳號？內部人員？條件越少，可能性越高。「影響」是被利用後的後果：看到一筆、看到全部、能改錢。兩者相乘後由大到小修。下一課會再細談。
  2. 修補並寫回歸測試：每個修好的漏洞都留一個攻擊測試，重現當初的攻擊並確認它被擋下，確定它不會在之後的修改中回來（第 26 課的期末專題就是這樣做）。

把這一課找到的問題套上第 3 步。執行後看排序結果，注意最先要修的是哪一個，以及「看起來最嚴重」和「排在最前面」是不是同一個：

排在最前面的 /v1/orders 和簡訊灌量同為 6 分，理由卻不同：一個是影響大（一般店員就能看到所有門市的訂單），一個是可能性高（不用登入就能打，又直接變成帳單）。同分時再看哪個修起來快、哪個正在被利用，決定先後；這裡的先後只是排序穩定留下的原順序。CSV 注入聽起來嚴重，卻排在最後：要成功得等管理員匯出、用試算表打開，通常還要按過安全警告，條件多，所以可能性低；成功了影響是誤導或外連，而不是直接讀到全部資料。這就是排序的意義：讓團隊先花力氣在最可能出事、出事損失最大的地方。

這次審查是你一個人逐端點做的。但端點每週都在增加，不可能每次都從頭人工審一遍。能交給機器的檢查放進 CI，每次合併程式都自動跑，人工審查才有時間看業務邏輯：

  • secret scanning：掃描程式碼裡有沒有寫死的金鑰。第 17 課讓 API key 帶固定前綴，就是為了讓掃描器認得；工具如 gitleaks（部署課第 11 課）。
  • 相依套件稽核：npm audit 與 lockfile 檢查（Node 課第 3、25 課），對應 A03 供應鏈。
  • SAST 與 DAST：SAST（static application security testing，靜態分析）讀原始碼找危險寫法，例如字串拼接的 SQL；DAST（dynamic application security testing，動態掃描）對執行中的服務送攻擊請求，看它怎麼反應。兩者都只找得到一部分問題：它們不知道「這筆訂單應該只有王小明看得到」，所以抓不到 BOLA 和 API6。
  • 授權矩陣測試：補上掃描工具抓不到的授權問題。把每個端點 × 每種角色 × 自己的資料／別人的資料的預期結果寫成表格，自動跑一遍。第 19 課把授權判斷寫成不讀資料庫、不讀時鐘的純函式，就是為了讓這種組合好測；第 18 課的「每個路由都要有政策」檢查也屬於這一類。這是擋住 API1、API3、API5 最有效的自動化。

回到開場的任務：你交給主管的是一份排好序的問題清單，每一項寫明對應哪一類、怎麼重現、建議怎麼修；再加上一組放進 CI 的自動檢查，讓這次修好的問題不會在下次上線時回來。

💡 實務上：審查常發生在 PR 和上線前
大部分團隊不會每季從頭審一次，而是在新功能的設計討論和 PR 審查時，拿上面那組問題問新增或改動的端點；大型上線或客戶要求時，才會另外請外部資安公司做滲透測試（實際模擬攻擊者來打你的系統）。回報問題時，每一項寫清楚「怎麼重現、誰能利用、影響多大、建議怎麼修」，PM 和主管才排得進時程。不要一次丟出三十項沒排序的清單，團隊會不知道從哪裡開始，最後一項都沒修。發現的是正在被利用的漏洞時，就不是排時程的問題，要立刻通報負責人。

補充與查表

主線用不到、但查清單出處或實作淘汰標頭時會用到的細節。

清單的出處與版本沿革

API Top 10 十項的英文名稱以 OWASP 官方頁面為準（2026-10-31 確認）；OWASP Top 10:2025 的名稱以 top10.owasp.org/2025 為準（2026-10-31 確認）。

API3 是 2023 版才合併出來的：2019 版的「回傳太多資料（Excessive Data Exposure）」與「mass assignment」本質相同，都是欄位層級沒做授權。

OWASP Top 10:2025 新增的 A10「例外狀況處理不當」（Mishandling of Exceptional Conditions）講的也是錯誤回應那一節的事：出錯時的行為要跟正常路徑一樣被設計和測試。

框架預設的 body 大小上限

Express 預設 100 KB、Fastify 預設 1 MiB，超過回 413。

Deprecation 與 Sunset 標頭

Deprecation 是 RFC 9745（2025 年 3 月），值像 @1688169599，是 Unix 時間；Sunset 是 RFC 8594，值是停止回應的時間。

練習

練習 1：修好兩個 API4 的漏洞。

  • listOrders(query, orders)：query.limit 沒給就回 20 筆；超過 100 就只回 100 筆；不是正整數字串（例如 'abc'、'-1'、'0'、'1.5'、'50abc'、''、'1e3'、' 5'）回 { status: 400, error: 'invalid_limit' }。
  • createExportOrders() 回傳一個 exportOrders(ctx, now)：每個租戶在每個整點小時（以 UTC 計，例如 10:00:00.000～10:59:59.999）最多匯出 3 次，超過回 { status: 429, retryAfterSeconds }，秒數是距離下一個整點還有多少秒（無條件進位）。now 是毫秒。第 16 課的視窗從第一次請求起算；這裡改成對齊整點，配額可以寫成「每小時 3 次，整點重置」，客戶看得懂、客服也好解釋。

練習 2：聖誕節限量咖啡豆。寫 purchaseLimited(customer, qty, ctx)，依序檢查，第一個不通過的規則就是回傳的 reason：

  1. qty 只能是 1 或 2，其他（0、3、負數、小數、NaN）回 invalid_qty。
  2. 帳號建立未滿 24 小時（ctx.now - customer.createdAt 小於一天）回 account_too_new；剛好滿 24 小時可以買。
  3. 同一位顧客在 ctx.history 裡已買的數量加上這次超過 2 包，回 per_customer_limit。
  4. 同一張付款卡（ctx.cardFingerprint，金流給的卡片指紋，同一張卡永遠相同）在全站已買的數量加上這次超過 2 包，回 per_card_limit。

都通過回 { ok: true }。history 是這個商品全站的購買紀錄，不要修改它（成功後由呼叫端寫入）。

練習 3：寫全域錯誤處理用的 toErrorResponse(err, requestId)。err 是任何被丟出來的東西（unknown）：

  • 是 HttpError（用 instanceof 判斷）：回它的 status，body.message 用它的 message。這種錯誤是程式刻意丟給使用者看的。
  • 其他任何東西（一般的 Error、字串、null、剛好有 status 屬性的物件）：status 一律 500，body 只有 { message: '伺服器發生錯誤', requestId }，不能帶原始訊息、stack、SQL。
  • body 一定有 requestId；log 一定有 requestId、status、message。未預期的錯誤要記完整的 message（不是 Error 時用 String(err)），是 Error 時再加上 stack；HttpError 是預期中的錯誤，不用記 stack。

練習 4：寫 CI 用的 API 清單檢查 findInventoryGaps(registered, openapi, today)。registered 是框架實際註冊的路由（參數寫成 :id），openapi 是文件（參數寫成 {id}）。回傳三個清單：

  • undocumented：有註冊、文件沒有（影子 API）。
  • missing：文件有、沒註冊（文件過時）。
  • pastSunset：有註冊、文件裡有 x-sunset，而且 today 大於或等於它（殭屍 API）。只標 deprecated 沒寫日期的不算。日期都是 YYYY-MM-DD。

比對規則：方法不分大小寫；路徑裡的參數只看位置，不看名字（/orders/:orderId 和 /orders/{id} 相同）。每一項寫成「大寫方法、空白、路徑」，undocumented 與 pastSunset 用註冊時的路徑，missing 用文件的路徑；三個清單都排序。

練習 5：吧台的帳號能呼叫 DELETE /admin/menu-items/7，把拿鐵從菜單刪掉。這屬於哪一項？

✓ b：菜單品項不屬於任何店員，問題不在「這一筆」，而是吧台根本沒有 menu:write（第 18 課）。a 是常見迷思：把所有授權問題都叫 BOLA，修法就會找錯地方；c 是欄位層級，這裡是整個動作；d 管理端點本來就該存在，只要有權限檢查而且列在清單上。

練習 6：註冊送 50 點（可換一杯美式咖啡）。有人寫程式註冊了一萬個帳號，把點數轉進同一個帳號換咖啡。每個請求都通過了驗證與授權，程式也照規格執行。這是什麼問題？

✓ c：沒有 bug 也可以是漏洞，被大量自動化走完的業務流程就是 API6。a 正是這一項要破除的迷思，損失一樣是真的錢；b 密碼規則與刷帳號無關；d 限流擋得住一台電腦狂打，擋不住分散到很多 IP、每個帳號只註冊一次的攻擊，要從業務規則下手。

練習 7：OWASP Top 10:2025 和 OWASP API Security Top 10（2023）是什麼關係？

✓ d：API 版把授權拆成三項（API1、API3、API5），卻沒有注入與供應鏈；網頁版的 A03 Software Supply Chain Failures、A05 Injection、A09 Security Logging and Alerting Failures 都適用於 API。a、b 把兩份混為一談；c 讓你漏掉 SQL injection 這種後端最常見、損害最大的漏洞。

常見錯誤

  • 審查靠靈感，想到什麼查什麼：查完說不出漏了哪一類。先從 OpenAPI 和實際路由列出所有端點，每個端點照同一組問題走，兩份 OWASP 清單都對照。
  • 只修「程式 bug」，忽略業務流程被濫用：限量、點數、優惠碼的損失不需要 bug。設計時就問「這個流程被大量自動化，誰會受損」，和產品一起選限制手段。
  • 分頁與匯出沒有上限：一個請求就能拖垮資料庫。伺服器端驗證 limit 是正整數並套上上限；匯出這類昂貴操作加上每個租戶的配額。
  • 用 parseInt 或 Number 轉使用者輸入：'50abc'、''、'1e3' 都會變成數字。先用規則驗證字串，再轉換。
  • 忘了付費的第三方服務也是資源：簡訊、email、AI API 被灌量就是帳單。每個手機號碼、IP 都要限次數，供應商那邊設花費上限或告警。
  • 錯誤回應帶資料庫訊息或 stack：洩漏資料表、索引、內網位址，還能拿來列舉帳號。對外只給通用訊息與 request id，細節進 log；只有刻意丟出的 HttpError 才把訊息給使用者。
  • 舊版 API 沒有下線計畫：新版的安全修補沒回到舊版，舊版就成了後門。寫下 sunset 日期、送 Deprecation／Sunset 標頭、CI 檢查過期的路由。
  • staging 對外開放還連正式資料：防護通常只做在正式環境前面。非正式環境不放正式資料，或用同樣的防護。
  • 以為 Top 10 就是全部：API 版沒有注入、供應鏈、記錄與告警。兩份清單都要對照，加上第 25 課的威脅建模。
  • 以為掃描工具會找到授權問題：SAST／DAST 不知道哪筆資料屬於誰。授權靠設計審查與授權矩陣測試。

小結

  • 審查一支 API 要有清單：OWASP API Security Top 10（2023）是 API1 BOLA、API2 認證、API3 BOPLA、API4 資源耗用、API5 BFLA、API6 敏感業務流程、API7 SSRF、API8 設定錯誤、API9 資產管理、API10 不安全地使用第三方 API。它是十類要問的方向，不是十個要打勾的功能。
  • 分辨三種授權失效：少檢查這一筆（API1）、這個欄位（API3）、這類動作（API5）。
  • API4：一個請求就能讓所有人用不了服務。分頁、body、上傳、昂貴操作、付費服務、時間都要有上限；使用者輸入先驗證字串再轉數字；配額依租戶、帳號、手機號碼計算；超過回 429 加 Retry-After。
  • API6：程式沒 bug 也會被濫用，限流擋不住分散到很多帳號的攻擊；用累計限購、綁定付款卡或手機、帳號年齡、延遲發放、行為偵測疊加防護，這些是產品決策。
  • API8：錯誤回應只給通用訊息與 request id，細節進 log；CORS、安全標頭、HTTP 方法、debug 端點、Swagger UI、TLS、雲端儲存的設定都要檢查。
  • API9：別人給的端點清單不可盡信。OpenAPI 文件就是清單，自動比對實際路由找出影子 API；舊版要有 sunset 日期並如期下線；每個對外版本與主機都要同樣的防護。
  • OWASP Top 10:2025 是另一份清單，注入（A05）、供應鏈（A03）、記錄與告警（A09）只在這一份，審查 API 時一併對照。
  • 安全審查：列端點 → 每個端點問同一組問題 → 依可能性 × 影響排序 → 修補並留攻擊測試；能自動化的（secret scanning、套件稽核、SAST／DAST、授權矩陣測試）放進 CI。
