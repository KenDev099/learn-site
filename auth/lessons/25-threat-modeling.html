階段 6：資深工程師的資安實務 · 第 25 課

威脅建模、稽核紀錄與事故應變

上個月，咖啡店的 POS 出現一筆 1,100 元的退款，那張訂單原價只有 110 元。店長去問，當班的陳美華說不是她按的。系統裡只查得到「POS 帳號 store-01 那天有登入」，可是三個店員共用這個帳號，退款這個動作本身也沒有留下任何紀錄。最後誰也說不清楚，店家自己吸收了這筆錢。

下個月，咖啡店要上線「線上點餐＋集點」：顧客用 Vue 網頁和 App 下單，外送平台用 webhook 把訂單送進來，店員在 POS 上退款，背景 worker 呼叫金流扣款。老闆只提了一個要求：「出了事查不出來、也不知道該怎麼辦」的狀況，不能再發生。這課從頭到尾就做這件事，替這次上線準備好三樣東西：上線前的威脅模型，先找出設計上會出什麼錯；上線後的稽核紀錄與偵測，防護被繞過時發現得到、查得出誰做了什麼；出事時的事故劇本，凌晨三點照著做。前面 24 課補上的密碼、session、JWT、OAuth、授權、SSRF、加密，都是針對已知問題的防護；這課練的是把它們組織起來的工作方式。範例一路沿用那筆退款。

這課的路線：
  1. 那筆退款能不能在寫程式之前就想到：威脅建模的四個問題，以及老闆那個要求的最小答案。
  2. 畫資料流程圖、用 STRIDE 逐一問：把系統畫成圖，對每條跨過信任邊界的箭頭問六種錯，退款那條為什麼一定會被抓出來。
  3. 風險排序：清單列出幾十條之後先修哪些，每一條怎麼做決定。
  4. 稽核紀錄：補上退款紀錄時該記什麼、不能記什麼，藏在字串裡的秘密怎麼擋，怎麼讓紀錄改不了（雜湊鏈那節選讀）。
  5. 偵測與事故應變：誰會發現正在發生的攻擊，告警響了先做哪一步，事後怎麼回頭更新威脅模型。
這課會用到：
  • 第 1 課的信任邊界與攻擊面：信任邊界是資料從不可信的地方進到可信的地方的那條線，跨過就要重新驗證；所有攻擊者碰得到的入口合起來叫攻擊面。
  • 第 16 課的登入事件與限流：每次登入成功、失敗都記一筆，再依帳號和 IP 計數、超過就延遲或擋下。
  • Node 課第 19 課的結構化 log：每筆 log 是一個有固定欄位的 JSON 物件，並依欄位名稱遮掉敏感值。

那筆退款，能不能在寫程式之前就想到？

先回頭看那筆退款是怎麼發生的。「店員可以退款」寫在需求裡；「三個人共用一個 POS 帳號」是為了交班方便；「退款要不要留紀錄」從頭到尾沒有人問過。程式沒有寫錯任何一行，每個功能都照需求動作。錯在設計：在動手之前，沒有人問過「這個功能可能被怎麼用壞」。這種問題，測試和 code review 抓不到。它們檢查的是程式有沒有照設計做（少了一個 await、條件寫反），而需求裡本來就沒有的東西，程式照做也照樣沒有。

要在設計階段抓到這類問題，靠的是威脅建模（threat modeling）。它的做法是拿系統的一種表示（通常是一張資料流程圖），有系統地找出安全與隱私上可能出錯的地方。它不是工具，也不是文件格式，而是一組固定要問的問題。Threat Modeling Manifesto 把它整理成四個：

  1. 我們在做什麼？（What are we working on?）畫出系統：有哪些元件、資料怎麼流。
  2. 可能出什麼錯？（What can go wrong?）對每個元件和資料流列出威脅。
  3. 我們要怎麼處理？（What are we going to do about it?）每個威脅決定修、接受還是轉移。
  4. 做得夠好嗎？（Did we do a good enough job?）回頭檢查：有沒有漏掉的元件、決定有沒有落實、測試有沒有寫。

拿退款功能走一遍：我們在做的是「POS 呼叫退款 API」；可能出的錯之一是「店員退了款，事後卻能否認」；處理方式是每人一個帳號、每筆退款寫一筆紀錄；做得夠不夠好，就是上線前確認紀錄真的寫進去、查得到。這只是一場會議裡十分鐘的討論，上個月那筆 1,100 元至少查得出是誰按的。

老闆的要求也就有了最小版本的答案。上線前，由負責的工程師照這四個問題把新功能想一遍；上線後，靠安全事件的紀錄與告警發現防護被繞過；出事時，照事先寫好的劇本，先止血（換掉外洩的金鑰、讓偷走的憑證失效）再調查。這課後面的小節，就是把這三件事一件一件做出來。

什麼時候做威脅建模有三個時機：設計新功能時，這是改設計最便宜的時候；架構改變時，例如加了一個第三方、拆出一個服務；事故之後，檢查模型漏了什麼。一次一兩個小時，拉負責的工程師和一位懂資安的人一起，比上線前找外部做一次滲透測試更早抓到設計上的錯。滲透測試（penetration test）是請人在系統做好之後，實際扮成攻擊者去打；它找到問題時，程式已經寫完了，要改設計就得重寫。

💡 實務上：小團隊的威脅建模，就是設計審查裡多問的半小時
很少團隊有專職資安，常見的做法是在設計文件或 PR 範本裡加一段「安全考量」。觸發條件要明確：碰到登入與權限、金額（退款、儲值）、個資、新的第三方串接（例如接外送平台 webhook）就要做；改按鈕顏色、調文案就不用。資深工程師審設計時會先問三句：誰能呼叫這個 API？資料跨過了哪條信任邊界？出事時我們從哪裡知道？答不出來的地方，就是威脅清單的第一條。

四個問題裡，第二題「可能出什麼錯」最難回答：憑空想，大部分人只會想到最有名的 SQL injection。要有一個具體的東西可以對著問，所以第一題要先做好：把系統畫出來。

「我們在做什麼」：怎麼把系統畫成一張能逐項檢查的圖？

威脅清單只會涵蓋你列出來的東西。只用嘴巴描述「線上點餐」，每個人腦中的系統都不一樣：有人想到外送平台，有人沒想到 worker 會直接呼叫金流。畫成一張圖，大家對著同一張圖一個元件一個元件問，沒被問到的地方才會顯眼。最常用的畫法是資料流程圖（data flow diagram，DFD）。它不畫類別、不畫畫面，只關心「資料從哪裡來、到哪裡去、經過誰的手」，而這正好是攻擊會走的路。

DFD 只有四種元素，再加上一種線：

  • 外部實體：你控制不了的人或系統。顧客、店員、外送平台、金流。他們送進來的東西，一律不能直接相信。
  • 程序（process）：你寫的、會處理資料的程式。API 伺服器、背景 worker。
  • 資料存放：PostgreSQL、Redis、S3。資料停留的地方，也就是被整份拿走時損失最大的地方。
  • 資料流：箭頭，標上傳什麼（「帳密」「訂單 JSON」「webhook」）。
  • 信任邊界：第 1 課教過的那條線。資料跨過它，就要重新驗證。

咖啡店這次要上線的「線上點餐＋集點」畫出來是這樣：

畫完先數跨過虛線的箭頭：顧客的帳密和訂單、POS 的退款、外送平台的 webhook、對資料庫的 SQL 與佇列、worker 對金流的扣款請求。每一條都要能回答三個問題：對方是誰（認證）？他能做這件事嗎（授權）？內容可信嗎（驗證與簽章）？

拿 POS 的退款那條箭頭試試。「對方是誰」的答案是「store-01」，不是某一個人。上個月的事故，在這張圖上一眼就看得到：一條會動到錢的箭頭，對面的身分是三個人共用的。

圖還有一個用處：沒畫出來的元件就不會被分析。所以畫圖時要把「平常不會想到」的東西問清楚、畫進去，例如「staging 也連著正式資料庫」「店長用 Google 試算表匯出會員」。這也是第 24 課 API9 資產管理的問題：你不知道它存在，就不會保護它。

三個問題能找出不少洞，但「內容可信嗎」範圍太大，每個人會想到不同的東西，也很容易漏掉一整類。需要一張固定的清單，對每條箭頭照表問。

對著每條箭頭，要問哪幾種「可能出什麼錯」？

這張固定的清單最常用的是 STRIDE，Microsoft 提出的六個分類，每個字母是一種錯的英文字首。它不容易漏的原因是：每一類都對應一個被破壞的安全性質。安全性質就那幾個（認證、完整性、不可否認性、機密性、可用性、授權），六個字母各守一個，問完一輪，等於每個性質都檢查過一次。

用法是一次拿一個元件或一條資料流，六個字母問一遍。拿「POS → API 的退款」這條箭頭來問：

  • S 偽冒：店員是誰？
  • T 竄改：金額能不能被改？
  • R 否認：事後能不能證明是誰退的？
  • I 資訊洩漏：回應會不會帶出顧客卡號？
  • D 阻斷服務：能不能一秒退一千筆？
  • E 權限提升：一般店員能不能退超過權限的金額？

表裡五類都在前面的課講過防護，只有 R 是這課的主角，值得多講一點。R 破壞的是不可否認性（non-repudiation），意思是做過的事事後賴不掉。光有登入不夠。如果三個店員共用一個 POS 帳號，就算有紀錄也只知道「某個店員」；如果紀錄存在應用程式能改的表裡，店長也可以說「那是被改過的」。所以否認這一類的防護要三樣一起：每個人有自己的帳號、記下誰在什麼時候做了什麼、紀錄改不了。上個月的事故，三樣全缺。

對 DFD 上每條跨邊界的箭頭和每個元件都問一輪，清單很快就有幾十條，而上線日期不會因此往後延。下一個問題是：這麼多條，先修哪幾條？

清單列出幾十條之後，先修哪一條？

工程時間有限，不可能全部修完再上線，所以先處理風險最高的。常用的估法是風險 = 可能性 × 影響。可能性看攻擊需要什麼條件：匿名就能打，還是要先拿到店長帳號。影響看出事之後損失多少：全部會員資料，還是一筆訂單的備註。用乘的，是因為兩個都高的才最急；只有一個高的，排在後面。用 1～3 分各打一個分數就夠用，重點是大家用同一把尺，而不是分數多精確。

下面是咖啡店清單裡的五條，按執行後看排序結果：第一名是哪一條，上個月那筆退款對應的「店員退款沒有稽核紀錄」排第幾。

外送 webhook 沒驗簽章拿到 9 分：任何人都能偽造已付款訂單（可能性高），每一張都是直接的金錢損失（影響高）。退款沒有紀錄排第二。排完之後，每個威脅要有一個明確的決定，寫進設計文件（系統設計課第 18 課的 ADR）。決定只有四種：

  • 緩解（mitigate）：做防護，降低可能性或影響。大多數高風險的威脅走這條。webhook 驗簽章、退款寫稽核紀錄都是緩解。
  • 消除：把造成風險的功能拿掉。「店長可以匯出全部會員 email」如果沒人真的需要，刪掉最省事。
  • 轉移（transfer）：交給別人負責。卡號不自己存，交給金流的代碼化（tokenization）；或買資安保險。轉移不會讓風險消失，剩下的部分要寫清楚。
  • 接受（accept）：知道風險，決定不處理。例如「錯誤回應帶出資料表名稱」影響小、修的成本卻要動到整個錯誤格式，排到下一季。接受要有人簽名、寫理由、訂重新檢視的日期，否則「接受」就只是「忘了」。
威脅模型做一次就丟著，半年後就跟系統對不起來。把 DFD 和威脅表放在 repo 裡（例如 docs/threat-model.md），架構改變的 PR 要一起更新，事故檢討時也回頭看「模型裡有沒有這一條」。

排第一的 webhook 也決定緩解，做法是驗 webhook 簽章，第 17 課已經做過。這課要補的是前面的課都沒教過的第二名：「店員退款沒有稽核紀錄」，同樣決定緩解。緩解要做的事聽起來很簡單：把退款記下來。但記哪些欄位、記在哪裡、哪些東西絕對不能記，每一點做錯都會讓紀錄在需要它的那天派不上用場。

補上退款紀錄：稽核紀錄該記什麼、不能記什麼？

任何防護都可能失效。失效的那天，你要能回答五件事：誰、什麼時候、從哪裡、做了什麼、成功了沒有。套到退款就是：哪個店員的帳號、幾點幾分、從哪台 POS、退了哪張訂單多少錢、退款有沒有成功。答不出來，就是上個月的處境。OWASP Top 10:2025 把這種「記錄和告警不足」列為 A09 Security Logging and Alerting Failures，典型的情況是攻擊者在系統裡待了幾個月，卻沒有任何紀錄能查。

你可能會想：伺服器本來就有 log，退款時多印一行不就好了？問題在於應用程式 log 是為了除錯而寫的，格式隨時在變、幾天後就輪替刪掉，工程師也能隨手清掉。要能拿來舉證，需要另一種紀錄：稽核紀錄（audit log），專門回答「誰在什麼時候做了什麼」。兩者的差別：

應用程式 log稽核紀錄
目的除錯、看效能調查、舉證、法規要求
內容什麼都可能有，格式隨版本變固定的事件與欄位
保存幾天到幾週依法規與合約，常是一年以上
誰能讀工程團隊少數人，讀取本身也要記錄
能不能改可以輪替、刪除只能新增，改了要被發現

稽核紀錄不是每個動作都記，而是記會被追問的事件：跟身分、權限、金錢、資料外流有關的動作。依 OWASP Logging Cheat Sheet 與這門課的流程，要記的事件有：登入成功與失敗、登出、MFA 與 passkey 的新增移除、密碼重設申請與完成、email 變更、角色與權限變更、API key 建立與撤銷、授權失敗（403、跨租戶的 404）、refresh token 重用偵測、資料匯出、店員的退款與改價、設定變更。

每一筆的欄位要固定，才能在出事時用同一個查詢找出來。每筆要有的欄位：時間、事件名稱、主體（誰，使用者 id 或服務名稱）、目標物件（哪張訂單、哪個帳號）、結果（成功、失敗與原因代碼）、來源 IP、User-Agent、request id。request id 是 Node 課第 19 課的 request context 產生的，有了它，就能把稽核紀錄和同一個請求的應用程式 log 串起來，看到那次退款前後伺服器做了什麼。

記得太少查不到，記得太多則會讓 log 自己變成外洩來源。絕對不能記的：密碼（包括登入失敗時輸入的錯誤密碼，那常常是另一個網站的真密碼或差一個字的正確密碼）、access／refresh token、session ID、API key、重設密碼 token、OAuth 的 code、加密金鑰、資料庫連線字串、完整卡號。這些東西拿到就能直接用，而 log 被複製的份數遠比資料庫多。手機和 email 視需要遮罩（0912***678）。真的需要追蹤「同一個 session」時，記 token 的 SHA-256 前幾碼，而不是 token 本身。

💡 實務上：最先來要稽核紀錄的，常是客服和業務
真實情況多半不是駭客，而是客服問「這筆退款是誰按的」、會員說「我沒下這張單」、企業客戶的資安問卷問「你們的操作紀錄保存多久、誰能看」。稽核事件要在做功能的同時就加，事後補只能查到補上之後的事。上線前資深工程師會檢查：退款、改價、改權限、匯出這些動作有沒有寫進稽核表；稽核紀錄有沒有後台頁面讓客服自己查，而不是每次都找工程師下 SQL。

「不能記什麼」的規則寫清楚了，實作上卻有一個常見的漏洞：大部分 logger 只會依欄位名稱遮罩。

logger 已經遮掉 password 欄位，秘密為什麼還是寫進了 log？

「不能記什麼」這條規則不只管稽核紀錄。同一個服務的應用程式 log（除錯用的那種）更容易出事，因為錯誤 log 是程式出錯時自動印出來的，內容不是你像稽核紀錄那樣逐欄挑的。Node 課第 19 課的 logger 會把名稱是 password、token、authorization 的欄位換成 [REDACTED]。這擋得住「秘密放在有名字的欄位裡」的情況。但秘密常常藏在字串值裡：錯誤訊息印出完整的 callback 網址、資料庫驅動程式的錯誤帶著連線字串、有人把標頭串進 message。下面這筆錯誤 log 就混了好幾種，按執行看看哪些被擋下、哪些沒有：

password 欄位擋下來了，但 OAuth 的 code、資料庫密碼、整張 JWT 都原封不動寫進 log。log 會被送到 log 平台、備份、轉給外部廠商、貼到 Slack 討論，看得到它的人遠比看得到資料庫的人多。所以寫出去之前，還要掃一次字串值。欄位名稱靠不住，就改用秘密本身的格式認出它：連線字串長得像 ://帳號:密碼@，JWT 以 eyJ 開頭，API key 有固定前綴。這就是第 17 課讓 API key 有固定前綴的原因，GitHub 的 secret scanning 也是靠格式找 token。

用正規表示式掃字串時，要記得Node 課第 25 課的 ReDoS：(a+)* 這種巢狀量詞，遇到故意構造的輸入會回溯到指數時間。這裡特別危險，因為 log 的內容有一部分是攻擊者送來的（網址、標頭），一條 50 KB 的惡意 log 就能卡住整個程序：本來是保護紀錄的程式，變成阻斷服務的入口。寫法上的規則是每個量詞前面都要有固定的開頭（eyJ、Bearer 、://），量詞裡面不要再包量詞。練習 1 就是照這個規則寫出完整的掃描函式。

到這裡，稽核紀錄記對了東西，也不會洩漏秘密。但回到陳美華：如果紀錄上清楚寫著她的帳號退了那 1,100 元，而她說「這筆紀錄是被人改過的」，你要怎麼證明沒有？

如果有人說「紀錄被改過」，怎麼讓稽核紀錄改不了？

稽核紀錄存在資料庫裡，有寫入權限的人就能改，包括拿到應用程式資料庫帳號的攻擊者。他進來的第一件事，常常就是刪掉自己留下的紀錄。所以第一層防護是權限：應用程式用的資料庫角色（cafe_app）只能新增，不能改、不能刪稽核表。稽核表的擁有者（owner）要是另一個角色，因為擁有者可以把自己的權限加回來，只拿掉權限、擁有者卻還是 cafe_app，等於沒擋。

REVOKE UPDATE, DELETE, TRUNCATE ON audit_log FROM cafe_app;

PostgreSQL 課第 38 課的做法更嚴：應用程式角色對 audit_log 完全沒有權限，只能透過 trigger 呼叫的 SECURITY DEFINER 函式寫入，連假紀錄都塞不進去。

權限擋得住應用程式帳號，擋不住能管整個資料庫的人，例如 DBA，或拿到超級使用者的攻擊者。對他們，目標要從「改不了」退一步，變成「改了會被發現」。常見做法是雜湊鏈：每筆紀錄的雜湊把前一筆的雜湊也算進去，改一筆，後面就全斷；再定期把最新一筆的雜湊存到另一個系統。怎麼做在下一節（選讀）。多數團隊的做法是先把權限做好，再把稽核紀錄另外送一份到應用程式帳號改不到的地方，例如另一個雲端帳號的 log 服務。

到這裡，紀錄寫得對，應用程式帳號改不了，被改了也藏不住。但它們都是在出事之後才派上用場；攻擊正在進行的時候，誰會注意到？

雜湊鏈：改了一筆紀錄，怎麼讓它藏不住？（選讀）

這節是選讀：上一節的資料庫權限是每個專案都該做的；雜湊鏈用在稽核要求高的系統（金流、醫療、要給稽核單位看的紀錄）。要實作這類稽核紀錄時再回來看。跳過不影響後面的課；練習 2 對應這一節。

雜湊鏈（hash chain）的做法是：每筆紀錄都存前一筆的雜湊，自己的雜湊再把前一筆的雜湊算進去：

hash[i] = SHA-256( hash[i-1] + 標準化 JSON(紀錄 i) )      hash[-1] = 64 個 0

這個做法有三個細節，少一個就會失效。

第一是前一筆的雜湊要算進去。如果只雜湊自己的內容，攻擊者改完一筆、重算那一筆的雜湊就好，後面的不受影響。把前一筆算進去，改一筆就會一路連鎖到最後一筆，這才是「鏈」的意思。

第二是雜湊前要標準化。同一個物件 { a: 1, b: 2 } 和 { b: 2, a: 1 }，JSON.stringify 出來的字串不同。紀錄存進 PostgreSQL 的 jsonb 再讀出來，鍵的順序就可能變了，內容一個字都沒改，驗證卻會誤報竄改。所以雜湊前要依鍵名排序，巢狀物件也要遞迴排序；陣列的順序有意義，保持原樣。

第三是外部錨定（anchoring）。能寫整張表的人，可以從被改的那筆開始把後面全部重算一次，鏈又是完整的。所以要定期（例如每小時）把最新一筆的雜湊寫到另一個系統：另一個雲端帳號裡開了 Object Lock compliance 模式（保存期限內連 root 帳號都不能改、不能刪）的 S3、或另一個團隊管理的儲存。驗證時從錨點對起，攻擊者要同時攻破兩個系統。

雜湊鏈只能偵測竄改，不能防止，也不能證明紀錄「一開始就是真的」：應用程式被入侵後寫進去的假紀錄，鏈一樣完整。它的價值是讓「事後偷改」變得藏不住。

選讀到這裡，回到主線：紀錄防得了事後抵賴，接下來看攻擊進行中怎麼發現。

紀錄都寫下來了，誰會發現有人正在攻擊？

稽核紀錄回答的是事後的問題。可是攻擊進行中的時候，紀錄只是安靜地堆在資料庫裡，沒人看就等於沒有。要讓系統主動通知人，有兩種看法，要一起用。

第一種是監控指標加告警：把認證系統的健康狀況變成數字，突然變化就通知值班的人（部署課第 22 課的指標、第 25 課的告警）。它看的是整體，不用知道攻擊長什麼樣子，只要「跟平常不一樣」就會響。先舉退款的版本：上個月那種退款異常，如果有一條指標盯著「每個店員帳號的退款次數與金額」，當下就會有人收到通知，不用等月底對帳。表裡其他幾列看的是登入事件，因為大多數攻擊從登入開始，練習 3 用的也是登入事件：

指標突然變化代表什麼
每個店員帳號的退款次數與金額一小時內遠高於這個人平常的量，或退款金額大於原訂單（110 元的單退了 1,100 元）：帳號被盜或有人在套錢
登入成功率從 85% 掉到 5%：有人拿外洩的帳密清單在撞庫
每分鐘 401、403 數量有人在掃 API；或剛部署的版本把權限弄壞了
refresh token 重用偵測次數（第 10 課）平常接近 0；增加代表 token 被偷了在用
重設密碼請求量、簡訊發送量帳號列舉、簡訊轟炸、燒你的簡訊費
資料匯出次數與筆數帳號被盜後在搬資料

第二種是偵測規則（detection rule）：針對已知的攻擊樣態，在事件裡找符合條件的組合。指標告訴你「有事」，規則告訴你「是什麼事、誰在做」。登入事件常見的三種攻擊，剛好需要三種不同的看法：

  • 暴力破解（brute force）：同一個帳號短時間內大量失敗。看「每個帳號的失敗次數」就抓得到，第 16 課的每帳號逐步延遲就是在擋它。
  • 密碼噴灑（password spraying）：同一個 IP 對很多不同的帳號各試一兩次常見密碼（Coffee2026!）。每個帳號只失敗一兩次，每帳號的限制完全不會觸發，要用「一個來源碰了幾個不同帳號」來抓。
  • 撞庫（credential stuffing）：拿別的網站外洩的帳密，用大量 IP 分散嘗試。單一 IP 和單一帳號都看不出來，要看整體的成功率，也就是上面的指標。

規則一定有誤報：公司或學校的出口 IP 後面有幾百個人，下課時間大家同時打錯密碼，看起來也像噴灑。所以偵測規則觸發的是告警和額外驗證（要求 CAPTCHA、要求 MFA），而不是直接封鎖；門檻也要用過去的資料調整。練習 3 會把暴力破解和噴灑這兩條規則寫出來。

💡 實務上：每條告警都要能回答「收到之後要做什麼」
告警太多、大半是誤報，值班的人很快就會習慣性忽略，真的出事那一條也一起被略過。所以一開始只開少數幾條：登入成功率驟降、refresh token 重用、匯出量異常。每條告警附上處理步驟的連結（就是下一節的劇本），並分級：要半夜叫醒人的，和隔天上班再看的分開。每次誤報都回頭調門檻或刪掉那條規則，而不是叫大家忍耐。

告警響了之後，值班的人要知道下一步做什麼，而凌晨三點不是開始思考的好時機。這就是老闆要求的最後一件事。

凌晨三點告警響了，先做哪一步？

發現資安事件後的處理叫事故應變（incident response）。出事時人會慌，會漏步驟，也會做錯順序，所以要事先寫好劇本（playbook）：每種事故的步驟、誰負責、要找誰，平常還要演練。各種劇本共通的原則是先止血，再調查：外洩的東西多活一分鐘，攻擊者就多用一分鐘；調查可以晚一點做，止血不行。下面是認證系統最常見的三種，每一種的第一步都是止血。

(a) JWT 簽章金鑰外洩

HS256 的 JWT_SECRET 被推到公開 repo，任何人都能簽出 sub 是店長的 access token。

  1. 產生新金鑰，放進 secret 管理（第 23 課），部署成用新金鑰簽發。
  2. 停止接受舊金鑰：驗證端把舊金鑰拿掉。這一步之後所有舊的 access token 都失效，使用者要用 refresh token 換新的；如果 refresh token 是存在資料庫的隨機值（第 10 課），它沒被影響，使用者不用重新登入；如果 refresh token 也是同一把金鑰簽的 JWT，就要撤銷全部、讓所有人重新登入（第 11 課）。
  3. 查 log：金鑰外洩後到換掉之間，有沒有不是你簽發的 token 被使用。只靠簽章分不出來，因為攻擊者拿到金鑰，簽出來的 token 跟你簽的一模一樣。每張 JWT 可以帶一個 jti claim，是簽發時產生的唯一編號（第 8 課）。平常就在簽發時把 jti 記下來，驗證時查到從沒記過的 jti，就表示這張 token 不是你簽的。
  4. 找出外洩原因：為什麼 secret 會進 repo？加上 secret scanning（部署課第 11 課的 gitleaks）。刪掉 commit 是最後才做的清理，不是第一步：公開過的東西已經被 fork、被快取、被掃描機器人抓走了。

(b) 資料庫外洩

  1. 評估範圍：哪些表、哪段時間的資料、透過什麼方式拿走的；先把入口關掉（撤銷被盜的資料庫帳密、修漏洞）。
  2. 讓偷走的憑證失效：資料庫裡如果有明文的 session ID、refresh token、API key，攻擊者可以直接拿來用，全部撤銷。只存 SHA-256 的高熵 token（第 10、17 課）反推不回來，風險低很多，但保守起見還是輪替。
  3. 密碼：argon2id 讓每次猜測變慢，但「12345678」「coffee2026」這種弱密碼一樣會被猜到。依雜湊的強度決定：至少通知所有人並要求下次登入改密碼，舊的 MD5／SHA-1 雜湊就要強制重設。
  4. 依法通報與通知當事人：台灣的個人資料保護法、有歐盟使用者時的 GDPR，都規定了要通知誰、多快通報（條文與期限見課末「補充與查表」）。這一步交給法務，工程師要提供範圍、時間、資料種類。

(c) 帳號被盜

  1. 撤銷那個人所有 session 與 refresh token（第 11 課的 token 版本加 1），撤銷他建立的 API key。
  2. 重設密碼，檢查 email、手機、MFA、passkey、OAuth 連結有沒有被改；攻擊者常先加一把自己的 passkey 或改 email，密碼改回來他還是進得去。
  3. 用稽核紀錄查被盜期間做了什麼：下了哪些單、用了多少儲值金、匯出了什麼，決定要不要退款或通知受影響的人。前面花力氣補上的稽核紀錄，就是在這一步回本。

相依套件被植入惡意程式的劇本不限於認證系統，放在課末「補充與查表」。

事後檢討：回到威脅模型

處理完之後寫事後檢討（postmortem）（部署課第 25 課）：時間軸、影響範圍、根本原因、哪些事做得好、要改的流程與系統，每一項有負責人和期限。原則是不究責（blameless）：「工程師把 secret 推上去」不是根本原因，「沒有 pre-commit 掃描、secret 能直接寫在設定檔裡」才是。追究個人只會讓下一次大家隱瞞，而且換一個人一樣會發生。拿開場那筆退款來說，要檢討的不是「哪個店員可疑」，而是「為什麼三個人共用帳號、為什麼退款沒有紀錄」。

檢討的最後一步，是回到這課的起點：這次的事故，威脅模型裡有沒有？沒有的話補上。威脅模型、稽核紀錄、偵測、劇本就這樣接成一個循環，每出一次事，下一次上線前就多想到一件事。

補充與查表

主線用不到、但做威脅模型、設計 log 或寫劇本時會查的細節。

威脅建模與 OWASP Top 10:2025

威脅建模找的是設計上的問題，例如「退款 API 誰都能呼叫」「webhook 沒驗簽章」。程式寫錯（少了一個 await）要靠測試和 code review。OWASP Top 10:2025 把這類問題歸在 A06 Insecure Design；記錄與告警不足則是 A09 Security Logging and Alerting Failures。

log 注入

結構化 log（JSON）還有一個好處：擋 log 注入（log injection）。純文字 log 一行一筆，攻擊者在帳號欄位填「x\n2026-10-31 登入成功 admin」，就能偽造一行假紀錄。JSON 會把換行跳脫成 \n，偽造不了新的一筆。

資料外洩的通報規定

台灣的個人資料保護法第 12 條要求通知當事人（2025 年 11 月修正的條文再加上向主管機關通報，施行日期由行政院另定）；有歐盟使用者時，GDPR 第 33 條要求知道後不無故拖延、可行時 72 小時內通報主管機關（不太可能危害當事人權利的除外）。

劇本 (d)：相依套件被植入惡意程式

  1. 確認受影響的版本與時間，鎖住已知安全的版本，檢查 lockfile 裡實際安裝的是哪一版（Node 課第 3 課、第 25 課）。
  2. 惡意版本裝過的機器（開發者電腦、CI）都當成被入侵：輪替那些環境碰得到的所有 secrets，包括 CI 的部署金鑰、npm token、雲端帳號的金鑰。
  3. 重建映像、重新部署，查 log 有沒有往外的可疑連線。

練習

練習 1：寫 scrubSecrets(text)，在 log 訊息寫出去之前，把字串值裡的秘密換掉。依序處理：

  1. 網址 userinfo 裡的密碼：postgres://app:secret@db:5432/cafe → postgres://app:[REDACTED]@db:5432/cafe（帳號保留）。
  2. 網址查詢參數 code、state、token、access_token、refresh_token、password 的值 → [REDACTED]，參數名稱要完全相同才算（前面是 ? 或 &；codes=1、mytoken=2 不動），值到 &、# 或空白為止，其他參數原樣保留。
  3. 第 17 課格式的 API key：cafe_live_ 或 cafe_test_ 加剛好 36 個 base62 字元 → 保留前綴，其餘換成 [REDACTED]；長度不對的不是 key，不動。
  4. Bearer（大小寫不拘，HTTP 的認證方案名稱不分大小寫）後面的 token → Bearer [REDACTED]，原本的大小寫保留，token 一個字元都不能留下。
  5. 三段 base64url、前兩段都以 eyJ 開頭的 JWT → [JWT]。

其他文字（包含中文）一個字都不能改。測試會丟 50,000 字元的病態輸入，要在 200 毫秒內處理完：不要用巢狀量詞。

練習 2（選讀）：做一條改了會被發現的稽核紀錄（對應選讀節「雜湊鏈」，跳過不影響其他練習）。完成三個函式：

  • canonicalJson(value)：物件依鍵名排序（用陣列的 sort()）、巢狀物件遞迴處理，陣列保持順序，其他值用 JSON.stringify。
  • appendAudit(chain, data)：回傳新的陣列（不改傳入的 chain），最後多一筆 { data, prevHash, hash }：prevHash 是前一筆的 hash，第一筆用 GENESIS（64 個 0）；hash = sha256Hex(prevHash + canonicalJson(data))。
  • verifyChain(chain)：從頭檢查每一筆的 prevHash 和 hash，全部正確回 { ok: true }，否則回 { ok: false, brokenAt }，brokenAt 是第一筆不對的索引。

練習 3：寫偵測規則 detectAttacks(events, now)，now 和 at 都是毫秒：

  • 只看最近 15 分鐘：at > now - 900000，剛好 900000 毫秒前的不算。成功的登入（ok: true）不算。
  • 同一個 IP 對 10 個以上不同帳號失敗 → { kind: 'password_spraying', ip }。
  • 同一個帳號失敗 20 次以上（不管從哪些 IP）→ { kind: 'brute_force', account }。
  • 同一個警報只出現一次。結果先依 kind、再依 ip 或 account 的字串順序排序。不要改傳入的 events。

練習 4：店員陳美華說「那筆 1,100 元的退款不是我做的」，系統裡只看得到 POS 帳號 store-01 有登入。用 STRIDE 來看，系統缺的主要是哪一類的防護？

✓ b。「做了卻賴得掉」就是否認。有登入只代表「有人用 store-01 登入過」，三個店員共用帳號時誰做的都說不清；就算有個人帳號，沒有記下退款事件、或紀錄能被改，一樣無法舉證。a 的 MFA 防的是偽冒，不會留下「誰退了哪筆」的紀錄。c 店員能不能退款是業務決定，可以用金額上限處理，但這題要回答的是「事後怎麼證明」。d 沒有證據顯示金額被竄改。

練習 5：工程師把含有 HS256 JWT_SECRET 的 .env 推到了公開的 GitHub repo，十分鐘後才發現。第一步該做什麼？

✓ c。公開的 secret 要當成已經被拿走：掃描公開 repo 的機器人通常幾分鐘內就會抓到，fork 和快取也刪不掉。只要舊 secret 還被接受，任何人都能簽出店長的 token，所以先換掉、停用舊的，代價是使用者要用 refresh token 換新的 access token（必要時重新登入）。a、b 是之後的清理，不能讓已經外洩的 secret 失效。d 查 log 很重要，但查的時候攻擊者還能繼續偽造，要在換金鑰之後做。

練習 6：會員資料庫被整份拿走，密碼是用 argon2id（OWASP 建議的參數）存的，refresh token 只存 SHA-256，但 sessions 表存的是 session ID 原文。下面哪個處理最完整？

✓ d。session ID 原文可以直接拿來登入，不需要破解，要立刻全部失效；refresh token 只存雜湊，風險低，但保守起見一併輪替。argon2id 只是讓每次猜測變慢，coffee2026 這種弱密碼一樣會被字典猜到，所以 a 錯。b 只處理了密碼，攻擊者手上的 session ID 不用密碼就能直接登入。c 改的是你這邊的資料，攻擊者手上那份舊雜湊不會變。另外別忘了先找出入口並關掉，否則換完的東西會再被拿走一次。

練習 7：同事說「log 只有我們工程師看得到，記完整的 refresh token 方便除錯」。哪個回應最正確？

✓ a。log 是全公司複製最多份的資料：log 平台、告警通知、Slack 截圖、備份、廠商支援工單，每一份都是外洩點，而且很少有人把 log 存取當成敏感權限管理。refresh token 的效期以週計，拿到就能一直換新的 access token。b 的加密只防路上被偷聽和硬碟被拿走，有權限讀 log 的人看到的還是明文。c 的 access token 雖然短效，期限內一樣能直接用，也不能記。d 七天內誰讀到都能用；而且刪掉的是 log，不是 token。

常見錯誤

  • 威脅模型做一次就丟著：系統一直在變，模型半年後就沒用了。放進 repo，架構改變的 PR 與事故檢討時一起更新。
  • 每個威脅都想修，或都不決定：用可能性 × 影響排序，每一條明確寫下緩解、消除、轉移或接受；接受要有人負責、有重新檢視的日期。
  • log 記太少：出事時查不到誰、從哪裡、做了什麼。登入、權限變更、匯出、退款都要有稽核事件，帶著主體、目標、結果、IP、request id。
  • log 記太多：密碼（包括輸錯的）、token、session ID、API key、OAuth code 寫進 log。這些都不記，要追蹤就記雜湊前幾碼。
  • 只依欄位名稱遮罩：錯誤訊息裡的完整網址、連線字串、Authorization 標頭照樣進 log。寫出去之前用秘密的格式再掃一次字串值，正規表示式不要有巢狀量詞。
  • 稽核紀錄可以被應用程式帳號修改或刪除：拿掉 UPDATE、DELETE 權限，加上雜湊鏈，定期把最新雜湊錨定到另一個系統。
  • 雜湊前沒有標準化 JSON：資料存進 jsonb 再讀出來鍵的順序變了，驗證就誤報。鍵要遞迴排序。
  • 噴灑只看失敗次數或只做每帳號限制：噴灑每個帳號只試一兩次。要看同一個來源碰了多少不同帳號。
  • 偵測規則直接封鎖：共用出口 IP 會誤報，把整間公司鎖在外面。先告警、加驗證，再依資料調整門檻。
  • 金鑰外洩時先刪 commit：外洩的 secret 已經被複製走了。先換掉、停用舊的，再查 log、再清理。
  • 沒演練過劇本，出事才開始想：誰有權限換金鑰、怎麼讓所有 session 失效、要通知誰，事先寫好並演練。
  • 事後檢討追究個人：下一次大家只會隱瞞。找出讓錯誤能發生的流程與系統，每一項改善都有負責人與期限。

小結

  • 開場那筆查不出是誰做的退款，問題出在設計而不是程式：沒有人在動手前問過「可能出什麼錯」。威脅建模就是回答四個問題：我們在做什麼、可能出什麼錯、要怎麼處理、做得夠好嗎。在設計時、架構改變時、事故之後做。
  • 畫 DFD（外部實體、程序、資料存放、資料流、信任邊界），對每個元件與跨邊界的資料流用 STRIDE 逐一問：偽冒、竄改、否認、資訊洩漏、阻斷服務、權限提升。共用帳號的退款落在「否認」：要個人帳號、稽核紀錄、紀錄改不了三樣一起。
  • 風險 = 可能性 × 影響；每個威脅明確決定緩解、消除、轉移或接受，寫進設計文件。
  • 稽核紀錄記安全事件與主體、目標、結果、IP、request id；不記密碼、token、session ID、金鑰、連線字串。欄位名稱遮罩之外，再依秘密的格式掃字串值，正規表示式不用巢狀量詞。
  • 防竄改：資料庫權限只給 INSERT，稽核表的擁有者是另一個角色；（選讀）雜湊鏈要標準化 JSON、把前一筆的雜湊算進去，並外部錨定。
  • 偵測靠指標告警加規則：暴力破解看同一帳號的失敗次數，密碼噴灑看同一來源的不同帳號數，撞庫看整體成功率。規則觸發告警與額外驗證，不直接封鎖。
  • 事故應變先止血再調查：金鑰外洩先換金鑰、資料庫外洩先讓憑證失效、帳號被盜要檢查 email 與 MFA、套件被植入要輪替 CI 的 secrets；最後寫不究責的事後檢討，回頭更新威脅模型。
