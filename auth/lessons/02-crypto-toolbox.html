階段 1：地基：身分、信任與密碼學工具 · 第 2 課

密碼學工具箱：編碼、雜湊、HMAC 與安全亂數

咖啡店的線上點餐上線第一週，客服收到一張截圖：一位顧客說他打開 DevTools，把 cookie 的值從 cart:41 改成 cart:42，重新整理之後，看到的是陳美華的購物車，裡面有一杯拿鐵和一塊起司蛋糕。原因很單純：伺服器把購物車編號直接放在 cookie 裡，收到什麼編號就拿哪一台購物車。第 1 課說過，cookie 是客戶端的資料，每個位元組都在使用者手上，他想改成什麼都可以。

團隊開會討論修法，冒出四個提案：「把 42 用 base64 編一下，使用者就看不懂了」「在後面附一段 SHA-256 當檢查碼」「編號改用 Math.random() 產生的亂碼」「附上簽章，伺服器收到時重算一次，用 === 比對」。每一個聽起來都合理，每一個都是真實系統出過的漏洞。

這一課的任務：把購物車 cookie 改成使用者改不了、也猜不到別人的。我們依序檢查這四個提案，看每一個缺了什麼，過程中用瀏覽器與 Node 都內建的 Web Crypto 親手做出編碼、雜湊、安全亂數、HMAC 與常數時間比較。這些工具之後每一課都會用到：存密碼要雜湊、session ID 要安全亂數、cookie 和 JWT 要簽章、比對 token 要常數時間。

這課的路線：
  1. 「base64 之後就看不懂了」為什麼擋不住：編碼、雜湊、HMAC、加密、簽章各保護什麼；開場問題的最小答案是用只有伺服器知道的金鑰替 cookie 算一段 HMAC 標籤。
  2. 簽章是位元組，怎麼放進 cookie：密碼學函式只收位元組，字串要先轉 UTF-8，結果再編成 hex 或 base64url。
  3. 附上 SHA-256 當檢查碼、用亂數當編號：雜湊為什麼擋不住沒有秘密的竄改，秘密要用 CSPRNG 產生、要有多少熵才猜不到。
  4. 用 HMAC 簽出 cart:42.簽章，收到時用常數時間比對：為什麼不能 SHA-256(秘密 + 訊息)，為什麼不能用 ===。
  5. 上線前整理：完整的簽章 cookie 流程，哪些交給平台內建的實作，為什麼不要自己發明密碼學。
這課會用到：
  • Node 課第 11 課的編碼：同一串位元組可以寫成 hex 或 base64，只是換表示法。這課用瀏覽器與 Node 都有的 Uint8Array 裝位元組（Node 的 Buffer 是它的子類別）。
  • TypeScript 課第 9 課的 async/await：await 等 Promise 有結果再往下，crypto.subtle 每個操作都回傳 Promise。
  • 第 1 課的信任邊界：從客戶端回來的資料都不能相信，簽章讓伺服器能確認它沒被改過。

「base64 之後就看不懂了」，為什麼還是擋不住？

第一個提案最省事：cookie 不放 cart:42，改放它的 base64，Y2FydDo0Mg==。使用者打開 DevTools 只看到一串亂碼，好像就不知道該改哪裡了。

問題是 base64 沒有任何秘密。它是一套公開的轉換規則，瀏覽器內建的 atob('Y2FydDo0Mg==') 一行就還原成 cart:42；攻擊者改成 cart:43，再用 btoa 編回去，伺服器解開之後拿到的就是 43。結尾的 == 和固定的字元集，讓有經驗的人一眼就認得出這是 base64。「看不懂」只擋得住沒有試過的人。

這個提案的錯，在於把編碼當成保護。編碼、雜湊、HMAC、加密、簽章這五樣東西，都會把資料「變成一串看不懂的字」，所以常被混為一談；但它們保護的東西完全不同。要比較它們，先認識三組詞：

  • 金鑰（key）是一串只有授權的一方知道的秘密位元組。有沒有用到金鑰，決定了攻擊者能不能自己做出同樣的結果。
  • 保護資料可以保護三件不同的事。機密性是別人看不到內容；完整性是內容沒被改過；來源是能確定這份資料是誰產生的。
  • 私鑰與公鑰是一對一起產生的金鑰：私鑰自己留著，公鑰可以公開給所有人。私鑰做出來的東西，任何人都能用公鑰核對。第 8 課詳講。
工具比喻要金鑰嗎能還原嗎保護什麼咖啡店的例子
編碼（encoding）換成摩斯密碼不用任何人都能什麼都不保護，只是換表示法把位元組放進網址、JSON
雜湊（hash）指紋不用不能完整性：內容有沒有變檢查下載的檔案、存 token
HMAC蠟封印章（共用一枚）要，雙方同一把不需要還原，內容本來就看得到完整性＋來源：是持有金鑰的人產生的簽名的 cookie、webhook
加密（encryption）上鎖的保險箱要有金鑰才能機密性：別人看不到內容資料庫裡的身分證字號（第 23 課）
簽章（signature）只有你有的印章，大家都能核對要，私鑰簽、公鑰驗不需要還原完整性＋來源，而且驗的人簽不出來JWT 的 RS256／ES256（第 8 課）、passkey

用這張表回頭看購物車。購物車編號被看到沒有關係，42 本身不是秘密，所以我們要的不是機密性。我們要的是伺服器收到 cookie 時能確認兩件事：值沒被改過（完整性），而且是伺服器自己發出去的（來源）。表裡做得到這兩件事的是 HMAC 和簽章。簽章的特點是「驗的人簽不出來」，適合簽的人和驗的人是不同單位的情況；購物車 cookie 是伺服器自己發、自己驗，用一把共用金鑰的 HMAC 就夠了。

HMAC 是把金鑰和訊息一起丟進雜湊、算出固定長度一段位元組的方法，這段結果叫標籤（tag）；沒有金鑰就算不出正確的標籤。它內部怎麼運作、為什麼安全，第 4 節再講。

叫法先說好：Web Crypto 的 API 叫 sign／verify，程式碼和這課後面也把「用 HMAC 算出標籤」叫做簽章；這課說的「簽章 cookie」「比對簽章」都是 HMAC 標籤。表格裡的「簽章」專指私鑰簽、公鑰驗那種，第 8 課才會用到。

以下用陳美華的購物車 cart:42 當例子：伺服器發給她的 cookie 是 cart:42.標籤，攻擊者想改成別的編號。開場問題的最小答案是：伺服器準備一把只有自己知道的金鑰，發 cookie 時用它對 cart:42 算出一段 HMAC 標籤，接在值後面一起發出去，例如 cart:42.Kx3…。收到 cookie 時，用同一把金鑰對前半段重算一次，跟後半段對不上就當作沒有購物車。使用者還是看得到 42、也改得了 42，但改了之後他算不出對應的標籤，因為他沒有金鑰。

這一課要做的，就是把這段話裡的每一步做對。我們用的是 Web Crypto：瀏覽器與 Node 都內建的密碼學 API，入口是 crypto.subtle，每個操作都回傳 Promise，所以範例裡都要 await。同一份程式在前端和後端都能跑。加密與公鑰簽章這課不做，留到後面的課。

動手之前有一個基本問題要先解決：HMAC 算出來的標籤是什麼形狀，又要怎麼塞進 cookie？

簽章是一串位元組，要怎麼放進 cookie？

上一節的最小答案說「把標籤接在值後面」，但 Web Crypto 算出來的標籤不是字串，它的函式也不收字串。密碼學函式處理的是位元組（byte），所以我們得先學會在字串和位元組之間來回。

一個位元組是 0～255 的數字。電腦裡所有資料最後都是一串位元組，文字、圖片、簽章都一樣。JavaScript 用 Uint8Array 裝一串位元組：外表像陣列，可以用索引讀寫、可以用 for…of 走過，但每一格只能放 0～255 的整數。

字串要先轉成位元組。問題是「拿」這個字要變成哪幾個數字？這需要一套大家都同意的對照規則，現在網路上通用的規則叫 UTF-8：英文字母、數字、空白各佔 1 byte，中文字通常 3 bytes，emoji 3～4 bytes。規則必須一致，因為同一個字串用不同規則轉出來的位元組不同，算出來的雜湊和簽章也就不同；發 cookie 的程式和驗 cookie 的程式只要用的規則不一樣，正確的簽章也會被判成錯的。JavaScript 內建 TextEncoder 把字串轉成 UTF-8 位元組，TextDecoder 把位元組轉回字串。

反方向也有問題。HMAC 標籤是 32 個 0～255 的數字，裡面有很多不是可見字元的值，例如 0 或 10（換行），不能直接放進網址、JSON、cookie 這些只收文字的地方。所以要把位元組編碼成文字。這就是上一節表格第一列「編碼」真正的用途：它不保護任何東西，只負責讓位元組能放進文字的地方。常用的有三種：

  • hex：每個 byte 寫成兩個 16 進位字元，例如 15 寫成 0f、230 寫成 e6。長度變成 2 倍，但好讀、好比對，雜湊值通常用它顯示。
  • base64：把每 3 bytes（24 bits）切成 4 段 6 bits，每段對應一個字元，所以長度只多三分之一，比 hex 短。字元集是 A-Z a-z 0-9 + / 共 64 個；位元組數不是 3 的倍數時，在結尾補 = 讓長度湊成 4 的倍數。
  • base64url：把 + 換成 -、/ 換成 _，再拿掉結尾的 =。原因是這三個字元在網址裡各有用途：/ 分隔路徑，= 分隔查詢字串的名稱與值，+ 在表單格式的查詢字串裡代表空白。換掉之後，字串可以原樣放進網址和 cookie，不必再跳脫。JWT（第 8 課）、PKCE（第 12 課）、passkey（第 15 課）都用它，我們的購物車標籤也會用它。

hex 那一行的 padStart(2, '0') 也不能省。(15).toString(16) 是 'f'，只有一個字元；不補 0 的話，hex 長度就不是位元組數的 2 倍，而且 [1, 15] 和 [31] 都會寫成 '1f'，兩個不同的位元組陣列得到同一個 hex，拿它比對雜湊就會出錯。

寫 TypeScript 時還有一個型別細節：自己寫的函式要把位元組傳給 crypto.subtle，參數型別寫 Uint8Array<ArrayBuffer>，只寫 Uint8Array 會報 TS2345。練習裡的函式都照這個寫法，原因與示範見課末「補充與查表」。

現在任何位元組都能放進 cookie 了。回到會議桌上的第二個提案：在 cart:42 後面附一段 SHA-256 當檢查碼，伺服器收到時重算一次，對不上就拒絕，這樣擋得住嗎？

附上 SHA-256 當檢查碼，能擋住竄改嗎？

要回答這個提案，先弄清楚 SHA-256 是什麼。它是一種雜湊函式（hash function）：把任意長度的輸入，變成固定長度的一串位元組，這串結果叫摘要（digest）。不論輸入是兩個字還是一部電影，SHA-256 的摘要都是 32 bytes，寫成 hex 是 64 個字元。

好的雜湊函式有四個性質，每一個都對應一種用途：

  1. 同樣的輸入，一定得到同樣的摘要。所以兩個人各算一次就能比對，伺服器也能事後重算。
  2. 不能從摘要反推輸入。手上只有摘要的人，沒辦法用計算把原文還原。
  3. 很難找到兩個不同的輸入得到同一個摘要。這種情況叫碰撞（collision）。如果碰撞容易找到，攻擊者就能準備一份內容不同、摘要卻一樣的假檔案。
  4. 輸入改一點點，摘要整個變掉。所以多一個空白、少一個字都看得出來。

最常用的是 SHA-256。較舊的 MD5 和 SHA-1 已經能被製造出碰撞，違反第 3 個性質，新系統不要用。下面這格算三次摘要，執行後比較三行：第一行和第三行輸入相同，摘要一樣；第二行只多了一個空白，摘要完全不同。

這四個性質讓雜湊很適合當「內容有沒有變」的檢查碼。現在套回購物車：伺服器發出 cart:42 加上 SHA-256('cart:42')，收到時重算一次比對。使用者只改 42 不改摘要，確實會被抓到。

但攻擊者不會只改一半。SHA-256 是公開的演算法，不需要金鑰，任何人都能算：他把值改成 cart:43，自己算出 SHA-256('cart:43') 一起換上去，伺服器重算的結果完全吻合。雜湊只能證明「內容和這個摘要一致」，不能證明「這個摘要是伺服器算的」。當內容和摘要放在同一個地方，攻擊者可以兩個一起換，檢查碼就失去作用。雜湊要發揮防竄改的效果，摘要必須來自攻擊者碰不到的地方，例如事先存在伺服器上；cookie 裡的摘要不符合這個條件。

「不能反推」不等於「猜不到」

會議上還有人提了變形：cookie 不放 42，改放 SHA-256('42')，反正雜湊不能反推，使用者就不知道自己是幾號，也不知道別人的該怎麼填。

雜湊不能反推，但攻擊者可以猜：把每一個可能的輸入都算一次摘要，跟手上的比對，一樣就找到了。這種做法叫列舉。輸入的可能性越少，列舉越快。購物車編號從 1 開始往上加，跟 4 位數 PIN 一樣只有很少的可能。下面用 PIN 示範：假設資料庫外洩，攻擊者只拿到 0427 的摘要，試完一萬種要多久。執行後看最後一行花了幾毫秒：

一萬種可能，一眨眼就找完了；購物車編號的雜湊也一樣，算出 1 到 10 萬的摘要再比對就好。手機號碼（台灣 09 開頭只有一億種）、身分證字號、生日也是同一個道理：雜湊之後不算匿名，一台電腦很快就能全部列舉。密碼的可能性其實也不多，大部分人用的是常見密碼，所以存密碼不能只用 SHA-256，要用刻意很慢的雜湊，這是第 3 課的主題。

💡 實務上：SHA-256 最常用來「確認內容一樣」
工作中最常碰到雜湊的地方是比對內容：咖啡店後台上傳商品圖片時，用檔案的 SHA-256 當檔名，同一張圖傳兩次只會存一份；package-lock.json 裡的 integrity 欄位也是雜湊，確保裝到的套件沒被換掉。要注意雜湊只證明「和你手上的摘要一樣」，摘要本身如果跟檔案放在同一個地方，攻擊者可以一起換掉，這時就需要後面的 HMAC 或簽章。行銷或資料團隊想「把手機號碼雜湊後交給廠商」時，資深工程師會先指出這不算去識別化，再一起討論對方到底需要什麼欄位。

兩個雜湊提案輸在同一點：演算法是公開的，伺服器算得出來的，攻擊者也算得出來。伺服器需要一樣攻擊者沒有的東西，也就是一個秘密。秘密要怎麼產生，才不會被猜到？

秘密要怎麼產生，攻擊者才猜不到？

上一節的結論是伺服器需要一把金鑰，而金鑰就是一串攻擊者猜不到的位元組。會議上的第三個提案也繞到同一件事：把購物車編號 42 換成一串亂碼，別人就猜不到其他人的編號。兩條路都要「猜不到的亂數」，差別只在亂數拿來當金鑰還是當編號。session ID、重設密碼連結裡的 token、第 6 課要做的 CSRF token 也一樣，安全性全靠攻擊者猜不到。

猜不到靠兩件事：亂數的來源夠好，長度夠長。先看來源。

第三個提案用的 Math.random() 不能用。電腦上的程式本身沒有真正的隨機，Math.random 這類函式叫偽亂數產生器：它內部保存一組數字當作狀態，每次呼叫就用固定的演算法把狀態往前推一步，再從狀態算出一個看起來隨機的數。同樣的狀態一定產生同樣的序列。Chrome 與 Node 用的 JavaScript 引擎叫 V8，V8 的 Math.random 用的是 xorshift128+ 演算法，設計目標是快和分布均勻，不是保密：攻擊者看到足夠多的輸出，就能算出內部狀態，預測接下來的每一個值。實際的攻擊是攻擊者自己先開幾台購物車、拿到幾個編號，推出狀態之後，接下來發給別人的編號他全都算得出來。Date.now() 和自動遞增的 ID 更直接，猜個範圍就中。

當秘密用的亂數，要來自密碼學安全亂數產生器，英文是 cryptographically secure pseudo-random number generator，常縮寫成 CSPRNG。它的保證正好補上 Math.random 缺的那一塊：看過再多輸出，也推不出下一個。瀏覽器與 Node 的 CSPRNG 入口都是 crypto.getRandomValues()，它把傳進去的 Uint8Array 每一格都填上亂數，再把同一個陣列回傳。

接著看長度。長度夠不夠用熵（entropy）衡量。熵描述「有多少種可能」，單位是 bits：n bits 的熵代表有 2n 種同樣可能的值，攻擊者平均要試一半才猜中。用 bits 算的好處是可以直接相加，多 1 bit 可能性就多一倍。常用的算法有兩種：

  • 每個字元從 k 種字元中隨機挑，長度 L：熵 = log2(k) × L。4 位數 PIN 每位有 10 種，熵是 log2(10) × 4 ≈ 13 bits，也就是上一節一萬種、一眨眼就試完的那個大小。
  • 直接用隨機位元組：每個 byte 有 256 種，正好 8 bits，32 bytes 就是 256 bits。

那要多少才夠？OWASP（一個整理網站資安實務的開放社群）建議 session ID 至少 64 bits，自己產生時至少 128 bits。這門課的 token 一律用 32 bytes，也就是 256 bits，簡單好記，也遠超過任何人能試完的範圍。下面這格產生一個 32 bytes 的 token，用上一節的方法編成 base64url。執行後比較 Math.random 那一行和 token 那一行，再看長度和熵：

32 bytes 是 256 bits，base64url 每個字元裝 6 bits，256 ÷ 6 無條件進位是 43 個字元。要注意熵算的是亂數來源，不是字串長度：用 Math.random 湊出 43 個字元，長度一樣，熵卻遠低於 256 bits，因為整串都由一個可預測的內部狀態決定，猜中狀態就猜中整串。

最後一行的 crypto.randomUUID() 也來自 CSPRNG，但 UUID 的 128 bits 裡有 6 bits 是固定的版本標記，只有 122 bits 隨機。拿它當購物車編號、訂單 ID 夠用；當作秘密的 token，用 32 bytes 的 getRandomValues 意圖比較清楚。

回到購物車。用 CSPRNG 產生的亂碼當編號，確實讓別人的購物車猜不到。但這條路有代價：cookie 裡只剩一串沒有意義的亂碼，伺服器必須另外存一張「亂碼 → 購物車」的對照表，每個請求都去查。這正是 session 的做法，第 4 課會完整走一次。另一條路是簽章：cookie 照樣放 cart:42，再附上一段只有伺服器簽得出來的標籤，伺服器不用存任何東西，看標籤就知道值沒被改過。這課走第二條路，而它需要的就是一把用 CSPRNG 產生的 32 bytes 金鑰。

💡 實務上：凡是「連結裡的秘密」都要用 CSPRNG
重設密碼信、邀請同事加入咖啡店後台的連結、優惠券兌換碼、API key，都是拿到就能用的秘密，產生方式和 session ID 一樣要用 crypto.getRandomValues。Code review 時看到 Math.random、Date.now() 或流水號出現在產生 token 的地方，就該直接提出來。反過來，訂單編號、商品 ID 這種公開的識別碼不需要保密，用資料庫 ID 或 UUID 就好，不必每樣都用 32 bytes；但別人猜得到編號，所以查詢時一定要檢查「這筆訂單是不是你的」（第 19 課）。資深工程師還會接著問：這個 token 多久過期、用過一次後是否作廢、資料庫裡存的是原文還是雜湊，這些會在後面的課逐一處理。

手上有了金鑰，下一步是把它和 cart:42 結合，做出攻擊者算不出來的標籤。

有了金鑰，怎麼替 cart:42 簽章？

把金鑰和訊息結合成標籤的標準工具是 HMAC，全名 Hash-based Message Authentication Code，意思是「用雜湊做出來的訊息驗證碼」。它的輸入是一把金鑰和一段訊息，輸出是一段固定長度的標籤；用 SHA-256 當底層雜湊時，標籤是 32 bytes。HMAC 保證的是：沒有金鑰的人，就算看過再多組「訊息與標籤」，也算不出新訊息的正確標籤。伺服器用同一把金鑰對收到的訊息重算一次，跟收到的標籤一樣，就知道訊息沒被改過，而且是持有金鑰的人產生的。這正是上一節雜湊檢查碼缺的那一塊。

在 Web Crypto 裡，金鑰不是直接傳位元組，而是先包成一個 CryptoKey 物件。建立的方法是 crypto.subtle.importKey，五個參數依序是：

  1. 金鑰位元組的格式，'raw' 表示直接給原始位元組。
  2. 金鑰位元組本身。
  3. 演算法，這裡是 { name: 'HMAC', hash: 'SHA-256' }，也就是底層用 SHA-256 的 HMAC。
  4. 能不能再匯出。給 false 之後，就算程式其他地方拿到這個物件，也不能用 exportKey 取回原始位元組。
  5. 這把金鑰的用途，例如 ['sign', 'verify']。

演算法和用途在建立時就決定，之後不能拿去做別的事。這是刻意的限制：一把金鑰只做一件事，程式寫錯時會直接報錯，而不是默默用錯演算法。

crypto.subtle.sign 算出標籤，crypto.subtle.verify 用同一把金鑰重算並比對，回傳 true 或 false。攻擊者把 42 改成 43，手上的標籤還是 42 的，又沒有金鑰算出 43 的標籤，驗證就失敗。開場的漏洞到這裡補上了。

再看一次發出去的 cookie：前半段 cart:42 還是明文。HMAC 只保證完整性與來源，不會把內容藏起來，任何人都看得到。對購物車編號來說這沒有問題；但如果有人想把會員等級、手機號碼這類不想讓人看到的資料放進「只有簽章」的 cookie 或 JWT，就錯了。要保密就要加密。

為什麼不用 SHA-256(秘密 + 訊息)？

有了金鑰，很多人的第一個寫法不是 HMAC，而是把秘密接在訊息前面一起雜湊：SHA-256(秘密 + 'cart:42')。這樣有秘密參與，攻擊者不知道秘密，看起來也算不出新的摘要。

問題出在 SHA-256 的內部結構。它把輸入切成 64 bytes 一塊，一塊一塊吃進一個內部狀態，每吃一塊就更新一次狀態，最後輸出的摘要就是那個內部狀態。攻擊者在 cookie 裡看到摘要，等於拿到了「吃完 秘密 + 訊息 之後的狀態」。他可以從這個狀態接著吃自己加的資料，算出 SHA-256(秘密 + 訊息 + 填充 + 攻擊者的資料)，完全不需要知道秘密。這裡的「填充」是 SHA-256 在最後一塊補上的固定格式位元組，攻擊者只要知道總長度就能自己補出來，秘密有多長可以用試的。這種攻擊叫長度延伸攻擊（length extension attack）：攻擊者不能改掉原本的訊息，但可以在後面接上任意內容，例如 &admin=true，並附上伺服器會認可的摘要。

HMAC 的做法是雜湊兩層：先算 內層 = SHA-256(金鑰⊕ipad + 訊息)，再算 SHA-256(金鑰⊕opad + 內層)。⊕ 是 XOR，一種逐位元比較的運算，下一節會詳細用到；ipad、opad 是 HMAC 規格（RFC 2104）定好的兩個固定常數，作用是讓內外兩層混進去的金鑰不一樣。攻擊者看到的是外層的摘要，外層吃進去的是「金鑰 + 內層結果」，他接著算只會得到外層延長後的結果，接不回內層的訊息，長度延伸就失效。

你不需要自己實作這兩層，crypto.subtle.sign('HMAC', …) 就是它。要記住的是：需要「有金鑰的雜湊」時用 HMAC，不要自己把秘密和訊息拼起來。

同一套做法在購物車以外也很常見。金流商通知你「這筆付款成功了」的 webhook 請求，就是金流商和你共用一把金鑰，對請求內容算 HMAC 放在標頭裡，你收到時重算一次比對。NestJS 課第 22 課驗證金流 webhook 用的就是這個，第 17 課會做完整的 webhook 驗證。

💡 實務上：HMAC 金鑰就是整個系統的鑰匙
簽過的 cookie、有時效的下載連結、金流商的 webhook，背後都是 HMAC，安全性全押在那把金鑰上。金鑰用 CSPRNG 產生 32 bytes，放在環境變數或 secrets 管理服務，不寫進程式碼、不 commit 進 git，開發、測試、正式環境各用不同的金鑰。換金鑰時，舊金鑰簽出去的值會全部驗不過，例如所有人的購物車 cookie 失效，所以上線前要先想好：可以接受大家重新來過，還是要讓新舊金鑰並存一段時間。金鑰管理在第 23 課詳講。

範例裡的 verify 替我們做完了「重算再比對」。但會議上的第四個提案是另一種寫法：伺服器自己 sign 出正確的標籤，再用 === 跟 cookie 裡的比。這樣有什麼問題？

收到 cookie 時，比對簽章為什麼不能用 ===？

第四個提案的結果看起來沒錯：標籤一樣就是 true，不一樣就是 false。問題不在結果，而在花了多少時間。=== 比兩個字串時，是從頭一個一個字元比，遇到第一個不同就停，因為後面已經不必再看。所以前 5 個字元都猜對的標籤，比第 1 個字元就錯的標籤，多花一點點時間才得到 false。

差異只有幾奈秒，一次請求根本量不出來，網路延遲的變動大得多。但攻擊者可以對同一個猜測送幾千次請求，把回應時間取平均，隨機的網路雜訊會互相抵消，剩下的就是那幾奈秒的差。這種從回應時間的差異推測秘密的手法，叫時序攻擊（timing attack）。

下面這格用「比了幾個字元」代替時間，模擬 === 的做法。correct 是伺服器算出來的正確標籤，攻擊者不知道；他送出五個猜測，每個都比前一個多猜對一個字元。執行後看每一行的步數：

每多猜對一個字元，就多一步。攻擊者的做法是：對第一個位置試遍 64 種字元，挑出最慢的那個，就猜中了第一位；固定第一位，再去猜第二位。總共只要 64 × 長度次，而不是 64長度 次。以 43 個字元的標籤來說，前者是兩千多個猜測（每個重複送幾千次取平均），後者是一個天文數字。HMAC 本身再安全，比對的方式洩漏了答案，整套就被繞過了。

解法是常數時間比較（constant-time comparison）：不論兩邊在哪個位置不同、有沒有不同，都把每一個位置比完才給答案，花的時間只跟長度有關，跟內容無關。攻擊者量到的時間永遠一樣，就推不出任何東西。實務上有三種做法：

  • 讓 Web Crypto 比：Chrome 與 Node 的 crypto.subtle.verify 驗 HMAC 時，內部用常數時間比較。所以驗 HMAC 時不要自己 sign 再比，直接呼叫 verify，上一節的範例就是這樣寫的。
  • Node 的 crypto.timingSafeEqual(a, b)：比對兩段位元組。兩邊長度不同時它會丟錯，所以要先檢查長度。比對 API key、比對資料庫裡存的 token 雜湊，這些沒有 verify 可用的地方就用它。
  • 自己寫：用 XOR。XOR 在 JavaScript 寫成 ^，它把兩個數字逐位元比較，同一位相同得 0、不同得 1，例如 0b0101 ^ 0b0110 是 0b0011。所以兩個位元組 a ^ b 等於 0，代表它們完全相同。比對時準備一個從 0 開始的變數，每個位置都把 XOR 結果用 |= 併進去；| 是位元 OR，任一邊是 1 結果就是 1，所以只要有一個位置不同，這個變數就不會回到 0。迴圈從頭跑到尾、中間不提早離開，最後變數是 0 才算相等。練習 5 要你寫的就是這個。

長度不同時可以直接回傳 false，不必比完：標籤的長度是公開的（HMAC-SHA256 一定是 32 bytes），攻擊者本來就知道，提早離開不會洩漏秘密。

到這裡，四個提案都有了答案。最後把它們整理成上線時真正要用的做法。

上線前：哪些自己寫、哪些交給平台？

回頭看開場的四個提案，每一個都缺了一塊，而這課的工具正好各補一塊：

提案缺了什麼改成
把 42 base64 編碼編碼沒有秘密，任何人都能還原再編回去編碼只用來把位元組放進 cookie
附上 SHA-256 檢查碼沒有金鑰，攻擊者能自己算新的摘要用 HMAC，金鑰只有伺服器有
編號改用 Math.random()可以預測秘密一律用 crypto.getRandomValues，32 bytes
簽章用 === 比對比對時間洩漏猜對了幾個字元用 crypto.subtle.verify 或常數時間比較

合起來，簽章購物車 cookie 的完整流程是：

  1. 部署前：用 CSPRNG 產生 32 bytes 的金鑰，放進環境變數。伺服器啟動時用 importKey 建立 CryptoKey，設成不能匯出、只做 sign 和 verify。
  2. 發 cookie：用 TextEncoder 把 cart:42 轉成位元組，sign 出標籤，編成 base64url，組成 cart:42.標籤。
  3. 收 cookie：用最後一個 . 切開值和標籤，因為值本身可能含 .；標籤先從 base64url 解回位元組，不是合法的 base64url 就直接當作無效；再用 verify 檢查。任何一步失敗，都當作沒有購物車，不要把錯誤細節回給使用者。

練習 4 要你寫的 signValue 和 readSignedValue，就是這個流程。

這課親手寫了 base64url、常數時間比較，是為了理解它們在做什麼，不是為了在正式環境用自己的版本。正式環境的原則是：

  • 用標準演算法（SHA-256、HMAC-SHA256、AES-GCM（加密用，第 23 課）、Ed25519（公鑰簽章用，第 8 課）…）和平台內建的實作（Web Crypto、node:crypto）。這些實作經過大量檢驗，像常數時間比較這種細節都已經處理好。
  • 不要自己組合，例如「先雜湊再 XOR 一個固定值」「加密兩次比較安全」「把 base64 的字元表打亂當加密」。這些組合看起來更複雜，但沒有經過分析，通常比標準做法弱。SHA-256(秘密 + 訊息) 就是一個例子：看起來合理，卻有長度延伸攻擊。
  • 不確定時，找現成的、有人維護的做法：OWASP Cheat Sheet、官方文件、這門課後面每一課給的參數。

練習

練習 1：寫出 base64url 的編碼與解碼，再用它們寫出文字版本。

  • base64urlEncode(bytes)：位元組 → base64url 字串，不能有 + / =。
  • base64urlDecode(text)：反過來。遇到 base64url 字元集（A-Z a-z 0-9 - _）以外的字元要丟錯。
  • encodeText(s)、decodeText(t)：字串用 UTF-8 轉成位元組再編碼，中文也要能來回轉換。

練習 2：寫 sha256Hex(text)，用 UTF-8 把字串轉成位元組，算 SHA-256，回傳 64 個小寫 hex 字元。

練習 3：寫 randomToken(byteLength = 32)：用 CSPRNG 產生 byteLength 個隨機位元組，回傳 base64url 字串。再寫 entropyBits(byteLength)，回傳這麼多隨機位元組有幾 bits 的熵。base64urlEncode 已經寫好了。

練習 4：替咖啡店的 cookie 加上簽章。

  • hmacSha256Hex(key, message)：回傳 HMAC-SHA256 的 hex。
  • signValue(value, secret)：回傳 value + '.' + base64url(HMAC-SHA256)。
  • readSignedValue(signed, secret)：簽章正確就回傳原本的 value，否則回傳 null（包括沒有 .、簽章不是 base64url）。要用 crypto.subtle.verify 驗證。value 本身可能含 .，例如 'a.b'，簽章一定在最後一個 . 後面。

練習 5：寫 timingSafeEqual(a, b)：長度不同直接回傳 false；長度相同時，不論在哪裡不同，都要讀完每一個位置，用 XOR 把差異累加起來，最後才判斷。不能用 every、some、filter、join、String() 這類會提早結束或轉成字串比較的方法。

練習 6：把使用者的密碼 base64 編碼後存進資料庫，安全嗎？

✓ 編碼只是換一種表示法，沒有金鑰、沒有秘密，拿到資料的人一行 atob 就還原。「不讓別人知道演算法」不是保護：base64 的字元集和結尾的 = 一看就認得出來。base64 可以完整還原，所以也沒有碰撞的問題。密碼要用慢雜湊，第 3 課會做。

練習 7：SHA-256(秘密 + 訊息) 也有秘密參與，為什麼還要用 HMAC？

✓ SHA-256 的摘要就是它的內部狀態，攻擊者可以從那裡接著算，這是長度延伸攻擊。SHA-256 本身沒有被破解，HMAC 內部用的就是它。HMAC 不加密，內容照樣看得到。HMAC 要雜湊兩次，反而比較慢。

練習 8：重設密碼的 token 用 Math.random().toString(36).slice(2) 產生，看起來很亂，有什麼問題？

✓ V8 的 Math.random 是 xorshift128+，攻擊者拿到幾個自己帳號的 token，就能推出內部狀態，預測別人的 token。接三次只是同一個可預測來源的輸出，熵沒有增加。「看起來亂」不等於「猜不到」，token 一律用 crypto.getRandomValues 產生 32 bytes。

常見錯誤

  • 把 base64 當加密：編碼任何人都能還原。要保密用加密，要防竄改用 HMAC 或簽章。
  • 用 Math.random、Date.now、自增 ID 產生 token：都可以預測。用 crypto.getRandomValues，至少 128 bits，這門課用 256 bits。
  • 雜湊手機號碼、身分證字號就以為匿名了：輸入的可能性少，可以全部列舉。
  • 用 === 比對簽章或 token：會洩漏比對到第幾個字元。用 crypto.subtle.verify 或 timingSafeEqual。
  • 用 split('.')[0] 取簽章前的值：value 含 . 時就切錯了。用 lastIndexOf('.')。
  • 把字串直接丟給 btoa、hex 忘了補 0：先 TextEncoder 轉位元組；每個 byte 用 padStart(2, '0')。
  • 位元組參數寫成 Uint8Array：傳給 crypto.subtle 會報 TS2345。寫成 Uint8Array<ArrayBuffer>，原因見課末「補充與查表」。
  • 以為簽過的 cookie 別人看不到內容：HMAC 只防竄改，內容是明文。
  • 自己發明密碼學組合：用標準演算法和平台內建的實作。

TypeScript：位元組參數為什麼寫 Uint8Array<ArrayBuffer>

自己寫的函式要把位元組傳給 crypto.subtle 時，參數寫 Uint8Array<ArrayBuffer>，只寫 Uint8Array 會報 TS2345。TextEncoder.encode()、new Uint8Array(n) 回傳的本來就是這個型別，直接用。

原因是 TypeScript 5.7 起 Uint8Array 有一個型別參數，表示它底下是哪種記憶體；5.9 起內建型別又把 ArrayBuffer 和 SharedArrayBuffer（可以在多個執行緒之間共用的記憶體）分開。只寫 Uint8Array 等於 Uint8Array<ArrayBufferLike>，底下可能是 SharedArrayBuffer，而 crypto.subtle 的參數只收 ArrayBuffer。寫成 Uint8Array<ArrayBuffer>（5.9.3 與 7.0.2 都一樣）。下面這格的第一個函式會在編輯器裡標出型別錯誤：

為什麼不用 Uint8Array.prototype.toBase64()

Chrome 已經有 Uint8Array.prototype.toBase64()，但這裡的型別設定（lib es2024）沒有它，用了會報型別錯誤，所以這門課一律用 btoa／atob。

crypto.getRandomValues 的上限

crypto.getRandomValues() 一次最多填 65,536 bytes。產生金鑰和 token 只需要 32 bytes，碰不到這個上限。

小結

  • 編碼換表示法、不保護；雜湊是指紋、不能還原；HMAC 用共用金鑰證明沒被改過；加密保密；簽章用私鑰簽、公鑰驗。購物車 cookie 要的是完整性與來源，伺服器自己發、自己驗，用 HMAC。
  • 密碼學處理位元組：字串先 TextEncoder 轉 UTF-8，再編碼成 hex 或 base64url。位元組參數寫 Uint8Array<ArrayBuffer>。
  • SHA-256 輸出 32 bytes。沒有金鑰的雜湊擋不住竄改，攻擊者能自己算新的摘要；不能反推不代表猜不到，可能性少的輸入雜湊後仍可列舉。
  • 秘密的亂數一律用 crypto.getRandomValues；熵 = log2(字元數) × 長度，隨機位元組每 byte 8 bits，這門課用 32 bytes。
  • 有金鑰的雜湊用 HMAC，不用 SHA-256(秘密 + 訊息)；HMAC 不隱藏內容。
  • 比對簽章與 token 用常數時間比較：crypto.subtle.verify、timingSafeEqual 或 XOR 累加。
