階段 5：授權：能做什麼、能看哪些資料 · 第 21 課

在 NestJS 實作認證與授權

前 20 課在瀏覽器的練習區裡，一次寫一個小函式：雜湊密碼、驗證 JWT、輪替 refresh token、算權限、擋別人的訂單。每一個單獨看都對，但它們還沒有一起保護過一支真的 API。這一課的練習專案 auth21 是咖啡店的訂單 API：有 PostgreSQL、有 Prisma、有菜單和訂單，資料庫裡有兩位顧客和兩位店員的帳號，認證與授權卻是空的。它的 OrdersService 現在不管是誰在問，GET /orders 都回傳全部的訂單，顧客王小明會看到陳美華的 2 號訂單。

怎麼讓王小明只看得到自己的訂單、吧台登入了也退不了款？這課的任務就是回答它，讓這支 API 可以上線：王小明只看得到自己的 1、3 號訂單；吧台店員登入了也不能退款；店長被降權、帳號被停用時立刻生效；refresh token 被偷時伺服器發現得了、收得回來。最後用 E2E 測試從攻擊者的角度打一遍，拿出「這些關卡真的有作用」的證據。零件接起來時最容易出事的地方，正是單獨寫時看不到的：某個 controller 忘了掛 guard、JWT 驗證用真實時間而其他程式用注入的時鐘、權限讀了 token 裡過時的角色。這課會一個一個遇到它們。

這課的路線：
  1. 起點：這支 API 現在擋不住誰、做完要長什麼樣子，一個請求要經過哪幾道關卡（開場問題的最小答案）。
  2. 登入：王小明的密碼怎麼用 node:crypto 存和驗、為什麼登入是最貴的 API；密碼對了之後發的 access token 怎麼簽、怎麼驗。
  3. 誰能打這個路由：一個全域 guard 讓每個路由預設要登入，另一個讓每個路由預設要宣告權限，吧台因此退不了款。
  4. 能動哪一筆：王小明有讀訂單的權限，「只能看自己的」為什麼寫在 service 的查詢條件裡，不是 guard。
  5. 不用一直重新登入、又證明得了安全：refresh token 輪替怎麼用一句 SQL 擋住同時兩個請求，最後用 E2E 測試攻擊自己。
這課會用到：
  • NestJS 課第 6 課的 guard：實作 CanActivate，在 controller 之前執行，回傳 false 就擋下；Reflector 讀出裝飾器貼在路由上的資料。
  • NestJS 課第 13 課、第 14 課的 Prisma：在 schema.prisma 定義資料表，用 prisma.order.findMany() 這類方法查詢。
  • NestJS 課第 10 課的 E2E 測試：啟動整個 app，用 supertest 送真的 HTTP 請求、檢查狀態碼。
  • 第 9 課、第 10 課的 JWT 與 refresh token：驗 JWT 要固定演算法並檢查 iss、aud、exp；refresh token 每用一次就換新，舊的再出現代表被偷了。

起點：這支 API 現在擋不住誰？

練習專案在 NestJS 課的練習資料夾裡，叫 auth21。它已經有商品、顧客、訂單，也有 User 與 RefreshToken 兩張表和第一個 migration。seed 建了四個帳號，密碼都是 latte-110-please：顧客王小明（wang@coffee.example，1、3 號訂單是他的）、顧客陳美華（chen@coffee.example，2 號訂單）、吧台店員（lin@coffee.example）、店長（zhang@coffee.example）。整課都用這四個帳號和這三筆訂單。先把環境準備好（NestJS 課第 12 課教過）：

# 在 learn/nestjs/practice
npm ci                        # 第一次才要
docker compose up -d --wait   # 啟動練習用的 PostgreSQL

# 在 learn：第一次執行會建立 nestjs/practice/work/auth21/，並跑一次測試
node check.mjs nestjs auth21

想自己用 curl 打 API 的話，在 work/auth21 執行 npx prisma migrate dev（建立開發用的資料庫 nest_auth21 並套用 migration）、npx prisma db seed（建立上面四個帳號），再 npm run start:dev。判分用的是另一個資料庫 nest_auth21_test，每次判分前重建，不會動到你的開發資料。

打開 src/auth/ 會看到 JwtAuthGuard、PermissionsGuard 都只有一行 throw new Error('TODO')，OrdersService 的方法收到了 user 卻沒有用它。這課要把它們補成下面這張表的樣子，每個端點都有明確的「誰能用」：

端點誰能用說明
GET /menu公開菜單
POST /auth/login公開email＋密碼 → access token（body）＋refresh token（cookie）
POST /auth/refresh公開，讀 cookie用 refresh token 換新的 access token 與新的 refresh token
POST /auth/logout公開，讀 cookie撤銷這次登入的 refresh token 家族、清掉 cookie

表裡有兩個地方要先說明。第一，取消訂單用的是 order:create：權限表沒有另外開 order:cancel，取消沿用下單的權限，能下單的人才能取消自己下的單。第二，「班長」是前面沒出現過的角色。權限表（src/auth/permissions.ts，第 18 課）裡的角色有顧客 customer、吧台 barista、班長 shift_lead、店長 manager，還有最上層的老闆 owner；seed 只建了顧客、吧台、店長的帳號，沒有班長。班長能核准退款，店長繼承班長，所以也能。

表裡有兩種「登入後的證明」：access token 放在 response body，之後每個請求用 Authorization: Bearer 標頭帶著；refresh token 放在 cookie。為什麼不用第 4 課的 session cookie 就好？因為同一支 API 要服務兩種前端：會員網站（Vue）和店員的 POS App。POS App 不是瀏覽器，帶 Authorization: Bearer 標頭比管理 cookie 簡單。如果只有一個同網域的 Vue 前台，session cookie 加上第 11 課的伺服器端撤銷更簡單，不需要這一課的大部分程式。

開場的問題「怎麼讓王小明只看得到自己的訂單、吧台退不了款」，最小的答案是：每個請求依序通過三道檢查，每一道回答不同的問題，擋下時回不同的狀態碼。

從左到右讀這張圖：

  • JwtAuthGuard 回答「你是誰」，這是認證。沒帶 token、token 是假的或過期了，回 401，意思是「我不知道你是誰，請先登入」。
  • PermissionsGuard 回答「你這種身分能不能做這類動作」，這是功能層級授權（第 18 課的 RBAC）。吧台店員登入了，但他的角色沒有 order:refund，退款請求在這裡回 403：「我知道你是誰，但你不能做這件事」。
  • service 回答「這一筆是不是你能動的」，這是物件層級授權（第 19 課）。王小明有 order:read，兩個 guard 都放行，但他要的 2 號訂單是陳美華的，service 查不到就回 404，跟訂單不存在一模一樣。

三道檢查分在三個地方，是因為它們需要的資訊不同：第一道只要 token，第二道要知道使用者的角色和路由宣告的權限，第三道要知道是哪一筆資料、屬於誰。後面的小節照這個順序一道一道做出來。

💡 實務上：先問「登入要不要自己做」
新專案常見的選擇是交給現成的身分服務（Auth0、Amazon Cognito、Supabase Auth、Firebase Authentication，或自架 Keycloak），密碼雜湊、MFA、重設密碼流程都由它負責，你的 API 只驗它簽的 token。要考量的是費用、資料放在誰那裡、登入頁能客製到什麼程度，以及以後想搬走有多難。但不管選哪個，這張圖的後兩道一樣是你的：全域 guard 預設拒絕、權限宣告、service 裡的擁有者條件。資深工程師在技術選型會議上會把這條線講清楚：「認證可以買，授權一定是自己寫」。

這課選擇自己做認證，所以三道檢查之前還有一步：王小明要先登入。登入就是拿 email 和密碼換 token，第一個要做好的零件是密碼。

王小明送來密碼：伺服器要怎麼存、怎麼驗？

王小明在登入頁輸入 latte-110-please，請求送到 POST /auth/login。伺服器要判斷這個密碼對不對，就得在資料庫裡存某個能拿來比對的東西。第 3 課講過為什麼不能存密碼本身：資料庫總有一天可能外洩，外洩時拿到的應該是攻擊者難以還原的東西。所以存的是密碼的雜湊，而且要用故意很慢的雜湊演算法。原因是攻擊者拿到雜湊後，會在自己的機器上一個一個猜密碼、算雜湊、比對；每算一次都很貴，他一秒能猜的次數就少，弱密碼也能多撐一段時間。

第 3 課選的演算法是 argon2id。它有三個參數，三個都在調「每猜一次要花多少」：

  • m（memory）：每算一次要佔多少記憶體。攻擊者想用大量平行的硬體同時猜很多個，每一個都要準備這麼多記憶體，成本就上去了。
  • t（passes）：在那塊記憶體上來回算幾遍，越多越慢。
  • p（parallelism）：同一次雜湊分成幾條平行計算。

這課用 OWASP 的最低建議：argon2id、m=19456 KiB（19 MiB）、t=2、p=1。Node 的 node:crypto 已經內建 argon2()，所以不用另外安裝 bcrypt 或 argon2 套件（為什麼避開它們、從哪個 Node 版本開始內建，見課末「補充與查表」）。

算出雜湊之後要存什麼？只存雜湊不夠：驗證時要用同樣的 salt 和同樣的參數重算一次，才能比對。所以存的是 PHC 字串，一種把演算法名稱、版本、參數、salt、雜湊值串成一行的標準格式，第 3 課用過。資料庫的 password_hash 欄位只要這一個字串，驗證需要的東西都在裡面：

$argon2id$v=19$m=19456,t=2,p=1$BlGJJtxr+5gS72F4xFNuYg$2YrsVMqEszCNXpCcD5P0il1hmf8u66fPMKbQ/URzZio
         版本   參數              salt（16 bytes）       雜湊（32 bytes），base64 去掉結尾的 =

產生雜湊的程式。argon2() 是 callback 版，用 promisify 包成 Promise 才能 await；salt 每次都用 randomBytes 產生新的，同樣的密碼存兩次也會得到不同的字串：

import { argon2, randomBytes } from 'node:crypto'
import { promisify } from 'node:util'

const argon2Async = promisify(argon2)   // callback 版包成 Promise
const salt = randomBytes(16)
const hash = await argon2Async('argon2id', {
  message: password, nonce: salt, tagLength: 32,
  memory: 19456, passes: 2, parallelism: 1,
})

驗證是反方向：從資料庫的 PHC 字串拆出 m、t、p 和 salt，拿王小明這次送來的密碼重算一次，再跟字串裡的雜湊比對。重點是用字串裡記錄的參數，不是程式裡目前的設定。哪天你把 t 調成 3，資料庫裡那些 t=2 的舊雜湊照樣要能驗證；用目前的設定重算，所有舊帳號都會登入失敗。驗證成功後，再用 needsRehash 判斷這個雜湊的參數是不是舊的，是的話用新參數重新雜湊、寫回資料庫（第 3 課），使用者完全不會察覺。

比對兩個雜湊時用 crypto.timingSafeEqual，不用 ===。=== 比到第一個不同的位元組就停，比對花的時間會透露「前面有幾個位元組對了」；timingSafeEqual 不管哪裡不同都比完全部，花的時間一樣（第 3 課）。

但慢是雙面刃：每一次登入都很貴

argon2 的慢和吃記憶體是故意的，用來擋攻擊者。可是同樣的成本，你的伺服器每處理一次登入也要付一次。這會在兩個地方顯現：

  • 執行緒：Node 用一條執行緒跑你的 JavaScript，這條執行緒被佔住，所有請求都要等。所以讀檔案、DNS 查詢這類會卡住的工作，Node 交給 libuv 的 thread pool：一組在背景待命的執行緒，預設 4 條（Node 課第 7 課）。callback 版的 argon2() 就在 thread pool 上算，不會卡住事件迴圈；argon2Sync() 在主執行緒上算，算的那幾十毫秒裡整個 API 都停住，所以 API 裡不要用它。thread pool 只有 4 條，同時 8 個人登入時，後 4 個要排隊等前 4 個算完（本機實測數字見課末）；而讀檔案、DNS 查詢也在同一個 pool 排隊，登入尖峰會連帶拖慢它們。
  • 記憶體：每個進行中的雜湊佔 19 MiB。100 個同時登入就要約 1.9 GB。攻擊者不用猜對任何密碼，只要一直送登入請求，就能把伺服器的記憶體吃光。

所以登入端點一定要限流（第 16 課），參數要用壓測決定，不是照抄建議值：用 autocannon 對 POST /auth/login 壓測（Node 課第 23 課），看在你預期的尖峰同時登入數下，p95 延遲和記憶體能不能接受，再決定 m、t 與 thread pool 大小（環境變數 UV_THREADPOOL_SIZE）。OWASP 的值是「最低」，硬體允許時可以更高。

💡 實務上：部署時把登入端點當成「最貴的 API」看待
放進容器部署時，容器的記憶體上限要把同時登入的 argon2 算進去，否則活動開跑、大家同時登入時，最先出現的症狀可能是容器被系統砍掉重啟，而不是登入變慢。監控上把 POST /auth/login 的延遲和錯誤率獨立出來看，不要跟其他 API 平均在一起。調參數時也要跟維運說一聲：t 或 m 調高，同一台機器能撐的同時登入數就跟著下降。

登入失敗時回什麼

密碼驗證不一定會成功。AuthService.login 收到 email 和密碼時，失敗的原因有三種：email 不存在、密碼錯、帳號已停用。三種都要回一模一樣的 401。如果 email 不存在時回「查無此帳號」，攻擊者就能拿一份 email 清單逐一試，找出哪些人是咖啡店的會員，這是第 16 課的帳號列舉。

訊息一樣還不夠，回應時間也要一樣：email 不存在時也要拿一個假的雜湊跑一次 verify。不然「不存在」幾乎立刻回應、「密碼錯」要算一次 argon2，約 20 ms 才回應，從回應時間就能判斷帳號存不存在。

三種失敗都處理好，剩下的就是密碼對了的情況。正因為每驗一次密碼都這麼貴，王小明不能每個請求都送一次密碼。密碼驗過一次之後，伺服器要發給他一張證明，之後的請求帶這張證明就好。這張證明就是 access token。

密碼對了：發給王小明的 access token 要怎麼簽、怎麼驗？

access token 是一個 JWT（第 8、9 課）：伺服器把「這是誰、什麼時候過期」寫進 payload，用只有伺服器知道的秘密金鑰簽名。之後王小明每個請求都帶著它，伺服器驗簽章就知道內容沒被改過，不用查密碼。這一節決定兩件事：簽發和驗證的設定，以及 payload 裡放什麼。

NestJS 官方提供 @nestjs/jwt，它包裝了第 9 課用過的 jsonwebtoken：JwtModule 負責設定，JwtService 提供 signAsync（簽發）與 verifyAsync（驗證）。設定裡的秘密金鑰不能寫死在程式碼裡，要從 ConfigService（NestJS 課第 11 課）讀環境變數。JwtModule.register({…}) 只能收一個寫好的物件；要先拿到 ConfigService 再算出設定，就用 registerAsync：inject 列出要注入的 provider，useFactory 收到它們、回傳設定物件。

JwtModule.registerAsync({
  inject: [ConfigService],
  useFactory: (config: ConfigService) => {
    const issuer = config.getOrThrow<string>('JWT_ISSUER')
    const audience = config.getOrThrow<string>('JWT_AUDIENCE')
    return {
      secret: config.getOrThrow<string>('JWT_SECRET'),          // 32 bytes 以上的隨機值
      signOptions: { algorithm: 'HS256', expiresIn: 900, issuer, audience },
      verifyOptions: { algorithms: ['HS256'], issuer, audience },
    }
  },
})

裡面的 issuer 和 audience 對應 JWT 的兩個標準欄位。iss（issuer）是「誰簽發的」，aud（audience）是「這張 token 是給誰用的」。咖啡店如果有好幾個服務，例如這支 API 和 POS 的同步服務，各自的 token 寫著不同的 aud；驗證時檢查 aud 是不是自己，就能拒絕「原本是給別的服務用」的 token。expiresIn: 900 是 15 分鐘，單位是秒。

signOptions 和 verifyOptions 看起來重複，但缺一不可。signOptions 只決定簽出來的 token 長什麼樣子，verifyOptions 才決定驗證時檢查什麼。第 9 課講過 jsonwebtoken 驗證時的預設陷阱：

  • 驗證時沒給 audience、issuer 就不檢查。只在 signOptions 設，簽出來的 token 有 aud，但驗證時任何 aud 都收。同一把秘密如果也拿來簽別的服務的 token，那些 token 就能拿來打你的 API。
  • 驗證時沒給 algorithms，秘密金鑰預設接受 HS256、HS384、HS512。明寫只收一種（RFC 8725：每把金鑰只用一種演算法）。
  • alg: none 的 token 在有給秘密時會被拒絕，但要用測試確認，不要只靠記憶。

這三項都不會讓正常的登入流程出錯，所以漏了也不會有人發現，直到有人拿竄改過的 token 來打。這課最後一節的攻擊測試會一條一條驗證它們。HS256 用的是共用秘密，簽和驗用同一把，只適合「自己簽、自己驗」；以後有別的服務也要驗這些 token 時怎麼改，見課末。

access token 裡放什麼

payload 只放兩個欄位：sub（使用者 id 的字串）和 ver，加上函式庫自動加的 iat、exp、iss、aud。ver 是簽發當時的 User.tokenVersion：資料庫裡每個使用者有一個計數器，店長按「登出所有裝置」或王小明改密碼時把它加 1，token 裡的 ver 就對不上了，下一節的 guard 會因此拒絕所有舊 token（第 11 課）。

角色不放進去。直覺上把 role: 'manager' 放進 token，guard 就不用查資料庫，好像比較快。但角色會變，token 在 15 分鐘內不會變：店長今天被降成吧台，他手上那張還寫著 manager 的 token 在過期前照樣能退款。這就是第 11 課的「過期權限」。token 只負責證明「你是誰」，「你現在能做什麼」每次都從資料庫讀。

時鐘要用同一個

還有一個只在測試裡才會露出來的問題。專案用注入的 Clock（NestJS 課第 3 課的寫法）取得現在時間，而不是直接呼叫 Date.now()。這樣測試可以用 overrideProvider(CLOCK) 換成假時鐘，把時間往前推 16 分鐘，就能測「token 過期後要回 401」，不用真的等 16 分鐘。

問題是 jsonwebtoken 不認得你的 Clock，它自己會呼叫 Date.now()。兩邊都要把你的時鐘傳進去：

  • 簽發：payload 有 iat 就用它，沒有才用 Date.now()；exp 從 iat 加上 expiresIn 算。所以簽發時傳 iat: Math.floor(clock.now() / 1000)（JWT 的時間單位是秒）。
  • 驗證：clockTimestamp 選項（秒）取代「現在時間」判斷 exp、nbf。呼叫 verifyAsync(token, { clockTimestamp })，這個選項會和 verifyOptions 合併，前面寫死的演算法、issuer、audience 還在（細節見課末）。

兩邊時鐘不一致時，測試推進了假時鐘，token 卻還用真實時間判斷，「過期」測不出來；正式環境裡兩個時鐘是同一個，行為正常，所以這個錯誤平常完全看不到。

到這裡，伺服器能驗密碼、能簽出 access token，也知道怎麼正確地驗它。但「驗」這件事要有人去做：每個需要登入的路由，都得在 controller 執行之前檢查 token。下一節決定由誰檢查，以及怎麼保證沒有一個路由被漏掉。

怎麼讓每個路由預設都要登入，連明天新加的也一樣？

檢查 token 的工作交給 guard：它在 controller 之前執行，回傳 false 或丟出例外就擋下請求。NestJS 課第 6 課的 AdminKeyGuard 是用 @UseGuards() 掛在個別 controller 上的。認證也這樣做，現在的 OrdersController 加一行就好。問題出在以後：下個月同事新增 ReportsController，忘了加那一行，月報就變成公開的，任何人不用登入都能打。程式能編譯、測試也會過，因為沒有人寫「沒登入要被擋」的測試。第 18 課把這類漏洞叫 BFLA（功能層級授權失效）：應該受保護的功能，任何人都呼叫得到。

根本的問題是「預設公開、要記得才安全」。反過來做：預設每個路由都要登入，公開的路由要明寫。這樣忘記的後果是「該公開的頁面打不開」，馬上會有人回報；而不是「該保護的資料外洩」，沒人察覺。NestJS 官方文件的做法（Passport recipe 的「Enable authentication globally」一節；這課不用 passport，只用它的全域 guard 寫法）有兩個零件：

  1. 全域 guard：在任何模組的 providers 裡用 APP_GUARD 這個 NestJS 提供的特殊 token 註冊 guard，它就會套用到整個 app 的每一個路由，包括以後新增的。
  2. 公開的標記：菜單、登入這些路由要能不登入就打，所以要有辦法在路由上貼一個「這個是公開的」標籤，讓 guard 看到就放行。

標籤用 SetMetadata 做。它是 NestJS 提供的裝飾器工廠：SetMetadata(key, value) 回傳一個裝飾器，貼在方法或 class 上，就在那裡記下一筆「key → 值」的資料（TypeScript 課第 24 課的 metadata）。guard 執行時用 Reflector 讀這筆資料。reflector.getAllAndOverride(key, [handler, class]) 先看方法上有沒有，沒有再看 class 上有沒有，都沒有就回傳 undefined。三個零件合起來：

// public.decorator.ts
export const IS_PUBLIC_KEY = 'isPublic'
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true)

// auth.module.ts 的 providers
{ provide: APP_GUARD, useExisting: JwtAuthGuard },

// jwt-auth.guard.ts 的 canActivate 一開頭
const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [context.getHandler(), context.getClass()])
if (isPublic) return true

GET /menu 和 POST /auth/login 加上 @Public()，其他什麼都不用寫就要登入。註冊時用 useExisting 而不是 useClass，原因見課末。

因為 getAllAndOverride 也會看 class，@Public() 加在 class 上時，整個 controller 的每個路由都公開，包括之後別人在這個 controller 裡新增的路由，又回到「預設公開」。只有像健康檢查這種「整個 controller 本來就該公開」時才加在 class 上，其他時候加在方法上。

token 驗過了，為什麼還要查一次資料庫？

不是 @Public() 的路由，guard 從 Authorization: Bearer 標頭取出 token，用 verifyAsync 驗證。驗證通過只代表一件事：「15 分鐘內的某個時間點，這個人登入過」。這段時間裡，店長可能停用了他的帳號，或他改了密碼。所以 guard 再用 sub 查一次使用者（主鍵查詢，很快）：

  • 找不到、已停用（disabledAt 有值）、ver 不等於目前的 tokenVersion → 401。上一節的「登出所有裝置」就是在這裡生效的。
  • 通過的話，把資料庫裡的最新狀態放進 request.user：{ id, email, role, customerId }。後面的 PermissionsGuard 和 service 都用它，不再讀 token。

代價是每個請求多一次查詢，換來停權、降權、改密碼立即生效（第 11 課的取捨）。流量大到這一次查詢成為瓶頸時，可以快取幾秒，但要接受「最多晚幾秒生效」。

擋下時回 401，並帶 WWW-Authenticate 標頭，告訴客戶端這個 API 要哪一種憑證（RFC 9110 規定 401 要帶它）：沒帶 token 時是 Bearer，token 無效時是 Bearer error="invalid_token"（RFC 6750）。不要在訊息裡說是「過期」「簽章錯」還是「被撤銷」，這些細節寫進 log 就好，回給客戶端只是幫攻擊者除錯。前端只需要知道「401 → 去 refresh 或重新登入」。

練習 2 寫這一整段：JwtModule、登入、JwtAuthGuard 與 @Public()。測試會在你的 app 上另外掛一個沒有任何裝飾器的 controller，它必須回 401，這就是「明天新加的也一樣」。

💡 實務上：讀懂已用 @nestjs/passport 與 JwtStrategy 的專案
很多 NestJS 專案的這一段是用 @nestjs/passport 寫的：JwtStrategy 加 AuthGuard('jwt')，寫法對照見 NestJS 課第 6 課的燈泡區塊。拿這課的清單去讀它：super() 的選項有沒有寫死 algorithms、issuer、audience（沒寫就跟第 9 課的陷阱一樣不檢查）；validate() 是直接回傳 payload，還是像這課一樣用 sub 查使用者、比對 tokenVersion（直接回傳的話，停權和「登出所有裝置」要等 token 過期才生效）；全域的 JwtAuthGuard extends AuthGuard('jwt') 有沒有在 canActivate 先檢查 @Public()。三項都對，它跟這課的手寫 guard 是同一件事，不需要為了統一寫法而改掉。

JwtAuthGuard 回答了「你是誰」。但吧台店員 lin@coffee.example 也是合法登入的使用者：他打 POST /orders/2/refund，這道關卡會放行，退款就成功了。

吧台登入了，為什麼還不能退款？權限 guard 預設拒絕

認證只回答「你是誰」，不回答「你能做什麼」。退款要的是第 18 課的權限：專案的 src/auth/permissions.ts 已經有那張權限表，每個角色有哪些權限、繼承哪個角色。吧台（barista）沒有 order:refund，班長（shift_lead）有，店長繼承班長所以也有。程式只檢查權限名稱，不檢查角色名稱，以後加角色、調權限都只改這張表。permissionsOf(role) 把一個角色連同繼承來的權限展開成一個 Set。

剩下的問題是：每個路由需要什麼權限，寫在哪裡？做法跟 @Public() 一樣，用 SetMetadata 做一個 @RequirePermissions(...) 裝飾器貼在路由上，再做第二個全域 guard PermissionsGuard 讀它。宣告有三種情況：

@RequirePermissions('order:refund')   // 需要 order:refund
@RequirePermissions()                 // 明確宣告「登入就可以」
（什麼都沒寫）                         // → 403

第三種是這個 guard 的重點，理由跟上一節一樣：忘記宣告時要安全地失敗。「沒寫」和「寫了空的」在程式裡是兩個不同的值：getAllAndOverride 讀不到時回 undefined，@RequirePermissions() 讀到的是 []。常見的寫法 if (!required?.length) return true 把兩者混在一起，同事新增的路由忘了宣告，就變成「任何登入的人都能用」，正是上一節的 BFLA 換個地方發生。要寫成三個分支：undefined → 403、[] → 放行、其他 → 每個權限都要有。

權限用 permissionsOf(request.user.role) 算，而 request.user 是 JwtAuthGuard 這次請求剛從資料庫讀的。所以店長被降成吧台後，他手上的 token 雖然還沒過期，下一個請求就拿不到 order:refund。這是上一節「token 裡不放角色」換來的。

兩個全域 guard 的執行順序就是 APP_GUARD 註冊的順序。PermissionsGuard 要排在 JwtAuthGuard 之後，原因有兩個：它要用 request.user，那是前一個 guard 放的；沒登入的人打需要權限的路由，該得到 401（「請先登入」），不是 403（「你沒權限」）。前端會依狀態碼做不同的事：401 導去登入頁，403 顯示「沒有權限」，順序錯了，沒登入的人只會看到一個沒有出路的錯誤頁。

練習 3 寫 @RequirePermissions() 與 PermissionsGuard。吧台的退款請求現在會被擋在 403。但王小明的角色 customer 有 order:read，他打 GET /orders/2，兩個 guard 都會放行，請求進到 OrdersService，而它回傳的是陳美華的訂單。

王小明有 order:read，為什麼還不能看 2 號訂單？物件層級授權放在 service

權限回答的是「這類動作能不能做」：顧客可以讀訂單。它回答不了「這一筆能不能讀」：2 號訂單是陳美華的。這是第三道檢查，物件層級授權。漏掉它的漏洞在第 19 課叫 BOLA（物件層級授權失效）：把網址裡的 id 從 1 改成 2，就看到別人的資料。訂單 id 是連續的數字，攻擊者寫個迴圈就能把所有人的訂單抓一遍。

第一個直覺是再寫一個 guard 檢查擁有者。但 guard 執行時只知道路由和網址裡的 :id，要判斷「這筆屬於誰」，guard 得自己查一次訂單；而且每種資源（訂單、集點卡、地址）都要寫一個對應的查詢，等於把 service 的邏輯搬一份到 guard。更大的問題是，之後別的 controller、排程或 GraphQL resolver 直接呼叫 OrdersService，根本不經過這個 guard。

第 19 課的做法是把擁有者條件直接寫進查詢，讓資料庫只回傳屬於這個人的資料：

// 錯：先查再比對，不是你的回 403 → 洩漏「這筆訂單存在」
const order = await prisma.order.findUnique({ where: { id } })
if (order.customerId !== user.customerId) throw new ForbiddenException()

// 對：條件寫進 where，查不到和不是你的都是 404
const order = await prisma.order.findFirst({ where: { id, customerId: user.customerId } })
if (!order) throw new NotFoundException()

錯的寫法也擋住了王小明，問題出在狀態碼。王小明打 /orders/2 得到 403，打 /orders/999 得到 404，他就知道 2 號訂單存在、只是不是他的；拿這個差別掃一遍，就能知道店裡有多少筆訂單。對的寫法裡，「不是你的」和「不存在」對資料庫來說是同一件事：查不到。回應也就自然一模一樣。

條件寫在 service 而不是 controller，是為了讓檢查跟著資料走：不管誰呼叫 OrdersService，都繞不過它。所以 OrdersService 的每個方法都收 user，讀單筆、列表、取消都要用它；findMine 的 findMany 也要加同樣的條件，王小明的「我的訂單」才只有 1、3 號。

Prisma 的 undefined 陷阱：where: { customerId: undefined } 在 Prisma 裡等於沒寫這個條件。店員的 customerId 是 null，寫成 customerId: user.customerId ?? undefined 的話，店員打 GET /orders 會拿到全部顧客的訂單。擁有者條件不存在時要明確處理（這個專案：店員沒有「我的訂單」，回空陣列或 404），不能讓條件消失。

練習 4 修好 OrdersService。到這裡，圖上的三道檢查都在了。但 access token 15 分鐘就過期，王小明點餐點到一半，難道要重新輸入密碼？

15 分鐘後要重新登入嗎？refresh token 輪替

不用。第 10 課的答案是第二張 token：登入時除了 15 分鐘的 access token，再發一張 14 天的 refresh token。access token 過期時，前端拿 refresh token 打 POST /auth/refresh 換一張新的，王小明不會察覺。refresh token 活得久，被偷的傷害也大，所以它不像 access token 那樣只靠簽章，而是存在伺服器的資料庫裡：伺服器能查到它、也能把它標成撤銷，被偷時收得回來。

它還每用一次就換新的，叫輪替。用王小明來看：登入時拿到 refresh token A；15 分鐘後用 A 換到 B，A 就算用過了；再過 15 分鐘用 B 換到 C。A、B、C 是同一次登入一路換出來的，共用同一個 familyId，這一串就叫一個家族。如果有人拿已經用過的 A 再來換，代表有兩個人拿著同一張，伺服器分不出誰是小偷，就把整個家族撤銷，王小明和小偷都得重新登入。這一節把這個設計搬進 Prisma，資料存在 RefreshToken 表，欄位如下：

欄位用途
tokenHash（unique）token 的 SHA-256。token 是 32 bytes 的隨機值，夠長夠隨機，不需要慢雜湊；資料庫外洩時拿不到能用的 token
familyId（有索引）同一次登入一路輪替出來的 token 共用，重用時整個家族撤銷
usedAt換過新 token 了。用過的不刪除，留著才認得出重用
revokedAt、expiresAt撤銷時間、到期時間（14 天）

tokenHash 用 SHA-256 而不用 argon2，跟密碼的情況剛好相反：密碼是人想的，可能很短、很常見，所以要用慢雜湊拖慢猜測；refresh token 是 32 bytes 的隨機值，沒有東西可猜，快的雜湊就夠了，每次 refresh 也不用付 argon2 的成本。

同時兩個請求拿同一張 token 來換

輪替的流程是：用 tokenHash 找到這一列，確認還沒用過，標記成用過，發一張同家族的新 token。最直覺的寫法是先 findUnique 讀出來檢查 usedAt，再 update 寫入。想像小偷偷到王小明的 refresh token，和王小明的瀏覽器幾乎同時拿它來換：兩個請求都先讀，都讀到 usedAt 是空的，都通過檢查，都換到新 token。重用偵測就在最需要它的時候失效了。

關鍵是「檢查還沒用過」和「標記成用過」要在同一句 SQL 裡完成，不讓別人插進中間（第 10 課、PostgreSQL 課第 19 課）。做法是把檢查的條件寫進更新的 where：

const claimed = await prisma.refreshToken.updateMany({
  where: { id: row.id, usedAt: null, revokedAt: null, expiresAt: { gt: now } },
  data: { usedAt: now },
})
if (claimed.count === 0) { /* 沒搶到：用過了 → 撤銷整個家族、401 */ }

updateMany 回傳改到幾列（NestJS 課第 15 課）。PostgreSQL 執行這句 UPDATE … WHERE used_at IS NULL 時會鎖住那一列，第二個請求等第一個提交後重新檢查條件，發現 used_at 已經有值，改到 0 列。所以兩個請求裡剛好一個拿到 count === 1，另一個拿到 0，就知道這張 token 被用了兩次。

還有一個細節，要照時間順序看才看得出來：

  1. 小偷和王小明同時拿舊 token A 來換。王小明搶到（count === 1），他那邊接著要插入一張同家族的新 token B。
  2. 小偷那邊拿到 count === 0，判定重用，把這個家族的每一列都標上 revokedAt。但這時 B 還沒寫進資料庫，撤銷的那句 SQL 看不到它，B 的 revokedAt 仍是空的。
  3. B 寫進去了，王小明拿到 B。之後他拿 B 來換，B 自己這一列沒用過、沒撤銷、沒過期，單看它完全有效。
  4. 如果 rotate 只檢查 B 這一列，被撤銷的家族就靠 B 繼續活下去。所以 rotate 一開始先查「同一個 familyId 有沒有任何一列的 revokedAt 不是空的」，有就 401。B 跟被撤銷的 token 同家族，在這裡就被擋下，不管它是什麼時候插入的。

refresh token 放在什麼樣的 cookie

access token 由前端放在記憶體、自己加到標頭；refresh token 則放在 cookie，讓前端的 JavaScript 完全碰不到它（第 10 課比較過四個位置）。cookie 的每個屬性都在限制「誰讀得到、什麼時候會被送出」：

Set-Cookie: __Secure-rt=…; Max-Age=1209600; Path=/auth; HttpOnly; Secure; SameSite=Strict
  • HttpOnly：JavaScript 讀不到，XSS 偷不走（第 7 課）。Secure：只走 https；瀏覽器把 http://localhost 當成例外，開發時也能用。
  • Path=/auth：只有 /auth/refresh 和 /auth/logout 會收到，打其他 API 時不會帶上。第 10 課設的是 Path=/auth/refresh，這個專案放寬到 /auth，因為登出也要讀它才知道要撤銷哪個家族。
  • 名稱用 __Secure- 前綴。前綴是瀏覽器強制的規則：名稱以 __Secure- 開頭的 cookie 必須有 Secure，沒有 Secure 的 cookie 就冒用不了這個名稱。__Host- 更嚴格，但它要求 Path=/，跟 Path=/auth 一起用，瀏覽器會整個拒收這個 cookie（第 4 課）。
  • Max-Age=1209600 是 14 天（秒）。登出時用同樣的名稱與 Path 送 Max-Age=0 讓瀏覽器刪掉它。用 Express 設這兩個值各有一個容易踩的坑，見課末。

CSRF 與 CORS

cookie 放在瀏覽器裡，換來 XSS 偷不走，也帶來一個新問題：瀏覽器會自動帶上 cookie。王小明開著咖啡店網站時又開了一個惡意網站，那個網站可以讓他的瀏覽器對 /auth/refresh 發請求，cookie 自動跟著去。這就是 CSRF（第 6 課），/auth/refresh 正是它的目標。

第一層防線是 SameSite=Strict：跨站的請求瀏覽器不帶這個 cookie。第二層是第 6 課的 Fetch Metadata：瀏覽器會在請求上加 Sec-Fetch-Site 標頭，說明發出請求的頁面和目標是什麼關係，網頁的 JavaScript 改不了它。它的值有四種：same-origin（同源）、same-site（同站不同源，例如 shop.coffee.example 打 api.coffee.example）、cross-site（跨站）、none（使用者自己打網址、開書籤）。/auth/refresh 的規則：

  • same-origin 或 none → 放行。
  • same-site 或 cross-site → 只有 Origin 在信任清單（設定的 CORS_ORIGINS）裡才放行。比對要完整相等：用 startsWith 的話，https://shop.coffee.example.evil.example 也會通過。前台 https://shop.coffee.example 呼叫 https://api.coffee.example 是同站不同源，送的是 same-site，所以前台要在清單裡；https://marketing.coffee.example 一樣是 same-site，不在清單就擋下。
  • 沒有 Sec-Fetch-Site 時比對 Origin；兩個都沒有，代表不是瀏覽器（POS App、curl），放行。不是瀏覽器就不會自動帶受害者的 cookie，也就沒有 CSRF。

反過來，自己的前台要能正常 refresh。前台用 fetch(url, { method: 'POST', credentials: 'include' }) 呼叫，瀏覽器才會帶 cookie、才會收下回應的 Set-Cookie。這時 CORS 回應要有明確的前台來源（不能是 *）和 Access-Control-Allow-Credentials: true（第 5 課）；專案的 configureApp 已經用 enableCors({ origin: CORS_ORIGINS, credentials: true }) 設好。

練習 5 寫 RefreshService 與三個 /auth 端點。做完之後，開場列的四個目標在程式裡都有了對應的一段。但「有寫」不代表「有作用」：guard 少一行、where 少一個條件，正常操作看起來完全一樣。怎麼證明？

怎麼證明這些關卡真的有作用？用 E2E 測試攻擊自己

認證的程式最常見的測試只有一個：「正確的帳密能登入」。這個測試在 guard 完全沒作用時也會過，因為它只測了正常使用者會走的路。這課做的每一道檢查，都是為了擋住某個不正常的請求，所以測試要從攻擊者的角度寫：前面每一節擋下的攻擊，各寫一條測試真的打一次，確認被擋下。整理起來就是這張表，每一列對應前面某一節：

測試擋的是
沒帶 token → 401忘了掛 guard 的路由
改了 payload 的 sub → 401沒驗簽章
alg: none、HS512 → 401沒固定演算法
同一把秘密、別的 aud 或 iss → 401沒檢查 audience、issuer
推進假時鐘後 → 401沒檢查期限、時鐘不一致
tokenVersion 加 1、帳號停用 → 401撤銷不生效
降權後同一個 token → 403讀 token 裡的角色
顧客 A 讀 B 的訂單 → 404，與不存在相同BOLA、列舉
舊 refresh token 再用 → 401，最新的也失效refresh token 被偷
同時兩個 refresh → 剛好一個成功先讀後寫的競態

只有這張表還不夠。如果 guard 寫成「全部拒絕」，表裡每一條都會通過，但沒有人能用這支 API。所以每一條攻擊測試旁邊都要有對照組：同樣的請求換成正常使用者，要成功。王小明讀 2 號訂單要 404，讀 1 號要 200；吧台退款要 403，店長退款要 200。攻擊組證明擋得住，對照組證明擋的只有攻擊。

測 refresh 時還有一個 supertest 的特性要處理：每個 request() 都是獨立的請求，不會像瀏覽器一樣記住上一個回應的 cookie。測試要自己解析 Set-Cookie，同時斷言 HttpOnly、Secure、SameSite、Path，再手動帶 Cookie 標頭送下一個請求。這反而是好事：cookie 的屬性變成規格的一部分被測試守住，而不是「瀏覽器會處理」。

這一課的隱藏測試就是照這張表寫的，打開 work/auth21/ex2.test.ts 等檔案可以看到每一條怎麼寫。第 26 課的期末專題你要自己寫這些測試。

練習

五題依序做：練習 2 的登入要用練習 1 的 PasswordService，練習 3 到 5 都要先能登入。每題完成後在 learn 資料夾執行 node check.mjs nestjs auth21，再回到這一頁按「讀取測試結果」。

練習 1：實作 PasswordService：

  • hash(password)：用 node:crypto 的 argon2（用 promisify 包成 Promise），argon2id、m=19456、t=2、p=1、16 bytes 的隨機 salt、32 bytes 輸出，回傳 PHC 字串（base64 去掉結尾的 =）。
  • verify(password, stored)：用字串裡的 m、t、p 與 salt 重算，用 crypto.timingSafeEqual 比對。格式不對、長度不同、參數不合法都回 false，不丟錯。
  • needsRehash(stored)：不是 argon2id，或參數跟目前的設定不同時回 true。

測試會自己解析你的 PHC 字串，用 argon2Sync 重算比對，所以換成 scrypt、SHA-256 或固定的 salt 都過不了；也會拿 t=1 的舊雜湊和截短的雜湊來驗證，並記錄 timingSafeEqual 的呼叫，確認 verify 的結果就是它的比對結果。

練習 2：完成登入與全域認證：

  • auth.module.ts：JwtModule.registerAsync 從 ConfigService 讀 JWT_SECRET、JWT_ISSUER、JWT_AUDIENCE；簽發固定 HS256、15 分鐘、issuer、audience；verifyOptions 固定 algorithms、issuer、audience。把 JwtAuthGuard 用 APP_GUARD＋useExisting 註冊成全域 guard。
  • public.decorator.ts：用 SetMetadata 寫出 @Public()。
  • auth.service.ts：login 在 email 不存在、密碼錯、帳號停用時丟同一個 401，email 不存在時也要呼叫一次 verify；signAccessToken 的 payload 只有 sub（字串）與 ver，iat 用注入的時鐘。
  • jwt-auth.guard.ts：@Public() 放行；其他路由讀 Authorization: Bearer，用 verifyAsync 驗證並傳 clockTimestamp；再用 sub 查使用者，不存在、停用、ver 不等於 tokenVersion 都 401；通過後把 { id, email, role, customerId } 放進 request.user。401 要帶 WWW-Authenticate: Bearer…。

測試會用假時鐘推進 16 分鐘、自己用同一把秘密簽出 aud 或 iss 不同的 token，並在你的 app 上另外掛一個沒有任何裝飾器的 controller，它必須回 401。

練習 3：用 SetMetadata 寫出 @RequirePermissions(...permissions)，實作 PermissionsGuard：@Public() 放行；沒有宣告權限的路由一律 403；宣告了就用 permissionsOf(user.role) 檢查每一個權限，@RequirePermissions() 不帶參數代表登入就可以。宣告了好幾個權限時，每一個都要有。在 auth.module.ts 把它註冊成第二個 APP_GUARD，排在 JwtAuthGuard 後面。

測試會在資料庫裡把店長降成吧台，再用他原本的 token 退款，必須 403。

練習 4：OrdersService 的 findMine、findMineById、cancelMine 收到了 user 卻沒有用。把擁有者條件寫進 Prisma 的 where：只能讀、列出、取消自己的訂單；不存在或不是自己的一律 NotFoundException，回應完全相同。店員的 customerId 是 null，沒有「我的訂單」：列表回空陣列、單筆回 404。

練習 5：完成 refresh token：

  • refresh.service.ts：issue 產生 32 bytes 的隨機 token，資料庫只存 SHA-256；rotate 用原子的 updateMany 標記使用（條件包含還沒用過、沒撤銷、expiresAt 還沒到，時間用注入的時鐘），成功時發同一個家族的新 token；用過的 token 再出現時撤銷整個家族；家族裡有任何一張被撤銷過就拒絕；revokeFamily 給登出用。
  • auth.controller.ts：登入時另外設 __Secure-rt cookie（HttpOnly、Secure、SameSite=Strict、Path=/auth、14 天）；新增 @Public() 的 POST /auth/refresh（回 { accessToken } 並換新 cookie）與 POST /auth/logout（撤銷家族，用同樣的名稱與 Path 送 Max-Age=0）。/auth/refresh 照上面「CSRF 與 CORS」的規則檢查 Sec-Fetch-Site 與 Origin，不通過回 403；信任清單從 CORS_ORIGINS 讀。

回傳 cookie 要用 @Res({ passthrough: true }) res: Response，return 的物件照樣由 Nest 轉成 JSON。測試會讓每次讀 refresh token 的查詢互相等待，同時送出兩個 refresh，「先讀再寫」的寫法一定會兩個都成功。

練習 6：「顧客只能看自己的訂單」為什麼不寫在 guard 裡，而是寫在 service 的查詢條件？

✓ b。guard 可以注入 PrismaService，a 錯；但它只知道路由與參數，要為每個路由寫「這個 id 屬於誰」的查詢，等於把 service 的邏輯搬一份過去，而 service 被別的地方呼叫時又沒有保護。速度不是重點，c 錯。d 是最常見的誤解：guard 適合「這類動作能不能做」（RBAC），「這一筆能不能動」屬於資料存取層（第 18、19 課的兩層分工）。

練習 7：JwtModule.register({ secret, signOptions: { expiresIn: 900, audience: 'https://api.coffee.example' } })，沒有設 verifyOptions。用同一把秘密簽、aud 是 https://pos.coffee.example 的 token 打這個 API，會怎樣？

✓ c。signOptions 和 verifyOptions 是兩組獨立的設定，驗證時只會檢查有明確給的 audience、issuer（exp 預設會檢查）。d 也錯：沒給 algorithms 時，秘密金鑰預設接受 HS256、HS384、HS512，HS512 一樣會通過。所以 verifyOptions 要寫齊 algorithms、issuer、audience，再用測試確認。

練習 8：refresh token 的 cookie 要設 Path=/auth。名稱該用哪個前綴？

✓ a。前綴是瀏覽器強制執行的規則，不是命名習慣：__Secure- 要求 Secure；__Host- 要求 Secure、Path=/、不能有 Domain，任何一條不符，瀏覽器就丟掉這個 cookie，所以 b、d 錯。c 少了前綴的好處：沒有 Secure 的 cookie（例如 http 頁面或被竄改的 http 回應設的）不能用 __Secure- 開頭的名稱，蓋不掉你的（第 4 課）。

常見錯誤

  • 密碼雜湊參數照抄建議值，沒有壓測：登入尖峰時 thread pool 排隊、記憶體爆掉。壓測決定參數，登入端點一定要限流；API 裡不用 argon2Sync()。
  • JWT 秘密寫在程式碼裡，或用 secret123 這種短字串：HS256 的秘密可以離線暴力破解。用 32 bytes 以上的隨機值，從設定讀（第 23 課會細講秘密管理）。
  • verifyOptions 沒設 algorithms、issuer、audience：jsonwebtoken 沒給就不檢查。三個都寫，並用竄改的 token 測試。
  • JWT 驗證用真實時間、其他邏輯用注入的時鐘：測試測不到過期。簽發傳 iat、驗證傳 clockTimestamp。
  • 在個別 controller 上 @UseGuards：新 controller 忘了加就是公開的。用 APP_GUARD 讓所有路由預設要登入，公開的用 @Public() 明寫。
  • @Public() 加在 class 上：整個 controller 連同之後新增的路由都公開。只在整個 controller 本來就該公開時這樣用，其他時候加在方法上。
  • guard 讀 JWT 裡的角色當權限：降權要等 token 過期才生效。token 只放 sub 與 ver，角色每次從資料庫讀。
  • 沒有宣告權限的路由放行：if (!required?.length) return true 把「沒寫」和「明確寫了登入就好」混在一起。undefined 一律 403。
  • 物件層級授權寫在 controller：service 的其他呼叫路徑沒檢查。條件寫進 service 的查詢。
  • where 的值可能是 undefined：Prisma 會拿掉這個條件，查出所有人的資料。擁有者不存在時明確處理。
  • refresh 先讀後寫、或用過就刪：前者並發時兩個都成功，後者認不出重用。用 updateMany 的 count，用過的留著標 usedAt。
  • E2E 測試只測成功的路徑：guard 沒作用也會過。每個攻擊都寫一個測試，旁邊配一個正常使用的對照組。

補充與查表

node:crypto 的 argon2：版本、為什麼不用套件、本機實測

Node 24.7.0 起，node:crypto 內建 argon2()（callback 版）與 argon2Sync()，本機 Node 24.22.1 可以直接用，沒有實驗性警告。bcrypt 和 argon2 套件是原生模組（C/C++ 寫的，要在你的電腦上編譯），換 Node 版本或 CPU 架構時容易裝不起來；bcrypt 還只吃密碼的前 72 bytes。

在本機 Node 24.22.1 實測，同時 8 個 argon2id（m=19456、t=2、p=1）在預設 4 條執行緒時分兩波完成，約 30 ms 與 50 ms；設 UV_THREADPOOL_SIZE=8 後一波完成。

@nestjs/jwt 的版本與 verifyAsync 的選項合併

這課用的 @nestjs/jwt 是 12.0.3，包裝的 jsonwebtoken 是 9.0.3。verifyAsync(token, { clockTimestamp }) 傳進去的選項會和模組設定的 verifyOptions 合併（看過 @nestjs/jwt 12.0.3 的原始碼：{ ...verifyOptions, ...options }），所以只傳 clockTimestamp 不會蓋掉 algorithms、issuer、audience。

什麼時候從 HS256 改成 ES256 與 JWKS

只有這一個服務自己簽、自己驗，用 HS256（共用秘密）可以接受。如果之後有別的服務也要驗證這些 token，就改用 ES256 加 JWKS（第 8 課）：秘密只在簽發的一方，其他服務只拿公鑰。

APP_GUARD 為什麼用 useExisting

用 useExisting 而不是 useClass：JwtAuthGuard 本身也是一個普通 provider，全域 guard 指向同一個實例，測試可以 overrideProvider 換掉它或它的依賴（NestJS 第 6 課）。

SetMetadata 與 Reflector.createDecorator

SetMetadata 跟 NestJS 課第 6 課的 Reflector.createDecorator 是同一件事的兩種寫法：都是在 handler 或 class 上貼一個標籤，guard 用 Reflector 讀。這課的練習用 SetMetadata。

用 Express 設 cookie 的兩個坑

  • Express 的 res.cookie 的 maxAge 單位是毫秒，送出的 Max-Age 是秒。14 天要傳 14 * 24 * 60 * 60 * 1000。
  • 登出時用同樣的名稱與 Path 送 Max-Age=0。res.clearCookie(name) 不帶選項時 Path 是 /，瀏覽器會當成另一個 cookie，原本那個留著。

小結

  • 一個請求依序經過三道檢查：JwtAuthGuard 認證（你是誰，401）、PermissionsGuard 功能層級授權（能不能做這類動作，403）、service 的物件層級授權（這一筆是不是你的，404）。
  • 密碼用 node:crypto 的 argon2id（Node 24.7.0 起內建），存 PHC 字串，驗證時用字串裡的參數；每次雜湊佔 19 MiB 記憶體、在 thread pool 上排隊，所以要壓測、要限流。登入失敗的回應與時間都要一樣。
  • JwtModule 的 verifyOptions 固定 algorithms、issuer、audience；payload 只放 sub、ver，角色不放；簽發與驗證都用注入的時鐘。
  • 兩個全域 guard 都是「沒寫就拒絕」：JwtAuthGuard 預設必須登入，驗證後查資料庫得到最新的使用者；PermissionsGuard 對沒宣告權限的路由回 403，權限依資料庫裡的角色。順序是先認證、再授權。
  • 物件層級授權寫進 service 的查詢條件，不是你的和不存在的都是 404。
  • refresh token 只存 SHA-256、放在 __Secure-、HttpOnly、SameSite=Strict、Path=/auth 的 cookie；輪替用原子更新，重用時撤銷整個家族；/auth/refresh 再加 Fetch Metadata 檢查。
  • 資安的測試從攻擊者的角度寫，每條攻擊配一個正常使用的對照組。

練習 9：同事新增「月底對帳匯出」路由，忘了寫 @RequirePermissions。PermissionsGuard 排在 JwtAuthGuard 之後，核心是這幾行，哪裡會出事？

const required = this.reflector.getAllAndOverride<Permission[] | undefined>(
  PERMISSIONS_KEY, [context.getHandler(), context.getClass()])
if (!required?.length) return true
const granted = permissionsOf(request.user.role)
return required.every((p) => granted.has(p))

✓ undefined（沒寫）和 []（明確寫了登入就好）被混在一起，這就是 BFLA。要寫成 undefined 回 403、[] 放行，再用測試比對所有路由和政策表。a 錯在宣告了好幾個權限代表每一個都要有，改成 some 反而放寬。（第 18、21 課）

練習 13：RLS 的租戶變數在每個請求開頭用 SELECT set_config('app.tenant_id', $1, false) 設定。背景工作忘了設定，結果大多時候一列都查不到，偶爾卻查到某一個租戶的資料。先查什麼？

✓ 「偶爾、而且是某一個租戶」是連線池沿用設定的特徵。改成在交易裡用 set_config(…, true)（等於 SET LOCAL），交易結束就消失，沒設定時一列都看不到。c 錯在 RLS 被繞過時每次都會看到全部租戶，不會大多時候查不到。（第 20 課）

練習 14：老闆新規定：班長只能退自己門市、而且是值班中的訂單。班長的角色目前有 order:refund，這條規則該怎麼加？

✓ RBAC 只管「能不能做這類動作」，管不了「這一筆」：角色有 order:refund，權限檢查就放行任何門市的單。權限仍是第一個條件，門市、班表交給 ABAC 的政策函式（PDP），now 從參數傳入，每種組合都能測。a 錯在權限檢查根本不看角色名稱裡的門市和時段，還會造成角色爆炸。（第 18、19 課）

練習 15：refresh 端點這樣檢查舊 token（重用時撤銷家族的部分省略）。哪裡會出事？

const row = await prisma.refreshToken.findUnique({ where: { tokenHash } })
if (!row || row.usedAt || row.revokedAt || row.expiresAt <= now) {
  throw new UnauthorizedException()
}
await prisma.refreshToken.update({ where: { id: row.id }, data: { usedAt: now } })
return issueNewPair(row.familyId)

✓ 先讀後寫，偷到 token 的人和使用者同時 refresh 時，重用偵測就失效了。把「還沒用過」寫進更新條件：updateMany({ where: { id, usedAt: null, … } })，count 是 0 就是重用。a 錯在刪掉之後就認不出重用，用過的要留著標 usedAt。（第 21 課）

練習 16：同事寫了三條 E2E 測試：沒帶 token 回 401、竄改 sub 回 401、顧客 A 讀 B 的訂單回 404，全部通過。最該補的是什麼？

✓ 只有攻擊測試的話，guard 把所有請求都擋掉也會通過。每條攻擊配一個正常使用的對照組，才證明擋下的是攻擊。c 錯在多加攻擊測試還是同一個盲點：「全部拒絕」照樣全過。（第 21 課）
