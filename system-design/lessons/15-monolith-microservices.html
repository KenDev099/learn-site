階段 4：架構：服務、事件與即時推送 · 第 15 課

單體、模組化單體與微服務

咖啡店的後端現在是一個 NestJS 專案：菜單、下單、付款、集點、廚房出單、通知全部在同一個程式裡，一起建置、一起部署，共用一個 PostgreSQL。兩年前寫它的是 3 個工程師，現在是 15 個。最近有兩件事讓大家很煩：每週五發版要排隊，只要有一個人的測試沒過，所有人的功能都上不了；上個月行銷要改「第二杯半價」的促銷規則，負責的人順手改到結帳的程式，付款壞了 20 分鐘。技術會議上有人提議：「我們拆成微服務吧，大公司都這樣做。」

這一課從頭到尾處理同一件事：替這個提案做出判斷，而且說得出理由。你會依序回答：拆了能換到什麼、要付什麼；如果要切，線該畫在哪裡；下單 API 從呼叫函式變成呼叫好幾個網路服務之後，可用性和延遲會怎樣；怎麼從 git 歷史看出邊界畫錯了；訂單明細頁需要好幾個服務的資料時怎麼組；最後，什麼訊號出現才真的該拆、拆完要看哪些數字。先說方向：拆服務不是升級，是用一組問題換另一組問題。

這課的路線：
  1. 「拆成微服務」到底改變了什麼：三種形狀各用什麼換什麼，為什麼對這個提案的預設回答是「先做模組化單體」（開場問題的最小答案）。
  2. 模組的邊界要畫在哪裡：依業務能力切，每張表只有一個主人。
  3. 把模組搬到網路上的代價，以及拆錯時的分散式單體：可用性相乘、延遲相加，怎麼從 git 歷史找出畫錯的邊界。
  4. 訂單明細頁要三個服務的資料：怎麼組，選用的服務掛了怎麼還能回傳部分結果。
  5. 回到提案：什麼訊號出現才拆、怎麼拆、拆完看哪些數字。
這課會用到：
  • NestJS 課第 4 課的 Module：一個 Module 只匯出它想給別人用的 provider，其餘藏在裡面。
  • NestJS 課第 26 課的模組邊界：模組之間只透過公開介面或事件溝通，用架構測試擋住越界的 import。
  • 第 4 課的串聯可用性：每個都必須活著的硬相依，可用性要相乘；軟相依壞了還能降級。
  • 第 8 課的逾時：每個網路呼叫都要有時間上限，時間到用 AbortSignal 取消。

「拆成微服務」到底改變了什麼？三種形狀

要判斷這個提案，先弄清楚「拆」改變的是哪一件事。咖啡店現在的程式碼已經分成好幾個資料夾，「菜單」和「下單」在程式裡也是不同的類別，所以「拆」說的不是程式碼分不分資料夾，而是部署單位。

部署單位（deployable unit）是一次建置、一次上線的東西，例如一個 Docker 映像。咖啡店現在只有一個部署單位：不管你改的是菜單還是集點，上線時整個程式一起重新建置、一起換版。開場說的「發版要排隊」就是從這裡來的：大家的修改都要裝進同一個映像，只要其中一個人的測試沒過，這個映像就不能上線。

依照「有幾個部署單位」和「內部有沒有清楚的邊界」，系統有三種常見的形狀：

  • 單體（monolith）：一個部署單位包含所有功能。函式之間直接呼叫，大家共用一個資料庫，任何程式都可以讀寫任何一張表。咖啡店現在就是這樣，所以改促銷的人才會「順手」改到結帳：中間沒有任何東西擋著。
  • 模組化單體（modular monolith）：還是一個部署單位，但內部依業務切成邊界清楚的模組。模組之間只透過公開的介面或事件溝通，不能直接碰別人的資料表。這就是 NestJS 課第 26 課做的事：每個 NestJS Module 只匯出公開的 service，再用架構測試擋住越界的 import。
  • 微服務（microservices）：每個業務能力是一個可以獨立部署、擁有自己資料的服務，服務之間只能透過網路溝通。網路溝通的方式有幾種：你熟悉的 HTTP；gRPC，這是 Google 開源的 RPC 框架，用 HTTP/2 傳二進位格式的訊息，讓呼叫遠端服務寫起來像呼叫函式；或是第 12 課的訊息佇列。

下面這張圖把咖啡店的六個業務能力畫成三種形狀。注意中間和右邊：兩者的邊界可以畫得一模一樣，差別只在邊界上走的是函式呼叫還是網路呼叫。

「函式呼叫還是網路呼叫」聽起來只是實作細節，但它會一路影響到部署、交易、擴展、團隊分工和維運。函式呼叫在同一個程序裡完成，不會「對方剛好掛了」；網路呼叫要花毫秒級的時間，會逾時、會只成功一半。下表逐項比較：

單體模組化單體微服務
部署一起部署一起部署每個服務各自部署
模組之間的呼叫函式呼叫，奈秒級、不會「網路斷掉」函式呼叫或同一個程序內的事件網路呼叫，毫秒級、會逾時、會部分失敗
跨模組的交易一個資料庫交易一個資料庫交易（但要克制）沒有共同交易，要用 saga（第 13 課）
擴展整個一起加機器整個一起加機器只擴展需要的服務
團隊大家改同一份程式，容易互相卡住各團隊負責模組，但共用發版流程團隊自主，可以自己決定發版時間與技術
維運成本一套 CI／CD、監控、告警一套每個服務一套，還要分散式追蹤、版本相容

讀這張表時，把它拆成兩個差別來看。左邊兩欄的差別是「程式內部有沒有邊界」；右邊兩欄的差別是「邊界上走不走網路」。拿開場的兩個痛點對照：「改促銷改到結帳」是內部沒有邊界造成的，從單體走到模組化單體就能解決，不需要網路；「發版要排隊」屬於「團隊」與「部署」那兩列，模組化單體能緩解（每個模組有負責的人、修改的影響範圍變小），但大家還是共用一次發版，真正要獨立發版才需要拆成服務。微服務最右欄的好處都是真的，代價也是真的：它用網路失敗、分散式資料和多好幾倍的維運工作，換來獨立部署、獨立擴展和團隊自主。

那該從哪一種開始？Martin Fowler 在〈MonolithFirst〉這篇文章整理了他看到的案例：幾乎所有成功的微服務系統，都是先有一個單體，長得太大才拆開；幾乎所有一開始就做成微服務的系統，都遇到嚴重的麻煩。原因是一開始很難把邊界畫對，而在服務之間搬功能，比在模組之間搬難得多：模組之間搬只要移動程式碼、改 import，服務之間搬要改 API、搬資料、協調兩邊一起部署。他也提到微服務有「額外成本（microservice premium）」：管理很多服務本身就會拖慢團隊，系統要複雜到一定程度才划算（出處見課末「補充與查表」）。

所以資深工程師對這個提案的預設回答通常是先做模組化單體：在一個部署單位裡把邊界練習清楚，等真的出現值得拆的訊號（最後一節會列出來），再把已經切乾淨的模組搬出去。這就是開場問題的最小答案。不過這個回答有個前提：你得知道模組的邊界要畫在哪裡。邊界畫錯了，不管後來拆不拆都會痛，下一節就處理這件事。

💡 實務上：有人提議拆微服務時，先問要解決什麼問題
在新創或小團隊，「要不要拆微服務」常出現在技術會議或面試題裡。資深工程師不會先回答「要」或「不要」，而是先問：現在痛的是什麼？是發版要排隊、某個功能吃資源拖垮其他功能，還是只是程式碼很亂？程式碼亂通常是模組邊界沒畫好，拆成服務只會把亂搬到網路上。也要問有沒有人力負責多出來的 CI／CD、監控和值班；一個人顧五個服務，比顧一個單體累得多。咖啡店的兩個痛點，一個是邊界問題、一個是發版流程問題，要分開回答。

模組的邊界要畫在哪裡？依業務能力切，每張表只有一個主人

決定先做模組化單體之後，第一件事是把線畫出來。最常見的錯誤是依技術分層切：「前端服務」「API 服務」「資料庫服務」。用開場的促銷當例子：「第二杯半價」要改畫面上的價格顯示、改 API 的計價邏輯、改資料表存折扣的方式，三層都要動。依技術分層切，這一個需求就要同時改三個模組（或三個服務）、一起上線，邊界完全沒有幫你擋住任何東西，拆了等於沒拆。

正確的切法是依業務能力（business capability）：店裡實際在做的一件事，例如「管理菜單」「接單」「收款」「集點」「出餐」「通知顧客」。每個能力自己從 API、商業邏輯一路到資料表，全部包在同一個模組裡。這樣「第二杯半價」只會落在負責計價的那個模組，結帳模組的程式根本不在改動範圍內。上一節圖裡的六個名字就是這樣來的：catalog（菜單與價格）、ordering（接單）、payment（收款）、loyalty（集點）、kitchen（出餐）、notification（通知）。後面的例子還會用到兩個：inventory（門市庫存）和 customers（顧客資料），圖上為了簡單沒畫出來。

切的時候會遇到一個問題：同一個詞，在不同模組眼中意思不一樣。「訂單」對廚房是「要做哪幾杯、加不加冰」，對會計是「金額、發票、付款方式」，對集點是「這位會員消費多少、能拿幾點」。如果硬要所有模組共用同一個 Order 類別，它就會長成一百個欄位，每個模組只用其中幾個，但誰改了任何一個欄位，大家都可能受影響，最後沒有人敢改。

解法是承認「訂單」在不同範圍裡本來就是不同的東西。這個觀念叫限界上下文（bounded context）：一個範圍內，每個詞的意思是一致的；跨出這個範圍，同一個詞可以有不同的意思和不同的模型。廚房的上下文裡有自己的「訂單」（品項與做法），會計的上下文裡有自己的「訂單」（金額與發票），兩者各自只存自己需要的欄位。當你發現某個詞在兩群人口中意思不同，那裡通常就是一條邊界。

邊界畫出來之後，要靠一條規則守住它，這條規則是資料擁有權（data ownership）：每張表只有一個模組（或服務）能寫。別人需要這份資料，就呼叫它公開的 API，或訂閱它發出的事件（第 16 課會深入），不能直接 SELECT 它的表。為什麼連「只是讀」都不行？因為一旦別人直接讀你的表，表的欄位名稱和結構就成了你跟對方之間的介面，而且是沒有寫下來、沒有版本管理的介面：你改一個欄位名稱，對方就壞了，你卻不知道有人在讀。咖啡店的分配如下：

模組擁有的資料別人怎麼拿
catalogproducts（品名、價格）查詢 API；改價時發出 ProductPriceChanged 事件
orderingorders、order_items查詢 API；發出 OrderPlaced、OrderPaid
payment付款紀錄、金流交易編號只透過 API；法規上要隔離
loyalty會員點數查詢 API；訂閱 OrderPaid 自己加點

看 ordering 那一列：order_items 自己存了 unit_price。下單當下的價格是「訂單」上下文的事實（顧客就是用這個價格買的），不是每次讀訂單時去 products 即時查的。這樣菜單改價不會改到舊訂單的金額，ordering 也不需要在每次讀訂單時呼叫 catalog。這是資料擁有權的常見結果：與其每次跨邊界去問，不如在事情發生的當下，把自己需要的那份資料記下來。

共用資料庫是反模式：兩個服務都直接讀寫 orders 表，任何人改欄位名稱，另一個服務就壞；要改就得兩邊一起改、一起部署。程式分成兩個 repo，但耦合一點都沒少。在模組化單體裡，可以用 NestJS 課第 26 課的架構測試守住規則：禁止互相 import 形成環、禁止 import 別的模組的內部檔案、每張表只屬於一個模組。

邊界畫好、規則守住之後，「改促銷改到結帳」這類事故在模組化單體裡就擋得住了。如果之後真的要把某個模組搬出去變成獨立服務，它的邊界已經是乾淨的，搬起來最省力。但搬出去的那一刻，邊界上的函式呼叫就變成網路呼叫，下一節算算這會付出什麼。

💡 實務上：接手舊專案，先替每張表找主人
接手一個長了幾年的單體，最快看出邊界的方法是列出所有資料表，標上「誰會寫它」。如果一張表有三個模組在寫，那裡就是最容易出 bug、也最難拆的地方。常見的例外需求是報表：營運要一張「每週各分店銷售加點數」的報表，很容易就寫成一條跨三個模組的 JOIN。改去查第 6 課的唯讀複本只能避免拖慢正式資料庫，表結構還是綁在一起；比較穩的做法是讓各模組透過事件或匯出，把報表要的資料送進專門給報表用的資料庫（常叫資料倉儲），模組改表時只要顧好送出去的格式。咖啡店開會前，就可以先做這張「表與主人」的清單。

把模組搬到網路上，下單 API 會變成怎樣？延遲相加、可用性相乘

假設咖啡店照提案把模組都拆成服務。原本下單在同一個程式裡依序呼叫幾個函式，現在變成 ordering 服務依序同步呼叫 4 個服務：catalog 查價格、inventory 扣庫存、payment 付款、loyalty 替會員加點。「同步」的意思是 ordering 要等對方回應，才能繼續做下一步、最後回應顧客。

這 4 個呼叫都是第 4 課說的硬相依：任何一個失敗，這次下單就失敗。所以整條路徑的可用性是每個服務的可用性相乘，而不是取最低的那個。ordering 自己也可能掛，所以要算 ordering 加 4 個依賴，共 5 個。延遲也一樣累加：每一跳都要等前一跳回來才開始，總時間就是第 1 課說的逐段相加。下面這格程式把三件事算出來，執行後依序看：5 個服務串聯後的可用性與停機預算、依序與平行呼叫的延遲、把 loyalty 改成非同步之後的可用性。

  • 可用性：5 個 99.9% 串聯只剩 99.50%，每 30 天能停機的時間從單一服務的 43 分鐘變成約 216 分鐘。每個服務自己都達標，加起來卻差了五倍。
  • 延遲：依序呼叫是 210 ms。catalog、inventory、loyalty 互不相依，可以同時發出去，只等最慢的那一個，再接著付款，降到 192 ms。平行能省掉一部分，但付款那 180 ms 怎樣都要等。
  • 非同步：把 loyalty 從同步路徑上拿掉，可用性回到 99.60%。少乘一個數，就少一個會讓下單失敗的理由。

第一行的結論最重要：拆服務本身不會讓系統變可靠，反而多了網路這個失敗點。在單體裡，ordering 呼叫 loyalty 是一次函式呼叫，不會「loyalty 剛好在重新部署」；拆開之後，這種事每天都會發生。要把可靠性拿回來，每一個網路呼叫都要補上前一個階段學的東西：逾時與重試（第 8 課）、冪等（第 9 課），以及斷路器與隔艙（第 11 課）；原本一個資料庫交易就做完的事，變成要設計補償的 saga（第 13 課）。這些都是拆開之後才需要付的工。

上面最後一行為什麼能讓可用性回升？因為同步呼叫還有一個代價：呼叫的那一刻，對方必須活著。這種「兩邊必須在同一時間都在線」的綁定，叫做時間耦合（temporal coupling）。解法是改成非同步：下單成功後，把「這張訂單付款了」的事件放進佇列（第 12 課），loyalty 之後自己從佇列取出來加點。能移出同步路徑的前提是這個請求不需要它的結果：加點可以晚點做；如果顧客要用點數折抵，折抵金額會影響付款金額，那一步就必須留在同步路徑上。這樣 loyalty 就不在這個請求的可用性路徑上：集點服務掛 10 分鐘，下單照樣成功，點數晚 10 分鐘入帳。代價是使用者不會立刻看到點數，而且要處理訊息重送與順序。下圖用 inventory、payment 和 notification 畫出同一條規則：loyalty 改成非同步之後，就和圖中的 notification 一樣走虛線。

延遲和可用性是算得出來的代價，還有一些算不出來、但每天都會碰到的：

  • 除錯：一個請求跨好幾個服務，出錯時要靠分散式追蹤（部署課第 23 課）才找得到是哪一跳出的問題；單體裡一個 stack trace 就看得到。
  • 本機開發與測試：要在自己的電腦上試下單，得同時起好幾個服務，或替它們寫假的替身；整合測試也變慢。
  • 維運：每個服務都要自己的 CI／CD、監控、告警和值班。15 個人顧 8 個服務，這些工作會吃掉一大塊時間。

這些代價是拆開時一定要付的，換來的是獨立部署與團隊自主。最糟的情況是付了代價，卻沒拿到換來的東西：服務拆開了，卻還是要一起部署、一起修改。下一節看怎麼認出這種狀態。

拆了卻沒拿到好處：怎麼認出分散式單體？

上一節說的最糟情況有個名字：分散式單體（distributed monolith）。它拆成了很多服務，但這些服務必須一起部署、共用資料庫、彼此大量同步呼叫。它承受了微服務的網路失敗與維運成本，卻沒有獨立部署與團隊自主的好處，等於同時拿到兩邊的缺點。它通常不是故意做出來的，而是邊界沒畫好就拆的結果。常見的徵兆有四個：

  • 一起部署：上線清單寫著「先部署 A，再部署 B，最後 C，順序錯了會壞」。服務之間的介面一改就要另一邊配合，代表它們沒有真正分開。
  • 聊天式的同步呼叫（chatty calls）：顯示一個頁面，要在服務之間來回呼叫幾十次。每一次都是上一節算過的延遲與失敗機率，通常代表該在同一個服務裡的資料被切到兩邊去了。
  • 共用資料庫：好幾個服務直接讀寫同一張表，也就是邊界那一節（第二節）的反模式。
  • 共用含領域模型的套件：一個 common 套件裡放著 Order、Customer 類別，改一個欄位所有服務都要一起升級，這是限界上下文沒有分開的結果。共用沒有業務意義的工具（日誌格式、HTTP 客戶端）沒問題。

前三項看設定和架構圖就知道。還有一個徵兆藏在歷史裡：共同變更耦合（change coupling），指兩個模組總是在同一次提交或同一次部署裡一起修改。如果 ordering 和 loyalty 十次修改有九次一起改，它們其實是同一個東西被切成兩半，邊界畫錯了。這個指標在拆之前就能用：咖啡店現在還是單體，正好可以先在現有的程式上量一次，看看預計的邊界是不是真的分得開。

資料不用另外收集，git 已經記錄了。下面這行指令列出半年內每個 commit 改了哪些檔案，--%h 那行是 commit 的短雜湊，用來分隔：

共同變更耦合是證據，不是判決。兩個模組一起改，也可能是一次跨全站的重新命名或套件升級。看數字之後還要點開那些 commit，確認是不是業務上綁在一起。

邊界畫對了，服務也真的能各自部署，還是會有一類需求必須穿過邊界：一個畫面要同時顯示好幾個服務的資料。下一節處理這件事。

訂單明細頁要三個服務的資料：怎麼組、某個服務掛了怎麼辦？

單體裡，訂單明細頁用一條 JOIN 就能把訂單、顧客姓名和點數一起查出來。拆開之後，這三份資料分屬三個主人：訂單在 ordering、顧客姓名在 customers、目前點數在 loyalty，邊界那一節（第二節）的資料擁有權也不允許你直接 JOIN 別人的表。

最直接的做法叫 API composition：由一個服務分別呼叫這幾個服務，把結果組合成一個回應交給前端。誰來負責組？有兩個常見的位置。第一個是 API 閘道（API gateway），也就是所有外部請求進來的單一入口，第 8 課見過。第二個是 BFF（Backend for Frontend）：專門為某一個前端組資料的後端層，例如只服務咖啡店 App 的那一層。你寫 Vue 時常遇到「一個頁面要打三支 API 再自己拼」，BFF 就是把這段拼接搬到後端，前端只打一支。

組資料的關鍵，是區分哪些資料必要、哪些選用。沒有訂單，這頁沒有意義，訂單拿不到就應該整頁失敗；但點數只是附加資訊，集點服務掛了，應該把點數那一格藏起來，而不是整頁回 500。這是第 11 課的降級（graceful degradation），也就是第 4 課說的把硬相依變成軟相依。下面的程式讓 loyalty 固定失敗，比較兩種寫法。執行後看兩行輸出：第一行整頁失敗，第二行回傳了訂單和顧客，只有點數是 null：

寫法一用 Promise.all，只要有一個 Promise 失敗，整個就 reject，所以一個選用的服務壞掉，就拖垮整頁。寫法二用 Promise.allSettled，它會等所有 Promise 都有結果，再逐一告訴你每個是成功還是失敗；選用的失敗就填 null，並把名稱記進 degraded。

寫法二還不夠。如果集點服務沒有失敗、只是很慢（30 秒才回），allSettled 會陪它等 30 秒，整頁一樣卡住。所以選用的呼叫要有自己的短逾時，時間到就 abort 並當作失敗（第 8 課），這是練習 3 要補上的。degraded 欄位有兩個用途：讓前端知道哪一塊沒拿到、該怎麼顯示；也該記成指標，降級次數突然變多，就是有依賴出事了。

API composition 每次查詢都要依賴其他服務活著。另一條路是乾脆不在查詢時呼叫：ordering 訂閱 loyalty 發出的事件，在自己的資料庫存一份唯讀的點數複本（第 16 課的投影）。查詢只讀自己的資料庫，不再依賴集點服務；換來的代價是資料會晚幾秒，而且多一份要維護的資料。兩種做法的取捨：

API composition事件複製的唯讀資料
新鮮度即時晚幾秒到幾分鐘
可用性每個必要的服務都要活著只要自己活著
延遲平行呼叫中最慢的那個一次本機查詢
適合資料量小、要即時、能降級的畫面大量讀、跨服務的搜尋與報表

訂單明細頁資料量小、點數晚幾秒也沒關係，兩種都可以；咖啡店先用 API composition 加降級，比較簡單。到這裡，拆開之後的代價和做法都看過了，可以回到會議桌上的那個問題：咖啡店現在到底該不該拆？

💡 實務上：降級的畫面要跟 PM、設計師一起決定
身為全端工程師，你常常會同時寫 BFF 和前端畫面，degraded 就是兩邊的約定。點數拿不到時要整格藏起來、顯示「點數暫時無法顯示」，還是用上一次的數字？這是產品決定，不是工程師自己猜，最好在開發前就跟 PM 和設計師對好。前端也要測這個狀態：開發時刻意讓選用的 API 失敗，確認畫面不會整頁壞掉或顯示 null。另外注意不要把降級的回應快取起來，否則服務恢復後使用者還是看到缺一塊的頁面。

回到提案：什麼時候該拆、怎麼拆、拆完看什麼？

前面幾節看到，拆服務要付網路失敗、維運和資料分家的代價。所以值得拆的時機，是某個模組跟其他部分的需求差到「綁在一起的代價比拆開的代價還高」。常見的訊號有四種：

  • 擴展需求差很多：會員上傳大頭照要縮圖，吃 CPU、尖峰很尖，跟下單放在一起會互相搶資源。拆開之後，只有縮圖服務需要多開機器。
  • 變動頻率差很多：促銷活動每週改，金流整合一年改兩次；綁在一起，每次上促銷都要冒動到金流的風險。開場那 20 分鐘的付款事故看起來像這個訊號，但下一段會說明為什麼它還不足以構成拆的理由。
  • 團隊互相卡住：15 個人改同一個 repo，發版要排隊、互相等審查、一個人的壞程式擋住大家上線。開場的發版排隊看起來像這個訊號，但下一段會說明為什麼它還不足以構成拆的理由。
  • 隔離需求：付款要符合支付卡產業的資安標準（PCI DSS），把處理卡號的部分隔成獨立服務、獨立網路，稽核範圍就能縮小到那一塊，不必整個系統都受檢。

沒有這些訊號，只是「感覺比較現代」，就繼續用模組化單體。對照咖啡店：促銷改到結帳，第一步是先畫好模組邊界（第二節），讓計價和結帳在程式裡就互相碰不到；如果邊界守住之後，付款還是因為變動頻率和法規隔離而需要獨立，payment 會是第一個值得拆的候選。發版排隊也一樣，先看模組化之後每個模組有沒有明確的負責人、測試能不能只跑受影響的模組，還是卡住，才是拆的理由。

決定要拆時，還要看團隊怎麼分。這裡有一個經驗法則：設計系統的組織，產出的設計會複製這個組織的溝通結構。Melvin Conway 在 1968 年的文章裡提出這個觀察，後來被稱為 Conway 定律（出處見課末）。放到咖啡店：如果一個團隊同時負責 ordering 和 loyalty，這兩個服務很快就會長出私下的捷徑，因為同一群人改起來最方便；如果兩個團隊共用一個服務，它就會因為兩邊的需求拉扯而變形。所以畫服務邊界時，要同時畫團隊邊界：一個服務只屬於一個團隊。反過來也成立：想要什麼樣的架構，就先把團隊調整成那個樣子，讓系統自然長成對應的形狀，業界稱為反向 Conway 操作（inverse Conway maneuver）。

拆的方法是一塊一塊來，不要一次全部重寫：在單體旁邊長出新服務，把流量逐步導過去，舊程式最後退役。這種做法叫 strangler fig，第 19 課會實作。為什麼要這麼謹慎？因為拆服務接近一扇單向門：單向門指做了之後很難回頭的決定。拆出去之後，資料分家、團隊分工、外部依賴都跟著變，要合回來的成本很高。這種決定要寫設計文件與 ADR，把理由和考慮過的替代方案留下來，一年後的人才知道當時為什麼這樣做。ADR（Architecture Decision Record）是一份短文件，記下一個架構決定、當時的理由和考慮過的替代方案；第 18 課會細講。

拆完之後，要用數字確認當初想換的東西真的換到了，也確認代價沒有失控。上線後持續看這五類：

  • 每個服務自己的 SLO（第 3 課的服務水準目標）：成功率、延遲；加總起來要撐得住整條請求路徑的目標。
  • 依賴圖：從分散式追蹤（部署課第 23 課）自動畫出誰呼叫誰；同步呼叫鏈越來越長，就是可用性在往下掉。
  • 部署頻率與一起部署的次數：拆服務的目的是獨立部署，如果每次都要好幾個服務一起上線，就是分散式單體的徵兆。
  • 跨服務呼叫的延遲、錯誤率、逾時與降級次數：分開看每一條邊，才知道是哪個依賴拖慢整體。
  • 共同變更耦合：定期跑練習 2 的分析，耦合程度高的配對列進技術債清單（第 20 課）。
💡 實務上：在會議上，對這個提案的回答長這樣
把這一課串起來，咖啡店的回應可以是：「先不拆。這一季把單體整理成模組化單體：依業務能力畫邊界、替每張表找主人、加架構測試擋越界 import，並跑一次共同變更耦合確認邊界分得開。payment 是第一個候選，因為它的變動頻率和法規隔離需求都跟其他模組不同；邊界穩定後，寫 ADR 評估用 strangler fig 拆出去。拆之前先準備好分散式追蹤與每個服務的 SLO。」這樣的回答有診斷、有順序、有退路，比單純說「要」或「不要」更容易讓團隊接受。

練習

練習 1：寫 requestPathAvailability(graph, entry)，算一個請求的可用性。從 entry 出發，只沿著 mode: 'sync' 的邊走，走得到的服務（包含 entry 自己，每個服務只算一次）的可用性全部相乘。syncDeps 是除了 entry 以外走得到的服務名稱，用 sort() 預設的順序排序。async 的邊不走：對方之後再處理就好，不影響這個請求成不成功。圖可能有環，也可能有兩條路通到同一個服務（菱形依賴）。不能修改傳入的資料。

練習 2：寫 changeCoupling(commits, moduleOf, minDegree)，從 git 歷史找出總是一起修改的模組。

  • 先用 moduleOf 把每個 commit 的檔案換成模組，同一個 commit 裡同一個模組只算一次。
  • 每個模組的「修改次數」是碰到它的 commit 數（只碰到一個模組的 commit 也要算）。
  • 同一個 commit 裡的每一對模組 a < b（字串比較）的 together 加 1。只碰到一個模組的 commit 不形成配對。
  • degree = together ÷ min(a 的修改次數, b 的修改次數)：較少被修改的那一邊，有多少比例的修改牽動了另一邊。
  • 回傳 degree ≥ minDegree 的配對 { a, b, together, degree }，依 degree 由大到小，相同時依 a、再依 b 由小到大。

練習 3：寫訂單明細頁的 API composition getOrderDetails(orderId, deps, opts)。

  • 先呼叫 deps.orders 取訂單（必要）。失敗就用同一個錯誤 reject，也不要再呼叫其他服務。
  • 拿到訂單後，用訂單的 customerId 同時呼叫 deps.customers 與 deps.loyalty（選用）。每個呼叫有自己的 AbortController 和 opts.optionalTimeoutMs 的逾時：時間到就 abort 那個呼叫，當作失敗。
  • 選用的呼叫失敗或逾時，對應欄位（customer、points）為 null，名稱（'customers'、'loyalty'）依字母排序放進 degraded。點數是 0 不算失敗。
  • 計時器只能用 opts.schedule：schedule(ms, fn) 代替 setTimeout，回傳取消函式，測試用假時鐘推進時間，不用真的等（第 3 課的寫法）。呼叫成功或失敗時要取消它，結束後不能留下計時器。

練習 4：把咖啡店拆成 6 個微服務，每個服務各自部署在 3 台機器上。系統會比原本的單體更可靠嗎？

✓ b。下單 API 同步呼叫 4 個 99.9% 的服務，整條路徑只剩約 99.5%。服務分開不等於故障隔離：只要是同步的硬相依，對方掛了你一樣掛（a 錯）。3 台機器的冗餘單體也可以做，跟拆不拆無關（c 錯）。拆開之後要另外把呼叫改成非同步、加上逾時、斷路器與降級，才能把可靠性拿回來。

練習 5：ordering 服務和 reporting 服務分別有自己的 repo、各自部署，但都直接讀寫同一個資料庫的 orders 表。這算微服務嗎？

✓ c。微服務的關鍵是每份資料只有一個擁有者。兩個服務共用 orders 表，表結構就是它們之間沒有版本管理的介面：ordering 改欄位，reporting 就壞（a 錯）。權限只決定誰能寫，不會讓耦合消失（b 錯）。改法是 reporting 透過 ordering 的 API 或事件取得資料，自己存一份報表用的複本。

練習 6：3 個人的新團隊要做咖啡店 App，需求每週都在變。應該一開始就做成微服務嗎？

✓ a。需求還在變的時候，邊界幾乎一定會畫錯；在服務之間搬功能要改 API、搬資料、協調部署，比在模組之間搬難得多（b 錯）。Fowler 的 MonolithFirst 就是這個觀察。3 個人顧 6 個服務，光是 CI／CD、監控、值班就吃掉大部分時間，而且同一批人管所有服務，團隊自主的好處也不存在（c 錯）。

練習 7：Conway 定律說了什麼？對畫服務邊界有什麼影響？

✓ b。Conway 1968 年的論文講的正是系統設計：組織怎麼溝通，產出的系統就會長成那個形狀。兩個團隊共用一個服務，它就會被拉扯變形；一個團隊同時負責兩個服務，它們就會長出捷徑。這直接影響架構（a 錯）。它沒有規定要用哪種架構，模組化單體一樣可以讓每個團隊負責一個模組（c 錯）。

常見錯誤

  • 依技術分層切服務（前端服務、API 服務、資料庫服務）：任何一個功能都要改三個服務、一起上線。依業務能力切，每個能力從 API 到資料表一路到底。
  • 共用資料庫：沒有資料擁有權，等於沒拆。每張表只有一個服務能寫，別人透過 API 或事件取得。
  • 同步呼叫鏈越拉越長：延遲相加、可用性相乘。不需要立刻知道結果的步驟改成非同步。
  • 邊界還不清楚就拆：在服務之間搬功能比在模組之間搬難得多。先做模組化單體，用架構測試守住邊界，用共同變更耦合檢查邊界畫得對不對。
  • 共用一個包含領域模型的 common 套件：改一個欄位所有服務都要一起升級。每個服務保留自己需要的模型，只共用沒有業務意義的工具。
  • 低估維運成本：每個服務都要 CI／CD、監控、告警、值班、API 版本相容（第 19 課）。團隊撐不起來就不要拆。
  • API composition 時一個選用的服務壞了就整頁 500：區分必要與選用，選用的加短逾時、失敗時降級並記錄 degraded。
  • 選用的呼叫逾時後沒有 abort：結果已經不要了，對方還在做白工、佔著連線。用 AbortController 取消。

小結

  • 「拆」改變的是部署單位，以及邊界上走函式呼叫還是網路呼叫。微服務用網路失敗、分散式資料、維運成本，換獨立部署、獨立擴展、團隊自主。
  • 對「拆成微服務吧」的預設回答是先做模組化單體（MonolithFirst）：先把邊界在一個部署單位裡練清楚，因為在服務之間搬功能比在模組之間搬難得多。
  • 依業務能力與限界上下文畫邊界；每張表只有一個擁有者，別人透過 API 或事件取得資料，共用資料庫是反模式。
  • 同步依賴的可用性相乘、延遲相加；非同步的依賴不在請求的可用性路徑上，拆開之後要用逾時、冪等、斷路器、saga 把可靠性補回來。
  • 分散式單體的徵兆：一起部署、聊天式同步呼叫、共用資料庫、共用領域模型套件；從 git 歷史量共同變更耦合，拆之前就能找出畫錯的邊界。
  • 跨服務查詢用 API composition：必要的失敗就失敗，選用的加逾時、失敗就降級並記錄 degraded；或用事件複製一份唯讀資料，用新鮮度換可用性。
  • 擴展需求差很多、變動頻率差很多、團隊互相卡住、法規隔離這些訊號出現才拆，用 strangler fig 一塊一塊拆並寫 ADR；Conway 定律提醒畫服務邊界時一起畫團隊邊界；拆完看 SLO、依賴圖、一起部署的次數、跨服務呼叫與共同變更耦合。
