階段 2：擴展：冗餘、快取與資料 · 第 7 課

分片與一致性雜湊

咖啡店開放加盟，三年後全球 5,000 家店、每天 300 萬筆訂單。讀取已經有第 5 課的快取和第 6 課的讀副本分擔，但寫入只能進 primary 那一台：每一筆訂單、每一次付款狀態更新都擠在同一台機器的 CPU、磁碟和連線上。再加讀副本也沒用，因為每個副本都要重播和 primary 一樣多的寫入，寫入量並沒有被分掉。

這一課的任務是：把 orders 表拆到好幾台資料庫上，而且拆完之後，店員的待做清單、顧客的「我的訂單」、總部後台的「全公司最新訂單」都要照常運作。這件事一旦做了就很難回頭：分片鍵選錯，某一台會被打爆；分配方法用錯，加一台機器就要搬動八成資料；跨分片查詢寫錯，結果會少資料而且不會報錯；訂單編號沒設計好，不同機器會產生同一個號碼。這課就照這個順序，一個一個解決。大部分系統用不到分片，所以這課是選修；但它的每一個問題，在快取叢集、訊息佇列這些地方都會再出現。

這課的路線：
  1. 真的該分片了嗎、要依哪個欄位拆：什麼數字出現才該分片，依顧客還是依門市拆，選錯為什麼會有一台被打爆。
  2. hash 值怎麼對到機器：hash % N 加一台機器為什麼要搬八成資料，一致性雜湊怎麼只搬一小部分；快取叢集加減機器也是同一個問題。
  3. 查詢沒帶分片鍵怎麼辦、訂單編號怎麼不撞號：總部後台的「全公司最新 20 筆訂單」怎麼查才不會少資料，各台怎麼產生不重複的訂單編號。
  4. 上線之後：某一片太滿時怎麼不停機搬資料，要看哪些指標。
這課會用到：
  • 第 6 課的 primary 與讀副本：所有寫入只進 primary，讀副本只能分擔讀取。
  • PostgreSQL 課第 35 課的分割表：在同一台資料庫裡，把一張大表依某個欄位拆成好幾塊。

寫入擠在一台 primary：真的該分片了嗎？

開場的問題是「寫入只能進一台」。直覺的解法是把訂單拆開，放到好幾台資料庫，每台只負責一部分的訂單，寫入自然就分散了。這個做法叫分片（sharding），拆出來的每一份叫一個分片（shard）。每個分片是一套完整、獨立的資料庫，有自己的 primary 和讀副本；訂單 A 只存在第 1 片，訂單 B 只存在第 3 片，兩片之間互不知道對方有什麼資料。

你在 PostgreSQL 課第 35 課看過很像的東西：分割表（partitioning）也是把一張大表依某個欄位拆成好幾塊。差別在於分割表的每一塊還在同一台機器上，PostgreSQL 自己知道每一塊在哪，查詢、交易、JOIN 都照常；分片則把每一塊放到不同的機器，這些機器之間沒有共同的資料庫幫你協調。這個差別就是分片所有代價的來源：一筆交易跨兩片時，沒有一個資料庫能保證兩邊一起成功或一起失敗；一個查詢要的資料散在各片時，得由應用程式自己去每一片問、自己合併。

所以分片之前要先確認：單機真的撐不住了嗎？先回到第 2 課算過的現況：每天 6 萬筆訂單，5 年含副本與索引約 284.7 GB，尖峰每秒 3.33 筆寫入。一台 PostgreSQL 完全撐得住，連讀副本都還不一定需要。開場的 300 萬筆是三年後的情境，而且我們假設那時監控圖已經顯示 primary 長期滿載。分片要解決的，正是單機在這三種地方撐不住的時候：

  • 寫入：primary 的 CPU、磁碟寫入量或 WAL 產生量到頂。讀副本幫不上忙，因為副本也要重播同樣的 WAL。
  • 儲存：資料大到單機的磁碟放不下，或是備份與還原的時間不能接受。例如還原 10 TB 可能要好幾個小時，這段時間服務都是停的。
  • 連線與記憶體：查詢經常碰到的那部分資料，稱為 working set。它大到放不進一台機器的記憶體時，查詢就一直要去讀磁碟，整體變慢。連線數也是單機上限：primary 能同時開的連線有限，每條連線還會佔用記憶體。

就算真的撐不住，分片也不是第一個選擇。下面這張表由便宜到昂貴排列，每一步都比分片簡單，而且做錯了可以回頭。表中的 IOPS 是磁碟每秒能完成幾次讀寫，換大機器時它通常會跟著變大：

順序做法解決什麼代價
1垂直擴充（換大機器）CPU、記憶體、IOPS 全部一起變大有上限；越大越貴；換機要停機或切換
2讀副本（第 6 課）讀取複寫延遲；不解決寫入

第 6 步的代價為什麼說「一直要付」？因為它不是一次性的工程，而是之後每一天的工作方式：跨分片的 JOIN 和交易做不到或很貴；每寫一個查詢都要先想清楚它會去哪一片；增減機器要搬資料；備份、升級、監控的工作量乘以分片數。所以「什麼時候分片」的答案是：有數字證明前五步都不夠的時候。

💡 實務上：有人提「我們該分片了」，先問證據
會議上有人說「資料越來越多，該分片了」，資深工程師會先問：現在卡的是寫入、儲存還是記憶體？有沒有監控圖？上表前五步做過哪些、各換來多少空間？很多時候真正的問題是一支沒索引的慢查詢、一張該封存的舊表，修掉之後常常就不用分了。真的要分，也先評估現成方案（例如 Citus 這類 PostgreSQL 的分散式擴充），自己在應用程式裡寫分片路由是最後才考慮的選項。咖啡店的三年後情境，就是前五步都做過、寫入仍然到頂的那一天。

假設那一天到了，監控證明 primary 的寫入已經到頂。下一個問題是：訂單要依什麼拆？「這筆訂單放第幾片」必須由訂單上的某個欄位決定，這個欄位選得好不好，決定了後面所有查詢的難易。

訂單要依什麼拆？從存取模式選分片鍵

決定一筆資料放在哪一片的欄位，叫分片鍵（shard key），有些資料庫的文件叫 partition key，指的是同一件事。分片鍵一旦決定，每筆訂單的去處就固定了；之後任何查詢只要帶著分片鍵的值，就能算出該去哪一片，只問那一片；沒帶的話，系統不知道資料在哪，只能每一片都問一次。

所以選分片鍵不是看哪個欄位好實作，而是看存取模式（access pattern），也就是系統實際上會用什麼條件、多頻繁地讀寫這些資料。PostgreSQL 課第 27 課設計索引時也是從存取模式出發：先列出最常跑的查詢，再讓結構配合它們。好的分片鍵要滿足三個條件：

  1. 大部分查詢都帶著它：查詢有分片鍵才知道去哪一片，否則要問每一片。
  2. 不會產生熱點：熱點（hot spot，也叫 hot partition）指某一片承受的流量或資料遠多於其他片。分片的目的是把負載分攤到多台機器，如果有一片扛了三成的量，其他片再閒也幫不上它，整個系統的上限就變成那一片的上限。
  3. 一筆交易落在同一片：同一片內可以用一般的資料庫交易；跨片就沒有資料庫幫你保證原子性，需要第 13 課的 saga 這類補償流程。

拿這三個條件檢查咖啡店的三個候選欄位：

  • store_id：店員的「待做清單」每幾秒更新一次，帶的都是 store_id，下單也帶著它，所以單片查詢的比例最高。問題在熱點：不管用什麼規則分配，同一個 store_id 的訂單一定在同一片。台北旗艦店佔全部訂單的 30%，分成 10 片時理想上每片 10%，旗艦店那一片卻至少扛 30%。
  • customer_id：「我的訂單」「下單」都帶它；100 萬個會員，每個人的訂單量差不多，分布平均，一個顧客的下單交易也都在同一片。代價是店員的待做清單不帶 customer_id，會變成跨片查詢，要另外處理（後面「查詢沒帶分片鍵怎麼辦？」那節的全域次要索引）。
  • order_id：每個值只有一筆，分布最平均。但除了查單筆訂單詳情，幾乎沒有查詢只帶 order_id，「我的訂單」也要問遍每一片。

三個都有缺點，「哪個比較好」要用數字比，不要憑感覺。兩個指標分別對應前兩個條件：

  • 單片查詢比例 = 帶分片鍵的查詢每秒次數 ÷ 全部查詢每秒次數。要用流量加權，不是數有幾種查詢：每秒 400 次的待做清單和每秒 5 次的日報，份量差了 80 倍。
  • 最熱的一片佔多少 = 最大的那個值的資料量 ÷ 總量。旗艦店就是 store_id 最大的那個值。

做法是先訂出能接受的熱點上限，在不超過上限的候選裡選單片比例最高的。咖啡店把熱點上限訂在 10%：store_id 光旗艦店一家就佔 30% 的資料，出局；customer_id 和 order_id 最熱的值都不到 1%，都符合。再比單片比例（依每秒查詢數加權）：customer_id 是 350 ÷ 755 ≈ 46%，order_id 只有訂單詳情帶它，約 13%，所以選 customer_id。練習 1 你會寫出這兩個指標和選擇規則，並看到門檻放寬時答案會變成 store_id。

💡 實務上：多租戶 SaaS 幾乎都用租戶 ID 當分片鍵
做給很多公司用的 SaaS（例如給各家咖啡店用的 POS 後台），幾乎每個查詢都帶著「哪一家店」，所以 tenant_id 是最自然的分片鍵：同一家的資料、交易都在同一片，也方便做資料隔離和單一客戶的匯出、刪除。坑在大客戶：連鎖品牌的量遠大於一般小店，就是上面旗艦店的熱點；常見做法是讓大客戶獨立一片，再用一張對照表記錄每個租戶在哪一片（後面「一致性雜湊與虛擬節點」那節會講的目錄表）。選鍵前先把前幾名查詢和最大的幾個租戶列出來看，比在白板上討論有用。

決定用 customer_id 之後，還差一步：customer_id 是 c1024 這種值，要怎麼換算成「第幾片」？

customer_id 怎麼對到某一片？range 與 hash

把分片鍵的值對應到分片，有兩種基本規則。range 分片是依值的範圍分：例如依下單月份，2026-01 的訂單一片、2026-02 一片。hash 分片是先把值丟進雜湊函式，得到一個看起來隨機、但同樣的輸入永遠得到同樣輸出的數字，再依這個數字決定分片：hash(customer_id) 落在哪一段就去哪一片。兩者的取捨：

range 分片hash 分片
怎麼分依值的範圍：2026-01 的訂單一片、2026-02 一片依分片鍵的雜湊值：hash(customer_id) 落在哪一段就去哪一片
範圍查詢快：「這個月的訂單」只打一片慢：相鄰的值被打散，要問每一片
熱點容易：新資料全部寫進「最新的那一片」不同的值會平均，但同一個值永遠在同一片
適合依時間查、舊資料要整片封存依 ID 查單筆、寫入要平均

咖啡店要分攤的是寫入，而 range 分片依時間分時，今天所有的新訂單都寫進同一片，等於沒分。customer_id 本身也沒有「範圍查詢」的需求，沒有人會查「c1000 到 c2000 的顧客」。所以選 hash 分片。

表中「同一個值永遠在同一片」常被誤解成「hash 會自動消除熱點」。hash 只能把不同的值打散：如果當初選了 store_id，旗艦店的所有訂單雜湊值都一樣，全部進同一片，hash 一點忙都幫不上。熱門的值可以手動再拆：把旗艦店的 key 加上 0～7 的尾碼，變成 8 個不同的值，分到 8 片；代價是查旗艦店時要讀 8 片再合併。這也是 customer_id 的優勢：沒有任何一位顧客的訂單量大到需要這樣處理。

現在規則是「依 hash(customer_id) 決定分片」，但「落在哪一段就去哪一片」的「段」要怎麼切？最直覺的寫法是取餘數，下一節就會看到它在加機器時出大問題。

加一台機器為什麼要搬八成資料？hash % N 的問題

最直覺的分配方式是 hash(key) % N：N 台機器，雜湊值除以 N 的餘數是幾就去第幾台。這裡用的雜湊函式是非加密雜湊函式（non-cryptographic hash），它只負責把字串變成分布平均的數字，速度很快，但不防有人刻意製造碰撞。你在認證課第 2 課看過的 SHA-256 是加密雜湊，設計目標是安全，計算比較慢；分片只是要決定位置，用快的就好。下面範例的 hash32 以 FNV-1a 這個常見的非加密雜湊為基礎（為什麼多了幾行收尾見課末）。

平常 N 不變時，% N 分得很平均，看不出問題。問題出在 N 改變的時候。用快取叢集當例子，因為它最常加減機器：從 4 台加到 5 台，執行後看第一行，有多少 key 換了機器：

約 79% 的 key 換了機器，而理想上只需要搬新機器分到的那 20%。原因是除數變了：同一個雜湊值除以 4 和除以 5 的餘數，只有少數情況會相同。如果這是快取，加一台機器等於快取幾乎全部失效，所有請求同時打到資料庫，就是第 5 課的雪崩：大量 key 同時失效，所有未命中一起壓到資料庫，而且不是因為 TTL，是因為 key 換了機器。如果這是咖啡店的訂單分片，就是 80% 的訂單要在線上搬家，搬的期間每一筆都要確保不遺失、不重複。

我們要的是：加一台機器時，只有新機器該負責的那一份需要移動，其他 key 原地不動。下一節的一致性雜湊就是為此設計的。

怎麼讓加機器只搬一小部分？一致性雜湊與虛擬節點

% N 的毛病在於每個 key 的位置都依賴 N。一致性雜湊（consistent hashing）出自 Karger 等人 1997 年的論文，它的想法是讓 key 的位置不再依賴機器總數，只依賴「離它最近的是哪台機器」。做法是把雜湊值的範圍（0～232−1）想像成首尾相接的一個環，機器和 key 用同一個雜湊函式放上環。規則只有一條：key 歸順時針方向遇到的第一台機器。

照這條規則，加入一台機器 D 時，只有 D 和它逆時針方向上一個點之間的那一段 key 會改變歸屬：這段 key 原本往順時針走會先遇到下一台，現在先遇到 D，於是全部搬到 D。環上其他段的 key，順時針遇到的第一台機器沒變，完全不動。移除一台時也一樣，只有原本屬於它的 key 要搬到下一台。平均下來，N 台加到 N+1 台只要搬 1/(N+1) 的 key，正好是新機器該分到的那一份。

但每台機器只放一個點不夠平均。點的位置是雜湊決定的，等於隨機，有的機器運氣好分到一大段弧，有的只有一小段，負責的資料量就差很多。解法是虛擬節點（virtual node）：一台實體機器在環上放很多個點，例如 db-1#0、db-1#1…db-1#99 各自雜湊出一個位置。每個點仍然負責它和上一個點之間的那段弧，一台機器的總負擔就是它所有點的弧長加起來；點越多，隨機造成的大小段會互相抵消，每台的總和越接近平均。執行後比較三行，看每台的比例怎麼隨點數變平均：

每台 1 個點時，最多的一台分到 63%、最少的不到 9%；10 個點還是有一台分到 48%；100 個點時落在 22%～30% 之間。虛擬節點還有一個好處：可以依機器大小給不同數量的點，大一倍的機器放兩倍的點，就分到約兩倍的資料。Amazon 的 Dynamo（2007）就用這個做法。點多了也讓增減機器更平順：只放一個點時，加入的新機器只從順時針下一台分走一段，移除一台會把它的量全部倒給下一台，那位鄰居的負載直接翻倍。每台有 100 個點時，新機器的點散在環上各處，會從所有舊機器各分走一小段；移除一台時，它的量也分散到所有機器，不會壓在單一鄰居上。練習 2 你會寫出完整的雜湊環，並用 1 萬個 key 驗證搬動比例和分布。

雜湊環不是唯一做法，還有 jump consistent hash、rendezvous hashing 等演算法，比較表放在課末。正式環境更常見的是一個折衷：固定數量的邏輯分片＋目錄。一開始就把 key 空間切成例如 1,024 個邏輯分片，key 用雜湊對應到邏輯分片，這個對應永遠不變；再用一張目錄表（directory）記錄「每個邏輯分片目前放在哪一台實體機器」。加機器時，把幾個邏輯分片整個搬到新機器、改目錄就好，不用重新計算任何 key。目錄的代價是它本身要高可用、要快取，是另一個要維運的元件；好處是最有彈性，前面說的大客戶獨立一片，也是靠目錄記錄。

到這裡，每筆訂單依 customer_id 穩定地落在某一片，加機器也只搬一小部分。接著輪到查詢：帶著 customer_id 的查詢只問一片，但總部後台和店員的查詢沒帶它。

查詢沒帶分片鍵怎麼辦？scatter-gather

總部的後台要看「全公司最新的 20 筆訂單」。這個查詢沒帶 customer_id，系統不知道最新的訂單在哪幾片，只能每一片都問，再把結果合併。這個做法叫 scatter-gather：把查詢分散（scatter）到每一片，再收集（gather）回來合併。

概念很簡單，但最常見的錯誤出在「每片要取幾筆」。直覺是要 6 筆、有 3 片，每片取 2 筆就好。下面的資料刻意讓最新的訂單都在第 0 片，像是某位大客戶正在辦活動。執行後比較兩行的結果：

每片取 2 筆的結果混進了 b、c 的舊訂單，第 0 片真正最新的 a2～a5 被漏掉了，而且程式不會報任何錯。原因是「最新的 6 筆」是對全部資料的條件，某一片可能剛好擁有全部 6 筆；每片取 limit ÷ 片數，等於假設每片各有一樣多，這個假設在大客戶辦活動、某一片特別忙的時段就不成立。hash 分片保證的是長期總量平均，不保證某一段時間內每片都一樣多。正確做法是每片都取 limit 筆，合併排序後再取前 limit 筆：最壞情況下 6 筆都在同一片，也拿得到。代價是片數多時要讀很多資料，所以 API 的 limit 要設上限。

每片都要問，就帶出延遲的問題：整個查詢要等所有分片都回來才能合併，所以延遲由最慢的一片決定。第 3 課講過扇出：每片有 1% 的機率很慢，問 8 片時至少一片很慢的機率是 1 − 0.998 ≈ 7.7%，原本 p99 才會遇到的慢，變成幾乎每 13 次就遇到一次。所以各片一定要平行查詢（Promise.all），不能一片一片依序問；而且要為慢的分片設逾時，這是第 8 課的主題。

後台還要能翻頁。單機時常用 OFFSET，但跨片時翻到第 50 頁，每一片都要先跳過 50 頁的資料，越後面越慢；而且翻頁之間有新訂單進來，前面的資料往後擠，offset 會讓同一筆出現兩次或漏掉。改用 Node 課第 14 課的 cursor：記住上一頁最後一筆的 (orderedAt, id)，下一頁時每片只回傳排在它之後的資料。只記 orderedAt 不夠，同一毫秒可能有兩筆訂單，翻頁時會重複或遺漏；加上 id 讓每一筆的順序都唯一。練習 3 你會把平行查詢、每片取 limit 筆與 cursor 分頁寫在一起。

scatter-gather 適合總部後台這種頻率低的查詢。但店員的待做清單每幾秒就查一次，每次都問遍所有分片太浪費，這時改用全域次要索引（global secondary index）：另外維護一張以 store_id 為分片鍵的「店 → 訂單」索引表，待做清單只查一片。代價是寫一筆訂單要寫兩個地方，通常用非同步的方式更新（第 12 課的 outbox），所以索引會短暫過時，店員可能晚一兩秒才看到新訂單。原則還是：選分片鍵時就讓最重要的查詢不必跨片，跨片的只留給頻率低、能容忍慢一點的查詢。

查詢的問題處理完了，還剩寫入的一個細節：每一片都在各自新增訂單，訂單編號從哪裡來？

各片同時新增訂單，編號怎麼不撞？全域唯一 ID

單機時，PostgreSQL 用 identity 欄位自動編號，1、2、3 往上加，由那一台資料庫保證不重複。分片後每一片是獨立的資料庫，各自從 1 開始，第 0 片和第 1 片都會產生訂單 1 號。這不只是顯示上的問題：顧客拿 1 號訂單查詢，系統不知道是哪一筆；之後重新平衡把訂單搬到別片，兩筆 1 號就直接衝突。所以需要全域唯一 ID：不靠任何一台資料庫協調，也保證不重複的 ID。

比較各種做法之前，先認識一個評估角度：ID 會被當成主鍵，存在 B-tree 索引裡。B-tree 是 PostgreSQL 預設的索引結構，把值依大小排序存放在一頁一頁的索引頁中。新的 ID 如果都比舊的大，就永遠插在最右邊那一頁，常用的頁一直在記憶體裡；如果 ID 是隨機的，每次插入的位置都不同，索引頁要不斷分裂，常用的頁也散到各處，快取命中率變差。所以表中的「依時間排序」不只是方便，也直接影響寫入效能：

做法大小依時間排序優點缺點
各片自動遞增64 位元片內是簡單跨片撞號；設不同起點與間隔也很難再加片
集中發號服務64 位元是連號發號服務是單點與瓶頸
UUIDv4128 位元否，完全隨機不用協調B-tree 索引的插入位置分散，索引頁一直分裂、快取命中率差
UUIDv7128 位元大致是（毫秒）不用協調；新資料插在索引尾端比 64 位元大一倍；會透露建立時間
Snowflake64 位元大致是（毫秒）放得進 bigint；可以從 ID 讀出時間與機器每台機器要有唯一編號；依賴時鐘

前兩種各有硬傷：各片自動遞增會撞號，集中發號又把所有寫入重新集中到一台，正是分片要避免的事。UUIDv4 不用協調，但完全隨機，傷 B-tree。剩下的 UUIDv7 和 Snowflake 都是「開頭放時間、後面放不會重複的部分」，同時做到不用協調和大致依時間排序。

UUIDv7：開頭是時間的 UUID

UUIDv7 定義在 RFC 9562（2024 年 5 月）：128 位元中，前 48 位元是 Unix 時間的毫秒數，接著是版本號、變體與隨機位元。因為開頭是時間，依 UUID 排序大致就是依建立時間排序，新資料都插在 B-tree 的右端；後面的隨機位元則讓不同機器在同一毫秒產生的 ID 也幾乎不可能相同。PostgreSQL 18 內建 uuidv7()，文件說它用毫秒時間戳加上次毫秒的時間與隨機值產生。因為時間就在 ID 裡，可以直接讀出來：下面從 PostgreSQL 18 文件的範例值讀出版本與建立時間。

這裡說「大致依時間排序」，是因為不同機器的時鐘有幾毫秒的差，同一毫秒內的先後也不保證，但整體上越新的 ID 越大。這種「整體有序、誤差在一個小範圍內」的性質叫 k-sorted。對 B-tree 來說這就夠了：新 ID 都插在右端附近，不會散到各處。

UUIDv7 的缺點是 128 位元，比 bigint 大一倍，每個索引、每個外鍵都跟著變大。如果想要 64 位元、又能從 ID 讀出是哪台機器產生的，就是 Snowflake。它要把幾個欄位擠進一個 64 位元整數，得先會位元運算。

拼裝 Snowflake 之前：位元運算

Snowflake ID 是 Twitter 2010 年開源的做法：把一個 64 位元整數切成幾個欄位，分別放時間、機器編號、序號。要把三個數字拼成一個、再從一個拆回三個，要用位元運算。前面的課沒用過，先看這四個：

運算意思例子（二進位）
a << n左移 n 位，等於乘以 2n，右邊補 0101 << 2 = 10100（5 → 20）
a >> n右移 n 位，等於除以 2n 取整數，最右邊 n 位丟掉10111 >> 2 = 101（23 → 5）
a | b或：任一邊是 1 就是 1。欄位不重疊時，等於把它們拼起來10100 | 00011 = 10111
a & b且：兩邊都是 1 才是 1。用遮罩（mask）只留下想要的位元10111 & 00011 = 00011

拼的方法是：把每個欄位左移到它該在的位置，再用 | 合起來；拆的方法是：右移把欄位移回最右邊，再用遮罩去掉左邊不要的位元。還有一個 JavaScript 特有的限制：number 做位元運算時會先被轉成 32 位元整數，64 位元的 ID 會被截掉，所以要用 bigint（TypeScript 課第 5 課）。bigint 的字面值後面加 n，例如 22n；bigint 和 number 不能混著算，要用 BigInt(x) 與 Number(x) 轉換。下面先用一個縮小版練習拼和拆，後半段示範用 number 會出什麼錯：

Snowflake 的結構與兩個邊界情況

實際的 Snowflake 把 64 位元切成四段：

最高位固定為 0，讓整個 ID 是正數，放得進 PostgreSQL 有號的 bigint。時間欄位存的不是 1970 年起的毫秒數，而是距離 epoch 的毫秒數；epoch 是自己選的起點，例如服務上線那天，這樣 41 位元從那天開始算，可以用 241 毫秒 ≈ 69.7 年。機器編號讓不同機器產生的 ID 一定不同，序號讓同一台機器同一毫秒產生的 ID 不同。這個設計有兩個邊界情況，練習 4 都會測：

第一個是序號用完。同一毫秒內，序號從 0 遞增，12 位元最多到 4,095。如果同一毫秒要產生第 4,097 個，序號會溢位到機器編號的位元，產生的 ID 可能和別台機器的重複。正確做法是等到下一毫秒，序號歸零再繼續。

第二個是時鐘倒退。伺服器會透過 NTP（網路校時協定）定期跟時間伺服器對時，校時可能把時鐘往回調幾毫秒。這時再產生 ID，時間欄位比上一個小，序號又從 0 開始，可能和之前產生過的 ID 完全一樣。Twitter 開源的 Snowflake 專案在 README 裡寫的做法是：拒絕產生，直到時間超過上一次產生 ID 的時間。

ID 產生的方式也會影響安全。連號的 ID 會洩漏營業量：今天的訂單號減昨天的，就是一天的單量；它也讓人可以一個一個試別人的訂單，就是認證課第 19 課的 BOLA。Snowflake 和 UUIDv7 雖然不連號，但看得出建立時間，也不是完全猜不到。所以授權檢查一定要做，ID 難猜只是多一層保護。

💡 實務上：64 位元 ID 進 API 一律用字串
後端用 Snowflake 或 bigint 當訂單 ID 時，回給前端的 JSON 要放字串：JSON.parse 會把超過 253 的數字悄悄改掉，畫面上看不出錯，直到用這個 ID 查訂單查不到才發現。Twitter 的 API 就是因此另外提供 id_str。新專案選 ID 時，單機 PostgreSQL 用 identity 就好；要在多個服務或分片產生 ID，UUIDv7 不用分配機器編號，時鐘倒退頂多讓順序亂一點、靠隨機位元也不會撞號，通常比自己寫 Snowflake 省事。咖啡店的訂單分片後，訂單編號就屬於這種情況。

到這裡，訂單表的拆法、查法、編號都定好了，可以上線。但分片不是上線就結束：幾個月後，某一片可能因為一批大客戶而比其他片滿得快。

上線之後：某一片太滿怎麼辦、平常要看什麼？

增減節點、或某一片太滿時，把資料搬動讓各片重新平均，叫重新平衡（rebalancing）。前面選一致性雜湊或邏輯分片，就是為了讓這件事只需要搬一小部分；但就算只搬一小部分，也是在服務持續接單時搬，不能停機。常見的步驟是：

  1. 開始雙寫：新進的寫入同時寫到舊位置和新位置。
  2. 回填：把舊位置既有的資料複製到新位置。
  3. 比對兩邊是否一致。
  4. 讀取切到新位置。
  5. 停止寫舊位置。

順序的用意是：任何時候舊位置都還有完整的資料，所以每一步出問題都能回頭，細節在第 19 課。搬動本身也會消耗磁碟 IO，跟正常的下單搶資源，所以要限速，並避開尖峰時段。

重新平衡是事後補救，更好的是提早發現哪一片快出問題。分片上線後要看每一片各自的指標，不能只看平均：10 片的平均 CPU 是 40%，可能是 9 片 30%、1 片 100%，平均值會把熱點藏起來。

  • 資料量與成長速度：哪一片會最先滿，什麼時候該開始搬。
  • QPS（每秒查詢數）與 p99 延遲：最熱的一片是不是遠高於中位數。比例持續失衡代表分片鍵有熱點。
  • 最熱的 key：一個大客戶或一家旗艦店可能就讓一片過熱，需要單獨搬走或加尾碼拆開。
  • 跨片查詢的比例：越來越高代表存取模式變了，選分片鍵時的假設已經不成立，分片鍵可能要重新評估。

最後一個指標接回了這課的起點：分片鍵是依當時的存取模式選的，存取模式會變，所以選完之後還要持續驗證。

補充與查表

hash32 為什麼多了收尾步驟

本課的 hash32 是 FNV-1a 再加上 MurmurHash3 的收尾步驟（fmix32），也就是範例裡 h ^= h >>> 16 開始的那幾行。只用 FNV-1a 的話，db-1#0、db-1#1 這種只差一個字的字串，雜湊值會擠在一起，虛擬節點就散不開；收尾步驟把位元再攪亂一次，讓相近的輸入得到差很遠的輸出。

雜湊環＋虛擬節點本課的做法可以任意增減、可以依容量給權重要存所有點；查詢要二分搜尋
jump consistent hashLamping 與 Veach（2014）的短演算法，輸入 key 與桶數，算出桶編號不需要記憶體、分得比環更平均桶必須是 0～N−1 連續編號，只能從尾端增減；中間壞一台不能直接拿掉

分片之外的分擔方式：資料儲存怎麼選

分片是把同一種資料拆到多台；另一種分擔方式是讓不同的資料去適合它的儲存。選法同樣從存取模式出發：

類型擅長咖啡店的例子
關聯式（PostgreSQL）交易、約束、JOIN、各種查詢訂單、付款、會員
鍵值（Redis 這類）依 key 讀寫單筆，非常快，常有 TTLsession、購物車、限流計數（第 10 課）
文件資料庫結構多變的 JSON 文件，依 ID 整份讀寫各國加盟店不同格式的設定；PostgreSQL 的 JSONB 常常就夠
全文搜尋引擎斷詞、相關度排序、模糊比對菜單搜尋；先用 PostgreSQL 課第 28 課的全文檢索
物件儲存（S3 這類）大檔案，便宜、耐久商品圖片、匯出的報表檔
資料倉儲大量資料的彙總分析營運報表，由 CDC 從主資料庫同步

表中的 CDC（change data capture）是把資料庫的每一筆變更串流出去，讓其他系統跟著更新。每多一種儲存，就多一套要學、要監控、要備份、要和主資料同步的系統。原則是：先用 PostgreSQL，等數字證明它撐不住再加。資料同步到第二個儲存時，它一定會比主資料晚一點，要用第 6 課的眼光決定哪些讀取能容忍過時。

練習

練習 1：量化比較分片鍵。寫 evaluateShardKey(key, queries, rowsByValue)：singleShardShare 是「filters 包含 key 的查詢」的 perSec 總和 ÷ 全部查詢的 perSec 總和；hottestShare 是 rowsByValue 裡最大的值 ÷ 所有值的總和。再寫 chooseShardKey(candidates, queries, maxHottestShare)：在 hottestShare ≤ maxHottestShare 的候選中，選 singleShardShare 最大的；一樣大時選 hottestShare 較小的；還是一樣就選前面的；沒有候選符合時回傳 null。

練習 2：完成 HashRing。add(node) 在環上放 vnodes 個點，第 i 個點（i 從 0 開始）的位置是 hash(`${node}#${i}`)；remove(node) 拿掉這台的所有點；get(key) 算出 h = hash(key)，回傳第一個位置 ≥ h 的點所屬的節點，超過最後一個點就繞回第一個點。兩個點位置相同時，節點名稱字母順序較小的排前面。環是空的時候，get 丟 Error。測試會用 1 萬個 key 檢查搬動比例和分布。

練習 3：跨分片查最新訂單。寫 latestOrders(shards, limit, before)：每個 shard 函式回傳該片中排在 before 之後的前 limit 筆（before 是 null 時從最新開始）。順序是 orderedAt 由新到舊，相同時 id 由大到小（字串比較）。你要同時查詢所有分片，每片都要給 limit 與 before，合併後依同樣的順序取前 limit 筆。next 是最後一筆的 cursor（只有 orderedAt 與 id 兩個欄位）；取到的筆數不足 limit 時 next 是 null。

練習 4：Snowflake ID 產生器。寫 createSnowflake({ machineId, epochMs, now })，回傳一個每次呼叫產生一個 bigint ID 的函式：ID = (now − epochMs) << 22n | machineId << 12n | sequence。規則：machineId 必須是 0～1023 的整數，否則丟 RangeError；同一毫秒內 sequence 從 0 遞增；換到新的毫秒時 sequence 歸零；序號用完（同一毫秒已經產生 4,096 個）時，一直呼叫 now() 直到進入下一毫秒；now() 比上一次產生 ID 的時間小時，丟 ClockMovedBackwardsError。另寫 parseSnowflake(id, epochMs) 把 ID 拆回三個欄位。時間只能用傳進來的 now。

練習 5：4 台快取伺服器用 hash(key) % N 分配 key。加到 5 台時，大約多少 key 會換到別台？

✓ 雜湊值沒變，但 % 4 和 % 5 的結果只有在少數情況下相同（本課範例實測約 79% 換機器）。對快取來說，這等於幾乎全部失效、所有請求同時打到資料庫。20% 是一致性雜湊才做得到的理想值：只有新機器負責的那一段要搬。

練習 6：用 store_id 當分片鍵、用 hash 分配。台北旗艦店佔全部訂單的 30%，會發生什麼事？

✓ hash 只能把不同的值打散，同一個值永遠雜湊到同一個位置。分成 10 片時，理想上每片 10%，旗艦店那片卻至少 30%。要嘛換分片鍵（例如 customer_id），要嘛替熱門值加尾碼拆成多個 key，代價是查旗艦店時要讀多片。用 store_id 做 hash 分片時，同一個值不會被自動拆到多片。

練習 7：訂單分在 4 片。要查全公司最新的 20 筆，工程師讓每片取 5 筆再合併。這樣對嗎？

✓ 平均而言每片各有 5 筆，但「最新的 20 筆」是全域的條件，某一片在某個時段特別忙（大客戶辦活動）時，前 20 筆可能全部來自它。只取 5 筆就會漏掉資料，而且沒有任何錯誤訊息。hash 讓長期總量平均，不保證某一段時間內每片都一樣多。

練習 8：資料庫分成 4 片之後，訂單 ID 還能繼續用每片 PostgreSQL 的 identity 自動編號嗎？

✓ identity 只保證在那一個資料庫裡唯一。第 0 片和第 1 片都會產生 1 號訂單。加上分片編號可以暫時區分，但資料一搬到別片（重新平衡）ID 就要改，外部系統存的 ID 全部失效。UUIDv7 和 Snowflake 不需要協調就全域唯一，而且大致依時間排序。

練習 9：訂單表 300 GB、尖峰每秒 5 筆寫入，「我的訂單」和報表越來越慢。同事提議馬上依 customer_id 分片，最恰當的回應是？

✓ 這個量一台 PostgreSQL 撐得住，慢的是讀取；讀副本、快取、分割表都比分片便宜，而且可以回頭。分片的跨片查詢、重新平衡和維運代價會一直付下去。c 錯在報表不帶 customer_id，每次都要查遍所有分片，延遲由最慢的一片決定。

常見錯誤

  • 太早分片：咖啡店 5 年才 284.7 GB，一台 PostgreSQL 就夠。先用垂直擴充、讀副本、快取、分割表、依功能拆庫；分片的代價（跨片查詢、重新平衡、維運）會一直付下去。
  • 選好實作而不是好查詢的分片鍵：從存取模式出發，量化「單片查詢比例（依流量加權）」和「最熱的一片佔多少」。
  • 以為 hash 就不會有熱點：hash 只打散不同的值，同一個值永遠在同一片。熱門的店或大客戶要單獨處理。
  • 用 hash % N 分配：增減一台機器幾乎所有資料都要搬、快取幾乎全部失效。用一致性雜湊或固定數量的邏輯分片。
  • 一致性雜湊不放虛擬節點：每台只放一個點時，分布可能差好幾倍。
  • 跨片查詢每片只取一部分：結果會少資料，而且不會報錯。每片都取 limit 筆，平行查詢，並且記得延遲由最慢的一片決定。
  • 跨片分頁用 offset 或只用時間當 cursor：會重複或遺漏。cursor 用 (orderedAt, id)。
  • 64 位元 ID 用 JavaScript number：超過 253 就不精確。計算用 bigint，JSON 裡用字串。
  • 忽略時鐘倒退：NTP 校時後可能產生重複 ID。拒絕產生，等時鐘追上。
  • 連號 ID 直接對外：洩漏營業量、方便列舉他人的資料。授權檢查一定要做。

小結

  • 分片是把同一張表拆到多台獨立的資料庫，解決單機撐不住的寫入、儲存與記憶體。代價是跨片交易與查詢要自己處理，所以先用垂直擴充、讀副本、快取、分割表、依功能拆庫，有數字證明都不夠才分片。
  • 分片鍵從存取模式選：大部分查詢都帶、沒有熱點、一筆交易在同一片。用「單片查詢比例（依流量加權）」與「最熱的一片佔多少」量化比較；咖啡店因此選 customer_id。
  • range 分片利於範圍查詢，但新資料集中在最新的一片；hash 分片打散不同的值，但同一個值永遠在同一片。
  • hash % N 改變 N 時大部分 key 要搬；一致性雜湊只搬約 1/(N+1)（新機器分到的那一份），虛擬節點讓分布平均、也能依容量加權。正式環境常用固定數量的邏輯分片＋目錄。
  • 沒帶分片鍵的查詢用 scatter-gather：平行查詢、每片都取 limit 筆再合併，用 (時間, id) 的 cursor 分頁，延遲由最慢的一片決定。高頻的跨片查詢改用全域次要索引。
  • 全域唯一 ID：UUIDv7（RFC 9562，PostgreSQL 18 的 uuidv7()）或 Snowflake（41／10／12 位元），開頭是時間所以對 B-tree 友善；用 bigint 計算、JSON 用字串、處理序號用完與時鐘倒退。
  • 上線後看每一片各自的資料量、QPS、延遲與跨片查詢比例；某一片太滿時用雙寫、回填、比對、切讀、停寫的步驟線上重新平衡。
  • 不是所有資料都要放進分片的 PostgreSQL：先用 PostgreSQL，有數字證明撐不住再加別種儲存（見課末）。
