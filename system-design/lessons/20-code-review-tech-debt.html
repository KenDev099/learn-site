階段 5：資深工程實踐：決策、演進、審查與除錯 · 第 20 課

Code review 與技術債

同事送來一個 PR：櫃台可以用集點卡兌換點數。三位審查者留了 14 則意見：「變數叫 tmp 不好」「這裡少一個空行」「建議改用 const」……全部都是命名和排版，然後核准、合併。週年慶當天，同一張卡在兩台 POS 上同時兌換，10 點兌出了 20 點的飲料；兌換失敗時 API 還回傳成功，店員以為扣到了。log 裡印滿了顧客的完整手機號碼。三個問題都寫在那個 PR 裡，沒有人看到，因為大家在看容易看的東西。

這課從審查者的位置重走一次這個 PR：review 到底該擋什麼、時間有限先看哪裡、意見怎麼寫作者才分得出輕重、後端程式碼裡哪些寫法一看到就要停下來。接著換到作者的位置，送出修正的 PR。事後檢討時，團隊發現這個 bug 的根源是一段沒人敢改的舊程式，最後兩節處理它：用「利息」決定先還哪一筆技術債，再用特徵測試在沒有測試的舊程式上安全地重構。

這課的路線：
  1. 審查者該負責什麼、先看哪裡：為什麼 14 則意見都在命名排版，三個真正的 bug 卻沒人看到（開場問題的最小答案）。
  2. 意見怎麼寫：用 Conventional Comments 標出「不改不能合併」，評論程式碼、不評論人。
  3. 正確性看什麼：先讀再寫、吞掉錯誤、log 印個資這類後端寫法，審查時一眼認出來。
  4. 換到作者：修正的 PR 怎麼寫才好審、多大才審得完、收到意見怎麼回。
  5. 事後檢討：兌換流程為什麼難改。用利息決定先還哪一筆技術債，用特徵測試鎖住舊程式的行為再重構。
這課會用到：
  • 部署課第 14 課的分支與 PR：在自己的分支上改，開 PR 請同事審查，通過後才合併進主分支。
  • PostgreSQL 課第 19 課的 lost update 與條件更新：兩個請求都先讀再寫會互相蓋掉；把判斷放進 UPDATE … WHERE 就是一個原子操作。

審查者到底該負責什麼？

開場那三位審查者並沒有偷懶，14 則意見代表他們真的逐行讀過。問題出在他們不清楚 review 是為了什麼，所以自然把力氣花在最容易看出來的地方。要改掉這個習慣，得先把 review 的目的講清楚。

Code review 是程式碼合併進主分支之前，由作者以外的工程師檢視這次的改動。在 GitHub 上，被審查的那一組改動叫 PR（pull request）；Google 公開的審查指南（Google Engineering Practices）把它叫 CL（changelist），指的是同一件事，這課一律寫 PR。

Review 有三個目的：

  • 及早抓錯：並發、權限、資料正確性這類錯誤，測試常常測不到，因為單獨執行時程式完全正確。合併前發現，改幾行就好；上線後才發現，要修資料、道歉、寫事故報告。開場的超額兌換，兌出去的飲料已經被喝掉了，收不回來。
  • 維持程式碼健康（code health）：程式碼健康指的是程式碼好不好讀、好不好改、好不好測、會不會出錯的整體狀態。每個 PR 都讓它變好一點或變差一點，累積起來就決定了一年後大家敢不敢改這個專案。
  • 分享知識：每一段程式碼至少有兩個人看過，原作者請假或離職時，還有人懂。新人從意見裡學到團隊的做法，資深的人也從新人的問題發現自己沒寫清楚的地方。

拿這三個目的對照開場：14 則命名與排版的意見只碰到「好不好讀」這一小塊，「及早抓錯」完全落空。Google 的指南把維持程式碼健康當成主要目的，抓錯和分享知識都是為了它；但對開場這種會出事故的 PR，第一關是抓錯。審查者不是看錯了，而是從一開始就沒有去找會出事的地方。

那審查者要把 PR 要求到什麼程度才核准？Google 的指南給了一個標準：只要這個 PR 明確改善了整體程式碼健康，審查者就應該傾向核准，即使它不完美。指南的說法是沒有「完美」的程式碼，只有更好的程式碼。審查者追求的是持續改善，不是讓作者改到審查者心中的理想樣子為止。這個標準存在的原因很實際：如果每個 PR 都要改到審查者滿意，一個 PR 來回好幾輪，作者就會傾向少送、送大的，審查反而更難做。

同一份指南還有兩條處理分歧的原則。第一，技術事實與資料優先於個人意見與偏好：「我覺得 map 比較好看」敵不過「兩種寫法結果相同」。第二，風格問題以團隊的 style guide 為準。style guide 是團隊寫成文件的程式風格規範，規定命名、排版、該用哪些寫法；有了它，風格之爭查文件就好，不用每個 PR 重新吵。

要注意「明確改善整體健康就核准」的前提：PR 本身不能引進新的錯誤。兌換集點的 PR 帶進了一個並發 bug，它讓整體健康變差，再整齊也不該核准。所以審查者的首要責任是找出會出事的地方。但一個 PR 動輒幾百行，審查者的時間有限，該先看哪裡，才不會像開場那樣把注意力全花在命名上？

時間有限，先看哪裡？

排序的原則只有一條：先看錯了影響最大、最難事後補救的東西。變數名稱取得不好，下一個 PR 改名就好，沒有任何使用者受影響；超額兌換一旦發生，錢和飲料都已經出去了。Google 指南列的檢查重點依序是設計、功能、複雜度、測試、命名、註解、風格、一致性、文件；對後端來說，可以整理成這個順序：

最上面那層「風格」，根本不該花人力。縮排、引號、空行、import 順序，這些都有工具可以處理：

  • formatter 是自動排版的工具，例如 Prettier。它不判斷寫法好壞，只把縮排、引號、換行統一成同一種樣子，存檔或提交時自動改好。開場「少一個空行」這種意見，交給它就不會出現。
  • lint 是靜態檢查工具，例如 ESLint。它不執行程式，只讀原始碼，依照規則找出可疑的寫法：宣告了卻沒用的變數、可以用 const 卻用了 let。開場「建議改用 const」這則意見，lint 規則就能擋。

把 formatter 與 lint 放進 部署課第 15 課的 CI，每次 push 都自動跑；型別檢查、測試、相依套件的漏洞掃描、API 的破壞性變更檢查（第 19 課）也讓 CI 先跑。CI 沒過，PR 根本不會進到審查者手上。機器擋得住的，人就不用看，每多一個自動檢查，人就少爭論一件事，審查者的注意力留給機器看不懂的設計與正確性。

把注意力移到下層之後，還有一個常見的盲點：只看 diff。diff 只顯示改了哪幾行，但正確性常常取決於這幾行周圍的東西。新的函式會被誰呼叫？呼叫者是不是在交易裡？這個 SQL 查的表有多大？以兌換集點為例：diff 只是一個新檔案，看不出櫃台有幾台 POS、會不會同時兌換同一張卡，也看不出 logger 寫到哪裡、誰看得到那裡的 log。把 diff 打開成完整檔案、搜尋呼叫者、問一句「這個會在什麼情況下被呼叫」，常常才看得出問題。

另一個習慣是被指派審查的程式碼，人寫的部分每一行都要真的讀過；產生出來的檔案、大型資料可以快速掃過。看不懂就直接說看不懂：審查者看不懂的程式碼，以後接手的人也看不懂，這本身就是值得提出的意見。

假設這次審查者真的看到了先讀再寫的問題，把它寫成第 15 則意見，夾在 14 則命名建議中間送出去。作者打開 PR，看到 15 則看起來分量差不多的意見，還是分不出哪一則不改就會出事。所以下一個問題是意見本身怎麼寫。

怎麼讓作者分得出哪一則非改不可？

作者收到一堆意見時，最怕的是分不出哪則是「不改就不能合併」、哪則是「隨口一提」。如果全部當成必須修改，每一則都要改或爭論，PR 拖好幾天；如果全部當成建議，真正的 bug 就可能被當成偏好略過。解法是讓每則意見自己說明分量。

Conventional Comments 是一種公開的意見格式約定：每則意見開頭先寫一個標籤（label），說明這則意見是什麼；後面可以加上裝飾（decoration），說明它擋不擋合併；冒號後面才是內容。格式是：

<label> [decorations]: <subject>

[discussion]

標籤有十幾個，日常最常用的是這五個（完整清單在課末的補充與查表）：

  • issue：指出一個具體的問題，最好附上建議的修法。
  • suggestion：提出改善方式，說明建議什麼、為什麼。
  • nitpick：不重要、偏好性的小建議（常簡寫成 nit），應該是 non-blocking。
  • question：可能有問題、可能沒有，請作者說明。
  • praise：稱讚做得好的地方。真心的才寫。

Conventional Comments 的官方網站（conventionalcomments.org）列出的裝飾有三種（團隊也可以自己定義，但越少越清楚）：(blocking) 這則沒解決就不能合併；(non-blocking) 不影響合併；(if-minor) 改起來很小才需要改。拿開場的 PR 套用，意見會長這樣：

issue (blocking): 先讀餘額再扣點，兩台 POS 同時兌換時兩邊都會通過檢查。
  改成一句條件更新：UPDATE … SET balance = balance - $1 WHERE id = $2 AND balance >= $1

nitpick (non-blocking): tmp 改成 cardId 比較好讀。

question: 50 點的上限是哪裡來的？產品規格還是暫定？

praise: 輸入驗證寫得很完整，非整數和負數都擋掉了。

作者一眼就知道：第一則不處理就不能合併，第二則改不改自己決定，第三則要回答，第四則的做法要保留。這就是格式帶來的差別：分量寫在意見的第一個字，不用靠作者猜審查者的語氣。

這套格式要有用，blocking 的意見必須少而且有理由：資料錯誤、安全漏洞、會造成事故的設計。命名、偏好的寫法標 non-blocking，讓作者自己決定。如果審查者什麼都標 blocking，標籤就失去意義，作者又回到分不出輕重、每一則都要爭論的狀態，review 也跟著慢下來。Google 的做法類似：不重要的意見前面加 Nit:。

praise 看起來像客套，其實有實際用途。Google 的指南特別提到，看到做得好的地方就說出來，以培養人來說，有時比指出錯誤更有用：作者因此知道哪些做法要保留、下次照做。Conventional Comments 也建議每次審查至少有一則真心的 praise。

最後是語氣。同一個問題，換一種說法，作者的反應完全不同：

評論程式碼，不評論人。「你為什麼又沒處理錯誤？」換成「這裡的 catch 會把資料庫錯誤變成成功的回應，呼叫端會以為扣到了」。說事實、說後果、說建議的做法。

審查者這一側還有兩件事。第一是 PR 太大時：Google 指南的建議是請作者拆成幾個互相銜接的小 PR；真的拆不了，至少先對整體設計留意見、退回改善，不要硬著頭皮逐行看完一整天。

第二是速度，它也是標準的一部分。Google 的建議是收到審查請求後，最多一個工作天內回覆（不一定要看完，至少要回應）。這條和 PR 大小是連在一起的：審查卡住，作者就會把好幾件事塞進同一個 PR 以免再等一次，PR 越來越大，就更沒人想審，審查又更慢。審查者在剩下的意見都很小、或確定作者會處理時，也可以「帶著意見核准」，讓作者改完直接合併，省一輪往返，跨時區時特別有用。

💡 實務上：新人也能審資深同事的 PR
剛進團隊，你常會被指派審資深同事的 PR，例如兌換集點的 PR。架構好壞你也許還判斷不了，但有幾件事一定看得出來：點數不夠會怎樣、同一筆按兩次會不會扣兩次、出錯時回給前端什麼。看不出答案就用 question: 問，例如「兩台 POS 同時兌換同一張卡會怎樣？」，這不算打擾，也是最快熟悉系統的方式。只對你真的看懂的部分核准，並在意見裡寫清楚範圍，例如「我看了 API 與輸入驗證，交易的部分請另一位同事確認」。

正確性要看什麼？後端高風險寫法圖鑑

知道要先看正確性、也知道怎麼標 blocking 之後，剩下最難的一步是認出問題。開場三位審查者都讀過那幾行，卻沒人看出來，因為這些寫法單獨看起來都很正常。

前端的錯通常只影響一個使用者的畫面，重新整理就好；後端的錯會同時影響所有人，而且寫進資料庫就收不回來。後端的高風險寫法有一個共同點：單獨執行時完全正確，所以測試會過、手動點也沒問題，要等到同時有很多請求、網路出錯、資料量變大時才出事。審查者能做的，是記住這些寫法的「形狀」，看到時停下來問一句。下面先拆開開場 PR 裡最難看出來的那個，再列出其他常見的。

第一個也最常被漏掉的：先讀再寫。程式先查餘額、判斷夠不夠，再扣。這段範例用假資料庫模擬：每次讀寫都要等一次往返，等待的時候別的請求可以插進來，就像真的資料庫連線一樣。執行後比較兩行輸出的回傳結果和最後的餘額：

第一行是 PR 裡的寫法：兩個請求都回傳 'ok'，只有 10 點的卡兌換了兩次，餘額變成 −10。過程是這樣的：

  1. 請求 A 讀餘額，讀到 10，判斷夠扣。
  2. 請求 A 等待寫入的往返時，請求 B 也讀餘額。A 還沒扣，所以 B 也讀到 10，也判斷夠扣。
  3. A 扣 10 點，餘額 0；B 再扣 10 點，餘額 −10。

你可能會想：把寫入改成 balance = balance - $1 的相對更新，不就不會互相蓋掉了嗎？相對更新確實能讓兩次扣點都算進去，但它救不了這個 bug，因為「夠不夠」是在另一句查詢裡判斷的，兩個請求判斷時看到的都是 10。問題不在怎麼寫入，而在檢查和寫入之間有空隙。

第二行是修正後的寫法：檢查和扣點在同一步完成，中間沒有空隙，所以只有一個請求成功，另一個拿到 'insufficient'，餘額停在 0。在真的資料庫裡，讓檢查和寫入成為同一個原子操作有三種做法（PostgreSQL 課第 19 課）：

  • 條件更新：把判斷寫進 UPDATE … WHERE balance >= $1，更新了 0 列就代表餘額不足。只要一句 SQL，最常用。
  • SELECT … FOR UPDATE：讀的時候就鎖住這一列。另一個同樣用 SELECT … FOR UPDATE 讀這一列的請求，要等前一個交易結束才拿得到鎖，讀到的就是扣完的餘額。一般的 SELECT 不會被這個鎖擋住，所以兩邊都要用 FOR UPDATE 才有效。
  • CHECK (balance >= 0) 限制：讓資料庫拒絕任何會讓餘額變成負數的寫入。前提是扣點用相對更新 balance = balance - $1，這時就算程式漏了檢查，餘額也不會變負數；如果程式先讀再把算好的值寫回去，兩個請求都寫 0，CHECK 照樣放行。違反限制時資料庫會丟出錯誤（不是更新 0 列），程式要把它轉成餘額不足，否則又會掉進下面表格「catch 之後回傳成功」的坑。它適合當最後一道防線，不能取代條件更新。

審查時看到「先查、判斷、再寫」，就問自己：兩個請求同時進來會怎樣？

開場 PR 的另外兩個 bug 也各有固定的形狀：catch 之後回傳成功、log 裡出現手機號碼。下面這張表收集了後端審查最值得停下來看的寫法，前幾課大多教過修法。查表用，不用背；審查時對照著看，久了自然會記住形狀。

金額用浮點數0.1 + 0.2 !== 0.3，對帳差一塊錢用整數（元或分），或資料庫的 numeric
只檢查有沒有登入，沒檢查資源是不是他的改網址的 id 就能看別人的訂單（BOLA）每個資源都檢查擁有者（認證課第 24 課）

表裡的「catch {} 之後回傳成功」值得多說一句，因為它在開場直接造成了店員的誤會：catch 把資料庫錯誤和找不到卡片都變成 ok: true，前端收到成功就顯示扣點完成，實際上什麼都沒發生，而且因為沒有錯誤被記錄，也沒有人收到告警。同理，log 系統通常比資料庫開放給更多人看（維運、客服、外包廠商），手機號碼一旦印進去，就等於複製到一個權限更寬的地方。

這張表可以當成團隊的審查清單，但不要變成照表打勾。清單抓的是「已知的錯」；設計上的問題（這個功能真的需要同步呼叫嗎？資料該由哪個模組擁有？）要靠理解需求。到這裡，審查者這一邊的工作講完了：知道要擋什麼、先看哪裡、怎麼寫意見、怎麼認出高風險寫法。但審查者只看得到作者給他的東西，review 的品質有一半掌握在作者手上。

換到作者：修正的 PR 怎麼寫才好審？

兌換集點要重送一個修正的 PR，這次你是作者。審查者不在你的腦袋裡：他不知道你為什麼這樣改、你測了什麼、上線會不會動到大表。他只看得到 diff 和 PR 說明，沒寫出來的，他就只能猜，或者乾脆不看。

第一件事是讓 PR 小而單一目的：一個 PR 只做一件事。最常見的違規是把重構和新功能混在一起。重構的 PR 行為不變，審查者只要確認「結構變好、行為一樣」；功能的 PR 只看新行為。混在一起，審查者分不出哪一行改了行為，等於每一行都要當成功能來審。

大小直接決定審查的品質。1,500 行的 PR 沒有人能認真看完，審查者最後只能按核准，review 變成橡皮圖章：有蓋章，但沒有人真的檢查。團隊可以訂一個 PR 大小的慣例，讓大改動拆成可以審的小步驟；功能還沒做完就要合併時，用第 19 課的功能旗標把它藏起來。

第二件事是把說明寫清楚。下面是修正 PR 的說明範本，先認識裡面兩個名詞：staging 是正式上線前、設定和正式環境相同的測試環境，在那裡試過的結果最接近上線後的樣子；CREATE INDEX CONCURRENTLY 是建索引時不擋住寫入的做法（PostgreSQL 課第 22 課），大表上建索引要用它，否則建索引的期間寫入全部卡住。

## 為什麼
櫃台要能用集點兌換飲料（#412）。目前只能在 App 兌換。

## 做了什麼
- 新增 POST /stamp-cards/:id/redeem，扣點用條件更新，餘額不足回 409
- 用 Idempotency-Key 防止重送扣兩次
- stamp_ledger 新增 idempotency_key 欄位與唯一索引

## 怎麼驗證
- 單元測試：餘額不足、重複 key、10 個並發請求只成功 4 個
- 在 staging 用兩台 POS 同時兌換同一張卡

## 風險
- stamp_ledger 的唯一索引建在 200 萬列的表上，用 CREATE UNIQUE INDEX CONCURRENTLY

## 怎麼回滾
- 功能旗標 pos-redeem 關掉即可；資料表改動是新增欄位，不用回滾

每一欄都在回答審查者光看 diff 回答不了的問題。「為什麼」讓審查者判斷這個改動該不該存在；「怎麼驗證」告訴他哪些情況已經測過，例如「10 個並發請求只成功 4 個」：測試裡卡片有 40 點、每次兌換 10 點，所以應該剛好成功 4 個，這直接回應了上一版的 bug，審查者不必自己再想一次；「風險」寫的是 diff 看不出來的事，例如那張表有 200 萬列。

「怎麼回滾」逼作者在上線前想好退路：只加欄位、程式碼可以直接退版；刪了欄位，就退不回去了（第 19 課的 expand → contract）。寫不出這一欄，通常代表這個改動需要再拆。

第三件事是送出之前自己先看一遍 diff：除錯用的 console.log、註解掉的程式、不相關的格式變動，自己先清掉。審查者的每一分注意力都很貴，不要花在這些地方。

Review 是作者和審查者一起為團隊的速度負責：作者送出小而清楚、自己先檢查過的 PR；審查者快速回應、分清楚輕重。誰拖延都會讓整個團隊變慢。

PR 送出去之後，意見會回來。收到意見時：

  • 先假設審查者是對的、試著理解他看到什麼。不同意時用事實與資料回應（跑一個測試、量一下查詢時間），不要用「我覺得」。
  • 每則意見都要有結果：改了、說明為什麼不改、或另外開 issue 之後處理。審查者寫了 blocking 的意見，在它解決之前不能合併。
  • 同一個問題來回三次還沒結論，就改成面對面或視訊談，談完把結論寫回 PR。意見衝突時依 Google 的原則：技術事實與資料優先、風格看 style guide、真的是設計取捨就找更資深的人或寫成 ADR（第 18 課）。
  • 審查者一直問「這是在做什麼」，代表程式碼本身不夠清楚。改程式碼（命名、拆函式）通常比在 PR 裡解釋更好，因為之後讀程式的人看不到 PR 的討論。

修正的 PR 合併了。事後檢討時有人問：當初為什麼會寫成先讀再寫？原作者說，兌換要經過訂單模組那支 600 行的 service，裡面已經有一段扣點邏輯，但沒人說得清楚它的行為，他不敢動，只好在外面另寫一段。這次的 bug 不只是一個人的疏失：程式碼難改，大家就繞著它寫，繞出來的路最容易出錯。

兌換流程為什麼這麼難改？技術債與利息

那支 600 行的 service 就是典型的技術債（technical debt）。這是 Ward Cunningham 在 1992 年提出的比喻：為了現在更快交付而做的設計妥協，像是借錢。借來的「本金」讓你這次早點上線；之後要把設計整理好，就是還本金，要花一筆時間。借錢本身不是壞事，問題在利息：在還清之前，每次修改那段程式，都要多花時間繞過它、搞懂它、小心不弄壞它。不還，利息一直付；利息夠高，團隊所有時間都拿去付利息，開場那種「不敢動、另寫一段」就是在付利息。

債不是都一樣的。Martin Fowler 的技術債四象限（2009）依兩個問題分類：借的時候是魯莽（reckless）還是謹慎（prudent）？是刻意（deliberate）還是無意（inadvertent）？

刻意無意
魯莽「沒時間做設計」：知道該怎麼做，但直接亂寫「分層是什麼？」：不知道有更好的做法
謹慎「先上線，之後再處理後果」：清楚知道借了什麼、打算何時還「現在才知道當初該怎麼做」：做完、學到了，才看出更好的設計

這張表的重點在下面那一列。謹慎而刻意的債，如果利息夠小，可以一直不還。謹慎而無意的債是好團隊一定會有的：你對領域的理解會進步，回頭看一年前的設計一定有地方想改。所以「零技術債」不是目標，目標是知道債在哪裡、利息多少，有計畫地還。上面那一列的魯莽債，則是 code review 和團隊規範要減少的。

知道有債還不夠，咖啡店的待辦裡不只一筆：訂單 service、舊的月報表 SQL、一段已經沒人用的優惠券程式。下一季能撥給還債的時間有限，該先還哪一筆？

「這段程式很亂」排不贏新功能，因為沒有人知道它到底讓團隊慢了多少。要排得進去，就要把亂換成數字：

  • 每月利息 = 每次修改多花的時間 × 每月修改次數。
  • 回本月數 = 償還要花的時間 ÷ 每月利息。整理完之後利息歸零，省下的時間要幾個月才抵得過整理花掉的時間。

結果跟直覺不一樣。訂單模組每週都要改，每次多花 3 小時，每月利息 12 小時；整理它 16 小時，一個多月就回本。舊報表更亂，每次改要多花 4 小時，但一年只改 3 次，每月利息只有 1 小時；整理它要 48 小時，4 年才回本，不如放著。沒人用的優惠券程式利息是 0，永遠不會回本；它該被刪掉，但不急。

這就是熱點（hotspot）的想法：修改頻率高、又複雜的檔案先處理。很亂但沒人改的程式，債的利息是 0；很常改但很乾淨的程式，也沒有債。兩個條件同時成立的地方，才是團隊每天在付利息的地方。修改頻率可以從 git 歷史算出每個檔案被改了幾次（指令在課末的補充與查表），複雜度可以看行數或 lint 工具算的指標。

利息之外還要看風險：有些債平常不收利息，但隨時可能造成事故，例如訂單表沒有唯一限制、只靠程式檢查。這種債不看回本，排最前面，因為它的代價不是每月幾小時，而是一次事故。練習 4 會把這個排序寫成程式。

決定了先還哪一筆，接下來是怎麼還：

  • 小步驟：做功能時順手整理要碰到的那一塊（童子軍規則：離開時比來的時候乾淨一點）。每次一小步，每步都能上線。
  • 放進待辦、寫出利息：每筆債都寫進待辦，附上估計的利息與風險，跟功能一起排優先順序，不要等到「有空再說」。「整理訂單 service，估 16 小時，每月省 12 小時」排得進去；「重構訂單 service」永遠排不上。
  • 小心「重寫」：舊程式裡每一個奇怪的 if，可能都是某次事故之後補的。從零重寫要重新發現這些邊界情況，而且重寫期間舊系統還在改，兩邊要同步。真的要換，用第 19 課的 strangler fig 一塊一塊換，而不是停下來一次重寫。
💡 實務上：跟 PM 談技術債，講對方在乎的事
跟 PM 說「訂單 service 很亂，想重構」，幾乎一定被往後排；PM 在乎的是交付時間和事故風險，要把利息換成這兩件事。例如「下個月的會員活動要改訂單流程好幾次，先整理，活動可以早幾天上線」，或「訂單表沒有唯一限制，尖峰時同一筆訂單可能建立兩次」。還在驗證市場、可能整個砍掉的功能，債先不用還；確定要長期維護的核心流程（訂單、付款、點數）才值得投資。資深工程師通常不會要求整個團隊停下來還債，而是把整理拆成小塊，搭著會碰到那段程式的功能一起估、一起做。

沒有測試的舊程式，怎麼改才不會改壞？

團隊決定先還訂單 service，一個多月就回本。但動手前馬上撞上一個問題：這支 service 沒有任何測試，裡面的外帶杯費、會員折扣怎麼算，沒人說得清楚。原作者當初不敢動它，原因正是這個。

我們要做的是重構（refactoring）：不改變外部行為地改善程式結構。同樣的輸入，改完前後的輸出必須一模一樣，只有程式碼變得比較好讀、好改。既然前提是「改完行為一樣」，就需要測試來證明。問題是最需要重構的程式，通常正好沒有測試；想補測試，又因為沒人知道它「應該」怎麼運作，寫不出規格。

Michael Feathers 在《Working Effectively with Legacy Code》提出的解法是特徵測試（characterization test），又稱 golden master。它換了一個問法：不管程式「應該」做什麼，先記錄它現在實際做了什麼。做法分三步：把一大批輸入丟進舊程式、存下輸出；重構；讓重構後的程式跑同一批輸入，輸出要完全相同。

特徵測試描述的是現況，不證明程式正確，舊程式有 bug，特徵測試也會把 bug 一起記下來。它的用處是抓回歸（regression）。回歸指的是原本正常的功能被新的改動弄壞；重構時任何一點非預期的行為改變，都會讓輸出不同，測試立刻失敗。

下面用訂單 service 裡的外帶杯費示範這三步。舊程式有一個沒人知道原因的規則：會員少 2 元。重構的人覺得它很怪，順手拿掉了。執行後看最後兩行：有幾個案例不同、不同的是哪些。

測試馬上抓到「順手」拿掉的會員優惠：會員買 1 杯以上的每個案例都不同。如果沒有特徵測試，這個改動會安靜地上線，直到某位會員發現杯費變貴了。從這個例子可以看出特徵測試的幾條紀律：

  • 連怪行為一起鎖住：會員減 2 元看起來像 bug，但可能是店長三年前談好的合作。重構時不判斷對錯，只保證不變。
  • 疑似 bug 另外處理：開一個 issue 問清楚，確定是 bug，再用一個獨立的 PR 修正、並更新特徵測試。這就是上一節「重構和功能分開」的同一條規則：重構 PR 和行為改變 PR 分開，出事時才知道是哪一個造成的。
  • 小步改、每步都比對：抽一個函式就跑一次。一次大改後才比對，出現差異時不知道是哪一步造成的。
  • 輸入要夠多樣：範例只試了 0～8 杯，手寫幾個案例會漏掉邊界。實務上用固定種子的亂數產生幾千組輸入，或從正式環境的 log 取樣（記得去除個資）。

有了特徵測試這張安全網，訂單 service 就可以一小步一小步地整理；整理到扣點邏輯清楚了，兌換功能也不必再繞著它另寫一段，開場那類 bug 的根源就消失了。練習 3 會讓你親手做一次：拆一段沒有測試的計價程式，而且結果要跟舊程式完全相同。

💡 實務上：前端的 snapshot 測試就是同一個概念
Jest／Vitest 的 snapshot 測試也是「先存下現在的輸出，之後比對」，你可能已經用過。後端常用在接手沒有測試的舊模組，例如整理咖啡店的計價或報表程式之前，先把一批輸入和輸出存成檔案。常見的坑是輸出裡有時間、亂數 id、排序不固定的陣列，每次跑都不同；先把它們固定或排除，否則測試會一直誤報。另一個坑是一看到差異就直接更新快照（-u），這等於把測試關掉；先確認差異是不是預期的改變。重構完成、補上描述規格的單元測試後，特徵測試就可以刪掉。

寫 review()，回傳你的審查意見。這段程式有三個必須擋下的問題，每個問題都要有一則 label: 'issue'、blocking: true 的意見，line 寫在問題所在的行（跨好幾行的問題，寫其中任何一行都可以）。另外還有兩個不影響正確性的小地方，要不要留意見由你決定；留的話用 nitpick 或 suggestion，而且不能 blocking。沒有問題的行不能有 blocking 的意見；每則意見的 subject 寫一句說明，不能是空字串。

練習 2：修好同一個功能。起始程式是 PR 裡的寫法搬到假資料庫上（createAsyncDb() 每個操作都要等一次往返，同時進行的請求可以在中間插隊）。改寫 redeemStamps，做到：

  • 用原子操作 db.tryDebit(cardId, points) 扣點（餘額夠才扣、回傳新餘額；不夠回傳 null），不要先讀再寫。
  • 冪等：用 db.insertIfAbsent('redeemKeys', idempotencyKey, …) 先占住這把 key。同一把 key 再送一次，回傳第一次的結果、不再扣點；第一次還沒做完就收到同一把 key，丟 RedeemInProgressError。扣點時資料庫出錯，要用 db.delete 放掉這把 key，讓之後可以用同一把 key 重試。
  • log：開始時記 'redeem start'、扣點成功後記 'redeemed'，欄位有 cardId、phone、points；手機一律遮罩成只留最後 3 碼，其他每一碼換成 *（'0912345678' → '*******678'）。
  • 資料庫丟錯時把錯誤往外丟，不能回傳成功。

練習 3：起始程式的 legacyPrice(order) 是一段沒有測試的舊程式。依照它目前的實際行為，價格是這樣算的：

  • 小計：品項的單價 × 數量加總；PRICES 裡找不到的商品直接略過（不丟錯）。
  • 優惠券：有優惠券時（coupon > 0），最多折抵 Math.floor(小計 * 3 / 10)，而且在會員折扣之前扣。
  • 會員：扣完優惠券的金額 * 95 / 100，然後只在這裡 Math.round 一次（x.5 往上進位，例如 104.5 → 105）。
  • 外帶杯費：前 5 杯每杯 5 元，第 6 杯起每杯 3 元。

寫 priceBreakdown(order)，每一種費用一個小函式，回傳 { subtotal, discount, cupFee, total }：discount 是小計減掉「優惠券與會員折扣、四捨五入之後的商品金額」，total = subtotal - discount + cupFee，而且對任何訂單，total 都要和 legacyPrice 完全相同（包括看起來奇怪的地方）。這是重構，不改行為：不能修改 legacyPrice，也不能呼叫它（直接或間接都不行）。

練習 4：寫 prioritizeDebt(items, budgetHours)，在這一季的預算時數內挑出要還的技術債，回傳依處理順序排列的 id：

  • 每月利息 = hoursLostPerChange × changesPerMonth；回本月數 = fixHours ÷ 每月利息（利息為 0 時是 Infinity）。
  • 順序：risk 是 3（隨時可能造成事故）的最先，依 fixHours 由小到大；其餘依回本月數由小到大，回本月數相同時 risk 高的先；再相同就維持輸入的順序。
  • 依這個順序挑：放得進剩餘預算就選、扣掉時數；放不進就跳過，繼續看下一個。
  • 回本月數是 Infinity 而且 risk 小於 3 的，永遠不選。
  • 不能修改傳入的陣列。

練習 5：同事送來一個 1,500 行的 PR，裡面同時有「把訂單 service 拆成三個檔案」的重構和「新增兌換集點」的功能。你怎麼 review？

✓ c。重構和功能混在一起，審查者分不出哪一行改了行為，逐行看完也很難發現問題，而且作者要等一整天才收到回應（a 錯）。CI 只證明它能編譯、既有測試通過，抓不到設計與並發的問題，核准看不完的 PR 就是橡皮圖章（b 錯）。Google 的建議是太大的 CL 請作者拆成互相銜接的小 CL，拆不了至少先對整體設計留意見。

練習 6：同事用 for...of 加 push 組陣列，你比較喜歡 map。這種寫法符合團隊的 style guide，結果也正確。你該怎麼做？

✓ a。Google 的標準：風格問題以 style guide 為準，技術事實與資料優先於個人偏好；只要這個 PR 改善了整體程式碼健康就該核准。把個人偏好標成 blocking（b）或拖著不核准（c），作者分不出哪些意見真的重要，review 也變慢。真的覺得全團隊都該用某種寫法，去改 style guide 或加 lint 規則，而不是在每個 PR 裡爭。

練習 7：「訂單模組太亂了，下個月停下功能開發，整個重寫。」這是好計畫嗎？

✓ b。舊程式裡奇怪的 if 常常是某次事故之後補的，重寫時這些知識不在任何文件裡，只能上線後再踩一次；重寫期間舊系統還在改，兩邊要同步，而且一個月後常常還沒做完（a 錯）。這跟資深與否無關，沒有人記得所有邊界情況（c 錯）。先用特徵測試鎖住行為、依利息挑熱點小步重構；真的要換掉，用 strangler fig 一塊一塊換。

練習 8：要重構一段沒有測試的舊程式，第一步是什麼？

✓ c。重構的定義是不改變外部行為，所以要先知道現在的行為是什麼。依需求文件寫的測試，會在第一次跑時就因為舊程式的實際行為不同而失敗，你分不清楚是文件過時還是程式有 bug（a 錯）。看起來像 bug 的行為可能有人依賴，要另外開 issue 確認、用獨立的 PR 修，不能混在重構裡（b 錯）。

常見錯誤

  • 只挑命名與排版：容易看的先看，並發、錯誤處理、個資這些資料正確性的問題被漏掉。依優先順序看，風格交給 formatter 與 lint。
  • 所有意見都當成必須修改：作者分不出什麼重要，每一則都要爭論。用 Conventional Comments 標出 blocking 與 non-blocking，blocking 要少而且有理由。
  • 只看 diff 不看上下文：沒發現呼叫者會在交易裡呼叫這個新函式、這張表有幾百萬列。打開完整檔案、搜尋呼叫者。
  • 核准還有 blocking 意見沒解決的 PR：blocking 的意思就是解決之前不能合併。
  • 超大 PR：沒人能認真看完，最後變成橡皮圖章。請作者拆小，重構和功能分開。
  • 針對人而不是程式碼的評論：說事實、後果和建議的做法，不說「你又……」。
  • 用 review 處理風格爭議：交給 formatter、lint 與 style guide，人不要在每個 PR 裡爭。
  • 審查拖好幾天：作者只好把更多東西塞進同一個 PR。一個工作天內至少回應一次。
  • 重構時順便改行為卻沒告訴任何人：特徵測試會抓到；疑似 bug 另外開 issue、另外一個 PR 修。
  • 技術債沒有利息估計：永遠排不贏新功能，或憑感覺全部重寫。寫出每月利息、回本月數與風險，跟功能一起排。

補充與查表

Conventional Comments 的標籤

正文用到的是最常用的五個，完整的標籤如下。查表用，不用背；團隊通常只挑幾個來用。

標籤意思
praise稱讚做得好的地方。真心的才寫
nitpick不重要、偏好性的小建議（nit），應該是 non-blocking
suggestion提出改善方式，說明建議什麼、為什麼
issue指出一個具體的問題，最好附上建議的修法
question可能有問題、可能沒有，請作者說明
todo、chore小但必要的修改；合併前必須完成的流程工作
thought、note審查時想到的點子；提醒讀者注意的事（note 一律不擋）
typo、polish、quibble錯字；內容沒錯但可以馬上改得更好；nitpick 的輕鬆說法

從 git 歷史找熱點

列出被改最多次的檔案，數字越大代表修改頻率越高，再對照檔案的行數或 lint 的複雜度指標，就能找出熱點：

git log --format= --name-only | grep -v '^$' | sort | uniq -c | sort -rn | head

小結

  • Code review 的目的是維持程式碼健康、及早抓錯、分享知識。明確改善整體健康就核准，沒有完美的程式碼；但引進新錯誤的 PR 不算改善。
  • 依優先順序看：設計與正確性 → 安全 → 可維運性 → 測試 → 可讀性 → 風格；風格交給 formatter、lint 與 CI；看 diff 也看上下文。
  • 用 Conventional Comments（issue (blocking)、nitpick (non-blocking)、question、praise…）讓作者分得出輕重；blocking 要少而且有理由；評論程式碼，不評論人。
  • 後端高風險寫法單獨執行時都正確：先讀再寫、缺冪等、交易裡呼叫外部 API、N+1、沒有上限的查詢、吞掉錯誤、log 出個資、快取 key 漏掉使用者、重試沒退避、金額用浮點數。先讀再寫的修法是讓檢查和寫入成為同一個原子操作。
  • 好的 PR 小而單一目的，說明為什麼、做了什麼、怎麼驗證、風險、怎麼回滾；審查者一個工作天內回覆，太大的 PR 請作者拆。
  • 技術債的利息 = 每次修改多花的時間 × 修改頻率；依利息、風險與成本排序，先處理熱點，小步償還，不要輕易重寫。
  • 重構沒有測試的程式前，先用特徵測試鎖住目前的行為（包括怪行為），小步改、每步比對；行為改變另外一個 PR。
