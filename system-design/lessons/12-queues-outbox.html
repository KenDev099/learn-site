階段 3：可靠性：失敗是常態 · 第 12 課

佇列、送達語意與 outbox

第 11 課那個早上 8 點，金流恢復之後，客服又收到新的抱怨：結帳按下去要轉 5 秒才有反應。追下去發現，結帳 API 在回應顧客之前，要依序做完五件事：扣款、寫入訂單、寄收據 email、通知廚房出單、幫會員集點。寄 email 的服務這個早上很慢，一封要 5 秒，於是每一張訂單都跟著慢 5 秒；它如果直接回錯，整個結帳請求就失敗，顧客不知道自己到底買成功沒有。收據晚幾秒寄出根本沒人在意，卻拖住了顧客最在意的「付款成功」。

這一課的任務是把一張訂單走完：王小明點了一杯拿鐵（110 元），這是今天的訂單 41。我們要讓結帳只做必須馬上完成的事就回應，寄收據、廚房出單、集點交給背景處理，而且這些背景工作要做到三件事：不漏（收據一定會寄出、點數一定會加上）、不重（點數不會加兩次）、不亂（App 上的訂單狀態不會倒退）。每一節補上其中一個洞。學完你能分清楚三種送達語意，親手寫出 visibility timeout 佇列、冪等消費者（inbox）、outbox relay 和「同一張訂單依序、不同訂單平行」的消費者，也知道上線後要看哪些指標、什麼情況選哪一種佇列。

第一輪只要記住：
  • 佇列只能延後工作，不能減少工作。它換來回應快、解耦、可重試，代價是最終一致。
  • 幾乎所有佇列都是「至少一次」：同一則訊息一定會來兩次。消費者用 inbox（訊息 id 和副作用寫在同一個交易）讓重複無害。
  • 「寫資料庫」和「送訊息」沒有一個交易包得住，用 outbox：訊息和訂單寫在同一個交易，relay 先送出、再標記。
這課的路線：
  1. 結帳裡哪些事可以晚一點做：把工作搬進佇列，看它換來什麼、付出什麼。
  2. 消費者做到一半當機會怎樣、佇列怎麼知道它當機了：三種送達語意與 visibility timeout，結論是重複一定會發生（不漏）。
  3. 點數被加兩次怎麼辦：用 inbox 讓重複無害（不重）。
  4. 訂單成立了訊息卻沒送出怎麼辦：雙寫問題與 outbox（生產者這端的不漏）。
  5. 狀態會不會倒退、上線後怎麼顧：依訂單排序（不亂），再看監控與選型。
這課會用到：
  • NestJS 課第 20 課的 BullMQ：工作失敗用 attempts、backoff 重試，用 jobId 去重，worker 要冪等。
  • PostgreSQL 課第 33 課的工作佇列與 outbox：用 SKIP LOCKED 讓多個 worker 各取各的，事件和訂單寫在同一個交易。
  • 第 9 課的冪等：同一個請求做一次和做很多次，結果相同。
  • 第 8 課的退避：重試時每次等久一點，並加一點隨機量。

結帳裡哪些事可以晚一點做？

先把結帳的五件事分成兩堆。分的標準只有一個問題：顧客要不要在按下結帳的這個畫面上，就知道這件事的結果？付款成功沒有、訂單有沒有建立，顧客必須馬上知道，失敗了也要馬上告訴他，讓他換一張卡或改點別的。收據、廚房出單、集點則不同：晚幾秒完成，顧客感覺不到；就算失敗，也可以等一下再試，不應該因此讓整張訂單失敗。

在請求裡做（同步）晚一點做（非同步）
檢查商品與金額、扣款、寫入訂單寄收據 email、通知廚房出單、集點、推播「訂單成立」
顧客要馬上知道結果，失敗要馬上告訴他晚幾秒沒關係；失敗可以重試，不影響訂單成立

右邊那一堆「晚一點做」的工作，要先記在某個地方，之後才有人來做。這個地方就是訊息佇列（message queue）：一個暫時保管「待辦事項」的系統。咖啡店櫃台的出單夾就是佇列：店員把單子夾上去，就轉身招呼下一位客人，不用站在旁邊等咖啡做好；吧台師傅照自己的速度，一張一張從夾子上取單。

這個比喻裡有三個角色，後面會一直用到：

  • 生產者（producer）：把訊息放進佇列的一方。這課是結帳 API，它放進去的訊息像「訂單 41 已付款」。
  • 消費者（consumer）：從佇列取出訊息、實際做事的一方。寄收據的程式、通知廚房的程式、集點的程式各是一個消費者，通常跑在跟 API 不同的程序裡，也常被叫做 worker。
  • broker：中間負責保管訊息的系統，例如 Redis、Amazon SQS、RabbitMQ、Kafka。它要確保訊息放進去之後不會因為某個程序重啟就不見。

生產者把訊息交給 broker 就算完成，不用等消費者在線，也不用等它處理完。回到早上的事故，這帶來四個好處，每一個都直接對應剛才的問題：

  • 回應變快：結帳 API 只做左邊那一堆就回應，寄 email 的 5 秒不再算在顧客的等待時間裡。
  • 解耦：email 服務掛了，訊息就留在佇列裡等，結帳照常成功。兩個服務不用同時活著。
  • 可重試：寄信失敗的訊息還在佇列裡，消費者等一下再試，不需要顧客重按結帳。
  • 削峰：尖峰時湧進來的工作先排著，消費者照自己的速度消化，不會因為一瞬間的量被壓垮。

第四個好處最容易被誤會。削峰有一個常被忽略的前提：佇列只能延後工作，不能減少工作。工作只是換了地方排隊，總量一件都沒少。用第 1 課的情境卡算一次：每天 6 萬筆訂單，早上 7:30～9:30 佔 40%。假設廚房出單服務每秒只能處理 2 張。執行後看兩件事：尖峰結束時佇列裡積了多少張，以及最後下單的人要等多久。

尖峰時每秒到 3.33 張、只處理得了 2 張，每秒多出來的 1.33 張就留在佇列裡，兩小時累積近萬張。到達率比處理速度高時，積壓會一直長（第 3 課的 Little's Law）。佇列讓結帳 API 不會倒，但顧客的咖啡晚了 80 分鐘。最後一段迴圈顯示，處理速度一旦達到每秒 3.4 張（高於到達率），積壓就是 0。所以真正的解法還是讓處理速度跟上尖峰（加消費者、加快處理），佇列吸收的是短暫的高峰，不是長期的不足。

除了積壓，把工作搬出請求還有幾個代價，設計時要寫下來，讓團隊知道換到了什麼、付出了什麼：

  • 最終一致：訂單成立了，收據幾秒後才寄出。這段時間內，系統各處的狀態不一致，最後才會一致，這就叫最終一致（eventual consistency）。畫面上要能顯示「處理中」。
  • 多一個會壞的元件：broker 本身要監控、要備援、要升級。
  • 除錯變難：一次結帳被拆到好幾個程序、好幾個時間點執行，要靠 trace id 串起來（第 21 課）。
  • 可靠性變成你的責任：以前寄 email 失敗，整個請求回錯，顧客至少知道。現在結帳已經回了「成功」，背景工作再出事，沒有人會在畫面上看到錯誤。訊息會不會掉、會不會被處理兩次、順序會不會亂，都要自己設計。這就是本課接下來要處理的事。
💡 實務上：先問「使用者需不需要馬上看到結果」
PM 說「結帳後要寄收據、通知廚房」時，資深工程師會一項一項問：顧客要在這個畫面上看到它的結果嗎？失敗了要不要擋下整張訂單？要的就留在請求裡，不要的才丟佇列。丟進佇列的工作，前端要跟著改：API 回「已受理」，畫面顯示「處理中」，再用輪詢或推播更新狀態。只有一兩件小事、量也不大時，不要為了它多架一套 broker，先用現有 PostgreSQL 裡的佇列，或專案已經有 Redis 時用 BullMQ（本課最後一節的選型）。

現在結帳 API 把「寄收據給王小明」放進佇列就回應了顧客。從這一刻起，這封收據寄不寄得出去，只剩消費者在負責。那麼，消費者寄到一半，程序被部署重啟了，會怎樣？

消費者做到一半當機，訊息會掉還是會重複？

要回答這個問題，先看消費者處理一則訊息時到底做了哪些動作。它有兩個動作：

  • 處理：真正做事，例如呼叫 email 服務寄出收據。
  • ack（acknowledge，確認）：告訴佇列「這則我處理完了，可以刪掉」。

為什麼需要 ack？因為佇列不知道消費者做完了沒。如果佇列在把訊息交出去的那一刻就刪掉，消費者拿到之後當機，這則訊息就沒有任何人保管了。所以佇列會先保留訊息，等消費者明確說「完成」才刪。問題在於，「處理」和「ack」是兩個分開的動作，兩者之間程序隨時可能當機，而且兩個動作誰先誰後，當機的結果完全不同。

下面的程式模擬這件事：佇列裡只有一則「寄收據給王小明」，在兩個動作之間讓程序當機一次，重啟後繼續消費。執行後看最後一行和倒數第三行：兩種順序在當機時各寄出幾封。

先 ack 再處理：訊息已經刪了，還沒寄就當機，重啟後佇列是空的，王小明永遠收不到收據。先處理再 ack：信已經寄出，還沒 ack 就當機，訊息還在佇列裡，重啟後又寄一次，王小明收到兩封。沒有第三種順序可以選，所以只能在「可能遺失」和「可能重複」之間挑一個。這兩種結果，加上理想中的第三種，業界合稱送達語意（delivery semantics），用來描述一個佇列系統對訊息保證到什麼程度：

語意定義怎麼來的
至多一次（at-most-once）訊息可能遺失，但不會重送先 ack 再處理：處理到一半當機，訊息已經刪了
至少一次（at-least-once）訊息不會遺失，但可能重送先處理再 ack：處理完、ack 前當機，訊息會再被送一次
恰好一次（exactly-once）每則訊息只被處理一次需要「處理結果」和「已處理的紀錄」一起成功或一起失敗

咖啡店該選哪個？收據寄兩封，顧客頂多覺得奇怪；訂單通知掉了，廚房不做咖啡、顧客白付錢。重複可以事後處理，遺失沒辦法補救，所以幾乎所有系統都選至少一次：Kafka 預設就是至少一次；Amazon SQS 的標準佇列也是至少一次，文件寫明即使在 visibility timeout（下一節）內也不保證只送一次；BullMQ 也一樣（NestJS 課第 20 課）。這也是本課「不漏」的基礎：先處理、成功後才 ack。

那為什麼不直接選恰好一次？看表格最後一欄：它要求「信寄出去了」和「這則已處理」這兩件事一起成功或一起失敗。這兩件事分別在 email 服務和佇列裡，是兩個不同的系統，沒有一個交易能同時包住它們。無論哪一個先做，中間當機都會讓兩邊不一致，這正是上面那段程式示範的事。有些 broker 提供名為 exactly-once 的功能（例如 Kafka），但它只在 broker 自己內部成立，碰到寄 email、呼叫金流這種外部副作用就管不到了（細節見課末「補充與查表」）。

跨系統能做到的是：至少一次送達＋冪等處理＝效果上一次（effectively-once）。訊息可能來兩次，但第二次什麼都不做。這就是第 9 課的冪等，從 API 那一端換到消費者這一端。

選了至少一次，就等於接受「同一則訊息會被處理兩次」。不過上面的模擬是程序真的當機、重啟。現實中，佇列看不到消費者的程序，它怎麼判斷消費者當機了、什麼時候該把訊息交給別人？這個判斷方式，會讓重複比你想的更常發生。

佇列怎麼知道消費者當機了？visibility timeout 與死信佇列

佇列和消費者之間只有網路，佇列看不到消費者的程序還在不在。它唯一能觀察到的訊號是：消費者有沒有在合理的時間內回來 ack。所以佇列用的是租約（lease）：一段有期限的持有權。消費者取走訊息，等於借走它一段時間；時間內還回來（ack）就結束，時間到了沒消息，佇列就當作消費者已經死了，把訊息借給別人。就像圖書館借書：館員不會打電話確認你還在不在讀，只看到期日。

以 Amazon SQS 為例，這個租約的運作方式是：

  • 消費者取走訊息時，訊息還留在佇列裡，只是對其他消費者隱藏一段時間。這段時間叫 visibility timeout（可見性逾時），SQS 預設 30 秒。
  • 處理完要在時間內刪除，也就是 ack。時間到了還沒刪，訊息重新出現，讓別的消費者處理。當機的消費者手上的訊息不會遺失，靠的就是這一條。
  • 每次取走都會拿到一張新的 receipt（SQS 叫 receipt handle），代表「這一次的租約」。刪除要用 receipt，不是用訊息 id。同一則訊息被取走第二次，會拿到不同的 receipt；SQS 的文件要求刪除時用最近一次的 receipt。為什麼要分得這麼細，下面的時間軸會看到。
  • 處理比較久時，可以呼叫 ChangeMessageVisibility 延長隱藏時間。文件建議用心跳（heartbeat）定期延長：處理中每隔一段時間就告訴佇列「我還活著，再借我一陣子」。延長的上限見課末。

租約的弱點在於：佇列只能看時間，分不出「消費者當機了」和「消費者還活著，只是很慢」。早上 email 服務一封要 5 秒，慢的時候更久。如果處理時間超過 visibility timeout、又沒有延長，會發生什麼事？按「下一步」看：

時間消費者 A消費者 B佇列裡的訊息「寄收據 #41」
0 秒取走，receipt r1隱藏到 30 秒
5 秒寄信中……（很慢）隱藏中
30 秒還在寄重新可見
31 秒還在寄取走，receipt r2隱藏到 61 秒
40 秒寄出 ✉；用 r1 ack
receipt 已過期		寄信中隱藏中（B 持有）
45 秒寄出 ✉；用 r2 ack ✓刪除

這段時間軸說明了兩件事。第一，receipt 為什麼要每次不同：A 的 ack 如果能刪掉訊息，B 萬一寄信失敗，就沒有人會再試，收據就漏了。用 receipt 區分「哪一次的租約」，過期的租約就碰不到訊息。第二，就算程序完全沒當機，只要處理得夠慢，同一則訊息也會被兩個消費者處理。像 A 這樣租約已經過期、自己卻不知道，還繼續做事的消費者，叫殭屍消費者（zombie consumer）。

所以 visibility timeout 要比正常的處理時間長，但也不能太長：消費者真的當機時，訊息要等整個 timeout 過去才會重試，收據就晚了這麼久。處理時間不固定時，設一個中等的值，處理中每隔一段時間延長一次（心跳）；延長也失敗了，代表租約已經被別人拿走，這時就停止處理，不要繼續做副作用。

SQS 用舊的 receipt 刪除時，文件說「請求會成功，但訊息不一定被刪掉」，所以不能拿刪除的回應判斷自己是不是還持有訊息。這一課練習 1 的佇列更嚴格，直接回傳 false。第 14 課的 fencing token 會再處理「殭屍拿著過期租約繼續寫」的問題。

租約會帶來另一個問題。假設有一則訊息怎麼處理都會失敗，例如 JSON 格式壞掉，或引用的訂單已經被刪除。它每次失敗就不 ack，時間到又重新出現，再失敗、再出現，永遠佔著消費者。這種訊息叫毒訊息（poison message）。重試對它沒有用，因為失敗的原因不會自己消失。

解法是限制一則訊息最多被取走幾次。SQS 在 redrive policy 裡設定 maxReceiveCount：一則訊息被取走超過這個次數仍沒被刪除，就移到另一個佇列，叫死信佇列（DLQ，dead-letter queue）。DLQ 不會自動被處理，它的用途是把毒訊息隔離出來，讓正常的訊息繼續流動，等人來看原因。

maxReceiveCount 不要設太小。設成 1 的話，email 服務一次暫時性的 503 就讓收據直接進 DLQ。失敗有兩種：暫時性的（對方忙、網路抖動）靠重試加退避（第 8 課）就會好；永久性的（資料壞了）再試幾次都一樣。maxReceiveCount 要大到足以撐過暫時性失敗，DLQ 留給永久性失敗。

💡 實務上：DLQ 要有人看，也要能搬回去重跑
沒有人看的 DLQ 等於把訊息默默丟掉：王小明的收據躺在 DLQ 裡，沒有任何錯誤畫面。所以 DLQ 有任何訊息就告警。告警之後要有重新處理的流程：查出原因、修好 bug，再把訊息搬回原佇列（SQS 叫 redrive）。搬回去等於再送一次，所以消費者冪等，重跑才安全。SQS、BullMQ、PostgreSQL 佇列都有這套概念，只是名字不同，對照表與 DLQ 保存期限的細節見課末。

到這裡結論很清楚：visibility timeout 能讓訊息「不漏」，但它只能減少重複，不能消除重複。王小明的集點訊息就算一切設定正確，還是可能被處理兩次。下一步是讓第二次處理什麼都不做。

點數被加了兩次：怎麼讓重複的訊息無害？

集點的消費者收到「訂單 41 已付款」，要幫王小明加 11 點（110 元，每 10 元 1 點）。收據寄兩封只是尷尬，點數加兩次就是錢的問題。既然重複一定會發生，消費者就要能認出「這則我處理過了」。

做法叫 inbox，也叫冪等消費者（idempotent consumer）：在消費者自己的資料庫裡準備一張表，記錄處理過的訊息 id，並把 id 設為主鍵。主鍵保證同一個 id 只能有一列，所以「這則處理過沒有」由資料庫的唯一約束來判斷，不由程式判斷。處理一則訊息時，記錄 id 和加點數寫在同一個交易裡：

CREATE TABLE processed_messages (
  message_id text PRIMARY KEY,
  processed_at timestamptz NOT NULL DEFAULT now()
);

BEGIN;
INSERT INTO processed_messages (message_id) VALUES ('evt-41')
  ON CONFLICT DO NOTHING;          -- 影響 0 列 → 處理過了：ROLLBACK，直接 ack
UPDATE members SET points = points + 11 WHERE id = 3;   -- 副作用：3 是王小明的會員 id
COMMIT;                            -- 成功之後才 ack

第一次收到 evt-41，INSERT 影響 1 列，接著加點數、提交、ack。第二次收到，INSERT 撞到主鍵，因為 ON CONFLICT DO NOTHING 而影響 0 列，程式看到 0 就知道處理過了，回滾並直接 ack，點數不會再加。

關鍵在同一個交易。把幾種看起來也行的寫法排在一起比較，看當機或失敗時各會怎樣：

寫法當機或失敗時
inbox 和副作用在同一個交易 ✓交易失敗兩個一起回滾，重送時重新處理；交易成功兩個一起留下，重送時被認出來
先做副作用，另一個交易再記 inbox兩者之間當機 → 沒有紀錄 → 重送時再做一次
先記 inbox（自己提交），再做副作用副作用失敗 → 紀錄已經在 → 重送時被當成處理過而略過＝遺失
先 SELECT 查有沒有，再 INSERT兩個消費者同時處理同一則（上一節的殭屍）時，兩個都查到「沒有」，都做了

第二、三列跟上一節「先 ack 還是先處理」是同一個問題換了位置：兩個動作分開提交，中間當機就會重複或遺失。放進同一個交易，兩件事就變成一件事，沒有「中間」可以當機。

最後一列是 PostgreSQL 課第 19 課的「先讀再寫」競態：先讀出來、在程式裡判斷，再寫回去，兩個交易中間會互相看不到。上一節的時間軸裡，A 和 B 確實會同時處理同一則訊息；換成集點的 evt-41，兩邊都 SELECT 到「沒有」，就都加了點數。用主鍵加 INSERT … ON CONFLICT DO NOTHING 是原子的：兩個交易同時插入同一個 id 時，第二個會等第一個結束；第一個提交了，第二個就是衝突；第一個回滾了，第二個就插入成功、接手處理。

inbox 只保護得了同一個資料庫裡的副作用。加點數在消費者自己的資料庫裡，可以跟 inbox 同一個交易；寄 email、呼叫金流這種外部副作用沒辦法跟資料庫同一個交易，要靠對方的冪等鍵：把訊息 id（或由它衍生的值）當成 Idempotency-Key 傳給對方（第 9 課），對方看到同一個鍵就不重做。對方不支援冪等時，只能盡量縮小重複的機會，並在設計文件裡寫清楚「極少數情況會寄兩封」。

重複的訊息還會帶來一個比較隱蔽的問題：訊息可能排了 10 分鐘才被處理，這段時間訂單可能已經取消了。如果訊息裡帶著完整的訂單資料，消費者會照著過時的內容做事。所以訊息裡放 id，不放完整資料：寫「訂單 41 已付款」，處理時再去查訂單的最新狀態（NestJS 課第 20 課）。最後，inbox 表每處理一則就多一列，也要定期清理：保留比「最長可能重送的時間」再長一些，例如 7 天，之後刪掉舊紀錄。

💡 實務上：review 消費者時先問「同一則來兩次會怎樣」
典型客訴是「我的點數被加了兩次」或「收到兩封收據」，原因幾乎都是消費者不冪等。review 一個新的 worker 時，資深工程師會看：訊息 id 是生產者產生、重送時不變的嗎？inbox 紀錄和副作用在同一個交易嗎？呼叫外部服務有沒有帶冪等鍵？測試也很直接：把同一則訊息送兩次，斷言資料只變一次。

消費者這一端現在不漏也不重了。但這一切有個前提：訊息有被送進佇列。回頭看結帳 API，它寫完訂單、再送出訊息，這兩步之間也有一個洞。

訂單成立了，收據卻永遠沒寄：生產者怎麼保證訊息一定送出？

結帳 API 要做兩件事：在資料庫寫入訂單 41，並送出「訂單 41 已付款」的訊息到 broker。資料庫和 broker 是兩個系統，沒有一個交易能同時包住兩者。要同時寫進兩個系統、又沒有交易保護，這叫雙寫問題（dual write）。三種常見的寫法都會出事，只是出事的時機不同：

寫法出事的時機結果
交易裡先送訊息，再 COMMIT送出之後交易失敗回滾訂單不存在，廚房卻收到出單通知
COMMIT 之後再送訊息提交之後、送出之前當機（部署重啟、broker 連不上）訂單成立，收據永遠不會寄、廚房永遠不知道
程序內的事件（NestJS 課第 21 課的 EventEmitter）事件處理完之前程序結束同上，而且連重試的機會都沒有

這跟消費者端的「先 ack 還是先處理」是同一種結構：兩個系統、兩個動作，中間會當機。消費者那邊靠「重複無害」解決，但生產者這邊的第二列是遺失，沒有任何重試會發生。「當機剛好在那一瞬間」聽起來很少見，但每天 6 萬筆訂單、每週部署好幾次，一年下來一定會遇到，而且這種錯不會報錯，只會有顧客說「我沒收到收據」。

解法是把兩個系統的問題變回一個系統的問題。transactional outbox 的做法是：結帳 API 不直接送訊息，而是把要送的訊息當成一筆資料，跟訂單寫在同一個交易裡的 outbox 表。這樣訂單和訊息一起提交或一起回滾，不會只有一邊存在。再另外跑一個 relay（轉送）程序，負責把 outbox 裡還沒送出的列送到 broker。microservices.io 的說法是：只有在資料庫交易提交時，訊息才保證送出。

雙寫的問題沒有消失，只是移到了 relay：relay 也要做兩件事，「送到 broker」和「在 outbox 標記已送出」，兩者還是分屬兩個系統。差別在於，relay 失敗了可以一直重來，因為訊息安全地存在 outbox 裡；結帳 API 的請求卻只有一次機會。表和 SQL 在 PostgreSQL 課第 33 課寫過，這裡看 relay 的邏輯。每一輪：

  1. 依 id 取一批還沒送出的列。
  2. 依序一筆一筆送出，前一筆成功才送下一筆。
  3. 遇到第一個失敗就停下來，只把已經成功送出的列標記為已送出；失敗那筆和後面的留到下一輪。

為什麼是「先送出、再標記」？兩個順序都試想一次：

  • 先標記、再送出：送出失敗或當機，這列已經被標記，永遠不會再送 → 遺失。
  • 先送出、再標記：送出之後、標記之前當機 → 下一輪再送一次 → 重複。重複可以靠消費者的 inbox 解決，遺失沒辦法補救，所以選這個。

這又是至少一次的選擇。下面把訂單 41 從結帳一路走到消費者，看 relay 當機時，上一節的 inbox 怎麼接住重送：

步驟結帳 APIrelayoutbox 第 41 列消費者（inbox）
1INSERT orders、INSERT outbox、COMMIT未送出
2取出第 41 列未送出
3送出 evt-41 ✓未送出處理 evt-41，記入 inbox
4當機（還沒標記）未送出
5重啟，再送一次 evt-41未送出
6標記第 41 列 ✓已送出
7已送出evt-41 已在 inbox → 略過、ack

最後一步點出 outbox 和 inbox 的接點：訊息 id 必須在重送時保持不變，inbox 才認得出來。用 outbox 那一列的 id 當訊息 id，就自然滿足這一點。

relay 要怎麼知道 outbox 有新的列？有兩種做法：

輪詢（polling publisher）CDC（change data capture）
怎麼做定期 SELECT … WHERE published_at IS NULL ORDER BY id LIMIT 100讀資料庫的變更紀錄（PostgreSQL 的 WAL），看到 outbox 有新列就發布，例如 Debezium
延遲最多一個輪詢間隔通常更低
對資料庫的負擔一直在查詢；已送出的列要清理不用查詢，但會佔用一個 replication slot，CDC 停太久 WAL 會堆積
維運一個小程式，好懂好除錯多一套系統（Debezium 常跑在 Kafka Connect 上）

replication slot 是 PostgreSQL 為了讓某個讀取者（這裡是 Debezium）不漏讀變更而保留的書籤。讀取者沒有往前讀，PostgreSQL 就不能刪掉書籤之後的舊 WAL，所以 CDC 停太久，磁碟會被 WAL 撐滿。

咖啡店一開始用輪詢就夠了。用 Debezium 時，它的 outbox event router 對欄位名稱與送往的位置有預設慣例，見課末「補充與查表」。

輪詢版上線前要想好三件事。第一，多個 relay 同時跑時要分工：用 FOR UPDATE SKIP LOCKED 讓每個 relay 拿不同的列，或用 advisory lock 保證只有一個 relay 在跑（PostgreSQL 課第 33 課）。但只要有兩個 relay 平行送同一張訂單的事件，順序就沒有保證，這是下一節的主題。第二，已送出的列要定期刪除：outbox 每天多 6 萬列以上，只更新不刪除，表和索引會一直長，VACUUM 跟不上（PostgreSQL 課第 30 課的表膨脹）。第三，佇列本身就在 PostgreSQL 裡時（PostgreSQL 課第 33 課、pg-boss），工作和訂單本來就能寫在同一個交易，沒有雙寫問題，也就不需要 outbox。outbox 解決的是「broker 在資料庫之外」的情況。

💡 實務上：outbox 用在「漏了會有人來問」的事件
訂單成立、付款完成、庫存扣減這類漏掉會變成客訴或對帳差異的事件，才值得走 outbox。使用者行為追蹤、分析用的事件掉幾筆沒關係，直接送就好，不用多一張表。outbox 表本身也是很好的除錯工具：客服說「沒收到收據」時，先查那張訂單的 outbox 列有沒有、送出了沒。上線後加一個告警：「超過幾分鐘還沒送出的列」大於 0，代表 relay 停了或 broker 連不上。

現在訂單 41 的訊息從生產者到消費者都不漏、不重了。只有一個 relay 依 id 依序送出時，訂單 41 的 order.paid 會比 order.preparing 先進 broker。但就算依序進了 broker，有好幾個消費者平行在處理，它們處理完的順序還會跟送進來的一樣嗎？

訂單 41 的狀態會倒退嗎？順序與平行

同一張訂單會有好幾個事件：order.paid → order.preparing → order.done。王小明的 App 依收到的事件更新畫面，如果先處理到 done、再處理到 preparing，畫面就會從「可以取餐」倒退回「製作中」。要保證順序，最簡單的方法是只開一個消費者，所有訊息一則一則做；但尖峰每秒 3 張以上的訂單，一個消費者根本跟不上。順序和平行，看起來只能二選一。

關鍵在於觀察：我們要的其實不是「全店所有事件依序」，而是「同一張訂單的事件依序」。訂單 41 和訂單 42 誰先處理，沒有人在意。broker 的順序保證也正是這樣設計的，都是局部的：

  • Kafka：一個 topic（一類訊息的名稱，例如「訂單事件」）分成多個 partition（分區），每個 partition 是一條獨立的、完全有序的佇列，partition 之間沒有順序。每則訊息帶一個 key，key 決定它進哪個 partition，同一個 key 一定進同一個。同一個消費群組裡，一個 partition 同時只會交給一個消費者，所以 partition 內的順序保得住，不同 partition 則可以平行。
  • SQS FIFO：同一個 message group ID 依序處理：群組裡有訊息還在處理（已取走、還沒刪除）時，同群組後面的訊息要等它被刪除或 visibility timeout 到期才會被取出。不同群組可以平行。SQS 文件提醒：在乎順序的 FIFO 佇列不要接 DLQ，訊息被移走會打亂順序。
  • SQS 標準佇列、多個 worker 的 BullMQ：不保證順序。

所以順序要靠設計決定：用 orderId 當 key，同一張訂單的事件依序處理，不同訂單平行處理。這樣訂單 41 的三個事件一定照順序，同時另一個消費者可以處理訂單 42。練習 4 會在單一程序裡實作這個規則。

這個設計有兩個代價。第一是隊頭阻塞（head-of-line blocking）：排在隊伍最前面的那則卡住，後面的全部跟著卡住。如果訂單 41 的 order.paid 一直處理失敗，它的 order.preparing、order.done 全部要等。有人在等的流程要設重試上限，到上限就停在那裡並告警，不能跳過去先做後面的，因為跳過就是亂序。第二是熱門 key：同一個 key 只能一則一則處理，某個 key 的量特別大時，它就是瓶頸，加再多消費者也沒用。所以 key 要選「需要順序的最小範圍」：用訂單 id，不要用門市 id。用門市 id 的話，整間門市的訂單全部排成一列，平行度就沒了。

重試也會打亂順序：第一則失敗、等退避的時候，第二則先處理成功了。真的在乎順序時，除了依 key 排隊，還要在事件裡帶版本號，消費者遇到比目前狀態舊的版本就略過（第 16 課）。很多事件其實只需要「最後狀態正確」，這時版本號比嚴格排隊便宜。
💡 實務上：先問「這個事件真的需要順序嗎」
需要順序的通常是同一個東西的狀態變化，例如訂單 41 從付款、製作到完成；寄收據、集點這類各自獨立的工作，就不必排隊，平行處理最快。設計時把每一種事件標上「需不需要順序、順序的範圍是什麼」，key 就跟著決定了。App 這種只在乎最後狀態的地方，用版本號擋掉舊事件，通常比嚴格排隊省事。

不漏、不重、不亂都有了對應的機制。最後兩個問題是上線之後的事：這些機制什麼時候開始出問題、怎麼提早發現，以及咖啡店到底該用哪一種佇列來實作它們。

上線後怎麼知道佇列健康？又該選哪一種佇列？

佇列出問題時通常不會報錯。結帳照常成功，只是收據越寄越晚、廚房越來越慢出單，等到顧客來問才發現。所以監控要看的是「工作有沒有在時間內完成」，不是「有沒有錯誤」：

指標看什麼
最老訊息的年齡（age of oldest message，SQS 是 ApproximateAgeOfOldestMessage）最重要的一個，直接回答「顧客要等多久」。告警門檻依業務定：收據 5 分鐘、廚房出單 1 分鐘
佇列長度單看沒有意義：1 萬則如果 10 秒內消化完不是問題，100 則卡了一小時才是問題。要跟處理速度一起看
到達率與處理速度到達持續大於處理，積壓只會一直長
DLQ 的訊息數大於 0 就告警
重送次數、處理時間的 p99處理時間接近 visibility timeout，就會開始出現殭屍與重複

這張表的每一列都對應前面某一節：最老訊息的年齡和到達率是第一節積壓的計算，DLQ 是毒訊息，處理時間接近 visibility timeout 是殭屍消費者的前兆。

告警響了、積壓已經很大時怎麼辦？AWS Builders' Library〈Avoiding insurmountable queue backlogs〉提了幾個做法。積壓很大時優先處理新的訊息：舊的反正已經晚了，新的還來得及準時。依租戶分開佇列或分開處理容量，讓一個門市或一個客戶的爆量不會拖垮全部（文中的 shuffle sharding）。會被之後的「完整同步」取代的舊訊息，可以直接丟掉。這些都是取捨，要依訊息的性質決定，例如「推播：訂單已完成」晚了 2 小時，不如不送；但收據就算晚了也還是要寄。

最後是選型。前面所有的機制，在每一種佇列裡都要用到，差別在於哪些是內建的、哪些要自己做。比較的面向有五個：順序、能不能保留訊息並重播、一則訊息能不能給多個消費者（扇出）、維運成本，以及適合的情境。

順序保存與重播一則訊息給多個消費者（扇出）維運成本適合
PostgreSQL 佇列（PostgreSQL 課第 33 課、pg-boss）自己用 SQL 決定看你保不保留列要自己做最低，沿用現有資料庫量不大、想跟業務資料同一個交易
Redis／BullMQ多個 worker 時不保證處理完就移走要自己做低，Redis 持久化設定決定會不會掉工作背景工作、延遲工作、重試退避
Amazon SQS標準不保證；FIFO 依群組刪除就沒了搭配 SNS 之類的服務全託管在 AWS 上、不想維運 broker
RabbitMQ單一佇列、單一消費者時有序ack 就刪exchange 路由，原生支援中，要自己維運叢集需要彈性的路由規則

各家 Node 客戶端套件的版本見課末「補充與查表」。

咖啡店的建議：一開始就用 PostgreSQL 佇列或沿用 NestJS 課的 BullMQ，加上 outbox。訂單 41 的收據、出單、集點，量都不大，也都只有咖啡店自己的系統在讀。等到有多個團隊、多個系統要讀同一份訂單事件、需要重播時，再評估 Kafka。這是第 1 課的 YAGNI。

  • Kafka 的「exactly-once」功能，文件說得很清楚：它只在 Kafka 內部成立（Kafka Streams、交易式 producer 搭配 read_committed 的消費者），寫到外部系統要對方配合，例如把讀到哪裡（offset）和輸出存在同一個地方。寄 email、呼叫金流都是外部副作用，Kafka 管不到。

Amazon SQS 的上限與 DLQ 保存期限

  • ChangeMessageVisibility 延長隱藏時間：從第一次取走起算，最長 12 小時，延長不會重置這個上限。
  • SQS 建議 DLQ 的保存期限比原佇列長：標準佇列的訊息從原本送進來的時間算到期，移到 DLQ 不會重新計時。

Debezium 的 outbox event router

Debezium 3.7 的 outbox event router 預設讀 id、aggregatetype、aggregateid、type、payload 這幾個欄位，送到 outbox.event.<aggregatetype> 這個 topic，並以 aggregateid 當訊息的 key，所以同一個聚合（例如同一張訂單）的事件會落在同一個 partition、保持順序。聚合（aggregate）在這裡指「事件屬於哪一個東西」，咖啡店通常就是訂單。

練習

練習 1：完成 InMemoryQueue，一個有 visibility timeout 和死信佇列的佇列：

  • send(body)：放到佇列尾端，馬上可見，回傳訊息 id（每則不同）。
  • receive(max)：依送出順序取出目前可見的訊息，最多 max 則。每取一則：receiveCount 加 1、用 makeReceipt(id, receiveCount) 發新的 receipt、隱藏到 now() + visibilityTimeoutMs。
  • 某則訊息已經被取走 maxReceives 次仍沒被 ack，下一次 receive 遇到它（它又可見了）時，把它移到 DLQ，不再送出。
  • ack(receipt)：只有這則訊息目前的 receipt 能刪除它，成功回傳 true；舊的或不存在的 receipt 回傳 false，什麼都不改。
  • extend(receipt, ms)：只有目前的 receipt 能把隱藏時間改成 now() + ms，規則同 ack。
  • dlq()：回傳已經移到 DLQ 的 { id, body }，依移入順序。時間只能用傳進來的 now。

練習 2：寫 createInboxHandler，把一個會重複收到訊息的處理函式變成冪等的。回傳的函式收到 msg 時：

  • 在 db.transaction(async tx => …) 裡，先用 tx.insertIfAbsent('inbox', msg.id) 記錄訊息 id（原子操作，id 已經存在就回傳 false）。
  • 回傳 false 就是處理過了，回傳 'duplicate'；否則呼叫 handle(msg, tx)，回傳 'processed'。
  • handle 丟錯時讓錯誤往外傳（訊息不 ack，之後會重送）。交易的 callback 丟錯時，callback 裡的所有寫入都會回滾，包括 inbox 紀錄。

測試用的假資料庫跟 PostgreSQL 一樣：兩個交易同時插入同一個 key，第二個會等第一個提交或回滾。

練習 3：寫 outbox relay 的一輪 relayOnce：

  • 用 store.fetchUnpublished(batchSize) 取一批未送出的列（已依 id 排序）。
  • 依序逐筆 publish，前一筆完成才送下一筆。
  • 遇到第一個失敗就停下來（後面的不送）。這一輪送完或停下之後，呼叫一次 store.markPublished，只傳失敗之前已成功送出的列的 id（一筆都沒送成功就不用呼叫）；回傳標記的筆數。
  • markPublished 丟錯時（例如資料庫斷線）讓錯誤往外傳，下一輪會重送這些列：允許重複，不允許遺失。

練習 4：寫 processByKey，消費一批訊息：

  • 同一個 key（例如訂單 id）的訊息，依陣列順序一則做完才做下一則。
  • 不同 key 可以同時進行，但同時進行的 handler 總數不超過 concurrency；有空位、也有可做的 key 時，就要開始做。
  • 全部完成才 resolve；任何一個 handler 失敗就 reject 那個錯誤（不必取消其他進行中的）。不能修改傳進來的陣列。

提示：TypeScript 課第 9 課「限制同時 N 個」的 worker 寫法（依 key 排隊的想法見 TypeScript 課第 12 課），讓每個 worker 一次負責一整個 key。

練習 5：集點的消費者先 ack 訊息，再去資料庫加點數。加到一半程序被部署重啟了，這則訊息會怎樣？

✓ ack 就是告訴佇列「可以刪了」，刪除之後佇列手上沒有這則訊息，重送無從發生（a、c 都不成立）。visibility timeout 只保護「還沒 ack」的訊息。所以要先處理、成功之後才 ack，代價是可能重複，再用 inbox 讓重複無害。

練習 6：結帳程式在交易 COMMIT 成功之後，才把「寄收據」放進佇列。同事說：「提交之後到送出之間只有幾毫秒，當機剛好落在中間的機率很低，不用管。」你怎麼回？

✓ 機率低乘上量大、部署頻繁，就是「一定會發生」，而且發生時沒有錯誤可以查，只有顧客抱怨（a 的代價是找不到哪些人漏了）。移到 COMMIT 之前（b）換成另一個錯：交易回滾了，訊息卻已經送出，廚房收到不存在的訂單。outbox 讓訂單和訊息一起提交，relay 負責送出，消費者用 inbox 處理重送。

練習 7：監控顯示廚房出單的佇列裡有 1 萬則訊息。這一定代表出問題了嗎？

✓ 等待時間 = 積壓 ÷ 處理速度（Little's Law）。同樣 1 萬則，消費者每秒處理 1,000 則就是 10 秒，每秒 2 則就是 80 多分鐘，所以長度要跟處理速度一起看（b 少了處理速度）。最直接的指標是最老訊息的年齡，它就是「最慘的顧客等了多久」。c 忽略了到達率持續大於處理速度時，積壓會一直長下去。

練習 8：團隊改用 Kafka，並開啟了 exactly-once 的設定。寄收據 email 的消費者還需要用訊息 id 去重嗎？

✓ Kafka 4.4 的文件寫明：exactly-once 適用於 Kafka Streams 和交易式 producer 搭配 read_committed 的消費者，也就是「從 Kafka 讀、寫回 Kafka」；寫到外部系統需要對方配合（a 誤會了範圍）。email 服務不會跟 Kafka 一起回滾，所以仍要冪等：用訊息 id 當 inbox 的 key，或傳給 email 服務當冪等鍵。c 也錯：Kafka 在 partition 內完全有序。

常見錯誤

  • 以為佇列能解決長期的處理不足：佇列只能延後工作，到達率長期大於處理速度時積壓會一直長。加消費者或加快處理，佇列只吸收短暫的高峰。
  • 先 ack 再處理：處理到一半當機，訊息就遺失了。先處理，成功後才 ack。
  • 處理時間超過 visibility timeout 又不延長：同一則訊息被兩個消費者同時處理。依處理時間設定 timeout，處理中用心跳延長，延長失敗就停下來。
  • 用訊息 id 或過期的 receipt 刪除：殭屍消費者刪掉別人正在處理的訊息，那次處理失敗時就沒有人會重試。只用最近一次取得的 receipt。
  • DLQ 沒有告警、也沒有重新處理的流程：訊息默默躺在那裡。有任何訊息就告警，修好後 redrive。
  • 消費者不冪等：至少一次的佇列一定會重複。用 inbox 或對方的冪等鍵。
  • inbox 紀錄不在副作用的同一個交易裡：紀錄在前會遺失，紀錄在後會重複。兩者放同一個交易，並用唯一約束的原子插入，不要先查再寫。
  • 訊息裡放完整資料：處理時資料可能已經改了。訊息放 id，處理時查最新的。
  • 在交易提交前送訊息，或提交後直接送：前者會送出不存在的訂單，後者當機時訊息遺失。用 transactional outbox。
  • relay 先標記再送出：送出失敗就永遠遺失。先送出再標記，重複交給消費者處理。
  • outbox 表從不清理：表越來越大、VACUUM 跟不上。定期刪除已送出的列。
  • 以為整個佇列全域有序：只有同一個 partition 或 message group 內有序。用訂單 id 當 key，需要時再加版本號。
  • 只監控佇列長度：長度不等於延遲。監控最老訊息的年齡，並跟處理速度一起看。

小結

王小明的訂單 41 從結帳到收據、出單、集點，每一個洞對應一個機制：

  • 結帳只做顧客要馬上知道結果的事（扣款、寫入訂單），其他交給佇列。佇列讓請求快速回應、削峰、解耦、可重試；代價是最終一致、多一個元件、除錯變難。佇列只能延後工作，到達率長期大於處理速度時積壓會一直長。
  • 先 ack 再處理是至多一次，先處理再 ack 是至少一次。跨系統的恰好一次做不到，能做到的是「至少一次＋冪等＝效果上一次」。
  • visibility timeout 是租約：時間到沒 ack 就重新出現；每次取走拿新的 receipt，只有最新的 receipt 能 ack 或延長；超過最多接收次數移到 DLQ，DLQ 要告警。它讓訊息不漏，但只能減少重複，不能消除。
  • 不重靠 inbox：訊息 id 用唯一約束原子插入，跟副作用在同一個交易；外部副作用用對方的冪等鍵。
  • 生產者端的不漏靠 outbox：訊息跟業務資料同一個交易寫入，relay 依序送出、成功後才標記；送出後、標記前當機會重送，所以消費者要冪等。relay 可以輪詢或用 CDC（Debezium）。
  • 不亂靠 key：順序只在同一個分區或群組內成立，用訂單 id 當 key，同一張訂單依序、不同訂單平行；小心隊頭阻塞和熱門 key。
  • 監控最老訊息的年齡、DLQ、到達率與處理速度；佇列選型依順序、重播、扇出與維運成本決定，量小時從 PostgreSQL 佇列或 BullMQ 開始。
