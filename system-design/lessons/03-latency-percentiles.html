階段 1：基本功：需求、估算與效能指標 · 第 3 課

延遲、吞吐量與百分位數

週年慶前兩週，主管在群組裡問：「下單 API 撐得住週年慶嗎？」第 1 課已經把「要快」寫成可以驗收的目標：尖峰時下單 API 的 p99 小於 300ms；第 2 課算出週年慶尖峰大約是平常的 20 倍。你手上有五樣證據，乍看每一樣都說「沒問題」：

  1. 下單查詢用的資料庫連線池總共只有 10 條，是套件預設值，從來沒出過事。
  2. 監控儀表板上，下單 API 的平均延遲是 132ms，離 300ms 很遠。
  3. 三台 API 各自的 p99 平均起來，也在 300ms 以內。
  4. 機器 CPU 平常只用到 50% 上下，維運說「跑到 90% 再加機器都來得及」。
  5. 同事上週用壓測工具量的報告：p99 只有 15ms。

這一課逐一檢查這五樣證據，每一樣都可能騙人。要看出它們錯在哪，需要幾個工具：延遲和吞吐量的差別、把兩者連起來的 Little's Law、百分位數與 histogram、使用率和排隊的關係，以及正確的壓測方法。學完你能回答主管：撐不撐得住、證據是什麼、哪裡要先改。

第一輪只要記住：
  • 延遲是一個請求等多久，吞吐量是每秒完成幾個；加機器提高吞吐量，不會讓單一請求變快。
  • Little's Law：並行數 = 每秒請求數 × 延遲（秒）。連線池大小、系統上限都用它估。
  • 延遲看 p95／p99，不看平均；監控用 histogram 估百分位數，各台的 p99 不能拿來平均。
  • 使用率接近 100% 時排隊會暴增，所以機器不跑滿；壓測要用固定到達率，不然會少算慢的請求。
hedged request 和 coordinated omission 的實測放在兩節選讀裡（練習 4 也是選讀），跳過不影響後面的課。
這課的路線：
  1. 「快」和「撐得住」是同一件事嗎？延遲、吞吐量、並行數各是什麼，p99 的最小答案；接著用 Little's Law 算出連線池 10 條夠不夠（證據 1，開場問題的最小答案）。
  2. 平均 132ms 為什麼不能信？百分位數怎麼算，尾延遲為什麼影響的人遠多於 1%（證據 2）。
  3. 監控系統怎麼算出 p99？histogram 怎麼估、SLO 門檻為什麼要是桶邊界、三台機器的 p99 為什麼不能平均（證據 3）。
  4. CPU 50% 真的很空嗎？使用率與排隊的關係，以及下單同時呼叫好幾個服務時尾延遲怎麼被放大（證據 4；選讀：hedged request，對應練習 4）。
  5. 壓測報告的 15ms 可信嗎？壓測工具的兩種送法、怎麼看出報告少算了慢的請求、量測守則（證據 5；選讀：coordinated omission 實測）。
這課會用到：
  • 第 2 課的尖峰流量與目標使用率：容量照尖峰每秒請求數規劃，平常只讓機器用到約 60%，留餘裕給突發。
  • Node 課第 20 課的連線池：事先開好固定條數的資料庫連線，請求輪流借用，借不到就排隊。

「快」和「撐得住」是同一件事嗎？

主管那句「撐得住嗎」其實包了兩個問題：每一張訂單要等多久，以及每秒能處理多少張訂單。這兩件事常被混在一起講，但它們的數字不同、改善的方法也不同。先用咖啡店的吧台把它們分開。

一位咖啡師做一杯拿鐵要 3 分鐘，一小時做 20 杯。多請兩位咖啡師，一小時變成 60 杯，但每一杯還是 3 分鐘。客人問「我的拿鐵要等多久」和老闆問「一小時能賣幾杯」，是兩個不同的問題：

換成後端的說法，有三個要分清楚的數字。

第一個是延遲（latency）：一個請求從送出到收到回應花的時間。延遲有兩種量法。一種只算伺服器真正在處理的時間，例如查詢本身跑了 20ms；另一種是使用者實際等待的總時間，包括請求到了但伺服器正忙、只能等的那段。這門課說的延遲一律指後者，也叫回應時間（response time），包含排隊。這個選擇很重要：週年慶時延遲變差，多半不是處理變慢，而是排隊變長；只量處理時間的話，那段等待就看不到。

第二個是吞吐量（throughput）：單位時間內完成的請求數，常寫成 req/s（每秒請求數）。吧台一小時 20 杯、API 每秒 200 個請求，都是吞吐量。

第三個是並行數（concurrency）：同一時刻正在處理中的請求數，也就是已經送進來、還沒回應的那些，所以也叫 in-flight。三位咖啡師同時各做一杯時，並行數是 3。

圖裡的結論是：加人手（加機器）提高吞吐量，但每一杯的延遲不變。想讓單一請求變快，得改做法，例如改程式、少打幾次資料庫、加快取。反過來也成立：延遲變差不一定是程式變慢，常常是排隊（queueing），也就是請求到了但資源正忙，只能等。客人排到門外時，咖啡師做一杯還是 3 分鐘，客人卻等了 20 分鐘。

所以「撐得住」的完整意思是：在週年慶那樣的吞吐量下，包含排隊在內的延遲仍然達標。第 1 課的目標用的是 p99，這裡先給最小答案：把一段時間內所有請求的延遲從快排到慢，排在第 99% 位置的那個值就是 p99，意思是 100 個請求裡只有最慢的 1 個比它慢。目標寫「p99 小於 300ms」，等於承諾幾乎每個人都不用等超過 300ms。為什麼不看平均、p99 實際上怎麼算，留到檢查證據 2 和 3 時再細講。

現在手上有吞吐量、延遲、並行數三個數字。它們之間有一條公式連起來，用它就能檢查第一樣證據：連線池 10 條，週年慶夠不夠。

Little's Law：連線池 10 條夠不夠？

連線池的條數，本質上就是一個並行數的上限：每個查詢執行期間佔著一條連線，查完才還回去。所以「10 條夠不夠」可以換成另一個問題：週年慶尖峰時，平均同時有幾個查詢在用連線？如果超過 10，多出來的查詢只能排隊等連線。

回答它的公式叫 Little's Law。它成立的前提是系統處於穩定狀態：在一段夠長的時間裡，進來的請求數跟完成的請求數一樣多，沒有越積越多。滿足這個前提時：

L = λ × W
L：系統裡平均同時有幾個（並行數）
λ：每秒到達幾個（吞吐量，念作 lambda）
W：每個平均停留多久（延遲，單位要換成秒）

為什麼成立，可以用咖啡店想：平均每分鐘進來 2 位客人，每位在店裡待 5 分鐘。任何一個時刻還在店裡的，就是最近 5 分鐘內進來的那些人，大約 2 × 5 = 10 位。每秒進來 λ 個請求、每個停留 W 秒，任何時刻還沒處理完的，就是最近 W 秒內到達的那 λ × W 個。

這個推理沒有用到請求長什麼樣、怎麼排隊，所以它幾乎在任何系統都成立，而且可以三個方向用：

  • 算並行數：尖峰每秒 50 個請求、平均 200ms → 50 × 0.2 = 同時約 10 個在處理。
  • 算連線池：每秒 100 個查詢、每個查詢佔用連線 20ms → 100 × 0.02 = 平均 2 條連線在用。再乘上餘裕，就是池子該開的大小。
  • 反過來算上限：池子只有 10 條、每個查詢 50ms → 一條連線每秒最多 20 個查詢 → 最多每秒 200 個查詢。超過就開始排隊等連線。

現在套到下單 API：每張訂單打 8 次資料庫，每次佔用連線 20ms。執行後看兩件事：週年慶那一行平均要幾條連線，以及 pool 10 條最多撐幾筆訂單。這裡算的是全系統平均要幾條連線；機器有好幾台時，要比的是 台數 × 每台 pool 的總和（第 2 課），而這個總和又不能超過資料庫的 max_connections，見本節的實務上。

平常尖峰平均只要 0.53 條，難怪「從來沒出過事」。週年慶時平均要 10.66 條，pool 只有 10 條，最多撐每秒 62.5 筆訂單，而週年慶要 66.6 筆：查詢一定會排隊等連線。這時下單延遲會變差，但程式一行都沒改，這就是「延遲變差但程式沒變」的典型原因。

還要注意 Little's Law 算出的是平均。實際流量會一陣多、一陣少，平均 10.66 條的時候，忙的那幾秒可能要 15 條。所以不能把 pool 開成剛好等於平均，要再留餘裕，也就是第 2 課的目標使用率。

單位要統一。λ 是每秒、W 是毫秒時，一定要先把 W 除以 1000，不然 pool 會算大 1,000 倍。

證據 1 的結論：連線數不能靠「從來沒出過事」，要用 Little's Law 算出總需求，再對照 台數 × pool 和資料庫的 max_connections。

💡 實務上：連線池大小用算的，也要算總數
大部分專案的連線池都是套件預設值，直到週年慶出現「等不到連線」的逾時才去看。上線前用 Little's Law 估一次，記在設定旁邊的註解，數字變了才知道要重算。另一個常見坑是只算單台：API 從 2 台擴到 6 台，每台 pool 20 條就是 120 條，可能超過資料庫的連線上限（PostgreSQL 預設 max_connections 是 100），結果擴機反而讓資料庫拒絕連線。資深工程師調 pool 前會先問：總共有幾個實例、資料庫能接幾條、慢查詢是不是才是真正把連線佔住的原因。

但這一節用的「每個查詢 20ms」是平均值。Little's Law 要的就是平均，可是使用者感受到的不是平均，而是自己那一次等了多久。下一節檢查第二樣證據：儀表板上平均 132ms，能不能代表使用者的體驗。

平均值會騙人：儀表板上的 132ms 代表誰？

平均值能用在 Little's Law，是因為那裡要算的就是「平均有幾條連線在用」。但描述使用者的等待時，平均會出問題，因為延遲不是一個數字，而是一個分布：大部分請求很快，少數很慢。慢的原因有很多種：兩個交易搶同一列資料時，後到的要等鎖；Node 做垃圾回收（GC，第 2 課提過）時，程式會短暫停下來；遇到一個沒用到索引的慢查詢；網路掉了封包，要等一段時間才重傳。這些事件不常發生，但一發生就是幾百毫秒到幾秒。部署課第 22 課看過這個現象，這裡把它算一次。

假設儀表板那 132ms 背後是 1,000 個下單請求：965 個 50ms，35 個卡住 2,400ms。執行後比較平均和 p99：

平均是 132ms，但沒有任何一個請求真的花了 132ms：96.5% 的人等 50ms，3.5% 的人等 2.4 秒。平均值把兩群人混成一個不存在的數字。它不代表「大部分人」，因為大部分人比平均快；也看不到慢的那群，因為 35 個 2.4 秒被 965 個 50ms 稀釋了。證據 2 不能信：同樣是平均 132ms，背後如果是這種分布，p99 是 2,400ms，目標早就沒達到；光看平均分辨不出來。

要回答「最慢的那一小群有多慢」，用的是百分位數（percentile）：p 百分位數是一個值，至少 p% 的資料小於或等於它。p50 就是中位數，一半的請求比它快；p99 是 99% 的請求都不超過它。

直覺上「排在第 99% 位置」很清楚，但資料只有有限個時，這個位置常常不是整數，例如 5 個值的 p30 是第 1.5 個。所以要先講好怎麼取整數。這門課用最直接的 nearest-rank 定義：把位置無條件進位，取那一個實際存在的值。進位而不是捨去，是為了保證至少有 p% 的值小於或等於取出來的那個。

把 n 個值由小到大排好
rank = ceil(p × n ÷ 100)       （1 起算）
p 百分位數 = 第 rank 個值

例：[15, 20, 35, 40, 50]，n = 5
p30 → rank = ceil(1.5) = 2 → 20
p50 → rank = ceil(2.5) = 3 → 35
p100 → rank = 5 → 50（最大值）
p × n ÷ 100 要先乘再除。0.07 * 100 在 JavaScript 是 7.000000000000001，Math.ceil 之後變成 8，多算一名；7 * 100 / 100 剛好是 7。

p99、p99.9 這些描述最慢那一小段的百分位數，合稱尾延遲（tail latency）。名字來自分布圖：把延遲畫成橫軸，大部分請求擠在左邊，少數很慢的請求拉成右邊一條長長的尾巴。百分位數還有別的算法，數值會略有不同，見課末「補充與查表」。

你可能會想：p99 只影響 1% 的請求，有那麼重要嗎？問題是使用者一次操作通常不只一個請求。App 首頁要打 5 個 API，只要其中一個碰到 p99，這一頁就慢。每個 API 各有 1% 機率慢，整頁至少碰到一次的機率是 1 − 0.995 ≈ 4.9%，每 20 次開 App 就有 1 次。重度使用者每天開好幾次，他們幾乎天天遇到，而重度使用者正是週年慶最會下單的那群人。後面講扇出時會把這個效應算到更大的規模。

所以 SLO 用 p99 是對的，證據 2 要換成 p99 來看。

💡 實務上：週報和告警看 p95／p99，不看平均
監控儀表板預設常顯示平均延遲，看起來一切正常，客服卻一直收到「下單轉很久」的回報，這時要把圖改成 p95、p99。跟 PM 或主管報告時，用「100 個人裡最慢的 1 個要等多久」來講，比百分位數這個詞好懂。也要注意樣本數：一小時只有 50 筆的冷門 API，p99 幾乎就是最大值，跳動很大，不適合拿來告警。前端也一樣，Google 的 Core Web Vitals 就是看第 75 百分位數，而不是平均。

可是正式環境每秒幾百個請求，監控系統不可能把每個延遲都存下來排序，那儀表板上的 p99 是怎麼來的？第三樣證據「三台的 p99 平均起來達標」就卡在這個問題上。

Histogram：監控系統不存每個值，怎麼算出 p99？

上一節的算法要把所有延遲排序。假設一個 API 每秒 100 個請求，一天就是 864 萬個值，還要每個路由、每台機器各存一份，記憶體和排序成本都太高。監控系統用的辦法是直方圖（histogram）：不存每個值，只存計數。

做法像學校量身高分組：不記每個人幾公分，只記「150 以下幾人、150～160 幾人、160～170 幾人」。延遲也一樣，先定好邊界，例如 50、100、200、400、800ms，每個請求落在哪一桶（bucket）就把那一桶加 1。不管來了多少請求，存的永遠只是 6 個數字。代價是失去了精確值：只知道某個請求在 100～200ms 之間，不知道是 101 還是 199。

值剛好等於邊界時放進那一桶，例如 50ms 算在 (0, 50] 桶。超過最後一個邊界的放進 +Inf 桶，代表「比 800ms 還慢」。部署課第 22 課用來收集、查詢指標的系統 Prometheus 就是這樣存的，它把每個桶的邊界標成 le，意思是「小於等於」。

只有計數時，p 分位要用估的。Prometheus 的 histogram_quantile 這樣估（官方文件，classic histogram）：

  1. rank = q × 總數（q 是 0～1，p99 就是 0.99）。
  2. 從第一桶開始累加，找到第一個累計數 ≥ rank 的桶。
  3. 假設桶內的值平均分布，在桶的上下邊界之間線性內插：下界 + (上界 − 下界) × (rank − 前面的累計數) ÷ 這一桶的數量。第一桶的下界當作 0。
  4. 落在 +Inf 桶時，沒有上界可以內插，回傳最後一個有限邊界。

第 3 步的「線性內插」是這樣想的：已經知道答案在某一桶裡，但不知道桶裡的值怎麼分布，只好假設它們平均地排在上下邊界之間，再按 rank 在這一桶裡的位置，取對應比例的那個點。用下面這張表跟著算一次：

桶(0, 50](50, 100](100, 200](200, 400](400, 800]+Inf
數量60306301
累計6090969999100

p95：rank = 95，第一個累計 ≥ 95 的是 (100, 200] 桶，前面累計 90、這桶 6 個，rank 落在這桶的第 5 個 → 100 + 100 × (95 − 90) ÷ 6 ≈ 183ms。真正的值可能是 101 也可能是 200，誤差最多是一個桶寬。這個誤差會直接影響證據 3 的判斷，下面分兩件事看。

SLO 門檻要剛好是桶邊界

第 1 課那個「尖峰時 p99 小於 300ms」的目標，正式名稱是服務水準目標（SLO，service level objective）：一個可量測、團隊承諾要達到的延遲或可用性目標。要判斷有沒有達標，histogram 的桶怎麼切很關鍵。

如果桶是 200、400，估出來的 p99 只能在 200～400 之間用內插猜：估出 280 時，真正的值可能是 350，判斷不了到底有沒有達標。把 300 設成邊界，問題就從「估 p99」變成「數 ≤ 300ms 的有幾個」：直接看 (0, 300] 以下的累計數佔總數多少，大於等於 99% 就達標，這個判斷沒有內插誤差。Prometheus 的 histogram 實務文件也這樣建議。

百分位數不能平均，histogram 可以相加

現在可以處理證據 3 了。三台 API 的 p99 是 100、120、900ms，平均是 373ms；就算平均剛好低於 300，它也沒有意義，因為整體 p99 不是三個 p99 的平均。百分位數是「把所有請求排在一起後的某個位置」，三台合在一起排時，每台的請求佔多少比例會改變那個位置：

  • 慢的那台如果處理了大部分流量，整體 p99 會接近 900ms；如果只處理一點點，可能比 120 還低。
  • 正確做法是把三台同一個桶的計數相加，再對合併後的 histogram 算一次（練習 3 的 merge）。
  • Prometheus 還有另一種指標叫 summary，它在每台機器上直接算好分位數再送出去。Prometheus 文件說 summary 不能跨實例彙總，原因就是這裡講的：分位數一旦算好，就沒辦法再合併。

histogram 能合併，是因為它存的是計數：A 台 (100, 200] 桶有 6 個、B 台同一桶有 4 個，合起來就是 10 個，跟把兩台的請求記在同一個 histogram 完全一樣。前提是兩邊的桶邊界相同，邊界不同就對不起來。Prometheus 另一種較新的 histogram 格式見課末「補充與查表」。

證據 2 和 3 都處理完了：改成合併三台的 histogram、算整體 p99，並把 300ms 設成桶邊界。

💡 實務上：加 histogram 指標前先想好桶和標籤
幫咖啡店 API 加延遲指標時，桶的邊界通常放 SLO 門檻和它前後幾個值，不需要切得很細。每多一個桶、每多一種標籤組合，Prometheus 就多存一條時間序列，所以標籤只放路由、狀態碼這種種類有限的值，不要放使用者 ID 或訂單編號（部署課第 22 課的基數爆炸）。在 Grafana 看到的 p99 曲線是估計值，跟從 log 精確排序算出的 p99 對不上是正常的，誤差最多一個桶寬；如果 p99 曲線一直平平地貼在最後一個邊界，代表它落在 +Inf 桶，最後一個邊界設太小了。

但就算現在 p99 達標，那也是平常的流量。週年慶時機器會更忙，第四樣證據說「CPU 才 50%，跑到 90% 再加機器都來得及」，這句話對嗎？

CPU 才 50%，跑到 90% 再加機器來得及嗎？

使用率（utilization）是資源忙碌的時間比例：CPU 50% 代表一半的時間在做事、一半的時間閒著。維運那句話背後的直覺是「使用率跟延遲大致成正比，90% 只比 50% 慢一點點」。實際上差非常多，原因是排隊。

回到吧台：平均每 6 分鐘來一位客人，做一杯 3 分鐘，咖啡師一半時間在做、一半時間閒著，使用率 50%。如果客人準時每 6 分鐘來一位，永遠不用等。但真實的客人是隨機來的，有時 10 分鐘沒人，有時 3 位同時進門，第 3 位要等前兩杯做完，等 6 分鐘。使用率低的時候，這種擠在一起的隊伍很快就被後面的空檔消化掉；使用率越高，空檔越少，一次擠出來的隊伍還沒消化完，下一批又來了，隊伍越積越長。所以越接近滿載，排隊時間不是慢慢增加，而是急遽上升。

排隊理論用模型把這個形狀算出來。最簡單的模型叫 M/M/1：請求隨機到達、每個請求的處理時間也隨機、只有一個服務者在處理。在這個模型下：

平均回應時間 = 處理時間 ÷ (1 − 使用率)

這是理想化的模型，真實系統的數字會不同，但「接近 100% 時急遽上升」的形狀是一樣的。看圖，再執行程式看數字：

執行後看使用率 90% 以上那幾行：回應時間從 50% 時的 2 倍跳到 10 倍、20 倍以上。同樣一個 20ms 的查詢，使用率 50% 時使用者平均等 40ms，90% 時等 200ms，95% 時等 400ms，光是這一個查詢就超過整個下單 300ms 的目標。從這條曲線可以得到三件事：

  • 目標使用率：這就是第 2 課用 60% 當目標的原因，留空間吸收突發，延遲也還在平穩的區段。
  • 量測：只在低負載下量延遲沒有意義，使用率高的時候，排隊才是延遲的主角。
  • 過載時：與其讓每個請求都排很久、全部逾時，不如直接拒絕一部分，讓其他請求正常完成，這叫負載卸除，第 11 課會實作。

證據 4 的結論：等到 90% 才加機器，新機器開好之前延遲早就衝上去了。

💡 實務上：自動擴展和告警不要等到快滿才觸發
設定自動擴展（autoscaling）時，觸發門檻設在 CPU 90% 看起來省錢，但新機器開起來要時間，這段期間延遲已經衝上去了。比較穩的做法是門檻放在延遲還平穩的區段，並對 p99 延遲設告警，而不是只看 CPU。可預期的尖峰（週年慶、行銷推播）要事先手動加機器，不要全靠自動擴展臨場反應。維運同事問「現在 CPU 才 70%，為什麼就慢了？」時，這張曲線就是答案。

排隊讓一個服務的尾巴變長；而下單 API 並不是自己一個人做完所有事，它還要同時查菜單、查會員（第 1 課的下單流程）。每多一個下游，就多一次碰上尾延遲的機會，下一節看這個效應有多大。

下單同時呼叫好幾個服務：扇出怎麼放大尾延遲？

下單 API 驗證完 token 後，會同時查菜單、查會員（第 1 課的下單流程），兩個都回來才能寫訂單。這種一個請求同時呼叫多個下游、要等全部回來才能繼續的結構，叫扇出（fan-out），像扇子一樣從一點展開成很多條。扇出部分的延遲是最慢的那一個（第 1 課的「平行取最大」），所以只要有一個下游慢，整個請求就慢。

上一節講 App 首頁打 5 個 API 時已經算過一次：每個 1% 慢，整頁約 4.9% 慢。下面把扇出數加大。執行後看扇出 100 個那一行：

扇出 100 個時，63% 的請求會慢。這是 Google 的論文〈The Tail at Scale〉（CACM 2013）的例子：規模大了，「1% 的慢」會變成「大多數人都慢」。搜尋、推薦這類要同時查上百台機器的系統，最先撞上這個問題。

咖啡店的下單只扇出 2 個，每個 1% 慢時約 2% 的下單會慢，還在可控範圍；但這也說明了為什麼每個下游的 p99 都要壓低，整個請求的延遲才會好看，以及為什麼服務的延遲目標要看 p99，不看平均：上游看到的延遲，是所有下游尾延遲疊起來的結果。

壓低每個下游的 p99 是根本做法。扇出很大、尾延遲已經是瓶頸時，還有一招直接在呼叫端把尾巴剪掉，下一節是選讀；不讀的話，直接跳到〈壓測報告說 p99 15ms，可信嗎？〉那節檢查最後一樣證據。

hedged request：慢了就再送一次（選讀）

這節是選讀：扇出很大、尾延遲已經是瓶頸時才需要它，一般的 API 先把逾時與重試做好（第 8 課）就夠了；要優化扇出很大的讀取時再回來看，練習 4 是這節的實作。跳過不影響後面的課。

這個做法需要副本（replica）：跑同一個服務、資料也相同的另一台機器，請求送給哪一台都會得到一樣的答案。〈The Tail at Scale〉提出的一個解法是 hedged request（避險請求）：送出請求後，如果超過一段時間（例如該請求的 p95）還沒回應，就再送一個給另一台副本，用先成功回來的那個，並取消另一個。它利用的是尾延遲的特性：慢通常是那一台當下碰到 GC、鎖或排隊，換一台很可能就快了。設計時有四個要點：

  • 為什麼等 p95 才送：只有最慢的約 5% 會觸發第二次，額外負載大約 5%。一開始就送兩個，負載直接加倍。
  • 第一次失敗就馬上送第二次：不用等計時器。
  • 要取消輸的那個：用 AbortController（TypeScript 課第 11 課）通知它停下來，不然下游白做工；成功後也要取消計時器，不然計時器到了又送出第二次。
  • 只用在可以重複執行的讀取：查菜單、查會員可以；建立訂單送兩次就是兩張訂單。寫入要搭配第 9 課的冪等鍵（idempotency key）：同一個操作帶同一把鍵，伺服器只做一次。

練習 4 會實作它。時間不直接用 setTimeout，而是由外面傳入 schedule(ms, fn)（回傳取消函式），測試就能用假時鐘精確推進，不用真的等（Node 課第 22 課的作法）。這門課之後每個跟時間有關的練習都用這個寫法。

壓測報告說 p99 15ms，可信嗎？

前四樣證據來自設定和正式環境的監控；最後一樣來自壓測。壓測很重要，因為第 2 課的台數公式需要「單台實測容量」，這個數字只能靠壓測量出來。但壓測量出來的數字準不準，取決於壓測工具怎麼送請求。工具有兩種送法：

  • 封閉負載模型（closed workload）：固定開 N 條連線，每條等上一個回應回來才送下一個。autocannon（Node 課第 23 課用過的壓測工具）預設就是這樣（預設 10 條連線）。
  • 開放負載模型（open workload）：請求依固定速率到達，不管伺服器有沒有回應。真實使用者就是這樣：伺服器卡住時，客人照樣一直進來。

兩種送法在伺服器正常時量出來差不多，差別出在伺服器卡住的時候。假設伺服器因為 GC 或資料庫鎖卡住 2 秒：封閉模型的 10 條連線全都在等回應，等的這 2 秒內一個新請求都不會送出，最後只記下 10 個慢的請求。真實世界裡，如果每秒有 50 位客人下單，這 2 秒會進來 100 個請求，全部排隊、全部很慢。這 100 個請求在封閉模型裡根本沒有被送出、也沒有被量到，報告裡慢的請求就少了一大截，p99 自然好看。

這個現象叫 coordinated omission：壓測工具跟著伺服器一起停下來，就像兩者「協調好」一起漏掉了最慢的那一段。同事那份 p99 15ms 的報告，如果用的是 autocannon 預設設定，就是封閉模型，證據 5 不能直接信。

所以壓測要用開放模型，用固定到達率送請求：

  • wrk2 用固定速率送出，並從「本來應該送出的時間」開始算延遲。這樣伺服器卡住期間，本來該送出的請求也會被算進去，延遲包含它們等待的那段。
  • autocannon 用 -R（--overallRate）指定整體速率時，也會修正 coordinated omission。

送法對了，還要注意量測條件，不然數字一樣沒有參考價值：

  • 先暖機：剛啟動時連線池還沒建好、快取是空的，JavaScript 引擎也還沒把常執行的程式碼編譯成機器碼（JIT 編譯），前幾十秒特別慢，這段的數字不算。
  • 條件接近正式環境：資料量、機器規格、網路距離都會影響結果。用空資料庫量出來的數字沒有參考價值，因為查詢在幾筆資料上跟在幾百萬筆資料上的速度完全不同。
  • 依路由分開看：菜單（快、量大）和下單（慢、量小）混在一起，下單的尾延遲會被菜單稀釋，跟證據 2 的平均值是同一個問題。
  • 逐步加壓，找延遲開始上升的點：p99 還在目標內的最大吞吐量，才是單台容量。把它回填到第 2 課的機器數量公式，取代猜的數字。

五樣證據都檢查完了，現在可以回答主管：連線池要照 Little's Law 重算，並檢查所有台數加起來沒超過資料庫上限；監控改看合併後的 p99，300ms 設成桶邊界；擴展門檻放在延遲還平穩的區段，週年慶前手動加機器；用固定到達率重新壓測，量出 p99 達標的單台容量，再回填台數。下一節是選讀，用模擬算出封閉模型到底少算了多少。

百分位數的其他定義

nearest-rank 之外，也有別的定義，例如在兩個值之間線性內插，數值會略有不同；團隊內要講好用哪一種。

Prometheus 的 native histogram

Prometheus 另外有 native histogram（桶邊界自動、解析度高），但目前要用 protobuf（Google 的二進位資料格式）輸出；部署課用的 prom-client 15.1.3 輸出的是 classic histogram，也就是這課實作的這種。

練習

練習 1：寫三個 Little's Law 的函式。做完的樣子：inFlight(50, 200) 印出 10，三個函式都對得上「Little's Law」一節那三個例子。輸入的延遲都是毫秒，算之前要換成秒。

  1. inFlight(rps, latencyMs)：每秒 rps 個請求、平均 latencyMs，平均同時有幾個在處理（L = λ × W）。
  2. poolSizeFor(o)：尖峰每秒 peakRps 個請求、每個請求打 queriesPerRequest 次資料庫、每次佔用連線 queryMs，先算平均幾條連線在用，再乘上 1 + headroom（0.5 代表多 50%），最後進位成整數。
  3. maxRpsForPool(poolSize, queriesPerRequest, queryMs)：連線池有 poolSize 條時，每秒最多撐幾個請求（「反過來算上限」那個例子）。
提示
  • maxRpsForPool 先算一個請求佔用連線幾秒（查詢次數 × 每次秒數），再用池子條數去除。
  • Math.ceil 遇到剛好整除的值時，浮點誤差可能讓結果多 1（例如 0.1 * 3 * 10 是 3.0000000000000004）。測試允許這種情況，但不允許少算。

練習 2：寫 percentile(values, p)，用 nearest-rank 定義算出 p 百分位數。做完的樣子：percentile([15, 20, 35, 40, 50], 30) 印出 20，跟「平均值會騙人」一節的例子一樣。

  1. 檢查輸入：p 不在 (0, 100] 之間、或 values 是空陣列時，丟 RangeError。
  2. 排序：不能修改 values（呼叫端可能還要用原本的順序），先複製再排序，而且要依數值排序。
  3. 取值：rank 用 Math.ceil(p * n / 100)，先乘再除；rank 是 1 起算，陣列索引要減 1。
提示

[...values].sort() 不傳比較函式會照字串排，[100, 20] 排完還是 [100, 20]；要寫 (a, b) => a - b。NaN 不在範圍內，用 !(p > 0 && p <= 100) 才擋得到。

練習 3：完成 LatencyHistogram。做完的樣子：起始程式最後一行印出 5 75（5 筆；p50 的 rank 是 2.5，落在 (50, 100] 桶，內插出 75）；用「Histogram」一節那張表的資料，quantile(0.95) 約是 183。建構子和欄位已經寫好：counts[i] 是第 i 桶的數量，最後一格是 +Inf 桶。照順序寫：

  1. record(ms)：放進第一個 ms ≤ 邊界 的桶，都不符合就放 +Inf 桶；負數或 NaN 丟 RangeError。
  2. count()：總共記了幾個。
  3. quantile(q)：照「Histogram」一節的四個步驟估計。q 在 (0, 1] 之外丟 RangeError；沒有資料回傳 NaN。
  4. merge(other)：邊界完全相同才能合併（否則丟 Error），回傳計數相加的新 histogram，不能修改 this 或 other（「百分位數不能平均，histogram 可以相加」）。
提示
  • record：this.bounds.findIndex(b => ms <= b) 找不到時回傳 -1，那就是 +Inf 桶（索引 bounds.length）。!(ms >= 0) 同時擋得到負數和 NaN。
  • quantile：用一個 before 記「前面的累計數」，逐桶檢查 before + counts[i] >= rank。第一桶的下界是 0，其他桶的下界是 bounds[i - 1]。
  • merge：new LatencyHistogram(this.bounds) 建一個空的，再把兩邊的計數逐格相加進去。

練習 4（選讀，對應「hedged request」一節）：寫 hedged(attempt, hedgeAfterMs, schedule)，對一個可以重複執行的讀取做 hedged request。做完的樣子：最多送 2 次，回傳先成功的那個，輸的那個被 abort、計時器被取消；兩次都失敗才 reject。不能用 setTimeout，時間只能透過 schedule（它回傳的函式呼叫後就取消計時器）。

  1. 開始：立刻呼叫 attempt(1, signal)，並用 schedule 排一個 hedgeAfterMs 的計時器。
  2. 送第 2 次：計時器到了、或第 1 次失敗時，呼叫 attempt(2, signal)。第 1 次失敗而提早送出時，計時器要取消。
  3. 成功：回傳第一個成功的結果，abort 另一個還在跑的嘗試，並取消計時器。
  4. 失敗：兩次都失敗時，用最後一個失敗的錯誤 reject。
提示

用 new Promise<T>((resolve, reject) => { … }) 自己決定何時 resolve；每次嘗試配一個 AbortController；用一個 done 旗標避免輸的那個在之後又改到結果。測試用 Promise.withResolvers 做的 deferred（自己決定何時 resolve／reject 的 Promise）控制每次嘗試何時成功或失敗，用假的 schedule 推進時間。

練習 5：下單 API 平均 120ms、p99 2.4 秒。App 首頁一次打 5 個 API。哪個數字比較能代表使用者的體驗？

✓ c。平均值把很快的大多數和很慢的少數混成一個沒人真的經歷過的數字；它不代表「大部分人」（大部分人比平均快），也看不到慢的那群（a 錯）。每個 API 各 1% 慢、一頁打 5 個，約 4.9% 的頁面會慢，重度使用者幾乎天天遇到，所以 b 錯。

練習 6：三台 API 的 p99 分別是 100、120、900ms。整體的 p99 是多少？

✓ b。百分位數取平均在統計上沒有意義（a 錯）。整體 p99 取決於每台處理了多少流量、分布長什麼樣：900ms 那台只處理 1% 的流量時，整體 p99 可能遠低於 900（c 錯）。histogram 只存計數，同一個桶可以直接相加。

練習 7：為了省錢，想把機器使用率從 50% 提高到 95%。平均回應時間會怎樣？

✓ a。回應時間包含排隊，處理時間不變（c 錯）不代表等待時間不變。M/M/1 模型下回應時間是處理時間 ÷ (1 − 使用率)：50% 是 2 倍、95% 是 20 倍，差 10 倍，不是線性（b 錯）。真實系統的數字不同，但形狀一樣。

練習 8：壓測工具開 10 條連線，每條等上一個回應回來才送下一個，量出 p99 = 15ms。報告可信嗎？

✓ c。封閉模型下，伺服器卡住 2 秒只會記下 10 個慢請求，真實使用者在那 2 秒內會持續湧入、全部排隊（a 錯）。多開連線只是讓「同時被卡住的」多幾個，還是少算（b 錯）。用 wrk2 或 autocannon 的 -R 固定速率送，延遲從本來應該送出的時間算起。

常見錯誤

  • 連線池用預設值、不算總數：平常流量用不滿，週年慶才開始排隊等連線。用 Little's Law 算尖峰要幾條、再留餘裕，並確認 台數 × pool 沒超過資料庫的 max_connections。
  • Little's Law 單位混用：ms 和 s 沒換算，pool 大小差 1,000 倍。先把延遲除以 1000。
  • 用平均值描述延遲：平均會被大量快的請求拉低，看不到真正等很久的人。SLO 和告警用 p95／p99。
  • 把各台機器的百分位數取平均：沒有意義，整體 p99 取決於每台處理了多少流量。用 histogram 記錄，合併計數後再算。
  • histogram 的桶邊界沒有包含 SLO 門檻：估出來的值在桶寬內飄，判斷不了是否達標。把門檻（例如 300ms）設成邊界。
  • 只在低負載下量延遲：使用率高時排隊才是主角。要逐步加壓，找 p99 開始超標的點。
  • 對寫入做 hedging：同一筆訂單被建立兩次。只用在可以重複執行的讀取，寫入要搭配冪等鍵（第 9 課）。
  • hedged request 沒取消輸的那個：下游白做工，失敗時還可能留下沒處理的 rejection。成功後要 abort 另一個、取消計時器。
  • 相信封閉模型的壓測數字：coordinated omission 會讓 p99 好看很多倍。用固定到達率。

小結

  • 延遲是一個請求等多久（包含排隊），吞吐量是每秒完成多少個，並行數是同時在處理幾個；加機器提高吞吐量，不會讓單一請求變快。
  • Little's Law：L = λW。用它算並行數、連線池大小、某個 pool 能撐的上限；延遲要換成秒，算出的是平均，要再留餘裕。咖啡店週年慶平均要 10.66 條連線，預設的 10 條撐不住。
  • 延遲要用百分位數描述；nearest-rank：排序後取第 ceil(p × n ÷ 100) 個。平均 132ms 的背後，p99 可能是 2.4 秒。一次操作打越多 API、扇出越多，越多使用者遇到尾延遲。
  • histogram 只存計數、桶內線性內插、誤差在一個桶寬內；SLO 門檻要是桶邊界；跨機器要合併計數，不能平均百分位數。
  • 使用率越接近 100%，排隊時間越暴增，所以要留餘裕、擴展門檻放在延遲還平穩的區段，過載時要卸除負載。
  • （選讀）hedged request 在 p95 之後才送第二次，用先成功的、取消另一個，只用在可以重複執行的讀取。
  • 壓測要用開放模型（固定到達率），避免 coordinated omission；暖機、依路由分開看，量出 p99 達標的單台容量回填估算。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：結帳 API 先驗證 token 5ms，再同時查庫存 40ms、查優惠券 25ms，最後寫訂單 20ms。哪個優化真的會讓總延遲變短？

✓ 總延遲 ＝ 5 ＋ max(40, 25) ＋ 20 ＝ 65ms，關鍵路徑是查庫存，壓到 30ms 總共省 10ms。a 錯在查優惠券本來就比查庫存早結束，沒人在等它，省了 23ms 總延遲還是 65ms。c 不行：寫訂單要用到兩個查詢的結果，有依賴的步驟不能平行。（第 1 課）

練習 10：週年慶前用尖峰的請求組合壓測：API 4 台、使用率 55%；PostgreSQL CPU 95%、慢查詢變多，下單 p99 超標。主管問要加幾台 API，你先做什麼？

✓ 瓶頸是資料庫：它最先到頂，決定整個系統的上限，加 API 機器上限一點都不會變。要讓資料庫少被打：減少下單路徑的查詢次數、提高快取命中率，之後再考慮讀副本（第 6 課）。a 是最常見的直覺，花了錢，p99 不會改善。（第 1 課）

練習 11：行銷 10:00 推播「買一送一」，預估當天 1.2 萬筆訂單，其中 60% 會在推播後 10 分鐘內下單。下單 API 要照哪個數字規劃容量？

✓ 容量照尖峰規劃，推播造成的瞬間尖峰要用「幾分鐘」去除：7,200 筆擠在 600 秒內，每秒約 12 筆。b 沿用平常「早上 2 小時」的尖峰時段，低估了 12 倍，推播後幾分鐘就撐不住。c 是全天平均，差了將近兩個數量級。（第 2 課）

練習 12：咖啡店的設定如下。週年慶時自動擴展一路加到上限，會怎樣？

API：自動擴展，最少 2 台、最多 12 台
每台 API 的 node-postgres Pool：max 10
排程程式：另外一個 Pool，max 10
PostgreSQL：max_connections 100，保留 3 條給超級使用者

✓ 要檢查 台數 × pool ＋ 其他程式的 pool ≤ max_connections − 保留：9 × 10 ＋ 10 ＝ 100，超過 97。擴展上限要照這條算，或調小 pool、改用 PgBouncer 這類連線池代理。a 錯在擴到上限的時候正是尖峰，每台的 pool 都會用滿。（第 2 課）

練習 13：週年慶時下單變慢，程式沒改、API CPU 只有 40%。這台 API 每秒打資料庫 600 次，每次佔用連線 25ms，pool 是 10 條。最可能的原因是？

✓ Little's Law：L ＝ λ × W ＝ 600 × 0.025 ＝ 15，pool 比平均需要的連線數還少，一定會排隊，這就是「延遲變差但程式沒變」。Little's Law 給的是平均，調 pool 要再留餘裕，也要算所有台數加起來的總數。d 錯在 25ms 沒換成秒，算大了 1,000 倍。（第 3 課）

練習 14：儀表板上下單 API 平均 150ms，三台各自的 p99 取平均是 280ms，都在「300ms」目標內，客服卻一直收到「下單轉很久」。先改什麼？

✓ 平均會把等很久的少數藏起來，各台 p99 取平均在統計上沒有意義，兩個「達標」都不能信。histogram 只存計數，同一個桶可以跨機器相加，合併後再算 p99；300ms 要設成桶邊界，才判斷得出有沒有達標。b 錯在 p50 跟平均一樣看不到慢的那群，SLO 和告警要看 p95／p99。（第 3 課）

練習 15：維運想省錢，把自動擴展門檻從 CPU 60% 改成 90%：「處理時間又沒變，90% 只會慢一點點。」你怎麼回？

✓ 回應時間包含排隊；在 M/M/1 模型下是處理時間 ÷ (1 − 使用率)，60% 是 2.5 倍、90% 是 10 倍，不是線性（a 錯）。門檻放在延遲還平穩的區段，並對 p99 設告警；可預期的尖峰要事先手動加機器。b 錯在使用率正是排隊的原因，而平均延遲會藏住尾延遲。（第 3 課）

練習 16：要量出單台 API 的容量，回填第 2 課的台數公式。壓測該怎麼做？

✓ 開放模型（固定到達率）才像真實使用者，伺服器卡住時客人照樣進來；容量看 p99 還達標的最大吞吐量，不是撐到出錯為止。a 是封閉模型：伺服器卡住時工具也跟著等，那段的請求沒被量到（coordinated omission），p99 會好看很多倍。b 會讓下單的尾延遲被菜單稀釋，c 量出來的數字沒有參考價值。（第 3 課）
