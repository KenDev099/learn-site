階段 4：架構：服務、事件與即時推送 · 第 16 課

事件驅動與 webhook

咖啡店的訂單服務在顧客付款成功後，要通知五個地方：集點、廚房出單、寄收據、營收報表，還有外送平台。最早的寫法很直覺：付款成功之後，依序呼叫這五個服務，全部成功才回應顧客「付款完成」。後來報表服務部署失敗、掛了 10 分鐘，這 10 分鐘內所有付款都回 500。錢其實已經扣了，失敗的只是「通知報表」這一步，顧客卻看到付款失敗，有人還再付了一次。再後來行銷部門想加「首購送優惠券」，又得去改訂單服務的程式、重新部署，跟一個與優惠券無關的團隊排上線時間。

這一課就做一件事：把「付款後通知其他人」從同步呼叫改成事件。訂單服務只宣布「這張訂單付款了」，誰需要就自己來聽。改完之後要做到四件事：報表掛了不影響付款；加新功能不用改訂單服務；集點不會因為同一則通知來兩次而加兩次、廚房畫面不會因為通知晚到而倒退；公司外面的外送平台也收得到，而且收得到的方式不會被某一個客戶拖垮。

這課的路線：
  1. 「通知報表」為什麼能讓付款失敗：同步呼叫的問題，命令和事件差在哪（開場問題的最小答案）。
  2. OrderPaid 裡要放多少資料：只放 ID、放完整資料，還是折衷。
  3. 消費者怎麼認出同一個事件、排出先後：每個事件該帶的 ID、來源和序號。
  4. 集點為什麼會加兩次、廚房畫面為什麼會倒退：消費者怎麼處理重複與亂序，以及廚房畫面怎麼從事件組出來。
  5. 怎麼把事件送到公司外面的外送平台：webhook 的重送、簽章與隔離；最後是什麼時候不該用事件。
這課會用到：
  • NestJS 課第 21 課的程序內事件（EventEmitter2）：發出事件、多個 listener 各自處理；限制是程序一重啟，還沒處理的事件就沒了。
  • 第 12 課的至少一次送達與 outbox／inbox：同一則訊息一定會來兩次，消費者用 inbox 去重；訊息和訂單寫在同一個交易，不會漏送。
  • 第 9 課的冪等鍵：同一把鍵送很多次，對方只做一次。

「通知報表」為什麼能讓付款失敗？命令與事件

先看開場的事故是怎麼發生的。付款 API 的程式長這樣：扣款成功，然後 await 集點、await 廚房、await 收據、await 報表、await 外送平台，最後回應顧客。任何一個 await 丟錯，整個請求就失敗。這五個呼叫都是硬相依：每一個都必須活著，付款 API 才會成功。第 15 課算過，硬相依的可用性要相乘，五個 99.9% 的服務串在一起，付款 API 最多只剩約 99.5%，而且延遲是五個服務的延遲加起來。

但仔細想，顧客其實只在乎一件事：卡有沒有過。集點晚 3 秒加上去、報表晚 10 分鐘更新，顧客根本不會發現。問題出在付款 API 把「付款」和「付款之後別人要做的事」綁在同一個請求裡。要拆開它們，得先分清楚服務之間傳的訊息有哪幾種意圖。

服務之間傳的訊息有三種意圖，把它們混在一起，是很多設計問題的起點：

種類意思咖啡店的例子可以被拒絕嗎格式誰決定
命令（command）要求某個服務去做一件事PlaceOrder、ChargeCard可以（庫存不足、卡被拒）接收者
事件（event）宣布一件已經發生的事實OrderPlaced、OrderPaid不行，已經發生了發布者
查詢（query）問現在的狀態，不改變任何東西GetOrder只會查不到接收者

原本的付款 API 發的是五個命令：「集點服務，去加點」「報表服務，去記一筆」。命令通常只有一個接收者，發送者在等它的結果，所以接收者失敗，發送者也跟著失敗。事件不一樣：它說的是「訂單 A-1001 付款了」這個已經發生的事實。事實不能被拒絕，所以事件用過去式命名，OrderPaid 是「付款了」，不是「去付款」。

事件的送法叫發布／訂閱（pub/sub）。發布者把事件交給一個中間的系統，想知道這件事的服務事先向這個系統登記（訂閱），之後每個訂閱者各收到一份。發布者不知道、也不需要知道有誰在聽。這個中間的系統叫事件匯流排（event bus），常見的有 Kafka，或 SNS 搭配 SQS（SNS 負責把一則訊息複製給多個訂閱者，每個訂閱者用自己的 SQS 佇列接）。匯流排會把事件存起來，訂閱者暫時掛掉，事件就留在那裡等它回來。

這就是開場兩個問題的最小答案。報表掛了不影響付款，因為付款 API 不再等報表；加優惠券不用改訂單服務，因為發布者本來就不知道有誰在聽。

表格最後一欄「格式誰決定」，說的是耦合的方向。命令的格式由接收者決定：金流服務說要哪些欄位，呼叫它的人就得照給，金流改格式，所有呼叫者都要跟著改。事件的格式由發布者決定：訂單服務定義 OrderPaid 長什麼樣，訂閱者照著讀，訂單服務不用為了任何一個訂閱者改程式。

分辨命令和事件，不能只看它有沒有走匯流排。最常見的假事件是 SendReceiptEmail：它走匯流排送出，看起來是非同步的事件，但名字是命令，只有一個接收者，發布者其實在指揮別人做事。它換了傳送方式，耦合卻沒有減少：哪天收據改成簡訊，訂單服務還是要改。正確的是發 OrderPaid，由通知服務自己決定要寄信、發簡訊還是推播。

💡 實務上：先用程序內事件，真的跨服務再上訊息系統
多數團隊一開始是單體（第 15 課），同一個程式裡用 NestJS 的 EventEmitter 就能把「付款後要做的事」拆成各自的監聽器，先把事件的命名與邊界練好。等報表、外送整合變成獨立服務，或「程序重啟事件就沒了」已經不能接受（例如集點），才值得引進 outbox 加 Kafka、SQS+SNS 這類匯流排，它們要有人維運、要監控積壓。審設計時資深工程師常問一句：「明天多一個要知道這件事的功能，發布者要改程式嗎？」要改，就表示你發的其實是命令。

決定發 OrderPaid 之後，馬上碰到下一個問題：這個事件裡要放什麼？集點要知道金額，廚房要知道品項，外送平台要知道地址。全部塞進去，還是只放一個訂單 ID？

OrderPaid 裡要放多少資料？

這個問題沒有單一答案，因為「事件驅動」這個詞底下其實有好幾種不同的做法。Martin Fowler 在 2017 年的文章〈What do you mean by "Event-Driven"?〉把它們分開來看。跟這課有關的有三種，前兩種回答的正是「事件裡放多少」。

第一種是事件通知（event notification）：事件只告訴你「發生了什麼」，例如 { type: 'OrderPaid', orderId: 'A-1001' }，內容就這樣。集點服務收到後，要知道金額，就自己呼叫訂單服務的 API 回頭查。這種只帶 ID 的事件，這課叫薄事件。它的好處是契約小：訂單服務以後改了內部欄位，只要查詢 API 不變，訂閱者不受影響。代價是每個訂閱者都要多打一次 API，而且訂單服務掛了，大家都查不到，等於又把訂閱者綁回訂單服務身上。

第二種是事件攜帶狀態轉移（event-carried state transfer）：事件直接帶上訂閱者需要的資料，例如金額、品項。訂閱者不用回查，甚至可以在自己的資料庫存一份副本，訂單服務掛了也照樣能工作。這種事件這課叫胖事件。代價是事件裡的每個欄位都成了對所有訂閱者的承諾：哪天訂單服務把 total 改名成 amount，所有讀 total 的訂閱者一起壞掉，而發布者往往不知道有誰在讀。資料也是事件產生當下的快照，訂閱者拿到時可能已經過時。

第三種是事件溯源（event sourcing），它回答的是另一個問題：資料怎麼存。資料庫不存「目前狀態」，而是存所有發生過的事件；目前狀態等於從頭依序套用每一個事件的結果。銀行帳戶就是這樣：餘額是所有存款、提款紀錄加總出來的。它不是傳遞事件的方式，後面講到廚房畫面時會再回來看它。

薄事件胖事件事件溯源
訂閱者要回查嗎要，多一次呼叫；訂單服務掛了就查不到不用，發布者掛了也能工作（這是儲存方式，不是傳遞方式）
契約大小小：只有 ID 和類型大：每個欄位都是承諾，改名就打壞訂閱者事件是永久紀錄，格式要能一直讀
資料新鮮度回查時拿到最新的事件當下的快照，可能已經過時隨時能重算任何時間點的狀態
個資只在回查的地方每個訂閱者都拿到一份永久保存的個資很難刪除

表格最後一列常被忽略。如果 OrderPaid 帶了王小明的手機與地址，集點、報表、外送平台的每個訂閱者都拿到了一份個資：每一個都要保護好，顧客要求刪除個資時，每一個都要能跟著刪。發布者送出事件的那一刻，就失去了對這些資料的控制。

所以實務上多半取中間：帶上大多數訂閱者真正需要、不敏感的欄位（訂單 ID、門市、金額、狀態），個資和少數人才要的細節讓需要的人回查。咖啡店的 OrderPaid 就照這個原則帶訂單 ID、門市與金額，外送平台要地址，就用訂單 ID 回查。

內容決定了，但事件還缺一樣東西。下一節會看到，事件在路上會重複、會亂序，訂閱者需要一個辦法認出「這則我看過了」「這則比我手上的還舊」，而光靠 { type, orderId, total } 做不到。

消費者怎麼認出同一個事件、排出先後？

訂閱者要做兩個判斷：這個事件是不是已經處理過，以及它跟同一張訂單的其他事件誰先誰後。第一個判斷需要每個事件有一個唯一的身分；第二個判斷需要一個可靠的先後依據。這些描述「事件本身」而不是「訂單內容」的欄位，叫事件的中繼資料（metadata）。

事件一旦送出就不能改，它是已經發生的事實，所以中繼資料的格式要一開始就想好。不必自己發明：CloudEvents 是一份公開規格，定義事件的中繼資料該有哪些欄位，各家的 SDK 與雲端服務都看得懂。事件裡的 specversion 填 "1.0"（規格的維護單位與版本見課末）。它的欄位如下，前四個必填：

屬性必填意思
id是這個事件的 ID；發布者必須保證 source + id 對每個不同的事件都唯一
source是事件在哪裡發生的（URI），例如 /cafe/orders
specversion是規格版本，"1.0"
type是事件類型，常用反向網域：tw.cafe.order.paid
time否事情發生的時間，RFC 3339 格式
subject否事件關於 source 裡的哪個東西，例如訂單編號
datacontenttype否data 的格式，例如 application/json

第一個判斷靠 source 加 id。規格寫明：重送的事件可以帶相同的 id，消費者可以把 source 與 id 都相同的事件視為重複。這有一個前提：ID 要在事件產生時就決定好，例如寫進 第 12 課的 outbox 那一刻，之後每次重送都沿用。如果每次送出時才產生新的 ID，同一個 OrderPaid 送兩次就是兩個不同的 ID，消費者分不出它們是重複的。

第二個判斷，CloudEvents 沒有管，要自己加兩個欄位。先講第一個名詞：聚合（aggregate）是一組一起變化、需要維持一致的資料，例如一張訂單和它的明細。每張訂單就是一個聚合，用訂單 ID 識別。第二個是序號（seq）：這個聚合的第幾個事件，從 1 開始、每次加 1。訂單 A-1001 的 OrderPlaced 是 1、OrderPaid 是 2、OrderCompleted 是 3。同一張訂單的事件靠序號排先後；不同訂單之間不需要順序，A-1001 和 A-1002 誰先處理沒有人在意。第 12 課講順序時提到的「版本號」，就是這個序號。CloudEvents 允許加自訂欄位，叫擴充屬性（extension attribute），這兩個欄位就用它加上去。

下面是咖啡店的 OrderPaid 完整長相。執行後看兩處：data 裡只有訂單 ID、門市、金額，沒有個資；最後一行印出消費者去重用的鍵。

這個格式一旦有人在讀，就是公開的 API：加欄位沒問題，改名、刪欄位、改意思都會打壞你不知道的訂閱者。演進的規則跟 HTTP API 一樣，第 19 課詳談。

每個事件都有了 ID 和序號。下一節就站到消費者那一邊，看這兩個欄位怎麼擋住「集點加兩次」和「畫面倒退」。

集點為什麼會加兩次、畫面為什麼會倒退？

上一節說事件會重複、會亂序，這一節先講清楚為什麼。第 12 課學過，可靠的傳遞只能做到至少一次（at-least-once）：消費者處理完、還沒回報 ack（告訴匯流排「這則我做完了」）就當機，匯流排沒收到 ack，會把同一個事件再送一次。所以重複不是 bug，是可靠傳遞的代價。集點服務如果收到就加點，同一個 OrderPaid 來兩次，王小明就拿到兩倍點數。

順序也不保證，原因有三個：

  • 重試：OrderPaid 第一次處理失敗，在等退避的時候，後面的 OrderCompleted 先處理成功了。
  • partition：Kafka 把一類事件分成好幾條各自有序的佇列，叫 partition，partition 之間沒有順序（第 12 課）。同一張訂單的事件如果沒用訂單 ID 當 key，就可能分到不同 partition，各走各的。
  • outbox relay 重送：relay 送到一半當機，重啟後把還沒確認的事件再送一次，這時它可能排在更新的事件後面。

所以消費者要假設事件會重複、會亂序。先看一個沒有這個假設的消費者：收到什麼就套用什麼。範例模擬 OrderPaid 第一次送出時逾時、重試排到 OrderCompleted 之後才到，執行後看每一行「畫面顯示」的變化。

畫面先顯示「做好了」，接著被晚到的 OrderPaid 蓋回「已付款」。這張訂單會一直卡在已付款，因為不會再有新事件來修正它。要擋住重複與亂序，消費者需要三樣東西，正好用上上一節的 ID 和序號：

  1. 依事件 ID 去重：看過的 ID 直接跳過，回報「重複」，照樣 ack，不然匯流排會一直重送。正式環境用 第 12 課的 inbox 表記住看過的 ID，而且跟這次的點數更新寫在同一個交易裡，才不會出現「點數加了，ID 卻沒記到」的半套狀態。
  2. 依聚合的序號丟掉過時事件：記住每張訂單已經套用到第幾號。收到的序號 ≤ 它，表示這件事已經反映在狀態裡了，丟掉。上面的範例裡，OrderPaid（seq 2）晚到時，這張訂單已經套用到 3，所以它會被丟掉，畫面停在「做好了」。注意：ID 不同、序號舊的也要丟，例如上游重新產生了一次同樣的事件，去重擋不住它，序號擋得住。
  3. 還沒輪到的先暫存：收到 seq 5，但最後套用的是 3，表示 4 還在路上。先把 5 存起來；等 4 到了，套用 4，再接著套用暫存的 5。另一種做法是收到跳號時直接回查訂單服務拿最新狀態，代價是多一次呼叫。

你可能會想：每個事件都有 time，為什麼不直接照時間排？因為時間是不同機器的時鐘產生的，時鐘會有誤差。付款服務的時鐘快了 2 秒，OrderPaid 的時間就可能比 OrderCompleted 還晚，照時間排反而排錯。序號由擁有這張訂單的訂單服務在同一個交易裡遞增，只有一個來源、只往上加，不會有這個問題。練習 1 你會寫出包含這三樣東西的完整消費者。

暫存區要有上限與逾時：缺的那一號如果永遠不來（上游的 bug、被手動刪掉），暫存會一直長大，那張訂單也永遠卡住。等太久就告警、回查來源服務的最新狀態補上。
💡 實務上：寫消費者時，測試先把同一個事件送兩次
「集點加了兩次」「訂單卡在已付款」這類客訴幾乎都出在這裡，而且只在正式環境重試、重新部署時才出現，本機很難重現。code review 消費者時，資深會先問三件事：同一個事件送兩次結果一樣嗎？舊事件晚到會不會蓋掉新狀態？處理到一半當機，重來會不會多做一次副作用（寄兩封收據）？把「送兩次」「倒過來送」直接寫成測試案例，比上線後翻 log 便宜得多。

集點只要記一個數字，廚房要的卻是一整個畫面：每家門市還沒做完的訂單、各自的品項。消費者收到事件之後，要把它們組成什麼樣的資料，才撐得起這個畫面？

廚房出單畫面怎麼從事件組出來？投影與 CQRS

廚房出單畫面要的是「每家門市還沒做完的訂單、各自的品項」。最直接的做法是去查訂單服務的資料庫，但有兩個問題：這個查詢要 JOIN 訂單和明細、過濾狀態，在訂單資料庫上很貴，尖峰時會拖慢下單；而且廚房服務不該直接讀訂單服務的表（第 15 課：每張表只有一個擁有者），不然訂單服務一改欄位，廚房就壞掉。

做法是廚房服務訂閱訂單事件，在自己的資料庫維護一份專門給出單畫面用的資料：收到 OrderPlaced 就新增一列「待製作」，收到 OrderCompleted 就把它改成「已完成」。實際上廚房會在 OrderPlaced 先記下品項（OrderPaid 依上一節的原則不帶品項），等 OrderPaid 到了才列為待製作；如果 OrderPlaced 也不帶品項，就用訂單 ID 回查一次。這種從事件算出來、專門為某個查詢設計的資料，叫投影（projection），也叫讀取模型（read model）。上一節的三樣東西就是投影的更新規則。

讀與寫用不同的模型，就是 CQRS（Command Query Responsibility Segregation，命令查詢職責分離）。寫入端是訂單服務，顧規則：不能付兩次款、已取消的不能完成。讀取端是廚房的投影，只顧查詢快，表的形狀完全照畫面需要來設計。兩邊各自最佳化，不用互相妥協。

投影有兩個好性質。第一，它可以重建：投影的程式有 bug，或要新增一個查詢，把所有事件從頭重播一次，就得到新的投影。前提是事件有保存下來，例如 Kafka 設定了保存期限。第二，重建和重送都會讓同一個事件再來一次，所以投影的更新要冪等，結果必須一樣，上一節的去重和序號就是為此。

「重建投影」其實就是把事件依序套進一個函式，跟陣列的 reduce 一樣。範例把一串事件依序套進去，算出廚房的畫面資料（函數式程式把這個動作叫 fold，程式註解裡會看到這個字）。範例為了簡短只記狀態和金額、不記品項，執行後看印出來的是哪幾張訂單：

A-1001 已經 OrderCompleted，所以只剩 A-1002 在廚房的待辦裡。

投影的代價是最終一致（第 6 課）：資料最後會一致，但中間有一段落差。顧客剛付款，廚房和訂單列表的投影可能還沒收到事件。UI 要誠實地呈現這段落差：付款完成頁直接用付款 API 的回應顯示「已付款」，訂單列表若還沒更新就顯示「處理中」，不要讓顧客以為付款失敗而再付一次，那正是開場事故的翻版。

上一節提過的事件溯源，可以看成把這個做法推到底：連寫入端都不存目前狀態，只存事件，每次都從事件算出狀態。它換來完整的歷史，代價也大得多（快照、格式永遠不能壞、個資難刪，細節見課末）。只有真的需要完整歷史的領域，例如金流、點數帳本，才值得；一般的訂單用普通的表加 outbox 發事件就夠了，咖啡店的訂單服務就是這樣。

💡 實務上：先問「一條 SQL 加索引夠不夠」，再考慮投影
同一個資料庫裡的後台報表、訂單列表，通常加索引、建一個 view 或改讀讀副本（第 6 課）就解決了，不需要 CQRS。投影適合跨服務的查詢：廚房、外送整合讀不到訂單服務的表，只能靠事件在自己這邊組出需要的資料。導入前要跟 PM 和設計師講清楚「處理中」會出現在哪些畫面，讓設計稿先準備好這個狀態；也要先想好重建流程：重播全部事件要多久、重建期間畫面顯示什麼。

集點、廚房、收據、報表都在公司裡，可以訂閱我們的匯流排。開場要通知的五個地方只剩外送平台：它是別家公司的系統，碰不到我們的 Kafka。事件要怎麼送出公司？

怎麼把事件可靠地送到外送平台？webhook

外送平台想知道訂單什麼時候做好，好派外送員來拿。一種做法是讓它每 5 秒呼叫我們的 API 問一次，這叫輪詢，成本在第 17 課會算。更好的做法是反過來：外送平台事先在我們的後台登記一個網址，事件發生時由我們主動 POST 到那個網址。這就是 webhook，可以看成事件跨出公司邊界的形式。

webhook 有兩端。接收端的責任（驗簽、去重、快速回 2xx）在 NestJS 課第 22 課，簽章的原理在認證課第 17 課。這一課站在送出端：外送平台的伺服器會慢、會掛、會部署失敗、會改網址，我們的責任是在這些狀況下還送得到，而且不被任何一個客戶拖垮。這裡依照 Standard Webhooks 這份公開規格來做，它統一了 webhook 的標頭名稱、簽章方式與重送建議，讓接收端可以用同一套程式驗證不同廠商送來的 webhook。下面分兩個問題看：重送時要注意什麼，以及一個客戶出事時怎麼不拖累其他人。

重送時，ID、時間戳和簽章怎麼處理？

外送平台週末部署壞了，週一才修好。這段時間的事件要一直重送，直到對方收到為止。重送牽涉到三個標頭，各自的規則不同：

  • webhook-id 永遠不變：接收端靠它去重，它就是第 9 課的冪等鍵。每次重送換一個新 ID，接收端會把它當成新事件，外送平台就派了兩次外送員。用的就是事件產生時決定好的那個 ID。
  • body 不變：內容只序列化一次，每次都送一模一樣的字串。
  • webhook-timestamp 和簽章每次重算：原因要從簽章怎麼防攻擊講起。

簽章證明這則 webhook 真的是我們送的，而且內容沒被改過。但光有簽章還不夠：攻擊者可以把一則合法的 webhook 原封不動錄下來，過幾天再送一次，簽章照樣正確，這叫重放攻擊（replay attack）。所以時間戳也包在簽章裡，接收端只接受時間戳在一段容忍範圍內的請求，官方 standardwebhooks 套件預設是前後 5 分鐘，太舊的一律拒絕，不管簽章對不對。

這就是為什麼重送要重新簽章。如果第一次送出時算好時間戳和簽章，之後重送都沿用，那 5 分鐘之後的每一次重送，時間戳都太舊，全部被拒絕。規格也寫明每次重試都要更新 webhook-timestamp。規格給的範例重送排程是：立即、5 秒、5 分、30 分、2 小時、5 小時、10 小時、14 小時、20 小時、24 小時，共 10 次。下面的範例算出每一次距離第一次送出多久，以及「只簽一次」的話會不會被接收端拒絕：

只簽一次的話，第 3 次（第一次之後 5 分 5 秒）以後全部失敗。而真正需要重送的，往往就是這些「客戶修了好幾個小時」的情況。規則很單純：ID 不變、body 不變、時間戳與簽章每次重算。

知道怎麼重送之後，還要決定「該不該重送、等多久」，這取決於對方回了什麼。下表是送出端依回應決定下一步的規則，查表用，不用背，練習 2 會把它寫成程式：

表裡的「逾時 15～30 秒」帶出了下一個問題：一個慢客戶每次都占住連線 30 秒，其他客戶的 webhook 會不會跟著卡住？

一個客戶掛了，怎麼不拖垮其他客戶？

咖啡店不會只接一家外送平台，還可能有會員系統、加盟主的 POS。所有客戶的 webhook 如果排在同一條佇列，一個每次都逾時 30 秒的客戶，就會讓排在它後面的所有客戶一起等。解法是每個端點各自的佇列與並行上限，這就是第 11 課的隔艙：一個艙進水，其他艙不受影響。

整個送出流程的其他部分，也各有一個「不做會出什麼事」：

  • 從 outbox 開始：在訂單的交易裡寫一筆 outbox（第 12 課），交易提交後才送。交易提交前就送，萬一交易回滾，外送平台已經收到一張其實不存在的訂單。
  • 防 SSRF：SSRF（server-side request forgery）是讓我們的伺服器替攻擊者去連它自己連不到的位址。webhook 的網址是客戶填的，可能填 http://169.254.169.254/（雲端主機的中繼資料服務，查得到這台主機的憑證）或內網位址。送出前檢查網址解析後的 IP、不跟隨轉址，送出用的 worker 放在只能連外網的子網路（認證課第 22 課）。
  • 重播（replay）：客戶的系統壞了三天，修好後要補收這三天的事件，而這時重送次數早就用完了。提供「重送某段時間的事件」的 API 或後台按鈕，用原本的 webhook-id，讓客戶的去重照樣有效。
  • payload 要小：規格建議通常小於 20 KB；大的資料讓客戶用 ID 回查，順便避開胖事件的個資問題。

Node 端可以用 Standard Webhooks 官方的 standardwebhooks 套件簽章與驗證（版本見課末）；退避排程與佇列仍然要自己設計，練習 2、3 就是這一段。

💡 實務上：先當過接收端，自己做送出端前評估現成服務
工作中更常接的是別人的 webhook，例如 Stripe 的付款通知、GitHub 的 push 通知。看看它們的後台會發現同一套設計：每次送達的紀錄、對方回的狀態碼、手動重送按鈕。開放 webhook 給客戶時，這個「送達紀錄」頁幾乎是必備，客戶說「沒收到通知」時，客服和客戶自己就查得到，不用找工程師翻 log。送出端要做對的事很多（簽章、退避、隔艙、SSRF、重播），人手少時可以評估 Svix 這類託管的 webhook 送出服務；自己做的話，上線前找一個測試網址實際接收，故意回 500、410，確認重試與停用照規格走。

到這裡，付款後的五個通知都改成了事件。但這不代表所有服務之間的溝通都該改成事件，最後一節看界線在哪。

什麼時候不要用事件？上線後看什麼？

事件換來的是發布者不用等、不用知道誰在聽；付出的是最終一致，以及流程散在各個訂閱者裡、沒有一個地方看得到全貌。下面三種情況，這個代價不值得：

  • 呼叫端需要立刻知道結果：付款授權。顧客站在櫃台前，要馬上知道卡有沒有過，這是同步的命令。開場的付款 API 裡，扣款本身一直都是同步的，改成事件的只有付款成功之後的集點、收據、報表。
  • 流程太長、看不見：Fowler 指出事件通知的缺點是「整個流程不在任何一段程式碼裡」，要看執行中的系統才知道誰接著做什麼。事件串了五、六層，出錯時沒人說得清發生了什麼。需要明確流程、補償與狀態的，改用 orchestration（第 13 課）。
  • 只有一個接收者、而且在等結果：那就是命令，直接呼叫或放進工作佇列。包成事件就是第一節的假事件。

決定用事件後，系統的問題會從「請求失敗」變成「事件卡在某處」，錯誤不會再直接回到使用者的畫面上，所以要主動看這些指標：

  • 每個消費者的延遲（事件產生到投影更新的時間）與積壓：報表掛了 10 分鐘，這裡會看到積壓上升，而不是付款失敗。
  • 去重次數、因序號被丟棄的事件數、暫存中等待缺號的事件數與最久的等待時間。
  • 每個 webhook 端點的成功率、重試次數、被停用的端點數。
  • 事件也要帶 trace context（部署課第 23 課），不然非同步的那一段在追蹤裡會斷掉。

補充與查表

主線省略的出處、版本與延伸細節，查表用，不用背。

CloudEvents 的維護單位與版本

  • CloudEvents 由 CNCF（雲原生運算基金會，也維護 Kubernetes）維護。最新的發布版本是 v1.0.2，事件裡的 specversion 填 "1.0"。
  • 擴充屬性的名稱只能用小寫英數字，所以範例寫成 aggregateid，不是 aggregateId。

事件溯源的代價

  • 每次讀狀態都要重播事件，事件一多就慢，所以要定期存一份「到第 N 個事件為止的狀態」當快照（snapshot），之後只重播 N 之後的。
  • 事件是永久紀錄，格式永遠不能壞，舊格式的事件也要一直讀得懂。
  • 永久保存的事件裡有個資時，刪除很麻煩。
  • 換來的是完整的歷史與稽核：每一點集點都查得到來源。

Standard Webhooks 的套件版本

  • Node 端的官方套件是 standardwebhooks 1.1.1，簽章與驗證都用它；時間容忍預設前後 5 分鐘。

練習

練習 1：完成 OrderProjection。apply(e) 依序檢查：

  • 看過的 id → 'duplicate'。
  • seq ≤ 這張訂單已套用的最後序號 → 'stale'（還沒套用過任何事件時，最後序號是 0）。
  • seq 等於最後序號 + 1 → 套用，接著把暫存中接得上的事件依序套用，回傳 'applied'。
  • seq 更大 → 暫存，回傳 'buffered'。

套用的規則：OrderPlaced 建立 { status: 'pending', total, updatedAt: at }；OrderPaid、OrderCompleted、OrderCancelled 把狀態改成 'paid'、'done'、'cancelled' 並更新 updatedAt。get(orderId) 回傳投影，沒有就是 undefined。不同訂單的序號各自獨立；順序只能看 seq，不能看 at。

練習 2：寫 webhook 的重送決策 nextAttempt(state, retrySchedule, random)。state.attempt 是已經失敗的次數（從 1 開始），retrySchedule[k] 是第 k 次失敗後要等的毫秒數（retrySchedule[0] 是第一次送出前的 0）。規則依序：

  • lastStatus 是 410 → { action: 'disable-endpoint' }。
  • attempt ≥ retrySchedule.length → { action: 'give-up' }。
  • 否則 { action: 'retry', delayMs }，delayMs = max(Math.round(retrySchedule[attempt] × (0.9 + random() × 0.2)), retryAfterMs ?? 0)：±10% 的 jitter，Retry-After 比較長就聽它的。

lastStatus 為 null 代表逾時或連線失敗。除了 410，其他狀態碼（包括 404、429、500）都重試。不能用 Math.random。

練習 3：寫 deliverWebhook(endpoint, event, deps)，把一個事件送到客戶的端點，失敗就依練習 2 的 nextAttempt 重送（起始程式已貼好參考解，也貼好認證課第 17 課的 signWebhook）。要求：

  • body 只序列化一次：JSON.stringify(event.payload)，每次都送一模一樣的字串。
  • 每次嘗試都取當下的 deps.nowSeconds() 當時間戳，重新呼叫 deps.sign(endpoint.secret, { id, timestamp, payload: body })。
  • 標頭：webhook-id（永遠是 event.id）、webhook-timestamp（字串）、webhook-signature、content-type: application/json。
  • 回應 2xx 才算成功，回傳 { result: 'delivered', attempts }。deps.post 丟錯（逾時、連線失敗）時當作 lastStatus: null、retryAfterMs: null。
  • 失敗時呼叫 nextAttempt：retry → await deps.sleep(delayMs) 再送；disable-endpoint → 'disabled'；give-up → 'gave-up'。attempts 是實際送出的次數。

練習 4：OrderPaid 事件要不要帶顧客的姓名、手機與完整明細，讓每個訂閱者都不用回查？

✓ 胖事件的每個欄位都是對所有訂閱者的承諾，改名就打壞別人；帶了手機和姓名，每個訂閱者（集點、報表、外送平台）都持有個資，都要保護、都要能刪除。(a) 只看到不用回查的好處。(b) 太極端：純薄事件讓每個訂閱者都回查，訂單服務掛了大家都不能工作，事件也失去「發布者掛了照樣能處理」的好處。

練習 5：廚房的消費者收到訂單 A-1001 的 seq 5，但這張訂單最後套用的是 seq 3。直接套用 seq 5 會怎樣？

✓ 重試、不同 partition、relay 重送都會讓事件亂序，seq 4 晚到時直接套用會覆蓋掉 seq 5 的結果。(a) 是最常見的錯誤假設：送達順序不等於產生順序。(c) 時間來自不同機器的時鐘，有誤差，不能決定順序；序號由擁有訂單的服務在同一個交易裡遞增，才可靠。

練習 6：送 webhook 時，重送沿用第一次算好的 webhook-timestamp 與簽章，2 小時後的重送會怎樣？

✓ 時間戳在簽章範圍內，防的就是重放攻擊：太舊的時間戳一律拒絕，不管簽章對不對（認證課第 17 課）。規格要求每次重試都更新時間戳。(b) 只檢查了簽章，忽略了時間容忍。(c) 重複處理是「每次換新 webhook-id」造成的問題，不是這一題。

練習 7：有人提議把付款授權改成「訂單服務發一個 PaymentRequested 事件，金流服務處理完再發 PaymentAuthorized」，讓兩個服務解耦。適合嗎？

✓ PaymentRequested 名字就說明它是命令，只有一個接收者、發送者在等結果。改成事件只是把同步呼叫藏起來，還多了「結果要多久才來、沒來怎麼辦」的問題。(a) 事件不是一律比較好，它的代價是最終一致與看不見的流程。(b) 訂閱者多寡不改變「顧客要立刻知道結果」這個需求。

常見錯誤

  • 把命令包裝成事件（SendEmail）：只有一個接收者、發布者在指揮別人，耦合沒有減少。發布已經發生的事實（OrderPaid），讓訂閱者自己決定做什麼。
  • 胖事件帶個資：每個訂閱者都拿到一份，都要保護、都要能刪除。只帶大多數人需要、不敏感的欄位，其他回查。
  • 事件沒有唯一 ID，或送出時才產生 ID：消費者無法去重。ID 在事件產生時就決定，重送沿用。
  • 假設事件依序到達，或用時間排序：重試、分區都會亂序，時鐘有誤差。用每個聚合的序號，舊的丟掉、還沒輪到的暫存或回查。
  • 交易提交前就發事件：交易回滾了事件卻已經送出。用 outbox（第 12 課），提交後才送。
  • webhook 重送不重新簽章，或每次換新的 webhook-id：前者 5 分鐘後的重送全被拒絕，後者讓接收端無法去重。ID 不變、時間戳與簽章每次重算。
  • 所有客戶的 webhook 共用一條佇列：一個每次都逾時的客戶拖住所有人。每個端點自己的佇列與並行上限。
  • 跟隨轉址、送到內網位址：SSRF。不跟隨轉址，檢查解析後的 IP，送出的 worker 只能連外網（認證課第 22 課）。
  • 沒有重播工具：客戶的系統壞了三天，修好後只能請工程師手動補資料。提供依時間範圍重送的 API，沿用原本的 webhook-id。

小結

  • 付款後的通知用同步命令串起來，任何一個下游掛了付款就失敗；改成發布 OrderPaid，下游自己訂閱，報表掛了不影響付款、加功能不改訂單服務。
  • 命令要求別人做事、可以被拒絕、格式由接收者決定；事件宣布已經發生的事實、用過去式命名、格式由發布者決定。偽裝成事件的命令不會減少耦合。
  • 薄事件契約小但要回查；胖事件不用回查但契約大、會散播個資；事件溯源用事件當儲存，只在需要完整歷史時才值得。
  • 事件要有唯一 ID 與來源（CloudEvents 1.0：id、source、specversion、type），再加上聚合 ID 與序號。
  • 消費者要假設重複與亂序：依 ID 去重、依序號丟掉舊的、暫存還沒輪到的；投影可以重播重建，UI 要呈現最終一致的落差。
  • 送 webhook：ID 不變、每次重新簽章、只有 2xx 算成功、410 停用、尊重 Retry-After、跨多天退避加 jitter、每個端點各自的佇列、防 SSRF、提供重播。
  • 需要立刻知道結果的（付款授權）用同步命令；流程長到看不見時改用 orchestration。上線後看消費延遲、去重與丟棄次數、每個端點的成功率。
