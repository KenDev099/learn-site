階段 1：基本功：需求、估算與效能指標 · 第 1 課

系統設計在想什麼：需求、限制與取捨

你在 NestJS 課做出了一個咖啡店訂單 API：一台伺服器、一個 PostgreSQL，功能都能動。現在老闆說，下個月要推出線上點餐 App，全台 200 家門市一起上線，週年慶還要辦買一送一。他問你兩件事：「現在這套撐得住嗎？不夠的話要加什麼？」

這課從頭到尾都在回答這兩個問題。回答這類問題的工作叫系統設計（system design）：決定系統由哪些元件組成、資料怎麼在它們之間流動、某個元件壞了時怎麼辦，並把每個選擇的理由寫清楚。它沒有標準答案，只有「在這組需求和限制下，哪個選擇比較好」。學完這課，你能把老闆那句話拆成可以算的問題，算出一筆下單要花多久、整個系統每秒撐得住幾個請求、哪個元件會先垮，最後寫出一段有數字、有理由、也說得出「這次不做什麼」的回答。

這課的路線：
  1. 「撐得住嗎」為什麼沒辦法直接回答？先把情境換成數字，再把「撐住」寫成可量測的目標，並找出限制（開場問題的最小答案在第一節）。
  2. 有了數字，為什麼還不能馬上畫架構圖？設計的七個步驟，以及老闆的問題落在哪一步。
  3. 一筆下單要花多久？延遲依序相加、平行取最大，優化要打在關鍵路徑上。
  4. 整個系統每秒撐幾個請求？放大係數與請求組合，算出瓶頸是資料庫而不是 API。
  5. 找到瓶頸之後加什麼、怎麼講給老闆聽？咖啡店的成長路線（也是這門課的地圖），以及取捨與 YAGNI。
這課會用到：
  • NestJS 課第 27 課的期末專題：一台伺服器加一個 PostgreSQL 的單體訂單 API，這門課從它開始長大。
  • TypeScript 課第 9 課的依序與平行：連續 await 是一個做完才做下一個，Promise.all 是同時開始、全部完成才往下走。

「撐得住嗎」為什麼沒辦法直接回答？先把情境換成數字

老闆的問題聽起來是是非題，但你沒辦法回答「撐得住」或「撐不住」，因為題目少了兩樣東西：會有多少人、做多少事，以及「撐住」的標準是什麼。缺了前者，你不知道系統要扛多大的量；缺了後者，你不知道扛到什麼程度才算及格。系統設計的第一件事，就是把這些缺的東西問出來。

這一節先處理第一樣。你去問老闆和 PM：有多少門市、多少會員、大家多常用、什麼時候最忙、會不會辦活動、要跟哪些外部系統串接。問完整理成下面這張情境卡。這門課每一課都用同一組數字，之後的估算、瓶頸、設計都從這裡出發：

類別數字
門市全台 200 家（storeId 1～200，1 號是台北旗艦店）
會員100 萬人，App 每日活躍使用者（DAU）20 萬人
瀏覽每位活躍使用者每天看菜單 5 次
訂單每人每天平均 0.3 筆，每天 6 萬筆；每筆（含明細）約 1 KB，保存 5 年
尖峰早上 7:30～9:30 這 2 小時佔全天訂單 40%
活動週年慶買一送一當天，尖峰是平常的 20 倍
外部依賴金流閘道（付款）、簡訊／推播服務、外送平台

表裡有兩個地方要多說一句。DAU 是 daily active users 的縮寫，指一天之內至少打開過一次 App 的人數；100 萬會員裡每天真的會用的只有 20 萬，流量要用這個數字算。外部依賴是別人的系統：金流、簡訊、外送平台變慢或掛掉時，我們的下單也會跟著受影響，所以它們也要列進來。外送平台會用 webhook 通知我們訂單狀態，也就是事件發生時由對方主動呼叫我們的 HTTP 端點，第 16 課細講。

有了這張卡，「撐得住嗎」就能改寫成兩個能算的問題：尖峰時每秒會有幾個請求進來，以及系統裡每個元件（API 伺服器、資料庫、快取）每秒最多能處理幾個。把兩者一比，最先處理不完的那個元件就是會先垮的地方，這個元件叫瓶頸（bottleneck）。這就是開場問題的最小答案：算出每個元件的上限，最先到上限的那個先垮；快取、微服務這些東西，只有在能拉高那個上限時才值得加。「會進來多少」留給下一課算，這課後半算「撐得住多少」，並實際找出咖啡店的瓶頸。

不過就算算出系統每秒撐得住 3,000 個請求，還有一個問題沒解決：每個請求都成功了，但每筆下單要等 5 秒，這樣算撐住嗎？這就是老闆的話裡缺的第二樣東西，「撐住」的標準。

「撐住」的標準是什麼？功能需求、非功能需求與限制

要定出「撐住」的標準，先分清楚需求有兩種。

功能需求（functional requirement）是系統要做什麼。以咖啡店來說：顧客可以預先點餐、到店取餐；門市可以看到待做的訂單；付款成功後集點。功能需求回答的是「有沒有這個功能」，NestJS 課做的就是這一類。

但功能全部做出來，系統還是可能在尖峰時慢到沒人想用，或者偶爾重複扣款。這些「做得多好」的要求叫非功能需求（non-functional requirement），也稱為品質屬性。老闆問的「撐不撐得住」，問的就是非功能需求。常見的有這幾種，每一種在咖啡店都找得到對應的擔心：

  • 延遲（latency）：一個請求從送出到收到回應花的時間。顧客在櫃檯前按下單，等越久越可能放棄。
  • 吞吐量（throughput）：單位時間內能處理多少請求。業界常用 QPS 或 RPS 當單位，分別是每秒查詢數（queries per second）和每秒請求數（requests per second）。早上 8 點全台門市一起湧入，比的就是吞吐量。
  • 可用性（availability）：系統能正常服務的時間佔多少比例，例如 99.9%。App 掛掉的那幾分鐘，所有門市都收不到線上訂單（第 4 課詳談）。
  • 一致性（consistency）：不同地方看到的資料是否相同、多久之後會相同。顧客剛下單，門市平板上要多快看得到（第 6 課）。
  • 耐久性（durability）：已經告訴使用者「成功了」的資料不會遺失。顧客看到「付款成功」，訂單就不能因為機器重開而消失。
  • 擴展性（scalability）：負載變大時，加資源就能撐住。週年慶流量變 20 倍時，能不能靠多開機器解決，還是要改架構。
  • 還有成本、安全，以及可維運性：出事時查得到原因、要改的時候改得動。

問題在於，老闆和 PM 說出口的非功能需求幾乎都是形容詞：「要快」「不能掛」。形容詞沒辦法驗證，上線後也沒辦法判斷做到了沒有。所以要把它們改寫成可量測的目標，也就是有指標、有數字、有條件，任何人量完都會得到同一個結論。

延遲的目標最常用 p99 來寫，先講清楚它是什麼。把一段時間內所有請求的回應時間從快排到慢，排在第 99% 位置的那個值就是 p99：100 個請求裡，有 99 個不超過它，只有最慢的 1 個比它慢。為什麼不用平均值？因為平均會把卡住的人藏起來。假設大部分請求 50ms、少數卡了 3 秒，平均可能只有 100ms，看起來很好，但那些卡 3 秒的顧客已經在櫃檯前不耐煩了。p99 直接告訴你「最慢的那 1% 有多慢」。第 3 課會完整講百分位數。

另外，目標一定要寫在什麼負載下。半夜沒人用時 p99 很漂亮沒有意義，老闆擔心的是早上 8 點和週年慶，所以要量尖峰時段。照這個原則，把老闆和 PM 的四句話改寫：

模糊的說法可量測的目標
下單要快尖峰時段，下單 API 的 p99 小於 300ms
不能掛以 30 天為單位，可用性 99.9%（每月最多約 43 分鐘無法服務）
不能錯帳同一張訂單最多扣款 1 次
集點晚一點沒關係付款成功後 60 秒內入帳

每一列都補上了原本沒說的東西。「下單要快」補上了百分位數、負載條件和毫秒數。「不能掛」補上了統計區間：同樣是 99.9%，以 30 天算每月最多約 43 分鐘停機，以一年算則可以集中在某一天停 8 個多小時，對門市的影響完全不同（換算方法見課末「補充與查表」）。「不能錯帳」從一個願望變成可以寫測試的條件。最後一列反過來，它說明了哪裡可以放鬆：集點不用即時，這讓後面的設計多了選項，例如把集點丟給背景慢慢做。

需求寫清楚之後，還有第三種輸入：限制（constraint），也就是不能改變的條件。例如只有 2 個工程師、3 個月後要上線、既有系統是 NestJS＋PostgreSQL、每月預算多少。限制和需求一樣決定答案：同一組需求，3 個人做 3 個月和 30 個人做 1 年，會設計出完全不同的系統。限制的作用常常是刪掉選項，例如團隊沒有人維運過某種資料庫，就算它在紙面上最適合，3 個月內導入也是很大的風險。

💡 實務上：接到需求先把形容詞換成數字
PM 開需求單寫「結帳要快、不能掛」時，先回問：哪幾個流程最重要？尖峰大概多少人同時用？出錯的後果是什麼（重新整理就好，還是會重複扣款）？哪些這次不做？把答案寫成驗收條件，上線後才有辦法判斷做到沒有。限制常常沒人講，例如上線日期、團隊只熟 NestJS、不能多開機器，要主動問出來，因為它們會直接刪掉很多選項。回到老闆的問題，這一步做完，「撐得住嗎」才變成「尖峰時下單 p99 小於 300ms、每月停機不超過 43 分鐘，做不做得到」。

數字、目標、限制都有了。這時最常見的衝動是打開白板，開始畫架構圖。

有了數字，可以開始畫架構圖了嗎？設計的七個步驟

還不行。接到「設計一個點餐系統」，很多人第一個動作是畫一張架構圖，上面放負載平衡器、Redis、Kafka。負載平衡器負責把請求分給多台伺服器，Redis 是放在記憶體裡的快取，Kafka 是訊息佇列，後面的課會逐一講到。這裡的問題不在元件本身，而在順序：還沒算過流量和資料量，就沒辦法判斷這張圖畫得對不對。Redis 要放什麼？能讓資料庫少被打幾次？資料庫真的會不夠用嗎？沒有估算，這些都只能憑感覺回答。

所以系統設計有一個固定的順序，每一步都用上一步的結論當輸入：

步驟要回答的問題
① 釐清需求誰在用？做什麼？多快、多穩？錯了會怎樣？有哪些限制？哪些不做？
② 估算每秒多少請求？尖峰多少？資料一年長多少？讀多還是寫多？
③ API 與資料有哪些端點？資料表長什麼樣？最常見的查詢是什麼？
④ 高階架構需要哪些元件（API、資料庫、快取、佇列）？請求怎麼流過它們？
⑤ 深入瓶頸哪個元件最先撐不住？某個依賴變慢或掛掉時會發生什麼？
⑥ 取捨與風險這樣選放棄了什麼？哪些假設一旦失效，答案就要改？
⑦ 寫成文件半年後的同事看得懂當初為什麼這樣選嗎？

前兩節做的就是第①步。第②步估算是下一課的主題，第③④步會在後面設計各個元件時反覆出現，第⑦步在第 18 課。實務上不會一次走完：估算之後發現某個需求做不到，例如預算撐不起 99.99% 的可用性，就回到①跟 PM 談，把目標調成做得到的。

老闆的問題「哪裡會先垮」落在第⑤步。「先垮」有兩種意思，要分開看。第一種是單一請求太慢：一筆下單的每個步驟加起來超過 300ms，目標就沒達到。第二種是整體容量不夠：每筆都很快，但每秒湧入的請求太多，某個元件處理不完。這課接下來先看第一種，因為要先知道一個請求內部發生什麼事，才能算一堆請求一起來時的情況。

一筆下單要花多久？依序相加、平行取最大

回到「尖峰時下單 p99 小於 300ms」這個目標。要知道做不做得到、慢了該改哪裡，得先知道一筆下單的時間花在哪。下單 API 收到請求後要做四件事：先驗證 token，花 5ms；接著查菜單 20ms、查會員 30ms；最後寫訂單 15ms。

這四件事不是都得排隊。驗證 token 一定要先做，沒通過就不用往下了；寫訂單一定要最後做，因為它需要菜單的價格和會員的資料。但查菜單和查會員彼此不需要對方的結果，所以可以同時開始。這種「做完一個才做下一個」和「同時開始」的差別，決定了總時間怎麼算，規則只有兩條：

  • 依序（一個做完才做下一個）：延遲相加。
  • 平行（同時開始，全部完成才往下走）：延遲取最大，因為要等最慢的那個做完。

關鍵路徑重要，是因為它決定了優化有沒有用。用 TypeScript 課第 9 課的寫法實際量一次，用 setTimeout 假裝每個查詢要花的時間。執行後比較三行輸出的毫秒數：

全部依序約 70ms，中間平行約 50ms，光是把兩個互不相關的查詢改成同時做，就省了 20ms。第三次把查菜單從 20ms 壓到 2ms，快了 10 倍，總時間卻還是約 50ms，因為查菜單不在關鍵路徑上，它變快只是讓它更早開始等查會員。結論是：優化不在關鍵路徑上的步驟，總延遲不會變。真正有用的是讓查會員變快，或讓寫訂單不必等它。

這也說明了為什麼優化前要先畫出這張時間軸。在正式環境裡，一個請求可能經過好幾個服務和資料庫，沒辦法靠讀程式碼畫出來。這時用的工具叫分散式追蹤（distributed tracing）：系統替每個請求記下它在每個元件花了多少時間、誰先誰後，再畫成跟上面一樣的時間軸。看追蹤，其實就是在找關鍵路徑。

💡 實務上：「下單好慢」先看追蹤，不要先猜
客服回報 App 下單轉很久，第一步是打開監控工具的分散式追蹤，找一筆慢的請求，看哪一段最長、是不是在關鍵路徑上，而不是憑感覺去改查菜單。程式碼裡最常見的浪費，是一連串互不相關的 await 寫成依序執行，改成 Promise.all 就能省下來。但只有彼此不依賴的步驟才能平行。平行還有一個代價：同一時間占用的資料庫連線變多。程式通常透過連線池存取資料庫，連線池是預先開好、數量固定的一組連線，查詢時借一條、用完歸還（Node 課第 20 課）；池子設得小時，平行反而讓請求排隊等連線。

現在一筆下單 50ms，離 300ms 的目標還很遠。但這只回答了「一個請求」的情況。早上 8 點全台門市一起下單，每秒進來幾千個請求，每一個都很快，系統就撐得住嗎？

整個系統每秒撐幾個請求？放大係數與瓶頸

不一定，因為每個元件每秒能處理的量有上限，這個上限叫容量（capacity），通常要用壓力測試量出來。請求一多，最先超過容量的元件就開始排隊，延遲跟著暴增，這就是第一節說的瓶頸。這一節把它實際算出來。

要算的系統是哪一套？開場那套是一台伺服器加一個 PostgreSQL，而且 API 和資料庫擠在同一台機器上互搶 CPU 和記憶體，機器一壞就全掛（後面成長路線表的第一列）。200 家門市一起上線，這套顯然不夠，所以團隊在上線前已經先做了最常見的兩步：把 API 開到 3 台，並把菜單放進 Redis 快取，減少資料庫的讀取。這兩件事怎麼做是第 4、5 課的內容。接下來要問的是：做了這兩步，這套上線版本夠不夠？從這裡開始，老闆問的「現在這套」指的就是它。先列出上線時每個元件的容量：

元件容量
API 伺服器3 台，每台 1,000 req/s，共 3,000 req/s
Redis（快取）50,000 ops/s（每秒 5 萬次讀寫操作）
PostgreSQL2,000 查詢/s

直覺會說：API 的數字最小，所以系統上限是 3,000 req/s。這個直覺漏了一件事：表上的單位不一樣。API 的容量以「請求」計算，資料庫的容量以「查詢」計算，而一個請求進來，不一定只查一次資料庫。

一個外部請求會對某個元件造成幾次內部呼叫，這個倍數叫放大係數（amplification）。看菜單的請求大多直接從 Redis 拿到菜單，只有快取沒命中時才查資料庫，平均下來每次只打資料庫 0.1 次。下單就不同了：查商品、查會員、寫訂單、寫明細、扣庫存……一共打 8 次。同一個「1 個請求」，對資料庫的負擔差了 80 倍。Redis 也一樣要算：這裡假設看菜單每次讀 1 次快取；下單時先從快取讀 1 次菜單確認價格，再做 1 次限流計數（記錄這個使用者剛剛下了幾單，第 10 課），所以是 2 次。

所以光知道放大係數還不夠，還要知道兩種請求各佔多少。流量裡各種請求的比例叫請求組合（request mix）。咖啡店平常是 90% 看菜單、10% 下單，把放大係數依比例加權，就是平均每個請求打某個元件幾次。再用元件的容量除以它，就得到這個元件能撐的請求數：

平均每個請求打資料庫：0.9 × 0.1 ＋ 0.1 × 8 ＝ 0.09 ＋ 0.8 ＝ 0.89 次
平均每個請求打 Redis： 0.9 × 1   ＋ 0.1 × 2 ＝ 1.1 次（看菜單 1 次、下單 2 次）
平均每個請求打 API：   1 次

資料庫能撐的請求數 ＝ 2,000 ÷ 0.89 ≈ 2,247 req/s
API 能撐的請求數   ＝ 3,000 ÷ 1    ＝ 3,000 req/s
Redis 能撐的請求數 ＝ 50,000 ÷ 1.1 ≈ 45,454 req/s

三個數字裡最小的是 2,247，所以瓶頸是資料庫，不是 API。瓶頸決定整個系統的上限：流量超過每秒約 2,247 個請求時，就算 API 和 Redis 還很閒，資料庫也已經處理不完了。老闆的第一個問題（撐得住嗎）回答了一半：「撐得住多少」算出來了，在這組假設下系統每秒大約撐 2,200 個請求，先垮的是資料庫；「會進來多少」，也就是尖峰時每秒進來幾個請求，下一課算出來後再拿來比。

換個方向看同一件事：在某個流量下，每個元件的容量被用掉幾成。執行後看資料庫和 API 哪一個先超過 100%：

到 2,500 req/s 時資料庫已經超過 100%，API 才 83%。這時候加 API 機器，上限一點都不會變，因為擋住的是資料庫。有用的做法都是讓資料庫少被打：提高快取命中率，讓看菜單更少落到資料庫；減少每張訂單的查詢次數，把 8 次壓低；或者加讀副本（read replica），也就是複製一份資料庫專門處理讀取，分攤主資料庫的讀取壓力（第 6 課）。

請求組合會變。週年慶時下單比例升高，每個請求平均打資料庫的次數變多，上限跟著下降。估算時要用尖峰時段的組合，不是全天平均。
💡 實務上：「要不要加機器？」先問瓶頸在哪
週年慶前主管問要不要多開幾台 API，資深工程師會先看各元件的使用率：資料庫的 CPU、連線數、慢查詢，通常比 API 機器早滿。接著看下單這條路徑每次打幾次資料庫，能不能少打幾次。比較穩的做法是活動前用尖峰的請求組合做一次壓力測試，看哪個元件先到上限，再決定把錢花在哪。直接加 API 機器很容易花了錢，上限卻沒變。

瓶頸找到了，是資料庫。老闆的第二個問題接著來：那要加什麼？

瓶頸找到了，接下來加什麼？咖啡店的成長路線

要加什麼，取決於瓶頸在哪，而每加一樣東西，解決一個瓶頸的同時也會帶來新問題。系統不是一開始就長成最終的樣子，而是一步一步長大的。下表是咖啡店可能走的路線，也是這門課的地圖。表裡有兩個還沒介紹的名詞：佇列與背景工作是把不急的工作先排進佇列，由另一支背景程式慢慢處理，請求本身不用等它做完；分片（sharding）是把資料拆到多台資料庫，每台只存一部分；無狀態（stateless）是指伺服器不把使用者資料（例如 session）存在自己的記憶體裡，這樣請求不管被分到哪一台，處理結果都一樣（部署課第 13 課）。

階段解決什麼帶來的新問題對應的課
一台機器跑 API＋資料庫最快上線兩者搶 CPU 和記憶體，機器壞了全掛NestJS 課期末專題
資料庫分到自己的機器資源不再互搶多了網路往返第 2、3 課估算與量測
多台 API＋負載平衡API 容量、單台故障服務必須無狀態（部署課第 13 課），資料庫變成瓶頸第 4 課
快取資料庫的讀取壓力資料過時、快取失效瞬間壓垮資料庫第 5 課
讀副本更多讀取複寫延遲：剛下的單查不到第 6 課
佇列與背景工作慢的工作（簡訊、集點）不擋下單重複處理、順序、訊息遺失第 12 課
分片單一資料庫寫不下跨分片查詢、重新分配資料第 7 課

上一節的咖啡店已經走到「多台 API＋快取」，而表上那一列預告的新問題「資料庫變成瓶頸」，正是剛才算出來的結果。往下看，能減輕資料庫負擔的有三條路：把快取用得更好、加讀副本、分片。前兩條處理的是讀取，分片處理的是寫入量大到一台資料庫寫不下。咖啡店每天 6 萬筆訂單，寫入離這個程度還很遠，所以分片暫時不在選項裡。每條路的「帶來的新問題」那一欄也要一起看：加讀副本，就要處理顧客剛下單卻查不到的情況。

表上沒列的是另一大類問題：元件會失敗。中間的第 8～14 課處理這些：逾時、重試、冪等、限流、斷路器、saga、分散式鎖。最後幾課練資深工程師每天在做的事：寫設計文件、不停機地演進、code review、處理線上事故。

表的每一列都同時有「解決什麼」和「帶來的新問題」。所以「要加什麼」從來不是只看好處的問題，回答老闆時，你得把兩邊都講出來。

怎麼把答案講給老闆？取捨與 YAGNI

「得到某個好處，同時付出某個代價」叫取捨（trade-off）。加快取換來速度，代價是資料可能過時；拆成微服務讓團隊各自部署，代價是多了網路呼叫和分散式的失敗。系統設計就是在限制下做取捨，並把理由寫下來。沒有「最好」的架構，只有「在這組需求下比較好」的。資深工程師講設計時，會一起講出這三件事：

  • 選了什麼、放棄了什麼：「集點走佇列非同步處理，下單不用等它；代價是付款後最多 60 秒才看到點數。」這正是第二節那個「可以放鬆」的需求換來的選項。
  • 什麼數字改變，答案就要改：「每天 6 萬筆、5 年約 110 GB，單一 PostgreSQL 足夠；如果訂單量成長 50 倍，要重新評估分片。」
  • 這個決定能不能反悔：換掉快取函式庫很容易，選了錯的資料分片鍵很難改。不可逆的決定要花更多時間（第 18 課）。

第二件事裡藏著一個常見的爭議：既然知道之後可能要分片，為什麼不現在就做？這裡用到一個原則叫 YAGNI，是 You Aren't Gonna Need It 的縮寫，意思是不要為了還沒出現的需求先付出複雜度。微服務、分片、多區域部署都有代價，而且是現在就要付：更多元件要維運、更多失敗模式要處理、功能交付變慢。對只有 2 個工程師、3 個月後要上線的團隊來說，這些代價可能直接讓專案延期。合理的做法是為看得到的成長（例如 3 倍）設計，並知道到了 30 倍時下一步怎麼走，而不是現在就付 100 倍規模的複雜度。

另一頭也是錯：完全不想未來。把「到什麼數字要做什麼」寫進文件，等指標接近時就有準備，不會在週年慶當天才發現資料庫撐不住。

把這課的結論組起來，你給老闆的回答大概是這樣：「目前的架構在平常的請求組合下，每秒大約撐 2,200 個請求，先到上限的是資料庫，不是 API，所以加 API 機器沒有用。建議先減少下單時打資料庫的次數、提高菜單的快取命中率，活動前用尖峰的請求組合做一次壓力測試。分片和微服務這次不做：5 年的訂單約 110 GB，一台 PostgreSQL 放得下；訂單量成長到現在的幾十倍時再評估。週年慶尖峰每秒會有多少請求，算出來之後再對照這個上限。」每一句都有數字、有理由，也說了不做什麼。

💡 實務上：在 PR 和設計討論裡把取捨講出來
你提議「加 Redis」或「改用佇列」時，同事和主管最常問的是：解決了什麼問題、多了什麼要維運、壞掉時會怎樣。PR 描述或討論時直接回答這三件事，再加一句「到什麼數字要重新評估」，審查會快很多。反過來，看到別人想導入新元件時，也可以問：現在的數字真的需要它嗎？只是「大家都在用」不算理由。

補充與查表

99.9% 每月約 43 分鐘怎麼算

30 天 × 24 小時 × 60 分鐘 ＝ 43,200 分鐘，允許無法服務的比例是 1 − 99.9% ＝ 0.1%，43,200 × 0.001 ≈ 43 分鐘。同樣的 99.9% 改用一年算，365 × 24 × 60 × 0.001 ≈ 526 分鐘，約 8.8 小時，可以全部集中在同一天，所以可用性目標一定要寫統計區間。

放大係數和 N+1 是同一類問題

PostgreSQL 課第 25 課的 N+1，是一個請求先查出一份列表，再對列表裡每一筆各查一次，結果一個請求變成很多次查詢。從系統設計的角度看，它就是放大係數失控：程式碼裡一個不起眼的迴圈，可能讓下單的放大係數從 8 變成 20，資料庫能撐的請求數跟著掉一半以上。

練習

練習 1～3 用同一個型別描述一條請求路徑：call 是一次呼叫，seq 是依序執行的子步驟，par 是平行執行的子步驟。情境卡的下單流程寫成：

{ kind: 'seq', steps: [
  { kind: 'call', name: '驗證 token', ms: 5 },
  { kind: 'par', steps: [
    { kind: 'call', name: '查菜單', ms: 20 },
    { kind: 'call', name: '查會員', ms: 30 },
  ] },
  { kind: 'call', name: '寫訂單', ms: 15 },
] }

練習 1：寫 pathLatency(step)，回傳整條路徑的延遲：call 回傳自己的 ms；seq 是子步驟延遲的總和；par 是子步驟延遲的最大值。空的 seq 和空的 par 都是 0。子步驟本身也可以是 seq 或 par，巢狀幾層都要算對；不能修改傳進來的樹。

練習 2：寫 criticalPath(step)，回傳關鍵路徑上依序經過的 call 名稱。seq 把每個子步驟的關鍵路徑依序接起來；par 只取延遲最大的那個分支（一樣慢時取第一個）；空的 seq／par 回傳 []。pathLatency 已經寫好，可以直接用。

練習 3：團隊提了幾個優化方案，每個方案把某些 call 改成新的 ms。寫 bestImprovement(tree, options)：算出每個方案實際能省下多少總延遲，回傳省最多的 { id, savedMs }（一樣多時取第一個）；沒有任何方案能省時間時回傳 null。不能修改原本的樹；changes 裡指到不存在的 call 就忽略。巢狀在 seq、par 裡的 call 也要能改到。

練習 4：寫 systemLimit(capacity, mix)，算出整個系統每秒最多能撐幾個請求、瓶頸在哪：

  • perRequestCalls[元件] ＝ Σ（每種請求的 share × 它對這個元件的 calls），也就是平均每個請求打這個元件幾次。
  • maxRps ＝ 所有 perRequestCalls 大於 0 的元件中，capacity ÷ perRequestCalls 的最小值；bottleneck 是取到最小值的元件（一樣小時依名稱字母順序取第一個）。
  • share 加總不是 1（容許 1e-9 的誤差）時丟 RangeError；calls 裡出現 capacity 沒有的元件時丟 Error。不能修改傳進來的資料。

練習 5：把非功能需求寫成資料，交給程式檢查。寫 checkNfr(n)，依下面的順序回傳問題代碼（沒有問題回傳 []）：

  1. target 是 null（沒有數字）→ 'no-target'
  2. 延遲（latency）：沒有 percentile → 'no-percentile'；percentile 小於 90 → 'low-percentile'；沒有 load 或 load 是 'average' → 'not-at-peak'
  3. 可用性（availability）：沒有 window → 'no-window'；target 是數字但不在 0 和 1 之間（不含 0 和 1）→ 'bad-ratio'

再把情境卡的四句話「下單要快」「不能掛」「不能錯帳」「集點晚一點沒關係」寫成 COFFEE_NFRS，數字用這一課表格裡的目標（集點的 target 單位是秒、錯帳是最多扣款次數），每一筆都要通過 checkNfr。

練習 6：PM 在需求文件裡寫「下單要很快」。這是一個好的非功能需求嗎？

✓ 形容詞沒辦法驗證，上線後也沒辦法判斷有沒有達標。平均值會把少數很慢的請求藏起來，所以要寫百分位數（例如 p99），並說明是尖峰時段：「尖峰時下單 API 的 p99 小於 300ms」。

練習 7：API 有 2 台、每台撐 600 req/s；資料庫撐 2,000 查詢/s；每張訂單要打 8 次資料庫。只看下單的話，系統每秒最多處理幾張訂單？

✓ 每張訂單打 8 次資料庫，資料庫最多撐 2,000 ÷ 8 ＝ 250 張/秒；API 能撐 1,200，還有很多餘裕。只看單一元件的容量、忘了放大係數，就會以為上限是 1,200。這時再加 API 機器也沒有用。

練習 8：同事說：「先設計成能撐 100 倍流量，比較保險。」你怎麼回應？

✓ 分片、微服務、多區域都會讓系統更難維運、更多種失敗、功能交付變慢，而 100 倍的流量可能永遠不會來（YAGNI）。架構可以演進（第 19 課），關鍵是事先寫下觸發條件，例如「單一資料庫寫入超過多少時評估分片」。

常見錯誤

  • 一開始就畫架構圖：沒有先問清楚需求與數字，畫出來的東西無法判斷好壞。先問「多少使用者、多少資料、多快、多穩、錯了會怎樣」，再估算，最後才畫圖。
  • 用形容詞寫需求：「要快、要穩」沒辦法驗證。延遲寫成百分位數＋負載條件＋數字，可用性要寫統計區間。
  • 只看單一元件的容量：忘了放大係數和請求組合。一個下單請求打 8 次資料庫，資料庫才是瓶頸，加 API 機器沒有用。
  • 優化不在關鍵路徑上的呼叫：平行分支裡比較快的那條再變快，總延遲不會變。先找出關鍵路徑再動手。
  • 為想像中的規模設計：微服務、分片、多區域都有代價，而且是現在就要付。為看得到的成長設計，並寫下到什麼數字要走下一步。
  • 沒寫下限制與假設：之後沒人知道當初為什麼這樣選，也不知道哪個假設已經失效。

小結

  • 「撐得住嗎」不能直接回答，要先把情境換成數字（情境卡），再把「撐住」寫成可量測的目標；系統設計就是在限制下做取捨，並把理由寫下來。
  • 需求分功能與非功能；非功能需求要寫成可量測的目標（百分位數、負載條件、統計區間、數字）。限制也是設計的輸入，常常直接刪掉選項。
  • 設計照固定步驟走：釐清需求 → 估算 → API 與資料 → 高階架構 → 深入瓶頸 → 取捨與風險 → 寫成文件。沒有數字之前不畫架構圖。
  • 一筆請求的延遲：依序相加、平行取最大；只有關鍵路徑上的優化會讓總延遲變短。
  • 整個系統的上限：每個元件的容量 ÷ 請求組合加權後的放大係數，取最小值的那個就是瓶頸；咖啡店的瓶頸是資料庫，加 API 機器沒有用。
  • 每加一個元件都解決一個瓶頸、帶來新問題；回答「要加什麼」時講出選了什麼、放棄什麼、什麼數字改變要重來。YAGNI：為看得到的成長設計，並寫下到什麼數字要走下一步。

這課的回答還缺一個數字：週年慶尖峰每秒到底會進來多少請求。下一課用情境卡算出每秒幾筆訂單、5 年要存多少資料、要幾台機器，以及哪個數字改變時答案會跟著變。
