階段 6：期末專題 · 第 22 課

期末專題：咖啡店線上點餐系統

前面 21 課，每一課解決一個問題：估算、快取、重試、冪等、限流、斷路器、佇列、saga、推送、設計文件、除錯。這一課把它們用在同一個系統上：老闆決定在週年慶前推出 App 線上點餐，由你負責設計。

驗收的場景很具體。週年慶早上 8 點，買一送一，流量是平常的 20 倍。王小明在 App 點了一杯拿鐵、按下結帳。同一時間，金流比平常慢、菜單每秒被讀上千次、有人等不及連按好幾次結帳。你的設計要保證王小明這張訂單最多扣一次款、不賣超過庫存、扣了錢一定有咖啡、做好時 App 會通知他，而且其他顧客的結帳不會被拖垮。

難的地方不在單一機制，每一個你都在前面寫過、測過。難在組合：每個機制單獨看都對，順序一放錯，組起來就會重複扣款。這一課跟著王小明這張訂單，從老闆的需求一路走到上線審查，每一節解決上一節留下的問題；練習再把七個部分親手寫出來。學完你拿到一份新需求時，知道從哪裡開始、做到哪裡算可以上線。

這課的路線：
  1. 需求：老闆說的「要快、不能掛」，怎麼改寫成可以驗證的數字。
  2. 架構：哪些事王小明要等、哪些交給 outbox；開場的重複扣款最常出在哪（開場問題的最小答案）。
  3. 時間預算：500ms 的 p99 逐段扣下來，金流失敗時還夠不夠重試一次。
  4. 組起來的順序：限流、冪等、重試、斷路器、saga 誰先誰後、誰包住誰，放錯會怎樣。
  5. 故障模式：每個依賴壞掉時這張訂單會怎樣；結果未知的付款交給對帳。
  6. 上線審查：上線那天盯哪些訊號、出事怎麼止血。
讀完上面六段，再依序動手做七個步驟，每步一題：1 需求與估算、2 下單 API、3 菜單、4 付款呼叫、5 saga 與 outbox、6 狀態推送、7 設計文件與 ADR，最後是階段檢核。
這課會用到：整門課，其餘各課在正文用到的地方都有連結。最擋路的是：
  • 第 1 課的設計步驟：先把需求改寫成可以量測的目標，再估算、畫架構、找瓶頸和取捨。
  • 第 9 課的冪等鍵：同一把鍵送很多次，對方只做一次；重送時換了鍵，就會被當成另一筆。
  • 第 13 課的 saga 與 pivot：跨服務的流程失敗時用補償收拾；pivot（扣款）是過了就不能回頭的那一步，之後只能往前做完。
  • 第 18 課的設計文件與 ADR：動手前寫下目標、方案、故障模式與回滾計畫；每個重要決定一份 ADR 記下理由。

老闆說「要快、不能掛」：怎麼改寫成能驗證的目標？

系統設計最常見的失敗，是聽到「線上點餐」就開始畫微服務。畫圖之前要先知道系統要做到什麼程度，否則沒辦法判斷一個設計是太簡單還是做過頭。做法跟 PostgreSQL 課第 26 課先讀需求再設計資料表一樣：先把需求讀完、改寫成可以驗證的數字，再決定要做什麼。

老闆給的需求：

  • 會員用 App 預先點餐：選門市、選品項、付款，到店取餐。
  • 咖啡做好時，App 收到推送通知。
  • 付款成功後集點。
  • 週年慶買一送一，當天尖峰是平常的 20 倍。

這份需求混了兩種東西。前三項說系統要「做什麼」，叫功能需求。第四項，加上老闆開會時口頭補的「結帳要快」「不能掛」「不能多扣錢」，說的是系統要「做得多好」，叫非功能需求（non-functional requirements）。功能需求寫錯，做出來的東西不對；非功能需求沒寫清楚，做出來的東西平常好好的，週年慶當天才倒。

「要快」沒辦法驗證：200ms 算快嗎？3 秒呢？每個人心裡的數字不一樣，上線後也沒人能說它達標了沒有。第 1 課的做法是把每個形容詞改寫成能量測的數字，並寫明量什麼。延遲用 p99（第 3 課：把請求的耗時由小到大排，第 99 百分位的那個值），因為平均值會把少數很慢的請求藏起來，而週年慶會抱怨的正是那些等很久的人。可用性用一段期間內服務正常的時間比例，再換算成停機預算，讓「不能掛」變成「這個月最多能掛幾分鐘」。改寫後：

老闆說的可以量測的目標這課哪一步負責
結帳要快尖峰時段，下單 API 的 p99 小於 500ms步驟 1 寫下來，步驟 4 用 deadline 守住
不能掛每 30 天可用性 99.9%（停機預算約 43.2 分鐘）步驟 1、7
不能多扣錢同一張訂單最多扣款 1 次步驟 2、4、5
不能賣超過庫存預留庫存成功才付款；付款失敗要釋放步驟 5
點數不用馬上到付款成功後 1 分鐘內入帳步驟 5（事件交給集點服務）
做好要通知訂單狀態 5 秒內推送到 App步驟 6

第三欄是這張表最重要的用途：每個目標都要有一個負責守住它的設計，沒人負責的目標等於沒寫。注意「不能多扣錢」對到三個步驟，表示它不是一個機制做得到的，而是入口、付款、saga 三層一起守；只要其中一層的寫法跟其他層對不上，就會破功。開場說的組合問題就是從這裡來的。

「點數 1 分鐘內入帳就好」這種「可以晚一點」的需求一樣要問出來。它決定了集點可以不在結帳的路徑上，下一節的架構就靠它。

💡 實務上：需求幾乎不會以數字的形式交到你手上
PM 或老闆通常只會說「要快」「不能掛」「活動當天人會很多」。資深工程師拿到需求會先問：尖峰大概多少人、從哪裡量快慢、哪些事可以晚一點（像點數 1 分鐘內入帳就好）、出錯時最不能接受的是什麼（少賺一筆，還是多扣顧客的錢）。問完把數字寫進設計文件，請 PM 確認，之後有爭議就回來看這份紀錄。不是每個功能都要談到 p99：只有幾個店員在用的後台報表，講清楚「資料可以晚幾分鐘」就夠了。

數字有了，下一個問題是：要用哪些元件、怎麼擺，才守得住這些數字？

系統要長什麼樣子？哪些事王小明要等、哪些不用？

畫架構時第一個要決定的不是用什麼元件，而是哪些工作要在王小明按下結帳、畫面轉圈的那段時間內完成。這段時間裡的呼叫都是同步的：呼叫的一方停下來等結果，顧客也跟著等。另一種是非同步：把工作交出去就不等了，之後由別人處理。

判斷的標準是：哪些事沒做完，就不能告訴王小明「付款成功」？答案只有三件：確認沒有超賣、確實扣到款、訂單已經存下來。其他的事，像廚房出單、集點、推送通知，晚幾秒做也沒人察覺，上一節的需求也明寫點數 1 分鐘內入帳就好。把它們移出同步路徑有兩個好處：同步路徑越短，p99 越好守；同步路徑上的依賴越少，結帳越不容易被別人拖垮，因為串在同步路徑上的每個硬相依，它的可用性都會乘進結帳的可用性。

這一課說的端到端（end-to-end），是從王小明按下「結帳」，到 App 顯示「你的拿鐵做好了」為止的完整路徑。中間經過 nginx、API、資料庫、金流、佇列、廚房、推送，任何一段出問題，顧客都會覺得「App 壞了」。下圖畫出這條路徑，實線是同步呼叫，虛線是非同步：

圖上每個元件的位置都是一個決定，逐一看理由。

API 無狀態、多台。無狀態是指 API 不把訂單、計數這類資料存在自己的記憶體裡，狀態都在 PostgreSQL 與 Redis，所以哪一台處理王小明的請求結果都一樣。任何一台壞掉，負載平衡器把流量轉給其他台（第 4 課）。台數由步驟 1 的估算決定：週年慶尖峰需要 N 台，就部署 N+1 台，壞一台還撐得住。

Redis 是軟相依。第 18 課把依賴分成兩種：硬相依壞了，功能就做不了；軟相依壞了，功能降級但還能用。Redis 在這裡只負責菜單快取和限流，前者是加速、後者是保護，都不影響訂單算得對不對，所以設計成軟相依：它壞了，限流改用每台 API 的本機計數，菜單改讀資料庫並限制並發。這要在設計時就決定，因為事故當下沒時間想；而且「改讀資料庫」如果沒有限制並發，原本被快取擋下的上千個請求會一次壓到資料庫上。

金流是硬相依，也是最慢的一段。沒有它就收不到錢，所以它是硬相依；它在別人家，多慢你控制不了。所以所有的逾時、重試、斷路器、隔艙都集中在呼叫金流的這一層，而且只在這一層重試。隔艙是替呼叫金流的請求設一個並行上限：金流變慢時，最多只有固定數量的請求卡在等金流，其他 API 的連線和工作執行緒不會被佔光（第 11 課）。第 8 課講過多層重試會相乘放大：如果 App、API、付款客戶端三層各自最多試 3 次，金流一變慢，王小明按一次結帳最多會變成 3 × 3 × 3 = 27 次呼叫，壓在已經很慢的金流上。

付款之後的事都走 outbox。第 12 課的 outbox 是把要發出去的事件，跟訂單狀態寫在同一個資料庫交易裡，再由 relay 讀出來送到佇列。廚房出單、集點、通知因此不在結帳的同步路徑上：它們慢了、壞了，結帳照樣成功，事件留在 outbox 等它們恢復。

推送只是通知。訂單的真實狀態以 API 為準，SSE 推送只是讓 App 早一點知道。SSE 斷線、漏掉一則都沒關係，App 重連時用 Last-Event-ID 補，補不了就重新拿完整狀態（第 17 課）。

這張圖也給出了開場問題的最小答案：重複扣款會出在哪？整張圖只有一個地方會動到錢，就是 API 呼叫金流的那條實線。王小明連按結帳、網路逾時後自動重試，最後都會變成「對金流再送一次付款」。金流靠第 9 課的冪等鍵認出重送：同一把鍵送幾次都只扣一次，換了鍵就是新的一筆。所以最常見的重複扣款，不是哪個機制寫錯，而是某一層在重試時產生了一把新的鍵。〈誰先誰後〉那一節會逐層檢查這件事。

不過架構只說了誰在同步路徑上，沒說同步路徑有多少時間。500ms 要分給 nginx、資料庫和金流，剩下的夠不夠在金流失敗時重試一次？

500ms 夠用嗎？把下單路徑的時間逐段扣下來

需求那一節的「p99 小於 500ms」是整條同步路徑的時間預算：路徑上每一段都要從這 500ms 裡分一份，加起來不能超過。檢查的方法是把每一段的 p99 列出來相加，看金流佔了多少、還剩多少。執行後看最後兩行：剩下多少時間，以及重試一次會不會超過預算。

前面六段加起來用掉 362ms，剩 138ms；重試一次要再花 350ms（退避等 50ms，再呼叫一次金流 300ms），總共 712ms，超過預算。每一段都取 p99 再相加是悲觀的算法，真實情況不會每一段同時都那麼慢。但這個悲觀的估算已經足以說明兩件事。

第一，重試會吃掉 p99。p99 看的是最慢的那 1% 請求。只要需要重試的請求少於 1%，它們落在 p99 之外，目標還守得住；金流一變慢，大量請求開始重試，最慢的那 1% 全是重試過的請求，p99 第一個破。這時繼續重試只會讓情況更糟。第 11 課的斷路器就是為這種情況設計的：它統計最近呼叫的失敗率，超過門檻就暫時不再呼叫金流、直接回失敗，讓顧客馬上知道付款暫時不能用，而不是每個人都轉圈到逾時。

第二，deadline 決定什麼時候停。deadline 是「整個付款最晚要在什麼時間點結束」，請求進來時就算好，往下傳給每一層（第 8 課）。每次要呼叫金流之前先看：剩下的時間夠不夠一次完整的呼叫？不夠就不要送了。送了也來不及回給王小明，只是多一筆不確定有沒有扣款的請求，之後還要有人查清楚。步驟 4 會實作這個判斷。

到這裡，入口有限流與冪等，付款有重試、斷路器與 deadline，扣款後有 outbox。每一個機制在自己那一課都測過了，剩下的問題是：它們疊在一起時，誰先誰後？開場說的重複扣款就藏在這裡。

每個機制都對，為什麼組起來會重複扣款？誰先誰後、誰包住誰

「A 包住 B」指的是 A 呼叫 B，B 的每一次執行都經過 A。順序決定了每個機制看到什麼：放在外層的只看到整體的結果，放在內層的看到每一次嘗試。跟著王小明的請求，由外往內走三段。

入口：限流、冪等、驗證。請求進到 API，第一關是限流，第二關是冪等。限流放前面，是因為它最便宜，只要一次記憶體或 Redis 操作；冪等要查資料庫。反過來放的話，一支失控的 App 每秒重送上千次，每一次都會打到冪等鍵表，資料庫比限流器先倒。原則是由便宜到貴：越便宜的檢查越早做，把明顯不該進來的請求擋在成本最低的地方。接著驗證內容。驗證放在冪等之後，因為要先確認這把鍵用過沒有；但驗證失敗時，不能把 400 存成這把鍵的結果。驗證失敗代表請求根本沒開始執行，王小明修正內容後會用同一把鍵重送，如果冪等表裡存著 400，他會永遠收到被回放的 400，或因為內容跟第一次不同被判成 422。

付款：重試在外、斷路器在內、同一把冪等鍵。斷路器要放在重試裡面，因為它要看到每一次嘗試，才算得出真正的失敗率；放在外面，它只看到「重試三次之後」的最終結果，金流已經壞了一陣子才打開。冪等鍵在重試之前產生一次（例如由訂單編號組成），每次嘗試都用它。如果每次重試才產生新的鍵，就會出現開場的事故：第一次呼叫其實扣款成功，只是回應在路上逾時；第二次換了鍵，金流當成另一筆，再扣一次。

同一段還有最容易判斷錯的一件事：逾時的付款，結果是「未知」，不是失敗。逾時只代表你沒收到回應，請求可能已經到了金流、扣了款。把它當成失敗而取消訂單，王小明就是被扣了錢、訂單卻是取消。

付款之後：pivot、outbox、投影。下單是第 13 課的 saga，付款是 pivot：在它之前的步驟（建立訂單、預留庫存）都能補償；扣款成功之後只能往前把訂單做完。所以預留庫存要排在付款之前。扣款之後確認訂單失敗，要重試到成功，真的做不完交給人，不能釋放庫存，否則就是錢收了、咖啡沒了。確認時，訂單狀態和要給廚房的事件寫在同一個交易：事件只在交易提交後才存在，不會出現狀態改了、事件沒寫，廚房永遠收不到單。最後是推送：佇列至少投遞一次，事件會重複、亂序（第 16 課），所以不能收到一個就推一個。中間要先經過投影（projection）：它是依事件維護每張訂單「目前狀態」的一份資料，記得每張訂單已經處理到哪個狀態。收到重複的、或比目前狀態還舊的事件時，它會忽略並回報「沒有改變」；只有狀態真的往前走，才回報 applied（第 16 課）。所以只有投影回 applied 才推送；直接把每個事件推給 App，王小明的畫面會從「做好了」跳回「已付款」。

狀態和事件在同一個交易事件只在交易提交後才存在狀態改了、事件沒寫（或反過來），廚房永遠收不到單
只推送投影真的改變的狀態事件會重複、亂序（第 16 課）App 的狀態從「做好了」跳回「已付款」

順序排好之後，成功路徑不會重複扣款，逾時的付款也不會被誤取消；但它最後算成功還是失敗，還沒有人負責。而且這張表的每一列都假設資料庫、Redis、佇列正常運作。週年慶那天任何一個依賴都可能壞掉，壞掉時王小明的訂單會怎樣？

依賴壞掉時，王小明的訂單會怎樣？

只設計成功路徑的文件，審查時一定會被問「金流掛了呢？」。故障模式（failure modes）是設計文件裡的一節，逐一寫出每個依賴壞掉或變慢時，系統怎麼做、顧客看到什麼、誰會被通知。寫它的目的，是把事故當下要做的判斷提前到設計時做：那時有時間想清楚，能跟 PM 確認顧客看到的畫面，也能事先演練。

表裡 Redis 那一列用到兩個詞，先說清楚。限流器是保護機制，保護機制自己壞了的時候有兩種選擇：fail open 是放行請求，fail closed 是擋下請求。限流選 fail closed，Redis 一掛所有人都不能下單，等於把軟相依變成了硬相依；所以選 fail open，再加上每台 API 各自的本機粗略限流，保留一點保護。另一個詞是卸載（load shedding）：請求量超過能處理的量時，直接拒絕多出來的那些，保住已經在處理的請求（第 11 課）。

依賴系統怎麼做顧客看到告警
PostgreSQL primary切到 replica（約 1 分鐘）；期間下單回 503 加 Retry-After「目前無法下單，請稍後再試」，菜單照常（快取）立刻呼叫值班
Redis限流 fail open 加本機粗略限流；菜單讀資料庫並限制並發，超過就卸載大多數人沒感覺，尖峰時菜單變慢告警，不用半夜叫人
金流變慢重試受 deadline 限制；失敗率高時斷路器打開、快速失敗；隔艙保護其他 API「付款暫時無法使用」，或降級成到店付款立刻呼叫值班並通知金流廠商
佇列或 relay事件留在 outbox；恢復後依序補送，消費者冪等集點、通知變慢，結帳不受影響outbox 最老一筆的年齡超過 1 分鐘
SSE 連線App 用 Last-Event-ID 重連；補不了就收到 reset，重新拿完整狀態通知晚幾秒重連率異常升高

有一種情況這張表裝不下：上一節留下的「結果未知的付款」。它不是某個依賴壞了，而是你不知道金流那邊發生了什麼，所以沒有一列可以負責。saga 遇到結果未知、或補償和確認重試都做不完時，會把訂單標成 needs-attention，意思是需要有人查清楚。這要另外設計對帳（reconciliation）：一個定期執行的排程，拿出這些訂單，用當初同一把冪等鍵向金流查詢這筆到底有沒有扣款，有就確認訂單，沒有就取消（第 13 課）。王小明的付款如果剛好逾時，他的訂單會先停在 needs-attention，由對帳決定結果，而不是被直接取消。

成功路徑、順序、故障模式都寫好了，設計看起來完整。但「看起來完整」不等於可以上線：怎麼確定沒漏掉什麼？上線那天又要盯什麼？

可以上線了嗎？上線準備度審查與止血手段

上線準備度審查（production readiness review）是上線前的一次正式檢查，逐項確認可靠性、可觀測性、安全與回滾都準備好了。它用一份問題清單，而不是靠大家的感覺：一個人想得到的漏洞有限，清單把整門課的教訓都帶進來。下面這份清單每一列對應前面的課，拿王小明的訂單路徑逐列回答；答不出來的，寫進設計文件的「未解決的問題」。清單是查表用的，不用背。

清單通過，只代表你想得到的情況都處理了。上線那天還要盯著正式流量，每個訊號對應路徑上的一段：

  • 下單 API 的請求率、錯誤率、p99（第 21 課的 RED）：結帳整體是否正常。
  • 付款成功率與斷路器狀態：金流那一段。
  • outbox 最老一筆的年齡、佇列最老訊息的年齡與死信佇列數量：非同步那一半有沒有卡住。
  • needs-attention 訂單數：結果未知的付款有沒有堆積。
  • SSE 連線數與重連率：推送。

每一個都要先定好「超過多少就回滾」，事故當下才討論門檻就來不及了。訊號超過門檻時，第 21 課的原則是先止血、再找根因：先停止對顧客的影響。下面這些止血手段要在上線前就做好、演練過：

  • online-ordering 旗標調回上一個百分比，或直接關掉（回到電話訂位）。
  • ops 旗標（第 19 課的 kill switch）暫停非必要功能（推薦、行銷活動頁），把容量留給下單。
  • 金流出問題時改成「先下單、到店付款」的降級流程。代價是有人訂了不來拿，所以只在事故期間開。
💡 實務上：審查做多細，看出事的代價
上面這份清單是給結帳這種會動到錢的流程用的；後台加一個報表頁，通常只要確認有監控、能回滾。準備度審查也不只工程師參加：降級成「到店付款」時顧客看到什麼要 PM 點頭，客服要先拿到回覆顧客的說法，值班的人要知道告警響了先看哪裡。上面說的演練，是在測試環境真的動手：關掉旗標、停掉 Redis，看顧客畫面和告警是不是跟故障模式表寫的一樣。寫進「未解決的問題」的項目要附上負責人和期限，否則清單會一直留著沒人處理。

補充與查表

為什麼這裡是 500ms，第 1 課是 300ms？第 1 課的表格寫的是 p99 小於 300ms，這裡變成 500ms：需求會在討論中改變，改了就要更新所有依賴它的地方（估算、SLO、設計文件）。步驟 7 會檢查設計文件跟步驟 1 的數字一致。

練習

練習分成七步，對應王小明這張訂單經過的每一段，每一步一題、各自判分。每一題的起始程式都已經貼好它需要的、前面各課的參考解，所以前面哪一步卡住，後面照樣可以做。有些是只留下這一題用得到的精簡版（例如斷路器少了半開時的探測次數設定、隔艙少了取消），註解會寫出跟原本那一課差在哪裡。

步驟 1：需求與估算（第 1、2、4 課）

所有設計決定都從這裡的數字出發：要幾台 API、要不要分片、停機預算有多少。需求那一節的需求表在這裡變成程式裡的 requirements；估算用第 2 課的規則，這裡一次用上：尖峰要用尖峰算，儲存要乘副本，台數要無條件進位再加 N+1。

練習 1：填好 requirements（照上面「需求」一節的表格：功能需求至少包含點餐、付款、通知、集點；延遲是尖峰 p99 500ms）並寫 estimate(s)，每個欄位的公式寫在起始程式 Estimate 型別的註解裡。不要四捨五入。

步驟 2：下單 API（第 9、10 課）

這一步寫的是〈誰先誰後〉那一節的「入口」段。下單 API 是整個系統最貴的入口：每一次都會查資料庫、呼叫金流，所以處理順序由便宜到貴：先檢查請求有沒有帶冪等鍵，這不用任何 I/O；再限流，只用記憶體；再查冪等鍵表，要打資料庫；最後才驗證內容、下單。驗證放在冪等之後，是因為要先確認這把 key 是不是已經用過；但驗證失敗代表請求沒有開始執行，要把處理中的紀錄刪掉，讓顧客修正後可以用同一把 key 重送。Stripe 對參數錯誤也是這樣處理，不保存結果。

練習 2：寫 createOrderEndpoint(deps)，回傳處理請求的函式。依序：

  • 沒有 idempotencyKey → 400。
  • 每位顧客各自一個 token bucket（用 deps.newBucket() 建立），每個請求拿 1 個 token；不夠 → 429，標頭用 rateLimitHeaders(deps.policy, { remaining: 0, resetSec: retryAfterMs ÷ 1000, allowed: false })，裡面有 Retry-After 與 RateLimit 標頭。
  • deps.idem.begin(...)：replay 回傳保存的回應；mismatch → 422；in-progress → 409。
  • parseOrderBody(body) 回傳 null → 先 abandon 再回 400。
  • 呼叫 deps.placeOrder({ customerId, ...內容 })：成功 → 201，body 是它的結果，用 complete 保存；丟錯 → 先 abandon 再回 503。

body 寫什麼都可以（例如 { error: 'in-progress' }），測試只看狀態碼、標頭與 201 的 body。回應物件的格式是 { status, headers, body }，沒有標頭時給 {}。customerId 一律用 req.customerId（登入身分），不能被 body 裡的欄位蓋掉。

placeOrder 丟錯時 abandon、回 503，前提是 placeOrder 失敗時沒有留下任何寫入（例如整個在一個交易裡回滾）。如果它可能做到一半（已經扣款才丟錯），abandon 會讓重送用新的訂單編號再扣一次，這時要改成保存錯誤回應，或像步驟 5 一樣把進度記在訂單上、重送時接手。Stripe API v1 選的是前者：端點開始執行後連 500 也保存，重送拿到同一個 500。

步驟 3：菜單（第 5 課）

王小明下單之前會先看菜單。看菜單是下單的 16 倍以上，週年慶尖峰每秒上千次，全部打資料庫撐不住。菜單每家門市不同、改價不頻繁，很適合快取。三個要顧好的地方：熱門門市過期瞬間不能有上百個請求同時載入（single-flight）；過期一點點時先回舊的、背景更新，顧客不用等；改價要生效，而且改價前就開始的那次載入，帶著舊價格回來時不能寫回快取。

練習 3：寫 createMenuService(opts)。每家門市一份快取，載入完成時記下 opts.now() + ttlMs 當過期時間。getMenu(storeId)：

  • 還沒過期 → 直接回傳快取。
  • 過期但沒超過 staleMs → 立刻回傳舊菜單，並在背景更新（同一家門市同時只能有一個載入）；背景更新失敗呼叫 opts.onError，保留舊菜單，不能有未處理的 rejection。
  • 沒有快取，或過期超過 staleMs → 等載入完成；同一家門市同時的請求共用同一次載入。

onPriceChanged(storeId) 讓那家門市的快取失效：之後的 getMenu 要重新載入，不能去等改價前開始的載入；改價前開始的載入完成時，也不能把結果寫回快取（提示：每家門市一個版本號）。時間只能用 opts.now()。

步驟 4：付款呼叫（第 8、11 課）

這一步寫的是〈時間預算〉與〈誰先誰後〉兩節的付款那一段，把可靠性模式疊起來，由外到內是：隔艙 → deadline → 重試 → 斷路器 → 單次呼叫。隔艙在最外層，因為它限制同時有多少個付款在進行：金流變慢時，付款最多佔用固定數量的併發，不會拖垮其他 API。deadline 是整個付款最晚要結束的時間點。重試最多 3 次、用 full jitter 退避、只重試暫時性錯誤。斷路器在重試裡面，每一次嘗試都經過它。

比較細的是失敗的分類。卡片被拒是確定的答案，不重試。unavailable（連線被拒，或金流明確回應「這次沒有處理」）確定沒扣款，可以放心重試。逾時不一樣：請求可能已經到了金流、扣了款，只是回應沒回來。因為每次重試都用同一把冪等鍵，重試本身是安全的；但如果重試用完、時間用完還是沒有確定的答案，就只能回報「結果未知」，交給下一步處理，不能當成失敗。

練習 4：寫 createPaymentClient(deps)，回傳 { pay(orderId, amount, deadline) }：

  • 一開始 now() + MIN_CALL_MS > deadline → { ok: false, reason: 'unavailable' }，不呼叫 charge。
  • 整段放在 deps.bulkhead.run(...) 裡；BulkheadFullError → unavailable。
  • 每次嘗試是 deps.breaker.execute(() => deps.charge(req))，冪等鍵一律是 pay:<orderId>。成功 → { ok: true, chargeId }。
  • ChargeError 的 card_declined → declined，不重試。BreakerOpenError → 停止，不重試。timeout、unavailable 可以重試。
  • 第 attempt 次失敗後，等 backoffDelay(attempt, deps.random) 毫秒（用 deps.sleep）再試；已經試了 MAX_ATTEMPTS 次，或 now() + 等待時間 + MIN_CALL_MS > deadline 時停止。
  • 停止時（重試用完、時間不夠、斷路器打開）：只要有任何一次嘗試是 timeout，回 unknown；否則回 unavailable。

步驟 5：saga 與 outbox（第 12、13 課）

這一步寫的是〈誰先誰後〉那一節的「付款之後」段。下單是一個 saga：建立訂單 → 預留庫存 → 付款 → 確認。付款是 pivot：在它之前的步驟都能補償（釋放庫存、取消訂單）；它成功之後就只能往前，確認步驟失敗要重試到成功，真的做不完交給人，不能「退款了事」。確認時，訂單狀態和要給廚房、集點、通知的事件寫在同一個交易，這就是 outbox。

付款回 unknown 時兩條路都不能走：不能確認，因為可能沒扣到款；也不能取消，因為可能已經扣了。回報 needs-attention，由〈依賴壞掉時〉那一節的對帳用同一把冪等鍵查清楚。

練習 5：寫 placeOrderSaga(deps, order)：

  • 用一個交易 insertOrder 建立 pending 訂單，再 reserveStock。預留失敗 → 取消（見下）並回 cancelled，不付款。
  • 呼叫 pay。成功 → 在同一個交易裡 setStatus(orderId, 'paid') 並寫入一筆 OrderConfirmed（aggregateId 是訂單編號，payload 是 JSON 字串，內容自訂），用 tryTimes 最多試 5 次；成功回 confirmed，都失敗回 needs-attention，不釋放庫存。
  • 回 declined 或 unavailable → releaseStock 最多試 3 次（都失敗回 needs-attention），再取消。
  • 回 unknown → 直接回 needs-attention，不釋放、不取消。
  • 取消：同一個交易裡 setStatus(orderId, 'cancelled') 並寫入 OrderCancelled，最多試 5 次；成功回 cancelled，都失敗回 needs-attention。

步驟 6：狀態推送（第 16、17 課）

王小明的拿鐵做好了，最後一段是通知他。廚房做好咖啡時發出 OrderCompleted，經過佇列送到推送服務。佇列是至少一次，事件會重複、亂序，所以先交給第 16 課的投影：只有投影真的改變了狀態（回傳 applied）才推送。推送只是通知，送的是那張訂單「目前」的狀態，補齊缺號時一次跳到最新狀態也沒關係，App 要完整資料就打 API。

練習 6：寫 createStatusStream(projection, log)：

  • EventLog 是第 17 課練習 2 的參考解，多了一個 latestId()：回傳目前最新的 id，還沒有事件時是 null。
  • onEvent(e)：projection.apply(e) 回傳 'applied' 時，把 { orderId, status: 投影目前的狀態 } append 到 log；其他結果不推送。
  • connect(customerOrderIds, lastEventId) 依 log.since(lastEventId) 回傳要寫進 SSE 回應的文字。replay：只輸出這位顧客的訂單，每則寫成 id: <id>\nevent: status\ndata: <JSON.stringify(data)>\n\n，依序串起來。reset：寫一則 id: <log.latestId()>\nevent: reset\ndata: <JSON>\n\n，data 是這位顧客每張訂單（依 customerOrderIds 的順序，投影裡沒有的跳過）的 { orderId, status } 陣列；latestId() 是 null 時省略 id 那一行。

步驟 7：設計文件與 ADR（第 18、19 課）

最後把前六步的決定寫下來，交給〈上線審查〉那一節的準備度審查。設計文件給審查的人看「做什麼、為什麼、壞了怎麼辦、怎麼上線」；ADR 記下兩個之後會有人問「當初為什麼這樣做」的決定。數字不要手抄：估算直接呼叫 estimate(SCENARIO)，假設一改，文件跟著改，就不會出現「文件寫 2 台、實際要 11 台」。

練習 7：DesignDoc、reviewDoc、validateAdrLog 沿用第 18 課的規則；DesignDoc 的估算換成步驟 1 的 Estimate，上線步驟多了放量百分比 percent。起始程式的 designDoc 是上次開會的草稿，adrs 只寫了一半（不要改上面已經寫好的程式）。修好它們，讓 reviewDoc(designDoc) 和 validateAdrLog(adrs) 都回傳空陣列，而且：

  • estimates 跟步驟 1 的 estimate(SCENARIO) 一致；slo 的可用性與延遲跟 requirements 一致。
  • payment 寫出壞掉時的行為（至少 8 個字）；替代方案至少 2 個。
  • 上線步驟用 online-ordering 旗標（flag）依序放量（percent）1% → 10% → 50% → 100%，每一步都有回滾方式；不可逆的「移除舊的電話訂位流程」放在最後，只有它不可逆。
  • 1 號 ADR（outbox）補上負面後果；新增 2 號「訂單狀態用 SSE 推送」：status 是 'accepted'、decision 以「我們將」開頭並寫出斷線時用 Last-Event-ID 續傳、至少一個負面後果。

最後三題是事故演練：上線後真的出事時，先做什麼。

練習 8：週年慶早上 8 點，金流的 p99 從 300ms 升到 8 秒，下單錯誤率開始上升。你是值班工程師，第一步該做什麼？

✓ 事故處理先停止影響、再找根因（第 21 課）。根因在金流那一邊，你也修不了；你能做的是讓自己的系統不被拖垮、讓顧客還能用。(a) 查根因時顧客一直付款失敗。(c) 逾時拉長，下單的 p99 直接超過 500ms 的目標，而且每個請求佔住連線更久，隔艙與連線池更快被用光，連看菜單都會受影響。(d) 瓶頸不在 API 台數；更多台 API 只會送更多請求給已經很慢的金流，連資料庫連線數都可能超過上限。

練習 9：Redis 掛了，限流和菜單快取都靠它。下單 API 應該怎麼做？

✓ Redis 在這個設計裡是軟相依：它管的是保護與加速，不是正確性。Stripe 的限流器出錯時也是 fail open。(a) 把軟相依當成硬相依，Redis 的可用性直接變成整個系統的上限。(b) fail closed 等於 (a)：每個請求都被擋。菜單改讀資料庫時一定要限制並發，否則快取擋掉的上千個請求會同時打到資料庫（第 5 課的容量型快取）。

練習 10：測試全部通過了，PM 希望上線第一天就把 online-ordering 旗標開到 100%。你怎麼回應？

✓ 測試只能證明你想到的情況是對的。真實的金流延遲、某家門市的奇怪菜單、尖峰的併發，只有正式流量才會出現。逐步放量讓出問題時只影響一小部分顧客，而且回滾只是調一個旗標，幾秒鐘就生效（第 19 課）。(b) 混淆了「測試通過」和「上線安全」。(c) 發 hotfix 要寫程式、review、部署，幾十分鐘內全部顧客都受影響；扣錯的款也收不回來。

常見錯誤

  • 直接寫程式，不先寫需求與數字：做完才發現撐不住週年慶，或做了不需要的東西（每秒幾十筆訂單就拆了十個微服務）。先估算，再決定架構。
  • 每個機制各自正確，組起來順序錯：限流放在冪等之後、斷路器包在重試外面、每次重試換冪等鍵。組合時逐一檢查誰包住誰。
  • 把逾時當成失敗：逾時的付款可能已經扣款，直接取消訂單就是「扣了錢、沒有咖啡」。結果未知要交給對帳。
  • pivot 之後還在補償：付款成功、確認失敗就釋放庫存或退款。pivot 之後只能往前，做不完交給人。
  • 只設計成功的路徑：故障模式、補償、對帳、告警都沒寫。審查時一個依賴一個依賴問「它壞了呢？」。
  • 軟相依被寫成硬相依：Redis 掛了整個系統就掛了。設計時就決定每個依賴壞掉時的行為，並且真的演練過。
  • 沒有放量與回滾計畫就上線：出事時只能發 hotfix。用旗標逐步放量，不可逆的步驟放在最後。
  • 設計文件與實作分歧：實作改了，文件與 ADR 沒跟著更新，半年後沒人知道哪個是對的。數字從程式算出來，決定改了就寫新的 ADR 取代舊的。

小結

  • 系統設計從需求開始：把形容詞改寫成可以量測的目標（尖峰 p99 500ms、每月 99.9%、最多扣款一次），再用估算決定台數、儲存與停機預算。
  • 同步路徑只放顧客在等的事（限流、冪等、下單、付款、確認）；其餘的透過 outbox 交給佇列，慢了、壞了都不影響結帳。
  • 把 p99 預算逐段扣下來，才知道還能不能重試：重試會吃掉 p99，時間不夠就由 deadline 停止、由斷路器快速失敗。
  • 重複扣款多半出在組合，不在單一機制：順序是設計的一部分：便宜的檢查放前面、重試在外斷路器在內、同一把冪等鍵、付款是 pivot、狀態與事件同一個交易、只推送真的改變的狀態。
  • 逾時代表結果未知，不等於失敗；saga 要有 needs-attention 與對帳這條路。
  • 每個依賴都要寫出故障模式；軟相依壞了要能降級，硬相依壞了要快速失敗並告警。
  • 上線前用準備度清單逐項審查；上線時用旗標逐步放量、每一步看指標，止血手段事先做好、演練過。

階段檢核：面試會問的觀念

這個階段就是整門課，所以這裡是總檢核：系統設計面試最常問的 8 件事，全部放進這個點餐系統裡。先在心裡回答，再選。

練習 11：週年慶前，同事把菜單快取從 4 台 Redis 加到 5 台，key 用 hash(key) % N 決定放哪一台。加完那一刻資料庫 CPU 衝到 100%，最可能的原因是？

✓ % 4 和 % 5 的餘數只有少數相同，範例實測約 79% 的 key 換機器，整個快取等於變冷，請求同時打到資料庫。改用一致性雜湊加虛擬節點，4 台加到 5 台只搬約 1/5，也就是新機器分到的那一份。a 最多人選：「只有新機器那一份失效」是一致性雜湊才有的性質，% N 做不到。（第 7 課）

練習 12：App 送出訂單最多等 1 秒。閘道、訂單服務各自把逾時訂成 1 秒，訂單服務到 900ms 才呼叫金流，金流也給 1 秒。設計審查時該怎麼改？

✓ 每層各自 1 秒，金流到 1.9 秒才結束，App 早就放棄了，後面 900ms 全是白工。往下傳的是 deadline：剩餘 ＝ deadline − 現在 − 餘裕，太少就直接不做，做完也沒人收。b 最多人選：固定的數字不看前面已經用掉多少，訂單服務 400ms 才呼叫金流、再給 500ms，就超過閘道的期限。（第 8 課）

練習 13：菜單快取的 TTL 是 60 秒。店長剛把拿鐵從 110 改成 120，顧客的 App 還顯示 110 就按了結帳。下單 API 計算金額時，價格該從哪裡來？

✓ 快取不是資料來源：菜單頁可以顯示快取的價格，下單時要從資料庫讀價格與庫存，錯一次就是錯帳。a 錯在請求內容由客戶端控制，改一下就能用 1 元買拿鐵。c 在快取和 App 都還是舊價格時，照樣收 110。（第 5 課）

練習 14：為了分擔週年慶的讀取，同事把點餐系統的查詢都改到 replica。下面哪一個最不該這樣做？

✓ 非同步複寫有延遲，剛寫進 primary 的訂單，replica 可能還沒有，顧客以為下單失敗就再按一次。這種讀自己剛寫的資料要讀 primary，或用 LSN 導向夠新的 replica。其他三個晚幾秒沒人察覺：每種讀取選夠用的最弱一致性，並寫下可以舊多久。（第 6 課）

練習 15：下單 API 這樣處理冪等鍵，本機測試重送同一把 key 都只下一次單。上線後哪裡會出事？

const done = new Map()   // 冪等鍵 → 第一次的回應
app.post('/orders', async (req, res) => {
  const key = `${req.user.id}:${req.headers['idempotency-key']}`
  if (done.has(key)) return res.status(201).json(done.get(key))
  const order = await placeOrder(req.user.id, req.body)
  done.set(key, order)
  res.status(201).json(order)
})

✓ 冪等鍵要存在所有 API 共用的資料庫：負載平衡不保證重試回到同一台，部署重啟時 Map 也會清空，兩種情況都會再下一次單。存進資料庫時用 INSERT … ON CONFLICT DO NOTHING 判斷誰先到，同時送來的兩個請求也擋得住。a 錯在 409 只代表「還在處理中」，已經完成的要回放第一次的結果。（第 9 課）

練習 16：結帳 saga 有三個步驟：預留庫存、金流扣款、送出廚房單。順序該怎麼排？

✓ 不可逆的步驟要等所有驗證都成功才做：預留庫存可以釋放，放前面；扣款是 pivot，成功就不回頭；廚房單放在它之後，失敗就重試到成功。b 最多人選：拿鐵賣完就要退款，退款是新的一筆金流紀錄、可能有手續費，顧客帳單上還會出現扣了又退。c 錯在咖啡做出來就收不回來。（第 13 課）

練習 17：訂單 API 回應裡的金額欄位要從 total 改名成 amount，舊版 App 還裝在很多顧客的手機上。怎麼改？

✓ 不相容的改動拆成 expand → migrate → contract：先加新的、舊的保留，各端改讀、用量歸零才收掉，每一步都相容、可回滾。a 最多人選：已經裝在手機上的舊版 App 不會跟著更新，一改名就讀不到金額。c 錯在 Deprecation 只是通知，App 要等使用者更新才改得了。（第 19 課）

練習 18：PM 想在結帳完成畫面顯示「本次獲得 5 點」，同事提議下單時同步呼叫集點服務（可用性 99.9%），等它回應再回給顧客。哪個說法正確？

✓ 同步的硬相依串聯時，可用性相乘、延遲相加；走 outbox 的集點不在結帳的可用性路徑上，慢了、壞了都不影響付款。a 錯在 p99 看的就是慢的那些請求，集點的尾延遲會直接加進下單的 p99。b 錯在同步呼叫一樣會逾時、結果未知，重試時照樣要冪等鍵。（第 4、15 課）
