階段 3：可靠性：失敗是常態 · 第 9 課

冪等性：重試也不會重複扣款

早上 8 點，陳美華在捷運上用 App 點了一杯拿鐵。訂單服務向金流閘道扣了 110 元，扣款成功，可是回應在路上遺失了：列車進隧道，手機斷線。App 等到逾時就自動重試，正好踩中第 8 課警告過的情況：扣款的 POST 逾時不代表對方沒收到。伺服器又建了一張訂單、又扣了 110 元。她收到兩封扣款通知，客服電話開始響。

上一課學會「失敗之後重試」，這一課處理重試的代價：同一件事被做了兩次。整課只做一件事：修好這個事故，讓結帳用的 POST /orders 不管被送幾次，都只建一張訂單、只扣一次款。我們會從「重複從哪裡來」一路做到伺服器端的冪等鍵、做到一半當機的復原，最後回到 App 端，看它要怎麼配合。

這課的路線：
  1. 為什麼重試會扣兩次款、冪等保證什麼：逾時之後 App 為什麼分不出「沒做」和「做了但回應丟了」；冪等講的是效果而不是回應，POST 要怎樣才能安全重試（開場問題的最小答案）。
  2. 結帳裡哪些步驟自己就能冪等：集點、改訂單狀態用唯一約束和條件更新，為什麼「先查再寫」擋不住重複。
  3. 冪等鍵與請求指紋：建立訂單怎麼認出「同一次結帳」，同一把 key 帶了不同內容時怎麼擋。
  4. 扣款後當機：扣款成功、伺服器還沒記下來就當機，重試怎麼從中斷的地方接著做。
  5. App 端與「只扣一次」：App 什麼時候沿用 key、什麼時候換新的，整套做完能不能說是「恰好一次」。
這課會用到：
  • 第 8 課的重試規則：只重試暫時性錯誤；POST 逾時不代表對方沒收到，直接重試可能扣兩次款。
  • PostgreSQL 課第 18 課的交易：BEGIN 到 COMMIT 之間的修改一起生效，ROLLBACK 就一起取消。
  • PostgreSQL 課第 31 課的 UPSERT：INSERT … ON CONFLICT 撞到唯一約束時改成更新或跳過，檢查和寫入一步完成。

為什麼 App 重試一次，顧客就被扣兩次款？

先站在 App 的位置看這件事。App 送出 POST /orders 之後，唯一能讓它知道結果的就是伺服器的回應。回應沒來，它只知道「等太久了」，不知道問題出在去程還是回程。所以逾時的那一刻，實際上可能是下面兩種情況之一：

  • 請求根本沒到伺服器：沒有建單、沒有扣款。
  • 請求到了、也做完了，只是回應在回程遺失：訂單已建立、錢已經扣了。

這兩種情況在 App 看來一模一樣，都是「逾時」。陳美華遇到的是第二種，下面這張時間軸把它畫出來：

App 只有兩個選擇，兩個都會出事。不重試，碰上第一種情況，顧客以為點好了，咖啡師卻從沒收到訂單；重試，碰上第二種情況，就是陳美華的重複扣款。因為 App 分辨不出是哪一種，「永遠不重試」和「永遠重試」都不對。

就算把 App 的自動重試關掉，問題也不會消失，因為同一個請求被送兩次的來源不只一個：

來源例子
使用者連點「結帳」按了兩下，送出兩個請求
網路與代理手機從 Wi-Fi 切到 4G，連線斷掉後 App 重送；負載平衡器在上游逾時後轉給另一台
佇列重送消費者處理完、還沒回報「這則處理好了」（ack）就當機，訊息再送一次（第 12 課）
webhook 重送金流通知「付款成功」，你回得太慢，對方再送一次（NestJS 課第 22 課）
排程兩台伺服器都在 03:00 跑同一個結算工作（第 14 課）

這張表的共同點是：送出的一方都有正當理由再送一次，因為它們都無法確定上一次有沒有成功。網路上的請求沒辦法保證「只送一次」。我們能控制的只有伺服器這一端：同一件事收到幾次，效果都只發生一次。這個性質叫做冪等。「做幾次都一樣」聽起來很直白，但「一樣」指的是什麼很容易誤解，下一節先把定義講精確。

「做幾次都一樣」到底保證什麼？

上一節說伺服器要做到「收到幾次，效果都只發生一次」，這就是冪等（idempotent）的定義：同一個請求執行一次或執行很多次，對伺服器狀態造成的效果相同。看兩個咖啡店的例子：「把訂單 42 設成已付款」做三次，訂單還是已付款，跟做一次一樣，所以冪等；「顧客點數加 10」做三次，就多了 30 點，跟做一次不一樣，所以不冪等。

定義裡說的是伺服器狀態，不是回應。第一次 DELETE /orders/42 回 204（刪除成功），第二次回 404（找不到），兩次回應不同，但做完之後訂單都不在了，伺服器的狀態相同，所以仍然冪等。這個區分在實務上有用：客戶端重試 DELETE 收到 404，不代表出錯，可能只是上一次其實已經成功。反過來，判斷一個操作冪不冪等，要看它對資料做了什麼，不能只看回應長得一不一樣。

HTTP 本身就有冪等的概念。規格 RFC 9110 替每個方法標了它在語意上是不是冪等，也就是規格要求伺服器照這個意思實作。客戶端和中間的程式就靠這個標記決定「這個請求失敗了能不能自動再送」：

方法冪等說明
GET、HEAD、OPTIONS、TRACE是安全方法（safe）：只讀不改，當然冪等
PUT是「把這個資源設成這個內容」，設幾次結果都一樣
DELETE是刪一次和刪兩次，資源都不在了
POST否「建立一張新訂單」，送兩次就兩張
PATCH否（RFC 5789）規格不保證冪等，但可以設計成冪等：「狀態改成 paid」重做沒差，「數量加 1」就不行

夾在客戶端和伺服器中間、負責轉送請求的程式叫做代理（proxy），像上一節表裡的負載平衡器就是一種。RFC 9110 對重試的規定是：客戶端不應（SHOULD NOT）自動重試非冪等的請求，除非知道這個請求實際上冪等，或能確認原本的請求沒有被套用；代理一定不能（MUST NOT）自動重試非冪等請求。陳美華的 App 自動重試了一個 POST，正好踩在這條規定上。

反過來也要小心：方法標成冪等，不代表你的實作冪等。把 PUT /orders/42/pay 寫成「呼叫金流扣款」，用了 PUT 也不會讓重複扣款消失。規格說的是你應該做到的語意，做不做得到，看程式怎麼寫。

所以開場事故的方向很清楚：下單一定要用 POST，那就要讓這個 POST「實際上冪等」，App 才能放心重試。最小版本的做法是冪等鍵：App 每次結帳時產生一個唯一的字串，放在請求裡一起送出，重試時沿用同一個；伺服器記住用過的字串，看到重複的就回傳第一次的結果，不再建單、不再扣款。這要多一張表來記住這些字串，還有清除它們的工作，第四節會完整實作。在那之前先看更便宜的做法：結帳流程裡有些步驟，只要寫法對了，本身就能重做也沒差，根本不需要冪等鍵。

結帳裡哪些步驟不用冪等鍵，自己就能重做？

陳美華的一次結帳，伺服器實際做了好幾件事：建立訂單、向金流扣款、把訂單改成已付款、替這張訂單集點。上一節的例子已經暗示，其中「改成已付款」和「集點」可以設計成重做也沒差。這種不靠額外的紀錄、靠操作本身的寫法就做到的冪等，叫做自然冪等。能這樣設計的地方，就不需要冪等鍵表。常用的手法有四種：

手法不冪等的寫法冪等的寫法
絕對值取代增量SET points = points + 10SET status = 'paid'（設成某個值，而不是加減）
條件更新（conditional update，也叫 compare-and-set，NestJS 課第 18 課）先 SELECT 狀態，程式判斷後再 UPDATEUPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'pending'，看影響了幾列
唯一約束＋已存在就跳過先查「這張訂單集過點了嗎」，沒有再 INSERTINSERT INTO stamp_awards (order_id, …) VALUES (…) ON CONFLICT (order_id) DO NOTHING
自然鍵付款表用自動遞增 id，同一張訂單可以有很多筆付款付款表以 order_id 當唯一鍵：一張訂單只能有一筆付款

逐列看它們怎麼擋住重做：

  • 絕對值取代增量：「設成 paid」不管做幾次，結果都是 paid；「加 10 點」每做一次就多 10 點。能用「設成某個值」表達的，就不要用「加減」。
  • 條件更新：把「現在是什麼狀態」寫進 WHERE。第一次執行時訂單是 pending，更新 1 列；重試時訂單已經是 paid，條件不成立，更新 0 列，什麼都沒變。程式看影響列數就知道這次有沒有真的改到。
  • 唯一約束＋已存在就跳過：集點沒辦法寫成「設成某個值」，因為點數本來就是累加的。改成先插入一筆「這張訂單集過點」的紀錄，order_id 設唯一約束；重試時插入撞到約束，DO NOTHING 跳過，後面的加點也就不做。
  • 自然鍵：用業務上本來就唯一的東西當鍵。一張訂單只該有一筆付款，那付款表就以 order_id 為唯一鍵，資料庫會擋掉第二筆。

表裡「不冪等的寫法」那一欄，第二、三列有個共同的形狀：程式先查詢，再依查詢結果決定要不要寫，叫做「先讀再寫」。它在只有一個請求時看起來沒問題，問題出在兩個請求同時進來。陳美華的重試和第一個請求就可能同時在跑：兩個請求都去查「這張訂單集過點了嗎」，都讀到「還沒有」，於是兩個都去加點。查詢和寫入之間隔著一次網路往返，另一個請求就是在這個空檔插隊的。

條件更新和 ON CONFLICT DO NOTHING 不會有這個問題，因為它們是原子的：「檢查」和「寫入」在資料庫裡一步完成，中間沒有空檔讓別人插隊。下面用一個每次存取都要等一次網路往返的假資料表重現兩種寫法，執行後比較兩行「陳美華的點數」：先讀再寫的那行多給了點數，原子操作那行剛好 3 點。

注意第二段的點數仍是增量（加 3），但它被「這張訂單只能集一次」的唯一約束保護住了，所以整體冪等。真實系統裡，插入集點紀錄和加點數要放在同一個交易：如果插入成功、加點前當機，交易回滾，集點紀錄也跟著消失，重試時才會再做一次；如果兩者分開提交，集點紀錄留下了、點數卻沒加，重試時會被唯一約束擋住，這張訂單的點數就永遠少了。

💡 實務上：先問「這段被呼叫兩次會怎樣」
Code review 時看到 SET stamps = stamps + 1、「先 SELECT 查有沒有、再 INSERT」，就是該停下來問的地方，咖啡店的集點、發兌換券、改訂單狀態都是常見位置。能用唯一約束或條件更新解決的，就不要急著加冪等鍵表：少一張要維護、定期清除的表。條件更新記得檢查影響列數：0 列代表條件不成立，可能是別人已經做過，也可能訂單根本不在那個狀態（例如已取消），要再查一次狀態決定回傳什麼，不是直接丟 500。替既有的表補唯一約束時，舊資料裡可能已經有重複，migration 會失敗，要先查出來、跟 PM 確認怎麼處理再上線。

改狀態和集點解決了，但結帳還剩兩步做不到自然冪等。第一步是建立訂單：陳美華可能真的想連買兩杯拿鐵，同樣內容的兩個請求不一定是重送，資料庫沒有任何唯一約束能分辨。第二步是扣款：它發生在金流的系統裡，不在你的資料庫，你的唯一約束擋不到，交易回滾也退不回錢。像扣款、寄簡訊這種發生在別人系統裡、無法用你的交易回滾的動作，叫做外部副作用（foreign state mutation）。這兩步都需要冪等鍵，而扣款這一步，還要把同一把 key 傳給金流。下一節從建立訂單開始。

建立訂單：伺服器怎麼認出「這是同一次結帳」？

上一節留下的問題是：兩個內容一模一樣的 POST /orders，伺服器分不出是「重送」還是「真的又買一杯」。光看內容永遠分不出來，因為差別不在內容，而在顧客的意圖：按下一次「結帳」是一個意圖，App 為了這個意圖送幾次請求都還是同一個意圖；顧客再按一次「結帳」，才是新的意圖。

伺服器看不到意圖，只有 App 知道，所以要讓 App 把它說出來。做法是：每一個意圖產生一個唯一的字串，叫做冪等鍵（idempotency key），下面簡稱 key。App 把它放在請求標頭裡；重試時沿用同一把，下一次結帳換新的。伺服器第一次看到某把 key 時，照常建單、扣款，並把回應存起來；之後再看到同一把 key，就不再做一次，直接回傳存下的那份回應。對陳美華的 App 來說，重試拿到的回應跟第一次完全相同，它不會知道、也不需要知道伺服器其實沒再做一次。

POST /orders
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
Content-Type: application/json

{"items":{"2":1},"storeId":1}

Idempotency-Key 這個標頭有一份 IETF 正在制定的規格，目前是草案，還不是 RFC（版本見課末「補充與查表」）。草案把標頭的值定義成 Structured Field 的 String，也就是要用雙引號包起來，所以範例的 key 有引號。key 本身通常用 V4 UUID：隨機產生的 128 位元識別碼，像上面那串，幾乎不可能撞到。

Node 課第 14 課做過冪等鍵的基本規則。伺服器收到請求時會遇到的情況，加上草案建議的狀態碼，整理如下：

情況伺服器怎麼做草案建議
這個端點要求 key，請求沒帶拒絕，回應裡連到冪等規則的文件400
第一次看到這把 key記下 key，執行，存下回應依結果
同 key、同內容，第一次已經完成不執行，回傳存下的回應同第一次
同 key，第一次還在處理中拒絕，請客戶端稍後再試409 Conflict
同 key、不同內容拒絕，這是 key 被誤用422 Unprocessable Content

後兩列要分開看。「還在處理中」發生在重試比第一個請求還快到：第一個請求還在扣款，重試就進來了。這時不能回放（還沒有回應可回放），也不能再做一次，只能請客戶端等一下再用同一把 key 來問。「同 key 不同內容」則是客戶端寫錯了，例如結帳成功後沒換 key，就拿去送下一張訂單；這種情況再試幾次都一樣，客戶端不該重試。兩者用不同的狀態碼，客戶端才能分辨「等一下再來」和「你的程式有 bug」。各家 API 在這裡的選擇不完全一樣，本課程照 IETF 草案（對照見課末）。

伺服器要記住 key，就需要一張表。下面是 PostgreSQL 的版本，有幾個欄位要到後面兩節才用得到，先看懂主鍵就好：

CREATE TABLE idempotency_keys (
  customer_id     bigint      NOT NULL,
  idempotency_key text        NOT NULL CHECK (length(idempotency_key) BETWEEN 1 AND 255),
  request_method  text        NOT NULL,
  request_path    text        NOT NULL,
  request_hash    text        NOT NULL,              -- 下一節的請求指紋
  recovery_point  text        NOT NULL DEFAULT 'started',
  locked_at       timestamptz,
  response_code   int,
  response_body   jsonb,
  created_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (customer_id, idempotency_key)
);

主鍵是 (customer_id, idempotency_key)，不是只有 key。key 是客戶端產生的，伺服器不能假設不同使用者不會撞到同一把：有 bug 的 App 可能把它寫死成同一個值。只用 key 當主鍵時，王小明的請求可能拿到陳美華的訂單回應，或被當成「同 key 不同內容」而失敗。所以 key 要限定在使用者範圍內：同一把 key，對不同顧客是不同的紀錄。request_method 和 request_path 記下這把 key 用在哪個端點，response_code、response_body 就是要回放的那份回應。

還有一個並發的問題：陳美華的重試可能在第一個請求還沒寫進 key 紀錄之前就到了，兩個請求都查「這把 key 有沒有紀錄」，都讀到沒有。這就是上一節的「先讀再寫」，解法也一樣，用原子操作 INSERT … ON CONFLICT DO NOTHING 判斷誰先到：插入成功的那個請求負責執行；插入失敗代表 key 已經存在，再讀出紀錄，依上面的表決定回放、409 或 422。另外，咖啡店的 API 跑在多台伺服器、多個程序上，同一把 key 的重試可能被負載平衡器送到另一台，所以 key 一定要存在大家共用的資料庫，不能放在某個程序的記憶體裡（Node 課第 24 課）。

這張表會一直長大，所以 key 不能永遠保存。草案允許 key 有保存期限，但有的話要把保存政策公開寫在 API 文件裡，客戶端才知道重試最晚要在什麼時候之前送出。實際的 API 保存多久、錯誤回應存不存，以 Stripe 為例整理在課末。

💡 實務上：只替「重複會造成損失」的端點加冪等鍵
咖啡店後台裡，結帳、付款、退款、儲值、發送兌換券是優先名單；改暱稱、更新營業時間這類 PUT 本來就重做沒差，不需要。設計 API 時可以先問：「這個請求被送兩次，誰會損失、損失多少？」會扣到錢或寄出東西的，才值得多一張表和一個清除程式。冪等鍵是前後端的約定，要寫進 API 文件：哪些端點要求 key、保存多久、409 和 422 代表什麼，App 和網頁的同事才會照同一套規則實作。

規則表裡還有一列沒說怎麼做：「同 key、不同內容」要回 422，伺服器得先能比較兩次請求的內容。這比看起來難，下一節處理。

同一把 key 送來的，怎麼確認是同一份內容？

要偵測上一節的「同 key、不同內容」，伺服器得把這一次的請求內容跟第一次的比較。把整份 body 存起來逐欄比對很浪費空間，常見做法是只存請求指紋（request fingerprint）：把請求內容算成一個固定長度的雜湊值。內容一樣，指紋就一樣；內容差一個字，指紋就完全不同。前面那張表的 request_hash 欄位存的就是它。

直覺的寫法是 sha256(JSON.stringify(body))。問題是同一份資料可以有不同的 JSON 字串：咖啡店的 iOS 和 Android App 各自組 JSON，欄位順序不一定一樣。下面這格執行後，先看「字串相同嗎？」那一行，再看最後兩行的順序：

第一段：最上層的鍵順序不同，字串就不同，指紋也不同。伺服器會把一次正常的重試誤判成「同 key 不同內容」，回 422，陳美華的 App 就把一次本來會成功的結帳當成錯誤。注意 items 裡的 '5'、'2' 反而自動排好了：JavaScript 物件的整數鍵（像 '2'、'10'）永遠依數字大小排在其他鍵前面，跟插入順序無關。

第二段說明為什麼不能「建一個依序插入鍵的新物件再 JSON.stringify」：你想要字串順序 '10'、'9'，JavaScript 卻給你 '9'、'10'。如果另一個用 Go、Python 寫的服務照字串順序算，兩邊的指紋就對不起來。

解法是正規化 JSON（canonical JSON）：一套固定的輸出規則，讓同樣的資料一定得到同樣的字串。規則有三條：物件的鍵遞迴地依固定順序排列；沒有多餘空白；陣列保持原順序，因為陣列的順序有意義，[拿鐵, 可頌] 和 [可頌, 拿鐵] 可以是不同的請求。鍵的順序要選一個各語言都算得一樣的。RFC 8785（JSON Canonicalization Scheme）用的是 UTF-16 碼位，剛好就是 JavaScript 陣列 sort() 對字串的預設順序。上面第二段已經示範過，物件的鍵順序靠不住，所以輸出要自己一段一段串字串。

正規化之後算 SHA-256（認證課第 2 課）：TextEncoder 把字串轉成位元組，crypto.subtle.digest('SHA-256', bytes) 回傳 32 個位元組，轉成 64 個字元的小寫 hex 存進 request_hash。

指紋的用途要分清楚：它只拿來比對同一把 key 的兩次請求，不是拿來去重。不能反過來用「內容相同就當成重複」：同一位顧客 10 分鐘內真的買了兩杯一模一樣的拿鐵，內容相同、意圖不同，這正是上一節要引入 key 的原因。認出重複靠 key，確認 key 沒被誤用才靠指紋。

到這裡，伺服器能認出重送，也能擋住誤用的 key；第一次做完的請求，重試時回放存下的回應就好。但規則表默默假設了一件事：第一次的請求要嘛做完了，要嘛還在做。如果它做到一半，伺服器就當機了呢？

扣款成功後伺服器當機，重試要從哪裡接著做？

上一節留下的情況在正式環境並不少見：部署重啟、記憶體不足、機器被回收，都會讓程序在任意一行停下來。而下單不是一個動作，是一串：建立訂單（自己的資料庫）→ 扣款（金流，外部）→ 把訂單改成已付款、排入寄收據的工作（自己的資料庫）。假設伺服器在扣款成功之後、記下扣款之前當機，key 紀錄裡沒有存下的回應，陳美華的 App 用同一把 key 重試時，伺服器該重新扣款嗎？只有「存下最後的回應」不夠回答這個問題，伺服器還需要知道上次做到哪一步。

直覺的做法是把整串包進一個資料庫交易：要嘛全做，要嘛全不做。這行不通，原因有兩個。第一，扣款不在你的資料庫裡：交易回滾只會撤銷你資料庫裡的修改，金流那邊的錢不會退回來。第二，呼叫金流要幾百毫秒到幾秒，這段時間交易一直開著、握著鎖，其他要動同一筆資料的請求都在等。結論是：呼叫外部服務不要放在交易裡。

Brandur Leach 仿照 Stripe 的設計提出了另一種做法。把整串工作切成幾個原子階段（atomic phase），每個階段是一個資料庫交易，交易裡除了做這個階段的事，還同時更新這把 key 的復原點（recovery point）：一個記錄「做到哪一步」的欄位，就是 key 表裡的 recovery_point。因為更新復原點和這個階段的寫入在同一個交易，兩者一定一起成功或一起消失，復原點永遠不會跟實際資料對不上。外部呼叫放在兩個交易之間。重試時先讀出這把 key 的復原點，從那裡繼續，做過的階段不再做。

這套設計對不對，要逐一檢查每個可能當機的位置，看重試時會發生什麼：

當機的位置資料庫裡的狀態重試時
交易 1 提交前交易回滾，沒有訂單、沒有 key 紀錄從頭開始，只會建一張訂單
交易 1 提交後、扣款前復原點 order_created沿用那張訂單，去扣款
扣款成功、交易 2 提交前復原點仍是 order_created，但金流已經扣了錢再呼叫一次金流，帶同一個 pay:<key>，金流認出重複，回傳原本那筆扣款
交易 2 提交後復原點 payment_captured不再扣款，直接做交易 3
交易 3 提交後、回應送出前復原點 finished，回應已存直接回傳存下的回應

第三列就是開場那種「扣款成功、還沒記下來」的情況，也是整個設計的關鍵。你的資料庫和金流之間沒有共同的交易，「扣款成功」和「記下扣款」之間一定有空隙，不管程式怎麼排都消不掉。補上空隙的是外部服務自己的冪等：金流也接受冪等鍵，你把由本地 key 衍生的 pay:<key> 傳過去，你的 key 跟金流的 key 一對一，重試幾次都是同一筆扣款。這正是第三節末尾說的「扣款這一步，還要把同一把 key 傳給金流」。所以挑金流、簡訊這類外部服務時，「支不支援冪等鍵」是要確認的條件。

剩下三件事要處理，才能讓這套流程在正式環境跑得住。

第一是交易 3 裡的寄收據。如果在交易外直接寄信，交易 3 提交前當機，重試時會再做一次交易 3，顧客就收到兩封收據；寄信也是外部副作用。做法是不直接寄，而是在交易 3 裡把「要寄這封信」寫進一張工作表，由背景程式讀出來送。這樣「排入寄信」和「復原點改成 finished」一起提交，要嘛都有、要嘛都沒有。這個做法叫 outbox，第 12 課會完整實作。

第二是兩個同 key 的請求同時在跑。規則表說第二個要回 409，伺服器得知道第一個「還在處理中」。做法是處理開始時設 locked_at = now()，第二個同 key 的請求看到有鎖就回 409。但程序當機時，鎖不會自己解開：locked_at 留在那裡，之後的重試永遠拿到 409，這把 key 就卡死了。所以鎖要有逾時：超過一段時間沒完成，就視為上一個處理者已經不在，允許下一次重試接手，從復原點繼續。第 14 課會把這種「有期限的鎖」正式叫做租約（lease）。

第三是清除舊的 key。建立訂單那一節說過 key 表會一直長大，要有一個背景程式定期清掉夠舊的紀錄。保存期限一定要比客戶端最長的重試時間長，否則 key 被清掉之後才到的重試，會被當成新請求，重複扣款又回來了。各家建議的期限見課末。

💡 實務上：復原點留給「跨外部服務、牽涉金額」的流程
大部分端點只動自己的資料庫，一個交易加上唯一約束就夠了，不需要切階段。結帳、退款、跟物流或發票系統串接這類「中間夾著外部呼叫」的流程，才值得付出更多狀態與測試的成本。設計審查時，資深工程師常做的事就是畫出上面那張「當機的位置」表：每個外部呼叫前後各當機一次，重試會發生什麼。串接新的金流或簡訊廠商前，先確認它支援冪等鍵、保存多久；不支援的話，要另外想辦法查詢「上次到底成功了沒」，這會讓設計複雜很多。

伺服器端到這裡完整了：認得出重送、擋得住誤用、做到一半也接得回來。但這一切都建立在一個前提上：App 送來的 key 是對的。如果陳美華的 App 每次重試都換一把新 key，伺服器做得再好也沒用。

App 端怎麼配合，才算真的「只扣一次」？

上一節的前提要靠 App 遵守，伺服器沒辦法替它做。App 端的規則都從同一句話推出來：一把 key 代表一個意圖。

  • 一個意圖一把 key。key 在使用者按下「結帳」那一刻產生，不是每次送出請求時產生。如果寫在送請求的函式裡，每次重試就會自動拿到新 key。
  • 重試沿用同一把。每次重試換新 key，伺服器會把重試當成新的意圖，等於沒有 key，陳美華還是會被扣兩次。
  • 成功或放棄之後，下一個意圖換新 key。拿舊 key 下第二張訂單，伺服器會回放第一張的回應，App 以為成功了，第二杯拿鐵卻沒被點到。
  • 連點共用同一個請求。第一個請求還在跑時使用者再按一次，回傳同一個進行中的 Promise（TypeScript 課第 12 課的單一飛行），不產生新 key，也不送第二個請求。
  • 收到 409 就等一下再用同一把 key 重試；收到 422 不要重試。409 代表第一個請求還在處理，等一下就會有結果；422 是程式的 bug（同一把 key 被拿去送不同內容），重試幾次都一樣。

伺服器和 App 都照規則做之後，陳美華的事故就不會再發生：App 逾時重試，帶的是同一把 key，伺服器回放第一次的回應，她只被扣一次款。那可以說這套系統做到了「恰好一次」嗎？

精確地說，不行。「恰好一次」（exactly-once）送達，在跨系統的網路上做不到。回想第一節：網路可能遺失訊息，所以要重送；重送就可能重複，而送出的一方永遠分不出是哪一種。訊息送達只有兩種保證可選，加上處理端的冪等，才得到我們要的結果：

送達語意做法結果
至多一次（at-most-once）不重試不會重複，但可能遺失
至少一次（at-least-once）重試直到確認不會遺失，但可能重複
效果上一次（effectively-once）至少一次 ＋ 處理端冪等訊息可能到很多次，效果只發生一次

這一課做的就是第三列：App 至少送一次（逾時就重試），伺服器靠冪等鍵讓效果只發生一次。請求確實可能到了兩次，只是第二次沒有造成任何效果。

會聽到有人說「某某系統支援 exactly-once」，要問清楚範圍。常見的訊息佇列系統 Kafka 也號稱支援 exactly-once，但它指的是 Kafka 內部：從 Kafka 讀、處理、再寫回 Kafka 這一段可以做到不重複（靠 Kafka 自己的交易）。消費者拿到訊息後去扣款、寄信，這些動作不在 Kafka 的交易裡，仍然要靠冪等鍵或去重，第 12 課會實作。

💡 實務上：上線後用指標確認冪等真的在運作
冪等鍵上線之後要看四個指標。每個端點的回放次數（同 key 回傳存下的回應），突然上升代表客戶端或網路在大量重試；409 與 422 的比例，422 不該出現，出現就是某個客戶端版本的 bug，要找 App 的同事查是哪一版；key 表的列數與清除進度，清除工作停了，表會一直長大；停在中間復原點太久的 key，代表有請求做到一半被放棄，可能有顧客被扣了款卻沒拿到訂單確認。

補充與查表

查表用，不用背。實作或串接時，以各自最新的官方文件為準。

  • IETF 草案：draft-ietf-httpapi-idempotency-key-header-08（2026-10-22 更新），還不是 RFC。標頭值是 Structured Field 的 String（要加雙引號）。缺 key 回 400、同 key 處理中回 409、同 key 不同內容回 422。key 可以有保存期限，有的話要把保存政策公開寫在 API 文件裡。
  • HTTP 方法的出處：方法的冪等語意定義在 RFC 9110 §9.2.2。PATCH 不在 RFC 9110 裡，定義在 RFC 5789。
  • Stripe（API v1，依官方文件）：key 最長 255 字元，建議用 V4 UUID，不要放 email 等個資。key 存滿 24 小時之後才可能被清除；清除之後再用同一把 key，會被當成新請求。端點開始執行之後才保存第一次的狀態碼與 body，包含 500：同 key 重試會一直拿到那個 500。參數驗證失敗、或撞上同 key 正在執行的請求時不保存，可以再試。會比對參數，不同就回錯誤。只有 POST 接受冪等鍵（GET、DELETE 本來就冪等）。
  • Stripe API v2：改成重試時把失敗或做一半的工作做完，再回傳更新後的結果。
  • Brandur Leach〈Implementing Stripe-like Idempotency Keys in Postgres〉：參數不符時回 409；本課程照 IETF 草案用 422，讓 409 只代表「還在處理中」，客戶端比較好分辨。文章建議由另一個背景程式清掉約 72 小時前的 key。另外建議（列為進階目標）加一個背景程式（completer），主動把被放棄的請求做完，客戶端沒再重試也不會卡在半路。

練習

練習 1：寫三個函式，替冪等鍵表準備資料。

  • canonicalJson(value)：輸出跟 JSON.stringify 一樣（沒有空白），但物件的鍵遞迴地用陣列 sort() 的預設順序排列，陣列保持原順序。要自己串接字串，不能「建一個依序插入鍵的新物件再 JSON.stringify」（整數鍵會被重新排序）。字串、數字、true／false、null 的寫法可以交給 JSON.stringify（引號、換行的跳脫才會一樣）。遇到 undefined、函式、bigint、NaN、Infinity（不管在第幾層）丟 TypeError。
  • fingerprint(body)：canonicalJson 之後用 TextEncoder 轉成位元組，算 crypto.subtle.digest('SHA-256', …)，回傳小寫 hex（起始程式附了 toHex）。
  • recordKey(customerId, method, path, key)：回傳 `${customerId}:${方法轉大寫}:${path}:${key}`，當作 key 表的查詢鍵；key 是空字串或超過 255 字元時丟 RangeError。

練習 2：起始程式提供一個假資料庫 createAsyncDb()，每個操作都會先等一次往返，同時進行的請求可以在中間插隊。它有非原子的 get／put，以及三個原子操作：insertIfAbsent（像 INSERT … ON CONFLICT DO NOTHING）、compareAndSet（像 UPDATE … WHERE 值 = 預期）、increment（像 SET v = v + n）。寫兩個函式：

  • awardStamps(db, orderId, customerId, stamps)：同一張訂單只能集點一次，就算同時被呼叫很多次。第一次回 'awarded' 並把點數加到 'stamps' 表（鍵是 String(customerId)），之後回 'already'。用 'stampAwards' 表（鍵是 String(orderId)）記錄哪些訂單集過點。
  • markPaid(db, orderId)：'orderStatus' 表（鍵是 String(orderId)，值是狀態字串）只有在 'pending' 時才改成 'paid'，回傳 { changed } 表示這次有沒有改到。

練習 3：寫 checkout(input, deps)，用復原點完成三個原子階段（型別都在起始程式裡）：

  • 先用 db.getKey(key) 讀這把 key 的紀錄。沒有紀錄就是 started：在一個交易裡 insertOrder 建立 pending 訂單，並 setKey 成 order_created（記下 orderId）。
  • order_created：呼叫 pay，冪等鍵固定是 `pay:${key}`、金額是 cartTotal(cart)；成功後在一個交易裡 markOrderPaid 並 setKey 成 payment_captured（記下 chargeId）。
  • payment_captured：在一個交易裡 enqueueJob({ type: 'receipt', orderId })，並 setKey 成 finished，存下回應 { status: 201, body: { orderId, chargeId, total } }。
  • finished：直接回傳存下的回應。

任何一步都可能丟錯（模擬當機），丟錯就讓它往外丟；呼叫端會用同一把 key 重試，你要從復原點繼續、做過的階段不重做。transaction 的 callback 不能是 async（不能在交易裡呼叫金流）。

練習 4：寫 App 端的 createCheckoutClient(api, newKey, isRetryable)，回傳 { submit(cart) }。規則：

  • 一次 submit 是一個意圖：只呼叫 newKey() 一次，每次呼叫 api(cart, key) 都帶這把 key。
  • isRetryable(err) 為 true 的錯誤最多重試 2 次（總共 3 次嘗試），沿用同一把 key；不可重試的錯誤直接 reject。三次都失敗就 reject 最後一次的錯誤。這題不用等待（退避在第 8 課做過）。
  • 上一次 submit 還在進行時再呼叫（連點），回傳同一個 Promise，不呼叫 newKey、不呼叫 api。
  • 這次 submit 結束（成功或失敗）後，下一次 submit 是新的意圖，用新的 key。

練習 5：RFC 9110 說 PUT 和 DELETE 是冪等的。下單用的 POST /orders 逾時了，App 可以直接自動重試嗎？

✓ c。RFC 9110 說客戶端不應自動重試非冪等的請求，除非知道它實際上冪等。帶冪等鍵、伺服器實作了去重，POST 就「實際上冪等」，可以重試；所以 d 說「永遠不能」太絕對。a 忽略了方法的語意。b 的交易只保證「一次請求」的原子性，擋不住第二次請求再做一遍。

練習 6：App 送出結帳後逾時，重試時用一把新產生的冪等鍵。伺服器會怎樣？

✓ b。伺服器認重複只靠 key：key 不同就是不同的意圖（顧客本來就可能連買兩杯一樣的拿鐵），所以 a 不會發生。422 是「同 key、不同內容」，c 剛好相反。重試一定要沿用同一把 key。

練習 7：同一把冪等鍵送來第二次，但購物車從 1 杯拿鐵變成 2 杯。伺服器應該怎麼做？

✓ a。key 代表一個意圖，內容不同代表客戶端誤用了 key。b 會讓顧客以為點了 2 杯、實際只有 1 杯，而且沒有任何錯誤訊號；c 等於忽略 key，重複扣款的問題又回來了。請求指紋就是用來偵測這種情況的。

練習 8：團隊打算用 Kafka 傳「付款請求」事件，消費者收到就呼叫金流扣款。有人說「Kafka 支援 exactly-once，所以只會扣一次」。對嗎？

✓ c。Kafka 文件的 exactly-once 是指 Kafka 內部：讀 Kafka、寫回 Kafka 這一段靠 Kafka 自己的交易做到不重複。b 的交易式 producer 也只保證寫進 Kafka 的訊息不重複，管不到金流。消費者扣款成功、還沒回報 Kafka「這則處理好了」就當機，訊息會再被處理一次，金流不在 Kafka 的交易裡，a 也錯在這裡。能做到的是「至少一次＋冪等＝效果上一次」：扣款時帶由訊息 ID 衍生的冪等鍵。第 12 課會實作冪等消費者。

常見錯誤

  • 以為只有 HTTP API 需要冪等：佇列消費者、webhook 處理、排程工作都會被重複觸發，都要冪等。
  • 先讀再寫判斷「做過了沒」：並發時兩個請求都讀到「還沒做」。用唯一約束、ON CONFLICT DO NOTHING 或條件更新，讓檢查和寫入在資料庫裡一步完成。
  • 冪等鍵沒有限定使用者：主鍵只用 key，別人送同一把 key 會拿到你的回應或互相衝突。主鍵用 (customer_id, key)。
  • 用 JSON.stringify 算指紋：鍵順序不同就被當成不同請求，正常的重試被誤判成 422。用正規化 JSON。
  • 用「排序後重建物件」做正規化：JavaScript 物件的整數鍵永遠依數字排在前面，{ '10': 1, '9': 2 } 重建後還是 9 在前。正規化要自己串字串。
  • 把呼叫金流放在資料庫交易裡：交易拉長、握著鎖，而且金流無法回滾。切成原子階段，外部呼叫放在交易之間，並傳由本地 key 衍生的冪等鍵。
  • 復原點和資料寫在不同的交易：一邊提交、一邊回滾，重試時依錯的復原點繼續。同一個階段的寫入和復原點一起提交。
  • 冪等鍵永遠不清除，或保存期限比客戶端重試的時間還短：前者讓表無限長大，後者讓遲來的重試被當成新請求。訂好期限並寫進 API 文件。
  • 每次重試產生新的冪等鍵：等於沒有 key。key 在使用者按下按鈕時產生一次，重試沿用。
  • 成功後沿用舊 key 下新訂單：伺服器回放上一張的回應，新訂單沒被建立。一個意圖結束後換新 key。

小結

  • 逾時之後，客戶端分不出「沒做」和「做了但回應遺失」，所以重試必然帶來重複；連點、代理、佇列、webhook、排程也都會重送。能控制的是伺服器：收到幾次，效果只發生一次。
  • 冪等讓同一件事做很多次，效果跟做一次相同；它講的是伺服器狀態，不是回應。HTTP 方法的冪等是語意，實作做不做得到看程式；POST 要「實際上冪等」才能自動重試。
  • 先讓操作本身冪等：絕對值取代增量、條件更新、唯一約束與 ON CONFLICT DO NOTHING、自然鍵。並發下要用原子操作，不要先讀再寫。
  • 天生不冪等的操作（建立訂單）和外部副作用（扣款）用冪等鍵：一個意圖一把 key，限定在使用者範圍，存在共用的資料庫。IETF 草案（還不是 RFC）建議缺 key 回 400、處理中回 409、同 key 不同內容回 422。
  • 請求指紋用正規化 JSON 加 SHA-256，確認同一把 key 送的是同一份內容；認出重複靠 key，不靠指紋。
  • 跨越外部服務的請求切成原子階段，每個交易同時更新復原點；外部呼叫放在交易之間，帶由本地 key 衍生的冪等鍵；後續工作用 outbox 在交易裡排入；處理中的鎖要有逾時，key 要定期清除。
  • App 端一個意圖一把 key、重試沿用、結束後換新。「恰好一次」跨系統做不到，能做到的是「至少一次＋冪等＝效果上一次」。
