階段 2：擴展：冗餘、快取與資料 · 第 4 課

冗餘與負載平衡：可用性的算術

咖啡店的下單 API 現在只跑在一台伺服器上。假設這台機器某天早上 8 點因為系統更新重開，重開要 3 分鐘。早上 8 點正好是第 1 課說的尖峰，照第 2 課估的每秒 3.33 筆，這 3 分鐘裡大約 600 筆訂單全部失敗，排隊的客人只能等，或改去隔壁買。

老闆問：「多開一台就好了吧？」這課就把這個問題追到底。多開一台確實有用，但要能回答老闆，得說出幾件事：多開一台到底能換到多少、兩台要放在哪裡才不會一起壞、壞掉一台之後剩下的扛不扛得住、前面負責分流量的那台機器怎麼分、它怎麼知道某台壞了並停止送流量過去、它自己壞了又怎麼辦。學完這課，你能拿算式回答老闆，也看得懂 nginx 和雲端負載平衡器的設定在防什麼。

這課的路線：
  1. 先算帳：99.9% 換成停機幾分鐘；下單背後還串了資料庫、Redis、金流，多開一台到底換到多少（開場問題的最小答案）。
  2. 兩台會不會一起壞、壞一台撐不撐得住：單點故障、故障域，以及「掉一個可用區之後」要幾台。
  3. 請求要送給哪一台：負載平衡演算法為什麼不是「選最閒的」，以及哪些情況會讓分流失準。
  4. 壞掉的機器怎麼踢出去：主動與被動健康檢查，為什麼剔除要有上限。
  5. 前面那台負載平衡器自己壞了怎麼辦，以及上線後怎麼確認備援真的有用。
這課會用到：
  • 部署課第 13 課的無狀態服務與水平擴展：服務不把使用者狀態存在單台機器上，請求送到哪一台都一樣，才能靠多開機器擴展。
  • 第 2 課的 N+1 與目標使用率：比剛好夠用多準備一台，平常只讓機器用到約 60%。

多開一台能換到什麼？先把可用性換成停機預算

要回答「多開一台有多少幫助」，先要有一把尺，量「現在有多可靠」和「改了之後有多可靠」。這把尺叫可用性（availability）：在一段期間裡，服務能正常使用的時間佔多少比例。一個月 30 天裡壞了 43 分鐘，可用性大約是 99.9%。

業界習慣用「幾個 9（nines）」來說可用性：99.9% 叫三個 9，99.99% 叫四個 9。問題是百分比很抽象，99.9% 和 99.99% 聽起來差不多，對老闆和 PM 都沒有感覺。所以要把它換成停機預算（downtime budget）：在這個目標下，一段期間內最多可以壞多久。算式是 (1 − 可用性) × 期間長度。以 99.9%、30 天為例：0.001 × 30 天 × 1440 分鐘 = 43.2 分鐘。

每多一個 9，預算就只剩十分之一。拿開場那次 3 分鐘的重開來對照：在三個 9 的目標下，它用掉當月 43.2 分鐘預算的 7%；在四個 9 的目標下，一次重開就用掉 4.32 分鐘的將近七成。四個 9 的預算連值班的人被叫醒、打開電腦的時間都不夠，所以要做到四個 9，只能靠機器自動恢復，不能靠人。（表格數字的出處見課末。）

用時間來算有一個盲點：它把每一分鐘當成一樣重要。凌晨 3 點掛 10 分鐘幾乎沒人受影響，早上 8 點掛 10 分鐘會打到大量訂單，但用時間算兩者都是 10 分鐘。所以正式環境更常用請求來算：可用性 = 成功的請求 ÷ 有效的請求。「有效」的範圍由團隊在 SLO 裡定義清楚。這個比例就是部署課第 22 課的 SLI，它會反映「什麼時候壞」。

下面用同一次事故比較兩種算法：咖啡店一天 6 萬筆訂單，早上 7:30～9:30 佔 40%，尖峰時掛 10 分鐘。執行後看最後一行「用掉預算」。

以時間算，10 分鐘只用掉 43.2 分鐘預算的 23%；以請求算，尖峰 10 分鐘就用掉 111%，一次就爆了。這就是為什麼 SLO 多半用請求來算：它跟使用者實際感受到的一致。對咖啡店來說，結論很直接：尖峰時段那台機器不能停，「多開一台」值得認真算。

但到目前為止，我們把下單 API 當成一個整體來算可用性。實際上它要能回應，背後還依賴好幾個服務，多開一台 API 只改善了其中一環。下一節把這些相依關係也算進來。

💡 實務上：先談「要幾個 9」，再談架構
PM 或老闆常說「系統不能掛」，資深工程師會把它翻成具體數字：結帳、下單這類直接影響營收的路徑要幾個 9，後台報表、員工排班頁面可以低一點。每多一個 9，機器、跨可用區、值班和自動化的成本都往上跳，所以目標要分功能訂，不要整個系統一刀切。也要注意你依賴的雲端服務自己承諾幾個 9，你的目標不可能比串聯起來的結果還高（下一節會算）。訂好之後，停機預算就是團隊的共同語言：本月預算快用完時，先暫停高風險上線、優先修穩定性。

下單 API 背後還有誰？相依怎麼把可用性往下拉

下單 API 收到請求後，要寫 PostgreSQL、讀 Redis、呼叫金流閘道，三個都正常，這筆訂單才會成功。這種「它壞了，你就跟著壞」的關係叫硬相依（hard dependency）。硬相依越多，能讓下單失敗的原因就越多。

把好幾個硬相依排成一條線，每一個都要正常才行，這叫串聯（serial）。串聯的可用性要相乘：假設各元件壞掉的時間互不相關，「全部同時正常」的機率就是各自正常機率的乘積。三個 99.99% 的元件串聯，結果是 0.9999 × 0.9999 × 0.9999 ≈ 99.97%，比其中任何一個都低。下單 API 再穩，整體也不會高過它最弱的那個依賴。

老闆說的「多開一台」是另一種結構：冗餘（redundancy），也叫並聯。同一件事準備兩份，任一份正常就能服務，只有兩份同時壞掉時才會停。所以算法反過來：先算「全部同時壞」的機率，也就是各自不可用率的乘積，再用 1 去減。兩台 99.9% 的 API 並聯：1 − 0.001 × 0.001 = 99.9999%。這就是開場問題的最小答案：多開一台，API 這一環的可用性從三個 9 跳到六個 9。

還有第三種關係。下單成功後會發簡訊通知顧客，但簡訊服務壞了，訂單照樣可以成功：把簡訊排進佇列，晚點再送。這種「它壞了，你有備案」的依賴叫軟相依（soft dependency）。軟相依不會拉低你的可用性，因為它的失敗不會變成你的失敗。常見的備案有三種：排進佇列晚點再做、改用快取裡的舊資料、把畫面上那個區塊藏起來。把硬相依改成軟相依，通常比加機器便宜。

加機器是一條路，另一條路是讓每次壞掉的時間變短。有些元件沒有公布可用性，這時可以用兩個量來估：MTBF（mean time between failures）是平均多久壞一次，MTTR（mean time to recover）是每次壞掉平均多久修好。一個週期裡，正常的時間是 MTBF，壞掉的時間是 MTTR，所以可用性 ≈ MTBF ÷ (MTBF + MTTR)。開場那台機器重開要 3 分鐘，這 3 分鐘就是 MTTR。

下面這格前兩行驗證串聯和並聯的算式，後兩行用 MTBF 和 MTTR 比較兩種元件：一種 150 天壞一次、1 小時修好，另一種 75 天壞一次、30 分鐘修好。執行後比較最後兩行。

第二組故障次數多一倍，但修復時間減半，可用性一樣。縮短修復時間跟減少故障一樣有效，而且常常更容易做到：自動重啟、自動切換、一鍵回滾、好的告警，都是在縮短 MTTR。

回到老闆的問題。兩台並聯的 99.9999% 有兩個前提：第一，兩台不會一起壞；第二，壞掉一台之後，剩下那台扛得住全部流量。這兩個前提只要有一個不成立，六個 9 就是紙上的數字。下一節逐一檢查。

💡 實務上：設計新功能時，先問每個依賴「它掛了會怎樣」
例如在下單流程加上「會員點數折抵」和「推薦加購商品」：點數服務掛了，可以先讓顧客不折抵照樣下單；推薦服務掛了，直接把那個區塊藏起來。這些降級行為要跟 PM 事先講好，因為畫面要怎麼呈現、會不會被客訴是產品決定，不是工程師臨時決定。code review 時看到新增一個同步呼叫外部服務的地方，資深會先問：這是硬相依嗎？有沒有逾時（第 8 課）？失敗時的畫面是什麼？

兩台會不會一起壞？單點故障與故障域

先處理第一個前提。在擔心「兩台會不會一起壞」之前，要先確定每個元件都至少有兩份。只有一份、壞了整個系統就跟著壞的元件，叫單點故障（SPOF，single point of failure）。找單點故障的方法很樸素：把架構裡每個元件列出來，一個一個問「它壞了會怎樣」。

咖啡店把 API 開成兩台之後，還有幾個常被漏掉的單點。第一個是負載平衡器本身：兩台 API 前面如果只有一台 nginx，它壞了兩台 API 都收不到請求（後面〈前面那台負載平衡器壞了怎麼辦〉會處理）。第二個是唯一的資料庫主機，主機掛掉時怎麼切到副本，見 PostgreSQL 課第 37 課。第三個是唯一的 NAT gateway。雲端上的後端機器通常放在外面連不進來的私有網路裡，它們要呼叫金流這類外部服務時，要經過一個叫 NAT gateway 的出口；出口只有一個，它壞了，所有對外呼叫都會失敗。最後一個不是機器：只有一個人知道怎麼部署，那個人休假時出事就沒人能修。

每個元件都有兩份了，還要看兩份會不會因為同一個原因一起壞。會一起壞掉的範圍叫故障域（failure domain）。由小到大是這樣：同一台主機上的兩個程序，主機斷電時一起壞；同一個可用區裡的兩台主機，機房斷電時一起壞；同一個區域裡的所有可用區，整區出事時一起壞。

圖裡的可用區（availability zone）是同一個雲端區域裡、電力與網路互相獨立的機房群（部署課第 18 課）。上一節的並聯公式 1 − 0.001 × 0.001 有個前提：兩台彼此獨立，一台壞掉不會讓另一台更容易壞。兩台放在同一個可用區，機房斷電時一起壞，這個前提就不成立，算出來的 99.9999% 也不成立。所以咖啡店的兩台 API 至少要分到兩個可用區。

分到不同可用區還不夠，因為圖右邊那一行：同一個壞掉的部署會跨過所有框框。多個元件因為同一個原因一起壞，叫相關性故障（correlated failure）。常見的原因是同一個有 bug 的版本部署到每一台、同一份錯誤的設定、同一張過期的憑證、同一個月底才觸發的時間 bug。這些原因跟機器放在哪裡無關，實際的大型事故多半屬於這一類。對付它的方法是分批部署、設定變更要能快速回滾，第 19、21 課會再談。

到這裡，第一個前提（兩台不會一起壞）的做法是：跨可用區擺放、分批部署。接下來檢查第二個前提：真的壞掉一份時，剩下的扛得住嗎？

壞掉一台之後，剩下的扛得住嗎？

第二個前提是容量。第 2 課說過，機器要留餘裕，目標使用率大約 60～70%。但那時只算了平常的狀況。冗餘的目的是讓系統在壞掉一份之後繼續服務，所以目標使用率要在壞掉一份之後還成立。這就是 N+1 真正的意思：N 台扛得住尖峰，再多 1 台給壞掉時用。

下面這格算兩個例子：3 台 API 平常各跑 70%，掛掉一台之後剩下的每台要扛多少；以及 3 個可用區、每區 2 台、平常 60%，整區掛掉之後每台要扛多少。

第一個例子剩下兩台要扛 105%。總負載是 2.1 台的量，分給 2 台，超過 100% 就是處理不完：佇列越排越長，請求逾時，客戶端重試，負載更高，剩下的機器也跟著倒（第 3 課的排隊曲線，第 11 課的連鎖故障）。原本只壞一台，結果三台全倒。第二個例子平常 60%，掉一區後 90%：沒倒，但第 3 課講過，使用率接近 100% 時排隊時間會暴增，這時的延遲已經很難看。所以容量規劃要以「掉一個故障域之後」為準，練習 2 會把它寫成函式。

到這裡，老闆的「多開一台」已經變成：至少兩個可用區、每區的機器數讓「掉一區之後」使用率還在目標內。機器準備好了，下一個問題是：請求進來時，要送給哪一台？

💡 實務上：上線前做一次「單點故障盤點」
把架構圖攤開，一個框一個框問「它壞了會怎樣、誰會發現、多久能恢復」，常常會挖出只有一台的資料庫主機、寫死某台 IP 的設定，或只有某位同事會操作的部署流程。不是每個單點都要立刻消除：咖啡店剛起步時，資料庫只有一台、但有自動備份和演練過的還原步驟，可能就夠了。重點是把風險寫下來，讓老闆知道「這裡壞了會停多久」，再依預算決定先補哪個。

請求進來，要送給哪一台？負載平衡演算法

顧客的手機只知道一個網址，不會知道後面有幾台 API。站在所有後端前面、接下每個請求再轉給其中一台的元件，叫負載平衡器（load balancer），例如部署課第 12 課的 nginx。它決定「這個請求給誰」的規則，叫負載平衡演算法。

演算法為什麼重要？上一節算容量時，假設流量平均分給每台。如果分得不平均，一台已經 100%、另一台還閒著，整體看起來容量夠，那一台上的請求卻在排隊逾時。演算法的工作，就是讓上一節的假設在現實裡成立。

最簡單的是 round robin：依序輪流，第 1 個請求給 1 號、第 2 個給 2 號、第 3 個再回到 1 號。nginx 沒設定時預設就是加權的 round robin。它的弱點在請求成本不一樣時：看菜單 5ms，結帳 2 秒，輪流分的結果可能是一台剛好拿到一串結帳請求，另一台拿到的都是看菜單，請求數一樣，忙碌程度差很多。機器規格不同時可以用加權 round robin，大機器分多一點，但權重是事先寫死的，反映不了當下誰比較忙。

要反映當下，就要看每台的即時狀態。最少連線（least connections）每次選「進行中請求最少」的那台，請求長短差很多時比較平均。直覺上更進一步，「每次都選全世界最閒的那台」應該最好，實際上它有個問題：負載資訊總是過時的，而且通常有好幾台負載平衡器各自做決定。大家在同一瞬間都看到「3 號最閒」，就一起把請求丟給 3 號，3 號瞬間爆量；下一刻大家又看到另一台最閒，一起湧過去。這種一群決策者同時做出同一個選擇、輪流把某台壓垮的現象，叫羊群效應（herding）。

解法是 P2C（power of two choices）：每個請求只隨機挑兩台，選比較閒的那台。因為有隨機，不同請求挑到的兩台不同，不會全部湧向同一台；因為有比較，又能避開很忙的機器。理論上兩台已經是最划算的點，多挑幾台改善很小（理論結果見課末）。

下面模擬羊群效應：5 台後端，這一秒內進來 20 個請求，但負載平衡器手上都是同一份舊快照。一種做法每次都選快照裡最閒的，另一種用 P2C。執行後比較兩行陣列，看哪一台被塞爆。

同樣拿過時的快照，全選最閒的把 20 個請求全部丟給 0 號；P2C 分散到好幾台，最忙的一台只到 12。實務上不用自己寫：Envoy 是常用的開源代理（proxy），常放在服務前面當負載平衡器，它的 least request 負載平衡在權重相同時就是 P2C（預設挑 2 台）；nginx 也有對應的寫法（版本與設定見課末）。練習 3 你會自己寫一個。

一致性雜湊同一個 key 永遠到同一台讓快取集中在某台（第 7 課）熱門 key 會讓單台過熱

演算法再好也會失準：黏性 session 與長連線

演算法能決定「這個請求給誰」，但有兩種情況會讓它根本沒機會決定。

第一種是黏性 session（sticky session）：負載平衡器記住使用者，讓同一個使用者的請求固定送到同一台。會用它，通常是因為應用程式把登入狀態存在那台機器的記憶體裡，換一台就認不得。代價是那台機器一壞，上面所有使用者的 session 一起消失，全部被登出；新機器加進來，也分不到已經黏在舊機器上的使用者。這就是部署課第 13 課要你把狀態放到 Redis 的原因：狀態不在機器上，送到哪一台都一樣，演算法才能自由分配。

第二種是長連線。負載平衡器分兩種層級：L4 只看 IP 與 port、轉送整條 TCP 連線；L7 看得懂 HTTP 內容、能逐個請求分流（細節在〈前面那台負載平衡器壞了怎麼辦〉）。HTTP/2 會讓同一個客戶端的很多請求共用一條長時間不關的 TCP 連線。所以 WebSocket 連線，或經過 L4 負載平衡器的 HTTP/2 連線，一建立就一直使用，負載平衡器只在建立連線時分配一次。新開的機器分不到既有連線，round robin 分得再平均也沒用。看得懂 HTTP/2 的 L7 負載平衡器可以把同一條連線裡的請求分到不同後端；WebSocket 的處理在第 17 課。

到目前為止，我們都假設每台後端都是好的。但機器會壞，負載平衡器如果不知道，就會繼續把請求送過去。下一節處理這件事。

💡 實務上：從一台變多台時，先找出藏在本機的狀態
多數團隊直接用雲端的負載平衡器，不自己架；真正花時間的是讓應用程式能被分流。咖啡店從一台擴成兩台後最常見的 bug 是「有時候會被登出」「上傳的圖片有時看不到」，原因是 session 存在記憶體、上傳檔案存在本機硬碟、排程工作每台各跑一次。擴充前先盤點這三類：session 放 Redis、檔案放物件儲存（例如 S3）、排程只讓一台執行。用黏性 session 繞過去看似最快，但機器一壞那批使用者就全掉，屬於技術債。

某台壞了，負載平衡器怎麼知道？健康檢查與異常剔除

假設咖啡店有 3 台 API，用 round robin 分流，其中一台的程序卡死了。負載平衡器不知道，照樣每 3 個請求送 1 個過去，結果三分之一的訂單失敗。機器有冗餘，請求卻沒有避開壞的那台，冗餘等於沒用。所以負載平衡器要能判斷哪台壞了，暫時不送流量給它。判斷方式有兩種。

第一種是主動檢查（active health check）：負載平衡器每隔幾秒主動打一次後端的檢查端點，例如 /ready（部署課第 13 課的 readiness，表示「這台準備好接流量了」）。好處是就算沒有流量，也能知道哪台壞了；壞處是檢查端點成功，不代表真實的下單請求會成功，例如 /ready 沒有碰到金流，金流連線出問題它也看不出來。

第二種是被動檢查，也叫異常剔除（outlier ejection）：不另外發請求，直接看真實請求的結果，某台的表現異常就暫時把它移出輪替。它看的就是使用者遇到的情況，但要有流量送過去才看得出來。nginx 的 max_fails 和 fail_timeout 就是最簡單的被動檢查：在 fail_timeout 這段時間內失敗 max_fails 次，就把這台視為不可用，同樣持續 fail_timeout 那麼久。預設值是 1 次、10 秒。

Envoy 的異常剔除規則比較完整，是設計時的好參考。預設是：同一台連續 5 次回 5xx 就剔除；剔除時間 = 基本 30 秒 × 這台第幾次被剔除，一直壞就越踢越久，最長 300 秒；最多只能剔除 10% 的主機，已經到上限就不再剔除（倍數怎麼降回來見課末）。

前兩條很好懂，第三條的上限乍看奇怪：壞的機器為什麼不全部踢掉？想像健康檢查本身出 bug，或資料庫慢了一下，讓每台都回 503。沒有上限的話，負載平衡器會把所有機器都踢掉，原本只是部分請求失敗，變成 100% 失敗。剔除是為了避開「少數幾台壞掉」，一大批機器同時看起來壞掉，問題多半不在機器本身，踢掉它們沒有幫助。

Envoy 還有第二道保險 panic threshold（預設 50%）：健康主機的比例低於它時，乾脆忽略健康狀態，把流量分給所有主機。理由是「一半以上都壞了」比較可能是檢查出錯，而不是機器真的全壞；就算真的壞了大半，把全部流量壓在剩下的少數機器上，也只會把它們一起壓垮，這就是〈壞掉一台之後，剩下的扛得住嗎？〉那節 105% 的情況。

liveness 不要檢查依賴：部署課第 13 課講過，liveness 失敗會讓程序被重啟。如果 liveness 去查資料庫，資料庫一慢，所有副本同時被重啟，小問題變成全面停機。依賴的狀態放在 readiness，而且要有上面說的剔除上限。

後端的冗餘和剔除都處理好了。回頭看最前面：所有請求都要先經過負載平衡器，如果只有一台，它就是〈兩台會不會一起壞？〉那節單點故障清單上的第一項。

前面那台負載平衡器壞了怎麼辦？

咖啡店如果自己架一台 nginx 當負載平衡器，它壞了，後面幾台 API 再健康也收不到請求。負載平衡器也需要冗餘，常見的做法有三種。

第一種，也是多數團隊的選擇，是直接用雲端的負載平衡器，例如 AWS 的 ALB、NLB。它本身由雲端業者跨可用區部署，你不用處理它自己的冗餘；你要做的是讓它啟用多個可用區，並在每個可用區都放後端機器，這樣掉一區時它還有地方送。

第二種是自己架多台負載平衡器，這時要先分清楚兩種層級。L4 負載平衡只看 IP 與 port，轉送的是 TCP 連線，看不懂裡面的 HTTP，所以快，也能轉任何協定。L7 負載平衡看得懂 HTTP，能依路徑、標頭分流，能改寫標頭，也能做 TLS 終止：在負載平衡器這裡解開 HTTPS，後面用一般的 HTTP 轉給後端。常見組合是前面一層 L4，把連線分給後面多台 L7（例如多台 nginx），這樣任何一台 nginx 壞了，L4 會把流量送給其他台。前面〈演算法再好也會失準〉講長連線時提到的 L4 和 L7，就是這裡的兩層。

第三種是 DNS 輪詢：同一個網域回傳多個 IP，客戶端自己挑一個連。它很簡單，但有一個限制：DNS 的查詢結果會被客戶端和中間的伺服器快取，每筆紀錄都帶著一個 TTL，表示這筆紀錄可以被快取多久。某個 IP 壞了，要等 TTL 過了，客戶端才會重新查詢、拿到新的 IP 清單，在那之前仍然有人連到壞掉的 IP。另一種在網路層做的方式（anycast）見課末。

到這裡，架構圖上每一層都有備援了。但備援畫在圖上不等於真的能用，最後一節談上線後怎麼確認。

上線後，怎麼確認備援真的有用？

備援平常用不到，所以它壞掉也不會有人發現，直到真的需要它的那天。上線後要持續看四件事：

  • 每台後端各自的錯誤率與延遲：整體平均正常時，可能有一台特別差，被平均蓋掉了。
  • 剔除事件：哪台、什麼時候、被剔除幾次，有沒有碰到剔除上限。碰到上限通常代表問題不在單台機器。
  • 掉一個可用區後的容量餘裕：把尖峰負載除以「去掉最大一區後」的機器數，看是否低於目標使用率。機器數會隨擴縮改變，這個數字要持續看，不是上線時算一次。
  • 故障演練：真的關掉一台、一個可用區，確認剔除、切換、容量都如預期。沒演練過的備援，常常在需要時才發現不能用。

故障演練最好先在 staging 做。staging 是正式上線前、設定跟正式環境相同的測試環境，在那裡關機器不會影響真實顧客。確認流程沒問題後，再挑離峰時段在正式環境做一次。

現在可以完整回答老闆了：多開一台有用，但要開在另一個可用區、數量要算到「掉一區還撐得住尖峰」，前面放跨可用區的負載平衡器，用 P2C 分流，用有上限的異常剔除踢掉壞的機器，最後實際關一台演練過，才算真的不怕早上 8 點那 3 分鐘。

練習

練習 1：寫兩個可用性函式。downtimeMinutes(availability, days) 回傳停機預算的分鐘數：(1 − availability) × days × 1440。systemAvailability(node) 計算一棵相依樹的可用性：component 回傳自己的 availability；serial（硬相依串聯）相乘；redundant（獨立冗餘）是 1 − Π(1 − a)；soft（有備援的軟相依）視為 1，但裡面的節點一樣要檢查合法。availability 不在 0～1 之間（含 NaN）時丟 RangeError；serial、redundant 的 parts 是空陣列時也丟 RangeError。

練習 2：寫 nodesForZoneFailure(input)，算出「整個可用區掛掉之後還撐得住尖峰」最少要幾台。機器輪流放在各可用區（第 i 台放在 i % zones），所以一區掛掉時最多失去 Math.ceil(n / zones) 台。回傳最小的 n，使得 (n - Math.ceil(n / zones)) * perNodeCapacity * maxUtilization >= peakLoad（照這個順序計算，結果才跟測試一致）。zones 不是 2 以上的整數時丟 RangeError（只有一個可用區，整區掛掉就什麼都不剩）；peakLoad、perNodeCapacity 不是正數，或 maxUtilization 不在 (0, 1] 時也丟 RangeError。

練習 3：寫 pickP2C(backends, random)。先只留下 healthy 的後端（設為 h，數量 n），沒有健康的回傳 null；只有一台時直接回傳它的 id，不呼叫 random。否則 i = Math.floor(random() * n)、j = Math.floor(random() * (n - 1))，j >= i 時 j 加 1（保證兩台不同）；回傳 h[i]、h[j] 中 inFlight 比較小的那台的 id，一樣時回傳 h[i]。random 由呼叫端傳入，不能用 Math.random，也不能改動傳進來的陣列。

練習 4：完成 OutlierDetector（被動健康檢查）。report(host, status)：500～599 讓這台的連續失敗數加 1，其他狀態碼歸零；被剔除期間收到的回報（剔除前就送出、晚到的請求）直接忽略。連續失敗數達到 consecutive5xx 時，先把連續失敗數歸零，再嘗試剔除：如果目前被剔除的台數已經達到 Math.floor(hosts.length * maxEjectionPercent / 100)，就不剔除；否則剔除，剔除時間 = baseEjectionMs × 這台第幾次被剔除。isEjected(host)：now() 到達剔除結束時間就自動恢復。available() 依原本順序回傳沒被剔除的主機。時間一律用 opts.now()。這是簡化過的規則：Envoy 的上限比較方式、剔除倍數會降回來等細節不同。

練習 5：下單 API 本身 99.99%，硬相依 PostgreSQL 99.95%、Redis 99.9%、金流 99.9%。下單的理論可用性大約是多少？

✓ 硬相依是串聯，每個都要好才行，所以相乘：0.9999 × 0.9995 × 0.999 × 0.999 ≈ 0.9974，每個月約 1.9 小時的停機預算，比任何一個元件都差。平均或取最差都高估了。要提高它，可以減少硬相依（改成軟相依）或提高最弱的幾個。

練習 6：兩台 99.9% 的 API 放在同一個可用區，用同一條部署流程同時更新。可以說它們的組合可用性是 1 − 0.001² = 99.9999% 嗎？

✓ 並聯公式的前提是「彼此獨立」。機房斷電、同一個有 bug 的版本、同一份錯誤設定都會讓兩台同時壞，這叫相關性故障。要讓公式比較接近事實，要分散到不同可用區、分批部署。健康檢查只能把壞的踢掉，兩台一起壞時它也沒辦法。

練習 7：3 台 API 平常各跑在 70% 使用率。其中一台掛掉會怎樣？

✓ 總負載是 3 × 70% = 2.1 台的量，分給 2 台就是每台 105%，超過能處理的上限，佇列越排越長，逾時引發重試讓負載更高。容量要以「掉一台（或一個可用區）之後」的使用率來規劃。負載平衡器預設不會幫你限流，限流與負載卸除在第 10 課、第 11 課。

練習 8：健康檢查程式出了 bug，讓每台機器都回 503。負載平衡器把所有機器都剔除，服務全掛。哪個設計最能避免這種事？

✓ Envoy 預設最多剔除 10%、健康比例低於 50% 時進入 panic 模式忽略健康狀態，就是為了這種情況。更嚴格的檢查會更快把機器踢光；liveness 檢查資料庫會讓資料庫一慢所有副本都被重啟，是反效果。

常見錯誤

  • 以為多一份就是冗餘：兩份放在同一台主機、同一個可用區，或用同一次部署一起更新，會一起壞。冗餘要跨故障域，部署要分批。
  • 只算正常時的容量：平常 70% 很安全，掉一台就超過 100%。N+1 要算「壞掉一台／一個可用區之後」的使用率。
  • 依賴越加越多卻沒算可用性：每多一個硬相依就多一個讓你掛掉的機會。能改成軟相依（佇列、快取的舊資料、隱藏區塊）就改。
  • 健康檢查沒有上限地剔除：檢查本身出錯、或共同的依賴慢了一下，會把所有機器踢光。要有最多剔除比例或 panic threshold。
  • liveness 檢查資料庫：資料庫一慢，所有副本同時被重啟。依賴放在 readiness。
  • 負載平衡器只有一台：它自己就是單點故障。用雲端跨可用區的負載平衡器，或至少兩台加上切換機制。
  • 每次都選全域最閒的機器：資訊過時時，多台負載平衡器會同時湧向同一台。用 P2C。
  • 長連線用 round robin：連線建立後就不再分配，新機器分不到流量（第 17 課）。

補充與查表

數字的出處

停機預算表的數字出自 Google SRE 書的可用性表。第二節程式格裡的串聯、並聯和「150 天壞一次、1 小時修好」三個數字出自 AWS Well-Architected 可靠性支柱；「75 天壞一次、30 分鐘修好」是拿來對照的。

P2C 的理論結果

把 n 個請求隨機分給 n 台時，最忙的那台大約有 log n / log log n 個；改成挑兩台選比較少的，降到 log log n / log 2 左右（Mitzenmacher 等人 2001 年的綜述）。從挑一台變挑兩台是指數級的改善，再多挑幾台只多一個常數倍的改善，所以兩台是最划算的點。

nginx 與 Envoy 的對應設定

  • nginx 1.15.1 起有 random two least_conn：隨機挑兩台，選連線比較少的那台，作法跟 P2C 相同。
  • Envoy 的異常剔除倍數：一台被剔除後恢復，如果之後一直正常，下次剔除用的倍數會慢慢降回來，不會永遠記著過去被踢過幾次。

anycast

anycast 是在網路路由層做的分流：同一個 IP 在多個地點同時宣告，網路路由會把封包送到最近的那個地點。某個地點壞了，路由會改送到其他地點，不用等 DNS 的 TTL。CDN 常用這種方式。

小結

  • 可用性換成停機預算才有感：99.9% 每 30 天 43.2 分鐘、99.99% 只有 4.32 分鐘。以請求計算時，尖峰的停機特別貴，所以 SLO 多半用請求算。
  • 硬相依串聯要相乘，比任何一個都低；獨立的冗餘是 1 − 不可用率的乘積，兩台 99.9% 並聯是 99.9999%；軟相依不拉低可用性，把硬相依改成軟相依常比加機器便宜。
  • 可用性 ≈ MTBF ÷ (MTBF + MTTR)，縮短修復時間跟減少故障一樣有效。
  • 冗餘公式假設獨立：先找出單點故障，再讓冗餘跨故障域（主機、可用區），並提防相關性故障（同一個部署、同一份設定）。
  • 容量以「掉一個可用區之後」的使用率規劃，不然壞一台會拖垮剩下的。
  • 負載平衡器拿到的負載資訊總是過時，「全選最閒」會造成羊群效應；P2C 隨機挑兩台選比較閒的，Envoy 的 least request 在權重相同時就是它。黏性 session 和長連線會讓演算法失效。
  • 健康檢查分主動與被動；異常剔除要有連續失敗門檻、逐次加長的剔除時間和最多剔除比例，panic threshold 防止把機器踢光。
  • 負載平衡器本身也要冗餘：雲端跨可用區的負載平衡器、L4 加多台 L7，或 DNS 輪詢（受 TTL 限制）。沒演練過的備援不算數。
