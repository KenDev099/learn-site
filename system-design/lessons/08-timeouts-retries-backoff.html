階段 3：可靠性：失敗是常態 · 第 8 課

逾時、重試與退避：失敗之後怎麼辦

週年慶早上 8 點，咖啡店的下單 API 每秒收到約 50 筆訂單，每筆都要呼叫金流閘道扣款。某天金流那邊出了狀況，回應從 200ms 變成 30 秒才回來。下單 API 的程式一行都沒改，卻開始大量逾時、記憶體上升、連菜單都打不開。接著值班同事發現：App 和 API 都在「失敗就馬上再試一次」，金流剛恢復一點又被重試的流量壓垮。

前幾課把系統變大、變多台。從這一階段開始，我們假設失敗是常態：網路會掉、下游會慢、機器會重開。這一課從頭到尾只處理一件事：把訂單服務裡「呼叫金流扣款」的那一段改好，讓下次金流再出狀況時，壞掉的只有扣款，咖啡店的其他功能照常運作，金流恢復時也不會被我們自己的重試壓垮。要改好它，得依序回答三個問題：要等多久（逾時）、要不要再試（重試）、隔多久再試（退避）。

這課的路線：
  1. 金流變慢為什麼連菜單都打不開：一個沒有逾時的呼叫怎麼把整台伺服器拖垮。
  2. 逾時要訂幾秒：照下游延遲的百分位數訂，再照呼叫端剩下的時間往下傳（deadline），這節結束時先給三個問題的最小答案。
  3. 金流逾時了，可以再送一次嗎：哪些錯誤值得再試，為什麼扣款的 POST 逾時不能直接重送。
  4. 隔多久再試、伺服器叫你等時怎麼辦：指數退避、jitter 與 Retry-After。
  5. 每一層都重試會怎樣、整套怎麼收尾：重試放大與重試預算，重試和其他工具的分工，上線後看哪些指標。
這課會用到：
  • Node 課第 17 課的呼叫外部 API：fetch 會遇到哪幾種錯誤、用 AbortSignal.timeout 設逾時、基本的 withRetry。
  • TypeScript 課第 11 課的取消：AbortController 發出取消訊號，AbortSignal.any 把多個訊號合成一個，任一個觸發就取消。
  • 第 3 課的 Little's Law 與百分位數：同時在系統裡的請求數 = 每秒請求數 × 每個請求停留的秒數；p99 是 100 個請求裡只有 1 個比它慢的那個延遲。

金流變慢，為什麼連菜單都打不開？

先看開場事故的第一個怪現象：出問題的是金流，看菜單根本不呼叫金流，為什麼也打不開？原因是一個還在等回應的請求，會一直佔著資源。訂單服務呼叫金流之後，這個請求在等待期間仍然佔著一塊記憶體（請求內容、還沒做完的程式狀態）、一條連到金流的連線，如果它在交易裡呼叫金流，還佔著一條資料庫連線。這些資源都有上限：資料庫連線池是事先開好、數量固定的一組連線（Node 課第 20 課），借光了，後面的請求只能排隊。

同時有多少請求在等，可以用第 3 課的 Little's Law（L = λW）算：每秒進來的請求數乘上每個請求停留的秒數。執行下面的程式，看三種情況下「同時卡著」的數字差多少：

這也說明為什麼慢比掛掉更危險。金流如果直接掛掉，連線馬上被拒絕，請求立刻失敗，資源也立刻釋放，影響只限於扣款。金流變慢時，每個請求都還「有希望」，所以沒有人放手，資源被一點一點吃光，最後連不相干的功能一起倒。

要讓請求放手，就要設逾時（timeout）：等超過這個時間就放棄，回報失敗，把資源還回去。上面程式的第三行就是答案：同樣是金流卡住，設了 2 秒逾時，同時卡著的只有 100 個，因為每個請求最多停留 2 秒。逾時沒辦法讓金流變快，它做的是替等待設上限，把損害限制在扣款這一個功能裡。

設逾時時要知道，一個網路呼叫的「等待」分成好幾段，對應不同的逾時：

  • 連線逾時（connect timeout）：連不上對方多久就放棄。只管「建立連線」這一段，連上之後就不管了。
  • 讀取逾時（read timeout）：連上之後，兩次收到資料之間最多等多久。只要對方每隔一段時間送一點資料，它就不會觸發，所以整個回應可以拖得很久。
  • 整體逾時：從送出請求到收完整個回應的上限。

保護資源要靠的是整體逾時，因為只有它限制了「這個請求最多佔著資源多久」。Node 課第 17 課講過，Node 的 fetch 沒有整體逾時，要自己傳 AbortSignal.timeout(ms)。規則只有一條：每個網路呼叫都要有逾時，包含資料庫查詢、Redis、內部服務，不只是呼叫第三方。所以修好金流呼叫的第一步，是在 fetch 加上 AbortSignal.timeout。問題是這個數字要填多少，下一節回答。

💡 實務上：接手專案時先盤點「哪些呼叫沒有逾時」
除了上面的 fetch，很多套件預設也不逾時，例如 axios 的 timeout 預設是 0（不限制），PostgreSQL 的 statement_timeout 預設也是 0，要自己設定。資深工程師 code review 時會問：「這個呼叫最久會等多久？逾時的時候使用者看到什麼？」咖啡店後台常見的事故是報表頁的慢查詢卡住連線池，結果收銀機下單也跟著失敗，跟開場的金流事故是同一種病。逾時的數字最好集中寫在設定裡、附上依據（看了哪個監控），之後才知道要不要調。

逾時要訂幾秒？先看下游延遲，再看呼叫端還剩多少時間

上一節決定了金流呼叫一定要有逾時，接著是數字。這個數字兩頭都會出事：訂太短，金流其實正常、只是這一次稍微慢一點的請求也被當成失敗，使用者明明付得了錢卻看到錯誤；訂太長，又回到上一節的問題，金流一變慢，資源就被卡住。

AWS Builders' Library 的〈Timeouts, retries, and backoff with jitter〉給的做法，是先決定能接受多少誤判，再拿下游延遲對應的百分位數當逾時。誤判指的是「下游其實會成功，只是我們等不及」。如果逾時訂在金流的 p99.9，代表正常情況下 1,000 個請求只有 1 個會比它慢，也就是只有 0.1% 的正常請求被誤判成逾時。能接受 0.1% 誤判，就用 p99.9；能接受 1%，就用 p99。咖啡店從監控看到金流的 p99.9 是 1.2 秒，扣款的逾時就訂 1.2 秒左右，而不是拍腦袋寫 30 秒或 100ms。下游的延遲會隨著版本、流量改變，所以這個數字要定期依監控重新檢查。

只看單一呼叫還不夠，因為扣款不是使用者直接呼叫的。使用者按下「送出訂單」，App 最多等 1 秒；請求先經過 API 閘道，再到訂單服務，訂單服務才呼叫金流。如果每一層各自訂 1 秒逾時：訂單服務自己花了 900ms 才呼叫金流，金流又可以用滿 1 秒，總共 1.9 秒。App 在 1 秒時就放棄了，後面那 900ms 不管成功失敗都沒人收，全是白工，而且還佔著資源。

問題出在每一層都以為自己有完整的 1 秒。解法是 deadline：不再說「我最多等多久」，而是說「這個請求最晚要在哪個時間點完成」。最外層定下 deadline 之後，每一層往下傳的是「還剩多少時間」，這叫 deadline 傳遞（deadline propagation）。Google SRE 書〈Addressing Cascading Failures〉的作法是：每一層拿到剩下的時間，減掉自己已經用掉的，再扣一點餘裕（margin），留給回應從下游傳回來、自己再處理一下的時間；剩下的時間太少就直接不做，因為做完也沒人收。下圖是咖啡店的例子：

到目前為止講的逾時都是「一次呼叫」。後面要加上重試，一個請求可能會呼叫金流好幾次，所以要先分清楚兩種限制：單次逾時（per-attempt timeout）限制一次嘗試，例如前面依 p99.9 訂的 1.2 秒；總期限就是 deadline，限制「所有嘗試加上中間的等待」。每次嘗試的逾時取兩者的較小值：剩下 650ms 時，這一次最多等 650ms，不會因為單次逾時是 1.2 秒就等到 1.2 秒。

到這裡，開場的三個問題可以先有一版最小的答案：

  • 要等多久：逾時照下游延遲的百分位數訂（例如 p99.9），而且不超過呼叫端剩下的時間。
  • 要不要再試：只重試暫時性錯誤；非冪等的請求沒有冪等鍵就不自動重試。
  • 隔多久再試：每次重試前等的時間加倍，再加上隨機。
💡 實務上：deadline 怎麼在服務之間傳
gRPC 內建 deadline，客戶端設定的 deadline 會轉成 grpc-timeout 標頭送到伺服器端。HTTP 沒有標準標頭，團隊通常自訂一個（例如 X-Request-Deadline），裡面放剩餘毫秒數；放剩餘時間比放絕對時間好，因為不怕兩台機器的時鐘不一致。在 Node 裡，訂單服務收到剩餘時間後，用 AbortSignal.timeout(剩餘) 變成 signal，再用 AbortSignal.any 跟「客戶端斷線」的 signal 合併（TypeScript 課第 11 課），往下傳給呼叫金流、查資料庫的每一個呼叫。這樣使用者關掉 App 或時間用完，整條鏈都會一起停下來。

第一個答案這兩節已經講完。第二個答案裡的「暫時性錯誤」「冪等」還沒解釋，而扣款剛好是最需要想清楚的那種請求，下一節就從「金流逾時了，能不能再送一次」開始。

金流逾時了，可以再送一次嗎？

有了逾時，金流變慢時訂單服務會在時間內放棄。放棄之後，最自然的念頭是「再送一次」，這正是開場事故裡 App 和 API 做的事。要不要再送，得先看失敗的是哪一種。

很多失敗是暫時性錯誤（transient fault）：問題出在當下的狀況，等一下再試就會好，例如逾時、連線被重設、503 Service Unavailable（伺服器暫時無法處理）。另一種是永久錯誤：問題出在請求本身，再試幾次結果都一樣，例如 400（請求格式錯）、404（找不到）、409（衝突）、422（內容不合規則）。重試永久錯誤不會成功，只會增加對方的負擔。

暫時性錯誤為什麼值得重試？第 4 課算過，硬相依的可用性相乘：下單要經過三個 99.9% 的服務，整體只剩約 99.7%。但這些失敗大部分只持續一瞬間，例如某台機器剛好在重開、某條連線剛好被重設，再試一次多半就會打到正常的機器而成功。所以加上重試，使用者實際感受到的成功率會比 99.7% 高。代價是多送的請求，這一節和後面兩節都在處理這個代價。

不過對扣款來說，比錯誤種類更重要的問題是：重試會不會造成重複的副作用。副作用指的是請求對外界造成的改變，例如扣了一筆錢、建了一張訂單。描述這件事的詞是冪等（idempotent）：同一個請求做一次跟做很多次，伺服器的最終狀態一樣。「把訂單 42 的狀態設成已取消」做幾次都一樣，是冪等的；「扣 110 元」做兩次就是扣 220 元，不是冪等的。

HTTP 方法的規格 RFC 9110 §9.2.2 規定：PUT、DELETE 和安全方法（GET、HEAD、OPTIONS、TRACE）是冪等的，POST 和 PATCH 不是。RFC 9110 也規定：客戶端不應（SHOULD NOT）自動重試非冪等的請求，除非知道它實際上冪等，或能確認原本的請求沒被套用；代理（proxy）一定不能（MUST NOT）自動重試非冪等請求。

扣款用的是 POST，所以它落在最危險的那一格。原因在於逾時能告訴你的事很少：

逾時不代表對方沒收到。POST /orders 逾時，可能是請求沒到，也可能是訂單已經建立、扣款也成功了，只是回應在路上遺失。直接重試就可能扣兩次款。POST 要能安全重試，得帶冪等鍵（Idempotency-Key，Node 課第 14 課介紹過，下一課深入做）。

失敗重試？理由
呼叫端自己取消（AbortError）不重試使用者離開頁面或上游已經放棄；也不該記成錯誤或告警
逾時、連線失敗可以暫時性；非冪等方法要有冪等鍵
408 Request Timeout可以伺服器等請求內容等太久
429 Too Many Requests可以，照 Retry-After被限流（RFC 6585，第 10 課）；不照它等只會一直被擋
500、502、503、504可以伺服器或閘道暫時出錯；503 常附 Retry-After
501 Not Implemented不重試伺服器不支援這個方法，再試也一樣
400、401、403、404、409、422不重試請求本身的問題；401 要先重新取得 token，那是另一條流程

表裡最容易被忽略的是第一列。呼叫端取消，代表上游已經不要這個結果了，例如使用者關掉頁面、或上一節的 deadline 到了。這時重試是替沒人要的結果做白工，把它記成錯誤或觸發告警，也會讓值班的人以為系統壞了。取消是正常的結束。

決定了「哪些可以重試」，還要決定「最多試幾次」。Google SRE 書〈Handling Overload〉建議每個請求最多 3 次嘗試（第一次加上最多 2 次重試）。另一個上限是上一節的總期限：次數還沒用完，但 deadline 到了，也要停。資料庫交易的重試有自己的規則，細節見課末。

回到扣款：它是 POST，沒有冪等鍵之前，金流逾時了也不能自動重送，這一課先讓它「失敗就回報」，下一課再補上冪等鍵。查訂單狀態、查菜單這類 GET 則可以重試。接下來三節講退避、Retry-After、重試放大時，還是會拿扣款當例子，前提是它已經帶上冪等鍵（下一課實作），或者換成查詢扣款狀態的 GET；兩種都屬於可以安全重試的請求，所以能套用下面的規則。那可以重試的請求，失敗後應該馬上再送嗎？開場事故的後半段說明了答案是否定的，下一節處理。

💡 實務上：加重試前先問「重複做一次會發生什麼事」
查菜單、查訂單狀態重試幾次沒關係；扣款、寄簡訊、寄 Email、通知外送平台，重複一次就是客訴。加重試前先列出這支呼叫的副作用，再看第三方有沒有提供冪等鍵。也要確認你用的 SDK 是不是已經內建重試（例如 AWS SDK 預設就會重試），自己外面再包一層就變成兩層重試。前端也一樣：使用者狂按「送出」其實就是人工重試，按鈕送出後先停用、顯示處理中。

隔多久再試？指數退避與 jitter

開場事故裡，App 和 API 都是「失敗就馬上再試一次」。這樣做的問題是：失敗的原因通常還在。金流正在過載，你馬上再送，它還沒恢復，只是多收到一個請求，負擔更重。重試要有用，中間得給下游一點恢復的時間。

最常見的做法是指數退避（exponential backoff）：每次重試前等的時間加倍，100ms、200ms、400ms、800ms……一路加倍到一個上限（cap）為止。加倍的道理是：第一次失敗可能只是一瞬間的問題，短短等一下就好；連續失敗好幾次，代表下游的問題比較嚴重，就等久一點，越來越少打擾它。上限是為了不要等到好幾分鐘：倍數一路翻下去，第 10 次重試就要等 51 秒，那時使用者早就離開了。

只有退避還不夠。想像 1,000 支手機在同一刻遇到 503：它們用同一套程式，都在 100ms 後重試，又一起失敗，再一起在 300ms 重試……每一波都準時擠在同一刻，下游剛恢復一點，又被整整 1,000 個請求同時打倒。問題不在等多久，而在大家等得一樣久。

解法是 jitter：在等待時間裡加入隨機，讓每個客戶端等的時間不一樣，回來的時間就錯開了。下面模擬 100 個客戶端在 0ms 同時失敗，之後每次重試都還是失敗，每 100ms 一格，數有幾個請求打到伺服器。比較的是兩種等待方式：不加 jitter，以及 full jitter，也就是把等待時間改成在 0 到退避時間之間隨機取一個值。程式用固定種子的亂數，所以每次執行的輸出都一樣。執行後比較兩張圖的形狀：

不加 jitter 時，100 個請求每一波都準時落在同一格（100、300、700、1500ms），每一波都是完整的 100 個，也就是下游每隔一段時間就被同時打一次。full jitter 沒有整齊的波：最高的是第一格（原本的 100 個請求，加上很快就重試的那些），之後逐格變少，最多也只有六十幾個。第一次重試只能在 0～100ms 之間隨機，能攤開的空間小；越後面的重試範圍越大，攤得越開。同樣的請求數，攤開之後下游每一刻承受的量就小得多。

jitter 有好幾種加法。AWS 架構部落格 Marc Brooker 的〈Exponential Backoff And Jitter〉（2015）用模擬比較了幾種公式，結論是不加 jitter 最差，full jitter 和 decorrelated jitter 大幅減少總呼叫次數。下面四種公式照 AWS 的 aws-arch-backoff-simulator 整理，查表用，練習 1 會實作其中三種（指數部分的起算方式和 AWS 差一個 2 倍，見課末）：

名稱第 n 次重試前等多久特性
不加 jitterexp = min(cap, base × 2n−1)大家同步湧回，不要用
full jitterrandom() × exp，範圍 [0, exp)最分散；偶爾等得很短
equal jitterexp ÷ 2 + random() × exp ÷ 2，範圍 [exp/2, exp)保證至少等一半
decorrelated jittermin(cap, base + random() × (上一次 × 3 − base))依上一次的等待時間決定範圍，第一次以「上一次 = base」計算

到這裡，可以重試的請求知道自己該等多久了。但有時候下游會直接告訴你該等多久，這時要聽誰的，下一節回答。

💡 實務上：不只重試，所有定期執行的東西都要加 jitter
「大家同一刻一起來」不只發生在重試：每分鐘的排程、快取到期時間、健康檢查、斷線後重新連線，全部都會。例如 200 家門市的 POS 機都設定在整點同步，伺服器就在每個整點被打一次；快取的到期時間都設成剛好 10 分鐘，同一批資料就會在同一刻一起失效、一起回資料庫查。看到「固定時間」「固定間隔」的設定，就問一句：幾百個客戶端會不會剛好對齊？會的話就加一點隨機。

金流說「等 30 秒再來」時怎麼辦？Retry-After

上一節的退避時間是客戶端自己猜的。下游其實比你更清楚自己什麼時候會恢復：它知道自己正在限流、還是正在重開。HTTP 讓伺服器把這個資訊告訴客戶端：429 或 503 回應可以附 Retry-After 標頭（RFC 9110 §10.2.3），值有兩種格式：

Retry-After: 120                              ← delay-seconds：非負整數秒，只能是數字
Retry-After: Fri, 31 Dec 1999 23:59:59 GMT    ← HTTP 日期：要減掉現在的時間

收到 Retry-After 時要等的是 max(退避時間, Retry-After)：伺服器說的時間是下限，比它早回去只會再被拒絕；自己的退避時間如果比較長，也照樣遵守，因為退避還負責把大家錯開。

這時要跟第二節的 deadline 一起看。如果 Retry-After 比剩餘的時間還長，例如金流說 120 秒後再來，但這張訂單的 deadline 只剩 2 秒，就直接放棄並回報：等完早就超過期限，結果沒人收，等待期間還佔著資源。快速失敗，讓上游決定要顯示什麼，例如「金流忙碌中，請稍後再試」。

規則很單純，難的是把標頭的值正確讀出來。JavaScript 內建的轉換函式在這裡有兩個陷阱：第一，parseInt 與 Number 都太寬鬆；第二，Date.parse 在 V8（Chrome、Node）裡會把很多不是日期的字串猜成日期。執行下面的程式，看同一組值被三種函式解析成什麼：

  • parseInt('1.5') 是 1：小數不是合法的 delay-seconds，卻被默默截成 1 秒。
  • Number('') 是 0：伺服器送了空的標頭，你的程式卻解讀成「馬上重試」，正好是上一節要避免的事。
  • Date.parse('1.5') 會是 2001 年的某一天：這是 V8 對非標準字串的猜測，別的引擎可能不同，總之不能拿來當 HTTP 日期。

正確做法是先檢查格式，再轉換：去掉前後空白後全是數字，才當成秒數；日期先比對 RFC 9110 規定送出端要用的 IMF-fixdate 格式（Sun, 06 Nov 1994 08:49:37 GMT），符合了才交給 Date.parse。HTTP 日期一律是 GMT，不會有時區問題（TypeScript 課第 6 課）。兩種格式都不符合，就當成沒有 Retry-After，改用自己的退避。練習 2 會照這個規則寫 parseRetryAfter；RFC 9110 另外要求接收端能讀的兩種過時日期格式，見課末。

到這裡，單一個呼叫端已經會逾時、會判斷能不能重試、會等對的時間。但開場事故裡重試的不只一個地方：App 會重試，API 也會重試。好幾層都照這套規則重試時，金流會收到多少請求，下一節來算。

每一層都重試，金流會收到幾倍的請求？

咖啡店的呼叫鏈是：App → API 閘道 → 訂單服務 → 金流客戶端。假設每一層都寫了「失敗就最多試 3 次」，而金流整個當掉了。閘道的每一次嘗試，都會讓訂單服務跑完自己的 3 次；訂單服務的每一次，又讓金流客戶端試 3 次。所以金流在最壞情況下收到的是 3 × 3 × 3 = 27 倍的請求，是相乘，不是相加。這叫重試放大（retry amplification）。層數越多放大越快，Google SRE 書的例子是每層 4 次，資料庫收到 64 倍。

更糟的是放大發生在最不該發生的時候。下游健康時幾乎不失敗，重試很少；下游一過載，失敗變多，重試就變多，流量變成好幾倍，下游更加過載，失敗又更多。這個惡性循環叫重試風暴（retry storm），開場事故裡「金流剛恢復一點又被壓垮」就是它。對策有三層，從簡單到精細：

  • 只在一層重試：通常是最靠近失敗的那一層的上一層。以（帶冪等鍵的）扣款來說，就是金流客戶端那一層；閘道和 App 收到錯誤就往上傳，不再自己重試。這樣最壞情況從 27 倍降回 3 倍。
  • 限制重試的比例：只在一層重試，3 倍還是 3 倍。Google SRE 書建議每個客戶端的重試佔請求的比例低於 10% 才允許重試。這條規則會自動分辨兩種狀況：下游健康時，偶爾的失敗很少，比例遠低於 10%，照樣重試；大面積失敗時，比例一下就超過，重試自動停止，讓下游喘口氣。
  • 重試預算（retry budget）：把上一點做成具體的計數器。gRPC 提案 A6 的 retry throttling 是這樣做的：每個伺服器一個計數 token_count，從 maxTokens 開始；每次失敗減 1、每次成功加 tokenRatio；計數小於等於 maxTokens 的一半時停止重試，回到一半以上才恢復。tokenRatio 超過 3 位的小數會被忽略。

重試預算的效果用程式看最清楚。下面的設定是 maxTokens 10、tokenRatio 0.1：失敗到第 5 次，計數掉到 5，就停止重試；之後要成功十次以上，計數才爬回 5 以上、恢復重試。失敗扣得快、成功加得慢，所以下游一出事，重試很快就停；下游要穩定好一陣子，重試才會恢復。執行後看每一行最後的「可以重試／停止重試」：

到這裡，扣款這條呼叫鏈需要的規則都有了：每次嘗試有逾時、整個請求有 deadline、只重試該重試的錯誤、退避加 jitter、聽從 Retry-After、只在一層重試、用預算在大面積失敗時煞車。最後一節把它們放回整套可靠性工具裡，並決定上線後怎麼確認它們有在作用。

💡 實務上：在設計文件寫清楚「誰負責重試」
重試常常藏在你沒注意的地方：前端的請求函式、API 閘道的設定、HTTP 客戶端套件、雲端 SDK。資深工程師在架構討論時會把呼叫鏈畫出來，逐層問「這層會不會重試？幾次？」，再決定只留哪一層。事故檢討時，如果下游流量在故障期間反而暴增好幾倍，第一個懷疑的就是重試放大，開場的事故就是這樣。這類設定要讓維運也看得到，例如寫在設計文件或 README，不要只藏在某個套件的預設值裡。

重試和其他工具怎麼分工？上線後要看什麼？

這一課的工具都在處理「下游出問題」，但各自只管一種情況。重試只是其中一種，其他工具有的前面講過，有的接下來幾課會加入，先把分工看清楚，才知道哪個問題該交給誰。表中的 hedged request 是第 3 課選讀講過的做法：請求超過 p95 還沒回應，就再送一份給另一台副本，用先成功回來的結果。

工具解決什麼什麼時候觸發
逾時不讓慢的依賴佔住資源每一次呼叫
重試＋退避暫時性錯誤失敗之後
hedged request尾延遲還沒失敗、只是慢（超過 p95），只用在可重複執行的讀取

冪等鍵（第 9 課）讓有副作用的請求可以安全重試寫入類的請求

放回開場事故來看：逾時讓金流變慢時不再拖垮菜單；重試加退避處理金流一瞬間的失誤；重試預算在金流大面積失敗時讓重試停下來。斷路器更進一步，金流明顯壞掉時連第一次呼叫都不送（第 11 課）；冪等鍵則讓扣款這種 POST 也能安全重試（第 9 課）。

正式環境不用自己從零寫重試迴圈，Node 有現成的套件（例如 p-retry、cockatiel，版本與其他語言的例子見課末）。用套件時要確認的就是這課的每一點：哪些錯誤重試、有沒有 jitter、有沒有總期限、取消時會不會停。練習 5 會把這些規則自己組成一次，之後看套件的設定時，就知道每個選項對應哪一條規則。

最後是上線之後。這些規則有沒有在作用、數字訂得對不對，要靠指標確認：

  • 重試率（重試 ÷ 全部請求），依下游分開看。重試率突然上升，常常是下游開始出問題的第一個訊號，比錯誤率更早。下次金流變慢，你最先看到的就是它。
  • 每個請求的嘗試次數分布：大多數應該是 1 次。
  • 各依賴的逾時次數與延遲百分位數：逾時是不是還貼著 p99.9。
  • 重試預算用光的次數：用光代表下游在大面積失敗。
  • 被取消的請求要分開記，不要算進錯誤率，也不要觸發告警。

這一課修好的扣款呼叫還留著一個缺口：它是 POST，沒有冪等鍵之前，逾時了也不能重試，使用者只能看到錯誤。補上這個缺口是下一課的事。

補充與查表

主線用不到、但讀別人的程式或調設定時會用到的細節。

退避公式的指數從哪裡算起

AWS 模擬器寫的是 min(cap, 2n × base)，第一次重試 n = 1 時就是 2 × base。這門課定義成「第一次重試等 base」（指數用 n − 1），兩者差一個 2 倍，看別人的程式時要注意它從哪裡算起。gRPC 的重試設計（提案 A6）也是指數退避，再乘上 0.8～1.2 的隨機係數當 jitter。

資料庫交易的重試

PostgreSQL 回 40001（序列化失敗）或 40P01（死結）時，要重試的是整個交易，不是失敗的那一句（PostgreSQL 課第 31 課）。

Retry-After 的過時日期格式

RFC 9110 另外要求接收端也要能讀兩種過時的日期格式（RFC 850 與 asctime），這課的練習只處理 IMF-fixdate；正式環境交給 HTTP 客戶端函式庫，或把解析不了的值當成「沒有 Retry-After」，改用自己的退避。

重試預算的其他實作

AWS SDK 在 2016 年也加入了類似 gRPC retry throttling 的本機 token bucket。

現成的重試套件

Node 可以用 p-retry 8.0.1 或 cockatiel 4.0.0 的 retry policy；.NET 的 Microsoft.Extensions.Http.Resilience 標準處理器預設重試 3 次（指數退避加 jitter），還提供 DisableForUnsafeHttpMethods 關掉 POST、PATCH、PUT、DELETE 的重試。

練習

練習 1：實作退避公式。backoffDelay(attempt, opts)：attempt 從 1 開始（第一次重試），不是正整數（0、負數、小數、NaN）就丟 RangeError。exp = Math.min(capMs, baseMs × 2^(attempt − 1))；jitter 是 'none' 回傳 exp、'full' 回傳 random() × exp、'equal' 回傳 exp ÷ 2 + random() × exp ÷ 2。再寫 decorrelatedDelay(prevMs, opts) = Math.min(capMs, baseMs + random() × (prevMs × 3 − baseMs))，第一次重試由呼叫端傳 prevMs = baseMs。亂數一律用參數的 random。

練習 2：把「該不該重試」寫成規則。shouldRetry(input) 依序判斷：

  1. error 是 'aborted'（呼叫端取消）→ 不重試。
  2. attempt >= maxAttempts（attempt 是已經做過的次數）→ 不重試。
  3. 方法（不分大小寫）是 GET、HEAD、OPTIONS、TRACE、PUT、DELETE 才算冪等；其他方法（POST、PATCH……）要 hasIdempotencyKey 才能重試。
  4. 可以重試的失敗只有：error 是 'timeout' 或 'network'，或狀態碼是 408、429、500、502、503、504。

再寫 parseRetryAfter(value, nowMs)，回傳要等的毫秒數：null 回傳 null；去掉前後空白後，全是數字（/^\d+$/）就是秒數 × 1000；符合已經寫好的 IMF_FIXDATE 就用 Date.parse 解析，回傳 Math.max(0, 日期 − nowMs)；其他（空字串、小數、負數、亂寫）都回傳 null。

練習 3：完成 gRPC retry throttling 的 RetryBudget。token 從 maxTokens 開始，永遠介於 0 和 maxTokens 之間；onFailure() 減 1、onSuccess() 加 tokenRatio；canRetry() 在 token 大於 maxTokens ÷ 2 時為 true；tokens 回傳目前的 token 數。tokenRatio 最多 3 位小數，判斷門檻時不能被浮點誤差影響（提示：用整數的千分之一記帳）。再寫 amplification(attemptsPerLayer)：每一層最多嘗試幾次，回傳最底層最多收到幾倍的請求。

練習 4：deadline 傳遞。planCall(input) 決定這一層要不要呼叫下游：deadline <= now 回傳 { action: 'skip', reason: 'deadline-exceeded' }；否則 remaining = deadline − now − marginMs，remaining < minUsefulMs 回傳 { action: 'skip', reason: 'not-enough-time' }；都不是就回傳 { action: 'call', timeoutMs }，timeoutMs 取 perAttemptTimeoutMs 與 remaining 的較小值。

再寫 propagate(hops, startDeadline, startNow, marginMs)，模擬一個請求依序經過每一跳：第一跳拿到 startDeadline，在 startNow 開始；每一跳做完自己的 workMs 之後才呼叫下一跳，傳給下一跳的 deadline 是自己的 deadline 減 marginMs。每一跳記錄 { name, deadline, remainingMs }（remainingMs = 自己的 deadline − 開始的時間）。某一跳開始時 remainingMs <= 0 就不呼叫它，回傳到前一跳為止。

練習 5：把前面的規則組成一個重試迴圈 retryCall(call, o)。call(attempt, timeoutMs) 做一次嘗試，回傳成功或失敗（失敗時告訴你能不能重試、伺服器的 Retry-After 換算成的毫秒數）。attempt 從 1 開始，每一輪：

  1. remaining = o.deadline − o.now()，remaining <= 0 就回傳 reason: 'deadline'。
  2. 呼叫 call(attempt, Math.min(o.perAttemptTimeoutMs, remaining))。
  3. 成功：o.budget.onSuccess()，回傳 { ok: true, value, attempts }。
  4. 不能重試的失敗：回傳 'not-retryable'（不動預算）。
  5. 可以重試的失敗：先 o.budget.onFailure()；attempt >= o.maxAttempts 回傳 'attempts-exhausted'；接著 !o.budget.canRetry() 回傳 'budget'。
  6. 等待時間 = Math.max(backoff(attempt, …), retryAfterMs ?? 0)；o.now() + 等待 >= o.deadline 就不等，直接回傳 'deadline'；否則 await o.sleep(等待)，進入下一輪。

失敗結果的 attempts 是實際呼叫了幾次，error 是最後一次失敗的 error（一次都沒呼叫時是 'deadline-exceeded'）。時間、等待、亂數都用 o 裡傳進來的。

練習 6：App 送出 POST /orders，等了 2 秒逾時。App 可以直接用同樣的內容重試嗎？

✓ b。逾時只代表「沒在時間內收到回應」，請求可能根本沒到，也可能已經做完（a 錯）。等多久都一樣，伺服器不會因為你晚一點送就認出它是同一張訂單（c 錯）。RFC 9110 規定客戶端不應自動重試非冪等的請求；要安全重試 POST，得帶冪等鍵，讓伺服器認出重複（第 9 課）。

練習 7：API 閘道、訂單服務、金流客戶端三層，每一層都「失敗就最多試 3 次」。金流當機時，一次下單最多會對金流送出幾個請求？

✓ c。閘道的每一次嘗試都會讓訂單服務跑完自己的 3 次，訂單服務的每一次又讓金流客戶端試 3 次，所以是相乘不是相加（b 錯），也不會只有 3 次（a 錯）。下游已經壞掉時還被放大 27 倍，這就是重試風暴。只在一層重試，其他層把錯誤往上傳，再加上重試預算。

練習 8：1,000 支手機同時收到 503，程式都寫成「固定等 1 秒再試，最多 5 次」。會發生什麼？

✓ a。大家同時失敗、等一樣久，就會同時回來，每一波都是完整的 1,000 個（b 錯）。只改成指數退避，大家還是在 1、3、7 秒同步湧回，只是波與波之間隔得比較遠（c 錯）。加入 jitter 才會把請求攤開。

練習 9：金流回 503 並附上 Retry-After: 120，但這個下單請求的 deadline 只剩 2 秒。怎麼做？

✓ b。使用者 2 秒後就放棄了，等 120 秒只是佔著連線和記憶體（a 錯）。伺服器已經明說 120 秒內不要來，在 2 秒內硬試只會被拒絕、增加它的負擔（c 錯）。快速失敗，讓上游決定怎麼呈現（例如「金流忙碌中，請稍後再試」）。

常見錯誤

  • 沒有逾時或逾時太長：一個慢的依賴把連線、記憶體、進行中的請求全部卡住，連不相干的功能都受影響，就像開場金流變慢、菜單也打不開。依下游的 p99.9 訂逾時，並定期檢查。
  • 每一層各自設完整的逾時：下游還在做，上游早就放棄了，後面全是白工。deadline 要往下傳，每一層用剩餘時間減掉餘裕。
  • 不分錯誤種類全部重試：400、409、422、501 再試也一樣，只會增加負擔。照決策表分類。
  • 沒有冪等鍵就重試 POST：逾時不代表沒做，重試會重複下單、重複扣款（第 9 課）。
  • 把呼叫端取消（AbortError）當成失敗：重試它、記成錯誤或觸發告警都不對。取消是正常的結束。
  • 退避不加 jitter：大家同時回來，下游剛恢復又被打倒。定期工作和快取到期時間也要加 jitter。
  • 最後一次失敗後還 sleep：白白延遲回應。先判斷還能不能重試，再等。
  • 重試沒有總期限：使用者早就離開了還在重試。deadline 要往下傳，Retry-After 超過剩餘時間就放棄。
  • 用 parseInt、Number 或直接 Date.parse 解析 Retry-After：'1.5' 變 1 秒、空字串變 0、亂寫的字串被猜成日期。先檢查格式。
  • 每一層各自重試：放大倍數相乘。只在一層重試，其他層把錯誤往上傳。

小結

  • 慢比掛掉更危險：等待中的請求佔著資源，Little's Law 算得出會卡住多少。每個網路呼叫都要有整體逾時。
  • 逾時依可接受的誤判比例選下游延遲的百分位數（0.1% → p99.9）。
  • deadline 往下傳：每一層用剩餘時間減掉餘裕；時間不夠就不要開始。每次嘗試的逾時取單次逾時與剩餘時間的較小值。
  • 重試的條件：暫時性錯誤（逾時、連線失敗、408、429、500、502、503、504）、方法冪等或有冪等鍵、不是呼叫端取消、還沒到次數上限與期限。扣款的 POST 沒有冪等鍵就不自動重試。
  • 指數退避一定要加 jitter；full、equal、decorrelated 三種都能錯開，不加 jitter 的會同步湧回。
  • Retry-After 有秒數和 HTTP 日期兩種格式，要嚴格解析；等待取 max(退避, Retry-After)，超過期限就放棄。
  • 多層重試會相乘放大；只在一層重試，並用重試預算（gRPC retry throttling）在大面積失敗時自動停止重試。
  • 上線後看重試率、嘗試次數分布、逾時次數、預算用光次數；取消分開記。
