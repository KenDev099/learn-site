階段 5：資深工程實踐：決策、演進、審查與除錯 · 第 19 課

演進：API 相容性、功能旗標與 strangler fig

咖啡店的訂單 API 已經上線兩年。後端工程師覺得 total 這個名字不好，改成 amount，順便把 id 從數字改成字串，部署。十分鐘後客服電話響個不停：App 的訂單頁全部顯示「NT$ undefined」，合作的外送平台對帳程式整批失敗。App 已經在幾十萬支手機上，沒辦法跟後端同時更新；外送平台的工程師下週才有空。系統一旦有了使用者，就不能說改就改。

回滾之後，檢討會議的結論不是「以後不要改」，因為訂單 API 接下來還有四件事要做：total 改名 amount、id 改成字串；訂單多一個「已退款」狀態 'refunded'；新的結帳頁要上線；還有第 15 課評估過的方向，把訂單功能從單體搬到獨立的服務。主管交給你的任務是：把這四件事排成一份演進計畫，每一步都不弄壞任何正在用的人。這一課從頭到尾都在完成這份計畫。

這課的路線：
  1. 改名為什麼會壞：誰在讀這個欄位，同一個改動為什麼對某些人沒事、對某些人是破壞；改名要分幾步（開場問題的最小答案）。
  2. 後端加了 'refunded'，前端怎麼不整頁壞掉：寬容的讀取端，以及它為什麼不能對錯誤寬容。
  3. total 改成 amount 的完整步驟：expand → migrate → contract，誰先部署，怎麼在合併前自動抓到破壞。
  4. 外送平台等不了怎麼辦：讓新舊版本並存，舊版怎麼量、怎麼通知、怎麼關。
  5. 新結帳頁怎麼只給 10% 的人、出事一鍵關掉：功能旗標與穩定分桶。
  6. 把訂單整塊搬出單體：strangler fig 與影子流量；最後一節整理每一步上線後要看的指標。
這課會用到：
  • NestJS 課第 23 課的 API 版本：用網址區分 /v1、/v2，用 Deprecation／Sunset 標頭通知舊版要退場，在 CI 比對新舊 OpenAPI 抓出破壞。
  • 部署課第 16 課的部署策略：滾動更新時新舊版本會同時在線；金絲雀先讓一小部分流量走新版，功能旗標不重新部署就能開關功能。
  • 第 7 課的 hash32：把任意字串穩定地轉成一個 32 位元整數，同樣的輸入永遠得到同樣的結果。

改名為什麼會壞？先搞清楚誰在讀

開場的後端工程師沒有寫錯任何一行程式。amount 有值、id 是合法的字串、測試全部通過。壞掉的是別人的程式：App 裡寫著 order.total，現在拿到 undefined；外送平台把 id 存進整數欄位，現在收到 "ord_42"。所以要回答「這個改動安不安全」，不能只看自己的程式，要看所有讀這份資料的程式。

會讓現有使用者壞掉的改動，叫破壞性變更（breaking change）。開場的改名就是一個。它的反面是「相容」，而相容有兩個方向，分開想比較清楚：

  • 向後相容（backward compatible）：新版的伺服器仍然能服務舊版的客戶端。後端升級了，還沒更新的 App 照樣能用。開場的改動就是破壞了這一點。
  • 向前相容（forward compatible）：舊版的讀取端能處理新版產生的資料，通常靠「看不懂的部分就忽略」。後端在回應裡多加一個欄位，舊版 App 不認得它，但照樣能顯示訂單。

你可能會想：文件上沒寫的東西，別人不該依賴，改了是他們的問題。實務上不是這樣。Google 工程師 Hyrum Wright 觀察到：使用者夠多時，你的系統所有可以被觀察到的行為，都會被某人依賴，不管文件有沒有寫。這叫 Hyrum 定律。文件說「訂單清單沒有保證順序」，但回應一直是依時間排序，就一定有人的程式假設第一筆是最新的；你改成依 id 排序，他的「最近一筆訂單」就錯了。對方不會去讀你的文件，他只會看到程式壞了、客服電話響了。

用 Hyrum 定律看計畫裡的改動，會發現每一個都有人依賴：

  • total 改名 amount：讀 order.total 的程式拿到 undefined。
  • id 從 42 改成 "ord_42"：用 id === 42 比對、或把 id 存進整數欄位的程式都會壞。
  • 狀態多了 'refunded'：Vue 前端用 switch (order.status) 決定徽章顏色，沒有 default，退款的訂單徽章是空白；如果用的是「找不到就丟錯」的寫法，整頁直接壞掉。
  • 錯誤訊息的文字改了：有人用 message.includes('庫存不足') 判斷錯誤種類。

既然什麼都可能被依賴，怎麼判斷一個改動會不會出事？關鍵是資料流動的方向：誰寫、誰讀。請求是客戶端寫、伺服器讀；回應是伺服器寫、客戶端讀；事件（第 16 課）是生產者寫、所有消費者讀。出事的永遠是讀的那一邊，所以問題要問成「讀的那一邊能不能接受這個改動」。同樣是「加一個欄位」，加在請求和加在回應，結果完全不同：

改動方向相容嗎為什麼
請求加一個選填欄位 note客戶端 → 伺服器相容舊客戶端不帶，伺服器用預設值
請求加一個必填欄位，或把選填改成必填客戶端 → 伺服器破壞所有舊客戶端都會收到 400
請求放寬限制（數量上限 10 改 20）客戶端 → 伺服器相容以前合法的請求現在還是合法
回應加一個新欄位 currency伺服器 → 客戶端相容（對寬容的讀取端）不認得的欄位被忽略；嚴格驗證「不能有多餘欄位」的讀取端會壞
回應刪掉或改名欄位伺服器 → 客戶端破壞讀那個欄位的程式拿到 undefined
回應的列舉多一個值 'refunded'伺服器 → 客戶端看讀取端沒有處理未知值的讀取端會壞
改型別（數字 id 改字串）、改單位（元改成分）任何方向破壞格式一樣也可能語意不同：110 從元變成分，程式不會報錯，帳會錯

表裡有一個規律：「加」通常相容，「刪、改名、改型別、改單位」幾乎都是破壞。開場的改名正是刪一個欄位、加一個欄位，刪的那一半弄壞了所有讀 total 的人。這就是開場問題的最小答案：把 total 改成 amount 不能一步做完。先讓回應同時送 total 和 amount（只有「加」，相容），等 App 和外送平台都改讀 amount，最後才拿掉 total。第三節會把這三步講完整。

💡 實務上：改回應格式前，先問「誰在讀它」
前端工程師最常踩到的不是外部客戶，而是自己人：後端部署了，使用者還開著昨天的分頁，舊的 JS 打新的 API；App 更是會有好幾個版本同時在外面跑。所以審查一個改回應的 PR，第一個問題是「讀這個欄位的有哪些程式、哪些版本」，答不出來就當作有人在用。改名、改型別、改單位這三種，在 PR 說明裡要明確寫出影響範圍，不要藏在「順便重構」裡。只有呼叫端和提供端在同一次部署裡一起換、而且沒有快取或舊分頁的情況，才可以直接改。

表裡還有兩列寫著「看讀取端」：回應多一個欄位、列舉多一個值，會不會壞取決於讀的程式怎麼寫。計畫的第二件事 'refunded' 就屬於這一類，而咖啡店自己的 Vue 前端就是讀取端之一。讀取端要怎麼寫，後端「加東西」時才不會弄壞它？

後端加了 refunded，前端怎麼不整頁壞掉？

先看問題出在哪。Vue 前端拿到訂單後，會檢查 status 是不是 pending、paid、done、cancelled 這四種已知狀態之一，不是就丟錯。這個檢查原本是好意：擋掉壞資料。但後端開始送 'refunded' 的那一刻，這段檢查把一筆完全正常的訂單當成壞資料，整筆失敗。讀取端寫得越「嚴格」，對方每加一樣東西，它就越容易壞。

Martin Fowler 在〈Tolerant Reader〉（2011）建議讀取外部資料時：只讀你需要的、忽略不認得的欄位、對結構做最少的假設、把解析集中在一個地方。照這四條寫的讀取端，叫寬容讀取端（tolerant reader）。它讓對方「加東西」不會弄壞你，等於讀取端自己替對方取得了向前相容。

你可能會想：TypeScript 不是已經會檢查了嗎？TypeScript 課第 16 課的窮舉檢查（用 never 確認每一種狀態都處理過）確實有用，但它只在編譯時檢查你寫的程式有沒有處理完所有已知的值。伺服器在執行時送來的字串不會經過型別檢查，已經裝在使用者手機上的舊版 App 也不會重新編譯。所以解析資料時，要把未知值明確轉成 'unknown' 這個分支，型別裡也寫出它，畫面上給一個「其他」的樣式。這樣窮舉檢查會逼你處理 'unknown'，執行時也不會遇到沒處理的值。

寬容讀取端很好用，但「寬容」很容易被推過頭：既然要寬容，那金額是負數、必填欄位缺了，是不是也收下？答案是不行，而這個教訓有一段歷史。網際網路早期有一條 Postel 法則（robustness principle）：「送出時保守，接收時寬容」。它讓早期各家不完美的實作能互相溝通，但用了幾十年之後副作用浮現了。IAB（Internet Architecture Board，網際網路架構委員會）在 2023 年的 RFC 9413〈Maintaining Robust Protocols〉（資訊性文件）指出，長期對錯誤寬容會讓協定腐化：

  1. 送錯資料的一方從來沒收到錯誤，所以永遠不會修。
  2. 各家讀取端為了容忍這些錯誤，各自累積一堆將就的寫法。
  3. 最後這些怪行為變成大家都得相容的「事實標準」，新寫的實作必須「連 bug 都相容」。

RFC 9413 的建議是分清楚兩種情況：在設計好的擴充點上寬容，例如新欄位、新列舉值，這些是規格允許長大的地方；對違反規格的資料明確地失敗，問題才會在源頭被修好。放到咖啡店的訂單上，就是下面這張表。注意第三列：遷移期間 total 和 amount 會同時出現，這是第一節那個「先兩個都送」的過渡期，讀取端要兩個都接受；但兩個值不相等，代表某一邊算錯了，不能默默挑一個用：

情況寬容讀取端怎麼做
多了不認得的欄位（currency、lines）忽略，輸出裡也不要帶著走
列舉多了不認得的值轉成 'unknown'，畫面有預設樣式
遷移期間新舊欄位都可能出現（total／amount）兩個都接受，優先讀新的；兩個都有但不相等就報錯，不要默默挑一個
金額是負數、是小數、必填欄位缺了拒絕：這是違反規格，不是擴充

第一列的「輸出裡也不要帶著走」容易被忽略：如果解析時用展開把整個物件複製下來，不認得的欄位會跟著流進你的程式，某天有人開始用它，你就又多了一個沒寫在規格裡的依賴。

這些規則要寫在一個解析函式裡，其他地方只用解析後的型別，這就是 TypeScript 課第 26 課的 parse, don't validate。好處是之後格式再變，只要改一個地方。練習 1 會把這張表寫成程式。

寬容讀取端處理的是「對方加東西」：新欄位、新列舉值。但 total 改名 amount 不只是加，還要刪掉 total，讀取端再寬容，也變不出一個被刪掉的欄位。刪的那一半要怎麼安全地做？

total 改成 amount 要分幾步？誰先部署？

第一節已經看到，「加」通常相容、「刪」通常破壞。既然如此，就把一個不相容的改名，拆成「先加、等大家搬家、最後才刪」幾個各自相容的步驟。這個做法叫 parallel change（Danilo Sato，2014），三個階段的名字描述了介面的形狀先變大、再變小：

  1. expand（擴充）：加上新的，舊的保留。回應同時有 total 和 amount，兩個值永遠相同。這一步只有「加」，舊 App 完全不受影響。
  2. migrate（遷移）：讓使用者一個一個搬到新的。App 改讀 amount、外送平台改讀 amount，同時量測還有誰在讀舊的。
  3. contract（收縮）：確定沒人用舊的之後，才移除 total 和為了相容寫的程式。

為什麼要拆成三步，而不是「加完 amount 隔天就刪 total」？因為每一步單獨看都是相容的，所以每一步都可以單獨部署、單獨回滾；出事時你只要退一小步。中間的 migrate 是最花時間的一步，因為它不在你的控制之內：App 要等使用者更新，外送平台要等對方排時間。量測就是在這裡派上用場：不量的話，你只能猜「應該都搬完了吧」，然後重演開場的事故。

三步裡還藏著一個順序問題：誰先部署？以計畫的第二件事 'refunded' 為例，如果後端先開始送，前端的寬容版本還沒上線，就會重演上一節的整頁壞掉。規則是讀的那一邊先準備好，寫的那一邊才開始送：

改動先部署再部署
請求多一個新欄位伺服器（先能接受、沒帶時有預設）客戶端開始送
回應多一個新欄位或列舉值客戶端（先能忽略或處理未知值）伺服器開始送
事件多一個新欄位或新種類所有消費者（先寬容）生產者開始送

這個順序不只對外部客戶有意義，對自己的部署也是。部署本身就是一段新舊並存的時間：部署課第 16 課的滾動更新會讓新舊版本同時在處理請求；回滾則會讓新版寫入的資料被舊版讀到。所以「新版本寫出的資料，舊版本讀得懂」本身就是一個要求，就算這個 API 只有你自己的服務在用也一樣。

同樣的三步也用在 API 以外的介面，只是每一種介面的「舊資料」活得一樣久或更久：

  • 資料庫：加新欄位 → 雙寫並回填 → 程式改讀新欄位 → 刪舊欄位。每一步的鎖與安全寫法在 PostgreSQL 課第 34 課，跟部署怎麼配合在 部署課第 17 課。
  • 事件：事件存在佇列裡、可能被重播，所以舊格式的事件會存在很久，比 API 的舊回應久得多。消費者要比生產者更早能讀新格式。

最後一個問題：拆成三步要靠人記得，人會忘。有沒有辦法讓「不小心一步刪掉 total」在合併前就被擋下來？有兩種工具，抓的東西不一樣，所以是互補的：

  • OpenAPI 比對：NestJS 課第 23 課在 CI 比對新舊兩份 OpenAPI 文件，可以自動抓出「刪了欄位」「選填改必填」這類格式上的破壞。它不需要知道誰在用，所以設定一次就能保護所有呼叫端。它的盲點是語意：金額從元改成分、排序改了、預設值改了，OpenAPI 長得一模一樣，比對不出差異。
  • 契約測試（consumer-driven contract test）：反過來由呼叫端寫下「我依賴回應裡的哪些欄位、什麼樣的值」，例如 App 團隊寫下「amount 是整數元」。提供端的 CI 每次都對所有呼叫端的契約跑一遍，改壞了在合併前就知道。Pact 是常見工具。它抓得到語意上的依賴，代價是每個呼叫端都要寫、要維護。外部的、你不認識的使用者寫不了契約，這部分只能靠下一節的版本與棄用流程。
💡 實務上：一個改名會變成好幾張工作單
在團隊裡，「把 total 改成 amount」不會是一個 PR，而是 expand、各端改讀、contract 三到四個 PR，可能橫跨好幾個迭代。最常被忘記的是最後的 contract：新欄位上線後大家就去做別的事，舊欄位和相容程式留了好幾年。資深工程師會在開工時就把 contract 開成工作單、寫上「用量歸零後執行」的條件，並在估時程時跟 PM 說明這是好幾週的事，不是改一行。

expand → migrate → contract 有一個前提：所有讀取端終究會搬家。但外送平台的工程師下週才有空，之後也未必排得出時間；id 改成字串，也許可以另加一個字串型的 orderId 欄位來 expand；但 contract 的前提是外送平台終究會改讀新欄位。對方排不出時間，舊欄位就永遠刪不掉，id 這個名字也永遠沒辦法換成字串。等不了、又非改不可的時候，該怎麼辦？

外送平台等不了：怎麼讓新舊版並存，舊版怎麼退場？

答案是讓兩個版本的 API 同時存在：還沒準備好的人繼續用舊版，準備好的人改用新版，彼此互不影響。Node 課第 14 課介紹過 API 版本，這裡要回答的是資深工程師在意的三件事：版本標在哪裡、多個版本的程式怎麼維護、舊版怎麼收掉。

先看版本標在哪裡。客戶端必須在請求裡說「我要哪個版本」，常見三種寫法：

方法例子好處代價
URI 版本/v1/orders、/v2/orders一眼看得出來，好路由、好快取（NestJS 課第 23 課的做法）版本粒度粗，改一個欄位就要整套 v2
標頭版本Api-Version: 2網址不變瀏覽器直接開、看 log 時比較不明顯；回應要加 Vary: Api-Version，快取才會把不同版本分開存
日期版本Stripe-Version: 2026-10-28.endive每個不相容改動都有日期，可以細到單一欄位要有轉換鏈的基礎設施

咖啡店選 URI 版本，跟 NestJS 課第 23 課的做法一樣：外送平台繼續打 /v1/orders，新的 App 改打 /v2/orders。標在哪裡比較好選，難的是第二件事：多個版本的程式怎麼維護。最直覺、也最危險的做法是每個版本複製一整套程式：OrdersV1Controller、OrdersV2Controller……到 v7 時修一個 bug 要修七份，而且總會漏掉一份。

Stripe 在〈APIs as infrastructure〉（2017）描述了另一種做法：程式只有最新版一份；每一個不相容的改動，另外寫成一個版本轉換（version change module），內容只有一件事：「怎麼把改動後的回應轉回改動前的樣子」。以咖啡店為例，id 改字串那天寫一個轉換，負責把 "ord_42" 轉回 42；total 改名那天再寫一個，負責把 amount 轉回 total。

請求指定了某個舊版時，伺服器照常算出最新版的回應，再把「比目標版本新」的轉換由新到舊依序套用。順序很重要：越新的轉換，假設它拿到的是越新的格式。如果先套用舊的轉換，它會拿到一份它不認得的格式。這樣一來，商業邏輯只維護一份，舊版只是「在出口多做幾次轉換」；修 bug 只修一處。練習 2 會實作這條轉換鏈。Stripe 目前的版本命名與發布節奏放在課末「補充與查表」。

有了新版本，舊版就不能永遠留著，否則轉換鏈會越來越長。第三件事是舊版怎麼退場，順序是先量、再通知、最後才關：

  • 量：每個請求記下版本與呼叫者（API key、App 版本），做成「各版本每天的請求數、還在用舊版的客戶清單」。沒有這份資料就訂退場日，等於賭沒人在用，開場的事故就是賭輸的樣子。
  • 通知：寄信給清單上的客戶，回應也加上機器讀得懂的標頭。這裡有兩個常被混用的詞：棄用（deprecation）是宣告「不建議再用」，舊版仍然正常服務；Sunset 是宣告「哪一天停止服務」。
  • 關：用量真的降到可以接受（或期限到了、已經個別聯絡過剩下的客戶）才關。關之前可以先在低峰時段短暫回 410（Gone，資源已經不在）做「斷電演習」（brownout）：還沒搬家的人會在這短短幾分鐘內發現，而且是在你預期、可以馬上恢復的時間點。

通知用的兩個標頭各有標準格式：Deprecation 是「@ 加 Unix 秒數」，Sunset 是 HTTP 日期，而且 Sunset 不能早於 Deprecation。下面這格產生咖啡店 v1 的退場標頭，執行後看三個標頭的值，以及最後一行的檢查：

💡 實務上：大部分內部 API 不需要開 v2
只給自家前端用的 API，通常靠「只加不刪」加上 expand → migrate → contract 就夠了，開 v2 反而要多維護一整套。版本與 Sunset 流程主要用在對外的 API：合作夥伴、開放平台、改不動的舊 App。以這份計畫來說，咖啡店自己的 Vue 前端用 expand → migrate → contract 就好，外送平台才需要版本。有人提議開 v2 時，資深工程師會先問：這個改動能不能拆成相容的步驟？舊版要維護多久、誰負責通知客戶？這兩題沒答案，就先不要開。

到這裡，計畫的前兩件事都有了做法。它們有一個共同點：改的是資料的格式，只要格式相容，就不會弄壞別人。計畫的第三件事不一樣：新結帳頁的 API 格式可能完全相容，但它是一段全新的行為，算錢的邏輯可能有 bug。一部署上去，所有人同時用到；出事時唯一的退路是回滾整個部署。能不能先讓一小部分人用，出事時立刻關掉？

新結帳頁怎麼只給 10% 的人，出事一鍵關掉？

問題的根源是「部署」和「讓使用者用到」綁在一起了。把它們拆開：部署（deploy）是把程式放上伺服器，發布（release）是讓使用者用到新功能。拆開的工具是功能旗標（feature flag，也叫 toggle）：程式裡寫 if (旗標開了) 走新結帳頁 else 走舊的，而旗標的值存在程式外面，可以在執行時改，不用重新部署。

有了旗標，新結帳頁的上線變成這樣：先部署，旗標關著，沒有任何人看到；再對 1%、10%、50% 的人打開，每一步看錯誤率；出事就把旗標關掉，所有人立刻回到舊結帳頁，不用回滾整個部署，同一次部署裡的其他修正也不受影響。

「出事時立刻關掉」這個用法本身有一個名字：kill switch，出事時立刻關掉某個功能的開關。它不只用在新功能。第 11 課的降級（推薦服務慢就不顯示推薦）如果事先做成旗標，值班時就是一鍵的事，不用在半夜改程式、跑 CI、部署。旗標依用途不只一種，壽命與管理方式也不同。Pete Hodgson 在〈Feature Toggles〉（martinfowler.com）把旗標依用途分類：新結帳頁這種逐步放量、放量完就刪的叫 release 旗標；kill switch 屬於 ops 旗標；依方案開放功能（企業方案才有的團購）叫 permission 旗標，會存在好幾年。另外還有 A/B 實驗用的 experiment 旗標，完整的四類對照表放在課末「補充與查表」。

接下來是這一節的核心：「對 10% 的人開」，怎麼決定是哪 10%？直覺的寫法是 Math.random() < 0.1，比例確實是 10%，但它每個請求重抽一次：

  • 王小明重新整理一次看到新結帳頁、再整理一次看到舊的，購物車可能在兩個版本之間壞掉。
  • 如果是 A/B 實驗，結果沒辦法比較，因為同一個人兩組都待過。
  • 從 10% 調到 30% 時，原本看到新版的人不保證還看得到。

需要的性質是：同一個人每次都得到同樣的結果。這個性質叫黏著性（stickiness）。做法是分桶（bucketing）：把「旗標名稱＋使用者 ID」用第 7 課的 hash32 雜湊，再取除以 100 的餘數，得到 0～99 的桶號；桶號小於百分比就開啟。雜湊對同樣的輸入永遠給同樣的輸出，所以王小明永遠落在同一個桶。

結果的意義：

  • 桶號是固定的，百分比從 10 調到 30 只是把門檻往上移：原本開啟的人（桶號 0～9）一定還在範圍內，放量只會加人、不會把人關掉。
  • 兩個 30% 的旗標只重疊約 9%，是因為雜湊裡放了旗標名稱。如果只雜湊使用者 ID，桶號 0～9 的那群人會是每一個新功能的白老鼠，而且兩個實驗的結果會互相污染：你分不清轉換率上升是哪個功能造成的。

正式環境通常不自己寫旗標系統，而是用 OpenFeature 這類廠商中立的 API 接上現成的服務（套件與版本見課末）。不管用哪一套，程式裡只問「這個使用者的 new-checkout 開了嗎」，判斷邏輯集中在一處。練習 3 會把百分比、kill switch、允許與拒絕名單組合成完整的判斷。

旗標是有持有成本的庫存。每個旗標讓程式多一條分支，兩個旗標就有四種組合要測。Hodgson 的建議：加 release 旗標時就在待辦清單放一張「移除旗標」的工作；每個旗標設到期日，過期就讓測試失敗；限制旗標總數，要加一個就得先移除一個。放量到 100% 一週沒事之後，就把舊路徑和旗標一起刪掉。
💡 實務上：前端的旗標只管「顯示」，不管「權限」
在 Vue 裡用旗標藏起一個按鈕很常見，但前端的判斷使用者改得掉，而且還沒發布的功能程式碼可能已經打包在 JS 裡，被人翻出來。所以 permission 類的旗標（企業方案才有的團購）一定要在後端的 API 再檢查一次，前端只負責「要不要顯示」。上線前也要確認旗標關閉時的畫面：旗標服務連不上時，預設值應該是安全的那一邊（通常是「不開放新功能」）。

旗標切換的是同一個程式裡的兩條路徑：新結帳頁和舊結帳頁都在同一次部署裡。計畫的最後一件事規模大得多：新的路徑是一整個新服務，有自己的程式和資料庫。同樣「一小部分一小部分切過去、隨時能切回來」的想法，放大到整個系統要怎麼做？

把訂單整塊搬出單體：strangler fig 怎麼一塊一塊換？

第 15 課說過，要從單體拆出服務，不能一次重寫再切換：重寫期間舊系統還在改，新系統永遠追不上；切換那天所有差異同時爆發，而且退不回去。strangler fig（絞殺榕，Martin Fowler 取的名字）的做法是：在舊系統旁邊長出新系統，一塊一塊接手功能，直到舊系統可以退休。絞殺榕在宿主樹上發芽，慢慢長到包住整棵樹，名字就是這樣來的。

它用的工具都是這一課前面出現過的：用分桶決定哪些人走新路徑，用相容的步驟讓每一步都能退回。下圖是做到一半的樣子：

咖啡店把訂單功能搬到新服務，分五步。每一步都在解決上一步留下的風險：

  1. 建立切換點：所有請求先經過閘道，閘道一開始把 /orders/* 全部轉給單體。這一步不改任何行為，看起來什麼都沒做；但從此之後，每一步都只是改閘道的設定，切回去也只是改設定。
  2. 影子流量（shadow traffic）：新服務寫好了，但你不知道它跟舊系統算出來的結果是不是一樣。影子流量的做法是把真實請求複製一份給新服務執行，比對兩邊的結果，但回給使用者的永遠是舊系統的。這能用真實資料找出新系統的差異，又不影響使用者。條件是新系統在影子模式下不能有副作用：不寄收據、不扣款、不推播，否則同一位顧客會收到兩封收據、被扣兩次款。最簡單的影子是只讀的請求（查訂單）；寫入的請求要讓新服務在「乾跑」模式下只算出結果、不提交。
  3. 雙寫與回填（dual write／backfill）：新服務有自己的資料庫，裡面一開始是空的。遷移期間舊系統寫入時也寫一份到新的那邊，這叫雙寫，最好用第 12 課的 outbox 確保不漏；再把歷史資料批次複製過去，這叫回填。接著要比對：筆數、金額總和、抽樣逐筆比較。雙寫不比對，新舊資料會默默分歧，到切換那天才發現。
  4. 切換讀取，再切換寫入：用上一節的穩定分桶讓 1%、10%、100% 的使用者走新服務，每一步看錯誤率與延遲。舊路徑保留著，隨時可以切回去。
  5. 移除舊路徑：停止寫舊表、刪掉單體裡的訂單程式、刪掉閘道的分流規則和比對程式。這是 expand → migrate → contract 的 contract，放大到整個系統。

注意第 5 步要刪的東西：閘道規則、雙寫、比對程式。它們有一個共同的名字，過渡架構（transitional architecture）：只為遷移期間存在、遷移完就要丟掉的程式。它們跟 contract 工作單一樣容易被遺忘，所以在設計文件（第 18 課）的上線計畫裡就要寫出它們什麼時候移除，否則它們會變成永久的複雜度。

第 2 步的影子比對程式本身也要寫對，它是放在正式請求路徑上的程式，寫錯會直接影響使用者。要小心三件事，練習 4 會實作：

  • 回應不能等新系統，否則新系統的延遲直接加到使用者身上。
  • 新系統的任何錯誤都不能影響回應，包括變成未處理的 rejection。
  • 比對要看「內容」而不是字串：{"a":1,"b":2} 和 {"b":2,"a":1} 是同一筆資料；時間戳記、自動產生的 id 這類本來就會不同的欄位要排除，否則比對結果全是雜訊。

五步裡的每一步都有一個「可以往下走了嗎」的判斷：影子比對夠一致了嗎？雙寫的資料對得上嗎？10% 的錯誤率正常嗎？前面幾節也一樣：total 還有人讀嗎？v1 還有誰在用？這些判斷都要靠資料，而不是感覺。

最後一列最常被忽略。這一課的每個做法都假設「出事可以退回去」，但退路會在不知不覺中消失：遷移做到一半，新服務已經寫了一週的資料，舊系統卻沒有，這時「回滾」已經不是改閘道設定那麼簡單。每往前一步，都要確認退路還在，或者明確地決定「從這裡開始不回頭」並寫進文件。

這就是主管要的演進計畫的完整樣子：改名用 expand → migrate → contract，'refunded' 先讓讀取端寬容再開始送，外送平台用版本並存與退場流程，新結帳頁用旗標逐步放量，訂單服務用 strangler fig 一塊一塊接手；每一步都有可以量測的「往下走」條件，和確認過的退路。

補充與查表

這一節不用背，實作時需要再回來查。

Stripe 的版本命名與發布節奏：Stripe 的帳號有一個預設版本，〈APIs as infrastructure〉說明預設是帳號第一次呼叫 API 時的最新版；目前的官方文件建議在每個請求用 Stripe-Version 標頭（或固定版本的 SDK）明確指定，版本名稱是日期加名稱，例如 2026-10-28.endive。Stripe 從 2024-09-30.acacia 開始改成每月發一個不含破壞性變更的版本，一年兩次發「大版本」（例如 basil、endive），破壞性變更只放在大版本的第一個版本裡，讓使用者能預期什麼時候要改程式。

功能旗標的四種類型：Pete Hodgson 在〈Feature Toggles〉（martinfowler.com）把旗標分成四類，壽命和「多常改」差很多，管理方式也不同：

類型咖啡店的例子壽命決定方式
release：發布用新結帳頁逐步放量幾天到幾週，放量完就移除依使用者分桶
experiment：實驗用燕麥奶加購按鈕的 A/B 測試到統計結果出來依使用者分組，分組要穩定
ops：維運用尖峰時關掉推薦區塊的 kill switch多半短，kill switch 可能長期存在值班人員在執行時直接切換
permission：權限用企業客戶才有的團購功能好幾年依使用者或方案

Unleash 的分桶：Unleash 的做法跟這課的分桶一樣：它用 MurmurHash 雜湊使用者 ID 加上 groupId（預設是旗標名稱）；幾個旗標設成同一個 groupId 就會選到同一群人，改 groupId 會整個重新洗牌。演算法跟我們的 hash32 不同，原理相同。練習 3 的 salt 就是同樣的用途。

旗標系統的套件：部署課第 16 課介紹的 OpenFeature 是廠商中立的 API（@openfeature/server-sdk 1.23.0），後面可以接 Unleash（unleash-client 6.12.2）、LaunchDarkly 或自架的服務。Hodgson 把「程式裡問旗標開了沒」的地方稱為切換點，主張把切換點和決策邏輯分開，OpenFeature 的設計就是這樣。

練習

練習 1：寫 parseOrderTolerant(json)，把從外部收到的訂單（可能是舊格式、新格式或遷移中的格式）解析成 ParsedOrder。規則：

  • 必須是物件（不是 null、不是陣列），否則 not_object。
  • id 可以是正整數（舊版）或非空字串（新版），一律輸出字串；其他情況 bad_id。
  • 金額優先讀 amount（新），沒有（undefined）就讀 total（舊）。兩個都有但不相等 amount_mismatch；兩個都沒有 missing_amount；讀到的值不是非負整數 bad_amount。
  • status 不是字串 bad_status；是四種已知狀態之一就照用，其他字串變成 'unknown'。
  • items 沒有（undefined）時是 []；有但不是陣列 bad_items；每一筆要是物件，且 productId、quantity 都是正整數，否則 bad_item。
  • 每一層多出來的欄位都忽略：輸出只有規定的欄位。不能修改輸入。

錯誤一律丟 new ParseError(代碼)。

練習 2：寫 renderForVersion(latest, requested, changes, oldestSupported)，用 Stripe 式的轉換鏈把最新版的回應轉成客戶端要求的版本。版本是 'YYYY-MM-DD' 字串（這種格式直接用字串比較就是日期先後）。規則：

  • requested 格式不對，或比 oldestSupported 舊，丟 UnsupportedVersionError。等於 oldestSupported 是可以的。
  • 先 structuredClone(latest)，再把 version 嚴格大於 requested 的改動，依版本由新到舊套用 down（每個 down 回傳轉換後的物件，下一個 down 接著處理它）。
  • changes 傳進來不一定有排序。不能修改 latest（它可能是好幾個請求共用的快取資料）。

練習 3：寫 isEnabled(flag, userId)，決定某個使用者的功能旗標是否開啟。依序判斷：

  1. percent 不是 0～100 的整數，丟 RangeError。
  2. killed 是 true（kill switch）→ false，連 allow 名單上的人也關。
  3. deny 包含 userId → false。
  4. allow 包含 userId → true（例如內部員工先試用）。
  5. 否則桶號 = hash32(`${flag.salt ?? flag.key}:${userId}`) % 100，桶號小於 percent 時開啟。

不能用 Math.random。hash32 已經寫好了。

練習 4：寫 shadowCompare(primary, candidate, opts)，做 strangler fig 的影子比對。primary 是舊系統、candidate 是新系統。規則：

  • 兩個同時開始。回傳（或丟出）primary 的結果，不能等 candidate。
  • primary 成功後開始計時 timeoutMs（用 opts.schedule：代替 setTimeout，回傳取消函式，測試用假時鐘推進，見第 3 課）：candidate 在時限內成功，就用 opts.diff 比較，沒有差異 report({ kind: 'match' })，有差異 report({ kind: 'mismatch', paths })；candidate 失敗 report({ kind: 'candidate-error', error })；時限到了還沒完成 report({ kind: 'candidate-timeout' })，之後才完成也不再 report。candidate 在 primary 之前就完成的話，primary 一成功就比較。比較完要取消計時器。
  • primary 失敗時照樣丟出它的錯誤，不 report。
  • candidate 的任何錯誤（包含呼叫時就同步丟出的）都不能影響回應，也不能變成未處理的 rejection。

練習 5：訂單 API 的回應多了一個狀態值 'refunded'，其他什麼都沒改。Vue 前端用 switch (order.status) 決定徽章，沒有 default。這算相容的改動嗎？

✓ c。相不相容要看讀取端：沒有處理未知值的讀取端，遇到新值就出錯或顯示空白，新增不一定相容（a 錯）。TypeScript 的型別只存在於編譯時，伺服器在執行時送來的字串不會經過前端的型別檢查，而且已經裝在手機上的舊版 App 也不會重新編譯（b 錯）。列舉本來就會長大，禁止新增不切實際；正確的做法是寬容讀取端加上「讀取端先部署」的順序（d 錯）。

練習 6：產品要求下單請求的 note（備註）欄位改成必填。最好的上線方式是？

✓ b。請求從選填改必填是破壞性變更：直接部署的話，所有舊客戶端（包含使用者沒更新的 App）都會 400，訂單直接掉單（a 錯）。Deprecation 只是通知，沒人會在一天內改完並上架，而且 App 要等使用者更新（c 錯）。先量測、再過渡、再收掉，是 expand → migrate → contract 的順序。

練習 7：新結帳頁用 Math.random() < 0.1 決定要不要顯示，「統計上就是 10% 的人」。有什麼問題？

✓ a。比例對，但是「誰」每次都在變：王小明重新整理就可能從新版跳回舊版。A/B 實驗需要同一個人一直在同一組，放量需要「已經開啟的人不會被關掉」，這些都要靠用旗標 key 加使用者 ID 的雜湊分桶（b 錯）。問題不在亂數的品質，換成更好的亂數一樣每次不同（c 錯）。

練習 8：新訂單服務跑了一週影子流量，比對結果 99.9% 一致。可以把流量切過去了嗎？

✓ d。一致率是平均值，0.1% 可能全部集中在「有折扣碼的訂單」或「金額」欄位，這種錯一筆都不行（a 錯）。影子流量通常只比對得到讀取或乾跑的結果，真的寫入、扣款、寄信，以及新服務在真實負載下的延遲都沒驗證過，所以要小比例放量並保留回滾（b 錯）。有些差異是預期的（時間戳記、新產生的 id、浮點格式），要求 100% 一致會永遠切不過去；重點是每一類差異都解釋得出來（c 錯）。

常見錯誤

  • 直接改回應的形狀：改名、刪欄位、改型別或單位，任何依賴舊行為的客戶端都會壞（Hyrum 定律）。用 expand → migrate → contract，或開新版本。
  • 嚴格的讀取端：對方多送一個欄位或一個新列舉值，整個功能就壞。只讀需要的、忽略不認得的、未知列舉有預設處理。
  • 過度寬容：金額為負、必填欄位缺了也收下，錯誤被吞掉，最後誰都不敢修（RFC 9413）。在擴充點寬容，對違反規格的資料明確地失敗。
  • 部署順序搞反：伺服器先送新列舉值、客戶端還沒能處理。讀的那一邊先準備好，寫的那一邊才開始送。
  • 沒有使用量資料就移除舊版：不知道誰還在用，關掉的那天才知道。每個請求記下版本和呼叫者，用量歸零（或已個別聯絡）才關。
  • 每個版本複製一整套程式：v1 到 v7 每次修 bug 要修七份。程式只維護最新版，舊版用轉換鏈產生。
  • 旗標永遠不移除：程式裡充滿死掉的分支和測不完的組合。加旗標時就排好移除工作、設到期日、限制數量。
  • 放量用隨機而不是穩定的分桶：同一個人每次看到不同版本。用旗標 key 加使用者 ID 的雜湊。
  • 影子流量沒關掉副作用：同一位顧客收到兩封收據、被扣兩次款。影子模式只讀或乾跑，副作用全部關掉。
  • 影子比對的錯誤影響了正式回應：等新系統、或新系統丟錯讓整個請求失敗。新系統的結果只用來比對，錯誤全部接住。
  • 雙寫卻沒有比對：新舊資料默默分歧，切換那天才發現。定期比對筆數、總和、抽樣逐筆比較。
  • 過渡架構沒有移除計畫：閘道規則、雙寫程式、相容欄位變成永久的。在設計文件裡寫出每一個什麼時候刪。

小結

  • Hyrum 定律：使用者夠多時，所有可觀察的行為都會被依賴。判斷相容性要看資料流動的方向：讀取端能不能接受。「加」通常相容，「刪、改名、改型別、改單位」幾乎都是破壞。
  • 寬容讀取端：只讀需要的、忽略不認得的、未知列舉有預設、遷移期間新舊欄位都接受；對違反規格的資料不寬容（RFC 9413）。解析集中在一個函式。
  • 不相容的改動拆成 expand → migrate → contract，每一步都相容、可回滾；讀取端先部署，寫入端後開始送。OpenAPI 比對抓結構，契約測試抓呼叫端實際依賴的行為。
  • 等不了所有人搬家時開新版本：URI、標頭或日期版本；程式只維護最新版，舊版用由新到舊的轉換鏈產生。舊版退場先量、再用 Deprecation（RFC 9745）與 Sunset（RFC 8594）通知、最後才關。
  • 功能旗標把部署和發布分開。分桶用旗標 key 加使用者 ID 的雜湊：結果穩定、放量只加人、不同旗標選到不同的人。kill switch 讓降級變成一鍵操作。旗標要有到期日和移除計畫。
  • Strangler fig：建立切換點 → 影子流量比對（不等、不影響回應、關掉副作用）→ 雙寫、回填、比對 → 分桶逐步切換 → 移除舊路徑與過渡架構。
  • 每一步都要有可量測的「往下走」條件，並確認退路還在；回不去的那一步要明確決定並寫進文件。
