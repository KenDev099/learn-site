階段 2：擴展：冗餘、快取與資料 · 第 6 課

複寫與一致性：讀副本、複寫延遲與 CAP

咖啡店的 App 上線後，第 5 課的快取接住了菜單，但資料庫還是九成的時間在處理讀取：顧客查「我的訂單」、門市看今天的單、總部跑報表。這些都是會變動、不能放快取的資料，第 5 課說過訂單不放快取，所以每一次都直接查 PostgreSQL。一台資料庫開始吃不消時，最常見的下一步是加幾台讀副本（read replica）：把同一份資料複製到其他機器上，讀取分過去。

你照做了，把「我的訂單」改成讀副本。上線第二天，客服轉來一張單：「顧客說剛下的單在『我的訂單』裡看不到，重新整理一次出現，再整理一次又不見了，他以為沒下成功，又下了一次。」資料庫沒有壞，SQL 也沒有錯。這課從這張客服單出發：先弄懂副本怎麼運作、為什麼一定會落後，再修好這個 bug，最後把同樣的判斷用到咖啡店的每一種讀取，以及機房之間斷線的時候。

這課的路線：
  1. 一台資料庫撐不住讀取，副本怎麼分擔？複寫怎麼運作、為什麼副本一定會落後（客服單的最小答案在這一節）。
  2. COMMIT 回成功時，資料在哪幾台？同步與非同步複寫，在下單延遲和「主機壞掉會掉幾筆」之間取捨，以及為什麼同步複寫修不好客服單。
  3. 剛下的單為什麼一下有、一下沒有？用時間軸重現客服單，認識三種異常，再用 LSN 把讀取導向夠新的副本。
  4. 每一種讀取都要這麼嚴格嗎？一致性模型給你跟 PM 討論「這個畫面可以舊多久」的詞彙；機房斷線時，CAP 與 PACELC 告訴你要選一致還是可用。
  5. 選讀兩節：沒有 primary 的資料庫怎麼用 quorum 讀到新資料；多個地方都能寫入時，衝突怎麼用版本向量判斷。跳過不影響後面的課。
這課會用到：
  • PostgreSQL 課第 37 課的串流複寫：primary 把 WAL 持續傳給 replica 重播；synchronous_commit 決定 COMMIT 要不要等 replica 確認；replica 會落後一點。
  • TypeScript 課第 5 課的 bigint：超過 253 的整數用 number 會不精確，要用 bigint。

一台資料庫撐不住讀取：副本怎麼分擔？

把同一份資料存在多台機器上，叫複寫（replication）。這課的起點是分擔讀取，但同一套機制一次解決三件事，所以正式環境的資料庫幾乎都會開：

  • 分擔讀取：「我的訂單」、報表這些讀取分給其他機器，主資料庫專心處理寫入。
  • 高可用：主資料庫壞了，把一台副本升格接手，也就是第 4 課的故障轉移。
  • 異地備援：整個機房出事，另一個區域還有一份。

要讓另一台機器的資料跟主資料庫一樣，PostgreSQL 用的是它本來就有的一份日誌。PostgreSQL 每改一筆資料，都會先把「改了什麼」依序寫進日誌，再去改真正的資料檔；當機重開時照著日誌補做，資料就不會停在改一半的狀態。因為是「先寫日誌、後寫資料」，這份日誌叫 WAL（write-ahead log，預寫日誌）。

既然 WAL 已經依序記下每一個變更，另一台機器只要拿到同一份 WAL、照順序做一遍，資料就會跟原本那台一樣。這個「照著做一遍」叫重播（replay）。PostgreSQL 的串流複寫就是這樣運作：接受寫入的那台叫 primary，它把 WAL 持續傳給其他機器；收到 WAL、重播、只能讀不能寫的機器叫 replica。所有寫入都送到 primary，讀取可以分給 replica。這種「一台收寫入、其他台跟著重播」的架構，一般的叫法是 leader／follower，中文也叫主從；這課統一用 PostgreSQL 的 primary 和 replica，開場說的讀副本就是 replica。

圖中間那行字是這一課所有問題的來源：replica 一定會落後。WAL 從 primary 出發，要經過網路送到 replica、寫進 replica 的磁碟、再重播，每一步都要時間。平常可能只有幾毫秒；primary 一次大量寫入（例如批次匯入）、replica 自己在跑很重的報表查詢、網路抖動時，就可能落後好幾秒甚至幾分鐘。replica 落後 primary 的時間或資料量，叫複寫延遲（replication lag）。

💡 實務上：加 replica 之前，先確認真的需要
replica 會帶來這一課講的整套一致性問題，所以它不該是第一個手段。先看是不是有慢查詢可以補索引，熱門又不常變的資料能不能放快取（第 5 課），這兩件事做完，常常就不必加 replica。還要注意 replica 只分擔讀取：每台 replica 都要重播一樣多的寫入，寫入太多的問題它幫不上忙，那是第 7 課分片要處理的。

客服單的最小答案已經在這裡：顧客的訂單寫進了 primary，「我的訂單」讀的是 replica，讀的那一刻 replica 還沒重播到這筆。既然問題是 replica 慢了一步，直覺的修法是讓 primary 等 replica 跟上再回「成功」。下一節就來看這個做法，叫同步複寫。

COMMIT 回成功時，資料在哪幾台？同步與非同步複寫

要讓 primary「等 replica 跟上」，先要決定 primary 收到 COMMIT 之後，什麼時候回「成功」給 App。有兩種做法：

  • 非同步複寫：primary 自己寫好就回成功，WAL 之後再慢慢送。快，但 primary 若在送出前壞掉，最後幾筆已經回成功的交易會不見。
  • 同步複寫：要等指定的 replica 確認收到才回成功。慢一點（多一次網路往返），但 primary 壞掉時資料還在 replica 上。

比較兩者之前先認識一個詞：RPO 是 recovery point objective 的縮寫，意思是「出事時最多能接受掉多少資料」，例如「最多掉最近 1 秒的訂單」或「一筆都不能掉」。它是業務決定的目標，決定了你需不需要同步複寫。

非同步同步
COMMIT 的延遲只有本機寫入多等一次 replica 的確認（跨區域可能幾十毫秒）
primary 壞掉時會掉資料嗎（RPO）可能掉最後幾筆已回成功的不會掉
同步的 replica 壞掉時寫入照常寫入卡住，直到它回來或改設定

最後一列最常被忽略。同步複寫的意思是 primary 一定要等到那台 replica 確認，所以那台 replica 當機或網路斷了，COMMIT 就一直等下去，咖啡店的下單跟著卡住。PostgreSQL 18 文件明寫，同步副本當機時，等它確認的 COMMIT「可能永遠不會完成」，所以通常會設兩台以上的同步候選，一台掛了還有別台可以確認。

那同步複寫能修好開場的客服單嗎？大多數情況不能，原因有兩個。第一，「replica 確認收到」不等於「replica 上查得到」。PostgreSQL 用 synchronous_commit 決定 COMMIT 要等到哪一步，預設值 on 等的是同步 replica 把 WAL 寫進磁碟；寫進磁碟之後還要重播，重播之前查詢看不到這筆。只有 remote_apply 這個等級會等到 replica 重播完、查得到（各等級的差別整理在課末「補充與查表」）。第二，這些等級只管「同步」的 replica，非同步的 replica 不在等待名單裡，哪一個等級都不保證它追上。

就算把所有 replica 都設成同步、等級設成 remote_apply，每一筆 COMMIT 都要等每台 replica 重播完，下單變慢，任何一台 replica 卡住，寫入就跟著卡住。這等於用整個系統的寫入速度和可用性，去換「我的訂單」看得到剛下的單，代價太高。所以分擔讀取的 replica 通常是非同步的，落後是常態。要修的不是複寫，而是讀取：每次讀之前，要知道該讀哪一台。下一節先把客服單完整重現，看清楚讀錯台時到底發生什麼事。

💡 實務上：先問「最多能掉幾筆」，再決定同步或非同步
這個問題要拿去問 PM 和財務，不是工程師自己猜：咖啡店的訂單和付款紀錄掉一筆就要人工對帳，瀏覽紀錄掉幾筆沒人在意。雲端代管資料庫（例如 AWS RDS）的「讀副本」和「高可用備援」通常是兩個不同的選項，複寫方式也不一樣，開之前先看文件確認你買到的是哪一種。資深工程師會在設計文件寫下 RPO，並確認兩件事：同步 replica 掛掉時寫入會不會卡住、failover 會升格哪一台。

客服單把兩件事混在一起講，但它們是兩種不同的異常，修法也不一樣，要分開看。

第 2 步是讀不到自己剛寫的：王小明自己下的單，自己卻讀不到。使用者對系統最基本的期待是「我做的事，我自己馬上看得到」，這個保證叫讀己之寫（read-your-writes）：一個人寫入之後，他自己之後的讀取一定看得到這筆。注意它只管「自己」：陳美華晚幾秒才在門市後台看到這張單，不違反讀己之寫。

第 4 步是資料倒退：王小明已經看過 #501，下一次讀卻回到更舊的狀態，好像訂單被刪掉了。對應的保證叫單調讀（monotonic reads）：讀到某個版本之後，之後的讀取不會再看到比它更舊的版本。「單調」是數學用語，指只增不減。這個異常的成因是兩次讀取分到落後程度不同的 replica，每一台自己都只會越來越新，是「換台」讓時間倒流。

第三種異常不在時間軸裡，但同樣常見：因果顛倒，結果比原因先被看到。例如付款服務確認付款後送出推播「訂單已付款」，王小明點開推播，App 讀到落後的 replica，畫面顯示「待付款」。他看到了結果（推播），卻看不到原因（付款紀錄），以為扣款失敗又付一次。推播走的是另一條路，比 replica 重播還快到，所以「先發生的事」反而晚被看到。

三種異常有一個共同點：每一台資料庫都沒壞，SQL 也沒錯，錯在讀取被送到哪一台。這也是它在本機重現不了的原因：本機只有一台資料庫，讀寫都在同一台。所以修法要放在「選哪一台來讀」這一層，下一節就來設計它。

怎麼保證讀得到自己剛寫的？從讀 primary 到記住 LSN

要讓每次讀取挑到一台夠新的機器，常見的做法有三種，由粗到細。

第一種是寫入後幾秒內讀 primary。primary 永遠是最新的，所以使用者剛寫過資料，就讓他接下來一段時間的讀取都走 primary。這是最簡單的做法，問題在「幾秒」是猜的：設 3 秒，replica 某天落後 10 秒就失效；而且尖峰時大家都在下單，大家的讀取都回到 primary，剛好在最需要 replica 的時候失去它。

第二種是讓 session 黏在同一台 replica。同一台 replica 只會越來越新，只要一直讀它，就不會出現時間軸第 4 步的倒退，單調讀解決了。但它解決不了讀己之寫：你黏的那台可能還沒收到你剛寫的那筆，時間軸第 2 步照樣發生。那台 replica 掛掉、換到別台時，連單調讀也保不住。

第三種是記住 LSN，最精確。LSN（log sequence number）是 WAL 裡的位置，也就是時間軸裡 0/5000 那種數字。WAL 是依序寫的，位置越後面代表越新的變更，所以 primary 寫到哪、每台 replica 重播到哪，都可以用一個 LSN 表示，兩個 LSN 比大小就知道誰比較新。PostgreSQL 18 文件說 LSN 在內部是 64 位元整數，文字格式是兩個最多 8 位的十六進位數字中間加斜線，例如 16/B374D848，代表 0x16 × 2^32 + 0xB374D848。在 PostgreSQL 裡可以這樣拿到：

-- primary，寫入的交易 COMMIT 之後
SELECT pg_current_wal_lsn();        -- 例如 0/5000

-- 每一台 replica
SELECT pg_last_wal_replay_lsn();    -- 已經重播到哪裡，例如 0/4F00

有了 LSN，讀取導向這樣做：

  1. 寫入的交易 COMMIT 之後，在 primary 上查 pg_current_wal_lsn()，記成這個使用者的「最後寫入位置」。這筆寫入一定在這個位置以前。
  2. 讀取時，挑一台 pg_last_wal_replay_lsn() 大於或等於這個位置的 replica。它已經重播過這筆寫入，一定查得到，讀己之寫成立。
  3. 每次讀完，也記下讀的那台重播到哪，當成「最後讀取位置」。下次需要的位置取兩者中較大的，就不會讀到比上次更舊的 replica，單調讀也成立。
  4. 沒有任何 replica 追上，就讀 primary。

拿時間軸驗證：第 2 步需要 0/5000，A 只到 0/4F00、B 只到 0/4E00，兩台都不夠新，改讀 primary，王小明看得到 #501。第 4 步需要的位置至少是 0/5000，B 不會被選到，倒退也不會發生。和第一種做法比，它不必猜要等幾秒：replica 追上了就讀 replica，沒追上才讀 primary，primary 只扛真正必要的讀取。實作時不會每個請求都去問每台 replica，通常由程式定期查一次各台重播到哪，存在記憶體裡比對。

同一個機制也修得好第三種異常，推播的因果顛倒。問題出在推播帶著「已付款」這個結果，卻沒帶著「結果建立在哪筆寫入之上」。所以讓它帶上：付款服務把付款紀錄寫進 primary、COMMIT 之後，查 pg_current_wal_lsn()，把這個 LSN 放進推播內容（或推播點開的連結參數）。王小明點開推播時，App 把這個 LSN 交給後端，後端把它當成這次讀取需要的位置去做上面的導向：有 replica 重播到這個位置就讀它，沒有就讀 primary。這樣只要他看得到「已付款」的推播，點進去就一定讀得到付款紀錄，不會再看到「待付款」而重複付款。這裡的 LSN 不是王小明自己寫入的位置，而是「造成這則推播的那筆寫入」的位置：把原因的位置跟著結果一起傳遞，結果就不會比原因先被看到。這正是下一節表裡「因果一致」要保證的事。

💡 實務上：客服說「重新整理才出現」，先懷疑複寫延遲
這類 bug 在本機重現不了，上線後也只是偶爾出現，所以看到「剛改的資料有時看不到」就要先想到 replica：查那個時間點的 replay_lag，再確認那個畫面的查詢是不是走 replica。多數團隊一開始不會做到 LSN 導向，而是用框架內建的讀寫分離，它們通常是第一種做法「寫入後改讀 primary」的變形（例子見課末「補充與查表」）。上線前先確認你用的框架是哪一種行為、保證到哪裡為止。

到這裡「我的訂單」修好了。但咖啡店不只這一種讀取：菜單、結帳時的價格、付款狀態、總部報表，每一種都要套 LSN 導向嗎？下一節建立判斷的詞彙。

每一種讀取都要這麼嚴格嗎？一致性模型：選夠用的最弱保證

不需要。菜單晚幾秒更新沒人在意，報表晚一分鐘也沒關係，這些讀取用 LSN 導向只是白白把負載推回 primary。要逐一判斷「這個讀取需要多新」，先要有一組精確的詞彙。一致性模型（consistency model）是系統對「讀到什麼」的承諾，上一節的讀己之寫和單調讀就是其中兩種。把比它們更強和更弱的也放進來，由強到弱：

模型保證咖啡店的例子
線性一致（linearizability）像只有一份資料：寫入完成後，所有人都讀得到讀 primary
因果一致（causal）有因果關係的事件，每個人看到的順序都一樣看得到「已完成」就一定看得到「已付款」
讀己之寫（read-your-writes）自己寫的，自己之後一定讀得到（別人不一定）下單後「我的訂單」有這筆
單調讀（monotonic reads）讀到新的之後，不會再讀到更舊的重新整理不會倒退
最終一致（eventual consistency）不再有寫入時，副本最後會一致；中間可能讀到舊的菜單晚幾秒更新沒關係

表裡的新面孔有三個。線性一致是最強的：整個系統表現得像只有一份資料，任何人在寫入完成之後讀，都一定讀到它。咖啡店只有一台 primary 收寫入，讀 primary 就有這個保證。因果一致處理的是上一節的第三種異常：推播「已付款」是因為付款紀錄已經寫入，有因果關係，所以任何人看得到推播的結果，就一定要看得到付款紀錄。最終一致是最弱的：只承諾「不再有寫入時，副本最後會一樣」，沒說「最後」是多久，中間讀到什麼都有可能。

越強的保證需要越多協調：線性一致要每次都問 primary（或等多數副本確認），延遲高、primary 壓力大；最終一致隨便讀一台都行。保證越強，能回答請求的機器也越少：讀己之寫要找夠新的那幾台，最終一致任何一台活著都能回答。這一點到下一節機房斷線時會變得很重要（更精確的說法見課末「補充與查表」）。

資深工程師的做法：每一種讀取選「夠用的最弱模型」，並在設計文件裡寫清楚哪些讀取可以容忍過時、可以舊多久。全部讀 primary 很安全，replica 就白買了；全部讀 replica 很省，結帳就可能用到舊價格。練習 4 會替咖啡店的 8 種讀取做這個決定。

💡 實務上：前端也能幫忙做到讀己之寫
下單成功後，前端可以把 API 回傳的那筆訂單直接放進「我的訂單」列表，不必馬上重新查詢，使用者在這個畫面就感覺不到 replica 落後。但這只顧得到這個分頁：換一台裝置或重新整理頁面，還是要靠後端的讀取導向。跟 PM 討論時把「要即時」換成具體問題：「這個畫面舊 5 秒可以嗎？舊 1 分鐘呢？誰會因此受損？」答案寫進設計文件，之後有人想把某個查詢改走 replica 時才有依據。

到目前為止都假設機器之間的網路是通的，replica 只是慢了一點，等一下就會追上。如果網路整個斷了，replica 再也收不到新的 WAL，它還該回答問題嗎？

機房之間斷線時，高雄的 replica 該不該回答？CAP 與 PACELC

咖啡店為了異地備援，在高雄機房放了一台 replica，平常也分擔南部門市的讀取。某天台北和高雄兩個機房之間的線路斷了：兩邊的機器都還活著，只是彼此連不上。這種狀況叫網路分割（network partition）。高雄的 replica 收不到台北傳來的 WAL，資料停在斷線那一刻。這時它收到讀取請求，只有兩個選擇：

  • 回答手上的資料，請求有回應，系統是可用的（Availability，簡稱 A），但資料可能是舊的；
  • 拒絕或等待，直到確認是最新的，保住一致（Consistency，簡稱 C，指的是上一節的線性一致），但使用者會看到錯誤。

沒有第三個選項：它連不上台北，就沒辦法知道自己是不是最新的。這就是 CAP，P 是分割（Partition）。常聽到的「C、A、P 三選二」是誤導，Brewer 自己在 2012 年〈CAP Twelve Years Later〉裡澄清：

  • 分割不是可以不選的。只要資料在兩台以上的機器上，網路就可能斷。所以真正的選擇只有「分割時選 C 還是 A」。
  • 沒有分割的時候，C 和 A 可以兼得。
  • 可以依操作選。同一個系統裡，付款選 C、菜單選 A。
  • 逾時就是在做選擇。系統沒辦法分辨「對方很慢」和「網路斷了」；等多久放棄、放棄後回舊資料還是回錯誤，就是 C 與 A 的選擇（第 8 課會講逾時）。

CAP 只講分割的時候，但分割很少發生，這一課前面做的決定都發生在網路正常的時候。Abadi 2012 年提出的 PACELC 補上平常的情況：Partition 時在 A 與 C 間選，Else（沒有分割）時在 Latency（延遲）與 C 間選。回頭看，第二節的同步複寫就是平常用延遲換一致；「我的訂單」改讀 replica，是用一點過時換低延遲、低負載；LSN 導向則是在兩者之間找到剛好夠用的點。

回到高雄機房，依操作選：

咖啡店的資料分割時選理由
付款狀態、退款C寧可請顧客稍後再試，也不能重複退款
庫存扣減C超賣要退錢、道歉
菜單、門市營業時間A舊幾分鐘沒關係，顯示錯誤頁反而損失訂單
推薦商品A不準也沒人會發現

這張表和上一節「每種讀取選夠用的最弱模型」是同一件事的兩面：平常決定每種讀取可以舊多久，斷線時決定每種讀取要回舊資料還是回錯誤。主線到這裡結束，接下來兩節是選讀。

沒有 primary 的資料庫怎麼讀到新資料？Quorum：R + W > N（選讀）

這節是選讀：PostgreSQL 這類只有一台 primary 收寫入的資料庫用不到 quorum，等你要用 Cassandra 這類沒有 primary 的資料庫，或面試被問到 Dynamo 的設計時再回來看。跳過不影響後面的課。

到這裡為止，判斷「誰比較新」都靠 LSN，前提是寫入只有 primary 一個入口，所有變更排在同一份 WAL 裡。另一類系統沒有 primary，任何副本都能收寫入，例如 Amazon 2007 年發表的 Dynamo 論文（Amazon 購物車背後的儲存系統）和受它啟發的開源資料庫 Cassandra。這類系統一筆寫入不會傳到每一台，讀取也不知道該問哪一台，它們用 quorum（法定人數）保證讀得到新資料。因為沒有共同的 WAL，每筆寫入會自己帶一個版本號（例如遞增的計數或時間戳），讀取時比版本號決定誰新；用時間戳當版本號會出什麼問題，留到下一節的「最後寫入者勝」。

  • 每份資料存 N 份。
  • 寫入要等 W 份確認才算成功。
  • 讀取要等 R 份回應，取其中版本最新的。

只要 R + W > N，讀到的 R 份和寫入的 W 份一定至少重疊一份，所以一定讀得到最新的寫入。原因是機器不夠分：如果讀和寫完全沒有重疊，總共需要 R + W 台不同的機器，但只有 N 台。Dynamo 論文裡常見的設定是 (N, R, W) = (3, 2, 2)。用程式把所有組合列出來確認，看最後一欄：R + W > N 的組合，讀不到新值的組合數都是 0：

讀到的 R 份裡，版本有新有舊。取最新的回傳之外，可以順便把新值寫回落後的副本，這叫 read repair。只靠 read repair 的話，沒人讀的資料永遠不會修好，所以這類系統另外有背景比對（anti-entropy）。

調 R 和 W 就是在調取捨：W = N 寫入最慢、任何一台壞了就寫不進去；R = 1 讀取最快。(3, 2, 2) 允許壞一台，讀寫都還能進行。R + W > N 也不是萬能：寫入失敗時部分副本可能已經寫了、用機器時鐘決定版本時會出錯（下一節），實際的保證要看各系統的文件。

quorum 解決了「讀到哪一份」，但留下另一個問題：任何副本都能收寫入時，兩個人同時改同一筆資料，誰算數？

多個寫入點同時改同一筆，誰算數？最後寫入者勝與版本向量（選讀）

這節是選讀：咖啡店只有一個 primary 收寫入，不會有寫入衝突；等你要做離線也能用的 App、多人同時編輯，或多個區域都能寫入的資料庫時再回來看。跳過不影響後面的課。

只有一個 primary 時，寫入的先後由 primary 決定，WAL 裡誰在前面誰就先。但有些情況下，多個地方都能寫：離線也能點餐的 App（手機先存、上線再同步）、台北與高雄兩個區域各有一個可寫的資料庫。兩邊同時改同一筆資料，就會衝突，而且沒有一份共同的 WAL 可以排先後。

最省事的解法是最後寫入者勝（LWW，last write wins）：每筆寫入帶時間戳，時間大的贏。問題是時間戳來自各台機器的時鐘，而時鐘會偏移。主機的時鐘靠 NTP（網路校時協定）定期校正，兩次校正之間會慢慢走快或走慢，幾台機器的時間不會完全一樣。執行下面的程式，看 LWW 留下了哪一筆：

LWW 只適合「丟掉一個也無所謂」的資料。要知道兩個寫入到底是先後關係還是同時發生，不能看時鐘，要看「寫的人有沒有看過對方的修改」。版本向量（version vector）就是記錄這件事的工具：每個寫入點一個計數器，自己寫一次就把自己的計數器加 1，同步時逐個取最大。例如購物車一開始在 App 寫了一次，版本是 { app: 1 }；App 再改一次變成 { app: 2 }；同時網頁版從 { app: 1 } 那一版開始改，變成 { app: 1, web: 1 }。比較兩個版本：

AB關係原因
{ app: 1 }{ app: 2 }A 在 B 之前（before）A 的每一格都 ≤ B，至少一格 <；B 是在看過 A 之後寫的
{ app: 2 }{ app: 1, web: 1 }並行（concurrent）A 的 app 比較大，B 的 web 比較大；兩邊都沒看過對方的修改
{ app: 1 }{ app: 1, web: 0 }相同（equal）沒有的 key 視為 0

先後關係很好處理：後面的直接取代前面的。並行的版本沒有誰對誰錯，只能合併：

  • 購物車取聯集：Dynamo 論文的做法。好處是「加入購物車」不會遺失；代價是在並行的另一支裡還留著的品項，刪掉後可能「復活」。
  • 交給使用者選：像 Git 的合併衝突。
  • CRDT（conflict-free replicated data type）：把資料結構設計成怎麼合併結果都一樣，例如每個寫入點各記一個計數再相加的計數器、記得刪除紀錄的集合。

能用單一 primary 就用單一 primary。多寫入點的衝突處理會滲進每一個功能，是很貴的選擇；咖啡店只有購物車這種「合併錯了也不嚴重」的資料值得這樣做。

💡 實務上：前端最常在離線與多人協作遇到衝突
離線也能用的 App（PWA、行動 App 先存本機再同步）和多人同時編輯的功能，都是多寫入點，衝突一定會發生。動手前先問：衝突時丟掉一邊可以嗎？要讓使用者自己選嗎？多人協作編輯通常直接用現成的 CRDT 函式庫（例如 Yjs、Automerge），不要自己寫合併邏輯。如果需求只是「離線時暫存、上線後送出」，把離線的操作排進佇列、上線後依序送到單一 primary，通常就夠了，不需要真的做多寫入點。

補充與查表

synchronous_commit 的等級（查表用，不用背）

細節在 PostgreSQL 課第 37 課。這裡只列和「同步 replica 上查不查得到」有關的三個等級：

等級COMMIT 等到同步 replica 上查得到嗎
remote_writereplica 把 WAL 寫進作業系統不一定；replica 的作業系統當機時還可能掉
on（預設值）replica 把 WAL 寫進磁碟不一定，可能還沒重播
remote_applyreplica 重播完查得到

只有 remote_apply 保證同步 replica 上查得到剛寫的資料；on 和 remote_write 只保證資料已經送到 replica。非同步的 replica 不在等待名單裡，哪一個等級都不保證它追上。

框架內建的讀寫分離

例如 Laravel 讀寫分離的 sticky 選項、Rails 的自動切換連線，都是「寫入後改讀 primary」的變形：前者限同一個請求內，後者是寫入後一段時間內。它們都要猜一個範圍，保證不到 LSN 導向那麼精確。

保證越強，能回答的機器越少：sticky available

Jepsen（專門測試分散式資料庫一致性的專案）的整理指出，讀己之寫以及更強的模型，最多只能做到 sticky available：client 要一直連同一台（或同一批）副本，那台活著就能回應；換到別台就可能失去保證。更弱的模型才做得到「連到任何一台活著的副本都能回應」。

練習

練習 1：寫三個函式，讓讀取同時做到讀己之寫和單調讀。

  • parseLsn(text)：把 'X/Y'（兩段各 1～8 位十六進位，大小寫都可以）轉成 bigint，值是 X × 2^32 + Y。格式不對就丟 Error。
  • routeRead(session, replicas, primary)：需要的 LSN 是 lastWriteLsn 和 lastReadLsn 中較大的（null 忽略，兩個都是 null 就是 0）。依陣列順序選第一台 replayLsn ≥ 需要的 LSN 的 replica；沒有就讀 primary。回傳 { target, session }：target 是選中的名稱；session 是新的物件（不能改傳入的），lastReadLsn 改成選中節點的 LSN 文字（replica 的 replayLsn 或 primary 的 currentLsn）。
  • afterWrite(session, commitLsn)：回傳新的 session，lastWriteLsn 取原本的和 commitLsn 中較大的那個（保留原本的文字）。

練習 2（選讀，對應「Quorum」一節）：實作 quorum 讀取。replies 依抵達順序排列，null 代表那台逾時或失敗。quorumRead(replies, r) 只用前 r 個成功的回應（讀到 r 個就回傳，不再等後面的）；不到 r 個就丟 QuorumError。回傳這 r 個裡版本最大的 value、version，以及 repair：這 r 個回應裡版本比較舊的副本名稱，依抵達順序。另寫 isQuorum(n, r, w)：三個都是正整數、R 和 W 都不超過 N，而且 R + W > N 時回傳 true。

練習 3（選讀，對應「多個寫入點」一節）：寫版本向量的工具，再用它合併並行的購物車。

  • compareVV(a, b)：沒有的 key 視為 0。每一格都相等是 'equal'；a 的每一格都 ≤ b、至少一格 < 是 'before'；反過來是 'after'；互有大小是 'concurrent'。
  • mergeVV(a, b)：每個 key 取較大的值。bump(vv, node)：回傳 node 加 1 的新物件，不改輸入。
  • resolveSiblings(siblings)：先丟掉被其他版本支配的（compareVV 是 'before'），剩下的版本 vv 全部合併、items 取聯集。items 一律去重、用 sort() 排序。

練習 4：替咖啡店的 8 種讀取選「夠用的最弱」保證，填好 READ_POLICY：'primary'（一定要最新）、'read-your-writes'（至少看得到自己剛寫的）、'replica-ok'（舊一點沒關係）。每個 why 寫一句自己的理由（至少 8 個字，不能重複）。再寫 routeFor：primary 永遠讀 primary；read-your-writes 用練習 1 的 routeRead（已經寫好）；replica-ok 讀陣列裡第一台 replica，沒有 replica 才讀 primary。primary 和 replica-ok 都回傳原本的 session，不更新。

練習 5：顧客結帳後立刻跳到「我的訂單」，卻看不到剛下的單；重新整理後又出現了。最可能的原因是什麼？

✓ 重新整理就出現，代表資料早就寫進去了，只是第一次讀的那台還沒追上。INSERT 沒有「補寫」這回事；沒 COMMIT 的資料重新整理也看不到。PostgreSQL 在任何隔離等級都不會讀到還沒提交的資料，而且這裡是「讀不到」不是「多讀到」。寫完馬上讀卻時有時無，第一個要查的是讀取導向。修法：LSN 導向（練習 1）、或寫入後讀 primary。

練習 6：「CAP 說三選二，單機的 PostgreSQL 選的是 CA。」這句話哪裡有問題？

✓ 只要資料分散在兩台以上的機器，網路就可能斷，P 不是可以放棄的選項。CAP 真正的問題是「分割發生時，選一致還是可用」；沒有分割時兩者可以兼得。單機沒有「機器之間連不上」這回事，CAP 根本不適用；有交易也跟 CAP 的 C（線性一致）是兩回事。一旦加了 replica，就要開始回答這個問題。

練習 7（選讀，對應「多個寫入點」一節）：台北和高雄兩個區域都能改同一張訂單，衝突時用各自主機的時間做 LWW。台北主機的時鐘快了 2 秒，會發生什麼事？

✓ LWW 只比時間戳。台北的時間戳多了 2 秒，2 秒內在高雄做的修改都會輸給台北比較早的寫入，被默默丟掉。主機的時鐘靠 NTP（網路校時協定）定期校正，誤差是常態；要判斷真正的先後或並行，要用版本向量（練習 3）。

練習 8（選讀，對應「Quorum」一節）：N = 3、R = 1、W = 1。寫入回成功之後馬上讀，一定讀得到剛寫的值嗎？

✓ 寫入只等 1 台確認，讀取只問 1 台，兩台可能不是同一台。「最後都會收到」是最終一致，但「最後」不是「現在」。要保證讀到，R + W 要大於 N，例如 (3, 2, 2)。

常見錯誤

  • 寫完馬上從 replica 讀：自己剛寫的資料可能還沒到。用 LSN 導向、黏著，或寫入後讀 primary。
  • 讀取在多台 replica 之間隨機分配：兩次讀到落後程度不同的 replica，資料看起來在倒退。記住讀過的 LSN，或讓 session 黏在同一台。
  • LSN 用字串比較或用 number 存：'0/9' > '0/10' 是 true；64 位元超過 2^53 會失去精度。解析成 bigint 再比。
  • 以為開了同步複寫就絕對不會掉資料：synchronous_commit 的等級、failover 時升格哪一台、同步 replica 掛掉時寫入會卡住，都要確認（PostgreSQL 課第 37 課）。
  • 用牆上時間做 LWW：時鐘偏移會默默丟掉比較新的寫入。要判斷先後用版本向量，能用單一 primary 就用單一 primary。
  • 說「最終一致」卻沒有上限和監控：量 replay_lag 並告警，落後太多的 replica 從讀取名單拿掉。
  • 該讀 primary 的讀 replica、可以讀 replica 的打 primary：付款狀態、庫存走 replica 會出錯；報表這種重查詢打 primary 會拖慢結帳。每一種讀取都要選過。

小結

  • 複寫是把同一份資料存在多台機器上，分擔讀取、高可用、異地備援。PostgreSQL 的寫入只到 primary，replica 重播 primary 傳來的 WAL；每一步都要時間，所以 replica 一定會落後，這叫複寫延遲。
  • 同步複寫用延遲換不掉資料，同步 replica 壞掉時寫入會卡住；非同步快，但可能掉最後幾筆。先問 RPO 再決定。同步複寫修不好「讀不到剛寫的」：只有 remote_apply 保證同步 replica 查得到，非同步 replica 不受任何等級保證。
  • 複寫延遲造成三種異常：讀不到自己剛寫的（讀己之寫）、資料倒退（單調讀）、因果顛倒。資料庫沒壞，錯在讀到哪一台。
  • 修法由粗到細：寫入後讀 primary、session 黏同一台、記住 LSN。LSN 導向只讀已重播到需要位置的 replica，沒有就讀 primary；LSN 要解析成 bigint 再比。replica 的落後要用 replay_lag 監控並設上限。
  • 一致性模型由強到弱：線性一致、因果、讀己之寫／單調讀、最終一致。每種讀取選夠用的最弱模型，並寫下可以舊多久。
  • CAP 只在網路分割時才要選一致或可用，而且可以依操作選；PACELC 補上平常的取捨：延遲與一致。
  • （選讀）Quorum：R + W > N 讀寫一定重疊；讀到多個版本取最新、順便 read repair。
  • （選讀）多個寫入點會衝突。LWW 在時鐘偏移時會丟掉較新的寫入；版本向量分得出先後或並行，並行時要合併（購物車取聯集）。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 9：下單流程新加了「推薦加購」：同步呼叫推薦服務（99.5%），失敗就整張單回 500。上線後下單成功率明顯下降，怎麼改最有效？

✓ 硬相依串聯要相乘，下單最多只剩 99.5% 再乘上其他依賴；改成軟相依後，推薦壞了下單照常，不再拉低可用性，通常比加機器便宜。降級時畫面怎麼呈現要先跟 PM 講好。a 錯在冗餘公式假設獨立，同一次壞部署、同一份設定會讓兩台一起壞，而且它仍然是硬相依。（第 4 課）

練習 10：6 台 API 平均放在 2 個可用區，平常每台使用率 60%。老闆問：「一整個可用區掛掉撐得住嗎？」

✓ 總負載是 6 × 60% = 3.6 台的量，掉一區剩 3 台，每台 120%，排隊暴增、逾時又引發重試。容量要以「掉一個可用區之後」的使用率規劃。c 錯在可用性公式只說「至少有一區活著」，不保證活下來的那一區扛得住全部流量。（第 4 課）

練習 11：3 台負載平衡器共用一份每秒更新一次的後端負載資料，每個請求都送給「目前最閒」的後端。監控上卻看到後端輪流爆量：這一秒是 2 號，下一秒換 5 號。為什麼？

✓ 大家在同一瞬間看到「2 號最閒」，就一起湧向 2 號，下一刻又一起湧向另一台，這是羊群效應。P2C 隨機挑兩台選比較閒的，不同請求挑到的兩台不同，不會全部湧向同一台；Envoy 的 least request 預設就是它。a 錯在 round robin 不看負載，請求長短差很多時本來就分不平均。（第 4 課）

練習 12：菜單用 cache-aside 加 TTL，後台改價的程式這樣寫。哪裡會出事？

async function updatePrice(id, price) {
  await db.query('UPDATE products SET price = $1 WHERE id = $2', [price, id])
  await cache.set(`price:${id}`, price)
}

✓ A 改 120、B 改 130，B 先更新快取、A 的 set 慢一步，資料庫是 130、快取卻是 120。改成寫完資料庫後刪除快取：刪除是冪等的，誰先誰後結果都是空的；再用 lease 擋住讀取把舊值寫回，TTL 當最後的保險。a 錯在資料庫寫失敗時快取會留下沒存進去的價格，兩個寫入交錯時一樣會留下舊值。（第 5 課）

練習 13：每次部署會把 2,000 個商品一次寫進快取，TTL 都是 60 秒。部署後資料庫 CPU 每 60 秒就跳一次，最該先改什麼？

✓ 同一時間寫入、同一個 TTL，2,000 個 key 就同一時間過期、一起打資料庫，這是雪崩。TTL 加隨機（jitter）讓過期分散開，改動很小。a 錯在 single-flight 只合併同一個 key 的載入，2,000 個不同的 key 還是各查一次資料庫。（第 5 課）

練習 14：「我的訂單」改走 replica 之後，顧客偶爾看不到剛下的單。哪個做法能保證讀得到自己剛寫的？

✓ LSN 是這次寫入在 WAL 裡的位置，replica 重播到那裡就一定查得到這筆，不必猜要等幾秒；比較時要解析成 bigint。a 錯在黏著同一台只保證單調讀（不會倒退），那台可能還沒收到你剛寫的。（第 6 課）

練習 15：台北和高雄機房之間斷線，高雄的 replica 同時收到「查這筆退款完成了沒」和「看菜單」兩個請求。怎麼回應最恰當？

✓ CAP 只在網路分割時要選一致或可用，而且可以依操作選：退款狀態讀到舊的可能重複退款，選 C；菜單舊幾分鐘沒關係，回錯誤頁反而損失訂單，選 A。a 錯在「最終」不是「現在」，顧客看到舊的「未退款」就可能再申請一次。（第 6 課）

這個階段的重點整理成一頁圖解。

下一課（選修）：分片與一致性雜湊。複寫解決了讀取量，但所有寫入還是擠在同一台 primary；資料和寫入多到一台放不下時，要把資料切開放到多台機器上。大部分系統用不到分片，跳過的話直接進第 8 課，階段 3：可靠性。
