階段 4：架構：服務、事件與即時推送 · 第 17 課

即時推送：輪詢、SSE 與 WebSocket 的規模化

咖啡店的 App 要上線「取餐通知」：王小明點了一杯拿鐵，店員在出單畫面按下「可以取餐了」，他的手機要馬上從「製作中」變成「可以取餐」。門市的出單畫面是同一個需求反過來：顧客一付款，新訂單就要出現在店員眼前，晚 10 秒就可能漏做一杯。

難處在 HTTP 的基本模式是「瀏覽器問、伺服器答」。伺服器只能回應別人送來的請求，沒辦法自己開口；你在 Vue 裡寫的每一個 fetch 都是這個模式。要讓手機在狀態改變的那一刻知道，只有兩條路：讓手機一直問，或讓一條連線一直開著、伺服器有事就往裡面寫。這一課從頭到尾只做一件事：把「拿鐵可以取餐了」這個事件，在尖峰 10 萬個 App 同時在線、好幾台伺服器、前面還有 nginx 和負載平衡器的環境裡，準時而且不漏地送到王小明手上。在一台開發機上什麼做法都能動，問題都是規模和真實網路帶出來的，我們照遇到的順序一個一個解。

這課的路線：
  1. 最簡單的做法：每 5 秒問一次，伺服器每秒要接多少請求，貴在哪裡。
  2. 讓伺服器有事才開口：長輪詢、SSE、WebSocket 怎麼運作，「取餐通知」為什麼選 SSE（開場問題的最小答案）。
  3. SSE 裡傳的是什麼：事件的格式，自己讀串流時資料被任意切塊怎麼解析。
  4. 斷線續傳：手機進電梯再出來，怎麼補上漏掉的「可以取餐了」；同一件事換成 WebSocket 要自己寫多少。
  5. 多台伺服器：更新落在 A 機、連線接在 B 機時怎麼送到，一支慢手機怎麼不拖垮整台機器。
  6. 上線：nginx、心跳、連線數上限，以及重新部署時幾萬條連線同時重連怎麼不把資料庫打垮。
這課會用到：
  • Node 課第 16 課的 SSE 與背壓：回應不結束、一段一段 write 出去；對方讀得慢時 write 回傳 false，要等 drain 再寫。
  • 部署課第 12 課的 nginx 反向代理：請求先到 nginx 再轉給 Node，proxy_read_timeout 時間內後端沒送資料，nginx 就把連線關掉。
  • 第 8 課的退避與 jitter：重試時每次等久一點，再加隨機量，避免大家同時重試。

最簡單的做法：每 5 秒問一次，要花多少？

伺服器不能主動開口，最直接的辦法就是讓 App 自己一直問。這叫短輪詢（polling）：客戶端每隔固定幾秒送一次一般的 GET，問「訂單 41 現在是什麼狀態」。寫成程式就是 setInterval(() => fetch('/orders/41'), 5000)，前端多半寫過。它不需要任何特別的伺服器設定，每個請求都是普通的 API 呼叫，所以一定能動。問題是它要花多少。

先看延遲。狀態可能在兩次詢問之間的任何時刻改變：剛問完就改，要等將近 5 秒才知道；快要問的時候才改，幾乎馬上知道。平均下來，延遲是間隔的一半，每 5 秒問一次就平均晚 2.5 秒。想要更即時，只能把間隔縮短。

再看伺服器的負擔，用第 2 課的方法估算。假設尖峰時有 10 萬個 App 停在首頁（訂單狀態、集點、優惠都在首頁更新），每個 App 每 5 秒輪詢一次。一張訂單從成立到取餐有 4 次狀態變化（已收單、製作中、可取餐、已取餐），尖峰 2 小時有 2.4 萬張訂單。執行後先看前四行：每秒真正的狀態變化有幾次，以及三種間隔下的請求量；後兩行（長輪詢與 SSE）是下一節才介紹的做法，先放著。

每秒真正的狀態變化只有十幾次，但每 5 秒輪詢一次，伺服器每秒要處理 2 萬個請求，其中 99.9% 以上回「沒有更新」。這些請求不是免費的：每一個都要經過 nginx、驗證身分、查資料庫或快取，再回一個 JSON。想讓延遲變小，把間隔改成 2 秒，請求量變成每秒 5 萬，而有用的請求數一個都沒有增加。

這就是輪詢的本質：成本跟「客戶端數 ÷ 間隔」成正比，跟實際有沒有事件無關。訂單少的離峰時段，10 萬個 App 照樣每 5 秒問一次。反過來想，如果伺服器能在有事的時候才開口，工作量就只跟每秒十幾次的狀態變化有關。

💡 實務上：先問「晚幾秒可以嗎」，再挑技術
輪詢不是錯的。後台每 60 秒刷新的報表、只有幾十個使用者的內部工具，用輪詢最簡單，也沒有長連線要維運。PM 說「要即時」時，先問清楚能接受晚幾秒、有多少人同時在線：出單畫面晚 10 秒會讓店員漏單，集點數字晚 30 秒沒人在意。用數字判斷：客戶端多、要求即時、大部分時間沒有變化，才值得換成推送。很多團隊一開始用輪詢上線，使用者變多之後才換，換的時候只動「怎麼知道有變化」這一層，畫面拿資料的 API 不變。

讓伺服器有事才開口：長輪詢、SSE 與 WebSocket 怎麼選？

上一節的結論是：要省下那 99.9% 的空回應，就要讓伺服器等到有事才回答。有三種做法，差別在「等待」發生在哪裡。

長輪詢（long polling）是最小的改動：客戶端照樣送請求，但伺服器不馬上回，而是把請求掛著，等到訂單有新狀態才回應；一直沒有，就等到逾時（例如 30 秒）回一個「沒有更新」。客戶端收到任何回應後，馬上再送下一個請求。這樣空回應從每 5 秒一次變成每 30 秒一次，上一節範例的長輪詢那一行，請求量從每秒 2 萬降到每秒 3 千多。代價是伺服器上同時掛著 10 萬個等待中的請求，而且每送出一個事件，這個請求就結束了；連續兩個事件之間，客戶端得重新發一次請求，第二個事件要等新請求到了才送得出去。

SSE（Server-Sent Events）把「掛著的請求」再往前推一步：既然回應可以晚一點才寫，那就永遠不結束它。客戶端送一個普通的 GET，伺服器回 Content-Type: text/event-stream，然後不結束這個回應，有事件就往裡面寫一段文字。同一條連線可以送好幾個小時、好幾百個事件，不必每次重發請求。這種建立後一直開著、持續好幾分鐘甚至好幾小時的連線，叫長連線。瀏覽器用內建的 EventSource 接收，斷線會自動重連。方向是單向的：只有伺服器往瀏覽器寫；瀏覽器要送東西給伺服器，另外發一般的 HTTP 請求。上一節範例的 SSE 那一行：伺服器要同時維持 10 萬條連線，但每秒只送十幾個事件，加上定期的心跳（每次只有幾個位元組，用途在後面「部署到 nginx 後面」那一節講）。

WebSocket 走得最遠：它一開始也是一個 HTTP 請求，但這個請求要求「升級」（Upgrade）成另一個協定；伺服器同意後，這條 TCP 連線就不再說 HTTP，改成雙方都能隨時送訊息的通道。它是雙向的，適合客戶端也要頻繁送東西的情境。握手時的標頭和相關 RFC 放在課末「補充與查表」。

回到取餐通知。「訂單狀態更新」只有伺服器往瀏覽器的方向；客戶端偶爾要做的事（取消訂單）用一般的 HTTP 請求就好。這種情況選 SSE：它就是 HTTP，瀏覽器內建重連與續傳用的事件 ID，代理、身分驗證、日誌都沿用原本的設定。WebSocket 留給真的需要雙向、頻繁互動的功能。表格最後兩列說 WebSocket 的重連和補資料要「全部自己寫」，具體是哪些，等後面「手機進電梯再出來」那一節看完 SSE 怎麼續傳就會清楚。

選了 SSE，成本就從「大量的短請求」換成「10 萬條同時開著的長連線」。這一課後面處理的，都是很多條長連線帶來的問題。第一步是搞清楚這條不結束的回應裡，到底傳了什麼。

SSE 的回應裡傳的是什麼？自己讀串流時怎麼解析？

選定 SSE 之後，先看伺服器實際寫進那條連線的內容。Node 課第 16 課寫過 SSE 伺服器，它送出的回應本體是 UTF-8 文字，一行一個欄位，空行代表「一個事件結束，送出」。下面是王小明那張訂單的串流：

: 這一行是註解，用來當心跳
retry: 5000

id: 1041
event: order-status
data: {"orderId":41,"status":"making"}

id: 1042
event: order-status
data: {"orderId":41,
data: "status":"ready"}

由上往下讀：冒號開頭的第一行是註解，瀏覽器會忽略它，所以伺服器可以拿它當心跳，證明連線還活著。retry 告訴瀏覽器斷線後等 5000 毫秒再重連。接下來是兩個事件，每個事件以空行收尾：id 是事件編號，event 是事件類型，data 是內容。第二個事件的 data 寫成兩行，瀏覽器會用換行把它們接起來，所以收到的仍然是一段完整的 JSON。

瀏覽器端用 EventSource 接收，解析都由它做：

const es = new EventSource('/orders/41/events')
es.addEventListener('order-status', e => {
  const { status } = JSON.parse(e.data)   // e.lastEventId 是 '1042'
  render(status)
})

大多數時候這樣就夠了。但有兩種情況要自己解析：一是 EventSource 不能自訂標頭，你的 API 如果要帶 Authorization 標頭，就得改用 fetch 自己讀回應串流；二是在 Node 或 Worker 裡接收別的服務送來的 SSE，那裡沒有 EventSource。自己解析時，要照 WHATWG HTML 標準（Living Standard）定義的規則做，EventSource 內部也是照這份規則。下面這份清單是練習 1 的規格，查表用，不用背：

  • 開頭的 BOM（位元組順序記號，字元 \uFEFF）去掉一次。
  • 行尾可以是 CRLF（\r\n）、LF（\n）或單獨的 CR（\r）。
  • 空行：送出目前累積的事件。
  • 冒號開頭的行是註解，忽略。
  • 其他行：第一個冒號之前是欄位名，之後是值；值如果以空白開頭，只去掉一個空白。沒有冒號時整行是欄位名，值是空字串。
  • data：把值加上 \n 附加到資料緩衝。所以多行 data 會用換行接起來。
  • event：設定事件類型。沒設定時類型是 message（es.onmessage 收的就是它）。
  • id：值裡沒有 NULL 字元（\u0000）才採用，設定「最後的事件 ID」。這個值送出後不會清掉，之後的事件都沿用，直到下一個 id。
  • retry：值全是 ASCII 數字才採用，設定斷線後等多少毫秒再重連。
  • 其他欄位名：忽略。
  • 送出時：資料緩衝是空的就不送（只清掉類型）；否則去掉最後一個 \n 再送出。送出後清空資料緩衝與事件類型。
  • 串流結束時，最後一個沒有空行收尾的事件丟掉。

每一條規則單獨看都單純，難的是資料怎麼到達。TCP 傳的是一連串位元組，不保留「訊息」的邊界：伺服器寫一次 res.write()，瀏覽器可能分兩次收到，也可能把兩次寫入合成一次收到；路上的代理、壓縮、TLS 都可能重新切。所以解析器每次拿到的一塊資料（chunk）可能停在任何位置：一行的中間、一個 \r\n 的 \r 和 \n 之間、甚至 UTF-8 解碼後的任何字元之間。

下面這個解析器只在每個 chunk 內部找事件，不記得上一塊剩下什麼。執行後看三件事：一次收到時結果正確；同一段串流被切成兩塊時，JSON 被切成兩半；只用 CR 換行時，兩個事件被黏成一個，內容也帶著 \r 和下一行的欄位名。

正確的做法是讓解析器有記憶：把收到的文字累積在緩衝裡，只處理已經看到行尾的完整行，剩下的半行留到下一次 push。CR 最麻煩：chunk 剛好結束在 \r 時，你不知道下一塊是不是以 \n 開頭。可以先把這一行當成結束（CR 本身就是合法的行尾），記住「下一個字元如果是 \n 就跳過」，不然 \r 和 \n 會被當成兩個行尾，中間多出一個空行，事件被提早送出。練習 1 要你寫出這個解析器，測試會把同一段串流在每一個位置切開，結果都要一樣。

解析器能把每一個事件正確收下來，前提是連線一直開著。手機的連線不會一直開著。

手機進電梯再出來，漏掉的「可以取餐了」怎麼補？

手機從 Wi-Fi 切到 4G、進電梯、App 被切到背景，連線都會斷。斷線期間「拿鐵可以取餐了」這個事件送出去了，王小明的 App 沒收到，畫面永遠停在「製作中」。他會一直等，直到想起來去櫃檯問，咖啡已經涼了。

SSE 為這件事設計了兩個機制，剛才的格式裡都看過。第一個是自動重連：連線斷了，瀏覽器等 retry 指定的時間後自己重新發 GET。第二個是事件 ID：伺服器替每個事件加上遞增的 id，瀏覽器記住收到的最後一個；重連時，瀏覽器自動在請求標頭帶上 Last-Event-ID，等於告訴伺服器「我收到 1042 為止」。

伺服器要做的是另一半：記住最近送過的事件，才有東西可以補。做法是為每個頻道（例如一間門市、一張訂單）保留最近 N 個事件，依 Last-Event-ID 把之後的事件補送。為什麼只保留 N 個？因為事件永遠在產生，全部留著記憶體遲早用完。只保留最近 N 個、新的進來就擠掉最舊的，這種結構叫環狀緩衝（ring buffer）。

緩衝有上限，就代表斷線太久的客戶端要的事件可能已經被擠掉了。這時候不能假裝沒事、從還留著的最舊那個開始補：中間被擠掉的事件會被悄悄跳過，客戶端以為自己什麼都沒漏。要明確告訴客戶端「續傳不了」，讓它重新整理整份狀態。下面的時間軸一步一步看這三種結果：補得到、剛好補得到、補不到。

還有兩種要 reset 的情況：Last-Event-ID 不是合法的數字（被竄改或格式錯誤），以及它比目前最新的還大。後者通常代表伺服器重啟過、記憶體裡的緩衝和 ID 都從頭開始了，客戶端手上的 ID 屬於上一輪，數字比較沒有意義。正式環境的 ID 可以用資料庫的序號（例如第 12 課 outbox 表的 id），重啟後也不會倒退。練習 2 實作這個緩衝。

自動重連本身也有例外，不能完全依賴它：

EventSource 的自動重連只發生在網路錯誤或連線正常結束時。伺服器回 200 以外的狀態碼（401、503）或 Content-Type 不是 text/event-stream，WHATWG 標準規定「fail the connection」：readyState 變成 CLOSED，不會再重連。所以在 onerror 裡要檢查 es.readyState === EventSource.CLOSED，自己用退避加 jitter 重建連線（401 時先去換新的憑證）。標準也提到可以用 204 No Content 叫客戶端停止重連。

把這一節看到的放在一起：推送可能遺失（斷線、緩衝被擠掉）、可能重複（補送時有些事件客戶端其實收過）、可能在 reset 後整個重來。所以要守住一條原則：推送只是通知，狀態以 API 為準。落到程式上是四件事：

  • 畫面的初始狀態一律從 API 拿；推送只負責「有變化了」。
  • 客戶端套用事件要冪等（第 9 課：同一件事做兩次，結果跟做一次一樣）：事件帶訂單的版本號或序號，比手上舊的就丟掉，跟第 16 課的投影一樣。
  • 收到 reset、或重連後不確定有沒有漏，就重新拿完整狀態。
  • 重要的狀態（付款成功）不能只靠推送通知：使用者打開訂單頁時也要能查到。
💡 實務上：前端最常漏的是「回到前景」那一刻
寫訂單頁時，常見的 bug 是 App 在背景待了十分鐘，回到前景後畫面還是舊的，因為瀏覽器暫停了分頁或連線早就斷了。做法很單純：監聽 visibilitychange 或網路恢復（online 事件），回到前景就重新呼叫一次 API 拿完整狀態，再接上推送。把「收到推送」和「重新拿狀態」都交給同一個更新函式處理，新舊只在這裡比一次版本號，才不會兩條路各寫一套、結果不一致。Code review 看到推送事件直接改畫面、卻沒有初始的 API 呼叫，就要問一句「斷線期間的變化怎麼辦」。

如果當初選 WebSocket，這些要自己寫多少？

上一節的續傳，SSE 一半是瀏覽器內建的：自動重連、記住最後的 ID、重連時帶上 Last-Event-ID。「讓伺服器有事才開口」那一節說 WebSocket 的重連和補資料要「全部自己寫」，現在可以具體列出來。WebSocket 給你一條雙向的管子，雙方傳的是一個一個的訊框（frame），其他都要自己設計：

  • 沒有確認與重送：協定本身不保證對方處理了哪些訊息。斷線時，路上的訊息就沒了，要自己替訊息編序號、重連後告訴伺服器「我收到第幾號」、伺服器補送，跟 SSE 的 Last-Event-ID 是同一件事，只是要自己寫。
  • 沒有自動重連：瀏覽器的 WebSocket 斷了就是斷了，重連、退避、jitter 都是應用程式的事。
  • 訊息格式自己定：哪一種訊息、怎麼回應、錯誤怎麼表示，沒有 HTTP 的狀態碼和標頭可以用。
  • 身分驗證只發生在建立連線時：瀏覽器的 new WebSocket(url, protocols) 不能自訂標頭，常見做法是用 cookie，或先用一般 API 換一張短效、只能用一次的票券放在網址上（網址會進存取日誌，所以不能放長效 token）。用 cookie 時，伺服器要檢查 Origin 標頭是不是自己的網站（RFC 6455 第 10.2 節：不認可的來源回 403），否則別的網站可以在使用者的瀏覽器裡帶著他的 cookie 開連線（跨站 WebSocket 劫持，cross-site WebSocket hijacking）。
  • 代理要另外設定：nginx 轉送 WebSocket 要加 Upgrade、Connection 標頭（部署課第 12 課）。

它也有 SSE 沒有的東西：協定內建 Ping／Pong 控制訊框，收到 Ping 必須回 Pong，可以當心跳、確認對方還活著。但對取餐通知來說，上面那份清單全是額外的工作，換來的雙向能力用不到。

清單裡的身分驗證，帶出一個 SSE 也有的問題：長連線上的身分會過期。一般 API 每個請求都重新驗一次 token，長連線只在建立時驗一次。連線建立時 token 還有效，兩小時後使用者已經登出或被停權，連線還開著，推送照樣送到。伺服器要記住每條連線的身分到期時間，到期就關掉連線，讓客戶端帶新的憑證重連；權限被撤銷時（例如店員離職），也要主動關掉那個人的連線。

到這裡，一台伺服器上的取餐通知已經完整：送得出去、斷了補得回來。但尖峰 10 萬條連線不會只放在一台機器上。

好幾台伺服器時，A 機的事件怎麼送到 B 機的連線？

只有一台伺服器時，「訂單 41 變成可取餐」這件事發生在哪個程序，就從哪個程序推送，連線和事件在同一個地方。擴展成多台之後，兩者會分開：王小明的 SSE 連線接在 B 機，店員按「可取餐」的 API 請求卻落在 A 機。A 機手上沒有王小明的連線，它也不知道王小明的連線在哪一台。最簡單可靠的做法是 A 機把事件送到每一台可能有訂閱者的機器，再由每台機器送給自己手上的連線。一個事件送給很多個訂閱者，叫扇出（fan-out）。

負責「把事件送到每一台」的，通常是一個發布／訂閱（pub/sub）系統：每台 SSE 伺服器啟動時訂閱訂單事件的頻道，A 機把事件發布到頻道，所有訂閱者都收到一份。常見的工具是 Redis 的 pub/sub（PUBLISH／SUBSCRIBE）；只有一個資料庫、程序不多時，Node 課第 24 課的 PostgreSQL LISTEN／NOTIFY 也能做。

要注意它的送達保證。Redis 文件寫明 pub/sub 是至多一次（第 12 課）：Redis 把訊息交給當下連著的訂閱者就算完成，不保存、不等確認；訂閱者當時沒連上、或處理時出錯，那則訊息就永遠遺失，Redis 不會重送。SSE 伺服器重啟、跟 Redis 的連線閃斷，都會漏掉事件。所以分工要清楚：pub/sub 只負責「快」，「不漏」要靠前一節的續傳緩衝與 reset（或改用可保存、能從某個位置重讀的 Redis Streams）。事件本身要從 outbox 送出，訂單寫入和事件才不會一個成功一個失敗。

一支訊號很差的手機，會不會拖垮整台伺服器？

事件扇出到每台之後，每台要把它寫進自己手上的幾萬條連線。這裡有一個只有在扇出時才會冒出來的問題：連線的另一端讀得有多快，不是伺服器能控制的。

伺服器寫進連線的資料，會先放進作業系統替這條連線準備的 socket 緩衝，再由網路慢慢送出。客戶端讀得慢、網路差，socket 緩衝滿了，寫不進去的資料就堆在程序的記憶體裡。讀得比事件產生得慢的客戶端叫慢消費者（slow consumer）。Node 課第 16 課教過背壓（backpressure）：下游處理不了時，要上游放慢或停止。但扇出時上游是「整間門市的事件」，不能因為一支訊號很差的手機，就讓出單畫面和其他 50 個顧客都等它。

做法是每條連線一個有上限的送出佇列，讓慢的只影響自己：

  • 發布事件是同步的：放進每個訂閱者自己的佇列就走，不等任何人寫完。
  • 某條連線的佇列已經滿了，直接斷掉這條連線，不是默默丟掉這個事件。默默丟掉，客戶端不知道自己漏了，畫面永遠錯；斷線後它會重連，用 Last-Event-ID 補資料，太舊就 reset。這裡用上了前一節的續傳：斷線不是失敗，而是一條已經設計好的恢復路徑。
  • 取消訂閱（連線關閉）時，從頻道移除並釋放佇列，不然記憶體只增不減。

上限要設多少，用記憶體算。假設 10 萬條連線平均分在 4 台機器上，執行後看三種上限下，每台在最壞情況要多少記憶體：

佇列上限 10000 時，最壞情況每台要 93 GB，遠超過機器的記憶體，程序會被作業系統殺掉，所有連線一起斷、一起重連。上限 100 時最壞不到 1 GB。這裡的事件大小是假設值，正式環境要量自己的事件大小，以及每條連線本身的固定成本（socket 緩衝、TLS 狀態、框架物件），一起算出每台能放多少連線。練習 3 實作這個扇出。

到這裡，程式的邏輯都對了：多台機器、慢客戶端、斷線續傳都有處理。接下來要把它部署到真正的網路上，而 SSE 最常壞掉的地方就在那裡。

部署到 nginx 後面，為什麼事件會卡住、連線會被切斷？

前面的一切在本機都能正常運作，因為瀏覽器直接連到 Node，中間什麼都沒有。正式環境裡，請求會先經過負載平衡器、nginx，有時還有 CDN，每一層都是為「短請求、很快回完」設計的，遇到一條好幾小時不結束的回應就會出狀況。SSE 部署到 nginx 後面就壞掉，原因幾乎都是下面這幾個：

症狀原因做法
事件要等很久才一次出現好幾個，或連線結束才收到nginx 的 proxy_buffering 預設是 on，會先把上游的回應收進緩衝SSE 回應加標頭 X-Accel-Buffering: no（nginx 文件：上游回應可以用這個標頭關掉緩衝），或在那個 location 設 proxy_buffering off。如果有對 text/event-stream 開壓縮（nginx 的 gzip_types、或應用程式的壓縮中介層），也要關掉：壓縮器會先攢一批資料再送
沒有事件時，連線每 60 秒斷一次nginx 的 proxy_read_timeout 預設 60 秒，是兩次讀取之間的逾時，不是整個回應的上限；雲端負載平衡器也有閒置逾時送心跳（heartbeat）：每隔一段時間送一行註解（: ping），間隔要比路上最短的閒置逾時短。WHATWG 標準建議大約每 15 秒一次。也可以調高 proxy_read_timeout，但心跳還是要有
開到第 7 個分頁，新分頁一直轉圈，連一般 API 都卡住HTTP/1.1 時，瀏覽器對同一個網域最多 6 條連線（MDN；Chrome、Firefox 標記為不修），6 個分頁各開一條 SSE 就用完了走 HTTP/2：同一條連線上多工，同時的 stream 數由伺服器設定（HTTP/2 規格 RFC 9113 建議至少 100）。或只讓一個分頁連線，用 BroadcastChannel（瀏覽器內建、同網域分頁之間互傳訊息的 API）分享給其他分頁
伺服器以為客戶端還在，其實手機早就沒訊號沒有收到 TCP 的關閉，連線看起來還開著心跳也能幫伺服器發現死掉的連線：寫入失敗或送出佇列一直不動，就關掉。WebSocket 用 Ping／Pong

前兩列的原因都一樣：代理預設「回應會很快結束」。緩衝讓 nginx 先把上游的回應收好再轉送，閒置逾時用來回收卡住的連線，對一般 API 都是好設定，對 SSE 就變成把事件攢著不送、把安靜的連線當成卡住。心跳在「SSE 的回應裡傳的是什麼」那一節的格式裡看過，就是那行冒號開頭的註解：瀏覽器忽略它，但路上的每一層都看到「有資料在流動」。

連線開得夠久之後，還會碰到伺服器這一端的兩個上限。第一個是檔案描述子（file descriptor）：作業系統用它代表程序開著的每一個檔案或連線，每條長連線都佔一個。程序能開的數量有上限（ulimit -n），Linux 預設的軟限制常常只有 1024，一台要撐幾萬條連線就要先調高。

第二個是負載平衡的分配方式。第 4 課的輪流分配（round robin）假設每個請求差不多長，輪著分下去每台的工作量就平均。長連線一接就是好幾個小時，這個假設不成立：新上線的機器只會分到新連線，舊機器上的連線一直不走、一直滿載。改用最少連線，看的是每台目前開著的連線數，新連線優先給最閒的機器。

💡 實務上：在跟正式環境一樣的路徑上測
這一節的問題在本機 localhost 都看不到，因為中間沒有 nginx、負載平衡器、CDN。上線前在 staging 走完整條路徑測一次：開著頁面放 5 分鐘不動，看連線有沒有被切斷；觸發一個事件，看是馬上出現還是等很久才一起出現。新增 SSE 或 WebSocket 端點時，要先跟負責基礎設施的人確認每一層的閒置逾時、有沒有緩衝或壓縮、能不能走 HTTP/2，這些設定通常不在應用程式的程式碼裡。

重新部署時，幾萬條連線同時重連怎麼辦？

上一節處理的都是穩定運作時的問題。取餐通知最危險的時刻，反而是自己重新部署的那幾分鐘。舊程序要停掉，它身上的 2.5 萬條連線同時斷開。前面設計的每一個機制在這時都會被觸發：這些客戶端在同一秒重連，打到還活著的機器，每個重連都要驗證身分、查補送的事件，reset 的還要呼叫 API 拿完整狀態，資料庫跟著被打爆。這叫重連風暴（reconnect storm）。更糟的是連鎖反應：被打爆的機器回 503，EventSource 不再自動重連（前面斷線續傳那一節的警告），客戶端的重試邏輯如果沒有 jitter，下一波又是同一秒。

問題不在總數，而在集中。2.5 萬個重連攤在一分鐘裡，其他機器撐得住；擠在同一秒就撐不住。下面模擬三種做法，執行後比較每一種「最忙的那一秒」有幾個重連：

固定 3 秒重連時，2.5 萬個全部擠在同一秒；把重連時間隨機攤在 30 秒裡，最忙的一秒不到一千個；伺服器再花 60 秒分批關閉連線，又降到一半左右。三個手段一起用：

  • 伺服器慢慢排空（部署課第 13 課）：收到停止訊號後先不接新連線，在一段時間內分批關掉現有連線，而不是一次全斷。
  • 客戶端重連加 jitter（第 8 課）：自己寫的重連要退避加 jitter。EventSource 自動重連的等待時間由 retry 欄位決定，伺服器可以在關閉連線前替每條連線送一個隨機的 retry 值，把重連攤開。
  • 續傳緩衝不能放在要被關掉的程序裡：只存在記憶體的緩衝會跟著程序消失，重連的人全部 reset、全部打 API。緩衝可以放在 Redis、或直接從 outbox 表依 id 查。

這三個手段都是事前的設計，有沒有效要靠上線後的數字確認。

練習

練習 1：完成 SseParser，依 WHATWG 規則解析 text/event-stream。push(chunk) 會被呼叫很多次，每次給一段已經解碼的文字，可能停在任何位置，回傳這段文字讓哪些事件完成（依序）。

  • 第一個不是空字串的 chunk 開頭如果是 \uFEFF，去掉（只有串流開頭這一次）。
  • 行尾是 \r\n、\n 或單獨的 \r；\r 在 chunk 結尾時，下一塊開頭的 \n 屬於同一個行尾。還沒看到行尾的半行留到下一次 push。
  • 冒號開頭的行忽略。欄位名是第一個冒號之前的文字，值是冒號之後、去掉最多一個開頭空白；沒有冒號時整行是欄位名、值是 ''。
  • data：值加上 \n 附加到資料緩衝；event：設定類型；id：值裡沒有 \u0000 才更新最後的事件 ID（之後的事件都沿用，空值也算更新）；retry：全是數字（0～9）才採用，retry() 回傳最後一次採用的值，沒有就是 null。其他欄位忽略。
  • 空行：資料緩衝是空的就不送出（但清掉類型）；否則送出 { type, data, lastEventId }，data 去掉最後一個 \n，type 沒設定時是 'message'。送出後清空資料緩衝與類型。

練習 2：完成 EventLog<T>，伺服器替一個頻道保留最近的事件，讓重連的客戶端依 Last-Event-ID 補資料。

  • append(data)：新增一個事件，回傳 { id }，id 是從 '1' 開始遞增的整數字串。只保留最近 capacity 個。
  • since(lastEventId)：
    • null（新連線，客戶端會先用 API 拿完整狀態）→ { kind: 'replay', events: [] }。
    • 不是我們發出的 id 格式（正整數、沒有前導 0、空白、小數點或正負號，例如 'abc'、'-1'、'1.5'、'0'、'04'）→ { kind: 'reset' }。
    • 比目前最新的 id 還大（伺服器重啟過或被竄改）→ reset。
    • lastEventId 之後的事件全部還在緩衝裡 → replay 這些事件（依 id 由小到大，可能是空陣列）。
    • 有任何一個已經被擠掉 → reset。

練習 3：完成 Hub<M>，一台 SSE 伺服器內部的扇出：從 pub/sub 收到的事件，放進這個頻道每條連線自己的送出佇列。

  • subscribe(channel, { maxQueue, onDrop })：新增一個訂閱者，回傳 { id, take, unsubscribe }，id 每個訂閱者不同。
  • publish(channel, msg)：同步地把訊息放進這個頻道每個訂閱者的佇列。某個訂閱者的佇列已經有 maxQueue 個時，不放入，改為移除這個訂閱者、清空它的佇列，並呼叫一次它的 onDrop（讓連線關閉、客戶端重連補資料）。其他訂閱者照常收到。
  • take(n)：依序取出最多 n 個（模擬連線把資料寫出去）。被移除或取消訂閱之後回傳 []。
  • unsubscribe()：從頻道移除、清空佇列；之後不再收到，也不會呼叫 onDrop。呼叫第二次沒有作用。
  • subscriberCount(channel)：這個頻道目前的訂閱者數。

練習 4：尖峰時有 10 萬個 App 停在首頁，每 5 秒輪詢一次訂單狀態。同事說：「輪詢就是一般的 GET，很便宜。」伺服器每秒要處理多少請求？

✓ 輪詢的請求量是「客戶端數 ÷ 間隔」＝ 100,000 ÷ 5 ＝ 20,000，跟有沒有事件無關；尖峰時每秒真正的狀態變化只有十幾次（a 是推送的事件數，不是輪詢的請求數）。每個請求都要驗證身分、查資料，快取只能減少查詢成本，請求還是要進來（b）。d 把間隔乘錯了方向。

練習 5：出單畫面的 SSE 在本機正常，部署到 nginx 後面之後，店員要等很久才一次看到好幾張訂單，有時要等連線斷掉才出現。最可能的原因？

✓ nginx 的 proxy 模組文件寫明 proxy_buffering 預設 on，上游回應可以用 X-Accel-Buffering: no 關掉。本機直連沒有代理，所以正常（a 不成立，EventSource 收到空行就送出事件）。proxy_read_timeout（c）太短的症狀是「沒事件時每 60 秒斷一次」，事件不會被攢著；而且它是兩次讀取之間的逾時，該用心跳解決，不是調成很大的數字。

練習 6：重新部署時，一台伺服器上的 2.5 萬條 SSE 連線同時被關掉。同事說：「瀏覽器會自動重連，幾秒就好了，不用處理。」實際會發生什麼，該怎麼做？

✓ 問題不在連線總數，而在同一秒：每個重連都要驗證身分、查補送的事件，reset 的還要打 API（b 只看了平均）。被打爆的機器回 503 時，WHATWG 標準規定回應不是 200 時 EventSource 不再重連，客戶端要自己退避加 jitter 重建。c 只是把重連搬到應用程式裡，沒有 jitter 照樣是風暴，還要自己補資料。

練習 7：每台 SSE 伺服器都用 Redis pub/sub 訂閱訂單事件。某台機器跟 Redis 的連線閃斷了 2 秒又連回來。這 2 秒內發布的事件會怎樣？

✓ Redis 文件寫明 pub/sub 是 at-most-once：送出之後不會再送，訂閱者斷線或出錯時那則訊息就永遠遺失（a、b 都不成立，pub/sub 沒有 ack 也不保存）。所以 pub/sub 只負責快速扇出，「不漏」要靠能依 id 重讀的地方（outbox 表、Redis Streams）加上客戶端的 Last-Event-ID 與 reset。

常見錯誤

  • 單向通知也用 WebSocket：重連、續傳、訊息格式、代理設定都要自己做。只有伺服器往客戶端推送時，SSE 都內建了。
  • 用 split('\n') 解析、不保留半行：單獨的 CR、被切開的 CRLF、被切開的 JSON 都會出錯。累積緩衝，只處理完整的行。
  • 把推送當成狀態來源：推送會遺失、重複、reset。初始狀態從 API 拿，套用事件要冪等，重連後不確定就重新整理。
  • 續傳時從最舊的開始補：中間被擠掉的事件被悄悄忽略。補不了就 reset。
  • 只靠 EventSource 的自動重連：回應不是 200 時它就不再重連。在 onerror 檢查 CLOSED，自己退避加 jitter 重建。
  • 長連線的身分過期了卻沒處理：使用者登出、被停權後還收得到推送。記住到期時間，到期或權限撤銷就關掉連線。
  • 以為 Redis pub/sub 不會漏：它是至多一次。搭配續傳緩衝或可保存的串流。
  • 每條連線的送出緩衝沒有上限：一群慢的客戶端吃光記憶體，整台機器被殺掉。設上限，滿了就斷線讓它重連補資料，不要默默丟掉訊息。
  • 代理緩衝 SSE：事件被攢著，連線結束才送出。回應加 X-Accel-Buffering: no，關掉這條路徑的壓縮。
  • 沒有心跳：沒事件時代理或負載平衡器把閒置連線切掉（nginx 預設 60 秒沒讀到東西就斷）。定期送註解行，間隔比路上最短的閒置逾時短。
  • 每個分頁一條 SSE、走 HTTP/1.1：超過 6 條，同網域的其他請求也被卡住。用 HTTP/2，或一個分頁連線、用 BroadcastChannel 分享。
  • 長連線用 round robin 分配：新機器一直很閒、舊機器一直滿。用最少連線。
  • 部署時沒有排空與 jitter：幾萬條連線同一秒重連。分批關閉、重連時間隨機化，續傳緩衝不放在要被關掉的程序裡。

小結

  • 輪詢的成本是「客戶端數 ÷ 間隔」，跟事件數無關；推送的成本跟事件數成正比，代價是很多條長連線。客戶端多、要即時、變化少時才值得推送。
  • 單向的狀態更新選 SSE（就是 HTTP，內建重連與 Last-Event-ID）；需要雙向、頻繁互動才用 WebSocket，它沒有確認、重送、重連，都要自己設計。
  • SSE 解析：三種行尾、空行送出、冒號開頭是註解、只去掉一個空白、id 會沿用、retry 只收數字；資料會在任何位置被切開，要累積緩衝並處理被切開的 CRLF。
  • 斷線續傳：每個頻道保留最近 N 個事件，依 Last-Event-ID 補送；補不了、id 不合法或比最新的還大就 reset，客戶端重新拿完整狀態。推送只是通知，狀態以 API 為準，套用事件要冪等。長連線的身分會過期，到期或撤權就關掉連線。
  • 多台伺服器：用 pub/sub 把事件扇出到每一台（Redis pub/sub 是至多一次，要搭配續傳）；每條連線一個有上限的送出佇列，發布不等任何人，慢的斷線重連。
  • 維運：關掉代理緩衝、心跳比閒置逾時短、HTTP/1.1 的 6 條上限、檔案描述子上限、最少連線負載平衡；部署時分批排空加 jitter；看連線數、佇列長度、被踢掉的數量、重連率、reset 次數。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：咖啡店的單體越改越亂，改集點常常弄壞下單。有人提議：「拆成微服務，各管各的就不會互相弄壞了。」資深工程師會怎麼回？

✓ 程式碼亂通常是模組邊界沒畫好，拆成服務只是把亂搬到網路上，還多了網路失敗與維運成本。預設模組化單體，等真的出現值得拆的訊號，再用 strangler fig 一塊一塊拆。a 錯在下單若同步呼叫集點，集點壞了下單一樣壞，而且改 API 還要協調兩邊上線。（第 15 課）

練習 9：訂單明細頁要同時顯示訂單內容和這筆訂單拿到的點數，點數在 loyalty 服務。loyalty 服務掛了 10 分鐘，這頁該怎麼處理？

✓ API composition 要區分必要與選用：訂單拿不到才失敗，點數拿不到就降級，逾時後用 AbortController 取消。b 讓選用的依賴變成硬相依，同步依賴的可用性相乘，loyalty 掛了訂單頁也跟著掛。c 是共用資料庫，loyalty 改欄位就打壞訂單服務，等於沒拆。（第 15 課）

練習 10：訂單服務付款成功後，透過訊息匯流排發出 SendReceiptEmail，收據服務收到就寄信。同事說：「走了匯流排，兩個服務已經解耦了。」對嗎？

✓ 判斷方法：明天多一個要知道付款的功能，發布者要改程式嗎？發 SendReceiptEmail 時要，因為訂單服務還在指揮別人做事。事件宣布已經發生的事實，格式由發布者決定，誰需要誰來聽。a 錯在非同步只解決了等待，沒解決「發布者知道下游要做什麼」的耦合。（第 16 課）

練習 11：訂單狀態的投影這樣消費訂單事件，已經依事件 ID 去重，匯流排是至少一次送達。哪裡會出事？

async function onOrderEvent(e) {
  await db.query('BEGIN')
  const r = await db.query(
    'INSERT INTO inbox (event_id) VALUES ($1) ON CONFLICT DO NOTHING', [e.id])
  if (r.rowCount === 1) await db.query(
    'UPDATE order_view SET status = $1 WHERE id = $2', [STATUS[e.type], e.data.orderId])
  await db.query('COMMIT')
  await ack(e)
}

✓ 重試、不同 partition、relay 重送都會讓舊事件晚到；事件 ID 只擋得住同一個事件來兩次，擋不住亂序。要記住每張訂單套用到第幾號，序號 ≤ 它就丟掉；不能改用事件的時間比，時間來自不同機器的時鐘。a 錯在 inbox 和更新在同一個交易，更新失敗時 inbox 那一列也一起回滾。（第 16 課）

練習 12：外送平台的 webhook 端點每次都 30 秒才逾時。從那天起，所有客戶收到通知都晚了好幾個小時。先改什麼？

✓ 所有客戶共用一條佇列時，一個慢客戶就占住送出用的連線，這是隔艙要解決的問題。b 讓它占得更久，其他人更晚收到。c 會讓外送平台恢復後永遠漏掉這些事件；失敗的要照退避排程重試，修好後還能用重播補。（第 16 課）

練習 13：App 要顯示「你的拿鐵做好了」，只有伺服器往手機推送，尖峰有 10 萬個 App 在線。同事提議用 WebSocket，你會怎麼選？

✓ 單向的狀態更新選 SSE：瀏覽器自動重連，並在標頭帶上最後收到的 id，伺服器照著補送。WebSocket 適合雙向、頻繁互動；它沒有確認、重送、重連，這些都要自己設計。c 是最常見的誤解，以為 WebSocket 比較「完整」，其實這些機制它都沒有。（第 17 課）

練習 14：訂單頁的 Vue 元件這樣寫，在本機測都正常。哪裡會出事？

const status = ref('')
onMounted(() => {
  const es = new EventSource(`/orders/${id}/events`)
  es.onmessage = (e) => {
    status.value = JSON.parse(e.data).status
  }
})

✓ 推送只是通知，會遺失、重複、reset，狀態以 API 為準：先呼叫 API 拿完整狀態再接推送，收到 reset 或回到前景就重新拿，套用時比版本號。a 錯在瀏覽器重連時會自動帶上這個標頭。b 是自己寫解析器才要處理的事，EventSource 收到空行才送出完整的事件。（第 17 課）

練習 15：一台 SSE 伺服器的記憶體在尖峰時一路漲到被系統砍掉，查下去是幾百個訊號很差的手機讀得很慢，事件都堆在它們的送出緩衝裡。該怎麼改？

✓ 慢消費者不能拖垮整台機器，也不能拖慢別人：發布不等任何人，佇列滿的就斷線，重連時再補。a 讓一支慢手機拖住所有人的推送。c 是最容易選的錯：默默丟掉事件，客戶端不知道自己漏了，畫面一直停在錯的狀態。（第 17 課）
