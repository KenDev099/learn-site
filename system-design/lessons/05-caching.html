階段 2：擴展：冗餘、快取與資料 · 第 5 課

快取：命中率、失效與擊穿

上一課把下單 API 放到好幾台機器後面，API 不再是瓶頸，壓力全部落到 PostgreSQL 身上。下個月是週年慶，第 2 課估過：尖峰時每秒約有 1,111 次在讀菜單，是平常的 20 倍。假設資料庫每秒只撐得住約 200 次菜單查詢，照現在的寫法，活動一開始資料庫就會被讀取淹沒，連下單一起失敗。可是菜單一天只改幾次，這 1,111 次查詢幾乎都在拿同一份資料，等於用資料庫最貴的容量重複做同一件事。

這課的任務：替菜單加上一層快取（cache），讓週年慶當天資料庫撐得住。快取就是把查過、算過的結果先存在比較快、比較便宜的地方，下次同樣的請求直接從那裡拿，不再問資料庫。把資料存進去只要幾行程式；這課要處理的是存進去之後的三個問題：店長改價後，顧客會不會一直看到舊價？熱門的菜單資料過期的那一瞬間，會不會幾百個請求同時衝去資料庫？快取自己壞了，資料庫會不會跟著倒？

這課的路線：
  1. 快取能省多少、資料怎麼放進去：命中率要多高資料庫才撐得住週年慶，菜單、購物車、訂單各該怎麼處理（開場問題的最小答案）。
  2. 改價之後：為什麼要刪除快取而不是更新它，刪除之後舊價為什麼還會被寫回去，lease 怎麼修。
  3. 過期的那一瞬間：熱門 key 過期時怎麼只打一次資料庫，大量 key 同時過期怎麼辦，能不能在過期前就先更新。
  4. 快取壞掉時與上線後：哪些資料不該快取、Redis 掛了怎麼不拖垮資料庫、週年慶當天要盯哪些指標。
這課會用到：
  • NestJS 課第 19 課的 Redis cache-aside：先查快取，沒有再查資料庫並放回快取；改價時刪除快取，Redis 壞掉時退回查資料庫。
  • TypeScript 課第 12 課的「同一個 key 共用同一個 Promise」：好幾個人同時要同一份資料時只查一次，大家等同一個結果。
  • PostgreSQL 課第 19 課的 lost update：兩個人交錯讀寫，後寫的蓋掉先寫的。

快取放哪裡、要擋下多少？命中率要多高才撐得住週年慶

要算命中率，得先知道算的是哪一層的命中率，所以先決定快取放在哪裡。一個請求從顧客的手機一路到資料庫，沿路每一層都可以放快取。越靠近使用者，命中時省下的路越多，但能放的東西越受限：瀏覽器裡的快取只有這一位顧客用得到，資料庫自己的快取只省下讀磁碟，網路和 API 的工作一樣都沒省。

這課會遇到的三個選擇（瀏覽器／CDN、程序記憶體、Redis）各適合放什麼，差別在「所有人看到的是不是同一份」和「多台機器要不要一致」：

層適合放不適合放
瀏覽器、CDN檔名帶雜湊的圖片、JS；所有人看到都一樣的公開菜單依登入身分而不同的內容（「我的訂單」）
程序記憶體（Map、LRU）極熱門、很小、晚幾秒沒關係的資料（門市清單）要多台一致的資料：每台各有一份，改價後各台過期時間不同
Redis多台共用的查詢結果、session、購物車以它為準的金額、付款狀態

咖啡店的 API 有好幾台，改價後希望每台看到的菜單一致，所以菜單放 Redis：所有 API 共用同一份，改價時只要處理一個地方。

放好之後，要知道它替資料庫擋下了多少。每一次讀取，快取裡有這筆資料、直接拿到，叫命中（hit）；沒有，只好回資料庫查，叫未命中（miss）。所有讀取裡命中的比例叫命中率（hit ratio），記作 h。只有未命中的讀取會到資料庫，所以：

平均延遲     = h × 命中延遲 + (1 − h) × 未命中延遲
資料庫讀取量 = (1 − h) × 總讀取量

第二個算式很反直覺。命中率從 90% 到 99%，看起來只多了 9 個百分點，但到資料庫的比例從 10% 變成 1%，資料庫的負載變成原本的十分之一。命中率越接近 100%，每多一個百分點，資料庫少扛的比例越大。用週年慶尖峰的每秒 1,111 次讀取跑跑看，假設命中花 1ms、未命中 25ms，執行後看每一列的「資料庫每秒幾次」：

回到開場的數字：資料庫每秒只撐 200 次，就要 (1 − h) × 1,111 ≤ 200，命中率至少約 82%。表裡 90% 時資料庫每秒約 111 次，還撐得住；命中率掉到 50%，資料庫每秒要扛 555 次，就倒了。練習 1 會把這個算法寫成函式。

這個算式也透露了這個快取的身分。Google SRE 書〈Addressing Cascading Failures〉把快取分成兩種：拿掉它，系統只是變慢，叫延遲型快取（latency cache）；拿掉它，系統就撐不住負載，叫容量型快取（capacity cache）。週年慶的菜單快取是容量型的：命中率一掉到 0，每秒 1,111 次全部壓到只撐 200 次的資料庫上。所以快取空掉的時候，例如 Redis 重啟、擴容、一大批資料同時過期，服務會倒。這課最後一節會回來處理怎麼保護。

快取不是免費的。它帶來三個代價，後面每一節都在處理其中一個：

  • 資料可能過時：店長改了價格，快取裡還是舊的。
  • 失效邏輯：每一個會改資料的地方，都要記得處理對應的快取。漏一個就是 bug，而且很難重現。
  • 多一個會壞的元件：Redis 也會當機、也會滿、也會慢。
💡 實務上：先找出慢在哪，再決定要不要加快取
工作中常聽到「API 很慢，加個 Redis 吧」。資深工程師會先問：慢的是哪一支查詢？用 EXPLAIN 看過了嗎？很多時候補一個索引、修掉 N+1 查詢（在迴圈裡一筆一筆查資料庫）就夠了，根本不需要多一個會壞、要維運的元件。真的要加時，再問 PM「價格晚幾秒、幾分鐘更新可以接受嗎？」，這個答案決定 TTL（下一節會講）；同時在設計文件寫清楚這個快取是延遲型還是容量型，維運才知道它掛掉時會發生什麼事。週年慶的菜單快取，兩個問題的答案都要先寫下來。

知道命中率要 82% 以上之後，下一個問題是：資料一開始是怎麼進到快取的？誰負責放、什麼時候放？

資料怎麼進到快取？菜單、購物車、訂單各怎麼處理

最常用的做法是 NestJS 課第 19 課寫過的 cache-aside，又叫 lazy loading：快取擺在資料庫旁邊（aside），由應用程式自己決定什麼時候去查、什麼時候放進去。讀菜單時，API 先問 Redis；有就直接回傳；沒有就查資料庫，把結果放進 Redis，再回傳。只有真的被讀過的資料才會進快取，這就是「lazy」。寫入時，API 先改資料庫，再處理快取裡對應的那一筆。Redis 壞了，API 還能直接查資料庫，因為資料庫才是真正的資料來源，快取只是副本。

副本放進快取之後要放多久？資料庫改了、快取卻沒人處理，舊資料會永遠留著。所以每一筆快取都要設 TTL（time to live，存活時間）：放進去之後經過這段時間，就當作不存在，下一次讀取會未命中、重新查資料庫。TTL 決定了「最壞情況下舊資料會留多久」，也就是上一節 💡 要問 PM 的那個數字。

TTL 到期之前，快取的記憶體也可能不夠放。這時快取會淘汰（eviction）一部分資料騰出空間，例如 Node 課第 23 課寫過的 LRU（least recently used）：丟掉最久沒被讀過的那幾筆。被淘汰的資料下次讀取一樣會未命中，所以淘汰太多也會拉低命中率。

cache-aside 不是唯一的做法。四種常見策略的差別在「讀的時候誰去資料庫拿」和「寫的時候快取怎麼跟著變」：

策略讀寫優點風險
cache-aside（又叫 lazy loading）應用程式先查快取，未命中再查資料庫並寫回快取寫資料庫，刪除快取只快取真的被讀的資料；快取壞了還能退回資料庫未命中要多走兩趟；可能過時
read-through應用程式只問快取，由快取層自己去資料來源載入同 cache-aside載入邏輯集中在一處同 cache-aside；需要支援的快取函式庫或服務
write-through同 cache-aside寫資料庫時同步更新快取讀的時候比較少過時快取很多沒人讀的資料；新節點一開始是空的；兩個寫入交錯時仍可能留下舊值
write-behind（又叫 write-back）讀快取先寫快取，之後批次寫回資料庫寫入非常快快取在寫回前壞掉，資料就遺失了

AWS 的快取策略文件對 cache-aside 和 write-through 的比較也是這樣，並建議兩者都要加上 TTL。write-behind 的風險最值得記住：資料只存在快取裡的那段時間，快取一壞就沒了，所以它不適合任何不能掉的資料。

咖啡店的三種資料，各自對應不同的選擇，判斷依據是「錯了或晚了會怎樣」：

  • 菜單：cache-aside 加 TTL。讀很多、改很少，顧客晚幾秒看到新價格可以接受。
  • 購物車：直接放 Redis 當主要儲存（部署課第 13 課）。這不是快取，購物車的資料本身就只存在 Redis，所以要設好 TTL，也要開持久化：讓 Redis 定期把資料寫到磁碟，重啟後不會全部消失。
  • 訂單、付款狀態、結帳時的價格與庫存：不快取，一律讀資料庫。錯一次就是錯帳。

到這裡可以先給開場三個問題的最小答案：資料改了就刪掉快取，不要更新它；熱門 key 過期時，只讓一個請求去資料庫，其他人等它的結果；快取壞了，要限制打到資料庫的量，不能全部放過去。接下來每一節把其中一個答案講透，先從改價開始：cache-aside 的寫入說「刪除快取」，為什麼不是直接把快取改成新價？

店長改價之後，快取要更新還是刪除？

店長把拿鐵從 110 改成 120。資料庫改完之後，快取裡的 price:2 要怎麼處理？直覺是「把快取也改成 120」，這樣下一個讀取馬上看到新價。只有一個人改價時這樣沒問題，但店長和另一位同事幾乎同時改價時，兩個寫入會交錯：

步驟寫入 A（改成 120）寫入 B（改成 130）資料庫快取
1寫資料庫 120120110
2寫資料庫 130130110
3更新快取 130130130
4更新快取 120（比較慢）130120 ✗

A 寫資料庫比較早，但更新快取比較晚，可能是網路慢了一下，或那台 API 剛好在忙。資料庫最後是 130，快取卻是 120，而且會一直錯到 TTL 到期。問題出在「更新快取」這個動作的結果取決於誰最後到：兩個寫入誰先誰後，快取就留下誰的值，而這個順序沒有人控制得了。結果取決於好幾個動作誰先誰後，叫競態（race condition）。

改成刪除，這個動作叫失效（invalidation）：讓快取裡的這一筆失去效力，下次讀取自然會去資料庫拿最新的。刪除跟更新不同，它的結果不管做幾次、誰先誰後都一樣，最後快取都是空的。一個操作做一次和做好幾次結果相同，叫冪等（idempotent），第 9 課會詳談。上面的例子改成刪除，不管 A、B 的刪除哪個先到，快取都是空的，下一個讀取會去資料庫拿到 130。Facebook 在〈Scaling Memcache at Facebook〉（NSDI 2013）也是這樣選的，理由正是刪除是冪等的。

所以 cache-aside 的寫入規則是：先寫資料庫，再刪除快取。但刪除也不是萬無一失：刪除只處理了「寫入和寫入」交錯的情況，還有「讀取和寫入」交錯的情況沒處理。

刪了快取，舊價為什麼還會被寫回去？

cache-aside 的讀取也會寫快取：未命中時，讀取請求查完資料庫，會把結果放回快取。這個「放回」如果晚了一步，就可能把舊價放回去。這個競態叫舊值寫回（stale set），按「下一步」看：

步驟讀取請求 A店長改價資料庫快取
1查快取：未命中110（空）
2查資料庫：讀到 110110（空）
3寫資料庫 120120（空）
4刪除 price:2120（空）
5寫回快取 110120110
6之後的讀取全部命中舊價120110 ✗

每一步都照規矩做：店長先寫資料庫再刪快取，讀取請求未命中就查資料庫並放回。出錯的原因是請求 A 從「讀資料庫」到「寫回快取」之間有一段空檔，店長的改價和刪除剛好落在這段空檔裡。刪除發生在 A 寫回之前，等於刪了一個還不存在的東西，A 接著把手上過時的 110 放了進去。

要修這個問題，快取必須有辦法分辨「這個寫回是在刪除之前讀的，還是之後讀的」。Facebook 的修法叫 lease（租約）：未命中時，快取發給呼叫者一張一次性的票（token），等於說「這個 key 由你負責去載入」；之後寫回時要附上這張票。刪除會讓這個 key 的票作廢，拿作廢的票寫回會被拒絕。同一個情境加上 lease：

步驟讀取請求 A店長改價讀取請求 B快取
1查快取：未命中，拿到 lease 7（空），有效票：7
2查資料庫：讀到 110（空），有效票：7
3寫資料庫 120、刪除 price:2（空），沒有有效票
4寫回 110（lease 7）
被拒絕		（空）
5未命中，拿到 lease 8；讀到 120（空），有效票：8
6寫回 120（lease 8）120 ✓

A 的票是在刪除之前發的，刪除讓它作廢，A 帶著 110 回來時就被擋下；B 的票是刪除之後發的，B 讀到的一定是改價後的資料。lease 把「讀的時間點」記在票上，讓快取能拒絕過時的寫回。練習 4 會實作這個機制。

lease 還有另一個用途，下一節會看到。

lease 需要快取這一端支援。沒有 lease 時，還有兩個比較簡單的保險。第一個是把版本號放進 key：菜單整份重新發布時，key 從 menu:v41 換成 menu:v42，讀取一律讀新版本的 key，就算有人把舊值寫回 menu:v41，也不會再有人讀它，等 TTL 自然清掉。這適合「整批換掉」的資料，代價是要有地方存目前的版本號。第二個是 TTL 本身：失效邏輯總有漏掉的時候，舊值寫回這類競態也不可能百分之百擋住，TTL 保證任何錯誤最多持續 TTL 那麼久。所以不要把 TTL 設成永不過期，它是最後一道保險。

💡 實務上：失效最常漏在「不是走正常 API」的寫入
後台改價的 API 通常記得刪快取，出事的多半是別條路：CSV 批次匯入、排程同步供應商價格、工程師直接下 SQL 修資料、另一個服務直接改同一張表。實務上會把「改這份資料」收斂到同一個函式或服務，刪快取寫在裡面；code review 時多問一句「這個寫入會影響哪些快取 key？」。週年慶前常會批次調價，客服回報「網頁上的價格不對」時，第一步就是比對資料庫和快取的值，不一致就是失效漏了，手動刪掉那個 key 能先止血，再回頭找是哪條寫入路徑。

到這裡，改價後的正確性處理好了。但 TTL 和刪除都會讓快取「變空」，而菜單是全站最熱門的 key：它變空的那一瞬間，會發生什麼事？

菜單 key 過期的那一瞬間，資料庫會被打幾次？

週年慶尖峰每秒 1,111 次讀菜單。菜單的 key 因為 TTL 到期或被刪除而變空的那一瞬間，正在讀菜單的幾百個請求同時未命中。cache-aside 的寫法是「未命中就自己去查資料庫」，所以它們會同時去資料庫查同一份菜單，在第一個人把結果寫回之前，每一個都會打到資料庫。這叫快取擊穿（cache stampede），也叫驚群（thundering herd）：像一群動物同時受驚往同一個方向衝。執行下面的範例，先看簡單的 cache-aside 寫法讓 500 個同時的請求打了資料庫幾次，再看改成 single-flight 之後的次數：

single-flight 就是 TypeScript 課第 12 課「同一個 key 共用同一個 Promise」的做法：第一個未命中的人去載入，並把這個載入中的 Promise 記在 inflight 裡；後來的人看到同一個 key 已經在載入，就等同一個 Promise，不再自己去查。500 個請求只打一次資料庫。

這個寫法有三個細節，練習 2 都會考。第一，載入失敗時也要把 inflight 裡的紀錄清掉，上面用 finally 做到；不清的話，那個失敗的 Promise 會一直留著，之後每個人都拿到同一個錯誤，資料庫恢復了也沒用。第二，錯誤不要寫進快取：資料庫抖了一下是幾百毫秒的事，寫進快取就變成整個 TTL 的故障。第三，single-flight 只在同一個程序裡有效，因為 inflight 是那個程序記憶體裡的 Map。API 有 10 台時，每台各自擋成一次，資料庫還是收到 10 次。要跨機器擋成一次，有三個做法：上一節的 lease、分散式鎖（多台機器共用的一把鎖，同一時間只有一台能去載入，第 14 課），或下一節之後會講的提早更新。

上一節的 lease 剛好能做到。Facebook 讓每個 key 每 10 秒只發一張票：10 秒內其他未命中的請求拿不到票，被告知「稍等一下再查」，等第一個拿到票的人把值寫回。票是快取那一端發的，所有 API 共用同一個快取，所以不管請求落在哪台 API，熱門 key 未命中時都只有一個請求會去資料庫。論文的量測是：一組特別容易出擊穿的熱門 key，資料庫的尖峰查詢量從每秒 17K 次降到 1.3K 次。

single-flight 解決的是「一個熱門 key 過期」。但週年慶菜單不只一個 key，每個商品也各有一筆快取，它們可能同時過期。

兩千個商品同時過期、有人一直查不存在的商品，怎麼辦？

擊穿是一個 key 過期，雪崩（avalanche）是大量 key 在同一時間過期，所有未命中一起壓到資料庫。最常見的原因是部署或活動前先預熱：主動一次把所有商品載入快取（不是 cache-aside 那種被讀到才載入），TTL 都是 60 秒，60 秒後它們一起過期，再一起被寫回、再過 60 秒又一起過期，資料庫的負載就每 60 秒跳一次。single-flight 擋不住這種情況：它合併的是同一個 key 的載入，兩千個不同的 key 還是各查一次。

修法是讓過期時間錯開，叫 TTL 加隨機（jitter）：例如 TTL = 60 秒 × (1 − 0.2 × 隨機數)，隨機數在 0～1 之間，過期時間就分散在 48～60 秒之間。同一批寫入的 key 不再同一秒過期，資料庫的負載攤平成一條比較平的線。

還有一種讓快取完全失效的情況：有人一直查不存在的商品，例如 /products/99999。資料庫查不到，沒有東西可以放進快取，所以這個請求永遠不會命中，每次都打資料庫。爬蟲或攻擊者大量送這種請求，就能繞過快取直接壓資料庫。修法是負快取（negative caching）：把「查無此資料」也當成一個結果快取起來，例如存一個 null，下次同樣的查詢直接命中這個 null。負快取的 TTL 要短，例如 30 秒，原因有兩個：商品可能剛好被新增，存太久會讓新商品一直顯示不存在；攻擊者也可以用大量不同的不存在 id 把快取塞滿，把真正的熱門資料擠出去。所以負快取要搭配限流，限制每個來源一段時間內能送幾個請求（第 10 課）。

💡 實務上：看到「固定時間點」的資料庫尖峰，先懷疑 TTL
雪崩在監控上的樣子是：資料庫 CPU 每隔固定時間跳一下，或每次部署後剛好過了一個 TTL 就突然變慢。排查時先看那批 key 是不是同一時間寫進去、TTL 是不是同一個整數，確認了就加 jitter，改動很小。另外，週年慶、推播發出去之前，先問行銷什麼時候發，提前把熱門資料載入快取，不要讓第一波流量撞上空的快取。

到這裡，過期時資料庫只會被打一次，大批過期也錯開了。但 single-flight 留下一個代價：去載入的那一個請求，和所有等它的人，都要等完整的一次資料庫查詢。

能不能不等到過期，就先在背景更新？

過期才更新，就一定有一批人在等。更好的做法是在過期之前就更新，或過期後先回舊值、在背景更新，讓讀取的人永遠不用等資料庫。

第一個做法來自 HTTP 快取（Node 課第 15 課）的 stale-while-revalidate，意思是「先用舊的，同時重新驗證」。例如 Cache-Control: max-age=600, stale-while-revalidate=30：前 600 秒資料是新鮮的；之後 30 秒內，快取可以先回舊值，同時在背景重新驗證。我們把同樣的語意搬到應用程式的快取裡，用 staleMs 表示「過期後還能容忍多舊」，對應 HTTP 的 stale-while-revalidate=30，跟 TTL 一樣要跟 PM 確認。讀取時依資料的狀態決定怎麼做：

讀取時的狀態做法
沒有快取等待載入（single-flight）
還沒過期直接回傳
過期不到 staleMs馬上回傳舊值，背景重新載入（同一個 key 只載入一次）
過期超過 staleMs舊到不能用了，等待重新載入

菜單過期幾秒內先回舊價，顧客幾乎感覺不到，但沒有人需要等資料庫。

stale-while-revalidate 還是要等到過期之後的第一個讀取才開始更新。XFetch（Vattani 等人，PVLDB 8(8)，2015）再往前推一步：還沒過期時，就讓每個讀取以一定的機率「提早」重新載入，越接近到期機率越高。條件是：

now − Δ × β × ln(random()) ≥ expiresAt

一個一個看。Δ 是上次載入花的時間；β 預設 1，調大就更積極地提早。random() 在 0～1 之間，所以 ln(random()) 是負數，−Δ × β × ln(random()) 是一個正的「提早量」：random 很小時提早量很大，random 接近 1 時提早量趨近 0。整個條件是在問「現在加上這次抽到的提早量，有沒有超過到期時間」。離到期越近，需要的提早量越小，越容易成立；載入越慢（Δ 越大），提早量整體越大，就越早開始。下面的範例算出離到期還剩多少時，單一讀取觸發的機率，執行後看機率怎麼隨剩餘時間變化：

單一讀取的機率很低，但熱門的 key 每秒有很多讀取。週年慶的菜單每秒被讀上千次，接近到期時幾乎一定有某一個讀取先觸發、在背景更新完，其他人從頭到尾都命中，連擊穿都不會發生。冷門的 key 讀取少，多半等到真的過期，這也沒關係，因為冷門的 key 本來就不會造成擊穿。

背景更新是「射後不理」：呼叫端已經拿到舊值走了，背景載入失敗時沒有人會 await 它。一定要自己 .catch 並記錄錯誤，否則就是未處理的 Promise rejection，Node 15 起預設會讓整個程序結束。練習 3 會檢查這一點。

實際專案不用自己從頭寫，可以用現成的函式庫，見練習前的「補充與查表」。到這裡，菜單快取在 Redis 正常時已經很穩。剩下兩件事：有些資料根本不該放進快取，以及 Redis 自己壞掉的時候。

哪些資料不該快取？Redis 掛了怎麼不拖垮資料庫？

先看不該快取、或要特別小心的資料。最危險的是依身分而不同的資料用了共用的 key：如果用網址 /me/orders 當 key，第一個人查完，王小明的訂單就被快取起來，接著陳美華查同一個網址，拿到的是王小明的訂單。這是 NestJS 課第 19 課 CacheInterceptor 的陷阱。key 要包含使用者 id，或乾脆不快取；HTTP 快取也一樣，這類回應要設 private 或 no-store。

第二種是結帳時的價格與庫存。菜單頁可以顯示快取的價格，晚幾秒沒關係；但下單時要從資料庫讀價格與庫存再計算金額，因為快取可能是舊的，用舊價收錢就是錯帳。快取不是資料來源。

第三種不是資料不該快取，而是快取放的位置會出問題：熱門 key 讓單一 Redis 節點過熱。到目前為止我們把 Redis 當成一台，但資料量或流量大時，Redis 會拆成好幾台一起用（Redis Cluster，原理是第 7 課的分片），每個 key 只存在其中一台。所有人都讀 menu，這個 key 存在哪台 Redis 上，所有讀菜單的請求就都落在那台，那台最忙，其他節點閒著也幫不上忙。常見的做法是在每台 API 的程序記憶體再放一層 TTL 很短的快取，讓大部分讀取不必出門；或把同一份資料複製成幾個 key，分散到不同節點讀。

程序記憶體這層跟第一節的表格有衝突：表格說程序記憶體不適合要多台一致的資料，菜單正是因此放 Redis。這裡是刻意取捨：這層的 TTL 只設幾秒，代表改價後各台 API 最多會有幾秒看到不同的價格。這是用一點一致性換掉單點過熱，要先跟 PM 確認可以接受；結帳不受影響，因為下單一律從資料庫讀價格。

再來是快取壞掉時。NestJS 課第 19 課的做法是：Redis 的 get／set 失敗就記 log，直接查資料庫。對延遲型快取這是對的，系統只是變慢。但第一節算過，週年慶的菜單快取是容量型快取：Redis 一掛，每秒 1,111 次讀取全部壓到只撐 200 次的資料庫上，資料庫變慢，跟它共用資料庫的下單也一起失敗。這時「退回查資料庫」反而是讓資料庫倒下的原因。要做的是三件事。

第一，限制同時打到資料庫的請求數，超過的直接回錯誤或回較舊的資料。這是第 11 課的兩個做法：隔艙是給每一類工作固定數量的位子，例如讀菜單最多同時佔 20 條資料庫連線，用完就不再接，下單永遠有自己的位子；負載卸除是超過容量時主動拒絕一部分請求，保住其他的。讀菜單失敗一部分，總比所有人連下單都失敗好。

第二，暖機（warm-up）。Redis 重啟或擴容後，快取是空的，叫冷快取，命中率是 0，跟 Redis 掛掉對資料庫來說是一樣的。所以恢復時要先預先載入熱門 key，或把流量慢慢導進來，不要一次全部吃下。

第三，在第 2 課的容量估算裡寫清楚：哪些快取是容量型的、命中率最低要多少。週年慶菜單的答案是約 82%，練習 1 的 requiredHitRatio 算的就是這個數字，它就是上線後要監控的門檻。

設計都到位了，但快取出問題時多半不會報錯，只會「變慢」或「資料怪怪的」。週年慶當天，要怎麼在顧客抱怨之前發現？

週年慶當天要盯哪些指標？

前面每一節處理的問題，都對應一個可以事先放上監控的指標。上線前把這些放好，出事時才知道是哪一種問題：

指標看什麼
命中率，依 key 前綴分開整體 95% 可能掩蓋 product:* 只有 30%；掉下來時資料庫負載會跟著跳
淘汰數、記憶體用量淘汰一直很高代表空間不夠，熱門資料被擠出去
未命中時的載入延遲XFetch 的 Δ 就是它；變慢時擊穿的影響變大
同一個 key 同時載入的次數大於 1 就是擊穿的訊號（跨機器、或 single-flight 沒生效）
lease 被拒絕的次數突然升高代表某個 key 被頻繁修改，或有寫回競態

命中率要依 key 前綴分開看，原因是第一節的算式：命中率最後幾個百分點對資料庫影響最大，整體平均會把某一類 key 的問題蓋掉。菜單的命中率一旦接近 82% 這條線，就是資料庫快撐不住的預警。

補充與查表

  • 程序內快取的現成函式庫：正式環境的程序內快取可以用 lru-cache（npm 11.5.3）：設定 fetchMethod 後，cache.fetch(key) 會把同一個 key 同時的載入合併成一次，搭配 allowStale 會先回傳過期的值並在背景重新載入。Redis 端的寫法見 NestJS 課第 19 課。
  • stale-while-revalidate 的出處：RFC 5861（2010-05，Informational），定義在 HTTP 的 Cache-Control 擴充裡。

練習

練習 1：寫 cacheEffect：依命中率算出平均延遲 avgMs 和資料庫每秒讀取量 dbReadsPerSec；hitRatio 不在 0～1 之間（0 和 1 本身可以；NaN 也算不在範圍內）時丟 RangeError。再寫 requiredHitRatio：資料庫每秒只撐得住 dbCapacityPerSec 次讀取時，命中率至少要多少（資料庫撐得住時回傳 0）。

練習 2：寫 createCachedLoader，回傳一個 (key) => Promise 的讀取函式。規則：

  • store.get(key) 有東西就是命中，回傳裡面的 value（包括快取起來的 null）。
  • 未命中時，同一個 key 同時只呼叫一次 load，其他呼叫等同一個結果（single-flight）。
  • load 成功：值是 null（查無此資料）就用 negativeTtlMs 存；否則 TTL = Math.round(ttlMs × (1 − jitter × random()))。
  • load 失敗：所有等待者收到同一個錯誤，不寫入快取。
  • 不管成功或失敗，結束後都要清掉進行中的紀錄。亂數只能用傳進來的 random。

練習 3：寫 createSwrCache，加上 stale-while-revalidate 和 XFetch。每筆快取記住 value、expiresAt（載入完成時的 now() ＋ ttlMs）和 delta（這次載入前後 now() 的差）。讀取時依序判斷：

  1. 沒有快取 → 等待載入（single-flight）。
  2. 過期超過 staleMs（now ≥ expiresAt + staleMs）→ 等待重新載入。
  3. 已經過期，或還沒過期但 XFetch 觸發（now − delta × beta × Math.log(random()) ≥ expiresAt）→ 馬上回傳目前的值，並在背景重新載入。
  4. 其他 → 直接回傳。

同一個 key 同時只有一個載入（不管是前景還是背景）。前景載入失敗時，等待的呼叫端收到那個錯誤。背景載入每失敗一次就呼叫一次 onError、保留舊值，不能變成未處理的 rejection。

練習 4：完成 LeaseCache，修好課文時間軸裡的「舊值寫回」：

  • get(key)：有值回傳 { hit: true, value }。沒有值時，如果這個 key 沒有有效的 lease，發一張新的：{ hit: false, lease: token }，token 從 1 開始、整個快取共用一個遞增的計數器；如果已經有人拿著有效的 lease，回傳 { hit: false, lease: null }（請稍後重試）。
  • set(key, value, lease)：只有 lease 等於這個 key 目前有效的 token 才寫入並回傳 true，寫入後這張 lease 就用掉了；其他情況回傳 false、不寫入。
  • delete(key)：刪掉值，並讓這個 key 目前的 lease 作廢。
  • lease 發出後經過 leaseMs（now() − 發出時間 ≥ leaseMs）就失效：不能再拿來 set，下一個 get 會拿到新的。

練習 5：店長把拿鐵從 110 改成 120，寫完資料庫之後，快取裡的 price:2 應該怎麼處理？

✓ 刪除是冪等的，兩個寫入不管誰先誰後，快取最後都是空的；更新快取（a）在兩個寫入交錯時，會留下比較慢的那一個寫入的舊值。只靠 TTL（c）不會錯得更離譜，但到期前所有人都看到舊價。刪除之後還有「舊值寫回」的競態，所以要 lease 或版本號，TTL 當最後的保險。

練習 6：熱門的菜單 key 過期瞬間，500 個請求同時未命中。你在 API 程式裡加了 single-flight。API 共有 10 台，資料庫大約會收到幾次查詢？

✓ single-flight 靠的是程序記憶體裡的 Map，每台 API 各有一份，只擋得住同一台裡的重複載入，所以是每台各一次。a 忘了每台各有一份 Map；b 說反了，同一台裡 500 個請求本來就會被合併成一次載入。要跨機器擋到一次，要用快取端的 lease、分散式鎖，或用 stale-while-revalidate／XFetch 讓 key 在過期前就被更新。

練習 7：菜單快取的命中率從 90% 提高到 99%，資料庫要處理的菜單讀取量變成原本的多少？

✓ 資料庫讀取量 = (1 − 命中率) × 總讀取量。未命中的比例從 10% 變成 1%，是十分之一。b 把命中率多了 9 個百分點，誤當成資料庫讀取量少了 9%；c 沒有任何算式支持。命中率最後幾個百分點的影響最大，這也是為什麼要依 key 前綴監控命中率。

練習 8：Redis 突然掛了。同事說：「反正還有 PostgreSQL，讓所有請求直接打資料庫就好，只是慢一點。」什麼時候這樣做會出事？

✓ 延遲型快取掛了只是變慢；容量型快取掛了，所有讀取都壓到資料庫上，超過它的容量。要限制同時打到資料庫的請求數、卸除部分負載（第 11 課），Redis 恢復後也要暖機或逐步導流。c 說的是另一件事：session 放在 Redis 是資料本身，不是快取。

常見錯誤

  • 依身分而不同的資料用共用的 key：王小明的訂單被快取給陳美華看。key 要包含使用者 id，或乾脆不快取。
  • 寫入時更新快取而不是刪除：兩個寫入交錯時，快取留下比較慢的那個寫入的舊值。改成刪除。
  • 刪除之後就以為沒事：讀到舊值的請求晚一步寫回，舊價一直留到 TTL 到期。用 lease 或版本號，並保留 TTL。
  • 所有 key 用一樣的 TTL：同一時間大量過期造成雪崩。TTL 加隨機。
  • 把錯誤或 null 長時間快取：資料庫抖一下就變成長時間的故障。錯誤不快取，null 只快取很短的時間。
  • 以為程序內的 single-flight 擋得住跨機器的擊穿：10 台 API 就是 10 次。跨機器要 lease、鎖或提早更新。
  • 背景更新沒有 catch：射後不理的 Promise 失敗時變成未處理的 rejection，可能讓整個程序結束。
  • 把快取當成資料來源：金額、庫存、付款狀態以資料庫為準，結帳時重新讀。
  • 重啟或擴容後冷快取直接吃全部流量：容量型快取要暖機或逐步導流，Redis 掛掉時要限制打到資料庫的並發。

小結

  • 快取可以放在瀏覽器、CDN、反向代理、程序記憶體、Redis、資料庫自己的緩衝；越靠近使用者越省，能放的資料越受限。多台 API 共用的菜單放 Redis。
  • 平均延遲 = h × 命中延遲 + (1 − h) × 未命中延遲；資料庫負載 = (1 − h) × 讀取量。命中率 90% → 99%，資料庫負載變成十分之一；週年慶每秒 1,111 次、資料庫撐 200 次，命中率至少約 82%。
  • 分清延遲型和容量型快取：拿掉只是變慢的是延遲型，拿掉就撐不住的是容量型。
  • cache-aside 加 TTL 是最常用的組合；write-behind 快但可能遺失資料；訂單、付款、結帳時的價格與庫存不快取。
  • 寫入時刪除快取，不要更新：刪除是冪等的。「舊值寫回」的競態用 lease 修正；lease 每個 key 一段時間只發一張，也順便擋住擊穿。版本號放進 key 與 TTL 是另外兩道保險。
  • 擊穿用 single-flight（同一程序）、lease 或提早更新（跨程序）；雪崩用 TTL 加隨機；查無此資料用短 TTL 的負快取。
  • stale-while-revalidate 先回舊值、背景更新；XFetch 在到期前以遞增的機率提早更新；背景更新的錯誤要自己接住。
  • 容量型快取壞掉或變冷時，不能直接退回查資料庫：要限制並發、卸除負載、暖機；命中率依 key 前綴監控，門檻就是算出來的最低命中率。
