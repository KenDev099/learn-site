階段 3：可靠性：失敗是常態 · 第 13 課

Saga：跨服務的流程與補償

咖啡店的下單流程原本在一個 NestJS 服務、一個 PostgreSQL 裡：建立訂單、扣庫存、記帳，一個交易全部包住，失敗就整個 ROLLBACK。現在庫存交給門市系統、扣款交給金流閘道、集點交給會員服務。王小明下單買一杯 110 元的拿鐵，錢包裡只有 100 元：訂單 #501 建好了、拿鐵也預留了，扣款卻因為餘額不足失敗。這時沒有 ROLLBACK 可以按，預留的拿鐵會一直卡著，別人買不到。

這一課從頭到尾處理同一件事：讓訂單 #501 這種跨服務的下單，不管在哪一步失敗、協調的程式在哪一刻當機，最後都只會落在「全部完成」或「全部抵銷」其中一個結果，而且不會重複扣款、不會讓拿鐵一直卡著。學完之後，你能說出為什麼跨服務的流程不能用一個交易包住；能把下單拆成一連串步驟、替每一步設計補償，並排出正確的順序；能自己寫出依序執行、失敗時反向補償、當機後從紀錄續跑的協調者；也知道 saga 沒有隔離會出什麼事、逾時為什麼不能直接補償，以及什麼時候根本不需要 saga。

第一輪只要記住：
  • 跨服務沒有 ROLLBACK 可以按。Saga 把流程拆成各自提交的步驟，失敗時對已完成的步驟做補償；補償是一筆新的交易，不是回滾。
  • 不可逆的步驟（扣款）放在所有驗證之後；過了它，後面的步驟只能重試到成功。
  • 協調者每一步都寫紀錄、帶冪等鍵。逾時代表結果未知，要先查清楚再決定補償；補不回來就標成 stuck，交給人處理。
  • 全部在同一個資料庫時直接用交易，不需要 saga。
這課的路線：
  1. 為什麼一個交易包不住，以及王小明的拿鐵怎麼還回去：把下單拆成步驟與補償、排出順序（開場問題的最小答案）。
  2. 誰照著步驟表執行：協調者怎麼依序執行、失敗時補償；它自己當機後，怎麼從紀錄續跑而不重複扣款。
  3. 能不能不要協調者：choreography 的做法與取捨。
  4. 付款處理中顧客按了取消：saga 沒有隔離時會出什麼事、怎麼擋。
  5. 扣款逾時、不知道成功還是失敗時怎麼辦；要自己寫還是用工具，什麼時候根本不需要 saga。
這課會用到：
  • PostgreSQL 課第 18 課的交易：同一個資料庫裡的修改全做或全不做，失敗就 ROLLBACK。
  • 第 8 課的逾時與重試：逾時代表結果未知，重試要有上限和退避。
  • 第 9 課的冪等鍵：同一把鍵送很多次，對方只做一次。
  • 第 12 課的 outbox：要送出的命令和本地資料寫在同一個交易，不會只成功一半。

為什麼不能用一個交易包住整個下單？

先回想交易在單一資料庫裡是怎麼救你的。PostgreSQL 課第 18 課的 BEGIN 之後，建立訂單、扣庫存、記帳都還沒有真正生效；中途任何一句出錯，ROLLBACK 就把這些修改全部丟掉，就像什麼都沒發生。這件事做得到，是因為所有資料都在同一個資料庫裡：它自己保管著「還沒提交的修改」和「改之前的樣子」，要丟掉時不用問任何人。

拆成多個服務之後，下單流程橫跨四個地方：

  • 訂單服務的 PostgreSQL
  • 門市庫存服務的資料庫（另一個團隊、另一台機器）
  • 金流閘道（別家公司的 HTTP API）
  • 會員服務（集點）

訂單服務的 BEGIN 只管得到自己那條資料庫連線。門市系統預留拿鐵時，是在它自己的資料庫裡提交的；訂單服務就算 ROLLBACK，也碰不到那一筆。金流閘道更不用說，它是別家公司的系統，你只能呼叫它的 API。開場那杯卡住的拿鐵就是這樣來的：訂單服務知道扣款失敗了，但門市那邊的預留早就提交，沒有人去還。

「讓分散在多個資料庫或服務上的修改，要嘛全部成功、要嘛全部失敗」這件事，叫做分散式交易（distributed transaction）。傳統的做法是兩階段提交（2PC，two-phase commit）：找一個協調者，第一階段先問每個參與者「你能提交嗎？」（prepare），每個參與者把要改的資料準備好、鎖住，回答「可以」；第二階段，協調者確認大家都說可以，才叫所有人一起提交，只要有一個說不行就叫所有人放棄。這樣確實能做到「全部或全無」，但放到咖啡店的下單流程裡，有三個問題：

  • 協調者卡住，大家一起卡住：參與者回了「可以」之後，就不能自己決定提交或放棄，只能鎖著資料等協調者下令。協調者當機十分鐘，拿鐵的庫存就鎖十分鐘，其他顧客也買不了。
  • 外部系統不支援：金流閘道只給你「扣款」和「退款」兩個 HTTP API，不會陪你做 prepare。
  • 延遲與耦合：每次下單都要等最慢的參與者兩輪往返，任何一個服務不在線，整個流程都不能做。

既然做不到「像什麼都沒發生」，就換一個目標：接受每一步都各自提交，失敗時再用新的動作把已經生效的效果抵銷掉。這就是 saga：把一個大流程拆成一連串各自提交的本地交易，每一步在自己的服務裡用普通的交易完成（名稱的出處見課末「補充與查表」）。某一步失敗時，不是回滾（前面的早就提交了），而是對已完成的步驟執行補償交易（compensating transaction），在語意上抵銷它們的效果。

代價是一致性變成第 6 課的最終一致：中間會有一段時間，系統處在「訂單已建立、還沒付款」這種半完成的狀態，別人也看得到；但最後會走到「全部完成」或「全部抵銷」其中一個。真的走不下去時，停下來交給人處理，後面會講。

回到王小明：他的拿鐵要靠「補償」還回去。但補償具體是什麼、每一步的補償長什麼樣子、哪一步該先做，要先把整個下單流程攤開來看。

王小明的拿鐵怎麼還回去？把下單拆成步驟與補償

設計 saga 的第一步，是把流程列成一張表：每一步做什麼、做完之後要怎麼抵銷。先看前兩步。建立訂單的補償是「把訂單改成 cancelled」；預留拿鐵的補償是「釋放預留」。訂單 #501 在扣款失敗時，只要把這兩個補償執行一次，拿鐵就回到架上，訂單也標成取消，這就是開場問題的最小答案。

補償不是回滾。ROLLBACK 讓資料庫像什麼都沒發生；補償是一筆新的本地交易，在語意上抵銷前面的效果。退款不會讓扣款消失，帳上會有兩筆；釋放庫存時，中間可能已經有別人改過庫存。所以補償通常寫成「加回 1 杯」，而不是「把庫存改回原來的 3 杯」。

接著往下列，會發現不是每一步都能這樣乾淨地抵銷。扣款的「補償」是退款：會產生一筆新的金流紀錄、可能有手續費，顧客的帳單上還會出現「扣了又退」。廚房出單更麻煩：咖啡做出來就收不回來，根本沒有補償。所以每一步除了寫補償，還要標出它屬於哪一種。Azure Architecture Center 的 Saga 模式文件把步驟分成三種：

  • 可補償的交易（compensable）：之後還能被補償抵銷，例如預留庫存（補償是釋放）。
  • pivot 交易：不可回頭的點。它成功之後，前面的補償都用不到了，只能往前把流程做完。
  • 可重試的交易（retryable）：pivot 之後的步驟。必須冪等，暫時失敗就重試，最後一定要成功。

把咖啡店的下單照這三種排好：

順序步驟動作補償類型
1createOrder訂單服務建立訂單，狀態 pending_payment把訂單改成 cancelled可補償
2reserveStock門市預留拿鐵 1 杯釋放預留可補償
3capturePayment金流扣款 110 元（不補償，見下面說明）pivot
4confirmOrder訂單改成 paid—可重試
5sendKitchenTicket廚房出單、開始做咖啡—可重試
6awardStamps會員集點 +1—可重試

這個順序有三個理由，每一個都是「如果不這樣排會出什麼事」。

第一，扣款放在所有驗證之後。如果先扣款再預留庫存，拿鐵賣完時就得退款，退款的成本和顧客觀感前面說過了。先把能失敗、又便宜抵銷的步驟（建訂單、預留庫存）做完，確定拿鐵真的有，最後才動錢。原則是：不可逆或代價高的步驟，要等所有關鍵驗證都成功之後才做。

第二，扣款是 pivot。嚴格說退款也算一種補償，但成本高、顧客看得到，所以這裡的設計選擇是「扣款成功就不回頭」。pivot 選在哪裡是業務決定，不是技術限制：另一家店也可以決定扣款後仍可退款取消，那 pivot 就往後移。

第三，出廚房單一定要在 pivot 之後。它沒有補償，放在 pivot 之前的話，萬一後面扣款失敗，咖啡已經做了、錢卻沒收到。放在之後，它就變成可重試的步驟：廚房系統暫時當機，就重試到成功並告警，而不是退款。

圖上的箭頭也說明了失敗時的方向：pivot 之前的步驟失敗，就從最後完成的一步往回補償，先釋放庫存、再取消訂單。反向的好處是，每個補償執行時，它之後做的事都已經抵銷了，狀態跟它當初剛做完時一樣，比較不會出乎意料。這不是唯一的做法（彼此無關的補償也可以平行做，見課末），但這一課的練習都用最常見、最安全的反向依序補償。

💡 實務上：步驟表要先跟 PM、財務對過，再開始寫程式
像上面這張步驟與補償表，在團隊裡通常出現在設計文件裡，而不是寫完程式才補。pivot 放在哪、退款誰負責、手續費誰吸收、出了餐的單能不能取消，這些都是業務問題，工程師要拿著表去問 PM 和財務，而不是自己決定。常見的坑是只想「成功的路徑」：每一列都要問「這步失敗怎麼辦？補償失敗又怎麼辦？顧客這時看到什麼？」。外送平台、訂票、電商結帳都是同樣的結構：先保留名額或庫存，最後才扣款。

表排好了，但表不會自己動。接下來要有一段程式照著它執行：依序呼叫每一步、記住哪些做完了、失敗時倒著補償。

誰照著步驟表執行？協調者依序執行與補償

最直接的做法是 orchestration：由一個協調者（orchestrator）拿著步驟表，依序告訴各服務該做什麼，並且記住做到哪裡。協調者不是新的服務類型，它通常就是訂單服務裡的一段程式，或一個獨立的小服務。

先寫出最小的協調者，重現開場的訂單 #501：王小明的錢包只有 100 元，拿鐵 110 元，扣款會失敗。執行後看補償的順序：

輸出裡有兩件事對應前一節的規則：失敗的 capturePayment 本身不補償，因為它的本地交易沒有成功（或已經被它自己的資料庫回滾），沒有東西可以抵銷；補償從最後完成的一步往回做，先釋放拿鐵、再取消訂單。

這個迴圈只要一失敗就補償，放到正式環境還差兩件事。

第一件，先重試，再補償。失敗有兩種：一種是暫時性錯誤，例如網路抖一下、對方回 503，等一下再試很可能就成功；另一種是業務失敗，例如餘額不足、庫存不夠，再試幾次結果都一樣。如果門市系統只是回了一次 503，協調者就把整張訂單取消，等於把一個小晃動放大成顧客下單失敗。所以暫時性錯誤先照第 8 課的退避重試；重試用盡，或確定是業務失敗，才開始補償。補償是最後手段，不是第一反應。

第二件，補償本身也會失敗。釋放庫存時，門市系統可能剛好當機。這時先重試幾次；仍失敗就把 saga 標成 stuck、告警、停下來。不要繼續補償更早的步驟：這一步到底釋放了沒有已經不確定，再往前做只會讓狀態更難收拾。也不要無限重試，對方本來就有問題，一直打只會把它打得更爛。

把這兩件事加進去，協調者就是一個有固定幾種狀態的狀態機（TypeScript 課第 27 課用型別描述狀態機；NestJS 課第 18 課寫過訂單的狀態機）：

running 時一步一步往前；每一步都成功就到 completed。某一步確定失敗就進入 compensating，補償全部成功到 compensated，訂單 #501 就是走這條路；某個補償重試用盡則停在 stuck，等人來處理。練習 1 會把上面的迴圈補成這個狀態機：寫紀錄、補償的重試上限、stuck。

但這個協調者還有一個致命的假設：它把「做完了哪些步驟」放在記憶體裡的 done 陣列。協調者本身也是一個會當機的程序，它一停，陣列就沒了。

協調者當機了，怎麼不重做也不漏做？

部署新版本、記憶體不足、機器被雲端回收，都可能讓協調者停在流程中間。重啟後如果從頭再跑一次，已經扣款的顧客就會被扣兩次；如果什麼都不做，預留的庫存就一直卡著。協調者需要一份當機也不會消失的進度：saga 紀錄。

saga 紀錄就是資料庫裡的一張表，例如 saga_steps，每完成一步、每補償一步，就寫一筆，例如「saga #502 的 reserveStock 已 done」。協調者啟動時先讀這張表，就知道每個 saga 做到哪裡，從中斷的地方繼續。王小明的 #501 補償一路順利，協調者沒有在中途停下；要看當機時怎麼辦，換一張補償做到一半、協調者剛好被重新部署的訂單：陳美華買卡布奇諾的訂單 #502。

步驟協調者saga 紀錄（#502）外部效果
1createOrdercreateOrder: done訂單 #502 pending_payment
2reserveStockreserveStock: done卡布奇諾預留 1 杯
3capturePayment ✗capturePayment: failed沒有扣款
4補償 reserveStockreserveStock: compensated卡布奇諾釋放

紀錄解決了「做到哪裡」，但還有一個它救不了的縫隙：動作成功了、還沒寫紀錄就當機。重啟後紀錄說這一步沒做，協調者只能再呼叫一次。這時要靠第 9 課的冪等鍵：每一步都用 saga:<sagaId>:<步驟> 當鍵傳給對方，例如 saga:502:reserveStock。門市系統看到同一把鍵的重複請求，就回傳上次的結果，不會預留兩杯；金流收到重複的 saga:501:capturePayment，也只會扣一次款。補償也一樣要帶自己的冪等鍵，否則重做一次補償就會退兩次款。

紀錄負責「做到哪裡」，冪等負責「重做也沒關係」，兩者缺一不可。把協調者可能當機的時間點整理成一張表：

協調者在哪裡當機重啟後讀到的紀錄怎麼續跑
呼叫某一步之前這一步沒有紀錄照常執行這一步
動作成功、還沒寫紀錄這一步沒有紀錄再呼叫一次；對方靠冪等鍵認出重複，回傳上次的結果
寫完 done、還沒呼叫下一步這一步 done從下一步繼續
補償到一半（上面的時間軸）有一步 failed，部分步驟已 compensated只補償 done 但還沒 compensated 的步驟

還剩最後一個縫隙。實際的系統裡，協調者常常不是直接呼叫門市系統，而是寫一筆紀錄、再送出一則「請預留庫存」的命令到佇列。這就是第 12 課的雙寫問題：紀錄寫好了、命令還沒送出就當機，命令就永遠不會送出。解法也一樣：把命令和 saga 紀錄寫在同一個本地交易的 outbox 裡，由 relay 送出。

練習 2 會寫出續跑的邏輯。

到這裡，整個流程都寫在協調者這一個地方，協調者自己也要部署、監控、保管紀錄。很自然會有人問：能不能不要這個中央元件，讓各服務自己接力完成？

能不能不要協調者？Choreography 的取捨

不要中央協調者的做法叫 choreography（編舞）：每個服務訂閱別人發出的事件，做完自己的事再發出新的事件，像舞者聽音樂各自起舞，沒有人在台上指揮：

下單成功時，訂單服務發出 OrderCreated，庫存服務聽到後預留拿鐵並發出 StockReserved，金流服務聽到後扣款並發出 PaymentCaptured。失敗時也一樣靠事件：金流發出 PaymentFailed，庫存服務聽到就釋放、訂單服務聽到就取消。補償還是那幾個補償，只是「誰決定該補償」從協調者分散到了每個服務。

流程寫在哪裡協調者的一份程式分散在每個服務訂閱了哪些事件
新增步驟改協調者要追出誰聽誰，容易漏
互相依賴成環由協調者控制，不容易出現服務彼此訂閱，可能繞成一個環
測試可以只測協調者（假的參與者）整合測試要把所有服務都跑起來
單點協調者是一個要顧好的元件沒有額外元件
適合步驟多、有補償、流程會改步驟少、參與者少的簡單流程

「少一個元件」不等於簡單。步驟一多，choreography 的流程只存在於各服務的程式碼裡，沒有人說得出「訂單 #503 現在卡在哪一步」，也沒有一份 saga 紀錄可以讀。實務上常混用：下單這種有補償的核心流程用 orchestration；「訂單完成後寄收據、更新推薦」這種互不相干的後續反應用事件（第 16 課）。

不管選哪一種，saga 都少了一個交易原本免費提供的保護。前面一直說「中間狀態別人也看得到」，下一節就看看別人真的看到時會發生什麼事。

付款處理中，顧客按了取消：saga 沒有隔離會出什麼事？

#502 已經取消了。陳美華隔天又下了一張訂單 #504，這次正在扣款，狀態還是 pending_payment，她在 App 上按了「取消訂單」。如果取消的 API 直接把訂單改成 cancelled，接下來 saga 的扣款成功、confirmOrder 又把訂單改回 paid：陳美華以為取消了，卻被扣了款。或者反過來，訂單停在 cancelled，錢卻已經扣走。

在單一資料庫的交易裡，這種事不會發生，因為 ACID 裡的 I 是隔離（isolation）：別的交易看不到你還沒提交的中間狀態，也不能跟你同時改同一筆資料而互相蓋掉。Saga 的每一步都是各自提交的，所以中間狀態對所有人都看得到，別的請求、別的 saga、報表都可能在流程走完前讀到或改到它。Azure 的文件列出三種因此出現的異常：

  • lost update：一個 saga 沒考慮另一個 saga 的修改就覆蓋了它。上面的取消就是一例：取消請求寫的 cancelled 被 saga 的 paid 蓋掉。
  • dirty read：讀到另一個 saga 還沒走完的修改。例如報表把「已預留、但最後因付款失敗被釋放」的拿鐵算成賣出。
  • fuzzy read（不可重複讀）：同一個 saga 的兩步讀到不同的值，因為中間有人改了。例如 reserveStock 時讀到訂單金額 110 元，扣款前店家改了價格或顧客套用了折扣，capturePayment 讀到的是另一個金額，就會扣錯錢。下面對策表裡的「重新讀取」就是擋這種情況。

lost update 最容易在庫存這種數字上出現，因為預留和補償都會改它。兩個 saga 同時處理拿鐵，比較兩種寫法：第一種是「讀出來、算好、整個寫回去」，第二種是只送「增減多少」。執行後看兩個最後的庫存數字：

第一種寫法裡，B 寫回的 2 是根據它讀到的舊值算的，A 的那一筆就這樣消失了。第二種寫法不管 A、B 和補償以什麼順序套用，結果都一樣。補償也是同一個道理：如果 A 失敗後的補償寫成「把庫存改回 3 杯」，一樣會蓋掉 B 的預留；寫成「加回 1 杯」才不會。這就是前面要求補償寫成「加回」的原因。

沒有隔離不代表只能放著不管。Azure 整理了幾種對策，各自擋住不同的情況：

對策做法咖啡店的例子
semantic lock用應用層的狀態標示「這筆正在進行中」，其他操作看到就擋下或排隊訂單在 pending_payment 時不接受修改；App 顯示「付款處理中」
交換律更新（commutative update）更新設計成任何順序套用結果都一樣UPDATE stock SET qty = qty - 1，不是 SET qty = 2
pessimistic view調整順序，把會被別人讀的更新放到 pivot 之後的可重試步驟集點在扣款之後才加，就不會有人看到「加了又扣回」的點數
重新讀取（reread values）更新前再確認資料沒變，變了就停下或重來扣款前再讀一次訂單金額，跟預留時的一致才扣
version file記錄對某筆資料的所有操作，依正確順序套用庫存異動記成一筆筆紀錄，而不是只存一個數字

回到陳美華 #504 的取消。正確的做法是 semantic lock：pending_payment 本身就是一把用狀態做的鎖，告訴其他操作「這筆正在進行中」。這段期間取消按鈕回「付款處理中，請稍候」，或把取消請求記下來，等 saga 走到終點再處理：已經扣款成功，就走退款流程；扣款失敗，saga 自己就會取消訂單。

💡 實務上：中間狀態要讓畫面和報表都知道
身為前端，你最先碰到的就是 pending_payment 這類中間狀態：App 要顯示「付款處理中」並停用取消、修改按鈕，而不是顯示成功或失敗，也不要讓使用者狂按重送。後台和報表也一樣，營收、熱銷排行只該算 paid 之後的訂單，不然會把最後被釋放的預留算成賣出。資深工程師在設計 saga 時，會把每個中間狀態列成表，逐一問「顧客看到什麼？客服看到什麼？報表算不算？」。庫存、點數、餘額這類數字，在 code review 時看到「讀出來再整個寫回去」就該提出來。

到目前為止，我們都假設每一步會清楚回答「成功」或「失敗」，協調者再決定往前走或補償。最麻煩的情況是，對方什麼都沒說。

扣款逾時：不知道成功還是失敗時怎麼辦？

最危險的情況不是「失敗」，而是不知道成功還是失敗。第 8 課說過，逾時代表結果未知：扣款請求逾時，可能是請求沒送到，也可能是對方已經扣款、只是回應在路上掉了。這時如果直接當成失敗、開始補償（取消訂單、釋放庫存），王小明的錢被扣了、訂單卻取消了。

下面用一個假的金流閘道重現：第一次請求對方真的扣了，但回應掉了。接著比較兩種重試：用同一把冪等鍵，和換一把新鍵。執行後看每次印出的扣款筆數：

同一把鍵重試，金流認出這是同一筆，回傳第一次的結果，扣款仍是一筆；換新鍵，金流把它當成新的扣款，王小明被扣了兩次。所以逾時的處理順序是：用同一把冪等鍵重試或查詢，確定結果之後才決定往前走還是補償。重試用盡仍不知道結果，就標成 stuck 交給人，不要猜。

即使每一步都照這課寫對了，協調者的 bug、有人手動改資料、金流那邊的異常，還是可能讓「金流的扣款紀錄」和「訂單狀態」對不起來，而且 saga 本身不會發現，因為它以為自己做完了。所以資深工程師會在 saga 外面再加一層保險：對帳（reconciliation），也就是定期拿兩邊各自的紀錄逐筆比對。例如每天把金流閘道的交易明細下載下來，跟訂單比對：

  • 金流有扣款、訂單是 cancelled → 漏了退款或確認
  • 訂單是 paid、金流沒有這筆 → 不該出餐
  • saga 停在 stuck 超過一小時 → 告警沒人處理

最後一項提醒了一件事：stuck 不是終點，而是交給人的開始。Azure 的補償交易文件也把「交給人工處理」列為正式的一環：stuck 的 saga 要進到一個有人看的地方（死信佇列、後台的待處理清單），附上 saga 紀錄，讓客服或工程師能決定手動退款還是手動補完。

💡 實務上：stuck 清單是給客服用的，不是只給工程師看
顧客打電話說「被扣款卻沒拿到咖啡」，客服第一個要查的就是這張清單。所以後台要讓非工程師看得懂：訂單編號、顧客、卡在哪一步、金流那邊的狀態，以及「手動退款」「標記已處理」這類按鈕，而且每次手動操作都要留下誰、什麼時候、做了什麼。對帳差異也要有負責人：通常是工程師和財務一起看，先約定誰每天看報表、多久內要處理。上線前，資深工程師會先問：「金流逾時、協調者當機、補償失敗時，各會出現在哪裡？誰會被通知？」答不出來，就還沒準備好上線。

回頭數一數，協調者要處理的事已經很多：紀錄、續跑、冪等鍵、重試、逾時、stuck、告警、對帳。這引出最後兩個問題：這些要自己寫嗎？以及，這張訂單真的需要 saga 嗎？

要自己寫協調者嗎？什麼時候根本不需要 saga？

自己寫協調者，要處理的就是上一段列的那些重複工作。這些工作有現成的工具：

  • Temporal：一種 durable execution 引擎，意思是「程式執行到哪裡會被持久保存，當機後能接著執行」。你用普通的 TypeScript 寫流程（workflow），每個外部呼叫是一個 activity；Temporal 伺服器把每一步的結果記在事件歷史（event history）裡，等於替你做了 saga 紀錄。執行流程程式的程序叫 worker，worker 當機後由另一個 worker 重播歷史、從中斷處繼續。activity 依重試政策自動重試。要注意的是，activity 還是可能被執行不只一次，所以依然要冪等。版本與官方範例見課末。
  • BullMQ 的 flow（NestJS 課第 20 課）：用父子工作表示「子工作都完成後才執行父工作」，適合「扇出再收斂」（一次分出好幾個平行的子工作，全部做完再彙整），但補償要自己寫。
  • 自己做：一張 sagas 表（目前狀態）＋一張 saga_steps 表（每步的紀錄）＋第 12 課的 outbox 送命令＋定期掃描卡住的 saga。步驟少、團隊不想多維運一套系統時夠用。

比選工具更重要的，是先確認這裡需不需要 saga。Saga 換來的是跨服務也能「全部完成或全部抵銷」，付出的是補償、中間狀態、紀錄與對帳。下面三種情況付了代價卻換不到東西：

  • 全部在同一個資料庫：直接用交易。有人把模組化單體（一個程式、一個資料庫，內部分成幾個模組，第 15 課會教）裡的「訂單模組」和「庫存模組」也做成 saga，平白多了補償和中間狀態。
  • 只有一個外部呼叫：先在本地寫好訂單（pending_payment），呼叫金流，再依結果更新，搭配冪等鍵和對帳就夠了。
  • 失敗了也沒關係的步驟：寄收據失敗不用取消訂單，丟到佇列重試即可。

咖啡店的下單需要 saga，是因為庫存、金流、會員分屬不同的系統。Saga 是拆分服務之後付出的代價之一（第 15 課會再談）：拆之前，先問這兩邊的資料是否真的需要分開。

補充與查表

  • 名稱出處：saga 出自 Hector Garcia-Molina 與 Kenneth Salem 1987 年的論文〈Sagas〉。
  • 這課引用的 Azure 文件：步驟的三種分類（compensable、pivot、retryable）、三種隔離異常與五種對策、orchestration 與 choreography 的比較，出自 Azure Architecture Center 的 Saga 模式文件（2025-02-25）。「不可逆的步驟要等所有關鍵驗證都成功之後才做」與「交給人工處理」出自補償交易（Compensating Transaction）模式文件（2026-04-16）。
  • 補償的順序：Azure 的補償交易文件提醒，補償不一定要照完全相反的順序，彼此無關的補償可以平行做。這一課的練習用反向依序補償。
  • Temporal：Node 客戶端套件 @temporalio/client 1.25.0（2026-10-27）。activity 的重試政策裡，maximumAttempts 設 0 代表不限次數。官方範例 samples-typescript/saga 示範失敗時反向呼叫補償 activity。

練習

練習 1：完成 runSaga(steps, log)。依序執行每一步的 action：

  • 成功就 log.append({ step, status: 'done' })，繼續下一步；全部成功回傳 { status: 'completed' }。
  • 某一步的 action 丟錯（假設它自己的重試已經用盡）：記 failed，後面的步驟不再執行，然後把已經 done 的步驟依相反順序補償。失敗的那一步本身不補償。
  • 每個補償最多呼叫 3 次，成功就記 compensated；3 次都失敗就記 stuck，立刻回傳 { status: 'stuck', step }，不再補償更早的步驟。
  • 補償全部成功回傳 { status: 'compensated', failedStep }。runSaga 本身不丟錯。

練習 2：協調者當機重啟後，寫 resumeSaga(steps, entries, log) 依照已經寫下的紀錄 entries 續跑。新的紀錄一樣寫進 log（不要重寫舊的），補償規則同練習 1（反向、最多 3 次、stuck 就停）：

  • 沒有 failed 紀錄：saga 還在往前走。從第一個還沒 done 的步驟繼續；之後失敗時，要補償的是所有 done 的步驟（包含當機前完成的）。
  • 有 failed 紀錄：saga 在補償中。不再執行任何 action，只補償「done 但還沒 compensated」的步驟，依步驟的相反順序；結果的 failedStep 是紀錄裡 failed 的那一步。
  • 已經 done 的步驟不能再呼叫 action，已經 compensated 的不能再補償。entries 是空的時候，等於從頭執行。

練習 3：先寫 validateSaga(def) 檢查 saga 定義，回傳問題代碼的陣列，沒有問題回傳 []：

  • 'no-pivot'：沒有任何 pivot。這時只回傳 ['no-pivot']。
  • 以第一個 pivot 為界：它之前出現 retryable → 'retryable-before-pivot'；它之後出現 compensable → 'compensable-after-pivot'；之後又出現 pivot → 'multiple-pivots'。
  • 每種代碼最多出現一次，依「第一個觸發它的步驟」的位置排序。

再填寫 ORDER_SAGA：用上面的 6 個步驟名稱各一次，排出咖啡店下單的順序並標上種類，讓 validateSaga(ORDER_SAGA) 回傳 []。想想哪些步驟做了就收不回來、哪些驗證要先做。

練習 4：王小明的扣款成功了，接著建立廚房工單時，廚房系統回 503。協調者應該怎麼做？

✓ 扣款是 pivot，它成功之後流程只能往前走。出廚房單是可重試的步驟：503 是暫時性錯誤，照第 8 課退避重試，冪等鍵讓重送不會出兩張單；長時間失敗要告警，讓人處理（例如請店員手動出單）。(a) 把「失敗就補償」套在 pivot 之後，顧客付了錢卻被退款取消，原本只是廚房系統晃一下。(b) 讓顧客重新下單會扣第二次款。

練習 5：關於補償交易，哪一個說法正確？

✓ 前面的步驟早就提交了，沒有東西可以「回滾」。補償是往前寫一筆新的交易：退款在帳上是第二筆紀錄，釋放庫存時其他 saga 可能已經動過庫存，所以要寫成「加回 1 杯」。(a) 混淆了 ROLLBACK 與補償。(c) 補償處理的是原子性，不提供隔離：中間狀態一直都看得到，要靠 semantic lock、交換律更新等對策。

練習 6：團隊想把下單流程改成 choreography，理由是「不用多一個協調者，比較簡單」。流程有 6 步、其中 2 步要補償。你的看法？

✓ Azure 的比較：choreography 適合步驟少、參與者少的簡單流程；步驟多、有補償時，沒有人能從一個地方看出「訂單現在卡在哪」，新增步驟也要追出誰聽誰。(b) 協調者確實是要顧好的元件，但它的狀態存在資料庫、可以多台跑、當機後從紀錄續跑，這個代價通常比流程失控小。(c) 兩者的流程寫在不同地方，維運與測試方式差很多。

練習 7：陳美華的訂單正在扣款（狀態 pending_payment），她在 App 上按了「取消訂單」。系統應該怎麼處理？

✓ Saga 沒有隔離，pending_payment 就是 semantic lock：它告訴其他操作「這筆正在進行中」。(a) 直接改狀態，saga 下一步扣款成功、確認訂單會把它改回 paid，或者訂單取消了錢卻被扣走。(b) 忽略扣款成功的事件，錢已經扣了卻沒有訂單、也沒有退款，只能等對帳發現。

常見錯誤

  • 同一個資料庫內也用 saga：多了補償和中間狀態，什麼都沒換到。同一個資料庫直接用交易。
  • 不可逆的步驟放在前面：先扣款再檢查庫存，庫存不足時只能退款。把不可逆或代價高的步驟放在所有驗證之後。
  • 一失敗就補償：網路抖一下就退款取消。暫時性錯誤先重試，重試用盡或確定是業務失敗才補償；pivot 之後根本不補償。
  • 補償失敗後無限重試或默默放棄：前者打爆對方，後者留下沒人知道的不一致。設上限，用盡就標成 stuck、告警、交給人。
  • 沒有記錄進度：協調者當機後不知道做到哪裡，只能從頭跑或放著不管。每完成一步就寫進 saga 紀錄，重啟時依紀錄續跑。
  • 步驟或補償不冪等：協調者在「呼叫成功、還沒寫紀錄」時當機，重啟後再呼叫一次，就重複扣款或重複退款。每一步都帶 saga:<id>:<步驟> 冪等鍵。
  • 以為 saga 有隔離：其他流程會看到中間狀態，用「讀出來再寫回去」會蓋掉別人的修改。用 semantic lock 擋住衝突操作，用交換律更新（qty = qty - 1）。
  • 把逾時當成失敗：扣款逾時就補償，但對方可能已經扣款。用同一把冪等鍵重試或查詢，確定結果再決定。
  • 沒有對帳：saga 的 bug 會留下金流與訂單對不起來的資料，沒人發現。每天把金流明細跟訂單比對。

小結

  • 跨服務、跨外部系統沒有一個交易包得住；2PC 會讓參與者在協調者卡住時一起鎖著，外部金流也不支援。Saga 用一連串各自提交的本地交易加上補償，達成最終一致。
  • 補償是語意上的抵銷，不是回滾：退款是新的一筆，釋放庫存寫成「加回」。訂單 #501 扣款失敗時，反向補償：先釋放拿鐵、再取消訂單。
  • 步驟分三種：可補償的在前、pivot 一個、可重試的在後。不可逆的步驟放在所有驗證之後；咖啡店下單的 pivot 是扣款。
  • Orchestration 協調者：先重試再補償、反向補償、補償有重試上限、用盡就 stuck 交給人。每步寫 saga 紀錄，當機後依紀錄續跑；加上冪等鍵讓重做也安全，命令與紀錄用 outbox 一起寫。
  • Choreography 沒有協調者，但流程分散、難追蹤，適合簡單流程。
  • Saga 沒有隔離：用 semantic lock（例如 pending_payment 時不接受直接取消）、交換律更新、pessimistic view、重新讀取處理。
  • 逾時是「結果未知」，用同一把冪等鍵確認再決定；每天對帳是最後一道保險，stuck 清單要讓客服看得懂。
  • Temporal 這類 durable execution 工具替你保存進度與重試，步驟依然要冪等；同一個資料庫內不需要 saga。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 8：金流當機的那 10 分鐘，下單請求數跟平常一樣，金流收到的請求卻是平常的 9 倍。最先該查什麼？

✓ 9 倍正好是 3 × 3：上層的每一次嘗試，都讓下層再跑完自己的 3 次，所以是相乘。只留一層重試，其他層把錯誤往上傳，再用重試預算在大面積失敗時自動停止。a 錯在 jitter 改變的是重試的時間點，不改變總次數。（第 8 課）

練習 9：App 的結帳這樣寫，伺服器已經實作了冪等鍵。哪裡會出事？

async function checkout(cart) {
  for (let attempt = 1; attempt <= 3; attempt++) {
    const key = crypto.randomUUID()
    try {
      return await api.post('/orders', cart, { headers: { 'Idempotency-Key': key } })
    } catch (err) {
      if (!isRetryable(err) || attempt === 3) throw err
      await sleep(backoffWithJitter(attempt))
    }
  }
}

✓ 伺服器認重複只靠 key，key 換了就是新的意圖。把產生 key 移到迴圈外，使用者按下結帳時產生一次，所有重試沿用；下一張訂單再換新的。c 錯在帶冪等鍵、伺服器做了去重，POST 就「實際上冪等」，可以重試。（第 9 課）

練習 10：合作夥伴平常每秒送 5 次，整點會一口氣送 50 筆。你要讓最多 50 個的突發通過，長期平均不超過每秒 10 次。怎麼設？

✓ token bucket 的容量決定一次能通過多少（突發），補充速率決定長期平均。b 錯在每秒只放 10 個，整點的 50 筆有 40 筆會收到 429。a 擋不住同一秒湧入幾百個，視窗交界還可能到 1,200；d 把兩個數字放反了。（第 10 課）

練習 11：金流沒有掛，只是回應從 200 毫秒變成 8 秒。幾分鐘後，根本不呼叫金流的菜單 API 也開始逾時，健康檢查跟著失敗。為什麼？

✓ L = λW：每個付款請求卡的時間 W 從 0.2 秒變 8 秒，同時卡著的請求多了 40 倍，共用的資源被佔滿，健康的功能和健康檢查一起被拖垮。修法是每個呼叫都有逾時，用隔艙讓金流只能用自己那一格，滿了快速失敗。c 錯在「變慢」比「掛掉」更危險：掛掉會快速回錯、釋放資源，變慢才會一點一點吃光共用資源。（第 11 課）

練習 12：結帳成功後要送「訂單成立」事件給廚房。哪一種寫法既不會漏送，也不會送出其實沒成立的訂單？

✓ 訂單和事件一起提交、一起回滾，relay 只送已提交的列；送出後、標記前當機會再送一次，所以消費者要冪等。b 錯在 COMMIT 之後、送出之前程序當機或被部署重啟，訊息就沒了，重試幾次都救不回來，而且不會報錯。a 會在 COMMIT 失敗時送出不存在的訂單，d 送出失敗就永遠遺失。（第 12 課）

練習 13：集點的消費者這樣寫，佇列是至少一次送達。哪裡會出事？

async function onOrderPaid(msg) {
  const seen = await db.query('SELECT 1 FROM inbox WHERE msg_id = $1', [msg.id])
  if (seen.rowCount > 0) return ack(msg)
  await db.query('UPDATE customers SET points = points + 10 WHERE id = $1', [msg.customerId])
  await db.query('INSERT INTO inbox (msg_id) VALUES ($1)', [msg.id])
  await ack(msg)
}

✓ inbox 紀錄要跟副作用在同一個交易，用 ON CONFLICT DO NOTHING 原子插入，看影響列數決定要不要加點，不要先查再寫。c 錯在紀錄在前會遺失：寫完 inbox、加點前當機，重送時被當成做過了，點數永遠沒加上。b 是至多一次，處理到一半當機訊息就沒了。（第 12 課）

練習 14：saga 已經預留了庫存，呼叫金流扣款時逾時了。協調者接下來該怎麼做？

✓ 逾時是結果未知：請求可能沒到，也可能已經扣款、只是回應掉了。同一把 key 重試不會重複扣款，拿到確定的結果才決定下一步；一直確認不了就標成 stuck 交給人。b 錯在對方可能已經扣款，顧客付了錢、訂單卻被取消。（第 13 課）
