階段 3：可靠性：失敗是常態 · 第 10 課

限流：保護服務，也保護其他客戶

咖啡店開放下單 API 給外送平台和企業團購客戶，每個合作夥伴用自己的 API key 呼叫。某天其中一家外送平台更新了程式，裡面有個 bug：收到錯誤就立刻重試，完全不等待。伺服器一忙就回錯誤，錯誤又引發更多重試，很快變成每秒 3,000 個請求的無窮迴圈。API 的容量被它一家吃光，其他合作夥伴送來的訂單一路排隊到逾時，200 家門市的顧客點不了餐。

第 8 課站在呼叫方，讓你的程式失敗後有節制地重試；這一課站到另一邊：別人送得太多時，你的 API 要怎麼擋。整課只做一件事：替咖啡店的合作夥伴 API 加上限流（rate limiting），讓這家外送平台的 bug 只傷到它自己，不拖垮其他客戶。

這課的路線：
  1. 為什麼一家暴衝會拖垮所有人，最簡單的擋法是什麼：容量先搶先贏；固定視窗每分鐘數次數、超過就拒絕，以及它在視窗交界的漏洞。
  2. 怎麼數得更準、又允許合理的突發：滑動視窗看「剛剛這 60 秒」，token bucket 把突發和長期平均分開管。
  3. 依誰計數、被擋了回什麼：依 API key 還是 IP，多層限流的檢查順序，回 429 並用 Retry-After 告訴客戶端何時再來。
  4. 搬上正式環境：好幾台 API 時計數放在哪裡，限流器自己壞了要放行還是拒絕，規則怎麼安全上線。
這課會用到：
  • 第 3 課的使用率與排隊：機器越接近滿載，排隊時間越暴增。
  • 第 8 課的 Retry-After 與退避：伺服器告訴客戶端多久之後再來，客戶端每次重試前等的時間加倍。

一家合作夥伴暴衝，為什麼其他人也點不了餐？

API 伺服器同一時間能處理的請求數是固定的：CPU、資料庫連線、記憶體都有上限。請求來得比處理得快，多出來的就排隊。第 3 課講過，使用率越接近 100%，排隊時間不是慢慢變長，而是暴增。

關鍵在於：所有合作夥伴的請求排在同一條隊伍裡，伺服器不知道誰是誰，先到先處理。外送平台每秒送 3,000 個，其他合作夥伴加起來每秒可能只有幾十個，隊伍裡幾乎全是外送平台的請求。其他人的訂單排在它後面，等到逾時都還沒輪到。沒有任何保護時，誰送得最多，誰就拿到最多的容量，安分的客戶反而被擠掉。流量暴增的原因很多，合作夥伴的程式寫錯是一種，爬蟲、搶購活動、有人故意攻擊也是，結果都一樣。

限流就是替每個客戶設一個「一段時間內最多幾個請求」的上限，超過的請求在入口直接拒絕，不進入下單流程。一段時間內允許的總量叫配額（quota），例如「每個 API key 每分鐘 100 次」。拒絕一個請求只要查一個計數，不碰資料庫，所以外送平台再怎麼狂送，它多出來的請求只花掉極少的資源，容量留給其他人。

所以限流有兩個目的：保護自己，不要被壓垮；保護其他客戶，一家出事不拖累所有人。後者常被忽略，但對有很多客戶的 API 來說才是主要理由：就算伺服器勉強撐得住，你也不希望一家的 bug 變成所有人的事故。

「限制請求」其實有三種機制，常被混在一起。它們擋的是不同的問題：

  • 限流（rate limiting）：限制一段時間內的請求數，例如每個 API key 每分鐘 100 次。外送平台的事故就是這一種：一個客戶送太多。
  • 並行數限制（concurrency limit）：限制同時進行中的請求數，例如每個客戶最多 20 個。用 第 3 課的 Little's Law 看：並行數 = 速率 × 每個請求的時間。匯出報表一個要 2 秒，每秒 10 個就有 20 個同時在跑。速率限制管不到「每個都很慢」的請求，並行數限制可以。
  • 負載卸除（load shedding）：伺服器整體過載時，主動拒絕一部分（通常是低優先的）請求，不管它屬於誰。第 11 課詳談。

前兩個針對某個客戶，最後一個針對整台伺服器。這課專注在前者，以及怎麼讓兩者配合；Stripe 怎麼把這三種疊成線上的四層，見課末「補充與查表」。

💡 實務上：先從「最貴、最容易被濫用」的端點開始
小專案不需要一開始就設計完整的多層限流。先找出這幾類端點：登入和忘記密碼（暴力破解）、寄簡訊或 Email 驗證碼（每封都要錢，被灌爆就是帳單爆炸）、搜尋和匯出報表（一個請求就很吃資料庫）、開放給合作夥伴的 API。咖啡店的菜單查詢通常有快取擋著，不是第一優先；合作夥伴的下單 API 就在這份清單上，這也是本課從它開始的原因。資深工程師會先問：這個端點被狂打時，壞掉的是什麼？伺服器、資料庫、帳單，還是其他客戶的體驗？答案決定要用限流、並行數限制，還是別的保護。

接下來要回答的是：怎麼替每個 API key 數「一段時間內幾次」？

最簡單的擋法：每分鐘數次數，夠嗎？

「數一段時間內幾次」最直覺的做法是固定視窗（fixed window）。把時間切成整分鐘：0:00 到 0:59.999 是第 0 個視窗，1:00 到 1:59.999 是第 1 個，以此類推。每個 API key 在每個視窗有一個計數器。請求進來時，先用 Math.floor(現在時間 ÷ 60000) 算出它屬於第幾個視窗，把那個視窗的計數加 1；加之前已經到上限，就拒絕。下一分鐘換成新的視窗，計數自然從 0 開始。每個 key 只要存一個數字，很好懂，認證課第 16 課就用它擋登入的暴力破解。

套到開場的事故：外送平台的合約是每分鐘 100 次。它每秒送 3,000 個，一分鐘就是 180,000 個；每分鐘的前 100 個通過，剩下的 179,900 個在入口就被拒絕，不碰資料庫。其他合作夥伴的請求不用再排在它後面。這就是開場問題的最小答案。

但它有一個漏洞，出在視窗交界。上限每分鐘 100 次，有人在 0:59 送 100 個、1:01 再送 100 個：兩波請求分屬不同視窗，各自都沒超過上限，全部通過。2 秒內通過了 200 個，是你以為的兩倍。

這個誤差要不要緊，看限流是為了什麼。擋暴力破解時無所謂：攻擊者一小時能試的次數還是被限制住了。但這課的限流是為了保護容量：你照「每個合作夥伴每分鐘 100」規劃資料庫的負載，實際瞬間湧進來的是兩倍，固定視窗就不夠了。要堵住這個漏洞，限流器看的不能是「時鐘上的這一分鐘」，而要是「剛剛這 60 秒」。

怎麼數「剛剛這 60 秒」？滑動視窗

最直接的做法是把每個請求的時間都記下來，這叫滑動視窗紀錄（sliding window log）。每個 key 存下最近每個請求的時間戳；新請求來時，先丟掉一分鐘前的紀錄，剩下的數量還沒到上限才放行，並把這次的時間記進去。它看的永遠是「剛剛這 60 秒」，視窗跟著時間滑動，沒有交界，所以沒有邊界問題，而且精確。代價是記憶體：上限每分鐘 1,000 次，每個 key 就要存最多 1,000 個時間戳；客戶一多，這就是大量記憶體。

能不能只存幾個數字，又沒有固定視窗的漏洞？滑動視窗計數（sliding window counter）是 Cloudflare 用的近似法。它照樣把時間切成固定視窗，但只存「上一個視窗」和「目前視窗」兩個計數。要估「剛剛這 60 秒」有幾個請求時，目前視窗的請求全部都在範圍內；上一個視窗只有後半段還在範圍內，但我們不知道它的請求落在哪些時間點，所以假設它們是平均分布的，照還留在範圍內的時間比例去算：

估計值 = 上一個視窗的數量 × (視窗長度 − 目前視窗已經過的時間) ÷ 視窗長度 + 目前視窗的數量

用 Cloudflare 文章裡的數字來算，練習 2 的測試也用這一組：上限每分鐘 50 次，上一分鐘有 42 個，這一分鐘過了 15 秒、已經有 18 個。「剛剛這 60 秒」涵蓋上一分鐘的後 45 秒，所以拿 42 的 45/60。執行後看兩行：這個請求和下一個請求各自放行還是拒絕。

42 × 45/60 + 18 = 49.5 < 50，這個請求放行；放行後目前視窗變成 19，下一個請求的估計值 50.5，被拒絕。注意比較的是「加入這個請求之前的估計值 < 上限」，不是「加 1 之後 ≤ 上限」，兩種寫法在小數時結果不同。

回到上一節的漏洞：上限每分鐘 100 次，0:59 送了 100 個，1:01 再來時目前視窗才過 1 秒，估計值是 100 × 59/60 ≈ 98.3，只能再放行 2 個，不是固定視窗的 100 個。

它只是近似：上一個視窗的請求如果全擠在最後一秒，估計值會偏低。但 Cloudflare 在約 4 億個請求、27 萬個來源的樣本裡量到，只有 0.003% 的請求被誤判放行或誤擋。每個 key 只要兩個數字，換來接近精確的結果，這是正式環境常見的選擇。練習 2 你會寫一個。

滑動視窗解決了邊界問題，但它和固定視窗回答的是同一個問題：「這段時間用了幾次」，到上限就一律拒絕。真實流量常常是一陣一陣的：客戶的 App 開啟時一次打 6 支 API，是正常行為，不該被擋。要讓這種短暫的一波通過，同時長期平均還是被限制住，就需要能把「突發」和「平均」分開調的方法。

想允許短暫突發，又要限制長期平均？Token bucket

先把名詞說清楚。突發（burst）是短時間內超過平均速率的一波請求，例如平均每秒 5 個的客戶，某一瞬間連送 6 個。前面的方法都在「數一段時間內的次數」，突發只要讓那段時間的總數超過上限就會被擋。

Token bucket 換一個角度：每個 key 有一個桶子，裡面裝 token，可以想成「預先發好的入場券」。桶子以固定速率補充 token，滿了就不再增加；每個請求拿走一個 token，沒有 token 就拒絕。一個請求要拿走幾個 token 叫它的 cost，預設 1；很吃資源的端點（例如匯出報表）可以設成一次拿 5 個，同樣的桶就只夠它用較少次。

外送平台的合約「每分鐘 100 次」換成 token bucket，就是補充速率每秒約 1.67 個（100 ÷ 60），容量則決定一次能突發多少。1.67 這種小數不好心算，所以這節的例子改用練習 1 的設定：容量 10、每秒補 5 個。原理完全一樣，只是數字不同；合約的上限沒有變。

兩個參數各管一件事。容量（capacity）決定允許多大的突發：客戶一段時間沒送請求，桶子會補滿到 10 個，下一波最多一次可以衝 10 個，App 開啟時一次打 6 支 API 就不會被擋。補充速率決定長期平均：桶子空了以後，每秒只會多出 5 個 token，所以不管怎麼送，長期下來每秒最多 5 個。套到外送平台的無窮迴圈：前 10 個請求用掉桶裡的 token 通過，之後每秒只有 5 個通過，其餘全部拒絕。

實作上有兩個細節，練習 1 會檢查。第一，不要用計時器補充。每個 key 開一個 setInterval，一百萬個客戶就是一百萬個計時器，還要記得清掉，而且計時器本身不準。改成記下「上次計算的時間」，下次有請求時用時間差一次補足：tokens = min(容量, tokens + 經過秒數 × 速率)。閒置的 key 完全不花 CPU。

第二，token 用小數記。每 100ms 來一個請求、每秒補 5 個，每次只補 0.5 個。如果每次都向下取整，0.5 變成 0，永遠補不到。

拒絕時也要算出「多久後可以再試」：還差 cost − tokens 個，除以速率就是秒數。這個數字之後會變成回應裡的 Retry-After，後面「被擋的請求要回什麼」那一節會用到。

還有一個名字很像的方法：leaky bucket。它的方向相反：請求進到桶子（佇列）裡，以固定速率流出去處理，桶子滿了就拒絕。它讓輸出變平滑，後端看到的是穩定的速率；代價是排在桶裡的請求要等。部署課第 12 課的 nginx limit_req 就是 leaky bucket，它的參數怎麼對應這兩種桶，見課末「補充與查表」。

咖啡店的合作夥伴 API 選 token bucket：合作夥伴的系統常會一次送一批訂單，容量讓這種正常的突發通過，補充速率守住長期平均。不選 leaky bucket，是因為它會讓超量的下單請求在桶裡排隊等，合作夥伴那邊看到的會是逾時，而不是明確被拒絕、知道該多久後再來；它適合放在需要穩定輸入的後端前面，例如部署課的 nginx。演算法選好了，但「每秒 5 個」還沒說清楚是誰的每秒 5 個。

「每秒 5 個」是誰的？限流的鍵與多層順序

限流器替每個「誰」各準備一個桶子，這個「誰」叫限流的鍵（key）。外送平台的事故裡，鍵很明顯是 API key：每個合作夥伴一把，各用各的桶，外送平台的桶空了，不影響別人的桶。但不是每個端點都有 API key，例如登入前的請求只有 IP，所以要知道每種鍵的優缺點。

用 IP 當鍵之前，要先知道兩件事。第一是 NAT（網路位址轉譯）：公司、學校、行動網路常讓很多台裝置透過同一個對外 IP 上網，所以一個 IP 背後可能是一整間公司。第二，經過代理或負載平衡器時，伺服器看到的連線來源是代理，原始 IP 要從 X-Forwarded-For 標頭讀；但這個標頭客戶端也能自己填，只能信任自己的代理加上的那一段（部署課第 12 課）。

實務上不會只選一種，而是疊好幾層，由外到內：入口先依 IP 擋掉明顯的濫用，再依 API key 確保每個客戶公平，最後有一個全站的桶守住總容量。

檢查的順序很重要。如果先扣全站的 token、再檢查客戶的，外送平台每秒 3,000 個請求雖然都被它自己的限制擋下，卻在被擋之前先把全站的 token 拿光了，其他客戶全部被拒絕：限流反而幫它拖垮了大家。正確的順序是先檢查客戶，通過了才去拿全站的。反過來也要處理：客戶通過、全站拒絕時，要把客戶的 token 還回去，不然它是因為別人而被扣了配額。

每個 key 一個桶，還有記憶體的問題。攻擊者只要每次換一個假的 API key 或 IP，存桶子的 Map 就無限長大，直到程序記憶體耗盡。用 Node 課第 23 課的有上限 LRU 限制數量，淘汰最久沒用的。代價：被淘汰的客戶下次從滿的桶開始，等於拿到一次額外的突發。只要上限比「同時活躍的客戶數」大得多，被淘汰的都是很久沒來的客戶，它們的桶本來也早就補滿了，這個誤差可以接受。練習 4 把這幾件事寫在一起。

💡 實務上：上限數字要跟 PM 和業務一起定
對外 API 的上限常常直接對應付費方案，例如免費方案每分鐘 60 次、企業方案另外談，這是產品決策，不是工程師自己決定。訂數字前先拉出各客戶現有的用量，上限放在正常尖峰之上並留餘裕，不然規則一上線就擋到大客戶。上限要寫進 API 文件，讓串接的工程師開發時就知道，而不是上線後才看到 429。大客戶快碰到上限時，最好由業務或客服先聯絡，不要讓對方從錯誤報表發現。外送平台的配額也一樣：寫進合約和文件，對方的工程師才知道自己的程式該控速到多少。

鍵和層次決定了誰被擋，下一個問題是被擋下的那些請求，要回什麼給外送平台。

被擋的請求要回什麼？429 與 Retry-After

被限流時回 429 Too Many Requests（RFC 6585，2012）：意思是「你在一段時間內送太多了」。RFC 6585 只定義狀態碼，不規定怎麼辨識使用者或怎麼計數，那是前面幾節的設計。

它和 503 Service Unavailable 不一樣：503 是「我現在撐不住」，跟哪個客戶無關，是負載卸除（第 11 課）該回的。分清楚，外送平台看錯誤報表時才知道是自己的問題還是你的問題，你的告警也才不會把「某客戶送太多」當成「服務掛了」。nginx 的 limit_req 被拒絕時預設回 503，部署課把它改成 429，就是這個原因。

光回 429 還不夠。外送平台的 bug 是「收到錯誤就立刻重試」，如果回應裡沒有說多久之後再來，客戶端只能用猜的，最常見的猜法就是立刻重試，於是被拒絕的請求變成更多請求。所以 429 要附 Retry-After（RFC 9110 §10.2.3），503 也可以附：值是 HTTP 日期或非負整數秒數，例如 Retry-After: 12。有它，第 8 課的客戶端就能照著等。注意單位是秒，token bucket 算出來的是毫秒，要除以 1000 並無條件進位，四捨五入會讓客戶端早到、又被拒絕一次。

Retry-After 是被擋之後才告訴客戶端。如果合作夥伴能在被擋之前就知道還剩多少配額，它可以自己放慢，根本不會碰到 429。這就是 IETF 的 RateLimit 標頭要做的事。它目前還是草案，欄位名稱和參數在成為 RFC 前還可能改。本課依草案 -11 的格式（練習 3 也是）；撰寫時最新版已是 -12，它把 RateLimit 的參數 r、t 改名為 a、w，這正是「還可能改」的例子，版本與日期見課末「補充與查表」：

HTTP/1.1 429 Too Many Requests
RateLimit-Policy: "default";q=100;w=60
RateLimit: "default";r=0;t=12
Retry-After: 12
  • RateLimit-Policy：政策名稱（Structured Field 字串，要加雙引號），q 是配額、w 是視窗秒數。上面是「每 60 秒 100 個」。可以列好幾個政策，例如 "burst";q=100;w=60,"daily";q=1000;w=86400。
  • RateLimit：r 是剩下幾個；t 是有效視窗的秒數，意思是「接下來 t 秒內最多只能再用 r 個」，實務上就是配額多久後重置。
  • 同時有 Retry-After 時，客戶端以 Retry-After 為準；草案也建議（SHOULD NOT）伺服器不要讓 Retry-After 指向比有效視窗結束還早的時間。

你會看到很多服務和套件還在用 X-RateLimit-Limit、X-RateLimit-Remaining 這類非標準的欄位（NestJS 的例子見課末）。新設計照草案的格式寫，並在文件裡註明它是草案。練習 3 會產生這三個標頭。

💡 實務上：前端和串接第三方時，你是被限流的那一方
這課的外送平台事故反過來看，就是你自己的程式可能犯的錯。串地圖、簡訊、金流這類第三方 API，或前端呼叫自己的後端時，都要預期會收到 429。照 Retry-After 等待再試，不要立刻重試。搜尋框加 debounce：使用者停止輸入一小段時間才送出，不要每打一個字就送一個請求。畫面上顯示「操作太頻繁，請稍後再試」，而不是通用的「系統錯誤」。批次同步資料的排程也要自己控速，一次處理一小批、批與批之間留間隔。被擋時記 log，才看得出是該升級方案，還是該改呼叫方式。

到這裡，單台 API 的限流已經完整：數得準、允許合理突發、依 API key 分開、被擋時告訴客戶端何時再來。但咖啡店的 API 不只一台。

API 有 4 台時，計數要放在哪裡？

到目前為止，桶子和計數都存在程序的記憶體裡。第 4 課之後咖啡店的 API 有 4 台，負載平衡器把請求分給它們，每台只看得到自己收到的那部分。每台各算各的會怎樣？下面這格模擬三種情況，執行後比較三行印出的通過數量。

三行的結果依序是：

  • 每台各限 100，請求輪流分給 4 台，每台都只看到四分之一，各自放行 100 個：客戶實際能送 400 個。
  • 改成每台限 100 ÷ 4 = 25，請求平均分配時，總共剛好 100。
  • 但分配不均時（長連線、第 7 課的一致性雜湊），9 成請求落在同一台。這個客戶只送了配額內的 100 個，卻只有 35 個通過，65 個被冤枉擋下。機器數量變動時還要記得改這個數字。

要準確，計數就要集中在所有機器共用的地方，通常是 Redis。但集中之後馬上有新問題：4 台同時在改同一個計數，會不會互相覆蓋？這要靠原子操作：一個操作從開始到結束不會被其他請求插進來，從外面看只有「還沒做」和「做完了」兩種狀態，沒有「做到一半」。

固定視窗用 Redis 很直接。INCR rl:{key}:{視窗編號} 把計數加 1 並回傳新值，本身就是原子操作；回傳 1 時代表是這個視窗的第一個請求，再用 EXPIRE 設過期時間，舊視窗的計數才會自動清掉。

Token bucket 就麻煩了。它要「讀 token 數 → 算補充 → 扣掉 → 寫回」，是先讀再寫。兩台同時讀到 1 個 token、各自扣掉，兩個請求都放行，這就是第 9 課的競態。解法是把整段邏輯交給 Redis 自己執行。Redis 內建 Lua 這種小型程式語言的執行環境，可以把整段邏輯寫成 Lua 腳本，用 EVAL 送給 Redis；Redis 執行一個腳本時不會穿插其他指令，整段就是一次原子操作。Stripe 就是把 token bucket 放在 Redis 裡做。

代價是每個請求多一次 Redis 往返，而且 Redis 變成限流的依賴。實務上不用自己寫：rate-limiter-flexible 的 RateLimiterRedis 搭配 ioredis 就有原子的計數，它被拒絕時給 msBeforeNext（毫秒）可以換算 Retry-After。要注意它的演算法是「每個 key 從第一個請求開始算的固定視窗」，有第二節說的邊界突發；要壓低突發，常見做法是再加一個短視窗的限制（例如每秒 5 個），用它的 RateLimiterUnion 同時套用兩個限流器。版本見課末。

計數集中到 Redis 之後，限流器多了一個會壞的零件。下一節處理它壞掉的時候，以及整套規則怎麼安全上線。

Redis 壞了、規則要上線：限流器自己出事怎麼辦？

Redis 連不上時，限流器沒辦法判斷這個請求該不該放行，只有兩個選擇：

  • fail open：放行全部。服務繼續運作，只是暫時沒有限流保護。
  • fail closed：拒絕全部。安全，但限流器的故障直接變成整個 API 的故障。

選哪一個，看你保護的是什麼。保護容量的 API 限流通常 fail open：Stripe 的建議是限流器出錯或 Redis 掛掉時要放行，各層都要 catch 例外。咖啡店的合作夥伴 API 屬於這一種：為了限流器的故障拒絕所有訂單，比暫時沒有限流更糟。

折衷的做法是退回每台各自的記憶體限流。rate-limiter-flexible 的 insuranceLimiter 就是做這件事：Redis 壞掉時改用本機的限流器，每台設 100 ÷ 4，不準但還有保護。

// rate-limiter-flexible 11.2.3 的基本用法（示意，不能在頁面執行）
const limiter = new RateLimiterRedis({
  storeClient: redis,               // new Redis({ enableOfflineQueue: false })
  points: 100,                      // 配額
  duration: 60,                     // 視窗秒數
  insuranceLimiter: new RateLimiterMemory({ points: 25, duration: 60 }),  // Redis 壞掉時改用本機
})

保護登入的暴力破解防護就要保守一點，例如退回本機的嚴格限制，因為那裡放行的代價是帳號被盜。不管哪一種，都要告警：fail open 是暫時的取捨，要有人知道並盡快修好。

限流器本身沒壞，規則也可能訂錯。上線前先 dark launch：先只記錄「這個請求會被擋」、不真的擋，觀察一兩週：會被擋的是哪些客戶、多少比例。不然第一天就可能擋到最大的客戶，因為它的正常用量本來就很高。

Stripe 還建議每個限流器都要有開關，誤擋時能馬上關掉。這種開關叫功能旗標：不用重新部署、改設定就能切換程式行為，第 19 課詳談。上線後要監控：被擋的比例、被擋最多的是哪些客戶、限流器本身的延遲與錯誤。

回到開場：同一家外送平台的 bug 再發生一次，它每秒 3,000 個請求在入口就被它自己的桶擋下，收到附 Retry-After 的 429；全站的 token 沒被它動到，其他合作夥伴照常下單；告警告訴你是哪一把 API key 被擋最多，業務可以直接聯絡對方修程式。

Stripe 線上的四層限流

Stripe 在 2017 年的文章〈Scaling your API with rate limiters〉描述他們線上用的四層，剛好涵蓋第一節的三種機制。前兩個是針對某個客戶，後兩個是針對整台伺服器：

機制做什麼屬於
請求速率限制每個使用者每秒最多 N 個，允許短暫突發限流
同時請求限制每個使用者同時進行中的請求數上限（文中例子是 20）並行數限制
整體用量卸除保留一部分基礎設施給重要請求（例子：留 20%），非重要請求超過它的 80% 就回 503負載卸除
worker 使用率卸除worker 忙不過來時，從最低優先的流量開始丟負載卸除

nginx limit_req 的參數

  • limit_req 是 leaky bucket：rate=1r/s 是流出速率。
  • burst=5 是桶的大小：超過速率的請求先排隊延後處理，超過 burst 就拒絕。
  • 加上 nodelay 時，burst 內的請求立刻處理、不再延後，行為就很接近 token bucket。
  • 被拒絕的請求預設回 503（limit_req_status 的預設值），部署課改成了 429，原因見「被擋的請求要回什麼」那一節。

RateLimit 標頭草案版本

  • draft-ietf-httpapi-ratelimit-headers-11：2026-05-23 發布、2026-11-24 到期。本課正文與練習 3 依這版：RateLimit 用 r（剩下）與 t（有效視窗秒數）。
  • draft-ietf-httpapi-ratelimit-headers-12：2026-11-20 發布、2027-05-24 到期。RateLimit 的參數改成 a（available quota）與 w（effective window）；RateLimit-Policy 的 q、w 不變。實作前到 IETF datatracker 確認最新版。

套件版本

  • @nestjs/throttler 6.7.1 預設送 X-RateLimit-* 標頭（NestJS 課第 6 課）。
  • rate-limiter-flexible（npm 11.2.3）搭配 ioredis（6.0.0）。

練習

練習 1：完成 TokenBucket。一開始是滿的。tryTake(cost = 1)：先依距離上次計算的時間補充 token（可以是小數、不超過 capacity），夠就扣掉並回傳 { ok: true, remaining: Math.floor(剩下的 token) }；不夠回傳 { ok: false, retryAfterMs }，retryAfterMs = Math.ceil((cost − 目前 token) ÷ refillPerSec × 1000)。cost 不是正數或大於 capacity（永遠拿不到）時丟 RangeError。時間只能用 opts.now()，不能用計時器或 Date.now。

練習 2：完成 SlidingWindowCounter。視窗以 Math.floor(now ÷ windowMs) 對齊。hit()：estimate = 上一個視窗的數量 × ((windowMs − 目前視窗已經過的毫秒) ÷ windowMs) + 目前視窗的數量；estimate < limit 時允許並把目前視窗加 1。回傳 { allowed, estimate }，estimate 是加入這個請求之前的值。被拒絕的請求不計入。中間隔了一個以上的空視窗時，「上一個視窗」的數量是 0。

練習 3：寫 rateLimitHeaders(policy, state)，照 IETF 草案 -11 的格式產生回應標頭。一律包含 RateLimit-Policy（政策名稱加雙引號，接 ;q=配額;w=視窗秒數）與 RateLimit（政策名稱加雙引號，接 ;r=剩下;t=幾秒後恢復）；allowed 是 false 時另加 Retry-After，值跟 t 相同。r 和 t 都要是非負整數：resetSec 無條件進位，remaining 向下取整、小於 0 時當成 0。欄位名稱的大小寫要跟上面一樣。

練習 4：寫 createLimiter(opts)，組合每個客戶的桶和全站的桶。下面已經提供練習 1 的 TokenBucket，另外多了 refund(cost)：把 token 加回去、不超過容量。check(customerId) 每次消耗 1 個 token：

  • 先檢查這個客戶的桶，被拒絕就回傳 { ok: false, scope: 'customer', retryAfterMs }，不能動到全站的桶。
  • 客戶通過再拿全站的；全站被拒絕時把客戶的 token 還回去，回傳 scope: 'global' 與全站的 retryAfterMs。
  • 客戶的桶最多保留 maxCustomers 個，超過時淘汰最久沒用的（被拒絕的 check 也算使用）；新客戶從滿的桶開始。trackedCustomers() 回傳目前保留幾個。

練習 5：固定視窗限制每分鐘 100 次。最壞情況下，2 秒內最多能通過幾次？

✓ 在前一個視窗的最後一秒送 100 個、下一個視窗的第一秒再送 100 個，兩波分屬不同視窗，都沒超過各自的上限。上限只保證「每個對齊的整分鐘」內不超過 100，不保證任意 60 秒。(b) 是平均速率，固定視窗完全不管平均。要擋住這種突發，用滑動視窗或 token bucket。

練習 6：4 台 API 各自在記憶體裡限制「每個客戶每分鐘 100 次」，負載平衡用 round robin。同一個客戶實際上每分鐘最多能送幾次？

✓ 每台只看到四分之一的請求，各自放行 100 個，加起來約 400 個；實際值還取決於負載平衡怎麼分。要準確就集中計數（Redis 原子操作或 Lua 腳本）；或每台設 100 ÷ 4 並接受分配不均時的誤差，而且機器數量一變就要改。(c) 把「每台的上限」和「客戶的總量」搞混了：每台各自放行，總量是加起來的；就算把每台設成 25，客戶總共也還有約 100 個，不是 25。

練習 7：限流用的 Redis 連不上了。API 限流器應該怎麼做？

✓ 一律 fail closed 會讓 Redis 的故障直接變成整個 API 的故障，Stripe 的建議是限流器出錯時放行。但登入防護放行的代價是帳號被盜，可以退回本機較嚴格的限制。(b) 錯在「不重要」：fail open 是暫時的取捨，要有告警、盡快修好，最好有本機的備用限流器。

練習 8：某個客戶送太多回 429。如果是伺服器整體過載（跟哪個客戶無關），應該回什麼？

✓ 429 的意思是「你送太多了」，是針對這個客戶的；整體過載是伺服器自己的問題，用 503，兩者都可以附 Retry-After。回錯狀態碼，客戶會以為是自己的程式有問題，你的告警也分不出「某客戶太吵」和「服務撐不住」。500 表示程式出錯，客戶端不會知道該等多久再試。

常見錯誤

  • 用固定視窗保護容量：視窗交界前後可以送出兩倍的量。擋暴力破解可以用；保護容量用滑動視窗計數或 token bucket。
  • 每台伺服器各自限流，卻當成全域上限：N 台就是 N 倍。集中計數，或明確地把上限除以台數並接受誤差。
  • 先讀再寫的集中計數：兩台同時讀到「還剩 1 個」，兩個請求都放行。用 INCR 或 Lua 腳本做成原子操作。
  • 只用 IP 當鍵：NAT 後面整間公司共用一個 IP，一個人觸發就全公司被擋；X-Forwarded-For 可以偽造，只信任自己代理加上的部分。登入後改用使用者或 API key。
  • 被拒絕的請求也消耗其他層的配額：吵鬧的客戶被自己的限制擋下，卻先吃光全站的 token。先檢查客戶層，全站拒絕時把客戶的 token 還回去。
  • 每個 key 一個計數器卻沒有上限：攻擊者每次換一個假 key，記憶體無限成長。用有上限的 LRU。
  • 用計時器補充 token：每個 key 一個計時器，又多又不準。記下上次的時間，請求來時用時間差計算；token 用小數記。
  • 429 沒附 Retry-After，或秒數四捨五入：客戶端只能猜，通常會立刻重試；四捨五入讓它早到又被拒絕。用整數秒、無條件進位。
  • 沒有 dark launch 就啟用：第一天就擋到正常用量最大的客戶。先只記錄「會被擋」的請求，觀察後再啟用，並準備開關。

小結

  • 沒有限流時，誰送得最多誰就拿到最多容量。限流替每個客戶設一段時間內的上限，除了保護自己，也保護其他客戶。限流管「一段時間幾次」、並行數限制管「同時幾個」、負載卸除管「整體過載時丟掉低優先的」。
  • 固定視窗簡單但交界處可達兩倍；滑動視窗紀錄精確但耗記憶體；滑動視窗計數只存兩個數字、誤差很小。
  • Token bucket：容量是突發、補充速率是平均；用時間差和小數補充，不用計時器。nginx limit_req 是 leaky bucket，nodelay 讓它接近 token bucket。
  • 選對鍵（使用者、API key、IP、端點、租戶），多層由外到內；先檢查客戶再拿全站的，被拒絕的請求不消耗後面的配額；每個 key 的狀態要有上限。
  • 被限流回 429 加 Retry-After（整數秒、無條件進位），客戶端才不會立刻重試；整體過載回 503。RateLimit／RateLimit-Policy 標頭還是草案，本課依 -11 的格式。
  • 多台伺服器要集中、原子地計數，或接受「除以台數」的誤差；限流器壞掉時 API 限流通常 fail open 並告警；上線前 dark launch、準備開關。
