階段 5：資深工程實踐：決策、演進、審查與除錯 · 第 21 課

除錯方法論：從 bug 到線上事故

週五晚上，咖啡店的客服轉來一句話：「有些會員升級成金卡之後，App 還是顯示銀卡。」三個工程師各自打開不同的東西：一個重開了 Redis，一個在程式裡加了十幾行 console.log，一個開始讀上週所有的 PR。兩個小時後問題「好像沒了」，但沒有人知道是哪個動作修好的，下週一又出現了。

三個人都很努力，缺的是方法：沒有人先確認問題能不能重現，沒有人寫下自己在懷疑什麼，三個改動又同時發生。這一課把那個週末重來一次：把「金卡顯示銀卡」從客服的一句話，一路追到根因、一個每次都會失敗的測試、一個修正，以及讓它不再回來的防線。後半段換成另一種情況：週六中午結帳開始大量失敗，顧客每分鐘都在受影響，這時候該做的事和順序都不一樣。

這課的路線：
  1. 週五晚上為什麼白忙：除錯是「寫下假設、用實驗排除」的迴圈，三個實驗就把金卡問題縮到快取的讀寫順序（開場問題的最小答案）。
  2. 懷疑怎麼變成確定：先重現。比對環境差異、把時間變成參數，用 canonical log line 在正式環境的請求裡找共同點。
  3. 偶爾才發生的 bug：用 deferred 控制交錯順序，讓金卡 bug 每次都重現；先寫失敗的測試，再修。
  4. 範圍太大時：用二分法在元件、版本（git bisect）、輸入上每次排除一半。
  5. 結帳正在失敗：從指標和 trace 找出錯誤源頭在哪個服務，先止血再找原因、多人怎麼分工，事後怎麼檢討、補上哪些防線。
這課會用到：
  • 第 5 課的「舊值寫回」競態：讀到舊資料的請求比更新的請求晚寫進快取，舊值就把新值蓋掉。
  • Node 課第 22 課的假時鐘與依賴注入：把現在時間當成參數傳進去，測試就能指定任何時刻。
  • 部署課第 23 課的 trace 與 span：一個請求經過的每一段工作是一個 span，串起來就是整個請求的 trace。

週五晚上為什麼白忙？除錯是一個排除假設的迴圈

先回頭看週五晚上那三個動作，它們各自少了一樣東西。重開 Redis 是先動手、後想原因：就算問題因此消失，也說不出為什麼，而且快取裡原本可以拿來檢查的內容跟著被清掉了。加十幾行 console.log 是沒有想驗證的問題：印出來的東西很多，卻不知道哪一行能證明什麼。讀上週所有的 PR 是範圍沒有縮小：幾十個 PR 裡大部分跟會員等級無關。再加上三件事同時發生，問題「好像沒了」的時候，沒有人能說出是哪一個動作造成的。

Google SRE 書的〈Effective Troubleshooting〉把除錯描述成假設—驗證（hypothetico-deductive method）的迴圈。假設是一句可以被證明錯的話，例如「App 自己快取了舊的會員資料」；實驗是一個動作，它的結果能告訴你這句話對不對。做完實驗，根據結果提出下一個假設，再做下一個實驗。

這個迴圈的重點在「排除」。好的實驗不管結果是什麼，都會讓可能的原因變少：結果是「是」，範圍縮到這個假設；結果是「不是」，這個假設就可以劃掉。「加 console.log 看看」不是實驗，因為你事先說不出看到什麼代表什麼。

實際做起來，記錄不用複雜，一張表就夠。下面是週五晚上本來可以這樣做的版本：

時間假設實驗結果結論
20:10App 端快取用 curl 直接打 APIAPI 也回銀卡排除 App
20:18資料庫沒更新查 members 表已經是金卡排除資料庫，問題在 API 和資料庫之間
20:25Redis 快取沒失效看升級時的 log有呼叫 invalidate失效有做，但快取還是舊值 → 懷疑舊值寫回

每一列都在回答一個問題。第一列問「錯的資料是 App 自己留的，還是伺服器給的」：用 curl 繞過 App 直接打 API，API 也回銀卡，所以 App 可以劃掉。第二列問「資料庫裡的資料是不是就是錯的」：查表發現已經是金卡，所以錯誤發生在 API 和資料庫之間，剩下的就是 Redis 快取。第三列問「升級時有沒有讓快取失效」：log 顯示有呼叫 invalidate。快取明明刪了，裡面卻還是舊值，代表刪掉之後又有人把舊值寫了回去。

這就是第 5 課的舊值寫回。把時間線攤開：

順序請求 A：GET /members/7升級流程
1快取未命中，查資料庫，讀到「銀卡」
2把資料庫改成「金卡」
3呼叫 invalidate，刪掉快取
4把剛才讀到的「銀卡」寫進快取

第 4 步之後，所有讀這位會員的請求都命中快取，拿到銀卡，直到快取過期或被清掉為止。這也解釋了週五晚上：重開 Redis 清掉了那筆舊值，問題就「好像沒了」；但造成它的程式沒變，下一次升級剛好碰上未命中，就又出現了。三個實驗，範圍就從「整個系統」縮到「快取的讀寫順序」。

每一輪要選哪個假設來驗證，SRE 書和實務上有幾個固定的習慣。第一，先問「最近改了什麼」：部署、設定、功能旗標、流量、依賴的版本、資料量。大部分問題是某個改動帶進來的，所以部署紀錄和設定變更紀錄是最快的線索。第二，先想常見的原因：SRE 書借用醫學的說法：「聽到馬蹄聲，先想馬，不要想斑馬。」設定錯、逾時、連線池用完、快取沒更新這些常見原因先查，不要一開始就懷疑編譯器或硬體。上面的表就是這樣排的：App 快取、資料沒更新、快取沒失效，都是「馬」。

第三，一次只改一件事。同時改三個地方，好了不知道是哪個修好的，壞了也不知道是哪個造成的，週五晚上就是這樣。第四，負面結果也寫下來：「直接打 API 也是銀卡」排除了 App，這是有用的資訊；不寫下來，十分鐘後換人接手，又會有人去清 App 的快取。

第五，先確認異常跟問題有關。SRE 書把「追無關的症狀」列為常見陷阱：log 裡本來就有很多錯誤，看到一個就追下去，常常追了半小時才發現它每天都在。先看這個異常在問題開始前是不是也一樣多。第六，限時：卡在同一個假設 30 分鐘沒有進展，就找人講一遍。講給別人聽的過程，常常就會發現自己漏掉的假設。

最後，這個迴圈不是一拿到問題就開始的。SRE 書的流程在檢查之前有一步分級（triage）：先判斷問題有多嚴重、影響多少人。嚴重的問題「先止血」是第一優先，原因之後再找，這一課的後半段會講。金卡顯示錯誤影響的是一部分會員的畫面，沒有擴大，可以照這個迴圈慢慢查。

不過到這裡，「舊值寫回」還只是推論：記錄表最後一列是從「刪了卻還是舊值」推出來的，沒有人親眼看到舊值被寫回去。要確定，就得讓它在你面前發生一次。

舊值寫回只是懷疑：怎麼讓 bug 在你面前發生？

要把推論變成確定，第一步是重現。不能重現的 bug，你沒辦法確認自己修好了：改了程式之後問題沒再出現，可能是修好了，也可能只是這兩天剛好沒觸發。金卡 bug 本來就是偶爾出現，週五晚上它「好像沒了」，週一又回來，「沒出現」不能當證據。

重現的目標是讓問題穩定出現，而且越小越好。最小重現（minimal reproduction）是能觸發問題的最小程式或輸入：不用啟動整個系統、不用登入 App，跑一小段程式就看得到錯。它讓每次實驗只要幾秒，也讓別人能直接幫你看。

工程師在自己電腦上試，常常得到「我這邊好好的」。這句話通常代表你的環境和出問題的環境不一樣，所以下一步是逐項比對差在哪裡：

金卡 bug 落在最後一列。你在本機一次只發一個請求，「讀到銀卡」和「升級」永遠是一個做完才做另一個，時間線上第 1 步和第 4 步之間不會有人插進來。正式環境同時有幾百個請求，偶爾就會剛好交錯。

時間和並發這兩列，解法是同一個想法：把不受控的因素變成參數。程式自己去讀現在時間、自己決定執行順序，測試就只能碰運氣；改成由呼叫者傳進去，測試就能指定任何情況。交錯順序要用到一個新工具，下一節再處理；先用最常見、也最容易掌握的時間來看這個想法怎麼用。下面是同一週被發現的另一個 bug：「營業日」函式把台北早上 8 點以前的訂單，算到前一天的報表。因為時間是參數，我們可以直接指定要測的時刻，不用等到明天早上 7 點半。執行後看每一列的「有 bug」和「修正」兩欄：

只有 7:30 那一筆錯。toISOString() 輸出的是 UTC 時間，台北早上 7:30 是 UTC 前一天的 23:30，取前 10 個字就拿到前一天的日期；8 點以後 UTC 也跨過午夜，兩個版本才一致。這種 bug 在白天測試永遠看不到，因為測試用的是真實時間。Node 課第 22 課的作法在這裡就是除錯工具：把時間、亂數、排程變成參數，就能把「偶爾」變成「每次」。

回到金卡 bug。在本機重現之前，可以先用正式環境的資料檢查假設是不是站得住。如果真的是舊值寫回，拿到銀卡的那些請求應該有共同點：當時快取未命中，而且資料庫查得慢。查得越慢，第 1 步和第 4 步之間的空檔越長，升級剛好插進去的機會越大。要回答「這些請求有什麼共同點」，就需要每個請求留下足夠的資訊。

Stripe 的作法叫 canonical log line：每個請求結束時，多寫一行結構化 log，把這個請求最重要的欄位放在一起，例如方法、路徑、狀態碼、使用者、總耗時、資料庫耗時、快取命中與否。平常的 log 分散在請求處理的各個步驟，要拼出一個請求的全貌得把好幾行對起來；這一行則是一個請求一筆完整的紀錄。這些 log 送進部署課第 21 課的集中 log 系統之後，就能像查資料表一樣篩選與彙總。執行後看最後一行篩出了哪個請求：

篩出來的是 r2：未命中，資料庫花了 820ms。如果客服回報的那幾位會員，升級前後的請求都落在這種「慢的未命中」，舊值寫回的假設就更站得住；如果都是命中、資料庫也不慢，就要回到上一節的表，重新列假設。重現不了的 bug 也是這樣處理：不要猜，先加觀測，讓它下次發生時留下足夠的資訊。

加 log 時不要印出手機、email、token 這些個資與憑證（Node 課第 19 課）。用會員 ID 這類不敏感的識別碼，需要時再到資料庫查。
💡 實務上：客服轉來的 bug，第一件事是補齊能重現的資訊
工作中最常見的 bug 回報長這樣：「有客人說點數沒加到」，沒有時間、沒有訂單編號。先回頭要齊這幾樣：會員 ID 或訂單編號、發生的時間（含時區）、App 或瀏覽器版本、畫面上的錯誤訊息或 request ID，有了這些才能去 log 裡撈到那一筆。所以錯誤畫面上顯示 request ID、讓客服能複製給工程師，是很值得的小投資。重現之後，先把它寫成一個會失敗的測試再動手修，修完測試轉綠就是「修好了」的證據，也能直接放進 PR 給 reviewer 看。資深工程師同時會問「影響多少人、從什麼時候開始」，這決定它是今天要修還是排進下個迭代。

假設篩出來的都是這種慢的未命中，資料就支持了假設，但它還沒在你面前發生過。金卡 bug 的不受控因素是交錯順序，下一節要做的就是把它變成參數。

偶爾才發生：怎麼讓交錯順序每次都一樣？

上一節把時間變成參數；金卡 bug 需要控制的是交錯順序，也就是兩個同時進行的流程，各自的步驟誰先誰後。這一類 bug 有個名字：非確定性（nondeterministic）的 bug，同樣的輸入有時成功、有時失敗；出現在測試裡時常叫 flaky。原因幾乎都是三種：時間（跨日、月底、逾時）、並發的交錯順序、亂數。控制的方法都一樣，把不受控的因素變成參數：時間用注入的 now()（上一節做過），亂數用注入的 random()，交錯順序接下來用 deferred 處理。

還有一種特別讓人抓狂的叫 heisenbug：一加上 log 或用除錯器停下來，bug 就消失了。它通常跟時間或交錯有關：印 log 讓某一步慢了一點，交錯順序就變了，原本會撞在一起的兩個步驟錯開了。週五晚上那十幾行 console.log，有可能讓金卡 bug 更難出現，卻不代表它被修好。

要控制交錯，得先知道交錯發生在哪裡。在 JavaScript 裡，一個 async 函式碰到 await 就會暫停，等那個 Promise 完成才繼續；其他請求就是在這個空檔插進來的。平常 Promise 什麼時候完成，由資料庫或網路決定，所以順序不受控。deferred 是一個把 resolve 函式拿到外面的 Promise：它建立之後會一直等著，直到你自己呼叫 resolve。用它代替資料庫查詢，「資料庫什麼時候回來、回來什麼值」就由測試決定了。

先在最簡單的形狀上試：PostgreSQL 課第 19 課的 lost update。兩個集點請求都先讀到 3 點，各自加 1 寫回。它和金卡 bug 是同一個形狀：讀、等待、用讀到的值寫回，等待的期間別人改了資料。執行後看最後印出的點數：

這個範例每次執行都會得到 4，沒有 setTimeout、沒有「多跑幾次看看」。關鍵在兩個 resolve 都在任何一次寫回之前呼叫，兩個請求因此都讀到 3。換個順序，例如等 first 寫回之後才 b.resolve，就會得到正確的 5，你可以自己改改看。

金卡 bug 的重現用的是同一招，只是把集點換成快取。依時間線安排：get 開始載入，載入用的是 deferred，先不讓它完成；接著升級、呼叫 invalidate；然後才讓第一次的載入帶著「銀卡」完成，它就把銀卡寫進快取；最後再 get 一次，拿到的是銀卡。這一串在練習 4 會寫成程式，每次跑都失敗。修法是讓快取認得「這次載入開始之後，資料已經被改過了」：每個 key 記一個版本號，invalidate 時加 1，載入完成時版本沒變才寫回。

有了每次都會失敗的測試，修 bug 的順序就固定了：

  1. 先寫一個會失敗的測試，確認它失敗的原因跟使用者看到的一樣。如果測試因為別的原因失敗，它證明不了你的修正有效。
  2. 再修，看著同一個測試變成通過。這就是「修好了」的證據，不再是「這兩天沒人回報」。
  3. 留下這個測試。之後有人重構快取、改了寫回的時機，這個 bug 如果又回來，測試會先擋下。原本正常、被新改動弄壞的情況叫回歸（regression），留下來的這種測試就叫回歸測試。
用 sleep(100) 讓順序「通常」對的測試，本身就是 flaky：機器忙的時候順序就變了。用 deferred 控制順序的測試不依賴速度，在 CI 上跑一千次結果都一樣。

到這裡金卡 bug 有了根因、測試和修正。週一的會議上還有人問：上個月沒有人回報過，這個 bug 是一直都在，還是哪次改動帶進來的？這決定受影響的會員要從哪天算起。版本那麼多，一個一個試不完，下一節處理這種「範圍太大」的問題。

範圍太大、一個一個試不完：怎麼每次排除一半？

回頭看第一節的記錄表，三個實驗其實都在用同一個技巧：把可能出錯的地方切成兩邊，用一個實驗判斷問題在哪一邊。用 curl 直接打 API，是把系統切成「App」和「伺服器」；查資料庫，是把伺服器切成「資料庫」和「API 到資料庫之間」。SRE 書把這種「分而治之」列為通用的技巧。

每次都切在正中間，就是二分法（bisection）。它的威力在次數：每個實驗排除一半，1,000 個可能最多 10 次就找得到，因為 210 = 1,024；逐一試則可能要試將近 1,000 次。執行後比較兩種做法在不同規模下的次數：

規模每大 10 倍，逐一測的次數跟著大 10 倍，二分法只多 3、4 次。可以二分的東西有三種：元件與設定、版本、輸入。元件第一節做過了：請求經過 nginx → API → Redis → PostgreSQL，用 curl 直接打 API 就是略過前面那一層，看問題還在不在；設定也一樣，例如 12 個功能旗標，關掉一半看問題還在不在。下面看另外兩種。

版本：git bisect

週一的問題是：「兩週前的 v2.3.0 是好的，現在是壞的，中間有 120 個 commit。」部署課第 14 課教過 git bisect：它每次挑中間的 commit 讓你測，你回答 good（好）或 bad（壞），它就丟掉一半。120 個 commit 最多測 7 次。

每次手動切換、執行、回答很累。判斷好壞能寫成腳本的話，交給 git bisect run 自動跑。金卡 bug 現在剛好有一個每次都會失敗的測試，check.sh 只要執行它就好：

git bisect start
git bisect bad HEAD           # 現在是壞的
git bisect good v2.3.0        # 兩週前的版本是好的
git bisect run ./check.sh     # 每個 commit 都跑一次 check.sh，依結束碼判斷
git bisect reset              # 結束後回到原本的分支

git bisect run 用腳本的結束碼（exit code）判斷這個 commit 算什麼：0 是好，非 0 大多算壞，125 有特別的意思：這個 commit 無法測試，跳過，等於手動下 git bisect skip。完整的結束碼對照見課末「補充與查表」。

這裡有個陷阱：這個回歸測試是剛寫的，只存在最新的 commit 裡。bisect 切到舊 commit 時，測試檔跟著消失，每個 commit 都變成「無法測試」。所以測試檔和 check.sh 要放在 repo 外面，或保持未追蹤（git 切換 commit 時不會動未追蹤的檔案），讓每個被切到的 commit 都跑同一份測試。check.sh 的規則是：測試失敗 exit 1，測試通過 exit 0，程式建置不過或測試用到的 API 在那個版本還不存在時 exit 125。

即使這樣，跳過還是常有的事：某個 commit 剛好編譯不過，或那時候程式的寫法和測試對不上。跳過之後，git 改測附近的 commit。但如果被跳過的剛好緊鄰答案，git 就沒辦法確定第一個壞的是哪一個，只能告訴你「可能是這幾個之一」。這時候答案是一個範圍，不是一個 commit，你要自己再看這幾個 commit 的內容。練習 1 會實作這個邏輯（git 實際挑選替代 commit 的方式更複雜，練習用簡化的規則）。

bisect 能用的前提是「好」和「壞」判斷得出來而且穩定。金卡 bug 如果沒有上一節的測試，只能「在每個版本上操作幾次，看會不會出現銀卡」；它本來就是偶爾才出現，某個壞的版本剛好沒觸發，就會被判成好的，一次誤判就把你帶到錯的那一半。所以隨機出現的 bug，要先讓它穩定重現，再 bisect。真的沒辦法讓它穩定重現時，至少每個 commit 多測幾次再判定好壞。

輸入：把會失敗的輸入縮到最小

金卡 bug 的輸入只是一個會員 ID，沒有東西可以縮。但很多 bug 的觸發條件藏在一大份輸入裡，所以換一個同一週的例子：顧客回報「我這張訂單結帳一直失敗」，訂單有 30 個品項和客製選項。到底是哪個（或哪幾個）造成的？一個一個猜很慢，而且失敗原因可能是兩個選項的組合，單獨拿出來都不會失敗。

Zeller 與 Hildebrandt 2002 年發表的 delta debugging 就是在解決這件事，它的演算法叫 ddmin。目標是把會失敗的輸入自動縮到 1-minimal：結果還是會失敗，而且再拿掉其中任何一個單位就不會失敗。注意 1-minimal 不保證是「最小的」那一組，只保證裡面沒有多餘的單位。論文裡的例子：讓 Mozilla 當掉的 95 個使用者操作縮到 3 個，896 行的 HTML 縮到 1 行。

ddmin 的做法是先把輸入切成 2 塊，試「只留某一塊」和「拿掉某一塊」還會不會失敗；會的話就用比較小的那份繼續，不會的話切得更細（4 塊、8 塊⋯⋯），直到每塊只有一個單位。「只留某一塊」處理原因集中在一塊的情況，「拿掉某一塊」處理原因分散在好幾塊的情況。失敗原因只跟少數幾個單位有關時，它很快就能丟掉一大半。

如果只要 1-minimal，更簡單的作法也可以：從頭到尾逐一試著拿掉每個單位，拿掉後還會失敗就真的拿掉，不會失敗就留著。它最多呼叫大約 n 次，在 n 很大、失敗原因很少時比 ddmin 慢，但很好寫也很好懂。練習 2 兩種都可以。

💡 實務上：bisect 好不好用，取決於平常怎麼 commit
如果團隊習慣把兩週的工作壓成一個上千行的 commit，bisect 最後只會告訴你「是這一大包」，幫助不大；main 上的每個 commit 都能建置、測試都會過，bisect 才不會一路被跳過。另外要記得，很多問題根本不在 git 裡：改了環境變數、開了功能旗標、資料庫多了一批怪資料，這些要去看部署紀錄和設定變更紀錄。實務上的順序通常是先對時間線：「問題從幾點開始？那時候部署了什麼、改了什麼設定？」對不上時才拿 bisect 出來。

到這裡，金卡 bug 從客服的一句話走到了根因、測試、修正和「從哪個版本開始」。整個過程都可以慢慢來，因為它只影響一部分會員的畫面，不會越來越糟。下一節的情況就不是這樣了。

結帳正在失敗：錯誤從哪個服務開始？

週六中午，告警響了：結帳的錯誤率在升高，顧客看到 502。這次和金卡 bug 有兩個不同。第一，結帳請求要經過閘道、訂單服務、金流服務，再到銀行的 API，第一節那種手動一個元件一個元件排除的方式太慢。第二，顧客正在受影響，每多查一分鐘，就多一批人結帳失敗。這一節先處理第一個，下一節處理第二個。

手動排除太慢，就要靠系統平常就留下的資料。系統對外透露自身狀態的資料統稱 telemetry，常見的有三種，各自回答不同的問題：

  • 指標（metric）：隨時間變化的數字，例如每分鐘的請求量、錯誤率、耗時。它回答「有沒有出事、從幾點開始、哪個服務不正常」，告警就是盯著指標設的。
  • log：一件事一行的文字紀錄，例如第二節的 canonical log line。它回答「某一個請求發生了什麼」。
  • trace：一個請求經過所有服務的完整路徑與時間。它回答「這個請求的錯誤或時間花在哪一段」。

指標告訴我們結帳從幾點開始壞，接著打開一個失敗請求的 trace。先分清兩個詞：症狀（symptom）是我們看到的表象，這裡是顧客看到的 502；根因（root cause）是真正造成問題的地方。在分散式系統裡，兩者常常在不同的服務。部署課第 23 課教過，一個 trace 由很多 span 組成，每個 span 有自己的開始、結束時間和父 span。下面是一次失敗的結帳：

為什麼有四個 span 都標示錯誤？因為錯誤會沿著呼叫者一路往上傳：銀行 API 逾時，金流的 charge 拿到錯誤，於是它也失敗；訂單服務拿到金流的錯誤，也失敗；閘道最後回給顧客 502。閘道的 502 是症狀，從它開始查，只會一層一層往下追。

所以找根因的規則是：帶錯誤、而且所有後代都沒有錯誤的 span。後代都沒有錯誤，代表錯誤不是從底下傳上來的，是在這一層產生的。如果有好幾個符合（兩條分支各自出錯），先看最早開始的那個，後面的常常是它引起的。這張圖裡符合的只有 POST bank。

不是每次都有錯誤。結帳沒有失敗、只是變慢時，所有 span 都沒有錯誤可以找，這時要看自身耗時（self time）：一個 span 的總時間扣掉子 span 所涵蓋的時間，也就是「這一層自己在做事」的時間。為什麼不直接看總時間？因為父 span 的總時間包含所有子 span，根 span 的總時間永遠最長，但它的自身耗時可能很短，真正花時間的在下面某一層。

「子 span 所涵蓋的時間」有兩個地方容易算錯。第一，平行的子 span 會重疊：同時查價格和庫存，各花 150ms 和 135ms，但它們重疊在一起，只涵蓋 150ms；直接相加會扣掉太多，甚至算出負數，所以要先把區間合併。第二，子 span 可能超出父 span：父 span 已經回應了，背景的子工作（例如送通知）還在跑，超出的部分不屬於父 span 的時間，要先裁掉。結帳那個 trace 的子 span 都是一個接一個執行，沒有平行的，看不出重疊會出什麼問題；菜單 API 的 listMenu 同時查價格和庫存（前兩個子 span 平行），剛好可以示範。執行後比較兩行的數字：

💡 實務上：trace 要在出事之前就埋好
事故發生時才發現服務之間沒有傳遞 trace ID，就只能各看各的 log、靠時間戳硬對，非常痛苦。所以新服務上線前，資深工程師會確認：每個請求有沒有 trace ID、呼叫下游（HTTP、佇列訊息）時有沒有帶下去、log 裡有沒有印出同一個 ID。另一個常見的坑是取樣：為了省成本只保留一部分 trace，偏偏出事的那一筆沒被留下來；常見的做法是錯誤和特別慢的請求一定保留。咖啡店這種規模不一定要上完整的 tracing 平台，但「log 裡每一行都有 request ID」幾乎零成本，應該第一天就做。

這次結帳的 trace 很清楚：錯誤源頭是金流服務呼叫銀行 API 逾時。下一步的直覺是去查銀行 API 為什麼逾時，但顧客每分鐘都在結帳失敗，這個順序對嗎？

顧客正在受影響：先找原因，還是先止血？

答案是：先止血。使用者正在受影響時，優先順序就不一樣了。Google SRE Workbook 的〈Incident Response〉寫得很直接：先停止影響，再找根因。止血（mitigation）是先讓使用者不再受影響，問題本身可能還在，原因之後再查。

止血為什麼可以不等根因？Workbook 的說法是：止血只需要知道根因在哪裡，不需要知道它是什麼。例如知道「14:00 那次部署之後才開始」就能回滾，不需要先找到是哪一行程式碼。上一節的 trace 花幾分鐘就告訴你「在金流呼叫銀行 API 那一段」，這正是止血需要的資訊；「銀行為什麼逾時」可以等顧客不再受影響之後再查。

知道在哪裡之後，從下面這幾種手段挑一個對準它的：

止血手段適合的情況代價
回滾（rollback）問題在最近一次部署之後出現新功能暫時下線；有改 schema 時要確認舊版還能用新的 schema
關功能旗標（第 19 課）問題跟某個新功能有關幾乎沒有，所以新功能都應該包在旗標裡
導流（把流量從有問題的地方移開）只有某一區、某幾台、某個依賴有問題其他地方的負載變高
擴容流量真的超過容量花錢；如果瓶頸是資料庫，加 API 機器沒用
負載卸除、降級（第 11 課）撐不住全部的請求部分使用者被拒絕，或看到簡化的結果

選的方法是先對時間線：問題開始前有沒有部署或設定變更？有，就回滾或關掉旗標，這是最快、副作用最小的。這次的源頭在外部的銀行 API，咖啡店自己沒有東西可以回滾，就看表格的後三列：有其他可用的路徑就導流；沒有，就用第 11 課的斷路器和降級，讓結帳快速失敗並提示顧客稍後再試，不要讓每個請求都等到逾時、佔住連線，連菜單這些跟金流無關的功能也一起拖垮。

值班的人怎麼在半夜想起有哪些手段可用？靠 runbook：事先寫好的處理步驟，寫明某種告警出現時先看什麼、可以執行哪些止血動作、怎麼確認有效。照著做就能止血，不必現場想。

止血前後，記得保留證據。回滾前先記下壞掉的版本號；必要時留一台壞掉的機器，把它拉出負載平衡、不再接流量，留給之後調查；存下 log 和 heap snapshot。heap snapshot 是某個時間點記憶體裡所有物件的快照，查記憶體洩漏時要用它。重開機會讓問題暫時消失，也會讓證據跟著消失，週五晚上重開 Redis 就是這樣把舊值清掉的。

技術之外，多人一起處理事故時，最常見的問題是協調：三個人在不同頻道各查各的，兩個人同時改同一個設定，誰也不知道哪個改動有效，這正好違反了第一節的「一次只改一件事」。SRE Workbook 建議及早宣告事故，而且常常宣告。宣告事故是正式說「這是事故，進入事故流程」：開一個專用的頻道，所有討論和決定都在那裡。與其猶豫「這算不算事故」，不如先宣告，有了流程再說。宣告之後明確分工：

角色做什麼
事故指揮官（incident commander，IC）掌握全局、分派工作、做決定（例如「現在回滾」）。不親自修，還沒分派出去的角色都由 IC 負責。
操作負責人（operations lead，OL）實際執行止血與修復：回滾、關旗標、查 log。
溝通負責人（communications lead，CL）對外的窗口：用固定頻率（例如每 30 分鐘）向客服、主管、使用者更新狀態，即使沒有進展也說「還在處理」。

三個角色把「做決定」「動手改」「對外說明」分開：只有操作負責人在改系統，實驗結果才不會互相干擾；溝通負責人固定更新，客服才不必一直追問，工程師也不會被打斷。

💡 實務上：第一次值班接到告警，先開口再動手
新人最常犯的錯是收到告警後自己默默查了一個小時，等大家發現時影響已經擴大。比較好的做法是：先在事故頻道說「我看到結帳錯誤率升高，正在看」，然後依序確認影響範圍、最近的部署和設定變更、runbook 有沒有對應的止血步驟。拿不定主意就往上求援（escalate），找資深的人或主管一起看，這不丟臉，拖延才是。給客服和 PM 的更新要用他們聽得懂的話，例如「部分顧客結帳失敗，已回滾，預計 10 分鐘內恢復」，而不是「payment service 的 p99 飆高」。資深工程師在事故裡最常問的一句是：「我們現在能不能先回滾？」

止血之後，結帳錯誤率回到平常的水準。事故到這裡還沒結束：根因還在，同樣的事下次還會發生。

事故結束之後：怎麼讓同一個問題不再回來？

止血解決的是「現在」，接下來要處理「下一次」。事故結束後寫事後檢討（postmortem）：時間線、影響範圍、根因、哪些地方做得好、哪些靠運氣，以及有負責人和期限的改善行動。這時候才是回頭查「銀行 API 為什麼逾時、我們的逾時與重試設定是否合理」的時機，查的方法就是這一課前半段的迴圈。

檢討的原則是不究責（blameless）：問「系統為什麼讓這個錯誤有機會發生」，不問「是誰的錯」。找戰犯的結果是下一次大家隱瞞細節，組織就學不到東西。範本和流程見部署課第 25 課與 PostgreSQL 課第 39 課。

不管是金卡 bug 還是結帳事故，修好之後都要補上三樣東西，各自擋住不同的「下一次」：

  • 回歸測試：同樣的 bug 不會再回來。金卡 bug 的那個 deferred 測試就是。
  • 告警：下次在使用者回報之前就知道。金卡 bug 是客服先發現的，結帳事故至少有告警；可以再補一個「銀行 API 逾時比例」的告警，比結帳錯誤率更早響。
  • runbook：值班的人照著做就能止血。把這次「銀行 API 逾時時怎麼降級、怎麼確認恢復」寫下來。

另外，在正式環境做任何實驗之前，先想清楚怎麼還原；能在 staging 或用一台機器做的，就不要動全部。週五晚上重開 Redis，如果當時是在流量高峰，所有請求同時未命中、一起打到資料庫，就會從一個顯示錯誤變成一場事故。

補充與查表

SRE 書的除錯流程：問題回報 → 分級（triage）→ 檢查 → 診斷 → 測試與處置。分級判斷有多嚴重；書裡明白寫著，嚴重的問題「先止血」是第一優先，原因之後再找。

125這個 commit 無法測試，跳過（等於 git bisect skip）
其他（例如 exit(-1) 會變成 255）中止整個 bisect

看指標的兩個檢查清單：看服務用 RED（Rate 請求量、Errors 錯誤率、Duration 耗時），看資源（CPU、記憶體、連線池、磁碟）用 USE（Utilization 使用率、Saturation 飽和度，也就是排隊的量、Errors 錯誤）。先用 RED 找出哪個服務不正常，再用 USE 看它的哪個資源不夠。

練習

練習 1：寫 bisect(versions, test)，模擬帶跳過的 git bisect。versions[0] 已知是好的、最後一個已知是壞的，兩者都不要測。

  • 維持 lo（最後已知好的索引，一開始 0）和 hi（第一個已知壞的索引，一開始最後一個），hi - lo > 1 時繼續。
  • 每次先算 mid = Math.floor((lo + hi) / 2)。mid 已經被跳過時，依 mid+1、mid-1、mid+2、mid-2⋯⋯ 的順序，找第一個在 lo 和 hi 之間（不含兩端）、還沒被跳過的版本來測。
  • test 回傳 'good' 時更新 lo，'bad' 時更新 hi，'skip' 時記下這個版本不能再測。
  • 正常結束：firstBad = versions[hi]、candidates = [versions[hi]]。找不到可測的版本而停止：firstBad = null、candidates 是 lo 之後到 hi（含）的所有版本，依原順序。
  • tested 是依序呼叫過 test 的版本（包含回傳 skip 的）。

練習 2：寫 minimizeFailing(input, fails)，把會失敗的輸入縮到 1-minimal。

  • 回傳 input 的一個子序列（元素保持原本的先後順序），fails(結果) 仍然是 true，而且拿掉其中任何一個元素後 fails 都是 false。
  • fails 的呼叫次數不能超過 input.length² + 10（擋住列舉所有子集合的暴力法）。可以實作 ddmin，也可以用逐一嘗試移除的方式。
  • 一開始 fails(input) 就是 false 時丟出 Error：沒有可以縮小的東西。不要修改 input。

可以假設失敗條件是「單調」的：一個集合會失敗，加上更多元素也還是會失敗。

練習 3：寫 rootCause(spans)，從一個 trace 的所有 span 找出根因。spans 沒有特定順序，parentId 是 null 的是根 span。

  • 有任何帶 error 的 span 時：候選是「帶 error、而且所有後代（子、孫⋯⋯）都沒有 error」的 span。取 startMs 最早的；相同時取 spanId 字串比較較小的。reason 是 'error'。
  • 沒有錯誤時：算每個 span 的自身耗時 = (endMs - startMs) 減去「直接子 span 的區間，先裁切到父 span 的範圍內、再合併重疊部分」的總長度。取自身耗時最大的；相同時取 startMs 早的，再相同取 spanId 較小的。reason 是 'slow'。
  • 兩種情況都要回傳那個 span 的 selfMs（自身耗時）。不要修改傳入的 spans。

練習 4：開頭「金卡顯示銀卡」的 bug。起始程式有一個有 bug 的會員資料快取 createProfileCache(load)：get 未命中時 await load(key) 再寫回快取；invalidate 直接刪除。還有三個工具：deferred()、makeLoader()（每次 load 都放進 pending，由你決定何時、用什麼值完成）、flush()（讓已經可以往下跑的 Promise 都跑完）。

  1. 寫 reproduce(factory)：用 factory(load) 建立快取，安排「get 開始載入 → 會員升級、invalidate → 第一次的 load 才帶著舊資料（'銀卡'）完成 → 再 get 一次（這次載入的話回傳 '金卡'）」，回傳第二次 get 是否拿到舊資料。true 代表重現了 bug。不能用 setTimeout 或任何真實時間。
  2. 寫 createProfileCacheFixed(load)：每個 key 一個版本號，invalidate 時加 1；get 開始載入前記下版本，載入完成時版本沒變才寫回快取（不管有沒有寫回，都回傳載入的值）。命中時不呼叫 load。

練習 5：錯誤率從 14:02 開始飆升，14:00 剛部署過新版本。你第一步做什麼？

✓ b。時間點吻合，問題「大概在哪裡」已經知道了，止血不需要知道是哪一行。a 讓使用者在你找原因的期間一直受影響；c 在錯誤率飆升時白白延長影響；d 不針對已知的改動，還會清掉記憶體裡的證據，新版本也還在。

練習 6：一個測試偶爾失敗。你加上 console.log 想看清楚，結果它跑一百次都通過了。這代表什麼？

✓ c。加 log 改變的是時間，不是邏輯，bug 還在（a 錯），換一台比較忙的機器就會再出現。b 和 d 都是忽略訊號：flaky 的測試常常在告訴你程式真的有競態。把順序變成參數，就能讓它每次都失敗，再修。

練習 7：監控圖上，CPU 使用率和錯誤率在同一分鐘一起升高。同事說：「CPU 太高造成錯誤，加機器吧。」你怎麼回應？

✓ a。兩個指標一起動只是相關。b 和 c 都直接選了一個因果方向，沒有證據；如果真正的原因是重試風暴，加機器只會讓更多重試打到已經很慢的依賴。SRE 書的例子是封包遺失和硬碟故障同時出現，共同原因是停電。

練習 8：結帳失敗的事故中，三位工程師各自在不同的頻道查問題，其中兩位同時在調整同一個設定；客服一直問「什麼時候會好」，沒有人回答。最缺的是什麼？

✓ d。問題是協調，不是人力或資訊：兩個人同時改同一個設定，會讓實驗結果互相干擾，誰也不知道哪個改動有效。a 讓混亂更大；b 不能解決沒人做決定、沒人對外說明；c 太晚了，影響正在發生。

常見錯誤

  • 一次改很多東西：好了不知道是哪個修好的，壞了不知道是哪個造成的。一次改一件事，每次都記錄結果。
  • 沒有記錄假設與實驗：繞回做過的實驗，交接時別人只能從頭來。用一張表記下時間、假設、實驗、結果。
  • 追無關的症狀：log 裡平常就有的錯誤，不一定跟這次有關。先確認這個異常在問題開始前是不是也存在。
  • 重現不了就猜：猜中的機率很低。先縮小環境差異，把時間、亂數、順序變成參數，或加上 canonical log line 等它下次發生。
  • 只修症狀就結案：重開機、清快取讓問題暫時消失，根因還在。止血之後要繼續找根因，並寫進事後檢討。
  • 事故中先找根因再止血：使用者在你找的期間一直受影響。先回滾、關旗標、導流或卸載，保留證據，再查。
  • bisect 時把無法測試的版本當成好或壞：會把你帶到錯的那一半。編譯不過或測試不存在時用 skip（run 腳本回傳 125）。
  • 用 sleep 重現競態：機器一忙順序就變了，測試本身變成 flaky。用 deferred 明確控制每一步何時完成。
  • 事後檢討找戰犯：大家開始隱瞞細節，組織學不到東西。問系統為什麼讓錯誤有機會發生。
  • 修好之後沒有留下回歸測試與告警：同樣的 bug 會回來，而且下次還是使用者先發現。
  • 在正式環境除錯時把個資印進 log：log 會被很多人看到、保存很久。用 ID，不要印手機、email、token。

小結

  • 除錯是假設—驗證的迴圈：觀察、列出假設、設計能排除假設的實驗、記錄結果（包含負面結果）。先問最近改了什麼，先想常見的原因，一次只改一件事，卡住 30 分鐘就找人講。金卡 bug 三個實驗就縮到快取的舊值寫回。
  • 先穩定重現再修：比對版本、設定、資料、時間、並發的差異，把不受控的因素變成參數；重現不了就先加觀測，例如每個請求一行的 canonical log line。
  • 非確定性的 bug：把時間、亂數、交錯順序變成參數，用 deferred 讓它每次都失敗；先寫失敗的測試，再修，最後留下它當回歸測試。
  • 二分法：元件、設定、版本、輸入都能每次排除一半。git bisect run 的結束碼 0 是好、1～127（125 除外）是壞、125 跳過；被跳過的版本緊鄰答案時，結果是一個範圍；判斷好壞要穩定才能 bisect。輸入用 ddmin 或逐一移除縮到 1-minimal。
  • 從 telemetry 找根因：指標看範圍與開始時間（相關不等於因果），trace 看錯誤在哪一段。有錯誤時找「帶錯誤、後代都沒有錯誤」的 span；只是慢時看自身耗時，子 span 要先裁切、再合併重疊。
  • 線上事故：止血只需要知道根因在哪裡；先止血（回滾、關旗標、導流、擴容、卸載）並保留證據；及早宣告，分出指揮、操作、溝通三個角色並固定頻率更新；事後不究責地檢討，補上回歸測試、告警和 runbook。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 9：時段名額的決策矩陣算出來，條件更新 46 分、Redis 鎖 45 分；把「維運成本」的權重降 20%，Redis 鎖就變成第一。設計文件的結論該怎麼寫？

✓ 分數是 1～5 的主觀判斷，46 對 45 就是平手；敏感度檢查顯示贏家會換，代表結論其實是「維運成本有多重要」這個判斷。寫出來，審查才會討論那個權重，而不是吵總分；能量測的就做原型補上事實。a 是假精確：權重本身就是判斷，換個合理的權重答案就變了。（第 18 課）

練習 10：訂單清單 API 的文件寫著「不保證順序」，但回應一直是新到舊排列。同事為了效能改成未完成的訂單排前面，OpenAPI 比對沒有任何差異。這個改動怎麼看？

✓ Hyrum 定律：使用者夠多時，所有可觀察的行為都會被依賴，不管文件有沒有寫。依賴「第一筆是最新的」的程式不會報錯，只會默默顯示錯的訂單。c 最多人選：OpenAPI 比對只抓結構，排序、單位、預設值這類語意上的改變它看不到，要靠契約測試和問清楚誰在讀。（第 19 課）

練習 11：兩台 POS 同時退同一筆訂單，金流退了兩次款。單獨測試時這段程式完全正確。最小而正確的修法是？

async function refundOrder(orderId: number) {
  const order = await db.one('SELECT status, charge_id FROM orders WHERE id = $1', [orderId])
  if (order.status !== 'paid') return 'not_refundable'
  await db.query("UPDATE orders SET status = 'refunded' WHERE id = $1", [orderId])
  await payments.refund(order.charge_id)
  return 'ok'
}

✓ 這是先讀再寫：兩個請求都在對方更新之前讀到 'paid'，都通過檢查。讓檢查和寫入成為同一個原子操作，只有一個請求更新得到那一列，另一個拿到 0 列就不退款。a 最多人選：預設的 READ COMMITTED 下，交易裡的普通 SELECT 擋不住別人，讀和寫之間的空檔還在。d 只擋得住同一個畫面連按，擋不住兩台 POS。（第 20 課）

練習 12：這一季只夠還一筆技術債。訂單 service 每週都要改，每次多花 3 小時，整理要 16 小時；月報表 SQL 最難讀，每次改多花 4 小時，但一年只改 3 次；訂單表沒有唯一限制，重複下單只靠程式先查再寫擋著，目前沒出過事，補上要 6 小時。先還哪一筆？

✓ 會造成事故的債不看回本，排最前面：先查再寫在並發時擋不住重複，重複訂單寫進資料庫就要人工對帳退款，6 小時就能消除。a 最多人選，用利息排序是對的方法，但它排的是「讓團隊變慢」的債，風險要另外看；訂單 service 排第二。b 的利息每月只有 1 小時，48 小時要 4 年才回本。（第 20 課）

練習 14：週年慶開賣，訂單量是平常的 5 倍，資料庫 CPU 100%、結帳開始逾時；過去兩天沒有任何部署或設定變更。你第一步做什麼？

✓ 止血要對準瓶頸：瓶頸是資料庫，就減少打到資料庫的工作，犧牲推薦區塊、拒絕一部分請求，保住結帳。a 最多人選：API 機器越多，同時打到資料庫的查詢越多，瓶頸沒變。c 不針對原因，這兩天根本沒有改動；d 是找根因，修好之前顧客一直結帳失敗，留到止血之後。（第 21 課）
