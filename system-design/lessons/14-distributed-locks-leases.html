階段 3：可靠性：失敗是常態 · 第 14 課

分散式鎖、租約與 fencing token

咖啡店的 API 跑在三台伺服器上。每天 03:00 要產生前一天的營業報表、寄給 200 家門市的店長。上線第一天，店長們收到三封一模一樣的信：三台伺服器的排程都在 03:00 醒來，各做了一次。有人加了一把 Redis 鎖，信變成一封。一個月後，報表內容偶爾是錯的：某台伺服器做到一半停了 40 秒，醒來時鎖早就換人拿了，它卻照樣把舊的結果寫了進去。

這一課從頭到尾處理這份報表：讓三台伺服器每天只做一次報表，而且就算某一台停住 40 秒、醒來還以為自己拿著鎖，它的舊結果也寫不進去。學完之後，你能判斷一個問題該交給資料庫約束還是真的需要鎖；能寫出取得、釋放、續約都正確的租約鎖；能說明為什麼「寫入前先檢查租約還在」擋不住過時的寫入，並用 fencing token 讓報表儲存自己擋；能讓三台伺服器的排程只由一台負責；也能在 code review 看到「加一把 Redis 鎖」時，說出該選哪一種做法、上線後要看哪些數字。

第一輪只要記住：
  • 能用唯一約束、條件更新解決的，就不要用分散式鎖。讓工作本身冪等，鎖只用來減少重複的工作。
  • 分散式鎖一定是有期限的租約；釋放和續約都要「值還是我的才做」，而且比對和動作是同一個原子操作。
  • 持有者可能停住而不自知，所以只靠鎖保證不了「同一時間只有一個人在寫」。要正確，就讓資源用遞增的 fencing token 拒絕過時的寫入。
  • 量時間間隔、算租約剩多久，一律用單調時鐘。
這課的路線：
  1. 報表重寄了，要加鎖嗎：什麼是分散式鎖，為什麼先讓工作冪等，鎖是為了效率還是正確性（開場問題的最小答案）。
  2. 第一把鎖怎麼做：持有者當機時為什麼需要租約；用 SET NX PX 取得、值相符才刪、續約；已經有 PostgreSQL 時用 advisory lock。
  3. 拿著鎖為什麼還會蓋掉報表：程序暫停、時鐘跳動、主從切換；fencing token 怎麼讓報表儲存自己擋住過時的寫入。
  4. 讓一台負責所有排程：leader election 怎麼續約、什麼時候退位；租約剩多久要用哪一種時鐘量。
  5. 有人提議用 Redlock：它的爭議、實務上怎麼選，以及上線後看哪些數字。
這課會用到：
  • PostgreSQL 課第 19 課的 lost update 與條件更新：兩人同時讀完再寫會蓋掉對方；UPDATE … WHERE stock > 0 把判斷和寫入放進同一個原子操作。
  • PostgreSQL 課第 33 課的 advisory lock 與 SKIP LOCKED：用一個數字當鎖名、交易結束自動釋放；多個 worker 各拿各的工作，不會拿到同一筆。
  • NestJS 課第 19 課的 Redis 指令：SET 寫值、GET 讀值、DEL 刪除，key 可以帶 TTL 到期自動消失。
  • 第 9 課的冪等：同一件事做一次和做很多次結果相同，常用唯一約束擋掉第二次。

報表重寄了：第一個念頭是加鎖，真的需要嗎？

三封信的問題，最直覺的修法是「加一把鎖，拿到的那台才做」。先把這把鎖是什麼講清楚。在同一台機器上，多段程式要輪流使用同一份資料時，可以用程式語言或作業系統提供的鎖：鎖就放在這台機器的記憶體裡，誰拿著、誰在等，都在同一個地方記錄。咖啡店的三台伺服器各有各的記憶體，api-1 記憶體裡的鎖，api-2 看不到。

所以要把鎖放到三台都連得到的地方，例如 Redis 或資料庫，由它記錄「現在誰拿著」。這種讓不同機器上的程序輪流、互斥地使用同一個資源的機制，叫分散式鎖（distributed lock）。它比單機的鎖難得多：拿著鎖的程序和記錄鎖的服務是兩台機器，中間隔著網路。持有者可能當機、可能被暫停、也可能只是網路斷了，鎖服務看到的都是同一件事：「它沒有消息了」。鎖服務分辨不出是哪一種，這一課後面每個問題都從這裡來。

既然分散式鎖本身是一個會壞的元件，加之前先問：能不能不用？回到報表。三封信的根源是「寄報表」做三次就有三封。如果寄之前，先在資料庫寫一筆「2026-10-30 的報表已寄出」，並在報表日期上加唯一約束（第 9 課），三台同時去寫，只有一台寫得進去，另外兩台的 INSERT 直接失敗、不寄。這個檢查和寫入是資料庫的同一個原子操作，中間沒有空檔可以讓兩台都通過。就算之後加的鎖失效了，最後這一道約束也不會讓店長收到第二封。

唯一約束擋得住重寄，卻擋不住開場的第二個事故：舊報表蓋掉新報表。要判斷一把鎖該做到多可靠，Martin Kleppmann 在〈How to do distributed locking〉（2016-02-08）建議先問：這把鎖是為了效率，還是為了正確性？

  • 效率鎖：鎖失效只是重複做事。例如報表多算一次、同一張圖多縮一次。偶爾失效可以接受，成本低的做法就夠了。
  • 正確性鎖：鎖失效會弄壞資料。例如兩個程序同時改同一份帳、覆蓋對方的結果。這種鎖不能只靠鎖本身，要讓被保護的資源也參與檢查。

三封信原本是正確性問題（店長收到重複的信），加上「已寄出」的唯一紀錄後，鎖失效只會讓第二台在 INSERT 時失敗，就變回效率問題。報表被舊結果蓋掉則是正確性問題，它的修法也是同一個思路：寫入報表時，由資料庫檢查「這次寫入是不是最新一任持有者」，過時的就拒絕。這就是後面的 fencing token。資深工程師的習慣可以濃縮成一句：讓工作本身冪等，鎖只用來減少浪費。

💡 實務上：在 code review 看到「加一把 Redis 鎖」，先問三個問題
常見的 PR 是：API 擴成三台後排程重複跑，或兩個人同時按「結帳」扣出負庫存，於是有人包一層 Redis 鎖。先問：鎖失效時最壞會怎樣？（多寄一封信，還是帳對不起來）；能不能改成唯一約束或條件更新？扣庫存、重複付款幾乎都可以，而且比鎖可靠；真的要鎖，失效時有誰會知道？有沒有日誌或告警。三個問題答完，常常會發現根本不需要新增一個 Redis；報表這種情況，答案是先補上「已寄出」的唯一紀錄，鎖只是省工。

那報表還需要鎖嗎？需要，但目的變了：產生報表要把前一天的訂單全部撈出來算一遍，三台各算一次，只有一份會被用上。鎖讓另外兩台一開始就跳過，省下兩份重複的工作。其他常見的「看起來要鎖」的問題，例如付款只能一次、扣庫存不能扣成負數，不用鎖的解法整理在課末的〈補充與查表〉。接下來就為這個目的做第一把鎖。

第一把鎖：持有者當機了，鎖要怎麼放掉？

最直覺的寫法是：在 Redis 設一個 key lock:daily-report，設得成功的那台去做報表，做完把 key 刪掉。Redis 的 SET 加上 NX 選項，意思是「key 不存在才設定」，三台在 03:00 同時送出，只有一台會成功，另外兩台得到失敗、跳過今天的工作。

問題出在「做完把 key 刪掉」。如果拿到鎖的 api-1 在做報表時當機，它永遠不會執行刪除，這個 key 就一直留在 Redis 裡。隔天 03:00，三台都設不成功，報表從此不再產生，而且沒有人會收到錯誤。上一節說過，鎖服務分辨不出持有者是當機還是做得慢，所以它也不能自己判斷「該放掉了」。

解法是讓鎖本身有期限：取得時就說好最多借多久，時間到了，就算持有者沒有釋放，鎖服務也自動放掉。這種有期限的鎖叫租約（lease），跟租房子一樣，租期到了沒續約就收回。分散式鎖幾乎一定是租約。代價是持有者必須在期限內做完；做不完，就要在到期前向鎖服務把期限延長，這個動作叫續約（renew）。因為續約通常是固定間隔送出，像在報告「我還活著」，有些工具也把它叫 heartbeat。

Redis 文件〈Distributed Locks with Redis〉給的單機寫法：

SET lock:daily-report 7f3a9c…（隨機值） NX PX 30000
  • NX：key 不存在才設定，所以同一時間只有一個人設得成功。
  • PX 30000：30,000 毫秒後自動過期，這就是租約的期限。
  • 值是擁有者 token：每次取得都產生一個唯一的隨機值，證明「這把鎖是我這一次拿的」。文件要求它在所有客戶端、所有請求之間唯一。下一節會看到它為什麼必要。

租約你其實已經用過：第 12 課佇列的 visibility timeout，就是「這則訊息租給你 30 秒，沒有 ack 就交給別人」；第 5 課的快取 lease 也是同一個想法。它們解決的都是「拿走東西的人可能消失」。

有了期限，鎖不會永遠卡住了。但期限也帶來一個新情況：持有者做完要釋放時，手上那把鎖可能已經過期、被別人拿走了。這時直接刪掉 key，刪的是誰的鎖？

做完要釋放：怎麼不刪到別人的鎖？

下面用一個迷你 Redis 重現這個情況：api-1 拿到 30 秒的租約，卻花了 40 秒，期間租約過期、被 api-2 拿走；api-1 做完照樣釋放，接著 api-3 也來搶。程式會跑兩輪，一輪用 DEL 釋放，一輪用「值相符才刪」。執行後看兩輪的最後一行：api-3 能不能拿到鎖。

用 DEL 時，api-1 刪掉的是 api-2 的鎖，api-3 接著拿到，api-2 和 api-3 同時以為自己拿著鎖。改成「值相符才刪」，api-1 發現 key 裡的值已經不是自己的 api-1#7f3a，就不刪，api-3 也拿不到。這就是上一節擁有者 token 的用途：它讓釋放的人能確認「這把還是我拿的那一把」。

「值相符才刪」還有一個條件：比對和刪除必須是同一個原子操作。如果先送 GET 比對、再送 DEL 刪除，這是兩個指令，中間隔著一次網路來回；鎖可能就在這段空檔裡過期、被別人拿走，你的 DEL 一樣刪到別人的。Redis 在執行一段 Lua 腳本時，不會穿插其他客戶端的指令，所以 Redis 文件的做法是把比對和刪除寫進同一段腳本：

-- Lua 腳本在 Redis 裡是原子執行的
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end

新版 Redis 另外有一個指令直接做這件事，版本與寫法見課末〈補充與查表〉。續約也是同一個道理：值還是自己的，才延長期限，一樣用 Lua 比對後再 PEXPIRE；否則你會替別人的鎖續約。拿不到鎖的那一方，Redis 文件建議隨機延遲後再試，跟第 8 課的 jitter 同一個道理：大家同時重試，只會一起再撞一次。

如果咖啡店已經有 PostgreSQL，報表這把鎖常常不必為它多架一個 Redis。PostgreSQL 課第 33 課的 advisory lock 可以直接用：SELECT pg_try_advisory_xact_lock(20261030) 用一個數字當鎖名，拿不到立刻回傳 false，拿到的話，交易結束時自動釋放。它的生命跟著交易走，交易所在的連線斷掉、交易結束，鎖就放掉，所以不需要 TTL，也不會有「持有者當機、鎖卡住」的問題。另一種不用交易包住、要自己釋放的寫法，見課末。

💡 實務上：TTL 照實際耗時來設，取得和釋放包成一個共用函式
TTL 太短，工作還沒做完鎖就換人；太長，持有者當機後大家要乾等很久。做法是先量這個工作平常要跑多久，TTL 設成明顯比它長；會跑好幾分鐘的工作改用續約，不要把 TTL 一口氣設成一小時。取得、續約、「值相符才刪」最好包成專案裡唯一的一個函式或模組，不要讓每個人各自手寫 SET NX 和 DEL，經典的「刪到別人的鎖」通常就出在某個複製貼上的版本。也要先決定拿不到鎖時怎麼辦：報表這類排程通常直接跳過並記一筆日誌，使用者正在等的請求則回一個明確的錯誤，不要無限重試。

到這裡，三封信變成一封，鎖不會永遠卡住，也不會被刪到別人的。可是開場的第二個事故還在：報表偶爾被舊的結果蓋掉。api-1 明明照規則拿鎖、照規則釋放，為什麼還會寫進去？

拿著鎖，為什麼還會蓋掉別人的報表？

租約解決了「持有者當機、永遠鎖住」，卻帶來另一種情況：持有者沒死，只是停住了。程式停住一段時間，自己卻不知道，叫程序暫停（process pause）。從程式的角度看，它只是從一行執行到下一行；中間實際過了 40 秒，它完全沒感覺。常見的原因：

  • 垃圾回收（GC）的 stop-the-world 暫停：執行環境回收記憶體時把整個程式停住，Kleppmann 的文章提到有時長達好幾分鐘。
  • 虛擬機或容器被暫停、遷移；筆電闔上；作業系統把記憶體換到磁碟。
  • 網路延遲：請求已經送出，卻在路上卡了很久才到（文章引用 GitHub 一次約 90 秒的封包延遲）。

逐步看一次開場的事故。報表程序 api-1 拿到 30 秒的租約，產生報表要 10 秒，看起來綽綽有餘；它也很謹慎，寫入前先檢查租約還在：

時間api-1鎖服務api-2報表儲存
0:00取得租約持有者 api-1，到 0:30（空）
0:05檢查租約：還在 ✓持有者 api-1（空）
0:05GC 暫停 40 秒…持有者 api-1（空）
0:30（暫停中）到期，釋放（空）
0:31（暫停中）持有者 api-2取得租約、寫入報表api-2 的報表
0:45醒來，直接寫入持有者 api-2api-1 的舊報表 ✗

重點在步驟 2 和 3：「寫入前先檢查租約還在」沒有用。暫停可以發生在檢查之後、寫入之前的任何一刻，把檢查移得再靠近寫入也一樣，兩行程式之間永遠有空檔。把 TTL 設長一點，也只是讓機率變小：暫停可能比任何你選的 TTL 都長。注意鎖服務在這裡沒有做錯任何事，0:30 放掉鎖正是租約該做的，它沒辦法分辨 api-1 是當機還是暫停。

暫停不是唯一的原因，還有兩種情況會讓兩個程序同時拿到鎖。第一種是時鐘跳動：租約什麼時候到期，是 Redis 伺服器看自己的時間決定的。Redis 判斷 key 有沒有過期，看的是伺服器的系統時間，而系統時間是可以被調整的（Redis 文件明白寫著它不是單調時鐘，兩種時鐘的差別後面會講）。伺服器的時間被往前調，鎖就會提早過期，持有者還在做，別人已經拿到了。第二種是主從切換：Redis 的複寫是非同步的，api-1 在 master 拿到鎖，master 還沒把這個 key 傳給 replica 就掛了，replica 升為 master，上面沒有這把鎖，api-2 就能再拿一次（Redis 文件的例子）。這跟PostgreSQL 課第 37 課非同步複寫切換時會遺失最後幾筆交易，是同一件事。

三種原因加起來的結論：只靠鎖，沒有辦法保證「同一時間只有一個人在寫」。持有者自己判斷不了，鎖服務也攔不住一個已經醒來、正要寫入的程序。能攔住它的，只剩被保護的資源自己：報表儲存在收到寫入的那一刻，判斷這個寫入是不是過時的。

怎麼讓報表儲存自己擋住過時的寫入？

報表儲存要判斷「過時」，就需要一個可以比大小的依據。做法叫 fencing token：fence 是柵欄，用一個數字把過時的持有者擋在外面。鎖服務每次把鎖交給一個新的持有者，就給它一個比上次大的數字；持有者寫入時把這個數字一起帶上；資源記住自己看過最大的數字，拒絕比它小的。數字越大，代表越晚拿到鎖，也就是越新的一任。Kleppmann 的例子：

關鍵是檢查發生在資源那一端，而且和寫入是同一個原子操作。上一節的「寫入前先檢查租約」失敗，是因為檢查在持有者這邊、寫入在資源那邊，中間有空檔。現在兩件事在同一個地方、同一個操作裡完成，api-1 不管在哪一刻被暫停，醒來帶著 33 去寫，都會被擋下來。

接下來的問題是：誰發這個遞增的數字？前面 Redis 的擁有者 token 是隨機值，只能證明「是不是我」，不能比大小，所以 SET NX 本身給不了 fencing token。報表的資料本來就在 PostgreSQL，可以直接用一張鎖表當鎖服務：locks(name, owner, token, expires_at)，用條件更新取得租約，每取得一次 token 就加 1。到期的判斷用資料庫自己的 now()，三台伺服器都問同一個時鐘，不會因為各自的時間不同而判斷不一致：

UPDATE locks
SET owner = $1, token = token + 1, expires_at = now() + interval '30 seconds'
WHERE name = 'daily-report' AND expires_at <= now()
RETURNING token;          -- 回傳 0 列 = 別人還拿著

每個鎖事先 INSERT 一列、expires_at 設成過去的時間；釋放就是把自己那一列的 expires_at 改回 now()（條件是 owner 和 token 都相符，跟上一節「值相符才刪」同一個道理）。這一列永遠不刪，token 才會一直往上加，不會從頭再來；如果刪掉重建，token 回到 1，新的持有者反而會被當成過時的。

報表那一端的檢查，在 PostgreSQL 裡就是一個條件更新，跟扣庫存的 WHERE stock > 0 是同一種寫法：

UPDATE reports
SET body = $1, last_token = $2
WHERE report_date = '2026-10-30' AND last_token <= $2;
-- 影響 0 列 = token 過時，這次寫入被拒絕

條件用 <= 而不是 <，是因為同一個持有者在一次租約裡可能寫好幾次，它每次帶的都是同一個 token，等於的情況要放行。下面把開場的事故跑一次，比較有沒有 fencing：api-2 帶著 34 先寫，api-1 醒來帶著 33 再寫。執行後看最後內容是誰的報表：

fencing 要能用，有三個條件：

  • token 要由鎖服務產生，而且一定遞增。上面的鎖表用 token = token + 1 就有。之後會介紹的 ZooKeeper 這類協調服務，每次變更都會帶一個遞增的編號（zxid），Kleppmann 建議可以直接拿它當 token；另一個選擇是 znode（ZooKeeper 裡存資料的一個節點）的版本號。
  • 資源要配合檢查。資料庫做得到；如果被保護的是一個不認識 token 的外部 API（例如寄信、扣款），fencing 就幫不上忙，要改用冪等鍵（第 9 課）讓重複的呼叫無害。寄報表給店長就屬於這種，所以第一節的「已寄出」唯一紀錄仍然要留著。
  • 每個資源各自記住最大 token：報表和庫存是不同的東西，互不影響。

報表的寫入安全了。但咖啡店的排程不只報表：清理過期訂單、把 outbox 送進佇列（第 12 課）也都跑在三台伺服器上，也都只該跑一份。每個排程各自寫一套取得、續約、fencing，重複又容易漏。更常見的做法是：從三台裡選一台，讓它負責所有排程。

能不能讓一台負責所有排程？Leader election

在多個程序中選出一個負責的程序，被選出來的叫 leader，其他的叫 follower，選的過程叫 leader election。最常見的做法就是前面的租約：三台都去搶同一把租約，搶到的就是 leader，負責跑所有排程；leader 定期續約保住位子，沒續到，租約過期，其他台就能搶到、接手當新的 leader。

難的是 leader 自己怎麼知道「我還是 leader」。如果它搶到時記一個布林值 isLeader = true，之後每次跑排程前看這個值，就會重演報表事故：暫停 40 秒醒來時，這個值還是 true，但租約早就給了別人。兩個程序都以為自己是 leader，同時跑排程，這叫 split-brain（腦裂）。要避免它，leader 每次做事前都要依租約的實際期限重新判斷，具體規則用一個 30 秒的租約來看：

  • 大約每三分之一個租約續約一次：30 秒的租約，每 10 秒續一次。一次續約失敗（網路抖一下）還有機會再試。
  • 每次要做事之前，用自己的時鐘重新算：「現在 < 到期時間 − 安全餘裕」才是 leader，不能讀快取的布林值。安全餘裕（safety margin）是故意少用的那一段時間，用來吸收兩台機器時鐘速度的小誤差和續約回應在路上的時間。到期時間要從送出續約請求之前記下的時間起算，因為回應晚到的那段時間，租約已經在走了。
  • 續約失敗就立刻退位：停止排程、放棄手上的工作，變回 follower。繼續做就是兩個 leader。
  • 續約不是重新取得：同一任 leader 的 token 不變；重新取得會拿到新 token，等於換了一任。
  • leader 的寫入也要帶 fencing token：就算做到以上全部，暫停仍然可能發生在「算完我是 leader」之後，跟上一節「寫入前先檢查租約」是同一個空檔。最後一道防線還是在資源端。

這些規則實務上很少自己寫。能讓多台機器對一件事達成一致、在部分機器故障或網路分割時仍然不會選出兩個結果的系統，叫共識系統（consensus），例如 ZooKeeper、etcd，它們內部用 Raft、ZAB 這類演算法做到這件事。Kubernetes 的 Lease 物件、etcd、ZooKeeper 都有現成的 leader election。這一課的練習 3 實作上面的規則，讓你知道這些工具在替你做什麼。

💡 實務上：「排程只跑一台」最簡單的做法常常不是選舉
咖啡店的 API 開三台，報表排程卻只該跑一次（NestJS 課第 21 課與部署課第 13 課遇過的問題）。最簡單的是把排程拆成獨立的 worker，只開一份；但部署時新舊版本會短暫重疊（例如 Kubernetes 預設的滾動更新會先啟動新的再停掉舊的），那幾秒內仍可能有兩份在跑。所以不管用單一 worker、advisory lock 還是 leader election，工作本身都要冪等，例如「今天的報表已寄出」的唯一紀錄。只有在服務很多、要自動接手又不能停的時候，才值得用 Kubernetes Lease 或 etcd 做正式的 leader election。

第二條規則說「用自己的時鐘重新算」。但一台機器上不只一種時鐘，選錯了，這條規則本身就會出錯。

租約靠量時間：該用哪一種時鐘？

租約從頭到尾都在量時間：租了多久、還剩多久、該不該續約。程式裡能拿到的時間有兩種，用途完全不同：

牆上時間（wall clock）單調時鐘（monotonic clock）
是什麼日曆時間：2026-10-30 03:00:00從某個起點開始累計，只會往前
JavaScriptDate.now()、new Date()performance.now()
會不會被調整會：NTP 校時、手動改時間，可能往前跳也可能倒退不會
適合記錄事件發生的時刻、跟別人比對日期量時間間隔、逾時、租約剩多久

牆上時間就是牆上的時鐘：它要對得上真實世界的日期，所以作業系統會定期向網路上的時間伺服器校時，用的協定叫 NTP，不斷修正它，修正的方向可能往前也可能往回。MDN 的說法：Date.now() 依賴系統時鐘，會受系統或使用者調整時鐘影響；performance.now() 相對於單調時鐘的 timeOrigin，不會變小、也不受調整影響。第 7 課的 Snowflake 遇過時鐘倒退產生重複 ID；用牆上時間量間隔也會出事。下面模擬一段真的花了 120ms 的工作，期間 NTP 把系統時間往回調了 2 秒。執行後比較兩行量到的耗時：

用牆上時間量出負的耗時。換成租約，就是「租約還剩多久」被算成很久，leader 以為自己還有時間、不續約也不退位，逾時永遠不觸發。所以規則是：量間隔、算期限一律用單調時鐘。上一節的「用自己的時鐘算」，指的就是用單調時鐘記下送出續約的時刻，再加上租約長度減掉安全餘裕。

單調時鐘也有限制：它的起點是程序自己定的，只在同一台機器的同一個程序裡有意義，不能傳給別台比較。api-1 的 5,000 和 api-2 的 5,000 不是同一個時刻。所以跨機器的租約只能靠兩個假設：各機器的時鐘走的速度差不多，以及安全餘裕夠大，能吸收速度上的小誤差。前面的鎖表用資料庫的 now() 判斷到期，就是讓「到期了沒」只由一個時鐘決定，避開各台時間不一致的問題。如果只需要知道事件的先後、不需要真實時間，也可以完全不靠時鐘，做法見課末。

到這裡，報表需要的每一塊都自己做過了：唯一紀錄擋重寄、租約鎖省重複的工作、fencing token 擋過時的寫入、leader 依單調時鐘續約與退位。剩下的是工具選擇：單一 Redis 掛掉就沒有鎖，主從切換又可能遺失鎖，於是常有人提議改用 Redlock。

有人提議用 Redlock：該選哪一種鎖，上線後看什麼？

Redlock 是 Redis 文件提出的演算法，目的是不依賴單一 Redis：準備 N 個（範例是 5 個）完全獨立的 Redis master，客戶端同時向全部設定鎖，在多數（至少 3 個）拿到、而且花的時間小於租約時才算取得；剩下的有效時間要扣掉取得花的時間和時鐘漂移。某一台掛掉，其他台的多數仍然記得這把鎖，所以不會像主從切換那樣遺失。

Kleppmann 在 2016 年的文章指出兩個問題，兩個都是這一課前面遇過的：

  • 沒有 fencing token：Redlock 給的是隨機值，不是遞增數字，所以擋不住報表事故那種暫停情境。多幾台 Redis 讓鎖更不容易遺失，但持有者被暫停的問題不在 Redis 那一端。
  • 安全性依賴時間假設：它假設網路延遲、程序暫停、時鐘誤差都遠小於租約。這些假設一旦不成立（某一台時鐘往前跳、GC 暫停、封包卡住），兩個客戶端就可能都以為自己拿到鎖。

Redis 的作者 antirez 寫了回應文章，Redis 文件把兩篇都附在 Redlock 段落最後，並在免責說明裡寫：在意正確性的話，要實作 fencing token，而且 Redis 的 TTL 不是單調時鐘。兩邊的論點值得各讀一次。回到第一節的問題「這把鎖是為了效率還是正確性」，實務上的選擇：

情況建議
效率鎖：失效只是多做一次單一 Redis 的 SET NX PX＋值相符才刪就夠了，寫清楚這把鎖是「大致上」互斥；不需要 Redlock 的 5 台
正確性鎖，已經有 PostgreSQL交易、唯一約束、條件更新、advisory lock；需要租約時用鎖表，資源端用 last_token 擋
正確性鎖，跨很多服務、要高可用共識系統（etcd、ZooKeeper）的鎖或 leader election，搭配 fencing token
資源不認識 token（外部 API）鎖只能降低機率；靠冪等鍵讓重複呼叫無害

咖啡店的報表兩種都有：「三台各算一次」是效率問題，單一 Redis 或 advisory lock 就夠；「舊報表蓋掉新報表」是正確性問題，資料已經在 PostgreSQL，用鎖表發 token、reports.last_token 擋；寄信給店長是外部動作，靠「已寄出」的唯一紀錄。三層各自負責一件事，Redlock 一層都不需要。

💡 實務上：上線之後看三個數字
等鎖的時間：變長代表競爭變多，或有人拿太久。租約過期的次數：持有者沒有正常釋放，代表工作比 TTL 久、或有程序當機或被暫停。fencing 拒絕的次數：平常應該是 0；只要大於 0，就代表「兩個人都以為自己拿著鎖」真的發生過，fencing 剛剛救了你一次，要去查是哪次暫停或切換造成的。報表排程的話，三個數字都記在同一筆日誌裡，出事時才查得到是哪一天、哪一台。

補充與查表

不用分散式鎖的常見解法（查表用，不用背）。第一節的思路套到其他「看起來要鎖」的問題：

問題不用分散式鎖的解法為什麼比較好
一張訂單只能付款一次付款表的 order_id 加唯一約束（第 9 課）第二筆 INSERT 直接失敗，沒有時間窗口
扣庫存不能扣成負數條件更新 UPDATE … SET stock = stock - 1 WHERE id = $1 AND stock > 0判斷和寫入在同一個原子操作裡
同一張訂單的事件要依序處理依 order_id 分區，同一個 key 只有一個消費者（第 12 課）用設計讓衝突不會發生
每天的報表只寄一次只讓一個程序跑排程；或用 PostgreSQL advisory lock；再加上「今天寄過了」的唯一紀錄最後一道是資料庫約束，鎖失效也不會重寄
工作佇列不能兩個 worker 拿同一筆SELECT … FOR UPDATE SKIP LOCKED（PostgreSQL 課第 33 課）鎖跟著交易，連線斷掉就釋放

Redis 的「值相符才刪」指令：Redis 8.4 開始有 DELEX key IFEQ value，直接做比對加刪除，不必寫 Lua；更舊的版本用正文的 Lua 腳本。

-- Redis 8.4 以後
DELEX lock:daily-report IFEQ 7f3a9c…

session 層級的 advisory lock：正文的 pg_try_advisory_xact_lock 跟著交易，交易結束自動釋放。session 層級的 pg_try_advisory_lock 不跟著交易，要自己呼叫 pg_advisory_unlock 釋放；連線斷掉時也會自動釋放（PostgreSQL 18 文件）。兩種的鎖生命都跟著連線或交易，不需要 TTL。

Lamport 邏輯時鐘：只需要知道事件的先後、不需要真實時間時，可以完全不靠時鐘。每個程序維護一個計數器，每發生一件事就加 1，收到別人的訊息時取「自己的、對方的」較大者再加 1。這樣有因果關係的事件，數字一定照順序。fencing token 也是同一個思路：用遞增的數字排順序，而不是用時間。

練習

練習 1：完成 LeaseLockService（一個在記憶體裡的鎖服務，時間只能用 now()）。租約在 now() >= expiresAt 時就算過期，過期的租約等於不存在。

  • acquire(resource, owner, ttlMs)：資源沒人持有（或租約已過期）時授予，回傳 { ok: true, token, expiresAt }，expiresAt = now() + ttlMs。token 是整個服務共用的 fencing token，第一次授予是 1，之後每次授予加 1（沒授予不加）。用一個計數器，就不必替每個資源另外保存「上次給到幾號」，資源的紀錄被刪掉也不會從 1 重來（ZooKeeper 的 zxid 也是全域遞增）。被持有時回傳 { ok: false, heldBy, retryAfterMs }，retryAfterMs 是租約剩下的毫秒數。同一個 owner 已經持有時再 acquire 也是 ok: false（不可重入）。
  • renew(resource, owner, token, ttlMs)：只有租約還沒過期、owner 和 token 都相符時，把 expiresAt 改成 now() + ttlMs 並回傳 true；否則 false。
  • release(resource, owner, token)：只有租約還沒過期、owner 和 token 都相符時才釋放並回傳 true；否則 false，而且不能動到別人的鎖。

練習 2：練習 1 的 LeaseLockService 已經寫好放在最上面。完成兩件事：

  • FencedStore：write(key, value, token) 記住每個 key 看過的最大 token；token 比它小就回傳 { ok: false, reason: 'stale_token' }，值不變；等於或比較大就寫入並回傳 { ok: true }（同一個持有者可以寫很多次）。read(key) 回傳目前的值，沒寫過是 undefined。
  • simulatePause(locks, store, clock)：重現本課的暫停情境。依序：'A' 取得 'daily-report' 的租約（ttl 1000ms）→ clock.advance(1500)（A 被暫停）→ 'B' 取得同一個資源（ttl 1000ms）→ B 用自己的 token 把 'B' 寫進 key 'daily-report' → A 醒來，用自己的 token 把 'A' 寫進同一個 key。回傳 { aWrite, bWrite }：兩次寫入各自有沒有成功。拿不到鎖時丟 Error。

練習 3：用租約做 leader election。練習 1 的 LeaseLockService 已經寫好。完成 createLeaderElector(opts)，回傳三個方法：

  • tick()：由外部定期呼叫。目前持有租約時用 renew 續約（不是重新 acquire），成功就把自己記的到期時間更新成「呼叫 renew 之前的 now() + ttlMs」；失敗就丟掉租約、變回 follower，並呼叫 onStepDown() 一次（這次 tick 不馬上重新取得）。沒有持有租約時嘗試 acquire。
  • isLeader()：持有租約，而且 now() < 到期時間 − safetyMarginMs 時才是 true。每次都要用 now() 重新判斷：就算一直沒有呼叫 tick（程序被暫停），時間到了也要回傳 false。
  • token()：目前持有的租約 token，沒有時是 null。

練習 4：每天 03:00 的營業報表三台伺服器都會寄。你加了一把 30 秒 TTL 的 Redis 鎖，做完才釋放，拿不到鎖的伺服器每 10 秒再試一次。產生報表要 2 分鐘，會發生什麼？

✓ b。租約到期就自動釋放，Redis 不知道持有者還在工作，也不會去中斷它（c 錯），所以「做完才釋放」不成立（a 錯）。修法：TTL 要比工作時間長並在期間續約；更根本的是讓工作冪等，例如先寫一筆「2026-10-30 已寄出」的唯一紀錄，鎖失效也不會重寄。

練習 5：釋放鎖時直接 DEL lock:report，會有什麼問題？

✓ c。key 名稱一樣，DEL 不知道現在的值是誰的。要在同一個原子操作裡比對值（擁有者 token）再刪：Redis 8.4 起用 DELEX key IFEQ value，舊版用 Lua 腳本。a 忽略了租約可能已經換人；b 會讓其他人白等；d 混淆了兩件事，fencing token 是在授予時產生的，和釋放的方式無關。

練習 6：持有鎖的程序在寫入資料前，先檢查「我的租約還沒過期」，通過了才寫。這樣能避免兩個程序同時寫嗎？

✓ a。暫停不看程式碼有多短，它可以發生在任意兩行之間（b 錯）；GC 暫停、VM 暫停、封包延遲都可能比你選的 TTL 長，TTL 只能降低機率（c 錯）。可靠的做法是把檢查放到資源那一端，和寫入在同一個原子操作裡：WHERE last_token <= $token。

練習 7：量一個請求花了多久，用兩次 Date.now() 相減有什麼風險？

✓ b。Date.now() 是牆上時間，會被調整（a 錯）；它的單位是毫秒（c 錯）。performance.now() 只會往前，適合量間隔、逾時與租約剩餘時間，但只在同一個程序裡有意義，不能拿去和別台機器的值比較。

練習 8：每天的對帳結果由拿到 Redis 租約鎖的那台寫進資料庫。api-1 GC 暫停 40 秒，租約過期由 api-2 接手寫完，api-1 醒來又用舊結果蓋掉。哪個修法擋得住？

✓ 只有資源那一端擋得住過時的寫入：檢查 token 和寫入是同一個原子操作，api-1 的 token 比資料庫看過的小就被拒絕。c 錯在暫停可以發生在檢查之後、寫入之前。a 只是降低機率；Redlock 給的是隨機值，不是遞增的 token。

常見錯誤

  • 能用唯一約束或條件更新解決，卻用分散式鎖：多一個會壞的元件，還有時間窗口。先讓資料庫保證，鎖只用來減少重複的工作，例如報表先補上「已寄出」的唯一紀錄。
  • 鎖沒有 TTL：持有者當機後永遠鎖住。用租約，或用跟著連線、交易走的 advisory lock。
  • TTL 比工作時間短又不續約：工作做到一半鎖就沒了，別人進來重做。TTL 要大於工作時間並定期續約，工作本身也要冪等。
  • 釋放時不比對 token：刪掉別人的鎖。比對和刪除要是同一個原子操作，用 Lua 腳本或 DELEX … IFEQ；先 GET 再 DEL 中間仍有空檔。
  • 以為「寫入前先檢查租約」就安全：暫停可以發生在檢查之後、寫入之前。要正確就讓資源端檢查 fencing token。
  • 正確性需求卻沒有 fencing：程序暫停後醒來覆蓋別人的資料。鎖服務給遞增的 token，資源用 last_token <= $token 擋。
  • 用牆上時間量間隔或判斷租約：NTP 調整會讓判斷錯誤。程序內用 performance.now()；跨機器的到期判斷交給同一個時鐘（例如資料庫的 now()）並留安全餘裕。
  • 以為 Redis 主從切換後鎖還在：非同步複寫可能遺失剛設定的鎖。需要正確性就不要只靠 Redis 的鎖。
  • 續約失敗後 leader 繼續工作，或用快取的布林值判斷自己是 leader：出現兩個 leader。每次做事前用自己的單調時鐘重算，續約失敗立刻退位。

小結

  • 分散式鎖讓不同機器上的程序互斥地使用同一個資源；鎖服務分辨不出持有者是當機、暫停還是斷線，這是它難的根源。
  • 先問需不需要鎖：唯一約束、條件更新、依 key 分區、單一擁有者常常更好。需要時分清楚效率鎖（失效只是多做）和正確性鎖（失效會弄壞資料）。報表靠「已寄出」的唯一紀錄擋重寄，鎖只用來省下重複的計算。
  • 租約鎖：SET key token NX PX ttl 取得；值相符才刪，比對和刪除是同一個原子操作（Lua，或 Redis 8.4 的 DELEX IFEQ）；到期前續約；拿不到就隨機延遲再試。已有 PostgreSQL 時用 advisory lock。
  • 租約一定會在某些時候失效：程序暫停、網路延遲、時鐘跳動、非同步複寫的切換。「寫入前先檢查」擋不住，因為檢查和寫入之間永遠有空檔。
  • Fencing token：每次授予就遞增（例如鎖表的 token + 1），資源記住每個 key 看過的最大值，拒絕更小的；檢查和寫入在資源端原子完成。資源不認識 token 時改用冪等鍵。
  • Leader election：用租約、每 1/3 租約續約、續約失敗立刻退位、每次做事前用自己的時鐘加安全餘裕判斷，寫入仍然帶 fencing token。
  • 量間隔、算期限用單調時鐘；跨機器的到期判斷交給同一個時鐘。
  • Redlock 沒有 fencing 且依賴時間假設。效率鎖用單一 Redis，正確性用資料庫或共識系統加 fencing；上線後看等鎖時間、租約過期次數、fencing 拒絕次數。
