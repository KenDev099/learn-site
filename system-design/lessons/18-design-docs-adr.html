階段 5：資深工程實踐：決策、演進、審查與除錯 · 第 18 課

設計文件與 ADR：把決定和理由寫下來

咖啡店要做「預約取餐時段」：顧客下單時選 10 分鐘一格的時段，每格有名額，到店直接拿。半年前有人用 Redis 鎖保護名額，最近週年慶超賣了兩次。新同事問：「當初為什麼用 Redis 鎖？」沒人記得。有人提議改成資料庫的條件更新，另一個人說「這個之前討論過，好像有問題」，但說不出是什麼問題。會議開了一小時，最後決定「再研究看看」。

這件事指派給你：把名額的保護方式換掉，而且要讓一年後的人不必再開一次這種會。卡住的地方不是技術，而是當初的決定和理由沒有留下來。這一課教你兩種文件：動手前寫的設計文件，用來找出問題、取得共識；每個重要決定一份的 ADR，用來記住「當時為什麼這樣選」。整課都在完成這件事：替預約取餐時段寫設計文件、比較方案、寫下取代舊決定的 ADR，再送審查。

這課的路線：
  1. 會議為什麼沒有結論：缺的是哪幾樣東西，設計文件和 ADR 各補哪一塊（開場問題的最小答案）。
  2. 這次改動值得寫設計文件嗎：沒有取捨的事不用寫；用單向門、雙向門判斷該慢還是該快。
  3. 設計文件寫什麼：以預約取餐時段為例，每一段回答審查者一定會問的一個問題，最後列出替代方案。
  4. 三個方案怎麼比：加權決策矩陣，以及用敏感度檢查結論穩不穩。
  5. 決定怎麼留給一年後的人：寫 ADR 7 取代 ADR 3；送審查時問什麼、意見不同怎麼收斂、核准後文件怎麼維護。
這課會用到：
  • 第 2 課的估算：寫出假設、計算、結論與「何時要重算」；敏感度分析是一次改一個假設，看結論會不會變。
  • 第 3 課的 p99 與 SLO：p99 是 99% 請求都比它快的延遲；SLO 是團隊承諾的目標，例如「p99 ≤ 300 ms」。
  • 第 14 課的結論：能用條件更新（判斷和寫入在同一句 SQL）就不要用分散式鎖。分散式鎖通常帶租約（lease），也就是時間到就自動釋放；持有者如果卡住超過租約，自己不知道鎖已經沒了，另一個請求就能拿到同一把鎖。

會議為什麼開了一小時還沒有結論？

回頭看那場會，大家缺的不是能力，而是三樣東西。第一，當初的理由。半年前選 Redis 鎖，也許是因為那時資料庫已經很忙，也許只是寫的人熟 Redis。理由不同，今天該不該推翻的答案就不同：如果理由是「資料庫扛不住」，就要先確認現在扛不扛得住；如果只是習慣，直接換掉就好。沒有人知道理由，就只能猜。第二，被否決過的方案和否決的原因。「條件更新之前討論過，好像有問題」這句話，只存在某個人模糊的記憶裡，沒辦法檢查它對不對，也沒辦法反駁，只能讓大家不敢動。第三，大家看著同一份提案。提議改條件更新的人腦中有一套做法，反對的人想像的是另一套，討論的一小時有一半花在弄清楚彼此在說什麼。

這三樣東西對應兩種文件。設計文件（design doc）是動手寫程式之前，寫下「要解決什麼問題、打算怎麼做、有哪些取捨、考慮過哪些別的做法」的文件。它補的是第三樣：在動手前讓所有人對著同一份具體的提案討論，順便把考慮過的方案一起寫下來。有些公司把它叫做 RFC，是 request for comments 的縮寫，意思是「這是草案，請大家提意見」。

ADR（architecture decision record，架構決策紀錄）則是一個重要決定寫一份的短文件，記下當時的背景、決定了什麼、會帶來什麼後果。它補的是第一樣和第二樣。設想半年前有人寫了「ADR 3：用 Redis 鎖保護時段名額」，背景寫了當時的考量，後果寫了「租約過期時可能有兩個請求同時以為拿到鎖」：今天的會只要讀完它、確認那個風險已經發生了，十分鐘就能決定。這就是開場問題的最小答案：動手前寫設計文件取得共識，決定之後寫 ADR 留下理由。ADR 的格式在後面寫 ADR 7 時再細講。

設計文件的價值不只解決這一場會。Malte Ubl 在〈Design Docs at Google〉（2020）列出它的用途，套到這次的任務上是：

  • 在改動還便宜的時候找出問題：在文件上改一段話只要幾分鐘；程式寫完、資料搬完才發現方向錯，要幾週。
  • 取得共識：前端、後端、門市營運、資安看同一份文件，在動手前把分歧說出來，而不是在會議裡各自想像。
  • 確保跨領域的問題有人想過：安全、隱私、可觀測性這些容易漏掉的事，文件裡有固定的段落逼你回答。
  • 把資深工程師的經驗傳出去：審查時的提問和回覆都留在文件上，新人讀了就學到。
  • 留下組織的記憶：一年後有人問「為什麼這樣做」，答案在文件裡，不在某個已經離職的人腦中。
💡 實務上：進新團隊，先找舊文件，再寫自己的
開場那位新同事其實該先做一件事：找找看有沒有舊的設計文件或 ADR。多數團隊已經有地方放（Notion、Confluence、Google Docs 或 repo 的 docs/），也常有範本，先照團隊的格式寫，不要自創一套。接手一個系統前先讀它的文件，很多「為什麼這麼怪」的疑問會直接有答案。你的第一份通常是小型設計文件，例如「訂單列表改成無限捲動」。寫到三成、方向還能改時，就先給一位資深同事看，比寫完整份才發現方向錯省很多時間。

文件有用，但寫文件要花時間，審查也要占用別人的時間。如果每個改動都要寫，團隊會慢到什麼都做不了。所以動筆之前，先回答下一個問題：這次的改動值得寫嗎？

這次改動值得寫設計文件嗎？

第一個判斷標準是有沒有取捨。答案很明確、沒有其他合理做法的時候（例如修一個 bug、加一個欄位），寫出來只會是一份「先改這個檔案、再改那個檔案」的實作手冊，審查者沒有東西可以判斷，不如直接寫程式，在 PR 描述寫清楚就夠了。反過來，有好幾種合理做法、各有代價，而且團隊裡已經有人意見不同，就值得把取捨攤開來寫。預約名額這件事正是後者：至少有三種做法，會議上已經吵過，選錯的後果是超賣。

第二個判斷標準是做錯了能不能退回來。Amazon 2015 年的致股東信把決定分成兩種。單向門（one-way door）是影響重大、做了就很難或不可能回頭的決定，像走進一扇只能從一邊開的門；這種決定要慢、要仔細、要多方討論。雙向門（two-way door）是做錯了可以改回來的決定，應該由判斷力好的個人或小團隊快速決定，錯了就退回。信裡也提醒反方向的風險：組織變大以後，常把單向門的流程套在雙向門上，結果每件小事都要開會，團隊變得很慢、不敢實驗。

雙向門：快速決定、寫一份短 ADR 或直接做單向門：寫設計文件、審查
加一層快取（拿掉就回到原樣）公開 API 的格式（外部客戶已經在用，第 19 課）
換一種 log 格式、調整逾時秒數資料模型、主鍵的設計（改了要搬資料）
旗標後面的新功能把模組拆成獨立服務（第 15 課）
換一個內部用的套件版本刪除資料、綁定某家雲端廠商的專屬服務

表格右欄的共同點是：改了以後，資料、外部使用者或廠商已經跟著變了，退回去的成本很高。不過門不是天生固定的。很多單向門可以被設計成雙向門：用旗標放量、新舊並行、先雙寫再切換（第 19 課）。資深工程師的價值之一，就是把「一次賭上全部」的決定拆成可以退回的小步，只留下一個範圍最小、而且排在最後的不可逆步驟。等一下寫上線計畫時，你會看到預約名額的改動就是這樣處理的：換做法本身可以隨時切回去，只有「刪掉舊的 Redis 鎖程式」退不回來。

至於要寫多長，Ubl 給的參考是：大型專案約 10～20 頁，再長就該拆成幾個子問題；小改動寫 1～3 頁的小型設計文件（mini design doc）就好。預約名額的改動範圍不大，但有取捨、出錯會超賣，寫一份幾頁的設計文件剛好。

💡 實務上：前端也有單向門
前端的決定大多是雙向門，改個元件、換個樣式，下次部署就回來了。但有幾種很難退：已經被分享、被搜尋引擎收錄的網址結構（改了要做轉址）；存在使用者瀏覽器 localStorage 裡的資料格式（新版程式要能讀舊格式）；已經上架的 App 版本（使用者不更新，舊版會繼續打你的 API）。遇到這幾種，先停下來寫幾段說明、找人看過再動手。反過來，不要因為怕犯錯就把每個改版都拿去開會，旗標後面的實驗直接做就好。

決定要寫了，下一個問題是寫什麼。設計文件不是想到什麼寫什麼，每一段都對應審查者一定會問的一個問題。

設計文件寫什麼？每一段回答審查者的一個問題

下面用預約取餐時段逐段寫一次。順序跟審查者讀文件時腦中的問題一樣：要解決什麼、規模多大、打算怎麼做、哪裡會壞、出事怎麼退、還有什麼沒想到、為什麼不用別的做法。不管文件多長，最前面先放一段三句話以內的摘要，寫出要決定什麼、建議怎麼做，讓忙碌的人讀完就知道要不要細看。

要解決什麼、不解決什麼？背景、目標與非目標

背景與範圍（context and scope）用幾句話客觀說明現況與要做什麼。它是寫給還不了解這件事的人看的，所以要寫事實，不要寫成推銷提案。

目標（goals）寫做到什麼才算成功，而且要可以量測。「系統要穩定」沒辦法檢查；「名額不超賣（超賣次數 = 0）」上線後看數字就知道有沒有做到。可以量測的目標也讓後面的設計有依據：要達到「p99 ≤ 300 ms」，就得先知道尖峰有多少流量。

非目標（non-goals）是「合理、別人可能以為會做，但這次刻意不做」的事。它最容易被省略，卻很有用：不寫的話，審查時有人問「那外送平台的時段呢？」，範圍就開始長大，文件永遠審不完。寫出非目標，審查者知道哪些問題不必在這份文件裡回答；被排除的事也不是消失，而是明確地留給另一份文件。注意非目標要是「合理但不做」，不是「顯然不做」：寫「不會把資料庫換成 Excel」沒有資訊量。

【背景】門市尖峰排隊 15 分鐘以上。App 已能下單，但不能指定取餐時間。
【目標】顧客下單時可以選 10 分鐘一格的取餐時段；每格名額不超賣（超賣次數 = 0）；
       預約 API 的 p99 在週年慶尖峰下 ≤ 300 ms（SLO，第 3 課）。
【非目標】外送平台的時段（另案）；依現場人力動態調整名額；改動現有的付款流程。

目標裡寫了「週年慶尖峰」，審查者馬上會問：尖峰到底多少？這就是下一段要回答的。

設計扛得住嗎？假設與估算

照第 2 課的格式寫：每個數字從哪個假設來、怎麼算，讓別人能檢查、能重算。「流量很大」沒辦法判斷設計夠不夠；「尖峰每秒 1.67 筆」可以。執行下面這格，看「尖峰每秒」那一行，並跟「平均每秒」比較。

平均值把半夜沒人下單的時間也算進去，會嚴重低估；設計要扛的是尖峰。這組數字直接決定設計方向：每秒幾十筆的寫入，一台 PostgreSQL 綽綽有餘，不需要為了分擔寫入而把名額搬到 Redis；同一格名額 10 分鐘內最多被搶 20 次，同一列的鎖等待也不會是問題。這就是後面選擇條件更新、不用分散式鎖的依據。把這段寫進文件，一年後流量變成十倍時，讀的人知道哪個假設失效了、該重算哪裡。

打算怎麼做？脈絡圖、API 與資料

有了規模，就可以寫提案本身。先畫系統脈絡圖（system context diagram）：一張只畫「新系統在哪裡、跟誰溝通」的圖，不畫內部細節。它讓審查者一眼看出這個功能依賴哪些東西。依賴要分兩種：硬相依是它壞了，預約就做不了，圖上用實線；軟相依是它壞了，功能變慢或變陽春但還能用，圖上用虛線。這個區分下一段寫故障模式時會用到。

注意 Redis 在新設計裡只剩「時段列表快取」，是軟相依：它壞了，列表改查資料庫，只是慢一點。名額的正確性不再依賴它。

接著寫 API 和資料。只寫到能討論的程度，是草圖，不是把程式碼貼上來：審查者要判斷的是「這個介面和資料結構對不對」，不是逐行看實作。

POST /pickup-slots/{slotId}/reservations    標頭 Idempotency-Key（第 9 課）
  201 { reservationId, expiresAt }          名額保留 10 分鐘等付款
  409 { code: 'slot_full' }                 名額已滿

pickup_slots(id, store_id, starts_at, capacity, booked)
  CHECK (booked BETWEEN 0 AND capacity)、UNIQUE (store_id, starts_at)

-- 搶名額：一句條件更新，回傳 0 列就是滿了（第 14 課）
UPDATE pickup_slots SET booked = booked + 1
WHERE id = $1 AND booked < capacity
RETURNING booked;

只有沒人見過的演算法才需要貼程式碼。這裡要寫清楚的是「為什麼一句條件更新就夠」：檢查「還有名額」和「加 1」在同一句 SQL 裡完成，資料庫保證不會有兩個請求同時看到「還剩 1 個」。舊做法的問題是先在 Redis 拿鎖、再查資料庫、再寫入，鎖和資料分在兩個地方；第 14 課看過，鎖的租約一過期，持有者自己不知道，另一個請求就能拿到同一把鎖，兩邊都寫入，名額就超賣了。CHECK 約束是第二道防線：就算程式哪天寫錯，資料庫也不允許 booked 超過 capacity。

到這裡描述的都是一切順利的情況。但脈絡圖上的每條實線都是一個可能壞掉的地方，審查者下一個問題一定是：它壞了會怎樣？

哪裡會壞？故障模式

故障模式（failure modes）這一段，逐一寫出每個依賴壞掉或變慢時，系統會怎麼反應、使用者看到什麼。只描述一切順利的設計，審查時一定會被打回來，因為正式環境裡依賴一定會壞，差別只在你有沒有事先決定它壞的時候怎麼辦。寫法是從脈絡圖出發，每個硬相依至少一列，再加上這個功能特有的壓力情境（這裡是熱門時段被大量同時搶）：

狀況系統的行為使用者看到
金流逾時或掛掉（硬相依）逾時 3 秒（第 8 課）；名額先保留 10 分鐘，付款結果沒確認就到期釋放「付款確認中」，10 分鐘內沒結果就通知重新預約
PostgreSQL 主庫切換（約 30 秒）寫入失敗，回 503 加 Retry-AfterApp 帶同一個冪等鍵自動重試，不會重複預約
Redis 掛掉（軟相依）時段列表直接查資料庫，延遲變高列表慢一點；名額的正確性不受影響
熱門時段大量同時搶同一列的更新排隊，第 21 個人拿到 0 列「這個時段滿了」，並推薦相鄰時段

每一列都在回答「壞了之後，資料會不會錯、使用者會不會卡住」。例如主庫切換那一列，靠的是 API 草圖裡的 Idempotency-Key：重試時帶同一個鍵，伺服器認得出是同一筆預約，不會因為重試而多佔一個名額。故障模式寫完，常常會回頭修改提案設計，這正是在文件階段找出問題的意義。

故障模式處理的是依賴壞掉。還有一種更麻煩的情況：依賴都好好的，是新做法本身有沒想到的問題。上線之後才發現，要怎麼退？

新做法出事怎麼退？上線與回滾計畫

上線與回滾計畫（rollout／rollback plan）寫的是怎麼一步步放出去，以及每一步出事時怎麼退回。一次全部切換的話，出問題就是全部門市一起出問題；分步放量，問題只會出現在一小部分門市，而且你有時間觀察。

分步放量要靠功能旗標（feature flag）。功能旗標是程式裡的一個開關，值存在設定或專門的服務裡，程式執行時讀它來決定走新做法還是舊做法；改開關不用重新部署（第 19 課會細講）。這次用旗標以門市為單位放量：開了旗標的門市用條件更新，其他門市繼續用 Redis 鎖。

為什麼可以隨時切回去？有兩個條件。第一，以門市為單位切換，同一個時段只會走一種做法，不會有一半請求用鎖、一半用條件更新，互相不知道對方存在。第二，兩種做法都讀寫同一個 booked 欄位，切回去時資料不用搬。這就是上一節說的「把單向門設計成雙向門」。唯一退不回去的是最後一步：

1. 部署條件更新的新程式，旗標 slot-booking-pg 關閉     回滾：不用動
2. 5% 門市開啟，觀察超賣次數與 p99 三天               回滾：關閉旗標
3. 全部門市開啟                                       回滾：關閉旗標
4. 穩定兩週後移除 Redis 鎖的程式（不可逆）             回滾：從 git 還原並重新部署

不可逆的步驟放在最後。移除 Redis 鎖的程式之後，旗標就沒有舊做法可以切回去了，要退只能從 git 還原再重新部署，慢而且容易出錯。所以等新做法穩定兩週再做：前面每一步都能用旗標退回，拆掉退路的那一步不會夾在中間。如果把它放在第 2 步，5% 門市一出問題，你就沒有快速退回的路了。

到這裡，提案、故障、上線都有了。但這些都是從「預約功能」本身出發想的，還有一些問題不屬於任何一個功能，卻每個設計都逃不掉。

還有什麼沒想到？跨領域考量與開放問題

跨領域考量（cross-cutting concerns）是每個設計都要回答、但很容易因為「不是這個功能的重點」而漏掉的問題。固定寫一段，就不會漏。這次的回答是：

  • 安全：照認證課第 25 課做威脅建模。有人寫程式把熱門時段全部搶光怎麼辦？要限流（第 10 課）。
  • 隱私：預約紀錄有顧客的到店時間，算個人資料。要保存多久是法務和產品的決定，這次還沒有答案，所以不在這裡拍板，而是列進下面的開放問題。
  • 可觀測性：上線後看哪些數字判斷它正常：超賣次數、預約 p99、名額用完的比例。上線計畫第 2 步「觀察超賣次數與 p99」看的就是這些。
  • 成本與相容性：不多開機器。前面估算的週年慶尖峰每秒約 33 筆寫入，現有的 PostgreSQL 扛得住，條件更新也不需要新服務。舊版 App 不會呼叫新的預約 API，照舊用一般下單，不受影響。

開放問題（open questions）是還沒有答案、需要別人決定的事。寫出問題、誰來回答、什麼時候前，例如「名額要不要開放給外送平台？（產品經理，11/15 前）」、「預約紀錄的到店時間保存多久？（法務，11/15 前）」。把不確定寫出來，比假裝都想好了誠實，也讓審查者知道哪裡還能幫忙；不寫的話，這些問題會在實作到一半時才冒出來。

為什麼不用別的做法？替代方案

最後一段是替代方案（alternatives considered）：認真考慮過、但沒選的做法，以及不選的理由。Ubl 認為這是最重要的段落之一，因為審查者靠它判斷你有沒有想清楚：只看提案，看不出它為什麼比別的好。它也直接回答開場那句「之前討論過，好像有問題」：把每個方案的問題寫下來，以後就不用憑記憶。

替代方案要是真的考慮過的方案。只寫「什麼都不做」，或故意寫一個很差的方案來襯托提案，等於沒寫。後者叫稻草人：先立一個一推就倒的假對手，再推倒它來顯示自己對，審查者一眼就看得出來。這次至少要寫兩個真實的方案：

  • 維持 Redis 鎖：程式已經寫好、延遲最低，但租約過期時會超賣，週年慶已經發生兩次。
  • 依門市排隊：每家門市的預約請求先放進一條佇列，由一個消費者依序處理。同一家門市一次只處理一筆，自然不會超賣；代價是要多維運一套佇列，而且顧客要等前面的請求處理完才知道結果。

三個方案各有優點，也各有人支持。文件裡只寫「我們覺得條件更新比較好」說服不了人，需要一個讓大家對著同一套標準比較的方法。

三個方案各有人支持，怎麼比出結論？加權決策矩陣

方案一多，討論容易變成各說各話：支持 Redis 鎖的人講延遲，支持條件更新的人講正確性，雙方都對，但比的不是同一件事。決策矩陣（decision matrix）把比較拆成兩步。第一步，先列出評分標準和每個標準的權重，權重代表這個標準對這次的決定有多重要。第二步，替每個方案在每個標準上打 1～5 分，總分 = Σ 權重 × 分數。

順序很重要：先定標準和權重，再打分。先打分再定權重的話，人會不自覺地調權重讓自己喜歡的方案贏。這次的權重反映了任務本身：超賣是事故的起因，所以正確性的權重最高（4）；名額要長期維運，維運成本次之（3）；延遲在估算裡已經確認不是瓶頸（2）；實作時間只是一次性的成本（1）。執行下面這格，先看前三行的總分，再看維運成本權重降低之後，排名有沒有變。

條件更新 46 分，Redis 鎖 33 分，依門市排隊 31 分；維運成本的權重降 20% 之後，條件更新還是第一。

但矩陣只是輔助，不是自動算出答案的機器。權重本身就是判斷：把「實作時間」的權重從 1 一路調高，Redis 鎖（已經寫好了，實作時間 5 分）就會越來越好看，調到 8 以上它就贏了。誰都可以挑一組權重讓自己的方案贏，所以總分本身說服不了人，要檢查結論穩不穩。做法是第 2 課的敏感度分析：一次只把一個權重改 ±20%，其他不動，看贏家會不會換人。

  • 不會換：結論穩，文件裡寫一句「任一權重 ±20% 結論不變」。審查者就不必再爭權重的細節。
  • 會換：結論取決於那個權重。文件裡要明講「如果你認為維運成本沒那麼重要，答案會是 B」，讓審查聚焦在那個權重該是多少，而不是吵總分。

還要避免假精確：分數是 1～5 的主觀判斷，本身就有一兩分的誤差，總分 46 對 45 就是平手，不要寫成「方案 A 勝出 2%」。差距小的時候，回頭找能量測的事實，例如做一個小原型壓測延遲，用資料取代打分。

矩陣幫團隊做出了決定：名額改用條件更新。這個決定會寫在設計文件的提案裡，但設計文件很長，討論的是一整個功能。一年後的新同事只想知道「名額為什麼用條件更新、不用 Redis 鎖」，不會去讀一份十頁的文件。這個決定需要一個更小、更好找的家。

一年後有人問「為什麼」，答案在哪？寫 ADR 取代舊決定

ADR 的格式來自 Michael Nygard 的〈Documenting Architecture Decisions〉（2011）：每個重要決定寫一份一兩頁的短文件。短，是為了讓它真的會被寫、也真的會被讀。一份 ADR 有五個部分：

段落寫什麼
標題短的名詞片語，帶編號，例如「ADR 7：時段名額改用 PostgreSQL 條件更新」
背景（Context）當時有哪些力量在拉扯：技術、團隊、時程、成本。客觀描述
決策（Decision）用完整句子、主動語態寫：「我們將……」（We will …）。不寫「建議」「可能」
狀態（Status）proposed（還在討論）、accepted（已同意）；之後可能變成 deprecated（不再適用）或 superseded（被另一份取代，並寫出被哪一份）
後果（Consequences）做了這個決定之後的影響，正面、負面、中性都要寫。沒有負面後果的 ADR 通常是沒想清楚

每一段都對應開場那場會缺的東西。背景記下「當時為什麼這樣選」，理由不再成立時一看就知道；決策用「我們將」寫，讀的人不會分不清這是建議還是定案；後果裡的負面項目，告訴之後的人要注意什麼，例如這次要監控熱門時段的 p99。下面是這次要寫的 ADR 7：

# ADR 7：時段名額改用 PostgreSQL 條件更新

狀態：accepted（取代 ADR 3）

## 背景
ADR 3 用 Redis 鎖保護時段名額。週年慶時租約過期，兩個請求都以為自己拿到鎖，
超賣了兩次（事故報告 2026-10-12）。尖峰每秒約 1.7 筆、週年慶約 33 筆，
單一時段 10 分鐘內最多 20 次更新。

## 決策
我們將用一句條件更新（booked < capacity 才加 1）保護時段名額，並在穩定兩週後移除 Redis 鎖。

## 後果
- 正面：名額由資料庫保證，租約過期、程序暫停都不會超賣；少一個硬相依。
- 負面：熱門時段的同一列會排隊等鎖，要監控預約 API 的 p99。
- 中性：旗標以門市為單位放量，同一個時段不會混用兩種做法。

背景裡的數字直接從設計文件的估算搬過來，所以一年後流量變了，讀的人知道這個決定是在什麼規模下做的。

ADR 7 推翻了 ADR 3，那 ADR 3 怎麼處理？直覺是刪掉或改寫，但這正是 ADR 最容易用錯的地方。下面三條規則讓 ADR 長期有用：

  • 編號依序遞增、不重複使用。號碼就是引用的方式：程式註解、PR 描述寫「這是 ADR 7 的決定」。號碼重複了，引用就指不清楚。
  • 被推翻時不刪、不改寫：ADR 3 保留，狀態改成 superseded 並指向 ADR 7；ADR 7 寫「取代 ADR 3」。Nygard 的說法是：它曾經是決定，這件事本身就有價值。刪掉，以後有人提議「改用 Redis 鎖吧，比較快」，就沒有紀錄告訴他這條路走過、在哪裡出過事。改寫 ADR 3 的內容，會讓人以為當初就是這樣決定的，舊 PR 裡寫著「依 ADR 3」的連結也會指到不同的內容。
  • 放在程式碼的 repo 裡，例如 docs/adr/ 資料夾，跟程式一起 review、一起留歷史；資料夾和檔名的常見慣例見課末。程式裡容易被誤改的地方加一行註解連到 ADR，例如在那句條件更新旁邊註明「見 ADR 7」，PR 描述也附上連結。

現在可以說清楚設計文件和 ADR 的分工了。設計文件討論一整個功能，裡面可能做了好幾個決定；其中影響長遠的（例如「名額用條件更新」）各寫一份 ADR，連回設計文件。設計文件反映的是某個時間點的完整想法，實作之後會慢慢過時；ADR 則是一條一條可以追的決定歷史，新的取代舊的，鏈條不斷。Nygard 的五段格式之外，也有段落更完整的範本 MADR，多了「考慮過的方案」和「怎麼確認決定有被落實」，細節見課末。

💡 實務上：什麼時候會輪到你寫 ADR
前端工程師最常碰到的 ADR 是選型：狀態管理用哪個套件、表單驗證怎麼做、API 型別要不要從後端自動產生。有人在 PR 提議「換回舊做法」時，資深工程師第一句常是「有 ADR 嗎？當初的理由現在還成立嗎？」。理由不再成立就寫一份新的取代它，就像這次 ADR 7 取代 ADR 3，而不是在留言串裡吵完就算。常見的坑是 ADR 資料夾沒人讀：新人到職時把 ADR 清單排進必讀，比寫更多份有用。不要替每個小選擇都寫 ADR，留給「一年後有人會問為什麼」的決定。

設計文件和 ADR 7 的草稿都寫好了，狀態還是 proposed。要變成 accepted，得先讓其他工程師看過。

送審查：要問什麼？意見不同怎麼收斂？

設計審查（design review）是讓其他工程師在實作前檢視設計。可以很輕，把文件丟到團隊頻道收留言；也可以很正式，開會請資深工程師看。審查者的工作是找出風險，不是挑語病，也不是展示自己懂多少。下面這份問題清單，每一題都對應文件裡的一段；文件寫得好，審查者能在文件裡找到答案，找不到就是要補的地方：

  • 需求可以量測嗎？「要快」→ 在多少負載下 p99 多少？（目標）
  • 數字從哪來？DAU、尖峰佔比的來源，錯了會不會改變結論？（假設與估算）
  • 哪裡會壞？每個硬相依壞掉時，使用者看到什麼？（故障模式）
  • 怎麼回滾？哪一步之後就退不回去了？（上線與回滾）
  • 怎麼遷移？舊資料、舊版 App 怎麼辦？
  • 怎麼知道它正常？要看哪些指標、什麼時候告警？（可觀測性）
  • 多少錢？機器、第三方服務、維運的人力。

審查一定會有意見不同的時候。假設審查時，一位資深同事堅持「條件更新在週年慶會因為鎖等待拖慢 p99」，另一位說不會，兩人都憑經驗，誰也說服不了誰。這就是開場那場會的翻版。Google 的 code review 指引有一句可以直接搬到設計審查：技術事實與資料優先於意見和個人偏好。做法是把爭論轉成可以驗證的問題：「條件更新在週年慶尖峰下的 p99 是多少？」然後花半天做原型壓測，答案就出來了。比起聽年資深的人、或投票多數決，這樣做錯了也知道錯在哪。

有些問題驗證不了，或驗證的成本太高。這時由事先講好的決策者（通常是技術負責人）決定，並把理由寫進文件或 ADR。「事先講好」很重要：沒有人負責拍板，討論就只能結束在「再研究看看」。審查也要限時，結論寫回文件，不要讓文件卡在「再討論」。審查通過後，ADR 7 的狀態改成 accepted，ADR 3 改成 superseded。

到這裡，決定做完、理由也留下了。但文件的工作還沒結束：接下來要實作、上線，而實作很少完全照著文件走。

核准之後，文件還要做什麼？

文件最常見的下場是寫完就沒人更新，最後跟程式對不上。照這次任務的時間順序，文件在三個時間點要被動到：

  • 實作中：實作時發現設計行不通是常態。例如壓測發現熱門時段的鎖等待比預期久，要加一層排隊。改了做法就更新文件，大的改動另寫補充文件並從原文件連過去。程式改了文件沒改，比沒有文件更誤導，因為讀的人會相信它。
  • 上線後：補一段「我們學到什麼」：哪些估算準、哪些不準，例如週年慶實際尖峰是不是每秒 33 筆。跟 PostgreSQL 課第 39 課的事後檢討一樣，寫事實、不寫責怪。
  • 一兩年後：Ubl 建議回頭重讀自己的設計文件，問自己當初哪些判斷對、哪些錯、今天會怎麼決定。這是累積判斷力最便宜的方法。

回到開場：下次有新同事問「名額為什麼用條件更新」，他會在程式註解看到「見 ADR 7」，從 ADR 7 連到被取代的 ADR 3 和設計文件，十分鐘就知道當初比較過什麼、為什麼這樣選，以及哪個假設變了就該重新討論。

MADR（Markdown Architectural Decision Records）是比 Nygard 格式更有結構的 ADR 範本，目前最新是 4.0.0，2024-09-17 發布。它的段落是 Context and Problem Statement、Decision Drivers（選填）、Considered Options、Decision Outcome（底下有選填的 Consequences 與 Confirmation；Confirmation 寫怎麼確認這個決定有被落實，例如架構測試或 code review）、Pros and Cons of the Options（選填）、More Information（選填）。跟 Nygard 格式比，MADR 多了「考慮過的方案」和「怎麼確認」。

設計文件的段落與它回答的問題：

段落回答審查者的問題
摘要要決定什麼、建議怎麼做？
背景與範圍、目標與非目標要解決什麼、不解決什麼？怎樣算成功？
假設與估算規模多大？設計扛得住嗎？
提案設計（脈絡圖、API、資料）打算怎麼做？依賴哪些東西？
故障模式每個依賴壞掉時會怎樣？
上線與回滾怎麼放出去？哪一步之後退不回來？

替代方案為什麼不用別的做法？

練習

練習 1：寫 weightedDecision(criteria, options)：

  • 每個方案的 total = Σ weight × scores[id]（依 criteria）。某個方案缺少某個標準的分數時丟 Error。
  • ranking 依 total 由大到小；同分時依 name（用 < 比較字串）由小到大。winner 是第一名。
  • fragileOn：一次只改一個標準的權重，改成 × 0.8 或 × 1.2，其他維持原值，重新排名；只要贏家換人，就把那個標準的 id 放進來（依 criteria 的順序、不重複）。
  • 輸入是凍結的，不要修改它們。

練習 2：寫 validateAdrLog(adrs)，檢查一整份 ADR 紀錄，回傳 `${number}:${code}` 的陣列，依號碼、再依代碼（用 < 比較）排序；沒有問題回傳 []。每一條規則各自檢查：

代碼什麼情況要報（報在哪一份上）
duplicate-number號碼跟別份重複（同號碼的每一份都報）
not-active-voicedecision 不是以「我們將」或「We will」開頭
no-negative-consequenceproposed 或 accepted，卻沒有 kind: 'negative' 的後果
superseded-without-linkstatus 是 superseded，卻沒有 supersededBy
dangling-linksupersededBy 指到不存在的號碼
supersede-backwardssupersededBy ≤ 自己的號碼（新的決定一定是較大的號碼）
link-not-mutualsupersededBy 指到的 ADR 存在，但它的 supersedes 沒有列出自己
conflicting-accepted同一個 topic 有兩份以上 accepted：號碼最小的以外都報

練習 3：起始程式是「預約取餐時段」設計文件的草稿 pickupSlotsDoc，和已經寫好的審查規則 reviewDoc。先按「執行」看它被挑出哪些問題，再修改 pickupSlotsDoc（不要改 reviewDoc 和 assumptions），讓審查回傳 []：

  • 至少一個非目標。
  • peakBookingsPerSec = dau × ordersPerUserPerDay × slotShare × peakShare ÷ (peakHours × 3,600)，誤差 0.01 以內。
  • 每個 hard 依賴都有 failureBehavior：它壞掉時預約會怎樣、使用者看到什麼。
  • 至少 2 個替代方案，每個不選的理由（whyNot）至少 8 個字；要包含原本的做法 Redis 鎖。
  • 每個上線步驟都有 rollback，不可逆的步驟都在最後，至少一個步驟用功能旗標（flag）。調整順序，不要刪掉步驟。

練習 4：咖啡店決定把時段名額從 Redis 鎖改成 PostgreSQL 條件更新。起始程式是目前的 ADR 紀錄 adrLog（1～6 號）。請：

  • 新增 7 號：title 是「時段名額改用 PostgreSQL 條件更新」、topic 是 'slot-booking'、status 是 'accepted'、decision 以「我們將」開頭並提到「條件更新」、至少一個負面後果、supersedes: [3]。
  • 把 3 號改成 status: 'superseded'、supersededBy: 7。3 號的其他內容不要改，也不要刪掉它。

測試會用練習 2 的規則檢查整份紀錄。

練習 5：一份設計文件的「替代方案」段落只寫了「什麼都不做：維持現狀」。審查者該怎麼回應？

✓ 替代方案是審查者判斷「作者有沒有想清楚」的地方：沒有比較，就看不出提案為什麼比較好。a 把它當形式；b 的總分本身就是跟其他方案比出來的，沒有其他方案就沒有意義。只放一個很差的方案來襯托（稻草人）也一樣不行。

練習 6：「在菜單 API 前面加一層 Redis 快取」和「把訂單資料庫從 PostgreSQL 換成另一種資料庫」，哪個比較像單向門？

✓ 快取拿掉就回到原樣，是雙向門，可以快速試；換資料庫牽涉資料搬遷、所有查詢與維運知識，是單向門，值得寫設計文件並審查。c 正是 Amazon 提醒的問題：把單向門的流程套到每個決定上，團隊會慢到不敢實驗。

練習 7：設計審查時，兩位資深工程師各自用過去的經驗堅持不同的做法，僵持不下。最好的做法是？

✓ 技術事實與資料優先於意見；把爭論轉成可以量的問題，往往半天的原型就能回答。b 和 d 用資歷或人數取代證據，錯了也不知道錯在哪；c 讓成本加倍，而且兩套都要維運。

練習 8：ADR 3 的決定被推翻了，新的決定寫成 ADR 7。ADR 3 該怎麼處理？

✓ 「當時為什麼這樣選、後來為什麼改」本身就是價值：之後有人想改回 Redis 鎖，讀到 ADR 3 和 7 就知道會遇到什麼。a 讓歷史消失；b 讓人以為當初就是這樣決定的，還讓引用「ADR 3」的舊 PR 和註解指到不同的內容。狀態和連結已經能防止有人照舊的做。

常見錯誤

  • 把設計文件寫成實作手冊：只有步驟沒有取捨，審查者沒東西可以判斷。沒有取捨的事直接寫程式。
  • 沒有非目標：範圍一直長大，審查也抓不到重點。把「合理但這次不做」的事寫出來。
  • 沒有數字：「高流量」「很慢」沒辦法判斷設計夠不夠。照第 2 課寫假設、計算和何時重算，而且用尖峰不用平均。
  • 替代方案是稻草人：故意寫很差的方案來襯托提案。要寫真正考慮過的方案，包含「維持現狀」的真實樣貌。
  • 只描述一切順利的情況：沒有故障模式、沒有回滾計畫。每個硬相依都要寫壞掉時的行為，不可逆的步驟放最後。
  • 決策矩陣的假精確：把主觀分數算到小數點、用 2% 的差距下結論。做敏感度檢查，結論取決於某個權重時要寫出來。
  • ADR 被推翻時直接改寫或刪除：失去「當時為什麼這樣選」。保留舊的、標記 superseded、雙向連結。
  • ADR 只寫好處：沒有負面後果，讀的人不知道要注意什麼。每個決定都有代價，寫出來。
  • 文件寫完就不再更新：實作改了文件沒改，比沒有文件更誤導。改了做法就改文件或補一份補充文件。
  • 審查變成比資歷或挑語病：聚焦在風險與證據，爭論轉成可以驗證的問題，由決策者收斂並寫回文件。

小結

  • 會議沒有結論，是因為缺了當初的理由、被否決過的方案、大家對著同一份提案。設計文件在動手前取得共識，ADR 在決定後留下理由。
  • 有取捨、做錯難退回的決定才寫設計文件；答案明確的事直接做，在 PR 描述寫清楚。單向門慢慢決定、寫文件審查，雙向門快速決定；盡量把單向門拆成可以退回的小步。小改動寫 1～3 頁就好，摘要放最前面。
  • 設計文件每一段回答審查者一個問題：背景與範圍、目標與非目標、假設與估算（用尖峰不用平均）、提案設計（脈絡圖分硬相依與軟相依、API、資料）、故障模式、上線與回滾（不可逆的步驟放最後）、跨領域考量、開放問題、替代方案（不能是稻草人）。
  • 決策矩陣是輔助：先定標準和權重再打分；權重就是判斷，一次改一個權重 ±20% 看贏家會不會換，會換就寫出來；分數差距小就是平手，回頭找能量測的事實。
  • ADR 一個決定一份：標題、背景、決策（我們將……）、狀態、後果（含負面）。編號不重複；被推翻時保留舊的、標記 superseded、雙向連結；放在 repo，程式註解與 PR 連過去。
  • 審查問：可量測嗎、數字從哪來、哪裡會壞、怎麼回滾、怎麼監控、多少錢。事實與資料優先於意見，驗證不了的由事先講好的決策者決定，結論寫回文件；實作改了就更新文件，上線後補「學到什麼」。
