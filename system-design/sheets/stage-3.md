網路會掉、下游會慢、程序會暫停。每個呼叫都要有逾時，重試要有節制，重複一定會發生，所以處理端要冪等；跨系統沒有恰好一次，也沒有一個交易包得住全部。[回 系統設計 學習地圖](../index.html)

## A 逾時與 deadline 傳遞 {span=2}
```flow LR
(App 期限 1,000ms) -> [API 閘道]
[API 閘道] -> [訂單服務：用掉 300ms]: 傳剩餘時間
[訂單服務：用掉 300ms] -> *[呼叫金流：逾時 650ms]: 再扣餘裕 50ms
```
- 每個網路呼叫都要有逾時，包含資料庫、Redis、內部服務。慢比掛掉更危險：資源被一點一點吃光。
- 依可接受的誤判比例選下游延遲的百分位數：接受 0.1% 誤判就用 p99.9。
- 每一層傳下去的是剩餘時間；時間不夠就不要開始。每次嘗試的逾時取單次逾時與剩餘時間的較小值。

## B 該不該重試、隔多久
| 失敗 | 重試？ |
|---|---|
| 呼叫端自己取消 | no 不重試，也不記成錯誤 |
| 逾時、連線失敗、408、500、502、503、504 | ok 方法冪等或有冪等鍵時 |
| 429 | ok 照 `Retry-After` 等 |
| 400、401、403、404、409、422 | no 請求本身的問題 |
| 501 | no 伺服器不支援這個方法，再試也一樣 |

指數退避一定要加 jitter（full、equal、decorrelated 都能錯開）。等待取 max(退避, Retry-After)，超過期限就放棄。多層重試會相乘（每層 3 次 → 27 倍）：只在一層重試，並用重試預算在大面積失敗時自動停止。

## C 冪等：重試也不會重複扣款 {span=2}
```sequence
participants: App, 訂單服務, 金流
App -> 訂單服務: POST /orders，Idempotency-Key k1
訂單服務 -> 金流: 扣款，帶由 k1 衍生的冪等鍵
訂單服務 --> App: 回應遺失，App 逾時
App -> 訂單服務: 重試，同一把 k1
note 訂單服務: 認出 k1 已完成，回傳存下的回應
```
| 同一把 key 的情況 | IETF 草案 -08 建議（還不是 RFC） |
|---|---|
| 端點要求 key，請求沒帶 | 400 |
| 第一次還在處理中 | 409 |
| 內容不同（請求指紋不符） | 422 |

先讓操作本身冪等：絕對值取代增量、條件更新、唯一約束與 `ON CONFLICT DO NOTHING`。key 一個意圖一把、限定在使用者範圍、存在共用的資料庫；指紋用正規化 JSON 加 SHA-256。跨外部服務的請求切成原子階段，每個交易同時更新復原點。

## D 限流：保護自己，也保護其他客戶
| 演算法 | 特性 |
|---|---|
| 固定視窗 | warn 交界處可達兩倍 |
| 滑動視窗紀錄 | ok 精確，但耗記憶體 |
| 滑動視窗計數 | ok 只存兩個數字，誤差很小 |
| token bucket | ok 容量是突發、補充速率是平均；用時間差和小數補充 |

多層由外到內，先檢查客戶再扣全站；每個 key 的狀態要有上限。被限流回 429 加 `Retry-After`（整數秒、無條件進位），整體過載回 503。多台伺服器要集中、原子地計數；限流器壞掉時 API 限流通常 fail open 並告警。

## E 斷路器、隔艙與負載卸除 {span=2}
```flow LR
(closed) -> open: 最少呼叫數達到且失敗率達到門檻
open -> [half-open]: 經過開啟時間
[half-open] -> closed: 試探都成功
[half-open] -> open: 任何一個失敗
```
```flow LR
[並行上限（隔艙）] -> 總逾時 -> 重試 -> *斷路器 -> 單次逾時
```
- 連鎖故障常從依賴「變慢」開始：L = λW，W 變大就佔滿共用資源。
- 斷路器每個依賴一個；4xx（408、429 除外）不算失敗；`BreakerOpenError` 不重試。重試要在斷路器外面，斷路器才看得到每次嘗試。
- 隔艙大小用 Little's Law 算、佇列上限設小、名額在 `finally` 歸還。
- 過載時佇列要有上限、開始前檢查 deadline、依重要性卸除，健康檢查最優先，拒絕要便宜並回 503。
- 客戶端自適應節流：p = max(0, (requests − K × accepts) ÷ (requests + 1))，K = 2 時後端拒絕超過一半才在本機丟。
- 降級做少一點但不要全掛；備援不能掩蓋錢和權限的錯誤。用故障注入確認它們真的會動。

## F 佇列與 outbox：至少一次＋冪等
```flow TB
[結帳交易：INSERT orders 與 outbox] -> relay: 只送已提交的列
relay -> [(broker)]: 先送出，再標記
[(broker)] -> [消費者 inbox]: 可能重送
[消費者 inbox] -> *[訊息 id 唯一約束＋副作用同一個交易]
```
| ack 時機 | 語意 |
|---|---|
| 先 ack 再處理 | warn 至多一次：可能遺失 |
| 先處理再 ack | ok 至少一次：可能重複，消費者要冪等 |

visibility timeout 是租約，只有最新的 receipt 能 ack；超過最多接收次數移到 DLQ，DLQ 要告警。順序只在同一個分區或群組內成立，用訂單 id 當 key。監控最老訊息的年齡。

## G Saga：各自提交加上補償 {span=2}
```flow LR
[建立訂單] -> [預留庫存] -> *[扣款 pivot] -> [確認訂單] -> [廚房出單] -> [集點]
[預留庫存] --> [釋放預留]: 扣款失敗時反向補償
[建立訂單] --> [訂單改成 cancelled]
```
可補償的在前、pivot 一個、可重試的在後；不可逆的步驟放在所有驗證之後。補償是語意上的抵銷，不是回滾：釋放庫存寫成「加回」。協調者每步寫紀錄、先重試再補償、補償有重試上限、用盡就 stuck 交給人；當機後依紀錄續跑，冪等鍵讓重做也安全。Choreography 沒有協調者，但流程分散、難追蹤，適合簡單流程。

```callout warn 逾時是結果未知
不能直接補償，用同一把冪等鍵確認結果。saga 沒有隔離：用 semantic lock、交換律更新、重新讀取處理。每天對帳是最後一道保險；同一個資料庫內不需要 saga。
```

## H 分散式鎖、租約與 fencing token
先問需不需要鎖：唯一約束、條件更新、依 key 分區常常更好。鎖失效只是多做的叫效率鎖，會弄壞資料的叫正確性鎖。

```sequence
participants: api-1, 鎖服務, api-2, 儲存
鎖服務 --> api-1: 租約，token 33
note api-1: GC 暫停，租約到期
鎖服務 --> api-2: 租約，token 34
api-2 -> 儲存: 寫入，帶 34
api-1 -> 儲存: 醒來寫入，帶 33
儲存 --> api-1: 拒絕：看過 34
```
「寫入前先檢查租約」擋不住暫停。token 由鎖服務遞增產生，資源端原子地檢查。釋放鎖要值相符才刪；量間隔用單調時鐘。Redlock 沒有 fencing，效率鎖用單一 Redis 就夠。Leader election 也用租約：每 1/3 租約續約、續約失敗立刻退位，寫入仍帶 fencing token。
