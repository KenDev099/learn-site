拆服務不是升級，是用一組問題換另一組問題，所以預設模組化單體。事件要假設重複與亂序；推送只是通知，狀態以 API 為準。[回 系統設計 學習地圖](../index.html)

## A 三種形狀：差在邊界上的呼叫方式 {span=2}
| | 單體 | 模組化單體 | 微服務 |
|---|---|---|---|
| 部署 | 一起 | 一起 | 各自 |
| 模組之間 | 函式呼叫 | 函式呼叫或程序內事件 | 網路呼叫，會逾時、會部分失敗 |
| 跨模組交易 | 一個資料庫交易 | 一個資料庫交易 | 沒有，要用 saga |
| 擴展 | 整個一起 | 整個一起 | 只擴展需要的服務 |

```callout ok 預設選模組化單體（MonolithFirst）
出現擴展需求差很多、變動頻率差很多、團隊互相卡住、法規隔離這些訊號才拆，用 strangler fig 一塊一塊拆。依業務能力與限界上下文畫邊界，每張表只有一個擁有者，共用資料庫是反模式。Conway 定律：畫服務邊界時一起畫團隊邊界。
```

## B 拆開的代價
```flow LR
*[下單 API] -> catalog & inventory & payment & loyalty: 依序同步呼叫
*[下單 API] --> notification: 經佇列，非同步
```
同步依賴的可用性相乘、延遲相加：課文的例子 5 個 99.9% 串聯是 99.50%。非同步的依賴不在請求的可用性路徑上。

分散式單體的徵兆：一起部署、聊天式同步呼叫、共用資料庫、共用領域模型套件。從 git 歷史量共同變更耦合，找出畫錯的邊界；它是證據，不是判決。

## C 跨服務查詢
| 做法 | 新鮮度 | 可用性 |
|---|---|---|
| API composition | ok 即時 | warn 每個必要的服務都要活著 |
| 事件複製的唯讀資料 | warn 晚幾秒到幾分鐘 | ok 只要自己活著 |

API composition：必要的失敗就失敗；選用的加短逾時，失敗就降級，回應標出哪一塊沒拿到。

## D 命令、事件、查詢
| 種類 | 能被拒絕 | 格式誰決定 |
|---|---|---|
| 命令 `PlaceOrder` | ok 可以 | 接收者 |
| 事件 `OrderPaid`（過去式） | no 已經發生 | 發布者 |
| 查詢 `GetOrder` | 只會查不到 | 接收者 |

偽裝成事件的命令（`SendReceiptEmail`）不會減少耦合。薄事件契約小但要回查；胖事件不用回查但契約大、會散播個資；事件溯源只在需要完整歷史時才值得。

## E 消費者假設重複與亂序 {span=2}
```flow LR
(收到事件) -> {ID 看過了?}
{ID 看過了?} -> [略過並 ack]: 是
{ID 看過了?} -> {序號比較}: 否
{序號比較} -> [丟掉]: 小於等於已套用
{序號比較} -> *[套用到投影]: 剛好下一號
{序號比較} -> [暫存，等缺號]: 跳號
```
事件要有唯一 ID 與來源（CloudEvents 1.0：`id`、`source`、`specversion`、`type`），再加上聚合 ID 與序號。不用 `time` 排序：時間來自不同機器的時鐘。暫存要有上限與逾時。投影可以重播重建，UI 要呈現最終一致的落差。

## F 送出 webhook
```kv cols=1
webhook-id: 重送時不變，接收端靠它去重
簽章: 每次嘗試用當下的時間重新簽
成功: 只有 2xx；3xx 也算失敗，不跟隨轉址
410: 停用端點
重試: 跨多天的指數退避加 jitter，尊重 Retry-After
隔離: 每個端點各自的佇列，防 SSRF，提供重播
```
事件從 outbox 開始送。需要立刻知道結果的（付款授權）用同步命令；流程長到看不見時改用 orchestration。

## G 四種推送方式 {span=2}
| 做法 | 適合 |
|---|---|
| 短輪詢 | warn 成本是「客戶端數 ÷ 間隔」，跟事件數無關 |
| 長輪詢 | warn 環境不允許長連線時的退路 |
| SSE | ok 單向狀態更新；就是 HTTP，內建重連與 `Last-Event-ID` |
| WebSocket | warn 雙向、頻繁互動才用；確認、重送、重連都要自己設計 |

客戶端多、要即時、變化少時才值得推送，代價是很多條長連線。SSE 解析：三種行尾、空行送出、冒號開頭是註解、只去掉一個空白、`id` 會沿用、`retry` 只收數字；資料會在任何位置被切開，要累積緩衝並處理被切開的 CRLF。長連線上的身分會到期，到期就關掉連線。

## H 斷線續傳與多台扇出
```flow LR
[訂單 API A 機] -> [Redis pub/sub]: 至多一次
[Redis pub/sub] -> [SSE 伺服器 B 機]
[SSE 伺服器 B 機] -> *[每條連線一個有上限的送出佇列]
```
- 每個頻道保留最近 N 個事件，依 `Last-Event-ID` 補送；補不了、id 不合法或比最新的還大就 reset，客戶端重新拿完整狀態。套用事件要冪等。
- 發布不等任何人；佇列滿的慢消費者直接斷線，讓它重連補資料。
- 關掉代理緩衝、心跳比閒置逾時短、HTTP/1.1 每個網域 6 條上限、調高檔案描述子上限、最少連線負載平衡。
- 部署時分批排空，重連加 jitter，續傳緩衝不能只放在要被關掉的程序裡。
