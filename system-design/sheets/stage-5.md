## A 設計文件：動手前找出問題 {span=2}
```flow LR
[背景與範圍] -> [目標與非目標] -> [假設與估算] -> *[提案設計] -> [故障模式]
[故障模式] -> [替代方案] -> [跨領域考量] -> [上線與回滾] -> [開放問題]
```
答案明確、沒有取捨時不用寫；小改動寫 1～3 頁，摘要放最前面。提案設計含脈絡圖（硬相依、軟相依）、API、資料，只寫到能討論的程度。

| 審查時問 | 例子 |
|---|---|
| 可量測嗎 | 「要快」→ 在多少負載下 p99 多少 |
| 數字從哪來 | DAU、尖峰佔比的來源 |
| 哪裡會壞、怎麼回滾、怎麼監控、多少錢 | 每個硬相依壞掉時使用者看到什麼 |

事實與資料優先於意見；驗證不了的由事先講好的決策者決定，結論寫回文件。

## B 決策矩陣、單向門與 ADR
- 決策矩陣是輔助：權重就是判斷。一次改一個權重 ±20% 看贏家會不會換，會換就寫出來；分數接近就是平手。
- 單向門慢慢決定、寫文件審查；雙向門快速決定。盡量把單向門拆成可以退回的小步，不可逆的步驟放最後。

```kv cols=1
標題: 帶編號，例如「ADR 7：時段名額改用 PostgreSQL 條件更新」
背景: 當時有哪些力量在拉扯
決策: 「我們將……」，不寫「建議」
狀態: proposed、accepted；之後可能 deprecated 或 superseded
後果: 正面、負面、中性都要寫
```
編號不重複；被推翻時保留舊的、標記 superseded、雙向連結；放在 repo。

## C 相容性：看資料流動的方向 {span=2}
| 改動 | 相容嗎 |
|---|---|
| 請求加選填欄位、放寬限制 | ok 相容 |
| 請求加必填欄位 | no 舊客戶端收到 400 |
| 回應加新欄位 | ok 對寬容的讀取端相容 |
| 回應刪掉或改名欄位 | no 讀到 `undefined` |
| 列舉多一個值 | warn 看讀取端有沒有處理未知值 |
| 改型別、改單位 | no 格式一樣也可能語意不同 |

```flow LR
(expand：total 與 amount 並存) -> [migrate：量測還在讀 total 的客戶端] -> *[contract：用量是 0 才移除 total]
```
Hyrum 定律：使用者夠多時，所有可觀察的行為都會被依賴。寬容讀取端只讀需要的、忽略不認得的、未知列舉有預設；對違反規格的資料不寬容（RFC 9413）。讀取端先部署，寫入端後開始送。OpenAPI 比對抓結構，契約測試抓呼叫端實際依賴的行為。

## D 版本、功能旗標與 strangler fig
- 版本：URI、標頭或日期版本；程式只維護最新版，舊版用由新到舊的轉換鏈產生。舊版退場先量、再用 `Deprecation`（RFC 9745）與 `Sunset`（RFC 8594）通知、最後才關。
- 功能旗標把部署和發布分開。分桶用「旗標 key ＋ 使用者 ID」的雜湊：結果穩定、放量只加人、不同旗標選到不同的人。kill switch 讓降級變成一鍵操作；旗標要有到期日和移除計畫。

```flow LR
App -> 閘道: 切換點
閘道 -> [舊單體]: 80% 訂單
閘道 -> *[新訂單服務]: 20% 訂單
閘道 --> *[新訂單服務]: 影子流量，只比對
```
影子流量不等、不影響回應、關掉副作用。雙寫、回填、比對，再分桶逐步切換，最後移除舊路徑與過渡架構；每一步都確認退路還在。

## E Code review：先看最難補救的
```flow BT
[設計與正確性] -> 安全 -> 可維運性 -> 測試 -> 可讀性 -> [風格：交給工具]
```
明確改善整體健康就核准，沒有完美的程式碼；一個工作天內回覆，太大的 PR 請作者拆。用 Conventional Comments 分輕重：`issue (blocking)`、`nitpick (non-blocking)`、`praise`。

```callout warn 後端高風險寫法
- 先讀再寫、缺冪等、交易裡呼叫外部 API
- N+1、沒有上限的查詢、吞掉錯誤
- log 出個資、快取 key 漏掉使用者
- 重試沒退避、金額用浮點數
```
好的 PR 小而單一目的，寫出為什麼、做了什麼、怎麼驗證、風險、怎麼回滾。

## F 技術債：用利息排順序
每月利息 ＝ 每次修改多花的時間 × 每月修改次數；回本月數 ＝ 償還時間 ÷ 每月利息。依利息、風險與成本排序，先處理改得多又複雜的熱點；很亂但沒人改的利息是 0。會造成事故的債不看回本，排最前面。小步償還，不要輕易重寫。

```callout info 特徵測試
重構沒有測試的程式前，先記錄它現在實際的輸出（包括怪行為），小步改、每步比對；疑似 bug 另開一個 PR 修。
```

## G 除錯：用實驗排除假設 {span=2}
```flow LR
(觀察) -> 假設 -> 實驗 -> 記錄
記錄 --> 假設: 負面結果也寫下
記錄 -> *[只剩一個原因：修正並留下回歸測試]
```
- 先問最近改了什麼，先想常見原因，一次只改一件事。先穩定重現再修；重現不了就先加觀測（canonical log line）。
- 二分法：`git bisect run` 的結束碼 0 是好、1～127（125 除外）是壞、125 跳過；被跳過的版本緊鄰答案時，結果是一個範圍。輸入用 ddmin 或逐一移除縮到 1-minimal。
- 從 trace 找根因：找「帶錯誤、後代都沒有錯誤」的 span；只是慢時看自身耗時，子 span 先裁切、再合併重疊。相關不等於因果。
- 非確定性的 bug：把時間、亂數、交錯順序變成參數，用 deferred 讓它每次都失敗。

## H 線上事故：先止血，再找原因
| 止血手段 | 適合 |
|---|---|
| 回滾 | 問題在最近一次部署之後 |
| 關功能旗標 | 跟某個新功能有關 |
| 導流 | 只有某一區、某幾台有問題 |
| 擴容 | 流量真的超過容量 |
| 卸載、降級 | 撐不住全部的請求 |

止血時保留證據。及早宣告，分出指揮、操作、溝通三個角色並固定頻率更新。事後不究責地檢討，補上回歸測試、告警和 runbook。
