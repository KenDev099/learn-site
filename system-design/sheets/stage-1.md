系統設計是在限制下做取捨並寫下理由：先把形容詞換成可量測的目標，再用估算與量測得到的數字做決定。[回 系統設計 學習地圖](../index.html)

## A 設計的固定步驟 {span=2}
```flow LR
(釐清需求) -> 估算 -> [API 與資料] -> 高階架構 -> 深入瓶頸 -> 取捨與風險 -> *寫成文件
估算 --> 釐清需求: 發現做不到，回去跟 PM 談
```
先問清楚、先算，再畫架構；一開始就畫負載平衡器、Redis、Kafka，沒有數字就無法判斷好壞。限制（人力、上線日期、既有技術、預算）和需求一樣是設計的輸入。YAGNI：為看得到的成長設計，並寫下到什麼數字要走下一步。

## B 形容詞改成可量測的目標
| 模糊的說法 | 可量測的目標（第 1 課例子） |
|---|---|
| 下單要快 | 尖峰時段，下單 API 的 p99 小於 300ms |
| 不能掛 | 以 30 天為單位，可用性 99.9% |
| 不能錯帳 | 同一張訂單最多扣款 1 次 |
| 集點晚一點沒關係 | 付款成功後 60 秒內入帳 |

非功能需求寫成百分位數、負載條件、統計區間和數字。

## C 延遲怎麼加、瓶頸在哪
```flow LR
(驗證 token 5ms) -> [查菜單 20ms] & *[查會員 30ms]
[查菜單 20ms] -> [寫訂單 15ms]
*[查會員 30ms] -> [寫訂單 15ms]
```
依序相加、平行取最大：5 ＋ max(20, 30) ＋ 15 ＝ 50ms。只有關鍵路徑上的優化會讓總延遲變短。

瓶頸 = 容量 ÷ 放大係數（依請求組合加權）最小的元件。這課的示範：90% 看菜單打資料庫 0.1 次、10% 下單打 8 次，資料庫只撐約 2,247 req/s，比 API 的 3,000 小，加 API 機器沒有用。

## D 流量：從每天到尖峰每秒 {span=2}
```flow LR
[DAU 20 萬 × 0.3 筆] -> [每天 6 萬筆]: 每日總量
[每天 6 萬筆] -> [平均約 0.69 筆每秒]: ÷ 86,400
[每天 6 萬筆] -> *[尖峰約 3.33 筆每秒]: × 40% ÷ 7,200 秒
*[尖峰約 3.33 筆每秒] -> [週年慶約 66.7 筆每秒]: × 20
```
數字來自課程情境卡。容量照尖峰規劃，不照平均；推播造成的瞬間尖峰要用「幾分鐘」去除。估算追求數量級，每個假設都寫出來。

## E 儲存、頻寬、台數、連線
```kv cols=1
儲存: 單筆 × 筆數 × 天數 × 副本 ×（1 ＋ 索引負擔）；備份、WAL、log 另列。第 2 課示範（2 份副本、索引 30%）：情境卡 5 年約 284.7 GB
單位: KB 是 1,000 bytes、KiB 是 1,024 bytes；課程估算一律用十進位
頻寬: bytes × 8 ＝ bits；頻寬看尖峰，費用看總量
台數: ceil(尖峰 ÷ (單台實測 × 目標使用率)) ＋ 備援；單台容量要壓測，不要猜
連線: 台數 × pool ≤ max_connections − 保留的連線
```

```callout info 敏感度分析
一次只改一個假設，找出會讓結論翻轉的那幾個，寫成「何時重算」的觸發條件。格式：假設＋計算＋結論＋何時重算。
```

## F Little's Law 與百分位數 {span=2}
$$ L = \lambda \times W $$
並行數 ＝ 每秒到達數 × 每個停留的秒數。用來算並行數、連線池大小、某個 pool 能撐的上限；延遲要先換成秒。加機器提高吞吐量，不會讓單一請求變快。

| 做法 | 結果 |
|---|---|
| 平均延遲 | no 把少數等很久的人藏起來 |
| nearest-rank 百分位數 | ok 排序後取第 ceil(p × n ÷ 100) 個；先乘再除 |
| 各台 p99 取平均 | no 沒有意義 |
| histogram 合併計數再算 | ok 桶內線性內插，誤差在一個桶寬內 |

SLO 門檻要剛好是桶邊界。扇出越多，越多使用者碰到尾延遲。

## G 使用率與排隊
使用率越接近 100%，排隊時間越暴增（M/M/1 模型只看形狀），所以要留餘裕，過載時卸除負載。

```callout warn hedged request（選讀）
扇出很大、尾延遲已是瓶頸時才需要，跳過不影響後面的課。超過 p95 還沒回應才送第二次給另一台副本，用先成功的、取消另一個和計時器。只用在可以重複執行的讀取；寫入送兩次就是兩張訂單。
```

## H 怎麼量才對
| 壓測模型 | 結果 |
|---|---|
| 封閉：固定 N 條連線，等回應才送下一個 | no 卡住期間的請求沒被量到（coordinated omission，選讀） |
| 開放：固定到達率 | ok 接近真實使用者 |

先暖機、條件接近正式環境、依路由分開看；逐步加壓，p99 還在目標內的最大吞吐量才是單台容量，回填到台數公式。
