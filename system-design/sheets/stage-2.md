每一種擴展都在解一個瓶頸、同時帶來新問題：冗餘要跨故障域，快取會過時，副本會落後，分片很難回頭。先用便宜、可以回頭的方法，有數字證明不夠再往下走。[回 系統設計 學習地圖](../index.html)

## A 可用性的算術 {span=2}
| 可用性 | 每 30 天最多停機 |
|---|---|
| 99.9% | 43.2 分鐘 |
| 99.99% | 4.32 分鐘 |

```kv cols=1
串聯的硬相依: 可用性相乘，比任何一個都低
獨立的冗餘: 1 − 各自不可用率的乘積
軟相依: 壞了有備援，不拉低可用性；改成軟相依常比加機器便宜
MTBF 與 MTTR: 可用性 ≈ MTBF ÷ (MTBF ＋ MTTR)，縮短修復時間跟減少故障一樣有效
```
以請求計算時，尖峰的停機特別貴。冗餘公式假設獨立：要跨故障域（主機、可用區），並提防相關性故障（同一個部署、同一份設定、同一張過期憑證）。容量以「掉一個可用區之後」的使用率規劃。

## B 負載平衡怎麼挑機器
| 演算法 | 狀態 |
|---|---|
| round robin | warn 請求長短差很多時不平均 |
| 每次選全域最閒的 | no 資訊過時，多台負載平衡器一起湧向同一台（羊群效應） |
| P2C：隨機挑兩台選比較閒的 | ok 大多數情況的好預設；Envoy 的 least request 預設就是它 |
| 一致性雜湊 | warn 讓快取集中，但熱門 key 會讓單台過熱 |

異常剔除要有連續失敗門檻、逐次加長的剔除時間和最多剔除比例；liveness 不檢查依賴。負載平衡器本身也要冗餘。

## C 快取：命中率與讀寫策略
```kv cols=1
平均延遲: h × 命中延遲 ＋ (1 − h) × 未命中延遲
資料庫負載: (1 − h) × 讀取量；命中率 90% → 99%，資料庫負載變成十分之一
```
| 策略 | 狀態 |
|---|---|
| cache-aside 加 TTL | ok 最常用的組合 |
| write-behind | warn 快，但寫回前快取壞掉會遺失資料 |
| 訂單、付款、結帳時的價格與庫存 | no 不快取，讀資料庫 |

## D 失效：刪除，而且擋住舊值寫回 {span=2}
```sequence
participants: 讀取 A, 快取, 資料庫, 店長
讀取 A -> 快取: 未命中，拿到 lease 7
讀取 A -> 資料庫: 讀到 110
店長 -> 資料庫: 改成 120
店長 -> 快取: 刪除 price:2，lease 7 作廢
讀取 A -> 快取: 寫回 110（lease 7）
快取 --> 讀取 A: 拒絕
note 快取: 下一個未命中的讀取拿新票，寫回 120
```
寫入時刪除快取，不要更新：兩個更新交錯會留下比較慢的那個舊值。lease 每個 key 一段時間只發一張，也順便擋住擊穿。TTL 是最後的保險，不要永不過期。

## E 擊穿、雪崩與冷快取
| 問題 | 解法 |
|---|---|
| 熱門 key 過期，大家同時查資料庫（擊穿） | single-flight（只在同一程序內有效）；跨程序用 lease 或提早更新 |
| 大量 key 同時過期（雪崩） | TTL 加隨機 |
| 一直查不存在的資料 | 短 TTL 的負快取 |
| 不想讓人等未命中 | stale-while-revalidate 先回舊值、背景更新；XFetch 到期前以遞增機率提早更新 |

```callout warn 延遲型與容量型快取
拿掉只會變慢的是延遲型；拿掉資料庫就撐不住的是容量型。容量型快取壞掉或變冷時，要限制打到資料庫的並發、卸除負載、暖機。背景更新的錯誤要自己 `.catch`。
```

## F 複寫延遲與一致性 {span=2}
```flow LR
App -> *[(primary)]: 寫入
*[(primary)] -> [(replica A)] & [(replica B)]: 傳 WAL，replica 重播
App --> [(replica A)]: 讀取
```
| 異常 | 例子 |
|---|---|
| 讀不到自己剛寫的 | 下單後「我的訂單」沒有這筆 |
| 資料倒退 | 重新整理一次出現、再一次又不見 |
| 因果顛倒 | 收到「已付款」推播，畫面卻顯示待付款 |

修法：寫入後記下 LSN，讀取只選已重播到那裡的 replica，沒有就讀 primary；LSN 解析成 bigint 再比。同步複寫用延遲換不掉資料，同步 replica 壞掉時寫入會卡住；非同步快，但可能掉最後幾筆。

## G 一致性模型、Quorum 與 CAP
- 由強到弱：線性一致 → 因果 → 讀己之寫／單調讀 → 最終一致。每種讀取選夠用的最弱模型，寫下可以舊多久。
- Quorum（選讀）：R ＋ W ＞ N 讀寫一定重疊；讀到多個版本取最新、順便 read repair。
- CAP 只在網路分割時要選一致或可用，可以依操作選：付款、庫存選 C，菜單、推薦選 A。PACELC 補上平常的取捨：延遲與一致。
- 多個寫入點（選讀）：LWW 在時鐘偏移時會丟掉較新的寫入；版本向量分得出先後或並行，並行時合併（購物車取聯集）。能用單一 leader 就用單一 leader。

## H 分片：先別分，要分就選對鍵 {span=2}
```flow LR
[垂直擴充] -> 讀副本 -> 快取 -> [分割表與封存] -> [依功能拆庫] -> *分片
```
| 分配方式 | 狀態 |
|---|---|
| range | warn 範圍查詢快，新資料集中在最新一片 |
| hash | warn 打散不同的值，同一個值永遠在同一片 |
| hash % N | no 改變 N 時大部分 key 要搬 |
| 一致性雜湊＋虛擬節點 | ok 加一台只搬約 1/(N＋1)，可依容量加權 |

分片鍵從存取模式選：大部分查詢都帶、沒有熱點、一筆交易在同一片；用「單片查詢比例（依流量加權）」與「最熱的一片佔多少」量化。跨片查詢要平行、每片都取 limit 筆再合併，用 (時間, id) 當 cursor；延遲由最慢的一片決定。上線後看每一片各自的資料量、QPS 與延遲，不只看平均。

```callout info 全域唯一 ID
各片自動遞增會撞號。用 UUIDv7（RFC 9562，開頭是毫秒時間；PostgreSQL 18 有 `uuidv7()`）或 Snowflake（41／10／12 位元）。用 bigint 計算、JSON 用字串，處理序號用完與時鐘倒退。先用 PostgreSQL，有數字證明撐不住再加別種儲存。
```
