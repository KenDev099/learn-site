# 上線檢查清單：咖啡店客服助理

## 權限
- 模型只讀得到檢索到的官方文件（trust = official）與工具回傳的欄位（訂單編號、狀態、金額、品項），拿不到電話、Email、付款資料。
- 工具只有兩個查詢：get_my_orders、get_order。顧客身分只從登入的 session 來，input_schema 沒有顧客 id；查不到與不是你的訂單回同一句。
- 退款、改價、取消訂單不做成工具，模型只能請顧客找店員。
- API key 放在伺服器的環境變數，前端拿不到；只有後端呼叫模型。

## 預算
- 每天上限 30 美元（成本報告估計每天 500 則對話約 9 美元，留 3 倍空間）。
- 每位顧客每分鐘 5 次（TenantLimiter），一次 ask 最多 4 輪、20,000 token。
- 當天費用到 80% 發告警；到 100% 把功能旗標關掉，改成固定回覆，隔天自動恢復。

## 告警
- 每 5 分鐘的錯誤率超過 5%：通知值班工程師。
- p95 延遲超過 15 秒持續 10 分鐘：通知值班工程師。
- 轉店員（abstain）比例一天超過 40%，或拒答（refusal）超過 2%：通知負責這個功能的工程師，看是檢索還是 prompt 出問題。
- 當天費用超過預算 80%。

## 回退
- 功能旗標 AI_CHAT_ENABLED：關掉後端點回固定訊息「AI 客服暫停服務，請直接詢問店員」，前端照常運作，不用重新部署。
- 主要模型 529／逾時時，依第 14 課的 fallback 改用 Sonnet 5.5，再失敗就回固定訊息。
- 每次部署前跑 eval；新版本出問題時，用上一版的映像重新部署（prompt 與程式一起有版本號）。

## 資料保留
- 每次 ask 一筆 log：遮蔽後的問題、狀態、原因、sources、工具名稱、token、費用、延遲，保留一段時間。
- 不存完整的模型輸出與未遮蔽的問題；需要除錯時用 request id 對照。
- 顧客要求刪除資料時，依 customer id 刪除 log。

## 已知限制
- 只回答文件裡寫的東西；文件沒更新（例如臨時售完），助理就會答錯，要靠店員更新文件並重新匯入。
- 檢索在同義詞很多、問題很口語時可能找不到，會轉店員；recall@5 目前 0.8 以上，但只測了 6 題。
- prompt injection 只能降低機率：工具權限與輸出過濾限制了傷害範圍，但模型仍可能說出不恰當的話。
- 一次 ask 要等整個回答驗證完才送出，首字延遲比逐字串流長（約 3～8 秒）。
- eval 只有 20 題，每題 3 次；上線後要從真實對話補題目。

# ADR 001：知識庫用 PostgreSQL＋pgvector，查訂單用工具

## 背景
客服助理要根據門市文件回答（菜單、過敏原、營業時間、退款），也要能查登入顧客自己的訂單。文件只有幾十段，訂單資料已經在 PostgreSQL，團隊沒有維運其他資料庫的經驗。

## 決定
文件切塊後連同 embedding 存在既有的 PostgreSQL（pgvector＋pg_trgm 混合搜尋）；訂單不放進 prompt，做成兩個只讀的工具，由程式依 session 檢查擁有者。

## 考慮過的其他方案
- 專門的向量資料庫（例如 Pinecone）：多一套服務要維運、要同步資料、要另外處理權限；我們的資料量（幾十段）用 pgvector 就夠，交易與備份也跟訂單在一起。
- 把全部文件直接放進 system prompt 並快取：現在文件很少可以做到，但文件會變多，而且無法做「隔離某份文件」與引用驗證；之後文件少於 2 萬 token 時可以重新評估。
- 把顧客的訂單直接放進 prompt：每次都要查、會送出用不到的資料（多花 token、多一份外洩面），也容易把別人的資料放錯；工具只在需要時查，而且權限寫在程式裡。

## 後果
- 好處：只多一個 PostgreSQL 擴充套件，備份、權限、監控沿用現有的；權限檢查在程式裡，可以測試。
- 代價：要自己維護切塊、重新 embedding 與 HNSW 索引；資料量到百萬筆以上要再評估效能。
- 查訂單多一輪模型呼叫（約多 1～2 秒、多一次的 token 費用）。
