階段 4：RAG：讓模型根據你的資料回答 · 第 8 課

RAG 是什麼：切塊與 embedding

客服助理上線後，最常被問的不是價格，而是「起司蛋糕含堅果嗎」「除夕有開嗎」「飲料做錯了可以退嗎」。這些答案寫在一本 40 頁的門市手冊裡，模型沒看過這本手冊，只能猜；猜錯過敏原，後果比答錯價格嚴重得多。把整本手冊每次都塞進 prompt 可以解決一部分，但每個問題都要付 40 頁的 token 錢、等比較久，手冊越長，模型也越容易漏看中間那一句。

這一課學 RAG 的前半段：先把手冊切成一小塊一小塊，替每一塊算出一串代表「意思」的數字（embedding），問題進來時只挑最相近的幾塊給模型。練習都在頁面上用 TypeScript 完成，不需要 API key。

這課的路線：
  1. 模型不知道你的店、RAG 的兩個階段：整本手冊每次都塞進 prompt 有什麼問題，RAG 怎麼只挑相關的幾段給模型（開場問題的最小答案）。
  2. 切塊：手冊要怎麼切、切多大，才找得到答案，又記得住「這段出自哪一章」。
  3. embedding、相似度：文字怎麼變成一串數字，怎麼算兩段文字的意思有多接近。
  4. top-k、實務規則：怎麼從所有塊挑出最像的幾塊，資料多到什麼程度要換方法，上線前要記下哪些資訊。
這課會用到：
  • 第 1 課的 token 與 context window：計費和長度上限都用 token 算，送進去的每一段資料都要付錢。
  • TypeScript 課第 6 課的 Unicode：length 數的是 UTF-16 單位，emoji 佔兩個；要依字元切就先 Array.from(text)。
  • TypeScript 課第 2 課的參考與複製：sort 會改到原陣列，filter、map 會產生新陣列。

模型不知道你的店

模型的知識來自訓練資料，訓練完就固定了。你家咖啡店的過敏原、營業時間、退款規則不在裡面，就算在，價格明天也可能改。所以「根據我們的資料回答」只有一個辦法：每次請求都把需要的資料放進 prompt（第 4 課的 <menu> 就是這樣）。問題是放多少：

做法適合代價
整份資料放進 prompt資料小（例如菜單幾千 token）、很少變資料一大，每次請求都付全部的輸入費用、首字延遲變長；context 越長，模型越容易漏看中間的細節
RAG：只放相關的幾段資料大、常更新、要能指出答案出自哪裡多一套切塊、embedding、搜尋的程式；搜尋可能找錯或找不到
微調（fine-tuning）：用你的資料再訓練模型要改的是語氣、格式這類習慣訓練成本高、資料一改就要重訓，而且模型「記住」的事實無法指出出處，不適合會變的知識

RAG（retrieval-augmented generation，檢索增強生成）的意思是：先檢索（retrieval）出和問題相關的資料，再把它放進 prompt 讓模型根據這些資料產生回答。模型還是同一個，差別是它每次都拿到「這題的參考資料」。

資料小的時候不要急著上 RAG。菜單只有 2,000 token，整份放進 system 再開 prompt caching（第 13 課），重複的部分只收一小部分的價錢，又不會有「找錯段落」的問題。資料大到放不下、或每次全部送太貴，才換成 RAG。

RAG 的兩個階段

RAG 的工作分成兩段，在不同的時間執行：

  • 離線（文件改了才跑）：把文件切成小塊，每塊算一次 embedding，連同來源資訊存進資料庫。這一步花的錢和時間，跟問題數量無關。
  • 線上（每個問題都跑）：把問題也算成 embedding，找出最相近的幾塊，用第 4 課的方式包在標籤裡放進 prompt，請模型只根據它們回答，並說出用了哪幾塊。

RAG 的回答品質，上限就是「找到的那幾塊」：該找的沒找到，模型再強也只能說不知道或亂猜。所以這一課和下兩課的重點都在檢索，而不是 prompt 的措辭。

切塊：按結構切、控制長度、保留來源

切塊（chunking）是把長文件切成適合檢索的小段，每一段叫一個塊（chunk）。檢索的單位是塊：找到哪一塊，模型就看到哪一塊。切法決定了能不能找對：

  • 塊太大（例如整本手冊一塊）：一塊裡有營業時間、過敏原、退款規則，它的 embedding 是這些主題的「平均」，跟「起司蛋糕含堅果嗎」的相似度被其他內容稀釋，反而比不上一塊剛好在講甜點的段落；而且一找到就把整大塊塞進 prompt，浪費 token。
  • 塊太小（例如一句一塊）：「它含堅果」這句被單獨切出來，「它」是誰已經不知道了；「週末 08:00 開門」跟標題「營業時間」分開，也找不太到。

實務上的起點是三個規則：

  1. 先按文件結構切。Markdown 的標題本來就把主題分好了：每個 #、##、### 底下是一節。每一塊記下它的標題路徑，例如 門市手冊 › 過敏原 › 蛋糕。
  2. 一節太長才再切，而且盡量切在換行的地方，段落、清單的每一項、表格的一列都不會被切斷；找不到換行才在長度上限硬切。用固定字數一路硬切，句子和表格會被切成兩半。
  3. 相鄰的塊重疊一小段。重疊（overlap）是指下一塊的開頭重複上一塊結尾的幾個字，這樣剛好落在切點附近的句子，至少在其中一塊是完整的。

每一塊還要帶著 metadata（描述資料的資料）：來自哪份文件（docId）、標題路徑、在文件裡的順序（seq），之後還會加上更新時間、用哪個 embedding 模型算的。沒有 metadata，你就沒辦法「只搜過敏原文件」、沒辦法告訴顧客答案出自哪裡，文件改版時也不知道要換掉哪些塊。

長度要用字元算，不能用 string.length。TypeScript 課第 6 課講過，length 數的是 UTF-16 的單位，emoji 這類字元佔兩個單位，用 slice 切在中間就會切出半個字：

半個字元送去算 embedding 或放進 prompt，會變成亂碼（常見的是 �，顯示成 �）。所以切塊時一律先 Array.from(text)，用字元陣列算長度、切位置，再 join('') 接回字串。

長度上限要設多少沒有標準答案。上限是用字元還是 token 計都可以，重點是一致；切好後用一組固定的問題（第 11 課的 eval）比較不同切法找到正確段落的比例，再決定。這一課的練習用很小的上限（30 個字元），只是為了讓你看得到切點。

還有一個常用的小技巧：算 embedding 時，把標題路徑接在內容前面，例如 過敏原 › 蛋糕\n起司蛋糕含蛋、奶、小麥，不含堅果。。內容裡沒寫「過敏」兩個字，搜尋「過敏原」時也找得到它。練習 3 的資料就是這樣算的。

💡 實務上：切塊程式是資料管線，不是一次性腳本
門市手冊、FAQ、退款規則會一直改版，切塊程式每次改版都要重跑，所以它要跟其他程式一樣有測試、可以重複執行、同一份文件切出來的結果每次一樣。真實文件常比練習亂：PDF 轉出來沒有標題、表格變成一堆空白、同一段話在三份文件裡重複。資深工程師接手 RAG 時，第一件事通常是把切好的塊印出來一塊一塊看，而不是先調模型；找不到答案的問題，很多是切塊時就已經把答案切壞或弄丟了。

embedding：把文字變成一個位置

向量（vector）就是一串固定長度的數字，例如 [0.12, -0.03, 0.88, …]，長度叫維度。embedding 是一個把文字轉成向量的模型，也指它產生的那個向量。可以把它想成地圖：每段文字被放在一個位置上，意思相近的文字，位置也相近。「拿鐵多少錢」和「拿鐵的價格」會落在很近的地方，「退款規則」在很遠的地方。地圖不是二維的，而是幾百到幾千維，你不需要知道每一維代表什麼，只需要會比較兩個位置有多近。

真實的 embedding 模型是另外訓練的神經網路，懂得同義詞與語意。Anthropic 沒有自己的 embedding 模型，官方文件推薦 Voyage AI（2026-11-01 查詢）：通用的 voyage-4 預設輸出 1024 維（可選 256、512、2048），每一段輸入文字最長 32,000 token（context length；一次請求裡所有文字加總另有上限）；另有品質最好的 voyage-4-large 與最便宜、最快的 voyage-4-lite。在 Node 裡呼叫它長這樣（第 9 課的 live.ts 會用到，這一課不用執行）：

// 離線：替每一塊算 embedding（input_type 是 'document'）
const res = await fetch('https://ai.mongodb.com/v1/embeddings', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${process.env.VOYAGE_API_KEY}` },
  body: JSON.stringify({
    input: ['過敏原 › 蛋糕\n起司蛋糕含蛋、奶、小麥，不含堅果。', '營業時間\n週六、週日 08:00–18:00。'],
    model: 'voyage-4',
    input_type: 'document',
  }),
})
const json = await res.json()
// { data: [{ embedding: [1024 個數字], index: 0 }, …], model: 'voyage-4', usage: { total_tokens: … } }

// 線上：顧客的問題用同一個模型，但 input_type 是 'query'

這一課的練習不能連網路，所以頁面附了一個玩具 embedding toyEmbed：把中文切成相鄰兩字（「起司蛋糕」→「起司」「司蛋」「蛋糕」）、英數取整個單字，每個片段用雜湊決定放在 64 維裡的哪一格、加 1，最後把長度調成 1。它只看字面，不懂意思：

第一組很像，因為共用了好幾個雙字片段；第二、三組是 0，因為一個相同的片段都沒有。真實的 embedding 模型會把「拿鐵」和「咖啡牛奶」放得很近，玩具做不到。另外 64 格太少，不同的片段可能被雜湊到同一格，讓不相關的句子也有一點分數。這些都沒關係：練習要學的是管線（切塊 → 向量 → 相似度 → 排序），換成真的模型時，只有產生向量的那一行會變。

查詢與文件一定要用同一個 embedding 模型（與版本）。每個模型有自己的「地圖」，就算維度一樣，A 模型的座標和 B 模型的座標也不能比較。換模型就要把所有塊重算一次，所以資料庫要記下每一塊是用哪個模型、幾維算的（第 9 課的 embed_model 欄位）。Voyage 另外要求檢索時指定 input_type：文件用 'document'、問題用 'query'，官方文件說不要省略，指定了檢索品質比較好。
💡 實務上：換 embedding 模型是一次資料遷移
新模型推出、或想換便宜一點的模型時，不能只改程式裡的模型名稱：所有塊都要重算，重算完成前查詢還得用舊模型。常見做法是新增一組欄位或一張新表，背景把所有塊用新模型算一遍，用 eval（第 11 課）比較新舊兩組找到正確塊的比例，確定比較好才把查詢切過去，舊的那組留一段時間再刪。這件事會牽動成本（整批重算的 embedding 費用）和上線時程，要事先跟 PM 講清楚。

相似度：cosine 與正規化

比較兩個向量最常用的是 cosine 相似度：看兩個箭頭的方向有多接近，跟箭頭多長無關。1 表示方向完全相同，0 表示無關（垂直），-1 表示完全相反。算法是：

cosine(a, b) = 內積 ÷（a 的長度 × b 的長度）

內積（dot product） = a[0]×b[0] + a[1]×b[1] + …
長度 = √(a[0]² + a[1]² + …)

正規化（normalize）是把向量每個數字除以它的長度，讓長度變成 1。兩個長度都是 1 的向量，cosine 的分母是 1，內積就等於 cosine，少算兩次開根號。Voyage 回傳的 embedding 已經正規化，toyEmbed 也是，所以實務上常直接用內積排序。有兩個邊界要自己處理：

  • 零向量：長度是 0，除下去得到 NaN。toyEmbed('！？') 沒有任何片段，就會得到全 0 的向量。NaN 跟任何數字比較都是 false，排序結果會亂掉而且不會報錯，所以零向量的 cosine 直接回 0。
  • 長度不同：1024 維和 512 維的向量放在一起比，通常代表用錯了模型或設定。默默只算前 512 維會得到一個看起來正常、其實沒有意義的分數，要直接丟錯。

top-k：暴力搜尋與它的極限

top-k 是「取分數最高的前 k 筆」。最直接的做法叫暴力搜尋（brute force）：問題算一次 embedding，跟每一塊都算一次 cosine，由高到低排序，取前 k 個。實務上還有兩個細節：

  • 過濾要在取前 k 之前。顧客在「過敏原」頁面提問，只想搜 docId === 'allergens' 的塊：如果先取全部的前 3 名再過濾，可能一筆都不剩。
  • 同分要有固定的順序。分數一樣時依 docId、seq 排，同樣的問題每次得到同樣的結果，測試、除錯、快取才有意義（第 4 課講過「同樣的輸入，同樣的請求」）。

咖啡店的手冊切完大概幾百塊，暴力搜尋在 1 毫秒內就做完，完全夠用。到了幾十萬、上百萬塊，每個問題都把全部掃一次就太慢了，這時要用向量索引：第 9 課在 PostgreSQL 裡用 pgvector 的 HNSW 索引，只看一小部分的塊就找到「幾乎最近」的結果。索引加速的就是你在練習 3 寫的這件事，代價是偶爾漏掉一兩個真正的最近鄰。

top-k 只保證「相對最像」，不保證「真的相關」。問「可以帶狗嗎」，手冊裡沒寫，前 3 名照樣有分數。第 10 課會加上分數門檻：最高分太低時，直接回「這個問題我需要請店員確認」，不讓模型硬掰。
💡 實務上：先用暴力搜尋，量到慢了再加索引
咖啡店客服、公司內部 FAQ 這類幾百到幾萬塊的資料，暴力搜尋就夠快，而且結果一定是真正的前 k 名，除錯最單純。要不要加向量索引，看的是量出來的查詢延遲，不是塊的數量聽起來大不大。加了索引之後，結果可能跟暴力搜尋不完全一樣，所以要留著暴力搜尋的版本，拿來比對索引漏掉了多少（第 9 課）。

實務規則

  • 記錄 embedding 模型與維度。資料庫的每一塊記下 embed_model（例如 voyage-4）。哪天要升級模型，才知道哪些塊要重算；重算期間，新舊兩組向量不能混在一起搜。
  • embedding 也要花錢，只重算有變的塊。每一塊記下內容的雜湊值（hash），文件改版時只有雜湊變了的塊才重算（第 9 課）。
  • 塊的大小用 eval 調。準備一組「問題 → 應該找到哪一塊」的題目，換切法前後比較命中率（第 11 課），不要憑感覺。
  • 檢索不只有向量。embedding 擅長找意思，對產品編號（SKU-0042）、專有名詞反而不準；第 10 課會把向量搜尋和 PostgreSQL 課第 28 課教過的關鍵字搜尋合併。

練習

三題都在頁面上做，可以分開做。練習 3 的起始程式已經附上寫好的 toyEmbed、cosine 和 15 個切好的塊。

練習 1：寫 chunkMarkdown(docId, md, opts)，把一份 Markdown 文件切成塊。起始程式已經寫好型別和 overlap 的檢查，你要完成兩個函式：

splitSection(text, opts)：把一節的內容切成好幾塊。

  • 先 const chars = Array.from(text)，長度、位置都用 chars 算。長度 ≤ maxChars 時整節就是一塊。
  • 否則從 start = 0 開始：先令 end = start + maxChars，再從 end 往回找，找到第一個滿足 p > start + overlap 而且 chars[p - 1] === '\n' 的位置 p（切在換行後面），找到就令 end = p，找不到就維持硬切。
  • 這一塊是 chars.slice(start, end).join('')，下一塊從 end - overlap 開始（重疊 overlap 個字元）。剩下的字元數 ≤ maxChars 時，剩下的全部是最後一塊。

chunkMarkdown(docId, md, opts)：

  • 用 md.split('\n') 逐行讀。符合 /^(#{1,6})\s+(.+)$/ 的行是標題，# 的個數是層級；其他行屬於目前這一節。
  • 遇到標題時，先把上一節收尾，再更新標題路徑：保留比它高的層級，換掉同層與更深的。例如 ['門市手冊', '過敏原', '蛋糕'] 遇到 ## 退款規則 變成 ['門市手冊', '退款規則']。第一個標題之前的內容，標題路徑是 []。
  • 一節的內容是這節的行用 '\n' 接起來再 trim()；是空字串就略過（只有標題的章節不產生塊）。檔案結束時也要收尾最後一節。
  • 每一塊是 { docId, headingPath, text, seq }：headingPath 是當下標題路徑的複本，seq 整份文件從 0 連續編號。

練習 2：寫 cosine(a, b) 與 normalize(v)。

  • cosine：內積 ÷（a 的長度 × b 的長度）。兩個陣列長度不同時丟出 Error；其中一個是零向量（長度 0）時回傳 0，不能出現 NaN。
  • normalize：每個數字除以長度，回傳新陣列，不能改到傳進來的陣列。零向量回傳全 0 的陣列。

練習 3：寫 topK(query, chunks, k, filter?)，回傳最相似的前 k 塊 { chunk, score }：

  • score 是 cosine(toyEmbed(query), chunk.vector)（查詢只算一次 embedding）。
  • 有 filter 時，只考慮 filter(chunk) 為 true 的塊，而且要先過濾、再取前 k。
  • 依 score 由高到低排；同分時依 docId 的字母順序（用 <、> 比較字串），再依 seq 由小到大。
  • k 大於塊的數量時回傳全部；不能改到傳進來的 chunks（sort 會改原陣列）。

練習 4：菜單文件只有 2,000 token，而且很少變動。要讓客服助理根據菜單回答，最簡單合適的做法是？

✓ 整份放進 prompt 最簡單也最準：模型看得到全部內容，不會有「找錯段落」的問題，快取讓重複的部分很便宜。RAG 有自己的複雜度與失敗方式（找不到、找錯），資料小時不值得（a 錯）。微調改的是習慣，價格一改就要重訓（c 錯）；上網查既慢又不保證找到你家的最新資料（d 錯）。

練習 5：文件的塊用 voyage-4 算 embedding 並存進資料庫。為了省錢，同事把查詢改用另一家的 embedding 模型，維度也是 1024。結果會？

✓ 每個模型有自己的座標系，維度一樣只代表數字的個數一樣，第 37 維在兩個模型裡代表完全不同的東西，所以 a、c 都不對，排出來的結果接近隨機。也不會有任何錯誤提醒你（d 錯），程式照樣算出分數。要換模型就把全部的塊重算，所以資料庫要記錄 embed_model。

練習 6：把整份 40 頁的門市手冊當成一個塊算 embedding。顧客問「起司蛋糕含堅果嗎」，會怎樣？

✓ 一個向量要代表 40 頁的所有主題，跟任何一個具體問題都不會特別像，所以 a、d 錯；就算找到了，也是把整本手冊送進 prompt，費用和延遲都回到原點。40 頁不一定超過 embedding 模型的輸入上限（voyage-4 每段文字是 32,000 token），所以不一定會被拒（c 錯）；真的超過時，Voyage 預設（truncation 開啟）是把超過的部分截掉，也不會報錯，後面的內容等於沒算進去。問題是品質。反過來塊太小會失去上下文，起點是按標題切、適度重疊，再用 eval 調。

常見錯誤

  • 用固定字數一路硬切：句子、清單、表格被切成兩半，兩塊都找不到。先按標題切，太長再切在換行的地方，相鄰塊重疊一小段。
  • 用 length、slice 計算和切字串：emoji 被切成兩半變成亂碼。用 Array.from(text) 算字元、切位置。
  • 塊沒有 metadata：不能依文件過濾、不能引用來源、文件改版時不知道要換哪些塊。每一塊至少帶 docId、標題路徑、seq。
  • 查詢與文件用不同的 embedding 模型：分數照樣算得出來，但沒有意義。兩邊用同一個模型與版本。
  • 忘了 input_type：不會報錯，但檢索品質比較差。文件用 'document'、問題用 'query'。
  • 沒有記錄 embedding 模型版本：換模型時分不出哪些向量是舊的。每一塊存 embed_model，換模型就全部重算。
  • 先取前 k 再過濾：結果比 k 少，甚至一筆都沒有。先過濾再排序取前 k。
  • 零向量沒有處理：cosine 變成 NaN，排序默默出錯。分母是 0 時回 0。
  • 資料很小也上 RAG：多了一整套會出錯的程式，回答反而不準。幾千 token 的資料直接放進 prompt 加快取。

小結

  • RAG＝先檢索相關的資料，再讓模型根據它回答。離線切塊、算 embedding、存起來；線上把問題算成 embedding、找最相近的幾塊、組 prompt。
  • 資料小、很少變時，整份放進 prompt 加快取更簡單；要改語氣與格式才考慮微調；資料大、常變、要能引用來源才用 RAG。
  • 切塊：按標題切並保留標題路徑，太長再切在換行處，相鄰塊重疊；每塊帶 docId、標題路徑、seq 等 metadata；長度用 Array.from 算。
  • 塊太大會稀釋相似度、浪費 token；塊太小會失去上下文。起點按結構切，再用 eval 調。
  • embedding 把文字變成向量，意思相近的向量也相近；查詢與文件要用同一個模型與版本，並記錄在資料庫。Anthropic 沒有 embedding 模型，官方文件推薦 Voyage AI（voyage-4，預設 1024 維）。
  • cosine＝內積 ÷ 兩個長度的乘積；正規化後內積就是 cosine。零向量回 0，長度不同要丟錯。
  • 暴力 top-k：全部算一次、先過濾、由高到低排、同分依 docId 與 seq；資料多到幾十萬筆以上才需要向量索引。
