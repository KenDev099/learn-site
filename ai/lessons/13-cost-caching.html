階段 5：上線：評估、安全、成本、可靠性與可觀測性 · 第 13 課

成本：token 預算、prompt caching、模型選擇與批次處理

客服助理上線一個月，帳單比預估多了好幾倍。拆開來看，錢大部分不是花在顧客的問題上，而是花在每一個請求都重送一次的東西：客服規則、工具定義、整份菜單與門市文件。顧客問「拿鐵多少錢」只有十幾個 token，前面那一大段卻有好幾千個。

這一課教你看懂帳單，把錢省在不影響品質的地方。

這課的路線：
  1. 帳單怎麼來的、prompt caching：一個請求的錢花在哪幾種 token，每次重送的規則和菜單怎麼用快取變便宜（開場問題的最小答案）。
  2. 讓快取命中：請求的內容要怎麼排，快取才不會每次都落空。
  3. 選模型與 effort、count_tokens：什麼時候換便宜的模型或讓它少想一點，太長的輸入怎麼在送出前擋下。
  4. Message Batches：每晚分類評論這種不急的工作，怎麼用批次打 5 折。
  5. 預算與告警：怎麼替每位顧客設每天的花費上限，避免一個人燒掉整月額度。
這課會用到：
  • 第 1 課的費用算法：輸入 token × 輸入單價＋輸出 token × 輸出單價，單價以每百萬 token 計，輸出比輸入貴。
  • 第 2 課的 usage 與對話歷史：每個回應都附這次的 token 數；API 沒有記憶，每一輪都重送整段歷史。
  • 第 4 課的穩定請求：同樣的輸入要組出逐位元相同的請求，例如菜單一定排序、不在 system 放現在時間。
  • 系統設計課第 5 課的快取：重複的東西存起來直接拿，省下多少取決於命中率（拿得到的比例）。

帳單怎麼來的：一個請求的四種 token

第 1 課的公式是「輸入 token × 輸入單價＋輸出 token × 輸出單價」。用了快取之後，回應的 usage 會把輸入拆成三種，各有各的價錢：

usage 欄位是什麼Opus 5.5 單價（每百萬 token）
input_tokens沒有用到快取的輸入：通常是最後一個快取斷點之後的部分$4
cache_creation_input_tokens這次寫入快取的輸入（cache write）$5（5 分鐘 TTL，1.25 倍）／$8（1 小時 TTL，2 倍）
cache_read_input_tokens這次從快取讀到的輸入（cache read）$0.20（0.05 倍）
output_tokens輸出，包含思考的 token$20

三種輸入互不重疊：input_tokens 不包含快取的部分，整個 prompt 的長度是三者相加。兩個快取欄位在 SDK 的型別裡是 number | null，計算時要用 ?? 0。

三個現行模型的價格（2026-11-01 查詢官方定價頁；價格會變，程式裡集中放在一個檔案）：

模型輸入5 分鐘寫入1 小時寫入快取讀取輸出
claude-opus-5-5$4$5$8$0.20$20
claude-sonnet-5-5$2$2.50$4$0.10$10
claude-haiku-5-5（prompt ≤ 10 萬 token）$0.10$0.125$0.20$0.01$0.50
claude-haiku-5-5（prompt > 10 萬 token）$0.50$0.625$1$0.05$2.50

快取讀取的倍率不是每個模型都一樣：一般是輸入價的 0.1 倍，Opus 5.5 與 Sonnet 5.5 是 0.05 倍。Haiku 5.5 依 prompt 長度分兩段價格，「prompt 長度」是 input_tokens＋cache_creation_input_tokens＋cache_read_input_tokens，超過 10 萬時整個請求（包括輸出）都用高的那組價格。

算一個客服請求：tools＋system＋菜單文件 6,000 token、這次的問題與歷史 500 token、回答 300 token，用 Opus 5.5、沒有快取：

輸入 6,500 × $4  ÷ 1,000,000 = $0.026
輸出   300 × $20 ÷ 1,000,000 = $0.006
合計 $0.032／次；一天 1 萬次 = $320／天，其中 $240 花在每次都一樣的 6,000 token

同樣的請求，固定的 6,000 token 命中快取：

輸入（沒快取的部分） 500 × $4    = $0.0020
快取讀取         6,000 × $0.20 = $0.0012
輸出               300 × $20   = $0.0060
合計 $0.0092／次；一天 1 萬次約 $92，少了七成，回答一個字都沒變

練習 1 要把這個算法寫成 costOf(usage, model, opts)：記 log、做成本報表、扣預算都靠它。

💡 實務上：每個請求都記下 usage 與費用
咖啡店後台的成本報表、月底對帳、PM 問「這個新功能每天多花多少錢」，答案都來自每個請求的 log：模型、四種 token、算出的費用，加上功能名稱（客服、評論分類）與顧客或租戶 id。沒有這些欄位，帳單只有一個總數，找不出是哪個功能、哪位顧客在花錢。資深工程師在功能上線前就把這幾個欄位放進 log（第 15 課），而不是等帳單來了才補。

prompt caching：重複的前綴只付一點點

prompt caching（提示快取）是 API 把請求的開頭（前綴）存起來，下一個請求開頭一模一樣時，那一段用快取讀取的價格計費，處理也比較快。它跟系統設計課的快取一樣看命中率，但比對方式很嚴格：

  • 前綴比對，逐位元相同：請求依 tools → system → messages 的順序組成一長串，從頭開始比，第一個不同的位元組之後全部算沒命中。
  • 你決定存到哪裡：在某個 block 上加 cache_control: { type: 'ephemeral' }，就是一個快取斷點（breakpoint）：從開頭到這個 block 為止的前綴會被寫入快取。一個請求最多 4 個斷點。
  • 自動快取：在請求頂層寫 cache_control: { type: 'ephemeral' }，API 會自動把斷點放在最後一個可快取的 block，對話變長時跟著往後移。它也佔 4 個名額中的 1 個。
  • TTL（time to live，存活時間）：預設 5 分鐘，每次命中會重新計時；可以設 ttl: '1h'。寫入價 5 分鐘是 1.25 倍、1 小時是 2 倍。
  • 太短不快取：Opus 5.5、Sonnet 5.5、Haiku 5.5 的前綴至少要 512 token（Haiku 4.5、Opus 4.6 是 4,096）。不夠長時不會報錯，只是 cache_creation_input_tokens 一直是 0。
  • 快取依模型分開：換模型、換 speed 都從零開始。

划不划算：5 分鐘 TTL 時，同樣的前綴用兩次就回本（Opus 5.5：1.25＋0.05 = 1.3 倍，不快取是 2 倍）；1 小時 TTL 要三次（2＋0.05＋0.05 = 2.1 倍，對 3 倍）。客服這種一直有人問的流量，用預設的 5 分鐘就好；一小時才來幾個請求、每次間隔超過 5 分鐘的工作，才考慮 1 小時。

讓快取命中：穩定的在前、會變的在後

第 4 課要求「同樣的輸入產生逐位元相同的請求」，這裡就是它省錢的地方。快取不命中的原因，幾乎都是前綴裡有東西在變：

會讓前綴改變的東西改成
system 裡寫現在時間、日期、顧客名字放到最後一則 user 訊息的開頭
工具清單的順序不固定（從 Map、物件、資料庫查出來）依 name 排序；工具也不要依顧客動態增減
文件順序、JSON 的 key 順序不固定排序後再組字串
對話中途要加營運方指令，改了 system在 messages 後面加 { role: 'system' } 訊息（第 12 課），前面的快取保留
重送歷史時改寫、刪除了前面的訊息歷史只往後加，assistant 存完整 content（第 2 課）

客服請求的組法：

return {
  model: 'claude-opus-5-5',
  max_tokens: 16000,
  tools: [...tools].sort(byName),                       // 複製後排序，不改到呼叫者的陣列
  system: [
    { type: 'text', text: RULES },
    { type: 'text', text: `<menu>\n${menuDoc}\n</menu>`, cache_control: { type: 'ephemeral' } },  // 斷點 1
  ],
  messages: [...history, { role: 'user', content: `今天是 ${taipeiDate(now)}。\n\n${question}` }],
  cache_control: { type: 'ephemeral' },                 // 自動快取：歷史越長越划算
}

斷點放在菜單那個 block，快取存的是「tools＋規則＋菜單」：tools 排在 system 前面，所以斷點放在 system 的最後一個 block 就把 tools 一起包進去。放在第一個 block 的話，只有 tools＋規則被快取，最貴的菜單每次照價計費。頂層的自動快取負責對話：第 3 輪時，前兩輪的歷史已經在上一個請求寫入快取，這次就讀得到。代價是自動斷點落在最後一則訊息，每個請求都會把「這次的問題」用 1.25 倍寫入快取；多輪對話下一輪會讀回來，划算，但如果大多是只問一句就走的請求，那一小段寫了也沒人讀，這時只留菜單上的斷點就好。每個 block 都加 cache_control 不會更好：超過 4 個斷點直接 400。

用 usage 驗證，不要假設

加了 cache_control 不代表有省到錢。快取不命中時 API 不報錯，只會在 usage 看得出來：

你看到的代表
第 1 個請求 cache_creation 有值，之後 cache_read 接近前綴長度正常
每個請求都在 cache_creation，cache_read 一直是 0前綴每次都不同：有東西在變
cache_creation 與 cache_read 都是 0前綴短於最小長度（512 token），或根本沒放 cache_control

上線後把快取命中率（cache_read 佔全部輸入的比例）放進監控（第 15 課），改了 prompt 之後命中率掉下來，就知道哪次部署出了問題。第 1 個請求本來就不會命中，判斷「沒命中」要從第 2 個請求看起。

選模型與 effort：看「每完成一個任務」的成本

快取和精簡 token 是免費的優化，回答不會變。換模型、降 effort 是取捨：便宜了，品質可能掉。所以順序是先做免費的，再用第 11 課的 eval 比較取捨。

任務常見的選擇
分類（評論好壞、問題類型）、路由、擷取欄位Haiku 5.5：比 Opus 5.5 便宜 40 倍，簡單任務常常一樣準
一般客服問答Opus 5.5 較低的 effort，或 Sonnet 5.5
多步驟的 agent、困難的推理Opus 5.5，effort medium 以上

effort 控制模型思考與輸出的投入程度，寫在 output_config 裡（不是請求頂層）：output_config: { effort: 'low' }，可選 low、medium、high、xhigh、max。Opus 5.5 預設 medium、Sonnet 5.5 預設 high。effort 越低，思考 token 越少，輸出 token（含思考）就越少，回應也越快。Opus 5.5 的思考不能關，effort 是唯一能調的地方。

資深工程師會注意三件事：

  • 先試「最強的模型＋較低的 effort」，再考慮模型路由（model routing：先用小模型分類，再依難度交給不同模型）。路由多一次呼叫、多一個要維護的 prompt，而且快取依模型分開，兩個模型各寫一次快取。
  • 看每完成一個任務的成本，不是每個請求的單價。小模型答錯，顧客再問兩次、agent 多跑三輪、最後轉真人，總成本反而更高。
  • 用 eval 決定：同一組 eval 集跑兩種設定，比較通過率與平均成本（用練習 1 的 costOf 加總）。通過率沒掉才換。
💡 實務上：換模型是一個要留紀錄的決定
PM 說「客服太貴，換便宜的模型」時，先拿出 eval 結果：兩種設定的通過率、每個任務的平均成本、轉真人的比例。通過率掉了幾個百分點，要換算成多出來的轉真人次數，再跟省下的 API 費比，人工成本可能反而更高。決定換的話，在設定檔裡改模型與 effort（不要散落在程式各處），上線後一週內盯著快取命中率、轉真人比例與顧客回饋，有問題可以馬上改回來。

count_tokens：送出前先知道多長

顧客上傳一份 300 頁的合約、或是 RAG 一次撈回太多段落，送出去才從 usage 知道花了多少，已經來不及。client.messages.countTokens() 用跟真正請求一樣的參數（model、system、tools、messages）算出輸入 token 數：

const { input_tokens } = await client.messages.countTokens({ model, system, tools, messages })
if (input_tokens > 50_000) return '文件太長，請只貼要問的段落'          // 或先摘要、先切塊檢索

// 最壞情況的估計：輸入全部照價＋輸出用滿 max_tokens
const worst = (input_tokens * price.input + maxTokens * price.output) / 1_000_000
  • 它是 Claude 自己的 tokenizer 算的，第 1 課說過，其他家的 tokenizer（例如 tiktoken）算出來的數字對 Claude 是錯的。
  • 免費，但有自己的每分鐘請求數上限（跟送訊息的上限分開算）；結果是估計值，跟實際可能差幾個 token。
  • 每個請求都先數一次會多一次網路來回。適合用在長度不可控的輸入（上傳檔案、大量檢索結果）；一般短問題直接送，事後用 usage 記帳。

Message Batches：不急的工作打 5 折

有些工作不需要馬上有結果：每晚把當天的評論分類、跑第 11 課的 eval、重算所有商品的摘要。Message Batches API 讓你一次送出很多請求，Anthropic 在背景處理，所有 token 都打 5 折，而且跟快取的倍率疊加。限制（官方文件）：

  • 一批最多 100,000 個請求或 256 MB；多數在 1 小時內完成，最長 24 小時，超過就過期（expired）。
  • 結果保留 29 天。結果的順序跟送出的順序不一定一樣，每個請求要有 custom_id，用它對應。
  • 每筆結果的 result.type 是 succeeded、errored、canceled 或 expired；後三種不收費。errored 裡如果是 invalid_request_error，要先修請求再重送，其他錯誤可以直接重送。
let batch = await client.messages.batches.create({
  requests: reviews.map(r => ({ custom_id: r.id, params: reviewParams(r) })),   // params 就是 messages.create 的參數
})
while (batch.processing_status !== 'ended') {           // in_progress → ended（取消時會經過 canceling）
  await sleep(60_000)
  batch = await client.messages.batches.retrieve(batch.id)
}
for await (const row of await client.messages.batches.results(batch.id)) {   // 一行一筆的 JSONL 串流
  if (row.result.type === 'succeeded') save(row.custom_id, row.result.message)
  else retry.push(row.custom_id)
}

正式環境不會讓一個程序睡 1 小時等批次：用 BullMQ（NestJS 課第 20 課）排一個每晚送出批次的工作，把 batch id 存進資料庫，另一個重複執行的工作每幾分鐘檢查一次狀態，ended 之後下載結果、把失敗的重新排入下一批。批次也不佔即時請求的處理量，白天的客服不會被晚上的大量工作拖慢（第 14 課）。很多請求共用同一段長前綴時，因為批次可能處理超過 5 分鐘，可以考慮用 1 小時 TTL 的快取，讓後面處理的請求還讀得到；官方文件也提醒，批次裡的快取命中是盡力而為（best-effort），不保證每個都命中。

預算與告警：一個人不能燒掉整月額度

有人寫個腳本對你的客服連續貼長文，或是 agent 被誘導繞圈（第 7 課），沒有上限的話，帳單會在你睡覺時暴增。成本控制要在三個層級都有：

層級做法
單一請求max_tokens 限制輸出；輸入太長先用 countTokens 擋下
單一任務agent 的輪數與 token 預算（第 7 課）
每位顧客／每個租戶每天送出前檢查「今天已花＋這次估計 ≤ 上限」，收到回應後用 usage 算出的實際費用累加

每日預算有幾個要注意的地方：

  • 送出前用估計、送出後用實際：估計用 countTokens 或平常的平均值；實際值用 costOf(response.usage)。只在事後檢查的話，最後一個請求會超出很多。
  • 「一天」用哪個時區：顧客在台灣，就用台北時間的日期當 key；直接用 toISOString() 的 UTC 日期，會在台灣早上 8 點才重置。
  • 存在哪裡：練習 5 存在記憶體的 Map 裡，只適用單一程序。多台伺服器要共用計數，用 Redis 的 INCRBYFLOAT 加上一天多一點的過期時間，key 像 budget:2026-11-01:u42。
  • 超過時降級，不是直接報錯：改用較短的回答、較便宜的模型，或回「今天的線上諮詢次數已用完，已幫你轉給店員」，並記 log、發告警。
  • 整個帳號也要有上限：在 Claude Console 為 workspace 設花費上限，並對每日總花費設告警，這是程式出錯時最後一道防線。
💡 實務上：上限要先跟 PM、客服講好
每日上限設多少、超過時顧客看到什麼，是產品決定，不只是技術決定：太低會讓正常的熟客被擋，太高擋不住濫用。常見做法是先看上線第一週每位顧客每天花費的分布，上限設在絕大多數正常顧客之上，再對碰到上限的帳號發告警，讓客服或維運看一下是真的熟客還是腳本。降級的文案也要客服知道，顧客打電話來時才答得出來。

練習 1：完成 costOf(usage, model, opts)，回傳美元、四捨五入到小數第 6 位。input_tokens、output_tokens、cache_creation_input_tokens、cache_read_input_tokens 各用 PRICES 裡自己的單價；寫入的單價依 opts.cacheTtl（預設 '5m'）；快取欄位是 null 時當成 0；Haiku 5.5 的 prompt（三種輸入相加）大於 10 萬時整個請求改用 HAIKU_LONG；opts.batch 時全部乘上 BATCH_DISCOUNT。

練習 2：完成 buildCachedRequest(menuDoc, tools, history, question, now)。tools 依 name 排序（不改到傳進來的陣列）；system 是兩個 text block：RULES，以及用 <menu> 包住的菜單（這個 block 加 cache_control）；messages 是 history 加上最後一則 user 訊息「今天是 <台北日期>。」空一行再接問題；請求頂層加 cache_control 開啟自動快取。日期與問題不同時，tools＋system 序列化後要逐字相同。

練習 3：完成 checkCacheHealth(usages)。hitRate 是全部 cache_read_input_tokens 除以全部輸入（三種相加），null 當成 0、沒有輸入時是 0。有兩個以上的請求、而且從第 2 個起 cache_read_input_tokens 全部是 0 或 null 時，warning 是「快取沒有命中，檢查前綴是否有變動的內容」，其他情況是 null。

練習 4：完成 runNightlyBatch(client, reviews, sleep)。用 client.messages.batches.create 送出，每則評論一個請求（custom_id 是評論 id、params 用寫好的 reviewParams）；processing_status 不是 'ended' 就用傳進來的 sleep(POLL_MS) 等待再 retrieve；結束後讀 results，succeeded 的用 readLabel 放進 labels（以 custom_id 為 key），其他結果的 custom_id 放進 retry，不要丟錯。

練習 5：完成 DailyBudget。canSpend(userId, estimateUsd) 在「這位顧客今天已花的＋這次估計」小於或等於上限時回傳 true；record(userId, actualUsd) 累加實際費用；spent(userId) 回傳今天已花多少。不同顧客分開算，「今天」用建構時傳入的 now() 與寫好的 taipeiDay，台北時間換日就重新計算。

練習 6：加了 cache_control，可是 usage.cache_read_input_tokens 一直是 0，也沒有錯誤。最可能的原因是？

✓ 快取是逐位元的前綴比對，任何一個位元組改變，它和後面的全部重算；前綴短於 512 token（Opus 5.5 等）時不快取也不報錯。快取不用申請（a 錯），一般請求就能用（c 錯），5 分鐘 TTL 在請求頻繁時一樣命中（d 錯）。要用 usage 驗證，不要假設。

練習 7：每晚要把 5 萬則評論分類，隔天早上看結果。最省的做法是？

✓ 不需要即時的工作適合批次：費用減半，也不佔即時客服的處理量。分類是簡單的任務，用 Haiku 5.5 再用 eval 確認品質。a 一次送 5 萬個很容易碰到 rate limit（429），而且照原價；c 的 fast mode 是更快但更貴（價格 2 倍），也不能用在批次；d 要跑將近 14 小時，照原價。

練習 8：想降低客服成本，第一個該試的是？

✓ 快取與精簡 token 不會讓回答變差。換模型、降 effort 是取捨，要用 eval 驗證，並且看每完成一個任務的成本（a）。max_tokens 太小會把回答（含思考）截斷，stop_reason 變成 max_tokens（c）。不送菜單，模型就只能猜價格（d）。

常見錯誤

  • 沒驗證快取有命中就以為省到錢：快取不命中不會報錯。看 cache_read_input_tokens，把命中率放進監控。
  • 在 system 放時間、顧客名字或沒排序的資料：前綴每次都不同，快取永遠寫入、從不讀取，比不快取還貴 25%。會變的內容放在最後一則 user 訊息。
  • 快取讀取用 0.1 倍計算 Opus 5.5：Opus 5.5、Sonnet 5.5 是 0.05 倍。價格表集中在一個檔案，附上查詢日期。
  • 算費用時漏掉 cache_creation_input_tokens：寫入是另外計費的，而且比一般輸入貴。
  • 為了省錢換小模型卻沒跑 eval：品質掉了你不會馬上知道；顧客重問、轉真人的成本比省下的多。
  • 批次結果依順序對應：結果的順序跟送出的不一定一樣，一定用 custom_id。
  • 批次裡有失敗的請求就讓整個工作丟錯：errored、expired 是預期中會發生的，記下來重送就好，成功的結果要保留。
  • 沒有每位使用者的預算上限：一個濫用者就能燒掉整月額度。送出前檢查估計值，收到回應後扣實際值，超過時降級並告警。

小結

  • 一個請求的費用 = input、cache_creation（1.25 倍或 2 倍）、cache_read（Opus 5.5／Sonnet 5.5 是 0.05 倍）、output 各乘自己的單價；Haiku 5.5 的 prompt 超過 10 萬 token 整個請求用高價；批次全部 5 折並與快取疊加。
  • prompt caching 是逐位元的前綴比對，順序 tools → system → messages；斷點放在穩定部分的最後一個 block，頂層 cache_control 自動快取對話；最多 4 個斷點，前綴至少 512 token。
  • 穩定的在前、會變的在後：工具排序、日期放在最後一則 user 訊息、中途指令用 role: 'system' 訊息。用 usage 驗證命中。
  • 先做免費的（快取、精簡 token），再用 eval 比較較低的 effort（output_config.effort）或較小的模型；看每完成一個任務的成本。
  • countTokens 在送出前估計輸入長度（可能跟實際差幾個 token），用來擋下太長的輸入。
  • 不急的工作用 Message Batches：5 折、用 custom_id 對應、輪詢到 ended、失敗的重送。
  • 每位顧客每天設上限：送出前用估計檢查，收到回應後扣實際值，超過時降級並告警。
