階段 1：LLM 基礎與第一個 API 呼叫 · 第 3 課

串流：邊產生邊顯示、中斷與首字延遲

咖啡店的「問店員」視窗接好了第 2 課的 ask()，測試都過了。上線後顧客的回饋卻是「按了送出就沒反應，以為壞了」：問一個要解釋三種咖啡差別的問題，畫面要空白十幾秒，整段回答才一次跳出來。有人等不及關掉視窗，但後端還在等 Claude 把回答寫完，那些 token 照樣算錢。

這一課改用串流（streaming）：模型產生一點就送一點，畫面邊收邊顯示。

這課的路線：
  1. 為什麼要串流：同一個回答，為什麼一次回傳讓顧客以為壞了，串流讓第一個字一兩秒就出現（開場問題的最小答案）。
  2. 串流長什麼樣、用 SDK 收串流：SSE 事件依什麼順序來，SDK 怎麼替你組回完整的回答。
  3. 量 TTFT：顧客等到第一個字要多久，怎麼量才不會量錯。
  4. 中斷、串流中途出錯：顧客關掉視窗時怎麼讓上游停下、不再花錢，回答到一半出錯時畫面怎麼處理。
  5. 資深視角：串流的代價：串流讓什麼事變難，上線後要記錄哪些指標。
這課會用到：
  • 第 2 課的回應：content 是 block 陣列，usage 記 token 數，stop_reason 說明回答能不能用。
  • TypeScript 課第 10 課的 for await：一筆一筆讀非同步產生的資料，讀完一筆才拿下一筆。
  • TypeScript 課第 11 課的 AbortController：呼叫 abort() 時，它的 signal 會通知正在進行的工作停下。
  • 系統設計課第 3 課的百分位數：p95 是 95% 的請求都不超過的延遲，延遲看分佈，不看平均。

為什麼要串流

模型是一次產生一個 token（第 1 課），所以回答本來就是一段一段「長」出來的。非串流的請求（第 2 課的 messages.create）要等全部產生完，API 才把整個 Message 一次回傳。同一個回答，兩種做法的總時間差不多，使用者的感受差很多：

非串流串流
畫面第一次出現文字12 秒後（全部產生完）約 1 秒後
全部顯示完12 秒12 秒
使用者看到的空白、轉圈，不知道有沒有在動文字一直在長，知道系統有在工作

從送出請求到收到第一段文字的時間叫 TTFT（time to first token，首字延遲）。聊天介面最看重它：使用者能忍受一段長回答慢慢出現，很難忍受十秒的空白。

第二個理由是逾時。一個很長的回答可能要產生好幾分鐘，一個 HTTP 回應這麼久沒有任何資料，中間的代理伺服器、負載平衡器常常會先把連線切掉。串流的連線一直有資料在流動，不會有這個問題。SDK 也替你擋了：用 SDK 1.3.0 實測，client 沒有自己設 timeout 時，非串流的 messages.create 只要 max_tokens 超過 21,333，還沒送出就丟出 AnthropicError：「Streaming is required for operations that may take longer than 10 minutes」。要更大的 max_tokens（最多 128K）就要用串流。

💡 實務上：串流是給「有人在等著看」的畫面用的
不是每個地方都要串流。從顧客訊息擷取訂單（第 5 課）、背景批次處理，要的是完整、驗證過的結果，沒有人在看文字一個字一個字出現，用 messages.create 比較簡單；max_tokens 很大時，用下面的 stream() 加 finalMessage() 一樣能拿到完整的 Message。決定前先問一句：這段文字會不會即時出現在某個人眼前？咖啡店的「問店員」視窗會，夜間把評論分類的排程不會。

串流長什麼樣：SSE 事件

請求多帶一個 stream: true，API 就改用 SSE（Server-Sent Events）回應：HTTP 回應保持連線，用文字一段一段送出事件，每個事件是一行 event: 加一行 data:（JSON），中間空一行。系統設計課第 17 課是伺服器「送」SSE 給瀏覽器；這裡你的後端是「收」SSE 的那一方，第 15 課再把它轉送給前端。問「拿鐵多少錢？」，原始的回應大概是這樣（省略部分欄位）：

event: message_start
data: {"type":"message_start","message":{"id":"msg_01…","role":"assistant","content":[],"stop_reason":null,"usage":{"input_tokens":41,"output_tokens":1,…}}}

event: content_block_start
data: {"type":"content_block_start","index":0,"content_block":{"type":"thinking","thinking":"","signature":""}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"signature_delta","signature":"EqQB…"}}

event: content_block_stop
data: {"type":"content_block_stop","index":0}

event: content_block_start
data: {"type":"content_block_start","index":1,"content_block":{"type":"text","text":""}}

event: ping
data: {"type":"ping"}

event: content_block_delta
data: {"type":"content_block_delta","index":1,"delta":{"type":"text_delta","text":"拿鐵一杯"}}

event: content_block_delta
data: {"type":"content_block_delta","index":1,"delta":{"type":"text_delta","text":" 110 元。"}}

event: content_block_stop
data: {"type":"content_block_stop","index":1}

event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"end_turn",…},"usage":{"output_tokens":186,…}}

event: message_stop
data: {"type":"message_stop"}
事件內容
message_start一個 content 是空陣列的 Message：id、model、輸入 token 數。stop_reason 是 null，output_tokens 只是開頭的數字。
content_block_start一個 block 開始，index 就是它在最後 content 陣列的位置。Opus 5.5 第一個 block 通常是 thinking。
content_block_deltablock 的一小段新內容。text_delta 是要顯示的文字（叫 text delta）；thinking block 是 thinking_delta、signature_delta，不是給使用者看的。
content_block_stop這個 block 結束。
message_delta整個 Message 的最後變化：stop_reason 和 usage。官方文件提醒這裡的 token 數是累計值，不是增加的量。
message_stop串流結束。
ping沒有內容，讓連線保持活著，可能出現在任何位置，可以忽略。
error串流途中出錯，例如 overloaded_error。後面會專門處理。

Opus 5.5 的思考內容預設不顯示（第 2 課），所以 thinking block 只有一個 signature_delta，沒有文字。設 thinking: { type: 'adaptive', display: 'summarized' } 時才會出現 thinking_delta 的摘要文字，這一課不需要。官方文件也說之後可能新增事件類型，程式要能忽略不認得的事件。

這些事件可以自己解析，但不需要：SDK 已經把切行、解析 JSON、把 delta 累積成完整 Message 都做好了。

用 SDK 收串流

把 messages.create 換成 messages.stream，參數一樣，SDK 會自動加上 stream: true：

const stream = client.messages.stream({
  model: 'claude-opus-5-5',
  max_tokens: 16000,
  messages: [{ role: 'user', content: '拿鐵和卡布奇諾差在哪？' }],
})

stream.on('text', delta => {
  process.stdout.write(delta)        // 每收到一段 text delta 就呼叫一次；thinking 不會進來
})

const message = await stream.finalMessage()   // 等串流結束，拿到跟 create 一樣的完整 Message
console.log(message.stop_reason, message.usage.output_tokens)

stream() 不用 await：它立刻回傳一個 MessageStream 物件，請求在背景送出。在同一段同步程式裡掛上 .on('text', …) 就不會漏掉任何事件。finalMessage() 回傳的 Message 跟第 2 課 create 的一樣：content 有 thinking 和 text block、stop_reason、最終的 usage，所以第 2 課的 readAnswer 那套檢查可以照用。

常用的事件：

寫法什麼時候呼叫
stream.on('text', (delta, snapshot) => …)每個 text delta；snapshot 是這個 text block 到目前為止的全文
stream.on('streamEvent', (event, snapshot) => …)每個原始事件（上一節那張表），snapshot 是累積中的 Message
await stream.finalMessage()串流正常結束時回傳完整 Message；出錯或被中斷時 reject
stream.abort()中斷這個串流（下面會講）

也可以用 for await 一個一個讀原始事件，適合要依事件類型做不同處理的時候：

for await (const event of stream) {
  if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
    send(event.delta.text)
  }
}

兩個要避開的寫法：

  • 自己把 .on() 包成 new Promise、自己接字串組回答：要處理 end、error、abort 三種結束方式，很容易漏一種讓 Promise 永遠不 resolve。要完整結果就 await stream.finalMessage()，它已經處理好這些情況。
  • 用 stream.finalText() 拿文字：看 SDK 1.3.0 的原始碼，它把多個 text block 用空白接起來（join(' ')），一個 text 都沒有時還會丟錯。中文回答中間會多出空格。跟第 2 課一樣，自己從 finalMessage() 過濾 type === 'text' 再 join('')。

量 TTFT

TTFT 要算到第一個 text delta，因為那是使用者第一次看到字的時候。容易量錯的兩個點：

  • message_start：請求一被接受就送來，通常很快，可是畫面上什麼都沒有。
  • thinking block 開始：Opus 5.5 一定會先思考，思考期間一樣沒有可以顯示的文字。

所以 Opus 5.5 的 TTFT 包含思考的時間。想縮短它，可以把 output_config: { effort: 'low' }（SDK 1.3.0 的值有 low、medium、high、xhigh、max，Opus 5.5 預設 medium）用在簡單的問答上：思考少，第一個字來得早，也比較便宜，代價是困難的問題答得比較草率。也可以換成比較快的模型（第 13 課）。

計時用參數傳進來的 now()，不要在函式裡直接呼叫 Date.now()，測試才能用假的時鐘得到固定的結果：

const start = now()
let ttftMs: number | null = null
const stream = client.messages.stream(params)
stream.on('text', () => { ttftMs ??= now() - start })   // ??= 只在第一次（還是 null 時）賦值
const message = await stream.finalMessage()
const totalMs = now() - start

正式環境用 performance.now()：它不受系統時間校正影響，適合量經過的時間。整個回應都沒有文字（例如模型拒答，或第 6 課的只呼叫工具）時，TTFT 不存在，記成 null，不要用總時間代替，否則統計會被扭曲。

TTFT 跟其他延遲一樣要看分佈，不是平均（系統設計課第 3 課）：p50 是 0.8 秒、p95 是 6 秒，代表每 20 個顧客就有一個要等 6 秒以上才看到字。第 15 課會把每個請求的 TTFT、總時間、token 數記進 log。

💡 實務上：顧客說「助理好慢」，先分清楚是哪一種慢
客服或 PM 轉來「好慢」的回報時，先看 TTFT 和總時間哪一個變長。TTFT 長是「按下送出後一直空白」，常見原因是思考太多（effort 太高）、prompt 太長或 API 那端排隊；總時間長但 TTFT 正常，是回答太長，該在 prompt 要求精簡。兩者的修法完全不同，所以 log 要分開記，不能只記一個「延遲」。

中斷：使用者走了就停

使用者關掉視窗或按了「停止」，你的後端如果繼續讀，模型就會一路產生到結束，這些 token 照樣算錢，連線也一直占著。API 不知道你的前端已經斷線，要由你的程式把請求中斷。

AbortSignal 是 JavaScript 標準的取消訊號（TypeScript 課第 11 課）：AbortController 呼叫 abort() 時，它的 signal 會觸發。把 signal 放在 stream() 的第二個參數（請求選項），SDK 會在它觸發時關掉連線：

const stream = client.messages.stream(params, { signal })   // 第一個參數是 API 的內容，第二個是這次請求的選項
stream.on('text', delta => { partial += delta; onDelta(delta) })
try {
  await stream.finalMessage()
  return { status: 'done', partial }
} catch (err) {
  if (err instanceof Anthropic.APIUserAbortError) return { status: 'aborted', partial }
  throw err      // 其他錯誤不是使用者造成的，照樣往外丟
}
  • 中斷後 finalMessage() 會丟出 APIUserAbortError（SDK 1.3.0 實測）。這是預期中的結束方式，不是錯誤，接住它，回傳「已中斷」和中斷前收到的文字。
  • 只接 APIUserAbortError。用空的 catch {} 把所有錯誤都當成「使用者中斷」，API 過載、key 失效都會被藏起來。
  • 手上有 stream 物件時，也可以直接呼叫 stream.abort()，效果一樣。用 signal 的好處是同一個 signal 可以一路往下傳：Express 或 NestJS 收到前端斷線時觸發它，資料庫查詢、API 呼叫一起停（第 15 課實作）。
  • 中斷前產生的部分沒有完成，不要存成正式的對話紀錄。要保留就明確標示「已中斷」。
signal 要傳給 SDK，只在自己的程式裡檢查是沒用的。常見的錯法是 if (signal.aborted) return 寫在讀取之後：程式不再處理新的文字，但連線沒關，模型繼續產生、繼續算錢。檢查方法：中斷後，SDK 送出的請求所帶的 signal 也要是 aborted（練習 2 的測試就是這樣檢查的）。
💡 實務上：「停止」按鈕要真的讓上游停下來
聊天介面幾乎都有「停止」按鈕，前端工程師很容易只做到「畫面不再更新」。整條線要一路斷到底：前端用 AbortController 取消 fetch，後端偵測到連線關掉就觸發 signal，SDK 再關掉跟 API 的連線。上線前在「問店員」視窗按一次停止，再去後端 log 確認這次請求記成「已中斷」，而不是一路跑到完成。code review 看到串流的 API 沒有接收 signal，就要問：使用者走了之後，這個請求停得下來嗎？

串流中途出錯

非串流的請求，出錯時直接是 HTTP 錯誤，例如 529 overloaded_error（API 暫時過載）。串流多了一種情況：HTTP 已經回 200、文字已經送出幾段了，接著才收到一個 error 事件：

event: error
data: {"type":"error","error":{"type":"overloaded_error","message":"Overloaded"}}

用 SDK 1.3.0 實測：收到 error 事件時，finalMessage() 和 for await 都會丟出 Anthropic.APIError，err.type 是 'overloaded_error'，err.status 是 undefined（因為 HTTP 狀態碼是 200，錯誤是後來才來的）。一開始就 529 的話，丟出的是 InternalServerError（APIError 的子類別），status 529、type 一樣是 'overloaded_error'。所以兩種情況都用 err instanceof Anthropic.APIError 接住、讀 err.type，不要比對錯誤訊息字串。

這時候畫面上已經有半截回答了。處理原則：

  • 不能當成功：半截的退款規則可能剛好少了「需持收據」這個條件。回傳明確的失敗，帶著已收到的文字和錯誤類型，讓介面顯示「回答中斷了」和重試按鈕。
  • 不要存成正式紀錄：不能把它當成 assistant 的回答放進對話歷史（第 2 課的 Conversation 只在成功時加入歷史）。
  • 已經顯示的收不回來：所以不要偷偷從頭重試再接在後面，使用者會看到兩段開頭不一樣的回答。
SDK 的自動重試（maxRetries 預設 2，第 2 課）只對「還沒開始串流」的錯誤有效，例如一開始就 429、529、連線失敗。串流開始之後才收到的 error 事件，SDK 不會替你重試，因為它也收不回已經給你的文字。這就是資深的取捨：重試只在第一個字之前做；第一個字之後出錯，交給使用者決定。想接著寫下去，官方文件建議 Claude 4.6 之後的模型把已收到的文字放進一則新的 user 訊息、請模型從斷掉的地方繼續，但思考與工具呼叫的 block 沒辦法接續，多數客服情境直接讓使用者重問比較單純。

資深視角：串流的代價

  • 串流讓驗證變晚：文字邊產生邊送給使用者，你沒有機會在顯示前檢查整段內容。第 5 課的結構化輸出要完整結果才能驗證，通常不串流；第 12 課的輸出過濾也要考慮「已經送出去的收不回來」。
  • stop_reason 還是要看：串流結束時 finalMessage().stop_reason 如果是 max_tokens 或 refusal，畫面上的文字一樣不完整，要補一個提示，不能只靠「串流沒出錯」。
  • 連線占得更久：一個串流可能開好幾十秒，伺服器同時開著的連線數變多。設好 client 的 timeout（第 2 課），使用者離開就中斷，第 14 課再加上限流。
  • 要記錄的指標：TTFT、總時間、輸出 token 數、結束方式（完成、中斷、中途出錯）。中斷率突然上升，常代表 TTFT 變長了，使用者等不下去。

練習

在 learn 資料夾執行 node check.mjs ai 03，會建立 ai/practice/work/03/。四題各自獨立，可以照任何順序做。測試用假的 fetch 回放事先寫好的 SSE 事件：fixture 會在事件之間停住，檢查你是不是真的邊收邊處理，也會插入 thinking block、error 事件、時間點。做完後如果有 API key，可以在 ai/practice 執行 node --env-file-if-exists=.env work/03/live.ts，看真實模型的 TTFT 和中斷效果。

練習 1：完成 streamAnswer(client, question, onDelta)：用 client.messages.stream 送出一則 user 訊息（max_tokens 16000），每收到一段 text delta 就依序呼叫 onDelta，不能等串流結束才一次呼叫，也不能把 thinking 的內容送進去。結束後回傳 { text, usage }：text 是所有 text block 直接接起來的文字（回答可能有兩個 text block），usage 是最終的 usage（output_tokens 要是 message_delta 帶來的值）。

練習 2：完成 streamWithAbort(client, question, signal, onDelta)。跟練習 1 一樣串流並呼叫 onDelta；signal 觸發時上游請求要跟著中斷，回傳 { status: 'aborted', partial }（中斷前收到的文字），不丟錯；正常結束回傳 { status: 'done', partial: 完整文字 }；不是中斷造成的錯誤（例如 HTTP 529）要照樣往外丟。

練習 3：完成 safeStream(client, question, onDelta)。正常結束回傳 { ok: true, text }；任何 API 錯誤，不論是一開始的 HTTP 529 還是串流中途的 error 事件，都回傳 { ok: false, partial, errorType }：partial 是出錯前收到的所有文字，errorType 是錯誤物件的 type（例如 'overloaded_error'）。只把 Anthropic.APIError 轉成失敗結果，其他例外（例如 onDelta 自己出錯）照樣往外丟。不要自己重試。

練習 4：完成 measure(client, question, now)，回傳 { ttftMs, totalMs, outputTokens }。時間一律用參數 now()，起點是送出請求前；ttftMs 算到第一個 text delta（不是 message_start，也不是 thinking 開始），整個回應沒有文字時是 null；totalMs 算到 finalMessage() 完成；outputTokens 用最終的 usage。

練習 5：使用者在回答產生到一半時關掉了聊天視窗，你的後端沒有中斷對 Claude 的請求。後果是？

✓ API 只知道你的後端還連著，不知道你的前端已經斷線，所以 a、d 都不會發生；產生出來的 token 都算在 usage 裡，跟有沒有人看無關（c 錯）。要把前端的斷線轉成 AbortSignal 傳給 SDK，上游連線才會關掉（第 15 課實作）。

練習 6：串流已經送出 200 個字給顧客，然後收到 overloaded_error。最合理的處理是？

✓ 串流開始後已經顯示的內容收不回來。a 會讓顧客看到兩段開頭不一樣的回答；c 讓半截內容（可能少了重要條件）被當成完整答案；d 讓畫面上的字突然被換掉，顧客不知道發生什麼事。自動重試只在第一個字之前做，之後交給使用者決定。

練習 7：Opus 5.5 的串流，TTFT 應該從哪裡算到哪裡？

✓ 使用者感受到的是第一個看得到的字。HTTP 200 和 message_start 很早就到，之後還有一段思考時間沒有任何可顯示的文字，用它們會讓 TTFT 看起來比實際好很多；message_stop 是總時間，不是首字延遲。

常見錯誤

  • 等 finalMessage() 才把文字送出去：用了串流卻沒有邊收邊顯示，TTFT 跟非串流一樣。在 on('text') 裡處理每一段。
  • 把 SDK 的事件包成 new Promise 自己組文字：容易漏掉 error 或 abort，Promise 永遠不結束。要完整結果用 finalMessage()。
  • 用 finalText()：多個 text block 之間會被加上空白。從 finalMessage() 過濾 text block 再 join('')。
  • usage 讀 message_start 的：那時 output_tokens 還只是開頭的數字，費用會算錯。用 finalMessage().usage。
  • 前端斷線沒有中斷上游：白白付錢。把 signal 傳給 stream() 的第二個參數。
  • 用空的 catch 吞掉所有錯誤：API 錯誤被當成「使用者中斷」藏起來。只接 APIUserAbortError。
  • 串流途中出錯還把半截內容存成正式回答：回傳明確的失敗，不寫進對話歷史。
  • TTFT 量到 message_start 或 thinking：要量到第一個 text delta；沒有文字時記 null。

小結

  • 串流讓第一個字在一兩秒內出現；TTFT 是送出請求到第一個 text delta 的時間，要看 p95。SDK 1.3.0 在 max_tokens 很大（超過 21,333）又沒設 timeout 時，要求改用串流。
  • Claude 的串流是 SSE：message_start → 每個 block 的 content_block_start／delta／stop → message_delta（stop_reason、累計的 usage）→ message_stop，中間可能有 ping 和 error。thinking 和 text 是不同的 block。
  • SDK：client.messages.stream(params, { signal })，on('text') 邊收邊處理，await finalMessage() 拿完整 Message；文字自己過濾 text block 再接。
  • 使用者離開時用 AbortSignal 中斷上游，接住 APIUserAbortError，其他錯誤照樣往外丟。
  • 串流中途的 error 事件會變成 APIError（type 有值、status 是 undefined）；回傳明確的失敗與已收到的文字，不當成功、不存成紀錄。
  • 已經送出的文字收不回來：自動重試只在第一個字之前做。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：「問店員」上線後，同一位顧客聊到第 20 輪時，每次請求的費用是第 1 輪的好幾倍，回答長度卻差不多。為什麼？

✓ API 無狀態，記憶是你的程式每次重送的歷史：第 20 輪會把前 19 輪全部再送一次。估費用要算進去；太長就修剪最舊的問答，或開新對話。a 錯在 API 根本不保存對話，貴的是重送的輸入 token。（第 1、2 課）

練習 9：「問店員」很肯定地回答「我們有抹茶拿鐵，95 元」，但菜單上從來沒有這個品項。這是怎麼發生的？

✓ 模型不查資料庫，它產生的是機率上合理的文字，所以講錯時語氣一樣肯定。修法是把這家店真正的菜單放進這次請求、要求附上來源，並用 eval 持續量錯誤率。a 錯在新模型一樣會幻覺，而且它從來就不知道你店裡的菜單，這些資料要由你的程式放進請求。（第 1 課）

練習 10：顧客在 LINE 傳「兩杯熱拿鐵、一杯美式少冰」，要回覆總金額。哪種分工最合適？

✓ 金額有明確規則、答案只有一個，錯了代價高又不容易被發現，交給程式；模型負責看懂亂七八糟的自然語言。c 錯在列出算式只讓答案看起來可信，數字仍是取樣產生的，不保證每次都對。（第 1 課）

練習 11：一位常客跟「問店員」聊了很久，之後的回答開始停在句子中間，log 裡沒有任何錯誤。先查什麼？

✓ context window 包含輸入和輸出，歷史塞滿後請求照樣被接受，產生到上限就被切斷，停止原因會寫明是截斷。修法是修剪最舊的一問一答（這次的問題一定留），程式也要先看停止原因，截斷就不當成功。d 錯在輸入本身超過會直接被拒絕、一個字都不產生，不會有半截回答。（第 1、2 課）

練習 12：多輪對話的 send() 這樣寫。哪裡會出事？

async send(text) {
  this.history.push({ role: 'user', content: text })
  const res = await client.messages.create({ model, max_tokens, system, messages: this.history })
  const answer = readAnswer(res)   // 截斷或拒答時丟錯
  this.history.push({ role: 'assistant', content: res.content })
  return answer
}

✓ API 錯誤、截斷、拒答都會丟錯，剛加的 user 卻留在歷史裡；下一次 API 不報錯，把兩則併成同一輪，模型看到一個沒被回答的舊問題，可能答非所問。修法是失敗時拿掉最後一則 user，或成功後才一起加。a 錯在完整的 content 本來就該原樣送回，thinking 和之後的工具呼叫都靠它。（第 2 課）

練習 13：顧客按了「停止」之後，前端確實不再收到文字。這段後端程式哪裡會出事？

const stream = client.messages.stream(params)
stream.on('text', delta => {
  if (!signal.aborted) onDelta(delta)   // 按了停止就不再推給前端
})
await stream.finalMessage()

✓ 只在自己的程式裡檢查，畫面停了，上游還在跑；API 不知道你的前端已經走了。把 signal 傳進 stream() 的請求選項，SDK 才會關掉跟 API 的連線，再只接住使用者中斷的那一種錯誤。a 錯在 signal 根本沒交給 SDK，這裡不會有中斷錯誤，請求會一路跑到完成。（第 3 課）

練習 14：同事要替「問店員」的串流加上「出錯自動重試」。重試的界線該放在哪裡？

✓ 已經顯示的文字收不回來，從頭重送會讓顧客看到兩段開頭不一樣的回答。第一個字之後出錯，回傳明確的失敗和已收到的文字，顯示「回答中斷了」和重試按鈕，半截內容不存成正式紀錄。a 錯在問題不是重送會不會成功，而是前面那一段已經送出去了。（第 3 課）

練習 15：客服轉來「助理變慢了」。log 裡首字延遲（TTFT）和平常一樣，總時間卻長了很多。先往哪個方向修？

✓ TTFT 已經包含排隊、讀 prompt 和思考的時間，它正常代表這些都沒變；多出來的時間花在產生文字，就是回答太長。b 錯在思考發生在第一個字之前，想太多會先讓 TTFT 變長。所以 TTFT 和總時間要分開記。（第 3 課）
