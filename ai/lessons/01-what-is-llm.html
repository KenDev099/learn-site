階段 1：LLM 基礎與第一個 API 呼叫 · 第 1 課

LLM 在做什麼：token、context window 與每次不一樣的輸出

咖啡店老闆想在 LINE 官方帳號加一個自動回覆：顧客問菜單、價格、營業時間，由 AI 回答。你接好 API，測了幾句都很順，就上線了。一週後出現兩個問題：

  • 同一個問題「拿鐵一杯多少？」，昨天回「110 元」，今天回「拿鐵是 110 元喔，要加燕麥奶嗎？」。測試程式比對整句，每天都有幾個測試隨機失敗。
  • 帳單是預估的 10 倍。你估算時只算了顧客的問題（大約 30 個字），忘了每次請求都要連同規則、菜單和前面的對話一起送，也忘了模型產生的文字（包括你看不到的思考）單價是輸入的 5 倍。

這兩個問題都不是程式寫錯，而是對大型語言模型的運作方式有錯誤的想像。這一課先建立正確的心智模型，學完你能估算費用、判斷請求放不放得下、修剪過長的對話歷史，並說明為什麼「把 temperature 設成 0」在現在的 API 行不通。

這課的路線：
  1. 一次產生一個 token、token 不是字元：模型怎麼一小段一小段接出回答，為什麼錢和長度都用 token 算，不用字數（開場問題的最小答案）。
  2. 費用怎麼算：一次請求的錢由哪些部分組成，PM 問「一個月要花多少」時怎麼算給他看。
  3. context window 與 max_tokens：一次請求放得下多少，對話太長時怎麼修剪歷史。
  4. 每次不一樣：取樣：同一個問題為什麼每次措辭不同，測試和「必須一字不差」的文字該怎麼處理。
  5. API 沒有記憶、知識會過期、會說錯，以及什麼時候不要用 LLM：哪些事要由你的程式負責。
這課會用到：
  • TypeScript 課第 5 課的浮點數誤差：0.1 + 0.2 !== 0.3，金額要四捨五入到固定位數再比較。
  • TypeScript 課第 18 課的函式型別：參數本身可以是函式，例如 random: () => number，呼叫端決定傳哪個函式進來。
  • TypeScript 課第 2 課的參考與複製：陣列是傳參考，slice 回傳新陣列，splice 會改到傳進來的原陣列。
這一課的練習都在頁面裡完成，不需要 API key，也不會呼叫真的模型。從第 2 課起才會在自己的電腦上用官方 SDK 送請求。

一次產生一個 token

大型語言模型（LLM, large language model）是一個「讀一段文字，預測接下來最可能出現什麼」的模型。聊天、摘要、從顧客訊息擷取訂單，全部都是用這個能力做的：你給它一段開頭（叫做 prompt，就是你送給模型的全部文字），它一小段一小段往後接。

它接的單位叫 token（下一節細講，先當成「一小段文字」）。每一步，模型對「下一個 token 是什麼」給出一組機率，從中選一個接上去，再拿接好的整段去預測下一個。用一張玩具表格來看，輸入是「拿鐵一杯」：

目前的文字下一個 token 的候選與機率這次選到
拿鐵一杯「110」0.7、「120」0.2、「大約」0.1110
拿鐵一杯110「元」1.0元
拿鐵一杯110元「。」1.0。
拿鐵一杯110元。（模型判斷說完了）停止

真的模型每一步考慮的是幾萬個候選 token，機率由神經網路算出來；神經網路怎麼算不影響你寫程式時的判斷，這門課不談。你要記住的是這個迴圈：讀進全部文字 → 給出下一個 token 的機率 → 選一個 → 接上去 → 重複。它在什麼時候停下？

  • 模型判斷說完了：API 回應的 stop_reason 是 end_turn。
  • 碰到你設的 max_tokens：這次最多產生幾個 token 的上限。到了就硬生生停下，句子可能斷在一半，stop_reason 是 max_tokens。
  • 碰到停止字串（stop sequence）：你指定「產生到這段文字就停」，stop_reason 是 stop_sequence。

token 不是字元

token 是模型處理文字的單位，可能是一個字、半個詞、一個常見的英文單字或一個標點。計費、長度上限全部以 token 計算，不是字元數。把文字切成 token 的程式叫 tokenizer，每家模型的 tokenizer 都不一樣，同一段文字在不同模型上的 token 數不同。

下面是一個玩具 tokenizer，只為了讓你看見「切法」長什麼樣子。它不是 Claude 的 tokenizer，算出來的數字不能拿來估價。它的規則：認得的詞（像「拿鐵」「latte」）算一個 token，其他中文一個字一個 token，數字三位一組，認不得的符號（像 emoji）拆成 UTF-8 位元組，一個位元組一個 token。

從結果看出三件事：字元數和 token 數對不上；數字、emoji 這類東西常常比你想的多；換一段文字比例就不同。所以：

  • 估預算時可以粗估，但計費和上限判斷要用 Claude 自己算的數字：每次回應的 usage 欄位會告訴你實際用了多少（第 2 課），送出前想先知道就呼叫 token counting API（client.messages.countTokens()，第 13 課）。
  • 不要拿別家的 tokenizer（例如 OpenAI 的 tiktoken）算 Claude 的 token，數字不會一樣，也沒有固定偏多或偏少。
  • 連同一家的不同模型也會不同：官方遷移指南寫明，Claude Opus 4.7 起的模型改用新的 tokenizer，同樣的文字比之前的模型大約多 30% 的 token（依內容不同，最多約 35%）。換模型時要重新量，不能沿用舊的估算。
  • 要一個大概的數量級：官方模型總覽寫，用目前的 tokenizer，1M（一百萬）token 大約是 250 萬個 Unicode 字元。只能拿來估「放不放得下一份文件」，不能拿來算錢。

回到開場的兩個問題。測試隨機失敗：每一步的 token 是照機率抽出來的，上一節的玩具迴圈多跑幾次就會看到不同結果。帳單變 10 倍：計費的是送進去的全部 token（規則、菜單、前面的對話都算）加上模型產生的全部 token，只算顧客那 30 個字一定低估。細節在後面的〈費用怎麼算〉與〈每次不一樣：取樣〉。

費用怎麼算

每次請求的費用是兩部分加起來：

費用（美元）＝ 輸入 token 數 × 輸入單價 ÷ 1,000,000 ＋ 輸出 token 數 × 輸出單價 ÷ 1,000,000
  • 輸入 token：你送出去的全部內容，包括 system prompt（給模型的規則）、整段對話歷史、這次的問題、你附上的菜單或文件。
  • 輸出 token：模型產生的全部內容，包括你看不到的思考。Claude Opus 5.5 的思考（thinking）一直開著、不能關，由模型依題目決定想多少（很簡單的問題可能不想）；想了多少，就以輸出價付多少。
  • 單價以「每百萬 token」（MTok）計，不是每千 token。

context window 與 max_tokens

context window 是一次請求能處理的 token 上限，輸入和這次產生的輸出都算在裡面。Claude Opus 5.5、Sonnet 5.5、Haiku 5.5 的 context window 都是 1M（一百萬）token，一次最多產生 128K token（max_tokens 的上限）。

依官方 context windows 文件（2026-11-01 查詢），有兩種「放不下」，後果不同：

情況API 的反應你會看到
輸入本身就超過 context window直接拒絕HTTP 400 invalid_request_error（prompt is too long），一個字都沒產生
輸入沒超過，但輸入＋max_tokens 超過接受請求，照常產生如果產生到 context window 用完，以 stop_reason: 'model_context_window_exceeded' 停下，回答可能斷在一半
輸入＋max_tokens 不超過正常最壞情況是用完 max_tokens 停下（stop_reason: 'max_tokens'）

第二種最容易漏掉：沒有錯誤、沒有例外，只是回答少了後半段。第 2 課會教你檢查 stop_reason，不把半截回答送給顧客。（Claude 4.5 之前的舊模型在第二種情況會直接回錯誤；這門課用的模型都是上面的行為。）

max_tokens 是這次最多產生多少 token，包括看不到的思考。官方文件寫明思考 token 是 max_tokens 的一部分、以輸出價計費、也算進 context window。所以把 max_tokens 設很小想讓回答變短，常見的結果是思考就用完了額度，回答被截斷。要短回答，在 prompt 裡要求（第 4 課），不是壓低 max_tokens。

對話越來越長時怎麼辦？聊天機器人每一輪都要把前面的對話重送一次（下一節說明為什麼），總有一天會太長、太貴。最直接的做法是從最舊的對話開始丟，但有兩個規則：

  • 一問一答要一起丟。只丟問題、留下回答，模型會看到一句沒頭沒尾的回答。模型是用 user、assistant 輪流的對話訓練的，修剪後的歷史也要從 user 開始、保持輪流。
  • 這次的問題一定要留。連它都放不下，就該回報「問題太長」，而不是送一個空請求。

最後一個判斷：1M token 很大，但不代表該塞滿。context 越長，每次請求越貴、越慢；官方文件也指出 token 越多，模型找回前面細節的準確度會下降（稱為 context rot）。只放這次回答需要的東西，是資深工程師的基本功：第 8～10 課的 RAG 就是「只挑相關的文件段落放進去」。

💡 實務上：對話要記多久，是產品決定，不只是技術問題
LINE 客服機器人上線後，PM 常會問「顧客隔天回來，機器人還記得昨天聊的嗎？」。先講清楚取捨：記得越多輪，每次越貴、越慢，舊內容還可能干擾這次回答（例如昨天問的品項今天已經下架）。常見做法是對話歷史存在自己的資料庫，閒置一段時間就開新對話，修剪以 token 數判斷而不是固定留幾輪。真正要一直記得的事（例如顧客對牛奶過敏），存成資料庫欄位、每次放進 system，不要指望它留在會被修剪的歷史裡。

每次不一樣：取樣

回到第一節的迴圈。模型給的是機率，選 token 的方式叫取樣（sampling）：照機率「抽」一個，機率 0.7 的比較常被抽到，但不是每次。所以同樣的輸入會得到不同的輸出，這叫不確定性（non-determinism）。長的回答有幾百步，每一步都可能抽到不同的 token，整句話一模一樣的機會很低。

舊的 API 有 temperature、top_p、top_k 這幾個參數調整抽籤的方式，網路上很多範例寫「把 temperature 設成 0，輸出就固定」。現在不行了：

  • API 版本 2026-10-21（@anthropic-ai/sdk 1.0.0 起預設使用，這門課用 1.3.0）送了 temperature、top_p 或 top_k 一律回 400，就算送的是預設值也一樣；SDK 1.x 的型別也把它們拿掉了。
  • 官方遷移指南也說明，Claude 4.7 起的模型本來就只接受預設值，沒有其他設定可以取代。

所以要接受「輸出會變」，從設計上處理：

  • 測試不比對整句。判斷「有沒有提到 110 元」「有沒有拒答」，或要求模型照固定格式輸出（第 5 課的結構化輸出），再用一組題目評分（第 11 課的 eval）。
  • 必須一字不差的文字由程式產生。退款政策、法律聲明、價格表，從資料庫或範本產生，不讓模型改寫。
  • 快取回應要想清楚：把模型回答存起來給下一個人用，等於固定了那一次抽到的版本；好壞都會被重複使用。

練習 4 會寫出第一節那個抽籤迴圈。重點是：抽籤用的 random() 由外面傳進來，測試就能傳入固定的數字，讓結果每次一樣。這是測試任何有亂數的程式的通用做法。

💡 實務上：客服回報「同一個問題，兩個顧客得到不同答案」
這是 LLM 功能上線後很常見的回報。先分兩種：措辭不同但事實一樣，是取樣造成的正常現象，跟 PM 說明不能也不該保證一字不差；事實不同（一個說 110 元、一個說 120 元），才是要修的 bug，通常是資料沒放進請求，或規則沒寫清楚。要求「每次一模一樣」的內容（價格、政策），改成由程式從資料庫產生。

API 沒有記憶、知識會過期、會說錯

這三個限制決定了後面大半門課要做的事：

限制咖啡店會出的事怎麼處理
無狀態（stateless）：API 不記得上一次請求顧客先問拿鐵，再問「那大杯呢？」，只送第二句的話，模型不知道「那」是什麼每次把需要的對話歷史全部送過去，記憶由你的程式負責（第 2 課）；歷史太長就修剪（練習 3）
知識截止日（knowledge cutoff）：訓練資料只到某個時間（Claude Opus 5.5 是 2026 年 6 月，官方模型總覽）上週拿鐵漲到 120 元，模型不知道價格、營業時間從你的資料庫取出，放進這次請求（第 4 課），文件多的時候用 RAG 挑出相關段落（第 8～10 課）
幻覺（hallucination）：講出聽起來合理、其實錯的內容編出菜單上沒有的「抹茶拿鐵 95 元」，語氣很肯定要求回答附上引用來源（第 10 課），用 eval 持續量錯誤率（第 11 課）

無狀態要特別記住：聊天介面（例如 claude.ai）看起來記得你說過的話，是因為介面每次都幫你把歷史重送。你寫的後端也要自己做這件事，這也是為什麼對話越長、每一輪越貴。

資深視角：什麼時候不要用 LLM

LLM 擅長的是處理自然語言：看懂顧客寫得亂七八糟的訊息、整理、摘要、改寫、分類。它不擅長、也不該負責的是有明確規則、答案只有一個的事：

  • 計算訂單金額、折扣、找零：用程式算。模型可能算錯，而且每次不一樣。
  • 判斷現在有沒有營業：用程式比對時間。模型不知道現在幾點。
  • 判斷這位顧客能不能看這筆訂單：用程式檢查權限（第 12 課會講為什麼不能讓模型決定）。

常見的好分工是：模型理解語言，程式執行規則。例如顧客說「我要兩杯熱拿鐵一杯不要糖」，模型負責把它轉成 [{ item: '拿鐵', qty: 2 }, …]（第 5 課），金額由程式依資料庫的價格計算。

決定要不要用 LLM 時問兩個問題：錯了的代價多大？（推薦飲品講錯沒關係，退款金額講錯會出事）錯了能不能被發現？（能用程式驗證格式、能讓人確認、能引用來源，就比較可以放心交給它）。兩題的答案都不好，就用傳統程式寫。

練習

練習 1：寫 estimateCost(usage, price)：用本課的公式算出一次請求的費用（美元），四捨五入到小數第 6 位。usage 的欄位名稱跟 API 回應的 usage 一樣；price 是每百萬 token 的單價。

練習 2：寫 checkContext(req, contextWindow)，在送出前判斷請求放不放得下：輸入（system＋全部歷史＋這次問題）大於 contextWindow 回 'too_long'（API 會回 400）；輸入沒超過、但輸入＋maxTokens 大於 contextWindow 回 'output_may_be_cut'（API 接受，但回答可能以 model_context_window_exceeded 停下）；其他回 'ok'。剛好等於上限不算超過。

練習 3：寫 trimHistory(turns, budget)，把對話歷史修剪到總 token 數 ≤ budget。turns 是一問一答交錯、以 user 開頭、以 user（這次的問題）結尾。規則：從最舊的一組問答（一則 user 加一則 assistant）開始丟，丟到放得下為止；不能拆開一問一答，結果必須以 user 開頭；最後這次的問題永遠保留；不能改到傳進來的陣列。連最後這句都放不下時，丟出 new Error('問題太長')。這題只處理 token 數；真的送給 Opus 5.5 時，刪掉舊訊息還要一起拿掉留下來的 thinking block，否則較新的帳號會收到 400，第 2 課會說明。

練習 4：寫出第一節的抽籤迴圈。sampleNext(options, random)：呼叫一次 random() 得到 0（含）到 1（不含）之間的數 r，依序累加每個候選的機率，回傳第一個「r 小於累加值」的 token。例如機率 0.7、0.2、0.1 時，r 在 [0, 0.7) 選第一個、[0.7, 0.9) 選第二個、其餘選第三個。浮點數加總可能不到 1（試試 0.7 + 0.2 + 0.1），r 很接近 1 時都沒選到，就回傳最後一個。generate(prompt, steps, random)：從 prompt 開始，每一步用「最後一個 token」查 NEXT，抽一個接上去，最多 steps 步；查不到就停止。只能用傳進來的 random，不能用 Math.random。

練習 5：客服回答偶爾措辭不同，同事建議「把 temperature 設成 0 就會每次一樣」。用 @anthropic-ai/sdk 1.3.0 呼叫 claude-opus-5-5，會怎樣？

✓ b：API 版本 2026-10-21（SDK 1.0.0 起預設）送 temperature、top_p、top_k 一律回 400，就算是預設值也一樣，SDK 1.x 的型別也拿掉了它們，所以 a、d 都錯；c 錯在串流只是改變回應送回來的方式（第 3 課），跟取樣無關。正確做法是不比對整句、用結構化輸出與 eval 驗證，必須固定的文字交給程式產生。

練習 6：顧客先問「拿鐵一杯多少？」，第二句問「那大杯呢？」，你的程式只把第二句送給 API。模型會怎樣？

✓ b：Messages API 是無狀態的，每次請求只看得到這次送去的內容，所以 a 錯；API 沒有 session 的概念，c 錯；只送一句完全合法，不會 400，d 錯（模型多半會反問或亂猜）。記憶是你的程式負責的：每次把需要的歷史一起送（第 2 課），太長就用練習 3 的方式修剪。

練習 7：context window 是 1M token，你的輸入是 990K token，max_tokens 設 16K，送給 claude-opus-5-5。會發生什麼？

✓ b：Claude 4.5 之後的模型只有在輸入本身超過 context window 時才回 400，輸入＋max_tokens 超過時照樣執行、到上限就停，所以 a 錯（那是舊模型的行為）。自動摘要是要另外開啟的 compaction 功能，不會自己發生，c 錯；API 不會替你換模型，d 錯。要避免截斷就縮短輸入，而且塞滿 context 本來就又貴又慢。

練習 8：用 OpenAI 的 tiktoken 估算 Claude 的 token 數，結果會怎樣？

✓ b：token 的切法由各家 tokenizer 決定，中英文都會不同，所以 a、c 錯；差距也沒有固定方向，不能當上限或下限，d 錯。連 Claude 自己的新舊模型都不同（Claude 4.7 起的模型，同樣文字約多 30% token）。粗估預算可以，計費與上限判斷要用 countTokens() 或回應的 usage。

常見錯誤

  • 把字數當 token 數：中文、數字、emoji 的 token 數都跟字數不同，預算會算錯。要準確數字用 token counting API 或回應的 usage。
  • 估費用只算顧客的問題：每次請求都要重送 system prompt、文件和整段歷史；輸出（含思考）單價是輸入的 5 倍。
  • 以為 context window 只管輸入：輸入塞滿後，回答會以 model_context_window_exceeded 被切斷，而不是報錯。送出前用練習 2 的方式檢查。
  • 把 max_tokens 壓很小讓回答變短：思考也吃 max_tokens，常常思考完就沒額度了。要短回答用 prompt 要求。
  • 以為模型記得上一句：API 無狀態，歷史要自己送；修剪時一問一答一起丟，這次的問題一定留著。
  • 用 temperature 求穩定：新版 API 會回 400。穩定性靠結構化輸出、驗證與 eval，固定的文字由程式產生。
  • 讓模型算金額、判斷營業時間：有明確規則的事用程式做，模型負責理解語言。

小結

  • LLM 一次產生一個 token：讀進全部文字、給出下一個 token 的機率、抽一個接上去，直到說完、碰到 max_tokens 或停止字串。
  • token 不是字元，每家（甚至每代模型）的 tokenizer 都不同；準確數字看 usage 或用 token counting API。
  • 費用＝輸入 token × 輸入單價＋輸出 token × 輸出單價，單價以每百萬 token 計；輸出是輸入的 5 倍價，思考算輸出。
  • context window 包含輸入和輸出：輸入本身超過 → 400；輸入＋max_tokens 超過 → 接受，但可能以 model_context_window_exceeded 被切斷。1M 不代表該塞滿。
  • 取樣讓每次輸出不同；API 版本 2026-10-21 起不能用 temperature，要從設計上接受變化。
  • API 無狀態、有知識截止日、會產生幻覺；有明確規則、錯了代價高又難發現的事，用程式做。
