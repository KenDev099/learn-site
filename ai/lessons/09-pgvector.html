階段 4：RAG：讓模型根據你的資料回答 · 第 9 課

pgvector：在 PostgreSQL 裡存向量與搜尋

第 8 課把門市手冊切成塊、算出每一塊的 embedding，再用暴力搜尋找出最像的幾塊。那些塊和向量都放在記憶體的陣列裡：程式一重啟就不見，每次啟動都要重新 embedding（要花錢），資料一多，每個問題都要把全部的塊算一遍。

這一課用 pgvector 把它們存進 PostgreSQL。

這課的路線：
  1. 為什麼放在 PostgreSQL：重啟就不見、每次重算要錢的問題，為什麼不必另外架向量資料庫（開場問題的最小答案）。
  2. 練習環境與三個距離運算子、建表：三種距離各怎麼算，向量欄位怎麼建，為什麼每一塊要記下 embedding 模型。
  3. 寫入與更新：店長改了手冊一句話，怎麼只重算那一塊的 embedding。
  4. 查詢、HNSW 索引：top-k 怎麼寫成一句 SQL，資料多了怎麼用索引換速度，怎麼確認真的用到索引。
  5. 過濾的陷阱：加了 WHERE 條件結果卻變少，客服回報「問過敏原只回一筆」時怎麼處理。
這課會用到：
  • 第 8 課的檢索：cosine 相似度比較兩個向量的方向，top-k 取最像的前 k 塊，每塊記下 embed_model，換模型時才知道哪些要重算。
  • PostgreSQL 課第 20 課的索引：讓資料庫不用掃完整張表就找到資料，規劃器會判斷用索引是否比較快。
  • PostgreSQL 課第 21 課的 EXPLAIN：印出資料庫打算怎麼執行查詢，看得到有沒有用到索引。
  • PostgreSQL 課第 31 課的 INSERT … ON CONFLICT：資料已經存在就改成更新，一句 SQL 完成「有就改、沒有就新增」。

為什麼放在 PostgreSQL

專門存向量、做相似度搜尋的資料庫叫向量資料庫（vector database），例如 Pinecone、Qdrant、Weaviate。咖啡店一開始不需要它，因為你的 PostgreSQL 加上 pgvector 擴充就能做同樣的事。pgvector 是 PostgreSQL 的擴充（extension），提供三樣東西：vector 型別、計算距離的運算子、向量索引。

放在同一個資料庫的好處，是那些你已經會的東西全部可以直接用：

  • 過濾與 JOIN：「只找過敏原文件」「只找還在販售的商品」就是一個 WHERE，要商品價格就 JOIN products。分成兩個系統時，要先在向量資料庫找、再回 PostgreSQL 查，兩邊的資料還可能不同步。
  • 交易：文件改版時，更新塊和刪除舊塊在同一個交易裡完成，搜尋不會看到改到一半的文件。
  • 備份、權限、監控：沿用現有的，不用多維護一套系統。

什麼時候才考慮專門的向量資料庫：向量多到上億筆、每秒查詢量非常高、需要它們特有的功能，而且你已經量過 pgvector 撐不住。幾百萬筆以內，pgvector 加上 HNSW 索引通常足夠。這是「先用最簡單、能滿足需求的工具，等量測出瓶頸再換」的判斷。

練習環境與三個距離運算子

練習用 PGlite：編譯成 WebAssembly、在 Node 程序裡執行的 PostgreSQL，資料放在記憶體，不用裝 Docker、不開 port。這門課鎖定 @electric-sql/pglite 0.5.13（PostgreSQL 18.6）加 @electric-sql/pglite-pgvector 0.0.14，本機實測載入的 pgvector 是 0.8.7。這兩個套件的版本是綁在一起的（0.0.14 對應 0.5.13），升級時要一起升。helpers/pg.ts 的 openVectorDb() 已經寫好，開一個載入 vector 擴充的全新資料庫。

正式環境用一般的 PostgreSQL 伺服器，要裝了 pgvector 的：Docker 可以用 pgvector/pgvector:0.8.7-pg18-trixie 映像（NestJS 課 compose.yaml 用的 postgres:18.6-alpine 沒有 pgvector）；雲端資料庫多半內建，在資料庫裡執行一次 CREATE EXTENSION vector 就能用。SQL 寫法完全一樣。

向量在 SQL 裡寫成方括號包起來、逗號分隔的字串，再轉型成 vector：

SELECT '[1,2,3]'::vector <=> '[2,4,6]'::vector;   -- 0：方向一樣，cosine 距離是 0
SELECT '[1,0]'::vector   <=> '[0,1]'::vector;     -- 1：互相垂直，沒有關係

pgvector 提供三個常用的距離運算子。注意它們算的都是距離：越小越像，所以 ORDER BY 距離 由小到大，就是由像到不像。

運算子意思對應的索引運算子類別什麼時候用
<=>cosine 距離 = 1 − cosine 相似度vector_cosine_ops預設選它：只看方向，不受向量長度影響
<->L2 距離（直線距離）vector_l2_opsembedding 模型的文件指定用 L2 時
<#>負的內積vector_ip_ops向量都正規化過、想省一點計算時（排序結果跟 cosine 一樣）

<#> 回傳負數，是因為 PostgreSQL 的索引只能由小到大掃描，內積是越大越像，取負號之後才能一樣 ORDER BY … ASC。第 8 課說過 Voyage 的 embedding 已經正規化，這時 cosine 和內積的排序相同；這門課一律用 <=>，分數最好理解：相似度 = 1 − (embedding <=> 查詢向量)。

建表：vector(n) 與 embed_model

這是練習 1 要寫的 migration（PostgreSQL 課第 22 課：schema 的變更寫成可以重複執行的 SQL 檔）。每一列是一塊：

CREATE TABLE IF NOT EXISTS chunks (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  doc_id text NOT NULL,              -- 哪一份文件，例如 'hours'
  seq integer NOT NULL,              -- 文件裡的第幾塊，從 0 開始
  heading_path text[] NOT NULL,      -- ['門市手冊', '過敏原']，引用來源時用（第 10 課）
  content text NOT NULL,
  content_hash text NOT NULL,        -- 內容的雜湊，用來判斷要不要重算 embedding
  embedding vector(64) NOT NULL,     -- 64 維：練習用的 toyEmbed
  embed_model text NOT NULL,         -- 這個向量是哪個模型算的
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (doc_id, seq)
);
  • vector(n) 是固定 n 維的向量欄位。維度寫在型別上，資料庫會擋下維度不對的向量；只寫 vector 不給維度，什麼長度都收，而且建不了 HNSW 索引。不要用 real[] 或 jsonb 存向量：它們沒有距離運算子，也不能建向量索引。
  • 維度跟著模型走：練習的 toyEmbed 是 64 維，Voyage voyage-4 預設 1024 維。換一個維度不同的模型，就要寫 migration 改欄位型別，並把全部的塊重算。本機實測 pgvector 0.8.7：vector 欄位要建 HNSW 索引最多 2,000 維，超過就報錯；halfvec（每個數字用一半的空間存）最多 4,000 維，所以選 voyage-4 的 2048 維時要改用 halfvec(2048)。
  • embed_model：第 8 課說過不同模型的向量不能互相比較。換模型時如果沒記錄，新舊向量混在同一張表，搜尋結果會悄悄變差，沒有任何錯誤訊息。記下來才能查出「還有哪些塊是舊模型算的」並重算。
  • UNIQUE (doc_id, seq)：同一份文件的第幾塊只有一列。下一節的 ON CONFLICT (doc_id, seq) 就是靠它判斷「這一塊已經存在，改成更新」。

migration 要能重複執行，所以每一句都加 IF NOT EXISTS：CREATE EXTENSION IF NOT EXISTS vector、CREATE TABLE IF NOT EXISTS，索引也一樣，但 CREATE INDEX IF NOT EXISTS 必須寫出索引名稱（沒有名字就沒辦法判斷「是不是已經有了」）。

💡 實務上：換 embedding 模型是一次資料遷移
維度不同要改欄位型別；維度相同也要全部重算，因為不同模型的向量不能互相比較。常見做法是新模型先寫進新欄位或新表，背景重算完、用 eval 比較過，再把查詢切過去，最後刪掉舊的。這段期間查詢向量和文件向量一定要用同一個模型，所以查詢程式要知道目前用哪個 embed_model。跟 PM 估時程時，重算的 API 費用和時間要一起算進去。

寫入與更新：內容雜湊與 UPSERT

手冊會改。店長把「可頌含奶油與小麥」改成「可頌含奶油、小麥與蛋」，整份 50 塊只有一塊變了。如果每次都把 50 塊重算 embedding，就是花 50 倍的錢和時間做白工。做法是替每塊記下內容雜湊（content hash）：用文字算出一個固定長度的值（例如 SHA-256），文字一樣雜湊就一樣，文字改了一個字雜湊就完全不同。比雜湊就知道哪些塊要重算，不用把整段內容拿出來比。

import { createHash } from 'node:crypto'
const contentHash = (text: string) => createHash('sha256').update(text).digest('hex')

雜湊的是「送去 embedding 的那段文字」。練習 2 送的是標題路徑加內容（embedText(c)，已經寫好），所以標題改了也會重算。一份文件的更新分三步：

  1. 讀出現有的雜湊與模型：SELECT seq, content_hash, embed_model FROM chunks WHERE doc_id = $1。
  2. 挑出要重算的塊，一次批次呼叫 embed：新的塊、雜湊不同的塊，以及 embed_model 跟這次不同的塊（換了模型，內容沒變也要重算）。embedding API 都接受一次送很多段文字，一次呼叫比逐塊呼叫快，也比較不會被限流。沒有要重算的就不要呼叫。
  3. 在一個交易裡寫入與刪除：每一塊用 UPSERT 寫入，再刪掉 seq 大於等於新塊數的舊塊（文件變短了，舊的第 5 塊已經不存在，留著會被搜到）。
INSERT INTO chunks (doc_id, seq, heading_path, content, content_hash, embedding, embed_model)
VALUES ($1, $2, $3, $4, $5, $6::vector, $7)
ON CONFLICT (doc_id, seq) DO UPDATE SET
  heading_path = EXCLUDED.heading_path, content = EXCLUDED.content,
  content_hash = EXCLUDED.content_hash, embedding = EXCLUDED.embedding,
  embed_model = EXCLUDED.embed_model, updated_at = now();

DELETE FROM chunks WHERE doc_id = $1 AND seq >= $2;   -- $2 是新的塊數；一定要有 doc_id 條件

EXCLUDED 是「這次想插入、但因為衝突沒插進去的那一列」，PostgreSQL 課第 31 課教過。向量用 helpers/pg.ts 的 toSql(v) 轉成 '[0.1,0.2,…]' 字串，當成參數傳、在 SQL 裡寫 $6::vector。所有值都用 $1、$2 參數傳，不要拼進 SQL 字串：文件內容裡有單引號（店員's 推薦）時，拼接的 SQL 會直接壞掉，內容是使用者寫的時候就是 SQL injection。

PGlite 的交易寫法：

await db.transaction(async tx => {
  await tx.query('INSERT …', [...])     // 交易裡一律用 tx：用 db.query 會排隊等這個交易結束，PGlite 就卡住了
  await tx.query('DELETE …', [...])
})                                       // callback 正常結束就 COMMIT，丟錯就 ROLLBACK

正式環境用 pg 的連線池時，是 Node 課第 20 課的 BEGIN／COMMIT／ROLLBACK 寫法，SQL 本身一樣。

embedding 放在交易外面呼叫。呼叫外部 API 可能要好幾秒，甚至逾時；在交易裡等它，連線和鎖會一直被佔住，其他請求跟著排隊。所以順序是：先讀、在交易外呼叫 embed、拿到所有向量後才開交易寫入。embed 失敗時還沒寫任何東西，資料表自然維持原狀；寫到一半出錯（例如某個向量維度不對）時，交易把已經寫進去的也回滾。
💡 實務上：文件更新通常交給背景工作
店長在後台按「儲存」時，常見做法是先存好文件、丟一個「重建這份文件的塊」的工作到佇列，由背景程式呼叫 upsertDoc，不要讓店長的請求等 embedding API。因為有內容雜湊，同一份文件重跑幾次結果都一樣，失敗了直接重試就好。也別忘了整份文件被刪除或下架時，要把它的塊一起刪掉，不然顧客還會搜到已經不存在的規定。每次更新記下重算與刪除了幾塊，費用突然變高時才查得出是哪份文件在反覆重算。

查詢：ORDER BY 距離 LIMIT k

top-k 搜尋就是一句 SQL。第 8 課在 JavaScript 裡算全部的相似度再排序，現在交給資料庫：

SELECT doc_id, seq, content, 1 - (embedding <=> $1::vector) AS score
FROM chunks
WHERE doc_id = ANY($2::text[])          -- 只搜這幾份文件
ORDER BY embedding <=> $1::vector       -- 距離由小到大 = 由像到不像
LIMIT 5;
  • 查詢向量用參數傳：db.query(sql, [toSql(queryVector), ['hours', 'menu']])。1024 個數字拼進 SQL 字串又長又難除錯，也會養成拼接 SQL 的習慣；用參數傳，資料庫把它當成一個值，不會當成 SQL 解讀。
  • 排序用距離，分數另外算：SELECT 裡算 1 - 距離 當分數給程式用，ORDER BY 直接寫 embedding <=> $1。pgvector 的索引只在「ORDER BY 距離運算子 由小到大，加上 LIMIT」時用得到；寫成 ORDER BY score DESC 結果一樣，但永遠用不到索引。
  • 過濾寫在 WHERE：先過濾再取前 k 名。如果先 LIMIT 5 取全部文件的前 5 名、再在 JavaScript 裡留下 hours，可能只剩 1 筆甚至 0 筆。
  • 可選的條件：沒給 docIds 時不過濾，可以寫成 WHERE ($2::text[] IS NULL OR doc_id = ANY($2::text[]))，參數傳 null；不必組兩種 SQL 字串。
  • 分數門檻：分數太低的塊多半不相關，放進 prompt 只會干擾模型。結果已經依分數排序，拿回來後 filter(r => r.score >= minScore) 就好；門檻要用 eval 決定（第 11 課），第 10 課會用它判斷「資料不夠，不回答」。

HNSW 索引：用一點準確度換速度

沒有索引時，上面那句 SQL 會把每一列的距離都算一次再排序，跟第 8 課的暴力搜尋一樣，資料量變成 100 萬塊就太慢了。向量沒辦法像數字一樣用 B-tree 排序，所以 pgvector 提供近似最近鄰（ANN, approximate nearest neighbor）索引：不保證找到真正最近的那幾個，但只看一小部分資料就找到「幾乎最近」的，用一點準確度換大量速度。

HNSW 是其中最常用的一種。你可以把它想成一張分好幾層的「鄰居關係圖」：搜尋時從上層粗略地跳到大概的區域，再到下層一步步往更近的鄰居走。細節不用記，要記的是它的取捨：

  • 查得快、查詢品質好；代價是建索引比較慢、比較吃記憶體，而且結果是近似的。
  • 近似的意思是偶爾會漏掉一兩個真正的最近鄰。衡量的指標叫召回率（recall）：真正最近的 k 筆裡，有多少比例被找回來。要不要接受，用第 11 課的 eval 量，不是用感覺。
  • 每次查詢先取多少候選由 hnsw.ef_search 決定，預設 40。調高會更準、更慢。
CREATE INDEX IF NOT EXISTS chunks_embedding_hnsw
  ON chunks USING hnsw (embedding vector_cosine_ops);

括號裡的 vector_cosine_ops 是運算子類別（operator class），決定這個索引是照哪一種距離建的。索引的運算子類別要和查詢的運算子一致：用 vector_l2_ops 建的索引只服務 <->，查詢寫 <=> 時規劃器用不到它，悄悄退回全表掃描。資料少時看不出差別，資料一多就慢下來。

確認有沒有用到索引，用 PostgreSQL 課第 21 課的 EXPLAIN：

Limit
  ->  Index Scan using chunks_embedding_hnsw on chunks
        Order By: (embedding <=> '[…]'::vector)

看到 Index Scan using … on chunks、而且有 Order By 這一行，就是索引在幫你排序。如果是 Seq Scan 加 Sort，就是全部算完再排。

有一個容易誤會的地方：資料很少時，PostgreSQL 選全表掃描是對的。練習的表只有 1,000 筆，全部算一次比走索引還快，規劃器會選 Seq Scan。這時想確認「索引能不能被用到」，在交易裡關掉全表掃描再看計畫：

await db.transaction(async tx => {
  await tx.query('SET LOCAL enable_seqscan = off')   // 只在這個交易裡生效
  const { rows } = await tx.query('EXPLAIN SELECT …', [toSql(v)])
})

SET LOCAL 的設定在交易結束時自動恢復；寫成 SET 會一直留在這條連線上，正式環境的連線池會把這條連線借給別的請求，它們全部都不能全表掃描了。enable_seqscan = off 只用在檢查與測試，不要寫進正式的查詢。

💡 實務上：向量欄位和索引很佔空間
1024 維的 vector 每列約 4 KB（每個數字 4 bytes），100 萬塊就是 4 GB，HNSW 索引還要再加。估資料庫容量時要算進去；SELECT 不需要向量時不要把它撈回來。大量匯入時先寫資料、最後再建索引比較快；正式環境對大表建索引用 CREATE INDEX CONCURRENTLY（PostgreSQL 課第 22 課），避免鎖住寫入。

過濾的陷阱：iterative scan 與部分索引

索引上線後，客服回報：「問過敏原，只回一筆。」資料表裡明明有 20 塊過敏原的內容。原因是 HNSW 處理 WHERE 的順序：

索引只負責「找最近的 40 個」（ef_search），WHERE 是拿到候選之後才套用。1,000 塊裡只有 3% 是過敏原，40 個候選平均只有 1 個符合。這不是 bug，是近似索引的工作方式。三種處理方式：

  • iterative scan（pgvector 0.8 起）：候選被過濾掉太多時，索引繼續往下掃，直到湊滿 LIMIT 的筆數，或掃到 hnsw.max_scan_tuples（預設 20,000）為止。設定值有兩種：strict_order 保證結果嚴格依距離排序；relaxed_order 允許結果稍微亂序，但召回率比較好。
  • 部分索引（PostgreSQL 課第 27 課）：常用、固定的條件，可以建只包含那些列的索引：CREATE INDEX … USING hnsw (embedding vector_cosine_ops) WHERE doc_id = 'hours'。適合條件的值只有少數幾種時；值很多就不實際。
  • 讓規劃器用一般索引：條件夠嚴格、而且 doc_id 有 B-tree 索引時（例如 UNIQUE (doc_id, seq) 附帶的那個），PostgreSQL 常會直接用 B-tree 找出那 30 塊、全部算距離再排序。這是精確搜尋，結果完全正確；本機實測練習 1 的表就是這樣。陷阱發生在過濾欄位沒有合適的索引、或條件看起來不嚴格的時候，所以上線後要用 EXPLAIN 和 eval 確認。

iterative scan 的設定一樣用 SET LOCAL 只開在這次查詢的交易裡。relaxed_order 可能讓結果稍微亂序，pgvector 文件的做法是把查詢包進 MATERIALIZED 的 CTE，外面再排一次：

await db.transaction(async tx => {
  await tx.query('SET LOCAL hnsw.iterative_scan = relaxed_order')
  return (await tx.query(`
    WITH hits AS MATERIALIZED (
      SELECT doc_id, seq, content, embedding <=> $1::vector AS distance
      FROM chunks WHERE doc_id = $2
      ORDER BY distance LIMIT $3
    )
    SELECT doc_id, seq, content, 1 - distance AS score FROM hits ORDER BY distance + 0`,
    [toSql(v), 'allergens', 5])).rows
})

MATERIALIZED 讓 CTE 先單獨執行完（用索引取出 5 筆），外層再對這 5 筆排序。distance + 0 是 pgvector 文件特別寫的：PostgreSQL 17 以後要加 + 0，外層的排序才不會被最佳化掉。

💡 實務上：召回率要量，不要用感覺判斷
HNSW 是近似的，ef_search、過濾條件、iterative scan 都會改變找回來的塊。調整這些設定前後，拿一批真實問題各查兩次：一次走索引，一次在交易裡 SET LOCAL enable_indexscan = off 做精確搜尋，前 k 名重疊的比例就是索引的召回率。至於「找回來的塊是不是使用者要的」，則要靠一組「問題 → 應該找到的塊」的 eval（第 11 課）。客服回報「明明手冊有寫，卻說找不到」時，先用 EXPLAIN 看計畫、再查召回率，不要先改 prompt。

練習

在 learn 資料夾執行 node check.mjs ai 09，會建立 ai/practice/work/09/。練習 2～4 的測試會用你在練習 1 寫的 ex1.sql 建表，所以照順序做。每個測試檔會開一個記憶體裡的 PGlite，第一次開要幾秒鐘，不需要 Docker、也不需要任何 API key。fixtures.ts 是測試用的工具，不用改。做完後可以在 ai/practice 執行 node --env-file-if-exists=.env work/09/live.ts，把咖啡店的文件寫進資料庫再搜尋：.env 裡有 VOYAGE_API_KEY 時用 voyage-4（1024 維），沒有就用 toyEmbed（只比字面，結果會比較怪）。

練習 1：寫 ex1.sql 這份 migration：啟用 vector 擴充；建 chunks 表，欄位照課文（id、doc_id、seq、heading_path text[]、content、content_hash、embedding vector(64)、embed_model、updated_at timestamptz 預設 now()），全部 NOT NULL，加上 UNIQUE (doc_id, seq)；再建 embedding 的 HNSW 索引，用 cosine 距離。整個檔案要能連續執行兩次都不出錯。

練習 2：完成 upsertDoc(db, docId, chunks, embed, model)。讀出這份文件現有的 content_hash 與 embed_model；只把新的、雜湊變了、或模型不同的塊（雜湊用寫好的 contentHash(embedText(c))）一次交給 embed，沒有就不要呼叫；然後在一個 db.transaction 裡用 INSERT … ON CONFLICT (doc_id, seq) DO UPDATE 寫入這些塊，並刪除這份文件 seq 大於等於新塊數的舊塊。回傳 { embedded, deleted }（重算了幾塊、刪了幾塊，刪除筆數可以用 affectedRows）。所有值都用參數傳。測試會檢查 embed 是在 db.transaction 之前呼叫的，也會讓 embed 失敗、讓某一塊寫入失敗，檢查資料表都維持原狀。

練習 3：完成 search(db, queryVector, { k, docIds, minScore })，回傳 { docId, seq, content, score }[]：score 是 1 − cosine 距離，由高到低，最多 k 筆；有 docIds 時只搜這些文件（先過濾再取前 k 名）；有 minScore 時不回傳分數比它低的（0 也是門檻：cosine 相似度可以是負的）。排序和距離要在 SQL 裡用 <=> 做，ORDER BY 要寫成索引用得到的形式，查詢向量用參數傳。測試傳入的 db 包了一層，會記錄你送出的每一句 SQL。

練習 4：完成兩個函式。explainUsesIndex(db, queryVector)：在交易裡 SET LOCAL enable_seqscan = off，對 SELECT id FROM chunks ORDER BY embedding <=> $1::vector LIMIT 5 跑 EXPLAIN（結果每一列的欄位叫 QUERY PLAN），計畫裡出現 Index Scan using … on chunks 時回傳 true。searchFiltered(db, queryVector, { k, docId })：在交易裡 SET LOCAL hnsw.iterative_scan = relaxed_order，查出這份文件最像的 k 塊，回傳跟練習 3 一樣的形狀，依分數嚴格由高到低（relaxed_order 會稍微亂序，要用課文的 MATERIALIZED CTE 再排一次）。測試在 1,000 塊、只有 3% 屬於該文件的表上查，並拿掉 doc_id 的 B-tree 索引、關掉全表掃描，模擬大資料表上規劃器選 HNSW 的情況；查完後連線的設定要恢復原狀。

練習 5：索引建成 USING hnsw (embedding vector_l2_ops)，查詢寫 ORDER BY embedding <=> $1 LIMIT 5。會用到這個索引嗎？

✓ pgvector 的索引綁定一種距離。不一致時規劃器根本不會選它，查詢退回全表掃描：結果是對的（所以 d 錯），只是資料一多就很慢，而且沒有任何錯誤訊息。跟資料量無關（c）。用 EXPLAIN 確認有沒有 Index Scan。

練習 6：HNSW 查詢加了 WHERE doc_id = 'allergens'，LIMIT 5 卻只回 1 筆，資料表裡明明有 20 塊過敏原的內容。最可能的原因是？

✓ 近似索引是「先取候選、再過濾」，條件越嚴格，剩下的越少。pgvector 0.8 起的 hnsw.iterative_scan 會繼續往下掃到湊滿筆數；常用的固定條件也可以建部分索引。這是近似索引的工作方式，不是資料壞了（a）；SQL 的語法順序也沒有問題（c），任何 WHERE 都能和距離排序一起用（d）。

練習 7：FAQ 只改了一個錯字，你的匯入程式每次都把整份 50 塊重新 embedding。主要的問題是？

✓ 每次 embedding 都是一次付費的 API 呼叫，文件多、更新頻繁時，全部重算的費用和時間會是增量更新的幾十倍，還更容易碰到限流。同一個模型對同一段文字算出的向量基本上相同，重算不會讓它變準或變不準（c 錯）；向量欄位可以像一般欄位一樣 UPDATE（d 錯）。

常見錯誤

  • 沒記錄 embed_model：換模型後新舊向量混在一起，搜尋悄悄變差。每一塊記下模型，換模型時把舊的全部重算。
  • 用 real[]、jsonb 或沒寫維度的 vector 存向量：沒有距離運算子、建不了索引、擋不住維度錯誤。用 vector(n)。
  • 索引的運算子類別與查詢的運算子不一致：vector_l2_ops 配 <=> 用不到索引。用 EXPLAIN 確認。
  • ORDER BY score DESC：結果一樣，但索引只認「ORDER BY 距離運算子 由小到大」，永遠用不到。分數在 SELECT 裡算，排序用距離。
  • 過濾在 LIMIT 之後做：在 JavaScript 裡過濾前 k 名，結果會少於 k 筆。條件寫在 SQL 的 WHERE；HNSW 加嚴格條件時開 iterative scan。
  • 把向量或文字拼進 SQL：內容有單引號就壞掉，還有 SQL injection 的風險。一律用參數，向量用 $1::vector。
  • 每次全部重算 embedding：用內容雜湊，只重算新的和改過的。
  • 在交易裡等 embedding API：外部呼叫可能好幾秒，連線和鎖被佔住。先在交易外拿到向量，再開交易寫入。
  • 用 SET 而不是 SET LOCAL：設定留在連線上，連線池把它借給下一個請求，影響到不相關的查詢。

小結

  • pgvector 讓 PostgreSQL 存向量、算距離、建向量索引；塊和商品、訂單在同一個資料庫，過濾、JOIN、交易、備份都是現成的。幾百萬筆以內先用它。
  • vector(n) 把維度寫在型別上；記下 embed_model，換模型或換維度就是一次 migration 加全部重算。
  • <=> 是 cosine 距離，相似度 = 1 − 距離；ORDER BY embedding <=> $1 LIMIT k，過濾寫在 WHERE，值一律用參數。
  • 用內容雜湊只重算變動的塊，一次批次呼叫 embed；寫入、刪除多出來的塊放在同一個交易，embed 在交易外呼叫。
  • HNSW 是近似最近鄰索引，用一點召回率換速度；運算子類別要和查詢一致，用 EXPLAIN 確認；資料少時全表掃描是正確的選擇。
  • 嚴格的過濾條件會讓近似索引回傳太少結果：用 SET LOCAL hnsw.iterative_scan、部分索引，或讓規劃器用 B-tree 做精確搜尋。
