階段 2：讓輸出可靠 · 第 5 課

結構化輸出與驗證：從顧客訊息擷取訂單

咖啡店開放用 LINE 點餐。顧客打的是自然語言：「兩杯拿鐵少冰，再一個可頌，外帶」「老樣子」「拿鐵算我 100 就好」。後端要的卻是一筆訂單：哪些商品、各幾個、多少錢。把自然語言整理成固定格式的資料，正是 LLM 擅長的事；但模型的輸出是要寫進資料庫、要收錢的，它不能「大部分時候對」。

這一課寫出一條從顧客訊息到訂單的可靠管線：模型負責「理解」，金額、庫存、要不要建立訂單由你的程式決定。

這課的路線：
  1. 為什麼不能直接 JSON.parse、structured outputs：自由文字的 JSON 會怎麼壞，怎麼讓 API 保證回傳符合 schema 的 JSON（開場問題的最小答案）。
  2. schema 保證什麼、給模型「不知道」的出口：通過 schema 的資料還可能錯在哪，顧客說「老樣子」時怎麼不讓模型硬編一筆訂單。
  3. 業務驗證：價格、庫存、能不能下單，為什麼一律由你的程式和資料庫決定。
  4. 有上限的回饋重試：驗證失敗時怎麼請模型修正，試幾次就該放棄。
  5. 圖片與 PDF、資深視角：同一套做法怎麼用在收據照片和報價單，為什麼結構化輸出讓 AI 功能測得了。
這課會用到：
  • TypeScript 課第 26 課的 zod：用 schema 驗證外部資料，safeParse 不丟錯，回傳成功的資料或錯誤清單。
  • TypeScript 課第 27 課的 Result：用 { ok: true, … } | { ok: false, … } 回傳預期中的失敗，不丟例外。
  • 第 2 課的回應與測試：stop_reason 說明回答能不能用，多輪對話要把 assistant 的完整 content 放回歷史，練習用假的 API 判分。

為什麼不能直接 JSON.parse

最直覺的寫法：在 prompt 裡寫「請用 JSON 回答，格式是 {…}」，拿到文字後 JSON.parse。測試幾次都正常，上線後每天幾千則訊息，下面三種情況一定會出現：

// 1. 多了說明文字：JSON.parse 直接丟 SyntaxError
好的，以下是整理後的訂單：
{"intent":"order","items":[{"product":"拿鐵","quantity":2}]}

// 2. 形狀不對：少了 items、數量變成字串、商品名稱多了「熱」
{"intent":"order","product":"熱拿鐵","quantity":"兩杯"}

// 3. 被 max_tokens 截斷（第 2 課）：後半段不見了
{"intent":"order","items":[{"product":"拿鐵","quan

第 1、3 種會丟錯，至少你知道出事了。第 2 種最危險：JSON.parse 成功，程式拿著 undefined 的 items 和字串的數量繼續往下跑，可能建出一張金額是 NaN 的訂單。這些不是模型「不聰明」，而是自由文字本來就沒有任何保證。第 1 課說過模型的輸出每次不一樣，你沒辦法靠多寫幾句「一定要用 JSON」把機率降到零。

新模型也不能用以前「在 messages 最後放一則 assistant 訊息，先寫好 { 讓模型接著寫」的預填（prefill）技巧：Opus 5.5 會回 400。要固定格式，用的是下一節的結構化輸出。

structured outputs：output_config.format 與 messages.parse

結構化輸出（structured outputs）是在請求裡附上一份 JSON Schema，API 在模型產生文字的時候就限制它，只能產生符合這份 schema 的 JSON：不會有前後的說明文字、不會少欄位、型別一定對。JSON Schema 是描述「一份 JSON 長什麼樣子」的標準格式，例如「這是物件，有 intent 欄位，型別是字串」。

你不需要手寫 JSON Schema。用 zod 定義形狀，SDK 的 zodOutputFormat 會轉成 JSON Schema 放進請求；再用 client.messages.parse() 取代 create()，SDK 收到回應後會用同一份 zod schema 驗證，結果放在 parsed_output，而且有完整的 TypeScript 型別：

import * as z from 'zod'
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod'

const OrderIntentSchema = z.object({
  intent: z.enum(['order', 'question', 'unclear']),
  items: z.array(z.object({
    product: z.enum(['美式咖啡', '拿鐵', '卡布奇諾', '伯爵紅茶', '可頌', '起司蛋糕']),
    quantity: z.int().min(1).max(20),
  })),
  note: z.string().nullable(),
})

const response = await client.messages.parse({
  model: 'claude-opus-5-5',
  max_tokens: 16000,
  system: SYSTEM,
  messages: [{ role: 'user', content: wrapMessage(text) }],   // 跳脫後包進 <message>（第 4 課）
  output_config: { format: zodOutputFormat(OrderIntentSchema) },
})

response.parsed_output   // 型別：{ intent: 'order' | 'question' | 'unclear'; items: …[]; note: string | null } | null
  • zodOutputFormat 從 @anthropic-ai/sdk/helpers/zod 匯入。這門課用 SDK 1.3.0 與 zod 4.6.7，寫法和 TypeScript 課第 26 課的 zod 一樣；z.int() 是 zod 4 的整數型別。
  • 參數寫在 output_config: { format }。網路上的舊範例會寫頂層的 output_format，那個參數已經淘汰，不要用。
  • note 用 .nullable() 而不是 .optional()：欄位一定要出現，沒有內容就是 null。結構化輸出要求每個物件 additionalProperties: false，zod 的 z.object 交給 zodOutputFormat 時會自動加上。
  • 不支援的組合：結構化輸出不能和 citations（第 10 課的引用來源）同時用，會回 400。

其他供應商也有一樣的功能，名稱不同：OpenAI 叫 structured outputs（response_format 或 Responses API 的 text.format），也有「JSON mode」這種只保證是 JSON、不保證形狀的較弱版本。架構相同：定義 schema、讓 API 限制輸出、程式再驗證一次。

schema 保證什麼、不保證什麼

把 SDK 1.3.0 實際送出的 schema 印出來（測試的 requests[0].body.output_config 就看得到），會發現跟你寫的 zod 不完全一樣：

"quantity": { "type": "integer", "description": "{minimum: 1, maximum: 20}" },
"product":  { "type": "string",  "description": "{enum: [\"美式咖啡\",\"拿鐵\",…]}" },
"note":     { "type": ["string", "null"] }

API 端的限制只支援 JSON Schema 的一部分：minimum、maximum、字串長度、複雜的陣列條件都不支援。SDK 的處理方式是把這些條件從 schema 拿掉、寫進 description 給模型參考，收到回應後再在本機用 zod 驗證。實測 SDK 1.3.0 的 zodOutputFormat 連 enum 也搬進了 description（官方文件說 API 支援 enum，這是這個 SDK 版本的轉換行為），所以商品名稱同樣是在本機才擋下來。三層的分工：

誰檢查擋得住什麼失敗時
API（產生時限制）是合法的 JSON、物件形狀、必填欄位、型別（字串、整數、陣列、null）、沒有多餘的欄位不會發生，除非被截斷或拒答
SDK 在本機用 zod數值範圍、字串長度、enum（SDK 1.3.0）、refine 這類自訂規則parse() 丟出 AnthropicError，訊息以 Failed to parse structured output 開頭，附上哪個路徑錯了
你的程式（業務驗證）商品今天有沒有賣、庫存夠不夠、價格多少、這位顧客能不能下單由你決定怎麼回顧客

還有兩種情況 schema 管不到，第 2 課的 stop_reason 在這裡一樣重要：

  • 被截斷（max_tokens）：JSON 只寫了一半，parse() 解析失敗，丟出同一種 AnthropicError。
  • 拒答（refusal）：回應可能沒有任何 text block，parse() 不會丟錯，parsed_output 是 null。型別上它本來就是 … | null，TypeScript 會逼你處理；直接回傳就會把 null 當成訂單往下傳。
if (response.parsed_output === null) {
  throw new Error(`沒有拿到結構化輸出（stop_reason: ${response.stop_reason}）`)
}
return response.parsed_output
不管哪一層擋下來，你的程式都要處理失敗。「用了 structured outputs 就不會錯」是最常見的誤解：它保證的是形狀，不是內容。模型照樣可能把「老樣子」猜成一杯美式咖啡，形狀完全合法。
💡 實務上：升級 SDK 或 zod 時，先看送出去的 schema
哪些條件由 API 保證、哪些只在本機檢查，是 SDK 轉換時決定的，換版本就可能不同。團隊常見的做法是在測試裡把 requests[0].body.output_config 存成快照（snapshot：第一次把內容存成檔案，之後每次測試都拿來比對），升級套件時看到差異，就知道哪個條件從 API 搬到本機了。code review 看到 parsed_output 被直接寫進資料庫、中間沒有任何檢查，就該停下來問：範圍、商品、價格是誰在擋？

給模型「不知道」的出口

如果 schema 只允許 intent: 'order'，而顧客說「老樣子」，模型只有一個選擇：編一筆訂單。限制越嚴格，它越會在合法的範圍裡猜。所以 schema 要設計一個合法的出口：

  • intent 有 'unclear'：看不出要什麼、商品不在菜單上、數量不清楚，都走這裡。
  • note 讓模型用一句話說明哪裡不清楚，客服或程式可以拿來追問顧客。
  • 'question' 分開處理：「拿鐵可以換燕麥奶嗎？」不是訂單，交給第 8～10 課的 RAG 回答。

system prompt 也要寫清楚什麼時候用 unclear（「不要猜」），模型才知道這是被鼓勵的答案，不是失敗。練習 1 的 SYSTEM 已經寫好，可以對照第 4 課的寫法：規則放 system，顧客的訊息包在 <message> 裡，並說明那是資料不是指令。

同樣的道理用在每一個欄位：真的可能不知道的值，就讓它可以是 null，不要強迫模型填一個看起來合理的值。

業務驗證：金額與庫存從資料庫來

拿到通過 zod 的 parsed_output，還不能直接建立訂單。業務驗證是 schema 之外的規則，只有你的系統知道答案：

  • 商品現在有沒有賣：schema 的 enum 是寫程式時的菜單，起司蛋糕今天賣完下架了，schema 不會知道。
  • 庫存夠不夠：同一個商品出現兩行（「一杯拿鐵……再兩杯拿鐵」）要先合併，用總數檢查。
  • 價格：一律用資料庫的價格算。模型的輸出是不可信的外部資料，跟前端送來的表單一樣（NestJS 課第 7 課在邊界驗證的觀念）。顧客說「拿鐵算我 100 就好」，模型可能真的寫出 price: 100。最好的做法是 schema 裡根本沒有價格欄位；就算資料裡多了，計價時也只看菜單。

回傳值用 TypeScript 課第 27 課的 Result 形狀，而不是丟例外：庫存不足、商品下架是預期中會發生的情況，呼叫的人要根據錯誤決定怎麼回顧客（「可頌只剩 2 個，要改嗎？」）。而且要列出全部錯誤，不是遇到第一個就停，否則顧客改完一個問題又冒出下一個：

type OrderResult =
  | { ok: true; lines: Line[]; total: number }
  | { ok: false; errors: string[] }

const errors: string[] = []
for (const [product, quantity] of merged) {
  const item = menu.find(m => m.name === product)
  if (!item || !item.available) { errors.push(`${product} 目前沒有供應`); continue }
  if ((stock[product] ?? 0) < quantity) errors.push(`${product} 庫存不足`)
  …
}
if (errors.length) return { ok: false, errors }

金額是整數（元），小計和總額都用整數乘加，不會有 TypeScript 課第 5 課的浮點數誤差。stock[product] ?? 0 這個細節也要注意：查不到庫存當成 0，不是當成無限；寫成 stock[product] < quantity 時，undefined < 2 是 false，等於沒檢查。

正式系統裡，這一步是在資料庫交易裡查菜單、檢查並扣庫存（PostgreSQL 課的交易與鎖），練習用傳進來的 menu 和 stock 代替。重點是分工：模型只負責把文字變成「顧客想要什麼」，事實與決定都在你的程式和資料庫。

💡 實務上：LLM 擷取的結果，先給人確認再成立
LINE 點餐、客服單分類、從 email 建立預約，這類功能上線時通常不會讓模型的輸出直接變成訂單，而是回一張「確認卡」：「兩杯拿鐵、一個可頌，共 290 元，確認送出？」顧客按下確認，才進入建立訂單的 API；那支 API 跟 App 點餐用的是同一支，驗證也是同一套。這樣模型猜錯的代價只是多問一次。PM 會關心「多一步確認會不會掉單」，資安會關心「一句話能不能改到價格」，有了這條分工，兩個問題都答得出來。

有上限的回饋重試

zod 驗證失敗時（例如 quantity: 0），同樣的請求再送一次，結果多半差不多。比較有效的是回饋重試：把上一次的回答和「錯在哪裡」告訴模型，請它修正。做法跟第 2 課的多輪對話一樣，把 assistant 的完整 content 放回歷史，再加一則 user 訊息：

要做回饋，就需要失敗那次的原始回應，但 parse() 失敗時只丟出錯誤，拿不到回應本身。所以拆成兩步：parse() 其實就是 create() 加上對文字跑 format.parse()，自己分開做就能保留回應：

const format = zodOutputFormat(OrderIntentSchema)
const response = await client.messages.create({ …, messages, output_config: { format } })   // API 錯誤在 try 外面，直接往外丟
const raw = response.content.filter(b => b.type === 'text').map(b => b.text).join('')
try {
  return format.parse(raw)          // 跟 messages.parse 一樣：JSON 解析＋zod 驗證，失敗丟 AnthropicError
} catch (e) {
  if (!(e instanceof Anthropic.AnthropicError)) throw e
  messages.push(
    { role: 'assistant', content: response.content },
    { role: 'user', content: `你上一次的回答沒有通過驗證：\n${e.message}\n請修正後重新回答。` },
  )
}

錯誤訊息裡有 items.0.quantity: Too small: expected number to be >=1 這類路徑，模型讀得懂，比「格式不對，再試一次」有用得多。哪些錯誤適合回饋重試：

情況怎麼處理原因
zod 驗證失敗、JSON 被截斷回饋重試，有上限模型改得了
stop_reason: 'refusal'不重試，回傳失敗同樣的內容再問一次，通常還是拒答（第 14 課再談備援）
400、401、403、帳號額度用完不重試，往外丟是請求或帳號的問題，送幾次都一樣，只會浪費錢
429、529、連線錯誤往外丟SDK 的 maxRetries 已經自動重試過（第 2 課），第 14 課再設計完整策略

上限一定要有。每次重試都是一次完整的 API 呼叫，輸入還越來越長（多了上一次的回答和錯誤說明），延遲和費用一起變大。一般 2～3 次就夠；用完還是失敗，就回 ok: false，讓顧客看到「我沒看懂，可以再說一次嗎？」。把重試次數記進 log，第 13 課算成本、第 15 課做監控時，重試率突然升高通常代表 prompt 或 schema 改壞了。

💡 實務上：重試失敗的原始回應要留下來
回饋重試用完還是失敗的那幾筆，是改 prompt 和 schema 最好的素材：把顧客原文、模型最後的回答、zod 的錯誤訊息一起記進 log（顧客個資要遮罩），每週挑幾筆看。常見的發現是「商品名稱多了『熱』『大杯』」這類規律，修法通常是在 system prompt 補一句對照規則，或在 schema 加一個欄位，而不是調高重試次數。這些案例之後也能直接變成第 11 課 eval 的測資。

圖片與 PDF 也能擷取

同樣的做法可以用在文字以外的輸入：顧客上傳的收據照片、廠商寄來的 PDF 報價單。把檔案放進 user 訊息的 content block，搭配同一套 structured outputs：

const pdf = readFileSync('quote.pdf').toString('base64')   // base64 字串，不能有換行
await client.messages.parse({
  model: 'claude-opus-5-5',
  max_tokens: 16000,
  messages: [{
    role: 'user',
    content: [
      { type: 'document', source: { type: 'base64', media_type: 'application/pdf', data: pdf } },
      { type: 'text', text: '擷取這份報價單的品項、單價與有效期限。' },
    ],
  }],
  output_config: { format: zodOutputFormat(QuoteSchema) },
})
  • 圖片用 { type: 'image', source: { type: 'base64', media_type: 'image/jpeg', data } }，放在文字前面。
  • 同一個檔案要用很多次時，先用 Files API（client.files.upload()，已經正式推出，不需要 beta 標頭）上傳，之後把 block 的 source 寫成 { type: 'file', file_id } 引用，不必每次重傳。
  • 上限：一個請求最多 32 MB、600 頁（PDF 頁數與圖片合計）。大檔案的每一頁都算 token，記得估成本。

這一節只示範，不練習。業務驗證的原則完全一樣：報價單上的金額要跟採購系統核對，不能因為「是從 PDF 讀出來的」就直接相信。

資深視角：結構化輸出是可測試性的基礎

  • 可以比對欄位，不必比對句子。自由文字每次措辭不同，測試只能用「包含某個詞」這種脆弱的判斷；結構化輸出可以斷言 intent === 'unclear'、items 正好是兩杯拿鐵。第 11 課的 eval 就是建立在這上面。
  • schema 是介面，要有版本。改 schema 就像改 API 的回應格式：下游的程式、eval、存在資料庫的舊結果都要跟著檢查。加欄位比改欄位安全。
  • schema 越大越容易出錯。欄位少、每個欄位意思明確、加上 .describe() 說明，比一個塞滿可選欄位的大物件可靠。一次請求做一件事。
  • 什麼時候不用 LLM。顧客是在 App 裡點選商品和數量，就直接是結構化資料，不需要模型；LLM 只用在真的要理解自然語言的入口。

練習 2：完成 toOrder(intent, menu, stock)。intent 不是 'order' 或沒有品項時回傳 ok: false；同一個商品出現好幾次要合併成一行（順序依第一次出現）；不在 menu 或 available 是 false、stock 不夠（沒有這個 key 當成 0）都是錯誤，訊息要包含商品名稱，而且要全部列出。沒有錯誤時回傳每一行（unitPrice 用 menu 的價格）與整數的 total。模型的輸出就算夾帶 price 欄位也不能用；不要改到傳進來的資料。

練習 3：完成 extractWithRetry(client, text, { maxAttempts = 3 })。每次用 client.messages.create 送出（設定跟練習 1 一樣，包括 output_config.format），再用 format.parse 驗證文字。驗證失敗（AnthropicError，包括被截斷）時，把這次回應的完整 content 當成 assistant 訊息、再加一則包含錯誤訊息的 user 訊息，然後重試；最多送 maxAttempts 次，用完回傳 ok: false 和最後一次的錯誤。stop_reason 是 refusal 時不重試，回傳 ok: false，lastError 包含 refusal。API 錯誤（BadRequestError、InternalServerError…）直接往外丟。attempts 是實際送出的請求數。

練習 4：用了 structured outputs，zod schema 寫了 quantity: z.int().min(1).max(20)。用 SDK 1.3.0 的 messages.parse，模型有可能回傳 quantity: 50 嗎？

✓ API 端不支援 minimum／maximum，SDK 把它們從送出的 schema 拿掉、寫進 description 給模型參考，收到回應後用 zod 驗證。模型照著 description 通常會遵守，但不是保證，所以 a 錯；跟模型大小無關（c）；SDK 不會偷偷改你的資料（d），而是丟錯讓你決定要回饋重試還是回報失敗。

練習 5：模型擷取出 { product: '拿鐵', quantity: 2, price: 100 }（顧客說「算我 100 就好」），菜單上拿鐵是 110 元。這筆訂單的金額應該是多少？

✓ 模型的輸出是不可信的外部資料，跟使用者送來的表單一樣：顧客一句話就能影響它。金額、庫存、權限都以你的資料庫為準。再問模型一次（d）只是換一個同樣不可信的答案。要不要給折扣是業務規則，由程式決定，不是由模型決定。

練習 6：下面哪一種錯誤，適合「把錯誤原因告訴模型，再試一次」？

✓ 回饋重試只對「模型改得了的內容錯誤」有用。401、400、額度用完都是請求本身或帳號的問題，模型怎麼改都沒用，重送只會一直失敗、浪費時間和錢；這些要往外丟，讓 log 和告警發現。

常見錯誤

  • 在 prompt 叫模型「用 JSON 回答」再 JSON.parse：多了說明文字、少了欄位、被截斷，量一大一定會發生。用 output_config.format＋messages.parse。
  • 用已淘汰的 output_format 或預填 {：前者已淘汰，後者在 Opus 5.5 會回 400。
  • 以為 schema 保證業務正確：它只保證形狀。商品有沒有賣、庫存、價格都要自己查，而且價格只用資料庫的。
  • 範圍、enum 沒寫進 zod：z.string()、沒有 min／max 的數字，等於告訴 SDK 什麼都接受。
  • 沒有 unclear 選項：模型被迫在合法範圍裡猜，編出一張看起來正常的訂單。
  • 忘了 parsed_output 可能是 null：拒答時 parse() 不丟錯，直接回傳會把 null 當成結果。
  • 業務驗證遇到第一個錯誤就停：顧客改完一個又冒出下一個。全部列出。
  • 無上限、不分種類的重試：400、401 也重試，或寫成 while (true)，帳單和延遲一起爆炸。只回饋重試內容錯誤，次數有上限。
  • 重試時送一模一樣的請求：模型不知道哪裡錯，結果多半一樣。把 assistant 的回應和錯誤訊息加進對話。

小結

  • 自由文字沒有任何格式保證；要固定格式用 structured outputs：output_config: { format: zodOutputFormat(Schema) } 搭配 client.messages.parse()，結果在有型別的 parsed_output。
  • API 保證 JSON 形狀、必填欄位與型別；SDK 1.3.0 把範圍、長度、enum 搬進 description，在本機用 zod 驗證，失敗或截斷時丟出 AnthropicError；拒答時 parsed_output 是 null。
  • schema 要有「不知道」的出口（unclear、可以是 null 的欄位），模型才不會被迫亂猜。
  • 業務驗證在 schema 之後：商品是否供應、合併後的庫存、價格一律從資料庫來；回傳 Result、列出全部錯誤。
  • 回饋重試：把 assistant 的完整 content 和錯誤說明加進對話再試，有次數上限；拒答與 API 錯誤不回饋重試。
  • 圖片、PDF 用 image／document block（或 Files API 的 file_id），一樣搭配 structured outputs。
  • 結構化輸出讓測試和 eval 可以比對欄位，是後面每一課的基礎。

練習 7：code review 看到這段組 prompt 的程式，menu 已經依 id 排序。哪裡會出事？

const system = `價格只根據 <menu> 回答。
<menu>
${menu.map(m => `${m.id}｜${m.name}｜${m.price}`).join('\n')}
</menu>`

✓ 不是親手寫在程式裡的文字，放進標籤前都要跳脫，後台的品名、公告、資料庫查回來的資料都算。最好整個專案只有一個組 prompt 的函式負責跳脫。a 錯在顧客輸入混進 system，正是讓模型分不清規則和資料的寫法。（第 4 課）

練習 8：客服助理開了 prompt caching，system 裡沒有時間戳記或亂數，log 卻顯示快取幾乎沒命中。先查什麼？

✓ 快取是前綴比對，沒寫 ORDER BY 時資料庫不保證順序，菜單順序一變，system 和後面全部重算，API 也不會報錯。資料排序、物件的鍵順序固定。c 錯在 user 訊息在 system 後面，日期只影響它之後的部分，前面的 system 照樣命中。（第 4 課）

練習 9：為了統一語氣，同事加了三組 few-shot，都是顧客問價格、助理報出價格。之後「燕麥奶拿鐵多少？」又開始被報出菜單上沒有的價格，為什麼？

✓ 範例是 prompt 裡最強的訊號，有時強過規則。2～3 組、彼此不同，而且一定要有「不知道」或「沒有」的情況。a 錯在只有最後一則 assistant 才算預填，中間的是正常的對話歷史。（第 4 課）

練習 10：擷取訂單的 schema 寫 intent: z.enum(['order', 'question'])，顧客傳「老樣子」，結果是一杯美式咖啡，形狀完全合法。怎麼修？

✓ schema 只允許 order 和 question 時，模型只能在合法範圍裡猜。給它合法的「不知道」出口，system 也說明這是被鼓勵的答案。a 錯在美式咖啡有賣、庫存也夠，業務驗證只檢查事實，看不出這不是顧客要的。（第 5 課）

練習 11：業務驗證這樣寫，merged 是合併過的品項，stock 只有部分商品有 key。哪裡會出事？

for (const [product, quantity] of merged) {
  const item = menu.find(m => m.name === product)
  if (!item || !item.available) { errors.push(`${product} 目前沒有供應`); continue }
  if (stock[product] < quantity) errors.push(`${product} 庫存不足`)
  lines.push({ product, quantity, unitPrice: item.price })
}

✓ undefined < 2 是 false，查不到庫存就通過了。要寫成 (stock[product] ?? 0) < quantity，查不到當成 0。c 錯在價格一律用資料庫的，顧客一句話就能影響模型的輸出，折扣是業務規則，由程式決定。（第 5 課）

練習 12：同事的重試是 zod 驗證失敗時，把同一份 messages 原封不動再送，最多 3 次。log 顯示常常三次都錯在同一個欄位，怎麼改？

✓ 一模一樣的請求，結果多半差不多；把錯在哪（例如 items.0.quantity）告訴模型才改得了，次數仍然有上限。a 錯在每次重試都是一次完整的呼叫，加次數只是讓延遲和費用一起變大，該做的是看失敗的原文去改 prompt 或 schema。（第 5 課）
