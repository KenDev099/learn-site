階段 3：工具與 Agent · 第 6 課

Tool use：讓模型呼叫你的函式

顧客在官網的客服視窗問：「我 10 分鐘前點的拿鐵好了嗎？」模型讀過大量文字，但它沒看過你的資料庫，不知道這張訂單是製作中還是已經可以取餐。這時它只有兩種回答：誠實說「我不知道」，或是編一個看起來合理的答案。後者更糟，顧客會跑到櫃台領一杯還沒做好的咖啡。

這一課讓模型在需要時「請你查」：你告訴它有哪些函式可以用，它在回答途中提出「我要呼叫 get_order_status，參數是 42」，由你的程式執行、把結果送回去，它再根據真實資料回答。

這課的路線：
  1. 分工：模型提出，你的程式執行：模型沒看過你的資料庫，怎麼讓它先「請你查」再回答（開場問題的最小答案）。
  2. 一輪工具呼叫的完整流程、定義好工具：查一次訂單要送幾次請求、每則訊息放什麼，工具的說明怎麼寫，模型才會用對。
  3. 執行與回傳：模型給的參數為什麼要先驗證，查不到或出錯時怎麼回傳，模型才看得懂。
  4. 平行呼叫、控制什麼時候用工具：顧客一次問兩張訂單時怎麼同時查，怎麼讓模型該查的時候不要用猜的。
  5. 其他做法與資深視角：SDK 的 Tool Runner、MCP 和別家的 function calling 跟你手寫的版本是什麼關係。
這課會用到：
  • 第 2 課的回應：content 是 block 陣列，stop_reason 說明模型為什麼停下，assistant 要把完整 content 放回歷史。
  • TypeScript 課第 26 課的 zod：safeParse 驗證外部資料，不丟錯，回傳成功的資料或錯誤。
  • TypeScript 課第 9 課的 Promise.all：同時等好幾個非同步工作，全部成功才成功，一個失敗就整個失敗。

分工：模型提出，你的程式執行

tool use（也叫 function calling）是讓模型在回答過程中，要求呼叫你定義的函式。名字容易讓人誤會，先把分工講清楚：

  • 模型只「提出」：它在回應裡放一個 tool_use block，寫著要呼叫哪個工具（name）、參數是什麼（input），以及這次呼叫的編號（id）。它碰不到你的資料庫，也不會執行任何程式。
  • 你的程式「執行」：讀出 tool_use block，自己呼叫對應的函式，把結果包成 tool_result block 送回去，用 tool_use_id 說明這是哪一次呼叫的結果。

所以權限、驗證、記錄全部是你的責任。模型提出 get_order_status({ order_id: 42 })，你的程式可以照做、可以拒絕、也可以發現 42 號根本不是這位顧客的訂單（第 12 課會處理這件事）。模型給的參數跟顧客在表單裡打的字一樣，是不可信的外部資料。

這課講的是你自己定義的工具（client tools）。Anthropic 另外有幾個在它的伺服器上執行的工具，例如網頁搜尋、程式碼執行，那些不需要你執行，結果直接出現在回應裡；這門課不會用到。

一輪工具呼叫的完整流程

以「3 號訂單好了嗎？」為例，從顧客發問到得到答案，你的程式要送兩次請求：

第 ② 步的回應長這樣（Opus 5.5 通常先有一個空的 thinking block）：

{
  "stop_reason": "tool_use",
  "content": [
    { "type": "thinking", "thinking": "", "signature": "EqQB…" },
    { "type": "tool_use", "id": "toolu_01A…", "name": "get_order_status", "input": { "order_id": 3 } }
  ],
  …
}

第 ④ 步要送的 messages：

messages: [
  { role: 'user', content: '3 號好了嗎？' },
  { role: 'assistant', content: response.content },        // ② 的完整 content，原樣放回
  { role: 'user', content: [
    { type: 'tool_result', tool_use_id: 'toolu_01A…', content: '{"id":3,"status":"ready",…}' },
  ] },
]

幾個規則，違反任何一個都會收到 400 或悄悄變差：

  • assistant 放完整的 content，不是只放文字。tool_result 要對應到 assistant 訊息裡的 tool_use id，少了 tool_use block，API 不知道你在回答什麼。這就是第 2 課說「原樣送回」的原因。
  • 每個 tool_use 都要有 tool_result，而且緊接在下一則 user 訊息裡。漏掉一個，API 會回 400（錯誤訊息類似「tool_use ids were found without tool_result blocks immediately after」）。
  • tool_result 要放在 user 訊息 content 的最前面，想補充文字只能放在它們後面。
  • 第二次請求也要帶同樣的 tools：歷史裡有 tool_use，請求卻沒有工具定義，會被拒絕。

tool_result 的 content 可以是字串或 block 陣列，這課一律用 JSON.stringify(結果)：模型讀 JSON 沒有問題，你也不用另外想格式。

定義好工具

工具是請求裡 tools 陣列的一個物件（SDK 的型別是 Anthropic.Tool）：

欄位說明
name只能用英文字母、數字、底線、連字號，1～128 字（^[a-zA-Z0-9_-]{1,128}$），中文和空白會被拒絕。用動詞＋名詞：get_order_status，不要叫 order、tool1。
description模型靠它決定要不要用、什麼時候用。官方文件說這是影響工具表現最大的因素，建議至少 3～4 句：做什麼、什麼時候用（以及什麼時候不要用）、參數的意思、回傳什麼、不回傳什麼。
input_schema參數的 JSON Schema（第 5 課的結構化輸出也用它），type 一定是 'object'。每個參數也寫 description。
stricttrue 時 API 保證模型產生的 input 符合 schema、name 一定是你定義的工具。需要 additionalProperties: false。

比較兩種 description。只寫「查訂單」，模型不知道顧客問「我的拿鐵呢」算不算、沒給編號要怎麼辦、回傳的 status 有哪些值。好的寫法：

查詢一張訂單目前的狀態。顧客問訂單好了沒、做到哪裡、點了什麼時使用；
需要訂單編號，顧客沒給編號時先問，不要猜。
回傳 id、status（preparing 製作中、ready 可以取餐、picked_up 已取餐）、items、orderedAt。

用 zod 寫 schema，一份定義兩個用途

手寫 JSON Schema 容易跟程式裡的型別脫節。用 zod 寫一次，同時拿來產生 input_schema，也拿來在執行前驗證：

import { z } from 'zod'

const GetOrderStatusInput = z.object({
  order_id: z.number().int().positive().describe('訂單編號，正整數，例如 42'),
})

z.toJSONSchema(GetOrderStatusInput)
// { "$schema": "https://json-schema.org/draft/2020-12/schema", "type": "object",
//   "properties": { "order_id": { "type": "integer", "exclusiveMinimum": 0,
//                                 "maximum": 9007199254740991, "description": "訂單編號…" } },
//   "required": ["order_id"], "additionalProperties": false }

這是 zod 4.6.7 實際的輸出：z.object 已經帶 additionalProperties: false 和 required。但 strict: true 支援的 JSON Schema 是一個子集：minimum、maximum、exclusiveMinimum 這類數值限制、minLength／maxLength 都不支援，官方文件寫明用了會回 400。.int() 自己就會產生 maximum，所以直接送這份 schema 會失敗。

練習裡的 toInputSchema() 已經寫好：用 z.toJSONSchema 的 override 選項拿掉這些關鍵字和 $schema。拿掉的限制不會消失，因為執行前你還會用同一個 zod schema 驗證一次。這就是分工：strict 保證形狀（一定有 order_id、一定是整數），zod 在你這邊檢查範圍和業務規則（要是正數）。第 5 課看過 SDK 的 zodOutputFormat 做的是同一件事，只是它把限制搬進 description。

工具越少越好

  • 一個工具做一件事、彼此不重疊。同時有 get_order、get_order_status、find_order_by_id，模型常選錯，你也很難說它錯在哪。官方建議把相關的操作合併成少數幾個工具。
  • 資料固定、又小的東西，直接放進 prompt。營業時間、退款規則每次都一樣，放進 system prompt 就好（第 4 課），做成工具反而多一輪請求、多花錢、多一次延遲。會變的（訂單狀態）、大的（整份商品資料庫）、要依參數查的，才做成工具。
  • 回傳模型需要的欄位就好。把訂單表整列（含顧客電話、內部備註）丟回去，浪費 token，也可能把不該給模型看的資料送出去。
💡 實務上：先列出「模型需要知道什麼」，再決定做不做成工具
咖啡店客服要上線前，PM 通常會給一串問題：訂單好了沒、今天有什麼、能不能退款。資深工程師會逐條分類：會變的、要依顧客查的（訂單狀態）做成唯讀工具；固定的規則（營業時間、退款政策）寫進 system prompt；會改資料的（取消、退款）先不給，或第 7 課那樣經過人確認。第一版通常兩三個唯讀工具就夠，等真實對話紀錄顯示模型缺什麼再加。

執行與回傳：錯誤也是一種結果

拿到回應後，依 name 把每個 tool_use 分派到對應的函式：

const handlers = {
  get_order_status: async (input: unknown) => {
    const parsed = GetOrderStatusInput.safeParse(input)   // 模型給的參數是外部資料，先驗證
    if (!parsed.success) throw new Error('order_id 要是正整數；請向顧客確認訂單編號')
    const order = await db.findOrder(parsed.data.order_id)
    if (!order) throw new Error(`找不到 ${parsed.data.order_id} 號訂單`)
    return order
  },
  get_menu: async () => MENU,
}

有了 strict: true 為什麼還要驗證？strict 只保證符合你送出去的 schema，而那份 schema 已經拿掉了「要是正數」；沒開 strict 的工具、換了供應商、或有人改了 schema 忘記改程式，驗證都是最後一道防線。查資料庫前驗證一次，成本只有幾微秒。

出錯時不要丟出例外讓整個請求失敗，也不要省略那個 tool_result。回一個 is_error: true 的結果，content 寫一句說明：

{ type: 'tool_result', tool_use_id: 'toolu_01A…', is_error: true, content: '找不到 99 號訂單' }
情況錯的做法對的做法
參數不合法（order_id: '12'）照樣查資料庫，或丟錯讓 API 回 500不查；回 is_error「order_id 要是正整數」，模型會改用正確的參數再試，或問顧客
找不到訂單回 null，模型可能誤以為「訂單不存在＝已經取走」回 is_error「找不到 99 號訂單」
資料庫逾時整個請求失敗；或省略這個 tool_result（下一次請求 400）回 is_error「查詢逾時，請稍後再試」，模型會跟顧客說明，不會編答案
模型要求不存在的工具略過回 is_error「沒有 cancel_order 這個工具」

錯誤說明寫給模型看：說清楚哪裡錯、可以怎麼做（「請向顧客確認訂單編號」），比「failed」有用得多。但不要把堆疊追蹤、SQL、連線字串放進去，那些會跟著對話送出去，第 12 課再談怎麼遮蔽。

💡 實務上：工具的錯誤分兩種，處理方式不同
客服回報「機器人說找不到我的訂單」時，你要分得出是模型或顧客能修正的（參數給錯、訂單真的不存在），還是系統出問題（資料庫掛了）。給模型的 is_error 說明要短、可行動；完整的錯誤（含堆疊）寫進你自己的 log，並記下 tool_use_id 方便對照。資料庫逾時這類系統錯誤還要照 Node 課第 18 課的做法發告警，不能只靠模型跟顧客道歉了事。

平行呼叫：一次查好幾張

顧客問「我的 3 號和 5 號訂單好了嗎？」，模型可以在同一則回應裡放兩個 tool_use，這叫平行工具呼叫（parallel tool use），預設就會發生。你的程式要做兩件事：

  1. 同時執行：用 Promise.all，兩個查詢各 200ms，總共 200ms，不是 400ms。在 for 迴圈裡逐一 await 會變成依序執行。
  2. 全部的 tool_result 放在同一則 user 訊息：{ role: 'user', content: [result3, result5] }。拆成兩則 user 訊息不會報錯，但官方文件說明這會讓模型「學到」不要平行呼叫，之後的對話悄悄變慢。
const calls = response.content.filter(block => block.type === 'tool_use')
const results = await Promise.all(calls.map(async block => {
  …執行，成功或失敗都回傳一個 tool_result
}))
// Promise.all 的結果順序跟 calls 一樣，不是誰先完成誰在前

注意 Promise.all 只要有一個 reject 就整個 reject。所以每個工具的錯誤要在自己的 async 函式裡 try/catch，轉成 is_error 的結果，一張訂單查不到不能拖垮另一張。

有副作用的工具（取消訂單、退款）平行執行要小心順序與重複，第 7 課會把這類工具改成「只提出、由人確認」。如果真的需要模型一次只呼叫一個工具，可以送 tool_choice: { type: 'auto', disable_parallel_tool_use: true }。

控制什麼時候用工具

tool_choice 控制模型要不要用工具：

tool_choice意思claude-opus-5-5
{ type: 'auto' }模型自己決定（有 tools 時的預設）可以
{ type: 'none' }這次不准用工具可以
{ type: 'any' }一定要用某個工具400
{ type: 'tool', name }一定要用指定的工具400

強制呼叫工具（any、tool）在 Claude Opus 5.5、Sonnet 5.5、Fable 5.1 會回 400，舊文章常見的寫法在這些模型上不能用。替代做法：

  • 用 auto，在 system prompt 寫清楚「訂單狀態一律用 get_order_status 查，不要猜」，description 也寫明使用時機。
  • 不要假設模型一定會呼叫：auto 不保證。重要的流程要檢查 stop_reason，模型直接回答時就照一般回答處理（用第 2 課的 readAnswer）。
  • 如果你其實只是想拿到固定格式的 JSON（例如從顧客訊息擷取訂單），那不是工具，用第 5 課的結構化輸出（output_config.format），不必假裝成一個工具再強制呼叫。

Opus 5.5 呼叫工具前常會先思考，回應的 content 通常是 [thinking, tool_use, …]，也可能先有一段 text（「我幫你查一下」）。程式一律用 type 過濾，不要假設 tool_use 在第幾個位置。還有一點：只有 stop_reason === 'tool_use' 才執行工具。max_tokens 截斷時，最後一個 tool_use 的參數可能不完整，不能執行。

其他做法與資深視角

  • SDK 的 Tool Runner：client.beta.messages.toolRunner() 搭配 betaZodTool()，會替你跑「送出 → 執行 → 送回」的迴圈並用 zod 驗證參數（SDK 1.3.0 在 beta 命名空間）。先自己寫過一次，你才知道它替你做了什麼、出問題時去哪裡查；第 7 課寫完自己的迴圈後再看它。
  • MCP（Model Context Protocol）：把工具做成獨立伺服器的開放協定。同一組「查訂單」工具做成 MCP 伺服器後，Claude Code、其他 AI 應用程式都能接上。這門課的工具直接寫在後端程式裡，不需要它；什麼時候該用，第 15 課再談。
  • 其他供應商的 function calling 結構幾乎一樣：用 JSON Schema 定義函式、模型回傳「要呼叫哪個函式、參數、呼叫編號」、你執行後帶著同一個編號送回結果。差別在欄位名稱與角色，例如 OpenAI 的 Responses API 回傳 function_call 這種 item，你用 function_call_output 加上 call_id 送回；Claude 則把 tool_use 和 tool_result 放在一般的 assistant／user 訊息裡。
💡 實務上：每次工具執行都留一筆紀錄
上線後最常被問的是「模型為什麼這樣回答顧客」。只要每次執行工具都記下工具名稱、參數（遮蔽個資）、成功與否、耗時和 tool_use_id，就能從一段對話追到它查了哪張訂單、拿到什麼結果。這些紀錄也是第 7 課的 trace、第 11 課的評估和第 15 課可觀測性的原料，晚點補很難補齊。

練習 2：完成 runTools(content, handlers)：對 content 裡每個 tool_use block，用 name 找 handler、傳入 input，全部同時開始執行；回傳 tool_result 陣列，順序跟 tool_use 一樣（不是完成的順序），tool_use_id 對應、成功時 content 是 JSON.stringify(回傳值)。找不到工具或 handler 丟錯時，那一個結果是 is_error: true 加一句說明（包含工具名稱或錯誤訊息），其他結果照常回傳，runTools 本身不丟錯。

練習 3：完成 askWithTools(client, question, deps)。送出帶 orderTools 的請求（MODEL、max_tokens 16000、SYSTEM、一則 user 訊息，不要送強制的 tool_choice）。stop_reason 不是 tool_use 時用 readAnswer 回傳。是 tool_use 時用 runTools 執行：get_order_status 先用 GetOrderStatusInput 驗證，不合法就不呼叫 findOrder，找不到訂單（null）也算錯誤；get_menu 回傳 deps.menu。再送一次（同樣的 tools），messages 依序是 user、assistant（第一次回應的完整 content）、user（全部 tool_result 在同一則），用 readAnswer 回傳第二次的回答。這題只處理一輪，第二次又是 tool_use 時讓 readAnswer 丟錯。

練習 4：模型回應了 tool_use：get_order_status({ order_id: 42 })。這時訂單查詢已經執行了嗎？

✓ 你定義的工具一律由你的程式執行，API 碰不到你的資料庫，所以 a、c 都錯；串流（d）只影響回應怎麼傳過來，不會替你執行任何東西。也因為執行在你這邊，參數驗證、權限檢查、記錄都是你的責任（第 12 課）。

練習 5：一則回應有 3 個 tool_use。你把 3 個 tool_result 分成 3 則 user 訊息送回去，會怎樣？

✓ 官方文件明確建議所有 tool_result 放在同一則 user 訊息；拆開不會報錯（所以不是 c），模型也讀得到全部（不是 d），但它會悄悄停止平行呼叫，原本一輪能查完的事變成好幾輪，延遲和費用都增加，所以也不是「沒差」。

練習 6：查訂單時資料庫逾時。這個 tool_use 的 tool_result 應該？

✓ 少了 tool_result，下一次請求會 400（a）；丟例外（d）讓顧客只看到「系統錯誤」，其他查成功的工具結果也一起浪費；假資料（c）會讓模型對顧客說錯的事。is_error 讓模型知道發生什麼事，可以誠實告訴顧客、改問別的，或稍後再試。

常見錯誤

  • 以為模型會自己執行工具：模型只提出要呼叫什麼，執行、權限、記錄都在你的程式。
  • 沒驗證就拿參數查資料庫：模型給的參數是不可信的外部資料。執行前用 zod safeParse，不合法就回 is_error。
  • assistant 只存文字：tool_result 對應不到 tool_use，下一次請求 400。assistant 一律放完整的 response.content。
  • tool_result 拆成多則訊息，或漏掉某一個：漏掉會 400，拆開會讓模型停止平行呼叫。每個 tool_use 一個結果，全部放在同一則 user 訊息。
  • 出錯時丟例外或回 null：回 is_error: true 和一句說明，其他工具的結果照常送回。
  • 平行的工具用 for 迴圈逐一 await：延遲是全部加總。用 Promise.all，錯誤在每個工具裡各自 catch。
  • 把 zod 產生的 JSON Schema 直接配 strict 送出：minimum、maximum 這類關鍵字 strict 不支援，會 400。先拿掉，範圍改在本機驗證。
  • 工具太多、描述重疊、description 只寫一句：模型選錯工具。少而清楚，寫明什麼時候用、什麼時候不用。
  • 在 Opus 5.5／Sonnet 5.5 用 tool_choice any 或 tool 強制呼叫：會 400。用 auto 加 prompt 指示；只是要 JSON 就用結構化輸出。
  • max_tokens 截斷時照樣執行工具：參數可能不完整。只有 stop_reason === 'tool_use' 才執行。

小結

  • tool use 的分工：模型用 tool_use block 提出 name、input、id；你的程式執行，用帶 tool_use_id 的 tool_result 送回。
  • 一輪工具呼叫要兩次請求：第二次的 messages 是 user、assistant（完整 content）、user（全部 tool_result），而且帶同樣的 tools。
  • 工具定義：英文的動詞＋名詞名稱、寫清楚使用時機的 description、JSON Schema、strict: true（需要 additionalProperties: false，不支援數值與長度限制）。
  • 用同一個 zod schema 產生 input_schema 並在執行前驗證；strict 管形狀，zod 管範圍與業務規則。
  • 錯誤是一種結果：參數錯、找不到、逾時、未知工具都回 is_error: true 與說明，不丟例外、不省略。
  • 平行呼叫用 Promise.all 執行，結果依 tool_use 的順序放在同一則 user 訊息。
  • tool_choice 在 Opus 5.5／Sonnet 5.5 只能用 auto 或 none；固定、小的資料放 prompt，只想要 JSON 就用結構化輸出。
