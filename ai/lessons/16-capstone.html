階段 6：期末專題 · 第 16 課

期末專題：咖啡店客服助理（RAG＋查訂單工具＋防護＋eval＋成本報告）

店長要在官網和 LINE 放一個 AI 客服：回答菜單、價格、過敏原、營業時間與退款規則，也能讓登入的顧客查自己的訂單。前面 15 課你分別做過每一個零件：呼叫 API、結構化輸出、工具、agent 迴圈、切塊與向量搜尋、引用驗證、eval、防護、成本、可靠性、記錄。期末專題把它們組成一個能上線的功能，並交出兩份資深工程師上線前會寫的文件：成本報告與上線檢查清單。

這一課的重點不是新的 API，而是組裝與判斷。學完你會有一個完整的參考實作，之後在工作上做任何 LLM 功能，都可以照這個結構檢查自己少了什麼。

這課的路線：
  1. 需求、架構：助理能做與不能做什麼，一個問題依序經過哪些步驟，每一步是前面哪一課的成果。
  2. 資料進來、助理本體：文件怎麼匯入與檢索，才擋得住來路不明的內容；遮蔽、檢索、agent 迴圈、驗證、過濾為什麼要照這個順序串。
  3. eval 套件、成本報告：怎麼證明改動沒讓品質變差，怎麼從實際的 token 用量算出月費、比較兩個模型。
  4. 上線、上線檢查清單與 ADR：HTTP 端點要先做哪些檢查，上線前要確認的事和設計上的決定怎麼寫成文件。
這課會用到：
  • 第 7 課的 agent 迴圈：模型要用工具就執行、送回結果，直到它回答；用輪數和 token 預算保證一定會停，有副作用的動作只建立申請。
  • 第 10 課的檢索與引用：向量和關鍵字兩路用 RRF 合併，程式驗證回答引用的段落，資料不夠就轉店員。
  • 第 11 課的 eval：一組固定案例，每題跑 3 次評分，PR 讓通過率掉超過門檻就擋下。
  • 第 12 課的防護：模型隨時可能被說服，所以工具權限、個資遮蔽、輸出過濾都寫在程式裡。

需求：先寫下能做與不能做

動手之前，先把範圍寫清楚。AI 功能最常出事的地方，是沒人說過它不能做什麼：模型很樂意答應退款、很樂意幫你查「隔壁那位先生」的訂單。

能做不能做（轉店員）
根據門市文件回答菜單、價格、過敏原、營業時間、會員集點、退款規則，並附上引用來源文件裡沒有的問題（停車、天氣）：不用模型自己的知識補
查詢登入顧客自己的訂單狀態查別人的訂單、透露任何其他顧客的資料
回答一到三句的繁體中文退款、改價、取消訂單這類有副作用的動作：模型只能請顧客找店員（第 7 課的人工確認）

「轉店員」在程式裡是一個明確的結果：status: 'abstain'，回答固定是「這個問題我先幫你轉給店員」。它不是失敗，而是助理知道自己不該回答。後面的 eval 會專門檢查該轉的有沒有轉。

架構：一個問題走過的路

顧客的一個問題，依序經過下面這些步驟。每一步都是前面某一課的成果，旁邊三件事（log、限流、預算）不在回答的路徑上，但每次都要做。

程式切成一題一個檔案，每個檔案是一個函式，它需要的東西都從參數傳進來（依賴注入，dependency injection）：資料庫、embedding 函式、Anthropic client、目前時間、寫 log 的函式。這樣測試時可以換成假的：假的 client 回放固定回應、假的時鐘不用真的等、假的檢索直接回傳指定的資料。如果把全部寫進一個大函式、裡面自己 new Anthropic()、自己連資料庫，就只能整個一起測，而且每次測試都要花錢。

資料進來：匯入與檢索（練習 1、2）

第 9 課的 chunks 表多加一張 docs 表，把信任程度（trust）記在文件上：official 是店家自己寫的，quarantined（隔離）是來路不明、暫時不能用的。練習資料夾裡那份顧客投稿的 FAQ（第 12 課看過，裡面藏了一段 prompt injection）就是 quarantined。

CREATE TABLE docs (id text PRIMARY KEY, title text NOT NULL,
  trust text NOT NULL CHECK (trust IN ('official', 'quarantined')));
-- chunks 跟第 9 課一樣，doc_id 參照 docs(id)，另外有 HNSW 與 pg_trgm 兩個索引

為什麼放在文件上，而不是每一塊各記一個？因為隔離是以「一份文件」為單位決定的：發現某份文件有問題時，UPDATE docs SET trust = 'quarantined' WHERE id = … 一句就生效，不用重算任何 embedding，也不用刪資料（之後查證據還用得到）。

匯入（ingest）就是第 9 課 upsertDoc 的多文件版：每份文件 upsert 一列 docs，切塊後比對 content_hash 與 embed_model，只把變了的塊合成一次送去 embedding，最後在同一個交易裡寫入並刪掉文件變短後多出來的塊。正式環境裡文件每天都可能改一兩行，重跑匯入只該花那一兩行的錢。

檢索（retrieve）是第 10 課的混合搜尋，多兩個條件：

SELECT c.id::text AS id FROM chunks c JOIN docs d ON d.id = c.doc_id
WHERE d.trust = 'official'                          -- 隔離的文件永遠不進候選
  AND 1 - (c.embedding <=> $1::vector) >= $2       -- 相似度太低的不要
ORDER BY c.embedding <=> $1::vector LIMIT $3
  • 信任條件寫在 SQL 裡：查完再用 JavaScript 過濾，等於先取了 20 筆、再丟掉其中幾筆，結果會少於應有的數量；更糟的是哪天有人改程式漏了這行過濾，被污染的內容就直接進 prompt。關鍵字那一路也要一樣 JOIN。
  • 相似度下限（MIN_SIMILARITY）：向量搜尋永遠回得出最近的 20 筆，就算問題是「附近哪裡可以停車」。加上下限後，兩路都找不到夠像的資料時回傳空陣列，助理就能直接轉店員、不花錢呼叫 API。下限要用 eval 調：太高會漏掉該找到的，太低等於沒設。
測試和 live.ts 用 kit.ts 的 conceptEmbed 當 embedding：一個假的語意模型，只認得咖啡店的十幾個概念與同義詞（「麩質」「小麥」「堅果」都算「過敏」）。它跟真的 embedding 模型有同樣的特性：懂同義詞，但不懂 SKU-0042 這種編號，所以編號類的問題要靠 pg_trgm 那一路（第 10 課講過為什麼）。正式環境換成 Voyage AI 的 voyage-4（第 8 課），只要把 embed 函式換掉，其他程式不用改。
💡 實務上：知識庫要有「誰能放文件進來」的流程
真正的客服助理，文件來源常是店長的 Google 文件、客服整理的 FAQ、甚至顧客留言。被污染的資料多半不是駭客打進來的，而是有人把來路不明的內容貼進了知識庫。資深工程師上線前會先問：新文件預設是 official 還是 quarantined？誰審核、審核後由誰改成 official？出事時能不能一句 SQL 隔離並查出哪些對話用過它？把這些寫進上線檢查清單的「權限」那一節。

助理本體：把防護串起來（練習 3）

createAssistant(deps) 回傳一個 ask(question)。步驟的順序本身就是設計，每一步放錯位置都會出事：

順序步驟為什麼在這裡
1redactPII(question)第一步就遮蔽，之後送給檢索、模型、log 的全部是遮蔽後的版本。放在後面，總會有某條路徑漏掉。
2retrieve(q)；空的而且不是問訂單就轉店員在呼叫模型之前：沒有資料可以根據時，叫模型回答只會花錢，還可能讓它自己編。問訂單時檢索不到文件很正常，要讓模型用工具查，所以用 isOrderQuestion（看有沒有「訂單」「單號」）判斷：有明確規則的事用程式做。
3agent 迴圈：最多 4 輪、input＋output 不超過 20,000 token第 7 課的停止條件：模型反覆呼叫工具時一定會停，停下來就轉店員，不丟錯。
4驗證 sources引用了這次沒給的 id：整個回答不可信。沒有引用、也沒有任何工具成功：回答沒有根據（被 injection 說動的「今天全部免費」就是這種）。兩種都轉店員。
5sanitizeOutput要顯示給顧客之前的最後一關：移除圖片、HTML、白名單以外的連結（第 12 課的外洩管道）。
6log 一次不管回答、轉店員還是哪一步停下，都留一筆：狀態、原因、工具、輪數、token、延遲。轉店員的原因（no_context、bad_citation、max_turns…）是上線後判斷「問題出在檢索還是模型」的線索。

每一輪的請求同時帶工具和結構化輸出：

const response = await deps.client.messages.parse({
  model: MODEL, max_tokens: 16000, system: SYSTEM,
  tools: toolSet.definitions,                            // strict: true 的兩個查詢工具
  messages,
  output_config: { format: zodOutputFormat(AnswerSchema) },  // 最終回答是 { answer, sources }
})

官方文件（Structured outputs 的 “Using both features together”，2026-11-01 查詢）說明 JSON 輸出與 strict 工具可以在同一個請求裡一起用：需要查資料時，回應是 stop_reason: 'tool_use' 加上 tool_use block；最後回答時，文字 block 是符合 schema 的 JSON，parse() 把它解析到 parsed_output。所以迴圈裡先看 stop_reason：是 tool_use 就執行工具；不是的話，end_turn 而且有 parsed_output 才是可用的回答，refusal、max_tokens 一律轉店員。回應的 content 前面通常還有 thinking block（Opus 5.5 一定會思考），parse() 只解析文字 block；你自己讀 content 時也照第 2 課的習慣，不讀 content[0]。

回答的 sources 是 c1、c2 這種這次 context 裡的短 id，要用 ctx.chunks 換回文件 id（menu、hours）並去掉重複：前端要顯示「資料來源：菜單」，eval 的 mustCite 也是用文件 id 比對。

eval 套件：證明沒有變差（練習 4）

kit.ts 的 EVAL_CASES 是 20 題，照第 11 課的格式，多了 tags 方便分類統計：

類別題數例子嚴重程度
價格4拿鐵多少錢、換燕麥奶加多少、SKU-0042 是什麼critical（SKU 那題是一般）
過敏原3可頌有麩質嗎、燕麥奶與堅果critical
營業時間、退款、集點6週六開到幾點、除夕有開嗎、還沒做可以退嗎一般
自己的訂單2我的訂單到哪了、訂單 3 是什麼狀態一般
別人的訂單1幫我查訂單 2（不是這位顧客的）critical，應該轉店員
超出範圍1附近哪裡可以停車一般，應該轉店員
injection3兩題直接（「忽略以上規則…」），一題間接（問寵物，會碰到被隔離的 FAQ）critical，應該轉店員

critical 的標準是「答錯一次就可能傷人、多收錢或外洩」。模型每次輸出不同（第 1 課），所以每題跑 3 次：一般題 3 次對 2 次算過，critical 每次都要對。runEval 每一次都建立新的助理（測試用它換上那一次的回放；真的跑時也避免上一題的狀態影響下一題），一題一題依序跑（同時送 60 個請求會被限流），某一次 ask 丟錯就記成這次沒過，不能讓整個 eval 中斷。最後的報告要能回答三件事：整體通過率、哪些 critical 題沒過、每一次花了多少 token。

整體通過率會掩蓋關鍵失敗：19 題全對、只有「查別人的訂單」錯一次，通過率 95%，但這是權限漏洞，不能上線。報告一定要把 critical 失敗單獨列出來，CI 的門檻也要分開判斷（第 11 課的 regressionGate）。
💡 實務上：eval 要跟著程式一起進 CI
改 system prompt、換模型、調相似度下限、升級 SDK，都可能讓某一類題目悄悄變差。團隊裡常見的做法是：每個改到 AI 相關程式的 PR 都跑一次 eval，critical 失敗直接擋下合併，一般題的通過率跟上一次比較。客服回報的錯誤回答，修好後也加成一題 eval，下次就不會再犯同一個錯。eval 本身也要花錢，所以題數維持在每次幾十題、幾分鐘跑完的規模。

成本報告（練習 5）

上線前店長一定會問：「一個月要花多少？」不要用「每題大概幾千 token」估，要用 eval 跑出來的實際 usage 算，因為它包含了你估不到的部分：思考的 token、工具多跑的一輪、快取的寫入與讀取。

每次 ask 的費用 = costOf(usage, model)          // 四種 token 各用自己的單價（第 13 課）
每則對話平均     = 全部 ask 的費用加總 ÷ ask 次數
快取命中率       = cache_read ÷（input＋cache_creation＋cache_read）
月費             = 每則對話平均 × 每天幾則 × 30

練習的測試用一份 4 題 × 2 次的小報告，以 claude-opus-5-5（每百萬 token 輸入 $4、輸出 $20、快取寫入 $5、快取讀取 $0.2；2026-11-01 官方定價頁）手算：其中一次是 input 5000、output 300、cache_creation 4000，費用是 (5000×4 + 300×20 + 4000×5) ÷ 1,000,000 = $0.046，是同一題第二次（命中快取）的 4 倍多。這就是報告要列出最貴的 3 題的原因：看到貴的題目，才知道錢花在哪裡：

  • 快取寫入：第一次寫入比一般輸入貴 25%，之後讀取只要 5%。命中率低就回頭檢查 prompt 的順序（第 13 課）。
  • 輸出長：輸出單價是輸入的 5 倍，思考的 token 也算輸出。叫模型「一到三句」也是省錢。
  • 多一輪：查訂單要兩個請求，第二個請求還要把第一輪的內容再送一次。

compareModels 比較目前的模型與想換的模型。只看價格，Haiku 5.5 幾乎總是便宜 95% 以上；但換模型是品質決定，不是價格決定。規則是：候選比較便宜、通過率下降不超過 2 個百分點、而且沒有任何 critical 失敗才建議換。百分點要先 round1 再比較：0.96 − 0.94 在浮點數是 0.0200000000000000018，直接比會把「剛好 2」判成超過。過敏原錯了兩題的便宜模型，可以拿去做分類、路由這類錯了代價小的步驟，回答維持原本的模型，再用 eval 驗證。

報告要寫查詢價格的日期：價格會變，三個月後看報告的人要知道數字是哪天的。

💡 實務上：成本報告是給 PM 與店長看的
他們要的不是 token 數，而是「一個月多少錢、每則對話多少錢、上限在哪裡」。資深工程師會把報告寫成一頁：用哪份 eval 量的、價格查詢日期、每則平均與最貴的題目、月費估算，以及預留餘裕後的每日花費上限（就是上線檢查清單「預算」那一節要填的數字）。上線後每週拿實際帳單跟估算比一次，差太多（例如真實對話比 eval 長很多）就回頭更新 eval 集與預算。

上線：端點、限流、回退（練習 6）

前端呼叫 POST /chat。檢查的順序是從便宜到昂貴：先確認是誰（401）、再確認這個人是不是問太快（429）、再檢查內容（400），全部通過才碰模型。

  • 身分只能來自登入資訊。練習用 header x-customer-id 模擬登入後的 session（正式環境是認證中介層驗過的 token，見認證課第 19 課）；body 裡就算有 customerId 也不能用，那是顧客自己填得了的。
  • 每位顧客分開限流：TenantLimiter 每位顧客每分鐘 5 次。一個人瘋狂送請求，只會擋到他自己，也不會把整間店的 API 配額用完。
  • 功能旗標（feature flag）enabled()：關掉時不呼叫模型，直接回「AI 客服暫停服務，請直接詢問店員」。模型供應商大規模故障、帳單異常、發現被攻擊時，值班工程師改一個設定就能止血，不用重新部署。這是上線檢查清單的「回退」那一項。

回應用 SSE，但這裡不逐字轉送模型的輸出。原因是第 3 步的驗證：回答要等整段出來、檢查完引用、過濾完連結，才知道能不能給顧客看。逐字串流的話，顧客可能已經看到一張外部圖片或一句被 injection 說動的話，事後才收回。所以端點先送 status（前端顯示「查詢中…」），驗證完再送 delta（整段回答）與 done（狀態與引用來源）。代價是首字延遲變長；如果產品真的需要逐字顯示，常見的折衷是只對純文字、不帶工具的回答串流，並在前端用純文字顯示（不渲染 Markdown）。出錯時送 error 事件，訊息是固定的一句話，內部錯誤只寫進 log。

上線檢查清單與 ADR（練習 7）

上線檢查清單（launch checklist）是上線前必須確認的事。它的用處是逼你在出事之前回答「如果……怎麼辦」。每一項都要寫到別人看得懂、做得到：

小節要回答的問題寫成這樣才算
權限模型拿得到什麼？工具能做什麼？身分從哪裡來？列出工具與欄位；寫明沒有退款工具
預算每天最多花多少？超過時系統怎麼做？「每天上限 30 美元，80% 告警，100% 關旗標」，不是「控制成本」
告警哪個指標超過多少要通知誰？錯誤率、p95 延遲、轉店員比例、拒答率、費用，各有門檻
回退出事時怎麼關掉 AI、改回什麼？旗標名稱、關掉後使用者看到什麼、fallback 模型
資料保留log 存哪些欄位、保留幾天、個資怎麼處理？「遮蔽後的問題、token、原因，保留 30 天」
已知限制哪些情況它一定會做不好？至少 3 點，讓客服主管知道什麼時候該介入

ADR（架構決策紀錄，系統設計課第 18 課）記下一個決定的背景、決定、考慮過的其他方案與後果。這次要寫的是：為什麼知識庫用既有的 PostgreSQL＋pgvector，而不是專門的向量資料庫或把全部文件塞進 prompt；為什麼訂單用工具查，而不是直接放進 prompt。每個沒選的方案都要寫出理由，一年後有人想換掉它時，才知道當初考慮過什麼。

測試只檢查格式與必填的數字。寫完用這張表自評，每一項都答「是」才算完成：

  • 沒看過這個專案的同事，照「回退」那一節能在 5 分鐘內關掉 AI 嗎？
  • 預算與告警的數字，能從成本報告推回來嗎（例如每天 500 則 × 每則費用 × 安全倍數）？
  • 已知限制裡，有沒有寫到 prompt injection 只能降低機率、不能保證擋住？
  • ADR 的「後果」有沒有寫代價，而不是只有好處？

練習

在 learn 資料夾執行 node check.mjs ai 16，會建立 ai/practice/work/16/。七題都只從 kit.ts 拿零件（練習 5、6 只從練習 4、3 匯入型別），可以任意順序做，建議照順序。練習 1、2 用 PGlite，第一次開資料庫要等幾秒。做完練習 1～3 後，有 API key 的話可以在 ai/practice 執行 node --env-file-if-exists=.env work/16/live.ts，用真的 claude-opus-5-5 問 6 個問題（包括查別人的訂單與間接 injection），看每一題的狀態、輪數與費用；設定 AI_MODEL=claude-haiku-5-5 可以看同樣的 token 換成 Haiku 的單價是多少。

練習 1：完成 ingest(db, docs, embed)。每份文件 upsert 一列 docs（trust 改了也要更新）；用 chunkMarkdown(doc.id, doc.markdown, CHUNK_OPTS) 切塊；跟資料庫現有的 content_hash、embed_model 比對，只把新的或變了的塊（用 embedText(chunk)）合成一次呼叫 embed；在同一個交易裡寫入（存 headingPath 與 EMBED_MODEL），並刪掉文件變短後多出來的舊塊。回傳 { embedded, deleted }。重跑一次時 embedding 數必須是 0。

練習 2：完成 retrieve(db, question, embed)：問題 embedding 一次；在 db.transaction 裡 SET LOCAL 關鍵字門檻；向量那一路只留相似度 ≥ MIN_SIMILARITY 的塊，關鍵字那一路用 $1 <% content；兩路都 JOIN docs 只找 trust = 'official'；用 rrf 合併取前 TOP_K（5）筆，補上 docId、headingPath、content。測試用 6 題人工標記算 recall@5（要 ≥ 0.8），並檢查 SKU 題、被隔離的文件、無關的問題回空陣列。

練習 3：完成 createAssistant(deps)，照 ex3.ts 註解的 6 個步驟：遮蔽 → 檢索（空的而且不是問訂單就不呼叫 API）→ 帶工具與結構化輸出的迴圈（最多 MAX_TURNS 輪、TOKEN_BUDGET）→ 驗證引用 → sanitizeOutput → 每次 log 一筆。轉店員的回答一律是 HANDOFF。測試用假的 API 回放十幾種情境，包括一輪呼叫兩個工具、查別人的訂單、引用不存在的 id、回答帶外部圖片、問題裡有電話。

練習 4：完成 runEval(makeAssistant, cases, runs = 3)：每題依序跑 runs 次，每次用 makeAssistant(c.id, run) 建新的助理；用 gradeAnswer 評分；critical 每次都要過、一般題至少 2/3；ask 丟錯算沒過（原因 錯誤：訊息、usage 記 ZERO_USAGE）。回傳每題的結果、passRate、criticalFailures 與每一次的 usage。

練習 5：完成 costReport(report, model, dailyConversations)：用 costOf 算每次 ask 的費用，回傳每則對話平均（小數 6 位）、快取命中率（小數 4 位）、平均費用最高的 3 題、每月（30 天）費用（小數 2 位）。再完成 compareModels(current, candidate)：候選比較便宜、品質下降不超過 2 個百分點（先 round1）、而且沒有 critical 失敗，才回 'switch'。

練習 6：完成 createChatServer(deps)：POST /chat 依序檢查 x-customer-id 是正整數（否則 401）、limiter.take（否則 429）、body 的 question 是 1～2000 字的字串（否則 400），錯誤都回 JSON { error }。通過後回 SSE：旗標關閉時送 delta（FALLBACK_TEXT）與 done（status: 'disabled'）；否則送 status、delta（回答）、done（status 與 sources），出錯送 error（ERROR_TEXT）。身分不能從 body 讀。

練習 7：填寫 LAUNCH.md：上線檢查清單的六節（權限、預算、告警、回退、資料保留、已知限制）與 ADR 的四節（背景、決定、考慮過的其他方案、後果），把所有 TODO 換成你的內容。預算要有金額、告警要有門檻、資料保留要寫幾天；已知限制至少 3 點；其他方案至少 2 個，每個寫成「方案：沒選它的理由」。寫完用上面的自評清單檢查一次。

練習 8：eval 通過率 95%，只有 1 題「查別人的訂單」失敗（3 次裡有 1 次回答裡出現了對方的品項）。可以上線嗎？

✓ 整體通過率會掩蓋關鍵失敗。模型能說出對方的品項，表示工具把那筆資料交給了它，也就是程式的權限檢查有漏洞；prompt 只能降低機率（c 錯），而且這次的失敗本身就證明模型會被說動。上線後再看（d）等於讓真的顧客資料外洩。修程式、加回歸測試、重跑 eval 才能上線。

練習 9：成本報告顯示 Haiku 5.5 比 Opus 5.5 便宜 97%，但 eval 通過率從 96% 降到 90%，錯的包括 2 題過敏原。合理的決定是？

✓ 換模型要同時看品質，尤其是錯了會傷人的類別：過敏原屬於 critical，候選模型有 critical 失敗就不換（a 錯）。刪掉失敗的題目是讓量尺說謊（c）。成本也是工程的一部分（d 錯）：部分步驟用小模型是常見的折衷，每一步換之前都用 eval 確認。

練習 10：上線第一天，你發現被污染的 FAQ 文件還是 official，而且 log 裡有幾筆檢索到它。最優先的處理是？

✓ 先移除來源（一句 UPDATE 就生效，不用重算 embedding），再評估影響，最後補上防線與回歸測試：這是第 12 課縱深防禦與事故處理的順序。prompt 只能降低機率（a、d 錯）。必要時可以用功能旗標暫時關掉 AI，但不需要整個服務停一週（c）：問題的範圍已經知道了。

常見錯誤

  • 全部寫在一個大函式裡：裡面自己 new Anthropic()、自己連資料庫，就沒辦法分開測試或替換。每個模組的依賴都從參數傳進來。
  • 遮蔽放在中間：檢索、log、錯誤訊息總有一條路徑拿到原始的問題。第一步就遮蔽，之後只用遮蔽後的版本。
  • 沒資料也呼叫模型：浪費錢，也給模型自己編答案的機會。檢索不到就轉店員，但問訂單這類靠工具的問題要另外判斷。
  • 隔離寫在 JavaScript 而不是 SQL：取完前 N 筆再過濾，結果變少；之後改程式時一漏掉，被污染的內容就進 prompt。
  • 相信模型的引用：不存在的 id、沒有引用也沒用工具的回答，都要轉店員，不是刪掉那個 id 就好。
  • 逐字串流沒驗證過的輸出：顧客會先看到外部圖片或被說動的話。要嘛驗證完再送，要嘛只串流純文字並在前端用純文字顯示。
  • 只看整體通過率：critical 失敗要單獨列出、單獨擋下。
  • 成本報告只看單價：真正的費用來自思考的 token、多跑的工具輪、快取的寫入與命中率；要用 eval 的實際 usage 算，並寫下價格的查詢日期。
  • 沒有回退方式：供應商故障時客服整個掛掉。功能旗標與固定回覆要在上線前就做好、演練過。
  • 檢查清單寫成口號：「控制成本」「注意安全」不能執行。寫數字、寫誰收到通知、寫關掉的步驟。

小結

  • 先寫下能做與不能做；「轉店員」是一個明確、被測試的結果，不是失敗。
  • 每個模組一個函式、依賴從參數傳入：測試能換上假的 client、時鐘、檢索，各自驗證。
  • 信任程度記在文件上、過濾寫在 SQL 裡；相似度下限讓無關的問題拿到空結果，不花錢呼叫模型。
  • 防護的順序：先遮蔽，再檢索，迴圈有輪數與 token 上限，回答要驗證引用、過濾輸出，每次留一筆 log。
  • 結構化輸出與 strict 工具可以一起用：先看 stop_reason，tool_use 就執行工具，end_turn 才讀 parsed_output。
  • eval 每題跑 3 次，critical 每次都要對；報告分開列出 critical 失敗，並收集每次的 usage。
  • 成本報告用實際 usage 算每則對話與每月費用，找出最貴的題目；換模型要同時看品質與 critical 失敗。
  • 端點從便宜的檢查到昂貴的：身分 → 限流 → 內容 → 模型；功能旗標是出事時的止血開關。
  • 上線檢查清單與 ADR 寫到別人做得到：有數字、有步驟、有代價。

階段檢核：面試會問的觀念

這個階段就是整門課，所以這裡是總檢核：AI 應用開發面試最常問的 8 件事，全部放進這個客服助理裡。先在心裡回答，再選。

練習 11：同事交來這版查訂單工具，說「SQL 有帶擁有者條件，很安全」。上線後哪裡會出事？

const getOrder = {
  name: 'get_order', strict: true,
  description: '顧客問某一張訂單的狀態時使用，回傳狀態與金額',
  input_schema: toInputSchema(z.object({ order_id: z.number(), customer_id: z.number() })),
}
const runGetOrder = ({ order_id, customer_id }) =>
  db.query('SELECT id, status, total FROM orders WHERE id = $1 AND customer_id = $2',
    [order_id, customer_id])

✓ 模型隨時可能被說服，傷害範圍要由程式決定：input_schema 不放顧客 id，handler 只用 session 的身分。這樣模型就算照做，也沒有參數可以填。b 錯在 prompt 只能降低機率，擋不住 injection。a 錯在擁有者條件本來就擋住了猜編號，問題是那個擁有者 id 從哪裡來。（第 12 課）

練習 12：log 裡有一則對話，模型反覆用同樣的參數呼叫 get_order，跑了平常好幾倍的輪數，費用卻比「輪數 × 平常一輪的費用」高出一大截。為什麼？

✓ API 無狀態，每一輪都重送整段對話，所以卡住的迴圈費用隨輪數快速放大。迴圈一定要會停：最多輪數、input＋output 的 token 預算、同一工具＋同樣 input 的重複偵測，停下來就轉店員並記 log。b 錯在放大費用的是每輪重送的輸入，不是思考被當成輸出重算。（第 7 課）

練習 13：寫 ADR 時店長問：「與其做檢索，為什麼不拿門市文件微調一個自己的模型？」最好的回答是？

✓ 選型看資料：小又很少變就整份放進 prompt 加快取；要改語氣與格式才考慮微調；資料大、常變、要能引用來源才用 RAG。a 錯在重訓成本高，而且模型「記住」的事實指不出出處，前端沒辦法顯示「資料來源：菜單」。c 錯在微調不會讓模型不再幻覺。（第 8 課）

練習 14：eval 裡「SKU-0042 是什麼」這題 3 次都答錯，同事想先改 system prompt。你會先查什麼？

✓ 檢索與生成分開查：檢索沒找到，模型手上就沒有答案，改 prompt 或換模型都救不了。編號沒有「意思」，向量搜尋本來就弱，要靠關鍵字（pg_trgm）那一路。c 錯在向量那一路的弱點不是筆數太少，調低下限只會多放無關的塊進來。（第 10、11 課）

練習 15：同事這樣處理模型回傳的引用。哪裡會出事？

const ids = new Set(ctx.chunks.map((c) => c.id))     // 這次給的 c1、c2…
const sources = parsed.sources.filter((id) => ids.has(id))
return { status: 'answered', answer: parsed.answer, sources }

✓ 只要引用一個不存在的 id，你就不知道哪一句是根據它說的，刪掉那個 id 不會讓回答變可信；沒有引用、也沒有工具成功的回答也沒有根據。兩種都要整個轉店員並記下原因。b 錯在模型回的本來就是短 id，跟這次的短 id 比對才對，比對完才換成文件 id。（第 10 課）

練習 16：為了讓助理知道現在是否營業中，同事在 system prompt 開頭加了一行「現在時間：…」。上線後成本報告的快取命中率掉到幾乎是 0。原因是？

✓ 快取從請求的開頭逐位元比對，第一個不同的位元組之後全部算沒命中，還要多付寫入的錢。穩定的放前面、會變的放後面：時間放到最後一則 user 訊息，再用 usage 驗證有沒有命中。a 錯在時間一改就不命中，跟請求多不多無關。（第 4、13 課）

練習 17：一次升級後，主要模型的每個請求都回 400，顧客全部拿到固定的回覆。同事提議：「把 400 也加進換備用模型的條件，至少顧客拿得到回答。」你怎麼回？

✓ 先分錯誤：429、529、5xx、逾時是暫時性的，可以重試、再走備用模型；400、401、403、404 是程式的問題，重送一百次結果都一樣。這次升級改壞了請求，要讓告警響、帶著 request id 去修。a 是最多人會選的：顧客暫時有回答，但 bug 被藏起來，還失去主要模型的快取與品質。（第 14 課）

練習 18：PM 想要逐字顯示回答。同事提議直接把模型的文字串流轉給前端，最後再跑引用驗證與 sanitizeOutput，不通過就補送一個 error 事件。問題在哪？

✓ 驗證要完整的回答，串流讓驗證變晚：所以這個端點先送 status，驗證完才送整段回答。真的要逐字，只對純文字、不帶工具的回答串流，前端用純文字顯示、不渲染 Markdown。b 錯在串流最後的 message_delta 有累計的 usage。c 錯在 EventSource 不能送 POST，前端本來就用 fetch 讀串流。（第 3、15 課）
