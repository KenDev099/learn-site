階段 1：LLM 基礎與第一個 API 呼叫 · 第 2 課

第一個 API 呼叫：Messages API、回應結構與對話歷史

咖啡店想在官網加一個「問店員」的小視窗。同事花十分鐘照著網路範例接好：response.content[0].text 拿到回答就顯示。上線第一天就出事：有的顧客看到空白，有的看到說到一半就斷掉的退款規則，還有人問第二句「那大杯呢？」，助理完全不知道在說什麼。這三個問題都跟模型聰不聰明無關，是程式沒讀懂 API 的回應。

這一課用官方的 TypeScript SDK 送出第一個請求，把回應讀懂，練習全部不花錢、不連網路就能判分。

這課的路線：
  1. 準備與第一個請求：SDK 怎麼裝、API key 放哪裡，一個請求要送哪幾個欄位（開場問題的最小答案）。
  2. 讀懂回應、stop_reason：回答在 content 的哪一塊、這次花了多少 token，什麼時候回答不能直接給顧客看。
  3. 多輪對話：API 不記得上一句，顧客問「那大杯呢？」時，歷史要怎麼由你的程式保存。
  4. 這門課怎麼判分、client 的設定：測試怎麼不花錢檢查你送出的請求，正式環境的 client 怎麼建立。
這課會用到：
  • Node 課第 2 課的環境變數：設定值從 process.env 讀，不寫死在程式碼裡，密碼類的值也不進 git。
  • Node 課第 6 課的 node:test 與 node check.mjs：練習在本機寫 .ts，用指令跑測試看哪裡沒過。
  • TypeScript 課第 16 課的可辨識聯合：用共同的 type 欄位判斷是哪一種物件，判斷完 TypeScript 才讓你讀那種物件特有的屬性。
  • TypeScript 課第 4 課的自訂錯誤類別：class X extends Error，呼叫端用 instanceof 分辨是哪一種錯誤。

準備：安裝套件與 API key

SDK（Software Development Kit）是官方寫好的套件，替你處理 HTTP 請求、標頭、重試、型別和串流解析。Claude 的 TypeScript SDK 是 @anthropic-ai/sdk，這門課鎖定 1.3.0（2026-10-23 發布）。1.0.0 起 SDK 預設送 anthropic-version: 2026-10-21 標頭，所以這門課講的都是這個 API 版本的行為。

這門課的本機練習都在 ai/practice/，套件已經寫在它的 package.json，版本由 lockfile 鎖住（Node 課第 3 課），裝一次就好：

node -v                         # 要 v24.16.0 以上
cd ai/practice && npm install   # 裝 SDK、zod、PGlite（之後的課會用到），裝完就不需要網路
cd ../..                        # 回到 learn/
node check.mjs ai 02            # 建立 ai/practice/work/02/ 並跑測試（現在當然都沒過）

API key 是呼叫 API 用的密碼，在 platform.claude.com 的 Console 建立，長得像 sk-ant-api03-…。拿到 key 的人可以用你的帳號呼叫 API、花你的錢，所以：

  • 只放在環境變數裡。本機開發寫在 .env 檔，ai/practice/.gitignore 已經排除它；正式環境用部署平台的 secret 設定。
  • 絕對不寫進程式碼、不 commit、不放前端。Vue 前端打包後的程式任何人都看得到，前端一律呼叫你自己的後端 API，由後端拿 key 去呼叫 Claude。
💡 實務上：API key 要當成密碼管理
開發、測試、正式環境各用一把 key，log 和錯誤訊息裡不要印出 key。發現 key 被 commit 或貼到聊天室，第一件事是到 Console 停用那把 key 再換新的，刪掉 commit 沒有用：它可能已經被複製走了。上線前資安或維運通常會問三件事：key 放在哪裡、誰拿得到、外洩時怎麼換。
沒有 API key 也能做完整門課的練習。判分用的是事先錄好的回應（最後一節說明），不連網路、不花錢。每課的 work/NN/live.ts 是選用的：想看真實模型怎麼回答時，在 ai/practice/.env 寫一行 ANTHROPIC_API_KEY=你的 key，在 ai/practice 執行 node --env-file-if-exists=.env work/02/live.ts（Node 直接執行 .ts 的限制見 Node 課第 5 課）。它會印出整個回應和這次的費用，用 claude-opus-5-5 問一題大約 0.004 美元；加上 AI_MODEL=claude-haiku-5-5 會更便宜。

第一個請求

Claude 的主要端點是 Messages API：POST /v1/messages。聊天、從文字擷取資料、讓模型呼叫工具，全部都走這一個端點，差別只在送出的欄位。用 SDK 送出一個請求：

import Anthropic from '@anthropic-ai/sdk'

const client = new Anthropic()   // 沒傳 apiKey 時，自動讀環境變數 ANTHROPIC_API_KEY

const response = await client.messages.create({
  model: 'claude-opus-5-5',
  max_tokens: 16000,
  system: '你是咖啡店的店員，用繁體中文回答，一兩句就好。',
  messages: [
    { role: 'user', content: '拿鐵一杯多少錢？' },
  ],
})
欄位意思
model用哪個模型。寫成 'claude-opus-5-5' 這種不帶日期的 id；這門課預設用 Opus 5.5（輸入每百萬 token 4 美元、輸出 20 美元），第 13 課再談怎麼選便宜的模型。
max_tokens這次最多產生幾個 token，是上限不是目標：沒用到的不收錢。下一節會看到設太小的後果。
systemsystem prompt：給模型的角色和規則。跟使用者說的話分開放，模型才分得出哪些是你的規則、哪些是顧客輸入的內容（第 4、12 課會再用到這個區分）。
messages對話內容，依時間順序排列，每則有 role（user 或 assistant；Opus 5.5 另外接受在對話中間插入 system，第 12 課會用到）和 content。第一則要是 user。

還有兩個常在舊範例看到的寫法，在這個 API 版本已經不能用：

  • temperature、top_p、top_k：API 版本 2026-10-21 起送了就回 400，SDK 1.x 的型別也拿掉了。第 1 課說過，輸出會變是正常的，要用設計處理，不是靠參數關掉。
  • 在 messages 最後放一則 assistant 訊息，讓模型「接著寫」（叫 prefill）：Opus 5.5 會回 400。要固定格式用結構化輸出（第 5 課）。

請求送得出去之後，開場的三個問題都出在讀回應這一側：畫面空白，是因為 content[0] 不一定是文字；退款規則斷在一半，是因為碰到了 max_tokens；「那大杯呢？」接不上，是因為 API 不記得上一個請求。細節在後面的〈讀懂回應〉〈stop_reason〉〈多輪對話〉。

讀懂回應：content、usage

回應是一個 Message 物件。用 live.ts 印出來大概長這樣（id 和數字每次不同）：

{
  "id": "msg_01…",
  "type": "message",
  "role": "assistant",
  "model": "claude-opus-5-5",
  "content": [
    { "type": "thinking", "thinking": "", "signature": "EqQB…" },
    { "type": "text", "text": "拿鐵一杯 110 元，換燕麥奶加 10 元。", "citations": null }
  ],
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "stop_details": null,
  "usage": { "input_tokens": 41, "output_tokens": 186, "cache_creation_input_tokens": 0, "cache_read_input_tokens": 0, … }
}

content 是陣列，不是字串。每個元素叫一個 content block，用 type 區分：text 是回答的文字、thinking 是模型的思考、tool_use 是模型要呼叫你的函式（第 6 課）。一個回答也可能拆成好幾個 text block。

thinking block：Opus 5.5 的思考（thinking）一直開著、不能關，想多少由模型自己決定（叫 adaptive thinking），送 thinking: { type: 'disabled' } 會回 400。思考的內容預設不回傳（display 預設是 omitted），所以你通常會看到一個 thinking 是空字串的 block 排在最前面。看不到內容，思考照樣會產生 token、照樣算錢。

所以開頭那位同事的 response.content[0].text 讀到的是 thinking block：它根本沒有 text 屬性，結果是 undefined，畫面一片空白。TypeScript 其實擋過他：content[0] 的型別是好幾種 block 的聯合，不先縮小就讀不到 .text。正確寫法是挑出所有 text block 再接起來：

const answer = response.content
  .filter(block => block.type === 'text')   // TypeScript 5.5 起會自動推論成 TextBlock[]
  .map(block => block.text)
  .join('')

usage 記錄這次請求用了多少 token，是計費和監控的依據。input_tokens 是你送出的（system＋messages），output_tokens 是模型產生的，包含看不到的思考。cache_* 兩個欄位是 prompt caching 用的，第 13 課再談。用第 1 課的 estimateCost（輸入 token × 輸入單價＋輸出 token × 輸出單價，單價以每百萬 token 計）算這次的費用：

41 × 4 ÷ 1,000,000 ＋ 186 × 20 ÷ 1,000,000 = 0.000164 ＋ 0.00372 ≈ 0.0039 美元

回答只有一句話，輸出卻有 186 個 token，多出來的是思考。正式環境要把每次的 usage 記進 log（第 15 課），帳單才查得出是哪個功能花的錢。

stop_reason：先確認回答能不能用

stop_reason 說明模型為什麼停下來。拿到回應的第一件事是看它，不是看文字：

stop_reason意思回答能不能用
end_turn模型說完了可以
stop_sequence產生了你在 stop_sequences（請求的選用欄位：遇到這些字串就停）設定的字串可以
max_tokens碰到 max_tokens 上限，被切斷不行：後面的內容不見了
model_context_window_exceeded輸入加輸出碰到 context window 上限（第 1 課），被切斷不行
refusal模型拒答；stop_details.category 說明類別（例如 cyber），可能是 null不行：要給使用者另外的訊息（第 14 課）
tool_use模型要呼叫工具還沒說完，第 6 課處理
pause_turn用了 Anthropic 端執行的工具（例如網頁搜尋）、一輪跑太久時暫停，要把回應送回去讓它繼續還沒說完

開頭那段「說到一半就斷掉的退款規則」就是 max_tokens：文字看起來像一句話，其實後面還有。截斷常發生在最不該發生的地方：JSON 少了結尾的 }、步驟說明少了最後一步。程式要把這些情況變成明確的錯誤，呼叫的人才不會把半截回答送給顧客：

switch (response.stop_reason) {
  case 'end_turn':
  case 'stop_sequence':
    return text
  case 'max_tokens':
  case 'model_context_window_exceeded':
    throw new TruncatedError(text, response.stop_reason)   // 帶著半截文字，方便記 log
  case 'refusal':
    throw new RefusalError(response.stop_details?.category ?? null)
  default:
    throw new Error(`沒有處理的 stop_reason：${response.stop_reason}`)
}

stop_details 只在 refusal 時有值，其他情況是 null；就算是 refusal 也可能是 null，所以一律用 ?. 讀。default 那一支很重要：以後 API 多了新的 stop_reason，或是這個函式被用在有工具的請求上，你會得到一個看得懂的錯誤，而不是把不完整的東西當回答。

不要用 max_tokens 控制回答長度。想要短回答就在 system prompt 寫「一兩句就好」。把 max_tokens 壓到 300，Opus 5.5 光思考就可能用完，結果 stop_reason: 'max_tokens'、一個字的回答都沒有。官方建議非串流的請求 max_tokens 設 16000 左右；要更大的值（最多 128K）改用串流（第 3 課），否則 HTTP 請求可能等太久逾時。
💡 實務上：每一種 stop_reason 都要對應到顧客看到的畫面
咖啡店的聊天視窗不能只有「成功」和「失敗」兩種畫面：截斷時可以提示「回答太長，請把問題問得具體一點」，拒答時說「這個問題我沒辦法回答，可以改問菜單或訂單」，其他沒處理的情況顯示一般錯誤並記 log。log 至少記 id、model、stop_reason、usage，客服回報「助理答一半」時，才查得到是哪一次請求。跟 PM 討論的是這幾種畫面的文案，不是「模型會不會出錯」。

多輪對話：API 沒有記憶

Messages API 是無狀態的：每個請求都是獨立的，它不記得你上一次問過什麼。顧客的第二句「那大杯呢？」如果單獨送出去，模型不知道「那」指什麼。對話的記憶由你的程式負責：每次都把到目前為止的完整對話送過去。

assistant 那一則要放什麼？放回應的完整 content，原樣送回，不是只放文字：

messages.push({ role: 'user', content: '拿鐵多少？' })
const response = await client.messages.create({ model, max_tokens: 16000, system, messages })
messages.push({ role: 'assistant', content: response.content })   // 整個 block 陣列，包括 thinking

只存文字字串，簡單的聊天看起來也能動，但 thinking block 帶著模型的思考脈絡，第 6 課的 tool_use block 更是下一個請求一定要有的（tool_result 要對應到它的 id）。官方的建議就是原樣送回，模型讀不了的 block API 會自己略過，不會算錢。

還有兩個實務細節：

  • 失敗時要復原。先把 user 訊息加進歷史，呼叫失敗（API 錯誤、或回答被截斷）卻沒拿掉，下一次就會出現兩則連續的 user 訊息。API 不會報錯，會把它們併成同一輪，模型看到的是一個沒被回答的舊問題加上新問題，回答就可能答非所問。要嘛成功後才一起加，要嘛失敗時拿掉。
  • 歷史越長越貴。第 10 輪的請求會把前 9 輪全部再送一次，輸入 token 和延遲一起變大。第 13 課的 prompt caching 讓重複的前綴便宜很多。
💡 實務上：歷史只往後加，不要改前面
Opus 5.5 的 thinking block 會綁定產生它的那段對話：system、和它前面的每一則訊息。之後的請求如果改了、刪了前面的訊息，或換了 system，後面的 thinking block 就失效；2026-08-31 以後建立的帳號會直接收到 400（較早的帳號目前還不擋，但程式一樣照這個規則寫，prompt caching 也要前面不變才有效）。所以第 1 課的 trimHistory（丟掉最舊的問答）在 Opus 5.5 上要多一步：丟的同時把留下來的歷史裡所有 thinking block 拿掉，代價是模型看不到之前的思考、快取重來，所以只在真的太長時做一次，不要每輪都修剪。平常讓對話只往後加：system 在對話開始時就固定，話題換了就開一段新對話。失敗時拿掉「最後一則」user 訊息不算改前面，因為它後面沒有別的訊息。

這門課怎麼判分

練習的測試不會真的呼叫 Claude：那樣要 API key、要花錢、每次回答不一樣，測試也就沒辦法每次都得到同樣結果。做法是把 SDK 的 fetch 換掉。SDK 允許 new Anthropic({ fetch }) 傳入自己的 fetch，測試就傳一個假的：它不連網路，依序回放事先寫好的回應。這種事先寫好、測試時回放的資料叫 fixture。看一個測試怎麼寫：

import { fakeAnthropic } from '../../helpers/fake-anthropic.ts'
import { message, text, thinking } from '../../helpers/replies.ts'
import { ask } from './ex1.ts'

test('回傳所有 text block 接起來的文字', async () => {
  // 準備一個回應：跟 Opus 5.5 一樣，先一個空的 thinking block
  const { client, requests } = fakeAnthropic([message([thinking(), text('拿鐵'), text(' 110 元')])])
  assert.equal(await ask(client, '拿鐵多少錢？'), '拿鐵 110 元')
  // requests 記錄你的程式實際送出的請求
  assert.equal(requests[0].body.model, 'claude-opus-5-5')
  assert.equal(requests[0].body.max_tokens, 16000)
})

你的程式拿到的 client 是真正的 SDK：組請求、送標頭、解析回應、丟出錯誤類別，跟正式環境完全一樣，只有最底層的網路換掉了。測試因此可以檢查兩件事：你的函式回傳什麼，以及你送出了什麼（model、max_tokens、system、messages 的順序與角色、有沒有多送 temperature）。「回傳值碰巧對、送出的請求是錯的」也會被抓到。

所以練習裡的函式都把 client 當參數傳進來，不在函式裡自己 new Anthropic()。這也是正式環境的好寫法：建立 client 的地方只有一個（下一節），其他程式碼不需要知道 key 從哪裡來，換成測試用的 client 也不用改程式。

測試的 fixture 都照 SDK 1.3.0 的型別和 Opus 5.5 的實際形狀寫，但它終究是你自己準備的資料：真實模型某天回了 fixture 沒想到的形狀，測試不會知道。所以正式環境還要靠 stop_reason 的完整處理、log（第 15 課）和 eval（第 11 課）。

client 的設定與正式環境

SDK 的 client 有兩個跟可靠性有關的設定：

設定預設說明
timeout600000（10 分鐘）單位是毫秒（Python SDK 是秒）。寫成 timeout: 30 是 30 毫秒，幾乎每個請求都會逾時。
maxRetries2遇到 408、409、429、5xx 和連線錯誤時自動重試，會遵守 retry-after 標頭。逾時也會重試，所以最壞要等 timeout ×（maxRetries＋1）。
💡 實務上：逾時依功能設定，不是整個專案一個值
預設的 10 分鐘對網頁上的聊天視窗太長：顧客不會等那麼久，你的伺服器卻一直占著連線。客服回答可以設 30 秒，背景的批次整理可以長一點；也可以在單一請求覆蓋：client.messages.create({ … }, { timeout: 60_000 })。設定前先算最壞情況：30 秒逾時加上重試 2 次，顧客可能要等 90 秒以上（三次逾時，再加上重試前的等待），前端要有「處理中」和「重試」的畫面。第 14 課會把逾時、重試、換模型串成完整的策略。

正式環境的 client 由一個函式建立，key 從環境變數來，缺了就在啟動時失敗，而不是等第一個顧客發問才發現：

export function createClient(env: Record<string, string | undefined>) {
  const apiKey = env.ANTHROPIC_API_KEY
  if (!apiKey) throw new Error('缺少 ANTHROPIC_API_KEY：在 .env 或部署平台的 secret 設定')
  return new Anthropic({ apiKey, timeout: 30_000, maxRetries: 2 })
}

注意 !apiKey 同時擋掉沒設定和空字串：.env 寫了 ANTHROPIC_API_KEY= 卻忘了填值時，值是空字串，用 === undefined 判斷會讓它過關，等到呼叫時才收到 401。把 env 當參數傳進來而不是直接讀 process.env，測試就能傳入各種情況。

SDK 1.x 還有兩個跟 0.x 不同的地方，查舊文章時要注意：API key 改用 Authorization: Bearer 標頭送出（以前是 X-Api-Key），以及 apiKey、authToken 這類憑證只能傳一種，同時傳會丟出 TypeError。

在 NestJS 裡，把它包成一個 provider，用 NestJS 課第 11 課的 ConfigService 讀設定，整個應用程式共用同一個 client：

export const ANTHROPIC = Symbol('ANTHROPIC')

@Module({
  providers: [{
    provide: ANTHROPIC,
    inject: [ConfigService],
    useFactory: (config: ConfigService) => createClient({ ANTHROPIC_API_KEY: config.getOrThrow('ANTHROPIC_API_KEY') }),
  }],
  exports: [ANTHROPIC],
})
export class LlmModule {}
// 使用的地方：constructor(@Inject(ANTHROPIC) private readonly claude: Anthropic) {}

換成其他供應商，架構不用變，改的是欄位名稱。例如 OpenAI 的 Responses API：最大輸出叫 max_output_tokens，被截斷時是 status: 'incomplete' 加上 incomplete_details.reason: 'max_output_tokens'，拒答是一種 refusal 類型的內容；官方 SDK 的逾時預設也是 10 分鐘。「回答放在陣列裡、要先確認為什麼停下、歷史由你維護」這三件事各家都一樣。

練習

在 learn 資料夾執行 node check.mjs ai 02，會建立 ai/practice/work/02/。四題在同一個資料夾，練習 3 會用到練習 2 的 readAnswer，照順序做。

練習 1：完成 ask(client, question, opts)：送一則 user 訊息給 MODEL（'claude-opus-5-5'），回傳所有 text block 依序接起來的文字。opts.maxTokens 沒給時 max_tokens 用 16000；opts.system 有值時放進請求的 system 欄位，不要接進 user 訊息；不要送 temperature；程式碼裡不能有 API key。測試的回應以空的 thinking block 開頭，有時文字分成好幾個 text block。

練習 2：完成 readAnswer(message)。end_turn、stop_sequence 回傳文字；max_tokens、model_context_window_exceeded 丟出 TruncatedError（帶著已產生的文字 partial 和 reason）；refusal 丟出 RefusalError，category 從 stop_details 拿，stop_details 是 null 時用 null；其他 stop_reason（tool_use、pause_turn…）丟出一般的 Error，訊息包含那個值。兩個錯誤類別已經寫好。

練習 3：完成 Conversation。send(text) 把 user 訊息加進歷史，帶著 system 和完整歷史呼叫 API（max_tokens 16000），用 readAnswer 檢查回應，把 assistant 的完整 content 加進歷史，回傳文字。API 錯誤、回答被截斷或拒答時丟錯，歷史要恢復成這次 send 之前的樣子。history 回傳副本，外面改它不能影響對話。

練習 4：完成 createClient(env)：從參數 env（不是 process.env）讀 ANTHROPIC_API_KEY，沒有或是空字串時丟出 Error，訊息要提到 ANTHROPIC_API_KEY 和在哪裡設定；有的話建立 client，逾時 30 秒、最多重試 2 次。做完後如果有 API key，可以執行 work/02/live.ts 看真實的回應。

練習 5：claude-opus-5-5 的回應 content 是 [{ type: 'thinking', thinking: '' }, { type: 'text', text: '拿鐵 110 元' }]。response.content[0].text 會是什麼？

✓ content 是可辨識聯合，thinking block 只有 thinking 和 signature，讀 .text 得到 undefined（不會丟錯，所以也不是 d）。空字串是 thinking 欄位的值，不是 text。Opus 5.5 的思考不能關、預設不回傳內容，這個形狀很常見，所以要過濾 type === 'text'。

練習 6：stop_reason 是 max_tokens，content 裡有一段看起來完整的文字。應該怎麼做？

✓ max_tokens 代表模型還沒說完就被切斷，「看起來完整」只是剛好斷在句號，後面可能還有重要的條件；JSON 被切斷更是直接解析失敗。它不是伺服器錯誤（HTTP 是 200），同樣的請求再送一次，大概又在差不多的地方被切斷。

練習 7：多輪對話時，assistant 的歷史訊息應該存什麼？

✓ Messages API 是無狀態的，client 也不會替你記，所以 b 錯：歷史是你的程式每次重送的。只存文字（a）在簡單聊天看似可行，但會丟掉 thinking 的脈絡，到第 6 課的工具呼叫就一定壞掉，因為 tool_result 要對應 assistant 訊息裡的 tool_use id。官方建議原樣送回完整 content。

常見錯誤

  • 把 API key 寫進程式碼或前端：key 外洩就會被盜刷。只放在後端的環境變數，前端永遠呼叫你自己的 API。
  • 讀 content[0].text：碰到 thinking 或 tool_use block 就拿到 undefined。過濾 type === 'text' 的 block 再接起來。
  • 只看文字、不看 stop_reason：max_tokens 截斷和 refusal 都會被當成成功，顧客收到半截或空白的回答。先檢查 stop_reason，把不能用的情況變成錯誤。
  • 用很小的 max_tokens 讓回答變短：思考也算在 max_tokens 裡，可能一個字都沒輸出就被截斷。長度用 prompt 控制，非串流的 max_tokens 設 16000 左右。
  • 以為 API 記得對話：每次請求都要帶完整歷史；assistant 存完整的 content，不是只存文字。
  • 失敗時歷史沒有復原：留下沒有回答的 user 訊息，下一次請求出現兩個連續的 user。
  • 回頭改前面的歷史或 system：Opus 5.5 後面的 thinking block 會失效，新帳號直接 400。歷史只往後加，要修剪時連 thinking block 一起拿掉。
  • timeout 單位寫錯：TypeScript SDK 是毫秒，30 秒是 30_000。
  • 照舊範例送 temperature 或 prefill：API 版本 2026-10-21 會回 400。

小結

  • 所有功能都走 POST /v1/messages；用 @anthropic-ai/sdk 1.3.0 的 client.messages.create({ model, max_tokens, system, messages })，key 只放環境變數。
  • 回應的 content 是 block 陣列，Opus 5.5 通常先有一個內容是空字串的 thinking block；讀文字要過濾 type === 'text'。
  • 先看 stop_reason：end_turn、stop_sequence 才是完整的回答；截斷、拒答、工具呼叫都要另外處理。
  • usage 的 output_tokens 包含思考，是計費的依據，要記錄下來。
  • API 無狀態：每次送完整歷史，assistant 存完整的 content，失敗時復原；歷史只往後加，不改前面。
  • client 的 timeout 單位是毫秒、預設 10 分鐘，maxRetries 預設 2；依功能設定合理的值，由一個地方建立 client 再傳給需要的程式。
  • 練習用真正的 SDK 加上假的 fetch 判分：檢查回傳值，也檢查實際送出的請求。
