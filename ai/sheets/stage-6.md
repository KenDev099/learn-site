把整門課組成一個能上線的客服助理。先寫下能做與不能做，防護放在模型的前後。用 eval 證明沒有變差，用實際 usage 算月費。[回 AI 應用開發 學習地圖](../index.html)

## A 先寫下能做與不能做
| 能做 | 不能做（轉店員） |
|---|---|
| ok 根據門市文件回答菜單、價格、過敏原、營業時間、集點、退款規則，附引用來源 | no 文件裡沒有的問題，不用模型自己的知識補 |
| ok 查登入顧客自己的訂單 | no 查別人的訂單、透露其他顧客的資料 |
| ok 一到三句的繁體中文 | no 退款、改價、取消訂單，只能請顧客找店員 |

「轉店員」是 `status: 'abstain'`，一個明確、被測試的結果，不是失敗。

## B 一個問題走過的路 {span=2}
```flow LR
(POST /chat) -> [身分 → 限流 → 內容] -> [遮蔽個資] -> [混合檢索，只搜官方文件] -> {有資料}
{有資料} --> [轉店員]: 沒有且不是問訂單，不呼叫 API
{有資料} -> [agent 迴圈] -> {驗證引用}
{驗證引用} --> [轉店員]: 引用不存在或沒有根據
{驗證引用} -> [過濾輸出] -> *[SSE 回前端]
```
每個模組一個函式，依賴（資料庫、embedding、client、時鐘、log）從參數傳入：測試能換上假的 client、時鐘、檢索，各自驗證。這個專題的迴圈最多 4 輪、20,000 token；不管哪一步停下，每次都留一筆 log。

## C 防護的順序
| 順序 | 步驟 | 為什麼在這裡 |
|---|---|---|
| 1 | 遮蔽個資 | 之後檢索、模型、log 拿到的都是遮蔽後的版本 |
| 2 | 檢索；空的且不是問訂單就轉店員 | 沒有資料可以根據，叫模型回答只會花錢 |
| 3 | agent 迴圈有輪數與 token 上限 | 一定會停，停下來就轉店員 |
| 4 | 驗證 sources | 引用不存在、或沒有引用也沒有工具成功，都轉店員 |
| 5 | 過濾輸出 | 移除圖片、HTML、白名單以外的連結 |
| 6 | log 一次 | 轉店員的原因是判斷問題在檢索還是模型的線索 |

## D 資料與模型呼叫
- 信任程度記在文件上（`official`／`quarantined`），過濾寫在 SQL 裡；隔離一份文件只要一句 UPDATE。
- 相似度下限讓無關的問題拿到空結果，不花錢呼叫模型；下限用 eval 調。
- 結構化輸出與 strict 工具可以一起用：先看 stop_reason，`tool_use` 就執行工具，`end_turn` 才讀 `parsed_output`。
- 回答的 `c1`、`c2` 換回文件 id 並去掉重複，前端顯示來源、eval 比對 `mustCite` 都用它。

## E Eval 與成本報告
```callout warn 整體通過率會掩蓋關鍵失敗
每題跑 3 次，critical 每次都要對；報告分開列出 critical 失敗，並收集每次的 usage。查別人的訂單錯一次，就是權限漏洞。
```
```kv cols=1
每次費用: `costOf(usage, model)`，四種 token 各用自己的單價
每則對話平均: 全部 ask 的費用加總 ÷ ask 次數
月費: 每則對話平均 × 每天幾則 × 30
最貴的題目: 找出錢花在快取寫入、輸出長還是多一輪
```
換模型要同時看品質與 critical 失敗，不只看價格；報告寫上價格的查詢日期。

## F 端點與上線文件
端點從便宜的檢查到昂貴的：身分（401）→ 限流（429）→ 內容（400）→ 模型。身分只來自登入資訊，body 裡的 customerId 不能用。功能旗標是出事時的止血開關。SSE 先送 status，驗證完才送 delta（整段回答）與 done，不逐字轉送沒驗證過的輸出。

| 小節 | 寫成這樣才算 |
|---|---|
| 權限 | 列出工具與欄位；寫明沒有退款工具 |
| 預算 | 有數字、超過時系統怎麼做，不是「控制成本」 |
| 告警 | 每個指標有門檻、寫明通知誰 |
| 回退 | 旗標名稱、關掉後使用者看到什麼 |
| 資料保留 | log 存哪些欄位、保留幾天、個資怎麼處理 |
| 已知限制 | 至少 3 點 |

ADR 記下背景、決定、沒選的方案與代價。上線檢查清單與 ADR 寫到別人做得到：有數字、有步驟、有代價。
