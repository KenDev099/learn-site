階段 3：檔案與位元組 · 第 10 課

檔案系統：路徑、錯誤碼與原子寫入

咖啡店的小後台還沒有資料庫：菜單存在 data/menu.json，訂單存在 orders.json。本機測試一切正常，上線第一週卻接連出了四件事：

  1. 從別的資料夾啟動伺服器，就說找不到菜單。
  2. 有一天菜單檔的權限被設錯，網站沒有報錯，而是顯示「今天沒有商品」，直到客人抱怨才有人發現。
  3. 後台存訂單檔的同時有別的請求在讀它，讀到寫一半的 JSON，那段時間的請求全部 500。
  4. 兩筆訂單同時送出，orders.json 裡只存進一筆。

這四件都不是語法錯誤，是對檔案系統的假設錯了：以為相對路徑一定從程式旁邊算、以為讀檔失敗就代表檔案不存在、以為寫檔是一瞬間的事、以為同一時間只有一個人在改檔案。這課依序修好它們，練習裡的 loadMenu、print-menu.ts、saveOrders、addOrder 就是這四個事故的修法。

這課的路線：
  1. 讀菜單用哪一種寫法：node:fs 有三種 API，為什麼處理請求只用 fs/promises。
  2. 換個資料夾就找不到菜單（事故 1）：相對路徑從哪裡算，程式自己帶的檔案怎麼找。
  3. 讀檔失敗怎麼分辨「還沒有資料」和「出事了」（事故 2）：看 err.code，不先檢查存在、不吞掉錯誤。
  4. 存檔時別人讀到半份 JSON（事故 3）：寫到暫存檔再 rename 的原子寫入。
  5. 兩筆訂單只存進一筆（事故 4）：一個程序內排隊，好幾個程序用鎖檔，什麼時候該換成資料庫；最後補上自己開的檔案為什麼一定要關。
這課會用到：
  • 第 4 課的 import.meta.dirname：目前這個程式檔所在的資料夾，不受從哪裡執行 node 影響。
  • 第 7 課的 thread pool：非同步的檔案讀寫交給 libuv 管理的一組背景執行緒，主執行緒繼續處理別的事。
  • 第 9 課的阻塞：同步的工作佔住唯一的 JavaScript 執行緒時，所有請求一起等。
  • TypeScript 課第 12 課的 Promise 鏈鎖：新工作接在上一個工作的 Promise 後面，讓非同步的操作一個一個來。

範例在 node/practice/work/10/examples/，第一次執行 node check.mjs node 10 後就會出現；在 work/10/ 裡執行 node examples/檔名.ts。

讀菜單要用 node:fs 的哪一種寫法？

修事故之前，先決定讀檔要怎麼寫。Node 操作檔案的內建模組是 node:fs（fs 是 file system 的縮寫）。因為歷史因素，同一件事有三種寫法，它們讀到的內容一樣，差別在「讀檔的這段時間，你的程式在做什麼」：

  • callback：呼叫時多傳一個函式，Node 讀完後呼叫它，第一個參數是錯誤（沒出錯是 null），第二個是結果。這是 Node 最早的非同步風格，Promise 出現之前的程式和套件都這樣寫。
  • Sync：函式名稱結尾是 Sync，例如 readFileSync。它一直到讀完才回傳，回傳值直接是內容，失敗時直接 throw。
  • Promise：從 node:fs/promises 匯入，回傳 Promise，配 await 和 try／catch 用，寫起來跟前端的 fetch 一樣。

執行 node examples/api-styles.ts，三種寫法依序讀同一份菜單：

import { readFile as readFileCb, readFileSync } from 'node:fs'
import { readFile } from 'node:fs/promises'

readFileCb(file, 'utf8', (err, text) => { … })   // 1. callback：做完時呼叫你的函式，第一個參數是錯誤
const text = readFileSync(file, 'utf8')          // 2. Sync：讀完才往下走
const text2 = await readFile(file, 'utf8')       // 3. fs/promises：回傳 Promise
Sync      讀到 241 個字
callback  讀到 241 個字
promises  讀到 241 個字

看輸出的順序：callback 寫在最前面，卻比 Sync 晚印。原因是 callback 版把讀檔交給 thread pool（第 7 課），自己馬上回傳，主執行緒繼續往下跑，才先跑到了 Sync 那一行。Sync 版本則是主執行緒自己等：讀完之前，整個程序什麼都不能做。命令列工具只做一件事，等一下無所謂；但在伺服器裡，這段時間所有請求都一起等（第 9 課）。菜單檔很小，讀一次只要很短的時間，可是每個請求都讀一次，或者檔案變大、磁碟變慢，就會累積成第 9 課那種整站卡住。

所以三種寫法的分工是：

寫法什麼時候用
node:fs/promises預設。處理請求時一律用它，配 async／await 和 try／catch
readFileSync 等 Sync程式啟動時讀一次設定、命令列小工具。這時還沒有請求在等，卡住沒關係
callback舊程式和舊套件。看得懂就好，新程式不用

這課接下來都用 fs/promises，讀菜單寫成 await readFile(path, 'utf8')。第二個參數 'utf8' 告訴它把讀到的位元組轉成字串；不給的話回傳的是 Buffer，也就是原始的位元組，第 11 課詳講。寫入、列出資料夾、刪除這些其他操作的函式整理在課末的「補充與查表」，用到時再查。

寫法決定了，但事故 1 跟寫法無關：同一行 readFile('./data/menu.json', 'utf8')，換三種寫法都一樣，換個資料夾啟動就找不到檔。問題出在 './data/menu.json' 這個路徑是怎麼算出來的。

為什麼換個資料夾啟動，就找不到菜單？

每個程序都有一個工作目錄（current working directory）：啟動它的程序替它決定的資料夾。從終端機手動執行時，就是你當下在終端機所在的資料夾；由 Docker、系統服務或排程工具啟動時，則是它們設定的資料夾。程式裡可以用 process.cwd() 查到它。不是 / 開頭的路徑叫相對路徑，例如 './data/menu.json'；作業系統解讀相對路徑時，是從工作目錄算起，不是從程式檔放的位置算起。第 4 課已經碰過這件事，fs 的每個函式都照這條規則。

所以在 work/10/ 執行時，'./data/menu.json' 指到 work/10/data/menu.json，找得到；到上一層 work/ 執行同一支程式，它指到 work/data/menu.json，那裡沒有檔案，讀檔就會失敗。這種失敗的錯誤碼是 ENOENT，意思是找不到檔案或資料夾，下一節會詳講錯誤碼。程式一個字都沒改，只是啟動的地方不同。

親眼看一次：執行 node examples/paths.ts，再到上一層執行 node 10/examples/paths.ts，比較兩次的輸出。下面是在 work/10/ 執行的結果：

process.cwd()         /Users/you/…/work/10
import.meta.dirname   /Users/you/…/work/10/examples
resolve('data/menu.json') /Users/you/…/work/10/data/menu.json
join(import.meta.dirname, '..', 'data', 'menu.json') /Users/you/…/work/10/data/menu.json
join('a/b', '../c', 'd.json') a/c/d.json
resolve('/srv', 'menu', '/etc') /etc
dirname  /srv/shop/data
basename menu.json menu
extname  .json
new URL('../data/menu.json', import.meta.url) file:///Users/you/…/work/10/data/menu.json

換到上一層執行時，process.cwd() 和 resolve('data/menu.json') 跟著變，後者指到不存在的 work/data/menu.json；import.meta.dirname 和用它組出來的路徑不變。

這就是修法：程式自己帶的檔案，要以程式檔所在的資料夾為起點，而不是工作目錄。import.meta.dirname（第 4 課）是 Node 載入這個模組時就決定的絕對路徑，跟從哪裡啟動無關。把它和後面的片段接起來，用的是 node:path 模組，不要自己用字串相加：自己接容易多一個或少一個斜線，也不會幫你處理 ..。node:path 裡最常用的兩個函式行為不太一樣：

函式做什麼
join(a, b, …)用 / 接起來並整理 ..、.、重複的斜線；結果可能還是相對路徑
resolve(a, b, …)從右往左組到變成絕對路徑為止，不夠就補上工作目錄。遇到 / 開頭的片段，前面的全部丟掉（上面的 /etc）
dirname／basename／extname取出資料夾、檔名、副檔名

對照輸出看：join('a/b', '../c', 'd.json') 只是把片段接起來、把 b/.. 抵銷，結果 a/c/d.json 還是相對路徑，拿去讀檔一樣從工作目錄算；resolve('data/menu.json') 片段不夠組成絕對路徑，就在前面補上工作目錄，所以它會跟著啟動位置變。菜單要寫成 join(import.meta.dirname, '..', 'data', 'menu.json')：起點本身是絕對路徑，接出來的結果就固定了。這裡多一個 '..'，是因為 paths.ts 在 examples/ 裡，data/ 在它的上一層；程式檔和 data/ 在同一層時（例如練習 2 的 print-menu.ts），寫 join(import.meta.dirname, 'data', 'menu.json') 就好。另一種寫法 new URL('../data/menu.json', import.meta.url) 以程式檔的網址為基準，得到 file:// 網址，fs 的函式也收這種 URL。

那 resolve() 什麼時候用？看路徑是誰給的：

  • 程式自己帶的檔案（菜單範本、SQL、測試資料）：以程式檔為準，用 join(import.meta.dirname, …) 或 new URL(…, import.meta.url)。
  • 使用者給的路徑（命令列參數，例如 node tool.ts ./orders.csv）：使用者打 ./orders.csv 時，指的就是他當下所在資料夾裡的檔案，所以以工作目錄為準，用 resolve() 轉成絕對路徑。
上線後「找不到檔」還有一個跟工作目錄無關的原因：大小寫。macOS 預設的檔案系統（APFS）不分大小寫：import './Menu.ts' 找得到 menu.ts，readFile('Data/menu.json') 也讀得到。部署到 Linux（分大小寫）就變成 ENOENT。檔名一律小寫，程式裡照實際大小寫寫。
💡 實務上：上線後的工作目錄常常不是你以為的那個
本機你習慣在專案根目錄執行 node，但上線後程式通常不是你手動啟動的：容器（Docker）、系統服務、排程工具會照它們自己的設定決定工作目錄，可能是別的資料夾、甚至根目錄 /，相對路徑就在這時壞掉，事故 1 就是這樣來的。另一個常見坑是把使用者上傳的檔案（例如咖啡店的商品照片）存在程式資料夾裡：重新部署時程式資料夾整個被換掉，照片跟著不見。所以實務上會把「程式自己帶的檔案」和「執行時產生的檔案」分開：前者用 import.meta.dirname 找，後者的位置用環境變數設定（第 2 課）。code review 看到 './data/…' 這種寫法，資深工程師會先問：「這支程式在正式環境是從哪個資料夾啟動的？」

路徑對了，readFile 就一定會成功嗎？不一定：檔案可能還沒建立、權限可能被設錯、路徑指到的可能是資料夾。事故 2 的菜單顯示「今天沒有商品」，就是把這些失敗混成了同一種情況。

讀檔失敗時，怎麼分辨「還沒有資料」和「出事了」？

讀檔失敗的原因很多，處理方式卻不一樣：菜單檔還沒建立，可以當成「還沒有商品」；權限被設錯，是設定壞了，要讓人知道。要分辨它們，看的是錯誤物件上的 code 屬性。fs 的函式最後都是請作業系統做事，作業系統做不到時會回傳一個錯誤碼（error code），Node 把它原封不動放進 err.code，是一個像 'ENOENT' 這樣的字串。錯誤訊息的文字可能因版本或作業系統而不同，錯誤碼是固定的，程式判斷一律看錯誤碼。

執行 node examples/errors.ts，它在暫存資料夾裡故意製造幾種常見的失敗，印出每次的 code 和訊息：

讀不存在的檔案         ENOENT | ENOENT: no such file or directory, open '/var/folders/…/nope.json'
把資料夾當檔案讀       EISDIR | EISDIR: illegal operation on a directory, read
把檔案當資料夾         ENOTDIR | ENOTDIR: not a directory, open '/var/folders/…/menu.json/x'
'wx' 開已經存在的檔案  EEXIST | EEXIST: file already exists, open '/var/folders/…/menu.json'
建立已經存在的資料夾   EEXIST | EEXIST: file already exists, mkdir '/var/folders/…/images'

這幾個加上權限錯誤，就是工作上最常見的錯誤碼。每一個代表什麼、通常怎麼處理：

code意思通常怎麼處理
ENOENT路徑上某一段不存在（No such file or directory）看情況：可以當成「還沒有資料」，或回 404
EACCES／EPERM沒有權限設定錯了，要讓人知道：丟錯、記 log
EISDIR／ENOTDIR是資料夾／路徑中間某段不是資料夾路徑錯了，丟錯
EEXIST已經存在用 'wx' 建檔時代表「別人先建了」（後面的鎖檔就靠它）
EMFILE這個程序開了太多檔案通常是開了沒關，見最後一節

表裡只有 ENOENT 對菜單來說是「正常情況」：還沒有菜單檔，就是還沒有商品。其他每一種都代表環境或程式有問題，該讓錯誤往外傳，讓呼叫的人和看 log 的人知道。往外丟之前還有一件事：注意上面 EISDIR 的訊息沒有寫路徑。只看到 illegal operation on a directory, read，在 log 裡根本不知道是哪個檔案出事。所以包裝錯誤時，要自己把路徑寫進訊息，並用 cause 保留原本的錯誤（TypeScript 課第 4 課），錯誤碼和原始訊息才不會在包裝時遺失：

try {
  text = await readFile(path, 'utf8')
} catch (err) {
  if ((err as NodeJS.ErrnoException).code === 'ENOENT') return { items: [] }   // 只有「不存在」是正常情況
  throw new MenuLoadError(`讀不到菜單檔 ${path}`, { cause: err })             // 其他都往外丟
}

這裡的 as 是因為 catch 拿到的 err 型別是 unknown（TypeScript 課第 17 課），TypeScript 不讓你直接讀 .code。NodeJS.ErrnoException 是 @types/node 提供的型別，描述 Node 系統錯誤上的 code、path、syscall 這幾個屬性。

這段的寫法是「直接讀，失敗了再看錯誤碼」。很多人直覺會反過來寫，先檢查檔案在不在：

if (!existsSync(path)) return { items: [] }
const text = await readFile(path, 'utf8')   // 還是可能 ENOENT

看起來更安全，其實有兩個問題。第一，檢查和讀取是兩個動作，中間有一段空檔，這段時間檔案可能被別的程序刪掉、被換掉。這類錯誤叫 TOCTOU（time-of-check to time-of-use）：檢查時的狀態，到使用時已經不一樣了。空檔很短，所以平常測不出來，上線後偶爾出現一次，最難查。Node 官方文件也明說不要在 open／readFile／writeFile 之前用 fs.exists 或 fs.access 檢查，直接做，再處理錯誤。第二，existsSync 只回答「在不在」：檔案在但沒有權限、路徑是個資料夾，它一樣回傳 true，接下來的 readFile 還是會失敗，catch 終究要寫。既然 catch 跑不掉，前面的檢查就只是多了一個 TOCTOU 的空檔。

另一個極端是 catch { return { items: [] } }，把所有錯誤都吞掉。這正是事故 2：菜單檔權限設錯時，readFile 丟出 EACCES，被 catch 接住、變成空菜單，網站顯示「今天沒有商品」，沒有報錯、沒有 log，要等客人抱怨才發現。原則是：只把你預期、知道怎麼處理的錯誤碼當成正常情況，其他一律往外丟。練習 1 就是把 loadMenu 改成這樣。

💡 實務上：正式環境最常遇到的是 EACCES 和磁碟滿
本機用自己的帳號跑什麼都能寫；上線後程式常以權限較低的使用者執行（容器裡常見），要寫入的資料夾卻屬於系統管理員帳號（root），結果一寫就 EACCES。另一個是 ENOSPC（磁碟空間不足），常常是 log 或暫存檔沒清，把磁碟塞滿。這些都不是程式能自己修好的，所以錯誤訊息要帶路徑和錯誤碼、記進 log，維運才能一眼看出要改權限還是清磁碟。事故 2 如果一開始就這樣寫，那天 log 裡會有一行帶著菜單路徑的 EACCES。寫 catch 前先問自己：「這個錯誤碼我知道怎麼處理嗎？不知道就往外丟。」

讀檔的兩個事故修好了。接下來是寫檔：事故 3 裡，後台存訂單檔的同時有人在讀，讀到的是半份 JSON。讀的那一方程式沒有錯，問題在 writeFile 寫檔的方式。

存訂單檔時，為什麼別人會讀到半份 JSON？

writeFile(path, text) 的行為是：檔案不存在就建立，存在就先把它清成 0 位元組，再把新內容一段一段寫進去。小檔一下就寫完，看不出問題；訂單檔累積到幾 MB，寫一次要好幾毫秒，這段時間裡檔案是空的或只有前半段。await writeFile 只是讓你這段程式等它寫完，別的請求、別的程序照樣可以在這段時間去讀，讀到的就是殘缺的 JSON，JSON.parse 一 parse 就丟錯，請求變成 500。

執行 node examples/torn-write.ts 看實際有多常發生：它一邊把約 5MB 的訂單檔存 20 次，一邊不停讀檔並 JSON.parse，數壞掉幾次。前一行是直接 writeFile，後一行是這一節要講的做法：

直接 writeFile：讀了 52 次，壞掉 51 次
暫存檔 + rename：讀了 31 次，壞掉 0 次

次數每次不同，但直接 writeFile 幾乎每次讀都壞。要的效果是：讀的人只會看到完整的舊檔或完整的新檔，看不到中間狀態。這個性質叫原子性（atomicity）：一個動作要嘛完全沒發生、要嘛完全做完，外面的人看不到做一半的樣子；有這個性質的寫檔叫原子寫入（atomic write）。writeFile 一段一段寫，本身做不到。做法是不要在原本的檔案上寫：先把新內容寫到同一個資料夾裡的另一個暫存檔，寫完再一步把它換上去。

const tmp = `${path}.${randomUUID()}.tmp`   // 同一個資料夾，每次不同的名字
try {
  await writeFile(tmp, JSON.stringify(orders))
  await rename(tmp, path)                   // 一步把新檔換上去
} catch (err) {
  await rm(tmp, { force: true })            // 失敗時清掉暫存檔
  throw err
}

短短幾行，每一個細節都有原因，少一個就會在某種情況下壞掉。

為什麼 rename 能一步換上去。寫暫存檔的這段時間，orders.json 完全沒被動到，讀的人讀到的是完整的舊檔。rename 在同一個檔案系統上蓋過已存在的檔案，是一步完成的：它不搬動資料，只是把 orders.json 這個名字改成指向新檔，所以任何時刻這個路徑要嘛指向舊檔、要嘛指向新檔。已經打開舊檔在讀的人，也會讀完完整的舊內容。

為什麼暫存檔要放在同一個資料夾。直覺會想放到系統的 /tmp，但 /tmp 可能是另一個檔案系統（例如另一顆磁碟、或記憶體裡的檔案系統）。跨檔案系統沒辦法「只改名字」，rename 會失敗，錯誤碼是 EXDEV；有些搬移工具遇到這種情況會自動改成「複製再刪除」，複製的過程又是一段一段寫，就不是原子的了。放在目標檔旁邊，就保證是同一個檔案系統。

為什麼名字每次都要不同。如果固定叫 orders.json.tmp，兩個同時存檔的呼叫會寫進同一個暫存檔，內容互相蓋掉；先 rename 的那個把暫存檔搬走了，後 rename 的那個就找不到檔案，得到 ENOENT。官方文件也寫了：同一個檔案在前一次 writeFile 結束之前再呼叫一次，是不安全的。用 randomUUID() 產生隨機名字，每次呼叫各寫各的暫存檔。

為什麼失敗時要刪掉暫存檔。寫到一半磁碟滿了、或 rename 失敗時，暫存檔會留在資料夾裡。不清掉的話，每次失敗都留下一個幾 MB 的 .tmp，磁碟慢慢被吃光，又變成上一節的 ENOSPC。清完之後要把原本的錯誤再丟出去，呼叫的人才知道這次沒存成功。

原子寫入保證的是「別人不會讀到寫一半的檔案」，不保證「斷電後資料還在」：writeFile 結束時，資料可能還在作業系統的記憶體裡沒寫到磁碟。這是另一件事，叫持久性，要靠 fsync 把資料真正寫到磁碟，細節見課末的「補充與查表」。練習 3 的 saveOrders 就是把上面這段寫完整。

💡 實務上：後端什麼時候還會自己寫檔
正式資料多半在資料庫，但後端還是常寫檔：匯出給會計的 CSV 報表、命令列工具的設定或狀態、下載到本機的暫存資料。只要「有別人可能同時讀這個檔」或「寫到一半程式可能被中斷」，就用暫存檔＋rename，成本只多兩三行。只有自己寫、寫完才有人用的一次性檔案（例如跑完才上傳的報表），直接 writeFile 就夠了。咖啡店的 orders.json 一邊被讀、一邊被寫，屬於前者。

現在讀的人不會再讀到半份 JSON，事故 3 解決了。但事故 4 換上原子寫入之後還在：兩筆訂單同時送出，存進去的還是只有一筆。這次壞的不是「寫」這個動作，而是寫之前讀到的資料。

兩筆訂單同時送出，為什麼只存進一筆？

新增一筆訂單要做三件事：讀出 orders.json、在陣列裡加一筆、整份寫回。這種「讀出、修改、寫回」的模式叫 read-modify-write。三步之間有 await：在等讀檔、等寫檔的時候，event loop 會去處理別的請求，別的請求也可以開始自己的三步。

執行 node examples/lost-update.ts：它讓 20 個請求同時把計數檔裡的數字加 1，每個請求都是讀出、加 1、寫回：

加了 20 次，結果是 1

過程是這樣：20 個呼叫幾乎同時開始，都在 await readFile 時讀到 0；接著各自在記憶體裡加成 1，再各自寫回 1。每一次寫入都把前一次的結果蓋掉，最後只剩 1。這就是 PostgreSQL 課第 19 課的遺失更新（lost update），只是資料從資料表換成檔案。事故 4 的兩筆訂單一樣：兩個請求都讀到同一份舊的訂單陣列，各自加上自己那筆再寫回，後寫的蓋掉先寫的。

換成上一節的原子寫入也沒用。原子寫入保證「寫進去的是一份完整的檔案」，但兩份完整的檔案，都是從舊資料算出來的，後寫的照樣蓋掉先寫的那筆訂單。問題不在「寫到一半」，而在「讀到的資料在寫回之前已經過時」。要修，就得讓 read-modify-write 這三步不能交錯：一個請求做完三步，下一個才能開始讀。

最簡單的情況是只有一個 Node 程序在改這個檔案。這時用 TypeScript 課第 12 課的 Promise 鏈鎖就夠了：程式記住「最後一個排進來的工作」的 Promise，新工作用 .then() 接在它後面，再把自己記成最後一個。所有新增訂單的呼叫就像排隊，同一時間只有一個在做 read-modify-write。這種讓操作一個一個來的做法叫互斥（mutual exclusion，常簡稱 mutex），用佇列實作時也叫序列化佇列。

但這個佇列是一個 JavaScript 變數，存在這個程序的記憶體裡。正式環境不一定只有一個程序在改 orders.json。

開成好幾個程序之後，怎麼讓它們排隊？

正式環境常把同一個伺服器開成好幾個程序，好用上多顆 CPU（第 24 課）；也可能另有一支排程程式會改同一個檔。每個程序有自己的記憶體、自己的一份佇列，程序 A 的佇列根本不知道程序 B 在做什麼，兩邊還是會同時 read-modify-write。這時需要一個所有程序都看得到的東西，而它們共同看得到的就是檔案系統。做法是鎖檔（lock file）：約定好「orders.json.lock 這個檔案存在」代表「有人正在改 orders.json」。想改的人先建立鎖檔，建成功才算拿到鎖；改完刪掉鎖檔，就是放鎖。

關鍵在「建立鎖檔」這一步本身不能有空檔。如果寫成 if (!existsSync(lock)) await writeFile(lock, '')，又是上一節的 TOCTOU：兩個程序同時檢查到「不存在」，都去建檔，都以為自己拿到了鎖。正確寫法是 open(lockPath, 'wx')。open 的第二個參數是開檔模式：w 是寫入，x 是「已經存在就失敗」。「檢查不存在」和「建立」由作業系統合成一步完成（底層是 O_EXCL 旗標），兩個程序同時搶，只會有一個成功，另一個拿到 EEXIST，也就是錯誤碼表裡說的「別人先建了」。

const handle = await open(lockPath, 'wx')   // 拿不到就丟 EEXIST
try {
  // 讀出 → 加一筆 → 寫回
} finally {
  await handle.close()
  await rm(lockPath, { force: true })        // 成功、失敗都要放鎖
}

拿到 EEXIST 代表別人正拿著鎖，等一下再試。等待時間要加一點隨機（例如 10～30ms）：如果大家都固定等 20ms，一群等鎖的程序會在同一瞬間一起重試、一起撞上，又一起等。放鎖一定要寫在 finally，因為中間任何一步都可能 throw（訂單格式不對、訂單檔壞掉）；沒刪掉鎖檔，之後每個人都在等一個永遠不會消失的鎖，整個新增訂單功能就停了。

這樣在正常情況下就夠了。但鎖檔是「大家約定好」的機制，有幾種情況約定會失效，要知道它的極限在哪裡：

程序當掉留下的鎖（stale lock）。程序拿著鎖時被 kill -9 強制結束或機器斷電，finally 根本沒機會執行，鎖檔就永遠留著。常見做法是看鎖檔的修改時間（stat 的 mtimeMs），超過某個門檻就當成沒人要了，刪掉重拿。門檻要比「正常持有鎖的最長時間」長很多：太短的話，會把別人還在用的鎖刪掉，兩個人又同時寫。練習 4 用的門檻是 5 秒。

刪除舊鎖本身也有競態。兩個程序同時判定鎖過期：A 先刪掉，重新拿到鎖；B 這時才執行刪除，刪掉的其實是 A 的新鎖，接著 B 也拿到鎖，兩個人同時在改。機率小但存在。要完全正確，需要在鎖檔裡寫入自己的編號、刪之前比對內容，或改用作業系統提供的檔案鎖，複雜度跟著上升。

網路磁碟與多台機器。NFS 這類網路檔案系統上，「已經存在就失敗」不一定可靠。伺服器開在多台機器上時，每台機器有自己的磁碟，A 機器上的鎖檔，B 機器根本看不到。

所以鎖檔適合的範圍有限。依情況選擇的方式：

情況做法
一個程序，資料量小（設定檔、本機工具的狀態）原子寫入＋程序內排隊
同一台機器上幾個程序，寫入不頻繁原子寫入＋鎖檔
多台機器、寫入頻繁、需要查詢或交易資料庫：交易與列鎖（第 20 課）、advisory lock（PostgreSQL 課第 33 課）

advisory lock 是 PostgreSQL 提供的「約定好的鎖」：概念跟鎖檔一樣，只是放在所有機器都連得到的資料庫裡，程序當掉時連線斷了，鎖也會自動釋放。

咖啡店的訂單會一直增加、會被同時寫入，正式環境應該放資料庫。這一課還是用檔案練習，是因為鎖、原子性、當掉後的清理這些問題，換成資料庫也還在，只是資料庫替你處理好了；先在檔案上親手做一次，才知道它替你做了什麼。練習 4 的 addOrder 就是用鎖檔把「讀出 → 加一筆 → 寫回」包起來，四個事故到這裡都有了修法。

還剩一個細節：鎖檔的程式碼裡，open() 回傳了一個 handle，在 finally 裡特地 close()。前面用的 readFile、writeFile 從來不用關，為什麼這裡要？

open() 拿到的檔案，為什麼一定要關？

readFile、writeFile 是「一次做完」的函式：自己開檔、讀寫、關檔，你只拿到結果。需要更細的控制時，例如只讀檔案前幾個位元組、或像鎖檔那樣要用 'wx' 模式建檔，就要自己呼叫 open()。它回傳一個 FileHandle：代表「一個開著的檔案」的物件，之後的讀寫都透過它。

為什麼開著的檔案要關？作業系統替每個開著的檔案記一個整數編號，叫檔案描述元（file descriptor，常簡稱 fd），FileHandle 裡面包著的就是這個編號。每個程序能同時持有的 fd 數量有上限，而且網路連線也佔 fd。開了不關，fd 一直累積，用完之後所有開檔都失敗，連接受新的網路連線也一起失敗，錯誤碼是 EMFILE。這種洩漏不會馬上出事，常常是伺服器跑了幾天、累積夠多才突然全面失敗。

以前的寫法是用 try／finally 包起來，在 finally 裡 close()，就像鎖檔那段。Node 24 可以改用 JavaScript 新的 await using 宣告：用它宣告的變數，在離開所在的區塊時，會自動呼叫物件的 [Symbol.asyncDispose]() 方法並等它完成；不管是正常 return 還是 throw 離開都一樣。FileHandle 的這個方法做的就是 close()。執行 node examples/filehandle.ts，它印出 fd 編號和檔案的前 12 個位元組：

async function firstBytes(n: number) {
  await using fh = await open(file, 'r')
  const { bytesRead, buffer } = await fh.read(Buffer.alloc(n), 0, n, 0)
  return buffer.subarray(0, bytesRead).toString('utf8')
}   // ← 離開時自動 fh.close()，return 或 throw 都一樣

那鎖檔為什麼不用 await using？因為放鎖要做兩件事：關掉 FileHandle，還要刪掉鎖檔。await using 只負責關閉，刪檔還是得自己寫，所以練習 4 直接用 try／finally 把兩件事寫在一起比較清楚。await using 的支援版本見課末。

回到開場的四件事：菜單路徑用 import.meta.dirname 組、讀檔失敗只把 ENOENT 當正常、存檔寫暫存檔再 rename、新增訂單用鎖檔排隊，自己開的檔案用完就關。下面的練習把這四個修法實際寫一次。

練習

練習檔在 node/practice/work/10/，在 learn/ 執行 node check.mjs node 10 判分。測試在暫存資料夾裡建立各種情況（沒有權限的檔案、資料夾、壞掉的 JSON、舊的鎖檔），用隨機資料，也會開子程序。

練習 1：load-menu.ts 的 loadMenu(path) 現在先 existsSync 再讀，其他錯誤原封不動丟出去。改成：

  • 直接讀檔。檔案不存在（ENOENT）時回傳 { items: [] }。
  • 其他讀檔錯誤（沒有權限、是資料夾）和 JSON 格式錯，都丟出 MenuLoadError：訊息要包含完整的檔案路徑，cause 是原本的錯誤（new MenuLoadError(訊息, { cause: err })）。

不能用 catch 把所有錯誤都變成空菜單。

練習 2：print-menu.ts 印出旁邊 data/menu.json 的菜單。在 work/10/ 執行 node print-menu.ts 正常，到上一層執行 node 10/print-menu.ts 就 ENOENT。修好它，從哪個資料夾執行都讀到程式旁邊的 data/menu.json。測試會把它複製到別處、換一份菜單，從三個不同的工作目錄執行。

練習 3：save-orders.ts 的 saveOrders(path, orders) 現在直接 writeFile。改成原子寫入：

  • 寫入期間不管什麼時候讀，都是完整的舊內容或完整的新內容（測試一邊存約 5MB 的資料，一邊讓另一個程序不停讀檔；改成 writeFileSync 擋不住別的程序）。
  • 暫存檔放在目標檔的同一個資料夾（測試會讓系統暫存資料夾不能用）。
  • 同時呼叫好幾次存同一個檔，每次都要成功，最後檔案是其中一次的完整內容，資料夾裡不留暫存檔。
  • 寫入失敗時 Promise 要 reject，而且不能留下暫存檔（測試把目標路徑先建成資料夾，讓 rename 失敗）。

練習 4：add-order.ts 的 addOrder(path, order) 讀出 orders.json、加一筆（id 是最後一筆加 1）、用練習 3 的 saveOrders 寫回，回傳存進去的訂單。現在同時呼叫會遺失更新。用鎖檔 path + '.lock' 把「讀出 → 檢查 → 加一筆 → 寫回」包起來：

  • 用 open(lockPath, 'wx') 拿鎖。EEXIST 代表別人拿著，等 10～30ms（加一點隨機）再試；其他錯誤往外丟。
  • 做完在 finally 關閉 FileHandle 並刪掉鎖檔，成功、失敗（訂單不合法、訂單檔壞掉）都一樣。
  • 鎖檔的修改時間超過 5 秒，當成當掉的程序留下的：刪掉後重拿。剛建立的鎖檔是別人正在用，要等它消失。

測試會在同一個程序同時呼叫 50 次、開 4 個程序各加 25 筆（只用程序內的佇列不會過），還會預先放一個 10 秒前的鎖檔和一個 300ms 後才被刪掉的鎖檔。

練習 5：程式先 if (existsSync(path))，成立才 await readFile(path)。這樣還可能拿到 ENOENT 嗎？

✓ 檢查和使用是兩個動作，中間的狀態變化叫 TOCTOU。正確做法是直接讀，再處理 err.code === 'ENOENT'。a 是這個誤解本身；c 錯：任何作業系統都一樣，只要有別的程序（或同一程序裡另一個 async 流程）會動這個檔案。

練習 6：設定檔每次都用 writeFile(path, JSON.stringify(config)) 整份覆蓋。另一個程序偶爾讀到 Unexpected end of JSON input。原因是？

✓ 覆蓋寫入期間檔案是不完整的，別的程序隨時能讀。修法是寫到同一個資料夾的暫存檔，再 rename 蓋過去。b 錯：writeFileSync 只擋住自己這個程序，另一個程序照樣能在寫到一半時讀。a 錯：stringify 是同步的，回傳的一定是完整字串。

練習 7：addOrder 用 Promise 鏈排隊，單機測試 100 筆同時寫入都正確。部署時把伺服器開成 2 個程序，共用同一個 orders.json。還安全嗎？

✓ Promise 鏈存在程序的記憶體裡，只管得到同一個程序裡的呼叫。跨程序要用所有程序都看得到的東西：鎖檔（open(…, 'wx')）或資料庫的鎖。c 錯：原子寫入只保證不會讀到寫一半的檔案，兩個程序都讀到舊資料、各自寫回，還是遺失更新。

常見錯誤

  • 用相對路徑讀程式自己帶的檔案：相對路徑以工作目錄為準，換個資料夾啟動就 ENOENT。用 join(import.meta.dirname, …)。
  • 在 macOS 上能跑、到 Linux 就找不到檔：macOS 預設不分大小寫，Linux 分。檔名一律小寫，程式照實際名稱寫。
  • 先 existsSync 再讀：檢查和讀取之間狀態會變（TOCTOU），而且其他錯誤還是要處理。直接讀，看 err.code。
  • 吞掉所有錯誤：catch { return [] } 讓權限錯誤、壞掉的檔案看起來像「沒有資料」。只處理預期的錯誤碼，其他丟出去，保留 cause。
  • 直接覆寫重要檔案：writeFile 先清空再寫，讀的人會讀到一半，寫到一半當掉檔案就壞了。寫暫存檔再 rename。
  • 暫存檔用固定名字或放在 /tmp：固定名字讓同時存檔互相蓋掉；/tmp 可能是別的檔案系統，rename 不再原子。同資料夾、隨機名字。
  • 以為程式裡的鎖擋得住別的程序：Promise 鏈只在一個程序裡有效。跨程序用鎖檔，跨機器用資料庫。
  • 放鎖沒寫在 finally：中途出錯就留下鎖，之後所有人卡住。
  • open 之後沒有 close：檔案描述元用完就 EMFILE，連新的網路連線都接不了。用 await using 或 try／finally。

小結

  • 處理請求用 node:fs/promises；Sync 會佔住主執行緒，只用在啟動時或命令列工具；callback 看得懂就好。
  • 事故 1：相對路徑從工作目錄算，不是從程式檔算。程式自己帶的檔案用 import.meta.dirname 組路徑，使用者給的路徑用 resolve()。
  • 事故 2：直接做，失敗再看 err.code：ENOENT、EACCES、EISDIR、EEXIST、EMFILE。不先檢查存在（TOCTOU），只處理預期的錯誤碼，其他包成有路徑、有 cause 的錯誤丟出去。
  • 事故 3：writeFile 先清空再寫。原子寫入用同資料夾、隨機名字的暫存檔，寫完 rename，失敗時刪掉暫存檔；防斷電還要 fsync。
  • 事故 4：read-modify-write 會遺失更新，原子寫入擋不住。一個程序用 Promise 鏈排隊；多個程序用 open(…, 'wx') 的鎖檔，在 finally 放鎖，處理當掉留下的鎖；多台機器或寫入頻繁就交給資料庫。
  • open() 回傳的 FileHandle 佔著一個檔案描述元，一定要關，await using 會自動關。

下一課看檔案和網路底下真正流動的東西：位元組。為什麼「拿鐵」的長度是 2，存起來卻佔 6 個位元組，以及 Buffer 和編碼怎麼處理。

常用的 fs/promises 函式

查表用，不用背。全部從 node:fs/promises 匯入。

要做的事寫法
讀文字檔await readFile(path, 'utf8')（不給編碼會回傳 Buffer，第 11 課）
寫文字檔await writeFile(path, text)：不存在就建立，存在就先清空再寫
附加到檔尾await appendFile(path, line)
建資料夾await mkdir(dir, { recursive: true })：連中間的資料夾一起建，已經存在也不報錯
列出資料夾await readdir(dir, { withFileTypes: true }) 回傳 Dirent，可以問 isDirectory()；加 recursive: true 連子資料夾一起列（v20.1.0 起）
找符合樣式的檔案for await (const f of glob('**/*.json', { cwd }))（v24.0.0 起 stable）
大小、修改時間await stat(path) 的 size、mtime、mtimeMs
改名、搬移await rename(from, to)
刪除await rm(path, { force: true })（不存在也不報錯）；資料夾加 recursive: true
複製await copyFile(from, to)；整個資料夾 await cp(from, to, { recursive: true })（v22.3.0 起 stable）

執行 node examples/list.ts 看 readdir、stat、glob 的輸出。stat 印出 menu.json 有 281 位元組，api-styles.ts 卻說讀到 241 個字：中文字在 UTF-8 裡一個字 3 個位元組，第 11 課詳講。

持久性：斷電後資料還在嗎

持久性（durability）和原子寫入是兩件事：writeFile 結束時，資料可能還在作業系統的記憶體裡，這時斷電，新檔可能是空的。要確定寫到磁碟，要呼叫 fsync：writeFile(tmp, text, { flush: true }) 會在寫完後呼叫 filehandle.sync()。嚴格來說，rename 這個改名動作也要對資料夾做一次 fsync 才不會在斷電後消失。代價是每次存檔慢很多。只防「別人讀到一半」不需要它；防「斷電後資料壞掉」才需要。資料重要到這種程度，通常已經該放資料庫了。

版本備註

  • readdir 的 recursive 選項從 v20.1.0 起可用。
  • fs/promises 的 cp 從 v22.3.0 起 stable；glob 從 v24.0.0 起 stable。
  • FileHandle 的 [Symbol.asyncDispose]()（讓 await using 自動關檔）從 v24.2.0 起不再是實驗功能。await using 是 JavaScript 的新語法，Node 24 的 V8 支援，type stripping 也能處理。
