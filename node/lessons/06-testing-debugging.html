階段 1：Node 與開發環境 · 第 6 課

測試與除錯入門

咖啡店的結帳程式這個月出了兩次事。第一次，同事改了一行折扣規則，上線後「剛好 300 元」的訂單沒有折到 30 元，客人在櫃台抱怨才被發現。第二次，POS 機匯出的一筆訂單讓結帳程式直接當掉，終端機上只留下一大段錯誤訊息，沒有人看得出是哪裡壞了。

這一課要讓這兩種事故以後在你的電腦上就被抓到，而不是在櫃台。第一種靠測試：一份會自己把每條折扣規則檢查一遍的程式，改完程式幾秒內就知道有沒有改壞。第二種靠除錯：從錯誤訊息一路追到真正的原因，修好之後再補一個測試，讓同一個 bug 回不來。兩件事都在 work/06/ 的同一套結帳程式上做。

這課的路線：
  1. 「剛好 300 元」為什麼會溜到櫃台、第一個測試：手動點一點為什麼擋不住它，怎麼用內建的 node:test 把這條規則寫成會自己檢查的程式。
  2. 全部通過就代表守住了嗎：好的測試要在程式壞掉時失敗；async 測試為什麼會什麼都沒檢查就通過。
  3. 怎麼證明測試抓得到 bug：用故意改壞的版本檢驗測試，這也是這門課 check.mjs 判分的方式。
  4. 結帳當掉了：讀 stack trace 找到出事的那一行，再用除錯器停下來看當時的值。
  5. 錯誤發生在伺服器上：被包過一層的錯誤怎麼讀，接到 bug 回報先要什麼。
這課會用到：
  • TypeScript 課第 4 課的 throw 與 cause：包裝錯誤時用 new Error('…', { cause: err }) 把底層原因帶著走。
  • TypeScript 課第 9 課的 async 錯誤：async 函式裡丟的錯會變成 rejected Promise，要 await 才接得到。

「剛好 300 元沒折到」為什麼會一路溜到櫃台？

先看那次事故是怎麼發生的。折扣規則是「打折後的金額 ≥ 300，再折 30」。同事整理程式時把 >= 寫成了 >。改完他試了幾筆：一杯拿鐵 110 元，對；一筆 350 元的訂單折成 320，也對。他看不出任何問題，就上線了。壞掉的只有「剛好 300 元」這一個金額，而他沒有試到。

這就是手動測試的極限。你在前端改完程式，會打開瀏覽器點一點，看畫面對不對，這也是在測試，只是靠人來做。結帳的規則有好幾條：單價乘數量、數量必須是正整數、優惠碼打九折、滿 300 折 30、最後四捨五入。每條規則又有好幾個要試的金額。每改一次程式，就要把這些組合全部重試一遍；人會累、會趕時間、會覺得「我只改了一行，應該沒事」，於是每次都只試幾個順手的例子。bug 偏偏就躲在沒試到的那幾個。

自動化測試（test）是把「試一試」寫成程式：一段程式呼叫你的結帳函式，傳進準備好的訂單，再檢查回傳的金額是不是預期的值。它跟你手動試的是同一件事，差別在於寫好之後每次都完整重跑：幾百個情況幾秒內跑完，第一千次跟第一次一樣仔細。如果那次改動之前就有一個「剛好 300 元要折成 270」的測試，同事存檔、跑一次測試，馬上就會看到它失敗。

這帶來兩個長期的好處。第一，測試是可以執行的規格：「剛好 300 元也折 30」寫在需求文件裡會被忘記，寫成測試就每次都會被檢查，新同事讀測試的名稱就知道有哪些規則。第二，你敢改程式：重構、升級套件之後跑一次測試，全部通過，才有根據說「原本的行為沒被弄壞」。這門課每一題的判分其實就是測試：你在第 1 課看到的「測試沒通過」，背後就是這一課要教的 node:test。

測試也有成本：要寫、要跟著規則一起維護，而寫得差的測試會給你錯誤的安全感，讓人以為有在檢查，其實沒有。這一課後半大部分在處理這件事。先從最小的一步開始：在 Node 裡，這段「會自己檢查的程式」要怎麼寫、怎麼執行？

第一個測試：怎麼把一條規則寫成會自己檢查的程式？

要讓測試自動跑，需要兩樣東西。第一樣是測試執行器（test runner）：一個負責找出測試檔、一個一個執行裡面的測試、記下哪些通過哪些失敗、最後印出總結的工具。前端常見的 Vitest、Jest 就是測試執行器。Node 內建了一個，從 node:test 引入，不用安裝任何套件。

第二樣是斷言（assertion）：一句「這個值應該等於那個值」的檢查。斷言成立時什麼事都不會發生；不成立時它丟出一個 AssertionError。測試執行器會接住這個錯誤，把這個測試標成失敗、記下錯誤訊息，然後繼續跑下一個測試。所以「測試失敗」的意思就是：測試裡有一個斷言丟了錯。Node 的斷言從 node:assert/strict 引入。

先寫一個最小的測試，確認一杯拿鐵算出 110 元：

// order-total.spec.ts
import test from 'node:test'
import assert from 'node:assert/strict'
import { calcOrderTotal } from './order-total.ts'

test('一杯拿鐵是 110 元', () => {
  assert.equal(calcOrderTotal([{ name: '拿鐵', price: 110, qty: 1 }]), 110)
})

逐行看：前兩行引入測試執行器和斷言；第三行引入要測的函式，import 路徑寫 .ts，因為 Node 直接執行 TypeScript（第 5 課）。test(名稱, 函式) 登記一個測試，名稱寫的是這個測試守住的規則，函式裡呼叫 calcOrderTotal，再用 assert.equal(實際, 預期) 檢查結果。執行時把測試檔交給 node --test：

$ node --test order-total.spec.ts
✔ 一杯拿鐵是 110 元 (0.5ms)
ℹ tests 1
ℹ pass 1
ℹ fail 0

✔ 是這個測試通過，下面三行是總結：總共幾個測試、通過幾個、失敗幾個。

斷言要從 node:assert/strict 引入，不是 node:assert。兩者都有 equal，但舊的 node:assert 裡的 equal 用寬鬆的 == 比較，'110' == 110 會成立。結帳程式如果不小心回傳了字串 '110'，寬鬆的斷言會讓它通過，而你的前端拿到字串去做加法就會出事。strict 版的 equal 是嚴格相等，跟 === 差不多（差別是 NaN 等於 NaN）。

斷言可以加第三個參數，寫失敗時要顯示的說明，例如 assert.equal(total, 270, '剛好 300 元要折 30')。測試失敗時，這句話會直接告訴你哪條規則壞了，不用回頭讀程式。

測試失敗時，Node 會把預期值和實際值的差異印出來。assert.deepEqual 會逐層比對物件和陣列的內容，型別也要一樣。下面是用它比對一個包含陣列的物件時失敗的輸出（這裡用最小的例子，只為了看懂輸出格式）：

✖ 拿鐵兩杯 (1.5ms)
  AssertionError [ERR_ASSERTION]: Expected values to be strictly deep-equal:
  + actual - expected

    {
      a: [
        1,
  +     2
  -     3
      ]
    }
      at TestContext.<anonymous> (file:///…/b.spec.ts:5:48)

由上往下讀：✖ 和測試名稱告訴你哪個測試失敗；+ 開頭的是實際得到的值，- 開頭的是你預期的值，這裡是第二個元素預期 3、實際 2；最後一行 b.spec.ts:5:48 是失敗的斷言在哪個檔案的第 5 行第 48 欄。

有任何一個測試失敗，node --test 就以結束碼 1 結束（第 2 課講過結束碼：0 代表成功，非 0 代表失敗）。這個數字讓測試能接上自動化流程。很多團隊會設定一個服務，每次有人推程式碼，就自動在一台乾淨的機器上跑全部測試，這叫 CI（continuous integration，持續整合）。CI 看的就是結束碼：是 1 就把這次修改標成失敗、不讓它合併。回到開場的事故：如果當時有「剛好 300 元」的測試和 CI，把 >= 改成 > 的那個修改根本合併不進去。

只跑名稱符合的測試、存檔自動重跑、用 describe 分組、在測試前後準備和清理資源的 hook，還有其他常用斷言，都整理在課末的「補充與查表」，用到時再查。

現在你會寫測試、看得懂通過與失敗了。但這裡有個陷阱：測試能失敗，不代表它會在該失敗的時候失敗。

測試全部通過，就代表規則守住了嗎？

回到同事的情況。假設他當時其實有寫測試，只是測的是 350 元的訂單：預期 320，>= 和 > 兩種寫法都算出 320，測試照樣通過。這份測試全部通過，卻完全守不住「滿 300 折 30」這條規則。判斷一個測試好不好，標準只有一個：程式壞掉時，它會不會失敗。「全部通過」只說明現在的程式符合測試，不說明測試有能力發現錯誤。

下面幾個寫法，都是為了讓測試在程式壞掉時真的會失敗。

測邊界。bug 最常躲在「剛好」的地方：剛好等於門檻、門檻減 1、0、空陣列、不合法的輸入。>= 寫成 > 只有在剛好 300 時才算出不同的結果，所以 300 一定要測，299 也要測（確認沒滿的不折）。不合法的輸入也是邊界：規則說數量必須是正整數，那數量 0、數量 1.5 都應該丟出 RangeError。檢查「一定要丟錯」用 assert.throws：

assert.throws(() => calcOrderTotal([{ name: '拿鐵', price: 110, qty: 0 }]), RangeError)

注意傳進去的是一個函式 () => calcOrderTotal(…)，不是直接呼叫的結果。直接寫 assert.throws(calcOrderTotal(…), RangeError) 的話，calcOrderTotal 在 assert.throws 開始執行之前就丟錯了，錯誤直接讓測試中斷，assert.throws 根本沒機會接住它。包成函式，assert.throws 才能自己呼叫、自己接住、檢查錯誤的類型；呼叫後沒丟錯，它會讓測試失敗。

一個測試只測一個行為。名稱寫出規則，例如「優惠碼不分大小寫」。一個測試塞十個斷言的話，第一個斷言失敗，後面的就不會執行，你只看到一個錯，不知道其他規則是好是壞；名稱也說不出是哪條規則壞了。一個測試一條規則，失敗的名稱本身就是診斷。

準備、執行、檢查三段（Arrange-Act-Assert）。先準備資料，再呼叫一次要測的函式，最後斷言。三段分開，讀的人一眼看得出「在什麼情況下、做了什麼、預期什麼」：

test('先打折再看有沒有滿 300', () => {
  // 準備：原價 320，打九折後 288
  const items = [{ name: '美式咖啡', price: 80, qty: 1 }, { name: '起司蛋糕', price: 120, qty: 2 }]
  // 執行
  const total = calcOrderTotal(items, 'LATTE10')
  // 檢查：288 沒有滿 300，不再折 30
  assert.equal(total, 288)
})

這個測試守住的是「順序」這條規則：如果有人改成先判斷滿額再打折，320 會先折 30 變 290、再打九折變 261，測試就會失敗。

測試之間互不依賴。每個測試自己準備需要的資料，不靠上一個測試留下的狀態。否則單獨跑某一個測試、或換個順序跑，結果就變了，你會花時間追一個根本不在程式裡的 bug。

先看到它失敗。寫完測試，故意把程式改壞（例如把 >= 改成 >），確認測試會變紅，再改回來。從來沒紅過的測試，你不知道它到底有沒有在檢查。這一步看起來多餘，下面的 async 測試會說明它為什麼必要。

async 測試一定要 await

結帳程式不會永遠只算數字。menu-price.ts 的 fetchMenuPrice(name) 查一個品項的價格，它是 async 函式：現在先用 setTimeout 假裝要等一下，之後會換成真的去問菜單服務。測這種函式時，有一類測試會什麼都沒檢查就通過，而且看起來完全正常。

先看測試執行器怎麼處理 async 測試。測試函式是 async 函式時，它會回傳一個 Promise；測試執行器會等這個 Promise 完成：成功就算通過，失敗（rejected）就算失敗。換句話說，測試執行器只等「測試函式回傳的那個 Promise」，不知道你在函式裡另外開了哪些 Promise。

work/06/examples/unawaited.spec.ts 就踩到這一點（裡面的 fetchPrice 故意回傳 999）：

test('拿鐵是 110 元', async () => {
  fetchPrice().then(price => assert.equal(price, 110))   // 沒有 await
})

這段程式的執行順序是：呼叫 fetchPrice()，拿到一個還沒完成的 Promise，在它後面掛一個 .then，然後測試函式就結束了，因為沒有任何東西叫它等。測試函式回傳的 Promise 馬上成功，測試執行器判定通過。20 毫秒後 fetchPrice 才回傳 999，.then 裡的斷言這時才執行並丟錯，但這個測試早就記成通過了：

$ node --test examples/unawaited.spec.ts
✔ 拿鐵是 110 元 (0.4ms)
ℹ Error: Test "拿鐵是 110 元" at examples/unawaited.spec.ts:11:1 generated asynchronous
  activity after the test ended. This activity created the error "AssertionError …
  999 !== 110" and would have caused the test to fail, but instead triggered an
  unhandledRejection event.
✖ examples/unawaited.spec.ts

這個測試本身顯示 ✔。Node 24 在測試結束後發現有斷言丟錯，所以把整個檔案判為失敗（最後一行的 ✖），但訊息不在那個測試底下，很容易看漏。

更糟的是下面兩種寫法，連這個補救都沒有，永遠通過：

// 1. 沒有 await：price 是一個 Promise，Promise 一定是 truthy
const price = fetchMenuPrice('拿鐵')
assert.ok(price)

// 2. 斷言只寫在 catch 裡：程式沒丟錯時，catch 不會執行，一個斷言都沒跑
try {
  await fetchMenuPrice('珍珠奶茶')
} catch (err) {
  assert.match(err.message, /珍珠奶茶/)
}

第一種用了 assert.ok(值)：它只檢查值是不是 truthy，是最弱的斷言。121、'abc'、一個 Promise 都會過，所以沒 await 拿到的 Promise 也會過，價格算錯成 121 也會過。知道預期值時就用 assert.equal。第二種的斷言寫在 catch 裡：查不到的品項如果沒有丟錯（這正是 bug），程式根本不會進 catch，一個斷言都沒執行，測試照樣通過。這兩種寫法在 Node 裡不會有任何警告，只有「先看到它失敗」那一步會讓你發現。

正確寫法是等到值出來再斷言：assert.equal(await fetchMenuPrice('拿鐵'), 110)。要求「一定要失敗」時用 assert.rejects：它接收一個 Promise，等它完成；Promise 失敗而且錯誤符合條件才算通過，Promise 成功了反而讓測試失敗。assert.rejects 本身也回傳 Promise，所以前面一樣要 await：await assert.rejects(fetchMenuPrice('珍珠奶茶'), /珍珠奶茶/)。

💡 實務上：修 bug 之前，先寫一個會紅的測試
客服回報「剛好 300 元沒有折 30」，有經驗的工程師不會直接改程式，而是先寫一個重現這個 bug 的測試，看到它紅，再修到它綠。這個測試留在專案裡，以後有人再改折扣規則，同一個 bug 就回不來。測試的力氣優先花在算錯會出事的地方：金額、權限、訂單狀態；只是把資料原樣傳下去的程式，測了價值不高。code review 時資深會問：「這個 PR 改的規則，壞掉時哪一個測試會紅？」答不出來，通常就是少了邊界的測試。

到這裡你有了一張檢查清單：測邊界、一個測試一個行為、該 await 的都 await、先看到它失敗。不過「我覺得我的測試夠好」還是主觀的判斷。下一節看怎麼客觀地證明一份測試抓得到 bug。

怎麼證明測試抓得到 bug？變異測試與 check.mjs 的判分

上一節的「先看到它失敗」是手動做的：把程式改壞，看測試紅不紅。把這件事自動化、一次做很多個，就是這門課判分的方式。

那「寫測試」的題目要怎麼判分？檢查你的測試「全部通過」沒有意義：上一節看過，一個斷言都沒有的測試、沒 await 的測試，都會全部通過。判分用的是變異測試（mutation testing）。做法是：把正確的程式故意改壞一個地方，例如把 >= 改成 >、拿掉四捨五入，每一種改法做成一個「變異」版本；然後拿你的測試分別配上正確的程式和每一個變異版本去跑。

配上正確的程式要全部通過，證明測試沒有誤判；配上每一個變異版本都要至少一個測試失敗，證明測試守得住那條規則。只要有一個變異版本讓你的測試全部通過，就代表那個 bug 上線時你的測試不會發現。開場那次事故，就是「>= 改成 >」這個變異真的發生了，而當時沒有任何測試抓得到它。練習 1 的變異版本清單，就是結帳規則最容易被改壞的幾種方式。

判分本身就是 node --test；check.mjs 會把所有 *.test.ts 當成判分測試，所以你自己的測試檔取名 *.spec.ts，執行時寫出檔名。check.mjs 的細節整理在課末的「補充與查表」。

正式專案也有工具自動做這件事（例如 JavaScript 的 Stryker），通常只用在最重要的商業邏輯上，因為每個變異都要把測試整個跑一次，很花時間。

比變異測試常見得多的指標是覆蓋率（coverage）：跑測試時記錄哪些程式碼被執行過，算出測試執行到幾成的程式碼。覆蓋率能告訴你哪些程式從來沒被測試碰過，這很有用；但它的盲點是「有執行到」不等於「有檢查」。上一節的 assert.ok(price) 那種測試，fetchMenuPrice 的每一行都執行到了，覆蓋率一樣是 100%，可是它什麼都沒檢查。覆蓋率量的是測試「走過哪裡」，變異測試量的是測試「守得住什麼」。

💡 實務上：覆蓋率拿來找漏洞，不要拿來當 KPI
有些團隊在 CI 設覆蓋率門檻，未達標就擋下合併，結果大家開始寫只執行、不斷言的測試來湊數字。比較好的用法是打開覆蓋率報告，找「重要但完全沒被執行過」的程式路徑，例如咖啡店的退款、優惠碼過期這些很少走到的路徑，再替它們補測試。review 時看的是新規則有沒有對應的斷言，而不是百分比漲了多少。

測試守得住的，是你事先想得到的規則。開場的第二次事故不一樣：結帳程式不是算錯，而是被一筆沒人想到的資料弄得直接當掉。這時候你手上沒有測試可以看，只有終端機上那一大段錯誤訊息。

結帳直接當掉：錯誤訊息怎麼追到出事的那一行？

重現第二次事故。work/06/checkout.ts 讀進 POS 機匯出的 data/pos-order.json，算出合計。在 work/06 執行 node checkout.ts：

file:///…/work/06/checkout.ts:22

              ^

TypeError: Cannot read properties of undefined (reading 'price')
    at lineTotal (file:///…/work/06/checkout.ts:22:15)
    at file:///…/work/06/checkout.ts:26:44
    at Array.reduce (<anonymous>)
    at checkout (file:///…/work/06/checkout.ts:26:16)
    at file:///…/work/06/checkout.ts:32:21

Node.js v24.22.1

這段輸出的主體叫 stack trace。要看懂它，先回想TypeScript 課第 7 課的呼叫堆疊（call stack）：函式 A 呼叫函式 B，B 就疊在 A 上面；B 回傳了就拿掉，回到 A 繼續。錯誤被丟出的那一刻，Node 把當下的呼叫堆疊從最上面到最下面抄一份，存在錯誤物件裡，這份紀錄就是 stack trace。它回答的是：「出事的那一刻，程式是經過哪些函式、一層一層呼叫到這裡的。」

stack trace 的每一行 at … 叫一個 frame，代表堆疊裡的一層：哪個函式、在哪個檔案的第幾行第幾欄。最上面的 frame 是最後被呼叫、也就是錯誤發生的那一層；越往下越接近程式的起點。照這個結構，讀法是：

  1. 第一行是錯誤類型和訊息：TypeError，讀了 undefined 的 price。所以 item 是 undefined。
  2. 從上往下，第一個 frame 是錯誤發生的地方：lineTotal，checkout.ts 第 22 行。往下是誰呼叫它：reduce 的 callback（第 26 行）→ checkout → 檔案最下面的主程式（第 32 行）。
  3. 跳過不是你寫的 frame：Array.reduce (<anonymous>)、node:internal/…、node_modules/… 幾乎不會是兇手，它們只是把你的資料傳下去。
  4. 錯誤發生處不一定是 bug 所在：第 22 行只是「讀 price」，真正的問題是 findItem 為什麼回傳 undefined，也就是傳進來的資料有什麼不同。要往資料的來源追。

行號可以直接信任：Node 執行 .ts 時把型別換成等長的空白（第 5 課），所以 stack trace 的行號就是你檔案裡的行號，不用額外設定。

照第 4 點往資料的來源追。item 來自第 21 行的 findItem(line.name)，打開 findItem：

看一下 findItem：MENU.find(…)!。find 找不到時回傳 undefined，TypeScript 原本會警告「item 可能是 undefined」，有人加了 ! 叫它閉嘴，錯誤就延後到第 22 行才爆。用 ! 或 as 蓋掉型別錯誤之前，先想清楚「真的不可能嗎」。

所以真正的問題是：某個品名在菜單裡找不到。可是打開 data/pos-order.json，三個品名看起來都在菜單上。stack trace 告訴你在哪裡出事、經過哪些函式，卻不告訴你當時每個變數是什麼值。要看到值，得讓程式在出事前停下來。

看不出當時的值：怎麼讓程式停下來看變數？

除錯器（debugger）就是做這件事的工具：讓程式停在你指定的那一行，這時你可以看所有變數當下的值，再一步一步往下執行，看值怎麼變。你在瀏覽器用 DevTools 的 Sources 面板除錯前端，用的就是除錯器。Node 也有同樣的東西：它內建一個叫 inspector 的除錯介面，Chrome DevTools 和 VS Code 都能連上去，連上之後的操作跟除錯前端一樣。

要讓 inspector 打開，啟動程式時加旗標：

$ node --inspect-brk checkout.ts
Debugger listening on ws://127.0.0.1:9229/184e7203-…
For help, see: https://nodejs.org/learn/getting-started/debugging

--inspect 打開 inspector，程式照常執行；--inspect-brk 打開後停在第一行，等你連上再開始。checkout.ts 這種一跑就結束的短命程式要用 --inspect-brk，不然你還沒連上，它已經當掉結束了。接著從下面兩種方式擇一連上：

  • Chrome：網址列輸入 chrome://inspect，在 Remote Target 底下找到 checkout.ts，按 inspect，會開一個 DevTools 視窗。
  • VS Code：命令選擇區（Cmd+Shift+P）執行「Debug: JavaScript Debug Terminal」，在這個終端機裡直接 node checkout.ts，VS Code 會自動連上，停在你在編輯器左邊點出的紅點。

連上之後，在 checkout.ts 的 findItem 裡設一個中斷點（breakpoint）：在行號上點一下，程式執行到這一行之前會停下來。除錯器側邊有一個 Watch 面板，在裡面輸入運算式，每次停下來都會顯示它當下的值。在 Watch 加上 JSON.stringify(name)，然後讓程式繼續跑。第一次停下來是 "拿鐵"，正常；第二次會顯示 "可頌　"：品名後面多了一個全形空白（U+3000）。菜單上寫的是 可頌，兩個字串不相等，find 找不到，回傳 undefined，這就是整串錯誤的源頭。

為什麼用 JSON.stringify？因為 console.log(name) 在終端機印出來的全形空白跟什麼都沒有一樣，肉眼看不出差別；JSON.stringify 會加上引號，字串的邊界在哪裡一目了然。這也是除錯器比 console.log 好用的地方：不用改程式、不用重跑，停在那一刻就能用各種方式檢查同一個值。

除錯器的常用操作，Chrome DevTools 和 VS Code 都一樣（查表用，不用背）：

找到原因之後怎麼修，是練習 2：比對菜單之前把品名前後的空白去掉；真的不在菜單上的品項要丟出有名字的錯誤，而不是讓 TypeError 在別處爆開。修之前，照前面的做法，先讓一個測試用帶全形空白的品名重現這個錯誤，看到它紅，再修到它綠。

inspector 預設只聽 127.0.0.1:9229，只有這台電腦連得到。不要寫 --inspect=0.0.0.0：連上 inspector 的人可以在你的程序裡執行任意程式碼，等於把伺服器交出去（官方 CLI 文件的警告）。正式環境要除錯，請用 SSH 通道連到伺服器的 127.0.0.1。

這次的錯誤發生在你自己的電腦上，可以重跑、可以停下來看。但大部分的錯誤發生在伺服器上，你能拿到的只有當時記錄下來的錯誤訊息。

錯誤發生在伺服器上：被包過一層的錯誤怎麼讀？

伺服器上的程式多半在讀檔、查資料庫、呼叫別的服務，這些都是 async 的，錯誤的樣子會跟剛才不太一樣。有兩個差別要先知道。

第一個差別是 async 的 frame。await 之後的程式是在另一輪事件中才繼續執行，那時原本的呼叫堆疊早就清空了。不過 V8 會把 await 串起來的呼叫補回 stack trace，這些 frame 前面會標 async，你一樣能看出是誰一路 await 到這裡的。

第二個差別是錯誤常常被包過一層。讀檔失敗時，底層的錯誤只會說「檔案不存在」，不會說你當時在做什麼；所以程式常在 catch 裡丟出一個新的錯誤，說明「在做什麼事時失敗」，再用 cause 帶著原本的錯誤（TypeScript 課第 4 課）。Node 印出這種錯誤時，會把 cause 一起印成 [cause]。work/06/examples/cause.ts 的 loadMenu 就是這樣包的，執行 node examples/cause.ts：

Error: 讀不到菜單：data/menu-2026.json
    at loadMenu (file:///…/examples/cause.ts:8:11)
    at async openShop (file:///…/examples/cause.ts:13:16)
    at async file:///…/examples/cause.ts:17:1 {
  [cause]: Error: ENOENT: no such file or directory, open 'data/menu-2026.json'
      at async open (node:internal/fs/promises:1345:25)
      at async readFile (node:internal/fs/promises:2003:14)
      at async loadMenu (file:///…/examples/cause.ts:6:23)
      …
    errno: -2,
    code: 'ENOENT',
    syscall: 'open',
    path: 'data/menu-2026.json'
  }
}

這段要分兩層讀。外層告訴你「在做什麼事時失敗」：開店時讀菜單失敗，openShop 和檔案最下面那行前面都標了 async。[cause] 告訴你「底層真正的原因」：檔案不存在（ENOENT，第 10 課）。[cause] 的 frame 從 node:internal 開始，照上一節的讀法跳過它們，往下找第一個自己的檔案：cause.ts:6 的 readFile。如果程式只把 err.message 記下來，你只會看到「讀不到菜單：data/menu-2026.json」，stack 和 cause 這些資訊全都看不到。

伺服器上通常也沒有除錯器可以停下來看，所以 console.log 在這裡是正當的除錯方法：在看不到畫面的環境（CI、伺服器），有時它是唯一的方法。只是除錯用的 console.log 要記得刪掉，不然會混在程式的正常輸出裡（第 1 課的練習就會因此判錯）。長期需要的紀錄改用結構化 log（第 19 課）。遇到難重現、跨服務的 bug，要一套有系統的查法，系統設計課第 21 課會講。

把這一課串起來，處理一個 bug 的完整流程是：拿到完整的錯誤，照 stack trace 找到出事的地方，順著資料往來源追（需要時用除錯器看值），用一個會紅的測試重現它，修到測試變綠，測試留在專案裡守著。

💡 實務上：接到 bug 回報，先要完整的錯誤和當時的輸入
客服或 PM 說「結帳壞了」，資深工程師會先問：完整的 stack trace（包括 [cause]）、是哪一筆訂單或什麼輸入、從什麼時候開始、最近有沒有部署新版本。有了輸入就能在本機重現，接著先寫成會紅的測試再修。如果伺服器的紀錄只寫了 err.message，stack 和 cause 都不見了，只能用猜的，所以記錄錯誤時要把整個錯誤物件記下來。不要在錯誤訊息或回應裡直接把 stack trace 回給使用者，那會洩漏內部檔案路徑和程式結構。

練習

在 learn/ 執行 node check.mjs node 06 建立 work/06/。前兩題寫測試，自己跑測試的指令是在 work/06 執行 node --test 檔名.spec.ts。

練習 1：order-total.ts 的 calcOrderTotal(items, coupon?) 已經寫好了（不用改），規則寫在檔案開頭：小計是單價×數量；數量不是正整數時丟出 RangeError；優惠碼 LATTE10（不分大小寫）打九折；打折後的金額 ≥ 300 再折 30；最後四捨五入到整數。在 order-total.spec.ts 為它寫測試。

判分用變異測試：你的測試配上正確的程式要全部通過，而且至少 5 個測試；配上下面每一個改壞的版本，都要有測試失敗：門檻寫成 > 300、先判斷滿額再打折、沒有四捨五入、數量 0 沒丟錯、數量 1.5 沒丟錯、優惠碼分大小寫。測試檔只能 import node:test、node:assert/strict 和 import { calcOrderTotal } from './order-total.ts'，calcOrderTotal 只能直接呼叫：測試要靠呼叫結果來檢查，不能去讀程式的原始碼。提示：選菜單上的價格打九折都是整數，要測四捨五入得自己挑一個價格。

練習 2：執行 node checkout.ts 會得到上面那個 TypeError。照著 stack trace 找到真正的原因並修好 checkout.ts：比對菜單之前把品名前後的空白（包括全形空白）去掉；真的不在菜單上的品項，要丟出 errors.ts 的 UnknownItemError（throw new UnknownItemError(品名)，訊息會包含品名），而不是 TypeError。修好後 node checkout.ts 印出 合計 370。

測試會用隨機的品項、隨機的全形／半形空白和不在菜單上的品名呼叫 checkout()。不能用 try/catch 或 ?. 把錯誤吞掉回傳 0：結帳金額算錯比程式停下來更糟。也不要改到傳進來的資料（例如 line.name = line.name.trim()），呼叫的人可能還要用原本的品名。

練習 3：menu-price.ts 的 fetchMenuPrice(name) 有 bug：查不到的品項回傳 undefined，沒有丟錯。可是 node --test broken.spec.ts 兩個測試都顯示通過。找出這份測試為什麼抓不到 bug，改寫 broken.spec.ts（不要改 menu-price.ts），讓它在有 bug 的版本失敗、在正確的版本通過。一樣只能 import node:test、node:assert/strict 和 fetchMenuPrice，靠呼叫它來檢查。正確的版本：拿鐵回傳 110，查不到的品項丟出訊息含品名的錯誤。

判分會把你的測試配上三個版本：正確的版本要全部通過（至少 2 個測試）；「查不到不丟錯」和「價格多算一成」兩個有 bug 的版本都要有測試失敗。

練習 4：test('x', async () => { fetchPrice().then(p => assert.equal(p, 110)) })，fetchPrice() 在 20 毫秒後回傳 999。在 Node 24 用 node --test 執行會看到什麼？

✓ 測試函式沒有 await 也沒有 return 這個 Promise，所以它馬上結束、被判為通過；20 毫秒後斷言才丟錯。Node 24 會把這個錯誤記為 generated asynchronous activity after the test ended，讓整個檔案失敗，但不是記在測試 x 底下（所以不是 a）。這個補救只在斷言真的有執行時才有用；斷言根本沒執行到的寫法（例如只寫在 catch 裡）就會像 b 一樣靜靜通過。測試執行器不會等沒被 await 的 Promise，所以不會逾時。

練習 5：stack trace 第一個 frame 指向 checkout.ts:22 的 item.price。bug 一定在第 22 行嗎？

✓ 第一個 frame 是「出事的地方」：在這裡讀了 undefined 的屬性。但 item 為什麼是 undefined？要往前追：findItem 找不到，因為品名多了全形空白。最後一個 frame 只是程式的入口，通常也不是原因。從第一個 frame 開始，順著資料往來源追。

練習 6：同事說：「我的測試全部通過，覆蓋率 100%，所以測試很好。」為什麼練習 1 還要用改壞的版本來測你的測試？

✓ 沒有斷言、只寫 assert.ok(true)、沒 await 的測試，配上正確的程式都會全部通過，覆蓋率也可能是 100%，因為「執行到」不等於「檢查了」。把程式改壞後測試會失敗，才證明它守得住那條規則。b 弄反了目的；c 不對：node --test --experimental-test-coverage 就能算覆蓋率（v24 仍標為實驗功能），而且算得出來也只代表「執行到」。

常見錯誤

  • async 測試沒有 await：斷言在測試結束後才執行，甚至根本不執行。await 每一個 Promise，要求失敗就用 await assert.rejects(…)。
  • 斷言只寫在 catch 裡：程式沒丟錯時一個斷言都沒跑，測試照樣通過。改用 assert.throws／assert.rejects。
  • 只測 happy path：只測一切正常的情況，bug 都躲在邊界：剛好等於門檻、0、空陣列、錯誤的輸入。
  • 一個測試測很多件事：第一個斷言失敗後面就不跑，名稱也說不出是哪條規則壞了。一個測試一個行為。
  • 測試依賴執行順序或彼此的狀態：單獨跑或換順序就壞。每個測試自己準備資料，共用的資源用 hook 建立和清理。
  • 用 node --test tests/ 跑整個資料夾：資料夾不會被展開。不給參數讓 Node 用預設檔名找，或明確列出檔案。
  • 用 assert.ok 檢查數字：121 和 110 都是 truthy。知道預期值就用 assert.equal。
  • 在 node_modules 或 node:internal 的 frame 裡找 bug：先找第一個自己的檔案，再順著資料往來源追。
  • 除錯用的 console.log、debugger 忘了刪：會混進正常輸出、讓測試判錯。送出之前搜尋一次。
  • 用 ?.、! 或 try/catch 讓錯誤消失：錯誤沒有被解決，只是變成算錯的金額。找不到就丟出有名字、有內容的錯誤。

補充與查表

常用斷言（查表用，不用背）

全部從 node:assert/strict 引入。每一個都可以加最後一個參數，寫失敗時的說明。

斷言檢查什麼
assert.equal(實際, 預期)兩個值嚴格相等（跟 === 差不多，但 NaN 等於 NaN）
assert.deepEqual(實際, 預期)物件、陣列的內容一樣（逐層比對，型別也要一樣）
assert.throws(() => f(), RangeError)呼叫 f() 一定要丟出 RangeError
await assert.rejects(promise, /訊息/)Promise 一定要失敗，錯誤訊息符合正規表示式
assert.match(字串, /規則/)字串符合正規表示式
assert.ok(值)值是 truthy。最弱的檢查，121、'abc'、一個 Promise 都會過，能用 equal 就別用它

指令作用
node --test不給檔名：在目前資料夾往下找符合預設檔名的測試檔，例如 *.test.ts、*_test.ts、test/ 資料夾裡的檔案（會跳過 node_modules）
node --test a.spec.ts b.spec.ts只跑指定的檔案。*.spec.ts 不在預設檔名裡，要明確寫出來
node --test tests/不行：資料夾不會被展開，Node 把它當成一個檔案去載入，得到 MODULE_NOT_FOUND
node --test --test-name-pattern=拿鐵 …只跑名稱符合的測試
node --test --test-only …只跑標成 test.only(…) 的測試。少了 --test-only，test.only 不會生效，Node 只印一行提醒，其他測試照跑
node --test --watch …watch mode：檔案存檔就自動重跑，寫測試時開著很方便

describe／it 分組

測試多了可以用 describe 分組、it 寫單一測試（it 就是 test 的別名），讀起來像一句話：「結帳，滿 300 折 30」。

import { describe, it } from 'node:test'

describe('結帳', () => {
  it('剛好 300 元也折 30', () => { … })
  it('先打折再看有沒有滿 300', () => { … })
})

hook：測試前後的準備與清理

測試前後要準備或清理東西（建暫存資料夾、開伺服器、關資料庫連線）時用 hook：before／after 在整組測試前後各跑一次，beforeEach／afterEach 在每個測試前後各跑一次，afterEach 在測試失敗時也會跑。「測試之間互不依賴」要靠它做到：共用的資源在 hook 裡建立和清理。第 22 課會大量用到。

check.mjs 怎麼跑你的題目

在 learn/ 執行 node check.mjs node 06 時：

  1. 把 start/06/ 複製到 work/06/：你改過的檔案不會被蓋掉，但 exN.test.ts（每題一個隱藏的測試檔）每次都換成最新的。
  2. 在 work/06/ 執行 node --test，一次一個測試檔，每個測試檔在自己的程序裡跑，一題壞掉不會拖累別題。
  3. 同時用兩種 reporter（輸出格式）：一份印在終端機給你看，一份整理成 JSON 寫到 results/06.json，課程頁讀這個檔顯示每一題的結果。你的檔案載入就出錯（例如語法錯誤）時，頁面會顯示真正的錯誤訊息。

用除錯器跑測試

測試也能除錯：測試檔可以直接用 node --inspect-brk order-total.spec.ts 執行（直接執行測試檔也會跑裡面的測試）；用 node --inspect-brk --test 檔名 也可以，Node 會提醒它因此改成一次只跑一個測試檔。

小結

  • 手動試幾個例子擋不住只在邊界出錯的 bug。自動化測試把「試一試」寫成程式，每次改完都完整重跑；node:test 是 Node 內建的測試執行器，搭配 node:assert/strict，node --test 檔名 執行，失敗時結束碼是 1，CI 靠它擋下修改。
  • 好的測試在程式壞掉時會失敗：測邊界（剛好等於門檻、0、不合法的輸入）、一個測試一個行為、準備／執行／檢查三段、測試之間互不依賴、先看到它失敗。
  • async 測試要 await；要求失敗用 assert.throws／await assert.rejects，不要只在 catch 裡斷言，也不要用 assert.ok 檢查知道預期值的結果。
  • 變異測試用改壞的版本檢驗測試本身，比「全部通過」和覆蓋率更能說明測試有沒有用；覆蓋率量的是執行到哪裡，不是檢查了什麼。
  • 讀 stack trace：先看錯誤類型和訊息，第一個 frame 是出事的地方，找第一個自己的檔案，再順著資料往來源追；[cause] 是底層的原因，記錄錯誤要記整個錯誤物件。
  • node --inspect-brk 加上 chrome://inspect 或 VS Code 的 JavaScript Debug Terminal，可以下中斷點、逐步執行、看變數當下的值；inspector 只開在 127.0.0.1。
  • 修 bug 的流程：拿到完整錯誤和輸入 → 找到原因 → 寫一個會紅的測試重現 → 修到綠，測試留在專案裡。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：咖啡店後台收到「匯出整年營收報表」的請求，直接在處理請求的程式裡跑一個要算 8 秒的迴圈。這 8 秒內，其他客人查菜單的請求會怎樣？

✓ Node 擅長等 I/O：等資料庫的時候執行緒是空的，可以去處理別的請求；算東西的時候執行緒被佔住，所有請求一起等。吃 CPU 的工作要另外規劃（第 9 課）。a 錯在「非同步」指的是等 I/O 時不佔住執行緒，不是每個請求各有一條執行緒。（第 1 課）

練習 8：結帳模組這樣讀金流金鑰，而正式環境忘了設 PAYMENT_API_KEY。哪裡會出事？

export async function charge(amount: number) {
  const key = process.env.PAYMENT_API_KEY
  return callPaymentApi(key, amount)
}

✓ 沒設定的環境變數只是 undefined，用到它的那一刻才出事，可能是半夜、可能是客人在櫃台。改成啟動時由 loadConfig 集中驗證，有問題就立刻結束（fail fast），其他程式只用它回傳的物件。b 正是 fail fast 會帶來的結果，這段程式沒有做到。（第 2 課）

練習 9：夜間對帳腳本由排程每天凌晨執行，最外層這樣寫。某天 reconcile() 丟出錯誤，會怎樣？

try {
  await reconcile()
} catch (err) {
  console.log('對帳失敗', err)
}

✓ 排程和監控看結束碼判斷成敗。錯誤被接住、程式自然結束，結束碼就是 0。catch 裡要 console.error 並設 process.exitCode = 1。a 錯在只有沒被接住的例外才會讓結束碼變 1，接住之後要自己設。（第 2 課）

練習 10：專案的 .gitignore 排除了 package-lock.json，部署腳本執行 npm install。結果你電腦上正常，部署當天裝到別的版本，服務壞了。根本的修法是什麼？

✓ lockfile 記下整棵依賴樹的版本和 integrity；npm ci 照它裝，跟 package.json 不一致就直接失敗，每台機器裝到的都一樣。a 錯在只鎖得住你直接寫的套件，它們自己依賴的套件還是照各自的範圍裝到新版。（第 3 課）

練習 11：同事打錯字，npm install 了一個名字很像熱門套件的假套件，發現後馬上 npm uninstall，程式從來沒有 import 它。接下來該怎麼處理？

✓ install script 在 npm install 的當下就執行，不用等 import，要拿的東西可能已經傳走了。之後用 allowScripts 或 ignore-scripts 把「誰可以跑 script」留在專案設定，安裝前看清楚名稱。a 是最常見的誤解：import 才執行的只有套件的主程式。（第 3 課）

練習 12：db.ts 用這段程式提供整個程式共用的連線池，上線後資料庫的連線數比預期多很多。原因是什麼？

let pool: Pool | undefined
export async function getPool() {
  if (!pool) pool = await createPool()
  return pool
}

✓ await 等待的期間 pool 還是 undefined，這段時間進來的呼叫都會再建一份。改成快取 Promise，後來的人一起等同一個；失敗時清掉快取，資料庫恢復後才能重試。b 錯在模組只執行一次，所有檔案拿到的是同一個 pool。（第 4 課）

練習 13：咖啡店的 API 用 node src/main.ts 直接執行，tsconfig 開了 strict。怎樣才能確保型別錯誤不會合併上線？

✓ Node 用 type stripping 把型別換成空白就執行，不檢查型別，也不讀 tsconfig；strict 只對 tsc 和編輯器有效。typescript 裝成 devDependency，本機和 CI 用同一版。a 是最常見的誤會：程式跑得起來，不代表型別是對的。（第 5 課）

練習 14：同事改了 calcOrderTotal，數量 0 不再丟錯。這個測試會怎樣？

test('數量 0 要丟出 RangeError', () => {
  try {
    calcOrderTotal([{ name: '拿鐵', price: 110, qty: 0 }])
  } catch (err) {
    assert.ok(err instanceof RangeError)
  }
})

✓ 斷言只寫在 catch 裡，程式沒丟錯時測試什麼都沒檢查，照樣通過。改成 assert.throws(() => calcOrderTotal(…), RangeError)。好的測試要在程式壞掉時失敗，寫完先把程式改壞，確認它會紅。a 錯在 catch 根本沒有執行，裡面的斷言沒有機會失敗。（第 6 課）
