階段 1：Node 與開發環境 · 第 5 課

用 Node 跑 TypeScript

咖啡店的同事從舊專案複製了一個訂單模組過來，執行 node main.ts 卻馬上出錯；另一支營收報表跑得好好的，營收卻印成 01108070-12090免費90 元。兩個問題的根源一樣：Node 執行 TypeScript 的方式，跟你在 Vue 專案裡習慣的不一樣。

這一課的任務就是修好這兩支程式：訂單模組要能直接 node order-module/main.ts 執行、行為不變；營收報表要算出正確的營收；而且以後這類錯誤要在執行之前就被擋下，不是等到客人或會計發現。我們會照著訂單模組實際噴出來的錯誤一個一個修，每一節都在解決修理途中遇到的下一個問題。練習 1 到 3 就是把這三件事親手做一遍。

這課的路線：
  1. Node 拿到 .ts 做了什麼：它只擦掉型別、不檢查型別，所以型別錯了照樣跑，營收才會印成一長串字。
  2. 訂單模組的第一個錯誤：Node 為什麼找不到 ./order，import 路徑該寫 .ts 還是 .js。
  3. 補上副檔名又撞到 parameter properties 和 enum：哪些語法擦不掉，怎麼改成 Node 能跑的寫法。
  4. 最後一個錯誤與事前檢查：只用到型別的 import 為什麼要寫 import type，以及怎麼用 tsc 在執行前、在 CI 裡一次抓出這些錯。
  5. 什麼時候還是要建置：NestJS、發布套件這類情況，為什麼還需要 tsc 或 swc。
這課會用到：
  • TypeScript 課第 13 課：TypeScript 做兩件事，檢查型別、擦掉型別；執行前型別會全部拿掉，型別只在編輯器和 tsc 裡有作用。
  • TypeScript 課第 15 課的字面值聯合型別與 as const、第 20 課的 typeof／keyof：'ready' | 'done' 只允許這幾個字串；as const 讓物件的值保持字面值，再用 typeof X[keyof typeof X] 取出所有值的聯合。
  • TypeScript 課第 23 課的 parameter properties：constructor(private x: number) 一行同時宣告並指定欄位。

Node 拿到一個 .ts 檔時，做了什麼？

先回想你在 Vue 專案裡的經驗：你寫的 .ts 從來不是直接被執行的。Vite 先把它轉成 JavaScript，瀏覽器拿到的是轉好的結果；型別錯誤則是編輯器的紅線在提醒你。瀏覽器的 JavaScript 引擎只看得懂 JavaScript，Node 用的 V8 引擎也一樣。那 Node 24 怎麼能直接執行 node main.ts？

答案是 Node 在把程式交給 V8 之前，自己先做了一個很簡單的轉換，叫 type stripping（擦掉型別）：把型別註記換成空白，剩下的就是 JavaScript，再交給 V8 執行。

原始碼：  const price: number = 110
擦掉後：  const price         = 110     ← 型別換成等長的空白

這個轉換只看眼前這一個檔案，看到型別的語法就換成空白，不需要知道其他檔案的內容，也不讀任何設定檔。正因為它這麼單純，所以有三個直接的結果，這一課後面遇到的每個問題都能追回這三點：

  • 不檢查型別。檢查型別要知道每個變數、每個函式的型別，還要對照其他檔案，擦除器完全不做這件事。const price: number = '110' 照跑，price + 10 印出 11010。能跑不代表沒有型別錯誤。
  • 不讀 tsconfig.json。tsconfig 裡的 paths、target、strict 對 Node 都沒有作用，那些設定只給 tsc 和編輯器看。
  • 行號不會跑掉。程式出錯時，Node 會印出 stack trace：一串「經過哪個檔案、第幾行」的紀錄，讓你找到出錯的位置。如果轉換時把程式碼刪掉或搬動，執行的程式和你看到的原始檔行號就會對不上，得再靠一份叫 source map 的對照檔把行號翻回原始檔。type stripping 是把型別換成空白、不是刪掉，所以 stack trace 指到的行號就是你在編輯器看到的行號，不需要 source map。

在練習資料夾執行 node examples/strip.ts 親眼看。第一行確認 Node 用的是 strip（只擦除）模式；第二行是負責擦除的元件 amaro 的版本，版本細節見課末；第三行是 stack trace 的一行，指到的正是原始檔的第 9 行：

$ node examples/strip.ts
process.features.typescript = strip
型別擦除器 amaro 版本 = 1.1.11
at file:///…/work/05/examples/strip.ts:9:13      ← 就是原始檔的第 9 行

現在可以解釋營收報表了。report.ts 宣告了 type Sale = { name: string, price: number }，但 POS 匯出的 sales.json 裡，拿鐵的價格是字串 "110"。型別註記寫著 number，執行時卻沒有任何東西在確保它：Node 擦掉型別之後，total += sale.price 就是普通的 JavaScript +。0 + "110" 只要有一邊是字串就變成串接，得到 "0110"；從此 total 是字串，後面每一筆都接在尾巴，負數 -120、字串 "免費" 也一起接上去，最後印出 01108070-12090免費90。

所以 Node 能跑一支 .ts，只代表它擦得掉，不代表型別是對的。營收報表的問題要等到後面講型別檢查時才能根治；先處理一執行就倒下的訂單模組。

訂單模組一執行就倒：Node 為什麼找不到 ./order？

執行 node order-module/main.ts，第一個錯誤還輪不到 TypeScript 語法，而是找不到檔案：

$ node order-module/main.ts
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '…/order-module/order' imported from …/order-module/main.ts

main.ts 寫的是 import { Order } from './order'，沒有副檔名。在 Vue 專案裡你也一直這樣寫，那是因為 Vite 處理 import 時會自己試著補上 .ts、.js 這些副檔名。Node 不做這件事：第 4 課講過，ES module 的相對路徑要寫完整的檔名，Node 寫什麼就去找什麼。磁碟上沒有一個叫 order 的檔案，所以找不到。

這就是 import 的第一條規則：相對路徑寫磁碟上真的存在的檔名。聽起來很直接，但你在網路上的範例和 NestJS 專案裡，會看到很多 import … from './price.js'，明明資料夾裡只有 price.ts。兩種寫法都對，差別在專案是怎麼執行的：

專案怎麼執行import 寫法為什麼
直接 node main.ts（本課程的練習）'./price.ts'磁碟上只有 price.ts，寫 './price.js' 或 './price' 都是 ERR_MODULE_NOT_FOUND
先用 tsc 編譯成 .js 再執行（NestJS、要發布到 npm 的套件）'./price.js'執行的是 dist/price.js；tsc 檢查時會對到同名的 price.ts，輸出時路徑原封不動

第二列要多想一步。編譯型的專案裡，真正被 Node 執行的是 tsc 輸出到 dist/ 的 .js 檔，而 tsc 輸出時不會改動 import 路徑。原始碼寫 './price.js'，輸出的 dist/main.js 裡也是 './price.js'，執行時旁邊正好有 dist/price.js，所以找得到。換句話說，import 路徑要寫的是「執行的那一刻，磁碟上存在的檔名」。編譯型專案也有辦法改寫 .ts，見課末。

訂單模組是直接用 node 執行的，所以三個檔案的 import 都補上 .ts：'./order.ts'、'./status.ts'、'./types.ts'。順帶一提，前端專案常用的 @/ 別名也一樣找不到，因為它是 tsconfig 的 paths 設定，而 Node 不讀 tsconfig；替代做法見課末。

💡 實務上：寫 import 之前，先看專案怎麼啟動
加入一個新專案，先打開 package.json 的 scripts："start": "node dist/main.js" 代表先編譯，import 寫 .js；"start": "node src/main.ts" 代表直接執行，import 寫 .ts。寫錯邊就會在 tsc 報錯或執行時 ERR_MODULE_NOT_FOUND，從別的專案複製程式過來時最容易發生，這次的訂單模組就是例子。內部別名也一樣，從前端專案習慣帶來的 @/ 在 Node 不會生效，跟團隊約定用 # imports。這些規則不要靠 code review 用眼睛抓，交給後面 tsc 那一節的設定自動擋。

補上副檔名之後再執行，檔案都找到了，Node 卻在讀 order.ts 時拒絕執行，這次是 TypeScript 語法本身的問題。

補上副檔名，又撞到 parameter properties 和 enum：哪些語法擦不掉？

補完副檔名後的錯誤長這樣，^^^^ 指出 order.ts 第 7 行哪一段不能擦：

$ node order-module/main.ts
…/order-module/order.ts:7

  constructor(public readonly customer: string, private items: Item[]) {}
                              ^^^^^^^^^^^^^^^^

SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript parameter property is not supported in strip-only mode

上一節說擦除器看到型別就換成空白，那 public readonly 為什麼不能也換成空白？因為這段語法不只是型別。constructor(public readonly customer: string) 是 TypeScript 的簡寫，意思是「宣告一個 customer 欄位，並在建構子裡執行 this.customer = customer」。那行指定是 TypeScript 編譯時幫你產生的程式碼。如果只把 public readonly 換成空白，剩下 constructor(customer, items) {}，欄位永遠不會被指定，summary() 就會印出 undefined。擦掉會讓程式行為改變，所以 Node 選擇直接報錯，而不是默默跑出錯的結果。

enum 是同一類問題，而且更明顯。用 tsc 編譯一個 enum，看它變成什麼 JavaScript：

// TypeScript
export enum OrderStatus {
  Pending = 'pending',
  Ready = 'ready',
}

// tsc 輸出的 JavaScript
export var OrderStatus;
(function (OrderStatus) {
    OrderStatus["Pending"] = "pending";
    OrderStatus["Ready"] = "ready";
})(OrderStatus || (OrderStatus = {}));

enum 在執行時是一個真正的物件，main.ts 的 OrderStatus.Ready 讀的就是它。擦掉之後這個物件就不存在了，執行到 OrderStatus.Ready 只會出錯。就算 order.ts 的 parameter properties 修好了，status.ts 的 enum 一樣會被擋下（兩者怎麼改，下一節一起講）。直接執行 status.ts 看得最清楚：

$ node order-module/status.ts
file:///…/order-module/status.ts:2
export enum OrderStatus {
       ^^^^^^^^^^^^^^^^^^
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode

判斷的標準只有一個：拿掉之後，剩下的 JavaScript 行為完全不變。符合這個條件的語法叫可擦除語法（erasable syntax），Node 能直接執行；會產生執行時程式碼的語法，擦掉就少了東西，Node 只能拒絕。下表都在 Node v24.22.1 實測過，查表用，不用背，記住上面的判斷標準就能推回來：

語法Node 直接執行錯誤訊息
型別註記、interface、type、泛型、as、satisfies、!可以
private、protected、readonly、abstract 修飾子、overload、declare、只有型別的 namespace、using（離開區塊時自動釋放資源的宣告）可以
enum、const enum不行ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX：TypeScript enum is not supported in strip-only mode
parameter properties：constructor(private x: number)不行同上：TypeScript parameter property is not supported…
含程式碼的 namespace不行同上：TypeScript namespace declaration is not supported…
import x = require('…')不行同上
角括號斷言 <number>value不行同上，訊息會建議改用 as
裝飾器 @Controller()不行SyntaxError: Invalid or unexpected token

注意第二列：private、readonly 單獨寫在欄位上是可以的，因為那只是給 tsc 看的限制；寫在建構子參數上才不行，因為那裡它們代表「幫我產生指定欄位的程式碼」。知道哪些不能擦之後，下一步就是把它們換成拿掉型別後仍然是完整 JavaScript 的寫法。

怎麼把 enum 和 parameter properties 改成 Node 能跑的寫法？

每一種不行的語法都有可擦除的寫法，行為一樣。改寫的原則就是把原本「TypeScript 偷偷幫你產生」的程式碼自己寫出來。

enum → as const 物件＋同名的聯合型別。enum 同時扮演兩個角色：執行時是一個物件，檢查時是一個型別。改寫就是把這兩個角色拆開，物件負責執行時的值，型別負責檢查：

// 改寫前
export enum OrderStatus {
  Pending = 'pending',
  Ready = 'ready',
}

// 改寫後
export const OrderStatus = {
  Pending: 'pending',
  Ready: 'ready',
} as const
export type OrderStatus = typeof OrderStatus[keyof typeof OrderStatus]
//          ↑ 'pending' | 'ready'

值和型別可以同名，因為 TypeScript 把它們放在不同的命名空間：寫在型別位置（status: OrderStatus）的是型別，寫在值的位置（OrderStatus.Ready）的是物件。所以用的地方完全不用改，訂單模組裡 main.ts 的 OrderStatus.Ready、status.ts 裡的 Record<OrderStatus, …> 都照舊。型別那一行從裡往外讀：typeof OrderStatus 拿到物件的型別，keyof 拿到所有鍵，再用鍵去取值的型別，就得到所有值的聯合（TypeScript 課第 20 課）。少了 as const，值的型別會被放寬成 string，聯合型別就失去意義，任何字串都能當成訂單狀態。

parameter properties → 先宣告欄位，再在建構子指定。就是把上一節說的「TypeScript 幫你產生的那行指定」親手寫出來：

// 改寫前
class Order {
  constructor(public readonly customer: string, private items: Item[]) {}
}

// 改寫後
class Order {
  readonly customer: string
  private items: Item[]
  constructor(customer: string, items: Item[]) {
    this.customer = customer
    this.items = items
  }
}

改寫後，readonly、private 寫在欄位宣告上，是可擦除的；this.customer = customer 是普通的 JavaScript，擦除後原封不動。

其他：含程式碼的 namespace 改成一個獨立的模組檔案；<number>value 改成 value as number；import x = require() 改成 import。

新專案這樣寫沒有損失：as const 物件是普通的 JavaScript，可以 Object.values() 列出全部狀態，也能直接當 JSON 傳給前端；字串聯合比數字 enum 更好讀、更好除錯。

💡 實務上：改寫舊程式是一次獨立的變更，不要順手混進功能裡
接手舊專案、想改成直接用 node 執行時，最常見的就是像這次的訂單模組一樣，一路撞到 enum 和 parameter properties。資深的做法是開一個只做改寫的 PR：在 tsconfig 開 erasableSyntaxOnly（後面 tsc 那一節會講）讓 tsc 列出所有要改的地方，一個一個改，跑過測試確認行為沒變，review 的人才看得清楚。如果專案本來就用 tsc 建置（例如 NestJS），enum 能正常運作，沒有理由為了「新寫法」去大改。新寫的程式則一開始就用 as const 物件，之後不管怎麼執行都不用再改。

兩處都改完再執行一次，訂單模組還剩最後一個錯誤，而且這次跟語法無關。

最後一個錯誤：明明有 export，為什麼說找不到 Item？

語法都改好之後，執行到的是這個錯誤：

$ node order-module/main.ts
SyntaxError: The requested module './types.ts' does not provide an export named 'Item'

types.ts 明明寫了 export interface Item，為什麼說沒有？回到第一節的那句話：擦除器只看眼前這一個檔案。

先看 types.ts 自己。它裡面只有一個 interface，擦掉型別之後整個檔案是空的，執行時它什麼都沒有匯出。再看 order.ts 的 import { Item } from './types.ts'。擦除器處理 order.ts 時不會去打開 types.ts，它不知道 Item 是 interface（擦掉就沒了）還是 class（執行時真的存在），只好保留這行 import。結果執行時 Node 真的去 types.ts 要一個叫 Item 的東西，當然拿不到。

所以 import 的第二條規則是：只用到型別的 import 要標 type。標了 type，等於你親口告訴擦除器「這是型別，可以擦」，它不用看別的檔案也能做對：

import type { Item } from './types.ts'                 // 整行擦掉
import { Order, type OrderInput } from './order.ts'   // 只擦掉 OrderInput

import { Item } from './types.ts'   // 沒標 type：執行時真的去要 Item，但它已經被擦掉了
// SyntaxError: The requested module './types.ts' does not provide an export named 'Item'

把 order.ts 改成 import type { Item }，訂單模組終於跑起來：

$ node order-module/main.ts
王小明：290 元（pending）
王小明：290 元（ready）
請到櫃台取餐

回頭看這段修理過程：四個錯誤，每一個都要真的執行才會出現，而且一次只出現一個，修好一個才看得到下一個。營收報表更糟，它根本不報錯，只會默默算錯。我們需要一個在執行之前、一次把所有問題列出來的工具。

怎麼在執行前一次抓出這些錯？把型別檢查交給 tsc

先把兩個常被混在一起的詞分開。轉譯（transpile）是把 TypeScript 轉成 JavaScript，讓程式能執行；型別檢查（type check）是讀遍所有檔案，確認每個值的用法都符合它的型別。兩件事互相獨立：Node 只做了最簡單的轉譯，也就是擦掉；型別檢查要另外跑 TypeScript 的編譯器 tsc。在 Vue 專案裡也是這樣分工，Vite 只負責轉譯，型別錯誤靠編輯器和另外的檢查指令。

tsc 照 tsconfig.json 的設定檢查（TypeScript 課第 25 課）。Node 不讀這個檔，但 tsc 讀，所以前面每一個「Node 執行時才會炸」的問題，都可以在 tsconfig 裡找一個選項，讓 tsc 提前抓到。練習資料夾的 tsconfig.json 就是給 Node 直接執行的專案用的設定，一行一行看：

{
  "compilerOptions": {
    "target": "esnext",                   // 不降版本：Node 24 認得最新語法
    "module": "nodenext",                 // 照 Node 的規則檢查 import（要副檔名、看 package.json 的 type）
    "noEmit": true,                       // 只檢查、不輸出 .js：執行交給 node
    "allowImportingTsExtensions": true,   // 允許 import 路徑寫 .ts（要搭配 noEmit）
    "erasableSyntaxOnly": true,           // enum、parameter properties 這類不能擦的語法直接報錯
    "verbatimModuleSyntax": true,         // 只引入型別卻沒寫 import type 就報錯
    "strict": true,                       // 嚴格模式：隱含 any、可能是 undefined 都報錯
    "types": ["node"],                    // 載入 @types/node：process、Buffer 才有型別
    "skipLibCheck": true                  // 不檢查 node_modules 裡的 .d.ts，比較快
  },
  "include": ["helpers", "work"]
}

對照訂單模組的修理過程：

  • 找不到 ./order：module: nodenext 讓 tsc 照 Node 的規則檢查 import，漏寫副檔名就報錯；allowImportingTsExtensions 允許你寫 .ts。它要搭配 noEmit：如果 tsc 要輸出 .js，路徑裡的 .ts 會原封不動留在輸出檔裡，執行時就找不到檔案。
  • parameter properties 和 enum：erasableSyntaxOnly 讓 tsc 把不能擦除的語法當成錯誤。
  • 找不到 Item：verbatimModuleSyntax 要求只用到型別的 import 一定寫 import type。

tsc 一次列出所有它找得到的錯，不用執行程式，也不必修好一個才看到下一個。唯一的例外是 import type 那個錯誤：路徑沒補副檔名時，tsc 找不到 types.ts，也就不知道 Item 是型別，要等路徑修好再跑一次才會報出來。Node 官方文件建議 TypeScript 5.8 以上，因為 erasableSyntaxOnly 從 5.8 才有；本課程用 TypeScript 7.0.2。types 和 strict 為什麼要明寫，跟 TypeScript 6.0 改了預設值有關，見課末的版本備註。

怎麼跑：

$ cd learn/node/practice

tsc 的錯誤訊息都帶一個錯誤碼。下面是這一課會遇到的（本機用 tsc 7.0.2 驗證），查表用，不用背，看到錯誤碼時回來對照它是哪個選項在擋：

那營收報表呢？對 report.ts 跑 tsc，它會抓到一個一直沒人發現的型別錯誤（是哪一個，練習 3 跑 tsc 時自己看），但抓不到「價格是字串」這件事。原因在 JSON.parse：它的回傳型別是 any，意思是「不檢查，你說它是什麼就是什麼」。const sales: Sale[] = JSON.parse(…) 這一行，等於程式設計師單方面宣稱檔案裡每一筆的價格都是數字，tsc 沒有辦法驗證一個執行時才讀進來的檔案。用 as number 也一樣，斷言只影響型別檢查，執行時 "110" 還是字串。

所以型別檢查有一條邊界：它能保證你的程式碼之間互相一致，但保證不了外面進來的資料。POS 匯出檔、HTTP 請求、資料庫回傳的東西，都要先當成 unknown，在執行時逐筆驗證、轉換之後，才能放心當成 Sale（TypeScript 課第 17 課）。練習 3 就是把營收報表改成這樣。

最後，tsc 要怎麼確保團隊裡每個人都有跑？tsc 發現錯誤時，結束碼（exit code）是非 0，代表「失敗」。團隊通常會設定一條自動流程：每次有人推程式碼或開 PR，伺服器就自動跑一遍檢查和測試，有任何一步結束碼非 0，這次變更就不能合併。這條流程叫 CI（continuous integration，持續整合）。把 tsc 放進 CI，型別錯誤就進不了主分支。開發時的節奏則是：node --watch（第 3 課）快速看結果，送出前跑一次 tsc。編輯器的紅線和 tsc 偶爾會不一致，判分和 CI 都以 tsc 為準，原因見課末。

💡 實務上：型別檢查要放進 CI，紅線不算數
團隊專案通常在 package.json 放一個 "typecheck": "tsc -p ."，CI 每次 PR 都跑，沒過就不能合併；只靠每個人自己看編輯器的紅線，一定有人漏掉。typescript 要裝在專案的 devDependencies 並由 lockfile 鎖住版本，本機和 CI 才會用同一版、結果一致。看到 CI 因為型別錯誤失敗，不要用 as any 或 // @ts-ignore 讓它變綠：那等於把錯誤藏起來、等到正式環境才出事，像練習 3 的營收就會默默算錯。

到這裡，訂單模組和營收報表都能直接用 node 執行、用 tsc 檢查。但整套做法有個前提：程式只用可擦除語法。如果專案非用 enum 或裝飾器不可呢？

如果非用 enum 或裝飾器不可：什麼時候還是要建置？

直接用 node 跑 .ts 零設定、啟動快，代價是只能用可擦除語法。另一條路是建置（build）：執行之前，先用一個真正的轉譯器把所有 .ts 轉成 .js，放到 dist/ 這類資料夾，執行的是轉好的 .js。真正的轉譯器會像前面看到的 tsc 輸出那樣，替 enum、parameter properties 產生執行時的程式碼，所以什麼語法都能用。三種做法的比較：

做法能用的語法適合代價
node app.ts可擦除語法新的後端服務、腳本、這門課不能用 enum、裝飾器
tsx（第三方 TypeScript 執行器）全部舊專案有 enum，想直接執行多一個依賴，一樣不檢查型別
tsc 或 swc 建置成 .js全部NestJS（裝飾器、emitDecoratorMetadata）；發布到 npm 的套件；要支援舊版執行環境多一個建置步驟，執行的是 dist/

tsx 能跑全部語法，是因為它的做法跟 Node 不同：Node 只是把型別擦掉，tsx 則在載入每個 .ts 時用 esbuild 完整轉譯一次，enum、parameter properties 都會像 tsc 輸出那樣產生執行時的程式碼。用法是把 node 換成它：npx tsx main.ts。它一樣不做型別檢查，所以 tsc 和 CI 照樣需要。

發布到 npm 的套件一定要建置：Node 不處理 node_modules 裡的 .ts 檔，所以套件要附上編譯好的 .js。

swc 是用 Rust 寫的轉譯器，只轉譯不檢查型別，比 tsc 快很多，NestJS 可以用它取代 tsc 產生 .js。不論用哪一種，型別檢查都還是 tsc 的工作，上一節的 CI 設定照樣需要。

NestJS 是最典型、一定要建置的例子。它不能直接 node main.ts，原因有兩層。第一層，它的 @Controller()、@Injectable() 是裝飾器，從上面的表可以看到，Node 遇到裝飾器直接 SyntaxError。第二層更根本：依賴注入要靠 emitDecoratorMetadata 在編譯時把建構子參數的型別寫進產生的程式碼裡（TypeScript 課第 24 課），而 type stripping 的工作恰好是把型別擦掉，擦掉之後就沒有這份資訊了。NestJS 課第 1 課會看到它的建置流程。

回到這一課的任務：訂單模組和營收報表改寫之後都只用可擦除語法，直接 node 執行、用 tsc 檢查就夠了。判斷的順序也是這樣：能用可擦除語法就直接執行；用了框架需要的裝飾器、或要發布套件，就建置；Node 有個能轉換 enum 的實驗旗標，但不要依賴它，見課末的版本備註。

練習

在 learn/ 執行 node check.mjs node 05 建立 work/05/。三題都會用 tsc 7.0.2 檢查，設定跟練習資料夾的 tsconfig 一樣嚴格。

練習 1：order-module/ 是從舊專案搬來的訂單模組，用了 enum OrderStatus、parameter properties、沒寫副檔名的 import，還沒用 import type 引入 interface。把它改寫成能直接 node order-module/main.ts 執行、行為不變的版本：OrderStatus 改成 as const 物件＋同名聯合型別（鍵和值不變），Order 的建構子改成明確宣告欄位。測試會換一位顧客和一張訂單操作 Order，並確認 OrderStatus 的型別正好是 'pending' | 'brewing' | 'ready' | 'picked_up'。先自己執行 node order-module/main.ts，照錯誤訊息一個一個修。

練習 2：tsconfig-task/tsconfig.json 只寫了一半。把它補完，讓 npx tsc -p tsconfig-task（在 work/05 執行）對 src/ 裡正確的程式 0 錯誤，而且能抓出這些錯：enum 與 parameter properties（TS1294）、只引入型別卻沒寫 import type（TS1484）、參數隱含 any（TS7006）、可能是 undefined（TS2532）、import 漏副檔名（TS2835）。測試會把你的 tsconfig.json 複製到幾個暫存資料夾，各放一個壞檔案進 src/ 檢查錯誤碼，所以 "include": ["src"] 要保留。一次只加一個選項，每加一個就重跑一次 tsc，看哪個錯誤消失、記下它在擋什麼；注意 strict 底下的個別檢查（例如 strictNullChecks）也不能關掉。

練習 3：report/report.ts 跑得起來，營收卻是錯的：POS 匯出的 sales.json 有些價格是字串（"110"），被 += 串接成字串了；還有一個型別錯誤沒人發現。先跑 npx tsc --noEmit --types node --module nodenext report/report.ts --ignoreConfig 看 tsc 怎麼說，再修正：

  • 讀進來的資料當成 unknown（TypeScript 課第 17 課），逐筆驗證：要有非空字串的 name；price 的型別必須是數字或字串（true 這類其他型別一律不合格，因為 Number(true) 是 1），用 Number() 轉成數字後要大於 0。
  • 不合格的那一筆用 console.error 印 略過第 N 筆：原因（N 從 1 開始，原因自己寫）並跳過，程式不能當掉、結束碼是 0。
  • stdout 只印一行 有效 4 筆，營收 350 元（筆數和營收只算合格的資料）。

用 as number 讓 tsc 閉嘴沒有用：斷言只影響型別檢查，執行時它還是字串。

練習 4：types.ts 裡 Order 是 interface。main.ts 寫 import { Order } from './types.ts'，只拿來標註型別，執行 node main.ts 會怎樣？

✓ 擦除器一次只看一個檔案，不知道 Order 是型別，所以保留這個 import；而 types.ts 擦完之後沒有任何匯出，執行時就找不到 Order。要寫 import type { Order }。TS1484 是 tsc 開了 verbatimModuleSyntax 才會報的，Node 不做型別檢查；檔案本身找得到，所以不是 ERR_MODULE_NOT_FOUND。

練習 5：為什麼 NestJS 專案不能直接 node src/main.ts？

✓ 裝飾器不是可擦除語法，Node 直接 SyntaxError；就算有轉換，emitDecoratorMetadata 也要編譯器讀型別、產生程式碼，所以要用 tsc 或 swc 建置。檔案數量無關。改成 .ts 解決不了裝飾器，而且 .js 在先編譯再執行的專案裡本來就是對的寫法。

練習 6：import { lineTotal } from './price.js'，在本課程的練習裡和在 NestJS 專案裡，哪邊能跑？

✓ NestJS 先用 tsc 編譯成 dist/*.js 再執行，執行時磁碟上真的有 price.js；tsc 檢查時會自己對到 price.ts。本課程直接執行 .ts，磁碟上沒有 price.js，Node 也不會幫你換副檔名，所以是 ERR_MODULE_NOT_FOUND，要寫 ./price.ts。.js 寫法不是舊的，是給編譯型專案用的。

常見錯誤

  • 以為能跑就沒有型別錯誤：Node 只擦掉型別。送出前跑 tsc，最好放進 CI。
  • 以為 Node 會讀 tsconfig：paths、strict、target 對 Node 都沒用。內部別名用 package.json 的 "imports"。
  • import 副檔名寫錯邊：直接用 node 執行的專案寫 .ts；先用 tsc 編譯的專案（NestJS）寫 .js。先看專案怎麼執行。
  • 只引入型別卻沒寫 type：執行時 SyntaxError。開 verbatimModuleSyntax 讓 tsc 先抓到。
  • 新程式繼續寫 enum 和 parameter properties：Node 不能執行。用 as const 物件＋聯合型別、明確宣告欄位，並開 erasableSyntaxOnly。
  • 用 as 處理外部資料：斷言不會轉換也不會檢查，JSON 裡的字串還是字串。外部資料先當 unknown，驗證再轉換。
  • VS Code 和 tsc 結果不一樣：編輯器用的 TypeScript 版本跟專案不同。以 tsc 為準，並讓編輯器改用專案的版本。
  • 依賴 --experimental-transform-types：Node 26 已經移除。要完整語法就用 tsx 或建置。

小結

  • Node 24 用 type stripping 執行 .ts：型別換成空白，不檢查型別、不讀 tsconfig，行號不變。營收報表的字串串接就是型別沒人檢查的結果。
  • import 路徑寫執行當下磁碟上存在的檔名：直接執行的專案寫 .ts，編譯成 .js 的專案寫 .js。
  • 只有可擦除語法能直接跑，判斷標準是拿掉後行為不變。enum 改成 as const 物件＋同名聯合型別，parameter properties 改成明確宣告欄位，角括號斷言改 as。
  • 擦除器一次只看一個檔案，只用到型別的 import 要寫 import type。
  • 型別檢查交給 tsc 並放進 CI：noEmit、allowImportingTsExtensions、erasableSyntaxOnly、verbatimModuleSyntax、strict、types: ["node"]。外部資料 tsc 保證不了，要當 unknown 在執行時驗證。
  • 裝飾器（NestJS）、發布套件、舊專案的 enum 還是需要 tsc、swc 或 tsx。

下一課學寫測試和除錯：用 node:test 把「程式該做什麼」寫成可以一直重跑的檢查，出錯時用 stack trace 和除錯器找到原因。

補充與查表

主線用不到、但工作上會查的細節集中在這裡。

版本備註：type stripping

type stripping 在 v22.6.0 加入、v23.6.0 起預設開啟、v24.3.0 起不再印實驗警告、v24.12.0 起是穩定功能（Stability 2）。用比較舊的 Node 24 會看到 ExperimentalWarning。本課的輸出來自 v24.22.1，它用的擦除器是 amaro 1.1.11。

.ts 檔是 ESM 還是 CommonJS，哪些檔案 Node 不處理

檔案是 ESM 還是 CommonJS，規則跟第 4 課的 .js 一樣：.ts 看最近的 package.json 的 "type"，.mts 一律 ESM，.cts 一律 CommonJS。.tsx 不支援；node_modules 裡的 .ts 檔 Node 也不處理，所以發布到 npm 的套件還是要附上編譯好的 .js。

編譯型專案也想在 import 寫 .ts

編譯的專案也可以寫 .ts，再開 tsconfig 的 rewriteRelativeImportExtensions，讓 tsc 輸出時改成 .js。

內部別名：tsconfig 的 paths 在 Node 不生效

tsconfig 的 paths（例如 "@/*"）Node 不認得，import '@/lib/price.ts' 會找不到模組。要內部別名，用第 4 課的 package.json "imports"（#lib/*），Node 和 tsc 都看得懂。

版本備註：TypeScript 6.0 起的預設值

TypeScript 6.0 改了幾個預設值，7 也一樣：types 預設變成 []，不寫 "types": ["node"] 時，沒有 import 任何 node: 模組的檔案用到 process 會報 TS2591；strict 預設變成 true。網路上舊教學的 tsconfig 不一定適用，兩個都明寫最清楚。

編輯器紅線和 tsc 結果不一致

VS Code 的紅線也是 TypeScript 在檢查，但編輯器用的 TypeScript 版本可能跟專案 node_modules 裡的不同（例如 6.0 改了預設值，舊版本就不知道），紅線和 tsc 的結果會不一致。判分和 CI 都以 tsc 為準；看到不一致時，先確認編輯器用的是哪個版本。

版本備註：--experimental-transform-types

Node 24 還有一個旗標 --experimental-transform-types，能轉換 enum 這類語法，但它一直是實驗功能（執行時會印 ExperimentalWarning），而且 Node 26.0.0 已經移除。不要讓專案依賴它，升級時會直接壞掉。
