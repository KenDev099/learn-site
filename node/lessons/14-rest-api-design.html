階段 4：HTTP 服務 · 第 14 課

REST API 設計

上一課的伺服器能動了：能依方法和路徑分派路由、讀完 body 再驗證、出錯時統一回 500。現在前端同事要用它寫咖啡店 App 的點餐畫面，開工前他先丟來四個問題：

  1. 王小明按下「送出訂單」，成功時 API 回什麼？App 要怎麼拿到剛建好的那張訂單？
  2. 失敗時回什麼？欄位填錯、訂單不存在、伺服器壞了，App 怎麼分辨？每支 API 的錯誤長得一樣嗎？
  3. 「我的訂單」往下捲到一半，店裡進來新訂單，下一頁會不會重複或漏掉？
  4. 捷運上網路斷掉，App 逾時後重送，會不會變成兩杯拿鐵？

這些問題設計時沒想好，前端就得替每支 API 寫特例，上線後還要處理重複扣款的客訴。這一課的任務是：替咖啡店的訂單 API 做一份設計，讓前端照著寫一次就好。我們從網址開始，一節回答一個問題，最後再看這份設計上線之後要怎麼改才不會弄壞舊版 App。練習裡你會把它做成真的伺服器。

這課的路線：
  1. 前端要打哪些網址：從需求裡的名詞找出資源，「取消訂單」這種動作要放在哪裡。
  2. 打了之後回什麼：建立成功回什麼、該回 4xx 還是 5xx；這節結尾先給開場四個問題的最小答案。
  3. 錯誤的 body 長什麼樣：為什麼每支 API 的錯誤要長一樣，前端才不用寫特例；problem details 怎麼寫。
  4. 訂單列表怎麼翻頁：offset 分頁為什麼會重複或漏掉，cursor 分頁怎麼解決。
  5. 會改變訂單的請求：已取餐的訂單被取消時回什麼；手機逾時重送，怎麼保證不會變成兩杯拿鐵。
  6. 上線之後怎麼改：哪些修改會弄壞還在用舊版 App 的人。
這課會用到：
  • 第 12 課的方法語意與狀態碼：GET 是安全的、PUT／DELETE 是冪等的，POST 兩者都不是；4xx 是客戶端的錯、5xx 是伺服器的錯。
  • 第 13 課的 node:http 伺服器：自己依方法和路徑分派路由、讀完 body 再驗證，處理函式丟錯時統一回 500。

前端要打哪些網址？從需求找出資源

前端同事要做的第一件事，是知道每個畫面要打哪個網址、用哪個方法。網址其實可以隨便取：/doOrder、/api?action=create 都能動。問題是每個人取法不同，前端每接一支新 API 就得讀一次文件、猜一次「查詢是 /getOrder 還是 /order/get」。團隊需要一套大家都懂的取法，業界最常用的是 REST。

REST 是一種 API 風格。它的想法是：系統裡的東西都看成資源（resource），也就是可以被讀取、建立、修改、刪除的「一樣東西」，例如一張訂單、一項商品。每個資源有自己的網址，要對它做什麼，由 HTTP 方法（GET、POST、PATCH、DELETE…）表達。REST 不是一份規格，沒有誰會檢查你「符不符合 REST」。大家照這個風格寫，是因為前端、快取、監控工具都已經懂 HTTP 的方法和狀態碼：GET 不會改資料所以可以快取、DELETE 是刪除，這些不用另外解釋。照著用，前端看到網址和方法就猜得到它做什麼。

資源從哪裡來？把需求裡的名詞挑出來。咖啡店的需求是「顧客可以點飲料、查自己的訂單、店員把訂單改成製作中」，裡面的名詞是顧客、飲料（商品）、訂單。每個名詞會變成兩種網址：

  • 集合（collection）：一群同類的資源，例如所有訂單 /orders。對集合 GET 是取得列表，POST 是新增一筆。
  • 單一資源：集合裡的一筆，例如 42 號訂單 /orders/42。GET 讀、PATCH 改一部分、PUT 整筆換掉、DELETE 刪除。

把咖啡店的需求一條條對上去：

需求方法與網址
看菜單GET /products
點一杯POST /orders
看某張訂單GET /orders/42
看某位顧客的訂單GET /customers/7/orders（從屬關係放進路徑）或 GET /orders?customerId=7（篩選）
店員改成製作中PATCH /orders/42，body { "status": "brewing" }

表裡的網址都遵守同一組慣例：用名詞、複數、小寫，單字之間用 - 連接。動作交給方法表達，所以不要寫 /createOrder、/getOrderById。原因是方法已經說了要做什麼，網址再寫一次動詞是重複；而且照動詞取名，同一張訂單會散在 /createOrder、/getOrderById、/deleteOrder 三個網址，前端要記三個名字。改成 /orders 和 /orders/42，同一個東西永遠是同一個網址，換的只有方法。巢狀路徑最多一兩層：/customers/7/orders/42/items/3 這種深度，通常表示 /order-items/3 更直接，因為那一項本身就有唯一的編號，不需要靠上面三層才找得到。

不是每個動作都是「改一個欄位」。王小明點錯了想取消訂單，這個動作有兩種表示法：

  • PATCH /orders/42，body { "status": "cancelled" }：把取消看成「把狀態改成 cancelled」，和店員改成製作中走同一個入口，前端很好寫。
  • POST /orders/42/cancel：把動作當成訂單底下的子資源。當取消要附帶退款原因、會觸發退款流程、需要的權限和其他修改不同時，這種寫法比較清楚，也比較好在 log 和權限設定裡單獨處理。

兩種都常見，重點是選一種並在整個 API 保持一致。這課用 PATCH。

到這裡，前端知道每個畫面要打哪個網址、用哪個方法了。下一個問題是打了之後會收到什麼：成功時 App 怎麼確定成功，失敗時怎麼知道是哪一種失敗？

打了之後回什麼？用狀態碼告訴前端發生了什麼事

前端拿到回應，第一個看的是狀態碼，也就是回應第一行的那三位數（第 12 課看過它的分類）。它在讀 body 之前就決定了 App 要走哪條路：fetch 的 res.ok 只有在 200–299 時是 true，前端通常就用它分出「成功」和「失敗」兩條路，再看失敗的是哪一種。所以設計 API 時，替每種情況選對狀態碼，就是在告訴前端「該怎麼處理」。

先看成功。訂單 API 的成功有三種：

  • 讀取成功回 200：GET /orders/42 的 body 就是那張訂單。
  • 建立成功回 201 Created：POST /orders 建好訂單後，加一個 Location: /orders/43 標頭指出新訂單的網址，body 放新訂單本身。這回答了開場第一個問題：App 拿到 201 就知道訂單成立了，body 裡已經有訂單，不用再查一次；之後要重新整理訂單頁，直接 GET Location 的網址就好。只回 200 又不給網址，App 就得自己想辦法找出剛建的是哪一張。
  • 刪除成功回 204 No Content：沒有 body，前端只要知道「刪好了」。

再看失敗。第一個要分清楚的是 4xx 還是 5xx，判斷方法只有一句：客戶端改一下請求就能成功是 4xx；客戶端怎麼改都沒用是 5xx。王小明的訂單數量填 0，改成 1 就能成功，是 4xx；資料庫連不上，他怎麼改都沒用，是 5xx。

4xx 裡面還要再分，因為前端對每一種的處理不同：

  • 請求本身就不對，回 400：欄位缺了、格式錯了、數量不在範圍內。不管什麼時候送都不會成功。
  • 要的東西不存在，回 404：GET /orders/999，沒有 999 號訂單。
  • 請求沒錯，但時機不對，回 409：取消一張已經取餐的訂單。同一個請求對還沒開始做的訂單就會成功，錯在它和訂單目前的狀態衝突。

前端會依這些狀態碼決定怎麼做：400 把欄位錯誤標在表單上，404 顯示「找不到這張訂單」，409 重新讀取訂單顯示最新狀態，5xx 顯示「稍後再試」。如果後端全部回 400 或全部回 500，前端就只能猜，或者去解析錯誤訊息的文字，後端改一個字前端就壞。

現在可以先給開場四個問題最小版本的答案：建立成功回 201 加 Location；每支 API 的錯誤都用同一種格式；列表記住「上一頁最後一筆是誰」，從那裡往下接，翻到一半有新訂單也不會重複（後面叫 cursor 分頁）；重送時帶上同一個識別碼，伺服器認得是同一次下單，只建一張（後面叫冪等鍵）。第一題剛剛已經回答；接下來三節分別回答第二、三、四題，中間會先處理改狀態時的 409，最後一節談上線後怎麼改。

先從第二個問題的後半開始。狀態碼只告訴前端是哪一類失敗。王小明的表單回 400 時，前端還要知道是哪個欄位錯、旁邊要顯示什麼字，這些資訊在 body 裡。body 要長什麼樣，就是下一節的問題。

錯誤的 body 長什麼樣？每支 API 都用 problem details

第 13 課的錯誤 body 是自己定的 { error: { code, message } }。自己定格式有兩個問題。第一，每個團隊都不一樣，前端換一個後端就要重寫錯誤處理。第二，就算在同一個團隊，也常常每支 API 各寫各的：一支回 { error }、一支回 { message }、一支把欄位錯誤放在 details。前端每接一支就要加一個特例，這正是開場同事擔心的事。

解法是用一個大家都認得的標準格式。網路上的通訊協定和格式由 IETF 這個組織訂成編號文件，叫 RFC；HTTP 本身（RFC 9110）也是。problem details 就是 HTTP API 錯誤格式的標準（RFC 9457，取代舊的 RFC 7807）。回應的 Content-Type 是 application/problem+json，前端看到這個 Content-Type 就知道 body 是錯誤說明，而且欄位固定：

欄位意思
type問題種類的 URI，客戶端用它判斷是哪一種錯誤。沒給時預設 about:blank（表示「就是這個狀態碼，沒有更多分類」）；RFC 建議用絕對網址，最好放一頁說明文件
title這種問題的簡短說明，同一個 type 的 title 不變
statusHTTP 狀態碼，和回應的狀態碼相同
detail這一次發生了什麼，給人看的
instance（選用）這一次問題的識別，例如請求的路徑或追蹤編號

這幾個欄位分工很清楚：type 給程式判斷（前端用 if (problem.type === …) 分支，不要拿 title 或 detail 的文字比對，那些是給人看的，可能改字或翻譯），title 描述這一類問題，detail 說明這一次的情況。同樣是 409，type 可以區分「訂單狀態不能這樣改」和「同一個請求還在處理中」，前端對兩者的處理不一樣。

標準只規定這幾個欄位，不夠用時允許加自己的擴充欄位，規則是客戶端不認得的欄位要忽略。驗證錯誤最常加的擴充欄位是欄位清單，讓前端把每個訊息標到對應的表單欄位（檢查外部資料的寫法見 TypeScript 課第 26 課）。做完練習 1 之後，在 work/14 用 node examples/server.ts create-order 開起練習 1 的伺服器，送一個欄位不對的訂單，看回應的 Content-Type 和 body：

$ curl -i -X POST localhost:3000/orders -H 'content-type: application/json' -d '{"drink":"珍奶","qty":0}'
HTTP/1.1 400 Bad Request
content-type: application/problem+json; charset=utf-8

{"type":"https://coffee.example/problems/validation","title":"資料格式不對","status":400,
 "detail":"訂單資料有誤","errors":[{"field":"drink","message":"drink 要是 美式咖啡、拿鐵、卡布奇諾、伯爵紅茶 其中之一"},
 {"field":"qty","message":"qty 要是 1 到 20 的整數"}]}

兩個欄位都錯，errors 一次列出兩個，前端可以同時把「珍奶」和「0」兩格標紅，不用讓使用者改一個、送一次、再發現下一個。

格式定好了，怎麼確保整個 API 真的都照著用？靠每個人記得是不夠的，總會有人在某個路由裡手寫一個 res.end(JSON.stringify({ message }))。可靠的做法是讓只有一個地方會產生錯誤回應：練習裡所有錯誤都經過 problem.ts 的 sendProblem，連讀 body 失敗（415、413、JSON 壞掉）和 500 都是。錯誤種類集中在一張表 PROBLEMS，每種錯誤的狀態碼和 title 都在表裡；新增一種錯誤時改這張表，不在路由裡寫死狀態碼。這樣錯誤格式要改，只改 sendProblem 一個地方，整個 API 一起變。

detail 是給客戶端看的，不能放 stack、SQL、內部主機名稱或第三方回傳的原始錯誤。RFC 9457 也提醒：problem details 描述的是 HTTP 介面，不是實作細節。完整錯誤寫進伺服器的 log（第 18 課、第 19 課）。
💡 實務上：錯誤格式先看團隊現況，再決定要不要換
新專案或新服務，一開始就用 problem details，前端只要寫一套錯誤處理：依 type 決定行為，有 errors 就把訊息標到對應的表單欄位。已經上線的 API 如果早有自己的格式，直接換成 problem+json 對所有客戶端都是破壞性變更（本課最後一節），要排進版本計畫，不是順手改。動手前先問前端：畫面上顯示的是 detail 還是前端依 type 自己準備的文字？要不要多語系？客服回報「下單失敗」時，能不能從 instance 或追蹤編號在 log 裡找到那一次請求？

單筆訂單的建立、讀取和錯誤都講好了。但王小明打開「我的訂單」時，看到的不是一筆，而是一長串，而且這串一直在變長。這就是開場第三個問題。

訂單列表怎麼翻頁，才不會翻到重複的訂單？

咖啡店開了半年，GET /orders 如果一次回所有訂單，回應會有好幾萬筆，App 要等很久、手機要花很多記憶體，資料庫也要一次讀出全部。所以列表要分頁：一次只回一小段，使用者往下捲再拿下一段。

最直覺的做法是 offset 分頁：前端送 ?page=2，伺服器換算成「跳過前 10 筆，拿 10 筆」，SQL 是 LIMIT 10 OFFSET 10（PostgreSQL 課第 5 課）。OFFSET 的意思只有「跳過幾筆」，它不知道使用者上一頁看到哪裡。這帶來兩個問題：

  1. 資料變動時重複或漏掉：列表是新的在前。假設一頁 3 筆，使用者看第一頁時進來兩筆新訂單，所有訂單往後擠兩格。第二頁「跳過前 3 筆」跳過的變成新的那兩筆加上原本的第一筆，於是第一頁的後兩筆又出現在第二頁。刪除時則相反，會漏掉。
  2. 越後面越慢：OFFSET 100000 資料庫還是要先找出前 100000 筆再丟掉（PostgreSQL 課第 27 課）。

第一個問題就是開場同事擔心的事，親眼看一次。範例有 10 筆訂單（編號 1 到 10，編號越大越新），一頁 3 筆，翻完第一頁之後進來訂單 11、12，再翻第二頁，左邊是 offset、右邊是等一下要介紹的 cursor。在 work/14 執行，看「第二頁」那一行：

$ node examples/offset-vs-cursor.ts
第一頁         offset: 10, 9, 8 ｜ cursor: 10, 9, 8
（新增了訂單 11、12）
第二頁         offset: 9, 8, 7 ｜ cursor: 7, 6, 5
offset 第二頁重複出現： 9, 8

新訂單進來後，列表變成 12、11、10、9、8、7…。offset 第二頁「跳過前 3 筆」跳過的是 12、11、10，於是從 9 開始拿，9 和 8 使用者在第一頁已經看過了。在無限捲動的畫面上，使用者會看到同一張訂單出現兩次；如果是刪除造成的漏掉，就更難發現。

cursor 分頁（也叫 keyset pagination）換一個問法：不記「跳過幾筆」，而是記「上一頁最後一筆是誰」，下一頁從它後面接著找。第一頁最後一筆是 8，第二頁就要「比 8 還舊的 3 筆」，也就是 7、6、5。新訂單 11、12 排在最前面，不會影響「比 8 還舊」的是哪些，所以不管中間進來多少新訂單，第二頁都接得剛剛好。

這個做法要成立，cursor 必須能唯一定位一筆，「比它舊」才有明確的答案。所以排序要是穩定排序（stable ordering），意思是每次查詢的順序都一模一樣，不會因為某些值相同而前後對調。做法是排序鍵的最後一定要有唯一的欄位。只用 createdAt 排序時，同一毫秒進來的三筆順序不固定，cursor 只記時間的話，「比這個時間舊」會把同時間、還沒看到的那幾筆跳過。所以排序用 createdAt DESC, id DESC，cursor 也記這兩個值：

-- 第一頁
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 11;
-- 下一頁：$1、$2 是上一頁最後一筆的 created_at 和 id
SELECT * FROM orders WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC LIMIT 11;

(created_at, id) < ($1, $2) 是列比較：先比 created_at，相同再比 id，和排序的規則一致。它也順便解決了第二個問題：資料庫配合 (created_at, id) 的索引，可以直接跳到上一頁最後一筆的位置往下讀，不用先數過前面幾萬筆，第 1 頁和第 1000 頁一樣快（SQL 和索引在 PostgreSQL 課第 27 課做過，這課做 API 這一端）。

API 這一端要決定前端怎麼拿到 cursor、怎麼帶回來：

  • 回應 { items, nextCursor }。nextCursor 是把最後一筆的 { createdAt, id } 用 base64url 編起來的字串（第 11 課的 encodeCursor），客戶端原封不動帶回來：GET /orders?limit=10&cursor=…。編成一個字串，前端就不用知道裡面是什麼，以後排序方式改了，前端也不用跟著改。
  • 多拿一筆（LIMIT 11）：拿得到第 11 筆才表示有下一頁。最後一頁的 nextCursor 是 null，客戶端看到就停，不用再多打一次拿到空頁。
  • limit 一定要有上限，不然有人送 limit=1000000 就能拖垮資料庫；不是 1 到上限的整數回 400。
  • cursor 是客戶端送來的字串，可能被改過或亂寫。解不開是客戶端的錯，回 400，不能讓解碼的例外變成 500。

cursor 分頁也有代價：它只能「從這裡往下」，不能直接跳到第 37 頁，也不容易算總頁數。訂單列表、動態牆、無限捲動很適合；需要「第幾頁」的後台報表，資料量不大時用 offset 也可以。

💡 實務上：列表 API 第一版就要有分頁
咖啡店上線第一週只有幾十筆訂單，GET /orders 直接回整個陣列看起來沒問題；半年後回應越來越大、越來越慢，這時回應從陣列改成 { items, nextCursor }，所有舊客戶端都會壞。所以任何「會一直長大」的列表，第一版就用物件包起來並帶分頁，就算現在只有一頁。分頁方式要和前端、PM 一起決定：無限捲動或「載入更多」用 cursor；PM 想要頁碼和總筆數時，先問清楚是誰在用、資料量多大，後台小表格用 offset 就好。

讀取的部分完成了：單筆、列表、錯誤都有固定的樣子。接下來是會改變訂單的請求：店員把訂單改成製作中、王小明想取消訂單。這時請求能不能成功，不只看請求本身寫得對不對，還要看訂單現在是什麼狀態。

已經取餐的訂單被取消，該回什麼？狀態轉換與 409

一張訂單從建立到結束，會經過幾個固定的狀態：等待中（pending）、製作中（brewing）、可以取餐（ready）、已取餐（picked_up），或中途被取消（cancelled）。不是任何兩個狀態之間都能隨便跳：還沒開始做的訂單可以取消，已經取走的咖啡不能取消。把「有哪些狀態、哪些轉換合法」寫清楚的規則，叫做狀態機（state machine）。咖啡店的訂單狀態機長這樣（用型別表達狀態機見 TypeScript 課第 27 課）：

TypeScript 課第 27 課用型別在編譯時擋住不合法的轉換。但 API 的輸入來自網路：前端送來的 { "status": "cancelled" } 只是一段文字，編譯時根本還不存在，型別擋不到，所以執行時也要檢查。練習的 orders.ts 已經有 TRANSITIONS（每個狀態可以變成哪些狀態）和 canTransition(from, to)，你要負責的是把檢查結果對照成上一節的狀態碼。同樣是「改不了」，原因不同，前端該做的事就不同：

請求回應原因
{ "status": "done" }（不認得的狀態）400請求本身就不對，什麼時候送都不對
PATCH /orders/999（不存在）404
訂單是 ready，要求 cancelled409格式正確，但和訂單目前的狀態衝突；同一個請求對 pending 的訂單就會成功

409 的 detail 要寫出目前狀態和要求的狀態，例如「訂單 42 目前是 ready，不能改成 cancelled」。前端拿到 409 通常會重新讀取訂單，讓使用者看到最新狀態：王小明的畫面可能還停在「等待中」，其實店員早就做好了，重新讀取後他會看到「可以取餐」，也就明白為什麼不能取消。

這節的檢查是「先讀狀態、再判斷、再寫入」。兩位店員同時操作同一張訂單時，這個順序中間可能被插隊；這課的訂單存在記憶體裡、同步執行，不會遇到，接上資料庫之後的寫法見課末「補充與查表」。

狀態機還順便讓改狀態的請求可以放心重送：店員的平板把「改成 brewing」送了兩次，第二次到的時候訂單已經是 brewing，狀態機不允許 brewing → brewing，回 409，訂單不會被改第二次。代價是第二次會收到 409，即使第一次其實成功了；前端照上面的做法重新讀取訂單，看到已經是 brewing，就知道剛才那次有成功。但建立訂單沒有狀態可以擋：同一個 POST /orders 送兩次，就是兩張訂單。這就是開場第四個問題。

手機逾時重送，怎麼不變成兩杯拿鐵？冪等鍵

先把情境看清楚。王小明在捷運上按下「送出訂單」，請求送到伺服器、訂單建好了，回應在回程的路上因為網路斷掉不見了。App 只看到逾時，不知道訂單到底有沒有成立。重送，可能變成兩杯；不重送，可能一杯都沒有。App 自己沒辦法分辨這兩種情況，因為它看到的都是「沒有收到回應」。

第 12 課講過冪等（idempotent）：一個操作做一次和做很多次，結果一樣。GET、PUT、DELETE 是冪等的：把 42 號訂單刪掉兩次，結果還是「42 號訂單不存在」，所以逾時了可以放心重送。POST 不是：POST /orders 的意思是「新增一筆」，送兩次就是新增兩筆。

冪等鍵（Idempotency-Key）是讓 POST 也能安全重送的做法。它的想法是讓伺服器分得出「這是同一個請求的重送」還是「另一個新請求」：客戶端為「這一次下單」產生一個唯一的 key（通常是 UUID），放在 Idempotency-Key 標頭，重送時帶同一個 key。伺服器記住每個 key 第一次的結果，下次看到同一個 key 就直接回那個結果，不再建立訂單。

只比對 key 還不夠。客戶端可能有 bug，拿上一筆訂單的 key 去送一筆新訂單，伺服器如果只看 key，會把舊訂單回給它，使用者以為新訂單成功了。所以伺服器除了 key，還要記下請求內容的指紋（fingerprint）。指紋是從請求內容算出的一段摘要，內容一樣指紋就一樣，內容有一點不同指紋就不同，伺服器用它判斷「同一個 key 送來的內容是不是同一份」。把所有情況列出來：

收到的請求回應
沒看過的 key照常處理，記下 key、請求內容的指紋和回應
同一個 key、同樣內容，第一次已經完成回第一次的狀態碼和 body，不再建立
同一個 key、不同內容422：客戶端拿舊 key 送新訂單，是客戶端的 bug，不能默默回舊訂單
同一個 key，第一次還在處理中409：請客戶端稍後再試
沒有 key依 API 的規定：這課照常建立；也可以規定一定要帶，沒帶回 400

第二列是開場問題的答案：王小明的 App 逾時後帶同一個 key 重送，拿到的是第一次的 201 和同一張訂單，只有一杯拿鐵。422 和 409 這兩個狀態碼來自制定中的標準草案，草案的狀態與標頭的寫法細節見課末「補充與查表」。

最容易寫錯的是並發，也就是兩個請求的處理過程在時間上重疊。使用者連按兩下，兩個同 key 的請求幾乎同時到。如果寫成「查 key → 沒有 → await 建立訂單 → 存 key」，第一個請求在 await 等資料寫入的時候，Node 會先去處理第二個請求；第二個請求查 key，第一個還沒存，於是兩個都以為自己是第一個，結果還是兩杯。

正確的做法是查到沒有就立刻佔住：在同一段同步程式裡存一筆「處理中」，中間沒有 await。Node 單執行緒，同步的那幾行一定會一口氣跑完，不會被別的請求插隊（第 7 課）。第二個請求進來時，key 已經是「處理中」，它就回 409。建立失敗時要放掉 key，刪掉那筆「處理中」，讓客戶端能用同一個 key 重試；不放掉的話，這個 key 永遠卡在處理中，重試一直拿到 409。

這課把 key 記在程序記憶體裡的 Map。正式環境還要決定 key 保存多久、存在哪裡才能在多個程序之間共用，見課末「補充與查表」。

💡 實務上：冪等鍵留給「重複了會出事」的操作
最常見的是付款、下單、扣庫存、發優惠券，Stripe 這類金流 API 也是用 Idempotency-Key 標頭讓客戶端安全重試。前端要在「使用者決定送出這一筆」時產生 key，自動重試和使用者再按一次都帶同一個；每次重送都產生新 key，等於沒做。留言、收藏這類重複了也只是多一筆、使用者自己刪掉就好的操作，通常不值得多一張表和一套清理機制。設計時先問：這個操作重複執行，會多扣錢、多出貨，還是只是多一筆紀錄？

到這裡，開場的四個問題都有了完整的答案，這份設計可以交給前端、上線了。但上線不是終點：下個月 PM 要加新功能，欄位要改名、狀態要多一種，這時改 API 的方式不對，就會弄壞已經在使用者手上的 App。

上線之後要改 API，怎麼不弄壞舊版 App？

API 上線之後，有網頁前端、手機 App、合作夥伴依賴它。網頁前端可以跟後端一起部署，但手機 App 的舊版本會在使用者手上留好幾個月：王小明沒開自動更新，他手機裡的 App 還是照上線那天的格式在解析回應。你沒辦法讓所有客戶端同時更新，所以每次修改都要先問：舊的客戶端還能正常運作嗎？

能的修改叫向後相容（backward compatible）：新版 API 對舊客戶端來說，用起來跟以前一樣。不能的叫破壞性變更（breaking change）：舊客戶端照原本的方式用，會出錯或算錯。對照訂單 API 的例子：

向後相容（backward compatible）破壞性變更（breaking change）
新增選用的回應欄位刪除或改名欄位（drink → productName）
新增端點改欄位型別（price 從 80 變成 "80"）
新增選用的請求參數原本選用的參數變成必填
放寬驗證（qty 上限 20 → 50）改語意（total 從含稅變成未稅，型別沒變，金額全錯）
改狀態碼或錯誤的 type

判斷的方式是站在舊客戶端的位置想：它送出的請求還會被接受嗎？它讀到的回應還是它認得的樣子嗎？新增欄位相容，前提是客戶端忽略不認得的欄位，這和 problem details 的擴充欄位是同一個規則。改語意最危險，因為型別沒變，舊客戶端不會報錯，只是默默算錯。另外要小心看起來相容、其實不相容的情況：新增一個列舉值（例如狀態多了 refunded），寫了 switch 窮舉的舊客戶端可能直接出錯，因為它從來沒想過會收到這個值。

真的需要破壞性變更時，就要讓新舊兩種行為同時存在，讓客戶端自己選要用哪一個，這叫版本化。常見的做法有兩種：

  • 網址加版本：/v2/orders。一眼就看得出來、好測試、好在 log 和閘道裡分流；代價是同一筆資源有兩個網址。
  • 標頭帶版本：例如自訂的 Api-Version: 2026-10-01。網址不變，可以做到很細的版本；但在瀏覽器和 log 裡比較不明顯，快取要記得 Vary（第 15 課）。

不論哪一種，版本都是成本：每多一版就多一套要維護、測試的行為。資深的做法是盡量用相容的方式演進（新增欄位、新增端點），真的要改時新舊並存一段時間，先公告、看 log 確認沒人用舊版，再移除。NestJS 的版本化和 OpenAPI 文件在 NestJS 課第 23 課，大型系統怎麼演進在系統設計課第 19 課。

整份訂單 API 的設計到這裡完成了。接下來把前五節的設計做成真的伺服器：統一的錯誤格式、201 加 Location、cursor 分頁、狀態轉換的 409、冪等鍵。

練習

在 learn/ 執行 node check.mjs node 14 建立 work/14/。共用的檔案不用改：orders.ts（訂單型別、狀態機、驗證、記憶體裡的 OrderStore）、http-utils.ts（sendJson、readJson、withErrors、orderIdFrom）、cursor.ts（第 11 課的 encodeCursor／decodeCursor）。每題的 createApp(store) 回傳一個伺服器，測試會傳入自己的 store；想用 curl 試，執行 node examples/server.ts <檔名>（例如 list-orders）。

練習 1：先把 problem.ts 的 sendProblem 改成 RFC 9457 的格式：Content-Type application/problem+json; charset=utf-8，body 是 { type, title, status, detail }（type 是 PROBLEM_BASE 加上種類名稱，title 和 status 來自 PROBLEMS 表），有 errors 時再加上 errors 陣列。所有錯誤都經過它，改這一個地方，整個 API 的錯誤格式就一致了。再完成 create-order.ts：POST /orders 成功回 201、Location: /orders/{id}，body 是訂單本身（不要再包一層）；GET /orders/:id 回那筆訂單，找不到回 404，方法不對回 405＋Allow: GET。測試會比對每個錯誤的 type 和 title，也會用 Location 直接 GET 拿回同一筆訂單。

練習 2：完成 list-orders.ts 的 GET /orders cursor 分頁。?limit= 預設 10、最大 50，不是 1 到 50 的整數（0、51、abc、1.5）回 400；依 createdAt 由新到舊、同時間再依 id 由大到小；回傳 { items, nextCursor }，nextCursor 用 encodeCursor 把這頁最後一筆的 { createdAt, id } 編起來，最後一頁是 null（剛好整除時也是）；?cursor= 解不開回 400。測試會建立 25 筆（有很多筆同一個 createdAt，而且 id 大的不一定比較新）逐頁讀完，也會在第一頁和第二頁之間新增 3 筆，兩種情況都要每筆剛好出現一次。

練習 3：完成 update-status.ts 的 PATCH /orders/:id，body 是 { "status": "brewing" }。status 不是認得的狀態（或 body 不是物件、沒有 status）回 400；訂單不存在回 404；canTransition 不允許的轉換回 409 problem+json，detail 要寫出目前的狀態和要求的狀態；合法時改好並回 200 和改好之後的訂單。測試會試過所有「從 → 到」的組合，不合法的轉換不能改到訂單。

練習 4：讓 idempotent-create.ts 的 POST /orders 支援 Idempotency-Key：同一個 key 再送相同內容，回第一次的狀態碼、body 和 Location，不建立新訂單；同一個 key 不同內容回 422（'idempotency-key-reused'）；同一個 key 的第一個請求還在處理中又收到時回 409（'request-in-progress'）；沒帶 key 的照常建立。記錄放在 createApp 裡的一個 Map 就好（每個伺服器各自一份）。測試會讓 store 寫入延遲 300ms，再同時送兩個同 key 的請求，必須一個 201、一個 409，而且只建立一筆；也會讓第一次寫入失敗，同一個 key 重試要能成功。

練習 5：訂單列表用 ?page=（LIMIT 10 OFFSET (page-1)*10），新的訂單排在前面。使用者在看第 1 頁時進來 3 筆新訂單，接著他翻到第 2 頁，會看到什麼？

✓ 新訂單排在最前面，所有舊訂單往後擠 3 格；OFFSET 10 跳過的 10 筆裡有 3 筆是新的，所以原本第 1 頁的最後 3 筆被擠到第 2 頁，重複出現。OFFSET 只是「跳過幾筆」，不知道你上一頁看到哪裡，也不會報錯。新訂單在最前面，要回到第 1 頁才看得到。cursor 分頁記的是上一頁最後一筆，不受影響。

練習 6：客戶端用同一個 Idempotency-Key 送了 {"drink":"拿鐵","qty":1}，成功之後又用同一個 key 送 {"drink":"拿鐵","qty":3}。伺服器該怎麼做？

✓ 冪等鍵代表「同一個請求的重送」，內容不同就不是重送，通常是客戶端重用了舊的 key。回第一次的結果會讓客戶端以為 3 杯點成功了；改掉舊訂單或建立新訂單都讓 key 失去意義。草案建議用 422 明確告訴客戶端出錯了，所以伺服器除了 key 還要比對請求內容的指紋。

練習 7：為了顯示方便，想把回應裡的 price 從 110 改成 "110"。這是相容的變更嗎？

✓ 舊客戶端用 price * qty 還算得出來（JavaScript 會自動轉型），但 price + tax（tax 是 5）會變成字串相接 "1105"，強型別語言的 App 則直接解析失敗。JSON 的數字和字串是不同型別。要提供格式化的價格，新增一個欄位（例如 priceText），保留原本的 price。

常見錯誤

  • 網址用動詞（/createOrder、/cancelOrder?id=42）：動作應該由方法表達。用 POST /orders、PATCH /orders/42，真的需要動作時用 POST /orders/42/cancel 並保持一致。
  • 建立成功回 200、沒有 Location：客戶端不知道新資源在哪。回 201、Location，body 放新資源。
  • 所有錯誤都回 400 或 500：前端無法區分「表單填錯」「資源不存在」「狀態衝突」「伺服器壞了」。照決策表選：請求本身錯 400、不存在 404、和目前狀態衝突 409、伺服器的問題 5xx。
  • 每個端點的錯誤格式不同：前端得替每支 API 寫錯誤處理。用 problem details，並讓所有錯誤經過同一個函式。
  • offset 深分頁：資料變動時重複或漏掉，頁數越後面越慢。列表類的 API 用 cursor 分頁，limit 設上限。
  • 排序沒有唯一鍵：同時間的資料順序會跳動，cursor 會跳過或重複。排序最後加上 id，cursor 也帶 id。
  • 壞掉的 cursor 變成 500：cursor 是外部輸入，解碼失敗要回 400。
  • 冪等鍵只存結果，沒處理並發：「查 → await 建立 → 存」讓同時到的兩個請求都建立。查到沒有就立刻佔住，處理中的回 409；也要比對內容，不同就回 422。
  • 直接改既有欄位的型別或意思：舊客戶端會壞，而且常常不會報錯，只是算錯。新增欄位，舊欄位保留到確認沒人用。

小結

  • 從需求的名詞找資源：集合 /orders、單一資源 /orders/42；網址用名詞複數，動作交給方法。
  • 建立回 201＋Location；4xx 是客戶端改請求就能成功，5xx 是伺服器的問題；400、404、409 分別是請求本身錯、不存在、和目前狀態衝突。
  • 錯誤用 RFC 9457 problem details（application/problem+json，type、title、status、detail），驗證錯誤加 errors；所有錯誤經過同一個函式，不洩漏內部細節。
  • cursor 分頁用上一頁最後一筆的 (createdAt, id)，排序以唯一欄位收尾，多拿一筆判斷有沒有下一頁，limit 有上限，壞 cursor 回 400。
  • 狀態機在執行時也要把關，不合法的轉換回 409，detail 說明目前與要求的狀態。
  • Idempotency-Key 讓 POST 可以安全重送：同 key 同內容回第一次的結果、不同內容 422、處理中 409；先佔住 key 再 await；key 要有期限，多程序時存在共用的地方。
  • 新增選用欄位和端點是相容的；改名、改型別、改語意是破壞性變更，盡量避免，真的要改時用版本並讓新舊並存一段時間。

下一課看 HTTP 本身提供的機制：用 Cache-Control 和 ETag 讓回應可以被快取，用 Vary 避免快取給錯版本，用 If-Match 防止兩個人同時修改時互相覆蓋。

Idempotency-Key 標頭的標準化狀態

（IETF 與 RFC 見「錯誤的 body 長什麼樣？」一節。）Idempotency-Key 標頭目前是 IETF 的草案 draft-ietf-httpapi-idempotency-key-header-08（2026-10-22 更新），還不是 RFC；主線表格裡的 422、409 是草案建議的做法。草案規定標頭值是 Structured Fields 的字串，所以會帶雙引號：Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"。

冪等鍵在正式環境：期限與存放位置

  • 期限：key 不能永遠留著，草案建議定一個保存期限並寫在文件裡（例如 24 小時），過期就刪。
  • 存在哪裡：存在程序的記憶體裡，重開就忘記，開好幾個程序時也不共用。要存 Redis 或資料庫，佔位要用原子操作（例如 Redis 的 SET … NX 或資料庫的唯一索引），第 24 課會遇到；更完整的設計在系統設計課第 9 課。

兩位店員同時改同一張訂單

兩位店員同時操作同一張訂單時，「先讀狀態、檢查、再寫入」中間可能被別人插隊，檢查就失效了。資料庫裡要用 UPDATE … WHERE id = $1 AND status = 'pending' 讓檢查和寫入一次完成（PostgreSQL 課第 19 課）；這課的 store 在記憶體裡、同步執行，不會有這個問題。
