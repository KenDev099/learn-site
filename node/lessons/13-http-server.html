階段 4：HTTP 服務 · 第 13 課

用 node:http 寫伺服器

上一課用 node:net 把 HTTP 拆到最底層：自己切請求行、自己算 Content-Length、自己把回應的文字一行一行拼出來。這一課換成 Node 內建的 node:http。這些格式上的苦工它都替你做好了，留給你的是真正屬於「後端」的決定：這個請求該由哪段程式處理、前端送來的資料能不能信、出錯時要回什麼。

這課的任務：咖啡店的 Vue 前台要接四支 API，看菜單 GET /menu、看單一品項 GET /menu/:id、下單 POST /orders、店員篩選訂單 GET /orders?status=…&drink=…。不用任何框架，只用 node:http 寫出來，而且要撐得住真實世界：前端網址後面多帶了查詢字串、有人送來 2GB 的 body、JSON 少了一個括號、你自己的程式 throw 了。最後一種最致命：沒處理好的話，一個壞掉的請求會讓整台伺服器倒掉，正在結帳的其他顧客一起斷線。練習 1 做菜單的兩支 GET、練習 2 做下單、練習 4 做篩選訂單，練習 3 補上讓伺服器不會倒的錯誤處理。

這課的路線：
  1. 最小的伺服器、把回應寫對：node:http 怎麼把一個請求交給你；回應為什麼要先轉成 Buffer、標頭送出後為什麼改不了，以及把回應做成 sendJson／sendError 兩個工具。
  2. 菜單 API 的路由：依方法和路徑分派時，為什麼 /menu?lang=zh 會變成 404；路徑參數、查詢參數怎麼取；404 和 405 怎麼分。
  3. 下單 API 讀 request body：讀前端送來的 JSON 時，怎麼擋超大 body、不把中文切壞、驗證欄位。
  4. 一個壞請求為什麼讓整台伺服器倒：throw 的錯誤去了哪裡，怎麼在最外層接住。
  5. 不守規矩的客戶端與框架：Node 預設替你擋了哪些攻擊、客戶端中途離開時怎麼停手；最後對照這課手寫的東西在 Express、NestJS 裡叫什麼。
這課會用到：
  • 第 12 課的 HTTP 訊息與 curl：請求是「方法＋路徑＋標頭＋body」，回應是「狀態碼＋標頭＋body」，用 curl -i 看原始回應。
  • 第 11 課的 Buffer.concat：資料片段要先接完整再解碼，不然中文會被切壞。

最小的伺服器：node:http 怎麼把請求交給你？

上一課用 node:net 時，你拿到的是一條 TCP 連線上流進來的原始位元組，要自己找出哪裡是請求行、哪裡是標頭。node:http 把這一段做掉了：它負責聽連線、解析請求文字，解析好一個請求，就呼叫一次你給它的函式。

這個「你給它的函式」叫請求處理函式（request handler）。它跟 Vue 的 @click="onClick" 是同一種關係：你不自己去呼叫 onClick，而是把它交出去，事件發生時由別人呼叫。這裡的事件是「一個 HTTP 請求進來了」，呼叫的人是 Node。用 createServer(處理函式) 交出去，每次呼叫 Node 會傳入兩個物件：

  • req（型別叫 IncomingMessage）：客戶端送來的請求。req.method 是方法、req.url 是請求行裡的目標（例如 /menu?size=L）、req.headers 是標頭（名稱一律轉成小寫，所以寫 req.headers['user-agent']）。body 不在這裡面，要另外讀，下單那一節會講。
  • res（型別叫 ServerResponse）：你要寫回去的回應。設定狀態碼和標頭，最後 res.end(body) 送出。

咖啡店的第一版：不管誰來問，都回一份只有拿鐵的菜單。

// examples/hello.ts
import { createServer } from 'node:http'

const server = createServer((req, res) => {
  console.log(req.method, req.url, req.headers['user-agent'])
  const body = Buffer.from(JSON.stringify([{ id: 2, name: '拿鐵', price: 110 }]))
  res.writeHead(200, {
    'content-type': 'application/json; charset=utf-8',
    'content-length': String(body.length),
  })
  res.end(body)
})

server.listen(Number(process.env.PORT ?? 3000), () => {
  const { port } = server.address() as { port: number }
  console.log(JSON.stringify({ msg: 'listening', port }))
})

在 work/13 執行 node examples/hello.ts，另開一個終端機用 curl 打它：

$ curl -i http://localhost:3000/menu

content-type: application/json; charset=utf-8
content-length: 38
Date: Sat, 31 Oct 2026 15:35:34 GMT
Connection: keep-alive
Keep-Alive: timeout=5

[{"id":2,"name":"拿鐵","price":110}]

伺服器那邊印出 GET /menu curl/8.7.1。回應裡的 Date、Connection、Keep-Alive 你沒有寫，是 node:http 自己補上的；上一課用 node:net 時，這些都得自己拼。

再看最後那段 server.listen(…)。listen(port) 是「開始在這個 port 等連線」。之後程式不會像一般腳本那樣跑完就結束：伺服器是一個撐住 event loop 的 handle（第 7 課），只要它還在聽，程序就活著，要按 Ctrl+C 才會停。這也帶來一個常見的狀況：上一次啟動的伺服器沒停掉，又啟動一次，第二個 listen 會丟出 Error: listen EADDRINUSE: address already in use :::3000，意思是 3000 已經有程式在聽了。看到它就先停掉舊的那個。

port 給 0 有特別的意思：讓作業系統挑一個現在沒人用的 port。測試都這樣做，好幾個測試同時開伺服器也不會搶同一個 port。挑到哪一個，要在 listen 完成後用 server.address().port 問，上面的程式就是這樣印出 port 的。

本課程的約定：伺服器程式從環境變數 PORT 讀 port，沒給就用 3000；聽好之後印一行 {"msg":"listening","port":N}。測試用 PORT=0 啟動你的程式，讀這一行就知道要連哪裡。第 19 課會把這種一行一筆 JSON 的 log 寫完整。

還有一件事先記著：req 是可讀串流、res 是可寫串流。意思是 body 是一段一段流進來、一段一段寫出去的，不是一次全部到齊。下單那一節讀 body 時會用到這一點；第 16 課再詳講串流。

這個版本有一個明顯的問題：打 /abc 也回菜單，因為處理函式根本沒看路徑。接下來要讓不同路徑回不同東西：菜單、單一品項、找不到時的 404、方法不對的 405。每一種都要寫一次 writeHead、算一次 Content-Length。所以在分派路徑之前，先把「怎麼回應」這件事弄對，做成每個分支都能共用的工具。

回應怎麼寫才不會出錯？

上一節的 hello.ts 回應前做了兩件看起來多餘的事：先把 JSON 字串轉成 Buffer、自己算 content-length。這一節先說回應是怎麼送出去的，再回頭看這兩件事為什麼必要。

回應由三部分組成：狀態行、標頭、body。它們在連線上是依序送出的一串位元組，跟上一課看到的原始文字一樣：先是 HTTP/1.1 200 OK，再來每行一個標頭，空一行，最後是 body。res 上對應的寫法：

寫法做什麼
res.statusCode = 404設定狀態碼（預設 200）
res.setHeader(名稱, 值)先記下一個標頭，還沒送出
res.writeHead(狀態碼, { 標頭 })一次設定狀態碼和標頭；和 setHeader 設過的同名標頭衝突時，writeHead 的優先（本機實測）
res.write(資料)送出一段 body；第一次 write 時標頭就跟著送出
res.end(資料)送出最後一段 body，結束這個回應

因為順序固定，標頭一定比 body 先離開伺服器。第一次 write 或 end 時，狀態行和標頭就已經送上網路，客戶端可能都收到了，不可能再收回來改。Node 用 res.headersSent 告訴你標頭送出了沒；送出之後還呼叫 setHeader 或 writeHead，Node 會丟出 ERR_HTTP_HEADERS_SENT。

實際寫程式時，這個錯誤最常見的成因是同一個請求回應了兩次。例如在 if 裡回了 404，忘了 return，程式繼續往下走，又回一次 200。第一次回應已經把標頭送出去，第二次就丟錯。所以本課的寫法一律是 return sendJson(…)：回應和離開函式寫在同一行，不會忘。

回到 hello.ts 那兩件事。Content-Length 告訴客戶端 body 有幾個位元組，客戶端靠它判斷 body 在哪裡結束；上一課看過，這個數字算錯，客戶端就只拿到半個 JSON。而 JavaScript 字串的 length 算的是字元不是位元組：'拿鐵'.length 是 2，用 UTF-8 送出去卻是 6 個位元組（第 11 課）。先 Buffer.from 轉成位元組，body.length 才是正確的位元組數。

content-type 裡的 charset=utf-8 是同一類問題的另一端：它告訴客戶端「這些位元組請用 UTF-8 解讀」。少了它，有些客戶端（舊瀏覽器、某些 HTTP 函式庫）會用別的編碼解讀，中文變成亂碼。

每個回應都要記得這三件事（轉 Buffer、算長度、寫 charset）太容易漏，所以練習的 http-utils.ts 已經把它們包成兩個小工具。這課所有回應都經過它們，格式才會一致：

export function sendJson(res, status, data, headers = {}) {
  const body = Buffer.from(JSON.stringify(data))
  res.writeHead(status, {
    'content-type': 'application/json; charset=utf-8',
    'content-length': String(body.length),
    ...headers,
  })
  res.end(body)
}

// 錯誤格式：{ error: { code, message } }，驗證錯誤再加 details: [{ field, message }]
sendError(res, 404, 'NOT_FOUND', '找不到這個路徑')

sendError 的錯誤格式分成兩個欄位，各有用途：code 是給程式判斷的固定字串，前端用它決定顯示什麼、要不要重試；message 是給人看的說明。這樣分開之後，哪天把訊息文字改得更友善，前端的判斷也不會壞。sendError 的第 5 個參數可以帶 headers（額外標頭）和 details（驗證錯誤清單），後面的 405 和 400 會用到。第 14 課會換成業界標準的錯誤格式。

有了 sendJson 和 sendError，回應這件事就處理好了。現在回到上一節留下的問題：讓 /menu、/menu/2、不存在的路徑各回各的。

菜單 API：怎麼依方法和路徑分派？

「依方法和路徑，決定由哪段程式處理這個請求」叫路由（routing）。用 node:http 時沒有人替你做，處理函式裡要自己寫判斷。新手最常寫成：

if (req.url === '/menu') return sendJson(res, 200, menu)

自己用 curl 測都正常。直到前端送來 /menu?lang=zh：req.url 是請求行裡的整個目標，也就是路徑加上查詢字串，'/menu?lang=zh' === '/menu' 不成立，這個請求就掉到最後的 404。前端只是多帶一個參數，API 就說「沒有這個路徑」。

要先把路徑和查詢字串拆開。不要自己切 ?，用標準的 URL 類別，它跟瀏覽器裡的 new URL() 是同一個東西。有一個地方要注意：URL 需要完整的網址（scheme、host、路徑），而 req.url 只有路徑那一段，所以要給第二個參數當「基底網址」補上前面的部分。我們只要它拆出來的路徑和查詢參數，基底填什麼都可以，本課一律寫 'http://localhost'：

// examples/url.ts
const raw = '/orders?status=ready&drink=%E6%8B%BF%E9%90%B5&drink=%E7%BE%8E%E5%BC%8F%E5%92%96%E5%95%A1&page=2'
const url = new URL(raw, 'http://localhost')

$ node examples/url.ts
pathname: /orders
status: ready
drink（get）: 拿鐵
drink（getAll）: [ '拿鐵', '美式咖啡' ]
沒有的參數: null
手動 split: [ 'status=ready', 'drink=%E6%8B%BF%E9%90%B5', … ]

這個例子用的是練習 4「店員篩選訂單」會收到的網址。url.pathname 是乾淨的路徑 /orders，路由比對它就不會被查詢字串干擾。

? 後面那段叫查詢字串（query string），格式是 名稱=值，多個之間用 & 分隔。你會發現「拿鐵」在網址裡變成了 %E6%8B%BF%E9%90%B5。原因是網址只允許一小組 ASCII 字元，中文、空白、還有 &、= 這種在網址裡有特殊意思的字元，都要先轉成 UTF-8 位元組，每個位元組寫成 % 加兩位十六進位。這種轉換叫 URL 編碼（percent-encoding）。「拿」在 UTF-8 是 3 個位元組，所以是 %E6%8B%BF 三組。瀏覽器和 fetch 會自動把網址裡的中文編碼，所以後端收到的是編碼過的樣子。

url.searchParams 是一個 URLSearchParams 物件，已經替你把每個值解碼回中文：

  • get(名稱)：第一個值；沒有這個參數時回 null。
  • getAll(名稱)：同名參數的所有值，陣列。前端用 ?drink=a&drink=b 表示多選時要用它；用 get 只會拿到第一杯。
  • 自己 split('&') 會拿到沒解碼的字串，+ 代表空白這類規則也要自己處理，不要這樣做。舊教學常見的 url.parse() 也不要用，原因見課末。

/menu/2 的 2 怎麼取出來？

路徑拆乾淨之後，/menu 用 === 比對就好。但練習 1 還有 GET /menu/:id：/menu/2、/menu/5 都要進同一段程式，再把 2 取出來查菜單。路徑裡代表某一筆資料的那一段叫路徑參數（path parameter），框架通常寫成 /menu/:id。

自己寫時用正規表示式（TypeScript 課第 5 課）比對。正規表示式裡的括號是擷取群組：比對成功時，括號裡對到的內容會被另外存下來。exec 成功時回傳陣列，[0] 是整段、[1] 是第一個括號抓到的內容；失敗回傳 null：

const match = /^\/menu\/(\d+)$/.exec(pathname)
// '/menu/2'   → [ '/menu/2', '2' ]
// '/menu/abc' → null（\d+ 只收數字）
// '/menu/'    → null
// '/menu/2/x' → null（$ 要求到這裡結束）

^ 和 $ 讓它必須從頭對到尾，/menu/2/x 這種多一截的路徑才不會被當成 2 號。取到的 match[1] 是字串 '2'，拿去查菜單前要轉成數字。

找不到時，回 404 還是 405？

比對完路徑，還沒結束：/menu 只支援 GET，前端送 DELETE /menu 時要回什麼？直覺是 404，但「路徑找不到」和「路徑在、方法不對」是兩回事，客戶端該做的修正也不同：

請求狀態碼意思
GET /menus404 Not Found沒有這個資源，檢查網址
GET /menu/99（沒有 99 號）404 Not Found路由對了，但這筆資料不存在
DELETE /menu405 Method Not Allowed資源存在，但不支援這個方法

回 404，前端工程師會去檢查網址有沒有打錯，白忙一場；回 405，他立刻知道要換方法。405 還一定要帶 Allow 標頭，列出這個路徑支援的方法，例如 Allow: GET，客戶端才知道該換成哪個（RFC 9110 規定 405 必須帶 Allow）。

要分得出這兩種情況，判斷順序就得是：先看路徑對不對得上，對上了再看方法。反過來先看方法的話，DELETE /menu 在「是不是 GET」那關就被當成不認得，只能回 404。

const { pathname } = new URL(req.url ?? '/', 'http://localhost')
if (pathname === '/menu') {
  if (req.method !== 'GET') return sendError(res, 405, 'METHOD_NOT_ALLOWED', '不支援這個方法', { headers: { allow: 'GET' } })
  return sendJson(res, 200, menu)
}
// … 其他路由
sendError(res, 404, 'NOT_FOUND', '找不到這個路徑')

注意每個回應前面都有 return，就是上一節說的「一次請求只回應一次」。所有路由都沒對上，才會走到最後一行的 404。

到這裡，練習 1 菜單 API 需要的東西都有了。不過菜單的 GET 都是把伺服器上的資料送出去，資料從伺服器流向前端。下單反過來：資料從前端送進來，而且是一段你控制不了的 body。下一節處理它。

下單：怎麼安全地讀 request body？

前端用 fetch('/orders', { method: 'POST', body: JSON.stringify(order) }) 下單時，訂單內容放在請求的 body 裡。第 1 節說過，body 不在 req 的屬性上：req 是可讀串流，body 會被切成好幾段陸續抵達，因為網路本來就是一個一個封包送的，大的 body 不會一次全部到。每一段叫一個 chunk，在 Node 裡是一個 Buffer。req 可以用 for await 一段一段讀。最直覺的寫法是：

let text = ''
for await (const chunk of req) text += chunk   // ✗ 三個問題
const data = JSON.parse(text)                   // ✗ 第四個問題

在自己電腦上用前端正常送，它會動。問題都出在「不正常」的請求上：

  1. 沒有上限：有人送 2GB 的 body，你的伺服器就把 2GB 讀進記憶體，程序被作業系統砍掉，所有人一起斷線。上限要一邊讀一邊算，超過就停，不能讀完才檢查：讀完才檢查時，記憶體早就被吃掉了。Content-Length 標頭可以先拿來快速拒絕，但客戶端可以用 chunked（第 12 課）完全不給長度，所以邊讀邊算才是一定要有的那道檢查。
  2. 中文會被切壞：text += chunk 把每段 Buffer 各自轉成字串。chunk 在哪裡切開是網路決定的，不會照字元的邊界：「拿」的 3 個位元組可能一段 1 個、下一段 2 個，各自解碼都變成 �。要先 Buffer.concat 把所有位元組接起來，再一次解碼（第 11 課）。
  3. 沒檢查格式：客戶端送的可能是表單或純文字，照樣丟給 JSON.parse。這支 API 只收 JSON，所以 Content-Type 不是 application/json 就回 415 Unsupported Media Type，告訴客戶端「這種格式我不收」。比對時注意它可能帶參數：application/json; charset=utf-8 也是 JSON。
  4. JSON.parse 會丟錯：少一個括號的 JSON 會讓它丟出 SyntaxError。在 async 處理函式裡沒接住，整個伺服器會倒掉（下一節細講為什麼）。要 try/catch，回 400，告訴前端「你送的 JSON 壞了」。

四個問題各要一道檢查。順序依成本由便宜到貴排：看標頭最便宜，讀 body 要花時間和記憶體，解析 JSON 和驗證欄位要花 CPU。前面沒過就直接回錯誤，後面的都不用做：

中間兩關（上限、concat）合在一個 readBody 函式裡。骨架長這樣，超過上限的那一行留給練習 2：

async function readBody(req: IncomingMessage, limit: number) {
  const chunks: Buffer[] = []
  let size = 0
  for await (const chunk of req) {
    size += chunk.length
    // 超過 limit：停止讀取，讓呼叫端回 413
    chunks.push(chunk)
  }
  return Buffer.concat(chunks)
}

size 加的是 chunk.length，也就是這一段的位元組數，所以上限算的是位元組，不是字元。chunk 先存進陣列，全部收完再 Buffer.concat，中文就不會被切壞。

「停止讀取」怎麼做？在 for await 裡 return 或 throw 離開迴圈時，Node 會關掉這個請求的串流，剩下的 body 就不再讀進來。超過上限的狀態碼是 413 Payload Too Large（body 太大）。回 413 時加上 Connection: close 標頭，告訴客戶端這條連線不會再用，因為連線上還有沒讀完的 body，不能接著拿來送下一個請求。提早關連線對客戶端有副作用，有些客戶端收不到這個 413，細節與取捨見課末。

也因為有這個副作用，正式環境通常不只靠 Node 擋大 body。Node 前面多半放一台反向代理（reverse proxy）：它是一台站在你的程式前面的伺服器，客戶端的請求先到它那裡，它檢查、處理過再轉給你的 Node 程式。超大 body 在反向代理那一層就先擋掉（例如 Nginx 的 client_max_body_size），根本到不了 Node。devops 課會設定它。

最後一關是欄位驗證。JSON 能解析，不代表內容對：{"drink":"珍奶","qty":-3} 是合法的 JSON，卻不是合法的訂單。做法照 TypeScript 課第 26 課：JSON.parse 的結果當成 unknown，每個欄位檢查型別和範圍。重點是一次收集所有錯誤再回傳。只回第一個錯誤的話，前端改好 drink 送出，才發現 qty 也錯，要來回好幾次。一次列出來的回應長這樣：

HTTP/1.1 400 Bad Request
content-type: application/json; charset=utf-8

{"error":{"code":"VALIDATION","message":"資料格式不對","details":[
  {"field":"drink","message":"drink 要是菜單上的品項"},
  {"field":"qty","message":"qty 要是 1 到 20 的整數"}]}}

四關都過，才建立訂單回 201。這就是練習 2 要做的事。

💡 實務上：body 上限依端點決定，前後兩層要對得上
咖啡店的建立訂單只送幾個欄位，10KB 綽綽有餘；但後台「上傳商品照片」就不該塞進同一個 JSON 上限，常見做法是讓前端直接把檔案傳到雲端的檔案儲存服務（例如 AWS S3），API 只收檔案網址。資深工程師會先問：這個端點合理的最大 body 是多少？前面的反向代理設了多少？代理的上限比你小時，使用者看到的是代理的 HTML 錯誤頁，不是你設計的 JSON 錯誤，前端解析也跟著壞。另外 details 的 field 要跟前端表單欄位同名，前端才能把錯誤直接標在對應的輸入框旁邊，上線前跟前端對一下命名。

四個問題裡，第四個說得最輕描淡寫：「沒接住的話整個伺服器會倒掉」。一個請求的 JSON 壞了，為什麼會影響到其他人？下一節親眼看一次。

一個壞請求，為什麼整台伺服器跟著倒？

examples/crash.ts 模擬這個狀況。它有兩個路由：/slow 要 3 秒才回應，代表一位正在結帳、等待中的顧客；/boom 會丟錯，代表那個壞掉的請求。先打 /slow，在它回應之前打 /boom：

$ node examples/crash.ts
{"msg":"listening","port":3000}
file:///…/work/13/examples/crash.ts:14
    throw new Error('查詢失敗：資料庫密碼 s3cret')
          ^

Error: 查詢失敗：資料庫密碼 s3cret
    at Server.<anonymous> (file:///…/work/13/examples/crash.ts:14:11)

Node.js v24.22.1

# 另一個終端機，先打 /slow，再打 /boom：
$ curl http://localhost:3000/slow &
$ curl http://localhost:3000/boom
curl: (52) Empty reply from server
curl: (52) Empty reply from server     ← /slow 跟著陪葬

伺服器印出錯誤後就結束了。兩個 curl 都拿到「Empty reply」：不只 /boom，連跟它毫無關係、正在等的 /slow 也沒有回應。用 fetch 打的話，兩個請求都拿到 TypeError: fetch failed。

為什麼會這樣？處理函式是 async 時，裡面丟出、沒被接住的錯誤會讓它回傳的 Promise 變成 rejected。而呼叫你處理函式的是 Node，node:http 不會去看這個 Promise，也不會替你把錯誤轉成 500。沒有任何人處理的 rejected Promise 叫未處理的 rejection（unhandled rejection，第 8 課），Node 預設的反應是印出錯誤、讓整個程序以結束碼 1 結束。所有請求都在同一個程序裡處理，程序一結束，每條連線一起斷掉。倒的不只是出錯的那個請求，是整台伺服器。

一般（非 async）函式裡同步 throw 也是一樣的結局，只是名字不同：叫未捕捉的例外（uncaught exception），程序同樣以結束碼 1 結束。

前端開發時很少碰到這種事，因為瀏覽器裡一個事件處理函式丟錯，頂多那個按鈕沒反應，頁面照樣能用。後端不同：一個程序服務所有使用者，一個沒接住的錯誤就是全體停機。

解法是在最外層包一層：任何處理函式出的錯，同步的、非同步的，都在這裡接住，轉成 500 Internal Server Error（伺服器自己出錯了，不是客戶端的問題）。這一層要做到三件事：

  1. 回固定的訊息，不回原始錯誤：看上面的輸出，錯誤訊息裡有資料庫密碼。錯誤訊息和 stack 可能含有 SQL、檔案路徑、密碼，回給客戶端等於公開給攻擊者。客戶端只拿到 { error: { code: 'INTERNAL', message: '伺服器發生錯誤' } }。
  2. 完整的錯誤記在伺服器的 log：客戶端看不到細節，你自己一定要看得到。用 console.error(err) 印到 stderr（第 2 課），不然出事時沒有線索。第 18、19 課會加上請求編號，讓客戶端回報的錯誤對得到 log。
  3. 標頭已經送出時，只能中斷連線：例如報表寫到一半才出錯，客戶端已經收到 200 和一部分內容。這時不能再 writeHead(500)：第 2 節說過標頭送出後改不了，會丟 ERR_HTTP_HEADERS_SENT，而這個錯誤發生在你的錯誤處理裡，沒人接住，伺服器照樣倒。也不能 res.end()：客戶端會以為收到的是完整的報表。要用 res.destroy() 直接斷線，客戶端看到連線中斷，就知道回應不完整。用 res.headersSent 判斷是哪一種情況。

這一層的形狀是「收一個處理函式、回傳一個包好的新處理函式」，跟前端常寫的 debounce(fn) 一樣：debounce 收一個函式，回傳一個多了防抖功能的函式；withErrorHandling 收一個處理函式，回傳一個多了錯誤處理的處理函式。用的時候包在所有路由外面：

const server = createServer(withErrorHandling((req, res) => {
  // 原本的路由；這裡丟出的任何錯誤都會被 withErrorHandling 接住
}))

要同時接住同步的 throw 和 async 的 rejection，關鍵在於 try 裡要 await 處理函式的結果。await 一個 rejected Promise 會在那一行丟出錯誤，catch 就接得到；同步函式回傳的不是 Promise，await 一個普通值也沒問題，直接拿到那個值。少了 await，try 只接得到同步的那一半，async 的錯誤照樣變成未處理的 rejection。這是第 3 題要寫的函式。

接住錯誤之後，伺服器的狀態不一定還正確，例如記憶體裡的資料改了一半。對於處理函式裡的錯誤，回 500 讓伺服器繼續服務其他人是業界的標準做法；但真正意料之外、來自程式外層的錯誤（uncaughtException），正確做法是記 log 後讓程序結束，由負責看管程序的工具（例如 Docker 的重啟策略）重新啟動。第 18 課講這條界線。
💡 實務上：外層錯誤處理只接得到 await 鏈上的錯誤
常見的漏網之魚是「順手」的背景工作：建立訂單後不 await 就去寄確認信，或在 setTimeout、事件監聽器的 callback 裡 throw，這些錯誤不經過 withErrorHandling，照樣讓伺服器倒掉。Code review 時資深工程師會看兩件事：回應裡有沒有出現 err.message 或 err.stack，以及有沒有沒被 await、也沒有 .catch 的 Promise。客服回報「結帳時出現伺服器發生錯誤」時，你手上只有 log，所以 console.error 那一步不能省。

到這裡，四支 API 都能正確回應，自己程式的錯誤也不會拖垮伺服器。但還有兩種情況不是「哪個請求出錯」，而是客戶端本身不守規矩：一種是故意送得極慢，一種是等到一半就走了。

客戶端太慢、或中途離開，伺服器怎麼辦？

伺服器開在網路上，就會遇到惡意或有問題的客戶端。先看「太慢」。有一種攻擊叫慢速攻擊（slowloris）：攻擊者開很多連線，每條每隔幾秒才送一個標頭字元，永遠不送完。伺服器得替每條沒送完的連線保留資源、一直等下去，量夠多時，正常使用者就連不進來了。攻擊者不需要很大的頻寬，只要很有耐心。

對付它的方法是設時限：標頭必須在多久內收完，超過就把連線踢掉。這件事你不用自己寫，Node 已經內建幾道防線（本機 24.22.1 用 examples/defaults.ts 印出，與官方文件一致）：

設定預設值超過時
server.headersTimeout60000（60 秒）標頭還沒收完：回 408 並關閉連線
server.requestTimeout300000（5 分鐘）整個請求（含 body）還沒收完：回 408 並關閉連線
server.keepAliveTimeout5000（5 秒）keep-alive 連線閒置太久就關掉
http.maxHeaderSize16384（16KiB）標頭太大：回 431 Request Header Fields Too Large

headersTimeout 就是上面說的「標頭必須在多久內收完」，直接對付慢速攻擊；requestTimeout 把同樣的限制延伸到整個請求。這兩個值有一些使用上的提醒（例如不要設成 0），放在課末。表中的 408 Request Timeout 意思是伺服器等這個請求等太久，放棄了。keep-alive 是同一條 TCP 連線送完一個請求後先不關，留給下一個請求用，curl 回應裡的 Connection: keep-alive 就是這個意思（第 12 課）；keepAliveTimeout 管的是這條連線閒置多久沒有新請求就關掉。

這些預設值都只管「收請求」的時間和標頭大小。body 要多大才算太大，Node 不知道，因為那取決於你的 API：下單 10KB 就夠，上傳檔案可能要更多。那是上一節 readBody 上限的工作。

使用者關掉分頁了，伺服器知道嗎？

另一種是「中途離開」。店長打開後台的月報表，你的伺服器開始查資料庫，查到一半他等不及關掉了分頁。如果伺服器不知道，資料庫照樣查完，結果寫給一條已經斷掉的連線，白做工。報表查詢越重，浪費越多。

Node 給你兩個訊號：

  • req.signal：一個 AbortSignal（第 8 課），連線在回應完成前斷掉時被 abort。把它傳給支援取消的 API（fetch、計時器、資料庫查詢），客戶端一離開，那些工作就一起停下。req.signal 要 Node 24.20 以上才可靠，更舊的 24.x 上這個訊號的行為不同，會誤判；練習的 engines 只要求 24.16，自己用它時先確認版本，細節見課末。
  • res 的 close 事件：回應結束時觸發，但不管正常結束或中途斷線都會觸發，所以單看它分不出是哪一種。要搭配 res.writableFinished：true 是回應完整送出，false 是還沒送完連線就斷了。

examples/disconnect.ts 用 5 秒的 sleep 假裝在查資料庫，把 req.signal 傳給它，並在 close 時印出兩個訊號的狀態。分別試「等不及按 Ctrl+C」和「等它完成」：

// examples/disconnect.ts 的重點
res.on('close', () => {
  console.log('res close：writableFinished =', res.writableFinished, '，signal.aborted =', req.signal.aborted)
})
await sleep(5000, undefined, { signal: req.signal })   // 假裝在查資料庫；客戶端離開就取消

# curl 等不到 5 秒就按 Ctrl+C：
res close：writableFinished = false ，signal.aborted = true
客戶端離開了，停止產生報表
# 等它正常完成：
res close：writableFinished = true ，signal.aborted = false

中途離開時，sleep 被取消，報表不再產生；正常完成時，兩個訊號都說「沒事」。第 17 課呼叫外部 API 時，會把 req.signal 一路往下傳。

💡 實務上：讀取可以取消，寫入要想清楚
值得接上 req.signal 的是又慢又只是「讀」的工作：後台的月報表、匯出訂單 CSV、使用者每打一個字就送一次的搜尋建議，取消掉能省下資料庫的負擔。寫入就不一樣：顧客按下結帳後網路斷了，訂單可能已經寫進資料庫，只是回應沒送到，中途硬停反而可能留下寫了一半的資料。這時重點不是取消，而是讓前端重送時不會變成兩筆訂單，第 14 課的冪等鍵就是處理這件事。

咖啡店的四支 API 到這裡完整了：路由、回應、body、錯誤、不守規矩的客戶端都處理過。回頭看，這課寫的每一樣東西，框架都替你做了。最後一節對照一次。

這些事，框架替你做了哪些？

先認識 Express 的核心概念 middleware：它是 (req, res, next) 這樣的函式，跟這課的處理函式幾乎一樣，只多了一個 next。處理完就回應；不處理就呼叫 next() 交給下一個。所有請求依註冊順序走過這條鏈，路由、body 解析、錯誤處理都是鏈上的一個 middleware。對照這課手寫的東西：

這課手寫的Express 5 的對應NestJS 的對應
if (pathname === …)、正規表示式路徑參數、404／405app.get('/menu/:id', (req, res) => …)；都沒對到的請求交給最後一個 middleware，404／405 在那裡自己回@Get(':id') 這類路由裝飾器
readBody、上限、415、JSON 解析app.use(express.json())：預設上限 100kb（limit 選項可改）；Content-Type 不是 JSON 時它不解析，415 要自己判斷內建的 body parser（上限可以設定）
欄位驗證、一次列出所有錯誤沒有內建，自己寫或接驗證函式庫DTO 加 ValidationPipe
withErrorHandling四個參數的錯誤 middleware (err, req, res, next) => …，註冊在所有路由之後。Express 5 起 async 處理函式丟出的錯誤（Promise 被 reject）會自動交給它；Express 4 要自己 next(err)exception filter
createApp(menu)：資料從外面傳進來沒有內建，一樣用函式參數傳進去依賴注入

表上可以看到，框架並沒有替你做所有事：Express 的 express.json() 遇到不是 JSON 的請求只是不解析，415 還是你要自己判斷；欄位驗證也沒有內建。自己寫過一次，才知道框架在背後做了哪些決定、哪些沒做、出問題時去哪裡找。

最後一列值得多看一眼。練習裡的 createApp(menu) 不自己 import 菜單，而是由呼叫的人傳進來，測試就能傳一份隨機的菜單，確認你沒有把品項寫死。這種「需要的東西由外部傳入，而不是自己建立」叫依賴注入（dependency injection），第 22 課和 NestJS 課會大量使用。

💡 實務上：工作中很少直接寫 node:http，但常靠這課的知識除錯
正式專案幾乎都用框架，手寫路由和 body 解析只會在很小的工具裡出現，例如只回 {"ok":true} 的健康檢查，或接收第三方 webhook 的小程式。這課的價值在於看懂框架的錯誤：前端說「送大一點的資料就收到 413」，你會去查 body parser 和反向代理的上限；log 出現 ERR_HTTP_HEADERS_SENT，你會去找哪裡回應了兩次。不要因為學會了就在團隊專案裡自己造一套路由，維護和安全性的成本都比用框架高。

補充與查表

  • 為什麼不用 url.parse()：舊教學常用它解析 req.url。Node 24 執行時會印出 [DEP0169] DeprecationWarning: `url.parse()` behavior is not standardized and prone to errors that have security implications（本機 24.22.1 實測）。一律用 new URL(req.url, 'http://localhost')。
  • URLPattern：Node 24 也有全域的 URLPattern，可以直接寫 /menu/:id 比對路徑參數，但官方文件標示 Stability 1 Experimental（實驗中），本課程不用。
  • 寫出中文字串的已知問題：這台的 Node 24.22.1 有一個已回報的問題，分段寫出中文字串可能卡住。一律先轉成 Buffer 再寫，就不會遇到；sendJson 就是這樣做的。
  • 413 與提早關連線的取捨：伺服器提早關連線時，還在拚命送資料、沒在讀回應的客戶端，可能收到 EPIPE 或 ECONNRESET，而不是那個 413（本機用 fetch 一次送出 1MB 實測多半如此；本機 curl 8.7.1 送 1MB 則收到 413）。另一個選擇是回 413 之後繼續把剩下的 body 讀掉丟棄，代價是頻寬和時間。正式環境通常交給反向代理先擋（例如 Nginx 的 client_max_body_size）。
  • 逾時設定的提醒：官方文件提醒，沒有反向代理擋在前面時，headersTimeout 和 requestTimeout 不能設成 0。另外，逾時是每隔 connectionsCheckingInterval（預設 30 秒）檢查一次，所以實際踢掉的時間會比設定值晚一點。
  • req.signal 的版本差異：v24.16.0 加入；v24.20.0 起請求正常完成後不再被 abort。在更舊的 24.x 上正常完成也會觸發，拿它判斷「客戶端離開」會誤判，所以要靠它時請用 24.20 以上。

練習

在 learn/ 執行 node check.mjs node 13 建立 work/13/，裡面有內文的範例（examples/）、菜單 menu.ts、回應工具 http-utils.ts，和四題的起始檔。所有回應都用 sendJson／sendError。想自己用 curl 試，可以在檔案最後暫時加上 createApp(MENU).listen(3000)，試完記得拿掉。

練習 1：app.ts 的 createApp(menu) 回傳一個伺服器（還不用 listen，測試會自己 listen）。完成路由：GET /menu 回 200 和整份 menu；GET /menu/:id（id 是數字）回那個品項，沒有就 404；其他路徑（包括 /menu/abc、/menu/）回 404，code 是 NOT_FOUND；/menu 和 /menu/:id 收到 GET 以外的方法回 405，code 是 METHOD_NOT_ALLOWED，並帶 Allow: GET。網址後面加了查詢字串（/menu?x=1）也要照常運作。

練習 2：create-order.ts 的 POST /orders 現在照抄了「讀 request body」一節開頭的四個問題。修好它：Content-Type 不是 application/json（可以帶 ; charset=…）回 415 UNSUPPORTED_MEDIA_TYPE；body 超過 BODY_LIMIT（10240 位元組，不是字元；剛好 10240 可以）回 413 PAYLOAD_TOO_LARGE，而且一超過就要回應，不能等整個 body 收完；JSON 壞掉回 400 INVALID_JSON；drink 要是 menu 上的品名、qty 要是 1 到 20 的整數，不合格回 400 VALIDATION，details 列出所有錯的欄位（[{ field, message }]）；成功回 201 和 { order: { drink, qty } }。測試會把中文字切在兩段 chunk 中間送。看到測試訊息是 SyntaxError: …，代表 JSON.parse 的錯誤沒接住，伺服器倒了。

練習 3：完成 http-utils.ts 的 withErrorHandling(handler)（現在原封不動地回傳 handler）。server.ts 已經用它包住所有路由，不用改；它有 /boom-sync（同步 throw）、/boom-async（async 裡 throw）、/boom-after-headers（送出標頭和一段 body 之後才 throw）。要求：前兩個回 500 和剛好 { error: { code: 'INTERNAL', message: '伺服器發生錯誤' } }，不能帶原始錯誤訊息；標頭已送出時用 res.destroy() 中斷連線；每個錯誤都用 console.error 印出來；之後 GET /menu 照常回 200。先執行 node server.ts，用 curl 打 /boom-async 看伺服器倒掉。

練習 4：list-orders.ts 的 createApp(orders) 處理 GET /orders，現在不管查詢參數一律回全部。加上篩選：status 可以省略，給了就只能是 STATUSES 裡的值（大小寫也要一樣）；drink 可以出現多次（?drink=拿鐵&drink=美式咖啡）表示多選，每個都要是 MENU 上的品名；兩個都給時都要符合。不合法回 400 VALIDATION，details 列出所有出錯的欄位（status、drink）。不認得的參數忽略。成功回 200 和 { orders: […] }，順序不變。測試送出的中文會經過 URL 編碼。

練習 5：處理函式裡已經 res.end(body)，接著程式往下走，又執行了 res.setHeader('x-cache', 'miss')。會發生什麼事？

✓ 標頭在第一次寫 body（write 或 end）時就送出了，之後 setHeader、writeHead 都會丟 ERR_HTTP_HEADERS_SENT（本機實測），在 async 處理函式裡沒接住還會讓伺服器倒掉。它不會附加，HTTP/1.1 一個請求也只有一個回應。成因多半是回應後少了 return，用 res.headersSent 可以檢查。

練習 6：createServer(async (req, res) => { … }) 裡，某個請求的程式 throw 了，沒有任何 try/catch。結果是？

✓ node:http 不會替你把錯誤轉成 500，那是框架（或你寫的 withErrorHandling）做的事。async 函式裡的 throw 變成 rejected Promise，沒人處理，Node 預設讓程序結束，正在處理的其他請求也一起收到「Empty reply」。所以錯誤處理要包在最外層，每個處理函式都經過它。

練習 7：報表 API 查資料庫查到一半，使用者關掉了分頁。在 Node 24.22 的伺服器裡，怎麼知道這件事？

✓ 連線在回應完成前斷掉，req.signal 會 abort，可以直接傳給資料庫查詢或 fetch 一起取消。close 在正常完成時也會觸發，要看 writableFinished 才分得出來，所以 c 不夠。不需要等到寫回應才發現，b 錯。注意 v24.20.0 以前正常完成的請求也會讓 req.signal abort。

常見錯誤

  • 同一個請求回應兩次：回應後少了 return，第二次寫入丟出 ERR_HTTP_HEADERS_SENT。一律寫 return sendJson(…)。
  • Content-Type 漏了 charset=utf-8：有些客戶端會用別的編碼解讀，中文變亂碼。
  • 用 req.url 直接比對路徑：加了查詢字串就對不上。用 new URL(req.url, 'http://localhost') 取 pathname。
  • 還在用 url.parse 或自己 split('&')：前者已經 deprecated，後者沒有 URL 解碼。用 url.searchParams，多選參數用 getAll。
  • 方法不對回 404：資源存在時應該回 405 並帶 Allow，客戶端才知道該改方法而不是改網址。
  • 沒有 body 上限：一個超大請求就能把記憶體吃光。一邊讀一邊累計位元組數，超過就停止並回 413；只看 Content-Length 擋不住 chunked 請求。
  • 每段 chunk 各自轉成字串再串接：中文字被切在兩段之間時變成亂碼。先 Buffer.concat 再解碼。
  • async 處理函式沒有處理錯誤：一個請求的錯誤讓整台伺服器倒掉。最外層包一層，同步和非同步的錯誤都轉成 500。
  • 把錯誤訊息或 stack 回給客戶端：洩漏內部細節。客戶端拿固定訊息，完整錯誤寫進 log。

小結

  • createServer(handler) 每個請求呼叫一次 handler，傳入 req 和 res；listen(0) 讓系統挑 port。本課程的伺服器讀 PORT，聽好後印 {"msg":"listening","port":N}。
  • 回應：狀態碼、標頭、body 依序送出，標頭送出後不能再改，所以一個請求只回應一次。JSON 回應帶 charset=utf-8，先轉成 Buffer，Content-Length 才是位元組數。
  • 路由用方法加 pathname；查詢參數用 searchParams 的 get／getAll；路徑參數用正規表示式。先比路徑再比方法：路徑不存在 404，方法不對 405＋Allow。
  • 讀 body：檢查 Content-Type（415）→ 邊讀邊算上限（413）→ Buffer.concat 後解析（400）→ 驗證並列出所有錯誤（400）。
  • 沒接住的錯誤會讓整個程序結束，所有連線一起斷。最外層的錯誤處理把任何錯誤轉成固定的 500，完整錯誤寫進 log；標頭已送出時 res.destroy()。
  • Node 預設有 headersTimeout、requestTimeout、maxHeaderSize 擋慢速攻擊與超大標頭；客戶端中途離開用 req.signal 或 close＋writableFinished 偵測。
