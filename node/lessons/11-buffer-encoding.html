階段 3：檔案與位元組 · 第 11 課

Buffer 與編碼

咖啡店後台這週要接上三個新的資料入口：門市每晚上傳當天的訂單檔、咖啡機定時上傳杯數紀錄，以及給前端用的訂單列表 API。開發時的測試資料全是 latte、mocha 這類英文商品名，一切正常。換上真實資料的第一天，客服收到四個回報：匯入的訂單偶爾有幾筆名字變成「拿�」；API 回「拿鐵」那筆時，前端只收到半截 JSON；咖啡機的累計杯數變成負數；有人把訂單列表網址裡的 cursor 改了幾個字，伺服器就回 500。

四個 bug 都出在程式沒把位元組當位元組看待：前兩個把「字」和「位元組」混為一談，後兩個是誤讀了位元組的意思、或盲目相信別人送來的位元組。前端幾乎只碰字串，瀏覽器替你處理掉了位元組；後端卻天天碰位元組，檔案、網路封包、HTTP body、資料庫欄位都是以位元組計算，而這些 bug 在只有英文的測試資料裡完全看不到。這一課從「拿鐵」這兩個字開始，一個一個修掉它們；練習的三題就是這三個資料入口的正式版本。

這課的路線：
  1. 「拿鐵」的長度是 2，存起來卻是 6 個位元組：字元、編碼、位元組各是什麼，後端該用哪一種長度。
  2. Node 用什麼拿著位元組：Buffer 是什麼、怎麼和字串互相轉換，為什麼切出來的一段會改到原本的資料。
  3. 訂單檔一段一段到、API 回應只剩半截：中文被切在兩段之間怎麼辦，Content-Length 為什麼要填位元組數。
  4. 咖啡機的二進位紀錄：位元組順序、有號與無號、旗標，杯數為什麼會變成負數。
  5. 訂單列表的「下一頁」標記：怎麼用 base64url 放進網址、怎麼擋下被亂改的值；最後看自己建立和比較 Buffer 時會洩漏什麼。

「拿鐵」的長度是 2，為什麼存起來是 6 個位元組？

要回答這個問題，得先回到電腦怎麼存東西。電腦只存數字。最小的單位是位元（bit），只能是 0 或 1；8 個位元組成一個位元組（byte），可以表示 0–255 共 256 種值。檔案大小、網路流量、記憶體用量，都是用位元組算。

文字要存起來，得先變成數字，這件事分兩步。第一步是替每個字元定一個編號。Unicode 是一份全世界共用的對照表，替每個字元定一個編號，叫 code point，習慣寫成 U+ 加 16 進位數字：「拿」是 U+62FF，「☕」是 U+2615，「😀」是 U+1F600。Unicode 只規定「哪個字是幾號」，沒有規定這個號碼在檔案裡佔幾個位元組。

第二步是把編號寫成位元組，這套規則叫編碼（encoding）。同一個 code point，用不同的編碼寫出來的位元組不同，所以讀的人必須用寫的人那套編碼才解得回來。最常用的編碼是 UTF-8，網頁、JSON、Linux 檔案、PostgreSQL 的預設幾乎都是它。UTF-8 是變動長度的：英數字 1 個位元組，常用中文 3 個，emoji 多半 4 個。英數字只用 1 個位元組，所以純英文的 UTF-8 檔案和老式的英文檔案完全相同，也不浪費空間；代價是一個字佔幾個位元組要看是哪個字。

既然長度不固定，讀的人怎麼知道一個字到哪裡結束？UTF-8 把答案寫在位元組本身：一個字的第一個位元組，開頭的幾個位元說明這個字總共有幾個位元組，後面跟著的位元組一律以 10 開頭。例如「拿」的第一個位元組 e6 寫成 2 進位是 11100110，開頭三個 1 代表「這個字共 3 個位元組」；第二個 8b 是 10001011，以 10 開頭，代表「我是前一個字的後續」。解碼的程式靠這個規則判斷一個字讀完了沒有，後面處理切成兩段的資料時會再用到它。

那 JavaScript 的 '拿鐵'.length 為什麼是 2？因為 JavaScript 的字串又是第三種算法。字串在記憶體裡用 UTF-16 存，每 16 個位元算一格，叫 UTF-16 code unit，length 數的就是格數。常用中文一個字剛好 1 格；編號超過 U+FFFF 的字元（大部分 emoji，例如 U+1F600 的「😀」）一格放不下，要佔 2 格。用範例實際比一比，下面每一行印出字串、length、UTF-8 位元組數（Buffer.byteLength，下一節介紹）和實際的位元組，看 length 和位元組數哪裡開始不一樣：

$ node examples/bytes.ts
latte length = 5 位元組 = 5 <Buffer 6c 61 74 74 65>
拿鐵 length = 2 位元組 = 6 <Buffer e6 8b bf e9 90 b5>
拿鐵☕ length = 3 位元組 = 9 <Buffer e6 8b bf e9 90 b5 e2 98 95>
😀 length = 2 位元組 = 4 <Buffer f0 9f 98 80>
…

第一行是整個問題藏起來的原因：英文字串的 length 剛好等於位元組數，所以只用英文測試的程式，就算把兩者混用也看不出問題。換成中文差 3 倍，換成 emoji 又是另一個比例。到這裡，一個字串至少有三種「長度」，而不同的系統各用一種：

長度怎麼算拿鐵☕😀誰用這一種
字元數（code point 數）[...s].length31PostgreSQL 的 varchar(20) 限制的是字元數
UTF-16 code unit 數s.length32JavaScript 字串、前端的 maxlength
UTF-8 位元組數Buffer.byteLength(s)94HTTP 的 Content-Length、上傳大小限制、log 一行的長度限制、PostgreSQL NOTIFY 的 payload 上限（預設要小於 8000 位元組）

後端碰到的上限大多是最後一種：Content-Length 標頭是 body 的位元組數（這課後面實測），網路和磁碟只認位元組。但也不能一律換成位元組數：PostgreSQL 的 varchar(20) 數的是字元，和 JavaScript 的 length 也不一樣，emoji 在 JS 算 2，在 PostgreSQL 算 1。所以驗證長度之前，要先想清楚這個上限是誰訂的、對方用哪一種算法，再用同一種算法檢查。

💡 實務上：「最多 20 個字」要先問清楚是哪一種長度
咖啡店後台的商品名稱、顧客備註，PM 常寫「最多 20 個字」。前端的 maxlength 和 length 數 UTF-16 code unit，PostgreSQL 的 varchar(20) 數字元，第三方 API 的上限有時是位元組數，三邊對不上，就會出現「前端過了、後端擋下」，或送到外部系統後被截斷。資深會先確認上限最後由誰決定（通常是資料庫欄位或外部 API），前後端照同一種算法驗證，錯誤訊息也用同一種單位。測試資料至少放一筆中文和一筆 emoji，只用英文永遠測不出來。

後端要的多半是位元組數，但到目前為止我們手上只有字串。要數位元組、切位元組、讀位元組，Node 得先有一個東西把位元組拿在手上。

Node 用什麼拿著位元組？Buffer

上一節輸出裡的 <Buffer e6 8b bf …> 就是答案。Buffer 是 Node 用來裝位元組的物件：一段固定長度的記憶體，每一格是一個 0–255 的數字。fs.readFile 不給編碼時（第 10 課）、socket 收到資料時、crypto 算出雜湊時，拿到的都是它。

為什麼不直接用字串裝？因為字串裝的是「已經解碼好的文字」。要把位元組變成字串，就得先選一種編碼來解；碰到圖片、壓縮檔這種本來就不是文字的資料，或是一個只到一半的中文字，解碼器只能用替代字元頂上，原本的位元組就不見了。Buffer 什麼都不解，原封不動保留位元組，等你決定要怎麼看它。

Buffer 不是 Node 自創的一整套東西，它建立在瀏覽器也有的標準型別上：

型別是什麼
ArrayBuffer一塊固定大小的原始記憶體，本身不能直接讀寫
Uint8Array把一塊 ArrayBuffer 看成「每格 0–255 的陣列」，瀏覽器和 Node 都有
BufferNode 的 Uint8Array 子類別，多了編碼轉換、讀寫數字等方法。buf instanceof Uint8Array 是 true，所以收 Uint8Array 的 API（例如 fetch 的 body、TextDecoder）都能直接傳 Buffer

印出 Buffer 時，每個位元組顯示成兩個 16 進位字元，這種寫法叫 hex。16 進位每一位有 16 種值（0–9、a–f），兩位剛好是 16 × 16 = 256 種，正好對應一個位元組的 0–255：e6 就是 230，ff 就是 255。所以 hex 是看位元組最直接的方式，除錯時你會一直看到它。

日常最常做的是字串和位元組之間的轉換。從字串變位元組要選一種編碼，從位元組變字串也要用同一種，兩邊都不指定時是 UTF-8。下面是常用的操作，buf 是 Buffer.from('拿鐵')：

Buffer.from('拿鐵')                 // 字串 → 位元組，預設 UTF-8：<Buffer e6 8b bf e9 90 b5>
Buffer.byteLength('拿鐵')           // 6，不用真的建 Buffer 也能算位元組數
buf.toString()                      // 位元組 → 字串，預設 UTF-8
buf.toString('hex')                 // 'e68bbfe990b5'：每個位元組寫成兩個 16 進位字元
buf.toString('base64')              // '5ou/6ZC1'
buf.toString('base64url')           // '5ou_6ZC1'
Buffer.from('e68bbfe990b5', 'hex')  // 反過來：hex 字串 → 位元組
Buffer.concat([a, b])               // 接成一個新的 Buffer
buf.subarray(0, 3)                  // 取一段，不複製

hex 和 base64 是同一類東西：都是「把位元組寫成文字」的方式，用在 JSON、標頭、網址這些只能放文字的地方。注意它們和 UTF-8 方向相反：UTF-8 把文字變成位元組，hex 和 base64 把任意位元組變成安全的文字。hex 好讀，但長度變成 2 倍；base64 比較省，base64url 則是能直接放進網址的版本，兩者在後面「下一頁」標記那一節用到時再細講。

subarray 不是複本

最後一行的 subarray 要特別看一下，因為接下來處理分段資料、練習 2 解析大 Buffer 裡的一段紀錄，拿到的都是這種「一段」。subarray 回傳的 Buffer 和原本的共用同一塊記憶體，它只是看同一塊記憶體的另一個視窗，就像 TypeScript 課第 2 課兩個變數指向同一個物件：

const buf = Buffer.from('拿鐵')
const head = buf.subarray(0, 3)
head[0] = 0x41
console.log(buf)   // <Buffer 41 8b bf e9 90 b5>：原本的也被改了

這是刻意的設計：處理大檔案時切段不必複製，省記憶體也省時間。代價是你把 subarray 交給別的函式，它改了內容，原本的資料也跟著壞，而且錯誤會出現在離修改處很遠的地方。要獨立的複本就用 Buffer.from(buf.subarray(0, 3)) 或 Uint8Array.prototype.slice。前端工程師要特別小心 Buffer 的 slice()：陣列的 slice() 會複製，Buffer 的 slice() 卻和 subarray() 一樣共用記憶體，不要用它（細節見課末）。

有了 Buffer，就能回頭看開場的第一個 bug：匯入門市的訂單檔時，「拿鐵」為什麼會變成「拿�」。

訂單檔一段一段到，中文被切在兩段之間怎麼辦？

門市上傳的訂單檔不會一次整份交到你的程式手上。從檔案、網路、stdin 讀資料時，資料是一段一段到的，每一段叫一個 chunk：作業系統一次讀一塊磁碟，網路一次送一個封包，Node 每收到一段就交給你處理，不必等整份到齊，也不必把整份都放進記憶體（第 16 課詳講 stream）。每段多大由作業系統和網路決定，它們只管位元組，完全不知道哪裡是一個字的結尾。

範例 split.ts 模擬最糟的情況：「拿鐵」6 個位元組，第一段只到第 4 個位元組，也就是「拿」的 3 個位元組加上「鐵」的第 1 個。執行後依序看五種處理方式的結果：

$ node examples/split.ts
每段各自 toString： 拿���
第一段是完整的 UTF-8 嗎？ false
StringDecoder： 拿鐵
TextDecoder stream： 拿鐵
先 concat 再解碼： 拿鐵

第一行就是開場那個 bug。用上一節的 UTF-8 規則來看：第一段結尾的 e9 宣告「這個字共 3 個位元組」，但這一段已經結束了；第二段開頭的 90、b5 都以 10 開頭，是後續位元組，前面卻沒有開頭的位元組。兩段各自 toString() 時，解碼器看到的都是不完整的字，只能換成 �（U+FFFD，replacement character，專門表示「這裡解不出來」）。換掉之後原本的位元組就不在字串裡了，事後把兩段字串接起來也救不回「鐵」，資料就這樣永久壞掉。

第二行用 Node 內建的 isUtf8（node:buffer）確認：單看第一段，結尾確實是不完整的 UTF-8，結果是 false。這證明問題出在切段，而不是檔案本身的編碼（這個函式的其他用途見課末）。

修法的關鍵只有一個：解碼的一方要記得「上一段結尾還有幾個位元組沒湊成一個字」，等下一段來了接上再解。輸出的第三、四行是兩種「記住上一段結尾」的寫法（StringDecoder、TextDecoder 的 stream 模式），第五行是直接避開問題：全部收完再解碼。再加上 Readable stream 的 setEncoding，共四種：

  • StringDecoder（node:string_decoder）：write(chunk) 回傳能解的部分，結尾不完整的位元組先留著，下一次 write 再接上；資料結束時呼叫 end() 拿剩下的。
  • TextDecoder（瀏覽器也有的標準 API）：decode(chunk, { stream: true }) 效果一樣，最後呼叫一次不帶參數的 decode() 收尾。忘了 { stream: true } 就和各自 toString() 一樣會壞。
  • stream.setEncoding('utf8')：讓 Readable stream 直接吐出字串，內部就是用 StringDecoder。
  • 先 Buffer.concat 再解碼：資料不大、可以全部收完再處理時最簡單。資料可能很大時要配上大小上限，不然一個超大請求就能吃光記憶體。

前三種都在「邊收邊解」，適合要一行一行處理、不想等整份到齊的情況，像練習 1 的訂單匯入；第四種等全部到齊才解，程式最簡單，代價是整份資料都要放在記憶體裡。兩邊都要記得收尾：資料結束時，解碼器裡可能還留著不完整的位元組，end() 或最後一次 decode() 會把它們解出來（解不出來就變成 �），不呼叫就會默默丟掉最後一點資料。

💡 實務上：「偶爾有一兩個字變成 �」，先懷疑逐段解碼
這個 bug 很難在測試時發現：小資料通常一段就到齊，只有大檔案、慢網路、或剛好切在中文字中間時才出現，客服回報時常常只說「匯入的訂單有幾筆名字壞掉」。多數時候你用的是框架的 body parser 或 fs.readFile(path, 'utf8')，它們已經處理好了；自己處理 data 事件、socket 或分段讀檔時，才要套用上面的做法。這類程式的測試要故意把資料切在中文字中間，像練習 1 那樣。如果是整份都亂碼而不是零星幾個 �，例如門市從 Excel 匯出的 CSV，要懷疑的是檔案根本不是 UTF-8，不是切段。

收進來的方向修好了。送出去的方向有一個鏡像的 bug：API 回應「拿鐵」那筆時，前端只收到半截 JSON。

API 回應為什麼只剩半截 JSON？

伺服器送出的 body 也只是一串位元組，客戶端得知道這串位元組到哪裡結束，才知道回應收完了；同一條連線上可能接著還有下一個回應，不能靠「連線斷了」來判斷。第 12 課會完整講 HTTP 怎麼決定 body 有多長，其中一種是 Content-Length 標頭：客戶端讀到這麼多位元組就認定 body 結束，後面不再讀。

如果用字串長度來填會怎樣？範例用 node:http 開一個小伺服器（第 13 課詳講），兩個網址回同一個 JSON，差別只在 Content-Length 怎麼算：/chars 用 body.length，/bytes 用 Buffer.byteLength(body)。執行後比較兩行「收到」的結尾：

$ node examples/content-length.ts
body.length = 25 Buffer.byteLength = 29
/chars 收到： {"name":"拿鐵","price":
/bytes 收到： {"name":"拿鐵","price":110}

「拿鐵」在字串裡算 2，在 UTF-8 裡是 6 個位元組，差了 4。/chars 的標頭說 body 有 25 個位元組，伺服器實際送了 29 個，客戶端照標頭只讀 25 個，最後 4 個位元組 110} 被截掉，JSON.parse 就失敗了。這正是第一節那張表的情況：Content-Length 屬於「位元組數」那一列，填進來的卻是「UTF-16 code unit 數」，英文商品兩者相等，所以只有中文商品壞掉。

正確做法是 Buffer.byteLength(body)；更省事的是根本不自己設，res.end(body) 時 Node 會自己算。要自己設時（例如先寫標頭再分段寫 body），一律用位元組數。

到這裡處理的都是文字：先把位元組解成字，或把字算成位元組。咖啡機上傳的紀錄卻根本不是文字，裡面的位元組直接代表數字。

咖啡機的二進位紀錄怎麼讀？杯數為什麼變成負數？

不是所有資料都是文字。咖啡機的感應器、收據印表機、圖片和壓縮檔的檔頭，都用固定位置的位元組表示數字，這種格式叫二進位格式。為什麼不用文字？以機台編號 300 為例，寫成文字是 "300" 三個字元，數字變大字元就變多，讀的人還要一個字一個字轉回數字；寫成二進位只要固定 2 個位元組，放在固定位置，讀的人直接拿來用。資料比較小、解析比較快，對記憶體和頻寬都有限的機器很重要。

讀這種格式要知道兩件事：每個數字佔幾個位元組，以及這幾個位元組的先後順序，叫位元組順序（endianness）。先看第一件。一個 uint16（無號 16 位元整數）佔 2 個位元組，16 個位元能表示 0–65535。300 寫成 16 進位是 0x012c（0x 開頭是 16 進位的寫法，和 Buffer 那節的 hex 一樣，每兩位數字剛好是一個位元組：01 和 2c）。這兩個位元組要放進記憶體或檔案時，誰放前面？有兩種擺法：

兩種擺法都有人用，位元組本身也看不出是哪一種，所以只能靠格式文件。格式文件一定會寫清楚每個欄位在第幾個位元組、佔幾個位元組、用哪一種順序，照著選 Buffer 對應的方法。方法名稱就是這三件事拼起來的：read 加上有號（Int）或無號（UInt），加上位元數，再加上 BE 或 LE，參數 offset 是從第幾個位元組開始讀：

方法讀什麼範圍
readUInt8(offset)1 個位元組，無號0–255
readUInt16BE(offset)／LE2 個位元組，無號0–65535
readUInt32BE(offset)／LE4 個位元組，無號0–4294967295
readInt32BE(offset)／LE4 個位元組，有號（最高位元代表負號）−2147483648–2147483647

表格最後兩列是開場「杯數變成負數」的原因。同樣 4 個位元組、32 個位元，無號的版本全部拿來表示大小；有號的版本把最高的那個位元拿來表示正負，最高位元是 1 就是負數，所以正數最多只到 21 億多。範例 endian.ts 依序示範三件事：用兩種順序讀同樣兩個位元組、把 30 億寫進 4 個位元組再分別用無號和有號讀、從只有 3 個位元組的 Buffer 讀 4 個位元組：

$ node examples/endian.ts
BE（高位在前） 300
LE（低位在前） 11265
<Buffer b2 d0 5e 00> readUInt32BE = 3000000000 readInt32BE = -1294967296
長度不夠： RangeError ERR_BUFFER_OUT_OF_BOUNDS
  • 第一、二行：同樣的 01 2c，順序選錯就從 300 變成 11265，而且不會報錯，只會默默算錯。
  • 第三行：30 億超過 21 億，寫進去後最高位元是 1（b2 寫成 2 進位是 10110010）。用 readUInt32BE 讀回 30 億；用 readInt32BE 讀，最高位元被當成負號，變成 −1294967296，也就是 30 億減掉 232。為什麼剛好差 232？有號 int32 把最高位元的權重當成 −231，無號時則是 +231，兩者差 2×231 = 232，所以同樣的位元組讀成有號，就是無號值減掉 232。累計杯數跨過 231（約 21 億）時，不論是真實資料裡長期累加的計數器，還是驗收用的測試資料，用有號讀就會變負數，這就是開場那個 bug；練習 2 的測試就刻意放了超過 231 的值。
  • 第四行：讀超過結尾會丟 RangeError，錯誤碼是 ERR_BUFFER_OUT_OF_BOUNDS。

第四行引出讀不可信資料時的兩個檢查。咖啡機上傳的資料可能傳到一半斷線，所以讀之前要先檢查長度：讓 RangeError 直接漏出去，錯誤訊息只會說越界，不會說出「哪裡不對」；先檢查才能回報「資料長度 30，不是一筆 12 個位元組的整數倍」這種看得懂的訊息。另外如果長度剛好被截在一筆紀錄的邊界，迴圈只讀完整的部分就不會報錯，最後一筆就這樣被默默丟掉，所以要明確檢查「長度是不是一筆的整數倍」，練習 2 就要求這樣做。

旗標：一個位元一個開關

二進位格式除了數字，還常用一個位元組裝好幾個是非值。咖啡機的紀錄要記「熱飲嗎」「加濃縮嗎」，每個問題只需要 0 或 1，各用一整個位元組太浪費，於是一個位元組的每個位元各代表一個開關，叫旗標（flags）。bit0 是最右邊那個位元，往左依序是 bit1、bit2。

要讀其中一個開關，就用位元 AND 運算子 &：兩邊同一個位置都是 1，結果那一位才是 1。拿一個「只有要看的那一位是 1」的數字去 AND，其他位元就全被遮成 0，結果不是 0 就代表那一位有開（0b 開頭是 2 進位的寫法，0b10 就是 2）：

const flags = 0b011              // bit0 = 1、bit1 = 1
const hot = (flags & 0b01) !== 0      // true：bit0 有開
const extraShot = (flags & 0b10) !== 0  // true：bit1 有開

不要寫成 flags === 1 來判斷熱飲：它比的是整個位元組，只要別的位元也開著（兩個旗標都開是 3，未來格式加了 bit2 是 5），判斷就錯了。格式文件寫「其他位元不用管」時，正是要你用 & 只看自己那一位。

咖啡機的紀錄讀得出來了。最後一個 bug 回到給前端的訂單列表 API：它的「下一頁」標記要放進網址，網址只能放文字，資料要怎麼放進去，又怎麼防有人亂改？

訂單列表的「下一頁」標記怎麼放進網址？

訂單列表會用 cursor 分頁（第 14 課詳講）：回應附上一個 nextCursor，客戶端要下一頁時原樣帶回 ?cursor=…。伺服器把「這一頁最後一筆的 createdAt 和 id」包進去，下次從那之後開始查。這種 cursor 叫不透明 cursor（opaque cursor）：客戶端不需要、也不應該理解內容，只要原樣傳回。這樣伺服器以後改排序欄位、改內容格式，客戶端都不用改。

要讓客戶端「原樣傳回」，cursor 得是一個能直接放進網址的字串。直接把 JSON 放進網址不行，引號、大括號、冒號都要跳脫，網址變得又長又難處理。常見做法是把 JSON 先變成位元組，再用 base64url 寫成文字：

Buffer.from(JSON.stringify({ createdAt: '2026-10-31T08:00:00.000Z', id: 42 })).toString('base64url')
// 'eyJjcmVhdGVkQXQiOiIyMDI2LTEwLTMxVDA4OjAwOjAwLjAwMFoiLCJpZCI6NDJ9'

這裡把 Buffer 那節留下的 base64 講完。base64 用 64 個字元（A–Z、a–z、0–9、+、/）表示位元組：每 3 個位元組（24 個位元）切成 4 段、每段 6 個位元，6 個位元剛好有 64 種值，各對應一個字元。所以 base64 約是原本的 1.33 倍長，比 hex 的 2 倍省；最後不足 3 個位元組時，結尾用 = 補齊。

問題出在 +、/、= 這三個字元。用一般的 base64 放進網址前要先跳脫，否則 + 會被當成空白、/ 和 = 會打亂網址解析。base64url 把 + / 換成 - _，也不補 =，產生的字串可以直接放進網址，這就是 cursor 用它的原因。

base64 不是加密：任何人把字串貼進解碼工具都能看到、也能改內容再編回去。cursor 裡不能放客戶端不該看到的東西，伺服器也要把它當成不可信的輸入。要防止竄改，就加上 HMAC 簽章（Auth 課第 2 課）。

開場那個「改了幾個字就 500」的 bug 就出在這裡：伺服器以為 cursor 一定是自己發出去的，解開就直接用。解碼不可信的 cursor 時，每一步都可能出錯，而且錯法不只一種：

  • Buffer 解碼很寬鬆：Buffer.from(s, 'base64url') 碰到不認得的字元會默默略過，不會報錯（Buffer.from('aGk!!', 'base64url') 解出 hi）；它也接受一般 base64 的 + /（Node 文件有寫）。要嚴格，就先用正規表示式 /^[A-Za-z0-9_-]+$/ 檢查字元。
  • JSON.parse 會丟 SyntaxError；解出來可能是 null、數字、陣列，或欄位型別不對。
  • 每一種壞輸入都要轉成同一種自己的錯誤（例如 InvalidCursorError），API 才能統一回 400。讓 SyntaxError 漏出去，使用者亂改網址就會變成 500，還會在 log 裡製造假警報。

三點合起來就是解碼的順序：先檢查字元，再解 base64url，再包住 JSON.parse，最後逐一驗證欄位型別，任何一步失敗都丟同一種錯誤。練習 3 照這個順序修好 cursor。

💡 實務上：看到 eyJ 開頭的字串，多半是 base64 的 JSON
JSON 物件以 {" 開頭，編成 base64 後幾乎都是 eyJ 開頭；分頁 cursor、登入用的 JWT token（三段用 . 隔開，前兩段就是 base64url 的 JSON）都常長這樣。除錯時用 Buffer.from(s, 'base64url').toString() 解開看內容，比猜快得多。但正式環境的 token 不要貼到網路上的線上解碼工具，那等於把登入憑證交給陌生網站。反過來設計 API 時，要假設一定有人會解開你的 cursor 來看，裡面只放排序需要的欄位。

這一節防的是外面送進來的壞資料。開場的四個 bug 都有了答案，最後反過來看自己這一側：自己建立和比較 Buffer 時，哪些寫法會把不該外流的東西送出去。

自己建立、比較 Buffer 時，會洩漏什麼？

第一個風險在建立 Buffer。Buffer.alloc(n) 建立 n 個位元組並全部填 0。Buffer.allocUnsafe(n) 省掉填 0 這一步，所以比較快，但 Node 文件寫明它的內容沒有初始化：拿到的那塊記憶體之前可能被別的程式碼用過，裡面殘留的可能是別人的請求、密碼或金鑰。如果你建了一個 allocUnsafe 的 Buffer，只寫了前半段就送出去或寫進檔案，後半段的殘留資料就跟著外流了。所以只有在你馬上會把每個位元組都寫滿時才用 allocUnsafe，那時填 0 純屬浪費；其他時候一律用 Buffer.alloc，絕對不要把沒寫滿的 allocUnsafe Buffer 送出去或寫進檔案。

第二個風險在比較。咖啡機上傳紀錄時帶著一把 API key，伺服器要比對它對不對。比較祕密值（API key、簽章）不要用 === 或 buf.equals()：它們從頭一個一個比，可能在第一個不同的位元組就停下來，所以「前面對了越多個位元組」，比較就花越久。差距雖然極小，攻擊者送大量請求、統計回應時間，就能一個位元組一個位元組猜出整把 key。要用 crypto.timingSafeEqual(a, b)，不管內容哪裡不同，花的時間都一樣；兩邊的位元組長度不同時它會直接丟錯，所以要先處理長度（Auth 課第 2 課詳講）。

到這裡，三個資料入口需要的工具都齊了：逐段解碼、讀二進位紀錄、安全地編解碼 cursor。練習就是把它們做成正式版本。

練習

在 learn/ 執行 node check.mjs node 11 建立 work/11/，裡面有內文的範例（examples/）和三題的起始檔。

練習 1：匯入門市的訂單檔時，資料一段一段到達。line-decoder.ts 的 LineDecoder 要把它切成一行一行：push(chunk) 回傳「這段資料讓哪些行完整了」（陣列），end() 在資料結束時回傳最後沒有換行的那一行（[last]，沒有就 []）。現在的版本有兩個 bug：字被切在兩段之間時變成 �，以及 Windows 的 \r\n 換行會在行尾留下 \r（\r 和 \n 也可能分在兩段）。修好它。測試會從每一個位元組位置切段，也會檢查 push 當下就回傳已完整的行，不能等到 end() 才一次回傳；資料在字的中間結束時，end() 要把解碼器裡剩下的位元組也解出來（會變成 �），不能默默丟掉。只去掉行尾的 \r，行裡前後的空白要保留。

練習 2：完成 parse-reading.ts 的 parseReadings(buf)，解析咖啡機上傳的紀錄。每筆 12 個位元組、數字都是 big-endian：位置 0–1 是 uint16 機台編號；2 是 uint8 杯型（1=S、2=M、3=L）；3 是 uint8 旗標（bit0 熱飲、bit1 加濃縮，其他位元不用管）；4–7 是 uint32 時間戳記（Unix 秒，也就是 1970-01-01 00:00 UTC 起算的秒數）；8–11 是 uint32 累計杯數。回傳每筆的 { machineId, size, hot, extraShot, timestamp, totalCups }。長度不是 12 的倍數時丟 RangeError，訊息要提到 12；杯型不是 1–3 時也丟 RangeError。測試的累計杯數會超過 231，也會傳入大 Buffer 中間的一段（subarray），只能讀、不能修改它。

練習 3：修好 cursor.ts。encodeCursor({ createdAt, id }) 要產生只含 base64url 字元的字串；decodeCursor(s) 要確認字串只含 base64url 字元、內容是 JSON 物件、createdAt 是 toISOString() 格式的時間字串、id 是正整數，成功時只回傳 { createdAt, id }（cursor 裡多出來的欄位不要），任何一項不符都丟 InvalidCursorError（檔案裡已經定義好），不能讓 SyntaxError 或 TypeError 漏出去。提示：new Date(s).toISOString() === s 可以確認格式，但無效的日期呼叫 toISOString() 會丟 RangeError，要先擋掉。

練習 4：'拿鐵'.length 是多少？用 UTF-8 存成檔案要幾個位元組？

✓ length 數的是 UTF-16 code unit，常用中文一個字 1 格，所以是 2；UTF-8 裡常用中文一個字 3 個位元組，所以是 6（Buffer.byteLength('拿鐵')）。「一個字一個位元組」只對英數字成立；「中文 2 個位元組」是 Big5 或 UTF-16 的算法，不是 UTF-8。

練習 5：伺服器寫了 res.setHeader('Content-Length', body.length)，英文商品都正常，「拿鐵」的回應在客戶端 JSON.parse 失敗。為什麼？

✓ 客戶端照 Content-Length 讀到那麼多位元組就停，「拿鐵」多出的 4 個位元組讓 JSON 結尾被截掉。改用 Buffer.byteLength(body)，或乾脆不設，讓 res.end(body) 自己算。中文在 body 裡，不在標頭裡；charset 只告訴客戶端怎麼解碼，不會改變它讀幾個位元組。

練習 6：const head = buf.subarray(0, 3) 之後執行 head.fill(0)，原本的 buf 會變嗎？

✓ subarray 只是「看同一塊記憶體的另一個視窗」，不複製，所以 buf 的前 3 個位元組也變成 0。要獨立的複本用 Buffer.from(buf.subarray(0, 3))。Buffer 的內容可以隨意修改，它不是不可變的。

常見錯誤

  • 用 string.length 當位元組數：Content-Length、大小限制、位元組上限都會算錯，而且只有非英文資料才出錯。用 Buffer.byteLength()。
  • 以為 subarray 是複本：交出去被改，原資料跟著壞。需要獨立的資料時複製一份。
  • 每段資料各自 toString()：切在字中間就變成 �，資料永久損壞。用 StringDecoder、TextDecoder 的 { stream: true }、setEncoding('utf8')，或全部收完再解碼。
  • 忘了位元組順序或有號／無號：讀出的數字錯了卻不會報錯。照格式文件選 BE／LE、UInt／Int，並用已知的資料寫測試。
  • 把 base64 當加密：任何人都能解開、修改。不能放祕密，收到時要當不可信的輸入驗證；要防竄改就加簽章。
  • 相信 Buffer.from(s, 'base64') 會檢查輸入：不合法的字元會被默默略過。需要嚴格時自己先檢查字元。
  • 把 allocUnsafe 的內容直接送出去：可能夾帶之前留在記憶體裡的別人的資料。預設用 Buffer.alloc。

補充與查表

  • 檢查一段位元組是不是完整的 UTF-8：buffer.isUtf8(buf)（import { isUtf8 } from 'node:buffer'，Node 24 可用），範例 split.ts 的第二行就是用它。收到外部上傳的檔案、要拒絕不是 UTF-8 的內容時會用到。
  • Buffer 的 slice()：和 subarray() 一樣共用記憶體，Node 文件已標示棄用，不要用。要切一段用 subarray()，要複本用 Buffer.from(buf.subarray(…)) 或 Uint8Array.prototype.slice。
  • SlowBuffer：在 v24.0.0 改成執行時就印出棄用警告（DEP0030），舊程式碼裡看到它就換成 Buffer.allocUnsafeSlow()。

小結

  • 字元、UTF-16 code unit、UTF-8 位元組是三種不同的長度，英文資料三者剛好相等，所以 bug 只在中文和 emoji 出現。後端的大小限制和 Content-Length 都是位元組，用 Buffer.byteLength() 算；varchar 數的是字元，驗證前先問清楚上限是誰訂的、用哪一種算法。
  • Buffer 是 Uint8Array 的子類別，原封不動保留位元組，能在 UTF-8、hex、base64、base64url 之間轉換；subarray 共用記憶體，concat 產生新的。
  • 一段一段到的資料不能各自解碼：用 StringDecoder、TextDecoder 的 stream 模式，或先接起來再解碼，結束時記得收尾。
  • 讀二進位格式要照格式文件選對位元組順序和有號／無號，先檢查長度是不是一筆的整數倍，用 & 判斷旗標。
  • base64url 適合把 cursor 放進網址，但不是加密；解碼外部輸入時檢查字元、包住 JSON.parse、驗證欄位型別，所有錯誤轉成同一種錯誤。
  • 預設用 Buffer.alloc；比較祕密值用 crypto.timingSafeEqual。

  }
}

✓ 只有 ENOENT 是「沒有菜單」，其他錯誤（EACCES、JSON 格式壞掉）要包成有路徑、有 cause 的錯誤丟出去，維運才查得到。c 錯在先檢查再讀是 TOCTOU，檢查完檔案還是可能被刪；權限和格式錯誤也照樣進 catch 被吞掉。（第 10 課）

練習 9：同事把存訂單改成「暫存檔再 rename」，說這樣就是原子寫入了。這段哪裡會出事？

const tmp = '/tmp/orders.json.tmp'
await writeFile(tmp, JSON.stringify(orders))
await rename(tmp, path)

✓ 暫存檔要放在同一個資料夾、每次用隨機名字（例如 randomUUID()），失敗時刪掉。跨檔案系統 rename 會 EXDEV，改成複製再刪除就不是原子的。a 錯在同一個檔案系統上 rename 會一步蓋過舊檔；先刪掉反而會有一段時間沒有檔案。（第 10 課）

練習 10：老闆想把會員點數存在 points.json，API 要開在兩台機器上，尖峰每秒幾十筆加點。怎麼做最恰當？

✓ 多台機器、寫入頻繁，正是該交給資料庫的情況。兩台機器沒有共用的磁碟，鎖檔看不到彼此；就算放在 NFS，「已經存在就失敗」也不一定可靠。c 錯在鎖檔只管得到同一台機器上的程序。（第 10 課）

練習 11：外送平台的 API 規定商品名稱最多 30 個位元組，超過就截斷。後台用 name.length <= 30 驗證，中文長名稱送過去後還是被截斷，怎麼改？

✓ 上限由外部 API 決定，單位是 UTF-8 位元組：常用中文一個字 3 個位元組，emoji 多半 4 個。前後端照同一種算法驗證，測試資料放一筆中文和一筆 emoji。a 錯在「中文 2 個位元組」是 Big5 的算法，UTF-8 裡 10 個中文字就有 30 個位元組。（第 11 課）

練習 12：門市上傳訂單檔，小檔從來沒事，大檔偶爾有幾筆名字出現 �。接收的程式如下，原因是？

let text = ''
req.on('data', (chunk) => { text += chunk.toString() })
req.on('end', () => importOrders(text))

✓ 段落在哪裡切由作業系統和網路決定，不管字的邊界；切到一半的字解成 � 就永久壞掉。改用 StringDecoder、TextDecoder 的 { stream: true }，或先 Buffer.concat 再解碼並設大小上限。a 錯在編碼不對會整份亂碼，不會只有零星幾個 �。（第 11 課）

練習 13：訂單列表的 cursor 是 { createdAt, id, storeId } 編成的 base64url，伺服器解開後用裡面的 storeId 查那家門市的訂單。這個設計最大的問題是？

✓ base64 只是編碼，不是加密，cursor 要當成不可信的輸入。門市由伺服器依登入身分決定，cursor 只放排序需要的欄位；要防竄改就加 HMAC 簽章。b 錯在 base64url 本來就沒有 +、/、=，這正是它適合放進網址的原因。（第 11 課）
