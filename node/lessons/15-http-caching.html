階段 4：HTTP 服務 · 第 15 課

HTTP 快取與條件請求

咖啡店的 App 每次打開都會呼叫 GET /menu 抓菜單。菜單一天只改一兩次，伺服器卻每秒都在回同一份 JSON。維運提議在 API 前面放一層 CDN，讓它替你回菜單，你的 Node 程式只要偶爾被問一次就好。問題是 CDN 不懂你的業務，它只看回應標頭決定要存什麼、存多久：標頭寫對，伺服器輕鬆很多；標頭寫錯，王小明的「我的訂單」會出現在下一個客人的手機上。

這一課把咖啡店的菜單 API 一路改到可以放心放在 CDN 後面：先說清楚誰能存、存多久，再讓過期的快取用一句「變了沒」確認，接著推出英文菜單，最後處理後台兩位店長同時改菜單的問題。這些全部靠 HTTP 標頭完成，而且會一直用到同一個東西：代表菜單版本的 ETag。

這課的路線：
  1. 誰會把菜單存起來：從瀏覽器到 Node 之間有哪幾層快取，它們會帶來哪兩種風險。
  2. 怎麼告訴快取規則：用 Cache-Control 讓菜單存 60 秒、讓「我的訂單」一律不被 CDN 存下來。
  3. 過期之後一定要重新下載嗎：用 ETag 問「變了沒」，沒變就回 304，不傳 body。
  4. 推出英文菜單：同一個 /menu 回兩種語言時，用 Vary 避免 CDN 把英文版給中文使用者。
  5. 兩位店長同時改拿鐵：把同一個 ETag 放進 If-Match，讓後存的人收到 412，而不是默默蓋掉別人；最後整理出問題時怎麼查。
這課會用到：
  • 第 12 課的標頭：請求和回應開頭的 名稱: 值 文字行，用 curl -i 可以看到原始回應。
  • 第 13 課的 node:http 伺服器：在送出 body 之前用 res.setHeader 設回應標頭。
  • 第 14 課的狀態碼選擇與 problem details：錯誤一律回 application/problem+json，帶 type、title、status、detail。

放了 CDN 之後，菜單會被誰存起來？

要讓別人替你回菜單，先要知道「別人」是誰。HTTP 快取（HTTP cache）指的是：某個中間人把收到的回應存起來，下次有人發出同樣的請求，它直接拿存著的那份回應，不再去問你的伺服器。前端每天都在用它，只是多半沒注意：DevTools 的 Network 分頁裡，狀態欄寫著 (disk cache) 或 (memory cache) 的那些請求，根本沒有離開瀏覽器。

從 App 發出 GET /menu，到請求抵達你的 Node 程式，路上可能經過好幾層會存回應的伺服器：

這幾層分成兩種，差別在「一份存著的回應會給幾個人」。

第一種是私有快取（private cache），也就是瀏覽器（或 App 的 HTTP 客戶端）自己的快取。它只存這個使用者收到的回應，也只拿來回這個使用者，所以就算存了個人資料，也不會跑到別人那裡。

第二種是共用快取（shared cache），一份存著的回應會給很多使用者。維運提議的 CDN 就是這種。CDN 的全名是 Content Delivery Network：一群分散在各地的伺服器，替你保存並提供內容，使用者連到離自己最近的節點，不用每次跨海連到你的伺服器。另一種常見的共用快取是反向代理（reverse proxy）：一台擋在你的伺服器前面、替它接收並轉送請求的伺服器，例如 Nginx（部署課第 12 課）。它不只轉送，也可以設定成把回應存起來。

快取的好處很直接：使用者拿到回應比較快、流量比較省、你的伺服器負載比較低。代價是兩種風險，這一課的每個標頭都在控制其中一種：

  • 舊資料：店長已經把拿鐵改成 120 元，快取裡存的還是 110 元那份，客人看到的是舊價格。
  • 給錯人：共用快取把王小明的 GET /me/orders 存起來，下一個請求同一個網址的人拿到的是王小明的訂單。這是資安事故，比舊資料嚴重得多。

這些快取都在你的伺服器外面。你沒辦法登入使用者的瀏覽器刪掉某筆快取，也沒辦法從程式裡叫 CDN「剛剛那份不算」。你唯一能做的，是在每個回應上用標頭寫清楚規則，而回應一送出去，規則就跟著它走了，收不回來。（程式自己把查詢結果放進記憶體或 Redis，是另一種叫伺服器端快取的東西，差別見課末的補充與查表。）

那如果什麼規則都不寫，快取是不是就不會存？不是。HTTP 快取的規格 RFC 9111 允許快取對沒有明確期限的回應（例如帶 Last-Modified 的 200）自己估一個新鮮時間，叫啟發式新鮮度（heuristic freshness），規格舉的典型值是「距離上次修改時間的 10%」。不寫，等於讓別人替你決定。所以下一步，是讓每個回應都明確說出自己能不能存、存多久。

怎麼告訴快取：菜單存 60 秒，「我的訂單」一律不存？

規則寫在 Cache-Control 回應標頭裡。它的值由幾個指令（directive）組成，用逗號分開，例如 Cache-Control: public, max-age=60。先從菜單開始，一次加一個指令。

菜單：存多久？

菜單的問題是「每個人都在抓同一份」，我們希望快取存下來直接回。但存多久要有個上限，不然店長漲價之後，客人可能好幾天都看到舊價格。max-age=60 就是這個上限：回應存下來之後的 60 秒內，它是新鮮的（fresh），快取可以直接拿來回，完全不問你的伺服器。超過 60 秒，這份回應就過期（stale）了，快取不能直接用它，要先向伺服器重新驗證（revalidation）：問一句「我手上這份還是最新的嗎」。怎麼問，是下一節的主題。

60 秒是一個業務取捨：值越大，伺服器越輕鬆，但店長改價格後，客人最久要等這麼久才看到新價格。咖啡店的菜單漲價晚一分鐘生效可以接受，所以選 60。如果是限時搶購的庫存，可能連 5 秒都嫌長。

菜單：誰可以存？

光寫 max-age，還沒說清楚共用快取能不能存。菜單每個人看到的都一樣，存在 CDN 讓所有人共用正是我們要的，所以加上 public：明確表示這份回應可以快取，共用快取也可以存。菜單的完整標頭就是 Cache-Control: public, max-age=60。

「我的訂單」：不能讓 CDN 存

GET /me/orders 正好相反：每個人拿到的內容都不同，一旦被共用快取存下來，就是開場說的「王小明的訂單出現在別人手機上」。有兩個指令可以選：

  • private：只能存在單一使用者的私有快取。CDN、反向代理不能存，瀏覽器可以。
  • no-store：任何快取都不能存，包括瀏覽器。

「我的訂單」是個人資料，也沒有需要留在瀏覽器裡重複使用的理由，所以寫 private, no-store：CDN 不存，瀏覽器也不存。如果內容因人而異、但讓瀏覽器存一下能省流量（例如使用者的頭像網址清單），才會只寫 private。

這裡有兩個跟直覺不同的規則，都和「個人資料」有關：

第一，請求帶了 Authorization 標頭（例如登入後送的 token）時，共用快取預設不會拿存著的回應回它。但這個保護有例外：回應明確寫了 public、s-maxage 或 must-revalidate 時，共用快取就可以用。所以「反正有帶 token，CDN 不會存」不成立，個人資料一寫 public，保護就沒了。

第二，Cookie 也一樣。Cookie 是伺服器用 Set-Cookie 回應標頭請瀏覽器保存的一小段資料，瀏覽器之後每次請求都會自動帶回來，常用來記住登入狀態（Auth 課第 4 課）。很多人以為帶 Set-Cookie 的回應不會被快取，但 RFC 9111 第 7.3 節寫明 HTTP 規格並不禁止。如果回應帶 Set-Cookie 又寫了 public, max-age=60，CDN 可能把這份回應連同 A 的 Cookie 一起給所有人，等於把 A 的登入狀態送給別人。帶 Set-Cookie、或依 Cookie 回不同內容的回應，一律 private 或 no-store。

no-cache 的字面意思很容易誤會。它不是「不要快取」，而是「可以存，但每次使用前都要先問過我」。真的不想讓任何地方存下來（個人資料、付款結果），要用 no-store。

到這裡用到的指令，加上之後查資料會遇到的幾個，整理成下表。查表用，不用背：

指令意思（RFC 9111）
max-age=60存下來之後 60 秒內是新鮮的，不用問伺服器
s-maxage=300只給共用快取看的 max-age，會蓋過 max-age
public明確表示可以快取，共用快取也可以存
private只給單一使用者：共用快取不能存，瀏覽器可以
no-cache可以存，但每次使用前都要先向伺服器重新驗證
no-store任何快取都不能存這個回應
immutable新鮮期間內內容不會變，連使用者按重新整理都不用重新驗證（RFC 8246），用法見課末

💡 實務上：每個路由的 Cache-Control 都是一個要做的決定
新增 API 時，code review 常問的一句是「這個回應會因人而異嗎？」會的話就是 private 或 no-store，不確定也先選保守的那邊：把個人資料放上 CDN 是資安事故，晚一分鐘看到新菜單只是體驗問題。後台、管理介面這類流量小又常變的 API，通常直接 no-store，不值得為了省一點流量去調快取。咖啡店要接 CDN 之前，先把「路由 → Cache-Control」列成上面那樣的表給團隊看，比事後查 CDN 為什麼給錯資料便宜得多。

菜單現在能被 CDN 存 60 秒了。但 60 秒一過，快取手上的菜單就過期，它得回頭問你的伺服器。菜單一天才改一兩次，絕大多數時候答案都是「沒變」，難道每 60 秒都要重新傳一次整份菜單？

60 秒過期之後，一定要重新下載整份菜單嗎？

不用。快取真正想知道的只是「我手上這份還能不能用」，這個問題可以只問、不重新下載。HTTP 把這種「帶著條件發出、伺服器依條件決定怎麼回」的請求叫條件請求（conditional request）。要讓它成立，需要三樣東西：

第一，伺服器要能替每一版菜單取一個名字，客戶端才說得出「我手上是哪一版」。這個名字叫 ETag（entity tag），是伺服器在回應裡附上的版本標記，例如 ETag: "4Czwyn…"。規則只有一條：內容一樣，ETag 就一樣；內容變了，ETag 就變。

第二，客戶端要有地方說出它手上的版本。快取重新驗證時，會把存著的 ETag 放進 If-None-Match 請求標頭送出去，意思是「如果你現在的版本不是這個，才把內容給我」。

第三，伺服器要能只回答「沒變」。ETag 相符時，伺服器回 304 Not Modified：「沒變，繼續用你手上那份」，不帶 body。快取收到 304，就把手上那份重新當成新鮮的，再用 60 秒。

ETag 怎麼算？

ETag 的要求是「內容一樣就一樣、內容變了就變」，最直接的做法是用內容本身算出來。這種「從內容算出代表值」的工具叫雜湊（hash）：它把任意長度的資料變成固定長度的值，同樣的輸入一定得到同樣的結果，輸入只要差一個字，結果就完全不同。把雜湊結果轉成 base64url（第 11 課）這種只含英數字和 -、_ 的字串，就能放進標頭。Node 的 crypto.hash() 可以一次算完一小段資料：

import { hash } from 'node:crypto'

const body = JSON.stringify(menu)
const etag = `"${hash('sha256', body, 'base64url')}"`   // 雙引號是 ETag 格式的一部分

這三行有三個容易寫錯的地方。

雙引號不能少。ETag 的格式規定值要用雙引號包起來。"abc" 是強 ETag（strong），代表兩份內容一個位元組都不差；前面加 W/ 的 W/"abc" 是弱 ETag（weak），代表「意思一樣」，位元組不一定相同，例如同一份內容壓縮過。沒有雙引號的 abc 不是合法的 ETag，快取無法正確比對。強弱的差別在下面的 304 規則和後面的 If-Match 都會用到。

不能用時間戳記或亂數。這樣算出來的 ETag，內容沒變也會變，客戶端帶來的舊 ETag 永遠對不上，每次都回 200 和整份 body，等於沒做。

每次請求都用當下的內容算。如果只在啟動時算一次存起來，店長改了菜單，ETag 卻沒變，客戶端帶舊 ETag 來問會一直拿到 304，永遠看不到新菜單。這比沒做還糟。

動手看一次。在 learn/ 執行 node check.mjs node 15 建立 work/15/，到 work/15 執行 node examples/etag-server.ts（一個回「今日特調」的小伺服器，算 ETag 的方式和上面一樣），另開一個終端機用 curl 觀察。第一次請求不帶條件，看回應裡的 etag；第二次把這個 ETag 放進 If-None-Match，看狀態碼變成什麼：

第二次拿到 304，沒有 body，但 etag 和 cache-control 都還在。這不是巧合，是 304 的規則。

回 304 時要遵守什麼規則？

這個範例伺服器只拿 If-None-Match 和 ETag 直接比是否相等，是簡化版。真正的快取送來的 If-None-Match 比這複雜，RFC 9110 對 304 和比對方式有幾條規則，練習 1 要全部處理。

304 沒有 body。它的意思就是「用你手上那份」，帶 body 沒有意義。Node 會替你把關：node examples/no-body-304.ts 在 304 的 res.end() 裡寫了文字，客戶端收到的 body 仍是空字串。

200 會帶的 ETag、Cache-Control、Vary，304 也要帶。快取收到 304 時，會用這些標頭更新自己存的那份，例如重新開始算 60 秒的新鮮期。304 少了 Cache-Control，快取就不知道這次能再用多久。（Vary 是下一節的主角。）

If-None-Match 可以是一串 ETag。快取可能存了同一個網址的好幾個版本，它會把這些 ETag 用逗號分開一次送來，問「這幾個裡面有沒有還能用的」，其中一個相符就算命中。值也可能是 *，代表「任何版本」，只要資源存在就算命中。

If-None-Match 用弱比較（weak comparison）：比對前去掉 W/，只看引號裡的值。為什麼要這麼寬鬆？因為 CDN 替你壓縮回應時，位元組變了，它常把你的強 ETag 改成弱 ETag 再傳給瀏覽器。瀏覽器之後帶著 W/"abc" 來問，你的伺服器算出來的是 "abc"。內容意思沒變，弱比較讓它照樣命中 304。

另一組舊的條件請求 Last-Modified／If-Modified-Since 用時間代替 ETag，新寫的 API 用 ETag 就好，原因見課末。

💡 實務上：304 省的是傳輸，不是查詢
用內容算 ETag，伺服器還是要查資料庫、組出整份 JSON 才知道 ETag，省下的只有傳輸。咖啡店的菜單很小，這樣就夠了；資料大、查詢貴的資源，可以改用資料表的 version 或 updated_at 欄位組成 ETag，先查這一個欄位就能決定要不要回 304。代價是你要保證每次修改都更新這個欄位。動手之前先用 curl -i 看一下：很多框架、反向代理和 CDN 已經會自動加 ETag、處理 304，不一定要自己寫。

到這裡，菜單的快取都建立在一個前提上：同一個網址，每個人拿到的內容都一樣。咖啡店接下來要推出英文菜單，這個前提就不成立了。

推出英文菜單後，CDN 為什麼把英文版給了中文使用者？

英文菜單有兩種做法：開一個新網址 /en/menu，或是沿用 /menu，依請求決定回哪個語言。瀏覽器每次請求都會帶 Accept-Language 標頭，說明使用者偏好的語言，伺服器依它挑一個版本回，這種做法叫內容協商（content negotiation）。回應再用 Content-Language 標頭說明這份是哪個語言。咖啡店選了第二種，App 不用改網址。

問題出在快取。快取找「同樣的請求」時，預設只用「方法＋網址」當鑰匙，看不到 Accept-Language。假設 CDN 上的菜單剛過期，第一個打開菜單的是英文使用者，CDN 就把英文版存在 GET /menu 這把鑰匙下。接下來 60 秒，所有中文使用者請求 GET /menu，鑰匙一樣，拿到的全是英文菜單。

解法是 Vary 回應標頭：它告訴快取「這個回應會因為哪些請求標頭而不同」。回應帶 Vary: Accept-Language，快取就會把請求的 Accept-Language 也加進鑰匙，中文版、英文版分開存。上一節說 304 也要帶 Vary，就是因為快取靠它知道這份回應是用哪把鑰匙存的。

ETag 也要跟著分開。中文版和英文版是不同的內容，ETag 必須不同；不然英文使用者拿著中文版的 ETag 來問，伺服器比對相符就回 304，他會繼續看中文。只要用「這個語言版本的內容」算 ETag，兩個版本的 ETag 自然不同，不需要額外處理。

剩下的工作是讀懂 Accept-Language，這也是練習 2 要寫的部分。瀏覽器送的值長這樣：

Accept-Language: zh-TW,zh;q=0.9,en-US;q=0.8,en;q=0.7
  • 用逗號分開好幾個語言，q 是偏好程度（0 到 1，沒寫就是 1），要依 q 由高到低挑，不是照出現順序。q=0 代表「不要這個語言」，要跳過。
  • 語言代碼不分大小寫；en-US、en-GB 的主要語言都是 en，比對時要看第一段。
  • 都不支援時用預設語言，不要回錯誤：菜單用中文顯示，總比 App 打不開好。
Vary 列的標頭值越分散，快取越沒用。Vary: User-Agent 幾乎每個瀏覽器版本都不同，等於每個人一份；Vary: Cookie 也一樣。內容真的因人而異時，用 private 比較直接。

同樣的問題也會出現在壓縮和 CORS：只要依某個請求標頭回不同內容，就要把它列進 Vary，常見的例子見課末。

到這裡，讀菜單的這一側都處理好了：CDN 存得住、過期了問得便宜、不同語言不會混。最後一個問題出在寫入：店長在後台修改菜單的時候。

兩位店長同時改拿鐵，怎麼不讓後存的人蓋掉先存的人？

後台的品項編輯頁是這樣運作的：打開頁面時 GET 品項，表單填好目前的值，店長改完按儲存，前端用 PUT 把整筆品項送回去（PUT 的語意是「用這份整個換掉」）。兩位店長同時打開同一個品項時會發生什麼？node examples/lost-update.ts 模擬這個情況，執行後看最後一行的價格：

$ node examples/lost-update.ts
A、B 讀到： { id: 2, name: '拿鐵', price: 110 }
A 漲價成 120 → { id: 2, name: '拿鐵', price: 120 }
B 改名成「拿鐵（燕麥奶）」→ { id: 2, name: '拿鐵（燕麥奶）', price: 110 }
最後： { id: 2, name: '拿鐵（燕麥奶）', price: 110 } ← A 的漲價不見了

B 只想改名，但他送回去的是整筆品項，裡面的價格是他打開頁面時讀到的 110。他的 PUT 晚到，就把 A 剛改好的 120 蓋回 110。A 以為漲價成功了，B 不知道自己蓋掉了別人的修改，沒有任何人收到錯誤。

這就是 PostgreSQL 課第 19 課的 lost update（更新遺失），只是發生在 HTTP 這一層。資料庫交易救不了它：交易只能保護同一個請求裡的讀和寫，而這裡的「讀」和「寫」是兩個分開的 HTTP 請求，中間隔著店長思考、打字的好幾分鐘。你不可能讓一個資料庫交易開著等使用者好幾分鐘。

樂觀鎖：送出時再確認沒人改過

既然不能在讀的時候就鎖住，那就反過來：讀的時候不鎖，讓每個人自由打開編輯；送出修改時，伺服器再檢查「從你讀到現在，有沒有人改過」，有就拒絕。這種做法叫樂觀鎖（optimistic concurrency），「樂觀」是指它假設衝突很少發生，所以平常不付鎖的代價，真的衝突時才處理。

要檢查「有沒有人改過」，需要一個版本號。我們手上已經有了：前面替菜單算 ETag 的方法，也能套在單一品項上。編輯頁 GET 品項時，伺服器用這個品項的內容算出 ETag 放在回應裡，品項一改 ETag 就變，正好就是版本號。HTTP 的寫法是讓客戶端把讀到的 ETag 放進 If-Match 請求標頭，意思是「只有在目前的版本是這個時，才執行我的修改」，和 If-None-Match 剛好相反：

伺服器依 If-Match 的比對結果決定回什麼：

情況回應
If-Match 和目前的 ETag 相符（或是 * 且資源存在）修改，回 200 和新的 ETag，客戶端下次修改不用再 GET
不相符412 Precondition Failed：請求帶的前提條件不成立（RFC 9110），不修改
沒帶 If-Match428 Precondition Required：伺服器要求這個請求一定要帶條件（RFC 6585），錯誤訊息說明怎麼重送

沒帶 If-Match 為什麼要擋下來，而不是直接修改？因為只要有一個客戶端（舊版後台、同事寫的腳本）可以不帶條件就改，lost update 就又回來了。回 428 等於強制所有修改都要說出「我是根據哪一版改的」。

不相符時為什麼是 412，不是第 14 課用過的 409？409 Conflict 的意思是「這個請求跟資源目前的狀態衝突」，例如取消一筆已經做好的訂單，那是業務規則不允許，和你讀到哪一版無關。412 專指「你帶的條件不成立」，客戶端看到就知道問題出在自己手上的資料舊了，該重新 GET。用對狀態碼，前端才能寫出對的處理。

If-Match 的比對比 If-None-Match 嚴格，用強比較：W/ 開頭的弱 ETag 永遠不算相符。原因在兩者的後果不同。If-None-Match 比錯了，頂多讓客戶端用到一份「意思一樣」的回應；If-Match 是要不要讓一筆修改寫進去，弱 ETag 只保證意思一樣、不保證位元組相同，不足以證明「沒有人改過」，所以不算。

比對和修改之間不能有空隙

樂觀鎖還有一個容易寫錯的地方。如果處理函式先比對 ETag、接著 await 讀 body、最後才修改，兩個幾乎同時到的請求會這樣交錯：A 比對通過，進入 await；這時 B 也到了，資料還沒被改，B 也比對通過；接著兩個人先後修改，又回到 lost update。在單一 Node 程序裡，要讓「比對＋修改」之間沒有 await（例如先讀完 body，再一口氣比對和修改）。資料在資料庫時，把條件寫進同一句 SQL，讓資料庫保證比對和修改是一起完成的：

UPDATE products SET price = $1, version = version + 1
WHERE id = $2 AND version = $3      -- $3 是從 If-Match 解出來的版本
-- 影響 0 列 → 版本不符（或品項不存在），回 412 / 404

後台如果是從另一個來源的 Vue 頁面呼叫 API，送 If-Match 和讀 ETag 還要多處理 CORS，做法見課末。

💡 實務上：多人會同時編輯的資料才需要樂觀鎖
最常用在後台的編輯頁：咖啡店的品項、內容管理系統（CMS）的文章、多位客服一起處理的工單，打開表單到按下儲存之間隔了好幾分鐘。前端收到 412 時不要只跳「錯誤」，要告訴店長「這筆資料剛被別人修改」，重新載入最新內容，並保留他剛填的值讓他決定要不要再送，不然他打了半天的內容就白費了。只有本人會改的資料（個人設定）通常不需要；庫存扣減、點數加減這類「在目前的值上加減」的操作，用 UPDATE … SET stock = stock - 1 讓資料庫原子地完成，比要使用者帶 ETag 重試更合適。設計 API 時先問 PM：「兩個人同時改同一筆，後存的人應該看到什麼？」答案決定要不要做、412 時畫面怎麼呈現。

菜單 API 該有的標頭到這裡都齊了。但快取住在你的伺服器外面，出問題時你看不到它，只能從標頭推回去。

客人說「改了價格還是看到舊的」，要從哪裡查起？

接上 CDN 之後，客服最常轉來的就是這類回報。查的順序是由外往內，一層一層確認是誰給了這份回應：

  • 使用者說「改了價格還是看到舊的」：先用 curl -i 直接打你的伺服器，看 Cache-Control 和 ETag；再打 CDN 的網址，看回應的 Age 標頭（這份回應在快取裡放了幾秒）。有 Age 而且大於 0，通常就是快取給的。如果 Age 還沒超過 max-age，這是規則允許的舊資料，等它過期，或縮短 max-age。
  • 304 一直沒出現：連打兩次比對 ETag，不一樣就是 ETag 算法有問題（時間、亂數、物件的 key 順序不固定）。
  • 別人的資料出現在畫面上：最嚴重的快取事故。檢查個人化的回應是不是 public 或沒寫 Cache-Control，修好之後還要請 CDN 清除（purge）已經存著的回應，因為標頭只影響之後的請求。
  • DevTools 的 Network 分頁：狀態欄的 304 是重新驗證成功；(disk cache) 是新鮮期內直接用、沒有發出請求，伺服器的 log 看不到它。

接下來的練習，就是把這一課的三個標頭親手做進咖啡店的菜單 API：先做 ETag 和 304，再做英文菜單，最後做後台的樂觀鎖。

練習

在 learn/ 執行 node check.mjs node 15 建立 work/15/。http-utils.ts 有 sendJson、回 problem details 的 sendProblem、讀 JSON body 的 readJson，menu.ts 是菜單的型別，這兩個檔案不用改。三題依序做：練習 2、3 會用到練習 1 寫的 etag.ts。

練習 1：先完成 etag.ts：etagOf(body) 依內容算出用雙引號包住的強 ETag；noneMatch(header, etag) 判斷 If-None-Match 標頭是否命中，要處理沒有標頭、逗號分開的清單（逗號後面不一定有空白）、*、W/ 開頭的弱 ETag。再改 menu-cache.ts 的 GET /menu：回應帶 ETag 和 Cache-Control: public, max-age=60；命中時回 304，同樣帶這兩個標頭。createApp 收到的 menu 陣列之後可能被改，測試會在伺服器執行中漲價，舊 ETag 要拿到 200 和新的 ETag。

練習 2：改 menu-lang.ts 的 GET /menu，依 Accept-Language 回中文（zh-TW，預設）或英文（en）品名，每項是 { id, name, price }，name 是選到的語言的品名（英文在 nameEn）。依 q 值由高到低挑第一個支援的語言（q=0 的跳過），語言代碼不分大小寫，en-US 這類要對到 en、zh-* 對到 zh-TW，都不支援就用 zh-TW。回應帶 Content-Language（zh-TW 或 en）、Vary: Accept-Language、用這個語言版本的內容算的 ETag，並支援 If-None-Match → 304（304 也要帶 Vary）。

練習 3：改 menu-update.ts 的 PUT /menu/:id，加上樂觀鎖：沒帶 If-Match 回 428；If-Match 和品項目前的 ETag 不符回 412，不修改；相符（清單裡有一個相符，或是 *）才修改，回 200、修改後的品項和新的 ETag。If-Match 用強比較，W/ 開頭的不算相符。錯誤都用 sendProblem。測試會讓兩個請求的標頭先到、body 晚一點才送，所以比對 ETag 和修改之間不能有 await。

練習 4：一個回應帶 Cache-Control: no-cache，瀏覽器會怎麼處理？

✓ no-cache 的意思是「使用前一定要先問過伺服器」，存著的那份加上 ETag 就能換來 304。完全不存是 no-store，個人資料要用它；直接使用不問伺服器是 max-age 還沒過期時的行為。

練習 5：登入後的 GET /me 回應帶了 Set-Cookie: session=…，又設了 Cache-Control: public, max-age=60，網站前面有 CDN。會發生什麼事？

✓ RFC 9111 明寫 Set-Cookie 不會阻止快取，public 又明確允許共用快取存它，結果就是 A 的資料和登入 Cookie 給了別人。有些 CDN 預設會跳過帶 Set-Cookie 的回應，但那是各家的設定，不是規格保證。CDN 會不會存 API 回應取決於你的標頭和 CDN 設定，不是「永遠不會」。

練習 6：店長 B 帶著舊的 If-Match 送出修改，為什麼回 412 而不是 409？

✓ RFC 9110 把 412 定義為「請求標頭裡的條件在伺服器上判定為假」，正好描述 If-Match 不符；客戶端程式可以依 412 自動重新 GET 再提示使用者。409 描述的是業務規則上的衝突，和有沒有帶條件無關。409 不限 POST，任何方法都能用。

常見錯誤

  • 個人資料用 public，或乾脆沒寫 Cache-Control：共用快取會把 A 的資料給 B，沒寫時快取還可能自己估新鮮時間。個人資料用 private 或 no-store，每個回應都明確寫出來。
  • 把 no-cache 當成不快取：no-cache 會存，只是每次要重新驗證。不想被存用 no-store。
  • 以為帶 Set-Cookie 或 Authorization 就不會被 CDN 存：規格不保證，寫了 public 更是明確允許。登入後的回應一律 private 或 no-store。
  • ETag 用時間戳記、亂數，或啟動時只算一次：前兩種讓 304 永遠不會出現，後一種讓客戶端永遠拿到舊資料。每次用目前的內容（或版本欄位）算。
  • ETag 忘了雙引號、304 忘了帶 ETag 和 Cache-Control：快取無法正確比對和更新。
  • 依標頭回不同內容卻沒加 Vary：CDN 會把第一個人拿到的版本給所有人。
  • 修改的 API 沒有防 lost update：後存的人默默蓋掉先存的人，沒有任何錯誤。要求 If-Match，不符回 412、沒帶回 428。
  • 先比對 ETag，await 之後才修改：同時到的兩個請求都會通過比對。比對和修改之間不要有 await，或讓資料庫用 WHERE version = $n 一次完成。
  • 把 HTTP 快取和伺服器端快取混在一起：Redis 快取由你的程式控制、隨時能清；HTTP 快取在你的伺服器外面，回應一送出就收不回來，只能等它過期或請 CDN 清除。

小結

  • 快取分私有（瀏覽器）和共用（CDN、反向代理），風險是舊資料和給錯人；它們在你的伺服器外面，你只能用回應標頭告訴它們規則，不寫也會被估一個新鮮時間。
  • Cache-Control 決定誰能存、存多久：公開資料 public, max-age，個人資料 private 或 no-store。no-cache 是「每次重新驗證」，no-store 才是「不存」；帶 Set-Cookie 或 Authorization 不會自動阻止快取。
  • 過期後用條件請求確認：ETag 依內容算、加雙引號；If-None-Match 命中回 304，沒有 body、照樣帶 ETag、Cache-Control、Vary；If-None-Match 用弱比較，可以是清單或 *。304 省傳輸，不省查詢。
  • 依請求標頭回不同內容要加 Vary，各版本的 ETag 也要不同；Vary 的值越分散，快取越沒用。
  • 修改用同一個 ETag 搭配 If-Match 做樂觀鎖：相符才改並回新 ETag，不符 412，沒帶 428；強比較；比對和修改之間不能有空隙。

下一課處理大資料：用 stream 一段一段讀寫，不把整個檔案放進記憶體，並學會背壓，讓快的一方等慢的一方。

補充與查表

主線用不到、但實務上和查資料時會遇到的細節，查表用，不用背。

  • HTTP 快取和伺服器端快取：把資料庫查詢結果存在程式的記憶體或 Redis（一種放在記憶體、多個程序共用的鍵值資料庫）裡，叫伺服器端快取。它省的是你的伺服器去查資料庫的時間，由你的程式決定什麼時候失效，隨時能清（系統設計課第 5 課、NestJS 課第 19 課）。HTTP 快取存在你的伺服器外面，你只能用回應標頭告訴它規則，一旦送出就收不回來。兩者可以同時用。
  • 前端打包檔與 index.html：
    資源Cache-Control理由
    /assets/index-B3f9a1cD.jspublic, max-age=31536000, immutable檔名含內容的雜湊（Vite build 的輸出就是這樣），內容一改檔名就換，所以舊檔名可以存一年
    /index.htmlno-cache它指向最新的 js 檔名，每次都要確認，但沒變時可以用 304 省下傳輸
    前端部署最常踩的坑在 index.html：如果它被快取很久，使用者拿到的舊 HTML 會指向已經被刪掉的舊 js 檔名，畫面直接白掉，所以它要 no-cache，部署時舊的雜湊檔也先留著一陣子。
  • crypto.hash() 的版本：Node 的 crypto.hash() 從 24.13.1 起不再是實驗功能。
  • Last-Modified：舊的做法：另一組條件請求是 Last-Modified（最後修改時間）配 If-Modified-Since。它的時間格式只到秒，同一秒內改兩次就分不出來，而且「時間」不等於「內容」：內容改回原樣，時間還是變了。請求同時帶兩種時，規格要求忽略 If-Modified-Since，以 If-None-Match 為準。新寫的 API 用 ETag。
  • 其他常見的 Vary：依 Accept-Encoding 決定要不要壓縮時加 Vary: Accept-Encoding（第 16 課）；依請求的 Origin 回不同的 CORS 標頭時加 Vary: Origin（Auth 課第 5 課）。
  • 從瀏覽器送 If-Match 的 CORS 設定：從瀏覽器的 Vue 頁面送 If-Match 時，如果 API 在不同的來源（例如 localhost:5173 呼叫 localhost:3000），前端要讀到 ETag 標頭，伺服器得加 Access-Control-Expose-Headers: ETag；帶 If-Match 的請求也會先送預檢請求（Auth 課第 5 課）。
