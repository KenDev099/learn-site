階段 2：非同步與 event loop · 第 8 課

EventEmitter 與取消

咖啡店接了外送平台。流程是這樣：客人在平台上下單，平台打一支 API 到我們的伺服器，意思是「訂單 1024 做好了再回我」；伺服器收到後就開始等，等吧台把那一杯做好，再把結果回給平台。

上線一週後出了兩件事。第一件：伺服器的記憶體一天比一天大，log 裡反覆出現一行 MaxListenersExceededWarning，重啟就降回去，過幾天又長回來。第二件：某天集點服務出問題，結果不只集點失敗，整台伺服器直接結束，所有客人都點不了餐。

兩件事都出在同一個地方：我們用事件來串程式，卻沒想清楚三件事。第一件出在「等訂單 1024 做好」的那段 handleRequest，第二件出在結帳付款後通知吧台與集點的那段。沒想清楚的三件事是：事件的處理出錯時錯誤去哪裡、等完之後誰把掛上去的東西拿掉、平台不等了要怎麼停。這一課從頭把那段程式寫對，最後寫出 waitForReady(board, orderId, { signal, timeoutMs })（練習 1）：等到了、等太久、對方不等了，三種結局都乾淨收尾。同一個平台還會把新訂單一筆一筆推過來，這個需求在練習 3 處理。途中會學到 Node 裡最常見的兩樣工具：負責發事件、聽事件的 EventEmitter，和負責取消一件還在等的事的 AbortSignal。

這課的路線：
  1. 伺服器要怎麼「等」吧台：事件是什麼、EventEmitter 怎麼發和聽，以及上線那段程式長什麼樣子。
  2. emit 之後監聽器什麼時候執行、集點服務掛了為什麼整台伺服器跟著結束：emit 是同步的，以及三種錯誤情況（第二件事故的答案）。
  3. 記憶體為什麼一天比一天大：監聽器洩漏與 MaxListenersExceededWarning（第一件事故的答案）。
  4. 能不能直接 await「訂單好了」、平台一直推新訂單怎麼一筆一筆處理：events.once 與 events.on。
  5. 平台不等了、等太久了怎麼停，三種結局怎麼都收尾：AbortSignal 與 cleanup；最後回頭判斷這件事該不該用事件。
這課會用到：
  • 第 7 課的程序結束規則：event loop 裡沒有東西撐著程序時 Node 就結束；unref() 的計時器不撐住程序；頂層 await 的 Promise 永遠不會完成時，以結束碼 13 結束。
  • TypeScript 課第 11 課的 AbortController：呼叫 abort() 時，所有拿到它 signal 的工作都收到取消通知。

範例在 work/08/examples/，先在 learn/ 執行一次 node check.mjs node 08 讓它複製出來，再到 node/practice/work/08 執行。

伺服器要怎麼「等」吧台做好訂單 1024？

先看清楚問題的形狀。處理外送請求的程式和吧台的程式是兩段不相干的程式碼：請求那邊想知道「1024 什麼時候好」，吧台那邊只知道「我剛做好一杯」，不知道誰在等、有幾個人在等。最笨的做法是請求那邊每 100ms 去問一次「好了沒」，這叫輪詢（polling）：問得太勤浪費資源，問得太疏又會晚知道。比較好的做法反過來：吧台每做好一杯就喊一聲，在乎的人自己聽。

這一聲「發生了某件事」的通知就叫事件（event）。發出通知的物件叫發送者（emitter），收到通知時要執行的函式叫監聽器（listener）。你在前端天天用這個模式：button.addEventListener('click', …) 裡按鈕是發送者、你傳的函式是監聽器；Vue 子元件 emit('update')、父元件 @update 也是。這種寫法叫觀察者模式（observer pattern），重點在發送者只管喊「發生了」，不需要知道誰在聽、有幾個人在聽。吧台不用為了外送平台改程式，正是我們要的。

Node 把這個模式做成內建模組 node:events 的 EventEmitter，而且核心 API 幾乎都建立在它上面：HTTP 伺服器每來一個請求就發 request（第 13 課），stream 每讀到一段資料就發 data（第 16 課），process 收到關機訊號時發 SIGTERM（第 21 課）。這課學的行為，之後每一課都會再遇到。

咖啡店的出餐看板就是一個 emitter。最常見的寫法是讓自己的類別 extends EventEmitter（繼承，TypeScript 課第 23 課），這樣看板就有了發事件、聽事件的方法。TypeScript 可以在角括號裡寫出每個事件帶什麼參數，下面寫的是「ready 事件帶一個 Order」，之後 emit('ready', …) 和 on('ready', …) 的參數都會被檢查。練習用的 order-board.ts 就是這段：

import { EventEmitter } from 'node:events'

type Order = { id: number, item: string }

class OrderBoard extends EventEmitter<{ ready: [order: Order] }> {
  ready(order: Order) {
    this.emit('ready', order)
  }
}

吧台做好一杯就呼叫 board.ready(order)，裡面用 emit 喊出 ready。想聽的人用下面這幾個方法：

方法作用
on(名稱, fn)加一個監聽器，每次發生都呼叫（addListener 是同一個東西）
once(名稱, fn)只聽一次：第一次呼叫前自動移除
off(名稱, fn)移除監聽器。要傳同一個函式，所以監聽器要先存成變數，寫在 on 裡的匿名函式移不掉
emit(名稱, ...參數)發出事件，依註冊順序呼叫每個監聽器；有人在聽回傳 true
listenerCount(名稱)目前有幾個監聽器，查洩漏時最常用

有了這些，上線的那段程式就很好懂了。每個外送請求進來，就在共用的看板上 on('ready') 掛一個監聽器，每次有訂單好了就比對 id，是自己那張就通知（這是 examples/leak.ts，為了單獨執行，看板用的是一般的 EventEmitter，事件直接帶訂單 id）：

// examples/leak.ts
const board = new EventEmitter()

function handleRequest(orderId: number) {
  board.on('ready', (id: number) => {
    if (id === orderId) console.log('通知客人：訂單', id, '好了')
  })
}

這段程式跑得起來，訂單好了也真的會通知。第一件事故就藏在它裡面，但要看出來，得先弄清楚一件事：吧台呼叫 emit 的那一刻，這些監聽器到底是什麼時候執行的？

emit 之後，監聽器是什麼時候執行的？

看板之外，結帳也用事件：付款成功後 shop.emit('paid', 訂單 id)，吧台、集點、統計各掛一個監聽器。第二件事故就發生在這裡，所以接下來用 shop 來看 emit 的時機。

前端的直覺多半是「emit 把事件丟出去，等一下再處理」，像 setTimeout 那樣排進佇列。不是這樣。emit 當場、依註冊順序把每個監聽器呼叫完，才執行 emit 的下一行。下面的範例在結帳時發 paid，掛了三個監聽器（第 2、3 個順便印出 this，細節見課末），執行後看「emit 之前」和「emit 之後」夾住了什麼：

// examples/sync-emit.ts
shop.on('paid', (orderId: number) => console.log('1. 吧台收到訂單', orderId))
shop.on('paid', function (this: EventEmitter, orderId: number) {
  console.log('2. 集點：一般函式的 this 是 emitter 嗎？', this === shop)
})
shop.on('paid', () => console.log('3. 統計：箭頭函式沒有自己的 this'))

console.log('emit 之前')
const had = shop.emit('paid', 42)
console.log('emit 之後，有沒有人在聽：', had)
$ node examples/sync-emit.ts
emit 之前
1. 吧台收到訂單 42
2. 集點：一般函式的 this 是 emitter 嗎？ true
3. 統計：箭頭函式沒有自己的 this
emit 之後，有沒有人在聽： true

三個監聽器全部夾在「emit 之前」和「emit 之後」中間，順序就是註冊順序。原因很單純：EventEmitter 內部替每個事件名稱存一個監聽器陣列，emit 做的事就是把那個陣列跑一遍、逐一呼叫，跟一般的 for 迴圈呼叫函式沒有兩樣。它完全沒有經過第 7 課的任何佇列，所以不管 event loop 當時在哪個 phase，結果都一樣。

這帶來一個直接的後果：監聽器慢，發送者就慢。如果某個監聽器做了 200ms 的同步計算，emit 就卡 200ms 才回傳；這 200ms 裡執行緒被佔住，整個 event loop 也跟著停，其他請求都得等。吧台程式呼叫 board.ready(order) 時，實際花的時間是「所有監聽器的時間加總」，而吧台的作者完全看不到這件事。看板上掛的監聽器越多，每次出餐就越慢；下兩節會看到，這個數字在洩漏時是會一直長的。

同步呼叫還有另一個後果，而且比變慢更嚴重：既然 emit 是在自己的呼叫堆疊裡直接呼叫監聽器，那監聽器 throw 的時候，錯誤會跑去哪裡？這就是集點服務那次事故。

集點服務掛了，為什麼整台伺服器跟著結束？

回到剛才的 shop：結帳在付款成功後 emit('paid')，吧台螢幕和集點服務各掛一個監聽器。監聽器出錯時有三種情況，行為都不一樣（v24.22.1 實測，範例 examples/error-event.ts、examples/async-listener.ts）。我們一種一種看，最後對回事故。

1. 監聽器同步 throw：錯誤從 emit 傳出來

shop.on('paid', () => { throw new Error('吧台螢幕斷線') })
shop.on('paid', () => console.log('集點（不會印出來）'))
shop.emit('paid')   // ← 這裡丟出「吧台螢幕斷線」，集點的監聽器沒有執行

上一節說過，emit 就是一個依序呼叫函式的迴圈。第一個監聽器 throw 了，迴圈就斷了，後面的監聽器根本沒被呼叫，錯誤沿著呼叫堆疊往上丟回 emit 的呼叫者。放到咖啡店裡看：吧台螢幕壞掉，結果客人沒集到點；錯誤還丟回了結帳的程式，可是結帳根本不知道有誰在聽，更不知道怎麼處理「吧台螢幕斷線」。如果結帳沒有 try/catch，這個請求就失敗了。（瀏覽器那套 EventTarget 在這裡的行為不同，見課末。）

2. error 事件：沒人聽就 throw

error 是 EventEmitter 特別處理的事件名稱，用來回報「這個物件本身出問題了」，例如連線斷了、檔案讀不到。emit('error', err) 時如果有 error 監聽器，就跟一般事件一樣呼叫它；如果沒有任何 error 監聽器，Node 直接把 err throw 出來。沒人接住，程序就結束：

$ node examples/error-event.ts
emit 丟出了： 吧台螢幕斷線
接下來 emit error，沒有人監聽……
file:///…/examples/error-event.ts:16
shop.emit('error', new Error('刷卡機故障'))
                   ^

Error: 刷卡機故障
Emitted 'error' event at: …

這是故意的設計。一般事件沒人聽就算了，但錯誤如果沒人聽時也安靜略過，你會在完全不知情的狀況下繼續用一個壞掉的連線。Node 寧可讓程序結束，逼你面對它。所以 Node 的規矩是：會發 error 的東西（伺服器、socket、stream、子程序），一定要掛 error 監聽器，至少記到 log。

3. async 監聽器 reject：沒有人在等它

監聽器寫成 async 函式時，呼叫它會回傳一個 Promise，函式裡的錯誤變成這個 Promise 的 reject。問題是 emit 只負責呼叫，不看回傳值，也不會 await。所以這個 Promise reject 時沒有任何人處理，變成 unhandled rejection（沒人處理的 rejection），而 Node 24 的預設行為是讓程序以結束碼 1 結束（第 18 課詳講）。執行後先看第一行，emit 已經回傳了，錯誤才在後面出現：

$ node examples/async-listener.ts
emit 已經回傳了，async 監聽器的 Promise 還沒 settle
…
Error: 集點服務逾時
$ echo $?
1

這就是那次事故的全貌。集點的監聽器是 async 的，裡面 await 一個打到集點服務的請求。集點服務掛掉、請求逾時，Promise reject，沒人接，Node 依預設讓整個程序結束，伺服器上所有進行中的請求一起陪葬。集點只是「順便」的功能，卻拖垮了點餐。

修法有兩層。第一層：在 async 監聽器裡自己 try/catch，把錯誤記到 log，不讓它變成 rejection。第二層是 EventEmitter 提供的安全網：建立 emitter 時傳 { captureRejections: true }，Node 會接住 async 監聽器的 rejection，改成發 error 事件。這樣錯誤至少有地方去，但別忘了第 2 種情況，error 事件還是要有人聽：

$ node examples/async-listener.ts --capture
emit 已經回傳了，async 監聽器的 Promise 還沒 settle
error 事件收到： 集點服務逾時
emit 不等 async 監聽器，也就是說 emit 回傳時，async 監聽器的工作還沒做完。需要「每個監聽器都做完、各自的錯誤都有人處理」時，不要用 emit，自己逐一呼叫並 await（練習 2）。

三種情況整理起來：同步 throw 會中斷後面的監聽器並丟回發送者；沒人聽的 error 會直接讓程序結束；async 監聽器的 rejection 沒人等，依預設也讓程序結束。共通點是，事件把錯誤和發送者切開了，你得替每一種錯誤安排好去處。

💡 實務上：接手專案時，先找「會發 error 卻沒人聽」的物件
工作中你很少自己 emit('error')，但天天在用會發 error 的東西：資料庫連線池、Redis（常拿來當快取）的 client、WebSocket、stream。咖啡店後台半夜 Redis 斷線一次，整個 Node 程序就跟著結束，常見原因就是 client 沒掛 error 監聽器。資深的人 code review 時會看兩件事：每個長期存在的連線物件有沒有 .on('error', …) 並記到 log；監聽器裡有沒有 async 函式卻沒有 try/catch，就像這次的集點監聽器。常見的資料庫和 Redis client 多半會自己重連，所以這個監聽器通常只要記 log；重點是不要讓一個外部服務的斷線變成整個程序結束。

第二件事故有答案了。回到第一件：記憶體一天比一天大，log 裡一直出現 MaxListenersExceededWarning，這跟上線那段 handleRequest 有什麼關係？

記憶體為什麼一天比一天大？

再看一次 handleRequest：每個請求都在共用的 board 上 on('ready')，但整段程式沒有任何一個 off。請求結束、回應送出之後，那個監聽器還掛在 board 上。

為什麼這會讓記憶體一直漲？JavaScript 的記憶體由垃圾回收（garbage collection，GC）管理：只要一個物件還能從某個「活著」的東西一路找到，GC 就不會回收它。board 是整個程序共用、一直活著的物件；它的監聽器陣列引用著每個監聽器；每個監聽器是閉包，記著外層的 orderId，以及它用到的其他東西，在真實程式裡常常包括整個請求物件。這一整串都還找得到，所以一個都收不掉。一天幾萬個請求，就有幾萬個早就沒用的監聽器堆在 board 上，記憶體一路漲。前面說過 emit 是同步逐一呼叫，所以每次出餐，吧台還要多呼叫幾萬個沒用的函式，越來越慢。這種「監聽器加了卻從不移除」的問題叫監聽器洩漏（listener leak）。

Node 幫你設了一條警戒線：同一個 emitter 的同一個事件加到第 11 個監聽器時（預設上限 EventEmitter.defaultMaxListeners 是 10），印出一次警告。範例模擬 12 個請求：

$ node examples/leak.ts
ready 監聽器數量： 12
(node:7643) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 ready listeners added to [EventEmitter]. MaxListeners is 10. Use emitter.setMaxListeners() to increase limit
(Use `node --trace-warnings ...` to show where the warning was created)

注意它只是警告：程序照常執行，第 12 個監聽器照樣加得上去，監聽器數量印出來就是 12。它是線索，告訴你「這裡可能有洩漏」，不是問題本身。遇到它時這樣查：

  1. 用 node --trace-warnings examples/leak.ts 執行，警告後面會印出 stack trace，其中 at handleRequest (…/leak.ts:9:9) 就是加上第 11 個監聽器的那一行。
  2. 想清楚這個監聽器「應該什麼時候拿掉」。只要一次就用 once；有明確的結束時機（請求結束、逾時、取消）就在那裡 off；或者交給下一節的 events.once／events.on 搭配 signal，它們結束時會自己移除。
  3. 用 listenerCount 寫測試確認：每種結束方式之後，數量都回到 0。

警告訊息自己建議了 emitter.setMaxListeners()，但 setMaxListeners(100) 只是把警戒線往後挪，洩漏還在，只是你看不到了。只有在你確定「同時會有很多正當的監聽器」時才調高，例如一個 emitter 本來就要給 50 個模組各掛一個。外送請求的監聽器不是這種情況：同時在等的請求可能很多，但每一個等完就該離開。

💡 實務上：洩漏通常是「重啟就好了」的那種問題
監聽器洩漏在本機幾乎測不出來，因為你只發幾個請求；上線後的樣子就是這次的事故：監控圖上記憶體一路往上爬，重啟就降回去，過幾天又爬上來。很多團隊的第一反應是排程定期重啟，那只是把問題延後。遇到這種圖，先搜尋 log 有沒有 MaxListenersExceededWarning，再找「在請求或連線裡 on、掛在共用物件上」的程式碼。新寫這類程式時，在測試裡加一行 listenerCount 斷言，比上線後追查便宜得多。

修法的核心是「每個監聽器都要有拿掉的時機」。在 handleRequest 裡手動 off 做得到，但結局一多（等到了、出錯了、平台不等了）就很容易漏掉某一條。Node 有沒有現成的工具，讓「等一次」這件事自己收尾？

能不能直接 await「訂單好了」，等完自動拿掉監聽器？

換個角度看 handleRequest 真正要的東西：它不是「每次有訂單好了都做某件事」，而是「等訂單好一次，然後繼續往下走，把結果回給平台」。「等一件事完成再繼續」正是 Promise 和 await 的形狀。所以問題變成：怎麼把一次事件變成一個 Promise？

直覺的寫法是自己包：new Promise(resolve => board.once('ready', resolve))。它在事件發生時會 resolve，但漏了兩件事：等的過程中 board 發了 error，這個 Promise 不會 reject：有別的 error 監聽器時它永遠卡著，沒有的話就是上一節的第 2 種情況，程序直接結束；而且沒有辦法叫它停，平台不等了，監聽器還是掛在那裡。node:events 提供的 events.once 把這些都處理好了：

events.once：等一次

import { once } from 'node:events'

const [order] = await once(board, 'ready')   // 回傳的是參數陣列，所以要解構

它回傳的 Promise 在事件第一次發生時 resolve，值是 emit 傳的參數組成的陣列，所以要用 [order] 解構出第一個。它幫你處理了三件容易漏的事：

  • 自動移除：等到之後，它掛的監聽器就拿掉了，不會洩漏。
  • error 變成 reject：等的過程中 emitter 發了 error，Promise 就以那個錯誤 reject。它在等的期間替你掛了 error 監聽器，所以不會變成上一節「沒人聽的 error」讓程序結束。
  • 可以取消：可以傳 { signal }，取消時 reject，錯誤的 name 是 AbortError、code 是 'ABORT_ERR'，取消的原因放在 err.cause。signal 是什麼、從哪裡來，後面「平台不等了」那一節會講，這裡先知道它支援就好。

但它有一個限制：它只看事件名稱。once(board, 'ready') 在任何一張訂單好了時就 resolve，不能只等訂單 1024。看板上同時有幾十張訂單在做，第一個好的多半不是你那張。要過濾，就得自己 on、自己比對 id、自己在每一種結局 off，這就是練習 1 的 waitForReady。它還缺 signal 這個零件，會在「平台不等了」那一節補齊。

「等一張訂單」的形狀清楚了。在回到 waitForReady 之前，先處理外送平台的另一個需求（練習 3）：它會把新訂單一筆一筆推給我們，這不是等一次，而是一直來。處理完這個，再回到 waitForReady 補上取消。

events.on：一筆一筆處理平台推來的新訂單

平台的新訂單從一個 feed 物件進來：每來一筆就 emit('order', 訂單)，平台結束推送時 emit('closed')，斷線時 emit('error', err)。每筆訂單都要寫進資料庫、通知吧台，是一段 async 的處理。

直接寫 feed.on('order', async order => { await handle(order) }) 會踩到前面兩個坑。第一，emit 不等 async 監聽器，所以每來一筆就馬上開始處理一筆，十筆同時在跑，順序也不保證；如果下游（資料庫、吧台系統）一次只承受得住幾筆，就會被壓垮。第二，handle 出錯變成沒人處理的 rejection，就是集點那次事故。我們要的是「一次處理一筆，處理完才拿下一筆，出錯就停下來」。

events.on 就是做這件事的。它回傳一個 async iterator。先說 iterator：它是一個可以「一個一個取值」的物件，for…of 就是在跟它要下一個值；async iterator 是取值要 await 的版本，用 for await…of 走訪，每一圈等到下一個值才進入迴圈本體（TypeScript 課第 10 課）。events.on 把「每發生一次事件」變成「迴圈拿到一筆」：

import { on } from 'node:events'

for await (const [order] of on(feed, 'order', { signal, close: ['closed'] })) {
  await handle(order)   // 這一筆處理完，才會拿下一筆
}

這幾行裡有四個重點：

  • 一次一筆：迴圈本體裡的 await 還沒結束，下一圈不會開始，所以訂單照收到的順序一筆一筆處理。跟 feed.on('order', async …) 每來一筆就同時開始一個完全不同。
  • close：列出代表「結束」的事件名稱，發生時迴圈正常結束，程式繼續往下走。沒寫的話，迴圈不知道什麼時候算完，平台收工了它還在等下一筆。
  • error 與 signal：emitter 發 error，迴圈丟出那個錯誤；signal 取消，迴圈丟出 AbortError。兩者都可以在迴圈外面用 try/catch 接住，錯誤不會沒人管。
  • 收尾：不論迴圈怎麼結束（close、error、取消、迴圈裡 throw 或 break），它都會移除自己掛的監聽器（本機驗證：三種事件的 listenerCount 都回到 0）。這正是上一節要的「自己收尾」。

還有一種狀況要想：處理得比事件來得慢時呢？例如平台尖峰時段每 10ms 推一筆，我們每筆要處理 100ms。for await 讓我們一次只處理一筆，但平台那邊不會因此停下來，事件照樣 emit。處理不完的事件會排進 events.on 自己的暫存，而對一般的 EventEmitter，這個暫存沒有上限（控制上限的 highWaterMark 選項為什麼對它沒用，見課末）。執行後看最後一欄「排隊中」的數字怎麼變：

$ node examples/on-buffer.ts      # 每 10ms 來一筆，每筆處理 100ms；數字每次會有點不同
處理完   2 筆，已經收到 18 筆，排隊中 16 筆（目前這筆 #2）
處理完   4 筆，已經收到 36 筆，排隊中 32 筆（目前這筆 #4）
處理完   6 筆，已經收到 54 筆，排隊中 48 筆（目前這筆 #6）
…

排隊的數量一直漲，記憶體也是。for await 只是讓你「一次處理一筆」，不會讓發送的那一端慢下來。能叫上游慢下來的機制叫背壓（backpressure）：消費端處理不完時，回頭告訴生產端先暫停。EventEmitter 沒有這個機制，stream 才有，第 16 課會學。所以 events.on 適合「事件來得不會比處理快太多」的情況；平台可能長時間推得比你快，就要改用有背壓的 stream 或佇列。

最後一個本機驗證的細節，練習 3 會用到：closed 之後、signal 取消之後，已經排在暫存裡的事件還是會一筆一筆交出來。也就是說，平台不等了、你取消了，迴圈不會立刻停，還會把排隊中的訂單繼續交給你處理。要取消後立刻停，每一筆開始前要自己檢查 signal（練習 3）。這裡已經是第二次提到 signal 了，下一節正式來看它。

平台不等了、等太久了：怎麼取消還在等的工作？

回到 waitForReady。平台打來「訂單 1024 好了再回我」，它不會無限期等下去：平台自己有逾時，時間到就斷線；客人也可能在平台上取消訂單。對方已經不等了，我們這邊如果還在等，那個監聽器、那個計時器就白白掛著，又回到洩漏。所以等待一定要能被「從外面叫停」，而且要有上限。

這就是 TypeScript 課第 11 課你自己寫過的取消機制：AbortController 是按下取消的那一方；它的 signal（一個 AbortSignal 物件）交給要被取消的工作；工作監聽 signal 的 abort 事件，取消時停下來並 reject。AbortSignal 本身也是一種事件發送者，只是它只會發一次 abort。好消息是 Node 的內建 API 已經直接接受 signal，不用每個都自己接，只是取消時丟出的錯誤不完全一樣：

API取消時 reject 的錯誤（v24.22.1 實測）
setTimeout（node:timers/promises）AbortError，cause 是 signal.reason
events.once、events.onAbortError，cause 是 signal.reason
fs.promises.readFile 等AbortError，cause 是 signal.reason
fetchsignal.reason 本身（逾時就是 TimeoutError）
child_process.spawn 等子程序被終止，發 error 事件（第 9 課）

signal.reason 是取消的原因：呼叫 controller.abort(原因) 時傳進去的值，沒傳就是一個名稱為 AbortError 的錯誤。表格的重點是：判斷「是不是被取消的」時，Node 內建 API 看 err.name === 'AbortError'，想知道原因再看 err.cause；fetch 是例外，直接丟出原因本身。examples/abort-apis.ts 會印出前三種和下面 AbortSignal.any 的錯誤。

逾時與合併：AbortSignal.timeout、AbortSignal.any

waitForReady 要停下來的理由有兩種：平台斷線，和我們自己設的等待上限。Node 提供現成的工具把這兩種理由變成同一個 signal：

  • AbortSignal.timeout(ms)：ms 毫秒後自動取消的 signal，reason 是名稱為 TimeoutError 的 DOMException。逾時（TimeoutError）和使用者取消（AbortError）分得開，呼叫端才能決定回 504 還是什麼都不回。
  • AbortSignal.any([a, b])：任何一個來源取消，合併的 signal 就取消，reason 跟著先取消的那個。典型用法：「客人斷線」或「最多等 5 秒」，哪個先到都停。
  • signal.throwIfAborted()：已經取消就丟出 signal.reason。適合放在每一步開始前，例如上一節 for await 迴圈每一筆的開頭。

合起來，處理外送請求時就是這兩行。req.signal 是 Node 24 的 http 請求物件提供的 signal，連線在回應完成前斷掉時會 abort，第 13 課細講：

const signal = AbortSignal.any([req.signal, AbortSignal.timeout(5_000)])
const order = await waitForReady(board, 1024, { signal })   // 客人走了或 5 秒到了，都會停
AbortSignal.timeout 的計時器不撐住程序（第 7 課的 unref）。如果程式唯一在等的就是它，event loop 認為沒事可做，程序直接以結束碼 13（還有沒完成的頂層 await）結束，catch 根本不會執行。試試 node examples/once-timeout.ts; echo $?。在伺服器裡這不是問題，因為伺服器本身撐著程序。

既然 signal 已經能帶逾時，為什麼練習 1 的 waitForReady 還要另外收 timeoutMs？因為這樣函式本身就保證有上限，呼叫端沒帶逾時也不會無限等；也藉這個機會練習自己清計時器。

有了 signal，waitForReady 的零件都齊了：自己 on('ready') 過濾 id、自己的計時器處理 timeoutMs、監聽 signal 的 abort。剩下的問題是，三條路裡任何一條先到，另外兩條掛上去的東西怎麼辦？

等到、逾時、取消：waitForReady 怎麼確保三條路都收尾？

一個「等某件事」的函式有三種結局：等到了、逾時、被取消。為了等，它掛了三樣東西：board 上的 ready 監聽器、signal 上的 abort 監聽器、逾時用的計時器。不論哪一種結局先發生，這三樣都要拿掉。漏了一個就是洩漏：等到訂單卻忘了 off，監聽器留在 board 上，就是第一件事故；resolve 了卻沒 clearTimeout，計時器時間到還是會觸發，對一個已經結束的 Promise 再 reject 一次，白白撐著程序；被取消卻沒移除 abort 監聽器，它就跟著 signal 活著。

最不容易漏的寫法是三條路共用同一個 cleanup()：任何一條路觸發時，先 cleanup，再 resolve 或 reject。這樣「要拿掉哪些東西」只寫在一個地方：

圖說最後那一點很常被忘。abort 事件只發生一次，就在取消的那一刻。signal 傳進來時如果已經取消（例如客人在你開始等之前就斷線了），你再 addEventListener('abort', …) 永遠等不到它，只能乾等到逾時，白白佔著資源。所以函式的第一行先檢查：if (signal?.aborted) return reject(signal.reason)，或呼叫 signal.throwIfAborted()，確定還沒取消才開始掛東西。

把這節和前面幾節合起來，就是練習 1 的 waitForReady：先檢查 signal；掛上 ready 監聽器（id 不符就不理）、計時器、abort 監聽器；三條路都先 cleanup 再結束。測試會用 listenerCount 和計時器檢查每一種結局都收乾淨了，這正好對應第一件事故的修法。

💡 實務上：取消只是「不等了」，不是「沒做過」
最常見的用法就是這課做的事：把逾時和客人斷線往下傳。API 要呼叫外部服務（外送平台、金流、地址查詢）時，一律帶 signal 和逾時，不讓一個慢的下游把你的請求全部卡住。逾時多長要看那個呼叫平常要多久，以及使用者願意等多久，可以問 PM 或看監控，不要每支 API 都抄同一個數字。要小心的是寫入：你取消了「等金流回應」，金流那邊可能已經扣款成功，所以讀取可以放心取消，付款、建立訂單這類寫入要能查得到結果或安全重試。同一個請求做兩次，結果跟做一次一樣，這個性質叫冪等，見系統設計課第 9 課。log 裡也要分得出逾時和使用者取消，排查時才知道是下游慢還是客人自己走了。

兩件事故都修好了。最後退一步問一個設計問題：結帳之後通知吧台、集點，一開始就該用事件嗎？

回頭看：通知吧台和集點，該不該用事件？

事件的好處是解耦（decoupling）：兩段程式不直接互相呼叫，改動一邊不用改另一邊。結帳只要 emit('paid', order)，吧台、集點、統計各自監聽；之後新增一個「開發票」的功能，只要多掛一個監聽器，不用改結帳的程式。代價是這課一路看到的事：

  • 流程看不見：讀結帳的程式，看不出 paid 之後會發生什麼，要全專案搜尋 'paid'。出問題時很難追。
  • 錯誤容易遺失：上面三種錯誤情況，任何一種沒處理好，不是拖垮發送者，就是錯誤沒人知道。集點那次事故就是這樣。
  • 同步 emit 拖慢發送者：監聽器越多、越慢，結帳就越慢。
  • 只在同一個程序裡有效：EventEmitter 的事件只存在記憶體裡。開了兩個程序（第 24 課）時，A 程序發的事件 B 程序聽不到；程序重啟時，還沒處理的事件就沒了，也沒有重試。要跨程序、不能遺失的通知要用佇列或 webhook（系統設計課第 16 課）。

判斷方式：結帳必須知道結果的事（扣庫存、寫訂單），直接呼叫函式並 await，失敗就讓結帳失敗；發生了「順便通知一下」、失敗也不影響主流程的事，才適合用事件，而且要決定好錯誤去哪裡。照這個標準，集點用事件可以，但它的監聽器必須自己接住錯誤；如果集點不能遺失（例如會員點數牽涉到錢），就該改成寫進佇列，而不是靠記憶體裡的事件。

補充與查表

主線用不到、但查資料或讀別人的程式時會遇到的細節。

EventEmitter 與瀏覽器的 EventTarget

瀏覽器的 EventTarget（addEventListener／dispatchEvent）在 Node 裡也有，AbortSignal 就是一個 EventTarget。兩者都同步呼叫監聽器，差別在監聽器同步 throw 時：EventEmitter 的 emit 會中斷、錯誤從 emit 丟出；EventTarget 的 dispatchEvent 則讓其他監聽器照樣執行，錯誤改成在下一個 tick 丟出、變成未捕捉的例外，程序一樣以結束碼 1 結束。

監聽器裡的 this

TypeScript 課第 1 課講過：一般函式的 this 由呼叫方式決定，箭頭函式沿用外層的。所以監聽器用一般 function 寫，this 是發出事件的 emitter（sync-emit.ts 第 2 個監聽器印出 true）；用箭頭函式寫，this 是外層的 this，在 ES module 頂層是 undefined。要拿 emitter 時，直接用變數比依賴 this 清楚。

events.on 的 highWaterMark

events.on 的 highWaterMark 選項預設值是 Number.MAX_SAFE_INTEGER，而且只對有 pause()／resume() 的 emitter 有作用，一般 EventEmitter 等於沒有上限。

events.addAbortListener

events.addAbortListener(signal, fn)：監聽取消，回傳一個 Disposable，也就是有 [Symbol.dispose]() 方法、用完要釋放的物件，呼叫它的 [Symbol.dispose]() 就移除監聽器。跟直接 addEventListener('abort', …) 比，別人在 signal 上呼叫 stopImmediatePropagation() 也擋不住它。

版本備註

  • events.once 的 signal 選項從 v15.0.0 開始支援。
  • events.on 的 close 選項從 v20.0.0 起支援。
  • events.addAbortListener 從 v24.0.0 起是 stable。
  • 本課的輸出與錯誤行為都在 v24.22.1 實測。

練習

練習 1：完成 wait-for-ready.ts 的 waitForReady(board, orderId, { signal, timeoutMs })。board 是 order-board.ts 的 OrderBoard，訂單做好時 emit('ready', order)。

  • 收到 order.id === orderId 的訂單才 resolve 那張訂單；別的訂單好了繼續等。
  • 超過傳進來的 timeoutMs 毫秒就 reject，錯誤的 name 是 'TimeoutError'（例如 new DOMException('…', 'TimeoutError')）。
  • signal 取消時 reject signal.reason；signal 一開始就已取消時立刻 reject。signal 可以不傳。
  • 不論哪一種結局，board 上的 ready 監聽器、signal 上的 abort 監聽器、計時器都要清掉。計時器要 clearTimeout，unref() 不算清掉（它只是不撐住程序，時間到還是會執行）。測試會檢查 listenerCount、getEventListeners(signal, 'abort') 和你開的計時器。

練習 2：起始的 safe-hub.ts 直接用 EventEmitter，第一個訂閱者壞掉就拖垮全部。改寫 SafeHub：subscribe(name, fn) 登記一個訂閱者，fn 可能是同步或 async 函式；publish(event) 呼叫每一個訂閱者，回傳的 Promise 在所有訂閱者都結束後才 resolve，而且永遠不 reject。任何一個訂閱者同步 throw 或 async reject，都不能影響其他訂閱者，錯誤交給建構子傳入的 onError(err, name)，name 是它訂閱時的名稱。測試期間不能出現 unhandled rejection。

練習 3：完成 order-feed.ts 的 consumeOrders(feed, { signal, handle })。外送平台的 feed 會 emit('order', 訂單)，結束時 emit('closed')，斷線時 emit('error', err)。

  • 每一筆都 await handle(order)，一次只處理一筆，依收到的順序；closed 時正常結束，回傳處理了幾筆。
  • feed 發 error 時以那個錯誤 reject；handle 丟錯時不再處理下一筆，以那個錯誤 reject。
  • signal 取消時：正在處理的那筆做完，之後一筆都不開始，reject 名稱為 AbortError 的錯誤；沒有訂單、正在等下一筆時取消，也要馬上 reject；已取消的 signal 一筆都不處理。
  • 不論怎麼結束，feed 上 order、error、closed 的監聽器都要是 0。

提示：events.on 加上 close 和 signal 選項可以處理掉大部分；剩下的一件事，回頭看「events.on：一筆一筆處理」那一節的最後一段。

練習 4：下面的程式印出的順序是？

shop.on('paid', () => console.log('A'))
shop.emit('paid')
console.log('B')

✓ emit 就是依序呼叫每個監聽器的普通函式呼叫，跟 event loop 的佇列無關，所以一定是 A 再 B。這也代表監聽器慢、監聽器 throw，都會直接影響 emit 的呼叫者。想延後執行要自己用 setImmediate 或 process.nextTick（第 7 課）。

練習 5：正式環境的 log 一直出現 MaxListenersExceededWarning: … 11 ready listeners added。同事說：「把 setMaxListeners(100) 加上去警告就沒了。」怎麼回應？

✓ 警告本身不會擋住任何東西（b 錯，第 11、12 個照樣加得上去），它是「可能有洩漏」的線索。調高上限（a）只是把線索藏起來，記憶體照漲。只有在確定同時有很多正當的監聽器時才調高。

練習 6：一支腳本只有這一行，執行後會怎樣？

await once(board, 'ready', { signal: AbortSignal.timeout(1000) })   // 沒有人會發 ready

✓ AbortSignal.timeout 的計時器不撐住程序，等 ready 的監聽器也不算，所以 event loop 沒有任何東西撐著，程序立刻結束，結束碼 13 代表頂層 await 沒完成。如果有別的東西撐著程序（例如伺服器），才會是 c：events.once 取消時丟 AbortError，原因在 cause；b 是 fetch 的行為。

常見錯誤

  • 以為 emit 是非同步的：emit 當場呼叫完所有監聽器。監聽器裡的同步重活會卡住發送者和整個 event loop。
  • async 監聽器 reject 沒人處理：emit 不 await 監聽器，rejection 變成 unhandled，程序以結束碼 1 結束。在監聽器裡 try/catch，或用 captureRejections: true 加 error 監聽器。
  • 會發 error 的東西沒掛 error 監聽器：一次 emit('error') 就讓程序當掉。伺服器、socket、stream、子程序都要掛。
  • 每個請求都 on 卻沒 off：監聽器和它記住的資料永遠收不掉。想清楚結束時機，在每一種結局都移除；off 要傳同一個函式。
  • 把 setMaxListeners 調大掩蓋洩漏：警告是線索。先用 --trace-warnings 找到來源。
  • 用 once 等事件卻沒處理 error 與取消：自己寫 new Promise(r => emitter.once('ready', r)) 不會在 error 時 reject，也停不下來；用 events.once 加 signal，需要過濾時自己處理三種結局。
  • 忘了檢查已經取消的 signal：abort 事件只發生一次，已取消的 signal 不會再發，要先看 signal.aborted。
  • 以為 for await + events.on 會讓上游變慢：它只是排隊，暫存沒有上限；取消後已排隊的事件還會交出來。
  • 監聽器寫成箭頭函式又用 this 取 emitter：箭頭函式沒有自己的 this，直接用 emitter 的變數。

小結

  • 事件讓吧台只管喊「做好了」、不用知道誰在等。EventEmitter 用 on／once／off／emit；emit 是同步的，依註冊順序當場呼叫每個監聽器，監聽器慢，發送者就慢。
  • 集點服務拖垮整台伺服器，是因為錯誤沒有去處。三種情況：同步 throw 從 emit 傳出、後面的不執行；沒人聽的 error 直接 throw；async 監聽器的 rejection 沒人等。修法是監聽器自己 try/catch，或 captureRejections 加 error 監聽器。
  • 記憶體一天比一天大，是每個請求都 on 卻沒 off。監聽器加了就要有拿掉的時機；MaxListenersExceededWarning 是洩漏的線索，用 --trace-warnings 找來源，不要只調高上限。
  • events.once 把一次事件變成 Promise（會處理 error、支援 signal、自動移除），但不能過濾；events.on 搭配 for await 一次處理一筆，close 決定何時結束，但暫存沒有上限，取消後已排隊的事件還會交出來。
  • Node 內建 API 接受 signal，取消時丟 AbortError、原因在 cause；AbortSignal.timeout 逾時、AbortSignal.any 合併來源；timeout 的計時器不撐住程序。
  • 「等某件事」的函式（像 waitForReady）要處理三種結局（等到、逾時、取消），共用一個 cleanup 全部收尾，還要先檢查已取消的 signal。
  • 結帳必須知道結果的事直接呼叫並 await；「順便通知」才用事件，而且要決定錯誤去哪裡。要跨程序、不能遺失的通知用佇列。
