階段 1：Node 與開發環境 · 第 2 課

程序與設定：參數、環境變數、輸出入與結束碼

咖啡店有一支夜間對帳腳本：每天凌晨三點，排程系統自動執行它，讀當天的訂單、算出合計，結果存成報表給會計。沒有人坐在螢幕前看它跑。月底會計對帳時發現三件怪事：報表裡夾著「第 2 行格式錯誤」這種不是資料的字；有幾天的報表只有前面一小段，後面不見了；而排程系統的紀錄上，每一天都寫著「成功」。

腳本的計算邏輯其實沒錯。出問題的是它和外界之間的溝通：誰啟動它、告訴它什麼、它把東西印到哪裡、結束時回報了什麼。後端程式幾乎都不是你手動點開來用的，而是被部署工具、排程、CI 或別的程式啟動，所以這些溝通管道寫錯，程式邏輯再對也會出事。這課的任務是把這些管道一條一條弄懂，讓咖啡店的程式能被別的程式正確地呼叫，學完你會知道上面三件怪事各是哪裡寫錯、怎麼修。

這課的路線：
  1. 執行 node 的那一刻，程式從外界拿到什麼：程序、父程序，以及參數、環境變數、三條輸出入管道、結束碼這四條溝通管道。
  2. 命令列參數：怎麼可靠地讀出「這一次要做什麼」，使用者把選項換順序、打錯名稱時不會讀亂。
  3. 環境變數與啟動時驗證：port、資料庫密碼這類「在哪個環境跑」的設定怎麼帶進程式；設定錯了為什麼要一啟動就停。
  4. stdin、stdout、stderr 與管線：結果和錯誤訊息為什麼要走兩條管道，這是報表混進錯誤訊息的原因。
  5. 結束碼與 process.exit()：排程怎麼判斷成功或失敗，為什麼 process.exit() 會讓報表少一截。
這課會用到：
  • 第 1 課的 node 檔名.ts、process.argv[2]、process.exitCode：用 node 執行檔案、從命令列拿參數、設定結束時回報成功或失敗的數字。
  • TypeScript 課第 4 課的自訂 Error 類別：class ConfigError extends Error 讓呼叫端用 instanceof 分辨是哪一種錯。

這課的範例在 node/practice/start/02/examples/。先在 learn/ 執行一次 node check.mjs node 02 建立 work/02/，之後的指令都在 work/02 裡執行。

執行 node 的那一刻，程式從外界拿到什麼？

要修對帳腳本，得先看清楚「排程執行它」這件事到底發生了什麼。硬碟上的 total.ts 只是一個檔案，裡面是一堆文字，本身不會做任何事。你（或排程）執行 node total.ts 時，作業系統把 node 載入記憶體開始跑，再由 node 去讀你的檔案。這個「正在執行中的程式」叫程序（process）。

同一個檔案可以同時變成好幾個程序。開兩個終端機各執行一次 node total.ts，就是兩個程序：各有各的記憶體，一邊改了變數，另一邊完全看不到。作業系統為了分辨它們，給每個程序一個編號，叫 PID（process id），Node 裡用 process.pid 讀得到。在終端機執行 ps 可以列出目前的程序，macOS 的「活動監視器」看到的也是這份程序清單；之後你要查「伺服器是不是還活著」「是哪個程序吃掉記憶體」，看的都是它。

程序不會憑空出現，一定是另一個程序把它啟動的。你在終端機打指令時，負責接收指令的 shell（macOS 預設是 zsh）就是啟動 node 的那一方，叫父程序（parent process），node 則是它的子程序。對帳腳本的父程序是排程系統，伺服器的父程序是部署工具。不管父程序是誰，它和子程序之間只有這幾條溝通管道：

由上往下對照這張圖，每一條管道回答父程序和子程序之間的一個問題：

  • 參數：這一次要做什麼。例如「對哪一天的帳」「點哪一杯」。Node 放在 process.argv。
  • 環境變數：在哪個環境跑。例如 port、資料庫網址、密碼。Node 放在 process.env。
  • stdin、stdout、stderr：資料從哪裡讀進來、結果和訊息往哪裡送。這是程序活著的時候一直開著的三條管道。
  • 結束碼（exit code）：程序結束時一定會交回給父程序的一個數字，告訴它成功了沒。

開場那三件怪事都出在這幾條管道上：錯誤訊息混進報表是輸出走錯管道，失敗卻顯示成功是結束碼回報錯了，報表少一截是程式結束的方式把還沒送完的輸出丟掉了。接下來依照程序的生命週期，從啟動時拿到的參數，一路講到結束時交回的結束碼。對帳腳本的參數太少看不出名堂，先用咖啡店另一支點單小工具的參數，看一次 node 拿到什麼：

$ node examples/argv.ts --size L 拿鐵
PID： 4821
argv： [ '/usr/local/bin/node', '/Users/you/…/work/02/examples/argv.ts', '--size', 'L', '拿鐵' ]
參數： [ '--size', 'L', '拿鐵' ]

你打的 --size L 拿鐵 被切成三個字串放進陣列，前面還多了兩個路徑。這些字串要怎麼變成「點一杯 L 的拿鐵」，就是下一節的問題。

命令列參數：怎麼可靠地讀出「這一次要做什麼」？

上一節的 process.argv 就是 Node 收到的命令列參數（command-line arguments）：指令裡程式名稱後面的那些字。切字的不是 Node，而是 shell：它用空白把指令切開，再交給 node；所以一個參數要包含空白，就要用引號包起來，例如 "冰 拿鐵"。陣列的前兩個固定是 node 執行檔和你的檔案的路徑，真正的參數從 process.argv.slice(2) 開始。

這一節就繼續用剛才那支點單小工具 order.ts 來練習。點單工具有品項、尺寸、數量好幾個參數，正好能看出「讀參數」哪裡容易出錯。它和對帳腳本用的是同一套機制。像這樣在終端機裡打指令使用、沒有圖形介面的程式，叫命令列工具，英文是 command-line interface，常縮寫成 CLI。

參數分兩種。以 - 或 -- 開頭、用來調整行為的叫選項（option），例如 --size L，或縮寫成一個字母的 -q 2；後面不接值、出現就代表「打開」的選項（例如 --hot）又常被叫做旗標（flag）。其他不帶名稱、靠位置決定意思的參數叫位置參數（positional）。

第 1 課用 process.argv[2] 直接拿參數，參數一多就會亂。假設你規定「第一個是品項、第二個是尺寸」，使用者實際會這樣打：

  • 換順序：--size L 拿鐵。這時 argv[2] 是 '--size'，被你當成品項。
  • 換寫法：--size=L。整串是一個參數，跟 --size L 的兩個參數長得不一樣。
  • 打錯名稱：--sise L。你的程式找不到 --size，就默默用預設的 M 杯。

每一種都要自己寫判斷，很容易漏。Node 內建的 util.parseArgs 把這些情況都處理好了：你宣告有哪些選項、各是什麼型別，它回傳整理好的結果（版本細節見課末）。

// examples/parse-args.ts
import { parseArgs } from 'node:util'

const { values, positionals } = parseArgs({
  options: {
    drink: { type: 'string' },
    qty: { type: 'string', short: 'q', default: '1' },
    hot: { type: 'boolean', default: true },
  },
  allowNegative: true,   // 讓 --no-hot 把 hot 設成 false
})
console.log(values, positionals)

$ node examples/parse-args.ts --drink 拿鐵 -q 2 --no-hot
[Object: null prototype] { drink: '拿鐵', qty: '2', hot: false } []
qty 的型別： string

執行後看 values：-q 2 被認成 qty，--no-hot 把 hot 設成 false，選項不管放在哪個位置都讀得到。宣告選項時用到的設定只有這幾個：

設定作用
type'string'（後面要接一個值）或 'boolean'（出現就是 true）。沒有數字型別
short一個字母的縮寫，-q 2 等於 --qty 2
default沒出現時的值，型別要跟 type 一致
strict預設 true：遇到沒定義的選項就丟出錯誤
allowPositionalsstrict 時預設 false：多出一個字就丟出錯誤

表上的 strict 決定了打錯時會怎樣。strict 模式下，使用者打錯不會被安靜忽略，而是丟出錯誤。這是好事：--sise L 打錯字時，你會想要程式直接說「沒有這個選項」，而不是默默做出一杯 M 杯。錯誤物件的 err.code 告訴你是哪一種錯：

輸入錯誤碼（err.code）
--tip 10（沒定義的選項）ERR_PARSE_ARGS_UNKNOWN_OPTION
--drink 拿鐵 外帶（多一個字）ERR_PARSE_ARGS_UNEXPECTED_POSITIONAL
--qty（後面沒有值）、--qty -1（值以 - 開頭）ERR_PARSE_ARGS_INVALID_OPTION_VALUE；負數要寫成 --qty=-1

丟出錯誤之後，還有兩件事 parseArgs 不會幫你做。第一件是把錯誤接住。Node 遇到沒接住的錯誤，會印出 stack trace，也就是錯誤發生時一層層的函式呼叫路徑。這是給工程師除錯用的，使用者看不懂。如果不接，使用者打錯一個字就會看到一大段 stack trace，看不出自己錯在哪。正確的做法是用 try／catch 接住，印一行看得懂的說明，再印出用法，並回報「用法錯誤」的結束碼（結束碼在後面「結束碼」一節講）。

第二件是驗證值。上面的輸出寫著 qty 的型別： string：參數從 shell 傳進來時就只是一串文字，parseArgs 也沒有數字型別，所以 -q 2abc 的 '2abc' 是完全合法的字串，它不會擋。你得自己確認它真的是正整數再轉成數字，而 JavaScript 內建的轉換函式對壞資料都很寬容：

parseInt('2abc')   // 2：讀到不是數字的字就停，前面的照收
Number('')         // 0：空字串變成 0
Number('1.5')      // 1.5：不是整數
Number('1e1')       // 10：科學記號也算數字
/^[1-9]\d*$/.test(qty)   // 只接受正整數的寫法：先檢查格式，通過才 Number(qty)

前四行都會讓錯誤的輸入「看起來像數字」而過關，所以做法和 TypeScript 課第 5 課一樣：先用正規表示式檢查整個字串的格式，通過了才轉數字。

品項也要驗證，這裡有一個不明顯的陷阱。價目表通常寫成一般物件 { 拿鐵: 110, … }，而一般物件會從原型（prototype）繼承 toString、constructor 這些屬性，所以 'toString' in menu 是 true，menu['toString'] 也不是 undefined。使用者打 --drink toString，用 in 或 menu[drink] !== undefined 檢查的程式就會讓它混過去。要用 Object.hasOwn(menu, drink)，它只看物件自己定義的屬性。

💡 實務上：營運腳本常常是你第一個 CLI
工作中很少從零寫給大眾用的命令列工具，比較常見的是團隊內部的營運腳本：補登漏掉的訂單、匯出上個月的報表、幫某個客人重設點數。這類腳本常由別人（同事、客服、值班的人）在緊張時執行，所以參數名稱要清楚、打錯要擋下來、--help 要看得懂。會寫入資料的腳本，資深工程師通常會先問「有沒有 --dry-run？」：先印出會改哪些資料，確認無誤再真的執行。只跑一次、只有你自己用的小腳本，就不用做到這麼完整。

參數適合放「這一次要做什麼」。但對帳腳本每次執行還需要另一類資訊：資料庫在哪裡、密碼是什麼。這些每次都一樣，而且開發機和正式機不同，不該每次都打在指令裡，這是下一節的環境變數要解決的。

每次都一樣的設定放哪裡？環境變數

上一節的參數是每次執行時由呼叫的人決定的；資料庫網址、port、API 金鑰則不一樣：同一台機器上每次都相同，換一台機器（你的電腦、測試機、正式機）才會不同。這類設定放在環境變數（environment variable）裡。

環境變數是一組「名稱＝值」，每個程序都有自己的一份，啟動時從父程序複製過來。Node 把它放在 process.env。可以這樣分辨該用哪一個：參數是「這一次要做什麼」（點哪杯飲料、對哪一天的帳），環境變數是「在哪個環境跑」（port、資料庫網址、金鑰）。

$ PORT=4000 DEBUG=false node examples/env.ts   # 寫在指令前面：只對這一個指令有效
PORT： "4000" string
DEBUG： "false"
if (process.env.DEBUG) 成立了！

$ export PORT=4000      # export：之後在這個終端機執行的指令都帶著它
$ echo $HOME            # shell 裡用 $名稱 讀環境變數

執行後看前兩行的型別：PORT 是字串 "4000"，不是數字 4000。環境變數和參數一樣，在作業系統裡就只是文字，所以 process.env 裡的值永遠是字串，沒設定的則是 undefined。第三行更容易出事：DEBUG=false 得到的是字串 'false'，而非空字串在 if 裡是 truthy，所以 if (process.env.DEBUG) 成立了。寫成 DEBUG=（等號後面什麼都不寫）則會得到空字串 ''。結論是：環境變數用之前一定要自己轉型，而且要明確比對，例如 === 'true'。

環境變數是怎麼一層一層傳下去的，決定了你在哪裡設定它才有效。子程序啟動時複製父程序的那一份，之後兩邊各自獨立，所以只能往下傳，不能往回傳：

  • PORT=3000 node a.ts：PORT 只放進 a.ts 這個程序的環境，shell 自己沒有這個變數。所以 PORT=3000 node a.ts && node b.ts 裡只有 a.ts 讀得到 PORT。
  • export PORT=3000：把 PORT 設在 shell 自己的環境裡，之後這個終端機啟動的每個程序都會複製到它。
  • 程式裡改 process.env.PORT，只改到自己這一份，啟動它的 shell 看不到。

為什麼設定要放在環境變數，而不是直接寫在程式碼裡？業界常引用的一份雲端應用程式設計原則叫 12-factor（The Twelve-Factor App），其中一條就是：跟環境有關的設定不寫死在程式碼裡，而是從環境變數讀。這樣同一份程式在你的電腦、測試機、正式機跑，只要換環境變數，不用改程式、重新部署；密碼也不會跟著程式碼進 git。部署課的第 11 課會講正式環境怎麼管這些值。但開發時每次執行都要在指令前打一長串環境變數，很快就會受不了。

開發時每次都要打一長串？.env 檔

解決這個麻煩，習慣的做法是把它們寫在專案裡的 .env 檔，一行一個 名稱=值，執行時讓程式讀進來。Node 24 可以直接讀，不用裝套件：

$ node --env-file=examples/demo.env examples/env.ts             # 檔案不存在時 node 不會啟動（結束碼 9）
$ node --env-file-if-exists=.env examples/env.ts                # 檔案不存在就略過
$ PORT=4000 node --env-file=examples/demo.env examples/env.ts   # PORT 是 "4000"：真正的環境變數優先

// 或在程式裡讀：預設讀工作目錄的 .env，檔案不存在會丟出 ENOENT
process.loadEnvFile()

第三行要特別看：真正的環境變數優先於 .env。.env 只補上還沒設定的值，已經從父程序拿到的不會被蓋掉。這個順序是刻意的：開發時 .env 提供預設值；到了正式環境，部署平台設的真正環境變數一定會生效，不會被誰忘了刪的 .env 蓋過。

.env 不能進 git：裡面通常有密碼和金鑰，進了 git 就等於公開給所有看得到這個 repo 的人，刪掉也還在歷史紀錄裡。把 .env 寫進 .gitignore，另外提交一份 .env.example，只列名稱和假的值，讓新同事知道要設定哪些東西。練習資料夾 node/practice/.env.example 就是這樣做的。
💡 實務上：.env 只在開發用，正式環境的值由部署平台給
新同事加入時，通常是複製 .env.example 成 .env、填入自己的值就能跑起來，所以這份範例要跟程式一起更新，不然大家會卡在「少設了一個變數」。正式機的密碼不會放在 .env 檔裡傳來傳去，而是由部署平台或機密管理服務注入成環境變數。萬一 .env 不小心推上 git，光刪檔不夠：裡面的密碼和金鑰要當作已外洩，馬上換新（rotate），再通知負責資安的人。

到這裡設定已經能從外面帶進程式了。但環境變數是人設定的，人會打錯、會忘記設，而 process.env 照單全收，不會有任何人替你檢查。下一節處理這個問題。

設定錯了，要在什麼時候發現？啟動時就驗證

上一節留下的問題用一個例子看：咖啡店的伺服器上線時，PORT 被打成 3000abc，ADMIN_TOKEN（管理 API 用的密碼）忘了設。如果程式是在用到的地方才直接讀 process.env，伺服器照樣啟動、看起來一切正常；等到半夜第一個人呼叫管理 API，才因為 token 是 undefined 而爆炸。這時離改設定的人已經好幾個小時，出事的地方又離真正的原因很遠，要查很久。

解法叫 fail fast（快速失敗）：程式一啟動，先把所有設定讀進來、全部驗證完，有任何一個不對就立刻結束，並說清楚哪裡錯；全部通過才開始提供服務。這樣錯誤在「部署的那一刻」就出現，部署工具會馬上看到「啟動失敗」並停止上線，舊版本繼續服務，改設定的人也還在旁邊。代價是啟動時多跑一段檢查，這幾乎沒有成本。

要做到 fail fast，實作上有五個要點，每一點都對應一個實際會踩的坑：

  1. 集中在一個地方：寫一個 loadConfig(env)，把字串轉成有型別的物件 { port: number, … }，其他程式只用這個物件，不再碰 process.env。這樣「所有設定都檢查過」才有保證，不會有某個角落偷偷讀到沒驗證的值。
  2. 參數傳 env，不要在裡面讀 process.env：測試可以直接傳一個物件進去，不用改全域狀態。
  3. 一次列出所有問題：遇到錯誤先收集起來，最後一起丟出。不然修好 PORT 重新部署，才發現 TOKEN 也錯了，一個設定錯誤就要部署一輪。
  4. 格式要嚴格：參數那一節看過的 parseInt('2abc') 是 2、Number('') 是 0；換成 PORT 就是 parseInt('3000abc') 得到 3000。這些都會讓壞設定看起來正常，驗證就形同虛設。
  5. 機密不印出來：token、密碼不管成功或失敗都不能出現在輸出裡，log 會被很多人和很多系統看到。印設定時換成 ***，錯誤訊息只說「太短」不說內容。

寫成程式就是下面這個輪廓。錯誤用 TypeScript 課第 4 課的自訂錯誤類別 ConfigError 丟出，呼叫端用 instanceof 就能分辨「設定錯了」和其他錯誤，決定要印什麼訊息：

// 輪廓：每個欄位都「檢查 → 有問題就 push 一行訊息」，最後一起決定
const errors: string[] = []
const rawPort = env.PORT ?? '3000'
if (!/^\d+$/.test(rawPort) || Number(rawPort) > 65535) errors.push(`PORT 要是 0–65535 的整數，收到 ${JSON.stringify(rawPort)}`)
// …其他欄位…
if (errors.length > 0) throw new ConfigError(errors)

欄位多了，這種手寫檢查會變得冗長，可以改用資料驗證函式庫（TypeScript 課第 26 課、NestJS 課第 11 課），但上面五個原則不變。

💡 實務上：新增環境變數就是一次部署上的協調
你在 PR 裡加了一個新的必填設定（例如金流的 API 金鑰），程式合併了，但正式環境還沒設定這個值，部署時新版本就會因為 fail fast 啟動失敗、上不去。這不是程式寫錯，而是改程式和改環境設定沒有協調好。資深工程師在 review 時會確認：.env.example 有沒有一起改、PR 說明有沒有寫「部署前要先設定哪些值」、負責部署的人知不知道。能給合理預設值的設定（像 LOG_LEVEL）就給預設值，只有真的沒辦法猜的才設成必填。

現在程式能正確拿到參數和設定，也能在設定錯時馬上停下來。接著看程式開始工作之後的事：資料從哪裡讀進來、結果印到哪裡。開場第一件怪事，報表裡混進錯誤訊息，就出在這裡。

結果和錯誤訊息該印到哪裡？stdin、stdout、stderr 與管線

第一節的圖裡，父程序和子程序之間除了啟動時給的參數和環境變數，還接著三條管道。程序活著的期間，這三條管道一直開著，用編號 0、1、2 稱呼：

管道用途Node 裡
stdin（0，標準輸入）讀進來的資料，預設是鍵盤process.stdin
stdout（1，標準輸出）程式的結果，預設是終端機畫面console.log、process.stdout
stderr（2，標準錯誤）錯誤、警告、進度這些給人看的訊息，預設也是終端機畫面console.error、process.stderr

你平常在終端機跑程式時，stdout 和 stderr 都顯示在同一個畫面上，看起來沒有差別，所以很多人習慣全部用 console.log。差別要等到把它們接到別的地方時才看得出來。shell 提供這幾種寫法來改接管道：

寫法意思
a | b管線（pipe）：a 的 stdout 接到 b 的 stdin
a > out.txt重新導向（redirect）stdout 到檔案（覆蓋）；>> 是附加
a 2> err.txt只把 stderr 存到檔案
a < in.txt從檔案讀當作 stdin

管線讓你把幾個小程式串成一條生產線，每個只做一件事：對帳腳本負責算，sort 負責排序，> 負責存檔。實際接起來看兩條輸出管道的差別：

$ node examples/streams.ts > out.txt
第 2 行格式錯誤：數量不是正整數        ← stderr 沒被導向，還是出現在畫面
$ cat out.txt
拿鐵 2 × 110 = 220
stdout 是終端機嗎？ false             ← process.stdout.isTTY：接到檔案或管線時不是 true

$ cat data/orders.csv | node total.ts | sort > report.txt

執行後看第一個指令：> 只把 stdout 接到檔案，所以 console.log 印的結果進了 out.txt，console.error 印的錯誤訊息仍然留在畫面上。這就是開場第一件怪事的原因。對帳腳本被接成最後一行那樣時，下一個程式只收得到 stdout；如果錯誤訊息也用 console.log 印到 stdout，它就會混進資料裡，被 sort 排進報表，甚至被下一個程式當成一筆訂單處理。改成 console.error 印到 stderr，資料管道裡就只有資料，錯誤訊息則留在畫面上（或排程系統的 log 裡）給人看。

輸出裡的 process.stdout.isTTY 是順便看的：它判斷 stdout 是不是直接接到終端機。這裡的 TTY 指的就是終端機。有些工具靠它決定要不要印顏色，因為顏色的控制字元寫進檔案只會變成亂碼。

stdin 是另一頭：對帳腳本要從 stdin 一行一行讀訂單，讀法是用 node:readline 搭配 for await…of。for await…of 是會等待的迴圈：每次等下一筆資料到了才跑一圈，在 TypeScript 課第 10 課講過：

import { createInterface } from 'node:readline'

for await (const line of createInterface({ input: process.stdin, crlfDelay: Infinity })) {
  console.log('讀到：', line)   // 一次一行，不含換行字元；最後一行沒有換行也會讀到
}
console.log('stdin 結束了')      // 上游程式結束（或檔案讀完）時迴圈才跑完

迴圈不是一次把整個檔案讀進來，而是資料來一行處理一行，等上游程式結束或檔案讀完，迴圈才跑完。crlfDelay: Infinity 讓 Windows 的換行 \r\n 一律當成一個換行。stdin 是一種 stream（串流），第 16 課詳講。

輸出走對管道之後，報表乾淨了。但第二件怪事還在：腳本明明遇到錯誤，排程系統卻記錄「成功」。排程系統沒有看畫面，它看的是程序結束時交回的那個數字。

程式怎麼告訴呼叫它的人「成功了沒」？結束碼

排程系統、部署工具這些父程序，沒辦法讀懂你印出來的文字訊息，它們判斷成敗只靠一件事：程序結束時交回的結束碼。結束碼是一個 0–255 的整數，規則只有一條：0 代表成功，其他都代表失敗。在 shell 裡用 $? 看上一個指令的結束碼，&& 也是靠它決定：前一個指令成功（0）才執行下一個。

$ node order.ts --drink 珍珠奶茶
錯誤：沒有這個品項：珍珠奶茶
用法：node order.ts --drink <品項> [--size S|M|L] [--qty|-q <數量>]
$ echo $?
2
$ npm test && npm run deploy    # 測試沒過（非 0）就不部署

最後一行是整個部署流程的縮影：測試程式用結束碼告訴 shell「沒過」，shell 就不會往下部署。團隊裡負責這件事的通常是 CI（continuous integration，持續整合）：每次有人 push 程式碼，CI 系統就自動跑測試和檢查，依結果決定能不能合併、能不能部署（部署課第 15 課）。CI、部署工具、排程都只看這個數字。所以程式出錯時如果結束碼還是 0，等於明確告訴它們「一切正常」，後面的步驟就會照常進行。

除了「0 成功、非 0 失敗」，幾個常見的結束碼有固定的意思：

結束碼意思
0成功
1一般錯誤；Node 遇到沒被接住的例外（uncaught exception）也是 1
2慣例：用法錯誤（參數打錯），讓呼叫的人知道是「你用錯了」不是「程式壞了」
128＋訊號編號被訊號終止（下面說明）。SIGTERM 是 15，shell 顯示 143

Node 自己還定義了幾個結束碼，例如 --env-file 的檔案不存在時的 9，列在課末的查表。

表上最後一列的訊號（signal）是作業系統送給程序的通知，用來要求它停下來之類。你在終端機按 Ctrl+C，就是送 SIGINT 訊號給程序；部署工具要停掉舊版本時，則是送 SIGTERM。程序因為訊號而結束時，並不是自己交回結束碼，shell 才會用「128＋訊號編號」來表示。收到 SIGTERM 時程式要怎麼收尾，在第 21 課詳講。

💡 實務上：排程腳本的結束碼決定「出錯時有沒有人知道」
咖啡店的夜間對帳腳本由排程每天凌晨執行，沒有人盯著畫面看。排程和監控系統通常是靠結束碼判斷要不要發告警，如果腳本把錯誤 catch 起來、印一行 log 就以 0 結束，對帳失敗好幾天都不會有人發現，直到會計月底對不起來。資深工程師看到這類腳本會先問：「失敗的時候誰會收到通知？」再回頭確認每條錯誤路徑都有設非 0 的結束碼。

知道要回報非 0 之後，下一個問題是怎麼設定它。Node 有兩種寫法，其中一種正是第三件怪事，報表少一截的原因。

設定結束碼：為什麼不要用 process.exit()？

設定結束碼的兩種寫法看起來一樣，結果不一樣：

  • process.exitCode = 1：只記下「結束時用 1」，程式照常跑完、等該寫的東西都寫完才結束。
  • process.exit(1)：立刻結束，還在排隊的工作直接丟掉，包括還沒寫出去的 stdout。

你可能會想：console.log 都已經執行過了，輸出怎麼還會「沒寫出去」？官方文件（process 的「A note on process I/O」）寫明：在 macOS／Linux 上，stdout 接到檔案或終端機時是同步寫入，console.log 回來時資料已經寫好；但接到管線時是非同步寫入，console.log 只是把資料排進佇列，之後才慢慢送出。

管線本身只有幾十 KB 的緩衝區（大小由作業系統決定，下面的實驗大約裝得下 1,700 行）。下游程式沒把資料讀走，緩衝區就塞滿了，剩下的資料只能在你的程序裡排隊。這時呼叫 process.exit()，程序立刻結束，排隊中的資料也跟著消失。用範例實際看：

$ node examples/exit-early.ts | (sleep 1; wc -l)            # 印 2 萬行後 process.exit(1)
    1753
$ node examples/exit-early.ts --gentle | (sleep 1; wc -l)   # 改用 process.exitCode = 1
   20000

執行後看 wc -l 數到的行數。這是 v24.22.1 實測：讀取端晚 1 秒才讀，用 process.exit(1) 只送出不到一成，每次數字不同；改用 process.exitCode = 1，2 萬行一行不少。這種錯誤很難查，因為你直接在終端機跑時是同步寫入、完全看不出問題，只有接進管線、CI、log 收集器時才出事。對帳腳本接著 sort，下游又不一定讀得快，報表少一截就是這樣來的。

所以 CLI 的寫法是：設定 process.exitCode，讓程式自然結束。官方文件也這樣建議。真的遇到無法繼續的錯誤，讓例外丟出去（結束碼 1）也比 process.exit() 安全。回到開場的對帳腳本，三件怪事現在都有答案：錯誤訊息改走 stderr，錯誤時設非 0 的 process.exitCode，不用 process.exit() 提早結束。下面的練習把點單工具、伺服器設定、對帳腳本這三支程式實際寫一次。

練習

練習 1：完成 order.ts：用 parseArgs 解析 --drink、--size（預設 M）、--qty（縮寫 -q，預設 1），價格從 menu.ts 讀：單價是 menu[品項] + sizeExtra[尺寸]。node order.ts --drink 拿鐵 --size L --qty 2 印出 拿鐵 L ×2 = 260。

錯誤用法（未知選項、多出來的字、沒給 --drink、沒有的品項、尺寸不是 S／M／L、數量不是正整數，例如 2abc、0、1.5、1e1、空字串）時：stdout 不印任何東西，用 console.error 印一行說明錯在哪，再印用法（起始檔的 usage），process.exitCode = 2。parseArgs 丟出的錯誤也要接住，不能讓 stack trace 印出來。測試會換一份價目表，價格不能寫死。

練習 2：完成 config.ts 的 loadConfig(env)，回傳 { port, shopName, logLevel, adminToken }：

  • PORT：沒給就是 3000；有給的話必須是 0–65535 的整數字串（'3000abc'、''、'70000'、'3.5'、' 80'、'1e3' 都不行），轉成數字。
  • SHOP_NAME：必填，只有空白也算沒填。
  • LOG_LEVEL：debug／info／warn／error 之一，沒給就是 info。
  • ADMIN_TOKEN：必填，至少 16 個字元。

每個問題一行訊息、開頭寫變數名稱，全部收集完再 throw new ConfigError(errors)；訊息裡不能出現 token 的內容；只讀參數 env，不要碰 process.env，也不要修改傳進來的 env（預設值放進回傳的物件）。接著完成 main.ts：loadConfig(process.env) 成功就用 console.log(JSON.stringify(…)) 印出設定（adminToken 換成 "***"）；遇到 ConfigError 就把每個問題各印一行到 stderr，process.exitCode = 1。測試也會用 node --env-file=.env main.ts 執行，確認你不用多寫任何東西就能讀 .env。

練習 3：完成 total.ts：從 stdin 一行一行讀「品項,數量,單價」（可以先試 node total.ts < data/orders.csv）。每個欄位去掉前後空白；好的行在 stdout 印 拿鐵 2 × 110 = 220，最後印 合計 NT$ 520。空行（包括只有空白的行）直接跳過；格式錯誤的行（欄位不是 3 個、品項是空的、數量或單價不是正整數）在 stderr 印 第 N 行格式錯誤：原因 然後繼續，行號從 1 開始，空行也算一行。只要有錯誤行，結束碼就是 1，合計照樣要印。測試會餵 2 萬行，而且等你的程式全部印完才開始讀它的 stdout（模擬比較慢的下游程式），一行都不能少。

練習 4：執行 PORT=3000 node a.ts && node b.ts（之前沒有 export 過 PORT），b.ts 裡的 process.env.PORT 是什麼？

✓ PORT=3000 node a.ts 只把 PORT 放進 a.ts 這個程序的環境，shell 自己沒有這個變數，所以 b.ts 拿不到。要讓之後的指令都帶著它要用 export PORT=3000。而且就算讀得到，環境變數也一定是字串 '3000'，不會是數字。

練習 5：執行 DEBUG=false node app.ts，app.ts 裡的 if (process.env.DEBUG) { … } 會怎樣？

✓ 環境變數沒有布林值，只有字串或 undefined。'false' 是長度 5 的字串，在 if 裡當成 true。要明確比對，例如 process.env.DEBUG === 'true'，最好在 loadConfig 裡統一轉成布林值、遇到看不懂的值就報錯。

練習 6：執行 node report.ts > out.txt，程式裡 console.error 印的訊息去哪了？

✓ > 是 1> 的簡寫，只動 stdout；console.error 走 stderr，還是接在終端機上。這正是分開兩條管道的目的：結果存進檔案，錯誤留給人看。要另外存錯誤用 2> err.txt。

常見錯誤

  • 以為 process.env.PORT 是數字：環境變數和參數的值都是字串。process.env.PORT + 1 會得到 '30001'。在 loadConfig 裡驗證後轉成數字。
  • 用 parseInt 或 Number 直接轉：parseInt('3000abc') 是 3000、Number('') 是 0、Number(' 80') 是 80，壞資料全都過關。先用正規表示式檢查格式。
  • 錯誤訊息印到 stdout：接管線時下一個程式會把錯誤訊息當資料。錯誤、警告、進度一律 console.error。
  • 錯誤時結束碼還是 0：CI 和部署工具只看結束碼。失敗要設 process.exitCode，用法錯誤慣例是 2。
  • 用 process.exit() 結束 CLI：stdout 接管線時是非同步寫入，還沒送出的輸出會被丟掉。設定 process.exitCode，讓程式自然結束。
  • parseArgs 的錯誤沒接住：使用者打錯一個選項就看到一大段 stack trace、結束碼 1。用 try／catch 接住，印說明和用法，結束碼 2。
  • .env 進了 git，或以為 .env 會蓋過真正的環境變數：.env 放進 .gitignore、改提交 .env.example；真正的環境變數優先，.env 只補沒設定的值。

小結

  • 執行一次 node 就是一個程序，有自己的 PID；它從父程序拿到參數、環境變數和三條管道，結束時交回結束碼。開場對帳腳本的三件怪事，都是這幾條管道用錯。
  • 參數放「這一次要做什麼」，用 util.parseArgs 解析：strict 模式會對打錯的選項丟錯誤，要接住並印用法；值都是字串，自己驗證再轉型，品項用 Object.hasOwn 檢查。
  • 環境變數放「在哪個環境跑」的設定，值是字串或 undefined，只會從父程序往下傳；--env-file／process.loadEnvFile() 讀 .env，真正的環境變數優先；.env 不進 git。
  • 設定在啟動時集中驗證、一次報完所有問題、不印出機密（fail fast），錯誤在部署當下就出現。
  • 結果走 stdout、訊息走 stderr；|、>、2>、< 把程式組合起來，錯誤訊息走 stdout 就會混進下游的資料。
  • 0 成功、非 0 失敗，用法錯誤慣例是 2；CI、部署工具、排程只看這個數字。用 process.exitCode，不要用 process.exit()：stdout 接管線時是非同步寫入，提早結束會丟掉輸出。

128＋訊號編號被訊號終止。SIGTERM 是 15，shell 顯示 143。如果是你用 Node 的 child_process 啟動別的程式，結束事件拿到的是 code null、signal 'SIGTERM'，不是 143
