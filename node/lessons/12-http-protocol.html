階段 4：HTTP 服務 · 第 12 課

HTTP 協定與 curl

咖啡店的 App 上，客人點了兩杯拿鐵，按下「送出訂單」。在前端，這只是一行 fetch('/orders', { method: 'POST', body })：瀏覽器替你找到伺服器、送出請求、等回應，再把回應包成你拿到的 res。換到後端，你變成收下這個請求、決定回什麼的那一方，瀏覽器以前替你藏起來的細節，現在每一個都可能變成 bug：

  • 回應的 Content-Length 算錯，App 只收到半個 JSON，JSON.parse 直接爆掉。
  • 失敗時狀態碼回錯，前端的錯誤處理、快取、監控全部跟著判斷錯。
  • 用 GET 做「取消訂單」，某天爬蟲或瀏覽器的預先載入路過，訂單就被取消了。

這課跟著這一張訂單的請求走完一趟，回答五個問題：它怎麼到達伺服器、伺服器實際收到的位元組長什麼樣、該用哪個方法送、伺服器怎麼回報結果、回應的 body 到哪裡結束。最後用 curl 在終端機重現同一個請求。途中你會用 Node 最底層的 node:net 親手解析請求、寫出回應；下一課改用 node:http 時，你會知道它替你做了哪些事。

這課的路線：
  1. 請求怎麼到達伺服器：從網址到回應經過哪四步，為什麼 TCP 逼得 HTTP 自己規定「訊息到哪裡結束」。
  2. 伺服器實際收到什麼：把原始位元組印出來，看懂請求行、標頭、空行、body，以及回應的狀態行。
  3. 下單該用哪個方法：安全與冪等是什麼，為什麼不能用 GET 改資料，哪些請求網路斷掉時可以放心重送。
  4. 伺服器怎麼回報結果：狀態碼的五個家族，該回 4xx 還是 5xx，前端和監控怎麼靠它判斷。
  5. body 到哪裡結束、怎麼用 curl 重現：Content-Length 和 chunked、keep-alive，以及在終端機測 API、看標頭的常用寫法。
這課會用到：
  • 第 11 課的位元組與 Buffer：中文一個字在 UTF-8 是 3 個位元組，長度用 Buffer.byteLength 算；收到的片段用 Buffer.concat 接起來，subarray 切出一段。

按下「送出訂單」之後，請求怎麼到達伺服器？

要看懂伺服器收到什麼，得先知道請求是怎麼送過來的。這中間有兩個角色：發出請求的一方叫客戶端（client），可以是瀏覽器、手機 App、curl，也可以是另一台呼叫你 API 的後端；收下請求、送回回應的一方叫伺服器（server）。兩邊之所以能溝通，是因為都遵守同一套規則：HTTP（HyperText Transfer Protocol）。它規定請求和回應要寫成什麼格式、每個部分代表什麼意思。這課用的 HTTP/1.1，訊息就是一行一行的文字，後面可能再接一段內容本體（body）。

客人打開 App 時，App 會先拿菜單，然後才能下單。先用菜單的網址看客戶端怎麼知道要找誰，它把五個部分都用上了：

部分http://localhost:3000/menu?size=L意思
schemehttp用什麼協定。https 是在 TLS 加密之上的 HTTP
hostlocalhost哪一台電腦，可以是網域名稱或 IP 位址
port3000那台電腦上的哪個程式。沒寫時 http 是 80、https 是 443
path/menu要哪個資源
query?size=L附加的參數

網址只說了「找誰、要什麼」。真正把請求送到，客戶端依序做四件事：

第 1 步要解決「名稱對應到哪台電腦」。網路上找電腦靠的是 IP 位址，像 127.0.0.1 或 ::1（這兩個都代表「這台電腦自己」）。人記不住數字，所以網址裡寫的是 shop.example 這種名稱，再由 DNS（Domain Name System）把名稱查成 IP 位址。localhost 不用問外面的 DNS，作業系統自己就知道它指向本機。DNS 的細節在部署課第 4 課。

找到電腦之後，還要找到電腦上的哪個程式。一台電腦同時跑著很多程式，port 就是用來區分它們的號碼：咖啡店的 API 在 3000 等請求，資料庫可能在 5432。IP 加 port，才指到唯一一個程式。

第 2 步是建立 TCP 連線。TCP 是 HTTP 底下的傳輸規則：雙方先來回握手，建立一條連線，之後送出的位元組保證照順序、不遺失地到達對方。HTTP 的文字就是在這條連線上傳的。如果網址是 https，連線建立後還會先完成 TLS 加密的握手，再在加密通道裡傳一模一樣的 HTTP 文字（部署課第 5 課）。

第 3、4 步才是 HTTP 本身：客戶端寫出請求文字，伺服器讀完、處理，寫回回應文字。

這裡有一個關鍵限制。TCP 只保證位元組的順序，不管「一則訊息」從哪裡開始、到哪裡結束。客戶端一次送出的請求，伺服器可能分兩段收到；兩個請求也可能黏在同一段裡到達。對 TCP 來說，那只是一條沒有斷點的位元組流。所以 HTTP 必須在文字格式裡自己標出邊界：標頭到哪裡結束、body 有幾個位元組。下一節就把伺服器實際收到的位元組印出來，看 HTTP 怎麼標。

伺服器實際收到的是什麼？

要看到原始的位元組，不能用 node:http，因為它收到後會先替你解析好。這裡改用 node:net：它是 Node 內建的 TCP 模組，比 node:http 低一層，只負責在連線上收發位元組，不理解 HTTP。練習資料夾的 examples/show-request.ts 用它開一個伺服器，把收到的東西原封不動印出來。開著它，另開一個終端機執行 curl http://localhost:3000/menu（curl 是在終端機發請求的工具，這課最後一節會詳細介紹）：

$ node examples/show-request.ts
在 http://localhost:3000 等請求
收到 81 個位元組：
"GET /menu HTTP/1.1\r\nHost: localhost:3000\r\nUser-Agent: curl/8.7.1\r\nAccept: */*\r\n\r\n"

這 81 個位元組就是一個完整的 HTTP 請求。它有固定的結構，下單的請求也一樣，只是後面多了 body：

由上往下對照剛才印出來的位元組：

  • 請求行（request line）：方法 目標 版本，用一個空白分隔，例如 GET /menu HTTP/1.1。方法說明想做什麼，目標通常是網址的 path 加 query，版本告訴伺服器用哪一版 HTTP 解讀後面的內容。
  • 標頭（header）：一行一個 名稱: 值，放這個請求的附加資訊，例如 body 的格式、客戶端能接受什麼。名稱不分大小寫，Content-Type 和 content-type 是同一個標頭，所以 Node 的 HTTP 伺服器把收到的標頭名稱一律轉成小寫（下一課的 req.headers）。HTTP/1.1 規定一定要有 Host：同一個 IP 上可能放了好幾個網站，伺服器要靠它知道客戶端要找哪一個。
  • 空行：每一行都用 \r\n 結尾，也就是 CR 和 LF 兩個位元組，不是只有 \n。連續兩個 \r\n 就是空行，代表標頭結束。這是上一節說的第一個邊界：伺服器一直讀，讀到 \r\n\r\n 就知道標頭讀完了。
  • body：訊息的內容本體。拿菜單的 GET 通常沒有 body；下單的 POST 要把 {"drink":"拿鐵","qty":2} 送過去，就放在這裡。

回應用同一種結構，只是第一行換成狀態行（status line），例如 HTTP/1.1 200 OK：版本、三位數的狀態碼（status code），和一段給人看的說明文字。examples/raw-request.ts 反過來站在客戶端那邊：自己用 net.connect 寫出請求文字，再把伺服器回的原始位元組印出來。為了不用另外開伺服器，這個範例自己先用 node:http 開了一個回菜單 JSON 的伺服器（下一課會詳講），listen(0) 讓系統挑一個空的 port，所以下面的 port 不是 3000，每次執行也不一樣。輸出分兩段：上半是伺服器解析後看到的標頭，名稱已經轉成小寫；下半是客戶端收到的原始回應，\r\n 顯示成 ⏎：

$ node examples/raw-request.ts
伺服器看到的標頭（名稱都轉成小寫了）： {
  host: 'localhost:57006',
  accept: 'application/json',
  connection: 'close'
}
---- 原始回應（\r\n 顯示成 ⏎）----
HTTP/1.1 200 OK⏎
Content-Type: application/json; charset=utf-8⏎
Date: Sat, 31 Oct 2026 15:21:35 GMT⏎
Connection: close⏎
Content-Length: 30⏎
⏎
{"drink":"拿鐵","price":110}

注意 Content-Length。body 是 {"drink":"拿鐵","price":110}，在 JavaScript 裡 .length 是 26，Content-Length 卻是 30。因為 Content-Length 算的是 UTF-8 的位元組數，「拿鐵」兩個字各佔 3 個位元組，比字串長度多出 4（第 11 課）。這個數字就是第二個邊界：告訴對方 body 有幾個位元組。它算錯會發生什麼事，留到「body 到哪裡結束」那一節細看。

還有一個標頭決定伺服器怎麼讀 body：Content-Type。body 對伺服器來說只是一串位元組，要靠 Content-Type 才知道該當成 JSON 解析、當成表單拆欄位，還是當成圖片存起來。HTTP 本身不限定 body 的格式：application/json、text/html、image/png、表單送出的 application/x-www-form-urlencoded，都是正常的 HTTP。下單的請求要帶 Content-Type: application/json，伺服器才會把 body 當 JSON 讀。

練習 2 會請你只用 node:net 寫出一個會回應的伺服器，需要的 API 只有這幾個：

import { createServer, connect } from 'node:net'

// 伺服器：每有一條新連線，callback 收到一個 socket（代表這條連線）
const server = createServer(socket => {
  socket.on('data', chunk => { /* chunk 是 Buffer，一個請求可能分好幾段到 */ })
  socket.write('…')   // 送出文字或 Buffer，連線還開著
  socket.end('…')     // 送出最後一段，然後關閉這一邊的連線
})
server.listen(0)      // 0：讓系統挑一個空的 port
server.on('listening', () => console.log(server.address()))   // { port: 5xxxx, … }

// 客戶端：連到某個 port，連上後一樣用 write／end 送、on('data') 收
const socket = connect(3000, '127.0.0.1', () => socket.end('GET / HTTP/1.1\r\nHost: x\r\n\r\n'))

注意 on('data') 的註解：一個請求可能分好幾段到，這正是第一節說的 TCP 不分訊息邊界。你的程式要先把片段累積起來，看到 \r\n\r\n 才算收完標頭。

格式看懂了，再回到請求行的第一個字。拿菜單用 GET，下單用 POST，這只是習慣嗎？如果哪天有人用 GET 來下單或取消訂單，會出什麼事？

下單該用哪個方法？為什麼不能用 GET 改資料？

請求行的第一個字是方法（method），告訴伺服器你想對這個資源做什麼。方法不只是給你自己的伺服器看的：瀏覽器、快取、代理伺服器、爬蟲、HTTP 函式庫這些中間經手的程式，都會依方法決定能不能快取、能不能自動重送、能不能預先發出。

這裡的代理伺服器（proxy）在後面會一直出現，先講清楚。正式環境裡，App 的請求通常不會直接打到你的 Node 程式，而是先到擋在它前面的一層程式：反向代理（reverse proxy，例如 Nginx）或負載平衡器（load balancer，例如雲端的 LB），由它決定轉給後面哪一台 Node，再把 Node 的回應轉回給 App。對代理來說，後面那台真正處理請求的伺服器叫上游（upstream）。換個角度看，代理對 App 是伺服器，對 Node 則是客戶端：它自己開連線、送請求給 Node、等 Node 回應。

它們之所以能這樣做，是因為大家遵守同一份標準。HTTP 語意的標準是 RFC 9110。RFC（Request for Comments）是網際網路標準文件的編號系列，對 HTTP 行為有爭議時，以它為準。

常用的方法和它們的兩個性質如下，表格後面逐一解釋「安全」和「冪等」：

方法用途安全冪等
GET讀取資源是是
HEAD同 GET，但只回標頭（例如只想知道檔案多大）是是
OPTIONS問伺服器支援什麼，瀏覽器的 CORS 預檢就是它是是
POST送資料讓伺服器處理，常用於建立（下一張訂單）否否
PUT用送來的內容整個取代資源否是
PATCH修改資源的一部分否不保證
DELETE刪除資源否是

安全（safe）的意思是：客戶端只是在讀，不要求伺服器改變任何狀態。正因為 GET 被約定成安全的，很多程式會在沒有人點擊的情況下自動發 GET：搜尋引擎的爬蟲會順著頁面上的連結一路發 GET，瀏覽器會預先載入使用者「可能會點」的連結，快取會替你重發 GET 確認內容有沒有更新。它們都假設 GET 不會改變任何東西。

所以用 GET 修改資料，例如把「取消訂單」做成 GET /orders/7/cancel，就是在邀請這些程式幫你取消訂單。只要這個網址出現在某個頁面上，爬蟲或預先載入路過一次，訂單就被取消了，而且沒有任何人按過按鈕。改資料一定要用 POST、PUT、PATCH 或 DELETE。

冪等（idempotent）的意思是：同一個請求做一次和做很多次，伺服器最後的狀態一樣。拿訂單來看：

  • PUT /orders/7 {"status":"ready"} 送三次，訂單狀態還是 ready，和送一次一樣。
  • DELETE /orders/7 送三次，訂單還是只被刪掉一次。後兩次可能回 404，回應不同，但伺服器的狀態一樣。
  • POST /orders 送三次，就是三張訂單。

冪等跟「會不會改資料」是兩回事：PUT、DELETE 會改資料，但它們是冪等的。冪等關心的是「重複」：網路不穩時，客戶端常常不知道剛才的請求有沒有成功。例如客人按下送出，請求已經到了伺服器、訂單也建好了，但回應在路上斷掉，App 只看到連線錯誤。這時要不要重送？如果請求是冪等的，重送最多就是再做一次一樣的事，結果不變；如果是 POST，重送可能變成兩張訂單，付款的話就是扣兩次錢。

這兩個性質會在後面的課反覆出現：安全的請求才能放心快取（第 15 課），冪等的請求才能在網路斷掉時自動重送（第 17 課）。

💡 實務上：設計 API 時先問「這個請求被送兩次會怎樣」
咖啡店的「送出訂單」按鈕，客人網路慢會連點，手機切換網路時客戶端也可能自動重送，用 POST 建單就可能多出一張一樣的訂單。資深工程師看到會改資料的 API，第一個問題常是「重送兩次會怎樣」：查詢用 GET，改狀態盡量設計成冪等（例如 PUT 設定狀態，而不是「把狀態往下推一格」），建立訂單、付款這類非冪等的操作，前端先防連點，後端再用冪等鍵（idempotency key）防重複：客戶端替每一次下單產生一個唯一的 id，放在標頭裡一起送，重送時沿用同一個 id；伺服器看到這個 id 已經處理過，就直接回上次的結果，不再建第二張單（細節在第 14 課）。另外，Code Review（程式碼審查）時看到用 GET 做刪除、取消、寄信，直接退回，不用等出事。

下單用 POST 送出去了。伺服器處理完，要告訴 App 結果：訂單建好了嗎？沒建好的話，是客人填錯了、沒登入，還是伺服器自己壞了？這就是回應第一行那三位數的工作。

伺服器怎麼告訴前端結果？狀態碼

狀態行裡的三位數狀態碼，是伺服器對「這個請求結果如何」的正式回答。為什麼不直接在 body 裡寫 {"ok":false} 就好？因為讀回應的不只是你寫的前端程式。前端的 res.ok、監控系統的錯誤率、快取、HTTP 函式庫的重試邏輯，都只看狀態碼，不會去解析你的 body。狀態碼是所有經手的程式都看得懂的共同語言。

狀態碼的第一位數代表家族，先記住家族就夠了，個別的碼查表用，不用背：

家族意思常用的
1xx資訊：還沒完，繼續很少直接處理
2xx成功200 OK、201 Created（建立成功，通常附 Location 標頭）、204 No Content（成功，沒有 body）
3xx去別的地方拿301 永久搬家、302 暫時轉址、304 Not Modified（你手上的快取還能用，第 15 課）
4xx請求有問題，客戶端要改400 格式錯、401 沒登入、403 登入了但沒權限、404 找不到、405 方法不對、409 和目前狀態衝突、413 body 太大、415 Content-Type 不支援、422 格式對但內容不合規則、429 請求太頻繁
5xx伺服器的問題，客戶端沒做錯500 程式出錯、502 前面的代理（見方法一節）沒從上游拿到正常的回應（例如上游突然斷線，或回了不合格式的東西）、503 暫時無法服務（維護、過載）、504 代理等上游回應等到逾時

套回下單的請求：訂單建好了，回 201 Created，並在 Location 標頭附上新訂單的網址；客人沒登入，回 401；body 不是合法的 JSON，回 400；JSON 沒問題但 qty 是 0，回 422；送來的 Content-Type 不是 JSON，回 415；程式自己丟出例外，回 500。

最常要判斷的是 4xx 還是 5xx。判斷的方式是問：同一個請求原封不動再送一次，會不會成功？請求本身錯了（4xx），再送幾次都一樣，要改的是請求；伺服器的問題（5xx），客戶端沒做錯，過一陣子可能就好了。監控也是這樣分：4xx 變多，通常是客戶端改版或有人在亂試；5xx 變多，是你的伺服器該被叫醒了。

不要所有回應都用 200，再在 body 裡寫 {"ok":false}。前端的 res.ok、監控的錯誤率、快取、重試邏輯都看狀態碼；錯誤回 200，快取會把錯誤存起來，監控也看不到錯誤。
💡 實務上：狀態碼是前後端之間的約定
前端通常會依狀態碼統一處理：401 導去登入頁、403 顯示「沒有權限」、400 或 422 把錯誤標在表單欄位上、5xx 跳「系統忙碌，請稍後再試」。所以後端回哪個碼不是個人喜好：權限不足卻回 401，前端就會把已經登入的使用者踢去重新登入。團隊實務上會在 API 文件寫清楚每支 API 可能回哪些狀態碼，並約定錯誤 body 的格式（第 14 課）。400 和 422 要怎麼分，各團隊做法不同，挑一種寫下來、全部 API 一致，比爭論哪種才標準重要。

狀態碼和標頭都在 body 前面，App 讀到空行就拿到了。但它真正要的是 body 裡那份訂單 JSON，而 body 裡可能有任何位元組，包括 \r\n，不能再靠空行判斷結尾。開場那個「半個 JSON」，就是在這裡出事。

回應的 body 到哪裡結束？

回到第一節的限制：TCP 只是一串沒有斷點的位元組。標頭用空行標出結尾，body 則要另外說明自己有多長。HTTP/1.1 主要有兩種方式，最後再看第三種：送完就關掉連線。

方式一：先講好總長度，Content-Length

Content-Length 標頭寫的是 body 的位元組數。客戶端讀完標頭，再讀滿這麼多位元組，就知道 body 結束了。上一節看到它跟字串長度不同，用錯會怎樣？examples/content-length.ts 用兩種長度回同一段 JSON：

$ node examples/content-length.ts
body.length（UTF-16 單位）： 18
Buffer.byteLength(body)： 26
Content-Length 用字串長度（18）→ 收到：{"message":"歡迎
Content-Length 用位元組數（26）→ 收到：{"message":"歡迎光臨"}

客戶端完全相信 Content-Length：它說 18，就只讀 18 個位元組，剩下的「光臨"}」被當成不屬於這個回應，JSON.parse 拿到半個 JSON 就爆了。反過來，寫得比實際大，客戶端會一直等那些不存在的位元組，直到逾時。所以 Content-Length 一定用 Buffer.byteLength(body) 算，不能用 body.length。

方式二：不知道總長度時，Transfer-Encoding: chunked

有時候送出第一個位元組時，還不知道 body 總共多長，例如邊查資料庫邊把結果送出去。這時改用 Transfer-Encoding: chunked：把 body 切成一段一段送，每段前面先寫這段的位元組數（十六進位），最後送一個長度 0 的段代表結束。Node 的 HTTP 伺服器（下一課）在你沒設 Content-Length、又分好幾次寫出 body 時，會自動這樣送；分次寫出用的是 res.write，它是 node:http 送出一段 body 但不結束回應的方法，下一課會用到。

下面這個回應，每次 write 之間隔了一段時間（例如在等資料庫）。用 curl -i --raw 看原始格式，--raw 是叫 curl 不要幫你把段落拼回去：

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Date: Sat, 31 Oct 2026 19:31:08 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked

7
拿鐵

7
美式

0

「拿鐵」加換行是 7 個位元組，所以每段前面是 7；最後的 0 告訴客戶端 body 結束了。段落在哪裡切由送的一方決定，例如同一段同步程式裡連續 write，Node 可能把它們併成一段送（實測結果見課末）。接收方不能假設段落和你的 write 一一對應，只能照每段標的長度讀。

兩種方式只能用一種：request smuggling

Content-Length 和 Transfer-Encoding: chunked 不能同時出現。原因是正式環境裡，一個請求常常先經過前面的代理，再轉給後面的伺服器（方法一節說過的那一層），兩者都要各自判斷「這個請求到哪裡結束」。如果一個請求同時帶了兩種標頭，或格式寫得模稜兩可，代理可能照 Content-Length 讀、伺服器照 chunked 讀，兩邊切出的邊界不同。攻擊者就能在第一個請求的 body 尾端藏一段完整的第二個請求：代理以為那是 body 的一部分，一起放行；伺服器卻把它當成下一個獨立的請求來執行，繞過代理上的檢查。這種攻擊叫 request smuggling。

所以正式的 HTTP 解析器對格式非常嚴格，有一點不合規就直接拒絕，不去猜對方的意思。Node 的解析器遇到只有 \n 的行尾、Host : x（名稱和冒號之間有空白）、Content-Length: 0x10，都直接回 400 Bad Request（實測版本見課末）。練習 1 的解析器也照這個標準：格式不對就丟錯，不要幫忙修正。

方式三：送完就關，Connection: close

回應加上 Connection: close，意思是「這個回應送完就關連線」。客戶端讀到連線被關閉，也就知道 body 結束了。練習 2 就這樣做，同時也帶上正確的 Content-Length。

但每次都關連線很浪費：建立 TCP 連線要來回握手，HTTPS 還要再加 TLS 握手，App 拿菜單、下單、查訂單狀態，如果每個請求都重新連線，大部分時間都花在握手上。所以 HTTP/1.1 預設反過來，連線不關。

連線不關，下一個請求接著送：keep-alive

HTTP/1.1 預設持久連線（keep-alive）：回應送完不關連線，下一個請求繼續用同一條，第一節圖中第 1、2 步就只發生一次。

這也是 body 結尾一定要講清楚的另一個原因。同一條連線上，下單請求的 body 後面緊接著就是下一個請求的請求行。Content-Length 寫得太大，伺服器會把下一個請求的開頭當成這一個的 body；寫得太小，剩下的 body 又會被當成下一個請求的開頭。

持久連線不會永遠留著。伺服器和客戶端各自有一個閒置逾時：連線閒置超過這個時間，就由自己這一邊關掉或不再重用。Node 的 HTTP 伺服器預設 5 秒，回應裡的 Keep-Alive: timeout=5 就是在告訴客戶端這件事（各預設值與版本見課末）。

💡 實務上：客戶端的閒置時間要比伺服器短，偶發 502 常是這裡出錯
如果客戶端願意把連線留得比伺服器久，就會發生這種情況：伺服器剛因為閒置把連線關掉，客戶端還以為連線可用，拿它送出下一個請求，得到 ECONNRESET。咖啡店 API 前面放了負載平衡器時，負載平衡器就是 Node 的客戶端（方法一節說過，代理對上游來說是客戶端），所以 Node 的 keepAliveTimeout 要設得比負載平衡器的閒置時間長。設反了，症狀是正式環境偶爾冒出零星的 502，重試又好了，本機怎麼都重現不出來。這是正式環境偶發 502 的經典原因之一，查不到原因時，先比對兩邊的閒置時間。

到這裡，下單請求和回應的每一個位元組你都看得懂了。但每次都開 node:net 印原始文字太麻煩；工作上要重現一支 API 的行為、確認它回了什麼，用的是 curl。

怎麼在終端機重現這個下單請求？curl

curl 是在終端機發送 HTTP 請求的工具，macOS 內建（這台是 curl 8.7.1）。前端看請求用瀏覽器的 Network 面板，後端用 curl，因為它能做到面板做不到的事：指令可以複製給同事、可以寫進腳本自動跑，連到沒有瀏覽器的伺服器上也能用。

送出下單的 JSON：-d 和 --json 的差別

要用 curl 送出下單請求，最直覺的寫法是 -d 加上 JSON。但 -d 不看內容，不會因為內容長得像 JSON 就改 Content-Type。開著 show-request.ts 比較兩種寫法，看伺服器收到的 Content-Type：

$ curl -d '{"drink":"拿鐵"}' http://localhost:3000/orders
"POST /orders HTTP/1.1\r\n…Content-Length: 18\r\nContent-Type: application/x-www-form-urlencoded\r\n\r\n{\"drink\":\"拿鐵\"}"

$ curl --json '{"drink":"拿鐵"}' http://localhost:3000/orders
"POST /orders HTTP/1.1\r\n…Content-Type: application/json\r\nAccept: application/json\r\nContent-Length: 18\r\n\r\n{\"drink\":\"拿鐵\"}"

第一種告訴伺服器「這是表單」。還記得第二節說的，伺服器靠 Content-Type 決定怎麼讀 body：會檢查 Content-Type 的伺服器（下一課你就會寫）會回 415。送 JSON 用 --json（舊版 curl 的寫法見課末）。

對回菜單 JSON 的伺服器用 -v，看到的完整對話：

從上往下，正好是第一節那四個步驟：* 開頭的幾行是解析名稱、建立 TCP 連線，> 開頭是送出的請求，< 開頭是收到的狀態行和標頭，最後是 body；結尾的 left intact 表示連線因為 keep-alive 留著沒關。API 出問題時先用 curl -v 重現，就能分清楚是連不上（停在 Trying）、伺服器回錯（看狀態碼），還是前端送錯（看 > 那幾行）。

💡 實務上：用「Copy as cURL」重現客服回報的 bug
客服回報「客人結帳失敗」、前端查到是結帳 API 回 500 時，最有用的不是截圖，而是一行能重跑的 curl：在瀏覽器 DevTools 的 Network 面板對那個請求按右鍵，選 Copy → Copy as cURL，就能拿到包含方法、標頭、body 的完整指令。後端拿到後先在本機或測試環境重跑，確認能重現再改程式，改完再用同一行驗證。要注意的是複製出來的指令常帶著 Cookie 或 Authorization 標頭，等於使用者的登入憑證，貼到 Slack、issue 之前要先刪掉或換成測試帳號的。

只看狀態碼、送 PATCH 加標頭

有時候你只想知道一支 API 現在回幾號，例如部署完確認服務活著，或在腳本裡判斷成功失敗。body 和進度訊息都是雜訊，要一個一個關掉：

$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/menu
200
  • -o /dev/null：-o 叫 curl 把 body 寫進指定的檔案，而不是印到 stdout。/dev/null 是系統裡一個「寫進去就消失」的特殊檔案，所以這等於把 body 丟掉。
  • -s：安靜模式。body 不印到終端機時，curl 會改在 stderr 印一張進度表（下載多少位元組、速度多少），-s 把它關掉；它也會關掉錯誤訊息，連不上時你只會看到空白。
  • -w '%{http_code}\n'：傳輸完成後，照你給的格式印出資訊。%{http_code} 會換成狀態碼，後面的 \n 讓它自己佔一行。

三個合起來，stdout 只剩一個狀態碼，腳本可以直接拿來比較。

另一個常見的需求是送 GET、POST 以外的方法，例如把訂單狀態改成「做好了」，還要帶一個追查用的標頭：

$ curl -i -X PATCH --json '{"status":"ready"}' -H 'X-Request-Id: abc' http://localhost:3000/orders/7
HTTP/1.1 204 No Content
Date: Wed, 25 Nov 2026 20:23:05 GMT
Connection: keep-alive
Keep-Alive: timeout=5
  • -X PATCH：指定方法。--json 預設會用 POST，-X 把它換成 PATCH，body 和 Content-Type 照樣由 --json 處理。
  • -H 'X-Request-Id: abc'：加一個請求標頭，寫法就是請求裡那一行的 名稱: 值。要加好幾個，就寫好幾個 -H。
  • -i：輸出也包含狀態行和標頭。這個伺服器回 204 No Content，成功但沒有 body，不加 -i 會什麼都看不到。

用到的選項整理成表，查表用，不用背：

選項作用
-i輸出也包含回應的狀態行和標頭
-v印出整段對話：連到哪個 IP、送出的請求（> 開頭）、收到的回應標頭（< 開頭）。這些印在 stderr
-X PATCH指定方法。沒給 body 時預設 GET，給了 body 時預設 POST
-H 'X-Request-Id: abc'加一個請求標頭，可以寫好幾個
-d '…'送 body，方法自動變 POST，Content-Type 是 application/x-www-form-urlencoded
--json '…'送 JSON body，自動加上 Content-Type: application/json 和 Accept: application/json，方法預設 POST
-s安靜模式，不印進度條
-o 檔案body 寫進檔案而不是 stdout；-o /dev/null 就是丟掉
-w '%{http_code}'傳輸完成後印出指定的資訊，例如狀態碼

存成腳本，換環境只改網址

拿菜單、下單這幾個請求你會反覆送：本機改完程式送一次，部署到測試環境再送一次。把它們寫成 .sh 檔，一行一個指令，用 sh requests.sh 執行，換環境時只改 BASE_URL：

# requests.sh
curl -s "$BASE_URL/menu"
curl -s --json '{"drink":"美式咖啡","qty":1}' "$BASE_URL/orders"

$ BASE_URL=http://localhost:3000 sh requests.sh

注意網址用雙引號、JSON 用單引號，這不是隨便選的。shell 的兩種引號差在變數會不會展開（部署課第 2 課詳講）：

  • 單引號裡的內容原封不動。JSON 放在單引號裡，裡面的雙引號就不用跳脫。但 '$BASE_URL/menu' 送出去的網址就是字面上的 $BASE_URL/menu。
  • 雙引號裡的 $變數 會被換成值。網址寫 "$BASE_URL/menu"。

練習 3 就是把下單相關的三個請求寫成這樣的腳本。

補充與查表

主線用不到、但調整設定或查問題時會用到的細節。

keep-alive 的閒置時間（Node 24.22.1）

  • Node 24.22.1 的 HTTP 伺服器閒置 5 秒就關（server.keepAliveTimeout 實測是 5000，回應裡也看得到 Keep-Alive: timeout=5）。v24.6.0 起真正關掉前會再多等 keepAliveTimeoutBuffer 的 1 秒，第 21 課關機時會用到。
  • Node 內建的 fetch（由 undici 實作）的客戶端預設閒置 4 秒就不再重用（undici 文件的 keepAliveTimeout 預設 4e3）。比伺服器的 5 秒短，符合「客戶端要比伺服器短」。

解析器與 chunked 的實測結果

  • Node 24.22.1 的解析器是 llhttp 9.4.3。本機實測遇到只有 \n 的行尾、Host : x、Content-Length: 0x10，都回 400 Bad Request。
  • 同一段同步程式裡連續兩次 write，本機 Node 24.22.1 實測併成一段 e（14 個位元組）送出。

舊版 curl 送 JSON

--json 從 curl 7.82.0 開始支援。更舊的版本改寫成 -H 'Content-Type: application/json' -d '…'。

HTTP/2 與 HTTP/3

HTTP/1.1 的一條連線上，回應要照請求的順序一個一個回來，前一個慢，後面的全部卡住，瀏覽器只好同時開好幾條連線。HTTP/2 把訊息改成二進位的 frame，在一條連線上同時傳好幾個請求，標頭也會壓縮；HTTP/3 改走 QUIC（建立在 UDP 上），連線換網路（例如手機從 Wi-Fi 切到行動網路）也不用重建。方法、標頭、狀態碼的意思都和這課一樣，只是傳送格式不同。實務上 HTTP/2、HTTP/3 通常由前面的反向代理或 CDN 處理，Node 程式在後面講 HTTP/1.1，這門課也都用 HTTP/1.1。

練習

在 learn/ 執行 node check.mjs node 12 建立 work/12/，裡面有內文的範例（examples/）和三題的起始檔。

練習 1：寫 parse-request.ts 的 parseRequest(raw)，把原始的 HTTP/1.1 請求（Buffer）解析成 { method, target, version, headers, body }。規則寫在檔案開頭的註解：標頭區到第一個 \r\n\r\n，行尾必須是 \r\n；標頭名稱轉小寫、值去掉前後空白、同名的多個值用 ", " 合併；body 依 Content-Length 的位元組數從原本的 Buffer 切，多出來的位元組不屬於這個請求，body 也可能是圖片這種不是文字的位元組；格式錯誤（缺空行、請求行不是三段、標頭行壞掉、Content-Length 不是數字、body 不足）就 throw new HttpParseError(…)。提示：Buffer 也有 indexOf，回傳的是位元組位置。

練習 2：在 raw-server.ts 只用 node:net 完成 createRawServer()：把連線收到的資料累積起來，看到標頭結尾的空行之後，回應 HTTP/1.1 200 OK、Content-Type: application/json; charset=utf-8、正確的 Content-Length、Connection: close，body 是 {"message":"歡迎光臨"}，送完關閉連線。不能改用 node:http 的伺服器。測試會用 fetch、node:http 的 get，和一個把請求分三段慢慢送的客戶端來檢查。寫好可以執行 node raw-server.ts，再用 curl -i http://localhost:3000/ 看看。

練習 3：在 requests.sh 寫三個 curl 指令，網址都用 $BASE_URL 開頭：(a) GET /menu，stdout 只印出狀態碼；(b) POST /orders 送 JSON {"drink":"拿鐵","qty":2}，Content-Type 要正確；(c) PATCH /orders/1 送 {"status":"ready"}，並帶 X-Request-Id: test-123 標頭。測試會開一個記錄所有請求的伺服器，設好 BASE_URL 執行 sh requests.sh，檢查伺服器收到的方法、路徑、標頭、body，以及整個腳本的 stdout 只有 (a) 的狀態碼（(b)、(c) 的回應是沒有 body 的 204）。可以先開 show-request.ts，用 BASE_URL=http://localhost:3000 sh requests.sh 自己看看送出了什麼。

練習 4：GET、POST、PUT、DELETE 之中，哪些是冪等的？

✓ 冪等是說「做一次和做很多次，伺服器最後的狀態一樣」，跟會不會改資料無關。PUT 用同樣的內容取代三次，結果一樣；DELETE 刪三次，資源還是被刪掉一次（後面幾次可能回 404，但狀態相同）。POST 送三次會建立三張訂單。冪等也不是「回應一樣」，DELETE 第二次的回應可能不同。

練習 5：前端呼叫 API，一次拿到 404，另一次拿到 500。各該由誰處理？

✓ 4xx 代表請求本身有問題，原封不動重送還是會失敗，要改的是客戶端（或使用者輸入）；5xx 代表客戶端沒做錯，是伺服器出了問題。如果客戶端送錯資料，正確的伺服器應該回 400 或 422，回成 500 就是後端的 bug。

練習 6：curl -d '{"a":1}' http://localhost:3000/orders 送出的 Content-Type 是什麼？

✓ -d 不看內容，一律用表單格式 application/x-www-form-urlencoded（本機 curl 8.7.1 實測）。檢查 Content-Type 的伺服器會回 415，或把 body 當成表單解析。--json 會同時設好 Content-Type 和 Accept。

常見錯誤

  • 以為 HTTP 就是 JSON：HTTP 只規定訊息的格式，body 是什麼由 Content-Type 說明，HTML、圖片、表單、純文字都可以。
  • Content-Length 用字串長度：中文一個字 3 個位元組，客戶端會讀到半個 JSON。用 Buffer.byteLength(body)。
  • 用 GET 修改資料：GET 是安全的方法，爬蟲、預先載入、快取都會自動發。修改用 POST、PUT、PATCH、DELETE。
  • 錯誤時回 200，在 body 裡寫失敗：前端的 res.ok、監控、快取、重試都看狀態碼。錯誤就回對應的 4xx 或 5xx。
  • 以為 4xx 代表伺服器壞了：4xx 是請求的問題。看到大量 4xx，先檢查客戶端送了什麼（curl -v）。
  • 客戶端的 keep-alive 閒置時間比伺服器長：客戶端會拿伺服器剛關掉的連線送請求，得到 ECONNRESET，前面有負載平衡器時就是偶發 502。讓 Node 的 keepAliveTimeout 比前面那一層的閒置時間長。
  • curl 用 -d 送 JSON 忘了 Content-Type：預設是表單格式。用 --json。
  • 網址放在單引號裡：'$BASE_URL/menu' 的變數不會展開。網址用雙引號，JSON 用單引號。

小結

  • 一次請求：DNS 把名稱換成 IP、和那個 port 建立 TCP 連線、送出請求文字、收到回應文字；HTTPS 在 TCP 上多一層 TLS。TCP 不分訊息邊界，所以 HTTP 要自己標出結尾。
  • HTTP/1.1 訊息：請求行（方法 目標 版本）或狀態行、一行一個標頭、空行、body；行尾是 \r\n，標頭名稱不分大小寫，Content-Type 說明 body 的格式。
  • GET、HEAD、OPTIONS 是安全的；GET、HEAD、OPTIONS、PUT、DELETE 是冪等的，POST 不是。這決定能不能快取和自動重送；改資料不能用 GET。
  • 2xx 成功、3xx 轉址或用快取、4xx 客戶端要改、5xx 伺服器的問題。判斷方式是「原封不動重送會不會成功」。
  • body 的結尾看 Content-Length（位元組數）或 Transfer-Encoding: chunked，兩者不能同時出現；keep-alive 讓同一條連線送多個請求，Node 伺服器閒置 5 秒關閉，fetch 客戶端 4 秒，客戶端要比伺服器短。
  • curl：-i、-v 看標頭和對話，-X 指定方法，-H 加標頭，--json 送 JSON，-s -o /dev/null -w '%{http_code}' 只印狀態碼；-d 預設是表單格式。
