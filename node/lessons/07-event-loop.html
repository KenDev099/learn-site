階段 2：非同步與 event loop · 第 7 課

Node 的 event loop

咖啡店的 API 伺服器白天接訂單，晚上還有一件固定的工作：在同一個程序裡，把白天累積的訂單通知一筆一筆送出去。上線後維運回報一件怪事：每到跑通知的那幾分鐘，部署平台定期打的健康檢查網址 /health 就沒有回應。平台判定服務死了，把它重啟，通知做到一半被砍掉，隔天又從頭來一次。

通知的程式沒有丟任何錯誤，/health 也只是回一個 ok，為什麼會回不了？要回答這個問題，得先知道 Node 怎麼用一條執行緒同時顧這麼多事。答案是 event loop：一個不斷繞圈、檢查「哪件事做完了，就接著處理它」的迴圈。這課沿著這個事故把 event loop 拆開來看；學完你能預測 Node 裡非同步工作的執行順序，並找出讓伺服器卡住、讓腳本不結束、讓登入變慢的原因。

這課的路線：
  1. 一條執行緒怎麼同時服務很多請求，等待的工作交給誰：先得到事故的最小答案，「/health 回不了，代表那條執行緒被佔住了」。
  2. 做完的工作按什麼順序回來：event loop 每一圈的 phases，setTimeout 和 setImmediate 誰先。
  3. nextTick 與 microtask 為什麼能插隊，通知批次怎麼靠插隊把 /health 擋在門外，怎麼修。
  4. 把通知搬到獨立腳本後，它做完了卻不結束：程序什麼時候才會結束，怎麼找出是誰撐著它。
  5. 尖峰時登入變慢，連讀檔也跟著慢：thread pool 為什麼要排隊。
這課會用到：
  • TypeScript 課第 7 課的瀏覽器 event loop：同步程式在 call stack 上跑完，才輪到排隊的 task；每個 task 之後先清空 microtask（Promise.then 的 callback 就排在這裡）。
  • 第 4 課的 ES module 與 CommonJS：Node 的兩套模組系統，.cts 一定是 CommonJS。

只有一條執行緒，怎麼同時服務很多請求？

先回到熟悉的地方。TypeScript 課第 7 課講過瀏覽器的模型：JavaScript 跑在一個 call stack 上，一次只執行一段程式；setTimeout、點擊事件這些 callback 排在 task 佇列；Promise.then、queueMicrotask 排在 microtask 佇列。每段程式跑完，先把 microtask 全部清空，才輪到下一個 task。Node 沿用同一套想法，只是要服務的對象從一個使用者的畫面，變成同時連進來的很多個請求。

要理解這件事，先講清楚「執行緒」。執行緒（thread）是程式裡一條獨立的執行路線：一條執行緒在同一時間只能做一件事，要同時做兩件事，就需要兩條執行緒，或是讓一條執行緒在兩件事之間切換。Node 執行你的 JavaScript 只用一條執行緒，所以同一時間只有一段 JavaScript 在跑。好處是兩個 callback 不會同時改到同一個變數，你不用處理多執行緒搶資料的問題。

聽起來一條執行緒應該一次只能服務一個請求。看一個下單請求實際花時間的地方：收到請求、驗證資料只要零點幾毫秒，接著查資料庫，要等資料庫回應 30ms，拿到結果再組回應。這 30ms 裡，執行緒其實沒有事做，只是在等。

如果執行緒就這樣停下來等，叫做阻塞（blocking）：在等的 30ms 裡別的請求全部進不來，一秒最多服務三十幾個請求。Node 的做法是非阻塞 I/O（non-blocking I/O）：發出「查資料庫」「讀檔案」這類輸入輸出（I/O）的請求後，不等它完成就先回去處理別的事；I/O 完成時，再把你事先交代的 callback 排進佇列，等執行緒有空時執行。這個「看佇列裡有什麼做完了、輪流交給執行緒」的迴圈，就是 event loop。

所以「單執行緒」不等於「一次只服務一個請求」。一個請求在等資料庫的 30ms 裡，執行緒是空的，可以去處理別的請求。反過來說，真正會讓所有請求一起卡住的，只有一種情況：你的 JavaScript 自己佔著執行緒不放，例如一段跑很久的運算，或這課後面會看到的「不斷插隊的工作」。

這就是事故的最小答案：/health 的處理函式只回一個 ok，幾乎不花時間，它回不了，代表那條唯一的執行緒一直沒空去接它。是誰佔著？通知程式看起來每一筆都是非同步的，不像在佔執行緒。要找出原因，得先知道「等待交給別人」裡的「別人」是誰，以及做完的工作怎麼回到執行緒上。

等待的工作交給誰？

上一節說，Node 把等待交出去、做完再排 callback 回來。負責這件事的是 libuv，第 1 課提過的那個 C 函式庫。event loop 本身也是 libuv 實作的。libuv 手上有兩種交出去的做法，看工作的種類決定：

圖的右邊就是兩種做法：

  • 網路 I/O 交給作業系統。作業系統本身就有「同時盯著上千個連線，哪個有資料進來再通知我」的機制，macOS 叫 kqueue、Linux 叫 epoll。libuv 把所有連線登記給它，自己只要等通知。所以一個 Node 程序能同時掛著上千個連線，不需要上千條執行緒。咖啡店伺服器收請求、回應、對外 fetch，都走這條路。
  • 作業系統沒有好的非同步介面的工作，交給 thread pool。有些工作作業系統只提供「呼叫了就要等它做完」的版本，例如讀寫檔案。libuv 的解法是預先準備一組背景執行緒，叫 thread pool，讓背景執行緒去等，主執行緒不用等。交給它的工作有：node:fs 的非同步檔案操作、dns.lookup（把網域名稱查成 IP，http.get('http://shop.example') 預設會用到）、crypto.pbkdf2／scrypt／randomBytes 這類耗時的密碼學運算，以及 zlib 壓縮。

注意一件容易誤會的事：thread pool 的背景執行緒不會執行你的 JavaScript。它們只做 C 寫的那段工作（讀檔、雜湊），做完把結果交回 event loop，你的 callback 還是在那條唯一的 JavaScript 執行緒上跑。所以「Node 只有一條執行緒」這句話只對你的 JavaScript 成立；Node 整個程序裡其實有好幾條執行緒在工作。

回到事故。送通知本身是網路 I/O，已經交給作業系統去等；/health 的連線也一樣，作業系統收到後就在它那裡排好了。交出去的這一側是作業系統在等，跟 JavaScript 的執行緒無關，沒有理由擋住 /health。會卡住的只剩另一側：通知程式每一筆在 JavaScript 這一側要做的事（組內容、呼叫送通知的函式）是同步跑完的，練習 3 裡每筆大約 1ms。所以疑點不在等待，而在排隊：不管工作交給作業系統還是 thread pool，做完之後都要回到 event loop 排隊，等執行緒來處理。同時有計時器到期、檔案讀完、新連線進來時，event loop 先處理哪個？

做完的工作按什麼順序回來？event loop 的 phases

event loop 不是把所有做完的工作丟進同一個佇列。它每繞一圈，依序經過幾個階段，叫做 phase。每個 phase 負責一類 callback，有自己的佇列；輪到它時，把佇列裡該跑的 callback 跑完，再往下一個 phase 走，五個走完就是一圈：

phase處理什麼
timers時間到了的 setTimeout、setInterval
pending callbacks上一圈被延後的少數系統層 callback，例如某些 TCP 錯誤
poll收 I/O 事件、執行 I/O callback（讀完檔案、收到連線、收到資料）。沒事做時在這裡等待，最多等到最近的計時器到期
checksetImmediate 的 callback：poll 之後立刻執行
close callbackssocket.on('close') 這類關閉事件

表裡最要記住的是 poll。它是 event loop 接收外界的地方：檔案讀完、新連線進來、請求的資料到了，都在 poll 被收進來並執行 callback。咖啡店的 /health 請求也一樣，要等 event loop 走到 poll，伺服器才會開始處理它。沒有任何事要做時，event loop 會停在 poll 等，最多等到最近一個計時器該觸發的時間，這也是閒置的 Node 程序幾乎不吃 CPU 的原因。

知道 phase 之後，就能回答一個常被問的問題：setTimeout(fn, 0) 和 setImmediate(fn) 誰先？setImmediate 是 Node 專屬的 API，意思是「這一圈的 poll 結束後馬上執行」，它的 callback 排在 check。setTimeout(fn, 0) 的 callback 排在 timers。兩者看起來都是「盡快執行」，但在不同的 phase，所以順序看你在哪裡呼叫它們：

  • 在主程式裡同時排兩者：誰先不保證。setTimeout(fn, 0) 實際上是 1ms，event loop 第一次走到 timers 時，如果 1ms 還沒過，就先跑到 check 執行 setImmediate；過了就先跑 timeout。這台 Mac 連續執行六次，兩種順序都出現過。
  • 在 I/O callback 裡（例如讀完檔案）排兩者：setImmediate 一定先。I/O callback 在 poll 執行，接下來就是 check，timers 要等下一圈。

這課的範例以 Node 24.22.1 為準；不同 Node 版本在 timers 的實作上有調整，但上面的 phase 順序和兩條規則不受影響，細節見課末。

到這裡，所有 callback 都屬於某個 phase，event loop 一圈一圈轉，每一圈都會經過 poll，/health 照理一定輪得到。但通知程式排下一筆用的是 process.nextTick，它不在上面任何一個 phase 裡。圖下方那條「每段 callback 跑完先清 nextTick、再清 microtask」說的就是它。

不屬於任何 phase 的兩個佇列：nextTick 與 microtask 為什麼能插隊？

上一節的五個 phase 之外，還有兩個佇列，它們的優先權比所有 phase 都高：

  • process.nextTick(fn)：Node 專屬。在目前這段程式結束後、event loop 往下走之前就執行。名字裡有 tick，但它跟「下一圈」無關，比 setImmediate 早得多。
  • microtask：Promise.then、await 之後的程式、queueMicrotask，和瀏覽器一樣。

它們的規則只有一條：每段 callback 跑完，Node 先清空 nextTick 佇列，再清空 microtask 佇列，然後才繼續 event loop 的下一步。「清空」的意思是一直做到佇列沒有東西為止，清的過程中新加進來的，也會在同一次被清掉。這兩個佇列等於排在所有 phase 前面插隊。

用範例確認這條規則。先在 learn/ 執行 node check.mjs node 07，它會建立 work/07/，裡面的 examples/ 就是這課的範例。在 work/07 裡執行三個範例，它們在同一段程式裡各排一個 setTimeout、setImmediate、Promise.then、process.nextTick，再印一行同步的文字；看每個結果的印出順序：

$ node examples/order.ts     # ES module
sync
promise
nextTick
timeout
immediate

$ node examples/order.cts    # 同樣的程式，CommonJS
sync
nextTick
promise
timeout
immediate

$ node examples/in-io.ts     # 在 readFile 的 callback 裡
readFile callback
nextTick
promise
immediate
timeout

先看三個結果共同的地方：同步的那行永遠第一，因為它就是「目前這段程式」；nextTick 和 promise 一定排在 timeout、immediate 前面，因為它們插隊。最後一個結果在 readFile 的 callback 裡，也就是 poll phase，所以接下來的 check（immediate）比下一圈的 timers（timeout）先，跟上一節的規則一致。

前兩個結果的 nextTick 和 promise 順序卻相反。CommonJS 的頂層程式是一段普通的同步程式，跑完先清 nextTick，所以 nextTick 先；ES module 的頂層程式本身就在一個非同步的載入流程裡執行（為了支援頂層 await），它結束時 Node 正在清 microtask，所以 promise 先。這是這台 Node 24.22.1 的實測結果（timeout 和 immediate 在主程式裡的先後也可能對調）。

同一段程式換個模組格式順序就變，代表這種先後是執行環境的細節。資深的做法是不要寫依賴 nextTick 和 Promise 先後的程式。需要「晚一點再做」時，Node 官方文件建議優先用 setImmediate，行為最好預測。process.nextTick 適合一個特定用途：讓 callback 在呼叫端的同步程式跑完之後、任何 I/O 之前執行，練習 1 會用到。

回頭看那條規則裡的「清的過程中新加進來的，也會在同一次被清掉」。如果 nextTick 的 callback 自己又排了一個 nextTick，會發生什麼事？通知程式就是這樣寫的。

通知批次為什麼讓 /health 回不了？

通知程式的寫法大致如下（練習 3 的起始檔）：處理一筆，再用 process.nextTick 排下一筆，直到全部做完。

const step = () => {
  if (i === items.length) return resolve()
  handle(items[i++])
  process.nextTick(step)
}
step()

照上一節的規則一步一步走：step 跑完，Node 去清 nextTick 佇列，裡面有下一個 step；執行它，它又排了一個 step，因為清空時新加進來的也要清，所以接著執行。佇列要等最後一筆做完才會真的空掉，在那之前 event loop 一步也沒有往下走，永遠到不了 poll。/health 的連線其實早就到了，已經在作業系統那裡排好，但 libuv 要等 event loop 走到 poll 才會去問作業系統有哪些事件，所以一直沒有人去收。

這種情況叫 I/O 飢餓（starvation）：插隊的工作一直佔著，I/O 永遠輪不到。每一筆通知都很短，看起來像非同步，但串起來就是一段沒有空檔的同步工作。範例 starve.ts 用遞迴 nextTick 空轉 1 秒，同時排了一個 10ms 的計時器，看計時器實際在幾毫秒執行：

$ node examples/starve.ts
nextTick 迴圈結束
10ms 的計時器在 1003 ms 才執行

計時器晚了將近一秒，因為 timers phase 也一直輪不到。修法是把插隊改成排隊：把範例裡的 process.nextTick(spin) 改成 setImmediate(spin) 再跑一次，計時器就準時在 10ms 執行。setImmediate 在 check phase 排的新 callback 要等下一圈，中間 event loop 會經過 timers 和 poll，計時器和新連線都有機會被處理。通知程式也一樣，每一筆之間用 setImmediate 讓出 event loop，/health 就能在兩筆通知之間被回應，這就是練習 3 要做的事。

同樣的陷阱也藏在 async 函式裡。把迴圈塞滿 await Promise.resolve() 一樣會餓死 I/O：await 一個已經完成的 Promise 只是排一個 microtask，microtask 也是插隊的，沒有讓出 event loop。「有寫 await」不等於「有讓別人跑」，要看等的東西是不是真的要等 I/O。

💡 實務上：批次工作要記得讓出 event loop
咖啡店晚上產生每日報表、或匯入幾千筆商品的 CSV，常見寫法是直接在 API 的程序裡跑迴圈。如果迴圈裡都是同步運算或 await 已完成的 Promise，event loop 一直輪不到 poll，這段時間顧客的請求全部卡住。部署平台還會定期打一個檢查網址（例如 /health）確認服務活著，回不了就把它重啟，批次做到一半就斷掉，看起來像「服務莫名其妙一直重開」。code review 看到處理大量資料的迴圈時，資深會先問：每一批之間有沒有用 setImmediate 讓出 event loop？中途被重啟能不能從斷點接著做？要跑好幾分鐘的工作，通常就移到另一個程序或排程去做，不跟對外的 API 擠在一起。

咖啡店照這個建議，把通知改成一支獨立的腳本，每晚由排程啟動。API 伺服器不再受影響，但新的狀況出現了：排程報告說這支腳本從來沒有「完成」過，它印出了最後一筆，卻一直掛著不結束。

腳本做完了，為什麼不結束？

第 2 課說過，程式「跑完」就會以結束碼 0 結束。有了 event loop 的模型，這句話可以說得更精確：event loop 裡沒有任何還撐著程序的東西，Node 就結束。反過來說，只要還有東西撐著，event loop 就會一直繞、一直在 poll 等，程序就不會結束，不管你的程式碼是不是已經跑到最後一行。撐著程序的東西有名字：

  • handle：event loop 追蹤的長期資源，例如計時器、伺服器、socket、子程序。只要還有一個在活動，loop 就繼續繞，程序就不結束。這就是第 1 課的伺服器不會自己停的原因：它開著一個等連線的 handle。
  • ref／unref：handle 預設是 ref 的，意思是「撐住程序」。呼叫 unref() 後，這個 handle 照樣會運作，但如果只剩它，程序就不等它直接結束。
  • process.getActiveResourcesInfo()：列出目前撐著程序的資源種類，程式不結束時用它查是誰。

範例 alive.ts 開了一個伺服器、一個 interval 和一個 unref 的 timeout，先印出撐著程序的清單，再關掉伺服器、清掉 interval：

$ node examples/alive.ts
開著： [ 'TCPServerWrap', 'Timeout' ]
beforeExit：loop 空了 []
exit：結束碼 0
  • 第一行的清單只有兩個：TCPServerWrap 是伺服器，Timeout 是 interval。unref 的 timeout 不撐住程序，所以不在清單裡。
  • 關掉伺服器、清掉 interval 之後清單變空，event loop 沒有理由再繞，觸發 beforeExit。
  • 最後觸發 exit，程序以結束碼 0 結束。

unref() 的寫法通常是在建立時直接接上去：

setInterval(() => console.log('已送出', sent, '筆'), 60_000).unref()

它適合「順便做的事」：每分鐘印一次統計、定期清快取，主要工作做完時這些事沒有理由把程序留下來。它不能拿來處理「該關卻沒關」的資源。資料庫連線沒關時，如果去找底層 socket 把它 unref，程序是結束了，但連線沒有正常關閉，資料庫那一端要等逾時才知道連線斷了；該送出的查詢或交易也可能還沒完成。判斷方式很簡單：這個資源是你開的、用完就該關，就關掉它；只有「主要工作做完就不需要」的背景工作才用 unref()。

這兩個結束前的事件用途不同：beforeExit 在 loop 空了時觸發，這時還能排新的非同步工作，排了 loop 就會繼續；exit 在真的要結束時觸發，只能做同步的事。

找到撐著的 handle 之後，怎麼讓程式結束也有對錯之分。

程式不結束時，不要用 process.exit() 硬砍。stdout 接到管線（pipe，例如被另一個程式或 log 收集器讀取）時是非同步寫出的，process.exit() 會把還沒寫出去的輸出丟掉（第 2 課實測過）。正確做法是找出撐著的 handle，關掉它（clearInterval、server.close()），讓程式自然結束；要回報失敗就設 process.exitCode。

咖啡店的通知腳本就是這種情況：它開了資料庫連線來讀待送的通知，做完卻沒有關。資料庫連線本質上是一條 TCP socket，這時 process.getActiveResourcesInfo() 的清單裡會多出一項 'TCPSocketWrap'（這台 Node 24.22.1 連上一個 TCP 服務後實測的名稱），而不只是 Timeout；連線池開了幾條連線，就可能看到幾個。練習 2 是同一類問題的小版本，一支報表程式開著狀態伺服器和進度計時器，做完不結束，你要用 process.getActiveResourcesInfo() 找出撐著的 handle 並關掉。

💡 實務上：腳本跑完卻不結束，多半是連線沒關
最常遇到的地方不是伺服器，而是一次性的腳本：資料庫 migration、每天凌晨的對帳、補資料的 script。它們印出「完成」卻一直掛著，常見原因是資料庫連線池或快取（例如 Redis）的連線還開著，它們是撐住程序的 handle（連線池在第 20 課）。放在排程或 CI 裡就麻煩了：工作永遠不算完成，最後被判逾時失敗，或下一次排程又啟動一份。資深的寫法是在 finally 裡關掉自己開的連線，而不是在結尾補一行 process.exit()；伺服器收到關機訊號時怎麼有順序地關，第 21 課再談。

通知腳本關好連線、每晚準時結束之後，API 伺服器又出了一個問題，這次跟通知無關：週末早上的點單尖峰，客服回報登入很慢，維運還發現連讀菜單設定檔都變慢了。登入和讀檔看起來毫無關係，JavaScript 也沒有佔著執行緒，慢在哪裡？

尖峰時登入變慢，為什麼連讀檔也跟著慢？

答案在第二節的 thread pool。登入時要用 pbkdf2 驗證密碼，讀設定檔要用 node:fs，這兩件工作都交給同一個 thread pool。而 thread pool 預設只有 4 條執行緒，同時丟進去超過 4 件工作，多的要排隊。examples/threadpool.ts 同時做 8 次 pbkdf2（把密碼反覆雜湊 30 萬次的運算，存密碼時用來拖慢暴力破解），印出每個做完的時間：

$ node examples/threadpool.ts
第 1 個完成：105 ms
…（4 個在 100ms 左右）
第 5 個完成：214 ms
…（另外 4 個在 200ms 左右）

$ UV_THREADPOOL_SIZE=8 node examples/threadpool.ts
第 4 個完成：123 ms
…（8 個都在 120–150ms 之間）

預設時分成兩波：前 4 個佔滿 4 條執行緒，後 4 個排隊，等前一波做完才開始，所以多等了一整輪。把 UV_THREADPOOL_SIZE 環境變數設成 8，8 個同時開始，幾乎一起完成。尖峰時段的登入就是這樣：很多人同時登入，pbkdf2 把 4 條執行緒佔滿，這時要讀設定檔的工作只能排在它們後面，所以看起來毫無關係的讀檔也變慢了。

這也劃清了 thread pool 的影響範圍。網路的收發（伺服器處理連線、fetch 傳送和接收資料）交給作業系統，不佔 thread pool，不受影響；但連到網域名稱前的 dns.lookup 那一步會佔。真正吃 CPU 的 JavaScript 運算則是另一回事，它佔的是唯一那條 JavaScript 執行緒，第 9 課處理。

看到這裡，直覺的修法是把 UV_THREADPOOL_SIZE 調大。它可以調，但有兩個限制：

  • 要在啟動前設定：Node 文件說明，thread pool 可能在你的程式執行前就建好了，在程式裡寫 process.env.UV_THREADPOOL_SIZE = '8' 不保證有效。放在啟動指令或部署設定裡。
  • 調大不是免費的：執行緒多於 CPU 核心數時，CPU 運算不會變快，只是輪流做。它主要幫的是「很多檔案 I/O 或 DNS 查詢在等」的情況。
💡 實務上：調 UV_THREADPOOL_SIZE 之前先確認瓶頸
常見情境：尖峰時段登入變慢，有人在網路上看到「把 UV_THREADPOOL_SIZE 調大」就直接改。資深會先確認慢的是什麼：是密碼雜湊（pbkdf2）在 pool 裡排隊、大量檔案讀寫，還是 JavaScript 自己的運算佔住執行緒（這種調 pool 完全沒用）。容器分到的 CPU 核心常常不多，pool 開再大，密碼雜湊也不會變快。決定要調的話，寫在部署設定的環境變數裡，並在 PR 裡附上調整前後量到的結果，讓之後的人知道這個數字怎麼來的。

咖啡店這一路遇到的三件事，都可以用同一個模型解釋：一條 JavaScript 執行緒、把等待交出去的 libuv、一圈一圈轉的 event loop，以及能插隊的 nextTick 和 microtask。下面的練習讓你親手修這三類問題。

練習

在 learn/ 執行 node check.mjs node 07 建立 work/07/，裡面有內文的範例（examples/）和三題的起始檔。

練習 1：shop.ts 的 Shop 繼承 EventEmitter（Node 內建的事件工具：on(名稱, fn) 掛監聽器，emit(名稱, 參數) 會同步呼叫目前掛著的監聽器，第 8 課詳講）。它在建構子裡 emit('open', 店名)，但使用者一定是 new Shop('信義店') 之後才 on('open', …)，永遠收不到。修改 Shop：建構完立刻掛上的監聽器一定收得到、每個只收到一次，而且要在 event loop 進入下一個 phase 之前發出：setTimeout 和 setImmediate 都太晚（測試用假時鐘，setTimeout 根本不會觸發）。

練習 2：report.ts 產生報表時每 100ms 印一次 處理中…，做完印出 2 萬行明細和 報表完成，但之後程式一直不結束。修正它：做完就自然結束、結束碼 0，「處理中…」照常印。測試會在程式結束後才開始讀它的輸出，所以用 process.exit() 收尾會丟掉輸出而過不了。先執行 node report.ts 看它停住，可以在最後加一行 console.error(process.getActiveResourcesInfo()) 看是誰撐著（看完記得拿掉）。

練習 3：drain-queue.ts 的 drainQueue(items, handle) 用遞迴 process.nextTick 一筆一筆處理訂單通知，處理期間同一個程序裡的伺服器回應不了 /health。改寫它：處理期間 /health 仍能回應，處理的筆數與順序不變，全部做完時回傳的 Promise 才完成。測試讓 600 筆通知各花 1ms，處理到第 20 筆時送出 /health，回應時處理的筆數要還不到一半；也會檢查沒有改到傳進來的陣列、空陣列時直接完成。

練習 4：一個 ES module（.ts，package.json 有 "type": "module"）的最外層同時寫了 Promise.resolve().then(() => console.log('promise')) 和 process.nextTick(() => console.log('tick'))，在 Node 24 誰先印？

✓ 實測 Node 24.22.1：ESM 的頂層程式在非同步的載入流程裡執行，結束時正在清 microtask，所以 promise 先；CommonJS 的頂層是普通同步程式，跑完先清 nextTick。「nextTick 永遠最先」只在 CommonJS 或一般 callback 裡成立。它也不是隨機，同樣的模組格式每次結果一樣，只是規則依賴執行環境，所以不要依賴。

練習 5：setTimeout(a, 0) 和 setImmediate(b)，誰先執行？

✓ 兩者在不同 phase：timeout 在 timers，immediate 在 check。主程式裡要看 loop 第一次到 timers 時那 1ms 過了沒，所以不保證；I/O callback 在 poll 執行，下一個就是 check，所以 immediate 一定先。setTimeout(fn, 0) 也不是立刻，最少 1ms，而且要等目前的程式、nextTick、microtask 都跑完。

練習 6：fs.readFile 和 fetch 都會佔用 libuv 的 thread pool 嗎？

✓ 作業系統能同時盯著大量的網路連線，所以網路的收發不需要 thread pool（只有連線前把網域名稱查成 IP 的 dns.lookup 那一步會用到）；檔案、dns.lookup、pbkdf2 這類沒有好的非同步介面的工作才交給 thread pool。「Node 只有一條執行緒」只對你的 JavaScript 成立，libuv 在背後還有 thread pool。

常見錯誤

  • 以為 setTimeout(fn, 0) 會立刻執行：至少要等目前的程式、nextTick、microtask 都跑完，再等 event loop 走到 timers phase，實際最少 1ms。
  • 用遞迴 nextTick 或 microtask 處理大量工作：佇列清不完，event loop 到不了 poll，整個伺服器沒反應。分批處理時用 setImmediate 讓出 event loop。
  • 以為把函式改成 async 就會在背景執行：async 函式裡的同步部分照樣佔著唯一的執行緒，await 已完成的 Promise 也不會讓出 event loop。
  • 用 process.exit() 收尾：輸出接到管線時會被截斷。關掉撐著的 handle 讓程式自然結束，用 process.exitCode 設定結束碼。
  • 在程式裡設定 process.env.UV_THREADPOOL_SIZE：thread pool 可能已經建好了，不保證有效。在啟動指令或部署設定裡用環境變數設定。
  • 用 setTimeout 排很久以後的事：延遲超過 231−1 毫秒（約 24.8 天）時，Node 印出 TimeoutOverflowWarning 並改成 1 毫秒後就觸發（本機實測）。而且程序重啟計時器就不見了。長時間的排程交給排程器或資料庫。

小結

  • Node 用一條執行緒跑 JavaScript，靠非阻塞 I/O 把等待交出去，所以能同時服務很多請求；會讓所有請求一起卡住的，是 JavaScript 自己佔著執行緒。
  • 等待交給 libuv：網路 I/O 交給作業系統（kqueue、epoll），檔案、dns.lookup、部分 crypto、zlib 交給預設 4 條的 thread pool；callback 一律回到那條 JavaScript 執行緒上跑。
  • event loop 每圈經過 timers → pending callbacks → poll → check → close callbacks；新連線和 I/O callback 在 poll。setTimeout 在 timers、setImmediate 在 check：主程式裡兩者順序不保證，I/O callback 裡 setImmediate 一定先。
  • 每段 callback 跑完先清 nextTick 再清 microtask，清空時新加的也一起清；ESM 和 CommonJS 頂層的先後不同，不要依賴。遞迴排 nextTick／microtask 會讓 I/O 餓死（/health 回不了），改用 setImmediate 讓出 event loop。
  • 沒有 ref 的 handle 時程序就結束；unref() 讓計時器不撐住程序；用 process.getActiveResourcesInfo() 查是誰撐著。關掉資源讓程式自然結束，不用 process.exit()。
  • 超過 thread pool 大小的工作會排隊，所以密碼雜湊的尖峰會拖慢讀檔；UV_THREADPOOL_SIZE 要在啟動前設定，調之前先確認瓶頸。

補充與查表

版本備註

  • 官方的 event loop 文件註明：Node 20（libuv 1.45.0）起，timers 改成在每一圈的 poll 之後才執行。正文的 phase 順序和 setTimeout／setImmediate 的兩條規則不受影響。這課以 Node 24.22.1（libuv 1.52.1）為準。
  • process.getActiveResourcesInfo() 從 v24.0.0 起是穩定功能。

thread pool 的細節

  • node:fs 的非同步操作都交給 thread pool，只有監看檔案變動的 fs.watch 例外。
  • UV_THREADPOOL_SIZE 的上限是 1024。

AbortSignal.timeout 不撐住程序

AbortSignal.timeout(ms) 內部的計時器不會撐住程序：如果頂層 await 只在等它，程序會直接以結束碼 13（頂層 await 沒有完成）結束，而不是等它逾時。
