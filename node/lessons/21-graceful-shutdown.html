階段 5：上線前的準備 · 第 21 課

優雅關機與健康檢查

咖啡店的訂單 API 一天部署好幾次。最近維運發現一個規律：每次部署，監控上就跳出一小撮 502 和「連線被重設」，不到一分鐘就消失；客服偶爾收到客人回報「結帳畫面顯示失敗，但好像有扣款」。把錯誤圖表跟部署時間疊在一起，兩者完全對得上。

問題出在舊程序被關掉的方式。部署時平台會先開新程序、再關舊程序；舊程序如果一收到通知就直接倒下，正在結帳的請求會斷線，扣了庫存的交易可能做到一半，最後幾行 log 也來不及寫出去。這一課的任務是讓部署對客人無感：王小明在部署那一刻按下結帳，他的請求要照常成功；新上線的程序也不能在資料庫還沒準備好時就開始接客。學完你能寫出一個會照順序收尾、會回報自己狀態、啟動時會等依賴的 Node 服務。

這課的路線：
  1. 部署那一刻舊程序經歷了什麼、誰通知它結束：服務的生命週期，SIGTERM 怎麼送到你的程式，攔下來之後由誰決定何時結束。
  2. 怎麼讓負載平衡器先別送新請求：健康檢查的 liveness 和 readiness 各回答什麼問題、各該檢查什麼。
  3. 手上的結帳請求怎麼做完再關：優雅關機的步驟與順序，以及請求都做完了、程序卻還不結束的 keep-alive 問題。
  4. 排空永遠做不完怎麼辦：關機的時限與第二次訊號。
  5. 新程序上線時資料庫還沒好怎麼辦：啟動時有限次數的重試。
這課會用到：
  • 第 2 課的訊號與結束碼：訊號是作業系統送給程序的通知，SIGTERM 是「請結束」；0 是成功、非 0 是失敗。
  • 第 7 課的 handle：計時器、連線這類還在等的東西會撐住 event loop，程序不會結束；.unref() 讓它不撐住。
  • 第 13 課的 createServer：建立 HTTP 伺服器，listen 之後開始接請求。
  • 第 20 課的連線池：程序共用一組資料庫連線，結束前要 await pool.end() 全部關掉。

部署那一刻，舊程序經歷了什麼？

要知道王小明的結帳為什麼會失敗，先看一個程序從啟動到結束會經過哪些階段。這些階段合起來叫生命週期（lifecycle）。一個 API 服務大致是這樣：

上半圈是開店：讀設定、確認資料庫連得上，然後開始 listen 接請求。圖裡的 readyz 是程序回報「我現在能不能接客」的網址，健康檢查那一節會講。下半圈是打烊：收到結束通知，先告訴外界「別再送客人來」，把店裡的客人服務完（這一步叫排空），關掉資料庫連線這類資源，最後結束。

這下半圈不是偶爾才發生的事。部署新版本（部署課第 16 課）會先開新程序、再關舊程序；流量變少時平台會關掉幾個程序；機器維修時程序會被搬到別台機器。每一次都會走「收到 SIGTERM → 結束」這半圈，一天可能走好幾十次。

回頭看開場的 502：那時的訂單 API 根本沒有下半圈，收到通知就從「服務中」直接跳到「結束」。正在跑的請求跟著程序一起消失，所以客人看到失敗。請求是負載平衡器轉給程序的，程序在回應前斷線，負載平衡器拿不到上游的回應，只好回給客人 502 Bad Gateway；直接連程序的客戶端則看到「連線被重設」。至於扣款：交易做到一半就斷，資料庫最後會回滾；也可能 COMMIT 已經完成、回應卻沒送出去。客人只看到失敗，不知道到底成功了沒，所以覺得「好像有扣款」。這課要做的，就是把下半圈一格一格補上。

下半圈的第一格是「收到 SIGTERM」。所以第一個問題是：這個通知是什麼、誰送的、你的程式收到之後能做什麼？

誰通知程序結束？攔下通知之後，誰決定何時結束？

通知程序結束的是訊號。第 2 課看過，訊號（signal）是作業系統送給程序的通知，每種訊號有名字和編號。跟關機有關的有三個：

訊號編號意思誰會送能攔截嗎
SIGINT2中斷，「使用者按了 Ctrl+C」終端機可以
SIGTERM15請你結束kill <pid>、docker stop、Kubernetes可以
SIGKILL9強制終止kill -9；平台等太久時不行，程序直接消失

三者的差別在「能不能攔截」。SIGINT 和 SIGTERM 是有禮貌的請求：程序可以先做點事再結束。SIGKILL 是作業系統直接把程序移除，程序沒有機會執行任何一行程式，所以它是平台最後的手段。這課要做的收尾全都發生在 SIGTERM 和 SIGKILL 之間；如果收尾拖到 SIGKILL 來了，等於又回到直接倒下。

如果你什麼都不寫，Node 對 SIGTERM 和 SIGINT 的預設處理是立刻結束，結束碼是 128＋訊號編號，所以從 shell 看是 143（SIGTERM）或 130（SIGINT）。這就是開場那個訂單 API 的行為：收到 SIGTERM 立刻消失。

要改變它，用 process.on('SIGTERM', fn) 加上監聽器。只要加了監聽器，預設行為就取消了：收到訊號不會再自動結束，什麼時候結束由你的程式決定（Node 24 process 文件）。另一方面，監聽器本身不會撐住 event loop：收尾做完、沒有 handle 了，程序就自然結束，不需要自己呼叫 process.exit。下面的範例看第一件事；範例用 setInterval 刻意撐住程序，所以看不出第二件事，它要到後面的 shutdown() 才看得到（最後兩行做完，程序自然以 0 結束）。執行後看結束碼，以及第一次 Ctrl+C 有沒有讓程序結束：

// examples/signal.ts（節錄）
console.log('pid', process.pid)
setInterval(() => {}, 1000)   // 讓程序一直活著

if (process.env.HANDLE) {
  let count = 0
  const onSignal = (signal: NodeJS.Signals) => {
    count++
    console.log(`收到 ${signal}（第 ${count} 次）`)
    if (count >= 2) process.exit(1)
  }
  process.on('SIGINT', onSignal)
  process.on('SIGTERM', onSignal)
}
$ node examples/signal.ts          # 另開終端機 kill <pid>
pid 51764
$ echo $?
143

$ HANDLE=1 node examples/signal.ts # 按 Ctrl+C 兩次
pid 51498
^C收到 SIGINT（第 1 次）
^C收到 SIGINT（第 2 次）
$ echo $?
1

第一段沒有監聽器，kill 一送，程序就以 143 結束。第二段的第一次 Ctrl+C 沒有讓程序結束：監聽器接手了，預設的「立刻結束」被取消。這帶來一個新責任：如果監聽器什麼都不做，使用者再怎麼按 Ctrl+C 都關不掉，只能 kill -9。所以範例在第二次訊號時呼叫 process.exit(1)，讓「再按一次」代表「我不想等了」。

正式環境沒有人按 Ctrl+C，送訊號的是執行容器的平台。它們的做法都是「先禮後兵」：先送 SIGTERM，等一段時間，還沒結束就送 SIGKILL。這段等待的最長時間叫關機時限（grace period），你的收尾必須在這段時間內做完。

  • docker stop：送 SIGTERM 給容器的主程序，預設等 10 秒，還沒結束就 SIGKILL（部署課第 8 課）。
  • Kubernetes（管理大量容器的平台）：同樣先 SIGTERM，關機時限預設 30 秒，到了就 SIGKILL。

注意上面寫的是「主程序」：訊號只送給容器裡最先啟動的那一個程序，不會自動傳給它開出來的子程序。第 3 課實測過：npm start 會把 SIGTERM 轉送給你的 node server.ts，node --run start 不會，你的程式被留在原地，什麼都沒收到，最後被 SIGKILL。所以容器裡的主程序直接寫 node server.ts，你寫的關機程式才收得到訊號。

到這裡，程式收得到 SIGTERM，也能自己決定何時結束。但收到訊號的當下，負載平衡器還在持續把新的結帳請求送過來。開始收尾之前，要先讓它別再送；這要靠健康檢查。

怎麼讓負載平衡器別再送新請求過來？

先說誰在送請求。正式環境的訂單 API 通常不只一個程序，客人的請求先到負載平衡器（load balancer），由它分給各個程序或各台機器（部署課第 12 課的 Nginx、第 13 課的水平擴展）。部署時舊程序要退場，負載平衡器得知道這件事，才會把新請求改送給新程序。

負載平衡器不會讀你的程式碼，它知道程序狀態的方法是定期去問：每隔幾秒對每個程序打一個固定的網址，看回應的狀態碼。程序提供的這種網址叫健康檢查端點（health check endpoint）。

平台會問兩個不同的問題，答「不行」之後的處置也不同：

liveness（存活）readiness（就緒）
問題這個程序還活著嗎？現在可以送流量給你嗎？
慣用路徑/healthz/readyz
檢查什麼只要能回應就是 200，不碰任何依賴依賴（資料庫）可用、而且不在關機中才 200
失敗時平台做什麼重新啟動這個程序暫時不送新流量給它，程序不動
什麼時候會失敗程序卡死（例如 event loop 被同步迴圈卡住，第 9 課）資料庫斷線、啟動中、關機中

為什麼要分成兩個？因為「程序壞了」和「程序暫時不方便接客」需要完全不同的處理。程序卡死時，重新啟動是唯一的辦法，這是 liveness 的工作。程序本身好好的，只是暫時不該接新請求，就只要把它從分流名單拿掉，等它好了再加回來，這是 readiness 的工作。

關機中的程序正好是第二種：它很健康，手上還有王小明的結帳要做完，只是不想再接新的。所以收到 SIGTERM 時，把 /readyz 改成回 503，/healthz 照樣回 200。靠健康檢查摘除程序的負載平衡器（例如 Nginx 或雲端負載平衡器），下一次檢查看到 503，就不再送新請求給它，而且不會重啟它，讓它安心收尾。Kubernetes 摘除的時機不同：Pod 一進入終止流程，就被標成不接一般流量，不必等 readiness 失敗（Kubernetes Pod termination 文件）。

分清楚這兩個問題，也能避開最常見的錯誤：liveness 也檢查資料庫，理由是「檢查越多越安全」。想像資料庫重開，晃了 30 秒：所有程序的 liveness 同時失敗，平台把它們全部重新啟動。重啟不會讓資料庫變好，反而所有程序同時在啟動、同時重新建立連線，把剛恢復的資料庫又打垮。資料庫不可用時該做的是「先別送流量」，那是 readiness 的工作。

寫成程式是這樣，shuttingDown 是收到 SIGTERM 時設成 true 的旗標：

if (pathname === '/healthz') return sendJson(res, 200, { status: 'ok' })
if (pathname === '/readyz') {
  if (shuttingDown) return sendJson(res, 503, { status: 'not ready', reason: 'shutting down' })
  try {
    await withTimeout(checkDb(), 500)   // checkDb 例如 pool.query('SELECT 1')
  } catch (err) {
    return sendJson(res, 503, { status: 'not ready', reason: `database: ${(err as Error).message}` })
  }
  return sendJson(res, 200, { status: 'ready' })
}

注意 checkDb() 外面包了 withTimeout。資料庫卡住時，SELECT 1 可能一直不回來，/readyz 也跟著卡住。平台的檢查有自己的逾時，到了一樣判失敗，但你的程序裡會堆著一堆等不到結果的檢查請求，每幾秒多一筆。所以自己先設一個比平台短的上限，例如 500ms，時間到就回 503。

withTimeout 通常用 Promise.race 讓 checkDb() 和一個 setTimeout 賽跑。容易漏的是：checkDb() 先贏時，那個 setTimeout 還在，它會多撐住 event loop 500ms，關機時程序就晚 500ms 結束。所以不管誰贏，最後都要把計時器清掉。寫法在練習 1。

失敗時回 503 Service Unavailable，body 寫原因。平台只看狀態碼，reason 是給半夜查問題的人看的：看到 shutting down 就知道是正常的關機，看到 database: … 就知道要去看資料庫。

💡 實務上：readiness 只放「少了它就完全不能服務」的依賴
健康檢查的請求很頻繁（平台每隔幾秒就對每個程序各打一次），/readyz 的檢查要便宜：一句 SELECT 1 可以，跑報表查詢不行；也不要每次都寫 access log（第 19 課），不然 log 一半都是健康檢查。檢查的對象也要挑：咖啡店訂單 API 少了資料庫什麼都做不了，算；寄收據的 email 服務、第三方金流就不該放進去，否則外部服務一晃，你所有程序會一起被摘除（負載平衡器不再送流量），整個網站下線。上線前資深工程師會跟維運確認平台的檢查間隔、逾時，以及失敗幾次才判定，健康檢查的逾時和關機的等待時間都跟這些數字有關。

readiness 改成 503 之後，新請求不會再來。但已經在處理中的那幾筆，像王小明正在跑的結帳，還在等資料庫回應。下一步是讓它們做完再關。

手上的結帳請求，怎麼做完再關？

做完手上的工作、關好資源再結束，叫優雅關機（graceful shutdown）。其中「不再接新工作，等進行中的完成」這一段叫排空（draining），就是生命週期圖下半圈中間那格。完整的步驟和順序：

  1. readiness 改成 503：讓負載平衡器停止送新流量（上一節）。
  2. server.close()：不再接受新連線，之後連進來的會被拒絕（ECONNREFUSED）。
  3. 等進行中的請求完成，並關掉閒置的 keep-alive 連線。server.close(callback) 的 callback 在所有連線都關掉後才呼叫。
  4. 關閉資源：資料庫 pool（await pool.end()）、計時器、其他連線。
  5. 自然結束：沒有 handle 撐住 event loop，程序以結束碼 0 結束（第 7 課）。

這個順序的原則是「先擋住入口，再等裡面的人離開，最後才關燈」。每一步都在保護前一步還在進行的工作，所以順序不能反。舉例來說，如果先關 pool 再關伺服器，王小明的結帳請求還在處理，下一句查資料庫時會拿到 Cannot use a pool after calling end on the pool（pg 的錯誤訊息），客人收到 500，跟直接倒下沒兩樣。

那為什麼不收到 SIGTERM 就 process.exit(0)，乾脆俐落？因為 exit 會立刻結束程序，不管手上還有什麼：

  • 進行中的請求斷線，客人看到失敗。
  • 交易沒有 COMMIT 也沒有 ROLLBACK。資料庫最後會把它回滾，但客人不知道結果，這就是「顯示失敗、好像有扣款」的來源。
  • 還在寫入的 log 可能掉了：第 19 課講過，stdout 接管線時是非同步寫入，程序一結束，還沒送出的就沒了。事後要查也查不到。

結束碼也寫 0，讓平台以為一切正常。優雅關機反過來，不呼叫 exit，把東西一樣一樣關掉，讓程序因為「沒事可做」而自然結束。

第 1 步和第 2 步之間還有一個時間差。readiness 改成 503 之後，負載平衡器要等到下一次檢查才會知道，在那之前它還會送新請求過來，而第 2 步的 server.close() 已經在拒絕連線了。

所以有些團隊收到 SIGTERM 後先等幾秒（例如 5 秒，略大於檢查間隔）才呼叫 close()。代價是每次部署變慢；要不要等，看平台怎麼摘除程序（部署課第 26 課）。

照這個順序寫，理論上請求做完、pool 關掉，程序就自然結束。實際跑起來卻常常多拖好幾秒，甚至拖到平台的時限。問題出在第 3 步提到的 keep-alive 連線。

請求都做完了，程序為什麼還不結束？

先回顧 keep-alive。第 12 課講過，HTTP/1.1 預設 keep-alive：一個請求做完，TCP 連線不關，留著給同一個客戶端的下一個請求用，省掉每次重新建立連線的時間。對效能是好事，但對關機是麻煩：每條留著的連線都是一個 handle，會撐住 event loop。

server.close() 處理連線的方式是這樣：呼叫的當下，閒置的連線會被關掉；正在處理請求的連線不動，讓請求做完。問題在後者：王小明的結帳請求在 close() 呼叫時還在處理，回應送出之後，那條連線就變成閒置，但 close() 已經呼叫過了，不會再回頭去關它。這條連線要等客戶端自己關，或等伺服器的 keep-alive 逾時（keepAliveTimeout）到期；在 Node 24 上合計約 6 秒（版本細節見課末）。在它關掉之前，close() 的 callback 不會被呼叫，關機流程就停在第 3 步。

下面的範例在一個 1 秒的慢請求進行中呼叫 server.close()。執行後看「慢請求完成」和「callback」之間差了多久：

$ node examples/keep-alive.ts
127ms 呼叫 server.close()
1059ms 慢請求完成
4066ms server.close 的 callback：所有連線都關了

$ FIX=1 node examples/keep-alive.ts
111ms 呼叫 server.close()
1021ms server.close 的 callback：所有連線都關了
1027ms 慢請求完成

這是在這台電腦上用 Node 24.22.1 跑的結果。第一段裡，請求 1 秒就做完了，程序卻多等了 3 秒，因為 fetch 的客戶端把連線留著。如果客戶端是用 http.Agent 的 keepAlive 這類不會自己關閒置連線的寫法，要等滿約 6 秒。部署時每個舊程序都多等幾秒，平台的時限一緊就被 SIGKILL，又回到直接倒下。第二段加了修正，連線在請求完成時就關了。

修法有兩種，目標都是「請求做完的那一刻，順手把連線關掉」。第一種是上面 FIX=1 的做法：關機期間的回應加上 Connection: close。這個 header 告訴客戶端「這條連線用完就關」，Node 送完這個回應也會自己關掉連線，所以最後一個請求做完，最後一條連線也跟著關了：

function sendJson(res: ServerResponse, status: number, data: unknown) {
  const body = Buffer.from(JSON.stringify(data))
  const headers: Record<string, string> = { 'content-type': 'application/json; charset=utf-8', 'content-length': String(body.length) }
  if (shuttingDown) headers.connection = 'close'
  res.writeHead(status, headers)
  res.end(body)
}

第二種是每完成一個請求就呼叫 server.closeIdleConnections()，把當時閒置的連線全部關掉。效果一樣，差別在第一種只改回應的 header，第二種要在請求完成的地方多掛一段程式。

💡 實務上：「每次部署都有一小段 502」通常是關機沒寫好
常見情境：咖啡店後台每次部署，監控上就跳出一小撮 502 或連線被重設，客服偶爾收到「結帳顯示失敗，但好像有扣款」。資深工程師會先把錯誤圖表跟部署時間對起來，對得上就依序查：主程序收不收得到 SIGTERM、readiness 有沒有先改 503、keep-alive 有沒有處理、pool 是不是最後才關。驗證不用很複雜：本機用迴圈持續打 API，同時對服務送 SIGTERM，看有沒有任何請求失敗。之後改用 Fastify 這類 Web 框架時，框架有自己的關機掛鉤（hook），但順序和時限仍要自己確認，不要假設預設就對。

keep-alive 處理好之後，正常情況下幾秒內就能關完。但「正常情況」不保證每次都成立：如果某個請求永遠做不完呢？

排空永遠做不完怎麼辦？

排空是「等進行中的請求完成」，而有些請求不會完成。例如某個請求卡在一個沒有逾時的上游呼叫，或是 SSE 這種本來就不會結束的長連線（第 16 課）。只要有一個這種請求，server.close() 的 callback 就永遠等不到，程序會一直撐到平台的時限，被 SIGKILL 砍掉，連一行「為什麼關不掉」的 log 都沒留。

所以關機一定要有自己的時限，而且比平台的短一點（平台 30 秒，你可以設 25 秒）。時間到了就自己收拾：強制斷線、留下 log、以非 0 結束。被自己的時限關掉和被 SIGKILL 砍掉，結果都是有請求失敗，差別在前者知道發生了什麼。再加上前面 SIGINT 範例的第二次訊號處理，整段關機程式是這樣：

async function shutdown(signal: NodeJS.Signals) {
  if (shuttingDown) process.exit(1)          // 第二次訊號：使用者不想等了
  shuttingDown = true

  setTimeout(() => {
    console.error(JSON.stringify({ msg: 'shutdown timeout, forcing exit', signal }))
    server.closeAllConnections()             // 連進行中的也一起斷
    process.exit(1)                          // 沒有完整收尾，結束碼不是 0
  }, timeoutMs).unref()                      // unref：這個計時器不撐住程序

  await new Promise<void>(resolve => server.close(() => resolve()))
  await pool.end()
}
process.on('SIGTERM', shutdown)
process.on('SIGINT', shutdown)

由上往下看：

  • if (shuttingDown) process.exit(1)：已經在關機中又收到訊號，代表有人不想等了（開發時多按一次 Ctrl+C），立刻結束。
  • 時限的 setTimeout：時間到先記一筆 log，寫下為什麼強制結束，事後才查得到；接著呼叫 server.closeAllConnections()，連正在處理請求的連線也關掉。這是強制手段，只在時限到了才用。結束碼用 1，讓平台和監控知道這次關機沒有完整收尾。
  • .unref()（第 7 課）：這個計時器不撐住程序。沒有它，就算一切在 0.1 秒內收好，程序也要等到時限的計時器觸發才結束，而且是以結束碼 1 結束，看起來像關機失敗。也可以存下計時器，最後 clearTimeout。
  • 最後兩行就是上一節「手上的結帳請求」的關機順序：等伺服器關好，再關 pool。兩者都做完，沒有 handle 了，程序自然以 0 結束。

SSE 這類長連線不該靠時限硬砍。它們本來就不會自己結束，所以關機時要主動結束：對每個串流送最後一則事件再 res.end()，客戶端的 EventSource 會自動重連，而負載平衡器會把重連送到別的程序。

💡 實務上：不只 HTTP 伺服器，背景工作也要能優雅停下
咖啡店的佇列 worker 正在寄訂單收據、排程程式正在跑每日對帳，部署時被砍在一半，就可能重複寄信或對帳只做一半。思路跟 HTTP 一樣：收到訊號就不再拿新工作，把手上這一筆做完（或放回佇列）再結束。如果單筆工作可能超過平台的關機時限，就要把工作切小，或讓它被重做也不會出錯。Code review 看到會長時間執行的程式，資深工程師會問一句：「這支被 kill 在一半會怎樣？」

到這裡，舊程序的下半圈完整了。但部署還有另一半：新程序上線。它也可能在資料庫還沒準備好時就開始接客。

新程序上線時，資料庫還沒好怎麼辦？

回到生命週期圖的上半圈第一格「啟動」。新程序啟動時會碰到兩種錯誤，處理方式完全相反，要先分開：

  • 設定錯了（環境變數缺少、格式不對）：再試幾次也不會好，立刻印出原因並以結束碼 1 結束，這是第 2 課的 fail fast（快速失敗）。
  • 依賴暫時還沒好：容器一起啟動時，資料庫常常比 API 晚幾秒準備好。這種錯誤等一下就會好，值得重試。但不能無限重試：資料庫網址打錯時，程序會永遠卡在「啟動中」，平台看起來它還活著，沒人發現。

第二種的做法是有限次數加退避，也就是第 17 課的指數退避：每次失敗後等久一點再試，例如間隔 100、200、400、800ms，最多 5 次。間隔越拉越長，是為了給資料庫越來越多的準備時間，而不是在它還在開機時一直敲門。每次失敗都記 log，事後才看得出是「試了兩次就好」還是「五次都失敗」。全部失敗就以結束碼 1 結束，交給監督者（Docker 的 restart policy、Kubernetes）決定要不要重新啟動。

還有一個順序：檢查成功之後才 listen。一 listen，負載平衡器就可能把流量送進來；資料庫還不能用的期間接到的每一筆結帳都會失敗，等於把舊程序關機時避開的錯誤，換到新程序啟動時再犯一次。

另一種做法是先 listen，但 /readyz 回 503 直到依賴可用。這也是前面健康檢查那一節 readiness 的用法：程序活著，但還不接客。兩者的取捨：

重試後 fail fast先啟動、readiness 503
錯誤看得見嗎程序反覆重啟，平台上一眼看得到程序活著但一直沒就緒，要看 readiness 才知道
依賴恢復時要等平台重啟程序自己恢復，不用重啟
適合資料庫是必要依賴，沒它什麼都做不了有部分功能不需要該依賴；或啟動成本很高

咖啡店的訂單 API 沒有資料庫什麼都做不了，所以這課的練習用第一種，它比較單純，錯誤也最明顯。

把整課串起來，一次部署就是：新程序等到資料庫可用才 listen、readiness 回 200，開始接客；舊程序收到 SIGTERM，readiness 改 503，等王小明的結帳做完、連線關好、pool 關掉，在時限內以 0 結束。兩邊都做到，客人就感覺不到部署。

Node 的 HTTP 關機相關 API（依 Node 24 http 文件），查表用，不用背：

API／設定行為版本

被訊號結束時的結束碼：從 shell 看是 128＋訊號編號（SIGTERM 143、SIGINT 130）；從 Node 的父程序（例如用 child_process 啟動它的測試）看，是 code null、signal 'SIGTERM'。練習 2、3 的測試就是用子程序啟動你的程式。

SIGTERM 和 uncaughtException 的收尾不一樣：第 18 課的 uncaughtException 也是一種結束，但那時程式狀態已經不可信，記 log、停止接新請求、以 1 結束，不需要等排空。SIGTERM 是「程式很健康，只是該下班了」，值得花幾秒好好收尾。

練習

在 learn/ 執行 node check.mjs node 21 建立 work/21/，裡面有內文的範例（examples/）、假的連線池 pool.ts（行為模仿 pg，end() 之後再 query 會丟錯）、練習 3 的進入點 main.ts，和三題的起始檔。練習 2、3 的測試會用子程序啟動你的程式並送訊號；想自己試，照檔案開頭的註解執行。

練習 1：app.ts 的 createApp({ checkDb }) 回傳 { server, startShutdown }。加上兩個端點：GET /healthz 永遠回 200 和 { status: 'ok' }，不能呼叫 checkDb；GET /readyz 每次都呼叫 checkDb()，成功回 200，失敗回 503，body 帶字串 reason 說明原因；checkDb 超過 500ms 沒結果也算失敗（測試的 checkDb 會卡住永遠不回應，/readyz 要在約 500ms 後回 503，測試最多等 2.5 秒）；呼叫 startShutdown() 之後 /readyz 一律回 503，/healthz 仍是 200。

練習 2：讓 server.ts 收到 SIGTERM 或 SIGINT 時優雅關機：不再接受新連線、等進行中的請求完成、不被 keep-alive 連線拖住；伺服器關好時印 {"msg":"server closed"}，接著 await pool.end()（它會印 {"msg":"pool closed"}），最後印 {"msg":"bye"}，以結束碼 0 結束。SHUTDOWN_TIMEOUT_MS（預設 10000）毫秒內沒做完，就強制關閉所有連線並以結束碼 1 結束。關機途中又收到訊號，立即以結束碼 1 結束。測試會在 1.5 秒的請求進行中送 SIGTERM，客戶端會一直留著 keep-alive 連線：那個請求要成功，程序要在它完成後馬上結束（測試容許 2.5 秒，只呼叫 server.close() 會多等約 6 秒）。

練習 3：完成 start.ts 的 start({ checkDb, listen })（main.ts 會傳入假的 checkDb，用環境變數 FAIL_TIMES 控制前幾次失敗）。checkDb() 成功才呼叫 listen()；失敗就等一下再試，間隔依序 100、200、400、800ms，最多試 5 次；每次失敗都用 console.error 印出錯誤的 message；5 次都失敗就以結束碼 1 結束，不呼叫 listen，最後一次失敗後不用再等。

練習 4：同事把 Kubernetes 的 liveness 檢查改成「SELECT 1 成功才回 200」，理由是檢查越多越安全。某天資料庫重開，晃了 30 秒。會發生什麼事？

✓ liveness 失敗的處置是重新啟動程序，而資料庫的問題不會因為重啟 API 而變好，所有實例同時重啟還會讓服務完全中斷、連線數瞬間暴增。a 忽略了 liveness 失敗幾次後平台就會動手。c 描述的是 readiness 的行為：依賴檢查應該放在 readiness，liveness 只回答「程序還能不能回應」。

練習 5：收到 SIGTERM 後呼叫了 server.close()，所有請求都回應完了，程序卻過了好幾秒才結束（或一直不結束）。最可能的原因是？

✓ 程序在沒有 handle 撐住 event loop 時自然結束。close() 不會關掉呼叫之後才閒置的 keep-alive 連線，要等客戶端或 keepAliveTimeout；關機時限的計時器沒 unref、pool 沒 end() 也會撐住。a 會讓進行中的請求失敗；b 錯在監聽器只是取消預設的「立刻結束」，不會撐住程序。

練習 6：Dockerfile 的最後一行寫 CMD ["node", "--run", "start"]，start 腳本是 node server.ts，裡面寫好了 SIGTERM 的優雅關機。docker stop 時會怎樣？

✓ 第 3 課在 Node 24.22.1 實測：node --run 收到 SIGTERM 不會轉送給子程序（npm start 會，npm 11.19.1）。容器的主程序是收訊號的那一個，所以直接寫 CMD ["node", "server.ts"]，中間不要多一層。b 錯在多了一層 node --run，訊號到不了你的程式；c 錯在 node --run 不會等子程序，它收到 SIGTERM 就自己先結束了。

常見錯誤

  • 容器裡用 npm start 或 node --run 當主程序：多一層程序，訊號可能到不了你的程式，寫好的關機程式根本沒執行。直接 node server.ts。
  • 攔截 SIGINT 後第二次 Ctrl+C 沒反應：開發時只能 kill -9。關機中再收到訊號就立刻結束。
  • liveness 檢查依賴：依賴一晃，所有程序一起被重啟。依賴放在 readiness，liveness 能回應就是 200。
  • readiness 沒有逾時：資料庫卡住時健康檢查也卡住、請求越堆越多。設一個比平台短的上限，逾時用的計時器要清掉。
  • 收到 SIGTERM 就 process.exit(0)：進行中的請求斷線、交易結果不明、log 可能沒寫完。照順序收尾，讓程序自然結束。
  • 先關 pool 再關伺服器：進行中的請求查資料庫失敗。先等伺服器關好，再 pool.end()。
  • 只呼叫 server.close()：之後才閒置的 keep-alive 連線讓關機拖延好幾秒。關機中的回應加 Connection: close，或請求完成後 closeIdleConnections()。
  • 關機沒有時限：一個卡住的請求或 SSE 長連線讓程序永遠不結束，最後被 SIGKILL，連 log 都沒有。設時限，到了 closeAllConnections() 並以 1 結束；計時器要 unref()。
  • 啟動時無限重試，或先 listen 再檢查：前者讓設定錯誤永遠沒人發現，後者在依賴還沒好時就接流量。有限次數退避，成功才 listen。

小結

  • 部署時的 502 來自舊程序直接倒下。服務的一生：啟動（設定、依賴）→ 就緒 → 服務中 → SIGTERM → 不再就緒、排空 → 關閉資源 → 結束。每次部署、縮減、重啟都會走一遍下半圈。
  • 平台先送 SIGTERM，關機時限到了才送攔不到的 SIGKILL。SIGTERM／SIGINT 預設以 128＋編號結束，加了監聽器就由你決定何時結束。容器主程序直接執行 node，訊號才到得了你的程式。
  • /healthz（liveness）只看程序能不能回應，失敗會被重啟；/readyz（readiness）檢查依賴（有逾時）與是否關機中，失敗回 503，只是暫時不送流量。
  • 關機順序：readiness 503 → server.close() → 等請求完成並處理 keep-alive → pool.end() → 自然結束。close() 不關之後才閒置的連線，關機中的回應要加 Connection: close。
  • 關機要有比平台短的時限（計時器 unref），到了 closeAllConnections() 並以 1 結束；第二次訊號立即結束。
  • 新程序啟動時暫時不可用的依賴：有限次數退避重試，成功才 listen，全部失敗以 1 結束交給監督者。
