階段 6：資深工程師的功課 · 第 26 課

期末專題：不用框架的咖啡店訂單 API

星期六早上，王小明在捷運上用咖啡店的 App 點了兩杯拿鐵。按下「送出」的那一刻列車進了隧道，畫面轉了十秒之後顯示失敗，他又按了一次。同一個早上，店裡剛好在部署新版本；櫃台兩個店員，一個對這張訂單按了「開始製作」，另一個按了「取消」；王小明出隧道後一直盯著訂單頁，等它變成「可以取餐」。這一個早上同時考驗了好幾件事：重按會不會扣兩次錢、部署那一刻的請求會不會掉、兩個店員的操作誰說了算、出事時客服查不查得到原因。

前面 25 課，每一課練一個零件：設定、伺服器、錯誤格式、快取、SSE、外部呼叫、log、交易、關機、安全。王小明的那個早上需要這些零件同時運作：一個下單請求會經過 body 上限、驗證、交易、冪等鍵、log 和錯誤邊界，任何一環沒接好，出事時就查不到原因，或是在部署時掉單。這一課把整個訂單 API 從頭做一遍，不用框架，只用 node:http 和 pg，從頭到尾跟著王小明這張訂單走。

這課不教新語法，每一步都標出對應的課。要練的是三件資深工程師每天在做的事：把模糊的需求寫成可以驗收的條件、在動手前把介面與錯誤設計好、用自動化測試和上線檢查清單證明它能上線。

這課的路線：
  1. 老闆說「網路斷了不要重複下單」，怎樣才算做完：把需求改寫成驗收條件，切成里程碑。
  2. 動手之前先定合約：王小明的 App 打哪條路由、成功與每一種錯誤長什麼樣，再加上設定與資料表；接著決定檔案怎麼分、依賴怎麼傳進來，測試才不用啟動整個程序。
  3. 王小明按下送出之後，請求依序經過哪些關卡，出錯時他和客服各看到什麼。
  4. 四個並發與故障的決策：重按兩次怎麼只有一張訂單、兩個店員同時按聽誰的、狀態怎麼即時推給王小明、供應商掛了怎麼不被拖垮。
  5. 照什麼順序動手，測試全過之後，怎麼確認真的可以上線。
這課會用到：
  • 第 14 課的 API 設計：錯誤用 problem details、列表用 cursor 分頁、POST 帶 Idempotency-Key 才能安全重送。
  • 第 18 課的錯誤邊界：處理函式只管丟錯，由一個地方轉成回應；500 不給細節，只給可以對 log 的 errorId。
  • 第 20 課的連線池與交易：交易裡每一句都用同一條借出來的連線，用完一定還。
  • 第 21 課的健康檢查與優雅關機：收到 SIGTERM 先讓 readyz 回 503、做完進行中的請求再關資源。

老闆說「網路斷了不要重複下單」，怎樣才算做完？

王小明重按兩次的那件事，老闆的說法是「網路斷了不要重複下單」。這句話聽得懂，但沒辦法拿來判斷做完了沒有：怎樣叫「網路斷了」？請求送到了、回應沒回來，算不算？服務通常同時跑好幾個程序，前面的負載平衡器把每個請求分給其中一個，所以重送的請求不一定回到同一個程序（第 24 課）。重按的請求剛好被送到另一台機器，又算不算？每個人心裡的答案不一樣，做完之後就會吵「我以為是這樣」。

所以和 PostgreSQL 課的期末專題一樣，先寫需求，再談技術。工程師的第一個工作，是把老闆的話改寫成驗收條件（acceptance criteria）。驗收條件是一句可以用測試判斷對錯的話，說清楚「怎樣才算做完」。它有三個特徵：講的是外面看得到的行為（回什麼狀態碼、資料庫最後是什麼樣子），不是實作方式；條件寫得具體到可以造出來重現（幾個人、同時、送到哪一台）；結果只有對或錯，沒有「大概可以」。

「網路斷了不要重複下單」照這個標準改寫，就變成「同一個 Idempotency-Key 不管送到哪一台機器，只建立一張訂單」。Idempotency-Key 是第 14 課教過的冪等鍵：App 第一次送出時產生一個唯一的字串放在標頭裡，重送時帶同一個，伺服器靠它認出「這是同一個請求的重送」。改寫之後，測試怎麼寫就很清楚了：同一個 key 送兩次，其中一次送到另一個程序，最後資料庫只能有一張訂單。老闆其他的要求也一樣改寫：

右欄每一句之後都會變成一個測試。反過來說，需求寫不出驗收條件，通常代表還沒想清楚。例如「手機上要快」，是多快？這裡用快取標頭回答：內容沒變就回 304、不重傳 body，手機少下載一次菜單。正式專案還會再寫成延遲的目標，例如 p99（把請求依耗時排序，99% 的請求都在這個時間以內）要在多少毫秒內，用第 23 課的方法量。最後兩列是營運的需求，老闆不會說，但上線之後出事時第一個需要它們的就是你，所以工程師要自己補上。

七列需求一次做不完，也不該一次做完：全部寫完才第一次跑測試，壞掉時不知道是哪一部分壞的。所以把它們切成里程碑（milestone）。里程碑是一段可以獨立驗收的進度：做完就有一組測試會從失敗變成通過，而且不必等其他里程碑。這課切成 6 個里程碑，每個對應一題練習和一個測試檔，順序在「從哪裡開始動手」那一節再說明。

💡 實務上：拿到需求單，先問到能寫出驗收條件為止
工作中的需求常常只有一句話，例如 PM 開的單寫「訂單頁要即時更新」。動手前先回問：即時是指幾秒內？誰在看？連線斷了怎麼辦？把答案寫成驗收條件貼回需求單，讓 PM 確認，之後驗收時大家看的是同一份東西，不會吵「我以為是這樣」。里程碑也是溝通工具：每做完一個就能展示、能上線，PM 中途改需求時，你也知道哪些做完的不會受影響。

驗收條件說的是系統的行為，但還沒說王小明的 App 要打哪個網址、失敗時會收到什麼。前端工程師拿到上面那張表，還是沒辦法開始寫。

動手之前，要先定下哪些合約？

先從王小明的 App 要知道什麼開始。App 要知道的是介面：有哪些路由、每條路由成功時回什麼、失敗時又分成哪幾種。這份東西要在寫程式之前定下來，因為它是前端、後端、測試三方的共同合約：前端照它寫畫面和錯誤處理，後端照它實作，測試照它斷言。少了這份合約，常見的情況是寫到一半才有人問「庫存不足要回 400 還是 409」，前端已經照 400 寫好了，後端回的是 409。

合約最清楚的寫法是一張路由表。表裡「錯誤」那一欄和「成功」一樣重要：王小明的 App 要對每一種錯誤做不同的事，例如 409 out-of-stock 顯示「拿鐵賣完了」，409 request-in-progress 則是等一下再查結果。

狀態碼照第 14 課的分法選：請求本身格式不對（欄位少了、數量不是整數）回 400；格式對，但和資源目前的狀態衝突（庫存不夠、訂單已經不能這樣改、同一個 key 還在處理中）回 409；同一個冪等鍵被拿來送內容不同的請求，是客戶端的 bug，回 422。413、415 是第 13 課讀 body 時的檢查：累計長度超過上限回 413，Content-Type 不對回 415。

同樣是 409，App 的處理卻不一樣，所以只看狀態碼不夠，還要有一個欄位說明是哪一種錯。所有錯誤都用第 14 課的 problem details 格式（application/problem+json），type 是 https://coffee.example/problems/ 加上種類，例如 …/out-of-stock。客戶端用 type 判斷錯誤種類，不解析中文訊息：detail 是給人看的，改字或翻譯時 App 不會跟著壞。

對外的合約不只 HTTP 這一面。部署這個服務的人（可能是維運同事，也可能是三個月後的你）看不到程式碼，只看得到環境變數，所以設定也是介面的一部分。把它列成一張表，寫清楚哪些必填、預設值、格式；程式啟動時照這張表檢查，缺的一次列出全部、以結束碼 1 結束（第 2 課），而不是缺一個報一個，讓部署的人來回改五次：

最後是資料庫這一面。資料表沿用 coffee.sql 的 customers、products、orders、order_items，schema.sql 為了王小明那個早上加上三樣東西：

  • products.stock，帶 CHECK (stock >= 0)。庫存主要靠程式的條件式 UPDATE 守住，CHECK 是程式寫錯時資料庫最後擋一次的保險。
  • orders.status，帶 CHECK 限定五種狀態，店員的操作不會寫出第六種。
  • idempotency_keys 表（第 24 課），記錄每個冪等鍵和它第一次的回應。放在資料庫而不是記憶體，所以重送的請求不管落到哪個程序都查得到。

路由、錯誤、設定、資料表都定下來了，可以開始寫程式。但第一個決定不是寫哪一行，而是這些程式要放在哪裡。

程式怎麼分，測試才能換掉資料庫？

所有東西寫在一個檔案裡，第一週很快，第三週就沒人敢改：改菜單要捲過下單的程式，改一個地方不知道會不會影響另一個。這個專案依功能分檔案，每個檔案對應路由表的一兩列；所有路由都會用到的基礎設施（設定、logger、資料庫、回應工具）放在 platform/：

work/26/

  app.ts               createApp：路由表、請求管線、錯誤邊界、健康檢查
  menu.ts              GET /menu、GET /menu/:id
  restock.ts           GET /menu/:id/restock
  orders.ts            POST /orders、GET /orders/:id
  order-status.ts      PATCH /orders/:id、GET /orders/:id/events
  platform/config.ts   loadConfig(env)
  platform/logger.ts   結構化 logger（第 19 課）
  platform/db.ts       createPool、withTransaction（第 20 課）
  platform/http.ts     sendJson、sendProblem、readJson、HttpError、Ctx 型別
  schema.sql、examples/、ex1.test.ts … ex6.test.ts

分檔只解決「好不好找」。另一個問題是測試：驗收條件說「庫存 5、12 個人同時下單」，測試每次都要一個乾淨的資料庫；「出事查得到原因」要檢查 log 寫了什麼，測試要能讀到 log；「供應商掛了」要能造出一個會掛的供應商。如果 app 自己在裡面讀 process.env、自己 new Pool() 連到正式的資料庫、自己把 log 印到終端機，測試就只能整個程序跑起來，再從外面猜它做了什麼，什麼都換不掉。

做法是反過來：app 不自己去拿它需要的東西，而是由呼叫它的人傳進來。這就是依賴注入（dependency injection，第 22 課）。「依賴」指的是 app 要用、但不屬於業務邏輯本身的東西，這裡是設定、資料庫連線池、logger；「注入」指的是從參數傳進來。這個專案的入口是 createApp({ config, pool, logger })，app 自己不讀 process.env、不 new Pool()。這樣做有三個好處：

  • 測試：測試可以傳入指向全新資料庫的 pool、把 log 收進陣列的 logger、指向假供應商的 config，不用啟動整個程序。這課的練習 2、4、5 就是這樣測的。
  • 生命週期集中在 main.ts：pool 只在啟動時建立一次，關機時關一次。在處理函式裡 new Pool() 是常見的錯：每個請求開一個池子，連線數很快爆掉，而且沒人關。
  • 換掉零件：要把 logger 換成 pino，只改 main.ts 一行。

正式執行時，是 main.ts 讀環境變數、建立真的 pool 和 logger，再傳給 createApp；測試時，是測試檔建立假的或臨時的版本傳進去。app.ts 本身不知道、也不需要知道自己在哪一種情況下執行。

依賴進了 app 之後，還要再往下傳給每個處理函式。為了讓每個處理函式的寫法都一樣，app 把一個請求需要的所有東西裝進一個物件，叫 Ctx（context 的縮寫），意思是這個請求的執行環境。每個處理函式都拿到同樣形狀的 Ctx：

export type Ctx = {
  req: IncomingMessage, res: ServerResponse, url: URL,
  params: string[]            // 路由正規表示式的捕捉群組，/menu/(\d+) → ['2']
  config: Config, pool: pg.Pool,
  logger: Logger              // 已經帶著這個請求的 requestId
  orderEvents: EventEmitter   // 'status'：訂單換了狀態；'shutdown'：開始關機
}
export type Handler = (ctx: Ctx) => Promise<void>

注意 logger 那一行：處理函式拿到的不是全域的 logger，而是已經綁好這個請求 requestId 的那一個，它寫的每一行 log 都會自動帶上 requestId。這是怎麼做到的，下一節會看到。

處理函式還有一條規矩：遇到「客戶端的錯」（找不到商品、格式不對、庫存不足），就 throw new HttpError('not-found', '沒有編號 9 的商品')，不自己組回應。HttpError 是 platform/http.ts 定義的錯誤類別，帶著 problem 的種類和要給客人看的說明。為什麼不讓處理函式自己回 404？因為錯誤格式要全站一致，而一致最可靠的方法，是只有一個地方負責把錯誤變成回應；處理函式各自組回應，遲早有人漏了 type，或把 Content-Type 寫錯。

💡 實務上：這些分層就是框架替你做的事
依功能分檔、依賴從參數傳入、處理函式只丟錯，這三件事正好是 NestJS 的 Controller、Provider（加上 DI 容器）和 exception filter 在做的事。這課先徒手做一次，之後在NestJS 課第 18 課和第 26 課用框架把同樣的分層再做一次，你會知道框架替你省了哪幾行，也知道哪些判斷它省不了。面試被問「為什麼要用 DI」，答「測試時可以換掉資料庫和 logger」比背定義有說服力。

處理函式只管丟錯，那就要有人接住它丟出來的錯；requestId 要先產生，才能綁進 logger。這些「每個請求都要做」的事，放在 app.ts 的請求管線裡。

王小明按下送出之後，請求經過哪些關卡？

王小明的 POST /orders 進到伺服器，在 orders.ts 開始扣庫存之前和之後，都要先經過 app.ts 的請求管線（pipeline）。管線是每個請求都會依序經過的固定步驟：產生 requestId、比對路由、交給處理函式、把結果或錯誤變成回應、最後記一行 access log。處理函式只管業務，這些共通的事由管線統一做，所以菜單和訂單不會各寫一套：

照圖從左到右走一遍：

  1. requestId：請求一進來就產生一個每次都不同的 id，放進回應標頭 x-request-id，再用 logger.child({ requestId }) 做出一個綁好 id 的 logger 放進 Ctx（第 19 課）。之後這個請求寫的每一行 log 都帶著同一個 id，查問題時用它把散落的 log 串回同一個請求。
  2. 比對路由：在路由表裡找符合的路由。網址不存在回 404，網址存在但方法不對（例如對 /menu 送 DELETE）回 405。
  3. 處理函式：orders.ts 驗證、扣庫存、建立訂單，成功就回 201。
  4. 錯誤邊界：處理函式丟出的錯都在這裡接住（第 18 課）。HttpError 是預期中的錯，照它的種類轉成 problem 回給客人；其他的錯一律是 500。
  5. access log：不管成功還是失敗，回應結束時記一行，寫下 requestId、方法、路徑、狀態碼、花了幾毫秒。它掛在 res 的 close 事件上，而不是寫在處理函式的最後一行：處理函式丟錯時根本跑不到最後一行，王小明在回應送出前就關掉 App 時也一樣。close 在這三種情況都會觸發，所以剛好記一行。

第 4 步的「其他的錯」值得多講。未預期的錯誤（程式 bug、資料庫掛了）的訊息常常含有內部資訊：表名、約束名，甚至個資。例如 pg 的 unique 違反會在 detail 寫出 Key (phone)=(0912-345-678) already exists.。如果錯誤邊界把這段原樣回給客人，等於把別人的電話送給任何一個會觸發錯誤的人。所以 500 只回固定的說明和一個新產生的 errorId；原始錯誤（含 stack）連同同一個 errorId 和 requestId 寫進 log。這樣分開之後，兩邊都拿到自己需要的：王小明的畫面上只有「系統錯誤，代碼 xxx」，他截圖給客服，客服用 errorId 在 log 裡一搜，就找到完整的錯誤和那個請求前後的每一行 log。

錯誤不回給客人了，但它進了 log，問題就搬到 log 那邊：log 本身也會外洩個資。log 通常會被送進集中的查詢系統，看得到的人比看得到資料庫的人多。第 19 課的 logger 依欄位名稱遮蔽 authorization、password，但上面那支電話藏在 detail 和錯誤訊息裡，欄位名稱不叫 phone，依名稱遮蔽抓不到它。這種「形狀固定」的個資（手機、信用卡號），要在輸出前對整行字串用正規表示式找出來遮掉，不管它在哪個欄位：

const PHONE = /\b09\d{2}[- ]?\d{3}[- ]?\d{3}\b/g
const maskPhones = (line: string) => line.replace(PHONE, p => p.slice(0, 4) + '*'.repeat(p.length - 7) + p.slice(-3))
// 0912-345-678 → 0912*****678

保留前 4 碼和後 3 碼，客服核對「是不是 0912 開頭、678 結尾那支」還用得上，完整號碼卻不會出現在 log 裡。同樣的理由，access log 只記 pathname，不記查詢字串：查詢字串裡常有 email、電話、token，一記下來就跟著 log 送到每一個看得到 log 的地方。

💡 實務上：客服轉來的 errorId，是你查事故的起點
王小明的截圖到了客服手上，客服把 errorId 轉給你。你在 log 系統搜這個 id，找到那一行 error 和它的 requestId，再用 requestId 搜出這個請求的每一行 log：它查了哪些資料、在哪一步出錯、花了多久。這條鏈任何一環缺了（500 沒給 errorId、log 沒帶 requestId、access log 漏記失敗的請求），事故就只能靠猜。審 PR 時看到新增的 log，資深工程師會問一句：「這行會不會印出個資或 token？」

管線替每個請求處理好了共通的事。但王小明那個早上最麻煩的問題不在單一請求裡，而在好幾個請求同時發生的時候：他按了兩次送出、兩個店員同時按下不同的按鈕、他的訂單頁一直連著等通知、補貨查詢要問一個可能掛掉的供應商。接下來四節，一節處理一個。

王小明按了兩次送出，怎麼只建立一張訂單？

回到開場：王小明第一次送出時，請求其實已經到了伺服器，訂單也開始建立，只是回應在隧道裡丟了。App 帶著同一個 Idempotency-Key 重送，這時伺服器要分辨四種情況：這個 key 沒見過（照常建立）；見過而且已經做完（回第一次的結果，不再建立）；見過但第一個請求還在處理中（兩個請求同時在跑）；見過但這次送來的內容不同，例如同一個 key 的訂單變成三杯拿鐵，那不是重送，而是 App 重用了舊的 key，屬於客戶端的 bug，回 422，不能默默回第一次的兩杯。第三種最麻煩，因為負載平衡器可能把重送的請求交給另一個程序，兩個程序要對「誰先到」有同一個答案。所以 key 存在資料庫，用 idempotency_keys 的唯一約束決定誰先到。

第 24 課的做法，是把「佔住 key、建立訂單、存回應」全部放在同一個交易：第一個請求在交易裡 INSERT 了 key，還沒提交；重送的請求執行 INSERT … ON CONFLICT 時撞到這筆還沒提交的 key，會停下來等前一個交易結束，再看結果。這樣正確，但等待的那段時間，重送的請求一直佔著一條資料庫連線和一個請求。如果建立訂單很慢，或者王小明的 App 每隔幾秒就重送一次，等著的請求會越積越多，把連線池用光。第 24 課也提到另一種做法，這個專題用它，分成兩段：

  1. 用一句自己提交的 INSERT … ON CONFLICT (key) DO NOTHING 佔住 key。rowCount 是 1 代表我先到；別的程序立刻看得到「處理中」（response_status 是 NULL）。
  2. 在交易裡建立訂單，並在同一個交易把回應寫回 idempotency_keys：要嘛訂單和回應都存在，要嘛都沒有。
  3. 失敗（庫存不足、資料庫錯誤）就刪掉 key，客戶端可以用同一個 key 重試。

每一步都有它的理由。第 1 步一定要自己提交，不能包在後面的交易裡：還沒提交的資料別的連線看不到，重送的請求就又會停下來等，回到第 24 課的做法。自己提交之後，重送的請求一 INSERT 就撞到這筆已經存在的 key，rowCount 是 0，再讀出它的 response_status：NULL 代表第一個請求還在處理中，立刻回 409 request-in-progress，不佔著連線等；有值就回第一次存下的結果。第 2 步把訂單和回應放在同一個交易，是為了不出現「訂單建好了、回應沒存到」的狀態：那樣重送的請求會一直看到「處理中」，王小明永遠拿不到結果。第 3 步刪掉 key，是因為失敗的請求沒有建立任何東西，等庫存補上再用同一個 key 送，應該被當成新的嘗試。因為 key 已經刪掉，這次送來時伺服器沒見過它，就不會被當成「內容不同」而回 422。

代價是多了一個中間狀態。程序在第 1 步和第 3 步之間當掉，key 會一直停在「處理中」，這個 key 的重送永遠拿到 409。正式環境怎麼清理這種 key，見課末「補充與查表」。

訂單建好了，王小明的那張單進了店裡。接下來輪到店員改它的狀態，而這裡有另一種並發。

兩個店員同時按，訂單狀態聽誰的？

訂單狀態有固定的走法：pending（等待中）可以變成 brewing（製作中）或 cancelled（已取消）；brewing 只能變成 ready（可取餐）；ready 只能變成 picked_up（已取餐）；picked_up 和 cancelled 是終點，不能再變。哪些轉換合法，寫在 order-status.ts 的 TRANSITIONS 裡，這就是狀態機：一組狀態，加上「從哪個狀態可以到哪個狀態」的規則（第 14 課）。不合法的轉換回 409 invalid-transition。

直覺的寫法是三步：先 SELECT status，在 JS 裡查 TRANSITIONS 判斷可不可以轉換，可以再 UPDATE。單獨一個店員操作時沒問題。但王小明那張單，兩個店員幾乎同時按下了「開始製作」和「取消」：兩個請求都先 SELECT，都讀到 pending；都在 JS 裡判斷「pending 可以變成我要的狀態」；都去 UPDATE，都成功。最後訂單的狀態取決於誰的 UPDATE 晚一點到，店員 A 以為在做、店員 B 以為取消了，王小明的畫面可能顯示「已取消」，咖啡卻照樣做了出來。這種「先查、再判斷、再動手」的寫法叫 check-then-act，它的問題是查和動手之間有空檔，別人的修改可以插進來（PostgreSQL 課第 19 課）。

修法是不留空檔：把判斷寫進 UPDATE 的 WHERE，讓「檢查」和「修改」在資料庫裡變成同一個動作：

UPDATE orders SET status = $2
WHERE id = $1 AND status = ANY($3)   -- $3：可以轉換成 $2 的狀態，例如改成 brewing 時是 ['pending']
RETURNING id

$3 的方向和 TRANSITIONS 剛好相反：TRANSITIONS 寫的是「從某個狀態可以去哪些狀態」，$3 要的是「哪些狀態可以轉到 $2」。所以要把 TRANSITIONS 反過來查，找出所有能轉到目標狀態的來源狀態。例如目標是 cancelled 時，只有 pending 的清單裡有 cancelled，$3 就是 ['pending']；目標是 picked_up 時，$3 是 ['ready']。

兩個 UPDATE 同時打到同一列時，第二個 UPDATE 會等第一個交易提交，再對更新後的那一列重新檢查 WHERE（PostgreSQL 18 文件，Read Committed）。店員 A 的「開始製作」先提交，訂單變成 brewing；店員 B 的「取消」接著重新檢查，status = ANY(['pending']) 已經不成立，一列都不改，rowCount 是 0。

rowCount 是 0 有兩種可能：訂單根本不存在，或訂單存在但目前狀態不允許這個轉換。這時再查一次目前狀態，分辨是 404 還是 409；409 的 detail 寫出目前狀態，店員 B 的平板重新讀取，就會看到「這張單已經在製作中」。扣庫存的 UPDATE … WHERE stock >= $1 是同一個道理（第 20 課）：條件寫在 UPDATE 裡，12 個人同時搶 5 個庫存，也只有 5 個 UPDATE 改得到列。

店員 A 的「開始製作」成功了，資料庫裡的狀態變成 brewing。但王小明還盯著手機上的訂單頁，他怎麼知道？

狀態變了，王小明的畫面怎麼即時更新？

訂單頁用第 16 課的 SSE（Server-Sent Events）：App 對 GET /orders/:id/events 開一條不會結束的 HTTP 回應，伺服器有新消息就往裡面寫一則事件。消息從哪來？PATCH 成功之後，order-status.ts 會 orderEvents.emit('status', { orderId, status })；每一條 SSE 連線都在 orderEvents 上掛了一個監聽器，比對 orderId 是自己那張單，就把新狀態寫給客人。

難的地方在收尾。一般的請求回完就結束，SSE 連線卻不會自己結束，所以有兩個時間點要主動收：

  • 客戶端離開時：王小明關掉 App，連線斷了，但掛在 orderEvents 上的監聽器還在。要在 res.on('close') 把它拿掉（第 16 課），不然每條斷線都留下一個監聽器，它抓著已經關掉的 res 不放，記憶體慢慢漲，這就是第 23 課的洩漏。
  • 關機時：開場那次部署，平台送來 SIGTERM，server.close() 會等所有連線結束才完成。SSE 連線不會自己結束，server.close() 就永遠等不到它們，一直拖到關機時限被強制砍掉（第 21 課）。所以 startShutdown() 會發出 'shutdown'，每條串流收到後自己 res.end()。

還有一種正常的結束：訂單變成 picked_up 或 cancelled 之後不會再變，送完這一則就結束串流，不讓連線白白掛著。

這個設計有一個限制，要寫進文件：orderEvents 是程序記憶體裡的 EventEmitter，只有同一個程序的監聽器聽得到。部署成兩個程序時，店員的 PATCH 進了 A，王小明的 SSE 連在 B，B 收不到事件，王小明的畫面就停在「等待中」。第 24 課的 LISTEN／NOTIFY 可以解決，這個專題先不做，但要知道它在哪裡會壞。

💡 實務上：把「先不做」的限制寫下來
專案總有做不完的事。差別在於限制有沒有被寫下來：README 或設計文件寫著「SSE 只在單一程序有效，擴展前要改成 LISTEN／NOTIFY」，半年後要開第二台機器的人就知道要先改什麼；沒寫，就是上線後客人回報「畫面不會動」，大家才從頭查起。資深工程師評估擴展計畫時，第一個問的就是「記憶體裡有沒有該共享的狀態？」，冪等鍵、快取、事件都在這張清單上。

到這裡，訂單從建立到取餐的流程都在我們自己的服務和資料庫裡。最後一個需求不一樣：補貨時間要問供應商，那是一個我們控制不了的服務。

供應商掛了，補貨查詢怎麼不拖垮整個服務？

王小明想加點的起司蛋糕賣完了，App 會呼叫 GET /menu/:id/restock 顯示「預計幾點補貨」。這個資訊是「有最好、沒有也行」：查不到，王小明頂多少看到一行字。但如果供應商的 API 卡住不回，而我們的請求就一直等，每一個查補貨的請求都會掛著不放；請求越積越多，佔掉的記憶體和連線最後會拖慢整個服務，連下單也受影響。一個「沒有也行」的功能，拖垮了「一定要有」的功能。

所以給上游一個預算：我們最多願意為它花多少時間、試幾次，超過就放棄，回 503 告訴客戶端稍後再試（第 17 課）。這個專題的預算是：

  • 每一次呼叫 1 秒逾時。逾時的那一次不重試：上游已經慢到一秒回不來，馬上再打一次多半也一樣。
  • 只對 503 重試，最多 2 次。503 代表上游暫時忙不過來，等一下可能就好。404、500 不重試：再試一次也是同樣的結果，只是讓供應商更忙。
  • 尊重 Retry-After，但有上限：上游用這個標頭說要等多久就等多久，但超過 2 秒就直接放棄；沒給就等 100、200ms。

回應的內容也要過濾。上游的錯誤內容只進 log，回給客戶端的 detail 自己寫，因為上游可能把它的內部資訊放在錯誤訊息裡，原樣轉出去，等於替它洩漏。

最後一件事：王小明等不及，關掉了 App，但我們對供應商的請求還在跑，甚至還在等重試。沒有人在等的回應，不值得佔著一條連線。所以客戶端離開時，要取消還在進行的上游請求：把 res 的 close 接到一個 AbortController，再用 AbortSignal.any 把它和每一次呼叫的 1 秒逾時合併成一個 signal 傳給 fetch。這樣不管是逾時先到，還是客人先離開，上游請求都會被取消。

四個決策都定了。設計到這裡完整，接下來是動手：從哪裡開始寫，怎麼知道每一步寫對了。

從哪裡開始動手？

在 learn/ 執行 node check.mjs node 26 建立 work/26/。測試需要 PostgreSQL：先打開 Docker Desktop，在 learn/node/practice 執行 docker compose up -d --wait。每個測試檔會建立自己的隨機資料庫，跑完就刪，不會動到你手動測試用的 coffee 資料庫。這正是前面「程式怎麼分」那一節依賴注入的用處：測試把指向臨時資料庫的 pool 傳進 createApp，每個測試從乾淨的資料開始，彼此不互相影響。

起始專案已經能跑：路由表、平台工具、GET /orders/:id 都寫好了，要你寫的地方標著 TODO。六個里程碑對應下面的練習 1 到 6，照順序做，因為後面的測試依賴前面的成果：練習 3 的測試會啟動兩個 main.ts，所以練習 1 的啟動與關機要先能動；練習 6 會讀它的 log。

每完成一個里程碑就跑一次 node check.mjs node 26，前面通過的不能變回失敗。這就是回歸測試（regression test）的用途：「回歸」指的是原本好的東西退回壞掉的狀態。做練習 4 改到 app.ts 時，練習 1 的關機測試還在跑，如果你不小心讓 SSE 擋住了關機，馬上就會看到，而不是等到部署時才發現。

想自己把服務跑起來、用 curl 試試，照 examples/README.txt：examples/setup.ts 重建資料，examples/fake-supplier.ts 是假的供應商。啟動後終端機會印出結構化的 log，每個請求一行 access log：

$ SUPPLIER_URL=http://localhost:4000 node --env-file=../../.env main.ts
{"time":"…","level":"info","msg":"listening","port":3000}
{"time":"…","level":"info","msg":"request","requestId":"3f0c…","method":"GET","path":"/menu","status":200,"durationMs":4}

六個里程碑做完、測試全過，驗收條件的每一句都有測試證明了。但這還不是「可以上線」。

測試全過，就可以上線了嗎？

測試證明的是「我們想到的情況都對」。上線之後出事的，常常是沒想到的那些：某個外部呼叫忘了設逾時、pool 大小乘上程序數超過資料庫的上限、CI 沒有跑型別檢查。這些不屬於任何一條驗收條件，所以需要另一份東西：上線檢查清單（production readiness checklist）。它是上線前逐項確認的清單，來源是過去的事故：把「上次出事的原因」變成「下次上線前一定會問的問題」。下面是這門課整理出來的版本，每一項都是一課：

檢查問自己課
設定缺設定時一次列出全部、以 1 結束？錯誤訊息沒印出密碼？2
型別檢查CI 有跑 tsc？（Node 只去掉型別，不檢查）5
event loop有沒有同步的大迴圈、大 JSON、危險的正規表示式？9、25
輸入的上限body 上限、標頭與請求逾時、分頁的 limit 上限？13、25
錯誤格式一致（problem）？500 不洩漏細節、有 errorId？14、18
快取該快取的有 ETag、Cache-Control？不該快取的（訂單）沒有？15

用王小明的那個早上對一遍：重按不重複建單是「多程序」那一列，部署不掉單是「健康檢查與關機」，客服查得到原因是「錯誤」和「log」，供應商掛了不被拖垮是「外部呼叫」。這門課每一課教的東西，最後都收斂成這張表上的一個問題。

清單不用每次全部重來。改了哪個部分，就重看相關的幾項；有新的事故，就加一項。

💡 實務上：清單要放在每次都會經過的地方
團隊裡這份清單通常放進 PR 範本或上線流程的步驟，而不是存在某份沒人打開的文件裡。出事後的事故檢討（postmortem），除了在清單加一項，更好的結論是把它變成 CI 會自動擋的檢查，像表裡的「CI 有跑 tsc」，能自動化的就不要靠人記。資深工程師審 PR 時，常問的就是這幾句：「上游卡住會怎樣？」「部署那一刻進行中的請求呢？」「這行 log 會不會印出個資？」

補充與查表

下面是主線用不到、但上線之後會需要的細節。

卡在「處理中」的冪等鍵：程序在佔住 key 之後、存回應或刪 key 之前當掉，key 會一直停在處理中。正式環境用 created_at 判斷，處理中超過幾分鐘的可以重做，並定期刪掉一天以上的 key（第 24 課）。

驗證時用的 Node 版本：本專題以 Node 24.22.1 驗證。部署到 Node 26 這類新的主版本時，重新跑一次全部測試。

練習

六個里程碑，照順序完成。每一題列出要改的檔案，檔案開頭的註解寫著詳細規格。

練習 1（里程碑 1：啟動與平台）：platform/config.ts 的 loadConfig 現在遇到第一個錯就停，改成檢查完五個設定、一次列出所有錯誤（格式與預設值見檔案開頭；錯誤訊息不能印出 DATABASE_URL 的值），main.ts 已經會印出錯誤並以 1 結束。app.ts：GET /readyz 要真的查一次資料庫（SELECT 1，最多等 500ms），可用才 200，否則 503 並附 reason；呼叫 startShutdown() 之後一律 503。main.ts：收到 SIGTERM 或 SIGINT 時優雅關機（呼叫 app.startShutdown()、不接新連線、等進行中的請求、不被 keep-alive 連線拖住、關掉 pool、以 0 結束）；SHUTDOWN_TIMEOUT_MS 到了強制關閉並以 1 結束。

練習 2（里程碑 2：菜單）：GET /menu?limit=&cursor= 回 { items: [{ id, name, price }], nextCursor }，依 id 排序，limit 預設 20、範圍 1–50。用 cursor 分頁：翻頁途中有商品被刪掉，也不能重複或漏掉（測試會這樣做）；最後一頁 nextCursor 是 null；limit 或 cursor 不對回 400 validation。回應帶依內容計算的 ETag 和 Cache-Control: public, max-age=60，If-None-Match 相同時回 304、沒有 body。GET /menu/:id 同樣支援 ETag，商品不存在回 404 problem。

練習 3（里程碑 3：下單）：完成 orders.ts 的 validateNewOrder 和 createOrder。驗證失敗回 400，errors 一次列出所有欄位（customerId、items、items[i].productId、items[i].quantity；quantity 要是 1–20 的整數，字串 "2" 不算，同一個商品不能出現兩次）；顧客不存在也是 400。在交易裡扣庫存，不足回 409 out-of-stock，兩個程序同時搶也不能超賣；金額用資料庫的價格計算（用 insertOrderRows 寫入）；成功回 201 和 Location: /orders/:id。帶 Idempotency-Key 時，key 存在 idempotency_keys 表：先用一句自己提交的 INSERT … ON CONFLICT DO NOTHING 佔住 key；同一個 key 同內容回第一次的結果，內容不同回 422，第一個請求還在處理中回 409 request-in-progress（不能讓重送的請求卡著等）；失敗時刪掉 key。測試會同時啟動兩個 main.ts，把同一個 key 送到不同程序。

練習 4（里程碑 4：訂單狀態與即時通知）：PATCH /orders/:id 依 TRANSITIONS 轉換，成功回 { id, status } 並 orderEvents.emit('status', { orderId, status })；不認得的狀態 400、訂單不存在 404、不能這樣轉換 409 invalid-transition；兩個請求同時改同一張訂單時只能有一個成功。GET /orders/:id/events 用 SSE：一連上先送目前狀態，之後這張訂單每次變化送一則 event: status（orderEvents 上是所有訂單的事件，要比對 orderId），data 是 {"orderId":…,"status":…}；變成 picked_up 或 cancelled 送完就結束串流；收到 'shutdown' 也結束；客戶端離開時把監聽器拿掉。

練習 5（里程碑 5：補貨查詢）：GET /menu/:id/restock 呼叫 {SUPPLIER_URL}/restock/{id}，成功回 { productId, restockAt }；我們沒有的商品回 404，不呼叫上游。每次呼叫 1 秒逾時（逾時不重試）；只有 503 重試，最多 2 次，有 Retry-After 照著等、超過 2 秒就不等了，沒有就等 100、200ms；其他失敗都回 503 upstream-unavailable，不能帶上游的回應內容。客戶端離開時取消還在進行的上游請求。

練習 6（里程碑 6：log 與錯誤）：app.ts 的請求管線：每個回應（包括 404、500）帶 x-request-id，每個請求不同；處理函式拿到的 logger 是 logger.child({ requestId })；回應結束時記一行 access log：msg 是 "request"，欄位 requestId、method、path、status、durationMs。未預期的錯誤回 500 problem，只帶固定的說明和 errorId；同時用 log.error 記下同一個 errorId 和錯誤本身（logger 會序列化出 stack）。platform/logger.ts：輸出前遮掉完整的手機號碼（09 開頭 10 碼，中間可能有 - 或空白），不管它出現在哪個欄位。測試會用 ENABLE_TEST_ROUTES=1 開啟 /__test/boom，它丟出的錯誤和 pg 一樣，把電話放在 detail。

練習 7：這個 API 要部署成 3 個程序，前面放負載平衡器。哪一個功能不改設計就會出錯？

✓ orderEvents 是程序記憶體裡的 EventEmitter，只有同一個程序的監聽器聽得到，要用 LISTEN／NOTIFY 這類跨程序的管道（第 24 課）。a 錯：冪等鍵存在 PostgreSQL，所有程序共用（練習 3 的測試就是兩個程序）。b 錯：UPDATE … WHERE stock >= $1 由資料庫保證，程序幾個都一樣。d 錯：ETag 依回應內容計算，內容相同 ETag 就相同；如果改用「啟動時間」或亂數當 ETag，才會有這個問題。

練習 8：功能都做完、測試全過，明天要上線，只剩半天。你會優先確認哪一組？

✓ b 是「出事時影響多大」的三項：沒有逾時，一個上游卡住就拖垮整個服務；500 洩漏細節是資安事故；關機沒做好，每次部署都會掉單，而上線後一天可能部署好幾次。a 是好用的改善，但不做也不會出事。c 的數字本身不保證什麼，關鍵是錯誤路徑和並發有沒有測到；功能做完不等於可以上線，上線檢查清單就是為了這個時候。

練習 9：之後在 NestJS 課把這個 API 重做一次。哪一個說法正確？

✓ 框架省掉的是「每個專案都長一樣」的部分：路由表、驗證 decorator、DI 容器、exception filter。b 錯：超賣和冪等是業務規則加上並發，框架不知道你的庫存怎麼扣、key 存在哪。c 錯：NestJS 要自己呼叫 enableShutdownHooks() 才會在收到訊號時執行關機的 hook，排空的順序、時限、SSE 的收尾還是你決定（NestJS 課會實作）。

常見錯誤

  • 沒列路由表與錯誤格式就開始寫程式：寫到一半才發現每條路由的錯誤長得不一樣，前端要寫三種解析。先定合約，再實作。
  • 所有東西寫在同一個檔案：改菜單要捲過下單的程式，測試也沒辦法只換掉資料庫。依功能分檔，依賴從 createApp 的參數傳入。
  • 在處理函式裡 new Pool()：每個請求一個池子，連線數爆掉，而且沒人關。pool 在 main.ts 建立一次，關機時 end()。
  • 測試只測 happy path：超賣、重送、上游卡住、客戶端中途離開，都是正式環境一定會遇到的。驗收條件裡的每一句都要有測試。
  • 先 SELECT 再判斷再 UPDATE：並發時兩個請求都通過檢查。把條件寫進 UPDATE … WHERE，看 rowCount。
  • 冪等鍵存在記憶體：兩個程序各有一份，重送到另一台就重複建立。存在資料庫，用唯一約束決定誰先到。
  • 關機時忘了 SSE 與 pool：SSE 不會自己結束，server.close() 一直等；pool 沒關，程序不會自然結束。
  • 500 回原始錯誤訊息，或 log 沒有遮蔽：資料庫的錯誤訊息裡有表名和個資。回應只給 errorId；log 依欄位名稱遮蔽之外，形狀固定的個資要對整行遮蔽。
  • 對所有錯誤重試：404、500 再試一次也一樣，只會放大上游的負擔。只重試暫時性的錯誤，有次數和時間的上限。

小結

  • 從需求開始：把老闆的話改寫成可以測試的驗收條件，切成可以獨立驗收的里程碑。
  • 動手前先定合約：路由表（成功與每一種錯誤）、problem 格式、環境變數表、資料表。
  • 依功能分檔，createApp({ config, pool, logger }) 依賴注入，測試才能換掉資料庫、logger 和供應商；資源的建立與關閉集中在 main.ts。
  • 請求管線統一處理 requestId、路由、錯誤邊界與 access log；500 只給 errorId，log 遮蔽 token 與個資。
  • 並發的正確性交給資料庫：條件式 UPDATE 防超賣與非法轉換，唯一約束加兩段式的冪等鍵讓多程序共用，重送的請求遇到「處理中」立刻回 409。
  • SSE、上游呼叫都要能被取消與結束；上游呼叫要有逾時、有限的重試、尊重 Retry-After。
  • 測試全過不等於可以上線：上線前用檢查清單逐項確認，改了哪裡就重看相關的幾項。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 10：GET /orders/export 太慢，你錄了 CPU profile。Bottom-Up 表格裡：handleExport total time 98%、self time 1%；buildRows self time 70%；(garbage collector) 8%。先改哪裡？

✓ 熱點看 self time。total time 包含它呼叫的所有函式，handleExport 只是呼叫了 buildRows，自己幾乎沒做事。改 buildRows，改完用同樣的方法再量一次。a 錯在把 total time 當熱點，路由處理函式的 total time 一定高。（第 23 課）

練習 11：訂單服務的容器每 6 小時被 OOM 砍掉一次，監控上 heapUsed 每次 GC 後的低點一路往上爬。同事提議把 --max-old-space-size 調到 4GB。比較好的下一步是？

✓ GC 後的低點持續上升就是洩漏，要找出保留者修掉。兩張 snapshot 用 Comparison 依建構子看哪種物件變多，Retainers 往回找到你程式碼裡的 Map、監聽器或閉包。b 錯在上限調大只是晚一點 OOM：物件還被抓著，GC 空間再多也回收不了。（第 23 課）

練習 12：登入 API 用模組層級的 Map 記每個 IP 一分鐘內試了幾次，上限 5 次。服務改成 4 個 cluster worker 後，攻擊者每次都開新連線，一分鐘實際能試幾次？

✓ worker 是獨立的程序，記憶體各自一份；primary 用 round-robin 輪流分配連線，實際上限變成 5 × 程序數。計數要移到 Redis 或資料庫，所有程序才共用。a 錯在 cluster 分配連線不看來源 IP；就算用黏性連線綁住，程序一重啟計數也歸零。（第 24 課）

練習 13：改成 4 個 worker 後，訂單狀態用 LISTEN／NOTIFY 推給每個程序的 SSE。改狀態的程式這樣寫，客人的畫面偶爾顯示「製作中」，訂單其實已經被取消了。哪裡出事？

await pool.query("SELECT pg_notify('order_status', $1)", [JSON.stringify({ orderId: id, status: next })])
const r = await pool.query('UPDATE orders SET status = $2 WHERE id = $1 AND status = ANY($3)', [id, next, from])
if (r.rowCount === 0) throw new HttpError(409, 'invalid-transition')

✓ NOTIFY 在交易 COMMIT 後才送出，這裡 pg_notify 單獨一句就提交了：UPDATE 被取消搶先、rowCount 是 0 時，通知早就發出去。把 UPDATE 和 pg_notify 放進同一個交易，更新成功才通知，失敗就 ROLLBACK、不會送出。c 錯在不同交易的通知依 COMMIT 的順序送達。（第 24 課）

練習 14：每個容器一個程序，pg 的 Pool 設 max: 20，原本開 3 個容器。週末活動加到 8 個容器，流量一上來，新的資料庫連線一直被拒絕。PostgreSQL 的 max_connections 是預設的 100。先查什麼？

✓ 每個程序各有一個 pool，總連線數是 pool 大小 × 程序數 × 機器數：原本 60 條，加到 8 個容器最多 160 條，超過 100 就被拒絕。擴展前先算這筆帳。c 錯在慢查詢只會讓請求排隊，連線上限是固定的，160 條本來就開不出來。（第 24 課）

練習 15：圖片伺服器這樣檢查路徑，name 是 /images/ 後面那一段。哪一個請求會讀到根目錄外的檔案？

const ROOT = resolve('public/images')
const file = resolve(ROOT, decodeURIComponent(name))
if (!file.startsWith(ROOT)) return notFound(res)
createReadStream(file).pipe(res)

✓ startsWith 只比字串，…/images-private/recipe.jpg 也以 …/images 開頭。比對 ROOT + sep，再用 realpath 換掉符號連結比一次，副檔名用白名單。d 錯在 resolve 這一步是對的，漏的是比對：少了分隔符號，也沒處理符號連結。（第 25 課）

練習 16：點餐備註用 /^(\w+\s?)*$/ 驗證。有人送了 30 個字元、結尾是 ! 的備註，之後幾秒所有客人的點餐都沒有回應。原因和修法是？

✓ \s? 可有可無，同一串字有指數多種切法，結尾的 ! 讓每一種都失敗；Node 只有一條執行緒跑 JavaScript，這個請求卡住，所有請求一起卡。把可有可無的分隔符號改成必要的。b 錯在指數成長下 30 個字元就可能卡一秒，限制長度只能降低風險，規則本身要改。（第 25 課）

練習 17：登入 API 在雲端負載平衡器後面，限流拿 X-Forwarded-For 最左邊的值當客戶端 IP。有人暴力猜密碼，限流一次都沒擋下來，為什麼？

✓ 客戶端也能送 X-Forwarded-For，代理只附加、不清掉，最左邊是攻擊者想讓你看到的值。直連的是信任的代理才看這個標頭，從右往左跳過信任的代理，第一個不信任的位址才是客戶端。a 錯在代理是附加在最右邊，不會取代；真的變成同一個來源，限流反而會把所有人一起擋下。（第 25 課）
