階段 5：上線前的準備 · 第 18 課

錯誤處理策略

咖啡店的 API 上線一週，客服轉來三件事。第一件：一位客人點餐時，畫面上出現 duplicate key value violates unique constraint "orders_pkey"，這是資料庫的原始錯誤訊息，連表名和約束名稱都露出來了。第二件：另一位客人的畫面顯示「點餐成功」，店裡卻沒有收到這筆訂單。第三件：凌晨三點程序整個掛掉，當時正在點餐的客人全部斷線。另外，重啟後翻 log 時發現，有一筆點餐遇到的同一個資料庫逾時被印了兩行，看不出是一次還是兩次、是哪個請求造成的，原本資料庫給的錯誤碼也不見了。

三件事的原因都不是某一行打錯字，而是整個系統沒有一致的錯誤處理策略：錯誤該在哪一層接、接了要做什麼、客戶端看到什麼、log 記下什麼。這一課把三件事當成一次事後檢討，一件一件追到根源，最後替咖啡店的 POST /orders 定下這套策略。練習裡你會親手把它做出來。

這課的路線：
  1. 先分類：三件事裡的錯誤，哪些是正常運作會發生、要處理的，哪些是要修的 bug。
  2. 錯誤物件與邊界：錯誤要帶 code 和 cause 往上傳，在 HTTP 邊界一個地方轉成回應，用 errorId 對上 log。這兩節處理第一件事。
  3. 只記一次、不要吞掉：log 為什麼印了兩行，「點餐成功」為什麼是假的。
  4. async 錯誤的陷阱：哪些錯誤根本到不了邊界，為什麼它們會讓整個程序結束。
  5. 程序層級的最後一道防線：沒人接的錯誤最後去哪，uncaughtException 之後為什麼不能繼續跑。這兩節處理第三件事的當機。
這課會用到：
  • TypeScript 課第 4 課的錯誤基礎：throw 丟出、try／catch 接住；自訂錯誤類別 extends Error，包裝時用 { cause } 留住原始錯誤。
  • TypeScript 課第 9 課的 async 錯誤：async 函式丟錯會變成被 reject 的 Promise，沒有人 await 或 catch 就成了 unhandled rejection。
  • 第 14 課的 problem details：錯誤回應統一用 application/problem+json，帶 type、title、status、detail。

先分類：哪些錯誤要處理，哪些是要修的 bug？

面對三件事，最直覺的兩種反應都不對。一種是「所有東西都 try/catch 起來回 500」：客人送錯欄位也拿到 500，他不知道自己該改什麼，值班的人也分不出哪些 500 是真的壞了。另一種是「什麼都不接，讓程序倒掉」：一位客人填錯數量，所有人一起斷線。要決定一個錯誤該怎麼對待，得先知道它是哪一種。錯誤分成兩種，處理方式完全不同。

第一種是可預期的錯誤（operational error）：程式寫得完全正確，正常運作時也一定會碰到的失敗。客人點了不存在的商品、欄位填錯、同一筆訂單送了兩次、資料庫因為負載高而查詢逾時、外部金流 API 回 503，都屬於這種。它們是需求的一部分，你在寫功能時就該想到，所以要處理：回對的狀態碼讓客戶端知道怎麼辦、重試、或改用備案。

第二種是程式錯誤（programmer error），也就是 bug：讀 undefined 的屬性、把字串當數字加、呼叫函式時參數給錯。它們本來不該發生，發生了就代表程式對資料的假設是錯的。這時「處理」它沒有意義：你不知道程式現在的狀態對不對，接住之後硬往下跑，只會產生更多錯的結果。對 bug 要做的是修：記下完整資訊，回頭改程式碼。

判斷方法只有一句：這個錯誤在程式完全正確的情況下會不會發生？會，就是可預期的；不會，就是 bug。注意同一個例外可能兩種都是，要看它從哪裡來：JSON.parse 讀客戶端送來的 body 失敗是可預期的（客人送了壞資料，回 400）；讀自己剛寫進去的設定檔失敗則是 bug（正確的程式不會寫出壞掉的設定檔）。用這個問題把咖啡店常見的錯誤分一次：

錯誤種類怎麼做
找不到 42 號訂單可預期404，告訴客戶端
qty 是 0可預期400，列出哪個欄位錯
同一個訂單編號已存在（資料庫 23505）可預期409
資料庫查詢逾時（57014）、上游 503可預期503、可能重試（第 17 課），記 log 觀察頻率
TypeError: Cannot read properties of undefined (reading 'price')bug500＋errorId，記完整 log，修程式
處理函式之外的例外（計時器、事件 callback 裡 throw）bug記 log，讓程序結束、重新啟動

回到第一件事：客人看到的 duplicate key 是表格第三列，資料庫錯誤碼 23505，代表同一個訂單編號已經存在，例如客人連按兩次送出。這是可預期的錯誤，正確的反應是回 409，告訴客戶端「這筆訂單已經存在」。實際上沒有任何一層分辨或轉換它，資料庫的原始訊息就這樣一路傳到回應裡。也就是說，程式從頭到尾沒有分辨過它是哪一種。

💡 實務上：分類決定誰要半夜被叫起來
團隊的告警通常這樣設：5xx 和 bug 會通知值班的人，404、409 這類只進統計圖表。所以把「找不到訂單」錯分成 bug，值班的人每晚被假警報吵醒；反過來把 bug 當成可預期的錯誤吞掉，問題就安靜地累積到客服爆量。Code review 看到新的 catch，資深工程師會先問兩句：「程式完全正確時這會發生嗎？」「客戶端或使用者能做什麼來修正？」答案決定它回 4xx、5xx，還是該直接修掉。也要小心對 bug 自動重試：重試十次也是同一個 TypeError，只是多打了十次資料庫。

分類的判斷有了，但還有一個問題：23505 是在最底層的 repository（負責查資料庫的那一層）發生的，決定回 409 的卻是最上層的 HTTP 處理函式。分類的結果要怎麼一路帶上去？這要靠錯誤物件本身。

要讓分類一路帶上去，錯誤物件該帶什麼？

一個請求在伺服器裡會經過好幾層：handler（處理 HTTP，讀請求、寫回應）→ service（業務規則，例如「庫存不足不能下單」）→ repository（查資料庫）。錯誤從最底層丟出，一路往上傳到 handler。上層的人看不到底層發生了什麼，手上只有那個錯誤物件，所以錯誤物件要自己說清楚「我是哪一種錯、為什麼發生」。TypeScript 課第 4 課寫過自訂錯誤類別，放到伺服器裡，每個錯誤物件要帶三樣東西。

第一樣：類別與 name。用子類別區分種類，例如 NotFoundError、ConflictError，上層看類別就知道該回 404 還是 409。name 屬性要設成類別名稱，因為 log 和 stack 的第一行印的是 name；沒設的話，每個子類別印出來都只是 Error，看 log 的人分不出種類。不用每個子類別各寫一次：在父類別的建構子寫 this.name = new.target.name。new.target 指的是實際被 new 的那個類別，new ConflictError() 時它就是 ConflictError，即使這行程式寫在父類別裡。

第二樣：錯誤碼（code）。一個穩定的字串常數，例如 'NOT_FOUND'，給程式判斷用。為什麼不直接看錯誤訊息？因為訊息是寫給人看的，會被改寫、會被翻譯；今天比對 '找不到訂單' 能動，明天有人把文案改成「查無此訂單」就壞了，而且沒有任何測試會提醒你。code 是約定好不變的。Node 自己的錯誤也這樣做：ENOENT（檔案不存在）、ECONNREFUSED（連線被拒）、ERR_MODULE_NOT_FOUND。pg 套件丟出的資料庫錯誤帶 SQLSTATE，也就是 PostgreSQL 的五碼錯誤碼，第一件事的 '23505' 就是其中一個。

第三樣：cause。repository 接到 23505 時，會把它換成自己的 ConflictError 再往上丟，這叫包裝：上層不需要懂 PostgreSQL 的錯誤碼，只要懂領域錯誤。但包裝不能把原始錯誤丟掉。寫成 new XxxError(訊息, { cause: 原始錯誤 })，原始錯誤會掛在新錯誤的 cause 屬性上；如果原始錯誤自己也有 cause，就一層接一層，形成 cause 鏈。少了它，log 只看得到外層的「資料庫查詢逾時」，看不到是哪一句 SQL、哪個 code。第三件事裡「原本資料庫給的錯誤碼不見了」，就是包裝時沒有放 cause。

三樣東西放進同一個父類別 AppError，每個子類別只決定自己的 code。status 是這個錯誤對應的 HTTP 狀態碼，expose 決定訊息能不能直接給客戶端看，下一節會用到：

export class AppError extends Error {
  code: ErrorCode
  status: number
  expose: boolean          // 訊息能不能給客戶端看：4xx 可以，5xx 不行
  constructor(code: ErrorCode, message: string, options: { cause?: unknown, expose?: boolean } = {}) {
    super(message, { cause: options.cause })
    this.name = new.target.name
    // …
  }
}
export class ConflictError extends AppError {
  constructor(message: string, options: ErrorOptions = {}) {
    super('CONFLICT', message, options)
  }
}

throw new ConflictError('這筆訂單已經存在', { cause: dbError })

接著實際看一條 cause 鏈長什麼樣子。範例會用到 Error.isError(value)，它判斷一個值是不是真的 Error 物件，下一節會說明為什麼需要它。在 learn/ 執行 node check.mjs node 18 建立 work/18/，再到 work/18 執行 node examples/cause.ts：

err.cause === dbError： true
JSON.stringify(err)： {"code":"UPSTREAM_UNAVAILABLE","name":"UpstreamError"}
Error.isError(err)： true ／Error.isError({ message })： false
---- util.inspect（console.log 印 Error 時用的就是它）----
UpstreamError: 資料庫查詢逾時 {
  code: 'UPSTREAM_UNAVAILABLE',
  [cause]: Error: canceling statement due to statement timeout {
    code: '57014'
  }
}

由上往下看：

  • err.cause === dbError：原始錯誤原封不動地掛在外層錯誤上，沒有被複製或轉成字串。
  • JSON.stringify 只輸出物件自己的可列舉屬性，message、stack、cause 都不是，所以全部不見了。正式環境的 log 是一行一個 JSON，要把錯誤寫進去得自己序列化，第 19 課會做。
  • Error.isError 對真的錯誤回 true，對長得像錯誤的普通物件 { message } 回 false。
  • console.log 印 Error 時用的是 util.inspect，它會把整條 cause 鏈印出來（[cause] 那段），外層的 UPSTREAM_UNAVAILABLE 和底層的 57014 都看得到。

錯誤物件現在帶齊了種類、code 和原因，能一路傳到最上層。下一個問題是：到了上層，由誰、在哪裡把它變成客人看到的回應？第一件事裡原始訊息漏給客人，就是這一步沒有人負責。

錯誤在哪裡變成回應？在邊界統一轉換

答案是只在一個地方，而且是最外層。這個地方叫錯誤邊界（error boundary）：所有往上傳的錯誤最後都會到這裡，由它統一轉成回應。HTTP 伺服器的邊界就是第 13 課包住所有路由的那一層；之後學 NestJS 時，同樣的角色叫 exception filter。其他每一層只做自己懂的事：

repository 懂資料庫，所以由它把 23505 包成 ConflictError、把 57014 包成 UpstreamError；service 懂業務規則，但通常不知道怎麼處理「資料庫逾時」，所以它不接，讓錯誤原樣往上；handler 是邊界，用一張對照表把領域錯誤轉成狀態碼和第 14 課的 problem details。業務程式只丟領域錯誤（NotFoundError），完全不知道 HTTP 的存在。這樣做有兩個好處：「哪種錯誤回哪個狀態碼」的規則只寫在一個地方，要改只改一處；service 不依賴 HTTP，同一段下單邏輯也能被排程工作、CLI 重複使用。

邊界拿到錯誤後，第一步是認出它是哪一種。有三種判斷方式，各有適合的對象：

  • err instanceof ConflictError：判斷自己寫的錯誤類別最方便，TypeScript 還會幫你把型別縮小成 ConflictError，之後讀 err.status 不用轉型。邊界判斷「這是不是我的 AppError」就用它。
  • err.code === '23505'：判斷別人的錯誤（pg、Node 的系統錯誤）只能用它，因為你拿不到他們內部的類別。repository 認 23505、57014 就用 code。
  • Error.isError(value)：判斷「這到底是不是一個 Error」。下面會看到，邊界拿到的東西不一定是 Error。

為什麼需要最後一種？catch (err) 裡的 err，TypeScript 給的型別是 unknown，因為 JavaScript 可以 throw 任何東西：字串、普通物件、甚至 null。邊界如果直接讀 err.message，遇到 throw null 時讀屬性本身就會再丟一個 TypeError，錯誤處理程式自己變成新的錯誤來源。所以處理錯誤的程式要先確認，再讀屬性。instanceof 在少數情況會判斷錯（同一個套件被裝了兩份、錯誤來自另一個執行環境），細節見課末。

認出種類之後，就要決定客戶端看到什麼。第一件事的原始訊息為什麼不能給客人看？資料庫、檔案系統的錯誤訊息常常含有表名、SQL、檔案路徑、內部主機名稱。對攻擊者，這是了解你系統內部的現成情報；對客戶端，它毫無用處，因為他看了也什麼都改不了。規則分三條：

  • 4xx 的訊息是寫給客戶端看的，例如「找不到 42 號訂單」「這筆訂單已經存在」，可以原樣回傳。AppError 的 expose 就是這個意思：4xx 預設 true。
  • 5xx 一律回通用訊息，加一個 errorId。errorId 是每次出錯時產生的隨機編號（crypto.randomUUID()），同時寫進回應和 log。客人回報「錯誤代碼 7f3c…」，你在 log 裡搜尋這串字，就找到那一次的完整 stack 和 cause 鏈。回應裡沒有細節，細節都在 log 裡，兩邊靠 errorId 對起來，這就是上圖右邊的兩個方框。
  • 不認得的東西一律當成 500：TypeError、被 throw 的字串或物件都是。被 throw 的普通物件 { status: 404 } 不是你的錯誤類別，不知道是誰丟的，不能相信它的欄位。

套回第一件事：repository 把 23505 包成 ConflictError，邊界認出它是 AppError、expose 是 true，回 409「這筆訂單已經存在」。客人看到一句他看得懂的話，資料庫的表名和約束名稱不會再出現在畫面上。練習 1 的 toProblem 就是這段轉換。

💡 實務上：errorId 要讓客人看得到、抄得下來
errorId 只有送到客服手上才有用，所以前端的錯誤畫面不要只寫「發生錯誤」，要把它用小字顯示、可以一鍵複製。客人截圖給客服、客服轉給工程師，工程師貼進 log 搜尋就到了，不用再問「你大概幾點、點了什麼」。資安檢查常做的一項是故意送壞資料，看 500 的回應有沒有漏出 SQL、路徑或套件版本；錯誤都在邊界統一轉換的話，這一項只要檢查一個地方。errorId 只是隨機編號，不要拿使用者 id 或訂單編號拼成它。

邊界設計好了，但它有一個前提：錯誤要能完整地、只有一份地傳到這裡。如果中間某一層自己 log 了一次、甚至把錯誤接住不再往上丟呢？第二件事的「點餐成功」和第三件事的那兩行 log，就是這樣來的。

log 為什麼印了兩行，「點餐成功」為什麼是假的？

這是事發時 POST /orders 的程式碼。repository、service 各自 catch 了一次，各自 log，service 還把錯誤吞掉回傳 null：

// repository
catch (err) {
  logger.error({ msg: 'insert failed', error: String(err) })
  throw new UpstreamError('資料庫查詢逾時')            // 沒有 cause
}
// service
catch (err) {
  logger.error({ msg: 'placeOrder failed', error: String(err) })
  return null                                          // 吞掉
}

當資料庫查詢逾時，事情依序這樣發生：

  • repository 記一行 log，再丟出新的 UpstreamError，但沒有放 cause，原始的 57014 就在這裡丟了。
  • service 接住它，再記一行 log，然後回傳 null。錯誤到這裡就消失了，吞掉（swallow）指的就是這種接住之後既不處理、也不往上丟的寫法。
  • handler 拿到 null，不知道發生過錯誤，照常回客人「201 點餐成功」。訂單根本沒有寫進資料庫，這就是第二件事。
  • repository、service 各記一行，同一個錯誤就是兩行。告警數量翻倍，搜尋時分不出是一次還是兩次，每一行都沒有 errorId 能對上是哪個請求，這就是第三件事看到的 log。

每一層都 log，看起來是「多記一點比較保險」，實際上資訊沒有變多，只是重複，而且最關鍵的原始 code 反而丟了。修正的規則有四條，每一條都對應上面一個問題：

  • 在處理錯誤的那一層記錄，而且只記一次。中間層不知道錯誤最後會不會被處理掉，例如上層可能重試一次就成功了，那這次失敗根本不算問題。中間層沒有資格判斷，所以不記；邊界是最後決定怎麼回應的地方，由它記。
  • 往上丟的時候用 cause 包起來，資訊只會變多，不會變少。
  • catch 之後一定要做一件事：處理它（回應、重試、改用備案）、包裝後往上丟，或在邊界記錄。空的 catch {} 是最難除錯的 bug，因為它什麼痕跡都不留。真的要忽略時，寫註解說明為什麼可以忽略，並且只接你預期的那一種（檢查 code，其他的重新 throw）。
  • 可預期的錯誤不記成 error。404、409 是正常運作的一部分，記成 error 會淹沒真正的問題；需要統計時用 info 等級或指標（第 19 課）。

照這四條改，repository 只包裝、放 cause、不 log；service 不 catch；handler 產生一個 errorId，只有 5xx 才記一行，裡面有沿著 cause 鏈收集到的每一層 code。資料庫逾時時，客人收到 503 和 errorId，log 剛好一行、對得上同一個 errorId、看得到 57014。這正是練習 3 要你做的事。

💡 實務上：review 時看到 catch，先問它做了哪一件事
「只記一次、不要吞掉」很難靠記性維持，因為每一個多餘的 log 單獨看都很合理。團隊 review 時可以把新增的 catch 都過一遍：它處理了錯誤、包裝後往上丟，還是在邊界記錄？三者都不是，就是吞掉；它自己 log 之後又往上丟，就是重複記錄。return null、return [] 這種「失敗時回傳空值」的寫法特別要注意，呼叫的人分不出「沒有資料」和「出錯了」，咖啡店的「點餐成功」就是這樣發生的。

到這裡，同步的錯誤都能完整傳到邊界了。但第二件事還有另一種可能、第三件事的當機也還沒解釋：有些錯誤發生的時候，外面的 try/catch 早就執行完了，它們永遠到不了邊界。

哪些錯誤根本到不了邊界？async 錯誤的陷阱

邊界能接住錯誤，靠的是錯誤沿著呼叫鏈往上傳：handler await service、service await repository，任何一層 throw，錯誤就會一路回到 handler 的 try/catch。只要中間有一段沒被 await，這條鏈就斷了。TypeScript 課第 9 課練過 async 的幾個經典 bug，放到伺服器上，後果是錯誤遺失：客戶端已經拿到成功的回應，錯誤才在之後發生，而且沒有任何 catch 接得到。下面這段想一次存三筆資料，在 work/18 執行 node examples/floating.ts，先看「回應 201」那行印出的陣列：

;[1, 2, 3].forEach(async id => await save(id))   // forEach 不理 callback 回傳的 Promise
console.log('回應 201，這時已經存好的：', saved)
回應 201，這時已經存好的： []
file:///…/examples/floating.ts:7
  if (id === 3) throw new Error(`第 ${id} 筆寫入失敗`)
                      ^

Error: 第 3 筆寫入失敗

callback 裡的 await 只暫停 callback 自己，forEach 呼叫完三次 callback 就回傳，不看它們回傳的 Promise。所以回應說成功時，其實一筆都還沒存，這是第二件事的另一種成因。第 3 筆失敗時，外面的 try/catch 早就執行完了，錯誤變成沒人處理的 rejection，整個程序以結束碼 1 結束，其他客人的請求也一起斷掉，這就是第三件事的當機。這種沒被 await、也沒接 .catch 的 Promise 叫浮動 Promise（floating promise）。

改法看你要的是依序還是同時：依序存用 for…of 加 await；同時存用 await Promise.all(ids.map(save))。兩種寫法都讓外層真的等到每一筆完成，任何一筆失敗都會變成 handler 接得到的錯誤。typescript-eslint 的 no-floating-promises 規則能在編輯器裡就把漏掉的 await 標出來。

改用 Promise.all 之後，還有一個常被誤會的地方：它在第一個失敗時就 reject，但其他的 Promise 不會停，會繼續在背景跑完。下單後同時寄簡訊、Email、推播，Email 失敗時另外兩個還在進行。執行 node examples/all-settled.ts，看 reject 的時間點和後面兩行「完成」：

Promise.all 在 22ms 就 reject：Email 失敗
  62ms 推播 完成
  101ms 簡訊 完成
---- allSettled ----
  …
  成功 簡訊
  失敗 Email 失敗
  成功 推播

所以要先想清楚你要的是哪一種行為。要「一個失敗就全部停下」，得像第 17 課那樣用 AbortController 主動取消其他的；要「每個都做完，再看誰失敗」，用 Promise.allSettled，它等全部結束，回傳每一個的 { status: 'fulfilled', value } 或 { status: 'rejected', reason }。下單後的三種通知，一個失敗不該影響其他，就用 allSettled，再把失敗的記下來。

除了沒 await 的 Promise，還有兩個地方的錯誤會逃出 try/catch，原因都一樣：錯誤發生時，包住它的 try 已經不在呼叫堆疊上了。

  • 計時器和事件的 callback：try { setTimeout(() => { throw … }) } catch {} 接不到。setTimeout 只是登記一個 callback 就回傳，try 隨即結束；callback 是之後由 第 7 課的 event loop 呼叫的，那時已經沒有人包著它。錯誤變成 uncaught exception。
  • EventEmitter 的 'error' 事件：沒有掛 'error' 監聽器時，emit 'error' 會直接 throw（第 8 課）。stream、socket、伺服器都是 EventEmitter，所以這比想像中常見。
💡 實務上：浮動 Promise 靠工具抓，不靠眼睛
這類 bug 在本機幾乎測不出來：資料庫很快、不會失敗，回應和寫入的先後看起來都對，上線遇到慢查詢才出事。所以團隊專案通常直接開 typescript-eslint 的 no-floating-promises，讓 CI 擋下來，review 時就不用一行行找漏掉的 await。真的要「送出去不等結果」（例如下單後寄 Email），也要明確寫 .catch 記 log，讓讀程式的人知道這是刻意的。選 Promise.all 還是 allSettled 時先問：其中一個失敗，整件事算不算失敗？訂單寫入失敗算，通知失敗不算。

工具能擋掉大部分浮動 Promise，但不可能擋掉全部，計時器裡的 bug 也總會有漏網的。這些錯誤逃出所有 try/catch 之後，並不是憑空消失，而是落到程序層級。第三件事的當機就停在那裡，下一節看它落地之後該怎麼處理。

逃走的錯誤最後去哪？程序層級的最後一道防線

一路沒人接的錯誤，最後會變成程序層級的兩種事件，Node 對它們有預設的處理方式：

  • uncaughtException：同步丟出、沒有任何 catch 接住的例外，例如計時器 callback 裡的 throw。預設行為是把 stack 印到 stderr，以結束碼 1 結束程序。
  • unhandledRejection：被 reject、沒有任何地方處理的 Promise，例如上一節的浮動 Promise。目前 Node 的預設模式（--unhandled-rejections=throw）是：有掛 'unhandledRejection' 監聽器就交給它，沒有就把它當成 uncaught exception，程序同樣以結束碼 1 結束。舊版的行為不同，見課末。

也就是說，第三件事裡程序結束不是意外，而是 Node 的預設行為。第一個念頭通常是「那就掛個監聽器接住，別讓它結束」：process.on('uncaughtException', …) 確實可以取代預設行為。但 Node 文件寫得很明確：這個事件的正確用途是在結束前同步清理資源，在 uncaughtException 之後繼續正常運作是不安全的。

為什麼不安全？例外是在某段程式執行到一半時中斷它的。被中斷的那段程式可能正在改記憶體裡的一筆訂單，改了一半；可能拿了一個連線的鎖，還沒放；可能該把某個計數器減一，還沒減。這些都是程式裡沒有預期的中斷點，所以也沒有任何程式會去把它們復原。你不知道哪些狀態壞了，之後的每個回應都可能是錯的，而且錯得很安靜：不會再有錯誤，只會有錯的結果。這正是第一節說的：bug 不能「處理」，因為處理之後的狀態不可信。

所以業界的做法是讓它崩潰（let it crash）：記一行 log，停止接新請求，以非 0 的結束碼結束，再由監督者（supervisor）重新啟動一個狀態乾淨的程序。監督者是部署環境裡負責「程序掛了就重開」的系統，例如 systemd（部署課第 6 課）、Docker 的 restart policy、Kubernetes。結束碼要是 1，監督者和監控才知道這是壞掉、不是正常關機。新的程序從頭建立所有狀態，比在壞掉的狀態上繼續跑可靠得多。

寫成程式碼，兩個事件都交給同一個 fatal：

function fatal(origin: string, err: unknown) {
  const line = JSON.stringify({
    level: 'fatal', msg: origin, errorId: randomUUID(),
    name: Error.isError(err) ? err.name : typeof err,
    message: Error.isError(err) ? err.message : String(err),
  })
  writeSync(2, line + '\n')   // 同步寫進 stderr
  server.close()             // 不再接新的連線
  process.exit(1)
}
process.on('uncaughtException', err => fatal('uncaughtException', err))
process.on('unhandledRejection', reason => fatal('unhandledRejection', reason))

逐行看幾個刻意的選擇：

  • 為什麼用 fs.writeSync(2, …)，不用 console.error：Node 文件說明 stdout／stderr 接到管線（pipe）時，在 POSIX 系統上是非同步寫入；process.exit() 會立刻結束，還沒寫出去的內容就掉了。正式環境的 log 幾乎都是經過管線收集的，用 console.error 等於最重要的那一行最可能遺失。2 是 stderr 的編號（file descriptor，第 2 課）。
  • 為什麼先用 Error.isError 確認：'unhandledRejection' 的 reason 不一定是 Error，Promise.reject('字串') 也行。和上一節邊界的道理一樣，先確認再讀屬性。
  • 為什麼兩個都掛：只掛 'uncaughtException' 也接得到 rejection（會被轉成 uncaught exception），但分開掛，log 裡的 msg 直接告訴你是哪一種，比較清楚。
  • 進行中的請求會被切斷：這裡直接結束，正在處理的請求沒有機會回應。第 21 課會做優雅關機：先停止接新請求、等進行中的請求做完、設一個時限再結束。

讀到這裡可能會疑惑：第 13 課的處理函式丟錯時，伺服器回 500 之後繼續服務其他人，為什麼這裡卻要讓程序結束？差別在錯誤是在哪裡被接住的。

處理函式裡的錯誤和程序層級的錯誤界線不同。處理函式丟出的錯誤被邊界接住，回 500、程序繼續服務其他人，這是第 13 課的做法：錯誤只影響這一個請求。會一路跑到 uncaughtException 的，代表它發生在你沒預料的地方，那才是要讓程序結束的時候。

回到第三件事：凌晨三點的當機，根源就是上一節那種沒被 await 的 Promise，像 forEach(async …) 裡第 3 筆失敗的那個例子。修掉那個 bug 是一件事；加上這道防線後，下次再有漏網的錯誤，log 裡會留下一行帶 errorId 的 fatal，程序乾淨地結束並被重啟，而不是只有一段沒人看得懂的 stack。練習 2 要你在 main.ts 加上它。

💡 實務上：let it crash 的前提是有人會重開
敢讓程序結束，是因為部署時已經確認過三件事：監督者真的設了自動重啟（systemd 的 Restart=、Docker 的 restart policy）；正式環境通常跑不只一個實例，一個重開時其他的還在接請求；監控會看重啟次數。最後一點最容易漏：同一個 bug 每個請求都觸發時，程序會不停「啟動、崩潰、重啟」，服務看起來還活著，其實一直在斷線，所以重啟次數突然變多要告警。上線前問一句「這個程序掛了誰會重開、誰會知道？」，答不出來就還不能上線。

三件事都追到了根源，也都有了對應的規則。接下來在 work/18 把它們依序做出來：先做錯誤類別和轉換（練習 1），再加程序層級的防線（練習 2），最後把 POST /orders 的三層改成只在邊界記一次（練習 3）。

練習

在 learn/ 執行 node check.mjs node 18 建立 work/18/。report.ts 是練習 2 用的、有 bug 的排程工作，不用改。練習 3 會用到練習 1 的 errors.ts，請依序做。

練習 1：完成 errors.ts。AppError 的建構子：status 從 PROBLEMS[code] 查；expose 沒給時，4xx 是 true、5xx 是 false；options.cause 要保留成 err.cause；name 是實際的類別名稱。四個子類別（NotFoundError、ValidationError、ConflictError、UpstreamError）要把 options 傳下去。再完成 toProblem(err, errorId)：AppError 照表回 { type: PROBLEM_BASE + type, title, status, detail }，expose 是 true 時 detail 是錯誤訊息，否則是 GENERIC_DETAIL；ValidationError 多一個 errors（它的 details）；5xx 才加 errorId。其他任何東西（TypeError、被 throw 的字串、物件、null）一律是 INTERNAL 的 500，不能讀它的欄位，也不能讓原始內容出現在回應裡。

練習 2：main.ts 啟動伺服器，JOB_DELAY_MS 毫秒後執行一次排程工作；BUG=exception 時它在計時器裡同步 throw TypeError，BUG=rejection 時它忘了 await 一個會失敗的 Promise。先執行 BUG=exception node main.ts 看看現在的樣子。加上程序層級的處理：發生 uncaughtException 或 unhandledRejection 時，在 stderr 印一行 JSON，至少有 level: "fatal"、msg、errorId（每次不同）、name、message（原始錯誤的名稱和訊息）；接著停止接受新請求，並以結束碼 1 結束。測試會在出錯後最多等 10 秒，程序沒自己結束就算錯。

練習 3：order-flow.ts 的 POST /orders 經過 repository → service → handler 三層，現在每一層都 log、包裝時丟了 cause、service 把錯誤吞掉、errorId 產生了兩次。修好它：repository 把資料庫錯誤包成領域錯誤（code 是 '23505' → ConflictError、'57014' → UpstreamError，其他原樣往上丟；資料庫的訊息會隨語言設定改變，只能看 code），一律放 cause，不 log；service 不 log、不 catch；handler 是唯一的錯誤邊界：產生一個 errorId，用練習 1 的 toProblem 回應，只有 5xx 才呼叫一次 logger.error({ msg, errorId, name, message, codes })，name 是最外層錯誤的名稱，codes 是沿著 cause 一路往下收集到的每一層 code（例如 ['UPSTREAM_UNAVAILABLE', '57014']）。測試會傳入會丟各種錯誤的假資料庫和收集 log 的 logger：23505 要 409、0 行 log；57014 要 503、剛好 1 行；不認得的錯誤和 TypeError 要 500、剛好 1 行；回應的 errorId 要和 log 相同。

練習 4：「資料庫查詢逾時」和「讀到 undefined.price」各是哪一種錯誤？

✓ 程式完全正確，資料庫也可能因為負載高而逾時，這是正常運作中會發生的失敗，要處理：回 503、考慮重試、記 log 觀察頻率。讀 undefined 的屬性表示程式對資料的假設錯了，只有修程式能解決。兩者都可能回 5xx，但後續動作完全不同：前者調整逾時與重試，後者找出 bug 修掉。

練習 5：同事在 main.ts 加了 process.on('uncaughtException', err => console.error(err))，說「這樣伺服器再也不會掛了」。有什麼問題？

✓ 例外中斷了某段程式的中間，記憶體裡的資料、鎖、計數器可能停在不一致的狀態。Node 文件明確說在 uncaughtException 之後繼續正常運作是不安全的。正確做法是記 log 後以結束碼 1 結束，讓監督者重啟一個乾淨的程序。b 錯：沒有 'unhandledRejection' 監聽器時，rejection 也會變成 uncaughtException 交給它。d 錯：掛了監聽器，預設的結束行為就被取代了，這正是危險的地方。

練習 6：[1, 2, 3].forEach(async id => await save(id)) 的下一行開始執行時，三個 save 都完成了嗎？

✓ await 只暫停 callback 自己，forEach 呼叫完三次 callback 就回傳，不看它們回傳的 Promise。下一行通常在任何一個 save 完成之前就執行了，save 失敗時也沒人接，變成 unhandled rejection。外層是不是 async 都一樣。依序做用 for…of 加 await，同時做用 await Promise.all(ids.map(save))。

常見錯誤

  • catch 之後什麼都不做：錯誤消失，留下的只有奇怪的結果。處理它、包裝後往上丟，或在邊界記錄；真的要忽略，只接預期的 code，其他的重新 throw。
  • 失敗時回傳 null 或空陣列：呼叫的人分不出「沒有資料」和「出錯了」，咖啡店的「點餐成功」就是這樣來的。讓錯誤往上丟到邊界。
  • 每一層都 log：一個錯誤變成好幾行，告警翻倍、搜尋時分不出次數。只在錯誤邊界記一次，中間層用 cause 往上傳。
  • 包裝錯誤時丟掉 cause：log 只看得到外層的「資料庫查詢逾時」，看不到原始的 code 和訊息。一律 new XxxError(訊息, { cause: err })。
  • 把內部訊息回給客戶端：SQL、表名、檔案路徑、stack 都是攻擊者的情報。5xx 回通用訊息加 errorId，細節只寫 log。
  • throw 字串而不是 Error：沒有 stack、沒有 name，instanceof 和 Error.isError 都認不出來。一律 throw Error 或它的子類別；處理錯誤的程式也要能接受被 throw 的任何東西。
  • 子類別沒設 name：log 和 stack 都只寫 Error。在父類別寫 this.name = new.target.name。
  • 用錯誤訊息判斷種類：訊息會改、會翻譯。用 code 或 instanceof。
  • forEach(async …) 和忘了 await：回應先送出、錯誤後到，沒人接得住。用 for…of＋await 或 Promise.all，並開啟 no-floating-promises 檢查。
  • uncaughtException 之後繼續執行：程式的狀態不可信。記 log、以結束碼 1 結束，交給監督者重啟。
  • 可預期的 404、409 記成 error：真正的問題被淹沒。error 等級留給 5xx。

補充與查表

instanceof 什麼時候會判斷錯

instanceof 看的是原型鏈：物件的原型是不是那個類別的 prototype。兩種情況下，明明是同一種錯誤卻會得到 false。一是同一個套件被裝了兩份（例如兩個相依套件各自要求不同版本），兩份各有自己的錯誤類別。二是錯誤來自另一個 realm：realm 是一套獨立的全域環境，例如瀏覽器的 iframe、Node 的 node:vm，各有自己的一份 Error。這兩種情況改看 code，它跨套件、跨程序（錯誤被序列化傳過來）都還在。

Error.isError(value) 跨 realm 也判斷正確，{ __proto__: Error.prototype } 這種假的會回 false。Node 24 可以用（本機 24.22.1 驗證）；原本的 util.types.isNativeError 從 v24.2.0 起在文件中標為 deprecated，建議改用 Error.isError。

AggregateError：一次裝了多個錯誤

AggregateError 是一次裝了多個錯誤的錯誤，errors 屬性是陣列。Promise.any 全部失敗時會丟它；第 17 課連 localhost 失敗時，fetch 的 cause 也是它（IPv6 和 IPv4 各失敗一次）。log 時要把 errors 裡的每一個都印出來。

throw 還是回傳 Result？

TypeScript 課第 27 課用 Result 把「可能失敗」寫進型別。兩者可以並用：領域內的邏輯（例如狀態轉換能不能做）回傳 Result，呼叫的人一定得處理；跨好幾層、呼叫的人通常也沒辦法處理的失敗（找不到、資料庫逾時）用 throw，一路傳到邊界統一轉換。bug 一律是 throw，不要包成 Result。

程序層級事件的細節

  • unhandledRejection 的預設行為從 v15.0.0 起才是上面說的「沒有監聽器就當成 uncaught exception、結束程序」；之前只印警告，程序繼續跑。
  • 沒有掛 'unhandledRejection' 時，rejection 會變成 uncaughtException，'uncaughtException' 監聽器的第二個參數 origin 是 'unhandledRejection'。
  • 只想觀察、不改變預設的結束行為，可以用 'uncaughtExceptionMonitor' 事件。

小結

  • 可預期的錯誤（找不到、驗證失敗、衝突、上游逾時）要處理：回對的狀態碼、重試、改用備案；程式錯誤（bug）要修：記完整資訊，程序狀態不可信時讓它結束。判斷方法是問「程式完全正確時會不會發生」。
  • 錯誤物件帶三樣東西：子類別與正確的 name、穩定的 code、保留原因的 cause。自己的類別用 instanceof，別人的錯誤看 code，判斷是不是 Error 用 Error.isError。
  • 業務程式只丟領域錯誤，在 HTTP 邊界一個地方轉成 problem details；4xx 顯示訊息，5xx 回通用訊息和 errorId，同一個 errorId 寫進 log。
  • 每個錯誤只在邊界記一次，往上丟用 cause 包起來，不要吞掉，可預期的錯誤不記成 error。
  • 浮動 Promise、forEach(async …)、計時器與事件 callback 裡的 throw 都會逃出 try/catch；Promise.all 第一個失敗就 reject 但其他的還在跑，要收集全部結果用 allSettled。
  • uncaughtException 和 unhandledRejection 是最後一道防線：同步寫一行 fatal log，停止接新請求，以結束碼 1 結束，由監督者重新啟動。

這課的 log 只寫了「在邊界記一行」，還沒處理那一行該長什麼樣子。下一課把 log 做好：一行一個 JSON、正確序列化 Error 和整條 cause 鏈，並用 AsyncLocalStorage 讓同一個請求的每一行 log 都自動帶上 request id。
