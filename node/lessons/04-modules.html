階段 1：Node 與開發環境 · 第 4 課

模組系統：ESM、CommonJS 與套件解析

咖啡店有一支幾年前寫的價目表程式 convert/：讀進 menu.csv，用一個舊的稅金套件 legacy-tax.cjs 算稅，印出每個品項含稅的價格。它用 require() 和 module.exports 寫成。這課的任務是把它改成這門課的寫法 ES module，再讓它長成一個小專案：檔案多了、路徑變深時還好維護，最後接上資料庫，整個程式只建一個連線池。練習 1～3 就是這個任務的三個階段。

在 Vite 專案裡，import 少寫副檔名、寫錯路徑，打包工具會幫你補好或在建置時告訴你。Node 不會：它照字面去找檔案，找不到就停，而且錯誤訊息常常牽涉到你沒聽過的規則。搬移的每一步都會撞到一條這樣的規則，這課就跟著價目表遇到的錯誤，一條一條講清楚。

這課的路線：
  1. 價目表裡的 require 是什麼、Node 怎麼決定一個檔案用哪一套規則：為什麼有兩套模組系統，同樣是 .ts，Node 看什麼決定。
  2. 改成 ES module 之後哪幾行會壞：少了副檔名、__dirname、讀 JSON，在 Node 的 ES module 裡各要怎麼寫。
  3. 不能改的 legacy-tax.cjs 怎麼引入：ES module 和 CommonJS 互相引用的規則，named import 為什麼會失敗。
  4. import 'pg' 怎麼變成磁碟上的檔案、專案變深後路徑怎麼整理：套件解析、exports 與 imports 欄位。
  5. 怎麼讓整個程式只有一個連線池：模組只執行一次，以及伺服器剛啟動同時進來 10 個請求時，怎麼不建出 10 個。
這課會用到：
  • TypeScript 課第 25 課的 import／export：用 export 交出、import 拿來用。
  • 第 3 課的 package.json 和 node_modules：專案的設定檔，與裝好的套件放的資料夾。
  • TypeScript 課第 12 課的 single-flight：進行中的工作共用同一個 Promise，大家一起 await 它，同一件事不會被做好幾次。

價目表裡的 require 是什麼？Node 的兩套模組系統

先看價目表的 convert/main.ts 開頭：

const config = require('./config.json')
const menu = require('./menu.ts')
const tax = require('./vendor/legacy-tax.cjs')

這三行在做的事，你在 Vue 專案裡天天做：從別的檔案拿東西來用。只是寫法不是 import。要知道為什麼有兩種寫法，先從「模組」本身說起。

模組（module）就是一個檔案：檔案裡宣告的變數只在這個檔案裡看得到，要給別人用就匯出（export），要用別人的就匯入（import）。需要這個機制，是因為沒有它的時候，所有程式共用同一個全域範圍：兩個檔案都宣告 price，後載入的就把前面的蓋掉，而且看不出哪個檔案依賴哪個檔案。模組讓每個檔案有自己的範圍，依賴關係寫在 import 那幾行，一目了然。

Node 有兩套模組系統，原因是歷史：

  • CommonJS（CJS）：Node 從 2009 年就有的寫法，用 require() 和 module.exports。當時 JavaScript 語言還沒有模組，Node 自己設計了一套。require() 是一個普通的函式：執行到那一行才去讀檔、執行那個檔案，把它的 module.exports 同步回傳給你。價目表就是這種寫法。
  • ES module（ESM）：2015 年進入語言標準的 import／export，瀏覽器、Vite、Vue 專案都用它。import 不是函式呼叫，是語法，寫在檔案最外層，所以 Node 不用執行程式，讀原始碼就知道這個檔案依賴誰，能在執行前先把整串依賴載入好。

兩者的差別整理成一張表。最後兩列都來自上面那一點：CommonJS 執行到才載入，ES module 執行前先載入好。

這門課一律寫 ES module：它是標準，前後端寫法一樣。但舊套件、舊專案和某些工具的設定檔還是 CommonJS，所以要看得懂，也要知道兩邊怎麼互相呼叫。價目表要從左欄搬到右欄。不過把 require 換成 import 之前有個問題：convert/ 裡的檔案副檔名都是 .ts，Node 要怎麼知道該用哪一套規則執行它？

同樣是 .ts，Node 怎麼決定用哪一套規則？

Node 在執行一個檔案之前，必須先決定它是 CommonJS 還是 ES module，因為兩套的語法和行為不同：同一行 import，在 ES module 是合法語法，在 CommonJS 是語法錯誤。Node 依序判斷：

副檔名是最強的訊號：.mjs／.mts 一律是 ES module，.cjs／.cts 一律是 CommonJS，不管 package.json 寫什麼。一般的 .js／.ts 就要看最近的 package.json：從檔案所在的資料夾往上找，第一個找到的那個；它的 "type" 寫 "module" 就是 ES module，寫 "commonjs" 就是 CommonJS。

現在打開價目表的 convert/package.json：它只有 name 和 private，沒寫 type，落在圖上最右下那一格。這種情況叫語法偵測（syntax detection）：Node 先當 CommonJS 解析，遇到 import／export 解析失敗，再改用 ES module 重新解析一次。價目表目前全是 require，當 CommonJS 解析就成功，所以照 CommonJS 執行。等你把它改成 import，程式還是會跑，但會印出警告。在練習資料夾執行 node examples/typeless/hello.js（旁邊的 package.json 只有 name）就能看到：

$ node examples/typeless/hello.js
(node:91619) [MODULE_TYPELESS_PACKAGE_JSON] Warning: Module type of file:///…/hello.js is not specified
and it doesn't parse as CommonJS.
Reparsing as ES module because module syntax was detected. This incurs a performance overhead.
To eliminate this warning, add "type": "module" to …/examples/typeless/package.json.
路徑分隔符號是 /

警告說得很清楚：多解析一次有效能成本，修法是寫上 "type": "module"。附近完全沒有 package.json 的情況見課末「補充與查表」。

資深的做法是永遠寫上 type，不要讓 Node 猜。除了效能，更大的問題是猜的結果會隨著程式內容改變：同一個資料夾，今天全是 require 就是 CommonJS，明天有人加了一行 import 就變成 ES module，行為跟著變，而別人讀專案時從設定上看不出來。這門課的 node/practice/package.json 寫了 "type": "module"，所以底下的 .ts 都是 ES module。

所以搬移價目表的第一步，是在 convert/package.json 加上 "type": "module"。加上之後，Node 改用 ES module 的規則執行 main.ts 和 menu.ts，原本那些 require 寫法就一行一行開始失敗。

改成 ES module 之後，價目表哪幾行會壞？

上一節把 convert/ 切到 ES module 規則。ES module 在 Node 裡有四條和 Vite 習慣不同的規則，價目表正好每一條都會碰到。照錯誤出現的地方一條一條看。

第一條：沒有 require、module.exports、__dirname、__filename。它們不是語言內建的東西，是 Node 執行 CommonJS 檔案時，包在每個檔案外面提供的變數。ES module 沒有這層包裝。所以加上 "type": "module" 後執行 node convert/main.ts，第一個錯誤出在 main.ts 第一行的 require('./config.json')：

ReferenceError: require is not defined in ES module scope, you can use import instead

menu.ts 裡的 __dirname 是同一類錯誤，等 main.ts 改好、真的載入到 menu.ts 時就會出現：

ReferenceError: __dirname is not defined in ES module scope

匯入匯出的部分很直接：require 改成 import，module.exports = { readMenu } 改成在函式前面寫 export。__dirname 則要換成 import.meta，下面第三條說明。

第二條：相對路徑一定要寫副檔名。main.ts 引入菜單模組要寫 './menu.ts'，不是 './menu'；資料夾也不會自動找 index，要寫 './routes/index.ts'。漏了就是 ERR_MODULE_NOT_FOUND。你在 Vue 專案裡寫 './menu' 能動，是 Vite 在建置時幫你試了各種副檔名；瀏覽器本身拿到 './menu' 只會去請求那個網址。Node 的 ES module 也不猜，寫什麼就找什麼。這門課直接用 node 執行 .ts，所以寫 .ts；先用 tsc 編譯成 .js 再執行的專案寫法不同，第 5 課說明。

第三條：要知道「這個檔案在哪」，用 import.meta。價目表的 menu.ts 用 path.join(__dirname, 'menu.csv') 找到放在旁邊的 menu.csv。ES module 裡對應的東西是 import.meta：關於這個模組本身的資訊。執行 node examples/where-am-i.ts：

import.meta.url      file:///Users/you/…/work/04/examples/where-am-i.ts
import.meta.filename /Users/you/…/work/04/examples/where-am-i.ts
import.meta.dirname  /Users/you/…/work/04/examples
import.meta.main     true
typeof require       undefined
typeof __dirname     undefined

import.meta.url 是這個檔案的 file: 網址，filename 是完整路徑，dirname 是它所在的資料夾，對應原本的 __filename 和 __dirname。最後兩行印證了第一條：ES module 裡沒有 require 和 __dirname。import.meta.main 是比較新的功能，說明見課末。

為什麼一定要用它組路徑，不能直接寫 readFileSync('menu.csv')？因為相對路徑是從工作目錄（第 1 課：你在哪個資料夾下指令）算起，不是從程式檔所在的資料夾。你在 convert/ 裡執行時剛好找得到，換到上一層執行 node convert/main.ts 就變成去找上一層的 menu.csv，找不到。readFileSync(join(import.meta.dirname, 'menu.csv')) 不管從哪裡執行，永遠指向程式旁邊那個檔案。練習 1 的測試就會從別的資料夾執行價目表，專門抓這個錯。

第四條：引入 JSON 要加 import attributes。main.ts 的 require('./config.json') 不能只改成 import config from './config.json'，會得到：

TypeError [ERR_IMPORT_ATTRIBUTE_MISSING]: Module "…/config.json" needs an import attribute of "type: json"

import attributes 是 import 時附加的資訊，with { type: 'json' } 告訴 Node「我要的是 JSON，不是程式」。這是安全設計：明確說好要的是資料，就算那個檔案（或從網路載入的模組）被換成 JavaScript，也不會被當成程式執行。引入後只有 default，內容就是整個 JSON：

import config from './config.json' with { type: 'json' }   // 只有 default，內容就是整個 JSON

另外，內建模組照這門課的習慣加 node: 前綴：'node:fs'、'node:path'。價目表本來就這樣寫了，搬過來時保留。前綴讓人一眼看出這是 Node 內建的，也不會和 npm 上同名的套件混淆。

改成 ES module 之後，價目表也多了一個 CommonJS 沒有的能力：top-level await，在模組最外層直接 await，例如啟動時先讀設定檔。它可行正是因為 ES module 執行前就知道整串依賴，Node 可以讓依賴它的模組等它跑完。代價也在這裡：等待期間，import 這個模組的檔案全部跟著卡住（啟動變慢），而且有 top-level await 的模組不能被 CommonJS 的 require() 載入（下一節）。如果等的 Promise 永遠不會結束，Node 印出 Warning: Detected unsettled top-level await，並以結束碼 13 結束（結束碼在第 2 課）。

照這四條改完，menu.ts 已經是乾淨的 ES module，main.ts 也只剩一行：require('./vendor/legacy-tax.cjs')。這個稅金套件是 CommonJS，而且不能改。ES module 能直接 import 它嗎？

不能改的 legacy-tax.cjs，要怎麼從 ES module 引入？

先確認它的身分：副檔名是 .cjs，照上上節的判斷順序，它一律是 CommonJS，convert/package.json 加了 "type": "module" 也不影響它。所以這是一個「從 ES module 引入 CommonJS」的問題。

ES module 可以 import CommonJS，這是正式支援的。default import 拿到的就是 module.exports，一定拿得到。麻煩在 named import（import { calcTax } from …）：CommonJS 的 module.exports 要執行程式才會有值，但 ES module 要在執行前就知道每個名字存不存在。Node 的做法是靜態分析：不執行程式，只讀原始碼，猜出 module.exports 上有哪些名字。寫成 module.exports = { calcTax } 或 exports.calcTax = … 猜得到；寫成 module.exports = buildApi() 就猜不到，因為要執行 buildApi() 才知道結果。legacy-tax.cjs 正是後者：

// vendor/legacy-tax.cjs
function buildApi(rate) {
  return { rate, calcTax(price) { return Math.round(price * rate) } }
}
module.exports = buildApi(0.05)

// main.ts
import { calcTax } from './vendor/legacy-tax.cjs'
// SyntaxError: Named export 'calcTax' not found. The requested module './vendor/legacy-tax.cjs'
// is a CommonJS module, which may not support all module.exports as named exports.
// CommonJS modules can always be imported via the default export, for example using:
//   import pkg from './vendor/legacy-tax.cjs';
//   const { calcTax } = pkg;

錯誤訊息已經給了修法：先 default import，再從物件上拿。執行 node examples/interop.ts 看 default import 拿到什麼：印出來的就是 buildApi(0.05) 回傳的那個物件，有 rate 和 calcTax。

要注意 tsc 不會擋這個錯。練習資料夾的 legacy-tax.d.cts 是這個檔案的宣告檔：只描述型別、沒有程式的檔案（TypeScript 課第 25 課）。它用 export = 描述這個物件，npm run typecheck 對 named import 照樣通過（tsc 7.0.2 實測），要執行才失敗。型別檢查只看宣告檔怎麼描述，不知道 Node 執行時的靜態分析猜不猜得到。所以引入 CommonJS 套件時，習慣先用 default import。

真的需要 require（例如某個工具只說明了 require 的用法），可以用 node:module 的 createRequire 自己做一個。examples/interop.ts 也示範了，它拿到的和 default import 是同一個物件：

import { createRequire } from 'node:module'
const require = createRequire(import.meta.url)
const tax = require('./vendor/legacy-tax.cjs')

價目表的搬移到這裡完成：練習 1 就是把這幾節的步驟做一遍。價目表裡我們自己寫的檔案現在全是 ES module，看不到反方向的情況，要換到咖啡店後台才看得到：後台還是幾年前用 require 寫的 CommonJS，想用你剛改好的 menu.ts（ES module）讀菜單。這就是從 CommonJS 引入 ES module。以前只能用 await import()，現在 Node 24 的 require() 也能載入 ES module，稱為 require(esm)（各版本的狀態見課末）。條件是那個 ES module（包括它 import 的所有模組）沒有 top-level await。原因在第一節講過：require 是普通的同步函式，必須當場回傳 module.exports，不能等一個還沒完成的 await：

Error [ERR_REQUIRE_ASYNC_MODULE]: require() cannot be used on an ESM graph with top-level await. Use import() instead.

兩個方向都能互通，代表新舊程式可以並存一段時間，不必一次改完。

💡 實務上：新程式寫 ESM，舊的 CommonJS 不必一次改完
接手舊專案很常遇到：咖啡店後台是幾年前用 require() 寫的，新功能想用 ESM。不要為了統一一次改掉幾百個檔案，風險高又沒有帶來新功能；比較穩的做法是新模組用 ESM，靠上面的互通方式逐步替換。另一個常見情況是升級套件後 import 突然壞掉：先看套件的 changelog 是不是改成只提供 ESM，或改了匯出方式，再決定改寫法還是先固定在舊版本。資深工程師升級大版本前會先問一句：「這版有沒有改模組格式？」

價格要改從資料庫讀：import 'pg' 怎麼變成磁碟上的檔案？

價目表現在是 ES module 了。下一步，店裡想把價格從 menu.csv 改放進資料庫，main.ts 要寫 import pg from 'pg'。前面 import 的都是自己寫的檔案，路徑寫得清清楚楚；'pg' 只是一個名字，Node 怎麼知道它在哪裡？

Node 把 import 後面的字串對應到實際檔案的規則，叫模組解析（module resolution）。它先看字串長什麼樣子，分成三種：

  • './menu.ts'、'../lib/price.ts'：相對路徑，從目前這個檔案所在的資料夾算。
  • 'node:fs'：內建模組。
  • 'pg'、'pg/lib/client.js'：不是路徑、也沒有 node:，只有套件名稱的字串，叫做 bare specifier（裸名稱）。Node 會去 node_modules 找這個套件。

找 node_modules 的方式是從檔案所在的資料夾往上逐層找。work/04/convert/main.ts 寫 import pg from 'pg' 時，Node 依序看：

learn/node/practice/work/04/convert/node_modules/pg   ✗
learn/node/practice/work/04/node_modules/pg           ✗
learn/node/practice/work/node_modules/pg              ✗
learn/node/practice/node_modules/pg                   ✓ 找到了

所以只要在 practice/ 執行一次 npm install，底下每一課都用得到；專案外面的資料夾（例如 /tmp）就找不到。

找到套件的資料夾之後，還要決定載入裡面哪個檔案。Node 讀這個套件的 package.json，如果有 exports 欄位，它就是這個套件對外的「門」：只有列出來的路徑能被 import，其他路徑一律拒絕。以 pg 8.23.1 為例：

"exports": {
  ".": {
    "import": "./esm/index.mjs",
    "require": "./lib/index.js",
    "default": "./lib/index.js"
  },
  "./package.json": { "default": "./package.json" },
  "./lib/*": "./lib/*.js",
  "./lib/*.js": "./lib/*.js"
}
  • "." 是 import 'pg' 本身。裡面依「你怎麼載入」給不同檔案，叫做條件式匯出（conditional exports）：用 import 拿到 esm/index.mjs，用 require 拿到 lib/index.js。價目表用 import，所以拿到的是 esm/index.mjs。
  • 'pg/lib/client.js' 符合 "./lib/*.js"，可以 import。
  • 'pg/esm/index.mjs' 沒有列出來：Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './esm/index.mjs' is not defined by "exports" in …/node_modules/pg/package.json。檔案明明在磁碟上，也不給用。

為什麼要這樣擋？對套件作者來說，exports 決定了什麼算公開 API：沒列出的內部檔案可以隨意改，不算破壞相容（semver，第 3 課）。對使用者來說，看到 ERR_PACKAGE_PATH_NOT_EXPORTED 不要去改 node_modules，改成從套件允許的路徑引入。

💡 實務上：別 import 套件的內部檔案
Code review 常看到 import x from 'some-lib/dist/internal/utils.js'：沒有 exports 欄位的舊套件不會擋你，今天能用，但那不是它承諾的公開 API，下個小版本搬檔案就壞了。遇到「本機能跑、伺服器上找不到模組」，除了比對兩邊的啟動指令（下一節），也要確認伺服器上的 node_modules 裝在往上找得到的位置。

專案變深之後，'../../lib/price.ts' 怎麼整理？

上一節解決了別人的套件怎麼被找到。自己專案裡的檔案一多，問題換成另一個：相對路徑越寫越長。價目表長大後拆成了 aliases/ 這個樣子，三個檔案都要用 lib/price.ts 的 formatPrice，但寫法各不同：main.ts 是 './lib/price.ts'，routes/menu.ts 是 '../lib/price.ts'，routes/admin/report.ts 是 '../../lib/price.ts'。這樣很難一眼看出指的是同一個檔案，搬動任何一個檔案時，裡面的 ../ 也要一個一個重算。

在 Vue 專案你可能用過 tsconfig 的 paths 或 Vite 的 alias 設定 @/ 來解決這件事。但那是給 TypeScript 和打包工具看的，Node 執行時不讀 tsconfig，只設 paths 會得到 ERR_PACKAGE_IMPORT_NOT_DEFINED 或 ERR_MODULE_NOT_FOUND。編輯器不會報錯，執行才失敗。

Node 自己的解法是 package.json 的 imports 欄位（subpath imports）。它跟上一節的 exports 是同一套機制反過來用：exports 決定別人能從你的套件拿什麼，imports 給自己專案內部的路徑取別名。名字一定要以 # 開頭，跟 npm 套件名稱區分：

// package.json
{
  "type": "module",
  "imports": {
    "#lib/*": "./lib/*"
  }
}

// routes/admin/report.ts（不管在第幾層都一樣）
import { formatPrice } from '#lib/price.ts'

* 是萬用字元：#lib/price.ts 對應到 ./lib/price.ts，路徑從 package.json 所在的資料夾算，所以不管引入的檔案在第幾層，寫法都一樣。副檔名照樣要寫，前面那條規則在這裡也成立。imports 欄位 Node 和 TypeScript（module: nodenext）都讀，一份設定兩邊都對。練習 2 就是把 aliases/ 的三個檔案改成這樣。

💡 實務上：路徑別名要讓 Node 也看得懂
別名最常見的坑是開發時靠打包工具跑得好好的 @/lib/price，部署後改用 node 直接執行就 ERR_MODULE_NOT_FOUND。比較穩的做法是本機和伺服器用同一個指令啟動，內部別名一律用 imports 的 #。遇到「本機能跑、伺服器上找不到模組」，先比對兩邊的啟動指令。

接上資料庫：怎麼讓整個程式只有一個連線池？

路徑整理好了，回到資料庫。程式要查資料庫，得先和資料庫建立連線，而建立連線要時間（網路來回、登入驗證），資料庫能同時接受的連線數也有上限。所以後端不會每次查詢都開一條新連線，而是用連線池（connection pool）：事先開好幾條連線，查詢時借一條、用完還回去，輪流使用（第 20 課詳講）。

連線池整個程式只該有一個。如果每個請求都建一個新的連線池，每個池子各開好幾條連線，資料庫的連線數很快就會用光。問題是：價目表、訂單、報表好幾個檔案都要用它，怎麼讓大家拿到同一個？答案藏在模組的一個特性裡。

一個模組第一次被 import 時，Node 執行它最外層的程式，把匯出的東西存進模組快取（module cache）。之後不管多少檔案 import 它，都直接拿快取裡的同一份，不會再執行。執行 node examples/once/main.ts：a.ts 和 b.ts 都 import counter.ts：

counter.ts 的最外層執行了      ← 只印一次
a.ts 拿到 1
b.ts 拿到 2                  ← 共用同一個 count

如果每個 import 都重新執行一次，b.ts 會拿到另一個從 0 開始的 count，印出 1。它印出 2，證明兩個檔案用的是同一份。這讓模組成為天然的單例（singleton）：整個程式只有一份的物件。連線池就該這樣：在一個模組裡建立，大家 import 同一個。

麻煩在建立連線池要連上資料庫，是非同步的。直覺的寫法是等建好再存起來：

let pool: Pool | undefined
export async function getPool() {
  if (!pool) pool = await createPool()   // 建好之前 pool 一直是 undefined
  return pool
}

單獨呼叫時沒問題。但伺服器剛啟動時同時進來 10 個請求，10 個都在第一個 await 完成前檢查 pool，都看到 undefined，於是建了 10 個連線池。這就是 TypeScript 課第 12 課的競態。修法也一樣是 single-flight：快取 Promise，不是快取結果。Promise 在呼叫 createPool() 的當下就拿得到，不用等它完成；第一個呼叫的人建立 Promise 並存起來，後面的人拿到同一個 Promise，一起等它完成。

還有一個細節：如果第一次連線失敗，存起來的就是一個 rejected 的 Promise，之後每次呼叫都直接拿到同一個錯誤，資料庫恢復了也不會再試。失敗時要把快取清掉，讓下一次呼叫重新建立。練習 3 要你把這兩件事寫出來。

你可能會想到把價目表改成 ES module 時多出來的 top-level await：在最外層直接 const pool = await createPool()，也只會建立一次。但失敗時整個模組載入失敗，import 它的檔案全部跟著壞，沒有機會重試。

模組最外層的變數是全部請求共用的。連線池、設定這種本來就該共用的東西放這裡沒問題；「目前登入的使用者」「這次請求的購物車」放在模組變數裡，兩個請求同時進來就會互相蓋掉，A 看到 B 的資料。每個請求自己的狀態要當參數傳下去（第 19 課會介紹 request context）。

模組快取還牽涉兩個少見但很難查的問題：兩個模組互相 import（循環依賴），以及同一個套件被載入兩份（雙重套件危害）。細節見課末「補充與查表」。

💡 實務上：模組最外層的 let 是 code review 要多看一眼的地方
看到模組最外層有 let 或會被修改的物件，資深工程師會先問：「這個值會不會因請求而不同？兩個請求同時進來會怎樣？」只有整個程式一份、建好後不隨請求改變的東西（連線池、讀好的設定）才適合放這裡。這類問題在本機自己點一下測不出來，上線後請求同時進來才出現，而且很難重現。另外，單例會在測試之間留下狀態；需要在測試裡換掉的東西（例如連線池），改成當參數傳入會好測很多（第 22 課）。

練習

練習檔在 node/practice/work/04/，在 learn/ 執行 node check.mjs node 04 判分。convert/ 和 aliases/ 各有自己的 package.json，是兩個獨立的小專案。

練習 1：convert/ 是用 CommonJS 寫的價目表程式，現在能跑（先執行 node convert/main.ts 看輸出）。把它改成 ES module，輸出要完全一樣：

  • convert/package.json 加上 "type": "module"。
  • menu.ts：require 改成 import、module.exports 改成 export、__dirname 改成 import.meta.dirname。
  • main.ts：引入 menu.ts 要寫副檔名；config.json 用 import attributes 讀；vendor/legacy-tax.cjs 不要改，它是 module.exports = buildApi()，想想該用哪一種 import。

測試會把 convert/ 複製到別處，換掉菜單、店名和稅率，從上一層資料夾執行，所以要從檔案讀資料、用 legacy-tax.cjs 的 calcTax 算稅，也不能用工作目錄組路徑。

練習 2：aliases/ 裡有三個檔案用相對路徑引入 lib/price.ts：main.ts 的 ./lib/price.ts、routes/menu.ts 的 ../lib/price.ts、routes/admin/report.ts 的 ../../lib/price.ts。在 aliases/package.json 加上 "imports": { "#lib/*": "./lib/*" }，把三個檔案都改成 import { formatPrice } from '#lib/price.ts'。node aliases/main.ts 的輸出要跟改之前一樣；測試還會把 #lib/* 指到另一個資料夾，確認三個檔案都真的透過別名引入。

練習 3：db.ts 的 getPool() 現在每次呼叫都用 pool-factory.ts 的 createPool() 建立一個新的連線池（建立要 50ms）。先執行 node examples/try-pool.ts，會看到同時呼叫 10 次就建了 10 個。改好 getPool()：

  • 第一次呼叫時建立，之後都回傳同一個連線池。
  • 10 個呼叫同時進來，也只能建立 1 次，大家拿到同一個物件。
  • 建立失敗時，正在等的呼叫都要收到錯誤；下一次呼叫要重新建立。

不要改 pool-factory.ts，測試會換成一個會計數、也會故意失敗一次的版本。

練習 4：資料夾裡的 package.json 只有 { "name": "shop" }，旁邊的 main.ts 寫了 import { sep } from 'node:path'。執行 node main.ts 會怎樣？

✓ 沒寫 type 時，Node 先當 CommonJS 解析，遇到 import 失敗，偵測到 ES module 語法後重新解析並印警告，提醒你多解析一次有成本、應該寫上 "type": "module"。a 是語法偵測出現之前的舊行為；b 錯在「沒有訊息」：有 package.json 但沒寫 type 會警告。

練習 5：import { calcTax } from 'old-tax' 得到 SyntaxError: Named export 'calcTax' not found，但 import tax from 'old-tax' 之後 tax.calcTax(80) 可以用。為什麼？

✓ 從 ES module 引入 CommonJS 時，default 就是 module.exports，一定可以；named import 是 Node 不執行程式、只讀原始碼猜出來的，module.exports = buildApi() 這種寫法猜不到。a 錯：default import 證明 calcTax 存在。c 錯：ES module 可以 import CommonJS，這是正式支援的。

練習 6：orders.ts 和 menu.ts 都 import { pool } from './pool.ts'，pool.ts 最外層寫了 console.log('建立連線池')。程式啟動後這行會印幾次？

✓ 模組只執行一次，結果存在模組快取，所有 import 它的檔案拿到同一個 pool。這是單例的基礎。b 是常見誤解，如果真的這樣，每個檔案都會有自己的連線池。c 錯：import 一個模組一定會執行它的最外層程式。

常見錯誤

  • 相對 import 漏副檔名：Node 不會補 .ts、也不會找 index，得到 ERR_MODULE_NOT_FOUND。完整寫出 './menu.ts'。
  • 以為 tsconfig 的 paths 在執行時有效：Node 不讀 tsconfig。專案內部別名用 package.json 的 imports，名字以 # 開頭。
  • 在 ES module 用 require 或 __dirname：它們只存在 CommonJS。改用 import、import.meta.dirname，真的需要 require 時用 createRequire(import.meta.url)。
  • 用工作目錄組檔案路徑：readFileSync('menu.csv') 換個資料夾執行就找不到。用 join(import.meta.dirname, 'menu.csv')。
  • 對 CommonJS 套件用 named import：要看套件怎麼寫 module.exports，tsc 也不一定擋得住。不確定就用 default import。
  • 同一個套件被 ESM 與 CJS 各載入一次：會有兩份狀態，instanceof 失效。專案統一用 import。
  • 非同步初始化只快取結果：建好之前同時進來的呼叫都會再建一份。快取 Promise，失敗時清掉。
  • 把每個請求各自的狀態放在模組最外層變數：所有請求共用，會互相蓋掉。用參數傳下去。

補充與查表

循環依賴：兩個模組互相 import

循環依賴（circular dependency）：a.ts import b.ts，b.ts 又 import a.ts。執行 node a.ts 時，Node 先執行 a 依賴的 b.ts；b.ts 要的 a.ts 已經「載入中」，Node 不會回頭等它，直接往下跑。這時 a.ts 一行都還沒執行，b.ts 最外層一用到 a 的 const 就出錯：

// a.ts
import { b } from './b.ts'
export const a = 'A'

// b.ts
import { a } from './a.ts'
export const b = 'B' + a   // ← 這裡：a.ts 還沒執行到 export const a

ReferenceError: Cannot access 'a' before initialization

修法是把兩邊都要用的東西拆到第三個檔案，讓箭頭只有一個方向。出現循環依賴通常代表兩個模組的責任沒分清楚。

雙重套件危害：同一個套件被載入兩份

雙重套件危害（dual package hazard）：套件用條件式匯出給 import 和 require 各一份獨立的程式時，你的程式 import 它、另一個套件 require 它，就會載入兩份，各有各的模組快取和狀態：instanceof 失效、設定只套用到其中一份。pg 8.23.1 避開了這個問題：它的 esm/index.mjs 只是一層殼，裡面 import pg from '../lib/index.js' 再轉手匯出，兩種載入方式最後都是同一份 lib/index.js。遇到沒這樣處理的套件，整個專案統一用 import 引入它。

動態 import：執行到才載入

動態 import（import()）：執行到那一行才載入，回傳 Promise。適合「用到才載入」的大模組，或路徑要執行時才知道的情況，例如外掛：const plugin = await import(`./plugins/${name}.ts`)。這門課的測試也用它載入你的檔案：檔案壞了，只有那一個測試失敗。

import.meta.main：直接執行才跑

import.meta.main 在檔案被直接執行時是 true、被 import 時是 false，可以寫「直接執行才跑」的程式。它在 v24.2.0 才加入，還標示為 Stability 1.0（早期開發中），這門課只示範，不要求你依賴它。

版本備註

  • 語法偵測：如果附近完全沒有 package.json，同樣會偵測，但不印警告（v24.22.1 實測）。
  • import.meta.dirname 和 filename 從 v24.0.0 起是穩定功能。
  • JSON modules 和 import attributes 從 v23.1.0／v22.12.0 起是穩定功能。
  • require(esm)：v22.12.0 起不需要旗標，v24.15.0 起不再是實驗功能（Node 24 文件）。

小結

  • Node 有 CommonJS（require，執行到才同步載入）和 ES module（import，執行前先載入整串依賴）兩套模組系統；這門課寫 ES module，但要看得懂 CommonJS。
  • .mjs／.mts 是 ESM、.cjs／.cts 是 CJS，.js／.ts 看最近的 package.json 的 type；沒寫時 Node 會猜，所以永遠寫上 type。
  • 把價目表改成 ES module：相對路徑寫副檔名、__dirname 換成 import.meta.dirname、JSON 加 with { type: 'json' }；改完還多了 top-level await。
  • 引入 CommonJS 時 default 一定拿得到，named import 是靜態分析猜的，tsc 擋不住；CommonJS 可以 require 沒有 top-level await 的 ES module，新舊程式能並存、逐步替換。
  • 套件從檔案所在的資料夾往上找 node_modules；exports 決定能 import 哪些路徑，imports 給專案內部取 # 別名，Node 不讀 tsconfig 的 paths。
  • 模組只執行一次，可以當單例共用連線池；非同步的單例要快取 Promise，失敗時清掉快取；模組最外層變數是所有請求共用的。
