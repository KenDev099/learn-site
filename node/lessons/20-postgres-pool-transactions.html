階段 5：上線前的準備 · 第 20 課

連接 PostgreSQL：連線池與交易

到目前為止，咖啡店的訂單不是放在記憶體裡，伺服器一重開就不見；就是像第 10 課那樣存在 orders.json，好幾個程序同時寫入就得自己排隊、加鎖。這一課把資料搬進 PostgreSQL：用 pg 套件，寫完咖啡店資料層的四個檔案。db.ts 建立和資料庫的連線，products.ts 搜尋菜單，orders.ts 下單，customers.ts 註冊會員。

寫出「功能正常」的版本不難，PostgreSQL 課第 25 課已經用過 pool.query。難的是上線後的某個午餐尖峰：資料庫被一句慢查詢拖住，所有請求卡著沒有回應，log 卻一片安靜；兩位客人同時點最後一杯拿鐵，庫存變成 -1；有人拿已經註冊過的手機號碼再註冊一次，API 回 500，前端只能顯示「伺服器錯誤」。這一課每一節都在回答同一個問題：這四個檔案要怎麼寫，那天才不會出事。

這課的路線：
  1. 開始前：用 Docker 開一個練習用的 PostgreSQL，放進咖啡店的資料。
  2. db.ts：資料庫一慢，為什麼整台伺服器像當機？連線池怎麼設定，才會快速失敗而不是無限等。
  3. products.ts：菜單搜尋已經用了 $1 參數，搜尋「100%」、前端傳來的排序欄位、回傳的總筆數為什麼還會出錯。
  4. orders.ts：下單要寫三張表，交易為什麼一定要用同一條連線；兩位客人搶最後一杯時庫存怎麼不變成 -1；好幾個品項的訂單遇到死結怎麼辦。
  5. customers.ts 與收尾：手機號碼重複為什麼要回 409 而不是 500；程序結束時怎麼關掉連線池，測試怎麼互不影響。
這課會用到：
  • PostgreSQL 課第 25 課的 pg 基本用法：用 pool.query(sql, [參數]) 查詢，連線由連線池借還；使用者輸入一律走 $1 參數，接字串就是 SQL injection。
  • PostgreSQL 課第 18 課的交易：BEGIN 之後的修改要嘛全部 COMMIT，要嘛全部 ROLLBACK。
  • PostgreSQL 課第 19 課的原子 UPDATE 與死結：UPDATE … SET stock = stock - 1 WHERE stock >= 1 把檢查和扣減放在同一句；兩個交易互等對方的鎖就是死結，PostgreSQL 會取消其中一個。

開始前：讓咖啡店有一個真的資料庫

四個檔案都要連一個真的 PostgreSQL 才能測。我們不把 PostgreSQL 安裝在你的電腦上，而是用 Docker 跑它。先認識三個名詞：

  • 映像（image）：打包好的程式和它需要的執行環境，例如「PostgreSQL 18.6 加上一個精簡的 Linux」。
  • 容器（container）：把映像跑起來的那一份，和你的電腦隔離。刪掉容器，你的電腦不會留下任何東西。詳細原理在 部署課第 7 課。
  • Docker Compose：用一個 compose.yaml 描述要跑哪些容器、怎麼設定，一個指令就啟動。

練習資料夾裡已經有寫好的 compose.yaml，內容是：用 postgres:18.6-alpine 映像，帳號、密碼、資料庫是 learn／learn／coffee，開在你電腦的 54329 port，資料只放在記憶體裡。先打開 Docker Desktop，等選單列的鯨魚圖示顯示 running，再到 learn/node/practice 執行：

$ docker compose up -d --wait     # -d：在背景跑；--wait：等到 healthcheck 通過才結束
$ cp .env.example .env            # DATABASE_URL=postgres://learn:learn@localhost:54329/coffee

第一次會下載 postgres:18.6-alpine 映像（上百 MB）。指令失敗時看訊息：有 Cannot connect to the Docker daemon 表示 Docker Desktop 沒開；port is already allocated 表示 54329 被別的程式佔用（和第 1 課的 EADDRINUSE 是同一件事）。compose.yaml 每一行設定的意思、常用的 docker compose 指令，整理在課末「補充與查表」，現在不用看完。

第二行指令複製出來的 .env 裡有一個 連線字串（connection string）。它用一行描述資料庫在哪裡、用什麼帳號登入，慣例放在環境變數 DATABASE_URL：

postgres://learn:learn@localhost:54329/coffee
           帳號  密碼   主機      port  資料庫

連線字串含密碼，所以放在 .env（已在 .gitignore），不寫在程式碼裡（第 2 課）。

資料庫一開始是空的。先在 learn/ 執行 node check.mjs node 20 取得練習檔（第一次會順便跑測試，沒過沒關係），再到 learn/node/practice/work/20 把咖啡店的資料放進去：

$ node --env-file=../../.env examples/setup.ts    # 建表、放資料，加上這課的 stock 欄位；重跑會整個重建

這個資料庫給你跑範例、在 psql 裡亂改用。練習的測試不用它：每個測試檔會自己建一個隨機名稱的新資料庫，跑完刪掉，所以你怎麼改都不會影響判分。

資料庫準備好了。接下來寫第一個檔案 db.ts：整個程式要怎麼跟這個資料庫建立連線，而且在資料庫變慢的那天不會跟著卡死。

db.ts：資料庫一慢，為什麼整台伺服器像當機？

程式要跟 PostgreSQL 說話，得先建立一條連線：開一條 TCP 連線、送帳號密碼驗證，PostgreSQL 再為這條連線開一個專屬的程序，之後這條連線送來的 SQL 都由那個程序執行。這些步驟比跑一句簡單的 SELECT 還花時間，所以不能每個請求都開一條新連線、用完就關。

解法是連線池（connection pool）：程式先開幾條連線放著，要查詢時借一條，用完還回去給下一個請求用。pg.Pool 就是連線池，pool.query(sql, params) 一次替你做完「借一條、跑一句、還回去」。池子裡的連線數有上限，全部借出去時，下一個要借的請求會進入等候佇列，等到有人還回來才輪到它。

問題就出在「要排多久」。pg 8.23.1（pg-pool 3.14.0）的預設：

選項預設意思
max10池子最多幾條連線
idleTimeoutMillis10000閒置多久的連線關掉
connectionTimeoutMillis0建立連線、或連線全被借走時最多等多久。0 是永遠等
statement_timeout沒設一句 SQL 最多跑多久，超過由資料庫取消（錯誤碼 57014）

把開場的午餐尖峰套進來：資料庫因為一句慢查詢卡住，10 條連線都借給了在等它的請求。第 11 個請求來借連線，因為 connectionTimeoutMillis 是 0，它排隊永遠等。後面的請求一個接一個排上去，伺服器不會報錯、不會寫 log，只是全部沒有回應。前端看到的是逾時，你看到的是一片安靜的 log。

examples/exhaust.ts 重現這件事：它開一個 max: 2 的池子，借出 2 條都不還，再借第 3 條。執行後看第 3 個 connect() 有沒有結束。在 work/20 試試：

$ node --env-file=../../.env examples/exhaust.ts
借出 2 條，都還沒還
第 3 個 connect() 已經等了 1002ms…
第 3 個 connect() 已經等了 2002ms…        （一直等下去，按 Ctrl+C 結束）
$ node --env-file=../../.env examples/exhaust.ts 1000
借出 2 條，都還沒還
第 3 個 connect() 在 1002ms 失敗：timeout exceeded when trying to connect

第二次加上參數 1000，就是把 connectionTimeoutMillis 設成 1 秒：借不到就在 1 秒左右失敗。這叫快速失敗（fail fast）：請求在 1 秒內拿到錯誤、回 503，前端可以顯示「稍後再試」，log 和監控也看得到出事了。比起讓客人對著轉圈的畫面等，這好太多了。

但 connectionTimeoutMillis 只處理「排隊的人」，那句佔著連線的慢查詢還在跑。要限制它，得靠 statement_timeout：pg 在建立連線時把它送給資料庫，之後這條連線上的每一句都有時間上限，超過由資料庫取消。為什麼不能在 Node 這邊取消？因為 pg 的查詢不接受 AbortSignal：客人關掉網頁、第 13 課的 req.signal 被 abort 了，送出去的查詢還是會跑完。真正能限制它的是資料庫這一端的逾時。值依 API 的需求定，報表類的查詢可以在交易裡（用 withTransaction 借到的 client）先下 SET LOCAL statement_timeout 放寬，交易結束就自動恢復；SET LOCAL 在交易外下只會得到 warning，不會生效。

兩個逾時加上去，db.ts 的池子長這樣：

import pg from 'pg'

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 5,
  connectionTimeoutMillis: 1000,   // 借不到、連不上：1 秒就失敗
  idleTimeoutMillis: 10000,
  statement_timeout: 2000,         // 每一句最多 2 秒，資料庫會取消它
})
pool.on('error', (err) => {
  console.error('閒置的資料庫連線出錯', err)
})

最後那三行處理另一種出事的方式：連線沒在用的時候壞掉。閒置在池子裡的連線也可能出錯，例如資料庫重開、網路斷掉、DBA 把連線砍掉。這時沒有任何查詢在等結果，錯誤沒有 Promise 可以 reject，pg 只好從 pool 的 error 事件丟出來。第 8 課講過：EventEmitter 發出 error 而沒有 listener 時，會變成未捕捉的例外，整個程序崩潰。資料庫重開一次，所有伺服器跟著倒，pg 的文件也提醒要加。加了 listener 之後只要記 log 就好，壞掉的連線 pg 會自己移除，下次查詢會開新的。

剩下 max 要設多少。直覺是越大越好，其實不是：資料庫能接受的連線數有上限（max_connections，預設 100），而且上限要算總數。4 個程序、每個 max: 10 就是 40 條，再加上部署時新舊版本同時在跑，很快就到頂。池子大也不等於快，資料庫的 CPU 核心就那幾個，同時跑的查詢多了只是互相搶。細節在 PostgreSQL 課第 36 課。

同樣的道理，整個程序共用一個 pool：在 db.ts 這個模組裡建一次，所有請求共用。每個請求 new Pool 等於沒有池子，連線每次都重開，連線數還會爆掉。

💡 實務上：API 全部逾時，先分清楚是池子空了還是查詢慢
咖啡店午餐尖峰，客服回報「點餐頁一直轉圈」，第一個要回答的問題是：請求卡在「借連線」還是卡在「跑 SQL」。pg 的 pool 有 totalCount、idleCount、waitingCount，把它們定期寫進 log 或監控，waitingCount 一直大於 0 就是池子不夠用或有連線沒還。這時直覺是把 max 調大，但資深工程師會先問：是不是有一句慢查詢佔著連線、是不是漏了 release？調大池子只會把壓力推給資料庫。改 max 或逾時前也要跟維運或 DBA 確認總連線數，因為他們看的是所有服務加起來的量。

連線的問題解決了，接下來要在這個池子上跑真正的查詢。第一個是點餐頁的菜單搜尋，它已經照第 25 課用了 $1 參數，看起來很安全，但還有三個地方會出錯。

products.ts：菜單搜尋用了參數，為什麼還會出錯？

點餐頁的搜尋框呼叫 searchProducts(pool, { q, sort, limit })：q 是客人打的字，sort 是前端選的排序，回傳這一頁的品項 items 和符合條件的總筆數 total。使用者輸入一律用 $1、$2 參數傳，不要接進 SQL 字串，這擋住了 SQL injection（PostgreSQL 課第 25 課）。但參數只保證「值不會被當成 SQL 指令」，它管不到三件事：值在 LIKE 裡的意思、不是值的東西、結果回到 JS 的型別。我們照搜尋的三個欄位一個一個看。

第一個是 q：值本身會被 LIKE 解讀。搜尋用 name ILIKE '%…%'，ILIKE 是不分大小寫的 LIKE。LIKE 有兩個萬用字元：% 代表任意長度的字、_ 代表任意一個字。參數擋住了 injection，但客人打的 % 還是萬用字元。客人搜尋「100%」，條件變成 name ILIKE '%100%%'，會找到所有含「100」的品項；搜尋「%」就是全部商品，等於繞過搜尋把整張表倒出來，資料多時也拖慢資料庫。

做法是在送出前，把 q 裡的 %、_ 和跳脫字元 \ 本身前面都加上 \，讓它們變回普通字元：

const escapeLike = (s: string) => s.replace(/[\\%_]/g, '\\$&')

await pool.query(
  `SELECT id, name, price FROM products WHERE name ILIKE $1 ESCAPE '\\' LIMIT $2`,
  [`%${escapeLike(q)}%`, limit])   // 前後的 % 是我們加的萬用字元，q 裡面的都被跳脫

ESCAPE '\' 指定跳脫字元（PostgreSQL 的預設就是 \，寫出來比較清楚）。\ 自己也要跳脫：不然客人輸入的結尾是 \ 時，它會把我們加在後面的 % 變成普通字元，搜尋結果就錯了。

第二個是 sort：參數只能放「值」。欄位名稱、ASC／DESC、資料表名稱都是 SQL 的結構，不能用 $1。前端傳 ?sort=price_desc，你沒辦法寫 ORDER BY $1；直接把字串接進 SQL，又回到 injection。做法是白名單：把允許的選項對照成寫死的 SQL 片段，不在名單裡就回 400：

const SORTS: Record<string, string> = {
  price_asc: 'price ASC, id ASC',
  price_desc: 'price DESC, id ASC',
  name: 'name ASC, id ASC',
}
if (!Object.hasOwn(SORTS, sort)) throw new ValidationError('sort 不在允許的清單裡', 'sort')
// ORDER BY ${SORTS[sort]}：接進 SQL 的只會是上面三個字串之一

檢查用 Object.hasOwn，而不是看 SORTS[sort] 有沒有值：sort=constructor 時，SORTS['constructor'] 會拿到原型鏈上的函式，看起來「有值」就通過了。每個片段最後都加 id，是為了價格相同時順序固定（第 14 課的穩定排序），不然翻頁時同價的品項可能重複或漏掉。

第三個是 total：結果回到 JS 的型別。總筆數用 SELECT count(*) 算。PostgreSQL 回給 pg 的是文字，pg 依欄位的型別把文字轉成 JS 值，這套規則叫型別解析（type parser，由 pg-types 2.2.0 負責）。執行 examples/types.ts，看每一列左邊的 JS 型別：

$ node --env-file=../../.env examples/types.ts
n    string "6"                      count(*) 是 bigint
sum  string "580"                    integer 的 sum 也是 bigint
avg  string "96.6666666666666667"    numeric
max  number 120                      integer
now  Date "2026-10-31T15:49:34.768Z" timestamptz

count(*) 拿到的是字串 "6"，原因在它的型別：

  • bigint 可以到 9.2×1018，超過 JS number 能精確表示的範圍（Number.MAX_SAFE_INTEGER，約 9×1015）。
  • numeric 是精確小數（PostgreSQL 課第 13 課），轉成 number 會失去精度（TypeScript 課第 5 課）。
  • pg 選擇不猜，這兩種一律給字串；integer 給 number，timestamptz 給 Date。

直接把 total: "6" 回給前端，前端的 total + 1 會變成 "61"。確定不會超過安全範圍時（菜單的筆數當然不會），用 Number() 轉，或在 SQL 寫 count(*)::int；金額用 numeric 時保留字串，交給專門的十進位函式庫處理。

到這裡都是一句一句的查詢，每一句自己成功或失敗。下單不一樣：它要連續寫好幾張表，而且必須一起成功或一起失敗。

orders.ts：下單要寫三張表，為什麼交易一定要用同一條連線？

下單要做三件事：扣庫存、建立 orders、建立 order_items。中間任何一步失敗，例如可頌沒貨了，前面已經扣掉的拿鐵庫存要還原，不然會少一杯不見的咖啡。所以這三件事要包在交易裡（PostgreSQL 課第 18 課）。

關鍵在於：交易屬於一條連線。BEGIN 是記在那條連線上的狀態，也就是資料庫那頭那個專屬程序記得「我現在在交易裡」。只有從同一條連線送來的句子，才在這個交易裡。

而 pool.query() 每次都會借一條連線、跑一句、還回去。同時有好幾個請求時，三次 pool.query 很可能借到三條不同的連線。examples/pids.ts 讓每一句回報它跑在哪條連線上：pg_backend_pid() 回傳資料庫為這條連線開的程序編號，編號不同就是不同的連線。它先同時送出三次 pool.query，再用 pool.connect() 借一條連線連續跑三次，執行後比較兩組的編號：

$ node --env-file=../../.env examples/pids.ts
COMMIT     跑在連線 10664
UPDATE     跑在連線 10665
BEGIN      跑在連線 10663
client：BEGIN 跑在連線 10663
client：UPDATE 跑在連線 10663
client：COMMIT 跑在連線 10663

前三行分散在三條連線。三句是同時送出的，連完成的順序都不保證，COMMIT 甚至比 BEGIN 先跑完。如果交易用 pool.query('BEGIN')、pool.query('UPDATE …')、pool.query('COMMIT') 來寫，會發生兩件事：

  • UPDATE 可能在另一條沒有交易的連線上直接生效，之後 ROLLBACK 也還原不了。
  • BEGIN 留在某條連線上沒結束，下一個借到它的請求莫名其妙就在交易裡。

麻煩的是，本機一個人測試時看不出來：只有一個請求，池子總是把剛還回來的那條連線再借出去。要到上線、請求一多才偶爾出事。pg 的文件明確說不要用 pool.query 做交易。

後三行是正確做法：用 pool.connect() 借一條連線，拿到的物件叫 client，整個交易的每一句都用 client.query，最後一定還回去。每個需要交易的地方都要寫一樣的借、BEGIN、COMMIT／ROLLBACK、還，所以把它寫成一個輔助函式 withTransaction，呼叫的人只要寫交易裡要做的事 fn：

export async function withTransaction<T>(pool: pg.Pool, fn: (client: pg.PoolClient) => Promise<T>) {
  const client = await pool.connect()
  let broken: Error | undefined
  try {
    await client.query('BEGIN')
    const result = await fn(client)
    await client.query('COMMIT')
    return result
  } catch (err) {
    try {
      await client.query('ROLLBACK')
    } catch (rollbackErr) {
      broken = rollbackErr as Error     // 連 ROLLBACK 都失敗，這條連線狀態不明
    }
    throw err
  } finally {
    client.release(broken)              // 傳入錯誤：丟掉這條連線，不還回池子
  }
}

由上往下讀：

  1. pool.connect() 借一條連線，之後全部用這個 client。
  2. BEGIN、執行 fn(client)、COMMIT，成功就回傳 fn 的結果。
  3. 任何一步丟錯，進 catch 先 ROLLBACK，再把原本的錯誤丟出去，呼叫的人才知道為什麼失敗。
  4. 如果連 ROLLBACK 都失敗（例如連線已經斷了），這條連線處在什麼狀態沒人知道，記在 broken。
  5. finally 不論成功失敗都會執行，在這裡歸還連線。

為什麼歸還一定要放在 finally？因為忘了 release 的連線永遠不會回到池子。如果只在成功的路徑 release，每次出錯就漏一條，max: 5 的池子 5 次之後就空了，之後所有請求都借不到連線，正好回到上一節的「整台伺服器像當機」。有設 connectionTimeoutMillis 還會報錯，沒設就是全部卡住。

release() 不傳參數是「還回池子」；傳 true 或一個錯誤（任何 truthy 值）是「把連線關掉、不還回去」，池子之後會開新的。用在不確定這條連線還正不正常的時候，例如 broken 有值：把狀態不明的連線還回去，下一個借到它的請求就要倒楣。

💡 實務上：交易裡只放資料庫的事，越短越好
下單、退款、轉點數這類「好幾張表要一起成功或一起失敗」的操作才需要交易，單純查詢或只寫一句 SQL 不用包。新手常犯的錯是在交易中間呼叫外部服務，例如扣完庫存後在同一個交易裡呼叫金流 API 或寄確認信：扣庫存的 UPDATE 會鎖住那一列、直到 COMMIT 才放開，對方慢 5 秒，這條連線和那一列的鎖就被佔 5 秒，其他人點同一杯拿鐵全部排隊。常見做法是交易只做資料庫的寫入，COMMIT 之後再寄信、通知；金流則先建立「待付款」的訂單，付款結果回來再用另一個交易更新狀態。Code review 時看到 withTransaction 裡有 fetch 或 await 外部服務，就值得問一句。

有了 withTransaction，三件事一起成功或一起失敗。但「包在交易裡」不代表兩位客人同時下單時就安全，扣庫存那一步還有一個交易擋不住的問題。

兩位客人搶最後一杯拿鐵：庫存怎麼不變成 -1？

扣庫存最直覺的寫法是先查再寫：查出現在的庫存，夠就算好新的值寫回去：

const { rows } = await client.query('SELECT stock FROM products WHERE id = $1', [id])
if (rows[0].stock < qty) throw new OutOfStockError(id)
await client.query('UPDATE products SET stock = $1 WHERE id = $2', [rows[0].stock - qty, id])   // ✗

就算包在 withTransaction 裡也會超賣。拿鐵只剩 1 杯，兩位客人同時下單：

  1. 兩個交易同時 SELECT，都看到庫存 1。
  2. 兩邊都通過 stock < qty 的檢查。
  3. 兩邊都寫入算好的 0，賣出兩杯，其實只有一杯。

這是 PostgreSQL 課第 19 課的「遺失更新」。PostgreSQL 預設的隔離等級 READ COMMITTED 不會擋這種情況：SELECT 不上鎖，兩個交易讀到同一個舊值是允許的。問題的根源是「檢查」和「寫入」分成兩句，中間有空檔讓別人插進來。

所以正確的做法是讓檢查和扣除在同一句完成：

const res = await client.query(
  'UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1 RETURNING price',
  [qty, id])
if (res.rowCount === 0) throw new OutOfStockError(id)   // 庫存不夠：一列都沒改到

這句怎麼擋住第二位客人：UPDATE 會鎖住它改到的那一列，直到交易結束。第二個交易的 UPDATE 碰到同一列時會等第一個交易結束，再用最新的 stock 重新判斷 stock >= $1。這時庫存已經是 0，條件不成立，一列都沒改到，rowCount 是 0，程式丟出 OutOfStockError。withTransaction 接到錯誤就 ROLLBACK，這筆訂單前面已經扣掉的其他品項也跟著還原。RETURNING price 順便取回當下的價格，建立 order_items 時要用。

資料表上再加 CHECK (stock >= 0) 是最後一道防線：哪天有人寫錯程式，資料庫寧可報錯，也不讓庫存變成負的、賣出不存在的咖啡。

單一品項安全了。但一張訂單常常不只一個品項，每扣一個品項就鎖住一列，鎖一多，兩筆訂單就可能互相卡住。

一張訂單好幾個品項：死結怎麼避免、怎麼重試？

訂單 A 是「拿鐵＋可頌」，訂單 B 是「可頌＋拿鐵」，同時送出。A 先扣拿鐵、鎖住拿鐵那一列；B 先扣可頌、鎖住可頌那一列。接著 A 要扣可頌，等 B 放開；B 要扣拿鐵，等 A 放開。兩邊都在等對方，而對方要等自己的交易結束才會放開，永遠等不到。這就是死結（deadlock）。PostgreSQL 偵測到之後會讓其中一個交易失敗，錯誤碼 40P01，另一個就能繼續。

對策有兩個，要一起用。

第一個是固定上鎖順序，讓死結不容易發生。死結的條件是「互相等」繞成一圈。扣庫存前把品項依 productId 由小到大排序，所有交易都從小的 id 開始鎖：A 和 B 都先扣 id 小的那一個，先搶到的人做完，後到的人只是排在後面等，不會繞成一圈。排序要複製一份再排，Array.prototype.sort 會改到原陣列，而呼叫的人傳進來的 items 不該被你改掉。

第二個是可重試的錯誤，整個交易重來。固定順序只管得到照這個規則寫的程式；別的功能用不同順序鎖到同一批列時，死結還是可能發生。死結 40P01 和序列化失敗 40001（用 SERIALIZABLE 隔離等級時，PostgreSQL 課第 31 課）的意思都是「時機不巧」，資料本身沒有問題，重來一次可能就成功。重來時要注意三件事：

  • 重來的是整個交易：重新借連線、重新 BEGIN、從第一個品項開始扣。不能只重跑失敗的那一句，因為失敗時整個交易已經被取消了，前面扣的也都沒了。
  • 次數要有上限，不然一直撞上就一直重來。
  • 其他錯誤不重試：庫存不足、違反約束，重來幾次結果都一樣，直接丟出去。
const RETRYABLE = new Set(['40P01', '40001'])
const sorted = [...items].sort((a, b) => a.productId - b.productId)   // 複製一份再排

for (let attempt = 1; ; attempt++) {
  try {
    return await withTransaction(pool, client => insertOrder(client, customerId, sorted))
  } catch (err) {
    const code = (err as { code?: string }).code
    if (!code || !RETRYABLE.has(code) || attempt >= 3) throw err
  }
}

insertOrder 就是上一節的內容：照 sorted 的順序逐一用原子 UPDATE 扣庫存，再建立 orders 和 order_items。迴圈每一輪都呼叫一次 withTransaction，所以每次重試都是全新的交易。第 17 課重試外部 API 時加了退避（backoff）；資料庫的死結通常重來一次就好，量大時也可以加一點隨機延遲，讓兩個交易錯開。

這段程式用 err.code 判斷要不要重試。code 是資料庫錯誤帶的代號，下單的錯誤靠它分辨「重來」或「放棄」；下一個檔案 customers.ts 要靠同一個欄位，決定回給前端的是哪一種錯誤。

customers.ts：手機號碼重複註冊，怎麼回 409 而不是 500？

會員註冊時，手機號碼不能重複。最直覺的寫法和扣庫存一樣是先查再寫：先 SELECT 看這支手機有沒有註冊過，沒有才 INSERT。它有同樣的空檔：兩個請求同時查都說沒有，然後都 INSERT，資料庫裡就有兩個同手機的會員。

可靠的做法是交給資料庫的 UNIQUE 約束擋（PostgreSQL 課第 12 課）：customers 表上有 customers_phone_key 這個約束，第二個 INSERT 一定會失敗，不管同時來幾個請求。問題變成：失敗時 pg 丟出來的是一個資料庫錯誤，如果沒有處理，它一路往上丟，第 18 課的錯誤處理不認得它，只能回 500。前端分不出是「手機重複，請換一支」還是「伺服器壞了」。

所以要先認得這個錯誤。資料庫回的錯誤，pg 會變成 DatabaseError（可以 import { DatabaseError } from 'pg'），有三個欄位用得到：

  • code：SQLSTATE，五碼的錯誤代號。SQL 標準定義了一套，PostgreSQL 再補充自己的（例如 40P01 的 P 就是 PostgreSQL 加的）；前兩碼是分類，例如 23 開頭都是違反約束。
  • constraint：違反的約束名稱，看它才知道是哪個欄位重複。
  • detail：補充說明，可能含資料，不要直接回給客戶端。

第 18 課把錯誤分成描述業務上發生了什麼的領域錯誤，例如 ConflictError、ValidationError，錯誤處理再依類別決定狀態碼。知道 code，就能把資料庫錯誤翻成領域錯誤，再由錯誤處理轉成正確的 HTTP 狀態碼。常見的對照：

code意思領域錯誤HTTP
23505違反 UNIQUE（看 constraint 知道是哪個欄位）ConflictError409
23503違反外鍵：參照的資料不存在ValidationError400

手機重複就是第一列：23505，而且 constraint 是 customers_phone_key，翻成 ConflictError，回 409（第 14 課的「跟資源目前的狀態衝突」）。這張表也把前面幾節串起來：statement_timeout 取消的查詢是 57014，資料庫連不上是 ECONNREFUSED，它們都是「稍後再試」的 503，不是程式的 bug。

翻譯放在存取資料庫的那一層，也就是 customers.ts 這種檔案。路由只看到 ConflictError 這類領域錯誤，再由第 18 課的錯誤處理轉成 problem details；路由不需要知道 23505 是什麼。翻譯時把原本的錯誤放進 cause，log 才查得到真正的原因。

有一個例外要知道：pg-pool 3.14.0 借不到連線的逾時錯誤（timeout exceeded when trying to connect，第二節 exhaust.ts 看到的那個）只有訊息、沒有 code，照上表會落到「其他」回 500。要讓它也回 503，就在借連線的那一步（pool.connect()）單獨包 try/catch，不要去比對訊息。

判斷一定看 err.code，不要看 err.message。訊息會隨資料庫的語系（lc_messages）和版本改變：同樣的 23505，英文是 duplicate key value violates unique constraint，中文語系就變成中文，message.includes('duplicate') 在換一台資料庫後就默默失效。SQLSTATE 是標準，不會變。
💡 實務上：約束名稱就是前後端的錯誤契約
會員註冊時手機號碼重複，前端想顯示「這支手機已經註冊過」，而不是「伺服器錯誤」。做法是讓約束有固定、看得懂的名字（PostgreSQL 預設會取 customers_phone_key 這種「表_欄位_key」的名字，也可以在建表或改表結構的 migration 裡自己命名），存取層依 constraint 決定回哪個欄位的 409，前端再依欄位顯示訊息。所以改約束名稱其實是會影響 API 行為的變更，review migration 時要一起看翻譯的程式。和前端或 PM 對規格時，資深工程師會先列出「哪些錯誤使用者自己能修正（400、409）、哪些只能稍後再試（503）」，前端才知道每種情況該顯示什麼。

四個檔案都寫完了。最後還有兩件跟「池子本身」有關的事：程式要結束時怎麼收掉它，以及測試怎麼在同一個資料庫伺服器上互不干擾。

收尾：程序怎麼結束，測試怎麼互不干擾？

池子裡的閒置連線會讓 event loop 一直有事做（第 7 課），所以一次性的腳本跑完了，程序卻不會結束。程序結束前要 await pool.end()，關掉所有連線。pool.end() 會等借出去的連線都還回來才完成，所以漏了 release 的程式連關機都會卡住，這是「release 放 finally」的另一個理由。伺服器收到 SIGTERM 時要按什麼順序關，在下一課。

另一個做法是建立池子時設 allowExitOnIdle: true：連線都閒置時允許程序結束，適合一次性的腳本和測試。伺服器本來就要一直跑，不需要它。

測試要彼此隔離：一個測試改了庫存，不能影響另一個測試的結果，重跑也要得到一樣的結果。這課的測試每個檔案建立一個隨機名稱的資料庫，跑完 DROP DATABASE … WITH (FORCE)，所以互不影響、可以重複執行，你在 psql 裡改了什麼也不會干擾判分。也有人用「每個測試檔一個 schema」或「每個測試包在交易裡最後 ROLLBACK」，第 22 課會比較。

這一課的觀念不只適用於直接寫 SQL：換成 ORM，連線池、逾時、交易、原子更新、SQLSTATE 一樣都在，細節見課末。

練習

練習在 learn/node/practice/work/20。先確定 docker compose ps 顯示 healthy；測試會自己建立資料庫，不需要 .env。錯誤類別都在 errors.ts，不用改。

練習 1：完成 db.ts。createPool(url) 回傳設定好的 Pool：max 5、connectionTimeoutMillis 1000、idleTimeoutMillis 10000、statement_timeout 2000，並加上 pool.on('error', …) 用 console.error 記下閒置連線的錯誤。health(pool) 執行 SELECT 1，失敗時丟 DatabaseUnavailableError，cause 是原本的錯誤。測試會跑 SELECT pg_sleep(3)（要在 2 秒左右被取消）、借出 5 條連線不還再借第 6 條（要在 1 秒左右失敗）、用錯的密碼呼叫 health、用 pg_terminate_backend 切斷一條閒置連線（程序不能崩潰）。

練習 2：完成 products.ts 的 searchProducts(pool, { q, sort, limit })。品名包含 q 就符合（不分大小寫），q 裡的 %、_、\ 都當一般字元；sort 只接受 price_asc、price_desc、name（預設 name），其他丟 ValidationError（field 'sort'）；limit 是 1 到 50 的整數（預設 20），其他丟 ValidationError（field 'limit'）。回傳 { items, total }：total 是符合條件的總筆數（不受 limit 影響），型別是 number。現在的起始程式把 q 和 sort 直接接進 SQL。

練習 3：完成 orders.ts。先改 withTransaction：用 pool.connect() 借一條連線，BEGIN、fn(client)、COMMIT，出錯時 ROLLBACK 再丟出去，finally 一定歸還。再改 placeOrder(pool, customerId, items)：依 productId 由小到大，用一句原子 UPDATE 扣庫存，改不到就丟 OutOfStockError(productId)；建立 orders（ordered_at 用 now()）與 order_items（unit_price 是當下的價格）；遇到 40P01 或 40001 整個交易重來，最多一共 3 次，其他錯誤不重試；回傳 { orderId, total }。排序要複製一份，不能改到傳進來的 items。測試會檢查扣庫存的順序、讓 10 筆訂單同時搶 3 杯、讓第二個品項庫存不足（之後同一條連線再下一筆）、送出順序相反的並發訂單、模擬死結，並在每個測試結束時檢查連線都已歸還。

練習 4：完成 customers.ts 的 createCustomer(pool, { name, phone }) 的錯誤處理（資料表有 customers_phone_key 這個 UNIQUE 約束和 customers_name_check 這個 CHECK）：手機重複（23505，而且 constraint 是 customers_phone_key）→ ConflictError，field 'phone'；違反 CHECK（23514）→ ValidationError，field 'name'；連不上資料庫（ECONNREFUSED 等）或查詢逾時（57014）→ DatabaseUnavailableError；其他錯誤原樣丟出。轉換時都把原本的錯誤放進 cause。只能看 code 和 constraint：測試也會丟出訊息是中文的錯誤。

練習 5：Pool 用預設設定（沒設 connectionTimeoutMillis）。資料庫有個慢查詢，10 條連線全被借走、都在等。這時第 11 個請求呼叫 pool.query()，會怎樣？

✓ connectionTimeoutMillis 預設是 0，意思是不設計時器：請求進入等候佇列，有連線還回來才輪到它。慢查詢不結束，它就一直等，不會報錯也不會寫 log。pg 不會超過 max 開連線，也沒有預設的逾時或「池子滿了」的錯誤。所以要設 connectionTimeoutMillis，讓它快速失敗、回 503。

練習 6：const { rows } = await pool.query('SELECT count(*) AS n FROM orders')，rows[0].n 是什麼？

✓ count(*) 的型別是 bigint（int8），可能超過 JS number 能精確表示的整數範圍，所以 pg 一律回傳字串，不會依數值大小改變型別，也不會自動轉成 JS 的 bigint。需要數字時自己 Number() 或在 SQL 寫 count(*)::int，不然 n + 1 會變成 "81"。

練習 7：同事這樣寫交易：await pool.query('BEGIN')、await pool.query('UPDATE …')、await pool.query('COMMIT')。本機一個人測試都正常，上線後偶爾 ROLLBACK 還原不了。原因是什麼？

✓ 交易屬於一條連線。本機只有一個請求時，池子總是把剛還回來的那條連線再借出去，所以看起來正常；上線後請求一多，三句就分散到不同連線，UPDATE 在沒有交易的連線上直接生效。pg 支援交易，只是要用 pool.connect() 借到的同一個 client；程式有 await；隔離等級處理的是交易之間怎麼互相看見，和「句子不在交易裡」無關。

常見錯誤

  • 沒設 connectionTimeoutMillis、statement_timeout：資料庫一慢，所有請求排隊無限等，伺服器看起來當機卻沒有任何錯誤。兩個都設，讓請求快速失敗、回 503。
  • 沒有 pool.on('error')：資料庫重開或網路斷掉時，閒置連線的錯誤沒人接，整個程序崩潰。加上 listener 記 log 就好，pg 會自己換掉壞連線。
  • 交易用 pool.query：每句可能在不同連線，ROLLBACK 無效。用 pool.connect() 借一個 client，整個交易都用它。
  • 忘了 release：特別是出錯的路徑。每漏一次池子少一條，最後所有請求都借不到。release 放在 finally，狀態不明的連線用 release(err) 丟掉。
  • 先 SELECT 再 UPDATE 成算好的值：並發時會超賣。用 SET stock = stock - $1 WHERE … AND stock >= $1，看 rowCount。
  • 重試只重跑失敗的那一句：死結或序列化失敗時整個交易已經取消，要從 BEGIN 重來；只重試 40P01、40001，次數有上限。
  • 把 count(*) 當成數字：bigint 和 numeric 回傳字串。用 Number() 或 ::int 轉。
  • ORDER BY 直接用使用者輸入：欄位名稱不能參數化，接進 SQL 就是 injection。用白名單對照成寫死的片段。
  • LIKE 沒跳脫：搜尋「%」就把整張表倒出來。%、_、\ 都要跳脫，並寫 ESCAPE '\'。
  • 比對錯誤訊息文字：換語系、換版本就失效。看 err.code（SQLSTATE）和 err.constraint。
  • 每個請求都 new Pool：等於沒有池子，連線數很快爆掉。整個程序共用一個，關機時 pool.end()。

小結

  • 練習用的 PostgreSQL 用 Docker Compose 啟動；連線字串放在 DATABASE_URL，不進版本控制。
  • db.ts：建立連線很貴，所以用 pg.Pool 借還。connectionTimeoutMillis 預設 0（永遠等），一定要設，讓借不到連線的請求快速失敗；statement_timeout 限制每一句，因為 pg 的查詢不能用 AbortSignal 取消；pool.on('error') 防止閒置連線讓程序崩潰；整個程序共用一個 pool，max × 程序數不能超過資料庫上限。
  • products.ts：參數只管「值不會變成 SQL」。LIKE 要跳脫 %、_、\；欄位名稱和排序方向用白名單；bigint、numeric 回傳字串，timestamptz 回傳 Date。
  • orders.ts：交易屬於一條連線，用 pool.connect() 借到的同一個 client：BEGIN → 執行 → COMMIT，出錯 ROLLBACK，finally 歸還，狀態不明的連線 release(err) 丟掉。
  • 扣庫存用原子 UPDATE 加條件、看 rowCount，先查再寫就算在交易裡也會超賣；多品項依 id 排序上鎖；40P01、40001 整個交易重試，次數有上限。
  • customers.ts：重複交給 UNIQUE 約束擋，再依 SQLSTATE（和 constraint）把資料庫錯誤翻成領域錯誤：23505 → 409、23503／23514 → 400、連不上或逾時 → 503，其他原樣丟出，cause 保留原始錯誤；只看 code，不看訊息。
  • 程序結束前 await pool.end()；測試各用一個資料庫，互不影響。
