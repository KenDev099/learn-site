階段 6：資深工程師的功課 · 第 25 課

Node 安全

咖啡店的菜單圖片放在 /images/latte.jpg 這種網址。某天有人送了 /images/..%2F..%2F.env，伺服器把資料庫密碼當成圖片送了出去。程式沒有當掉、log 也只有一行 200，直到帳單異常才發現。安全問題通常就是這樣：功能都正常，只是有人用了你沒想到的輸入。

修掉這一支 API 不算處理完。事故檢討要回答三個問題：這個輸入是怎麼走到危險的地方的？服務裡還有沒有同樣形狀的洞？萬一還有一個沒找到，損害能不能限制在很小的範圍？這一課就用這三個問題，從攻擊者的角度把咖啡店的 Node 服務完整檢查一遍，最後處理已經外洩的密碼。

這課的路線：
  1. 密碼是怎麼流出去的：用攻擊者的角度列出所有輸入和危險的去處，找出每一條需要檢查的線。
  2. /images/..%2F..%2F.env 為什麼讀得到密碼、怎麼擋：URL 編碼、原樣的 req.url、符號連結，以及「把路徑算到底再檢查」的寫法。
  3. 同樣形狀的洞還有哪些：body 流到物件合併、檔名流到 shell、值流到回應標頭，以及一個優惠碼怎麼卡死整台伺服器。
  4. 不讓一個人用光資源：每種資源的上限，以及限流需要的客戶端 IP 在反向代理後面要從哪裡拿。
  5. 萬一還有漏網的：用 Permission Model 限制程式能碰的檔案，再處理外洩的密碼和依賴。
這課會用到：
  • 第 10 課的路徑與 fs：path.join 把片段接起來並算掉 ..，path.resolve 一定產生絕對路徑；相對路徑是相對於工作目錄，不是程式檔的位置。
  • 第 9 課的阻塞與子程序：同步的工作會卡住整條 event loop；exec 經過 shell，execFile 直接執行、參數不會被 shell 解讀。
  • TypeScript 課第 5 課的正規表示式：用 /^…$/ 檢查整個字串的格式，*、+ 是重複。

密碼是怎麼流出去的？用攻擊者的角度看服務

先回到事故本身。圖片 API 的寫法是「把網址最後一段接在 public/images 後面，讀出那個檔案送回去」。寫的人心裡想的是 latte.jpg 這種值，因為前端只會送這種值。但網址最後一段是誰決定的？是送請求的人。攻擊者不用你的前端，他用 curl 直接送任何位元組，你的前端做了什麼驗證，對他來說不存在。

所以後端要換一個前提：任何從外面來的資料都可能是攻擊者寫的。這種還沒驗證過的資料，叫做不可信輸入（untrusted input）。它不只是 body，網址、查詢字串、標頭、上傳的檔名都算；上游 API 的回應、環境變數、設定檔也算，因為上游可能被入侵、設定可能被別人改過。外界能影響你的系統的這些入口，合起來叫做攻擊面（attack surface）。攻擊面越大，要守的地方越多。

光有輸入不會出事。圖片 API 出事，是因為網址那一段最後被拿去當檔案路徑：路徑這種東西有自己的語法，.. 的意思是「上一層」。輸入一旦被當成某種語法解讀，攻擊者就能用語法改變程式的行為。同樣的事會發生在每一個「會解讀字串」的地方：shell 解讀 ;，SQL 解讀引號，正規表示式引擎會依輸入決定要試多少種走法。這些地方就是危險的去處。

把兩邊列出來，畫線連起來，就是一份最簡單的威脅模型（threat model）：系統可能怎麼被攻擊的整理。每一條從不可信輸入連到危險去處的線，中間都要有一道檢查。這次的事故就是「網址 → 檔案路徑」這條線上沒有檢查。

右邊每一個去處都有對應的攻擊和防法。有幾條在別的課已經學過，這一課處理標「本課」的那幾條，也就是 Node 服務本身最常出事的地方。下表是全課的地圖，現在先掃過，讀到各節時再回來對照：

💡 實務上：新增端點時先問「這個值是誰給的」
威脅模型不用開會畫大圖，最常用在設計和 code review：咖啡店新增「上傳商品照片」或「匯出訂單 CSV」時，列出這支 API 收哪些輸入、最後流到檔案、SQL 還是 shell。審 PR 時資深工程師常問的就是「這個值是誰給的？流到哪裡之前驗證過？」。只給員工用的後台也不例外：帳號被盜或有人誤用時，它一樣是入口。不需要每支 API 都寫文件，碰到檔案、shell、金額、權限的那幾支多看一眼就夠了。這次的圖片 API 如果在 review 時被問過這一句，事故就不會發生。

地圖有了，先處理出事的那條線：圖片網址到底經過什麼，才變成 .env 的路徑？

/images/..%2F..%2F.env 為什麼讀得到密碼？

這種攻擊叫路徑穿越（path traversal）：用 ../ 之類的寫法，讓伺服器讀到它本來不該讀的檔案。咖啡店的圖片伺服器把網址最後一段接在 public/images 後面：

const ROOT = join(import.meta.dirname, 'public', 'images')
const file = join(ROOT, decodeURIComponent(name))   // name 是 /images/ 後面那一段
createReadStream(file).pipe(res)

你可能會想：瀏覽器和 URL 不是會把 ../ 處理掉嗎？會，但只處理一部分，原因在 URL 編碼。

第 13 課看過 URL 編碼（percent-encoding）：網址裡的字元可以寫成 % 加兩位十六進位，. 是 %2e，/ 是 %2F。瀏覽器和 Node 的 URL 都照 WHATWG URL 標準解析網址，這個標準會把 .. 和 %2e%2e 都當成「上一層」算掉；但 %2F 不被當成分隔符號，它只是「網址裡的一個普通字元」，原封不動留在同一段裡。問題出在下一步：你的程式呼叫 decodeURIComponent，%2F 才變回真的 /，這時候 ../ 才出現，而 URL 的正規化早就做完了。

實際跑一次看看。在 learn/ 執行 node check.mjs node 25 建立 work/25/，再到 work/25 執行 node examples/traversal.ts。看每個輸入經過「URL 解析 → 解碼 → 接路徑」後變成什麼（v24.22.1 實測，節錄）：

輸入 ..%2F..%2F..%2Fetc%2Fpasswd
  new URL().pathname  /images/..%2F..%2F..%2Fetc%2Fpasswd
  解碼後              ../../../etc/passwd
  path.join           /etc/passwd
輸入 %2Fetc%2Fpasswd
  解碼後              /etc/passwd
  path.join           /srv/menu/images/etc/passwd
  path.resolve        /etc/passwd

第一個輸入：URL 完全沒動它，解碼後出現三個 ../，path.join 照規則往上走三層，跑到了 /etc/passwd。事故裡的 ..%2F..%2F.env 就是這樣走到專案根目錄的 .env。第二個輸入解碼後是絕對路徑，join 和 resolve 處理的方式不一樣，下一節會用到這個差異。

就算不編碼也擋不住。Node 的 req.url 是客戶端送來的原樣字串，Node 不會替你做 URL 正規化。瀏覽器送請求前會先把 ../ 算掉，但攻擊者不用瀏覽器：用 curl 加 --path-as-is，或用 node:net 直接寫請求列，連沒編碼的 /images/../../.env 都送得進來。所以「URL 會擋掉 ..」不能當防線。

到這裡原因清楚了：從網址到檔案路徑，中間的每一步（瀏覽器、URL、解碼）都不是為了安全設計的，各自只處理一部分寫法。那防線該放在哪裡？

怎麼擋？把路徑算到底，再檢查它在不在裡面

直覺的做法是在字串裡找 .. 並拒絕。這條路走不通：.. 可以編碼成 %2e%2e，/ 可以是 %2F，還有雙重編碼、反斜線，寫法太多，總有一種漏網。換個角度：不管攻擊者怎麼寫，最後真正被打開的只有一個檔案。讓 Node 把路徑算到底，算出那個最終的絕對路徑，再檢查它在不在圖片資料夾裡面。檢查最終結果，就不用猜攻擊者會用哪種寫法。

import { realpath } from 'node:fs/promises'
import { extname, join, resolve, sep } from 'node:path'

const ROOT = await realpath(join(import.meta.dirname, 'public', 'images'))

async function resolveImage(name: string): Promise<string | null> {
  let rel: string
  try { rel = decodeURIComponent(name) } catch { return null }   // %E0 這種壞掉的編碼會丟 URIError
  if (rel.includes('\0')) return null                            // NUL 字元
  if (!Object.hasOwn(TYPES, extname(rel).toLowerCase())) return null   // 白名單副檔名
  const file = resolve(ROOT, rel)                                // ① 算出絕對路徑
  if (!file.startsWith(ROOT + sep)) return null                  // ② 加上分隔符號再比
  const real = await realpath(file)                              // ③ 符號連結換成真正的位置（不存在會丟錯）
  if (!real.startsWith(ROOT + sep)) return null                  //    再比一次
  return real
}

先看主線的三步，它們是檢查的核心：

  • ① 用 resolve 算出絕對路徑：path.resolve(ROOT, rel) 把 .. 算掉，遇到絕對路徑（/etc/passwd）就直接用它，結果一定是絕對路徑，才能拿來比較。為什麼不用 join？join 只負責把片段接起來再整理，不保證結果是絕對路徑：ROOT 一旦是相對路徑，結果也是相對路徑，拿來跟絕對路徑比對就會出錯。它也會把絕對路徑的輸入硬接在後面，得到一個跟攻擊者原意無關的路徑。resolve 照作業系統解讀路徑的方式，算出「這個輸入實際指到哪裡」，檢查的對象就是真正會被打開的位置；攻擊者給 /etc/passwd，算出來就是 /etc/passwd，下一步一比就被擋下。
  • ② 比較時加上 sep：sep 是這個作業系統的路徑分隔符號（macOS、Linux 是 /）。只寫 startsWith(ROOT) 的話，/srv/menu/images-private/recipe.jpg 也以 /srv/menu/images 開頭，會被當成在裡面。加上 sep 之後，比的是「/srv/menu/images/ 開頭」，隔壁的資料夾就進不來。
  • ③ 用 realpath 處理符號連結，再比一次：到 ② 為止都只是在算字串，但檔案系統裡還有一種東西會讓字串和真實位置不一樣。

這種東西叫符號連結（symlink）：一個特殊的檔案，內容是「請去讀另一個路徑」，用 ln -s 目標 連結名稱 建立。假設 public/images/evil.jpg 是指向 /etc/passwd 的符號連結：路徑字串 /srv/menu/images/evil.jpg 完全在根目錄裡，② 會放行，但打開它讀到的是外面的檔案。資料夾也可以是符號連結：public/images/linked 指向 /etc 時，linked/passwd.jpg 這個檔案本身不是連結，只檢查最後的檔案是不是連結（fs.lstat 回傳的 isSymbolicLink()）會漏掉。fs.realpath 會把路徑上每一段的符號連結都換成真正的位置，換完再檢查一次，才是真正要打開的檔案。

誰能在你的圖片資料夾裡放符號連結？上傳功能、解壓縮使用者給的壓縮檔、部署時的設定錯誤都可能。用了 realpath 還有一個連帶的坑：根目錄本身也要先 realpath。macOS 的 /var 其實是指向 /private/var 的符號連結，暫存資料夾都在那底下。ROOT 沒有先 realpath，③ 的結果是 /private/var/…，跟 /var/… 永遠比不上，正常的圖片也全部 404。所以程式一開始的 ROOT 就是用 realpath 算出來的。

主線之前的三行是額外的保險，讓壞輸入在進入主線前就被擋下，伺服器也不會因為它們掛掉：

  • 壞掉的編碼：%E0 這種不完整的百分比編碼會讓 decodeURIComponent 丟 URIError。不接住就是 500，接住了回 404。
  • NUL 字元：%00 解碼後是 NUL 字元，Node 的 fs 會直接丟 ERR_INVALID_ARG_VALUE，沒接住就是 500 或伺服器掛掉。先檢查、先拒絕。
  • 白名單副檔名：只允許 .jpg、.png、.webp。這是第二道防線：就算哪天主線的檢查有漏洞，.env、.json、原始碼也送不出去。用 Object.hasOwn 查表，不會被 constructor 這類從原型繼承來的鍵騙過（下一節的原型污染會看到 __proto__、constructor 這類鍵怎麼通到所有物件共用的原型）。

還有一個平台差異：Windows 上 \ 也是分隔符號，要在 Windows 執行的程式直接拒絕含 \ 的檔名。

💡 實務上：最安全的做法是不讓使用者給路徑
正式環境的公開靜態檔案多半交給 Nginx 或 CDN（在各地機器上快取並送出檔案的服務），見部署課第 12 課，它們處理這些情況很多年了。需要自己用 Node 送的，通常是「下載自己的發票 PDF」「看訂單附件」這類要先檢查權限的檔案。這時資料庫存檔案的 id，id 對應到你自己產生的檔名（例如 UUID），使用者給的字串從來不碰檔案系統。上傳也一樣：不要用使用者的原始檔名存檔，原始檔名只存在資料庫裡拿來顯示。真的非讓使用者給路徑不可，才用上面那套 resolve 加 realpath 的檢查，並寫測試把 ..%2F、符號連結這些輸入都跑過。

圖片 API 補好了。但事故檢討的第二個問題還沒回答：同樣形狀的洞，服務裡還有沒有？

同樣形狀的洞還有哪些？輸入被當成結構的時候

回頭看路徑穿越的本質：使用者給的是資料（一個檔名），程式卻讓它被當成結構（路徑語法裡的「上一層」）解讀。照威脅模型的圖往右看，咖啡店服務裡還有三條線有同樣的形狀：body 流到物件合併、檔名流到 shell、使用者的值流到回應標頭。三個都在前面的課出現過，這裡看它們在 Node 服務裡從哪裡進來。

body 流到物件合併：原型污染

咖啡店有一支 PATCH /settings，把使用者送來的 JSON 合併進目前的設定。TypeScript 課第 3 課學過：JavaScript 的每個一般物件都有一個原型，找不到的屬性會去原型上找，而所有 {} 共用同一個原型 Object.prototype。在一般物件上，__proto__ 這個鍵不是普通的屬性，讀它會拿到原型本身。

先看 JSON.parse 會不會出事。JSON.parse('{"__proto__":{"isAdmin":true}}') 把每個鍵當成資料，只會產生一個名叫 __proto__ 的自有屬性，本身無害。危險的是之後那一步：天真的遞迴合併逐鍵執行 target[key]，當 key 是 '__proto__' 時，target['__proto__'] 讀到的是 Object.prototype，再把 isAdmin 寫進去。先看天真的合併長什麼樣：

function naiveMerge(target, src) {
  for (const key in src) {
    if (typeof src[key] === 'object' && src[key] !== null) {
      target[key] ??= {}                 // key 是 '__proto__' 時，target[key] 就是 Object.prototype
      naiveMerge(target[key], src[key])  // 於是往 Object.prototype 裡寫
    } else {
      target[key] = src[key]
    }
  }
}

for...in 會走到 JSON.parse 產生的那個自有鍵 '__proto__'。這時 target['__proto__'] 經過存取器讀到 Object.prototype，它已經是物件，??= 不會換掉它，遞迴下一層就是 Object.prototype.isAdmin = true。v24.22.1 實測：

const body = JSON.parse('{"__proto__":{"isAdmin":true}}')
Object.hasOwn(body, '__proto__')   // true：只是一個普通的鍵
({}).isAdmin                        // undefined：還沒污染
naiveMerge({}, body)
({}).isAdmin                        // true：全程式的每個物件都「是管理員」了

這叫原型污染（prototype pollution）：透過 __proto__、constructor.prototype 這些鍵，改到所有物件共用的原型。後果不只是一個請求：同一個程序裡之後每個請求的每個物件都被影響，例如權限檢查寫成 if (user.isAdmin)，沒設這個欄位的使用者也會通過。在 Node 服務裡，入口都是「把 request body 或查詢字串解析成物件，再合併進設定或資料」：PATCH /settings、合併預設選項、把查詢字串 a[b][c]=1 解析成巢狀物件的函式庫。

constructor 也一樣：任何一般物件的 constructor 是 Object，Object.prototype 又是所有物件共用的原型，所以 {"constructor":{"prototype":{"isAdmin":true}}} 經過同一個天真的合併，一樣寫進 Object.prototype。

防法有三層：先用 schema 驗證，只取你認得的欄位，不認得的鍵根本進不了合併；合併時略過 __proto__、constructor、prototype，只走 Object.keys；需要用使用者給的字串當鍵時，用 Map 或 Object.create(null)，它們沒有共用的原型可以污染。

檔名流到 shell：指令注入

假設咖啡店上傳商品照片後，用外部的命令列程式轉檔，檔名來自使用者。第 9 課學過：exec 把整個字串交給 shell 執行，shell 會解讀 ;、$() 這些符號，檔名裡如果有 ; rm -rf ~，後半段就被當成第二個指令執行。這叫指令注入（command injection）：輸入被 shell 當成指令。改用 execFile／spawn 加參數陣列，每個參數直接交給程式，不經過 shell 解讀。

參數陣列擋得住 shell，卻擋不住被執行的程式自己的選項。命令列程式把 - 開頭的參數當成選項：使用者給的檔名如果是 --output=/etc/cron.d/x，很多程式會把它當成「把輸出寫到那裡」。大部分命令列程式支援用 -- 表示「後面都是參數、不是選項」：execFile('grep', ['-n', '--', pattern, file])。最好的做法仍然是先驗證輸入的格式，例如檔名只能是你自己產生的 UUID。

值流到回應標頭：標頭注入

前面提到咖啡店要讓客人「下載自己的發票 PDF」。下載的回應常用 Content-Disposition: attachment; filename="…" 指定存檔時的檔名，如果這個檔名直接取自客人填的訂單備註，使用者給的值就進了回應標頭。HTTP 的標頭是一行一個，用換行（\r\n）隔開（第 12 課）。如果程式把使用者給的值直接放進回應標頭，而值裡有 \r\n，攻擊者就能自己多寫一行，例如 Set-Cookie，這叫標頭注入（header injection）。Node 會擋：res.setHeader('X-Name', 'a\r\nSet-Cookie: x') 丟出 ERR_INVALID_CHAR（v24.22.1 實測）。擋下來是好事，但沒接住的話就是 500，所以放進標頭之前還是要先驗證格式。

log 偽造（log injection）是同一種形狀，只是流向換成 log：如果用純文字一行一筆寫 log，使用者的值帶著換行寫進去，就能多偽造出一行看起來正常的假紀錄，誤導事後的調查。用第 19 課的結構化 JSON log，值裡的換行會被 JSON.stringify 跳脫成 \n，整筆紀錄仍是一行，就偽造不了。

三條線的防法有同一個模式：先驗證格式，再用不會把資料當結構的 API（schema 加安全的合併、參數陣列、Node 對標頭字元的檢查）。下一條線也是「輸入被引擎解讀」，但它不會讓攻擊者讀到或改到任何東西，而是讓伺服器停下來。

一個優惠碼怎麼卡死整台伺服器？

咖啡店的結帳 API 收一個優惠碼，先用正規表示式檢查格式。這條線是「body → 正規表示式」。正規表示式引擎遇到可以有好幾種比對方式的規則時，會一種一種試，失敗了退回去換下一種，這叫回溯（backtracking）。第 9 課看過 /^(\w+\s?)*$/ 遇到 29 個字元就卡住超過一秒：要試的走法隨長度指數成長。

這在 Node 特別嚴重。Node 只有一條執行緒在跑 JavaScript，正規表示式是同步執行的，它跑多久，event loop 就卡多久，這段時間所有請求都在等。攻擊者送出讓回溯爆炸的輸入，讓伺服器無法回應正常使用者，這叫 ReDoS（Regular expression Denial of Service）。「讓服務無法回應正常使用者」這一類攻擊統稱阻斷服務（DoS，Denial of Service）。

優惠碼的規則是：英文大寫或數字組成的一段或多段，段與段之間用一個 -。有人寫成下面這樣。執行 node examples/redos.ts，看時間怎麼隨字元數成長（v24.22.1 實測，數字每次會有差異）：

const COUPON = /^([A-Z0-9]+-?)*[A-Z0-9]+$/

16 個 A 加 !：3.1ms
20 個 A 加 !：11.3ms
22 個 A 加 !：46.4ms
24 個 A 加 !：197.5ms
改寫後，100,000 個 A 加 !：0.5ms

只多了 8 個字元，時間就從 3ms 變成將近 200ms，再長一點就是好幾秒。為什麼會爆？-? 可以不出現，所以 AAAA 可以切成 A|AAA、AA|AA、A|A|A|A…，每一種切法都讓 [A-Z0-9]+ 搶不同長度。結尾的 ! 讓每一種切法都失敗，引擎只好全部試完，n 個字元有 2n 級的組合。會這樣爆炸的規則有兩種形狀，看到就要警覺：

  • 巢狀量詞：量詞裡面還有量詞，而且裡面那段可以比對到長度不同的同一串字，例如 (a+)+、(\w+\s?)*、([A-Z0-9]+-?)*。
  • 重疊的選項：(a|a)*、(\w|\d)+：同一個字元可以被兩個選項吃掉。

兩種形狀的共同點是「同一串字有很多種走法」。所以改寫的原則是：讓每個字元只有一種走法。優惠碼的問題出在可有可無的 -?，把它改成必要的分隔符號：

/^([A-Z0-9]+-?)*[A-Z0-9]+$/      // 危險：-? 可有可無，相鄰的 [A-Z0-9]+ 搶同一串字
/^[A-Z0-9]+(-[A-Z0-9]+)*$/        // 安全：每一段一定由 - 開頭，A 只能屬於目前這一段

兩個接受的字串完全一樣，後者的時間跟長度成正比，就是上面 100,000 個字元只要 0.5ms 的那一行。改寫之外的其他防法：

  • 先限制長度：優惠碼不會超過 32 個字元，先檢查長度再跑正規表示式。這能大幅降低風險，但指數成長下 30 個字元就可能卡一秒，只靠長度不夠，規則本身還是要改。
  • 不用正規表示式：code.split('-').every(part => /^[A-Z0-9]+$/.test(part)) 一樣清楚。
  • RE2 類的引擎：RE2 是 Google 的正規表示式引擎，保證執行時間跟輸入長度成線性，代價是少了一些需要回溯才做得到的語法，例如用 \1 要求「跟前面括號比對到的內容一樣」。npm 上有綁定它的套件；這門課的練習不安裝。
  • 正規表示式是使用者給的（例如搜尋功能讓人輸入規則）：絕對不要直接 new RegExp(input)。要嘛跳脫特殊字元當純文字搜尋，要嘛用 RE2 這類引擎。

ReDoS 讓我們看到另一種攻擊方式：不偷資料，而是把伺服器的某種資源（這裡是 event loop 的時間）用光。event loop 不是唯一會被用光的資源。

還有哪些資源會被一個人用光？

阻斷服務不一定要很聰明，只要讓你的伺服器把某種資源用光：記憶體、連線數、event loop、資料庫連線。任何一種用光了，所有客人一起受影響。所以每一種資源都要有上限。下表列出每種資源的攻擊方式和對應的上限，大部分在前面的課做過，這裡集中成一張檢查表（查表用，不用背）：

資源攻擊上限
記憶體送 2GB 的 body讀 body 時累計長度，超過回 413（第 13 課）；反向代理也設上限
標頭超大標頭、慢慢送標頭（慢速攻擊 slowloris）http.maxHeaderSize 預設 16384；server.headersTimeout 預設 60000ms；server.requestTimeout 預設 300000ms（v24.22.1 實測，第 13 課）
event loopReDoS、超大 JSON改寫規則、限制長度、body 上限；量 event loop 延遲（第 9 課）

為什麼每一行都要有？因為攻擊者會找沒設上限的那一種：限了 body 大小，他就改送很多個很慢的請求；限了連線數，他就送一個會讓正規表示式爆炸的小請求。每一層各擋一種，合起來才擋得住。這種「不靠單一一道防線，每一層各負責一部分」的做法叫縱深防禦（defense in depth）。路徑穿越那一節的「白名單副檔名」也是縱深防禦：主線檢查失守時，還有一層擋著。

表的最後一行有一個前提沒講清楚。回到事故：攻擊者在得手之前，很可能先試了幾百種路徑寫法；之後也可能對優惠碼一個一個猜。這種掃描靠限流擋，而限流要「以正確的客戶端 IP 為單位」。在正式環境裡，這個 IP 並不好拿。

限流要算在誰頭上？反向代理後面的客戶端 IP

正式環境的 Node 服務前面通常有一層反向代理（reverse proxy）：一台站在你的服務前面、替它接收所有請求的伺服器，例如 Nginx 或雲端的負載平衡器（部署課第 12 課）。客戶端連的是代理，代理再開一條新的連線到你的服務。所以從 Node 看，TCP 連線的另一端永遠是代理，req.socket.remoteAddress 永遠是代理的 IP。直接拿它來限流，等於全世界的客人共用一個額度。

為了讓後面的服務知道真正的客戶端是誰，代理會把它看到的來源 IP 附加在 X-Forwarded-For 標頭的最右邊；經過好幾層代理時，每一層都附加一個，用逗號串起來：

客戶端 203.0.113.9 → 代理 A 10.0.0.5 → 代理 B 10.0.0.6 → Node

Node 看到：
  req.socket.remoteAddress   10.0.0.6
  X-Forwarded-For            203.0.113.9, 10.0.0.5

代理 A 附加了客戶端的 203.0.113.9，代理 B 附加了代理 A 的 10.0.0.5，代理 B 自己則是直連 Node 的 remoteAddress。看起來取最左邊就是客戶端了。陷阱在這裡：X-Forwarded-For 也只是一個標頭，也是不可信輸入，客戶端可以自己送。代理只是在後面附加，不會清掉原本的值：

攻擊者送出   X-Forwarded-For: 6.6.6.6
代理附加後   X-Forwarded-For: 6.6.6.6, 203.0.113.9

取最左邊的值，你拿到的就是攻擊者想讓你看到的 6.6.6.6：他每個請求換一個值，限流永遠擋不住他；稽核紀錄裡記的是無辜的人。能相信的只有你自己的代理加上去的部分，也就是從最右邊算起。你知道 IP、確定會正確附加這個標頭的那幾台，叫做信任的代理（trusted proxy）。取客戶端 IP 的演算法：

  1. 直連位址 req.socket.remoteAddress 不是信任的代理：對方直接連進來，X-Forwarded-For 是他自己寫的，完全不看，回傳直連位址。
  2. 是信任的代理：把 X-Forwarded-For 從右往左看，跳過信任的代理，第一個不信任的位址就是客戶端。它左邊的值都可能是偽造的。

用上面的例子走一遍：直連的 10.0.0.6 是信任的代理，所以看標頭；從右往左，10.0.0.5 是信任的代理，跳過；203.0.113.9 不是，它就是客戶端。攻擊者偽造的 6.6.6.6 在它左邊，根本不會被讀到。

真的寫程式時，有兩個地方的字串長得和上面的例子不一樣，比對前要先整理（v24.22.1 本機驗證）。第一，伺服器用預設的 listen(port) 時聽的是 IPv6 的 ::，同時接受 IPv4，IPv4 的客戶端在 remoteAddress 會長成 ::ffff:127.0.0.1（IPv4 對應的 IPv6 位址），跟信任清單比對之前要去掉 ::ffff:。第二，請求裡有兩行 X-Forwarded-For 時，node:http 把它們用 , 合併成一個字串（第 12 課學過哪些標頭會合併），所以一律當成逗號分隔的清單處理。框架通常有一個「trust proxy」設定做同一件事，設錯就等於取最左邊；另外還有一個標準化的 Forwarded 標頭，見課末。

💡 實務上：上線前先搞清楚前面有幾層代理
常見的架構是「CDN → 雲端負載平衡器 → Node」，每一層都會附加 X-Forwarded-For。信任清單少一層，拿到的是代理的 IP，所有人共用一個限流額度；設成全部信任，攻擊者就能偽造 IP。架構改了（加 CDN、換負載平衡器）時這個設定最容易被忘記，限流和稽核紀錄會默默失準。資深工程師會在測試環境用 curl 帶一個假的 X-Forwarded-For 打一次，確認 log 記到的是真正的 IP。代理有哪幾層、IP 範圍是什麼，問維運或查雲端服務的文件，不要用猜的。這次事故的事後調查也靠這個：稽核紀錄裡的 IP 不對，就查不出攻擊者試了多久。

到這裡，事故檢討的前兩個問題都有答案了：每一條輸入到危險去處的線都有了檢查，資源也都有了上限。但這些全部都是「讓程式不犯錯」。第三個問題還在：萬一還有一條線沒找到呢？

萬一還有漏網的？Permission Model：只給程式需要的權限

漏網是一定會發生的：你自己的程式可能有沒發現的漏洞，你裝的依賴也可能被植入惡意程式。回頭看事故，圖片伺服器只需要讀 public/images，卻有權限讀整台機器上程序能讀的所有檔案，包括 .env。如果它一開始就只能讀圖片資料夾，就算路徑檢查寫錯，.env 也讀不到。這就是最小權限（least privilege）：只給完成工作所需的最少權限，萬一被入侵，損害也被限制在那個範圍裡。

Node 的 Permission Model 讓你在啟動時決定這個程序能做什麼。加上 --permission 之後，檔案、子程序這些能力預設全部關閉，再用 --allow-* 旗標一項一項打開：

node --permission --allow-fs-read=./data '--allow-fs-write=./out/*' tools/report.ts

這一行的意思是：只能讀 ./data，只能寫 ./out 底下，其他檔案、子程序都不行。可以用的旗標：

旗標開了 --permission 之後，沒給就會被擋
--allow-fs-read=路徑讀檔（可以給好幾次；* 是全部）
--allow-fs-write=路徑寫檔、建資料夾、刪檔
--allow-child-process開子程序（exec、spawn…）
--allow-worker開 worker 執行緒
--allow-addons、--allow-wasi原生擴充模組、WASI

程式碼碰到沒給的權限時，Node 丟出 ERR_ACCESS_DENIED，錯誤物件上有 permission（例如 FileSystemRead）和 resource（哪個路徑）。程式裡也可以用 process.permission.has('fs.read', '/etc/hosts') 先問。到 work/25 執行看看，注意哪幾行是 ✓、哪幾行是 ✗（v24.22.1 實測）：

$ node --permission --allow-fs-read=./data examples/permission.ts
有沒有開 Permission Model： 有
✓ 讀 data/orders.json
✗ 讀 /etc/hosts：ERR_ACCESS_DENIED FileSystemRead /etc/hosts
✗ 開子程序 ls：ERR_ACCESS_DENIED ChildProcess ls
  回應： hi
✓ 開伺服器、用 fetch 連線

讀 data/ 成功，讀外面的檔案和開子程序都被擋，這是預期的。最後一行要特別注意：開伺服器、用 fetch 連線都成功了。Node 24 的 Permission Model 不限制網路，被入侵的程式在 Node 24 仍然可以把資料送出去（限制網路的旗標是之後的版本才加入，見課末）。

寫旗標時有兩條規則最容易踩到：

  • 相對路徑以執行時的工作目錄為準，不是腳本所在的資料夾。在別的資料夾執行，./data 指的就是另一個地方。
  • 不存在的資料夾要自己加 *：啟動時，存在的資料夾會自動變成「資料夾/*」；不存在的不會，權限只涵蓋那個路徑本身。out/ 還沒建立時，--allow-fs-write=./out 能建出 out，卻寫不進 out/report.json。要寫成 ./out/*，而且整個參數用單引號包起來，不然 shell 會先試著把 * 展開成檔名。* 之後的字元都會被忽略，./out* 連 ./outside 都包含。

最後，也是最重要的一點：它不是沙盒。官方文件明白寫著它不防惡意程式碼，惡意程式碼有辦法繞過它。文件列出的限制包括：符號連結會被跟過去，就算指到允許範圍之外；用已經開好的 file descriptor 操作檔案會繞過檢查；--env-file 這類在初始化之前讀檔的旗標不受管。它擋的是「你自己的程式和依賴不小心或被騙去做多餘的事」，像這次的路徑穿越；不是用來執行惡意程式碼的牢籠。要隔離不信任的程式碼，用容器、獨立的使用者帳號或虛擬機。

💡 實務上：Permission Model 最適合範圍明確的工具程式
很多團隊在正式環境靠的是容器、非 root 使用者和雲端的權限設定，Permission Model 是再多一層。它最好用在範圍很清楚的程式：例如咖啡店每晚產生報表的腳本、處理上傳檔案的轉檔工具，只讀一個資料夾、只寫一個資料夾。要套在整個 Web 服務上，先用 --permission-audit（只記錄、不阻擋，細節見課末）跑一段時間，看程式實際用到哪些權限，不然很容易在某個少用的功能上線後才撞到 ERR_ACCESS_DENIED。它不能取代前面那些輸入檢查，也擋不住 Node 24 的網路連線。

洞補了、權限也收了，但事故還剩一筆帳沒處理：那組已經被讀走的資料庫密碼。

密碼已經外洩了，還有什麼要做？依賴與祕密

先處理外洩的祕密。資料庫密碼、API token 這類東西叫祕密（secret）。它們不進 git、不進 log（第 19 課的遮蔽），從環境變數或祕密管理服務讀取（Auth 課第 23 課、部署課第 11 課）。一旦外洩過，就一律換掉：修掉漏洞只能阻止下一次被讀，已經被讀走的那一份要讓它失效才算處理完。同樣的道理，祕密不小心 commit 進 git 時，從 git 歷史刪除不算處理完，別人可能早就 clone 走了。

事故檢討的最後一步是往外看：這次的洞在自己寫的程式裡，但你的服務有一大半的程式碼是別人寫的。第 3 課學過的供應鏈防線（防的是「你依賴的套件本身出問題」），在這裡整理成上線前的檢查：

  • lockfile 進 git，部署用 npm ci：每次裝到的版本完全一樣，沒有人能在你不知情時換掉某一層依賴。
  • install script 政策：npm install 時依賴可以執行任意程式（install script）。用 allowScripts 記下哪些審查過、哪些拒絕（第 3 課：沒列入的目前仍會執行，只印警告），或用 ignore-scripts=true 全部關掉。加依賴之前先看它是誰維護的、下載量、最近有沒有異常的新版本。
  • npm audit：比對已知的漏洞資料庫。放進 CI，但要看懂報告：很多是開發工具裡的、你的程式用不到的路徑，修不修要判斷，不要只為了讓數字歸零就盲目升級大版本。
  • 最少依賴、定期更新：十行能寫完的功能不值得多一個依賴（和它底下的幾十個依賴）；用的依賴要定期升級，不要等到要一次跳三個大版本。

到這裡事故檢討的三個問題都回答完了：輸入怎麼進來（威脅模型）、同樣的洞還有哪些（路徑、合併、shell、標頭、正規表示式、資源、客戶端 IP），以及漏網時怎麼限制損害（Permission Model、換掉祕密、管好依賴）。練習會讓你親手修其中四條線。

練習

在 learn/ 執行 node check.mjs node 25 建立 work/25/。四題互相獨立。測試會在暫存資料夾複製你的檔案、放隨機的資料再執行，所以寫死答案不會過。

練習 1：image-server.ts 的 GET /images/:file 從 public/images 送出圖片，現在會被路徑穿越。改寫 resolveImage：可以有子資料夾（seasonal/pumpkin.webp、seasonal%2Fpumpkin.webp）；所有跑出根目錄的路徑（原始的 ../、..%2F、%2e%2e%2f、反斜線、解碼後是絕對路徑、跑到 public/images-private）都回 404；指向根目錄外的符號連結回 404（檔案和資料夾的連結都算）；只送 .jpg、.png、.webp；NUL 字元（%00）與壞掉的百分比編碼回 404，伺服器不能掛掉。Content-Type 照現在的寫法即可。想手動試：在 work/25 執行 ln -s ../../secret.env public/images/evil.jpg 建一個符號連結，啟動伺服器後用 curl --path-as-is localhost:3000/images/..%2Fimages-private%2Frecipe.jpg 試各種寫法。

練習 2：完成 client-ip.ts 的 clientIp(req, { trustedProxies })，回傳真正的客戶端 IP。直連位址是 req.socket.remoteAddress（先去掉 ::ffff: 前綴）；它不是信任的代理 → 直接回傳它，不看 X-Forwarded-For；它是信任的代理 → 把 X-Forwarded-For 的位址（逗號分隔、前後可能有空白，也要去掉 ::ffff:）從右往左看，跳過信任的代理，回傳第一個不信任的位址；全部都是信任的代理時回傳最左邊那個；沒有這個標頭時回傳直連位址。要回傳的值不是合法 IP（net.isIP() 回傳 0）時回傳 null。

練習 3：validators.ts 的 validateCouponCode 與 parseDrinkNote 用了會指數回溯的正規表示式。改寫成語意完全相同、不會卡住的版本：測試會拿幾千個隨機字串和原本的規則比對結果，再送 29 到 5,000 多個字元的惡意輸入，每次呼叫要在 50ms 內回傳（測試在子程序裡量，2 秒沒跑完就砍掉）；幾千個字元的合法優惠碼、備註也要照樣接受，所以「太長就當成不合法」過不了。檔案裡的註解有兩條規則的白話說明和例子。備註規則裡的 \p{L} 是「任何語言的字母」（包括中文字），\p{N} 是「任何數字」，要加 u 旗標才能用。

練習 4：tools/report.ts 讀 data/orders.json、把統計寫到 out/report.json（不用改它）。在 run-report.sh 寫一行 node 指令執行它，用 Permission Model 只給它需要的權限：能讀 data/、能寫 out/；不能讀其他檔案（包括同一個資料夾的 secret.env 和 /etc/hosts）、不能開子程序、不能寫 out/ 以外的地方。注意 out/ 一開始不存在。測試在暫存資料夾以 sh run-report.sh 執行，用環境變數 REPORT_MODE 讓 report.ts 模擬被入侵後去讀 /etc/hosts、讀 secret.env、開子程序、寫 data/hacked.txt、寫 out/ 旁邊的 outbox.json，每一種都要被 Permission Model 以 ERR_ACCESS_DENIED 擋下（測試用的是原本的 tools/report.ts，改它沒有用）。自己試：在 work/25 執行 REPORT_MODE=spawn sh run-report.sh。

練習 5：new URL('/images/../secret', 'http://localhost').pathname 和 new URL('/images/..%2Fsecret', 'http://localhost').pathname 分別是什麼？

✓ WHATWG URL 會正規化 .. 和 %2e%2e 這類路徑區段，但 %2F 只是一個被編碼的普通字元，留在同一個區段裡。等你的程式 decodeURIComponent 之後交給 path.join，才變成真的 ../（v24.22.1 實測），所以 a 錯。這兩個網址都合法，不會丟錯，c 錯。而且 Node 的 req.url 是原樣字串，連沒編碼的 ../ 都可能送進來。防線要放在最後：resolve 出真正的路徑再檢查。

練習 6：JSON.parse('{"__proto__":{"isAdmin":true}}') 這一行本身會讓 ({}).isAdmin 變成 true 嗎？

✓ JSON.parse 把每個鍵當成資料，建立自有屬性，Object.hasOwn(body, '__proto__') 是 true，({}).isAdmin 仍是 undefined（v24.22.1 實測），跟嚴格模式無關，a、b 錯。問題出在天真的合併：target['__proto__'] 經過存取器讀到 Object.prototype，再把 isAdmin 寫進去。所以防線在合併：先用 schema 驗證、略過 __proto__、constructor、prototype。

練習 7：服務用 Node 24 加上 node --permission --allow-fs-read=./public server.ts 啟動。程式裡的某段程式碼（例如被植入惡意程式的依賴）照一般的 API 呼叫下面三件事，哪一件會成功、不會丟 ERR_ACCESS_DENIED？

✓ Node 24 的 Permission Model 管檔案、子程序、worker、原生模組，不管網路：開了 --permission，fetch 照樣能連線（v24.22.1 實測），--allow-net 到 v25.0.0 才加入。process.env 已經在記憶體裡，不需要任何權限。~/.ssh 不在 ./public 底下，讀取會 ERR_ACCESS_DENIED，b 錯；沒有 --allow-child-process，開子程序也被擋，c 錯。所以它是縱深防禦的一層，網路出口還要靠防火牆或容器的網路規則限制。另外官方文件也說，真正的惡意程式碼有辦法繞過 Permission Model；要隔離不信任的程式碼，用容器或虛擬機。

常見錯誤

  • 只靠前端驗證：攻擊者不用你的前端，直接送請求。每一個檢查都要在伺服器上再做一次。
  • 用字串比對找 ..：編碼、雙重編碼、反斜線總有一種漏掉。resolve 出最後的路徑再檢查它在不在根目錄下。
  • 用 startsWith(root) 比對路徑卻沒加分隔符號：images-private 也以 images 開頭。比對 root + sep。
  • 忽略符號連結：路徑字串在裡面，檔案在外面。用 realpath 換成真正的位置再檢查，根目錄本身也先 realpath。
  • 用複雜的正規表示式驗證輸入：巢狀量詞遇到特製的輸入會卡死整個伺服器。讓分隔符號變成必要的、先限制長度，或乾脆用 split。
  • 用 exec 串字串：輸入變成 shell 指令。用 execFile／spawn 加參數陣列，需要時用 -- 隔開選項（第 9 課）。
  • 深合併不檢查鍵：__proto__、constructor 讓所有物件都被改掉（TypeScript 課第 3 課）。先驗證 schema，合併時略過危險的鍵。
  • 相信客戶端送來的 X-Forwarded-For：取最左邊的值、或不管直連的是誰都看這個標頭，限流和稽核紀錄都會被騙。只在直連的是信任的代理時才看，從右邊跳過信任的代理。
  • 把 Permission Model 當成沙盒：Node 24 不限制網路，符號連結與已開啟的 file descriptor 也能繞過。它是縱深防禦的一層，不是隔離不信任程式碼的方法。
  • --allow-fs-write=./out 但 out/ 還不存在：只允許 out 這個路徑本身。寫成 './out/*'。
  • 沒看清楚就 npm install：install script 會在你的電腦上執行任意程式。先看是誰維護的，用 allowScripts 或 ignore-scripts 控制，部署一律 npm ci。
  • 修好漏洞就當成事故結束：已經外洩的祕密還能用。外洩過的密碼、token 一律換掉。

補充與查表

標準化的 Forwarded 標頭

RFC 7239 定義了標準化的 Forwarded 標頭（Forwarded: for=203.0.113.9;proto=https），但實務上大部分代理仍然用 X-Forwarded-For 這個事實標準，規則一樣：只相信自己的代理加上去的部分。

Permission Model 的版本變化

以下整理自 Node 24 的 permissions 與 cli 文件，加上本機驗證：

  • v23.5.0／v22.13.0 起是 Stable。
  • v24.0.0 起旗標從 --experimental-permission 改名為 --permission。
  • v24.2.0 起進入點檔案自動可讀，所以不用為 tools/report.ts 加 --allow-fs-read（.ts 進入點一樣可以）。
  • v24.20.0 加入 --permission-audit，只檢查、不阻擋，每一次違規發到 node:diagnostics_channel 的 node:permission-model:fs 等頻道。用它跑一陣子，看程式實際用到哪些權限，再換成 --permission。
  • --allow-net 到 v25.0.0 才加入；Node 24 的 Permission Model 不限制網路。

小結

  • 威脅模型：列出不可信的輸入（網址、標頭、body、檔名、上游回應），列出危險的去處（檔案、shell、SQL、合併、正規表示式、標頭與 log），每條線都要一道檢查。出事的地方，都是輸入被當成某種語法解讀。
  • 路徑穿越：req.url 是原樣字串，URL 也不處理 %2F。不要在字串裡找 ..，而是解碼 → 白名單副檔名 → resolve → 比對 root + sep → realpath 再比一次；更好的設計是不讓使用者給路徑。
  • 同樣形狀的洞：原型污染的入口是合併使用者的物件；指令注入的入口是把輸入交給 shell 或當成選項；標頭注入靠換行，Node 會擋但要先驗證。防法都是先驗證格式，再用不會把資料當結構的 API。
  • ReDoS 來自巢狀量詞與重疊選項，會卡住整條 event loop；把可有可無的分隔符號改成必要的，讓每個字元只有一種走法。只限制長度不夠。
  • 每一種資源都要有上限：body、標頭、逾時、上游、連線與併發、次數。單一一項擋不住阻斷服務，要縱深防禦。
  • 反向代理後面：直連的是信任的代理才看 X-Forwarded-For，從右往左跳過信任的代理；記得去掉 ::ffff:。
  • Permission Model（--permission 加 --allow-*）實踐最小權限，讓漏網的洞損害有限；不存在的資料夾要加 /*；Node 24 不限制網路，它不是沙盒。
  • 依賴與祕密：外洩過的祕密一律換掉；lockfile＋npm ci、install script 政策、看懂 npm audit、最少依賴；祕密不進 git 和 log。
