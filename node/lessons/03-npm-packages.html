階段 1：Node 與開發環境 · 第 3 課

npm 與套件：semver、lockfile 與供應鏈

咖啡店的 API 要開始連 PostgreSQL 了。跟資料庫溝通的協定不用自己寫，npm 上有現成的 pg，一行 npm install pg 就裝好。這一課就從這一行開始，追到它在你的電腦、同事的電腦、自動跑測試的機器和正式環境的伺服器上各執行一次時，會發生什麼事。

這一行會帶出三個工作中真的會遇到的問題：同一份專案，你的電腦能跑，三週後加入的同事 clone 下來卻壞了；部署那天剛好裝到作者前一天發布的新版本，服務當掉；有人打錯一個字母，裝到名字很像的惡意套件，它在安裝的當下就把機器上的 token 傳走。這課的任務是：把咖啡店 API 的依賴整理好，讓任何人、任何機器、任何時間都裝出同一套、而且是你審查過的程式碼。

最後的練習在一個叫 shop 的小專案裡完成這件事：寫好 package.json、自己實作版本範圍的判斷、離線照 lockfile 安裝套件，並擋下一個 install script。

這課的路線：
  1. npm install pg 之後專案裡多了什麼，package.json 要寫什麼，同事 clone 下來才知道怎麼跑。
  2. "^8.23.1" 允許哪些版本，為什麼同一份 package.json 在不同時間會裝出不同版本，lockfile 和 npm ci 怎麼讓每台機器裝出同一套。
  3. 團隊怎麼用同一組指令啟動和測試：npm scripts、node --run、npx，以及正式環境為什麼不拿它們當主程序。
  4. 安裝的當下誰的程式在你的電腦上執行：怎麼擋下 install script 和剛發布的版本。
  5. 回到起點：下一個套件真的需要裝嗎，要裝的話先檢查什麼。
這課會用到：
  • 第 1 課的練習流程：在 learn/ 執行 node check.mjs node NN，它把起始檔複製到 work/NN/ 並跑測試。
  • 第 2 課的結束碼與訊號：0 代表成功、非 0 代表失敗；SIGTERM 是要求程式收尾結束的訊號。

任務：npm install pg 之後，專案裡多了什麼？

先從空資料夾做一次。建立專案設定檔，再裝 pg：

$ mkdir coffee-api && cd coffee-api
$ npm init -y          # 建立 package.json（-y：問題全部用預設答案）
$ npm install pg       # 下載 pg 和它需要的套件，記進 package.json
$ ls
node_modules  package-lock.json  package.json

這幾行背後有三個角色。第一個是套件（package）：別人寫好、打包發布的程式碼。pg 就是一個套件，它實作了跟 PostgreSQL 溝通的協定，你只要呼叫它提供的函式。

第二個是 npm registry：一台集中存放公開套件的伺服器，網址是 registry.npmjs.org。任何人註冊帳號就能把套件發布上去，這一點到供應鏈安全那一節會很重要。

第三個是 npm CLI：在終端機下載與管理套件的指令，安裝 Node 時一起裝好。這台電腦的 Node v24.22.1 附的是 npm 11.19.1，本課實測的行為都以這一版為準。執行 npm install pg 時，npm 到 registry 查 pg 有哪些版本、挑一版、下載它的壓縮檔，解開放進專案。這跟你在 Vue 專案裡裝套件是同一件事，差別在於這次裝下去的程式碼會在伺服器上執行，伺服器上有資料庫密碼和顧客資料。

裝完，資料夾裡多了三樣東西：

  • node_modules/：下載下來的套件。import pg from 'pg' 時 Node 從程式所在的資料夾開始，往上層逐層找 node_modules/pg（第 4 課詳講）。這也是 work/03/ 用得到 node/practice/node_modules 的原因。
  • package.json：專案的說明書，記下你要哪些套件、可以接受哪些版本。
  • package-lock.json：記下實際裝了哪一版。為什麼「要的」和「實際裝的」要分兩個檔案記，是這課後半的重點。

打開 node_modules 會發現裡面不只 pg，而是十幾個資料夾。原因是套件自己也會用別的套件。你在 package.json 寫下、親手裝的套件叫直接依賴；直接依賴自己需要、被 npm 一起裝進來的套件，叫遞移依賴（transitive dependency）。pg 8.23.1 自己就依賴 pg-pool、pg-types 等套件，pg-types 又依賴 postgres-date，一層接一層，形成一棵依賴樹。

假設專案之後也用 npm install -D typescript 裝上 TypeScript（-D 下一節會講），依賴樹大致長這樣：

這棵樹是整課的出發點。樹上每一個資料夾都是你的 API 會執行的程式碼，權限跟你的程式一樣：讀得到環境變數裡的資料庫密碼，連得上網路。你只寫了一行 npm install pg，實際上信任的是這整棵樹上每一位作者。要管好這棵樹，第一步是讀懂你唯一親手寫的那個檔案：package.json。

package.json 要寫什麼，同事 clone 下來才知道怎麼跑？

package.json 有兩種讀者。npm 讀它，決定要裝哪些套件；人讀它，知道這個專案怎麼啟動、怎麼測試、需要哪一版 Node。同事 clone 專案後手上只有原始碼，node_modules 不在 git 裡，所以他的整個環境都要從這個檔案重建出來。把剛才 coffee-api 的 package.json 補完整，會長得像下面這樣。練習 1 的 shop 小專案用的就是同一份內容，所以 name 寫的是 shop：

{
  "name": "shop",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "engines": { "node": ">=24.20.0" },
  "scripts": {
    "start": "node main.ts",
    "dev": "node --watch main.ts",
    "test": "node --test"
  },
  "dependencies": { "pg": "^8.23.1" },
  "devDependencies": { "typescript": "^7.0.2" }
}

逐欄看它回答了什麼問題：

欄位意思
name、version套件名稱和版本。發布到 registry 才真正用到，應用程式隨便填也可以
privatetrue 時 npm 拒絕 npm publish，避免公司的程式碼被不小心發布成公開套件。應用程式一律加上
type"module"：這個資料夾底下的 .ts／.js 都當成 ES module。沒寫時 Node 先當 CommonJS 解析，失敗再重來一次，並印出 MODULE_TYPELESS_PACKAGE_JSON 警告（第 4 課詳講）
engines這個專案需要的 Node 版本。Node 本身不看這個欄位，npm 也只是警告，見表後說明
exports套件對外公開哪些檔案，寫套件時才用到（第 4 課詳講）
scripts指令捷徑，後面「團隊怎麼用同一組指令啟動和測試」一節詳講
dependencies依賴：程式執行時需要的套件，例如 pg
devDependencies開發依賴：只有開發、測試、建置時需要，例如 typescript。部署時可以用 npm ci --omit=dev 不裝它們

有兩欄值得多講。

第一是 engines。它寫的是「這個專案需要哪一版 Node」，但 Node 執行時完全不看它；npm 的 engine-strict 設定預設是 false，版本不符時也只印警告，照樣安裝。既然擋不住，為什麼還要寫？因為它是寫給人和工具看的。團隊通常會有一套 CI（continuous integration，持續整合）：每次有人 push 程式碼，就有一台機器自動把專案 clone 下來、安裝依賴、跑測試和檢查，有錯就擋下合併（部署課第 15 課）。CI 的機器和部署平台都不是你的電腦，它們要用哪一版 Node，engines 就是最直接的依據。這門課寫 >=24.20.0，因為之後幾課用到的 req.signal 行為在 v24.20.0 才修正（第 13、17 課）。

第二是 dependencies 和 devDependencies 的分界。開發時兩邊的套件都裝在你的電腦上，分不分好像沒差；差別出現在部署。正式環境的伺服器只需要執行程式，不需要型別檢查和測試工具，部署時用 npm ci --omit=dev 只裝 dependencies：裝得快、映像小，伺服器上可執行的第三方程式碼也少一些。代價是分錯會出事：正式程式碼 import 的套件被放進 devDependencies，本機一切正常，部署後一啟動就找不到模組。判斷方法只有一條：正式程式碼在執行時 import 的，放 dependencies。

日常改這兩欄用 npm 指令，不用手改 JSON，npm 會同時更新 package.json 和 lockfile：

$ npm install pg              # 裝進 dependencies
$ npm install -D typescript   # -D：裝進 devDependencies
$ npm uninstall pg            # 移除，並更新 package.json 和 lockfile
$ npm install                 # 照 package.json 把缺的都裝好（clone 下來後第一件事）

其他欄位也可以用 npm pkg set 從指令列改，練習 1 可以用它，用法見課末的補充與查表。

💡 實務上：接手專案，先讀 package.json
剛加入團隊、clone 下咖啡店後台的那天，第一個要打開的檔案就是 package.json：scripts 告訴你怎麼啟動和跑測試，engines 告訴你該裝哪一版 Node，dependencies 一眼看出用了哪個框架、哪個資料庫驅動。README 常常過時，scripts 卻是每天在跑的，比較可信。看到不知道做什麼的 script 或套件，直接問同事，比自己猜安全。反過來，你自己開專案時也要讓 package.json 能回答這些問題，下一個接手的人才不用到處問。

回頭看 dependencies 那一行："pg": "^8.23.1"。它寫的不是「要 8.23.1」，前面多了一個 ^。同事 clone 下來會裝到哪一版，就由這個符號決定。

"^8.23.1" 到底允許哪些版本？

要看懂 ^，得先看懂版本號本身。npm 的版本號遵守 semver（語意化版本，Semantic Versioning）。它把版本號寫成 MAJOR.MINOR.PATCH 三段數字，每一段代表作者對使用者的一個承諾：哪一段加 1，就告訴你這次改了多少、你的程式要不要跟著改。

哪一段加 1作者的承諾例子
PATCH（8.23.1 → 8.23.2）只修 bug，用法不變修好某個情況下的連線洩漏
MINOR（8.23.1 → 8.24.0）加新功能，舊的用法照樣能用多一個選項
MAJOR（8.23.1 → 9.0.0）有不相容的變更（breaking change），舊程式可能要改移除舊 API、改預設值

有了這套承諾，你就能表達「哪些更新我願意自動接受」。package.json 裡寫的正是這個：一個版本範圍（range），代表可以接受的一群版本，而不是單一版本。npm 安裝時從 registry 上符合範圍的版本裡挑最新的一個。

npm install pg 預設存成 ^ 開頭的範圍（npm 設定 save-prefix 的預設值是 "^"），加 --save-exact 則存精確版本。^ 的意思是「不換 MAJOR」：只要作者承諾相容，新功能和修正都要。另一個常見的 ~ 更保守，只接受 PATCH。下表全部用 npm 11.19.1 內建的 semver 7.8.5 驗證過：

範圍等於白話
1.2.3=1.2.3只要這一版
^1.2.3>=1.2.3 <2.0.0不換 MAJOR，新功能和修正都要
~1.2.3>=1.2.3 <1.3.0不換 MINOR，只要修正
^0.2.3>=0.2.3 <0.3.00.x 時 MINOR 被當成 MAJOR
^0.0.3>=0.0.3 <0.0.40.0.x 時只接受這一版

所以 "pg": "^8.23.1" 的答案是：8.23.1 以上、9.0.0 以下的任何一版。表的後兩列是 1.0.0 之前的特例。semver 把 1.0.0 當成「API 穩定」的宣告，在那之前作者還在摸索，MINOR 加 1 也可能改壞用法，所以 ^ 把 0.x 的 MINOR 當成會壞東西的那一段：^0.2.3 不會裝到 0.3.0。到了 0.0.x，連 PATCH 都不可靠，^0.0.3 就只接受這一版。

範圍還要處理一種版本：prerelease（預發布版本），例如 2.0.0-rc.1、1.3.0-beta.2。它是正式版之前給人試用的版本，在 - 後面加標籤，排序上比同一個數字的正式版小（2.0.0-rc.1 < 2.0.0）。試用版不穩定，大家不會想在 npm install 時意外裝到它，所以 npm 的規則是：prerelease 預設不會被選到。^1.2.3 不接受 1.3.0-beta.1，雖然它的數字落在範圍裡。只有範圍本身寫了同一個 MAJOR.MINOR.PATCH 的 prerelease，才表示你主動要試這一版：^1.3.0-beta.1 接受 1.3.0-beta.2 和 1.3.0，但不接受 1.3.1-beta.1。

練習 2 要自己實作這套判斷，有一個陷阱先講：版本號要逐段用數字比。1.10.0 比 1.9.0 新，但直接用字串比會得到 '1.10.0' < '1.9.0'，因為字串從第一個不同的字元比起，'1' < '9'。要先用 . 切開、轉成數字，再一段一段比。

semver 是作者的承諾，不是保證。作者可能在 PATCH 版不小心改壞行為，你的程式也可能依賴了某個 bug。所以升級後一定要跑測試，而且要讓「什麼時候升級」由你決定，而不是由安裝的時間點決定。

最後那句話就是下一個問題。^8.23.1 允許的是一個範圍，而範圍裡「最新的一版」會隨時間改變。今天裝和三週後裝，可能是不同的版本。

同一份 package.json，為什麼同事裝到不同版本？

把時間拉開看。你今天 npm install，registry 上符合 ^8.23.1 的最新版是 8.23.1，就裝到它。三週後新同事 clone 專案，這段時間 pg 發布了 8.24.0，也符合範圍，他就裝到 8.24.0。同一份 package.json，在不同時間裝出不同的程式。這還只是一個直接依賴；遞移依賴每一個都寫著自己的範圍，數量多得多，任何一個發了新版都會讓兩台機器的依賴樹不同。如果 8.24.0 剛好有個 bug，就會出現「我這邊好好的，你那邊壞了」，而且很難查，因為兩人的程式碼完全一樣。

問題的根源是 package.json 只記「我願意接受什麼」，沒記「我實際測過的是哪一套」。lockfile（package-lock.json）補上後者。npm 每次安裝後，把整棵依賴樹每一個套件實際裝的版本記下來，連同下載網址，以及一個叫 integrity 的欄位：

"node_modules/pg": {
  "version": "8.23.1",
  "resolved": "https://registry.npmjs.org/pg/-/pg-8.23.1.tgz",
  "integrity": "sha512-…",
  "dependencies": { "pg-pool": "^3.14.0", … }
}

integrity 是套件壓縮檔內容的雜湊值。雜湊是把一份檔案算成一串固定長度的指紋，檔案只要改一個位元組，指紋就完全不同。npm 下載後重新算一次，跟 lockfile 記的比對，不一致就拒絕安裝。所以 lockfile 鎖住的不只是版本號，還有內容本身：就算有人在下載途中動了手腳，也裝不進來。

有了 lockfile，還需要一個「只照 lockfile 裝」的指令。npm install 是開發時用的，它會在需要時調整 lockfile，例如你剛改了 package.json。這對 CI 和部署反而是問題：它們應該安裝你 commit 的那一套，而不是自己決定。npm ci 就是為此設計的：

npm installnpm ci
用途開發時：加套件、改版本CI、部署、clone 後的乾淨安裝
lockfile需要時會更新它一定要有；照它安裝，不會改它，也不會改 package.json
和 package.json 不一致改 lockfile 讓兩邊一致直接失敗
node_modules保留，補上差異先整個刪掉再裝

「不一致就直接失敗」是刻意的：有人改了 package.json 卻忘了 commit 更新後的 lockfile，CI 當場報錯，而不是默默裝出一套沒人測過的版本。「先刪掉 node_modules」也是：上一次安裝留下的東西不會混進這一次。

所以規則是：package-lock.json 進 git，node_modules/ 不進 git（寫在 .gitignore）。node_modules 隨時可以從 lockfile 重建，放進 git 只會讓 repo 變大；lockfile 才是那份「我們測過的清單」。CI 和部署一律用 npm ci，每台機器裝到的東西才會一樣。練習 3 的測試就是這樣檢查的：把你的 shop 複製到別處、不帶 node_modules，執行 npm ci --offline，看能不能重建出來。

lockfile 把「什麼時候升級」變成你的決定：要升級時，在自己的分支上執行 npm update pg（在範圍內升級並更新 lockfile）或 npm install pg@9（換到新的 MAJOR，先讀 changelog，也就是作者寫的更新紀錄），跑測試，再把新的 lockfile 送審。團隊送審的方式通常是開 PR（pull request）：把分支上的變更提出來，同事審查、CI 通過後才合併進主線。lockfile 的變更跟著 PR 一起被看過，進到主線的每一個版本就都有人點過頭。查「裝了哪一版」「為什麼會裝它」的指令，和遞移依賴有漏洞時強制改版本的 overrides，整理在課末的補充與查表。

💡 實務上：lockfile 衝突不要手改，也不要整個刪掉
兩個人同時各加一個套件，合併分支時 package-lock.json 幾乎一定衝突。正確做法是先把 package.json 的衝突解好，再執行 npm install 讓 npm 重新整理 lockfile，最後跑測試確認。常見的錯誤是把 lockfile 刪掉重產：整棵樹可能一次升到範圍內的最新版，等於偷偷做了幾十個升級。審 PR 時也看一下：只改了 lockfile、package.json 沒動，或 lockfile 的變更多到不合理，都值得問一句「為什麼」。

到這裡，同事和 CI 都能裝出跟你一樣的依賴了。下一步是讓大家用同一組指令把專案跑起來，這就是 package.json 裡還沒講的 scripts。

團隊怎麼用同一組指令啟動和測試？正式環境呢？

每個專案啟動的方式都不一樣：有的要 node --watch main.ts，有的要先型別檢查再跑測試。如果這些只寫在某人的腦袋或過時的 README 裡，新同事、CI 各打各的，結果就不一致。npm scripts 把這些指令寫進 package.json 的 scripts 欄位，取一個名字，大家都用名字執行：

$ npm run dev          # 執行 scripts.dev
$ npm test             # npm run test 的縮寫；start 也有縮寫：npm start
$ npm test -- --test-only   # -- 後面的參數會接在 script 後面

npm run 執行 script 時做了幾件你看不到的事，了解它們才知道 script 為什麼能這樣寫：

  • 它會把 node_modules/.bin 加進 PATH。套件提供的指令（例如 typescript 的 tsc）安裝後放在這個資料夾，所以 script 裡可以直接寫 tsc，不用寫 ./node_modules/.bin/tsc。練習資料夾的 "typecheck": "tsc -p ." 就是這樣。
  • 它會找同名加 pre／post 前綴的 script：有 pretest 就會在 test 之前自動執行，posttest 在之後。方便，但也是「沒寫在你眼前的指令」，看 script 時要一起看。
  • script 失敗（結束碼非 0）時，npm 也用非 0 結束，所以 CI 能判斷成敗（結束碼在第 2 課）。

Node 自己也能跑 scripts：node --run test（v22.0.0 加入）。它比 npm 快，但官方文件寫明它刻意做得比較少：不執行 pre／post scripts，也不設定 npm 專屬的環境變數。開發時兩者都可以用，只要記得 pre／post 的差別。

正式環境就不一樣了。現在的服務常用容器部署：把程式和它需要的執行環境（Node、套件）包在一起，在一個跟主機隔離的環境裡執行（部署課第 7 課）。容器啟動時會執行一個指令，那個指令開出的程序叫主程序；主程序自己再啟動的程序，叫它的子程序。執行 npm start 時就是這樣：npm 是一個程序，它再啟動 node server.ts，所以你的程式是 npm 的子程序。

部署平台要關掉或替換服務時，會送 SIGTERM 給容器的主程序，讓它收尾：處理完進行中的請求、關掉資料庫連線，再結束（第 2 課）。平台只把訊號送給主程序。如果主程序是 npm start，收到訊號的是 npm，底下的 node server.ts 收不收得到，要看 npm 有沒有把訊號轉送下去。在這台電腦上實測（npm 11.19.1、Node 24.22.1）：

  • npm start 收到 SIGTERM 會轉送給 node server.ts，程式能正常收尾。
  • node --run start 收到 SIGTERM 時自己結束了，底下的 node server.ts 沒收到訊號，被留在背景繼續跑。

第二種情況下，你寫的收尾程式根本沒機會執行，進行中的請求可能被硬切斷。最穩的做法是不要中間層：容器裡的主程序直接寫 node server.ts，訊號直接送到你的程式（部署課第 8 課）。scripts 留給開發和 CI 用。

scripts 之外，有時你只想臨時跑一個套件提供的工具，例如 tsc 或 eslint，又不想為它寫一個 script，這時常用 npx。它等於 npm exec，用來執行套件提供的指令。它先找 node_modules/.bin，找不到就從 registry 下載並執行。在終端機它會先問你要不要下載；但 npm 文件寫明，stdin 不是終端機或偵測到 CI 環境時，自動當成你同意（--yes）。CI 裡把指令名稱打錯一個字，就是下載陌生人的程式來執行，而且這個程式沒經過 lockfile，版本和 integrity 都沒鎖。工具要裝成 devDependency，或加 --no 禁止下載：npx --no tsc。

npx 的問題其實是整課最後一塊拼圖的縮影：只要有程式從 registry 下載下來，它就可能在你沒注意的時候執行。而 npm install 本身，就有一個這樣的時機。

安裝的當下，誰的程式在你的電腦上執行？

前面一路假設 registry 上的套件都是善意的。第一節說過，任何人都能發布套件，而你信任的是整棵依賴樹。供應鏈攻擊（supply chain attack）就是利用這一點：攻擊者不直接攻擊你的伺服器，而是攻擊你依賴的套件，讓你自己把惡意程式裝進來。前端專案也會遇到，但後端的機器上有資料庫密碼、雲端金鑰，損失大得多（Auth 課第 23 課）。常見的手法有三種，每一種都對應前面學過的一個環節：

  • install script：套件的 package.json 可以寫 preinstall、install、postinstall 這三個 script，npm 安裝的當下就執行，不用等你 import。原本的用途是編譯 C++ 擴充或下載執行檔，惡意套件則拿來讀環境變數、偷 ~/.npmrc 裡用來發布套件的 token。這是 scripts 機制的另一面。
  • typosquatting：用跟熱門套件很像的名字發布惡意套件，例如少一個字母、多一個連字號，等人打錯字。這利用的是「任何人都能發布」。
  • 帳號被盜後發布的新版本：正常的熱門套件被發布了一個惡意的 PATCH 版，符合大家的 ^ 範圍，npm install 就會裝到。這利用的是 semver 範圍會自動接受新版。這類版本通常幾小時到幾天內被發現下架。

lockfile 和 npm ci 已經擋下一部分：已鎖定的版本不會自己換成惡意新版。但你主動加套件、升級的那一刻，或第一次安裝時，仍然會執行到新來的程式。npm 11 對這些時刻提供了幾道防線（預設值用 npm config ls -l 在 11.19.1 確認過）：

工具作用11.19.1 的預設
allowScripts（package.json）記下哪些依賴可以跑 install script。npm install-scripts ls 列出還沒審查的，approve 允許、deny 拒絕沒列入的照樣執行，安裝後印出警告；npm 文件說未來版本會預設擋下
ignore-scripts完全不執行依賴的 install script，也不跑你自己的 pre／post scripts（npm test 這類直接呼叫的照樣執行）false
min-release-age只安裝發布超過 N 天的版本，避開「剛發布就被下架」的惡意版本null（不限制）
npm audit對照已知漏洞資料庫，列出有漏洞的版本install 時自動執行

注意第一列的預設：11.19.1 還不會擋。在這台電腦實測，安裝有 postinstall 的套件時，script 照樣執行，最後才印出警告：

npm warn install-scripts 1 package has install scripts not yet covered by allowScripts:
npm warn install-scripts   coffee-color@1.0.0 (postinstall: node postinstall.js)

看到這段警告時，script 已經跑完了。要擋，得事先做決定。做法有兩種。

第一種是逐一審查：執行 npm install-scripts deny coffee-color，package.json 多了一筆 "allowScripts": { "…": false }，之後的 npm ci 就不再執行它。適合專案裡有少數套件確實需要 install script、其他要擋的情況。要注意的是，從本機 .tgz 檔安裝的套件，這筆的 key 是 tgz 的絕對路徑，專案搬到別的資料夾就對不上了；手寫 "coffee-color": false 對不上這個 key，擋不住。

第二種是全部關掉：在專案的 .npmrc 寫設定。.npmrc 是專案層級的 npm 設定檔，跟 package.json 放在一起、進 git，npm 在這個資料夾執行時會讀它：

ignore-scripts=true
min-release-age=7

第一行讓依賴的 install script 一律不執行，第二行讓 npm 只裝發布超過 7 天的版本，給社群時間發現並下架惡意版本。

兩種做法的共同點是把決定留在專案設定裡，任何人、任何機器執行 npm ci 都一樣。只在自己終端機打 npm install --ignore-scripts 只保護你這一次，隊友和 CI 照樣會執行。這跟 lockfile 是同一個道理：會影響每台機器的決定，要寫進 git 裡的檔案。

剩下的靠習慣：安裝前看清楚名稱，到 npmjs.com 確認下載量和原始碼連結；code review 時看 lockfile 的變更，突然多了一堆沒聽過的遞移依賴要問為什麼。更完整的做法在 第 25 課。

💡 實務上：npm audit 報一堆漏洞時，先分輕重
接手的專案跑 npm audit 常常列出幾十個漏洞，不用慌，也不要直接 npm audit fix --force：它可能幫你換到新的 MAJOR，把程式改壞。先看漏洞在哪：只在 devDependencies 的建置工具裡、不會跑上正式環境的，優先度低；可以用 npm audit --omit=dev 只看正式環境會裝的。再看用不用得到：漏洞在處理使用者上傳檔案的函式，而你的 API 根本沒用到它，風險就小很多。資安或主管問起時，能說清楚「哪些影響正式環境、打算怎麼處理」，比清成零更重要。

這些防線都是在套件已經決定要裝之後才發揮作用。最省事的防線在更前面：一開始就不裝。

下一個套件，真的需要裝嗎？

回到這課的起點。npm install pg 是合理的：PostgreSQL 的協定很複雜，自己寫不划算。但不是每個需求都這樣。每多一個依賴，就多一棵子樹要升級、要追漏洞、要確認授權，也多一個供應鏈的入口。所以資深工程師裝套件前先問：Node 內建有沒有？很多以前要裝套件的功能，Node 24 已經內建。在 work/03 執行 node examples/builtins.ts --size 大杯 --hot 看看：

需求以前常裝Node 24 內建
發 HTTP 請求node-fetch、axiosfetch（第 17 課）
讀命令列參數yargs、minimistutil.parseArgs（第 2 課）
寫測試jest、mochanode:test（第 6 課）
用萬用字元找檔案glob、fast-globfs.glob（v24.0.0 起 stable）
產生 UUIDuuidcrypto.randomUUID()

內建沒有，才評估套件。前兩項對應這課講過的風險，後三項是長期使用的成本與參考訊號：

  • 維護狀態：最近有沒有發版、issue 有沒有人回。沒人維護的套件，出了漏洞也不會有修正版。
  • 依賴數量：一個小工具帶進幾十個遞移依賴，就是幾十個供應鏈入口。
  • 授權（license）：MIT、Apache-2.0 通常沒問題；GPL 這類要求公開原始碼的授權，商用前要問清楚。
  • 型別定義：套件有沒有附 .d.ts，或有沒有 @types/套件名。
  • 使用量：用的人多，問題比較快被發現。

還要看它在專案裡的位置。框架、ORM、資料庫驅動這類核心依賴會滲進每個檔案，選了很難換，值得花時間比較；幾行就寫得完的小工具，自己寫通常比裝一個套件划算。

練習

練習 1、3、4 在 work/03/shop/ 這個小專案裡做。它有自己的 package.json，所以你改壞了也不會影響外面的測試檔。npm 指令要在 shop/ 裡執行：cd node/practice/work/03/shop。題目用的兩個套件放在 shop/vendor/，是 .tgz（npm 套件的壓縮檔格式），不用連網路就能裝。

練習 1：補完 shop/package.json：加上 "private": true、"type": "module"、"engines": { "node": ">=24.20.0" }，以及三個 scripts：start 執行 node main.ts、dev 執行 node --watch main.ts、test 執行 node --test。可以手改，也可以用 npm pkg set。完成後在 shop/ 執行 npm test 和 npm start，確認測試通過、沒有 MODULE_TYPELESS_PACKAGE_JSON 警告。

node --test 不給路徑時，會自己找符合預設檔名規則的測試檔，例如 *.test.ts、*-test.ts，並略過 node_modules。寫成 node --test tests/ 時，tests/ 會被當成一個檔案路徑，不會展開成資料夾裡的檔案。

練習 2：在 semver.ts 實作 npm 判斷版本範圍的規則。satisfies(version, range)：版本符合範圍就回傳 true；maxSatisfying(versions, range)：回傳陣列裡符合範圍的最高版本，一個都沒有就回傳 null。範圍只有三種：精確版本、^、~，都可能帶 prerelease。

要做到：三段版本號用數字比；^ 和 ~ 的上限照上面的表格（包括 0.x、0.0.x）；版本帶 prerelease 時，只有範圍本身也寫了 prerelease、而且 MAJOR.MINOR.PATCH 相同才算符合。比較兩個 prerelease 時一段一段比（用 . 分段）：都是數字就比大小，數字比英文小，英文照字母順序，前面都一樣時段數少的比較小；正式版比同一個數字的 prerelease 大。測試的預期答案由 npm 內建的 semver 7.8.5 產生。

練習 3：在 shop/ 執行 npm install ./vendor/latte-art-1.2.0.tgz，讓 node art.ts tulip 印出 ❀ 鬱金香。art.ts 不用改，它已經寫好 import { pour } from 'latte-art'。打開 package.json 和 package-lock.json，看 npm 記下了什麼：版本、resolved、integrity。

測試會把 shop/ 複製到別的資料夾、不帶 node_modules，執行 npm ci --offline 再跑 art.ts，模擬同事 clone 專案後的第一次安裝。所以手動把檔案複製進 node_modules、刪掉 lockfile、改成相對路徑 import，都過不了。

練習 4：shop/vendor/coffee-color-1.0.0.tgz 有一個 postinstall，會在 shop/ 留下一個 POSTINSTALL_RAN 檔案（假裝它是惡意程式）。把 coffee-color 加進依賴、讓 node color.ts latte 印出 #c8a27c，但不讓它的 install script 執行，而且這個決定要留在專案設定裡：之後任何人在 shop/ 執行 npm ci，都不會產生 POSTINSTALL_RAN。

兩種做法都可以：用 npm install-scripts deny coffee-color 寫進 package.json 的 allowScripts，或在 shop/.npmrc 設定 ignore-scripts=true。測試會刪掉 POSTINSTALL_RAN，直接在你的 shop/ 執行 npm ci --offline（不加任何旗標）來檢查。

練習 5：package.json 寫 "left-pad-x": "^0.2.3"，作者發布了 0.3.0。執行 npm update 會裝到 0.3.0 嗎？

✓ 1.0.0 之前作者還沒承諾 API 穩定，semver 把 0.x 的 MINOR 視為可能不相容的變更，所以 ^0.2.3 的上限是 0.3.0（不含）；^0.0.3 更只接受 0.0.3。a 套用的是 1.x 以後的規則。^ 從來不是「最新版」，^4.6.7 也不會裝到 5.0.0。

練習 6：CI 裡安裝依賴，該用哪個指令？

✓ npm ci 不改 lockfile、不改 package.json，從乾淨的 node_modules 照 lockfile 裝，每台機器結果都一樣；不一致時失敗，問題在 CI 就被發現。npm install 會在需要時改寫 lockfile，CI 測的就不一定是你 commit 的那組版本。在 CI 更新 lockfile 更糟：沒有人 review 過那些新版本。

練習 7：CI 的設定裡寫了 npx tsx check.ts，但專案沒有安裝 tsx。會發生什麼事？

✓ npm exec 文件寫明：stdin 不是終端機或偵測到 CI 環境時，視為 --yes。所以 CI 會下載當下最新的 tsx，版本沒鎖、也沒經過 lockfile 的 integrity；名稱打錯就是執行別人的程式。把工具裝成 devDependency（版本記在 lockfile），或寫 npx --no tsx 禁止下載。

常見錯誤

  • node_modules 進了 git，或 lockfile 沒進 git：node_modules 可以隨時重建，進 git 只會讓 repo 變大、在不同作業系統出問題；lockfile 沒進 git，每個人裝到的版本就不一樣。.gitignore 寫 node_modules/，lockfile 一定 commit。
  • 部署時用 npm install：每台機器在不同時間裝，可能裝到不同版本。部署和 CI 用 npm ci。
  • 以為 semver 保證升級不會壞：它只是作者的承諾。升級一個 PR 一個套件，跑完測試再合併。
  • 執行時需要的套件放進 devDependencies：本機有裝所以正常，部署時 npm ci --omit=dev 不裝它，程式一啟動就 ERR_MODULE_NOT_FOUND。import 在正式程式碼裡的，都放 dependencies。
  • 正式環境用 npm start 或 node --run 當主程序：多一層程序，訊號轉送的行為不同；node --run 不會把 SIGTERM 轉給你的程式。直接執行 node server.ts。
  • 沒看清楚名稱就安裝：typosquatting 就是等你打錯字。從官方文件複製名稱，裝之前到 npmjs.com 確認。
  • 以為 import 才會執行套件的程式：install script 在 npm install 的當下就執行了。不需要 script 的專案設 ignore-scripts=true，需要的用 allowScripts 逐一審查。

補充與查表

這一節收的是主線用不到、但寫設定、查問題或升級時會遇到的細節，查表用，不用背。

用 npm pkg set 改 package.json

不手改 JSON，用指令改欄位，練習 1 也可以這樣做：

$ npm pkg set engines.node='>=24.20.0' type=module   # 不手改 JSON，用指令改欄位
$ npm pkg set private=true --json                    # 要布林值時加 --json，不然存成字串 "true"

查依賴樹和升級的指令

$ npm ls pg            # 裝了哪一版、在樹的哪裡
$ npm explain pg-types # 為什麼會裝它：是誰依賴它
$ npm outdated         # 列出有新版的套件：Current（裝的）、Wanted（範圍內最新）、Latest（最新）
$ npm update pg        # 在 package.json 的範圍內升級，並更新 lockfile
$ npm install pg@9     # 換到新的 MAJOR：先讀 changelog（更新紀錄）

overrides：遞移依賴有漏洞，上游還沒更新

遞移依賴有漏洞、修正版已經出了，但直接依賴的作者還沒更新怎麼辦？用 overrides 強制整棵樹改用某個版本（只有專案根目錄的 package.json 有效），等上游更新後再拿掉：

"overrides": { "pg-types": "2.2.0" }

資深團隊的升級習慣

用 Renovate 或 Dependabot 這類工具自動開升級的 PR；一個 PR 只升一個 MAJOR；先讀 changelog，再看 CI 的測試結果才合併。

node --run 列出所有 scripts

不帶名稱執行 node --run 會列出所有 scripts（v24.22.0 起）。

小結

  • npm install pg 裝進來的是一整棵依賴樹，樹上每個套件都以你的程式的權限執行。
  • package.json 記下你要的套件和可接受的範圍；應用程式加 private、type、engines；執行時要的放 dependencies，開發時要的放 devDependencies。
  • semver：^ 不換 MAJOR、~ 不換 MINOR；0.x 時 ^ 更保守；prerelease 只有範圍寫了同一版的 prerelease 才會被選到；版本號逐段用數字比。
  • 範圍會隨時間裝出不同版本，lockfile 記下整棵樹的版本和 integrity，要進 git；CI 和部署用 npm ci。
  • npm run 有 pre／post scripts 和 node_modules/.bin；node --run 比較快但不跑 pre／post；正式環境直接 node server.ts；npx 在 CI 會自動下載。
  • 安裝套件就是執行別人的程式：用 allowScripts 或 ignore-scripts 把決定留在專案設定，用 min-release-age 避開剛發布的版本，看清楚名稱。
  • 先找 Node 內建的功能，再評估要不要多一個依賴。
