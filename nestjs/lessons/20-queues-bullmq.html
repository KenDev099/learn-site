階段 4：快取、背景工作與外部整合 · 第 20 課

佇列與背景工作：BullMQ

客人在 Vue 前台按下「付款」，後端要做三件事：把訂單改成已付款、寄電子收據、通知廚房。只有第一件是客人要等的。寄信要呼叫外部的寄信服務，平常 300 毫秒，尖峰時 5 秒，偶爾直接回 503。全部放在同一個請求裡，客人就得盯著轉圈圈，寄信服務一掛，付款也跟著失敗。

這一課的任務是重寫「付款後寄收據」，做到三件事：客人不用等寄信；寄信服務掛了，付款照樣成功；每張付了款的訂單最後都會收到收據，而且只收到一封。做法是把寄收據搬到背景：API 只把工作放進佇列，馬上回應；另一段程式在背景慢慢做，失敗了自己重試。這一課用 @nestjs/bullmq 12.0.0 和 BullMQ 6.5.3 實作。

這課的路線：
  1. 付款時哪些事要讓客人等：只有改訂單；寄收據記下來交給佇列，晚點再做（開場問題的最小答案）。
  2. 用 @nestjs/bullmq 把寄收據交給背景：API 怎麼放工作，worker 怎麼取工作來做。
  3. 寄信服務回 503、客人連按兩次：讓工作隔一陣子自己重試，讓同一張訂單只有一個寄收據的工作。
  4. 同一個工作還是可能做兩次、有些錯誤重試也沒用：怎麼不寄出兩封收據，哪些錯誤該放棄，放棄的工作誰來看。
  5. 付了款，收據一定寄得出去嗎：改訂單和放工作之間的空檔，用 outbox 補起來。
這課會用到：
  • 第 15 課的互動式交易：$transaction(async tx => …) 裡的操作一起 commit 或一起回滾；交易裡不要呼叫寄信這類外部服務。
  • PostgreSQL 課第 33 課的工作佇列與 outbox：用一張表當佇列，FOR UPDATE SKIP LOCKED 讓多個 worker 各拿不同的列，不互相等待。
  • 第 12 課與第 19 課的 Redis：compose 裡的 Redis 在 127.0.0.1:6380，連線網址從環境變數 REDIS_URL 讀。

付款時，哪些事該讓客人等？

回到開場的三件事，先問客人按下付款之後，畫面上需要知道什麼。他需要知道付款成功了沒：成功就顯示「付款完成」，失敗就請他再試一次。所以「把訂單改成已付款」的結果必須出現在這次的回應裡，客人得等它。收據不一樣。客人不會盯著信箱等它進來，他只需要它幾秒、甚至幾分鐘內到就好。通知廚房也是。

所以最小的答案是：付款請求只做「改訂單」，做完就回應；寄收據這件事先「記下來」，由別的程式晚點去做。寄信服務慢，客人感覺不到；寄信服務壞了，付款也不受影響，等它恢復再寄就好。

「記下來晚點做」要記在哪裡？一個直覺的寫法是呼叫 mailer.sendReceipt() 但不 await，讓它自己在背景跑。這樣回應確實變快了，但那個 Promise 只活在這個 Node 程序的記憶體裡：部署重啟時它就消失了，寄信失敗了也沒有人會再試一次，收據就這樣不見了。要「晚點一定會做」，工作必須記在程序以外、重啟也不會消失的地方，而且要有程式負責把它取出來做、失敗了再試。

這就是佇列（queue）：一份「先放進去、之後再處理」的工作清單。這課的佇列存在第 19 課用過的那台 Redis 裡。圍繞著佇列有三個角色：

  • 生產者（producer）：把工作放進佇列的程式。這課是付款 API：改完訂單，放一個「寄收據」的工作進去，就回應客人。
  • 消費者（consumer）：從佇列取出工作來做的程式，通常叫 worker。這課的 worker 取出工作後查訂單、呼叫寄信服務。
  • job：佇列裡的每一筆工作。它有名稱（name，例如 send-receipt）、資料（data，例如要寄哪張訂單）和選項（opts，例如失敗了要重試幾次）。

前端類比：你在 Vue 裡按「上傳影片」後，畫面先顯示「處理中」，伺服器在背景轉檔，好了再通知你。你不用等，伺服器也能照自己的速度做。佇列就是後端用來實作這種流程的元件。

一個寄收據的 job 從放進去到做完，會經過下面這些狀態。圖下方的 delayed 和 failed 是失敗時才會走到的路，後面講重試和錯誤處理時會一一用到：

寄收據適合丟到背景，不代表什麼都該丟。判斷的標準是剛才那個問題：客人需不需要在這次回應裡知道結果。

適合丟到背景不適合丟到背景
寄收據、推播、簡訊：客人不需要等它完成扣庫存、改訂單狀態：回應裡就要告訴客人成功或失敗
呼叫慢或常壞的外部服務：可以自動重試很快、不會失敗的小事：多一個佇列只是多一個會壞的元件
大量計算：產報表、轉圖片尺寸需要立刻讀到結果的計算

佇列也有代價，要算清楚：多了 Redis 這個要維運的服務；工作「什麼時候做完」不再確定；工作出錯時不會出現在 API 回應裡，沒有人會在畫面上看到錯誤，要另外監控。所以只把真的需要的工作搬出去。

💡 實務上：工作搬到背景，畫面也要跟著改
咖啡店後台常見的例子是「匯出本月訂單 CSV」：原本按下去要轉圈很久，改用佇列後，API 先回「已收到」和一個工作 id，畫面顯示「處理中」，做完再通知使用者下載。這個流程要先和 PM、前端講好，包括做到一半失敗時畫面要顯示什麼。把訂單同步到電子發票這類外部系統也常搬到背景，對方暫時掛掉時可以自動重試，不會讓結帳跟著失敗。資深工程師在設計會議上會先問三件事：延遲多久可以接受、失敗時誰會發現、跑兩次會不會出事。

決定了寄收據要交給佇列，下一步是在 Nest 裡真的寫出來：付款 API 怎麼放工作進去，worker 又怎麼把它取出來做。

怎麼把寄收據交給背景？生產者與消費者

這課用的佇列套件是 BullMQ：它把 job 和各種狀態存在 Redis 裡，也提供 worker 從 Redis 取工作的程式。@nestjs/bullmq 再把 BullMQ 包成 Nest 的模組與裝飾器，讓佇列和 worker 可以像其他 provider 一樣用依賴注入取得。練習專案已經裝好這些套件；自己的專案要安裝什麼，見課末的補充與查表。

接下來分三步：設定 Redis 連線、寫生產者、寫消費者。

第一步，在 AppModule 設定所有佇列共用的 Redis 連線。和第 11 課一樣，設定從 ConfigService 讀：

BullModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (config: ConfigService<Env, true>) => ({
    connection: { url: config.get('REDIS_URL', { infer: true }) },   // redis://127.0.0.1:6380/0
    prefix: config.get('REDIS_PREFIX', { infer: true }),              // Redis 裡所有 key 的開頭
  }),
}),

connection 是連到哪台 Redis。prefix 是 BullMQ 在 Redis 裡建立的每個 key 前面都會加的開頭，預設是 bull。它的用途是隔開共用同一台 Redis 的應用程式：兩個應用程式都用預設的 bull、又剛好都有叫 receipts 的佇列，就會讀寫同一批 key，搶到對方的工作。用不同的 prefix，兩邊的 key 就分開了。練習的判分也是靠它讓你的開發資料和判分資料分開。

第二步，在功能模組註冊佇列，然後寫生產者。registerQueue({ name: 'receipts' }) 宣告這個模組要用一個叫 receipts 的佇列；之後在任何 provider 用 @InjectQueue('receipts') 注入，拿到的是 BullMQ 的 Queue 物件，呼叫它的 add 就是放工作：

// receipts.module.ts
@Module({
  imports: [BullModule.registerQueue({ name: 'receipts' })],
  providers: [ReceiptsProducer, ReceiptsProcessor, Mailer],
  exports: [ReceiptsProducer],
})

// receipts.producer.ts
@Injectable()
export class ReceiptsProducer {
  constructor(@InjectQueue('receipts') private readonly queue: Queue<{ orderId: number }>) {}

  enqueue(orderId: number) {
    return this.queue.add('send-receipt', { orderId })   // 工作名稱、data，第三個參數是選項
  }
}

把 queue.add 包在 ReceiptsProducer 裡，付款的 service 只要呼叫 enqueue(orderId)，不用知道工作叫什麼名字、選項怎麼設。exports 它，訂單模組才能注入。

第三步，寫消費者。類別加 @Processor('receipts')、繼承 WorkerHost、實作 process(job)，並放進模組的 providers。WorkerHost 是 @nestjs/bullmq 提供的基底類別：Nest 啟動時看到 @Processor，會替這個類別建立一個 BullMQ Worker 並交給它，這個 Worker 會一直等 receipts 佇列裡的工作，收到的每個 job 都轉給你實作的 process。繼承 WorkerHost，Nest 才知道收到工作時要呼叫哪個方法：

@Processor('receipts')
export class ReceiptsProcessor extends WorkerHost {
  constructor(private readonly prisma: PrismaService, private readonly mailer: Mailer) {
    super()   // 繼承了 WorkerHost，constructor 要先呼叫 super()
  }

  async process(job: Job<{ orderId: number }>) {
    // 一個佇列有好幾種工作時，用 switch (job.name) 分開處理
    …
    return { sent: true }   // 回傳值會存在 job.returnvalue
  }
}

BullMQ 判斷一個工作成功或失敗，只看 process 怎麼結束：正常結束（return，或 async 函式回傳的 Promise resolve），工作就是 completed；丟出錯誤，工作就算這一次失敗。它不知道你在裡面寄了信沒有，只認這兩種結局。後面所有的重試和錯誤處理都建立在這條規則上。

到這裡，付款 API 放工作、worker 寄收據的路已經通了。但現在的 add 沒有傳任何選項，而預設只做一次：寄信服務回一次 503，process 丟出錯誤，這張訂單的收據就不會再寄了。

寄信服務回 503 時，怎麼讓工作自己再試？

寄信服務的 503 多半是暫時的：對方正在重啟、或尖峰時忙不過來，過幾秒再試就好了。要讓 BullMQ 自動重試，在 add 的第三個參數傳兩個選項：

await this.queue.add('send-receipt', { orderId }, {
  attempts: 3,                                     // 最多做 3 次（預設 1：失敗就不再試）
  backoff: { type: 'exponential', delay: 1000 },   // 重試前等多久
})

attempts 是這個工作最多做幾次，包含第一次。設成 3，第一次失敗後還有兩次機會；預設是 1，也就是失敗就不再試。

backoff（退避）決定每次重試前要等多久。為什麼要等，而不是失敗了馬上再試？Node 課第 17 課教過：對方正在出問題時，你立刻再打，多半還是失敗，而且所有失敗的工作同時一直打，只會讓對方更難恢復。所以重試要等一下，而且越等越久。BullMQ 的指數退避（exponential）在第 n 次失敗後等 2^(n-1) × delay 毫秒。以 delay: 1000、attempts: 3 來說：

  1. 第一次執行失敗，等 2^0 × 1000 = 1 秒。這段時間 job 在圖上的 delayed，時間到再回 waiting 等 worker 取。
  2. 第二次執行失敗，等 2^1 × 1000 = 2 秒。
  3. 第三次執行又失敗，次數用完，進 failed。

重試帶出一個容易忽略的問題：job 的 data 要放什麼。工作放進去之後，可能要等幾秒、幾分鐘才被處理，失敗了還會隔一陣子重試好幾次。如果 data 放的是整個訂單和顧客物件，worker 拿到的是「放進去那一刻」的快照：這段時間顧客改了 email，收據還是寄到舊地址；訂單被取消了，也照樣寄。而且同一份資料在 Redis 又多存一份。所以 data 只放 orderId，worker 處理時再去資料庫查最新的資料。多一次查詢的成本，跟寄錯地址比起來很小。

重試解決了 503。但「放工作」這一步本身也可能重複：例如客人連按兩次付款，enqueue 就會被呼叫兩次，佇列裡出現兩個寄同一張訂單收據的工作。

同一張訂單放進兩次，怎麼只留一個工作？

每個 job 都有一個 id。不指定時，BullMQ 會自己產生一個新的，所以呼叫兩次 add 就是兩個不同的工作。去重的做法是自己指定 jobId，用「這個工作代表的事」來命名：一張訂單只該有一個寄收據的工作，就叫 receipt-7。只要同一個 id 的 job 還留在 Redis（不論是 waiting、active、delayed，還是已經 completed、failed），這次 add 會被忽略，不會產生第二個工作。

自訂 id 的格式有限制：BullMQ 6.5.3 不接受純數字和含冒號的 id，所以不寫 7 或 receipt:7，而寫 receipt-7。會丟什麼錯誤、為什麼有這個限制，見課末的補充與查表。

「還留在 Redis」是關鍵。預設 BullMQ 會把完成和失敗的 job 一直留著，所以完成的工作留多久，直接決定去重有效多久；另一方面，全部留著，Redis 的記憶體又會一直長：一天一萬筆訂單，就多一萬筆 completed。所以要設定保留多久：

await this.queue.add('send-receipt', { orderId }, {
  jobId: `receipt-${orderId}`,                     // 自訂 id：同一個 id 還留在 Redis，這次 add 會被忽略
  attempts: 3,                                     // 最多做 3 次（預設 1：失敗就不再試）
  backoff: { type: 'exponential', delay: 1000 },   // 重試前等多久
  removeOnComplete: { age: 24 * 3600 },            // 完成的工作留 1 天（單位：秒）
  removeOnFail: { age: 7 * 24 * 3600 },            // 失敗的留 7 天
})

removeOnComplete 和 removeOnFail 都可以寫成 { age, count }：age 是保留幾秒，count 是最多保留幾筆。失敗的通常留得比較久，因為要留給人查原因、修好後重做（後面講 failed 時會用到）。清除的時機不是時間一到就準時刪，細節見課末。

保留時間和 jobId 去重是綁在一起的：去重靠的是舊工作還留在 Redis，舊工作一被移除，同一個 id 就能再加進來。

jobId 去重只在舊的工作還留在 Redis 時有效。設成 removeOnComplete: true，工作一完成就被刪掉，同一個 id 馬上可以再加進來（官方文件 Job Ids 一節明講）。保留時間就是去重的有效期間，所以就算有 jobId，worker 自己也要能承受重複執行。

警告的最後一句是下一節的主題：jobId 擋的是「放進去兩次」，擋不住「同一個工作被做兩次」。

同一個工作還是可能做兩次：怎麼不寄出兩封收據？

BullMQ 保證的是至少一次（at-least-once）：放進去的工作一定會被執行，但可能不只一次。為什麼會這樣？因為「寄出信」和「告訴 Redis 做完了」是兩個步驟，中間可能出事。常見的兩種情況：

  • 做完、還沒回報就當機：worker 寄完信，還沒告訴 Redis「這個工作完成了」，程序就被停掉（部署重啟、記憶體不足被系統砍掉）。worker 拿到工作時，會在 Redis 替這個工作設一把有期限的鎖（預設 lockDuration 30 秒），處理期間 worker 會定期自動替鎖續期，意思是「我還活著、還在做」。程序不在了就沒人續期，鎖過期後 BullMQ 會把這個工作當成卡住了，叫做 stalled，移回等待區交給下一個 worker 重做。信已經寄過一次，又寄一次。stalled 的工作最多重做幾次由 maxStalledCount 決定（預設 1，超過就進 failed），跟 attempts 無關。
  • 其實成功了，只是看起來失敗：寄信服務收到請求、寄出了信，但回應在路上逾時。process 只看到逾時錯誤，丟出錯誤，BullMQ 依上一節的 attempts 再做一次。

這兩種情況，佇列都不可能分辨「信到底寄出了沒」，它只能選「再做一次」，因為漏掉比重複更糟。所以防止重複的責任落在 worker 身上：worker 要寫成冪等（idempotent），意思是同一件事做一次或做很多次，結果都一樣。

寄收據要冪等，worker 得在做之前知道「這張訂單寄過了沒」。這個資訊不能只記在程序的記憶體裡（程序重啟就沒了，換一個 worker 也看不到），要記在資料庫。做法是訂單上有一個 receiptSentAt 欄位，寄出後記下時間：

const order = await this.prisma.order.findUnique({ where: { id: orderId }, select: { receiptSentAt: true, customer: { select: { email: true } } } })
if (order.receiptSentAt) return                        // ① 已經寄過：直接結束，不是錯誤
await this.mailer.sendReceipt(order.customer.email, orderId)   // ② 寄出
await this.prisma.order.update({ where: { id: orderId }, data: { receiptSentAt: new Date() } })   // ③ 寄成功才標記

① 遇到已經寄過的訂單是正常 return，不是丟錯誤。依上一節的規則，丟錯誤會讓 BullMQ 以為失敗而重試，但「已經寄過」是我們想要的結果，工作應該是 completed。

② 和 ③ 的順序是刻意的取捨。先標記再寄：寄信失敗時，重試看到「已寄」就跳過，客人永遠收不到。先寄再標記：寄成功、標記前當機，重試會再寄一封。兩種都不完美，但「偶爾多一封」比「偶爾漏掉」好得多。

要連那一封也避免，就得靠對方支援冪等鍵（idempotency key）：呼叫時帶一個代表這件事的鍵，對方記住處理過哪些鍵，同一個鍵只處理一次。例如寄信服務接受 Idempotency-Key: receipt-7，同一個鍵只寄一次。外部系統不支援時，「剛好一次」做不到，只能選偏向哪一邊。

上面的檢查在一個 worker、一次只做一個工作時成立。開多個 worker 或調高同時處理的數量後，① 和 ③ 之間會出現空檔，需要再加一道防線，見課末的補充與查表。

💡 實務上：code review 看到 worker，先問「跑兩次會怎樣」
寄兩封收據頂多被客人抱怨，但加兩次點數、發兩張優惠券、對外扣兩次款就是真的損失。常見的防線有三種：資料庫的唯一約束（例如點數紀錄表的 (order_id, type) 不能重複）、條件更新（只在 receiptSentAt IS NULL 時更新）、外部服務的冪等鍵（例如金流服務 Stripe 的 API 接受 Idempotency-Key 標頭）。寫測試時直接把同一個 job 的 process 呼叫兩次，斷言副作用只發生一次，比靠人腦推演可靠。

重試加上冪等，寄信服務暫時出問題時，收據最後會寄出、也不會多寄。但不是每種失敗都會因為再試一次而好轉。

重試也沒用的錯誤，和重試用完的工作怎麼處理？

想像顧客註冊時 email 打錯了，寄信服務每次都回「收件地址格式錯誤」。這種錯誤，等 1 秒、2 秒再試，結果都一樣。所以失敗要先分成兩種，處理方式相反：

暫時性錯誤永久性錯誤
例子逾時、503、連線被拒email 格式錯、訂單不存在、對方回 400
再試會好嗎可能會不會，試幾次都一樣
怎麼做丟一般的 Error，讓 BullMQ 依 attempts 重試丟 UnrecoverableError（從 bullmq import），直接進 failed，不管 attempts 設多少

在 worker 裡，把寄信包在 try 裡，依錯誤的種類決定丟什麼。練習的 Mailer 遇到地址格式錯時丟 InvalidRecipientError，這是永久性的，換成 UnrecoverableError；其他錯誤不知道會不會好，原樣丟出讓它重試：

try {
  await this.mailer.sendReceipt(email, orderId)
} catch (error) {
  if (error instanceof InvalidRecipientError) throw new UnrecoverableError(error.message)
  throw error   // 其他錯誤原樣丟出，交給 BullMQ 重試
}

這裡有兩種常見的錯法，都來自忘了「BullMQ 只看 process 怎麼結束」。第一種是用 catch 把錯誤吞掉、正常 return：BullMQ 會以為寄成功了，不會重試，也不會留下失敗紀錄，收據就安靜地消失了。第二種是永久性錯誤也丟一般 Error：白白重試到次數用完，每次都在 log 裡留一筆一樣的錯。

不論哪一種失敗，都要留下紀錄，之後才查得到。@OnWorkerEvent('failed') 標在 processor 的方法上，每一次失敗都會呼叫它（包含之後還會重試的那幾次），參數是 job 和錯誤。failed 事件有時發生在拿不到 job 的情況，所以型別是 Job | undefined，取值要用 ?.。this.logger 是 processor 自己的欄位，用第 4 課的 Logger（從 @nestjs/common import）建立：

private readonly logger = new Logger(ReceiptsProcessor.name)

@OnWorkerEvent('failed')
onFailed(job: Job<{ orderId: number }> | undefined, error: Error) {
  this.logger.error(`訂單 ${job?.data.orderId} 的收據寄送失敗（第 ${job?.attemptsMade} 次）：${error.message}`)
}

永久性錯誤、以及重試次數用完的暫時性錯誤，最後都進 failed。進了 failed 的工作不會自己消失，也不會自己重做：這張訂單的收據就停在那裡，直到有人處理。所以 failed 一定要有人看，做法有兩件：

  • 監控數量：queue.getJobCounts('failed', 'waiting') 可以拿到各狀態的工作數量，接到監控系統（第 24 課）。failed 變多代表有工作放棄了；waiting 一直變多代表 worker 做不完，或根本沒在跑。
  • 修好原因後重做：例如寄信服務的 API 金鑰過期，所有收據都失敗。換好金鑰之後，用 job.retry() 把失敗的工作送回佇列重做。能這樣做的前提是失敗的工作還在，這就是 removeOnFail 要保留一段時間（上一節設 7 天）的原因。

worker 要跑在哪裡（跟 API 同一個程序還是獨立出來）、同時處理幾個工作，也會影響它做不做得完。這兩個設定的取捨放在課末的補充與查表。

💡 實務上：佇列上線前先講好「誰看 failed」
背景工作壞掉時沒有使用者會看到錯誤畫面，最常見的狀況是客服接到「沒收到收據」，翻了才發現 failed 堆了三天。上線前就把 waiting 和 failed 的數量接到監控與告警，並寫一份簡短的處理步驟：看錯誤原因、修好、重做。團隊常會加一個查看佇列的後台頁面（例如 Bull Board），記得放在管理員登入後面，因為 job 的 data 和錯誤訊息可能含 email 等個資。

到這裡，只要工作進了佇列，它會被重試、不會重複寄、失敗了有人看得到。剩下最後一個缺口在更前面：付款的 API 到底有沒有成功把工作放進佇列？

付了款，收據一定寄得出去嗎？雙寫問題與 outbox

付款 API 要做兩次寫入：改資料庫裡的訂單，以及把工作寫進 Redis。資料庫和 Redis 是兩個系統，第 15 課的交易只管得到資料庫，沒有一個交易能同時包住兩邊，讓它們一起成功或一起失敗。這叫雙寫問題（dual write）。queue.add 放在交易的哪個位置，都有洞：

  • 在交易裡、commit 之前 queue.add：工作已經進了 Redis，之後交易卻回滾了（條件更新衝突、commit 失敗）。worker 替一張沒付款的訂單寄收據。
  • commit 之後才 queue.add（練習專案現在的寫法）：commit 成功後，程序剛好被重啟、或 Redis 暫時連不上，add 沒有成功，訂單付了款卻永遠不會寄收據；而且 Redis 一斷，付款 API 還回 500，客人以為沒付成功又付一次。這也違反了這課的任務：寄信相關的元件壞了，付款不該跟著失敗。

問題的根源是「要寄收據」這個事實寫在資料庫以外的地方。解法是 transactional outbox：付款時不直接寫 Redis，而是在付款的同一個交易裡，把「要送出的訊息」寫進資料庫的 outbox_events 表。outbox 就是「寄件匣」：訊息先放進寄件匣，之後再寄出去。訂單和這筆訊息在同一個交易，一起 commit 或一起回滾，不可能只有一邊。

寄件匣裡的訊息要有人送出去。這段程式叫 relay（轉送）：它定期把還沒送出的訊息取出來、放進佇列、標記已送出。relay 送失敗了也沒關係，訊息還在 outbox 裡，下一輪再送。PostgreSQL 課第 33 課用 SQL 寫過同一件事，這裡用 Prisma 和 BullMQ 接起來：

relay 在一個交易裡做三件事，對應圖上的 ① ② ③：

// relay：在交易裡取一批、送出、標記
return this.prisma.$transaction(async tx => {
  const events = await tx.$queryRaw<{ id: number; payload: { orderId: number } }[]>`
    SELECT id, payload FROM outbox_events
    WHERE published_at IS NULL AND type = 'receipt.requested'
    ORDER BY id LIMIT 50
    FOR UPDATE SKIP LOCKED`
  for (const e of events) await this.receipts.enqueue(e.payload.orderId)
  await tx.outboxEvent.updateMany({ where: { id: { in: events.map(e => e.id) } }, data: { publishedAt: new Date() } })
  return events.length
})

① 為什麼要 FOR UPDATE SKIP LOCKED？relay 通常每台伺服器都跑一個（第 21 課用 @Interval 每秒呼叫），所以同一時間可能有好幾個 relay 在讀 outbox。普通 SELECT 不上鎖，兩個 relay 會拿到同一批、各送一次。只寫 FOR UPDATE 不會重複，但第二個 relay 會停在那裡等第一個 commit，等於排隊。加上 SKIP LOCKED，別人鎖住的列直接跳過，每一列只會被一個 relay 拿到，也不用等。Prisma 的查詢 API 沒有這個語法，所以用第 15 課的 $queryRaw。

② ③ 為什麼先送、後標記？送進佇列之後才設定 published_at。反過來（先標記或先刪掉、commit 後才送），送失敗時事件已經不在待送清單裡，就漏了。這和上一節 worker「寄成功才標記」是同一個道理：寧可多送，不能漏送。

所以 relay 也可能重送。add 成功、標記前當機，交易回滾，這批事件又變回「未送出」，下一輪再送一次。這時前面設的 jobId 讓第二次 add 被忽略；就算舊工作已經被清掉、jobId 擋不住，worker 也是冪等的。outbox 給的是「至少一次」，不是「剛好一次」，最後一道防線永遠是冪等的 worker。

交易裡呼叫 Redis，不是違反第 15 課嗎？第 15 課說交易裡不要呼叫外部服務，因為交易拉得越長，鎖住的列就被佔得越久，別人得一直等。這裡是有意識的例外：鎖的只是 outbox 那幾列，沒有人在等它們（其他 relay 會跳過），一批最多 50 筆也不大，所以可以接受。付款交易本身仍然只碰資料庫。

回頭對照這課的任務：付款交易只寫資料庫，Redis 斷線時付款照樣回 200；只要付款 commit 了，outbox 裡就有這筆事件，relay 遲早會送出；重送與重做都由 jobId 和冪等的 worker 收尾，客人只會收到一封收據。

outbox 也有代價：多一張表、多一段要持續執行的 relay、工作會延遲到 relay 下一輪才出去（通常一秒內）。已經送出的列要定期清掉（例如保留 7 天）。所以不是每個背景工作都值得：「掉了也沒關係」的通知用 commit 後直接 add、甚至第 21 課的程序內事件就夠了；跟錢、收據、點數有關的才用 outbox。

練習 1：改 ReceiptsProducer.enqueue(orderId)，放入名稱為 send-receipt 的工作：

  • jobId 是 receipt-<orderId>（例如 receipt-7），同一張訂單呼叫兩次，佇列裡只有一個工作。
  • 最多做 3 次，指數退避（delay 自己決定，大於 0）。
  • data 只有 { orderId }。
  • 設定 removeOnComplete，完成的工作不要全部留著，但也要保留一段時間（{ age } 或 { count }）；寫 true 會一完成就刪掉，jobId 去重跟著失效。

判分：直接呼叫 enqueue，再從 Redis 讀出工作檢查 id、data、opts（這一題不啟動 worker）。

練習 2：寫 ReceiptsProcessor.process(job)：

  • 用 job.data.orderId 查出訂單和顧客的 email，用 this.mailer.sendReceipt(email, orderId) 寄出，寄成功後把 receiptSentAt 設成現在時間。
  • 冪等：receiptSentAt 已經有值就直接結束（正常 return，不是丟錯誤）。

判分：同一張訂單用不同的 jobId 放兩個工作，假的 Mailer 只能被呼叫一次；資料庫裡已經有 receiptSentAt 的訂單不能再寄（所以要看資料庫，不能只記在程序的記憶體裡）；Mailer 第一次失敗、第二次成功時，要真的寄出並標記。測試資料的訂單編號和顧客編號不同，email 要從訂單關聯的顧客查。

練習 3：在同一個 processor 加上錯誤處理：

  • 暫時性錯誤（Mailer 丟的其他錯誤）照樣丟出，讓 BullMQ 重試；用完次數要進 failed，不能被當成完成。
  • InvalidRecipientError 是永久性錯誤：換成 bullmq 的 UnrecoverableError 丟出（訊息保留原因），不再重試。
  • 加一個 @OnWorkerEvent('failed') 的方法，用 processor 的 this.logger.error 記下訂單編號與錯誤訊息。

判分用 10 毫秒的固定退避自己放工作：前兩次失敗、第三次成功 → completed、attemptsMade 3；一直失敗 → failed、attemptsMade 3；email 格式錯 → failed、attemptsMade 1，而且 error log 裡有那張訂單的編號。

練習 4：用 transactional outbox 可靠地寄收據。

  • OrdersService.pay：在同一個交易裡把訂單改成 paid，並用 tx.outboxEvent.create 寫一筆 type: 'receipt.requested'、payload: { orderId }。pay 裡不再呼叫 enqueue（拿掉之後，constructor 裡的 ReceiptsProducer 也可以刪）。
  • OutboxRelay.publishPending()：在一個互動式交易裡，用 $queryRaw 加 FOR UPDATE SKIP LOCKED 取最多 50 筆未送出的 receipt.requested（依 id 排序），逐筆呼叫 ReceiptsProducer.enqueue(orderId)，全部成功後設定 published_at；回傳送出的筆數。

判分：交易在 COMMIT 時失敗 → 沒有 outbox、沒有工作；Redis 連不上 → 付款仍回 200、事件留著，恢復後 relay 送出；送進佇列後、標記前當機 → 重送後仍只有一個工作；兩個 relay 同時處理 20 筆 → 每張訂單只被送一次。

練習 5：同事說：「BullMQ 很可靠，工作只會被執行一次，worker 裡不用檢查有沒有寄過。」哪個說法正確？

✓ c。佇列只能保證工作「至少被做一次」，做完和回報之間的當機、回應逾時造成的重試，都會讓同一件事再做一次。a 錯：jobId 只擋「同一個 id 的工作還留在 Redis 時又加入一次」，擋不住同一個工作被重做，舊工作被清掉後也擋不住新的。b 錯：stalled 的工作要不要重做由 maxStalledCount（預設 1）決定，跟 attempts 無關；attempts 1 只會讓暫時性錯誤也不重試。d 錯：單一 worker 的程序重啟一樣會造成重做。

練習 6：寄收據的 job data 為什麼只放 { orderId }，不放整個訂單和顧客物件？放整個物件，worker 不就省了一次查詢？

✓ b。job data 是放進去那一刻的快照，處理時可能已經過時；查詢的成本跟寄錯地址、替已取消的訂單寄收據比起來很小。a 錯：data 可以是任何能轉成 JSON 的物件（Date 會變字串）。c 錯：去重只看 jobId，跟 data 無關。

練習 7：付款時「在交易 commit 之前就 queue.add」有問題，所以改成「commit 成功之後才 queue.add」。這樣就安全了嗎？

✓ d。commit 之後才 add 解決了「回滾了工作卻出去」，但兩個系統之間的空檔還在，這就是雙寫問題。a 忽略了這個空檔。b 錯：訂單已經 commit 成 paid，客人再付一次只會拿到 409，收據還是沒有；程序當機時也根本沒有機會回 500。c 回到原本的問題：交易之後還可能在 commit 時失敗，工作卻已經出去。outbox 讓「付款」和「要寄收據」在同一個交易裡，送進佇列的事交給可以重試的 relay。

常見錯誤

  • worker 不冪等：以為佇列只會執行一次。重試、stalled、relay 重送都會讓同一件事再做一次。做之前先檢查（receiptSentAt），做完再標記；外部服務支援的話，帶上冪等鍵。
  • 先標記再做：做失敗時，重試看到「已完成」就跳過，那件事永遠沒做。標記放在成功之後。
  • 在交易 commit 前放進佇列，或以為 commit 之後再放就萬無一失：前者回滾了工作照樣出去；後者在兩步之間出事就漏掉。一定要完成的工作用 outbox。
  • 把暫時性與永久性錯誤混為一談：catch 起來 return，BullMQ 以為成功；永久性錯誤丟一般 Error，白白重試。前者原樣丟出，後者丟 UnrecoverableError。
  • 沒有 jobId 去重：重複點擊、relay 重送，就放進好幾個一樣的工作。用有意義的 id（receipt-7），不能是純數字、不能含冒號。
  • 以為 jobId 去重永遠有效：完成的工作被 removeOnComplete 移除後，同一個 id 可以再加入。保留時間就是去重的有效期間。
  • 保留所有完成的工作：沒設 removeOnComplete，Redis 記憶體一直長。設定 { age, count }。
  • job data 放整個物件：worker 拿到的是放進去那一刻的舊資料，顧客改了 email 也不知道。data 只放 id，處理時查最新的。
  • 忘了安裝 ioredis：BullMQ 6 起它是選用的 peer，不會自動安裝。npm install bullmq ioredis。
  • concurrency 開太大：每個同時處理的工作都要資料庫連線，加上 API 的請求超過連線池，整個服務一起變慢。依連線池大小算。
  • failed 沒人看：失敗的工作安安靜靜躺在 Redis。監控 failed 數量，修好原因後 job.retry()。
  • relay 用普通 SELECT：多台伺服器的 relay 會送同一批。用 FOR UPDATE SKIP LOCKED。

補充與查表

安裝：ioredis 要自己裝

BullMQ 6 起，Redis 客戶端套件 ioredis 變成選用的 peer dependency，npm install bullmq 不會自動裝它，要自己裝（練習的 package.json 已經鎖好 bullmq@6.5.3、ioredis@6.0.0）：

npm install @nestjs/bullmq bullmq ioredis

自訂 jobId 的格式限制

BullMQ 6.5.3 的自訂 id 有兩個限制：不能是純數字（'7' 會丟 Custom Id cannot be integers），不能含冒號（'receipt:7' 會丟 Custom Id cannot contain :，冒號是它自己 key 的分隔符號）。所以用 receipt-7。

removeOnComplete／removeOnFail 什麼時候真的刪

清除不是準時刪，而是之後有別的工作完成時順便清掉過期的（failed 那邊在有工作失敗時清）。

多個 worker 同時處理時的冪等

預設 worker 一次只做一個工作（concurrency: 1），同一張訂單的兩個工作不會同時跑到 ① 和 ③ 之間。調高 concurrency 或開多個 worker 時，① 的檢查和 ③ 的標記之間就會有空檔，這時要用第 15 課的條件更新先「搶」這筆（例如另一個 receipt_sending_at 欄位），這課不展開。

concurrency 與連線池

@Processor('receipts', { concurrency: 5 }) 讓一個 worker 同時做 5 個工作。每個工作都會查資料庫，同時處理的工作數 × 每個工作用到的連線數，加上 API 本身的請求，不能超過連線池（第 16 課，Prisma 預設 10 條）。開到 50，API 的請求就會等不到連線。

worker 放在哪個程序

worker 放在哪裡是取捨。放在 API 同一個程序最簡單，練習就是這樣；但寄信、產報表吃 CPU 時會拖慢 API，也沒辦法分開擴充。正式環境常把 worker 拆成獨立程序：另一個入口檔用 NestFactory.createApplicationContext(WorkerModule) 啟動，只有 DI 容器、不開 HTTP port，API 那邊只匯入 registerQueue 和生產者。不論在哪，app.close() 都會在 onApplicationShutdown（第 4 課的生命週期）關閉 worker；關機時怎麼讓手上的工作先做完，第 24 課會處理。

小結

  • 客人要在回應裡知道結果的事（改訂單）留在請求裡；慢的、會失敗、客人不用等的事（寄收據）放進佇列：API 當生產者 queue.add 後馬上回應，worker 在背景 process(job)。不 await 的 Promise 不能取代佇列，程序一重啟就消失。
  • @nestjs/bullmq：BullModule.forRootAsync({ connection, prefix })、registerQueue、@InjectQueue、@Processor ＋ extends WorkerHost。BullMQ 只看 process 怎麼結束：正常結束是 completed，丟錯誤是這次失敗。BullMQ 6 要自己裝 ioredis。
  • job 選項：attempts＋指數 backoff 重試，jobId 去重（舊工作還在時才有效），removeOnComplete／removeOnFail 控制保留量，data 只放 id。
  • 佇列是至少一次，所以 worker 要冪等：先檢查、做成功再標記，偏向「偶爾多一封」而不是「偶爾漏掉」。
  • 暫時性錯誤丟出讓它重試，永久性錯誤丟 UnrecoverableError，@OnWorkerEvent('failed') 記 log；failed 清單要監控，修好原因後 job.retry()。
  • 資料庫和佇列無法一起成功或失敗（雙寫問題）。transactional outbox：同一個交易寫 outbox_events，relay 用 FOR UPDATE SKIP LOCKED 取一批、送進佇列、再標記；重送靠 jobId 和冪等的 worker 收尾。

下一課讓程式自己動起來：用 @Cron 每天清過期的點數、用 @Interval 定時跑這一課的 relay，並比較程序內事件和佇列各適合什麼工作。
