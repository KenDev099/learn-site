階段 1：從 Node 到 NestJS（框架的骨架） · 第 5 課

單元測試：Vitest 與 Testing Module

上個月，同事把會員折扣從九折改成九五折，順手把四捨五入的 Math.round 換成無條件捨去的 Math.floor。程式照樣能跑，畫面照樣顯示金額，只是折扣後小數在 .5 元以上的會員單，每張都少收了 1 元。當下沒有人發現，直到月底對帳數字對不起來，才回頭一張一張翻訂單。

到目前為止，判斷你的程式對不對的，是課程準備好的測試。上線之後沒有人幫你出題，這種錯只有你自己寫的測試會在改壞的當下說出來。這一課的任務是替咖啡店的結帳流程寫一組這樣的測試，由簡單到難測三樣東西：算金額的 calcTotal、要查商品和存訂單的 OrdersService.create、看時間決定打不打折的 PricingService。最後回答一個更難的問題：你怎麼知道自己的測試真的抓得到 bug。練習的判分就是這樣檢查的：拿你寫的測試去跑幾個故意改壞的版本，每個壞版本都要讓測試失敗才算過。

這課的路線：
  1. 那 1 元怎麼在存檔時就被抓到：單元測試是什麼、替團隊解決什麼、代價是什麼。
  2. 用 Vitest 寫出第一個測試：把 node:test 的寫法換成 Vitest，替 calcTotal 寫下會抓到 Math.floor 的那一個測試。
  3. 不連資料庫怎麼測 OrdersService.create：用替身代替查商品、存訂單的依賴。
  4. 誰把替身交給 OrdersService：為什麼要讓 Nest 的 Testing Module 組裝，不要自己 new。
  5. 快樂時光與時間：測試為什麼下午跑會過、晚上跑會紅，怎麼把時間固定住。
  6. 只測一杯拿鐵夠嗎：除了快樂路徑，還要測哪些點。
  7. 先看到紅燈：怎麼確認你的測試真的抓得到 bug。
這課會用到：
  • Node 課第 6 課的 node:test：test('名稱', () => { … }) 包一個案例，assert.equal 這類斷言不成立就讓測試失敗。
  • Node 課第 22 課的 mock.fn() 與隔開外部依賴：資料庫、時鐘換成行為由測試決定的假函式，測試才快、才穩。
  • 第 3 課的 provider 與 CLOCK token：「現在幾點」包成可注入的 provider，useValue 讓同一把鑰匙對應到你給的固定值。

那 1 元，怎麼在存檔的當下就被抓到？

先看開場的事故問題出在哪。改錯本身不稀奇，任何人都會改錯；真正的問題是從改錯到發現隔了一個月。這一個月裡，「會員點一杯拿鐵該收多少」這件事只存在寫程式的人腦中，沒有任何東西會自動去核對。

要把發現的時間縮短到存檔的當下，就要把這個知識寫成一段會自動執行的程式：給 calcTotal 一杯 110 元的拿鐵和會員身分，檢查它回傳 105。110 × 0.95 = 104.5，四捨五入是 105；同事改成 Math.floor 之後會得到 104。這段程式一執行就知道結果不對，不用等到月底。

這種程式叫單元測試（unit test）。「單元」指一小塊邏輯，例如一個函式，或一個 service 的一個方法。單元測試只執行這一小塊，它需要的外部東西，像資料庫、別的 service、時鐘，都換成假的，第 3 節會講怎麼換。因為不碰網路和硬碟，一個單元測試通常幾毫秒就跑完，幾百個測試也只要幾秒，所以可以每次存檔都跑。

它替團隊解決三件事：

  • 防回歸：回歸（regression）是指原本正常的功能，因為改了別的地方而壞掉。開場的事故就是回歸：同事要改的是折扣率，壞掉的是捨入。有測試的話，存檔的當下就紅了。
  • 會執行的規格：測試名稱寫成「庫存剛好等於數量時可以下單」，它就是一條規格。註解會過時，測試不會，因為每次執行都會被驗證一次。
  • 敢重構：重構是只改內部寫法、不改對外行為，例如把 reduce 改成 for 迴圈。測試描述的是行為，只要行為不變，測試就照樣通過，你就知道沒改壞。

測試也有代價。它也是程式，需求變了要跟著改。更麻煩的是寫錯的測試：什麼都沒驗證的測試永遠是綠的，綁死內部寫法的測試每次重構都會紅。這種測試比沒有測試更糟，因為它讓你以為有保護。這一課最後兩節專門談怎麼判斷一個測試有沒有用。

測試除了在你的電腦上跑，在程式碼合併之前還會再跑一次。團隊通常會設定 CI（continuous integration，持續整合）：每次有人 push 程式碼、或開 PR（pull request）請求把自己的分支合併進主線，就在另一台機器上自動安裝套件、跑測試，紅燈就不能合併。這一點後面講時間時還會用到：CI 的機器跟你的電腦設定不一定一樣。

💡 實務上：先替「算錯會賠錢」的地方寫測試
接手一個沒有測試的專案，不用一口氣補滿：先挑金額、庫存、權限、狀態轉換這類算錯會直接造成損失或客訴的邏輯，這也是本課從結帳金額和扣庫存下手的原因。修 bug 時先寫一個重現問題的測試、看它變紅，再修到變綠，同一個 bug 就不會再回來。單純的 getter、把資料原封不動轉交出去的程式，測試的價值很低。CI 上的測試要跑得快、結果穩定，大家才不會想跳過它。

「給 calcTotal 一杯拿鐵、檢查回傳 105」現在還只是一個想法。要讓它每次存檔都自動執行，需要一個測試工具。

用 Vitest 把第一個測試寫出來

NestJS 12 的專案用 Vitest 當測試工具，這門課鎖定 Vitest 5.0.5（為什麼不是 Jest，見課末）。你在 Node 課第 6 課、第 22 課用過 node:test，Vitest 的寫法幾乎一一對應。

Vitest 的寫法大多由 expect 開頭。先講它背後的概念：斷言（assertion）是一句「程式執行到這裡，這件事必須成立」的宣告，不成立就讓這個測試失敗。node:test 用 assert.equal(實際, 預期) 表達斷言；Vitest 寫成 expect(實際).toBe(預期)：expect 包住要檢查的值，後面接的 toBe、toEqual 叫 matcher，決定要怎麼比。

下表是 node:test 和 Vitest 的對照，先掃過去就好，後面每一列都會用到：

要做的事node:testVitest
分組、一個測試describe、it／test一樣，而且設定 globals: true 後不用 import（設定方式見本節後面）
相等（同一個值）assert.equal(a, b)expect(a).toBe(b)
內容相等（物件、陣列）assert.deepEqual(a, b)expect(a).toEqual(b)
會丟錯assert.throws(() => f())expect(() => f()).toThrow(OutOfStockError)
Promise 會 rejectawait assert.rejects(p)await expect(p).rejects.toThrow()
假函式mock.fn()vi.fn()

有了斷言，就能把上一節的想法寫成測試。一個測試讀起來通常分三段，叫 AAA（Arrange-Act-Assert）：準備資料、執行要測的那一行、斷言結果。三段之間空一行，讀的人一眼就知道哪一行是被測的動作：

import { calcTotal, type OrderLine } from './calc-total.js'

describe('calcTotal', () => {
  it('會員點一杯拿鐵是 105 元（104.5 四捨五入）', () => {
    const lines: OrderLine[] = [{ name: '拿鐵', price: 110, size: 'S', quantity: 1 }]   // Arrange

    const total = calcTotal(lines, true)                                              // Act

    expect(total).toBe(105)                                                           // Assert
  })
})

describe 把同一個函式的測試收成一組，it 是一個案例，名稱寫成一句規則，失敗時讀名稱就知道哪條規則被打破。這就是開場事故的解答：同事把 Math.round 改成 Math.floor，calcTotal 回傳 104，這個測試在他存檔的當下就失敗，Vitest 會列出預期的 105 和實際的 104。

注意預期值 105 是手算好寫死的數字，不是在測試裡再算一次 Math.round(110 * 0.95)。如果測試用同一個公式算預期值，程式的公式錯了，測試的公式也跟著錯，兩邊永遠相等，測試就抓不到任何東西。第 6 節會再回到這一點。

上面的測試只 import 了要測的 calcTotal，describe、it、expect 都沒有 import。nest g service 產生的 *.spec.ts 也是這樣，因為每個 work/ 專案的 vitest.config.ts 設了 globals: true，讓這些名稱成為全域；tsconfig 也加了 vitest/globals 的型別，編輯器才認得它們。跑測試的指令：

cd nestjs/practice/work/05
npm test                              # 跑一次全部的 *.spec.ts
npx vitest src/calc-total.spec.ts     # 只跑一個檔，存檔就重跑（按 q 離開）

calcTotal 回傳的是數字，用 toBe 沒有問題。接下來要測的 OrdersService.create 回傳的是訂單物件，這時 toBe 會出乎意料地失敗。原因是 toBe 用 Object.is 比較：數字、字串這類值，內容一樣就相等；物件則要是記憶體裡同一個物件才算相等。兩個各自寫出來的 { total: 220 } 是兩個不同的物件，就算印出來一模一樣也不相等。要比內容，用逐欄比較的 toEqual；只想檢查幾個關鍵欄位，用 toMatchObject：

expect(110).toBe(110)                                // 過
expect({ total: 220 }).toBe({ total: 220 })          // 失敗：兩個不同的物件
expect({ total: 220 }).toEqual({ total: 220 })       // 過
expect(order).toMatchObject({ total: 220 })          // 過：只比列出來的欄位

calcTotal 好測，因為它是純函式：同樣的輸入永遠得到同樣的輸出，不讀資料庫、不看時間，直接呼叫就能測。結帳流程的下一站 OrdersService.create 就不是這樣了。

OrdersService.create 要查商品、存訂單：不連資料庫怎麼測？

先看 OrdersService.create({ productId, quantity }) 做的事：用 ProductsService.findOne 找商品；庫存比數量少就丟 OutOfStockError；否則算出 total = 單價 × 數量，把 { productId, quantity, total } 交給 OrdersRepository.save 存起來，回傳存好的訂單。這裡有兩個依賴：ProductsService 和 OrdersRepository。

這兩個依賴現在還是存在記憶體裡的簡化版，第 14 課會換成 Prisma，真的連資料庫。如果測試直接用真的依賴，到時候每個測試都要先啟動資料庫、準備商品資料，跑起來慢很多；兩個測試同時改同一筆庫存，結果會互相干擾；想測「資料庫斷線」這種情況，更是很難真的製造出來。而且這些都偏離了重點：你想驗證的是 OrdersService 的判斷對不對，例如庫存不足時有沒有擋下來、總額有沒有算對，不是資料庫能不能存東西。

做法是把依賴換成測試替身（test double）：長得跟真的依賴一樣（有同名的方法），但每個方法的行為由測試決定。就像拍電影時的替身演員，鏡頭裡看起來是同一個人，做的動作由導演安排。對 OrdersService 來說，它照樣呼叫 this.products.findOne(2)，只是拿到的商品是測試事先準備好的。

替身依用途有四種名稱，文章和面試都會出現，認得就好，日常不必分太細：

名稱做什麼Vitest 寫法
stub回傳固定的值vi.fn().mockReturnValue(x)、.mockResolvedValue(x)（回傳 resolve 成 x 的 Promise）
mock記錄被怎麼呼叫，讓你斷言expect(fn).toHaveBeenCalledWith(...)、.not.toHaveBeenCalled()
spy包住真的方法，照樣執行但記錄呼叫vi.spyOn(obj, 'method')
fake能動的簡化版實作自己寫，例如存在陣列裡的 repository

在 Vitest 裡，替身的基本單位是 vi.fn()：一個假函式，你可以指定它回傳什麼，它也會記下自己每次被怎麼呼叫。把 vi.fn() 放進一個物件，就是一個依賴的替身：

const products = { findOne: vi.fn() }
products.findOne.mockResolvedValue({ id: 2, name: '拿鐵', price: 110, stock: 3 })
products.findOne.mockRejectedValueOnce(new Error('資料庫斷線'))   // 只有下一次 reject

const orders = { save: vi.fn(async order => ({ id: 1, ...order })) }   // 把收到的東西加上 id 回傳
// …執行 service.create(...) 之後
expect(orders.save).toHaveBeenCalledWith({ productId: 2, quantity: 2, total: 220 })

逐段看：

  • findOne 是 async 方法，真的版本回傳 Promise，所以替身用 mockResolvedValue 回傳「resolve 成這個商品的 Promise」。改 stock 的數字，就能測庫存夠、剛好、不夠三種情況。mockRejectedValueOnce 讓下一次呼叫失敗，用來測依賴出錯時的行為。
  • save 的替身直接給一個實作：把收到的訂單加上 id 回傳，模擬「存好了」。
  • toHaveBeenCalledWith 檢查 save 收到的參數。這是測 OrdersService 的關鍵：總額算對了沒，看的就是它交給 save 的 total。

所以測一個有依賴的 service，要檢查兩件事：它回傳了什麼，以及它對依賴做了什麼。庫存不足的案例最能看出第二件事的重要：除了要丟 OutOfStockError，還要確認 save 沒有被呼叫，用 expect(orders.save).not.toHaveBeenCalled()。如果程式先存訂單才檢查庫存，錯誤照樣會丟，但資料庫已經多了一筆不該存在的訂單。

丟錯的斷言要注意一件事：create 是 async 方法，庫存不足時它不是直接丟錯，而是回傳一個會 reject 的 Promise，所以要用 rejects。.rejects 會等這個 Promise 結束：如果它 reject，就把 reject 的原因（丟出的錯誤）交給後面的 matcher 檢查；如果它反而成功了，斷言就失敗。對應的 .resolves 則是拿 resolve 的值來比，例如 await expect(service.create(input)).resolves.toEqual({ id: 1, total: 220 })。

非同步的斷言一定要 await。expect(p).rejects.toThrow() 本身也回傳 Promise，要等它結束，斷言才真的做完。測試函式要宣告成 async，在 expect 前面加 await：await expect(service.create(input)).rejects.toThrow(OutOfStockError)（await 與錯誤處理見 TypeScript 課第 9 課）。Vitest 5 會直接判忘了 await 的測試失敗，錯誤訊息是 Promise returned by `expect(actual).rejects.toThrow(expected)` was not awaited，看到這行就是漏了 await。舊版的行為見課末。

toThrow(OutOfStockError) 傳入錯誤的 class，檢查的是錯誤的種類。只寫 toThrow() 的話，丟任何錯都算過，程式丟錯了種類（例如把庫存不足丟成 NotFoundException，前端會顯示成「找不到商品」）也抓不到。

替身會記錄呼叫，測試之間就有互相影響的可能：上一個測試呼叫過 save，下一個測試斷言「save 沒被呼叫」就會失敗。所以 Vitest 5 預設 clearMocks: true：每個測試開始前清掉所有替身的呼叫紀錄，設定好的回傳值留著。要注意的是，在 beforeAll 或檔案最上層發生的呼叫，到了測試裡已經查不到。要斷言的呼叫，放在同一個 it 或 beforeEach 裡發生。

替身越多，測到的真東西越少。把被測的 OrdersService 自己也換成替身，測試會永遠通過，因為你在測自己設定的回傳值。只替換「被測物件的依賴」，被測的物件一定是真的。

替身準備好了，還差一步：誰把它們交給 OrdersService？最直覺的寫法是 new OrdersService(products, orders)，能跑，但有一種會讓正式環境啟動失敗的 bug，這樣寫永遠測不到。

誰把替身交給 OrdersService：自己 new，還是讓 Nest 組裝？

回想第 3 課：正式執行時，OrdersService 不是你 new 出來的，是 Nest 的容器建立的。容器讀編譯器記下的建構子參數型別（design:paramtypes），找到對應的 provider 再注入。這一步有好幾種寫錯的方式：漏了 @Injectable()、用 import type 匯入依賴、自訂 token 忘了 @Inject。

以 import type 為例。import type { ProductsService } 只匯入型別，編譯後整行消失，記下的參數型別就不是 ProductsService 這個 class，容器不知道要注入什麼。可是 new OrdersService(products, orders) 是你自己把參數傳進去，完全沒經過容器，所以測試照樣通過；直到上線啟動，才出現 Nest can't resolve dependencies of the OrdersService (?, OrdersRepository)。測試全綠，服務卻起不來。

要讓測試也經過同一套注入流程，用 Testing Module。它是 @nestjs/testing 提供的測試用容器：跟正式的 module 一樣登記 provider、一樣做依賴注入，差別是你可以把任何 provider 換成替身：

import { Test } from '@nestjs/testing'

const moduleRef = await Test.createTestingModule({
  providers: [
    OrdersService,                                          // 被測的：真的
    { provide: ProductsService, useValue: products },       // 依賴：替身
    { provide: OrdersRepository, useValue: orders },
  ],
}).compile()
const service = moduleRef.get(OrdersService)

providers 的寫法跟 @Module 一樣。OrdersService 照正常方式登記，所以容器會讀它的建構子、走完整的注入流程；兩個依賴用第 3 課的 useValue，讓同一個 token 對應到上一節做好的替身。compile() 就是容器實際建立物件的那一步，注入設定有錯會在這裡丟出跟正式啟動一樣的錯誤，import type 那種 bug 在測試裡就現形了。最後 moduleRef.get 取出組好的 OrdersService，之後的測試都對它呼叫 create。

那是不是每個測試都要用 Testing Module？不是。它的價值在於驗證注入設定，被測的東西沒有經過注入，就不需要它：

情況做法原因
純函式，例如 calcTotal直接呼叫沒有依賴，不需要容器
依賴少、只想測演算法的 classnew X(fake) 可以最快、最直接
Nest 的 service，依賴靠注入Testing Module順便驗證注入設定：漏了 @Injectable()、用了 import type（第 3 課）、自訂 token 忘了 @Inject，只有容器會發現
controller、guard、整條請求Testing Module＋HTTP第 10 課的 E2E 測試

最後一列的 E2E（end-to-end，端對端）測試，是真的發一個 HTTP 請求進應用程式、一路測到回應，那是第 10 課的主題；依賴很多時的寫法見課末。

OrdersService 的依賴都是看得見的物件，換成替身很直接。結帳流程的最後一站 PricingService 依賴的卻是一個平常看不見的東西：現在幾點。

快樂時光的測試，為什麼下午跑會過、晚上跑會紅？

咖啡店的快樂時光是每天台北時間 14:00 到 16:00（含 14:00、不含 16:00），飲品打八折，食物不打折：拿鐵 110 元，這段時間賣 88 元。PricingService.priceOf(item) 負責算這個價格，它要先知道現在幾點。

如果程式直接寫 new Date() 取得現在時間，測試結果就看你什麼時候跑：下午兩點跑，「飲品打八折」的測試會過；晚上跑，同一個測試會失敗，程式一行都沒改。這種程式沒變、結果卻時好時壞的測試叫 flaky test。它的傷害不只是一次紅燈：大家發現紅燈常常不是真的有問題，就開始習慣「再跑一次就好」，等到真的有 bug 讓測試變紅，也會被當成又一次的 flaky 而忽略。

問題的根源是：「現在幾點」是 priceOf 的一個輸入，卻藏在函式裡面，測試控制不到。解法是把它變成測試能決定的東西，有兩種做法。

第一種是注入時鐘，也就是第 3 課的 CLOCK token。練習裡的 PricingService 就是這樣寫的：建構子用 @Inject(CLOCK) 拿到一個有 now() 方法的物件，需要時間時呼叫 this.clock.now()，不自己 new Date()。正式環境的 now() 回傳真的現在時間；測試時用上一節的 Testing Module，把 CLOCK 換成回傳固定時間的替身：

const moduleRef = await Test.createTestingModule({
  providers: [
    PricingService,
    { provide: CLOCK, useValue: { now: () => new Date('2026-10-31T14:00:00+08:00') } },
  ],
}).compile()

這樣做的另一個好處是依賴寫在建構子上，一看就知道這個 service 跟時間有關。

第二種是 vi.setSystemTime(date)：不改程式，直接讓 new Date() 和 Date.now() 回傳你指定的時間；搭配 vi.useFakeTimers() 連 setTimeout 也能控制。它改的是整個測試環境的時鐘，用完要在 afterEach 呼叫 vi.useRealTimers() 換回來，否則會影響後面的測試。適合已經寫死 new Date()、不方便改建構子的舊程式；新寫的程式優先用注入。

不管哪一種，時間都要寫成帶時區的固定瞬間。JavaScript 的 Date 存的是一個絕對的瞬間，但 new Date(2026, 9, 31, 14) 這種寫法的意思是「執行測試那台電腦當地時間的 14 點」（月份從 0 起算，9 是十月）。你的電腦在台北，它是台北 14 點；CI 的機器多半設成 UTC，同一行就變成 UTC 14 點，也就是台北 22 點，測試在你這裡過、在 CI 失敗。寫成 new Date('2026-10-31T14:00:00+08:00')，字串裡寫明了時區，在哪台機器上都是同一個瞬間（日期與時區見 TypeScript 課第 6 課）。練習 3 的判分會用 TZ=Asia/Taipei 和 TZ=UTC 各跑一次你的測試，就是在檢查這件事。

亂數是同一類問題：結果看運氣的輸入，一樣讓函式接收 random() 參數或注入一個 provider，測試傳入固定值。

💡 實務上：code review 看到 new Date() 就多問一句
跟時間有關的規則到處都是：營業時間、限時優惠、優惠券到期、登入 token 過期、「下單 30 分鐘內可取消」。這些邏輯裡直接寫 new Date() 或 Date.now()，測試就很難寫，資深工程師在 review 時會請你改成注入時鐘，像這課的 PricingService 一樣。另一個常見坑是跨日和月底：營業到凌晨的店、「本月訂單」的查詢，都要拿 23:59 和 00:00 這種時間點測過。伺服器和 CI 多半是 UTC，「台北時間的今天」要在程式裡明確換算，不能假設機器的時區。

到這裡，結帳流程的三站都知道怎麼測了。但「有測試」不等於「抓得到 bug」：如果你對每一站都只測一個最普通的情況，例如一杯拿鐵 110 元，大部分的 bug 還是會溜過去。

只測一杯拿鐵 110 元夠嗎？要測哪些點

「一杯拿鐵 110 元」這種最常見、最不會出錯的情況叫快樂路徑（happy path）。快樂路徑當然要測，但寫程式的人最常想到的也是它，bug 多半藏在別的地方。寫完快樂路徑之後，對照這幾類再補：

  • 邊界值：規則的分界兩側都要測。快樂時光「14:00–16:00，含 14:00、不含 16:00」要測 13:59:59、14:00:00、15:59:59、16:00:00 四個點；「庫存不足」要測剛好等於庫存（可以下單）和多一個（不行）。把 < 寫成 <= 這種錯，只有剛好落在邊界上的資料抓得到，14:30 這種中間值兩種寫法都會過。
  • 錯誤路徑：會丟什麼錯？丟錯之前有沒有做了不該做的事？上一節的「庫存不足時 save 沒被呼叫」就屬於這類。
  • 空的、零的、只有一個的：空陣列、數量 0、只有一行。calcTotal([]) 應該回傳 0，一個不小心的改寫可能回傳 NaN。
  • 會產生小數的輸入：測四捨五入，要選一個真的會出現 .5 的金額。開場的事故就是這類：如果測試只用 100 元的商品（× 0.95 = 95，沒有小數），Math.round 和 Math.floor 都得到 95，測試抓不到；用 110 元的拿鐵算出 104.5，兩者才會不同。

知道要測什麼之後，也要知道什麼不該測：實作細節。例如斷言某個私有方法被呼叫了幾次、或檢查內部用了 reduce 還是 for。這些測試在重構時會壞，但對外的行為根本沒變，只會讓人覺得測試礙事。斷言的對象是「外面看得到的結果」：回傳值、丟出的錯、對依賴做了什麼（存了什麼、有沒有存）。

還有第 2 節提過的：預期值要自己算好寫死。expect(total).toBe(105) 是對的；expect(total).toBe(Math.round(110 * 0.95)) 等於把程式的公式抄一遍，公式錯在哪，測試就跟著錯在哪。

照這份清單寫，測試會好很多，但你還是無法確定：你寫的每一個測試，真的會在程式出錯時變紅嗎？

怎麼知道測試真的有用：先看到紅燈

一個從來沒失敗過的測試，你不知道它有沒有在測東西。它可能真的在保護你，也可能什麼都沒檢查：忘了寫 expect、預期值用同一個公式算、或測的其實是替身自己。這些測試永遠是綠的，看起來跟好測試一模一樣。

檢查方法是反過來做：故意把程式改壞一點，看測試會不會失敗。這叫突變測試（mutation testing）。每一個改壞的版本叫一個 mutant，例如把 Math.round 改成 Math.floor、把 < 改成 <=。測試在 mutant 上失敗，叫做把它「殺掉（killed）」，代表這種 bug 你抓得到；測試還是通過，叫做「存活（survived）」，代表這種 bug 會溜過去。開場的事故，從這個角度看，就是一個存活的 mutant。

這一課練習的判分就是突變測試，另外加了三條規則，防止「看起來有測試」的寫法過關：

  • 判分會給一個「行為完全一樣、只是改寫」的重構版本，你的測試在它上面要照樣通過。比對原始碼、斷言內部怎麼寫的測試，在這裡會失敗。
  • 開了 expect.requireAssertions：沒有任何 expect 的測試直接算失敗。
  • skip、todo、it.only 都不行，每個測試都要真的執行。

平常沒有判分程式時，也可以手動做同樣的事：寫完一個測試，把程式改壞一行，確認測試變紅，再改回來。看過它紅，才相信它綠。

你可能聽過另一個衡量測試的數字：覆蓋率（coverage），也就是測試執行時跑過了多少比例的程式碼。它回答的是「哪幾行有被執行過」，但被執行不代表被驗證：寫一個測試呼叫 calcTotal(lines, true) 卻沒有任何 expect，每一行都跑過了，行覆蓋率照樣是 100%，Math.floor 的 mutant 卻照樣存活。突變測試回答的是另一個問題：「這裡錯了，我會知道嗎？」

💡 實務上：別把覆蓋率當 KPI
很多團隊在 CI 設覆蓋率門檻，低於門檻就擋 PR。門檻可以防止大家完全不寫測試，但一旦變成要達成的數字，就會出現只呼叫不斷言的測試來湊數。review 測試時更有用的問題是：「這段邏輯改錯了，哪一個測試會紅？」答不出來就是缺測試，開場那次改錯就該在這裡被問出來。突變測試工具（例如 StrykerJS）可以自動做這件事，但跑一次要把程式改壞很多遍、比較慢，實務上多半只對金額、權限這類核心模組定期跑，不會每次 push 都跑全專案。

回到開場：如果當時 calcTotal 有一個「會員點一杯拿鐵是 105 元」的測試，同事存檔的當下就會看到紅燈。接下來的練習，就是替結帳流程的三站各寫一組這樣的測試。

補充與查表

  • 為什麼是 Vitest：NestJS 12 用 nest new 建立 ESM 專案時，預設的測試工具是 Vitest；CommonJS 專案才是 Jest。
  • 設定檔：Vitest 5 不會往上層資料夾找設定檔，所以每個 work/ 專案都有自己一份 vitest.config.ts。
  • 忘了 await 的行為：Vitest 4 以前，非同步斷言忘了 await 只會印警告、測試照樣通過；Vitest 5 直接判這個測試失敗。
  • 替身的自動清理：Vitest 5 預設 clearMocks: true（每個測試前清掉呼叫紀錄）、restoreMocks: false（vi.spyOn 包住的方法不會自動換回，要自己 mockRestore()）。vi.spyOn 用在不能換掉、只想監看的既有方法，例如確認某段程式有印出警告：它不是建立新的假函式，而是包住一個已經存在的方法並記錄呼叫，用完要 mockRestore() 換回原本的方法。本課的練習用不到，認得就好： 
    const warn = vi.spyOn(console, 'warn').mockImplementation(() => {})   // spy：記錄呼叫，這裡也順便不真的印出
// …執行會印警告的程式之後
expect(warn).toHaveBeenCalledOnce()
warn.mockRestore()   // 換回真的 console.warn：Vitest 5 預設不會自動還原（restoreMocks: false）
  • Testing Module 的另外兩種寫法：E2E 測試要的是整個應用程式，不是單一 service，所以寫法會換成載入正式的 AppModule，用 overrideProvider 只換掉其中一兩個 provider（第 10 課 E2E 用）。被測的 service 依賴很多、一個一個寫替身太累時，可以交給 useMocker：沒有登記的依賴，Nest 會把它的 token 傳給你的函式，由函式回傳替身。 
    // 載入整個正式模組，只換掉其中一個 provider（第 10 課的 E2E 測試常用）
await Test.createTestingModule({ imports: [AppModule] })
  .overrideProvider(CLOCK).useValue({ now: () => new Date('2026-10-31T14:00:00+08:00') })
  .compile()

// 依賴很多時，沒登記的依賴一律交給 useMocker 產生替身
await Test.createTestingModule({ providers: [OrdersService] })
  .useMocker(token => (token === ProductsService ? { findOne: vi.fn() } : {}))
  .compile()

練習

三題都是只寫測試、不改程式：src/calc-total.ts、src/orders.service.ts、src/pricing.service.ts 是正確的，判分會拿它們的改壞版本跑你的 spec。每題只用自己那個 spec 判分，別題還沒寫不會互相影響。在 work/05 執行 npm test 可以隨時跑自己的測試。

練習 1：替 calcTotal(lines, member) 寫測試。規則：每一行是 (單價 + 尺寸加價) × 數量，尺寸加價 S／M／L 是 0／10／20 元；會員打九五折，四捨五入到整數元；沒有品項時是 0。判分會準備七個改壞的版本，包括尺寸沒加價、大杯加錯、加價沒乘數量、無條件捨去、非會員也打折、空陣列回傳 NaN；另外有一個改用 for 迴圈、結果完全一樣的重構版本，你的測試要照樣通過。

預期值自己算好寫成數字，不要 import SIZE_UPCHARGE 再算一次。挑一個會產生 .5 的金額來測四捨五入（提示：拿鐵 110 元 × 0.95 = 104.5）。

練習 2：替 OrdersService.create({ productId, quantity }) 寫測試。它先用 ProductsService.findOne 找商品，庫存比數量少就丟 OutOfStockError（庫存剛好等於數量可以），否則算出 total = 單價 × 數量，把 { productId, quantity, total } 交給 OrdersRepository.save，回傳存好的訂單。

用 Test.createTestingModule 組出真的 OrdersService，兩個依賴換成 vi.fn 替身（mockResolvedValue）。至少要測：總額和 save 收到的參數、剛好等於庫存、庫存不足時丟錯而且 save 沒被呼叫。改壞的版本包括「先存訂單才檢查庫存」「吞掉錯誤回傳 null」「庫存不足卻丟成 NotFoundException」（所以要用 toThrow(OutOfStockError) 確認錯誤的種類），還有「用 import type 匯入 ProductsService」：自己 new OrdersService(...) 的測試抓不到最後這一個。

練習 3：替 PricingService.priceOf(item) 寫快樂時光的邊界測試：每天 14:00–16:00（台北時間，含 14:00、不含 16:00）飲品打八折，食物不打折。拿鐵 110 元，打折後 88 元。用 CLOCK 的替身或 vi.setSystemTime 決定時間，邊界兩側都要測，價格要比對確切的金額（88、110），不是只看「有沒有比較便宜」。

判分會用 TZ=Asia/Taipei 和 TZ=UTC 各跑一次你的測試，兩次都要在正確的程式上通過。new Date(2026, 9, 31, 14) 這種寫法在 UTC 會變成另一個瞬間，改用帶 +08:00 的字串。

練習 4：await expect(service.create(input)).resolves.toBe({ id: 1, total: 220 }) 失敗了，但印出來的值看起來一模一樣。為什麼？

✓ toBe 問的是「是不是同一個東西」，對物件和陣列幾乎都會失敗；toEqual 逐欄比較內容，toMatchObject 只比列出來的欄位。TypeScript 的型別在執行時不存在，不會被比較（b 錯）。resolves 後面可以接任何 matcher，包括 toEqual（a 錯）。

練習 5：同事寫的測試從寫好那天起就一直是綠的，從來沒紅過。這代表什麼？

✓ 沒有 expect、斷言 expect(true).toBe(true)、預期值用同一個公式算、測的是替身本身，這些測試都永遠是綠的。綠燈只有在「你看過它會變紅」之後才有意義（a 錯）。它也可能真的有用，只是程式沒壞過，檢查之前不該刪（c 錯）。

練習 6：測試裡寫了 expect(service.create({ productId: 2, quantity: 99 })).rejects.toThrow(OutOfStockError)，前面沒有 await。在 Vitest 5 會怎樣？

✓ Vitest 5 起，resolves、rejects 這類非同步斷言沒有 await 就讓測試失敗。b 是 Vitest 4 以前的行為：會在測試結束時補等並印警告，但斷言不是在你寫的那一行執行，後面的檢查（例如 save 沒被呼叫）可能在錯誤發生前就跑完了。c 是常見誤解：沒被 await 的 Promise，測試函式不會等它。

常見錯誤

  • 只測快樂路徑：bug 在邊界和錯誤路徑。每條規則測分界的兩側，每個 throw 至少一個測試；測四捨五入要選真的會出現 .5 的金額。
  • 在測試裡重算一次預期值：公式錯了，預期值也錯，兩邊永遠相等。手算好寫死。
  • 非同步斷言忘了 await：Vitest 5 直接判失敗。await expect(p).rejects.toThrow()，測試函式加 async。
  • 把被測的物件也換成替身：測到的是自己設定的回傳值，永遠會過。只替換依賴，被測的 class 從 Testing Module 拿真的。
  • 在 beforeAll 呼叫被測的方法，再到 it 裡檢查替身：Vitest 5 預設 clearMocks，每個測試前呼叫紀錄已經清空。把動作放進 it。
  • 測試之間共用可變狀態：上一個測試改了替身的回傳值或陣列，下一個測試的結果跟著變，換個順序就壞。在 beforeEach 重建被測物件和替身的設定。
  • 測試依賴真實時間、亂數或時區：今天過、明天不過；你的電腦過、CI 不過。時間用注入的時鐘或 vi.setSystemTime，寫成帶 +08:00 的固定瞬間。
  • 測實作細節：斷言私有方法被呼叫幾次，重構就壞。斷言回傳值、丟出的錯、對依賴做了什麼。

小結

  • 單元測試只測一小塊邏輯，依賴換成替身，幾毫秒跑完，可以每次存檔都跑；用來防回歸、當規格、讓你敢重構。開場那 1 元，一個「會員一杯拿鐵 105 元」的測試就抓得到。
  • Vitest：斷言寫成 expect(實際).matcher(預期)；toBe 比同一個值、toEqual 比內容、toThrow(錯誤 class) 測丟錯的種類；非同步斷言一定要 await（Vitest 5 沒 await 就失敗）。
  • 替身：vi.fn().mockResolvedValue(...) 決定回傳值，toHaveBeenCalledWith／not.toHaveBeenCalled 檢查呼叫；有依賴的 service 要同時檢查回傳值和它對依賴做了什麼。Vitest 5 每個測試前清空呼叫紀錄。
  • Test.createTestingModule 讓被測的 service 經過真的依賴注入、依賴換成替身，import type 這類注入錯誤在測試裡就會現形；overrideProvider 換掉正式模組裡的一個 provider，useMocker 一次補齊所有依賴。純函式直接呼叫就好。
  • 時間要可控：注入 CLOCK 或 vi.setSystemTime，時間寫成帶時區的瞬間，否則測試會在不同時間、不同機器上時好時壞。
  • 好測試抓得到 bug：測邊界、錯誤路徑、空值；預期值寫死；先看到紅燈再相信綠燈，覆蓋率只說明哪幾行被執行過。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：會員點數 service 這樣寫，本機測試全過，上線後尖峰時段有人回報點數加到別人身上。問題出在哪？

@Injectable()
export class PointsService {
  private memberId = ''
  async earn(memberId: string, amount: number) {
    this.memberId = memberId
    const rate = await this.rates.current()
    await this.repo.add(this.memberId, Math.floor(amount * rate))
  }
}

✓ provider 預設是 singleton，欄位等於全域狀態；兩個請求交錯時，await 回來讀到的是後來那個人的 memberId。這次請求的資料只放參數和區域變數。b 錯在問題不在寫入順序，而是讀錯了是誰，加交易也一樣會加到別人身上。（第 3 課）

練習 8：啟動時出現 Nest can't resolve dependencies of the OrdersService (?)。已經確認 OrdersModule import 了 ProductsModule，ProductsModule 也 export 了 ProductsService。接下來先查什麼？

✓ Nest 靠編譯器寫進 design:paramtypes 的 class 當 token；import type 編譯後消失，metadata 裡就不是那個 class，問號就出現。改成一般的 import。c 錯在模組已經 import 又 export 了，@Global() 只是省掉 imports，不是修法。（第 3、4 課）

練習 9：OrdersService 要查商品價格，需要用到 ProductsModule 裡的 ProductsService。哪一種做法最恰當？

✓ provider 預設只在自己的模組看得到，exports 開放、imports 取用，依賴寫在 imports 上看得見。一個 provider 只登記在一個模組。a 錯在會變成兩個實例，狀態不同步，記憶體裡的商品資料兩邊各一份。（第 4 課）

練習 10：GET /products/3 一直回 404，但 3 號商品明明存在。哪裡出事？

@Get(':id')
findOne(@Param('id') id: number) {
  const product = this.products.find((p) => p.id === id)
  if (!product) throw new NotFoundException()
  return product
}

✓ 路徑與查詢參數一律是字串，: number 只騙過型別檢查。改成 @Param('id', ParseIntPipe) id: number，不是數字還會直接回 400。c 錯在取整個物件也一樣是字串，問題在沒有轉型。（第 2 課）

練習 11：商品被刪掉後，前端打 GET /products/9 收到 500，畫面顯示「系統忙碌」。service 裡找不到商品時寫的是 throw new Error('找不到商品')。怎麼修？

✓ 一般的 Error 會變成不洩漏細節的 500；要回特定狀態碼就丟 HttpException 的子類別。前端靠狀態碼決定顯示「已下架」還是「系統忙碌」。a 錯在回傳 null 是 200 加空內容，前端每支 API 都要另外判斷，監控也看不出錯誤。（第 2 課）

練習 12：團隊的 CI 只跑 npm test。有人改了 ProductsService.findOne 的參數型別，卻漏改一個呼叫它的地方，測試全綠就合併了。CI 該加哪一步才擋得下來？

✓ Vitest 只轉譯、不檢查型別，型別錯誤的程式照樣會跑；nest build 用 tsc，會檢查型別。CI 同時跑測試和 build，build 不過就不能合併。a 錯在覆蓋率量的是有沒有執行到，跟型別對不對無關。（第 1 課）

練習 13：這個測試寫好之後從來沒紅過，連把 OrdersService.create 的總額算錯都還是綠的。為什麼？

const moduleRef = await Test.createTestingModule({
  providers: [
    { provide: OrdersService, useValue: { create: vi.fn().mockResolvedValue({ total: 220 }) } },
    { provide: ProductsService, useValue: products },
  ],
}).compile()
const service = moduleRef.get(OrdersService)
expect(await service.create({ productId: 1, quantity: 2 })).toEqual({ total: 220 })

✓ 只替換依賴，被測的 class 要放真的 OrdersService，讓 Testing Module 幫它注入替身。確認的方法是把程式改壞一行，看測試會不會紅。b 錯在 toEqual 比的就是內容，220 和 210 不會相等。（第 5 課）

練習 14：快樂時光（台北時間 14:00–16:00 飲品八折）的測試在你的電腦上都過，CI 上卻有時紅、有時綠。最先懷疑什麼？

✓ 測試看真實時鐘，就是今天過、明天不過；CI 多半是 UTC，getHours() 算的不是台北時間。把時鐘做成 provider（CLOCK）或用 vi.setSystemTime，時間寫成帶 +08:00 的固定瞬間。a 錯在沒 await 的斷言在 Vitest 5 會直接失敗，不是時好時壞。（第 3、5 課）
