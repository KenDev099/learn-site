階段 5：上線、維運與架構（資深） · 第 25 課

除錯與效能：從錯誤訊息到事件迴圈

週五下午，你接手同事留下的咖啡店 API 分支：分店菜單、下單、集點、收據防偽碼報表都寫好了，但它在 Vitest 裡一跑就報「找不到依賴」。你修到測試全部通過，部署之後執行 node dist/main.js，程式一啟動就結束，log 只有一行 ReferenceError。好不容易上線了，又冒出兩件事：尖峰時每個請求都比以前慢，剛下的訂單還會憑空消失；下午尖峰時段有人開了「收據防偽碼」報表，報表算完之前，所有人的點餐都卡住。

這些問題盯著程式碼看很難找到原因。這一課就用這一個專案（也就是練習的 work/25/），照一套固定的除錯步驟，從「起不來」一路修到「跑得動、不卡人」。學完你會有接到 bug 時的固定動作：怎麼讀 Nest 的錯誤訊息、為什麼測試會過正式環境卻壞、怎麼用量測證明效能問題出在哪，而不是靠猜。

這課的路線：
  1. 接手的第一步：不靠猜的除錯流程，以及這個專案的「重現指令」是什麼。
  2. 兩種起不來：Vitest 裡 Nest 說找不到依賴時，訊息的每一段各告訴你什麼；測試全過、部署後卻 ReferenceError，是循環 import 在 build 之後才爆開。
  3. 錯誤訊息不夠用時：讓程式停下來看變數，到套件原始碼裡找出丟錯的那一行。
  4. 變慢與卡住：依請求切換分店的 provider 為什麼拖慢整條注入鏈、讓訂單消失；一張報表為什麼讓所有人的點餐都卡住。
  5. 修完之後有人提議「換 Fastify、SWC 就會變快」：換之前先量什麼。
這課會用到：
  • 第 4 課的 exports／imports：provider 只在自己的模組裡可見，別的模組要用，得由提供的模組 exports、使用的模組 imports，否則啟動時就報找不到依賴。
  • 第 1 課的三條執行路徑：nest build 用 tsc 編譯並檢查型別，Vitest 只轉譯不檢查，兩邊的結果可能不一樣。
  • Node 課第 4 課的 ESM 載入順序：每個模組只執行一次，先沿著 import 走到底，再從最深的檔案開始執行。
  • Node 課第 7 課的事件迴圈：所有 JavaScript 都在一條主執行緒上跑，一段同步程式沒跑完，其他請求都得等。

接手一個起不來的專案，第一步做什麼？

看到一個起不來的專案，新手最常見的做法是「看到錯誤 → 猜一個原因 → 改 → 再跑」，猜錯就再猜。問題簡單時這樣還行，問題一複雜就會改了一堆地方，最後程式好了，卻不知道是哪一處改動真正有用；更常見的是順手改壞了別的地方，引入新的 bug。這個專案至少有三個問題疊在一起，用猜的會很痛苦。

資深工程師用的是一套固定的步驟。它的核心想法是：每一步都要有證據，每一次只改一個地方，改完就重跑同一個指令看結果有沒有變。

  1. 穩定重現：找到一個每次執行都會出錯的指令或請求。有了它，你才能在改完之後判斷「修好了」還是「這次剛好沒出現」。重現的範圍越小越好，用最少的程式、最少的步驟讓問題出現，這叫最小重現（minimal reproduction）：範圍小，可能的原因就少，也方便貼給同事或套件作者。偶爾才出錯的問題（例如兩個請求同時進來才會發生的並發問題），要先想辦法讓它每次都出現，像第 3 課的測試讓金流故意等 100 ms，把兩個請求重疊的時間拉長。
  2. 一字一句讀錯誤：錯誤訊息和堆疊（stack trace，錯誤發生時「誰呼叫了誰」的清單，最上面是丟錯的那一行）通常已經寫了答案。讀完整段，不要只看第一行：Nest 的錯誤會把「哪個參數、在哪個模組」寫在後半句，下一節就會看到。
  3. 列出假設：把所有可能的原因寫下來，而且每個假設都要能用一個實驗證明或推翻，例如「如果是少了 exports，加上之後這個錯誤就會換成下一個」。不能驗證的假設（「可能是環境怪怪的」）對縮小範圍沒有幫助。
  4. 縮小範圍：可能的地方很多時，用二分法（bisect），每次排除一半。例如「昨天還好好的」，就用 git bisect：你告訴它哪個 commit 是好的、哪個是壞的，它切到兩者中間讓你試，試完標記好或壞，再切一半。每試一次範圍就減半，2 的 10 次方是 1024，所以十次就能從一千個 commit 縮到一個。「十個模組裡有一個壞了」也一樣，先拿掉五個看問題還在不在。
  5. 修好之後寫一個會失敗的測試：先確認這個測試在修好之前會失敗、修好之後會通過，它才真的鎖住了這個 bug。修好前就會通過的測試，什麼都沒證明。

套到這個專案，第 1 步已經有現成的答案：node check.mjs nestjs 25 會在 Vitest 裡啟動整個應用程式，npm run build 之後的 node dist/main.js 則是正式環境的啟動方式。這兩個指令每次執行都會出同樣的錯，接下來每改一處就重跑一次。這門課每一題的隱藏測試，其實就是出題時做完第 5 步留下來的東西。

💡 實務上：接到 bug 回報，第一件事是要到重現條件
客服轉來「有客人說點餐失敗」，這句話沒辦法直接修。先問清楚：哪個時間、哪間分店、打哪個 API、帶了什麼資料、回應的狀態碼和 request id（第 24 課的 log 用它串起來）。拿到之後在本機或測試環境重現，把重現步驟寫進 issue，接手的人和 PM 才知道問題範圍。資深工程師不會直接在正式環境改程式碰運氣；就算要先上緊急修補，也會補上鎖住這個 bug 的測試，並在 PR 說明「原因是什麼、怎麼確認修好了」。正式環境的事故處理與檢討，系統設計課第 21 課會再談。

重現指令有了，第 2 步是讀錯誤。這個專案在 Vitest 裡第一次跑，就給了一段 Nest 的錯誤訊息。

Vitest 裡就起不來：Nest 說找不到依賴，問題在哪？

先回想 Nest 啟動時在做什麼。第 3 課講過，Nest 會讀每個 provider 的建構子需要哪些參數。Nest 怎麼知道建構子要哪些參數？TypeScript 編譯時會把每個參數的 class 記在 class 身上，這份紀錄叫 metadata，Nest 啟動時就是讀它。讀到參數之後，在這個 provider 所屬的模組裡，找出每個參數對應的實例。模組裡「找得到」的範圍，是自己的 providers，加上 imports 進來的模組所 exports 的東西（第 4 課）。只要有一個參數找不到，整個應用程式就不會啟動，而 Nest 會告訴你是哪一個。這個專案在 Vitest 裡印出的是這一句（NestJS 12.3.2）：

Nest can't resolve dependencies of the OrdersService (?, StampsService). Please make sure that
the argument ProductsService at index [0] is available in the OrdersModule module.

第 4 課逐段讀過這個訊息。照上一節「一字一句讀完」的原則，它其實回答了三個問題：

  • 哪一個參數失敗：括號裡是 OrdersService 建構子的參數清單，解析成功的寫名稱，失敗的寫 ?。(?, StampsService) 表示第 0 個參數失敗、第 1 個沒問題。後半句的 index [0] 說的是同一件事（從 0 算）。
  • 在哪個模組找：OrdersModule。修法一定在這個模組的 imports，或提供者那一邊的 exports。在 OrdersModule 的 providers 再寫一次 ProductsService 雖然能讓錯誤消失，卻會多出第二個實例，兩邊的狀態從此不同步。
  • 參數名稱有沒有出現：訊息寫出了 ProductsService，代表 Nest 知道要找什麼、只是在這個模組裡找不到，問題出在模組的 import／export。這個專案裡，是 ProductsModule 沒有把 ProductsService 放進 exports。

修好這一個，重跑重現指令，錯誤換成了另一句。這次參數名稱不見了：

Nest can't resolve dependencies of the OrdersController (?). Please make sure that the argument
at index [0] is available in the current module.

Potential solutions:
- The dependency at index [0] appears to be undefined at runtime
- This commonly occurs when using 'import type' instead of 'import' for injectable classes

這是另一種問題。Nest 連要找什麼都不知道，因為 metadata 裡記的就是 undefined。第 3 課講過原因：import type 只匯入型別，編譯後整行 import 會被刪掉，執行時根本沒有那個 class 可以記進 metadata。官方的常見錯誤文件也說明，該位置的依賴在執行時是 undefined 或 Object 時，訊息就不會寫出名稱。所以看到沒有名稱的 ?，先檢查那個檔案的 import，而不是模組的 exports。

如果兩種情況都對不上，就設 NEST_DEBUG 環境變數（任何非空字串都可以），讓 Nest 印出解析每個依賴時，在哪個模組找、找到了沒：NEST_DEBUG=1 node dist/main.js，輸出的讀法在第 4 課。

兩處都修好之後，Vitest 裡的測試全部通過。照理說可以部署了，但部署後的 node dist/main.js 一啟動就結束。

測試全過，為什麼 node dist/main.js 一啟動就 ReferenceError？

部署後的 log 是這樣：

file:///…/dist/orders/orders.service.js:40
        StampsService])
        ^

ReferenceError: Cannot access 'StampsService' before initialization
    at file:///…/dist/orders/orders.service.js:40:9

先讀懂這句錯誤本身。JavaScript 裡用 let、const、class 宣告的名稱，從它所在的範圍一開始就「存在」，但要等執行到宣告那一行才有值。在這之前讀它，就會丟出 Cannot access 'X' before initialization：

console.log(x)   // ReferenceError: Cannot access 'x' before initialization
let x = 1

從範圍開始到宣告那一行執行之間的這段時間，叫做 TDZ（temporal dead zone，暫時性死區）。所以這句錯誤的意思是：orders.service.js 第 40 行讀了 StampsService，但定義 StampsService 的那一行還沒執行到。

為什麼還沒執行到？因為這兩個檔案循環 import（circular import）：orders.service.ts import stamps.service.ts（下單後要算集點），stamps.service.ts 又 import orders.service.ts（集點數是從訂單算出來的）。回想 Node 課第 4 課：ESM 會先沿著 import 走到底，再從最深的檔案開始執行，每個檔案只執行一次。假設先被載入的是 stamps.service.js，Node 沿著它的 import 走進 orders.service.js，又在那裡遇到 stamps.service.js。它已經在載入中，Node 不會再進去一次，於是先執行手上的 orders.service.js。這時 stamps.service.js 一行都還沒執行，裡面的 export class StampsService 正處在 TDZ。錯誤指在 orders.service.js，正是這種情況。

平常循環 import 不一定會出事，因為大部分程式要等之後被呼叫時才讀另一個 class，那時兩個檔案都執行完了。問題在裝飾器：tsc 開了 emitDecoratorMetadata 之後，會在 class 定義的當下執行這一行，把建構子參數的 class 記下來，Nest 才知道要注入什麼：

__metadata("design:paramtypes", [ProductsService, StampsService])

這一行在檔案載入時就讀了 StampsService，剛好落在 TDZ 裡。錯誤訊息裡的 StampsService]) 就是它。

那為什麼 Vitest 會過？Vitest 不是用 Node 原生的方式載入 ESM，而是用 Vite 的模組執行器，它把 import 改寫成「讀某個物件的屬性」。另一個檔案還沒執行完時，讀到的是 undefined，不會丟錯；轉譯器產生的 metadata 遇到 undefined 就記成 Object，實際要注入什麼再交給 forwardRef。本課程用 Vitest 5.0.5 實測，OrdersService 的 design:paramtypes 在測試裡是 [ProductsService, Object]。同一份程式，兩種載入方式，一個安靜地記成 Object，一個直接丟錯，所以只在 Vitest 裡驗證抓不到這個錯。

專案裡已經有 forwardRef，為什麼還是壞？

這個專案兩邊的建構子都寫了 @Inject(forwardRef(() => StampsService))。forwardRef 是 Nest 的工具：它不直接給 class，而是給一個「之後再呼叫」的函式，讓 Nest 等兩邊都定義好了才去讀。它解決的是 Nest 容器裡「A 要 B、B 要 A，誰先建」的問題，所以 Nest 那一關過了。但 __metadata 那一行是 JavaScript 載入檔案時就執行的，發生在 Nest 開始建容器之前，forwardRef 管不到。

NestJS 的 SWC 文件提供了一個繞過的寫法：宣告 type WrapperType<T> = T，建構子參數寫成 WrapperType<StampsService>。型別經過一層別名，tsc 推不出是哪個 class，metadata 就記成 Object，載入時不再讀 StampsService，程式能啟動。實際要注入什麼交給 @Inject(forwardRef(() => StampsService))。

它能讓程式啟動，但沒有解決設計問題：兩個 service 還是互相依賴，任何一邊改動都要同時想另一邊，測試時兩個都要準備。forwardRef 只是讓 Nest 晚一點解析依賴，不會讓循環消失。根本的修法是讓依賴只往一個方向，常見的三種做法：

做法例子適合
改由一邊主動通知OrdersService 下單後呼叫 stamps.add(customer)，集點數由 StampsService 自己記，不再回頭問訂單其中一邊本來就是「事情發生後」才需要知道
抽出共用的部分兩邊都需要的查詢搬進第三個 provider，兩邊都依賴它兩邊都要讀同一份資料
用事件像第 21 課付款後發出 order.paid 那樣，訂單模組只發事件，集點模組用 @OnEvent 監聽兩個模組不該知道彼此，第 26 課會用它整理模組邊界

這個專案的集點本來就是「下單之後」才需要知道，第一種最簡單：StampsService 不再 import 訂單，循環就斷了。

循環 import 不是 Vitest 和正式環境唯一的差異。另外兩個常見的：import 路徑少了 .js，Vitest 會自動補上，tsc 在 nodenext 下卻報 TS2307: Cannot find module './app.service'（第 1 課）；Vitest 只轉譯不檢查型別，用 @ts-ignore 蓋掉的錯誤在測試裡完全看不出來。三者有同一個解法：在 CI 裡照正式環境的方式真的 build 一次、啟動一次。升級到 NestJS 12 時，lifecycle hook 的呼叫順序也可能讓測試和以前不一樣，細節見課末的補充與查表。

💡 實務上：CI 一定要跑「建置＋實際啟動」的冒煙測試（smoke test）
冒煙測試指最基本的檢查：程式能不能啟動、最簡單的請求有沒有回應。CI 跑完 Vitest 之後，再照正式環境的方式 nest build、node dist/main.js，打一次 /health，回 200 才算過。它跑得快、寫一次就好，擋下的卻是「整個服務起不來」這種最嚴重的事故。如果部署用 Docker，就直接對建好的映像檔做這件事，連打包時漏掉的檔案也一起抓到。這個專案的週五事故，有它就會在合併前被擋下。

回頭看這一節，有兩件事不是從錯誤訊息直接讀出來的：Vitest 裡 metadata 記成了 Object，以及丟錯的是 __metadata 那一行。錯誤訊息不夠用的時候，得有辦法自己去看。

錯誤訊息不夠用時，怎麼親眼看程式在做什麼？

最直接的方法是讓程式停在某一行，看當下每個變數的值。這就是除錯器（debugger）：你在某一行設中斷點（breakpoint），程式執行到那裡就暫停，你可以檢查變數、一行一行往下走。Node 課第 6 課用過 node --inspect-brk：--inspect 讓 Node 開放除錯連線，-brk 讓它停在第一行等你連上，不然程式可能在你連上之前就跑完或當掉了。在 NestJS 專案裡，依要除錯的程式選指令：

要除錯的程式指令
開發中的應用程式npm run start:debug（也就是 nest start --debug --watch），再用 Chrome 開 chrome://inspect 或 VS Code 的 JavaScript Debug Terminal 連上
編譯後的程式node --inspect-brk dist/main.js：停在第一行，等你連上；這門課開了 sourceMap，中斷點可以下在 .ts
Vitest 測試npx vitest --inspect-brk --no-file-parallelism（Vitest 官方的除錯指令）：只用一個 worker，才能逐步執行

以上一節的 ReferenceError 為例：用 node --inspect-brk dist/main.js 啟動，在 dist/orders/orders.service.js 的 __metadata 那一行下中斷點，停下來時就能看到 StampsService 還不能讀。Vitest 那一邊，用 vitest --inspect-brk 在測試裡停下來，檢查 OrdersService 的 design:paramtypes，就會看到第二個是 Object。

還有一個常被忽略的工具：讀套件的原始碼。node_modules/@nestjs/core/ 裡的 .js 就是實際在執行的程式，不是文件，不會過時。拿錯誤訊息裡一段固定的字串去搜尋，就能找到丟出它的地方：

$ grep -rn "is marked as a scoped provider" node_modules/@nestjs/core --include='*.js'

找到之後在那一行下中斷點，看是哪個條件成立。文件沒寫清楚的行為（例如關機時各個 hook 的順序、某個錯誤代碼什麼時候出現），這樣查最準。這門課的不少說明也是這樣查證的。

上面搜尋的這句 is marked as a scoped provider，不會出現在啟動 log 裡，要等測試用 app.get() 取 provider 時才會看到。它指向這個專案剩下的另一類問題：程式能啟動了，可是每個請求都變慢，訂單還會消失。

加上分店之後，為什麼每個請求都變慢、訂單還會消失？

咖啡店有兩間分店，菜單依請求的 X-Store-Id 標頭決定。要理解問題，先回到 provider 預設怎麼建立。第 3 課講過，Nest 的 provider 預設是 singleton：啟動時建立一個實例，之後所有請求共用它。這很省，但也表示 provider 本身不知道「現在是哪個請求」。同事想讓 service 讀到這次請求的標頭，直覺的寫法是改成 request scope：每個請求進來時建立一個新的實例，就能注入 REQUEST 物件：

@Injectable({ scope: Scope.REQUEST })
export class StoreContext {
  constructor(@Inject(REQUEST) private readonly req: Request) {}
  get storeId(): number { return Number(this.req.get('x-store-id') ?? 1) }
}

功能是對的，代價卻不只這一個 class。想想 ProductsService 依賴 StoreContext：如果 ProductsService 還是整個應用程式一個，它手上那個 StoreContext 就只會是某一個請求的，其他請求讀到的分店全錯。所以 Nest 只能讓 ProductsService 也跟著每個請求重建，再往上，依賴它的 controller 也一樣。官方 injection scopes 文件說明的就是這件事：依賴 request-scoped provider 的 class 也會變成 request-scoped，一路往上傳到 controller。這叫 scope 冒泡（scope bubbling）。

冒泡之後，開場的兩個症狀都解釋得通了，還多了一個不容易發現的副作用：

  • 變慢：實際量（這一課的起始專案），在 ProductsService 的建構子計數，打 5 次 GET /menu，它被建立了 5 次。每個請求都要重新建立整條鏈的物件。官方文件的評估是：設計良好的應用程式，延遲增加不應超過約 5%；但依賴鏈越長、請求量越大，成本越明顯。成本在哪裡？每個請求都要重建整條鏈的物件，請求結束後這些物件全變成垃圾，等 GC 回收；建立的物件數是「鏈的長度 × 請求數」，GC 的壓力跟著一起上升。離峰時幾乎感覺不到，尖峰時才會明顯，開場說的「變慢」指的就是尖峰時段。
  • 訂單消失：起始專案的 OrdersService 用陣列存訂單。它變成每個請求一個新實例之後，陣列每次都是空的：上一個請求存進去的訂單，跟著那個實例一起被丟掉了。
  • lifecycle hook 不會觸發：request-scoped provider 不會收到 onModuleInit 這類 lifecycle hook，原本寫在裡面的初始化不會執行。

request scope 還有一個測試時就能看到的特徵：app.get() 拿不到它，因為「整個應用程式那一個實例」根本不存在。這就是上一節搜尋的那句錯誤：

InvalidClassScopeException: OrdersService is marked as a scoped provider. Request and
transient-scoped providers can't be used in combination with "get()" method. Please, use
"resolve()" instead.

練習 2 的測試就是用這個方法確認整條鏈回到 singleton。那麼，不用 request scope，service 要怎麼知道這次請求是哪間分店？

改用 AsyncLocalStorage：provider 維持 singleton，值跟著請求走

官方文件的建議是：除非真的必要，provider 都用預設的 singleton；每個請求不同的值（目前使用者、租戶、語系）放在 AsyncLocalStorage 裡。第 24 課用它做過 RequestContext：als.run(store, fn) 執行 fn 時，fn 裡面以及它之後所有的非同步工作，呼叫 getStore() 都會拿到同一份 store；另一個請求在自己的 run 裡，拿到的是自己那一份。物件只有一個，值卻是每個請求各自的。分店也照這個做法：

  1. StoreContext 拿掉 scope 和 REQUEST，改持有一個 AsyncLocalStorage<{ storeId: number }>，提供 run(storeId, fn) 和 get storeId()（讀 getStore()）。
  2. 寫一個 middleware，讀 X-Store-Id，呼叫 context.run(storeId, next)：之後的 guard、pipe、handler、service，包括所有 await 之後的程式，讀到的都是這個請求的值。
  3. 在模組的 configure() 用 forRoutes('*') 套用到所有路由。

這樣 StoreContext 回到 singleton，依賴它的 ProductsService、OrdersService 也就不再冒泡，訂單陣列不會再每次清空。

不要用模組層級的變數或 singleton 的欄位存「目前的分店」。請求 A 設成 1 號店，在 await 查資料庫時，請求 B 進來設成 2 號店；A 回來讀到的就是 2。一次一個請求時完全看不出來，跟第 3 課的 currentCart 是同一種 bug。AsyncLocalStorage 的值跟著非同步呼叫鏈走，不會被別的請求蓋掉。

什麼時候 request scope 才合理？例如每個請求要用不同的資料庫連線、而且無法改成參數傳遞。多租戶系統另有官方的折衷做法，放在課末的補充與查表。大多數情況，AsyncLocalStorage 已經足夠。

💡 實務上：code review 看到 Scope.REQUEST 先問為什麼
常見的情況是有人為了拿「目前登入的使用者」或「目前分店」，在某個 service 加上 request scope，PR 只改了幾行，影響卻是整條依賴鏈，就像這個專案的分店功能。審查時先問：這個值能不能從 controller 當參數傳下去，或放進 AsyncLocalStorage？真的需要時，請對方說明哪些 class 會跟著變成 request-scoped、有沒有欄位會因此每次清空。這類改動最好附上改前改後的量測，而不是只寫「應該影響不大」。

菜單恢復了速度，訂單也不再消失。剩下最後一個症狀，而且它跟 DI 完全無關：下午有人開了報表，所有人的點餐都卡住。

一張報表，為什麼讓所有人的點餐都卡住？

報表 GET /reports/receipts-signatures?date=2026-11-01 要替當天 200 張收據各算一個防偽碼，用的是 pbkdf2Sync：反覆雜湊幾千次、故意算很慢的函式，跟存密碼用的是同一類（Node 課第 7 課看過）。在一台 M1 Pro 筆電上，200 次大約要 0.4 秒；機器同時在忙別的事時，會拉長到 1～2 秒。

為什麼一個人的報表會卡住別人？Node 用一條主執行緒跑所有 JavaScript。請求進來、計時器到期，都只是排進事件迴圈的待辦清單，要等主執行緒手上的事做完才輪得到。pbkdf2Sync 是同步函式，它算完之前主執行緒一直被佔著，其他請求連進來了也沒人處理，連 /health 都卡住，負載平衡器可能因此判定服務掛了。

這種卡住可以量化。設一個每 20 ms 該執行一次的計時器，如果主執行緒被佔住 400 ms，這個計時器就會晚 400 ms 才執行。這個「本來該馬上執行的東西，實際晚了多久」叫做事件迴圈延遲（event loop delay），它直接反映「其他請求要多等多久才開始被處理」。Node 內建量測它的工具：

import { monitorEventLoopDelay } from 'node:perf_hooks'

const h = monitorEventLoopDelay({ resolution: 20 })   // 每 20 ms 取樣一次
h.enable()
setInterval(() => {
  // 單位是奈秒，除以 1e6 變成毫秒
  logger.log('event loop delay', { p99: h.percentile(99) / 1e6, max: h.max / 1e6 })
  h.reset()
}, 10_000).unref()

這段程式每 10 秒記一次這段期間的延遲，然後歸零重算。看 p99（100 次取樣裡最慢的那 1 次左右）和 max，而不是平均：一次卡 400 ms 被幾百次正常的取樣平均掉，數字會很好看，但卡住的那一刻正是客人點不了餐的時候。最後的 .unref() 讓這個計時器不會擋住程式結束。

把它接上第 24 課的結構化 log 或指標，平常 p99 應該只有幾毫秒；突然跳到幾百毫秒，就去 CPU profile 找是哪個函式（Node 課第 23 課）。常見的元兇：pbkdf2Sync、bcrypt 的同步版、JSON.parse／JSON.stringify 幾十 MB 的資料、一次處理幾萬筆的同步迴圈、寫得不好的正規表示式。

知道原因之後，直覺的修法是「把它改成非同步」。但改法選錯，延遲一點都不會降。

為什麼改成 async 還是會卡？

最常見的誤解是把函式改成 async，或先 await new Promise(r => setTimeout(r, 0)) 再算。async 只是讓函式回傳 Promise，裡面的同步迴圈還是在主執行緒一口氣跑完；await 只有在等一個還沒完成的 Promise 時才會讓出主執行緒，而同步迴圈裡沒有任何這樣的等待。setTimeout 也只是晚一點開始，開始之後照樣卡住一樣久。要不卡，計算必須真的離開主執行緒，或切成小段、每段之間讓出時間。能讓計算離開主執行緒的地方之一是 thread pool：Node 底層的 libuv 準備的一組背景執行緒，專門做檔案讀寫、加密、壓縮這類工作，算完再把結果交回主執行緒。常見做法有這幾種：

做法怎麼做適合
改用非同步 APIcrypto.pbkdf2、scrypt、zlib 的非同步版會丟到 libuv 的 thread pool（預設 4 條執行緒）計算Node 本來就有非同步版的運算，最簡單
切成小塊每處理一小批（每批只花幾毫秒）就 await setImmediate()（從 node:timers/promises import）讓出主執行緒純 JavaScript、單塊很小的工作；總時間不會變短
worker_threads把運算放到另一條執行緒（Node 課第 9 課）自己寫的大量運算，沒有現成的非同步版
丟進佇列請求只建立工作，背景 worker 算完再通知（第 20 課）算很久、使用者不必當場等結果

pbkdf2 有非同步版，所以這份報表選第一個：用 util.promisify(crypto.pbkdf2) 包成回傳 Promise 的函式，200 個一起丟出去再 Promise.all，結果順序跟原本一樣。thread pool 只有 4 條，同時做的事情多了一樣要排隊（Node 課第 7 課），報表本身不一定變快，但主執行緒是空的，其他請求不受影響。

💡 實務上：報表、匯出、匯入是最常卡住事件迴圈的地方
後台的「匯出本月訂單 CSV」、「上傳 Excel 批次匯入商品」、「產生收據 PDF」，上線初期資料少看不出問題，幾個月後資料量變大，就變成「每天下午某個時段整個 API 變慢」，就像這份防偽碼報表。寫這類功能時先問：資料量一年後會長到多大？使用者需要當場拿到結果嗎？不需要就直接走佇列，做完再通知或給下載連結。上線後把事件迴圈延遲放進監控和告警，比等客服回報「點餐很慢」早發現。

三個問題都修好了。週一的檢討會上，有人提議「乾脆換成 Fastify、改用 SWC 編譯，整體會快很多」。

「換 Fastify、SWC 就會變快」：換之前先量什麼？

這兩個建議都有道理，但各自解決的是特定的問題。先弄清楚它們在換什麼：

  • 換成 Fastify 轉接器（@nestjs/platform-fastify）：Nest 本身不處理 HTTP 連線，而是架在一個 HTTP 函式庫上，預設是 Express，換成 Fastify 只換掉這一層。Fastify 的 HTTP 層比 Express 快，高吞吐量的服務有幫助。但大部分 API 的時間花在資料庫和外部呼叫，HTTP 層只占一小部分；而且為 Express 寫的 middleware（例如 cookie-parser、helmet 的用法）要換成 Fastify 的版本。先量出瓶頸真的在 HTTP 層再換。
  • 用 SWC 編譯（nest start -b swc）：SWC 是用 Rust 寫的編譯器，比 tsc 快很多，開發時重新編譯更快。它改善的是開發時等編譯的時間，不是 API 回應的速度。官方文件說明 SWC 本身不做型別檢查，要加 --type-check（或 nest-cli.json 的 compilerOptions.typeCheck: true）才會另外跑 tsc --noEmit；它對循環 import 的處理也更差，這課前面的 TDZ 更容易出現，WrapperType 這個寫法就出自 SWC 文件。

回到這個專案的經驗：慢的原因一個是 request scope 讓整條鏈重建，一個是同步計算卡住主執行緒，兩個都跟 HTTP 層或編譯器無關，換了也不會好。這一課用過的量測就是判斷依據：事件迴圈延遲高，去 CPU profile 找函式；請求延遲高但事件迴圈正常，多半是在等資料庫或外部服務；兩者都正常、而請求量大到 HTTP 層本身成為瓶頸，才輪到 Fastify。兩個都是「先量測，確定是瓶頸才動」，沒有量測就換框架或工具，多半只換來新的問題。

練習

在 learn/ 執行 node check.mjs nestjs 25 建立 work/25/。這一題不需要 Docker。專案有分店菜單 GET /menu、下單 POST /orders、集點 GET /stamps/:customer、報表 GET /reports/receipts-signatures?date=YYYY-MM-DD、GET /health。目前它在 Vitest 和 node dist/main.js 都起不來。每修一處就重跑一次 check.mjs，照除錯流程讀錯誤訊息。

練習 1：這個專案有三個啟動問題：某個模組沒有 export 別人要注入的 provider（要在提供它的模組加 exports，不是在別的模組再寫一次 providers）、某處用 import type 匯入要注入的 class、OrdersService 和 StampsService 循環 import。先用錯誤訊息找出前兩個並修好，讓 Vitest 裡的測試通過；再讓 npm run build 之後 node dist/main.js 能啟動。

循環 import 要真的拆掉：讓依賴只往一個方向（例如 OrdersService 下單後呼叫 StampsService 記一點，集點數由 StampsService 自己記），兩邊的 forwardRef 都拿掉。POST /orders 的回應是訂單加上這位顧客目前的集點數 stamps，GET /stamps/:customer 回 { customer, stamps }。測試會掃描 src/ 的 import（包括動態的 import()），有循環或還留著 forwardRef 就不通過，所以只加 WrapperType 過不了；StampsService 要留在 src/stamps/stamps.service.ts。

練習 2：先完成練習 1。StoreContext 注入 REQUEST 讀 X-Store-Id，讓 ProductsService、OrdersService 都變成 request-scoped。改用 AsyncLocalStorage：StoreContext 變回 singleton，提供 run(storeId, fn)，storeId 從 getStore() 讀；在 store.module.ts 寫一個 middleware（沒帶標頭就是 1 號店），讓 StoreModule 實作 NestModule，用 forRoutes('*') 套用到所有路由。ProductsService 不用改。

測試會用 app.get() 取得這三個 provider（request-scoped 會丟錯），並加一條測試自己的路由，在 await 前後各讀一次 storeId，同時送出 1 號店和 2 號店的請求，所以用模組層級變數存目前分店的寫法過不了。

練習 3：GET /reports/receipts-signatures 用 pbkdf2Sync 算 200 個防偽碼，計算期間其他請求全部卡住。改成不會卡住事件迴圈的寫法，結果（順序、內容）要跟原本完全一樣。

測試會先在主執行緒算一次同步版，量出這台電腦要多久（記為 T）。接著在報表計算期間用 monitorEventLoopDelay 量事件迴圈延遲，並每 20 ms 打一次另一個路由，兩者都要低於 T 的四成。卡住主執行緒的寫法延遲會接近 T，所以過不了；查詢的日期跟這頁的例子不同，預先算好的結果也過不了。

練習 4：錯誤訊息是 Nest can't resolve dependencies of the OrdersService (ProductsService, ?). Please make sure that the argument StampsService at index [1] is available in the OrdersModule module. 哪個依賴有問題，該去哪裡修？

✓ 括號裡的 ? 和 index [1] 都指向第二個參數 StampsService；ProductsService 有名稱、沒有問號，代表它解析成功了（a 錯）。in the OrdersModule module 說明是在這個模組找不到，所以看 OrdersModule 的 imports，以及 StampsModule 有沒有 exports。OrdersService 本身沒有 @Injectable() 時，Nest 讀不到它的參數清單，不會只標出其中一個 ?（c 錯）。

練習 5：同一份程式，Vitest 全部通過，nest build 之後 node dist/main.js 卻出現 ReferenceError: Cannot access 'StampsService' before initialization。最可能的原因和正確的處理是？

✓ Vitest 用 Vite 的模組執行器，載入 import 的方式和 Node 不同，測試通過不代表正式環境能啟動（b 錯）。Cannot access … before initialization 是 TDZ，典型原因是循環 import，跟 Node 版本無關（a 錯）。forwardRef 只處理 Nest 容器的解析順序，不改變 JavaScript 模組的載入順序，這個專案兩邊早就加了 forwardRef 還是壞（d 錯）。

練習 6：同事把報表裡 CPU 很重的同步迴圈包進 async 函式，說「這樣就不會卡住其他請求了」。對嗎？

✓ JavaScript 的 async／await 不會開新的執行緒（b 錯）。await 只是在等 Promise 時讓出主執行緒，但同步迴圈裡沒有任何 await，一開始跑就要跑完才會讓出（c 錯）。用 monitorEventLoopDelay 量一次就能看到，延遲跟同步版的計算時間一樣長。

常見錯誤

  • 沒有穩定重現就開始改程式：不知道哪一處改動真正有用，也無法確認修好了沒。先找到每次都會失敗的指令或測試。
  • 只讀錯誤訊息的第一行：index、模組名稱、參數名稱有沒有出現，答案常在後面幾行。
  • 在使用的模組再寫一次 providers 來消掉 DI 錯誤：錯誤不見了，卻多出第二個實例，兩邊的狀態不同步。在提供它的模組加 exports，使用的模組 imports。
  • 只在 Vitest 裡驗證：循環 import、少了 .js、被 @ts-ignore 蓋掉的型別錯誤都只在 build 或實際啟動時出現。CI 要跑 nest build 加啟動的冒煙測試。
  • 用 forwardRef 或 WrapperType 掩蓋循環依賴：程式能啟動，設計問題還在。讓依賴只往一個方向：一邊主動通知、抽出共用部分，或用事件。
  • 為了拿請求的資料而用 request scope：整條依賴鏈都變成每個請求重建，欄位資料每次消失，app.get() 也拿不到。用 AsyncLocalStorage，provider 維持 singleton。
  • 用模組變數或 singleton 欄位存「這個請求」的值：同時兩個請求就會互相蓋掉，一次一個時完全看不出來。
  • 以為 async 函式不會卡住事件迴圈：同步的計算放在哪裡都在主執行緒。用非同步 API、切小塊、worker_threads 或佇列。
  • 沒量測就換 Fastify、SWC：先用事件迴圈延遲、CPU profile、請求延遲找出瓶頸。SWC 預設不做型別檢查，要加 --type-check。

補充與查表

NestJS 12 的生命週期 hook 順序

升級時也會遇到「測試和以前的行為不一樣」的差異。NestJS 12 的 migration guide 寫明 lifecycle hook 改成依元件的階層順序呼叫，依賴彼此的 provider，onModuleInit、關機 hook 的先後可能跟 v11 不同。升級時要重新檢查「A 一定在 B 之前初始化」這類假設，測試裡也一樣。

多租戶系統的 durable provider

多租戶（multi-tenant，一套系統同時服務好幾個彼此隔開的客戶，例如好幾個品牌的咖啡店）系統，如果真的需要依租戶建立不同的物件，可以考慮官方的 durable provider：讓同一個租戶的請求共用一組物件，不必每個請求都重建。但租戶很多時效果有限，大多數情況 AsyncLocalStorage 已經足夠。

小結

  • 除錯流程：穩定重現 → 讀完整的錯誤 → 列假設 → 二分法縮小 → 修好並寫一個修好前會失敗的測試。每次只改一處，改完就重跑同一個重現指令。
  • DI 錯誤先看 ? 的位置（index）、在哪個模組找、參數名稱有沒有出現；有名稱是模組的 import／export，沒有名稱通常是 import type。分不出來用 NEST_DEBUG。
  • 循環 import 在 nest build 後會因為 decorator metadata 在載入時讀到 TDZ 裡的 class 而 ReferenceError，Vitest 的載入方式看不出來。forwardRef、WrapperType 只讓它啟動，根本解是讓依賴單向；CI 要有 build＋啟動的冒煙測試。
  • 錯誤訊息不夠用時：npm run start:debug、node --inspect-brk dist/main.js、vitest --inspect-brk --no-file-parallelism 讓程式停下來；node_modules 裡的 .js 是最準的文件。
  • request scope 會冒泡到整條依賴鏈：每個請求重建、欄位資料消失、app.get() 拿不到。每個請求的值放 AsyncLocalStorage，provider 維持 singleton。
  • 用 monitorEventLoopDelay 量事件迴圈延遲，看 p99 和 max；CPU 重的工作改用非同步 API、切小塊、worker 或佇列，async 本身不會讓它不卡。
  • Fastify、SWC 都是先量測、確定瓶頸在那一層才換；SWC 加快的是編譯，而且預設不做型別檢查。
