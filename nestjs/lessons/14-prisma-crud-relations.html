階段 3：資料庫（Docker、Prisma 7 ＋ PostgreSQL） · 第 14 課

CRUD、關聯與 Prisma 錯誤

上一課的 GET /products 已經從資料庫讀資料了。這一課的任務是把咖啡店剩下的 API 也接上資料庫：店員在後台新增商品、改價、下架，客人在前台下訂單、查訂單。寫法看起來只是把陣列操作換成 this.prisma.product.create(…)，但照這個直覺寫完就上線，會遇到這四件事：

  • 店員新增一個已經存在的商品名稱，後台跳出「伺服器錯誤」，店員看不出是自己輸入的問題。
  • 後台多加了「成本」欄位，前台菜單的 API 就把成本一起送給所有客人。
  • 訂單寫到一半出錯，資料庫留下一張金額 340、卻沒有任何明細的訂單。
  • 拿鐵漲價後，上個月的訂單金額跟著變了，對帳對不起來。

這一課照 API 被寫出來的順序，一件一件把它們擋下來：先把商品的新增、修改、刪除換成 Prisma，處理它丟出來的錯誤，再決定回應裡該放哪些欄位；接著加上訂單明細，讓一張訂單完整寫入，再讀回來給前端。最後處理 PM 的一個改名需求，看怎麼在不動資料表的情況下完成。

這課的路線：
  1. 把陣列換成 Prisma：每個方法送出哪一句 SQL，找不到資料時回 null 還是丟例外。
  2. Prisma 丟出例外之後：怎麼讓商品撞名時前端拿到 409 和 errorCode，而不是 500（開場第一件事的答案）；為什麼不能「先查有沒有重複再寫」。
  3. 回應裡該有哪些欄位：select 和 include 的差別，成本怎麼不送到前台。
  4. 下訂單：schema 怎麼描述訂單、明細、商品；訂單和明細怎麼一起成功或一起失敗；明細為什麼要存下單當下的單價。
  5. 讀回訂單給前端，以及 PM 的改名需求：@map 讓程式裡的名字改掉、資料表不動。
這課會用到：
  • 第 13 課的 Prisma：schema 描述資料表，migrate dev 產生並執行 migration，service 透過注入的 PrismaService 查資料庫。
  • PostgreSQL 課第 8 課的外鍵與一對多：子表用一個欄位存父表的 id，資料庫保證它指到存在的資料；一個顧客可以有很多張訂單。
  • PostgreSQL 課第 10 課的多對多：訂單和商品靠中間的明細表連起來，明細記下數量和下單當下的單價。
  • 第 8 課的領域錯誤：service 丟繼承 DomainError、帶 code 的錯誤，全域 exception filter 把它轉成對應的 HTTP 狀態碼和固定格式的回應。

把陣列換成 Prisma：每個方法送出什麼 SQL？

先從最單純的部分開始：商品的新增、查詢、修改、刪除。這四種操作合稱 CRUD，取自 Create、Read、Update、Delete 的字首，幾乎每個後台管理頁面背後都是一組 CRUD API。

Prisma Client 的方法看起來像在操作 JavaScript 物件，但它其實是一個翻譯器：你呼叫一個方法，它組出一句 SQL 送給 PostgreSQL，再把結果轉回物件。所以理解 Prisma 最快的方式，是知道每個方法翻成你在 PostgreSQL 課寫過的哪一句 SQL。之後遇到「為什麼這麼慢」「為什麼資料不對」，也都要回到 SQL 這一層才查得出來。商品 API 會用到的五個方法：

Prisma Client送出的 SQL（大致）找不到資料時
product.findUnique({ where: { id: 2 } })SELECT … WHERE id = $1 LIMIT 1回 null
product.findMany({ where: { categoryId: 1 }, orderBy: { id: 'asc' } })SELECT … WHERE category_id = $1 ORDER BY id回 []
product.create({ data: { name, price, categoryId } })INSERT … RETURNING …—
product.update({ where: { id }, data: { price: 120 } })UPDATE … WHERE id = $1 RETURNING …丟出錯誤 P2025
product.delete({ where: { id } })DELETE … WHERE id = $1 RETURNING …丟出錯誤 P2025

表裡最要記住的是最後一欄。findUnique 找不到回 null，update／delete 找不到卻是丟出例外。這個差別有它的道理：findUnique 是一個問題（「id 99 的商品是什麼？」），「沒有」是合法的答案；update 是一個命令（「把 id 99 的價格改成 120」），要改的東西不存在，代表命令失敗了。

對我們的 API 來說，這兩種情況要用不同方式處理。GET /products/99 用 findUnique，拿到 null 時要自己判斷，丟出第 8 課的 ProductNotFoundError；如果忘了判斷，controller 會回傳 null，前端收到 200 和一個空的 body。PATCH /products/99 用 update，Prisma 自己會丟例外，問題變成「誰來接住它」。這是下一節的主題。

還有一個寫列表 API 一定會碰到的規則。前台菜單的 GET /products?categoryId=1 要能依分類篩選，沒帶 categoryId 時回傳全部。Prisma 的規則是：where 裡值為 undefined 的條件會被忽略。所以 findMany({ where: { categoryId } }) 在沒有帶 ?categoryId= 時就是查全部，不用自己寫 if 組條件。

null 的意思則完全不同，它是「這個欄位是空值」。如果欄位允許空值，{ x: null } 會翻成 WHERE x IS NULL。categoryId 不允許空值，傳 null 給它，Prisma 在送出 SQL 之前就會丟出 PrismaClientValidationError 拒絕這個查詢。所以從 query string 解析參數時，沒給的值要保持 undefined，不要轉成 null。

上面表格裡的 SQL 不是猜的。建立 Prisma Client 時打開 query log，Prisma 會在每次送出 SQL 時通知你，內容包括 SQL 本身、參數和花了多久：

const prisma = new PrismaClient({ adapter, log: [{ emit: 'event', level: 'query' }] })
prisma.$on('query', e => console.log(e.query, e.params, `${e.duration}ms`))

這一課列出的 SQL 都是用這個方法實際記錄到的（版本見課末「補充與查表」）。開發時遇到「為什麼這麼慢」「為什麼查了這麼多次」，第一步就是打開它看。表格之外還有 upsert、updateMany、deleteMany 等方法，也整理在課末。

到這裡，商品的 CRUD 寫得出來了。但 update 找不到資料會丟例外，店員新增重複的名稱時資料庫也會拒絕。這些例外沒有人接住，前端會拿到什麼？

Prisma 丟出例外之後，前端拿到什麼？

上一節的 update 找不到資料會丟例外。開場那位新增重複名稱的店員也是同一類情況：products.name 有 UNIQUE 約束，資料庫拒絕這次 INSERT，Prisma 把拒絕轉成例外丟出來。

資料庫拒絕一個操作時，Prisma 丟出的是 Prisma.PrismaClientKnownRequestError。同一個 class 涵蓋很多種失敗，靠它的 code 屬性區分是哪一種。商品和訂單 API 會遇到的是這三個：

代碼意思咖啡店裡什麼時候發生HTTP
P2002唯一值衝突新增或改名時，名稱已經有別的商品在用409
P2003外鍵衝突建立商品時指定的分類不存在；或刪除一個還有訂單明細參照的商品（明細在後面加）409
P2025要操作的資料不存在update／delete 一個不存在的商品 id404

其他代碼（例如死結、違反 CHECK 約束）和每個代碼對應的 PostgreSQL 原始錯誤，整理在課末的查表。

如果什麼都不處理，這些例外一路往外丟，Nest 內建的 exception filter（第 8 課）會把它們全部變成 500。開場那位店員看到的「伺服器錯誤」就是這樣來的：明明是使用者能自己修正的輸入問題（換個名稱就好），卻用了代表「伺服器壞了」的狀態碼，前端也沒辦法針對它顯示有用的提示。

更危險的是另一種「處理」：有人為了讓前端看得懂，寫 message: e.message 把原文回給前端。Prisma 的錯誤訊息是寫給開發者除錯用的，長這樣：

Invalid `this.prisma.product.update()` invocation in
/srv/coffee/src/products/products.service.ts:21:31

  18   update(id: number, dto: UpdateProductDto) {
→ 21     return this.prisma.product.update(
An operation failed because it depends on one or more records that were required but not found. No record was found for an update.

這是 P2025，伺服器上的檔案路徑和原始碼片段都在裡面。P2002 的訊息是 Unique constraint failed on the constraint: `products_name_key`，洩漏了 constraint 名稱；違反 CHECK 約束的錯誤甚至帶著 PostgreSQL 的原始錯誤。第 8 課說過，給客戶端的訊息一律用自己寫的固定文字，原文只進 log。

所以要有人把 Prisma 錯誤「翻譯」成正確的狀態碼和安全的訊息。翻譯分兩層，因為兩層知道的事情不一樣：

  1. service 翻譯有業務意義的錯誤。只有 ProductsService 知道「建立商品撞到 P2002」的意思是「名稱已被使用」，所以由它丟 ProductNameTakenError（errorCode PRODUCT_NAME_TAKEN），前端拿到這個 errorCode，就能在名稱欄位旁邊顯示提示。更新商品撞到 P2025，丟 ProductNotFoundError。
  2. 全域的 PrismaExceptionFilter 接住其他的。service 不可能預想到每一種錯誤。filter 是最後一道防線：service 沒翻譯的 Prisma 錯誤，至少變成正確的狀態碼和固定訊息：P2002 → 409 UNIQUE_VIOLATION、P2003 → 409 FOREIGN_KEY_VIOLATION、P2025 → 404 NOT_FOUND，其他代碼一律 500 INTERNAL_ERROR 並寫 log。

service 這一層的寫法如下（select: productSelect 決定回傳哪些欄位，是下一節的主題，這裡先略過）：

// service：只接自己知道意思的代碼，其他的原樣往外丟
const isPrismaError = (e: unknown, code: string): e is Prisma.PrismaClientKnownRequestError =>
  e instanceof Prisma.PrismaClientKnownRequestError && e.code === code

try {
  return await this.prisma.product.update({ where: { id }, data: dto, select: productSelect })
} catch (e) {
  if (isPrismaError(e, 'P2025')) throw new ProductNotFoundError(id, { cause: e })
  if (isPrismaError(e, 'P2002') && dto.name) throw new ProductNameTakenError(dto.name, { cause: e })
  throw e
}

這段程式有四個地方要看懂，順序由上到下：

  • Prisma 從產生的 client import：import { Prisma } from '../generated/prisma/client.js'。filter 的 @Catch(Prisma.PrismaClientKnownRequestError) 也用同一個 class。
  • return await：少了 await，try 區塊會直接把還沒完成的 Promise 回傳出去，等資料庫真的回報失敗時，try 早就結束了，catch 根本接不到。
  • { cause: e }：原本的 Prisma 錯誤掛在 cause 上，log 裡查得到完整原因，回應裡不會出現（第 8 課）。
  • 依 code 分開處理，不認得的 throw e 原樣丟出去交給 filter。如果偷懶把所有 Prisma 錯誤都當成「找不到」，改名撞名的 P2002 也會變成 404，前端就顯示「商品不存在」，店員會一頭霧水。

為什麼不在 create 之前先查名稱有沒有重複？

看到上面的寫法，很多人會想：與其等資料庫拒絕再 catch，不如在新增之前先查一次，有重複就直接丟錯誤，看起來更直覺：

const taken = await this.prisma.product.findFirst({ where: { name: dto.name } })
if (taken) throw new ProductNameTakenError(dto.name)
return this.prisma.product.create({ data: dto })

只有一個人操作時沒問題。但兩位店員同時按下「新增焦糖瑪奇朵」：兩個請求都先查，都查不到，都去 INSERT。資料庫的 UNIQUE 約束擋下第二個，Prisma 丟出 P2002，而這段程式沒有處理它，第二位店員還是看到 500。問題出在「查」和「寫」是兩句獨立的 SQL，中間別的請求可以插進來。這個空隙只有幾毫秒，但正式環境的請求量夠大，一定會有人剛好碰上。

正確的做法是把「不能重複」交給資料庫的 UNIQUE 約束。約束是在寫入的那一刻由資料庫檢查的，不存在「查完還沒寫」的空隙；程式只負責把 P2002 翻譯成 ProductNameTakenError。先查再寫可以拿來在表單上提早給友善的提示，但不能取代 catch P2002。同樣的道理，「有就更新、沒有就新增」用 upsert（PostgreSQL 課第 31 課的 ON CONFLICT，課末有實際送出的 SQL），不要自己先查。

💡 實務上：前端靠 errorCode 做事，維運靠 log 查原因
後台新增商品撞名時，前端拿到 PRODUCT_NAME_TAKEN 就在名稱欄位下顯示「這個名稱已經有了」，不用去解析訊息文字；同樣的模式也會出現在註冊時 email 重複、優惠碼重複。客服回報「新增商品一直失敗」時，工程師是去 log 找那筆錯誤和它的 cause，而不是請使用者截圖錯誤訊息。所以上線前資深工程師會確認兩件事：回應裡沒有任何原始錯誤文字；每個 500 在 log 裡都找得到完整的原始錯誤。如果某個 409 或 500 突然變多，通常代表前端流程或資料出了問題，值得追。

失敗的情況處理好了，接著回頭看成功的情況：PATCH /products/2 成功時回傳的商品物件，裡面到底有哪些欄位？

回應裡該有哪些欄位？成本為什麼會跑到前台菜單

上一課的菜單 API 用的是 findMany({ include: { category: true } })，把查到的結果直接 return。這一課的 products 表多了 cost_price（成本）欄位，只給店內看。同一段程式不動，前台菜單 API 現在回傳的是：

[{ "id": 2, "name": "拿鐵", "price": 110, "costPrice": 35, "isAvailable": true,
   "categoryId": 1, "createdAt": "2026-10-01T02:00:00.000Z", "category": { "id": 1, "name": "咖啡" } }]

成本出現在回應裡，是因為 include 的意思是「這張表的全部欄位，再加上指定的關聯」。表多一欄，查詢結果就多一欄，直接 return 的 API 也就多送一欄。

回傳了前端用不到的欄位，叫做 over-fetching。它的代價有兩種：輕的是浪費頻寬；重的是把不該公開的資料送出去，像這裡的成本，或顧客的電話。最麻煩的是它「之後才發生」：寫 controller 的時候 products 還沒有 cost_price，三個月後有人在 schema 加了這一欄、跑了 migration，菜單 API 就默默開始外洩，而這次改動根本沒碰到 API 的程式碼，code review 時也很難看出來。

要讓回應不受資料表變動影響，查詢時就要明確列出要哪些欄位。Prisma 控制回傳內容的選項有兩個：

includeselect
意思全部欄位，再加上指定的關聯只拿列出來的欄位（關聯也可以巢狀 select）
資料表加了欄位自動跟著回傳不會出現，除非你加進 select
適合service 內部要用整筆資料做判斷要送出 API 的資料

商品 API 的每個方法都回傳同一組欄位，所以把 select 寫成一個常數，查詢和寫入（create、update 也接受 select）都用它：

const productSelect = {
  id: true, name: true, price: true, isAvailable: true, categoryId: true,
} satisfies Prisma.ProductSelect   // satisfies：檢查欄位名稱拼對，又保留精確的型別

findAll(categoryId?: number) {
  return this.prisma.product.findMany({ where: { categoryId }, select: productSelect, orderBy: { id: 'asc' } })
}

常數後面的 satisfies Prisma.ProductSelect 做兩件事：欄位名稱拼錯（例如 isAvaliable）時 TypeScript 會報錯；同時常數保留「這幾個欄位是 true」的精確型別，Prisma 才能據此推算出查詢結果只有這五個欄位。

你可能會想：service 的回傳型別寫成 Promise<ProductResponse[]>，而 ProductResponse 沒有 costPrice，型別不就擋住了嗎？擋不住，原因有兩個。第一，TypeScript 的型別檢查是結構性的：一個物件只要「至少有」目標型別要求的欄位，就可以指定給它，多出來的欄位不算錯（TypeScript 課第 14 課）。所以整個 model 照樣能當成 ProductResponse 回傳。第二，型別在編譯後就消失了，執行時 Nest 只是把物件交給 JSON.stringify，物件裡有什麼就送什麼。真正決定送出哪些欄位的，是查詢時的 select。

💡 實務上：同一張表，前台和後台通常是不同的 select
咖啡店的前台菜單只需要名稱、價格、是否供應；後台的商品管理還要看成本和建立時間。常見做法是每種用途各一個 select 常數（例如 publicProductSelect、adminProductSelect），後台那個要搭配權限檢查才能用。code review 時，看到 API 直接回傳 include 的結果，或 schema 新增欄位的 PR，資深工程師會問一句「這個欄位會從哪些 API 出去？」。如果有 e2e 測試，可以斷言回應的欄位清單，有人不小心多送欄位時測試就會失敗。

商品的部分到這裡完成了：CRUD、錯誤、回應的形狀都處理好。接下來是客人下單，而一張訂單不只一筆資料，資料庫要先知道訂單和商品之間怎麼連。

下單要寫哪些資料？schema 怎麼描述訂單、明細、商品

一張訂單可以點好幾樣商品，每樣有自己的數量；同一個商品也會出現在很多張訂單裡。這是多對多的關係，資料庫沒辦法在 orders 裡放一個「商品清單」欄位，所以沿用 PostgreSQL 課的做法：中間加一張明細表 order_items，每一列記錄「哪張訂單、哪個商品、幾杯、單價多少」。整個咖啡店的關係是：一個顧客有很多訂單，一張訂單有很多明細，每一筆明細指向一個商品。

起始專案已經有 Order 和 Product，要新增的是 OrderItem。在 Prisma schema 裡寫成這樣：

model OrderItem {
  id        Int     @id @default(autoincrement())
  orderId   Int     @map("order_id")                                                  // 外鍵欄位：資料表裡真的有這一欄
  order     Order   @relation(fields: [orderId], references: [id], onDelete: Restrict) // 關聯欄位：資料表裡沒有
  productId Int     @map("product_id")
  product   Product @relation(fields: [productId], references: [id], onDelete: Restrict)
  quantity  Int
  unitPrice Int     @map("unit_price")

  @@map("order_items")
}

model Order {
  // …原本的欄位
  items OrderItem[]   // 反向的關聯欄位：一張訂單的所有明細
}

這段 schema 裡，跟訂單有關的欄位出現了兩次：orderId 和 order。它們是兩種不同的東西，分清楚後面的查詢和寫入才看得懂：

  • 外鍵欄位（orderId）：資料表裡真的有的那一欄 order_id，存的是一個數字，跟 PostgreSQL 課寫的外鍵一樣。
  • 關聯欄位（order、Order 裡的 items）：資料表裡沒有這一欄。它只存在 schema 裡，告訴 Prisma「兩個 model 怎麼連」，讓你能在查詢時寫 include: { items: true } 或 select: { items: … } 一起拿到明細，或在建立訂單時順便建立明細。英文文件裡叫 relation field。

兩個 model 之間的連法只需要描述一次，寫在持有外鍵的那一邊：@relation(fields: [orderId], references: [id]) 的意思是「我這邊的 orderId 對到 Order 的 id」。另一邊 Order 的 items OrderItem[] 不寫 @relation，它的作用是讓你能從訂單往下查明細。Product 也要加上對應的 OrderItem[]。

onDelete 決定「被參照的資料要刪除時怎麼辦」。onDelete: Restrict 產生的 SQL 是 FOREIGN KEY … ON DELETE RESTRICT：還有明細參照的訂單或商品，資料庫拒絕刪除（PostgreSQL 課第 8 課）。另一個常見選項 Cascade 會連帶刪掉參照它的明細，對訂單來說這是錯的：訂單是帳務資料，不該因為某個商品被刪掉，就讓過去賣出它的明細跟著消失。所以這裡明確寫出 Restrict。

這個選擇也決定了店員「下架商品」該怎麼做。這一課的 DELETE /products/:id 真的刪資料，被訂單參照過的商品會因為 RESTRICT 刪不掉，Prisma 丟出 P2003，上一節的 filter 把它變成 409。實務上商品通常不刪，而是設成 isAvailable: false 停售：菜單不再顯示，舊訂單照樣查得到商品名稱。軟刪除與稽核紀錄在 PostgreSQL 課第 38 課。

改完 schema 執行 npx prisma migrate dev --name order_items，打開產生的 migration.sql，確認有兩個 ON DELETE RESTRICT 的外鍵。表建好了，下一個問題是：一張訂單要寫進 orders 一筆、order_items 好幾筆，怎麼寫才安全？

怎麼讓訂單和明細一起成功、一起失敗？

建立訂單要寫兩張表。直覺的寫法是分兩步：先 order.create 拿到新訂單的 id，再用這個 id orderItem.createMany 寫明細。交易是資料庫保證「一組修改要嘛全部生效、要嘛全部取消」的機制（PostgreSQL 課第 18 課）。問題在於這兩次呼叫各自是獨立的交易，沒有東西把它們綁在一起。第二步失敗時（違反約束、連線中斷、程式在中間丟了例外），第一步已經寫進去了，資料庫留下開場那張金額 340、卻沒有任何明細的訂單。廚房看到一張空單，帳上卻多了 340 元。

Prisma 的解法是巢狀寫入：在建立訂單的同一個 create 裡，透過關聯欄位 items 順便建立明細，Prisma 會把它們放進同一個交易：

const order = await this.prisma.order.create({
  data: {
    customerId: dto.customerId,
    total,
    items: { create: [{ productId: 2, quantity: 2, unitPrice: 110 }, { productId: 6, quantity: 1, unitPrice: 120 }] },
  },
  select: orderSelect,
})

這裡的 unitPrice 先寫成固定值，total 就是它們的總和（2×110＋1×120＝340，就是開場那張訂單）；它們實際上要從哪裡來，在本節最後的「明細為什麼要存單價？」說明。

用 query log 驗證它真的在同一個交易裡。記錄到的是（省略了 "public". 前綴與欄位清單）：

INSERT INTO "orders" ("customer_id","status","total","ordered_at") VALUES ($1,$2,$3,$4) RETURNING "orders"."id"
INSERT INTO "order_items" ("order_id","product_id","quantity","unit_price") VALUES ($1,$2,$3,$4), ($5,$6,$7,$8)
SELECT … FROM "orders" WHERE "orders"."id" = $1 …            -- 以下 4 句是 select: orderSelect 把結果讀回來
SELECT … FROM "customers" WHERE "customers"."id" = $1 …
SELECT … FROM "order_items" WHERE "order_items"."order_id" = $1 ORDER BY "order_items"."id" ASC …
SELECT … FROM "products" WHERE "products"."id" IN ($1,$2) …
COMMIT

由上到下看：

  • 第一句寫入訂單，RETURNING 拿回新的 id；第二句寫入兩筆明細。明細裡不用寫 orderId，Prisma 會用第一句拿到的 id 填上。
  • 中間 4 句 SELECT 是 select: orderSelect 把剛建立的訂單讀回來，下一節會講它。
  • 最後的 COMMIT 表示這幾句都在同一個交易裡（開頭的 BEGIN 不會出現在 query log）。明細寫入失敗，訂單也一起回滾，不會留下空單。

範例裡的顧客是直接給外鍵 customerId: dto.customerId。也可以透過關聯欄位寫成 customer: { connect: { id: 1 } }：巢狀寫入裡除了 create，還有 connect，意思是指向一筆已經存在的資料，效果跟直接給 customerId: 1 一樣。

明細為什麼要存單價？

上面的明細除了數量，還存了 unitPrice。products 表不就有價格了嗎？這是開場第四件事的答案。PostgreSQL 課第 10 課講過：訂單是歷史紀錄。拿鐵下個月從 110 漲到 120，上個月那張訂單的客人付的還是 110。如果查訂單時用商品現在的價格去算，舊訂單的金額就全部變了，對帳對不起來。「資料不要重複存」說的是同一件事實不要存兩份；下單當下的價格和商品現在的價格是兩件不同的事實，各存一份是對的。

那單價從哪裡來？不能用前端送來的價格。請求是客人的瀏覽器送的，任何人都能用 DevTools 改掉 body，否則客人可以自己把拿鐵改成 1 元。單價要從資料庫讀，所以建立訂單前先查一次這些商品：

const products = await this.prisma.product.findMany({
  where: { id: { in: ids }, isAvailable: true },
  select: { id: true, price: true },
})
// ids 是請求裡去掉重複的商品 id（同一個商品可以分兩行點）
// 查到的比 ids 少 → 有商品不存在或停售 → 丟 ProductUnavailableError，什麼都還沒寫

查到的價格乘上數量加總成 total，再用巢狀寫入一次寫進去。注意「先查商品，再寫訂單」在兩步之間，商品可能剛好被改價或停售，這跟上一節「先查再寫」是同一種空隙。這一課先接受它；要連庫存一起扣、絕對不能超賣時，就需要交易與鎖，那是下一課的主題。

訂單寫進去了。客人下單後，前端要顯示訂單詳情：買了什麼、各幾杯、總共多少。這就是剛才那 4 句 SELECT 要讀回來的東西。

怎麼把訂單讀回來給前端？

訂單詳情 GET /orders/:id 要的資料散在四張表：訂單本身、顧客的名字、每筆明細的數量和單價、每個商品的名稱。前面「回應裡該有哪些欄位？」那一節幫商品挑欄位用的 select 可以巢狀地沿著關聯欄位往下挑欄位，例如顧客只要 id 和名字：select: { customer: { select: { id: true, name: true } } }。這裡同樣不要用 include: { customer: true }，否則顧客的電話就跟著出去了，跟菜單外洩成本是同一個問題。

查詢結果的型別不用自己手寫，Prisma 會從 select 推算出來：Prisma.OrderGetPayload<{ select: typeof orderSelect }> 就是「用這個 select 查出來的那一筆」的型別。但 API 的回應型別要自己定義，例如 OrderResponse，再寫一個函式把查詢結果轉成它：

const toResponse = (o: OrderRow): OrderResponse => ({
  id: o.id,
  status: o.status,
  orderedAt: o.orderedAt,
  customer: o.customer,
  items: o.items.map(i => ({ productId: i.productId, name: i.product.name, qty: i.quantity, unitPrice: i.unitPrice })),
  total: o.total,
})

既然 select 已經挑好欄位了，這一層轉換看起來多餘。它存在的理由是讓 API 和資料表可以各自改變。資料表的欄位叫 quantity，前端從第 7 課的 DTO 起就叫 qty；商品名稱在資料表裡藏在 items[].product.name 這一層，前端要的是攤平的 items[].name。之後資料表拆表、改名，只要改這個函式，前端不受影響。反過來說，把 Prisma 的查詢結果直接當成 API，等於讓資料表的每一次改動都變成 API 的改動。

回應的型別還有一個前端工程師容易忽略的地方：orderedAt 在 service 裡是 Date，經過 JSON.stringify 送出去就變成 ISO 字串 "2026-10-01T02:30:00.000Z"（UTC 時間）。JSON 沒有日期型別，Vue 那邊拿到的是字串，要 new Date(…) 才能格式化，前端的型別要寫成 string。

最後看效能。這個查詢帶著 customer、items、items.product 三層 select，Prisma 預設送出 4 句 SQL，就是上一節 query log 裡那 4 句：訂單、顧客、明細各一句，所有明細的商品用 WHERE id IN (…) 一句查完。句數跟明細有幾筆無關，1 筆明細和 5 筆明細都是 4 句。

對照一個常見的錯誤寫法：先查出明細，再在迴圈裡對每一筆明細 findUnique 它的商品。5 筆明細就多 5 句，50 筆就多 50 句。這種「1 句查列表，再為列表的每一筆各查 1 句」的模式叫 N+1 查詢，是 API 變慢最常見的原因之一，第 16 課會詳細談。讓 Prisma 從 select 一次決定要查什麼，就不會寫出它。改成一句 JOIN 的寫法見課末。

到這裡，開場的四件事都擋下來了。最後一個需求不是事故，而是 PM 提的改名。

PM 要把分類的 name 改叫 title，要動資料表嗎？

產品經理說：分類的「名稱」以後在程式和 API 都叫 title，跟新的後台介面一致。直覺是把 schema 的 name 改成 title 再跑 migrate dev。但 Prisma 只比對 schema 前後的差異，看不出這是改名，第 13 課提過，它產生的 migration 是：

-- DropIndex
DROP INDEX "categories_name_key";

-- AlterTable
ALTER TABLE "categories" DROP COLUMN "name",
ADD COLUMN     "title" TEXT NOT NULL;

先刪欄位再新增：所有分類名稱都不見了。手動把它改成 ALTER TABLE categories RENAME COLUMN name TO title，資料保住了，但部署時還有一個問題。

正式環境通常不會讓服務整個停下來再換版，而是用滾動更新（rolling update）：同時有好幾台伺服器在處理請求，一台一台換成新版，所以換到一半時，新舊版本的程式同時在執行。migration 一執行，欄位就改名了，還沒換掉的舊版程式送出的 SELECT name FROM categories 全部失敗。PostgreSQL 課第 34 課說過，真的要改資料表欄位名，得用 expand／contract 分好幾次部署：先加新欄位、兩邊同步寫、搬資料、全部換新版之後才刪舊欄位。

但這個需求其實不用動資料表。PM 要改的是程式和 API 裡的名字，資料表的欄位叫什麼，前端根本看不到。第 13 課用過的 @map 正好做這件事，它把 schema 裡的欄位名對應到資料表裡另一個名字：

model Category {
  id    Int    @id @default(autoincrement())
  title String @unique @map("name")   // 程式裡叫 title，資料表欄位還是 name
  …
}

改完執行 npx prisma migrate dev，Prisma 會說資料庫已經同步、沒有產生新的 migration，因為資料表本來就有 name 欄位；再 npx prisma generate，Prisma Client 裡的欄位就變成 title，送出的 SQL 還是 SELECT "name" …。不用 migration、沒有停機、舊版程式照常執行。TypeScript 會把所有還在用 name 的地方標成錯誤，照著改完就好。

還有一種更省事的做法：只在 controller 回傳前把 name 換成 title。API 對了，但程式裡同一個東西就有兩個名字，下一個人寫查詢時還是要用 name，看 API 文件時又叫 title。@map 讓整個程式只有一個名字。

💡 實務上：先問清楚「要改的是哪一層的名字」
PM 說「名稱改叫 title」，可能只是畫面上的文字，也可能是 API 欄位或資料表欄位，三者的成本差很多：改畫面文字只動前端；改程式和 API 的名字用 @map，資料表不用動；真的要改資料表欄位，就得分好幾次部署。另外要注意，API 欄位改名對前端也是破壞性變更：網頁可以和後端一起部署，但已經裝在客人手機上的 App 還是會送舊的欄位名稱，這時要讓新舊欄位並存一段時間，或另開一個 API 版本（第 23 課）。資深工程師接到改名需求，第一步是列出影響範圍，再決定動哪一層。

練習

在 learn/ 執行 node check.mjs nestjs 14 建立 work/14/。起始專案接續第 13 課：PrismaService（@Global 的 PrismaModule）、分類、商品、顧客、訂單四個 model 與一個 init migration、全域 ValidationPipe、第 8 課的 DomainExceptionFilter，以及這一課要用的領域錯誤（ProductNameTakenError、ProductUnavailableError 等，已經在 src/errors/domain-errors.ts）。開發用的資料庫是 nest_14：

cd nestjs/practice/work/14
npx prisma migrate dev     # 建立 nest_14 並套用 migration
npx prisma db seed         # 3 個分類、6 個商品、6 位顧客
npm run start:dev

判分用的是另一個資料庫 nest_14_test，每次判分都會重建並套用你的 migration，所以兩邊互不影響。

練習 1：寫全域的 PrismaExceptionFilter，@Catch(Prisma.PrismaClientKnownRequestError)，用 APP_FILTER 登記在 AppModule。

  • P2002 → 409，errorCode UNIQUE_VIOLATION；P2003 → 409，FOREIGN_KEY_VIOLATION；P2025 → 404，NOT_FOUND。
  • 其他代碼 → 500，INTERNAL_ERROR，並用 new Logger(PrismaExceptionFilter.name).error(…) 記錄，訊息裡要有錯誤代碼，第二個參數傳 exception.stack。
  • 回應是 { statusCode, error, message, errorCode }，error 用 STATUS_CODES[status]，message 是你自己寫的固定中文，不能用 exception.message。

測試會丟出帶有檔案路徑和 constraint 名稱的 Prisma 錯誤，也會真的去資料庫更新不存在的商品、用不存在的分類建立商品。

練習 2：修好 ProductsService 的三個問題（起始程式裡有註解）。

  • 所有方法都只回傳 { id, name, price, isAvailable, categoryId }：寫一個 productSelect，查詢與寫入都帶 select。
  • findAll(categoryId?) 依 categoryId 篩選，沒給就回傳全部，依 id 排序。
  • 建立、更新撞到 P2002 → 丟 ProductNameTakenError；更新、刪除撞到 P2025 → 丟 ProductNotFoundError；其他錯誤原樣丟出去。

測試會用 5 個同時進來的請求建立同名商品（而且讓每次讀取慢 50 毫秒），要剛好一個 201、四個 409 PRODUCT_NAME_TAKEN。

練習 3：訂單明細。

  • 在 schema.prisma 寫 OrderItem：資料表 order_items，欄位 id、order_id、product_id、quantity、unit_price（都是 Int），兩個外鍵都 onDelete: Restrict；Order 和 Product 加上反向的 OrderItem[]。在 work/14 執行 npx prisma migrate dev --name order_items，會產生新的資料夾 prisma/migrations/<時間>_order_items/，打開 migration.sql 看過。
  • OrdersService.create：先查請求裡的商品（只要 isAvailable: true 的），有任何一個不存在或停售就丟 ProductUnavailableError(那些 id)（同一個商品可以分兩行點，比對前先去掉重複的 id）；單價用查到的價格；用一次 order.create 加 items: { create: [...] } 寫入訂單與明細，total 是單價 × 數量的總和。
  • 回應至少要有 id、total、items: [{ productId, qty, unitPrice }]（練習 4 的形狀也可以）。

測試會在寫入明細時故意讓資料庫出錯，確認不會留下沒有明細的訂單。

練習 4：GET /orders/:id 回傳剛好這個形狀：

{ "id": 1, "status": "paid", "orderedAt": "2026-10-01T02:30:00.000Z",
  "customer": { "id": 2, "name": "陳美華" },
  "items": [{ "productId": 2, "name": "拿鐵", "qty": 2, "unitPrice": 100 }],
  "total": 265 }

不能多出任何欄位（customerId、顧客的 phone、明細的 quantity 都不行），明細依 id 排序，金額用存下來的 unitPrice 與 total。用一個 orderSelect、Prisma.OrderGetPayload 與 toResponse 函式；找不到丟 OrderNotFoundError。測試會數 SQL 句數：1 筆明細和 5 筆明細要一樣多，而且不超過 4 句。

練習 5：程式與 API 把分類的 name 改叫 title。條件：

  1. GET /categories 回傳 [{ id, title }]，不再出現 name；
  2. 不能遺失任何資料；
  3. 採滾動更新，新版上線期間舊版程式還會執行 SELECT name FROM categories，必須照常運作。

Prisma Client 裡的欄位也要叫 title（測試會執行 findMany({ select: { title: true } })）。改完 schema 之後執行 npx prisma migrate dev，如果它想產生 migration，先停下來想想為什麼。

練習 6：商品列表的 API 用 findMany({ include: { category: true } })，回應型別寫成 Promise<ProductResponse[]>（只有 id、name、price）。下列哪個說法正確？

✓ c：include 是「全部欄位再加上關聯」，資料表多一欄回應就多一欄。TypeScript 的型別在執行時不存在，而且允許多出欄位的物件指定給較窄的型別，所以 a、d 都不會發生；b 錯在 include 不會限制商品自己的欄位。送出 API 的查詢用 select 列出要的欄位。

練習 7：create 之前先用 findFirst 確認名稱沒人用，查到就丟 409。為什麼還是會遇到 P2002？

✓ b：查詢和寫入是兩句 SQL，中間別的請求可以插進來。只有 UNIQUE 約束在寫入的那一刻檢查，所以要接住 P2002 翻成 PRODUCT_NAME_TAKEN。Prisma 沒有替你快取查詢（a）；大小寫是另一個問題（c），它跟並發無關。

練習 8：同事說「order_items 存 unit_price 是重複資料，查詢時 JOIN products 拿價格就好」。最主要的問題是？

✓ a：下單當下的價格和商品現在的價格是兩件不同的事實，訂單是歷史紀錄，不能跟著現在改。效能（b）不是重點；Prisma 可以巢狀 select 關聯欄位（c）；正規化是避免同一件事實存兩份（d），這裡不是同一件事實。

常見錯誤

  • 直接回傳 Prisma model：資料表加欄位，API 就跟著外洩（成本、電話），API 契約也綁死在資料表上。查詢用 select，回應型別自己定義，用 toResponse 轉換。
  • 先查再寫來檢查唯一值：並發時兩個請求都查不到。交給 UNIQUE 約束，接住 P2002。
  • 訂單與明細分兩次寫入：第二次失敗會留下孤兒訂單。用巢狀寫入，或下一課的交易。
  • 把 P2025 當成 500，或把所有 Prisma 錯誤都當成 404：依 e.code 分開處理，service 只翻譯自己懂的代碼，其他交給全域 filter。
  • 回傳 exception.message：Prisma 的訊息有檔案路徑、程式碼片段、constraint 名稱。回應用固定文字，原文進 log。
  • try { return this.prisma.x.update(…) } 少了 await：錯誤在 try 之外才發生，catch 接不到。
  • 忘了 Date 在 JSON 裡是字串：前端型別寫 string，要顯示時再轉成 Date。
  • 為了改程式裡的名字去改資料表欄位名：Prisma 會產生 DROP＋ADD 弄丟資料；就算改成 RENAME COLUMN，滾動更新時舊版程式也會壞。用 @map。

補充與查表

主線用不到、但寫其他 API 或查問題時會用到的細節。查表用，不用背。

這課的 SQL 是在哪個版本記錄的

課文裡列出的 SQL 與錯誤代碼，都是用 query log 在 Prisma 7.10.1 ＋ PostgreSQL 18（adapter-pg）實際記錄到的。其他版本的 SQL 細節可能不同，判斷時以你自己打開 query log 看到的為準。

用一句 JOIN 查關聯

Prisma 有一個 relationLoadStrategy: 'join' 選項，把關聯查詢改成一句 JOIN，而不是每層各一句。它在 Prisma 7 還是預覽功能，這門課不用；預設的每層一句（訂單詳情 4 句）不會隨明細筆數增加，已經避開 N+1。

小結

  • Prisma 的 CRUD 對應 SQL：findUnique 找不到回 null，要自己判斷；update／delete 找不到丟 P2025。where 裡的 undefined 會被忽略，null 是「空值」。用 query log 看實際的 SQL。
  • P2002 → 409、P2003 → 409、P2025 → 404：service 把自己懂的代碼翻成領域錯誤，全域 PrismaExceptionFilter 接住其他的，訊息不外洩。唯一值交給 UNIQUE 約束，不要先查再寫。
  • 送出 API 的查詢用 select，不用 include；型別擋不住多出的欄位，select 才擋得住。
  • 外鍵欄位存在資料表裡，關聯欄位只存在 schema 裡；持有外鍵的一邊寫 @relation(fields, references, onDelete)，帳務資料用 Restrict。
  • 巢狀寫入在同一個交易裡建立訂單與明細；明細存下單當下的單價，價格從資料庫讀，不相信前端。
  • 讀回訂單用巢狀 select；用 Prisma.XGetPayload 取得查詢結果的型別，API 回應型別自己定義，再寫 toResponse 轉換。
  • 只改程式裡的名字用 @map／@@map，不需要 migration；真的要改資料表才走 expand／contract。
