階段 4：快取、背景工作與外部整合 · 第 22 課

檔案上傳與 webhook

咖啡店下週要開放線上點餐，上線前資安同事看過程式，退回了兩支 API。第一支是 POST /products/:id/image，店長用它替商品上傳照片：它什麼檔案都收，而且直接用使用者給的檔名存檔，資安同事傳了一個取名 photo.png 的 shell script，伺服器照單全收。第二支是 POST /webhooks/payments，客人付款成功後，金流公司會呼叫它通知我們：資安同事自己用 curl 送了一筆 { data: { orderId: 1 } }，訂單就變成已付款了；同一個通知送三次，付款流程也跑了三次。

這兩支 API 看起來不相關，被退回的原因卻是同一個。到目前為止，咖啡店 API 收到的都是我們自己的 Vue 前台送來的 JSON，欄位長什麼樣子由我們決定。這兩支不一樣：檔案的名稱、類型、大小全由上傳的人決定；webhook 的請求根本不是我們的前台送的，任何知道網址的人都能送。請求跨過了信任邊界：邊界外面送進來的東西，每一個欄位都可能是假的，伺服器要自己確認。這一課把這兩支 API 修到能上線，修完之後，你遇到任何「外面送進來的東西」，都知道該問哪幾個問題。

這課的路線：
  1. 店長按下「上傳照片」，請求裡裝了什麼、Nest 怎麼把它變成一個檔案物件：哪些欄位是客戶端說了算的。
  2. 有人傳 500MB 上來要在哪裡擋、取名 photo.png 的文字檔怎麼認出來：大小在 multer 擋，類型看檔頭。
  3. 存檔時為什麼不能用使用者給的檔名：路徑穿越、撞名、副檔名欺騙一次解決。
  4. 客人付完款我們怎麼知道、怎麼確認通知真的是金流公司送的：webhook 與 HMAC 簽章。
  5. 同一個付款通知到了三次，怎麼只處理一次：用唯一約束做冪等。
這課會用到：
  • 第 6 課的 guard 與 timingSafeEqual：guard 在 controller 之前決定請求能不能進來；比對密鑰用固定時間比較，回應時間才不會洩漏猜對了幾個字。
  • 認證課第 2 課的 HMAC：用雙方共有的密鑰對內容算出一段簽章，內容被改過或沒有密鑰，就算不出相同的簽章。
  • Node 課第 11 課的 Buffer：Node 裡裝原始位元組的容器，檔案內容和 HTTP body 未解析前都是 Buffer。
  • 第 15 課的互動式交易與條件更新：交易裡的寫入一起 commit 或一起回滾；把判斷寫進 updateMany 的 where，看 count 知道有沒有改到。

店長按下「上傳照片」，請求裡裝了什麼？

要修上傳 API，得先知道它收到的是什麼。前面每一課的請求 body 都是 JSON，但 JSON 是文字格式，裝不下圖片這種任意位元組的二進位資料；硬要放進去，得先把位元組轉成 base64 字串，體積會變大，伺服器還要再轉回來。所以瀏覽器上傳檔案時用的是另一種格式：multipart/form-data。

multipart 的意思是「一個 body 分成好幾段」。每一段叫一個 part，對應表單裡的一個欄位；段與段之間用一行 boundary（分隔字串）隔開。每個 part 先有自己的標頭，說明這個欄位叫什麼、檔名是什麼、內容是什麼類型，空一行之後才是內容本身。因為內容是原始位元組，不用轉碼，圖片原封不動地放在裡面。

在 Vue 裡，你不用自己組這種格式。把檔案放進 FormData 交給 fetch，瀏覽器就會產生 multipart 請求：

const form = new FormData()
form.append('image', fileInput.files[0])      // 欄位名稱 image，第二個參數是 File
await fetch('/products/1/image', { method: 'POST', body: form })   // 不要自己設 Content-Type，瀏覽器會補上 boundary

註解裡那句「不要自己設 Content-Type」值得多看一眼：boundary 是瀏覽器隨機產生的，寫在 Content-Type 標頭裡告訴伺服器「用這串字切開 body」。你自己寫 Content-Type: multipart/form-data 會蓋掉瀏覽器的版本，少了 boundary，伺服器就切不開了。送出去的請求長這樣：

POST /products/1/image HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxk

------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="image"; filename="latte.png"
Content-Type: image/png

‰PNG␍␊␚␊…（檔案的位元組）
------WebKitFormBoundary7MA4YWxk--

從上往下看這個 part：Content-Disposition 說欄位名稱是 image、檔名是 latte.png；下一行的 Content-Type: image/png 說這段內容是 PNG 圖片；空一行之後是檔案的位元組；最後一行 boundary 後面多兩個 --，代表整個 body 結束。

這三樣東西：filename、part 的 Content-Type、內容本身，全部是客戶端填的。瀏覽器會依使用者選的檔案填入合理的值，但請求不一定是從瀏覽器來的：用 curl 或任何程式都能自己組一個 multipart 請求，三樣東西愛填什麼就填什麼，而且可以互相矛盾。資安同事就是這樣做的：內容是 shell script，檔名寫 photo.png，類型寫 image/png。伺服器如果相信前兩樣，就會把 script 當成圖片存起來。

這就是開場問題的最小答案：上傳 API 只能相信檔案內容，而且要自己看內容判斷類型；檔名一律由伺服器產生。在動手之前，還要知道這個 multipart 請求進到 Nest 之後，會變成什麼樣子。

Nest 怎麼把這個請求變成一個檔案物件？

上一節的 body 是一大串混著文字標頭和二進位內容的位元組，要按 boundary 切開、解析每段的標頭，才拿得到檔案。Nest 預設的 JSON body parser 不處理這種格式，NestJS 在 Express 平台上交給一個專門解析 multipart 的套件：multer。

@nestjs/platform-express 把 multer 包成一個 interceptor：FileInterceptor(欄位名稱, 選項)。第 9 課講過 interceptor 包在 controller 方法外面，在方法執行前後都能做事；FileInterceptor 做的是在方法執行前讓 multer 解析請求，把名為 image 的欄位取出來。controller 方法再用 @UploadedFile() 拿到解析好的檔案：

import { FileInterceptor } from '@nestjs/platform-express'

@Post(':id/image')
@UseInterceptors(FileInterceptor('image'))
uploadImage(@Param('id', ParseIntPipe) id: number, @UploadedFile() file: Express.Multer.File) {
  return this.products.saveImage(id, file)
}

FileInterceptor('image') 的 'image' 要跟 Vue 那邊 form.append('image', …) 的欄位名稱一致。file 的型別 Express.Multer.File 來自 @types/multer 套件，裡面有很多欄位，修這支 API 會用到的是這四個。注意「來源」那一欄：前兩個就是上一節那兩個可以亂寫的東西，換了個名字而已。

欄位來源能不能信
originalnamepart 標頭的 filename不能：可能有 ../、可能跟內容無關、兩個人可能上傳同名檔
mimetypepart 標頭的 Content-Type不能：客戶端自己填的
sizemulter 數的位元組數可以
buffer檔案內容（沒設 storage 時 multer 用記憶體儲存）這是唯一值得檢查的東西

最後一列的「記憶體儲存」決定了接下來的問題。multer 可以設定把檔案存到哪裡：沒有設定 storage 或 dest 時，它把整個檔案讀進記憶體，放在 file.buffer 這個 Buffer 裡。對 2MB 以內的商品照片，這是最簡單的做法：內容就在手上，要檢查、要寫檔都直接用（更大的檔案怎麼辦見課末）。但「整個檔案讀進記憶體」也表示，對方傳多大，伺服器就要先拿出多少記憶體來裝。現在這支 API 沒有任何限制，有人傳 500MB 上來會怎樣？

有人傳 500MB 上來，要在哪裡擋？

上一節說到，multer 會把整個檔案收進記憶體。如果有人故意傳 500MB，或者同時傳十個，伺服器的記憶體可能在處理到 controller 之前就被吃光，整個程序當掉，所有客人的請求一起失敗。所以大小限制不只是「圖片別太大」的產品規則，也是保護伺服器的防線，重點是它在什麼時候生效。

先回顧兩個位置。第 7 課的 pipe 負責在參數交給 controller 方法之前做轉換與驗證，例如把字串轉成數字、檢查 DTO；它拿到的是「已經準備好的參數」。第 9 課的請求生命週期則規定了執行順序：guard → interceptor（前半）→ pipe → controller。記住這個順序，下面的問題就看得出來。

直覺的寫法是用 pipe：NestJS 有 MaxFileSizeValidator，放在 @UploadedFile() 的 pipe 裡檢查 file.size，超過就拒絕。測試送 3MB 的檔案，也確實會被拒絕。問題在順序。第 9 課的請求生命週期裡，interceptor 在 pipe 之前執行；FileInterceptor 是 interceptor，所以順序是：

  1. FileInterceptor 讓 multer 解析 multipart，把整個檔案收進 file.buffer。
  2. pipe 執行，這時才看得到 file.size。
  3. controller 方法執行。

pipe 看到的 size 是已經收完的大小。500MB 的檔案會先在第 1 步吃下 500MB 的記憶體，第 2 步才告訴對方「太大」，防線來得太晚。要讓限制在第 1 步就生效，得交給 multer 自己：它在收資料的過程中就在數位元組，超過上限就停止接收。限制寫在 FileInterceptor 的第二個參數：

const MAX_IMAGE_BYTES = 2 * 1024 * 1024

@UseInterceptors(FileInterceptor('image', { limits: { fileSize: MAX_IMAGE_BYTES, files: 1 } }))

fileSize 是單一檔案的位元組上限，這裡是 2MB；files: 1 限制一個請求只能帶一個檔案欄位。兩個限制都在解析階段生效，不用等到 controller：

  • 超過 fileSize 時 multer 丟 LIMIT_FILE_SIZE，@nestjs/platform-express 把它轉成 PayloadTooLargeException，客戶端收到 413。
  • 多送檔案會回 400。

這裡出現了兩種失敗的狀態碼，要分清楚。413 Payload Too Large 的意思是「請求本身太大」，伺服器連收都不收；422 Unprocessable Entity 的意思是「收下來了，但內容不符合規則」，第 7 課的驗證錯誤用的就是 422。大小在 multer 擋，回 413；下一節的類型檢查在 pipe 做，回 422。練習的判分會分別檢查這兩個狀態碼。

大小擋住了。但 1.5MB 的 shell script 取名 photo.png，大小完全合格，照樣會被收下來。下一個問題是：怎麼知道它不是圖片？

取名 photo.png 的文字檔，怎麼認出來？

前兩節已經確認，originalname 的副檔名和 mimetype 都是客戶端填的，不能拿來判斷類型。能信的只剩 file.buffer，也就是內容本身。問題變成：光看一串位元組，怎麼知道它是 PNG？

答案在檔案的開頭。大多數檔案格式規定，檔案的頭幾個位元組必須是一段固定的值，讀取程式看到這段值才知道該用哪種格式解析。這段固定的開頭叫檔頭，也常被叫做 magic number：

  • PNG 開頭永遠是 89 50 4E 47 0D 0A 1A 0A（‰PNG 加換行），上一節請求範例裡那串 ‰PNG␍␊␚␊ 就是它。
  • JPEG 開頭是 FF D8 FF。
  • GIF 是 GIF87a 或 GIF89a。

檔頭和副檔名、Content-Type 最大的差別是：副檔名與 Content-Type 隨便改，檔案內容都不會變；檔頭改了，檔案就不是那個格式了，看圖軟體打不開。所以判斷類型要看檔頭。資安同事那個 shell script 開頭是 #!/bin/sh，不是任何圖片格式的檔頭，看檔頭就認得出來。

這件事不用自己寫。@nestjs/common 的 FileTypeValidator 預設就是看檔頭（它用 file-type 套件偵測內容的類型）。把它用 ParseFilePipeBuilder 組成一個 pipe，放在 @UploadedFile() 裡：

@UploadedFile(
  new ParseFilePipeBuilder()
    .addFileTypeValidator({ fileType: /^image\/(png|jpeg)$/, overrideMimeType: true })
    .build({ errorHttpStatusCode: HttpStatus.UNPROCESSABLE_ENTITY }),
) file: Express.Multer.File

這幾行的每個選項都影響安全，看 FileTypeValidatorOptions 的定義逐一決定。下表後兩個選項是「關掉檢查」的開關，列出來是為了知道不能開：

選項意思這課的用法
fileType允許的 MIME 類型，字串或正規表示式。字串是「包含到名稱結尾」的比對：'png' 符合 image/png用正規表示式 /^image\/(png|jpeg)$/ 寫清楚只收兩種；GIF 是真的圖片也要擋
overrideMimeType偵測成功後，把 file.mimetype 換成偵測到的類型要開：後面決定副檔名用的就是 file.mimetype，不開它還是客戶端填的值
skipMagicNumbersValidation不看檔頭，只比對客戶端給的 mimetype不要開：等於沒驗
fallbackToMimetype檔頭認不出來時改信客戶端的 mimetype不要開：文字檔沒有檔頭，認不出來就會放行
errorHttpStatusCode（build 的選項）驗證失敗回哪個狀態碼，預設 400設 422，跟第 7 課的驗證錯誤一致

overrideMimeType 最容易漏。驗證只回答「能不能收」，不會自動改掉 file.mimetype；不開它，驗證雖然通過，file.mimetype 仍是客戶端寫的字串。下一節要靠 file.mimetype 決定副檔名，到時候用的就是一個沒驗過的值。

驗證失敗時 pipe 丟出例外，controller 方法不會執行，所以檔案也不會被存下來。這一點判分會查：422 之後 UPLOAD_DIR 裡必須是空的。到這裡，收進來的檔案大小合格、確定是 PNG 或 JPEG。剩下最後一步：存到硬碟上，要叫什麼名字？

存檔時，檔名為什麼不能用使用者給的？

起始程式的 saveImage 直接用 originalname 存檔。上一節已經確認內容是真的圖片了，檔名用使用者取的似乎沒差，但 originalname 本身就能出事，跟內容是什麼無關。三個理由，每一個都是真實發生過的事故：

  • 路徑穿越（path traversal）：檔名 ../../etc/cron.d/evil 經過 join(dir, filename)（Node 課第 10 課的路徑組合）會跑出上傳資料夾，寫到系統的其他地方。用 basename() 去掉路徑只擋得住這一種，下面兩種照樣中。
  • 撞名覆蓋：兩位店長都傳 photo.png，第二張蓋掉第一張，而且第一個商品的 imageUrl 現在指向別人的圖。
  • 副檔名欺騙：真的 PNG 取名 latte.html，存下來之後用 /uploads/latte.html 存取，瀏覽器會把它當網頁。反過來，拿 extname(originalname) 當副檔名，cake（沒有副檔名）會存成沒有副檔名的檔。這會出問題，是因為 express.static 這類靜態檔案伺服器依副檔名決定回應的 Content-Type，查不到副檔名就回 application/octet-stream（「一串不明的位元組」）；使用者直接打開圖片網址時，瀏覽器會把它當成檔案下載，而不是顯示成圖片。

三個問題的根源都是「檔名由客戶端決定」，所以解法是把檔名的兩個部分都收回伺服器手上：主檔名用 randomUUID() 產生，不可能有 ../，也不會撞名；副檔名查表，表的 key 是上一節偵測到的類型，PNG 一定存成 .png，客戶端取什麼名字都影響不到：

import { randomUUID } from 'node:crypto'

const EXT: Record<string, string> = { 'image/png': '.png', 'image/jpeg': '.jpg' }

const dir = this.config.get('UPLOAD_DIR', { infer: true })
await mkdir(dir, { recursive: true })
const filename = randomUUID() + EXT[file.mimetype]   // overrideMimeType 之後，mimetype 是偵測到的
await writeFile(join(dir, filename), file.buffer)
await this.prisma.product.update({ where: { id }, data: { imageUrl: `/uploads/${filename}` } })

這段程式從上往下：從設定讀出上傳資料夾、確保資料夾存在、組出檔名、寫入 file.buffer，最後把網址存到商品上。注意 EXT[file.mimetype] 這一行和上一節的連動：沒開 overrideMimeType 時，file.mimetype 是客戶端寫的，例如 application/octet-stream，查表拿到 undefined，檔名就變成沒有副檔名。

資料夾路徑 UPLOAD_DIR 從設定讀，不寫死在程式碼。第 11 課的 Env schema 已經有它，預設 uploads：開發時放在專案裡，正式環境可能是掛載的磁碟或暫存區，換地方只改設定，程式碼不用改。原始檔名如果對使用者有意義（例如下載時要顯示），另外存到資料庫欄位，不要拿它當路徑。這裡的做法只適合單一台伺服器，多台時要怎麼改見課末。

上傳 API 修好了：大小在 multer 擋（413）、類型看檔頭（422）、檔名由伺服器產生。

💡 實務上：上傳功能要先問清楚「誰傳、傳什麼、存多久」
商品照片、會員頭像、退款要附的收據照片，幾乎每個後台都有上傳。動手前資深工程師會先問：誰能上傳（一定要過登入與權限的 guard，不能是公開端點）、允許哪些類型和多大、換新圖時舊檔要不要刪（不刪的話硬碟只會越來越滿）。手機拍的照片常常是好幾 MB，還可能帶有拍攝地點的 EXIF 資訊，公開顯示前通常會縮圖並去掉這些資訊；這種比較慢的處理適合丟給第 20 課的佇列，不要卡在上傳請求裡。收據、身分證件這類敏感檔案不能放在任何人都能用網址打開的地方，要經過有權限檢查的 API 才能下載。

客人付完款，我們怎麼知道？

上傳的問題是「內容可能是假的」；資安同事退回的第二支 API 問題更大：連「是誰送的」都可能是假的。要理解為什麼，先看這支 API 存在的原因。

客人線上付款時，是在金流公司的頁面輸入卡號，付款結果在金流公司那邊產生，我們的伺服器不在這個流程裡。要知道某張訂單付款成功了沒有，有兩種方法：

  • 輪詢（polling）：我們每隔幾秒去問金流公司「訂單 1 付了沒」。結果出來之前的每一次詢問都是浪費，而且間隔多長，客人就要多等多久才看到「付款成功」。
  • 反過來，我們事先在金流公司後台登記一個網址，付款結果一出來，金流公司主動呼叫這個網址告訴我們。

第二種叫 webhook。它跟我們寫過的所有 API 方向相反：平常是我們的前台當客戶端、呼叫我們的伺服器；webhook 是金流公司當客戶端，呼叫我們的伺服器，請求什麼時候來、帶什麼內容，都由對方決定。我們只能提供一個網址，等它被呼叫。

問題就出在「網址」：POST /webhooks/payments 必須公開在網路上，金流公司才打得到。公開的網址任何人都打得到，任何人都能 POST /webhooks/payments 送一筆 { data: { orderId: 1 } } 把訂單改成已付款，這正是資安同事做的事。這支 API 不能像前台的 API 那樣靠登入判斷是誰，因為呼叫的不是使用者。

金流公司的解法是簽章。開通 webhook 時，金流後台會給我們一把密鑰，只有雙方知道。之後每送一個請求，金流公司都用這把密鑰對請求內容算出一段簽章，放在標頭裡一起送來；我們收到後用同一把密鑰再算一次，算出來一樣，才代表請求是持有密鑰的金流公司送的。這一課假設金流公司的格式是：

X-Signature: t=1767225600,v1=5f1a…（64 個 hex 字元）

簽的內容：`${t}.${原始 body}`
演算法：HMAC-SHA256，密鑰是後台給的 PAYMENT_WEBHOOK_SECRET

這個 t=…,v1=… 的結構和簽 ${t}.${body} 的方式取自 Stripe（Stripe 的標頭叫 Stripe-Signature，不是 X-Signature）：t 是簽章時的 Unix 秒數，v1 是 HMAC 的結果。認證課第 2 課說過 HMAC 證明兩件事：內容沒被改過，而且是持有密鑰的人算出來的。偽造者沒有密鑰，算不出正確的 v1；他把別人的請求內容改掉，原本的 v1 也就對不上了。所以密鑰是整個機制的根本：它只存在金流公司和我們的伺服器設定裡，不進 git、不寫在程式碼。

原理很短，實作卻有好幾個地方容易錯，錯了不是全部 401 就是形同沒驗。下一節一步一步寫出這個驗證。

怎麼確認這個通知真的是金流公司送的？

上一節的格式說明了「要算什麼」，這一節決定「在哪裡算、怎麼算才不會錯」。位置是 guard：第 6 課的 guard 在 controller 之前執行，簽章不對的請求到不了 controller，訂單也就不會被改。練習的起始專案已經在 controller 掛好 @UseGuards(WebhookSignatureGuard)，要寫的是 guard 的內容，分四個步驟，每一步都有常見的錯法。

1. 拿到原始的 body。HMAC 是算在位元組上的，差一個空白，算出來的值就完全不同。金流公司簽的是它送出的那串位元組，我們也要對同一串位元組算。問題是 Nest 的 body parser 會先把 JSON 解析成物件放在 req.body，原本的位元組就丟了。能不能用 JSON.stringify(req.body) 組回去？不行：{"a":1, "b":2} 和 {"b":2,"a":1} 解析成同一個物件，位元組卻不同，空白、換行、key 的順序在解析時都消失了，組回去的字串不一定跟原本一樣。所以要用解析前的位元組。NestJS 要在建立應用時開 rawBody，body parser 就會把原始位元組留在 req.rawBody：

// main.ts
const app = await NestFactory.create(AppModule, { rawBody: true })

// guard 裡
const req = context.switchToHttp().getRequest<RawBodyRequest<Request>>()
req.rawBody   // Buffer；沒開 rawBody 時是 undefined

這個設定有一個陷阱：它要開在每一個建立應用的地方。測試裡 createTestApp 可以用 options: { rawBody: true } 開，但正式啟動走的是 main.ts，兩邊都要有。只在測試開，測試全綠，上線後 req.rawBody 是 undefined，每一筆都 401。練習的判分會 nest build 後真的啟動一次，漏了 main.ts 就會在那裡失敗。

2. 解析標頭並檢查時間。拿到 body 之後，從 X-Signature 取出 t 和 v1。t=…,v1=… 這個格式把逗號換成 & 就能交給 URLSearchParams 解析。這一步要處理所有「格式不對」的情況：沒有標頭、t 不是數字、沒有 rawBody，一律 401；不能讓這些情況丟出其他錯誤變成 500。對方送來壞掉的請求是對方的問題，不是我們的伺服器壞了。

格式對了，還要檢查時間。為什麼簽章對了還不夠？想像有人在中途攔截到一個金流公司送來的合法請求，他不用改任何內容，原封不動地再送一次，簽章當然還是對的。這叫重放攻擊（replay）。擋重放靠的是 t：它被簽在內容裡，改了簽章就對不上；我們只接受 300 秒內簽出來的請求，錄下來的舊請求過了時間就沒用了：

const TOLERANCE_SECONDS = 300
if (Math.abs(Date.now() / 1000 - Number(t)) > TOLERANCE_SECONDS) throw new UnauthorizedException('簽章已過期')

Date.now() 是毫秒，除以 1000 換成秒才能和 t 比。用絕對值是因為對方的時鐘可能比我們快，未來的時間一樣要拒絕。300 秒是常見的容忍值，涵蓋網路延遲與雙方時鐘誤差。

3. 算出預期的簽章。用同一把密鑰、同一個演算法，對 `${t}.` 加上原始 body 算 HMAC。update 可以呼叫多次，內容會接在一起，所以先餵 `${t}.` 再餵 Buffer，不用把 Buffer 轉成字串：

const secret = this.config.get('PAYMENT_WEBHOOK_SECRET', { infer: true })
const expected = createHmac('sha256', secret).update(`${t}.`).update(req.rawBody).digest()   // Buffer，32 bytes
const given = Buffer.from(v1, 'hex')

密鑰從 ConfigService 讀，和 UPLOAD_DIR 一樣放在設定裡。digest() 不帶參數回傳 32 bytes 的 Buffer；對方送來的 v1 是 hex 字串，用 Buffer.from(v1, 'hex') 也轉成 Buffer，兩邊才能逐位元組比較。

4. 固定時間比較。最後比較 given 和 expected。第 6 課講過 === 比到第一個不同的字就停，回應時間會洩漏猜對了幾個字，攻擊者可以一個字一個字地試出正確的簽章。所以用 timingSafeEqual，它不管哪裡不同，都花一樣的時間比完。但它遇到長度不同會丟 RangeError，所以先比長度：

if (given.length !== expected.length || !timingSafeEqual(given, expected)) throw new UnauthorizedException('簽章不符')
return true

長度不同本來就代表簽章錯了，直接 401；沒有這一行，送一個 v1=abc 就能讓伺服器回 500，log 裡全是 RangeError。四個步驟走完，偽造的請求、被改過的請求、錄下來重放的請求都進不了 controller。

💡 實務上：每家金流的簽章格式都不一樣，照對方文件做
台灣常見的綠界、藍新，和國外的 Stripe，各有自己的簽章或檢查碼規則；原理都是「用雙方約好的密鑰算出一個值來比對」，但要簽哪些欄位、怎麼排序、怎麼編碼全看對方文件。對方有提供官方 SDK 的驗證函式時優先用它，自己照文件實作就要拿文件裡的範例值寫測試對過。開發時金流打不到你電腦上的 localhost，通常用金流的測試環境，再用 ngrok 這類轉發工具（Stripe 則有自己的 Stripe CLI）把請求轉到本機。驗簽失敗要記 log 方便追查，但不要把密鑰或完整簽章印出來；密鑰外洩時要能在金流後台換一組新的，只改設定、重新部署就生效。

偽造的問題解決了，但資安同事回報的第二個現象還在：同一個通知送三次，付款流程跑了三次。這三次請求都是金流公司真的送的，簽章完全正確，guard 擋不住，也不該擋。

同一個付款通知到了三次，怎麼只處理一次？

上一節的 guard 只回答「是不是金流公司送的」，不回答「是不是送過了」。而金流公司確實會重複送：它送 webhook 的規則通常是「沒收到 2xx 就重送」，間隔拉長，持續一天甚至更久。重送是功能不是 bug：我們的伺服器剛好在重啟、網路剛好斷，重送讓通知不會漏。代價是同一個事件會到好幾次，有時還是同時到：第一次回應太慢，對方逾時後重送，兩個請求一起在處理。

所以處理 webhook 要冪等（idempotent）：同一個事件處理一次和處理十次，結果一樣，訂單只付款一次、paidAt 不會被改掉。系統設計課第 9 課講過冪等的概念，這裡要把它做出來。要判斷「是不是同一個事件」，需要一個重送時不變的識別：金流公司送的每個事件都有 id（例如 evt_1），重送時不變，就拿它當依據。

最直覺的寫法是「先查有沒有處理過，沒有才處理」，這也是最常見的錯誤寫法：

// 錯：兩個同時進來的請求都查到「沒有」，兩個都處理
if (await tx.webhookEvent.findFirst({ where: { eventId: event.id } })) return
await tx.order.updateMany(…)
await tx.webhookEvent.create(…)

一次一個請求時它是對的；問題出在剛才說的「同時到」。第 15 課講過，查詢和寫入之間別人可以插進來：請求 A 查到「沒有」，還沒寫入之前，請求 B 也查到「沒有」，兩個都往下處理。應用程式層的檢查擋不住並發。正確的做法是把判斷交給資料庫：event_id 加唯一約束，資料庫保證同一個值只能存在一筆，兩個同時寫入的交易只有一個會成功，另一個收到 P2002（第 14 課的違反唯一約束錯誤）：

// schema.prisma
eventId String @unique @map("event_id")
// 然後 npx prisma migrate dev --name webhook-event-unique

有了唯一約束，handler 不用先查，直接寫；撞到 P2002 就代表這個事件已經處理過了：

async handle(event: PaymentEvent) {
  try {
    await this.prisma.$transaction(async tx => {
      const { count } = await tx.order.updateMany({
        where: { id: event.data.orderId, status: 'pending' },     // 條件更新：已付款的不再改
        data: { status: 'paid', paidAt: new Date() },
      })
      await tx.webhookEvent.create({
        data: { eventId: event.id, type: event.type, status: count === 1 ? 'processed' : 'ignored' },
      })
    })
  } catch (e) {
    if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2002') return   // 已處理過：成功
    throw e
  }
}

這段程式有四個設計決定，每一個都對應一種會出事的情境：

  • 改訂單和記事件在同一個交易。先記事件、再改訂單，改訂單那一步失敗（資料庫瞬斷）時，事件已經記成處理過，重送時會被當成重複而跳過，這張訂單永遠付不了款。放在同一個交易，改訂單失敗整筆回滾，事件沒有留下，重送就會重做。
  • P2002 當成成功，回 200。回 409 或任何非 2xx，金流公司會繼續重送，但重送也不會變好。「已經處理過」對對方來說就是成功。
  • 條件更新 status: 'pending'。金流公司可能替同一張訂單送兩個不同 id 的事件（例如系統重試造成）。第二個事件的 id 是新的，唯一約束擋不住它；靠 where 裡的 status: 'pending'，已付款的訂單 count 是 0，paidAt 不會被改掉。
  • 找不到訂單記成 ignored，也回 200。訂單不存在不是對方能修的問題，回錯誤只會換來一天的重送。留一筆 ignored，之後對帳時查得到「收過這個事件但沒有處理」。

只有一種情況該回 5xx：真的處理失敗、重送有機會成功，例如資料庫瞬斷。catch 裡其他錯誤照樣 throw e，就是把這種情況交給對方的重送。

這裡的「同一個交易」只包住資料庫。付款成功後要做的其他事（寄收據、通知廚房）不要塞進 webhook 的交易裡，照第 20 課的 outbox 與第 21 課的事件處理。webhook handler 的工作只有：驗簽、改狀態、記事件、回 200。到這裡，資安同事退回的兩支 API 都修好了。

💡 實務上：webhook 會遲到也會漏，要有對帳當後盾
客服最常接到的付款問題是「我付款了，訂單還顯示未付款」，原因通常是 webhook 晚到、被防火牆擋掉，或我們當時剛好在部署。所以實務上不會只靠 webhook：會有一個排程（第 21 課）定期找出卡在 pending 太久的訂單，主動呼叫金流的查詢 API 確認結果，再用和 webhook 相同的條件更新（只改還是 pending 的訂單），兩邊同時到也不會重複處理。這一課的 webhook_events 表在這時很好用，客服或工程師可以直接查到「這張訂單收過哪些事件、處理結果是什麼」。上線前也要確認 handler 回應夠快，對方的逾時通常不長，慢了就會觸發不必要的重送。

  • FileInterceptor 的 limits：fileSize 2MB、files 1。超過 2MB 要回 413（1.5MB 要收）。
  • @UploadedFile() 裡用 ParseFilePipeBuilder 加 FileTypeValidator：只收 image/png 與 image/jpeg，看檔頭、開 overrideMimeType，失敗回 422。GIF 是真的圖片也要 422；取名 photo.png 的文字檔要 422 而且不能存檔。

練習 2：寫 WebhookSignatureGuard.canActivate，並在 main.ts 開 rawBody：

  • 解析 X-Signature: t=<秒>,v1=<hex>。沒有標頭、格式錯、t 不是數字、沒有 req.rawBody：丟 UnauthorizedException（401），不能是 500。
  • t 與現在相差超過 300 秒（過去或未來）：401。
  • 用 PAYMENT_WEBHOOK_SECRET（從 ConfigService 讀，不能寫死）對 `${t}.` + rawBody 算 HMAC-SHA256，和 v1 用 timingSafeEqual 比較，先比長度。
  • main.ts：NestFactory.create(AppModule, { rawBody: true })。

判分每次用隨機密鑰啟動；body 有多餘空白、key 順序不同時簽章要通過（算在原始位元組上）；改過內容、別的密鑰、v1=abc、400 秒前或後都要 401，200 秒內要 200；原始碼要出現 timingSafeEqual(；最後會 nest build 真的啟動一次送合法請求，漏了 rawBody 會在這裡失敗。

練習 3：讓同一個事件只處理一次。

  • schema.prisma：WebhookEvent.eventId 加 @unique，執行 npx prisma migrate dev --name webhook-event-unique 產生 migration（判分會檢查資料庫裡真的有唯一索引）。
  • WebhooksService.handle：在一個 $transaction 裡，用 updateMany（where 含 status: 'pending'）改訂單，再 create 一筆 webhookEvent，status 依 count 是 'processed' 或 'ignored'。撞到 P2002 當成已處理，正常回傳（200）；其他錯誤照樣丟出。

判分把簽章 guard 換成一律放行，只看冪等：同一個事件同時送 5 次都要 200，只記一筆、只付款一次（先查再寫擋不住）；重送要 200 且 paidAt 不變；另一個事件 id 付同一張已付款的訂單要記成 ignored；訂單不存在要 200 並記 ignored；用 trigger 讓第一次更新訂單失敗，第一次要回 5xx，重送之後訂單要真的變成 paid（事件和訂單不在同一個交易就會過不了）。

練習 4：同事把上傳的大小限制寫成 ParseFilePipeBuilder().addMaxSizeValidator({ maxSize: 2MB })，測試送 3MB 的檔案也確實被拒絕了。這樣有什麼問題？

✓ c。順序是 multer 先解析整個 multipart、把檔案放進 file.buffer，然後才輪到 pipe；pipe 看到的 size 是已經收完的大小。a 錯在時機不同。b 錯：MaxFileSizeValidator 就是檢查大小，只是太晚。d 把狀態碼說反了：limits 擋下的是 413，pipe 擋下的才是 422（依 errorHttpStatusCode）。

練習 5：金流公司重送了一個已經處理過的 webhook，我們的程式發現 event_id 已經存在。應該回什麼？

✓ b。webhook 的契約通常是「2xx 代表收到，其他都重送」。重複的事件回 409、400 或 500 都會讓對方排進重送佇列，持續打一天；a、c、d 都是把 HTTP 語意套在不適用的地方。只有真的處理失敗、重送有機會成功的情況（例如資料庫瞬斷）才回 5xx。

練習 6：驗證簽章時，同事用 JSON.stringify(req.body) 重組 body 再算 HMAC，說這樣就不用開 rawBody。在測試裡送 JSON.stringify(event) 產生的 body 時通過了，上線後卻幾乎每一筆都 401。為什麼？

✓ d。測試會過是因為測試的 body 本來就是 JSON.stringify 的輸出，重組後一模一樣；真實的請求不是。a、b 會讓測試環境也全錯，不會只有正式環境錯。c 跟簽章內容無關，時間窗檢查的是 t 與現在的差距，和時區無關（Unix 秒數沒有時區）。

常見錯誤

  • 用 originalname 當檔名：路徑穿越、撞名覆蓋、副檔名欺騙三個問題同時存在。basename() 只擋第一個。檔名用 randomUUID()，副檔名依偵測到的類型查表。
  • 信任 file.mimetype 或副檔名：兩者都是客戶端填的。用 FileTypeValidator 看檔頭，不開 skipMagicNumbersValidation、fallbackToMimetype。
  • 忘了 overrideMimeType：驗證過了，但 file.mimetype 還是客戶端給的值，查表拿到 undefined，檔名變成沒有副檔名。
  • 大小限制寫在 pipe：整個檔案先進記憶體才被拒絕。寫在 FileInterceptor 的 limits.fileSize。
  • 用 JSON.stringify(req.body) 算簽章：空白、換行、key 順序一變就不符。開 rawBody: true，用 req.rawBody。
  • 只在測試裡開 rawBody：createTestApp 的 options 不會影響 main.ts，正式啟動後 req.rawBody 是 undefined，每一筆都 401。
  • === 比簽章、或 timingSafeEqual 前不比長度：前者洩漏時間資訊，後者長度不同就丟 RangeError 變成 500。先比長度再 timingSafeEqual。
  • 沒有時間窗：錄下來的合法請求可以無限次重放。只接受 ±300 秒內的 t。
  • 密鑰寫死在程式碼：進了 git 就等於公開，換密鑰還要重新部署。從 ConfigService 讀。
  • 先查再寫做冪等：並發的請求都查到「沒有」。用唯一約束，撞到 P2002 當成已處理。
  • 記事件與改訂單分開兩個交易：改訂單失敗時事件已記成處理過，重送被跳過，訂單永遠 pending。放同一個 $transaction。
  • 重複或找不到訂單時回 4xx／5xx：對方會重送一整天。回 200，必要時記成 ignored。
  • 更新訂單不帶 status: 'pending'：另一個事件 id 會把已付款的訂單再付一次，paidAt 被改掉。

補充與查表

版本備註

這課的寫法對照練習安裝的版本：Express 平台的 NestJS 用 multer（練習裝的是 2.5.0）解析 multipart，@nestjs/platform-express 12.3.2 把它包成 FileInterceptor；Express.Multer.File 型別來自 @types/multer（2.3.0）；@nestjs/common 12 的 FileTypeValidator 預設看檔頭（用 file-type 套件偵測）。

幾百 MB 的檔案怎麼收？

這課用 multer 的記憶體儲存，整個檔案放在 file.buffer，對 2MB 以內的商品圖最簡單。幾百 MB 的影片就要改用磁碟儲存或串流，不在這課範圍。

伺服器變成多台時，檔案存哪裡？

存在伺服器硬碟只適合單一台伺服器。第 21 課提到上線時會部署成三台；變成多台之後，上傳到 A 台的檔案 B 台看不到，那時要改存物件儲存（S3 這類服務），controller 與驗證的寫法不變，只有 saveImage 裡「寫到哪」會換。

小結

  • 從信任邊界外送進來的東西（上傳的檔案、別人呼叫的 webhook），每個欄位都可能是假的，伺服器要自己確認。
  • multipart 的 filename、Content-Type 與內容都是客戶端填的；只有內容值得檢查，而且要看檔頭。
  • FileInterceptor(欄位, { limits: { fileSize, files } }) 在 multer 這層擋大小（413），interceptor 比 pipe 先執行，pipe 擋就太晚；ParseFilePipeBuilder().addFileTypeValidator({ fileType, overrideMimeType: true }).build({ errorHttpStatusCode: 422 }) 看檔頭擋類型，失敗時不會存檔。
  • 檔名用 randomUUID()，副檔名依偵測到的類型查表，存到設定的 UPLOAD_DIR。
  • webhook 是對方主動呼叫我們；用 HMAC 簽章驗來源與完整性：rawBody: true 拿原始位元組、±300 秒時間窗擋重放、先比長度再 timingSafeEqual、密鑰從設定讀，所有失敗都是 401。
  • webhook 會重送，處理要冪等：event_id 唯一約束，改訂單（條件更新）與記事件在同一個交易，P2002 與找不到訂單都回 200。
