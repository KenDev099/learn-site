階段 2：請求管線與測試 · 第 9 課

Interceptor 與 RxJS 入門

前端同事在做 Vue 的「訂單追蹤頁」：顧客下單後，頁面先呼叫 GET /orders/1 顯示訂單內容，再呼叫 GET /deliveries/1/eta 顯示外送預計幾點到。客服轉來一則回報：「外送時間有時候轉圈圈轉十幾秒」。他和後端一起追這個回報，查出三個問題：

  1. 不知道慢在哪：外送時間的請求有時十幾秒才回來，可是後端的 log 看不出這個請求在伺服器上花了多久，是網路慢、前端慢還是後端慢，誰也說不清楚。
  2. 卡住時沒人喊停：外送平台偶爾卡住，我們的 API 就跟著一直等，顧客對著轉圈圈，沒有人告訴他「稍後再試」。
  3. 回應送出了不該送的東西：在 Network 分頁點開 GET /orders/1 的回應，裡面有顧客的手機號碼，還有店員寫的「曾經惡意退款」備註。

三個問題有一個共同點：它們都不是哪一支 API 自己的業務邏輯，而是每個請求進出時都該做的事。進去時記下時間，等太久就放棄，出來前把不該送的欄位拿掉。這一課用 NestJS 的 interceptor 一件一件修好它們，最後把三個 interceptor 組在一起，讓訂單追蹤頁的每個請求都經過。

這課的路線：
  1. 三件事為什麼不寫在 handler 裡：interceptor 是什麼，為什麼它是唯一能同時在 handler 前後做事的關卡（開場問題的最小答案）。
  2. next.handle() 回傳的 Observable 是什麼：用熟悉的 Promise 對照，只學寫 interceptor 需要的 RxJS。
  3. 計時：用 Server-Timing 標頭讓前端在 DevTools 直接看到後端花了多久，並補上最容易漏掉的錯誤回應。
  4. 逾時：外送平台卡住時 1 秒就回「稍後再試」，每個路由各自設上限；以及為什麼「不等了」不代表外送平台的請求停下來了。
  5. 序列化與組裝：回應只送允許清單裡的欄位；三個 interceptor 一起註冊時誰包誰，哪些事它們管不到。
這課會用到：
  • TypeScript 課第 8 課的 Promise：代表一個「之後才會有結果」的值，用 .then 串接、.catch 接錯誤。這課拿它對照 RxJS 的 Observable。
  • 第 6 課的請求生命週期與 Reflector.createDecorator：請求依序經過 middleware、guard、interceptor、pipe 才到 handler；createDecorator 在路由上貼標記，執行時再用 Reflector 讀出來。
  • 第 8 課的錯誤格式與 filter：錯誤回應帶 errorCode 讓前端判斷；丟出去的例外由 filter 統一轉成這個格式。

三件事為什麼不寫在 handler 裡？

最直覺的修法是在每個 handler 裡自己處理：開頭記下時間，回傳前設一個標頭；呼叫外送平台時自己用 Promise.race 跟計時器比賽；回傳訂單前 delete order.customer.phone。訂單追蹤頁只有兩支 API，這樣寫好像還應付得來。

問題在規模。咖啡店的 API 有幾十個路由，每一個都要記得寫這三段。哪天有人新增一個路由忘了其中一段，那支 API 就沒有計時、沒有逾時，或者把手機號碼送出去，而且沒有任何東西會提醒你。這三段程式也跟「查訂單」本身無關，混在 handler 裡，讀程式的人得先分辨哪幾行是業務、哪幾行是例行公事。這類「每個路由都要做、但不屬於任何一個路由」的工作，叫做橫切關注點：它們像一條橫線，切過所有的 controller。

所以要把它們搬到 handler 外面、每個請求都會經過的地方。第 6 課的請求生命週期有好幾個關卡，但前面學過的都做不到我們要的事：

  • middleware 拿不到 guard 用的 ExecutionContext，不知道這個請求會交給哪個 controller 的哪個方法，所以讀不到第 6 課 @AdminOnly 這種貼在路由上的標記；它也拿不到 handler 回傳的值，沒辦法在送出前過濾欄位。
  • guard 只在 handler 之前執行一次，回答「放不放行」，之後的事它看不到。
  • filter 只在出錯時才被叫到，成功的回應不會經過它。

我們要的關卡得同時做到兩件事：在 handler 之前執行（記下開始時間），而且在 handler 之後還拿得到它的結果或錯誤（算出耗時、等太久就放棄、過濾欄位）。這就是 interceptor，中文常譯作攔截器：一個實作 NestInterceptor 介面的 class，它包住 handler，前後都能執行程式，還能改寫 handler 的結果或錯誤。在第 6 課的生命週期圖裡，它是唯一出現兩次的關卡：請求進去時經過一次，回應出來時再經過一次。

「包住」是字面上的意思。interceptor 可以掛在三個層級，每一層包住裡面那一層，像洋蔥一樣：

請求從最外層進去，一路穿過每一層到 handler；handler 的結果再從裡往外，依相反順序穿出來。這課的三個 interceptor 都要套用到每個路由，所以都會註冊在最外圈的全域；同一層有好幾個時誰在外面，最後一節組裝時再談。

一個 interceptor 的骨架長這樣：

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    console.log('handler 之前')                       // ① 進去
    return next.handle().pipe(                        // ② 呼叫裡面那一層（最後是 handler）
      tap(() => console.log('handler 之後')),         // ③ 出來
    )
  }
}

每個請求進來，Nest 會呼叫一次 intercept()，給它兩個參數。context 跟 guard 拿到的是同一種 ExecutionContext：知道這次是哪個 controller 的哪個方法，所以讀得到路由上的標記，也能用 switchToHttp() 拿到 Express 的 req、res。next 代表「洋蔥裡面那一層」，呼叫 next.handle() 就是讓請求繼續往裡走，最裡面是 handler。

這也表示 interceptor 有權決定要不要往裡走：不呼叫 next.handle()，handler 就不會執行。第 19 課的 CacheInterceptor 就是用這招，快取裡有資料時直接回傳，不打擾 handler。

對照開場的三個問題，骨架已經給出最小的答案：在 ① 記下開始時間，在 ③ 算出耗時；在 ② 之後接一個「等太久就放棄」；在 ③ 把回傳值換成過濾後的版本。剩下的問題是 ② 那一行：next.handle() 回傳的不是 Promise，而是一個 Observable，「之後」的程式不能用 await 或 .then，要用 .pipe(tap(…)) 接在後面。要寫得出 ②、③，得先知道 Observable 是什麼。

next.handle() 回傳的 Observable 是什麼？

Observable 來自 RxJS，一個處理「隨時間陸續到來的值」的函式庫。Nest 內部用它把一層層的 interceptor 串起來，所以 next.handle() 交給你的是 RxJS 的物件。你不需要學會整個 RxJS，寫 interceptor 只需要懂一個概念和幾個函式。

Observable 是一個資料來源，可以陸續發出好幾個值，最後以「完成」或「出錯」結束。它跟 Promise 最大的不同是：Observable 本身只是一份「怎麼產生值」的說明，建立時什麼都不會發生。要有人訂閱它，也就是呼叫 subscribe，交給它「收到值怎麼辦、出錯怎麼辦、結束了怎麼辦」幾個回呼，它才開始執行，把值一個個送給訂閱的人。訂閱的人不想再聽了，可以取消訂閱（unsubscribe），之後就不會再收到任何值。用你熟悉的 Promise 對照：

PromiseObservable
值的數量一個零到很多個，最後「完成」或「出錯」
什麼時候開始跑建立時就開始有人 subscribe（訂閱）才開始
能不能取消不能（要另外傳 AbortSignal）取消訂閱（unsubscribe）：不再接收值
串接方式.then()、.catch()、.finally().pipe(operator, operator, …)

表上的「零到很多個值」聽起來複雜，但在 Nest 的 HTTP 請求裡用不到：handler 回傳的值（或 Promise 的結果）會被包成只發出一個值就完成的 Observable。所以寫 HTTP 的 interceptor 時，可以把它想成「會用 pipe 串接的 Promise」：要嘛成功給你一個值，要嘛出錯。

誰來訂閱？不是你，是 Nest。Nest 訂閱最外層 interceptor 回傳的 Observable，拿到值就送出回應，出錯就把錯誤交給第 8 課的 filter。你在 intercept() 裡做的事，是拿 next.handle() 給你的 Observable，加工成一個新的 Observable 回傳出去。外層的 interceptor 又會拿你回傳的去加工，一層層包到最外面。這就是洋蔥在程式裡的樣子。

加工用的工具叫 operator：一個函式，接收一個 Observable、回傳一個加工過的新 Observable。把好幾個 operator 放進 .pipe()，它們會依序套用，就像 Promise 一路 .then().then()。先認識兩個最常用的，都從 'rxjs' import：

  • map(fn)：把值換成 fn(值) 往下傳，等於 .then(v => fn(v))。要改寫 handler 的結果時用它。
  • tap(fn)：看一眼值、做點副作用（記 log、設標頭），值原樣往下傳，等於 .then(v => { fn(v); return v })。骨架的 ③ 用的就是它。

後面處理錯誤和逾時時，會在用到的地方再介紹 catchError、finalize、timeout 三個。這課用到的 operator 全部整理在課末補充與查表，查表用，不用背。

RxJS 的 pipe() 跟 Nest 的 pipe（第 7 課的 ValidationPipe）只是同名，毫無關係。前者是「把 operator 串起來」的方法，後者是在 handler 前轉換、驗證參數的元件。

現在 ①②③ 都讀得懂了：① 在訂閱之前執行，也就是 handler 之前；② 拿到裡面那一層的 Observable；③ 的 tap 在 handler 的值出來時執行。可以開始修第一個問題了：讓前端知道後端到底花了多久。

計時：怎麼讓前端在 DevTools 看到後端花了多久？

耗時量出來之後要放在哪裡？寫進後端的 log，只有後端看得到；前端同事查「轉圈圈」時開的是 DevTools，最好他在那裡就能看到。HTTP 正好有一個為此設計的回應標頭：Server-Timing（標頭見 Node 課第 12 課）。它告訴瀏覽器伺服器端花了多少時間，格式是 名稱;dur=毫秒，例如 Server-Timing: app;dur=12.3。Chrome DevTools 的 Network → Timing 分頁會直接把它畫出來，前端不用翻後端 log，就能分出慢在前端、網路還是伺服器。

把骨架的 ① 換成記下開始時間、③ 換成設標頭，第一版很直覺：

intercept(context: ExecutionContext, next: CallHandler) {
  const start = performance.now()
  const res = context.switchToHttp().getResponse<Response>()
  return next.handle().pipe(
    tap(() => res.setHeader('Server-Timing', `app;dur=${(performance.now() - start).toFixed(1)}`)),
  )
}

這幾行裡有三個選擇，每個都有原因：

用 performance.now() 而不是 Date.now()。Date.now() 讀的是系統時間，伺服器會定期跟時間伺服器校時，校時可能讓系統時間往前或往回跳，兩次相減就可能算出負數或不準的值。performance.now() 是單調時鐘：只會往前走，不受校時影響，而且有小數，量短時間更準。

start 寫在 intercept() 裡。interceptor 跟 service 一樣，預設是第 3 課的 singleton：整個應用程式只有一個實例，所有請求共用。intercept() 每個請求呼叫一次，寫在裡面的 start 才是這個請求自己的開始時間。寫在檔案最上層或 constructor，只會在應用程式啟動時記一次，量到的變成「應用程式啟動到現在」。

在 tap 裡設標頭。標頭必須在回應送出之前設好。tap 執行時，值還在往外傳的路上，Nest 要等值傳到最外面才送出回應，所以這時設的標頭來得及。

寫好之後，要讓每個路由都套用，就把它註冊成全域 interceptor：在 AppModule 的 providers 加上 { provide: APP_INTERCEPTOR, useClass: TimingInterceptor }。這跟第 6 課用 APP_GUARD 註冊全域 guard 是同一種寫法，其他註冊方式留到最後一節。

用 curl -i 打 GET /menu，回應有 Server-Timing。但改打一個不存在的商品 GET /products/999，404 的回應卻沒有這個標頭。

原因在 Observable 的兩個出口。handler 丟出 NotFoundException 時，Observable 發出的不是值，而是錯誤。tap(fn) 只在有值時呼叫 fn，錯誤會直接越過它往外傳，所以 404 沒有標頭。這不是小事：最慢、最需要量的請求，往往就是出錯的那些，例如逾時、資料庫錯誤。計時要可信，兩個出口都得量到。先把設標頭的那段抽成一個函式 record，寫在 intercept() 裡、start 和 res 的下面：

const record = () => res.setHeader('Server-Timing', `app;dur=${(performance.now() - start).toFixed(1)}`)

接著有三種寫法：

// 1. tap 同時給 next 和 error
next.handle().pipe(tap({ next: record, error: record }))

// 2. catchError 記完再丟出去
next.handle().pipe(tap(record), catchError(err => { record(); return throwError(() => err) }))

// 3. finalize：不論成功或失敗都執行
next.handle().pipe(finalize(record))

三種寫法差在把 record 掛在哪個出口：

  • tap({ next, error })：tap 也可以傳一個物件，next 在有值時呼叫，error 在出錯時呼叫。它只是「看一眼」，錯誤照樣往外傳。
  • catchError(fn)：出錯時執行 fn，對應 Promise 的 .catch()。它跟 .catch() 一樣會接住錯誤：fn 回傳的 Observable 會取代原本出錯的那一條。所以只想記錄、不想吞掉錯誤時，要回傳 throwError(() => err)，它建立一個「立刻發出這個錯誤」的 Observable，讓錯誤繼續往外丟。下一節的逾時會用到這個 operator。
  • finalize(fn)：不論成功、出錯或被取消訂閱，結束時都執行，對應 Promise 的 .finally()。

三種在 Nest 12.3.2 實測都會讓 404、409 的回應帶上標頭。不論用哪一種，錯誤本身都要原樣往外丟，第 8 課的 filter 才能照常把它轉成錯誤回應。三種在「被取消訂閱」時的表現不同，最後一節把逾時和計時組在一起時，這個差別會決定標頭還在不在。

💡 實務上：前端回報「好慢」時，先看 Server-Timing
前端說「查外送時間轉很久」，你請他在 DevTools 點開那個請求的 Timing：伺服器時間很短，就是網路或前端的問題；伺服器時間很長，才回頭查後端 log。這能省下很多「是你那邊慢還是我這邊慢」的來回。要注意 Server-Timing 任何人都看得到：只寫總時間沒問題，把 db;dur=…、cache;desc=miss 這類細節也公開，等於告訴攻擊者哪個請求打得到資料庫。正式環境的細項放 log 或追蹤系統（第 24 課）。

有了計時，前端同事在 Timing 裡看到外送時間的請求，伺服器時間真的是 12 秒：後端一直在等外送平台。第一個問題「慢在哪」有答案了，接著是第二個問題：等太久時，怎麼主動放棄？

逾時：外送平台卡住時，怎麼 1 秒就回「稍後再試」？

外送平台卡住時，我們的 API 什麼都不做，就會一直等下去。顧客對著轉圈圈，最後可能是瀏覽器或中間的代理伺服器先放棄，回一個看不懂的錯誤。我們寧可 1 秒就告訴顧客「外送時間暫時查不到，稍後再試」，讓前端顯示一個清楚的畫面。

「等太久就放棄」正是 Observable 擅長的事，因為它能取消訂閱。RxJS 的 timeout(ms) operator：超過 ms 還沒有值，就取消訂閱，不再等裡面那一層，並丟出一個 TimeoutError。用 Promise 要達到同樣效果，得自己用 Promise.race 讓工作跟計時器比賽。官方文件的逾時 interceptor 長這樣：

return next.handle().pipe(
  timeout(5000),
  catchError(err => {
    if (err instanceof TimeoutError) return throwError(() => new RequestTimeoutException())
    return throwError(() => err)   // 其他錯誤原樣丟出
  }),
)

讀法：timeout(5000) 在 5 秒內沒等到值，就丟出 TimeoutError；接著 catchError 接住錯誤，用 instanceof 判斷是不是逾時。是逾時就換成 Nest 的 HTTP 例外，讓 filter 轉成錯誤回應；不是逾時就原樣丟出。這個範例可以直接用，但套到咖啡店之前，有兩個地方要改。

第一個要改的是狀態碼。RequestTimeoutException 是 408 Request Timeout，意思是「伺服器等客戶端把請求送完，等太久了」，是客戶端的問題。我們的情況剛好相反：請求早就收完了，是我們自己處理太慢，應該回 5xx。第 8 課說過 504 是「等上游等到逾時」，看起來很貼切，但一個通用的逾時 interceptor 不知道 handler 是在等外送平台，還是在跑自己的運算，所以不能斷定是上游的錯。這裡用 503 Service Unavailable：暫時無法服務，可以稍後重試。再用第 8 課的寫法，在例外的選項帶上 errorCode: 'TIMEOUT'，前端就能據此顯示「稍後再試」，不用解析訊息文字。範例裡逾時那一行改成：

if (err instanceof TimeoutError) return throwError(() => new ServiceUnavailableException('外送時間暫時查不到，請稍後再試', { errorCode: 'TIMEOUT' }))

ServiceUnavailableException 就是 503，跟 RequestTimeoutException 一樣從 @nestjs/common import；{ errorCode: 'TIMEOUT' } 用的是第 8 課「選項物件放在最後一個參數」的寫法。

換的時候只能換 TimeoutError。如果圖省事把所有錯誤都換成 503，GET /products/999 的 404、庫存不足的 409 全都會變成「稍後再試」，前端會叫顧客一直重試一個永遠不會成功的請求。範例裡 return throwError(() => err) 那一行就是為了讓其他錯誤保持原樣。

第二個要改的是時間。官方範例所有路由都等 5 秒，但每個路由合理的等待時間不同：查菜單應該很快，每日報表本來就慢，外送時間我們只願意等 1 秒。做法是沿用第 6 課的 Reflector.createDecorator，做一個 @Timeout(ms) 貼在路由上，interceptor 執行時讀出來，沒標的路由用預設值：

// timeout.decorator.ts
export const Timeout = Reflector.createDecorator<number>()

// interceptor 裡
const ms = this.reflector.getAllAndOverride(Timeout, [context.getHandler(), context.getClass()]) ?? 3000

// controller
@Get(':orderId/eta')
@Timeout(1000)
eta(…) { … }

getAllAndOverride 依序看方法、再看 controller 上有沒有 @Timeout，回傳第一個找到的值；都沒有就是 undefined，?? 3000 補上預設的 3 秒。這樣逾時仍然是一個全域 interceptor，每個路由都自動有上限，只有需要不同時間的路由才要標。interceptor 能讀到這些標記，靠的就是第一節說的：它拿得到 ExecutionContext，知道這次是哪個方法、哪個 controller。逾時 interceptor 要在 constructor 注入 Reflector，這點在最後一節選註冊方式時會用到。

現在外送平台卡住時，顧客 1 秒就會看到「稍後再試」。但 503 送出去的那一刻，外送平台的那個請求呢？

503 送出去之後，外送平台的請求停了嗎？

沒有。timeout 觸發時做的事是取消訂閱：interceptor 不再等這個結果，馬上回 503。但 handler 已經開始的工作照樣在跑：送往外送平台的 HTTP 請求還在等回應，資料庫查詢還會跑完，跑完的結果沒有人要，就被丟掉。官方文件也寫明，取消訂閱不會中止 handler 已經開始的工作（例如還沒結束的資料庫查詢）。

為什麼停不下來？因為取消訂閱只是「我不聽了」，不是「你停下來」。handler 裡的 await fetch(…) 或資料庫查詢，是在 Observable 之外各自進行的非同步工作；JavaScript 沒有辦法從外面強行中斷一個已經開始的 Promise，除非那個工作本身接受取消的訊號。這跟前面對照表裡 Promise「不能取消」那一格是同一件事。

這在正式環境很要命。想像資料庫因為某個原因變慢：請求逾時，前端收到 503 後重試，重試的請求又開了一句新查詢，而舊的那句還在跑。同時在跑的查詢越來越多，資料庫就更慢，更多請求逾時。interceptor 的逾時讓顧客不用乾等，卻沒有減輕後端的負擔。要讓工作真的停下來，得讓底層的工作自己有期限：

  • 接受 AbortSignal 的工作（fetch、許多 HTTP 客戶端）：呼叫時傳 AbortSignal.timeout(1000)，時間到請求真的被中止（TypeScript 課第 11 課、Node 課第 17 課）。呼叫外送平台就屬於這一種。
  • 資料庫查詢：Prisma 的查詢不接受 AbortSignal，要在資料庫端設 statement_timeout，讓 PostgreSQL 自己停掉太久的查詢（第 16 課）。

兩層逾時的分工是：interceptor 的逾時是給使用者的上限，保證顧客最多等多久；底層工作的逾時要設得比它短，工作在 interceptor 放棄之前就先自己結束，才不會留下沒人等的工作。

💡 實務上：逾時的數字要跟前端、維運一起定
逾時不是隨便填 3000：先問「這個畫面使用者願意等多久」、「上游（外送平台、金流）平常多快、最慢多慢」。設太短，正常請求也被砍；設太長，等於沒設。前端收到 TIMEOUT 要決定怎麼呈現：查詢類可以顯示「稍後再試」或自動重試一次，但「送出訂單」這種會寫入的請求不能盲目重試，因為後端可能其實已經建好訂單。資深工程師會把逾時值寫在一個看得到的地方（decorator 或設定），而不是散落在各處的魔術數字。

前兩個問題都跟「慢」有關。第三個問題不一樣：GET /orders/1 很快，但回應的內容本身就錯了。

手機號碼為什麼會出現在 GET /orders/1 的回應裡？

handler 回傳一個物件，Nest 要把它變成 HTTP 回應的 JSON 字串。這個「把回傳值轉成要送出的格式」的步驟叫序列化（serialization）。Nest 預設的序列化就是直接 JSON.stringify 整個物件：service 從資料庫拿到什麼，客戶端就收到什麼。

追一下 GET /orders/1：OrdersService 查出訂單，連同下單的顧客一起回傳。顧客那筆資料有 phone 欄位（取餐簡訊要用）和 internalNote 欄位（店員要看），service 需要它們，所以不能從資料裡拿掉。handler 原樣回傳，序列化原樣送出，手機號碼和備註就到了前端。而且這不是一次性的意外：哪天資料表多了一個欄位，下一秒它就會出現在 API 回應裡，沒有人會發現。

要擋住它，有兩種思維：

  • 禁止清單：列出不能送的欄位，送出前刪掉，例如 delete body.phone。問題是它預設放行：新增敏感欄位時忘了加進清單，就洩漏了；巢狀的物件，例如訂單裡的 customer，也常被漏掉，第一層的 phone 刪了，customer.phone 照送。
  • 允許清單（allowlist）：只送出明確列出的欄位，沒列到的一律不送。它預設擋下：新增欄位時，最壞的結果是「前端拿不到」，而不是「洩漏」。前端拿不到會有人來問，洩漏卻可能沒人發現。回應用這種。

允許清單要在哪裡執行？跟計時、逾時一樣，它是每個回應都該做的事，而且要在 handler 回傳之後、送出之前改寫結果，正好是 interceptor 加上 map 的工作。這個 interceptor 不用自己寫，NestJS 12 新增了一個現成的：StandardSchemaSerializerInterceptor。

它的做法是：用 zod 這類 Standard Schema 寫出回應的形狀，送出前讓回傳值通過 schema，送出的是 schema 的輸出。第 7 課用 zod 的 schema 驗證進來的請求，這裡反過來，用同一套寫法規定出去的回應。要三個部分配合：

// customer.schema.ts
export const customerResponseSchema = z.object({ id: z.number(), name: z.string(), stamps: z.number() })

// customers.controller.ts
@Get(':id')
@SerializeOptions({ schema: customerResponseSchema })
findOne(…) { return this.customers.find(id) }   // 回傳的物件有 phone、internalNote

// app.module.ts
{ provide: APP_INTERCEPTOR, useClass: StandardSchemaSerializerInterceptor }

schema 檔寫出允許的欄位；@SerializeOptions({ schema }) 把 schema 貼在路由上，跟前一節的 @Timeout 一樣是一個標記；全域註冊的 StandardSchemaSerializerInterceptor 執行時用 Reflector 讀出這個標記，拿 schema 處理回傳值。它需要注入 Reflector，用 APP_INTERCEPTOR 註冊時 Nest 會自動注入。沒有 @SerializeOptions({ schema }) 的路由，回應原樣送出。

允許清單之所以成立，是因為 z.object 的預設行為：解析時丟掉沒列的欄位。customerResponseSchema 只列了 id、name、stamps，所以 phone、internalNote 被丟掉。zod 還有兩種寫法，行為不同，選錯會壞事：

  • z.looseObject 會保留沒列的欄位，正好讓允許清單破功，回應不要用。
  • z.strictObject 遇到多的欄位會丟出錯誤。回傳值裡本來就有 phone，用它每個請求都會失敗，所以回應用 z.object。

回到訂單：GET /orders/1 的手機號碼在巢狀的 customer 裡。schema 只會處理它列出的結構，所以訂單 schema 的 customer 欄位要用同一份 customerResponseSchema，巢狀物件才會一樣被過濾；寫成任意物件就等於沒過濾。handler 回傳陣列時，schema 會套用在每一個元素上，@SerializeOptions 傳單筆的 schema 就好。

反過來，回傳值不符合 schema 時，例如少了 stamps、型別不對，interceptor 會丟出錯誤，回應變成 500，而不是送出一半的資料。這是故意的：前端依賴這個形狀，形狀壞了就是後端的 bug，應該在測試裡抓到，而不是讓前端拿到缺欄位的 200 才在畫面上壞掉。

網路上的教學大多是另一種做法：class-transformer 的 @Exclude() 搭配 ClassSerializerInterceptor。它有一個陷阱，回傳一般物件時完全不起作用，細節見課末補充與查表；新專案用 schema 版。另一種常見的回應 interceptor，是把每個回應都包成 { data: … }，它不解決洩漏問題，要不要用的取捨也放在課末。

💡 實務上：資料表加欄位時，順手看回應 schema
真實的洩漏很少是有人故意送出密碼，多半是「資料表加了 internalNote、passwordHash，沒人想到它會跟著出去」。有回應 schema 之後，新欄位預設不會送出，前端真的需要時，後端再明確加進 schema，PR 裡也看得到「這次 API 多送了什麼」。Code review 時可以問兩件事：這個回應有沒有 schema？巢狀的關聯（訂單裡的顧客、店員）有沒有也過 schema？資安或個資相關的稽核問到「API 會送出哪些欄位」時，schema 就是現成的答案。

三個問題各有一個 interceptor 了：計時、逾時、序列化，三個都要套用到每個路由。最後一步是把它們一起註冊，這時就得決定誰包在誰外面。

三個 interceptor 一起上線：誰包在外面，哪些事它們管不到？

先確認註冊方式。interceptor 的註冊跟第 6 課的 guard 一樣有三個層級：@UseInterceptors() 貼在方法上，只套用到那個路由；貼在 controller 上，套用到整個 controller；全域則在模組的 providers 寫 { provide: APP_INTERCEPTOR, useClass: X }。全域還有另一種寫法 app.useGlobalInterceptors(new X())，寫在 main.ts，但它在模組之外自己 new 物件，Nest 沒辦法注入依賴，逾時和序列化都需要的 Reflector 就拿不到；而且只寫在 main.ts 的設定，測試裡建立的應用程式也沒有它（第 10 課會處理這個問題）。所以三個都用 APP_INTERCEPTOR。

同一層有好幾個時，全域 interceptor 依登記順序由外往內包：先登記的在外層。順序會影響結果，計時和逾時就是一個例子。在 12.3.2 實測，計時用前面第一種寫法 tap({ next, error })，外送平台的路由逾時：

  • 計時登記在逾時前面（計時在外層）：逾時的 interceptor 在裡面丟出 503 的錯誤，錯誤往外傳，經過計時的 error 出口，標頭照樣設上。503 回應帶有 app;dur=1003.8，正好是 1 秒的上限加上一點處理時間。
  • 順序反過來（計時在裡層）：逾時取消訂閱的是它裡面那一層，也就是計時。被取消訂閱的 Observable 不會再發出任何東西，計時既收不到值也收不到錯誤，503 就沒有標頭。
  • 計時在裡層但改用 finalize：finalize 在取消訂閱時也會執行，標頭還在，但它量不到外層 interceptor 花的時間。

結論是計時放最外層，它量到的才是包含所有 interceptor 在內的完整時間，前端在 Timing 看到的數字也才跟實際等待的時間一致。序列化放最靠近 handler，它處理的就是 handler 的回傳值：

providers: [
  { provide: APP_INTERCEPTOR, useClass: TimingInterceptor },                    // 最外層
  { provide: APP_INTERCEPTOR, useClass: TimeoutInterceptor },
  { provide: APP_INTERCEPTOR, useClass: StandardSchemaSerializerInterceptor },  // 最靠近 handler
]

組好之後，訂單追蹤頁的每個請求都會依序穿過這三層：有耗時、有上限、只送允許的欄位。但有兩種情況是 interceptor 管不到的，一種會讓剛修好的洩漏重新出現，一種是把不該放的東西放進來。

handler 用了 @Res()，回應轉換就失效。handler 注入 @Res() res，自己呼叫 res.json(…)，就進入官方文件說的 library-specific 模式：回應由你直接寫給 Express 送出，不再經過 Nest 的回傳值流程。interceptor 還是會執行，但它的 map、序列化都碰不到已經送出的內容，phone 會照送，Nest 也不會警告。除非真的需要自己控制回應（例如串流），handler 都用 return 回傳值。

商業邏輯不放 interceptor。interceptor 適合跟業務無關、每個路由都一樣的事，就是這課的計時、逾時、序列化，還有第 19 課的快取。「下單時順便加點數」如果寫在 interceptor 裡，讀 OrdersService 的人看不到這件事；第 20 課的佇列、第 21 課的排程直接呼叫同一個 service 時，請求沒有經過 interceptor，點數也就不會加。業務規則留在 service 裡。

練習

在 learn/ 執行 node check.mjs nestjs 09 建立 work/09/。起始專案接續第 8 課（request id、兩個 filter 都已經註冊），多了 GET /menu、GET /customers/:id、GET /orders/:id、GET /deliveries/:orderId/eta（呼叫外送平台）、GET /reports/daily（很慢的報表）。要寫的檔案已經有空殼，裡面有註解。可以用 npm run start:dev 啟動，再用 curl -i localhost:3100/menu 看標頭。

練習 1：在 src/interceptors/timing.interceptor.ts 寫 TimingInterceptor，用 APP_INTERCEPTOR 註冊成全域：

  • 每個回應都帶 Server-Timing: app;dur=<毫秒>，包含 404、400、409 這些錯誤回應。
  • 量的是這個請求自己的時間。測試會把報表換成固定 120ms 的假資料，檢查 dur 至少 120、又不能大到像「從啟動開始算」。

練習 2：逾時。

  • 在 src/timeout.decorator.ts 用 Reflector.createDecorator 匯出 Timeout。
  • 在 src/interceptors/timeout.interceptor.ts 寫 TimeoutInterceptor：讀路由或 controller 上的 @Timeout(ms)，沒標就是 3000ms；逾時回 503，errorCode 是 'TIMEOUT'；其他錯誤原樣往外丟。用 APP_INTERCEPTOR 註冊（想想它跟計時的先後）。
  • 外送平台最多等 1 秒：在 GET /deliveries/:orderId/eta 加上 @Timeout(1000)。

測試會另外加一個自己的 controller，裡面有一條 @Timeout(100)、跑 1000ms 的路由，還有一個整個貼了 @Timeout(100) 的 controller，所以逾時要寫在全域 interceptor，路由和 controller 上的值都要讀得到。逾時的 503 也要有練習 1 的 Server-Timing。

練習 3：GET /customers/:id 只能送出 id、name、stamps；GET /orders/:id 送出訂單的所有欄位，但裡面的 customer 也只能有這三個欄位。

  • 在 customer.schema.ts、order.schema.ts 用 zod 寫 customerResponseSchema、orderResponseSchema，用 @SerializeOptions({ schema }) 套到兩個路由，並註冊 StandardSchemaSerializerInterceptor。
  • CustomersService 的資料不能改：取餐簡訊要用 phone，店員要看 internalNote。

測試比對整個回應，每一層都不能多、不能少欄位。測試也會讓 CustomersService 回傳少了 stamps 的顧客，這時要回 500，不能送出缺欄位的 200，所以不能在 controller 裡自己挑欄位。

練習 4：計時 interceptor 寫成 next.handle().pipe(tap(() => res.setHeader('Server-Timing', …)))。handler 丟出 NotFoundException 時，404 回應有這個標頭嗎？

✓ Observable 出錯時，tap(fn) 的 fn 不會被呼叫，錯誤直接往外傳。a 是把 tap 當成 finally；finalize 才是。b 錯：filter 只負責轉換錯誤，不會知道 interceptor 本來想設什麼標頭。

練習 5：報表路由貼了 @Timeout(3000)，handler 裡的資料庫查詢跑了 10 秒。3 秒時 interceptor 回了 503，那句查詢會怎樣？

✓ 取消訂閱只代表「不等這個結果了」，已經開始的工作不會停，官方文件也這樣寫。b 是最常見的誤解：只有接受 AbortSignal、或有自己期限的工作才會真的停。c 錯：503 在 3 秒時就送出，這正是逾時的用意。

練習 6：全域註冊了 StandardSchemaSerializerInterceptor，某個 handler 改成注入 @Res() res，自己呼叫 res.json(customer)。回應會怎樣？

✓ 注入 @Res() 進入 library-specific 模式，回應由 handler 直接寫給 Express，interceptor 的回應轉換拿不到這個值。a 錯：interceptor 還是會執行，但改不到已經送出的內容。c 錯：Nest 不會阻止，所以這種洩漏很難發現。

常見錯誤

  • 把 RxJS 的 pipe 跟 Nest 的 pipe 搞混：next.handle().pipe(…) 是串接 operator；Nest 的 pipe 是轉換、驗證參數的元件。兩者無關。
  • 只用 tap(fn) 記錄結果：錯誤時不會執行，最該記錄的慢請求、失敗請求反而沒有紀錄。用 tap({ next, error }) 或 finalize。
  • 計時的開始時間寫在檔案最上層或 constructor：interceptor 是 singleton，量到的是應用程式啟動到現在。在 intercept() 裡記。
  • 以為 timeout 會取消工作：它只是不等了。底層的 HTTP 請求要傳 AbortSignal，資料庫要設 statement_timeout。
  • catchError 把所有錯誤都變成同一種：404、409 也變成 503，前端會一直重試不可能成功的請求。只轉換 TimeoutError，其他用 throwError(() => err) 原樣丟出。
  • 逾時回 408：408 是客戶端送請求太慢。自己處理太慢是 503（加上 errorCode）。
  • 計時登記在逾時後面：計時變成裡層，逾時取消訂閱時它收不到值也收不到錯誤，503 沒有 Server-Timing。計時登記在最前面，當最外層。
  • 序列化只處理第一層：在 controller 裡 delete body.phone，訂單裡的 customer.phone 照樣送出。用允許清單的 schema，巢狀物件也用 schema。
  • ClassSerializerInterceptor 配上回傳一般物件的 service：@Exclude 只對 class 實例有效，欄位照送。
  • 把商業邏輯寫進 interceptor：藏在看不到的地方，換一個入口（佇列、排程）就不會執行。interceptor 只做跟業務無關的橫切工作。

小結

  • 計時、逾時、序列化是每個路由都要做、但不屬於任何路由的事，放在 interceptor，不寫在每個 handler 裡。
  • interceptor 包住 handler：next.handle() 之前是「進去」，接在它後面的 operator 是「出來」；進去時全域 → controller → 路由，出來時反過來。不呼叫 next.handle()，handler 就不會執行。
  • next.handle() 回傳 Observable，HTTP 請求裡只有一個值。Nest 負責訂閱，你用 pipe 串 map、tap、catchError、timeout、finalize 加工後回傳。
  • 計時用 Server-Timing 讓前端在 DevTools 看到後端耗時；每個請求在 intercept() 裡記開始時間，錯誤路徑也要量。
  • 逾時用 timeout(ms) 加 @Timeout(ms)，只把 TimeoutError 轉成 503＋TIMEOUT。逾時只是不等了，底層工作要自己有更短的期限。
  • 回應用允許清單：v12 的 StandardSchemaSerializerInterceptor＋@SerializeOptions({ schema })，巢狀物件也要過 schema；不符合就是 500。
  • 全域用 APP_INTERCEPTOR 註冊，依登記順序由外往內包，計時放最外層；@Res() 會讓回應轉換失效；商業邏輯留在 service。

會保留沒列欄位的 z.looseObject，舊名是 passthrough。在舊專案的回應 schema 看到 .passthrough()，代表那個回應沒有過濾欄位。

舊做法：ClassSerializerInterceptor 與 @Exclude

網路上大多是 class-transformer 的寫法：在 class 的欄位貼 @Exclude()，註冊 ClassSerializerInterceptor。它有一個陷阱：只對 class 的實例有效。service 回傳一般物件（Prisma 查詢的結果就是），@Exclude 完全不起作用，欄位照送。要用它，每個 handler 都得 new CustomerEntity(data) 或 plainToInstance，忘了一個就洩漏。新專案用 schema 版。

要不要包一層 { data }

常見的另一種 interceptor 是用 map(data => ({ data })) 把每個回應包成 { data: … }。取捨：多數 API 不需要，HTTP 狀態碼和標頭已經能表達成功與否；包了之後每個前端呼叫都要多寫 .data，錯誤回應（filter 產生的）又不會被包，格式反而不一致。只有回應真的需要附帶資料時才包，例如分頁的 { data, total, nextCursor }（第 16 課），而且寫在那個 handler 的回應型別裡就好。
