階段 1：從 Node 到 NestJS（框架的骨架） · 第 4 課

Module：切分功能與封裝

到目前為止，所有 controller 和 provider 都登記在 AppModule。咖啡店只有菜單時沒問題；等商品、訂單、收據、會員點數都進來，AppModule 會變成一份幾十行的清單。清單裡的任何 service 都能注入任何 service，沒有人說得出「訂單功能到底依賴了什麼」，也沒有人能保證改了商品的資料存法不會弄壞訂單。

這一課的任務，就是練習用的 work/04 專案：一個所有東西都擠在 AppModule 的咖啡店後端。我們要把它整理成一個個功能模組：商品和訂單各自管好自己的東西，只開放該開放的；收據做成一個模組，讓信義店和板橋店各自帶入店名；菜單在開始接請求之前就載好，關機時把連線收乾淨。每一節都在解決整理途中遇到的下一個問題。

這課的路線：
  1. AppModule 一份清單缺了什麼、怎麼讓訂單用到商品卻碰不到商品的 repository：Nest 的 @Module 跟檔案的 import 管的事不同，provider 要給別的模組用，提供方 export、使用方 import。
  2. 搬家後啟動失敗：Nest can't resolve dependencies 怎麼逐段讀出「要在哪個模組修」，以及「再登記一次」為什麼會讓店長新增的商品，下單時卻找不到。
  3. 能不能乾脆設成全域、同一個收據模組怎麼讓兩家分店各印各的店名：@Global 的代價，以及在 import 時帶設定的動態模組。
  4. 菜單要在開門前載好、關機前收尾：這類工作寫在哪個方法、照什麼順序執行。
這課會用到：
  • 第 3 課的 provider 與 token：交給容器建立的物件叫 provider，容器用 token（通常就是 class 本身）找它；useFactory 用函式產生值，inject 列出這個函式要注入的 provider。

AppModule 一份清單，到底缺了什麼？

先看現在的 work/04 怎麼運作。第 1 課說過，Nest 只認得登記在模組裡的東西：main.ts 把 AppModule 交給 Nest，Nest 讀它的 providers，把每一個 provider 建好放進容器；之後任何建構子要什麼，容器就從這裡找。所有東西都登記在同一個模組，等於所有東西都在同一個房間裡，彼此都拿得到。

拿得到聽起來方便，問題出在「拿得到」沒有任何限制。OrdersService 想直接讀 ProductsRepository 裡的資料，Nest 不會阻止；過半年，商品資料的存法要換，你得先搜尋整個專案，才知道有哪些地方偷偷碰了 repository。這就是開場說的「說不出訂單依賴了什麼」：依賴關係沒有寫在任何一個地方。

Nest 的解法是把應用切成好幾個模組，每個模組自己決定哪些東西給外面用。在動手之前，要先分清楚一件很容易混淆的事：「模組」這個詞在 Nest 專案裡有兩個意思，管的事完全不同。

ES module（檔案）Nest 模組（@Module）
是什麼一個 .ts 檔案一個加了 @Module() 的 class
管什麼這個檔案能不能引用另一個檔案的 class、函式這個 class 能不能被注入到某個建構子裡
誰檢查TypeScript 與 Node（找不到檔案就報錯）Nest 的 DI 容器，在應用啟動時檢查
寫法import { ProductsService } from './products.service.js'@Module({ imports: [ProductsModule] })

檔案層級的 import／export 是 Node 課第 4 課教的東西，它只處理「這個檔案看不看得到那個名稱」。兩者互不代替：orders.service.ts 用 import 引用了 ProductsService，只代表這個名稱在檔案裡拿得到。第 3 課說過，編譯器會把建構子參數的 class 記成 design:paramtypes，Nest 靠這份紀錄知道要注入什麼；檔案 import 只是讓這份紀錄寫得出 ProductsService，不代表 Nest 找得到它。Nest 會不會真的把一個 ProductsService 交給 OrdersService，要看 @Module 的設定。這一課的錯誤幾乎都出在「檔案 import 了，Nest 模組卻沒設定」。

分清楚之後，就可以開始搬家：把商品的東西搬進 ProductsModule、訂單的東西搬進 OrdersModule。但訂單需要商品的價格，搬開之後，OrdersService 要怎麼拿到 ProductsService？

怎麼讓訂單用到商品，卻碰不到商品的 repository？

答案在 @Module() 的設定裡。把同一個功能的 controller、service 收在一起的 Nest 模組，叫做功能模組（feature module），例如 ProductsModule、OrdersModule。@Module() 有四個欄位，前兩個你在 AppModule 已經用過，後兩個負責模組之間的往來：

欄位放什麼意思
providersprovider（@Injectable class 或第 3 課的自訂 provider）由這個模組建立、在模組裡可以互相注入
controllerscontroller這個模組負責的路由
imports只能放模組要使用哪些模組開放出來的 provider
exports自己的 provider（或 import 進來的模組）開放給「import 我的模組」使用

這四個欄位背後是一條規則：provider 預設只在自己的模組裡看得到，模組外面的人既看不到、也注入不了。把內部細節藏起來、只透過明確開放的入口往來，這個設計叫封裝（encapsulation）。它正好補上一節缺的東西：依賴關係被迫寫在 imports 和 exports 上，不再藏在程式各處。

所以別的模組要用一個 provider，兩個條件缺一不可：提供的一方把它放進 exports，使用的一方把提供方的模組放進 imports。可以把模組想成有圍牆的院子：

寫成程式，就是練習 1 要你做的形狀：

// products/products.module.ts
@Module({
  controllers: [ProductsController],
  providers: [ProductsService, ProductsRepository],
  exports: [ProductsService],            // 只開放 service，repository 留在裡面
})
export class ProductsModule {}

// orders/orders.module.ts
@Module({
  imports: [ProductsModule],             // 要用 ProductsModule 開放的東西
  controllers: [OrdersController],
  providers: [OrdersService],            // OrdersService 的建構子可以注入 ProductsService
})
export class OrdersModule {}

// app.module.ts：根模組只負責把功能模組組起來
@Module({ imports: [ProductsModule, OrdersModule] })
export class AppModule {}

讀這段程式時，注意 AppModule 變成了什麼：它不再自己登記 service，只 import 功能模組。Nest 從 AppModule 開始，沿著 imports 一層層找到 ProductsModule、OrdersModule，各自建立它們的 provider。AppModule 因此叫根模組：整棵模組樹從它長出來。

為什麼不把 ProductsRepository 也 export，讓訂單想用什麼就用什麼？因為 export 出去的東西就是公開介面：別的模組會開始依賴它，你就不能再隨意改它。一旦訂單模組直接讀 repository，商品模組以後要改資料的存法（第 13 課換成資料庫）、要加「下架的商品不能賣」的規則，就得連訂單一起改，而且很容易漏掉。只開放 service，商品的規則集中在一個地方，訂單只透過 service 的方法拿資料。這跟 Vue 元件只透過 props／emits 溝通、不去改別的元件內部 state 是同一個道理。

💡 實務上：模組照業務功能切，exports 就是對外的承諾
工作上的 Nest 專案通常一個業務功能一個資料夾、一個模組：咖啡店會有 ProductsModule、OrdersModule、MembersModule，而不是 ServicesModule、ControllersModule 這種按技術分類的切法。code review 時資深工程師會特別看 exports 的變動：多 export 一個東西，就多一個別的團隊可能依賴、以後改不動的地方，所以會先問「對方真的需要這個，還是需要 service 上的一個新方法？」。一開始不確定怎麼切也沒關係，先照功能粗切，等某個模組變太大或兩個功能老是一起改，再拆或合併。建立新模組的 CLI 指令見課末。

規則聽起來簡單，但搬家的時候很難一次做對。最常見的情況是：OrdersService 搬進 OrdersModule 了，imports 卻忘了寫，存檔後應用直接起不來。

搬家後啟動失敗：Nest can't resolve dependencies 在說什麼？

忘了在 OrdersModule import ProductsModule，啟動時會看到下面這段錯誤（專案用的 Nest 12.3.2 實際輸出）。這是 Nest 專案最常見的啟動錯誤，值得一次學會怎麼讀：

ERROR [ExceptionHandler] UnknownDependenciesException [Error]: Nest can't resolve
dependencies of the OrdersService (?). Please make sure that the argument
ProductsService at index [0] is available in the OrdersModule module.

Potential solutions:
- Is OrdersModule a valid NestJS module?
- If ProductsService is a provider, is it part of the current OrdersModule?
- If ProductsService is exported from a separate @Module, is that module imported within OrdersModule?

Nest 在啟動時要建立 OrdersService，於是看它的建構子要哪些參數，再一個一個去找。找不到其中一個，就停下來告訴你三件事：

  • dependencies of the OrdersService (?)：括號裡是建構子參數的清單，? 標出解析失敗的那一個。如果建構子有三個參數、第二個失敗，會是 (ConfigService, ?, Logger)。
  • the argument ProductsService at index [0]：失敗的參數是誰、第幾個（從 0 算）。
  • is available in the OrdersModule module：Nest 是在哪個模組找的。這一句最重要：問題要在這個模組的 providers 或 imports 修。

知道「在哪個模組找」之後，再對照上一節的兩個條件，就能縮小範圍。同一句訊息有三種常見原因：

原因怎麼認出來修法
沒 import 提供的模組訊息說在 OrdersModule 找，OrdersModule 的 imports 沒有 ProductsModule加進 imports
有 import，但對方沒 export訊息一模一樣；用下面的 NEST_DEBUG 才看得出 Nest 有去 ProductsModule 找但沒拿到在 ProductsModule 加 exports
import type（第 3 課）參數名稱變成 Function（nest build 後）或 undefined，不是 class 名稱改回一般的 import

第三種最好認，因為訊息裡的名稱不對。前兩種的訊息完全相同，因為從 OrdersModule 的角度看結果一樣：都拿不到。要分辨，得看 Nest 找的過程。設環境變數 NEST_DEBUG=1 啟動，Nest 會印出每一步解析過程（在 work/04 先 npm run build，再 NEST_DEBUG=1 node dist/main.js）：

LOG [InjectorLogger] Resolving dependency ProductsService in the OrdersService provider
LOG [InjectorLogger] Looking for ProductsService in OrdersModule
LOG [InjectorLogger] Looking for ProductsService in ProductsModule
LOG [InjectorLogger] Looking for ProductsService in InternalCoreModule
ERROR [ExceptionHandler] UnknownDependenciesException …

這段是「有 import、沒 export」的情況：Nest 有走進 ProductsModule 找，但它沒有開放 ProductsService，所以找不到。如果是沒 import，中間那行 Looking for … in ProductsModule 根本不會出現，因為 Nest 只會去 imports 列出的模組找。

搬家時還有一種寫法會讓 Nest 報另一個錯：知道「要用就得 import」，於是把 service 本身放進 imports。imports 只能放模組，Nest 12 的訊息直接說了怎麼修：

InvalidClassModuleException [Error]: "OrdersService" is decorated with @Injectable() and cannot
appear in the "imports" array of a module. Please move "OrdersService" to the "providers" array
of the importing module instead.

Scope [AppModule -> OrdersModule]

Scope 那一行是從根模組一路 import 下來的路徑，告訴你是哪個模組寫錯：這裡是 AppModule import 的 OrdersModule。

讀懂訊息後，修法就是補上 imports 或 exports。但很多人第一次看到「在 OrdersModule 找不到 ProductsService」，會選另一條看起來更直接的路：把 ProductsService 也登記進 OrdersModule。錯誤確實會消失，問題卻才剛開始。

錯誤消失了，商品卻不見了：為什麼不能再登記一次？

照著「找不到就登記進來」的直覺，OrdersModule 會長這樣（ProductsService 需要 ProductsRepository，所以也一起登記）：

@Module({
  controllers: [OrdersController],
  providers: [OrdersService, ProductsService, ProductsRepository],   // ✗ 自己再建一份
})
export class OrdersModule {}

應用可以啟動了，但要理解哪裡出錯，得先知道 Nest 怎麼建立 provider：每個模組會替自己 providers 裡的每一項建立一個實例。同一個 class 出現在兩個模組的 providers，Nest 不會合併，也不會報錯，就是建兩個。

所以現在應用裡有兩個 ProductsRepository：ProductsController 用的是 ProductsModule 那個，OrdersService 用的是 OrdersModule 自己那個。店長用 POST /products 新增「燕麥拿鐵」，資料寫進第一個；客人下單時 OrdersService 去第二個找，回 404「找不到商品」。啟動時一切正常，錯誤要到執行時、而且要兩個功能交錯使用才會出現，所以比啟動錯誤難查得多。快取、計數器、連線池這類有狀態的 provider 被複製一份，都會出現這種「明明有存，另一邊卻看不到」的問題。

原則：一個 provider 只在一個模組的 providers 出現，別的模組要用就 imports 那個模組。第 3 課說的 singleton（整個應用共用一個實例），是在「每個模組只登記一次」的前提下才成立。練習 1 的測試會檢查這一點。

到這裡，商品和訂單的拆分已經完整了。但專案裡不只兩個模組，如果十個模組都要用 ProductsService，每個都寫一次 imports 似乎很囉嗦。Nest 確實有讓你省掉這行的做法。

乾脆設成全域，不就不用 import 了？

這個做法是 @Global()。在模組加上它，這個模組 export 的 provider 就變成全域的：任何模組不用寫 imports 都能注入。實例仍然只有一個，所以不會有上一節「兩份資料」的問題。

@Global()
@Module({ providers: [ProductsService, ProductsRepository], exports: [ProductsService] })
export class ProductsModule {}   // 只要 AppModule import 一次，到處都能注入 ProductsService

少寫的只是一行 imports，但這行正是封裝用來記錄依賴的地方。省掉它，開場的老問題就回來了：

  • 依賴關係看不見：打開 OrdersModule，看不出它依賴商品功能。新同事、code review、第 26 課的架構檢查都靠 imports 判斷模組之間的關係。
  • 模組不能單獨使用：第 5 課寫測試時，會用 Test.createTestingModule({ imports: [OrdersModule] }) 只拿這些模組組一個小應用。這時 OrdersModule 會建立失敗，因為它偷偷依賴一個沒被 import 的全域模組。練習 1 的測試就是這樣檢查的。
  • 很難換掉：哪些地方用到了它，只能全文搜尋。

Nest 官方文件也不建議把什麼都設成全域。適合 @Global 的只有「幾乎每個模組都要、而且整個應用只有一份」的基礎設施：設定（第 11 課 ConfigModule 的 isGlobal: true）、資料庫連線（第 13 課起的 Prisma）。這類東西每個模組都要，寫在 imports 上也看不出什麼資訊。商品、訂單這種業務功能一律明寫 imports。全域模組本身也只該由根模組 import 一次。

到目前為止，共用的都是「整個應用一份、設定也只有一組」的 provider。任務清單上的收據不一樣：同一個收據功能，信義店和板橋店要印不同的店名。

同一個收據模組，兩家分店怎麼各印各的店名？

小明咖啡有信義、板橋兩家分店，共用同一個後端：同一個程序裡有信義店的點餐模組，也有板橋店的點餐模組，兩邊都要印收據。收據的邏輯兩家店一樣，只有店名和結尾的問候語不同，所以應該只寫一個 ReceiptModule。問題是店名放哪裡。寫死在模組裡，兩家店就得各複製一份模組；讓 ReceiptService 自己去讀 process.env，整個程序只有一組環境變數，兩家店還是分不開，測試也很難換成別的值。

比較好的做法是反過來：讓使用模組的人在 import 時把設定傳進去，就像呼叫函式時傳參數：

@Module({ imports: [ReceiptModule.register({ shopName: '小明咖啡 信義店', footer: '謝謝光臨' })] })
export class XinyiOrdersModule {}

@Module({ imports: [ReceiptModule.register({ shopName: '小明咖啡 板橋店' })] })
export class BanqiaoOrdersModule {}

注意 imports 裡放的不是 ReceiptModule 這個 class，而是 ReceiptModule.register(…) 的回傳值。這個回傳值叫動態模組（dynamic module）。前面寫的模組都是固定的：@Module() 裡列了什麼，就是什麼。動態模組則是一個在執行時才組出來的物件 { module: ReceiptModule, providers: [...], exports: [...] }，比固定的模組多了一個 provider，裡面存的就是這次傳進來的設定。ReceiptService 注入這個 provider，就拿得到店名。

為什麼設定要放進 DI，而不是存在檔案裡的變數（let currentOptions）？因為同一個模組可以被註冊很多次：上面的 XinyiOrdersModule 和 BanqiaoOrdersModule 各 register 一次，每次都是獨立的動態模組、各有自己的設定 provider。存在模組層級的變數只有一份，後註冊的會蓋掉先註冊的，兩家店最後都印同一個店名。

動態模組可以手寫，同步版本不難；但通常還要支援 registerAsync，讓設定可以等別的 provider 算出來（例如從 ConfigService 讀），這部分的樣板就很長。Nest 提供 ConfigurableModuleBuilder，一次產生這些東西。先定義設定的形狀，再讓 builder 產生模組的基底：

// receipt/receipt.module-definition.ts
import { ConfigurableModuleBuilder } from '@nestjs/common'

export interface ReceiptModuleOptions {
  shopName: string
  footer?: string
}

export const { ConfigurableModuleClass, MODULE_OPTIONS_TOKEN } =
  new ConfigurableModuleBuilder<ReceiptModuleOptions>().build()

build() 回傳兩樣東西，分別解決「怎麼註冊」和「怎麼拿到設定」：

  • ConfigurableModuleClass：已經有靜態方法 register() 和 registerAsync() 的 class，你的模組 extends 它。
  • MODULE_OPTIONS_TOKEN：設定物件的 injection token（第 3 課），在 service 裡用 @Inject(MODULE_OPTIONS_TOKEN) 拿到傳進來的設定。
// receipt/receipt.module.ts
@Module({ providers: [ReceiptService], exports: [ReceiptService] })
export class ReceiptModule extends ConfigurableModuleClass {}

// receipt/receipt.service.ts
@Injectable()
export class ReceiptService {
  constructor(@Inject(MODULE_OPTIONS_TOKEN) private readonly options: ReceiptModuleOptions) {}
}

ReceiptModule 本身仍是一般的模組，照樣用 providers、exports 管封裝；extends 只是讓它多了 register 這些靜態方法。每次 register，MODULE_OPTIONS_TOKEN 就對應到那次傳進來的設定。

設定要從別的 provider 取得時，用非同步版本。寫法跟第 3 課的 useFactory 一樣：imports 列出工廠需要的模組、inject 列出要注入的 provider：

ReceiptModule.registerAsync({
  imports: [SettingsModule],
  inject: [ShopSettings],
  useFactory: async (settings: ShopSettings) => ({ shopName: settings.name }),
})

你以後 import 的套件模組，方法名稱不一定叫 register，也常見 forRoot、forFeature。名稱代表設定一次還是每次都設，對照表放在課末。

💡 實務上：你會常「用」動態模組，比較少「寫」
日常開發大多是在 import 別人做好的動態模組：設定、資料庫、JWT、佇列這些套件幾乎都用 forRoot／register 帶設定。自己寫可設定的模組，通常是同一段功能要在好幾個地方（或公司裡好幾個專案）用不同設定註冊，例如這課多分店的收據、包一個內部的金流或簡訊 client。如果模組只會被用一次、設定也只有一組，直接寫一般模組、在 service 裡注入設定就好，不用為了「以後可能要共用」先做成動態模組。

模組怎麼切、怎麼共用、怎麼帶設定都處理完了，任務還剩最後一項。work/04 的 MenuService 要從 MenuSource 載入菜單，而載入是非同步的：要在什麼時候做，才能確定第一個客人看到的不是空菜單？

菜單要在開門前載好：啟動和關機的工作寫在哪？

直覺是寫在 MenuService 的建構子裡，但建構子做不到。建構子不能是 async，new MenuService(…) 一定立刻回傳物件；Nest 呼叫完建構子就繼續建立下一個 provider，不會等你在裡面啟動的 Promise。結果是應用已經開始接請求，菜單可能還沒載完。

需要的是一個「所有物件都建好之後、開始接請求之前」的時間點，而且 Nest 要等這裡的工作做完。關機也有對應的需求：關閉連線、把 log 寫完，要在程序真的結束前做完。Nest 為這些時間點提供生命週期鉤子（lifecycle hooks）：在 provider、controller 或模組 class 上實作特定名稱的方法，Nest 會在那個時間點呼叫它。一共五個：

方法什麼時候呼叫
onModuleInit()所在模組的依賴都解析完之後
onApplicationBootstrap()所有模組都初始化完，開始聽 port 之前
onModuleDestroy()開始關機（app.close()，或收到 SIGTERM 這類要程序結束的訊號）
beforeApplicationShutdown(signal)所有 onModuleDestroy 都完成之後，關閉 HTTP 連線之前
onApplicationShutdown(signal)連線都關了之後，關機的最後一步

每個 hook 都可以是 async，Nest 會等它的 Promise 完成才往下走。這正是建構子缺的那一塊，所以非同步的初始化要寫在 onModuleInit 並 await：

@Injectable()
export class MenuService implements OnModuleInit {
  private items: Drink[] = []
  constructor(private readonly source: MenuSource) {
    // ✗ this.source.load().then(m => this.items = m)：建構子不能 await，Nest 不會等，第一個請求可能拿到空菜單
  }

  async onModuleInit() {
    this.items = await this.source.load()   // ✓ app.init() 會等這裡完成
  }
}

implements OnModuleInit（TypeScript 課第 23 課）不是必要的，Nest 只看有沒有這個方法；但加上之後方法名打錯，TypeScript 會報錯，不會變成一個永遠不被呼叫的方法。

這些 hook 什麼時候會被觸發？前兩個在 app.init() 或 app.listen() 時觸發；後三個在呼叫 app.close() 時觸發。正式環境裡，部署平台要停掉程序時會送 SIGTERM 訊號（Node 課第 21 課）。要讓 SIGTERM 也觸發關機 hook，main.ts 要呼叫 app.enableShutdownHooks()，預設沒有開，第 24 課會加上並講優雅關機的完整流程。關機 hook 的 signal 參數是觸發關機的訊號名稱，例如 'SIGTERM'；直接 app.close() 時是 undefined。

hook 不只能寫在 provider 上，也能寫在模組 class 上。練習 3 就會讓 AppModule 也實作 onModuleInit：

@Module({ imports: [MenuModule] })
export class AppModule implements OnModuleInit {
  onModuleInit() { /* 所有依賴都建好之後執行 */ }
}

練習 3 還要在 AppModule 的關機 hook 裡記一行 log。記錄訊息用 Nest 內建的 Logger（從 @nestjs/common import）：private readonly logger = new Logger('AppModule')，再 this.logger.log('…')。輸出會帶上 [AppModule] 這個名稱，看 log 時知道是誰寫的；log 的格式與該記什麼在第 24 課。

知道每個 hook 什麼時候被呼叫還不夠。MenuService 和 AppModule 都實作了 onModuleInit，兩個誰先？

好幾個模組都有 hook，誰先誰後？

Nest 依模組在模組樹裡的位置決定順序（規則來自官方 lifecycle 文件與 @nestjs/core 12.3.2 的原始碼）：

  • 以模組為單位，一個模組的 hook 全部完成，才換下一個模組。
  • onModuleInit、onApplicationBootstrap：離根模組越遠（被 import 得越深）的模組越先，全域模組也在前面，根模組最後。
  • 同一個模組裡，被依賴的 provider 先、依賴別人的後；模組 class 本身在它的 provider 之後。
  • 三個關機 hook：模組的順序反過來，根模組先、最深的模組最後。

這個順序的用意是讓「被依賴的先準備好、最後才關」成立：被 import 的模組通常是別人依賴的基礎，例如資料庫模組，它在業務模組之前連線，關機時等業務模組都收尾了才斷線。

但不要把業務邏輯建立在兩個不相干的模組誰先誰後上。這個順序是框架的實作，Nest 11 升到 12 時就改過一次（見課末版本備註）。真的有先後需求，就讓後者注入前者：Nest 一定先建好被注入的那一個，依賴關係本身就保證了順序。

💡 實務上：onModuleInit 適合「沒準備好就不該開門」的工作
常見用法是啟動時確認資料庫或 Redis 連得上、把很少變的資料（菜單、分店設定）先載進記憶體（代價是資料改了要重啟或另外做重新載入才會生效）。好處是失敗就直接啟動失敗，有做健康檢查的部署流程會看到新版本起不來而不切換流量，比上線後才在第一個請求出錯好查。要注意的是這裡的工作會拖慢每次啟動和部署，所以不要在這裡跑大量資料的同步或要等很久的外部 API。關機 hook 則用來關連線、把還沒送出的 log 寫完；記得上面說的 enableShutdownHooks() 預設沒開，沒開的話部署時舊版本收到 SIGTERM 不會跑這些 hook。

到這裡，work/04 的整理工作都講完了：商品、訂單各自封裝，收據模組帶設定註冊，菜單在開門前載好。接下來動手做一次。

練習

在 learn/ 執行 node check.mjs nestjs 04（用法見第 1 課）建立 work/04/。起始專案能啟動：商品、訂單的 controller 和 provider 都擠在 AppModule，src/products/products.module.ts 和 src/orders/orders.module.ts 是空的模組。

練習 1：把商品和訂單拆成功能模組。ProductsModule 登記 ProductsController、ProductsService、ProductsRepository，只 export ProductsService；OrdersModule 登記 OrdersController、OrdersService，並取得 OrdersService 需要的 ProductsService；AppModule 只 import 功能模組（原本的 MenuModule 留著）。

建議先故意只做一半：把 OrdersService 搬進 OrdersModule 但先不處理它的依賴，執行 npm run start:dev 讀一次錯誤訊息，找出它說「在哪個模組找」，再修好。完成後用 curl -X POST localhost:3100/products -H 'content-type: application/json' -d '{"name":"燕麥拿鐵","price":130}' 新增商品，再用回傳的 id 下單（POST /orders，內容 {"productId":7,"quantity":2}），確認總額是 260。測試會檢查每個模組的設定，也會只建立 OrdersModule 確認它能單獨存在，所以 @Global 或把 ProductsService 再登記一次都過不了。

練習 2：在 receipt.module-definition.ts 用 ConfigurableModuleBuilder<ReceiptModuleOptions> 產生並 export ConfigurableModuleClass 與 MODULE_OPTIONS_TOKEN，讓 ReceiptModule extends 它，得到 register(options) 和 registerAsync(…)（不要自己手寫這兩個方法）。ReceiptService 注入設定，render(order) 回傳以 \n 連接的幾行文字：第一行店名；第二行 品名 x數量 小計；第三行 合計 金額；有 footer 才加第四行。例如 register({ shopName: '小明咖啡' }) 時，拿鐵 3 杯是：

小明咖啡
拿鐵 x3 330
合計 330

測試會用不同的店名註冊兩次，兩邊的收據要各印各的；也會用 registerAsync({ imports, inject, useFactory }) 註冊。

練習 3：起始的 MenuService 菜單是空的，GET /menu 回 []。請完成：

  • MenuService 在 onModuleInit 用 await this.source.load() 載入菜單，完成後 lifecycleLog.push('MenuService.onModuleInit')（lifecycleLog 從 src/lifecycle-log.ts import）。
  • MenuService 在 onApplicationShutdown 等 this.source.close() 完成，再 push 'MenuService.onApplicationShutdown'。
  • AppModule 在 onModuleInit push 'AppModule.onModuleInit'；在 onApplicationShutdown(signal) 用 new Logger('AppModule') 的 .log(…) 記下包含 signal 的訊息（例如 收到 SIGTERM，應用程式關閉），並 push `AppModule.onApplicationShutdown:${signal}`。

測試會把 MenuSource 換成很慢的假物件，確認 app.init() 真的等菜單載入完、app.close() 真的等清理完成；關機會分別用 'SIGINT' 和 'SIGTERM' 測，signal 要用參數，不能寫死。最後檢查 lifecycleLog 的順序。先想想四個字串會以什麼順序出現，再跑測試對答案。

練習 4：ProductsService 在 ProductsModule 的 providers 裡，OrdersModule 也 import 了 ProductsModule，注入 ProductsService 還是出現 Nest can't resolve dependencies of the OrdersService (?)。最可能缺了什麼？

✓ import 一個模組只拿得到它 exports 的 provider，封裝預設是關著的。a 會讓錯誤消失，但多出第二個實例，兩邊資料不同步。b 是檔案層級的 import，管不到 Nest 的 DI 範圍。d 修不好：@Global 只把 exports 裡的 provider 變成全域，沒 export 一樣找不到；就算補上 export，也只是讓依賴關係變得看不見。

練習 5：同事為了省事，把 CartService（在記憶體裡存購物車）同時放進 CartModule 和 CheckoutModule 的 providers。會發生什麼事？

✓ 每個模組會替自己 providers 裡的每一項建立實例，兩個模組各有一份，各存各的資料。Nest 不會合併（a 錯），也不會報錯（c 錯），所以這種 bug 只會在執行時以「資料消失」的樣子出現。正確做法是只在 CartModule 登記並 export，CheckoutModule import CartModule。

練習 6：@Global() 最主要的缺點是什麼？

✓ 問題在可讀性與可替換性：OrdersModule 看起來沒有依賴，實際上沒有全域模組就建不起來。全域模組的 provider 仍然只有一個實例（b 錯）；它對效能沒有值得一提的影響（c 錯）。所以 @Global 只留給設定、資料庫連線這類每個模組都需要的基礎設施。

常見錯誤

  • 檔案 import 了，就以為 Nest 也拿得到：檔案的 import 只管 TypeScript 看不看得到名稱，注入要看 @Module 的 imports／exports。兩者都要設對。
  • 把 @Injectable class 放進 imports：imports 只能放模組，Nest 12 會報 InvalidClassModuleException。service 放 providers，要用別的模組的 service 就 import 那個模組。
  • 以為 import 了模組就什麼都拿得到：只拿得到對方 exports 的 provider。錯誤訊息一樣是 can't resolve dependencies，用 NEST_DEBUG=1 看 Nest 去了哪些模組找。
  • 同一個 provider 出現在多個模組的 providers：變成好幾個實例，狀態不同步。只登記一次，用 export／import 共用。
  • export 內部細節：repository、輔助 class 被別的模組直接使用後，就改不動了。只 export 別人需要的 service。
  • 什麼都 @Global：依賴看不見、模組無法單獨測試。只用在設定、資料庫連線這類基礎設施。
  • 可設定的模組把設定存在檔案層級的變數或讀 process.env：註冊兩次就互相蓋掉、測試換不掉。用 ConfigurableModuleBuilder，設定透過 MODULE_OPTIONS_TOKEN 注入。
  • 在建構子裡啟動非同步工作卻不等它：Nest 不會等，第一個請求可能看到還沒準備好的資料。寫在 async onModuleInit() 並 await。
  • 關機 hook 裡的非同步清理沒有 await：app.close() 結束時清理還沒做完，程序結束就被中斷。hook 寫成 async 並 await。
  • 依賴舊版的 hook 執行順序：Nest 12 改成依模組階層呼叫。不要讓兩個不相干的模組靠 hook 先後協調；有先後關係就用注入表達。

小結

  • 全部擠在 AppModule 的問題是依賴關係沒寫在任何地方。功能模組加上封裝，讓依賴寫在 imports／exports 上。
  • ES module 管檔案之間的引用；Nest 的 @Module 管 DI 的可見範圍。兩者都要設對。
  • providers 由模組建立、controllers 是路由、imports 只放模組、exports 決定開放什麼。provider 預設只在自己的模組裡看得到；export 出去的就是公開介面，只開放 service、不開放 repository。
  • Nest can't resolve dependencies of X (?)：看 index 是哪個參數、在哪個模組找；原因多半是沒 import、沒 export 或 import type，前兩種用 NEST_DEBUG=1 分辨。
  • 一個 provider 只登記在一個模組，登記兩次就是兩個實例、兩份資料；@Global 只給基礎設施。
  • 同一個模組要用不同設定註冊時做成動態模組：ConfigurableModuleBuilder 產生 register／registerAsync 與 MODULE_OPTIONS_TOKEN；forRoot 整個應用一次、register 每個使用者各一次。
  • 非同步初始化寫在 async onModuleInit()，Nest 會等它；Nest 12 依模組階層呼叫 hook：深層模組先初始化，關機時反過來；SIGTERM 要 enableShutdownHooks() 才會觸發（第 24 課）。

用 CLI 建立模組

新功能可以用產生器開始：nest g module products 產生 src/products/products.module.ts，並自動加進 AppModule 的 imports；接著 nest g service products 把 service 放進 src/products/，登記到離它最近的模組，也就是 ProductsModule。跟第 1 課一樣，兩個指令都在 work/04 執行（不要進到 src/ 裡，產生的 import 會少了 .js）。

動態模組的方法名稱（查表用，不用背）

方法名稱的慣例（官方文件的社群指引）：

名稱意思例子
register／registerAsync每個使用的模組各自帶設定註冊一次本課的 ReceiptModule
forRoot／forRootAsync整個應用設定一次，通常在根模組第 11 課 ConfigModule.forRoot()
forFeature用 forRoot 的設定，每個功能模組再補自己的部分第 20 課 BullMQ：forRoot 設定 Redis 連線，每個功能模組再 registerQueue 自己的佇列，是同樣的分工

要產生 forRoot 而不是 register，在 builder 加 .setClassMethodName('forRoot')。

模組互相 import：循環依賴

模組之間互相 import（A import B、B 又 import A）會造成循環依賴（circular dependency），Nest 會要你用 forwardRef()。那通常代表邊界切錯了，第 25 課看錯誤訊息、第 26 課講怎麼用事件拆開。

版本備註：hook 的執行順序

Nest 12 的 migration guide 列了一項 breaking change：lifecycle hook 改成依元件的階層（hierarchy level）呼叫。本課「誰先誰後」一節的規則以官方 lifecycle 文件與 @nestjs/core 12.3.2 的原始碼為準；從 Nest 11 升級的專案，原本靠 hook 先後運作的程式要重新檢查。
