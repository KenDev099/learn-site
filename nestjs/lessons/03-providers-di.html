階段 1：從 Node 到 NestJS（框架的骨架） · 第 3 課

Provider 與依賴注入

上一課做完的 ProductsController，把商品陣列、查詢、找不到時丟錯全都寫在 controller 裡。這一課店長提出兩條新需求：

  • 快樂時光：每天台北時間 14:00–16:00，飲品打八折。
  • 結帳接金流：開發時用假的金流（不會真的扣款），上線用 LINE Pay。

兩條需求本身都不難寫，難的是寫完之後怎麼確定它是對的。價格取決於「現在幾點」，想確認「剛好 16:00 不打折」，難道要等到下午四點再跑測試？金流要依環境切換，難道要在程式裡到處寫 if (開發環境)？這一課用 NestJS 的依賴注入回答這兩個問題，把這兩條需求做成測得到、換得掉的樣子；最後還會遇到一個只在上線尖峰、兩個客人同時結帳時才出現的 bug，一起把它修掉。

這課的路線：
  1. 快樂時光要怎麼測：controller 自己 new 的東西為什麼換不掉，依賴注入怎麼把「誰建立物件」反過來交給 Nest（開場問題的最小答案）。
  2. 建構子只寫了型別，Nest 怎麼知道要傳什麼：design:paramtypes、token、@Injectable()，以及 Nest 建好的物件為什麼只有一個。
  3. 時鐘和金流不是一般的 class，要拿什麼當鑰匙：Symbol 加 @Inject、抽象類別，以及 import type 為什麼會讓注入壞掉。
  4. 同一把鑰匙，開發給假金流、上線給 LINE Pay：四種自訂 provider，以及設定打錯字時為什麼要讓程式啟動失敗。
  5. 上線後的事故與收尾：收據印成別人的名字（singleton 的共用狀態）、把時間注入測 16:00 的邊界、哪些東西不需要多包一層 interface。
這課會用到：
  • TypeScript 課第 23 課的 parameter properties：constructor(private readonly x: X) 一行同時宣告屬性並把參數存進去。
  • TypeScript 課第 24 課的裝飾器與迷你 DI：開了 emitDecoratorMetadata，編譯器會把建構子參數的型別記成 design:paramtypes，容器讀它決定要傳什麼進去。

快樂時光要怎麼測？自己 new 的東西換不掉

先照最直覺的方式把快樂時光加進去：寫一個 PricingService 算價格，controller 需要它就自己 new 一個。商品資料也順手搬進 ProductsService，同樣自己 new。

@Controller('products')
export class ProductsController {
  private readonly products = new ProductsService()        // 自己 new
  private readonly pricing = new PricingService()

  @Get(':id/price')
  price(@Param('id', ParseIntPipe) id: number) {
    return { id, price: this.pricing.priceOf(this.products.findOne(id)) }
  }
}

這段程式能動，curl /products/2/price 也拿得到價格。問題出在你想寫測試確認「剛好 16:00 拿鐵是原價 110」的時候。PricingService 裡判斷時間用的是 new Date()，測試沒辦法叫它「假裝現在是 16:00」；想把 PricingService 整個換成測試專用的版本，也做不到，因為 new PricingService() 寫死在 controller 的 class 裡，測試碰不到那一行。同樣的道理，測試想讓 ProductsService 回固定的幾筆商品、不碰真正的資料，也換不掉。

這不只是測試的問題。一段程式依賴另一段程式的細節，叫做耦合（coupling）。controller 寫了 new PricingService()，就等於知道「PricingService 建立時不需要任何參數」這個細節。哪天 PricingService 需要一個時鐘、一份設定才能建立，每一個寫了 new PricingService() 的地方都要跟著改。

還有第三個問題：每個 new 都是一份新的物件。如果 OrdersController 也自己 new ProductsService()，咖啡店就有兩份商品陣列，店長在商品頁新增的商品，下單時找不到。

三個問題的根源是同一個：controller 自己決定要用哪個物件、自己建立它。解法是把這件事交出去。物件只在建構子裡寫「我需要一個 PricingService」，至於這個 PricingService 是誰建立的、是真的還是測試用的假貨、是不是跟別人共用同一個，都由外面決定再傳進來。這種「需要的東西由外面給」的做法叫依賴注入（Dependency Injection，簡稱 DI）；物件需要的那些東西叫它的依賴（dependency），把依賴傳進去的動作叫注入。

「外面」是誰？在 NestJS 裡是框架本身。它有一個負責建立物件、照順序把依賴傳進去的元件，叫 IoC 容器（container）。IoC 是第 1 課講過的控制反轉：原本你的程式主動 new，現在變成框架建好再交給你。交給容器建立與管理的物件，統稱 provider。service 是最常見的 provider，但一個設定值、一個時鐘物件、一個函式算出來的結果，也都可以是 provider。

如果你寫過 Vue 的 provide／inject，這是同一個想法：子元件 inject('theme')，不知道也不在乎值是哪一層 provide 的；Nest 的 service 在建構子寫需要什麼，也不知道拿到的是真的還是測試用的假貨。差別是 Nest 的 provider 預設整個應用共用一個，Vue 的則跟著元件樹。

改成注入後，controller 只負責 HTTP：取參數、呼叫 service、回傳結果。

@Controller('products')
export class ProductsController {
  constructor(
    private readonly products: ProductsService,
    private readonly pricing: PricingService,
  ) {}
  …
}

容器在啟動時會看每個 class 的建構子需要什麼，從最底層的依賴開始建，再一層一層往上傳。圖裡的 CLOCK 是等一下要做的時鐘，PricingService 需要它才能知道現在幾點：

這就是開場兩個問題的最小答案。「現在幾點」包成一個 provider，正式執行時給真的時鐘，測試時換成停在 16:00 的假時鐘，PricingService 一行都不用改；金流也是一個 provider，開發和上線由容器給不同的實作，程式裡不用寫 if。後面幾節把這兩件事真的做出來。

💡 實務上：controller 薄、service 厚，是 code review 常被要求的事
同一段「建立訂單」的邏輯，之後常常不只 HTTP 會用：每晚補單的排程、接收外送平台訂單的背景工作、管理員的匯入腳本都要呼叫它。邏輯放在 controller 裡，這些地方只能複製貼上，改一條規則要改好幾處。review 時看到 controller 裡有 if 判斷商業規則、直接操作資料，資深工程師通常會請你搬到 service。反過來，service 也不該碰 req、res 這類 HTTP 的東西，否則排程和背景工作就沒辦法呼叫它。快樂時光的打折規則放在 PricingService，之後後台報表要算「上週快樂時光少收多少」也能直接呼叫。

建構子只寫了型別，Nest 怎麼知道要傳什麼？

上一節的 controller 建構子裡只有兩個參數和它們的型別，沒有任何地方寫「去哪裡拿」。Nest 是怎麼知道第 0 個參數要給 ProductsService 的？

它不是看參數名稱 products，而是看型別。可是 TypeScript 的型別在編譯成 JavaScript 後會被擦掉，執行時照理說已經不存在了。關鍵在 TypeScript 課第 24 課看過的 emitDecoratorMetadata：開了這個選項，編譯器會替有裝飾器的 class，把建構子參數的型別另外記成一份資料，名字叫 design:paramtypes。nest build 編譯上面的 controller，dist/ 裡會出現：

__metadata("design:paramtypes", [ProductsService, PricingService])

這個陣列裡放的不是字串，而是 ProductsService、PricingService 這兩個 class 本身（JavaScript 的 class 在執行時是一個真的值）。Nest 讀這個陣列，知道第 0 個參數要 ProductsService、第 1 個要 PricingService，再到模組的 providers 清單裡找有沒有登記過它們，找到就建立（或拿出已經建好的）傳進去。

所以這裡的 ProductsService 同時有兩個角色：它是要被建立的 class，也是容器用來找 provider 的那把鑰匙。這把「用來找 provider 的鑰匙」叫 injection token，後面簡稱 token。用 class 當 token 是最常見的情況，你在 providers: [ProductsService] 登記、在建構子寫 ProductsService 型別，兩邊用的是同一把鑰匙，自然對得上。

那 @Injectable() 是做什麼的？它做兩件事。第一，標記「這個 class 交給容器管理」，也可以帶 scope 等選項（scope 是這個 provider 要建幾個實例，下面會講到）。第二，它是一個裝飾器，而編譯器只替有裝飾器的 class 記 design:paramtypes，沒有它，PricingService 自己的建構子需要什麼就沒人記得。沒有任何依賴的 service 不加也能用，但慣例一律加上，之後加依賴時才不會忘。

容器找到 provider 之後還有一個預設行為要先知道。容器第一次建好某個 provider，會用它的 token 把這個實例記下來；之後任何地方再用同一把鑰匙來要，容器不會再 new，而是直接交出已經建好的那一個，所以整個應用程式裡它只有一份。預設這樣設計，是因為大部分 service 沒有「每個請求不一樣」的狀態：每次重建只會浪費時間，還會像第一節那樣，各自 new 出兩份商品陣列、資料對不起來。

預設 scope 是 singleton（單例）：整個應用程式只建立一個 ProductsService，所有 controller、所有請求共用它，不是每個請求 new 一次。這正好解決了上一節的「兩份商品陣列」：ProductsController 和 OrdersController 拿到的是同一個 ProductsService。但它也有代價，在後面〈收據為什麼印成別人的名字〉一節會變成 bug 的來源。

到這裡，用 class 當鑰匙的情況都能運作。但快樂時光需要的時鐘只是一個 { now() } 物件，沒有自己的 class；金流我們想寫成 interface，讓假金流和 LINE Pay 各自實作。這兩個東西要拿什麼當鑰匙？

時鐘和金流不是一般的 class，要拿什麼當鑰匙？

上一節的機制有一個前提：design:paramtypes 裡要記得到一個執行時真的存在的 class。時鐘和金流剛好都不符合：

  • interface：TypeScript 的 interface 只在編譯時存在，編譯後整個消失。參數型別寫 interface，design:paramtypes 裡只會是 Object，Nest 不知道你要哪一個。
  • 一個值：例如時鐘物件 { now: () => new Date() }，它沒有自己的 class，沒有東西可以當鑰匙。

時鐘：自己做一把 Symbol 鑰匙

既然沒有現成的 class 可用，就自己做一把鑰匙。鑰匙只要是一個執行時存在、而且不會跟別人撞到的值就行。Symbol 是 JavaScript 內建的一種值，每次呼叫 Symbol() 都得到一個獨一無二的值，就算兩邊都寫 Symbol('CLOCK') 也是兩把不同的鑰匙，所以拿來當 token 不會和別人的字串撞名。

做法分三步：定義鑰匙、用鑰匙登記一個值、在需要的地方用 @Inject 指定鑰匙。

// clock.ts
export interface Clock {
  now(): Date
}
export const CLOCK = Symbol('CLOCK')        // 括號裡的字只是除錯時看得到的說明

// app.module.ts：用這把鑰匙登記一個值
providers: [{ provide: CLOCK, useValue: { now: () => new Date() } }]

// 使用的地方：型別寫 interface（給編輯器看），鑰匙用 @Inject 指定（給 Nest 看）
constructor(@Inject(CLOCK) private readonly clock: Clock) {}

注意最後一行分成兩半：Clock 這個 interface 讓編輯器知道 this.clock.now() 回傳 Date，有自動完成和型別檢查；@Inject(CLOCK) 則是告訴 Nest「這個參數不要看型別，用 CLOCK 這把鑰匙去找」。{ provide: CLOCK, useValue: … } 這種寫法叫自訂 provider，下一節會完整介紹，現在只要知道它是「用 CLOCK 登記一個現成的值」。

忘了 @Inject(CLOCK)，Nest 只看得到 Object，啟動時就失敗：

Nest can't resolve dependencies of the PricingService (?). Please make sure that the
argument at index [0] is available in the current module.

讀法：括號裡每個位置是一個建構子參數，? 是找不到的那個；index [0] 是第 0 個參數。訊息下面的 Potential solutions 會建議你檢查 import type（這一節最後會講），但這裡真正的原因是少了 @Inject：看到這段提示，兩件事都要查。第 4 課會把這個訊息的其他原因（沒 export、沒 import）講完。

金流：用抽象類別同時當 interface 和鑰匙

金流也可以照時鐘的做法，寫 interface 加 Symbol 加 @Inject。但還有一個更省事的選擇：抽象類別（abstract class，TypeScript 課第 23 課）。抽象類別不能直接 new，只能被繼承；它像 interface 一樣描述「要有哪些方法」，但它是 class，編譯後仍是一個執行時真的存在的值，可以出現在 design:paramtypes 裡。所以它本身就能當 token，建構子不需要 @Inject：

export abstract class PaymentGateway {
  abstract charge(amount: number): Promise<Payment>
}
export class FakePaymentGateway extends PaymentGateway { … }

constructor(private readonly payments: PaymentGateway) {}   // 抽象類別本身就是 token

CheckoutService 只認得 PaymentGateway，不知道背後是假金流還是 LINE Pay。時鐘用 Symbol、金流用抽象類別，差別在於：時鐘只是一個值，沒必要為它寫 class；金流有兩個以上的實作要繼承同一份規格，抽象類別剛好兩件事一次做完。

import type 會讓注入壞掉

改成抽象類別之後還有一個陷阱。import type 告訴編譯器「這只是型別，編譯後整行刪掉」。如果 CheckoutService 寫 import type { PaymentGateway } from './payment-gateway.js'，編譯後那行 import 消失，執行時根本拿不到 PaymentGateway 這個 class，design:paramtypes 裡記到的就不是它，Nest 找不到 provider。可是 DI 需要的正是執行時的那個 class。

錯誤訊息一樣是 Nest can't resolve dependencies of the CheckoutService (?)，但參數那一格記到的會是 Function 或 undefined 這種不是你寫的東西：看到它，先檢查那個參數的 import 是不是 import type。實際在這門課的專案裡，npm run start:dev 和 Vitest 印出來的訊息不一樣，兩種完整訊息見課末〈補充與查表〉。

規則：要注入的 class 用一般的 import；只當型別用的（interface、Product 這類 type）才用 import type。

現在時鐘和金流都有鑰匙了。但 CLOCK 目前只登記了一個值，PaymentGateway 還沒登記任何東西；金流要開發用假的、上線用 LINE Pay，同一把鑰匙要怎麼在不同時候對到不同的東西？

同一把鑰匙，開發給假金流、上線給 LINE Pay？

先回頭看最常寫的登記方式。providers: [ProductsService] 其實是下面這行的簡寫：

{ provide: ProductsService, useClass: ProductsService }

左邊的 provide 是鑰匙，右邊的 useClass 是「用這把鑰匙來拿時，給什麼」。平常兩邊是同一個 class，所以可以簡寫；把兩邊拆開，同一把鑰匙就能對應到不同的東西。這種拆開寫的登記方式叫自訂 provider，右邊有四種寫法，依咖啡店的需要一個一個看。

useValue：給一個現成的值。上一節的時鐘就是：{ provide: CLOCK, useValue: { now: () => new Date() } }。Nest 不會 new 任何東西，誰要 CLOCK 就拿到這個物件。常數、設定物件也用它；測試裡把某個 provider 換成假資料，也是用 useValue。

useClass：指定要 new 哪個 class。金流如果永遠只用假的，寫 { provide: PaymentGateway, useClass: FakePaymentGateway } 就好：誰要 PaymentGateway，Nest 就 new 一個 FakePaymentGateway 給它，而且 FakePaymentGateway 自己的依賴也會照常注入。可是 useClass 後面寫的是哪個 class，是寫死在程式碼裡的，沒辦法「開發時一個、上線時另一個」。

useFactory：執行時跑一段程式再決定。這正是金流需要的。useFactory 接一個函式，Nest 在建立模組時呼叫它，回傳值就是這個 provider：

// 依環境變數決定金流：只有 factory 做得到「執行時才決定」
{
  provide: PaymentGateway,
  useFactory: () => {
    const provider = process.env.PAYMENT_PROVIDER ?? 'fake'
    …
  },
}

函式裡讀環境變數 PAYMENT_PROVIDER，fake 就 new 假金流，linepay 就 new LINE Pay。CheckoutService 完全不用改，它只認得 PaymentGateway 這把鑰匙。這一課先在 factory 裡直接讀 process.env；第 11 課改用 ConfigService，在啟動時一次驗證所有設定。

factory 裡最容易出事的是「不認得的值」該怎麼辦：

設定打錯字要讓程式啟動失敗。PAYMENT_PROVIDER=linpay（少一個 e）如果默默退回假的金流，正式環境會「每一筆都付款成功、但一毛錢都沒收到」，而且沒有任何錯誤訊息。factory 在建立模組時執行，在這裡丟錯，程式根本啟動不了，部署當下就會被發現。

factory 自己也可以需要別的 provider。舉一個咖啡店的小需求：收據最上面要印「咖啡店收據 2026」這樣的抬頭，年份不能寫死，要問時鐘。這個抬頭只是一個字串，沒有現成的 class 可當鑰匙，這裡直接用字串 'RECEIPT_HEADER' 當 token。字串和 Symbol 一樣可以當鑰匙，使用的地方同樣要寫 @Inject 指定：

constructor(@Inject('RECEIPT_HEADER') private readonly header: string) {}

差別在字串可能和別的模組取的名字撞在一起，Symbol 不會，所以正式專案偏好用上一節的 Symbol；這裡用字串只是讓範例短一點。登記時，inject 陣列列出 factory 要注入的 token，順序對應函式參數的順序：

// factory 需要別的 provider：inject 陣列的順序對應函式參數的順序
{
  provide: 'RECEIPT_HEADER',
  useFactory: (clock: Clock) => `咖啡店收據 ${clock.now().getFullYear()}`,
  inject: [CLOCK],
}

useExisting：別名。最後一種比較少用：讓一把新鑰匙指向另一個已經登記的 provider，兩把鑰匙拿到同一個實例。常見於改名的過渡期。假設 PricingService 以前是用字串 token 'LEGACY_PRICING' 登記的，報表模組裡還寫著 @Inject('LEGACY_PRICING')。現在改成直接用 class 當鑰匙，但不想一次改完所有用到舊名字的地方，就讓舊鑰匙指向新的 PricingService。兩把鑰匙拿到的是同一個實例，不會多建一份：

// 別名：注入 'LEGACY_PRICING' 和 PricingService 拿到同一個物件
{ provide: 'LEGACY_PRICING', useExisting: PricingService }

四種寫法整理成一張表，查表用，不用背：

寫法得到什麼什麼時候用
useValue: 值就是那個值，Nest 不會 new常數、設定物件、真正的時鐘；測試裡換成假資料
useClass: 類別Nest 幫你 new 那個類別（它的依賴也會注入）實作固定、但想讓 token 和實作分開，例如 { provide: PaymentGateway, useClass: FakePaymentGateway }
useFactory: 函式＋inject函式的回傳值（可以是 async）要先計算、要依設定決定用哪個實作，或需要別的 provider 才能建立
useExisting: 另一個 token另一個 provider 的同一個實例（別名）舊名字還有人在用，想讓新舊兩個 token 拿到同一個物件
💡 實務上：useFactory 最常用來建立第三方 SDK 的 client
真實專案裡，自訂 provider 最常見的是包裝外部服務：金流、寄信、簡訊、雲端儲存的 SDK client，或是資料庫、Redis 連線。做法通常是 useFactory 讀設定、建立 client，再用 token 或抽象類別讓 service 注入，service 不直接 new SDK。這樣測試可以換成假的，換廠商時也只改 factory。資深工程師會先問：這個 factory 啟動時要不要連線？連不上時要讓整個程式啟動失敗，還是先啟動、等第一次使用再報錯？資料庫這種連不上就什麼都做不了的，通常選前者；寄信這種晚點補寄也行的，可以選後者。

金流接好了，本機一個人點結帳、跑測試都正常。可是上線後第一個尖峰時段，客服收到一則回報：「我的收據上是別人的名字。」

收據為什麼印成別人的名字？singleton 裡的共用狀態

回想第二節的預設行為：provider 是 singleton，所有請求共用同一個 CheckoutService 實例。這代表 service 的欄位等於全域變數，每個請求都讀寫同一份。看出事的這段結帳程式：

@Injectable()
export class CheckoutService {
  private currentCart: Cart = { customer: '', lines: [] }

  async checkout(cart: Cart): Promise<Receipt> {
    this.currentCart = cart
    const payment = await this.payments.charge(this.total())   // 等金流回應，約 100 ms
    return { customer: this.currentCart.customer, total: this.total(), … }
  }
}

寫的人把購物車先存進 this.currentCart，好讓 total() 這類輔助方法不用一直傳參數。一次一個請求時完全正常，測試也會過。兩個請求同時進來時：

時間王小明的請求陳美華的請求this.currentCart
0 msthis.currentCart = 王小明的車，付 110 元，開始 await王小明
1 ms（等待中）this.currentCart = 陳美華的車，付 290 元，開始 await陳美華
100 ms付款完成，讀 this.currentCart：收據寫著陳美華、290 元（等待中）陳美華
101 ms收據：陳美華、290 元陳美華

王小明付了 110 元，拿到的卻是陳美華的收據。這就是TypeScript 課第 12 課的競態：await 是插隊點，前後讀到的共用狀態可能已經被別人改掉。Node 只有一條執行緒，但「一條執行緒」不代表「一次一個請求」：一個請求在 await 等金流回應時，執行緒空下來，其他請求的程式就會跑。

修法：這次請求的資料只放在參數和區域變數。cart 本來就是參數，直接用它；total() 改成接收購物車當參數。每個請求呼叫 checkout() 時都有自己的一份區域變數，別的請求碰不到。service 的欄位只放所有請求共用、而且不會因為請求而改變的東西（注入的依賴、設定）。

有兩個做法看起來也能修，其實不對。第一個是改成 @Injectable({ scope: Scope.REQUEST })，讓每個請求 new 一個實例。bug 確實不見了，但依賴它的 controller 和 service 也全部變成每個請求重建，變慢，而且還有其他代價（見課末〈補充與查表〉）。Scope.REQUEST 是給「真的需要知道是哪個請求」的 provider 用的，不是拿來修共用欄位。

第二個是加一把鎖讓結帳排隊，一次只跑一個結帳。資料不會亂了，但 20 個人同時結帳，最後一個要等 20 次金流回應。問題出在共用欄位，不是同時執行；把同時執行拿掉，等於為了一個寫錯的欄位犧牲整個咖啡店的結帳速度。

💡 實務上：這種 bug 在本機幾乎重現不了
開發時一次只有你一個人點，測試也一次只跑一個請求，所以它通常是上線後、尖峰時段才出現，客服收到「我的收據上是別人的名字」。這種回報很難查，因為 log 看起來每個請求都正常。所以資深工程師 review 時會直接掃：singleton service 裡，有沒有在 async 方法中對 this.xxx 賦值？有的話，那個欄位是不是這次請求的資料？比起事後除錯，在 review 時擋下來成本低很多。

結帳的事故修好了。回到開場的另一條需求：快樂時光的 PricingService 已經注入了 CLOCK，但「剛好 16:00 算不算打折」到底要怎麼測？

剛好 16:00 算不算打折？把時間固定，把時區講清楚

快樂時光的規則是「台北時間 14:00–16:00」，含 14:00、不含 16:00。如果 PricingService 自己呼叫 new Date()，測試結果取決於你什麼時候跑測試；邊界（剛好 16:00 算不算）更是測不到。現在「現在幾點」已經是 CLOCK provider，測試只要把這把鑰匙對應的值換掉，時間就固定了：

const ref = await Test.createTestingModule({ imports: [AppModule] })
  .overrideProvider(CLOCK)
  .useValue({ now: () => new Date('2026-11-02T16:00:00+08:00') })
  .compile()
ref.get(PricingService).priceOf(latte)      // 剛好 16:00：原價 110

Test.createTestingModule 建立一個測試用的容器（Testing Module），內容跟 AppModule 一樣；overrideProvider(token).useValue(值) 是它提供的方法，意思是「同一把鑰匙，換成別的東西」。PricingService 的程式一行都沒改，它注入 CLOCK 時拿到的就是停在 16:00 的假時鐘。這就是第一節說的「換得掉」。第 5 課會用它寫完整的單元測試。

時間固定之後，還有一個時間陷阱：時區。Date 裡只存一個 UTC 毫秒數（TypeScript 課第 6 課），本身沒有時區；你問它「幾點」時，才用某個時區去換算。getHours() 用的是伺服器所在地的時區：你的 Mac 在台北，測試全部通過；部署到 UTC 的機器上，快樂時光就變成台北晚上十點到十二點。getUTCHours() 也不對，它固定用 UTC，比台北慢 8 小時。要明確指定時區：

const taipeiHour = new Intl.DateTimeFormat('en-US', { timeZone: 'Asia/Taipei', hour: 'numeric', hourCycle: 'h23' })
Number(taipeiHour.format(new Date('2026-11-02T06:30:00Z')))   // 14（UTC 06:30 是台北 14:30）

hourCycle: 'h23' 讓午夜是 00 而不是 24。這樣不論伺服器設在哪個時區，算出來的都是台北的小時。

💡 實務上：凡是「跟時間有關的規則」都值得注入時鐘
工作中常見的有：優惠券到期、會員點數過期、每日營收報表的切日、訂位只能預約七天內、營業時間外不能下單。這些規則最容易出錯的都是邊界：23:59:59 的訂單算今天還是明天、到期那一秒能不能用。PM 或會計發現「報表少了一筆」時，通常就是切日的時區或邊界寫錯。開發時先問清楚「以哪個時區為準、邊界含不含」，再用固定的時鐘把邊界寫成測試。

時鐘和金流抽成 token 之後，兩條需求都測得到、換得掉了。這時很容易冒出一個念頭：既然抽出來這麼好，是不是每個 service 都該這樣做？

每個 service 都要配 interface 和 token 嗎？

學會 token 之後，很容易幫每個 service 都配一個 interface 加一個 Symbol：IProductsService、PRODUCTS_SERVICE……理由是「以後可能會換實作」。代價是每個 service 多兩樣東西要維護、跳轉定義時多繞一層，而那個「以後」通常不會來。

判斷的標準是「現在有沒有第二種東西要放進這個位置」。只有一個實作的，例如 ProductsService、PricingService，直接注入 class。測試要換掉它，用 overrideProvider(ProductsService) 就夠了：class 本身就是鑰匙，一樣能換，不需要 interface。真的有兩個以上的實作（金流、寄信、儲存空間），或是外部的不確定因素（時間、亂數），才抽成 token 或抽象類別。這一課只抽了 CLOCK 和 PaymentGateway，正是因為只有它們符合這個條件。

這個原則叫 YAGNI（You Aren't Gonna Need It，你不會需要它）：需要的時候再加，而在 Nest 裡，之後要把一個 class 換成 token 的成本其實很低。原因是 class 本身就是鑰匙：真的出現第二個實作時，只要改 providers 那一行登記，例如 { provide: ProductsService, useClass: 新的實作 }，或把原本的 class 改成抽象類別；注入它的建構子寫法幾乎不用動，測試裡的 overrideProvider(ProductsService) 也照用。

練習

在 learn/ 執行 node check.mjs nestjs 03 建立 work/03/。它是第 2 課做完的咖啡店：ProductsController 有商品的 CRUD 和 GET /products/:id/price。npm run start:dev 在 work/03 啟動。

練習 1：把 ProductsController 裡的商品陣列、nextId，以及 findAll(category?)、findOne(id)、create(input)、update(id, input)、remove(id) 的邏輯搬到 ProductsService（同名方法，參數是一般的值）。找不到商品時由 service 丟 NotFoundException。controller 用建構子注入 ProductsService，每個路由只取參數、呼叫 service、回傳結果；狀態碼（POST 201、DELETE 204）不變。記得把 ProductsService 加進 AppModule 的 providers。

測試會直接呼叫 ProductsService 的方法，也會把它換成假的，確認每個路由都改用假的。

練習 2：快樂時光是每天台北時間 14:00–16:00（含 14:00、不含 16:00），coffee 和 tea 打八折，food 不打折。起始的 PricingService 有三個錯。改成用 @Inject(CLOCK) 注入 src/clock.ts 定義的時鐘，用 clock.now() 取得現在時間；在 AppModule 用 useValue 提供真正的時鐘。

測試會把時鐘固定在 13:59:59、14:00:00、15:59:59、16:00:00，並把程序的時區改成洛杉磯，所以 getHours()、沒指定 timeZone 的 Intl.DateTimeFormat 這種依賴伺服器時區的寫法過不了。

練習 3：PaymentGateway 現在是 interface，CheckoutService 用 import type 匯入它，而且還沒登記進 AppModule。把它改成抽象類別（兩個實作改成 extends），CheckoutService 改用一般的 import。在 AppModule 用 useFactory 登記 PaymentGateway：讀 process.env.PAYMENT_PROVIDER，fake 或沒設定時用 FakePaymentGateway，linepay 用 LinePayGateway，其他值丟出訊息含 PAYMENT_PROVIDER 的錯誤。最後把 CheckoutService 加進 providers。CheckoutService 只依賴 PaymentGateway，不要自己判斷該用哪個實作。

練習 4：先完成練習 3。CheckoutService 把購物車存在 this.currentCart，兩個同時進行的結帳會拿到對方的收據。只用參數和區域變數修好它，保持預設的 singleton。測試讓金流每次付款等 100 ms，同時送出王小明和陳美華的結帳，兩張收據都要正確，而且兩個結帳要在 180 ms 內一起完成，所以改成 Scope.REQUEST 或加鎖排隊都過不了。測試也會讓王小明用兩支手機同時結帳，並在等金流時檢查 service 的欄位：裡面不能出現這次結帳的資料，所以改存到以顧客名稱為 key 的 Map，或保留 this.currentCart = cart 只是不去讀它，都不算修好。

練習 5：OrdersService 的建構子寫 constructor(private readonly productsService: ProductsService)。Nest 怎麼知道要傳什麼進去？

✓ Nest 看的是 metadata 裡的 class，參數名稱改成 p 也照樣注入（a 錯）。TypeScript 的型別在執行時會被擦掉，只有開了 emitDecoratorMetadata、而且這個 class 有裝飾器時，建構子參數的型別才會另外被記下來（b 錯）。所以 interface、import type 都不行：前者只記成 Object，後者在執行時根本沒有那個 class。

練習 6：沒有特別設定 scope 的 CheckoutService，在應用程式裡有幾個實例？

✓ 預設 scope 是 singleton：應用程式啟動時建立一次，之後每個注入它的地方、每個請求都拿到同一個（b、c 錯）。每個請求一個是 Scope.REQUEST，要明確設定，而且會讓依賴它的整條鏈都變成每個請求重建。

練習 7：要依環境變數決定注入 FakePaymentGateway 還是 LinePayGateway，打錯字時要啟動失敗。用哪一種 provider？

✓ 只有 factory 是「執行時跑一段程式再決定」，可以讀設定、驗證、丟錯。同一個 token 登記兩次，後登記的會蓋掉前面的，Nest 不會幫你挑（a 錯）。useExisting 是別名，指向哪一個是寫死的，沒辦法依設定改變（c 錯）。

常見錯誤

  • 用 import type 匯入要注入的 class：編譯後那行 import 消失，metadata 變成 undefined 或 Function，錯誤是 Nest can't resolve dependencies of X (?)。要注入的 class 一律用一般的 import。
  • 參數型別寫 interface 就想注入：interface 在執行時不存在，metadata 是 Object。改用抽象類別，或用 Symbol token 加 @Inject(TOKEN)。
  • 自訂 token 忘了 @Inject：{ provide: CLOCK, … } 登記了，建構子卻只寫 clock: Clock，Nest 看不到 CLOCK。用 Symbol 或字串當 token 時，建構子一定要 @Inject(TOKEN)。
  • 在 singleton service 的欄位放這次請求的資料：一次一個請求時看不出來，同時兩個就互相蓋掉。這次請求的資料只放參數和區域變數。
  • 在 controller 或 service 裡 new 依賴：測試換不掉、多一份狀態。讓容器注入。
  • 在 service 裡直接呼叫 new Date()、Date.now()：邏輯和真實時間綁死，邊界測不到。注入時鐘。
  • 用 getHours() 算營業時間：用的是伺服器的時區，不是店的時區。用 Intl.DateTimeFormat 指定 timeZone。
  • 設定值不認得時默默用預設值：打錯字的設定要讓啟動失敗，錯誤訊息寫出是哪個設定。
  • 幫每個 service 都加 interface 和 token：沒有第二個實作之前，直接注入 class，測試用 overrideProvider 替換。

補充與查表

import type 在 tsc 和 Vitest 的錯誤訊息不同

實際在這門課的專案試（NestJS 12.3.2）：nest build（tsc）編譯出來的 metadata 變成 Function，Vitest（Vite 8 的 Oxc）則是 undefined，兩種都找不到 provider，但錯誤訊息不一樣。npm run start:dev 啟動時是：

Nest can't resolve dependencies of the CheckoutService (?). Please make sure that
the argument Function at index [0] is available in the AppModule module.

這個 Function 不是你寫的任何 class，看到它就先檢查那個參數的 import 是不是 import type。在 Vitest 裡跑測試時，metadata 是 undefined，Nest 12 會直接提示原因：

Nest can't resolve dependencies of the CheckoutService (?). …
Potential solutions:
- The dependency at index [0] appears to be undefined at runtime
- This commonly occurs when using 'import type' instead of 'import' for injectable classes

Scope.REQUEST 的其他代價

除了整條依賴鏈每個請求重建，request-scoped 的 provider 也不能用 moduleRef.get() 取得，要改用 moduleRef.resolve()。ModuleRef 是 Nest 提供的物件，讓你在程式裡向容器手動拿 provider，而不是透過建構子注入；平常用不到，但遇到這種 scope 時要知道 get() 會失敗。

小結

  • 依賴注入：class 在建構子宣告需要什麼，由 Nest 容器建立並傳進來。controller 只管 HTTP，邏輯放在 service；測試和不同環境才換得掉依賴。
  • Nest 靠 design:paramtypes 裡的 class 當 token 找 provider，所以 interface 和 import type 都會讓注入失敗。
  • 不是 class 的東西（時鐘）用 Symbol token 加 @Inject；要描述介面又要當 token（金流），用抽象類別。
  • useValue 給值、useClass 換實作、useFactory 執行時計算（可以 inject 別的 provider）、useExisting 做別名；設定不認得就讓 factory 丟錯、啟動失敗。
  • provider 預設是 singleton，欄位等於全域狀態；這次請求的資料放參數和區域變數，不靠 Scope.REQUEST 或加鎖。
  • 時間、亂數、金流這類外部因素做成 provider，測試才能用 overrideProvider 固定它們；時區用 Intl.DateTimeFormat 明確指定。只有一個實作的 service 不需要額外的 interface。
