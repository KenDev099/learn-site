階段 2：請求管線與測試 · 第 7 課

Pipe 與 DTO 驗證

咖啡店的下單 API POST /orders 到目前為止都是 @Body() 收到什麼就交給 handler 什麼。這週發生兩件事：有一筆訂單的品項杯數是 -3，因為客人的 App 有個 bug，送出了 { "qty": -3 }；另一筆訂單沒付錢卻顯示「已付款」，查 log 才發現有人用 curl 在 body 裡多塞了 "status": "paid"。前端表單明明有檢查，為什麼還會發生？因為前端檢查只是讓使用者填錯時馬上看到提示，任何人都能跳過畫面、直接對 API 送資料，繞過它只要一行 curl。後端必須自己檢查每一筆從外面進來的資料。

這一課的任務是把咖啡店的 API 補上這道關卡：不合格的資料在進到 handler 之前就回 400，handler 和 service 只會拿到形狀正確的資料。主角是下單的 POST /orders，做完之後再把同一套做法套到訂單列表、商品修改和集點卡兌換這三支 API，練習裡的四題就是這四支 API。

這課的路線：
  1. 第 2 課用過的 ParseIntPipe 是什麼：pipe 在請求的哪一站、能做什麼、為什麼它只能處理一個值。
  2. 整個訂單 body 怎麼驗：用 DTO 這個 class 寫下規則，交給全域的 ValidationPipe 檢查（開場 -3 的最小答案）；多塞的 "status": "paid" 為什麼還是進得來，要再開 whitelist。
  3. 品項陣列裡的規則為什麼會默默沒跑，錯誤訊息要長什麼樣子前端才好用。
  4. 同一套做法套到訂單列表的查詢參數、商品修改的 PATCH，再看 NestJS 12 用 zod 驗證的另一種寫法。
  5. 驗證通過就安全了嗎：驗證該放在哪一層，DTO 管不到的業務規則和權限放哪裡。
這課會用到：
  • 第 2 課的路徑與查詢參數：@Param()、@Query() 拿到的一律是字串，要數字得自己轉，例如 @Param('id', ParseIntPipe)。
  • 第 6 課的請求生命週期與 APP_GUARD：請求依序經過 middleware、guard、interceptor、pipe 才到 handler；用 APP_GUARD 這種特殊 token 登記 provider，它就變成全域元件。
  • TypeScript 課第 24 課的裝飾器 metadata：class 在編譯後還存在，裝飾器能在它上面記下資訊，型別（interface、type）編譯後就消失了。

第 2 課的 ParseIntPipe 到底是什麼？

先從已經用過的東西開始。第 2 課的 GET /products/:id 遇過一個問題：網址上的 id 是字串 '2'，拿去跟數字 2 比對永遠不相等；解法是在參數上加 ParseIntPipe：

@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) { … }

當時只說它「會把字串轉成數字，轉不了就回 400」。這一課要檢查整個訂單，得先知道它屬於哪一類元件、在什麼時間點執行。

pipe 是 Nest 在呼叫 handler 之前，對 handler 的每一個參數各跑一次的元件。Nest 先依 @Param()、@Query()、@Body() 從請求裡把值取出來，交給這個參數上的 pipe；pipe 回傳什麼，handler 就收到什麼。所以一個 pipe 能做的事只有兩種：

  • 轉換（transform）：回傳一個不同的值，例如把 '2' 變成數字 2、把沒給的值換成預設值。
  • 驗證（validate）：值不合規則就丟例外，預設是 400 Bad Request，handler 根本不會被呼叫。

為什麼要把這件事獨立成一站，而不是在 handler 第一行自己 Number(id)？因為「id 要是整數」這種規則幾乎每個 controller 都有。寫在 handler 裡，每個人轉換的方式、轉不了時回的狀態碼都會不一樣，有人忘了檢查，NaN 就一路傳進 service 去查資料。放在 pipe，handler 一被呼叫，參數就保證已經是對的型別、對的值。

同一個參數可以接好幾個 pipe，由左到右執行，前一個的輸出是下一個的輸入。訂單列表的頁碼是選填的，沒給就當第 1 頁：

@Get()
list(@Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number) { … }

DefaultValuePipe 在值是 undefined 或 null 時換成預設值。順序不能反：先放 ParseIntPipe 的話，沒給 page 時它拿到 undefined，轉不了，直接回 400。這裡的 DefaultValuePipe 要帶參數 1，所以自己 new 一個實例；ParseIntPipe 不用帶選項，傳 class 就好，Nest 會幫你建。要帶選項時兩種都能 new，例如第 2 課的 new ParseIntPipe({ optional: true })。Nest 還內建 ParseUUIDPipe、ParseEnumPipe 等處理單一值的 pipe，列在課末「補充與查表」。

到這裡，網址上的一個值已經處理得很好了。但下單的 body 不是一個值：它有顧客編號、備註，還有一個品項陣列，每一筆品項又有自己的商品、杯數、大小。替每個欄位各寫一個 pipe 不可行，-3 杯藏在陣列裡面，單一值的 pipe 也碰不到。我們需要一種方式，一次描述「整個 body 應該長什麼樣子」。

整個訂單 body 怎麼驗？DTO 與 ValidationPipe

描述整個 body 的方式，是寫一個 class，Nest 的慣例叫它 DTO。這個名字來自 Data Transfer Object，中文是「資料傳輸物件」：它代表一筆「從外面傳進來的資料」，每個屬性是一個欄位，欄位上用 class-validator 這個套件提供的裝飾器寫規則。對 Vue 工程師來說，它像是你替表單送出的 payload 寫的 TypeScript 型別，差別是 DTO 在執行時還存在，而且身上帶著規則。先從訂單的頂層欄位開始，品項陣列留到下一節：

// orders/create-order.dto.ts
import { IsInt, IsOptional, IsPositive, IsString, MaxLength } from 'class-validator'

export class CreateOrderDto {
  @IsInt()
  @IsPositive()
  customerId: number

  @IsOptional()          // 沒給（undefined 或 null）就跳過這個欄位的其他規則
  @IsString()
  @MaxLength(50)
  note?: string
}

每個裝飾器是一條規則：customerId 要是整數、要是正數；note 選填，有給的話要是字串、最多 50 字。@IsOptional() 的意思值得記住，後面會再遇到它：值是 undefined 或 null 時，這個欄位的其他規則全部跳過。

規則寫好了，誰來執行？Nest 內建的 ValidationPipe。它也是一個 pipe，套在 @Body() dto: CreateOrderDto 這個參數上時，依序做三件事：

  1. 從參數的 metadata 知道這個參數宣告的型別是 CreateOrderDto。
  2. 用 class-transformer 這個套件的 plainToInstance，把 JSON 解析出來的純物件變成 CreateOrderDto 的實例。規則是掛在 class 上的，純物件身上沒有規則可讀。
  3. 用 class-validator 讀裝飾器留在 class 上的 metadata，逐欄檢查。有任何一條沒過，就丟出 400，訊息列出每一條沒過的規則；全部通過，才把值交給 handler。

兩個套件分工，ValidationPipe 把它們串起來。本課程用 class-validator 0.15.1、class-transformer 0.5.1，要自己安裝。

從這三步可以看出為什麼 DTO 一定要是 class，不能是 interface 或 type。TypeScript 課第 24 課看過：型別在編譯後消失，只有 class 在執行時還存在、能掛 metadata。TypeScript 編譯帶裝飾器的 class 時，會把每個參數宣告的型別記在一筆叫 design:paramtypes 的 metadata 裡（TypeScript 課第 24 課）。ValidationPipe 從 design:paramtypes 知道要用哪個 class 驗證；型別是 interface 時那裡只剩 Object，ValidationPipe 看到 Object、String、Number 這些內建型別就直接放行，什麼都不驗。import type { CreateOrderDto } 也一樣，class 只被當成型別匯入，metadata 變成 Object。最麻煩的是這兩種寫法都不會有任何錯誤或警告，API 看起來正常運作，只是驗證從來沒跑過。

接下來是把 ValidationPipe 掛上去。可以在每個 handler 加 @UsePipes(ValidationPipe)，但只要有一個 handler 忘了加，那支 API 就沒有驗證，而且沒有人會發現。驗證應該全域開啟。做法跟第 6 課的 APP_GUARD 一樣，在 AppModule 的 providers 用 APP_PIPE 這個 token 登記，它就套用到每一個 handler 的每一個參數：

import { Module, ValidationPipe } from '@nestjs/common'
import { APP_PIPE } from '@nestjs/core'

@Module({
  providers: [
    { provide: APP_PIPE, useValue: new ValidationPipe({ transform: true }) },
  ],
})
export class AppModule {}

transform: true 決定 handler 拿到什麼。第 2 步其實已經建出了 CreateOrderDto 的實例，但沒開 transform 時，handler 拿到的不是 DTO 實例，而是一個純物件。這個純物件有沒有帶到 class-transformer 的轉換（等一下的 @Type()）和欄位預設值，要看有沒有開 whitelist 這類其他選項，行為不一致。開了 transform，handler 拿到的就一定是剛驗證過的那個實例，所以這門課一律開。

為什麼不用官方文件也常見的 main.ts 寫法 app.useGlobalPipes(new ValidationPipe())？它的問題是只在 main.ts 生效：測試用 Test.createTestingModule({ imports: [AppModule] }) 建出來的應用不會跑 main.ts，於是測試裡完全沒有驗證，「測試全過、正式環境行為不同」。登記在模組裡，AppModule 走到哪裡驗證就跟到哪裡（這一課的判分就是這樣建應用的）。第 10 課會把其他只能寫在 main.ts 的設定收進一個共用函式。

現在送 { "customerId": -3 }，@IsPositive() 沒過，回 400，handler 不會執行。這就是開場問題的最小答案：規則寫在 DTO，ValidationPipe 在 handler 之前替每個請求檢查。但試試開場的第二個攻擊，送 { "customerId": 1, "status": "paid" }：回 201，訂單建立了，而且是已付款。CreateOrderDto 上根本沒有 status，ValidationPipe 只檢查有規則的欄位，其他欄位它不管，照樣交給 handler。

多塞的 "status": "paid" 為什麼進得來？大量指派與 whitelist

多出來的欄位交給 handler，為什麼會變成「已付款」？要看 service 怎麼用這個 DTO。練習的起始程式裡，OrdersService.create 是這樣寫的：

create(dto: CreateOrderDto) {
  const order = { id: this.orders.length + 1, status: 'pending', ...dto }
  this.orders.push(order)
  return order
}

看起來沒問題：status 由伺服器決定，新訂單一律是 pending。但沒開 whitelist 時送這個（完整的訂單還有一個 items 品項陣列，它的規則留到下一節寫，這裡先照樣送）：

curl -X POST http://localhost:3100/orders -H 'Content-Type: application/json' \
  -d '{"customerId":1,"items":[{"productId":2,"qty":1,"size":"M"}],"status":"paid","total":0}'

回應是 "status":"paid","total":0。...dto 寫在 status: 'pending' 後面，物件展開時後面的同名屬性會蓋掉前面的，客戶端送的 status 和 total 就把伺服器設的值蓋掉了。

這種漏洞叫大量指派（mass assignment）：程式把客戶端送來的物件「整包」寫進資料，客戶端只要在 body 多塞欄位，就能改到原本不該由它決定的資料。為什麼寫的人沒發現？因為 TypeScript 擋不住：dto 的型別說它只有 customerId、items、note 三個欄位，編譯器相信這個型別，但執行時 dto 是客戶端送什麼就有什麼。用 ORM 時更危險，prisma.order.create({ data: { ...dto } }) 會一路寫進資料庫（第 14 課）。

修法是讓 ValidationPipe 處理多出來的欄位。它有兩個選項：

  • whitelist: true：沒有任何驗證裝飾器的欄位被默默刪掉。handler 拿到的物件只會有 DTO 上有規則的欄位，status、total 在進 handler 前就消失了。
  • forbidNonWhitelisted: true：要搭配 whitelist 使用。多出來的欄位不刪，改成直接回 400，訊息是 property status should not exist 這種格式。
{ provide: APP_PIPE, useValue: new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }) },

兩個怎麼選：whitelist 寬容，舊版 App 多送一個已經不用的欄位不會壞；forbidNonWhitelisted 嚴格，打錯欄位名稱馬上知道。例如前端送了 qyt 而不是 qty，只開 whitelist 時 qyt 被默默刪掉，錯誤會變成另一個看不出原因的「沒給 qty」；兩個都開，直接收到 property qyt should not exist。對外公開、需要相容很多版本客戶端的 API 可以只開 whitelist；自己的前後端一起改的 API，兩個都開比較好查問題。這門課兩個都開。

whitelist 從源頭把洞關掉，但只靠它不夠：哪天有人新增一支 API 時寫了 DTO 卻忘了某個欄位該不該開放，或者某支 API 不小心沒套到 DTO，...dto 又會把東西整包寫進去。另一層防線是 service 不要整包展開 DTO，明確挑出要用的欄位：

const order = { id: this.orders.length + 1, status: 'pending', customerId: dto.customerId, items: dto.items, note: dto.note }

兩層都做：pipe 擋住多的欄位，service 只寫它明確要寫的欄位，任何一層出錯，另一層還在。

💡 實務上：code review 看到「把 body 整包寫進資料庫」就停下來
大量指派是真實系統常見的資安漏洞，而且通常不是新手才寫得出來，而是某天資料表多了一個欄位（例如 isVip、discount），沒人想到 body 也能送它。review 時看到 ...dto、Object.assign(order, body) 直接寫進資料庫，先問「這張表現在和以後有沒有不該由客戶端決定的欄位」。另一個常見的坑是從 body 拿 customerId、userId：下單的人是誰應該來自登入狀態（認證課會做），不是客戶端自己填。顧客下單和後台店長修改訂單即使欄位相近，也分成兩個 DTO，各自只開放該開放的欄位。

頂層的欄位現在擋住了。但開場的 -3 杯不在頂層，它在 items 陣列的某一筆品項裡。只在 CreateOrderDto 加一行 items: OrderItemDto[]，裡面的規則會跑嗎？

品項陣列裡的 -3 杯怎麼擋？巢狀驗證與錯誤格式

先寫出品項的 DTO，再把它放進訂單。一筆品項的杯數是 1–10 的整數、大小只能是 S／M／L：

import { Type } from 'class-transformer'
import { ArrayMaxSize, ArrayMinSize, IsIn, IsInt, Max, Min, ValidateNested } from 'class-validator'

export class OrderItemDto {
  // productId：正整數，寫法同 customerId

  @IsInt() @Min(1) @Max(10)
  qty: number

  @IsIn(['S', 'M', 'L'])
  size: 'S' | 'M' | 'L'
}

export class CreateOrderDto {
  // customerId、note 同上一節

  @ArrayMinSize(1)
  @ArrayMaxSize(20)
  @ValidateNested({ each: true })   // 對陣列的每一項跑它自己的規則
  @Type(() => OrderItemDto)          // 告訴 class-transformer 每一項要變成哪個 class
  items: OrderItemDto[]
}

光寫型別 items: OrderItemDto[] 不夠，原因要回到上一節 ValidationPipe 的三步。TypeScript 留在 metadata 裡的只有「這個欄位是 Array」，陣列裡每一項是什麼 class 的資訊在編譯後就消失了。所以要靠兩個裝飾器補上：

  • @Type(() => OrderItemDto) 給第 2 步用：告訴 class-transformer 陣列的每一項要變成 OrderItemDto 的實例。少了它，每一項維持純物件，class-validator 在純物件上找不到規則，qty: 0 照樣通過。
  • @ValidateNested({ each: true }) 給第 3 步用：告訴 class-validator 驗完外層之後，要往下驗陣列的每一項。少了它，每一項雖然變成了 OrderItemDto，外層也不會往下驗。

兩個裝飾器缺一不可，而且少了任何一個都不會報錯，規則只是默默沒跑。這是這一課最容易踩的坑：測試只送合法資料時一切正常，要故意送錯的資料才看得出規則根本沒生效。

@ArrayMinSize(1) 擋掉沒有品項的空訂單。@ArrayMaxSize(20) 也別省：沒有上限，有人送一萬筆品項，每一筆都要驗證、計算價格，一個請求就能吃掉大量 CPU。

現在 -3 杯會回 400 了。接下來的問題是：400 裡面寫了什麼，前端拿到之後要怎麼用？Vue 的下單表單要把錯誤顯示在出錯的那一個輸入框旁邊，它得知道「是哪一筆品項的哪個欄位」錯了。ValidationPipe 預設的錯誤格式叫 'list'：message 是一個字串陣列，巢狀的訊息前面加上路徑。這適合給人讀，前端要拿來對應欄位，就得自己解析字串。NestJS 12 的 ValidationPipe 多了一個 errorFormat 選項，設成 'grouped' 時，message 改成以欄位路徑分組的物件。這是這門課的完整設定：

import { Module, ValidationPipe } from '@nestjs/common'
import { APP_PIPE } from '@nestjs/core'

@Module({
  providers: [
    {
      provide: APP_PIPE,
      useValue: new ValidationPipe({
        whitelist: true,
        forbidNonWhitelisted: true,
        transform: true,
        errorFormat: 'grouped',
      }),
    },
  ],
})
export class AppModule {}

開了 errorFormat: 'grouped' 後，巢狀錯誤的 key 是完整路徑（Nest 12.3.2 實際輸出）。這是一個多塞了 price、第二筆品項（索引 1）杯數是 0、大小也填錯的請求：

{
  "message": {
    "price": ["property price should not exist"],
    "items.1.qty": ["qty must not be less than 1"],
    "items.1.size": ["size must be one of the following values: S, M, L"]
  },
  "error": "Bad Request",
  "statusCode": 400
}

items.1.qty 就是「第二筆品項的杯數」。Vue 表單用這個 key 對應欄位就好，不用解析字串。下一課會把整個錯誤回應的格式定下來。

💡 實務上：錯誤格式是跟前端的約定，不是後端自己的事
開新專案時，先跟前端約好驗證錯誤長什麼樣子，寫進 API 文件，之後不要隨意改：Vue 表單靠這些 key 把錯誤顯示在欄位旁，key 一變畫面就壞。class-validator 預設的訊息是英文、給開發者看的，前端通常只拿 key 判斷哪個欄位錯，再顯示自己的中文文案，不會把 qty must not be less than 1 直接秀給客人。前端和後端各自檢查一次是正常的：前端檢查是為了即時提示、少一次來回，後端才是最後把關。

到這裡，POST /orders 開場的兩個事故都擋住了，這就是練習 1。接下來把同一套做法套到其他 API。第一支是店員後台的訂單列表，它沒有 body，資料全在網址的查詢參數裡，而查詢參數有一個 body 沒有的問題：全部都是字串。

訂單列表的 ?page=2 怎麼驗？查詢參數也用 DTO

訂單列表 GET /orders?page=2&pageSize=50&status=paid 有三個參數。第一節的寫法是每個參數各接一串 pipe，三個參數就是三串，還要各自處理預設值。@Query() 不帶名稱時拿到整個查詢物件，所以也可以寫一個 DTO，讓全域的 ValidationPipe 一次驗完：

export class ListOrdersQuery {
  @IsOptional()
  @Type(() => Number)     // '2' → 2
  @IsInt()
  @Min(1)
  page: number = 1        // 沒給時的預設值（開 transform 才保證有）

  @IsOptional() @Type(() => Number) @IsInt() @Min(1) @Max(100)
  pageSize: number = 20

  @IsOptional()
  @IsIn(ORDER_STATUSES)
  status?: OrderStatus
}

@Get()
list(@Query() query: ListOrdersQuery) { … }

跟訂單 body 比，這裡多了 @Type(() => Number)。第 2 課說過，查詢參數一律是字串。body 是 JSON，"qty": 2 解析出來本來就是數字；查詢字串沒有型別，?page=2 拿到的是 '2'，直接驗 @IsInt() 一定失敗。所以先讓 class-transformer 在第 2 步把它轉成數字，class-validator 在第 3 步再檢查。?page=abc 會轉成 NaN，被 @IsInt() 擋下，回 400。

預設值直接寫成 class 欄位的初始值 = 1。class-transformer 建實例時會先跑這些初始值，客戶端有給才蓋掉；這也是第二節講 transform: true 時要開它的原因：開了它，handler 拿到的一定是帶著預設值的 ListOrdersQuery 實例。

第一節的單一值寫法在這裡有一個陷阱：@Query('page') page: number 這種單一值的參數，開了 transform: true 時 ValidationPipe 會用 +value 轉數字（Nest 12.3.2 原始碼 transformPrimitive），?page=abc 變成 NaN 而且不會 400。單一值要驗證就用 ParseIntPipe；多個參數就用查詢 DTO。網路上還有一種讓所有欄位自動轉型、不用寫 @Type 的設定，這門課不用，原因見課末「補充與查表」。

最後是規則超出範圍時怎麼辦。pageSize=500 該回 400 還是默默改成 100？默默修正看起來友善，但前端以為拿到 500 筆、實際只有 100 筆，分頁就算錯了，而且沒有任何錯誤訊息可以查。規則寫清楚、超出就 400，讓呼叫的人第一次就發現。這是練習 3。

列表只讀資料。下一支 API 要改資料：店長在後台修改商品，只送有改的欄位。這時建立商品用的規則要「全部變選填」，而選填又帶出一個新問題：沒傳和傳 null 是同一件事嗎？

改商品時，「沒傳」和「傳 null」怎麼分？PartialType

PATCH /products/:id 的 body 是「CreateProductDto 的每個欄位都變成選填」：店長只改價格，就只送 { "price": 120 }。最直覺的做法是複製一份 CreateProductDto、每個欄位加 @IsOptional()，但不要手寫一份：兩份規則會漸漸不一致，有人把名稱上限從 30 改成 40，只改了建立那份，結果建立時能存 40 字的名稱、修改時卻被擋。@nestjs/mapped-types 提供跟 TypeScript 工具型別（TypeScript 課第 21 課）對應的函式，不只產生型別，連驗證規則一起複製：

Nest 函式對應的 TypeScript 型別結果
PartialType(Dto)Partial<Dto>每個欄位都選填，規則保留
PickType(Dto, ['name'])Pick<Dto, 'name'>只留下指定的欄位
OmitType(Dto, ['price'])Omit<Dto, 'price'>拿掉指定的欄位
import { PartialType } from '@nestjs/mapped-types'

export class UpdateProductDto extends PartialType(CreateProductDto) {}

這樣 { "price": 120 } 通過、{ "name": "" } 被沿用的 @IsNotEmpty() 擋下。但 { "name": null } 呢？PartialType 預設替每個欄位加上 @IsOptional()，而第二節說過，@IsOptional() 的意思是「值是 undefined 或 null 就跳過其他所有規則」。結果 null 一路通過，Object.assign 把商品名稱改成 null，菜單上出現一個沒有名字的商品。

PATCH 的語意應該是：沒傳＝不改；傳了就要合法。@nestjs/mapped-types 12.0.0 的 PartialType 有第二個參數：

export class UpdateProductDto extends PartialType(CreateProductDto, { skipNullProperties: false }) {}

這時它改用「值不是 undefined 才驗證」，null 會照樣跑 @IsString()、@IsNotEmpty()，回 400。真的需要「傳 null 代表清空」的選填欄位（例如備註），就在原本的 DTO 用 @ValidateIf(o => o.note !== null) 明確寫出來。這是練習 2。之後加上 Swagger 時，這些函式要改從另一個套件匯入，見課末。

到這裡用的都是 class-validator。最後一支 API 是新功能「集點卡兌換」，前端同事已經在 Vue 表單裡用 zod 寫好了同一份規則，問後端能不能直接共用。NestJS 12 起可以。

同一件事用 zod 怎麼做？Standard Schema

為什麼這裡換成集點卡的例子，而不是把訂單改寫成 zod？因為實務上很少把已經寫好的 DTO 整批換掉，比較常見的是新功能用新的做法；練習 4 也要求你在同一個 AppModule 裡讓兩種驗證並存。

先講名詞。zod、valibot、arktype 是三個常見的驗證套件，各自有一套寫 schema 的 API。Standard Schema 是它們共同實作的一個小介面：每個 schema 物件上都有 ~standard.validate() 這個方法，傳一個值進去，回傳驗證結果。框架只要認得這個介面，就能接受任何一個套件的 schema，不用替每個套件各寫一份整合。NestJS 12 起，@Body()、@Query()、@Param() 可以直接接一個 schema，由內建的 StandardSchemaValidationPipe 呼叫這個介面驗證。TypeScript 課第 26 課寫過的 zod schema 可以直接用（本課程是 zod 4.6.7）：

// stamp-cards/redeem.schema.ts
import { z } from 'zod'

export const redeemSchema = z.object({
  cardId: z.int().positive(),
  points: z.int().min(1).max(100),
  reason: z.string().max(50).default('兌換'),
})
export type RedeemInput = z.infer<typeof redeemSchema>   // 型別從 schema 推導，不用另外寫

// stamp-cards.controller.ts
@Post('redeem')
redeem(@Body({ schema: redeemSchema }) body: RedeemInput) {
  return { redeemed: body }   // body.reason 已經套上預設值
}

// app.module.ts：再登記一個全域 pipe
{ provide: APP_PIPE, useClass: StandardSchemaValidationPipe },

跟 DTO 對照著看，有幾個行為要知道（Nest 12.3.2 原始碼與實測）。

handler 拿到的是 schema 的輸出，不是客戶端送來的原始 body：.default()、.transform() 都已經套用，所以 body.reason 一定有值，預設值寫在 schema 裡就好，不用在 handler 裡補。驗證失敗時回 400，訊息是字串陣列，每一則前面加上欄位路徑，例如 ["points: Too small: expected number to be >=1"]。

兩個全域 pipe 為什麼不會打架？StandardSchemaValidationPipe 只處理有 schema 的參數，其他值原樣放行；ValidationPipe 只處理型別是 class 的參數，RedeemInput 是型別別名，metadata 是 Object，它會跳過。所以兩個 pipe 可以同時登記、互不干擾，訂單照樣由 DTO 驗證，集點卡由 zod 驗證。

多出來的欄位怎麼處理也要對照：z.object 預設刪掉多的欄位，效果像 whitelist；要像 forbidNonWhitelisted 一樣回 400，用 z.strictObject。另外 body 是 JSON，數字本來就是數字，不要用 z.coerce.number()：它會把 "3"、甚至空字串 ""（變成 0）都轉成數字，該擋的資料就放行了。coerce 只在查詢參數這種本來就是字串的地方用，角色等同 DTO 裡的 @Type(() => Number)。

還有一個常見的錯誤寫法：不登記 pipe，在 handler 裡自己 redeemSchema.parse(body)。驗證失敗時丟出的 ZodError 不是 HttpException，Nest 不認得它，會回 500，客戶端看到「伺服器壞了」而不是「你送錯了」。驗證交給 pipe，失敗才會是 400。

兩種寫法都能用之後，團隊要決定以哪一種為主：

class-validator（DTO class）zod（Standard Schema）
型別從哪來class 本身就是型別z.infer 從 schema 推導
跟前端共用難（裝飾器、class-transformer 綁在後端）容易：Vue 表單可以 import 同一個 schema
OpenAPI 文件Swagger 外掛直接讀 DTO（第 23 課）v12 起也能從 schema 產生
現有專案與資料Nest 專案最常見的寫法，網路範例多v12 才原生支援，範例較少
容易踩的坑忘了 @Type、interface 當 DTO、import type忘了登記 pipe、誤用 coerce

兩種都能做好。重點是一個專案選一種為主，寫進團隊的慣例：混著用時，每個新的 endpoint 都要重新決定一次，code review 也要懂兩套規則。接手的專案是 class-validator 就延用；新專案、前端也用 zod 的話，選 zod 可以少寫一份規則。這門課後面以 class-validator 為主，因為第 23 課的 Swagger 外掛與大部分 Nest 生態系的範例都是這種寫法。

四支 API 都有驗證了。最後要退一步問：資料通過驗證之後，後面的程式就可以完全放心了嗎？

驗證通過，就可以放心了嗎？在邊界驗證，裡面信任

這一課所有的驗證都放在同一個位置：資料從外面進來的那一刻。這個位置叫邊界，除了 HTTP 的 body、查詢參數，還包括第 20 課佇列裡的 job 資料、第 22 課別的系統打進來的 webhook。原則是在邊界驗證，裡面信任：通過之後，service 就信任 CreateOrderDto 的型別，不再到處 if (typeof qty !== 'number')。為什麼不多檢查幾次比較保險？因為檢查散落在各層，規則會互相矛盾（controller 說最多 10 杯、service 說最多 20 杯），出問題時也看不出哪一份才算數。一份規則放在邊界，才有一個地方可以查、可以改。

但「放心」有範圍。DTO 只檢查格式，不檢查業務規則和權限，這三種檢查各有自己的位置：

  • 格式：qty 是 1–10 的整數 → DTO。只看這一筆資料本身就能判斷。
  • 業務規則：productId: 99 格式正確，但商品不存在、已經下架、庫存不夠 → service 查資料後決定（第 8 課丟領域錯誤，第 15 課處理庫存）。要查資料庫才知道答案的，就不是 DTO 的事。
  • 權限：「只有店長能改價格」不能靠 DTO 拿掉 price 欄位來擋，因為同一個 DTO 店長也要用。誰能做什麼是 guard 的事（第 6 課；登入與角色在認證課）。驗證通過不代表有權限。
💡 實務上：收緊驗證規則也算 API 的破壞性變更
DTO 的規則就是對外的契約。把 note 從最多 50 字改成 30 字、把選填改成必填，後端改一行就上線了，但已經裝在客人手機上的舊版 App 還在送舊格式，更新前會一直收到 400。資深工程師改規則前會先問：現在有哪些客戶端在呼叫這支 API？放寬規則通常安全，收緊規則要先確認前端已經跟上，或等舊版用量降下來再改。上線後若客服回報「下單一直失敗」，先查有沒有一批 400 集中在同一個欄位，往往就是規則改了、某個客戶端沒跟上。

回到開場的兩個事故：-3 杯被品項 DTO 的 @Min(1) 擋下，多塞的 "status": "paid" 被 forbidNonWhitelisted 擋下，service 也不再整包展開 body。列表、商品修改、集點卡兌換用同一套原則補上了驗證。練習就是把這四支 API 親手做一遍。

補充與查表

主線用不到、但寫程式或讀舊專案時會查的細節。

Nest 內建的 pipe

都從 @nestjs/common 匯入，處理單一值。查表用，不用背：

ParseUUIDPipe檢查 UUID 格式（可用 { version: '4' } 限定版本）@Param('id', ParseUUIDPipe) id: string
ParseEnumPipe只接受某個 enum 的值@Query('size', new ParseEnumPipe(Size)) size: Size

ValidationPipe 這課用到的四個選項

選項沒開時開了之後
whitelist沒有規則的欄位照樣傳給 handler沒有任何驗證裝飾器的欄位被默默刪掉
forbidNonWhitelisted（要搭配 whitelist）多出來的欄位改成直接 400：property price should not exist

為什麼不用 enableImplicitConversion

網路上常看到另一種寫法：transformOptions: { enableImplicitConversion: true }，讓 class-transformer 依欄位的 TypeScript 型別自動轉換，不用每個欄位寫 @Type。代價是轉換規則不直覺：布林欄位收到字串 'false' 會變成 true（非空字串轉布林都是 true），而且它也套用在 body 上，"qty": "2" 這種該擋的資料會被轉成數字放行。這門課明寫 @Type。

加上 Swagger 之後的 PartialType

之後加上 Swagger（第 23 課），PartialType 等函式要改從 @nestjs/swagger 匯入，API 文件才會帶到欄位；它也有同樣的 skipNullProperties 選項。

練習

在 learn/ 執行 node check.mjs nestjs 07 建立 work/07/。起始專案有訂單、商品、集點卡三個 controller，資料放在記憶體；DTO 的欄位寫好了，規則還沒寫。邊寫邊用 npm run start:dev 和 curl -i 自己試送錯的資料。四題的測試都用 AppModule 建應用（不會跑 main.ts），全域 pipe 要登記在 AppModule。

練習 1：替 POST /orders 寫好 CreateOrderDto 與 OrderItemDto 的規則，並在 AppModule 用 APP_PIPE 登記全域的 ValidationPipe（whitelist、forbidNonWhitelisted、transform、errorFormat: 'grouped'）：

  • customerId：正整數。
  • items：1–20 筆；每一筆 productId 正整數、qty 1–10 的整數、size 只能是 S／M／L。
  • note：選填字串，最多 50 字。

測試會檢查：合法的訂單回 201，handler 拿到的是 CreateOrderDto 實例、items[0] 是 OrderItemDto 實例；多塞 price、status（頂層或品項裡）回 400；items[1].qty 是 0 時，錯誤裡有 items.1.qty 這個 key；字串 "1" 不能當數字。

練習 2：用 PartialType 從 CreateProductDto 產生 UpdateProductDto，讓 PATCH /products/:id 只更新有傳的欄位：{ "price": 120 } 不動到名稱；name 傳空字串或 null 都要 400，而且原本的名稱不能被改掉；CreateProductDto 的其他規則（name 最多 30 字、price 1–1000 的整數）照樣適用；多的欄位 400。不要手寫一份規則，測試會確認 UpdateProductDto 繼承自 PartialType(CreateProductDto, …)。這一題要先做完練習 1 的全域 ValidationPipe。

練習 3：完成 GET /orders 的查詢 DTO ListOrdersQuery：page 正整數、沒給是 1；pageSize 1–100 的整數、沒給是 20；status 選填，只能是 ORDER_STATUSES 之一。起始的 service 會把收到的條件原樣回傳，測試看的是型別：page 要是數字 3，不是字串 '3'。超出範圍一律 400，不要默默改成合法的值。

練習 4：用 zod 寫 POST /stamp-cards/redeem 的 body schema：cardId 正整數、points 1–100 的整數、reason 選填字串，沒給是 '兌換'。在 controller 用 @Body({ schema: redeemSchema })，並在 AppModule 再加一個 APP_PIPE 登記 StandardSchemaValidationPipe。預設值寫在 schema 裡（.default()），不要在 handler 裡補。測試會確認 schema 本身與 handler 都拿到預設值、points: 0 回 400 且訊息以 points: 開頭、字串 "3" 不能當 cardId，以及練習 1 的 POST /orders 驗證照常運作。

練習 5：同事把 DTO 寫成 export interface CreateOrderDto { qty: number }，用 import type 匯入到 controller（一般的 import 會被 TypeScript 擋下），全域 ValidationPipe 開了 whitelist。客戶端送 { "qty": "很多", "price": 0 } 會怎樣？

✓ interface 在執行時不存在，參數的型別 metadata 只剩 Object，ValidationPipe 遇到 Object 直接放行，什麼都不驗，whitelist 也沒有規則可以比對。a 是「型別寫了就會驗證」的誤解。c 錯：它不會拒絕，只會跳過。d 錯：用 import type 編譯會過，這正是它危險的地方。

練習 6：handler 寫 list(@Query('page') page: number)，沒有 ParseIntPipe，全域 ValidationPipe 也沒開 transform。請求 GET /orders?page=2，page === 2 的結果是？

✓ 查詢參數一律是字串，型別註記只給編譯器看，執行時什麼都不做（a 錯）；Express 5 的查詢解析只產生字串和字串陣列（b 錯）。要數字就加 ParseIntPipe，或用查詢 DTO 搭配 @Type(() => Number)。開 transform: true 雖然會轉，但 'abc' 會變成 NaN 而不是 400，單一值還是用 ParseIntPipe。

練習 7：UpdateProductDto extends PartialType(CreateProductDto)（預設選項），name 在 CreateProductDto 上有 @IsString()、@IsNotEmpty()。PATCH 送 { "name": null } 會怎樣？

✓ PartialType 預設替每個欄位加 @IsOptional()，而它對 undefined 和 null 都跳過其他規則，所以 b 不會發生。whitelist 只看「這個欄位有沒有規則」，不看值，name 有規則就保留（c 錯）。修法是 PartialType(CreateProductDto, { skipNullProperties: false })：只有沒傳才跳過，null 照樣驗證。

常見錯誤

  • DTO 寫成 interface、type，或用 import type 匯入：metadata 只剩 Object，ValidationPipe 什麼都不驗，也不會報錯。DTO 一律是 class，用一般的 import。
  • 只在 main.ts 用 useGlobalPipes：測試建出來的應用沒有驗證。用 APP_PIPE 登記在模組裡。
  • 沒開 whitelist，service 又整包展開 DTO：客戶端多塞 price、status 就改到資料（大量指派）。開 whitelist，自己的 API 再加 forbidNonWhitelisted；service 明確挑出要寫的欄位。
  • 巢狀物件忘了 @ValidateNested 或 @Type：不會報錯，裡面的規則默默不跑。兩個都要寫，陣列加 { each: true } 和 @ArrayMaxSize。
  • 單一值的查詢參數只靠 transform: true 轉數字：?page=abc 變成 NaN 而不是 400。單一值用 ParseIntPipe，多個參數用查詢 DTO 加 @Type(() => Number)。
  • 超出範圍默默修正：Math.min(pageSize, 100) 讓呼叫的人不知道規則。回 400。
  • PATCH 用 PartialType 卻沒處理 null：送 null 就把必填欄位清空。加 { skipNullProperties: false }。
  • 在 handler 裡 schema.parse()：ZodError 變成 500。用 @Body({ schema }) 加 StandardSchemaValidationPipe。
  • 同一個專案混用兩種驗證、沒有規則：選一種為主，寫進團隊慣例。
  • 以為驗證通過就有權限：DTO 只管格式。誰能改價格是 guard 的事，商品存不存在是 service 的事。

小結

  • pipe 在 handler 前對每個參數各跑一次，轉換或驗證單一值，失敗回 400、handler 不執行；多個 pipe 由左到右執行，DefaultValuePipe 放在 ParseIntPipe 前面。
  • 整個 body 用 DTO 描述：DTO 一定是 class，用 class-validator 寫規則；ValidationPipe 先用 class-transformer 建實例、再用 class-validator 驗證，用 APP_PIPE 全域登記，測試也會套用。
  • 大量指派：客戶端多塞欄位、service 整包展開，就改到不該改的資料。開 whitelist＋forbidNonWhitelisted，service 明確挑欄位，兩層都做。
  • 巢狀陣列要 @ValidateNested({ each: true })＋@Type()，少一個規則就默默不跑；v12 的 errorFormat: 'grouped' 讓錯誤以 items.1.qty 這種路徑分組，前端依欄位顯示。
  • 查詢參數一律是字串：查詢 DTO 用 @Type(() => Number) 轉換、欄位初始值當預設值（要開 transform），超出範圍回 400。
  • 更新用 PartialType 沿用規則，加 { skipNullProperties: false } 讓「沒傳＝不改、傳 null＝400」。
  • v12 的 @Body({ schema })＋StandardSchemaValidationPipe 能用 zod 驗證，handler 拿到 schema 的輸出；兩種 pipe 可以並存，但專案要選一種為主。
  • 在邊界驗證、裡面信任；驗證只管格式，業務規則在 service、權限在 guard。

下一課處理驗證之後的錯誤：service 丟出「庫存不足」這類領域錯誤時，怎麼用 exception filter 讓所有錯誤都變成同一種格式的回應。
