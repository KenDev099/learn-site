階段 5：上線、維運與架構（資深） · 第 24 課

日誌、健康檢查與優雅關機

咖啡店 API 上線後的第一個星期六。下午兩點部署了新版本，兩點十分客服傳來訊息：「王小明說他兩點整付了款，信用卡也扣了，但沒收到收據，App 上訂單還是『未付款』。」同一時間還有兩位客人回報付款時看到「連線中斷」。你打開伺服器的 log，看到幾千行 付款完成、收據工作已排入、收據已寄出 彼此交錯，好幾個程序、幾十個客人的紀錄混在一起，分不出哪一行屬於王小明那一次付款，也就回答不了客服最基本的問題：他的付款走到哪一步，為什麼停在那裡？

這一課的任務就是處理這件事：先讓 log 查得出王小明那筆付款發生了什麼，再修好造成它的原因，讓下一次部署不會再有人「款扣了、訂單沒變」。這兩件事都不是程式邏輯的 bug，而是程式在正式環境裡「怎麼活、怎麼死」沒處理好：活著的時候，log 要能把同一個請求串起來；被叫停的時候，要把手上的事做完再走。用到的工具是 Nest 12 內建的 ConsoleLogger、@nestjs/terminus 12.1.0 和 Node 的 AsyncLocalStorage。

這課的路線：
  1. 上線後只剩 log 看得到：log 要怎麼寫，搜尋工具才找得到王小明那張訂單；Nest 的 ConsoleLogger 怎麼改成一行一個 JSON。
  2. 同一張訂單有好幾次請求，怎麼分出哪一行屬於哪一次：給每個請求一個 requestId，以及為什麼它不能當參數一層層傳。
  3. AsyncLocalStorage：service 裡的 log 怎麼自動帶上「這一次請求」的 requestId。查到這裡，會發現王小明的付款是被部署中斷的。
  4. 健康檢查：部署平台怎麼決定送流量給誰、重啟誰，再用 Terminus 做出 /health/live 與 /health/ready。
  5. 優雅關機：收到停止訊號後，讓進行中的付款和收據做完再結束。
這課會用到：
  • Node 課第 19 課的結構化 log 與 AsyncLocalStorage：log 一行一個 JSON、欄位名稱固定；als.run(store, fn) 裡的所有非同步工作都讀得到同一份 store。
  • Node 課第 21 課的優雅關機與健康檢查：收到 SIGTERM 先停止接新請求、做完手上的再結束；liveness 回答「活著嗎」，readiness 回答「能接請求嗎」。
  • 第 4 課的生命週期 hook：app.close() 時依序呼叫 onModuleDestroy、beforeApplicationShutdown、onApplicationShutdown，要先 enableShutdownHooks() 才會在收到訊號時觸發。
  • 第 6 課的 middleware：請求進來後最早執行的一層，用 forRoutes 指定套用到哪些路由。

上線後只剩 log：怎麼寫才搜得到王小明那筆付款？

開發時程式跑在你的電腦上，出問題可以看終端機、可以下中斷點。上線後程式跑在部署平台的機器上，而且通常同時跑好幾個程序，你沒辦法停下它、也沒辦法看它的變數。你唯一看得到的，是它自己寫出來的 log（日誌）：程式執行到某個地方時留下的一行紀錄。程序把 log 寫到標準輸出，平台把所有程序的輸出收進一個集中的搜尋工具，出事時值班的人在那裡搜。

所以 log 真正的讀者不是一行一行看的人，而是搜尋工具。客服問「王小明的訂單 7 怎麼了」，你要的是在搜尋框打一個條件，就列出訂單 7 的所有紀錄。這件事做不做得到，取決於 log 寫成什麼樣子。如果寫成 `訂單 ${id} 付款完成` 這種把值拼進句子的文字，搜尋工具只看到一串字，你只能用關鍵字或正規表示式去猜，「訂單 7」還會順便撈到「訂單 70」；每個人拼句子的方式不同，欄位名稱也不固定。Node 課第 19 課的做法是結構化 log：一行一個 JSON，訊息是固定的一句話，會變動的值放在有名字的欄位裡。搜尋工具會把每一行解析成欄位，你就能下「params.orderId = 7」這種精確的條件。

Nest 的 Logger 你從第 1 課就在用：new Logger(OrdersService.name)，然後 this.logger.log('訂單建立', { orderId, total })。Logger 本身不負責輸出，它只是一個轉接頭，把呼叫轉給應用程式設定的那個 logger；預設是 ConsoleLogger，由它決定一行 log 長什麼樣子。ConsoleLogger 預設印成給人看的彩色文字，搜尋工具解析不了。Nest 12 的 ConsoleLogger 有 json 選項，開了就改成一行一個 JSON：

new ConsoleLogger({ json: true })

// this.logger.log('訂單建立', { orderId: 7, total: 190 }) 印出：
{"level":"log","pid":44658,"timestamp":1793514655225,"message":"訂單建立","context":"OrdersService","params":{"orderId":7,"total":190}}

這一行從左到右：

  • level：層級。log 是一般紀錄，另外還有 warn、error、debug 等，值班時常先篩 error。
  • pid：印出這行的程序編號。同時跑好幾個程序時，靠它分辨是哪一個程序寫的，這一課稍後就會用到。
  • timestamp：毫秒時間戳記。
  • message：固定的訊息，context：哪個類別印的（建立 Logger 時傳的名字）。
  • params：呼叫時傳的第二個參數，會變動的值都在這裡。

第二個參數要傳物件才會進 params；傳字串進去，Nest 會把它當成 context（類別名稱），例如 logger.log('付款完成', orderId) 的 orderId 會跑到 context 欄位，不會被當成資料。所以寫法固定是：訊息是不變的一句話，orderId、total 放在物件裡。這樣搜 params.orderId = 7 就能找出這張訂單的所有紀錄。

剩下的問題是讓整個應用程式都用這個 JSON 格式，包含 Nest 自己啟動時印的那些 log。做法是寫一個 AppLogger extends ConsoleLogger 的 provider，在 main.ts 用 app.useLogger(app.get(AppLogger)) 換上去。把它做成 provider，而不是直接 new ConsoleLogger({ json: true })，是因為 provider 可以注入別的東西，下一節要注入 RequestContext。這裡有一個時間差：NestFactory.create 的過程就已經在印 log，那時 AppLogger 還沒建好，這幾行會用預設的彩色格式印出，上線後收集工具只有這幾行解析失敗。bufferLogs: true 讓 Nest 先把 log 存著，等 useLogger 換好之後再用新的 logger 一起印：

const app = await NestFactory.create(AppModule, { bufferLogs: true })
app.useLogger(app.get(AppLogger))   // 練習專案放在 configureApp 裡，main.ts 和測試共用（第 10 課）
log 裡不要放個資與密鑰：email、電話、密碼、token、信用卡號。log 會被收進搜尋工具、保留很久、被很多人看到。練習專案的 Mailer 寄收據時只記 orderId，不記 email，就是這個原因。Node 課第 19 課的「不能記的東西」整節都適用。

現在搜 params.orderId = 7，王小明這張訂單的紀錄都找得到了，但還不夠。同一張訂單常常有好幾次請求：建立訂單一次、付款一次，客人看到連線中斷又按一次付款，前端也可能自動重試。這些請求印出的行都帶 orderId: 7，時間又挨在一起，你分不出哪幾行屬於同一次付款。還有一些 log 根本沒有 orderId，例如驗證失敗、guard 擋下的紀錄，這種行用 orderId 撈不到。缺的是一個代表「這一次請求」的編號。

💡 實務上：log 是寫給出事時值班的人看的
上線後 log 會被收進集中的搜尋工具（雲端平台的 log 服務、Grafana Loki、Datadog 之類），值班的人用 orderId、level 這些欄位篩選，不會一行一行讀。該記的是狀態改變和失敗：訂單建立、付款成功或失敗、收據寄送失敗；每個請求都印整個 request body 只會讓量和費用暴增，真正的線索反而被淹沒。正式環境通常只開 log、warn、error 這幾個層級（logLevels 選項），更細的 debug 留給本機。資深在 code review 時會問一句：「客服明天來問這筆訂單，只看 log 答得出來嗎？」王小明這種客訴，就是這個問題的實際考題。

同一張訂單有好幾次請求：怎麼分出哪一行屬於哪一次？

上一節留下的缺口，做法是每個請求一進來就給它一個編號，叫 requestId。這個請求執行過程中印的每一行 log 都帶上它，回應時也放在標頭 X-Request-Id 裡回給前端。這樣一來，「哪幾行屬於同一次付款」就變成「哪幾行的 requestId 相同」，搜一下就全部列出來，從請求進來到排入收據工作，按時間排好。

回應標頭這一步是讓編號能交到人手上。前端在錯誤畫面顯示這串編號，客服請客人截圖，工程師拿去搜，就不用再靠「大概兩點左右」去猜。反方向也可以：前端自己產生編號，放在請求標頭 X-Request-Id 送來，API 沿用它，Vue 前台、Nginx、API 三邊的 log 就能用同一個編號對起來。

編號要在請求一進來就決定，後面每一層才用得到，所以產生它的位置是 middleware（第 6 課）：它是請求進來後最早執行的一層，比 guard、pipe、controller 都早。

@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const incoming = req.get('x-request-id')
    // 只接受 1–64 個英數、-、_：換行會讓人偽造 log 行，超長的值會塞爆 log
    req.requestId = incoming && VALID_ID.test(incoming) ? incoming : randomUUID()
    res.setHeader('X-Request-Id', req.requestId)
    next()
  }
}

注意它沒有直接採用前端送來的值。請求標頭是任何人都能填的輸入：如果值裡有換行字元，印進 log 之後會變成兩行，第二行可以被偽造成一筆看起來真實的紀錄；值超長則會把 log 塞爆。所以先用正規表示式檢查格式，不合格就自己用 randomUUID() 產生一個。練習專案已經有這段，也已經用 consumer.apply(RequestIdMiddleware).forRoutes('*') 套到所有路由。

難的是下一步。middleware 把編號放在 req.requestId，但印 log 的地方不在 middleware：OrdersService.pay 裡的 this.logger.log('付款完成', …)，還有它呼叫的 ReceiptsProducer.enqueue 裡的 log，手上都沒有 req。它們要怎麼知道「現在這個請求」的 requestId？直覺會想到三種做法，都有問題。

下面表格的第三種做法會用到第 3 課的一個名詞，先補上：provider 預設是 singleton：整個應用程式只建一個實例，所有請求共用。另一種是 request scope：用 @Injectable({ scope: Scope.REQUEST }) 宣告，每個請求進來都建一個新的實例，所以它可以用 @Inject(REQUEST) 注入「這一次的請求物件」。

做法問題
當參數一層一層傳：pay(id, requestId)每個 service 方法都多一個參數；漏傳一層（ReceiptsProducer）那一層的 log 就沒有。requestId 是基礎設施的事，不該出現在業務方法的簽名裡
存在模組層級的變數：let current = idNode 是一個執行緒處理所有請求：A 在 await 付款服務的 1 秒裡，B 進來把變數改成 B 的 id，A 醒來後印出的 log 全帶著 B 的編號
request scope 的 logger：@Injectable({ scope: Scope.REQUEST }) 加 @Inject(REQUEST)注入它的 OrdersService、再注入 OrdersService 的 controller，整條鏈都變成每個請求重新建立一次：慢，而且 app.get(OrdersService) 會直接丟錯，測試和排程都拿不到它

第二種做法最容易讓人誤會，值得多說一句。「Node 只有一條執行緒」常被理解成「一次只處理一個請求」，所以放一個全域變數應該沒事。其實單一執行緒只代表同一瞬間只有一段 JavaScript 在跑；請求 A 一遇到 await（等付款服務、等資料庫），執行緒就去處理請求 B，等 A 的結果回來才接著跑 A。請求是交錯進行的，一個全域變數同時只能存一個值，誰最後寫入就是誰的。開場那幾千行交錯的 log，就是這種交錯執行的結果。

所以要找的東西有三個條件：不用改業務方法的參數、每個請求各自一份不會互相蓋掉、而且所有 provider 維持 singleton。Node 內建了一個剛好做這件事的工具。

AsyncLocalStorage：service 怎麼拿到「這一次請求」的 requestId？

那個工具是 AsyncLocalStorage（從 node:async_hooks 匯入），Node 課第 19 課用過。它是一個「跟著非同步流程走」的儲存空間：als.run(store, fn) 執行 fn，在 fn 裡面、以及 fn 引發的所有非同步工作裡（await 之後的程式、它建立的 Promise、計時器、callback），呼叫 als.getStore() 都拿到這份 store；在 run 外面拿到 undefined。

它能解決上一節的問題，關鍵在「引發的所有非同步工作」這幾個字。Node 會記住每個非同步工作是在哪一次 run 裡建立的，等它之後被執行，getStore() 回傳的就是當初那份 store，跟這段時間裡有沒有別的請求插進來無關。請求 A 和請求 B 各自 run 一次，就算交錯執行，A 的程式醒來讀到的永遠是 A 的 store，B 讀到 B 的。它不是全域變數，所以不會被蓋掉；它也不用當參數傳，因為讀的人直接問 getStore() 就好。

把它包成一個 singleton 的 provider，整個應用程式只有一個，誰需要就注入：

@Injectable()
export class RequestContext {
  private readonly als = new AsyncLocalStorage<{ requestId: string }>()

  run<T>(requestId: string, fn: () => T): T {
    return this.als.run({ requestId }, fn)
  }

  get requestId(): string | undefined {
    return this.als.getStore()?.requestId   // 情境外（啟動、排程、worker）是 undefined
  }
}

RequestContext 只有一個實例，卻能回答「這次請求的 id」，因為每個請求的資料不存在實例的欄位裡，而是存在 AsyncLocalStorage 為每次 run 各自保留的 store 裡。下面把「某次 run 範圍內」稱為情境：在情境裡讀得到 requestId，在情境外讀到 undefined。

接著要決定在哪裡開這個情境。我們要的是「這個請求接下來的所有處理」都在情境裡，而 middleware 的 next() 正好代表「接下來的所有處理」：guard、pipe、controller、service 都是從 next() 開始往下跑的。所以把 next 本身交給 run：

this.context.run(req.requestId, next)   // guard、pipe、handler、service 全都在這個情境裡執行

常見的失手是寫成 this.context.run(id, () => {})，然後另外呼叫 next()。情境只涵蓋傳給 run 的那個函式，那個空的 callback 一結束情境就結束了；next 在情境外面執行，整個請求讀到的都是 undefined。

最後讓 logger 自動帶上它，這樣 OrdersService 這些地方完全不用改。ConsoleLogger 在 json 模式下，每一行都會先經過 getJsonLogObject(message, options) 組成物件再轉成 JSON。覆寫這個方法，在父類別組好的物件上多加一個欄位：

@Injectable()
export class AppLogger extends ConsoleLogger {
  constructor(private readonly requestContext: RequestContext) {
    super({ json: true })
  }

  protected override getJsonLogObject(message: unknown, options: Parameters<ConsoleLogger['getJsonLogObject']>[1]) {
    return { ...super.getJsonLogObject(message, options), requestId: this.requestContext.requestId }
  }
}

情境外 requestId 是 undefined，而 JSON.stringify 會直接省略值是 undefined 的欄位，所以啟動、排程、worker 的 log 不會多出空字串，也不會帶到上一個請求的編號。OrdersService、ReceiptsProducer 一行都不用改，繼續 new Logger(…)，它們印的每一行都會經過 AppLogger，自動帶上當下情境的 requestId。下圖是兩個請求交錯時的樣子：

有了這套 log，回頭查王小明。不過 requestId 是這次事故之後才加上的，兩點那次付款的舊 log 裡沒有它；請求斷在半路、回應一直沒送出，App 也從來沒拿到 X-Request-Id。所以這一次只能用當時就有的線索：搜 params.orderId = 7，找得到這張訂單建立的紀錄，但付款那一段沒有「付款完成」，也沒有「收據工作已排入」，信用卡卻已經扣款。再看兩點整前後那幾行 log 的 pid：寫這幾行的是舊版本的程序，它在兩點整之後再也沒寫過任何 log，下一批 log 是新版本的啟動紀錄，換了另一個 pid。結論是：付款服務已經扣款，但在寫回訂單狀態之前，部署把舊程序停掉了，請求斷在半路。另外兩位看到「連線中斷」的客人，也是同一秒在那個程序上的請求。這次是靠 orderId 加時間和 pid 一點一點拼出來的；有了 requestId 之後，下次同類客訴只要前端在錯誤畫面顯示 X-Request-Id（或由前端自己產生、送出並記下），一次搜尋就能列出那一次請求的每一行。

💡 實務上：把 requestId 交到客服和下游手上
前端出錯時把 X-Request-Id 顯示在錯誤訊息或回報表單裡，客服拿到這串編號，工程師就能直接搜到那一次請求的所有 log，王小明這種客訴從「大概兩點左右」變成一次搜尋。AsyncLocalStorage 只管得到同一個程序裡的這一次請求：排進 BullMQ 的工作由 worker（第 20 課）另外執行，要把 requestId 放進 job 的資料、worker 處理時再印出來，收據那一段才接得上。呼叫其他內部服務時也把它放在標頭往下傳。服務一多，團隊通常會改用 OpenTelemetry 這類追蹤工具做同一件事，概念就是這一節的 requestId。

查清楚了，接下來要修。問題不在付款的程式，而在程序被停掉的方式。要修好它，得先知道部署平台怎麼跟你的程序溝通：它用健康檢查決定要不要把請求送給某個程序、要不要重啟它，用停止訊號通知程序該結束了。先看前者。

部署平台怎麼決定送流量給誰、重啟誰？

先看健康檢查要解決的處境。Node 課第 21 課講過，正式環境的服務不會只跑一個程序。前面有一個負載平衡器（load balancer）或容器平台，所有請求先到它那裡，再由它分給後面的好幾個程序（部署課會講 Nginx、Docker、雲端平台）。它要分得好，就得隨時知道每個程序的狀況，但它看不到你的程式內部，只能從外面問。做法是你的程式提供一個 HTTP 端點，平台每隔幾秒打一次，用回應的狀態碼判斷：這就是健康檢查端點。

平台想知道的其實是兩個不同的問題，答錯的後果也不同，所以要兩個端點：

liveness：還活著嗎readiness：能接客嗎
路徑/health/live/health/ready
檢查什麼程序能回應就是 200，不碰任何依賴資料庫、Redis 都連得上才 200，任何一項壞就 503
失敗時平台做什麼重啟這個程序暫停送流量給它，程序不動
該在什麼時候失敗事件迴圈卡死（下一課）依賴斷線、啟動中、關機中

判斷一個檢查該放在哪一邊，問自己一句：「這種狀況，重啟程序修得好嗎？」程序的事件迴圈卡死了、不回應任何請求，重啟可以修好，這是 liveness 的事。資料庫斷線，重啟程序修不好，程序本身沒壞，只是暫時沒辦法服務，正確的反應是「先別把請求送給我」，這是 readiness 的事。

最常見也最傷的錯，就是 liveness 也查資料庫。資料庫重開晃了 30 秒，所有程序的 liveness 同時失敗，平台把它們全部重啟；重啟修不好資料庫，反而讓所有程序同時啟動、同時重連，把剛恢復的資料庫再打一次。原本 30 秒的小狀況，變成整個服務一起掛掉。

readiness 表格最後一格的「關機中」跟王小明的事直接有關。部署時，平台會先讓新版本的程序起來，等它的 readiness 回 200 才開始送流量給它；舊程序要結束前，則要先讓它的 readiness 回 503，平台不再送新請求過去，它只需要把手上的請求做完。新舊交接時沒有請求被丟到不能處理的程序上，部署對客人來說才是無感的。最後一節會回來接上這一步。

概念清楚了，接下來用 Nest 的套件把這兩個端點做出來。實作時有一個陷阱要特別處理：依賴不是壞掉，而是卡住不回應。

用 Terminus 做出 /health/live 與 /health/ready

@nestjs/terminus 是 Nest 官方的健康檢查套件。它把每一項檢查（資料庫通不通、Redis 通不通）稱為一個健康指標（health indicator），你列出要檢查哪些指標，它負責執行、彙整成固定格式的回應、決定狀態碼。12.1.0 的用法：

// health.module.ts
@Module({ imports: [TerminusModule], controllers: [HealthController], providers: [RedisHealthIndicator] })

// health.controller.ts
@Controller('health')
export class HealthController {
  constructor(
    private readonly health: HealthCheckService,
    private readonly db: PrismaHealthIndicator,
    private readonly prisma: PrismaService,
    private readonly redis: RedisHealthIndicator,
  ) {}

  @Get('live')
  @HealthCheck()
  live() { return this.health.check([]) }            // 什麼都不查：能執行到這裡就是活著

  @Get('ready')
  @HealthCheck()
  ready() {
    return this.health.check([
      () => this.db.pingCheck('database', this.prisma).withTimeout(1000),
      () => this.redis.pingCheck('redis').withTimeout(1000),
    ])
  }
}

HealthCheckService.check 接一組函式，每個函式執行一項指標、回傳它的結果。live 傳空陣列，什麼都不查：請求能一路執行到這個 handler 並回應，本身就證明事件迴圈還在轉，這正是 liveness 要回答的。ready 傳兩項，結果是：

  • 全部 up：回 200，格式是 { status: 'ok', info, error, details }。
  • 任何一項 down：它丟 ServiceUnavailableException，也就是 503；details.database.status 這類欄位寫著 'down'，error 裡有原因。
  • @HealthCheck() 裝飾器另外加上 Cache-Control: no-cache，避免中間的代理把一分鐘前的「健康」快取起來。

資料庫的指標是內建的。PrismaHealthIndicator 的 pingCheck(key, prismaClient) 對資料庫跑一句 SELECT 1，它需要一個 Prisma client 來下這句查詢，所以要把注入的 PrismaService 傳給它。第一個參數 'database' 是這項在回應裡的名字，也就是 details.database 的 database。

Redis 沒有內建的指標，要自己寫。Terminus 12 的寫法是注入 HealthIndicatorService，用 check(key).attempt(fn)：fn 正常結束就是 up，丟錯就是 down：

@Injectable()
export class RedisHealthIndicator {
  constructor(private readonly indicator: HealthIndicatorService, private readonly redis: RedisService) {}

  pingCheck<const Key extends string>(key: Key) {
    return this.indicator.check(key).attempt(async () => {
      await this.redis.client.ping()   // 一定要真的問 Redis；什麼都不做的 attempt 永遠 up
    })
  }
}

fn 裡一定要真的碰到依賴。attempt(async () => {}) 永遠正常結束，指標永遠 up，Redis 掛了 readiness 也不會知道。網路上很多範例是 Terminus 11 以前的另一套寫法，在 12 照抄會編譯失敗，差異見課末「補充與查表」。

接著是上一節預告的陷阱：.withTimeout(1000) 為什麼是必要的。依賴壞掉有兩種樣子。一種是直接失敗，例如連線被拒絕，ping() 馬上丟錯，指標標 down，沒問題。另一種是卡住：連線還在，但 Redis 不回應，ping() 永遠不 resolve。沒有逾時的話，/health/ready 也跟著永遠不回應。平台等到它自己的逾時（例如 5 秒）就判定不健康、停掉流量，這部分結果是對的；但健康檢查本身卡住，你就看不到 details，分辨不出是資料庫壞還是 Redis 壞。加了逾時，1 秒後 Redis 那項標 down、整體 503，details 裡清楚寫著是 Redis，資料庫那項照樣顯示 up。

💡 實務上：readiness 只放「沒有它就完全不能服務」的依賴
健康檢查的路徑會填進部署平台或負載平衡器的設定裡，維運和你都會看它。咖啡店的資料庫壞了什麼都做不了，放進 readiness 合理；但寄信服務或第三方付款閘道掛了，如果也讓 readiness 失敗，所有程序同時被拔掉流量，連只是想看菜單的客人都進不來。這類外部服務交給錯誤處理、重試，或 Terminus 12 的 degraded 狀態（見課末）。另外，健康檢查端點不要被登入 guard 或限流擋住，平台的探測請求不會帶 token；details 會透露內部用了哪些元件，不必對外公開。

平台現在有辦法知道該不該把請求送給一個程序了。但王小明的付款不是被送錯程序，而是程序在處理它的途中被停掉。剩下的問題是：平台叫程序結束的那一刻，程序該怎麼反應。

收到 SIGTERM 之後：怎麼讓進行中的付款做完再走？

平台叫程序結束的方式是送一個訊號。訊號是作業系統送給程序的通知（Node 課第 21 課）。部署新版本、縮減機器數量、平台搬遷程序，都是同一個動作：先送 SIGTERM（「請你結束」），等一段寬限時間（Kubernetes 預設 30 秒，Docker 預設 10 秒），程序還沒結束就送 SIGKILL，這個訊號程序攔不住，會被直接終止。換句話說，平台給了你一段時間收拾，問題是程式有沒有利用這段時間。

Node 預設收到 SIGTERM 就立刻結束，正在處理的請求斷在半路。王小明的付款請求正好在 await this.payments.charge() 回來之後、prisma.order.update 之前：錢已經扣了，訂單還來不及改成 paid，收據工作也還沒排入，程序就沒了。平台給的 30 秒完全沒用到。

優雅關機（graceful shutdown）就是好好利用這段時間，依序做三件事：不再接新工作，把手上的做完，最後按依賴順序關閉資源。順序很重要：資料庫連線如果先關掉，手上的工作就沒辦法寫結果。

第一步是讓 Nest 接手這個訊號。Nest 的關機流程是 app.close()，但 SIGTERM 預設不會觸發它。要在 main.ts 加一行：

app.enableShutdownHooks()   // 收到 SIGTERM、SIGINT 等訊號時呼叫 app.close()，跑完 hook 才結束程序

不要自己寫 process.on('SIGTERM', () => process.exit(0))，這是反效果：process.exit 立刻結束程序，跟 Node 的預設行為一樣把請求切斷，還多寫了一段程式。也不要在任何 hook 裡呼叫 process.exit。hook 都跑完、沒有東西佔著事件迴圈時，Node 會自己結束；如果結束不了，表示有連線或計時器沒關，那是要找出來修的問題，不是用 exit 蓋掉的問題。

開啟之後，收到 SIGTERM 時 app.close() 會依序呼叫第 4 課的三個關機 hook，每個階段都等前一個階段的所有 provider 做完才往下走，中間還有一步是 Nest 自己關閉 HTTP 伺服器。優雅關機的三件事，就是分配到這幾個階段裡做：

順序階段適合做什麼
1onModuleDestroy()停止接新工作：關排程、停止拉新 job
2beforeApplicationShutdown(signal)等進行中的工作做完：await worker.close()
—關閉 HTTP 伺服器Nest 自己做：不再接新連線，等進行中的請求回應完
3onApplicationShutdown(signal)最後才斷連線：Prisma $disconnect()、Redis quit()

表格看起來理所當然，但練習專案裡有兩個資源，照目前的寫法都會在關機時出事，這正是順序要講究的原因。

第一個是 BullMQ 的 worker（第 20 課），也就是在背景寄收據的那一個。@nestjs/bullmq 會在 onApplicationShutdown 關閉 worker，但 PrismaService 的 $disconnect 也在那個階段，同一個階段裡誰先誰後取決於模組階層，你不能依賴它。正在寄的收據寄完之後要寫 receiptSentAt，如果 Prisma 已經斷線就寫不進去，收據寄了、紀錄卻沒寫，之後可能重寄。所以自己提早一個階段關：在 beforeApplicationShutdown 裡 await this.worker.close()。close() 會停止拿新工作，等手上的工作做完才 resolve；一定要 await 它，不 await 的話關機流程不會等，直接往下走。

第二個是 Prisma。很多範例把 $disconnect 寫在 onModuleDestroy，看起來「模組銷毀時斷線」很合理，但那是第一個階段，HTTP 請求還在處理。王小明那種付款請求接著執行 prisma.order.update，Prisma 發現已經斷線，會自動重新連線，於是關機流程留下一個沒有人會再關的連線池，程序因此結束不了，等到寬限時間用完被 SIGKILL。放到 onApplicationShutdown，那時 HTTP 已經關了、worker 也關了，不會再有人查資料庫。

圖的下半部是程序之外、要跟平台配合的兩件事。第一件接上健康檢查那一節：關機期間 readiness 要回 503。Terminus 的 HealthCheckService 在 app.close() 開始後會回 status: 'shutting_down' 與 503，不用你自己寫；負載平衡器看到就不再送新請求過來，程序剩下要處理的只有進行中的那些。第二件是整段流程要比平台的寬限時間短。worker 手上一個要 1 秒的工作沒問題，一個要 5 分鐘的報表就會被 SIGKILL 切斷；這種工作要設計成能被中斷、重跑時能從中斷的地方續做，第 21 課對帳工作的檢查點就是為了這個。

把這些放回兩點整的那次部署：平台送 SIGTERM 給舊程序，readiness 改回 503，新的付款請求都送到新版本；王小明那個已經在處理的付款請求繼續跑完，扣款回來、訂單改成 paid、收據工作排入，回 200 給他的 App；worker 把手上那封收據寄完、寫好 receiptSentAt；最後 Prisma 和 Redis 斷線，程序自己結束。整段在寬限時間內完成，客服那則訊息就不會出現。

💡 實務上：每次部署都在考驗你的關機流程
如果團隊發現「每次部署都有幾個請求失敗」「部署後偶爾有收據重寄或沒寄」，第一個要查的就是優雅關機，王小明的客訴就是這種症狀。上線前的檢查清單：enableShutdownHooks 有沒有開、平台的關機時限和最長的工作哪個長、在本機用 kill -TERM <pid> 實際送一次訊號，看 log 是不是照順序把事情做完才結束。再小心也擋不住機器斷電或 SIGKILL，所以 job 和付款流程本身還是要能安全重跑；優雅關機減少意外，不是保證不出意外。

練習

在 learn/ 執行 node check.mjs nestjs 24 建立 work/24/。這一題同時用到 PostgreSQL 和 Redis，先確認容器在跑（在 learn/nestjs/practice 執行 docker compose up -d --wait，第 12 課）。專案是第 20 課的咖啡店 API，已經有：

  • POST /orders 建訂單、POST /orders/:id/pay 付款：先呼叫 PaymentGateway.charge（模擬外部付款服務，要 1 秒），再改成 paid、排入收據工作。OrdersService、ReceiptsProducer 都已經用 new Logger(…) 記 log，訊息固定、值在第二個參數的物件裡。
  • LoggingModule（@Global）：RequestContext 與 AppLogger 的骨架，configureApp 已經 app.useLogger(app.get(AppLogger))，main.ts 已經 bufferLogs: true。
  • RequestIdMiddleware：驗證或產生 requestId、設定 X-Request-Id 回應標頭，已套用到所有路由。
  • RedisService：應用程式自己的 ioredis 連線，this.redis.client 可以下指令。ReceiptsProcessor：第 20 課的 worker，Mailer 寄一封要 1 秒。

想親手看：在 work/24 執行 npx prisma migrate dev、npm run start:dev，用 curl -i -X POST localhost:3100/orders -H 'content-type: application/json' -d '{"customerId":1,"total":190}' 看回應標頭的 X-Request-Id 和終端機裡帶同一個 id 的 JSON log；做完練習 3 後，付款途中按 Ctrl+C（送 SIGINT），看請求照樣回 200、程序才結束。

練習 1：讓同一個請求的每一行 log 都帶同一個 requestId。

  • RequestContext：用 AsyncLocalStorage 實作 run(requestId, fn) 與 requestId getter。run 裡面（包含 await 之後）讀到這次的 id，外面讀到 undefined。
  • RequestIdMiddleware：注入 RequestContext，讓請求接下來的處理都在情境裡執行。
  • AppLogger：覆寫 getJsonLogObject，每一行 JSON 的最上層多一個 requestId；請求以外的 log 不帶這個欄位。
  • OrdersService、ReceiptsProducer 不改，而且要維持 singleton。

判分：攔下 stdout，檢查「訂單建立」「付款完成」「收據工作已排入」每一行的 requestId 等於該請求的 X-Request-Id，orderId、total 留在 params；6 個請求同時進來、各自付款，每一行都帶自己的 id；new Logger('Startup').log(…) 沒有 requestId；app.get(OrdersService) 不會丟錯。用參數傳、模組變數、request scope 的 logger 都過不了。

練習 2：用 @nestjs/terminus 12 提供 GET /health/live 與 GET /health/ready。

  • HealthModule 匯入 TerminusModule，登記 RedisHealthIndicator。
  • live：this.health.check([])，不查任何依賴。
  • ready：PrismaHealthIndicator.pingCheck('database', this.prisma) 與 RedisHealthIndicator.pingCheck('redis')，兩項都 .withTimeout(1000)。
  • RedisHealthIndicator：注入 HealthIndicatorService 與 RedisService，用 check(key).attempt(…) 真的對 Redis ping()。

判分：正常時兩個端點都 200，details.database、details.redis 都是 up；把 Prisma 的查詢換成失敗 → ready 503、database down、redis 仍 up、live 仍 200；把 ping() 換成永遠不回應 → ready 在 1 秒左右回 503、redis down，live 不受影響。

練習 3：優雅關機。進行中的請求與工作做完，worker 先關，資料庫最後才斷線。

  • main.ts：app.enableShutdownHooks()。不要自己監聽 SIGTERM 呼叫 process.exit。
  • ReceiptsProcessor：在 beforeApplicationShutdown 裡 await this.worker.close()。
  • PrismaService：$disconnect() 從 onModuleDestroy 搬到 onApplicationShutdown。

判分：worker 正在寄一封要 1 秒的收據、同時有一個要 1 秒的付款請求進行中，這時 app.close()：請求要回 200、訂單 paid、收據的 receiptSentAt 有值；記錄每一步的順序，worker.close 要在 HTTP 關閉前結束、$disconnect 要在 HTTP 關閉後才開始；關機後 pg_stat_activity 裡不能剩下這個資料庫的連線。最後 nest build、啟動 dist/main.js，付款途中送 SIGTERM：請求要回 200，程序在 15 秒內結束。

練習 4：同事把 /health/live 改成也檢查資料庫，理由是「多檢查一項更安全」。哪個說法正確？

✓ c。liveness 失敗的後果是「重啟程序」，只有重啟能修好的狀況（事件迴圈卡死）才該讓它失敗。資料庫斷線重啟程序沒有用，正確的反應是 readiness 回 503、暫停送流量。a 把兩個問題混在一起。b 的逾時只是讓它失敗得快一點，後果一樣。d 錯：check 可以傳任何指標，問題在不該傳。

練習 5：為什麼 RequestContext 用 AsyncLocalStorage，而不是把 logger 設成 Scope.REQUEST 然後 @Inject(REQUEST) 讀 req.requestId？後者看起來更「Nest」。

✓ b。request scope 會沿著注入鏈往上傳染，代價是效能和可用性（app.get 失效、排程與 worker 裡沒有請求可以注入）。a 錯：request scope 還在，只是要知道代價。c 不是原因。d 錯：差別正是在 singleton 與否。

練習 6：PrismaService 在 onModuleDestroy 裡 $disconnect()，關機時平台等了 30 秒還是把程序 SIGKILL。最可能的原因是？

✓ d。斷線太早不會讓請求失敗（Prisma 會重連），而是讓程序卡著結束不了，這種「沒有錯誤訊息的卡住」最難查。a 如果成立，hook 完全不跑，程序會立刻結束而不是卡 30 秒。b 錯：斷線是毫秒級的事。c 錯：'exit' 事件裡不能做非同步的事，而且 Nest 的 hook 就是為此設計的。

常見錯誤

  • 把值拼進訊息字串：`訂單 ${id} 建立` 搜不到、也沒辦法用欄位篩選。訊息固定，值放第二個參數的物件裡，它會進 params。
  • 第二個參數傳字串：logger.log('付款完成', orderId) 的字串會被當成 context，不是資料。要傳物件。
  • 忘了 bufferLogs：啟動初期的 log 用預設的彩色格式印，上線後 log 收集工具只有這幾行解析失敗。NestFactory.create(AppModule, { bufferLogs: true })。
  • 相信外面送來的 X-Request-Id：含換行的值可以偽造出假的 log 行，超長的值塞爆 log。先用正規表示式驗證，不合格就自己產生。
  • run 只包了空的 callback，next() 在外面呼叫：情境在 callback 結束時就結束，整個請求讀到 undefined。把 next 本身交給 run。
  • 用模組層級的變數存「目前的 requestId」：第二個請求進來就蓋掉第一個的。單一執行緒不代表沒有並發。
  • request scope 的 logger：整條注入鏈變成 request scope，app.get 失效、效能變差。用 AsyncLocalStorage。
  • liveness 查資料庫：資料庫一晃，全部程序一起重啟。live 什麼都不查，依賴交給 ready。
  • 健康指標沒有逾時：一個卡住的依賴讓整個健康檢查卡住。每項 .withTimeout()。
  • 照抄 Terminus 11 的範例：extends HealthIndicator、HealthCheckError 在 12 已經移除。用 HealthIndicatorService 的 check(key).attempt(fn)。
  • 指標沒有真的碰依賴：attempt(async () => {}) 永遠 up。要 ping()、SELECT 1。
  • 沒有 enableShutdownHooks：SIGTERM 來了 Nest 直接結束，三個關機 hook 一個都不會跑。本機 Ctrl+C 看起來正常，上線才出事。
  • 自己 process.on('SIGTERM', () => process.exit())：立刻結束，進行中的請求被切斷。交給 Nest。
  • $disconnect 放在 onModuleDestroy：HTTP 還在跑，Prisma 自動重連留下連線池，程序結束不了被 SIGKILL。放到 onApplicationShutdown。
  • 關 worker 沒有 await：關機流程不等手上的工作做完就往下走，資料庫斷線後工作才寫結果。await this.worker.close()。
  • 關機流程比平台時限長：一個要跑 5 分鐘的 job 擋在 worker.close()，30 秒後被 SIGKILL。長工作要能被中斷、能續做。

補充與查表

主線用不到、但遇到時要知道的細節。

  • 課程驗證的版本：練習專案用 @nestjs/core 12.3.2、@nestjs/terminus 12.1.0、@nestjs/bullmq 12.0.0。
  • Terminus 11 以前的自訂指標寫法：網路上大量範例是 extends HealthIndicator、用 this.getStatus(key, true) 回報結果、失敗時丟 HealthCheckError。這兩個類別在 12 已經移除，照抄會編譯失敗。12 的寫法是本課的 HealthIndicatorService 加 check(key).attempt(fn)。
  • attempt 的取消訊號：attempt 的 callback 會收到 { signal }（AbortSignal，Node 課第 8 課），.withTimeout() 逾時時會被 abort，支援 signal 的呼叫（例如 fetch）可以順手取消，不會在背景繼續等。
  • degraded 狀態：Terminus 12 多了這個狀態，代表還在服務、但有損（例如快取失效只能查資料庫）。整體狀態變成 'degraded'，HTTP 仍是 200，流量照送，但監控看得到。這一課的練習不用它。

小結

  • 上線後只剩 log 看得到，而 log 的讀者是搜尋工具：ConsoleLogger({ json: true }) 一行一個 JSON，訊息固定、值放第二個參數的物件裡進 params；app.useLogger 換上自己的 AppLogger，bufferLogs: true 讓啟動的 log 也走它。
  • 同一張訂單有好幾次請求，要靠 requestId 分開：middleware 驗證或產生、回 X-Request-Id。參數傳會漏、模組變數會被交錯的請求蓋掉、request scope 會讓整條注入鏈每個請求重建。
  • AsyncLocalStorage 的 store 跟著非同步流程走：包成 singleton 的 RequestContext，middleware 把 next 交給 run，AppLogger 覆寫 getJsonLogObject 自動帶上，業務程式一行不改。
  • 健康檢查回答兩個問題：liveness 什麼都不查，失敗代表要重啟；readiness 查依賴，失敗代表先別送流量。判斷標準是「重啟修得好嗎」。Terminus 12：HealthCheckService.check、內建 PrismaHealthIndicator、自訂指標用 HealthIndicatorService.check(key).attempt(fn)，每項 .withTimeout()。
  • 部署會送 SIGTERM、給一段寬限時間再 SIGKILL。app.enableShutdownHooks() 讓 SIGTERM 走 app.close()：onModuleDestroy 停接新工作 → beforeApplicationShutdown 等 worker 做完 → Nest 關 HTTP → onApplicationShutdown 才斷 Prisma、Redis。不要 process.exit，流程要比平台時限短。王小明那種「款扣了、訂單沒變」就是這條流程沒做好的結果。

服務活著、也能好好關掉了，下一課處理「它活著但不對」的時候怎麼辦：從 Nest 的錯誤訊息找出循環 import 與 scope 問題，再用事件迴圈的角度看為什麼一個報表會讓所有請求變慢。
