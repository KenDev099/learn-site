階段 2：請求管線與測試 · 第 11 課

設定管理：環境變數、驗證與 secret

咖啡店 API 準備第一次上線。在這之前，同一份程式要跑在三個地方：你的筆電、測試環境、正式環境。打開這課的起始專案 work/11：它是上一課的咖啡店 API 精簡版，其中金流從第 10 課的 PaymentGateway provider 改成 PaymentModule，做法跟第 4 課的 ReceiptModule 一樣，用 register() 帶設定。專案裡有三個值是直接寫死在程式裡的：

  • configureApp 裡允許的 CORS 來源只有 http://localhost:5173，正式站的前端網域打不進來。
  • PaymentModule.register({ apiKey: 'dev-key', … }) 的金流金鑰和網址，本機要用沙盒，正式環境要用真的。
  • 一張訂單最多幾杯、集點功能開不開，店長說測試環境想調小一點試試看。

這些值在每個環境都不一樣，程式碼卻必須是同一份。業界的做法是把它們放在環境變數，由執行程式的環境提供。但只是「改成讀環境變數」還不夠：環境變數全是字串、可能少設一個、可能拼錯，而且金流金鑰是不能外流的密碼。這一課的任務是：把這三組寫死的值搬到環境變數，並且讓上線那天任何一個設定錯了，都在部署當下被擋下，而不是等到半夜第一筆付款才出事。工具是專案裡的 @nestjs/config 12 和 zod 4。

這課的路線：
  1. 直接把值改成讀 process.env 會怎樣：拼錯、漏設、型別不對各自在什麼時候、以什麼樣子出錯。
  2. 怎麼讓設定錯了就不啟動：ConfigModule.forRoot 加 zod schema，啟動時一次驗證全部變數（開場問題的最小答案）；接著把 "false"、"8080"、逗號分隔的網域清單轉成正確的型別。
  3. 值到底從哪裡來：.env 和平台設定的變數誰優先、什麼時候載入，為什麼模組檔案最上層讀到的是 undefined。
  4. 程式怎麼拿到驗證過的值：OrdersService 注入有型別、測試換得掉的設定；PaymentModule 用 registerAsync 從設定建立。
  5. 真正的金流金鑰放在哪裡：secret 怎麼保管，日常工作裡最常從哪裡外流。
這課會用到：
  • Node 課第 2 課的環境變數與 .env：程序從 process.env 讀「名稱＝值」字串，.env 檔是本機提供這些值的方式；設定要在啟動時就驗證。
  • TypeScript 課第 26 課的 zod：用 schema 驗證外部資料，z.coerce.number() 先轉型再檢查，transform 把驗證過的值再加工（第 7 課也用它驗證請求）。
  • 第 3 課的自訂 provider：不是 class 的東西用 @Inject(token) 注入；useFactory 用函式產生值，inject 列出這個函式需要的 provider。

直接改成讀 process.env，哪裡會出事？

先把「環境變數」講清楚。作業系統啟動一個程序時，會交給它一組「名稱＝值」的字串，例如 PORT=3100、DATABASE_URL=postgres://…，這組字串就是環境變數（environment variable）。Node 把它們放在 process.env 這個物件上，名稱是 key、值一律是字串。同一個程式，在你的終端機啟動和在部署平台啟動，拿到的環境變數可以完全不同，程式碼一行都不用改。

這正是「設定和程式分開」想要的效果。雲端應用有一份廣為採用的原則叫 12-factor，其中一條就是：會隨環境改變的設定不寫在程式裡，由環境提供。這樣同一份打包好的程式（下一課會學到，它叫映像，image）可以原封不動部署到測試環境和正式環境，兩邊只差在注入的環境變數。

原則沒問題，問題在「怎麼讀」。最直覺的做法是哪裡需要就在哪裡讀 process.env。咖啡店的程式改完之後，常常長這樣：

// orders.service.ts
const max = process.env.ORDER_MAX_ITME ?? 20          // 拼錯：永遠是 20，沒有任何錯誤
if (items.length > max) …                             // max 可能是字串 '20'

// payment.client.ts
const key = process.env.PAYMENT_API_KEY               // 正式環境忘了設：第一筆付款時才爆
const stamps = process.env.FEATURE_STAMPS === 'ture'  // 又一個拼錯

這四行每一行都能編譯、本機也都能跑，但各自埋了一顆會在不同時間爆的雷：

  • 拼錯變成 undefined：TypeScript 不檢查 process.env 上的名稱，ORDER_MAX_ITME 拼錯只會默默拿到 undefined，再被 ?? 蓋成 20。你在正式環境把上限設成 5，程式照樣用 20，沒有任何錯誤訊息告訴你。
  • 漏設要等到用到才發現：正式環境忘了設 PAYMENT_API_KEY，程式照樣啟動、部署顯示成功。直到第一位顧客結帳，金流商回「金鑰無效」，那筆付款已經失敗了。
  • 全是字串：'20'、'false' 都是字串。每個用的地方各自轉型，各自轉錯：有人記得 Number()、有人忘了；'false' 放進 if 卻是 true。
  • 散落各處、測試難替換：沒有一個地方說得出「這個應用需要哪些變數」，新同事不知道該設什麼。要測「上限是 2 杯」，只能去改全域的 process.env，一個測試改了會影響下一個。

四個問題對應到三件要做的事：用一個 schema 列出應用需要的全部變數；在啟動時依 schema 驗證並轉型，有錯就不啟動；其他程式透過 DI 拿驗證過的值，不再自己讀 process.env。第一件和第二件，正是 @nestjs/config 的 ConfigModule 要做的事。

怎麼讓設定錯了，應用就不啟動？

上一節的漏設和拼錯，共同的問題是「出錯的時間點太晚」。要把時間點提前到啟動那一刻，需要兩樣東西：一份寫明每個變數長什麼樣子的 schema，和一個在啟動時拿 schema 去檢查的人。

schema 用 zod 寫，跟第 7 課驗證請求 body 一樣，只是這次被驗證的是 process.env 這個物件。檢查的人是 @nestjs/config 的 ConfigModule.forRoot()：它在 app.module.ts 載入、@Module 執行時被呼叫，讀進 .env 檔、合併系統的環境變數，再用你交給它的 validationSchema 驗證；驗證通過後，才把值寫回 process.env（這個時間差，在後面「值到底從哪裡來」那一節會造成一個陷阱）。12 版的 validationSchema 直接接受 zod schema（哪些驗證套件可以用，見課末）。

先不碰開場那三組，用每個應用都有的三個變數示範：NODE_ENV 是現在跑在哪個環境，PORT 是聽哪個 port，DATABASE_URL 是資料庫網址，下一課接資料庫時就會用到。DATABASE_URL 沒設，應用完全不能運作，拿它示範「漏設」最清楚。開場那三組留到下一節轉型時再加進來。先只放這三個變數，看它擋下錯誤時長什麼樣子：

這段輸出就是開場問題的最小答案：少了 DATABASE_URL、PORT 寫成 abc，應用根本不會開始接請求，錯誤訊息直接寫出是哪個變數、錯在哪。讀這段輸出時注意三件事：

  • 停在啟動，而不是停在某個請求：這叫 fail fast（快速失敗），設定有錯就在最早的時間點停下。多數部署平台看到新版本起不來，會保留舊版本繼續服務，你在部署當下就知道出了什麼事，顧客完全不受影響。對照上一節「第一筆付款時才爆」，差別就在這裡。
  • 所有錯誤一次列出：zod 會把每個欄位都檢查完，一行一個變數。不會改完 PORT 重啟，才看到下一個 DATABASE_URL 的錯。
  • 值已經轉型：PORT 用的是 z.coerce.number()，它先做 Number(值) 再驗證，所以 'abc' 變成 NaN 被擋下；驗證通過時，拿到的是 number 而不是字串。

forRoot 的另一個參數 isGlobal: true 是讓 ConfigModule 變成全域模組。第 4 課說過，每個模組都需要的基礎設施適合設成全域；設定正是這種東西，設成全域後，OrdersModule、PaymentModule 不用各自 import ConfigModule，就能注入它提供的 ConfigService。

還有一個問題：驗證寫在 AppModule 裡，而不是 main.ts，差在哪？差在入口。上一課的 e2e 測試不執行 main.ts，而是用 Test.createTestingModule 自己建立 AppModule；之後的 CLI 指令也是。驗證跟著 AppModule 走，不管從哪個入口建立應用，都會經過同一道檢查；寫在 main.ts 只保護了一個入口。（驗證實際在什麼時間點執行，見課末。）

💡 實務上：新增一個變數，要改的不只程式碼
咖啡店要接新的金流商，加了 PAYMENT_WEBHOOK_SECRET。同一個 PR 裡要一起改：schema、.env.example，並在 PR 說明寫「上線前要先在平台設定這個變數」。順序很重要：先在測試與正式環境設好值，再部署新版本，否則 fail fast 會讓新版本起不來（這正是它該做的事，但會卡住這次上線）。資深工程師 review 這種 PR 會先問：「正式環境由誰、在哪裡設這個值？沒設的話會怎樣？」

環境變數全是字串，"false" 和 "a, b" 要怎麼轉？

上一節的 PORT 用 z.coerce.number() 就轉成了數字。但開場那三組值裡還有布林（集點開關 FEATURE_STAMPS）、清單（CORS 來源 CORS_ORIGINS），每一種從字串轉過去都有自己的陷阱，而且陷阱的共同點是：不報錯，只是值不對。

先看最容易中的布林。zod 有 z.coerce.boolean()，名字看起來剛好，但它做的是 JavaScript 的 Boolean(值)：任何非空字串都是 true，包括 'false'。.env 寫 FEATURE_STAMPS=false，拿到的是 true，集點功能關不掉，也沒有任何錯誤。環境變數的布林要用 z.stringbool()，它認得 'true'／'false'、'1'／'0' 這些寫法，其他值直接報錯。下面用一樣的規則示範兩者的差別，也示範清單的陷阱：

執行後看三件事：coerce.boolean("false") 是 true；stringbool("ture") 拼錯會報錯，而不是默默當成 false；沒有 trim() 時，清單第二項開頭多了一個空白。

那個空白在 CORS 會變成正式環境才看得到的事故。CORS 比對的是瀏覽器送來的 Origin 標頭，必須一字不差。' https://shop.example.com' 多一個空白就永遠不相符，正式站的前端會看到 CORS 錯誤，而你在本機（只設一個來源）完全重現不了。

數字也有兩個不報錯的陷阱。Number('') 是 0：.env 寫了 PORT= 卻沒給值，會得到 0，所以要加 .positive() 或 .min(1) 把範圍寫出來。另外，空字串也算「有設定」：.env 寫了 PAYMENT_BASE_URL= 卻沒給值，.default() 不會套用（預設值只補 undefined），會得到 Invalid URL。

把四種型別的寫法和陷阱整理成一張表，寫 schema 時查表用：

想要的型別寫法陷阱
數字z.coerce.number().int().min(1).max(50)'' 變 0、'2.5' 是小數；範圍要寫出來
布林z.stringbool()z.coerce.boolean() 用 Boolean(值)，'false' 是非空字串 → true
清單z.string().transform(v => v.split(',').map(s => s.trim()).filter(Boolean))沒有 trim() 時，'a, b' 的第二項是 ' b'
固定幾種值z.enum(['development', 'test', 'production'])寫 prod 會直接報錯，而不是被當成「不是 production」

剩下金流金鑰。它的規則不是單一欄位能表達的：本機和測試環境用沙盒，可以不設；只有 production 必須有。這種「看別的欄位決定這個欄位」的規則，要寫在整個物件上。zod 的 refine 就是做這件事：你給它一個函式，函式收到整個驗證過的物件，回傳假值就算驗證失敗。做法是欄位本身寫成 .optional()，再在物件上加 refine，並用 path 指出錯誤屬於哪個變數，錯誤訊息才會寫出它的名字：

export const envSchema = z.object({
  …,
  PAYMENT_API_KEY: z.string().min(1).optional(),
}).refine(env => env.NODE_ENV !== 'production' || env.PAYMENT_API_KEY, {
  path: ['PAYMENT_API_KEY'],
  message: 'production 環境必須設定',
})

export type Env = z.output<typeof envSchema>   // 轉型之後的型別：PORT 是 number、CORS_ORIGINS 是 string[]

最後一行從 schema 推出型別 Env。z.output 取的是「驗證並轉型之後」的型別，所以 PORT 是 number、CORS_ORIGINS 是 string[]，不是原本的字串。後面讀設定時，靠的就是這個型別。

做練習 1 時會遇到一個現象：實測 zod 4.6.7，某些欄位本身就沒過（例如 FEATURE_STAMPS=ture）時，物件層級的 refine 不會執行，修好那些錯誤後才會看到 PAYMENT_API_KEY 的錯誤。這是正常的：refine 要拿到一個欄位都合格的物件才有意義。

schema 寫完了，但它驗證的那些值是從哪裡來的？本機有 .env，部署平台會注入環境變數，你也可能在終端機臨時寫 PORT=4000。三個來源同時存在時聽誰的，下一節回答。

值到底從哪裡來？.env 和平台設定衝突時聽誰的

ConfigModule.forRoot() 拿到的值有兩個來源：專案資料夾裡的 .env 檔，和程序啟動時就有的系統環境變數（你在終端機 export 的、寫在指令前面的、部署平台注入的都算）。下圖是它從讀值到交出結果的流程：

圖上有三件事會直接影響你的除錯：

  • 衝突時系統環境變數贏：同一個變數同時出現在 .env 和系統環境變數時，用系統的。.env 寫 PORT=3100，終端機執行 PORT=4000 npm run start:dev，拿到 4000。這是刻意的設計：正式環境由平台注入的值，不會被某個意外打包進映像的 .env 蓋掉；你在本機也能用一行指令臨時換掉某個值。forRoot({ override: true }) 會反過來讓 .env 贏，一般不要用。
  • .env 從目前工作目錄找：預設讀的是目前工作目錄（process.cwd()，也就是你下指令時所在的資料夾）的 .env，不是 app.module.ts 所在的資料夾。在別的資料夾執行 node work/11/dist/main.js 就讀不到，所有值都會變成預設值或驗證失敗。需要時用 envFilePath 指定路徑。
  • 驗證後寫回 process.env：驗證通過後，.env 的值和 schema 的預設值會補進 process.env（已經存在的變數不動）。所以 main.ts 裡的 app.listen(process.env.PORT ?? 3100) 讀得到 .env 的 PORT。

第三點有一個前提：「驗證通過後」。在那之前讀 process.env，.env 的值還不在裡面。這個時間差會造成一個很難察覺的 bug。

ES module 的執行順序是：先執行被 import 的檔案，再執行 import 它的檔案。app.module.ts import 了 orders.service.ts，所以 orders.service.ts 最上層的這一行：

const max = Number(process.env.ORDER_MAX_ITEMS ?? 20)

會在 app.module.ts 的 @Module 執行、ConfigModule.forRoot() 載入 .env 之前就跑完。結果是：本機用 .env 設的 ORDER_MAX_ITEMS 完全不生效，程式一直用 20，你卻以為生效了；到了正式環境，值由平台注入、程序一啟動就在 process.env 裡，又剛好正常。這種「本機錯、正式對」的 bug 最難查。

規則：讀設定一律放在函式裡（下一節的 registerAs 工廠、useFactory、建構子），讓它在 Nest 建立 provider 時才執行。那時驗證已經完成，值也都轉好型別了。

這條規則引出下一個問題：放在函式裡讀，難道還是在函式裡寫 process.env.ORDER_MAX_ITEMS？那拼錯、字串、測試難換的問題都還在。OrdersService 需要的是一個從驗證結果拿值、有型別、測試換得掉的方式。

OrdersService 怎麼拿到有型別、測試換得掉的設定？

驗證通過的值存在 ConfigService 裡，它是 ConfigModule 提供的 provider，任何 class 都能在建構子注入。要讓 TypeScript 檢查你讀的名稱和型別，給它兩個型別參數。第一個是上一節的 Env，告訴它有哪些變數；第二個 true 告訴它「已經驗證過，值一定存在」，回傳型別就不會帶 undefined。讀值時再加上 { infer: true }，回傳型別就從 Env 推出來：

constructor(private readonly config: ConfigService<Env, true>) {}

const port = this.config.get('PORT', { infer: true })                 // number
const origins = this.config.get('CORS_ORIGINS', { infer: true })      // string[]
this.config.get('PROT', { infer: true })                              // 型別錯誤：拼錯會被抓到
this.config.getOrThrow('PAYMENT_API_KEY')                             // 沒有值就丟錯，而不是回 undefined

第一節的拼錯問題在這裡解決了：'PROT' 不是 Env 的 key，編譯就過不了。但如果 OrdersService 直接注入 ConfigService，它就依賴了「全部的設定」：它其實只需要一個 maxItems，測試卻得準備一個完整的 ConfigService。

所以功能程式用另一種方式：設定命名空間。registerAs('orders', 工廠函式) 把一個功能需要的幾個值包成一組，名字叫 orders；這一組有自己的注入 token，service 只注入這一組，依賴範圍跟它真正用到的一樣小。寫法分三個檔案：

// src/config/orders.config.ts
export const ordersConfig = registerAs('orders', () => ({
  maxItems: Number(process.env.ORDER_MAX_ITEMS),   // 工廠在驗證之後才執行，這裡讀得到值與預設值
}))

// src/orders/orders.module.ts
@Module({ imports: [ConfigModule.forFeature(ordersConfig)], … })

// src/orders/orders.service.ts
constructor(@Inject(ordersConfig.KEY) private readonly config: ConfigType<typeof ordersConfig>) {}
//          this.config.maxItems 的型別是 number

逐段看它怎麼運作：

  • 工廠函式：registerAs 的第二個參數是一個函式，不是物件。Nest 在驗證完成之後才呼叫它，所以這裡讀 process.env 拿得到 .env 的值和 schema 的預設值，避開了上一節的載入時機陷阱。
  • 登記到模組：ConfigModule.forFeature(ordersConfig) 把這一組設定登記成 OrdersModule 裡的 provider，OrdersService 才注入得到。
  • 注入 token 與型別：registerAs 回傳的函式多了一個 KEY 屬性，就是這一組的注入 token，用第 3 課的 @Inject(token) 注入。ConfigType<typeof ordersConfig> 取出工廠回傳值的型別，不用另外寫 interface。

這樣做之後，process.env 只出現在 src/config/ 底下：要回答「這個應用讀了哪些變數」，看這個資料夾就夠了。測試也不用再碰全域的 process.env：用第 5 課 Testing Module 的手法，overrideProvider(ordersConfig.KEY).useValue({ maxItems: 2 })，就能測「上限是 2 杯」，測試之間互不影響。第一節的四個問題，到這裡全部有了答案。

兩種讀法的分工：ConfigService.get 適合在基礎設施的地方讀一兩個值，例如 main.ts、第 10 課的 configureApp（開場寫死的 CORS 來源就在這裡改成讀 CORS_ORIGINS）、useFactory；功能程式（service）注入自己的命名空間，依賴範圍更小，測試只要準備那一小組值。

💡 實務上：不是每個設定都適合放環境變數
環境變數改了要重啟或重新部署才生效，適合「每個環境不同、很少改」的值：資料庫連線、外部服務網址、金鑰、CORS 來源。店長想自己調的東西，例如營業時間、每單杯數上限、促銷開關，通常會改放資料庫加上後台頁面，不然每次調整都要找工程師部署。判斷時問一句：「誰會改它？多久改一次？」答案是 PM 或店長、每週都改，就不該是環境變數。

PaymentModule 的金鑰，怎麼從設定傳進去？

開場三組寫死的值，CORS 來源和杯數上限都處理完了，剩下 PaymentModule.register({ apiKey: 'dev-key', … })。這個 register 跟第 4 課的 ReceiptModule 一樣，是用 ConfigurableModuleBuilder 做出來的，參數是一個寫死的物件。

最直覺的改法是把物件裡的值換成 process.env.PAYMENT_API_KEY，但這會踩到前一節講的載入時機：@Module({ imports: [PaymentModule.register(…)] }) 的參數，在 app.module.ts 這個檔案載入時就算好了。那時 ConfigModule 還沒驗證，.env 的值和 schema 的預設值都還沒寫進 process.env，拿到的是原始字串或 undefined。也沒辦法改用 ConfigService，因為那個時間點它還不存在。

需要的是「先說好怎麼算 options，等 Nest 建立模組時再算」。這就是 registerAsync：你不給 options 物件，而是給一個 useFactory 函式和它需要的 provider（inject）。Nest 建立 PaymentModule 時，先準備好 inject 列出的 ConfigService，再把它傳進 useFactory，用回傳值當 options。這跟第 3 課的 useFactory 是同一個機制：

PaymentModule.registerAsync({
  inject: [ConfigService],          // isGlobal 的 ConfigModule，不用再寫 imports
  useFactory: (config: ConfigService<Env, true>) => ({
    apiKey: config.get('PAYMENT_API_KEY', { infer: true }),
    baseUrl: config.get('PAYMENT_BASE_URL', { infer: true }),
  }),
})

本機沒設金鑰時，apiKey 就是 undefined，這是對的：schema 只在 production 要求金鑰，不需要在這裡補一把假的。baseUrl 的預設值也只寫在 schema 一個地方。後面的課接資料庫、Redis、JWT，都是這個「registerAsync 配 inject: [ConfigService]」的模式。如果已經有一個 registerAs 的命名空間剛好就是模組要的 options，還有更短的寫法，見課末。

到這裡，開場三組寫死的值全部搬到了環境變數，而且錯了就不啟動。但最後這一組有一個不同：PAYMENT_API_KEY 的真值是能直接扣款的金鑰。它要放在哪裡，誰看得到？

真正的金流金鑰要放在哪裡？

資料庫密碼、API 金鑰、簽 JWT 的金鑰這類值叫 secret（機密設定）。它跟 PORT 這種設定的差別在於：外流就等於把鑰匙交給別人。別人拿到金流金鑰，就能用咖啡店的身分呼叫金流商的 API。管理原則依「值從開發到上線經過的地方」排列：

  • .env 不進 git：.env 寫進 .gitignore。git 會永遠記得歷史，commit 過一次，之後刪掉也還在。萬一 commit 了，唯一正確的處理是到服務商那邊撤銷並換一把新的金鑰，改寫 git 歷史不夠。
  • 提供 .env.example：列出需要哪些變數、但只有假值或空值的範本，可以 commit。新同事複製成 .env 就能啟動，也解決了第一節「不知道該設什麼」的問題。練習資料夾的 prepare.mjs 就是這樣幫你建立 work/11/.env。
  • 本機只放假值：本機用金流的沙盒（sandbox，金流商提供的測試環境，不會真的扣款）或根本不設金鑰；這也是 PAYMENT_API_KEY 只在 production 必填的原因。
  • 正式環境由平台注入：部署平台的 secret 管理功能把值設成環境變數，不經過檔案、不進映像。上一節的優先順序保證它不會被 .env 蓋掉。細節在 DevOps 課第 11 課。
  • 不要把設定印進 log：console.log(process.env) 或 logger.log(config) 會把所有金鑰寫進 log 系統，看得到 log 的人都拿得到。要確認設定，只印「有沒有」（例如 有 API 金鑰）或遮罩後的值。
💡 實務上：金鑰外流常常不是從 git，而是從日常小動作
常見的外流管道：把 .env 整段貼到 Slack 問同事、截圖時剛好拍到終端機、錯誤追蹤工具（自動收集線上錯誤的服務）把含 Authorization 標頭的整個請求記了下來。發現外流時，先撤銷換新、再查原因，不要先花時間爭論「應該沒人看到」。上線前資深工程師會確認：每把金鑰誰有權限看、怎麼換新、換的時候服務會不會中斷。這些問題在出事前想好，出事時才不會手忙腳亂。

練習

在 learn/ 執行 node check.mjs nestjs 11 建立 work/11/，它也會把 .env.example 複製成 work/11/.env。起始專案能啟動：有 POST /orders（body 是 {"items":[{"productId":2,"qty":3}]}，商品 id 1–6 依序是美式咖啡、拿鐵、卡布奇諾、伯爵紅茶、可頌、起司蛋糕）、PaymentModule 用寫死的值 register、configureApp 寫死允許的 CORS 來源，還沒有任何設定管理。判分時的工作目錄是 nestjs/practice/，測試會自己設定環境變數，不會讀你的 .env。

練習 1：在 env.schema.ts 用 zod 寫 envSchema，並在 AppModule 用 ConfigModule.forRoot({ isGlobal: true, validationSchema: envSchema }) 啟動時驗證：

  • NODE_ENV：development、test、production 其中之一，預設 development
  • PORT：正整數，預設 3100（轉成 number；PORT= 空值、0、2.5 都要讓啟動失敗）
  • DATABASE_URL：必填，要是網址
  • CORS_ORIGINS：逗號分隔的來源，轉成每項去掉前後空白、沒有空字串的陣列，預設 http://localhost:5173
  • ORDER_MAX_ITEMS：整數 1–50，預設 20
  • FEATURE_STAMPS：'true'／'false' 轉成 boolean，預設 true；拼錯的值要讓啟動失敗
  • PAYMENT_BASE_URL：網址，預設 https://sandbox.pay.example.test
  • PAYMENT_API_KEY：只有 NODE_ENV=production 時必填，錯誤訊息要寫出這個變數名稱

最後讓 configureApp 的 enableCors 改用設定裡的 CORS_ORIGINS。完成後試試：把 work/11/.env 的 FEATURE_STAMPS 改成 ture、刪掉 DATABASE_URL，執行 npm run start:dev，讀一次錯誤訊息再改回來；也試試 PORT=4000 npm run start:dev，看它聽在哪個 port。測試會用多組環境變數重新建立 AppModule，用 ConfigService.get 檢查轉型後的值，也會帶 Origin 標頭檢查 CORS。

練習 2：在 orders.config.ts 用 registerAs('orders', …) export ordersConfig，內容是 { maxItems }（來自 ORDER_MAX_ITEMS）。讓 OrdersModule 拿得到它，OrdersService 用 @Inject(ordersConfig.KEY) 注入；一張訂單的杯數（所有 qty 加總）超過 maxItems 時，丟 src/errors/domain-errors.ts 裡已經寫好的 TooManyItemsError，第 8 課的 filter 會回 422、errorCode 是 TOO_MANY_ITEMS；等於上限可以下單。

src/orders/ 底下不能出現 process.env。測試會把 ordersConfig.KEY 換成 { maxItems: 2 }，也會在一個只有 .env 檔（ORDER_MAX_ITEMS=4）的資料夾裡啟動，確認從 .env 來的值也生效。

練習 3：AppModule 裡的 PaymentModule.register({ apiKey: 'dev-key', … }) 把設定寫死了。改成 PaymentModule.registerAsync，注入 ConfigService，用 PAYMENT_API_KEY 和 PAYMENT_BASE_URL 建立 PaymentClient 的設定。本機沒設定金鑰時 apiKey 就是 undefined，不要補假金鑰；baseUrl 的預設值只寫在 schema 一個地方。app.module.ts 和 src/payment/ 不能讀 process.env。

練習 4：.env 寫了 FEATURE_STAMPS=false，schema 是 FEATURE_STAMPS: z.coerce.boolean()。config.get('FEATURE_STAMPS') 會拿到什麼？

✓ z.coerce.boolean() 做的是 JavaScript 的 Boolean(值)，任何非空字串都是 true，所以 a 錯；它不會報錯（d 錯），也一定回傳布林（b 錯）。功能開關因此關不掉，而且沒有任何錯誤訊息。環境變數的布林用 z.stringbool()：'false'、'0'、'no' 是 false，拼錯的值會報錯。

練習 5：work/11/.env 寫 PORT=3100，你在終端機執行 PORT=4000 npm run start:dev（沒有設定 override）。應用聽在哪個 port？

✓ ConfigModule 合併時，已經在 process.env 的值不會被 .env 蓋掉。這讓部署平台注入的值永遠贏過檔案，也讓你臨時用一行指令換掉某個值。.env 只是本機的方便（a 錯）；兩個來源本來就會合併，不是錯誤（c 錯）。只有 forRoot({ override: true }) 才會反過來。

練習 6：同事說：「PAYMENT_API_KEY 只有退款功能會用到，等退款時再檢查有沒有設定就好，啟動時檢查太囉嗦。」最主要的問題是什麼？

✓ fail fast 的價值在「出錯的時間點」：啟動時失敗，部署當下就看得到，多數平台也會保留舊版本；用到才檢查，錯誤會在冷門路徑、某個凌晨三點才出現，還帶著一位受影響的顧客。讀一次環境變數的成本可以忽略（b 錯）；TypeScript 不知道執行時的環境變數有沒有設定（c 錯）。

常見錯誤

  • 用 z.coerce.boolean() 解析布林：'false' 變成 true，功能開關關不掉。用 z.stringbool()。
  • 逗號清單沒有 trim：'a, b' 的第二項多一個空白，CORS 比對永遠失敗。split(',').map(s => s.trim()).filter(Boolean)。
  • 只在 main.ts 檢查設定：測試、其他入口都跳過了。把 schema 交給 ConfigModule.forRoot，建立 AppModule 就一定會驗證。
  • secret 寫進 .env 又 commit：git 歷史會一直留著。.env 加進 .gitignore，只 commit .env.example；已經外流的金鑰要撤銷換新。
  • 在模組檔案最上層讀 process.env：ES module 先執行被 import 的檔案，那時 .env 還沒載入。讀設定放在 registerAs 的工廠或 useFactory 裡。
  • service 直接讀 process.env：測試只能改全域變數，互相影響。注入 ordersConfig.KEY，測試用 overrideProvider 換掉。
  • 用 register 傳 process.env 的值：@Module 參數在檔案載入時就算好，那時驗證還沒完成，.env 的值和 schema 的預設值都還沒寫進 process.env，拿到的是原始字串或 undefined。用 registerAsync 配 inject: [ConfigService]。
  • 把整包設定印進 log：所有金鑰跟著進 log 系統。只印「有沒有設定」或遮罩後的值。
  • 以為 .env 永遠在專案資料夾找：預設是目前工作目錄。從別的資料夾啟動就讀不到，必要時用 envFilePath。

補充與查表

validationSchema 接受哪些驗證套件

從 @nestjs/config 12 版起，validationSchema 接受任何實作 Standard Schema 規格的 schema，zod、Valibot、ArkType 都可以；舊版教學用的 Joi 要 18 版以上才符合（官方文件）。Standard Schema 是各驗證套件共同實作的一組介面，框架只要認得這組介面，就不用為每個套件各寫一份支援。

驗證實際在什麼時間點執行

ConfigModule.forRoot() 在 app.module.ts 第一次被 import、@Module 裝飾器執行時就被呼叫，當下讀進 .env 和 process.env。它在 12 版是 async 函式，驗證的結果是一個 Promise；Nest 建立 AppModule 時（NestFactory.create、測試的 Test.createTestingModule(…).compile()）會等它，驗證沒過就在那裡丟出錯誤。所以只要建立 AppModule，不管是 main.ts、e2e 測試還是之後的 CLI 指令，都會經過同一道驗證。

registerAs 的 asProvider()

registerAs('orders', 工廠) 回傳的函式除了 KEY，還有 asProvider()。如果已經有一個 paymentConfig = registerAs('payment', …)，而且它回傳的形狀剛好就是模組要的 options，可以直接寫 PaymentModule.registerAsync(paymentConfig.asProvider())：asProvider() 回傳的就是 { imports, useFactory, inject }。

小結

  • 設定放環境變數、和程式分開（12-factor）；但不要到處讀 process.env：拼錯變 undefined、漏設要到用到才爆、全是字串、散落各處難測試。
  • ConfigModule.forRoot({ isGlobal: true, validationSchema })：12 版接受 zod 等 Standard Schema，啟動時一次列出所有錯誤，有錯就不啟動（fail fast）；驗證跟著 AppModule 走，每個入口都會經過。
  • 字串轉型：數字用 z.coerce.number() 加範圍，布林用 z.stringbool()，清單 split 後 trim；跨欄位規則用 refine 加 path。
  • 系統環境變數優先於 .env；.env 從目前工作目錄找；檔案最上層讀 process.env 會比 .env 載入還早。
  • ConfigService<Env, true> 加 { infer: true } 讀有型別的值；功能程式注入 registerAs 的命名空間，測試用 overrideProvider 換掉。
  • 其他模組用 registerAsync({ inject: [ConfigService], useFactory }) 或 asProvider() 從設定建立。
  • secret：.env 不進 git、提供 .env.example、正式環境由平台注入、不印進 log、外流就撤銷換新。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：PATCH /products/:id 改價格，要擋三件事：呼叫的人是店長、price 是正整數、這個商品存在。各放在哪裡最合適？

✓ 每一站只回答一個問題：guard 管「能不能進來」，pipe 管「格式對不對」，要查資料的業務規則在 service。c 錯在驗證只管格式，商品存不存在要查資料，是 service 的事；a 錯在 middleware 在路由比對之前執行，看不到 handler 上的 @AdminOnly()。（第 6、7 課）

練習 8：前端收到 401 就導去登入頁、403 就顯示「沒有權限」。店長的金鑰失效後，畫面一直顯示「沒有權限」，沒有要他重新登入。guard 最可能哪裡寫錯？

✓ guard 回 false，Nest 不知道拒絕的原因，一律回 403。沒帶憑證或憑證無效要自己 throw new UnauthorizedException() 回 401；知道是誰但沒權限才是 403。b 錯在 guard 可以丟任何例外，401、403 都是 guard 的工作。（第 6 課）

練習 9：「修改個人資料」的 UpdateProfileDto 只有 name，service 寫 this.customers.update(id, { ...dto })。全域 ValidationPipe 只開了 transform，客戶端多送 "stamps": 99 會怎樣？

✓ 這是大量指派：TypeScript 型別在執行時不存在，dto 裡是客戶端送什麼就有什麼。開 whitelist 才會刪掉 DTO 沒宣告的欄位，自己的 API 再加 forbidNonWhitelisted 直接回 400。c 錯在 transform 只是把純物件變成 DTO 實例，不會刪欄位。（第 7 課）

練習 10：這個 catch-all filter 已經用 APP_FILTER 登記。上線後哪裡會出事？

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp()
    this.logger.error('未處理的例外', exception instanceof Error ? exception.stack : String(exception))
    this.adapterHost.httpAdapter.reply(ctx.getResponse(),
      { statusCode: 500, errorCode: 'INTERNAL_ERROR', message: '伺服器發生錯誤' }, 500)
  }
}

✓ catch-all 也會接到 HttpException。要先判斷 instanceof HttpException，用 getStatus()、getResponse() 保留原本的狀態碼和內容，否則前端無法提示使用者，監控也滿是假的 5xx。a 是反方向的錯：message 可能帶出資料表、主機與帳號，500 只回固定訊息和 request id，細節進 log。（第 8 課）

練習 11：OrdersService 庫存不足時丟 ConflictException。後來每晚的補單排程也呼叫同一個 service，資深工程師建議改丟領域錯誤，主要理由是什麼？

✓ service 只說「發生了什麼」（code＋details），由 @Catch(DomainError) 的 filter 翻譯成 HTTP 狀態碼；佇列、排程、CLI 呼叫同一個 service 時，各自決定怎麼處理。b 錯在 Nest 12 的 HttpException 也能帶 errorCode，只是要給前端代碼的話不必換成領域錯誤。（第 8 課）

練習 12：同事寫的逾時 interceptor 如下。哪裡會出事？

return next.handle().pipe(
  timeout(ms),
  catchError(() => throwError(() =>
    new ServiceUnavailableException({ errorCode: 'TIMEOUT', message: '請稍後再試' }))),
)

✓ catchError 接到的是所有錯誤，只有 TimeoutError 該轉成 503＋TIMEOUT，其他用 throwError(() => err) 原樣丟出。b 錯在 timeout 只是不等了，底層工作照樣跑完，要自己設期限；408 是客戶端送請求太慢，不是這個情況（c 錯）。（第 9 課）

練習 13：ValidationPipe 寫在 main.ts 的 app.useGlobalPipes()。E2E 測試送 qty: 0 預期 400，卻拿到 201，最可能的原因？

✓ 測試是用 Test.createTestingModule 自己建應用，main.ts 的設定一行都沒跑，測到的跟正式環境不一樣。pipe、filter、guard 用 APP_* 登記在模組；前綴、CORS 這種只能設在 app 上的收進 configureApp(app)，兩邊都呼叫。b 錯在 supertest 對 app.getHttpServer() 發請求，app.init() 就夠了。（第 10 課）

練習 14：同事把含金流金鑰的 .env commit 並 push 了。發現後他 git rm --cached .env、加進 .gitignore 再 push。接下來最該做的是？

✓ 金鑰一旦進過 git，就要當作已經外流：先撤銷換新，再查原因。a 不夠，改寫歷史擋不住已經 clone、fork 或被別處留下的副本，舊金鑰還是有效的。（第 11 課）
