階段 3：資料庫（Docker、Prisma 7 ＋ PostgreSQL） · 第 13 課

Prisma 入門：schema、migration 與 Prisma Client

到目前為止，咖啡店的 GET /products 回傳的是寫在 ProductsService 裡的陣列。店員新增一個商品，伺服器一重啟就不見了；開兩台伺服器，兩台看到的商品還不一樣。第 12 課已經用 Docker 跑起一台 PostgreSQL，這一課的任務是把商品搬進這台資料庫：

  1. 建出 categories（分類）和 products（商品）兩張表；
  2. 讓資料庫自己擋下負數的價格；
  3. 讓 GET /products 從資料庫查出所有商品，連同它的分類；
  4. 讓同事 clone 專案後，一個指令就有咖啡、茶、甜點可以看。

這四步就是課末的練習 1 到 4。工具是 Prisma 7，本課程鎖定 7.10.1。

這課的路線：
  1. 不手寫 SQL，Nest 怎麼跟 PostgreSQL 說話：Prisma 是什麼、由哪四個部分組成，整件事的最短流程；以及安裝時為什麼一定要寫死版本。
  2. 兩張表怎麼寫進 schema.prisma，又怎麼用 migrate dev 在資料庫裡真的建出來；改完 schema 為什麼還要 generate。
  3. Prisma 寫不出「價格不能是負數」時，怎麼自己補 SQL；順便學會在套用前審查 migration。
  4. migration 帶到測試與正式環境要用哪個指令，跑到一半失敗、資料庫只改了一半時怎麼收拾。
  5. PrismaService 讓 GET /products 查資料庫；最後用種子資料讓同事一拉下來就有東西看。
這課會用到：
  • PostgreSQL 課第 2 課的表與主鍵：CREATE TABLE 建表，主鍵唯一標示一列，通常用自動編號產生。
  • PostgreSQL 課第 8 課的外鍵與一對多：products.category_id 指向 categories.id，一個分類有很多商品，資料庫擋下指向不存在分類的商品。
  • PostgreSQL 課第 22 課的 migration：把每次改資料表結構寫成依序編號的 SQL 檔，跟程式一起進版本控制，每個環境照順序套用。
  • 第 12 課的 Docker 服務：PostgreSQL 跑在容器裡，docker compose up -d --wait 啟動，程式用 DATABASE_URL 連線字串連過去。

不手寫 SQL，Nest 要怎麼跟 PostgreSQL 說話？

最直接的做法是在 Nest 裡用 pg 套件，自己寫 SELECT * FROM products 送出去。這樣做得到，但很快會遇到三件事。第一，查回來的每一列在 TypeScript 裡都是 any，欄位名稱打錯要等到執行時才發現。第二，建表、改表的 SQL 要自己寫成 migration 檔（PostgreSQL 課第 22 課那種），還要自己記得哪些已經套用過。第三，資料庫裡的欄位叫 is_available，程式裡想叫 isAvailable，每次查完都要自己轉。

解決這類問題的工具叫 ORM（object-relational mapping）。資料庫存的是一張張的表和列，程式操作的是物件，ORM 負責在兩者之間對應：你用程式的寫法描述「要哪些資料」，它幫你產生 SQL、送出去，再把結果變成有型別的物件。Prisma 是 Node 生態裡常用的一套 ORM，它的做法是先讓你寫一份描述資料表的檔案，再從這份檔案產生其他東西。

Prisma 不是 import 進來就能用的單一函式庫，而是一組檔案和指令。這課每一步都是在動其中一樣，所以先把四個部分認清楚：

  • Prisma schema（prisma/schema.prisma）：用 Prisma 自己的語法描述資料表，是整件事的起點。裡面有三種區塊：model（一張表）、generator（要產生什麼程式、放哪裡）、datasource（哪一種資料庫）。
  • migration：Prisma 比對 schema 的前後差異，產生建表、改表的 SQL 檔，放在 prisma/migrations/<時間_名稱>/migration.sql。這些檔案進 git，每個環境的資料庫都照順序套用同一組檔案，跟你在 PostgreSQL 課手寫的 migration 是同一件事，只是不用自己寫。
  • Prisma Client：Prisma 依 schema 產生的一份 TypeScript 程式。你在 service 裡寫 prisma.product.findMany()，它送出 SQL，回傳的商品有完整的型別，欄位打錯在編輯器裡就會標紅。
  • prisma.config.ts：npx prisma … 這組指令（Prisma CLI）的設定檔，告訴 CLI schema 在哪、migration 放哪、要連哪個資料庫。

四個部分裡，你親手寫的是 schema 和 prisma.config.ts；migration 和 Prisma Client 都從 schema 產生，而且走的是兩條互相獨立的路。

上面那條路改的是資料庫：migrate dev 產生 SQL 並套用，PostgreSQL 裡才真的有表。下面那條路改的是你的程式：generate 產生 Prisma Client，放在 src/generated/prisma，程式用它建立 PrismaClient 去查詢。所以這課任務的最短流程就是：

  1. 在 schema.prisma 寫 model；
  2. npx prisma migrate dev：資料庫長出表；
  3. npx prisma generate：程式拿到型別；
  4. Nest 的 service 注入一個 PrismaClient，用它查 products。

接下來每一節都是把其中一步講細。不過這四步成立的前提，是裝到的 Prisma 是 7.10.1；照官網寫的 npm i 直接裝，就可能裝錯版本。

動手之前：怎麼確保裝到的是 7.10.1？

npm 上的套件除了版本號，還有 dist-tag。它是發布者貼在某個版本上的標籤，最常見的是 latest。npm i prisma 不寫版本時（版本範圍與 lockfile 見 Node 課第 3 課），npm 裝的是 latest 標籤指的那個版本。多數套件的 latest 是最新穩定版，但這只是習慣，不是規定，標籤指向哪裡由發布者決定。2026-10-31 查詢時，Prisma 就是例外：CLI 套件 prisma 的 latest 指向 8.0 的預覽版，而 @prisma/client 的 latest 還是 7.10.1。所以 npm i prisma @prisma/client 會裝出 CLI 8.0 RC 配 Client 7.10.1，兩邊對不上，npm 不會幫你對齊不同套件的版本，也不會擋預覽版。

做法是寫死版本：npm i -D prisma@7.10.1、npm i @prisma/client@7.10.1 @prisma/adapter-pg@7.10.1，並 commit lockfile。這門課的 practice/package.json 已經鎖好，你只要 npm ci，不要在 task 資料夾裡另外安裝。查文件時也有同樣的陷阱，網址要有 /docs/orm/v7/；查到的 dist-tag 實際狀況和文件網址的細節見課末的補充與查表。

💡 實務上：新專案的第一個 PR 就把版本鎖死
工具的主版本一升，指令、設定檔的寫法都可能整組換掉，Prisma 8 就是這樣。團隊裡最常見的事故不是程式寫錯，而是兩個人各自 npm i，裝出不同的版本，同一個指令在兩台電腦上的結果不一樣。資深工程師開新專案時會把 package.json 的版本寫死、commit lockfile、CI 用 npm ci；之後要升級，是開一個專門的 PR，讀完官方的升級指南再做，而不是順手照著 CLI「有新版」的提示升上去。這課的咖啡店也一樣：7.10.1 是整課所有指令成立的前提。

咖啡店的兩張表，在 schema.prisma 裡怎麼寫？

最短流程的第一步是寫 model。咖啡店要兩張表：categories（咖啡、茶、甜點）和 products，一個分類有很多商品，也就是 PostgreSQL 課第 8 課的一對多。完整的 schema 如下，練習資料夾裡的 generator 和 datasource 已經寫好，你要補的是兩個 model：

generator client {
  provider = "prisma-client"            // Prisma 7 的新產生器
  output   = "../src/generated/prisma"  // 必填：產生的程式放哪裡（相對於這個檔案）
}

datasource db {
  provider = "postgresql"               // Prisma 7 起連線網址不寫在這裡
}

model Category {
  id       Int       @id @default(autoincrement())
  name     String    @unique
  products Product[]                    // 關聯欄位：只存在於 Prisma Client，資料庫沒有這一欄

  @@map("categories")                   // 資料表名稱
}

model Product {
  id          Int      @id @default(autoincrement())
  name        String   @unique
  price       Int
  isAvailable Boolean  @default(true) @map("is_available")
  categoryId  Int      @map("category_id")
  category    Category @relation(fields: [categoryId], references: [id])
  createdAt   DateTime @default(now()) @map("created_at") @db.Timestamptz(3)

  @@map("products")
}

上面兩個區塊是給 Prisma 自己看的設定。generator 說「要產生 Prisma Client，放到 src/generated/prisma」，那就是圖裡下面那條路的終點。datasource 說「這是 PostgreSQL」，Prisma 產生的 SQL 才會用 PostgreSQL 的語法。連線網址不在這裡，下一節會看到它搬去哪了。

每個 model 對應一張表，裡面每一行是一個欄位，寫法是「名稱 型別 屬性」：

  • 型別與 NULL：String、Int 這些是 Prisma 的型別，會對應到 PostgreSQL 的型別（下面的表）。型別後面加 ?（例如 String?）表示可以是 NULL，不加就是 NOT NULL。所以這份 schema 裡的欄位全部 NOT NULL。
  • 主鍵與唯一：@id @default(autoincrement()) 表示主鍵、自動編號，產生 SERIAL。@unique 產生唯一索引，同一個名稱只能有一筆。後面種子資料能「重複執行也不會多一份」，靠的就是 name 的唯一索引。
  • @map／@@map：TypeScript 習慣 camelCase（isAvailable），PostgreSQL 習慣 snake_case（is_available）。@map 改欄位在資料庫裡的名稱、@@map 改資料表名稱，程式裡還是寫 isAvailable。不加的話，資料表會叫 "Product"、欄位叫 "isAvailable"，PostgreSQL 對有大寫的名稱要加雙引號，之後在 psql 每次都要寫 SELECT "isAvailable" FROM "Product"。

最需要停下來看的是關聯。Product 裡跟分類有關的有兩行，它們的身分不一樣：

  • categoryId Int @map("category_id") 是真正存在資料庫的欄位，就是 PostgreSQL 課第 8 課的外鍵欄位，存的是分類的 id。
  • category Category @relation(fields: [categoryId], references: [id]) 是關聯欄位，資料庫裡沒有這一欄。它是給 Prisma Client 用的：有了它，查商品時可以寫 include: { category: true }，一次把分類物件也帶回來。@relation 告訴 Prisma「外鍵是我這邊的 categoryId，指向 Category 的 id」，Prisma 就會據此產生外鍵約束。

Category 裡的 products Product[] 是同一段關係的另一端，也只存在 Prisma Client 裡，讓你從分類查它底下的商品。一對多的兩端都要寫，Prisma 才認得這是一段關係。

型別這邊有兩個預設值不是你通常想要的，寫 schema 時要主動處理：

Prisma預設產生說明
IntINTEGER金額用整數「元」（PostgreSQL 課第 13 課），不要用 Float（DOUBLE PRECISION，有誤差）
StringTEXT要限制長度用 @db.VarChar(100)，通常 text 就好
BooleanBOOLEAN
DateTimeTIMESTAMP(3)沒有時區。要 timestamptz 必須寫 @db.Timestamptz(3)

這就是 createdAt 後面多了 @db.Timestamptz(3) 的原因。@db. 開頭的屬性是「直接指定 PostgreSQL 的型別」，Prisma 的型別系統表達不出來的細節都用它補。

到這裡 schema 寫好了，但它只是一個文字檔，PostgreSQL 裡還什麼都沒有。下一步是讓資料庫照著它長出兩張表。

schema 寫好了，資料庫怎麼真的長出這兩張表？

要讓資料庫長出表，Prisma CLI 得先知道要連哪一台資料庫。上一節看到 datasource 裡沒有連線網址，因為 Prisma 7 把它搬到了 CLI 的設定檔 prisma.config.ts。練習資料夾裡已經有這個檔案：

import 'dotenv/config'                       // 把 .env 載入 process.env（已經有的變數不會被蓋掉）
import { defineConfig, env } from 'prisma/config'

export default defineConfig({
  schema: 'prisma/schema.prisma',
  migrations: { path: 'prisma/migrations' },
  datasource: { url: env('DATABASE_URL') },   // 沒有這個變數就直接報錯
})

注意第一行。Prisma 7 不會自動讀 .env，DATABASE_URL 寫在 .env 裡，沒有人把它載入 process.env，env('DATABASE_URL') 就找不到變數而直接報錯。import 'dotenv/config' 就是在設定檔一開始把 .env 載入。它不會蓋掉已經存在的環境變數，所以判分或正式環境從外面給的 DATABASE_URL 仍然優先，這跟第 11 課講的「平台設定優先於 .env」是同一個方向。

有了連線網址，在 task 資料夾執行：

npx prisma migrate dev --name init

migrate dev 依序做三件事：

  1. 比對 schema 和現有的 migration 差在哪。第一次執行時還沒有任何 migration，所以差異就是「整份 schema」。
  2. 把差異寫成一個新的 migration.sql，放在 prisma/migrations/<時間>_init/，--name 就是資料夾名稱的後半段。
  3. 把這個檔案套用到開發用資料庫。資料庫不存在會自動建立。

產生的檔案就是你在 PostgreSQL 課第 22 課手寫的那種 SQL，打開來逐句對照 schema：

-- CreateTable
CREATE TABLE "products" (
    "id" SERIAL NOT NULL,
    "name" TEXT NOT NULL,
    "price" INTEGER NOT NULL,
    "is_available" BOOLEAN NOT NULL DEFAULT true,
    "category_id" INTEGER NOT NULL,
    "created_at" TIMESTAMPTZ(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "products_pkey" PRIMARY KEY ("id")
);
-- CreateIndex
CREATE UNIQUE INDEX "products_name_key" ON "products"("name");
-- AddForeignKey
ALTER TABLE "products" ADD CONSTRAINT "products_category_id_fkey" FOREIGN KEY ("category_id")
  REFERENCES "categories"("id") ON DELETE RESTRICT ON UPDATE CASCADE;

可以看到上一節的每個屬性都變成了 SQL：@map 讓欄位是 snake_case，沒有 ? 的欄位都是 NOT NULL，@unique 變成 CREATE UNIQUE INDEX，@relation 變成外鍵約束。關聯欄位 category 和 products 在 SQL 裡完全沒有出現，因為它們本來就只存在 Prisma Client。

Prisma 怎麼知道下次要產生「新的差異」，而不是整份 schema 再建一次？這件事分成兩個問題，由兩樣不同的東西負責。

第一個問題是差異怎麼算。migrate dev 會用到一個 shadow database（影子資料庫）。它是 migrate dev 執行時暫時建立的另一個空資料庫，只拿來計算，用完就清掉，不會動到你的資料。migrate dev 把 migrations/ 裡的檔案依序在 shadow database 重播一遍，得到「目前這些 migration 加起來長成什麼樣」，再跟現在的 schema 比，多出來的部分就寫成新檔。

第二個問題是哪些檔案已經套用。Prisma 在你的資料庫裡建一張 _prisma_migrations 表，記下這個資料庫跑過哪些檔案，之後只套用還沒跑過的。

已經套用的檔案不會再跑，所以 migration 檔一旦套用過就不要再改，要改結構一律產生新的 migration。

表建好了，但最短流程還有第三步。回頭看那張圖：migrate dev 走的是上面那條路，只改資料庫。Prisma 7 起它不會順便產生 Prisma Client，也不會執行種子資料（7.10.1 實測）。所以改完 schema、跑完 migrate，還要自己執行：

npx prisma generate

沒有這一步，程式裡的 Prisma Client 還是舊的，看不到新的 model 或新欄位，編輯器會說 this.product 不存在。這門課的 node check.mjs 判分前會幫你跑一次 generate，但 npm run start:dev 不會，自己開發時要記得。

💡 實務上：改 schema 的固定三步
每次改 schema，順序都一樣：改 schema.prisma → migrate dev --name 說明這次改了什麼 → generate。--name 會變成資料夾名稱，半年後別人翻 migrations/ 時就靠它知道每一步在做什麼，寫 add_description 比寫 update 有用得多。src/generated/prisma 不進 git，每個人 clone 下來自己 generate；migrations/ 進 git，所有環境共用。拉了同事的程式後發現型別不對，第一個要懷疑的就是自己還沒 generate。

現在 products 表有了，但它會收下任何整數當價格，包括 -80。咖啡店需要「價格不能是負數」，這件事 schema 寫不出來。

價格不能是負數，Prisma 寫不出來怎麼辦？

在 PostgreSQL 裡，「價格不能是負數」是一個 CHECK 約束（PostgreSQL 課第 12 課）：寫入時資料庫檢查條件，不成立就拒絕。Prisma schema 沒有 CHECK 約束的語法，這條規則寫不進 model。

先回答一個問題：DTO 驗證（第 7 課）已經擋得下負數，為什麼還要資料庫擋？因為資料不只從你的 API 進來。別的服務、維運手動執行的 SQL、半年後新同事寫的批次程式，都會直接寫入這張表，它們不會經過你的 DTO。約束放在資料庫，所有入口都擋得住；DTO 驗證則負責給前端一個清楚的錯誤訊息。兩層各有用途，不是二選一。

既然 Prisma 產生不出這句 SQL，就自己寫。做法是先讓 Prisma 產生一個空的 migration，再把 SQL 填進去：

npx prisma migrate dev --create-only --name price_check   # 只產生檔案，不套用
# 打開新產生的 prisma/migrations/<時間>_price_check/migration.sql，寫入：
#   ALTER TABLE "products" ADD CONSTRAINT "products_price_check" CHECK ("price" >= 0);
npx prisma migrate dev                                     # 套用還沒套用的 migration

--create-only 讓 migrate dev 只做前兩件事：比對差異、產生檔案，但不套用。schema 沒有改，差異是空的，所以產生的是一個空檔，等你填。填好後再執行一次 migrate dev，它發現有一個還沒套用的 migration，就把它套用上去。為什麼不直接把 CHECK 加進 init 那個檔案？因為 init 已經套用過，_prisma_migrations 記著它，Prisma 不會再跑一次，你的資料庫和同事的資料庫從此就不一樣了。

--create-only 還有一個更重要的用途：在套用前審查。Prisma 只看得到「schema 改之前、改之後長什麼樣」，看不出你的意圖。假設店長要求把 isAvailable 改名成 onSale（@map("on_sale")），對 Prisma 來說，這等於「少了一個欄位、多了一個欄位」，Prisma 7.10.1 產生的是：

ALTER TABLE "products" DROP COLUMN "is_available",
ADD COLUMN     "on_sale" BOOLEAN NOT NULL DEFAULT true;

這是破壞性變更（destructive change），也就是會讓既有資料消失的變更：刪掉欄位，所有商品的上架狀態一起不見，新欄位全部變回預設值 true，已經下架的商品全部重新上架。migrate dev 偵測到會遺失資料時會先警告，但不能只靠它。正確做法是用 --create-only 產生草稿，打開檔案，把那兩句改成 ALTER TABLE "products" RENAME COLUMN "is_available" TO "on_sale";，資料就原封不動地跟著新名稱走。下一課會用 @map 處理另一種情況：程式裡改名、資料庫不動。

所以習慣要比 Prisma 的警告更嚴格：每個 migration.sql 套用前都打開看過，看到 DROP 就停下來想。

💡 實務上：migration.sql 是 PR 裡最該仔細看的檔案
在團隊裡，改 schema 的 PR 一定會附上產生的 migration.sql，review 時資深工程師通常先看它，而不是先看 schema.prisma。他會問：有沒有 DROP、改型別、加 NOT NULL 這類會動到既有資料的句子？表裡已經有幾萬筆訂單時，加 UNIQUE 或 CHECK 會不會因為舊資料不合格而失敗？如果這張表很大，這句會不會鎖表、讓咖啡店結帳卡住？看不懂某一句時，寧可在 PR 裡問一句，也不要讓它直接上線。

到目前為止，所有 migration 都只套用在你自己的開發資料庫。這兩個 migration 遲早要帶到判分用的資料庫、測試環境和正式環境，而且「舊資料不合格」這種失敗，正好最常在那些地方發生。

migration 帶到別的環境要用哪個指令？跑到一半失敗怎麼收拾？

先看為什麼不能在正式環境也用 migrate dev。它的設計是給開發機用的：會比對 schema、產生新檔，發現資料庫和 migration 對不上時，還會要求把資料庫重設。正式環境要的剛好相反：只照著 git 裡已經審過的檔案套用，不產生任何新東西，更不能重設。Prisma 為不同場合準備了不同的指令：

指令做什麼用在哪
migrate dev產生新的 migration 並套用；發現資料庫和 migration 對不上時會要求重設只在開發機
migrate deploy只套用 migrations/ 裡還沒套用的檔案，不產生、不重設、不比對 schema測試、正式環境、CI（每次 push 自動跑測試與部署的流程）；這門課的判分也用它
db push直接讓資料庫長得跟 schema 一樣，不留 migration 檔只適合丟掉也沒關係的原型。別的環境無法重現
migrate reset刪掉資料庫重建，再套用全部 migration開發機，資料全毀。Prisma 7.10 偵測到是 AI agent 在執行時會拒絕，要使用者明確同意

日常只會用到前兩個：開發機用 migrate dev 產生並套用，其他環境用 migrate deploy 套用同一組檔案。db push 看起來省事，但它不留下任何檔案，你的資料庫長對了，別的環境卻沒有東西可以重現，練習 1 的測試會抓這件事。

migrate deploy 也會失敗。最常見的例子是新的 UNIQUE 遇上已經重複的資料：你的開發資料庫很乾淨，正式資料庫裡卻有兩筆同名的商品。這時要知道一個關鍵事實：Prisma 7 不會把一個 migration 檔包成一個交易（7.10.1＋PostgreSQL 18 實測）。交易（PostgreSQL 課第 18 課）是「一組 SQL 要嘛全部生效、要嘛全部不生效」；沒有包成交易，就是一句一句各自生效。一個檔案有兩句、第二句失敗時：

  • 第一句已經生效，不會回滾；
  • _prisma_migrations 把這個 migration 記為失敗；
  • 之後每次 migrate deploy 都會停在錯誤 P3009（有失敗的 migration），不再往下套用。

資料庫現在處在「改了一半」的狀態，Prisma 也拒絕繼續。直接修好檔案再跑一次行不通：第一句會撞上「欄位已存在」，而且 P3009 會先擋住。收拾要照這個順序：

  1. 看清楚做到哪一句，用 SQL 手動還原做了一半的變更（例如 DROP 掉已經建好的欄位）。
  2. npx prisma migrate resolve --rolled-back <migration 名稱>：告訴 Prisma「這個失敗的 migration 已經處理掉了」，它就不再擋。反過來，如果你是手動把剩下的步驟做完，用 --applied。
  3. 修好 migration 檔（或資料），再 migrate deploy。

想從源頭避免「改了一半」，就在 migration 檔裡自己寫 BEGIN; … COMMIT;，把整個檔案包成一個交易，失敗時全部回到原狀。例外是 CREATE INDEX CONCURRENTLY：它不能在交易裡執行（PostgreSQL 課第 34 課），所以要單獨放一個 migration 檔。

💡 實務上：正式環境的 migration 由部署流程跑一次
常見做法是在 CI 的部署步驟、新版程式上線之前執行一次 migrate deploy，而不是每台伺服器啟動時各跑一次（migration 一失敗，每台伺服器都起不來，也很難從各台的 log 追出原因）。也因為部署時新舊版程式常會短暫同時連到同一個資料庫，migration 最好讓舊版程式還能正常運作，刪欄位這類變更等新版穩定後再做。動到大表或資料的 migration，上線前先跟維運確認有沒有備份、預計要跑多久。遇到 P3009 時先別急著重跑部署，照上面的順序查清楚做到哪一句。

表和約束都到位了，每個環境也知道怎麼套用。但 GET /products 還是回傳那個陣列，Nest 還沒有開始用資料庫。

Nest 裡怎麼讓 GET /products 查資料庫？

最短流程的第四步是「service 注入一個 PrismaClient」。generate 產生的 PrismaClient 是一個 class，new 出來就能查詢。問題是要 new 幾個、在哪裡 new，答案跟連線池有關。

每次查詢都重新跟 PostgreSQL 建一條連線很慢，所以程式會維持一組開著的連線重複使用，這組連線叫連線池（connection pool，見 PostgreSQL 課第 25 課）。查詢時從池裡借一條，用完還回去。Prisma 7 自己不負責連線，而是透過一個 driver adapter（轉接器）交給別的套件：這門課用 @prisma/adapter-pg 的 PrismaPg，它把連線工作交給 node-postgres（pg 套件），所以連線池就是 pg 的連線池。每個 PrismaClient instance 都帶著自己的一個池。

連線池（connection pool）預設最多 10 條連線，這是 pg 的預設值；拿不到連線的查詢會一直等（pg 預設沒有逾時，Prisma 6 是 5 秒）。千萬不要每個請求 new PrismaClient()：每個 instance 都有自己的連線池，連線數會一路漲到資料庫的上限。第 16 課再調整池的大小與逾時。

結論是：整個應用應該只有一個 PrismaClient，大家共用同一個池。在 Nest 裡做到這件事最自然的方法，就是讓一個 provider 繼承它。Nest 的 provider 預設是單例，整個應用只建立一次（第 3 課），所有注入它的 service 拿到的都是同一個：

// src/prisma/prisma.service.ts
import { Injectable, type OnApplicationShutdown } from '@nestjs/common'
import { ConfigService } from '@nestjs/config'
import { PrismaPg } from '@prisma/adapter-pg'
import { PrismaClient } from '../generated/prisma/client.js'   // 產生的程式；import 要寫到 client.js
import type { Env } from '../config/env.schema.js'

@Injectable()
export class PrismaService extends PrismaClient implements OnApplicationShutdown {
  constructor(config: ConfigService<Env, true>) {
    super({ adapter: new PrismaPg({ connectionString: config.get('DATABASE_URL', { infer: true }) }) })
  }

  async onApplicationShutdown() {
    await this.$disconnect()                                  // 關掉連線池
  }
}

這段程式有三個決定，各有原因：

  • 連線網址從 ConfigService 拿：用的是第 11 課驗證過的設定。開發、判分、正式環境只要換環境變數，程式不用改。寫死網址的程式在測試裡會連到錯的資料庫。
  • 在 onApplicationShutdown 關連線池：$disconnect() 關掉這個 instance 的連線池。應用結束前要做這件事，而且關的時機很重要。Nest 12 關機的順序是 onModuleDestroy → beforeApplicationShutdown → 關掉 HTTP 伺服器 → onApplicationShutdown（12.3.2 原始碼）。在前兩個 hook 關連線，HTTP 伺服器還開著，還沒結束的請求查資料庫就會出錯；放在最後一步，HTTP 伺服器已經關閉、不再收新的請求，才關連線池。第 24 課的優雅關機會細講。
  • 不需要在 onModuleInit 裡 $connect：第一個查詢會自動連線。早一點連上的好處是啟動時就發現連不上，代價是資料庫沒開時整個應用起不來，兩種都有人用。

關機的 hook 還有一個前提。docker stop 這類操作要求程序結束時，系統送給程序的是 SIGTERM 訊號（要求程序結束的訊號）。main.ts 要呼叫 app.enableShutdownHooks()，收到 SIGTERM 時上面這些 hook 才會執行。

接著讓別的模組拿得到它。PrismaService 放在自己的模組裡並 export：

// src/prisma/prisma.module.ts
@Module({
  providers: [PrismaService],
  exports: [PrismaService],   // 沒有 export，ProductsModule 就注入不到（第 4 課）
})
export class PrismaModule {}

ProductsModule 的 imports 加上 PrismaModule，ProductsService 的建構子就能注入 PrismaService。PrismaService 是很多模組都要的基礎設施，也可以加上 @Global() 省掉每個模組的 imports，代價是看不出誰依賴資料庫。這門課選擇明確 import。

最後，把 ProductsService.findAll 裡的陣列換成查詢：

findAll() {
  return this.prisma.product.findMany({
    include: { category: true },   // 順便把分類一起查出來
    orderBy: { id: 'asc' },        // 沒有 ORDER BY，PostgreSQL 不保證順序
  })
}

include: { category: true } 用的就是 schema 裡那個只存在 Prisma Client 的關聯欄位，每個商品會多一個 category 物件。orderBy 不能省：SQL 沒寫 ORDER BY 時，PostgreSQL 回傳的順序沒有保證，今天剛好照 id 排，資料改過之後就可能不是。

💡 實務上：連線數是資料庫最先用完的資源
PostgreSQL 能同時接受的連線數有上限，所有應用、所有伺服器共用。咖啡店開三台 Nest，每台一個池、每池 10 條，就是 30 條；如果有人在 service 裡每個請求 new PrismaClient()，尖峰時一下就用完，症狀是其他服務也開始連不上資料庫。資深工程師看到「資料庫連線數暴增」，第一個會去找的就是程式裡有沒有不只一個 PrismaClient。練習 3 的測試會同時送 30 個請求再數連線數，就是在抓這件事。

現在 GET /products 真的查資料庫了，但你的資料庫是空的，回傳的是 []。同事 clone 專案、跑完 migration，也是一張空表。

同事 clone 下來，怎麼一個指令就有商品可看？

答案是種子資料（seed）：開發和展示用的初始資料，跟著專案一起進 git，任何人跑一個指令就能把它放進自己的資料庫。這門課用 SQL 寫，最直接，也不用多裝套件。寫種子資料的重點是可以重複執行：同事拉了新程式再跑一次，不應該出錯，也不應該多出一份。

-- prisma/seed.sql
INSERT INTO categories (name) VALUES ('咖啡'), ('茶'), ('甜點')
ON CONFLICT (name) DO NOTHING;           -- 已經有同名的就跳過（靠 name 的 UNIQUE）

INSERT INTO products (name, price, category_id) VALUES
  ('美式咖啡', 80, (SELECT id FROM categories WHERE name = '咖啡'))
ON CONFLICT (name) DO NOTHING;

兩個寫法讓它可以重跑：

  • ON CONFLICT (name) DO NOTHING：要新增的這列如果撞上 name 的唯一索引，就跳過，不報錯。這是第一次寫 schema 時就加上 @unique 的回報。第一次執行時全部新增，第二次執行時全部撞名、全部跳過，結果一樣。
  • 外鍵用子查詢依名稱找：(SELECT id FROM categories WHERE name = '咖啡')，不要寫死 1、2。自動編號在別人的資料庫不一定一樣：同事的資料庫如果先有別的分類，「咖啡」的 id 可能是 4，寫死 1 就會把美式咖啡掛到錯的分類。

反過來，用 TRUNCATE 或 DELETE 先清空再新增，雖然也能重跑，但會把同事在開發資料庫裡自己加的資料一起刪掉，練習 4 的測試會抓這件事。

檔案寫好後，在 prisma.config.ts 的 migrations 加上 seed，告訴 Prisma 要執行什麼指令，npx prisma db seed 就會執行它：

migrations: {
  path: 'prisma/migrations',
  seed: 'prisma db execute --file prisma/seed.sql',   // db execute 會用 config 裡的連線網址
},

前面說過，Prisma 7 的 migrate 不會自動跑種子資料，所以新環境的完整順序是：migrate deploy（或開發機上的 migrate dev）建表，再 db seed 放資料。想直接看資料表裡有什麼，npx prisma studio 會開一個網頁版的資料表瀏覽器，不用進 psql。種子資料為什麼不用 TypeScript 寫，見課末的補充與查表。

💡 實務上：種子資料是給同事用的，不是給正式環境
新同事 clone 專案後，跑完 docker compose up、migrate deploy、db seed 就有一個能點的咖啡店後台，這是種子資料最大的價值；PM 展示新功能、前端接 API 時也靠它有東西可看。種子資料只放假資料，不要從正式資料庫匯出真實的顧客名字或電話。正式環境需要的固定資料（例如預設的分類），比較穩的做法是寫進 migration，每個環境都會套用、也留得下紀錄。

到這裡，開場的四步都有了做法：schema 加 migrate dev 建表、手寫 migration 加 CHECK、PrismaService 讓 GET /products 查資料庫、seed.sql 讓同事有資料。接下來在練習裡把它們實際做一遍。

練習

先確認容器在跑（第 12 課：在 learn/nestjs/practice 執行 docker compose up -d --wait），再在 learn/ 執行 node check.mjs nestjs 13 建立 work/13/，它會把 .env.example 複製成 .env（開發用資料庫 nest_13）。以下指令都在 work/13 執行。判分時 check.mjs 會重建判分用的資料庫 nest_13_test、執行 prisma generate，再用 prisma migrate deploy 套用你的 migration；測試會把 DATABASE_URL 換成這個資料庫。還沒有任何 migration 時，四題都會顯示「還沒有 migration」。

練習 1：在 schema.prisma 寫 Category 與 Product 兩個 model，然後執行 npx prisma migrate dev --name init，打開產生的 migration.sql 讀一遍。

  • categories：id（自動編號主鍵）、name（text，唯一）
  • products：id、name（text，唯一）、price（integer）、is_available（boolean，預設 true）、category_id（指向 categories 的外鍵）、created_at（timestamptz，預設現在時間），全部 NOT NULL
  • 資料表與欄位都是 snake_case；Prisma 裡的欄位名稱是 isAvailable、categoryId、createdAt，關聯欄位叫 category 和 products（練習 3 會用到）

測試讀判分資料庫的 information_schema 檢查欄位與型別，也會用 prisma migrate diff 確認 migration 和 schema 一致：schema 改了卻沒再執行 migrate dev，或用 db push 代替 migration，都會被抓到。

練習 2：價格不能是負數。用 npx prisma migrate dev --create-only --name price_check 產生空的 migration，在新的 migration.sql 寫 ALTER TABLE … ADD CONSTRAINT … CHECK …，再執行 npx prisma migrate dev 套用。schema.prisma 不用改；不要把 CHECK 加進已經套用過的 init。價格 0 要可以（免費招待）。測試會直接用 SQL 新增 price = -1，要失敗在 SQLSTATE 23514（違反 CHECK）。

練習 3：完成 PrismaService（繼承產生的 PrismaClient，用 ConfigService 取 DATABASE_URL 建立 PrismaPg，在 onApplicationShutdown 呼叫 $disconnect）與 PrismaModule，讓 ProductsService.findAll 從資料庫回傳所有商品，每筆包含 category，依 id 由小到大。先執行 npx prisma generate，編輯器才看得到 this.product。做完用 npx prisma db execute --stdin 或 psql 在 nest_13 加幾筆資料，npm run start:dev 後 curl localhost:3100/products 看看。

測試會在判分資料庫放 3 筆商品、檢查 GET /products 的內容與順序；把 PrismaService 換成假的物件，確認 ProductsService 用的是注入進來的那一個（自己 new PrismaClient() 會被抓到，就算用完有關也一樣）；同時送 30 個請求後數資料庫上的連線數（不能超過 10）；並確認 app.close() 走到 onApplicationShutdown 時才呼叫 $disconnect。

練習 4：在 prisma/seed.sql 寫種子資料：3 個分類（咖啡、茶、甜點）和 6 個商品（美式咖啡 80、拿鐵 110、卡布奇諾 110 屬於咖啡；伯爵紅茶 90 屬於茶；可頌 70、起司蛋糕 120 屬於甜點）。要能重複執行。在 prisma.config.ts 設定 migrations.seed，用 npx prisma db seed 執行兩次確認不會出錯。測試的資料庫裡會先有一個別的分類（所以分類的 id 不從 1 開始），兩次執行之間還會加一個別人的商品：分類要依名稱查、不能寫死 id，也不能用 TRUNCATE／DELETE 換取可以重跑。結果要剛好多出 3 個分類、6 個商品，別人的資料還在。

練習 5：新專案執行 npm i prisma @prisma/client（2026-10-31），裝到的是什麼？

✓ c。不寫版本時裝的是 latest 標籤，而標籤指向哪個版本由發布者決定：prisma 的 latest 目前是 8.0 RC，@prisma/client 的是 7.10.1。npm 不會幫你對齊不同套件的版本，也不會擋預覽版。所以要寫死 prisma@7.10.1 並 commit lockfile。

練習 6：你在 Product 加了 description String?，執行 npx prisma migrate dev --name add_description 成功，資料庫也有新欄位了，但程式裡 product.description 報型別錯誤。漏了哪一步？

✓ b。migrate 和 generate 是兩條路：migrate 改資料庫，generate 改 src/generated/prisma 裡的型別。Prisma 6 的 migrate dev 會順便 generate，Prisma 7 不會。資料庫已經有欄位，deploy 和重啟都沒用；名稱本來就一樣，不需要 @map。

練習 7：一個 migration.sql 有兩句：先 ALTER TABLE products ADD COLUMN sku text，再 CREATE UNIQUE INDEX … ON products (name)，第二句因為資料重複而失敗。用 Prisma 7.10.1 執行 migrate deploy 之後是什麼狀態？

✓ a。Prisma 7 不會把 migration 檔包成一個交易，第一句已經生效。直接改檔重跑會撞上「欄位已存在」，或被 P3009 擋住。正確做法：手動移除 sku、migrate resolve --rolled-back、修正後再 deploy；要全有或全無就在檔案裡自己寫 BEGIN;／COMMIT;。shadow database（影子資料庫）是 migrate dev 暫時建立、用來重播 migration 比對差異的資料庫，deploy 不用它，也不會試跑。

常見錯誤

  • npm i prisma 不寫版本：裝到 8.0 RC，跟 @prisma/client 7.10.1 對不上。寫死 prisma@7.10.1，commit lockfile。
  • 照著官網沒有 /v7/ 的頁面操作：那是 Prisma 8 的指令（contract emit、db update）。看 /docs/orm/v7/。
  • 以為 Prisma 7 會讀 .env：prisma.config.ts 第一行要 import 'dotenv/config'，否則 env('DATABASE_URL') 直接報錯。
  • 改完 schema 忘了 generate：資料庫有欄位，型別卻沒有。migrate dev 之後執行 npx prisma generate。
  • 用 db push 取代 migration：自己的資料庫看起來沒問題，別的環境卻沒有任何檔案可以重現。要留下紀錄就用 migrate dev。
  • 直接改已經套用過的 migration 檔：別人的資料庫已經跑過舊版本，不會再跑一次，環境之間開始不一致。變更一律寫成新的 migration。
  • 沒看過 migration.sql 就套用：改名會變成 DROP COLUMN＋ADD COLUMN，資料直接消失。用 --create-only 審過、必要時改成 RENAME COLUMN。
  • migration 失敗後直接改檔重跑：第一半已經生效，還會被 P3009 擋住。先手動還原，再 migrate resolve --rolled-back，最後 deploy。
  • DateTime 沒加 @db.Timestamptz(3)：產生沒有時區的 timestamp(3)，跨時區時會出錯。
  • 種子資料用 TRUNCATE 換取可以重跑，或寫死外鍵 id：前者會刪掉同事在開發資料庫裡的資料，後者在別人的資料庫指錯分類。用 ON CONFLICT (name) DO NOTHING，外鍵用子查詢依名稱找。
  • 每個請求 new PrismaClient()：每個都有自己的連線池，連線數爆掉。注入同一個 PrismaService。

種子資料為什麼不用 seed.ts

可以用，但產生的 Client 是 TypeScript，node prisma/seed.ts 只會擦掉型別，遇到 import 寫 .js 的 .ts 檔就找不到；要另外裝 tsx 這類工具。這門課不增加套件，種子資料用 SQL。

接手的專案用 TypeORM

不少 Nest 專案用的 ORM 是 TypeORM（目前 typeorm 1.1.3，搭配 @nestjs/typeorm 12.0.3），尤其是 Prisma 普及之前開始的專案。這課的三個部分都對得上：

PrismaTypeORM
schema.prisma 的 modelentity：加了 @Entity()、@Column()、@ManyToOne() 的 class，表的定義寫在 TypeScript 裡
Prisma Client：this.prisma.product.findMany()repository：模組 imports 加 TypeOrmModule.forFeature([Product])，service 用 @InjectRepository(Product) 注入，this.products.find()
prisma migrate dev／deploytypeorm migration:generate 比對 entity 產生 migration，migration:run 套用（-d 指向 DataSource 設定檔）；migration 是有 up()／down() 的 TypeScript class，SQL 寫在 queryRunner.query() 裡

接手時先找 TypeOrmModule.forRoot 的設定，看 synchronize 有沒有開：true 會在啟動時直接照 entity 改表，官方文件警告正式環境不要用，可能弄丟資料。再看 migrations 資料夾，跟這課一樣逐句讀 SQL。entity 改了卻沒產生 migration，程式裡的型別和資料庫就對不上，啟動不會報錯，查詢時才出事。

小結

  • Prisma 是一組檔案和指令：你寫 schema.prisma（model、generator、datasource），migrate dev 從它產生進 git 的 migrations/ 並建表，generate 從它產生有型別的 Prisma Client；prisma.config.ts 告訴 CLI 要連哪個資料庫。兩條路互不觸發。
  • 版本寫死 7.10.1：prisma 的 latest 標籤是 8.0 RC；文件看 /docs/orm/v7/。
  • @map／@@map 讓資料庫維持 snake_case；categoryId 是資料庫裡的外鍵欄位，category／products 是只存在 Client 的關聯欄位；金額用 Int；時間加 @db.Timestamptz(3)。
  • Prisma 7 不讀 .env，prisma.config.ts 先 import 'dotenv/config'；migrate dev 不 generate、不 seed，改 schema 的固定三步是改 schema → migrate dev → generate。
  • Prisma 寫不出的（CHECK、改名）用 --create-only 產生草稿再手寫；每個 migration.sql 套用前都要看過，看到 DROP 就停下來。
  • 開發機用 migrate dev，其他環境用 migrate deploy；db push 不留紀錄；migrate reset 刪光資料。migration 檔不是交易：失敗後先手動還原、migrate resolve --rolled-back，再 deploy。
  • PrismaService extends PrismaClient，網址從 ConfigService 拿，在 onApplicationShutdown 呼叫 $disconnect；全應用共用一個連線池，查詢記得 orderBy。
  • 種子資料用 ON CONFLICT DO NOTHING 和依名稱查外鍵寫成可以重複執行，透過 migrations.seed 與 npx prisma db seed 執行。
