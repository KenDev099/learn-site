階段 3：資料庫（Docker、Prisma 7 ＋ PostgreSQL） · 第 18 課

分層、領域邏輯與交易邊界

咖啡店的付款與取消 API 已經能用了，這週同時進來三件事。店長要排程每隔幾分鐘自動取消超過 30 分鐘還沒付款的訂單；行銷要「付款成功送 1 點集點」；客服轉來一則回報：王小明網路慢，連按兩次付款，後台的付款流程跑了兩次。你打開 OrdersController，付款的規則寫在路由裡，取消的規則又抄了一份，三件事都不知道該從哪裡下手。

這三件事卡住的原因是同一個：每段程式放錯了地方。這課拿同一支付款／取消 API 一路重構，每一步解決一個需求：先把規則搬到不依賴框架的地方，排程才能共用；再決定交易從哪裡開始，付款和加點才會一起成功或一起失敗；最後讓資料庫擋下第二次付款。學完之後，遇到一段新程式，你能判斷它該放哪一層，並說得出理由。

這課的路線：
  1. 這段程式的問題出在哪：把三個需求放到肥 controller 上，看它在哪裡卡住。
  2. 四件事該放在哪裡：四層各管一件事，付款規則屬於哪一層（開場問題的最小答案）。
  3. 規則寫成什麼樣子：訂單狀態機寫成不需要 Nest 和資料庫就能測的純函式；接著判斷要不要再包一層 repository。
  4. 付款和加點怎麼一起成功或一起失敗：誰開交易、tx 怎麼傳到別的 service。
  5. 連按兩次付款怎麼只算一次：用條件更新讓資料庫擋下第二次；最後決定失敗時要丟錯誤還是回傳 Result。
這課會用到：
  • TypeScript 課第 27 課的狀態機與 Result：用型別列出訂單所有可能的狀態，只能照規則轉換；Result 把失敗當成回傳值，而不是丟例外。
  • 第 8 課的領域錯誤：service 丟繼承 DomainError 的錯誤，DomainExceptionFilter 決定它變成哪個 HTTP 狀態碼。
  • 第 15 課的互動式交易與條件更新：$transaction(async tx => …) 裡丟例外就整筆回滾；把判斷寫進 UPDATE 的 WHERE，看 count 知道有沒有改到。

這段程式卡住三個需求，問題出在哪？

先看現在的程式。這是練習的起始程式，付款與取消兩個路由，註解標出每一行在做哪一類的事：

@Controller('orders')
export class OrdersController {
  constructor(private readonly prisma: PrismaService) {}

  @Post(':id/pay')
  @HttpCode(200)
  async pay(@Param('id', ParseIntPipe) id: number) {
    const order = await this.prisma.order.findUnique({ where: { id } })          // ① 查資料庫
    if (!order) throw new NotFoundException(`找不到訂單 ${id}`)                   // ② HTTP 細節
    if (order.status !== 'pending') throw new ConflictException('不能付款')      // ③ 業務規則
    return this.prisma.order.update({ where: { id }, data: { status: 'paid' } })  // ④ 寫入
  }

  @Post(':id/cancel')
  @HttpCode(200)
  async cancel(@Param('id', ParseIntPipe) id: number) {
    // 同樣的四步再寫一次，規則換成 pending 或 paid 才能取消
  }
}

它能跑，用 curl 打也會得到正確的回應。問題要把開場的三個需求一個一個放上去才看得出來。

第一個需求：排程要自動取消逾時的訂單。排程（第 21 課）是伺服器自己定時執行的程式，不是從 HTTP 請求進來的：它沒有 @Param，也不會經過 controller。可是「哪些狀態可以取消」這條規則只寫在 cancel 路由的 if 裡，排程要用，只能把判斷抄一份過去。抄了之後，規則就有兩份。哪天店裡加一個「外送中」狀態，你得找遍所有路由和排程，漏改一份就是 bug：App 上取消不了的訂單，排程卻取消掉了。

第二個需求：付款成功送 1 點。集點的資料由 StampCardsService 負責。照現在的寫法，你會在 pay 路由的 ④ 後面再加一段寫入集點卡的程式。controller 裡的資料庫操作從兩個變成三個，而「付款和加點必須一起成功」這件事該由誰保證，從程式上完全看不出來。

第三個需求：連按兩次不能付款兩次。現在的寫法是先讀狀態（①），判斷可以付款（③），再用 id 寫入（④）。兩個付款請求幾乎同時到達時，兩個都在 ① 讀到 pending、都通過 ③、都執行 ④。狀態最後確實是 paid，但付款流程跑了兩次；現在只是付款跑兩次，等加點上線，就會變成加 2 點。這個問題最難，放在最後一節處理。

還有一個平常就會遇到的困擾：想確認「已完成的訂單不能取消」這條規則對不對，得建 Nest 測試模組、準備資料庫、送 HTTP 請求。規則本身只是「哪個狀態可以做什麼」的一張表，卻要整套環境才測得到。

這些問題的根源相同：註解裡的 ①～④ 是四件性質完全不同的事，卻擠在同一個方法裡。它們各自因為不同的理由而改變，也各自需要不同的方式測試。下一節先把這四件事分開。

四件事該放在哪裡？四層各管一件事

上一節的 ①～④ 分別是：查資料庫、決定 HTTP 的回應方式、判斷業務規則、寫入資料庫。把程式依「負責哪一類的事」切成幾塊，就叫分層（layering）。分層有一條方向規則：上層可以呼叫下層，下層不知道上層存在。例如判斷規則的程式不知道自己是被 controller 還是排程呼叫的，所以兩邊都能用它。

要看懂後端常見的四層，先認識兩個詞。

第一個是 use case（使用案例）：使用者想完成的一件事，例如「付款」「取消訂單」。一個 use case 通常包含好幾個步驟：讀訂單、問規則、寫入、加點。這些步驟的順序、哪幾步要包在同一個交易裡，都是這個 use case 自己的事。use case 的名字用業務的動詞，例如 pay、cancel，不用 updateStatus 這種資料表的動詞，因為呼叫的人關心的是「付款」，不是「改了哪個欄位」。

第二個是領域邏輯（domain logic）：業務本身的規則，跟用什麼框架、什麼資料庫無關。判斷方法是問自己：把 Nest 換成 Fastify、把 Prisma 換成手寫 SQL，這段規則還成不成立？「已完成的訂單不能取消」換成什麼技術都成立，所以它是領域邏輯；「找不到訂單要回 404」只在 HTTP 裡才有意義，排程找不到訂單時根本沒有狀態碼可回，所以它屬於 HTTP 層。

有了這兩個詞，四層就是：

層放什麼不放什麼怎麼測
HTTP 層（controller）路由、@Param、DTO 驗證（第 7 課）、狀態碼業務規則、查詢e2e（第 10 課）
應用層（service，一個方法就是一個 use case）步驟順序：讀 → 問規則 → 寫；交易從哪裡開始到哪裡結束HTTP 例外、規則細節整合測試（第 17 課）
領域層（domain）業務規則：狀態轉換、折扣、點數怎麼算任何 I/O：資料庫、HTTP、時間、亂數單元測試，不用 Nest、不用資料庫
資料存取層查詢與寫入。這門課直接用 Prisma Client業務判斷跟著應用層一起用真的資料庫測

這就是開場問題的最小答案。把 pay 的 ①～④ 對回表格：

  • ③「pending 才能付款」換什麼技術都成立，放領域層。controller 和排程都去問它，規則只有一份。
  • ① 查詢和 ④ 寫入屬於資料存取層，這門課就是直接呼叫 Prisma Client。
  • 「讀 → 問規則 → 寫」這個順序，以及之後「付款和加點要在同一個交易」，是付款這個 use case 的事，放應用層的 OrdersService.pay()。
  • ② 的 NotFoundException 是 HTTP 的說法。service 改丟領域錯誤 OrderNotFoundError，由第 8 課的 DomainExceptionFilter 翻成 404；HTTP 層的 controller 只剩取 id、呼叫 service。

分層的目的是把規則集中、讓它好測，不是湊層數。判斷一層該不該存在，就看它有沒有自己的事可做：

如果 controller 呼叫 service、service 呼叫 repository、repository 呼叫 Prisma，而中間兩層都只是原封不動轉呼叫，那兩層就是多餘的。沒有規則可放的時候，少一層也沒關係。
💡 實務上：規則遲早會有第二個入口
咖啡店一開始只有 App 會取消訂單，接著店員後台要能取消、排程要自動取消超過 30 分鐘沒付款的單、客服工具也要能手動處理。規則寫在 controller 裡，每多一個入口就多抄一份，改規則時總有一份忘了改。review 時資深會問：「這段判斷如果改從排程或後台呼叫，還能直接用嗎？」不能的話，就是放錯層了。反過來，單純的查詢列表沒有規則，controller 直接呼叫 service 就好，不用為了分層硬拆。

知道付款規則屬於領域層之後，下一個問題是它具體要寫成什麼樣子，才能讓 controller 和排程都直接用、又不需要任何環境就能測。

付款規則寫成什麼樣子？訂單狀態機寫成純函式

領域層要放的第一條規則，就是肥 controller 裡那兩個 if：哪個狀態可以付款、哪個狀態可以取消。這類規則有一個固定的寫法，叫狀態機（state machine）。

狀態機是一份清單，列出一個東西所有可能的狀態，以及在每個狀態下收到哪個事件會變成哪個狀態。訂單的狀態有「待付款」「已付款」「製作中」等等，事件是「付款」「取消」這類動作。清單上沒列的組合一律不允許。它解決的正是第一節的「規則散落」：與其在每個路由各寫一個 if，不如把所有允許的轉換集中成一張表，所有入口都查同一張表。TypeScript 課第 27 課做過四個狀態的版本，這裡加上店裡製作的流程：

這張圖要寫成程式，而且要寫成純函式。純函式有兩個條件：同樣的輸入永遠得到同樣的輸出；執行時不改變外面的任何東西，也不讀外面會變的東西，也就是不查資料庫、不送 HTTP、不看現在時間。符合這兩個條件，函式就不需要任何環境：測試時直接呼叫，controller、排程、後台也都能直接呼叫。上一節表格裡說領域層「不放任何 I/O」，指的就是這件事。

把圖寫成一張表和一個函式，放在 src/orders/domain/order-state.ts：

import { DomainError } from '../../errors/domain-errors.js'   // 只依賴自己專案的純 TypeScript

export type OrderStatus = 'pending' | 'paid' | 'preparing' | 'ready' | 'completed' | 'cancelled'
export type OrderEvent = 'pay' | 'prepare' | 'ready' | 'complete' | 'cancel'

const TRANSITIONS: Record<OrderStatus, Partial<Record<OrderEvent, OrderStatus>>> = {
  pending: { pay: 'paid', cancel: 'cancelled' },
  // …其他狀態照圖填
}

export function transition(status: OrderStatus, event: OrderEvent): OrderStatus {
  const next = TRANSITIONS[status][event]
  if (!next) throw new InvalidTransitionError(status, event)   // 練習 1 自己寫這個類別
  return next
}

TRANSITIONS 就是那張圖：外層的 key 是目前狀態，內層的 key 是事件，值是下一個狀態。transition 查表，查得到就回傳下一個狀態，查不到就表示這個轉換不允許。這段程式有三個刻意的設計：

  • 輸入是狀態，不是整筆訂單，更不是 id：如果輸入是 id，函式就得自己去資料庫查，它就不再是純函式。所以呼叫的人負責把狀態讀出來再傳進來，函式只做判斷。
  • 型別自己定義：OrderStatus 不從 generated/prisma import。Prisma 的 enum 產生的是同樣的字串聯合，所以應用層把 order.status 傳進來時型別直接相容；但領域層不必知道 Prisma 存在，換掉 Prisma 時這個檔案一行都不用改。
  • 錯誤是領域錯誤：丟 InvalidTransitionError（繼承第 8 課的 DomainError，code 是 INVALID_TRANSITION），不丟 ConflictException。「這是 409」是 HTTP 的決定，交給 DomainExceptionFilter。同一個錯誤被排程呼叫時，根本沒有 HTTP 狀態碼這回事。

好處馬上看得到。6 個狀態乘上 5 個事件，一共 30 種組合，測試不需要 Nest 測試模組，也不需要資料庫，import 這一個檔案就能全部跑完：

import { transition, InvalidTransitionError } from './order-state.js'

it('ready 之後不能取消', () => {
  expect(() => transition('ready', 'cancel')).toThrow(InvalidTransitionError)
})

規則搬走之後，應用層的 service 只剩三個步驟：讀狀態、問規則、寫入。第一版的 cancel 長這樣（pay 只差在事件換成 'pay'）：

// orders.service.ts（第一版，寫入在「連按兩次付款」那一節還會再改）
const ORDER_SELECT = { id: true, customerId: true, total: true, status: true } as const

async cancel(id: number) {
  const order = await this.prisma.order.findUnique({ where: { id }, select: { status: true } })
  if (!order) throw new OrderNotFoundError(id)              // 領域錯誤，filter 翻成 404
  const next = transition(order.status, 'cancel')           // 能不能取消、變成什麼，問領域層
  return this.prisma.order.update({ where: { id }, data: { status: next }, select: ORDER_SELECT })
}

ORDER_SELECT 固定 API 回傳的欄位，也就是 { id, customerId, total, status }，避免把整列資料原樣回給前端；之後每個寫入都用同一份。

controller 只剩轉呼叫，不再注入 PrismaService，也不出現任何狀態字串：

// orders.controller.ts
@Post(':id/cancel')
@HttpCode(200)
cancel(@Param('id', ParseIntPipe) id: number) {
  return this.orders.cancel(id)
}

回到第一個需求：排程要取消逾時訂單時，呼叫同一個 OrdersService.cancel(id) 就好，走的是跟 App 一模一樣的規則。之後加「外送中」狀態，也只要改 TRANSITIONS 一個地方，再補幾個測試。

你可能聽過另一種寫法：把規則寫成訂單類別的方法，例如 order.cancel()。本課為什麼不這樣做，放在課末的補充與查表。

💡 實務上：狀態轉換表就是跟 PM 對齊的文件
訂單、退款、請假單、出貨單，幾乎每個系統都有一張狀態機。PM 問「製作中還能不能取消？」時，打開 TRANSITIONS 就能回答，不用翻好幾個 service。要加新狀態（例如「退款中」）時，先在表上畫出箭頭和 PM 確認，再改表、補測試、加資料庫 enum 的 migration。前端也常需要同一份資訊來決定要不要顯示「取消」按鈕，可以由後端回傳目前允許的動作，不要讓前端自己再寫一份規則。

現在 service 直接呼叫 this.prisma.order。很多教學到這裡會再加一層 repository，把 Prisma 藏起來。這門課要不要跟著加？

service 直接用 Prisma，要不要再包一層 repository？

先說 repository 是什麼。repository 是一個專門負責存取某一種資料的類別，例如 OrdersRepository 提供 findById(id)、updateStatus(id, status)。service 只呼叫它的方法，不直接碰 ORM。它想解決兩件事：同一個查詢不要在好幾個 service 各寫一次；service 的單元測試可以把 repository 換成假的，不用接資料庫。

聽起來划算，所以很多教學把它當成分層的必備。但它也有成本，要看情況：

好處代價
直接用 Prisma少一層；Prisma Client 本身就有型別、就是資料存取層；交易直接傳 tx複雜查詢重複寫在幾個 service；換 ORM 時要改 service
再包 repository同一個複雜查詢只寫一次；service 的單元測試可以換成假的 repository多一層要維護；每個方法都要想辦法接收 tx；只轉呼叫時純粹是成本

表格裡「每個方法都要想辦法接收 tx」這一項，下一節會親眼看到：交易要靠一個 tx 物件傳到每一個寫入，多一層 repository，它的每個方法就都要多收這個參數。至於「service 的單元測試可以換成假的」，第 17 課已經看過 mock 資料存取會漏掉約束、交易、並發這些 bug，service 本來就該用真的資料庫測，這個好處沒有表面上那麼大。

所以本課程的預設是直接用 Prisma。出現下面的情況再抽：同一個帶條件、帶 select 的查詢在三個地方重複；或者真的要換資料來源，例如部分資料改從另一個服務拿。「以後可能換 ORM」不算理由：真的換的時候，交易、錯誤碼、型別都要重寫，多一層也省不了多少。

咖啡店的付款與取消，目前每個查詢都只出現在 OrdersService 一個地方，沒有理由抽。決定好之後，回到第二個需求：付款成功要送 1 點。

付款和加點怎麼一起成功或一起失敗？交易邊界

送點數這件事，跨了兩個 service：付款屬於 OrdersService，集點屬於 StampCardsService。這兩個寫入必須一起成功或一起失敗。想像只成功一半的兩種情況：付款成功但點數沒加，客人會來抱怨；點數加了但付款回滾，就是白送點數。

「一起成功或一起失敗」是第 15 課的交易。這裡的新問題是：交易該由誰開？要回答它，先定義一個詞。交易邊界（transaction boundary）指的是哪些操作必須包在同一個交易裡、交易從哪一行開始到哪一行結束。

原則是由應用層的 use case 決定。看看其他人選：StampCardsService 只知道怎麼加點，不知道自己是被付款、退款還是客服補點呼叫的，它無法判斷該跟誰綁在一起；controller 是 HTTP 層，排程走不到它。只有 pay 這個 use case 知道「付款＋加點」是一件事，所以由它開交易，再把交易傳給別的 service：

// orders.service.ts
pay(id: number) {
  return this.prisma.$transaction(async tx => {
    const order = await this.changeStatus(tx, id, 'pay')
    await this.stampCards.addPoints(tx, order.customerId, 1)   // 同一個 tx
    return order
  })
}

// stamp-cards.service.ts
import type { Prisma } from '../generated/prisma/client.js'

async addPoints(tx: Prisma.TransactionClient, customerId: number, points: number) {
  const card = await tx.stampCard.findUnique({ where: { customerId } })
  if (!card) throw new StampCardNotFoundError(customerId)       // 丟出去 → 整個交易回滾
  await tx.pointTransaction.create({ data: { cardId: card.id, points, reason: '消費' } })
}

changeStatus 是把狀態機那一節 cancel 第一版的「讀狀態 → 問規則 → 寫入」收成的一個私有方法，下一節會把它寫完整。這裡要看的是 tx 怎麼流動：pay 開了交易，拿到 tx；改狀態用 tx，加點也收 tx、只用 tx 查詢和寫入。任何一步丟出錯誤，例如陳美華沒有集點卡、addPoints 丟出 StampCardNotFoundError，整個交易回滾，訂單狀態也跟著退回 pending。

addPoints 的參數型別 Prisma.TransactionClient，就是互動式交易傳進來的 tx 的型別（Prisma 7.10.1 產生的 client 裡有）。它能做的查詢跟 PrismaClient 一樣，但沒有 $transaction、$connect 這些管理用的方法。PrismaService 也符合這個型別，所以「有時在交易裡、有時不用」的方法可以收 db: Prisma.TransactionClient：pay 呼叫時傳 tx，不需要加點的 cancel 呼叫時傳 this.prisma。

為什麼一定要把 tx 傳下去，不能在 addPoints 裡照樣用注入的 this.prisma？因為交易是綁在一條資料庫連線上的，不是綁在 PrismaService 這個物件上：

同一個 PrismaService 不等於同一個交易。addPoints 裡如果寫 this.prisma.pointTransaction.create(…)，這一句會從連線池拿另一條連線，在自己的交易裡立刻 COMMIT。之後付款失敗、外面的交易回滾，這筆點數已經寫進去了。交易綁在連線上，只有透過 tx 送出的查詢才在那個交易裡。

把交易拉長到兩個 service，也要守第 15 課講過的兩條限制。交易進行中，這條連線一直被佔住，寫過的列也一直被鎖著，所以交易內不要呼叫外部 API、寄信，交易越短越好；互動式交易預設 5 秒逾時（timeout: 5000），等鎖等太久也會被中止。

把 tx 一層層傳下去的代價是每個方法多一個參數，換來的是一眼就看得出哪些查詢在交易裡。也有套件能讓交易自動跟著呼叫流程走、不用改方法簽章，本課不採用，原因見課末的補充與查表。

💡 實務上：先問「哪些一定要一起成功」
需求寫著「付款後加點、通知店員、寄收據給客人」時，資深會先把它分成兩類：加點必須跟付款一起成功或一起失敗，放進交易；通知和寄信失敗了可以重試，不該拖住交易，等交易 COMMIT 之後再做。常見的坑是把寄信放進交易：郵件服務慢 3 秒，交易就多佔一條連線 3 秒；寄信成功但後面回滾，客人收到一封付款不存在的收據。review 時看到收 tx 參數的函式裡出現 this.prisma，幾乎都是 bug。

付款和加點現在是同一件事了。但客服回報的那個 bug 還在，而且加點上線後更嚴重：王小明連按兩次，兩個請求各自開了自己的交易，兩個交易都會成功，連按兩次就會直接多送 1 點。交易保證的是「一起成功或一起失敗」，不保證「只做一次」。

連按兩次付款，怎麼讓資料庫只接受一次？條件更新

重複的付款請求不只來自連按。手機網路不穩時前端逾時自動重送、或兩個請求被負載平衡分到兩台伺服器，都會讓同一張訂單同時收到兩次付款。用上一節「先讀再寫」的寫法，時間軸是這樣：

時間請求 A請求 B
1讀到 pending，規則說可以付款
2讀到 pending，規則說可以付款
3update where id → paid，加 1 點
4update where id → paid，又加 1 點

狀態機沒有錯：在時間 2，訂單確實還是 pending，B 問規則得到「可以付款」是對的。錯在「讀」和「寫」之間有空檔，B 在時間 4 寫入時，依據的是一個已經過時的狀態。包在交易裡也擋不住，因為第 15 課講過，預設的 Read Committed 隔離等級下，普通的 SELECT 不上鎖，兩個交易都讀得到 pending。

修法跟第 15 課的樂觀鎖同一個道理：不要讓「判斷」和「寫入」分成兩句，而是把「狀態還是我剛剛讀到的那個」寫進 UPDATE 的條件，讓資料庫在同一句裡比對並寫入。這叫條件更新。上一節提到的 changeStatus 完整寫出來是這樣：

private async changeStatus(db: Prisma.TransactionClient, id: number, event: OrderEvent) {
  const order = await db.order.findUnique({ where: { id }, select: { status: true } })
  if (!order) throw new OrderNotFoundError(id)
  const next = transition(order.status, event)              // 領域層決定能不能、變成什麼
  const { count } = await db.order.updateMany({
    where: { id, status: order.status },                    // UPDATE … WHERE id = $1 AND status = $2
    data: { status: next },
  })
  if (count === 0) throw new OrderStateConflictError(id)    // 寫入前狀態已經被別人改掉 → 409
  return db.order.findUniqueOrThrow({ where: { id }, select: ORDER_SELECT })
}

照著時間軸再走一次。A 和 B 都讀到 pending，都送出 UPDATE … WHERE id = 1 AND status = 'pending'。A 先改到這一列，取得這一列的寫鎖（PostgreSQL 課第 19 課）；B 的 UPDATE 要改同一列，只能等 A 的交易結束。A 提交後，PostgreSQL 在 Read Committed 下會用最新的資料重新檢查 B 的 WHERE：這時狀態已經是 paid，條件不成立，影響 0 列。B 看到 count 是 0，丟出 OrderStateConflictError，B 的交易回滾，連帶 B 的加點也不會發生。結果是付款一次、點數一點，第二個請求收到 409。

這裡用 updateMany 而不是 update，是因為兩者在「條件不成立」時的行為不同。update 的 where 找不到列時會丟 P2025（第 14 課），你分不出是訂單不存在還是被別人搶先；updateMany 則回傳 count，讓你自己判斷並丟出意思明確的領域錯誤。

cancel 也走同一個 changeStatus，所以 where 裡的狀態一定要用剛讀到的值，不能寫死 'pending'：已付款的訂單也要能取消，寫死的話它永遠影響 0 列。

有人會想在程式裡自己排隊，例如每張訂單一個 Promise，前一個付款跑完才讓下一個進來。這擋不住重複付款：

不要用記憶體鎖（例如每張訂單一個 Promise 排隊）。它只管得到同一個 Node 程序；正式環境通常有好幾台伺服器、或同一台跑好幾個程序，請求打到不同台時鎖就不存在了。並發要交給所有程序共用的東西：資料庫的條件更新、列鎖，或之後課程的分散式鎖。
💡 實務上：每個寫入都先想「被執行兩次會怎樣」
重複請求比想像中常見：使用者連點、手機網路不穩時前端逾時自動重送、金流商沒收到回應就重送付款通知。前端把按鈕停用可以減少，但擋不住全部，最後一道防線一定在後端。收到 409 時，前端比較好的處理是重新讀取訂單、顯示目前狀態（「這張單已經付款了」），而不是跳出一個看不懂的錯誤。付款、扣庫存、發點數這類動到錢或數量的操作，資深在設計 API 時就會先確認重複執行是否安全。

三個需求到這裡都解決了。回頭看，最後兩節都靠同一件事運作：OrderStateConflictError、StampCardNotFoundError 一丟出去，交易就回滾，filter 就翻成對應的狀態碼。「失敗時丟錯誤」本身是一個選擇，另一種做法是回傳 Result。

失敗時丟錯誤還是回傳 Result？全專案選一種

領域函式遇到「不允許」，有兩種表達方式。一種是這課一直在用的丟領域錯誤；另一種是 TypeScript 課第 27 課的 Result：函式不丟例外，而是回傳一個物件，成功時是 { ok: true, value }，失敗時是 { ok: false, error }，呼叫的人檢查 ok 決定怎麼做。

丟領域錯誤（第 8 課）回傳 Result（TypeScript 課第 27 課）
寫法throw new InvalidTransitionError(…)return { ok: false, error: 'INVALID_TRANSITION' }
好處在交易裡丟出就自動回滾；filter 統一轉成回應；呼叫端程式短型別上看得到可能失敗，呼叫端不處理會被編譯器提醒
代價從簽章看不出會丟什麼每一層都要檢查、往上傳；在 $transaction 裡要記得自己丟例外才會回滾

表格最後一格用這課的程式說明最清楚。如果 addPoints 改成沒有集點卡時回傳 { ok: false }，而 pay 忘了檢查，$transaction 的 callback 就會正常結束，交易照常 COMMIT：訂單已付款，點數沒加，正是交易邊界那一節要避免的結果。用 Result 時，在交易裡每一步都要檢查，失敗就自己丟例外。

兩種都可以，重點是全專案用同一種。混著用時，呼叫的人每次都要去看實作才知道該 try/catch 還是檢查 ok，漏掉的那邊就是 bug。這門課用丟領域錯誤，因為它跟 Prisma 交易的回滾機制、Nest 的 filter 配合得最直接。

到這裡，肥 controller 已經拆成四層：規則在 order-state.ts，步驟和交易在 OrdersService，controller 只轉呼叫，寫入用條件更新。下面的練習就是把這個重構親手做一次。

練習

練習在 nestjs/practice 的第 18 題。要先 docker compose up -d --wait（第 12 課）。想自己用 curl 試：在 work/18 執行 npx prisma migrate deploy、npx prisma db seed，再 npm run start:dev，例如 curl -X POST localhost:3100/orders/1/pay。種子資料裡王小明有集點卡、陳美華沒有。

練習 1：把 OrdersController 裡的狀態判斷抽出來。

  • 在 order-state.ts 照上面的狀態圖寫出 transition(status, event)：合法時回傳下一個狀態，不合法時丟 InvalidTransitionError（自己寫並匯出，繼承 DomainError，code 是 'INVALID_TRANSITION'）。這個資料夾不能 import @nestjs/* 或 Prisma。
  • 在 OrdersService 寫 pay(id) 與 cancel(id)：讀訂單（不存在丟 OrderNotFoundError）→ transition → 寫入，回傳 { id, customerId, total, status }。這一題先用 update 寫入也可以，練習 2 再改。

練習 2：同一張訂單並發付款只能成功一次。把寫入改成條件更新：updateMany 的 where 同時比對 id 和剛剛讀到的狀態，count 是 0 就丟 OrderStateConflictError（409 ORDER_STATE_CONFLICT）。測試會開兩個 Nest 應用接同一個資料庫，同時送 5 次付款：只能有 1 次 200，其他 409。只在一個程序裡有效的記憶體鎖過不了。cancel 也走同一個條件更新，所以 where 裡的狀態要用剛讀到的值，不能寫死 'pending'：已付款的訂單也要能取消。

練習 3：付款成功時送 1 點。把 StampCardsService.addPoints 改成 addPoints(tx, customerId, points)，裡面只用 tx；OrdersService.pay 用 this.prisma.$transaction(async tx => …) 把改狀態和加點包在一起（cancel 不用改）。顧客沒有集點卡時，addPoints 丟的 StampCardNotFoundError 會讓 API 回 422，訂單必須還是 pending。測試也會檢查加點時有沒有碰到 this.prisma，以及同時付款 5 次是否只加 1 點。

練習 4：新規則「會員打九折」應該放在哪？

✓ c。折扣是業務規則，換框架、換 ORM 都成立，所以放領域層：純函式，單元測試直接驗。放 controller（a）的話，之後從排程、後台、批次匯入建立的訂單都不會打折，規則還得抄好幾份；寫在 Prisma 參數裡（b）就把規則和資料存取混在一起，測規則得接資料庫；filter（d）只處理例外，跟計價無關。

練習 5：什麼情況下值得在 Prisma 外面再包一層 repository？

✓ b。repository 有成本：多一層、每個方法都要能接收 tx。有重複的查詢可以集中、或有替換資料來源的實際需求時，這個成本才划算。a 是教條，沒有規則或重複時只是轉呼叫；c 是為想像中的需求付費，真的換 ORM 時交易與錯誤處理照樣要重寫；d 太絕對，查詢重複到一定程度時集中起來是值得的。

練習 6：pay 用 this.prisma.$transaction(async tx => …) 開了交易，但 addPoints 裡寫的是 this.prisma.pointTransaction.create(…)。加點之後，同一個交易裡的下一步失敗了，會怎樣？

✓ a。交易綁在連線上，Prisma 7 不會自動傳遞交易：只有透過 tx 送出的查詢在那個交易裡。this.prisma 從連線池拿另一條連線，那一句自己提交了。b 是最常見的誤解（自動傳遞要靠 AsyncLocalStorage 類的套件，而且要用它提供的 txHost.tx）；c、d 都不是 Prisma 的行為：外面的交易照樣回滾，只是回滾不到另一條連線上已經提交的東西。

常見錯誤

  • controller 越來越肥：查詢、規則、HTTP 細節擠在一起，別的入口用不到、測試要整套環境。controller 只取參數、呼叫 use case、回應。
  • 領域函式偷偷 import Prisma 或 Nest：為了省事 import Prisma 的 enum 型別、丟 ConflictException，規則就綁死在框架上。型別自己定義、錯誤丟 DomainError。
  • 為了分層而分層：controller → service → repository → Prisma，中間每層都只是轉呼叫。沒有規則或重複查詢可放的層，不要建。
  • 在 tx 之外寫入應該一起回滾的資料：helper 裡用了 this.prisma，或交易結束後才加點。需要一起成功的寫入，全部用同一個 tx，由開交易的 use case 傳下去。
  • 先讀狀態、再用 id 更新：狀態機判斷正確也擋不住並發。寫入的 where 要帶上剛讀到的狀態，count 為 0 就回 409。
  • 用記憶體鎖解決跨台伺服器的並發：只對同一個程序有效。交給資料庫。
  • 錯誤處理風格混用：有的丟例外、有的回傳 Result，呼叫的人一定會漏處理一邊。選一種，全專案一致。

補充與查表

規則寫成類別的方法，還是獨立的領域函式？

還有一種寫法是把規則做成類別的方法（order.cancel()），資料和規則放在一起。資料與規則分開放的寫法有個名字叫貧血模型（anemic model）：資料物件只有欄位，規則都在 service。本課的狀態機也是資料與規則分開，但規則集中在領域函式裡，不是散在 service 中，已經拿到主要的好處：集中、好測。用 Prisma 時查詢回來的是普通物件，不是類別實例，硬要包成有方法的類別，就得在每次查詢後轉換一次。

不傳 tx 的另一種做法：AsyncLocalStorage

另一種做法是用 AsyncLocalStorage（Node 課第 19 課）把目前的交易存在「這次呼叫的上下文」裡，例如 nestjs-cls 的 @nestjs-cls/transactional 外掛搭配 @nestjs-cls/transactional-adapter-prisma：在方法上加 @Transactional()，裡面透過注入的 TransactionHost 用 txHost.tx 查詢，自動拿到目前的交易；不在交易裡時，txHost.tx 就是一般的 client。好處是不用改方法簽章；代價是多三個套件、一層看不見的機制：同一行 txHost.tx.order.update() 在不同呼叫路徑下可能在交易裡、也可能不在，出問題時很難從程式碼看出來。本課程一律明確傳 tx，不另外安裝。

小結

  • 肥 controller 的問題是四件性質不同的事擠在一起：查詢、HTTP 細節、業務規則、寫入。規則只寫在路由裡，排程這類第二個入口就只能抄一份。
  • 四層：HTTP 層處理請求與回應；應用層（service）一個方法一個 use case，協調步驟並決定交易邊界；領域層是不做 I/O 的純函式；資料存取層這門課直接用 Prisma。
  • 判斷是不是領域邏輯：換掉框架和 ORM，這條規則還成立嗎？
  • 訂單狀態機寫成 transition(status, event)：一張表、一個函式，非法轉換丟 InvalidTransitionError，不需要 Nest 或資料庫就能測完所有組合。
  • repository 不是必備：有重複的複雜查詢、或要換資料來源時再抽。
  • 跨 service 的交易：use case 開 $transaction，把 tx（型別 Prisma.TransactionClient）明確傳下去；this.prisma 是另一條連線、另一個交易。
  • 交易保證一起成功，不保證只做一次。防重複付款：updateMany({ where: { id, status: 讀到的狀態 } })，count 為 0 就是被別人搶先，回 409；記憶體鎖跨不了程序。
  • 錯誤風格（丟領域錯誤或回傳 Result）全專案只用一種；用 Result 時，在交易裡要自己丟例外才會回滾。

階段檢核：面試會問的觀念

練習 7：拿鐵只剩 5 杯，20 個人同時下單。扣庫存已經包在交易裡，哪裡會出事？

await this.prisma.$transaction(async (tx) => {
  const p = await tx.product.findUnique({ where: { id } })
  if (p.stock < qty) throw new OutOfStockError()
  await tx.product.update({ where: { id }, data: { stock: p.stock - qty } })
})

✓ c。「讀 → 判斷 → 寫回」會 lost update，預設的 READ COMMITTED 交易不會阻止兩個交易讀到同一個值。改成原子條件更新：updateMany 的 where 加 stock: { gte: qty }、data 用 decrement，count 是 0 就是庫存不足。a 錯在普通 SELECT 不上鎖，請求根本不會排隊，問題正是沒有人在等。（第 15 課）

練習 8：顧客註冊時，程式先用 findUnique 查 email 有沒有人用，沒有才 create。上線後 log 偶爾出現 P2002，客人看到 500。怎麼修最恰當？

✓ a。查詢和寫入是兩句 SQL，兩個請求可以都查不到、都去 INSERT；只有 UNIQUE 約束在寫入的那一刻檢查。所以唯一值交給約束，P2002 在 service 翻成領域錯誤。b 錯在 READ COMMITTED 的交易擋不住兩個請求都查不到，第二個照樣撞上 P2002。（第 14 課）

練習 9：同事把「呼叫外送平台 API 建立配送單」放進下單的 $transaction callback 最後一步，理由是「API 失敗就整筆回滾，資料最一致」。問題在哪？

✓ d。交易只能回滾資料庫自己的修改，外部系統做過的事收不回來；外部呼叫又慢，其他客人排隊等鎖、連線池被佔滿。交易只做資料庫的事，COMMIT 之後再呼叫外送平台。b 只想到 API 失敗的情況：API 成功、交易後來逾時（P2028）回滾時，就有配送單卻沒有訂單。（第 15 課）

練習 10：咖啡店後台這次上線要加一個新欄位，migration 已經 commit。正式資料庫的 migration 該怎麼套用？

✓ b。migrate deploy 只套用 commit 過、還沒套用的檔案，不產生、不重設；migrate dev 發現資料庫和 migration 對不上時會要求重設，只用在開發機。a 錯在 migration 一失敗每台伺服器都起不來，也很難從各台的 log 追出原因。（第 13 課）

練習 11：訂單列表 API 隨著訂單變多越來越慢，整個請求要 800 毫秒；log 裡每一句 SQL 用 EXPLAIN 看都是 Index Scan、不到 1 毫秒。先查什麼？

✓ d。每句都快、整體卻慢，而且跟著資料量變慢，典型是 N+1：句數隨訂單數成長，時間花在一句句的往返。用 $on('query') 數句數，改成 select／include 帶回關聯，Prisma 7 每層關聯一句 IN (...)。c 錯在句數沒變，一個請求還同時佔用多條連線。（第 16 課）

練習 12：下面三段程式，哪一段最需要接真的 PostgreSQL 寫整合測試？

✓ a。條件更新對不對，取決於資料庫怎麼執行這句 SQL、並發時怎麼重新檢查 WHERE；mock 只回傳你設定的 count，永遠會通過。b 是不做 I/O 的純函式，單元測試就能測完所有組合，不需要資料庫。外部服務（c）才是 mock 該用的地方。（第 17 課）

練習 13：InventoryService.reserve 裡用 this.prisma.product.updateMany 扣庫存。下面的 order.create 因為外鍵錯誤（P2003）失敗時，會怎樣？

async create(dto: CreateOrderDto) {
  return this.prisma.$transaction(async (tx) => {
    await this.inventory.reserve(dto.items)
    return tx.order.create({ data: toOrderData(dto) })
  })
}

✓ c。交易綁在連線上，Prisma 7 不會自動傳遞交易，只有透過 tx 送出的查詢在那個交易裡。改成 reserve(tx, items)，裡面只用 tx；交易邊界由應用層的 use case 決定。a 錯在「在 callback 裡呼叫」不等於「在交易裡執行」。（第 18 課）

練習 14：手機 App 的「我的訂單」往下捲就載入更多，最新的排最前面，客人隨時可能再下單。分頁怎麼做？

✓ b。OFFSET 只記「跳過幾筆」：越後面越慢，新訂單插在最前面時整個列表往後推，下一頁會重複。cursor 從上一頁最後一筆之後接著查，不受新資料影響；排序值可能相同，要加 id 決勝，否則同一時間的訂單跨頁時會漏掉（c）。a 錯在固定順序只解決排序，資料一變動 OFFSET 照樣錯位。（第 16 課）
