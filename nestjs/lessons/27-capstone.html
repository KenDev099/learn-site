階段 5：上線、維運與架構（資深） · 第 27 課

期末專題：咖啡店訂單 API

星期六早上，王小明在咖啡店的 Vue 前台點了兩杯拿鐵，一共 220 元。他按下「下單」時捷運剛好進隧道，請求逾時，前端自動重送了一次。付款完成後，金流公司沒有及時收到我們的回應，同一個付款通知（webhook）送了三次。負責加點的 worker 寫完點數、回報之前連線逾時，工作被重試。那天下午部署新版本，Redis 也跟著重啟了一次。

這些事單獨看都不稀奇，正式環境每天都在發生。麻煩的是它們全部落在同一張訂單上：任何一環沒接好，王小明就會多一張訂單、多扣一次庫存、拿到 4 點而不是 2 點、收到兩封收據，或是付了錢卻什麼都沒發生。這一課只有一個任務：不管途中重送幾次、哪個元件重啟，王小明最後剛好有一張已付款的訂單、2 點、一封收據；而且要用測試與上線檢查證明，下個月有人改了程式，這件事仍然成立。

這課不教新語法。前面 26 課每課練一個零件：DI、驗證、交易、快取、佇列、排程、webhook、OpenAPI、健康檢查、關機、模組邊界。這裡把它們裝進同一條結帳流程，練資深工程師每天在做的三件事：盤點每一步會怎麼失敗、決定狀態存在哪裡、用測試和檢查清單證明它能上線。每一節都會標出用到的是哪一課。

這課的路線：
  1. 王小明的訂單經過哪些地方、每一步斷掉會怎樣：六個模組、兩條進來的路，以及為什麼每一個對策最後都落在 PostgreSQL 的交易與唯一約束。
  2. 下單送了兩次：Idempotency-Key 是什麼，怎麼讓重送拿回第一次的結果；兩個重送同時到、第一次就失敗時又怎麼辦。
  3. 付款通知送了三次、Redis 剛好重啟：為什麼交易裡只寫 PostgreSQL，送進佇列的事交給 outbox。
  4. 加點的工作被重試：worker 怎麼讓重試直接成功，而不是失敗三次把值班的人叫起來。
  5. 怎麼證明、能不能上線：用 e2e 測試保護這條流程，上線前逐項檢查請求以外的事。
這課會用到：
  • 第 15 課的互動式交易與原子扣庫存：交易裡的寫入一起 commit 或一起回滾；扣庫存用帶條件的 UPDATE，不先讀再寫。
  • 第 20 課的佇列與 outbox：佇列至少執行一次，所以 worker 要冪等；在同一個交易裡把要送的訊息寫進 outbox 表，再由 relay 送進佇列，就不會漏。
  • 第 22 課的 webhook：先驗簽章，再用 webhook_events.event_id 的唯一約束讓重送的同一個事件只處理一次。
  • 第 10 課的 e2e 測試：用 configureApp 建出跟正式環境一樣設定的應用，再用 supertest 送真的 HTTP 請求。

王小明的訂單會經過哪些地方？

要讓一張訂單不出錯，得先知道它從頭到尾經過哪些程式、每一份資料存在哪裡。專題的程式分成六個功能模組，資料歸屬在第 26 課定下，每張表只有一個模組會讀寫它：

  • catalog：商品與菜單。
  • orders：顧客、訂單，以及這一課要用到的 idempotency_keys。
  • payments：接收金流公司的 webhook，記錄處理過的 webhook_events。
  • loyalty：集點卡與點數明細，規則是第 26 課的每滿 100 元 1 點，所以王小明的 220 元是 2 點。
  • notifications：寄電子收據。
  • outbox：把交易裡寫下的訊息送進 BullMQ 佇列。

模組之間的依賴只往一個方向：payments 依賴 orders（要把訂單標成已付款）和 outbox（要寫下待送的訊息）；loyalty 與 notifications 只認得 outbox/events.ts 裡的事件型別，不知道是誰發的。這是第 26 課用事件解開循環 import 的結果：之後集點規則改了，只需要動 loyalty。

王小明的訂單沿著下圖走三段路。第一段，前台送 POST /api/v1/orders 進 orders，在一個交易裡記下這次請求、扣庫存、建訂單、存回應。第二段，付款成功後金流公司送 webhook 進 payments，在一個交易裡把訂單改成已付款、記下這個事件、寫下兩則待送的訊息。第三段，OutboxRelay 每秒把還沒送出的訊息送進 loyalty 與 notifications 兩個佇列，各自的 worker 加點、寄收據。

圖下方那句話是這課設計的核心，後面會一再回到它：左半邊兩條進來的路只碰 PostgreSQL，所以 Redis 掛了，下單與付款照樣成功；需要 Redis 的工作交給 relay 稍後補送。為什麼要這樣切，下一節把失敗點列出來就會看到。

起始專案已經能啟動，十張表的 migration 都寫好了，不用改 schema。這一課要你改的是五個地方：OrdersService.create、PaymentsService.handle、LoyaltyService.earnForOrder、test/checkout.e2e-spec.ts，以及練習 4 上線前檢查會點名的幾個檔案。

圖上每一個箭頭都是一次網路呼叫或一次寫入，每一個都可能斷。動手改這五個地方之前，先把「斷在這裡會怎樣」逐一列出來。

每個箭頭斷掉會怎樣？先盤點，再寫程式

資深工程師接到「下單、付款、集點、收據」這種需求，第一件事不是寫程式，而是沿著上一節的圖一步一步問：這裡掛了會怎樣、客人會看到什麼。這個動作叫失敗點盤點。它把「上線後才會被客人發現的事」提前到設計階段，而且每一列都會直接變成一個要寫的對策、一個要寫的測試。

下表是王小明那張訂單會經過的步驟。右欄是這一課的對策與對應的練習；現在看不懂對策沒關係，後面每一節會講其中一兩列：

看完整張表，前六列的對策其實是同一句話：把「這件事做過了沒」這個狀態放進 PostgreSQL，用交易和唯一約束保證只發生一次。為什麼不用更直覺的做法？直覺的做法有兩種，都擋不住：

  • 記在程序的記憶體裡，例如用一個 Set 記住處理過的 key。正式環境通常同時跑好幾台伺服器，重送的請求可能被送到另一台，那一台的 Set 是空的；部署或重啟之後，所有台的 Set 也一起清空。
  • 先查資料庫，沒有才寫。查和寫是兩個動作，中間有空檔：兩個同時進來的請求可能都在對方寫入之前查詢，兩個都查到「沒有」，於是各寫一筆。

唯一約束沒有這個空檔：「有沒有重複」的判斷和寫入，是資料庫在同一個動作裡完成的，不管請求從哪一台伺服器來、同時來幾個，同一個值最後只有一筆寫得進去。交易則保證相關的幾筆寫入一起成功或一起失敗，不會留下寫了一半的狀態。兩者合起來，就是這張表每一列的最後一道防線。

💡 實務上：這張表就是技術設計文件的核心
在團隊裡，這種盤點通常寫在開工前的技術設計文件（tech spec）或 PR 說明，讓 reviewer、PM、維運一起看。PM 關心客人會看到什麼（重複扣款、沒收到收據），維運關心出事時怎麼發現、怎麼補救。資深工程師會逐列追問：這種情況多常發生？發生了有沒有告警？能不能手動補？保護強度跟著後果走：收據漏寄一封，客服可以補寄；重複扣款就一定要在系統裡擋住。

下單送了兩次，怎麼只建一張訂單？

盤點表的第一列就是王小明早上遇到的事：前端送出下單後逾時，自動重送。從伺服器的角度看，難處在於它分不出兩件事：「這是同一次下單的重送」，還是「王小明真的想再點兩杯拿鐵」。兩個請求的內容一模一樣，只看內容是分不出來的。

能分辨的只有前端，因為只有前端知道自己在重送。冪等鍵（Idempotency-Key）就是把這個資訊帶給伺服器的方法：前端在客人確定要下這一單時，產生一個隨機字串（例如用 crypto.randomUUID()），放在 Idempotency-Key 這個 HTTP header 送出；逾時重送時帶同一個字串。伺服器記住每一個處理過的 key，看到同一個 key 再來，就不再下單，而是把第一次的結果再送一次。這樣不管送幾次，效果都跟送一次一樣，這種性質就叫冪等（idempotent）。系統設計課第 9 課講過原理，這一節是 NestJS 加 Prisma 的實作。

要把它做對，有三個設計決定要先想清楚，每一個都對應練習 1 的判分項目。

key 一定要帶，沒帶就拒絕

沒帶 key，或格式不對（只接受 1–64 個英數字、-、_），直接回 400 IDEMPOTENCY_KEY_REQUIRED。這看起來很嚴格，但另一種做法「沒帶就由伺服器自動產生一個」等於沒有保護：重送的請求一樣沒帶 key，伺服器又產生一個新的，對伺服器來說那是一個全新的請求，照樣多一張訂單。保護只有在前端真的帶 key 時才成立，所以伺服器要強制。

key 要綁定請求內容

伺服器除了記 key，也要記下請求內容的指紋。做法是把內容算成 SHA-256 雜湊：同樣的輸入一定得到同樣的一串值，內容差一點點，結果就完全不同。這個值存在 requestHash 欄位。

同一個 key 配上不同的內容，代表前端把舊 key 用在新的一單上，多半是前端的 bug，例如購物車改了卻沒換 key。這時回 422 IDEMPOTENCY_KEY_REUSED，讓前端馬上知道。如果默默回傳舊訂單，王小明以為點了三杯，實際只有兩杯，bug 也被藏起來了。

雜湊之前要自己挑欄位、固定順序，答案用的是 customerId 和每個品項的 productId、quantity。直接雜湊收到的原始 JSON 的話，{"customerId":1,"items":…} 和 {"items":…,"customerId":1} 意思一樣，雜湊值卻不同，會被誤判成換了內容；多一個空白、換行也一樣。所以自己挑欄位、固定順序再雜湊，key 順序與空白都不會影響結果。

存回應，不是重新查

重送時要送回的是「第一次那個請求的回應」：同樣的狀態碼（201）、一字不差的內容。所以第一次成功時，把狀態碼和回應字串存進 responseStatus、responseBody，重送時直接拿出來送。

另一種做法是重送時依 key 找到訂單、再查一次送回去。聽起來一樣，其實不同：王小明付款之後，如果前端又重送了一次，重新查會拿到 paid；但前端在等的是「那一次下單」的結果，也就是當時的 pending。同一個請求兩次拿到不同的回應，前端的邏輯就可能走錯分支。

responseBody 用 text 欄位存原始字串，不用 PostgreSQL 的 jsonb。jsonb 會把 JSON 轉成內部格式儲存，取出來時 key 的順序會重排，就做不到一字不差。

這三個決定處理的是「依序」的重送：第一次做完了，第二次才到。但王小明的重送不一定等第一次做完才到，第一次也不一定會成功。

兩個重送同時到、或第一次就失敗了呢？

先看同時到。前端逾時重送時，第一個請求其實可能還在伺服器裡跑：它正在扣庫存，第二個請求就進來了。如果程式寫成「先查 idempotency_keys 有沒有這個 key，沒有才下單」，就是上一節說的先查再寫：兩個請求都查到沒有，各下一張單。

解法是讓資料庫來裁決誰先。key 是 idempotency_keys 表的主鍵，交易的第一步就 create 這一列。後到的交易插入同一個 key 時，會在資料庫裡等先到的交易提交；先到的提交之後，後到的插入違反主鍵、失敗。Prisma 把這種「違反唯一約束」的錯誤包成錯誤碼 P2002 丟出來。程式接住 P2002，就知道這個 key 有人處理過或正在處理，改去讀存下來的那一列，依序檢查：

  • requestHash 跟這次不同：同一個 key 換了內容，丟 IdempotencyKeyReusedError，回 422。
  • 存下來的回應還是 null：第一個還沒做完，丟 IdempotencyKeyInProgressError，回 409 IDEMPOTENCY_KEY_IN_PROGRESS。
  • 都沒問題：回傳存下來的狀態碼與內容。

再看第一次就失敗。假設拿鐵剛好只剩一杯，王小明的下單因為庫存不足失敗了。店員補貨後，前端用同一個 key、同樣的內容重試，應該要成功。因為 key 和訂單寫在同一個交易裡，庫存不足丟出錯誤時整個交易回滾，key 那一列也跟著消失，重試就跟第一次一樣。如果把寫 key 放在交易外面先提交，下單失敗只回滾交易裡的部分，key 留在表裡、回應是 null，之後每次重試撞 P2002 都被當成「處理中」，補貨後怎麼重試都是 409。

把兩節的決定合起來，OrdersService.create 寫成程式是這樣：

// orders.service.ts
if (!key || !KEY_FORMAT.test(key)) throw new IdempotencyKeyRequiredError()
const requestHash = hashRequest(dto)
try {
  return await this.prisma.$transaction(async tx => {
    await tx.idempotencyKey.create({ data: { key, requestHash } })   // 第一步：搶 key
    const body = JSON.stringify(await this.placeOrder(tx, dto))      // 第 15 課的扣庫存、建訂單
    await tx.idempotencyKey.update({ where: { key }, data: { responseStatus: 201, responseBody: body } })
    return { status: 201, body }
  })
} catch (e) {
  if (!(e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2002')) throw e
}
// 撞到主鍵：有人處理過（或正在處理）
const saved = await this.prisma.idempotencyKey.findUniqueOrThrow({ where: { key } })
if (saved.requestHash !== requestHash) throw new IdempotencyKeyReusedError(key)
if (saved.responseStatus === null || saved.responseBody === null) throw new IdempotencyKeyInProgressError(key)
return { status: saved.responseStatus, body: saved.responseBody }

catch 只攔 P2002。庫存不足這類錯誤原樣丟出去：交易已經回滾，錯誤交給 exception filter 轉成對應的狀態碼。

Controller 也要跟著改。平常 controller return 一個物件，Nest 會替你序列化成 JSON，用預設的狀態碼送出。這裡兩樣都不行：狀態碼要用存下來的那個，內容要送存下來的原始字串。所以用 @Res() 拿到回應物件，自己送出：

@Post()
async create(@Headers('idempotency-key') key: string | undefined, @Body() dto: CreateOrderDto, @Res() res: Response) {
  const saved = await this.orders.create(dto, key)
  res.status(saved.status).type('application/json').send(saved.body)
}
三個領域錯誤 IdempotencyKeyRequiredError、IdempotencyKeyReusedError、IdempotencyKeyInProgressError 已經在 src/errors/domain-errors.ts，DomainExceptionFilter 會轉成 400、422、409。service 只丟錯誤，不碰狀態碼（第 8 課）。
💡 實務上：前端在「購買意圖」產生 key，不是每次點擊
身為前端，key 的另一半通常是你負責。結帳頁確定購物車內容時產生一次，逾時重試、客人連點按鈕都帶同一個；購物車內容改了就換新 key，否則會撞 422。收到 409 代表第一次還在處理，前端應該稍等再用同一個 key 重送，而不是顯示「下單失敗」讓客人重新下單。串接金流（例如 Stripe）時，你也會在對方的 API 文件看到同樣的 Idempotency-Key header，概念一模一樣。

付款通知送了三次、Redis 又剛好重啟，點數和收據會不會漏？

王小明的訂單只建了一張，接著他付款。金流公司付款成功後，會送一個 webhook 通知我們。同一個事件送三次這件事，第 22 課已經處理好了，起始專案也寫好了：先驗簽章，再用 webhook_events.event_id 的唯一約束讓同一個事件只處理一次。這一節要處理的是「處理」之後的事：付款成功要觸發加點與寄收據，這兩件事走 BullMQ 佇列，而佇列存在 Redis 裡。

起始專案的 PaymentsService.handle 是這樣做的：在一個交易裡把訂單改成 paid、記下 webhook 事件；交易提交之後，再呼叫 publisher.publish 把工作送進佇列。這是兩次寫入，寫到兩個不同的地方，一次寫 PostgreSQL、一次寫 Redis。PostgreSQL 的交易管不到 Redis，兩次寫入沒辦法一起成功或一起失敗，中間任何一點出事，兩邊就不一致。這就是第 20 課說的雙寫問題，第 20 課練習 7 問過這樣安不安全，答案是不安全。放到王小明身上，會出兩種事：

  • 提交之後、送進佇列之前，程序當機，例如剛好碰上部署。訂單已經是 paid，但工作沒進佇列，2 點和收據永遠不會出現，也沒有任何程式會再試。
  • webhook 進來時 Redis 正在重啟。publish 丟錯，handle 回 5xx；金流公司看到失敗會重送，但 event_id 在剛才提交的交易裡已經記錄了，重送被當成重複。這次的點數與收據就真的遺失了，而且是被我們自己的防重複機制擋掉的。

對策是第 20 課的 transactional outbox。它的想法是：既然 Redis 不能參與 PostgreSQL 的交易，交易裡就完全不碰 Redis，改成把「要送出的訊息」也當成資料，在同一個交易裡寫進 PostgreSQL 的 outbox_events 表。這樣「訂單變 paid」和「有訊息要送」一定一起提交、一起回滾。真正送進佇列的事交給 OutboxRelay：它用第 21 課的 @Interval(1000) 每秒撈出還沒送出的訊息，送進佇列、標記為已送，已經寫好了。Redis 這時連不上也沒關係，訊息還在表裡，下一秒再試。

handle 改成這樣：

await this.prisma.$transaction(async tx => {
  const order = await this.orders.markPaid(tx, event.data.orderId)        // 第 18 課的條件更新，沒改到回 null
  await tx.webhookEvent.create({ data: { eventId: event.id, type: event.type, status: order ? 'processed' : 'ignored' } })
  if (!order) return
  const payload = { orderId: order.id, customerId: order.customerId, total: order.total }
  await this.outbox.add(tx, { type: 'order.paid', payload }, { type: 'receipt.requested', payload })
})

三件事在同一個交易：訂單變 paid、記下事件、寫兩筆 outbox。要嘛全部發生，要嘛都沒發生。OutboxService.add 一定要傳交易的 tx；在 $transaction 外面用 this.prisma.outboxEvent.create 寫，就又變成兩次獨立的寫入，回到雙寫問題。markPaid 沒改到訂單（已經付過或取消了）時回傳 null，這時只記下事件、標成 ignored，不寫 outbox，同一張訂單就不會因為另一個事件 id 再加一次點。

relay 自己也可能重複送：送到一半當機，下次會再送一次同一筆。它把 outbox 的 id 當成佇列工作的 jobId，佇列看到同一個 jobId 就不會再建一個工作；多台伺服器同時跑 relay 時，用 FOR UPDATE SKIP LOCKED 讓每一列只被一台拿走。這部分已經寫好，原理在第 20 課。

payload 只放處理的人需要的事實：{ orderId, customerId, total }。loyalty 的 worker 拿到 total: 220 就能算出 2 點，不必回頭查訂單，也就不必認識 orders 模組（第 26 課）。

另一個常見的誘惑：「加點在同一個交易裡直接做，最簡單、最原子」。做得到，但 payments 就要碰 stamp_cards 與 point_transactions，資料歸屬被打破；之後集點規則改成「生日加倍」，要改的是付款的程式。第 26 課用事件打破循環，這裡一樣：付款只宣告「訂單付款了」，誰要處理自己去接。

到這裡，王小明的付款一定會變成兩個送進佇列的工作，一個都不會漏。但佇列為了不漏，給的保證是「至少執行一次」，同一個工作有可能被執行兩次。

加點的工作被重試了，怎麼不加兩次點、也不算失敗？

BullMQ 執行一個工作的流程是：worker 從 Redis 拿到工作、執行你的程式、做完之後回報 Redis「完成了」。點數已經寫進資料庫、卻沒有成功回報，有兩種情況，BullMQ 的處理方式不同：

  • 程式丟錯：worker 寫完點數，後面某一步（例如寫 log、呼叫別的服務）丟出錯誤。BullMQ 把這次記成失敗，照這個專案的工作設定重試：最多做 3 次，失敗後等 1 秒、2 秒再試（attempts: 3、backoff 指數 1000 毫秒）。
  • worker 斷線：worker 寫完點數就當機，或跟 Redis 的連線斷了，什麼都沒回報。worker 處理工作時會持有一把有期限的鎖並定期續約；斷線後鎖過期，BullMQ 的 stalled 檢查把這個工作判定為卡住（stalled），放回等待區交給 worker 再跑一次。這條路跟 attempts、backoff 無關，即使設 attempts: 1 也會發生。

兩種都會讓同一個工作再跑一次。這就是第 20 課說的至少一次：佇列寧可多做一次，也不會漏做，代價是 worker 必須承受同一個工作來兩次，也就是要冪等。

資料這一層已經有保護：point_transactions.order_id 有唯一約束，同一張訂單第二次 create 會撞 P2002，王小明不會拿到 4 點。但工作本身丟了錯，BullMQ 就當它失敗，再試一次又撞，3 次用完後進 failed 清單。監控看到 failed 工作就發告警，值班的人半夜被叫起來，看到的是一個「其實沒事」的錯。這種假警報一多，大家就開始忽略 failed 清單，真正的問題混在裡面沒人看見。

正確的做法是讓重試成功：發現這張訂單已經加過點，就當成這個工作已經完成。Prisma 的 createMany 加 skipDuplicates: true 會變成 INSERT … ON CONFLICT DO NOTHING，撞到唯一約束時什麼都不做、也不丟錯：

await this.prisma.$transaction(async tx => {
  const card = await tx.stampCard.upsert({ where: { customerId }, create: { customerId }, update: {} })
  await tx.pointTransaction.createMany({ data: [{ cardId: card.id, orderId, points, reason: '消費' }], skipDuplicates: true })
})

第一行的 upsert 是「有就用、沒有就建立」：王小明第一次加點時還沒有集點卡，就建一張；之後 update: {} 什麼都不改，直接拿到現有的卡。這樣第一次和第 N 次都走同一段程式。另一種寫法是 create 照舊，在 $transaction 外面接住 P2002 當成成功。不能在交易裡面接：PostgreSQL 的交易只要有一個語句失敗就整個作廢，後面的查詢都會失敗。

寄收據的 worker 已經寫好，它面對的是另一種情況：寄信是呼叫外部服務，我們資料庫的唯一約束管不到它。做法是把 idempotencyKey: receipt-<orderId> 傳給寄信服務，同一個 key 它只寄一次，重試也只寄一封。很多外部 API 都接受這樣的鍵，用它比自己記「寄過了」可靠：自己記的話，信寄出去之後、記下來之前當機，重試還是會再寄一封。

到這裡，王小明的訂單不管被重送幾次，最後都是一張訂單、2 點、一封收據。但這只是「現在」的程式做得到。下個月有人改了 OrdersService 的一行，怎麼知道它還做得到？

下個月有人改了一行，怎麼知道重送不會又多一張？

前面每一節的保護有個共同的弱點：它們保護的是「平常不會發生的事」。少傳一個 tx、重送時多查一次訂單，程式看起來都對，平常操作也完全正常，只有重送、同時送、付款後再重送這些情境才會露餡。人工測試幾乎不會每次都重做這些情境，所以要寫成自動化測試，每次改程式都跑一遍。

這裡用的是第 10 課的 e2e 測試，不只是測 service 的單元測試。原因是要保護的行為由好幾樣東西合起來決定：header 怎麼讀、controller 用哪個狀態碼送出、交易與唯一約束怎麼互動、outbox 怎麼被 relay 送進佇列。單元測試把其中任何一樣換成假的，就測不到它們之間的接縫。所以練習 3 有兩條限制：

  • 只透過 HTTP 操作與檢查：下單、查訂單、查點數都走 API，付款用 sendPaymentWebhook 模擬金流公司送 webhook，再用 drain 讓 relay 立刻送一次、等佇列的工作做完。測試看到的，就是前端與金流公司會看到的。
  • 不 mock Prisma：用真的 PostgreSQL 與 Redis，只是換成測試專用的資料庫與佇列前綴，不碰開發資料。mock 掉之後，交易、唯一約束、佇列全被假物件取代，測的是 mock 的行為。

要測哪些情境，直接從盤點表來：表裡每一列「可能出什麼事」，都該有一個測試去重現它。把王小明這一天寫成測試，大致是：沒帶 key 下單要 400；帶 key 下單、同一個 key 重送，狀態碼和 res.text 都要跟第一次一樣，庫存只扣一次；付款之後再重送一次，還是第一次的內容；換內容重送要 422；付款後 drain，再檢查點數與收據各只有一份。

怎麼知道測試真的有用？練習 3 的判分方式值得學起來：把正確的程式故意改壞，例如重送時重新查訂單、付款後沒寫 receipt.requested，看你的測試會不會失敗。改壞了測試還是全綠，就代表那種壞法沒被保護。這比看覆蓋率可靠：覆蓋率只說哪些行被執行過，不說結果有沒有被檢查。

測試證明了結帳流程沒壞。但流程沒壞，不代表這個服務可以部署：它在正式環境能不能啟動、平台怎麼判斷它健康、是不是誰都能改價，這些都不在結帳流程裡。

讀這張表的方式跟盤點表一樣：每一列都是「沒做會怎樣」。練習 4 要修的四列，各自的後果是：

  • 啟動：catalog 裡兩個 service 互相 import，Vitest 跑得過，nest build 之後正式啟動卻失敗。node dist/main.js 照 import 順序執行模組，兩個檔案互相 import 時，其中一方會在另一方的 class 還沒初始化完就讀它，丟出 Cannot access … before initialization（階段檢核練習 12）。Vitest 用 Vite 的模組執行器，載入 import 的方式和 Node 不同，所以測試通過不代表正式啟動沒問題，細節見第 25 課。第 25 課看過這種循環，forwardRef 只讓它啟動得起來，第 26 課的解法是讓依賴只往一個方向。
  • 探針：部署平台會定期打健康檢查端點。liveness 回答「這個程序要不要重啟」，readiness 回答「現在能不能把請求送給它」。判斷的問題是第 24 課那句：這種狀況，重啟程序修得好嗎？資料庫斷線重啟修不好，所以它只能放在 readiness；放進 liveness，資料庫一掛，每一台都被判定死掉、一起重啟。
  • 權限：改價的端點如果在方法裡自己比對金鑰，每新增一個路由就要記得寫一次，起始專案的 PATCH 就忘了，任何人都能改價。guard 掛在 class 上，新路由自動受保護。
  • 輸入：mass assignment 指的是請求多送了你沒打算讓它改的欄位，而程式照單全收，例如改價時多送 stock: 999，DTO 又直接當成 Prisma 的 data，庫存就被改了。whitelist 會把沒宣告的欄位悄悄丟掉，加上 forbidNonWhitelisted 則直接回 400，前端也馬上知道自己送錯了。

清單的價值在「下次上線前一定會問」。出過一次事故，就加一列；改了哪個部分，就重看相關的幾列。

練習 1：POST /api/v1/orders 加上 Idempotency-Key。

  • OrdersService.create(dto, key)：key 沒帶或不符合 ^[A-Za-z0-9_-]{1,64}$ 丟 IdempotencyKeyRequiredError（400）。
  • 在同一個互動式交易裡：第一步 tx.idempotencyKey.create（key 與請求內容的 SHA-256 requestHash）→ placeOrder → 把回應字串存進 responseStatus、responseBody。下單失敗整個交易回滾，key 不留下。
  • 撞到主鍵（P2002）：讀出存下來的那筆。requestHash 不同丟 IdempotencyKeyReusedError（422）；回應還是 null 丟 IdempotencyKeyInProgressError（409）；否則回傳存下來的狀態碼與內容。
  • Controller 用 @Headers('idempotency-key') 讀 key，用 @Res() 以存下來的狀態碼送出原始字串，Content-Type 是 JSON。

判分：沒帶 key、空字串、含空白、65 字都要 400 且不建立訂單；同一個 key 重送回 201 和一字不差的內容，只有一張訂單、庫存只扣一次；付款後重送仍回第一次的回應（pending）；同 key 不同內容 422；不同 key 同內容建兩張；同一個 key 同時送 5 次連跑 3 輪，每輪只建一張，其他是 201（同一內容）或 409；庫存不足失敗後補貨、同一個 key 重試要成功。

判分：付款後 outbox 有兩筆、relay 送出後加 2 點、寄一封收據；同一個事件重送三次都回 200，outbox 不多寫；不同事件 id 付同一張已付款的訂單不寫 outbox；Queue.prototype.add 被換成一直失敗時 webhook 仍回 200，恢復後 relay 補上點數與收據；OutboxService.add 第一次失敗時整個交易回滾，重送同一個事件要補上；earnForOrder 寫完點數後丟錯一次，重試後點數仍是 2、工作狀態是 completed；簽章錯 401 且沒有 outbox。

判分把你的測試套在標準答案上要全部通過，再套在八個故意改壞的版本上，每一個都至少要有一個測試失敗：沒看 key（重送多一張訂單）、沒扣庫存、重送回 200 而不是 201、重送時重新查訂單（付款後重送會回 paid）、同 key 換內容也回舊訂單、沒帶 key 也照樣下單、付款後沒寫 receipt.requested、沒寫 order.paid。所以：沒帶 key 要檢查 400；重送要比對狀態碼與 res.text，付款之後再重送一次，也換內容重送一次；付款後要 drain 再檢查點數與收據。

練習 4：上線前檢查。照上面的清單逐項修：

  • 啟動：catalog 裡 ProductsService ↔ MenuService 互相 import，用 forwardRef 蓋著。讓依賴只往一個方向：MenuService 自己用 Prisma 查 products（同一個模組的表），ProductsService 寫入後呼叫 menu.invalidate()；拿掉 forwardRef。
  • 探針：/health/live 不檢查任何依賴（this.health.check([])）；/health/ready 維持 database 與 redis。
  • 權限：ProductsController 的每個路由都要 AdminGuard，掛在 class 上；拿掉方法裡自己比對金鑰的程式與 ConfigService 的注入。
  • 輸入：configureApp 的 ValidationPipe 加上 whitelist: true, forbidNonWhitelisted: true。

判分：src 沒有循環 import，nest build 後 node dist/main.js 能啟動，/health/live、/health/ready、/api/v1/menu 都 200；資料庫查詢被換成失敗時 ready 503、live 200；POST、PATCH /api/v1/products 沒帶或帶錯 X-Admin-Key 都 401 且價格不變，每個路由都掛了 guard；PATCH 多送 stock 回 400 且庫存、價格都不變；菜單走快取，透過 API 改價後馬上看到新價格。

練習 5：同事提議把 Idempotency-Key 的處理搬到 interceptor，用 Redis 存「key → 回應」，service 完全不用改。哪個說法最準確？

✓ c。這條流程最強的保證來自「key 與訂單在同一個 PostgreSQL 交易」：同時進來的請求由主鍵裁決，失敗一起回滾，不會有空檔。搬到 Redis 不是不行，很多高流量服務這樣做，但每一個失敗點都要另外補：搶鎖、key 遺失、兩個儲存體之間的空檔。a 只看到速度；下單本來就要寫資料庫，多一筆 key 的成本很小。b 錯：interceptor 可以在 tap 裡拿到回應。d 錯：沒有這種規定，這是取捨。

練習 6：上線一週後，監控顯示 loyalty 佇列每天有十幾個 failed 工作，錯誤都是 P2002（point_transactions.order_id 唯一約束）。點數餘額都是對的。該怎麼處理？

✓ b。唯一約束擋住了重複加點，資料是對的，但工作失敗代表「worker 遇到它該處理的情況卻丟錯」，failed 清單裡的真問題會被這些假警報淹沒。先讓重試成功，再追重試的來源。a 把症狀藏起來，下次真的 P2002（例如別的 bug）也看不到。c 讓暫時性錯誤（資料庫連線中斷）也不重試，點數真的會漏。d 拿掉最後一道防線，餘額會開始錯。

練習 7：練習 3 的 e2e 測試全部通過。PM 問：「這樣是不是就不會再有重複訂單的 bug 了？」最誠實的回答是？

✓ d。練習 3 的判分方式就是這個道理：把程式故意改壞八種，看測試抓不抓得到；抓得到的是那八種，不是所有的壞法。測試是回歸的保險，不是正確性的證明。a、c 把「通過」當成「沒有 bug」；覆蓋率只說哪些行被執行過，沒說結果對不對。b 走到另一個極端：人工測試更不可能每次都重做重送與並發的情境。

常見錯誤

  • 先查 key 再建立訂單：兩個同時進來的請求都查到「沒有」，各建一張。key 當主鍵、交易第一步 create，由資料庫裁決誰先。
  • 在交易外先寫 key：下單失敗後 key 留著、回應是 null，客人之後怎麼重試都是 409。key 跟訂單同一個交易。
  • 重送時重新查訂單：付款後重送回 paid，客戶端拿到和第一次不一樣的內容。存回應字串，原封不動送回。
  • 沒存請求的雜湊：同一個 key 換了內容也回舊訂單，前端的 bug 被藏起來。
  • 沒帶 key 就自動產生一個：重送照樣多一張訂單，保護等於沒有。沒帶就 400。
  • 交易提交後才送進佇列：commit 與 add 之間當機、Redis 連不上，點數與收據永遠漏掉；而且 webhook 回 5xx 讓金流公司重送時，event_id 已經記錄，重送被當成重複。同一個交易寫 outbox。
  • 在交易外寫 outbox：outbox.add 沒傳 tx，又回到雙寫問題。
  • 付款的交易裡直接加點：原子，但 payments 碰了 loyalty 的表，之後改集點規則要改付款的程式。只寫事件。
  • 用 @nestjs/event-emitter 的程序內事件做加點：第 21 課比較過，程序內事件在程序當機時就丟了，也不會重試。要保證一定發生的工作走 outbox 與佇列。
  • worker 靠唯一約束的錯誤擋重複：資料對，但工作進 failed，假警報淹沒真問題。skipDuplicates 或接住 P2002，讓重試成功。
  • e2e 測試只測 happy path：改壞「重送回 200」或「付款後重送回現在的狀態」都抓不到。重送要比對狀態碼與 res.text，付款後再重送一次。
  • e2e 測試 mock Prisma：交易、唯一約束、佇列全被假物件取代，測的是 mock 的行為。這一層用真的資料庫。
  • liveness 順便查資料庫：資料庫一掛，每一台都被判定死掉、一起重啟，重啟也修不好資料庫。live 只看程序活著。
  • 金鑰比對寫在方法裡：新增一個路由就忘一個（起始專案的 PATCH 就忘了）。guard 掛在 class 上。
  • 只有 whitelist 沒有 forbidNonWhitelisted：多送的欄位被悄悄丟掉，前端不知道送錯；沒有 whitelist 時 dto 直接當 Prisma 的 data，stock: 999 就寫進去了。
  • 拆循環時順手拿掉 invalidate：改價後菜單一分鐘都是舊價。拆依賴方向，不拆功能。

小結

  • 王小明那一天的每一個失敗點，對策都是同一句：把「做過了沒」放進 PostgreSQL，用交易與唯一約束保證只發生一次。記憶體旗標在多台伺服器與重啟面前會失憶，先查再寫在同時進來的請求面前有空檔。
  • 先盤點再寫程式：沿著流程逐步問「這裡掛了會怎樣、客人看到什麼」，每一列變成一個對策和一個測試，保護強度跟著後果走。
  • Idempotency-Key：必填、綁定請求雜湊、存回應字串不重新查、key 當主鍵在交易第一步寫入、失敗跟交易一起回滾。撞 P2002 才去讀存下來的回應，內容不同 422，回應是 null 就 409。
  • 付款 webhook：markPaid、webhook_events、outbox_events 同一個交易，交易裡不碰 Redis，送進佇列交給 relay。payload 只放事實，loyalty、notifications 不認識 payments。
  • 佇列至少執行一次，worker 要讓重試成功：createMany 加 skipDuplicates，或接住 P2002；外部服務用它的 idempotency key。
  • e2e 測試保護主流程：只透過 HTTP、用真的資料庫與佇列、照盤點表測錯誤路徑與重送，用「故意改壞」確認它抓得到。
  • 上線前檢查請求以外的事：能正式啟動、live 不查依賴、guard 掛 class、forbidNonWhitelisted、寫入後快取失效、enableShutdownHooks、設定驗證。出過的事故變成新的一列。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：Redis 停機維護兩分鐘，PostgreSQL 正常，程序本身也沒問題。這段時間 /health/live 與 /health/ready 應該各回什麼？

✓ live 只回答「程序要不要重啟」，重啟修不好 Redis；ready 回答「現在能不能接流量」，依賴掛了就 503。每個指標都要 .withTimeout()，Redis 卡住時 ready 約 1 秒就回 503，不能跟著卡住。a 錯在把依賴的問題算到程序頭上，每一台一起重啟，Redis 還是沒好。（第 24 課）

練習 9：本機一次打一個請求，log 的 requestId 都對；上線後同一個請求的 log 卻出現別人的 requestId。原因和修法是？

let currentRequestId = ''

export function requestId(req: Request, res: Response, next: NextFunction) {
  currentRequestId = randomUUID()
  next()
}
// service 裡：this.logger.log('付款完成', { orderId, requestId: currentRequestId })

✓ 單一執行緒不代表沒有並發：第一個請求 await 資料庫時，第二個請求的 middleware 已經把變數換掉了，一次一個時完全看不出來。AsyncLocalStorage 讓每個請求有自己的情境，provider 照樣是 singleton。c 能動但代價大：request scope 會冒泡到整條依賴鏈，每個請求重建實例，app.get 也拿不到。（第 24、25 課）

練習 10：每次部署都有幾筆付款請求斷在半路。關機 hook 都寫好了，但部署時 log 裡一行 hook 的輸出都沒有。最可能的原因與修法是？

✓ 沒有 enableShutdownHooks，SIGTERM 不會走 app.close()，三個關機 hook 一個都不會跑；本機 Ctrl+C 看起來正常，上線才出事。也不要自己監聽 SIGTERM 呼叫 process.exit，那一樣會切斷進行中的請求。c 的症狀不一樣：$disconnect 放太早時 hook 有跑，是程序結束不了、最後被 SIGKILL。（第 24 課）

練習 11：報表 API 一被呼叫，連什麼都不查的 /health/live 也要好幾秒才回應。最先該查什麼？

✓ live 不碰任何依賴也變慢，代表主執行緒根本沒空處理請求：報表的同步 CPU 工作卡住了事件迴圈。修法是非同步 API、切小塊、worker_threads 或佇列；包成 async 不會讓它不卡。a 錯在連線池滿了只有要查資料庫的請求會排隊，live 不查資料庫，不會跟著慢。（第 25 課）

練習 12：orders 付款後要呼叫 LoyaltyService 加點，loyalty 算點數又要 OrdersService 查訂單，兩個模組互相 import，build 後啟動就報 Cannot access … before initialization。哪個解法對？

✓ 根本解是讓依賴只往一個方向：orders 只宣布事實，loyalty 從事件裡拿需要的欄位，兩邊不再互相 import。a 最多人選，但它只讓程式啟動得起來，兩個模組還是綁在一起。b 循環沒了，卻變成 orders 寫 loyalty 的表；c 讓 provider 失去歸屬、依賴圖消失。（第 25、26 課）

練習 13：notifications 模組寄收據的程式如下，測試都通過。code review 時該指出什麼？

@Injectable()
export class ReceiptsService {
  constructor(private prisma: PrismaService, private mailer: Mailer) {}

  async send(orderId: number) {
    const order = await this.prisma.order.findUnique({ where: { id: orderId } })
    await this.mailer.sendReceipt(order.customerId, order.total)
  }
}

✓ 一張表只有一個模組碰：orders 之後改欄位或加軟刪除，沒人會想到 notifications 也要改。外面只透過 exports 的 service 或事件互動。b 是最常見的藉口：@Global 只是省掉 import，不代表誰都能碰每一張表。（第 26 課）

練習 14：付款 webhook 的處理寫成這樣。哪裡會出事？

await this.prisma.$transaction(async tx => {
  await this.orders.markPaid(tx, orderId)
  await tx.webhookEvent.create({ data: { eventId, type, status: 'processed' } })
})
await this.queue.add('order.paid', { orderId, customerId, total })

✓ 提交與送進佇列是兩次寫入，中間任何失敗都會漏；而且金流公司重送時 event_id 已經記錄過，重送被當成重複。修法是同一個交易用 tx 寫 outbox，relay 再送進佇列。a 錯在 Redis 不參與 PostgreSQL 的交易，移進去也不會一起回滾，還讓付款跟著 Redis 失敗。（第 27 課）

練習 15：同事把搶 key 移到交易外面，撞 P2002 之後的處理照課文。拿鐵賣完、下單丟出庫存不足，客人等補貨後用同一個 key、同樣的內容重試，會怎樣？

await this.prisma.idempotencyKey.create({ data: { key, requestHash } })
return this.prisma.$transaction(async tx => {
  const body = JSON.stringify(await this.placeOrder(tx, dto))
