階段 2：請求管線與測試 · 第 6 課

請求生命週期（一）：middleware 與 guard

週一早上，店長發現菜單上的拿鐵變成 1 元，週末已經用這個價格賣出好幾十杯。同一時間客服接到顧客抱怨「下單一直失敗」。你打開 log，看到的是同一個 IP 一秒打幾百次 PATCH /products 和 POST /orders，幾萬行紀錄混在一起，分不出哪幾行屬於那位顧客的那一次下單。

這次事故暴露出三個缺口：商品 API 誰都能改價；出了事找不到是哪一個請求；有人用腳本連打，伺服器只能照單全收。這一課就是把這三個缺口補起來。它們有一個共同點：都不屬於某一個 handler，而是每個請求進來時都要做的事。Nest 把請求從進門到回應拆成幾個固定的關卡，這三件事分別落在前兩站：middleware 和 guard。

這課的路線：
  1. 三件事該放在哪一站：請求在 Nest 裡依序經過哪些關卡，編號、權限、限流各該放在哪裡，為什麼不寫在 handler 裡。
  2. Middleware 與 request id：middleware 怎麼寫、怎麼套用；替每個請求編號，客服拿到編號就能在 log 裡找出那一個請求。
  3. Guard：怎麼在路由上標記「只有店長能用」，guard 怎麼讀到標記、比對金鑰，401 和 403 怎麼分。
  4. 註冊：guard 掛在全域、controller 或單一路由的差別，哪一種寫法能注入依賴、在測試裡換得掉。
  5. 限流：用 @nestjs/throttler 擋下連打的腳本，它該排在金鑰檢查前面還是後面，開了多台伺服器後哪裡不夠。
這課會用到：
  • TypeScript 課第 24 課的裝飾器與 metadata：裝飾器能在 class 或方法上貼一份資料，執行時再用同一把 key 讀回來。
  • 第 3 課的 token 與 useExisting：容器用 token 找 provider；useExisting 讓一把新 token 指向已經登記的同一個實例。
  • 第 5 課的 Testing Module：overrideProvider(token).useValue(…) 在測試裡把某個 provider 換成替身。

三件事該放在請求的哪一站？

最直覺的修法是在每個 handler 開頭加幾行：先產生編號、再檢查金鑰、再算這個 IP 打了幾次。問題是咖啡店已經有十幾個 handler，同樣的三段程式要複製十幾份；之後有人新增一條路由忘了貼，那條路由就是新的漏洞，而且不會有任何錯誤提醒你。這類「每個請求都要做、但跟業務邏輯無關」的事，應該寫一次、套到所有該套的路由上。

Nest 的做法是把請求的處理拆成固定的幾站，叫做請求生命週期（request lifecycle）：一個請求從進到 Nest 到送出回應，依序經過的關卡。你可以在任何一站掛上自己的程式，它就會對經過的每個請求執行。每一站在流程裡的位置不同，能看到的資訊也不同，所以適合做的事也不同：

這課只處理前兩站，後面三站在第 7～9 課。下表先讓你知道每一站看得到什麼：

關卡看得到什麼典型用途
middleware原始的 req、res；不知道等一下由哪個 handler 處理request id、存取 log、解析 cookie、安全標頭
guardExecutionContext：知道是哪個 controller 的哪個方法、方法上貼了什麼標記能不能進來：登入、權限、限流
interceptor包住 handler，看得到回傳值計時、逾時、改寫回應
pipe單一個參數轉型、驗證

關鍵是第二欄。middleware 在 Nest 決定「這個請求交給哪個 handler」之前就執行，所以它只看得到原始的請求；guard 在那之後執行，知道目標是哪個方法。所有 middleware 都在所有 guard 之前跑完。用這個區別回頭看事故的三個缺口：

  • 替請求編號：每個請求都要有，越早產生越好，後面每一站寫 log 時才拿得到；它不需要知道 handler 是誰。放在 middleware。
  • 只有店長能改價：要知道這個請求要進的是「改價」這個方法，而且那個方法被標記為店長專用。只有 guard 看得到。放在 guard。
  • 限流：決定「這個請求能不能進來」，而且常常每條路由額度不同。這課用的 @nestjs/throttler 本身就是一個 guard。

位置定好了，接下來從最前面那一站開始：middleware 要怎麼寫，才能讓它對每個請求執行？

Middleware：每個請求進門先做的事怎麼寫？

middleware 是請求進到路由之前執行的函式。如果你寫過 Express，它跟 Express 的 middleware 是同一個東西，因為 Nest 預設就是跑在 Express 上。它拿到三個參數：請求 req、回應 res，和一個函式 next。做完自己的事之後呼叫 next()，請求才會往下一站走。

next() 是最容易出事的地方。middleware 有兩種正常的結局：呼叫 next() 交給下一站，或自己用 res 送出回應、結束這個請求。如果兩件事都沒做，請求就會一直掛著，客戶端等到逾時才放棄，伺服器這邊也不會有任何錯誤訊息。寫 middleware 時要確認每一條分支都走到其中一個結局。

Nest 的 middleware 有兩種寫法。需要用到其他 provider（例如注入一個 logger service）就寫成 class，Nest 會幫它注入依賴；沒有依賴時，一個普通函式就夠了：

// class 版：可以注入其他 provider
@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    console.log(req.method, req.originalUrl)
    next()
  }
}

// 函式版：沒有依賴時更簡單
export function logger(req: Request, res: Response, next: NextFunction) {
  console.log(req.method, req.originalUrl)
  next()
}

寫好之後要告訴 Nest 套用到哪些路由。middleware 不像 controller、provider 那樣寫在 @Module() 的欄位裡，而是讓模組實作 NestModule 介面，在它的 configure() 方法裡設定：

@Module({ controllers: [ProductsController, OrdersController] })
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(LoggerMiddleware)
      .exclude({ path: 'menu', method: RequestMethod.GET })   // 選用：排除某些路由
      .forRoutes('*')                                          // 所有路由；也可以傳 controller class
  }
}

apply() 放要套用的 middleware，forRoutes() 指定範圍，'*' 是所有路由，也可以傳 controller class 只套用到那個 controller 的路由；exclude() 是選用的，用來排除少數路由。

你在網路上還會看到另一種寫法：在 main.ts 用 app.use(logger) 註冊全域 middleware。它看起來更短，但官方文件提醒兩個限制。第一，app.use() 註冊的 middleware 在模組外面，拿不到依賴注入，只能用函式版。第二，測試通常直接編譯 AppModule，不會執行 main.ts，這段 middleware 在測試裡等於不存在，測試看到的行為跟正式環境不一樣。需要注入、或希望測試也有同樣的行為，就用 forRoutes('*')。

還要記得 middleware 的界線：它不知道請求會進到哪個 handler，也就讀不到 handler 上的標記。如果把「這個路由只有店長能用」放在 middleware，只能自己比對網址字串，例如 req.path.startsWith('/products')；之後路由改名或新增一條路徑，這條規則就默默失效，不會有任何錯誤。所以 middleware 只做不需要知道 handler 的事，權限判斷留給後面的 guard。

💡 實務上：自己寫的 middleware 通常很少
工作中的 Nest 專案，middleware 大多是現成套件：helmet 加安全標頭、壓縮、cookie 解析，再加上一兩個自己寫的，例如這課的 request id 或存取 log。會用到 handler 資訊的事（權限、回應格式）交給 guard 或 interceptor（第 9 課）。也要注意它套用的範圍：forRoutes('*') 連健康檢查、靜態檔都會經過，做太重的事（查資料庫、呼叫外部 API）會拖慢每一個請求。

知道 middleware 怎麼寫、怎麼套用，就可以處理事故的第一個缺口：客服說「下單失敗」，怎麼從幾萬行 log 裡找到那一次請求？

替每個請求編號：客服拿到編號，怎麼找到那一次請求？

事故當下 log 找不到人，是因為同一時間有幾百個請求在處理，它們的 log 交錯寫在一起，沒有任何欄位能把「屬於同一個請求的那幾行」串起來。解法是 request id（請求編號）：請求一進門就替它產生一個唯一的字串，之後這個請求寫的每一行 log 都帶上它，回應標頭也放一份。顧客或前端回報問題時給出編號，工程師用編號一搜，就能找出同一個請求的所有紀錄。Node 課第 19 課做過一樣的事，第 24 課會接上 Nest 的 logger。

它要在最前面產生，後面每一站才拿得到，所以放在 middleware。實作分成三步：決定編號、把編號存起來、交給 handler。

第一步：沿用前面給的編號，但不能照單全收

請求不一定是從顧客的瀏覽器直接到你的伺服器。前面可能還有前端的 BFF（Backend for Frontend，專門替某個前端整理資料、轉呼叫後端的一層伺服器）、API 閘道，它們可能已經替這個請求編好號，放在 X-Request-Id 標頭裡。如果你另外產生一個新的，同一個請求在不同系統裡就有兩個編號，串不起來。所以規則是：請求有帶 X-Request-Id 就沿用，沒有才自己產生。

但標頭是客戶端可以隨便填的，事故裡的腳本也能填。Node 的 HTTP 解析器會擋掉標頭值裡的換行（實測直接回 400），但幾 KB 長的字串、空白、引號、看起來像別的 log 欄位的文字（abc level=error user=admin）都進得來。這些值寫進 log 之後，輕則讓 log 難以搜尋，重則偽造出假的欄位，讓查事故的人被誤導。

防法是只接受允許清單裡的格式：列出「合法的長相」，不符合的一律不收，而不是去猜所有危險的寫法。這裡的清單是 1–64 個英數字、-、_。不符合就當作沒帶，換成新的 crypto.randomUUID()。

第二步：存在 req 上，並補上型別

編號決定好了，要放在某個地方讓後面的程式拿得到。最直接的是掛在這個請求的物件上：req.requestId = id，同一個請求後面的每一站拿到的都是同一個 req。但 Express 的 Request 型別沒有 requestId 這個欄位，TypeScript 會報錯。

解法是 TypeScript 課第 25 課的 declaration merging：TypeScript 允許你對同一個 interface 再宣告一次，兩份宣告的欄位會合併。@types/express 的 Request 繼承全域命名空間 Express.Request，所以對 Express.Request 加欄位，專案裡所有地方的 Request 都看得到：

// src/express.d.ts
declare global {
  namespace Express {
    interface Request {
      requestId: string
    }
  }
}

export {}   // 讓這個檔案是模組，declare global 才合法

第三步：用參數裝飾器交給 handler

handler 要拿編號（例如寫 log、放進回應），可以注入 @Req() req 再讀 req.requestId。但這樣 handler 就依賴整個 Express 請求物件，單元測試時也得假造一個 req。比較好的做法是做一個自訂參數裝飾器：像 @Body() 一樣，由 Nest 在呼叫 handler 前把值算好，直接當參數交給 handler，handler 只看得到它需要的那個字串：

import { createParamDecorator, type ExecutionContext } from '@nestjs/common'

export const RequestId = createParamDecorator(
  (data: unknown, ctx: ExecutionContext) => ctx.switchToHttp().getRequest().requestId,
)

// handler
@Get()
whoami(@RequestId() requestId: string) { … }

createParamDecorator 收一個回呼，Nest 在每次請求、呼叫 handler 之前執行它，回傳值就是參數的值。回呼的第一個參數 data 是使用裝飾器時傳的參數（@RequestId('x') 的 'x'），這裡用不到；第二個參數 ExecutionContext 下一節會細講，這裡只用它拿到 req。認證課第 21 課的「目前登入的人」@CurrentUser() 也是同一招。

有一個看起來更省事的寫法要避開：在 handler 用 @Headers('x-request-id') 取編號。那拿到的是客戶端送來的原始值，也就是可能已經被 middleware 判定不合法、換掉的那一個；log 和回應標頭用的是新編號，handler 用的卻是舊的，兩邊對不起來。一律從 req.requestId 讀。

💡 實務上：request id 是客服和工程師之間的共同語言
常見做法是前端在錯誤畫面或 toast 顯示「錯誤代碼：xxxx」，顧客截圖給客服，工程師拿編號到 log 系統一搜就找到那次下單的完整經過，不用再問「大概幾點、按了什麼」。前端要讀到這個回應標頭，跨網域時後端得在 CORS 設定 Access-Control-Expose-Headers: X-Request-Id，否則瀏覽器不讓 JavaScript 讀，這是很常見的坑。錯誤回應的 JSON 裡也放一份編號（第 8 課的 exception filter 可以統一加），前端就不用另外處理標頭。

下次再出事，至少找得到是哪一個請求了。但真正的問題還沒解決：任何人仍然可以把拿鐵改成 1 元。這需要一個知道「這個請求要進哪個方法」的關卡，也就是 guard。

誰能改價？guard 怎麼決定放不放行

guard 是實作 CanActivate 介面的 class，只回答一個問題：這個請求能不能進到 handler。它只有一個方法 canActivate()，回傳 true 就放行；回傳 false，Nest 直接回 403 和 {"message":"Forbidden resource","error":"Forbidden","statusCode":403}，handler 和後面所有的站都不會執行。

guard 能做 middleware 做不到的權限判斷，靠的是它的參數 ExecutionContext。這是 Nest 在決定好目標 handler 之後建立的物件，描述「現在要執行的是哪個 controller 的哪個方法」：

  • context.getHandler()：要執行的方法本身，例如 ProductsController 的 update。
  • context.getClass()：那個方法所在的 controller class。
  • context.switchToHttp().getRequest()：Express 的 req，標頭從這裡讀。

有了前兩個，guard 就能問「這個方法有沒有被標記為店長專用」，規則跟著方法走，路由改名也不受影響。middleware 執行時還沒有這些資訊，這就是權限判斷要放在 guard 的原因。

拒絕時回 401 還是 403？

拒絕請求時，狀態碼要讓前端知道「該做什麼」，而不只是「失敗了」。HTTP 用兩個狀態碼區分兩種拒絕（Node 課第 12 課、認證課第 1 課）：

  • 401 Unauthorized：沒帶憑證，或憑證無效，伺服器不知道你是誰。前端收到通常是導向登入頁，讓使用者補上憑證。guard 裡用 throw new UnauthorizedException()。
  • 403 Forbidden：知道你是誰，但你沒有權限。前端收到應該顯示「沒有權限」，重新登入也沒用。guard 回傳 false 預設就是 403。

所以 guard 不能只會回 false。如果「沒帶金鑰」也回 false，就變成 403，前端分不出該叫使用者去登入，還是告訴他沒權限。沒帶憑證要自己丟 UnauthorizedException；這個例外丟出去之後，同樣不會進到 handler。

guard 的骨架清楚了，但它要怎麼知道「改價」這個方法是店長專用的？這個資訊得先寫在路由上。

怎麼告訴 guard 哪些路由只有店長能用？

「只有店長能用」是路由的屬性，寫在路由旁邊最清楚：讀 controller 的人一眼就看得到哪些方法受保護，新增路由的人也會順手決定要不要貼。這要用到 metadata。metadata 是附在 class 或方法上的一份資料，本身不改變方法的行為，只是讓別的程式在執行時讀出來參考。TypeScript 課第 24 課看過，裝飾器能貼 metadata，執行時再用同一把 key 讀回來。

分工是這樣：用一個裝飾器 @AdminOnly() 在方法上貼「這是店長專用」的 metadata；guard 執行時，用 Nest 提供的 Reflector 讀出來。Reflector 是 Nest 專門用來讀 metadata 的 provider，guard 在 constructor 注入它就能用。

// admin-only.decorator.ts
import { Reflector } from '@nestjs/core'

export const AdminOnly = Reflector.createDecorator<boolean>({ transform: value => value ?? true })

// products.controller.ts
@Post()
@AdminOnly()
create(@Body() body: …) { … }

// guard 裡
const adminOnly = this.reflector.getAllAndOverride(AdminOnly, [context.getHandler(), context.getClass()])

逐段看：

  • Reflector.createDecorator<boolean>() 產生一個有型別的裝飾器。讀的時候不用另外記一個字串 key，直接把裝飾器本身傳給 Reflector，所以 guard 裡寫的是 getAllAndOverride(AdminOnly, …)。<boolean> 是這份 metadata 的型別，讀出來的值會自動帶著這個型別。
  • transform: value => value ?? true：讓不給參數的 @AdminOnly() 存 true，@AdminOnly(false) 存 false。沒有它，不給參數時存的值不是 true，跟 boolean 型別對不上（原始碼層級的細節見課末「補充與查表」）。
  • getAllAndOverride(key, [方法, class])：依序看方法、再看 class，回傳第一個有定義的值。所以可以在整個 controller 上貼 @AdminOnly()，讓每個方法都要金鑰，再在某個方法上用 @AdminOnly(false) 開放。兩層都沒貼，就是 undefined。

網路上和舊專案大多用另一種較早的寫法 SetMetadata，認證課第 21 課也用它；兩者的差別和對照寫法放在課末。新程式用 createDecorator。

現在 guard 讀得到標記了。剩下的是標記為店長專用之後，怎麼檢查這個請求真的是店長。

把金鑰 guard 寫完：讀設定、拒絕、比對

真正的登入與角色在認證課第 21 課。這一課先用一把共用的管理員金鑰保護商品的新增、修改、刪除：請求帶 X-Admin-Key 標頭，跟環境變數 ADMIN_KEY 比對。把前面幾節組起來：

@Injectable()
export class AdminKeyGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const adminOnly = this.reflector.getAllAndOverride(AdminOnly, [context.getHandler(), context.getClass()])
    if (!adminOnly) return true                                   // 沒標記的路由直接放行

    const given = context.switchToHttp().getRequest<Request>().get('x-admin-key')
    if (!given) throw new UnauthorizedException('需要 X-Admin-Key 標頭')   // 401

    const expected = process.env.ADMIN_KEY                        // 每次請求時才讀
    if (!expected) throw new ForbiddenException('伺服器沒有設定 ADMIN_KEY')
    …比對 given 與 expected，相同回 true，不同回 false（403）
  }
}

順序是：沒標記就放行（菜單、下單照樣誰都能用）→ 沒帶金鑰回 401 → 伺服器沒設定金鑰就拒絕 → 比對。這段程式看起來單純，但有三個地方寫錯了不會有錯誤訊息，只會在正式環境出事。

什麼時候讀 process.env？

起始專案的 main.ts 在 bootstrap() 裡呼叫 process.loadEnvFile() 載入 .env（Node 課第 2 課）。但 ES module 的 import 會在 main.ts 的任何程式之前先執行完：main.ts import 了 AppModule，AppModule import 了 guard 檔案，這些檔案最上層的程式在 bootstrap() 之前就跑完了。如果 guard 檔案最上層寫了 const ADMIN_KEY = process.env.ADMIN_KEY，讀的時候 .env 還沒載入，拿到 undefined。在 canActivate 裡讀，就是在請求進來時才讀，那時設定早就載入了。第 11 課會改成注入 ConfigService，啟動時就驗證設定。

沒設定金鑰時，放行還是拒絕？

部署時漏設 ADMIN_KEY 是很常見的事。這時 guard 有兩種選擇：當作「沒有金鑰要求」而放行，或當作「沒人能通過」而拒絕。前者叫 fail open，出錯時打開大門；後者叫 fail closed，出錯時關上大門。權限檢查一律選 fail closed：誰都不能改價頂多是店長打電話來抱怨，誰都能改價就是這次的事故重演。

為什麼不能用 === 比較金鑰？

=== 比較字串時，遇到第一個不同的字就停下來回傳 false。這代表猜對的前綴越長，比較花的時間越長。單次差距很小，但攻擊者可以送大量請求、統計回應時間：先試所有可能的第一個字，回應最慢的那個大概就是對的，再用同樣方法猜第二個字。這種靠量測時間推出秘密的手法叫計時攻擊（timing attack）。

防法是固定時間比較：不管在哪裡不同，都比完全部位元組才回傳，花的時間跟猜對幾個字無關。Node 內建 crypto.timingSafeEqual(a, b)（認證課第 2 課）。它只接受長度相同的 Buffer，長度不同會丟 RangeError，在 guard 裡沒接住就變成 500。所以先比長度：

const a = Buffer.from(given)
const b = Buffer.from(expected)
return a.length === b.length && timingSafeEqual(a, b)

先比長度會洩漏「金鑰有幾個位元組」，但不會洩漏內容；金鑰夠長、夠隨機（例如 32 個隨機位元組的 hex），知道長度也沒有幫助。

💡 實務上：共用金鑰適合「機器對機器」，不適合給人用
這種金鑰在工作中常見於內部排程呼叫管理 API、合作廠商串接、或專案初期還沒做登入的後台。它的限制是：所有人用同一把，log 只看得出「有人用金鑰改了價格」，查不到是誰；有人離職或金鑰外洩，就得換掉並通知所有使用者。最常見的事故是把金鑰放進前端的環境變數（例如 VITE_ 開頭的變數），打包後任何人打開 DevTools 都看得到；前端拿得到的值都不是秘密。給店長、店員用的後台，就該換成認證課的真正登入與角色。

guard 寫完了，但它現在只是一個 class，Nest 不會自動執行它。下一步是把它掛上去。

guard 寫好了，掛在哪裡才會執行、測試又換得掉？

guard 可以掛在三個層級：全域（所有路由）、controller（那個 controller 的所有方法）、單一路由（一個方法）。同一個請求如果經過好幾層的 guard，執行順序是全域 → controller → 路由，前一個拒絕，後面的就不跑。

金鑰 guard 該掛在全域。原因跟第一節一樣：如果改用 @UseGuards() 一個一個 controller 貼，之後有人新增一個管理用的 controller 卻忘了貼，@AdminOnly() 就形同虛設。掛在全域，guard 會檢查每一條路由，要不要金鑰完全由 @AdminOnly() 決定，不會漏。

決定層級之後，還要選寫法。四種寫法差在兩件事：guard 是誰建立的（Nest 建立才能注入 Reflector 這類依賴），以及測試能不能把它換掉：

寫法範圍能注入依賴測試能用 overrideProvider 換掉
@UseGuards(AdminKeyGuard)這個 controller 或方法能（Nest 建立）要用 overrideGuard
@UseGuards(new AdminKeyGuard(…))同上不能，參數自己傳不能
app.useGlobalGuards(new AdminKeyGuard(…))全域不能，在模組外建立不能；只寫在 main.ts，測試裡甚至不存在
{ provide: APP_GUARD, useExisting: AdminKeyGuard }＋AdminKeyGuard全域能能

表中第一列：用 @UseGuards(類別) 掛的 guard 不是一般 provider，overrideProvider 找不到它，Testing Module 另外提供 .overrideGuard(AdminKeyGuard).useValue(…) 來換。

全域的兩種寫法裡，useGlobalGuards 的問題跟上一節的 app.use() 一樣：在模組外自己 new，依賴要自己傳，而且只寫在 main.ts 時，直接編譯 AppModule 的測試裡根本沒有這個 guard。第 11 課的 guard 要注入 ConfigService，到時候這個限制會更明顯：new 的時候手上沒有 ConfigService。

所以全域 guard 用最後一種，在模組的 providers 裡註冊：

import { APP_GUARD } from '@nestjs/core'

@Module({
  providers: [
    { provide: APP_GUARD, useExisting: AdminKeyGuard },
    AdminKeyGuard,
  ],
})
export class AppModule {}

APP_GUARD 是 Nest 的特殊 token：註冊在這個 token 下的 provider 會變成全域 guard，不管寫在哪個模組。為什麼用 useExisting 而不是 useClass？官方文件的範例用 useClass，但那樣 Nest 會在 APP_GUARD 後面另外建一個實例，跟 AdminKeyGuard 這個 token 沒有關係，測試裡 overrideProvider(AdminKeyGuard) 換不到真正在執行的那一個。官方測試文件建議改成 useExisting：AdminKeyGuard 先當一般 provider 註冊，APP_GUARD 指向同一個實例。這樣測試其他功能時就能跳過金鑰：

const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
  .overrideProvider(AdminKeyGuard).useValue({ canActivate: () => true })   // 測其他功能時跳過金鑰
  .compile()

最後一個細節會在下一節變得很重要：APP_GUARD 可以註冊好幾次，依登記順序執行。

到這裡，改價已經需要金鑰了。但回頭看事故的 log：那個腳本一秒打幾百次。現在它改打 DELETE /products/1，每次換一把金鑰猜，guard 回 403，它就再試下一把，伺服器照樣一秒處理幾百次。

擋住改價之後，腳本還能一直猜：怎麼限流？

限流（rate limiting）是限制同一個客戶端在一段時間內能發幾次請求，超過就回 429 Too Many Requests，請求不會進到 handler。它保護兩件事：不讓腳本把伺服器打垮、讓其他顧客下單失敗，也不讓有人無限次猜密碼或金鑰。有了限流，同一個 IP 對同一條路由一分鐘最多只能試 20 次。32 位元組的隨機金鑰本來就猜不中，但金鑰或密碼很弱的時候，限流就是擋住暴力猜測的那一關；它也讓計時攻擊收集不到足夠的樣本，並且讓腳本拖不垮伺服器、不會害其他顧客下單失敗。演算法和多台伺服器的分散式限流在系統設計課第 10 課；這裡用 Nest 官方的 @nestjs/throttler（練習資料夾裝的是 6.7.1），它本身就是一個 guard，所以也用 APP_GUARD 註冊：

import { ThrottlerGuard, ThrottlerModule } from '@nestjs/throttler'

@Module({
  imports: [ThrottlerModule.forRoot({ throttlers: [{ ttl: 60_000, limit: 20 }] })],
  providers: [{ provide: APP_GUARD, useClass: ThrottlerGuard }],
})
export class AppModule {}

limit: 20 是最多幾次，ttl 是時間窗多長。讀這段設定要注意兩件事：

  • ttl 的單位是毫秒：60_000 是 60 秒。寫成 60 是 60 毫秒，等於沒有限流，而且不會有任何錯誤提醒你。
  • 計數單位：預設依 req.ip 區分客戶端；6.7.1 的原始碼用「controller 名稱＋方法名稱＋客戶端」當 key，所以是每條路由各自計數，不是整個 API 共用一個額度。同一個 IP 打了 20 次 DELETE /products/1，打 GET /products 的額度還在。

全域預設不會適合每一條路由。下單應該更嚴，門口看板每 2 秒來拿一次菜單則不該被擋。個別路由用裝飾器調整：@Throttle({ default: { limit: 3, ttl: 10_000 } }) 改這條路由的額度，default 指的是 forRoot 裡那組沒取名的設定；@SkipThrottle() 讓這條路由完全不限流。兩者都可以貼在 controller 或方法上。

被擋下時回 429，標頭 Retry-After 告訴客戶端幾秒後再試。其他回應標頭見課末。

限流 guard 要排在金鑰 guard 前面

上一節說 APP_GUARD 依登記順序執行，而前一個 guard 拒絕，後面的就不跑。如果金鑰 guard 排在 ThrottlerGuard 前面，猜錯金鑰的請求在第一關就被 403 擋下，根本輪不到限流計數，攻擊者可以無限次猜，限流對這次事故完全沒用。限流要排在驗證前面：每個請求先被計數，超過額度直接 429，連猜的機會都沒有。

上線之後會遇到的兩個限制

本機測得好好的限流，到正式環境可能失效或誤傷，原因都在「計數存在哪裡」和「用什麼認人」：

  • 計數存在記憶體：預設的 storage 是程序裡的一個 Map。開兩台伺服器（或兩個程序），每台各算各的，額度實際上變成兩倍；重新部署計數就歸零。要全域一致，得把計數放到 Redis 這類共用的地方。
  • 反向代理後面的 IP：正式環境前面通常有 Nginx（DevOps 課第 12 課）或雲端負載平衡器，Nest 收到的連線全部來自代理，req.ip 都是同一個位址，所有顧客共用一個額度，一個人用完大家都被擋。代理會把真正的客戶端 IP 寫在 X-Forwarded-For 標頭，Express 要開 trust proxy 才會用它： 
    const app = await NestFactory.create<NestExpressApplication>(AppModule)
app.set('trust proxy', 'loopback')   // 只信任本機上的代理
    只在確定前面是自己的代理時開，而且只信任那一層：前面沒有代理卻開了，任何人都能自己寫 X-Forwarded-For，每次換一個假 IP 就繞過限流。
💡 實務上：限流額度要依路由和使用情境來定
最常加嚴格限流的是登入、寄簡訊或 email 驗證碼、忘記密碼這類「會被猜、或每次都花錢」的 API；一般讀取的 API 額度寬鬆很多，或交給 Nginx、CDN 在更前面擋。設額度前先想清楚誰共用同一個 IP：公司、學校的網路，以及手機網路，常常很多人共用一個對外 IP，設太緊會擋到正常顧客。前端也要處理 429：停用按鈕、依 Retry-After 顯示「請稍後再試」，而不是讓使用者一直重按。

回到週一的事故：每個請求都有編號，客服說得出是哪一次；改價要店長的金鑰；腳本每條路由一分鐘最多 20 次，猜金鑰也一樣。三個缺口都補上了，練習就是把這三件事親手做一遍。

補充與查表

主線用不到、但讀舊專案或查問題時會遇到的細節。

Reflector.createDecorator 的細節

  • NestJS 12 的 nest g decorator 產生的也是 Reflector.createDecorator<T>() 這種寫法。
  • 在 12.3.2 的原始碼裡，不給參數的 @AdminOnly() 會存一個空物件當標記；加上 transform 讓它存 true，讀出來的值才跟型別一致。
  • getAllAndOverride 回傳第一個有定義的值；另一個 getAllAndMerge 會把方法和 class 兩層的值合併（陣列串起來），適合「角色清單」這類累加的標記。

舊寫法：SetMetadata

網路上和舊專案大多是較早的寫法 SetMetadata：用一個常數字串當 key。官方的 @Public() 範例和認證課第 21 課都用它，看到要認得：

export const IS_ADMIN_ONLY = 'isAdminOnly'
export const AdminOnly = () => SetMetadata(IS_ADMIN_ONLY, true)

const adminOnly = this.reflector.getAllAndOverride<boolean>(IS_ADMIN_ONLY, [context.getHandler(), context.getClass()])

差別在型別：SetMetadata 讀出來的型別要自己寫 <boolean>，寫錯 TypeScript 不會發現；createDecorator 的型別跟著裝飾器走。新程式用 createDecorator。

@nestjs/throttler 的其他細節

  • 套件也有 seconds(60)、minutes(1) 這類輔助函式，可以代替手寫毫秒。
  • 沒被擋時回應有 X-RateLimit-Limit、X-RateLimit-Remaining、X-RateLimit-Reset 標頭；被擋時回 429 加 Retry-After。

接手的專案用 @nestjs/passport

很多 Nest 專案的登入檢查不是自己寫 guard，而是用 @nestjs/passport（目前 12.0.2，搭配 passport 0.7.0、passport-jwt 4.0.1）。它把這課 canActivate 裡的事拆成兩半：

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {   // Strategy 來自 passport-jwt
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),   // 憑證從哪裡拿
      secretOrKey: config.get('JWT_SECRET'),                      // 用什麼驗
    })
  }
  validate(payload: { sub: number }) {     // 驗過才會呼叫；回傳值放進 req.user
    return { userId: payload.sub }
  }
}

@UseGuards(AuthGuard('jwt'))               // guard 只剩一行，'jwt' 是 strategy 的名字

對照這課：super() 的設定相當於「取標頭、比對金鑰」，驗證失敗時 AuthGuard 回 401；validate() 相當於驗過之後決定「這個人是誰」。JWT 是認證課第 8 課的簽章 token。讀這種專案時找三樣：Strategy 的 super() 設定、validate() 回了什麼、哪裡用了 AuthGuard('jwt')（全域的話一樣是 APP_GUARD 加 @Public() 排除）。JwtStrategy 沒列進模組的 providers，執行時會出現 Unknown authentication strategy "jwt"。

練習

在 learn/ 執行 node check.mjs nestjs 06 建立 work/06/。起始專案有四個 controller：GET /menu（門口看板每 2 秒來拿一次）、POST /orders（顧客下單）、/products 的 CRUD、GET /whoami。要寫的新檔案已經有空殼，裡面只有註解。第一次執行時 .env.example 會被複製成 .env，npm run start:dev 會讀到裡面的 ADMIN_KEY，可以用 curl -i 自己試。

練習 1：替每個請求編號。

  • 在 src/request-id.middleware.ts 寫 class RequestIdMiddleware：請求帶的 X-Request-Id 符合 1–64 個英數字、-、_ 就沿用，否則用 crypto.randomUUID() 產生；結果放在 req.requestId，並寫進回應標頭 X-Request-Id。
  • 在 src/express.d.ts 替 Express 的 Request 加上 requestId 欄位，req.requestId 才不會有型別錯誤。
  • 在 AppModule 把 middleware 套用到所有路由。測試直接編譯 AppModule，只寫在 main.ts 的不算。
  • 在 src/request-id.decorator.ts 用 createParamDecorator 寫 @RequestId()，讓 GET /whoami 回 { requestId }，值要跟回應標頭一樣，呼叫端送了不合法的編號時也一樣。

練習 2：只有店長能改商品。

  • 在 src/admin-only.decorator.ts 用 Reflector.createDecorator 寫 @AdminOnly()，貼在 POST、PATCH、DELETE /products 上。GET 和 POST /orders 照樣誰都能用。
  • guard 要讀路由上的標記決定要不要檢查，不能用 HTTP 方法或網址判斷；方法和 class 上的標記都要讀：整個 controller 貼 @AdminOnly() 時每個方法都要金鑰，方法上的 @AdminOnly(false) 可以蓋掉它。
  • 在 src/admin-key.guard.ts 寫 AdminKeyGuard：標了 @AdminOnly 的路由要帶 X-Admin-Key，跟環境變數 ADMIN_KEY 相同才放行。沒帶回 401，錯的回 403（長度不同也是 403，不能變成 500；長度指的是位元組數，é 這種字在 UTF-8 佔 2 個位元組），伺服器沒設定 ADMIN_KEY 時一律拒絕。用 timingSafeEqual 比較。
  • 在 AppModule 用 APP_GUARD＋useExisting 註冊成全域 guard。

測試在 import AppModule 之後才設定 ADMIN_KEY，中途還會換一把新的金鑰；會另外建一個測試用的 controller，在 class 和方法上貼你的 @AdminOnly()；最後用 overrideProvider(AdminKeyGuard) 把 guard 換成「一律放行」，確認規則只寫在 guard 裡。

練習 3：用 @nestjs/throttler 加上限流：

  • 全域預設：每個客戶端、每條路由 60 秒最多 20 次，ThrottlerGuard 用 APP_GUARD 註冊。想想它該排在 AdminKeyGuard 前面還是後面。
  • POST /orders：每個客戶端 10 秒最多 3 次，第 4 次回 429。
  • GET /menu：完全不限流。

測試用假的 Date.now() 往前快轉，會檢查 5 秒後還被擋、11 秒後恢復，所以 ttl 的單位要對。也會連續用錯的金鑰呼叫 DELETE /products/1，第 21 次要回 429，不是 403。

練習 4：middleware 和 guard 都能讀標頭。為什麼「這個路由只有店長能用」的判斷放在 guard，而不是 middleware？

✓ guard 能用 context.getHandler() 和 Reflector 讀到路由上的標記，規則跟著路由走；middleware 只能比對網址字串，路由改名就默默失效。a 錯：兩者看得到的資訊不同。c 錯：middleware 可以丟例外，也可以自己送回應，差別在看不看得到 handler。

練習 5：guard 的 canActivate 在沒帶憑證時直接 return false，前端收到什麼？

✓ guard 回傳 false，Nest 一律回 403 Forbidden resource，它不知道你拒絕的原因。a 是常見的誤解：要回 401 得自己 throw new UnauthorizedException()。b 錯：回傳 false 是正常的拒絕，不是錯誤。

練習 6：app.useGlobalGuards(new AdminKeyGuard(reflector)) 和在模組裡寫 { provide: APP_GUARD, useExisting: AdminKeyGuard }，差在哪？

✓ 兩者都是全域，差別在誰建立 guard：useGlobalGuards 要你自己 new，依賴得自己傳，Nest 管不到它。b 忽略了注入與測試的差別。c 錯：APP_GUARD 不管寫在哪個模組都是全域的。

常見錯誤

  • 在 middleware 做需要知道 handler 的判斷：middleware 在路由比對之前執行，看不到路由上的標記，只能比對網址，路由一改名規則就失效。權限判斷放在 guard。
  • middleware 沒呼叫 next() 也沒送回應：請求一直掛著，直到客戶端逾時。每條分支都要走到其中一個結局。
  • 401 與 403 混用：沒帶憑證或憑證無效是 401（UnauthorizedException），知道是誰但沒權限才是 403。guard 回 false 一律是 403。
  • X-Request-Id 照單全收：客戶端能填任何東西，長字串和假欄位會汙染 log。只接受允許清單的格式。
  • handler 用 @Headers('x-request-id') 拿編號：拿到的是客戶端送來的原始值，不是 middleware 決定的編號。用自訂參數裝飾器讀 req.requestId。
  • 全域 guard 用 useGlobalGuards：注入不到依賴（之後的 ConfigService），測試換不掉，只寫在 main.ts 時測試裡根本沒有它。用 APP_GUARD＋useExisting。
  • 在檔案最上層讀 process.env：ES module 的 import 先執行，.env 還沒載入。在請求時讀，或第 11 課改用 ConfigService。
  • 沒設定金鑰時放行：漏設 ADMIN_KEY 就等於拿掉保護。權限檢查出錯時一律拒絕（fail closed）。
  • 直接用 === 比較密鑰：花的時間會洩漏猜對了幾個字。用 timingSafeEqual。
  • timingSafeEqual 遇到長度不同的值：丟 RangeError，變成 500。先比長度。
  • 以為 throttler 的 ttl 是秒：單位是毫秒，ttl: 10 是 10 毫秒。
  • 以為記憶體限流在多台伺服器上是全域的：每個程序各算各的，重新部署就歸零。
  • 放在反向代理後面卻沒設定 trust proxy：所有人的 req.ip 都是代理的位址，共用同一個額度。反過來，沒有代理卻開了 trust proxy，任何人都能偽造 IP 繞過限流。
  • 驗證 guard 排在限流前面：猜錯的請求在驗證就被擋，限流數不到，等於可以無限次猜。

小結

  • 每個請求都要做、跟業務邏輯無關的事，不寫在 handler 裡，而是掛在請求生命週期的某一站：middleware → guard → interceptor → pipe → handler → interceptor → 回應；任何一站丟出例外交給 exception filter。
  • middleware 在路由比對之前執行，看得到 req、res，看不到 handler；做完要呼叫 next()。用 consumer.apply().forRoutes() 套用，app.use() 註冊的拿不到依賴注入、測試裡也不存在。
  • request id 讓一個請求的所有 log 串得起來：沿用前面給的編號但只收允許清單內的格式，否則 randomUUID()；用 declaration merging 擴充 Request 型別，用 createParamDecorator 交給 handler。
  • guard 回答「能不能進來」：ExecutionContext 知道是哪個 handler，Reflector.createDecorator 做有型別的標記，getAllAndOverride 先讀方法再讀 class。
  • 沒帶憑證丟 401，沒權限才 403；密鑰用 timingSafeEqual（先比長度）；設定在請求時讀，沒設定就全部拒絕。
  • 同一種元件依 全域 → controller → 路由 的順序執行；全域 guard 用 APP_GUARD＋useExisting：能注入、測試能換，多個 APP_GUARD 依登記順序執行。
  • @nestjs/throttler 是一個 guard：ttl 是毫秒、每條路由各自計數、存在記憶體；反向代理後面要設定 trust proxy；限流排在驗證前面。
