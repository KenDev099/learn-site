階段 4：快取、背景工作與外部整合 · 第 21 課

排程與事件

到目前為止，後端的每一行程式都是被請求「叫醒」的：客人按下付款，controller 才開始做事；沒有請求進來，程式就只是待在那裡。咖啡店準備正式上線，部署成三台伺服器，這時有三件工作沒有人會來按按鈕：每天凌晨把一年沒用的集點清掉；每天早上比對訂單和金流公司的付款紀錄，把卡住的訂單找出來；每次付款成功，順手在廚房看板加一張單、把金額加進當日營業額。

前兩件是「照時間表觸發」，第三件是「某件事發生之後觸發」。這一課把三件工作依序做出來，每一件都會碰到同一組問題：誰來叫醒它、三台伺服器會不會各做一次、做到一半當機或失敗了怎麼辦。這一課用 @nestjs/schedule 12.0.2 和 @nestjs/event-emitter 12.0.1 實作。

這課的路線：
  1. 凌晨三點誰來叫醒程式：用 @Cron 讓清點數的工作照時間表自己跑，時區寫清楚、「現在」當參數傳進來（開場問題的最小答案）。
  2. 部署成三台，點數為什麼被扣了三次：每個程序都會跑排程，用 advisory lock 讓一台做，用冪等讓重跑也無害。
  3. 早上的對帳：訂單和付款紀錄有哪三種對不上，哪一種能讓程式自己修；訂單有一百萬筆時，怎麼分批、續跑、先試跑。
  4. 付款之後通知廚房：用領域事件讓付款程式不用認識廚房和營業額，而且等交易 commit 之後才發。
  5. 事件漏了會怎樣：程序內事件在失敗、當機、多台時的限制，漏一次就不行的工作為什麼要交給第 20 課的佇列。最後選讀 SSE。
這課會用到：
  • 第 20 課的佇列與 outbox：工作放進 BullMQ 由 worker 在背景做、失敗會重試，所以 worker 要冪等；outbox 在同一個交易裡記下要送的訊息，保證不會漏。
  • Node 課第 8 課的 EventEmitter：emit 發出一個有名字的事件，所有用 on 登記這個名字的函式依序被呼叫。

凌晨三點，誰來叫醒程式？用 @Cron 排程

先看第一件工作。點數過期的規則是：一張集點卡的最後一筆紀錄早於一年前、餘額還大於 0，就把餘額歸零。這段邏輯寫成一個 service 方法不難，難的是「誰來呼叫它」。沒有客人會在凌晨三點發一個「請幫我清點數」的請求，所以程式得自己知道時間到了。

讓程式「在指定的時間或間隔自動執行某段程式」，叫做排程（scheduling）。Linux 上傳統的做法是系統內建的 cron：你寫一行時間表和一個指令，作業系統時間到了就幫你執行。時間表的寫法叫 cron 表示式，用幾個以空白分隔的欄位描述「哪一秒、哪一分、哪一時……」。

@nestjs/schedule 把同樣的概念搬進 Nest：你在 provider 的方法上加一個裝飾器，寫上 cron 表示式，應用程式啟動時，Nest 會找出這些方法，在這個 Node 程序裡各排一個計時器，時間到了就呼叫它。這跟你在 Vue 元件裡寫 setInterval 是同一類東西，只是時間表更有表達力。也因為計時器活在程序的記憶體裡，程序停著的那段時間不會執行，重新啟動後只會從下一次時間開始，錯過的那一次不會自動補跑。

它背後用的是 cron 套件（12.0.2 搭配 cron 4.4.0）。這個版本的 cron 表示式有 6 欄，第一欄是秒；省略秒那一欄、只寫 5 欄，就是傳統 Linux cron 的寫法：

* * * * * *
│ │ │ │ │ └─ 星期（0–7，0 和 7 都是星期日）
│ │ │ │ └─── 月（1–12）
│ │ │ └───── 日（1–31）
│ │ └─────── 時（0–23）
│ └───────── 分（0–59）
└─────────── 秒（0–59，可省略）

* 表示「每一個值都符合」，*/10 表示「每隔 10」，1-5 表示範圍。幾個常見的寫法，第一列就是點數過期要用的：

表示式意思
0 0 3 * * *每天 03:00:00
0 */10 * * * *每 10 分鐘（整點、10 分、20 分…）
0 30 9 * * 1-5週一到週五 09:30
0 0 4 1 * *每月 1 日 04:00

使用分兩步。第一步，在 AppModule 匯入一次 ScheduleModule.forRoot()。官方文件明講只能在一個模組呼叫：匯入兩次，每個工作會被註冊兩次，時間到了就跑兩次。第二步，在 provider 的方法上加 @Cron：

@Injectable()
export class StampCardsService {
  @Cron('0 0 3 * * *', { name: 'expire-stamps', timeZone: 'Asia/Taipei', waitForCompletion: true })
  async expireStampsDaily() {
    const count = await this.expireStamps(new Date())
    this.logger.log(`點數過期：${count} 張卡`)
  }

  async expireStamps(now: Date) { /* 真正的邏輯，時間由參數傳進來 */ }
}

第二個參數裡的三個選項，各自防一種正式環境才會遇到的狀況。

timeZone 決定「03:00」是哪裡的三點。不寫的話，用的是伺服器所在的時區。你的筆電設在台北，開發時一切正常；但雲端主機和容器幾乎都設成 UTC，部署上去之後，「UTC 03:00」是台北 11:00，正好是早上營業的尖峰，清點數的工作跟客人搶資料庫。所以時區一律明確寫出 'Asia/Taipei'，不要依賴伺服器的設定。

name 替這個工作取名字。有了名字，就能從 Nest 提供的 SchedulerRegistry 用 getCronJob('expire-stamps') 拿到它：暫停（stop()）、手動觸發一次，或在測試裡檢查它的時區和下一次執行時間。這一課練習 1 的判分就是這樣檢查你的排程。

waitForCompletion: true 處理「上一次還沒跑完，下一次的時間又到了」。點數過期一天一次不太會重疊，但「每 10 分鐘同步一次外部資料」這種工作，偶爾某次跑了 12 分鐘，就會和下一次同時在跑。打開這個選項，上一次還沒跑完時就跳過這一次。注意它只管得到同一個程序裡的自己，管不到別台伺服器上的同一個工作，下一節會看到這個差別。

除了 @Cron，還有兩個比較簡單的裝飾器：@Interval(1000) 每隔 1000 毫秒執行一次，@Timeout(5000) 在應用程式啟動 5 秒後執行一次。兩個都以毫秒為單位，適合「固定間隔」而不是「固定時刻」的工作，例如第 20 課 outbox 的 relay 每秒掃一次，下一節會再提到它。

最後看程式碼的結構：為什麼要拆成 expireStampsDaily() 和 expireStamps(now) 兩個方法？如果把 new Date() 寫在邏輯裡面，想測「一年前的紀錄會不會過期」，就只能真的等一年，或去改電腦的時間。拆開之後，@Cron 方法只做一件事：取得「現在」，交給真正的邏輯；邏輯方法接收 now 參數，測試直接傳 2030 年的某一天進去，馬上就能看結果。這跟第 3 課注入 CLOCK 是同一個想法：時間是輸入，不是在邏輯裡偷偷讀的全域狀態。

💡 實務上：排程工作最怕的是「沒跑」卻沒人知道
常見的排程有：每天清過期資料、每天早上產生前一天的營業報表、每小時同步外部系統的資料。它們半夜自己跑，壞了不會有客人來報錯，往往等到會計問「昨天的報表呢？」才發現已經停了一週。所以除了失敗時記 error log，也要能發現「該跑的時間過了卻沒跑」：每次跑完記下完成時間和處理筆數，由監控在超過預期時間沒更新時通知。時間也要挑：避開營業尖峰，也不要把所有工作都排在 00:00 一起擠資料庫。新增一個排程時，資深工程師會先問：跑一次要多久、失敗了誰會收到通知、漏跑一天能不能補跑。

到這裡，點數過期已經能每天凌晨自己跑。在你的電腦上只有一個程序，一切正常；但正式環境不會只有一個程序。

部署成三台，林志豪的點數為什麼變成 -6？

正式環境為了扛住流量，也為了某台掛掉時還有別台能接手，通常同時跑好幾個相同的程序，這叫水平擴展（Node 課第 24 課）。上一節說過，@Cron 是在「這個程序裡」排計時器。三台伺服器跑的是同一份程式，每一台啟動時都會各自排好一個 03:00 的計時器，彼此完全不知道對方存在。官方文件的說法是：排程器會在應用程式的每一個程序裡執行每一個工作。

於是上線第一天的凌晨三點，發生了這件事：

三台幾乎同時讀到林志豪的卡「餘額 3、一年沒用」，各自判斷「該過期了」，各自寫入一筆 -3。每一筆單獨看都是合法的資料，資料庫沒有理由擋，結果餘額變成 -6。上一節的 waitForCompletion 幫不上忙：它只讓同一個程序跳過自己的下一次，三台是三個不同的程序。

修法要兩層都有：第一層，讓同一時間只有一台在做；第二層，就算做了兩次，結果也一樣，也就是第 20 課講過的冪等。只做第一層不夠，因為鎖擋得住「同時」，擋不住「先後」：三台的時鐘差了幾秒，A 已經做完、把鎖放掉，B 才醒來，B 一樣拿得到鎖、再做一次。只做第二層也不理想：結果雖然對，但三台同時掃同一批資料是白做工，還可能在資料庫裡互相等鎖。

先看第一層。「只讓一台做」需要一個三台都看得到的裁判，最現成的就是它們共用的那個 PostgreSQL。你在第 15 課看過資料庫的列鎖：FOR UPDATE 鎖住某幾列，別人要改同一列就得等。這裡要鎖的不是某一列，而是「點數過期這個工作」這件事，資料表裡沒有一列能代表它。

PostgreSQL 為這種需求提供了 advisory lock（建議鎖）：一種不綁在任何資料列上的鎖，鎖的只是一個整數，這個整數代表什麼由應用程式自己決定，資料庫完全不管，只保證同一個整數同一時間只有一個人拿得到。「建議」的意思是資料庫不會因為它去擋任何讀寫，大家都說好「先拿到這把鎖才做事」，它才有效。我們想用「expire-stamps」這個名字當鎖，就用 hashtext('expire-stamps') 把字串轉成整數。PostgreSQL 課第 33 課用 SQL 練過它。

advisory lock 有好幾個版本的函式，這裡要的是 pg_try_advisory_xact_lock，名字裡的兩個部分各有原因：

try：拿不到鎖時立刻回傳 false，不等待。沒有 try 的 pg_advisory_xact_lock 拿不到會一直等，等 A 做完放掉鎖，B 接著拿到，然後照樣再做一次，等於只是把三次改成排隊做三次。我們要的是「拿不到就表示別人在做，我直接跳過」。

xact（transaction 的縮寫）：鎖跟著交易，交易 commit 或回滾時自動放掉。另一種是 session 層級的 pg_try_advisory_lock，鎖跟著資料庫連線，要自己呼叫 pg_advisory_unlock 才會放。麻煩在 Prisma 用連線池：上鎖和解鎖的兩句 SQL 不保證走同一條連線，解鎖那句可能在別條連線上執行，什麼也沒解開。鎖就一直留在原本那條連線上，那條連線不關，之後只有剛好借到同一條連線的那次拿得到鎖（session 層級的鎖在同一條連線上可以重複取得），其他時候每台都拿到 false，工作變成時有時無，而且不會報錯。

所以點數過期的做法是：把整個工作放進一個互動式交易（第 15 課的 $transaction(async tx => …)，交易裡可以依序執行多句查詢、中間跑自己的邏輯），第一句執行 SELECT pg_try_advisory_xact_lock(hashtext('expire-stamps'))。拿到 true 的那台繼續做，拿到 false 的直接回傳，什麼都不做；交易結束，鎖自動放掉。練習 2 要你寫出這一段。

再看第二層冪等。點數過期的冪等不靠額外機制，靠「怎麼算餘額」：餘額一律用這張卡所有紀錄加總，包含兌換和之前的過期紀錄。A 已經寫了一筆 -3，B 晚幾秒進來，算出來的餘額是 0，不符合「餘額大於 0」，就不會再寫。如果餘額是另外存在一個欄位、又沒跟著更新，B 讀到的就還是 3。

advisory lock 不是唯一的做法。如果專案已經有第 20 課的佇列，也可以把「時間到了」這件事交給 BullMQ：

做法怎麼運作適合
PostgreSQL advisory lock每台的 @Cron 照樣觸發，工作一開始在交易裡 SELECT pg_try_advisory_xact_lock(hashtext('expire-stamps'))，拿到 true 的那台做事，拿到 false 的直接跳過；交易結束自動放掉已經有 PostgreSQL、工作在一個交易內做得完
BullMQ job scheduler不用 @Cron，排程交給佇列：啟動時 queue.upsertJobScheduler('expire-stamps', { pattern: '0 0 3 * * *', tz: 'Asia/Taipei' })，同一個 id 不管呼叫幾次都只有一份時間表；時間到 BullMQ 產生一個 job，只有一個 worker 拿得到，失敗還能重試已經有第 20 課的佇列、工作要能重試或跑很久

兩者的差別在失敗時：advisory lock 版本失敗了就是失敗，只留一行 log，要等明天再跑；BullMQ 版本會照第 20 課設定的次數自動重試。官方文件另外推薦了一個專門的裝飾器，目前版本還很新，見課末「補充與查表」。

並不是每個排程工作都需要鎖。第 20 課 outbox 的 relay 也是排程工作：

@Interval(1000)
async relay() {
  await this.outbox.publishPending()
}

三台伺服器每秒都會呼叫它，但 relay 用 FOR UPDATE SKIP LOCKED 取資料：每一列被某一台鎖住時，其他台會直接跳過那一列去拿別的，所以每一列只會被一台處理。工作本身就是以「列」為單位分配的，多台同時跑反而分擔了負載，不需要額外的鎖。點數過期不一樣，它要先讀「餘額」再決定寫不寫，三台讀到的是同一個餘額，所以需要上面兩層。

點數過期在一個交易內就做得完，鎖加冪等就夠了。早上的對帳不一樣：它不只是「做一件事」，而是要先找出哪些資料出了問題。

早上的對帳：訂單和付款紀錄對不上時，哪些能讓程式自己修？

第二件工作要先知道付款的完整流程：客人在前台付款 → 金流公司扣款 → 金流公司呼叫我們的網址通知結果（第 22 課的 webhook）→ 我們把訂單改成 paid。這條路上任何一步都可能出錯：金流公司的通知沒送到、我們收到通知後處理到一半當機、有人直接在資料庫手動改了狀態。出錯的結果是兩邊的紀錄不一致，而且沒有人會發現，直到客人來問「我付了錢，為什麼訂單還沒做」。

對帳（reconciliation）就是定期拿兩份「應該一致」的紀錄互相比對，把差異找出來。這裡的兩份紀錄是我們的 orders，和記錄金流公司回報結果的 payments。比對之後，會看到三種差異：

找到差異之後，最直覺的想法是「全部自動修好」。但修之前要問：程式知不知道正確答案是什麼？

「付款成功，訂單還是 pending」（圖中的 #7）意思很明確：錢收到了，金額也對，只是我們沒記上，多半是通知漏了。把它改成 paid，就是補上本來該發生的事，不會錯。這一種可以讓程式自己修。

「金額不一致」（#21，訂單 80 元、只收到 70 元）可能是客人該補收 10 元，也可能是我們的訂單金額算錯、該修的是訂單；「已付款，卻沒有付款紀錄」（#13）可能是有人手動改了資料，也可能是金流那邊漏了紀錄。這兩種，程式猜不出正確答案，猜錯了會多收或少收客人的錢。所以原則是：先回報；只有能確定正確答案、安全的差異才自動修，其他記下來交給人處理。

💡 實務上：對帳報告的讀者通常是財務和客服，不是工程師
只要有收錢的系統，幾乎都會有每日對帳：電商、外送平台、訂閱制服務都是。程式找到差異後，要送到有人會處理的地方，例如寄給財務的每日報表、客服後台的待辦清單，而不是只留在 log 裡。動手前先跟財務確認兩件事：哪一份紀錄算數（通常以金流公司的資料為準），以及「一天」從幾點算到幾點、用哪個時區，否則跨夜的訂單會每天都被當成差異。自動修正也要留下修正紀錄（誰、何時、為什麼改），之後被問到「這筆怎麼變成 paid」才答得出來。

比對規則清楚了，剩下的問題是量。對帳每天都要跑，訂單會一直累積到十萬、百萬筆，對帳程式得把它們全部看過一遍。

一百萬筆訂單怎麼對完？分批、續跑、重跑、試跑

對帳這種「把大量既有資料逐筆檢查、補齊或改正」的程式，跟另外兩種常見工作長得一樣：替新欄位把舊資料補上值，叫資料回填（backfill）；把一批壞掉的資料改正，叫資料修復（repair）。這一節的寫法三者通用。

最直覺的寫法是 const orders = await prisma.order.findMany()，一次全部讀進來再用迴圈處理。資料少時沒事；一百萬筆時，一百萬個物件同時放在程序的記憶體裡，程序直接因為記憶體不足被終止。就算記憶體夠，把整件事包在一個大交易裡修，被修改的列在交易結束前都鎖著，別人要更新同一張訂單只能等好幾分鐘（PostgreSQL 課第 34 課）。

所以要分批：一次只讀一小批（例如 500 筆），處理完、提交，再讀下一批。每批一個短交易，鎖只會被拿住很短的時間。分批這個決定一做，就接連冒出四個問題：下一批從哪裡開始讀？跑到一半被中斷怎麼辦？重跑會不會修兩次？第一次在正式資料上跑，怎麼知道它會改什麼？下面依序回答。

下一批從哪裡開始？用 keyset 游標，不用 OFFSET

分頁最常見的寫法是 OFFSET：第 1 批 skip: 0, take: 100，第 2 批 skip: 100, take: 100。第 16 課講過它在資料多時很慢，因為資料庫得先數過前面那些列才能跳過。批次工作還有一個比「慢」更嚴重的問題：它會漏資料。

對帳只看沒取消的訂單（status <> 'cancelled'），用 OFFSET 時會這樣：

  1. 第 1 批：符合條件的前 100 筆（skip: 0）。
  2. 這時有 30 位客人取消了第 1 批裡的訂單，它們不再符合條件。
  3. 第 2 批：skip: 100，跳過「現在」符合條件的前 100 筆。前面少了 30 筆，原本第 101～130 筆往前移進了前 100 筆，就這樣被跳過了。

這 30 張訂單這一輪永遠不會被檢查，而且沒有任何錯誤訊息。OFFSET 的本質是「數第幾筆」，而批次工作跑的那幾分鐘裡，資料一直在變，「第幾筆」也跟著變。

第 16 課的 keyset 分頁不數位置，只記「上一批最後一筆的 id」，下一批從比它大的 id 開始：WHERE id > $cursor ORDER BY id LIMIT 500。前面的訂單被取消、被新增，都不影響「id 大於 1234 的是哪些」，後面的資料一筆都不會漏。這個 cursor 就叫游標。用 Prisma 寫就是 where: { id: { gt: cursor } } 加 orderBy: { id: 'asc' }（Prisma 另有一個 cursor 選項，這裡不用它的原因見課末）。

跑到一半被中斷？檢查點跟著那一批一起 commit

一百萬筆分成兩千批，中途很可能遇到部署重啟或當機。如果只能從頭來，每次部署都會讓前面的進度白費。解法是檢查點（checkpoint）：每處理完一批，就把游標（這批最後一張訂單的 id）存進資料庫，例如一張 job_checkpoints 表。下次啟動時先讀檢查點，從那裡繼續。

檢查點存在哪裡、什麼時候存，決定它可不可靠。只放在記憶體的變數裡，程序一重啟就沒了。存進資料庫，但跟那一批的修正分開寫，兩者之間當機就會對不上：修正寫了、檢查點沒寫，下次會重做這一批；檢查點寫了、修正沒寫，這一批的修正就永遠漏掉了。所以檢查點要和那一批的修正寫在同一個交易裡，兩者一起成功或一起不算數。整輪跑完之後刪掉檢查點，下次對帳才會從頭開始。

重跑會不會修兩次？修正要冪等

有了檢查點，同一批還是可能被處理兩次：例如前面「部署成三台」那節說的，三台伺服器的 @Cron 同時觸發對帳，或者交易 commit 成功、但回應在網路上遺失，程式以為失敗又重試。所以每個修正都要冪等，重做也不會多改。

第一個工具是第 18 課的條件更新：updateMany({ where: { id, status: 'pending' } })。條件寫在 where 裡，資料庫在更新的那一刻才檢查：如果讀完之後訂單已經被別人改成 paid，或被客人取消了，這句就影響 0 列，什麼都不做。如果寫成無條件的 update({ where: { id } })，就會把一張剛被取消的訂單改回 paid。

第二個工具是唯一鍵：修正紀錄表加上 UNIQUE(order_id, kind)，同一張訂單的同一種修正只能有一筆，就算程式邏輯出錯想記第二次，資料庫也會拒絕。兩者一起，不管重跑幾次、從哪一批續跑，最後的結果都一樣。

第一次在正式資料上跑？先 dry-run，跑完記摘要

修復工具第一次在正式資料上跑，沒有人敢直接按下去：條件寫錯一個字，可能改掉幾萬張訂單。dry-run（試跑）是讓程式照常讀資料、照常分類，但只回報「會修改什麼」，不真的寫入，也不讀、不移動檢查點。不移動，是因為試跑一次就會把正式那次的進度帶走；不從檢查點開始讀，是因為試跑要看的是完整一輪會改什麼，從中間開始只會看到剩下的一部分。先 dry-run，看摘要裡「要改成 paid：20 張」這種數字合不合理，確認了才正式跑。

不論試跑還是正式跑，結束時都用一行 log 記下摘要：掃了幾筆、每一類差異幾筆、花了多久、是不是 dry-run。出事時，這一行是唯一能回答「那天到底改了什麼」的東西。四件事組合起來，程式的骨架是這樣：

async reconcilePayments({ dryRun = false, batchSize = 500 } = {}) {
  const started = Date.now()
  const summary = { scanned: 0, markPaid: 0, missingPayment: 0, amountMismatch: 0 }
  const saved = dryRun ? null : await this.prisma.jobCheckpoint.findUnique({ where: { name: 'reconcile-payments' } })
  let cursor = saved?.cursor ?? 0
  for (;;) {
    const orders = await this.prisma.order.findMany({
      where: { id: { gt: cursor }, status: { not: 'cancelled' } },
      orderBy: { id: 'asc' },
      take: batchSize,
    })
    if (orders.length === 0) break
    // …查這一批的付款、分類…
    cursor = orders[orders.length - 1].id
    if (dryRun) continue
    await this.prisma.$transaction(async tx => {
      // …條件式 UPDATE、寫修正紀錄…
      await tx.jobCheckpoint.upsert({ where: { name: 'reconcile-payments' }, create: { name: 'reconcile-payments', cursor }, update: { cursor } })
    })
  }
  // 整輪跑完：刪掉檢查點，下次從頭對帳（dryRun 不碰）
  this.logger.log('對帳完成', { ...summary, dryRun, ms: Date.now() - started })
  return summary
}

每天的對帳用 @Cron 觸發；要手動試跑時，常寫一支只啟動 DI 容器、不開 HTTP 的小程式（第 20 課提過的 NestFactory.createApplicationContext），讀 --dry-run 參數再呼叫同一個方法。

回到前面「部署成三台」那節的問題：對帳也是 @Cron，三台都會觸發。它跨好幾個交易，沒辦法像點數過期那樣用一個交易層級的鎖包住整件事；但它的每一步都冪等，三台同時跑，結果也不會錯，只是重複做工。想要同一時間只有一個實例在跑，可以另外搭配 advisory lock，或改用 BullMQ 的 job scheduler。另外，大量回填該不該寫在 migration 裡，見課末「補充與查表」。

前兩件工作都是「時間到了」觸發的。第三件不一樣：它不看時間，而是在「付款成功」這件事發生之後才要做。

付款之後要通知廚房和營業額，付款程式需要認識它們嗎？

付款成功後，廚房看板要多一張單、當日營業額要加上這筆金額。最直覺的寫法是在 OrdersService.pay 的最後依序呼叫 kitchen.notify()、stats.add()。這樣能動，但付款模組因此必須 import 廚房模組和統計模組，認識它們的 service。下個月行銷要「付款後發優惠券」，又得打開付款程式加一行；再下個月要「付款後通知外送平台」，再加一行。付款是全店最不該常常改動的程式，每改一次都可能把收錢的流程改壞。

問題出在依賴的方向：每多一個「付款之後要做的事」，付款模組就得多認識一個模組。領域事件（domain event）把方向反過來。付款模組不再呼叫任何人，只宣布一件已經發生的事：「訂單已付款」。誰在乎這件事，誰自己來登記要聽。事件名稱用過去式（order.paid，而不是 pay.order），因為它描述的是既成事實，不是命令；聽的人不能拒絕它、也改變不了它，只能對它做出反應。

這樣一來，付款模組不知道有誰在聽、有幾個在聽。新增優惠券功能，只要在優惠券模組裡加一個 listener，付款程式一行都不用改。這種「發送者和接收者不需要互相認識」的關係叫解耦。Node 課第 8 課的 EventEmitter 就是這個模式；@nestjs/event-emitter 把 eventemitter2 這個套件包成 Nest 的模組，讓 listener 可以用裝飾器寫在任何 provider 上：

// app.module.ts：整個應用程式匯入一次
EventEmitterModule.forRoot()

// orders/order-paid.event.ts：事件的內容，只放聽的人需要的事實
export class OrderPaidEvent {
  constructor(readonly orderId: number, readonly customerId: number, readonly total: number, readonly paidAt: Date) {}
}

// orders/orders.service.ts：發送
constructor(private readonly events: EventEmitter2) {}
this.events.emit('order.paid', new OrderPaidEvent(order.id, order.customerId, order.total, new Date()))

// kitchen/kitchen.listener.ts：在別的模組聽
@OnEvent('order.paid', { async: true })
async handleOrderPaid(event: OrderPaidEvent) {
  await this.prisma.kitchenNotice.create({ data: { orderId: event.orderId } })
}

注意依賴的方向：事件類別 OrderPaidEvent 放在發送方的 orders 資料夾，廚房的 listener import 它；付款這一側完全沒有 import 廚房。事件內容只放聽的人需要的事實（哪張訂單、哪位客人、多少錢、什麼時候付的），不放整個 Prisma 物件，聽的人才不會跟付款的資料結構綁在一起。

{ async: true } 處理的是「付款要不要等 listener」。emit 預設是同步的：它會當場依序呼叫每一個 listener，全部呼叫完才回到付款程式的下一行。加上 async: true，listener 會被排到稍後執行，emit 馬上返回，付款的回應不用等廚房寫完資料。

還有一件事決定了 emit 寫在哪一行：要在交易 commit 之後才發。如果寫在 $transaction 的 callback 裡，事件發出去的時候交易還沒結束，之後仍可能回滾：例如後面的加點失敗、或 commit 時遇到衝突。這時付款已經不算數，廚房卻已經收到通知，開始做一杯沒付錢的咖啡。這跟第 20 課「在 commit 前 queue.add」是同一個錯：在結果確定之前，就把結果告訴了別人。正確的寫法是等 $transaction 回傳，確定 commit 了，再 emit：

async pay(id: number) {
  const order = await this.prisma.$transaction(async tx => { /* 改狀態、加點 */ })
  this.events.emit('order.paid', new OrderPaidEvent(…))   // 交易已經 commit
  return order
}

付款失敗（交易回滾、回 422 或 409）時，$transaction 會丟出錯誤，程式根本走不到 emit 那一行，所以不會發出事件。到這裡，付款程式已經不認識廚房和營業額。但「發出去了」不等於「做完了」，接下來看事件在出錯時會怎樣。

營業額沒加上、伺服器剛好重啟，事件會怎樣？

EventEmitter2 是程序內事件（in-process event）：emit 只是在同一個 Node 程序的記憶體裡，找出登記了這個名字的函式、呼叫它們。事件沒有被存到任何地方，也不會離開這個程序。這個設計讓它非常輕，但也決定了它在三種狀況下的行為。

listener 丟出錯誤時，預設只記一行 log

假設統計的 listener 寫入 daily_stats 時出錯了。@OnEvent 有一個選項 suppressErrors，預設是 true：listener 丟出的錯誤會被接住，用 Logger.error 記下來，不會傳回發送者。好處是統計壞掉不會連帶讓付款失敗，客人照樣付款成功、廚房照樣收到單。壞處是它可能默默失敗：營業額少算了一筆，系統裡只留下一行 error log。所以這些 log 一定要接到監控，有人會看到。

你可能會想：那改成 suppressErrors: false，讓錯誤傳回付款，付款就知道失敗了？不會。前面加了 async: true，emit 早就返回了，付款程式已經往下走，錯誤沒有地方可以回去。它會變成一個沒有人 catch 的 Promise 失敗，也就是 unhandled rejection；Node 對這種錯誤的預設處理是讓整個程序結束，等於統計的一個錯誤讓整台伺服器重啟。

真的要讓錯誤回到付款，得拿掉 async: true，發送者改成 await this.events.emitAsync(…)，等所有 listener 跑完、把錯誤丟回來，付款再回 500。但這時交易早就 commit 了：錢收了、訂單是 paid，客人卻看到「付款失敗」，可能再付一次。所以對 listener 的錯誤，正確的態度是「接受它只會記 log」，並據此決定什麼工作能交給事件。

程序當機時，事件就不見了

emit 之後、listener 把資料寫進資料庫之前，程序被重啟了（部署、記憶體不足、機器故障）。這個事件只存在於那個程序的記憶體裡，程序沒了，事件就沒了：沒有重試、沒有紀錄，重啟之後也不會有人知道曾經有一個 order.paid 沒處理完。

只在同一台伺服器上

三台伺服器是三個程序，A 伺服器發出的事件，只有 A 自己的 listener 聽得到，B 和 C 不知道。廚房看板和營業額寫進的是共用的資料庫，所以哪一台處理都沒差；但如果某個功能依賴「所有伺服器都收到這個事件」（例如清掉每台伺服器各自記憶體裡的快取），程序內事件就做不到。另外，應用程式還在啟動、listener 還沒登記好時發出的事件也可能沒人收到，細節見課末。

把這些限制和第 20 課的佇列並排，差別就清楚了：

程序內事件（EventEmitter2）佇列（第 20 課 BullMQ ＋ outbox）
當機時事件遺失工作留在 Redis／outbox，恢復後繼續
失敗時記一行 error log自動重試，用完次數進 failed
成本幾乎沒有：一次函式呼叫Redis、outbox 表、relay、冪等的 worker
適合掉了也沒關係、或有別的管道補救：廚房看板（店員還看得到訂單列表）、快取失效、即時通知一定要完成：寄收據、加點、退款、通知外部系統

判斷方法是問自己：「這件事漏了一次，會有人發現並補救嗎？」廚房看板漏了一張，店員看訂單列表就會發現，代價很小，用事件，簡單又解耦。寄收據、加點、退款漏了，沒有人會發現，或者補救的代價很高，就在付款的交易裡寫 outbox，交給佇列。不要讓 listener 去寫 outbox：listener 在 commit 之後才執行，commit 和 listener 之間當機一樣會漏，outbox 的保證來自「跟業務資料在同一個交易裡寫入」，listener 做不到這一點。

💡 實務上：事件好寫，但多了之後很難追
事件讓模組解耦，代價是讀程式的人看不出「付款之後到底會發生哪些事」，只能全專案搜尋 'order.paid' 這個字串。所以事件名稱集中定義成常數、事件類別放在發送方的模組裡，找起來才容易。也不是每個後續動作都值得變成事件：如果只有一個模組在乎、而且以後也不太會變，直接呼叫反而一眼就看得懂。code review 看到新的 @OnEvent 時，資深工程師會先問：這裡真的需要解耦嗎？還是只是把一次直接呼叫藏了起來？

到這裡，開場的三件工作都有了答案：點數過期用 @Cron 加 advisory lock 和冪等；對帳用分批、檢查點、冪等修正和 dry-run；付款後的通知用領域事件，一定要完成的交給佇列。最後一節是選讀，看程序內事件還能怎麼用來推送畫面。

選讀：用 SSE 把訂單狀態推給前端

客人付完款，Vue 前台想即時顯示「製作中 → 可取餐」。前端每隔幾秒打一次 API 問狀態（輪詢）可以做到，但大部分請求都只得到「還沒好」。另一種做法是讓伺服器在狀態改變時主動推給前端。

SSE（Server-Sent Events）是伺服器維持一條 HTTP 連線、持續推送文字事件給瀏覽器的標準，前端用原生的 new EventSource('/orders/7/events') 接收，比 WebSocket 簡單（單向、會自動重連）。Nest 用 @Sse() 回傳第 9 課的 RxJS Observable，每個值是一個 MessageEvent（@nestjs/common 的介面，data 是要送出的內容）。下面把程序內的 order.ready 事件轉成 Observable，只留下這張訂單的：

@Sse(':id/events')
events(@Param('id', ParseIntPipe) id: number): Observable<MessageEvent> {
  return fromEvent<OrderReadyEvent>(this.emitter, 'order.ready').pipe(
    filter(e => e.orderId === id),
    map(() => ({ data: { status: 'ready' } })),
  )
}

它聽的是程序內事件，所以碰到上一節「只在同一台」的限制：客人的 SSE 連線連到 A，廚房在 B 按下「可取餐」，事件只在 B 發出，A 收不到，客人的畫面就不會更新。多台時要讓各台透過 Redis pub/sub 互相轉發事件，這不在本課範圍。

常見錯誤

  • 以為 cron 只會跑一次：每台伺服器、每個程序都會跑。用 advisory lock 或 BullMQ job scheduler 讓一台做，工作本身也要冪等。
  • cron 沒指定時區：用的是伺服器的時區，雲端多半是 UTC，03:00 變成台北 11:00。一律寫 timeZone: 'Asia/Taipei'。
  • 邏輯裡直接 new Date()：測試只能等到真的那一天。@Cron 方法取得現在時間，邏輯方法接收 now。
  • 用 session 層級的 advisory lock：pg_try_advisory_lock 沒 unlock 就一直鎖著，連線池裡的連線也不一定是同一條。用 pg_try_advisory_xact_lock。
  • 在交易裡發事件：交易回滾了，事件已經出去。commit 之後才 emit。
  • 以為程序內事件不會遺失：當機就沒了，失敗也不重試。一定要完成的工作交給佇列（outbox）。
  • listener 自己 try/catch 把錯誤吞掉：連 error log 都沒有，壞了也沒人知道。讓預設的 suppressErrors 記 log，並監控 log。
  • 批次工作用 OFFSET：資料在途中變動時會跳過或重複。用 keyset 游標。
  • 一次把整張表載入記憶體：findMany() 不加 take，資料一多程序就爆。分批，每批短交易。
  • 修正不冪等：無條件 UPDATE 會把讀完之後被取消的訂單改回 paid，重跑也可能重複記錄。用條件式 UPDATE 加唯一鍵。
  • 沒有檢查點，或檢查點只在記憶體：中斷後只能從頭跑。檢查點寫進資料庫，和那一批的修正同一個交易。
  • 沒有 dry-run 就直接修正式資料：先 dry-run 看摘要，數字合理再正式跑。
  • 把大量回填塞進一個 migration：一個長交易鎖住大量資料列、失敗整個重來。migration 只改結構，資料用批次工作補。

補充與查表

@OnOneInstance（@nestjs/locks）

官方文件推薦用 @nestjs/locks 的 @OnOneInstance() 裝飾器處理「多台只跑一次」，它用共用的鎖存放處（PostgreSQL 或 Redis）協調。目前是 0.0.x 版、才剛發布，先知道有它，正式專案等它穩定。

BullMQ 6 移除了 repeat 選項

BullMQ 6 已經移除舊的 repeat 選項，週期性工作一律用 upsertJobScheduler（BullMQ 官方的 v5 → v6 遷移指南）。網路上舊教學的 queue.add(name, data, { repeat: … }) 在這門課的版本不能用。

Prisma 的 cursor 選項

Prisma 的 findMany 有一個 cursor 選項，但它會把游標那一筆也包含進結果，需要搭配 skip: 1 跳過。批次工作直接寫 where: { id: { gt: cursor } } 比較清楚。

啟動完成前發出的事件

官方文件說，在 onApplicationBootstrap 之前或期間發出的事件可能遺失，因為 listener 可能還沒註冊好。官方提供 EventEmitterReadinessWatcher，在那之前要發事件時先 await watcher.waitUntilReady()。

批次工作跟 migration 的分工

結構變更（加欄位、加 NOT NULL）照 PostgreSQL 課第 34 課的步驟用 migration 做；把幾百萬列舊資料補上新欄位的值，用這一課這種能分批、能續跑的工作做。不要把大量更新塞進 migration：一句 UPDATE 幾百萬列就是一個長交易，那些列在交易結束前都鎖著，別人要改同一列只能等；失敗了整個回滾、從頭來。

小結

  • 沒有請求會觸發的工作，用排程照時間表執行：ScheduleModule.forRoot() 匯入一次，@Cron('秒 分 時 日 月 星期', { name, timeZone: 'Asia/Taipei', waitForCompletion })、@Interval、@Timeout；SchedulerRegistry 可以取出工作。邏輯放在接收 now 的方法裡，測試才能指定時間。
  • 排程的計時器活在每個程序裡，部署幾台就跑幾次。用 pg_try_advisory_xact_lock 或 BullMQ 的 upsertJobScheduler 讓一台做，工作本身也要冪等，因為鎖擋不住先後執行。
  • 對帳比對兩份應該一致的紀錄：只自動修能確定答案的差異，其他回報給人。
  • 大量資料的工作：keyset 游標、每批一個短交易、檢查點和修正同一個交易、條件式 UPDATE ＋唯一鍵、dry-run 與摘要 log。
  • 領域事件讓發送者不用認識聽的人：commit 之後 emit，listener 用 @OnEvent(…, { async: true })。
  • 程序內事件會遺失、預設只記錯誤 log、只在同一台：掉了沒關係的用事件，一定要完成的用佇列。
