階段 4：快取、背景工作與外部整合 · 第 23 課

OpenAPI 文件與 API 演進

你在 Vue 前台寫下單頁，後端同事丟來一句「POST /orders，body 照 DTO 送」。DTO 在後端的 repo 裡，你看不到；qty 上限多少、note 能不能不送、庫存不足時回什麼，只能一個一個問，或是送錯了看 400 猜。三個月後後端把 GET /menu 改成依分類分組，Vue 前台跟著改了，已經上架、使用者還沒更新的 iOS App 卻開始閃退。

這兩件事是同一個問題的兩面。API 是後端和每一個客戶端之間的約定，而這份約定只寫在後端的程式碼裡：看不到，前端只能猜；改的時候沒人檢查，就有客戶端在不知情的情況下壞掉。這一課沿著咖啡店的 POST /orders 和 GET /menu，先把約定寫成一份從程式產生、機器讀得懂的文件，再用這份文件讓 Vue 前台自動拿到型別、讓非改不可的修改以新版本推出，最後在 PR 合併前自動擋下會弄壞客戶端的修改。實作用的是 @nestjs/swagger 12.0.5。

這課的路線：
  1. 前端看不到 DTO：OpenAPI 是什麼，為什麼要一份從程式產生、機器讀得懂的 API 說明。
  2. 從 Nest 程式產生文件：@ApiProperty 補上執行時看不到的欄位；CLI 外掛能代勞多少，為什麼測試裡它不生效。
  3. 庫存不足回什麼：錯誤回應也寫進文件；Vue 前台從文件產生型別，後端改了欄位，前端編譯時就報錯。
  4. iOS App 為什麼會閃退：哪些修改會弄壞客戶端，回應的形狀非改不可時，怎麼讓 v1、v2 並存，再讓 v1 退場。
  5. PR 改了 DTO 欄位：怎麼在合併前自動抓出不相容變更。
這課會用到：
  • 第 7 課的 DTO：用 class 加 class-validator 裝飾器（或 zod schema）描述 body 的形狀與規則，ValidationPipe 依它驗證。
  • 第 8 課的錯誤格式：所有錯誤回應用同一種固定格式，裡面的 errorCode 讓前端判斷是哪一種錯。
  • 第 10 課的 configureApp：把全域 pipe、filter 等設定收在一個函式，main.ts 和 e2e 測試都呼叫它，兩邊的行為才一致。
  • TypeScript 課第 20 課的索引存取型別：T['x'] 取出型別 T 裡 x 屬性的型別。

前端看不到 DTO：怎麼讓 API 自己說清楚怎麼呼叫？

先把前端缺的東西列出來。要送出一張訂單，Vue 前台需要知道：網址和方法；body 有哪些欄位、每個欄位的型別和限制（qty 是不是整數、最多幾杯）；哪些欄位可以不送；成功時回什麼；失敗時回哪個狀態碼、哪個 errorCode。這些資訊後端其實全都有，散在 controller 的路由、DTO 的 class-validator 裝飾器、第 8 課的錯誤類別裡。問題在於它們只存在後端 repo 的 TypeScript 裡，前端要嘛去翻，要嘛去問。

常見的補救是寫一份說明：Notion 頁面、Slack 上貼一段、口頭交代。這些做法有同一個毛病：說明和程式碼是兩份東西。後端把 @Max(10) 改成 @Max(20)，不會有人記得回去改 Notion，幾週之後說明就開始說謊，而且沒有人會發現。要讓說明可靠，它必須滿足兩個條件：

  • 從程式碼直接產生：程式改了，說明自動跟著改，不靠人記得。
  • 格式固定、程式讀得懂：不只給人看，還能交給工具，產生前端型別、比對新舊版本。

OpenAPI 就是這樣的格式。它是描述 HTTP API 的標準，一份 JSON 或 YAML 檔，寫清楚有哪些路徑、每個方法收什麼參數與 body、會回哪些狀態碼、每種回應長什麼樣。例如 qty 這個欄位，在文件裡會寫成 { "type": "integer", "minimum": 1, "maximum": 10 }：人看得懂，程式也讀得懂。

因為是寫給程式讀的，同一份文件可以拿來做好幾件事，這一課會依序用到三件：

  • Swagger UI：把 OpenAPI 文件變成網頁，每個 API 有說明、範例，還能直接填參數按「Try it out」打打看。前端想知道 POST /orders 怎麼送，打開這個網頁就好。
  • 產生前端的 TypeScript 型別，甚至整個 API 客戶端：後端改了欄位，前端重新產生，vue-tsc 直接告訴你哪裡要改。
  • 自動擋下會弄壞客戶端的修改：團隊通常會設定 CI，每次開 PR 時自動跑測試、lint 這些檢查，沒過就不能合併。在 CI 裡比對新舊兩份 OpenAPI 文件，就能在合併前發現「這次修改刪掉了一個回應欄位」。

圖上箭頭的方向就是這一課的做法：程式是來源，文件由程式產生，這叫 code-first（先寫程式）。也有團隊反過來，先寫 OpenAPI 檔、前後端一起審過再照著實作，叫 contract-first（先寫契約）。NestJS 的 @nestjs/swagger 是 code-first。咖啡店的前後端在同一個團隊、改得很快，最怕的是文件跟程式各說各話，code-first 正好解決這一點；要開放給外部合作夥伴串接的 API，常會改選 contract-first，讓設計在動工前就被雙方討論過。兩者的完整比較見課末「補充與查表」。

不管哪一種，文件都要在寫 API 的同時寫，不是上線前才補：前端開始串接的那一天，就是需要它的那一天。所以這一節的答案是：讓 Nest 從程式產生一份 OpenAPI 文件。接下來的問題是，Nest 要從哪裡知道 DTO 有哪些欄位？

怎麼從 Nest 程式產生這份文件？

產生文件分兩步：組出文件，再把它掛到網址上。設定放在第 10 課的 configureApp，main.ts 和測試都會套用，兩邊拿到的是同一份文件。這一點後面會很重要：練習的判分就是在 Vitest 測試裡產生文件來檢查，最後一節的 CI 比對也常這樣做。

import { DocumentBuilder, SwaggerModule } from '@nestjs/swagger'

export function configureApp(app: INestApplication) {
  const config = new DocumentBuilder()
    .setTitle('咖啡店 API')
    .setVersion('1.0')
    .build()
  // 第三個參數可以傳函式：第一次有人打開 /docs 才產生文件
  SwaggerModule.setup('docs', app, () => SwaggerModule.createDocument(app, config))
}

三個角色各管一件事：

  • DocumentBuilder 設定整份文件的資訊，例如標題和 API 的版本號。
  • SwaggerModule.createDocument 掃過每個 controller 的路由與裝飾器，組出 OpenAPI 文件。
  • SwaggerModule.setup('docs', …) 註冊三個網址：/docs 是 Swagger UI，給人看、給人試打；/docs-json 和 /docs-yaml 是文件本身，給程式讀。下一節產生 Vue 型別、最後一節 CI 比對，讀的都是 /docs-json。

如果沒有開 CLI 外掛（下一節會講；練習專案的 nest-cli.json 其實開著，所以你在 work/23 用 start:dev 看會有欄位），這時打開 /docs，POST /orders 已經出現了，body 的欄位卻是空的。在 Vitest 測試裡用 createDocument 產生文件時，就算外掛開著也是這個結果。原因要從 Nest 在執行時看得到什麼說起。路由的路徑、方法、@Body() 的類別，都寫在裝飾器裡，執行時還在，所以 Nest 知道。它不知道的是 DTO 有哪些欄位：TypeScript 的型別在編譯後就消失了。執行時還留得下來的，是裝飾器掛上去的資料：裝飾器在程式載入時會執行，把一些資料（metadata）掛在類別上，執行時可以讀回來；@ApiProperty 做的就是掛這種資料，Nest 產生文件時再去讀。沒有裝飾器掛 metadata 的欄位，執行時就等於不存在。class-validator 的 @Max(10) 是寫給驗證用的，@nestjs/swagger 預設不會拿它來產生文件。結果文件裡的 CreateOrderDto 就是 { "type": "object", "properties": {} }，前端看到的跟沒有文件一樣。

解法是用 @ApiProperty 把每個欄位寫出來，讓它在執行時也留下紀錄：

export class OrderItemDto {
  @ApiProperty({ type: 'integer', minimum: 1, maximum: 10, example: 1 })
  @IsInt() @Min(1) @Max(10)
  qty: number

  @ApiProperty({ enum: ['S', 'M', 'L'], example: 'M' })
  @IsIn(['S', 'M', 'L'])
  size: 'S' | 'M' | 'L'
}

export class CreateOrderDto {
  @ApiProperty({ type: [OrderItemDto] })     // 陣列：元素型別放在 [] 裡
  @ValidateNested({ each: true }) @Type(() => OrderItemDto)
  items: OrderItemDto[]

  @ApiPropertyOptional({ maxLength: 50 })     // 選填：不會出現在 required
  @IsOptional() @IsString() @MaxLength(50)
  note?: string
}

逐一看這幾個寫法在文件裡變成什麼：

  • type: 'integer'：number 在文件裡預設是 number，代表可以有小數。qty 是杯數，寫成 integer，前端產生的型別和表單才知道不用處理小數。
  • enum: ['S', 'M', 'L']：文件會列出允許的值，前端產生的型別會是 'S' | 'M' | 'L'，而不是任意字串。
  • type: [OrderItemDto]：陣列要把元素的類別放進 []，文件才知道 items 的每一個元素長什麼樣。
  • @ApiPropertyOptional：欄位不會列進 schema 的 required，前端就知道 note 可以不送。
  • example：Swagger UI 顯示的範例值。

注意這裡有兩套裝飾器，各管一件事。@IsInt() @Max(10) 在執行時擋下不合格的請求；@ApiProperty 只寫進文件，不驗證任何東西。所以兩者要說同一件事。文件寫 maximum: 10、驗證卻是 @Max(20)，前端以為最多 10 杯，把 11 杯擋在畫面上，其實伺服器收得下；反過來，文件寫 20、驗證寫 10，前端照文件送 15 杯，收到 400。這種不一致不會有任何錯誤訊息，只能靠測試比對文件與真的行為，練習 1 的判分就是這樣做的。

回應的形狀也是同樣的道理。路由回傳什麼，Nest 在執行前看不到，要用 @ApiCreatedResponse({ type: OrderResponse })（201）、@ApiOkResponse（200）這類裝飾器寫出來，OrderResponse 的欄位一樣用 @ApiProperty 描述。另外 @ApiTags('orders') 讓 Swagger UI 把路由分組；不寫時的預設行為見課末。

💡 實務上：/docs 要不要開在正式環境，上線前就要決定
Swagger UI 列出每一條路由、每個欄位，等於把後台的地圖交給任何打得開網址的人，連內部用的管理 API 也一覽無遺。常見的做法是只在開發與 staging 環境呼叫 SwaggerModule.setup（用環境變數判斷），或在正式環境放在登入、內網之後。如果 API 本來就要給外部串接，就另外整理一份只含公開路由的文件。資安審查常會問這一題，資深工程師會在第一次部署前就把它寫進設定，而不是等被掃描出來才關。

到這裡，POST /orders 的文件完整了。代價也很明顯：每個欄位的規則寫了兩次，一次給 class-validator、一次給 @ApiProperty。有沒有辦法少寫一份？

每個欄位寫兩次太囉嗦：CLI 外掛能代勞嗎？

@nestjs/swagger 為此提供了 CLI 外掛。要理解它，先看 nest build 在做什麼：它透過 TypeScript 編譯器（tsc）的 API 把 .ts 轉成 .js。這個 API 允許在轉換時掛上額外的步驟（transformer），在輸出的 JS 裡多寫一些程式碼；直接在終端機執行 tsc 指令則沒有這個入口。Swagger 外掛就是這樣一個 transformer。它之所以能自動知道欄位，是因為編譯的當下型別還沒消失，外掛讀得到 note?: 的問號、讀得到 @Max(10)，再把等同 @ApiProperty 的 metadata 寫進輸出的 JS，省下你手寫。

開啟的方法是在 nest-cli.json 的 compilerOptions 裡加上 "plugins": ["@nestjs/swagger"]，寫在最外層不會生效：

"compilerOptions": {
  "plugins": ["@nestjs/swagger"]
}

之後 nest build 會自動替檔名結尾是 .dto.ts、.entity.ts 的類別補上 @ApiProperty：note?: 的問號變成選填，class-validator 的 @Max(10) 變成 maximum: 10，還會依 handler 的回傳型別補上回應。

聽起來可以把上一節的 @ApiProperty 全部刪掉。關鍵在「編譯時」這三個字：外掛是 tsc 的一個轉換步驟，沒經過 tsc 的地方就沒有它。這一課的練習專案實際量到的結果：

怎麼執行經過 tsc 嗎沒寫 @ApiProperty 的 CreateOrderDto
nest build → node dist/main.js是欄位、必填、minimum／maximum 都有
Vitest（第 5 課：Vite 用 Oxc 轉譯，只拿掉型別）否{ "type": "object", "properties": {} }
SWC 建置（nest start -b swc）否要加 --type-check 外掛才會跑（官方文件）

所以只靠外掛時，正式環境的文件是完整的，測試裡產生的文件卻是空的。上一節說過，練習的判分在測試裡產生文件，CI 的比對也常這樣做。拿一份空文件去檢查，好一點的情況是測試失敗；更糟的情況是測試通過了：比對兩份空的 schema，當然找不到任何不相容變更，檢查等於什麼都沒做。外掛還只處理特定檔名，order-response.ts 這種名字就被跳過，文件裡少了整個回應卻不會有任何警告。

因此這一課的做法是手寫 @ApiProperty：多寫幾行，換來在哪裡執行都產生同一份文件。團隊習慣用外掛也可以，但要知道測試看到的文件跟正式環境的不同，不能在測試裡檢查文件。第 7 課的 zod 路由不受這個限制，用了 Swagger 之後 PartialType 要改從哪裡匯入，這兩件事見課末。

成功時的請求和回應都寫清楚了。但開場那位寫下單頁的前端，最常問的其實是另一題：庫存不足的時候，會收到什麼？

庫存不足時回什麼？把錯誤回應也寫進文件

只記錄 201 的文件，前端只知道成功時拿到什麼。下單頁真正難寫的是失敗的分支：收到 409 OUT_OF_STOCK 要顯示「這杯賣完了，要不要換一杯？」，收到 400 VALIDATION_FAILED 要把填錯的欄位標紅。第 8 課花了一整課讓錯誤有固定的格式與 errorCode，就是為了讓前端能這樣判斷；文件沒寫，前端還是只能去翻後端程式，或是故意送錯一次看看。

做法是把錯誤格式寫成一個文件用的類別 ErrorResponse（練習專案已經寫好，欄位都有 @ApiProperty），每個錯誤狀態碼都指向它，並附上一個完整的範例：

@ApiConflictResponse({
  description: '庫存不足（errorCode: OUT_OF_STOCK）',
  type: ErrorResponse,
  example: { statusCode: 409, error: 'Conflict', message: '庫存不足', errorCode: 'OUT_OF_STOCK', requestId: '…' },
})

一條路由這樣寫沒問題，但咖啡店有十幾條路由，每條都有兩三種錯誤。各自手寫，description 的寫法、example 的欄位很快就不一致；哪天 ErrorResponse 多了一個欄位，要改幾十個地方。重複的裝飾器組合，該收成一個。

收的工具是 @nestjs/common 的 applyDecorators。裝飾器本身就是函式，applyDecorators 接收好幾個裝飾器，回傳一個新的裝飾器；把這個新的套在方法上，就等於把裡面的每一個依序套上。用它包出一個 @ApiErrorResponses，每條路由只要列出自己可能回的錯誤：

export function ApiErrorResponses(...errors: ApiError[]) {
  return applyDecorators(...errors.map(e => ApiResponse({ status: e.status, type: ErrorResponse, /* … */ })))
}

// 用起來
@Post()
@ApiErrorResponses(
  { status: 400, errorCode: 'VALIDATION_FAILED', description: '欄位格式不對' },
  { status: 409, errorCode: 'OUT_OF_STOCK', description: '庫存不足' },
)
create(@Body() dto: CreateOrderDto) { … }

現在錯誤在文件裡長什麼樣，只由 ApiErrorResponses 一個地方決定，路由只負責說「我會回哪幾種錯」。這個手法不限於文件，課末列了另一個常見用法。

文件現在寫清楚了成功與失敗。前端除了打開 /docs 用眼睛看，還能怎麼用這份文件？

Vue 前台怎麼用這份文件？產生 TypeScript 型別

前端串接 API，通常會先寫一份型別：interface CreateOrder { items: …; note?: string }。這又是同一份約定的第二個副本，跟 Notion 說明有一樣的毛病：後端改了欄位，沒有人會來改你的 interface，錯誤要等到執行時才出現。既然 OpenAPI 文件機器讀得懂，型別就該由工具從文件產生。常用的工具是 openapi-typescript，在 Vue 專案裡執行（流程示範，練習專案沒有安裝它）：

npx openapi-typescript http://localhost:3100/docs-json -o src/api/schema.d.ts

產生的檔案匯出 paths 和 components 兩個型別。components['schemas'] 裡是每個 DTO；paths 則照著文件的結構一層層往下：路徑 → 方法 → 回應 → 狀態碼 → 內容類型。用索引存取型別（TypeScript 課第 20 課）取出需要的部分：

import type { components, paths } from './api/schema'

type CreateOrder = components['schemas']['CreateOrderDto']
//   { customerId: number; items: components['schemas']['OrderItemDto'][]; note?: string }
type Created = paths['/orders']['post']['responses'][201]['content']['application/json']
//   components['schemas']['OrderResponse']

這樣的好處要在後端改東西時才看得到。後端把 qty 改名成 quantity，前端重新產生 schema.d.ts，每個還在用 qty 的地方都會被 vue-tsc 標紅：錯誤在編譯時就出現，而不是使用者下單時才出現。

前提是文件正確。前兩節的功夫就是為了這裡：欄位沒寫進文件，產生的型別就是空物件，前端拿到的只是假的安全感。還想讓網址和參數也受型別檢查的話，可以搭配從同一份型別產生的 API 客戶端，見課末。

💡 實務上：把「產生型別」做成一個指令，放進日常流程
咖啡店的 Vue 前台通常會在 package.json 加一個 gen:api 指令，指向本機或 staging 的 /docs-json，後端合併 API 修改後，前端執行一次、把 schema.d.ts 一起 commit，PR 的 diff 就看得出這次 API 變了什麼。要先跟後端講好：哪個環境的文件算數、誰負責提醒前端重新產生。產生出來的檔案不要手動修改，下次一產生就被蓋掉；型別看起來不對，要回頭修後端的 @ApiProperty。

這套流程對 Vue 前台很有效，因為 Vue 前台和後端幾乎同時部署：型別報錯，改完一起上線。開場那支 iOS App 卻不是這樣。

型別擋得住 Vue，擋不住已上架的 App：哪些修改會弄壞客戶端？

iOS App 編譯、送審、上架之後，裝在使用者手機上的就是那一版程式。後端改了 API，那支 App 不會重新產生型別、不會重新編譯；要等使用者自己去更新，而很多人半年都不更新。網頁前端重新整理就是新版，手機 App 不行。所以 API 上線之後，你要假設有一群你改不到、甚至不知道是哪個版本的客戶端，正照著舊的約定在呼叫你。

會讓這些「現有、沒有改過的客戶端」壞掉的修改，叫做不相容變更（breaking change）。判斷的方法是看資料往哪個方向流：

  • 回應是你給客戶端的，只能多給、不能少給。舊客戶端只讀它認得的欄位，多出來的不理；少了它要讀的欄位，它就讀到 undefined。
  • 請求是客戶端給你的，只能少要求、不能多要求。舊客戶端只會送它當年知道的欄位；你多要求一個必填欄位，它給不出來，每一筆都被 ValidationPipe 擋成 400。

照這個方向，常見的修改可以這樣分：

修改相容嗎為什麼
回應新增欄位相容舊客戶端不讀它（前提：客戶端不要用嚴格的 schema 拒絕多出來的欄位）
請求新增選填欄位相容舊客戶端不送，伺服器用預設值
新增端點相容沒人呼叫過
回應刪除或改名欄位不相容舊客戶端讀到 undefined
請求新增必填欄位，或選填變必填不相容舊客戶端不會送，全部變成 400
欄位改型別（price: 80 → "80"）不相容price * qty 變成字串運算
刪除端點、改網址不相容404
改 errorCode、改狀態碼不相容前端用它判斷要顯示什麼
回應的 enum 多一個值（status 多了 refunded）看客戶端用 switch 沒寫 default 的客戶端會出錯；事先在文件說明「會增加新值」

相容的修改直接做。不相容的修改有兩條路：想辦法改成相容的（新增欄位、舊欄位留著一段時間），或推出新版本。更完整的演進策略（expand → migrate → contract、功能旗標）在系統設計課第 19 課。

回到開場的 GET /menu。它原本回 [{ id, name, price, category }]，改成依分類分組後變成 [{ category, items: [...] }]：每個元素的 name、price 都不見了，對照表格就是「回應刪除欄位」，iOS App 讀到 undefined 就閃退。能不能改成相容的寫法？很難：回應本身是一個陣列，沒有地方「多加一個欄位」放分組後的資料。這就是第二條路的時機：新版本。

菜單非改不可：怎麼讓 v1 和 v2 同時存在？

目標是讓兩個形狀同時存在：iOS App 繼續打 /menu，拿到原本的平面陣列；新版 Vue 前台改打 /v2/menu，拿到分組後的形狀。用網址區分版本，叫 URI 版本。Nest 內建這個功能：

// configureApp
app.enableVersioning({ type: VersioningType.URI })   // 網址前面加 /v1、/v2（前綴 v 是預設）

@Controller('menu')
export class MenuController {
  @Get()
  @Version([VERSION_NEUTRAL, '1'])     // /menu 和 /v1/menu：舊形狀，一個字都不改
  @Header('Deprecation', '@1798761600')
  @Header('Sunset', 'Thu, 01 Jul 2027 00:00:00 GMT')
  listV1() { … }

  @Get()
  @Version('2')                        // /v2/menu：新形狀
  listV2() { … }
}

enableVersioning 開啟版本功能，type: VersioningType.URI 表示版本寫在網址最前面。之後同一個 controller 裡可以有兩個 @Get()，用 @Version 決定各自回應哪個版本的網址：listV2 只回應 /v2/menu，舊的 listV1 一個字都不改。Deprecation、Sunset 兩個標頭是下一節的主題，先略過。

開版本最容易出事的地方，不是新版本，而是舊網址。有兩個陷阱。

第一個是舊網址本身。已經上架的 iOS App 打的是 /menu，不是 /v1/menu。如果舊 handler 只寫 @Version('1')，它只回應 /v1/menu，/menu 就變成 404：對 iOS App 來說，等於刪掉了一個端點，正是上一節表格裡的不相容變更。VERSION_NEUTRAL 代表「不管網址有沒有版本都符合」，跟 '1' 放在同一個陣列裡，/menu 與 /v1/menu 都由舊的 handler 處理。

第二個是沒寫版本的其他路由，例如 POST /orders。沒有設 defaultVersion 時，它們的網址不變：/orders 還是 /orders。如果為了「整齊」在 enableVersioning 設了 defaultVersion: '1'，所有沒標版本的路由都會搬到 /v1/…，/orders 一起 404，只為了改菜單，卻弄壞了下單。所以這裡刻意不設 defaultVersion。

兩個陷阱的共同點：開版本這個動作本身也可能是不相容變更。判斷的方法跟上一節一樣，問「舊客戶端打的那個網址，還在嗎？」

現在 v1、v2 並存了。但並存不是終點：每多一個版本，就多一份要維護、要測試的程式。v1 總有一天要關，問題是怎麼讓還在用 v1 的客戶端事先知道。

怎麼讓 iOS App 知道 v1 要退場？Deprecation 與 Sunset

上一節的程式已經在 v1 的回應加了兩個 HTTP 標頭，它們是通知客戶端「這個版本要退場」的標準做法：

  • Deprecation（RFC 9745）：告訴客戶端「這個版本被淘汰了，或將在某天被淘汰」。淘汰的意思是「還能用，但不要再新寫程式依賴它」。值是結構化欄位的日期：@ 加上 Unix 秒數，@1798761600 是 2027-01-01 00:00 UTC。網路上常看到的另一種寫法見課末。
  • Sunset（RFC 8594）：什麼時候停止服務，用 HTTP 日期格式。停止服務一定在宣告淘汰之後，所以 Sunset 不能早於 Deprecation 的日期。

標頭是給程式看的，人看的是文件。在 v1 的 handler 加上 @ApiOperation({ deprecated: true })，Swagger UI 會把它標示成已淘汰，串接的工程師一打開 /docs 就知道該換到 v2。

不過標頭只是通知，客戶端讀不讀、什麼時候改，你控制不了。真的要讓 v1 退場，還要看 log 或指標：v1 每天還有多少請求、來自哪個 App 版本。數字降到可以接受，才在 Sunset 那天移除。Nest 的版本文件沒有談淘汰流程，這部分是 HTTP 的慣例。也因為退場這麼費工，版本不是越多越好：能用新增欄位解決的，就不要開新版。

💡 實務上：淘汰舊版是溝通工作，不只是加標頭
要讓 iOS App 的 v1 退場，工程上加標頭只是第一步：要先知道誰在用（自家 App、外送平台、合作夥伴），跟 App 團隊確認新版何時上架、要不要跳出「請更新 App」的提示，再讓 PM 決定能接受多少還沒更新的使用者被影響。資深工程師開新版前會先問：外部串接的窗口是誰、要提前多久通知？v1 最晚哪天可以關？誰負責每週看一次 v1 的流量？答不出來，舊版往往就會一直留著沒人敢關。

到這裡，處理不相容變更的工具都齊了：判斷規則、新版本、淘汰通知。但這一切有個前提：改 API 的人在改的當下，就發現了「這是不相容變更」。

人會忘：怎麼在 PR 合併前自動抓出不相容變更？

規則都知道了，人還是會忘。PR 裡改了一個 DTO 的欄位名稱，diff 只有一行，審查的人不一定看得出它影響了哪個 API、哪個客戶端。開場的菜單改動如果在 PR 階段就被指出來，iOS App 就不會閃退。

好消息是文件由程式產生，所以檢查也可以交給程式。在 CI 裡做三件事：產生這次 PR 的 OpenAPI 文件；拿上一個正式版本的文件來比；發現不相容變更就讓 PR 失敗，除非作者明確標示「這是新版本」。比對的規則，就是前面那張相容性表格，只是改由程式來查。

「上一個正式版本的文件」從哪裡來？常見兩種做法：CI 先切到 main 分支產生一份，再切回 PR 產生一份；或是把 openapi.json commit 進 repo，每次發版時更新，PR 就拿 repo 裡那份來比。「明確標示」常見的做法是 PR label（例如 breaking-change），CI 看到這個 label 就放行，留給審查的人判斷；更好的做法是新的形狀確實放在新的 @Version 底下，這時比對程式只會看到新增的端點，舊端點沒變，本來就不會判成不相容。

寫比對程式時有一個陷阱，來自 Nest 產生文件的方式。Nest 不會把 DTO 的欄位直接寫在每條路由底下，而是把每個 DTO 收進 components.schemas，路由只寫一個引用：{ "$ref": "#/components/schemas/CreateOrderDto" }。$ref 的意思是「這裡的內容請到那個位置找」，同一個 DTO 被好幾條路由用到時，只需要寫一次。這對比對有兩個影響：

  • 只比對 paths 的話，改了 DTO 欄位完全看不出來：路由底下那一行 $ref 前後一模一樣。要順著 $ref 找到真正的 schema 再比。
  • 同一個 schema 被好幾個端點用到時，一次修改會影響每一個端點。

另外，這個檢查要能拿到完整的文件。如果是在 Vitest 裡產生文件，就是前面 CLI 外掛那一節說的情況：沒手寫 @ApiProperty 的欄位不會出現，比對兩份空 schema 永遠「沒有不相容變更」。

練習 4 會寫一個最小的版本，只抓四種最常見的情況。正式專案可以用現成的工具（例如 oasdiff），它涵蓋更多規則（參數、enum、狀態碼）。怎麼把檢查接進 GitHub Actions，在 DevOps 課第 15 課。

回頭看開場的兩件事：前端不用再問「body 怎麼送」，因為 /docs 和產生的型別都寫著；GET /menu 的改動會在 PR 階段被比對程式擋下，改成推出 v2、讓 v1 帶著淘汰標頭慢慢退場。接下來在練習裡把這些一一做出來。

練習

在 learn/ 執行 node check.mjs nestjs 23 建立 work/23/。這一題不用資料庫，商品與庫存放在記憶體。專案已經有：

  • POST /orders（OrdersController、CreateOrderDto、OrderResponse），庫存不足時丟第 8 課的 OutOfStockError（409，OUT_OF_STOCK），驗證失敗是 400 VALIDATION_FAILED。
  • GET /menu：回傳 [{ id, name, price, category }]，Vue 前台和 iOS App 都在用。
  • src/common/error-response.dto.ts：寫好 @ApiProperty 的 ErrorResponse。
  • nest-cli.json 已經開了 Swagger 外掛。判分在 Vitest 裡跑，外掛不會執行。

想親手看文件：在 work/23 執行 npm run start:dev，用瀏覽器打開 http://localhost:3100/docs，在 POST /orders 按 Try it out 下一張單。也可以比較 npx nest build 之後的 node dist/main.js：外掛開著，沒寫 @ApiProperty 的欄位在那裡也看得到。

練習 1：讓 POST /orders 的文件完整。

  • 在 configureApp 用 DocumentBuilder（標題 咖啡店 API）與 SwaggerModule.setup('docs', …) 提供 /docs 與 /docs-json。
  • CreateOrderDto、OrderItemDto、OrderResponse 的每個欄位加上 @ApiProperty，選填的 note 用 @ApiPropertyOptional。整數欄位（customerId、productId、qty）是 integer，size 是 enum，items 是 OrderItemDto 的陣列。
  • 在 OrdersController 加上 @ApiCreatedResponse，201 回傳 OrderResponse。

判分讀 /docs-json：檢查每個 schema 的欄位、型別、required，以及 201 指向 OrderResponse；再真的下一張單，確認回應的欄位跟文件寫的一樣。

練習 2：寫 ApiErrorResponses(...errors)：每個 { status, errorCode, description } 變成一個 @ApiResponse，type 是 ErrorResponse，description 寫進文件，example 是一個完整的錯誤回應，裡面的 errorCode 就是傳進來的那個。用 applyDecorators 組成一個裝飾器，然後在 POST /orders 記錄 400（VALIDATION_FAILED）與 409（OUT_OF_STOCK）。

判分除了看 POST /orders 的文件，還會把你的裝飾器套在另一個 controller 上，傳三個別的錯誤（404、422、429），三個都要出現在文件裡；文件上的 errorCode 也要跟 API 真的回的一樣。

練習 3：推出 GET /v2/menu，形狀是 [{ category, items: [{ id, name, price }] }]，分類照商品第一次出現的順序。新舊兩版都從注入的 ProductsService 算出來，不能寫死回應。

  • 在 configureApp 開啟 URI 版本，不要設 defaultVersion。
  • 舊的形狀一個字都不改，/menu 和 /v1/menu 都還能用，都帶 Deprecation（RFC 9745 的 @ 秒數）與 Sunset（HTTP 日期，不早於 Deprecation）標頭；文件裡標成 deprecated。
  • /v2/menu 不帶淘汰標頭，POST /orders 的網址不變。

練習 4：寫 findBreakingChanges(oldDoc, newDoc)，比較兩份 OpenAPI 文件，回傳四種發現（型別 Finding 已經定義好，順序不重要）：

  • endpoint-removed：舊文件有、新文件沒有的「方法 + 路徑」，例如 'GET /orders/{id}'。
  • response-field-removed：2xx 回應（application/json）裡，舊的有、新的沒有的欄位。
  • request-field-required：請求 body 裡，新文件必填、舊文件不是必填（或不存在）的欄位。
  • type-changed：兩邊都有、type 不同的欄位，in 寫 request 或 response。

欄位路徑用 . 接起來，陣列元素寫 []：items[].qty；回應本身是陣列時是 [].price。schema 可能是 $ref，要到 components.schemas 找。新增回應欄位、新增選填欄位、新增端點都不能回報；也不要修改傳進來的兩份文件（例如把解析後的 schema 寫回 $ref 的位置）。判分用好幾組手寫的文件，比對完整的回報清單。

練習 5：這次的 PR 做了兩件事：OrderResponse 多了 createdAt 欄位；CreateOrderDto 多了必填的 pickupTime。同事說「都是新增，所以都相容」。哪個說法正確？

✓ b。要看資料往哪個方向流：回應是伺服器給的，多給的欄位舊客戶端不讀；請求是客戶端給的，多要求的東西舊客戶端給不出來。要加 pickupTime 又不弄壞舊 App，就讓它選填、伺服器給預設值。a 忽略了方向。c 太保守，新增回應欄位、選填欄位每天都在做，每次都開新版只會累積一堆版本。d 方向剛好相反：舊前端的型別裡沒有 createdAt，執行時多一個欄位不會出錯。

練習 6：專案開了 Swagger CLI 外掛，DTO 都沒寫 @ApiProperty。nest build 後打開 /docs，欄位都在；但在 Vitest 測試裡用 SwaggerModule.createDocument 產生的文件，CreateOrderDto 是 properties: {}。為什麼？

✓ c。外掛在 nest build 時讀 TypeScript 的型別資訊，把 @ApiProperty 等價的 metadata 寫進編譯出的 JS。沒經過 tsc（Vitest、沒加 --type-check 的 SWC）就沒有這一步。a、b 錯：外掛跟執行方式、環境變數無關，它在執行前就已經做完（或沒做）。d：檔名確實要是 .dto.ts，但同一個檔案 nest build 後有欄位，代表檔名沒問題。所以要在測試裡驗證文件，欄位就得手寫 @ApiProperty（或用 zod schema）。

練習 7：兩個團隊在爭論文件該怎麼產生。A 團隊：前後端同一組人、每週上線好幾次；B 團隊：API 開放給外部的外送平台串接，對方有自己的開發時程。哪個建議最合理？

✓ d。兩種做法解決不同的問題。code-first 讓文件跟程式不會各說各話，適合變動快、溝通成本低的團隊；contract-first 讓設計在動工前就被討論，適合多方依賴、改一次很貴的公開 API。a、b 把其中一種當成唯一正解。c 錯：A 團隊的前端一樣需要型別與試打；Word 文件無法產生型別、無法自動比對相容性，很快就會跟程式不一致。

常見錯誤

  • 把文件當成上線前才補的作業：前端已經照猜的格式寫完了。文件跟著 API 一起寫、一起審。
  • 文件和程式說的不一樣：@ApiPropertyOptional 的欄位，驗證卻是必填；文件說 integer，程式回字串。用測試比對文件與真的回應。
  • 只靠 CLI 外掛：正式環境的文件完整，測試、SWC 建置裡卻是空的，檔名不是 .dto.ts 的也被跳過。要在測試裡驗證文件就手寫 @ApiProperty，或用 zod schema。
  • 用 @nestjs/mapped-types 的 PartialType 搭配 Swagger：驗證規則有複製，文件的欄位沒有。改從 @nestjs/swagger 匯入。
  • 文件只寫成功的回應：前端不知道會收到哪些錯誤、errorCode 叫什麼。每條路由用 @ApiErrorResponses 列出可能的錯誤與範例。
  • 偷偷改舊版本的形狀：「只是調整一下 v1 的回應」，已經上架的 App 就壞了。舊版本一個字都不改，新形狀放新版本。
  • 加版本時把舊網址弄丟：只寫 @Version('1')，/menu 就 404；設 defaultVersion，所有沒標版本的路由都搬家。舊網址用 VERSION_NEUTRAL 留著。
  • 淘汰了卻沒通知：沒有 Deprecation／Sunset 標頭，也沒在文件標 deprecated，客戶端到停機那天才知道。也要看 log 確認還有誰在用。
  • 比對文件時只看 paths：欄位都在 components.schemas，改 DTO 完全抓不到。順著 $ref 比。

補充與查表

code-first 與 contract-first 怎麼選

第一節提到文件從哪裡來有兩種做法，完整的比較：

code-first（先寫程式）contract-first（先寫契約）
做法寫 controller 與 DTO，由程式產生 OpenAPI先寫 OpenAPI 檔、前後端一起審，再照著實作
好處文件跟程式不會各說各話；後端一個人就能動手前端可以同時開工（用文件產生假資料伺服器）；設計先被討論
代價API 的設計常常變成「程式寫成什麼就是什麼」要另外檢查實作有沒有照文件
適合前後端在同一個團隊、迭代快給外部合作夥伴的公開 API、多個團隊同時依賴

第 7 課的 zod 路由不需要外掛

第 7 課的 zod 路由（v12 的 @Body({ schema: redeemSchema })）不需要外掛：createDocument 在執行時把 zod schema 轉成 JSON Schema，Vitest 裡也是完整的欄位與 minimum／maximum。

用了 Swagger，PartialType 要從哪裡匯入

有用 Swagger 時，PartialType、PickType、OmitType 要改從 @nestjs/swagger 匯入（第 7 課用的是 @nestjs/mapped-types）。兩個版本都會複製驗證規則，只有 @nestjs/swagger 的會連 @ApiProperty 一起複製；用錯了，UpdateProductDto 在文件裡就沒有欄位。

applyDecorators 的其他用法

同樣的手法也常用來把 @UseGuards(AuthGuard) 和 @ApiBearerAuth() 包成一個 @Auth()。

連網址和參數也做型別檢查

openapi-typescript 只產生型別。搭配 openapi-fetch 這類客戶端，連網址和參數都會被型別檢查。

版本備註

  • @nestjs/swagger 12.0.5 產生的是 OpenAPI 3.0.0。
  • 不寫 @ApiTags 時，12.0.5 預設用 controller 的名稱分組（autoTagControllers）。
  • openapi-typescript 目前是 7.x。
  • Deprecation 標頭的 RFC 9745 在 2025 年 3 月發布。舊的草稿寫成 Deprecation: true，網路上還很常見，但已經不是標準。

小結

  • API 是後端與客戶端的約定。只寫在後端程式裡，前端只能猜；另寫一份說明，很快就跟程式不一致。OpenAPI 是 API 的機器可讀契約，從程式產生，可以用 Swagger UI 試打、產生前端型別、在 CI 比對相容性。code-first 從程式產生，contract-first 先寫文件，依團隊與 API 的使用者選擇。
  • DocumentBuilder ＋ SwaggerModule.setup('docs', app, …) 提供 /docs 與 /docs-json。TypeScript 的型別執行時不存在，DTO 欄位用 @ApiProperty 寫出來，回應用 @ApiCreatedResponse 等裝飾器；@ApiProperty 只寫文件、不驗證，要跟 class-validator 說同一件事。
  • CLI 外掛只在 tsc 編譯時運作，Vitest、SWC（沒加 --type-check）裡沒有它；要在測試裡檢查文件，就手寫 @ApiProperty。zod schema 在執行時就能產生完整的文件。
  • 錯誤回應也寫進文件：applyDecorators 把重複的 @ApiResponse 組成 @ApiErrorResponses，範例帶出 errorCode。
  • Vue 前台從 /docs-json 產生型別，後端改欄位時 vue-tsc 就報錯；前提是文件正確。
  • 已上架的 App 改不到，所以回應只能多給、請求只能少要求。刪欄位、改型別、新增必填、刪端點、改 errorCode 都是不相容變更。
  • 不相容就推新版：enableVersioning({ type: VersioningType.URI })、@Version，舊版不改形狀、用 VERSION_NEUTRAL 保住舊網址、不設 defaultVersion；加上 Deprecation（@ 秒數）與 Sunset 標頭，看 log 確認沒人用了才移除。
  • 比對新舊文件要順著 $ref 進 components.schemas，在合併前抓出不相容變更。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：老闆改了拿鐵價格，偶爾有客人在 App 上看到舊價格整整一分鐘（TTL 是 60 秒）。改價的程式如下，問題出在哪？

async updatePrice(id: number, price: number) {
  await this.cache.del(menuKey())
  await this.cache.del(menuKey('coffee'))
  await this.prisma.product.update({ where: { id }, data: { price } })
}

✓ 先刪快取時，寫入還沒完成的空檔裡，任何一個沒命中的讀取都會把舊價格放回快取，一直留到 TTL 過期。改成先寫資料庫、成功後再刪所有相關的 key；在交易裡就等 commit 之後。b 只是縮短出錯的時間，沒有消除原因，TTL 是最後防線，不是失效的方法。（第 19 課）

練習 9：寄收據的 worker 這樣寫，job 設了 attempts: 5。哪裡會出事？

async process(job: Job<{ orderId: number }>) {
  const order = await this.orders.find(job.data.orderId)
  if (order.receiptSentAt) return
  await this.orders.markReceiptSent(order.id)
  await this.mailer.sendReceipt(order.email, order.id)
}

✓ 佇列是至少一次，worker 要冪等，但順序要對：先檢查、做成功再標記。先標記的話，寄信失敗時重試看到「已完成」就跳過，那件事永遠沒做。b 是「做成功再標記」才有的空檔，這段程式先標記，不會發生；那個空檔要靠外部服務的冪等鍵收尾。（第 20 課）

練習 10：outbox relay 取出一批事件，queue.add 都成功了，還沒寫回 published_at，程序就被重啟。接下來會怎樣？

✓ published_at 沒寫回，這批還是「未送出」，下一輪會再取出來送。outbox 保證的是至少一次：不會漏，但可能重送，所以 jobId 用有意義的 id（receipt-7）、worker 先檢查再做。c 錯在 Redis 不在資料庫的交易裡，沒有一個交易能同時包住兩邊，這正是雙寫問題。（第 20 課）

練習 11：點數過期的 @Cron 部署到 3 台伺服器後，每天 03:00 都扣了 3 次點數。哪個修法最合理？

✓ 每個程序都會跑每個排程工作，要靠資料庫讓一台做；交易層級的 advisory lock 在交易結束時自動釋放。鎖只是避免重複，工作本身還要冪等（條件式 UPDATE 加唯一鍵）。b 錯在 session 層級的鎖沒 unlock 就一直鎖著，連線池裡執行 unlock 的也不一定是同一條連線。（第 21 課）

練習 12：付款成功後要通知廚房看板，同事這樣寫。哪裡會出事？

await this.prisma.$transaction(async tx => {
  await tx.order.update({ where: { id }, data: { status: 'paid' } })
  this.events.emit('order.paid', new OrderPaidEvent(id))
  await tx.payment.create({ data: { orderId: id, amount } })
})

✓ 事件發出去就收不回來，交易回滾不會撤回它。emit 要放在 $transaction 回來、確定 commit 之後。c 錯在 listener 的錯誤預設只記一行 error log，不會影響發送方，所以一定要完成的工作不能交給事件。（第 21 課）

練習 13：webhook 第一次回應太慢，金流公司逾時後重送，兩個 event_id 相同的請求同時在處理（各自一個交易，event_id 沒有唯一約束）。這段程式會怎樣？

const seen = await tx.webhookEvent.findFirst({ where: { eventId: event.id } })
if (seen) return
await tx.order.updateMany({ where: { id: orderId }, data: { status: 'paid', paidAt: new Date() } })
await tx.webhookEvent.create({ data: { eventId: event.id, type: event.type } })

✓ 查詢和寫入之間別人可以插進來，應用程式層的檢查擋不住並發。把判斷交給資料庫：event_id 加唯一約束，後到的收到 P2002 就當成已處理、回 200；改訂單（帶 status: 'pending' 條件）和記事件放在同一個交易。a 錯在普通的查詢不會等別人的交易，只看得到已經 commit 的資料，兩邊這時都還沒 commit。（第 22 課）

練習 14：商品照片上傳只收 JPEG 和 PNG。有人把 evil.html 改名成 latte.png 送上來，哪個檢查擋得住？

✓ 檔名、Content-Type 與內容都是客戶端送的，只有內容值得檢查，而且要看檔頭；不符合回 422、不存檔。存檔時也不用 originalname，改用 randomUUID() 加偵測到的副檔名。b 錯在 file.mimetype 就是 multipart 裡客戶端填的 Content-Type，改了副檔名送上來一樣是 image/png。（第 22 課）

練習 15：新版 Vue 前台要依分類分組的菜單，已上架的 iOS App 還在讀平面陣列的 GET /menu。哪個做法最合適？

✓ 改回應的形狀是不相容變更，使用者可能半年不更新 App，所以兩個形狀並存：/menu 與 /v1/menu 都由舊 handler 處理，用 Deprecation、Sunset 標頭通知，看 log 確認沒人用了才移除。b 錯在 defaultVersion 會把所有沒標版本的路由搬到 /v1/…，/menu、/orders 的舊網址一起 404。（第 23 課）
