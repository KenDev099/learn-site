階段 1：從 Node 到 NestJS（框架的骨架） · 第 2 課

Controller：路由、參數與回應

上一課的 GET /menu 只會回一份固定的清單。這一課接到一個真正的需求：咖啡店要做商品管理後台，前端用 Vue 寫畫面，需要後端提供一組商品 API。商品列表要能依分類篩選，點進去看單一商品，可以新增、改價格、下架；首頁要顯示「本週推薦」，搜尋框要能同時勾選好幾個標籤。

這一課從起始專案裡那個只做了一半的 ProductsController 出發，把這份需求一條一條做完。途中會遇到三個不會報錯、卻會讓前端拿到錯誤結果的坑：id 的型別、路由的順序、查詢參數的形狀。

這課的路線：
  1. 先寫規格、請求怎麼找到方法：前端要的每支 API 成功和失敗各回什麼；GET /products/3 怎麼對到 controller 裡的一個方法。
  2. 從請求取值：商品 id、分類、新增時送來的 JSON 各用哪個裝飾器拿到；為什麼 GET /products/2 會永遠找不到拿鐵。
  3. 狀態碼、為什麼不用 @Res()：找不到回 404、建立回 201、刪除回 204 怎麼寫；照 Express 教學用 res.status() 為什麼會讓請求卡住。
  4. 路由順序：加上 /products/featured 之後，請求為什麼被 :id 攔走。
  5. 多選標籤搜尋：?tags=iced&tags=milk 拿到的是陣列還是字串。
這課會用到：
  • Node 課第 12 課的 HTTP 方法、狀態碼、標頭：GET 讀、POST 建立、PATCH 部分更新、DELETE 刪除；2xx 成功、4xx 是請求的錯、5xx 是伺服器的錯。
  • 第 1 課的專案：controller 處理請求、service 放邏輯，在 work/ 裡用 npm run start:dev 啟動、另開終端機用 curl 打。

任務：前端要一份什麼樣的商品 API？

動手寫程式之前，先跟前端對齊規格。前端的畫面怎麼寫，完全取決於後端回什麼：列表頁要一個陣列，商品頁要一筆物件，按下「儲存」之後要知道到底成功了沒有。HTTP 用狀態碼回答「成功了沒有」：前端看到 201 就知道建立成功，看到 404 就知道沒有這個商品。所以一份能用的規格，除了路徑，還要寫清楚成功和失敗各回什麼。

咖啡店後台的商品 API，規格如下。這份表沿用 Node 課第 14 課設計過的商品 API：

請求後台畫面的用途成功失敗
GET /products?category=tea商品列表，可依分類篩選200，陣列（沒有符合就是空陣列）—
GET /products/2商品詳細頁200，那一筆404；id 不是數字 400
POST /products新增商品201，含新 id 的那一筆400（第 7 課加上驗證）
PATCH /products/2修改價格或標籤200，更新後的那一筆404
DELETE /products/2下架商品204，沒有內容404

表裡有兩個選擇需要說明。

第一，修改用 PATCH，不用 PUT。PATCH 的語意是部分更新：只改送來的欄位。後台的店員把拿鐵從 110 元改成 115 元，前端只會送 { "price": 115 }；如果後端把這當成整筆資料，名稱、分類、標籤就會被洗掉，拿鐵變成一個只有價格的商品。要「整筆取代」的語意才用 PUT，那時前端必須送出完整的商品。

第二，刪除成功回 204 No Content。204 的意思是「做完了，沒有內容要給你」：商品已經刪掉，沒有東西可以回傳，前端收到 204 就把那一列從列表移除。

除了這五支，規格還有兩支：GET /products/featured 回本週推薦（拿鐵和起司蛋糕），GET /products/search 依名稱、價格上限、標籤搜尋。這兩支看起來最簡單，卻是本課兩個坑所在，留到最後做。

💡 實務上：先把對照表寫出來，再開始寫程式
接到「後台要能管理商品」這類需求，先列出像上面這樣的表：路徑、成功和失敗各回什麼，拿去跟前端對過再動手。前端可以照著表先用假資料做畫面，兩邊同時進行；事後才發現「刪除回 200 還是 204」「找不到是 404 還是空物件」，兩邊都要返工。表上也寫明 id 怎麼產生、刪掉的號碼會不會再用，前端存了連結或做了快取才不會指錯商品。

規格有了，再看手上的程式：起始專案的 ProductsController 只有 GET /products 和 GET /products/:id 兩條，而且 findOne 只會把收到的 id 原樣回傳。要把它補成上面那張表，第一步是看懂 Nest 怎麼把一個請求送到對的方法。

GET /products/3 怎麼找到要執行的方法？

路由（route）是「HTTP 方法＋路徑」對應到哪一段程式。在 Node 課第 13 課，你用 if (req.method === 'GET' && url.pathname === '/products') 一條一條自己比對：每多一支 API 就多一個 if，路徑裡的 id 也要自己切出來。

Nest 把這件事反過來：你只宣告「哪個方法處理哪個路由」，比對交給框架。宣告的地方叫 controller：一個加了 @Controller() 裝飾器的 class。裝飾器是寫在 class 或方法上面、以 @ 開頭的標記，Nest 啟動時會讀這些標記，知道每個方法負責哪個路由。controller 裡加了 @Get()、@Post() 這類裝飾器的方法叫路由處理器（route handler），以下簡稱 handler。

import { Controller, Get, Param } from '@nestjs/common'

@Controller('products')            // 這個 controller 的路徑前綴
export class ProductsController {
  @Get()                           // GET /products
  findAll() { … }

  @Get(':id')                      // GET /products/:id，:id 是路徑參數
  findOne(@Param('id') id: string) { … }
}

一個 handler 最終負責的路徑是「controller 的前綴＋方法上的路徑」：@Controller('products') 加上 @Get() 是 /products，加上 @Get(':id') 是 /products/:id。同一個 controller 裡的路由共用前綴，所以商品相關的 API 全部放在 ProductsController，以後的訂單 API 就放在另一個 OrdersController。

:id 這種以冒號開頭的片段是路徑參數（path parameter）：它是一個佔位符，可以比對路徑裡任何一段文字。/products/3、/products/abc 都會比對到 /products/:id，比對到的那段文字放在名為 id 的參數裡。下圖是 GET /products/3 進來時發生的事：

圖的下半部先記著：從網址切出來的 id 是字串 '3'，下一節會看到它造成的 bug。

controller 要登記在 module 的 controllers 裡，Nest 才會讀它的路由；第 1 課的 nest g controller 會自動登記，起始專案也已經登記好。規格表裡的其他動作用對應的裝飾器：@Post、@Patch、@Delete，整筆取代的 @Put 也一樣，用法跟 @Get 相同。

現在 GET /products/3 能進到 findOne，也拿得到 id。但規格裡的資料不只在路徑上：分類在 ?category=tea，新增商品的內容在請求送來的 JSON 裡。handler 要怎麼拿到它們？

handler 怎麼拿到 id、分類和新增的內容？

一個 HTTP 請求可以在四個地方帶資料給伺服器，規格表裡每一種都用得到：

  • 路徑：/products/2 的 2。指出「要操作哪一個資源」，少了它請求就沒有意義。
  • 查詢參數（query string）：網址 ? 後面的 名稱=值，多個用 & 連接，例如 ?category=tea。放選填的條件，例如篩選、排序、分頁；不給也是一個合法的請求。
  • 請求主體（request body）：POST、PATCH 在網址之外另外送出的內容，這門課都用 JSON，例如新增商品時的 { "name": "冰滴咖啡", "price": 130 }。
  • 請求標頭（header）：關於這個請求本身的資訊，例如是哪個客戶端送的、內容是什麼格式。之後的登入驗證也會放在標頭裡。

Nest 給每個位置一個參數裝飾器：寫在 handler 的參數前面，告訴 Nest「呼叫這個方法之前，把請求裡的某個值填進這個參數」。

裝飾器取什麼例子拿到的型別
@Param('id')路徑參數/products/3字串 '3'
@Query('category')查詢參數/products?category=tea字串；同名出現多次是字串陣列；沒給是 undefined
@Body()請求主體，POST／PATCH 送來的 JSON{ "name": "冰滴咖啡", "price": 130 }解析好的物件
@Headers('user-agent')請求標頭（名稱不分大小寫，Nest 會轉成小寫去找）User-Agent: curl/8.7.1字串

對到規格表：GET /products/2 用 @Param('id')，列表的分類篩選用 @Query('category')，新增和修改用 @Body()。@Headers 這一課的規格用不到，先認得就好。

不給名稱（@Query()、@Param()）會拿到整個物件，例如 ?category=tea&q=拿 會拿到 { category: 'tea', q: '拿' }。@Body() 能直接拿到物件，是因為 Nest 預設幫 Express 開了 JSON 解析，把請求送來的 JSON 文字轉成物件；Express 5 在沒有解析器時 req.body 是 undefined。

表格最後一欄「拿到的型別」，就是本課第一個坑。TypeScript 的型別註記只是你寫給編譯器看的宣告，Nest 不會照著它轉型。上一節的圖說過，網址本來就是文字，所以下面這段程式：

@Get(':id')
findOne(@Param('id') id: number) {             // 型別寫 number，執行時其實是 '2'
  return this.products.find(p => p.id === id)  // 2 === '2' 永遠是 false
}

型別檢查會通過，因為你告訴編譯器 id 是數字，編譯器就相信你。但執行時 id 是字串 '2'，而商品資料裡的 id 是數字 2。=== 會連型別一起比，數字和字串永遠不相等，所以 GET /products/2 永遠找不到拿鐵。這個 bug 沒有錯誤訊息，find 只是安靜地回傳 undefined。

修法是讓 Nest 在呼叫 handler 之前先把字串轉成數字。Nest 提供一種叫 pipe 的元件做這件事：參數從請求取出來之後、傳進 handler 之前，會先經過 pipe，pipe 可以轉換它（字串變數字），也可以檢查它（不合格就直接拒絕這個請求）。Nest 內建的 ParseIntPipe 兩件事都做：

findOne(@Param('id', ParseIntPipe) id: number) { … }

'2' 會變成數字 2，比對就成立了。/products/abc 的 'abc' 轉不了，ParseIntPipe 直接回 400，handler 根本不會被呼叫。這正好符合規格表的「id 不是數字 400」：id 寫錯是客戶端的錯，該回 4xx，不該讓 handler 拿著 NaN 去查資料。

查詢參數是選填的，沒給時是 undefined，直接套 ParseIntPipe 會因為轉不了而回 400。選填的數字參數用 new ParseIntPipe({ optional: true })，沒給時保持 undefined，有給才轉型；最後一節的搜尋會用到。第 7 課會完整講 pipe，以及怎麼檢查整個 body 的格式；這一課的 @Body() 還沒有檢查，送什麼進來就收什麼。

有了 ParseIntPipe，GET /products/2 找得到拿鐵了。那 GET /products/99 呢？find 找不到，回傳 undefined，handler 再把 undefined 回出去。前端會收到什麼？

找不到、建立成功、刪除成功，各回什麼狀態碼？

先看 Nest 怎麼產生回應：handler 的回傳值就是回應內容，上一課看過，物件和陣列會變成 JSON。handler 也可以是 async（TypeScript 課第 9 課），Nest 會等 Promise 完成再送出結果；之後接資料庫時，每個 handler 幾乎都是 async。

狀態碼也由 Nest 決定：POST 預設 201 Created，其他方法預設 200 OK。對照規格表，列表、查單筆、新增、修改的成功情況，用預設值就對了，不必寫任何東西。要處理的是兩個例外：找不到要回 404，刪除成功要回 204。

先看找不到。handler 回傳 undefined，Nest 回的是 200 加上空白內容。前端看到 200，會以為成功了，接著拿空的回應去畫商品頁，畫面出錯或一片空白。所以「找不到」不能用 return undefined 表達，要丟出例外。

Nest 為 HTTP 錯誤準備了一組例外類別，它們的共同父類別叫 HttpException。在 handler 裡丟出其中一個，Nest 會接住它，回對應的狀態碼和一段 JSON。404 用的是 NotFoundException：

import { NotFoundException } from '@nestjs/common'

@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {
  const product = this.products.find(p => p.id === id)
  if (!product) throw new NotFoundException(`找不到商品 ${id}`)
  return product
}

用 curl 的 -i 連狀態列和標頭一起看：

$ curl -i http://localhost:3100/products/99
HTTP/1.1 404 Not Found
Content-Type: application/json; charset=utf-8

{"message":"找不到商品 99","error":"Not Found","statusCode":404}

第一行是 404，內容裡的 message 是你丟例外時給的訊息。常用的還有 BadRequestException（400）、ConflictException（409），用法相同。

如果丟的不是 HttpException，而是一般的 Error，包括 async handler 裡沒接住的錯誤，Nest 一律回 500 和 {"statusCode":500,"message":"Internal server error"}，錯誤細節只寫進 log，不會送給前端。這是刻意的：錯誤訊息可能帶有資料庫結構或檔案路徑，不該讓外部看到。所以分辨很重要：你預期得到的失敗（找不到、格式錯）丟對應的 HttpException，讓前端知道怎麼處理；預期外的才變成 500。第 8 課會統一整個 API 的錯誤格式。

再看刪除。預設的 200 不符合規格，要改成 204，在方法上加 @HttpCode(204)。204 表示沒有內容，所以這個方法不要回傳任何東西：

@Delete(':id')
@HttpCode(204)
remove(@Param('id', ParseIntPipe) id: number) {
  // 找不到就丟 NotFoundException；刪掉之後不 return
}

同一類的還有 @Header()，用來加回應標頭，例如 @Header('Cache-Control', 'no-store')。這兩個裝飾器都只描述「回應要長什麼樣」，實際送出仍然由 Nest 負責。

💡 實務上：狀態碼是前端寫畫面的依據
咖啡店後台的商品頁收到 404，會顯示「商品已下架」並導回列表；收到 400 就把錯誤標在表單欄位旁；收到 500 才顯示「系統忙碌，請稍後再試」。如果 API 一律回 200、再用 { success: false } 表示失敗，前端每支 API 都要另外判斷，監控也看不出錯誤率。code review 時資深工程師會一條一條看：每個失敗分支丟的是不是對的例外，有沒有哪條路徑默默回了 undefined。

寫過 Express 的人看到「刪除要回 204」，第一個念頭通常是照網路教學拿到回應物件，自己 res.status(204)。在 Nest 裡這樣做會出事。

為什麼不直接用 Express 的 res.status()？

網路上的 Express 教學會這樣寫：

@Get()
findAll(@Res() res: Response) {
  res.status(200).json(this.products)
}

@Res() 也是參數裝飾器，把底層 Express 的回應物件交給你。Nest 送回應有兩種模式：預設是用 handler 的回傳值，由 Nest 送出；只要你注入 @Res()，Nest 就認定你要自己送回應，關掉自己的回應處理。後者叫 library-specific 模式，意思是你直接操作底層函式庫（這裡是 Express）的物件。代價是：

  • 回傳值不會被送出：如果你注入了 @Res() 卻只 return { … }，請求會一直卡著直到逾時。實測在 12.3.2 上就是如此：沒有錯誤、沒有 log，客戶端只看到轉圈圈。任何一條分支忘了 res.json() 都會這樣，例如找不到時有送 404，正常情況卻忘了送。
  • @HttpCode()、@Header()、攔截器都失效，因為它們都作用在 Nest 送出的回應上。攔截器（interceptor）是 第 9 課會教的元件，能在 handler 前後統一加工回應，例如把所有回應包成同一種格式；用了 @Res() 的 handler 會默默跳過它。
  • 綁死 Express：res.json 是 Express 的 API，換成 Fastify 就要改。

所以在 Nest 裡，狀態碼用 @HttpCode()、錯誤用 HttpException、內容用回傳值，三件事都不需要碰回應物件。真的需要碰（例如設定 cookie），用 @Res({ passthrough: true })：你可以設定標頭或 cookie，回應仍然由 Nest 用回傳值送出，上面三個代價都不會發生。

到這裡，規格表的五支 CRUD 都能對到 Nest 的寫法：

請求handler成功失敗
GET /products?category=tea@Get() ＋ @Query('category')200，陣列（沒有符合就是空陣列）—
GET /products/2@Get(':id')200，那一筆404；id 不是數字 400

實作這張表之前，還有兩件規格表沒寫、但練習 1 的測試會檢查的事。第一件是新增商品時，新 id 怎麼產生。起始程式有 6 項商品，id 是 1 到 6。直覺的做法是 products.length + 1，但刪掉 2 號拿鐵之後陣列剩 5 筆，length + 1 算出 6，跟還在的 6 號起司蛋糕撞號，GET /products/6 從此不知道該回哪一筆。改成「目前最大的 id ＋ 1」可以避開撞號，卻有另一個問題：刪掉 6 號起司蛋糕之後，最大 id 變成 5，下一個新商品又拿到 6。前端如果在書籤、快取或另一個分頁裡還留著 /products/6，點下去看到的就是別的商品，而且不會有任何錯誤提示。這就是第一節燈泡裡說「刪掉的號碼會不會再用」要寫進規格的原因：id 是前端拿來指認一筆資料的唯一依據，一個號碼一旦發出去，就不該再指向別的東西。所以用一個只增不減的計數器（例如 private nextId = 7，每次新增用 this.nextId++），刪除不會讓它倒退。之後接上資料庫，這件事交給 PostgreSQL 的 identity 欄位，它同樣不會重發用過的號碼。

第二件是 PATCH 怎麼合併。前面說過 PATCH 只改送來的欄位，做法是把 body 合併進原本的商品，沒送的欄位保留原值。要小心的是 body 裡可能也帶著 id，可能是前端把整筆物件送回來，也可能是有人故意改。商品的 id 以網址為準：PATCH /products/2 改的就是 2 號，合併時要讓網址的 id 蓋過 body 的 id（例如 { ...product, ...body, id }，id 放最後），否則一個 PATCH 就能把 2 號改成 6 號，又回到撞號的問題。

練習 1 就是把這張表實作出來。剩下規格裡的兩支：本週推薦和搜尋。本週推薦看起來最簡單，在 controller 裡加一個方法就好，結果卻回了 400。

為什麼 /products/featured 回 400？

咖啡店要加「本週推薦」：GET /products/featured。照直覺把它加在檔案最下面：

@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) { … }

@Get('featured')
featured() { … }
$ curl http://localhost:3100/products/featured
{"message":"Validation failed (numeric string is expected)","error":"Bad Request","statusCode":400}

錯誤訊息來自 ParseIntPipe：它收到的 id 是 'featured'，轉不成數字。也就是說，請求根本沒進到 featured()，而是進了 findOne。

原因在路由的比對方式。Express 依登記的先後一條一條比對，第一條符合的就處理，後面的不再看；Nest 照 class 裡方法的宣告順序把路由登記給 Express。上一節說過，:id 能比對路徑裡任何一段文字，featured 也算。所以先登記的 /products/:id 把請求攔走，/products/featured 永遠輪不到。這叫路由遮蔽（route shadowing）：一條路由被排在前面、範圍更大的路由擋住。

這一次還算幸運，ParseIntPipe 至少回了 400。沒有 ParseIntPipe 的話更難查：findOne 拿到 'featured'，回一個莫名其妙的結果，沒有任何錯誤。

修法：固定路徑寫在參數路徑前面。

@Get('featured')          // 先登記
featured() { … }

@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) { … }

NestJS 12 另外有兩個選用設定。一個是 routeResolutionStrategy，預設 'declaration'，照宣告順序登記；設成 'specificity' 會改成固定路徑優先。另一個是 routeConflictPolicy，在啟動時檢查路由衝突，預設 'off'。細節見課末的補充與查表。它們是輔助，不是修法：練習 2 的測試用預設設定建應用，所以仍然要靠正確的宣告順序。

💡 實務上：路由遮蔽多半在專案長大後才出現
一開始 controller 只有 CRUD，幾個月後陸續加上 /products/export、/products/stats，新進的人習慣加在檔案最下面，就被 :id 攔走。本機只測新功能時可能剛好沒發現，上線後才有人回報匯出按鈕回 400。review 時看到新增的固定路徑，順手確認它在參數路由前面；有 E2E 測試（第 10 課）打一次真正的網址，這類問題在合併前就會被擋下。

規格只剩搜尋。/products/search 也是固定路徑，同樣要宣告在 :id 前面；它真正的問題在查詢參數：使用者勾選兩個標籤時，handler 收到的 tags 長什麼樣？

多選標籤搜尋：?tags=iced&tags=milk 拿到什麼？

後台的搜尋框有三個條件，都可以不填：名稱關鍵字 q、價格上限 maxPrice、標籤 tags。標籤是多選，例如勾選「冰飲」「含奶」。前端用 URLSearchParams 的 append 加兩次同名參數，送出的網址是 /products/search?tags=iced&tags=milk。

NestJS 11 起預設跑在 Express 5 上（12.3.2 帶的是 Express 5.3.0），查詢參數由 Express 解析好再交給 @Query()。同名參數的規則是：

  • ?tags=iced&tags=milk 拿到陣列 ['iced', 'milk']。
  • 只有一個 ?tags=milk 時，拿到的是字串 'milk'，不是只有一個元素的陣列。
  • 沒給就是 undefined。

同一個參數有三種可能的形狀，這就是坑所在。宣告成 tags?: string[]，再呼叫 tags.every(…) 檢查商品是否有全部標籤：勾兩個標籤時正常；只勾一個時 tags 其實是字串，字串沒有 every 方法，丟出 TypeError，前端收到 500。型別檢查一樣攔不到，因為型別是你宣告的。

修法是把型別寫成實際可能拿到的 string | string[]，用之前先統一成陣列：[tags].flat()。tags 是 'milk' 時，['milk'].flat() 還是 ['milk']；tags 是 ['iced', 'milk'] 時，[['iced', 'milk']].flat() 攤平成 ['iced', 'milk']。兩種情況都得到陣列，後面的程式只要處理一種形狀。

價格上限為什麼叫 maxPrice，而不是有些 API 會用的 ?filter[price][lte]=100？Express 5 預設用 simple 方式解析查詢參數，不會把方括號變成巢狀物件，你收到的是一個名稱叫 'filter[price][lte]' 的鍵。所以設計 API 時就用平的參數名稱。maxPrice 是選填的數字，正好用上前面講的 new ParseIntPipe({ optional: true })：沒給時是 undefined，給了不是整數就回 400。Express 5 跟 Express 4 教學的其他差異，整理在課末的補充與查表。

💡 實務上：列表篩選的參數格式要跟前端講好
後台的商品列表常有多選篩選，例如勾選「冰飲」「含奶」兩個標籤。前端用 URLSearchParams 的 append 會送出 ?tags=iced&tags=milk，也有團隊習慣用逗號 ?tags=iced,milk，兩種都行，但同一個專案只用一種，並寫進 API 文件，也就是第一節那張規格表。

到這裡，規格表的每一列都有了做法：五支 CRUD、排在 :id 前面的本週推薦，以及先把 tags 統一成陣列的搜尋。下面的練習把它們實作出來。

練習

在 learn/ 執行 node check.mjs nestjs 02 建立 work/02/。起始專案只有一個 ProductsController，商品資料放在 controller 的 products 欄位裡（記憶體，重新啟動就回到初始資料；第 3 課搬到 service）。三題都改 src/products.controller.ts，邊寫邊用 npm run start:dev 和 curl -i 自己確認。

練習 1：完成商品的 CRUD：

  • GET /products：回全部；有 ?category= 時只回那個分類（沒有符合就是空陣列）。
  • GET /products/:id：回那一筆，id 在 JSON 裡是數字；找不到回 404；id 不是數字回 400。
  • POST /products：body 是 { name, price, category, tags }，回 201 和加上新 id 的商品；之後用 GET /products/:id 查得到。
  • PATCH /products/:id：只改 body 裡有的欄位，回 200 和更新後的商品；body 裡就算有 id 也不能改掉商品的 id（以網址為準）；找不到回 404。
  • DELETE /products/:id：回 204、沒有內容；找不到回 404。

測試會先刪掉一筆再新增，確認新 id 沒有跟現有商品撞號，也沒有重發刪掉的 id。可以用 curl -i -X POST http://localhost:3100/products -H 'Content-Type: application/json' -d '{"name":"冰滴咖啡","price":130,"category":"coffee","tags":["iced"]}' 這類指令自己試。

練習 2：起始程式的 GET /products/featured 寫在 GET /products/:id 後面，永遠到不了：還沒做練習 1 時它回 { "id": "featured" }，做完練習 1（用了 ParseIntPipe）之後變成 400。修好它，讓 /products/featured 回拿鐵和起司蛋糕，/products/2 照樣回拿鐵。網址不能改；在 findOne 裡判斷 id === 'featured'、或只在 main.ts 開 routeResolutionStrategy 都不算，測試會用預設設定建應用，也會檢查方法的宣告順序。

練習 3：新增 GET /products/search，三個查詢參數都可以不給，給了就全部都要符合：

  • q：名稱包含這段文字（?q=咖啡 → 美式咖啡）。
  • maxPrice：價格 ≤ 這個數字；不是整數回 400。
  • tags：可以出現多次（?tags=iced&tags=milk），商品要有全部這些標籤（標籤完全相同才算，ice 不算 iced）。只給一個時你拿到的是字串。

沒有任何參數時回全部 6 項。想想這個路由要宣告在哪裡。

練習 4：同事說「Nest 的 handler 全部都回 200，DELETE 想回 204 只能自己用 res.status(204)」。哪一個說法正確？

✓ Nest 的預設是 POST 201、其他 200，用 @HttpCode() 改，不需要碰回應物件。a 錯：注入 @Res() 會進入 library-specific 模式，關掉 Nest 的回應處理，連 @HttpCode() 都失效。b 錯：只有 POST 預設 201，DELETE 是 200。

練習 5：controller 裡 @Get(':id') 宣告在 @Get('featured') 前面，使用預設設定。GET /products/featured 會怎樣？

✓ 預設的 routeResolutionStrategy 是 'declaration'：照方法的宣告順序登記，Express 用第一條符合的，:id 比對得到 featured。b 是開了 routeResolutionStrategy: 'specificity' 才有的行為，預設沒開。c 錯：衝突檢查 routeConflictPolicy 預設是 'off'，不會丟錯。

練習 6：handler 的參數注入了 @Res() res: Response，方法裡沒有呼叫 res.json()，只寫了 return { ok: true }。客戶端會收到什麼？

✓ 注入 @Res() 代表你接手送回應，Nest 不再處理回傳值，也不會檢查你有沒有送，所以 a、c 都不會發生。請求就這樣掛著，伺服器端沒有任何錯誤訊息，很難查。需要碰回應物件時改用 @Res({ passthrough: true })。

常見錯誤

  • 以為路徑與查詢參數是數字：@Param('id') id: number 型別檢查會過，執行時是字串，=== 比對永遠失敗。路徑參數用 ParseIntPipe，選填的查詢參數用 new ParseIntPipe({ optional: true })。
  • 找不到資料回 200：回傳 undefined 或 null 是 200 加空內容。丟 NotFoundException。
  • 同時用 @Res() 又 return 值：回傳值不會送出，請求卡住。不用 @Res()，或改成 @Res({ passthrough: true })。
  • 固定路由宣告在參數路由後面：/products/featured 被 :id 攔走。固定路徑寫在前面。
  • 以為 ?a[b]=1 會變成巢狀物件：Express 5 預設 simple 解析，鍵名就是 'a[b]'。用平的參數名稱。
  • 假設重複的查詢參數一定是陣列：只出現一次時是字串。用 [x].flat() 統一。
  • 新 id 用 products.length + 1 或「目前最大的 id ＋ 1」：刪掉 2 號之後陣列剩 5 筆，length + 1 給出 6，跟還在的起司蛋糕撞號；「最大 id ＋ 1」在刪掉 6 號之後又發出 6，前端還留著的 /products/6 連結就指到另一個商品。用一個只增不減的計數器；接上資料庫後交給 PostgreSQL 的 identity 欄位產生，它也不會重發用過的號碼。
  • PATCH 整筆取代：沒送的欄位被洗掉。只合併送來的欄位，而且不讓 body 改到 id。
  • 在 controller 裡塞商業邏輯：這一課為了專心在 HTTP，資料和邏輯暫時放在 controller；controller 該只負責「HTTP 進、HTTP 出」，下一課搬到 provider。

NestJS 12 的路由順序與衝突檢查設定

NestJS 12 加了兩個選用的設定（NestFactory.create(AppModule, { … }) 的選項，12.3.2 預設都沒開）：

選項做什麼怎麼用
routeResolutionStrategy: 'specificity'登記路由時改成固定片段優先、參數其次、萬用字元最後，跟宣告順序無關。預設是 'declaration'（宣告順序）；Fastify 上沒有作用可以開，但不要拿它取代正確的宣告順序：測試或另一個入口用預設設定建應用時，問題又會回來
routeConflictPolicy: { duplicate, shadow }啟動時檢查路由衝突，每一種可以設 'off'、'warn'、'error'。duplicate 是方法與路徑完全相同；shadow 是兩條路由可能比對到同一個請求duplicate: 'error' 適合一直開。shadow 在 12.3.2 實測：順序正確的 featured 與 :id 也會被列出來，適合偶爾開 'warn' 掃一遍，不適合當成啟動失敗的條件

Express 5 跟 Express 4 教學不同的地方

NestJS 11 起預設跑在 Express 5 上，網路上大量的 Express 4 教學有幾處不再適用：

  • 查詢參數用 simple 解析：Express 4 預設的 extended 解析會把 ?filter[price][gte]=100 變成巢狀物件；Express 5 實測收到的是一個名稱叫 'filter[price][gte]' 的鍵，值是字串 '100'。設計 API 時就用平的參數名稱，例如 ?minPrice=100。
  • 同名參數變陣列：?tags=iced&tags=milk 拿到 ['iced', 'milk']，只有一個時是字串，見正文最後一節。
  • 萬用字元要命名：純 Express 5 要寫 'files/{*splat}'（splat 是自己取的名字；外面的大括號表示這一段可有可無）。Nest 有相容層，@Get('files/*') 仍然能用，但啟動時會印出 Unsupported route path 警告並自動改寫；新程式直接照新寫法。
  • async 錯誤自動交給錯誤處理：Express 4 裡 async 函式拋錯要自己 next(err)，Express 5 會自動接住。在 Nest 裡這件事本來就由框架處理。

從 NestJS 10（底下是 Express 4）升級的專案，若依賴 ?filter[price][gte]= 這種巢狀格式，升級後篩選會默默失效、不會報錯，升級前要先搜尋程式碼確認有沒有這種用法。

全域前綴與 CORS

正式的 API 通常在所有路徑前加 /api，用全域前綴（global prefix）app.setGlobalPrefix('api') 一次設定；前端網域不同時還要開 CORS。這兩件事在 第 10 課跟 E2E 測試一起做，這一課的路徑先不加前綴。

小結

  • 先寫規格：每支 API 的路徑、成功和失敗各回什麼，跟前端對過再動手。PATCH 只改送來的欄位，刪除成功回 204。
  • 路由＝HTTP 方法＋路徑；最終路徑是 @Controller() 前綴加上 @Get() 等裝飾器的路徑，:id 這類路徑參數能比對任何一段文字。
  • @Param、@Query、@Body、@Headers 取值；路徑與查詢參數一律是字串（或字串陣列），型別註記不會幫你轉型，用 ParseIntPipe 轉型並擋掉不合格的值。
  • 回傳值就是回應；POST 預設 201、其他 200，@HttpCode()、@Header() 調整；找不到等預期內的失敗丟 HttpException 的子類別，一般 Error 變成不洩漏細節的 500。
  • 不用 @Res()：它會讓回傳值、@HttpCode()、攔截器失效；要碰回應物件就用 passthrough: true。
  • Nest 照宣告順序登記路由，固定路徑寫在參數路徑前面；v12 的 routeResolutionStrategy、routeConflictPolicy 是輔助，不是修法。
  • Express 5 的同名查詢參數只出現一次時是字串，用 [x].flat() 統一；巢狀的 ?a[b]= 不會變成物件，用平的參數名稱。
