階段 3：資料庫（Docker、Prisma 7 ＋ PostgreSQL） · 第 17 課

資料庫整合測試與測試資料

第 15 課把下單改成「條件式更新＋交易」，早上八點 20 個人同時搶最後 5 杯拿鐵，也只會賣出 5 杯。想像下個月有位同事送了一個「重構」的 PR：他覺得 $transaction 包一層很囉嗦，把它拿掉；或者覺得 updateMany 加 WHERE 不好讀，改回「先查庫存、再扣」。程式照樣能跑，手動點幾次下單也都正常，單元測試全部通過，PR 就這樣合併了。直到某天限量商品開賣，庫存變成負數。

這一課的任務：替 OrdersService.createOrder 寫一套測試，讓上面這種改動在送出 PR 的當下就變紅。做法是讓測試連到真的 PostgreSQL。過程中會一路解決「連哪個資料庫」「測試之間的資料怎麼不互相干擾」「每個測試怎麼快速建好資料」「並發怎麼測」這幾個問題，最後在練習 3 寫出能抓到五種改壞版本的 orders.int-spec.ts。

這課的路線：
  1. 同事拿掉了交易，為什麼 mock 的測試還是綠的：bug 發生在資料庫裡，測試必須連真的資料庫（開場問題的最小答案）。
  2. 測試要連哪個資料庫：為什麼不能用開發的那一個，npm test 用的 nest_17_spec 怎麼準備。
  3. 上一個測試留下的資料怎麼辦：測試隔離的三種做法，為什麼這門課選「每個測試前清空」。
  4. resetDb() 怎麼把每張表清乾淨，以及每個測試要的資料怎麼用工廠一行建好。
  5. 寫出「改壞就變紅」的測試：拿掉交易靠檢查資料庫最後的狀態抓，改回先讀再寫靠同時送出 10 張訂單抓。
  6. PR 送出時誰來跑這些測試：CI 上的 PostgreSQL 從哪裡來。
這課會用到：
  • 第 15 課的互動式交易與條件式更新：下單包在 $transaction 裡，丟例外就整筆回滾；扣庫存用 WHERE stock >= 數量 的 UPDATE，不先讀再寫。
  • 第 10 課的整合測試與 flaky test：測試接上真的元件一起跑；測試之間共用狀態，結果就會時過時不過。
  • 第 12 課的 Docker Compose：課程的 PostgreSQL 跑在容器裡，docker compose up -d 啟動。
  • 第 13 課的 prisma migrate deploy：只套用已經 commit 的 migration 檔，不產生新的，部署和測試都用它建表。

同事拿掉了交易，為什麼 mock 的測試還是綠的？

先看團隊原本的測試。它是第 5 課那種單元測試：把 PrismaService 換成 vi.fn() 組成的假物件（mock），每個方法要回傳什麼，由測試事先設定：

const prisma = {
  $transaction: vi.fn(fn => fn(prisma)),          // 「交易」：直接把自己傳進去
  product: { findUnique: vi.fn(), updateMany: vi.fn() },
  order: { create: vi.fn() },
}

it('成功下單', async () => {
  prisma.product.findUnique.mockResolvedValue({ price: 110 })
  prisma.product.updateMany.mockResolvedValue({ count: 1 })
  prisma.order.create.mockResolvedValue({ id: 1, total: 220 })
  expect((await orders.createOrder(1, [{ productId: 1, quantity: 2 }])).total).toBe(220)
})

現在把同事的 PR 套上去，createOrder 不再呼叫 $transaction，直接用 this.prisma 查商品、扣庫存、建訂單。這個測試會怎樣？findUnique 照樣回傳 { price: 110 }，updateMany 照樣回傳 { count: 1 }，order.create 照樣回傳總額 220。每個方法回傳的都是測試事先寫好的值，跟有沒有交易無關，所以測試照樣通過。把條件式更新改回「先讀再寫」也一樣：只要 mock 回傳的值照舊，測試就看不出差別。

問題出在 mock 的本質：它只會回傳你設定的值，不會做資料庫真正做的事。而第 15 課保護下單的那幾招，全部是資料庫做的事：

  • 約束：UNIQUE、外鍵、CHECK (stock >= 0) 是資料庫檢查的。違反唯一約束時 Prisma 會丟 P2002（第 14 課），mock 不會。
  • 交易：回滾是資料庫做的。mock 的 $transaction 只是呼叫函式，失敗時沒有東西會被還原。
  • 並發：兩個請求搶同一列、鎖、WHERE stock >= 1 在等鎖之後重新判斷，都只發生在真的資料庫。
  • SQL 的語意：orderBy、include、時區、NULL 的比較，mock 只會照你寫的順序回傳。

mock 還有一個反方向的代價：它綁死了實作細節。測試寫明了「會呼叫 findUnique」，哪天有人把 findUnique 改成 findFirst，行為完全一樣，mock 測試卻全部壞掉。結果是該紅的時候綠、該綠的時候紅，團隊很快就不信任這些測試。

所以要抓到同事的 PR，測試必須讓 OrdersService 連到真的 PostgreSQL：真的建商品、真的下單、再真的查庫存。這種「service 接上真的資料庫一起跑」的測試，就是第 10 課提過的整合測試。這也讓第 10 課的測試邊界更明確：資料庫是你自己的，schema、migration、查詢都是你寫的，用真的測；mock 留給你控制不了的外部系統（金流、寄信、第三方 API），還有「資料庫出錯時程式怎麼反應」這種用真的資料庫很難製造的狀況。

整合測試的代價是慢：每個測試要真的寫入、查詢資料庫，要幾十到幾百毫秒。所以兩種測試分工：純邏輯（計價、狀態轉換）用單元測試；查詢、交易、約束用整合測試。

💡 實務上：先問「bug 會發生在哪一層」，再決定要不要 mock
Code review 看到改了查詢、交易、migration 或唯一約束的 PR，資深工程師會先問：「有沒有連真資料庫的測試？」咖啡店系統裡的下單、扣庫存、優惠券只能用一次、會員點數，這類「錢和數量」的路徑最值得寫整合測試，因為出錯就是客訴和對帳問題。反過來，單純的計價公式、狀態轉換規則用單元測試就夠，不必每個 CRUD 都連資料庫。常見的坑是團隊全部用 mock，CI 一片綠，上線後才發現唯一約束或回滾根本沒生效，就像本課開場那個 PR。

決定要連真的資料庫之後，第一個問題是：連哪一個？

測試要連哪個資料庫？

最直覺的答案是連開發時用的那個（這門課是 nest_17，npm run start:dev 用的）。這行不通。下一節會看到，整合測試每次開始前都要把資料表清空；跟開發共用的話，你在開發時手動建的商品、訂單，每跑一次測試就消失一次。反方向也會出事：你手動留下的資料，會讓測試的計數多出幾筆而失敗。

所以需要一個測試資料庫：只給測試用、裡面的資料隨時可以清空重建的資料庫。同一台 PostgreSQL 可以有很多個資料庫，所以不用多開一個容器，只要多建一個名稱不同的資料庫。這一課的專案準備了兩個測試資料庫：圖的上半是判分（node check.mjs nestjs 17）用的 nest_17_test，下半是你自己執行 npm test 用的 nest_17_spec；開發用的 nest_17 兩邊都不碰。兩個分開，是因為判分每次都要整個重建，你自己的那個則要保留資料，讓你在測試失敗後連進去看。

圖的下半是你自己執行 npm test 時發生的事，由專案裡已經寫好的兩個檔案負責。第一步要讓測試連到 nest_17_spec 而不是 nest_17。應用程式從環境變數 DATABASE_URL 讀連線網址，所以 vitest.config.ts 在讀完 .env 之後，把網址裡的資料庫名稱換掉：

config({ quiet: true })   // dotenv：讀 .env；已經有的環境變數優先
const url = new URL(process.env.DATABASE_URL)
url.pathname = url.pathname.replace(/(_test|_spec)?$/, '_spec')   // nest_17 → nest_17_spec
process.env.DATABASE_URL = url.href

測試裡啟動的 ConfigModule 讀到的也是這個改過的值，因為已經存在的環境變數優先於 .env（第 11 課）。

第二步是確保這個資料庫存在、而且有最新的資料表。test/support/global-setup.ts 登記在 Vitest 的 globalSetup 設定裡，意思是在所有測試檔開始前、在 Vitest 的主程序執行一次。它做三件事：

  1. 檢查資料庫名稱是不是 _spec 結尾，不是就拒絕執行。這是最後一道保險：設定寫錯時，寧可測試跑不起來，也不要清空開發用的資料。
  2. 資料庫不存在就 CREATE DATABASE。已經存在就不動它，所以測試失敗後，你還能連進去看當時留下的資料。
  3. 執行 prisma migrate deploy，套用還沒套用的 migration。

為什麼建表用 migrate deploy，而不是更省事的 db push？deploy 套用的是你 commit 的 migration 檔，跟正式環境部署時一樣（第 13 課）。這樣測試同時也在測 migration：migration 寫錯，測試就先失敗，而不是到部署那天才發現。

圖的上半是判分（node check.mjs nestjs 17）。它的思路一樣，只是更嚴格：每次都把 nest_17_test 整個刪掉重建，保證每次判分都從同一個起點開始。判分還有幾個設計細節，見課末「補充與查表」。

現在測試有了自己的資料庫，但這個資料庫在整個 npm test 期間是同一個：第一個測試建的商品，第二個測試也看得到。下一節處理這件事。

上一個測試留下的資料，怎麼不影響下一個測試？

先看會出什麼事。練習 3 有「庫存不足：不建立訂單」這個測試，它的斷言是 expect(await prisma.order.count()).toBe(0)。如果它前面的「成功下單」測試已經建了一張訂單，資料庫裡就有 1 張，這個斷言失敗。可是單獨跑「庫存不足」時，它又會通過。同一個測試，結果取決於前面跑了什麼，這就是第 10 課說的 flaky test，而共用的資料庫正是最典型的共用狀態。

要避免這種事，測試需要測試隔離（test isolation）：每個測試的結果不受其他測試影響。單獨跑、一起跑、換順序跑，結果都一樣。對資料庫來說，就是每個測試開始時，資料庫都處在同一個已知的狀態（通常是空的）。常見的三種做法如下，表中的 worker 與 template 資料庫，下面會說明：

做法怎麼做優點代價
每個測試前清空beforeEach 執行 TRUNCATE 所有資料表簡單；資料真的 commit，交易、並發都測得到同一個資料庫的測試檔不能平行跑；表多時每次清空要幾十毫秒
每個測試包在交易裡，最後回滾測試開始時 BEGIN，結束時 ROLLBACK，程式要用這個交易的連線最快，不用清空測不到 COMMIT 之後的行為與並發；程式自己開的交易要另外處理
每個 worker 一個資料庫每個平行執行的 worker 用自己的資料庫，常用 template 資料庫快速複製可以平行跑，速度隨核心數增加設定多；資料庫多，要記得清理

第二種「交易回滾」看起來最划算：不用清空，測試裡建的資料隨著 ROLLBACK 一起消失。但它跟本課的任務衝突。要抓到「改回先讀再寫」，測試得同時送出 10 張訂單（後面「改壞就變紅」那一節會寫），而第 15 課的超賣，只在多個交易同時 commit 時才會發生。10 個請求各自用自己的連線、自己的交易，看不到測試那個還沒 commit 的交易裡建的商品，所以根本找不到資料。反過來，如果讓 10 個請求都共用測試那一條連線，它們就變成一個接一個執行，「同時」也就不存在了。另外，本課的 createOrder 自己會呼叫 $transaction 開交易；要讓它跑在測試的交易裡，就得把 PrismaService 換成包著測試交易的版本，或改用 savepoint，這又多一層要維護的東西。

第三種「每個 worker 一個資料庫」要先知道 worker 是什麼。Vitest 預設會開好幾個子程序，每個子程序負責跑一部分的測試檔，讓不同的測試檔同時跑，這些子程序叫 worker。每個 worker 用自己的資料庫，就能平行又互不干擾，代價是要管理一批資料庫。

這門課選第一種：每個測試前清空，資料真的 commit，交易和並發都測得到。代價是同一個資料庫上的測試檔不能同時跑，所以 vitest.config.ts 設了 fileParallelism: false，讓測試檔一個一個跑。專案變大、測試變慢時，再換成每個 worker 一個資料庫：PostgreSQL 的 CREATE DATABASE x TEMPLATE y 可以從一個已經套用好 migration 的資料庫複製出新的，比每次跑 migration 快。

共用同一個資料庫又平行跑：A 檔案的 beforeEach 清空資料表的瞬間，B 檔案的測試剛建好商品，B 就莫名其妙找不到資料。這種錯誤時有時無，重跑又好了，是最難查的那一種。

決定了「每個測試前清空」，接下來要寫出負責清空的那個函式。

resetDb() 怎麼把每張表清乾淨？

清空資料表有兩種寫法（PostgreSQL 課第 6 課）：DELETE 逐列刪除，TRUNCATE 直接丟掉整份資料。測試要的是 TRUNCATE，再加兩個選項：

  • RESTART IDENTITY：自動編號（SERIAL 背後的 sequence）從 1 重新開始。DELETE／deleteMany() 不會重設，測試跑越多次 id 越大。
  • CASCADE：連同「有外鍵指向這些表」的表一起清空。一句 TRUNCATE 列出所有表時其實用不到；有了它，就算漏列某張子表也不會因為外鍵而失敗。
TRUNCATE "orders", "order_items", "products" RESTART IDENTITY CASCADE;

下一個問題是要清哪些表。常見的寫法是一張一張寫 deleteMany()。問題是下個月加了 audit_logs，沒人記得回來改，這張表的舊資料就留在測試之間，又回到上一節的 flaky test。更好的做法是每次從 pg_tables 查。pg_tables 是 PostgreSQL 自己維護的系統目錄，列出這個資料庫裡的每一張表；新增一張表，它就自動多一列，不用任何人記得改程式：

SELECT tablename FROM pg_tables WHERE schemaname = 'public';

查出來的表裡有一張不能清：_prisma_migrations。Prisma 在這張表記錄哪些 migration 套用過；清掉之後，下次 migrate deploy 會以為一個都沒套用，重跑 CREATE TABLE 然後失敗。

最後是怎麼在 Prisma 裡執行。第 15 課用過 $queryRaw`… ${x}`：${} 會變成參數 $1，值另外傳給資料庫，所以不會有 SQL injection。可是參數只能放值，不能放表名、欄位名。表名、欄位名這類用來指名資料庫物件的名字叫識別字（identifier），資料庫要先知道句子動到哪張表，才能規劃怎麼執行，所以識別字必須寫在 SQL 本身裡。因此 TRUNCATE 那一句只能把表名組成字串，用 $executeRawUnsafe(sql) 執行。這裡是安全的，因為表名來自資料庫本身，不是使用者輸入。

組字串時，每個表名還是要用雙引號包起來。PostgreSQL 會把沒加引號的識別字轉成小寫，Prisma 的 model 沒寫 @@map 時表名是 Category 這種有大寫的名稱，TRUNCATE Category 會去找 category，找不到就出錯；寫成 "Category" 才對。

練習 1 請你把這些組成 resetDb(prisma)。練習 3 的測試檔已經在 beforeEach 呼叫它，所以每個測試都從空的資料表開始。

可是資料表空了，每個測試就得自己建它需要的分類、商品、顧客，這會讓測試變得又長又難讀。

每個測試都要自己建資料：怎麼只寫在乎的欄位？

以「庫存不足」為例，它只需要一個庫存是 0 的商品。但商品要有分類（外鍵），名稱還要唯一。每個測試都把這些寫一遍，測試的重點就淹沒在雜訊裡：

// 每個測試都這樣寫：看不出這個測試在乎的是哪個欄位
const category = await prisma.category.create({ data: { name: '飲料' } })
const latte = await prisma.product.create({ data: { name: '拿鐵', price: 110, stock: 0, isAvailable: true, categoryId: category.id } })

讀這兩行的人得逐欄判斷：價格 110 重要嗎？isAvailable 重要嗎？其實只有 stock: 0 重要。而且 schema 哪天多一個必填欄位，所有這樣寫的測試都要改。

解法是測試資料工廠（factory，也叫 builder）：一組專門替測試建資料的函式，每個欄位都有合理的預設值，測試只傳它在乎的欄位，其他交給預設值：

const latte = await createProduct(prisma, { stock: 0 })   // 一眼看出：這個測試在乎的是庫存 0

工廠看起來只是包一層 create，但寫不好會讓測試以奇怪的方式失敗。好的工廠要做到這幾點，每一點都對應一種實際會遇到的失敗：

  • 回傳寫進資料庫的紀錄（有 id），測試拿 latte.id 去用，不寫死 productId: 1。寫死的 id 只在「剛好是第一筆」時成立，前面多建一筆資料就錯。
  • 唯一欄位每次都不同：用一個遞增的計數器組名稱（商品 1、商品 2）。固定的名稱，第二次呼叫就撞 UNIQUE，丟 P2002。
  • 需要的關聯自己建：沒給 categoryId 就先建一個分類；給了就用給的，不要多建。
  • 覆寫要照用，包括 0 和 false：stock: overrides.stock || 10 在傳入 0 時會變回 10，這個工廠就永遠建不出庫存 0 的商品。用展開 { ...defaults, ...overrides } 或 ??。
  • 只準備資料，不跑業務規則：createOrder 直接寫入訂單，不扣庫存。要測下單規則就呼叫 OrdersService；工廠是用來建「前提」的。

覆寫參數的型別可以直接用 Prisma 產生的 Partial<Prisma.ProductUncheckedCreateInput>。Prisma 為每個 model 產生兩種建立資料的型別：一般版用巢狀物件表示關聯（category: { connect: { id } }），Unchecked 版直接用外鍵欄位（categoryId）。工廠的呼叫端手上通常已經有 id，所以 Unchecked 版比較順手。

計數器放在模組層級，同一次 npm test 裡會一直遞增，resetDb() 之後也不會重複，因為資料都清掉了。練習 2 請你完成四個工廠。

💡 實務上：修 bug 前先用工廠寫一個會失敗的測試
客服回報「下架的商品還能加進訂單」，與其手動在後台點來點去重現，不如寫一個 createProduct(prisma, { isAvailable: false }) 的測試，確認它現在會失敗，修好後變綠，之後也不會再壞。工廠通常放在 test/support/ 給整個團隊共用；schema 新增一個必填欄位時，只要改工廠的預設值，不用改幾十個測試。要小心工廠預設值太「聰明」，例如自動幫你建好訂單和付款，測試就看不出自己依賴了哪些前提。

到這裡工具都齊了：獨立的測試資料庫、每個測試前清空的 resetDb()、一行建好資料的工廠。回到開場的任務，寫出能抓到同事 PR 的測試。

怎麼寫出「改壞就變紅」的測試？

判斷一個測試有沒有用，標準只有一個：把程式改壞，它會不會失敗。第 15 課的下單有兩道保護，同事的 PR 可能拆掉其中一道，所以要分別設計測試。

拿掉交易：斷言資料庫最後的狀態

交易保護的是「一張訂單有好幾項商品，任何一項失敗，前面扣掉的庫存要還原」。所以測試要製造一個「第二項才失敗」的情境：拿鐵庫存 5、起司蛋糕庫存 1，下單拿鐵 1 杯、蛋糕 3 個。

有交易時，createOrder 先扣拿鐵（5 → 4），再扣蛋糕時發現不夠，丟 OutOfStockError，整個交易回滾，拿鐵回到 5。拿掉交易後，拿鐵那句 UPDATE 已經自己 commit 了，蛋糕失敗時沒有東西會還原它，拿鐵停在 4。注意兩個版本都會丟 OutOfStockError，所以只檢查「有丟錯」分不出它們。差別只在資料庫裡，測試就要去資料庫裡看：

it('第二項庫存不足：整筆回滾，第一項的庫存也沒被扣', async () => {
  const customer = await createCustomer(prisma)
  const latte = await createProduct(prisma, { stock: 5 })
  const cake = await createProduct(prisma, { stock: 1 })

  await expect(orders.createOrder(customer.id, [
    { productId: latte.id, quantity: 1 },
    { productId: cake.id, quantity: 3 },
  ])).rejects.toBeInstanceOf(OutOfStockError)

  // 只看「有丟錯」不夠：沒有交易的版本也會丟錯，但拿鐵已經被扣成 4
  expect((await prisma.product.findUniqueOrThrow({ where: { id: latte.id } })).stock).toBe(5)
  expect(await prisma.order.count()).toBe(0)
})

這就是整合測試的斷言重點：資料庫最後的狀態，不只是函式的回傳值。練習 3 的其他測試也照這個原則，例如「成功下單」除了看回傳的總額，還要查商品確認庫存真的扣了。

改回先讀再寫：同時送出 10 張訂單

另一道保護是條件式更新。先讀再寫的版本，一個人下單時完全正常：讀到庫存 5，扣成 4，沒有問題。它只在兩個請求同時讀到同一個庫存、各自扣減時才會賣超（第 15 課）。所以測試也必須真的同時送出請求：拿鐵庫存 5，同時送出 10 張各買 1 杯的訂單，正確的程式應該剛好 5 張成功、庫存變 0。

這種測試要做到三件事：真的同時送出、等全部結束、斷言最後的狀態。

const results = await Promise.allSettled(
  Array.from({ length: 10 }, () => orders.createOrder(customer.id, [{ productId: latte.id, quantity: 1 }])),
)
expect(results.filter(r => r.status === 'fulfilled')).toHaveLength(5)
  • 先建好 10 個 Promise 再一起等，才是同時送出。for 迴圈裡一個一個 await，請求就變成依序執行，先讀再寫的版本也會過。
  • 用 Promise.allSettled，不是 Promise.all：預期有 5 個會失敗，Promise.all 遇到第一個失敗就 reject，其他請求還在跑，你就開始斷言了，甚至跑進下一個測試的 resetDb()。
  • 失敗的那 5 個要確認是 OutOfStockError，而不是逾時或其他錯誤；最後再查一次資料庫，確認庫存是 0。

為什麼是 10 個，不是 100 個？PrismaPg 的連線池預設最多 10 條（第 16 課），10 個互動式交易剛好用完。並發數超過連線池時，多出來的交易要排隊；排超過 maxWait（預設 2000 毫秒）就會失敗，測試失敗的原因就變成連線池，而不是你想測的庫存。

請求的先後順序每次都不同，這個測試在 CI 上能穩定重跑嗎？可以。資料每次從空表開始，對正確的程式來說，不管誰先誰後，「剛好 5 張成功、庫存 0」永遠成立；只有錯的程式才會有時賣超、有時不會。所以並發測試偶爾失敗時，要先懷疑程式，不是按重跑。

💡 實務上：搶購、限量、只能用一次，都是同一類並發問題
限量商品開賣、優惠碼只能兌換一次、同一張訂單被重複付款，都是「多個請求同時改同一筆資料」，本機一個人點永遠點不出來。修這類 bug 時，先寫出像上面那樣的並發測試，在舊程式上確認它會失敗，再修程式讓它通過；沒看過它失敗，就不知道它真的抓得到。修法通常就是第 14、15 課那幾招：條件式更新（WHERE stock >= 1）或唯一約束，讓資料庫替你擋，而不是在程式裡先查再判斷。

測試寫好了，但開場的問題還剩最後一半：同事送出 PR 時，誰來跑這些測試？

PR 送出時，誰來跑這些測試？

靠每個人記得在本機跑 npm test 是不夠的，開場那位同事可能根本沒跑。團隊的做法是持續整合（continuous integration，CI）：一個在每次 push 或送出 PR 時，自動把程式抓下來、安裝套件、跑測試的服務。測試沒過，PR 上就會顯示紅叉，大家在合併前就看得到。開場那個拿掉交易的 PR，就會在這一步被擋下。

整合測試搬到 CI 上，要多解決一件事：CI 的機器上也需要一個 PostgreSQL。GitHub Actions 可以宣告 service container：工作開始前先啟動 postgres:18.6-alpine 容器，測試用 localhost 連過去，DevOps 課會實作（DevOps 課第 15 課）。之後的流程跟本機一樣：建資料庫 → migrate deploy → 跑測試。

這跟這門課本機的做法是同一個思路：資料庫容器事先啟動好，測試直接連。另一種做法是 Testcontainers，在測試程式裡自己啟動資料庫容器；兩者的取捨見課末「補充與查表」。

到這裡，開場的任務完成了：拿掉交易，回滾測試變紅；改回先讀再寫，並發測試變紅；而 CI 讓這些紅燈在合併前就出現。

補充與查表

判分的設計細節

  • 不用 prisma migrate reset：它會刪掉整個資料庫的資料，而且 Prisma 7.10.1 偵測到在 AI agent 底下執行時會直接拒絕（migrate deploy 不受影響）。判分用 SQL 的 DROP DATABASE／CREATE DATABASE 重建，並且只刪名稱符合 nest_…_test 的資料庫，打錯設定也刪不到開發資料庫。
  • 每一題、每個資料夾一個資料庫：work/17 用 nest_17_test，出題檢查的 verify/17-answer 用 nest_17_answer_test，可以同時跑、互不干擾。
  • 工廠的計數器與平行執行：要讓多個 worker 共用一個資料庫時，名稱還要加上 worker 的編號才不會撞；這門課一次只跑一個檔，用不到。

Testcontainers

Testcontainers 是在測試程式裡啟動資料庫容器、測試結束時自動移除的做法。它的 PostgreSQL 模組（@testcontainers/postgresql）可以 new PostgreSqlContainer('postgres:18.6-alpine').start()，再用 getConnectionUri() 拿連線網址；還有 snapshot()／restoreSnapshot()，背後就是前面說的 template 資料庫。這門課沒有安裝它，只要知道取捨：

事先啟動的容器（這門課、CI service）Testcontainers
啟動開發時啟動一次，測試直接連每次測試都啟動容器，多幾秒
設定在哪compose.yaml、CI 設定檔測試程式裡，npm test 一個指令就能跑
適合大家都有同一套 Docker 環境每個專案要不同版本的資料庫、不想要求先啟動服務

測試資料庫的 fsync

測試資料庫還可以為了速度關掉 PostgreSQL 的 fsync：資料不會每次 commit 都寫到磁碟，機器當機時資料可能損壞。對隨時可以重建的測試資料庫可以接受，正式環境絕對不行。

練習

在 learn/ 執行 node check.mjs nestjs 17 建立 work/17/（Docker 的容器要先啟動，第 12 課）。OrdersService 是第 15 課做完的版本，這一課不改 src/，只寫測試用的程式。資料表有 categories、products（stock、is_available）、customers（phone 唯一）、orders、order_items，已經有 migration。

自己的測試在 work/17 執行 npm test，用的是 nest_17_spec；想看資料可以用 docker exec -it learn-nestjs-postgres psql -U learn -d nest_17_spec。三題依序做：練習 3 會用到練習 1、2 寫的函式。

練習 1：寫 resetDb(prisma)：從 pg_tables 查出 public schema 裡除了 _prisma_migrations 以外的所有表，用一句 TRUNCATE … RESTART IDENTITY CASCADE 清空，自動編號從 1 重新開始。

判分會在資料庫裡多建一張你沒看過的表（名稱每次不同、有大寫，像 Prisma 的 model 沒寫 @@map 時的表名），每張表都放資料，呼叫你的 resetDb 之後檢查：每張表都是 0 筆、新增的第一筆 id 是 1、_prisma_migrations 沒被動到、連續呼叫兩次不會出錯。寫死表名、表名沒加雙引號、用 DELETE／deleteMany() 都不會過。

練習 2：完成四個工廠，簽名已經寫好：createCategory、createProduct（預設可販售、庫存 10、價格大於 0；沒給 categoryId 就自己建分類）、createCustomer、createOrder（沒給 customerId 就建一位顧客；沒給 items 就建一個商品、買 1 個；quantity 預設 1；單價從商品複製、總額自己算；回傳帶 items 的訂單；不扣庫存）。

判分會在自動編號不是從 1 開始的資料庫裡呼叫你的工廠：每個工廠呼叫多次都不能撞到唯一欄位、傳入的值要蓋過預設值（包括 stock: 0 和 isAvailable: false）、給了 categoryId／customerId／productId 就不能多建資料。

練習 3：test/orders.int-spec.ts 已經寫好建立應用、取得 OrdersService 與 PrismaService、每個測試前 resetDb 的部分，以及五個 it.todo。把每個 it.todo 改成真的測試：成功下單（總額、明細、扣掉的庫存）、庫存不足（丟 OutOfStockError、沒有訂單）、第二項庫存不足時整筆回滾、單價快照（下單後改商品價格，findOrder 的單價與總額不變）、庫存 5 時同時送出 10 張訂單。資料一律用練習 2 的工廠建立。

這題只寫測試。判分會拿你的測試跑五個改壞的 OrdersService：沒有交易、扣庫存沒用 tx、改回先讀再寫、單價在查詢時才從商品讀、庫存不足時沒丟錯，每一個都要讓你的測試失敗。mock PrismaService、沒有並發測試、只看回傳值不看資料庫、拿掉 beforeEach 的 resetDb、it.todo／it.skip 都不會過。判分要跑六次你的測試，需要一兩分鐘。

練習 4：同事說「每個測試包在交易裡、最後回滾最快，乾脆全部改成這樣」。為什麼這樣就測不出第 15 課的超賣 bug？

✓ 回滾隔離的前提是「所有東西都在同一個交易裡」，這正好跟並發測試要的「多個交易同時跑、各自 commit」相反。約束在交易裡照樣有效（a 錯），交易裡當然可以 UPDATE（b 錯）。d 錯：在交易裡再下 BEGIN，PostgreSQL 只會發出警告、不會報錯，也可以用 savepoint 做出「交易裡的交易」；但這些操作還是擠在同一條連線上依序執行，一樣測不到並發。

練習 5：一個 repository 的測試把 Prisma 換成 mock，「因為比較快，而且一樣準」。下面哪一組 bug 是這種測試一定抓不到的？

✓ b 的每一個都是資料庫的行為：約束、外鍵、交易、SQL 的語意。mock 只回傳你設定的值，所以這些情況根本不會發生，測試照樣通過。a 是純邏輯，用單元測試就抓得到，也不需要資料庫。c 在 mock 下也會出錯（拿到 Promise 而不是值），抓得到。mock 的「準」只是對你自己的假設準。

練習 6：專案有 orders.int-spec.ts 和 products.int-spec.ts，都在 beforeEach 呼叫 resetDb()，共用同一個測試資料庫。有人把 fileParallelism: false 拿掉想加快速度，之後測試偶爾失敗、重跑又好。最可能的原因？

✓ 每個檔案「自己」清空資料，不代表兩個檔案互不影響：它們共用的是同一個資料庫。平行跑時，A 的 TRUNCATE 會清掉 B 正在用的資料（c 錯）。要平行就讓每個 worker 用自己的資料庫；不然就一次跑一個檔。beforeEach 在平行時一樣會執行（b 錯），問題正是它清的範圍超出自己的檔案。

常見錯誤

  • mock 掉資料庫，以為測過了交易：mock 的 $transaction 只是呼叫函式，不會回滾。交易、約束、並發用真的資料庫測。
  • 測試依賴上一個測試留下的資料：單獨跑或換順序就壞。每個測試前 resetDb()，需要的資料在測試裡用工廠建。
  • 寫死要清空的表名：新增的表不會被清空，舊資料留在測試之間。從 pg_tables 查，排除 _prisma_migrations。
  • 用 DELETE／deleteMany() 清空：編號不會重設，還要自己排好刪除順序。用 TRUNCATE … RESTART IDENTITY CASCADE。
  • 測試共用開發用的資料庫：跑一次測試，手動建的資料就消失。測試用自己的資料庫，並且在程式裡檢查名稱，不對就拒絕執行。
  • 測試寫死 id 或名稱：productId: 1 只在剛好是第一筆時成立，固定名稱第二次就 P2002。用工廠回傳的紀錄，名稱用計數器。
  • 並發測試沒有等全部完成就斷言：用 Promise.all 遇到第一個失敗就往下走，或在迴圈裡一個一個 await 變成依序執行。先建好所有 Promise，用 Promise.allSettled 等全部結束。
  • 只斷言回傳值或丟出的錯誤：沒有交易的版本也會丟 OutOfStockError。查資料庫確認庫存、訂單數。

小結

  • 開場的 PR 拿掉交易、改回先讀再寫，mock 測試照樣通過：約束、交易、並發、SQL 語意都發生在資料庫裡，mock 只回傳你設定的值。資料庫是你自己的程式，用真的 PostgreSQL 測，mock 留給外部服務。
  • 測試資料庫跟開發資料庫分開（nest_17_spec），程式裡檢查名稱，不對就拒絕執行；表用 migrate deploy 套用 commit 的 migration 建立，順便測到 migration。
  • 隔離方式：每個測試前清空（簡單、測得到並發）、交易回滾（快、測不到 commit 後與並發）、每個 worker 一個資料庫（可平行、設定多）。這門課選清空，所以同一個資料庫的測試檔不能平行跑（fileParallelism: false）。
  • resetDb()：從 pg_tables 查表名、排除 _prisma_migrations、一句 TRUNCATE … RESTART IDENTITY CASCADE；識別字不能當參數，只能組字串，表名加雙引號。
  • 工廠：預設值＋覆寫（0 與 false 也照用）、唯一欄位用計數器、自己建需要的關聯、回傳有 id 的紀錄、不跑業務規則。
  • 「改壞就變紅」：拿掉交易要靠斷言資料庫最後的狀態抓（兩個版本都會丟錯）；先讀再寫要靠並發測試抓：同時送出、Promise.allSettled 等全部結束，再檢查成功數與庫存。
  • CI 在每個 PR 自動跑這些測試，CI 上的 PostgreSQL 用 service container 提供，紅燈在合併前就出現。

下一課把肥大的 service 拆成清楚的分層，並決定交易的邊界該放在哪一層：這一課的整合測試，就是重構時不怕改壞的保障。
