階段 2：請求管線與測試 · 第 10 課

E2E 測試：從 HTTP 測整個應用

第 8 課做完之後，同事整理 AppModule，覺得 { provide: APP_PIPE, … } 那一行看不懂，順手刪掉了。第 5 課寫的 OrdersService 單元測試全部通過，CI 也是綠的，程式就這樣上線。隔天前端回報：漏送 items 的下單請求，畫面跳出「系統忙碌，請稍後再試」。照理說它該拿到 400 和 VALIDATION_FAILED，讓前端在欄位下方提示「請選擇商品」；實際上請求一路走進 service，在讀 items 時出錯，被 filter 轉成 500 INTERNAL_ERROR。

單元測試沒有錯，它只是看不到這個 bug：它直接呼叫 OrdersService.create，請求從來沒經過 pipe。一個真正的請求要走過一整條路：middleware、guard、pipe、controller、service、filter，每一段各自正確，接起來還是可能壞。這一課的任務是替 POST /api/orders 寫一組從 HTTP 進、從 HTTP 出的測試，目標有兩個：像開場這種改壞，在 CI 上就會被擋下；而且不管什麼時候、在哪台機器跑，結果都一樣。

這課的路線：
  1. 單元測試全綠，下單為什麼還是壞了：單元、整合、E2E 三種測試各看得到哪一類 bug，開場的 bug 要用哪一層抓（開場問題的最小答案）。
  2. 不開伺服器怎麼發 HTTP 請求，測試建出來的 app 跟正式環境是不是同一個：supertest 的用法，以及只寫在 main.ts 的設定為什麼在測試裡不存在。
  3. 前端在 5173、API 在 3100：搬進共用設定的 CORS 允許清單該怎麼寫、怎麼測。
  4. 下單會真的扣款，測試要斷言什麼：哪些依賴換成替身、哪些一定要用真的；只斷言前端依賴的欄位。
  5. 同一組測試為什麼有時過、有時不過：時好時壞的測試從哪裡來，CI 紅了為什麼不該直接重跑。
這課會用到：
  • 第 5 課的 Vitest 與 Testing Module：describe／it／expect 寫測試，Test.createTestingModule 讓 Nest 組出要測的東西，overrideProvider(token).useValue(…) 把某個依賴換成替身，CLOCK 把「現在幾點」固定住。
  • 第 6～8 課的全域元件：guard、ValidationPipe、exception filter 分別用 APP_GUARD（第 6 課）、APP_PIPE（第 7 課）、APP_FILTER（第 8 課）登記在模組裡，對每個請求都生效；錯誤回應帶 errorCode，前端靠它決定怎麼顯示。

單元測試全綠，下單為什麼還是壞了？

先把開場的事故拆開看。被刪掉的是一行模組設定，它影響的是「請求進到 controller 之前，有沒有人檢查 body」。第 5 課的單元測試從 service 的方法開始執行，前面那一段路根本不在它的範圍裡，所以 pipe 在不在，它的結果都一樣。這不是測試寫得不好，而是每一種測試只看得到某個範圍裡的 bug。

依照範圍大小，後端常見的測試分成三種：

  • 單元測試（unit test）：第 5 課學過，只執行一個函式或一個 class，它需要的外部東西都換成替身。範圍最小，所以最快，壞了也最容易知道是哪一行。
  • 整合測試（integration test）：把幾個元件接在一起測，最常見的是「service 加上真的資料庫」，確認你寫的查詢在真的資料庫上跑得出正確結果。第 17 課會寫。
  • E2E 測試（end-to-end，端到端）：從應用最外層的入口進去，看最外層出口出來的結果。對 API 來說，入口和出口都是 HTTP：送一個請求，檢查回應的狀態碼、body 和標頭。中間經過的 middleware、guard、pipe、controller、service、filter 全都是真的程式。

開場的 bug 只有 E2E 看得到。「缺欄位要回 400 VALIDATION_FAILED」不是任何一個函式的行為，而是全域 pipe 擋下請求、filter 把錯誤整理成固定格式，兩者組合出來的結果。同樣的道理也適用於「路由在 /api 底下」「沒帶金鑰要 401」「錯誤 body 一定有 errorCode」這些事：它們都發生在 service 之外。

三種測試的差別整理成表，看的時候注意「壞掉時」那一列：範圍越大，信心越接近使用者實際的體驗，但失敗時越難直接指出是哪一行。

單元測試整合測試E2E 測試
範圍一個函式或 class幾個元件＋資料庫整個應用，從 HTTP 進出
速度幾毫秒幾十毫秒到幾百毫秒每個應用啟動要幾十到幾百毫秒
給你的信心這段邏輯對跟資料庫接得起來使用者呼叫得到、格式對
壞掉時馬上知道是哪一行範圍在幾個元件內只知道「這個請求不對」，要再往下查
適合測計價、邊界、演算法查詢、交易、約束路由、驗證、錯誤格式、權限、標頭

既然 E2E 最接近真實，為什麼不全部用 E2E？因為它慢，而且失敗時只告訴你「這個請求不對」。常見的分配建議叫測試金字塔（test pyramid）：單元測試最多、整合測試中等、E2E 最少，像一座底寬頂窄的金字塔。另一種觀點叫測試獎盃（testing trophy），主張整合測試最多，因為它最接近真實使用方式、又不會太慢。兩種說法不衝突，背後的問題是同一個：這個 bug 用哪一層測最便宜、最穩。快樂時光的邊界、四捨五入，用單元測試；用 HTTP 測同樣的東西，結果一樣，只是比較慢。缺欄位要 400、錯誤格式、路由前綴，只能用 E2E。

這門課的判分大多是 E2E 和整合測試，原因也一樣：判分程式不知道你怎麼拆 class，只看 HTTP 出來的結果。

💡 實務上：E2E 先守住「壞了會被客訴」的路徑
接手一個沒什麼測試的專案，通常不是從單元測試補起，而是先替最重要的幾條 API 各寫一兩個 E2E：咖啡店後台就是下單、查商品、管理員權限。它們會在 CI 的每個 PR 跑，前端改版、升級套件時，壞了馬上知道。不要把每個 if 分支都用 E2E 測，CI 會越跑越慢，大家就開始想跳過。資深工程師 review 時常問：「這個 bug 如果再發生，哪一層的測試會先紅？」答不出來，就是少了一個測試。開場的事故答案就是：下單的 E2E。

結論是要寫 E2E。但 E2E 要送 HTTP 請求，聽起來得先把伺服器開起來、佔一個 port，測完再關掉。測試裡有沒有更直接的做法？

不開伺服器，怎麼對整個應用發 HTTP 請求？

平常啟動 API，是 main.ts 呼叫 app.listen(3100)：應用跟作業系統要一個 port（3100），開始在那裡等連線，之後 curl 或瀏覽器才連得進來。測試如果也這樣做會遇到兩個麻煩：port 可能已經被你正在跑的開發伺服器佔走；好幾個測試檔同時跑時，大家搶同一個 port。

supertest 是專門對 Node 的 HTTP server 發請求的測試工具，它解決的就是這件事：你把一個還沒 listen 的 server 物件交給它，它自己在背景開一個臨時的空 port、送出請求、拿回回應，測試完全不用管 port。下面是最小的完整例子，對 GET /products/2 發請求：

import { Test } from '@nestjs/testing'
import type { INestApplication } from '@nestjs/common'
import request from 'supertest'                     // ESM：預設匯入
import { AppModule } from '../src/app.module.js'

describe('GET /products/:id', () => {
  let app: INestApplication

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({ imports: [AppModule] }).compile()
    app = moduleRef.createNestApplication({ logger: false })   // 跟 NestFactory.create 一樣的應用
    await app.init()                                         // 註冊路由、跑生命週期，但不 listen
  })
  afterAll(() => app.close())                               // 一定要關

  it('存在的商品：200，有名稱與價格', async () => {
    const res = await request(app.getHttpServer()).get('/products/2')

    expect(res.status).toBe(200)
    expect(res.headers['content-type']).toMatch(/application\/json/)
    expect(res.body).toMatchObject({ name: '拿鐵', price: 110 })
  })
})

從上往下看，應用是這樣組出來的：

  1. Test.createTestingModule({ imports: [AppModule] })：第 5 課用它組出單一 service；這次直接匯入整個 AppModule，所以所有 controller、service，以及用 APP_* 登記的 guard、pipe、filter 都在裡面。
  2. createNestApplication()：把模組包成一個 Nest 應用，跟 main.ts 裡 NestFactory.create 建出來的是同一種東西。logger: false 讓測試輸出不被啟動訊息洗版。
  3. app.init()：把路由、middleware、全域 pipe／filter 都裝好，跑完第 4 課的啟動生命週期，但不 listen。
  4. app.getHttpServer()：拿到底層的 Node HTTP server，交給 supertest，由它負責連線。

拿到回應之後怎麼斷言也有講究。supertest 有鏈式寫法 .expect(201)，但它失敗時只會說 expected 201 "Created", got 400 "Bad Request"，看不到 body 裡是哪個欄位出錯。上面的寫法是先 await 拿到 res，再用 expect(res.status)、expect(res.body) 分開斷言，失敗時 Vitest 會把實際的值印出來，你一眼就知道後端回了什麼。

忘了 app.close()，應用持有的資源（之後的資料庫連線池、Redis 連線、BullMQ worker）不會釋放，Vitest 跑完測試卻遲遲不結束，或在逾時後印出警告。afterAll／afterEach 裡一定要關，而且要跟建立的次數一樣多。

這個測試會過。但仔細看它打的路徑：/products/2。正式環境的前端打的是 /api/products/2，因為 main.ts 設了全域前綴。測試是綠的，測的卻是一個正式環境不存在的網址。

測試建出來的 app，跟正式環境是同一個嗎？

不是，而這是 E2E 測試最常見的 bug。正式環境由 main.ts 啟動，測試由 Test.createTestingModule 建立，測試不會執行 main.ts。所以寫在 main.ts 裡的設定，測試裡就不存在：

// main.ts
const app = await NestFactory.create(AppModule)
app.setGlobalPrefix('api')        // 測試裡沒有：測試打 /orders 會過，正式環境是 /api/orders
app.enableCors()                  // 測試裡沒有：CORS 設錯也測不出來
await app.listen(process.env.PORT ?? 3100)

後果是「測試全過、正式環境行為不同」。上一節的測試就是例子：打 /products/2 會過，但前端真正會打的 /api/products/2 從來沒被測過；有人把前綴改掉或刪掉，測試也不會紅。

哪些設定會掉進這個坑？第 7、8 課已經把 pipe 和 filter 用 APP_PIPE、APP_FILTER 登記在模組裡，第 6 課的 guard 也一樣，所以只要用 AppModule 建應用，它們就跟著來，開場事故的 APP_PIPE 被刪時，E2E 一定看得到。剩下的是只能設定在 app 物件上的東西：全域前綴、CORS、之後的 API 版本（第 23 課）、enableShutdownHooks（第 24 課）。這些沒有對應的模組寫法，只能呼叫 app.xxx()。

解法是讓兩個入口走同一段程式：把這些設定收進一個函式，main.ts 和測試都呼叫它。

// src/app.setup.ts
import type { INestApplication } from '@nestjs/common'

export function configureApp(app: INestApplication) {
  app.setGlobalPrefix('api')
  app.enableCors({ origin: ['http://localhost:5173'] })
}

// src/main.ts
const app = await NestFactory.create(AppModule)
configureApp(app)
await app.listen(process.env.PORT ?? 3100)

// test/*.e2e-spec.ts
app = moduleRef.createNestApplication({ logger: false })
configureApp(app)          // 在 init 之前
await app.init()

測試裡的 configureApp(app) 要放在 app.init() 之前，因為前綴這類設定要在路由註冊前就定好。這樣之後有人改前綴、改 CORS，只會改到 configureApp 這一個地方，測試和正式環境一起變。下圖是兩個入口現在的關係：

既然有了 configureApp，會不會想把 pipe、filter 也搬進來，改用 app.useGlobalPipes？不要。useGlobal* 收的是你自己 new 出來的實例，Nest 沒有參與建立，所以它不能注入依賴，測試也不能用 overrideProvider 換掉（第 6 課比較過）。configureApp 只放模組管不到的東西。

即使兩邊走同一段設定，還有一種差異是 Vitest 本身造成的：Vitest 執行 TypeScript 時不做型別檢查，也會幫你補上 import 漏寫的 .js 副檔名，而正式環境跑的是 nest build 編譯出來的 JavaScript，兩件事都不會幫你（第 1 課講過為什麼）。所以這一課的練習 1 判分時，還會真的 nest build、再 node dist/main.js 啟動一次，用真的 HTTP 檢查。

configureApp 裡除了前綴，還多了一行 enableCors({ origin: ['http://localhost:5173'] })，原本 main.ts 只寫 enableCors()。為什麼要改成這樣一個清單？測試又要怎麼確認它是對的？

前端在 5173、API 在 3100：CORS 允許清單怎麼寫、怎麼測？

先講清楚 CORS 在解決什麼。瀏覽器用來源（origin）區分網站：通訊協定、主機名稱、port 三者合起來就是一個來源。Vue 前端開在 http://localhost:5173（Vite 的預設），API 在 http://localhost:3100，只差在 port，對瀏覽器來說就是兩個不同的來源。

瀏覽器有一條規則叫同源政策：網頁上的 JavaScript 預設不能讀取別的來源回來的回應。否則你登入網銀後，再打開任何一個網站，那個網站的程式都能用你瀏覽器裡的 cookie 去讀網銀的 API。CORS（Cross-Origin Resource Sharing，跨來源資源共用）是這條規則的例外機制：API 在回應裡帶上 Access-Control-Allow-Origin 標頭，寫明「允許這個來源讀我的回應」，瀏覽器看到自己的來源在裡面，才把回應交給網頁的程式。

還有一個前端常在 DevTools 看到、但不知道是誰送的請求：送 JSON 的 POST 這類請求，瀏覽器在真正送出之前，會先自動發一個 OPTIONS 請求問 API「這個來源可以用 POST 嗎」，這叫預檢請求（preflight）。API 回答可以，瀏覽器才送真正的下單請求。同源政策與 CORS 的完整說明在認證課第 5 課，這裡只講 Nest 的設定與測試。

Nest 的 app.enableCors(options) 把選項交給 Express 的 cors 套件，關鍵是 origin 怎麼寫。原本 main.ts 的 enableCors() 是第一列，下面幾種寫法看「結果」那一欄，想像你的使用者正在瀏覽一個惡意網站，看哪種寫法會讓那個網站讀到你的 API 回應：

寫法結果
enableCors() 或 origin: '*'回 Access-Control-Allow-Origin: *：任何網站的 JavaScript 都能讀你的回應
origin: true把請求的 Origin 原封不動回傳：等於允許所有來源，搭配 credentials: true 更危險，別人的網站能帶著使用者的 cookie 讀資料
origin: /localhost:5173/正規表示式沒錨定：http://localhost:5173.evil.example 也符合
origin: 'http://localhost:5173'（單一字串）不管請求從哪裡來，都回 Access-Control-Allow-Origin: http://localhost:5173。瀏覽器自己比對，別的網站還是讀不到；但伺服器分不出允許與不允許，測試也看不出差別，之後要加正式網域時還是得改成陣列
origin: ['http://localhost:5173']允許清單：完全相同的字串才允許，其他來源的回應沒有這個標頭

所以 configureApp 用最後一種：陣列形式的允許清單，只放自己的前端。這裡要分清楚 CORS 保護的是什麼：它是瀏覽器的保護，不是存取控制。curl、Postman、後端程式不看這個標頭，照樣能呼叫 API。它防的是「使用者瀏覽惡意網站時，那個網站用使用者的瀏覽器讀你的 API」。誰能下單、誰能改價，還是要另外用 guard 檢查。允許的來源在第 11 課會改成從設定讀，正式環境放正式網域。

知道了要什麼行為，測試就寫得出來：帶上 Origin 標頭模擬瀏覽器，檢查回應標頭。允許的來源要有、不允許的要沒有，預檢請求也要通過：

const ok = await request(app.getHttpServer()).get('/api/products/1').set('Origin', 'http://localhost:5173')
expect(ok.headers['access-control-allow-origin']).toBe('http://localhost:5173')

const evil = await request(app.getHttpServer()).get('/api/products/1').set('Origin', 'https://evil.example')
expect(evil.headers['access-control-allow-origin']).toBeUndefined()

// 預檢請求
const pre = await request(app.getHttpServer()).options('/api/orders')
  .set('Origin', 'http://localhost:5173').set('Access-Control-Request-Method', 'POST')
expect(pre.status).toBe(204)

「不允許的來源要沒有標頭」這一條最重要：只測允許的來源，origin: true 和 '*' 也會過。還有一個細節：第二個請求的狀態碼仍然是 200。伺服器照樣處理了這個請求，只是回應沒帶標頭，瀏覽器不會把結果交給那個網站的程式。這表示 CORS 擋不住「會改資料的請求被送出去」，那是 CSRF 的問題，認證課會講。

💡 實務上：CORS 錯誤多半是部署設定，不是程式 bug
常見情境：前端部署到新網域（正式站、staging、每個 PR 的預覽網址），瀏覽器一打 API 就報 CORS 錯誤。這時容易為了趕上線改成 origin: true 或 *，問題「解決」了，保護也沒了。比較好的做法是把每個環境的前端網域明確列進允許清單（第 11 課會改成從設定讀），並在上線清單加一條「新網域有沒有加進 CORS」。另外，CORS 錯誤只會出現在瀏覽器 console，用 curl 或 Postman 打同一支 API 都正常，前後端分屬不同人時要先講好誰負責維護這份清單。有了上面那組測試，有人在 configureApp 裡偷改成 *，CI 會先紅。

到這裡，測試裡的 app 已經跟正式環境一樣：同樣的模組、同樣的前綴、同樣的 CORS。可以開始測本課的主角 POST /api/orders 了。但「一樣」也帶來新麻煩：正式環境的下單會呼叫金流商扣款，測試裡也會。

下單會真的扣款：測試該把哪些東西換成替身？

下單時 OrdersService 檢查完庫存，會呼叫 PaymentGateway 向金流商扣款。E2E 測試如果用真的 PaymentGateway，問題一個接一個：要有網路，CI 的機器不一定連得出去；每跑一次就真的扣一次款；金流商的測試環境偶爾維修或變慢，你的測試就跟著紅；而且你沒辦法叫它「這次請失敗」，金流失敗時該回 502 的那條路徑就永遠測不到。所以金流要換成替身。

那乾脆多換一點，測試不是更快更穩？問題在於替身換越多，測到的越少。替身回傳的是你自己寫的值，換掉 OrdersService，就沒人在檢查庫存；全部換掉，剩下的只是在確認「替身回傳什麼，API 就回什麼」。這一課的原則叫測試邊界：你不能控制的外部系統（金流、寄信、簡訊、第三方 API）換掉；自己的程式（service、pipe、filter）用真的。

資料庫算哪一邊？算自己的：schema 和查詢都是你寫的，查詢寫錯正是要抓的 bug。第 17 課會用 Docker 跑一個真的測試資料庫，而不是把它換成替身。

換的方法跟第 5 課一樣是 overrideProvider，差別只在這次匯入的是整個 AppModule，只換金流這一個 provider：

const payments = { charge: vi.fn() }

beforeEach(async () => {
  payments.charge.mockResolvedValue({ chargeId: 'ch_test_1' })
  const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
    .overrideProvider(PaymentGateway).useValue(payments)    // 只換金流
    .compile()
  // …createNestApplication、configureApp、init
})

it('金流失敗：502 PAYMENT_FAILED', async () => {
  payments.charge.mockRejectedValue(new Error('connect ECONNREFUSED'))
  const res = await request(app.getHttpServer()).post('/api/orders').send(order)
  expect(res.status).toBe(502)
  expect(res.body.errorCode).toBe('PAYMENT_FAILED')
})

每個測試開始前，beforeEach 先讓替身回傳成功；「金流失敗」這個測試再用 mockRejectedValue 改成丟出連線錯誤。這就是替身的另一個用處：製造真實世界很難遇到的狀況，像金流逾時、拒絕交易。這些錯誤路徑用真的外部服務幾乎測不到，卻是上線後最容易出事的地方。

💡 實務上：替身測不到「對方真的長那樣」
替身的回應是你照文件寫的，金流商改了欄位名稱或錯誤格式，E2E 照樣全綠。所以團隊通常還有另一道防線：在 staging 環境接金流商提供的測試（sandbox）帳號，上線前手動或排程跑一次完整的扣款流程。寄信、簡訊也一樣，staging 用測試帳號，正式環境才發給真人。資深工程師接一個新的第三方服務時，會先問：有沒有 sandbox、失敗與逾時時回什麼、會不會重複扣款，再決定替身要模擬哪些情況。

全域 guard 能不能也這樣換掉，見課末「補充與查表」。現在下單的 E2E 能安全地跑了，下一個問題是：拿到回應之後，要檢查哪些東西？

斷言要寫到多細，才抓得到 bug 又不會一直誤報？

回到開場：前端壞掉，是因為它依賴的東西變了。它靠狀態碼判斷成功或失敗，靠 errorCode 決定顯示哪種訊息，靠 details 裡的欄位在畫面上標出哪個商品缺貨。這些前端依賴、改了就會壞的部分，叫做 API 的契約（contract）。E2E 測試要斷言的就是契約，不多也不少。

// 好：前端靠這些判斷
expect(res.status).toBe(409)
expect(res.body.errorCode).toBe('OUT_OF_STOCK')
expect(res.body.details).toMatchObject({ productId: 6, available: 2 })

// 不好：整個 body 做快照
expect(res.body).toMatchSnapshot()

「不多」是指不要把整個 body 都當成規格。快照（snapshot）會在第一次執行時把整個 body 存成檔案，之後每次跑都逐字比對，寫起來最省事。問題有三個，而且一個接一個：body 裡有第 6 課的 requestId，每次都不同，快照每次都壞；就算把它排除，後端加一個新欄位，這對前端完全無害，所有快照還是一起壞；壞多了，大家就習慣直接按「更新快照」，快照變成永遠通過的測試。toMatchObject 只比你列出來的欄位，新增欄位不會讓它失敗。

「不少」是指斷言不能寬鬆到什麼都過。expect(res.status).toBeLessThan(500) 看起來有檢查，但成功時回 200 而不是 201、庫存不足回 400 而不是 409，它都會過；前端卻可能因為這些差異走錯分支。狀態碼本身就是契約的一部分，要寫確切的值。

用這個標準回頭檢查開場的事故：如果下單的 E2E 有一個「缺 items：400、errorCode 是 VALIDATION_FAILED」的測試，APP_PIPE 被刪掉的那個 PR，CI 就會紅。練習 2 的判分就是這樣做的：拿幾個故意改壞的版本跑你的測試，每一個都要被抓到。

測試寫好了，在你的電腦上也全綠。但第 5 課遇過的狀況在這裡會更常見：同一組測試，換個時間、換台機器、換個執行順序，結果就不一樣。

為什麼同一組測試有時過、有時不過？

程式沒改，測試有時過、有時不過，這種測試叫時好時壞的測試（flaky test）。它比沒有測試還糟：團隊很快就學會「紅了就重跑一次」，等到真的 bug 讓測試變紅，也被重跑掉了。開場的目標之一「不管什麼時候、在哪台機器跑，結果都一樣」，就是要消滅它。

flaky 的根源都一樣：測試結果依賴了測試沒有控制的東西。E2E 比單元測試更容易遇到，因為它包含的東西更多：整個應用的狀態、真實時間、網路。下表列出常見的來源，查表用，不用背；先讀表下面兩個在本課專案裡真的會發生的例子。

原因症狀修法
真實時間只在某些時段、某些日子失敗（「半夜 CI 會紅」）注入 CLOCK，測試用 overrideProvider(CLOCK) 固定時間
時區你的電腦過、CI 不過程式用 Intl.DateTimeFormat 指定 timeZone；測試的時間寫成帶 +08:00 的瞬間
共用狀態單獨跑過、一起跑不過；換順序就壞每個測試用 beforeEach 重建 app 或重設資料
亂數偶爾失敗、重跑就好注入亂數來源，測試給固定值
忘了 await斷言在請求完成前就跑完，或錯誤出現在別的測試裡每個 request(...) 和 expect(...).rejects 都 await
真的網路、固定 port網路不穩或 port 被佔用就失敗外部服務換替身；supertest 不需要 port

第一個例子是共用狀態。這一課的專案還沒有資料庫，商品庫存放在 ProductsService 的記憶體裡，起司蛋糕只剩 2 個。如果所有測試共用一個 app（像一開始 GET /products/2 那個例子的 beforeAll），「成功下單」的測試扣掉了庫存，後面「庫存剛好夠」的測試就看到不一樣的數字；單獨跑它會過，整組一起跑就紅，換個順序又好了。這也是前面換掉金流那一節的範例改用 beforeEach 的原因：每個測試建一個新的 app 最乾淨，代價是慢一點。之後有資料庫時，改成每個測試前清空資料表（第 17 課）。

第二個例子是時間，而且時間的 bug 常常兩個混在一起。下面這段判斷優惠券有沒有過期，看起來沒問題：

const today = new Date().toISOString().slice(0, 10)   // '2026-10-31'
return today <= coupon.expiresOn

toISOString() 回傳的是 UTC 的時間。台北是 UTC+8，台北 11/1 00:00 到 07:59 時，UTC 還是 10/31，所以過期的優惠券還能多用八小時。這是程式的時區 bug。測試又用真實時間，所以只有剛好在這八小時內跑，測試才會紅，其他時候都是綠的，這是測試的時間 bug。兩個 bug 疊在一起，就成了「偶爾半夜 CI 會紅」的典型。

修法分兩邊。程式這邊：注入 CLOCK 取得現在時間，再用 new Intl.DateTimeFormat('sv-SE', { timeZone: 'Asia/Taipei' }).format(date) 取台北的 YYYY-MM-DD（TypeScript 課第 6 課）。這裡借用瑞典（sv-SE）的日期格式，是因為它剛好就是 YYYY-MM-DD，字串可以直接比大小。測試這邊：用 overrideProvider(CLOCK) 把時間固定在到期日午夜的兩側，例如台北 10/31 23:59 和 11/1 00:00，不管什麼時候跑，測的都是最容易出錯的那一刻。練習 3 就是做這件事。

💡 實務上：flaky test 要當 bug 處理，不是重跑
團隊裡常見的壞習慣是 CI 紅了就按「重新執行」，綠了就合併。比較健康的做法：發現 flaky 就開一張單、記下失敗的訊息與時間，暫時標記 skip 時要寫原因和負責人，不能就這樣放著。時間、時區相關的 bug 特別值得重視，因為它們在正式環境也會發生，例如跨日的營業報表、到期日的優惠券、月底結帳。測試框架的自動重試（例如 Vitest 的 retry 設定）只能當暫時止血，開了之後 flaky 會被藏起來，更沒人去修。

到這裡，下單的 E2E 測試走完了整個任務：從 HTTP 進出、跟正式環境用同一份設定、只把金流換成替身、斷言前端依賴的契約、每次跑結果都一樣。開場那個被刪掉的 APP_PIPE，現在會在 PR 上就被擋下。

補充與查表

  • 版本：這門課鎖定 supertest 7.3.1（型別是 @types/supertest 7.2.1）、Vitest 5.0.5。
  • 換掉全域 guard：第 6 課用 { provide: APP_GUARD, useExisting: AdminKeyGuard }＋AdminKeyGuard 登記，測試就能 overrideProvider(AdminKeyGuard).useValue({ canActivate: () => true })。不過權限本身就是要測的行為，多數情況應該帶真的金鑰去測 401／403；只在「這個測試跟權限無關」時才換掉。只套在 controller 上的 guard（@UseGuards(X)）用 overrideGuard(X)。
  • 覆蓋率是訊號，不是目標：vitest run --coverage 會列出每個檔案有幾成的程式被執行過。它要另外安裝 @vitest/coverage-v8 套件（這門課的練習沒有裝，只要知道它在做什麼）。覆蓋率 0% 的檔案代表完全沒測，值得看一下；但第 5 課說過，被執行不等於被驗證。把「覆蓋率 90%」當成目標，得到的是一堆沒有斷言的測試。

練習

在 learn/ 執行 node check.mjs nestjs 10 建立 work/10/。起始專案接續第 8 課：POST /orders、GET /products/:id、GET /coupons/:code，pipe 和 filter 已經用 APP_PIPE、APP_FILTER 登記在 AppModule。新加的是 PaymentGateway（src/payments/payment.gateway.ts，會呼叫外部的金流 API）：OrdersService 檢查庫存後扣款，金流失敗時丟 PaymentFailedError，filter 把它轉成 502。src/clock.ts 有 CLOCK token，已經登記在 AppModule。起司蛋糕（id 6）只剩 2 個。

自己的測試在 work/10 執行 npm test（會跑 test/*.e2e-spec.ts）。三題依序做：練習 2、3 的測試會用到練習 1 的 configureApp。

練習 1：main.ts 裡的 setGlobalPrefix('api') 和 enableCors() 搬到 src/app.setup.ts 的 configureApp(app)，CORS 改成只允許 http://localhost:5173。main.ts 改成呼叫 configureApp(app)，不要在那裡另外設定 CORS 或前綴。

測試會用 configureApp 建應用，檢查 /api/orders 有效、/orders 是 404、驗證錯誤仍是 400 VALIDATION_FAILED；帶 Origin 標頭檢查前端的來源（含預檢請求）有 Access-Control-Allow-Origin，https://evil.example、http://localhost:5173.evil.example、http://localhost:3000 都沒有（所以 origin 要寫成陣列，不是單一字串）。最後會 nest build、啟動 node dist/main.js，用真的 HTTP 再檢查一次。

練習 2：在 test/orders.e2e-spec.ts 寫 POST /api/orders 的 E2E 測試。用 Test.createTestingModule({ imports: [AppModule] }) 建應用、呼叫 configureApp，只用 overrideProvider(PaymentGateway) 換掉金流。至少要測：成功 201（總額、扣款金額）、缺 items 是 400 VALIDATION_FAILED、庫存不足是 409 OUT_OF_STOCK、金流失敗（替身 reject）是 502 PAYMENT_FAILED。

這題只寫測試，不改 src/。判分會拿你的測試跑幾個改壞的版本：成功時回 200、庫存不足變成 400、金流失敗變成 500、errorCode 改名、沒有全域前綴、沒有全域 ValidationPipe，每個都要讓你的測試失敗。用真的金流（判分時一呼叫就算錯，金流失敗也要用替身製造）、連自己的 OrdersService 也換成替身、it.skip、沒有 expect 的測試都不算。

練習 3：test/coupons.e2e-spec.ts 是 11 月 1 日下午寫的，當時全過；換個時間跑就不一定。先修 CouponsService：用 @Inject(CLOCK) 注入時鐘，以台北的日期判斷 valid（expiresOn 是最後可以用的那一天，'2026-10-31' 用到台北 10/31 23:59:59）。不要在程式裡改 process.env.TZ。

再改寫測試：用 overrideProvider(CLOCK) 把時間固定成帶 +08:00 的瞬間，測 HALLOWEEN 到期日的兩側。判分會在伺服器時區設成洛杉磯時檢查你的 CouponsService，並用 TZ=UTC、Asia/Taipei、America/Los_Angeles 跑你的測試，再拿四個改壞的 CouponsService（用 UTC 日期、用伺服器時區的日期、到期當天就不能用、不看 CLOCK）確認你的測試抓得到。

練習 4：E2E 測試全部通過，前端上線後卻收到 CORS 錯誤：瀏覽器說回應沒有 Access-Control-Allow-Origin。測試裡有檢查這個標頭，而且是綠的。最可能的原因？

✓ 測試不執行 main.ts。測試和正式環境各寫一份設定，就會各自演化。把設定收進 configureApp，兩邊呼叫同一個函式。supertest 拿到的是真的回應標頭（a 錯）。CORS 跟 HTTPS 無關，http://localhost:5173 一樣適用（c 錯）。

練習 5：POST /api/orders 會用到 ProductsService、資料庫（之後的 Prisma）和金流 API。E2E 測試裡哪個該換成替身？

✓ 測試邊界是「你不能控制的外部系統」。全部換掉（a）就只剩 controller 在跑，pipe、filter 之外的東西都是你自己設定的回傳值，測不到真的 bug。ProductsService 和資料庫是你自己的程式（b 錯）：狀態的問題用 beforeEach 重建或清空資料解決，第 17 課會跑真的測試資料庫。

練習 6：同事建議「錯誤回應的測試都改成 expect(res.body).toMatchSnapshot()，省得一個一個欄位寫」。主要問題是？

✓ 快照把「整個 body 現在長怎樣」當成規格，但契約只是其中幾個欄位：狀態碼、errorCode、前端會讀的 details。用 toMatchObject 斷言這些，新增欄位不會壞。Vitest 5 仍支援快照（b 錯），它適合輸出穩定、整體都重要的東西，例如產生出來的 OpenAPI 文件。速度不是主要問題（c 錯）。

常見錯誤

  • 測試和 main.ts 的全域設定不一致：測試不執行 main.ts。pipe、filter、guard 用 APP_* 登記在模組；前綴、CORS 放進 configureApp，兩邊都呼叫。
  • 把自己的 service 也換成替身：測到的是自己設定的回傳值。只換外部的金流、寄信、第三方 API。
  • CORS 用 '*'、origin: true 或沒錨定的正規表示式：任何網站都能用使用者的瀏覽器讀你的回應。寫完整來源字串的允許清單，並測一個不允許的來源。
  • 寬鬆的斷言：toBeLessThan(500)、只看 ok。狀態碼和 errorCode 寫確切的值。
  • 整個 body 做快照：新增欄位就壞、requestId 每次不同。用 toMatchObject 斷言契約欄位。
  • 測試依賴真實時間或時區：只在某些時段、某些機器失敗。注入 CLOCK，時間寫成帶 +08:00 的瞬間；判斷日期用 Intl.DateTimeFormat 指定 timeZone，不要用 toISOString().slice(0, 10) 或 getDate()。
  • 測試共用同一個 app 而且會改到狀態：換順序就壞。beforeEach 建新的 app，或每個測試前重設資料。
  • 忘了 app.close()：Vitest 結束不了，之後連線池也會用光。在 afterAll／afterEach 關掉。

小結

  • 每一種測試只看得到自己範圍裡的 bug：單元測試測邏輯、整合測試測跟資料庫的接合、E2E 測試測 HTTP 的契約。缺欄位要 400、錯誤格式、路由前綴這些由全域元件組合出來的行為，只有 E2E 抓得到；每個 bug 挑最便宜又最穩的那一層測。
  • Test.createTestingModule({ imports: [AppModule] }) → createNestApplication() → app.init()，supertest 對還沒 listen 的 app.getHttpServer() 發請求，不用管 port；最後 app.close()。
  • 測試不執行 main.ts：模組管得到的用 APP_*，只能設在 app 上的前綴、CORS 收進 configureApp(app)，兩個入口都呼叫。
  • CORS 是瀏覽器的保護，不是存取控制。用允許清單 origin: ['http://localhost:5173']；測試帶 Origin 標頭，允許的有、不允許的沒有。
  • 只把外部、不可控的依賴換成替身（overrideProvider），自己的 service、pipe、filter 和資料庫用真的；替身也用來製造金流失敗這類難遇到的錯誤路徑。
  • 斷言契約（狀態碼、errorCode、前端會讀的欄位），不做整個 body 的快照，也不寫寬鬆的斷言。
  • flaky 的根源是測試依賴了沒控制的東西：時間、時區、共用狀態、亂數、忘了 await、真的網路；每一種都有固定的修法，發現了要當 bug 處理，不是重跑。
