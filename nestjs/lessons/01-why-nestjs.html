階段 1：從 Node 到 NestJS（框架的骨架） · 第 1 課

為什麼要框架：第一個 NestJS 專案

在 Node 課你用 node:http 從零寫過咖啡店 API。現在店裡決定把它搬到 NestJS，同事先用 Nest 建好一個新專案交給你，留了一句話：「npm test 全過，可是 npm run build 失敗，上不了線。順便把菜單 API 搬進來。」

這一課就是你接手這個專案的第一天：先弄懂團隊為什麼要換框架、換了要付什麼代價，再逐檔讀懂專案、跟著一個請求走一遍，找出「測試會過、build 會壞」的原因並修好，最後用 Nest 的產生器把菜單 API 正式搬進來。

這課的路線：
  1. 路由一多，手寫 node:http 卡在哪？NestJS 替你接手了哪些重複的工作；換框架要付什麼代價、什麼情況不該換。
  2. 同事建好的專案裡每個檔案管什麼？一個 GET /menu 從 curl 到收到 JSON 經過誰。
  3. 為什麼 npm test 會過、npm run build 卻失敗？.ts 變成能執行的程式有哪幾條路，tsconfig 哪幾行決定了規則。
  4. 怎麼在練習專案裡動手，並用 nest g 把菜單 API 搬進自己的 service。
這課會用到：
  • Node 課第 13 課用 node:http 寫伺服器：自己比對 req.method 和網址、自己 res.writeHead 和 JSON.stringify。這課拿它跟 Nest 對照。
  • TypeScript 課第 23 課的 parameter properties：constructor(private readonly x: X) 一行同時宣告屬性並把參數存進去。
  • TypeScript 課第 24 課的裝飾器與迷你 DI：@Something() 替 class 加上 metadata，容器讀它決定要 new 什麼、傳什麼進建構子。

路由一多，手寫 node:http 卡在哪？

要回答團隊為什麼要換框架，先回頭看舊的 API 長什麼樣子。下面用 Node 課手寫 node:http 的寫法，寫出等一下要搬家的那支「GET /menu 回傳菜單」（簡化過，全課都用這個例子對照）：

// node:http：路由、回應格式、錯誤處理全部自己來
const server = createServer(async (req, res) => {
  try {
    const url = new URL(req.url ?? '/', 'http://localhost')
    if (req.method === 'GET' && url.pathname === '/menu') {
      res.writeHead(200, { 'content-type': 'application/json; charset=utf-8' })
      res.end(JSON.stringify(await listMenu()))
      return
    }
    res.writeHead(404, { 'content-type': 'application/json; charset=utf-8' })
    res.end(JSON.stringify({ error: 'not_found' }))
  } catch (err) {
    console.error(err)
    res.writeHead(500, { 'content-type': 'application/json; charset=utf-8' })
    res.end(JSON.stringify({ error: 'internal' }))
  }
})

真正跟菜單有關的只有 listMenu() 那一個呼叫，其餘十幾行都在處理 HTTP：解析網址、比對方法和路徑、寫狀態碼和標頭、把結果轉成 JSON 字串、沒對到路由時回 404、程式出錯時回 500。這些工作每個路由都要做一次。咖啡店的 API 會長到幾十個路由（商品、訂單、會員、付款），這段樣板就會被複製幾十次，而且每個人複製時都會改一點：有人忘了 charset，有人錯誤格式寫 { message } 而不是 { error }，有人漏了 try/catch，程式一出錯就沒有回 500。前端收到的 API 行為因此每支都不一樣。

同一個功能用 NestJS 寫是這樣：

// NestJS：只寫「這個網址做什麼」
@Controller('menu')
export class MenuController {
  constructor(private readonly menu: MenuService) {}

  @Get()
  findAll() {
    return this.menu.findAll()   // 回傳值自動變成 JSON，丟出的錯誤自動變成 500
  }
}

這段程式沒有比對網址、沒有 JSON.stringify、沒有 try/catch。@Controller('menu') 和 @Get() 兩個裝飾器宣告「GET /menu 由這個方法處理」，剩下的事由 NestJS 統一做：建立路由表、把回傳值轉成 JSON 回應、沒對到路由時回 404、方法裡丟出沒接住的錯誤時回 500。因為是同一份程式在做，幾十個路由的行為自然一致。

還有一件事被拿走了：建立物件。手寫版本裡，listMenu 需要的東西要你自己 new 好、自己傳進去；Nest 版本的建構子只寫了「我需要一個 MenuService」，Nest 會建好那個物件傳進來。這就是 TypeScript 課第 24 課做過的依賴注入，第 3 課會詳講。

這種「流程由別人掌控、你只寫特定步驟」的程式，就叫框架（framework）。對照的是函式庫（library）：函式庫是你的程式在需要時去呼叫它，流程還是你寫的；框架則反過來，它負責接請求、決定該做什麼，在對的時機呼叫你寫的方法。你寫的 findAll() 從頭到尾沒有被你自己呼叫過。這種「不是你呼叫它，而是它呼叫你」的關係叫控制反轉（Inversion of Control）。看懂這一點，之後讀 Nest 程式就會習慣去問「這個方法是框架在什麼時候呼叫的」，而不是在專案裡找誰呼叫了它。

NestJS 本身不處理 HTTP 連線的細節，例如讀取 socket、解析請求標頭。它把這些交給另一個更底層的 HTTP 框架，預設是 Express，Node 生態裡最常用的 HTTP 框架；自己則專心在上面那一層：用 class 和裝飾器組織程式、管理物件、統一回應和錯誤。也就是說，一個請求進來會先經過 Express，再交給 Nest，下一節的流程圖會看到這一段。底層可以替換成別的 HTTP 框架，細節見課末「補充與查表」。

所以開場第一個問題的答案是：路由一多，手寫版本的問題不是寫不出來，而是重複的 HTTP 樣板占掉大半程式、每個人寫得不一樣。NestJS 把路由、JSON 回應、錯誤處理和物件的建立統一接手，你只寫「這個網址要做什麼」。但把流程交給別人，是有代價的。

換框架要付什麼代價？什麼時候不該換？

上一節看到的都是好處；團隊決定換框架之前，要把代價一起放上桌面。資深工程師選框架時看的是整張表，不是只看「程式寫比較少」：

得到付出
路由、參數解析、回應格式都有固定寫法一定要先編譯：裝飾器 Node 不能直接執行（後面會看到）
驗證、統一的錯誤格式、log 都有現成的位置可以放（第 6–9 課）「魔法感」：誰呼叫了你的方法、物件從哪來，不看文件不知道
依賴注入：測試時可以把資料庫換成假的（第 3、5 課）要學它的慣例：module、provider、各種裝飾器
全隊同一種結構，新人看得懂別人的程式出錯時多一層要查：錯誤訊息常來自框架內部

右欄的每一項都是控制反轉的另一面。流程不在你手上，所以你看不到是誰呼叫了 findAll()，要靠文件和慣例才知道（魔法感）；出錯時錯誤堆疊裡大半是框架內部的函式，要學會從裡面找出自己的那一行（除錯多一層）。第一項「一定要先編譯」則會直接影響你今天的任務，同事遇到的 build 失敗就跟它有關，後面專門用一節講。

這些代價在專案小的時候不划算。一次性的小腳本、只有一兩個端點的小服務（例如只收一個 webhook）、對啟動時間和依賴數量非常敏感的工具，用 node:http 或 Express 就夠了：重複的樣板只有一兩份，不值得為它學一整套慣例。咖啡店 API 不一樣，它會長到幾十個端點、好幾個人一起維護，這時「全隊同一種結構」帶來的好處每天都在累積，框架的固定結構就值回票價。

💡 實務上：選框架是團隊決策，不是個人喜好
新專案開工時，選 Express 還是 NestJS 通常會在技術會議上討論。資深工程師會先問：會有幾個人維護、預計活多久、團隊有沒有人熟 Nest、公司其他服務用什麼。三個月後就下線的活動頁後端，用 Express 很合理；要跟著公司好幾年的訂單系統，固定結構的價值會越來越高。反過來，已經穩定運作的 Express 服務，很少只為了「Nest 比較整齊」就整個重寫，通常是新服務才採用。咖啡店這次也是一樣：舊 API 先留著，新功能從這個 Nest 專案開始。

決定換了，下一步就是打開同事建好的專案，看看裡面每個檔案在做什麼。

同事建好的專案裡，每個檔案管什麼？

同事是用 Nest CLI 建立專案的。Nest CLI 是 NestJS 官方的指令工具，負責建立專案（nest new）、產生檔案（nest generate）、編譯（nest build）和啟動（nest start）。建立專案的指令是：

npx @nestjs/cli@12.0.11 new coffee-api --no-observe

npx 會下載並執行指定版本的套件（Node 課第 3 課）。執行時它會問幾個問題，這門課選 npm 和 ESM；每個選項的意思和 --no-observe 是什麼，見課末「補充與查表」。

你不用自己執行這個指令。這門課的練習已經準備好專案（後面會說明怎麼取得），work/01/ 就是你要接手的那個專案，內容跟 nest new 產生的幾乎一樣：

work/01/
  package.json          ← "type": "module" 和 scripts（沒有 dependencies，套件共用上層的）
  tsconfig.json         ← TypeScript 設定
  tsconfig.build.json   ← nest build 用：排除測試檔
  nest-cli.json         ← Nest CLI 設定：原始碼在 src/、build 前先清空 dist/
  vitest.config.ts      ← 你自己的測試（npm test）
  src/
    main.ts             ← 進入點
    app.module.ts       ← 根模組
    app.controller.ts   ← 處理請求
    app.service.ts      ← 商業邏輯
    app.controller.spec.ts ← AppController 的測試

上半部是設定檔，後面講 build 時會用到；先看 src/ 裡的四個程式檔，它們合起來就是一個能回應請求的應用程式。

程式從 main.ts 開始執行。它裡面建立並啟動應用程式的那段程式，慣例上叫 bootstrap（啟動程序）：

import { NestFactory } from '@nestjs/core'
import { AppModule } from './app.module.js'

async function bootstrap() {
  const app = await NestFactory.create(AppModule)   // 讀 AppModule，建好所有物件、登記所有路由
  await app.listen(process.env.PORT ?? 3100)        // 開始聽 port；練習用 3100
}
await bootstrap()                                   // ESM 可以在最上層 await

注意 NestFactory.create 只拿到一樣東西：AppModule。Nest 不會掃描整個資料夾找 controller，它只從這個 module 出發，看裡面登記了什麼，就建立什麼。所以下面三個檔案的關係是這樣：

  • AppModule：@Module({ controllers, providers }) 告訴 Nest 這個應用有哪些 controller、哪些可以注入的物件。Nest 只認得登記在 module 裡的東西，寫了 controller 卻沒登記，它的路由就不存在。第 4 課詳講。
  • AppController：@Controller() 標記它處理請求，@Get() 把方法綁到 GET /。路徑是這樣組出來的：@Controller('x') 的字串是前綴，@Get('y') 的字串接在後面，合起來就是 /x/y；兩邊都沒寫字串，就是 /。所以 @Controller() 底下的 @Get('menu') 是 GET /menu，@Controller('menu') 底下的 @Get() 也是 GET /menu。第 2 課詳講。
  • AppService：@Injectable() 標記它可以被注入。AppController 的建構子寫了 private readonly appService: AppService，Nest 建立 controller 時就會把 AppService 的物件傳進去。

為什麼要分 controller 和 service 兩層，而不是把邏輯直接寫在 controller？controller 只負責 HTTP 這一側的事：哪個網址、從請求拿什麼、回什麼狀態碼。真正的商業邏輯，例如「菜單有哪些品項」「訂單總額怎麼算」，放在 service。這樣同一段邏輯可以被別的 controller、排程工作或測試重複使用，測 controller 時也能把 service 換成假的。今天要搬的菜單 API 就會照這個分法：菜單資料放 MenuService，MenuController 只負責回應 GET /menu。

💡 實務上：接手陌生的 Nest 專案，先看 main.ts 和 AppModule
到新公司拿到一個幾百個檔案的 Nest 專案，不用從頭讀起。先開 main.ts：整個應用共用的設定（例如所有 API 都加上 /api 前綴、統一驗證輸入、log）通常都在 bootstrap 裡。再看 AppModule 的 imports，它就是這個系統的功能地圖，例如訂單、會員、付款各一個 module。要追某個 API，就從網址找到對應的 controller，再跟著它注入的 service 往下讀。今天這個專案還很小，但用同樣的順序讀，之後專案長大也不會迷路。

知道每個檔案的角色之後，接著把它們串起來：一個請求打進來，會依序經過誰？

一個 GET /menu 從 curl 到 JSON 經過誰？

以等一下要搬進來的 GET /menu 為例。main.ts 啟動時，Nest 已經從 AppModule 找到所有 controller，讀了它們身上的 @Controller()、@Get()，建好一張「哪個方法和路徑對到哪個方法」的路由表。請求進來之後的路線是：

由左到右：Express 先收下 HTTP 請求；Nest 拿方法和路徑去查路由表，找到 findAll() 並呼叫它（這就是上一節說的控制反轉）；findAll() 回傳一個陣列；Nest 再把回傳值變成 HTTP 回應送回去。對照第一節的手寫版本，你原本自己寫的 if 比對、writeHead、JSON.stringify，分別落在圖上的路由表和最下面那一格。

最下面那一格怎麼把回傳值變成回應，決定了你的方法應該回傳什麼。規則是：陣列和物件會被轉成 JSON，Content-Type 是 application/json；字串原封不動送出，Content-Type 是 text/html。所以從 Node 課帶過來的習慣「回應前先 JSON.stringify」在這裡反而是錯的：你回傳的變成一個字串，前端收到的是一段 HTML 型別的文字，不是 JSON。直接回傳物件或陣列，讓 Nest 轉。

到這裡，這個專案「應該」怎麼運作已經清楚了。但同事說它根本 build 不起來，請求連 Express 都到不了。問題出在 .ts 變成能執行的程式那一段。

為什麼 npm test 會過，npm run build 卻失敗？

要回答這個問題，先釐清一件事：Node 只會執行 JavaScript。Node 24 雖然能直接執行 .ts，但它做的只是把型別註記擦掉，不會改寫程式（Node 課第 5 課）。所以 Nest 專案的 .ts 要先經過某個工具處理才能執行，而這門課裡不同的指令用的是不同的工具。

這些工具做的事分兩種，名稱先講清楚。編譯在這裡指用 tsc（TypeScript 官方的編譯器）處理：它會先檢查整個專案的型別，有錯就停下來，沒錯才把 TS 轉成 JS 寫成檔案。Nest 專案把這些編譯結果寫進專案根目錄的 dist/ 資料夾，src/app.service.ts 會變成 dist/app.service.js；之後真正被 Node 執行的，是 dist/ 裡的 .js，不是 src/ 裡的 .ts。轉譯（transpile）只做後半段：把每個檔案的 TS 語法轉成 JS，不檢查型別，所以很快，但型別寫錯它也照樣轉。同一份 .ts 在這門課會碰到四個指令，其實是三條路：

指令做了什麼檢查型別？
npm run build（nest build）用 tsc 把 src/ 編譯成 JavaScript 放進 dist/會，有錯就失敗
npm run start:dev（nest start --watch）先做跟 build 一樣的編譯，再執行 node dist/main.js；存檔就重來一次會
npm test（Vitest）Vite 8 內建的 Oxc 在記憶體裡即時轉譯，直接跑測試不會
node src/main.tsNode 擦掉型別後執行不會，而且跑不起來

同事的狀況就藏在這張表裡：npm test 走的是轉譯，npm run build 走的是編譯，兩者是不同的工具、不同的規則。Vitest 只轉譯、不檢查型別，而且 import 少了 .js 它也會自己找到 .ts；tsc 則會檢查型別，並要求 import 照 Node 的規則寫。所以 npm test 全過的程式，npm run build 照樣可能失敗。同事的專案裡正好有一個相對 import 少了 .js，就是這種情況，練習 1 會讓你親手找出來。

測試過了，不代表能 build。改完程式至少跑一次 npm run build。這門課的判分會先跑型別檢查，有些練習還會真的 build 再啟動一次。

那為什麼不乾脆跳過編譯，用表格最後一列的 node src/main.ts 直接執行？在這門課的專案實際試（Node 24.22.1）：

$ node src/main.ts
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '…/src/app.module.js'

$ node src/app.service.ts
@Injectable()
^
SyntaxError: Invalid or unexpected token

第一個錯是因為 main.ts 裡寫的是 import … from './app.module.js'，而 src/ 裡只有 app.module.ts，沒有 .js。就算繞過它（第二個指令直接執行 service），Node 的「擦掉型別」只會刪掉型別註記，不會改寫程式：裝飾器（@Injectable()）和 parameter properties（private readonly appService）都不是單純的型別，它們需要編譯器改寫成一般的 JavaScript，擦不掉，所以是語法錯誤。這就是上一節代價表裡「一定要先編譯」的意思，Nest 專案沒有不編譯就能跑的捷徑。

💡 實務上：正式環境跑的是 dist/，不是 start:dev
團隊通常會設定 CI：每次有人推程式碼，就由伺服器自動跑一輪檢查。檢查裡通常有一項叫 lint：用工具掃過原始碼，找出不符合團隊規則的寫法，例如沒用到的變數、容易出錯的語法、風格不一致的地方，它不執行程式，也不做 tsc 那種完整的型別檢查。CI 通常同時跑 lint、測試和 npm run build，build 不過就不能合併。這正好擋下同事遇到的「本機測試全過、部署才壞掉」。部署時是先 build，再用 node dist/main.js 啟動；之後用 Docker 打包（第 12 課起）也一樣，正式環境不應該跑 start:dev，它會監看檔案、每次重新編譯，只適合開發。上線出問題時，第一個要確認的就是：部署的 dist/ 是不是從這次的程式碼 build 出來的。

build 失敗的原因找到了：tsc 要求 import 寫 .js。但「要求寫 .js」「看得懂裝飾器」這些規則是誰定的？答案在 tsconfig.json。

tsconfig 哪幾行決定了這些規則？

tsconfig.json 是 tsc 的設定檔，nest build 和編輯器的型別檢查都讀它。練習專案的 tsconfig.json 繼承 practice/tsconfig.json，內容跟 nest new 產生的幾乎一樣（差在哪見課末）。前三列跟今天的任務直接相關，後兩列先知道有這回事就好：

設定為什麼
"module": "nodenext"、"moduleResolution": "nodenext"照 Node 真正的規則檢查 import。ESM 的相對 import 一定要寫副檔名，而且寫的是編譯後的 .js：import { AppService } from './app.service.js'（Node 課第 4 課、TypeScript 課第 25 課）
"experimentalDecorators": true使用舊版（TypeScript 實驗版）的裝飾器語法，Nest 用的是這一種
"emitDecoratorMetadata": true編譯時把建構子參數的型別記下來（design:paramtypes），Nest 靠它知道要注入什麼
"strictPropertyInitialization": false之後的課會出現一種只用來裝請求資料的 class（DTO，第 7 課），它的欄位由框架填值，不是在建構子裡設定；關掉這項檢查，TypeScript 才不會在每個欄位報「沒有初始化」
"types": ["vitest/globals", "node"]TypeScript 6 起 types 預設是空陣列，要明寫才看得到 Node 和 Vitest 的全域型別

第一列直接解釋了同事的 build 失敗。為什麼檔案明明是 app.service.ts，import 卻要寫 .js？因為 import 那個字串會原樣留在編譯結果裡：tsc 把 src/app.controller.ts 編譯成 dist/app.controller.js 時，不會幫你改寫 import 的路徑。真正執行的是 dist/ 裡的 .js，而 Node 的 ESM 只照字面找檔案，不會自己補副檔名。所以原始碼要直接寫出執行時那個檔案的名字 ./app.service.js。nodenext 讓 tsc 在編譯時就照這個規則檢查，少了 .js 就報錯，而不是等到 node dist/main.js 啟動時才找不到檔案。

第二、三列則是 Nest 能運作的前提：第一節看到的 @Controller()、@Injectable() 要靠 experimentalDecorators 才能編譯；Nest 之所以知道 AppController 的建構子要一個 AppService，是因為 emitDecoratorMetadata 讓編譯結果留下了參數型別。這份參數型別是 tsc 編譯時寫進輸出的，換成只轉譯的工具，就要看那個工具有沒有實作這一項。你可能會問：上一節說 Vitest 也只轉譯，為什麼練習 3 的測試裡注入正常？因為 Vite 8 內建的 Oxc 會讀 tsconfig 的 emitDecoratorMetadata，產生 design:paramtypes（Vite 文件寫的是「部分支援」：需要 tsc 型別推論的情況做不到，但建構子參數直接寫 class 型別，例如 private readonly menuService: MenuService，這種 Nest 最常見的寫法沒有問題）。tsx 用的 esbuild 則完全不支援這一項，所以如果改用 tsx 跑 Nest，產生的程式裡沒有參數型別，Nest 不知道建構子要什麼，注入的物件就會是 undefined。後兩列跟今天無關：strictPropertyInitialization 第 7 課用到 DTO 時就會看到它的作用，types 則是讓 describe、process 這些全域名稱在編輯器裡有型別。

規則清楚了，可以動手修同事的專案、把菜單 API 搬進來。先看練習資料夾怎麼運作。

怎麼在練習專案裡動手，並用 nest g 加上菜單 service？

每一課的練習是 learn/nestjs/practice/work/ 裡的一個小專案，所有課共用 practice/ 裡的同一份 node_modules：

learn/
  check.mjs                     ← 判分：在 learn/ 執行 node check.mjs nestjs 01
  nestjs/practice/
    package.json  node_modules/ ← 全部課程的套件，版本鎖死
    start/01/                   ← 起始檔（不要改）
    work/01/                    ← 你的專案：第一次判分時從 start/01 複製過來
      ex1.test.ts …             ← 判分用的測試，每次判分都換成最新的
    results/01.json             ← 判分結果，課程頁讀這個檔

第一次做練習：

  1. 在 learn/nestjs/practice 執行 npm ci，照 package-lock.json 安裝套件（約 500 MB，Node 課第 3 課講過 npm ci）。
  2. 在 learn/ 執行 node check.mjs nestjs 01，它會建立 work/01/。這時候會看到型別錯誤，就是同事留下的那個 build 失敗，正是練習 1 要修的。
  3. 之後的指令都在 work/01/ 裡執行：
指令（在 work/01/）用途
npm run start:dev編譯並啟動在 http://localhost:3100，存檔自動重來；Ctrl+C 停止
curl -i http://localhost:3100/另開一個終端機送請求（Node 課第 12 課），-i 會印出狀態碼和標頭
npm run build只編譯到 dist/，有型別錯誤會失敗
npm test跑你自己的 *.spec.ts
npx nest g service menu --flat用產生器建立檔案（下面說明）
不要在 work/01/ 裡執行 npm install：會多出第二份 node_modules，版本可能跟課程鎖定的不同。npx nest 會自己往上層找到 practice/node_modules。

修好 build 之後，任務的後半是把菜單 API 搬進來。照前面講的分層，菜單資料要放進一個 MenuService，由 MenuController 回應 GET /menu。這兩個檔案可以手寫，但每次都要記得加裝飾器、寫測試檔的骨架、再回 AppModule 登記，漏了登記路由就不存在。Nest CLI 的 nest g（nest generate）把這些步驟自動化：它用產生器（schematics）建立 controller、service 這類檔案。產生器就是一組產生檔案的範本，會建好檔案和對應的測試檔，還會自動登記到 AppModule。--flat 表示直接放在 src/，不另外開資料夾：

$ npx nest g service menu --flat
CREATE src/menu.service.spec.ts (449 bytes)
CREATE src/menu.service.ts (88 bytes)
UPDATE src/app.module.ts (314 bytes)

最後一行 UPDATE src/app.module.ts 就是它幫你登記的那一步。它寫進 app.module.ts 的 import 有沒有 .js，又會碰到上一節的規則。產生器怎麼知道要不要加 .js？它只讀目前資料夾的 package.json，有 "type": "module" 就加。這就是每個 work/ 專案都有一個沒有 dependencies 的 package.json 的原因。實際試過：在 work/01/src/ 裡執行同一個指令，那裡沒有 package.json，app.module.ts 就多了一行 import { MenuService } from './menu.service'，build 會失敗，等於親手重現同事的問題。所以 nest g 一律在專案根目錄 work/01 執行。

到這裡，接手專案需要的東西都齊了：修 import 讓 build 通過、在 controller 加路由、用 nest g 建 service 並注入。下面的練習就照這個順序完成今天的任務。

練習

練習 1：起始專案有一個相對 import 少了 .js。先在 work/01 執行 npm test（會過）和 npm run build（會失敗），看看兩者的差別。找出那一行修好，讓 npm run build 成功、npm run start:dev 啟動後 curl http://localhost:3100/ 回 Hello World!。字串要繼續由 AppService 提供：把 import 刪掉、在 controller 直接回傳字串不算修好。

測試會真的執行 nest build，再用 node dist/main.js 啟動。所以用 // @ts-ignore 蓋掉錯誤、或把 tsconfig 改成 bundler 都過不了：型別檢查不報錯了，但編譯出來的 import 還是沒有 .js，Node 啟動時找不到檔案。測試也會把 AppService 換成假的，確認 GET / 回的是注入進來的 AppService 給的字串。

練習 2：在 AppController 加兩個路由：GET /menu 回傳陣列 [{ name: '美式咖啡', price: 80 }, { name: '拿鐵', price: 110 }, { name: '卡布奇諾', price: 110 }]；GET /health 回傳 { status: 'ok' }。路由的路徑寫在 @Get('menu') 的參數裡。先用 npm run start:dev 啟動，curl -i http://localhost:3100/menu 自己確認狀態碼是 200、Content-Type 是 application/json，再判分。

練習 3：在 work/01 執行 npx nest g service menu --flat 和 npx nest g controller menu --flat。把菜單資料搬進 MenuService 的 findAll() 方法；MenuController（產生器已經寫好 @Controller('menu')）用建構子注入 MenuService，在 @Get() 方法裡回傳 findAll() 的結果；最後刪掉 AppController 裡的 /menu。除了下面列的檔案，你還會改到產生器建立的 src/menu.service.ts 和 src/menu.controller.ts；app.module.ts 由產生器自動登記，通常不用自己改。

測試會把 MenuService 換成假的，確認 /menu 真的是從注入的物件拿資料，所以 new MenuService() 或把資料留在 controller 都過不了。改完後 npm test 會出現 Nest can't resolve dependencies of the MenuController (?)：產生器寫的 menu.controller.spec.ts 只登記了 controller，在它的 providers 加上 MenuService 就好（這個檔不判分，但要能通過型別檢查）。

練習 4：Node 24 可以直接執行 .ts，為什麼 node src/main.ts 跑不起 NestJS 專案？

✓ Node 的 type stripping 只刪掉型別，不改寫程式、也不做型別檢查（所以 a 錯）。@Injectable() 和 constructor(private readonly x: X) 需要編譯器改寫成一般的 JavaScript，Node 遇到它們直接是 SyntaxError，不是慢不慢的問題（c 錯）。何況 import 寫的是 .js，src/ 裡根本沒有那些檔案。

練習 5：npm run start:dev（nest start --watch）實際做了什麼？

✓ nest start 就是 nest build 加上 node dist/main.js，型別錯誤會讓它啟動不了。它不是直接執行 TypeScript（a 錯，上一題說明了為什麼不行），也不是 Vite：只有 Vitest 用 Oxc 轉譯（b 錯）。

練習 6：同事說「npm test 全部通過，可以上線了」，結果部署時 npm run build 失敗。最可能的原因是？

✓ 測試和 build 用的是兩套不同的工具，Vitest 能跑不代表 tsc 能編譯。Node 版本確實可能出問題，但 build 失敗通常是型別錯誤或 import 少了 .js，不是版本（b 不是最可能）。測試檔本來就被 tsconfig.build.json 排除在 build 之外，這是設計好的，不會造成失敗（c 錯）。所以 CI 要同時跑測試和 build。

常見錯誤

  • 相對 import 忘了寫 .js：測試會過、build 會失敗，錯誤是 TS2307: Cannot find module './app.service'。寫成 './app.service.js'，即使檔案是 .ts。
  • 以為測試通過就沒有型別錯誤：Vitest 不做型別檢查。改完程式至少跑一次 npm run build。
  • 在 task 資料夾執行 npm install：會多一份 node_modules，版本跟課程不同。刪掉它，套件一律裝在 practice/。
  • 在錯的資料夾執行 nest g：在 src/ 裡執行，產生器讀不到 package.json，import 沒有 .js。一律在 work/01 執行。
  • 自己 JSON.stringify 回應：Content-Type 會變成 text/html。直接回傳物件或陣列。
  • 自己 new 依賴的物件：new MenuService() 能動，但測試和之後換實作時都換不掉。讓 Nest 從建構子注入。
  • 照舊教學寫 CommonJS：require、__dirname 在這個 ESM 專案不能用，改用 import 和 import.meta.dirname。
  • 用 tsx 或 node --watch src/main.ts 跑 Nest：tsx 用 esbuild 轉譯，esbuild 不支援 emitDecoratorMetadata，Nest 不知道建構子要什麼，注入的物件會是 undefined；node --watch src/main.ts 跟 node src/main.ts 一樣是語法錯誤。用 npm run start:dev。

小結

  • 手寫 node:http 的問題是重複的 HTTP 樣板和不一致的寫法。框架掌控流程、你填空（控制反轉）：NestJS 建立在 Express 5 上，接手路由、JSON 回應、錯誤處理和物件的建立。
  • 代價：一定要編譯、要學慣例、有魔法感、除錯多一層。小腳本和單一端點的服務不需要它。
  • 專案骨架：main.ts bootstrap → AppModule 登記 controller 和 provider → controller 處理請求 → service 放邏輯。回傳物件或陣列，Nest 會轉成 JSON。
  • 「測試過、build 壞」的原因：nest build／nest start 用 tsc 編譯，會檢查型別；Vitest 只轉譯；node src/main.ts 遇到裝飾器就是語法錯誤。
  • nodenext 下相對 import 寫 .js，因為執行的是 dist/ 裡的 .js；nest g 看目前資料夾的 package.json 決定要不要加，所以在專案根目錄執行。

補充與查表

主線用不到、但查資料或自己建專案時會遇到的細節，查表用，不用背。

  • NestJS 底下的 HTTP 框架：讓 Nest 跑在某個 HTTP 框架上的套件叫平台轉接器（platform adapter），預設是 @nestjs/platform-express。NestJS 12.3.2 預設跑在 Express 5（目前裝的是 5.3.0）上，Express 負責路由、解析請求、middleware。Nest 也能跑在 Fastify 上，那是另一個以效能為主的 HTTP 框架；第 25 課談什麼時候值得換。
  • nest new 的選項：NestJS 12 的 nest new 會問用哪個套件管理工具（npm、yarn、pnpm、bun）、要 ESM（搭配 Vitest）還是 CommonJS（搭配 Jest），以及要不要開 NestJS Observe。這門課用 npm 和 ESM（ESM 也是 12 版的預設）；Observe 是官方的付費雲端監控服務，用 --no-observe 先不開。新專案還附了 oxlint（12 版預設的 lint 工具，取代 ESLint），這門課不用它判分。
  • 練習的 tsconfig 跟 nest new 的差別：少了產生 .d.ts 的 declaration 和增量編譯的 incremental，應用程式用不到。
  • TypeScript 版本：這門課的 NestJS 專案用 TypeScript 6.0.3，不是 7：Nest CLI 12.0.11 依賴 typescript ~6.0.2，之後用到的 Swagger 外掛也要用 TS 6 的編譯器 API。
