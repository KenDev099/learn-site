階段 4：線性結構 · 第 13 課

鏈結串列：節點與反轉

咖啡店的取餐叫號系統要重寫，你負責其中的「排隊名單」：點完餐的顧客依序排進名單，飲料做好就從最前面叫號。第一個需求就卡住了：預約取餐的黃淑芬到店，店長要讓她排到第 2 位。名單如果用陣列存，splice 一行就能插進去，但陣列在背後要把她後面的每一位都往後搬一格；名單越長，每插一次就搬越多次。

這一課換一種存法，叫鏈結串列：每一位顧客自己記住「排在我後面的是誰」，插隊時只要改一兩個人的這條紀錄，其他人完全不動。代價有兩個：名單上不再有「第幾位」的編號，要找誰都得從第一位一路往後問；而且改這條紀錄時只要順序錯一步，後面整串顧客就從名單上消失了。所以整課都在練同一個檢查：改一個指向之前，它原本指著的那一串，還有沒有別的變數抓著？插隊、取消、把名單倒過來、合併兩個櫃檯的隊伍，最後讓「最近查過的訂單」快取每個操作都是 O(1)，靠的都是這一個檢查。面試很愛考鏈結串列，考的也正是這件事：你能不能把「誰指向誰」想清楚、一步都不弄丟。

這課的路線：
  1. 在名單中間插一個人，陣列為什麼要搬動後面每一位、沒有索引怎麼走完整條名單：節點與參考，以及「改變數」和「改節點」的差別。
  2. 黃淑芬插到第 2 位時兩個 next 先改哪一個、顧客取消時怎麼把他拿掉：順序反了會弄丟後半段，dummy 節點讓排第一的人也有前一個。
  3. 名單倒著存要怎麼原地反轉、兩個櫃檯的隊伍怎麼合併：面試最常見的兩題，怎麼把箭頭轉向、把兩條排好的串列接成一條，一個節點都不弄丟。
  4. 手上已經有節點時，最近查過的訂單快取（LRU）怎麼讓每個操作都是 O(1)。
  5. 寫完之後怎麼確認沒有弄丟節點：空串列、只有一個節點、要改的是第一個節點時，逐一手算。
這課會用到：
  • TypeScript 課第 2 課的值與參考：物件存在變數裡的是位置，兩個變數可以指向同一個物件，透過其中一個修改，另一個也看得到。
  • TypeScript 課第 14 課的物件型別：type ListNode = { val: number; next: ListNode | null } 描述一個物件有哪些欄位、各是什麼型別，型別可以引用自己。

在名單中間插一個人，陣列為什麼要搬動後面每一位？

先用陣列做一次開場的需求。名單裡有五位顧客，黃淑芬要插到第 2 位。執行後看第一行：陳美華以後的每一位，位置都往後移了一格。

陣列的元素在記憶體裡一格接一格排好，索引的意思就是「從第一格往後數幾格」，所以 queue[3] 能一步跳到。也正因為位置就是編號，要讓黃淑芬站上第 2 格，原本第 2 格以後的每一位都得往後挪一格。名單有 n 人、插在前面時，就要搬將近 n 次。第 3 課講過，這就是陣列在開頭或中間插入、刪除是 O(n) 的原因。

問題出在「位置就是編號」。如果每一位顧客不靠位置排順序，而是自己記住「我後面是誰」，插隊時就只要改兩個人的紀錄。這就是鏈結串列（linked list）的做法。它把每一筆資料包成一個節點（node），節點有兩個欄位：val 放這筆資料的值，next 指向排在後面的那個節點；最後一個節點後面沒有人，它的 next 是 null。整條串列只要記住第一個節點，沿著 next 一個一個往後問就能走完，這第一個節點叫頭節點（head）。名單一個人都沒有時，連第一個節點都不存在，所以空串列的 head 是 null。

「指向」在 JavaScript 裡具體是什麼？就是 TypeScript 課第 2 課講的參考（reference）：變數裡存的不是物件本身，而是物件在記憶體裡的位置。next 裡存的也是下一個節點的位置，不是它的複本。每個節點都靠 next 找到下一個，所以節點在記憶體裡放在哪裡都沒關係，不需要排在一起；插入時也就不用搬任何節點，只要改參考。下圖是黃淑芬插進去的過程：

第二列有個容易被忽略的前提：「在已經拿到的位置」。鏈結串列插入只改兩個 next，但改之前得先拿到前一個節點，也就是圖裡的王小明。如果要插在第 k 個後面，就得先從 head 走 k 步找到它，所以整體是 O(k)。「鏈結串列插入是 O(1)」只說對了一半，找位置的那段成本跑不掉。鏈結串列真正省事的情況，是手上本來就握著那個節點的參考、不用從頭找，例如 LRU 快取用 Map 直接拿到節點（本課的 LRU 那一節）。

💡 實務上：大多數時候陣列比自己寫的鏈結串列快
JavaScript 的陣列在大多數情況下比自己寫的鏈結串列快：元素放在一起，CPU 讀起來有效率，而且 push／pop 本來就是 O(1)。自己寫鏈結串列的場合主要是兩種：需要頻繁從中間拿掉或移動某一筆（LRU 快取、瀏覽器的上一頁／下一頁紀錄），以及面試。Node 課第 23 課處理記憶體時也會用到 LRU 快取。所以真的要做叫號系統時，資深工程師會先問：「名單會長到 splice 慢得讓人感覺得到嗎？」沒有量過就換資料結構，多半只是讓程式更難讀。這課用排隊名單，是因為「誰排在誰後面」最容易畫出來，練的是指標的思考方式。

到這裡知道了鏈結串列靠什麼省下搬動。但用節點存名單，第一件事就和陣列不同：沒有索引，連「把整條名單印出來」都得換一種寫法。

沒有索引，怎麼從頭走完整條名單？

陣列用 for (let i = 0; i < a.length; i++) 就能走完；鏈結串列沒有 i，也沒有 length，手上只有 head 和每個節點的 next。先把節點寫成程式。下面這格定義了三樣東西，這課的練習都會在起始程式貼好它們，你不用自己寫：

  • ListNode：節點的型別。next 的型別是 ListNode | null，型別引用了自己，因為下一個節點也是節點。
  • listFrom：從陣列建出串列。它從最後一個值往前建，每個新節點的 next 指向目前的 head，再讓自己變成新的 head。
  • listToArray：把串列轉回陣列，方便印出和比對。走超過一百萬個節點就丟錯，防止串列首尾相接時迴圈停不下來（這種情況插隊那節會遇到）。

範例的 val 用數字，比較好印、好比對：把每個節點想成名單上的一位顧客，80、110、70 是他們這張訂單的金額：王小明 80、陳美華 110、林志豪 70。執行後先看第一行的 JSON：

印出來的物件一層包一層：第一個節點的 next 是整個第二個節點，第二個的 next 又是第三個。這就是「只要有 head 就能走完整條」的意思。第三行是空串列：陣列是 []，串列本身是 null。

listToArray 裡那一行 for，就是走訪（traverse）的固定寫法。走訪的意思是從頭到尾每個節點各經過一次，之後每一題都會用到：

for (let cur = head; cur !== null; cur = cur.next) { … 處理 cur.val … }

三個部分分別是：從 head 開始、還沒走到 null 就繼續、每一步換成下一個節點。條件寫 cur !== null，不是 cur.next !== null：後者在最後一個節點就停了，會少處理一個，而且空串列時 cur 本身是 null，讀 null.next 會直接丟 TypeError。

這一行裡負責移動的是另一個變數 cur，不是 head。如果省掉 cur、直接移動 head 呢？下面這格用 head 本身走，加總今天的金額。執行後看第二行，走完之後 head 剩下什麼：

總額是對的，但 head 已經走到 null。串列只能從 head 進入，head 一移走，第一個節點就沒有任何變數指著，整條名單再也找不回來。這是開場那個檢查第一次出現：讓 head 往前走之前，先問它原本指著的那一串還有沒有別的變數抓著？這裡沒有，所以第一個節點就丟了。所以走訪一律用另一個變數往前走，head 留在原地。

可是 cur 和 head 一開始指著同一個節點，為什麼 cur 往前走不影響 head？要回答這個，得把「改變數」和「改節點」分開。節點是物件，複製變數不會複製節點（TypeScript 課第 2 課）：cur = head 之後兩個變數指向同一個節點。下面這格先透過 cur 改 val，再讓另一個變數 other 往前走一步。執行後比較三行：

  • 第一行是 90：cur.val = 90 改的是 cur 指著的那個節點，而 head 指著的是同一個，所以從 head 也看得到。
  • 第二行是 true：兩個變數裡存的是同一個參考。
  • 第三行 head 仍然是 90、other 是 110：other = other.next 只是讓 other 這個變數改指下一個節點，沒有動到任何節點，head 還在原地。

把這兩件事分清楚，整課就不難了：指定變數（cur = cur.next）只是讓變數改指別的節點，串列不受影響；指定欄位（cur.next = …）才是改串列的結構。之後讀每一行程式，先分辨它屬於哪一種：指定變數只是移動你的手指，指定欄位才是在改名單。

💡 實務上：「改到同一個物件」是前端最常見的參考 bug
工作中很少自己寫節點，但「兩個變數指向同一個物件」天天遇到。例如咖啡店後台的購物車：const items = cart.items; items.push(latte)，以為是在副本上加，其實改到了原本的購物車，其他也拿著這個物件的地方（例如「取消修改」要還原用的舊資料）一起被改掉；React 這類用參考比對狀態的框架，還會因為參考沒變而不更新畫面。所以前端狀態習慣寫成「建新物件」：{ ...cart, items: [...cart.items, latte] }。Code review 看到函式直接改傳進來的參數時，資深工程師會問一句：「呼叫的人知道這個物件會被改嗎？」要原地改就寫進函式名稱或註解，否則就回傳新的。

現在可以回到開場的插隊需求了。插隊要改兩個節點的 next，也就是兩次指定欄位；這兩行的先後順序有沒有關係？

黃淑芬插到第 2 位：兩個 next 先改哪一個？

上一節分清了指定變數和指定欄位，插隊就是兩次指定欄位。對照第一節的圖，cur 是王小明，node 是黃淑芬。下面的程式裡，good（和 bad）是王小明開頭的名單，a（和 b）是黃淑芬，她的訂單 90。在 cur 後面插入 node 要兩步，而且順序不能反：

node.next = cur.next   // ① 新節點先接上後半段
cur.next = node        // ② 前一個再指向新節點

為什麼不能反？改之前，從陳美華開始的後半段只有一個入口：王小明的 next。① 先讓黃淑芬的 next 也指向陳美華，這時後半段有兩個參考抓著；② 再把王小明改指向黃淑芬，就算蓋掉了王小明原本的 next，後半段仍然由黃淑芬抓著。反過來先做 ②，王小明的 next 一改成黃淑芬，後半段唯一的入口就被蓋掉，再也找不回來；接著做 ① 時讀到的 cur.next 已經是黃淑芬自己。下面這格兩種順序各跑一次，show 最多印 10 個節點，超過就標成「形成環」：

這是開場那個檢查第二次派上用場：改一個 next 之前，先問它原本指著的那一串，還有沒有別的變數抓著。沒有的話，就先找一個變數抓住它，或者先改另一個。插隊的需求到這裡完成了。另一個常見需求方向相反：排在中間的顧客取消訂單，要把他從名單拿掉。

顧客取消了：怎麼把他從名單拿掉？

插入是讓前一個人改指新來的人；刪除反過來，讓前一個人跳過要離開的人，直接指向他後面那一位。刪除 cur 後面那個節點只要一行：

cur.next = cur.next.next

被跳過的節點去哪了？JavaScript 引擎會自動釋放「再也沒有任何參考指著」的物件，這個機制叫垃圾回收（garbage collection）。被跳過的節點沒有人指著，引擎之後會把它清掉，不用自己處理。

注意這一行操作的是 cur，也就是要刪的那個節點的前一個。單向的串列裡，只有前一個節點的 next 指著它，要把它拿掉就得改那個 next；只拿到要刪的節點本身不夠，因為它不知道誰排在它前面。所以刪除題的走訪，通常讓變數停在「前一個」，檢查的是 prev.next。

排第一的人取消了：沒有前一個怎麼辦？

這套做法在一個地方行不通：要刪的是第一個節點。它沒有前一個，只能改 head：head = head.next，而且函式要回傳新的 head，呼叫的人才拿得到。於是程式裡出現兩種情況：

if (head 要刪) head = head.next
else 找到前一個，prev.next = prev.next.next

連續好幾個開頭都要刪時，第一種情況還要寫成迴圈，很容易漏。常見的解法是在 head 前面放一個假的節點，叫 dummy 節點，也叫哨兵（sentinel）。它的值不重要，只是讓「第一個節點」也有前一個，兩種情況就變成一種。下面這格用同一段 removeFirst 刪三次，執行後看三行：刪中間、刪第一個、刪到空，程式裡沒有任何 if 在區分它們：

到這裡，名單能插隊、也能取消。叫號前還得問一件事：名單是怎麼建出來的？如果收單時每來一位就放到最前面，叫號時會發生什麼事？

名單是倒著存的：怎麼原地把它反轉？

回頭看 listFrom 怎麼建串列：每處理一個值，就建一個新節點，讓它的 next 指向目前的 head，自己變成新的 head。在最前面加一個節點只改一個參考，O(1)；在尾端加則要先走到最後一個節點，除非另外記住它（陣列 vs 鏈結串列那張成本表）。最早的收單程式只存了 head，不想多維護一個 tail，所以每來一位新顧客，就像 listFrom 一樣放到最前面，名單就會變成最新的在前、最早的在後。listFrom 是刻意從陣列的最後一個值往前建，結果才剛好跟陣列同一個順序；收單時沒辦法預先知道後面還有誰，只能一位一位往前放。叫號要從最早來的那位開始，名單得先反轉。

題目：把一條串列原地反轉，回傳新的 head。例如 80 → 110 → 70 → null 變成 70 → 110 → 80 → null。這是 LeetCode 206. Reverse Linked List，面試最常見的鏈結串列題。

暴力解：走一遍把值放進陣列，反轉陣列，再建一條新串列。時間 O(n)，但要 O(n) 的額外空間，而且建出來的是新節點，原本的節點沒有被反轉。如果節點上還掛著別的資料、或別的地方握著這些節點的參考，就不對了。面試官要的是原地反轉，也就是第 3 課講過的原地修改：直接改原本的資料，不另外複製一份。不建新節點，只改每個節點的 next，額外空間 O(1)。

想法：從頭走到尾，把每個節點的箭頭轉向，改成指向前一個。這一步正好違反了開場那個檢查：cur.next 一改成前一個，後半段就沒人抓著了。所以除了「已經反轉好的」和「現在要處理的」，還要第三個變數先抓住後半段：

  • prev：已經反轉好的那一段的開頭，一開始是 null（原本的第一個節點反轉後要變成最後一個，指向 null）。
  • cur：現在要處理的節點，一開始是 head。
  • next：cur 原本的下一個，在改箭頭之前先存起來。

每一步做四件事：

const next = cur.next   // ① 先存：等一下 cur.next 就被改掉了
cur.next = prev         // ② 箭頭轉向
prev = cur              // ③ 反轉好的部分多了 cur
cur = next              // ④ 往前走到還沒處理的部分

用「改變數 vs 改節點」的分法讀這四行：只有 ② 是指定欄位，真正改了串列；①③④ 都是指定變數，只是在移動手指。迴圈在 cur 變成 null 時停止，這時 prev 是原本的最後一個節點，也就是新的 head。下面每一步印出兩段：從 prev 開始的「已反轉」和從 cur 開始的「還沒處理」：

表格裡看得到：每一步「還沒處理」少一個、「已反轉」多一個，兩段加起來永遠是全部的節點，沒有任何一個被弄丟。手算的時候也這樣畫兩段，比在腦中轉箭頭可靠得多。

這四行最常見的錯法有三種，各自對應一個沒做到的地方：

  • 不先存 next：② 之後 cur.next 已經是 prev，原本的後半段沒有人指著。
  • 回傳 head：head 這個變數還指著原本的第一個節點，反轉後它是最後一個；要回傳 prev。
  • 從 prev = head、cur = head.next 開始：原本第一個節點的 next 從來沒被改成 null，它還指著第二個，第二個又指回它，形成環。從 prev = null 開始，第一步就會把它設成 null。

邊界：空串列時 cur 一開始就是 null，迴圈不跑，回傳 null；一個節點時跑一次，回傳它自己。不需要另外寫 if。時間 O(n)，額外空間 O(1)。

遞迴寫法更短，為什麼還是寫迴圈？

反轉也能用遞迴寫：先把 head.next 之後的部分反轉好，再把 head 接到尾巴。程式很短，可是每個節點都佔一層函式呼叫。每呼叫一次函式，引擎就在呼叫堆疊（call stack）上記一筆「回來之後要從哪裡繼續」；這個堆疊的層數有上限，超過就丟 RangeError: Maximum call stack size exceeded。上限是多少依引擎和每一層用的空間而定，規格沒有規定（細節見課末）。第 15 課會細講呼叫堆疊，這裡先看結果：

三個節點時答案正確，十萬個節點時直接丟 RangeError。叫號系統的名單有多長沒人能保證，所以面試時遞迴寫法可以當作第二種解法提出來，但要主動說出這個限制。正式環境的資料長度通常沒有保證，串列題一律寫迴圈。

反轉處理的是一條名單。週末店裡開兩個櫃檯，各自有一條隊伍，取餐螢幕卻只能顯示一條。

兩個櫃檯各一條隊伍：怎麼合併成一條，還照取餐時間排？

兩個櫃檯各自有一條依取餐時間排好的訂單串列，val 是開店後第幾分鐘可以取餐。要合併成一條，仍然依時間排序。例如 5 → 12 → 20 和 8 → 12 → 30 合併成 5 → 8 → 12 → 12 → 20 → 30。這是 LeetCode 21. Merge Two Sorted Lists。

做法跟第 8 課合併兩個已排序的陣列一樣：兩邊各一個指標，每次比較兩邊的開頭，把比較小的接到結果的尾巴。差別在鏈結串列不用建新陣列，直接把原本的節點接過去就好。要接得對，需要四個安排：

  • 結果的第一個節點是誰，要比較過才知道。這跟刪除那一節「排第一的人沒有前一個」是同一個問題，所以用 dummy 當結果的開頭，最後回傳 dummy.next。
  • tail 記住結果目前的最後一個節點，每次接上一個節點後往後移。少了它，每接一個都要從 dummy 走到尾巴，就變成平方時間。
  • 其中一邊用完時，另一邊剩下的已經排好，整段直接接上：tail.next = a ?? b，O(1)，不用一個一個搬。
  • 時間相同時先取第一條（a.val <= b.val 取 a），讓先排進來的維持在前面。相同的值保持原本的先後，這個性質叫穩定（stable），跟第 8 課穩定排序的意思一樣。

表格的「結果」只印到 tail。注意 tail.next = a 之後立刻做 a = a.next，這一步不違反開場那個檢查嗎？被接過去的節點，它的 next 還指著 a 原本的下一個，而 a 原本的下一個同時也由變數 a 抓著，所以沒有東西會丟。那條舊的 next 也不用擔心：下一輪會被 tail.next = … 蓋掉，或者在最後被「剩下的那段」接上。時間 O(n + m)，n、m 是兩條的長度；額外空間 O(1)，只有 dummy 一個節點。

💡 實務上：合併兩個已排序來源，最常出現在「時間軸」
咖啡店後台要把「店內點單」和「外送平台訂單」兩支 API 的結果合成一條依時間排序的訂單列表，兩邊各自已經排好，就是這一題的寫法，只是換成陣列加兩個索引。先確認兩邊的排序欄位和時區一致，不然「已排序」的前提就不成立；時間相同時的規則也要固定，否則每次重新整理順序都在跳，客服會回報「訂單一直換位置」。如果兩份資料都在同一個資料庫，交給 SQL 的 ORDER BY 一次查出來，比在程式裡合併簡單。

到這裡，每一題都得從 head 一路走到要改的地方。成本表那裡說過，鏈結串列真正省事的是另一種情況：手上已經握著那個節點。

手上已經有節點時：最近查過的訂單快取怎麼做到 O(1)？

前面每一題都從 head 出發，走到要改的位置才動手。陣列 vs 鏈結串列那張成本表留了一個伏筆：如果手上本來就有某個節點的參考，從中間拿掉它、再放到別處，都只要改幾個參考。這一節的需求剛好就是這種情況。

店裡的系統常查最近的訂單，想把查過的訂單留在記憶體裡，下次不用再查資料庫。把常用的資料先存一份在比較快的地方，這種做法叫快取（cache）。記憶體有限，快取只能放 capacity 筆，滿了要丟掉一筆。丟哪一筆？最常見的策略是 LRU（least recently used）：丟掉最久沒被使用的那一筆。「使用」包括讀取（get）和寫入（put）。這是 LeetCode 146. LRU Cache，要求 get、put 都是 O(1)。

拆開來看，要 O(1) 做到兩件事：

  • 用 id 找到那筆資料：雜湊表做得到，第 4 課的 Map 平均 O(1)。
  • 維護「誰最久沒用」的順序，而且能把任何一筆移到「最近用過」：陣列做不到，indexOf 加 splice 是 O(n)，這正是開場插隊遇到的搬動問題。

第二件事就是「從名單中間拿掉一個人，再排到最後面」。鏈結串列做這件事只改幾個參考，但前提是能直接拿到那個節點；而第一件事的雜湊表剛好可以存「id → 節點」。在 JavaScript 裡還有更省事的路，先看它。

做法一：利用 Map 的插入順序

第 4 課講過 Map 依插入順序迭代。所以讓 Map 的順序就是「從最久沒用到最近用過」：

  • 使用一筆時，把它先 delete 再 set，它就移到最後。只呼叫 set 不夠：鍵已經存在時，set 只改值，位置不變。
  • 最久沒用的是第一個鍵：map.keys().next().value。keys() 回傳的是TypeScript 課第 10 課的迭代器，一個一次給一個值的物件；next() 只取第一個，O(1)，不會走完整個 Map。

下面這格對 101 試兩種更新方式，執行後比較「只 set」和「先 delete 再 set」兩行裡 101 的位置：

只 set 之後 101 還在最前面，下次淘汰時會被當成最久沒用的那一筆丟掉；先 delete 再 set，101 才移到最後，最久沒用的變成 102。Map 替你記住了「誰先加入」的順序，這就是做法一能這麼短的原因。

做法一短又正確，但它的 O(1) 靠的是 JavaScript 規格保證的 Map 順序。面試官常追問：「如果語言的雜湊表不保證順序，怎麼做？」（哪些語言是這樣，見課末。）這時就得自己做出 Map 替你記住的那條順序。

做法二：雜湊表 + 雙向鏈結串列

標準答案是用鏈結串列自己維護順序。可是單向串列有一個問題，「顧客取消了」那一節講過：要拿掉一個節點，得改它前一個的 next，而節點本身不知道前一個是誰，只能從 head 找。所以改用雙向鏈結串列（doubly linked list）：每個節點同時有 prev 和 next，拿到節點本身就知道前一個是誰，O(1) 把自己拿掉。

所有操作都由兩個小動作組成，兩個都只改常數個參考：

// 把節點從串列拿掉
node.prev.next = node.next
node.next.prev = node.prev

// 把節點放到 tail 前面（變成最近用過）
node.prev = tail.prev
node.next = tail
tail.prev.next = node
tail.prev = node

第二段的順序跟插隊那節一樣有講究：先設好 node 自己的兩個參考，抓住它前後的節點，再去改別人；最後一行才改 tail.prev，因為前一行還要用 tail.prev 找到原本的最後一個節點。用這兩個動作組出兩個操作：

  • get(id)：Map 找不到就回傳找不到；找到就「拿掉、放到 tail 前面」，回傳值。
  • put(id, total)：已經存在就更新值並「拿掉、放到 tail 前面」，不淘汰任何人（數量沒變）；不存在時，如果已滿，先把 head.next 從串列和 Map 都刪掉，再建新節點放到 tail 前面、加進 Map。

因為有 head、tail 兩個 dummy，任何真正的節點都一定有 prev 和 next，上面兩段程式不需要任何 if。這就是 dummy 的威力：把邊界情況變成一般情況，跟刪除第一個節點時是同一個道理。兩種做法並排比較：

Map 的插入順序Map + 雙向鏈結串列
時間get、put 都 O(1)（平均）get、put 都 O(1)（平均）
程式長度十幾行四十行左右，指標容易接錯
依賴JavaScript 規格保證的 Map 順序任何語言的雜湊表都能用
適合JavaScript／TypeScript 的實際專案面試追問、需要從中間 O(1) 移動任意一筆的其他結構
💡 實務上：LRU 用現成套件，要想的是「資料舊了怎麼辦」
實際專案裡，Node.js 常用的 lru-cache 套件已經處理了容量、過期時間這些細節，不需要自己寫。真正要決定的是：容量設多少、要不要設過期時間、訂單狀態改了之後誰負責把快取裡那筆刪掉；不處理的話，顧客會看到「已取餐」的訂單還顯示「製作中」。另外，記憶體裡的快取每台伺服器各一份，部署成多台時彼此不同步，這時通常改用 Redis 這類共用快取。資深工程師加快取前會先問：「這個查詢真的慢嗎？資料可以舊多久？」

面試時先寫 Map 版，再說明「不依賴順序時改用雙向鏈結串列」並畫出上面的圖，是很好的回答。LRU 的兩段程式能不寫 if，是因為頭尾有 dummy；前面幾題沒有這麼幸運，空串列、只有一個節點時，程式還撐得住嗎？

寫完之後，怎麼確認一個節點都沒弄丟？

上一節的 dummy 消掉了一部分邊界，但不是每一題都有。鏈結串列的 bug 很少出在主要的那幾行，多半出在名單特別短、或要改的是第一位的時候。寫完一律用這幾個輸入手算一次：

  • 空串列（head === null）：任何 head.next 都會丟 TypeError。
  • 一個節點：它同時是第一個和最後一個。
  • 兩個節點：反轉、刪除最容易在這裡接錯。
  • 要改的是第一個節點：用 dummy；回傳 dummy.next。
  • 做完之後最後一個節點的 next 是不是 null：不是的話就形成環，下一個走訪的人會無限迴圈。

手算的方法跟反轉那節一樣：畫出「已處理」和「還沒處理」兩段，每改一個 next 就問一次開場那個問題：它原本指著的那一串，還有沒有別的變數抓著？各操作的時間與空間整理在課末的表。下面的練習就照這幾個邊界出測試。

呼叫堆疊的上限與尾呼叫最佳化

呼叫堆疊能有幾層，依引擎和每一層用的空間而定，規格沒有規定。有一種技術叫尾呼叫最佳化（proper tail calls）：函式的最後一步如果是直接回傳另一個函式呼叫的結果，引擎可以重用目前這一層，不必再多記一層。V8（Chrome、Node）沒有實作它，所以在 JavaScript 裡不能靠它讓遞迴不佔堆疊。另外，本課的 reverseRecursive 在遞迴呼叫回來之後還要改 head.next.next 和 head.next，本來就不是尾呼叫。

其他語言的雜湊表與順序

做法二的追問裡說「雜湊表不保證順序」，例如 Java 的 HashMap、Python 3.7 以前的 dict。Java 其實有現成的 LinkedHashMap，內部就是雜湊表加雙向鏈結串列；面試官問這題，要看的是你會不會自己做。

練習

每題的起始程式都貼好了 ListNode、listFrom、listToArray。測試會檢查你回傳的是原本的節點物件（題目要求原地修改時），不是值相同的新節點；也會檢查結果有沒有形成環。

練習 1：寫 countAndSum(head)：head 是今天訂單金額的串列，回傳 { count, total }：節點數量與總額；空串列回傳 { count: 0, total: 0 }。只能讀，不能修改任何節點。

練習 2：寫 removeAll(head, cancelledId)：head 是待做飲料的商品編號串列，刪除所有等於 cancelledId 的節點（顧客取消了這個品項），回傳新的 head。要原地修改：保留下來的必須是原本的節點物件。建議用 dummy。注意：連續好幾個都要刪的時候，刪完一個先不要往前走。對應 LeetCode 203. Remove Linked List Elements。

練習 3：經典題。寫 reverseQueue(head)：原地反轉排隊名單，回傳新的 head。串列最多有 100,000 個節點，所以請用迴圈，遞迴會超出呼叫堆疊。測試會確認你重用了原本的節點、反轉後最後一個節點的 next 是 null。對應 LeetCode 206. Reverse Linked List。

練習 4：經典題。寫 mergeByTime(a, b)：a、b 是兩個櫃檯依取餐時間（val）由小到大排好的串列，合併成一條排序的串列並回傳 head。重用原本的節點，不要建立新節點（dummy 除外）；時間相同時 a 的節點排前面。對應 LeetCode 21. Merge Two Sorted Lists。

練習 5：進階經典題。完成 class RecentOrders（class 與 private readonly 見 TypeScript 課第 23 課），最多存 capacity 筆「訂單 id → 金額」：get(id) 回傳金額，沒有就回傳 undefined（招待的訂單金額是 0，也算找得到）；put(id, total) 存入或更新。get（找得到時）和 put 都算「使用」，會讓那一筆變成最近用過；put 一個新的 id 而且已經滿了，要先淘汰最久沒用的那一筆；put 已經存在的 id 只更新值和順序，不淘汰任何人。所有操作都要 O(1)：測試會用容量 40,000、2 萬次操作計時，計時期間陣列的 indexOf、splice、filter 這類要掃過整個陣列的方法會被停用，用它們維護順序的寫法會判錯。Map 的插入順序或雜湊表 + 雙向鏈結串列都可以。對應 LeetCode 146. LRU Cache（這題找不到回傳 undefined，不是 −1）。

練習 6：同事說「鏈結串列插入是 O(1)，所以在排隊名單的第 5,000 位插入一個人，鏈結串列一定比陣列快很多」。哪個說法正確？

✓ O(1) 的前提是「手上已經有前一個節點的參考」。從 head 找到第 k 個只能一步一步走，O(k)；陣列的 splice 則是搬後面的 n − k 個。哪個快要看位置和實際資料，而且陣列元素放在一起，實務上常常更快。a 錯：漏掉了找位置的成本。b 錯：鏈結串列插入不搬任何節點，這正是它和陣列不同的地方。

練習 7：原地反轉時，每一步為什麼要先寫 const next = cur.next，再寫 cur.next = prev？

✓ 鏈結串列只能沿著 next 走。改掉 cur.next 等於剪斷通往後半段的唯一路徑，所以要先用 next 變數抓住它。b 錯：順序反過來，迴圈走一步就停了，只剩一個節點。c 錯：跟 TypeScript 無關，這是執行時的資料結構問題。

練習 8：const a = listFrom([1, 2])、const b = a、b!.val = 9。這時 a!.val 是多少？

✓ 變數裡存的是物件的參考，b = a 只是複製參考（TypeScript 課第 2 課）。所以走訪時用 cur 改節點，從 head 也看得到。a 錯：要複本得自己建新節點。c 錯：const 只讓變數不能重新指定，物件的欄位照樣能改。

練習 9：用 Map 做 LRU。get(101) 找到之後，要讓 101 變成「最近用過」（移到 Map 的最後），該怎麼寫？

✓ Map 的順序是鍵被加入的順序。鍵已經存在時，set 只更新值、位置不變，所以要先 delete 讓它離開，再 set 讓它重新從最後加入。a 錯：位置不變，101 還是會被當成很久沒用而淘汰。b 錯：get 只讀，不改順序。

常見錯誤

  • 用 head 本身去走串列：走完 head 變成 null，第一個節點找不回來。走訪用另一個變數 cur。
  • 迴圈條件寫 cur.next !== null：最後一個節點沒處理，空串列還會丟 TypeError。走訪寫 cur !== null；要拿前一個節點才用 prev.next !== null。
  • 改 next 的順序錯：插入時先讓新節點接上後半段（node.next = cur.next），再改前一個（cur.next = node）；反轉時先存 next 再改。共同的檢查是：改一個 next 之前，它原本指著的那一串還有沒有別的變數抓著。
  • 第一個節點沒特別處理：刪除或插入在最前面時漏掉。用 dummy 統一，最後回傳 dummy.next，不是 head，也不是 dummy。
  • 刪完一個就往前走：連續兩個要刪的節點會漏掉第二個。刪除後留在原地，再檢查新的下一個。
  • 反轉後忘了尾巴：原本的第一個節點要指向 null，否則形成環。從 prev = null 開始就不會漏。
  • 很長的串列用遞迴：每個節點一層呼叫，超出呼叫堆疊丟 RangeError。串列題寫迴圈。
  • 轉成陣列處理再建新串列：多花 O(n) 空間，而且節點不是原本的物件；題目要求原地修改時不算對。
  • LRU 用 set 更新順序：鍵存在時 set 不改位置。要先 delete 再 set；put 已存在的 id 不淘汰別人。

小結

  • 鏈結串列是用 next 參考串起來的節點，記住 head 就能走完；最後一個的 next 是 null，空串列的 head 是 null。
  • 跟陣列比：沒有索引，找第 k 個 O(k)；拿到前一個節點後插入、刪除 O(1)，不用搬動元素。「插入 O(1)」的前提是手上已經有那個節點。
  • 走訪寫 for (let cur = head; cur !== null; cur = cur.next)；指定變數不改串列，指定 .next 才改。
  • 整課只有一個檢查：改一個 next 之前，先確認它原本指著的那一串還有變數抓著。插隊先接後半段、反轉先存 next，都是這個檢查；手算時畫兩段（已處理、還沒處理）最可靠。
  • 刪除要拿到前一個節點；dummy 讓「第一個節點」也有前一個，刪除、合併都只剩一種情況，最後回傳 dummy.next。
  • 原地反轉：prev = null、cur = head，每步先存 next、轉向、兩個往前；O(n) 時間、O(1) 空間。長串列不用遞迴。
  • 合併兩條排序串列：dummy + tail，每次接比較小的，相同取 a，剩下的整段接上；O(n + m)。
  • LRU：Map 的 delete＋set 維持順序，keys().next().value 是最久沒用的；不依賴順序時用雜湊表 + 雙向鏈結串列（頭尾 dummy），Map 給節點、串列 O(1) 搬動它。
