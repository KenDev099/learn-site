階段 8：進階題型（進階） · 第 24 課

動態規劃延伸：湊金額與最長共同子序列

店裡開始發行禮券，三個部門各丟來一個需求。櫃台：禮券面額跟第 22 課收銀機的代幣一樣是 1、3、4 元，客人要付 6 元，最少要收幾張？會計：這幾種面額湊出某個金額，一共有幾種湊法？行銷：比對兩位常客的點餐紀錄，找出兩人共同的最長點餐順序，拿來設計套餐。同一週，採購也問了一個問題：咖啡豆的進價「一路上漲」最長持續了幾個記錄點？

這幾題用第 22 課的貪婪法做不對，用第 21 課的回溯做得出來但太慢。它們都能用第 23 課的動態規劃（DP）解，而且流程跟第 23 課一樣：先回答狀態、轉移、初始值、答案在哪一格這四個問題，再寫程式。這課就拿這四個問題，依序處理這四個需求，每個需求都會在其中一個問題上逼出新的變化。學完你會寫兩種最常見的延伸題型：湊金額（背包類）和兩個序列互相比對（二維 DP）。

這課的路線：
  1. 四個需求各卡在哪：回顧 DP 的四個問題，先看出每個需求會在哪一個問題上出現新變化。
  2. 櫃台最少收幾張：有些金額湊不出來，表格裡要放什麼（開場第一個需求的最小答案）。
  3. 會計問有幾種湊法：只要數量時不用一筆一筆列，以及兩層迴圈的順序為什麼決定算的是組合還是排列。
  4. 行銷要共同的點餐順序：先確認「順序」要不要連續，再用二維表格比對兩位常客的紀錄，並讀出是哪幾個品項。
  5. 採購的進價一路上漲：答案不在最後一格的題目；最後整理說不出狀態時，怎麼從暴力解推出來。
這課會用到：
  • 第 23 課的 DP 四個問題：狀態（dp[i] 代表什麼）、轉移（怎麼用比較小的格子算出來）、初始值、答案在哪一格；轉移只看前幾格時可以壓縮成幾個變數。
  • 第 21 課的回溯：把每一種選法都走一遍，適合「列出所有方案」，方案一多就很慢。

四個需求，各會卡在 DP 的哪一個問題？

動手寫任何一題之前，先把第 23 課的流程拿出來。每一題都先回答這四個問題，再寫程式：

  1. 狀態：dp[x] 代表什麼？要用一句完整的中文說出來，例如「湊出 x 元最少要幾張」。說不出這句話，後面的轉移就寫不出來。
  2. 轉移：dp[x] 怎麼從比較小的格子算出來？通常是問「最後一步做了什麼」。
  3. 初始值：最小的那幾格是多少？算不出來的格子放什麼？
  4. 答案在哪一格：dp[amount]、dp[n][m]，還是整個表的最大值？

第 23 課的題目，這四個問題的答案都很單純：一個參數的狀態、每一格都算得出來、答案在最後一格。這課的四個需求，每一個都在其中一個問題上不再單純：

需求出現新變化的問題新在哪裡
櫃台：最少收幾張初始值有些金額根本湊不出來，「做不到」要用一個值放進表格
會計：有幾種湊法轉移兩層迴圈誰在外面，決定算出來的是組合還是排列
行銷：共同的最長點餐順序狀態有兩份紀錄，「做到哪裡」要用兩個數字描述，表格變成二維
採購：進價一路上漲答案在哪一格最長的那段可能在中間就結束，答案不在最後一格

先從櫃台開始。它的狀態和轉移都跟第 23 課很像，新問題只有一個：有些金額湊不出來，那一格要填什麼？

櫃台最少要收幾張？湊不出來的金額放什麼

櫃台的情境是：禮券面額 1、3、4 元，要付 6 元。這跟第 22 課代幣找零 6 元是同一題，只是代幣換成禮券、找零換成收款：貪婪法每次拿最大的會拿 4 + 1 + 1（3 張），但 3 + 3 只要 2 張。貪婪會錯，是因為先拿了 4 之後剩下的 2 元只能用兩張 1 元補，而這個「拿 4 會害到後面」在拿的當下看不出來。台灣硬幣 1、5、10、50 這種「大面額是小面額的倍數」的組合，先拿大的剛好不會出事；面額不是這種關係時，就要把每一種可能都考慮到，這正是 DP 擅長的。

狀態：dp[x] = 湊出剛好 x 元，最少要幾張。

轉移：問「最後一張是哪種面額」。最後一張如果是 c 元，前面就要湊出 x − c 元，最少 dp[x − c] 張，再加這一張。每種面額都試一次，取最小：

dp[x] = min( dp[x − c] + 1 )，c 是每一種 ≤ x 的面額

這個轉移把「最後一張是 1、是 3、是 4」三種情況都比較過，所以不會像貪婪一樣只看眼前最大的那一張。

初始值：dp[0] = 0，湊 0 元不用任何禮券。這是第 23 課就有的部分。新的問題是其他格子一開始要放什麼。

轉移用的是 min，所以一格的起始值要「輸給任何一個真的答案」，真的答案一出現就能蓋掉它。如果放 0，min(0, …) 永遠是 0，表格全部變成 0。放 -1 當成「湊不出來」也不行，-1 比任何真的張數都小，min 一樣會選它。要放一個「比任何真的答案都大」的值，代表「目前還湊不出來」。這種用來代表特殊情況、不會跟正常答案混在一起的值，叫哨兵值（sentinel）。JavaScript 的 Infinity 剛好合適：

  • Infinity + 1 還是 Infinity：從湊不出來的格子轉移過來，結果還是湊不出來。
  • Math.min(Infinity, 3) 是 3：只要有一條路湊得出來，就會蓋掉 Infinity。

答案：dp[amount]。金額從 0 到 amount 共 amount + 1 格。還是 Infinity 就代表湊不出來，經典題規定這時回傳 -1。下面印出每一格怎麼算出來，執行後看 x = 6 那一行：

x = 6 那一行：最後用 4 要 dp[2] + 1 = 3 張，最後用 3 只要 dp[3] + 1 = 2 張。DP 把每一種「最後一張」都比較過，所以不會像貪婪那樣被大面額騙走。這就是櫃台需求的最小答案：dp[6] = 2。

這組面額每個金額都湊得出來，還沒看到 Infinity 真正發揮作用。換一組湊不出來的資料，看 Infinity 怎麼一路傳下去；最後一行另外看 Infinity 交給 JSON 時會變成什麼：

面額 5、10 只湊得出 5 的倍數，dp 裡其他格一直是 Infinity：13 元那格沒有任何一條路能蓋掉它，所以回傳 -1；15 元可以由 10 元那格加一張 5 元得到，是 2。

最後一行是正式環境要注意的事：JSON.stringify 會把 Infinity 變成 null，前端收到 null 很容易當成「沒資料」或 0。哨兵值只在演算法內部用，回傳給外面之前要轉成約定好的值（這題是 -1），API 文件也要寫清楚。

為什麼要由下往上填表，而不是直接寫遞迴？同樣的題目用遞迴寫，go(x) 會去呼叫 go(x − 1)、go(x − 3)、go(x − 4)，同一個 x 被算了非常多次：面額 1、3、4 湊 40 元要三億多次呼叫，湊 50 元要三百多億次。加上第 15 課的記憶化（用陣列或 Map 記住算過的 x）就變成 O(amount × k)，跟表格一樣。由下往上填表的好處是沒有遞迴深度的限制：金額一萬元時，遞迴可能深到一萬層而丟出 RangeError。

複雜度：外層 amount 格，每格試 k 種面額，時間 O(amount × k)，空間 O(amount)。這類題目有一個通用的名字：把面額想成可以拿的東西、金額想成背包的容量，問「怎麼挑東西放進背包」，叫背包問題（knapsack）；每種東西可以拿任意多次的版本叫無限背包（unbounded knapsack）。禮券每種可以用任意張，所以櫃台這題是無限背包。

💡 實務上：先問面額能不能用貪婪，再決定要不要 DP
工作上會遇到這題的樣子，通常是點數折抵、禮券或儲值卡組合這類「用最少張數湊出剛好的金額」。資深工程師會先問面額是誰定的：如果是台灣硬幣這種固定面額，貪婪就對，程式簡單也好維護；面額由營運在後台自由設定時，才需要 DP，因為哪天有人設了 1、3、4 這種組合，貪婪就會悄悄算錯。金額記得用整數（元或分），不要用有小數的浮點數當陣列索引。另外先確認金額上限：表格有 amount + 1 格，金額是幾千、幾萬沒問題，如果有人輸入一億，要在 API 入口就擋下來。

櫃台的表格裡，每一格存的是「最少幾張」。會計要的是另一件事：同樣的面額、同樣一格一格的金額，每一格改存「有幾種湊法」。轉移會變成什麼？而「幾種」到底怎麼算才算一種？

會計問有幾種湊法：迴圈順序為什麼決定組合還是排列？

會計的問題換成小一點的數字：面額 1、2 元，湊 4 元有幾種湊法？用第 21 課的回溯列出來是 1+1+1+1、1+1+2、2+2，共 3 種。這裡 1+1+2 和 2+1+1 算同一種，因為會計只看用了哪些禮券、各幾張，不看收的先後。這種不計順序的算法叫組合；如果順序不同就算不同，叫排列，會有 5 種（1+1+1+1、1+1+2、1+2+1、2+1+1、2+2）。兩種都是合理的問題，寫程式前要先知道對方要哪一種。

只要數量時，不需要真的把每一種列出來。狀態：dp[x] = 湊出 x 元的方法數。轉移：櫃台題是「每種最後一張取最小」，問方法數就改成「每種最後一張的方法數加起來」，dp[x] += dp[x − c]。初始值：dp[0] = 1，湊 0 元剛好有一種方法：什麼都不用。這一格是 1 才能讓「只用一張 c 元」被算到（dp[c] += dp[0]）；寫成 0 的話，整張表都是 0。

剩下要決定的是兩層迴圈怎麼排：一層走面額、一層走金額。兩種排法看起來只是把迴圈對調，算出來的東西卻不一樣。執行後比較兩個答案，並看組合版每加入一種面額後 dp 怎麼變：

組合版是 3，排列版是 5。為什麼會不一樣？看組合版的過程：第一輪只能用 1 元，每個金額都只有「全部用 1 元」一種；第二輪加入 2 元，dp[x] += dp[x − 2] 的意思是「在已經算好的湊法後面再放一張 2 元」。因為所有 1 元一定在 2 元之前加入，每一種組合只會用「1 元在前、2 元在後」這一種順序被算到，1+1+2 算了，2+1+1 不會再算。

排列版是對每個金額 x 問「最後一張是哪種面額」，最後一張是 1 和最後一張是 2 分開算，所以 1+1+2（最後是 2）和 2+1+1（最後是 1）各算一次。這兩個問題都有人問，例如第 23 課的「補牛奶每趟搬 1 或 2 箱，有幾種順序」就是排列（1+2 和 2+1 算兩種）。重述題目時先確認：順序不同算不算不同？

組合版內層的 x 由小往大走，所以同一種面額可以用很多張，這正是無限背包要的；每種只有一張時，見課末「補充與查表」的 0／1 背包。

複雜度：O(amount × k) 時間、O(amount) 空間。回溯要把每一種湊法都走一遍，面額 1、2、5、10、20、50 湊 1,000 元有一億多種，回溯要走上億步；DP 只要 6 × 1,000 次加法。這就是第 21 課說的：要「所有方案」用回溯，只要「有幾種」用 DP。

💡 實務上：「有幾種」的需求，先把順序和數字大小問清楚
PM 或會計說「算一下有幾種組合」時，常常沒想過 1+2 和 2+1 算不算不同，這要在寫程式前問清楚，不然兩種寫法都能跑、數字卻差很多，而且測試很難發現。另一個要確認的是數字會長多大：方法數成長得很快，超過 Number.MAX_SAFE_INTEGER（約 9 × 10¹⁵）之後加法就不精確，也不會報錯；需要精確值就改用 BigInt，題目或需求只要餘數時，就在每一步加完後用 % 取餘數，數字不會變大。最後問一句「真的需要數量，還是其實要列出前幾個方案給使用者選？」，後者是另一個問題，通常要排序或加條件篩選，不是算總數。

禮券的兩個需求都只有一個「金額」在變，表格是一維的。行銷的需求不一樣：要比對的是兩位顧客的點餐紀錄，兩份紀錄各自有長度。但在建表之前，要先弄清楚行銷說的「共同的點餐順序」到底是什麼。

「共同的點餐順序」要連續嗎？子序列、子陣列、子字串

行銷說的「點餐順序」有兩種讀法：兩人都連續點過的一段，或者兩人都依同樣先後點過的幾個品項，中間可以夾別的。這兩種讀法對應三個常被混用的名詞，以點餐紀錄 'ALTC' 為例（A 美式咖啡、L 拿鐵、T 伯爵紅茶、C 卡布奇諾）：

名詞規則'ALTC' 的例子不是的例子
子陣列（subarray）／子字串（substring）連續的一段'LT'、'ALT''AT'（中間跳過 L）
子序列（subsequence）刪掉一些元素，剩下的順序不變，不需要連續'AT'、'AC'、'LC'、'ALTC''TA'（順序反了）

設計套餐時在意的是「先點了 A、之後也點了 T」，中間有沒有點別的不重要，所以行銷要的是子序列。長度 n 的序列有 2ⁿ 個子序列（每個元素留或不留），所以不能列出全部再比。題目寫「subsequence」就不要求連續，寫「substring」「subarray」就要連續，兩種的 DP 轉移不一樣。這是面試時最該先確認的一件事。

確定要找的是子序列之後，問題就變成：兩份紀錄共同的子序列裡，最長的是哪一個？

行銷要共同的最長點餐順序：狀態怎麼放兩個參數？

王小明最近的點餐紀錄是 'ALTC'，陳美華是 'LATC'。兩人共同的最長點餐順序是 'ATC'（王小明：ALTC；陳美華：LATC），長度 3；'LTC' 也是 3。兩個序列共同的子序列裡最長的那個，叫最長共同子序列（Longest Common Subsequence，LCS）。

禮券題的「做到哪裡」只要一個數字：湊到幾元。這次有兩份紀錄，「做到哪裡」要用兩個數字描述：a 用到第幾個、b 用到第幾個。只看 a 用到哪裡不夠，因為同樣是 a 的前 3 個字元 'ALT'，對上 b 的前 1 個 'L' 答案是 1，對上整個 'LATC' 答案是 2（'AT' 或 'LT'）。狀態有兩個參數的 DP 叫二維 DP，表格也從一排格子變成一張有列有行的表。

狀態：dp[i][j] = a 的前 i 個字元與 b 的前 j 個字元，最長共同子序列的長度。

轉移：跟禮券題一樣問「最後一步」，這次是看兩邊的最後一個字元 a[i − 1] 和 b[j − 1]（前 i 個字元的最後一個，索引是 i − 1）：

  • 相同：這個字元可以當共同子序列的最後一個，兩邊都退一格：dp[i][j] = dp[i − 1][j − 1] + 1。
  • 不同：兩個最後字元不可能同時用到，至少要丟掉一個。丟掉 a 的最後一個是 dp[i − 1][j]，丟掉 b 的最後一個是 dp[i][j − 1]，取比較大的：dp[i][j] = max(dp[i − 1][j], dp[i][j − 1])。

初始值：任何一邊是空的（i = 0 或 j = 0），共同子序列長度是 0。所以表格開 (n + 1) × (m + 1)，多一列一行全部是 0。這一列一行讓 i = 1 時讀 dp[i − 1] 也有東西可讀，不用另外寫 if。答案：dp[n][m]，整個 a 與整個 b。

建二維表：要用 Array.from，不要用 fill 放陣列

在 JavaScript 裡，二維表就是「陣列裡面放陣列」，每一列是一個陣列。建這張表時，很多人第一次會寫 new Array(n + 1).fill(new Array(m + 1).fill(0))。fill 是把同一個值放進每一格，放的是物件時，每一格都指向同一個陣列（TypeScript 課第 2 課的「陣列是參考」）。改一列，其他列跟著變。執行後看第一行，三列是不是都被改到了：

Array.from({ length: n }, () => …) 每一列都呼叫一次函式，建出不同的陣列。用 fill 建表不會報錯，只是答案偶爾不對，很難查，所以建表時就寫對。

從表格讀出共同的點餐順序

長度 3 回答了「有多長」，但行銷要設計套餐，要的是哪幾個品項。表格裡其實記著答案是怎麼來的：每一格的值，不是從左上加 1，就是從上或左抄過來。從右下角往回走，就能找回那條路：字元相同就把它收下、往左上走；不同就往數字比較大的那一邊走（上和左一樣大時，走哪邊都是一個正確答案）。走到第 0 列或第 0 行就停：

'ALTC' 和 'LATC' 讀出 'ATC'，是長度 3 的其中一個答案（'LTC' 也是長度 3，同樣正確）；第二組讀出長度 4 的 'ALCT'；'AL' 和 'TC' 沒有共同品項，回傳空字串。

這也是文字比對（diff）工具的核心問題：兩個版本的檔案，最長共同子序列是「沒變的行」，其他就是新增或刪除的行。

表格的大小是 n × m，紀錄一長就要注意記憶體。如果只要長度，dp[i] 這一列只用到上一列 dp[i − 1]，可以像第 23 課那樣只留兩列，空間降到 O(m)，這叫空間壓縮。兩個長度一萬的字串，完整的表是一億格，每格就算只佔 4～8 bytes（依引擎而定）也要幾百 MB，只留兩列就只要兩萬格。要像上面那樣讀回品項時，就需要完整的表。

💡 實務上：比對兩個版本時，用現成的 diff 套件
LCS 的觀念在工作上最常出現在「顯示兩個版本差在哪」：後台文章或商品說明的修改紀錄、設定檔改了什麼、Code Review 的 diff 畫面。這類需求直接用維護良好的套件（例如 npm 的 diff），它們用的是比基本 LCS 更省時間和記憶體的演算法，也處理好了逐行、逐字等不同比對方式。你需要決定的是比對的單位：單位越細，要比的元素越多：整篇文章逐字比會慢很多，逐行比通常就夠用，也比較好讀。理解這課的表格，讓你看得懂「為什麼兩份很長又差很多的檔案 diff 會變慢」，以及在效能出問題時知道該從比對單位和資料大小下手。

到這裡，四個問題裡的初始值、轉移、狀態都出現過新變化，答案卻一直在最後一格：dp[amount]、dp[n][m]。採購的需求會打破這一點。

採購的進價一路上漲：答案為什麼不在最後一格？

採購記下咖啡豆每週的進價，想知道「價格一路上漲」最長持續了幾個記錄點。這次只有一份資料，而且是數字，所以換一個例子：要比的是價格高低，不是兩份紀錄有沒有相同的品項。中間可以跳過幾週（子序列，不需要連續），而且要嚴格上漲，持平不算。這是最長遞增子序列（Longest Increasing Subsequence，LIS）。

只有一個序列，狀態一個參數就好，但定義要選對。狀態：dp[i] = 以第 i 週結尾的最長遞增子序列長度。「以 i 結尾」很關鍵：要接在某個子序列後面，必須知道那個子序列的最後一個值是多少，定義成「前 i 週的最長」就不知道最後一個值，接不上去。

轉移：第 i 週可以接在任何一個比它便宜的第 j 週（j < i、prices[j] < prices[i]）後面：dp[i] = max(dp[j] + 1)；一個都接不上時，自己一個就是長度 1。初始值：每一格先放 1。

答案：這裡就是新變化。dp[i] 規定了「以第 i 週結尾」，最後一格只代表「以最後一週結尾」的那些子序列；最長的那段可能在任何一週結束，所以答案是整個 dp 的最大值，不是最後一格。執行後比較最後一格和最大值：

最後一週 280 比前面都便宜，dp[8] 只有 1，答案 4 在中間就出現了。兩層迴圈，時間 O(n²)、空間 O(n)。另外有更快的 O(n log n) 做法，見課末「補充與查表」。

四個需求都解完了。回頭看，每一題的狀態都是直接給的；面試或工作上遇到新題目時，最難的正是想出狀態。最後一節整理說不出狀態時怎麼辦。

說不出狀態時，怎麼從暴力解推出來？

這課四題的狀態，其實都能從暴力解裡找到。看到題目說不出狀態時，照這個順序走：

  1. 先寫遞迴的暴力解，或第 21 課的回溯。寫的時候注意遞迴函式需要哪些參數，例如 LCS 是「a 用到哪、b 用到哪」。
  2. 參數就是狀態。同一組參數會被重複呼叫，就是有重疊子問題，DP 有用。參數有一個就是一維表，兩個就是二維表。
  3. 加記憶化，或改成由下往上填表。填表時確認順序：每一格用到的格子都要先算好。
  4. 說出時間（格子數 × 每格的工作量）與空間，再看能不能只留上一列。

拿櫃台題對照：遞迴的 go(x) 只有一個參數「還要湊幾元」，所以狀態是一維的 dp[x]；它會被重複呼叫上億次，所以 DP 有用。面試時邊做邊講這幾步，比直接背出轉移式更能說服面試官，因為你展示了推導的過程，換一題也做得出來。

寫出 DP 之後，還要判斷它夠不夠快。O(n²) 的 DP 什麼時候夠用？看資料量。這門課實測過，3 萬筆的雙迴圈約 0.3 秒，所以 n 在一萬以內 O(n²) 沒問題；n 到 10 萬就是 10¹⁰ 步，要換 O(n log n) 的做法。二維 DP 還要看記憶體：n × m 格要放得進記憶體，放不下就壓縮成兩列。正式環境的資料會長大，寫之前先問「資料最多多大」，跟第 2 課講的一樣。

補充與查表

  • 0／1 背包（每張禮券只有一張）：如果題目改成「每張禮券只有一張」，內層要由大往小走（for (let x = amount; x >= c; x--)），dp[x − c] 才會是還沒用過 c 的舊值。這叫 0／1 背包，面試常見的變化，記住「只能用一次就倒著走」即可。
  • LIS 的 O(n log n) 做法：另外有一種用二分搜尋（第 9 課）的 O(n log n) 做法，面試偶爾會追問，知道有這個做法即可，本課不展開。

練習

隱藏測試先跑固定案例，再用上百組隨機案例（由小到大）和參考解比對，失敗時會印出最小的失敗輸入，可以自己手算。傳進來的陣列會被凍結（Object.freeze），修改它會被判錯。最後一個案例比較大，指數時間的寫法會被 3 秒的上限判成逾時。

練習 1：寫 fewestVouchers：禮券面額 values（正整數、互不相同、每種可以用任意張），回傳湊出剛好 amount 元最少要幾張；湊不出來回傳 -1（沿用經典題的規定）；amount = 0 回傳 0。用由下往上的表格寫：最後一個案例金額 10,000 元。（對應 LeetCode 322. Coin Change）

練習 2：寫 voucherWays：面額 values（正整數、互不相同、每種可以用任意張），回傳湊出剛好 amount 元的組合數（只看用了哪些禮券，順序不同算同一種）；amount = 0 回傳 1。答案保證在安全整數內。最後一個案例是面額 1、2、5、10、20、50 湊 1,000 元。（對應 LeetCode 518. Coin Change II）

練習 3：寫 commonOrderLength：兩位顧客的點餐紀錄 a、b（每個字元代表一種品項），回傳最長共同子序列的長度（不需要連續，順序不變）。任何一邊是空字串時回傳 0。最後一個案例是兩個長度 400 的紀錄。（對應 LeetCode 1143. Longest Common Subsequence）

練習 4：寫 longestRise：咖啡豆每次記錄的進價 prices，回傳嚴格遞增的最長子序列長度（不需要連續，持平不算上漲）；空陣列回傳 0。O(n²) 即可，最後一個案例 n = 2,000。（對應 LeetCode 300. Longest Increasing Subsequence）

練習 5：禮券面額 1、3、4 元，要湊 6 元且張數最少。每次先拿最大面額可以嗎？

✓ c。先拿最大面額只有在特定的面額組合下才對（例如台灣硬幣 1、5、10、20、50）。a 是常見的直覺，這組面額就是反例；b 排序只是讓貪婪法能拿到最大的，不會讓它變對。DP 把每一種「最後一張」都試過，dp[6] = min(dp[5], dp[3], dp[2]) + 1 = 2。

練習 6：算「面額 1、2 元湊 4 元有幾種湊法」時，把迴圈寫成外層金額 x、內層面額 c，dp[x] += dp[x - c]。結果會是？

✓ a。外層金額時，每個金額都問「最後一張是哪種」，最後一張不同就算不同，所以是排列數。要組合數（不計順序）就外層面額、內層金額，讓每種組合只用「面額由前到後」一種順序被算到。b 錯在兩種寫法加總的是不同的東西，不只是加法順序；c 錯在 dp[0] = 1 是初始值，兩種寫法都會用到它。

練習 7：王小明點了 'ALTC'，陳美華點了 'ATLC'。「最長共同子序列」的長度是多少？

✓ b。子序列可以跳過中間的元素，但順序不能變：'ALC' 在兩邊都是 A 在 L 前、L 在 C 前。a 說的是最長共同子字串（要連續），那是另一題，轉移也不同；c 錯在品項相同但順序不同，L 和 T 的先後在兩邊相反，不能同時選。

常見錯誤

  • 用貪婪法算最少張數：面額 1、3、4 湊 6 元就錯了。除非能說出貪婪對的理由，否則用 DP。
  • 初始值全部放 0：求最小值時 min(0, …) 永遠是 0。除了 dp[0]，其他格放 Infinity（哨兵值）。
  • Infinity 沒轉成 -1：題目規定湊不出來回傳 -1；Infinity 放進 JSON 還會變成 null。回傳前轉成約定好的值。
  • dp 表大小差一：金額 0 到 amount 共 amount + 1 格；LCS 的表是 (n + 1) × (m + 1)，多一列一行放「空字串」的 0。
  • 迴圈順序錯：組合要外層面額、內層金額；外層金額算的是排列。寫之前先確認順序不同算不算不同。
  • 求方法數時 dp[0] = 0：整張表都會是 0。湊 0 元有一種方法：什麼都不用。
  • 子序列與子字串搞混：子序列不需要連續，字元不同時要取 max(上, 左)，不能歸零也不能取左上。重述題目時確認要不要連續。
  • 用 fill 建二維表：new Array(n).fill(new Array(m).fill(0)) 每一列是同一個陣列，不會報錯但答案會錯。用 Array.from({ length: n }, () => new Array(m).fill(0))。
  • LIS 回傳最後一格：dp[i] 是「以 i 結尾」的長度，最長的那段可能在中間結束，答案是整個 dp 的最大值。

小結

  • DP 每一題都先回答：狀態、轉移、初始值、答案在哪一格。這課的四個需求各在其中一點上有變化：櫃台是初始值、會計是轉移的迴圈順序、行銷是兩個參數的狀態、採購是答案不在最後一格。
  • 櫃台的最少張數（無限背包）：dp[x] = min(dp[x − c] + 1)；做不到用 Infinity 當哨兵值，回傳前轉成 -1。O(金額 × 面額數)。由下往上填表沒有遞迴深度的限制。
  • 會計的方法數：dp[0] = 1；外層面額、內層金額是組合，外層金額、內層面額是排列。只要數量就用 DP，不用回溯一筆一筆數。
  • 子序列不需要連續、順序不變；子字串、子陣列要連續。行銷的「共同點餐順序」是子序列。
  • 行銷的兩份紀錄用二維 DP：LCS 的 dp[i][j] 看左上、上、左三格；表格多一列一行；建表用 Array.from；從右下角往回走可以讀出共同的內容；只要長度時可以壓縮成兩列。
  • 採購的 LIS：狀態是「以 i 結尾」，答案是整個 dp 的最大值；O(n²) 在 n 一萬以內夠用，更大要 O(n log n)。
  • 說不出狀態時：先寫遞迴或回溯，參數就是狀態，加記憶化或改成填表。
