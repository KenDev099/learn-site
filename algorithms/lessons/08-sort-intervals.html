階段 3：陣列技巧 · 第 8 課

排序與區間：比較函式與合併的想法

咖啡店的包廂開放預約，店長想在後台看到一張報表：包廂今天實際被占用的時段。預約系統匯出來的資料是依「建立預約的先後」排的，不是依時間：[[15, 17], [10, 13], [9, 11], [11, 12]]，每一筆是 [開始, 結束]，例如 [9, 11] 是 9 點到 11 點。其中 9–11、10–13、11–12 這三筆時間彼此疊在一起，對店長來說包廂就是從 9 點連續用到 13 點；15–17 跟前面隔著空檔，是另一段。報表要的答案是 [[9, 13], [15, 17]]。

最直覺的做法是拿每一筆去跟其他每一筆比，任兩筆都要比一次，大約 n²／2 次，是 O(n²) 的量級。這一課要寫出快得多的版本，關鍵只有一步：先依開始時間排序。排好之後，時間疊在一起的預約一定排在隔壁，從左走到右一次就能合併完。但這一步要先做對：JavaScript 的 sort 預設不是照數字大小排、比較函式要回傳數字、它還會改到原本的陣列，每一個都會讓報表默默算錯。所以這課先把 sort 用對，再一路做到合併預約。

這課的路線：
  1. 排序先排對：[10, 9, 1, 100].sort() 為什麼排錯，比較函式怎麼告訴 sort 誰在前，多個欄位怎麼排。
  2. 排序的代價：sort 會改到誰的資料，O(n log n) 換到了什麼，什麼時候不該先排序。
  3. 兩份已排好的預約併成一份：兩個指標一次走完，以及不開新陣列的原地版本。
  4. 合併重疊的預約：排好之後為什麼只要跟最後一段比，新增一筆預約時怎麼不用整個重排，交出去前要測哪些邊界。
這課會用到：
  • 第 7 課的雙指標：用兩個存索引的變數走過陣列，每一步依比較結果移動其中一個。
  • TypeScript 課第 2 課的排序方法：sort 會改原陣列，toSorted 回傳排好的新陣列。
  • 第 2 課的 O(n log n)：內建排序的成本，比 O(n) 慢、比 O(n²) 快得多。

為什麼 [10, 9, 1, 100].sort() 排錯？預設排序是字串順序

報表的第一步是把預約依開始時間排好。開始時間就是數字，所以先拿一串最單純的數字來看 sort 怎麼排。下面把幾筆訂單金額和價差排序，沒給任何參數，執行後看第一行的順序：

第一行的結果是 [1, 10, 100, 9]，不是 [1, 9, 10, 100]。原因是規格規定：sort() 沒有給比較函式時，會先把每個元素轉成字串，再用字串的順序排，也就是像查字典那樣從第一個字元比起，第一個字元一樣才比第二個。

  • 第一行：'100' 跟 '9' 比第一個字元，'1' 比 '9' 小，所以 100 排在 9 前面。
  • 第二行：'-1' 跟 '-10' 前兩個字元一樣，短的那個排前面，所以 −1 排在 −10 前面，跟數字大小剛好相反。
  • 第三行：本來就是字串的陣列排出來的順序跟第一行一模一樣，證明數字真的被當成字串在排。

只要陣列裡有不同位數的數字或負數，結果就是錯的，而且不會報錯。這是它危險的地方：測試資料剛好都是兩位數時一切正常，上線遇到 100 元以上的訂單才排錯。放回這課的任務，預約是 [開始, 結束] 這樣的陣列，預設排序會把 [10, 13] 轉成字串 '10,13'，它會排在 '9,11' 前面，10 點的預約就跑到 9 點前面去了。字元實際上比的是什麼編碼，見課末「補充與查表」。

要讓 sort 照數字大小排，就得自己告訴它「大小」是什麼意思。這就是比較函式。

怎麼告訴 sort 誰在前？比較函式

上一節的問題出在 sort 不知道你想怎麼比，只好用字串順序。比較函式（comparator）就是你交給 sort 的判斷規則，形式是 (a, b) => 數字。

它怎麼運作：排序的過程中，sort 會挑出兩個元素交給比較函式，問很多次，每次只問一件事：「這兩個誰該在前面？」你不用管它挑哪兩個、問幾次、怎麼搬動元素，那是排序演算法的工作；你只負責回答每一次的問題。回答的方式是回傳值的正負號：

回傳值意思
負數a 排在 b 前面
正數b 排在 a 前面
0一樣大，保持原本的先後

由小到大排數字就寫 (a, b) => a - b。拿 9 和 10 來驗證：9 - 10 是 −1，負數，所以 9 排在 10 前面，正是想要的結果。由大到小就把兩個對調：(a, b) => b - a。只有正負號有意義，回傳 −1 或 −500 效果一樣，所以直接相減最省事。下面用同一串數字比較兩種方向：

為什麼不能回傳 true／false

知道比較函式要回答「誰在前」之後，很多人會直覺寫成 (a, b) => a > b，意思是「a 比較大就交換」。這是把比較函式誤解成「要不要交換」。在 TypeScript 裡這行會直接被擋下，因為比較函式的型別規定要回傳 number；但在 JavaScript 裡不會報錯，true 被當成 1、false 被當成 0。

問題在於回傳值永遠不會是負數，也就是比較函式從來不會說「a 在前」。排序演算法每次拿到的資訊只有「b 在前」或「一樣」，有一半的答案是錯的，結果依引擎的演算法而定，常常根本沒排好。下面用 Number(a > b) 重現 JavaScript 實際拿到的值，執行後比較兩行：

金額相同時看時間：多個欄位怎麼排？

合併預約只需要依開始時間這一個欄位，但實務上排的多半是物件，而且常常要比好幾個欄位。這一節換成後台的訂單列表來看，因為訂單有金額、時間兩個都會拿來排的欄位，比預約更能說明問題；練習 1 就是這一題。

比較函式拿到的是兩筆訂單物件，自己挑欄位相減就好。要「先依金額由小到大，金額一樣時再依時間由早到晚」，寫法是用 || 串起來：

(a, b) => a.total - b.total || a.time - b.time

它怎麼運作：

  • 金額不同時，a.total - b.total 不是 0，|| 直接回傳它，右邊根本不會算。
  • 金額相同時，它是 0。|| 的規則是左邊為 falsy 才看右邊；falsy 是在條件判斷裡會被當成 false 的值，0 就是其中之一。所以這時 || 才去算右邊的時間差，用時間決定先後。

要再多一個欄位，就繼續往後接 || …，越前面的欄位優先權越高。字串欄位不能相減，例如依顧客名字排，改用 a.name.localeCompare(b.name)，它比較兩個字串並回傳負數、0、正數，正好符合比較函式的規定。下面四筆訂單有兩組金額相同，執行後看金額相同的那兩筆是不是依時間排：

穩定排序：相等的元素不會被打亂

上面金額相同的訂單，是靠第二個欄位決定先後。那如果比較函式只比金額，金額相同的兩筆會怎麼排？這取決於排序是不是穩定的。

穩定排序（stable sort）是指：比較函式說「一樣」（回傳 0）的兩個元素，排完之後保持原本的先後順序。不穩定的排序則可能把它們對調，每次執行還可能不一樣。現在的規格要求 sort 和 toSorted 一定是穩定的（從哪個版本開始、引擎怎麼做到，見課末「補充與查表」）。

穩定帶來一個實用的做法：先依次要的欄位排，再依主要的欄位排，結果跟用 || 串起來一樣。第二次只比金額，金額相同的訂單被當成「一樣」，穩定排序就會保留第一次排好的時間順序。下面兩種寫法，執行後看印出的 id 順序是否相同：

💡 實務上：列表排序多半交給資料庫，前端只排手上已有的資料
咖啡店後台的訂單列表如果有分頁，排序要放在 API 的 ORDER BY：前端只拿到第一頁，在前端排只會把這 20 筆排好，不是全部訂單裡金額最高的。前端 sort 適合資料已經全部在手上的情況，例如購物車、一張菜單、幾十筆的下拉選單，這課的包廂預約一天幾十筆也屬於這種。不管在哪裡排，資深工程師都會在最後補一個唯一的欄位（例如 id）當最後的比較條件：金額相同的訂單順序才固定，翻頁時才不會同一筆出現兩次或漏掉。排中文名字用 localeCompare，並先跟 PM 確認使用者期待的是哪一種順序（例如依注音還是筆畫）。

到這裡，比較函式已經能把預約和訂單都排對了。但排序這個動作本身還有兩件事要知道：它改到了誰的陣列，以及它花了多少時間。

排序會改到誰的資料、花多少成本？

先看第一件事。sort 是原地排序：它不建新陣列，直接改動傳進來的那個陣列，回傳的也是同一個陣列。所以寫了 const sorted = prices.sort(…) 之後，prices 本身也被排了，sorted 和 prices 指向同一個陣列。執行下面兩段，看原陣列有沒有被改、=== 的結果：

這在這課的任務裡會出什麼事？產生報表的函式拿到的預約陣列是預約系統的資料，不是自己建的。如果在函式裡用 sort，報表是算對了，但呼叫的人手上的預約清單也被偷偷換了順序，原本「依建立先後」的意義就沒了。呼叫的人不知道自己的資料被改，這類 bug 很難查，因為出錯的地方和改資料的地方離得很遠。

不想改到原陣列有兩個寫法：用 toSorted 回傳新陣列，或先複製再排 [...arr].sort(…)。這門課的輸入型別是 readonly number[] 這類唯讀陣列，TypeScript 會在你寫 prices.sort 時就報錯（唯讀陣列型別上沒有 sort 方法），toSorted 則可以用。

💡 實務上：在 React／Vue 的狀態上直接 sort，是常見的畫面 bug 來源
商品列表的「依價格排序」按鈕，如果寫成 items.sort(…)，改到的是 props 或 store 裡的同一個陣列：排完再 setItems(items)，React 看到還是同一個陣列參考，會略過重新渲染；共用這份資料的其他元件，順序也被偷偷改掉。改用上面的 toSorted，或把排序後的結果用 useMemo／computed 算出來，原始資料保持不動。Code review 時看到 .sort( 作用在不是自己建立的陣列上，值得停下來問一句。

先排序值得嗎？O(n log n) 換到什麼

第二件事是成本。內建排序是 O(n log n)：比 O(n) 的「走一遍」貴，但比 O(n²) 的「兩兩比較」便宜很多。n 是 1 萬筆時，n² 是 1 億，n log n 大約只有 13 萬多。這課的報表從 O(n²) 的暴力解變快，靠的就是付出這個 O(n log n)，換到「重疊的預約排在隔壁」。

所以「先排序」不是免費的，判斷值不值得，要看排完之後問題有沒有變簡單。常見的幾種：

可以用雙指標從兩端往中間走第 7 課的兩數和、三數和

反過來有兩種情況不該排序。題目要回傳原本的索引時，排序會把位置打亂，第 5 課的 Two Sum 就是這樣。資料已經排好時，不要再排一次，直接利用它的順序，O(n log n) 就省下來了。

第二種情況馬上就會遇到：包廂的預約其實有兩個來源，而且兩邊各自已經排好了。

兩份已排好的預約怎麼併成一份？

包廂的預約一部分是客人在櫃台登記的，一部分是線上預約的，兩個系統各自匯出一份已經依開始時間排好的清單。報表要的是一份依開始時間排好的完整清單。最直覺的寫法是接起來再排序：[...a, ...b].sort((x, y) => x[0] - y[0])，O((m + n) log(m + n))，m、n 是兩份的筆數，而且很多人在這裡又忘了比較函式。但上一節說過，資料已經排好時不該再排一次。

想像兩疊由小到大疊好的號碼牌，每次只看兩疊最上面那一張，拿比較小的放進結果，再看新露出來的那張。因為每一疊都是排好的，最上面那張就是那一疊裡最小的，兩疊最上面比較小的那張，就是剩下所有牌裡最小的，放進結果一定不會錯。

寫成程式就是第 7 課的雙指標，只是兩個指標分別走在兩個陣列上：i 指向 a 下一個要看的、j 指向 b 下一個要看的。每一步一定有一個指標前進，總共 m + n 步，O(m + n)。為了讓指標的移動看得清楚，下面只取每筆預約的開始時間。執行後逐列看 i、j 和每一步拿走的數字：

有兩個地方要看懂。第一，迴圈條件是 i < a.length || j < b.length：只要還有一邊沒用完就繼續，另一邊用完時，takeA 的判斷會自動只拿還有的那一邊。第二，相等時拿 a（<=），這讓 a 的元素在相等時排在前面，結果是穩定的。這個步驟叫合併（merge），它也是一種排序演算法的核心，見課末「補充與查表」。

這個寫法要另外開一個 out 陣列。如果規定不能開新陣列、只能把 b 併進 a 本身呢？

原地合併：從後面開始放

面試的經典版本（LeetCode 88，練習 2 用取餐號碼出這題）多了一個限制：不能開新陣列，要原地修改（第 3 課）。a 的長度是 m + n，前 m 格是資料、後 n 格是空位（填 0），要把 b 合併進 a 本身。實務上多半直接開新陣列，這個限制練的是「寫入位置會不會蓋到還沒讀的資料」這種判斷，在處理大陣列、要省記憶體時會用到。

如果照上面從前面開始放，放進 a[0] 的可能是 b 的元素，就把 a[0] 原本的資料蓋掉了，而它還沒被比較過。解法是反過來，從後面放大的：三個指標 i = m − 1（a 的最後一筆資料）、j = n − 1（b 的最後一個）、k = m + n − 1（下一個要寫的位置）。每次比較 a[i] 和 b[j]，把比較大的放到 a[k]，然後往前移。

為什麼不會蓋到還沒處理的資料？a 裡還沒處理的有 i + 1 個、b 還有 j + 1 個，下一個要寫的位置 k = i + j + 1。只要 b 還沒用完（j ≥ 0），k 就在 i 的右邊，寫進去的格子是空位或已經搬走的元素。執行後逐列看 k 怎麼往前、a 怎麼從右邊被填滿：

迴圈條件只寫 j >= 0：b 用完就可以停了，a 剩下的元素本來就在 a 的前面、而且已經排好，留在原位就是正確的位置。反過來，a 先用完（i < 0）時，b 剩下的每一個都還要搬進來，所以判斷 fromA 時要先檢查 i >= 0，否則會去讀不存在的 a[−1]，拿到 undefined，程式對不對就變成靠比較結果剛好是 false 的巧合。

現在報表手上有一份依開始時間排好的完整預約清單。但時間疊在一起的預約還是分開的好幾筆，店長要的是「實際占用的時段」，下一步就是把它們合併。

重疊的預約怎麼合併？

先把要處理的東西講精確。每筆預約有開始和結束兩個時間點，這種「從某個點到某個點」的範圍叫做區間（interval），寫成 [開始, 結束]。兩個區間有共同的部分，就叫重疊（overlap），例如 [9, 11] 和 [10, 13] 共同占用 10 點到 11 點。合併重疊的區間，就是把它們換成一段涵蓋全部的區間：[9, 13]。

動手之前要先問清楚一件事：相接算不算重疊？[9, 11] 和 [11, 13] 沒有共同的時間，但包廂從 9 點連續占用到 13 點。這一課約定相接也要合併，得到 [9, 13]。不同的題目規定不同，例如會議室題常把相接當成不衝突（11 點結束的會議和 11 點開始的會議可以排在同一間）。這是需求的問題，不是程式的問題：面試時要問出口，寫程式時這只差一個 < 或 <=。

暴力解慢在哪，排序後為什麼只要比最後一段

開場提過的暴力解是：任兩個都檢查，重疊就合併成一個，然後重來，直到一整輪都沒有可以合併的。光一輪就是 O(n²)，而且合併一次可能讓新的區間又跟別的重疊，要跑好幾輪。它慢的原因是：每一筆都不知道哪些預約可能跟它重疊，只好全部比一遍。

排序解決的就是這件事。先依開始時間排序之後，從左走到右，手上拿著「目前合併中的區間」（也就是結果裡的最後一段），每看到下一筆預約，只有兩種情況：

  • 下一筆的開始 ≤ 目前的結束：重疊或相接，併進目前這段。結束時間改成兩者較大的。
  • 下一筆的開始 > 目前的結束：中間有空檔，目前這段定案，下一筆變成新的「目前」。

為什麼只要跟最後一段比，不用回頭看前面那些段？因為排過序：結果裡前面那些段在定案時，都已經跟它後面的區間隔著空檔，它們的結束都比最後一段的開始還早；之後的預約開始得更晚，更不可能跟它們重疊。能跟下一筆重疊的，只剩最後一段。下圖是開場那四筆排序後的樣子：

這段程式有三個地方各對應一個常見錯誤。第一，結束要取較大的：[10, 13] 之後遇到 [11, 12]，如果直接把結束改成 12，包廂就少算了一小時。[11, 12] 被完全包含在目前這段裡，被包含的區間不能縮短目前的結束，所以用 Math.max。

第二，排序一定要給比較函式：第一節看過，預設排序會把 [10, 13] 當成字串 '10,13'，排到 '9,11' 前面，「只跟最後一段比」的前提就不成立了。這裡寫 (x, y) => x[0] - y[0]，依每筆的開始時間排。

第三，放進結果的要是新陣列：merged.push([start, end]) 建了一個新的 [開始, 結束] 陣列。如果把輸入的那一筆區間直接放進去，後面 last[1] = … 改結束時間時，改到的就是預約系統的資料，跟上一節 sort 改到原陣列是同一種 bug。

插入一筆新預約

報表產生之後，客人又打電話來新增一筆預約。這時手上的時段已經依開始時間排好，而且互不重疊。可以把新的這筆放進去再整個合併一次，但那要重新排序，O(n log n)；前面說過資料已經排好時不該再排，一次走完 O(n) 就夠。

排好又不重疊的時段，相對於新預約只會落在三個位置：完全在它左邊、跟它重疊或相接、完全在它右邊，而且這三群在陣列裡是連續的三段。所以從左走到右，分三段處理：

  1. 結束時間 < 新預約開始的：完全在左邊，原樣複製進結果。
  2. 開始時間 ≤ 新預約結束的：跟新預約重疊或相接，把它們併進新預約（開始取較小、結束取較大）。新預約可能很長，一次蓋過好幾段，所以這一段要用迴圈，不能只併一筆。
  3. 放入合併後的新預約，剩下的原樣複製。

第 1 段用 <、第 2 段用 <=，就是「相接也合併」的約定落到程式上的樣子：結束時間剛好等於新預約開始的那一段，不算「完全在左邊」，要進第 2 段被合併。練習 4 就是這一題。

💡 實務上：預約、排班、行事曆都在處理區間
包廂預約、店員排班、Google 日曆的「忙碌時段」、統計一天實際營業了幾小時，背後都是區間的重疊與合併。實務上時間多半統一存成 UTC 時間戳，顯示時才轉成當地時間，而且常用「含開始、不含結束」的約定，讓 10:00–11:00 和 11:00–12:00 剛好不衝突，這個約定要跟 PM 和後端講好，前後端寫成一樣。前端檢查衝突只是給使用者即時提示；兩個客人同時按下預約，真正擋住重複預約的必須是後端的交易或資料庫約束。

合併與插入都寫完了。交給店長之前，還要確認幾種特殊的輸入不會讓報表出錯，並算清楚整體的成本。

交出報表前要測哪些輸入？邊界與複雜度

邊界情況是指資料量或形狀落在極端的輸入：一筆都沒有、只有一筆、全部重疊、全部不重疊。這些輸入平常的測試資料不會出現，卻最容易讓程式出錯。用上一節的合併程式逐一想一遍：

輸入合併重疊的結果
[][]（迴圈不跑，merged.at(-1) 是 undefined）
只有一筆原樣一筆（但是新陣列）
全部重疊一筆，結束是所有結束裡最大的
全部有空檔原本的每一筆，依開始時間排好
[[1, 10], [2, 3]][[1, 10]]，被包含的不能把結束改小
[[1, 3], [3, 5]][[1, 5]]（這一課的約定）

空陣列不用特別寫 if：第一筆進來時 merged.at(-1) 是 undefined，條件不成立，直接開始新的一段，所以同一段程式就能處理。有些寫法會先把第一筆拿出來當「目前」，就得自己處理空陣列，而且容易忘了在迴圈結束後把最後一段放進結果。

複雜度：合併重疊的報表是排序 O(n log n) 加上走一遍 O(n)，加起來是 O(n log n)，由排序主導。額外空間是排序的副本加上結果，O(n)。如果輸入已經排好（像插入一筆新預約那題），就省下排序，只要 O(n)。

合併兩份已排好的清單是 O(m + n)；原地版本的額外空間是 O(1)，只有三個指標。整條流程從 O(n²) 的兩兩比較，變成一次排序加幾次從左走到右。

補充與查表

預設排序比的是什麼

沒給比較函式時，sort 把元素轉成字串後，比的是字串的 UTF-16 編碼單位。只有數字和負號的字串，結果就是從第一個字元比起、像查字典那樣的順序；中文、大小寫字母混在一起時，順序就是編碼的順序，不是使用者以為的順序，所以排給人看的字串要用 localeCompare。

穩定排序與 toSorted 的版本

從 ES2019 起，規格要求 sort 一定是穩定的（V8 從 7.0、也就是 Chrome 70 起改用 TimSort 達成）。規格沒有規定用哪一種排序演算法，V8 用的 TimSort 是 O(n log n)。toSorted 是 ES2023 加入的。

合併排序

「合併兩個已排序的陣列」這一步，就是合併排序（merge sort）的核心：把陣列切成兩半、各自排好，再用合併這一步合起來，整體是 O(n log n)。這課只需要會合併這一步。

練習

傳進來的唯讀陣列與區間都被凍結了，直接 sort 或修改會判錯。練習 2、3 有大資料量的計時測試：O(n²) 的寫法會因為太慢判錯。

練習 1：寫 sortOrders(orders)：回傳新陣列，依金額 total 由小到大；金額相同時，依時間 time 由早到晚。不能改到傳進來的陣列。

練習 2：寫 mergeTickets(a, m, b, n)：a 的前 m 個和 b 的 n 個都是由小到大的取餐號碼（可能有負數、重複）；a 的長度是 m + n，後面 n 格是 0，當作空位。把 b 原地合併進 a，結果由小到大；直接修改傳進來的 a，回傳 void。指標已經宣告好，補完迴圈。要 O(m + n)：測試會跑 m = n = 100,000，每次插入都 splice 的寫法會太慢。對應 LeetCode 88. Merge Sorted Array。

練習 3：寫 mergeBookings(bookings)：每筆座位預約是 [開始, 結束]（整數小時，開始 < 結束，沒有排序）。把重疊或相接（前一段的結束等於下一段的開始）的預約合併，回傳依開始時間排序的新陣列；不能改到傳進來的陣列和裡面的每一筆。要 O(n log n)：測試會跑 16,000 筆，兩兩比較的寫法會太慢。對應 LeetCode 56. Merge Intervals。

練習 4（進階）：寫 insertBooking(bookings, extra)：bookings 已經依開始時間排序，而且互不重疊、也不相接；插入一筆新預約 extra，把跟它重疊或相接的合併，回傳依開始時間排序的新陣列。不能改到傳進來的資料。照課文的三段寫，一次走完 O(n)。對應 LeetCode 57. Insert Interval。

練習 5：[10, 9, 1].sort() 的結果是什麼？

✓ 沒給比較函式時，元素先轉成字串再比，'10' 的第一個字元 '1' 比 '9' 小，所以 10 排在 9 前面。a 是給了 (a, b) => a - b 才會得到的結果。c 錯：它會排，只是用字串順序排。

練習 6：在 JavaScript 裡寫 prices.sort((a, b) => a > b)，能正確由小到大排序嗎？

✓ 比較函式要回傳負數、0、正數：負數表示 a 在前。true 變成 1、false 變成 0，「a 在前」這個答案永遠不會出現，排序演算法拿到的資訊是錯的。a 錯：比較函式不是在回答「要不要交換」。b 錯：問題是結果不對，不是速度。數字由小到大要寫 (a, b) => a - b；TypeScript 會直接擋下回傳 boolean 的寫法。

練習 7：2026 年的瀏覽器與 Node 裡，sort 是穩定排序嗎？

✓ ES2019 起 sort 必須穩定，V8 從 7.0（Chrome 70）起用 TimSort。b 是 ES2019 以前的做法，現在不需要了。c 錯：toSorted 和 sort 的排序規則一樣，差別只在回傳新陣列、不改原陣列。

練習 8：原地合併兩個已排序的陣列（a 的後面是空位），為什麼要從後面開始放？

✓ 從後面放時，寫入位置 k = i + j + 1，只要 b 還沒用完，k 就在 i 的右邊，不會蓋到 a 還沒處理的資料。a 錯：兩種方向都是 O(m + n)，差別在正確性。從前面放在 b 的元素比較小時就會出錯。c 錯：從後面放大的只是因為空位在後面，跟元素重不重要無關。

常見錯誤

  • 用預設 sort() 排數字：預設是字串順序，[10, 9, 1] 會變成 [1, 10, 9]，而且不會報錯。一定要寫 (a, b) => a - b；排區間或物件時也一樣，要自己指定欄位。
  • 比較函式回傳 boolean：比較函式回答的是「誰在前」，不是「要不要交換」，要回傳負數、0、正數。多個欄位用 || 串起來，字串用 localeCompare。
  • 忘了 sort 會修改原陣列：別人傳進來的陣列被改了順序，例如預約系統的清單。用 toSorted 或先複製再排。
  • 資料已經排好還接起來重排：兩份已排序的清單用兩個指標合併，O(m + n)，不用 O((m + n) log(m + n))。
  • 原地合併從前面開始放：會蓋掉 a 還沒比較的資料。從後面放比較大的；迴圈條件寫 j >= 0，a 用完時把 b 剩下的搬完。
  • 合併區間沒先排序：一次走完只跟最後一段比，前提是已經依開始時間排好。
  • 合併時結束直接用下一段的結束：被包含的區間會把結束改小。要用 Math.max。
  • 沒問清楚相接算不算重疊：[1, 3] 和 [3, 5] 的答案取決於題目，寫成程式只差 < 和 <=。
  • 把輸入的區間直接放進結果再修改：改到了呼叫者的資料。放進結果時建新的 [開始, 結束]。

小結

  • 包廂占用報表的做法：先依開始時間排序，讓重疊的預約排在隔壁，再從左走到右一次合併，從 O(n²) 降到 O(n log n)。
  • sort() 沒給比較函式時依字串排序；比較函式回傳負數表示 a 在前、正數表示 b 在前、0 表示相等。數字寫 a - b，多個欄位用 || 串起來。排序是穩定的，相等的元素保持原本的先後。
  • sort 原地修改並回傳同一個陣列，會改到呼叫者的資料；toSorted 回傳新陣列。內建排序 O(n log n)，值不值得付，看排完之後問題有沒有變簡單；要原本的索引、或資料已經排好時就不要排。
  • 合併兩個已排序的陣列：兩個指標每次拿比較小的，O(m + n)；空位在後面時從後往前放大的，O(1) 額外空間。
  • 合併區間：只跟最後一段比，重疊就把結束改成較大的，放進結果時建新陣列。已排好的時段插入一筆新的，分三段一次走完，O(n)。相接算不算重疊要先問清楚。
