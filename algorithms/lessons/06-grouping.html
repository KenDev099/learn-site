階段 2：雜湊表 · 第 6 課

分組與計數：選對 key

午餐尖峰時，吧台一次收到十幾張出餐單。其中一張點了拿鐵、美式、可頌，另一張點了可頌、拿鐵、美式：點的東西一模一樣，只是點餐順序不同。店長希望系統把這種單排在一起，吧台就能一次做好幾份，不用一張一張看。這一課要寫出這個功能。

「把元素依某個標準放進不同的清單」這種操作叫做分組（group by）。決定一個元素放進哪個清單的那個值，叫做鍵（key），跟第 4 課 Map 的鍵是同一個東西：兩張單算出同一個鍵，就進同一組。前兩課你已經會用 Map 查「有沒有」「幾次」「在哪裡」，分組只是把 Map 的值換成一個陣列。

真正難的是鍵怎麼算。鍵算錯了，程式照樣跑得完、不會報錯，只是把不該合併的單合併了（吧台做錯飲料），或該合併的沒合併（功能形同沒做）。所以這課的主線是：怎麼從一張單算出鍵、怎麼檢查鍵對不對。最後用同一個想法「查表前先想清楚要查什麼」，解一題面試常見的題目：顧客最長連續來店幾天。

這課的路線：
  1. 分組怎麼寫：先用鍵已經現成的菜單分類練手，Map 的值換成陣列，第一次遇到某個鍵時要先放一個新陣列。
  2. 順序不同的出餐單怎麼算出同一個鍵：從暴力解找出重複的工作，改成算「簽名」查 Map（開場問題的答案）。
  3. 鍵選錯會怎樣：三個看起來合理、卻會把不同的單合併的鍵，以及選鍵的檢查清單。
  4. 顧客最長連續來店幾天：要查的變成「前一天、後一天有沒有來」，先用排序做到 O(n log n)，再用 Set 做到 O(n)。
  5. 題目沒說用哪一招時：從暴力解的內迴圈在問什麼，判斷用 Set、頻率表還是 Map 到清單。
這課會用到：
  • 第 4 課的 Map、Set 與頻率表：Set 記「有沒有」，頻率表用 Map 記每個值出現幾次；陣列不能直接當鍵，要先組成字串。
  • 第 2 課的複雜度：sort 是 O(n log n)，比 O(n) 慢、比 O(n²) 快得多。

分組怎麼寫？先用現成的菜單分類練一次

出餐單的鍵要自己算，這一步留到下一節。先把「分組」這個動作本身練熟，用一個鍵已經寫在資料裡的例子：菜單上每個品項都有 category 欄位，依分類把品項名稱分好，就是後台菜單頁「咖啡／茶／甜點」分欄顯示要的資料。

做法是走一遍菜單，對每個品項做兩件事：用它的分類當鍵，去 Map 拿這個分類的清單；再把品項名稱加進清單。唯一要小心的是第一次遇到某個分類時，Map 裡還沒有清單，get 會回傳 undefined，這時要先放一個只有自己的新陣列進去。執行後看每個分類底下有哪些名稱，以及分類出現的順序。

輸出有兩個順序要確認。分類的順序是咖啡、茶、甜點，也就是每個分類第一次出現的順序，因為 Map 依插入順序走訪（第 4 課）。組內的名稱也保持菜單原本的順序，因為 push 一律加在尾端。面試題常會規定這兩個順序，寫之前先確認。

如果省掉 get、每次都直接寫 groups.set(item.category, [item.name])，程式一樣不會報錯，但每次 set 都會用一個新陣列蓋掉舊的，每組最後只剩一個品項。練習 1 的錯誤答案裡就有這種寫法。

能不能一行寫完？Map.groupBy

這個迴圈太常見，ES2024 把它做成了內建函式 Map.groupBy(陣列, 算鍵的函式)。你只要告訴它「從一個元素怎麼算出鍵」，上面的 get、判斷、set、push 它都會做。本站的編輯器設定是 ES2024，可以直接用。執行後看兩件事：組內放的是什麼，以及同家族的 Object.groupBy 回傳的是不是 Map。

第一件事：組內放的是整個品項物件，不是名稱。手寫的迴圈 push 的是 item.name，但 groupBy 不知道你要哪個欄位，要名稱就得對每組再 map 一次。第二件事：Object.groupBy 用法一樣，回傳的卻是一個物件而不是 Map，鍵也只能是字串或 Symbol。題目要求回傳 Map 時用錯了，型別就不符（練習 1 會測）。最後兩行印出的「原型是 null」是什麼意思、兩者怎麼選，整理在課末「補充與查表」。

不管用迴圈還是 groupBy，它們都只負責「同一個鍵的放在一起」，鍵本身怎麼算，它們幫不上忙。菜單的鍵是現成的 category，出餐單卻沒有這種欄位：'LAC' 和 'CAL' 要放在一起，得先從單的內容算出一個共同的鍵，這是下一節的事。

💡 實務上：分組在前端還是資料庫做，先看資料量
咖啡店後台的「訂單依狀態分欄」（待製作／製作中／已完成）、報表的「依日期分組」，前端拿到一頁資料後用 Map.groupBy 分一下就好。但如果要的是「全部訂單依分類加總」，不要把幾萬筆撈到前端再分，交給資料庫的 GROUP BY（SQL 的分組語法），只回傳加總後的幾列。用內建的 groupBy 前，先確認專案要支援的瀏覽器與 Node 版本有沒有這兩個函式。另一個常見坑：Map 直接 JSON.stringify 只會得到 {}，API 要回傳分組結果時，先用 Object.fromEntries 轉成物件。

順序不同的出餐單，怎麼算出同一個鍵？

回到開場的出餐單。先把題目講精確：出餐單用大寫字母代表品項（L 拿鐵、A 美式、C 可頌…），一張單是一個字串，例如 'LAC'。把品項與數量完全相同的單分成一組，點餐順序不管：'LAC' 和 'CAL' 同組，'AL' 和 'LA' 同組；'AAL'（兩杯美式、一杯拿鐵）和 'AL' 數量不同，不同組。

照第 1 課的步驟，動手前先確認輸出：回傳 string[][]，每個內層陣列是一組；組的順序依每組第一張單出現的順序；組內依原本順序；空字串也是一張單（什麼都沒點），自成一組。這些規則跟上一節的菜單分組一樣，差別只在鍵不再是現成的欄位。

暴力解：每張單去跟每一組比

還不知道鍵怎麼算的時候，最直接的做法是：手上維護一份「目前已經有的組」，每來一張單，就拿它去跟每一組的第一張單比「品項是否相同」，比到了就加入那一組，全部比不到就開一個新組。「兩張單品項是否相同」第 4 課練習 3 寫過（sameTicket：用頻率表，一張單的字母加一、另一張減一，最後全部歸零就相同），長度 k 的單比一次是 O(k)。

成本出在「跟每一組比」。n 張單如果幾乎都不一樣，組數也會接近 n，每張單都要跟前面所有的組比一次，總共約 n² / 2 次比較，每次 O(k)，合計 O(n² × k)。吧台一天幾百張單還感覺不到，練習 2 會用 12,000 張單計時，這個寫法就過不了。

重複的工作在哪裡？每張單都在問「我屬於哪一組」

第 5 課的方法在這裡一樣適用：看內迴圈一直在問什麼。這裡的內迴圈對每一組問「你跟我是不是同一組」，一組一組問下去。如果能只看一張單自己就算出一個字串，而且同一組的單一定算出同一個字串、不同組的單一定算出不同的字串，那就不必一組一組問了：把這個字串當 Map 的鍵，查一次就知道該進哪一組，問題變回第 4 課的查表。

這種「代表一群被視為相同的東西」的鍵，叫做簽名（signature）。名字取得很貼切：同一個人每次簽出來都一樣，不同的人簽不出同一個。下圖是整個流程：每張單先算出自己的簽名，再用簽名去 Map 找自己那一組。

簽名怎麼算？排序或計數

要讓 'LAC' 和 'CAL' 算出同一個字串，就要把「點餐順序」這個資訊消掉，只留下「有哪些品項、各幾個」。常見的做法有兩種：

  • 把字母排序後串起來：[...t].sort().join('')。不管原本順序如何，排序後都是同一個順序，'CAL' 和 'LAC' 都變成 'ACL'。反過來，品項或數量不同的單，排序後的字串一定不同，因為每個字母都還在、個數沒變。這裡用預設排序是對的：預設排序會把元素轉成字串、依 UTF-16 code unit 的大小比較，而每個元素本來就是一個大寫字母，比出來就是字母順序。排數字時預設排序就不對了，第 4 節會看到。
  • 數每個字母出現幾次：開一個 26 格的陣列，第 0 格記 A 出現幾次、第 1 格記 B 出現幾次……，最後用 '#' 把 26 個數字串成一個字串。要從字母找到它的格子，用 t.charCodeAt(i)：它回傳字串第 i 個字元的編碼，'A' 是 65、'B' 是 66，所以 charCodeAt(i) - 65 就是 0～25 的格子編號。'CAL' 的 A、C、L 各 1 次，簽名是 '1#0#1#…#1#…'。中間的 '#' 不能省，原因下一節會看到。

這就是開場問題的答案：每張單算一次簽名、查一次 Map，就知道該跟誰排在一起。複雜度這樣算：

  • 排序簽名：每張單排序 O(k log k)，n 張單共 O(n × k log k)。
  • 計數簽名：每張單走一遍 O(k)，再串 26 格，n 張單共 O(n × k)。
  • 兩種都要查 Map，平均 O(1)；空間 O(n × k)，因為每張單都存進某一組。

出餐單很短時兩者差不多，排序版好寫好讀；單很長、字母種類固定時，計數版比較快。面試時說出這個取捨就夠了。計數版的 26 格只適用於 A～Z，字串來自使用者輸入（中文、emoji）時怎麼改，見課末「補充與查表」。

簽名能用，前提是它真的做到「同組必同、不同組必不同」。前半句比較容易檢查，後半句才是常出事的地方：下一節看幾個看起來也合理、卻違反後半句的鍵。

鍵選錯會怎樣？程式不報錯，結果默默錯

上一節說簽名要滿足兩個條件。違反前半句（同一組的單算出不同的鍵）時容易發現：例如直接拿原字串當鍵，'LAC' 和 'CAL' 各成一組，測試一跑就看得出沒合併。危險的是違反後半句，把不同的單算成同一個鍵。下面三個鍵都有人寫過，乍看都合理。執行後看每一行印出的兩個鍵是否相同。

三個都把不同的單算成了同一個鍵，逐一看原因：

  1. 用 Set：Set 只記「有沒有」，不記「幾次」。'AAB'（兩杯 A、一杯 B）和 'AB' 去重後都是 'AB'，吧台會把兩張單當成一樣的來做。
  2. 字元編碼加總：A 是 65、D 是 68，加起來 133；B 是 66、C 是 67，加起來也是 133。加總把「有哪幾個數」壓成一個數，不同的組合加出同一個數是必然會發生的。這跟第 4 課迷你雜湊表的碰撞是同一件事：不同的輸入算出同一個值。差別在於雜湊表內部會處理碰撞（在桶裡再用真正的鍵比一次），但你自己設計的分組鍵就是最終答案：Map 只看你給的鍵，沒有人會幫你再比一次原本的單。
  3. 次數直接串起來、沒有分隔符號：A 1 次、B 11 次，串成 '1' + '11' = '111'；A 11 次、B 1 次，串成 '11' + '1' = '111'。次數有一位數也有兩位數，沒有分隔就分不出邊界在哪裡。這就是上一節的計數簽名要用 '#' 串的原因：'1#11' 和 '11#1' 不一樣。

這三種錯有一個共同點：用 'LAC'、'CAL' 這種普通的例子跑，三種鍵都算得對，程式也不會報錯。要抓到它們，只能主動拿「很像但不同」的例子去試。

選鍵的檢查清單

把上面的教訓整理成三個問題，每次設計鍵時都問一遍。前兩個對應簽名的兩個條件；第三個在出餐單裡不會遇到（一張單只有一個字串），但工作上的鍵大多由好幾個欄位組成，所以一起列進來。

  1. 該相同的，鍵一樣嗎？ 'LAC' 和 'CAL' 都要得到同一個鍵。漏了這一條，該合併的沒合併（例如直接用原字串當鍵）。
  2. 該不同的，鍵不一樣嗎？ 找兩個「很像但不同」的例子試：次數不同（'AAB'／'AB'）、加起來一樣（'AD'／'BC'）、數字位數不同（1 與 11）。
  3. 多個欄位串起來時有分隔符號嗎？ 例如要把「同一位顧客點的同一個商品」分成一組：顧客 1 點了商品 23，和顧客 12 點了商品 3，直接串都是 '123'；寫成 `${customerId}|${productId}` 才分得開。分隔符號要選欄位裡不會出現的字元。

到這裡，吧台的分組功能已經完成，而且你知道怎麼檢查它不會默默合併錯。選鍵這件事在後端遠不只出現在分組，下面的實務區塊列出最常見的幾個地方。

💡 實務上：快取鍵、去重鍵、唯一索引，都是在選鍵
這三種東西都在回答「哪些算同一個」。快取鍵少了使用者 ID，A 會看到 B 的購物車，這是資安事故；少了語系，英文使用者會拿到中文頁；多了不必要的欄位（例如時間戳），快取永遠不會命中。資料庫的唯一索引（指定欄位的組合只能出現一次）也是同一件事，選錯欄位不是擋不住重複，就是把合法的資料擋掉。防止重複送單的鍵、會員資料去重的鍵（Email 要先轉小寫、去掉前後空白）也一樣，正規化沒做好，同一個人就會被當成兩個。資深工程師看到新的快取或去重邏輯，第一個問題就是「鍵由哪些欄位組成？有沒有漏掉會讓結果不同的欄位？」，必要時跟 PM 確認業務上什麼算「同一筆」。

換一個問題：顧客最長連續來店幾天？

分組問的是「誰跟我一樣」。店長的下一個需求問的卻是「誰跟我相鄰」：集點卡要辦「連續來店 7 天送一杯」，得先算出每位顧客最長連續來了幾天。這題沒辦法用分組做，因為第 3 天和第 4 天不是「相同」，而是「差 1」，所以要換一份資料。但解題的想法跟前面一樣：先想清楚要查的是什麼。分組時查的是從元素算出來的簽名；這一題要查的是元素旁邊的值：「這一天的前一天、後一天有沒有來？」

題目：一位顧客來店的日子用編號表示（第幾天），可能重複（同一天來兩次）、沒排序、可能有負數（活動開始前的日子）。回傳最長的連續序列（consecutive sequence）長度，也就是數字一個接一個，例如 2、3、4、5。[21, 5, 300, 2, 4, 3, 22] 的答案是 4（2、3、4、5）；空陣列是 0。

先排序再數：O(n log n)

用紙筆算的話，你會先把日子由小到大排好，再從頭往下看：跟前一天差 1 就是連著，連續長度加一；差超過 1 就是斷了，從 1 重新算。排好序之後，「相鄰的天」在陣列裡也剛好排在隔壁，所以走一遍就夠了。

預設排序會把每個元素轉成字串再比較。'10' 的第一個字元 '1' 比 '8'、'9' 小，所以 10 排到最前面；負數 '-1'、'-2'、'-3' 也是逐字元比，順序跟數值大小相反。排數字一定要給比較函式 (a, b) => a - b：它回傳負數代表 a 該排在 b 前面，所以小的數排前面。另外，sort 會直接修改原陣列；輸入不能改時，用 toSorted（ES2023，第 3 課）拿到排好的新陣列，或先複製再 sort。

用 Set 做到 O(n)：只從序列的起點開始數

不排序的話，要知道「x + 1 有沒有來」本來得掃整個陣列，每次 O(n)。第 4 課的 Set 正是用來把這種「有沒有」的查詢變成平均 O(1)：先把所有天數放進 Set，之後對任何一天 x，seen.has(x + 1) 都能立刻回答。有了它，就可以對每一天往上數：x、x + 1、x + 2…，一直數到某一天不在 Set 裡為止，數到的長度就是從 x 開始的連續天數。

直接這樣寫，答案是對的，但會做很多重複的工作。序列 1～5，從 1 往上數 5 次、從 2 數 4 次、從 3 數 3 次……同一段被數了好幾遍。1～n 的序列總共要數 1 + 2 + … + n = n(n + 1)/2 次，又回到 O(n²)。

重複的原因是：從 2 開始數到的那一段，已經包含在從 1 開始的那一段裡，數 2 是白做工。所以只需要從每一段的開頭數。序列起點的定義是「前一天（x − 1）不在 Set 裡」的那一天：它前面沒有連著的天，不可能被包含在更長的一段裡。以 [21, 5, 300, 2, 4, 3, 22] 為例，2 是起點（1 沒來），3、4、5 都不是，直接跳過。下面這格印出每一天被判斷成什麼，最後印出 has 一共呼叫了幾次：

for 裡面有 while，看起來像雙迴圈，但複雜度要看總共執行幾次，不是看有幾層（第 2 課）。while 只在起點執行，而每一天最多只會被它所在那一段的起點往上數到一次，不會再被別的起點數到。所以 for 走 n 次、while 加起來最多 n 次，總共 O(n)。空間 O(n)，用在 Set。重複的天數放進 Set 時自然被去掉了，不需要像排序解那樣特別處理。

注意 for 走的是 seen，不是 days。如果寫成 for (const d of days)，同一個起點在 days 裡出現幾次，就會被往上數幾次：[1, 2, …, 6000] 再加上 6,000 個 1，起點 1 被數 6,001 次、每次走 6,000 步，又回到 O(n²)。練習 3 的計時測試就用這個輸入。

起點檢查到底省了多少，可以直接量。下面用 1～n 的連續天數（倒過來放，順序不影響答案），分別數有、沒有起點檢查時 while 一共跑了幾步：

有起點檢查時工作量跟 n 成正比；沒有時，n 加倍，工作量變成約 4 倍，這是 O(n²) 的樣子（第 2 課）。

這樣這一題就有兩個解：排序解 O(n log n)、Set 解 O(n)。哪一個比較好，要看情況：

O(n) 不一定比較快。Set 要配記憶體、雜湊每個數字；n 不大時，排序解常常一樣快甚至更快，也比較好讀。面試時兩個都說出來：先給排序解，再說 Set 解怎麼做到 O(n)，以及「每個數只被往上數一次」的理由。
💡 實務上：連續天數真正的坑在「哪一天」
集點卡的「連續來店 7 天送一杯」、App 的連續登入獎勵，都是這題。實務上資料是資料庫裡的時間戳記，要先依店家的時區（例如 Asia/Taipei）換成日期，再去重、算連續；直接用 UTC 切日期，台灣早上 8 點以前的來店會被算到前一天。單一顧客的來店紀錄通常不多，排序解就夠了，好讀比 O(n) 重要。如果每次打開頁面都要顯示，常見做法是每次來店時更新「目前連續天數」存起來，而不是每次重算整段歷史。

題目沒說用哪一招時，怎麼判斷？

這一課的兩題，加上第 4、5 課的題目，走的其實是同一條路：先寫暴力解，找出內迴圈重複在做的工作，再換成查表。差別只在重複的工作在問什麼，而問的東西決定了用哪一種表：

重複的工作在問用例子
「這個看過沒？」Set有沒有重複的訂單編號、兩份名單的交集、連續天數
「這個出現幾次？」Map 計數（頻率表）兩張單品項是否相同、只出現一次的品項
「這個在哪裡？」Map 記索引（第 5 課）Two Sum、k 筆之內重複
「這些算不算同一組？」Map 到清單，鍵是簽名品項相同的出餐單、依分類分組

表的最後一列就是這一課的出餐單分組；連續天數問的是「x − 1、x + 1 來過沒」，所以落在第一列的 Set。練習 4、5 不會告訴你用哪一招：先別急著想技巧，照步驟寫出暴力解，看內迴圈在問哪一種問題，再對照這張表。

補充與查表

Map.groupBy 與 Object.groupBy 的差別

第 1 節那格最後兩行印出 Object.groupBy 結果的原型。查表用，不用背：

Map.groupByObject.groupBy
回傳Map原型是 null 的物件（null-prototype object）
鍵任何值，用 SameValueZero 比較（物件看參考）只能是字串或 Symbol，數字會變成字串
TypeScript 型別Map<K, T[]>Partial<Record<K, T[]>>：每一組都可能是 undefined
組內放的整個元素，不是你想要的某個欄位；要名稱就再 map 一次

原型是 null 的物件沒有 toString、constructor 這些繼承來的屬性，所以第 4 課那個「鍵剛好叫 constructor」的問題不會發生。代價是它跟一般物件 {} 的原型不同，用比較原型的深度比對（例如本站的 assert.deepEqual、Node 的 assert.deepStrictEqual）會判定不相等。

怎麼選：要繼續查表、鍵不是字串，用 Map.groupBy；結果要直接變成 JSON 回給前端，Object.groupBy 比較順手。

字串含中文或 emoji 時的簽名

字串來自使用者輸入時（中文、emoji），[...t] 依 code point 切、t.split('') 依 UTF-16 code unit 切，emoji 會被 split 拆成兩半（TypeScript 課第 6 課）。計數版的 26 格也只適用於 A～Z；字元種類不固定時，改用 Map 計數，再把「字元:次數」排序後串起來。

練習

每題的隱藏測試會用固定案例、大量隨機案例比對參考解，練習 2～5 還會用大資料量計時。判分逾時或「花了 … ms」的訊息，代表複雜度不夠，不是電腦太慢。傳進來的陣列都不能修改。

練習 1：寫 groupMenu(items)：依分類把品項名稱分組，回傳 Map<分類, 名稱陣列>。分類依第一次出現的順序，組內依原本順序。可以自己寫迴圈，也可以用 Map.groupBy（記得它組內放的是整個物件）。

練習 2：寫 groupSameItems(tickets)：把品項與數量完全相同的出餐單分在同一組（單由大寫字母 A～Z 組成，可能是空字串）。組的順序依該組第一張單出現的順序，組內依原本順序。測試會用 12,000 張單計時，拿每張單去跟每一組比的寫法會太慢。（對應 LeetCode 49. Group Anagrams）

練習 3：寫 longestStreak(days)：days 是一位顧客來店的日子編號（可能重複、沒排序、可能有負數），回傳最長的連續天數；空陣列回傳 0。測試會用 12,000 個打亂的連續天數計時：O(n) 的 Set 解或 O(n log n) 的排序解都能通過，沒有起點檢查、或起點重複出現時重複往上數的寫法不行。（對應 LeetCode 128. Longest Consecutive Sequence）

練習 4（混合複習）：寫 firstSingleItem(ticket)：出餐單是一串字元，回傳第一個「在整張單只出現一次」的品項的索引（不是字元）；沒有就回傳 -1（這題沿用經典題的規定，不是 null）。'LALC' → 1（A）。測試會用好幾千個不同字元的長字串計時。（對應 LeetCode 387. First Unique Character in a String）

練習 5（混合複習）：寫 commonFavorites(a, b)：兩位顧客各自點過的商品編號（可能重複），回傳兩人都點過的商品編號，不重複，依它在 a 中第一次出現的順序。a = [3, 1, 3, 2]、b = [2, 3, 3] → [3, 2]。測試會用兩個各 60,000 筆、幾乎沒有交集的陣列，和兩個各 80,000 筆、完全相同的陣列計時。（對應 LeetCode 349. Intersection of Two Arrays）

練習 6：用「字母的 Set 排序後串起來」當出餐單的分組鍵，'AAB' 和 'AB' 會怎樣？

✓ c。Set 只記「有沒有」，不記「幾次」，'AAB' 與 'AB' 的鍵都是 'AB'。程式不會報錯（b 錯），Map 只看你給它的鍵，不知道原本的字串（a、d 錯）。要保留次數，用排序後的完整字串，或用分隔符號串起來的計數。

練習 7：找最長連續天數時，寫 [...days].sort() 再往下數。這個做法有什麼問題？

✓ b。預設排序把數字轉成字串比較，'10' 排在 '8' 前面；排數字要寫 (a, b) => a - b。排序本身是 O(n log n)，不是 O(n)（a 錯）。[...days] 已經複製了，不會改到原陣列（c 錯）；負數不會出錯，只是也被當成字串排錯順序（d 錯）。

練習 8：Set 解法裡，for 迴圈裡面有一個 while 迴圈。它的時間複雜度是？

✓ a。複雜度要看「總共」執行幾次，不是看有幾層：非起點的數直接跳過，起點往上數時經過的數不會再被別的起點數到，所以 while 總共最多 n 次（b 錯）。Set 不排序，平均 O(1) 查詢（c 錯）。has 是 O(1)，但要呼叫約 2n 次，整體是 O(n)（d 錯）。

常見錯誤

  • 分組時每次都 set(key, [item])：前面放進去的被蓋掉，每組只剩最後一個。先 get，沒有才建新陣列。
  • 把 Object.groupBy 的結果當成 Map，或拿去 deepEqual 比一般物件：它回傳的是原型為 null 的物件，不是 Map，跟 {} 也不相等；要 Map 就用 Map.groupBy，要比內容就先轉成 Object.entries。
  • 鍵會把不同的東西合併：Set 去掉次數、加總會碰撞。用排序後的字串，或有分隔符號的計數；寫完拿「很像但不同」的例子試一次。
  • 多個欄位串接沒有分隔符號：'1' + '23' 與 '12' + '3' 都是 '123'。寫成 `${a}|${b}`，分隔符號選欄位裡不會出現的字元。
  • 預設排序數字：一定要給 (a, b) => a - b；輸入不能改時用 toSorted 或先複製。
  • 數連續時沒有只從起點開始：1～n 的序列會被數 n(n + 1)/2 次，退化成 O(n²)。for 也要走去重後的 Set，走 days 的話，重複出現的起點會被重複往上數。
  • 迴圈裡呼叫 includes、indexOf、lastIndexOf：每一次都是 O(n) 的掃描（第 2 課），整體 O(n²)；用 result.includes(x) 檢查「結果裡有沒有」也一樣。內建方法是原生程式碼，資料小時看不出來，資料一大就慢；先把「有沒有」「幾次」算進 Set 或 Map。

小結

  • 分組就是 Map 的值換成陣列：先 get，沒有就放新陣列。ES2024 的 Map.groupBy 一行做到同一件事，回傳 Map；Object.groupBy 回傳原型是 null 的物件。兩者組內都放整個元素，鍵怎麼算還是你的事。
  • 順序不同的出餐單要進同一組，就從每張單算出簽名當鍵：同一組必須算出同一個簽名，不同組必須算出不同的簽名。排序後的字串、用分隔符號串起來的計數都可以；每張單算一次、查一次 Map，取代暴力解的 O(n² × k)。
  • 鍵選錯程式不會報錯：Set 去掉次數、加總會碰撞、沒有分隔符號的串接分不出邊界。設計鍵時用檢查清單，拿「很像但不同」的例子試。
  • 最長連續天數要查的是「旁邊那一天」：排序解 O(n log n)（數字要給比較函式、重複的天要跳過）；Set 解只從起點（x − 1 不在 Set 裡）往上數，每個數最多被數一次，O(n)。
  • 不提示技巧的題目，先寫暴力解，看內迴圈在問「有沒有」（Set）、「幾次」（頻率表）、「在哪裡」（Map 記索引）還是「同一組嗎」（Map 到清單）。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 9：這段程式替訂單編號去重。n 筆編號幾乎都不重複時，時間與額外空間是？

const result: string[] = []
for (const id of ids) {
  if (!result.includes(id)) result.push(id)
}

✓ result 會長到 n 筆，每次 includes 都是 O(n) 的掃描，總共約 n² / 2 次比較。改成迴圈外建一個 Set、迴圈裡用 has，時間 O(n)，空間仍是 O(n)。a 錯在只數迴圈層數：一層迴圈裡呼叫 O(n) 的方法就是 O(n²)，原生程式碼只讓常數變小。（第 4、6 課）

練習 10：orders 有 n 筆、customers 有 m 筆。不算回傳的 rows，這段的時間與額外空間是？

const byId = new Map(customers.map(c => [c.id, c]))
const rows = orders.map(o => ({ ...o, customer: byId.get(o.customerId) }))

✓ 建 Map 走一次 m 筆，每筆訂單 get 平均 O(1)，合計 O(n + m)；Map 多存了 m 筆鍵值，額外空間 O(m)。這就是用空間換時間，面試時兩個都要說。b 錯在 Map 存的雖然是原物件的參考，m 筆項目還是要另外佔記憶體；c 是在迴圈裡寫 customers.find 的版本。（第 4 課）

練習 11：要找兩個不同位置的數，加總等於 target，回傳索引，沒有就回傳 null。下面這段在哪個輸入會答錯？

const seen = new Map<number, number>()
for (let i = 0; i < nums.length; i++) {
  seen.set(nums[i], i)
  const j = seen.get(target - nums[i])
  if (j !== undefined) return [j, i]
}
return null

✓ 先存再查，target 剛好是某個數的兩倍時，查到的是剛存進去的自己：[4, 9, 2] 回傳 [0, 0]，正確答案是 null。把兩行對調成先查再存，Map 裡就只有左邊、別的數。c 不會錯：判斷寫的是 !== undefined，索引 0 和值 0 都照常處理。（第 5 課）

練習 12：價格可以重複，要回傳有幾組 (i, j)、i < j，兩個價格加總剛好等於禮券金額，而且要一次走完。走到價格 x 時，該怎麼做？

✓ 走到 x 時，前面有幾個補數就多幾組，所以 Map 要記次數：[80, 80, 80]、160 依序加 0、1、2，共 3 組。a 最多人選：記索引只回答「有沒有」，每次最多 + 1，這個例子會得到 2。b 去重時就把同價的不同杯丟掉了。（第 5 課）

練習 13：要把「同一位顧客點的同一個商品」分成一組，customerId、productId 都是正整數。哪兩筆訂單會被錯誤地併成一組？

const groups = new Map<string, Order[]>()
for (const o of orders) {
  const key = `${o.customerId}${o.productId}`
  const list = groups.get(key)
  if (list) list.push(o)
  else groups.set(key, [o])
}

✓ 兩個欄位直接串起來，'1' + '23' 和 '12' + '3' 都是 '123'，兩位顧客的訂單併成一組，程式不會報錯。改成 `${o.customerId}|${o.productId}`，分隔符號選欄位裡不會出現的字元。a 不會撞：串起來是 '123' 和 '312'。（第 6 課）

練習 14：這段算最長連續天數，結果是對的。days 是打亂的 1～n、沒有重複時，時間複雜度是？

const set = new Set(days)
let best = 0
for (const x of set) {
  let len = 1
  while (set.has(x + len)) len++
  best = Math.max(best, len)
}

✓ 沒有檢查起點，1 往上數 n 個、2 往上數 n − 1 個……同一段被數很多次，共 n(n + 1) / 2 次。for 裡先加 if (set.has(x - 1)) continue，只從起點往上數，每個數最多被數一次，就是 O(n)。b 錯在只看單次 has 的成本，沒算 while 總共跑幾次。（第 6 課）

練習 15：你寫完 Two Sum 的 Map 解並講完複雜度，面試官追問：「資料多到記憶體放不下 n 筆的 Map，怎麼辦？」比較好的回答是？

✓ Map 是用 O(n) 空間換 O(n) 時間，空間不夠就換回排序：時間變 O(n log n)，雙指標只要 O(1) 額外空間；要回傳原索引時，得把索引跟著一起排。a、b 存的還是 n 筆，空間仍是 O(n)。d 最像實務上的快取做法，但被丟掉的價格再也查不到，會漏掉答案。（第 5 課）
