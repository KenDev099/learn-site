階段 3：陣列技巧 · 第 11 課

前綴和

店長的後台有一頁銷售報表，上面有一個日期區間選單：選「第 l 天到第 r 天」，頁面就顯示這段時間一共賣了幾杯。店長、各分店、排班的同事整天都在切這個選單，一天被查上萬次。現在的寫法是每查一次就從第 l 天一路加到第 r 天，資料一多，頁面就開始卡。

這課從頭到尾都在做這一頁報表背後的計算。先解決「每次查詢都從頭加」的問題：花一次 O(n) 把累計表建好，之後每次查詢只做一個減法。接著店長會在同一頁追加兩個問題，一個問「哪一天把這段時間切成前後一樣多」，一個是會計對帳時問「有退款的情況下，有幾段連續訂單加起來剛好是某個金額」。三個問題用的都是同一張累計表，只是用法不同。

這課的路線：
  1. 報表每切一次日期就從頭加一遍，慢在哪裡、重複的工作是什麼。
  2. 前綴和陣列：最前面多放一格 0 的累計表，任一段的總和只要一個減法（開場問題的最小答案），以及區間兩端含不含怎麼不出錯。
  3. 把累計表包進報表用的 CupLedger：該存什麼、什麼情況下值得先建表。
  4. 平衡點：只需要「左邊的總和」時，一個變數就夠，不用整張表。
  5. 有退款時總和剛好 k 的連續段有幾個：滑動視窗為什麼失效，前綴和加頻率表怎麼數；最後整理題目沒說用哪一招時怎麼選。
這課會用到：
  • 第 3 課的每日累計杯數 runningTotals：第 i 格是第 0 天到第 i 天的總和，用前一格加上今天算出來。
  • 第 5 課的補數與頻率表：走到 x 時問「目標 − x 之前出現過幾次」，先查再存，Map 記每個值出現的次數。

報表每切一次日期就從頭加一遍，慢在哪裡？

先把要算的東西說精確。陣列 cups 是每天賣出的杯數，索引 0 是第一天。報表要的是「索引 l 到索引 r 這一段的總和」，兩端都含，這種「陣列中某一段的總和」叫做區間和（range sum），這課寫成 sum(l..r)。例如 sum(1..3) 就是 cups[1] + cups[2] + cups[3]。

最直接的寫法，就是現在報表頁的寫法：每次查詢都跑一次迴圈，從 l 加到 r。下面用一週的資料查三次，steps 記錄一共做了幾次加法。執行後看最後一行：

三次查詢分別加了 3、7、4 次，一共 14 次。一次查詢最多要加 n 次（查整段的時候），q 次查詢就是 O(n × q)。一週 7 天看不出問題，但報表的 n 和 q 都會長大：一年 365 天、一天被查 1 萬次，就是幾百萬次加法；如果資料換成「每一筆訂單」，n 到幾十萬，每切一次選單都要等，使用者就感覺得到了。

慢的原因不是加法本身，而是重複的工作。查第 1～3 天和查第 2～5 天，兩次都把 15 和 9 加了一遍；查第 0～6 天時，第 1～3 天又整段重加一次；接著查第 2～5 天，又把 0～6 已經加過的第 2～5 天重加一遍。資料沒有變，每次查詢卻都在重算之前算過的東西。

能不能把「加過的」記下來？第 3 課的累計杯數就是一種記法：第 i 格存「從第 0 天到第 i 天」的總和。假設手上有這種累計，想要第 l～r 天，只要拿「到第 r 天為止的累計」減掉「到第 l 天之前的累計」，兩者共同的前段抵消，剩下的就是中間那一段。下一節把這個想法做成一張表，並處理它在 l = 0 時會出的問題。

怎麼讓每次查詢只做一次減法？前綴和陣列

「前綴」（prefix）指的是從陣列開頭開始、連續的一段：[12, 8, 15, 9, 20] 的前綴有空的 []、[12]、[12, 8]…一直到整個陣列。把每一個前綴的總和依序存進一個陣列，就是前綴和（prefix sum）陣列，這課叫它 prefix。

定義是：prefix[i] 是前 i 個元素的總和。前 0 個元素什麼都沒有，總和是 0，所以 prefix[0] = 0；最後一格是前 n 個，也就是全部的總和。從前 0 個到前 n 個一共 n + 1 種，所以 prefix 的長度是 n + 1，比原陣列多一格。

它跟第 3 課的 runningTotals 存的是同一批數字，只是位置不同。runningTotals 的第 i 格是「第 0 天到第 i 天」，也就是前 i + 1 個；這裡同一個值放在 prefix[i + 1]。整張表往右挪了一格，空出來的 prefix[0] 放 0。為什麼要這樣挪，這一節最後會看到。

為了讓圖放得下，下面改用前 5 天的資料。看圖時對照兩列的索引：上面 cups 的第 1～3 格，對應到下面 prefix 的哪兩格相減。

公式是 sum(l..r) = prefix[r + 1] − prefix[l]。拆開來看：prefix[r + 1] 是前 r + 1 個，也就是第 0～r 天；prefix[l] 是前 l 個，也就是第 0～(l − 1) 天。兩者的第 0～(l − 1) 天完全相同，相減後抵消，剩下第 l～r 天。圖中的例子是 sum(1..3) = prefix[4] − prefix[1] = 44 − 12 = 32，跟直接加 8 + 15 + 9 一樣。

建表的方法跟第 3 課一樣，一路加過去：每一格等於前一格加上當天的杯數，走一遍是 O(n)。建好之後，任何一段都只要讀兩格、做一次減法，是 O(1)。下面這格先印出建表的每一步，再用四組查詢驗證公式，看每一行的 prefix[i + 1] = prefix[i] + cups[i] 怎麼接起來：

這個公式最容易出的錯是索引差一：該用 r + 1 卻寫成 r，或者把「前 i 個」和「第 i 天」搞混，結果少算或多算一天。這種錯在程式圈叫 off-by-one，它不會報錯，只會得到一個看起來合理的錯數字。所以寫完先用兩個邊界手算驗證：只有第 0 天的 sum(0, 0) 要等於 cups[0]，全部的 sum(0, n − 1) 要等於總和。上面那格的 sum(0, 0) 和 sum(0, 4) 就是這兩個檢查，公式寫錯時一跑就抓得到。

為什麼不直接用第 3 課長度 n 的表？

你可能會想：runningTotals 已經寫過了，直接拿它當表（長度 n，第 i 格含第 i 天）不行嗎？可以，公式會變成 run[r] − run[l − 1]：run[r] 是第 0～r 天，run[l − 1] 是第 0～(l − 1) 天。問題出在 l = 0，也就是「從第一天開始」的查詢，而報表上最常見的查詢正是這種。下面這格看最後兩行：

l = 0 時要讀 run[-1]。JavaScript 讀不存在的索引不會報錯，只會拿到 undefined（第 3 課講過的越界讀取），44 − undefined 的結果是 NaN，報表上就會出現一個看不懂的值。要修只能加特例：l === 0 ? run[r] : run[r] - run[l - 1]。

這就是 prefix 最前面多放一格 0 的理由。那一格代表「前 0 天的總和是 0」，l = 0 時公式讀的是 prefix[0]，減掉 0 剛好就是 prefix[r + 1]，不用任何特例。所有區間套同一個公式，少一個分支就少一個出錯的地方。代價只是多一格，空間還是 O(n)。

到這裡，開場的問題已經有了答案：建一次 prefix，之後每次切換日期都是 O(1)。但這個公式有一個前提：l 和 r 兩端都含。報表的日期選單、API 的參數、SQL 的日期條件，兩端含不含各有習慣，這是接到真實系統時最常出錯的地方。

💡 實務上：區間用「含頭不含尾」最不容易差一
工作中的區間大多是含頭不含尾（半開區間）：slice(l, r)、substring 都不含 r，這時公式直接是 prefix[r] − prefix[l]，連 +1 都省了。日期查詢也一樣，「11 月 1 日當天」寫成 created_at >= '2026-11-01' AND created_at < '2026-11-02'，比 <= '2026-11-01 23:59:59' 安全，後者會漏掉 23:59:59 之後那不到一秒的資料。報表的日期選單接 API 時，在文件寫清楚結束日含不含，前後端才不會各自猜。Code review 看到區間，資深工程師通常先問的就是「兩端含不含」。

把累計表包進報表元件：CupLedger 該存什麼、什麼時候值得建？

公式有了，接下來要把它放進報表頁。報表載入一次資料，之後會被查很多次，所以適合寫成一個物件：建立時拿到每天的杯數，之後每次查詢呼叫它的方法。這就是練習 1：寫一個 class（TypeScript 課第 23 課）CupLedger，建構時拿到每天的杯數，之後可以被呼叫很多次 sumRange(l, r)，每次都要 O(1)。這題對應 LeetCode 303. Range Sum Query - Immutable。

這種「先把之後會反覆用到的結果算好存起來」的做法叫預先計算（precomputation）。在 CupLedger 裡，預先計算發生在建構子：花 O(n) 建好 prefix，存在物件上；sumRange 只讀兩格做一次減法。

寫的時候要決定物件上存什麼。答案是存 prefix，不存原陣列的參考。陣列是參考型別（TypeScript 課第 2 課）：把 cups 存進物件，存的是指向同一個陣列的參考，不是一份副本。如果建構時只記住 cups、等到查詢才去算，報表頁別的程式之後改了那個陣列（例如有人補登了一天的資料），你的查詢結果就會跟著變，而且你不會知道。在建構子裡就把 prefix 算好，之後的查詢只讀自己的 prefix，跟原陣列無關。練習 1 的測試會在建好之後改原陣列，檢查結果有沒有跟著變。

反過來，建構子也不能改傳進來的陣列。第 3 課講過的原地修改，就是直接在原陣列上累加（a[i] += a[i - 1]），省一份空間，但呼叫的人手上的每日杯數就被改成了累計，同一頁畫每日長條圖的程式拿到的資料就全錯了。把參數宣告成 readonly number[]，push、sort 和索引賦值在型別檢查時就會被擋下。

CupLedger 寫好了，但每次都先建表一定比較好嗎？

什麼時候值得先建表？

不一定，因為前綴和不是免費的：建表要先走一遍，還多用一張表的空間。它划不划算，要看查詢的次數。把兩種做法的成本並排：

做法建表每次查詢q 次查詢合計額外空間
每次都加一遍不用O(n)O(n × q)O(1)
前綴和O(n)O(1)O(n + q)O(n)

只查一次的時候，前綴和不會比較快。建表本身就要掃一遍，是 O(n)，跟直接加總那一段一樣，還多用了 O(n) 空間。前綴和省下的是「第二次以後」的查詢，所以查得越多越划算。報表頁一天被查上萬次，正是這種情況。

資料常常變動的時候，前綴和也不划算。改了第 i 天的杯數，prefix[i + 1] 之後的每一格都包含第 i 天，全部要跟著改，一次更新就是 O(n)。如果更新跟查詢一樣頻繁，每次更新都要重建大半張表，省下的查詢時間就被吃掉了；這種情況要換別的資料結構，課末「補充與查表」有說明。已經結束、不會再改的歷史資料，最適合前綴和。

這個取捨在後端很常見，只是換了規模。報表系統常建一張「每日彙總表」：每天結束時把當天的總和算好存起來，查詢時讀彙總表就好，不用掃整個 orders 表。它跟前綴和是同一個想法：用寫入時多做的工作和多用的儲存空間，換查詢時的速度。

💡 實務上：先問資料在哪一層、會不會被改
報表的區間總和多半由資料庫算（SUM 加上日期條件和索引），前端自己建前綴和的場景，是整份資料已經載到瀏覽器：例如一年的每日營收圖表，拖動日期區間滑桿時即時顯示合計，或畫「累計營收」折線圖，這時把 prefix 建一次（Vue 的 computed、React 的 useMemo）就好，不要每次拖動都重加。要注意的是「歷史資料會不會被改」：補登訂單、事後退款都會讓某天之後的累計全部失效，表要跟著重建。動手前先問三件事：資料量多大、查詢多頻繁、資料會不會回頭修改，答案決定要不要建表、建在哪一層。

報表的區間合計做好了。店長看著這週的數字，又提出一個新問題：「有沒有哪一天，剛好把這週切成前後一樣多？」這個問題也是在比兩段的總和，但它要的不是很多次任意區間，而是每一天的「左邊」和「右邊」。整張 prefix 表還需要嗎？

店長問哪一天把這週切成前後一樣多：一定要建整張表嗎？

先把店長的問題說精確。某一天是平衡點（pivot）的意思是：它左邊所有天的總和，等於它右邊所有天的總和，不含那一天自己。有好幾天符合就回傳最左邊的索引，一天都沒有就回傳 -1，這是沿用經典題的規定。這是練習 2，對應 LeetCode 724. Find Pivot Index。

動手前先手算一次，順便把邊界想清楚。先拿這週的 [12, 8, 15, 9, 20, 7, 11] 走一遍：每一天的左右都不相等，例如第 3 天左邊是 12 + 8 + 15 = 35，右邊是 20 + 7 + 11 = 38，所以這週的答案是 -1。這個結果正確，卻看不出平衡點長什麼樣，所以改用一組小資料。[2, 5, 4, 3, 4] 的索引 2：左邊是 2 + 5 = 7，右邊是 3 + 4 = 7，答案是 2。邊界上，索引 0 的左邊沒有任何一天，總和是 0；最後一天的右邊也沒有，總和也是 0。所以 [5, 2, -2]（−2 是退杯，跟練習 1 說的「cups 可能有負數」一樣）的答案是 0，因為右邊 2 + (−2) = 0，跟左邊的 0 相等；只有一天的時候，左右都是 0，答案是 0。

最直接的做法是暴力解：每個位置都把左邊加一次、右邊加一次，每個位置 O(n)，n 個位置總共 O(n²)。重複的工作跟報表那題一樣：相鄰兩天的「左邊」只差一天，卻每次從頭加。

用前一節的 prefix 表可以算：第 i 天的左邊是 prefix[i]，右邊是 prefix[n] − prefix[i + 1]。但看一下用法：從左往右檢查時，每一步只讀「目前這一格」的 prefix，讀過就不再回頭。報表那題要存整張表，是因為查詢的 l、r 可以是任何位置，什麼時候會讀到哪一格都不知道；這裡讀的順序是固定的，所以不用存下來，邊走邊算就夠了。

做法是這樣：先走一遍算出全部的總和 total；第二遍從左往右走，用一個變數 leftSum 記「目前位置左邊的總和」。那麼右邊就是 total − leftSum − cups[i]：全部減掉左邊，再減掉自己。順序要注意，比較完之後才把 cups[i] 加進 leftSum，因為比較的那一刻，左邊不能含自己；加完之後，leftSum 就變成下一天的左邊。下面這格印出每一步的左右兩邊，看左右兩欄在哪一列第一次相等：

平衡點只問「哪一個位置」，而且每一段都從開頭或結尾開始。會計對帳的問題就沒這麼單純了：段可以從任何地方開始、到任何地方結束，要數的是「有幾段」，而且資料裡有退款的負數。

有退款時，總和剛好 k 的連續段有幾個？

會計拿到一筆 k 元的款項，要對回訂單紀錄：changes 是一筆筆依時間排好的金額變化，一般訂單是正數，退款是負數。問題是：有幾段連續的紀錄，加起來剛好等於 k？這些段都是可能的對應。這是練習 3，對應 LeetCode 560. Subarray Sum Equals K。

「連續段」指的是陣列中相鄰、不跳過任何元素的一段，例如 [3, -3, 3] 的 [-3, 3] 是連續段，[3, 3]（第一個和最後一個）不是，因為跳過了中間。LeetCode 和多數教材把它叫做子陣列（subarray），題目看到這個字就是指連續段。

第 10 課的滑動視窗為什麼不行？

「連續段、總和」看起來就是第 10 課的可變視窗。但可變視窗靠一個性質才成立：全部是正數時，視窗變長總和一定變大，變短總和一定變小。所以總和超過 k 時可以放心收縮左邊，因為再往右擴張只會更大，左邊那一格不可能再屬於任何答案。

有退款時這個性質就不成立了：視窗往右加進一個負數，總和反而變小。收縮時丟掉的左邊，可能和後面的負數組成答案；更麻煩的是，程式不會報錯，只會數少。下面這格用同一段視窗程式跑兩個案例，第一個全是正數，第二個有負數，對照每行括號裡的正確答案：

第一個案例是對的，第二個少數了一段。第二個案例走到最後時，視窗是整段 [3, −3, 3]，總和 3 沒有超過 k，所以不收縮，只數到這一段；但「只有最後一個 3」那一段也等於 3，視窗的左邊停在 0，根本沒機會看到它。視窗的問題在於它一次只看「一段」，而以同一個位置結尾的合格段可能有好幾個。

換個問法：以 r 結尾的合格段，有幾個起點？

既然一次看一段不夠，就換個問法：固定結尾 r，問「有幾個起點 l，讓第 l～r 段的總和等於 k」。把每個 r 的答案加起來，就是全部的段數。

用前綴和改寫條件。第 l～r 段的總和是 prefix[r + 1] − prefix[l]，要等於 k，移項就是

prefix[l] = prefix[r + 1] − k

從左往右走，走到 r 時手上有目前的前綴和 p = prefix[r + 1]，所以 p − k 是已知的數字。問題變成：前面的前綴和裡，有幾個剛好等於 p − k？每一個都對應一個起點。注意這個推導只用了減法，沒有用到「越長越大」，所以有負數也成立。

「前面出現過幾次某個值」正是第 5 課 Two Sum 的補數問題：當時走到 x 時問「目標 − x 出現過沒有」，這裡走到 p 時問「p − k 出現過幾次」，補數是 p − k。記次數的方法也是第 5 課練習 3 數有幾組時用的頻率表：一個 Map，鍵是前綴和，值是它出現過幾次。

頻率表要放對三件事，每一件放錯都會得到錯的答案，而且不會報錯。第一，頻率表一開始要放 0 → 1，代表 prefix[0] = 0 出現過一次。它對應「起點是 0」，也就是從第一筆開始的段；少了它，[5]、k = 5 會數成 0，因為走到 r = 0 時 p − k = 0，表裡卻沒有 0。這跟報表那題多放一格 0 的理由一樣。

第二，每一步先查再存：先用 p − k 查次數加進答案，再把 p 的次數加 1。順序反過來時，表裡已經有目前的 p，k = 0 時 p − k 就是 p 自己，會把長度 0、一個元素都沒有的空段也算進去。理由跟第 5 課「先查再存」一樣：查的時候，表裡只能有「前面」的東西。

第三，要記次數，不能只用 Set 記「有沒有」。同一個前綴和可能出現好幾次，例如有退款時累計金額會回到之前的值，每一次出現都是一個不同的起點，都要算進去。

走到 r = 2 時 p = 3，需要的前綴和是 3 − 3 = 0，頻率表裡 0 出現過 2 次：一次是開頭的 prefix[0]，一次是 r = 1 時的 3 + (−3)。所以一次加 2，分別是起點 0 的整段 [3, −3, 3]，和起點 2 的 [3]。滑動視窗漏掉的就是後面這一段。

複雜度：一次走訪，每步 Map 查一次、寫一次，都是平均 O(1)，所以 O(n) 時間；頻率表最多存 n + 1 個不同的前綴和，O(n) 空間。暴力解是固定起點、往右累加，O(n²)。Map 用 O(n) 空間換掉了內迴圈，這是這題能做到 O(n) 的代價。

💡 實務上：金額先換成整數再累加
這題的頻率表靠「前綴和完全相等」才查得到。金額如果用小數（0.1 + 0.2 不等於 0.3），累加後的前綴和會帶著誤差，seen.get(p - k) 就會查不到，答案少算卻不會報錯。實務上金額一律存成整數的「分」或最小貨幣單位（TypeScript 課第 5 課），對帳、累計、比對都用整數做，最後顯示時才格式化。看到有人拿小數金額當 Map 的 key 或用 === 比較，就是 code review 該提出來的地方。

報表頁的三個問題都解決了，三題用的是同一個想法的三種形態：存整張 prefix 表、只留一個 leftSum、把前綴和放進頻率表。但這三題都是先知道「這課教前綴和」才去想的。真正的題目不會告訴你用哪一招，下一節整理怎麼判斷。

題目沒說用哪一招時，怎麼判斷？

到這一課，陣列題的工具已經有好幾種，而且剛剛才看過一個「看起來像滑動視窗，其實不能用」的例子。所以不要從「這題像哪一課」開始猜，而是照第 1 課的步驟先寫暴力解，再看它的內迴圈重複做的是哪一種工作，對照下表選工具：

題目的特徵用代價
同一份資料，問很多次「某一段的總和」前綴和建表 O(n)、空間 O(n)；資料要不常變動
資料已排序，找位置、數「落在某個範圍的有幾個」二分搜尋（第 9 課）每次 O(log n)；沒排序要先排 O(n log n)
連續段，而且全部是非負數，求最長／最短／最大滑動視窗（第 10 課）O(n)、O(1) 空間；有負數就失效
連續段的總和等於 k、有負數前綴和 + 頻率表（本課）O(n)、空間 O(n)
找配對、看過沒有、出現幾次雜湊表（第 4～6 課）O(n)、空間 O(n)
已排序，找兩個數的組合雙指標（第 7 課）O(n)、O(1) 空間

有些題目不會直接長成表上的樣子，要先把資料轉換一下。例如「1 和 0 的個數相等的最長連續段」：題目問的是個數，不是總和。但把每個 0 當成 −1 之後，「1 和 0 一樣多」就等於「這一段的總和是 0」，問題變回本課的「連續段總和等於 k」，k = 0。差別是這次要的是最長的一段，不是有幾段，所以頻率表改成記「每個前綴和第一次出現的位置」：同一個前綴和出現在越前面，跟目前位置之間的那一段就越長。這張 Map 一開始要放 0 → −1，代表 prefix[0] = 0 出現在「索引 −1」，也就是第一筆之前；這樣從開頭開始、到 r 結束的段，長度 r − (−1) = r + 1 才算得對。這跟計數版一開始放 0 → 1 是同一個理由：都是替「從第一筆開始的段」留一個起點。混合題常常要先做這一步轉換，轉換之後才看得出是哪一招。

練習 4～6 就是這種題目：題目只描述咖啡店的需求，不說用哪一招，範圍是第 1～11 課。先寫暴力解，找出重複的工作，再回來對照這張表。

補充與查表

總和會不會太大？

JavaScript 的數字到 Number.MAX_SAFE_INTEGER（2⁵³ − 1，約 9 千兆）都能精確表示整數（TypeScript 課第 5 課），杯數、整數元的金額加起來遠遠不到。LeetCode 上用 Java、C++ 的解答常提醒要小心溢位（overflow）：32 位元整數有上限，超過之後會變成錯的數字。在 JavaScript 用一般的 number 累加時不會發生這種事。

資料常常變動時用什麼？

前綴和一次更新是 O(n)。如果更新跟查詢一樣頻繁，要換成能 O(log n) 更新、也能 O(log n) 查區間和的結構，例如樹狀陣列（Fenwick tree）或線段樹（segment tree）。面試偶爾出現，這門課不教，知道有這類結構、知道什麼時候該去找它就好。

二維前綴和

二維也有前綴和：P[i][j] 存左上角 i × j 那一塊的總和，任一個矩形的總和用四格加減算出來（對應 LeetCode 304）。面試偶爾出現，想法跟一維相同：多放一列、一行 0，所有矩形套同一個公式。

練習

每題的隱藏測試會用固定案例、大量隨機案例比對參考解，最後再用大資料量計時。判分逾時或「花了 … ms」的訊息，代表複雜度不夠，不是電腦太慢。傳進來的陣列都不能修改。練習 4～6 是混合複習：題目不說用哪個技巧，範圍是第 1～11 課。

練習 1：完成 class CupLedger：constructor(cups) 建好前綴和；sumRange(l, r) 回傳第 l 天到第 r 天（兩端都含）的總杯數，要 O(1)。cups 可能有負數（退杯）；建好之後外面再改原陣列，結果不能跟著變。測試會建一份 20,000 天的資料、查 25,000 次計時。（對應 LeetCode 303. Range Sum Query - Immutable）

練習 2：寫 balanceDay(cups)：回傳最左邊的平衡點索引（左邊所有天的總和等於右邊所有天的總和，不含自己）；沒有就回傳 -1（沿用經典題的規定，不是 null）。要 O(n)，測試會用 25,000 天的資料計時。（對應 LeetCode 724. Find Pivot Index）

練習 3（進階）：寫 countSegmentsWithSum(changes, k)：changes 是每筆訂單的金額變化（退款是負數），回傳總和剛好等於 k 的連續段有幾個；空陣列回傳 0。要 O(n)，測試會用 30,000 筆計時。（對應 LeetCode 560. Subarray Sum Equals K）

練習 4（混合複習）：寫 countInPriceRange(prices, queries)：prices 是所有品項的價格，已由小到大排序（可能有重複）；每個查詢 [lo, hi] 要回傳價格在 lo～hi（兩端都含）之間的品項有幾個，依查詢順序回傳陣列。測試會用 100,000 個價格、3,000 次查詢計時。

練習 5（混合複習）：寫 longestBalanced(results)：一連串的試喝結果，1 是喜歡、0 是不喜歡，回傳「喜歡與不喜歡次數相等」的最長連續段長度；沒有就回傳 0。測試會用 30,000 筆計時。（對應 LeetCode 525. Contiguous Array）

練習 6（混合複習）：寫 maxSeatsInWindow(seats, k)：seats 是每個時段坐滿的座位數（都 ≥ 0），回傳任意連續 k 個時段的座位總數最大值；k ≥ 1，k 比時段數多時回傳 0。測試會用 50,000 個時段、k = 25,000 計時。

練習 7：前綴和陣列為什麼長度是 n + 1，而不是 n？

✓ b。多出來的是最前面那一格 0，所有區間都套同一個公式。長度 n 的版本要寫 run[r] − run[l − 1]，l = 0 時讀到 run[-1] 是 undefined，結果變 NaN，所以必須加特例（c 錯）。JavaScript 的索引從 0 開始（a 錯）；最後一格是全部的總和，不是長度（d 錯）。

練習 8：一份 n 天的資料，只要查一次某一段的總和。先建前綴和會比較快嗎？

✓ c。前綴和是預先計算：先付 O(n) 建表，之後每次查詢 O(1)。只查一次時總成本還是 O(n)，還多用了 O(n) 空間（a 只看了查詢那一半；b 錯，建表要走過每個元素）。前綴和對負數一樣正確，是滑動視窗才需要全部非負（d 錯）。

練習 9：退款會產生負數。要數「總和剛好等於 k 的連續段」，可以用第 10 課的滑動視窗嗎？

✓ a。視窗總和超過 k 時收縮左邊，是假設「再往右只會更大」；有負數時，後面的值可能把總和拉回來，[3, -3, 3]、k = 3 就會少數一段（b 錯）。連續段不能重新排序，排了就不是原本的段（c 錯）。Map 的鍵可以是負數，前綴和 + 頻率表正是靠它處理負數（d 錯）。

常見錯誤

  • 前綴和的索引差一：寫成 prefix[r] − prefix[l] 會少算第 r 天；用長度 n 的表會在 l = 0 時得到 NaN。固定用長度 n + 1、prefix[r + 1] − prefix[l]，寫完用 [0, 0] 和 [0, n − 1] 手算驗證。
  • 沒確認區間兩端含不含：日期選單、API 參數、slice 的習慣不同，含尾用 prefix[r + 1] − prefix[l]，不含尾用 prefix[r] − prefix[l]。先問清楚再套公式。
  • 建表時存了原陣列的參考：查詢時才去讀原陣列，外面改了陣列結果就跟著變。在建構子裡就把前綴和算好，只存前綴和。
  • 平衡點的左邊含了自己：比較完才把 cups[i] 加進 leftSum；右邊是 total − leftSum − cups[i]。
  • 頻率表忘了 0 → 1：漏掉從開頭開始的段，[5]、k = 5 會得到 0。找最長段時則是先放 0 → −1。
  • 先存再查：k = 0 時會把長度 0 的空段算進去。先查補數，再把目前的前綴和加進頻率表。
  • 有負數還用滑動視窗：結果錯，但不會報錯。看到「連續段＋有負數＋總和等於 k」，改用前綴和 + 頻率表。
  • 混合題直接套上一課的技巧：先寫暴力解，看重複的工作是「重算區間總和」「線性找位置」還是「重算相鄰的段」，再決定用前綴和、二分搜尋還是滑動視窗。

小結

  • 報表每次查詢都從頭加是 O(n × q)，慢在重算之前加過的東西；前綴和把「加過的」存成一張表。
  • 前綴和陣列長度 n + 1，prefix[0] = 0，prefix[i + 1] = prefix[i] + a[i]；任一段 sum(l..r) = prefix[r + 1] − prefix[l]，O(1)。多放的那格 0 讓 l = 0 不用特例。
  • 它是預先計算：先付 O(n) 時間、O(n) 空間，換每次查詢 O(1)。查很多次、資料不常變時才划算；只查一次不會更快。表裡存 prefix，不存原陣列的參考。
  • 只會按順序讀「目前位置左邊的總和」時，一個 leftSum 變數就夠（平衡點：右邊 = total − leftSum − a[i]）。
  • 總和等於 k 的連續段：以 r 結尾的段數等於「前面出現過幾次 p − k」，用頻率表、一開始放 0 → 1、先查再存，有負數也成立，O(n)。
  • 選技巧看重複的工作：重算區間總和用前綴和；在已排序資料找位置用二分搜尋；非負數的連續段用滑動視窗；配對、計數用雜湊表。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 10：下面四題，哪一題能用可變滑動視窗（right 擴張、while 收縮 left）做到 O(n)？

✓ 可變視窗靠單調性：全部非負時，視窗變長總和只會變大，超過 50 就收縮左邊，不會丟掉答案。a 最常被選錯：有負數時後面的值可能把總和拉回來，收縮會漏掉答案，結果錯卻不會報錯，要改用前綴和。c 不是連續段，用雜湊表；d 先把 0 換成 −1，變成前綴和的題目。（第 10、11 課）

練習 11：金額變化有正有負，要找總和剛好等於 k 的最長連續段有多長，O(n)。哪個做法對？

✓ 以 r 結尾的段，起點越早越長，所以 Map 只記前綴和第一次出現的位置，之後遇到同一個值不覆蓋；0 → −1 代表從開頭開始的段，長度是 r − (−1)。b 每次覆蓋成最後的位置，找到的是最短的起點。a 錯在有負數時「越長總和越大」不成立。（第 10、11 課）

練習 12：prices 沒排序、有 n 筆整數，要回答 q 次「價格落在 lo～hi 的有幾筆」。lowerBound 是第 9 課的寫法。這段的時間複雜度是？

function countInRange(prices, queries) {
  return queries.map(([lo, hi]) => {
    const sorted = prices.toSorted((a, b) => a - b)
    return lowerBound(sorted, hi + 1) - lowerBound(sorted, lo)
  })
}

✓ 排序放在每次查詢裡，q 次就排 q 次，每次還複製一份 O(n) 的陣列。把 toSorted 移到 map 外面，才是 b 的 O((n + q) log n)。b 是最多人選的：它描述的是「應該怎麼寫」，不是這段程式實際做的事。（第 9 課）

練習 13：已排序的價目表找兩杯不同飲料加起來等於 budget，回傳索引。這段在哪個輸入會回傳錯的答案？

let left = 0, right = prices.length - 1
while (left <= right) {
  const sum = prices[left] + prices[right]
  if (sum === budget) return [left, right]
  if (sum > budget) right--
  else left++
}
return null

✓ 170 太大，right-- 之後 left = right = 0，<= 讓迴圈再跑一圈，80 + 80 回傳 [0, 0]，同一杯用了兩次。找兩個不同的元素要用 left < right。b 是兩個不同的索引，一開始就回傳 [0, 1]，沒有錯。（第 7 課）

練習 14：同事寫的 lower bound（左閉右開），哪個輸入會讓它停不下來？

let lo = 0, hi = a.length
while (lo < hi) {
  const mid = Math.floor((lo + hi) / 2)
  if (a[mid] < target) lo = mid
  else hi = mid
}
return lo

✓ lo 走到 1 之後範圍剩 [1, 2)，mid 一直是 1，lo = mid 不會縮小範圍，無窮迴圈。a[mid] < target 代表 mid 不是答案，要 lo = mid + 1。d 一路走 hi = mid，範圍每圈都縮小，正確回傳 0。（第 9 課）

練習 15：合併重疊或相接的座位預約，這段在哪個輸入結果會錯？

const sorted = bookings.toSorted((a, b) => a[0] - b[0])
const merged = []
for (const [start, end] of sorted) {
  const last = merged.at(-1)
  if (last && start <= last[1]) last[1] = end
  else merged.push([start, end])
}
return merged

✓ [2, 3] 被 [1, 10] 整個包住，結束直接換成 3，結果變成 [[1, 3]]。要寫 last[1] = Math.max(last[1], end)。a 是相接，這課約定相接也合併，<= 正確得到 [[1, 5]]；c 先排序過，順序不影響。（第 8 課）

練習 16：面試題是「已排序的價目表找兩數和，回傳索引」。你用 Map 寫出 O(n) 的解，面試官問：「還能更好嗎？」怎麼回答？

✓ 時間已到下限，能省的是空間：排好序讓「太大時 right 跟誰配都太大」成立，雙指標不用 Map，O(1) 額外空間。b 錯在只看時間，沒用到「已排序」這個資訊。c 是每個元素各二分一次，總共 O(n log n)；d 的 Set 本身就是 O(n)，還會丟掉兩杯同價的組合和原本的索引。（第 7 課）

練習 17：數「總和剛好等於 k 的連續段」，同事的頻率表一開始是空的。哪個輸入會算錯？

const seen = new Map()
let p = 0, count = 0
for (const x of changes) {
  p += x
  count += seen.get(p - k) ?? 0
  seen.set(p, (seen.get(p) ?? 0) + 1)
}
return count

✓ 答案是從開頭開始的 [4, 1]，需要的前綴和是 0，也就是 prefix[0]，但表裡沒有它，回傳 0。頻率表一開始要放 0 → 1。其他三個的答案都不從索引 0 開始，所以缺了它也碰巧算對；寫完要用「答案從開頭開始」的例子測一次。（第 11 課）
