階段 6：進階結構與搜尋 · 第 19 課

Heap 與 Top K

中午尖峰，外送平台的單一張接一張進來。每張單都標著「還剩幾分鐘要出餐」：有的 30 分鐘，有的只剩 5 分鐘。廚房只有一位咖啡師，他每做完一杯，就要問出單機一句話：「現在最急的是哪一張？」問的同時，新單還在進來。這課的任務是寫出這台出單機的核心：一個能一直放進新單、每次都拿出最快到期那張的結構，而且單量從 100 張長到 10 萬張也不會變慢。

第 12 課的佇列做不到，因為它是先來先做，不看到期時間；每進一張單就把全部排序一次，單一多就太慢。答案是一個叫 heap 的結構。寫完之後，同一個工具還能回答店長的另一類問題：「菜單上第 3 高的價格是多少」「今天最常點的前 3 種飲料是什麼」。

這課的路線：
  1. 為什麼排序和掃描都不夠：「一直放進來、每次拿最急的」用陣列各慢在哪，heap 怎麼讓兩邊都只要 O(log n)（開場問題的最小答案）。
  2. heap 長什麼樣：一棵用陣列存的樹，為什麼它的高度只有 log n。
  3. 放進與拿出：新單往上調整、拿走根之後往下調整；再讓同一個 heap 能比較外送單這種物件，並實測它比每次 sort 快多少。
  4. 每輪拿最重的兩批：換成 max-heap，練習「拿出來、算完、放回去」。
  5. 前 k 名：第 k 高的價格為什麼要用 min-heap，以及最常點的前 k 種飲料怎麼處理並列。
這課會用到：
  • 第 16 課的二元樹名詞：最上面的節點是根，沒有子節點的是葉，高度是從根往下最長有幾層。
  • 第 2 課的 O(log n)：每一步把範圍砍半或每層加倍，100 萬筆也只要約 20 步。

一直有新單進來，為什麼排序和掃描都不夠？

先把出單機要做的事講精確。它只需要三個動作：

  • push：放進一張新單。
  • pop：拿出最急的那張（並從待辦裡移除）。
  • peek：只看一眼最急的是哪張，不拿走。

只要求這三個動作的結構，叫優先佇列（priority queue）。它和第 12 課的佇列差在「拿出哪一個」：佇列拿最早放進去的，優先佇列拿優先順序最高的，這裡就是剩餘分鐘數最小的那張。它不需要支援「列出全部的順序」「找某張單」，這一點等一下會變成 heap 能快的關鍵。

用學過的陣列做優先佇列，直覺上有三種寫法。看每一種把成本放在哪裡：

做法放進去拿出最小的問題
不排序的陣列，拿的時候掃一遍O(1)O(n)：要走過全部才知道誰最小拿的次數一多就慢
每次放進去都 sortO(n log n)O(1)（如果從尾端拿）放的次數一多就慢
保持排序，用二分搜尋找位置再 splice 插入O(n)：插入要搬動後面的元素O(1)還是 O(n)

前三種的共同問題是：它們不是在放進去時付 O(n)，就是在拿出來時付 O(n)。出單機兩種動作都很頻繁，尖峰時每分鐘有新單也有出餐，所以哪一邊慢都會卡。

heap 的做法是兩邊各付一點：放進去和拿出來都是 O(log n)。n = 100 萬時，log n 大約是 20，也就是每個動作只要幾十步，不管單量多大。它能這麼快，是因為它只維持「誰最小」，不維持完整的排序：第二小以後的順序它不知道，也不能快速查「某張單在不在裡面」。出單機剛好只需要知道最急的那張，這個代價對它不痛。

JavaScript 沒有內建 heap：到 ECMAScript 2024 為止，標準函式庫只有 Array、Map、Set 等，沒有 heap 或 priority queue（Java 有 PriorityQueue、Python 有 heapq）。面試時兩種做法都可以：自己寫一個（這課練習 1），或先問面試官「可以假設有一個 MinHeap 類別嗎？」，得到同意再直接用。工作上需要時，用維護良好的套件或自己的一份有測試的實作。

所以這課要自己做一個。

💡 實務上：「到期最早的先做」通常交給工作佇列或資料庫，不是自己的 heap
咖啡店後台的「15 分鐘未付款自動取消」「預約取貨前 10 分鐘提醒」都是優先佇列的需求，但工作上很少在 API 伺服器的記憶體裡放一個 heap 來做：伺服器重啟或部署時資料就沒了，開兩台伺服器時也各有一份。常見做法是存進資料庫用 ORDER BY due LIMIT 1 取，或用有延遲工作功能的佇列套件。記憶體裡的 heap 適合資料不怕遺失、算完就丟的場合，例如一次請求內的計算、排行榜的暫存、演算法題。資深工程師看到「之後再做」的需求，會先問：重啟後還要不要記得？有幾台伺服器在跑？

這課的出單機是後面那種：一次尖峰內的計算，重點是 heap 本身怎麼做到 O(log n)。要回答這個，得先看 heap 長什麼樣。

heap 長什麼樣，為什麼每個動作只要走 log n 步？

heap 能兩邊都 O(log n)，靠的是兩個規則同時成立。先看第一個規則需要的名詞。

完全二元樹（complete binary tree）是一種形狀很整齊的二元樹：除了最後一層，每一層都填滿；最後一層從左邊開始連續填，中間不留空位。也就是說，節點一個一個加進去時，永遠是填在「最後一層最左邊的空位」，填滿了才開新的一層。它不像第 16 課的一般二元樹可以一邊長很深、一邊很淺。

heap（堆積）是同時滿足下面兩個條件的二元樹：

  1. 形狀：是完全二元樹。
  2. 順序：每個節點都不大於它的子節點。這種叫 min-heap，最小的一定在根。反過來「每個節點都不小於子節點」叫 max-heap，最大的在根。

為什麼順序條件能保證最小的在根？因為從任何一個節點往上走，每一步都走到「不大於自己」的父節點，一路走到根，根就不大於所有人。

順序條件只管「父節點和子節點」，兄弟之間、不同分支之間沒有任何順序。這是 heap 和「排好序」最大的不同。下圖用出單機上 7 張外送單的剩餘分鐘數排成一個 min-heap：

為什麼可以用陣列存

第 16 課的樹用物件存，每個節點有 left、right 指標。heap 不用，因為完全二元樹沒有空洞：一層一層由左到右編號 0、1、2……，剛好就是陣列的索引，上圖下半部就是同一棵樹的陣列寫法。父子關係不用存指標，直接用索引算出來（索引從 0 開始）：

要找公式例子（上圖）
索引 i 的左子節點2 * i + 1i = 1（12）的左子節點是索引 3（20）
索引 i 的右子節點2 * i + 2i = 1（12）的右子節點是索引 4（15）
索引 i 的父節點(i - 1) >> 1i = 5（9）的父節點是 (5 − 1) >> 1 = 2（8）

公式為什麼成立：一個一個數位置就知道。根自己占索引 0，其他節點都是某個節點的子節點，而且按父節點的順序、每個父節點兩個，由左到右排下去。索引 i 前面有 i 個節點（索引 0 到 i − 1），它們的子節點一共 2i 個，依序占掉索引 1 到 2i。所以輪到 i 的時候，它的兩個子節點緊接著排在 2i + 1、2i + 2。用上圖驗算 i = 1：前面只有索引 0 一個節點，它的子節點占掉索引 1、2，所以 i = 1 的子節點是 3、4，就是 20 和 15。反過來從子節點 c 算回父節點：c 是 2i + 1 或 2i + 2，減 1 再除以 2 取整數，兩種情況都得到 i，就是 (c - 1) >> 1。x >> 1 是位元右移，對 0 以上的整數等於 Math.floor(x / 2)，寫 Math.floor((i - 1) / 2) 一樣對；它的限制見課末。

算出來的索引超過陣列長度，就代表那個子節點不存在。下面印出每個位置的父節點與子節點，並檢查 heap 的順序條件。執行後看最後兩行：它是 min-heap，但不是排序好的。

形狀條件帶來的好處在這裡：完全二元樹的高度大約是 log₂ n。第 0 層 1 個、第 1 層 2 個、第 2 層 4 個……每多一層容量加倍，100 萬個元素只有 20 層。接下來的 push、pop 都只沿著一條從根到葉的路走，最多走 20 步，所以是 O(log n)。

但這兩個條件很脆弱：放進一張新單，順序可能就壞了；拿走根，樹中間就多了一個洞。下一節看怎麼在 log n 步內把它修好。

新單進來、做完一張：heap 怎麼在 log n 步內修好自己？

修的原則是：先保住形狀，再沿著一條路修順序。形狀決定新元素放哪、洞從哪裡補；順序靠一路交換修回來。

push：放到最後，往上調整

新單只有一個位置可以放：陣列尾端，也就是最後一層最左邊的空位。放在其他地方，形狀就不再是完全二元樹。放上去之後，順序條件可能被破壞，例如新單只剩 3 分鐘，比它的父節點還急。修法叫往上調整（sift up）：

  1. 新元素放在最後，索引 i = length − 1。
  2. i 是 0（已經是根）就停。
  3. 算父節點 p = (i − 1) >> 1。新元素比父節點小就交換，i = p，回到第 2 步；否則停。

為什麼只修這一條路就夠？每次交換是把較小的值往上、較大的值往下。父節點位置換成更小的值，它跟另一個子節點的關係只會更成立；被換下來的舊父節點，本來就不大於它原本的子節點，所以放在下面也沒問題。路徑以外的父子關係完全沒被動到。

pop：拿走根，往下調整

咖啡師做完一杯，問「下一張是誰」，pop 回傳 heap[0]。難的是拿走之後怎麼補洞。直接 shift() 不行：所有元素往前一格，每個元素的索引都變了，用公式算出來的父子關係全亂了，而且 shift 本身就要搬動整個陣列，是 O(n)。

正確做法一樣先保住形狀：真正從陣列移除的，必須是最後一格。

  1. 記下根的值，等一下要回傳。
  2. 把最後一個元素 pop 出來，放到根。這樣形狀條件還成立（少的是最後一格）。
  3. 往下調整（sift down）：從 i = 0 開始，找出兩個子節點中較小的那個；它比目前的值小就交換，i 移到那個子節點，重複；沒有子節點或兩個都不比它小就停。

放到根的那個值原本在最底層，通常很大，所以要一路往下沉。為什麼一定要跟較小的子節點換？交換之後，換上來的那個要成為另一個子節點的父節點；只有較小的那個才不會比另一個大。跟錯的那個換，heap 就壞了。下面同時跑兩個版本，執行後比較最後兩行：錯誤版本的根已經不是剩下最小的值。

逐步看正確的那次（拿走 5，最後一個 30 放到根）：

步驟陣列做了什麼
開始[5, 12, 8, 20, 15, 9, 30]記下 5，pop 出最後的 30

補洞的過程也有三個邊界，出單機在離峰時都會遇到：

  • 空的 heap pop 回傳 undefined（跟陣列的 pop 一樣，本課約定），代表目前沒有待做的單。
  • 只剩一個時，pop 出最後一個之後陣列已經空了，不要再把它放回根，否則做完的單又會出現。
  • 右子節點可能不存在，每次讀子節點前都要檢查索引小於長度。

到這裡 push 和 pop 都能用了，但程式裡寫死了 <，只能比數字。出單機裡放的不是數字，是一張張外送單。

外送單是物件：讓呼叫的人決定誰先

真正的外送單長得像 { id, due }，< 沒辦法直接比兩個物件。與其為外送單、為價格、為「最大的先」各寫一個 heap，不如把「誰比較優先」交給呼叫的人：建構時傳一個函式 less(a, b)，a 應該比 b 先被拿出來時回傳 true。heap 本身只負責搬位置，不懂外送單是什麼。

需求傳入的 less
數字，小的先出來（min-heap）(a, b) => a < b
數字，大的先出來（max-heap）(a, b) => a > b
外送單，到期早的先出來(a, b) => a.due < b.due
到期一樣時，單號小的先(a, b) => a.due !== b.due ? a.due < b.due : a.id < b.id

最後一列是出單機真的需要的：兩張單都剩 10 分鐘時，如果不規定誰先，拿出來的順序取決於它們在 heap 裡被交換到哪裡，看起來像隨機。補上「單號小的先」，結果就固定了，客人抱怨時也查得出為什麼這張先做。

這跟第 8 課 sort 的比較函式不同：sort 要回傳負數、0、正數；這裡回傳 boolean，因為 heap 每次只需要問「誰比較優先」。把程式裡所有 heap[x] < heap[y] 換成 this.less(heap[x], heap[y])，<T> 是泛型：元素是什麼型別由使用的人決定，heap 本身不管（TypeScript 課第 19 課）。這樣就得到 MinHeap<T>。名字叫 MinHeap，但傳入 a > b 它就是 max-heap：「min」指的是「less 認為最優先的在根」。練習 1 請你寫出它。

工具齊了。剩下一個問題：開場說每次都 sort 太慢，到底慢多少，值不值得自己寫這些？

真的比每次 sort 快嗎？

先把每個操作的成本整理起來，原因都來自上一節「只沿一條從根到葉的路走」：

操作複雜度原因
peek（看最小的）O(1)就是 heap[0]
pushO(log n)最多從葉走到根，高度 log n
popO(log n)最多從根走到葉
把 n 個元素一個一個 push 進去O(n log n)n 次 push；另有更快的建法，見課末
空間O(n)一個陣列

每次都 sort 的出單機，每進一張單就要對整個陣列排序一次，單次 O(n log n)；n 張單放完就是 O(n² log n)。heap 放 n 張是 O(n log n)。差的不是常數，是多了一個 n。

出單機到這裡完成了：看下一張的 peek 是 O(1)；新單 push、出餐 pop 是 O(log n)，單量從 1,000 張長到 100 萬張，每個動作也只從約 10 步變成約 20 步。但 heap 的用處不只「最小的先」。接下來三個後台問題各要用不同的方式使用它，第一個需要的是 max-heap，而且拿出來的東西算完還要放回去。

每輪拿最重的兩批：max-heap 怎麼用？

出單機每次只拿一張、用完就丟，用不到 max-heap，也沒有「放回去」。烘焙區的問題剛好兩個都有：烘焙師有一堆咖啡豆批次，重量各不相同。每一輪拿最重的兩批 x ≥ y 一起處理：一樣重就兩批都用掉；不一樣重就剩下 x − y 放回去。問最後剩下的那批多重，全部用掉回傳 0。對應 LeetCode 1046. Last Stone Weight。

辨認的線索是「每一輪拿最大的兩個，再放一個回去」：每輪都要重新知道誰最大，而且集合一直在變，這正是優先佇列。用同一個 MinHeap，傳入 less = (a, b) => a > b 讓它變成 max-heap：

  1. 全部 push 進 max-heap。
  2. 還有兩批以上時：pop 出 x、pop 出 y；x ≠ y 就 push(x − y)。
  3. 剩一批就回傳它，沒有剩就回傳 0。

手算 [3, 9, 5, 2, 10, 2]：取 10、9 剩 1；取 5、3 剩 2；取 2、2 用掉；取 2、1 剩 1；只剩 1，答案 1。注意第二輪放回去的 1，到第四輪才被拿出來：放回去的值會依大小回到該在的位置，這就是為什麼不能只排序一次就從頭拿。

複雜度：每一輪至少少一批，最多 n 輪，每輪 O(log n)，總共 O(n log n)。對照每輪都 sort 再拿最前面兩個：每輪 O(n log n)，n 輪就是 O(n² log n)，跟上一節的出單機是同一個差距。寫的時候還有兩個容易踩的坑：不給比較函式的 sort()、直接改傳進來的陣列，都收在「常見錯誤」。

這題每輪都要拿出最大的，所以全部的批次都得放在 heap 裡。如果只關心「前幾名」，能不能不要全部都存？

店長只要前 k 名：為什麼找最大的反而用 min-heap？

店長想知道菜單上第 k 高的價格是多少，重複的價格各算一次（[110, 110, 80] 的第 2 高是 110）。對應 LeetCode 215. Kth Largest Element in an Array。這題有三種做法，面試時最好都說得出來，並說出各自適合的情況：

做法時間額外空間什麼時候用
複製一份、由大到小排序，取索引 k − 1O(n log n)O(n)最好寫、最不容易錯；n 不大時就用它
大小為 k 的 min-heapO(n log k)O(k)k 遠小於 n；或資料是一筆一筆進來（串流），不能全部存下來排序
quickselect（快速選擇）平均 O(n)，最壞 O(n²)O(1)～O(n)面試官追問「能不能更快」時提出；這課不要求寫

第二種是這節的重點，也是最反直覺的地方：找「最大的」，用的卻是 min-heap。

想法是：heap 裡永遠只留目前看過的最大的 k 個，可以把它想成一個只有 k 個座位的「前 k 名名單」。每看到一個新價格，要回答的問題是「它擠不擠得進名單？」，答案取決於名單裡最低的那個：比它高就擠進來、把它踢掉；不比它高就連名單都進不了。所以要能 O(1) 看到名單裡最小的，這就是 min-heap。而名單裡最小的那個，剛好就是「目前第 k 大」。

  1. heap 不滿 k 個：直接 push。
  2. 已經 k 個：新值比 peek() 大，就 pop 掉頂端、push 新值；否則丟掉新值（它連前 k 名都進不了）。
  3. 全部看完，peek() 就是第 k 大。

下面用 k = 3 跑一遍菜單價格，每一行印出看到的價格、做了什麼、heap 的內容和頂端。執行後看頂端怎麼隨著更高的價格出現而上升，最後一行再用排序對照答案：

heap 最多 k 個，每次操作 O(log k)，n 個值總共 O(n log k)。如果用 max-heap，就得把全部 n 個放進去再 pop k − 1 次：O(n log n) 加上 O(n) 空間，失去了這個做法的意義。前 k 小則反過來，用大小為 k 的 max-heap。

取捨要說清楚：n = 5 萬、k = 10 時，log k 約 3、log n 約 16，heap 比較省；但 JavaScript 內建的 sort 是引擎用 C++ 寫的，常數小，自己寫的 heap 在 n 不大時不一定比較快。真正非用 heap 不可的情況是資料一直進來：例如「即時顯示今天消費金額前 10 名」，每來一筆就跟頂端比一次，記憶體只需要 k 個，這跟出單機「一直有新單進來」是同一種處境。

💡 實務上：資料在資料庫裡時，前 k 名交給 SQL
咖啡店後台的「本月消費金額前 10 名會員」，資料本來就在資料庫，直接寫 ORDER BY total DESC LIMIT 10。有符合 ORDER BY 的索引時，PostgreSQL 可以直接從索引依序讀出前 10 筆，不用掃完整張表（PostgreSQL 課第 20 課，PostgreSQL 18 文件 11.4 節）。把整張表撈回應用程式再排序，是常見的效能問題。大小為 k 的 heap 留給資料不在資料庫、或是一筆一筆即時進來的情況。

價格這題，比較的就是值本身。店長的下一個問題要比的不是值，而是「出現了幾次」，而且次數一樣的很多。

最常點的前 k 種飲料：先計數，並列時誰在前面？

今天的點單是一串飲料代碼，例如 ['LAT', 'AME', 'LAT', 'CAP', 'AME', 'LAT', 'TEA']。要回傳點最多次的前 k 種，次數多的在前。對應 LeetCode 347. Top K Frequent Elements。

代碼本身沒有大小可比，要比的是次數，所以分兩步：

  1. 計數：用 Map 做頻率表（第 4 課）。不要用一般物件：代碼剛好是 'constructor'、'toString' 時，會讀到原型上的函式。
  2. 取前 k：把 (代碼, 次數) 依次數排序取前 k；或用上一節大小為 k 的 min-heap，只是比較的是次數。

並列時誰在前面

LAT 3 次、AME 2 次、CAP 和 TEA 各 1 次，k = 3 時第三名是 CAP 還是 TEA？原題說答案順序不限，但實際的報表（例如「熱銷排行」）每次重新整理順序都不一樣，使用者會以為資料變了。這跟出單機「兩張單都剩 10 分鐘」是同一個問題：並列的規則要先定義，面試時也要先問。這課約定：次數相同時，先出現的在前。

用排序做時，這個約定剛好可以免費做到，靠兩件學過的事：

  • Map 依插入順序迭代，所以 [...counts] 已經是第一次出現的順序。
  • sort 從 ES2019 起是穩定的（第 8 課）：比較結果相等的元素，保持原本的先後順序。

兩件事合起來：先依第一次出現排好，再依次數穩定排序，次數相同的自然維持「先出現的在前」。下面的點單多加了一筆 'constructor'，執行後看三件事：頻率表的順序、排序後 CAP 仍在 TEA 前面、最後一行一般物件讀到的不是次數。

用 heap 做時，穩定排序幫不上忙：heap 的交換會打亂相等元素的先後，它不是穩定的。比較函式要自己把並列規則寫進去：先比次數，次數相同再比第一次出現的位置。所以要先記下每個代碼第一次出現的索引，這跟外送單的 less 補上單號是同一招。

四種做法並排比較，n 是點單筆數、m 是飲料種類數：

做法時間（n 筆點單、m 種飲料）說明
Map 計數 + 排序O(n + m log m)最好寫，並列規則靠穩定排序
Map 計數 + 大小為 k 的 heapO(n + m log k)m 很大、k 很小時省；並列規則寫進比較函式
Map 計數 + 桶子（bucket）O(n + m)次數最多是 n，開 n + 1 個桶子，buckets[次數] 放代碼，從大的桶子往回收集到 k 個
每次掃描頻率表找最大的、刪掉，做 k 次O(n + m × k)m、k 都大時太慢（練習 4 會擋）
💡 實務上：SQL 排行榜要補一個不會重複的排序欄位，並列規則問 PM
後台的「本週熱銷前 10 名」通常在資料庫用 GROUP BY 計數再 ORDER BY 次數取前 10。只排次數時，次數相同的順序資料庫不保證，每次重新整理可能不一樣；搭配分頁（LIMIT／OFFSET）時，同一個品項還可能在第 1 頁和第 2 頁都出現、或兩頁都不見。做法是在 ORDER BY 最後補一個不會重複的欄位（例如品項 id），讓順序固定。並列時該怎麼排（先上架的在前？名稱排序？）是產品決定，寫程式前先問 PM，而不是由寫程式的人隨手決定。

從出單機到熱銷排行，用的都是同一個 heap，差別只在 less 怎麼寫、heap 留多少個。練習照這個順序走：先寫出 heap 本身，再用它解這三題。heap 在合併多條排序串列、最短路徑等問題的延伸用法，整理在下面的「補充與查表」。

補充與查表

主線用不到、但寫程式或面試被追問時會用到的細節。

>> 1 的限制

x >> 1 是右移一個位元，對 0 以上的整數等於 Math.floor(x / 2)：5 >> 1 = 2、4 >> 1 = 2。用它只是寫起來短；它會把數字轉成 32 位元整數，所以只適合陣列索引這種不會超過 21 億的小整數。寫 Math.floor((i - 1) / 2) 一樣對。

交換那一行為什麼以 ; 開頭

行首的 ; 是因為這門課不寫分號：上一行結尾接著一個 [ 開頭的行，JavaScript 會把兩行黏成 break[heap[i], …]，所以在 [ 開頭的那行前面補一個分號。用一個 swap(i, j) 函式就不用煩惱這件事，練習 1 的起始程式會給你。

一次建好整個 heap：heapify

把 n 個元素一個一個 push 進去是 O(n log n)。另有一種從底部整理的建法（heapify）是 O(n)，知道名字就好，這課的練習不需要。

記憶體的「heap」是另一件事

你可能聽過「物件存在 heap 上」，或在 Chrome DevTools 看過 heap snapshot：那是記憶體裡存放物件的區域，跟這課的資料結構同名但無關。

同一招的延伸

  • 合併 k 條已排序的串列（LeetCode 23. Merge k Sorted Lists）：幾家分店各有一條依時間排好的訂單，要合成一條。把每條的第一筆放進 min-heap；pop 出最早的一筆，再把它那條的下一筆 push 進去。heap 永遠只有 k 個，總共 O(N log k)，N 是全部筆數。第 8 課合併兩條用雙指標，k 條就換成 heap。
  • 最短路徑：第 20 課的 BFS 只能處理每一步代價相同的圖；每條路代價不同（外送時間）時要用 Dijkstra 演算法，它的核心就是「每次從 min-heap 拿出目前距離最短的點」。
  • 排程：「下一個要執行的工作」是到期時間最早的那個，計時器、工作排程器內部常用 heap。

練習

練習 1 寫出 heap 本身，練習 2～4 用它（或排序）解題。每題都有計時測試：每次都重新排序或重新掃描的寫法會太慢判錯（第 2 課：計時不過就是複雜度不夠）。傳進來的陣列在測試時是凍結的，改到它會判錯。

練習 1：完成 MinHeap<T>（class 見 TypeScript 課第 23 課，<T> 是第 19 課的泛型：元素型別由使用的人決定）：constructor(less)，less(a, b) 回傳 true 表示 a 要比 b 先出來；push(x)、pop()（拿出最優先的，空的時候回傳 undefined）、peek()、size 已經寫好一部分。請補完 push、pop、siftUp、siftDown，用索引公式在陣列上調整，不能用 sort（測試期間 sort 會丟錯）。測試會用數字的 min-heap、max-heap 和物件各測一次，最後放 5 萬個、再交錯「拿一個、放一個」2.5 萬輪、最後全部拿完並計時，只有 push、pop 都是 O(log n) 才會通過。

練習 2：寫 lastBatch(weights)：每一輪取最重的兩批 x ≥ y，相等就兩批都用掉，不相等就把 x − y 放回去；回傳最後剩下的重量，沒有剩下回傳 0。起始程式附上了練習 1 的 MinHeap 參考解，可以直接用（想想 less 要怎麼傳）。不要修改 weights。計時測試用 5,000 批，每一輪都重新排序的寫法會太慢。對應 LeetCode 1046. Last Stone Weight。

練習 3：寫 kthHighestPrice(prices, k)：回傳第 k 高的價格，重複的價格各算一次（[110, 110, 80] 的第 2 高是 110）；1 ≤ k ≤ prices.length。建議用大小為 k 的 min-heap（自己寫 heap 或貼上練習 2 的 MinHeap）；複製後排序也可以通過。不要修改 prices。計時測試用 2 萬個價格、k = 1 萬，每次找出最大的再刪掉、做 k 次的寫法會太慢。對應 LeetCode 215. Kth Largest Element in an Array。

練習 4：寫 topDrinks(codes, k)：回傳點最多次的前 k 種飲料代碼，依次數由多到少；次數相同時，先出現的在前。1 ≤ k ≤ 飲料種類數。代碼可能是任何字串（包括 'constructor'）。計時測試用 5 萬筆點單、4,000 種飲料、k = 2,000，每次掃描頻率表找最大的、做 k 次的寫法會太慢。對應 LeetCode 347. Top K Frequent Elements（本題規定了並列順序）。

練習 5：一個 min-heap 存成陣列 [5, 12, 8, 20, 15, 9, 30]。下面哪個說法正確？

✓ heap 的順序條件只管父子關係。9 在第 2 層、12 在第 1 層，但 9 比 12 小，因為它們不在同一條路上。a 錯：陣列明顯不是遞增的，heap 本來就不保證排序，要排序得一直 pop。b 錯：第二小的一定是根的某個子節點（索引 1 或 2），這裡是索引 2 的 8，不一定是索引 1。

練習 6：要從 100 萬筆即時進來的消費金額中，隨時知道「目前前 10 高」。用大小為 10 的哪一種 heap？

✓ 每來一筆，要回答的問題是「它能不能擠進前 10？」，也就是跟前 10 名裡最低的那個比，所以要 O(1) 看到最小值：min-heap。heap 最多 10 個，每筆 O(log 10)。b 錯：大小為 10 的 max-heap 頂端是最高的，要淘汰的卻是最低的，它埋在下面找不到；要用 max-heap 只能把 100 萬筆全部放進去，O(n) 空間。c 錯：上面說的就是兩者的差別。

練習 7：同事的外送系統每收到一張新單就把整個待辦陣列 sort 一次，再從最前面拿。他說「sort 是引擎內建的，很快，跟 heap 差不多」。單量有 n 張時，怎麼回答最精確？

✓ 每放一張單：sort 要處理整個陣列，至少 O(n)，一般是 O(n log n)；heap 只沿一條路往上，O(log n)。放 n 張總共是 O(n² log n) 對 O(n log n)，本課實測 5,000 張就差了上千倍。a 錯：內建的常數小，只在 n 很小時有意義。c 錯：O(n log n) 是單次 sort 的成本，不是 heap 單次 push 的成本；把 n 個元素全部建成 heap 才是 O(n log n)。

常見錯誤

  • sift down 跟錯的子節點交換：只看左子節點、或第一個比它小的就換，會讓換上去的值比另一個子節點大，heap 壞掉。要先找出兩個子節點中較優先的那個，再決定換不換。
  • 索引公式差一：索引從 0 開始時，父節點是 (i − 1) >> 1，子節點是 2i + 1、2i + 2。寫成 i >> 1、2i 是從 1 開始的版本，混用會找錯父節點。
  • pop 用 shift 補洞：所有父子關係錯位，而且 shift 是 O(n)。要把最後一個移到根，再往下調整。
  • 只剩一個時 pop 又把它放回根：pop 出最後一個之後陣列已經空了，再寫 items[0] = last 會把拿走的元素放回去。先檢查還有沒有剩。
  • 讀子節點沒檢查索引：右子節點可能不存在，less(undefined, x) 在物件上會丟錯，在數字上會默默算錯。
  • sort() 沒給比較函式：預設依字串排，[10, 9, 2] 會排成 [10, 2, 9]（第 8 課）。排數字一定要傳 (a, b) => a - b 或反過來。
  • 直接改傳進來的陣列：weights、prices 是呼叫的人的資料，在上面 sort 或 pop 會改到別人的東西。先複製，或全部放進 heap 再操作。
  • Top K 用錯 heap：前 k 大用 min-heap（頂端是第 k 大，用來淘汰）；前 k 小用 max-heap。
  • 並列沒有定義順序：結果每次可能不一樣。面試先問；工作上寫進規格與比較函式。
  • 頻率表用一般物件：'constructor'、'toString' 會讀到原型上的函式。用 Map。
  • 以為 JavaScript 有內建 priority queue：沒有。面試時自己寫，或先問能不能假設有一個。

小結

  • 出單機要的是優先佇列：一直放進來、每次拿出最優先的那個。用 heap 實作，push、pop 都是 O(log n)，peek 是 O(1)；它只維持「誰最小」，所以比每次排序快一個 n 的量級。
  • heap 是完全二元樹加上「父節點不大於子節點」；存成陣列，父節點 (i − 1) >> 1、子節點 2i + 1、2i + 2。陣列不是排序好的，只有根一定最小；高度約 log n，這是每個操作只要 log n 步的原因。
  • push：放到最後、往上調整；pop：記下根、最後一個移到根、跟較小的子節點往下調整。空的時候回傳 undefined。
  • 傳入 less(a, b)，同一個類別可以是 min-heap、max-heap，也能比較外送單這種物件；並列規則（例如到期相同比單號）也寫在 less 裡。
  • 前 k 大：大小為 k 的 min-heap，頂端是名單裡最低的、用來淘汰，O(n log k)、O(k) 空間，適合資料一直進來的情況；資料都在手上、n 不大時，排序最簡單；資料在資料庫裡就交給 ORDER BY … LIMIT。
  • 前 k 常見：Map 計數，再排序或用 heap；並列規則要先定義，Map 的插入順序加上穩定排序可以做到「先出現的在前」，用 heap 時要寫進比較函式。
