階段 1：解題基本功 · 第 1 課

解題流程：讀題、手算、先寫出暴力解

顧客拿著一張 160 元禮券到櫃檯，想點兩杯不同的飲料剛好用完。店長請你在點餐系統加一個功能：給菜單價格和禮券金額，找出是哪兩杯。這就是 LeetCode 第 1 題 Two Sum 換成咖啡店的樣子。很多人第一次看到它，都卡在同一個地方：題目看得懂，但不知道第一行要寫什麼。

卡住的原因通常不是少背了一個技巧，而是少了一套「拿到題目先做什麼、再做什麼」的流程。這一課把流程建起來，用它寫出禮券題一個一定對的版本，並且知道怎麼確認它真的對。之後 26 課的每一題都照這套流程走。

這課的路線：
  1. 拿到題目先做什麼：解題七步驟是什麼、為什麼是這個順序（開場問題的最小答案）。
  2. 先拿一個簡單需求「今日最高單筆訂單」練第 1、2 步：寫程式前要問清楚什麼、怎麼手算，程式錯時怎麼用手算表找到錯的那一行。
  3. 回到禮券題練第 3 步：想不出好方法時，先寫出試遍所有組合的暴力解；它留下的「會不會太慢」交給第 4、5、7 步和之後的課。
  4. 第 6 步邊界情況：範例都過了為什麼還會錯，每題要自己補哪些測試。
  5. 到 LeetCode 上自己寫：題目頁的簽章、範例、限制各告訴你什麼。
這課會用到：
  • TypeScript 課第 13 課的型別註記：在參數或變數後面寫 : number[] 標明型別；[number, number] 是 tuple，固定兩格的陣列。
  • TypeScript 課第 15 課的聯合型別：number | null 表示值可能是數字，也可能是 null。

拿到一題不知道從哪下手，該先做什麼？

回答之前，先把這門課會一直用到的幾個詞講清楚。

演算法（algorithm）是解決一個問題的明確步驟：給同樣的輸入，一定得到同樣的結果。「從頭看到尾，記住看過最大的那個」就是一個找最大值的演算法。它不一定要是程式，寫在紙上、說出口都算；寫成程式只是讓電腦照著做。

資料結構（data structure）是資料在記憶體裡的擺放方式。同一份菜單價格，可以排成一列放在陣列裡，也可以存成「價格 → 第幾杯」的對照表（Map）。擺法決定哪些操作快、哪些慢：在陣列裡找某個價格，要從頭一格一格看；在 Map 裡可以直接查到，第 4 課會講為什麼。禮券題最後能變快，靠的就是換資料結構。

這門課每一題都是一個函式。輸入（input）是函式收到的參數，輸出（output）是回傳的值。判分時，隱藏測試會用很多組輸入呼叫你的函式，比對回傳值，所以「印出來看起來對」不算數，回傳值對才算。

有了這些詞，解題的流程是七步：

為什麼是這個順序：每一步都先排除一種錯，下一步才不用同時操心它。重述題目排除「寫得很漂亮，但寫的不是題目要的」；手算排除「自己也說不清程式每一步該做什麼」；暴力解先拿到一個一定對的答案，之後所有改進都拿它來對照；找重複、改進、說出複雜度處理「太慢」；邊界情況處理「平常都對，特殊輸入才錯」。開場那種卡住，多半是跳過前三步直接想最佳解：題意、細節、速度要同時想，結果哪一件都想不清楚。

這一課練 ①②③ 和 ⑥；④⑤⑦ 先認識名字，第 2 課講複雜度，第 5 課把禮券題改成一次走完。

禮券題要同時處理「兩杯」「不同」「剛好等於」，拿來第一次練流程，要顧的東西太多。所以先拿一個一看就知道怎麼寫的需求，專心看第 1、2 步在做什麼。店長說：「幫我找出今天金額最高的一筆訂單。」

第 1 步：寫程式前，題目還有哪裡沒說清楚？

店長這句話聽起來很明確，但要寫成函式時，至少有四件事他沒說：輸入長什麼樣、要回傳什麼、輸入的範圍、找不到時怎麼辦。

第三件叫做限制條件（constraints）：題目保證輸入落在什麼範圍，例如「最多 10 萬筆」「金額是 1～10,000 的整數」。它決定兩件事。一是你的寫法夠不夠快：10 筆和 10 萬筆能接受的寫法不一樣，第 2 課會教怎麼算。二是要不要處理負數、0 這類特殊值：題目保證金額是正整數，你就不用為負數多寫判斷；沒保證，就得自己處理。

下面的表把四件事在這一題填一次。輸入的型別寫成 readonly number[]：readonly 表示函式只讀不改這個陣列，寫了 push、sort 這類會修改陣列的呼叫，TypeScript 直接報錯（第 3 課詳講）。要防的是：陣列是呼叫的人傳進來的，你在函式裡改了它，呼叫的人手上的資料也跟著變。

表的右欄有些是你猜的，店長沒說。重述時，把這些模糊的地方寫成問題：

  • 金額會不會是負的？退款算不算一筆訂單？
  • 兩筆一樣高，要回傳哪一筆？
  • 要回傳金額，還是那筆訂單的索引？

每一個答案都會改變程式。如果資料裡可能出現負數（退款、差額），找最大值的初始值就不能隨便寫 0（下一節會看到它怎麼出錯）；兩筆一樣高回傳哪一筆、回傳金額還是索引，決定了回傳值的型別。面試時，這些就是要問面試官的問題：問了代表你在確認題意，而不是用猜的。

問完之後，把答案寫成一行函式簽章（function signature）。函式簽章是函式的名稱、參數與回傳值的型別（TypeScript 課第 18 課）。它是重述的終點，因為型別沒有模糊空間，口頭講「回傳最高的那筆」可能有兩種理解，寫成型別就只剩一種：

function maxOrder(totals: readonly number[]): number | null

回傳型別 number | null 把「找不到」也寫進型別：呼叫的人沒處理 null 就直接拿去算，TypeScript 會報錯，這個情況不會被忘掉。這門課找不到答案一律回傳 null，不用 -1 或空陣列，除非題目另外說明。

簽章說清楚了「要什麼」，但還沒回答「怎麼做」。你心裡大概知道：從頭看到尾，記住最大的。這句話離程式還有一段距離：一開始的最大值是多少？每看一個元素要做什麼？這些要一格一格寫出來，就是第 2 步。

💡 實務上：工作中的需求比題目更模糊，先問清楚再動手
PM 開的票常常只有一句「後台首頁顯示今日最高單筆訂單」，跟店長這句話一樣。動手前要問的跟上面一樣，只是更多：「今天」是用台灣時間還是伺服器時間算？已取消、已退款的訂單算不算？今天還沒有訂單時畫面顯示什麼？資深工程師會把問到的答案寫回票裡，讓 PM、設計和測試看到的是同一份規格；漏問的代價通常是做完才發現要重做。

印出來的表跟紙上的一樣，看起來手算只是多做一次。它真正的用處在程式錯的時候。

第 1 步問過金額會不會是負的；店長的下一個需求，資料本來就有負數。隔週店長又說：「同樣的方法，幫我找出營收最好的一天。」diffs 是每天營收和目標的差額，沒達標就是負數。很多人寫最大值時把初始值寫成 0，理由是「金額不會是負的」。這個理由對訂單金額成立，換到差額就不成立了。下面是初始值寫 0 的版本，用 [-30, -10, -50] 跑，執行後對照每一列的 best：

表格第一列就看得出問題：x 是 -30，best 還是 0，因為 -30 不比 0 大。之後每一列都一樣，最後回傳一個陣列裡根本沒有的 0。根本原因是 0 不是資料裡的值，而是你替資料假設的下限；資料一旦低於這個下限，答案就錯。

修法是用第一個元素當初始值，它一定是資料裡的值；或用 -Infinity，任何數都比它大。兩種都要另外處理空陣列：前者沒有第一個元素可拿，後者在空陣列時會回傳 -Infinity，不是簽章說好的 null。

卡住時不要直接看解答。挑一組出錯的小輸入，先在紙上寫出「應該」的表，再讓程式印出「實際」的表，第一個不一樣的列就是錯的地方。

最大值這種題目，手算表一畫就知道程式怎麼寫。回到禮券題就不一樣了：試著畫它的手算表，你會發現不知道每一列該放什麼，因為還沒想出「怎麼找到那兩杯」。想不出好方法的時候，需要第 3 步。

第 3 步：想不出好方法時，怎麼先寫出一定對的版本？

回到開場的禮券題：顧客有一張 160 元禮券，想點兩杯不同的飲料剛好用完。菜單價格是 [80, 110, 70, 90]（美式咖啡、拿鐵、可頌、伯爵紅茶），回傳兩杯的索引。

先照第 1 步重述，把模糊的地方問清楚：

  • 回傳價格還是索引？要索引：點餐系統要知道是菜單上的哪兩項，而兩項的價格可能一樣，只回傳價格分不出是哪一項。
  • 同一杯能不能點兩次？不行，題目說兩杯不同的。
  • 有多組時回傳哪一組？i 最小的那組，i 一樣時取 j 最小。
  • 找不到怎麼辦？回傳 null。

回傳兩個索引，型別寫成 [number, number] | null。[number, number] 是 tuple：固定兩格、兩格都是數字的陣列，比 number[] 多說了「剛好兩個」。簽章是：

function giftCardPairBrute(prices: readonly number[], budget: number): [number, number] | null

手算卡住的地方是「怎麼找」。暴力解（brute force）的做法是不去想聰明的找法，把所有可能都試一遍：每一種兩杯的組合都加加看。它通常慢，但一定對，因為沒有任何一種組合被漏掉。把四杯的所有組合畫成表，這張表就是禮券題的手算表：

i \ j0（80）1（110）2（70）3（90）
0（80）同一杯190150170
1（110）重複同一杯180200
2（70）重複重複同一杯160 ✓
3（90）重複重複重複同一杯

只需要看對角線右上方：對角線是同一杯點兩次，左下方的 (1, 0) 跟 (0, 1) 是同一組。寫成程式就是第二層迴圈的 j 從 i + 1 開始，同時保證了 i < j。下面的程式每試一組就印一列，執行後看兩件事：每一組是怎麼被試到的，以及最後印出試了幾組。

印出的順序就是表格右上方一列一列往下讀。160 元在試到第 6 組 (2, 3) 時找到；100 元把 6 組試完都不行，回傳 null。回傳的是索引 [2, 3]，不是價格 [70, 90]：這是重述時就決定好的事，程式只是照做。

暴力解看起來笨，卻是這門課每一題的第一步，原因有兩個。第一，它確認你懂題目：寫得出暴力解，代表輸入、輸出、什麼算答案都弄清楚了，剩下的只是速度。面試時先說出暴力解，面試官可以馬上糾正你對題意的誤解，不用等你寫完最佳解才發現方向錯了。

第二，它是對照答案。之後寫更快的版本時，用很多組隨機輸入同時跑兩個版本，結果不一樣就是快的版本錯了。這門課的隱藏測試就是這樣做的：拿參考解跟你的程式比對幾百組隨機案例。工作上重寫一段複雜邏輯時也一樣，先留著舊版當對照。

暴力解對了，但它留下兩個問題。一是它會不會太慢：4 杯試了 6 組，菜單變大時要試幾組？二是它真的對嗎：兩組範例過了，不代表每一種輸入都對。

💡 實務上：資料量小時，暴力解常常就是最後的版本
咖啡店的菜單只有幾十項，在後台做「找出兩樣加起來剛好 160 元的組合」，雙迴圈跑起來使用者完全感覺不到差別。工作上先求正確、好讀，等資料量真的會變大（例如每天累積的訂單），或量測到真的慢了再改進。要考量的是「這份資料會不會一直長大」：菜單不會，訂單紀錄會。Code review 時，資深工程師比較常問的是「這個列表最多會有多少筆」，而不是要你一開始就寫出最快的版本。

暴力解會不會太慢？第 4、5、7 步要做的事

先看第一個問題。它是之後幾課的主線，這裡只看這三步各要做什麼，讓你知道寫完暴力解之後的路。

④ 找出重複做的工作。看暴力解在做什麼：對每一杯 i，都把後面所有飲料重新掃一遍，找「價格是 160 − prices[i] 的那杯」。i = 0 時找 80 元的那杯，i = 1 時找 50 元的那杯，每一次都是同一個動作「找某個價格在哪」，而且每次都重新掃一遍，前一輪掃過的結果沒有留下來。重複做的工作，就是可以省下來的地方。

⑤ 改進。把看過的價格記在 Map 裡，「找」就變成直接查，不用再掃一遍。這就是第一節說的換資料結構（第 4、5 課）。

⑦ 說出複雜度。輸入變大時，程式要跑幾步。4 杯飲料試了 6 組；1 萬杯要試將近 5,000 萬組。第 2 課教你不用真的去數，從迴圈的形狀就能說出這個數字怎麼長大。

這三步都在處理速度，前提是手上已經有一個對的版本，改快之後才有東西可以對照。所以在改快之前，要先回答第二個問題：暴力解真的對嗎？第 6 步在流程圖上排在改進之後，是因為每改一次都要再檢查一次，改過的版本最需要重新驗證；但第一次檢查從暴力解寫完就開始，先確認拿來對照的版本本身是對的。

第 6 步：範例都過了，為什麼還會錯？

回想第 2 步初始值寫 0 的程式：拿訂單金額 [80, 110, 70] 測，答案完全正確；換成全是負數的差額才出錯。題目給的範例通常只有一兩組「正常」的輸入，這種錯誤用範例測不出來。而會出錯的輸入通常屬於兩類：一是輸入落在範圍的邊緣，例如空的、只有一個、答案在頭或尾；二是輸入超出寫程式時默默做的假設，例如以為值不會低於 0。初始值寫 0 的錯屬於第二類。

邊界情況（edge case）指的就是這兩類輸入。第一類是範圍的邊緣：空陣列、只有一個元素、答案在第一個或最後一個。第二類是違反心裡假設的輸入：下面清單上的「負數與 0」「全部一樣」屬於這類，會不會出現要回頭對照題目的限制條件才知道。程式最容易在這裡出錯，因為寫程式時腦中想的是正常的例子；迴圈從哪裡開始、初始值是多少、找不到時回傳什麼，這些決定在正常輸入下看不出對錯，到了邊緣才露出來。

所以每一題都要自己對照一張清單。下面把這課的兩題各填一次：

邊界情況找最大差額禮券兩杯（160 元）
空的[] → null[] → null
一個元素[7] → 7[80] → null（同一杯不能點兩次）
兩個元素[3, 8] → 8[80, 80] → [0, 1]
重複的值[5, 9, 9] → 9[80, 80, 70, 90] → [0, 1]（有多組時取 i 最小）

💡 實務上：上線後的 bug 很多出在邊界情況
客服回報的問題常常是「新顧客還沒有任何訂單，會員頁就壞了」「購物車只剩一項時，刪除按鈕沒反應」，都是空的、只有一個這類情況。前端畫面也要對照同一張清單：列表是空的要顯示什麼、只有一筆時版面會不會跑掉、API 回 null 時會不會整頁白掉。修 bug 時，先把出錯的那組輸入寫成一個測試，看它失敗，修好後看它通過；測試留著，之後有人改壞同一個地方會先被抓到。

到 LeetCode 上自己寫時，題目頁的三塊各告訴你什麼？

這門課的題目都改寫成咖啡店情境，並標出「對應 LeetCode 題號」。做完一課後，到 leetcode.com 搜尋那個題號，自己再寫一次。LeetCode 的題目頁固定有三塊，剛好對應第 1 步要確定的四件事。下面用禮券題示範這種格式（內容是本課自己寫的）：

  • Example：手算用的現成例子，也是你的第一組測試。但它不含邊界情況，清單上的項目要自己補。
  • Constraints：回答「限制條件」和「找不到時」，是最常被跳過、其實最重要的一塊。prices.length <= 10^4 告訴你最多 1 萬筆，雙迴圈的暴力解大約 5,000 萬步，通常還過得了；如果是 10^5，暴力解就會太慢。限制和速度的對照在第 2 課。1 <= prices[i] 告訴你不用處理負數和 0。「Exactly one valid answer exists」表示不用處理找不到，也不用煩惱有多組時回傳哪一組。

按下 Submit 後，LeetCode 用隱藏的測試資料跑你的程式：全對是 Accepted，答案錯是 Wrong Answer，太慢是 Time Limit Exceeded。這門課的判分也一樣：隱藏測試包含邊界情況和隨機案例，需要更好複雜度的題目還會用大資料量計時。

下面的練習照這課的順序走：練習 1 是初始值的陷阱，練習 2 練邊界清單，練習 3 練手算表，練習 4 是禮券題的暴力解。

練習

練習 1：diffs 是每天營收和目標的差額（可能是負數）。補完 maxDiff：回傳最大的那一個；空陣列回傳 null。不能修改傳進來的陣列。

練習 2：寫 countAffordable：回傳價格小於或等於預算的飲料有幾杯（回傳數量，不是陣列）。剛好等於預算也買得起。寫完先對照邊界情況清單想一遍：沒有飲料、預算 0、全部買得起、全部買不起。

練習 3：手算表。firstOver100 回傳第一筆超過 100 元的訂單索引（剛好 100 不算）。在函式裡面加上 console.log（隱藏測試會拿別的輸入呼叫它，所以不能在函式外面把答案寫死），讓它每一步印出一列，格式是 i=0 total=80 超過=false（等號前後沒有空白，欄位之間一個空白）；找到時再印一列 答案=索引（例如 答案=2）然後停止；整個陣列都沒有時印 答案=null。先在紙上寫出兩組輸入應該印出的每一列，再寫程式對照。

練習 4：禮券暴力解（對應 LeetCode 1. Two Sum，這課只做暴力解）。寫 giftCardPairBrute：從菜單價格裡找兩杯不同的飲料，價格加起來剛好等於禮券金額，回傳兩個索引 [i, j]（i < j，是索引不是價格）。有多組時回傳 i 最小、再來 j 最小的那一組；找不到回傳 null。不要看上面的範例，先自己畫出組合表再寫。

練習 5：你的程式通過了題目給的兩個範例。接下來該做什麼？

✓ c：題目範例通常只有「正常」的輸入，初始值寫 0 這種錯誤用正常的訂單金額測不出來，要自己補邊界情況。a 錯在範例不含邊界情況；b 錯在同樣的輸入跑幾次結果都一樣，測不到新的情況。

練習 6：面試時拿到題目，你覺得自己大概知道最佳解。怎麼做比較好？

✓ b：說出暴力解只要幾十秒，能確認你和面試官對題意的理解一致，之後改進也有起點；萬一最佳解寫不出來，正確的暴力解仍有分數。a 錯在題意理解錯時整段白寫，也少了改進的說明。c 錯在把時間花在不打算交的版本上：說出來就夠了，除非面試官要你先寫。

練習 7：找最大值時把初始值設成 0，什麼情況會出錯？

✓ a：例如 [-30, -10, -50]，每個數都不比 0 大，best 一直是 0。用第一個元素當初始值（或 -Infinity），另外處理空陣列。b 錯：0 跟陣列大小無關，也不會溢位。c 錯在比得出大小不代表答案對。

練習 8：題目說「回傳哪兩杯飲料」，你回傳價格 [70, 90]，判分要的是索引 [2, 3]。七個步驟中，哪一步沒做好？

✓ b：「哪兩杯」可以指價格也可以指位置，重述題目時就要問清楚，最好直接寫成簽章。a 錯：加總算對了，只是回傳錯東西。c 錯：速度跟回傳格式無關。

常見錯誤

  • 沒讀限制就開始寫：不知道 n 最大多少，就不知道暴力解夠不夠快、要不要處理負數。限制和速度的對照在第 2 課。
  • 只測題目給的範例：範例過了不代表對，自己補邊界情況清單上的每一項。
  • 初始值隨便寫 0：全部是負數時答案錯。用第一個元素或 -Infinity，空陣列另外處理。
  • 回傳格式跟題目不同：索引與值、null 與 -1、[i, j] 的順序，重述題目時就確認，寫進函式簽章。
  • 為了找答案去排序輸入：sort 會改到傳進來的陣列（呼叫的人的資料也跟著變），排序後索引也對不回原本的位置；不給比較函式時還會照字串排序，[-30, -10, -50].sort() 的最後一個是 -50。
  • 一卡住就看解答：先挑一組出錯的小輸入，對照「應該」和「實際」的逐步表格，第一個不一樣的列就是錯的地方。

小結

  • 每一題都走七步：重述題目、手算、暴力解、找重複的工作、改進、檢查邊界情況、說出複雜度。順序的意義是每一步先排除一種錯：題意、細節、正確性，最後才是速度。
  • 重述題目要確定輸入、輸出、限制、找不到時回傳什麼，最後寫成函式簽章；型別沒有模糊空間。
  • 手算用 3～5 個元素的小例子畫逐步表格；程式錯時，讓程式印出同樣的表格，第一個不一樣的列就是錯的地方。
  • 想不出好方法時先寫暴力解：試遍所有可能，一定對；它確認你懂題目，也是之後改進版的對照答案。禮券題的暴力解在第 4、5、7 步會被改快。
  • 範例過了不代表對：空的、一個元素、重複、負數、全部一樣、答案在頭尾、找不到，每一項都寫一個測試。
  • LeetCode 題目看三塊：函式簽章、Example、Constraints，對應重述時要確定的四件事。

LeetCode 的簽章和這門課的簽章

LeetCode 的 TypeScript 範本常用 number[] 當回傳型別，例如上面示範的 giftCardPair(prices: number[], budget: number): number[]。到 LeetCode 上就照它的簽章寫。這門課改用 [number, number] | null，讓型別把「剛好兩格」和「找不到」說清楚，參數也加上 readonly，避免不小心改到傳進來的陣列。
