階段 3：陣列技巧 · 第 9 課

二分搜尋：範圍與邊界

店長的後台有一張訂單金額表，20 萬筆，已經依金額由小到大排好。這週要加一個「金額查詢」功能，輸入一個金額，回答兩個問題：有沒有一筆剛好 190 元的訂單？以及190 元以上的訂單從第幾筆開始？第二個問題比第一個更常用：知道從第幾筆開始，往後全部都是 190 元以上，「有幾筆」用總數一減就有，分頁也可以直接從那一筆開始顯示。這個功能一天大約會被查 2 萬次。

最直覺的寫法是從頭一筆一筆看，或直接呼叫 indexOf。這種從頭依序比到尾的找法叫線性搜尋（linear search）。這是 O(n)：最壞要看完 20 萬筆，查 2 萬次就是 40 億次比較。問題在於這種寫法完全沒用到「資料已經排好」這件事。這課要學的二分搜尋（binary search）就是專門利用這件事：每次只看範圍中間那一筆，就能一口氣丟掉不可能有答案的一半，20 萬筆只要看 18 筆左右。

二分搜尋的想法一句話就講完，難的是細節：範圍包不包含右端、迴圈什麼時候停、mid 要不要加 1。這些地方寫錯一個字，程式不會報錯，而是漏掉答案或停不下來。所以這課只教一種寫法，從頭用到尾：先用它解決店長的兩個問題，再看同一個骨架怎麼延伸到「沒有陣列」和「不完全有序」的情況，最後回到 20 萬筆、2 萬次查詢實測。

這課的路線：
  1. 從頭找太慢，怎樣一次丟掉一半：用猜數字看出為什麼只要 O(log n)，再看資料沒排序時它怎麼安靜地答錯。
  2. 範圍怎麼寫才不會漏、不會停不下來：左閉右開 [lo, hi)，起點、停止條件、mid 加不加 1 一次定下來。
  3. 店長的兩個問題：有沒有剛好 190 元的訂單（找值），190 元以上從第幾筆開始（lower bound）。這是開場問題的答案。
  4. 同一個骨架的兩個延伸：沒有陣列也能二分（找出第一批壞掉的可頌，跟 git bisect 是同一件事），以及旋轉過、不完全有序的價目表。
  5. 回到開場：20 萬筆查 2 萬次的實測、上線前要檢查的邊界、什麼時候值得為了二分先排序。
這課會用到：
  • 第 2 課的 O(log n)：n 可以除以 2 幾次才變成 1，100 萬筆大約 20 次。
  • 第 8 課的排序：數字要給比較函式 (a, b) => a - b，toSorted 回傳排好的新陣列。

從頭找太慢，怎樣才能一次丟掉一半？

先把訂單放一邊，用一個更單純的遊戲看清楚「丟掉一半」是怎麼運作的，因為它沒有陣列和索引這些細節。朋友心裡想一個 1～100 的數字，你每猜一次，他回答「太大」「太小」或「對了」。最笨的方法是從 1 猜到 100，最多 100 次。聰明的方法是每次猜剩下範圍的中間：猜 50，他說太小，那 1～50 全部不可能，只剩 51～100，一次就丟掉 50 個數字。

程式要記住「答案還可能在哪一段」，用兩個變數表示這一段的兩端：lo 是 low 的縮寫，指這段的開頭；hi 是 high 的縮寫，指這段的結尾。這一段叫做搜尋範圍。每一步取兩端的中間 mid 去猜，再依回答把其中一端移到 mid 旁邊，範圍就縮小一半。程式裡 hi 寫的是 101 而不是 100，原因下一節解釋，現在只要知道範圍是 1～100。執行後看「剩下」那一欄每一步怎麼變，以及最後一行的最壞次數：

每猜一次，剩下的數量大約砍一半：上面找 73 是 100 → 49 → 24 → 11 → 5，最壞的情況是 100 → 50 → 25 → 12 → 6 → 3 → 1，所以最多 7 次。這就是第 2 課說的 log₂ n：n 能除以 2 幾次才變成 1。log₂ 100 ≈ 6.6，log₂ 100 萬 ≈ 20，log₂ 10 億 ≈ 30。資料量變成 1000 倍，只多 10 次比較，所以二分搜尋是 O(log n)。

換回店長的訂單：log₂ 20 萬 ≈ 17.6，每次查詢最多看 18 筆。2 萬次查詢加起來約 36 萬次比較，跟從頭找的 40 億次差了一萬倍以上。不過這個推論藏著一個前提，下一小段就來看它不成立時會怎樣。

什麼時候不能丟一半？資料沒排序時

「猜 50 太小，所以 1～49 也全部太小」能成立，是因為數字有大小順序。陣列沒排序時這個推論就不成立，丟掉的那一半裡可能正好有答案。下面用同一個找法，在沒排序的訂單金額裡找 90，再排序後找一次。執行後比較兩行的結果：

第一步看到中間的 120 比 90 大，就把右半邊（包括 80、90）整個丟掉了。程式不會報錯，只會安靜地回傳錯的答案，這是二分搜尋最危險的地方：測試資料剛好排好時一切正常，上線遇到沒排序的資料才默默答錯。所以用之前要確定資料由小到大排好。

再往深一層看，二分真正依賴的其實不是「排好」本身。想像對每個位置問同一個是非題「這一筆 ≥ 90 嗎？」，在排好的陣列上，答案從左到右一定是 false, false, false, true, true：一旦變成 true，後面就不會再變回 false。這種只往一個方向變的性質叫做單調（monotonic）。看到中間是 true，就知道右邊全部是 true；看到 false，就知道左邊全部是 false，所以可以丟一半。排好的陣列只是保證單調的一種方式，後面「沒有陣列也能二分嗎」那一節會直接拿這個性質用。

知道要丟一半還不夠。上面的程式寫了 hi = 101、lo = mid + 1、hi = mid，這幾個值差一點點就會漏掉答案或停不下來，下一節把它們一次定下來。

範圍怎麼寫，才不會漏掉答案或停不下來？

上一節的程式有三個看起來隨意的選擇：hi 的初始值、迴圈的停止條件、更新時要不要加 1。網路上的二分搜尋有好幾種寫法，例如 hi = n − 1 配 while (lo <= hi) 和 hi = mid − 1。每一種單獨看都是對的，因為它們內部的三個選擇互相配合；混著用才會出錯，這是二分搜尋最常見的 bug 來源。所以這門課只用一種：左閉右開（half-open）範圍，寫作 [lo, hi)。

這個寫法來自數學的區間記號：方括號表示包含那一端，圓括號表示不包含。[lo, hi) 裡有 lo、lo + 1……一直到 hi − 1，不包含 hi。hi 是範圍外面的第一格，當作邊界用。從這個定義，三個選擇都跟著定下來：

  • 一開始是整個陣列：lo = 0、hi = n（不是 n − 1）。範圍裡剛好有 hi − lo = n 個元素。猜數字的 1～100 寫成 [1, 101)，就是上一節 hi = 101 的由來。
  • 範圍是空的條件是 lo === hi，所以迴圈寫 while (lo < hi)：還有元素就繼續。
  • 這跟 slice(lo, hi)、for (let i = lo; i < hi; i++) 是同一個習慣，你每天寫前端已經很熟了。

每一圈先算中間 mid = Math.floor((lo + hi) / 2)。Math.floor 往下取整，這一點等一下證明「不會停不下來」時會用到。接著依比較結果縮小範圍，只有兩種動作：

為什麼一個要 + 1、另一個不用？因為兩端的意義不同。hi 本來就不在範圍裡，寫 hi = mid 剛好把 mid 排除在外，同時讓它當新的邊界。lo 在範圍裡，要排除 mid 就得寫 lo = mid + 1；寫成 lo = mid，mid 會留在範圍裡被重複檢查。

為什麼這樣寫不會無窮迴圈

進迴圈時 lo < hi，而 Math.floor 往下取整，所以 lo ≤ mid < hi：mid 一定在範圍裡，永遠碰不到 hi。lo = mid + 1 讓 lo 至少變大 1，hi = mid 讓 hi 至少變小 1，範圍每一圈都會縮小，最後一定變成空的，迴圈就停了。如果寫成 lo = mid，範圍只剩兩個元素時 mid === lo，更新後範圍完全沒變，就會永遠跑下去。

比背公式更可靠的，是在心裡固定一句「迴圈每一圈都成立」的話。這種每圈都保持成立的條件叫做不變式（invariant）。找值時的不變式是「如果答案存在，它一定在 [lo, hi) 裡」。每次更新 lo 或 hi 之前問自己：我丟掉的部分確定沒有答案嗎？答得出來，這一行就是對的；答不出來，通常就是漏掉答案的地方。後面每一題都會先寫出它的不變式。

範圍的規則定好了，可以回到店長的第一個問題。

店長的第一個問題：有沒有剛好 190 元的訂單？

這是最基本的找值，對應 LeetCode 704. Binary Search。規格是：prices 由小到大、互不重複，回傳 target 的索引，找不到回傳 -1。真實的訂單金額當然會重複，這題先假設不重複，把注意力放在範圍怎麼縮；重複的情況正是第二個問題要處理的。另外，這門課通常用 null 表示找不到，這題沿用經典題的規定回傳 -1，練習也照這個規定。

開場說過，prices.indexOf(target) 是 O(n)：indexOf 不知道陣列排好了，只能從頭一個一個比。二分版本每一圈比較 prices[mid] 和目標，有三種情況。剛好等於，就回傳 mid。比目標小，因為陣列由小到大，mid 和它左邊全部更小，都不可能是答案，lo = mid + 1。比目標大，mid 和它右邊全部更大，hi = mid。三種情況都守住了上一節的不變式：丟掉的部分確定沒有答案。

找 190 只看了三筆就找到。找 100 時，範圍縮到空，lo 和 hi 都停在 3，回傳 -1。注意這個 3：它正好是 100 「應該插入的位置」，在 90（索引 2）和 110（索引 3）之間。也就是說，找不到的時候，二分其實已經算出「從第幾筆開始比目標大」，只是被我們丟掉了。

但店長的第二個問題不是「有沒有」，而是「190 元以上從第幾筆開始」；而且真實資料裡同一個金額會有好幾筆，找到其中一筆就回傳，不保證是第一筆。下一節把這個停下來的 3 變成正式的答案。

第二個問題：190 元以上的訂單從第幾筆開始？

上一節的找值在「等於」時就提早回傳，遇到重複值會拿到任意一筆。店長要的是另一件事：prices 由小到大、可能有重複，回傳第一個大於或等於 target 的索引；全部都比 target 小時回傳 n，表示「後面沒有了」。拿到這個索引 i，從 i 往後全部 ≥ 190，「190 元以上有幾筆」就是 n − i，分頁從第 i 筆開始顯示。

這個位置有個專有名詞叫 lower bound（下界）。它還有另一個意義：把 target 插在這裡，陣列仍然有序，而且會排在相同值的最前面，所以 LeetCode 35. Search Insert Position 問的「插入位置」就是它。

跟第一個問題比，程式只改兩處。第一，不提早回傳：看到等於目標時，左邊可能還有一樣的值，所以「等於」也只能算「可能是答案」，跟「大於」一起處理：prices[mid] >= target 時 hi = mid，把 mid 留在外面當邊界；否則 mid 確定太小，lo = mid + 1。第二，迴圈結束後回傳 lo：範圍縮到空的時候，lo 就停在第一個符合條件的位置；如果全部都不符合，lo 會一路被推到 n。

這兩處改動為什麼是對的，看這一題的不變式：「lo 左邊的全部 < target，hi 和它右邊的全部 >= target」。一開始 lo = 0 左邊沒有東西、hi = n 右邊也沒有東西，不變式成立；每次更新都只把確定的部分劃到正確的一邊；範圍空了，lo === hi，兩者相遇的地方就是小於和大於等於的分界線。

上一節的金額表沒有重複值，看不出「第一筆」的差別，所以這裡換一份有兩筆 80、三筆 110 的小表 totals；110 在這裡扮演 190 的角色。執行後看重複值、不存在的值、比全部大的值各回傳什麼，最後兩行是用同一個函式數筆數：

看結果：110 有三筆，回傳的是第一筆的索引 3；100 不存在，回傳 3（插在 80 和 110 之間）；130 比全部都大，回傳 7，也就是 n。

lower bound 的回傳值可以是 n，這不是索引越界，而是「插在最後面」「後面沒有符合的」。所以 hi 一開始一定是 n；寫成 n − 1，目標比全部大的時候就回傳錯的位置。拿回傳值去讀 prices[i] 之前，要先檢查 i < n。

同一個函式還能回答很多問題。「低於 x 的有幾筆」就是 lowerBound(x)，因為它左邊全部小於 x；「x 有沒有出現」是 i < n && prices[i] === x，所以第一個問題其實也能用它回答；把條件改成 prices[mid] > target，得到第一個大於目標的位置，這叫 upper bound。面試時與其背四五種變形，不如記住「找第一個讓條件成立的位置」這一個骨架，換條件就好。

💡 實務上：級距表與時間軸，都是在找「分界線」
工作中很少有人叫你「寫二分搜尋」，但 lower／upper bound 常常藏在需求裡：滿額折扣與運費級距（訂單 480 元落在哪一級）、會員等級門檻、圖表上滑鼠指到某個時間點時要顯示哪一筆資料。「滿 500」包不包含 500 是產品規則，先跟 PM 確認，再決定條件寫 >= 還是 >，這裡錯一個符號就是客訴。級距只有五六級時，用 find 從頭找就好，大家一眼看得懂；資料在資料庫裡就交給索引和 WHERE total >= 190，不要整批撈回來自己二分。要在大量已排序的記憶體資料上查，可以用 lodash 的 sortedIndex（就是 lower bound），不一定要自己手寫。店長的金額查詢如果資料本來就在資料庫，正確答案就是那一行 WHERE；這課自己寫，是為了看懂索引替你做了什麼。

回頭看 lower bound 的程式，陣列只出現在一個地方：prices[mid] >= target 這個是非題。二分需要的只是「能對任一個位置問是非題，而且答案是單調的」。那如果根本沒有陣列，只有一個能回答是非題、但每問一次都很貴的函式呢？

沒有陣列也能二分嗎？找出第一批壞掉的可頌

換一個例子，因為訂單陣列讀一筆幾乎不花錢，看不出二分真正省下的是「問的次數」。店裡的可頌由烘焙坊供應，某天出了 n 批，編號 1～n。其中某一批開始用到過期的奶油，從那一批之後全部都是壞的。檢驗一批要送實驗室，又貴又慢，要用最少的檢驗次數找出第一批壞的。這題對應 LeetCode 278. First Bad Version。

這裡沒有排好的陣列，只有一個函式 isBad(i)。但它的答案依編號排起來是 false, false, …, false, true, true, …, true，正是第一節說的單調。要找的是第一個 true，跟 lower bound 找「第一個 >= target」是同一件事，只是把 prices[mid] >= target 換成 isBad(mid)：

  • isBad(mid) 是 true：mid 可能就是第一批壞的，答案在 mid 或更左邊，hi = mid。
  • isBad(mid) 是 false：mid 和更早的都是好的，lo = mid + 1。

範圍是編號 1～n，照左閉右開寫成 [1, n + 1)，這是最直接的寫法。但題目保證至少有一批是壞的，所以答案一定 ≤ n，也可以寫 [1, n)：迴圈結束時如果 lo 停在 n，表示已經確定 1～n − 1 都是好的（最後問到的 n − 1 是好的，依單調性它前面也都好），那第一批壞的只能是 n，不必再問一次。兩種都對，後者有時能少問一次，下面的程式和練習 3 用的是後者。

編號可能很大，練習 3 的 n 會到 2³¹ − 1。mid 一樣寫 Math.floor((lo + hi) / 2)；網路上常見的快速寫法 (lo + hi) >> 1 在這個範圍會算出負數，原因和實驗放在課末「補充與查表」。執行後看每次檢驗了哪一批，以及總共檢驗幾次：

每問一次範圍減半，所以最多問 ⌈log₂ n⌉ 次，⌈ ⌉ 表示無條件進位到整數。n = 100 最多 7 次；n = 21 億也只要 31 次。逐批檢驗要 37 次，批次一多，差距就是實驗室帳單上的數字。

這個想法叫搜尋答案的範圍：答案本身不在陣列裡，但你能寫出一個「答案是 x 的話行不行」的是非題，而且它是單調的，就能對答案二分。常見的例子：「機器每小時至少要沖幾杯，才能在 8 小時內做完所有訂單」，沖得越快一定越做得完，所以「每小時沖 x 杯做得完嗎」是單調的，對沖泡速度二分。第 27 課的模擬面試會遇到這種題目。

💡 實務上：git bisect 就是在找「第一個壞掉的 commit」
「上週還好好的，今天結帳頁壞了」，中間有幾十個 commit 時，git bisect 會用跟上面一模一樣的方法，每次挑中間的 commit 讓你標 good 或 bad，幾次就找出是哪個 commit 弄壞的。前提一樣是單調：壞掉之後要一直是壞的，如果 bug 時有時無（測試不穩定、依賴外部 API），標錯一次就會指到錯的 commit。資深的做法是先寫一個能穩定重現問題的小腳本，再用 git bisect run 讓 Git 自動跑完（腳本成功結束算好、失敗算壞），結果可以直接貼進 issue 給大家看。

到這裡，每一題的前提都是「整段單調」。下一節看一個整段不單調、卻仍然能每次丟一半的情況；它沒辦法套模板，考的是你有沒有真的懂「丟掉的那一半確定沒有答案」這句話。

價目表不完全有序時，還能每次丟一半嗎？

店長的訂單表永遠是完整排好的，碰不到這種情況；但面試很愛考一種「原本排好、後來被切開搬動」的陣列，我們用一份價目表來看。這是面試常見的進階題，對應 LeetCode 33. Search in Rotated Sorted Array。一份原本由小到大、互不重複的價目表，從某個位置切開，後段被搬到前面，這個動作叫旋轉。例如 [70, 80, 90, 110, 120, 150, 160] 變成 [110, 120, 150, 160, 70, 80, 90]。切開的那個位置叫斷點，這裡是 160 和 70 之間。整個陣列不再有序，第一節說過，直接套一般的二分會安靜地答錯。還能 O(log n) 找值嗎？

關鍵觀察：斷點只有一個，從任何一個 mid 切開，斷點只會落在其中一半，所以左右兩半至少有一半是有序的。有序的那一半，看它的頭尾就知道目標在不在裡面：在，就往那一半找；不在，答案只可能在另一半。不管哪種情況，丟掉的那一半都確定沒有答案，不變式「如果答案存在，它一定在 [lo, hi) 裡」照樣成立。每一圈的步驟是：

  1. prices[mid] 等於目標就回傳。
  2. 判斷哪一半有序：prices[lo] <= prices[mid] 代表左半 [lo, mid] 沒有斷點，是有序的；否則右半 [mid, hi − 1] 是有序的。mid === lo 時左半只有 mid 自己，一個元素也算有序，所以比較用 <=，讓「相等」歸到左半。
  3. 看目標是否落在有序那一半的最小值和最大值之間。在裡面就往那一半找，不在就去另一半。

回到開場：20 萬筆查 2 萬次，上線前要檢查什麼？

先檢查邊界。二分搜尋的 bug 幾乎都出在範圍的兩端，寫完用這張表在腦中跑一遍。左閉右開的寫法大多不需要特別處理，因為 lo === hi 時迴圈根本不會進去：

輸入找值（第一個問題）lower bound（第二個問題）
空陣列迴圈不跑，回傳 -1回傳 0
一個元素看一次就知道0 或 1
目標比全部小hi 一路縮到 0，回傳 -1回傳 0

再看速度。每一圈範圍至少減半，所以時間是 O(log n)；只用了 lo、hi、mid 三個變數，額外空間是 O(1)。查 q 次就是 O(q log n)。下面照開場的規模實測：20 萬筆、查 2 萬次，目標都在後半段，讓 indexOf 每次都要走過一大段。執行後比較兩行的索引總和（確認答案一樣）和花費的時間：

資料沒排好時，值得先排序嗎？

店長的金額表已經排好，所以可以直接二分。如果拿到的資料沒排序，為了用二分先 sort 划算嗎？答案取決於要查幾次，因為排序本身有成本。只查一次時，排序 O(n log n) 已經比直接線性搜尋 O(n) 慢，再加上一次 O(log n) 的二分也救不回來，不划算。查很多次時，排序一次 O(n log n)，之後每次 O(log n)，總共 O((n + q) log n)；線性搜尋是 O(q × n)。q 一大，先排序就贏了，店長一天 2 萬次查詢就屬於這種。資料庫的索引也是同一個取捨：多花空間和寫入成本維持有序，換來快速查詢。

💡 實務上：先問「要查剛好等於，還是要查範圍」
只查「某個值在不在」（例如訂單編號、優惠碼），第 4 課的 Map／Set 是 O(1)，比排序再二分簡單；要查範圍或「最接近的值」（某段時間內的訂單、離 190 元最近的金額），才需要有序資料加二分。店長的第二個問題「190 元以上從第幾筆開始」是範圍查詢，Map 回答不了，這就是這課要二分的原因。如果資料常常新增，每次插入都要搬動後面的元素才能維持有序，寫入頻繁時要先想清楚值不值得。資料放在資料庫時，這件事交給索引：B-tree 索引讓資料保持有序、每次排除一大部分，跟二分搜尋是同一個想法（PostgreSQL 課第 20 課）。

補充與查表

主線用不到、但會在網路範例和面試裡遇到的細節集中在這裡。

mid 怎麼算：JavaScript 不會溢位，但位元運算會

其他語言的教材常說 (lo + hi) / 2 會溢位，要寫 lo + (hi − lo) / 2。那是 32 位元整數的問題：Java、C++ 的 int 最大約 21 億（2³¹ − 1），兩個大的索引相加就超過了。JavaScript 的數字是 64 位元浮點數，整數到 Number.MAX_SAFE_INTEGER（2⁵³ − 1，約 9 千兆）都精確，Math.floor((lo + hi) / 2) 不會出事。

真正會出事的是網路上常見的「快速寫法」(lo + hi) >> 1。依 ECMAScript 規格，>> 這類位元運算子會先把數字轉成 32 位元有號整數（ToInt32），超過 2³¹ − 1 的部分被丟掉。執行後看第三行：

陣列不會有 21 億個元素，但「搜尋答案的範圍」（例如可頌的批次編號）常常是 1～2³¹ − 1。一律寫 Math.floor((lo + hi) / 2)，就不用記這個例外。

旋轉過的陣列：先找斷點再分段二分

旋轉題的另一種想法是先用二分找出最小值的位置（也就是斷點），斷點兩側各自是有序的；再判斷目標落在哪一段，到那一段做一般的二分搜尋。兩次二分都是 O(log n)，總共也是 O(log n)。不管哪一種，都不能只對整個陣列做一般的二分，因為整體並沒有排序。

練習

四題都要 O(log n)。練習 1、2、4 會在 20 萬筆的陣列上查 2,000 次，並數你每次讀了幾個 prices[i]：二分搜尋每次只讀幾十個，線性搜尋、indexOf、先把整個陣列轉成 Map 都要讀到幾萬個，會被判錯（第 2 課說過，複雜度就是數「做了幾次」）。練習 3 會數 isBad 被呼叫幾次。範圍沒有縮小的寫法會無窮迴圈，引擎 3 秒後停止並判錯。傳進來的陣列被凍結了，不能 sort、push。

練習 1：findPrice(prices, target)：prices 由小到大且互不重複，回傳 target 的索引，找不到回傳 -1。lo、hi、while 和 mid 已經寫好（左閉右開），刪掉 throw，補上比較和更新範圍的三行。對應 LeetCode 704. Binary Search。

練習 2：自己寫完整的 insertPosition(prices, target)：prices 由小到大，可能有重複；回傳第一個大於或等於 target 的索引（lower bound），全部都比較小時回傳 prices.length。用左閉右開的寫法，O(log n)。對應 LeetCode 35. Search Insert Position（本題允許重複，要回傳第一個）。

練習 3：寫 firstBadBatch(n, isBad)：批次編號 1～n，從某一批開始之後全部是壞的（保證至少一批壞），回傳第一批壞的編號。isBad 最多只能呼叫 ⌈log₂ n⌉ + 1 次，而且只能傳 1～n 的整數。n 可能大到 2³¹ − 1，mid 要用 Math.floor 算。對應 LeetCode 278. First Bad Version。

練習 4（進階）：寫 searchRotated(prices, target)：原本由小到大、互不重複的價目表在某個位置被旋轉過（例如 [110, 120, 150, 160, 70, 80, 90]，也可能完全沒旋轉），回傳 target 的索引，找不到回傳 -1。要 O(log n)：每一圈判斷哪一半有序，再看目標在不在那一半。對應 LeetCode 33. Search in Rotated Sorted Array。

練習 5：訂單金額沒有排序，可以直接用二分搜尋找一筆 190 元的訂單嗎？

✓ c。「中間這筆比 190 大，所以右邊全部都比 190 大」只有在由小到大排好時才成立；沒排序時右邊可能正好有 190，二分會安靜地回傳 -1。a 錯在它不是變慢而是答錯；b 的重複與否跟這個前提無關。

練習 6：在 JavaScript 裡算 mid，下面哪個說法正確？

✓ b。JavaScript 的數字是 64 位元浮點數，整數到 Number.MAX_SAFE_INTEGER（2⁵³ − 1）都精確，相加不會像 Java 的 32 位元 int 那樣溢位，所以 a 的擔心在 JavaScript 不成立（那樣寫也沒錯，只是不必要）。c 錯在位元運算子會把數字轉成 32 位元有號整數，lo + hi 超過 2³¹ − 1 時會變成負數。

練習 7：已排序的 100 萬筆訂單，用二分搜尋找一個金額，最多大約要比較幾次？

✓ a。每比較一次範圍減半，2²⁰ ≈ 104 萬，所以 20 次就把範圍縮到 1 個。b 是 √n，跟二分無關；c 是線性搜尋的平均次數。

練習 8：一個沒排序、有 n 筆的陣列，只要找一次某個值在不在裡面。先 sort 再二分，和直接線性搜尋比較？

✓ c。總成本要把排序算進去：O(n log n) + O(log n) 仍是 O(n log n)，比線性搜尋 O(n) 慢。只有要查很多次（q 很大）時，排序一次、之後每次 O(log n) 才划算。a 只看了二分本身；b 忽略了排序的成本。

常見錯誤

  • 混用多種範圍寫法：hi = n − 1 配 while (lo < hi)、hi = mid − 1 配左閉右開，都會漏掉元素。選定左閉右開 [lo, hi)：hi = n、while (lo < hi)、lo = mid + 1、hi = mid，一種寫法用到底。
  • 寫成 lo = mid：範圍剩兩個元素時 mid === lo，範圍不縮小，無窮迴圈。mid 確定不是答案就要 + 1 丟掉。
  • 在沒排序的資料上二分：不會報錯，只會回傳錯的答案。用之前確認資料有序，或條件是單調的。
  • 用 (lo + hi) >> 1 算 mid：位元運算把數字轉成 32 位元整數，範圍超過 2³¹ 時變成負數。寫 Math.floor((lo + hi) / 2)。
  • 找第一個卻在等於時提早回傳：有重複值時拿到的是任意一個。要「第一個」就把等於也歸到 hi = mid，迴圈結束後回傳 lo。
  • 忘了 lower bound 可能回傳 n：直接拿去讀 prices[i] 會得到 undefined，先檢查 i < n。
  • 只查一次也先排序：排序 O(n log n) 比線性搜尋 O(n) 還慢，查很多次才划算。

小結

  • 店長的金額查詢從 O(n) 變成 O(log n)：二分搜尋每次看中間、丟掉不可能的一半，O(1) 額外空間；20 萬筆約 18 次，100 萬筆約 20 次。前提是資料有序，或更一般地說，是非題的答案是單調的；沒排序時它不會報錯，只會安靜地答錯。
  • 固定用左閉右開 [lo, hi)：lo = 0、hi = n、while (lo < hi)；mid 不是答案就 lo = mid + 1，可能是答案或答案在左邊就 hi = mid。範圍每圈至少縮小 1，不會無窮迴圈。每次更新前用不變式檢查：丟掉的部分確定沒有答案嗎？
  • 「有沒有剛好 190 元」是找值：等於就回傳，找不到回傳 -1。「190 元以上從第幾筆開始」是 lower bound：條件 prices[mid] >= target，迴圈結束回傳 lo，可能是 n；它同時是插入位置、「小於目標的有幾筆」。
  • 任何 false…false true…true 的是非題都能用同一個骨架找第一個 true，例如第一批壞掉的可頌、git bisect，以及對「答案的範圍」二分。
  • 旋轉過的陣列：每一圈至少一半有序，先判斷是哪一半，再看目標在不在它的頭尾之間。
  • mid 用 Math.floor((lo + hi) / 2)，不要用 >>；只查「在不在」用 Map／Set，要查範圍才需要有序加二分；查很多次時排序一次才划算。
