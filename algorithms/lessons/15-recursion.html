階段 5：遞迴與樹 · 第 15 課

遞迴入門：終止條件與呼叫堆疊

店長要在後台加一頁「菜單管理」。菜單是一層一層分的：「全部」底下有「咖啡」「茶」「甜點」，「咖啡」底下又有「冷萃」；店員可以自己新增子分類，所以有的分支兩層、有的五層。這一頁要做三件事：把整份菜單照層次縮排印出來；在每個分類旁邊顯示它底下（含所有子分類）一共幾個品項；把報表裡一層包一層的訂單金額攤平成一列。

用迴圈寫會卡住。數第一層要一個 for，數子分類要在裡面再套一個 for，數孫分類還要再套一個。可是你不知道菜單有幾層，就不知道要套幾個迴圈；今天寫死三層，明天店員多加一層就漏算。這種「裡面還有同樣形狀的東西」的資料，要用遞迴來寫：函式只處理眼前這一層，下一層交給自己。這課從最小的遞迴開始，一路做到這頁菜單管理，途中會碰到遞迴最常出事的三個地方：停不下來、疊得太深、同樣的事算很多次。接下來的樹、圖、回溯、動態規劃，全部建立在這課上面。

這課的路線：
  1. 迴圈不知道要套幾層怎麼辦：遞迴的兩個部分（終止條件、把問題縮小一步），先用最小的例子看懂，再想出數菜單品項的做法（開場問題的最小答案）。
  2. 函式呼叫自己時，電腦怎麼記得每一層做到哪：呼叫堆疊，以及遞迴的空間怎麼算。
  3. 堆疊會不會滿：終止條件寫錯、資料太深時丟出的 RangeError，以及菜單由誰編輯決定了能不能放心用遞迴。
  4. 同一個子問題被算很多次會怎樣：用 Fibonacci 看指數時間，再用記憶化降到 O(n)、改成迴圈降到 O(1) 空間。後面的動態規劃就從這裡長出來。
  5. 回到菜單管理：印出整份菜單、手寫 flat 攤平巢狀金額，並看出這種結構就是下一課的樹。
這課會用到：
  • 第 2 課的 Big-O：用 O(n)、O(2ⁿ) 描述輸入變大時步數怎麼長；判分逾時代表複雜度不夠。
  • 第 12 課的堆疊：只從頂端放入、拿出，後放的先拿（後進先出）。
  • 第 4 課的 Map：用鍵存取值，查詢 O(1)。
  • TypeScript 課第 1 課的閉包：內層函式記得外層函式的變數，所以可以把共用的資料藏在外層。

迴圈不知道要套幾層，遞迴怎麼解？

迴圈的問題是層數要寫死在程式裡。遞迴換一個角度：函式不去管總共幾層，只處理眼前這一層，碰到「裡面還有一份同樣的東西」時，就呼叫自己去處理那一份，拿到答案後再組合成自己的答案。這種函式呼叫自己、去解同一個問題的較小版本的寫法，叫遞迴（recursion）。

聽起來像在繞圈子，關鍵在「較小」兩個字：每呼叫一次，問題就縮小一點；縮到夠小時，答案直接知道，不再呼叫，前面等著的每一層才能一層一層拿到答案。

菜單的每個分類底下有好幾個子分類，一個分類要呼叫自己好幾次，一開始就拿它來看容易亂。先用一個每層只呼叫自己一次的問題把骨架看清楚：店裡有 n 位顧客要排隊，一共有幾種排法？

  • 0 位顧客：只有 1 種（什麼都不排）。這個情況不用再拆，直接知道答案。
  • n 位顧客：第一個位置有 n 種選法；選完之後剩下 n − 1 位，他們的排法就是「n − 1 位顧客的答案」。所以 orders(n) = n × orders(n − 1)。

第二句用到了「n − 1 位顧客的答案」，但沒有說它怎麼算，只說它跟原問題是同一種問題、而且小一號。這兩句話正好是每個遞迴函式都有的兩個部分：

  1. 終止條件（base case）：小到不用再拆、直接回傳答案的情況。這裡是 n = 0 回傳 1。它放在函式第一行，因為每一次呼叫都要先檢查「是不是已經小到可以停了」。
  2. 遞迴呼叫：把問題縮小一步（n → n − 1），呼叫自己拿到小問題的答案，再組合成這一層的答案（乘上 n）。

讀到 orders(n - 1) 時，很多人會想在腦中一路展開：orders(3) 呼叫 orders(2)，orders(2) 呼叫 orders(1)……層數一多就亂了。寫遞迴不用這樣想，改成依序回答三個問題：

  1. 這個函式在算什麼？用一句話寫下來：「orders(n) 回傳 n 位顧客的排法數」。這句話是你的約定，後面每一層都照它用。
  2. 最小的情況是什麼、答案是多少？寫成終止條件，放在函式第一行。
  3. 假設比較小的問題已經會算了，這一層怎麼用它組合出答案？這叫「相信遞迴」：你只負責這一層，下一層交給同一個函式。只要第 1 步的約定對、第 2 步會停，每一層都照約定組合，整體就是對的。

第 3 步的「比較小」是遞迴會停下來的保證：每次呼叫都要往終止條件靠近一步，例如 n 變小、索引往後、子分類往下。參數如果沒有變，函式就會用同一個問題一直呼叫自己，永遠到不了終止條件。

orders 縮小的是一個數字；練習 1 要處理的是陣列，陣列要怎麼一步一步變小？做法是傳索引：f(arr, i) 負責 arr[i] 到最後的這一段，處理完 arr[i] 後呼叫 f(arr, i + 1) 處理剩下的；i === arr.length 時這一段是空的，直接回傳。另一種寫法是 f(arr.slice(1))，看起來比較短，但 slice 每次都複製一份陣列，n 層就是 O(n²) 的時間和空間。面試寫遞迴時傳索引，練習 1 就是這個寫法。

現在回到菜單，照同樣三個問題來想：

  1. 函式在算什麼：countItems(category) 回傳這個分類加上底下所有子分類的品項總數。
  2. 最小的情況：一個沒有子分類的分類，答案就是自己的品項數，不用再往下問。
  3. 這一層怎麼組合：假設每個子分類的總數已經會算（交給 countItems 自己），這一層的答案就是「自己的品項數 + 每個子分類的總數」。

整個過程沒有一個地方需要知道菜單有幾層：每一層只看自己和自己的子分類，再深的分支都由同一個函式一層一層往下處理。這就是開場問題的答案，練習 4 會讓你寫出它。不過「交給同一個函式」在電腦裡是怎麼發生的？orders(3) 呼叫 orders(2) 的時候，自己那個還沒做的乘法存在哪裡？

函式呼叫自己的時候，電腦怎麼記得每一層做到哪？

先把問題看清楚：orders(3) 執行到 3 * orders(2) 時，乘法還不能做，得先去算 orders(2)。等 orders(2) 回來，電腦要記得「回到 orders(3)、這一層的 n 是 3、接著做乘法」。而 orders(2) 自己也會停在一半去等 orders(1)。所以每一層呼叫都需要一份「我的參數和變數是多少、回來後從哪一行繼續」的紀錄，而且這些紀錄要同時存在。

這份紀錄叫堆疊框（stack frame），裡面存這次呼叫的參數、區域變數，以及回傳後要回到哪一行。堆疊框疊在一起的方式就是第 12 課的堆疊：每呼叫一次函式，就在最上面放一個新的框；函式 return 時，拿掉最上面那一框，回到下面那一框繼續執行。最晚開始的呼叫一定最早結束，所以剛好是後進先出。這一疊堆疊框叫呼叫堆疊（call stack），就是 TypeScript 課第 7 課 event loop 裡的那個 call stack。它不是遞迴專用的東西，所有函式呼叫都靠它；遞迴的特別之處只是同一個函式會在上面疊很多層，每一層有自己的 n。

數菜單也一樣。countItems 走到最深的那個分類時，從「全部」到它的每一層各佔一框，所以它的空間是菜單的最大層數，不是分類總數；處理完一個子分類，那一框就拿掉，才換下一個子分類放上來。既然每一層都要佔一框，層數一多，堆疊會不會放不下？

堆疊會不會滿？終止條件寫錯、資料太深會怎樣

會。呼叫堆疊的空間有上限，函式一直往下呼叫、堆疊框一直疊上去，總有放不下的時候，這叫堆疊溢位（stack overflow）。最常見的原因有兩個：終止條件漏寫，或遞迴呼叫沒有把問題縮小，函式就會無止境地呼叫自己。

下面故意漏掉終止條件。Chrome、Node、Safari 碰到堆疊溢位會丟出 RangeError: Maximum call stack size exceeded（Firefox 的訊息是 InternalError: too much recursion）。它是一般的錯誤，可以用 try／catch 接住。執行後看兩行：錯誤的名稱和訊息，以及丟錯前疊了幾層：

印出來的層數就是你這個瀏覽器、這個函式大約的上限。它只能當參考：規格沒有規定上限，依引擎、執行的環境（主執行緒或 Worker）、每一層用多少區域變數而不同。2026-11-01 實測一個很小的函式：Node 24.22.1 主執行緒大約 1 萬層，Chrome 裡這個頁面的範例大約 4,500 層。這個頁面的範例是在 Worker 裡跑的：Worker 是瀏覽器在背景另開的執行緒，它的堆疊空間跟主執行緒分開計算，所以上限也不同。

所以能不能用遞迴，要看資料的深度有沒有上限。深度固定而且不大時，例如菜單分類幾層、平衡的樹幾十層，遞迴最好讀，放心用。深度可能跟資料量一樣大時，例如一條上萬節點的鏈結串列、歪成一直線的樹、使用者上傳的任意巢狀 JSON，就改成迴圈，或用陣列當自己的堆疊（第 20 課會做）。你可能聽過「寫成尾遞迴就不會溢位」，這在 Chrome 和 Node 上不成立，原因見課末〈補充與查表〉。

菜單管理這一頁屬於哪一種？分類是店員在後台編的，正常不會超過幾層；可是後台如果提供「匯入分類」，深度就由匯入的檔案決定了。所以結論是：店員在後台手動編的分類，直接用遞迴；要是做了「匯入分類」，匯入時先檢查最大深度，超過上限就拒絕，通過檢查的資料再交給遞迴處理。

💡 實務上：遞迴深度要看資料是誰給的
前端自己定義的菜單、設定檔，深度固定又不大，遞迴沒問題。風險在「深度由外部決定」的地方：API 收到使用者送來的巢狀 JSON、匯入的分類樹、多層回覆的留言。有人故意送一份很深的資料，遞迴就會丟 RangeError，沒接住的話整個請求失敗。資深會先問「這份資料最深可能幾層、誰能控制它」，對外的輸入就在驗證時限制最大深度，超過直接回傳錯誤，不要讓它跑進遞迴。看錯誤日誌時，如果堆疊裡同一個函式重複出現一大串，第一個懷疑的就是終止條件或沒有縮小問題。

同一個子問題被算很多次會怎樣？Fibonacci 照定義寫的代價

到這裡的遞迴，不論是 orders 還是 countItems，每個子問題都只處理一次。orders(3) 只呼叫 orders(2) 一次；countItems 雖然一層會呼叫自己好幾次，但每次處理的是不同的子分類，一個分類不會同時屬於兩個父分類，所以整份菜單每個分類剛好走過一次。遞迴還有一種很常見的出事方式，是菜單示範不出來的：同一個子問題被呼叫很多次。要看到它，得換一個子問題會重疊的例子。

店裡的會員有個規律：每個月新加入的會員數，等於前兩個月新會員數的和。第 0 個月 0 人、第 1 個月 1 人，之後是 1、2、3、5、8、13……這就是 Fibonacci 數列：f(0) = 0、f(1) = 1、f(n) = f(n − 1) + f(n − 2)。照定義寫成遞迴很直接。注意它有兩個終止條件：每一層往回看兩格，n = 1 時如果只有 f(0) 一個終止條件，f(1) 會去算 f(−1)，一路減到負數停不下來。程式裡寫成 n < 2 一次涵蓋兩個。

每次呼叫都把計數器加 1，執行後看「呼叫了幾次」那一欄怎麼長：

fib(30) 一共呼叫了約 269 萬次。n 只多 5，呼叫次數就多 11 倍左右。畫出 fib(5) 的呼叫樹就知道為什麼：每個節點分成兩個呼叫，而 fib(4) 底下要算 fib(3)，fib(5) 自己又要算一次 fib(3)，兩邊各自從頭算，誰也沒用到誰的結果。

看到每個節點分成兩個，直覺會以為呼叫數每層翻倍、是 O(2ⁿ)。但右邊的分支是 fib(n − 2)，比左邊少一層，越往右下越早碰到終止條件，所以呼叫樹不是滿的二元樹，圖裡右半邊明顯比左半邊矮。把呼叫次數寫成式子：calls(n) = calls(n − 1) + calls(n − 2) + 1，fib(n) 這一次自己算 1，加上兩個子呼叫各自的次數。這跟 Fibonacci 本身的定義長得一樣，所以呼叫次數和 Fibonacci 數列成長得一樣快，相鄰兩項的比值會趨近黃金比例，約 1.618。O(2ⁿ) 是一個比較鬆的上界，寫成 O(2ⁿ) 也不算錯，只是 O(1.6ⁿ) 更貼近實際。

所以每多一層，呼叫數大約乘上 1.6，時間大約是 O(1.6ⁿ)，屬於指數時間。2026-11-01 用 Node 24.22.1 實測：fib(35) 約 1 秒、fib(40) 超過 15 秒，fib(78) 這輩子算不完。它的空間倒只有 O(n)：上一節說過空間看最深有幾層，同一時間在堆疊上的只有從根走到目前節點的那一條路徑，最長 n 層。

只有一個參數 n，不代表是 O(n)。看的是總共呼叫幾次：一層分出兩個呼叫、又沒有共用結果，次數就會指數成長。

圖裡不同的子問題其實只有 6 個，卻呼叫了 15 次，多出來的全是重算。既然問題出在同一個答案算了好幾次，下一步就是讓每個答案只算一次。

算過的答案存起來：記憶化怎麼把指數時間變成 O(n)？

做法叫記憶化（memoization）：每算出一個 f(n)，就把它存起來；下次遇到同樣的 n，直接拿存好的結果，不再往下呼叫。鍵是 n、值是 f(n)，正好用第 4 課的 Map。每個 n 只會真正算一次，之後都是 O(1) 查表，總共 O(n) 時間；空間是 Map 的 O(n) 加上堆疊深度的 O(n)。

Map 要放在哪裡？它必須在所有遞迴呼叫之間共用，fib(5) 存進去的結果，fib(4) 底下的呼叫才拿得到。如果把 new Map() 寫在遞迴函式裡面，每次呼叫都建一個新的空 Map，存了也沒有人看得到，等於沒存。用 TypeScript 課第 1 課的閉包，把 Map 放在外層函式裡，裡面的遞迴函式每一層都看得到同一個。執行後比較呼叫次數和上一節的 269 萬次：

查表的那一行要寫 saved !== undefined，不要寫 if (saved)。if 會把 falsy 的值當成 false，falsy 指的是 0、''、null、undefined、NaN 這些值。Map.get 查不到時回傳 undefined，但存進去的答案也可能剛好是 0。寫 if (saved) 的話，存過的 0 會被當成沒存過。這題的 0 都被 n < 2 先擋掉，所以不會算錯；換到存的值可能是 0 或空字串的題目，就會重算或出錯。

記憶化不是每個遞迴都該加。它成立要有兩個條件：同樣的輸入一定得到同樣的結果，也就是函式不讀外面會變的狀態；而且子問題真的會重複出現。像 orders(n) 每個 n 只會被呼叫一次，countItems 每個分類只走一次，加記憶化沒有用，只是多佔空間。

記憶化把時間降到 O(n)，但遞迴本身還在：算 fib(n) 仍然要往下疊 n 層，堆疊的上限還在，Map 也要 O(n) 空間。能不能連這些都省掉？

💡 實務上：記憶化就是快取，要想清楚什麼時候失效
工作中常見的記憶化：React 的 useMemo、Vue 的 computed、把「算過的運費、折扣結果」存起來。最常見的坑是函式其實會讀到外面會變的東西，例如目前價格、庫存、登入的使用者，結果拿到舊答案。第二個坑是在長時間執行的伺服器上用一個全域 Map 記住所有輸入，Map 只增不減，記憶體越用越多。本來就很便宜的計算（幾次加法）不用記憶化，查表和管理快取反而比較貴。加之前先確認：真的有重複計算嗎？結果什麼時候會過期？

連堆疊都不要：怎麼由下往上改成迴圈？

記憶化是「從 f(n) 往下拆，用到哪個才算哪個」。反過來想：f(n) 只需要前兩個值，而 f(2) 只需要 f(0)、f(1)，f(3) 只需要 f(1)、f(2)……計算順序是固定的。那就從 f(0)、f(1) 開始，一路往上算到 f(n)。這叫由下往上（bottom-up），通常用迴圈寫。因為每一步只用到前兩個值，更早的值算完就可以丟掉，所以只要兩個變數，空間 O(1)，也沒有堆疊深度的問題。

執行後看每一圈印出的 prev、cur，它們就是前兩個值一路往前推：

手算時對照輸出：迴圈結束時 cur 是 f(n)。迴圈從 2 跑到 n（含），少跑一圈就會回傳 f(n − 1)，這是練習 3 最常見的錯。練習 3 的測試最多只算到 f(78)，因為那是 number 能精確表示的最後一項，第 79 項開始會悄悄差 1，原因和 BigInt 的寫法放在課末〈補充與查表〉。

到這裡同一個問題有了三種寫法，各有適合的時候：

寫法時間空間什麼時候用
照定義遞迴O(1.6ⁿ)O(n)（堆疊）只拿來確認定義、當對照答案
遞迴＋記憶化O(n)O(n)（Map＋堆疊）從定義直接改，最快寫對；子問題不規則時最好用
由下往上的迴圈O(n)O(1)知道計算順序時；沒有堆疊深度的限制

「照定義遞迴 → 發現重複 → 記憶化 → 改成由下往上」這條路，就是第 23 課動態規劃的做法。面試時照這個順序講，也能展現你知道每一步的取捨。

Fibonacci 能改成迴圈，是因為它的計算順序很規則。菜單沒有這種順序：形狀由店員決定，每個分類有幾個子分類、往下幾層都不一定，硬改成迴圈就得自己管一個堆疊，反而難讀。所以菜單管理這一頁仍然用遞迴。回到那一頁，把剩下兩件事做完。

回到菜單管理：怎麼印出整份菜單、攤平巢狀金額？

第一件事是照層次縮排印出整份菜單。印的時候要知道每個分類在第幾層，才知道要縮幾格；做法跟第二節追蹤 orders 一樣，把 depth 當參數往下傳，每往下一層加 1。函式只想「一個分類怎麼印」：先印自己的名稱和品項，再把每個子分類交給同一個函式。執行後看縮排是不是跟資料的巢狀一致：

這裡的終止條件沒有寫成 if：沒有子分類時 children 是空陣列，for 迴圈一次都不跑，函式自然就結束了。這在巢狀資料裡很常見，終止條件藏在「沒有下一層」本身。走過整份菜單時，每個分類只處理一次，時間是 O(全部分類數＋品項數)，堆疊深度是分類的最大層數。開場的「每個分類顯示品項數」也是同一個形狀，只是把「印出來」換成「加起來」，就是練習 4 的 countItems。

第二件事是攤平報表裡的巢狀金額。報表把訂單金額依門市、時段一層包一層，像 [80, [110, [70]], 90]，要攤平成 [80, 110, 70, 90]。這也是前端面試常見的手寫 flat。思路跟印菜單一樣：一個一個看元素，是數字就放進結果，是陣列就交給同一個函式往下處理。

先寫型別。type NestedOrders = readonly (number | NestedOrders)[] 是一個引用自己的型別別名，意思是「每個元素是數字，或是另一個同樣形狀的陣列」，型別本身也是遞迴的。判斷元素時用 typeof item === 'number'，TypeScript 會在兩個分支裡把型別分別縮小成 number 和陣列，這是 TypeScript 課第 16 課的型別縮小。

再決定結果放在哪。所有數字要放進同一個輸出陣列：寫一個內層函式 walk(list)，共用外層的 out，每個數字只 push 一次。另一種直覺的寫法是每一層都回傳一個新陣列，再展開合併到上一層；這樣在第 5 層的數字，會在每一層合併時被複製一次，越深的數字被複製越多次。練習 5 就是這題。

回頭看這頁處理的資料：菜單結構其實就是一棵樹，每個分類是一個節點，子分類是它的子節點。這課的三個函式都是同一個模式：處理自己，子節點交給同一個函式。下一課的二元樹，就是每個節點最多兩個子節點的樹。

💡 實務上：樹狀資料在前後端到處都是
電商的多層商品分類、留言的回覆串、檔案總管、組織圖，前端常用「元件裡再渲染自己」的遞迴元件來畫。資料庫通常不會存成巢狀，而是每一筆記 parent_id，後端或前端再組成樹；所以除了會走樹，也要會把平的列表組回樹。資料是人編輯的就可能出錯：把分類的父層設成自己的子分類，遞迴就永遠走不完，所以存檔時要擋，或走訪時限制深度。分類很多時，資深會問「要一次全部載入，還是點開才載入下一層」，這會決定 API 怎麼設計。

補充與查表

尾呼叫最佳化：為什麼寫成尾遞迴在 Chrome、Node 還是會溢位

有些語言會做尾呼叫最佳化（tail call optimization）：如果遞迴呼叫是函式的最後一個動作（return f(…)，回來後不用再做事），就重用同一個堆疊框，不會長高。ES2015 規格有寫這件事（proper tail calls），但 V8（Chrome、Node 用的引擎）和 Firefox 都沒有實作，目前只有 Safari 的 JavaScriptCore 有（MDN〈Execution model〉）。程式要在 Chrome 和 Node 上跑，「寫成尾遞迴」就省不了堆疊（在 Safari 執行下面的範例，10 萬層會算出結果）：

數字的上限：fib(79) 已經不精確

JavaScript 的 number 不會像其他語言的 32 位元整數那樣溢位成負數，但超過 Number.MAX_SAFE_INTEGER（2⁵³ − 1 = 9007199254740991）之後，整數就不一定能精確表示，而且不會報錯。Fibonacci 第 78 項還在範圍內，第 79 項就超過了：

第 79 項用 number 算是 …220，正確是 …221，差了 1 卻沒有任何提示。題目的答案可能超過 2⁵³ − 1 時，要嘛改用 BigInt（TypeScript 課第 5 課），要嘛照題目要求取餘數（LeetCode 常見「答案對 10⁹ + 7 取餘數」，就是為了讓數字一直保持在安全範圍內）。

練習

每題的隱藏測試會用固定案例和大量隨機案例比對參考解。判分逾時代表複雜度不夠或無限遞迴，不是電腦太慢。傳進來的資料都不能修改。

練習 1：寫 sumFrom(totals, i)：用遞迴回傳 totals[i] 到最後一筆的總和；i 等於長度時回傳 0。不能用 for、while、reduce，要自己呼叫自己（測試會檢查）。先寫終止條件，再想「假設 sumFrom(totals, i + 1) 已經算好了，這一層怎麼組合」。

練習 2：呼叫堆疊。把練習 1 的遞迴加上追蹤：進入時印出 縮排 + 呼叫 sum(i)，回傳前印出 縮排 + 回傳 結果，縮排是 ' '.repeat(depth)（每層兩個空白）；碰到終止條件的那一層也要印出「呼叫」和「回傳 0」。執行 traceSum([80, 110, 70], 0, 0) 應該印出 8 行。先在紙上寫出這 8 行，再寫程式對照。

練習 3：每個月的新會員數 f(0) = 0、f(1) = 1、f(n) = f(n − 1) + f(n − 2)，n 是 0～78 的整數。寫兩個版本：fibMemo(n) 用遞迴加 Map 記憶化；fibIter(n) 用迴圈和兩個變數，不能呼叫自己。測試會從 n = 0 一路算到 78：沒有記憶化（或 Map 沒有在呼叫之間共用）會跑不完、被 3 秒逾時判錯。（對應 LeetCode 509. Fibonacci Number）

練習 4：寫 countItems(category)：回傳這個分類加上所有子分類（任意層）裡的品項總數。不能修改傳進來的分類。想清楚：這一層自己的品項有幾個？每個子分類的數量由誰來算？

練習 5：手寫 flat。門市 → 時段 → 訂單金額，巢狀層數不固定，型別是 NestedOrders。寫 flattenOrders(nested)，照原本的順序回傳攤平後的金額陣列。不能用 flat、flatMap（測試會擋），也不能修改輸入；空的子陣列直接略過。巢狀最多 50 層。提示：用 typeof item === 'number' 判斷，讓 TypeScript 縮小型別。

練習 6：照定義寫的 fib(n) = fib(n − 1) + fib(n − 2)（沒有記憶化），時間複雜度是多少？

✓ c。時間看「總共呼叫幾次」：呼叫樹每往下一層幾乎翻倍，fib(30) 要呼叫 269 萬次，是指數成長。只有一個參數不代表 O(n)（a 錯）；兩個呼叫不是乘上 n，而是每一層都再分兩個，次數一直相乘（b 錯）；n 每次只減 1 或 2，不是減半（d 錯）。

練習 7：同事說「把遞迴改成尾遞迴（return f(n − 1, acc + n)），在 Chrome 裡就不會堆疊溢位了」。對嗎？

✓ b。ES2015 規格寫了 proper tail calls，但 V8 沒有實作，所以在 Chrome 裡 sumTo(100000, 0) 照樣丟 RangeError，嚴格模式也一樣（a、c 錯；只有 Safari 有實作，不能拿來當通用的解法）。尾遞迴是合法語法，只是省不了堆疊（d 錯）。

練習 8：sumFrom(totals, i) 沒有建立任何陣列或 Map。它的額外空間複雜度是多少？

✓ a。遞迴的空間看最深有幾層：每個堆疊框存參數、區域變數和回傳位置，n 層就是 O(n)。所以 b 錯；堆疊不會壓縮（c 錯）。傳索引不會複製陣列，用 slice(1) 往下傳才會變成 O(n²)（d 錯）。

練習 9：用一般的 number 算 Fibonacci 第 80 項，結果精確嗎？

✓ d。number 能表示到約 10³⁰⁸，但精確的整數只到 2⁵³ − 1，第 79 項就差了 1（a 錯）。JavaScript 不會溢位成負數（b 錯），也不會丟錯（c 錯），就是悄悄變得不精確，所以更要自己注意。

常見錯誤

  • 沒有終止條件，或終止條件不完整：丟 RangeError。先寫終止條件；一次往回看兩格的遞迴（Fibonacci）要有兩個終止條件，或寫成 n < 2。
  • 遞迴呼叫沒有把問題縮小：參數沒變（sumFrom(totals, i) 忘了 +1），永遠到不了終點。每次呼叫都檢查「有沒有往終止條件靠近」。
  • 重複計算同樣的子問題：呼叫樹裡同樣的參數出現很多次，就是指數時間。加記憶化，或改成由下往上的迴圈。
  • memo 寫在遞迴函式裡面：每次呼叫都是新的空 Map，等於沒存。放在外層（閉包或模組層級），讓所有呼叫共用。
  • 用 if (saved) 判斷有沒有存過：存的值是 0 時會被當成沒存。用 saved !== undefined 或 memo.has(n)。
  • 用 slice 縮小陣列：每層複製一次，O(n²)。傳索引。
  • 很深的遞迴：資料可能上萬層（長串列、歪斜的樹、使用者的任意 JSON）時，遞迴會溢位，改用迴圈或自己的堆疊。尾遞迴在 V8 沒有幫助。
  • 以為沒建陣列就是 O(1) 空間：遞迴的空間是最深的層數。

小結

  • 迴圈不知道要套幾層時用遞迴：函式只處理這一層，同樣形狀的下一層交給自己。遞迴有兩部分：終止條件（直接回傳）和把問題縮小一步的遞迴呼叫。寫的時候先寫終止條件，再「相信遞迴」：假設小一號的問題已經會算，只想這一層怎麼組合。
  • 每次呼叫在呼叫堆疊放一個堆疊框，回傳時拿掉。遞迴的空間是最深的層數；太深丟 RangeError，上限依引擎而定，V8 沒有尾呼叫最佳化。深度由外部資料決定時，先限制深度或改成迴圈。
  • 時間看總共呼叫幾次。照定義的 Fibonacci 子問題重疊，是 O(1.6ⁿ)；用共用的 Map 記憶化變成 O(n)；由下往上的迴圈是 O(n) 時間、O(1) 空間。
  • number 的精確整數只到 2⁵³ − 1，超過不會報錯；要精確就用 BigInt。
  • 巢狀資料（菜單分類、留言、巢狀陣列）用遞迴最自然：處理自己，子項目交給同一個函式；沒有子項目時迴圈不跑，就是終止條件。
