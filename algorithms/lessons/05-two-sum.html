階段 2：雜湊表 · 第 5 課

Two Sum：從雙迴圈到 Map

第 1 課的禮券題回來了。第 1 課用雙迴圈寫出一定對的暴力解，也留下一個問題：1 萬杯要試將近 5,000 萬組。這次咖啡店推出一張 190 元的禮券：要買兩杯不同的飲料，價格加起來剛好等於 190 才能用。店長希望 POS 收銀機能幫店員找出是哪兩杯。這一課的任務就是寫出這個函式 giftCardPair(prices, budget)：給它菜單價格的陣列和禮券金額，它回傳那兩杯飲料在陣列裡的位置。

這題就是 LeetCode 第 1 題 Two Sum（兩數之和），也是面試最常拿來暖身的題目。題目本身不難，難的是寫完之後會被一路追問：為什麼這樣寫？複雜度多少？價格重複怎麼辦？如果要數出有幾組呢？這課從最直接的雙迴圈寫起，找出它重複做的工作，再用 Map 改成只走一次，最後把每一個追問都回答完。學完你會帶走一個模式：要找 a + b = 目標，就對每個 b 問「目標 − b 我看過了嗎？」。後面的課會一再用到它。

這課的路線：
  1. 動手前先問清楚、最直接的寫法：giftCardPair 要回傳什麼；雙迴圈每一組都試，要比幾次。
  2. 雙迴圈浪費在哪、一次走完：內迴圈一直在找「還差多少」，用 Map 記住看過的價格，一次走完變 O(n)（開場問題的最小答案）。
  3. 兩行對調會怎樣、邊界情況：先查再存為什麼不能反過來，空陣列、負數、0、重複價格會不會出錯。
  4. 快了多少、代價是什麼：O(n) 時間換來 O(n) 空間，為什麼這題不先排序。
  5. 換一個追問：要數幾組、要找最近一次，只要換 Map 裡存的東西。
這課會用到：
  • 第 4 課的 Map：get／set／has 查找平均 O(1)，get 找不到時回傳 undefined。
  • 第 2 課的 Big-O：雙迴圈每一對都比一次是 O(n²)，n 到 10⁵ 就太慢。

動手前：giftCardPair 到底要回傳什麼？

拿到題目，第一步不是寫程式，而是用自己的話把題目重述一遍，把「會讓程式寫法不同」的地方問清楚。面試時這些問題要真的問出口；工作上則是跟 PM 或呼叫你函式的同事確認。不問就寫，常常寫完才發現答錯題，例如回傳了價格，對方要的卻是位置。

先講一個表格裡會用到的詞。陣列裡每個元素的位置叫索引（index），從 0 開始數：[90, 70, 110, 80] 裡，90 的索引是 0，80 的索引是 3。回傳索引而不是價格，是因為價格會重複（兩杯都是 110 元），只有位置能指出「是哪一杯」。以下是這題要問的問題和這課採用的答案：

要問的問題這一課的答案
回傳什麼？價格還是位置？回傳兩杯的索引，不是價格。[i, j]，而且 i < j
同一杯可以點兩次嗎？不行。兩個索引必須不同；但兩杯價格相同可以，例如兩杯 80 元的不同飲料
可能有很多組答案嗎？經典題保證最多一組；有多組時回傳任一組都算對
沒有答案時回傳什麼？null（不是 []，也不是 [-1, -1]）
可以改傳進來的陣列嗎？不行，型別是 readonly number[]
陣列有排序嗎？會有負數或 0 嗎？沒有排序；為了通用，數字可以是負數或 0

問完的答案，可以直接寫成 TypeScript 的函式簽章，題目就定下來了：

function giftCardPair(prices: readonly number[], budget: number): [number, number] | null

簽章裡每個部分都對應表格的一列。readonly number[] 表示函式裡不能 push、sort 這個陣列。回傳型別 [number, number] 不是一般的 number[]，而是 tuple（元組）：一種長度固定、每個位置型別也固定的陣列。寫成 tuple 之後，回傳 [] 或三個數字都會被型別檢查擋下來；| null 則明確告訴呼叫的人「可能沒有答案，你要處理」。把規格寫進型別，等於讓編譯器幫你守住剛剛問到的答案。

💡 實務上：「找不到」要回傳什麼，是團隊要先約定的規格
工作中同一個團隊裡，常有人找不到回 null、有人回 []、有人回 -1，呼叫的人只好每個都猜一次，猜錯就是 bug。例如咖啡店後台查「某位顧客的最近一筆訂單」，查不到時 API 是回 null，還是回 HTTP 狀態碼 404（找不到），前端的寫法完全不同。資深工程師會先把簽章（或 API 規格）寫下來給前後端一起看，讓型別檢查提醒呼叫的人處理「沒有結果」。慣例是：查「一個東西」找不到回 null，查「一串東西」找不到回空陣列。giftCardPair 找的是「一組」答案，所以回 null。

規格定好了，下一步是先寫出一個「一定對」的版本，不管快慢。

最直接的寫法：每一組都試，要比幾次？

最不會錯的做法，是把所有「兩杯的組合」都試一遍，這種把可能性全部列舉出來的做法叫暴力解（brute force）。寫法就是第 1 課寫過的雙迴圈：外層選第一杯 i，內層從 i + 1 開始選第二杯 j，加起來剛好是禮券金額就回傳 [i, j]。

內層從 i + 1 開始，而不是從 0 開始，是在落實上一節問到的兩條規格：j 永遠比 i 大，所以不會拿同一杯配自己；也不會把 (0, 1) 和 (1, 0) 這兩種「其實是同一組」的情況各試一次。回傳的 [i, j] 也自然滿足 i < j。

用價格 [90, 70, 110, 80]、禮券 190 手算。下面的程式把每一次比較印成一列，執行後看最後一行「共比較幾次」：

答案是 110 + 80，剛好在最後兩杯，所以每一組都試過了才找到：4 杯比了 6 次。為什麼是 6？第 0 杯要跟後面 3 杯各比一次，第 1 杯跟後面 2 杯比，第 2 杯跟最後 1 杯比，3 + 2 + 1 = 6。推廣到 n 杯，就是 (n − 1) + (n − 2) + … + 1 = n(n − 1) / 2 次。這個數大約是 n² 的一半，第 2 課說過常數不影響成長的速度，所以是 O(n²)。

菜單只有 4 杯時，6 次比較根本感覺不到。但同一個函式拿去處理 5 萬筆金額時，就要約 12.5 億次比較。暴力解證明了題目做得出來，也給我們一個可以對答案的版本；接下來的問題是：這 12.5 億次裡，有多少是白做的？

雙迴圈浪費在哪？內迴圈一直在問同一個問題

要讓暴力解變快，先別急著換寫法，而是看清楚內迴圈到底在做什麼。看外層停在 i = 0（90 元）的時候：內迴圈把後面每一杯拿出來加 90，看是不是 190。換個說法，它在問：

「後面有沒有一杯剛好是 190 − 90 = 100 元？」

這個「要湊到目標還差的數」，叫補數（complement），寫成 need = budget − x。一旦這樣想，內迴圈做的事就變得很單純：它不是在「加加看」，而是在陣列裡找一個特定的值 100。問題是它每一圈都從頭找一遍：外層換到 70 元時，又重新掃一次找 120；換到 110 元，再掃一次找 80。同一批價格被掃了一次又一次。

「找有沒有某個值」就是查找。第 4 課學過，查找有兩種成本完全不同的做法：在陣列裡找要從頭比到尾，是 O(n)；在雜湊表裡找，用雜湊函式直接算出值放在哪一格，平均 O(1)。所以只要把「看過的價格」放進雜湊表，內迴圈的那一整遍掃描，就能換成一次 O(1) 的查詢。

剩下要決定的是用 Set 還是 Map。Set 只能回答「有沒有看過 100 元」，但題目要回傳的是索引，光知道「有」不夠，還要知道它在哪個位置。所以要用 Map 記住「值 → 索引」（value → index）：鍵是價格，值是那杯飲料的索引。查到補數時，Map 直接給出它的位置。

這一節的推理可以帶走：先把內迴圈的工作說成一句話，再看那句話是不是「查有沒有／查幾次／查在哪裡」。是的話，通常就能用 Set 或 Map 把一層迴圈換掉。這是這一個階段最常用的改進方式，第 6 課的分組題也是這樣想出來的。

知道要記什麼之後，還有一個細節要決定：Map 什麼時候放東西、什麼時候查？

一次走完：Map 什麼時候查、什麼時候存？

最自然的做法是一邊走一邊記：從左走到右，每走到一杯價格 x（索引 i）就做兩件事。

  1. 先查：Map 裡有沒有 budget − x？有的話，它的索引就是第一杯，回傳 [map.get(need), i]。
  2. 再存：沒查到，把 x → i 存進 Map，留給後面的飲料查。

這樣做為什麼找得到答案？假設答案是索引 2 和 3 的兩杯。走到索引 2 時，它的搭檔還沒出現，查不到，於是把它存進 Map；走到索引 3 時，搭檔已經在 Map 裡，一查就中。也就是說，每一組答案都會在「走到後面那一杯」的時候被發現，不會漏掉。

也因為這個順序，Map 裡永遠只放「左邊已經走過的飲料」，查到的一定在 i 左邊，回傳時自然是 [小的, 大的]，滿足 i < j。整個陣列只走一次就有答案，這叫一次走完（one pass）。下圖是走到最後一杯時的狀態：

程式裡判斷「有沒有查到」寫的是 j !== undefined，不是 if (j)。原因是 get 查不到時回傳 undefined，但查到的索引可能剛好是 0，而 0 在 JavaScript 裡是 falsy（放進 if 會被當成 false 的值）。寫 if (j) 的話，答案的第一杯如果在索引 0，就會被當成「沒查到」，整組答案漏掉。Map 存的是數字時，一律跟 undefined 比，或先用 has 問有沒有。

💡 實務上：0 被當成「沒有」是很常見的線上 bug
不只索引，價格 0 的贈品、數量 0、折扣 0%、餘額 0 都是合法的值。if (!discount) 或 price || 預設價 會把 0 當成沒填，結果贈品被算成原價。code review 看到用真假值判斷數字時要多問一句「0 可能出現嗎？」；要給預設值用 ??（只在 null／undefined 時才換），要判斷有沒有就明確寫 !== undefined。

開場的問題到這裡已經有了最小的答案：用 Map 一次走完。但「先查、再存」這兩行看起來可以隨便排，真的是這樣嗎？

兩行對調會怎樣？先查再存在保護什麼

上一節特別強調先查再存，現在來看反過來會發生什麼事。下面放了三種寫法：先存再查、先查再存，以及另一種常見的「兩次走」：先把全部價格存進 Map，再走第二遍查補數。執行後看每一行回傳的是什麼：

第一組輸入是只有一杯 80 元、禮券 160。先存再查的寫法，走到這杯時先把 80 → 0 存進去，接著查補數 160 − 80 = 80，馬上查到剛存進去的自己，回傳 [0, 0]：同一杯用了兩次。這不是罕見的特例，只要禮券金額剛好是某一杯的兩倍，就會出事。先查再存的寫法，查的時候 Map 裡只有「別的、在左邊的」飲料，自己還沒存進去，所以不可能查到自己，正確回傳 null。

第二組輸入是兩杯都是 80 元。這時你可能會擔心：Map 的鍵不能重複，第二個 80 要怎麼放？答案是根本還輪不到放。走到第二個 80（索引 1）時先查補數 80，Map 裡已經有第一個 80 → 0，直接回傳 [0, 1]。就算之後還要繼續走，set 也只是把鍵 80 的值蓋成 1，不會出錯。所以先查再存一次解決了兩件事：不會配到自己，價格重複的兩杯也能正確配對。

兩次走的寫法也能得到正確答案，但它要多操心兩件事。第一，第二遍查的時候，整個陣列都已經在 Map 裡，自己也在，所以要額外檢查 j !== i。第二，第一遍存的時候，價格重複的話後面的索引會蓋掉前面的，[80, 80] 的 Map 裡只剩 80 → 1，回傳時得想清楚哪個在前。一次走完的寫法把這些問題都用「順序」解決了，比較少地方能出錯，面試時建議用它。

「配到自己」和「價格重複」是面試官最常追問的兩個情況，但不是全部。寫完之後，還要有系統地把其他特殊輸入也想一遍。

還有哪些輸入會讓它出錯？用邊界情況跑一遍

程式在「正常」的輸入上跑對，不代表它是對的。真正容易出錯的，是那些最小、最大或比較特殊的輸入，這些叫邊界情況（edge case）：空陣列、只有一個元素、負數、0、答案在最前面或最後面。寫完函式之後，資深工程師會先把這些輸入在腦中跑一遍，而不是等測試或使用者幫他找到。

拿上一節的先查再存寫法逐一檢查：

輸入結果一次走完的寫法怎麼處理

[80, 70]，禮券 160null先查再存，80 不會配到自己
[-30, 50, 200]，目標 170[0, 2]走到 200 時補數是 170 − 200 = −30，負數一樣能當 Map 的鍵，不用特別處理

表格最後一列是最慢的情況：答案藏在最後，Map 解法也得走完整個陣列。即使如此，它也只走 n 步。所以下一個問題是：n 步跟暴力解的 n(n − 1) / 2 次，實際差多少？這個速度又是用什麼換來的？

快了多少、付出什麼代價？

先算複雜度。一次走完的寫法，每個元素做一次 Map 查詢、一次 Map 寫入，兩者平均都是 O(1)，總共 O(n) 時間。但這個速度不是免費的：Map 最多要存 n 筆價格，需要 O(n) 額外空間。暴力解只用了幾個變數，額外空間是 O(1)。這種「多花記憶體，換來少做計算」的取捨，叫用空間換時間，是雜湊表最典型的用法。

為什麼不先排序？

講完「用空間換時間」，常有人會想到另一條路：先把價格排序，再從兩端往中間找。左邊指著最便宜的、右邊指著最貴的，加起來太大就把右邊往左移，太小就把左邊往右移。這叫雙指標，第 7 課會細講。它只要 O(1) 額外空間，聽起來比 Map 省，但用在這一題有兩個問題：

  • 排序要 O(n log n)，比 O(n) 慢。
  • 排序會打亂索引。題目要原本的位置，排序後找到的是新位置；要另外把 [價格, 原本的索引] 一起排序才能還原。

所以判斷方式是看資料的狀態：資料本來就排好（例如依價格排好的菜單），而且記憶體很緊時，用雙指標，省下排序也省下 Map；沒排序、又要回傳原本的索引，用 Map。反過來，如果資料多到記憶體放不下 n 筆的 Map，就是空間不夠付了，這時換回排序加雙指標：Map 用空間換時間，空間不夠就拿時間換回空間。面試時把這個取捨說出來，就是面試官想聽的資深視角；資料大到要分段排序的做法，見課末「補充與查表」。

到這裡，原題的「怎麼寫、為什麼對、多快、代價是什麼」都回答完了。面試官的下一個追問通常是改題目：如果不只要一組，而是要數出有幾組呢？

換一個追問：要數幾組、找最近一次，Map 裡該存什麼？

回頭看一次走完的骨架：「走過的東西記在 Map 裡，讓後面的元素查」。原題要回傳位置，所以 Map 記的是「價格 → 索引」。題目一換，問的東西不同，Map 裡該存的東西也跟著換，但骨架不變。變化題通常只是換掉 Map 裡存什麼：

題目問Map 的鍵 → 值走到 x 時做什麼
哪兩個索引（本題）價格 → 索引查到補數就回傳
總共有幾組（練習 3）價格 → 出現次數（第 4 課的頻率表）答案加上「補數出現過幾次」，再把 x 的次數 + 1
同一位顧客在 k 筆之內又點了（練習 4）顧客編號 → 最近一次出現的索引查上次出現的位置，距離 ≤ k 就是 true；不管有沒有查到，都更新成目前的索引

先看「有幾組」為什麼要存次數。以 [80, 80, 80]、禮券 160 為例：走到第一個 80，前面沒有 80，+0；走到第二個 80，前面有 1 個 80 可以配，+1；走到第三個 80，前面有 2 個 80 可以配，+2；總共 3 組，正好是 (0,1)、(0,2)、(1,2)。關鍵在「前面有幾個補數，就多幾組」，所以 Map 要記的是次數。如果只用 Set 記「有沒有看過」，第三個 80 也只會 +1，答案變成 2，少算了一組。

再看「k 筆之內又點了」。這題的補數不是「目標 − x」，而是「同一個顧客編號」：走到一位顧客時，問的是「他上次出現在哪裡、離現在多遠」。因為只關心最近的那一次，每走到一次都要把 Map 更新成目前的索引；只記第一次出現的位置，會錯過後面更近的兩次。

💡 實務上：「記住最近一次」就是重複送出偵測的雛形
咖啡店 POS 上店員連按兩次結帳、網路慢時顧客重整頁面，都會讓同一位顧客在幾秒內出現兩筆一樣的訂單。偵測的想法跟練習 4 一樣：Map 記「顧客 → 最近一次下單的時間」，跟上一筆太近就擋下或提醒，只是把索引差換成時間差。但這個 Map 只存在一台伺服器的記憶體裡，伺服器重啟就清空、開了多台也互相看不到，所以正式做法是前端送出後先停用按鈕，後端再交給資料庫擋。資料庫可以設定唯一限制（unique constraint）：規定某個欄位的同一個值只能存一筆。後端讓每次送出都附上一個唯一編號，存進設了唯一限制的欄位；同一次送出被重送時編號相同，第二筆寫入就會被資料庫拒絕。這種 Map 適合做報表上的「可疑重複訂單」檢查，不適合當唯一的防線。

下面的練習照這課的順序走：先補完 giftCardPair，再從空白寫一次，最後做「數幾組」和「k 筆之內」兩個變化題。

補充與查表

主線用不到、但面試追問時可能會碰到的延伸。

要回傳所有組合

Map 的值改成索引的陣列（價格 → 所有出現過的索引），走到 x 時把補數的每個索引都跟 i 配成一組。要注意輸出本身可能有 O(n²) 組，例如全部都是 80，這時任何寫法都至少 O(n²)，因為光是把答案寫出來就要這麼多步。

資料多到放不進記憶體

Map 需要 O(n) 記憶體，放不下時常見的做法是先把資料排序：分段讀進記憶體排序、寫回磁碟，再把排好的各段合併，這叫外部排序。排好之後，用只需要少量記憶體的雙指標掃一遍。面試時答出「Map 是用空間換時間，空間不夠時換回排序」這個取捨就夠了。

練習

練習 2～4 有大資料量的計時測試：雙迴圈或在迴圈裡用 indexOf／includes 會因為太慢判錯（第 2 課說過，判分逾時或計時不過就是複雜度不夠）。傳進來的陣列被凍結了，不能 sort、push。

練習 1：giftCardPair 的 Map 和迴圈已經寫好，在迴圈裡補上三步：算出補數 need、Map 裡有 need 就回傳 [它的索引, i]、沒有就把目前的價格和索引存進 seen。回傳索引，不是價格；沒有答案回傳 null。

練習 2：這次從空白開始，自己寫完整的 giftCardPair(prices, budget)：找兩杯不同的飲料，價格加總剛好等於禮券金額，回傳索引 [i, j]（i < j，是索引不是價格）；有多組時回傳任一組；沒有就回傳 null。要 O(n)：測試會跑 5 萬筆、答案藏在正中間的資料，不管從前面還是從後面開始的雙迴圈都會太慢。對應 LeetCode 1. Two Sum。

練習 3：寫 countGiftCardPairs(prices, budget)：回傳有幾組索引 (i, j)、i < j，兩杯價格加總剛好等於禮券金額。價格可以重複，例如 [80, 80, 80]、160 有 3 組（(0,1)、(0,2)、(1,2)）。要 O(n)。提示：Map 裡存的不是索引，而是「這個價格到目前為止出現幾次」。

練習 4：customerIds 是依點餐順序排好的顧客編號。寫 returnedWithin(customerIds, k)：有沒有同一位顧客在 k 筆之內又點了一次，也就是兩次出現的索引差 ≤ k？有就回傳 true。例如 [3, 1, 2, 3]：顧客 3 在索引 0 和 3，差 3，所以 k = 3 是 true、k = 2 是 false。同一位顧客出現很多次時，任兩次夠近就算。要 O(n)。對應 LeetCode 219. Contains Duplicate II。

練習 5：一次走完的 Map 解法，為什麼要「先查再存」？

✓ 先查再存時，Map 裡只有左邊、其他的飲料，查到的一定是另一杯。a 錯：[80]、禮券 160 時先存再查會回傳 [0, 0]。b 錯：兩種順序存進 Map 的筆數一樣，速度不是問題，正確性才是。

練習 6：價格 [80, 80]、禮券 160，用先查再存的 Map 解法會怎樣？

✓ 走到第二個 80（索引 1）時先查補數 80，Map 裡有第一個 80 → 0，回傳 [0, 1]，根本還沒走到「存」那一步。a 錯：鍵重複時 set 會覆蓋舊值而不是失敗，而且這裡查在存之前。c 錯：查到的是 Map 裡存的索引 0，不是目前的索引。

練習 7：同事說：「先把價格排序，再用雙指標從兩端往中間找，一樣是快的解法。」用在這一題，問題在哪？

✓ 這題要回傳原本的索引，排序後的位置不能直接用，還得把 [價格, 原索引] 一起排序；時間也從 O(n) 變成 O(n log n)。b 錯：只有在資料本來就排好時，雙指標才比較好（不用排序，也省下 Map 的 O(n) 空間）。c 錯：排好序之後的雙指標每一步移動一個指標，是 O(n)（第 7 課）。

常見錯誤

  • 先存再查：目標剛好是某個值的兩倍時，同一個元素被用兩次。先查，沒查到才存。
  • 回傳值而不是索引：重述題目時就確認輸出是什麼，並看函式簽章。
  • 用 if (j) 判斷有沒有查到：索引 0 是 falsy，會被當成沒查到。跟 undefined 比，或用 has。
  • 以為 Map 解法不用空間：它用了 O(n) 的額外記憶體。資料已經排序時，可以用雙指標省下這些空間。
  • 排序後忘了原本的索引：排序會打亂位置，回傳的索引就錯了。
  • 用 Set 處理需要次數的變化題：Set 只記「有沒有」，重複的值只算一次。要算有幾組就用頻率表。
  • 「k 筆之內」只記第一次出現的位置：之後的出現可能更近，Map 要一直更新成最近一次。

小結

  • 動手前先重述題目，把回傳什麼、能不能重複、找不到回什麼問清楚，寫成函式簽章：[number, number] | null。
  • 暴力解比對每一組，n(n − 1) / 2 次，O(n²)。它的內迴圈一直在問「有沒有一個值等於 budget − x」，這是查找。
  • 補數查找：對每個 x 問「budget − x 看過了嗎？」，用 Map 記住「值 → 索引」，一次走完，O(n) 時間、O(n) 空間。判斷查到沒要跟 undefined 比，因為索引 0 是 falsy。
  • 先查再存：Map 裡只有左邊的元素，保證不會用到自己，重複的值也能正確配對。
  • 陣列本來就排好時，可以改用雙指標省下 Map 的 O(n) 空間；沒排好又要原本的索引時，排序會把索引打亂，用 Map。
  • 變化題換的是 Map 裡存什麼：索引、出現次數、最近一次的位置。
