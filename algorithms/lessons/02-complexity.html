階段 1：解題基本功 · 第 2 課

複雜度：用迴圈次數看 Big-O

咖啡店的後台有一支「找出重複訂單」的程式：把今天的訂單編號一筆一筆放進結果清單，放進去之前先用 includes 檢查清單裡是不是已經有了。測試時只有 50 筆訂單，一瞬間就跑完。上線半年後訂單累積到 10 萬筆，同一支程式要跑好幾分鐘，API 逾時，店長的報表打不開。程式沒有寫錯，每一筆的判斷都對；錯在上線前沒有人問：資料變多時，它會慢多少？

這一課從頭到尾都在處理這支程式：先數出它要做幾步，再用 Big-O 說出它的成長速度，找出它明明只有一個迴圈、卻和雙迴圈一樣慢的原因，評估改用 Set 要多付多少記憶體，最後學會在上線前判斷夠不夠快、看不出來時自己量。面試時寫完程式，面試官幾乎一定會問「時間和空間複雜度是多少？」，回答的也是同一件事。第 1 課留下的問題「禮券題 4 杯試了 6 組，1 萬杯要試幾組？」其實也是同一個問題，第一節數迴圈時會一起回答。

這課的路線：
  1. 訂單從 50 筆變 10 萬筆會慢多少：不看秒數，改數最內層那一行跑幾次，寫成 n 的式子（開場問題的最小答案）。
  2. 式子長短不一怎麼比：Big-O 的兩條規則，程式一前一後、一層套一層時怎麼合起來；接著看六種常見複雜度在 10 萬筆時差多少。
  3. 只有一個 for 為什麼也是 O(n²)：藏在 includes 裡的迴圈，以及常用內建方法的成本。
  4. 改用 Set 變快了，代價是什麼：空間複雜度，為什麼「用空間換時間」是最常見的改進。
  5. 上線前怎麼判斷夠不夠快：從資料量的上限推回需要的複雜度；看不出複雜度時怎麼實測。
這課會用到：
  • 第 1 課的七步驟與暴力解：暴力解把所有可能都試一遍，一定對但通常慢；七步驟的最後一步「說出時間與空間複雜度」就是這一課。
  • TypeScript 課第 2 課的複製陣列：slice()、[...arr] 都會產生一個新陣列，原陣列不變。

訂單從 50 筆變 10 萬筆，程式會慢多少？

最先想到的做法是量秒數。但同一支程式在店長的筆電上跑 1 秒，在舊的收銀機上可能跑 3 秒；同一台電腦，背景有沒有在跑別的程式也會差。秒數同時混進了「程式本身做了多少事」和「這台電腦有多快」，拿它沒辦法比較兩種寫法，更沒辦法在 10 萬筆資料出現之前預測會花多久。

所以改數步數：程式裡最內層的那一行一共執行幾次。最內層那一行是重複最多次的工作，外面幾層跑的次數都不會比它多，數它就抓到了主要的成本。步數跟電腦無關：同一份輸入，在哪台電腦上數，答案都一樣。

步數會跟著輸入的大小改變，所以需要一個符號代表「輸入有多大」，慣例用 n。在找重複訂單裡，n 是訂單的筆數；在其他題目裡，通常是陣列或字串的長度。我們要的答案是一個用 n 寫成的式子：給一個 n，就能算出要跑幾步。

前兩種直接數得出來。單迴圈每個元素看一次，共 n 次。雙迴圈 j 從 0 開始時，外層跑 n 圈，每一圈內層都完整跑 n 次，所以是 n × n。

第三種要加一下：i = 0 時 j 從 1 跑到 n − 1，共 n − 1 次；i = 1 時 n − 2 次；……；最後一圈 0 次。把 0 到 n − 1 加起來就是 n(n − 1) / 2：第一個加最後一個、第二個加倒數第二個，每一對都是 n − 1，一共 n / 2 對。它是第二種的一半，但 n 變 10 倍時一樣變大約 100 倍。第 1 課的禮券題就是這個形狀：4 杯飲料兩兩配對，代進去是 4 × 3 / 2 = 6 組，和當時手算的一樣；換成 1 萬杯，就是大約 5000 萬組。找重複訂單最直覺的暴力解，每一筆都跟後面每一筆比一次，也是這個形狀。

第四種的 i 從 1 開始每次乘以 2，跑的次數有一個專門的名字：對數。log₂ n 讀作「以 2 為底 n 的對數」，意思是「n 可以除以 2 幾次才變成 1」，反過來說就是「從 1 開始乘 2，乘幾次會到 n」。之後簡寫成 log n。1000 大約 10 次，100 萬大約 20 次，10 億也只要大約 30 次。這是極慢的成長：資料變 1000 倍，步數只多 10。

有了這四個式子，開場的問題已經能回答一半：只要知道找重複訂單屬於哪一種，就能從 50 筆推到 10 萬筆。如果它是第二或第三種，筆數變成 2000 倍，步數就變成大約 2000² = 400 萬倍。但式子有長有短，n(n − 1) / 2 和 n² 算不算同一種？需要一個統一的說法。

式子長短不一，怎麼用一句話說出成長速度？

上一節表格的最右欄已經透露了方向：兩種雙迴圈的次數差了一半，可是 n 變 10 倍時都變大約 100 倍。比較寫法時，真正要知道的是這一欄，也就是資料變大時步數怎麼成長，而不是剛好幾步。

這個成長的方式叫做時間複雜度（time complexity），寫法叫 Big-O。O(n) 讀作「big O of n」，意思是「步數跟 n 同樣的速度成長」；O(n²) 就是「跟 n² 同樣的速度成長」。從式子變成 Big-O，規則只有兩條：

  1. 去掉常數倍：2n、n / 2、100n 都寫成 O(n)。常數會讓程式快或慢幾倍，但不會改變「n 變 10 倍、時間變幾倍」。
  2. 只留成長最快的那一項：n² + n 寫成 O(n²)。n = 10 萬時 n² 是 100 億，n 只有 10 萬，加不加它幾乎沒差。

所以 3n² + 5n + 2 是 O(n²)，n(n − 1) / 2 = n²/2 − n/2 也是 O(n²)。上一節的問題有了答案：兩種雙迴圈是同一個等級。

可以這樣丟，是因為 Big-O 只回答「n 變大時，時間變幾倍」這一個問題。常數倍不影響這個比例；比較小的項在 n 夠大時，佔總步數的比例會小到可以忽略。被丟掉的東西仍然會影響實際的毫秒數，這一點在本節最後的提醒再談。

實際的程式不會只有一個迴圈。拿到一段程式，先看它的形狀，再照這張表合起來：

第三列最常被寫錯。n 筆訂單逐筆比對 m 個商品是 O(n × m)；咖啡店只有 6 種商品，m 固定是 6，這段實際上跟 n 等比例成長。寫成 O(n²) 會讓人以為它很慢，也會讓你判斷錯該不該改寫。

還有一個問題：同樣是 n 筆訂單，步數不一定一樣。以開場的 dedupe 為例：外層迴圈每一筆都要走，不會提早結束；會提早停的是 includes，它一找到相同的編號就停，所以重複的編號很多時比較快。編號全部不重複時，每次 includes 都要比完整個結果清單，這就是 dedupe 的最壞情況，也是後面那個 lab 用的輸入。所以說複雜度時要講清楚指哪一種情況。最壞情況（worst case）是指在所有大小為 n 的輸入裡，步數最多的那一種。Big-O 沒特別說明時，指的就是最壞情況，因為上線後挑不了輸入，要保證的是最慢的那一次也能接受。面試時說「O(n²)」，意思是「最壞情況下步數跟 n² 一樣成長」。

Big-O 不是在說「幾毫秒」。n 很小時，O(n²) 的程式可能比 O(n) 但常數很大的程式還快；但 n 夠大時，O(n²) 一定會被追過去。所以實務上兩個都要看：先看成長速度選對演算法，同一個等級裡才比常數。

現在可以替程式分等級了。但等級之間到底差多少？10 萬筆訂單時，O(n²) 只是慢一點，還是根本跑不完？

n = 10 時，就算是 O(n²) 也只有 100 步，用哪一種都感覺不出來，這就是測試資料只有 50 筆時一切正常的原因。到 n = 10 萬，O(n) 是 10 萬步，O(n²) 是 100 億步，差了 10 萬倍；O(n log n) 跟 O(n²) 也差了大約 6000 倍。演算法的選擇，在資料小的時候幾乎看不出差別，資料大了才會一次爆開，所以面試官這麼在意這個問題。

O(n log n) 這一列值得多看一眼：它比 O(n) 慢，但慢得不多，10 萬筆時只多了大約 17 倍。排序就是這個等級，所以「先排序再走一遍」常常是把 O(n²) 降下來的第一步，第 8 課會用到。O(2ⁿ) 則是另一個極端，n 每多 1，步數就加倍，只有 n 很小時能用。

只有一個 for，為什麼也是 O(n²)？

答案在迴圈裡的那一行 includes。arr.includes(x) 沒有魔法，它就是從陣列的第一格開始一格一格比，比到相同的就停；如果 x 不在裡面，就要比完全部，最壞要比 n 次。程式碼裡看不到第二層迴圈，不代表它不存在。數步數時要數的是實際執行了幾次比較，不是程式裡寫了幾個 for。

下面的 dedupe 就是開場那支程式。為了看見藏起來的步數，用自己寫的 includesCounted 代替內建的 includes：做的事一樣，只是每比一次就把 steps 加一。輸入的編號全部不重複，所以每次都要比完整個結果清單，這是最壞情況。執行後看 n 變 10 倍時，比較次數變幾倍：

n 變 10 倍，比較次數變 100 倍：這是 O(n²)，不是 O(n)。算一下就知道為什麼：第 k 筆進來時，result 裡已經有 k − 1 筆，includes 要比 k − 1 次；從第 1 筆加到第 n 筆是 0 + 1 + … + (n − 1) = n(n − 1) / 2，跟第一節第三種迴圈是同一個式子。外層看起來只有一個 for，乘上 includes 裡藏的那一層，就是兩層。

要變成 O(n)，就得讓「查有沒有」這一步不再從頭比。第 4 課的 Set 做得到：它用雜湊表依照值直接算出該去哪一格找，不管裡面有幾個元素，查一次平均都是固定幾步。把 result 的查詢改成 Set 的 has，n 次查詢、每次 O(1)，整支程式就是 O(n)。

includes 不是唯一藏著迴圈的內建方法。寫程式時，迴圈裡每呼叫一個方法，都要問一句「它自己走了幾格」。下面這張表是常用方法的成本，查表用，不用背。記住判斷的方式就好：會從頭找的、會複製或處理每個元素的、會讓後面每一格搬動的，都是 O(n)。

表裡有兩個新的修飾詞。push 寫的是攤銷 O(1)（amortized），意思是偶爾有一次很慢、但平均下來每次都很快。陣列底下預留了一些空位，push 平常直接放進空位；空位用完時，要換一塊更大的記憶體、把全部元素搬過去，這一次是 O(n)。因為每次擴大都是按比例放大，不是每次只多一格，下一次搬家要隔很久才會發生，把搬家的總成本平均分攤到每次 push 上仍是常數。dedupe 裡的 result.push 就是攤銷 O(1)，所以拖慢它的只有 includes。

Map、Set 寫「平均 O(1)」，是因為雜湊表在極少數情況會退化變慢，實務上當成 O(1)。規格對這兩者和 shift 的實際要求，見課末的補充。

💡 實務上：code review 最常抓到的是「迴圈裡的 find」
最常見的樣子是在前端或 API 裡把兩份資料「接起來」：orders.map(o => customers.find(c => c.id === o.customerId))，訂單和顧客一多就是 O(n × m)。改法通常很簡單：迴圈外先用 new Map(customers.map(c => [c.id, c])) 建一次索引，迴圈裡改用 get。但也不要見到 find 就改：資料量本來就固定很小（例如咖啡店的 6 種商品），維持好讀的寫法就好。資深工程師 review 時會問的是「這兩份資料以後會長到多大？」，而不是一律要求最佳化。

找重複訂單改用 Set 之後，從 O(n²) 變成 O(n)。但 Set 不是免費的：10 萬筆編號全部不重複時，Set 裡就存了 10 萬個編號。這筆記憶體要怎麼算、值不值得付？

改用 Set 之後變快了，代價是什麼？

速度不是程式唯一的成本，記憶體也是。空間複雜度（space complexity）問的是：輸入變大時，程式額外用的記憶體怎麼成長。數法跟時間一樣，找出「會跟著 n 一起長大的東西」，看它最多多大，再用 Big-O 寫。

「額外」兩個字要說清楚。輸入本身不算，因為不管怎麼寫都得有它。題目要求回傳的輸出算不算，各家說法不一，面試時講明白就好，例如「除了輸出，額外 O(1)」。用這個說法看找重複訂單：includes 版除了輸出的 result，只用了幾個變數，額外 O(1)；Set 版多了一個最多 n 個元素的 Set，額外 O(n)。

常見的空間複雜度有下面幾種形狀。這裡用一個價格陣列 prices 示範，因為找重複訂單只用得到其中一種。第四種用到遞迴，也就是函式呼叫自己，第 15 課會細講；先要知道一個名詞：呼叫堆疊（call stack）是記錄「哪些函式呼叫還沒回傳」的記憶體，每呼叫一層就多一格，回傳時拿掉那一格。

// O(1) 額外空間：只用了幾個變數，跟 n 無關
let max = -Infinity
for (const p of prices) if (p > max) max = p

// O(n)：建了一個跟輸入一樣大的新陣列或 Map
const copy = [...prices]
const countById = new Map<number, number>()

// O(n²)：每一圈都 slice 一份新陣列，全部留著
const prefixes = prices.map((_, i) => prices.slice(0, i + 1))

// O(n)：遞迴深度 n，每一層都在呼叫堆疊上占一格（第 15 課）
function sum(i: number): number { return i === prices.length ? 0 : prices[i] + sum(i + 1) }

第三段每一圈 slice 出長度 1、2、…、n 的陣列，而且全部留在 prefixes 裡，加起來大約 n² / 2 格，所以是 O(n²)。練習 3 的起始程式也是每圈 slice 一份，所以時間和空間都會變成 O(n²)。第四段的 sum(0) 要等 sum(1) 回傳才能算完，sum(1) 又要等 sum(2)，一路到底，n 層同時留在呼叫堆疊上，所以雖然沒有建任何陣列，仍然是 O(n)。

這門課最常見的改進方式就是用空間換時間：多開一個 O(n) 的 Map 或 Set 記住看過的東西，把 O(n²) 的雙迴圈變成 O(n) 的單迴圈。找重複訂單換成 Set 正是這種交換：多付 O(n) 的記憶體，省掉藏在 includes 裡的那一層迴圈。第 5 課的 Two Sum 會用同一招改進第 1 課的禮券題。在後端，記憶體也有上限，所以時間和空間兩個都要說出來，讓面試官或同事知道你付出了什麼、換到了什麼。

💡 實務上：後端的記憶體是所有請求共用的
常見的坑是報表 API 把整張 orders 表全部讀進陣列，再用 filter、map 在程式裡算。資料少時沒事，資料變多時每個請求都占一份 O(n) 的記憶體，幾個人同時開報表，伺服器就可能記憶體不足而重啟。這時的改法通常不是寫更聰明的迴圈，而是讓資料庫去篩選和加總（WHERE、SUM），或改用分頁只拿需要的那幾筆。反過來，為了查詢變快多開一個小 Map 當索引，通常是很划算的交換。

現在找重複訂單有兩個版本：O(n²) 但不佔額外記憶體，O(n) 但多一個 Set。如果訂單永遠只有 50 筆，改寫值得嗎？上線前要怎麼判斷暴力解夠不夠用？

上線前怎麼判斷暴力解夠不夠快？

方法是把資料量的上限代進複雜度，算出步數，再換算成大概要幾秒。換算需要一個粗估：JavaScript 每秒大約能做 10⁷～10⁸ 個簡單步驟（只是數量級，依電腦和程式而定）。這個數字不精準，但不同複雜度之間的差距是幾千、幾萬倍，粗估差個 10 倍也不會改變結論。

套到找重複訂單：50 筆時 O(n²) 是 2,500 步，瞬間完成；10 萬筆時是 10¹⁰ 步，以每秒 10⁸ 步算要 100 秒，以每秒 10⁷ 步算要 1000 秒，這就是 API 逾時的原因。同樣 10 萬筆，O(n) 的 Set 版只要 10⁵ 步，一下就跑完。如果上線前有人做了這個計算，就會知道 50 筆的測試結果不能代表半年後。

LeetCode 這類題目會直接把上限寫出來，通常是「1 ≤ n ≤ 10⁵」這種限制。這不是裝飾，它在告訴你需要多快的解法。把常見的上限和對應的複雜度整理成表：

所以第 1 課的七步驟裡，「讀限制」排在寫程式之前：n ≤ 100 時暴力解就是正解，不用多花時間；n ≤ 10⁵ 時，寫完暴力解要接著想怎麼改進。這門課的練習也照這個規則判分：

本課程的判分怎麼看複雜度：需要更好複雜度的題目，隱藏測試最後會用大資料量計時，跟參考解比，慢 20 倍以上就判錯，訊息會寫出花了幾毫秒。更慢的寫法（例如指數時間）會碰到引擎的 3 秒上限，顯示「執行超過 3 秒，已強制停止」。在這門課看到這兩種訊息，幾乎都代表複雜度不夠，不是電腦太慢；換台電腦不會過，換演算法才會。
💡 實務上：工作上沒人告訴你 n 的上限，要自己去問
題目會寫 n ≤ 10⁵，需求單不會。開始寫之前先估：這份資料現在有幾筆、一年後大概多少？可以查資料庫的筆數，或問 PM「這個列表是只看今天的訂單，還是全部歷史？」。估出來很小（例如店員名單），暴力解就是好解，不用多花時間；會一直長（例如訂單、操作紀錄），就要選對複雜度，或加上分頁、時間範圍限制。把你的假設寫在 PR 說明裡，之後資料量超過時，接手的人才知道要回來改哪裡。

這套估算的前提是你看得出程式的複雜度。遇到看不出來的情況，例如呼叫了不熟的函式庫，或想確認改成 Set 之後真的變快了，就要自己量。

看不出複雜度時，怎麼自己量？

不必量出精準的秒數，只要看倍數：把 n 加倍，看時間變幾倍。O(n) 大約 ×2，O(n²) 大約 ×4，O(n log n) 略多於 ×2。這跟第一節「n 變 10 倍時」那一欄是同一個想法，只是改用實際時間來看。量時間用 performance.now()，它回傳毫秒（有小數），比 Date.now() 精準。

下面量一個 O(n) 和一個 O(n²) 的函式，各用兩個 n，一個是另一個的兩倍。執行後看每一行最後的「倍數」：

多按幾次執行，數字每次都不一樣，但 O(n²) 的倍數會明顯比 O(n) 大。數字會飄，是因為量時間會受很多東西干擾，這段程式的寫法就是在排除這些干擾。

第一個干擾是第一次執行特別慢。JavaScript 引擎會觀察哪些程式常被執行，邊跑邊把它們編譯成更快的機器碼，這種做法叫即時編譯（JIT）。第一次執行時還沒編譯好，比之後慢，所以 measure 先跑一次暖身，不計時。

第二個干擾是單次結果不穩。同一台電腦上的其他分頁、引擎自己的垃圾回收，都可能剛好在某一次插進來。所以 measure 量 5 次、排序後取中間那個，也就是中位數；偶爾一次特別慢，不會影響結果。

第三，只比數量級。倍數是 1.8 還是 2.3 不重要，重要的是 ×2 還是 ×4。不同電腦的毫秒數也會差好幾倍，所以只拿同一台電腦、同一次執行的結果互相比。

還有一個容易忽略的干擾：引擎發現一段計算的結果沒有人用，可能直接把它最佳化掉，量到的時間會接近 0。所以 linear 和 quadratic 都把結果累加到外面的 sink，讓引擎不能跳過這些計算。

在工作上也是同樣的想法：API 變慢時，先看資料量跟時間的關係。資料多一倍、時間多四倍，就去找程式裡的雙迴圈或迴圈裡的 includes／find，而不是先加機器。回到開場，如果上線前拿 1 萬筆和 2 萬筆訂單各跑一次找重複訂單，看到時間變成 4 倍，就知道它是 O(n²)，不必等到店長的報表打不開。

練習

練習 3、4 的隱藏測試會用大資料量計時，O(n²) 的寫法會被判錯。

練習 1：編輯器裡有六段程式 a～f，n 都是陣列長度。在 answers 填上每一段的時間複雜度（只能填型別允許的六種寫法，打錯字會有型別錯誤）。卡住時，回到第一節的方法：數一數最內層那一行會跑幾次。

練習 2：寫 pairCount(n)：店裡有 n 杯不同的飲料，兩兩配成一組試喝（不分順序，同一杯不能跟自己配），一共有幾組？n 是 0 到 9 × 10⁷ 的整數。

編輯器裡的 countByLoop 用雙迴圈數，可以拿來對照小的 n。但 n = 9 × 10⁷ 時雙迴圈要跑 4 × 10¹⁵ 次，連單迴圈都太慢：隱藏測試會對 200 個很大的 n 各呼叫一次，用迴圈數的寫法會超過 3 秒。請用第一節推出來的式子，O(1) 算出答案。

練習 3：寫 runningMax(prices)：prices 是每天的價差資料（可能是負數），回傳一個新陣列，第 i 個是第 0 天到第 i 天之中的最大值。不能修改傳進來的陣列。

編輯器裡的版本結果是對的，但每一天都 slice 一份再找最大值：slice 是 O(n)、找最大值又是 O(n)，放在迴圈裡就是 O(n²)，空間也浪費。改成 O(n)：前一天的最大值已經算過了，今天只要跟它比。隱藏測試會用 n = 20,000 計時。

練習 4：寫 canBecomeTop(stamps, bonus)：stamps[i] 是第 i 位顧客目前的集點數，店長要送其中一位 bonus 點。回傳一個布林陣列，第 i 個表示「第 i 位拿到 bonus 點之後，會不會成為最多點的人（並列也算）」。沒有顧客時回傳 []；不能修改傳進來的陣列。對應 LeetCode 1431. Kids With the Greatest Number of Candies。

先想暴力解：每個人都重新找一次最大值，複雜度是多少？再想：最大值會因為輪到誰而改變嗎？隱藏測試會用 n = 20,000 計時，O(n²) 不會過。

練習 5：兩個各跑 n 次的迴圈，一前一後（不是套在一起），複雜度是？

✓ 一前一後是相加：n + n = 2n，Big-O 去掉常數就是 O(n)。a 錯：只有套在裡面才相乘。c 錯：O(2n) 和 O(n) 是同一個等級，n 變 10 倍時兩者都變 10 倍。常數倍在實際毫秒數上仍有差，但成長速度一樣。

練習 6：for (const x of orders) if (vip.includes(x)) count++，orders 和 vip 的長度都是 n，複雜度是？

✓ includes 本身就是一個迴圈，最壞要比 n 次，放在跑 n 次的 for 裡就是 n × n。a 錯：要算的是步數，不是程式裡寫了幾個 for。b 錯：內建方法只是常數比較小，該走幾格還是要走幾格。改成先把 vip 放進 Set，has 平均 O(1)，整段就變 O(n)（第 4 課）。

練習 7：題目限制 n ≤ 10⁵，你只想得到 O(n²) 的解法。會怎樣？

✓ 把 n 代進去：(10⁵)² = 10¹⁰，以每秒 10⁸ 步粗估要 100 秒以上，所以 a 對。b 錯：10 萬筆走一遍很快，但兩兩比較是 100 億次。c 錯：好的機器頂多快幾倍，差距卻是幾千倍；而且資料還會繼續變多，換演算法才是解法。面試時就算寫不出更好的解，也要先說出暴力解的複雜度和它為什麼不夠。

練習 8：關於 Big-O，下面哪一句對？

✓ Big-O 丟掉了常數，只看成長速度。a 錯：毫秒數跟電腦、常數都有關，Big-O 不管這些。b 錯：例如 100n 和 n²，n < 100 時 n² 比較小；n 超過 100 之後，n² 就被 100n 甩開。所以 n 只有幾十的情況，簡單好懂的寫法常常就夠了；資料量會長大的地方，才值得換成複雜度更好的寫法。

常見錯誤

  • 忽略內建方法的成本：includes、indexOf、find、slice、展開、shift、splice 都會走過陣列，放在迴圈裡就多乘一個 n。開場的找重複訂單就是這樣變成 O(n²)。
  • 把兩個獨立迴圈當成 O(n²)：一前一後相加，套在裡面才相乘。
  • 兩個不同的輸入寫成同一個 n：n 筆訂單配 m 個商品是 O(n × m)，m 很小時跟 O(n²) 差很多。
  • 只量一次時間就下結論：第一次有 JIT 暖身，其他程式也會干擾；暖身、量多次取中位數，只看倍數的數量級。
  • 忘了空間也是成本：每一圈都 slice 一份新陣列，時間和空間都變成 O(n²)。
  • 用 Math.max(...arr) 處理很大的陣列：展開會把每個元素變成一個參數，參數數量有引擎上限（規格沒有規定，MDN 提到通常是幾萬個以上就可能出事），可能丟 RangeError。陣列可能很大時用迴圈找最大值。

小結

  • 秒數會隨電腦改變，所以改數步數：最內層那一行跑幾次，寫成 n 的式子。
  • Big-O 只描述 n 變大時步數怎麼成長：去掉常數、只留成長最快的項；一前一後相加，套在裡面相乘；不同的輸入用不同的變數；沒特別說明時指最壞情況。
  • 由快到慢：O(1)、O(log n)、O(n)、O(n log n)、O(n²)、O(2ⁿ)。資料小時差別看不出來，10 萬筆時 O(n) 和 O(n²) 差 10 萬倍。
  • 內建方法也是迴圈：includes、indexOf、slice、展開、shift、splice 是 O(n)；push、pop 攤銷 O(1)；Map／Set 平均 O(1)；sort 是 O(n log n)。只有一個 for 也可能是 O(n²)。
  • 空間複雜度看額外用的記憶體；用 O(n) 的空間換掉一層迴圈是最常見的改進，找重複訂單換成 Set 就是這樣。
  • 先讀限制再寫：n ≤ 10⁴ 時 O(n²) 勉強可以，10⁵ 以上要 O(n log n) 或 O(n)。工作上沒有人給上限，要自己估資料量。這門課判分逾時或計時不過，代表複雜度不夠。
  • 看不出複雜度時，把 n 加倍量時間：×2 是 O(n)，×4 是 O(n²)。暖身、量多次取中位數。

補充與查表

主線用不到、但查資料時會遇到的細節，查表用，不用背。

  • Map、Set 為什麼說「平均」O(1)：ECMAScript 規格只要求存取時間平均「低於線性」，V8 用雜湊表實作，實務上當成 O(1)。雜湊表在極少數情況會退化，第 4 課會講原因。
  • shift 一律當成 O(n)：shift 依規格要把後面每個元素往前搬一格；V8 對某些陣列有最佳化，但不保證，寫題目時一律當成 O(n)。
