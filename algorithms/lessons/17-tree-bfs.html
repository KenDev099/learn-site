階段 5：遞迴與樹 · 第 17 課

二元樹 BFS：逐層處理

咖啡店的線上菜單要改版。新的選單一開始只顯示最上層，使用者點了「咖啡」才展開咖啡底下的東西，再點一次才看到品項。前端同事開了一張需求單：「後端照層級回給我就好，第一層有哪些、第二層有哪些、第三層有哪些，每層一個陣列。」分類在資料庫裡本來就是一棵樹，第 16 課也學過怎麼用遞迴走過整棵樹，看起來只要走一遍、把值收集起來就好。

問題出在順序。第 16 課的深度優先搜尋（DFS）會先一路鑽到最深，走完「咖啡」底下的所有東西，才回頭處理旁邊的「輕食」。每個節點都走得到，但收集到的順序是「一條分支一條分支往下」，跟選單要的「一層一層往外」對不上。這一課從頭到尾處理這份菜單樹：先找出一種一層一層走的方法，叫做廣度優先搜尋（BFS）；再把結果切成每層一個陣列交給前端；接著用同一個骨架回答菜單的另外兩個問題，「每一層最右邊是哪個分類」和「最少要點幾層才碰到真正的品項」；最後整理什麼時候該用 BFS、什麼時候該用 DFS。

這課的路線：
  1. DFS 的順序為什麼給不出逐層的選單：層與層序走訪是什麼，DFS 為什麼會一路往下，要怎樣的「待辦清單」才會一層一層走。
  2. 怎麼保證一層走完才走下一層：用佇列做 BFS，看佇列每一步的樣子（開場問題的最小答案）；菜單變大時，取出前端為什麼用索引而不用 shift。
  3. 前端要每層一個陣列：佇列裡同時有兩層的節點，怎麼知道這一層到哪裡為止。
  4. 同一個骨架再回答兩個問題：每一層最右邊是誰（只沿著右邊走為什麼會錯）、最少點幾層碰到品項（把最大深度的 max 換成 min 為什麼會錯）。
  5. 下一題該選 BFS 還是 DFS：從題目的哪些字眼看出來，兩者各用多少記憶體。
這課會用到：
  • 第 12 課的佇列：從尾端放入、從前端取出，先進先出；用 head 索引記住下一個要取的位置，因為 shift 是 O(n)。
  • 第 16 課的二元樹：節點是 { val, left, right }，treeFrom 依層把陣列建成樹；遞迴 DFS 先一路往下走到底，最大深度是 1 + max(左, 右)。

選單要一層一層給，DFS 的順序為什麼不行？

先把菜單畫成樹。沿用第 16 課的表示法：每個節點是 { val, left, right }，沒有子節點的那一邊是 null。treeFrom([1, 2, 3, 4, null, 5, 6, null, 7]) 依層、由左到右讀陣列，null 代表那個位置沒有節點。節點上的數字是分類在資料庫裡的 id，前端拿到 id 再對照名稱顯示。這課的範例都用這一棵樹：

id名稱是什麼
1全部菜單根，選單最上層
2咖啡分類，目前只上架一個子分類
3輕食分類
4義式咖啡咖啡底下的子分類
5可頌品項（葉節點）
6起司蛋糕品項（葉節點）
7拿鐵品項（葉節點）

第 16 課說過，沒有子節點的節點叫葉節點。在這份菜單裡，葉節點就是使用者真正能點的品項，其他節點都是分類。圖裡淡色的 5、6、7 就是葉節點。

前端說的「第一層、第二層」，在樹上有正式的名字。跟根的距離相同的節點屬於同一層（level）。這課把根算成第 0 層，所以「全部菜單」在第 0 層，「咖啡」「輕食」在第 1 層，「義式咖啡」「可頌」「起司蛋糕」在第 2 層，「拿鐵」在第 3 層。有些題目把根算成第 1 層，題目會寫清楚，寫程式前先確認。

依層、每一層由左到右走過每個節點，叫做層序走訪（level-order traversal）。這棵樹的層序是 1、2、3、4、5、6、7。把它照層切開，就是前端要的 [[1], [2, 3], [4, 5, 6], [7]]。

拿第 16 課的前序走訪來比：它走這棵樹的順序是 1、2、4、7、3、5、6，處理完 2 底下整條分支（4、7），才回來處理 3。為什麼會這樣？遞迴其實也有一份「還沒處理的節點」清單，就是第 15 課的呼叫堆疊。處理 1 時，程式先遞迴進到左子節點 2，「之後還要處理 3」這件事被壓在堆疊下面；進到 2 又馬上遞迴進到它的左子節點 4，以此類推。堆疊是後進先出，越晚發現的節點越先處理，而越晚發現的節點通常越深，所以 DFS 會一路往下鑽。

要一層一層走，需要反過來：越早發現的節點越先處理。第 1 層的節點比第 2 層的早被發現（它們是處理根的時候發現的），只要照發現的順序處理，就一定先處理完第 1 層。「先放進去的先拿出來」正是第 12 課的佇列。用佇列當待辦清單、先走完同一層再往下一層的走法，叫做廣度優先搜尋（breadth-first search，BFS）：「廣」指的是先往旁邊把一層走寬，對照組 DFS 的「深」是先往下走到底。層序走訪就是在樹上做 BFS。

「照發現的順序處理」聽起來就會一層一層，但要確定它真的保證得了，而不是剛好這棵樹排得好，得把步驟寫出來，看佇列每一步長什麼樣子。

怎麼保證一層走完才走下一層？用佇列做 BFS

上一節的想法寫成步驟只有兩步：

  1. 把根放進佇列。
  2. 佇列不是空的就重複：從前端取出一個節點，處理它（例如記下它的值），再把它的左、右子節點（不是 null 的）放到佇列尾端。

為什麼這樣一定會一層一層？看節點是什麼時候被放進佇列的：第 1 層的節點，是處理第 0 層時放進去的；第 2 層的節點，是處理第 1 層時放進去的。換句話說，第 k + 1 層的節點全部要等到第 k 層的節點被取出時才會進佇列，所以它們在佇列裡一定排在第 k 層的所有節點後面。佇列又保證先放的先拿，結果就是走完上一層，才輪到下一層。這跟樹長什麼形狀無關。

下面的程式照這兩步走，每取出一個節點就印一列：取出誰、放進誰、佇列裡還剩什麼。treeFrom 和 TreeNode 已經貼好，這課每個範例和練習都有一份，不用自己寫。執行後對照上面的圖，看每一列的佇列裡，同一層的節點是不是都排在下一層的前面：

最後一行的層序 1 → 2 → 3 → 4 → 5 → 6 → 7，換成名稱就是「全部菜單、咖啡、輕食、義式咖啡、可頌、起司蛋糕、拿鐵」，正是選單由上往下的順序。開場的問題有了最小的答案：用佇列走，順序就對了。每個節點進佇列一次、出佇列一次，時間是 O(n)。

程式裡有一個細節要看清楚：放子節點之前先檢查 !== null。只把真的節點放進佇列，取出來的就一定能讀 node.val。如果把佇列寫成 (TreeNode | null)[]，把 null 也放進去，就得在取出時再檢查一次；忘了檢查，讀 null.val 會丟 TypeError。把佇列的型別寫成 TreeNode[]，你 push node.left（型別是 TreeNode | null）卻沒檢查時，TypeScript 會直接報錯，錯誤在寫程式的時候就被擋下來。

另一個細節是取出前端的寫法：程式沒有用看起來最直接的 queue.shift()，而是用 head 記住「下一個要取的位置」，取完就 head++。菜單只有 7 個節點時兩種寫法沒有差別；但「時間 O(n)」的前提是每次取出都是 O(1)，分類一多，這個前提就要檢查。

菜單變大時，用 shift 取出會出什麼事？

第 12 課講過：依規格，shift 拿走第一個元素之後，要把剩下的每個元素往前搬一格，所以一次 shift 的成本跟「佇列裡還有幾個」成正比，是 O(n)。BFS 要取出 n 次，總成本就看佇列平常有多長。

BFS 的佇列可以很長。先說一種常見的樹形：每一層都排滿，只有最後一層可能沒滿、而且從左邊開始排，這種樹叫完全二元樹（complete binary tree）。每往下一層，節點數就加倍，所以最下面一層大約就占了全部節點的一半。處理到倒數第二層時，最後一層的節點陸續被放進佇列，佇列裡會有將近 n / 2 個節點在等。這時每一次 shift 都要搬上萬個元素，整個 BFS 從 O(n) 變成 O(n²)。

head 索引版的時間跟著節點數大約加倍，符合 O(n)。shift 版在 2 萬個節點時可能還很快，到 4 萬個時卻多了十幾到上百倍。小陣列時 V8 有最佳化，不用真的逐一搬動，但這個最佳化什麼時候生效沒有保證，資料一大就回到 O(n) 的成本。你的瀏覽器跑出來的數字會不一樣，要看的是「節點加倍，時間變幾倍」；本課實測的數字記在課末。

head 索引的代價是：取出過的節點還留在陣列裡，記憶體要等整個 BFS 結束才釋放。一次性的 BFS（像這份菜單，每個請求走一次就結束）結束後整個陣列一起被回收，沒有問題；要一直跑下去的佇列（例如排程程式）才需要第 12 課的「偶爾整理」。面試時寫 head 索引，順口說一句「shift 是 O(n)，所以用 head 索引」，面試官就知道你清楚成本。

到這裡，順序對了，速度也對了。但程式輸出的是一串 1、2、3……，前端要的是每層一個陣列，而這串數字裡看不出哪裡換層。

前端要每層一個陣列：怎麼知道這一層到哪裡為止？

需求單上要的回傳值是 [[1], [2, 3], [4, 5, 6], [7]]：第 0 層一個陣列、第 1 層一個陣列，依此類推，前端拿到第 k 個陣列就畫第 k 層的選單。這也是一道常見的面試題，LeetCode 102. Binary Tree Level Order Traversal。

難處在於佇列裡會同時有兩層的節點。回頭看上一節的圖：取出第 1 層的 2 之後，佇列是 [3, 4]，第 1 層的 3 和第 2 層的 4 排在一起。單看佇列，分不出 3 和 4 之間是一條分層線。

關鍵在於找一個佇列裡剛好只有一層的時刻。上一節證明過：第 k + 1 層的節點要等第 k 層的節點被取出時才會進來。所以在第 k 層的第一個節點被取出之前，第 k − 1 層已經全部取完，第 k + 1 層一個都還沒放進來，佇列裡剩下的剛好全部是第 k 層。做法就是在這個時刻先記下佇列裡現在有幾個節點，存成 size，接下來只取 size 個。這 size 個節點取出時放進去的子節點全部屬於下一層，留給下一輪；下一輪開始時，佇列又回到「剛好只有一層」的狀態。

用 head 索引時要多想一步：佇列裡「還沒取出的」數量是 queue.length − head，不是 queue.length，因為前面取過的節點還留在陣列裡。

複雜度：每個節點進出佇列各一次，時間 O(n)。佇列裡同時「等著被取出」的節點最多是一整層，也就是最寬那一層的節點數，最壞 O(n)（上一節說過，完全二元樹的最後一層約 n / 2 個）。用 head 索引時，取出過的節點還留在陣列裡，陣列最後會長到 n；這題的回傳結果本來就有 n 個值，所以面試時說「空間 O(n)」就對了。

💡 實務上：樹形資料先問「一次給整棵，還是展開才載入」
菜單分類在資料庫裡通常是一張表，每列用 parent_id 記著自己的上一層是誰。分類只有幾十、幾百個時，後端一次撈出來、在記憶體裡建樹，再用這一節的寫法依層分組回傳最省事，還能整包快取。組織圖、留言串、雲端硬碟資料夾這種可能很大的樹，就改成「一次只回傳一層」：使用者展開某個節點，前端才帶著它的 id 去要子節點。資深工程師接到開場那種需求單，會先問：節點大概有多少、多久改一次、前端是一次全部顯示還是點了才展開，再決定 API 長什麼樣子。

「先記 size、只取 size 個」這個骨架，讓程式在每一層開始和結束時都有一個明確的位置可以做事。凡是「每一層的 X」的問題，都是在這個骨架上改一兩行。下一節用它回答菜單的第二個問題，順便看一個只看樹的形狀就會想錯的例子。

每一層最右邊是哪個分類？分層骨架改一行

選單畫出來後，店長想在每一層的最後面接一個「看更多」的按鈕，需要知道每一層最右邊的分類是誰，從上到下列出來。這是 LeetCode 199. Binary Tree Right Side View，題目的比喻是站在樹的右邊看過去，每一層只看得到最右邊那一個。練習 3 和下面範例裡的 shelf（展示櫃）沿用這個說法，指的就是這棵菜單樹。

直覺的寫法是從根一路往 right 走：1 → 3 → 6，也就是「全部菜單、輕食、起司蛋糕」。但看圖：第 3 層只有「拿鐵」7，它在左子樹裡（2 → 4 → 7）。第 3 層沒有別的節點擋在它右邊，所以它就是第 3 層最右邊的節點。正確答案是 [1, 3, 6, 7]。「每一層最右邊」問的是層，不是分支：同一層的節點可能分屬不同的子樹，右子樹比較淺時，下面幾層最右邊的節點就在左子樹裡。

有了上一節的分層寫法，這題只改一行：每一層的 size 個節點是由左到右取出的，所以最後一個（i === size − 1）就是這層最右邊的，把它記下來就好。

這題也可以用 DFS 寫，對照著看能更清楚 BFS 好在哪裡。DFS 的想法是：先走右子樹再走左子樹，那麼每一層「第一次到達」的節點，一定是這層最右邊的。怎麼知道是不是第一次到達某一層？結果陣列裡已經記了幾層，它的長度就是幾；目前的深度等於結果的長度時，代表這一層還沒有人記過，現在這個節點就是第一個。下面把 DFS 寫法和「只沿著 right 走」的錯誤寫法放在一起，執行後看兩者差在哪一層：

右視圖要走完整棵樹，才能確定最下面一層有誰。菜單的第三個問題不一樣，它找的是「最近」的東西：答案一出現，更深的地方就不用看了。

最少點幾層才碰到品項？

選單上線前，產品經理要檢查一件事：使用者從最上層開始點，最少要經過幾層才碰到第一個真正的品項（葉節點）。題目的定義是：回傳根到最近的葉節點那條路上有幾個節點；只有根時是 1，空樹是 0。這是 LeetCode 111. Minimum Depth of Binary Tree。題名的「深度」數的是節點，跟第 16 課表格裡數邊的深度（根是 0）差一，寫之前先確認題目怎麼數。

看圖：最近的品項是第 2 層的「可頌」5 和「起司蛋糕」6，路徑是 1 → 3 → 5，經過 3 個節點，答案是 3。第 2 層（從 0 算）的節點，路上經過 3 個節點：層號和題目要的節點數差 1，因為根本身也算 1 個。

DFS 的陷阱：null 不是葉節點

第 16 課的最大深度是 1 + max(左, 右)，空樹回傳 0。把 max 換成 min，好像就是最小深度。但它對這棵樹回傳 2，正確答案是 3。

錯在節點 2「咖啡」：它只有左子節點 4，右邊是 null。遞迴算到 2 時，右邊的空樹回傳 0，min(左邊的深度, 0) 取到 0，於是 2 的最小深度變成 1，等於說「咖啡本身就是一個品項」。但咖啡不是葉節點，它有子節點 4；沿著它往下走，碰到的第一個品項是第 3 層的拿鐵 7。問題的根源是：空樹回傳 0 代表「這裡沒有路」，不代表「這裡有一個深度為 0 的葉節點」，取最大值時這個差別無所謂（0 不會被選到），取最小值時就被選到了。

正確的遞迴要分開處理「只有一邊」：

if (node === null) return 0
if (node.left === null) return 1 + 右邊的最小深度    // 只能往右走
if (node.right === null) return 1 + 左邊的最小深度   // 只能往左走
return 1 + Math.min(左, 右)                          // 兩邊都有才取 min

寫對了也還有一個問題：DFS 不知道哪一邊比較淺，只能兩邊都算完再取最小值，就算其中一邊在第 2 層就碰到品項，另一邊再深都得走完。

BFS：遇到第一個葉節點就停

用 BFS 想就直接得多：一層一層往下走，第一個遇到的葉節點，它所在的層號加 1（因為題目數的是節點，根算 1 個）就是答案。程式裡的 depth 直接從根算 1，每進一層加 1，碰到葉節點時 depth 就是答案。理由是 BFS 照深度由淺到深檢查節點，碰到這個葉節點時，比它淺的層已經全部看過，都沒有葉節點，不可能有更近的。而且找到就能直接 return，下面的層不用看。判斷葉節點的條件是左右都是 null，跟 DFS 那個陷阱無關。

答案都是 2，但 DFS 要走完整條 2,000 個節點的鏈，才能確定右邊沒有更淺的葉節點；BFS 走到第 2 層就停了。反過來，如果葉節點都在很深的地方，BFS 也得走完幾乎所有節點，兩者一樣是 O(n)。最壞情況相同，但「答案在淺的地方」時 BFS 可以提早結束，這就是這題選 BFS 的理由。

💡 實務上：「找最近的」用 BFS，再加一個深度上限
像是在分類樹裡搜尋關鍵字，想讓層級最淺的分類排在最前面，或是這一節的「最多幾層就要能點到品項」這種檢查，都是一層一層往下找、找到就停。真實資料的深度不一定照設計走，所以實務上常再加一個層數上限：超過就停下來並記錄，不要讓一筆壞資料拖垮整個請求。如果要找的東西不在樹裡，而是在會繞回來的關係裡（例如連結、好友關係），就是圖了，需要記住走過哪些點，留到第 20 課。

菜單的三個問題都用 BFS 解完了。但第 16 課的最大深度、直徑也是樹題，用的是 DFS。下次遇到一道新的樹題，要怎麼判斷該用哪一種？

下一題該選 BFS 還是 DFS？

同一棵樹兩種都能走完，差別在走的順序，所以選哪個看題目要的答案跟哪種順序對得上。把這課和第 16 課的題目放在一起看：

題目在問選例子
跟「層」有關：每層的總和、每層最右邊、依層輸出BFS這課的依層分組、右視圖
最近、最短、最少幾步BFS：一層一層往外，第一次碰到就是最近的最淺的葉節點；第 20 課網格裡的最短路徑
要先知道整棵子樹的資訊才能算自己DFS（後序）第 16 課的最大深度、直徑、最近共同祖先
從根到某個節點的路徑DFS：遞迴的參數或堆疊裡就是目前的路徑根到葉的路徑總和

表格的前兩列，是因為 BFS 的順序本身就是「依層、由淺到深」，題目問層或問最近，答案直接落在這個順序上。後兩列是因為 DFS 一路往下再回頭：回頭的時候子樹已經算完，正好拿來算自己；往下走的時候，遞迴參數或堆疊裡留著從根到這裡的整條路。

記憶體也不一樣，兩者各自卡在樹的一個尺寸上：

  • BFS 的佇列最多同時等著一整層，空間是最寬那一層的節點數。又寬又淺的樹用得多（完全二元樹的最後一層約 n / 2 個）；一條鏈同時只等一個節點。這裡數的是「等著被取出」的節點；head 索引版的陣列會留著取出過的節點，最後長到 n（只想占最寬那一層的寫法見課末）。
  • DFS 的呼叫堆疊深度是樹的高度。平衡的樹是 O(log n)；歪成一條鏈時是 O(n)，太深還會丟 RangeError: Maximum call stack size exceeded（第 15 課）。BFS 用迴圈和陣列，沒有這個上限。

實務上碰到的樹（分類、組織圖、留言串、資料夾）通常不深，兩種都行，就選寫起來最直接對應題目的那一個。判斷的捷徑：題目說到「層」「最近」先想 BFS；說到「子樹」「路徑」先想 DFS。

💡 實務上：使用者能決定深度時，別讓遞迴吃掉堆疊
這課的菜單由店裡的人維護，深度幾乎不會失控；但留言的「回覆的回覆」、使用者自己建立的資料夾，深度由使用者決定，有人故意一路回覆下去，遞迴版的 DFS 就可能丟 RangeError。常見的做法有兩個：寫入時就限制層數（很多產品的留言只允許回覆到某一層，更深的就攤平顯示），或讀取時改用迴圈加佇列／堆疊。Code review 時看到遞迴走訪使用者產生的樹，可以問一句「最深可能到幾層？哪裡有擋？」

練習

每題都已經貼好 TreeNode 和 treeFrom。測試會傳入凍結的樹（不能修改節點），而且測試期間 shift() 和 splice(0, …) 會換成丟錯的函式：佇列請用 head 索引。練習 1、2 有計時測試，每取一個節點就複製一次佇列（例如 queue = queue.slice(1)）的寫法會太慢判錯（第 2 課：計時不過就是複雜度不夠）。

練習 1：寫 levelOrderFlat(root)：依層、每層由左到右，回傳所有節點的值（一維陣列）；空樹回傳 []。佇列用 head 索引。測試包含一棵 3 萬個節點的完全二元樹並計時。

練習 2：寫 levels(root)：回傳每一層的節點值，每層一個陣列、由左到右；空樹回傳 []（不是 [[]]）。對應 LeetCode 102. Binary Tree Level Order Traversal。測試包含一棵 3 萬個節點的完全二元樹並計時。

練習 3：寫 rightView(root)：站在展示櫃（樹）的右邊看，回傳從上到下每一層最右邊的節點值；空樹回傳 []。注意最下面幾層最右邊的節點可能在左子樹裡。對應 LeetCode 199. Binary Tree Right Side View。

練習 4：寫 shallowestLeaf(root)：回傳根到最近的葉節點（沒有子節點的節點）經過幾個節點；只有根時是 1，空樹是 0。用 BFS 寫，遇到第一個葉節點就回傳：測試會檢查答案在淺層時，你的程式沒有去讀更深的節點。對應 LeetCode 111. Minimum Depth of Binary Tree。

練習 5：同事寫 BFS 時用 queue.push() 放子節點、queue.shift() 取出節點，說「shift 跟 pop 一樣只拿一個，很快」。一棵 n 個節點的完全二元樹，這樣寫的問題是？

✓ shift 拿走索引 0 之後，後面每個元素都要往前一格，是 O(n)；完全二元樹的最後一層有約一半的節點，佇列很長時每次取出都很貴。V8 對小陣列有最佳化，但不保證，本課實測 2 萬個節點只要幾十 ms 以內、4 萬個就跳到將近 1 秒。a 錯：pop 拿尾端不用搬動，shift 拿開頭才要搬。b 錯：shift 拿的是最前面（最早放的），順序是對的，問題只在速度。d 錯：陣列長度的上限遠大於這個規模，不會因此丟錯。

練習 6：依層分組時寫了 for (let i = 0; i < queue.length - head; i++) { const node = queue[head++] … }，結果層和層混在一起。原因是？

✓ 一層開始的那一刻，佇列裡還沒取出的剛好全是這一層；之後一邊取出（head 變大）一邊放進下一層（queue.length 變大），算出來的數字就不再是這層的數量。先存成 size，只取 size 個。a 錯：head 是下一個要取的位置，一開始就是 0。c 錯：左右順序只影響同一層內的順序，跟分層無關，而且題目要由左到右。d 錯：用 shift 寫 i < queue.length 一樣會錯，問題在於沒有先記下數量。

練習 7：找最淺的葉節點時，哪一種寫法能在找到答案後立刻停下、不用看更深的節點？

✓ BFS 依深度由淺到深檢查節點，第一個葉節點出現時，更淺的層已經全部看過、都沒有葉節點，所以它就是答案，下面的層不用看。b 錯：DFS 第一個走到的葉節點可能在很深的分支裡（本課範例的 2,000 個節點的鏈），要走完其他分支才能確定沒有更淺的。c 錯：最壞情況（葉節點都很深）兩者都是 O(n)，但答案在淺的地方時 BFS 可以提早結束。

常見錯誤

  • 用 shift 當佇列：每次取出 O(n)，BFS 的佇列可能有約 n / 2 個節點，整體 O(n²)。用 const node = queue[head++]。
  • 分層時用會變動的長度：i < queue.length - head 寫在迴圈條件裡，每一圈都重算，層會混在一起。一層開始前先 const size = queue.length - head。
  • head 索引版用 queue.length 當作剩下的數量：取出過的還在陣列裡，要扣掉 head。
  • 把 null 放進佇列：取出後讀 node.val 丟 TypeError。放進去之前先檢查 !== null，佇列型別寫 TreeNode[]，讓 TypeScript 幫你擋。
  • 空樹回傳 [[]] 或丟錯：一開始先處理 root === null，依層分組回傳 []、最小深度回傳 0。
  • 右視圖只沿著 right 走：右子樹比較淺時，下面幾層看得到的是左子樹的節點。要取每一層的最後一個。
  • 最小深度把 null 當成深度 0 取 min：只有一邊子樹的節點不是葉節點。DFS 要分開處理只有一邊的情況；BFS 判斷左右都是 null 才是葉。

小結

  • DFS 的待辦清單是呼叫堆疊，越晚發現的越先處理，所以一路往下；要一層一層走，改用佇列，越早發現的越先處理，這就是 BFS。
  • BFS：根放進佇列；重複「取出前端、處理、把非 null 的子節點放到尾端」。下一層的節點要等上一層被取出才會進佇列，所以一層走完才走下一層。
  • 佇列用 head 索引：const node = queue[head++]，不要用 shift（O(n)，佇列長時整體變 O(n²)）。
  • 依層處理：每一層開始時佇列裡剛好只有這一層，先記下 size = queue.length − head，只取這 size 個；第 size − 1 個是這層最右邊的，右視圖問的是層，不是右邊那條分支。
  • 最淺的葉節點：BFS 遇到第一個左右都是 null 的節點就回傳，答案在淺層時可以提早結束；DFS 要小心只有一邊子樹的節點不是葉。
  • 選擇：層、最近、最短 → BFS；子樹的資訊、路徑 → DFS。空間：BFS 是最寬那一層，DFS 是樹的高度。
