階段 3：陣列技巧 · 第 10 課

滑動視窗

店長要在後台加一頁「連續區段報表」，給下週的檢討會用。上面有三個問題：拿鐵連續哪 3 天賣得最好（決定哪幾天加排人手）？今天最少要連續幾筆訂單，營收才達到 200 元？點餐紀錄裡，最長的一段連續訂單沒有同一位顧客出現兩次，有多長？這三個問題有一個共同點：問的都是陣列裡連續的一段。這課要寫出這頁報表背後的三個函式。

最直接的寫法是把每一段都拿出來，從頭算一遍。可是相鄰的兩段幾乎一模一樣，每次從頭算等於把同樣的加法做了很多次，資料一多報表就跑不動。這課的做法叫滑動視窗（sliding window）：用左右兩個索引框住一段，往右移時只處理進來的和離開的那一兩個元素，其他沿用上一段的結果。三個問題都能在 O(n) 內算完。

這課的路線：
  1. 第一題暴力解：「連續的一段」怎麼用兩個索引表示，每段重算時重複了哪些工作。
  2. 固定視窗：往右移一格時只加進來的、減離開的，連續 3 天的最高平均 O(n) 算完（開場問題的最小答案），以及交給後台前要擋哪些輸入。
  3. 第二題可變視窗：沒有給長度時，右邊擴張、左邊收縮；兩層迴圈為什麼還是 O(n)。
  4. 訂單有退款時：可變視窗靠的「單調性」是什麼，負數為什麼讓它失效。
  5. 第三題不重複的最長一段：用 Set 守住視窗裡有誰，再用 Map 讓左邊界一次跳到位；最後整理拿到新題目時怎麼判斷能不能用。
這課會用到：
  • 第 4 課的 Set 與 Map：Set 用 add／has／delete 記「有沒有」，Map 記「鍵 → 值」，查找都是平均 O(1)。
  • 第 7 課的雙指標：兩個存索引的變數，依條件各自移動，一共只走 O(n) 步。

第一題：連續 3 天平均最高，每段重算慢在哪？

報表的第一題用拿鐵這 7 天的杯數：[12, 15, 9, 20, 18, 7, 14]。店長想知道連續 3 天的平均杯數最高是多少。在寫任何程式之前，要先決定「連續 3 天」在程式裡怎麼表示。

陣列裡連續的一段，可以只用兩個索引描述：左邊界 left 和右邊界 right，兩端都包含在內。這樣框起來的一段就叫視窗（window）。因為兩端都算，視窗的長度是 right − left + 1：left = 2、right = 4 框住的是索引 2、3、4，共 3 個，不是 4 − 2 = 2 個。這個「+ 1」整課都會用到，少了它答案就差一。

連續的一段在陣列裡叫子陣列（subarray），在字串裡叫子字串（substring）。題目出現「連續」「一段」「subarray」「substring」，就是在問某個視窗。（另一個長得很像、但不是視窗的名詞「子序列」，見課末「補充與查表」。）

有了視窗的表示法，最直接的解法是：每個起點都把 3 天加一遍，記下最大的總和。長度 7、每段 3 天，起點從 0 到 4，共 n − k + 1 = 5 個視窗（n 是天數，這裡是 7；k 是視窗長度，這裡是 3）。下面的程式印出每一段和它的總和，最後一行數出總共做了幾次加法：

答案是對的，但成本是多少？每個視窗加 k 次，一共 n − k + 1 個視窗，總共 (n − k + 1) × k 次加法，是 O(n × k)（兩個變數相乘的寫法見第 2 課）。7 天看不出差別；但 n 和 k 一起變大時，差距會爆開。練習 1 的計時測試用 n = 50,000、k = 25,000，就是 6 億多次加法。

相鄰兩段重複了什麼？

要變快，先找出哪些加法是白做的。把相鄰兩個視窗排在一起看：

起點 0：12 + 15 + 9
起點 1：     15 + 9 + 20

15 + 9 被算了兩次。從起點 0 移到起點 1，視窗其實只變了兩格：左邊的 12 離開、右邊的 20 進來，中間的部分完全沒變。k 越大，中間沒變的部分越長，暴力解浪費的加法就越多。下一節就利用這件事：既然只有頭尾在變，就只處理頭尾。

每段重算太慢：能不能只處理進來和離開的那一格？

上一節看到，視窗往右移一格時只有兩個元素在變。所以新的總和不用重算，從舊的總和修正就好：

新總和 = 舊總和 + 進來的 − 離開的
sum += cups[i] − cups[i − k]

這裡的 i 是新視窗的右邊界。右邊進來的是 cups[i]；新視窗是 i − k + 1 到 i，所以剛離開的是它左邊那一格，也就是 cups[i − k]。整個流程是：先把第一個視窗（索引 0 到 k − 1）老老實實加一遍，之後 i 從 k 走到 n − 1，每一步只做一次加、一次減。視窗長度從頭到尾都是 k，所以這種寫法叫固定視窗（fixed-size window）。

同一組資料用滑動的寫法跑一遍，每一步印出進來、離開、總和與目前最好的總和。對照上一節暴力解的輸出，每一行的 sum 應該和那邊的總和一樣：

成本變成多少？第一個視窗加 k 次，之後每一步固定 2 次運算，共 n − k 步，總共大約 n + (n − k) 次，是 O(n)，跟 k 多大無關。暴力解在 k 變大時越來越慢，這個寫法不會。額外空間只有 sum、best 幾個變數，O(1)。

題目要的是平均，為什麼迴圈裡比總和？

店長問的是平均，但上面的程式一路比的都是總和，最後才除以 k。這樣做是對的：所有視窗的長度都是 k，平均就是總和除以同一個 k，總和最大的那一段，平均也一定最大。所以迴圈裡只比整數的總和，回傳前才除一次。

這樣做有兩個好處。第一，整數的加減在 JavaScript 裡是精確的；如果每一步都先除成小數再比，就是拿可能有誤差的小數互相比較。第二，少做很多次除法。最後除出來的平均是小數，要保留小數，不能用 Math.floor 或 | 0 截成整數，例如總和 29、k = 2 時平均是 14.5，截掉會變成 14。小數會有誤差，所以這一課的判分用「差距小於 10⁻⁹」比較平均值，原因和示範見課末「補充與查表」。

交給後台前要擋哪些輸入？

報表頁上的 k 是店長自己選的天數，資料也可能很短，所以函式不能假設輸入一定剛好。固定視窗要檢查的邊界有四個：

  • k > n：例如店剛開 2 天、店長選了 3 天。一個完整的視窗都沒有。不處理的話，第一個迴圈會讀到 cups[n] 這種不存在的位置，拿到 undefined，總和變成 NaN（第 3 課：越界不會報錯）。要先判斷，回傳 null，讓畫面顯示「資料不足」。
  • k < 1：長度 0 的視窗沒有意義，平均會變成除以 0。同樣回傳 null。
  • k === n：只有一個視窗，第二個迴圈一次都不跑，答案就是整段的平均。這不用特別處理，但要手算確認程式真的這樣跑。
  • 全部是負數：杯數有退杯調整時可能是負的。best 的初始值要用第一個視窗的總和，不能用 0，否則答案永遠不會小於 0（第 1 課講過的初始值錯誤）。

到這裡，報表的第一題已經可以交了：一次走完陣列、O(1) 空間、邊界都擋住，這就是練習 1。

💡 實務上：營收折線圖的「7 日移動平均」就是固定視窗
後台的營收折線圖常加一條 7 日移動平均線，抹平週末高、平日低的起伏，讓店長看出趨勢。動手前先問清楚「7 天」是日曆上的 7 天還是 7 筆資料：公休那天沒有訂單，資料裡就沒有那一天，用索引框 7 筆會跨到 8 天以上，要先把缺的日期補 0。資料多時通常交給資料庫的視窗函式（PostgreSQL 課第 17 課）或圖表套件算，前端只在資料已經載入、要即時切換天數時才自己滑。另外「頭幾天湊不滿 7 天要畫什麼」（留空或照實際天數平均），要先跟 PM 講好。

固定視窗有一個前提：事先知道視窗多長。報表的第二題就沒有給長度，長度正是要求的答案。

第二題沒有給長度：右邊擴張，左邊收縮

第二題用今天依序的訂單金額 [80, 70, 110, 90, 120, 40]，店長想知道最少要連續幾筆訂單，總額才會達到 200 元（≥ 200）。上一節的 sum += cups[i] − cups[i − k] 需要一個固定的 k，這裡沒有，所以要讓視窗的長度自己變。

暴力解是每個起點往右加，加到 ≥ 200 就記下長度，換下一個起點重來，O(n²)。它浪費的地方和第一題一樣：換起點時，把剛剛加過的又加了一遍。滑動視窗的做法是讓左右邊界各自決定什麼時候動：

  1. right 從左走到右，每一步把 totals[right] 加進視窗，視窗變長、總和變大。
  2. 只要視窗總和 ≥ 200，這一段就是一個候選答案，記下長度 right − left + 1。接著試著把最左邊那一筆丟掉（left++），看更短的還夠不夠。一直丟到不夠為止，再回到第 1 步。

為什麼可以放心把左邊丟掉？因為金額都是正數。視窗 [left, right] 已經達標時，同一個 left 再往右多拿幾筆只會更長，不可能是「最短」，所以以這個 left 開頭的段落已經找完了，可以丟掉它往右走。這種長度會依條件變大變小的視窗叫可變視窗（variable-size window）。下面用程式跑一遍，每一步印出加入了誰、視窗總和、收縮了幾次：

從表格看得出來，收縮要用 while，不能用 if：right = 3 加入 90 之後，要連續丟掉 70、110 兩筆總和才不夠。用 if 每次只丟一筆，視窗會留著不必要的左邊，答案偏長。另外，找不到任何一段達標時 best 還是 Infinity，回傳前要換成題目規定的值，這題沿用經典題的規定回傳 0。

把這一題的程式抽掉細節，所有可變視窗都長這樣：

let left = 0
for (let right = 0; right < n; right++) {
  把 a[right] 加進視窗
  while (視窗需要收縮) {
    （這一題：在收縮前更新答案）
    把 a[left] 移出視窗
    left++
  }
  （另一種題目：收縮完才更新答案）
}

這題的「需要收縮」是「總和已經 ≥ target」：已經達標，就看能不能更短，所以答案在收縮前更新。後面第三題剛好相反，「需要收縮」是「視窗不合法」，要收縮到合法之後才更新答案。兩種題目的差別就在答案更新的位置。

for 裡面包 while，為什麼還是 O(n)？

這個骨架是一個 for 裡面包一個 while，很容易直覺說「兩層迴圈，O(n²)」，那就跟暴力解一樣慢了。「巢狀就相乘」只在內層每次都從頭跑的時候成立；這裡的 while 不是從頭跑，它接著上一次的 left 繼續往右。

所以要數的不是「迴圈有幾層」，而是「left 和 right 總共走了幾步」。right 從 0 走到 n − 1，正好 n 步。left 只會往右、從不往回，而且不會超過 right，整個程式加起來最多也走 n 步。不管 while 某一圈跑了幾次，全部加起來最多 n 次。總步數 ≤ 2n，是 O(n)。這跟第 7 課的雙指標是同一個道理：兩個索引都只往同一個方向走。下面的程式在不同大小的資料上實際數兩個指標的步數：

💡 實務上：API 限流用的是「時間」視窗
登入 API 常規定「同一個帳號 1 分鐘內最多試 5 次」，這就是可變視窗：右邊進來新請求，左邊用 while 把超過 1 分鐘的紀錄移出，視窗裡的筆數超過上限就擋下，回 HTTP 狀態碼 429 Too Many Requests。跟這課不同的是，左邊界看的是時間戳，不是筆數。紀錄也不能只放在一台伺服器的記憶體：伺服器有好幾台就會各算各的，重啟還會清空。所以通常用框架現成的限流套件，把紀錄放在多台伺服器共用的地方，常見的是 Redis，一個把資料存在記憶體裡、速度很快的資料庫。資深會先問：用帳號還是 IP 計？被擋時要不要回傳還要等幾秒？

第二題的程式正確又快，但它成立的理由「可以放心把左邊丟掉」建立在金額都是正數上。真實的訂單資料不一定如此：有退款，就會出現負數。

訂單有退款時，還能這樣縮嗎？

回頭看第二題為什麼可以放心收縮：金額都是正數時，視窗往右多一筆，總和一定變大；左邊丟一筆，總和一定變小。所以「總和 ≥ target 就縮左邊、不夠就擴右邊」永遠是往對的方向走，不會錯過答案。這種「動一個方向，結果只會往同一個方向變」的性質叫單調性（monotonicity）。可變視窗能成立，全靠它。

如果訂單裡有退款，例如退 5 元記成 −5，單調性就不成立了：多加一筆，總和可能變小；丟掉一筆，總和可能變大。用一個最小的例子看：[1, -5, 6]、target 6。正確答案是只取最後一筆 [6]，長度 1。把第二題的程式原封不動跑一次：

程式回傳 0，說「怎麼連都不夠」。走到 6 時視窗是 [1, -5, 6]，總和 2，不到 6，所以程式判斷「還不夠，繼續擴張」，不收縮。可是這時丟掉左邊的 1 和 −5，總和反而會變大成 6。收縮的判斷依據失效了，答案就被漏掉。這不是改個 while 條件就能修的：問題在於程式沒辦法只看目前的總和，就知道該往哪邊移。

有負數時要換一個不靠單調性的方法：第 11 課的前綴和。它先算出「從第 0 筆到每個位置為止的累計總和」，任何一段的總和都能用兩個累計值相減得到，不管裡面有沒有負數都成立。實務上，報表要算的如果是「淨營收」（扣掉退款），就要記得這一點；面試時看到「連續一段的總和」，也先問一句：值會不會是負的？

單調性不只出現在總和。報表的第三題問的是「有沒有重複的顧客」，條件不是一個數字，但它同樣有單調性，所以還是能用可變視窗。

第三題：條件不是總和，怎麼判斷視窗合不合法？

第三題的資料是 customerIds：依點餐順序排好的顧客編號。店長想知道最長的一段連續訂單有多長，裡面沒有同一位顧客出現兩次。例如 [1, 2, 3, 1, 4, 2, 5] 的答案是 5，那一段是 [3, 1, 4, 2, 5]。

這題的視窗「合法」指的是「裡面沒有重複」。先確認它有上一節講的單調性：一段裡已經有重複，再往兩邊加長也還是有重複；一段裡沒有重複，從裡面拿掉幾筆也還是沒有。所以策略和第二題一樣：right 一直擴張，一出現重複就從左邊收縮到合法為止。差別在於收縮後才更新答案，因為要找的是「最長的合法視窗」，不合法的視窗不能算。

剩下的問題是：每加入一位顧客，怎麼快速知道他是不是已經在視窗裡？在視窗裡一個一個找是 O(k)，整體會變回 O(n²)。第 4 課的 Set 正好回答「有沒有」這種問題，而且是平均 O(1)。用一個 Set 記住視窗裡現在有哪些顧客：

  1. right 往右，準備加入 id = customerIds[right]。
  2. 如果 Set 裡已經有 id，加進來視窗就不合法了：從左邊一筆一筆移出（delete、left++），直到那個舊的 id 被移走。
  3. 加入 id。此時視窗一定合法，更新答案 right − left + 1。

Set 裡的內容要和視窗保持一致：left 往右一格，就要把離開的那位顧客從 Set 刪掉。下面的程式每一步印出移出了誰、目前的視窗和長度：

right = 3 遇到第二個顧客 1 時，要移出索引 0 的 1 視窗才合法；right = 5 遇到第二個顧客 2 時，要移出索引 1 的 2。如果重複的那位在視窗中間，while 會連續移出好幾筆，直到移走舊的那一筆。複雜度的算法和上一節一樣：每個元素最多被加入一次、移出一次，所以是 O(n)。額外空間是 Set 的大小，也就是視窗內不同顧客的數量。

能不能不要一筆一筆移出？用 Map 讓左邊界跳到位

上一節的 while 一直移到「舊的那個 id 被移走」為止，所以 left 最後一定停在舊的 id 上次出現的位置再往右一格。如果記得每位顧客上次出現在哪，就能直接把 left 設過去。這需要的是「顧客編號 → 最後一次出現的索引」的對照，也就是 Map，跟第 5 課 Two Sum 用過的「值 → 索引」是同一種用法。遇到重複時這樣設定 left：

const last = lastSeen.get(id)
if (last !== undefined) left = Math.max(left, last + 1)
lastSeen.set(id, right)

為什麼要包一層 Math.max，不直接寫 left = last + 1？因為 Map 跟 Set 不一樣：Set 版本會把離開視窗的顧客刪掉，Map 卻從來不刪，它記得所有走過的顧客，包括已經在 left 左邊、不在視窗裡的。查到的 last 可能是視窗外的舊位置。看 [1, 2, 2, 1]，下面的程式兩種寫法各跑一次：

走到最後的 1 時，它上次出現在索引 0，last + 1 = 1；可是 left 早就因為兩個 2 跳到 2 了。直接設成 1 等於左邊界往回走，把已經排除的第一個 2 又放回視窗，得到錯誤的 3。Math.max 保證 left 只會往右。這也剛好保住了上一節的 O(n) 論證：那個論證的前提就是 left 從不往回。

Set 版和 Map 版都是 O(n) 時間，報表或面試寫哪一個都可以。空間不太一樣：Set 只存視窗裡的顧客；Map 存所有出現過的顧客，也就是整個陣列裡不同值的數量，最壞都是 O(n)。Set 版比較好解釋，每一步都對得上「視窗裡有誰」；Map 版少走一些步，但要記得 Math.max。題目換成字串時的寫法與空間見課末「補充與查表」。

報表的三個函式到這裡都寫完了。最後要整理的是：下一次拿到一個新題目，怎麼判斷它是不是滑動視窗。

拿到新題目，怎麼判斷能不能用滑動視窗？

回顧報表的三題，你已經寫過兩種視窗：

種類長度怎麼移動典型問題
固定視窗（fixed-size window）固定 k整個往右移一格：右邊進來一個、左邊出去一個連續 k 天的最高平均
可變視窗（variable-size window）依條件變大變小右邊一直擴張；條件不成立時，左邊收縮最短達標的一段、最長不重複的一段

判斷的順序是：先看題目是不是在問「連續的一段」，再看長度固不固定，最後確認有沒有單調性。最後兩列是看起來像、但不能用的情況：

題目特徵做法
連續一段、長度固定 k固定視窗：sum += a[i] − a[i − k]
連續一段、找最長／最短，而且有單調性：擴張只會讓視窗「更容易達標」或「更容易不合法」，不會反過來（全部是正數的總和、不重複）可變視窗：right 擴張、while 收縮
連續一段，但有負數收縮的判斷失效，改用前綴和（第 11 課）
可以跳著挑（子序列）、或是挑任意兩個不是視窗題：挑兩個用雜湊表（第 5 課）或雙指標（第 7 課）；子序列常用動態規劃（第 24 課）

寫完之後，交出去前先過一遍邊界清單：空陣列（答案 0 或 null）、一個元素、k > n、k === n、全部一樣、全部不同、答案是整段。複雜度要能講出來：時間都是 O(n)；空間固定視窗 O(1)，Set 是視窗內不同值的數量，Map 是整個陣列不同值的數量。

補充與查表

子序列不是視窗

連續的一段叫子陣列或子字串。如果可以跳著挑、只要保持原本的先後順序，就叫子序列（subsequence），例如 [80, 70, 120] 的 [80, 120]。子序列不是這課的範圍，第 24 課會用到。題目寫「subsequence」就不是滑動視窗。

比較小數為什麼要用誤差範圍

TypeScript 課第 5 課講過，JavaScript 的數字是二進位浮點數，很多小數沒辦法精確表示，所以檢查小數答案時不要用 ===，要看差距是不是小於一個很小的數。這一課的判分都用 1e-9 的誤差範圍比較平均值：

題目換成字串

第三題的經典版本是字串（LeetCode 3）。做法完全一樣，只是 Set／Map 的鍵變成字元。如果字元只有 26 個英文字母，Set／Map 的大小最多 26，空間可以說是 O(1)。Map 小節的 [1, 2, 2, 1] 就是字串版的 'abba'，這也是 LeetCode 3 最常見的 Math.max 陷阱測資。

練習

三題都有大資料量的計時測試：每個起點都重新算一次的寫法會因為太慢判錯（第 2 課：判分逾時或計時不過就是複雜度不夠）。傳進來的陣列被凍結了，不能 sort、push。

練習 1：寫 bestAverage(cups, k)：cups 是每天的杯數（可能有負數，代表退杯調整），回傳連續 k 天的最高平均（要保留小數）；k < 1 或 k > cups.length 時回傳 null。要 O(n)：測試會跑 n = 50,000、k = 25,000，每個視窗重新加總會太慢。判分容許 10⁻⁹ 的誤差。對應 LeetCode 643. Maximum Average Subarray I。

練習 2：寫 shortestToTarget(totals, target)：totals 是今天依序的訂單金額，全部是正整數；target 是正整數。回傳總額 ≥ target 的最短連續訂單有幾筆；怎麼連都不夠時回傳 0（這題沿用經典題的規定，不是 null）。要 O(n)：測試會跑 4 萬筆、只有整段加起來才夠的資料，每個起點往右加的寫法會太慢。對應 LeetCode 209. Minimum Size Subarray Sum。

練習 3：寫 longestDistinctRun(customerIds)：customerIds 是依點餐順序的顧客編號，回傳最長的一段連續訂單有幾筆，這段裡面沒有同一位顧客出現兩次；空陣列回傳 0。用 Set 或 Map 都可以，用 Map 跳的話記得左邊界不能往回走。要 O(n)：測試會跑「1 到 25,000 依序排兩次」的資料，每個起點往右走到重複為止、或每一步都在視窗裡逐一找重複的寫法都會太慢。對應 LeetCode 3. Longest Substring Without Repeating Characters（這題用編號陣列代替字串）。

練習 4：可變視窗的程式是 for 裡面包一個 while。它的時間複雜度是？

✓ 要數的是指標總共移動幾次：right 走 n 步，left 從來不往回走，整個程式加起來最多也是 n 步，總共 ≤ 2n。a 錯：「巢狀就相乘」只在內層每次都從頭跑時成立，這裡 while 接著上次的 left 繼續。c 錯：while 每次縮多少不一定，沒有「一半」的關係，那是二分搜尋（第 9 課）。

練習 5：訂單金額有退款（負數），例如 [1, -5, 6]。還能用練習 2 的可變視窗找「總額 ≥ target 的最短一段」嗎？

✓ 可變視窗靠「擴張變大、收縮變小」這個單調的性質決定往哪邊移。[1, -5, 6]、target 6 時，視窗總和是 2，程式不會收縮，可是丟掉左邊的 1 和 −5 反而變成 6，答案 [6] 就被漏掉了。a 錯：會回傳 0，正確答案是 1。b 錯：if 只縮一格，連正數的情況都會錯。有負數時改用第 11 課的前綴和。

練習 6：同事寫的 bestAverage 在迴圈裡每一步都算 sum / k，再用 === 跟測試的預期平均比較，偶爾不相等。最好的改法是？

✓ 長度都是 k 時，總和最大的那段平均也最大，所以比總和就好，整數加減沒有誤差；小數的比較一律用誤差範圍（TypeScript 課第 5 課）。b 錯：答案變了，14.5 會變成 14，題目要的是真正的平均。c 錯：== 只是多了型別轉換，兩個數字之間跟 === 一樣，誤差還在。

常見錯誤

  • 每個視窗重新計算：O(n × k)。相鄰兩個視窗只差頭尾，加入進來的、減掉離開的。
  • 視窗個數或長度差一：視窗有 n − k + 1 個，迴圈條件是 start + k <= n；視窗長度是 right − left + 1。拿兩三個元素的例子手算一次就能確認。
  • 最大值初始為 0：全部是負數時答案錯。用第一個視窗的總和，或 -Infinity。
  • k > n 沒處理：讀到不存在的位置，得到 NaN。先判斷，回傳題目規定的值。
  • 平均值截成整數或用 === 比小數：Math.floor 會把 14.5 變成 14；迴圈裡比總和，最後才除，比較小數用誤差範圍。
  • 收縮用 if：一次只縮一格，視窗會留著不必要的左邊。收縮一律用 while，縮到條件不成立為止。
  • 用 Map 跳的時候左邊界往回走：Map 記得視窗外的舊位置，要寫 left = Math.max(left, last + 1)。
  • 有負數還用可變視窗：單調性不成立，改用前綴和。
  • 找不到答案時回傳 Infinity：best 的初始值只是內部用的記號，回傳前換成題目規定的 0 或 null。

小結

  • 視窗是連續的一段，用 left、right 表示，兩端都含，長度 right − left + 1；題目說「連續」「一段」時先想到它。
  • 每段重算慢，是因為相鄰兩段只差頭尾。固定視窗先算第一個視窗，之後 sum += a[i] − a[i − k]，O(n) 時間、O(1) 空間。平均值先比總和，最後再除。
  • 可變視窗：right 一直擴張，while 收縮 left；兩個指標都只往右，總共 O(n)。「最短達標」在收縮前更新答案，「最長合法」在收縮後更新答案。
  • 可變視窗要求單調性：全部是正數才能用總和決定收縮；有退款（負數）改用前綴和。
  • 條件是「有沒有重複」時，Set 守住視窗內有哪些值；Map 記住最後出現的位置，讓 left 用 Math.max 一次跳到位，不往回走。
