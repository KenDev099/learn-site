階段 9：期末 · 第 27 課

期末：模擬面試

前 26 課的每一題，標題都先告訴你這課教什麼技巧：在「滑動視窗」那課，題目當然用滑動視窗。真正的面試不會這樣。想像下週你要參加一場 45 分鐘的程式面試，面試官在共用編輯器上貼了一段情境：「店裡一天的點餐紀錄是飲料代碼的陣列，同一款被點兩次算一組撞單，回傳撞單的組數。」沒有提示技巧、沒有測試，只有一個函式簽章。接下來 45 分鐘，你要自己問清楚題目、選技巧、寫程式、測試，而且全程把想法說出來。寫完之後，面試官還會再丟一題你一眼看不出題型的題目。

很多人技巧都會，卻在這種場合卡住，原因不是不會寫，而是沒練過「不知道題型時從哪裡開始」和「邊寫邊說」。這一課就陪你把這場面試從第一分鐘走到最後一分鐘：先用撞單題走完整個流程，再用第二題練習看不出題型、甚至卡住時怎麼辦，最後用五題不提示技巧的模擬題自己實際走一次。

這課的路線：
  1. 面試官在評什麼、45 分鐘怎麼分：評分表的四塊決定了時間該花在哪裡（開場問題的最小答案）。
  2. 拿到撞單題之後：動手前要問什麼、怎麼用小例子確認題意，接著為什麼先說暴力解、再改成 O(n)。
  3. 寫完怎麼證明它對：空跑、邊界與收尾，把整套流程收成一份面試腳本。
  4. 第二題看不出題型、做到一半卡住：從關鍵字和資料量推出技巧，卡住時照固定的動作走；最後說明這課的五題模擬面試怎麼練。
這課會用到：
  • 第 1 課的解題七步驟：重述、手算、暴力解、找重複的工作、改進、邊界、複雜度。
  • 第 2 課的「從限制推回需要的複雜度」：先看資料量多大，就知道 O(n²) 能不能過、要不要找 O(n) 或 O(n log n)。

面試官在評什麼？為什麼只交程式碼不夠

在動手解撞單題之前，先弄清楚這 45 分鐘是怎麼被評分的，因為它決定了你該把時間花在哪裡。程式面試（coding interview）通常是 45～60 分鐘、一到兩題，在共用的線上編輯器或白板上寫。面試官不是只看最後的程式碼跑不跑得過，他手上有一張評分表，大致分成四塊：

面向面試官看的事只交程式碼時看不到的部分
溝通有沒有先確認題意、講得出自己的方向、聽得懂提示全部。沉默地寫完，這一塊就是空白
解題從暴力解出發、找出重複的工作、選對資料結構你是怎麼想到的、考慮過哪些做法
程式正確、命名清楚、結構乾淨—
驗證主動測試、找到自己的錯、說出複雜度空跑與邊界檢查的過程

看右邊那一欄：四塊裡只有「程式」一塊能從最後的程式碼看出來，其他三塊都發生在你寫的過程中。所以「寫出最佳解」只是其中一部分。一個人寫出正確的暴力解、說清楚為什麼慢、提出改進方向但時間不夠寫完，常常比一個沉默地寫出最佳解、卻答不出複雜度的人分數高，因為前者四塊都有東西可以評，後者只有一塊。

面試官為什麼要這樣評？因為他想知道的是你進團隊之後怎麼工作：會不會先確認需求、遇到問題會不會說、寫完會不會自己驗證。這些在最後的程式碼裡都看不到，只能在過程中觀察。資深職位的面試還會在寫完之後多一段追問（follow-up）：面試官把題目往真實系統推一步，例如「資料大到放不進記憶體怎麼辦？」「資料是一筆一筆進來的呢？」，看你能不能把演算法連到真實系統的取捨。撞單題寫完後，我們會實際回答一次這種追問。

知道了評分表，下一個問題是：45 分鐘這麼短，要怎麼分配，才能讓四塊都有東西可評？

45 分鐘要怎麼分，才讓四塊都有東西可評？

評分表的四塊，各自要在面試的不同時段裡展現：溝通在一開始的確認題意，解題在說出暴力解與改進，程式在寫的那一段，驗證在最後的測試。時間分配就照面試與職涯課第 5 課的那一套：

階段分鐘對到第 1 課的七步驟
釐清與舉例5① 重述 ② 手算
思路與複雜度8③ 暴力解 ④ 找重複 ⑤ 改進；面試官同意方向再寫
寫程式20把改進後的想法寫出來
測試與修正7⑥ 邊界
總結與問答5⑦ 複雜度：說出最終版本

那一課有每一段的示範對話和 60 分鐘的換算。注意前 13 分鐘都還沒開始寫程式，這是正常的。時間是參考值，重點是順序：沒釐清就寫，寫到一半才發現題意理解錯，前面的時間全部白費；沒說暴力解就直接改進，卡住時手上什麼都沒有。照順序走，每一步都替後面省時間。

這五段時間裡還有一件事要一直做：把正在想的事說出來，這叫思路說明（thinking aloud）。它不是表演，而是讓面試官跟得上你的方向：他聽得到你打算怎麼做，走偏時才能及早提醒；你卡住時，他知道卡在哪，才給得出剛好的提示。沉默地想十分鐘，面試官只能等，評分表上的「溝通」一塊也就空著。每一段要說的話可以事先準備成固定的句子，中英對照放在課末的「補充與查表」；接下來走撞單題時，每一段都會示範那一段該說什麼。

流程排好了，面試開始，第一段是「釐清與舉例」：拿到撞單題，動手前到底要問什麼？

拿到撞單題，動手前要問什麼？

面試官貼出的完整題目是：「店裡一天的點餐紀錄是飲料代碼的陣列。如果第 i 筆和第 j 筆（i < j）點了同一款，算一組撞單。回傳撞單的組數。」（對應 LeetCode 1512. Number of Good Pairs）

這段題目看起來清楚，其實留了好幾個空白：陣列可能是空的嗎？最多幾筆？(i, j) 和 (j, i) 算一組還是兩組？面試題常常故意寫得不完整，看你會不會問。開場要問的這些叫釐清問題（clarifying questions）：在動手前確認輸入、輸出和限制。問的目的不是表現謹慎，而是每個答案都可能改變你的寫法，問錯一個，後面寫的就是另一題。

要問哪些？下面這張表整理了常見的問題，以及每一個為什麼會改變寫法（查表用，不用背）。不用每題都問完，挑會改變這題寫法的問：

要問的事為什麼會改變寫法
輸入會不會是空的？空陣列、空字串常常要先處理，否則 arr[0] 是 undefined
找不到時回傳什麼？回傳索引還是值？null、-1、[] 的寫法不同；回傳格式錯就全錯
輸入多大？決定需要的複雜度（第 2 課）：n ≤ 20 可以試遍所有組合，n 到 10⁵ 要 O(n log n) 以下
有沒有重複的值？影響用 Set 還是 Map 計數、相等時算不算
會不會有負數或 0？負數讓滑動視窗的「越加越大」不成立，0 讓除法不能用
輸入已經排序了嗎？排序過就可以用雙指標或二分搜尋
可以修改輸入嗎？原地排序省空間，但呼叫端的資料會被改（TypeScript 課第 2 課的值與參考）

套到撞單題，會改變寫法的是空輸入、輸入大小和「怎樣算一組」。實際的對話像這樣：「陣列可能是空的嗎？」「可以，回傳 0。」「最多幾筆？」「10⁵ 筆。」「(i, j) 和 (j, i) 算同一組，對吧？」「對。」重複值不用問，因為題目本身就是在數重複；排序、負數在這題也不影響寫法，就不必問。

問完之後，用一個自己設計的小例子跟面試官確認題意：「輸入 ['LAT', 'AME', 'LAT', 'LAT']，拿鐵出現在 0、2、3，配對是 (0,2)、(0,3)、(2,3)，答案是 3，對嗎？」這一步花 30 秒，可以擋掉「整題理解錯」這種最貴的錯誤：如果面試官其實想要「有幾款被點了兩次以上」，答案會是 1，你在寫之前就知道了。

這個小例子之後還要拿來空跑，所以設計時讓它有點代表性：不要太短，要包含一個會讓粗心寫法出錯的地方，例如重複的值、答案在最後一格。上面的例子讓拿鐵出現三次，就是為了檢查「三杯一樣時是 3 組，不是 2 組」，而且最後一格也是拿鐵。

💡 實務上：接到需求也是先釐清、再舉例
上班後的「題目」是 PM 開的需求單，例如「咖啡店後台要顯示今天賣最多的飲料」，它一樣寫得不完整：算單一門市還是全部門市？「今天」照哪個時區切？退掉的訂單算不算？同樣杯數時顯示哪一款？跟撞單題一樣，挑會改變寫法的問，再拿一兩筆真實訂單跟 PM 確認「這幾筆的答案是拿鐵，對嗎？」。把確認過的例子寫進需求單或測試，就是驗收條件。資深工程師估工時前一定先問完這些，因為「整題理解錯」在工作上的代價是重做一個功能，不只是一題。

題意確認了，答案是什麼也有了例子，接下來進入「思路與複雜度」：該用什麼做法？

為什麼先說暴力解，再改成 O(n)？

很多人一確認完題意，就想直接寫最佳解。但第 1 課的七步驟在這裡是先說暴力解：不管效率、最直接把答案算出來的做法。先說它有三個理由：它證明你懂題目；它是保底，後面改進卡住時至少交得出一個正確的版本；而且暴力解在「重複做什麼」，通常就是改進的方向。

撞單題的暴力解，你可以這樣說：「兩層迴圈試遍所有 i < j，相同就加一。時間 O(n²)，空間 O(1)。n 到 10⁵ 時是 50 億次比較，太慢。」這句話同時完成了三件事：說出做法、說出複雜度、用剛才問到的 10⁵ 判斷它不夠。說完先跑一次，確認自己對題意的理解。執行後看兩件事：例子的答案是不是 3，以及 n = 2000 時比較了幾次：

n = 2000 就比較了近 200 萬次，大約是 n² / 2；n 變成 10⁵，次數會變成 2500 倍。暴力解的結果對，接下來要找它浪費在哪。

看第 j 筆進來的那一刻：暴力解往回掃前面所有的訂單，數有幾筆跟它一樣。但「前面有幾杯拿鐵」這件事，每一輪都在重新數，上一輪數過的下一輪又數一次，這就是重複的工作。如果用 Map 記住每款到目前出現幾次，往回掃就變成一次查表。第 j 筆是拿鐵、前面已經有 2 杯拿鐵，它就跟那 2 杯各湊成一組，新增 2 組撞單；然後把拿鐵的次數加成 3，留給後面的訂單用。

這就是第 4 課的雜湊表計數，時間 O(n)、空間 O(種類數)，這裡的種類數指陣列裡不同飲料代碼的數量，因為 Map 每種代碼只佔一格。在面試裡，這個改進要先說出來，等面試官點頭，再開始寫。這個「先說再寫」讓面試官有機會在你寫之前糾正方向，也讓評分表上的「解題」一塊有東西可評：他聽到了你是怎麼從暴力解看出重複的工作、再選出資料結構。

方向確定之後就是寫程式的 20 分鐘。程式寫出來了，但面試的編輯器常常不能執行，就算能執行也沒有測試。你要怎麼向面試官證明它是對的？

寫完怎麼證明它對？空跑、邊界與收尾

證明的方法叫空跑（dry run）：寫完後拿開場那個小例子逐行模擬程式，把每個變數在每一圈的值念出來，相當於口頭的手算。它的用處是抓出「看起來對、跑起來錯」的地方，例如忘了初始化、先加後查的順序寫反。開場設計的例子在這裡派上用場。下面的程式印出空跑時你應該念出的表格，執行後逐列看「前面已有」和「累計」怎麼變：

j = 3 那一列是關鍵：前面已經有 2 杯拿鐵，所以新增 2 組，累計從 1 變 3。如果你寫成先 seen.set 再 seen.get，這一列會變成新增 3，空跑時一念就會發現。注意「新增」和「前面已有」兩欄相同，因為新的一筆正好跟前面每一筆同款的各湊一組。

在面試裡寫程式最容易出事的是差一（off-by-one）：迴圈多跑或少跑一圈、二分的邊界、視窗的長度。寫到索引時把邊界的理由說出來，例如暴力解的內層迴圈：「j 從 i + 1 開始，所以不會拿自己配自己，也不會把 (i, j) 和 (j, i) 算成兩組；條件是 j < orders.length，最後一格是 j = 3。」空跑時特別看最後一格：如果寫成 <=，j 會跑到 4，orders[4] 是 undefined，程式不會報錯，只是默默多比一次。

開場的例子是一般情況，還要檢查邊界：最容易被忽略的極端輸入。撞單題的收尾可以這樣說：「空陣列時迴圈不跑，回傳 0；全部不同時每次 before 都是 0；全部一樣時答案是 n(n − 1) / 2，n = 10⁵ 是 49 億多，還在 Number.MAX_SAFE_INTEGER 以內。時間 O(n)，空間 O(種類數)。」最後這句「數字會不會太大」就是資深的人會主動補的檢查：答案的大小跟輸入的大小是兩件事，n 只有 10⁵，答案卻可能到 10⁹ 以上。

這時面試官可能接著追問：「如果點餐紀錄是一筆一筆即時進來的呢？」這就是第一節說的追問。這個 Map 的版本本來就是一筆一筆處理：每進來一筆，查一次、加一次，就能更新目前的撞單組數，不需要先拿到整個陣列。暴力解就做不到，每來一筆都要往回掃全部。能這樣把寫好的程式連到「資料怎麼進來」，就是追問想看的東西。

到這裡，撞單題從釐清、舉例、暴力解、改進、寫程式、空跑到收尾都走完了。整場面試你說出口的內容，可以先寫成註解，再寫程式。這門課的模擬題建議都照這個面試腳本開頭：

// 釐清：空輸入回傳？回傳格式？n 多大？有重複／負數嗎？可以改輸入嗎？
// 例子：輸入 …，答案 …（含一個邊界例子）
// 暴力解：…，時間 O(…)，空間 O(…)
// 重複的工作：…
// 改進：用 …，時間 O(…)，空間 O(…)
// 要測的邊界：空的、一個、全部一樣、答案在最後…

但撞單題有一個地方很順利：題目在數重複，你幾乎一眼就想到 Map。第二題就沒那麼好認了。

第二題看不出題型：怎麼選技巧？

面試官接著出第二題：「點餐紀錄是飲料代碼的陣列 orders，給一個整數 k，找出最多包含 k 種不同飲料的最長連續訂單，回傳它的長度。」釐清和舉例照前面的方法做，但到了「思路」這一段，你可能想不到該用什麼。這時不要從記憶裡翻「這題我做過嗎」，因為題目會換情境、換名字。改看兩個線索：題目在問什麼（關鍵字），以及資料量限制（需要多快）。

第一個線索是關鍵字。每種技巧都有它擅長的題目樣子，例如雜湊表擅長「有沒有看過」，因為查表是 O(1)；滑動視窗擅長「連續的一段」，因為一段的左右兩端都只會往右移。下面這張表把整門課整理在一起，看到新題目時先對照（查表用，不用背）：

回頭看撞單題，「計數」對到第一列，所以想到 Map；第二題的「最長連續訂單」對到「連續的一段、最長」那一列。但光看關鍵字常常有兩三個候選，例如「連續的一段」同時出現在滑動視窗和前綴和兩列。這時第二個線索幫你縮小範圍：用第 2 課的粗估（每秒大約 10⁷～10⁸ 個簡單步驟），把限制換成需要的複雜度：

≤ 10～20O(2ⁿ)、O(n!) 也可以回溯、試遍所有子集合
≤ 500O(n³)三層迴圈、區間 DP
≤ 10⁴O(n²)雙迴圈、二維 DP
≤ 10⁵～10⁶O(n log n) 或 O(n)排序、heap、雜湊表、雙指標、視窗、前綴和
更大，或值的範圍到 10⁹O(log n) 或對值域二分二分搜尋、數學

兩張表要一起看。例如「連續的一段」加上「n ≤ 10⁵」，指向 O(n) 的滑動視窗或前綴和；如果值可能是負數，視窗的「加進來就變大」不成立，改用前綴和配 Map（第 11 課）。第二題問的是種類數，不是總和，又要「最長」，對照表給的第一個猜測是滑動視窗。

對照表只給你第一個猜測，不保證它對。接下來一定要用小例子手算確認：拿你設計的例子，想像左右兩端怎麼移，看「最多 k 種」這個條件會不會隨視窗變長而單調變化。手算通得過，再跟面試官說出方向；手算時發現條件不單調，就換表上的下一個候選。

「單調」在這裡的意思是：視窗往右多收一杯，種類數只會不變或增加，不會減少。拿 ['LAT', 'AME', 'LAT', 'MOC']、k = 2 手算：前三杯是拿鐵和美式兩種，合法，長度 3；右端再收進摩卡，變成三種，超過 k。這時再往右延伸，視窗只會多收東西，種類數不可能變回 2，所以以目前的左端為起點，已經不會有更長的合法視窗，唯一的辦法是把左端往右移。左端丟掉第 0 杯的拿鐵，視窗裡還有一杯拿鐵，仍是三種；再丟掉第 1 杯的美式，美式沒了，回到兩種，合法。

這個性質正是滑動視窗成立的理由：超過條件時只需要移動左端，不必把右端退回去重試，左右兩端都只往右走，各走最多 n 步，整體 O(n)。如果條件不單調，移動左端就不保證會回到合法狀態，視窗會漏掉答案。例如找「總和不超過 2 的最長連續一段」，陣列是 [3, -2, 1]：右端收進 3 時總和已經超過 2，視窗只好把左端移過 3；可是整個陣列的總和 3 − 2 + 1 = 2 其實合法、長度 3，因為後面的負數會把總和拉回來。這時就換表上的下一個候選，例如前綴和配 Map（第 11 課）。

💡 實務上：工作中的 O(n²) 常藏在 map 裡的 find
前端最常見的慢，不是兩層 for，而是 orders.map(o => products.find(p => p.id === o.productId))：每筆訂單都把商品陣列掃一遍。這跟撞單題的暴力解是同一個形狀，只是內層迴圈藏在 find 裡。資料只有幾十筆時完全沒事，等後台的訂單列表長到幾千筆、商品也上千，頁面就開始卡；改法就是第 4 課的先建一個 Map 再查表。反過來，確定資料量很小（例如設定選單的十幾個選項）就不必為了複雜度改寫，可讀性優先。資深的人 code review 時會先問「這個陣列最多會有多大？」，再決定要不要在意複雜度，跟面試開場問輸入大小是同一件事；很多計數、分組的需求，其實交給資料庫的 GROUP BY（第 6 課）更合適。

方向選出來了，但寫第二題時，你可能還是會卡在某個細節上。卡住的那幾分鐘，該做什麼？

做到一半卡住了，該做什麼？

假設你決定用滑動視窗做第二題，寫到一半卡在「右端加進來一杯之後，怎麼知道視窗裡現在有幾種，而不是每次重新數一遍」。每個人都會卡住，差別是卡住之後做什麼。最糟的反應是靜靜地盯著螢幕：面試官不知道你卡在哪，給不了提示，時間一分一分過去，評分表上什麼都沒留下。所以要準備一套固定的動作，卡住時照著做：

  1. 說出來：「我現在卡在怎麼避免重算視窗裡的種類數。」面試官聽得到你卡在哪，才能給剛好的提示。
  2. 回到手算：換一個更小的例子（3～4 個元素）用手算一遍，注意你的手在「重複做什麼」。很多改進就是把手算時你自然記在腦中的東西，改成存在變數或 Map 裡。撞單題的 Map 就是這樣來的：手算時你會記得「前面已經有 2 杯拿鐵」，那就把它存起來。
  3. 先交出暴力解：還有 15 分鐘就先把暴力解寫出來、測過。正確的 O(n²) 遠比寫一半的 O(n) 有價值，因為寫一半的程式跑不起來，「程式」和「驗證」兩塊都是零；而且暴力解寫完，常常就看出重複的地方了。
  4. 對照技巧表：把題目的關鍵字和限制再看一次，從表上挑兩個候選，各花一分鐘想「用它的話第一步是什麼」。
  5. 接受提示：面試官的提示是幫助，不是扣分。聽到提示後複述一次、說出你打算怎麼用，再動手；假裝沒聽到、堅持原本的方向才會扣分，因為評分表的「溝通」一塊看的就是你聽不聽得懂提示。

套回第二題，看動作 2 怎麼解開剛才的卡點。拿 ['LAT', 'AME', 'LAT', 'MOC']、k = 2 手算，你會發現自己不是每次都重新數，而是腦中一直記著「拿鐵 2 杯、美式 1 杯」：收進一杯就把那一款加一，丟掉一杯就減一。把這份記憶存起來，就是一個 Map：代碼 → 視窗內的杯數，map.size 就是視窗裡的種類數，不用重數。右端收進一杯後，如果 size 變成 k + 1，就移動左端、把丟掉那杯的杯數減一，杯數歸 0 時要 delete 那一款，否則它還佔著一格，size 不會變小。照這個規則，Map 只會在右端剛收進一杯、還沒縮左端的那一刻短暫放到 k + 1 種，其餘時間不超過 k 種，所以空間是 O(k)。這也是你寫程式時可以說出口的 invariant（迴圈每一圈都維持成立的條件）：視窗裡的種類數不超過 k。

這五個動作的順序有道理：前兩個讓你自己脫困，第三個確保手上有東西可交，後兩個借助外部線索。它們的共同點是讓卡住的過程也被看見，這樣即使最後沒寫出最佳解，評分表的四塊仍然都有東西。

💡 實務上：上班卡住也照這套做
修客服回報的 bug 或做新功能卡住時，最常見的錯是一個人悶著查一整天。先替自己訂一個時間上限，到了就照上面的順序：用一句話寫下卡在哪、縮小到最小的重現例子、先交一個能動的簡單版本。問同事時附上「我試過什麼、看到什麼結果、我猜是哪裡」，對方幾分鐘就能幫上忙，這跟面試時說出卡點讓面試官給提示是同一件事。別人給的建議也照面試的方式接：先複述一次確認理解，再動手。

整場面試的流程到這裡都走過了一次。第二題你在練習 1 會用面試腳本規劃它；其餘的要靠自己實際計時、走幾題才會熟。

這課的模擬面試怎麼練？

練習 1 先練面試腳本：只規劃、不寫解法，題目就是上一節的第二題。練習 2～6 是五題模擬面試，題目只給情境和函式簽章，不寫用哪個技巧，跟真正的面試一樣：

  • 計時：每題標了建議時間（20～25 分鐘）。頁面不會幫你計時，用手機的計時器，時間到了先停下來，記下卡在哪一步，再繼續做完。
  • 先寫腳本：在編輯器上方用註解寫出面試腳本（釐清、例子、暴力解、改進、邊界），再寫程式。可以出聲說，或把要說的話打在註解裡。
  • 先求對再求快：寫完先用 console.log 跑自己的例子，再按「檢查答案」。測試會比對大量隨機案例，需要更好複雜度的題目還會用大資料量計時；判分逾時（3 秒）或計時不過，代表複雜度不夠。
  • 做完之後：每題最後標了對應的 LeetCode 題號，隔幾天到 leetcode.com 用它的簽章重寫一次，看自己能不能在時間內做完。

補充與查表

每一段要說的話（查表用，不用背）。外商面試用英文，所以附上英文說法。「寫程式」那一列的 invariant 是不變條件：迴圈每一圈開始和結束時都維持成立的事，說出它，面試官就知道你的迴圈在守什麼。

階段中文英文
釐清「我先確認一下，輸入可能是空陣列嗎？找不到的時候要回傳什麼？」Before I start, can the input be empty? What should I return if there is no answer?
舉例「我用這個小例子確認題意：輸入是…，答案應該是…，對嗎？」Let me check with a small example: for this input I expect …, is that right?
暴力解「最直接的做法是試遍所有的…，時間 O(n²)。我先說它，再想怎麼改進。」The brute force is to try every …, which is O(n²). Let me see if I can do better.
改進「暴力解重複在做…，如果用 Map 記住…，就能變成 O(n)。」The brute force keeps recomputing …; if I store … in a hash map, it becomes O(n).
寫程式「這個迴圈在維持一件事：視窗裡的種類數不超過 k。」This loop keeps the invariant that the window has at most k kinds.
測試「我用剛才的例子逐行跑一次，再檢查空陣列和全部一樣的情況。」Let me trace through the example, then check the empty and all-same cases.
收尾「時間 O(n)，空間 O(k)，因為 Map 最多放 k + 1 種。」It's O(n) time and O(k) space, since the map holds at most k + 1 keys.

練習

練習 1 是面試腳本的檢核題；練習 2～6 是模擬題，範圍是整門課；練習 7～9 是選擇題。

練習 1：面試腳本。面試官出題：「點餐紀錄是飲料代碼的陣列 orders，給一個整數 k，找出最多包含 k 種不同飲料的最長連續訂單，回傳它的長度。」這題先不寫解法，填好 plan：clarify 至少選 4 個要問的問題（一定要問空輸入和回傳格式）；examples 至少 3 組，expected 要自己手算正確，其中一組是空陣列、一組 k = 0（假設面試官回答：空陣列或 k = 0 都回傳 0）；bruteForce 寫出想法與複雜度；optimized 寫出要用的技巧與複雜度（空間用 k 表示）；tests 至少選 4 個要測的邊界，包含空輸入與全部一樣。（題目近似 LeetCode 340. Longest Substring with At Most K Distinct Characters，付費題；k = 2 的版本是 904. Fruit Into Baskets）

練習 2：模擬題 A（建議 20 分鐘）。做價格試算時，店長想知道「拿掉某一項之後，其他項相乘是多少」。寫 productOfOthers(prices)：回傳一個新陣列，第 i 格是「除了 prices[i] 以外所有元素的乘積」。值是整數，可能有 0 和負數；只有一個元素時回傳 [1]，空陣列回傳 []。不能用除法（乘上 x ** -1 也算；測試會檢查這個函式裡沒有 /，註解不算，把除法搬到別的函式也違反題目要求），不能修改 prices。測試會用 20,000 個元素計時。（對應 LeetCode 238. Product of Array Except Self）

練習 3：模擬題 B（建議 25 分鐘）。log 是一整天的品項代碼串，每個品項是一個小寫英文字母（例如 'a' 是美式、'l' 是拿鐵）。一張外送單 ticket 也是這樣的字串。寫 findTicketGroups(log, ticket)：回傳所有起點 i（索引從 0 開始），使得 log 從 i 開始、長度等於 ticket 的那一段，品項與數量都跟 ticket 一樣（順序可以不同）；起點由小到大，沒有就回傳 []。ticket 至少一個字元，log 可能是空字串。測試會用 log 長度 50,000、ticket 長度 5,000 計時。（對應 LeetCode 438. Find All Anagrams in a String）

練習 4：模擬題 C（建議 25 分鐘）。orders[i] 是第 i 份訂單要沖幾杯（正整數）。咖啡師設定一個速度 s（每小時沖 s 杯），每小時只處理一份訂單：一份 7 杯的訂單、s = 3 要 3 小時（3 + 3 + 1，最後一小時沒用完也不能接別的單）。寫 slowestBrewSpeed(orders, hours)：回傳能在 hours 小時內做完全部訂單的最小整數 s。保證 hours 不小於訂單數，所以一定做得完。測試的杯數最大到 10⁹、訂單 50,000 份。（對應 LeetCode 875. Koko Eating Bananas）

練習 5：模擬題 D（建議 25 分鐘）。菜單黑板是字母網格 board（每列是一個等長的字串）。寫 findOnBoard(board, word)：判斷 word 能不能從某一格出發，每次往上下左右相鄰的格子走一步，依序拼出來；同一格在一次拼字裡不能用兩次。word 是空字串時回傳 true。不能修改 board。（對應 LeetCode 79. Word Search）

練習 6：模擬題 E（建議 25 分鐘）。收銀機把一張單的點餐代碼接成一整串 code（沒有分隔符號），menu 是所有合法的品項代碼（每個至少一個字元，可以重複使用）。寫 canSplitCode(code, menu)：判斷 code 能不能完整切成一個個 menu 裡的代碼；空字串回傳 true。測試會用 1,001 個字元的代碼計時。（對應 LeetCode 139. Word Break）

練習 7：拿到題目後，你很快想到做法。哪一種開場最好？

✓ c：面試官評的是思考過程，溝通與驗證佔了評分表的一大塊。先確認題意能擋掉「整題理解錯」，說出方向後面試官可以及早提醒，寫的時候邊說，卡住時對方才知道怎麼幫。a 錯在題意理解錯時整段白寫，而且沉默的 15 分鐘裡面試官沒有東西可以評。b 錯在長時間沉默：說出還不完整的想法不會扣分，說的過程本身就是在展示能力。

練習 8：還剩 15 分鐘，你只想得到 O(n²) 的暴力解，O(n) 的做法還有一半沒想通。怎麼做？

✓ a：正確的暴力解代表你懂題目、寫得出可執行的程式，再加上說得出瓶頸在哪、可以怎麼改，是有分數的結果；寫完之後也常常就看出重複的工作。b 錯在寫一半的最佳解跑不起來，正確性、測試兩塊都是零。c 錯在放棄了展示過程的機會；卡住時說出卡在哪，面試官通常會給提示。

練習 9：程式寫完了，看起來沒問題。接下來呢？

✓ b：空跑時把變數的值念出來，最容易抓到差一和漏掉的初始化；主動找到並修正自己的錯，在評分表上是加分，被面試官找到則是扣分。a 錯在把驗證交給別人，評分表的「驗證」一塊就空了。c 錯在測試應該由你設計：面試官想看你會不會自己想到邊界情況，不是看你會不會等資料。

常見錯誤

  • 沒問清楚就開始寫：寫到一半才發現要回傳索引而不是值、空陣列要回傳 null。開場先問回傳格式、空輸入、重複值、輸入大小，再用小例子確認。
  • 跳過暴力解：直接衝最佳解，卡住時什麼都交不出來。先說出暴力解與複雜度；時間緊就先寫出來。
  • 沉默：面試官不知道你的方向，也沒辦法在你走錯時提醒。卡住的時候更要說出卡在哪裡。
  • 寫完不測試：差一的錯誤幾乎都是空跑時抓到的。用開場的例子逐行跑，再看空的、一個、全部一樣、答案在最後一格。
  • 只背題目：題目會換情境、換名字，這課的五題就是例子。練的是七步驟和「從題目特徵與限制選技巧」的判斷，做完一題要能說出為什麼是這個技巧。
  • 忽略限制：沒看 n 和值的範圍，就不知道暴力解會不會過，也會漏掉「答案到 10⁹，不能一個一個試」這種線索。

小結

  • 程式面試評的是溝通、解題、程式、驗證四塊；只交出程式碼，另外三塊都看不到，所以整場都要把想法說出來。
  • 45 分鐘照面試與職涯課第 5 課的分配：釐清與舉例 5、思路與複雜度 8、寫程式 20、測試與修正 7、總結與問答 5；前 13 分鐘還沒寫程式是正常的。
  • 開場問會改變寫法的問題（空輸入、回傳格式、輸入大小、重複、負數、排序、能不能改輸入），再用一個有代表性的小例子確認題意，撞單題的 ['LAT', 'AME', 'LAT', 'LAT'] 就是這樣設計的。
  • 先說暴力解和它的複雜度，找出它重複的工作，說出改進方向、面試官同意再寫。
  • 寫完要空跑、檢查邊界（包括答案會不會太大）、說出時間與空間複雜度；追問時把程式連到資料怎麼進來。
  • 看不出題型時看兩個線索：題目的關鍵字（配對、連續的一段、最少步數、所有方案、最多最少…）和資料量限制。對照表給第一個猜測，手算確認。
  • 卡住時：說出卡在哪、回到更小的例子手算、先交出正確的暴力解、對照技巧表、接受提示。

階段檢核：面試會問的觀念

這是整門課的總檢核：8 題課文沒出過的新題目，每題只問該用哪個做法，以及為什麼不是看起來也像的那個。先看題目的樣子和資料量，在心裡回答，再選。

練習 10：會員打卡紀錄是 10⁵ 筆會員編號（沒有排序）。找出「第二次出現得最早」的編號，例如 [5, 8, 8, 5] 要回傳 8。怎麼做？

✓ c：「有沒有看過」就是 Set，第一次撞到看過的編號，它的第二次出現就是最早的，O(n)。最多人選 b：Map 的插入順序是「第一次出現」的順序，[5, 8, 8, 5] 會回傳 5。a 排序後原本的順序沒了；d 結果對，但約 5 × 10⁹ 次比較，太慢。（第 4 課）

練習 11：10⁵ 杯飲料排成一列，每杯的點數是 1～100 的正整數。找總點數不超過 budget 的最長連續一段，怎麼做？

✓ a：點數都是正的，視窗變長總和一定變大，所以超過就縮左端是安全的；每杯最多進出一次，O(n)。最多人選 b：Map 只找得到總和「剛好等於」budget 的段，題目要的是不超過。c 結果對，但約 5 × 10⁹ 次；d 排序後就不是連續的一段了。（第 10、11 課）

練習 12：50,000 份訂單要照原本順序分給 d 天配送，每天送連續的幾份，每份重 1～10,000。最重那天的重量最小可以是多少？

✓ d：上限 x 送得完，比 x 大的也一定送得完，答案有分界，就能對答案二分；範圍是最重一份到總重，每次檢查 O(n)，共 O(n log 總重)。最多人選 a：每份不能拆、又要連續，平均不一定分得出來，[4, 4, 4] 分 2 天，平均是 6，答案是 8。b 結果對，但總重可到 5 × 10⁸，一個一個試太慢；c 打亂了順序。（第 9 課）

練習 13：收銀紀錄是 10⁵ 個字元的品項代碼串，相鄰兩個相同代表「點了又取消」，要一起刪掉；刪完之後新變成相鄰的相同代碼也要繼續刪，例如 abbaca 最後剩 ca。怎麼做？

✓ b：刪掉一對之後，下一個字元要跟「目前留下來的最後一個」比，那就是堆疊頂端；每個字元最多進出一次，O(n)。最多人選 a：只跟原字串的前一個比，abba 刪掉 bb 後兩個 a 變相鄰，它看不到。c 結果對，但 abc…cba 這種一層包一層的輸入每輪只刪一對，要 O(n²)。（第 12 課）

練習 14：菜單上有 5,000 個 4 個字母的配方代碼。從 cold 改到 warm，每次只能改一個字母，而且每一步都要是菜單上的代碼，最少改幾次？

✓ c：每一步代價一樣，BFS 第一次走到某個代碼用的就是最少步數，每個代碼只進佇列一次。最多人選 a：DFS 只保證走得到，第一條路可能繞了遠路。b 可能走進死路或不是最短；d 結果對，但路線數會隨代碼數指數成長。（第 17、20 課）

練習 15：10⁵ 筆訂單一筆一筆進來，從第 100 筆起，每進來一筆就要回報「目前金額第 100 高」是多少。怎麼做？

✓ a：要留下最大的 100 個，該淘汰的是其中最小的，所以用 min-heap，堆頂正好是第 100 高；每筆 O(log 100)。最多人選 b：max-heap 換掉的是留下來的最大值，最後留下的是最小的 100 個。c 結果對，但 10⁵ 次排序太慢；d 被換掉的值不一定還是第 100 高。（第 19 課）

練習 16：一串 50 位、沒有 0 的數字代碼，每 1 位或 2 位對應一個品項（1～26 都有），例如 123 可以讀成 1-2-3、12-3、1-23。這串有幾種讀法？

✓ b：問「有幾種」，而且前 i 位的讀法數會被後面反覆用到，是 DP；看最後一段是 1 位還是 2 位，dp[0] = 1，O(n)。最多人選 a：50 個 1 的讀法超過 10¹⁰ 種，列不完；回溯留給要列出所有方案、n 又很小的題目。c 錯在相鄰的兩組會搶同一位數字，111 有 3 種讀法，不是 4。（第 23 課）

練習 17：面試題是「每天的盈虧可能是負的，找總和剛好等於 k 的最長連續天數，n ≤ 10⁵」。你寫了滑動視窗，面試官問：「有負數時，你的視窗還對嗎？」怎麼接？

✓ d：面試官的問題通常就是提示，先用小例子驗證、說出原因再改方向，是評分表上的加分。有負數時，加進來的一天可能讓總和變小，「超過就縮左端」會把答案縮掉；改成找 prefix[j] − prefix[i] = k，Map 記每個前綴和最早出現的位置，O(n)。最多人選 a：負數影響的是正確性，不是速度。（第 10、11、27 課）

這個階段的重點整理成一頁圖解。

接下來可以學什麼：這門課涵蓋了面試最常見的題型。之後每週到 LeetCode 依各課標出的題號做 3～5 題，先回頭重做這門課錯最多的那一課；要再往上，可以學 Dijkstra 最短路徑（邊有權重的 BFS）、聯集-尋找（union-find，判斷兩個點是否連通）、字典樹（trie，前綴查詢）與區間 DP。要把演算法連到真實系統，可以接著看 PostgreSQL 課第 20 課的索引：資料庫的 B-tree 索引讓資料保持排序，查詢時一層一層縮小範圍，跟第 9 課的二分搜尋是同一個想法。
