階段 4：線性結構 · 第 12 課

堆疊與佇列

咖啡店後台要上線一個「點單工作台」。店員在畫面上幫顧客組一筆訂單：加入拿鐵、加入可頌、把拿鐵改成去冰；按錯了就按「復原」。訂單送出前，系統要先檢查備註裡的括號，像 (拿鐵[去冰]){加購 可頌}，括號寫錯就沒辦法解析。送出之後，訂單進入櫃檯的叫號名單，依先後叫號出餐。

這三個功能背後是同一個問題：一堆東西放進去之後，下一個該拿哪一個？復原要拿的是最後做的那一步，叫號要叫的是最早來的那位。這課把工作台需要的兩種結構，堆疊和佇列，從規則一路寫到可以交給同事用的 class，每個操作都說得出複雜度和理由。它們也是之後樹與圖的走訪（第 16、17、20 課）、單調堆疊（第 25 課）的基礎。

這課的路線：
  1. 復原和叫號為什麼要用兩種不同的結構，以及復原用 JavaScript 陣列怎麼寫、空的時候 pop 會發生什麼。
  2. 櫃檯叫號：佇列為什麼不能用 shift，資料一多會慢多少；改用 head 索引之後，叫過的人一直留在陣列裡怎麼辦。
  3. 送出訂單前檢查備註括號：為什麼只數數量不夠，堆疊怎麼一次抓出三種錯誤。
  4. 面試的兩個變形：只准用堆疊做出叫號佇列（考攤銷），以及訂單編輯器隨時答出最便宜的品項（考用空間換時間）。
  5. 交出去之前：空的時候回傳什麼、重複的值、交錯操作，以及整課的複雜度表。
這課會用到：
  • 第 2 課的攤銷 O(1)：陣列 push 偶爾要整個搬家，但分攤到每一次還是常數時間；shift 則每次都要搬動，是 O(n)。
  • TypeScript 課第 23 課的 class 與 private：把資料和方法包在一起，private 欄位外面讀不到也改不了。
  • TypeScript 課第 19 課的泛型：class Stack<T> 的 T 是使用時才決定的型別，同一個 class 可以裝數字也可以裝字串。

復原和叫號：為什麼要用兩種不同的結構？

先看工作台的兩個功能各自要拿哪一個。店員依序做了三步：加入拿鐵 → 加入可頌 → 拿鐵改成去冰。按一次復原，撤銷的應該是「拿鐵改成去冰」；再按一次，撤銷「加入可頌」。順序一定是從最後一步往回退，因為後面的步驟建立在前面的步驟上：「改成去冰」改的是前面加進去的那杯拿鐵，如果先撤銷「加入拿鐵」，「改成去冰」就變成在改一杯不存在的飲料。

叫號剛好相反。王小明、陳美華、林志豪依序點單，櫃檯要先叫王小明，因為他等最久；先叫最後來的林志豪，前面兩位會一直等下去。

這兩種「拿東西的順序」各有一個名字。

堆疊（stack）規定只能從同一端放進去、也從同一端拿出來，這一端叫頂端（top）。因為只能從頂端拿，最後放進去的一定最先被拿走，這個性質叫後進先出（last in, first out，簡稱 LIFO）。櫃檯旁疊起來的紙杯就是堆疊：新的杯子放在最上面，拿也只能從最上面拿。復原紀錄是堆疊：每做一步就放到頂端，復原時從頂端拿走。

佇列（queue）規定從一端放進去、從另一端拿出來。放進去的那一端叫尾端，拿出來的那一端叫前端。先排進來的人一路往前移，最先到前端，所以最早放進去的最先被拿走，這個性質叫先進先出（first in, first out，簡稱 FIFO）。排隊點餐就是佇列：新來的排在隊伍尾端，叫號從最前面叫。

兩者的操作都有固定的名字，面試和技術文件都直接這樣講，這課之後也只用這些名字：

放進去push：放到頂端enqueue：放到尾端
拿出來pop：拿走頂端dequeue：拿走前端
看一眼不拿走peek（或 top）：看頂端peek（或 front）：看前端

程式裡的例子函式的呼叫堆疊（第 15 課）、瀏覽器的上一頁事件迴圈的工作佇列（TypeScript 課第 7 課）、BFS（第 17 課）

堆疊和佇列不是新的儲存方式，底下通常還是陣列。它們是限制：只准從特定一端拿。為什麼要自己綁手綁腳？因為一般陣列什麼都能做，可以讀第 0 個、可以從中間 splice，復原紀錄如果只是一個陣列，某位同事寫了 history[0] 想撤銷，撤銷的就是最早的那一步，畫面不會報錯，只是結果錯了。規定「只能從頂端拿」之後，任何人看到堆疊，都知道拿到的一定是最後放的，程式比較好推理，也比較難誤用。

知道兩者的規則之後，也就聽得出題目在暗示哪一種：出現「最近的」「配對」「撤銷」「巢狀」，通常是堆疊；出現「依序」「先來的先處理」「一層一層」，通常是佇列。

規則知道了，接著用 JavaScript 寫出來。先寫復原，因為 JavaScript 的陣列已經內建了堆疊需要的操作。

訂單編輯器的復原：JavaScript 的堆疊怎麼寫？

JavaScript 沒有內建的 Stack 類別，直接用陣列：陣列的尾端當頂端，push 放進去、pop 拿出來。為什麼用尾端而不是開頭？第 3 課講過，陣列的元素一格一格連續排好，用索引找位置；在尾端加一格或拿掉一格，其他元素的索引都不變，不用搬動，所以是 O(1)。push 偶爾遇到空間不夠要整個搬家，分攤下來還是攤銷 O(1)。

復原拿走的是「拿鐵 改成去冰」，再復原是「加入 可頌」，跟上一節推出來的順序一樣。看頂端但不拿走，用 arr[arr.length - 1] 或 ES2022 的 arr.at(-1)，負數索引從尾端往回數。兩種寫法在執行時結果一樣，差別在 TypeScript 的型別：at(-1) 的型別是 T | undefined，會提醒你處理空的情況；arr[arr.length - 1] 的型別只是 T，空陣列時一樣拿到 undefined，但型別不會提醒。

最後兩行要特別看：空的時候 pop 不會報錯，只回傳 undefined。這比報錯更危險。假設工作台把每個品項的價格也存在堆疊裡，復原時 pop 出價格、從總金額扣掉；堆疊已經空了還 pop，拿到 undefined，總金額變成 NaN。程式不會停下來，錯誤要等到畫面顯示「NaN 元」、或某個比較永遠不成立時才被發現，那時已經離真正出錯的那一行很遠了。所以每次 pop 之前先想：這時候可能是空的嗎？空的時候該怎麼處理？

工作上要給同事用時，常把陣列包成一個 class，用 private 把陣列藏起來，只開放 push、pop、peek。這樣「只能從頂端拿」就寫死在程式裡，外面沒辦法誤用 arr[0] 或 splice。下面的紙杯堆疊依序放入 240、360、480 毫升的杯子，執行後看拿出來的順序是不是從 480 開始，以及空了之後的 pop 回傳什麼：

💡 實務上：復原功能就是兩個堆疊
點單工作台、文字編輯器、後台表單、繪圖工具的「復原／重做」，通常是一個 undo 堆疊加一個 redo 堆疊：復原時從 undo pop、push 到 redo；使用者做了新的動作，就把 redo 清空，因為那條「未來」已經不存在。堆疊裡存什麼要先決定：存整份狀態的快照最簡單，但資料大時很吃記憶體；存「做了什麼、怎麼反做」比較省，但每種操作都要寫反向邏輯。紀錄通常會設上限，太舊的直接丟掉。資深工程師會先問：哪些動作算一步（打一個字還是一整段）？儲存到伺服器之後還能不能復原？

堆疊只動陣列的尾端，所以每個操作都是 O(1)。但叫號佇列要從前端拿，陣列的前端就沒有這麼便宜了。

櫃檯叫號：佇列為什麼不能用 shift？

叫號最直覺的寫法是 push 排到尾端、shift 從前端拿走。小資料沒問題，問題出在 shift 拿走的是索引 0。上一節說過陣列靠連續的索引找位置：王小明在索引 0、陳美華在 1、林志豪在 2；王小明被拿走之後，陳美華要變成索引 0、林志豪要變成 1，後面每一位都得往前挪一格。第 2 課講過，shift 依規格就是把剩下的元素逐一往前搬，排了 n 個人就搬 n − 1 次，是 O(n)。n 個人排隊、一個一個叫完，總共搬 (n − 1) + (n − 2) + … ≈ n² / 2 次，是 O(n²)。尖峰時段排隊的人越多，每叫一號就越慢。

改法是不要真的把人移走。用一個索引 head 記住「下一個要叫的是第幾個」，叫完就 head++。叫過的人還留在陣列裡，但我們不再看他們，所以其他人的索引都不用變。下面兩種寫法各叫完同樣多的人並計時，執行後看的是「人數加倍，時間變幾倍」：

計時程式裡的 head 只是一個區域變數。叫號名單要給整個工作台用，得把陣列和 head 包在一起，不讓外面亂動。

head 索引的佇列：怎麼包成 class？

跟上一節的 Stack 一樣用 class 包起來：items 存所有排過隊的人，head 指向目前的第一位。三個操作各自這樣做：

  • enqueue(x)：items.push(x)，攤銷 O(1)。
  • dequeue()：空的時候回傳 undefined；否則回傳 items[head] 並 head++，O(1)。
  • size：items.length - head，不是 items.length，前面已經叫過的不算。

叫過的人一直留在陣列裡怎麼辦？

工作台的叫號名單從開店到打烊都不會重建，一直有人進、一直有人出。items 只會變長，叫過的人永遠不會被丟掉，記憶體只增不減。如果是一個整天開著的伺服器（例如排程程式），這就是記憶體洩漏。

解法是偶爾整理（compaction）：當前面叫過的部分夠多，例如 head 超過陣列長度的一半、而且大於 1,000，就執行 items = items.slice(head)、head = 0，把叫過的人一次丟掉，從頭開始算索引。

整理本身要複製剩下的元素，一次是 O(n)，看起來又回到 shift 的問題了。差別在頻率：shift 每叫一號就搬一次，整理只在「至少已經叫走一半」時才發生。觸發整理之前，那些出隊操作各只花了 O(1)；把這次 O(n) 的成本分攤給它們，每個出隊只多分到常數的工作，平均下來每次還是攤銷 O(1)。這跟第 2 課陣列 push 偶爾要搬家是同一個道理：昂貴的操作很少發生，而且每次發生之前都已經累積了夠多便宜的操作來分攤它。條件裡的「大於 1,000」是為了避免佇列很短時頻繁整理，那時省下的記憶體很少，不值得複製。練習 4 會請你把它寫完，第 17 課的 BFS 會用到這個佇列。

在面試的 BFS 題目裡，通常不用寫成 class，直接 const queue = [root]; let head = 0; while (head < queue.length) { const node = queue[head++] … } 就好：程式結束時整個陣列一起被回收，不需要整理。整理只在「佇列會活很久」時才需要。
💡 實務上：自己寫的佇列只活在記憶體裡
一次請求裡的 BFS、前端依序上傳檔案、限制同時只發幾個 API 請求，用這課的陣列佇列就夠了。但「外送單排隊出餐」「訂單成立後寄信」這種跨請求、不能遺失的工作，不會放在程式的陣列裡：伺服器一重啟，佇列裡的東西就全沒了，開兩台伺服器也各有一份。這時團隊會用現成的工作佇列（例如以 Redis 為基礎的 BullMQ，或雲端的 SQS）。資深工程師會先問：處理到一半失敗要不要重試？同一筆被處理兩次會不會出事？

工作台的兩個結構都有了：復原用堆疊，叫號用 head 索引的佇列。還剩一個功能，送出訂單前的備註檢查。它看起來跟復原無關，需要的卻正是堆疊。

送出訂單前：備註裡的括號寫對了嗎？

外送單的備註會寫成 (拿鐵[去冰]){加購 可頌} 這種格式：小括號包一杯飲料，中括號是這杯的客製，大括號是加購。系統要先確認括號寫對了才能解析，寫錯的備註要在送出前擋下來，讓店員修正。規則：()、[]、{} 三種括號要正確成對、正確巢狀，其他文字忽略。「巢狀」是指括號裡面可以再包括號，但裡面的要先關，外面的才能關。這題對應 LeetCode 20. Valid Parentheses，原題只有括號，這裡多了要忽略的文字。

只數數量為什麼不夠？

第一個想法常是「左括號和右括號一樣多就對」。下面三個反例數量都對，卻都不成對：

  • )(：一左一右，但右括號出現時前面根本沒有左括號。
  • (]：一左一右，但種類不對。
  • ([)]：每種都一左一右，但 [ 還沒關，) 就想關 (，交叉了。

數量只看「有幾個」，這三個反例錯在順序和種類。正確的規則是：每個右括號要配的是「最近一個還沒配對的左括號」。這跟復原是同一件事：最晚打開的括號必須最先關上，就像最後做的一步必須最先撤銷。「最近放進去、還沒處理的」正好是堆疊的頂端。

用堆疊怎麼檢查？

把還沒關上的左括號放進堆疊，頂端永遠是「最近一個還沒配對的」，右括號出現時只要跟頂端比：

  1. 由左往右讀每個字元。
  2. 左括號：push 進堆疊，代表「等著被關上」。
  3. 右括號：堆疊頂端必須是對應的左括號，是的話 pop 掉（配對完成）；否則就錯。
  4. 其他字元：跳過。
  5. 讀完之後，堆疊必須是空的；還有剩，代表有左括號沒被關上。

右括號對應哪個左括號，用一個查表物件 { ')': '(', ']': '[', '}': '{' }（第 4 課的查表），比一串 if 好讀，之後要多支援一種括號也只要加一個鍵。判斷「這個字元是不是右括號」用 ch in OPEN_OF：in 運算子在物件有這個鍵時回傳 true（它有一個查到原型的細節，這裡不會遇到，見課末）。下面印出每一步的堆疊，四個輸入分別是一個正確的備註和三種錯誤；執行後對照每一行的堆疊內容，看錯誤是在哪一步被發現的：

這個「遇到開始就 push、遇到結束就和頂端配對」的模式到處都是：HTML 標籤是否正確關閉、JSON 的巢狀、計算機解析 3 × (2 + 1)，都是同一件事。

💡 實務上：標準格式用現成的解析器，自訂格式才自己寫
JSON 用 JSON.parse、HTML 交給瀏覽器或成熟的套件，不要自己用堆疊重寫，邊界情況（跳脫字元、引號裡的括號）比想像中多。會自己寫的通常是公司內部的小格式，例如這課的外送單備註、通知模板裡的 {{顧客名稱}}、後台的自訂篩選語法。這時除了回傳 true／false，最好也回傳出錯的位置，讓店員看得到「第 12 個字的 ] 沒有對應的 [」。程式編輯器的括號配對高亮，用的也是同一個想法。

到這裡，工作台的三個功能都能寫了。面試考堆疊與佇列時，常把題目反過來：只給你一種結構，要你做出另一種。最常考的就是用堆疊做出叫號佇列。

只有堆疊，做得出叫號佇列嗎？

題目：只准用堆疊的操作（push、pop、看頂端、長度），做出一個先進先出的佇列。這是面試常見的「用 A 實作 B」題，對應 LeetCode 232. Implement Queue using Stacks。實務上很少需要這樣做，它考的是你能不能證明一個「偶爾很慢」的操作整體還是很快，也就是前面櫃檯叫號那一節整理佇列時用過的攤銷。這一題讓你自己把攤銷算出來。

難處在於堆疊只會吐出最後放的，佇列要的卻是最早放的。關鍵觀察：把一個堆疊的東西一個一個 pop 出來、push 到另一個堆疊，順序會反過來。原本最早放進去的在最底下，倒過去之後變成最上面，就可以第一個 pop 出來了。所以用兩個堆疊：

  • inbox：新來的一律 push 到這裡。
  • outbox：要 dequeue 時從這裡 pop。
  • 只有 outbox 空了，才把 inbox 全部倒過去。

為什麼一定要等 outbox 空了？outbox 裡的人都比 inbox 裡的人更早來。outbox 還有人時就把 inbox 倒過去，新來的會疊在舊的上面，被先拿出來，順序就錯了。下面讓王、陳、林排隊，叫一位之後張才來排；執行後看每一步兩個堆疊的內容，特別是張進來時 outbox 有沒有被動到，以及最後一共搬了幾次：

第一次 dequeue 時 outbox 是空的，三個人一次倒過去，王小明變成 outbox 的頂端被叫走；張排進 inbox，一直等到 outbox 的陳、林都叫完才被倒過去。程式裡 inbox.pop()! 的 ! 是TypeScript 課第 17 課的非空斷言：pop() 的型別是 string | undefined，但迴圈條件已經確認 inbox 不是空的，! 告訴 TypeScript 這裡不會是 undefined。

為什麼是攤銷 O(1)？

單看一次，最壞確實是 O(n)。但換個角度，不數每次操作花多少，而是數每個元素一生被做了幾件事：push 進 inbox 一次、從 inbox pop 一次、push 進 outbox 一次、從 outbox pop 一次，最多 4 次，而且不會被搬回去。不管操作的順序怎麼排，m 次操作總共最多 4m 步，平均每次 O(1)，這就是攤銷 O(1)。上面的程式 4 個人總共搬了 4 次，每人一次，正是這個道理。

錯誤的做法是每次 dequeue 都把 inbox 整個倒過去、拿一個、再整個倒回來。這樣同一個元素會被來回搬很多次，每次 dequeue 都是 O(n)，n 個操作就是 O(n²)。攤銷成立的前提是「每個元素只搬一次」，倒回去就破壞了它。練習 2 的計時測試會擋下這種寫法。

攤銷不是平均情況：「平均情況」是對隨機輸入取平均，運氣不好可能每次都很慢；「攤銷」是對任何操作順序都成立的保證：總成本 ≤ 每次常數 × 操作次數。所以面試說「單次最壞 O(n)，攤銷 O(1)」是精確的講法。

到目前為止的題目都在處理「拿出來的順序」。最後一個變形不改順序，而是要堆疊多回答一個問題，而且回答也要 O(1)。

訂單編輯器要隨時顯示最便宜的品項：怎麼做到 O(1)？

回到點單工作台的訂單編輯器。店長推出促銷「整筆訂單裡最便宜的那一項半價」，所以編輯器每加入一個品項，就把價格 push 進價格堆疊；按復原就 pop 掉最後一個。畫面要隨時顯示「目前堆疊裡最便宜的是多少」，每加一項、每復原一次都要重算。題目要求 push、pop、看頂端、取最小值四個操作都是 O(1)，對應 LeetCode 155. Min Stack。

暴力解：getMin 時走一遍所有價格找最小，O(n)。如果每次 push 後都問一次，n 次就是 O(n²)。Math.min(...items) 寫起來短，但一樣要走過整個陣列（另外還有一個陣列很大時會出錯的限制，見課末）。

第二個想法：多存一個變數 min，push 時跟新價格比，比較小就更新。push 沒問題，問題在 pop。依序加入 110、90、80 元，min 是 80；按復原把 80 拿走，最小值應該變回 90，可是變數只記得 80，不知道上一個最小值是多少，又得重新掃一遍。一個變數只能記住「現在」，復原需要的是「每一個過去的時間點」。

正解是把每個時間點的答案都記下來：多一個堆疊 mins，跟主堆疊一層對一層，mins 的第 i 層記錄「主堆疊從底到第 i 層為止的最小值」。push 時放 Math.min(新價格, 目前的最小值)；pop 時兩個一起 pop，上一層的最小值自然就回來了，不用重算。下面依序 push 110、90、120、80、80 再 pop 三次；執行後看每一行右邊的 mins，以及兩個 80 被 pop 掉時 getMin 怎麼變：

看最後幾步：第一個 pop 拿走一個 80，另一個 80 還在，getMin 仍然是 80；兩個 80 都走了之後，mins 的頂端是 90，不用重新掃。每個操作都只動兩個堆疊的頂端，全部 O(1)；代價是多一倍的空間，O(n)。這是這門課一再出現的取捨：用空間換時間。

連續兩次 push 80 就是在測重複的最小值。一層對一層的寫法每層都存，重複值不會出錯，面試時先寫它。有一種只在必要時才 push 進 mins 的省空間寫法，在重複值上很容易寫錯，細節見課末。

交出去之前：邊界和複雜度都檢查了嗎？

這類結構的 bug 很少出在主要流程，多半出在邊界：空的時候、值重複的時候、操作交錯的時候。寫完之後逐一檢查：

  • 空的時候：pop、peek、dequeue、getMin 要回傳什麼？這課一律 undefined。不要回傳 Infinity、0、-1，呼叫的人分不出來「真的是 0 元」還是「空的」。
  • peek 不能改變內容：只看不拿。兩堆疊佇列的 peek 可以倒 inbox（內部順序調整，外面看不出差別），但不能 pop 掉元素。
  • size 要算全部：兩堆疊佇列是兩個長度相加；head 佇列是 items.length - head。
  • 重複的值：最小值堆疊 push 兩個一樣的最小值，pop 一個之後最小值不變。
  • 交錯操作：只測「全部放進去再全部拿出來」抓不到「outbox 還有東西時就倒」這類錯誤，要測進出交錯的順序。

實務上怎麼選：一般程式裡要佇列，head 索引最簡單也最快；兩堆疊佇列主要是面試題，但「把成本延後、累積起來一次做」的想法在批次處理很常見。要依優先順序（不是先來後到）出隊時，例如外送單要先處理快超時的那張，佇列就不夠用了，要用第 19 課的 heap。

練習

傳進來的字串、class 的內部狀態都由你自己管理。練習 2、3 有計時測試：每次都重新搬動或重新掃描的寫法會太慢判錯（第 2 課：計時不過就是複雜度不夠）。練習 2、4 在測試期間會把 shift 換成會丟錯的函式。

練習 1：寫 isBalanced(note)：備註裡有 ()、[]、{} 三種括號和其他文字，括號全部正確成對、正確巢狀時回傳 true，否則 false；其他文字忽略，沒有括號（包含空字串）算成對。對應 LeetCode 20. Valid Parentheses。

練習 2：完成 TwoStackQueue<T>：enqueue(x)、dequeue()、peek()（看前端不拿走）、size（getter）；空的時候 dequeue、peek 回傳 undefined。內部只能用 inbox、outbox 兩個陣列當堆疊：只用 push、pop、length 和讀最後一個元素。所有操作攤銷 O(1)：測試會先放 6,000 個、再交錯進出 6,000 次並計時，每次 dequeue 都倒過去再倒回來的寫法會太慢。對應 LeetCode 232. Implement Queue using Stacks。

練習 3：完成 MinPriceStack：push(price)、pop()（回傳拿走的價格）、top()（看頂端）、getMin()（目前堆疊裡最小的價格），每個操作 O(1)；空的時候 pop、top、getMin 都回傳 undefined。價格可能重複。測試會 push 3 萬個遞減的價格、再全部 pop 掉，每一步都呼叫 getMin 並計時，每次掃描（包括 pop 時重新掃描）的寫法會太慢。對應 LeetCode 155. Min Stack。

練習 4：完成 OrderQueue<T>（第 17 課的 BFS 會用到）：enqueue(x)、dequeue()、peek()、size（getter）、isEmpty()；空的時候 dequeue、peek 回傳 undefined。用陣列 items 加 head 索引實作，不能用 shift。dequeue 之後，當 head 大於 1,000 而且超過 items.length 的一半時，把前面用過的部分切掉（compaction）。debugLength() 已經寫好，測試會用它確認：交錯進出 20 萬次之後，內部陣列的長度不超過 2 × size + 1000。

練習 5：用 array.push() 排隊、array.shift() 叫號實作佇列。叫一次號（dequeue）的成本是？

✓ shift 拿走索引 0 之後，原本索引 1 的要變成 0、2 變成 1……規格的步驟是逐一搬移，O(n)。本課用 Node 實測，1 萬人很快、2 萬人就慢了上百倍，說明最佳化不可靠。a 錯：pop 拿的是尾端，不用搬別的元素；shift 拿的是開頭。c 錯：搬動沒有二分的關係。大量出隊時改用 head 索引，每次 O(1)。

練習 6：兩個堆疊做的佇列，outbox 空的時候一次 dequeue 要把 inbox 的 n 個元素全部搬過去。dequeue 的複雜度怎麼說最精確？

✓ 數每個元素的總工作量：進 inbox、出 inbox、進 outbox、出 outbox，最多 4 步，不會被搬回去。m 次操作總共最多 4m 步，所以攤銷 O(1)；單看某一次確實可能是 O(n)。a 錯：只看最壞的一次，忽略了這種最壞情況不可能每次都發生。b 錯：搬動是 dequeue 做的工作，當然要算，只是分攤下來很小。

練習 7：同事說：「檢查括號只要數左括號和右括號一樣多就好，用不到堆疊。」哪一個輸入最能說明他錯了？

✓ )( 的左右數量都是 1，數數量會說「對」，但它不成對；(]、([)] 也一樣。括號要看順序和種類：每個右括號要配最近一個還沒配對的左括號，這正是堆疊的頂端。b 錯：數量不一樣，數數量也會正確地回答 false，說明不了問題。c 錯：它本來就成對，而且其他文字跳過就好，跟要不要堆疊無關。

常見錯誤

  • 用 shift 當佇列：每次出隊 O(n)，大量出隊時整體 O(n²)。用 head 索引，佇列會活很久時再加上整理。
  • pop 前沒檢查是否為空：空陣列的 pop 不報錯，只回傳 undefined，錯誤在很後面才出現（NaN、比較永遠不成立）。先判斷空的情況，回傳題目規定的值。
  • 結束時沒檢查堆疊是否為空：(( 被當成正確。讀完還有左括號，就是沒被關上。
  • 只數括號數量：)(、(] 數量都對卻不成對。要用堆疊檢查順序和種類。
  • 最小值堆疊只存一個值：pop 掉最小值之後不知道上一個最小值。用另一個堆疊一層對一層記錄。
  • 輔助堆疊只在「嚴格小於」時才放：重複的最小值 pop 一次就不見了。條件要用小於或等於，或直接每層都放。
  • 兩堆疊佇列每次都倒來倒去：每次 O(n)，失去攤銷 O(1)。只有 outbox 空了才倒，而且不倒回去。
  • head 佇列的 size 用 items.length：把叫過的也算進去。要扣掉 head；整理之後 head 要歸零。

補充與查表

in 運算子也會查到原型上的鍵

括號檢查用 ch in OPEN_OF 判斷右括號。in 不只查物件自己的鍵，也會查到原型上的鍵，例如 'toString' in {} 是 true。這裡的 ch 只是一個字元，不會撞到 toString 這類名字，所以沒有影響；查表的鍵可能是任意字串時，就要注意這一點。

括號數量是奇數，可以提早結束嗎？

可以：括號總數是奇數，一定不成對。但這課的備註有其他文字，要先把括號數過一遍才知道是不是奇數，省下的工作不多，不值得特別寫。

Math.min(...items) 的限制

除了一樣要走過整個陣列之外，展開運算子會把每個元素變成一個函式參數，陣列很大時參數太多，會丟 RangeError。要對大陣列取最小值，用迴圈或 reduce。

省空間的最小值堆疊：條件要用「小於或等於」

有一種省空間的寫法：只有新價格小於或等於目前最小值時才 push 進 mins，pop 時如果 pop 出來的等於 mins 頂端才一起 pop。如果條件寫成嚴格的「小於」，push 兩次 80 時 mins 只記一次，pop 掉第一個 80 就把它拿走，堆疊裡明明還有 80，getMin 卻回答 90。一層對一層的寫法沒有這個問題，面試時先寫它。

小結

  • 堆疊後進先出（push、pop、peek 都在頂端），適合復原：後面的步驟建立在前面的步驟上，所以從最後一步往回退。佇列先進先出（尾端 enqueue、前端 dequeue），適合叫號。題目說「最近的」「配對」「撤銷」想堆疊，「依序」「一層一層」想佇列。
  • JavaScript 用陣列當堆疊：尾端操作不用搬動元素，push／pop 攤銷 O(1)，頂端用 at(-1)。空的時候 pop 回傳 undefined，不會報錯，要在 pop 前想好空的情況。
  • 佇列不要用 shift（拿走索引 0 要把後面全部往前搬，O(n)）；用 head 索引，size = items.length - head，佇列會活很久時偶爾整理，攤銷還是 O(1)。
  • 括號檢查：最晚打開的要最先關上，所以左括號 push、右括號比對頂端；三種失敗是頂端不對、堆疊是空的、最後還有剩。
  • 兩個堆疊做佇列：outbox 空了才把 inbox 倒過去；每個元素只搬一次，單次最壞 O(n)、攤銷 O(1)。
  • 最小值堆疊：一個變數只記得現在的最小值，復原需要每個過去時間點的答案；多一個堆疊一層對一層記錄，所有操作 O(1)，用 O(n) 空間換時間。
