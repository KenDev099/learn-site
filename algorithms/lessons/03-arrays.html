階段 1：解題基本功 · 第 3 課

陣列：索引、原地修改與邊界

週一早上，店長在群組貼了後台「今日營運」頁的三張截圖，各附一句話：

  1. 「每日累計杯數」的表格多了一列，那一列顯示 NaN。
  2. 在菜單頁按了「依價格排序」看一下價錢，關掉之後，菜單原本的上架順序也被打亂了。
  3. 按了「售完的移到最後」，結果還有一個售完的品項卡在中間。

三個 bug 出在三支不同的函式，原因卻是同一件事：寫的人沒弄清楚陣列怎麼運作。這一課就跟著這張回報單走：先搞懂陣列在記憶體裡怎麼擺，再一個一個找出三個怪現象的原因，最後重寫「累計杯數」和「售完移到最後」兩支函式，寫到可以交出去：不越界、不改壞別人的資料、資料變多也不會變慢。面試的陣列題也幾乎都栽在這三個地方：索引差一格、改到了不該改的陣列、一邊刪除一邊走結果漏掉元素。

這課的路線：
  1. 陣列在記憶體裡怎麼擺：為什麼用索引讀寫是 O(1)，在開頭插入卻是 O(n)。
  2. 累計杯數為什麼出現 NaN：讀到不存在的索引時 JavaScript 為什麼不報錯，三種不會越界的迴圈怎麼寫（第一個怪現象）。
  3. 重寫累計杯數：照七步驟走完第一題，用前一天的結果把 O(n²) 變 O(n)。
  4. 排序後菜單為什麼也變了：回傳新陣列還是原地修改，怎麼讓 TypeScript 先擋下來（第二個怪現象）。
  5. 售完的品項為什麼卡在中間：邊走邊刪為什麼會漏，讀寫指標怎麼只用 O(1) 額外空間原地整理（第三個怪現象）。
  6. 交出去之前：邊界情況與複雜度，兩支函式要在腦中跑哪幾種輸入。
這課會用到：
  • 第 2 課的 Big-O：O(n) 是步數跟著資料量等比例成長，O(n²) 是資料變 10 倍、步數變 100 倍。
  • TypeScript 課第 2 課的「陣列是參考」：傳進函式的是同一個陣列，函式裡改了，外面也跟著變。

陣列在記憶體裡怎麼擺？

三個怪現象都跟「索引」有關，所以先弄清楚索引到底是什麼。陣列（array）是一排編了號的格子。格子裡放的值叫元素（element），格子的編號叫索引（index）。

索引從 0 開始，不是從 1。可以把索引想成「離第一格有幾格」：第一格離自己 0 格，所以是 0；第二格離第一格 1 格，所以是 1。照這個算法，長度 n 的陣列，最後一格的索引是 n − 1，而 n 這個編號根本沒有格子。這一點等一下就是第一個怪現象的答案。

下圖是菜單的價目表 prices，6 個價格放在 6 個連在一起的格子裡：

「連在一起」是陣列最重要的性質。因為每一格一樣大、一格緊接一格，要讀 prices[3] 時，電腦不用從第一格開始數，直接用「起點位置 + 3 × 每格大小」算出那一格在哪裡，一步就到。陣列有 6 格還是 600 萬格，這個算式都只算一次，所以用索引讀寫都是 O(1)。如果格子不是連在一起，像第 13 課的鏈結串列那樣一格指向下一格，要找第 3 格就只能從頭一格一格走過去，那是 O(n)。

代價出現在插入和刪除。陣列要一直保持「連在一起、索引從 0 連續編號」：在開頭插入一個 75（unshift(75)），原本在索引 0 的 80 必須變成索引 1，110 變成索引 2……每一個元素都得往後搬一格，才能空出最前面那格。同樣地，刪掉中間一個（splice(i, 1)），i 後面的元素都要往前搬一格補洞。要搬幾次跟元素數量成正比，所以是 O(n)。只在尾端加或刪就不一樣了，前面的元素都不用動：

操作成本原因
arr[i]、arr[i] = xO(1)直接算出位置
push、pop（尾端）O(1)（攤銷）不用搬動別的元素
unshift、shift（開頭）O(n)每個元素都要搬一格
splice(i, 1)（中間）O(n)i 後面的元素都要搬

表裡 push 寫的是「攤銷 O(1)」，這要從 JavaScript 陣列可以一直變長說起。JavaScript 的陣列是動態陣列（dynamic array）：長度不用事先決定。引擎的做法是先多預留一些空格，push 時把值放進下一個空格就好，不用動到別的元素。空格用完了，引擎才另外要一塊更大的空間，把全部元素搬過去，這一次搬家是 O(n)。但搬家很少發生，而且每次都多要一大截空間，之後很多次 push 都不用再搬。把偶爾一次的搬家成本平均分到所有 push 上，每次 push 還是 O(1)。這種「單次偶爾很貴、平均下來很便宜」的成本，叫做攤銷（amortized）O(1)。（這是估算成本用的模型，ECMAScript 規格其實沒有規定引擎怎麼存，見課末。）

💡 實務上：先問 n 有多大、多常做
咖啡店後台一張訂單列表通常只有幾十筆，unshift 還是 push 根本感覺不出差別，可讀性優先。真的會出事的是「大陣列 × 高頻率」：例如伺服器用陣列當工作佇列，每次 shift() 取出一筆，佇列累積到幾十萬筆時，照上面的成本表，每取一筆都要把剩下的元素搬一格。資深工程師看到效能問題，會先問「資料量最多多少、這段程式多久跑一次」，再決定要不要換寫法或資料結構，而不是見到 unshift 就改。

到這裡知道了：合法的索引只有 0 到 n − 1。那程式如果用了 n，或更大的索引，會發生什麼事？這就是累計杯數表格多出一列 NaN 的原因。

累計杯數為什麼出現 NaN？越界不會報錯

上一節說合法的索引只有 0 到 n − 1，用了這個範圍以外的索引，叫做越界（out of bounds）。後台的累計杯數函式原本長這樣：

const result: number[] = []
for (let i = 0; i <= cups.length; i++) {   // 條件多了一個 =
  let sum = 0
  for (let j = 0; j <= i; j++) sum += cups[j]
  result.push(sum)
}

cups 有 4 天的資料時，合法索引是 0 到 3，但外層條件 i <= cups.length 讓 i 跑到 4。這一圈內層迴圈讀到 cups[4]，那一格不存在。很多語言（例如 Java）遇到越界會立刻丟錯，程式停在出錯的那一行，一看就知道問題在哪。JavaScript 不會：它給你 undefined，計算繼續往下走，錯誤要到很後面才看得到。

lab 用第一節的價目表 prices 重現同一件事（跟 cups 一樣是數字陣列，讀到索引 n 時的行為一樣）。執行後看三件事：讀越界得到什麼、拿它計算之後變成什麼、寫越界時陣列怎麼了：

第一行印出 undefined：索引 3 沒有格子，JavaScript 不報錯，只回答「這裡沒有值」。接著 undefined + 80 得到 NaN（Not a Number，「不是一個數字」），而 NaN 會傳染：它加減乘除任何數字都還是 NaN，跟任何數字比大小都是 false。累計杯數表格裡的那一列就是這樣來的：最後一圈 sum += cups[4] 讓 sum 變成 NaN，再被 push 進結果。整個過程沒有任何錯誤訊息，畫面上只會看到「怪怪的結果」，所以才會是店長先發現。

最後兩行示範寫入越界：對長度 3 的陣列寫 copy[5] = 70，JavaScript 不會拒絕，而是直接把陣列拉長到 6。中間的索引 3、4 沒有被放過任何值，這種格子叫空洞（hole），讀到也是 undefined。所以寫越界比讀越界更難查：陣列長度悄悄變了，之後每一個用到 length 的迴圈都會多走幾格。

那 TypeScript 為什麼沒有在編輯器裡畫紅線？因為 TypeScript 預設相信你給的索引是對的：prices 的型別是 number[]，所以 prices[3] 的型別就是 number，執行時卻是 undefined。TypeScript 有一個選項 noUncheckedIndexedAccess，開了之後會把 arr[i] 的型別當成 number | undefined，逼你先處理沒有值的情況；但它不包含在 strict 裡，這門課的編輯器用的是 strict 設定，沒有開這個選項。更根本的是，型別只在編譯時檢查（TypeScript 課第 13 課），執行時已經沒有型別了。守住邊界是你自己的工作。

修法是把外層條件改成 i < cups.length。這種「條件多一個等號」的錯太常見，與其每次都重新推一遍，不如把陣列題最常用的幾種迴圈寫法記熟。

三種不越界的迴圈

陣列題的迴圈幾乎都是這三種之一。這裡用排隊名單示範，因為第三種配對迴圈要等練習 2 反轉名單才用得到；前兩種就是累計杯數和之後讀寫指標用的形狀。執行後對照每一行印出的索引，確認都落在 0 到 n − 1 之間：

第一種從頭走到尾：i 從 0 開始，條件是 i < n，最後一圈的 i 是 n − 1，剛好是最後一格。寫成 i <= n 就會多走一圈到 n，也就是累計杯數那個 bug。第二種從尾走到頭：i 從 n − 1 開始（不是 n），條件是 i >= 0，最後一圈是索引 0。

第三種只走一半，每一個 i 都配對到另一頭的 n − 1 − i：i = 0 配最後一格，i = 1 配倒數第二格，以此類推。這是反轉陣列的基本形狀。迴文是正著讀和倒著讀都一樣的序列，判斷時也是頭尾兩兩比對，用的是同一種迴圈。5 個人時 Math.floor(5 / 2) 是 2，只配對 (0, 4) 和 (1, 3)；正中間的索引 2 自己跟自己配對，不用處理。為什麼不走滿 n 次？因為走到後半段時，每一對會從另一頭再被處理一次：反轉的話，前半段換過去、後半段又換回來，結果等於沒動。

配對之後常常要交換（swap）兩格的值，例如練習 2 的反轉排隊名單。直覺寫法 a[i] = a[j]; a[j] = a[i] 是錯的：第一行已經用 a[j] 蓋掉了 a[i] 原本的值，第二行再讀 a[i]，拿到的是剛放進去的 a[j]，兩格變成一樣。要先把被蓋掉的那個值存起來：

const tmp = a[i]
a[i] = a[j]
a[j] = tmp

// 或用解構賦值（destructuring）一行寫完，右邊會先算好兩個值再分別放回去
;[a[i], a[j]] = [a[j], a[i]]

解構賦值那行前面的分號是不寫分號風格下的規則，原因見課末「補充與查表」。

💡 實務上：列表 API 一定會遇到空陣列
API 回傳的列表可能是空的：新顧客還沒有訂單、搜尋沒有結果、篩選後剩 0 筆。寫 orders[0].total 在開發時都正常，碰到空陣列就變成 Cannot read properties of undefined，畫面白掉，常常是客服先收到回報。習慣是：取第一筆或最後一筆前先判斷長度，或寫 orders[0]?.total 並決定沒有資料時要顯示什麼（例如「尚無訂單」）。新專案可以在 tsconfig 開 noUncheckedIndexedAccess，讓 TypeScript 把 arr[i] 當成可能是 undefined，代價是要多寫一些判斷。累計杯數也一樣：新開的分店還沒有任何一天的資料，cups 就是空陣列，函式要能處理。

把條件改成 i < cups.length，NaN 就消失了。但回頭看那段程式，還有第二個問題：每一天都用內層迴圈從第 0 天重新加一次。資料少的時候看不出來，資料一多就會慢，下一節照七步驟把它重寫。

怎麼重寫累計杯數，資料變多也不會慢？

上一節修好了越界，但雙迴圈的寫法還在。照第 1 課的七個步驟從頭走一次，看改進是怎麼「找」出來的。

① 重述：先用自己的話把題目講清楚，包括輸入、輸出和特殊情況。輸入 cups 是每天賣出的杯數，可能是負的，代表當天退杯多於賣出。輸出一個新陣列，長度跟輸入一樣，第 i 個是「第 0 天到第 i 天的總和」。像這種「從開頭到某個位置為止的那一段」叫前綴（prefix），所以第 i 個也可以說成「前 i + 1 天的前綴總和」。空陣列回傳空陣列。這題對應 LeetCode 1480. Running Sum of 1d Array。

② 手算：[3, 1, 2, 5] → 第 0 天 3、第 1 天 3 + 1 = 4、第 2 天 4 + 2 = 6、第 3 天 6 + 5 = 11，答案 [3, 4, 6, 11]。注意手算時你自然就是拿「上一天的答案」再加當天，沒有每次從 3 開始重加。這個直覺等一下會用到。

③ 暴力解：就是後台原本的寫法（條件修正後）：每一天都從第 0 天加到當天。第 i 天要加 i + 1 次，總共 1 + 2 + … + n = n(n + 1) / 2 次，是 O(n²)。

for (let i = 0; i < cups.length; i++) {
  let sum = 0
  for (let j = 0; j <= i; j++) sum += cups[j]   // j <= i：當天也要算進去
  result.push(sum)
}

內層的 j <= i 有等號是對的：j 走的是 0 到 i，i 本身是合法索引，當天也要算進去。等號該不該加，要看那個索引有沒有格子，不是憑感覺。

④ 找重複的工作：算第 3 天時，內層迴圈又把 3 + 1 + 2 加了一次，但這個 6 在算第 2 天時就已經得到了。暴力解慢，就慢在每一天都把前面所有天重算一遍。

⑤ 改進：既然前一天的累計已經算好，第 i 天的累計 = 第 i − 1 天的累計 + 當天杯數，也就是 result[i] = result[i − 1] + cups[i]。第 0 天前面沒有累計，result[-1] 不存在（又是越界），要單獨當成 0。另一種寫法是用一個 sum 變數從 0 開始一路加，每天把 sum 放進結果，兩種意思一樣。執行後看每一列的 result[i] 是不是等於上一列的 result[i] 加這一列的 cups[i]：

⑥ 邊界：空陣列時迴圈一次都不跑，回傳 []；只有一天時結果就是那一天；有負數（退杯）時累計可能變小，甚至變成 0，程式不需要特別處理，但測試要包含它。

⑦ 複雜度：每一天只做一次加法，O(n) 時間。空間方面，輸出本身就是長度 n 的陣列，這是題目要的結果，一般不算進「額外空間」；除了輸出以外只用了幾個變數，額外空間 O(1)。

💡 實務上：累計值就是報表裡的「累計營收」曲線
後台儀表板常有「本月累計營收」「累計會員數」的折線圖，做法就是對每日數字算一次前綴總和。一個月 30 天這種量，在前端或 API 裡跑一次迴圈就夠了。資料量大（例如一整年的每筆訂單）時，通常交給資料庫彙總好再回傳，不要把全部資料抓到前端再算。要先跟 PM 確認計算規則：退款要不要扣、日期以下單還是付款時間為準，這些比演算法本身更常出錯。

注意第 ① 步寫的是「輸出一個新陣列」。直接把累計寫回 cups 不是更省空間嗎？第二個怪現象，正是某支函式這樣「省」出來的。

排序後菜單為什麼也變了？回傳新陣列還是原地修改

上一節選擇了回傳新陣列，這一節說明為什麼。處理陣列有兩種做法：

  • 回傳新陣列：輸入原封不動，結果放在另一個新的陣列裡。要多 O(n) 的空間，但呼叫端手上的資料不會被動到。
  • 原地修改（in-place）：直接改傳進來的那個陣列，不另外建一個同樣大小的陣列，額外空間 O(1)。

原地修改是一種副作用（side effect）。副作用指的是：函式除了回傳值以外，還改了函式外面的東西。為什麼函式改得到外面的陣列？因為陣列是參考（TypeScript 課第 2 課）：變數裡存的不是陣列本身，而是「陣列在哪裡」。把陣列傳進函式，傳過去的是同一個位置，函式裡的參數和呼叫端的變數指向同一個陣列，函式裡改了格子，呼叫端看到的也跟著變。

菜單頁的「依價格排序」就是這樣出事的。那支函式名叫 sortedPrices，看名字以為會回傳一份排好的新陣列。執行後比較兩行輸出，再看最後一行：

sort 是原地排序：它把傳進來的陣列本身排好，再把同一個陣列回傳出來。所以 sorted 和 menu 根本是同一個陣列，最後一行印出 true。函式有 return，不代表回傳的是新東西。如果 menu 是 Vue 元件的 reactive 狀態，畫面上的菜單順序就會「莫名其妙」變掉，而且看畫面會以為是菜單頁出錯，真正的原因卻在另一個地方呼叫的 sortedPrices，很難查。

修法有兩層，一層在執行時，一層在編譯時：

執行時的修正是把 sort 換成 toSorted。toSorted 是 ES2023 加入的方法，排序邏輯跟 sort 一樣，但它複製一份再排，回傳新陣列，原本的不動。也可以先複製再排：[...prices].sort(…)，效果相同。

編譯時的修正是把參數型別寫成 readonly number[]，也就是「唯讀陣列」型別。它跟 number[] 是同一種陣列，只是型別上拿掉了所有會修改陣列的方法，也不准寫 prices[0] = 3 這種指定。這樣一來，如果之後有人在這個函式裡寫 prices.sort(...)，編輯器當場就畫紅線，錯誤不會等到店長截圖才被發現。它只是編譯時的檢查（TypeScript 課第 13 課：型別在執行前就被拿掉），執行時陣列還是一般陣列；呼叫端照樣傳普通的 number[] 進來，不用改。實際的錯誤訊息和型別相容的方向見課末「補充與查表」。

整理成兩個習慣：

  • 只讀的參數寫成 readonly number[]：讓 TypeScript 先擋下 push、sort、splice、arr[i] = x。這門課不能改的輸入都這樣宣告，隱藏測試也會用 Object.freeze 凍結輸入。凍結的意思是把物件鎖住，之後任何修改都會失敗；在練習的判分環境裡，改到凍結的陣列會丟出 TypeError。
  • 需要改就先複製：[...arr] 或 arr.slice()，代價是 O(n) 時間與空間。最常踩到的會改原陣列的方法是 sort、reverse、splice，完整的對照表見課末。

那什麼時候可以原地修改？面試題目通常會講明，例如題目寫「in-place」或「do not modify the input」。沒講就問面試官：「可以修改傳進來的陣列嗎？」這句話本身就是加分的資深習慣。實務上，資料是別人的（props、store、函式參數）就不要改；原地修改留給「這份資料是我建立的，而且量大到複製會吃記憶體」的情況。

把新陣列指定給參數，不是原地修改。函式裡寫 stock = stock.filter(x => x !== 0)，只是讓區域變數 stock 改指向新陣列，呼叫端手上的還是舊的那一個。原地修改一定要寫成 stock[i] = … 這種「改格子裡的值」。
💡 實務上：前端框架的狀態幾乎都用「回傳新陣列」
React 判斷狀態有沒有變是比較參考：items.push(x); setItems(items) 傳的還是同一個陣列，React 會認為沒變而不重新渲染，所以要寫 setItems([...items, x])。Vue 的 reactive 雖然偵測得到 push，但父元件透過 props 傳進來的陣列也不應該在子元件裡改，要用事件通知父元件改。Code review 時看到對參數、props、store 呼叫 sort、splice、reverse，是資深工程師一定會停下來問的地方。菜單排序就是這種情況：菜單是別人的資料，排序只是為了顯示，所以回傳新陣列。

第三個怪現象剛好相反：「售完的移到最後」這個功能，需求就是要整理庫存陣列本身，題目明確要求原地修改。原地修改本身沒有錯，錯在怎麼改。

售完的品項為什麼卡在中間？邊走邊刪的陷阱

上一節說原地修改的關鍵是「改格子裡的值」，這一節的問題就出在改格子的方式。先照七步驟的第 ① 步重述題目：stock 是每個品項的剩餘數量，0 代表售完。原地把所有 0 移到最後，其他品項保持原本的先後順序，回傳 void（什麼都不回傳，結果就是改好的 stock）。例如 [0, 1, 0, 3, 12] → [1, 3, 12, 0, 0]。這題對應 LeetCode 283. Move Zeroes。

後台原本的寫法很直覺：走過每一格，看到 0 就用 splice 刪掉，再在尾端 push 一個 0 補回去。店長說「還有一個卡在中間」，所以用連續兩個 0 跑跑看。執行後看每一行的 i 和陣列，找出第二個 0 是在哪一步被跳過的：

結果是 [5,0,3,0]，不是預期的 [5,3,0,0]。一步一步看：i = 1 時看到 0，splice(1, 1) 把它刪掉。照第一節的成本表，刪掉中間一格後，後面的元素都要往前搬一格補洞，所以原本在索引 2 的第二個 0 搬到了索引 1。但迴圈不知道這件事，照常 i++ 跑到索引 2，跳過了剛搬到索引 1 的那個 0。一邊刪除一邊用索引往前走，刪掉的那一格後面的第一個元素一定會被跳過；只有它也剛好要刪的時候，結果才會錯，所以這個 bug 只在「連續兩個 0」時出現，測試很容易漏掉。

那刪掉的時候不要 i++，不就修好了？結果會對，但還有效能問題：每次 splice 都要搬動後面的元素，是 O(n)；最壞情況每一格都要刪，O(n) 次 × O(n) = O(n²)。另一個方向是用 filter 挑出非 0 的品項、後面補 0，再一格一格寫回 stock。這樣時間是 O(n)，結果也對，但 filter 會建一個新陣列，用了 O(n) 的額外空間；選擇原地修改，本來就是為了不多用這份空間。

所以要的是：只走一次（O(n) 時間），而且不另開陣列（O(1) 額外空間）。

怎麼只走一次、不另開陣列？讀寫指標

做法是用兩個變數記住兩個位置。這門課說的指標（pointer），指的就是「存著某個索引的變數」，跟其他語言裡指向記憶體位址的指標不是同一件事。這題用兩個指標，分工不同：

  • 讀指標 read：從頭到尾走過每一格，每一圈都往前一格，負責「看」這一格是不是 0。
  • 寫指標 write：記住「下一個要保留的品項該放在哪一格」。只有真的放進一個品項時，它才往前一格。

為什麼這樣不會出錯？關鍵在 write 永遠不會超過 read：每一圈 read 一定前進，write 最多跟著前進。所以寫進去的位置一定是已經讀過的格子，不會蓋掉還沒看過的資料。而且保留的品項是照讀到的順序一個一個放進 write，先後順序不會變。跟 splice 版比，這裡從頭到尾沒有刪除任何一格，也就沒有「後面的元素往前搬、迴圈跳過」的問題；每個元素只被讀一次、最多被寫一次。

執行後看表格的每一列：read 每列都加 1，write 只在遇到非 0 時才加 1：

表格裡看得到：read = 1 時，1 被寫到索引 0；read = 3 時，3 被寫到索引 1；read = 4 時，12 被寫到索引 2。走完之後 write 是 3，前 3 格 [1, 3, 12] 就是保留的品項，順序沒變。但整個陣列是 [1, 3, 12, 3, 12]：後兩格是被搬走之前的舊資料，因為我們只寫了前面，沒有清後面。最後再用一個迴圈從 write 補 0 到結尾就完成，這是練習 3。

讀寫指標是原地整理陣列的通用形狀：只要是「留下符合條件的、丟掉其他的」，都能這樣寫，差別只在 if 的條件。例如練習 4 去掉取消的訂單，條件就是「不等於取消的編號」。第 7 課的雙指標是另一種用法：兩個指標從陣列的兩端往中間走。

兩支函式都重寫好了。交出去之前還差最後一步：三個怪現象都是在某種特定輸入才出現的，怎麼確定新版本在那些輸入上都對？

交出去之前要跑哪些輸入？邊界情況與複雜度

上一節的 splice 版在一般輸入都對，只有連續兩個 0 時才錯；累計杯數的越界也只在最後一圈出事。這類錯誤靠多跑幾個「普通」例子是找不到的，要刻意挑容易出事的輸入。陣列題交出去之前，把這張表的每一列在腦中跑一次（以售完移到最後為例）：

情況例子預期結果容易出的錯
空陣列[][]直接讀 arr[0] 得到 undefined
只有一個元素[0]、[7]不變[0] 時 write 停在 0，補 0 迴圈要從 write 開始才會寫到索引 0；[7] 時 write 走到 1，補 0 迴圈一次都不跑

最後說出複雜度。讀寫指標的版本：read 走一次 n 格、補 0 最多 n 格，O(n) 時間；只用了 read、write 兩個變數，O(1) 額外空間。面試時這兩句要主動講出來，並說明跟 splice 版（O(n²)）、filter 版（O(n) 額外空間）的取捨。這樣店長的三張截圖都有了答案：累計杯數多走了一格，菜單排序改到了別人的陣列，售完整理一邊刪一邊走。

補充與查表

這個模型和規格的關係

ECMAScript 規格沒有規定引擎內部怎麼存陣列，但面試和實務都用第一節「連在一起的格子＋動態陣列」這個模型估算成本。

readonly 陣列的錯誤訊息與指定方向

在參數是 readonly number[] 的函式裡寫這些，編輯器會報錯（TypeScript 5.9 的訊息）：

prices.push(1)   // Property 'push' does not exist on type 'readonly number[]'.
prices.sort()    // Property 'sort' does not exist on type 'readonly number[]'.
prices[0] = 3    // Index signature in type 'readonly number[]' only permits reading.

呼叫端傳普通的 number[] 給要 readonly number[] 的函式沒問題；反過來，把 readonly number[] 傳給要 number[] 的函式會報錯，因為那個函式可能會改它。

會改原陣列與回傳新陣列的方法

查表用，不用背：

會改原陣列回傳新陣列（ES2023 加入）
sort、reverse、splice、push、pop、shift、unshift、filltoSorted、toReversed、toSpliced、with

以 [ 開頭的一行前面要加分號

不寫分號的風格下，以 [ 開頭的一行前面要加 ;，否則會跟上一行連在一起。JavaScript 只在下一行無法接上前一行時才自動補分號（automatic semicolon insertion），而 [ 可以接在前一行的運算式後面，當成索引存取。例如交換的兩種寫法連著寫、中間不加分號：

a[j] = tmp
[a[i], a[j]] = [a[j], a[i]]

JavaScript 會把這兩行讀成一行 a[j] = tmp[a[i], a[j]] = [a[j], a[i]]：tmp[...] 變成對 tmp 做索引存取，交換根本沒有發生。在 [ 前面加上 ;，就明確把兩行切開。

練習

練習 1、3 的隱藏測試會用大資料量計時：比標準答案慢 20 倍以上就判錯，3 秒內沒跑完也判錯，這代表複雜度不夠，不是電腦太慢（第 2 課）。

練習 1：寫 runningTotals(cups)：回傳新陣列，第 i 個是前 i + 1 天的杯數總和。cups 可能有負數（退杯），可能是空陣列；不能修改 cups。要求 O(n)。對應 LeetCode 1480. Running Sum of 1d Array。

練習 2：寫 reverseInPlace(queue)：把排隊名單原地反轉（直接修改傳進來的陣列，回傳 void）。不能用內建的 reverse、toReversed、sort，要自己交換元素（判分時這幾個方法會被換成丟錯的函式）。課文要求 O(1) 額外空間，不要複製一份再寫回去（這點判分只看結果）。

練習 3：寫 moveSoldOutToEnd(stock)：原地把所有 0（售完）移到最後，其他品項保持原本的先後順序，回傳 void。要求 O(n) 時間、O(1) 額外空間，不能用 splice、sort、filter（判分時會被換成丟錯的函式）；隱藏測試有 n = 40,000、一半是 0 的計時案例。對應 LeetCode 283. Move Zeroes。

練習 4：寫 removeCancelled(orderIds, cancelledId)：原地移除所有等於 cancelledId 的訂單編號，回傳剩下的數量 k（是數量，不是陣列）。完成後 orderIds 的前 k 個要剛好是保留的訂單（順序不限），k 之後放什麼都可以，不檢查。要求 O(n) 時間、O(1) 額外空間，不能用 splice、filter（判分時會被換成丟錯的函式）。對應 LeetCode 27. Remove Element。

練習 5：const prices = [80, 110]，接著讀 prices[5] 會怎樣？

✓ JavaScript 讀不存在的索引不會報錯，只會得到 undefined；拿它去加減會變成 NaN，錯誤在很後面才出現。a 錯：那是其他語言（例如 Java）的行為。c 錯：沒開 noUncheckedIndexedAccess 時，prices[5] 的型別就是 number，TypeScript 不會提醒。d 錯：沒有值的格子不會自動變成 0。

練習 6：一個有 n 位顧客的排隊陣列，用 unshift 在最前面插入一位 VIP，成本是多少？

✓ 陣列的格子要連在一起、索引從 0 開始，在最前面插入，原本索引 0 的要變成 1、1 要變成 2……n 個元素都要搬。a 錯：push 放在尾端，不用動到其他元素，才是（攤銷）O(1)。b 錯：沒有任何「每次砍半」的動作。常常要從前面加入或取出時，用索引指標或別的資料結構（第 12 課的佇列）。

練習 7：下面的函式有什麼問題？

function sortedPrices(prices: number[]): number[] {
  return prices.sort((a, b) => a - b)
}

✓ sort 是原地排序，回傳的就是傳進來的那個陣列，這是副作用。改成 [...prices].sort(…) 或 prices.toSorted(…)，參數也宣告成 readonly number[] 讓 TypeScript 幫你擋。b 錯：有沒有 return 跟有沒有副作用無關。c 錯：a - b 是由小到大。

練習 8：for (let i = 0; i < arr.length; i++) 裡看到要刪除的元素就 arr.splice(i, 1)，為什麼連續兩個要刪的元素會漏掉一個？

✓ 刪除會讓後面的元素往前搬一格，原本在 i + 1 的元素現在在 i，而 i++ 直接去看 i + 1。a 錯：一次刪一個沒問題，問題在索引。c 錯：splice 不知道你的迴圈變數。就算刪除時不 i++，每次 splice 也要搬動後面的元素，整體 O(n²)；用讀寫指標一次走完是 O(n)。

常見錯誤

  • 迴圈寫成 i <= arr.length：最後多讀一個 undefined，不會報錯，結果變成 NaN，就是累計杯數多出一列的原因。從頭走用 i < n，從尾走從 n − 1 開始。
  • 修改了不該修改的輸入：sort、reverse、splice 都會改原陣列。先問清楚能不能改；不能改就把參數宣告成 readonly，需要時先複製或用 toSorted。
  • 以為把新陣列指定給參數就是原地修改：stock = stock.filter(…) 只改了區域變數，外面的陣列沒變。要改格子：stock[i] = …。
  • 邊走邊 splice：刪掉後下一個元素搬到目前的索引，i++ 就跳過它，連續兩個要刪的會漏一個；就算修好也是 O(n²)。改用讀寫指標。
  • 交換時沒有暫存：a[i] = a[j]; a[j] = a[i] 會讓兩格變成一樣。用暫存變數或 [a[i], a[j]] = [a[j], a[i]]。
  • 反轉或配對時走滿整個陣列：每一對被處理兩次，又換回原狀。只走 Math.floor(n / 2) 次。

小結

  • 陣列是一排連在一起的格子，索引是「離第一格有幾格」，合法範圍是 0 到 n − 1：用索引讀寫 O(1)，在開頭或中間插入、刪除 O(n)，push／pop 攤銷 O(1)。
  • JavaScript 越界不報錯：讀到 undefined、拿去計算變成 NaN，寫入讓陣列變長；TypeScript 預設也不提醒，邊界要自己守。
  • 三種迴圈：i < n 往後、從 n − 1 到 0 往前、i < Math.floor(n / 2) 配對兩端。
  • 前一步的結果能拿來用，就不要每次從頭算：累計杯數從 O(n²) 變 O(n)。
  • 回傳新陣列沒有副作用但多 O(n) 空間；原地修改省空間但會改到呼叫端的資料。資料是別人的就回傳新陣列，題目沒說就問。
  • 讀寫指標：讀指標走過每一格，寫指標記住下一個保留的元素放哪，O(n) 時間、O(1) 額外空間，取代邊走邊 splice。
  • 交出去之前跑一次邊界表：空陣列、一個元素、全部要刪、沒有要刪、連續要刪、頭尾。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：面試時你寫完禮券題的雙迴圈暴力解，也說了它是 O(n²)。面試官問「能更快嗎？」，你下一步先做什麼？

✓ 七步的第 4 步是找重複的工作：先說出暴力解在重複做什麼，改進的方向就出來了（第 5 課用 Map 記住看過的價格）。a 錯在題目要回傳索引，排序後索引對不回原本的位置，還會改到傳進來的陣列。c 的 find 本身就是迴圈，還是 O(n²)。（第 1 課）

練習 10：回傳每天的累計杯數（新陣列），n ≤ 10⁵。哪個寫法可以交出去？

✓ 第 i 天的累計 = 前一天的累計 + 當天，前一步的結果拿來用，O(n²) 變 O(n)。b 最多人選：slice 和 reduce 各是一個迴圈，map 每一圈都要走 i + 1 格，跟 a 一樣是 O(n²)。a 錯在代進去是 10¹⁰ 步，會逾時。（第 2、3 課）

練習 11：這段程式的時間和額外空間複雜度是？

function firstRepeat(ids: readonly number[]): number | null {
  for (let i = 0; i < ids.length; i++) {
    if (ids.indexOf(ids[i]) !== i) return ids[i]
  }
  return null
}

✓ 最壞情況是沒有重複：第 i 圈的 indexOf 從頭找到 i，總共 1 + 2 + … + n，O(n²)；沒有建新陣列，只用了 i，額外空間 O(1)。b 最多人選：只有一個 for，但 indexOf 是藏在一行裡的迴圈。改成 Set 記住看過的編號是 O(n) 時間、O(n) 空間（第 4 課）。（第 2 課）

練習 12：queue 有 n 筆訂單，handle 是 O(1)。這段的時間複雜度是？

while (queue.length > 0) {
  const order = queue.shift()
  handle(order)
}

✓ 陣列的索引要從 0 開始連續，取走第一格後剩下的每一格都要搬：(n − 1) + (n − 2) + … ≈ n² / 2。a 最多人選：迴圈只跑 n 次，但 shift 本身是 O(n)。佇列很大又常取時，改用索引指標往後走，或第 12 課的佇列。（第 2、3 課）

練習 13：寫 activeOrders(orders) 給 Vue 元件用，orders 是父元件透過 props 傳進來的陣列，要去掉已取消的訂單。怎麼寫？

✓ 資料是別人的（props、store、參數）就不要改；原地修改留給「資料是我建立的，而且大到複製會吃記憶體」的情況。b 最多人選：O(1) 空間沒錯，但父元件的資料被改掉了。c 只改了區域變數，呼叫端拿不到結果。題目沒講時，面試就先問「可以修改傳進來的陣列嗎？」。（第 3 課）

練習 14：這個函式在哪個輸入會回傳錯的結果？

function maxOrder(totals: number[]): number | null {
  let best = totals[0]
  for (let i = 1; i < totals.length; i++) {
    if (totals[i] > best) best = totals[i]
  }
  return best
}

✓ 空陣列時 totals[0] 是 undefined，回傳 undefined 而不是 null；越界不報錯，TypeScript 預設也把它當 number，不會提醒。開頭加 if (totals.length === 0) return null。a 最多人選：那是初始值寫 0 的錯，用第一個元素當初始值就沒問題。（第 1、3 課）

練習 15：把 0 移到最後的讀寫指標版本，補 0 的迴圈寫成這樣。哪個輸入會出錯？

let write = 0
for (let read = 0; read < stock.length; read++) {
  if (stock[read] !== 0) stock[write++] = stock[read]
}
for (let i = write + 1; i < stock.length; i++) stock[i] = 0

✓ write 那一格就是第一個要補 0 的位置，從 write + 1 開始會漏一格：[0, 1] 變成 [1, 1]。只有元素往前搬過，那格才會留著舊資料，所以其他三組都剛好對。a 最多人選：全部是 0 時沒有東西被搬動，索引 0 本來就是 0。邊界表每一列都要在腦中跑，不能只挑看起來最極端的。（第 3 課）

練習 16：面試時，你的程式在面試官給的一組 8 個元素的輸入上答案錯了。下一步怎麼做？

✓ 小輸入才手算得完；逐步表格裡第一個不一樣的那一列，就是錯的地方。邊做邊把對照講出來，面試官看得到你的除錯方法。b 最多人選：改到這組過了不代表修對，可能只是把錯誤搬到別的輸入。a 錯在還不知道錯在哪，重寫的版本也可能有同樣的問題。（第 1 課）
