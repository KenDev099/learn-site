階段 5：遞迴與樹 · 第 16 課

二元樹 DFS

咖啡店的後台要做一個「分類管理」頁。菜單是一層一層分的，跟第 15 課菜單管理頁用的是同一種資料，但這一頁規定每個分類最多分成兩個子分類（原因在第一節），所以咖啡和茶先收進「飲品」：「全部」底下有「飲品」和「甜點」，「飲品」底下有「茶」和「咖啡」，「咖啡」底下還有「冷萃」。這個頁面要回答三個問題：這份菜單最多有幾層（側邊選單要預留幾層縮排）；展示櫃改裝後要整個左右對調，資料怎麼跟著翻；兩個品項最近的共同分類是哪一個（例如「冷萃」和「茶」都屬於「飲品」，飲品的折扣兩者都能套用）。三個問題都得把整份菜單走過一遍才答得出來，而第 15 課的遞迴正好能處理這種「裡面還有同樣形狀的東西」的資料。

這課就用這份菜單當貫穿的例子，從「它在程式裡長什麼樣」一路做到三個問題都有答案，最後再看遞迴走這種資料要付出多少記憶體。

這課的路線：
  1. 菜單分類樹在程式裡長什麼樣：樹的名詞，以及節點寫成物件的樣子。
  2. 怎麼走過每一個節點：深度優先的前序、中序、後序，以及「菜單有幾層」的最小答案。
  3. 怎麼從子樹的答案算出整棵樹的答案：樹題共用的範本，正式算出菜單有幾層；再拿同一個範本把展示櫃左右對調，看它用來修改樹時的陷阱。
  4. 要的答案跟上一層需要的值不一樣時怎麼辦：最遠的兩個節點（直徑）；接著找兩個品項最近的共同分類。兩題都是面試常考題。
  5. 遞迴走樹佔多少記憶體：很長的回覆串這種歪斜的樹什麼時候會爆，怎麼改寫。
這課會用到：
  • 第 15 課的遞迴：先寫終止條件，再假設小一號的問題已經會算，只想這一層怎麼組合；每層呼叫在呼叫堆疊佔一框，太深會丟 RangeError。
  • 第 13 課的節點：每個節點是一個物件，用 next 存下一個節點的參考；樹的節點改成 left、right 兩個。

菜單分類樹在程式裡長什麼樣？

要讓程式回答開場的三個問題，先得把菜單放進程式裡。菜單的形狀是：一個分類底下掛著幾個子分類，子分類底下又掛著子分類，一路往下，直到最底下的品項。你每天寫的 Vue 元件也是這個形狀：App 底下有 Header、OrderList，OrderList 底下有很多 OrderItem；DOM、資料夾、留言串都一樣。這種形狀叫做樹（tree）。

樹由兩樣東西組成。一個一個的分類叫節點（node）；「飲品底下有咖啡」這種上下關係，畫成一條線把兩個節點連起來，這條線叫邊（edge）。樹有一個重要的限制：沒有環。從任何一個節點往下走，都不會繞回自己。菜單也是這樣，「咖啡」不可能同時又是「冷萃」的子分類。這個限制讓我們可以放心地「一路往下走」，不用擔心走不完。

這課只看二元樹（binary tree）：每個節點最多有兩個子節點，分成左邊那個和右邊那個。左右是有分的：一個節點只有左子節點，跟只有右子節點，是兩棵不同的樹。實際的菜單一個分類可能有五、六個子分類，這課先限制成最多兩個，因為面試題幾乎都用二元樹，而且「左、右」兩個欄位寫起來最短；換成任意多個子節點時寫法怎麼改，這一節最後的「💡 實務上」會講。

看著圖認識幾個名詞，後面每一節都會用到：

  • 最上面那個節點叫根（root），它沒有父節點。這棵樹的根是 1（全部）。一個節點也沒有的樹叫空樹，在程式裡它的根就是 null。
  • 一條邊上面的節點是下面那個節點的父節點（parent），下面的是子節點（child）。2（飲品）是 5（咖啡）的父節點。
  • 沒有任何子節點的叫葉節點（leaf），通常就是實際的品項：4、7、6。
  • 任何一個節點，連同它底下所有的節點，本身也是一棵樹，叫做以它為根的子樹（subtree）。以 2 為根的子樹就是圖上虛線框的「飲品」整區：2、4、5、7。這件事是整課的關鍵：既然每個子樹自己也是一棵樹，處理整棵樹的函式就能拿來處理子樹，這就是第 15 課的遞迴。
  • 從根往下走到某個節點經過幾條邊，叫這個節點的深度（depth），也就是它在第幾層。根在第 0 層，7（冷萃）的深度是 3。
  • 從某個節點往下，最長的那條路上有幾個節點，叫這個節點的高度（height）。葉節點的高度是 1，空樹是 0。2 的高度是 3（2→5→7），根的高度是 4，也就是整棵樹的高度。開場的「菜單最多有幾層」，問的就是根的高度。

💡 實務上：工作中的樹多半是「多個子節點」，而且常常要自己組出來
前端每天都在走樹：DOM、React 元件樹、巢狀留言、咖啡店後台的「分類 → 子分類 → 品項」側邊選單。這些樹的節點通常是 children: Node[]，不是 left／right，寫法一樣，只是把「走左、走右」換成用迴圈走每個子節點。另一個常見情況是資料庫或 API 給的是扁平的列表（每筆帶 parentId），要先用 Map 依 id 建索引、把每筆掛到父節點底下，才有樹可以走；這課的分類管理頁實際上就是這樣拿到菜單的。資深工程師接到這種需求會先問：最多幾層？會不會有 parentId 指到不存在的資料或繞成環？這些決定了要不要加防呆。

菜單已經在程式裡了，但三個問題都還沒答。它們有一個共同點：每個節點都得看過。下一個問題就是：怎麼保證每個節點都剛好走到一次，不漏也不重複？

怎麼走過每一個節點？深度優先的三種走訪

「每個節點都拜訪剛好一次」叫做走訪（traversal）。陣列的走訪很簡單，一個 for 迴圈從頭到尾；樹沒有「頭到尾」的順序，一個節點走完後有兩條路可以選，選了左邊，右邊得記著回來走。

最自然的做法是：先一路往下走到底，走不下去了，退回上一個岔路，改走另一條。這種「先往深處走」的走法叫深度優先搜尋（depth-first search，簡稱 DFS）。用菜單來想：先進「飲品」，再進「茶」，茶底下沒東西了，退回飲品，改進「咖啡」，再進「冷萃」……飲品整區走完，才退回「全部」去走「甜點」。

「記得退回去」這件事聽起來需要自己記錄走過的岔路，但用遞迴寫就不用：上一節說過每個子樹自己也是一棵樹，所以「走完整棵樹」可以拆成「走完左子樹，再走完右子樹」，而走子樹用的是同一個函式。函式呼叫回傳時，自然回到呼叫它的那一層，「退回岔路」由呼叫堆疊替你記住：

走訪(node)：
  如果 node 是 null → 什麼都不做（終止條件）
  走訪(node.left)
  走訪(node.right)

終止條件是 null：走到葉節點底下那個不存在的子節點時，什麼都不做直接回傳。葉節點本身不需要特別處理，它的左右都是 null，兩次呼叫都立刻回來。

這個骨架只是「走」，還沒有「做事」。處理一個節點（例如把它的值放進結果）可以放在三個位置：兩次遞迴之前、中間、之後。三種走法的名字就是從這裡來的：

名稱處理自己的時機上圖的順序
前序（preorder）左右子樹之前：自己 → 左 → 右1 2 4 5 7 3 6
中序（inorder）左右子樹中間：左 → 自己 → 右4 2 7 5 1 3 6
後序（postorder）左右子樹之後：左 → 右 → 自己4 7 5 2 6 3 1

三種都是先左後右，走過的路徑完全一樣，只差在「什麼時候把自己記下來」。這點很容易誤會成三種不同的路線，所以下面的範例在同一次走訪裡把三個時機都印出來。菜單樹有 7 個節點，每個節點印三行就有 21 行，不好對照；這裡先用 1、2、3 三個節點的小樹看清楚三個時機，看懂後再回到菜單樹。縮排表示遞迴的深度（呼叫堆疊上有幾層）；執行後看每個節點的三行分別出現在什麼時候：

節點 1 的「到達」最先印出來，「右邊走完」最後才印出來，中間夾著兩個子節點的全部輸出。前序在「到達」時記下自己，所以父節點排在子節點前面；後序在「右邊走完」時才記，所以子節點全部排在父節點前面。

把三個位置分開寫，就是三個函式。以前序為例：結果陣列 out 放在外層，遞迴的小函式 walk 往裡面 push。這樣每次呼叫 preorder 都有一個新的 out，不會跟上一次混在一起。執行後對照上面表格的前序那一欄：

三個時機怎麼選，看「處理自己的時候，需不需要子樹的資訊」：

  • 前序：處理自己時還不需要子節點的資訊。例如印出有縮排的分類清單：先印「飲品」，再印它底下的「茶」「咖啡」；或是複製一棵樹：先建出自己，再把複製好的子樹接上來。
  • 中序：用途比較窄。第 18 課會教二元搜尋樹，那種樹的每個節點，左子樹的值都比它小、右子樹的值都比它大；在它上面走中序，剛好是由小到大的順序。其他時候用得少。
  • 後序：要先知道子樹的答案才能算自己。例如資料夾的總大小，要先算完每個子資料夾；刪除一整個資料夾，要先刪裡面的東西。

開場的「菜單有幾層」屬於後序：一個分類往下有幾層，要先知道它的左右子樹各有幾層，取比較多的那邊，再加上自己這一層；空樹是 0 層。寫成一行就是 1 + Math.max(左邊的層數, 右邊的層數)，這就是第一個問題的最小答案。但它跟上面的 preorder 有一個根本的差別：preorder 的遞迴不回傳任何東西，只往外面的陣列 push；算層數卻需要子樹「把答案交回來」。下一節就把這種寫法整理成一個範本。

怎麼從子樹的答案算出整棵樹的答案？

上一節最後的算層數，遞迴函式不是只「走過」節點，而是讓每個子樹回傳一個答案，再由自己把兩個答案組合起來。樹的遞迴題大多長這個樣子，可以整理成一個範本。這就是第 15 課說的「相信遞迴」：假設對左右子樹呼叫同一個函式，已經拿到了正確答案，你只要想這一層怎麼把它們組合起來：

function solve(node) {
  if (node === null) return 空樹的答案      // 1. 終止條件：先想空樹
  const l = solve(node.left)                // 2. 左子樹的答案
  const r = solve(node.right)               // 3. 右子樹的答案
  return 用 l、r、node.val 組合出來的答案    // 4. 自己的答案（後序）
}

組合發生在兩個遞迴呼叫之後，所以這個範本是一次後序走訪。寫之前先回答兩個問題：空樹的答案是什麼？知道左右兩邊的答案後，自己的答案怎麼算？兩題都答得出來，程式就是四行；答不出來，代表題目還沒想清楚，硬寫也會錯。

為什麼先想空樹？因為遞迴最後一定會走到 null，空樹的答案是所有答案的起點。它寫錯的話，葉節點拿到的 l、r 就錯，葉節點的答案錯，它的父節點跟著錯，一路錯到根。

菜單有幾層

拿範本正式解開場的第一個問題（練習 2）：菜單分類樹最多有幾層，也就是根的高度，數節點，只有根時是 1，空樹是 0。（對應 LeetCode 104. Maximum Depth of Binary Tree）

  • 空樹的答案：沒有任何層，0。
  • 知道左子樹有 l 層、右子樹有 r 層時：自己這一層，加上比較深的那一邊，1 + Math.max(l, r)。

手算時從葉節點往上填：葉節點的左右都是空樹，拿到 0 和 0，回傳 1；它的父節點拿到這個 1，再加上自己的 1。下面的範例把每個節點回傳的值印出來，執行後看兩件事：印出的順序就是上一節表格的後序（4 7 5 2 6 3 1），而且每個節點都是等兩個子樹回報完才算出自己的值：

最後一行是根：左邊「飲品」回報 3 層、右邊「甜點」回報 2 層，取 3 再加 1，菜單有 4 層，側邊選單要預留 4 層縮排。每個節點只算一次，時間 O(n)。空間是遞迴的深度，等於樹的高度，最後一節再談。

到這裡範本只用來「讀」樹：每個節點回報一個數字，樹本身沒有被改動。開場的第二個問題不一樣，它要把整棵樹改掉。同一個範本能不能拿來修改樹？

展示櫃左右對調

題目（練習 3）：店裡的展示櫃照分類樹排列，改裝後要左右對調：每個節點的左右子樹交換，而且交換過去的子樹自己也要翻轉，就像照鏡子。要直接修改原本的樹，這叫原地修改（in-place），最後回傳根。（對應 LeetCode 226. Invert Binary Tree）

套範本回答兩個問題。空樹翻轉之後還是空樹，回傳 null。知道左右子樹各自翻轉後的結果時，把它們交換掛回來：翻好的右子樹掛到左邊，翻好的左子樹掛到右邊。邏輯沒有問題，但最直覺的寫法有個陷阱。錯誤只發生在同一個節點的兩行之間，用三個節點的小樹，輸出一行就看得出 2 不見了；修正版再用整棵菜單樹驗證。先看錯誤的版本，執行後比較「原本」和「錯誤」兩行：

兩邊都變成了 3，2 不見了。原因在兩行的先後：

  1. 第一行把 node.left 換成翻轉後的右子樹（3）。原本的左子樹（2）沒有任何變數再指著它，從此拿不到了。
  2. 第二行要把「原本的左子樹」翻好掛到右邊，但它讀的 node.left 已經是第一行剛放進去的 3，所以右邊也是 3。

這跟第 13 課反轉鏈結串列「改 next 之前先把下一個節點存起來」是同一件事：覆蓋一個參考之前，先把還要用的存下來。修正的做法是照範本的順序來：先把兩邊的答案都算好、存在變數裡，最後才修改 node。執行後看兩件事：整棵菜單樹都翻過來了，而且回傳的還是原本那個根物件：

也可以用解構一行交換：[node.left, node.right] = [mirror(node.right), mirror(node.left)]。它不會踩到同一個陷阱，因為右邊的陣列會先整個算完，才指定給左邊。

最後一行印出的 true 也是題目的要求。原地修改代表回傳的必須是原本的根物件。另外建一棵新的樹，形狀雖然一樣，但呼叫端手上拿的還是舊的參考，舊的那棵完全沒變（TypeScript 課第 2 課的值與參考）。

💡 實務上：React 的狀態樹通常不原地改
演算法題要求原地修改，但在 React（或 Redux 這類狀態管理）的狀態裡，直接改節點的 left、children 常會出事：React 比較的是參考，根物件沒換就不會重新渲染；其他畫面拿著同一個物件，也會被「偷偷」改到。實務上的做法是只複製從根到被改節點那條路徑上的節點，其他子樹沿用原本的參考，例如在咖啡店後台把某個子分類改名或搬家。寫樹的函式前先確認呼叫端預期的是「改原本的」還是「回傳新的」，並在函式名稱或註解寫清楚。

兩題用的都是同一個範本，而且有一個共同點：函式回傳給上一層的值，剛好就是最後要的答案。層數題回傳層數，翻轉題回傳翻好的子樹。如果這兩樣東西不一樣呢？

要的答案跟上一層需要的不一樣時怎麼辦？

這一題（練習 4）不是分類管理頁的需求，但它正好卡在範本的極限，面試也很常考：樹中任意兩個節點之間，最長的路徑有幾條邊？這個長度叫樹的直徑（diameter）。（對應 LeetCode 543. Diameter of Binary Tree）

先想一條路徑長什麼樣。路徑從某個節點出發，往上爬，在某個節點轉彎，再往下走到另一個節點。轉彎的那個節點是整條路徑上最高的點。反過來說，只要固定「最高點是 node」，以它為最高點的最長路徑，就是從 node 往左一路走到最深、加上往右一路走到最深。

「往左走到最深有幾條邊」剛好可以用「菜單有幾層」那一小節算的高度（數節點的那種）：從 node 往左下走，第一步走到左子節點，之後再走的邊數比左子樹的高度少 1，加起來正好等於左子樹的高度（數節點的那種）。右邊也一樣。所以：

以 node 為最高點的最長路徑 = 左子樹高度 + 右子樹高度

直徑就是每個節點算出來的這個值裡，最大的那個。為什麼要每個節點都算，不能只算根？在菜單樹上看不出差別，它的最長路徑剛好經過根（冷萃 7 → 咖啡 5 → 飲品 2 → 全部 1 → 甜點 3 → 蛋糕 6，5 條邊）。所以這裡換一棵左邊很深、右邊很淺的樹，它的最長路徑不經過根：

只算根會得到 5，但以 2 為最高點的路徑有 6 條邊。最高點可能是任何一個節點，所以每個節點都要算一次 l + r，取最大的。

一次走訪同時算出高度和直徑

最直接的寫法是：對每個節點，呼叫上一節的 maxDepth 算左右子樹的高度，相加，再取所有節點裡最大的。這樣一定對，但很慢。每次呼叫 maxDepth 都要把整個子樹走完一遍。想像一條很長的鏈，底下掛著一大棵樹：鏈上每個節點都會呼叫 maxDepth，每次都把底下那一大棵重走一遍。總工作量變成「節點數 × 高度」，寫成 O(n × 高度)；樹歪成一條線時高度就是 n，最壞 O(n²)。

重複的工作是「高度」被一直重算。其實算高度的那一次後序走訪，在每個節點都已經拿到 l 和 r 了，順手算一下 l + r 就好，根本不用另外再走。

卡住的地方是：函式只能回傳一個值，而這裡有兩個不同的東西。

  • 回傳給上一層的是高度。上一層要用它算自己的高度，也要用它算自己的 l + r。路徑往上延伸時只能選左右其中一邊（不能兩邊都帶上去，那就不是一條路徑了），所以上一層需要的是「比較長的那一邊」，也就是高度。
  • 最後要的答案是所有節點裡最大的 l + r。路徑可以在這個節點轉彎，所以是左加右。

做法是讓函式照常回傳高度，另外把答案放在外層的變數 best，遞迴每到一個節點就順便更新它。內層的遞迴函式讀寫得到外層的 best，靠的是閉包：內層函式記得外層函式的變數（TypeScript 課第 1 課）。用上面那棵不經過根的樹，執行後看 best 在哪個節點變成 6，以及每個節點回傳給上一層的高度：

到了節點 2，左高 3 + 右高 3 = 6，best 變成 6；之後根的 4 + 1 = 5 比較小，best 不變，但根照樣回傳自己的高度 5。每個節點只走一次，時間 O(n)。

差多少？下面用一條 1,000 個節點的鏈、底下接一棵 20,000 個節點的樹，比較「每個節點重算高度」和「一次走訪」兩種寫法。執行後看兩行的答案一樣，但時間差很多：

「回傳一個值給上一層、同時更新外面的答案」是樹題最常見的進階形狀，之後會碰到的「路徑總和的最大值」（LeetCode 124）也是它。寫之前先分清楚兩件事：上一層需要什麼（只能選一邊往上延伸，所以是高度），和最後要的是什麼（可以在這裡轉彎，所以是左 + 右）。

best 要宣告在函式裡面。寫在最外層的話，第二次呼叫時 best 還留著上一棵樹的答案；測試會連續呼叫好幾棵樹，只有第一棵對。

到目前為止，每個節點往上回報的都是數字：層數、高度。開場的第三個問題要找的卻是「某一個節點」：兩個品項最近的共同分類。往上回報的東西換成節點，範本還用得上嗎？

兩個品項最近的共同分類在哪裡？

題目（練習 5）：給樹的根和樹中兩個不同的節點 p、q，找它們的最近共同祖先（lowest common ancestor，簡稱 LCA）。一個節點的祖先，是從它往上走會經過的所有節點；p 和 q 共同的祖先裡，最下面的那一個就是最近共同祖先。這題有一個約定：節點也算自己的祖先，所以 p 在 q 上面時，答案就是 p。（對應 LeetCode 236. Lowest Common Ancestor of a Binary Tree）

用菜單樹手算三組：

  • 7（冷萃）和 4（茶）：冷萃往上是咖啡、飲品、全部，茶往上是飲品、全部，最先碰到的共同節點是 2（飲品）。開場說「飲品的折扣兩者都能套用」，就是這個答案。
  • 7（冷萃）和 5（咖啡）：咖啡本身就是冷萃的祖先，又算自己的祖先，答案是 5。
  • 4（茶）和 6（蛋糕）：一個在飲品、一個在甜點，只有根 1（全部）是共同的。

手算時是「從 p 和 q 各自往上走」，但程式做不到：節點只有 left、right，沒有指向父節點的參考，不能往上走。所以改成由下往上回報，也就是用範本：讓函式回傳「在這棵子樹裡找到的東西」。找到的可能是 p 或 q，也可能是已經確定的答案；什麼都沒找到就回傳 null。依照範本的順序想四種情況：

  1. 空樹：什麼都沒有，回傳 null。
  2. 自己就是 p 或 q：直接回傳自己，不用再往下找。如果另一個在自己底下，答案就是自己（節點也算自己的祖先）；如果另一個不在自己底下，上面的某個節點會從另一邊找到它，再由那個節點決定答案。兩種情況，往下找都沒有幫助。
  3. 否則問左右子樹。兩邊都不是 null：p、q 分在自己的左右兩邊，往上走時最先在自己這裡會合，自己就是最近共同祖先，回傳自己。
  4. 只有一邊不是 null：把那一邊的結果往上傳。它可能是 p、q 其中一個（另一個還沒找到，交給上面處理），也可能是下面已經找到的答案（原封不動傳到根）。兩邊都是 null，代表這棵子樹裡沒有 p 也沒有 q，回傳 null。程式裡的 l ?? r 一次涵蓋這兩種情況。

判斷「自己是不是 p 或 q」用的是 node === p，比較的是物件參考，不是值。實際的資料常有重複的值，例如飲品和甜點底下都有一個叫「季節限定」的分類；只比 val 的話，遇到第一個同名的節點就會停在錯的地方。每個節點最多走一次，時間 O(n)。

💡 實務上：同一棵樹裡比參考，跨請求比 id
LCA 的實務版本是「兩個分類最近的共同上層」，例如後台判斷兩個品項能不能套用同一個上層分類的折扣，或權限系統判斷兩個部門的共同主管。在同一棵記憶體中的樹裡比 === 沒問題；但資料從 API 重新抓回來後，每個節點都是新的物件，拿舊的參考去比一定找不到。這時要比唯一的 id，而不是 name 這種可能重複的顯示欄位。如果樹很大又常常查，可以讓每個節點記住父節點（或存 parentId，再用 Map 依 id 找到父節點），直接往上走，不用每次從根找一遍。

開場的三個問題都解完了，每一個都是 O(n) 時間，而且沒有建任何陣列或 Map。那它們用了多少記憶體？答案不是 O(1)。

遞迴走樹佔多少記憶體？

這課的每個函式都沒有建新陣列，但不是 O(1) 空間。第 15 課說過，每一層遞迴都在呼叫堆疊上佔一個堆疊框，函式回傳時才拿掉。走 DFS 時，堆疊上同時存在的，是「從根到目前這個節點」那一條路上的每一層呼叫；走到最深的葉節點時最多，層數等於樹的高度。所以額外空間是 O(樹的高度)，跟節點總數沒有直接關係：

樹的形狀高度遞迴 DFS 的額外空間
平衡（每層幾乎都填滿），例如 100 萬個節點約 log₂ n ≈ 20O(log n)
歪成一條線（每個節點只有一個子節點）nO(n)

面試時說複雜度要寫成 O(h)（h 是高度），再補一句「平衡時 O(log n)、最壞 O(n)」。菜單只有 4 層，完全不用擔心；但歪斜的樹在實務上不少見：依時間順序一筆一筆接下去的回覆串、照遞增順序插入的二元搜尋樹（第 18 課），都會變成一條線。這時遞迴太深，會丟第 15 課的 RangeError。

解法是不用呼叫堆疊，改用自己的堆疊（第 12 課：只從頂端放入、拿出，後放的先拿）。遞迴時，「還沒走的右子樹」由呼叫堆疊記住；改成迴圈後，把還沒處理的節點自己 push 進一個陣列，每一輪 pop 出一個來處理。先 push 右邊、再 push 左邊，下一輪 pop 出來的就是左邊，順序跟前序一樣。下面用一條 10 萬層的線比較兩種寫法，執行後看遞迴那行失敗、自己的堆疊那行正常數完：

為什麼一個會爆、一個不會？自己的堆疊是一個普通陣列，跟其他物件一樣放在一般的記憶體裡，幾百萬個元素也放得下；呼叫堆疊則是引擎替函式呼叫預留的一塊固定大小的空間，上限小得多，而且依引擎而定。

這不代表遞迴不好。深度在幾千層以內時遞迴最好讀，面試也預設用遞迴。判斷的依據是資料從哪裡來：自己控制形狀的樹（菜單、元件樹）用遞迴；使用者上傳的巢狀 JSON、可能被刻意做成很深的資料，改用自己的堆疊，或先限制深度。第 20 課的圖與網格會再用到這個寫法。本課練習的樹高度都在約 1,000 以內，遞迴可以通過。

練習

每題的隱藏測試會用固定案例和幾百棵隨機產生的樹比對參考解，練習 4 最後還會用大資料量計時；「花了 … ms」的訊息代表複雜度不夠。起始程式附的 treeFrom、treeToArray 只是方便你自己試，測試不會用你的版本。除了練習 3，傳進來的樹都不能修改。

練習 1：寫 preorder(root)、inorder(root)、postorder(root)，各自回傳節點值依前序、中序、後序排成的陣列；空樹回傳 []。preorder 已經搭好外殼，補上 walk 的內容，另外兩個自己寫。

練習 2：寫 maxDepth(root)：回傳菜單分類樹的層數（數節點：只有根是 1，空樹是 0）。用「左右子樹的答案組合」的範本。測試裡有一棵往左歪、高度 1,000 的樹。（對應 LeetCode 104. Maximum Depth of Binary Tree）

練習 3：寫 mirror(root)：把樹左右翻轉（每個節點的左右子樹交換，子樹本身也要翻轉）。直接修改傳進來的樹，回傳原本的根物件；空樹回傳 null。（對應 LeetCode 226. Invert Binary Tree）

練習 4（進階）：寫 widestSpan(root)：回傳樹中任意兩個節點之間最長路徑的邊數；空樹和只有一個節點都回傳 0。最長路徑不一定經過根。要 O(n)：測試最後會用一條 1,000 個節點的鏈、底下接 50,000 個節點的樹計時，每個節點都重算高度的寫法會不通過。（對應 LeetCode 543. Diameter of Binary Tree）

練習 5（進階）：寫 nearestSharedCategory(root, p, q)：p、q 是樹中兩個不同的節點，回傳它們的最近共同祖先節點（節點也算自己的祖先）。節點的值可能重複，請比較節點參考。（對應 LeetCode 236. Lowest Common Ancestor of a Binary Tree）

練習 6：用遞迴走訪一棵 n 個節點的二元樹，程式裡沒有建立任何陣列或 Map。額外空間是多少？

✓ c。每一層遞迴佔一個堆疊框，同一時間堆疊上只有「根到目前節點」那一條路上的呼叫，所以是高度 h。沒有 new 東西不代表不佔空間（a 錯）。只有平衡的樹才是 log n，一條線的樹高度就是 n（b 錯）。節點走完就會從堆疊拿掉，不會全部同時在堆疊上（d 錯，除非樹本身是一條線）。

練習 7：二元樹的最長路徑（直徑）一定經過根嗎？

✓ a。路徑的最高點可以是任何節點，例如左子樹裡的節點 2 左右各有 3 層，經過它的路徑是 6 條邊，而經過根的只有「左高 4 + 右高 1 = 5」。b 只說對了「要從左邊到右邊必須經過根」，但最長路徑不需要跨到右邊；c 跟節點數無關。所以每個節點都要算 l + r，取最大的。

練習 8：前序、中序、後序走訪的差別是什麼？

✓ b。三種走過的路徑完全一樣，只差在什麼時候把自己記下來。要先知道子樹的結果才能算自己（高度、直徑、共同祖先）就用後序。a 把左右順序當成差別；c 說的「一層一層走」是下一課的 BFS，不是 DFS。

常見錯誤

  • 沒處理 null：讀 node.left 時 node 是 null，丟 TypeError。每個遞迴函式第一行先處理空節點，空樹也一起處理好了。
  • 空樹的答案隨便寫：空樹的答案是所有答案的起點，寫錯的話每一層都跟著錯。先想清楚：層數是 0、路徑是 0、翻轉後是 null、找不到是 null。
  • 翻轉時覆蓋了還要用的子樹：node.left = mirror(node.right) 之後原本的左子樹就拿不到了。先把兩邊的結果存進變數，或用解構一次交換。
  • 每個節點都重算高度：O(n × 高度)，一條長鏈接一大棵樹就變慢。在算高度的同一次走訪裡順便更新答案。
  • 答案變數放在函式外面：第二次呼叫還留著上一次的值。best 宣告在外層函式裡面，讓內層的遞迴函式用閉包更新。
  • 深度與高度、節點數與邊數搞混：maxDepth 數節點，直徑數邊。重述題目時就確認，再用「只有一個節點」的案例檢查。
  • 比較值而不是節點：值會重複，找特定節點時用 === 比較參考；資料跨請求重新抓回來時改比唯一的 id。
  • 以為遞迴不佔空間：空間是 O(h)。資料可能很深（使用者上傳的巢狀資料）時，改用自己的堆疊。

小結

  • 菜單分類樹是一棵樹：二元樹的每個節點有 left、right 兩個參考，空樹是 null。根、葉、子樹、深度、高度要能對著圖說出來；每個子樹自己也是一棵樹，所以能用遞迴處理。
  • DFS 先往下走到底再回頭，回頭由呼叫堆疊記住。前序、中序、後序都是先左後右，走過的路徑一樣，差在處理自己的時機；需要子樹的結果才能算自己時用後序。
  • 樹題的範本：先寫空樹的答案，再假設左右子樹已經算好，只想這一層怎麼組合。菜單有幾層是 1 + max(l, r)；用範本修改樹（左右對調）時，先把兩邊的結果存好再覆蓋參考。
  • 上一層需要的值跟最後要的答案不同時（直徑：回傳高度、答案是最大的 l + r），讓函式回傳前者，用閉包更新後者，一次走訪做到 O(n)。
  • 最近共同祖先：自己是 p 或 q 就回傳自己；左右都回報非 null 時自己就是答案；比較的是節點參考。
  • 遞迴 DFS 的時間 O(n)、空間 O(h)；平衡時 O(log n)，歪斜時 O(n)，很深的資料改用自己的堆疊。

下一課換一種走法：分類管理頁要「先顯示第一層、展開再顯示下一層」時，DFS 一條一條往下的順序不合用，要用佇列一層一層走（BFS），解「每一層的最右邊」「最淺的葉節點」這類跟層有關的題目。

LeetCode 的層序陣列怎麼讀

LeetCode 把樹寫成層序陣列：從根開始一層一層、每層由左到右列出節點的值，null 表示那個位置沒有節點；只替存在的節點寫出它的兩個子節點位置，最後面多餘的 null 省略。本課的菜單樹寫成：

[1, 2, 3, 4, 5, null, 6, null, null, 7]

第一個值是根。之後從左到右讀，每兩個值是「下一個還沒分配子節點的節點」的左、右子節點，節點依它們在陣列裡出現的順序輪流分配：

陣列片段意思
1根
2, 31 的左、右
4, 52 的左、右
null, 63 沒有左子節點、右邊是 6
null, null4 是葉節點
75 的左；後面 5 的右、6 和 7 的子節點全是 null，放在最後所以省略

練習起始程式附的 treeFrom(陣列) 照這個規則把陣列變成節點、treeToArray(root) 把樹變回陣列，方便你在 LeetCode 的例子和程式之間對照。它們的內部用的是第 17 課的 BFS（用佇列記住「下一個要分配子節點的節點」），現在只要會用就好。
