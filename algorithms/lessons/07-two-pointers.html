階段 3：陣列技巧 · 第 7 課

雙指標：從兩端往中間走

第 5 課的禮券題用 Map 解：一邊走一邊記住看過的價格，對每一杯問「還差多少，看過了嗎」，O(n) 時間，代價是 Map 要多用 O(n) 的記憶體。那一課中段也提過另一條路：價格已經排好時，從兩端往中間找，不用 Map。第 6 課結尾也預告了這一課。這課就把那條路走完：Map 是拿空間換時間，如果手上的資料本來就排好，還需要付這個空間嗎？

這一課的任務就是回答它。後台的價目表是用 SQL 的 ORDER BY price 查出來的，送到你手上時已經由小到大排好。要寫 sortedPair(prices, budget)：一樣找兩杯不同的飲料、價格加起來剛好等於禮券金額，但不開 Map，只用兩個存索引的變數，一個從最便宜的那頭、一個從最貴的那頭，每一步排除掉一杯不可能是答案的飲料，一路走到中間。這個技巧叫雙指標（two pointers）。做完之後，同一副骨架還會拿去解店裡另外三個需求：幸運取餐號碼、甜點櫃的展示區、套餐組合。四題要回答的都是同一個問題：這一步憑什麼可以放心丟掉那一邊？說得出這句話，程式就不會寫錯方向。

這課的路線：
  1. 價目表已經排好，Map 還是最好的做法嗎、加總太大時憑什麼丟掉最貴那杯：從兩端往中間走，每一步丟掉一杯，O(1) 額外空間做完 sortedPair（開場問題的答案），並整理出對撞指標的骨架。
  2. 同一副骨架換一個理由：取餐號碼是不是迴文，順便處理手打號碼裡的空白和大小寫。
  3. 迴圈條件寫 left < right 還是 <=：兩個指標碰在一起那一圈該不該跑。
  4. 不是找剛好而是找最大、三個數怎麼拆回兩數和：最大展示區為什麼移動矮的那片，三數和怎麼變成「固定一個＋雙指標」，都是常見面試題。
  5. 遇到新題目怎麼判斷：該用雙指標還是 Map。
這課會用到：
  • 第 5 課的 Two Sum：用 Map 記住看過的價格，對每一杯問「還差多少看過了嗎」，O(n) 時間、O(n) 額外空間。
  • 第 3 課的索引與邊界：長度 n 的陣列最後一個索引是 n − 1，越界讀到 undefined 不會報錯。

價目表已經排好，Map 還是最好的做法嗎？

先把資料擺出來。這是後台依價格排好的價目表，禮券是 170 元：

prices = [70, 80, 90, 110, 110, 120]   // 可頌、美式、伯爵紅茶、拿鐵、卡布奇諾、起司蛋糕
budget = 170

第 5 課的 Map 解法照樣能用，答案也對：O(n) 時間、O(n) 額外空間。暴力解（每一組都試）不用額外空間，但要比 n(n − 1) / 2 組，n 一大就太慢。兩種做法都沒有用到「已經排好」這件事。Map 解法拿到亂序的陣列也一樣跑，排好序對它來說是白給的資訊。

排好序到底多給了什麼？它保證最左邊是最便宜的、最右邊是最貴的，而且往右只會越來越貴。這表示只要看兩端，就知道「目前範圍裡最小的值」和「最大的值」是多少，不用掃過整個陣列。雙指標就是要把這個資訊用起來。

做法需要兩個變數記住「現在看到哪裡」。這種存著索引的變數，在演算法題裡習慣叫指標（pointer）。它跟 C 語言裡存記憶體位址的指標無關，就是一個普通的數字變數，例如 let left = 0，意思是「左邊現在指著索引 0」。這題用兩個指標：left 從最便宜的索引 0 開始，right 從最貴的索引 n − 1 開始。兩個指標之間（含兩端）就是「還有可能是答案的範圍」。

第一步看兩端：70 + 120 = 190，比 170 大。現在要做一個決定：移動 left 還是 right？直覺可能會說「隨便動一個，反正要縮小範圍」。但動錯了會漏掉答案，所以這個決定需要一個理由，下一節就來證明它。

加總太大時，憑什麼可以直接丟掉最貴的那杯？

上一節停在 70 + 120 = 190 太大。來問一個具體的問題：right 指的這杯 120 元，還有沒有機會跟範圍裡的某一杯湊出 170？

範圍裡最便宜的是 left 指的 70 元（陣列排好序，左端就是最小值）。120 跟最便宜的配都已經 190、超過了；換成跟範圍裡任何其他一杯配，那杯只會比 70 貴，加總只會比 190 更大。所以 120 跟誰配都太大，它不可能是答案的一部分，可以丟掉：right--。注意這個結論不是「試過 120 的每一種配法」得出來的，而是用排序的性質一次推出來的。

三種情況整理起來：

  • 剛好：找到了，回傳 [left, right]。
  • 太大：right 跟範圍裡最小的值配都太大，跟誰配都太大。丟掉 right：right--。
  • 太小：反過來，left 跟範圍裡最大的值配都不夠，跟其他人配只會更小。丟掉 left：left++。

如果方向寫反會怎樣？太大時改動 left，換上來的是一杯更貴的飲料，加總只會更大、離答案更遠；更糟的是被丟掉的 70 元可能正是答案的一半，答案就這樣漏掉了，而且程式不會報錯，只會回傳 null。

這種「先證明某個部分不可能有答案，就不再檢查它」的做法叫剪枝（pruning），像修剪樹枝一樣，整根剪掉就不用再看上面的葉子。暴力解要把每一組都試過；雙指標每丟掉一杯，就等於一次剪掉「這杯和其他所有飲料的配對」一整排組合，所以最多 n − 1 步就走完。下面把整個過程畫出來：

同樣的過程用程式跑一次，執行後看最後一行：雙指標看了幾次，暴力解最壞要看幾次。

寫程式之前，先用一句話說出「為什麼可以丟掉這一邊」：太大時，right 跟範圍裡最小的配都太大，跟誰配都太大。說不出來，通常就是方向寫反了。太大時移動 left 只會讓加總更大。

價格重複也不用特別處理。例如 [80, 80]、禮券 160：left = 0、right = 1 是兩杯不同的 80 元飲料，第一步就剛好，回傳 [0, 1]。雙指標比的是兩個不同的位置，值一樣沒關係。

到這裡 sortedPair 就做完了：沒有 Map，只用了 left、right 兩個變數。把剛才的「決定」抽掉，剩下的就是對撞指標（一頭一尾往中間靠）的骨架，這課後面每一題都長這樣：

let left = 0
let right = arr.length - 1
while (left < right) {
  // 看 arr[left] 和 arr[right]，決定：
  //   找到答案 → 回傳
  //   left 不可能是答案 → left++
  //   right 不可能是答案 → right--
}

為什麼一定是 O(n)？每一圈至少移動一個指標，兩個指標之間的距離每次至少少 1，一開始距離是 n − 1，所以最多走 n − 1 圈：O(n) 時間。全程只用了兩個變數：O(1) 額外空間。這就是開場問題的答案：資料已經排好時，不用付 Map 的 O(n) 空間。

💡 實務上：先確認「排好序」是誰保證的
這課的價目表來自資料庫查詢的 ORDER BY，這也是工作中最常遇到的已排序資料，例如依價格排好的商品列表、依時間排好的訂單。寫雙指標前先確認排序是查詢或 API 規格明確保證的，不是剛好看起來有排；哪天有人改了查詢，雙指標不會報錯，只會悄悄漏掉答案。資料量只有幾十、幾百筆時（像咖啡店的菜單），Map 或甚至雙迴圈都夠快，選大家一眼看得懂的寫法就好。資深工程師在 code review 會問：「這個順序是誰保證的？資料量會長到多大？」答得出來，才值得為省記憶體換寫法。

骨架裡真正難的是中間那個「決定」，也就是丟掉一邊的理由。兩數和的理由靠排序；換一個題目，理由就會不一樣。下一節先看一個理由最直白、而且根本不需要排序的例子。

同一副骨架換一個理由：取餐號碼是不是迴文？

上一節的骨架能不能用在沒排序的資料上？可以，只要每一步仍然說得出「為什麼可以丟掉」。這裡換一個例子，是因為價目表的例子只示範了「靠排序丟」，看不出骨架本身跟排序無關；另外手打的資料會混進要跳過的字元，這是兩數和沒有的狀況。

咖啡店想在取餐號碼裡挑「幸運號碼」：正著讀和反著讀一樣的號碼，送一份可頌。這種字串叫迴文（palindrome），例如 'ABA'、'1221'。號碼是店員手打的，會混進空白、破折號，大小寫也不一定。動手前先把規則講清楚：

要問的問題這一課的答案
哪些字元要比較？只有英文字母和數字，合稱英數字元（alphanumeric）；其他字元（空白、-、_、標點）全部跳過
大小寫算不算一樣？算，'A' 和 'a' 一樣
數字和字母可以互相比嗎？可以比，但不會相等：'0P' 不是迴文
空字串、全部是符號呢？清理後什麼都不剩，算迴文，回傳 true

所以 'A-12-1a' 是迴文：去掉符號、轉小寫後是 'a121a'。

最直接的寫法：清理、反轉、比較

先寫一個一定對的版本：把英數字元挑出來、轉小寫，再把它反轉，跟原本的比。會用到兩個字串工具：s[i] 讀出第 i 個字元（索引從 0 開始，超出範圍得到 undefined）；s.toLowerCase() 回傳全部轉成小寫的新字串，原本的字串不變。執行後看每個號碼清理後、反轉後長什麼樣子：

isAlnum 判斷一個字元是不是英數字元，用的是正規表示式（TypeScript 課第 5 課）/^[a-z0-9]$/i：^ 和 $ 表示整個字串從頭到尾，[a-z0-9] 表示一個 a～z 或 0～9 的字元，結尾的 i 表示不分大小寫。合起來是「整個字串剛好是一個英數字元」。不要寫成 /\w/：\w 除了英數字元還包含底線 _，'ab_a' 本來是迴文（去掉底線是 aba），用 \w 會把底線留下來比，誤判成不是迴文。

這個解法是對的，時間 O(n)，但建了兩個新字串和兩個陣列，額外空間 O(n)。這跟價目表遇到的是同一個問題：答案對，但多付了空間。取餐號碼很短無所謂，面試官通常會接著問：「可以不複製嗎？」

雙指標：從兩端往中間比

反轉後再比，其實就是在比「第 1 個和倒數第 1 個、第 2 個和倒數第 2 個……」。那就不用真的反轉，直接用兩個指標比：

  1. left 指向開頭、right 指向結尾。
  2. left 指到符號就往右跳過；right 指到符號就往左跳過。跳的時候也要守住 left < right，否則全部是符號時會一路跳出字串。
  3. 兩邊都停在英數字元上，轉小寫比較：不一樣就回傳 false；一樣就兩個都往中間走一步。
  4. 兩個指標碰到（或交錯）時，代表每一對都比過了，回傳 true。

這裡丟掉兩邊的理由跟兩數和不一樣：迴文只要求對稱位置的字元相等，left 和 right 這一對比過、相等了，之後再也不會用到它們，所以兩個可以一起丟。不需要排序，也不需要「範圍裡最小的值」這種推理。下面把每一步印出來，執行後看每一行是「跳過符號」還是「比較一對」：

💡 實務上：比較使用者輸入前，先把「正規化規則」講清楚
工作中很少要判斷迴文，但這題前半段做的事，「去掉空白和符號、統一大小寫再比較」，天天都有：顧客輸入的手機號碼、訂單編號、優惠碼、搜尋關鍵字。哪些字元要忽略、全形半形算不算一樣，是產品規則，要跟 PM 確認，不要自己猜。規則寫成一個函式、寫清楚，前端驗證和後端比對都照同一套，否則會出現「前端說格式正確、後端說查無此單」。

到這裡兩題的迴圈條件都寫 left < right。為什麼不是 left <= right？這一個字元的差別，正是對撞指標最常寫錯的地方。

迴圈條件寫 left < right 還是 left <= right？

判斷的關鍵是想清楚 left === right 時代表什麼：兩個指標指著同一個元素。sortedPair 要找兩杯不同的飲料，同一杯不能跟自己配，所以兩個指標碰在一起時就該停，條件是 left < right。寫成 <= 會發生什麼？用兩杯飲料的價目表跑一次，執行後比較兩個版本的最後一行：

<= 的版本在 left = right = 0 時算了 80 + 80，回傳 [0, 0]：同一杯用了兩次。價目表裡只有一杯 80 元的美式，系統卻說「兩杯美式剛好 160」，把同一杯算了兩次，這就是線上 bug。不同題目的判斷方式：

題目條件原因
找兩個不同的元素（兩數和、下一節的最大展示區）left < right相等時只剩一個元素，湊不成一對
迴文left < right相等時是正中間那個字元，它跟自己對稱，不用比；寫 <= 也對，只是多比一次
要處理每一個元素（例如二分搜尋，第 9 課）看題目相等時那個元素還沒檢查過，常常要 <=

用 left < right 時，最短的輸入也自然處理好了。拿迴文來看：空字串時 right = -1，while 一次都不跑，回傳 true；只有一個字元時 left === right，也不跑，回傳 true。兩數和也一樣：空陣列或只有一杯時迴圈不跑，回傳 null。

不確定時，用只有一個、兩個元素的陣列手算一次，看 left === right 那一圈該不該跑。

到目前為止，兩題都在找一個「剛好」的答案：加總剛好等於禮券、字元剛好相等。如果題目要的不是剛好，而是所有組合裡的最大值，雙指標還能放心跳過組合嗎？

不是找剛好，而是找最大：展示區該移動哪一片隔板？

這題要換例子，因為前兩題的「丟掉」都有一個明確的對錯：加總不等於禮券、字元不相等。找最大值時，每一組都有一個面積，沒有哪一組是「錯的」，只有「比較小的」。要證明的事變成：被跳過的組合，面積都不會超過已經看過的最大值。

咖啡店的甜點櫃有一排高度不同的隔板，要選兩片隔板，中間圍出一個展示區放蛋糕。展示區的寬度是兩片隔板的距離（索引相減），能放的高度由比較矮的那片決定（高過矮的那片，蛋糕會滑出去）：

面積 = (right − left) × Math.min(heights[left], heights[right])

例如 heights = [3, 7, 2, 6, 4, 8, 1, 5]，選索引 1（高 7）和索引 7（高 5）：寬 7 − 1 = 6，高 min(7, 5) = 5，面積 30，這是最大的。注意寬度是 right − left，不是 right − left + 1：算的是兩片隔板之間的距離，不是隔板的片數。

暴力解是試過每一組 (i, j)，O(n²)。雙指標的做法：從最寬的兩端開始，每一步移動比較矮的那一邊。理由還是「這一邊不可能更好」，推理分三步：

  • 假設左邊比較矮，高 h。現在的面積是 寬 × h。
  • 如果保留左邊、把右邊往內換成任何一片：寬度一定變小；高度是 min(h, 新的那片)，不會超過 h。寬變小、高不會變大，面積只會更小。所以左邊這片跟範圍裡其他隔板的組合，都不會贏過現在這一組，可以丟掉：left++。
  • 反過來，如果移動的是比較高的那邊，矮的那片還在，高度仍被它卡住，寬度卻變小了，這一步一定不會變好；而且被丟掉的高隔板，可能正是跟更裡面某片高隔板組出最大面積的那一片，答案就錯過了。

兩邊一樣高時，移哪一邊都可以：兩片都不可能跟範圍內的其他隔板組出更大的面積。下面每一步印出寬、高、面積和目前的最大值，執行後看「最大」那一欄在哪一列變成 30：

這題跟兩數和不一樣的地方：雙指標不是在找某個值，而是在所有組合裡找最大值。它沒有試過每一組，但被跳過的組合都已經證明「不會比目前看過的更大」。面試時能把這段推理講出來，比寫出程式更重要。

到這裡處理的都是「一對」。如果要找的是三個數呢？骨架只有兩個指標，第三個數要放哪裡？

三個數加起來是 0：怎麼拆回已經會的兩數和？

店長在檢討菜單定價：每杯飲料的價格減掉目標價，得到一個差額（可以是負數）。想找出所有「三杯差額加起來剛好是 0」的組合，看哪些組合適合做套餐。例如差額 [-2, 0, 1, 1, 2, -3, 3]：

[-3, 0, 3]   [-3, 1, 2]   [-2, 0, 2]   [-2, 1, 1]

這題的輸出規則跟前面不同，先講清楚。這裡要的是值的組合，不是索引：[-2, 1, 1] 只算一組，即使有兩個 1 可以選。每組由小到大排，所有組之間依字典序排列。字典序就是查字典的排法：先比第一個數，第一個一樣再比第二個，依此類推，所以 [-3, 0, 3] 排在 [-3, 1, 2] 前面。

暴力解是三層迴圈試每一組，O(n³)，還要另外去掉重複的組合。改進的想法是把新問題拆成已經會的舊問題：

  1. 先排序（由小到大）。差額本來沒排序，這題又只要值、不要原本的索引，所以排序不會弄丟題目要的東西。
  2. 外層固定第一個數 a[i]。
  3. 剩下的問題是：在 i 右邊找兩個數，加起來等於 −a[i]。這就是 sortedPair，用雙指標 O(n) 解決。差別是 sortedPair 找到一組就回傳，這裡要找出所有組，所以找到後不停，繼續往內走，下面「跳過重複」會講怎麼走。

外層 n 次 × 內層 O(n) = O(n²)。排序是 O(n log n)，只做一次，比 O(n²) 小，被蓋過，所以整體是 O(n²)。

排序一定要給比較函式

第一步的排序就有一個陷阱。JavaScript 的 sort() 沒給比較函式時，會把數字轉成字串再比（細節在第 8 課），負數和多位數會排錯。執行後比較兩行的順序：

雙指標的「太大就丟右邊、太小就丟左邊」建立在真的排好序上，排錯了推理就不成立，答案會漏掉，而且不會報錯。另外 sort 會直接修改原陣列，題目的輸入不能改，要先複製再排：[...diffs].sort((a, b) => a - b)。不改原陣列的另一種寫法見課末。

跳過重複

排序好、會用雙指標了，還剩一件事：結果不能有重複的組合。排序後相同的值會排在一起，重複的組合從兩個地方來，兩個地方都要擋：

  • 外層：a[i] 跟前一個 a[i − 1] 一樣，以它開頭的組合上一圈都找過了，continue。注意是跟前一個比；跟後一個比，[-1, -1, 2] 在 i = 0 就被跳過，等到 i = 1 時右邊只剩一個 2，[-1, -1, 2] 這組就漏掉了。
  • 內層：找到一組之後，left、right 都往內走一步，再把跟剛才一樣的值跳過。只移動一個指標、或沒有跳過相同的值，下一圈可能又找到同一組，結果就重複了。

💡 實務上：前端排序最常出的包是「改到原本的陣列」
這題先複製再排序，是因為輸入不能改；工作中這個習慣一樣重要。商品列表依價格排序、訂單依金額排序，是後台頁面的日常需求。在 Vue 或 React 裡，直接對 props 或 state 呼叫 sort() 會改到別人的資料：父元件的順序跟著變、React 也可能因為陣列參考沒變而不重新渲染。另一個坑是分頁：列表只載入第一頁時，前端排序只排了這 20 筆，「全部訂單依金額排序」要交給後端查詢時排好再分頁。code review 看到沒有比較函式的 sort()，幾乎都值得留言問一句。

四題都用了雙指標，但第 5 課的 Map 也能解兩數和。下次遇到一個沒說用哪一招的題目，要怎麼判斷？

遇到新題目，怎麼判斷該用雙指標還是 Map？

回頭看這課的四題，能用對撞指標的共同點是：每一步都能說出一個「丟掉一邊」的理由。這個理由通常來自兩種結構：資料有排序（兩數和、三數和），或題目本身在比兩端（迴文的對稱、展示區的寬度）。所以看到題目時問自己：

  • 陣列已經排序（或可以排序、而且題目不要原本的索引），要找符合某個加總、差距的一對？→ 對撞指標。
  • 要比較兩端，例如對稱（迴文）、兩端組成的寬度？→ 對撞指標。
  • 要原地處理，不能用額外的陣列？→ 另一種擺法，讀寫指標（第 3 課）。雙指標的其他擺法整理在課末。

這課四題裡，兩數和是 Map 和對撞指標最常被拿來比較的一題，兩者的取捨：

Map（查補數）對撞指標
需要排序嗎不需要需要；沒排序時先排 O(n log n)
時間O(n)O(n)（已排序）／O(n log n)（要先排）
額外空間O(n)O(1)（不算排序要用的複本）
能回傳原本的索引嗎能已排序的輸入能；自己排序後索引就亂了

表格最後一列是關鍵：第 5 課的禮券題輸入沒排序、又要回傳原本的索引，自己排序會把索引打亂，所以用 Map；這課的價目表是後台排好送來的，索引就是價目表上的位置，所以用雙指標。面試的說法可以是：「沒排序、要原本的索引，我用 Map，O(n) 時間、O(n) 空間；如果輸入已經排好，我用雙指標，空間降到 O(1)。」在已排序的陣列上仍用 Map 不算錯，但說不出這個取捨，就少了資深工程師該有的判斷。

雙指標的三種擺法

這一課只講第一種，對撞指標。另外兩種在後面的課會用到，查表用，不用背：

擺法怎麼走例子
對撞指標：一頭一尾left 從 0、right 從最後一個開始，往中間靠近，碰到就停迴文、已排序找兩數和、最大展示區（本課）
讀寫指標：同方向、一快一慢一個讀、一個寫，原地整理陣列原地去重、移除元素（第 3 課）、鏈結串列的快慢指標（第 14 課）
兩個陣列各一個各自往前，每次拿比較小的合併兩個已排序的陣列（第 8 課）

LeetCode 167 回傳 1 開始的位置

本課的 sortedPair 回傳 0 開始的索引。LeetCode 167 的原題規定回傳 1 開始的位置，答案要各加 1，在網站上練習時記得改；這課的練習 2 照本課的約定，回傳 0 開始的索引。

不改原陣列的排序：toSorted

除了先複製再 sort，ES2023 加入了 toSorted：diffs.toSorted((a, b) => a - b) 回傳排好的新陣列，原陣列不變。比較函式的規則跟 sort 一樣，沒給時一樣是字串順序。

練習

傳進來的陣列被凍結了，不能 sort、push，要排序請先複製。練習 2～4 有大資料量的計時測試：雙迴圈或三層迴圈會因為太慢判錯（第 2 課：計時不過就是複雜度不夠）。

練習 1：寫 isPalindromeCode(code)：只看英文字母和數字、不分大小寫，判斷取餐號碼是不是迴文；空字串和全部是符號都算迴文。用左右兩個指標往中間比，不要建立清理後的新字串（課文要求，判分只看結果）。注意底線 _ 是符號。對應 LeetCode 125. Valid Palindrome。

練習 2：寫 sortedPair(prices, budget)：prices 已經由小到大排好（可能重複、可能有負數），找兩個不同的索引 i < j 讓 prices[i] + prices[j] === budget，回傳 [i, j]（0 開始的索引，不是價格）；有多組時回傳從兩端往中間走時第一個碰到的那一組（也就是 i 最小、同一個 i 裡 j 最大的那組）；沒有就回傳 null。要 O(n) 時間、O(1) 額外空間：測試期間不能用 Map、Set，還會跑 4 萬筆、答案在正中間的資料。對應 LeetCode 167. Two Sum II - Input Array Is Sorted（原題回傳 1 開始的位置，這裡是 0 開始）。

練習 3：寫 maxDisplayArea(heights)：heights 是一排隔板的高度，選兩片隔板，面積 = 兩片的距離（索引相減）× 比較矮那片的高度，回傳最大面積；少於兩片回傳 0。要 O(n)：測試會跑 3 萬片隔板的資料。對應 LeetCode 11. Container With Most Water。

練習 4：寫 zeroSumTriples(diffs)：找出所有加總為 0 的三個數（值的組合，不是索引），不能有重複的組合；每組由小到大，所有組依字典序排列；沒有就回傳 []。輸入不能修改。要 O(n²)：先排序，固定一個數，剩下的用雙指標；測試會跑 1,500 個數的資料，三層迴圈會判錯。對應 LeetCode 15. 3Sum。

練習 5：已排序的價目表找兩數和，prices[left] + prices[right] 比預算大，該移動哪個指標？

✓ left 是範圍裡最小的值，right 配它都超過預算，配任何更大的值只會更多，所以 right 可以丟掉。a 錯：left++ 換成更大的值，加總只會更大，離答案更遠，還可能把真正的答案跳過。c 錯：只有 right 被證明不可能，left 還可能跟比較小的 right 配成答案。

練習 6：「雙指標的題目都要先排序」對嗎？

✓ 找和的雙指標靠「太大就丟右邊、太小就丟左邊」，這要排好序才成立。迴文只比較對稱的位置，排序反而會破壞順序；讀寫指標（第 3 課）和最大展示區也不用排序。a 錯在把一種用法當成全部。b 錯：沒排序時找和的雙指標不是變慢，而是推理不成立、會找錯答案；其他雙指標本來就不需要排序，複雜度也還是 O(n)。

練習 7：三數和「先排序，再固定一個數＋雙指標」，整體時間複雜度是多少？

✓ 前後兩段相加取大的：O(n log n) + O(n²) = O(n²)。b 錯：排序只做一次，後面的 n 次雙指標才是大頭。c 錯：雙指標走一遍是 O(n)，但外層要對每個 i 各走一遍。

常見錯誤

  • 移錯邊：兩數和太大時移動 left、最大展示區移動比較高的那邊，都會丟掉可能是答案的元素，而且不會報錯。寫程式前先說出「為什麼可以丟掉這一邊」。
  • 已排序的陣列仍用 Map：結果正確，但多用了 O(n) 空間；面試時要能說出雙指標可以做到 O(1)。
  • 跳過符號時沒有守住 left < right：全部是符號時指標跑出字串，比較到 undefined 或停不下來。
  • 用 /\w/ 判斷英數字元：\w 包含底線 _。用 /^[a-z0-9]$/i。
  • 找兩個不同元素時寫 left <= right：兩個指標相等時是同一個元素，會被用兩次。用 left < right，並用一、兩個元素的陣列手算確認。
  • 排序數字沒給比較函式：預設是字串順序，[-1, -10, 2].sort() 不會由小到大。寫 (a, b) => a - b。
  • 直接排序輸入的陣列：sort 會修改原陣列，呼叫端的資料被改掉。先複製或用 toSorted。
  • 三數和沒有跳過重複：外層跟前一個比，內層找到後兩個指標都往內走並跳過相同的值，否則結果有重複的組合。

小結

  • 價目表已經排好時，sortedPair 不用 Map：left 從頭、right 從尾，每一步丟掉一個不可能的元素，O(n) 時間、O(1) 額外空間。這副骨架叫對撞指標。
  • 每次移動都要能說出理由：兩數和是「太大時 right 跟範圍裡最小的配都太大」、迴文是「這一對比過了」、最大展示區是「矮的那片換不出更大的面積」。
  • 找兩個不同的元素用 left < right；<= 會讓同一個元素用兩次。
  • 三數和：排序（給比較函式、先複製）→ 固定一個 → 雙指標，O(n²)；外層和內層都要跳過重複。
  • 跟 Map 的取捨：沒排序、要原本的索引用 Map（O(n) 空間）；已排序用雙指標（O(1) 空間）。
