階段 8：進階題型（進階） · 第 26 課

拓撲排序

咖啡店後台要加一個功能：店長在後台設定開店備料的規則，系統每天早上排出一份步驟表，店員照著做。現在的規則是：要先磨豆才能萃取濃縮；濃縮和糖漿都好了才能調拿鐵；拿鐵和可頌都好了才能組早餐盒。新來的店員只關心一件事：「我該照什麼順序做，才不會做到一半發現前一步還沒好？」

這個功能還有第二個要求。店長改規則時可能手滑，多設一條「煮糖漿要等組早餐盒」。可是組早餐盒本來就要等調拿鐵、調拿鐵要等煮糖漿，三個步驟互相等待，永遠做不完。系統要在存檔時發現這種錯，並說出卡在哪幾步。排出「每一步開始時，它的前置步驟都已經做完」的順序，就叫拓撲排序（topological sort）。這課從頭到尾都在把這個備料功能做出來；同樣的問題在工作上到處都是：套件的建置順序、建資料表時被外鍵參照的表要先建、排程工作之間的相依。

這課的路線：
  1. 規則畫成有向圖、存成相鄰串列和入度：程式怎麼知道哪個步驟現在能做（開場問題的最小答案）。
  2. Kahn 演算法：用入度和佇列排出整份步驟表，以及為什麼不能每一輪重新掃一遍。
  3. 偵測環：店長把規則設成互相等待時，程式怎麼發現、怎麼說出卡在哪；重複的規則為什麼可能被誤判成環。
  4. 驗證答案與方向錯誤：排出來的順序跟同事的不一樣時誰錯了；驗證不過時，先查邊的方向。
  5. DFS 與三種狀態：在別人的程式裡看到另一種寫法時，認得出來、知道該怎麼選。
這課會用到：
  • 第 20 課的圖：頂點加上邊；用相鄰串列 adj[v] 存每個頂點的鄰居，用 visited 讓每個頂點只處理一次。
  • 第 12 課的佇列：從尾端放入、從前端取出，先進先出；用 head 索引記住下一個要取的位置，不用 shift。

店員該照什麼順序做？先把規則畫成一張圖

店長輸入的規則是一條一條的「做 B 之前要先做 A」。條數少的時候還能用眼睛看，多到十幾條、而且一個步驟要等好幾個步驟時，光讀文字很難看出誰該先做。第 20 課處理過「東西之間有關係」的問題：把東西當成頂點，關係當成邊，就是一張圖。這裡也一樣，每個備料步驟是一個頂點，「做 B 之前要先做 A」畫成一條從 A 指向 B 的邊，寫成 A → B。

跟第 20 課不同的是邊的方向。第 20 課的道路是無向的，A 和 B 之間有路，兩邊都走得通；備料規則有方向，「萃取濃縮要等磨豆」不代表「磨豆要等萃取濃縮」。每條邊都有方向的圖，叫有向圖（directed graph）。這課的箭頭一律從「先做的」指向「後做的」。

有了圖，店員的問題可以說得更精確：把所有步驟排成一列，讓每一條邊 u → v 的 u 都排在 v 前面。這樣的一列就是拓撲排序的結果。上圖的一個答案是 0, 2, 4, 1, 3, 5：照這個順序做，每一步開始時，它的前置步驟都做完了。

開場的第二個要求也能用圖說清楚。在有向圖裡順著箭頭走，如果能走回出發點，這一圈就叫環（cycle）。店長多設的那條「煮糖漿要等組早餐盒」，會讓圖裡出現 煮糖漿 → 調拿鐵 → 組早餐盒 → 煮糖漿 這一圈。有環就排不出順序：環上每個步驟都在等環上的前一個步驟，沒有任何一個能先開始。反過來，邊有方向、而且沒有環的圖，叫有向無環圖（DAG，directed acyclic graph）。規則合理時，畫出來就是一張 DAG，一定排得出拓撲順序。

所以這個功能要回答兩個問題：「排得出來嗎？」也就是有沒有環；以及「排出來的順序是什麼？」。後面每一節都在回答其中一個。

很多團隊把好幾個專案放在同一個 repo 裡管理，這種做法叫 monorepo。工作上會遇到的拓撲排序，大多藏在工具裡：monorepo 裡套件 A 依賴套件 B，就要先建置 B；建資料表時，有外鍵（PostgreSQL 課第 8 課）參照 customers 的 orders 要在 customers 之後建；ES module 的 import 也是先執行被 import 的模組。這些工具內部做的就是這課的演算法（Kahn 或 DFS），看到「circular dependency」（環狀相依）的警告或錯誤，就是它在圖裡找到了環。

💡 實務上：遇到環狀相依，要拆的是相依，不是工具
工作上很少自己寫拓撲排序，比較常遇到的是工具回報環。例如 orders.ts import customers.ts、customers.ts 又 import orders.ts，某個模組初始化時可能拿到還沒準備好的值，出現 undefined 或 ReferenceError，而且換個進入點就不一定重現。常見解法是把兩邊共用的部分抽成第三個模組，讓箭頭只往一個方向走。資料表也一樣：兩張表互相用外鍵參照時，誰都沒辦法先建，常見做法是先建好兩張表，再用 ALTER TABLE 補上其中一條外鍵。code review 時看到「A 和 B 互相 import」，資深工程師會先問：這兩個模組的職責是不是沒分清楚？備料規則的環也是同一個道理，要改的是規則本身。

程式怎麼知道哪個步驟現在能做？相鄰串列和入度

圖是畫給人看的，程式要的是資料。後台存下來的規則是一份相依清單，這課的格式是 [step, before]，意思是「做 step 之前要先做 before」。要注意它把後做的寫在前面，畫成邊是 before → step。LeetCode 的 Course Schedule 也是這個格式（[a, b] 是「修 a 之前要先修 b」）。每一題的格式都可能不同，最保險的做法是拿題目的範例畫一次圖，確認箭頭方向再寫程式。

有了清單，排順序時程式會一直問兩個問題。第一個是「這個步驟現在能做嗎？」，也就是它還有沒有前置步驟沒做完。第二個是「這個步驟做完了，要通知誰？」，也就是哪些步驟在等它。如果每次都回頭翻整份清單，一個步驟就要掃一次全部的規則；所以事先把答案整理成兩樣東西：

  • 入度（in-degree）indeg[v]：回答第一個問題。它是「指向 v 的邊有幾條」，也就是「v 還有幾個前置步驟沒做完」。一開始等於 v 的前置步驟總數，每做完一個前置就減 1。入度 0 代表現在就能做。
  • 相鄰串列 adj（第 20 課）：回答第二個問題。adj[before] 放「做完 before 之後，可能可以開始的步驟」，也就是 before 的箭頭指向誰。

建法是把清單掃一次：每看到一條 [step, before]，就在 adj[before] 放進 step，並把 indeg[step] 加 1。執行後看「入度」那一欄：磨豆、煮糖漿、烤可頌是 0，對應圖上淡色、沒有箭頭指進來的三個步驟。

每條相依只看一次，所以建圖的時間是 O(V + E)：V 是頂點數（步驟數），E 是邊數（相依的數量），後面的複雜度都用這兩個字母。Array.from({ length: n }, () => []) 是第 20 課的寫法，讓每個步驟各自有一個新陣列；寫成 fill([]) 的話，所有步驟會共用同一個陣列，放進一個步驟的鄰居，其他步驟也跟著多出來。

到這裡，開場店員的問題已經有最小版本的答案：先做入度 0 的步驟；每做完一個，就看它的相鄰串列，把後面那些步驟的入度減 1；減到 0 的，代表前置全部做完，就可以開始做。照這個規則一直做下去，每一步開始時前置都已經完成。剩下的問題是：「現在可以做的步驟」要放在哪裡、怎麼一個一個拿出來，才不會漏掉也不會做太多白工。

怎麼排出整份步驟表？Kahn 演算法

上一節的規則，換成店員的動作是這樣：先把「沒有前置步驟」的寫在待辦板上；從板上拿一個來做，做完就去通知它後面的步驟「你的前置少了一個」；某個步驟的前置全部做完（入度變成 0），就寫上待辦板。一直做到板子空了為止。待辦板上放的永遠是「已經可以做、還沒做」的步驟，用第 12 課的佇列存剛好：新的從尾端放入，從前端取出。這套做法叫 Kahn 演算法（Kahn's algorithm）：

  1. 建相鄰串列和入度陣列。
  2. 把所有入度 0 的頂點放進佇列。
  3. 從佇列取出一個頂點 v，加到結果的最後面。
  4. 對 v 的每個鄰居 w：入度減 1；減到 0 就放進佇列。
  5. 重複 3、4 直到佇列空了。

讀表的方式：「減少 3:1」代表步驟 3 的入度減成 1，還在等另一個前置（煮糖漿已經做完、萃取濃縮還沒）；取出 1 之後 3 的入度變 0，才放進佇列。最後一列印出的順序，就是這天早上給店員的步驟表。

每個頂點進出佇列各一次，每條邊在處理它的起點時被減一次，加上建圖，總共 O(V + E) 時間；空間用在相鄰串列、入度和佇列，也是 O(V + E)。

表裡還有一個現象：同一時間待在佇列裡的步驟，入度都是 0，彼此之間沒有先後關係。例如一開始的磨豆、煮糖漿、烤可頌，如果有三個店員，可以同時開工。建置工具也是這樣，把同一批入度 0 的工作同時交給多個工作者執行。

💡 實務上：相依宣告漏了，平行執行時才會爆
monorepo 的建置工具，和每次推送程式碼就自動建置、測試的流程（這種流程叫 CI），兩者的設定檔裡都要寫「這個工作要等哪些工作」，這就是在畫這張圖，工具再照入度 0 的那一批平行跑。常見的坑是漏寫一條相依：在自己電腦上剛好照某個順序跑會過，到了平行執行的 CI 上變成時好時壞（flaky），因為兩個工作誰先完成不一定。排查「偶爾失敗的建置」時，先檢查失敗的那一步用到的東西，是不是都有宣告成相依。反過來，相依也不要為了保險全部串成一條鏈，那樣就失去平行的好處，整條流程變慢。

為什麼要佇列？每一輪掃描全部步驟會怎樣

不用佇列也排得出來：每一輪從頭掃一遍全部步驟，找一個「還沒做、入度 0」的，做完再掃下一輪。結果一樣對，但每輪掃 O(V)、共 V 輪，變成 O(V²)。步驟排成一條長鏈、而且能做的那一個剛好在最後面時最慢。執行後比較 n 加倍時兩種寫法的時間：

n 加倍，掃描的時間大約變成四倍，這是 O(n²) 的特徵（第 2 課）；Kahn 幾乎不動。差別在於佇列「記住哪些已經可以做」：一個步驟的入度變成 0 的那一刻就放進佇列，之後直接取，不用每輪重新找。備料只有六個步驟時感覺不到，但同樣的寫法拿去排幾萬個建置工作就會明顯變慢。

規則正確時，店員已經拿得到步驟表了。但店長把規則設錯、出現環的時候，這段程式會怎樣？它不會報錯，這正是下一節要處理的事。

店長把規則設成互相等待，系統怎麼發現？

上一節的程式遇到環時不會丟錯，也不會無窮迴圈。原因要從環上的入度看：環上的每個頂點，都至少有一條邊來自環上的另一個頂點。那個頂點自己也在等，永遠不會被處理，所以這條邊永遠不會被減掉，入度停在 1 以上，永遠進不了佇列。佇列裡的步驟拿完就停下來，結果是處理完的數量少於 V。所以偵測環不用另外寫一套，只要在最後比一個數字。

下面的範例用三份規則各跑一次：原本的規則、加上店長手滑的那一條、再加一條自己等自己的。執行後看每份規則「處理了幾個」，以及卡住的是哪些步驟：

第二份規則的環是 煮糖漿 → 調拿鐵 → 組早餐盒 → 煮糖漿，只有不在環上、也不被環擋住的磨豆、萃取濃縮、烤可頌做得完。第三份的自己相依自己（[0, 0]）也是環：磨豆的入度是 1，要等自己做完才能做，永遠不會開始。

回報錯誤給店長時要注意，入度還大於 0 的步驟不一定都在環上，也包括「在環之後、被環卡住」的步驟。例如有個步驟要等組早餐盒，它的入度也減不到 0，但它本身沒有錯。要精確說出環是哪幾個步驟，可以這樣找：

  1. 從任一個卡住的步驟出發。
  2. 每次往回走到它「同樣卡住的前置步驟」。每個卡住的步驟至少有一個這樣的前置，否則它的入度早就減到 0 了。
  3. 一直走到重複遇到某個步驟為止。從那個步驟繞一圈回到它自己的這一段，就是環。

面試時通常只要回答 true／false 或回傳空陣列；寫給店長用的功能時，錯誤訊息要印出環的路徑，店長才知道要改哪一條。

處理完的數量少於 V，一定是環嗎？重複的規則

「數量不夠就是環」有一個前提：相鄰串列和入度記的是同一批邊。後台的資料可能把同一條規則存兩次，例如店長按了兩次儲存，[3, 1] 出現兩次。這時有兩種正確的處理：都不去重（adj[1] 放兩次 3，indeg[3] 也加兩次，處理 1 時剛好減兩次）；或兩邊都去重。錯的是只有一邊去重。下面用 3 個步驟、[1, 0] 寫兩次的清單，把四種組合都跑一次，執行後看「處理了幾個」和最後的入度：

只有相鄰串列去重時，步驟 1 的入度是 2，處理 0 時只減一次，停在 1，被誤判成有環；只有入度去重時，入度會減成負數，如果步驟還有其他前置，就會太早開始。實作時不用特別去重，直接「都不去重」最短，也最不容易兩邊不一致。

💡 實務上：讓使用者設定相依的功能，存檔時就要擋環
咖啡店後台讓店長設定「備料步驟要等哪些步驟」，或是簽核流程、任務管理工具裡的「被哪些任務擋住」，都是使用者自己在畫有向圖。比較好的做法是在新增相依、存檔時就跑一次偵測，有環就拒絕這次修改，錯誤訊息說出環的路徑（例如「煮糖漿 → 調拿鐵 → 組早餐盒 → 煮糖漿」）。如果等到隔天早上排程執行時才發現，整批工作已經卡住，也很難知道是誰改的。檢查要放在後端，前端的檢查只是讓使用者早點看到提示。

到這裡，功能能排出順序，也能擋下環。接著要寫測試確認排程功能沒寫錯，馬上會遇到一個問題：同一份規則的正確答案不只一個。

排出來的順序跟同事的不一樣，誰錯了？

同一份備料規則，你的程式排出 0, 2, 4, 1, 3, 5，同事的排出 4, 2, 0, 1, 3, 5，兩個都可能是對的。原因在圖上：磨豆、煮糖漿、烤可頌互相沒有先後關係，誰先誰後都可以，所以合法的順序有很多個，0, 1, 2, 3, 4, 5 也對。只有整張圖是一條長鏈（每一步都依賴上一步）時，答案才唯一。

這會影響兩件事。第一，面試時要主動說「答案不唯一，我回傳其中一個」。第二，測試不能拿固定的答案比對，否則換一個同樣正確的實作，測試就失敗。正確的做法是寫一個驗證函式，直接檢查拓撲排序的定義有沒有成立：

  • 長度等於步驟數，沒有漏掉的步驟。
  • 每個步驟剛好出現一次，沒有重複，也沒有不存在的編號。
  • 每條相依的 before 都排在 step 前面。

驗證函式說「不合法」時，要回頭查排序的程式哪裡錯了。拓撲排序最常見的錯誤，是把相依清單的方向讀反。

💡 實務上：需要穩定的輸出時，自己決定平手的順序
合法順序不只一個，代表程式改一點（佇列換堆疊、相依清單的順序變了），輸出就可能不同。如果結果會被人看到或存起來，順序每次跳動會讓 diff 很難讀，也讓人以為有東西改了。例如後台顯示給店員的備料清單、會進版本控制的檔案，或是資料庫 migration：migration 是一支支修改資料表結構的腳本，工具自動排出的執行順序如果每次不同，就很難比對。這時可以規定平手時照名稱或編號排（做法見課末「補充與查表」的 min-heap），讓同樣的輸入永遠得到同樣的輸出。只是內部執行、沒人在意順序時，就不用多付這個成本，測試也照這節的方式驗證性質。

驗證不過時，先查什麼？邊的方向

方向讀反，是指把 [step, before] 寫成 adj[step].push(before)、indeg[before]++，等於把每條邊都反過來。原本的圖有環，反過來的圖也有環；原本沒有，反過來也沒有。所以「能不能完成」還是答對，但排出來的順序剛好倒過來，最後才做的變成第一個。更常見的是只反了一半：相鄰串列反了、入度沒反，這時連能不能完成都會算錯。下面用同一份備料規則跑三種建圖方式，執行後看每一列處理了幾個、順序從哪一步開始：

「全部反過來」從組早餐盒開始做，每條相依都違反，上一節的驗證函式會抓到。「只反了一半」更糟：圖裡沒有環，卻只處理了 3 個，回報「做不完」。放到備料功能上，就是店長存了一份完全合理的規則，系統卻說有環、拒絕存檔。

防止的方法很樸素：寫程式前拿題目的範例畫一次圖，確認箭頭從「先做的」指向「後做的」；寫完用一條最短的相依 [1, 0] 手算一次，應該得到 [0, 1]。

到這裡，整個備料功能都用 Kahn 演算法寫完了。但讀別人的程式、或面試官提示另一種解法時，常會看到拓撲排序用 DFS 寫，而且那種寫法有自己的陷阱。

別人用 DFS 寫拓撲排序，看得懂嗎？三種狀態

拓撲排序也可以用第 20 課的 DFS 做。這一節只講概念，讓你在面試或別人的程式裡看到時認得出來；練習用 Kahn。

DFS 版本找環的方式，是順著邊往下走，看會不會繞回自己這條路上。問題是只用 visited 不夠。visited 只分得出「走過」和「沒走過」，但「走過」有兩種意思：還在這條路上（走訪中，它的後續還沒走完），和已經完成（它後面的全部走完了、確定沒有環）。順著邊碰到「走訪中」的頂點，代表繞回了自己這條路，才是環；碰到「已完成」的頂點，只是兩條路會合。最簡單的例子是菱形：兩條路都通往同一個頂點，但沒有環。執行後看兩種寫法對同一張菱形圖的判斷：

只用 visited 的寫法，從 0 走 1 再走到 3，回頭從 2 又碰到 3，就以為繞了一圈。三種狀態的寫法知道 3 已經完成，不是環。

DFS 版本的順序從「完成順序」來：一個頂點要等它指向的所有頂點都完成，自己才算完成。所以「後做的」一定比「先做的」早完成，把完成順序倒過來，先做的就排在前面，正好是拓撲順序。

兩種做法的時間都是 O(V + E)。怎麼選：

Kahn（入度＋佇列）DFS（三種狀態）
偵測環處理完的數量 < V碰到「走訪中」的頂點
步驟很多、鏈很長沒問題，只用一個陣列當佇列遞迴深度等於鏈長，幾千層就可能 RangeError（第 15 課），要改成自己的堆疊，寫起來比 Kahn 繞
容易犯的錯忘了檢查處理完的數量只用 visited、忘了把完成順序倒過來

面試建議寫 Kahn：步驟固定、不會遞迴太深（第 15 課：呼叫堆疊有上限，太深會丟 RangeError）、偵測環只要比一個數字。看到題目出現「先後」「相依」「前置條件」「排出順序」「有沒有環狀相依」，就想到拓撲排序。

補充與查表

  • 佇列換成堆疊也對：放進去的都是「現在可以做」的步驟，先做哪一個都合法，只是排出來的順序不同（堆疊版的結果是 4, 2, 0, 1, 3, 5）。
  • 「編號小的優先」或要穩定的輸出：把佇列換成第 19 課的 min-heap，每次取最小的那個。V 個頂點各進出 heap 一次，時間變成 O(V log V + E)。
  • 出度（out-degree）：從一個頂點指出去的邊數，跟入度相對。Kahn 演算法用不到，但題目或文件可能會提到。
  • 名稱由來：Kahn 演算法是 Arthur Kahn 在 1962 年發表的。

練習

三題的相依清單格式都是 [step, before]：「做 step 之前要先做 before」，步驟編號 0 到 n − 1。隱藏測試會用固定案例和幾百個隨機產生的相依清單比對參考解，傳進來的陣列都會被凍結（不能修改）。練習 2、3 的測試期間 Array.prototype.shift 會丟錯，佇列請用 head 索引；最後還有計時（n = 25,000 的長鏈）和 50,000 個步驟的長鏈，「花了 … ms」代表複雜度不夠，「呼叫堆疊爆了」代表不要用遞迴。

練習 1：寫 indegrees(n, prereqs)，回傳長度 n 的陣列，第 v 格是步驟 v 的入度（有幾個前置步驟）。同一條相依出現兩次就算兩次；沒有前置步驟的是 0。

練習 2：寫 canFinishPrep(n, prereqs)：n 個備料步驟，判斷能不能全部完成（沒有環狀相依就是 true）。要求 O(n + 相依數)，用 Kahn 演算法，佇列用 head 索引。（對應 LeetCode 207. Course Schedule）

練習 3：寫 prepOrder(n, prereqs)：回傳任一個合法的備料順序（包含全部 n 個步驟，每個剛好一次，每條相依的 before 都在 step 前面）；有環狀相依時回傳 []，不要回傳做到一半的順序。答案不唯一，測試用驗證函式判分。（對應 LeetCode 210. Course Schedule II）

練習 4：同事寫了拓撲排序的測試：assert.deepEqual(prepOrder(6, rules), [0, 2, 4, 1, 3, 5])。後來他把佇列改成堆疊，結果變成 [4, 2, 0, 1, 3, 5]，測試失敗了。怎麼看？

✓ c。0、2、4 彼此沒有先後關係，誰先都可以，所以兩個順序都合法。放進佇列或堆疊的都是「現在可以做」的步驟，先拿哪一個都不違反相依（a 錯）；只有整張圖是一條鏈時順序才唯一（b 錯）。d 把測試綁在實作細節上，換個實作又會壞，而且真正的錯（順序違反相依）還是要靠驗證才抓得到。

練習 5：相依清單有環時，Kahn 演算法會發生什麼事？

✓ b。環上每個步驟都在等環上的另一個步驟，那個步驟永遠沒被處理，這條邊就永遠不會被減掉，所以它進不了佇列。佇列只會變短，不會無窮迴圈（a 錯）；每條邊只在處理起點時減一次，入度不會減成負數（c 錯）；一個步驟只有在入度剛好變成 0 的那一次放進佇列，不會重複（d 錯）。要自己比較處理完的數量和 n，才知道有沒有環。

練習 6：相依 [3, 1] 的意思是「做 3 之前要先做 1」。建圖時應該怎麼寫？

✓ a。Kahn 演算法做完一個步驟後，要通知「後面等它的步驟」，所以 adj[1] 要放 3；入度是「還有幾個前置步驟」，加在 3 身上。b 只反了一半：3 的入度是 1，但 adj[1] 是空的，做完 1 時沒有人去減 3 的入度，3 永遠進不了佇列，沒有環也會回報做不完。c 是全部反過來，能不能完成會答對，但排出來的順序剛好相反，每條相依都違反。

常見錯誤

  • 邊的方向反了：[step, before] 的邊是 before → step，入度加在 step。寫之前拿範例畫一次圖，寫完用 [1, 0] 手算，應該得到 [0, 1]。
  • 只反了一半：相鄰串列和入度用了不同的方向，沒有環也會回報做不完。
  • 沒檢查處理完的數量：有環時 Kahn 不會報錯，只會安靜地停下來；不比較數量就會回傳 true，或回傳做到一半的順序。
  • 用固定答案測試：拓撲順序通常不唯一，要寫驗證函式檢查長度、不重複、每條相依的先後。
  • 沒有相依的步驟漏掉：一開始要把 0 到 n − 1 每個入度 0 的步驟都放進佇列，不能只看相依清單裡出現過的。
  • 重複的相依只在一邊去重：相鄰串列和入度要一致，最簡單是都不去重。
  • 每輪掃描全部步驟找入度 0：O(V²)。用佇列記住已經可以做的。
  • DFS 只有 visited：分不出「走訪中」和「已完成」，會把菱形誤判成環；步驟很多時遞迴還會超出呼叫堆疊。

小結

  • 「先做 A 才能做 B」畫成有向邊 A → B；沒有環的有向圖叫 DAG，拓撲排序把它排成每條邊的起點都在終點前面的一列，也就是店員照著做不會卡住的步驟表。
  • 入度是「還有幾個前置步驟沒做完」，相鄰串列是「做完之後要通知誰」。Kahn 演算法：入度 0 的放進佇列，取出一個就把鄰居的入度減 1，減到 0 再放進佇列；O(V + E)。每輪重新掃描找入度 0 是 O(V²)。
  • 有環時環上的入度永遠不會變 0，處理完的數量 < V 就代表有環。自己相依自己也是環。讓使用者設定相依的功能，存檔時就在後端擋下環，並說出環的路徑。
  • 拓撲順序通常不唯一：測試寫驗證函式，面試時主動說明；需要穩定輸出時自己決定平手的順序。
  • 先確認相依清單的方向，相鄰串列和入度用同一個方向、重複的邊兩邊一致；驗證不過時先查方向。
  • DFS 也能做，要用三種狀態，完成順序倒過來就是答案；步驟多時遞迴太深，面試建議寫 Kahn。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 7：爬樓梯每次走 1 或 2 階，問走到第 n 階有幾種走法，先 1 後 2 和先 2 後 1 算不同走法。用湊金額的 DP 寫，迴圈該怎麼排？

✓ b。題目說先後不同算不同，要的是排列數；外層階數時每一階都問最後一步是哪種，n = 4 得到 5 種，也就是 dp[i] = dp[i − 1] + dp[i − 2]。a 是組合的寫法，1+1+2 和 2+1+1 只算一次，只得到 3 種。重述題目時先確認順序不同算不算不同。（第 24 課）

練習 8：這段最長遞增子序列（嚴格遞增）的程式，哪個輸入會回傳錯的答案？

function longestRise(prices: readonly number[]): number {
  const n = prices.length
  if (n === 0) return 0
  const dp = new Array<number>(n).fill(1)
  for (let i = 0; i < n; i++)
    for (let j = 0; j < i; j++)
      if (prices[j] < prices[i]) dp[i] = Math.max(dp[i], dp[j] + 1)
  return dp[n - 1]
}

✓ c。dp[i] 是「以第 i 個結尾」的最長長度，c 的 dp 是 [1, 2, 2, 3, 1]，最後一格是 1，正確答案是 3（2 → 5 → 7）。改成回傳整個 dp 的最大值。d 不會錯：持平不算上漲，答案本來就是 1。（第 24 課）

練習 9：對每一天，回傳它之後所有天裡最高的杯數，最後一天回傳 0。n 最多 10⁵，該怎麼做？

✓ a。要的是右邊「全部」裡最大的，不是「第一個」更大的；從後往前走，先把目前的最大值當這天的答案，再用這天更新，O(n)、不用堆疊。b 回答的是往右第一個更多的那天，[1, 3, 2, 5] 第 0 天會得到 3，正確是 5。c 排序後就分不出哪些天在「之後」。（第 25 課）

練習 10：面試題是「每一天要再等幾天才會賣得更多」。你先寫出雙迴圈暴力解，範例都對，面試官說 n 最多 10⁵、要在 1 秒內。下一步？

✓ c。暴力解遇到一路遞減的資料最慢，約 n² / 2 次，1 秒跑不完；單調堆疊每個索引最多 push、pop 各一次，O(n)。a 錯在只看平均，複雜度要說最慢的情況，break 對遞減的資料沒有幫助。b 排序會打亂天的順序，答案的天數差就算不出來了。（第 25 課）

練習 11：同事的拓撲排序沒有用佇列，而是每一輪從頭找入度 0 的步驟（adj、indeg 已正確建好）。時間複雜度是？

const used = new Array<boolean>(n).fill(false)
const order: number[] = []
while (order.length < n) {
  let v = 0
  while (v < n && (used[v] || indeg[v] !== 0)) v++
  if (v === n) return []                 // 找不到入度 0 的：有環
  used[v] = true; order.push(v)
  for (const w of adj[v]) indeg[w]--
}
return order

✓ a。每加一個步驟就從 0 重新掃描，n = 25,000 的長鏈約 3 億次，加上每條邊只減一次，是 O(V² + E)。b 只數了放進 order 和減入度，沒數每一輪的掃描。修法是用佇列記住入度剛變成 0 的步驟，回到 O(V + E)；空間兩種寫法都是 O(V + E)。（第 26 課）

練習 12：這段判斷能不能做完全部步驟（adj、indeg 照 before → step 正確建好），哪個輸入會回傳錯的答案？

const queue = [...new Set(prereqs.map(([, before]) => before))]
  .filter(v => indeg[v] === 0)
let head = 0
while (head < queue.length) {
  const v = queue[head++]
  for (const w of adj[v]) if (--indeg[w] === 0) queue.push(w)
}
return queue.length === n

✓ b。佇列只從相依清單裡出現過的 before 挑，沒有任何相依的步驟 2 不會被放進去，處理 2 個 < 3，沒有環也回報做不完。一開始要掃 0 到 n − 1 每個步驟。c 不會錯：重複的相依在相鄰串列和入度都算了兩次，兩邊一致；d 有環，回傳 false 本來就對。（第 26 課）
