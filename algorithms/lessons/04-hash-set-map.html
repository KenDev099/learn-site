階段 2：雜湊表 · 第 4 課

雜湊表與集合：查找、去重、計數

咖啡店每天打烊後，收銀機會匯出當天的訂單資料。店長請你寫一支「打烊對帳」程式，做三個檢查：訂單編號有沒有重複（重複代表同一筆被刷了兩次）、每種飲料代碼各賣了幾杯、櫃台開的單和吧台的出餐單品項是否一致。

第一版你用最直覺的寫法：走過每一筆訂單，用 includes 問「這個編號前面出現過了嗎？」。測試時幾十筆一下就跑完，週年慶那天匯入兩萬多筆就明顯變慢；資料再多 10 倍，等待時間會變成大約 100 倍。這一課從這個「越查越慢」開始，弄懂雜湊表為什麼查一次只要看一格，再用 JavaScript 的 Set 和 Map 把三個檢查寫完，並避開用一般物件 {} 計數時會出的錯。

這課的路線：
  1. 「這個編號看過了嗎？」為什麼越查越慢：includes 放在迴圈裡為什麼是 O(n²)，換成 Set 差多少（先看答案）。
  2. 雜湊表怎麼做到只看一格：自己做一個迷你版，看懂雜湊函式、桶、碰撞，以及平均 O(1) 要付出的記憶體。
  3. 檢查一：用 Set 找出重複的訂單編號（LeetCode 217）。
  4. 檢查二：用 Map 數每種飲料賣幾杯；代碼來自外部時 {} 為什麼會算錯，鍵是陣列時為什麼查不到。
  5. 檢查三：用頻率表比對兩張出餐單（LeetCode 242），只比 Set 為什麼不夠。
這課會用到：
  • 第 2 課的 O(1)、O(n)：includes 要從頭比到尾，是 O(n)；放在迴圈裡就變 O(n²)。
  • TypeScript 課第 19 課的泛型：Map<string, number> 角括號裡寫的是鍵和值的型別。

「這個編號看過了嗎？」為什麼越查越慢

先看第一版到底做了多少事。陣列的 includes(x) 從第 0 格開始，一格一格跟 x 比，比到相同或走完整個陣列才停。陣列有 n 筆，最壞要比 n 次，所以是 O(n)。

對帳時，走到第 i 筆訂單要問「前面那 i 筆裡有沒有這個編號」：第 1 筆比 0 次、第 2 筆比 1 次、第 3 筆比 2 次……全部加起來大約 n² / 2 次，就是 O(n²)。程式裡只寫了一層 for，但 includes 本身是一個藏在一行裡的迴圈。兩萬筆時，大約要比兩億次。

下面兩段程式做同一件事：檢查兩萬筆全部不重複的編號。全部不重複是最壞的情況，因為每次都找不到、每次都要走完。第一段用陣列記住看過的編號，第二段用 Set。Set 是 JavaScript 內建的容器，用來存一群不重複的值，可以用 has 問某個值在不在裡面；用法在檢查一會細講，這裡先看它快多少。執行後比較兩行印出的毫秒數（數字每次跑會有些不同）：

兩段的寫法幾乎一樣，只是 includes 換成 has、push 換成 add，花的時間卻差了很多倍。差別不在寫法，在資料怎麼存：陣列只能從頭找；Set 的內部是一種叫雜湊表（hash table）的結構，查一個值平均只看一格，跟裡面已經存了多少筆無關，也就是平均 O(1)。每一步從 O(n) 變 O(1)，整個迴圈就從 O(n²) 變 O(n)。

這就是開場問題的答案：把「在陣列裡找」換成「在雜湊表裡查」。這也是面試題裡最常見的一步改進。但「只看一格」是怎麼做到的？不懂原理，就說不清楚它什麼時候會變慢、要付出什麼代價。下一節自己做一個來看。

雜湊表怎麼做到「只看一格」？

上一節的陣列慢，是因為不知道要找的東西在哪一格，只好每一格都看。如果有一個規則，能直接從「要找的東西」算出「它放在第幾格」，就不用從頭找了。

想像一個有很多格抽屜的櫃子。每個名字都用固定的規則算出「該放第幾格」：存的時候算一次、放進那一格；查的時候用同一個規則再算一次，直接打開那一格看。同樣的名字一定算出同樣的格號，所以存和查一定會找到同一格。不管名單多長，都只看一格。這就是雜湊表。先把它的四個零件叫出名字，後面會一直用到：

  • 鍵（key）：拿來查的東西，例如顧客名字、訂單編號。
  • 值（value）：查到的內容，例如這位顧客今天點了幾杯。
  • 雜湊函式（hash function）：把鍵轉成一個數字的規則。同樣的鍵一定得到同樣的數字，這是存和查會算到同一格的原因。
  • 桶（bucket）：櫃子裡的一格。雜湊函式算出的數字除以桶數取餘數，就是桶的編號。

下面寫一個很陽春的版本，看清楚裡面在做什麼。這裡先用六位顧客的名字當鍵，不用訂單編號：名字比數字好認，比較看得出誰跟誰擠在同一格。雜湊函式把名字每個字的編碼加起來，再除以 7 取餘數，所以有 7 個桶（編號 0～6）。每個桶是一個小陣列，裡面放 [鍵, 值]。put 先算出桶，桶裡已經有這個鍵就更新值，沒有就加進去；get 也是先算出桶，再到桶裡找。執行後看三件事：每個名字進了哪個桶、每個桶裡有誰、最後兩次 get 的結果：

  • 王小明和林志豪都進了桶 4，張雅婷和黃淑芬都進了桶 1。不同的鍵算出同一個桶，叫做碰撞（collision）。
  • get('林志豪') 拿到 1：先算出桶 4，再在桶裡找到林志豪那一對。
  • get('吳先生') 是 undefined：算出的那個桶裡沒有這個鍵。

碰撞避免不了：桶的數量有限，可能的鍵卻沒有上限，一定會有不同的鍵算到同一格。碰撞也不會出錯，因為桶裡存的是完整的 [鍵, 值]，get 到了那一格，再用 find 逐一比較鍵，就分得出王小明和林志豪。碰撞的代價只是那一格要多比幾次。

所以查一次的成本有兩部分：算出桶號是 O(1)，加上在桶裡比較幾次。只要每個桶裡只有少數幾個鍵，查找就是平均 O(1)。這個迷你版的弱點也在這裡：桶永遠只有 7 個，放進一萬個名字，每個桶平均有一千多個，就又退化成逐一比較。

JavaScript 內建的 Map、Set 做的是同一件事，只是做得好很多：雜湊函式分散得更平均，鍵變多時會自動加桶，讓每個桶維持在少數幾個。Chrome 和 Node 用的 JavaScript 引擎叫 V8，它的 Map、Set 就是用雜湊表實作的。所以：

  • 平均 O(1)：加入、查詢、刪除都是。
  • 最壞情況會退化：如果大量的鍵都撞進同一個桶，那一格就變回逐一比較。日常寫程式不用擔心，但要知道「O(1)」指的是平均。
  • 規格沒保證 O(1)：ECMAScript 規格只要求平均存取時間「低於線性」（sublinear），沒有規定一定要用雜湊表。面試時說「平均 O(1)」最精確。
雜湊表不是免費的：它要另外的記憶體存放每個鍵和值。對帳時兩萬筆編號都不重複，Set 裡就存了兩萬個。把 O(n²) 變成 O(n) 的代價，通常是 O(n) 的額外空間。面試時要把這兩個一起講出來。在伺服器上拿 Map 當快取時，這個記憶體代價會變成實際的問題，細節見課末「補充與查表」。

原理清楚了，回到對帳。第一個檢查要回答「這個訂單編號有沒有出現過」：只關心有沒有，不需要另外記一個值。只存鍵的雜湊表就夠了，這就是 Set。

檢查一：訂單編號有沒有重複？

集合（Set）是只存鍵、不存值的雜湊表，同一個值只會存一份。它回答的問題只有一個：「有沒有」。先沿用上一節的顧客名字看基本操作。執行後看：size 是 2（第二次加王小明沒有多存一份）、has 的結果，以及最後一行的去重：

最後兩行是去重（deduplicate）：移除重複的元素。new Set(codes) 把陣列裡的值一個個加進 Set，重複的自然被擋掉；Set 依加入的順序迭代，所以 [...new Set(codes)] 轉回陣列時，保留的是每個值第一次出現的順序。

接著照第 1 課的七步驟寫對帳的第一個檢查。重述：輸入是今天的訂單編號 readonly number[]，輸出 boolean：只要有任何一個編號出現兩次以上就是 true。空陣列沒有重複，是 false。

暴力解：每一對 (i, j) 都比一次，j 從 i + 1 開始（從 i 開始的話，每個元素都會等於自己）。O(n²)。

重複的工作：走到第 j 個時，內迴圈其實在問「前面有沒有出現過這個值？」，這是查找，跟第一版的 includes 是同一件事。改進：把看過的值放進 Set，每一步只要 has 一次。下面的版本會印出每一步，執行後看每一列的「看過？」和右邊的 Set 內容：

前三列的編號都沒看過，各自被加進 Set；第 4 列（i = 3）的 101 已經在 Set 裡，立刻回傳 true，後面的 110 不用再看。每一步的順序是先 has 再 add：如果先加再查，每個編號都會查到剛放進去的自己。

還有一個中間方案：複製一份、排序，重複的值就會相鄰，再比相鄰兩個。O(n log n)，要記得 [...ids].sort((a, b) => a - b)：先複製（不能改呼叫端的陣列，第 3 課），並給比較函式（不給的話會照字串排序，第 1 課）。它的好處是不用另外建 Set：如果記憶體很吃緊、而且題目允許直接排序傳進來的陣列，可以考慮它，代價是時間從 O(n) 變 O(n log n)。

邊界：空的、一個元素、重複在最後兩個、負數編號。複雜度：O(n) 時間、O(n) 額外空間（最壞情況全部不重複，Set 存了 n 個）。

💡 實務上：code review 時看查找是不是放在迴圈裡
什麼時候不必用 Set？資料只有十幾筆、而且只查一兩次，includes 更簡單，差距量不出來。Set 的價值在「n 很大」或「在迴圈裡反覆查」，資深工程師看的是：查找是不是放在迴圈裡。這課開場的對帳程式就是典型的出事場景：匯入 CSV 時檢查重複的訂單編號，測試時幾十筆很順，上線遇到幾萬筆就卡住。另外，真正要保證「不重複」，要靠資料庫在欄位上設的 UNIQUE（唯一）限制；程式裡的 Set 只是事先擋下、給使用者清楚的錯誤訊息。

第一個檢查完成。第二個檢查要數每種飲料賣了幾杯：這次光知道「有沒有」不夠，還要替每個代碼記住一個數字。

檢查二：每種飲料賣了幾杯？

要替每個鍵記一個值，就用 Map。Map 也是雜湊表，存的是「鍵 → 值」的配對，跟迷你版每個桶裡放 [鍵, 值] 是同一個樣子。拿 Map 記錄每個值出現幾次，這種用法叫頻率表（frequency map）：鍵是飲料，值是目前數到幾杯。這裡先用中文品名示範，比代碼好認；下一節換回收銀機匯出的代碼時，會看到這個差別為什麼重要。執行後看：拿鐵是 3、沒賣過的起司蛋糕是 undefined，以及最後一行迭代的順序：

計數那一行要記熟：counts.set(k, (counts.get(k) ?? 0) + 1)。它的意思是「取出目前的次數，加 1 再存回去」。問題出在第一次遇到某個鍵時：get 找不到，回傳 undefined，而 undefined + 1 是 NaN，之後每次加 1 都還是 NaN。所以先用 ?? 0 把「沒有」換成 0。TypeScript 也知道這件事：Map<string, number> 的 get 回傳 number | undefined，不處理 undefined 直接加 1 會報型別錯誤。

不要寫 counts.get(k)! + 1。! 只是叫 TypeScript 閉嘴，執行時第一次遇到這個鍵照樣是 NaN。

對帳報表要把結果一行行印出來，所以要能走過 Map 裡的每一對。for (const [k, v] of map) 能用，是因為 Map 是可迭代的（TypeScript 課第 10 課的迭代器）：它依插入順序產生 [鍵, 值]。map.keys()、map.values()、map.entries() 也都是迭代器，要變成陣列就展開：[...map.keys()]。

💡 實務上：API 回來的陣列，先建成 Map 再查
對帳報表通常還要印出顧客名字。咖啡店後台的 API 常回傳 orders 和 customers 兩個陣列，每筆訂單只有 customer_id。在 orders.map 裡寫 customers.find(c => c.id === o.customer_id)，就是迴圈裡的線性查找，跟第一版的 includes 是同一個問題。先建 const byId = new Map(customers.map(c => [c.id, c]))，迴圈裡改用 byId.get(o.customer_id)，並處理找不到（例如顧客已被刪除）時的 undefined。Set 則常用在「勾選了哪些訂單」「標籤去重」。Map 要存進 localStorage 或送給 API 時有一個坑，見課末「補充與查表」。

你在前端可能習慣用 const counts = {} 計數，看起來也能做到同樣的事，為什麼這裡堅持用 Map？因為飲料代碼是收銀機匯出的，由外部系統決定，不是你寫死的。鍵來自外部時，一般物件會算錯，下一節實際看看。

為什麼不用 {} 計數？代碼來自外部的時候

資料是自己寫死的鍵時，用物件計數沒問題；但鍵來自使用者輸入或外部資料時，會出三種事。先看最嚴重的：假設收銀機匯出的代碼裡剛好出現 'constructor' 和 'toString'。執行後看三行印出的次數：

counts['LAT'] 是 2，沒問題；counts['constructor'] 卻不是 1，而是一長串字串。原因在原型（TypeScript 課第 3 課）：讀一個物件的屬性時，物件自己沒有，就往它的原型找。一般物件的原型是 Object.prototype，上面本來就有 constructor、toString 這些函式。所以第一次遇到 'constructor' 時，counts['constructor'] ?? 0 拿到的不是 undefined，而是函式；函式 + 1 會先把函式轉成字串，變成字串串接。TypeScript 也擋不下來，因為 Record<string, number> 說每個鍵都是 number。

另外兩件事是：鍵會被轉成字串，數字樣子的鍵順序會被重排。下面三段各看一件事：Object.keys(byObj) 只剩一個鍵、Map 版本的 size 是 2、shelf 印出的鍵順序跟加入的順序不同：

結論：鍵在執行時才知道（來自資料）的查找表，用 Map／Set。形狀固定、鍵是你寫死的（像 { name, price }），才用一般物件。一定要用物件時，Object.create(null) 建出來的物件沒有原型，就不會撞到 constructor，但鍵還是會被轉成字串。

💡 實務上：鍵來自外部時，資安也會關心
對帳的飲料代碼、使用者送來的標籤、搜尋關鍵字、表單欄位名稱，鍵都由別人決定。除了這課看到的計數錯誤，__proto__ 這類鍵在合併或寫入物件的程式裡，還可能被拿來做原型污染（prototype pollution），是資安檢查常看的漏洞類型。做法很單純：程式內部的查找表一律用 Map／Set；API 收發的 JSON 本來就是物件，在邊界用 new Map(Object.entries(json)) 轉進來、Object.fromEntries(map) 轉出去。Code review 看到 obj[userInput] = … 時，值得多問一句：這個鍵是誰給的？

比較表的第一列說 Map 的鍵可以是任何值、而且保留型別。那陣列也能當鍵嗎？當鍵需要兩個欄位一起決定時，這個問題就會出現。

鍵要由兩個值組成時，能直接用陣列當鍵嗎？

對帳用到的鍵都是單一的數字或字串，所以這一節換一個例子：店裡的座位用「第幾排、第幾個」兩個數字才能指定一個位置，要記住哪些位置有人坐，鍵就是兩個數字的組合。第 20 課的網格題也是這種鍵。

要回答這個問題，得先知道 Map 和 Set 怎麼判斷「兩個鍵是同一個」。它們用的規則叫 SameValueZero：跟 === 幾乎一樣，只差在 NaN 也算等於 NaN（NaN === NaN 是 false）；0 和 -0 跟 === 一樣算同一個。既然跟 === 一樣，陣列和物件比的就是參考，也就是「是不是同一個陣列」，不是內容（TypeScript 課第 2 課）。執行後看前兩個 has 的結果：

第一個 has 是 false：add 和 has 裡各寫了一次 [1, 2]，每寫一次就建立一個新陣列，內容一樣，參考不同。要用「內容」當鍵，就把內容組成字串，例如 `${row},${col}`：字串比的是內容，所以第二個 has 是 true。中間一定要有分隔符號，不然 1 和 23 跟 12 和 3 都會變成 '123'；最後一行印出 '1,23' 和 '12,3'，兩者不同。

鍵的規則都清楚了。回到對帳的最後一個檢查：比對櫃台單和吧台的出餐單。它會同時用到 Set 和 Map，也會看到只用 Set 為什麼不夠。

檢查三：櫃台單和出餐單一樣嗎？

為了讓每張單寫成一個字串，這裡把每個品項縮成一個字母：L 是拿鐵（LAT）、A 是美式（AME）、C 是卡布奇諾（CAP），'LAC' 就是這三杯各一杯。要判斷櫃台開的單和吧台的出餐單，品項和數量是否完全一樣（順序不管）。

第一個想法常是比 Set：兩張單的 Set 一樣就相同。但 Set 只記「有沒有」，把次數丟掉了：'AAB'（兩杯 A、一杯 B）和 'ABB' 的 Set 都是 {A, B}，吧台少做一杯 A、多做一杯 B，卻會被判成一致。需要次數，就用檢查二數杯數時的頻率表，這次改成一張加、一張減：

  1. 長度不同，直接回傳 false。
  2. 走過第一張，每個字母 +1；走過第二張，每個字母 −1。
  3. 最後每個字母都是 0，兩張單才相同。

拿 Map 當快取，記得它會一直長大

💡 實務上：拿 Map 當快取，記得它會一直長大
後端常見的寫法是在模組最上層放一個 const cache = new Map()，把查過的商品或顧客資料存起來，下次直接回傳。問題是伺服器程序會一直跑，鍵只加不刪，記憶體就會慢慢被吃光，而且通常要到上線一段時間後才發現。資深工程師會先問：最多會放多少筆？資料改了，快取怎麼跟著更新？開了好幾台伺服器時，每台各有一份會不會不一致？筆數要設上限，就用成熟的 LRU 套件（例如 lru-cache，滿了先丟最久沒用的）；要跨伺服器共用，就交給 Redis 這類專門的快取服務。

Map 不能直接 JSON.stringify

JSON.stringify(new Map(…)) 會得到 '{}'，存進 localStorage 或送給 API 前要先轉成陣列或物件，例如 [...map] 或 Object.fromEntries(map)。

練習

練習 2、4 有計時測試：用大量資料比較你的程式和參考解，慢太多（例如雙迴圈或迴圈裡 includes）就不算過。

練習 1：countByDrink 回傳每個飲料代碼出現的次數。Map 和迴圈都寫好了，補上計數的那一行。注意資料裡會出現 'constructor'、'toString'、'__proto__' 這種代碼。

練習 2：寫 hasDuplicateOrder：今天的訂單編號裡，只要有任何編號出現兩次以上就回傳 true，否則 false。要 O(n)，不能修改傳進來的陣列。對應 LeetCode 217. Contains Duplicate。

練習 3：寫 sameTicket：兩張出餐單各用一串大寫字母代表品項，判斷兩張單的品項與數量是否完全相同（順序不同沒關係）。兩張都是空字串時算相同。對應 LeetCode 242. Valid Anagram。

練習 4：寫 firstReturningCustomer：names 是今天依點餐順序排好的顧客名字。回傳「第一個來第二次的人」，以第二次出現的時間點為準；沒有人來第二次就回傳 null。例如 ['王小明', '陳美華', '陳美華', '王小明'] 要回傳 '陳美華'：她在第 3 筆就回來了，王小明要到第 4 筆。要 O(n)。

練習 5：map.get(key) 在 JavaScript（V8）裡的時間複雜度是？

✓ V8 用雜湊表實作，算出桶號直接去查，平均 O(1)；如果很多鍵擠在同一個桶，就要逐一比較而變慢。Map 不是排序樹（它照插入順序迭代，不照大小），所以不是 O(log n)。規格只要求平均「低於線性」，沒有保證 O(1)。

練習 6：const counts: Record<string, number> = {}，還沒放任何東西，counts['constructor'] 是什麼？

✓ 一般物件會沿著原型找屬性，Object.prototype.constructor 就是 Object 函式，所以 counts['constructor'] ?? 0 拿到函式，+ 1 變成字串串接。型別寫 number 只是 TypeScript 的假設，執行時不會變成 0。用 Map（或 Object.create(null)）就沒有這個問題。

練習 7：new Set([[1, 2]]).has([1, 2]) 的結果是？

✓ Set 用 SameValueZero 比較，陣列和物件比的是參考。每寫一次 [1, 2] 就是一個新的陣列。Set 可以放陣列，只是查不到「內容一樣的另一個陣列」。要依內容查，就用字串鍵，例如 `${r},${c}`。

練習 8：同事用 new Set(a) 和 new Set(b) 比較兩張出餐單是否相同。哪一組輸入會判錯？

✓ Set 只記「有沒有」，把次數丟掉了：'AAB' 和 'ABB' 的 Set 都是 {A, B}，被判成相同。a 本來就相同、b 的 Set 本來就不同，兩組都判對。需要次數時用頻率表。

常見錯誤

  • 迴圈裡用 includes／indexOf：看起來只有一層迴圈，其實每次都走過整個陣列，是 O(n²)。改成迴圈外建好 Set，迴圈裡用 has。
  • 以為雜湊表免費：時間從 O(n²) 變 O(n)，代價是 O(n) 的記憶體。面試時兩個都要說。
  • 忘了 get 會回傳 undefined：undefined + 1 是 NaN，加上 ! 也一樣。計數寫 (map.get(k) ?? 0) + 1。
  • 用一般物件當查找表：鍵會被轉成字串、會撞到原型上的 constructor、toString，整數鍵的順序也會被重排。鍵來自資料時用 Map／Set。
  • 用陣列或物件當鍵：比的是參考，另外建一個內容一樣的陣列永遠查不到。組成有分隔符號的字串鍵。
  • 需要次數卻只比 Set：Set 去掉了次數。要比「數量也一樣」時用頻率表。

小結

  • 把迴圈裡的線性查找換成 Set／Map，是最常見的 O(n²) → O(n)，代價是 O(n) 的額外空間。對帳程式變慢，就是迴圈裡的 includes。
  • 雜湊表用雜湊函式把鍵算成桶號，直接去那一格找，平均 O(1)；碰撞時桶裡逐一比較，大量碰撞會退化。
  • Set 回答「有沒有」、用來去重和找重複；Map 存「鍵 → 值」，用來計數或記位置。
  • 計數的寫法：map.set(k, (map.get(k) ?? 0) + 1)。
  • 鍵來自資料時用 Map／Set，不用一般物件：物件的鍵會變字串、會撞到原型上的名稱。
  • Map／Set 比較鍵用 SameValueZero，陣列和物件比參考；要依內容查就組成有分隔符號的字串鍵。
  • 比對「品項和數量都一樣」要用頻率表，Set 會丟掉次數。
