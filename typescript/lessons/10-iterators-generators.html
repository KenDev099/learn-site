階段 2：非同步、迭代與並發 · 第 10 課

迭代器與產生器：一次拿一筆

咖啡店有開外送，訂單存在外送平台上。老闆想把去年 300 萬筆外送訂單匯回自己的資料庫，算出每位顧客的消費額。平台提供一個訂單 API，一次只回一頁。最直覺的寫法是：把每一頁都抓回來，全部塞進一個陣列，再用 for 迴圈一筆一筆寫進資料庫。

這個寫法在測試時跑得好好的，因為測試資料只有幾十筆。換成正式資料就會出三個問題：300 萬筆同時待在記憶體裡，伺服器的記憶體可能不夠，程序被系統砍掉；要等最後一頁抓完，第一筆才開始寫，前面幾分鐘什麼事都沒做；匯入前想先抽查某一筆訂單的格式對不對，找到之前卻已經把後面幾十頁都抓回來，白白用掉 API 的呼叫次數。

這一課把它改成一次拿一筆，處理完再拿下一筆：寫一個 allOrders，讓迴圈一筆一筆從它拿訂單，它只在需要時才去抓下一頁；再寫一個 batch，每湊滿一批才寫一次資料庫。這就是練習 3 和練習 4。Node 讀大檔案的 Stream、資料庫套件一批一批讀查詢結果，背後都是這一課的同一套規則。

這課的路線：
  1. for…of 怎麼一筆一筆拿、自己的類別怎麼也能被走訪：迭代協定，以及手寫迭代器為什麼很快就變麻煩（節尾給開場問題的最小答案）。
  2. 產生器：一個會暫停的函式，讓語言替你記住「走到哪」；消費者提早離開時，資源怎麼關掉。
  3. 非同步產生器：每一頁都要等網路時，用 async function* 和 for await…of 一頁一頁讀訂單 API，拿夠了就停。
  4. 拉取、推送與背壓：寫資料庫比讀 API 慢時，資料為什麼不會越堆越多；再用批次寫入補回效能。
  5. 迭代器輔助方法：像陣列一樣 map、filter、take，但一筆一筆算。
這課會用到：
  • 第 9 課的 async／await：async 函式一定回傳 Promise，await 等它定案再往下。
  • 第 3 課的 class 與私有欄位：#items 這種 # 開頭的欄位，只有類別自己的方法讀得到。
  • 第 1 課的閉包：函式會記住建立它時周圍的變數，之後每次呼叫都讀寫同一份。

for…of 怎麼一筆一筆拿？迭代協定

要讓 allOrders 能被迴圈一筆一筆拿，先得知道 for…of 對一個東西提出了什麼要求。你在 Vue 裡寫 for (const item of list) 時，list 幾乎都是陣列，很容易以為 for…of 是陣列專用的語法。其實不是：for…of 不在乎對方是不是陣列，它只認一套約定，物件照這套約定提供方法，就能被走訪。這套約定叫迭代協定（iteration protocol）。

約定裡有兩個角色。為什麼要兩個？因為同一份資料可能同時被兩個迴圈走訪，例如一個在印菜單、一個在算總價，兩邊走到的位置不一樣。所以「資料本身」和「目前走到哪」要分開放：

  • 可迭代物件（iterable）：資料本身。它有一個 [Symbol.iterator]() 方法，通常每呼叫一次就回傳一個新的迭代器，每個想走訪它的人各拿一個。
  • 迭代器（iterator）：記住「目前走到哪」的物件。它有一個 next() 方法，每呼叫一次回傳 { value, done }：value 是這一筆的值；done 是 false 代表拿到了一筆，done: true 代表沒有了。

可迭代物件那個方法的名字長得很特別，先說 Symbol 是什麼。Symbol 是 JavaScript 的一種原始值，跟字串、數字同一類，特性是每個 Symbol 都獨一無二，不會跟任何其他值相等。物件的鍵可以是字串，也可以是 Symbol。語言把「怎麼走訪我」這個方法的鍵定成一個內建的 Symbol，叫 Symbol.iterator，這樣它永遠不會跟你自己取的屬性撞名：你的物件就算有一個叫 'iterator' 的字串屬性，也不會被誤認成走訪方法。外面的中括號是「用一個值當鍵」的寫法，menu[Symbol.iterator] 就是讀取鍵為這個 Symbol 的屬性。

有了這兩個角色，就能手動做一次 for…of 在背後做的事。執行後看三次 next() 的回傳值，特別是最後一次的 done：

for…of 做的就是這三步：先呼叫 [Symbol.iterator]() 拿一個迭代器，再一直呼叫 next()，把每次的 value 交給迴圈本體，看到 done: true 就停。迴圈本體還沒跑完，下一次 next() 就不會被呼叫，這一點後面會變得很重要。

這套協定也不是 for…of 專用。展開 [...x]、陣列解構 const [a, b] = x、Array.from(x)、new Set(x) 全部走同一套協定，所以它們能接受的東西都一樣。很多內建型別都是可迭代物件：陣列、字串、Map、Set（Map、Set 在第 2 課）。字串走訪時是依字元碼一個一個交出，所以 👍🏽 這種由兩個字元碼組成的 emoji 會被切成兩個（第 6 課）。而你最常用的普通物件，例如 { name: '拿鐵', price: 110 }，不是可迭代物件，因為它沒有 [Symbol.iterator] 方法。下面這格依序看字串、Map、Set 解構，最後看普通物件丟出的錯誤：

最後給這兩方取名字，後面會一直用到：拿值的一方叫消費者（consumer），例如 for…of、展開；產生值的一方叫生產者（producer），也就是迭代器背後的資料來源。在開場的任務裡，寫資料庫的那個迴圈是消費者，負責抓訂單的 allOrders 是生產者。下面這張圖是整個協定的樣子，注意主導權在誰手上：

消費者呼叫 next()，迭代器才去拿下一個值；消費者不呼叫，迭代器就停著不動。這正是開場要的「一次拿一筆」：只要訂單來源也遵守這套協定，寫資料庫的迴圈處理完一筆才會要下一筆。接下來的問題是：自己寫的東西，要怎麼遵守這套協定？

怎麼讓自己寫的類別也能被 for…of？

先拿比訂單 API 簡單的東西練習：菜單類別。它把商品存在私有陣列 #items 裡，外面看不到；外面想用 for…of 走訪菜單，先做最簡單的：把三個商品依序交出去。照上一節的協定，給類別一個 [Symbol.iterator] 方法、讓它回傳一個有 next() 的迭代器就行。選菜單是因為資料只有三筆，每一步的結果一眼看得出來；這裡學到的規則，之後原封不動用在訂單來源上。

直覺的寫法是讓菜單自己當迭代器：[Symbol.iterator]() 回傳 this，next() 直接寫在類別上，用 #index 記目前走到哪。下面這格先跑這個寫法（BuggyMenu），再跑修正版（Menu）。執行後看 BuggyMenu 第二次展開的結果：

BuggyMenu 第二次展開是空陣列。原因是位置 #index 存在菜單物件本身：第一次展開把 #index 推到 3；第二次展開再呼叫 [Symbol.iterator]()，拿到的還是同一個物件，#index 還停在 3，next() 一呼叫就回 done: true。同樣的道理，兩個迴圈同時走訪時會共用同一個 #index，你走一步、我也被推一步，兩邊都只拿到一部分。

這就是上一節說「資料本身」和「目前走到哪」要分開的原因。修正版的 Menu 每次被呼叫 [Symbol.iterator]()，都建立一個新的 index 變數和一個新的迭代器物件；next() 是箭頭函式，用閉包記住這一次走訪自己的 index。每次走訪各有一份位置，所以能重複走訪，同時走訪也不會互相干擾。規則記成一句話：每次呼叫 [Symbol.iterator]() 都要回傳新的迭代器。

菜單做到了，但回頭看開場的訂單任務，手寫 next() 會很痛苦。菜單只要記一個 index；訂單來源要記「目前這一頁的資料、這一頁走到第幾筆、下一頁的位置、是不是已經沒有下一頁」，而且每次 next() 都要從這些狀態推算這次該做什麼：是交出這頁的下一筆，還是先去抓下一頁。狀態一多，就很容易漏掉一種情況。

開場問題的最小答案先說在這裡：不要自己管這些狀態，改寫成一個產生器。用一般的迴圈寫「抓一頁、一筆一筆交出去、再抓下一頁」，讓語言替你記住執行到哪一行，消費者要下一筆時才繼續。下一節先用同步的產生器學會「暫停」，再下一節加上 await，讀真正的分頁 API。

產生器：怎麼寫一個「要下一筆才算下一筆」的函式？

上一節的麻煩在於：next() 每被呼叫一次，都要從頭判斷「我上次停在哪、這次該做什麼」。如果函式本身可以在交出一個值之後暫停，下次從暫停的地方繼續，狀態就留在函式的區域變數和執行位置裡，不必另外存。這種函式就是產生器函式（generator function），寫成 function*。

產生器函式跟一般函式有兩點不同。第一，呼叫它不會執行裡面任何一行，只會拿到一個產生器物件。第二，函式裡可以寫 yield：每次有人呼叫產生器物件的 next()，函式就往下跑，跑到 yield 就把後面的值交出去並暫停；下一次 next() 再從暫停的地方繼續。產生器物件同時扮演上一節的兩個角色：它有 next()，所以是迭代器；它也有 [Symbol.iterator]()，回傳的就是它自己，所以 for…of、展開可以直接走訪它。也因為回傳的是自己，產生器物件跟上一節的 BuggyMenu 一樣只能走一次：const g = gen() 之後 [...g] 第二次會是空陣列。要重新走訪，就要重新呼叫產生器函式拿一個新的產生器物件，這正是等一下菜單要把 [Symbol.iterator] 寫成產生器方法的原因。

第一個是惰性（lazy）：值在被要的時候才計算。brew() 呼叫完什麼都沒做，第一次 next() 才磨豆。換到訂單任務，就是消費者還沒要下一筆時，下一頁不會被抓。

第二個是能表示無限序列。一般函式裡寫 while (true) 會卡死，因為它停不下來；產生器裡的 while (true) 每一圈都在 yield 停住，消費者不拿，它就不跑。像店裡的取號機，號碼沒有盡頭，但一次只發一張。執行後看兩種拿號碼的方式，注意 for…of 裡的 break：

for…of 加 break 是安全的，因為由消費者決定什麼時候停。最後一行註解是危險的用法：展開會一直呼叫 next() 直到 done: true，無限序列永遠不會 done，程式就卡住、記憶體一直長。消費無限序列時，停止條件一定在消費者這邊；練習 2 的 take 就是把「只拿前 n 個」包成一個可以重複用的產生器。

回到上一節的菜單，這次再加上需求：只交出上架中的商品，所以商品改成帶 isAvailable 的物件。手寫 next() 要另外處理「跳過下架商品、繼續找下一個」；用產生器只要在迴圈裡加一個 if。產生器物件就是迭代器，所以把 [Symbol.iterator] 寫成產生器方法（方法名稱前面加 *），手寫 next() 的那些程式就都不用了。執行後看兩次展開的結果是不是一樣：

每次 [...menu] 都會呼叫一次 *[Symbol.iterator]()，產生一個新的產生器物件，各自從頭跑，所以上一節「每次回傳新的迭代器」的規則自動成立，這也是練習 1 的寫法。如果不需要篩選，迴圈還能更短：yield* 後面接一個可迭代物件，會把它的值一個一個 yield 出去，寫成 *[Symbol.iterator]() { yield* this.#items } 就好。下一節讀分頁 API 時，會用 yield* 把一整頁的訂單逐筆交出去。

消費者提早離開時，連線怎麼關？

訂單任務還有一件事沒處理。讀訂單的產生器會打開資源，例如資料庫連線或檔案，讀完要關掉。可是消費者不一定讀完：找到要的訂單就 break，或處理到一半丟出錯誤。這時產生器停在某個 yield，後面的程式永遠跑不到，寫在最後面的「關閉連線」也就不會執行。

迭代協定為這個情況準備了第三個方法：return()。for…of 被 break、return 或錯誤中斷時，會呼叫迭代器的 return()，通知它「我不要了」。產生器收到 return()，就像在暫停的那個 yield 位置執行了 return：函式結束，但結束前會先執行包住它的 finally。所以把關閉資源寫在 try…finally 的 finally 裡，正常走完和提早離開都會關到。執行後看「關閉連線」印在「迴圈結束」之前還是之後：

「關閉連線」印在「迴圈結束」之前：break 的當下，for…of 就呼叫了 return()，finally 立刻執行，迴圈才結束。最後兩行是自己呼叫 next() 的情況，沒有 for…of 幫忙，拿夠了就要自己呼叫 return()。

用 for…of 提早離開、解構只取前幾個（const [a] = readOrders()）時，語言會幫你呼叫 return()。自己呼叫 next() 的程式，拿夠了要自己呼叫 return()，否則 finally 永遠不會執行，資源就一直沒還。這是練習 2 要擋的錯誤。
💡 實務上：產生器很少在業務程式裡手寫，但常在套件裡遇到
咖啡店後台的商品列表、訂單明細，資料量小又要排序、分頁顯示，直接回傳陣列最好懂，不需要為了「看起來進階」改成產生器。本課的訂單匯入是少數值得自己寫的情況：資料量大，而且只需要從頭走一遍。你更常遇到的是別人寫好的迭代器：Node 的 readline 逐行讀檔（可以用 for await…of 一行一行拿）、資料庫套件一批一批讀查詢結果的 API，它們都靠這一節的規則運作。Code review 看到產生器或迭代器包著連線、檔案時，先檢查兩件事：資源是不是在 finally 裡釋放，以及呼叫端會不會只拿一半就丟掉、卻沒觸發 return()。

每一頁都要等網路，產生器怎麼 await？

有了產生器，可以回到開場的訂單 API 了。先看這個 API 怎麼分頁：外送平台一次只回一頁訂單，回應裡除了這一頁的 items，還附一個 nextCursor。nextCursor 是平台產生的一個字串，代表「這一頁讀到哪裡」；下一次請求帶著它，平台就從那個位置後面接著給下一頁。nextCursor 是 null 代表沒有下一頁了。這種分頁方式叫游標分頁（cursor pagination），跟 PostgreSQL 第 5 課提過的「記住上一頁最後一筆，從它後面接著拿」是同一個想法。

難處在於抓每一頁都要等網路：fetchPage 回傳 Promise，要 await。上一節的產生器是同步的，function* 裡不能寫 await。所以要用非同步產生器（async generator），寫成 async function*：它跟產生器一樣會在 yield 暫停，差別是 yield 之間可以 await。

非同步產生器可能要等網路才拿得到下一個值，所以它的 next() 回傳的不是 { value, done }，而是一個之後才會給出 { value, done } 的 Promise。消費它就要用 for await…of：每一圈先 await next() 給的 Promise，拿到值再執行迴圈本體。

下面這格用 PAGES 假裝外送平台，fetchPage 每次等 20ms，並印出 [API] 那一行。allOrders 就是開場要的那個函式：抓一頁、用 yield* 把這頁的訂單一筆一筆交出去、換成下一個游標，直到 nextCursor 是 null。消費者找到 #4 就停。範例為了短，allOrders() 直接呼叫外面的 fetchPage；練習 3 會改成把 fetchPage 當參數傳進來，寫成 allOrders(fetchPage)，測試才能換成假的 API，後面完整流程的寫法也是這個版本。執行後看 [API] 出現在哪幾行之間，以及最後一共抓了幾頁：

前三筆處理完、消費者要第四筆時，allOrders 才往下跑去抓第二頁；處理到 #4 就 break，for await…of 呼叫 return() 關掉產生器，第三頁從頭到尾沒被抓。開場的三個問題都解決了，跟「先全部載入陣列」的寫法對照：

全部載入陣列非同步產生器
記憶體所有頁的資料同時在記憶體裡只有目前這一頁
第一筆開始處理等全部頁面抓完第一頁回來就開始

這不表示陣列寫法就是錯的。產生器的代價是只能從頭往後走一遍：不能隨機拿第 500 筆，不能直接 .length 知道總數，也不能 .sort()。真的需要全部資料一起排序、或要重複使用時，還是收集成陣列；表格最後一列就是判斷依據。

非同步產生器不能用一般的 for…of 走訪，會丟 TypeError: … is not iterable。原因在協定：非同步產生器沒有 [Symbol.iterator]，它有的是非同步版的 [Symbol.asyncIterator]，回傳的迭代器 next() 給的是 Promise；for…of 只找前者。要用 for await…of。反過來，for await…of 可以走訪一般的可迭代物件，練習 4 會用到。
💡 實務上：每晚同步金流或外送平台的訂單，就是這種寫法
常見的排程工作：從金流、外送平台的 API 把昨天的交易一頁一頁拉回來對帳，或把全部訂單匯出成 CSV 給會計。寫之前資深工程師會先問：對方 API 有沒有呼叫頻率限制（rate limit）、遇到錯誤要不要重試、工作跑到一半掛掉能不能從上次的 cursor 接著跑，而不是從頭再拉一次。要注意 cursor 可能有期限，放太久再用會失效。反過來，後台畫面讓使用者自己按「下一頁」的列表，一次請求一頁就好，不需要非同步產生器。

寫資料庫比讀 API 慢時，訂單會堆在哪裡？

訂單讀進來之後要寫進資料庫，而寫入通常比讀取慢。假設讀一筆很快、寫一筆要 30ms，生產者就比消費者快。這時讀進來的訂單會不會越堆越多，最後又把記憶體塞爆？答案取決於誰決定速度。

迭代器是拉取模式（pull）：消費者呼叫 next()，生產者才做下一筆，速度由消費者決定，消費者慢，生產者就跟著停下來等。另一種是推送模式（push）：生產者自己決定什麼時候送，不管消費者處理完沒有，例如 setInterval 每 10ms 送一筆。你在前端用的 addEventListener 也是推送：事件發生就呼叫你的函式，你沒辦法叫使用者慢一點點擊。

消費者處理不完時，讓生產者慢下來的機制叫背壓（backpressure），意思是壓力從下游傳回上游。拉取模式天生有背壓，因為消費者不要，生產者根本不會動；推送模式沒有，送來還沒處理的資料只能先放進佇列等。下面這格兩種模式的消費者每筆都花 30ms，想像成寫資料庫。執行後比較兩行結果：推送模式的佇列裡堆了幾筆，拉取模式的生產者產生了幾筆：

推送模式每處理一筆，佇列就再多堆幾筆，處理越久堆越多；拉取模式處理了 5 筆，生產者就只產生 5 筆。在伺服器上，堆積的佇列就是越來越高的記憶體，堆到某個程度程序就被系統砍掉，這正是開場要避免的事。所以開場的訂單匯入用 allOrders 加 for await…of，就算寫資料庫比讀 API 慢，訂單也不會在記憶體裡越堆越多。Node 讀檔案用的 Readable stream 也是一段一段交出資料，同樣可以用 for await…of 讀，背壓的完整機制在 Node 課第 16 課。

不過一筆一筆拉也有代價：每拉一筆就寫一次資料庫，300 萬筆就是 300 萬次查詢，每次都要跟資料庫來回一趟，加起來很慢。常見的折衷是批次（batch）：仍然用拉取模式，但每拉 100 筆組成一批，一次寫進資料庫。記憶體裡最多只多一批，查詢次數變成原本的百分之一。開場的整條流程到這裡就完整了（insertOrders 是示意的寫入函式）：

for await (const group of batch(allOrders(fetchPage), 100)) {
  await insertOrders(group)
}

allOrders 是練習 3，batch 是練習 4。

💡 實務上：搬大量資料前，先想「誰決定速度」
匯入一份很大的舊系統訂單 CSV 到資料庫、消費佇列裡的訊息，都是生產者比消費者快的典型場景：用拉取加批次寫入，記憶體就不會跟著資料量一起長。批次大小沒有標準答案，太小查詢次數多、太大單次交易太久，要用實際資料量測。WebSocket、事件這類推送來源沒辦法叫對方慢下來，就要自己決定佇列上限，滿了要丟棄、合併還是回報錯誤。上線後盯著程序的記憶體用量，跑越久越高、不會回落，通常就是哪裡沒有背壓。

能不能像陣列一樣 map、filter，但仍然一筆一筆算？

這一節先換個例子：開場的訂單來源是非同步的，而這組方法目前只有同步迭代器有（原因見本節最後），所以這裡用一串價格看它怎麼運作。寫 Vue 時你習慣把陣列的 filter、map 串起來處理資料，拿到迭代器之後也會想這樣寫，例如從一串價格裡「只要 90 元以上、乘以 2、拿前 2 筆」。但陣列方法每一步都要把整個陣列跑完、產生一個新陣列，再交給下一步，等於又回到「全部放進記憶體」的做法；來源是無限序列時，更是永遠跑不完。

ES2025 給迭代器加上了一組跟陣列很像的方法，叫迭代器輔助方法（iterator helpers）：map、filter、take、drop、flatMap、reduce、toArray、forEach、some、every、find。名字跟陣列一樣，差別在執行順序：陣列是一步全部做完再做下一步，迭代器是每一筆依序流過全部步驟。下面的 prices.values() 會回傳陣列的迭代器，才能接上這組方法。執行後比較兩段 log 的順序和次數：

陣列版本把 6 個價格全部 filter、再把通過的 4 個全部 map，最後才 slice 出前 2 筆。迭代器版本每一筆 filter 通過就馬上 map；filter 到第 3 個價格時已經湊滿 2 筆，take 就不再向上游要資料，後面 3 個價格完全沒被碰到。資料量大或來源是無限序列時，這個差別就是能不能跑完。

這組方法有兩個限制。第一，它比較新，本課程 TypeScript 頁的型別設定沒有它的型別，所以只在這一頁的範例示範，練習不會用；各環境的支援版本見課末「補充與查表」。第二，非同步迭代器還沒有這組方法。開場的訂單來源是非同步的，所以練習 3 的 allOrders、練習 4 的 batch 都要用非同步產生器自己寫；練習 2 先讓你在同步的世界手寫一次 take，熟悉「拿夠就停、記得關閉來源」。

練習

練習 1：Menu 已經有 add(product)。實作 [Symbol.iterator]，讓 for…of 和展開只拿到上架中（isAvailable 為 true）的商品物件，而且同一份菜單可以重複走訪、兩個迴圈同時走訪也不互相干擾。之後新增的商品，或之後才改成上架的商品，下一次走訪都要出現。

練習 2：寫兩個產生器：

  • ticketNumbers(start)：從 start 開始無限產生號碼。
  • take(iterable, n)：交出 iterable 的前 n 個值。必須是惰性的：拿夠了就停，不能多拿一筆，而且要關閉來源（讓來源的 finally 執行）。來源不足 n 個時，有幾個就交幾個。

練習 3：寫 allOrders(fetchPage)。fetchPage(cursor) 回傳 Promise<{ items, nextCursor }>：第一頁傳 null，nextCursor 是 null 代表這是最後一頁。寫成非同步產生器，一筆一筆交出訂單，只在需要時才抓下一頁。中間的頁可能是空的（items 是空陣列，但還有下一頁）。

練習 4：寫 batch(source, size)，用來批次寫入資料庫。source 可以是非同步或一般的可迭代物件。寫成非同步產生器，每湊滿 size 筆就交出一個陣列，最後不足 size 的一批也要交出。size 不是正整數時丟 RangeError（第 4 課：值超出允許範圍時用的內建錯誤）。

練習 5：for (const x of { a: 1, b: 2 }) console.log(x) 會怎樣？

✓ 普通物件沒有 [Symbol.iterator] 方法，for…of 一開始就丟 TypeError。a 錯：印出鍵是 for…in 或 Object.keys 的行為；c 錯：印出值要先 Object.values；d 錯：不會安靜略過，一開始就出錯。要鍵和值就用 for (const [k, v] of Object.entries(obj))。

練習 6：下面執行完，印出了什麼？

function* g() {
  console.log('A')
  yield 1
}
const it = g()

✓ 呼叫產生器函式只會拿到產生器物件，裡面一行都還沒執行。要等第一次 it.next()，才會印出 A 並停在 yield 1。所以 a、b 都錯：A 還沒印，yield 1 交出的 1 也只會出現在 next() 的回傳值裡，不會自己印出來。「建立產生器」和「開始工作」是兩件事，資源（連線、檔案）也要到第一次 next() 才會被打開。

練習 7：用 for await (const order of allOrders(fetchPage)) 讀一個有 50 頁的分頁 API，在第 2 頁找到需要的訂單就 break。剩下的頁還會被抓嗎？

✓ 產生器是拉取模式：只有消費者呼叫 next() 時才會往下跑。break 之後沒有人再呼叫 next()，for await 還會呼叫 return() 把它關掉（finally 會執行）。b 錯：for await 每一圈只要一筆，不會預先抓；會先抓完的是「先把全部頁面放進陣列再 yield」的寫法，也就是練習 3 要擋的錯誤寫法。c 錯：產生器沒有自己的背景工作，停在 yield 時沒有程式在跑，被 return() 關掉後也不會再繼續。

常見錯誤

  • 以為呼叫產生器函式就會開始執行：呼叫只會拿到產生器物件，第一次 next() 才開始跑。連線、檔案這類資源也要到第一次 next() 才會被打開。
  • 自訂迭代器把位置存在物件上：只能走訪一次，兩個迴圈同時走訪也會互相干擾。每次 [Symbol.iterator]() 都要回傳新的迭代器，用產生器方法最簡單。
  • 對無限序列用展開、Array.from 或 [...x].slice()：會一直拿下去，程式卡死、記憶體用完。先用 take 限制數量。
  • 分頁讀取時把所有頁一次載入記憶體：資料量大時記憶體爆掉，第一筆也要等最久。用非同步產生器一頁一頁拿。
  • yield 同一個陣列再清空重用：消費者拿到的是同一個陣列的參考（第 2 課），清空時前面的批次一起被清掉。每批都建立新陣列。
  • 對非同步產生器用一般的 for…of：它只有 [Symbol.asyncIterator]，for…of 會丟 TypeError（不是可迭代物件），要用 for await…of。
  • 把同一個產生器物件拿去走訪兩次：產生器物件的 [Symbol.iterator]() 回傳自己，第一次走到底之後，第二次什麼都拿不到。要重複走訪就重新呼叫產生器函式，或把它寫成類別的 *[Symbol.iterator]()。
  • 自己呼叫 next() 卻沒有呼叫 return()：來源的 finally 不會執行，連線、檔案沒有被釋放。

小結

  • 迭代協定：可迭代物件有 [Symbol.iterator]()，回傳的迭代器有 next()，每次給 { value, done }。for…of、展開、解構、Array.from、Map、Set 都靠它；普通物件不是可迭代物件。消費者呼叫 next()，生產者才給下一筆。
  • 自訂迭代器時，「資料」和「走到哪」要分開：每次 [Symbol.iterator]() 都回傳新的迭代器。寫成 *[Symbol.iterator]() 產生器方法，這條規則自動成立。
  • function* 執行到 yield 會暫停，next() 才繼續；值在需要時才產生，所以可以表示無限序列。提早 break 會呼叫 return()、執行 finally，資源在那裡釋放。
  • 開場的訂單匯入：async function* 加 for await…of 一頁一頁讀分頁 API，記憶體只放一頁、第一頁回來就開始處理、拿夠就停，後面的頁不會被抓。代價是只能從頭走一遍。
  • 拉取模式天生有背壓：寫資料庫再慢，生產者也只在被要時才產生，資料不會越堆越多。再用批次寫入減少查詢次數。
  • 迭代器輔助方法讓 map、filter、take 一筆一筆流過，拿夠就停；目前只有同步迭代器有。

下一課：逾時與取消。上游服務卡住不回來時（像分頁 API 的某一頁，或結帳時的付款服務），怎麼設逾時，並用 AbortController 叫進行中的工作真的停下來。
