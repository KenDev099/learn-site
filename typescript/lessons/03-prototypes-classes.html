階段 1：JavaScript 的核心機制 · 第 3 課

原型與 class：物件怎麼共用方法

第 1 課用閉包做過咖啡店的集點卡：每呼叫一次 makeStampCard() 就發一張新卡，點數藏在閉包裡，外面改不到。現在咖啡店要把會員系統搬到後端正式上線，需求一次來了好幾個：一天要發上千張集點卡，點數不能被別的程式亂改；購物車要能算總額，也要能從 API 存下來的資料還原；菜單上有咖啡、有茶，共同的部分只想寫一次；客人的 app 還會送來自己的偏好設定 JSON，要合併進預設設定。之後要學的後端框架 NestJS，service、controller 全部是 class，所以這一課的任務是：把這些資料模型寫成 class，並且弄清楚每一步背後發生什麼事。

第一個問題跟記憶體有關。閉包版的集點卡，每發一張卡就產生一份新的 stamp 函式，一千張卡就有一千份內容完全一樣的函式。改成 class 之後，一千張卡是各帶一份 stamp，還是共用同一份？要回答這個問題，得先知道 JavaScript 呼叫 card.stamp() 時去哪裡找 stamp。答案是一個叫原型的機制，JavaScript 內建的 Error、Date、Map 的方法也都靠它。學完這一課，你能畫出物件找屬性的路線、說出 class 語法背後做了什麼、用 #private 把點數藏起來、用 extends 重用行為並判斷什麼時候不該繼承，最後還能認出一種真實存在的資安漏洞：原型污染。

這課的路線：
  1. 物件自己沒寫的方法是從哪來的：原型與原型鏈，JavaScript 找屬性的規則。
  2. 一千張卡的 stamp 是一份還是一千份：class 怎麼把方法放到原型上（開場問題的最小答案）；欄位、static、getter 各放在哪，資料經過 JSON 之後方法為什麼不見。
  3. 點數怎麼不讓外面的程式改：#private。
  4. 咖啡和茶怎麼共用又各自不同：extends 與 super，以及什麼時候該改用組合。
  5. class 為什麼不能先用再宣告：暫時性死區，檔案互相 import 時會怎麼出事。
  6. 合併客人送來的設定，怎麼會讓所有人變成管理員：原型污染與防法。
這課會用到：
  • 第 1 課的 this：點號前面是誰，this 就是誰；class 欄位寫成箭頭函式時，每個實例各一份函式，this 永遠是實例。
  • 第 2 課的參考：兩個變數可以指向同一個物件，一邊改了另一邊也看得到。

物件自己沒寫的方法，是從哪裡來的？

要知道一千張卡的 stamp 是幾份，先看一件更基本的事：寫 obj.method() 時，JavaScript 去哪裡找 method。用一個最小的物件觀察。下面的 drink 只有 name，我們卻去呼叫它沒寫過的 toString()。執行後由上到下看四行：

  • [object Object]：呼叫成功了，可見 toString 確實找得到。
  • false：可是它不在 drink 自己身上。
  • true：drink 背後連著一個叫 Object.prototype 的物件。
  • null：Object.prototype 背後就沒有東西了。

這就是原型（prototype）：每個物件背後都可以連到另一個物件，這個被連到的物件就是它的原型。用 {} 寫出來的普通物件，原型都是 Object.prototype。Object.getPrototypeOf(x) 會回傳 x 的原型，就是範例第三行做的事。

讀屬性時，JavaScript 照這個順序找：

  1. 先找物件自己身上有沒有這個屬性。直接放在物件本身的屬性叫自有屬性（own property），可以用 Object.hasOwn(obj, key) 判斷，就是範例第二行。
  2. 自己沒有，就去原型上找。
  3. 原型也沒有，就去原型的原型找，一路往上，直到碰到 null。走到 null 還沒找到，結果就是 undefined。

這一串「物件 → 原型 → 原型的原型 → … → null」叫原型鏈（prototype chain）。drink 的鏈很短：drink → Object.prototype → null。toString 放在 Object.prototype 上，所以每個普通物件都找得到它，卻沒有任何一個物件自己帶著一份。

為什麼要這樣設計？如果沒有原型，每建立一個物件，toString、hasOwnProperty 這些通用方法就得各複製一份到物件身上，物件越多，重複的函式越多。原型讓「大家都需要、內容都一樣」的東西只存一份，放在鏈上大家共用；物件自己只放屬於自己的資料，例如 name。

要注意方向：只有讀會沿著鏈往上找。寫（例如 drink.toString = …）一律寫在物件自己身上，不會改到原型。寫完之後讀 drink.toString，會先在自己身上找到新的那個；Object.prototype 上原本那份還在，其他物件完全不受影響。這條規則在最後一節很重要：正常的寫入不會碰到原型，原型污染是程式「自己走到原型上去寫」才發生的。

回到開場：只要把 stamp 放在所有集點卡共用的原型上，一千張卡就只需要一份。剩下的問題是，怎麼讓每張新卡都連到同一個原型，並且把方法放上去。

一千張卡，stamp 是一份還是一千份？

上一節說「方法放在共用的原型上」，這一節看實際怎麼做到。class 語法是 ES2015 才有的，在那之前大家用「建構函式＋prototype」手動設定；先看手動版，才看得出 class 幫你做了什麼。

先把幾個名詞講清楚。建構函式是一個普通函式，只是打算用 new 來呼叫。new OldCart(items) 會做三件事：

  1. 建立一個新的空物件，把它的原型設成 OldCart.prototype。
  2. 用這個新物件當 this，執行 OldCart 函式的內容，例如 this.items = items。
  3. 把這個新物件回傳出來。

new 出來的物件叫實例（instance）；new 時負責初始化實例的那段程式叫建構子（constructor）。第 1 步出現的 OldCart.prototype 最容易讓人混淆：用 function 宣告的一般函式（以及 class）身上都有一個名叫 prototype 的屬性（箭頭函式和 class 裡的方法沒有這個屬性，所以不能用 new 呼叫），它不是函式自己的原型，而是「用 new 建立的實例會拿來當原型的那個物件」。所以把方法掛在 OldCart.prototype 上，所有實例的原型鏈上就都有它。

下面用購物車對照兩種寫法。換成購物車是因為它的 total() 要讀實例自己的 items，比蓋章更容易看出「方法共用一份，資料各自一份」；集點卡留到下一節處理點數時再回來。執行後由上到下看：兩台車各自的總額、兩台車的 total 是不是同一個函式、total 放在哪裡、class 本身是什麼、舊寫法算出來對不對。

  • 220 80：兩台車各算各的，因為 items 是在建構子裡用 this.items = items 放在各自身上的。
  • true：兩台車拿到的是同一個 total 函式。
  • false true：total 不在實例 a 身上，在 Cart.prototype 上。
  • function：class 本身就是一個函式，跟 OldCart 一樣可以有 prototype 屬性。
  • 210：舊寫法的行為一模一樣。

這就是開場問題的答案：class 裡用 total() { … } 寫的方法，只存在 Cart.prototype 上一份。呼叫 a.total() 時，a 自己沒有 total，沿著原型鏈在 Cart.prototype 找到它，再依第 1 課的規則，用點號前面的 a 當 this 呼叫，所以算的是 a 的 items。一千張集點卡寫成 class，stamp 也只有一份；閉包版則是每張卡一份，因為每次呼叫 makeStampCard() 都會建立新的函式。

所以 class 並沒有發明新的機制，它做的就是手動版那兩步：constructor 的內容對應建構函式本體，方法寫在 class 裡面就等於掛到 Cart.prototype 上。兩種寫法還是有幾個小差異，例如 class 一定要用 new 呼叫，細節見課末。

折扣、從 JSON 還原、讀總額：每種成員放在哪裡？

實際的購物車不只 items 和 total()：還要記折扣、要能從 API 存下來的 JSON 還原、讀總額最好像讀屬性一樣不用加括號。class 為這些需求各準備了一種寫法，它們放的位置不同，份數也不同。先認識四種寫法：

  • 類別欄位（class field）：直接在 class 裡寫 items = []，效果相當於在建構子裡寫 this.items = []，每個實例建立時各放一份到自己身上。
  • 箭頭函式欄位：類別欄位的值是一個箭頭函式，例如 log = () => …。它也是欄位，所以每個實例各有一份函式。
  • 靜態成員（static member）：前面加 static，放在 class 本身（Cart 這個函式）上，不在實例上，用 Cart.fromJSON() 呼叫。適合「還沒有實例時就要用」的功能，例如從資料建立實例。
  • getter：前面加 get，讀 cart.total 時執行這個函式並回傳結果，寫起來像屬性，不用加括號。它跟一般方法一樣放在原型上。

執行後由上到下看：還原出來的購物車總額、實例上有哪些自有屬性、兩個實例的 log 是不是同一個函式、實例找不找得到 fromJSON：

  • total: 250：fromJSON 還原出真正的 Cart 實例，getter 用 120 × 1 ＋ 80 × 2 − 30 算出總額。
  • ['items', 'discount', 'log']：三個欄位都在實例自己身上；total 是 getter，在原型上，所以不在這裡。
  • false：箭頭函式欄位每個實例各一份，兩個實例的 log 不是同一個函式。
  • false：最後一行的 in 會檢查物件自己和整條原型鏈，連鏈上都沒有 fromJSON，因為它放在 Cart 本身，不在 Cart.prototype。
寫法放在哪裡份數
total() { … }（方法）Cart.prototype全部實例共用一份
items = []（類別欄位）每個實例自己身上每個實例一份
log = () => …（箭頭函式欄位）每個實例自己身上每個實例一份函式；換來 this 永遠是實例
static fromJSON() { … }（靜態成員）Cart 本身一份，用 Cart.fromJSON() 呼叫
get total() { … }（getter）Cart.prototype共用；讀 cart.total 時才計算

箭頭函式欄位是一個取捨。第 1 課講過，把上一節的一般方法交出去當 callback（例如 setTimeout(a.total, 0)）時，呼叫的人不是 a，this 就不見了。注意這一節的 total 是 getter，cart.total 會當場算出數字，不是交出方法，所以要拿 log 這種方法來比；箭頭函式沒有自己的 this，用的是建立它時的實例，所以交出去也不會掉。代價有兩個：每個實例多一份函式，一千個實例就一千份，回到開場想避免的情況；它也不在原型上，子類別沒辦法用後面會教的 super 呼叫它。所以預設用一般方法，只有真的要把方法交出去當 callback 時才用箭頭函式欄位。

static fromJSON 解決的是另一個問題。第 2 課講過，JSON.stringify 只留下資料，JSON.parse 和 structuredClone 還原出來的是普通物件，原型是 Object.prototype，不是 Cart.prototype。資料都還在，但原型鏈上找不到 total，方法就叫不到了。fromJSON 的做法是先 new Cart() 建立一個原型正確的實例，再把資料一欄一欄放回去，等於把原型重新接上。

💡 實務上：資料一過邊界，方法就沒了
class 實例在工作中最常在「邊界」出事：API 回應、存進 localStorage、SSR 時把狀態從伺服器帶到瀏覽器、丟給 Web Worker，只要經過 JSON 或 structuredClone，回來的都只剩資料。所以常見的寫法是 Pinia、Redux 這類狀態管理裡只放純資料（Redux 官方也建議 state 只放可序列化的值），計算（例如購物車總額）寫成獨立函式；真的需要 class 時，就在資料進來的那一個地方統一用 fromJSON 還原，不要散在各處。看到 cart.addItem is not a function，或 getter 突然讀到 undefined，資深工程師第一個會問：這份資料剛剛是不是被序列化過？

方法共用的問題解決了，但還有一個：items、discount 都是普通欄位，任何拿到這個物件的程式都能直接改。購物車被改了頂多算錯錢；集點卡的點數如果能被直接寫成 999，就等於在送咖啡。

集點卡的點數，怎麼不讓外面的程式改？

上一節的欄位誰都能讀寫：拿到集點卡的程式寫一行 card.points = 999 就改掉了。第 1 課閉包版的集點卡沒有這個問題，因為點數藏在閉包裡，外面根本拿不到。改成 class 之後，要怎麼保住「藏起來」這個優點，同時保有上一節的「方法共用一份」？

答案是私有欄位（private field）：名字前面加 # 的欄位，例如 #points，是 ES2022 加入的語法。它有三個特性：

  • 只有寫在這個 class 大括號裡面的程式碼能讀寫它，外面完全拿不到。
  • 它不是一般的屬性，所以 Object.keys、JSON.stringify、structuredClone 都看不到它。
  • 方法還是放在原型上共用，stamp() 透過 this 讀寫當下那張卡的 #points。

外面要讀點數怎麼辦？提供一個只有 getter、沒有 setter 的 points：讀得到，寫不進去。下面的 StampCard 還多了一個 static isCard(x)，裡面的 #points in x 檢查 x 身上有沒有這個私有欄位。私有欄位只有用這個 class 建立的實例才會有，所以它能分辨「真的集點卡」和「長得很像的普通物件」：{ points: 999 } 有 points 屬性，用 'points' in x 檢查會被騙過，用 #points in x 不會。

執行後由上到下看：蓋兩次章後的點數、Object.keys 和 JSON.stringify 看到什麼、假卡片和真卡片的檢查結果、直接改點數的下場：

  • points: 2：透過 getter 讀得到點數。
  • [] 和 {}：實例上沒有任何一般屬性，#points 不會出現在這裡。
  • false／true：假卡片騙不過 #points in x。
  • TypeError：points 只有 getter，寫入會丟錯。這頁的程式跟 class 內部一樣在嚴格模式下執行，才會丟錯；非嚴格模式下這行寫入會被默默忽略，點數一樣不會變。

那在 class 外面直接寫 card.#points 呢？這不是執行時才出錯，而是語法錯誤（SyntaxError）：JavaScript 在執行前先讀整份程式，讀到這行就拒絕，整段程式一行都不會跑。所以這裡只能用不能執行的方式展示：

const card = new StampCard()
console.log(card.#points)
// SyntaxError: Private field '#points' must be declared in an enclosing class

這是好事：違規的寫法在編輯器裡、在部署之前就會被抓到，不會等到線上才發現點數被改。

到這裡有好幾種「藏狀態」的做法，它們擋得住的程度不一樣：

做法外面拿得到嗎說明
普通欄位 points = 0拿得到，也改得到誰都可以 card.points = 999
閉包（第 1 課的 makeStampCard）拿不到回傳的是普通物件，沒有 class、沒有 instanceof；方法每張卡一份
#points拿不到方法仍在原型上共用；Object.keys、JSON.stringify、structuredClone 都看不到它
TypeScript 的 private points拿得到只在編譯時檢查，執行時就是普通屬性（第 23 課）

最後一列要特別記住：之後寫 TypeScript 時看到的 private 關鍵字只是編譯時的提醒，編譯成 JavaScript 之後就是普通屬性，執行時任何程式都讀得到。真的要在執行時擋住，用 #。

#private 也帶來一個新問題：JSON.stringify(card) 得到 {}，點數存不下來。要存成 JSON 時，自己寫一個 toJSON() 方法回傳要存的資料（JSON.stringify 遇到有 toJSON 的物件會改用它的回傳值），還原時用上一節的 static fromJSON。fromJSON 寫在 class 裡面，所以可以直接設定新實例的 #points。練習 2 就是把這整張集點卡寫出來。

集點卡只有一種，寫一個 class 就夠了。菜單不一樣：咖啡和茶都有名字和價格，咖啡另外有濃縮份數，茶另外有甜度。共同的部分要怎麼只寫一次？

咖啡和茶都是飲料：怎麼共用又各自不同？

咖啡和茶共用「名字、價格、印出說明」，又各自多一點東西。最直接的做法是繼承（inheritance）：先寫一個通用的 Drink，叫父類別；再寫 class Tea extends Drink，Tea 叫子類別，自動擁有 Drink 的方法，只要寫自己不一樣的部分。

extends 沒有把 Drink 的方法複製一份給 Tea，它做的還是第一節的原型鏈：把 Tea.prototype 的原型設成 Drink.prototype。於是 Tea 實例的鏈變成「實例 → Tea.prototype → Drink.prototype → Object.prototype → null」，Tea.prototype 上找不到的方法，就會往上在 Drink.prototype 找到。下圖用練習 3 會寫的 Coffee 畫出同樣的結構。圖裡假設 Drink 另外有一個 isHot() 方法，Coffee 自己沒寫，用來示範往上找到父類別的過程：

子類別常常要「在父類別的基礎上多做一點」，這時用 super。它有兩種用法：

  • 在建構子裡寫 super(name, price)：呼叫父類別的建構子，讓 Drink 把 name、price 設好。
  • 在方法裡寫 super.describe()：呼叫父類別的同名方法。Tea 自己也有 describe，寫 this.describe() 會先找到自己這個，變成呼叫自己；super.describe() 則是直接從父類別那一層開始找。

範例最後的 Broken 故意在 super() 之前用 this，看看會怎樣。執行後由上到下看：茶的說明、三個 instanceof、原型有沒有接上、Broken 丟出的錯誤：

  • 伯爵紅茶 90 元，半糖：前半段是 super.describe() 從 Drink 拿到的，後半段是 Tea 自己加的。
  • true true true：tea 同時是 Tea、Drink、Object 的實例。
  • true：Tea.prototype 的原型就是 Drink.prototype，這就是 extends 做的事。
  • ReferenceError：子類別的建構子沒先呼叫 super() 就用了 this。

最後一個錯誤的原因是：有 extends 的 class，實例是由父類別的建構子建立的。呼叫 super() 之前，實例還不存在，this 也就還沒有值，這時碰 this 就丟 ReferenceError。所以子類別建構子的第一件事一定是 super(…)，之後才設定自己的欄位。範例用 try／catch 接住錯誤、把訊息印出來，第 4 課會完整講。

第二行的 instanceof 也值得看清楚：x instanceof C 檢查的是「C.prototype 在不在 x 的原型鏈上」，不是比對 class 的名字。tea 的鏈上有 Drink.prototype，所以 tea instanceof Drink 也是 true。第 4 課用 instanceof 分辨不同的錯誤時，靠的就是這條規則。

繼承用起來很順手，於是很容易被拿去做不適合的事。下一個需求是訂單折扣，它也該用繼承嗎？

每多一種折扣就多一層子類別？什麼時候不要繼承

咖啡店的訂單有會員 9 折、下午茶時段折 20 元。用繼承的思路會寫出 MemberOrder extends Order、HappyHourOrder extends Order；會員在下午茶時段點餐，又要一個 MemberHappyHourOrder。每多一種折扣，組合就多好幾個子類別。問題出在：折扣不是一種訂單，它只是訂單「怎麼算價錢」的一個部分。

繼承只適合真正的「是一種」：茶是一種飲料，所以 Tea extends Drink 合理。如果只是想共用幾行程式，或想讓某個行為可以替換，用組合（composition）：把那個行為做成獨立的物件，當成欄位或參數傳進來。下面的 Order 不知道有哪些折扣，只知道自己有一個 pricingRule，它有 apply(total) 可以算價錢。執行後看同一份品項在三種規則下的總額：

110 ＋ 70 是 180，會員 9 折是 162，下午茶折 20 是 160。新增一種折扣只要多寫一個有 apply 的物件，Order 一行都不用改。對照繼承，差別在這幾點：

  • 改動範圍：繼承鏈每深一層，改父類別就可能影響所有子孫；組合的規則彼此獨立，改一個不影響別的。
  • 讀程式：繼承要往上讀好幾個檔案，才知道一個方法最後做了什麼；組合只要看傳進來的是哪個物件。
  • 測試與替換：每個規則可以單獨測試，也可以在執行時換掉，例如依時段決定傳哪個規則。

第 23 課的依賴注入、整個 NestJS 框架，都是組合的思路：service 需要的東西由外面傳進來，而不是繼承來的。

💡 實務上：會一直變多的東西，用組合
咖啡店的折扣規則、金流（信用卡、LINE Pay）、通知管道（Email、簡訊、推播）都屬於「之後一定會再加一種」的東西，做成可替換的物件傳進去，加新的一種只要多寫一個，不用動到既有的程式。繼承在實務上還是有合理用途，例如自訂錯誤類別 extends Error（第 4 課），或框架要求你繼承它的基底類別。Code review 時看到 BaseService 底下又繼承兩三層，資深工程師會問：子類別真的「是一種」父類別，還是只是想共用幾個方法？

到這裡已經寫了好幾個 class，而且 Tea extends Drink 要求 Drink 先存在。如果宣告的順序反了，或這些 class 拆到不同檔案互相 import，會發生什麼事？

為什麼 class 不能先用再宣告？

上一節的 Tea 寫在 Drink 下面。如果反過來，或在 class 那一行之前就 new 它，結果跟 function 不一樣。先看 function：function 宣告會提升（hoisting），意思是 JavaScript 在執行程式之前，就先把整個檔案裡的 function 宣告準備好，所以寫在檔案後面的 function，前面也能呼叫。

class 不會這樣。let、const、class 宣告的名字，從所在區塊的開頭到宣告那一行之間，處於一段「名字存在但還不能用」的區間，叫暫時性死區（temporal dead zone，簡稱 TDZ）。在這段區間裡讀取它，會丟 ReferenceError。這樣設計是為了讓「還沒執行到宣告就使用」變成明確的錯誤，而不是像 var 那樣安靜地拿到 undefined，等到後面才莫名其妙地出錯。

執行後由上到下看：寫在後面的 function 能不能先呼叫、class 在宣告前被 new 的錯誤訊息、宣告後是否正常：

第一行印出「拿鐵做好了」，function 先用沒問題；第二行是 Cannot access 'Later' before initialization，這句錯誤訊息要記住，之後會在別的地方看到它；第三行是 true，宣告之後就一切正常。

單一檔案裡很好避免：先宣告再使用。麻煩的是好幾個檔案互相 import。例如 order.js import 了 member.js，member.js 又 import 了 order.js，這叫循環依賴（circular dependency）。模組是一個檔案接一個檔案由上往下執行的，循環的時候，總有一邊在用到另一邊的 class 時，另一邊的檔案還沒執行到 class 那一行。於是你會在一個看起來完全正確的檔案裡看到 Cannot access '…' before initialization，或是拿到 undefined。NestJS 裡兩個 service 互相依賴，就會出現同樣的狀況，第 24 課和第 25 課會再遇到它。看到這句錯誤訊息，先檢查的不是那一行，而是 import 有沒有繞成一圈。

前面五節處理的都是我們自己寫的 class 和物件。最後一個需求不一樣：要接住客人 app 送來的資料。這時原型鏈會從「共用方法的機制」變成攻擊入口。

合併客人送來的設定，怎麼會讓所有人變成管理員？

需求是這樣的：客人在 app 裡調整自己的偏好（主題、預設甜度、冰塊），app 把設定 JSON 送到後端，後端把它合併進預設設定。設定是巢狀的，例如 options.ice，所以很多人會寫一個「逐鍵遞迴」的深層合併（deep merge）：走訪來源的每個鍵，值是物件就往下一層合併，不是物件就直接覆蓋。

要看懂這裡的漏洞，先認識一個特別的名字 __proto__。Object.prototype 上有一個叫 __proto__ 的存取器，也就是一組 getter／setter：讀 obj.__proto__ 會拿到 obj 的原型，寫它則會換掉 obj 的原型。它是 Object.getPrototypeOf 出現以前的舊寫法，至今還在，而且因為放在 Object.prototype 上，每個普通物件沿著原型鏈都找得到它。

漏洞由兩件事湊在一起：

  1. JSON.parse 看到 "__proto__" 這個鍵，會把它當成普通的鍵，在物件上建立一個名叫 __proto__ 的自有屬性，不會去動原型。這一步本身沒問題。
  2. merge 走訪到這個鍵，用 target['__proto__'] 讀目標物件。目標物件自己沒有叫 __proto__ 的自有屬性，就沿著原型鏈找到那個存取器，讀到的是 Object.prototype。merge 以為這是一個普通的巢狀設定物件，就遞迴進去，把 isAdmin: true 寫到 Object.prototype 上。

執行後由上到下看：body 自有的鍵、合併後一個完全無關的空物件有沒有 isAdmin、清掉之後的結果。範例最後用 delete 把寫進去的 isAdmin 刪掉，示範污染要手動清掉才會消失（這頁每個範例都在獨立的 Worker 裡執行，本來就不會互相影響）；真正的伺服器沒有人會幫你刪，所以會一直留到重啟：

  • ['theme', '__proto__']：JSON.parse 真的把 __proto__ 當成普通的自有鍵。
  • true：someUser 跟這次請求毫無關係，卻多了 isAdmin。它是從 Object.prototype 繼承來的。
  • undefined：刪掉 Object.prototype.isAdmin 之後恢復正常。

這叫原型污染（prototype pollution）：攻擊者讓程式去改 Object.prototype，所有普通物件從此都「繼承」到攻擊者塞的屬性。如果某處寫 if (user.isAdmin)，而 user 物件本來沒有這個欄位，現在每個人都是管理員。

在後端，影響範圍比前端大得多。伺服器程式啟動之後，會在記憶體裡持續執行同一份，這一份執行中的程式叫程序（process）。它會一直跑著，處理所有客人的請求，而所有請求共用同一個 Object.prototype。所以一次污染，會影響之後所有人的請求，直到伺服器重啟。前端被污染只影響那一個分頁。

只擋 __proto__ 這個鍵還不夠，還有第二條路：{"constructor":{"prototype":{"isAdmin":true}}}。任何普通物件的 constructor 屬性（從 Object.prototype 繼承來的）是 Object 這個函式，而 Object.prototype 就是 Object 函式的 prototype 屬性。merge 沿著 target.constructor.prototype 一層層遞迴下去，最後寫到的一樣是 Object.prototype。

防法由淺到深有三層。

第一層：跳過危險的鍵，並且只走訪自有屬性。遇到 __proto__、constructor、prototype 一律跳過。至於「只走訪自有屬性」，是因為上面的 naiveMerge 用 for…in 走訪來源，而 for…in 不只走自有屬性。下面用 Object.create(proto) 建立一個原型是 proto 的新物件，模擬「繼承了預設值的訂單」，看看 for…in 會走到什麼。執行後比較 for…in 和 Object.keys 列出的鍵：

for…in 列出了 size 和 ice，Object.keys 只列出 size；order.ice 讀得到「正常冰」，但它不是自有屬性。差別在於 for…in 會走訪整條原型鏈上所有可列舉的屬性，而 Object.keys、Object.entries、JSON.stringify 只看物件自己的可列舉屬性。

可列舉（enumerable）是每個屬性身上的一個開關，決定它會不會被這類走訪列出來。自己用 obj.x = 1 加的屬性是開的；內建的 toString 這類方法是關的，所以 for…in 不會跑出 toString。可是只要原型鏈上有人加了可列舉的屬性，例如被污染後的 isAdmin，for…in 就會把它當成來源的資料一起合併進去。所以合併、複製、走訪物件時一律用 Object.keys／Object.entries。練習 4 就是把這一層寫出來。

第二層：只取預期的欄位（白名單）。第一層是在「把整包使用者資料合併進來」的前提下擋掉危險的鍵，但擋得住已知的鍵，擋不住不該有的欄位，例如客人自己塞一個 vipLevel。更可靠的做法是根本不合併整包：先定義設定應該有哪些欄位、各是什麼型別，一個一個驗證後取出，其他的全部丟掉。第 26 課的 schema 就是做這件事，這是最可靠的做法。

第三層：用使用者給的字串當鍵時，用 Map 或 Object.create(null)。這是另一種常見情境：用物件當字典，例如以商品代號為鍵統計銷量。如果商品代號是使用者輸入的，剛好是 __proto__ 時，寫入會打到那個存取器，而不是存成一筆資料。Object.create(null) 建立的是沒有原型的物件，鏈上沒有存取器，也沒有 toString，__proto__ 就只是一個普通的鍵；Map（第 2 課的鍵值對照表）的鍵不是物件屬性，根本不會碰到原型鏈。執行後比較三種字典存進 __proto__ 的結果：

  • 普通物件：Object.keys 是空的，counts.__proto__ 還是 Object.prototype。這次寫入打到了存取器，而原型只能設成物件或 null，給數字 5 就被忽略，這筆資料就這樣不見了。
  • 沒有原型的物件：鍵 __proto__ 正常存進去，讀得到 5。
  • Map：一樣讀得到 5。

Node 還有一個關掉 __proto__ 存取器的啟動選項，但它擋不住 constructor.prototype 這條路，細節見課末。

💡 實務上：你最常在 npm audit 的報告裡遇到它
自己寫出原型污染的機會不多，更常見的是工具告訴你。npm audit 是檢查專案已安裝的套件有沒有已知漏洞的指令，GitHub 的 Dependabot 也會做同樣的檢查並發通知。它們常回報某個套件（deep merge、設定檔解析、query string 解析這類）有 prototype pollution 漏洞。資深工程師不會看到就慌，也不會直接忽略，而是先確認：這個函式有沒有吃到使用者可以控制的資料？有就優先升級，沒有也排進下一次更新。也別一看到報告就跑 npm audit fix --force，它可能直接把套件升到不相容的大版本，修了漏洞卻弄壞功能。

練習

練習 1：下面的 Cart 在建構函式裡把 total 塞進每個實例，一千台購物車就有一千份 total。不要改成 class，維持建構函式寫法，把 total 移到原型上，讓所有實例共用一份。

練習 2：寫 class StampCard：

  • 點數存在私有欄位 #points，new StampCard() 從 0 點開始。
  • stamp()：加 1 點，回傳目前點數。
  • redeem(n)：兌換 n 點，回傳剩下的點數。點數不夠時 throw new RangeError('點數不足')，而且點數不能被扣掉。throw 會中斷函式、把錯誤交給呼叫者；RangeError 是內建的錯誤，代表值超出允許範圍（第 4 課細講）。
  • get points：讀目前點數。只有 getter，外面不能直接改點數。
  • static fromJSON({ points })：從存起來的資料還原一張卡。

方法用一般的方法寫法，放在原型上。

練習 3：已經有 class Drink。寫 class Coffee extends Drink：

  • 建構子 (name, price, shots)，shots 是濃縮的份數，沒給時是 1。
  • 覆寫 describe()：在父類別的結果後面加上「（2 份濃縮）」。要用 super.describe() 重用父類別，不要把字串重寫一次。

例如 new Coffee('拿鐵', 110, 2).describe() 是「拿鐵 110 元（2 份濃縮）」。

練習 4：寫 safeMerge(target, source)，把使用者送來的設定（JSON.parse 的結果）深層合併進 target，回傳 target：

  • 只處理 source 的自有屬性。
  • 兩邊都是普通物件（不是陣列、不是 null）時遞迴合併；target 沒有這個鍵時，合併進一個新的 {}。
  • 其他值（字串、數字、陣列、null……）直接取代。
  • 遇到 __proto__、constructor、prototype 鍵一律跳過。

練習 5：class Cart { total() { return 0 } }，const a = new Cart()、const b = new Cart()。a.total === b.total 是什麼？

✓ class 裡的一般方法只存在原型上一份，a、b 自己都沒有 total，往原型找到同一個函式。this 是呼叫時才決定的，跟函式是不是同一個無關。只有寫成類別欄位（total = () => …）才會每個實例一份。

練習 6：在 class Shop {} 那一行之前執行 new Shop()，會發生什麼？

✓ class 跟 let、const 一樣有暫時性死區，宣告那一行之前存取就丟 ReferenceError。會提升且可以先呼叫的是 function 宣告；var 提升後是 undefined，class 不是這樣。多個檔案循環 import 時，NestJS 會因為同樣的原因出錯。

練習 7：把 JSON.parse('{"__proto__":{"isAdmin":true}}') 交給本課範例裡 naiveMerge 那種「沒過濾鍵、逐鍵遞迴」的 deep merge 之後，({}).isAdmin 是什麼？

✓ JSON.parse 本身沒問題，它把 __proto__ 當成普通的自有鍵。出事的是 merge：target['__proto__'] 讀到的是 Object.prototype，遞迴寫進去就污染了所有物件。JSON 規格沒有禁止這個鍵，不會丟錯。

常見錯誤

  • 以為 class 的方法每個實例各一份：一般方法和 getter 只存在原型上一份；只有寫成類別欄位（total = () => …）才會每個實例一份。
  • 以為 TypeScript 的 private 等於 #private：TS 的 private 只在編譯時檢查，執行時任何人都讀得到（第 23 課）。要在執行時擋住，用 #。
  • 子類別建構子忘了先呼叫 super()：還沒 super 就用 this 會丟 ReferenceError。建構子第一件事就是 super(…)。
  • 為了共用程式碼而繼承：繼承鏈越來越深，改一個父類別牽動所有子孫。只有「是一種」才繼承，行為的差異用組合傳進來。
  • 以為 class 像 function 一樣會提升：class 有暫時性死區，宣告之前不能用。在看似正確的檔案看到 Cannot access '…' before initialization，先查 import 有沒有繞成一圈。
  • 把使用者送來的物件直接合併進設定或資料物件：會被原型污染，或被塞進不該有的欄位。只取預期的欄位，至少要跳過 __proto__、constructor、prototype。
  • 用 for…in 走訪物件：會走到原型鏈上繼承來的可列舉屬性。改用 Object.keys／Object.entries，或搭配 Object.hasOwn。
  • 用普通物件當字典存使用者提供的鍵：鍵是 __proto__ 時不會存成資料。改用 Map 或 Object.create(null)。

補充與查表

主線用不到、但遇到時要知道的細節。

class 與建構函式寫法的差異

class 做的事跟「建構函式＋prototype」相同，但有三個差異：

  • class 一定要用 new 呼叫，直接寫 Cart() 會丟 TypeError；建構函式不加 new 也能呼叫，只是 this 不是新物件，很容易寫錯。
  • class 裡的方法不可列舉，所以 for…in 走訪實例時不會列出它們；用 OldCart.prototype.total = … 掛上去的方法是可列舉的。
  • class 的內容一律是嚴格模式。

Object.hasOwn 與 hasOwnProperty

Object.hasOwn(obj, key) 是 ES2022 加入的。舊程式常見 obj.hasOwnProperty(key)，判斷的是同一件事，但它是從原型鏈上找來的方法：物件沒有原型（Object.create(null)）時根本沒有這個方法，物件自己有一個叫 hasOwnProperty 的鍵時也會被蓋掉。所以新程式用 Object.hasOwn。

Node 的 --disable-proto 選項

Node 有 --disable-proto=delete 或 =throw 選項，可以移除或封鎖 __proto__ 存取器，但擋不住 constructor.prototype 這條路。不要把它當成唯一的防線；伺服器端的整體防護在 Node 課第 25 課。

小結

  • 物件自己沒寫的方法從哪來：讀屬性時先找自己，沒有就沿著原型鏈往上找，普通物件的鏈是自己 → Object.prototype → null。寫屬性一律寫在物件自己身上，不會改到原型。
  • 一千張卡的方法是幾份：一份。class 是設定原型的語法：方法和 getter 放在 prototype 上共用，類別欄位（包括箭頭函式欄位）每個實例一份，static 放在 class 本身。資料經過 JSON 或 structuredClone 會失去原型，用 static fromJSON 接回來。
  • 點數怎麼不讓外面改：#private 在執行時真正拿不到，方法仍然共用；只給 getter 就是唯讀。TypeScript 的 private 只是編譯時的提醒。
  • 咖啡和茶怎麼共用：extends 把子類別的原型接到父類別；子類別建構子先 super() 才能用 this；super.method() 重用父類別；instanceof 檢查原型鏈。只有「是一種」才繼承，會一直變多的行為用組合傳進來。
  • class 為什麼不能先用：class 有暫時性死區，宣告之前用會丟 ReferenceError；多個檔案循環 import 時就會碰到。
  • 合併使用者資料：deep merge 讀到 target['__proto__'] 或 constructor.prototype 就會污染 Object.prototype，影響整個程序。跳過 __proto__、constructor、prototype 並只走訪自有屬性，最好只取預期的欄位；字典用 Map 或 Object.create(null)。
