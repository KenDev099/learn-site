階段 3：型別基礎 · 第 13 課

TypeScript 在做什麼

前 12 課寫的都是 JavaScript，從這一課起練習區改成 TypeScript。先從一個你在 Vue 專案裡多半遇過的情況開始。

咖啡店後台的結帳頁要印收據，每一行長得像「拿鐵 ×2 = 220」。同事寫了 receiptLine 送上來請你審，你在編輯器裡打開，看到其中一行有紅線：

function lineTotal(price: number, quantity: number) {
  return price * quantity
}

function receiptLine(item: { name: string; price: number }, quantity: number) {
  const total = lineTotal(item.prise, '2')     // ← 這一行有紅線
  return `${item.name} ×${quantity} = ${total}`
}

同事說：「npm run dev 跑得起來，頁面也出得來，只是金額那格顯示 NaN，應該是後端資料的問題。紅線不影響執行，先不管吧？」

這一課要回答他：紅線到底是什麼、為什麼有紅線程式還能跑、紅線跟那個 NaN 有沒有關係。答完之後，你會讀懂錯誤訊息、知道型別寫在哪裡、哪些交給 TypeScript 自己推，也會知道為什麼有的專案抓得到這類 bug、有的抓不到。練習 1 就是動手修好這支 receiptLine。

這課的路線：
  1. 有紅線，為什麼程式還跑得起來？TypeScript 做兩件互不相干的事：檢查型別、擦掉型別。紅線不擋執行，但它預告了執行時會出的錯（開場問題的最小答案）。
  2. 紅線在說什麼？一個錯誤看三樣：第幾行、訊息、代碼，用它們讀懂 receiptLine 的紅線，也看出 NaN 從哪來。
  3. 紅線拿什麼當標準？型別註記寫在哪裡，常用的幾種型別怎麼寫。
  4. 每個值都要自己寫型別嗎？推論幫你補上大部分，只有幾個地方一定要自己寫。
  5. 為什麼同一段程式，有的專案有紅線、有的沒有？strict 擋下隱含的 any 和可能是 undefined 的值，也就是線上最常見的「讀到 undefined 當掉」。
這課會用到：
  • 第 5 課的金額字串：從表單、API 進來的價格是字串；字串碰到 + 會變成接字串（那課的 toFixed(0) + 1 就是這樣），所以 '100' + 60 會串成 '10060'，不會變成 160。
從這一課開始，練習區寫的是 TypeScript。編輯器跟 VS Code 一樣：滑鼠移到變數上會顯示推論出來的型別，寫錯的地方會當場畫紅線。

有紅線，為什麼程式還跑得起來？

要回答同事，先要知道 TypeScript 拿到你的 .ts 檔之後做了什麼。先鋪兩個詞。

型別（type）是對一個值的描述：它是哪一種資料、可以拿來做什麼。說一個值的型別是 number，意思是它是數字，可以拿來加減乘除；型別是 string，就是一段文字，可以取長度、串接。

型別註記（type annotation）是你寫在名稱後面、冒號之後的那段型別。price: number 裡的 : number 就是型別註記，它在宣告「price 只能放數字」。JavaScript 沒有這種寫法，TypeScript 可以想成「JavaScript 加上型別註記」。

問題是，瀏覽器和 Node 只看得懂 JavaScript，不認得 : number。所以 TypeScript 對每個檔案做兩件事：

  1. 型別檢查（type checking）：讀你的程式，拿型別註記當標準，找出值跟型別對不上的地方，列成錯誤清單。編輯器裡的紅線，就是這份清單畫在程式碼上的樣子。
  2. 擦掉型別（type erasure）：把所有型別註記拿掉，剩下的就是普通的 JavaScript，拿去執行。

這兩件事互不影響。檢查找到錯誤，不會擋住擦掉型別；擦掉型別的時候，也不管檢查結果是什麼。就像文書軟體的拼字檢查：錯字會畫紅線，但不會擋住你列印；印出來的紙上也不會有紅線。

為什麼要這樣設計？TypeScript 的定位是「在 JavaScript 上面加一層檢查」，不是另一種語言。擦掉型別之後剩下的必須是原原本本的 JavaScript，才能在任何瀏覽器、任何 Node 版本上執行，也才能跟現有的 JS 套件混著用。代價是：型別只存在於編譯時，也就是你寫程式、跑檢查的時候；到了執行時，也就是程式真的在瀏覽器或伺服器上跑的時候，型別已經完全不存在，沒有任何東西會再檢查一次。

這就是開場問題的最小答案。同事說的前半句是對的：紅線不影響執行，因為紅線來自第一條路，頁面來自第二條路。但後半句錯了：「跑得起來」不等於「跑得對」。上面的 11010 正是紅線事先告訴你的那個錯，程式只是沒有為了它停下來。同事收據上的 NaN 也是同一回事，下一節會看到。

那為什麼 npm run dev 一句都沒提？因為在實際專案裡，負責「擦掉型別」和負責「檢查型別」的常常是不同的工具：

實際專案裡，是誰在檢查型別？
  • tsc（TypeScript 官方的命令列編譯器）兩件事都做，但遇到型別錯誤時，預設照樣輸出 JS。要開 noEmitOnError 才會擋下來。
  • Vite（你的 Vue 專案用的開發伺服器和打包工具）只轉譯、不檢查：把 TS 轉成 JS 就交出去。官方文件說型別檢查交給編輯器和建置流程，Vue 專案通常用 vue-tsc，它是會連 .vue 檔一起檢查的 tsc。
  • Node 24 可以直接執行 .ts 檔，但一樣只是擦掉型別，不做檢查。
所以「跑得起來」不代表沒有型別錯誤，要另外跑 tsc --noEmit（只檢查、不輸出檔案）或 vue-tsc 才知道。

同事跑的 npm run dev 背後是 Vite，它從頭到尾沒有檢查型別，所以一句都沒提。紅線只出現在有開這個檔案的編輯器裡，這也是為什麼團隊不能只靠每個人自己看紅線。

💡 實務上：型別檢查要放進 CI，不能只靠編輯器紅線
開發時 Vite 不擋型別錯誤，同事沒開編輯器的那個檔案、或改了共用型別連帶壞掉的其他檔案，紅線你都看不到。所以團隊會設 CI：一台在每次有人推上程式碼、開合併請求（pull request，常簡稱 PR）時自動跑檢查的伺服器。做法是在 package.json 放一個 type-check 腳本，讓 CI 在每個 PR 都跑一次，沒過就不能合併；像開場這支 receiptLine，就會在 PR 上被擋下來，輪不到你審。用 create-vue 選 TypeScript 建的專案已經有這個腳本，npm run build 也會一起跑它，型別有錯 build 就失敗。接手專案時，資深工程師會先看兩件事：CI 有沒有跑型別檢查、build 指令會不會因為型別錯誤失敗。如果兩個都沒有，型別錯誤可能已經默默累積了幾百個。

紅線在說什麼？讀懂錯誤訊息

知道紅線不能不管之後，下一步是看懂它在說什麼。同事那一行 lineTotal(item.prise, '2') 其實藏了兩個錯。下面這格把咖啡店程式最常見的三種寫錯放在一起：欄位名稱拼錯、參數型別不對、少傳一個參數，前兩種就是同事那兩個錯。執行後先看錯誤清單，再看印出來的結果：

錯誤清單裡的每一個錯誤，都有三樣東西：

  • 第幾行：錯在哪裡。先跳到那一行，看紅線畫在哪幾個字底下，通常就是對不上的那個值。
  • 訊息：哪個型別跟哪個型別對不上。訊息是英文，但句型就那幾種，例如參數型別不對時會說 Argument of type 'string' is not assignable to parameter of type 'number'：你傳的是 string，這個參數要的是 number。看久了就熟。
  • 代碼：TS 加一串數字，像 TS2345。同一類錯誤永遠是同一個代碼，卡住時拿代碼去查，會比貼整段訊息好找，也不受訊息裡你自己的變數名稱干擾。

再看執行結果：第一行印出 undefined，因為物件上沒有 prise 這個屬性；第二行碰巧算對，因為 * 會把 '2' 轉成數字，換成 + 就會變成字串串接；第三行少了 quantity，110 * undefined 變成 NaN。型別錯誤不一定當場出事，但遲早會。

現在可以解釋同事的 NaN 了。item.prise 拼錯，拿到的是 undefined，undefined * '2' 就是 NaN，跟後端資料無關。第二條紅線在 '2' 底下，它只說「string 不能給 number」，也就是型別不對；它指出這裡有問題，但沒告訴你該怎麼改。把 '2' 改成數字 2，紅線就消失了，可是數量還是寫死的：客人點三杯，收據照樣印兩杯的錢。正確的修法是傳入參數 quantity。所以練習 1 只把 '2' 改成 2 不會過關：紅線消失不等於修好，紅線只是告訴你該去看哪裡。

工作中最常見的錯誤代碼不多，下面這張表查表用，不用背。表裡出現的 any 先說明一下：它是 TypeScript 的「不檢查」型別，什麼值都能放、什麼操作都允許，等於對這個值關掉型別檢查。它存在是為了讓 TypeScript 能跟沒有型別的 JavaScript 程式共處，代價是 any 經過的地方都不會有紅線。「隱含的 any」是你沒寫型別、TypeScript 也推不出來，只好自己補上的 any，因為它會悄悄關掉檢查，所以 TypeScript 要報錯提醒你（後面講 strict 時會再遇到它）。

升級套件、改了共用的 Order 型別、或從 API 拿到新欄位後，常常一次冒出幾十個錯誤。很多是同一個原因連帶出來的：一個型別寫錯，所有用到它的地方都會報錯，所以先修最上游（型別定義、共用函式）的那個，再重新看剩下幾個。訊息很長、分好幾層縮排時，通常最後一層才是真正對不上的那個屬性。在 PR 上跟同事說明時，附上錯誤代碼（像 TS2551）和那一行程式，比截一張整片紅線的圖有用得多。

紅線拿什麼當標準？型別寫在哪裡

上一節的紅線能出現，有一個前提：lineTotal 宣告了 price: number, quantity: number，receiptLine 宣告了 item 是有 name 和 price 的物件。TypeScript 就是拿這些型別註記當標準，去比對你實際傳進去、拿出來的值。沒有標準，就沒有東西可以比，也就不會有紅線。所以接下來要學的，是這些標準怎麼寫。

規則只有一條：型別寫在名稱後面的冒號之後。這條規則用在三個地方：變數、函式參數，以及函式的回傳值（寫在參數括號之後）。下面每一行都是咖啡店會出現的值，先讀註解，執行後滑鼠移到名稱上，看看型別跟你寫的一不一樣：

逐行看這幾種型別：

  • string、number、boolean：對應 JavaScript 的字串、數字、布林值。TypeScript 沒有「整數」型別，110 和 110.5 都是 number，所以金額要不要有小數，型別擋不住，要靠第 5 課的做法。
  • string | null：直線讀作「或」，這個值可以是字串，也可以是 null。備註欄這種「可能沒填」的資料很常見，第 15 課詳講。
  • string[]：陣列，裡面每一個都是 string。長度不固定，要放幾個都可以。
  • [string, number]：tuple，長度固定的陣列，而且每一格有自己的型別，第一格是 string、第二格是 number。要一次回傳「名稱和價格」這種成對的值時用它（練習 4）。
  • 函式：參數各自寫型別，回傳型別寫在 ) 和 { 之間。lineTotal 寫了 : number，等於承諾它一定回傳數字。

這樣寫，每個值都有了標準。但如果每個變數都要這樣寫，程式會比 JavaScript 長一大截。實際上你在 Vue 專案裡很少看到 let drink: string = '拿鐵'，原因在下一節。

每個值都要自己寫型別嗎？推論

不用。大多數時候 TypeScript 能從值本身看出型別，這叫推論（type inference）：變數看它的初始值，函式的回傳值看 return 的那個運算式，callback 的參數看它被傳給誰。推論出來的型別跟你手寫的一樣有效，一樣會拿來畫紅線。把滑鼠移到下面每個變數上，看它推出了什麼：

大部分結果跟你的直覺一樣，只有一個值得停下來：const size 推出來的是 "M"，不是 string。這叫字面值型別（literal type）：型別就是那個值本身，只允許 'M'。原因是 const 不能再改，它的值永遠是 'M'，TypeScript 就給它最精確的型別。let drink 之後還能改成別的字串，如果推論成 '拿鐵'，你寫 drink = '美式咖啡' 就會報錯，所以推論成比較寬的 string。字面值型別在第 15 課會變得很有用，例如尺寸只能是 S、M、L 其中之一。

推論不是萬能的。它只能從「已經看得到的值」推，看不到的就推不出來。最典型的是函式參數：lineTotal 宣告一次，會從十幾個地方被呼叫，每個地方傳的東西都可能不一樣，TypeScript 不會反過來從呼叫的地方猜參數該是什麼。所以什麼時候要自己寫型別，有一套很固定的判斷：

  • 自己宣告的函式，參數要寫。沒寫、又推不出來，參數就變成隱含的 any，也就是錯誤 TS7006。傳給 map、find 的 callback 不用寫，參數型別會從呼叫它的地方推出來（像上面的 p，從 prices 推出 number）。
  • 對外提供的函式的回傳值：建議寫。回傳值就是你給呼叫者的承諾，寫清楚之後，萬一改壞了，錯誤會出現在函式裡，而不是散落在每個使用的地方。
  • 推論得太寬時。例如你要的是 tuple，它卻推論成陣列（練習 4）。
  • 其他情況交給推論。const total: number = a + b 這種只是雜訊。

回頭看同事的 receiptLine：參數 item 和 quantity 都寫了型別，裡面的 total 沒寫，交給推論從 lineTotal 的回傳值推出 number。這正是上面的分工。

💡 實務上：回傳型別寫在「別人會呼叫的地方」
咖啡店後台的 api/orders.ts 裡，像 fetchOrders() 這種給元件呼叫的函式，寫上回傳型別最划算：後端欄位改了、你改壞了實作，錯誤會集中在這個檔案，而不是散到十幾個用到它的頁面。元件裡的區域變數、一次性的小函式就交給推論，同事審你的程式碼時看到 const count: number = 0 這種重複的註記，通常會建議拿掉。

為什麼同一段程式，有的專案有紅線、有的沒有？strict

上一節說參數沒寫型別會報 TS7006，這句話其實有前提：要開著 strict。同一段程式放進沒開 strict 的舊專案，可能一條紅線都沒有，你也就無從發現 bug。

strict 寫在 tsconfig.json 裡。tsconfig.json 是 TypeScript 專案的設定檔，放在專案根目錄，決定要檢查哪些東西、檢查得多嚴，第 25 課會完整介紹。strict 是其中一組檢查的總開關，打開它等於同時打開好幾項嚴格檢查，最常碰到的是兩個：

  • noImplicitAny：推論不出型別、只好當成 any 的地方，直接報錯（TS7006）。沒開的話，TypeScript 會默默把它當成 any，這個參數從此不受檢查，傳什麼都不會有紅線。
  • strictNullChecks：null 和 undefined 不能混進一般的型別；可能是 undefined 的值，用之前要先檢查。沒開的話，每個型別都默默允許 null 和 undefined，item.price 就算 item 可能不存在，也不會有紅線。

TypeScript 6.0 起 strict 預設就是開的；舊專案用的更早版本（包括 5.x）預設是關的，接手時記得打開 tsconfig 確認。練習區用的版本見課末「補充與查表」。這裡的練習區一律開著。

💡 實務上：接手舊專案，先確認 strict 有沒有開
很多舊專案沒開 strict，像上面這種「找不到商品就當掉」的 bug，型別檢查完全不會提醒，最後變成客服回報的「點某個商品頁面就白掉」。新專案一律開著；舊專案突然打開可能冒出幾百個錯誤，常見做法是先開其中一項（例如 noImplicitAny）、修完再開下一項，不要為了讓錯誤消失到處補 any。要不要花時間修，是工程主管和 PM 一起排優先順序的事，可以拿「這類 bug 過去出過幾次」當理由。

現在可以完整回答開場的同事了：紅線不擋執行，因為檢查型別和擦掉型別是兩件事，Vite 只做後者；但紅線預告了執行時的錯，收據上的 NaN 就是 prise 拼錯造成的，寫死的 '2' 則讓數量永遠是兩杯。修法不是把紅線弄掉，而是把值改對。練習 1 就從這支 receiptLine 開始。

練習

練習 1：receiptLine 裡有兩個型別錯誤。修好它，讓程式印出「拿鐵 ×2 = 220」，而且換成別的商品和數量也要對。

練習 2：幫 calcTotal 的參數 items 補上型別，讓錯誤消失。items 是訂單明細的陣列，每一筆有 price（單價）和 quantity（數量），兩個都是數字。不要用 any。

練習 3：priceOf 找不到商品時會當掉。修好它：找不到時回傳 0。

練習 4：cheapest 回傳最便宜商品的「[名稱, 價格]」，但 TypeScript 把回傳型別推論成 (string | number)[]，用的人分不出哪一格是什麼。把回傳型別改成 tuple [string, number]。

練習 5：程式有型別錯誤時，tsc 還會產生 JavaScript 嗎？

✓ b：tsc 預設照樣輸出 JS，要開 noEmitOnError 才會擋，所以 a 錯。c 也錯：擦掉型別只拿掉型別註記，不會刪掉任何一行程式，有錯的那行照樣留在 JS 裡執行。Vite 和 Node 更直接：只擦掉型別，完全不檢查。

練習 6：下面這段沒有型別錯誤。執行時會印出什麼？

function addShipping(price: number) {
  return price + 60
}
const body = JSON.parse('{"price": "100"}')
console.log(addShipping(body.price))

✓ b：JSON.parse 回傳 any，所以編譯時不會報錯。執行時型別早就擦掉了，沒有人檢查 price 其實是字串，'100' + 60 就成了字串串接。a 錯在以為 price: number 會把字串轉成數字；c 錯在以為執行時還有 TypeScript 在檢查，其實跑的只是擦掉型別的 JS。從外面來的資料要在執行時驗證，第 17 課和第 26 課會講怎麼做。

練習 7：let drink = '拿鐵' 的型別是什麼？

✓ b：let 之後還能改成別的字串，所以推論成 string。a 是 const 才有的結果：const 不能再改，才會保留字面值型別 '拿鐵'。c 錯：有初始值就推論得出型別，不會變成 any。

常見錯誤

  • 以為紅線不影響執行，就可以先不管：紅線不擋執行，但它指出的錯在執行時照樣發生，像開場收據上的 NaN。修法是把值改對，不是讓紅線消失。
  • 以為 Vite、Node 跑得起來就沒有型別錯誤：它們只擦掉型別，要另外跑 tsc --noEmit 或 vue-tsc。
  • 以為型別會在執行時檢查資料：API 回來的 JSON、JSON.parse 的結果，執行時都沒有人檢查。
  • 用 any 讓錯誤消失：等於關掉檢查，而且 any 會擴散：它的屬性、呼叫它的回傳值也都是 any。any、as、! 的完整用法在第 17 課。
  • 用 ! 或 as 讓「可能是 undefined」的錯誤閉嘴：錯誤不見了，執行時照樣當掉。在練習 3 試試看 item!.price。
  • 到處手寫推論得出來的型別：自己宣告的函式的參數，和對外函式的回傳值才需要寫，其他交給推論。

補充與查表

練習區的 TypeScript 版本

TypeScript 7.0 是用 Go 重寫的原生編譯器，目前沒有能在瀏覽器裡執行的版本，所以練習區用的是編輯器內建的 5.9.3。本課程每一題都在 5.9.3 和 7.0.2 上各檢查過一次，判分結果相同。兩版的差別主要在預設設定，例如 strict 從 6.0 起預設開啟（7.0 也一樣），其他預設設定的差別，第 25 課會整理。

Vue 專案要注意：TypeScript 7.0 還沒有提供給其他工具呼叫的 API，vue-tsc 這類嵌入 TypeScript 的工具只能用 6.0，所以 Vue 專案目前停在 TypeScript 6.0。

小結

  • TypeScript 做兩件獨立的事：檢查型別，以及擦掉型別產生 JS。有型別錯誤照樣產生 JS；執行時沒有型別。所以「跑得起來」不等於「跑得對」，紅線預告的錯在執行時照樣發生。
  • Vite、Node 只擦掉型別不檢查，型別檢查要靠 tsc --noEmit 或 vue-tsc，並放進 CI。
  • 讀錯誤看三樣：第幾行、訊息、代碼（像 TS2322）。開場的 NaN 就是拼錯欄位（TS2551）造成的。
  • 型別註記寫在名稱的冒號之後，是 TypeScript 比對的標準。自己宣告的函式，參數要寫型別；callback 的參數和其他大多交給推論，滑鼠移上去確認。
  • let 推論成寬的型別（string），const 保留字面值（'M'）。
  • strict 從 TypeScript 6 起預設開啟，最常擋下的是隱含的 any，以及可能是 null／undefined 的值。
