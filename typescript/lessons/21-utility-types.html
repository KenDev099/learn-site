階段 4：函式、泛型與型別運算 · 第 21 課

工具型別：從現有型別做出新型別

咖啡店後台要開一組商品 API：店員在後台新增商品（POST /products）、修改價錢或下架（PATCH /products/:id），前台菜單讀商品列表（GET /products）。這幾支 API 收進來、送出去的都是「商品」，形狀卻各不相同：新增時還沒有 id，因為 id 要等資料庫存進去才產生；修改時只傳要改的那幾個欄位；菜單只需要名稱和價錢；資料庫裡的那一列，又比這些多了成本價這種只給內部看的欄位。

最直覺的做法是每一種形狀手寫一個型別。麻煩出現在之後：商品多一個欄位，你要記得去改三、四個地方，漏改一個，編譯器不會提醒；更糟的是，如果對外回應的型別沒跟上，成本價可能就這樣送到前台。這一課的任務是：只維護一份商品型別，API 需要的其他形狀都從它推出來；資料表加欄位時，該跟著變的自動跟上，不該對外的不會洩漏。做這件事的工具是 TypeScript 內建的工具型別（utility types）。學完你會：

  • 用 Partial、Required、Readonly、Pick、Omit、Record、Exclude、Extract、NonNullable 從現有型別推出新型別
  • 從資料模型推出 API 的輸入與輸出型別
  • 知道哪些工具型別只作用一層、哪個打錯鍵不會報錯
  • 判斷對外的回應型別該推導還是獨立寫，並在執行時真的只送出該送的欄位
這課的路線：
  1. 為什麼不替每支 API 各寫一份商品型別？手寫版本怎麼漏改，改用 Omit、Pick、Partial 從一份 Product 推出其他形狀（開場問題的最小答案）。
  2. 這些工具型別怎麼算？什麼時候會算出意外的結果？只作用一層，以及 Omit 打錯鍵不報錯。
  3. 修改商品的輸入用 Partial 就安全了嗎？DTO 怎麼推導，「沒傳」和「傳了 undefined」為什麼不一樣。
  4. 對外的回應用 Omit 去掉成本價就夠了嗎？黑名單與白名單，型別為什麼擋不住多送的欄位。
  5. 訂單列表的篩選條件怎麼推導？Exclude、Extract、NonNullable、Record 處理聯合型別。
  6. 這些工具型別是怎麼寫出來的？按 F12 讀定義，看懂只作用一層、Omit 不檢查鍵的原因。
這課會用到：
  • 第 19 課的泛型型別：Paginated<T> 收一個型別、產生另一個型別；K extends … 限制 K 的範圍。
  • 第 20 課的 keyof 與索引存取：keyof Product 是所有鍵的聯合，Product['price'] 是 price 的型別。
  • 第 14 課的 readonly、Record 與多餘屬性檢查：直接寫出來的物件字面值多了欄位會報錯，變數或展開的物件不會。
  • 第 16 課的可辨識聯合 Payment：現金、信用卡、LINE Pay 三種，用 method 區分。

為什麼不替每支 API 各寫一份商品型別？

先照直覺寫一次。Product 是資料庫裡的商品。建立商品的 API 收的資料沒有 id：id 由資料庫在存入時產生，前端不該指定。列表頁只需要 id、名稱、價錢三個欄位。假設 Product 原本有五個欄位，後來為了讓店員調整菜單上的順序，加了第六個欄位 sortOrder。執行後看 console：input 沒有 sortOrder，卻沒有任何錯誤。

編譯器為什麼沒提醒？對 TypeScript 來說，CreateProductInput 和 Product 是兩個毫不相干的型別，欄位只是剛好從 Product 抄過來。它不知道「建立商品的輸入 = 商品去掉 id」這層關係，所以 Product 改變時，不會有人通知 CreateProductInput。同樣的原因，ProductListItem 的 id 少了 readonly：抄的時候漏掉了，也沒有人發現。

這是「同一份資訊寫在好幾個地方」的問題。第 20 課處理值的時候用過解法：只寫一份來源，其他從它算出來。型別也能這樣做：只寫一份 Product，其他形狀用工具型別推出來。下面是改寫後的版本。執行後把滑鼠移到三個型別名稱上，看展開的結果；也可以自己在 Product 加上 sortOrder: number，再看一次三個型別怎麼跟著變。

三行各做一件事：

  • Omit<Product, 'id'>：Product 去掉 id。Product 之後加了 sortOrder，結果自動多一個 sortOrder，建立商品時沒給就會報錯，這正是手寫版本做不到的事。
  • Partial<CreateProductInput>：把上一行結果的每個欄位都改成可以不填，用在只傳要改的欄位的修改 API。
  • Pick<Product, 'id' | 'name' | 'price'>：只留下這三個鍵。Product 加了新欄位，它不受影響，因為它只留指定的鍵。

工具型別到底是什麼？它們就是第 19 課的泛型型別。第 19 課的 Paginated<T> 收一個型別 T，產生「T 的陣列加上分頁資訊」；Partial<T> 也是收一個型別、產生另一個型別。差別只在這些是 TypeScript 已經寫好的，放在它附的型別定義檔 lib.es5.d.ts 裡，所以不用 import，任何 .ts 檔都能直接用。另外要記住：它們跟所有型別一樣只存在於編譯時，編譯成 JavaScript 後全部消失，不會產生任何執行時的程式碼。第 4 節會看到這件事為什麼重要。

開場的問題有了最小答案：只寫一份 Product，用 Omit、Partial、Pick 推出其他形狀。但目前你只是「看結果是對的」就拿來用。這些工具型別怎麼處理每個屬性的 readonly 和 ?？有沒有哪些情況會算出跟預期不同的結果？下一節把它們攤開來看。

這些工具型別怎麼算？什麼時候會算出意外的結果？

這課用到的物件工具型別有六個：上一節的 Omit、Pick、Partial，加上 Required、Readonly、Record。屬性除了型別，還可以帶兩種修飾：readonly（唯讀）和 ?（可選）。為了看清楚每個工具型別怎麼處理這兩種修飾，下表用一個兩種修飾都有的小型別示範，P 代表 { readonly id: number; name: string; price?: number }。查表用，不用背：

寫法做什麼結果
Partial<P>每個屬性變可選{ readonly id?: number; name?: string; price?: number }
Required<P>每個屬性變必填{ readonly id: number; name: string; price: number }
Readonly<P>每個屬性變唯讀{ readonly id: number; readonly name: string; readonly price?: number }
Pick<P, 'id' | 'name'>只留列出的鍵{ readonly id: number; name: string }
Omit<P, 'id'>去掉列出的鍵{ name: string; price?: number }
Record<'S' | 'M', number>用鍵的聯合做出物件{ S: number; M: number }

表裡的前五個可以分成兩類。Partial、Required、Readonly 是「改修飾」：鍵不變，每個屬性都加上或拿掉同一種修飾。Pick、Omit 是「挑鍵」：只決定哪些鍵留下，留下的屬性保留原本的 readonly 與 ?，不改屬性的修飾。所以上一節用 Pick 推出的 ProductListItem，id 的 readonly 自然保留，不必像手寫時自己記得。Record 不從現有物件出發，而是拿一組鍵做出新物件，第 5 節處理訂單狀態時會用到。

這套規則大多時候符合直覺，但有兩個地方會算出意外的結果，而且兩個都不報錯，只能靠理解它們怎麼運作來避開。

第一個：Partial、Required、Readonly 都只作用一層。「改修飾」只改第一層的屬性本身，屬性的型別原封不動搬過來。商品是平的，沒有巢狀物件，看不出這件事，所以這裡換一個有巢狀的例子：訂單草稿 OrderDraft 的 customer 本身是一個物件。執行後看兩個地方：b 那一行的 TS2741，以及 c.customer.name 的賦值沒有報錯。

Partial 讓 customer 這個屬性可以不填，所以 a 是空物件也合法；但 customer 的型別還是原本的 { name: string; phone: string | null }，一旦填了 customer，裡面的 name 仍然必填，所以 b 報錯。Readonly 也一樣：它不讓你把 c.customer 整個換掉，卻管不到 c.customer.name。這跟第 14 課的 readonly、第 2 課的 Object.freeze 只管一層是同一件事。不知道這點的後果是：你以為「整份草稿都可以只填一部分」或「這份資料不會被改」，其實只有最外層成立。需要深層的版本要自己用遞迴型別寫，第 22 課會教怎麼寫。

第二個：Omit 的鍵打錯不會報錯，Pick 會。執行後看 NoPrice 那一行沒有紅線、Short 那一行有，再看 console 印出的 x 還有 price：

差別在兩者對 K 的限制，也就是第 19 課的 K extends …。Pick 宣告成 Pick<T, K extends keyof T>，要求 K 必須是 T 的鍵，'prise' 不是 Product 的鍵，所以報 TS2344。Omit 宣告成 Omit<T, K extends keyof any>，keyof any 是所有能當物件鍵的型別，也就是 string、number、symbol，任何字串都符合，所以 'prise' 照收。去掉一個不存在的鍵，等於什麼都沒去掉，price 還在。完整的定義最後一節會看。

這在商品 API 裡的後果是：你以為從 PATCH 的輸入或對外的回應裡去掉了某個欄位，其實沒有。避開的方法有兩個：用 Omit 時，滑鼠移上去確認結果裡真的沒有那個鍵；能用 Pick 列出要留的鍵時就用 Pick，打錯會報錯。

有了這些規則，可以回頭處理商品 API 裡最容易出錯的一支：修改商品。Partial 的「每個欄位都可以不傳」看起來正好符合修改的需求，但它真的夠用嗎？

修改商品的輸入用 Partial 就安全了嗎？

先定一個名詞。進出 API 的資料有固定的形狀：建立商品要收哪些欄位、列表要回哪些欄位。這種只用來在前後端之間傳資料的形狀，後端習慣叫它 DTO，全名是 Data Transfer Object（資料傳輸物件）。它跟資料庫裡的 Product 是兩回事：Product 描述資料怎麼存，DTO 描述 API 這一頭收什麼、送什麼。第 1 節推出的三個型別，就是商品 API 的三個 DTO：

APIDTO推導方式
POST /productsCreateProductInputOmit<Product, 'id'>
PATCH /products/:idUpdateProductInputPartial<CreateProductInput>：只傳要改的欄位
GET /productsProductListItemPick<Product, 'id' | 'name' | 'price'>

注意 UpdateProductInput 是 Partial<CreateProductInput>，不能直接寫 Partial<Product>：那樣 id 也變成可選欄位，型別上允許前端在 PATCH 的 body 裡帶一個 id，等於允許用 PATCH 改商品的 id。正確的順序是先用 Omit 拿掉不該被改的欄位，再套 Partial。

但 Partial 還有一個型別擋不住的陷阱。Partial 做的事是替每個屬性加上 ?，而 ? 在型別上同時允許兩種情況：屬性根本不存在，以及屬性存在但值是 undefined。型別上兩者都允許，執行時卻不一樣。下面的 patch 只想改名稱，卻帶了 price: undefined。執行後看 console 印出的 price，再把滑鼠移到 updated 上看它的型別：

型別說 updated.price 是 number，執行時卻是 undefined。原因在展開：{ ...latte, ...patch } 把 patch 的每個屬性依序蓋到結果上，它只看屬性存不存在，不看值是什麼。patch 裡的 price 屬性存在、值是 undefined，就把 latte 原本的 110 蓋掉了。TypeScript 推論展開的型別時，把 ? 當成「可能不存在」，所以算出 price 仍是 number，跟執行結果對不上。

這不是刻意寫壞才會遇到。後端常這樣從 request body 組 patch：{ name: body.name, price: body.price }。前端只想改名稱、沒傳 price，body.price 是 undefined，但 patch 物件裡 price 這個屬性照樣存在。再把它展開蓋到原本的商品上，價錢就被清成 undefined。處理方式是逐個欄位判斷 !== undefined 再套用，或在驗證輸入時就拒絕。編譯器也有選項能從型別上擋住明寫的 undefined，見課末「補充與查表」。補預設值也是同一個坑，練習 4 會碰到。

💡 實務上：PATCH 要先跟前端講好「清空欄位」怎麼表示
例如商品的分類可以清掉，前端要送 category: null（清空）還是不送（不改）？這兩個意思不同，而且 Partial 只會加 ?、不會加 null，要能清空就得把欄位寫成 category?: string | null。團隊要先約定：常見做法是「不傳 = 不改、null = 清空、undefined 當作不傳」，並寫進 API 文件。後端組更新資料時只挑出真的有傳的欄位，不要把整個 body 展開進資料庫的更新。資深的人 review 商品的 PATCH 時會實際試三種請求：不傳、傳 null、傳錯型別，確認結果都符合約定。

輸入這一側處理好了：建立用 Omit，修改先 Omit 再 Partial，執行時只套用真的有傳的欄位。接下來是方向相反的一側：API 送出去的回應。直覺上可以照同樣的方法，用 Omit 把成本價拿掉。但對外的資料也用推導，會不會反而出事？

對外的回應用 Omit 去掉成本價就夠了嗎？

推導的好處是來源一改，推出來的型別跟著改。這個好處反過來看，就是耦合（coupling）：兩個型別綁在一起，一個變了另一個跟著變，而且沒有人提醒。對內的型別，耦合正是我們要的；對外的 API 回應，這可能就是資安事故。

情境：資料庫的商品列 ProductRow 比 Product 多了成本價 costPrice，也就是進貨成本，讓顧客看到等於公開毛利。回應型別用 Omit 去掉它，看起來很合理。幾個月後，有人在資料表加了 supplierNote（供應商備註），寫著「月底前改向 B 廠進貨」。執行後看印出的 JSON 有哪些欄位：

印出來的 JSON 有 costPrice 也有 supplierNote，型別檢查完全沒抱怨。這裡疊了兩個獨立的問題，只修一個不夠。

第一個問題：黑名單會漏。Omit<ProductRow, 'costPrice'> 的意思是「除了 costPrice 都可以送」。這種列出禁止項目的做法叫黑名單（denylist），它的預設是放行：資料表新加的欄位只要沒被列進去，就自動出現在回應型別裡，supplierNote 就是這樣溜進去的。反過來，Pick 列出允許的欄位，叫白名單（allowlist），預設是不給：新欄位不會自己出現，要有人刻意加進清單。對外的資料，少給一個欄位會被前端發現、回報再補；多給一個欄位卻可能一直沒人發現。所以對外的回應用 Pick 白名單。

第二個問題：型別擋不住執行時多出來的欄位。就算回應型別改成 Pick，return { ...row } 照樣通過檢查，執行時照樣送出 costPrice。原因是第 14 課的結構型別：TypeScript 判斷能不能指派時，只要求「至少有這些欄位」，多的不管。多餘屬性檢查是例外，但只對直接寫出來的物件字面值有效，row 是變數，{ ...row } 是展開，兩者都不檢查。再加上第 1 節說的，型別在編譯後完全消失，不會在執行時幫你刪掉任何欄位。所以光有正確的型別不夠，回應要在執行時明確挑選欄位，一個一個寫出來。這樣資料表之後再加什麼欄位，都不會被帶出去。練習 3 就是把這支函式修好。

回應裡多送了不該給的欄位，叫做過度暴露資料（excessive data exposure）。OWASP 是整理網路應用程式常見資安風險的開放社群，它的 API Security Top 10 把這類問題歸在 API3「物件屬性層級授權失效」。認證課第 19 課會從授權的角度再講一次。

那什麼時候該推導、什麼時候該獨立寫？判斷依據是：這個型別跟來源是不是本來就該一起變。

  • 推導：程式內部的型別、跟來源本來就該一起變的（更新的輸入跟著建立的輸入、列表項目跟著商品）。
  • 獨立定義或 Pick 白名單：對外的 API 合約。前端、手機 App 依賴它，資料表加欄位不該讓合約自己改變。全部從資料庫模型推導，API 就跟著資料表一起亂變。
  • 不管哪一種，工具型別疊到三層以上（Partial<Omit<Pick<…>>>）就拆成有名字的中間型別，錯誤訊息和滑鼠提示才看得懂。
💡 實務上：對外回應的型別一改，就是一次 API 合約變更
咖啡店的前台網站和手機 App 都在讀 GET /products，回應少了一個欄位或改了型別，舊版 App 可能直接壞掉，而手機 App 不能保證使用者都更新了。所以回應型別放在一個明確的地方（例如 toPublicProduct 這種轉換函式），改它的 PR 要通知前端和 App 的同事。新增欄位通常安全，刪除或改名要先跟對方確認。資深的人 code review 時看到 return row、res.json(row) 或 { ...row } 會直接標出來，並要求補一個測試，檢查回應的鍵只有允許的那幾個（跟練習 3 的測試一樣）。

商品 API 的輸入和輸出都處理完了。後台還有另一組 API：訂單列表。它的篩選條件是訂單狀態，型別不是物件，而是字串字面值的聯合，Omit、Pick 用不上。聯合型別也能從單一來源推出一部分嗎？

訂單列表的篩選條件怎麼推導？

訂單列表有一個「進行中」的篩選，意思是取消以外的所有狀態。手寫成 'pending' | 'paid' | 'done'，問題跟第 1 節的 sortOrder 一樣：之後 OrderStatus 加了 'preparing'（製作中），這裡不會跟著變，也沒有紅線，製作中的訂單就從「進行中」消失了。第 15 課的聯合型別也有對應的工具型別，從一組成員裡去掉或留下一部分，結果跟著來源走：

  • Exclude<T, U>：去掉 T 裡「能指派給 U」的成員。
  • Extract<T, U>：只留下 T 裡「能指派給 U」的成員。
  • NonNullable<T>：去掉 null 和 undefined。

「能指派給 U」是對聯合裡的每個成員分別問一次：這個成員的值，能不能放進 U？以 Exclude<OrderStatus, 'cancelled'> 來說，'cancelled' 能放進 'cancelled'，所以被去掉；其他三個不能，所以留下。

訂單上的付款方式也是聯合：第 16 課的 Payment。訂單明細只對刷卡的訂單顯示卡號末四碼，要從 Payment 挑出刷卡那一種，用的是 Extract。執行後把滑鼠移到每個型別名稱上，對照註解：

OrderStatus 是字串的聯合，Active 和 Finished 最直覺。挑出刷卡的付款就要想清楚 Extract 比的是「整個成員能不能指派給 U」。Payment 的成員是三個物件型別。U 寫成物件的形狀 { method: 'card' }，刷卡那個成員 { method: 'card'; last4: string } 有 method: 'card'，多出的 last4 不影響（結構型別只要求該有的都有），所以留下。U 寫成字串 'card'，沒有任何一個物件能指派給字串，結果是 never。never 是「沒有任何值」的型別，聯合被篩到一個成員都不剩，就是它。它本身不報錯，要等用到的地方，例如拿它當參數型別、傳值進去時，才冒出看不懂的錯誤，離真正寫錯的地方很遠。

💡 實務上：Extract 常用在「只處理某一種」的元件或函式參數
訂單明細裡顯示卡號末四碼的元件只該收到刷卡的付款，props 寫成 Extract<Payment, { method: 'card' }>，比手寫 { method: 'card'; last4: string } 好：Payment 的 card 成員多了欄位，元件的型別自動跟上。要注意 Extract 和 Exclude 跟 Omit 一樣不檢查第二個參數：Extract<OrderStatus, 'paid' | 'dnoe'> 打錯字不會報錯，只會悄悄少一個成員，所以寫完一樣把滑鼠移上去確認結果。字串字面值的聯合只用一兩次時，直接寫 'paid' | 'done' 比套 Extract 好讀，打錯也會報錯。

NonNullable 最單純：去掉 null 和 undefined。例如商品的 category 允許 null，某段程式已經確認過有值，就可以用 NonNullable<Product['category']> 表示一定有值的分類。

跟所有工具型別一樣，Exclude 的結果只存在於型別，執行時什麼都不剩。要在執行時判斷「這張訂單能不能出貨」，還是要寫函式；把它寫成第 17 課的型別守衛，判斷之後的型別就會縮小成 Exclude 的結果（練習 2）。

聯合型別也能反過來做出物件，這就是第 2 節表裡的 Record：Record<K, V> 拿鍵的聯合 K，做出「每個鍵都有、值是 V」的物件型別。訂單列表要把狀態顯示成中文，常寫成 const statusLabel: Record<OrderStatus, string> = { pending: '待付款', … }。好處是 OrderStatus 之後加了 'refunded'，這個物件會立刻報缺少屬性，畫面上不會冒出空白的狀態標籤：來源一改，相關的地方被逼著跟上。反過來，鍵是任意字串時要小心。例如用商品名稱查庫存，寫成 Record<string, number>，每次讀取都會被當成一定有值，查不到的時候拿到 undefined 也不會報錯。這種情況改用 Map（get 的回傳型別會帶 undefined，逼你處理查不到），或在讀取時自己檢查。所以看到 Record 要先問：鍵是一組固定的值，還是使用者給的任意字串？

訂單列表的查詢參數也用得到工具型別。?page=2 這類查詢參數每個欄位都可以不傳，型別 OrderQuery 的欄位全部可選；後端補上預設值之後，後面的程式拿到的每個欄位都一定有值，那個型別就是 Required<OrderQuery>。補預設值會遇到第 3 節「沒傳」和「傳了 undefined」的同一個坑，練習 4 要處理它。

到這裡，Omit、Exclude、Extract 打錯字都不報錯，只有 Pick 會。同樣是內建的工具型別，為什麼有的檢查、有的不檢查？答案寫在它們的定義裡。

這些工具型別是怎麼寫出來的？

在 VS Code 裡對 Partial 按 F12（前往定義）會打開 lib.es5.d.ts。TypeScript 5.9.3 附的定義是這樣：

type Partial<T> = { [P in keyof T]?: T[P] }
type Required<T> = { [P in keyof T]-?: T[P] }
type Readonly<T> = { readonly [P in keyof T]: T[P] }
type Pick<T, K extends keyof T> = { [P in K]: T[P] }
type Record<K extends keyof any, T> = { [P in K]: T }
type Exclude<T, U> = T extends U ? never : T
type Extract<T, U> = T extends U ? T : never
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>
type NonNullable<T> = T & {}

用第 20 課的 keyof 和索引存取 T[P] 來讀，前面幾節遇到的現象在這裡都找得到原因：

  • [P in keyof T]：對 T 的每一個鍵 P 做一次；T[P] 是那個鍵原本的型別。? 加上可選，-? 拿掉可選。這種寫法叫 mapped type。T[P] 原封不動搬過來、不再往裡面走，這就是第 2 節「只作用一層」的原因。
  • Pick 的 K extends keyof T 要求 K 是 T 的鍵，所以會報 TS2344。keyof any 是 string | number | symbol，所以 Omit 收任何鍵。
  • T extends U ? never : T 是條件型別（conditional type）：T 是聯合時會對每個成員分別判斷，能指派給 U 的變成 never（消失），其他留下。Exclude、Extract 的 U 沒有任何限制，所以打錯字也不報錯。
  • Omit 就是「先用 Exclude 算出要留的鍵，再 Pick」。打錯的鍵在 Exclude 那一步什麼都沒去掉，Pick 拿到全部的鍵，所以結果跟原本一樣。
  • T & {}：{} 代表「除了 null、undefined 以外的任何值」，跟它取交集，null 和 undefined 就被去掉了。

mapped type 和條件型別是下一課的主題，學完你就能自己寫出這些工具型別。

練習

練習 1：從 Product 推導三個型別，不要手寫欄位：CreateProductInput（沒有 id 的其他欄位）、UpdateProductInput（CreateProductInput 的欄位全部可選）、ProductListItem（只有 id、name、price）。

練習 2：用工具型別寫出 ShippableStatus（OrderStatus 去掉 'cancelled'）和 CardPayment（Payment 裡信用卡那一種）。再寫型別守衛 canShip(status: OrderStatus): status is ShippableStatus：只有取消的訂單不能出貨。

練習 3：ProductRow 是資料庫的列，多了成本價 costPrice 和供應商備註 supplierNote。把 PublicProduct 改成只有 id、name、price、category 四個欄位（用白名單），再修好 toPublicProduct(row)：執行時回傳的物件也只能有這四個欄位，而且不能改到傳進來的 row。

練習 4：訂單列表的查詢參數是 OrderQuery，每個欄位都可以不傳。寫 withDefaults(q)，回傳型別是 Required<OrderQuery>，缺的欄位補預設值：page 是 1、size 是 20、status 是 'paid'。欄位存在但值是 undefined 時，也要用預設值。

練習 5：type Draft = Partial<Order>，Order 有一個巢狀的 customer: { name: string; phone: string | null }。下面哪一個說法正確？

✓ Partial、Required、Readonly 都只處理第一層的屬性，T[P] 原封不動拿過來，所以 customer 的型別還是 { name: string; phone: string | null }。要深層的版本得自己寫遞迴型別（第 22 課）。

練習 6：type ProductNoPrice = Omit<Product, 'prise'>（price 拼錯了）會怎樣？

✓ Omit 的定義是 K extends keyof any，任何字串都收；Exclude<keyof Product, 'prise'> 什麼都沒去掉，所以結果就是全部的欄位。只有 Pick（K extends keyof T）會報 TS2344。

練習 7：商品 API 的回應型別寫成 Omit<ProductRow, 'costPrice'>，實作是 return { ...row }。主要的風險是什麼？

✓ 黑名單只擋列出的欄位，新欄位預設放行；型別在執行時不存在，也不會刪任何東西。展開出來的物件不做多餘屬性檢查，所以 c 也不對。對外回應用 Pick 白名單，並在執行時一個一個挑出欄位。

常見錯誤

  • 以為 Partial、Readonly 是深層的：它們只處理第一層，巢狀物件的屬性不變。深層的版本要自己寫（第 22 課）。
  • Omit 的鍵打錯沒發現：Omit 收任何字串，打錯等於什麼都沒去掉。用完滑鼠移上去看結果，或改用 Pick 列出要留的鍵。
  • UpdateProductInput 寫成 Partial<Product>：連 id 都能用 PATCH 傳進來。先 Omit 掉不該改的欄位再 Partial。
  • 用 Partial 表示 PATCH，卻沒分清「沒傳」和「傳了 undefined」：{ ...product, ...patch } 會被 undefined 蓋掉，型別卻還說是 number。逐欄判斷 !== undefined，或用 ?? 補值。
  • 把資料庫的列直接回傳或展開回傳：return row、{ ...row } 型別都相容，執行時卻把成本價、內部備註送給前端。對外回應要一個欄位一個欄位挑出來。
  • 所有型別都從資料庫模型推導：API 合約跟著資料表改變，前端毫無預警。對外的型別用白名單或獨立定義。
  • 工具型別疊太多層：Partial<Omit<Pick<…>>> 看不懂、錯誤訊息也看不懂。拆成有名字的中間型別。

小結

  • 開場的商品 API：只寫一份 Product，建立用 Omit<Product, 'id'>、修改用 Partial<CreateProductInput>、列表用 Pick。欄位改一次，推出來的型別全部跟著改。工具型別是 TypeScript 內建的泛型型別，只存在於編譯時。
  • 物件：Partial（可選）、Required（必填）、Readonly（唯讀）改修飾，只作用一層；Pick（留下）、Omit（去掉）挑鍵，保留原本的 readonly 與 ?；Record 用鍵的聯合做出物件。
  • Pick 會檢查鍵，Omit 不會：Omit 的 K 只要求 keyof any，打錯的鍵等於什麼都沒去掉。
  • PATCH：先 Omit 掉不該改的欄位再 Partial；? 允許「傳了 undefined」，展開時會蓋掉原值，執行時只套用真的有傳的欄位。
  • 對外回應：Omit 黑名單會把新欄位帶出去，型別也擋不住執行時多出來的欄位。用 Pick 白名單，並在執行時明確挑選欄位。對內推導，對外的 API 合約用白名單或獨立定義。
  • 聯合：Exclude（去掉）、Extract（留下）、NonNullable（去掉 null、undefined）。Extract 物件聯合時，條件要寫成物件的形狀。補完預設值的查詢參數用 Required。
  • 工具型別的定義只有幾行：mapped type 加上條件型別。
