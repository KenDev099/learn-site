階段 2：非同步、迭代與並發 · 第 11 課

逾時與取消：AbortController 與期限

結帳 API 要呼叫上游的付款服務。平常 200ms 回來，今天付款服務卡住了，每個請求都等 30 秒。你的伺服器每秒進來 50 個結帳請求，30 秒後就有 1500 個請求同時卡在「等」：每個都佔著記憶體、資料庫連線、對上游的連線，最後整台伺服器被拖垮，連不用付款的查菜單也一起變慢。反過來，客人已經關掉網頁，伺服器還在幫他查完三個上游服務，查完沒人要。

這一課從頭到尾處理這個結帳 API：讓它在付款服務卡住時及時放手，客人離開時停下為他做的工作，整個結帳有一個總時間上限，停下時不留下沒清掉的計時器。要用到兩個能力。第一個是逾時（timeout）：等一件事最多等多久，超過就放棄。第二個是取消（cancellation）：通知一件進行中的工作「不用做了」，讓它真的停下來、放掉手上的資源。這課會看到，只有逾時、沒有取消，伺服器還是會被拖垮。

這課的路線：
  1. 付款服務卡住時，為什麼 Promise 自己停不下來；先用一行 AbortSignal.timeout 擋住（開場問題的最小答案）。
  2. AbortController 怎麼把「停下來」的通知送到工作手上，自己寫的函式怎麼聽到它。
  3. 逾時怎麼寫，上游的工作才會真的停下；停下之後，catch 收到的錯誤怎麼分辨。
  4. 「客人離開」和「時間到」怎麼合成一個 signal；結帳三個步驟怎麼共用一個總期限，一路傳到扣款。
  5. 扣款結果不確定時，怎麼定期去問又停得乾淨；搬到 Node 伺服器上，這套機制接在哪裡。
這課會用到：
  • 第 8 課的 Promise：Promise 只是號碼牌，丟掉號碼牌不會讓正在做的工作停手；Promise.race 採用最先定案的那個，其他工作照樣跑完。
  • 第 9 課的 async／await：await 失敗會在那一行丟錯，用 try／catch 接住。
這頁的練習區不連網路：範例用 setTimeout 假裝慢的上游（查菜單、做飲料、問狀態），換成真正的 fetch 道理一樣。練習區會等所有計時器結束才算執行完，留下沒清掉的計時器，程式會跑到 3 秒被強制停止。

付款服務卡住時，為什麼工作自己停不下來？

先看開場那 30 秒裡，每個結帳請求在做什麼。結帳函式執行到 await 呼叫付款服務的那一行就暫停了，等付款服務回應。這段時間裡，請求本身的資料、它拿著的資料庫連線、對付款服務開著的那條連線都還佔著。要讓它放手，得有人對這件工作說「不用等了」。問題是：現在的程式裡，沒有任何人能說這句話。

需要「中途叫工作停下」的情況，在結帳 API 上每天都會遇到：

  • 客人不要了：客人在付款轉圈時關掉了頁面，伺服器上為他跑的查詢、呼叫已經沒有人要結果。前端也有同樣的事：搜尋框打「拿」再打「拿鐵」，第一個搜尋的結果已經沒用。
  • 上游太慢：付款服務卡住，結帳不能陪它等到天荒地老，要有逾時。
  • 伺服器要關機：部署新版本時，舊程序要通知正在跑的結帳收尾（Node 課第 21 課）。

這些工作如果不停，代價有三個：連線和記憶體被沒人要的工作佔住，就是開場的 1500 個請求；付款服務已經很慢了，你還繼續送請求，加重它的負擔，讓它更難恢復；舊的結果晚回來，蓋掉新的結果，這是第 12 課要處理的競態。

為什麼工作自己停不下來？第 8 課說過，Promise 是號碼牌，代表「將來會有一個結果」，不是工作本身。你手上拿著號碼牌，沒有辦法透過它叫正在做飲料的人停手；把號碼牌丟掉，做飲料的人也不知道。所以 Promise.race 或 Promise.all 先定案之後，其他工作照樣跑完。JavaScript 的 Promise 沒有「取消」這個操作。

要讓工作停下來，只能另外給它一條通知管道：呼叫工作時多交給它一個物件，工作在等待時一直留意這個物件；外面的人想叫它停，就透過這個物件發出通知，工作收到後自己停下、放掉資源。瀏覽器和 Node 內建的這套管道叫 AbortController，它交給工作的那個物件叫 signal。

開場的付款服務，用這套管道一行就能先擋住：

const res = await fetch(paymentUrl, { signal: AbortSignal.timeout(3000) })

AbortSignal.timeout(3000) 建立一個 3 秒後自動發出「停下來」的 signal。fetch 收到這個 signal，3 秒內付款服務沒回應，fetch 會中斷這個 HTTP 請求、關掉連線，回傳的 Promise 以錯誤失敗；結帳函式在 catch 裡回錯誤給客人，這個請求佔著的東西就都放掉了。每秒 50 個請求、每個最多等 3 秒，同時卡住的請求最多約 150 個，不會再累積到 1500 個。

這一行能運作，是因為 fetch 會「聽」signal。signal 到底是什麼、怎麼聽；結帳流程裡那些你自己寫的函式，又要怎麼聽到它，是下一節的問題。

AbortController：「停下來」的通知怎麼送到工作手上？

上一節說要另外給工作一條通知管道。這條管道有兩端，像外場和咖啡師之間的對講機：

  • AbortController：發出取消的那一端，留在「有權決定不做了」的人手上。呼叫 controller.abort()，就是對講機喊「那杯不用做了」。
  • AbortSignal：收聽的那一端，用 controller.signal 取得，交給工作。工作可以讀 signal.aborted（是否已取消）、signal.reason（取消的原因），呼叫 signal.throwIfAborted()（已取消就把 reason 丟出來），或監聽 abort 事件，在取消的那一刻收到通知。

拆成兩個物件，是為了分清楚權限。結帳流程會把 signal 一路交給很多函式，如果每個函式都能喊取消，任何一個小函式都可能讓整個結帳停下。拆開之後，拿到 signal 的工作只能「聽」，不能替別人喊取消；喊取消的權力只在拿著 controller 的那一個地方。

從輸出看出三件事：

  • abort() 沒給原因時，reason 是一個 DOMException，名稱（name）是 'AbortError'。DOMException 是瀏覽器與 Node 都內建的錯誤類別，取消和逾時的錯誤都是它（依據 MDN 的 AbortSignal.reason 說明）。之後判斷「這是不是取消」，就看這個名稱。
  • abort 事件是同步觸發的：「abort 事件」那行印在「取消後」之前。也就是說，abort() 這一行還沒執行完，監聽器就已經跑過了。這點之後很有用：監聽器裡做的清理（清掉計時器、讓 Promise 失敗），在 controller.abort() 回傳之前就全部做完了。下一節範例在 onAbort 裡 clearTimeout，就是在取消的當下生效，不會晚一拍。
  • 一個 signal 只會取消一次，第二次 abort() 沒有作用。要再做一次可以取消的工作，就建立新的 controller。

瀏覽器和 Node 的 fetch 都接受 signal：fetch(url, { signal })。signal 取消時，請求會被中斷，fetch 回傳的 Promise 以 signal 的 reason 失敗。上一節那一行能擋住付款服務，靠的就是這個。

結帳流程裡自己寫的函式，要怎麼聽 signal？

fetch 會聽 signal，是因為它的實作者寫了聽 signal 的程式。結帳流程裡還有你自己寫的非同步函式：查庫存、組訂單、包裝付款呼叫的函式。這些函式不會自動聽 signal，要你自己寫。

最簡單的方式是在每一步開始前檢查一次：signal.throwIfAborted()，已經取消就丟出 reason，函式在這裡結束。下面用咖啡師連做四杯飲料當成一件多步驟的工作，每杯 30ms，外場在 70ms 時喊取消。執行後看最後一杯做好的時間，和「停下來了」出現的時間：

70ms 喊了取消，卡布奇諾還是做完（大約 100ms）才停。原因是 throwIfAborted() 只在步驟之間檢查，取消發生時，函式正停在 await 等那 30ms，正在等的那一段沒有人在聽。這裡只多做了 30ms，看起來無所謂；但換成開場的情況，正在等的那一段是「等付款服務回應 30 秒」，步驟之間檢查完全幫不上忙，取消要等 30 秒後才生效。

所以等待本身也要能被打斷：負責等待的程式要監聽 abort 事件，取消的那一刻就停止等待、清掉手上的東西、讓 Promise 失敗。一個支援 signal 的非同步函式，要做到這四件事：

步驟做什麼漏掉會怎樣
1. 先檢查signal.aborted 已經是 true，就立刻以 signal.reason 失敗已經取消的 signal 不會再觸發 abort 事件，工作會一直等到做完
2. 監聽 abortsignal.addEventListener('abort', onAbort, { once: true })等待中聽不到取消
3. 取消時清理onAbort 裡清掉計時器（clearTimeout）、關掉連線，再 reject(signal.reason)Promise 失敗了，計時器還在，時間到還是會執行
4. 完成時移除監聽器正常完成時 signal.removeEventListener('abort', onAbort)監聽器跟著 signal 一直留著

第 1 步容易被跳過，因為看起來多餘：都已經監聽 abort 了，為什麼還要先檢查？原因是 abort 事件只在取消的那一刻觸發一次。如果 signal 在交給你之前就已經取消（例如結帳的總時間已經用完），你之後才掛上的監聽器永遠等不到事件，工作會照常做完。

第 4 步最常被忘。伺服器上一個結帳請求的 signal 常常要傳給幾十個小工作，每個工作做完都把監聽器留在 signal 上，請求越久、留得越多。這叫資源洩漏（resource leak）：工作結束了，它用過的計時器或監聽器卻還留著，佔著記憶體。{ once: true } 只在事件觸發後自動移除，沒觸發就不會移除，所以正常完成時還是要自己移除。

reject 時用 signal.reason，不要自己 new Error('aborted')。呼叫端要靠錯誤的 name 分辨「是自己取消的」還是「等太久了」，下一節會看到這兩種要分開處理；換成自己的 Error，名稱就不對了。下一節的範例就是照這四步寫的，練習 1 會把它們寫成可以重用的 sleep。

💡 實務上：前端最常在「離開畫面」時 abort
咖啡店後台的訂單頁，進頁面就送 fetch，使用者還沒等到結果就切去菜單頁。React 的寫法是在 useEffect 裡建立 controller，cleanup 時呼叫 controller.abort()（Vue 則放在 onUnmounted）；TanStack Query 這類資料抓取套件會把 signal 傳給你的 queryFn，你只要把它交給 fetch。自己包的 API client（例如 api.get(url, { signal })）一開始就要留 signal 這個選項，事後再補，得一個一個呼叫點去改。這跟本課的結帳 API 是同一件事的兩端：前端在離開畫面時 abort，後端在客戶端斷線時 abort（最後一節）。Code review 時看到「進畫面就抓資料」，資深會順手問一句：離開畫面時這個請求會停嗎？

工具齊了，回到付款服務卡住的問題。逾時最常見的寫法不是 signal，而是 Promise.race；下一節先看它為什麼不夠。

逾時怎麼寫，上游的工作才會真的停下？

很多人寫逾時的第一個想法，是讓工作跟一個計時器比賽：計時器先到就失敗（setTimeout 只保證「至少」等這麼久，第 7 課）。下面用查菜單代替付款服務，上游要 200ms 才回來，逾時設 50ms。執行後看兩個時間：呼叫端什麼時候放棄，上游的連線什麼時候才釋放：

呼叫端在 50ms 放棄了，但查詢一直跑到 200ms。Promise.race 只決定「呼叫端的這個 Promise 用誰的結果」，它沒有辦法通知 fetchMenu，fetchMenu 也沒有拿到任何 signal，根本不知道自己被放棄了。套回開場：結帳在 3 秒回錯誤給客人，但對付款服務的連線還是佔滿 30 秒，1500 條連線一條都沒少。上游卡住時，這種「放棄了但沒停下」的工作會越積越多，呼叫端還以為逾時已經保護了系統。

要讓工作真的停下，逾時就要透過 signal 送到工作手上。AbortSignal.timeout(ms) 會建立一個 ms 毫秒後自動取消的 signal，reason 是名為 'TimeoutError' 的 DOMException（MDN）。它等於「建立 controller、設計時器、時間到呼叫 abort()」三件事的現成版本，而且 reason 的名稱跟一般取消不同，呼叫端分得出來。

工作停下之後，catch 收到的錯誤該怎麼分？

現在結帳函式的 catch 會收到三種失敗，原因不同，處理方式也不同。分辨的依據是錯誤的 e.name：

e.name誰造成的該怎麼處理
'AbortError'呼叫端自己取消（使用者離開、換了搜尋字、伺服器關機）安靜結束：不顯示錯誤、不送錯誤回報，最多記一筆 debug log
'TimeoutError'對方太慢告訴使用者「太慢了，再試一次」，或回 504（HTTP 的 Gateway Timeout：上游沒在時間內回應）；要記錄，逾時變多代表上游有問題
其他真的出錯（網路斷、對方回 500）照第 4 課的方式處理：顯示、回報、往上丟

同樣的分類，前端和後端各寫一次，只是「怎麼處理」那一欄不同。先看前端載入菜單：

try {
  const menu = await loadMenu({ signal })
  render(menu)
} catch (e) {
  if (e.name === 'AbortError') return               // 使用者不要了：什麼都不顯示
  if (e.name === 'TimeoutError') return showToast('菜單載入太慢了，再試一次')
  throw e                                           // 其他錯誤照常處理
}

換成本課的結帳 API，三列對應的處理是這樣（虛擬碼，回應的寫法依框架而定）：

try {
  const order = await checkout(cart, { signal })
  回傳 200 和 order
} catch (e) {
  if (e.name === 'AbortError') {                   // 客人已經離開：沒有人在等回應
    記一筆 debug log；不回應
    return
  }
  if (e.name === 'TimeoutError') {                 // 付款服務太慢
    記錄逾時（監控要看得到）
    回傳 504
    return
  }
  throw e                                          // 其他錯誤往上丟，交給統一的錯誤處理
}

為什麼 AbortError 要安靜結束？取消是呼叫端自己決定的，不是故障。把它當錯誤顯示，使用者每換一次搜尋字就看到一次「發生錯誤」；送進錯誤監控，真正的錯誤會被淹沒在幾千筆取消裡。TimeoutError 則相反，它代表上游出了狀況，一定要記錄下來，監控上逾時的數量突然變多，通常就是開場那種事故的第一個訊號。

用 abort(new Error('…')) 自訂原因時，名稱就不是 AbortError 了，這時可以改用 signal.aborted 判斷「是不是自己取消的」。

💡 實務上：每個對外呼叫都要有逾時，數字從監控來
fetch 沒有逾時的參數，不傳 signal 就會一直等到連線層自己放棄，所以呼叫付款、簡訊、物流這類外部服務時，逾時是必備的，不是加分題。數字不要憑感覺：先看監控裡這個上游平常多久回來，逾時設在「正常情況的慢」之上留點空間；設太短，上游只是偶爾慢一點就被你當成失敗。不同操作可以不同：查菜單逾時短、失敗就顯示快取，扣款寧可多等一點再去查結果。資深會把各服務的逾時集中寫在設定裡，方便出事時一眼看到「我們到底等對方多久」。

到這裡，付款呼叫已經有了會真的停下的逾時。但結帳 API 停下的理由不只一個：客人也可能在等待中關掉頁面。fetch 只收一個 signal，兩個理由要怎麼同時交給它？

「客人離開」和「時間到」，怎麼合成一個 signal？

付款呼叫現在有兩個停下的理由：客人關掉頁面（一個由你呼叫 abort() 的 controller），和時間到了（AbortSignal.timeout）。fetch 的 signal 選項只收一個，任何一個理由發生都要停。

AbortSignal.any([signal1, signal2, …]) 做的就是這件事：它回傳一個新的 signal，傳進去的任何一個來源取消，它就跟著取消，reason 是第一個取消的來源的 reason（MDN）。後半句很重要：合併之後，上一節的分類照樣能用，客人離開是 AbortError、時間到是 TimeoutError，catch 不需要知道 signal 是怎麼組出來的。

第一行在約 30ms 印出 AbortError，第二行在約 100ms 印出 TimeoutError：誰先發生，合併後的 signal 就帶著誰的原因取消。後端的「客人離開」signal 從哪裡來，在最後一節。AbortSignal.any 是比較新的 API，各環境從哪一版開始支援，見課末的補充與查表。

付款呼叫現在有了兩個停下的理由。但結帳不只付款這一步：前面要查庫存，後面要寫訂單，每一步都可能慢。每一步各自加上逾時，整個結帳就安全了嗎？

結帳有三步，怎麼限制整件事最多花多久？

結帳有三個步驟：查庫存、扣款、寫訂單。每一步都設了 1 秒逾時，看起來很安全。但三步各花 0.9 秒時，每一步都沒逾時，整個結帳卻花了 2.7 秒；最壞的情況接近 3 秒。前端的請求如果只等 1 秒，早就放棄了，後端還在做。每一步各自的逾時只保證「單一步驟不會卡死」，不保證「整件事多久結束」。

要限制的是期限（deadline）：整件事最晚什麼時候要結束，跟「每一步最多等多久」不同。做法是在最外層建立一個 signal，把同一個 signal 交給每一步。計時器只在最外層啟動一次，第一步用掉的時間，後面的步驟就少了那麼多；時間一到，正在進行的那一步收到取消，後面的步驟還沒開始就不會開始。

第一行三步都做完，約 240ms：每一步各自都沒超過 100ms。第二行在約 100ms 以 TimeoutError 停下，停的時候扣款正在進行，所以印出「扣款收到取消」，寫訂單沒有開始。兩次的差別只在 AbortSignal.timeout(100) 寫在迴圈裡面還是外面。

signal 怎麼一路傳到扣款那一層？

整體期限要有效，有一個前提：每一步真的拿到了那個 signal。結帳函式收到 signal，但呼叫扣款時忘了傳下去，就會回到 Promise.race 的情況：外層放棄了，扣款請求還在跑，甚至在客人看到「逾時」之後才扣款成功。

把同一個 signal 交給每一層呼叫，直到真正在等的那一層（fetch、資料庫查詢、計時器），叫傳遞取消（cancellation propagation）。中間任何一層漏傳，從那一層往下的工作就聽不到取消。慣例是把 signal 放在最後一個參數或選項物件裡：checkout(order, { signal })、charge(card, amount, { signal })。寫函式時看到裡面有 await，就問自己：這個 await 等的東西，收到 signal 了嗎？

💡 實務上：期限要一層比一層短
一個結帳請求會經過好幾層：瀏覽器、你的後端、付款服務，每一層都有自己的逾時。如果前端等 10 秒就放棄，後端卻沒設期限、繼續做了 20 秒，前端放棄之後的那 10 秒全是白做，佔著伺服器資源卻沒人在等結果。原則是越內層越短：後端的整體期限要比前端願意等的時間短，留時間把錯誤回傳出去。實作上常在請求進來的地方建立一個 signal（客戶端斷線或期限到就 abort），一路傳給商業邏輯、資料庫查詢、外部 API；新同事寫的函式漏傳 signal，是 code review 很常抓到的問題。
取消只是通知，不是時光倒流。扣款請求已經送到付款服務，你在這邊 abort，只是不再等回應，對方可能已經扣款成功。所以會改變狀態的請求要搭配冪等鍵（idempotency key），讓重試不會扣第二次；逾時之後也要能查詢「剛剛那筆到底成功沒有」。這部分在 Node 課第 17 課。

扣款結果不確定，怎麼定期去問、又停得乾淨？

上一節留下一個問題：扣款逾時了，錢可能扣了、也可能沒扣，只能去問付款服務。付款服務處理完之前，問一次不一定有答案，所以要每隔一段時間問一次，直到有結果。這叫輪詢（polling）。它不只出現在這裡：前端等拿鐵做好才顯示「請取餐」、後端等匯出檔案產生好，都是輪詢。下面的範例和練習 4 用「等拿鐵做好」當題材，換成後端等付款結果，程式結構一模一樣。

直覺的寫法是 setInterval。但它只管「每隔多久觸發一次」，不管上一次的非同步工作做完了沒。下面每 10ms 問一次，每次問要 35ms，第 3 次問的時候拿鐵好了。執行後看兩個數字：一共問了幾次、同時最多有幾個請求在跑：

這個寫法有三個問題：

  • 請求重疊：每 10ms 送一次、每次要 35ms，同時就有 3、4 個請求在跑；第 3 次問到「好了」時，後面已經多送了好幾次。上游越慢，同時在跑的就越多，等於在上游最需要喘息的時候加倍施壓。這正是開場付款服務卡住時最不想看到的事。
  • 停不掉已送出的：clearInterval 只停掉之後的觸發，已經送出的請求不會停。
  • 可能永遠不停：拿鐵一直沒好、或客人已經離開而沒人呼叫 clearInterval，它會永遠跑下去。

改法是「做完一次，才排下一次」：用迴圈，問一次 → 還沒好就等 intervalMs → 再問一次。這樣同一時間永遠只有一個請求在跑，上游越慢，問的頻率自然越低。等待用支援 signal 的 sleep（練習 1），取消時計時器會被清掉；signal 也交給每次的檢查，讓進行中的那一次也能停下。這個 signal 就用前面學的組法：客人離開的 signal 和一個總期限用 AbortSignal.any 合起來，輪詢就一定有終點。練習 4 會寫出這個版本。

練習區會在 3 秒時強制停止沒清掉的計時器（課首說明），在伺服器上沒有人幫你強制停止：每個請求留下一個計時器，記憶體和連線會一直累積，直到程序被重啟。Node 的 setTimeout 還會讓程序保持執行，沒清掉的計時器也會讓程序關不掉（Node 課第 21 課）。

💡 實務上：輪詢要有終點，也要問「能不能不輪詢」
「等拿鐵做好」「等報表匯出完成」這種要等幾秒到幾分鐘的事，輪詢最簡單，前後端都不用多架東西。上線前要確認三件事：有沒有總期限（拿鐵 10 分鐘還沒好就停，改顯示「請洽櫃台」）、間隔會不會對後端造成負擔（上千個客人同時開著頁面，每人每秒問一次就是每秒上千個請求）、客人離開頁面時有沒有停下。如果狀態要「一變就知道」，或同時在等的人很多，就該考慮 WebSocket、SSE 這類由伺服器主動推送的方式（後面的課會教）；第三方付款結果則通常以對方的 webhook 為主（付款完成時，由付款服務主動呼叫你的 API 通知），輪詢只當補漏。

這一課的機制都在瀏覽器的練習區示範。真正的結帳 API 跑在 Node 上，最後一節看它在伺服器上接在哪裡。

搬到 Node 伺服器上，這套機制接在哪裡？

這一課的寫法在 Node 裡完全一樣，而且用得更多。開場的結帳 API 要用到的三個接點：

  • 對外呼叫和等待：Node 的 fetch、timers/promises 的 setTimeout、fs、child_process 等很多 API 都接受 { signal }，把結帳的 signal 交給它們就能停下，在 Node 課第 8 課。
  • 客人離開：這就是前面一直說的「客人離開」signal 的來源。Node 的 HTTP 伺服器會替每個進來的請求準備一個 req.signal，連線在回應完成前斷掉時，它就被 abort，不用自己建 controller。結帳的處理函式把它和整體期限合起來：AbortSignal.any([req.signal, AbortSignal.timeout(3000)])，再把這個 signal 交給 checkout，一路傳到扣款。req.signal 從哪一版開始可靠、怎麼用 res 的 'close' 事件確認客戶端離開，在 Node 課第 13 課；呼叫外部 API 時的逾時、重試與退避，在 Node 課第 17 課。
  • 伺服器關機：部署時用同一個機制通知所有進行中的結帳收尾，在 Node 課第 21 課。

回到開場：付款服務卡住時，結帳 API 有了總期限，3 秒內一定放手；放手時付款請求真的被中斷、計時器和監聽器都清掉；客人關掉頁面，為他做的工作也跟著停。伺服器上同時卡住的請求有了上限，查菜單不會再被拖慢。

資深工程師設計一個會呼叫別人的函式時，會先回答三個問題，也就是這一課的三條主線：最多等多久（逾時或期限）？誰可以叫它停（signal 從哪裡來）？停下時要清掉什麼（計時器、監聽器、連線）？

補充與查表

這一課用到的 API，查表用，不用背：

寫法做什麼
new AbortController()建立發出取消的一端
controller.abort(reason?)發出取消；沒給 reason 時是名為 AbortError 的 DOMException；只有第一次有效
controller.signal取得收聽的一端，交給工作
signal.aborted／signal.reason是否已取消／取消的原因
signal.throwIfAborted()已取消就丟出 reason
signal.addEventListener('abort', fn, { once: true })取消的那一刻同步呼叫 fn
AbortSignal.timeout(ms)ms 毫秒後自動取消，reason 名為 TimeoutError
AbortSignal.any([s1, s2, …])任一來源取消就取消，reason 是第一個取消的來源的 reason
  • AbortSignal.any 的支援版本：從 Chrome 116、Firefox 124、Safari 17.4、Node 20.3 開始支援（MDN 的瀏覽器相容性資料）。
  • AbortSignal.timeout 算的是「活動中」的時間：MDN 註明，瀏覽器的 worker 被暫停、頁面進了上一頁快取時，計時也會暫停。

練習

練習 1：寫出支援取消的 sleep(ms, { signal } = {})：ms 毫秒後成功；沒給 signal 時就是普通的 sleep。signal 已經取消時立刻以 signal.reason 失敗；等待中被取消時清掉計時器並以 signal.reason 失敗；正常完成後要移除 abort 監聽器。

練習 2：withTimeout(task, ms, parentSignal) 現在用 Promise.race 做逾時，task 從來不知道自己被放棄了。task 是 (signal) => Promise。改成：用 AbortSignal.timeout(ms) 做逾時，有 parentSignal 時用 AbortSignal.any 合併，把合併後的 signal 傳給 task。逾時要以 TimeoutError 失敗、父 signal 取消要以 AbortError 失敗，而且 task 要真的收到取消。

練習 3：runWithDeadline(steps, ms, parentSignal) 依序執行 steps（每一步是 (signal) => Promise），全部完成時回傳每一步結果的陣列。加上整體期限：整件事最多 ms 毫秒，不是每一步各 ms。期限到了，進行中的那一步要收到取消、後面的步驟不能開始，並以 TimeoutError 失敗；有 parentSignal 時也要能被它取消（AbortError）。

練習 4：pollUntil(check, { intervalMs, signal }) 要等拿鐵做好：呼叫 check(signal)（回傳 Promise），結果是 truthy 就以那個值成功；不是就等 intervalMs 再問一次。現在的版本用 setInterval，請求會重疊、也不能取消。改成：上一次 check 還沒結束不能開始下一次；signal 取消時以 signal.reason 失敗、清掉計時器、之後不再呼叫 check；一開始就已取消時直接失敗、一次都不呼叫 check；check 丟錯時以同一個錯誤失敗。練習 1 的 sleep 已經放在程式裡，可以直接用。

練習 5：await Promise.race([fetchMenu(), timeout(1000)])，1 秒後 timeout 先失敗了。這時 fetchMenu() 送出的請求怎麼了？

✓ Promise 沒有取消的能力，race 只是「誰先定案就用誰」，不會通知其他工作。fetchMenu 沒收到任何 signal，請求照樣佔著連線直到上游回應，所以 a、b 都不對。要讓它真的停下，寫成 fetchMenu({ signal: AbortSignal.timeout(1000) })，把 signal 傳到 fetch。

練習 6：結帳有三個步驟（查庫存、扣款、寫訂單），每一步都用 AbortSignal.timeout(1000) 設了 1 秒逾時。整個結帳最久大約會等多久？

✓ 每一步各自計時，三步各花 0.99 秒都不會逾時，加起來接近 3 秒。要限制整件事，在最外層建立一個 AbortSignal.timeout(1000)，把同一個 signal 傳給每一步，這才是整體期限。c 不對：每一步的逾時都有效，只是時間會相加。

練習 7：使用者在菜單載入到一半時切到別的頁面，程式呼叫了 controller.abort()，fetch 因此以 AbortError 失敗。catch 裡該怎麼處理？

✓ 取消是呼叫端自己決定的，不是故障。顯示錯誤會讓使用者每換一頁就看到一次錯誤訊息；送進錯誤監控會淹沒真正的問題。重試更不對：使用者已經不要這個結果了。要提示或重試的是 TimeoutError（對方太慢）和其他真正的錯誤。

常見錯誤

  • 用 Promise.race 做逾時，沒有取消輸家：呼叫端放棄了，工作還在跑、佔著連線。用 AbortSignal.timeout(ms)，把 signal 傳進工作。
  • 忘了檢查 signal 一開始就已取消：已經取消的 signal 不會再觸發 abort 事件，工作會一直等。開頭先 if (signal?.aborted) 或 signal.throwIfAborted()。
  • abort 時沒清掉計時器，或完成後沒移除監聽器：Promise 定案了，計時器和監聽器還在，伺服器上越積越多。取消時 clearTimeout，完成時 removeEventListener。
  • 把 AbortError 當成錯誤顯示或回報：使用者自己取消的事變成滿畫面的錯誤訊息。依 e.name 分類：AbortError 安靜結束、TimeoutError 提示重試、其他照常處理。
  • 每一步各自設逾時，以為整件事就有期限：總時間是各步相加。整體期限用一個 signal，傳給每一步。
  • signal 沒有一路傳下去：外層取消了，最底層的 fetch 或查詢還在跑。每一層呼叫都把 signal 交給下一層。
  • 用 setInterval 執行非同步工作：上一次還沒回來就送下一次，上游越慢越重疊；取消時也常忘了 clearInterval。改成迴圈：做完一次、等一段時間、再做下一次。

小結

  • 付款服務卡住會拖垮結帳 API，因為 Promise 不能取消：放棄等待不等於工作停下。要停下工作，用 AbortController 發出取消，把 AbortSignal 傳給工作。
  • 自己的非同步函式支援 signal 要做四件事：先檢查、監聽 abort、取消時清理並以 signal.reason 失敗、完成時移除監聽器。只在步驟之間檢查，正在等的那一段聽不到取消。
  • 逾時用 AbortSignal.timeout(ms)，不用 Promise.race；reason 的名稱分出 AbortError（自己取消，安靜結束）與 TimeoutError（對方太慢，提示重試並記錄）。
  • 「客人離開」和「時間到」用 AbortSignal.any 合成一個 signal。整體期限是最外層一個 signal 傳給每一步，不是每一步各自逾時；signal 要一路傳到真正在等的那一層。取消只是通知，已送出的扣款可能已經成功。
  • 輪詢用「做完一次才排下一次」的迴圈，等待可以被取消、計時器一定清掉，並且有總期限。
