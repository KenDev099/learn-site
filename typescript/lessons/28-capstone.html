階段 6：實戰 · 第 28 課

期末專題：型別安全的訂單模組

這是 JS、非同步與 TypeScript 課的最後一課，沒有新語法。店長準備開放線上點餐，給了你七條需求，要你做出咖啡店的訂單模組：客人送出訂單、檢查庫存、算金額、付款、取消，最後回覆 HTTP 回應。整課跟著同一個請求走：會員王小明在 App 上點了拿鐵、卡布奇諾、可頌各一，按下「結帳」。這個請求從進到伺服器、被檢查、扣庫存、存起來，到回覆「建立成功」，每經過一站就是這課的一個步驟；途中它還會被按兩次、送錯欄位、碰上庫存不足，這些都要處理好。

前 27 課各自練過一種技巧，這一課練的是把它們組起來時的判斷：一條規則該放在哪裡、先寫什麼後寫什麼、哪裡最容易在上線後出事。做完之後，你手上會有一份可以直接帶進 NestJS 課的設計。

這課的路線：
  1. 需求與規則：七條需求怎麼拆成型別和規則，每條規則該在哪裡檢查。
  2. 分層與 Result：規則分別放進 handler、service、repository 三層；service 失敗時，怎麼讓 handler 知道是哪一種失敗（到這裡，整個模組的骨架就定下來了）。
  3. 步驟 1～3（型別、驗證、儲存）：先定好各層之間的型別，把 HTTP 送來的 unknown 變成 CreateOrderInput，再寫存取都用複本的 repository。
  4. 步驟 4～5（下單、狀態）：先全部檢查再扣庫存、金額只捨入一次；付款、完成、取消照狀態轉換表走，取消要把庫存加回去。
  5. 步驟 6～7 與交付：結帳被連按、客人取消、付款逾時時只建一筆訂單；錯誤轉成 201／400／404／409；到了 NestJS 誰來做這些事，交付前要逐項確認什麼。
這課會用到：
  • 第 27 課的 Result、品牌 ID 與狀態轉換表：預期中的失敗放進回傳值 { ok, value | error }；品牌讓未經檢查的值不能冒充訂單編號；允許的狀態轉換寫成一張資料表。
  • 第 26 課的 parse 與 issues：外部資料用 unknown 接，檢查完回傳型別精確的新物件；問題帶路徑收進 issues，一次全部列出。
  • 第 23 課的建構子注入：service 需要的 repository 從建構子傳進來，測試時換成假的。
  • 第 19 課的泛型 repository：InMemoryRepository<T> 的存取方法寫一次，商品、訂單都能用。

店長的七條需求，要做出什麼？

店長給的需求只有七條。先完整讀一遍，不要急著寫程式：

  1. 客人送出訂單：顧客編號、是否為會員、品項（商品 id、數量）。輸入來自 HTTP，什麼都可能送來。
  2. 每個品項數量 1～20、最多 10 個品項、同一個商品不能重複出現。
  3. 商品要存在、上架中、庫存足夠；任何一項不符合，整張訂單都不成立，庫存不能被扣。
  4. 訂單記下當下的單價；會員打 85 折，整張訂單最後四捨五入一次到整數元。
  5. 訂單狀態：pending → paid → done；pending、paid 可以取消，取消時把庫存加回去。
  6. 同一個購物車在處理中被重複送出，只能建立一筆訂單；客人取消或逾時時，不能建立訂單。
  7. 對外：成功回 201；輸入錯誤 400；找不到 404；庫存不足、商品下架、狀態不允許 409。

第 7 條的數字是 HTTP 狀態碼，第 4 課見過 400、404、409。這裡多一個 201：「已建立」，新增資料成功時用，比 200 更精確。Node 課第 12 課會完整講。狀態碼分這麼細，是因為前端要靠它決定下一步：收到 400，知道要請客人改輸入；收到 409，知道是商品或訂單的狀態不允許，要換商品或減少數量；收到 404，知道要找的東西不在了。全部回同一個碼，前端只能顯示「發生錯誤」。

這七條讀起來像一張待辦清單，其實混著三種東西：要存下來的資料（訂單、商品）、要遵守的規則（數量 1～20、庫存足夠、狀態怎麼變）、對外的約定（狀態碼）。直接照順序寫，最常見的結果是一個很長的函式：開頭檢查欄位，中間查庫存、算錢，最後組回應，所有規則纏在一起。要改折扣得讀完整個函式，要測庫存不足得組出完整的 HTTP 請求。所以動手前的第一件事是拆開：哪些是資料，哪些規則該在哪裡檢查。

每條規則該在哪裡檢查？

跟 PostgreSQL 課的期末專題一樣，先把需求拆成兩堆。名詞會變成型別：商品（Product）、訂單（Order）、明細（OrderItem）、客人送進來的資料（CreateOrderInput）、購物車（這課只用到它的 id）。規則則要決定放在哪裡檢查：同一條規則放錯地方，不是擋不住，就是到處重複。

決定放哪裡，問一個問題就夠：只看客人送來的資料，就能判斷對錯嗎？拿王小明的訂單試試。如果他把拿鐵的數量送成 21，不用查任何東西就知道錯了，第 2 條寫了上限是 20；這類規則放在輸入驗證，請求一進來就檢查。如果他點的卡布奇諾只剩 1 杯，光看他送來的資料看不出問題，要查了目前的庫存才知道；這類規則放在下單的業務邏輯，也就是真正處理「下單」這件事的程式。

分成兩處的理由是成本與信任。輸入驗證不碰資料、很便宜，可以最先做，把格式錯誤的請求擋在最外面；業務邏輯要查資料、會修改資料，它只該處理格式已經確定正確的輸入，不必每一行都提防欄位是不是字串。照這個問題把七條需求過一遍（「步驟」欄是本課後面的步驟編號）：

規則在哪裡檢查步驟
欄位的型別、數量範圍、品項筆數、商品不重複輸入驗證：只看輸入本身就能判斷2
商品存在、上架、庫存足夠下單的業務邏輯：要查目前的資料才知道4
單價、會員折扣、四捨五入下單的業務邏輯4
狀態怎麼變、取消加回庫存狀態轉換表＋業務邏輯5
重複送出、取消、逾時呼叫下單的那一層6
狀態碼、回應欄位對外的那一層7

最後兩列不屬於前面兩堆。重複送出、取消、逾時跟「這張訂單合不合法」無關，問的是「同一個請求被送了幾次、等了多久」，所以由呼叫下單的那一層處理；狀態碼與回應欄位是 HTTP 的事，由對外的那一層處理。

💡 實務上：需求一定有洞，寫程式前先問清楚
工作中拿到的需求很少像這七條一樣完整，常常只有「做一個下單功能」。像上面這樣把規則逐條列出來、標上在哪裡檢查，空白處就會自己浮現：會員折扣跟優惠券能不能疊加？取消已付款的訂單要不要退款？第 6 條的「逾時」是幾秒？這些是店長或 PM 的決定，不是工程師自己猜。資深工程師會把問題整理成一張清單一次問完，把答案寫進需求文件或工單（ticket）裡，之後有爭議時才有依據。

表的第二欄出現了好幾個「地方」：輸入驗證、業務邏輯、呼叫下單的那一層、對外的那一層。它們在程式裡各是什麼？

這些「地方」在程式裡怎麼切開？

後端程式通常把上面那幾個地方切成三層，這種做法叫分層（layering）：每一層只做一種事，只跟相鄰的層說話。

handler 是對外的入口，NestJS 裡叫 controller。它是唯一認得 HTTP 的一層：從請求取出 body 和路由參數、檢查格式、呼叫 service，再把結果轉成狀態碼與回應。表格裡的輸入驗證、呼叫下單的那一層、對外的那一層，都在這裡。它不放業務規則：折扣怎麼算、庫存夠不夠，不歸它管。

service 放業務規則：下單、付款、取消都在這裡。它不知道 HTTP 的存在，收到的是已經驗證過的資料，回傳的是「成功了，這是訂單」或「失敗了，原因是什麼」，而不是狀態碼。它也不知道資料存在哪裡，要查商品、存訂單，都透過 repository。

repository 只管儲存：存、取、列出資料。這一課存在記憶體，換成 PostgreSQL 時只換這一層。

把王小明的請求放進下面這張圖：請求先到 handler，格式檢查通過後交給 service；service 透過 repository 讀出三個商品、確認庫存、算出金額、存下訂單；結果回到 handler，轉成 201。

為什麼要切三層，而不是一個函式從頭寫到尾？看看不切的時候會怎樣。第一是難測試：想測「會員打 85 折」，得先組出完整的 HTTP 請求、準備一個真的資料庫。切開之後，service 不碰 HTTP、不碰資料庫，測試時從建構子傳一個假的 repository 進去（第 23 課的建構子注入），直接呼叫下單的方法就能測折扣。

第二是難替換：資料存取散在各處時，從記憶體換成 PostgreSQL 要改遍每個函式；切開之後只換 repository，service 一行都不用改。第三是難找：客服回報「409 的訊息不對」，去 handler 找；「折扣算錯」，去 service 找。不切的話，兩件事都藏在同一個長函式裡。

分層也有代價：檔案變多，資料每過一層就要轉換一次。三五個端點的小工具不必分得這麼細；會長大、會有很多人一起改的服務才值得。訂單是咖啡店的核心，之後會一直加功能，所以這課照三層切。NestJS 課第 18 課會在真的專案裡再談一次。

切開之後，層與層之間要傳東西，最麻煩的是失敗。service 發現卡布奇諾不夠，handler 要回 409；發現商品不存在，要回 404。可是 service 不認得狀態碼，它要怎麼告訴 handler 是哪一種失敗？

下單失敗時，service 怎麼告訴 handler 是哪一種失敗？

第 4 課把失敗分成兩種。預期中的失敗是業務上本來就會發生的事：庫存不足、商品下架、找不到訂單。程式要好好處理，回給客人看得懂的訊息。bug 與基礎設施故障是不該發生的事：讀到 undefined 的屬性、資料庫斷線。處理方式是讓它爆出來、記 log、回 500，再去修。

如果預期中的失敗也用 throw，問題在於呼叫者看不到它：函式的回傳型別寫著 Order，看不出它可能丟出「庫存不足」的例外，哪一處忘了 catch，客人看到的就是 500。第 27 課的做法是把預期中的失敗放進回傳型別，這個型別叫 Result：

type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }

成功是 { ok: true, value }，失敗是 { ok: false, error }，用 ok()、err() 兩個小函式建立。呼叫者拿到的是聯合型別，不先檢查 ok 就讀不到 value，「忘了處理失敗」在編譯時就會被發現。error 再寫成可辨識聯合，每一種失敗有自己的 type，handler 用 switch 依 type 決定狀態碼。

所以這課的分工是：預期中的失敗回傳 Result，bug 與基礎設施故障才 throw。分層圖裡 service 回到 handler 的那條箭頭，傳的就是 Result。到這裡，整個模組的骨架已經定下來：七條需求拆成型別與規則，規則依「只看輸入能不能判斷」放進 handler 或 service，儲存交給 repository，層與層之間用 Result 回報失敗。剩下的是照什麼順序把它寫出來。

七個步驟照什麼順序寫？

實務上的順序是從約定往外寫。先定型別，因為每一層都要用它溝通。再寫最外面的驗證和最裡面的儲存，因為它們不依賴別的部分，可以單獨寫、單獨測。然後才寫夾在中間、同時用到兩者的業務邏輯：下單與狀態。最後處理只有真實環境才會出現的問題：同一個請求來兩次、等太久，以及對外的回應。

練習

下面每一步一題，各自判分。第 2 步之後的起始程式，下半部已經放好前面各步的參考解（標著「前面步驟的參考解（不用改）」），所以前面卡住也能繼續做後面。你只要改上半部標著 TODO 的地方。

步驟 1：各層之間要先約定哪些型別？

型別先寫，因為 handler、service、repository 都照它溝通，它定錯了，三層都要改。這一步有四個設計決定，每一個都在防一種上線後才會出現的錯誤。

狀態不用 string。訂單狀態只有四種：pending、paid、done、cancelled。型別寫 string 的話，有人寫成 'payed'，編譯照樣通過，switch 也沒辦法檢查有沒有漏掉哪一種。用字面值的聯合型別就能擋下拼錯。但聯合型別只在編譯時存在，執行時拿不到「有哪些狀態」這份清單，而驗證外部資料時正需要它。所以反過來寫：先寫一個 as const 的陣列，再從它推出聯合型別（第 20 課）。清單只寫一次，編譯時和執行時都用得到。

OrderId 是品牌字串。第 27 課的訂單編號是加了品牌的 number，這課改用字串。原因是訂單最後要存進 PostgreSQL，編號欄位用 bigint 時可能超過 JS 的 Number.MAX_SAFE_INTEGER（9007199254740991）；超過之後，number 沒辦法精確表示每一個整數（第 5 課），例如 9007199254740993 存成 number 會變成 9007199254740992，查到的就是別人的訂單。所以訂單編號在 JS 裡用字串保存。再加上品牌，一般字串就不能冒充訂單編號，只能經過 toOrderId 檢查後取得；toOrderId 就是第 27 課的 smart constructor：驗證通過才貼上品牌，是產生 OrderId 的唯一入口。

輸入型別跟資料型別分開。王小明送來的只有顧客編號、是否為會員、品項（商品 id、數量）。訂單上的 id、狀態、單價、總金額，都由伺服器決定。如果直接拿 Order 當輸入型別，等於宣告「客人可以送單價過來」，只要有一處程式照著輸入存，客人就能自己把拿鐵改成 1 元。所以另外寫 CreateOrderInput。它不重抄欄位，而是用 Pick 從 Order、OrderItem 挑出需要的欄位（第 21 課），之後欄位改名時兩邊一起變，不會一邊忘了改。

錯誤是可辨識聯合，不是字串訊息。錯誤如果只是一句「庫存不足」，handler 只能比對文字決定狀態碼，改一個字就壞；前端也拿不到「還剩幾杯」。所以每一種錯誤寫成帶 type 的物件，並帶自己需要的資料：庫存不足帶 available，前端才能顯示「卡布奇諾只剩 1 杯」；狀態不允許帶 from、to，log 裡才看得出是哪一步被擋。

💡 實務上：型別先定好，前後端可以同時開工
團隊裡常見的流程是後端先把輸入、回應、錯誤的形狀定下來，前端照著它做畫面、用假資料先跑，不必等 API 寫完。所以這份型別一旦有人在用，就不能隨手改：欄位改名或刪掉會讓前端壞掉，新增欄位通常比較安全。要改之前先問「誰在用這個欄位」，大改時跟前端約好一起上線。錯誤型別也算約定的一部分，前端會依 type 顯示不同的提示，新增錯誤種類要通知他們。

練習 1：完成四個 TODO：

  • ORDER_STATUSES：'pending'、'paid'、'done'、'cancelled'，OrderStatus 從它推導。
  • OrderId：品牌型別，底層是 string。toOrderId(raw) 只接受不以 0 開頭的數字字串（'1'、'9007199254740993'），其他（''、'0'、'012'、'12a'…）丟 RangeError。
  • CreateOrderInput：customerId（number）、isMember（boolean）、items（每筆只有 productId、quantity）。用 Pick 從現有型別推出 customerId 與 items 的每一筆。
  • OrderError：invalid_input 帶 issues: Issue[]；not_found、unavailable 帶 productId: number；out_of_stock 帶 productId 與 available；invalid_transition 帶 from、to（OrderStatus）；order_not_found 帶 id: OrderId。

步驟 2：HTTP 送來的資料，怎麼變成可以信任的 CreateOrderInput？

上一步的型別只在編譯時存在。王小明的請求從網路送進來時，伺服器拿到的是一段 JSON 文字，JSON.parse 之後的型別是 any，實際內容什麼都可能：欄位缺了、數字變成字串、多了奇怪的欄位（第 17 課）。這時如果寫 body as CreateOrderInput，編譯器就相信了，錯誤要等到 service 深處讀到 undefined 才爆出來，離來源很遠。所以入口用 unknown 接，逐欄檢查，通過才回傳一個型別是 CreateOrderInput 的新物件。這就是第 26 課的 parse, don't validate：檢查的結果不是 true／false，而是一個型別更精確的值，之後的程式不用再檢查。

寫這個 parse 函式時，有四個決定會影響前端與安全。第一，一次列出所有問題。遇到第一個錯就停的話，王小明送錯兩個欄位時，要改一次、送出、被擋、再改一次。所以把問題全部收進 issues 陣列，檢查完才回傳。每個問題帶路徑，例如 items[1].quantity 是第二個品項的數量，前端才能把錯誤訊息標在對的輸入框旁邊。商品重複時，路徑指向第二次出現的那一筆，因為那筆才是多出來的。

第二，不做型別轉換。JSON 本身能表達數字，前端送來 "quantity": "2" 是前端的 bug，偷偷轉成 2 會把 bug 藏起來，要擋下來。只有 query string（網址 ? 後面的參數）一定是字串，那裡才需要轉換。

第三，只輸出認得的欄位。客人多送的 coupon、note，甚至 unitPrice，都不會出現在 parse 組出來的新物件裡。如果改成把原本的 body 往後傳，未知欄位就可能一路被寫進資料庫，這就是第 26 課的大量指派（mass assignment）。之後的程式只用 parse 的回傳值，不再碰原本的 body。

第四，回傳 Result，不 throw。輸入有問題是預期中的事，所以回傳型別是 Result<CreateOrderInput, Issue[]>，前面講的分工在這裡第一次用上。這一步之後，王小明的輸入要嘛帶著完整的問題清單被退回，要嘛變成一個欄位乾淨、型別精確的 CreateOrderInput。

練習 2：寫 parseCreateOrderInput(x: unknown)：

  • x 不是物件（包括 null、陣列）：一個問題，路徑 ''。
  • customerId 正整數；isMember 布林；items 是 1～10 筆的陣列（不符合時路徑 'items'）。
  • 每一筆要是物件（路徑 items[i]）；productId 正整數、不能跟前面重複（路徑 items[i].productId）；quantity 1～20 的整數（路徑 items[i].quantity）。
  • 有問題回傳 err(issues)，全部列出；沒問題回傳 ok(新物件)，只包含認得的欄位。不能用 as 把 x 轉型後直接回傳。

步驟 3：訂單和商品存在哪裡？為什麼存取都要用複本？

輸入乾淨了，下單時要查商品、存訂單，這是 repository 的工作。repository 是 service 跟資料之間的介面：service 只知道它有 findById、save、list 三個方法，不知道背後是記憶體還是資料庫。這一步寫一個存在記憶體的版本，方法跟換成資料庫時一模一樣，所以 service 寫好之後，換儲存方式不用改。

這一步的關鍵是存進去、拿出來的都是複本。原因要從真的資料庫說起：從 PostgreSQL 查出一筆訂單，拿到的是那一列的複製品，你改了這個物件的 status，資料庫裡的那一列不會變，要再下 UPDATE 才會變。記憶體版本如果把物件直接放進 Map、再把同一個物件拿出來，行為就不一樣了：第 2 課講過，物件傳的是參考，service 改了拿出來的物件，Map 裡的那一份也跟著變，沒有 save 也「存好了」。結果是測試在記憶體版本上全部通過，換成資料庫後，忘了 save 的地方全部壞掉，而且只在上線後出現。讓記憶體版本也回傳複本，它的行為就跟資料庫一致，忘了 save 的 bug 在測試裡就會被抓到。

複製用 structuredClone：它會深層複製，訂單裡的 items 陣列也是新的，createdAt 仍然是 Date。另外兩種常見寫法都不夠：JSON.parse(JSON.stringify(x)) 會把 Date 變成字串；展開 { ...x } 只複製最外面一層，裡面的 items 陣列還是同一個，改它一樣會改到存著的那一份。

最後是型別。商品的 id 是 number，訂單的 id 是 OrderId，同一個泛型 repository 要兩種都能用，而且 findById 只收對的那一種，拿一般字串去查訂單要編譯錯誤。做法是把 id 的型別寫成 T['id']，意思是「T 的 id 欄位是什麼型別，這裡就是什麼型別」，於是 Repository<Order> 的 findById 只收 OrderId。要寫 T['id']，T 就一定得有 id 欄位，所以泛型要加限制。TypeScript 內建的 PropertyKey 型別就是 string | number | symbol，也就是能當屬性名稱的那幾種值，限制寫成 T extends { id: PropertyKey }：T 必須有 id，而且 id 是字串、數字或 symbol。

練習 3：寫 interface Repository<T>（findById(id) 回傳 T 或 undefined、save(entity)、list()）與實作它的 InMemoryRepository：用 Map 存，save 存複本（同 id 就取代），findById 與 list 回傳複本。

步驟 4：下單時，怎麼確保失敗了庫存一杯都沒扣、金額也不差 1 元？

型別、驗證、儲存都備齊了，現在寫夾在中間的 placeOrder：檢查每個品項、扣庫存、算金額、存訂單。聽起來是照順序做四件事，但有兩個地方很容易寫錯，而且錯了不會報錯，只會讓資料悄悄變錯。

第一個是邊檢查邊修改。王小明的訂單每樣只點一個，看不出問題，所以這裡換一張會失敗的訂單：拿鐵 2 杯、卡布奇諾 2 杯，但卡布奇諾只剩 1 杯。下面的寫法每檢查完一個品項就扣一個，看起來很自然。執行後看最後一行：拿鐵剩幾杯。

卡布奇諾不夠，訂單失敗，但拿鐵已經扣了 2 杯。這張訂單沒有成立，店裡卻憑空少了兩杯拿鐵的庫存，下一位客人點拿鐵時可能被告知賣完。原因是檢查和修改交錯進行：後面的檢查失敗時，前面的修改已經發生，也沒有人把它改回來。正確的順序是兩輪：第一輪只檢查、什麼都不改，任何一項不通過就直接回傳錯誤；全部通過才進第二輪修改。需求第 3 條「任何一項不符合，庫存不能被扣」要的就是這個順序。

第二個是金額只四捨五入一次（第 5 課）。回到王小明的訂單：他是會員，點了拿鐵 110、卡布奇諾 110、可頌 70。打 85 折有兩種算法：每一行先打折、捨入再加總，或整張加總後打折、最後捨入一次。執行後比較兩行印出的金額：

差 1 元。每一行先捨入，等於每一行都吃一次捨入誤差，品項越多差得越多。哪一種才對由店家決定，但要寫清楚、全系統一致：收銀機和 App 算出來差 1 元，客服就會接到電話。本課的規則是需求第 4 條：整張最後捨入一次。計算時先乘 85 再除以 100，中間值保持整數，避開乘上 0.85 時的浮點數誤差。

剩下三個決定比較單純，各自防一種問題。第一，明細記下當下的單價：訂單明細存 unitPrice，而不是只存商品 id、要用時再查目前的價格。下個月拿鐵漲價，上個月的訂單金額不能跟著變（PostgreSQL 課第 10 課）。

第二，時間和編號從外面傳進來：clock 與 nextId 由建構子注入，測試時傳固定的時間和編號，結果每次都一樣。service 裡直接寫 new Date()，就沒辦法測「建立時間對不對」。

第三，這一課的 placeOrder 收 unknown、自己先 parse：照分層圖，驗證應該在 handler。但這課沒有 HTTP 框架，沒有地方能在進 service 之前擋，所以在 placeOrder 開頭呼叫步驟 2 的 parse。到了 NestJS，框架會在請求進 controller 之前先跑一段檢查參數的程式，這段程式叫 pipe。parse 會搬到 pipe 裡，service 的參數就能直接寫成 CreateOrderInput（練習 8）。

兩輪的做法在這課成立，前提是 repository 是同步的：檢查和修改之間沒有 await，不會被別的請求插隊（第 7 課）。換成真的資料庫後，兩個請求可能同時通過檢查、一起把庫存扣成負的。那時要靠交易加上條件式更新：UPDATE products SET stock = stock - 2 WHERE id = 3 AND stock >= 2，影響 0 列就是庫存不足（PostgreSQL 課第 19 課、NestJS 課第 15 課）。

練習 4：完成 OrderService 的 placeOrder(input: unknown)，回傳 Result<Order, OrderError>：

  • 先用 parseCreateOrderInput 驗證，失敗回傳 invalid_input（帶 issues）。
  • 依序檢查每個品項：不存在 not_found、下架 unavailable、庫存不足 out_of_stock（帶目前庫存）。
  • 全部通過才扣庫存；明細記下當下的單價；會員 85 折，整張最後四捨五入一次。
  • 新訂單：id 用 nextId()、createdAt 用 clock()、狀態 pending，存進注入的 orders。

步驟 5：付款、完成、取消，怎麼讓訂單狀態只照規則走？

王小明的訂單建立了，狀態是 pending。接下來他付款（paid）、店員做好飲料（done）；或者他在付款前後改變心意，取消（cancelled）。需求第 5 條規定了哪些轉換可以發生，第 27 課把它寫成一張狀態轉換表，起始程式的參考解裡已經有 TRANSITIONS。這一步把它接到 service 的 pay、complete、cancel 三個方法。

執行時也要查表。第 27 課用型別讓「已知狀態的非法轉換」在編譯時報錯。但這裡的訂單是從 repository 讀出來的，它現在是什麼狀態，要執行時才知道；在型別上它只是 OrderStatus 四種之一，編譯器擋不住。所以每個方法都要在執行時查一次 TRANSITIONS：目前的狀態允不允許轉到目標狀態，不允許就回傳 invalid_transition。

取消時，先轉換，成功才加回庫存。取消要把每個品項的數量加回庫存。順序反過來會出事：先加庫存再轉換狀態的話，王小明連按兩次取消，第二次雖然會因為 cancelled → cancelled 不在表上而失敗，庫存卻已經又加了一次；每多按一次，庫存就憑空多出來。先轉換，第二次在轉換那一步就失敗，根本走不到加庫存。這跟步驟 4 是同一個道理：會失敗的檢查放在修改之前。

改完要存回去。步驟 3 的 repository 回傳複本，findById 拿到的訂單改了也不會影響存著的資料。所以用展開組一個狀態不同的新物件，再 save 回去，跟換成資料庫時要下 UPDATE 一樣。步驟 3 的設計在這裡發揮作用：忘了 save，測試會失敗。

三個方法做的事幾乎一樣：讀出訂單、找不到就回 order_not_found、查表、存新狀態。寫一個私有的共用方法（例如 #move(id, to)，# 開頭是第 23 課的私有成員），三個方法各自呼叫它，會比複製三次好改：以後轉換時要多記一個時間，只改一個地方。

練習 5：完成 pay(id)（→ paid）、complete(id)（→ done）、cancel(id)（→ cancelled），都回傳 Result<Order, OrderError>：找不到訂單回傳 order_not_found（帶 id）；轉換表不允許回傳 invalid_transition（帶 from、to）；成功時存回新物件並回傳它；cancel 成功後把每個品項的數量加回庫存。

步驟 6：結帳被按兩下、客人取消、付款逾時，怎麼只建一筆訂單？

到上一步為止，每個方法都假設一個請求只來一次、而且馬上處理完。真實的結帳不是這樣。王小明按下「結帳」後網路很慢，畫面沒反應，他又按了一次；或者手機從 Wi-Fi 切到行動網路，前端自動重送。兩個請求帶著同一台購物車進來，如果各自呼叫 placeOrder，就會建立兩筆訂單、扣兩次庫存。需求第 6 條要求：同一台購物車處理中被重複送出，只能建立一筆。

做法是第 12 課的 single-flight：同一件事正在進行時，後來的呼叫不重做一次，而是拿到同一個 Promise、等同一個結果。具體來說，用一個 Map 記下「哪台購物車（cartId）的結帳正在進行、對應的 Promise 是哪一個」。新呼叫進來先查 Map：有，就直接回傳那個 Promise，placeOrder 不會被執行第二次；沒有，才開始新的結帳並記進 Map。結帳結束時，不管成功還是失敗，都要把紀錄清掉；不清的話，失敗後客人重試，拿到的永遠是同一個失敗。

另一個問題是等待。結帳時要先等付款閘道回應，這裡用 delay(signal) 模擬這段等待。等待期間有兩種情況要停下來：客人按了取消，或等太久超過期限。兩種都透過第 11 課的 AbortSignal 傳進來：取消由呼叫者的 AbortController 觸發，逾時用 AbortSignal.timeout 產生。signal 被觸發時，delay 會以 signal.reason（取消或逾時的原因）失敗。需求說這時不能建立訂單，所以順序一定是先 await delay(signal)，確定沒被取消才呼叫 placeOrder；反過來先下單再等，客人取消時訂單已經建好了。

兩個機制合在一起，有一個設計決定要講清楚：共用的工作只用第一個呼叫者的 signal。第二個呼叫者按取消，只是他自己不等了，停不了別人的工作。如果要「所有人都取消才停」，得自己數還有幾個人在等、每個人離開時減一，複雜度高很多。結帳的情境裡，兩次點擊來自同一位客人，用第一個就夠了。

💡 實務上：Map 只擋得住同一個程序裡的重複送出
這個 Map 只存在一個程序的記憶體裡。正式環境有好幾台伺服器，王小明的兩次點擊可能被分到不同台；伺服器重啟，Map 也就清空了。這兩種情況下，Map 都擋不住重複送出。那時要用冪等鍵（idempotency key）：前端每次結帳帶一個唯一的鍵，伺服器把它存進資料庫的 UNIQUE 欄位，同一個鍵第二次進來就回傳第一次的結果（系統設計課第 9 課）。review 結帳、付款這類 API 時，先問「同一個請求來兩次會怎樣」，答案不能只靠記憶體。

練習 6：完成 createCheckout(service, { delay })，回傳 checkout(cartId, input, { signal })：

  • 同一個 cartId 處理中時，再呼叫拿到同一個 Promise，placeOrder 只執行一次。
  • 處理時先 await delay(signal)；被取消或逾時就以 signal.reason 失敗，不能呼叫 placeOrder。
  • 結束（成功或失敗）後，同一個 cartId 可以重新結帳；不同 cartId 互不影響。

service 的型別是 PlaceOrder：只要求有 placeOrder 方法。這一層只用到這一個方法，型別就只要求這一個，測試時傳一個假的物件就能測。

步驟 7：怎麼把 Result 轉成 HTTP 回應，又不多送欄位？

王小明的請求走到最後一站：service 回傳了 Result，handler 要把它轉成 HTTP 回應。成功時回 201 和訂單內容；失敗時依錯誤種類回 400、404 或 409，對應關係就是需求第 7 條。這一步有兩件事要做對。

第一，狀態碼用 switch 加 assertNever 對應（第 16 課）。switch 依 error.type 分支，每個 case 回一個狀態碼，default 呼叫 assertNever(error)。assertNever 的參數型別是 never，只有前面的 case 已經處理完所有種類、error 被縮小到什麼都不剩時，這個呼叫才通過編譯。所以以後有人在 OrderError 加了第七種錯誤，這裡會出現型別錯誤，提醒你決定它要回什麼。如果寫 default: return 409，新錯誤會悄悄被當成 409，沒有人會發現。

第二，回應只送該送的欄位。回應的型別寫成 Pick，看起來已經限制了欄位，但型別只是編譯時的約定，執行時不會幫你刪掉任何東西。執行後看第一行印出的 JSON：

編譯通過，顧客編號卻被送出去了。原因是 TypeScript 的結構型別：物件只要有目標型別要求的欄位，多出來的欄位不影響指定；只有當場寫的物件字面值才會做多餘屬性檢查（第 14 課）。這次多送的是顧客編號；換成會員資料，可能就是電話、地址或密碼雜湊。修法是白名單：一個欄位一個欄位挑出來，組成新物件。這樣以後 Order 加了內部欄位，也不會自動流到回應裡。

練習 7：寫 toHttpResponse(result)：成功回 { status: 201, body }，body 只有 id、status、total、items；失敗回 { status, body: { error } }：invalid_input 400，not_found、order_not_found 404，unavailable、out_of_stock、invalid_transition 409。用 switch 對應，default 交給 assertNever。

做完七步：到了 NestJS，誰來做這些事？

七個步驟做完，王小明的請求從進來到回覆 201，每一站都是你親手接起來的：parse 是你在 placeOrder 開頭呼叫的，repository 是你從建構子傳進去的，錯誤轉狀態碼是你寫的 switch。NestJS 這類框架接手的，正是「誰來呼叫、什麼時候呼叫」。型別可以照搬，變的是誰負責呼叫：

6 非同步記憶體裡的 single-flight冪等鍵＋interceptor（第 9 課、系統設計課第 9 課）
7 對外toHttpResponseexception filter／HttpException，或 controller 裡轉換 Result（第 8 課）

表裡的 NestJS 名詞，NestJS 課會一個一個教，這裡先知道它們各在哪一站：pipe 在 controller 方法執行前檢查參數，對應步驟 2；DTO 是描述請求內容的 class，pipe 照它檢查；exception filter 把丟出來的例外轉成 HTTP 回應，對應步驟 7；interceptor 包在 controller 方法的前後執行，對應步驟 6。下面三題用這課的知識推推看，每一題對應一個步驟。步驟 2 的 schema 寫法是較新的版本才有的，版本細節見課末「補充與查表」。

練習 8：到了 NestJS，步驟 2 的輸入驗證通常放在哪裡？

✓ NestJS 的 pipe 在 controller 方法執行前檢查參數，失敗直接回 400，service 收到的一定是合法資料。a 讓 service 的參數只能寫成 unknown，「格式對不對」跟「業務上允不允許」混在一起；本課的 placeOrder 這樣寫，是因為還沒有框架能在入口擋，有了 pipe 就該移出去。c 錯在型別在執行時已經擦掉，參數型別擋不住任何東西，所以 DTO 要寫成 class 才能讓 ValidationPipe 在執行時讀到規則（NestJS 課第 7 課）。

練習 9：步驟 4 的 OrderService 建構子要收 repository、clock、nextId。在 NestJS 裡，這些參數由誰傳進去？

✓ service 加上 @Injectable()、在 module 的 providers 註冊，容器會讀建構子參數的 metadata，找到對應的 provider 建好再傳進去（第 24 課的迷你 DI 就是這個機制）。a 讓 controller 綁死具體的實作，測試時換不掉。b 錯在 TypeScript 只檢查型別、不會產生建立物件的程式；clock、nextId 這種不是 class 的依賴，要用 token 註冊（NestJS 課第 3 課）。

練習 10：步驟 7 把錯誤轉成狀態碼。在 NestJS 裡對應的做法是什麼？

✓ 狀態碼是 HTTP 的語言，快取、監控、重試、前端的錯誤處理都看它。b 讓監控看到的全是成功，錯誤率永遠是 0。c 錯在 NestJS 內建的 exception filter 只認得 HttpException；不認得的錯誤一律回 500 Internal server error。要嘛改丟 ConflictException，要嘛寫 exception filter 把自己的錯誤對應到狀態碼（NestJS 課第 8 課）。

交付前，要逐項確認什麼？

模組寫完、測試通過，還不等於可以上線：王小明的請求順利跑完，不代表別人送來的請求也會。資深工程師交付前會拿一張上線前檢查清單逐項確認。清單上每一項都是過去有人出過事才加上去的，這課的七個步驟幾乎每一步都對應其中一項。它有兩種用法：交付自己的程式前逐項問自己，review 別人的程式時逐項問對方。

想再挑戰：把模組往正式環境再推一步

下面每一題都針對這課模組的一個限制，做完會更接近 NestJS 課的寫法。

  • 加上 listOrders({ page, size })，回傳 Paginated<OrderResponse>（第 19 課）。size 也要驗證上限，不然有人一次要一百萬筆。
  • 用 zod 改寫步驟 2，比較兩者的錯誤訊息和程式長度（第 26 課）。
  • 把步驟 5 的轉換寫進 SQL：UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'pending'，影響 0 列時再查一次，分辨是找不到還是狀態不對（PostgreSQL 課第 19 課）。
  • 讓 OrderService 的方法改成 async、repository 改成回傳 Promise，看看步驟 4 的「先檢查再修改」在 await 之間會出什麼問題。

常見錯誤

  • 輸入型別和資料型別共用一個：輸入沒有 id、狀態、單價，輸出有。共用的話，客人可以自己送 unitPrice。用 Pick、Omit 從同一個來源推出不同的型別。
  • 狀態用 string：拼錯字（'payed'）編譯會過，switch 也沒辦法檢查有沒有漏。用字面值的聯合型別。
  • 錯誤只有字串訊息：呼叫者只能比對文字來分辨，改一個字就壞。用可辨識聯合，每種錯誤帶自己的資料。
  • 記憶體版 repository 直接存取參考：改了拿出來的物件就等於存好了，忘了 save 的 bug 測試抓不到，換成資料庫才壞。存進去、拿出來都用 structuredClone 複製。
  • 邊檢查邊修改：後面失敗時前面已經改了，資料只改了一半。先全部檢查，全部通過才修改；用資料庫時放進同一個交易。
  • 回應直接送出整個資料物件：型別的 Pick 不會刪欄位，內部欄位會跟著出去。用白名單組新物件。
  • 結帳沒有去重與逾時：網路慢時重按一次就是兩筆訂單；付款閘道沒回應，請求就一直卡著。去重、取消、逾時要一起設計。
  • 以為 single-flight 的每個呼叫者都能取消：共用的工作只看第一個呼叫者的 signal，後來的人取消，只是自己不等了。要不要「所有人都取消才停」是要明講的設計決定。

補充與查表

主線用不到、但在別的環境寫程式時會遇到的細節，查表用，不用背。

  • NestJS 用 schema 驗證：NestJS 12 起，@Body()、@Param() 等裝飾器可以帶 schema 選項，搭配內建的 StandardSchemaValidationPipe 驗證，zod、Valibot 這類支援 Standard Schema 的函式庫都能用；原本的 class-validator 寫法仍然完整支援。

小結

  • 先讀需求，名詞變型別；規則依「只看輸入就能判斷」或「要查資料才知道」決定放在輸入驗證或業務邏輯。
  • 分層：handler 認得 HTTP，service 放業務規則，repository 管儲存；依賴從建構子傳進來，測試時換成假的。
  • 層與層之間用 Result 回報失敗：預期中的失敗放進回傳值，bug 與基礎設施故障才 throw。
  • 型別是層與層之間的約定：品牌 ID、字面值聯合的狀態、可辨識聯合的錯誤、從資料型別推出的輸入型別。
  • 外部輸入用 unknown 接、parse 之後才信任；一次列出所有問題，只留下認得的欄位。
  • 記憶體版 repository 存取都用複本，行為才跟資料庫一致。
  • 多步驟修改先全部檢查再改；取消先轉換狀態、成功才加回庫存；金額用整數、整張最後捨入一次；明細記下當下的單價。
  • 非同步要處理重複送出、取消、逾時；跨伺服器的去重要靠冪等鍵與資料庫。
  • 對外用 switch＋assertNever 對應狀態碼，回應用白名單挑欄位。
  • 到了 NestJS，型別照搬，呼叫交給框架；交付前用上線前檢查清單逐項確認。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 11：外送平台的 webhook 這樣接：const order = (await req.json()) as DeliveryOrder。上線一週後，service 深處偶爾報 Cannot read properties of undefined (reading 'quantity')。最該先改哪裡？

✓ as 編譯後就消失，對方送了缺欄位的資料，要等到深處用到才炸，離來源很遠。在進來的地方 parse 一次，錯誤帶路徑（例如 items[0].quantity），馬上知道是對方格式變了。a 只是把錯誤藏起來，缺數量的訂單照樣流進訂單表。（第 26 課）

練習 12：下單的 handler 這樣寫，parseCreateOrderInput 驗證失敗會丟 ValidationError。哪裡會出事？

const input = parseCreateOrderInput(req.body)
const order = { ...req.body, id: nextId(), status: 'pending' }
repo.save(order)

✓ parse 回傳的是只含認得欄位的新物件，不會改動輸入；之後要用的是它的回傳值。展開 req.body 等於把未知欄位一起寫進資料庫，這就是大量指派。c 錯在 parse 不改輸入，req.body 還是客人送來的原樣。b 剛好相反：後寫的屬性蓋掉前面的，'pending' 會贏。（第 26 課）

練習 13：placeOrder 回傳 Result<Order, OrderError>，handler 用 if (!r.ok) return toHttpResponse(r) 處理失敗。優惠碼過期時，客人會收到什麼？

function placeOrder(input: CreateOrderInput): Result<Order, OrderError> {
  if (coupon.expiresAt < now()) throw new CouponExpiredError()
  if (stock < quantity) return err({ type: 'out_of_stock', productId, available: stock })
  // …
}

✓ 同一個函式有的失敗 throw、有的回傳 err，呼叫者只處理了一種，另一種一路往上變成 500。優惠碼過期是預期中的業務失敗，該加進 OrderError（例如 coupon_expired），讓前端依代碼顯示提示。b 錯在 toHttpResponse 只收得到回傳值，丟出去的例外根本沒經過它。（第 27 課）

練習 14：OrderId 是品牌型別，toOrderId 是會檢查正整數的 smart constructor。路由 handler 卻這樣寫，請求 /orders/abc 會怎樣？

const order = findOrder(Number(req.params.id) as OrderId)

✓ as 繞過了 smart constructor，品牌保證的「驗證過」就不成立。改成 toOrderId(req.params.id)，不合法就回 400；as 只出現在 smart constructor 裡。a 錯在 as 可以把 number 轉成比它窄的型別，編譯器不會擋，這正是它危險的地方。（第 27 課）

練習 15：客人在 App 按「取消」的同一刻，金流的 webhook 通知付款成功。兩個請求都讀到 pending，也都通過 canTransition。哪一層擋得住這種情況？

✓ 兩個請求在記憶體裡各自檢查都會通過，只有資料庫在寫入的那一刻能再確認一次，後到的那個影響 0 列就知道狀態已經變了。b 錯在再查一次還是在寫入之前，兩個請求之間的空隙沒有消失。d 擋不住 webhook，API 也可以被直接呼叫。（第 27 課）

練習 16：placeOrder 庫存不足時回傳 err('庫存不足')。前端要顯示「拿鐵只剩 2 杯」，handler 要依錯誤種類回 404 或 409，錯誤該怎麼表示？

✓ 每種錯誤帶自己的資料（剩幾杯），handler 用 switch 依 type 對應狀態碼，default 交給 assertNever，新增種類時編譯器會提醒。字串只能比對，改一個字就壞，也帶不了資料。b 錯在代碼解決了比對，前端還是不知道剩幾杯。（第 27 課）

練習 17：下單時這樣扣庫存（商品都已確認存在）。哪裡會出事？

for (const item of input.items) {
  const p = repo.findById(item.productId)!
  if (p.stock < item.quantity) {
    return err({ type: 'out_of_stock', productId: p.id, available: p.stock })
  }
  repo.save({ ...p, stock: p.stock - item.quantity })
}

✓ 邊檢查邊修改，後面失敗時前面已經改了，資料只改了一半。先用一個迴圈全部檢查，都通過才用第二個迴圈扣庫存；換成資料庫時放進同一個交易。a 錯在這裡有呼叫 save，新物件會存回去，扣是扣到了，問題是扣得太早。（第 28 課）

練習 18：結帳用記憶體裡的 Map 做 single-flight，本機測試重按兩次只會建立一筆訂單。部署到三台伺服器後，偶爾還是出現重複訂單，最可能的原因是什麼？

✓ Map 只存在一個程序的記憶體裡，換一台伺服器、或伺服器重啟，就擋不住重複送出。跨伺服器要用冪等鍵：前端每次結帳帶一個唯一的鍵，存進資料庫的 UNIQUE 欄位，同一個鍵第二次進來就回傳第一次的結果。a 錯在保留再久也只在那一台有效。（第 28 課）
