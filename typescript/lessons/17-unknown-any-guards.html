階段 3：型別基礎 · 第 17 課

unknown、any 與型別守衛

咖啡店前台上週出了一個怪問題：顧客點兩杯拿鐵，結帳畫面的合計顯示「0110110 元」。追下去發現，後端改版時把商品的 price 從數字 110 改成了字串 "110"，前台用 + 加總，0 + "110" 變成字串串接。前台明明有 type Product = { id: number; name: string; price: number }，tsc 卻沒有報任何錯，因為抓菜單的程式是這樣寫的：const menu = JSON.parse(text)。

問題的根源是：型別只在編譯時存在。API 回來的 JSON、使用者填的表單、localStorage 讀出來的字串，執行時長什麼樣子，TypeScript 在編譯時看不到。程式裡「外面的資料第一次進來」的那個位置，叫做信任邊界（trust boundary）：邊界外的資料什麼都可能是，邊界內的程式卻照著型別在用它。這一課的任務，是把咖啡店前台的每一道門守好：菜單 JSON、點餐表單的數量、改訂單狀態的 request body、出錯時 catch 拿到的錯誤。做到「資料不對，在進門那一刻就被擋下，錯誤訊息指向原因」，而不是等合計顯示錯了才發現。

這課的路線：
  1. tsc 為什麼沒擋下來：JSON.parse 回傳 any，any 關掉檢查而且會擴散。最小答案：在邊界改用 unknown 接，檢查過才用。
  2. 換成 unknown 之後怎麼用：用 typeof、in、Array.isArray 一步一步確認它是商品、是菜單陣列。
  3. 菜單、購物車、訂單頁都要檢查商品：把檢查包成型別守衛 isProduct，以及守衛寫太鬆會怎樣。
  4. 改訂單狀態的 request body 不合就該停：斷言函式 assertOrderStatus。點餐表單的數量也屬於「不合就停」這一類，實作在練習 1 完成。
  5. catch 裡的 e 為什麼也是 unknown，怎麼安全取出錯誤訊息。
  6. as 和 ! 看起來更快：它們做了什麼、沒做什麼，什麼時候是在對編譯器說謊。
這課會用到：
  • 第 16 課的型別縮小：經過 typeof、in、instanceof、Array.isArray 這些檢查後，TypeScript 會在那個分支裡算出更小的型別。
  • 第 13 課的型別擦除：型別只給編譯器看，編譯成 JavaScript 後完全消失，執行時不做任何檢查。
  • 第 4 課的 throw：JavaScript 可以丟任何值，不一定是 Error。

tsc 為什麼沒擋下來？any 關掉檢查，而且會擴散

先重現開場的事故。JSON.parse 的回傳型別是 any。any 的意思是「這個值不用檢查」：對 any 做什麼都不報錯，讀不存在的屬性、當函式呼叫、跟數字相乘都可以。下面三行都對著 any 操作，執行前先找找看有沒有紅線：

三行都沒有紅線，執行結果卻是：

  • price 是 undefined：屬性名稱拼錯了，any 照樣放行。
  • total 是 220：碰巧算對，因為 * 會把字串 "110" 轉成數字。換成 + 就變成字串串接，也就是開場的「0110110」。
  • label 是正常的字串：這次 name 剛好真的是字串，所以沒出事。

第二件事更麻煩：any 會擴散。any 的屬性是 any，呼叫 any 的方法得到的也是 any，指定給沒有標註型別的變數，那個變數也變成 any。滑鼠移到 price、total、label 上看看，全都是 any。開場的菜單也是這樣：menu 是 any，menu[0] 是 any，menu[0].price 還是 any，一路流到計算合計的函式，沿路沒有任何一個地方會被檢查。編譯器閉嘴了，錯誤沒有消失，只是延到執行時，而且出現在計算合計的地方，離真正的原因（API 回應變了）很遠。

所以第一步是知道 any 從哪裡進來。很多 any 不是你自己寫的，而是這些來源給的：

來源型別
JSON.parse(text)any
await res.json()（fetch 的 Response）Promise<any>
沒有型別宣告的套件匯入的東西全是 any
Array.isArray(x)，x 是 unknown縮小成 any[]，元素是 any（下一節會遇到）
catch (e: any)、參數寫 any自己開的洞

前兩個正好是信任邊界：資料從外面進來的地方。這裡要換一個型別來接，那就是 unknown。unknown 的意思是「有一個值，但還不知道它是什麼」。它跟 any 一樣接得住任何值，any 也可以直接指定給它，差別在使用的時候：any 什麼都放行，unknown 在你檢查之前幾乎什麼都不准做。所以開場問題的最小答案是：在邊界立刻把 any 換成 unknown，例如 const data: unknown = JSON.parse(text)。這樣 any 停在這一行，不會再往下擴散，之後要用，就得先證明它是什麼。

但 unknown 什麼都不准做，菜單資料要怎麼拿來用？下一節就是「證明它是什麼」的過程。

💡 實務上：接手專案時，先看 any 藏在哪裡
舊專案從 JavaScript 搬到 TypeScript 時，常見的過渡做法是先到處寫 any 讓它編譯過，之後就沒人回頭收。接手時可以先搜尋 any、as any，看它們集中在 API 呼叫、第三方套件還是共用工具函式；集中在 API 呼叫的，就是開場這類事故的候選位置。不必一次全改：新寫的程式不再加 any，改到哪裡就把那裡的邊界換成 unknown。團隊通常也會用 ESLint 擋新的 any。ESLint 是檢查程式碼寫法的工具，typescript-eslint 的 no-explicit-any 規則會把明寫的 any 標出來；code review 看到新的 any 就會問「資料從哪來、為什麼不能檢查」。

換成 unknown 之後，怎麼一步一步確認它是商品？

上一節把菜單改成用 unknown 接，代價是現在連 data.name 都讀不了：對 unknown 讀屬性、呼叫、運算，都會報 TS18046（「'data' is of type 'unknown'」）。要用它，就要用第 16 課的縮小一層一層排除可能性，每通過一個檢查，TypeScript 就在那個分支裡把型別算得更小。下面先處理一個商品，注意每一層的 if 各排除了什麼：

從外到內，每一步都在回答一個問題：

  1. typeof data === 'object'：它是物件嗎？這排除了字串、數字、布林這些不可能有 price 的值。
  2. data !== null：typeof null 也是 'object'（第 16 課的陷阱），這一步把 null 排除。到這裡 TypeScript 才知道它是「某個物件」，但還不知道有哪些屬性。
  3. 'price' in data：它有 price 這個屬性嗎？通過 in 之後，TypeScript 會替 data 補上一個型別為 unknown 的 price 屬性，所以能讀 data.price，但值還沒驗證（版本細節見課末「補充與查表」）。
  4. typeof p === 'number'：price 是數字嗎？第 3 步只證明了「有這個屬性」，沒證明屬性的型別，所以 data.price 讀出來是 unknown，還要再檢查一次。開場的事故就卡在這一步：後端給的 price 是字串，這個檢查會讓它走不進去。

開場的菜單不是一個商品，而是一串商品，所以還要確認「它是陣列」。這裡有一個陷阱：Array.isArray 會把 unknown 縮小成 any[]，好不容易擋在門外的 any 又跑回來了。

通過 Array.isArray 只證明了「它是陣列」，裡面的元素一個都還沒檢查，型別卻是 any，所以 data.reduce((a, b) => a + b, 0) 沒有任何紅線，結果卻是字串串接，跟開場的合計同一種錯。修法是確認是陣列之後，立刻改回 unknown[]：const items: unknown[] = data。這樣每個元素又回到「用之前要先檢查」的狀態。最後一行的 filter 留下數字，滑鼠移上去會看到 number[]，這是怎麼來的，下一節講完型別守衛就能解釋。

到這裡，unknown 可以安全地用了，但寫法有個問題：檢查一個商品就要四層 if，而菜單頁、購物車、訂單明細都要檢查商品。每個地方各寫一次，遲早有一處漏掉 price 的檢查。下一節把這套檢查包成函式。

菜單、購物車都要檢查商品：怎麼包成型別守衛？

直覺的做法是寫一個 isProduct(x: unknown): boolean，裡面放上一節的檢查，呼叫端寫 if (isProduct(data))。但這樣行不通：回傳型別寫成 boolean 時，TypeScript 只知道「函式回傳了 true 或 false」，不知道 true 代表什麼，所以 if 裡的 data 還是 unknown，照樣讀不了 data.name。縮小只會發生在 TypeScript 看得懂的檢查上，而函式內部的檢查，呼叫端看不到。

解法是在回傳型別上把「true 代表什麼」寫出來：寫成 x is Product，意思是「這個函式回傳 true 時，參數 x 就是 Product」。這種回傳型別叫型別謂詞（type predicate），回傳型別謂詞的函式叫自訂型別守衛（user-defined type guard）。呼叫端的 if 看到守衛回傳 true，就把 x 縮小成 Product。

函式內容就是上一節那幾層檢查，改寫成提早 return false 的形式，最後把三個欄位都確認過。呼叫端的 if (isProduct(data)) 裡，data.name、data.price * 2 都能用，而且 price 確定是數字。

但有一件事要特別小心：TypeScript 完全相信你的守衛。它不會比對函式內容跟 x is Product 對不對得上，你宣稱 true 代表 Product，它就照單全收。守衛寫得太鬆，等於對編譯器說謊。下面這個守衛只檢查了 name，拿開場那份 price 是字串的資料來試：

守衛回傳 true，data 被縮小成 Product，data.price.toFixed(0) 沒有紅線，執行時卻丟出 TypeError，因為字串沒有 toFixed。注意錯誤出在哪裡：不是在守衛裡，而是在拿到「Product」、照著型別使用它的程式碼裡。換到真實專案，就是某個畫面元件在算金額時當掉，而原因藏在另一個檔案的守衛。所以守衛要檢查每一個會用到的欄位，型別也要檢查，不能只確認欄位存在。練習 2 會要求更嚴格的版本：price 還要排除 NaN、Infinity。

現在可以回答上一節留下的問題：items.filter(x => typeof x === 'number') 為什麼得到 number[]？filter 的型別定義有一個版本是：傳進去的 callback 如果是型別守衛 x is S，結果就是 S[]。而 x => typeof x === 'number' 這種簡單的箭頭函式，TypeScript 會自己推論出 x is number，不用你寫。推論有條件，有些看起來類似的寫法不會推論，細節和版本見課末「補充與查表」。

守衛回傳 true／false，讓呼叫端自己決定兩條路怎麼走，適合「不合也是正常情況」的地方，例如從菜單裡挑出格式正確的商品。但有些地方不合就不該繼續，例如後台送來的訂單狀態拼錯了，程式沒有「另一條路」可以走。下一節處理這種情況。

不合就該停下來：斷言函式怎麼寫？

咖啡店後台有一個「改訂單狀態」的 API，request body 裡帶著新的狀態，例如 'paid'。這個值從外面進來，所以是 unknown。如果它不是四種狀態之一（例如有人拼成 'payed'），正確的反應是直接丟錯、回 400，而不是寫進資料庫。用守衛的話要這樣寫：if (!isOrderStatus(body)) throw …，每個 API 都要重複這兩行。

斷言函式（assertion function）把「檢查」和「不合就丟錯」合在一起：回傳型別寫成 asserts x is T，意思是「這個函式如果正常結束（沒有丟錯），x 就是 T」。呼叫它只要單獨一行，下一行開始 x 就被縮小了。

assertOrderStatus(input) 之後，input 可以直接指定給 OrderStatus；傳 'payed' 則丟出 RangeError，錯誤訊息直接寫出收到的值，看 log 就知道哪裡錯。斷言函式跟型別守衛一樣，TypeScript 完全相信它：只要沒丟錯，就當成 OrderStatus，所以函式裡的檢查一樣要確實。

函式裡用 ORDER_STATUSES.some(s => s === x) 判斷，為什麼不用更直覺的 ORDER_STATUSES.includes(x)？因為 includes 的參數型別是陣列元素的型別，也就是 OrderStatus；把 unknown 傳進去會報 TS2345，等於要你先證明 x 是 OrderStatus，才准你檢查它是不是 OrderStatus。=== 可以比較任何兩個值，所以 some(s => s === x) 沒有這個問題。另一種寫法會用到 as，最後一節再看。

斷言函式還有一個寫法上的限制，練習 3 會遇到：寫成箭頭函式時，變數要明確標註型別，不然呼叫的地方會報 TS2775。用 function 宣告就沒有這個問題。原因在呼叫端：TypeScript 做控制流程分析時，必須不靠型別推論就直接知道「這一行呼叫是斷言」，才能決定之後的程式碼裡 x 是什麼型別，所以被呼叫的名字要有明確寫出的型別。const assertA = (…) => … 的型別是從右邊推論來的，不算明確；function 宣告本身的簽章就是寫出來的型別，所以沒有這個問題。

// ✗ 呼叫時報 TS2775：Assertions require every name in the call target
//   to be declared with an explicit type annotation
const assertA = (x: unknown): asserts x is OrderStatus => { … }

// ✓ 用 function 宣告，或替變數標註型別
type AssertStatus = (x: unknown) => asserts x is OrderStatus
const assertB: AssertStatus = (x) => { … }

守衛和斷言函式做的是同一件事，差別在不合時怎麼辦。依「不合是不是正常情況」來選：

型別守衛 x is T斷言函式 asserts x is T
不合時回傳 false丟錯
呼叫端寫在 if 裡，自己決定兩條路單獨一行，之後直接用
適合不合也是正常情況：篩選、依型別走不同處理不合就是錯誤：設定檔、API 參數、不該發生的狀態

開場提到的點餐表單數量也是同一類。表單送來的值同樣是外部資料，該用 unknown 接：可能是數字 3，也可能是字串 '3'，甚至是空字串或 'abc'。數量不合不是「換條路處理」的正常情況，而是請求本身有錯，所以跟 request body 的狀態一樣，不合就丟 RangeError，讓錯誤停在進門的地方。差別是它不只要檢查，還要把合格的字串轉成數字，所以寫成回傳 number 的 parseQuantity，而不是斷言函式。實作留給練習 1。

到這裡，菜單 JSON、表單數量和 request body 這三道門都有了檢查（表單數量在練習 1 寫）。還有一道門是 TypeScript 自己替你標成 unknown 的：catch 拿到的錯誤。斷言函式丟出的 RangeError，最後也會被某個 catch 接住，下一節看它該怎麼處理。

💡 實務上：檢查集中在資料進來的那一層
以咖啡店前台為例，抓菜單、抓訂單的程式通常集中在一個 API 模組（例如 api/orders.ts）：它拿到 unknown，用守衛檢查後才回傳 Order[]，畫面元件只拿到已經檢查過的資料，不用每個元件各自再檢查一次。開場的事故如果有這一層，錯誤會在 API 模組裡、帶著「price 不是數字」的訊息出現，而不是在合計欄。斷言函式常用在程式啟動時讀環境變數或設定檔，少了必要的值就直接丟錯，比上線後某個按鈕才壞掉好查。反過來，已經有型別的內部資料不要再包一層守衛，檢查只放在信任邊界。後端不合規格時，要整批丟錯、略過壞掉的那筆，還是顯示「資料異常」，通常要跟 PM 和後端一起講好。

catch 拿到的錯誤，為什麼也是 unknown？

上一節的斷言函式丟出 RangeError，但 catch 接到的不一定是 Error。第 4 課說過，JavaScript 可以 throw 任何值：Error、字串、數字，甚至 null。你自己的程式可以約定只丟 Error，但你管不了別人的套件。TypeScript 沒辦法知道 try 裡面呼叫的每一層會丟出什麼，所以在 strict 模式下，catch (e) 的 e 型別是 unknown。這跟 JSON.parse 的情況一樣，是一道信任邊界，只是這次 TypeScript 主動幫你用 unknown 接。

下面模擬一個刷卡模組丟出字串，而不是 Error：

第一個 console.log(e.message) 有紅線（TS18046），而且紅線是對的：e 是字串，字串沒有 message，執行時印出 undefined。第二種寫法先用 e instanceof Error 縮小：是 Error 就讀 message，不是就用 String(e) 轉成字串，不管丟出來的是什麼都能得到一段文字。

常見的偷懶寫法是 catch (e: any)：紅線消失了，問題卻還在。e.message 遇到字串是 undefined，遇到 null 則直接丟 TypeError，錯誤處理本身又丟出新的錯誤，原本的錯誤反而被蓋掉。每個 catch 都寫一次 instanceof 判斷又太囉嗦，實務上會把「從 unknown 取出訊息」寫成一個函式，整個專案共用，練習 4 就是寫這個函式，再用它修好菜單載入的 catch。

到這裡，每一道門用的都是「先檢查，再使用」。但很多專案裡你會看到更短的寫法：JSON.parse(text) as Product[]，一行就有型別，不用寫守衛。下一節看它到底做了什麼。

💡 實務上：給使用者看的訊息和給工程師看的錯誤要分開
結帳失敗時，畫面上給客人的是「付款沒有成功，請再試一次」這類固定文案，不是直接把 e.message 丟出去，裡面可能是英文、錯誤堆疊或內部細節。原始的錯誤值（不管是不是 Error）應該完整送進 log 或錯誤監控服務，客服回報時工程師才查得到原因。所以專案裡常見一個共用的取訊息函式，再加上一層「錯誤 → 使用者文案」的對應。資深工程師在 review 時會特別看 catch：有沒有把錯誤吞掉、有沒有記錄下來、使用者有沒有得到下一步該做什麼的提示。

as 和 ! 一行就有型別：什麼時候是在說謊？

上一節最後提到的 as 叫型別斷言（type assertion）：x as Product 是告訴編譯器「相信我，它是 Product」。另一個類似的寫法是非空斷言（non-null assertion）x!，意思是「相信我，它不是 null 或 undefined」，第 13 課用它讓錯誤閉嘴過。兩個名字裡都有「斷言」，但跟前面的斷言函式完全不同：斷言函式在執行時真的會檢查、不合就丟錯；as 和 ! 只存在於型別裡，編譯後完全消失，執行時什麼都不檢查。看編譯前後的對照就清楚了：

// TypeScript                                   // 編譯後的 JavaScript
const p = JSON.parse(text) as Product           const p = JSON.parse(text)
const item = menu.find(m => m.id === 9)!        const item = menu.find(m => m.id === 9)

右邊的 JavaScript 裡，as 和 ! 不見了，剩下的程式跟沒寫一樣。所以開場的菜單如果寫成 JSON.parse(text) as Product[]，事故照樣發生：型別說 price 是 number，執行時它是字串，沒有任何東西在中間檢查。下面兩行各示範一種：

第一段的 API 資料少了 price，as Product 讓編譯器以為它有，fromApi.price * 2 得到 NaN。第二段的 find 找不到 id 9，回傳 undefined，! 讓編譯器以為不會是 undefined，讀 item.name 時丟出 TypeError。兩個錯誤都沒有消失，只是從編譯時延後到執行時。

as 也不是什麼都放行。它只允許「有可能成立」的轉換，兩個型別完全不相關時，例如 '拿鐵' as number，會報 TS2352。判斷安不安全，看轉換的方向：

  • 往寬的方向轉（upcast）：例如把 'paid' 當成 string。'paid' 本來就是字串，這句話一定成立，永遠安全。
  • 往窄的方向轉：例如把 unknown 當成 Product。這是在對編譯器保證一件它沒辦法查證的事，保證錯了，代價在執行時才付。

有人想強迫轉成任何型別時，會寫 x as unknown as Product，這叫雙重斷言：先轉成 unknown（往寬，一定可以），再從 unknown 轉成任何東西，TS2352 就擋不住了。看到這種寫法要警覺，它通常代表型別設計有問題，或有人在繞過檢查。

那什麼時候用 as 合理？

  • 測試裡的假資料：只需要物件的一部分，{ id: 1 } as Product，騙的是自己的測試，範圍很小。
  • 往寬的方向轉：斷言函式那一節 includes 的另一種解法就是這種。先確認 typeof x === 'string'，再把 readonly OrderStatus[] 放寬成 readonly string[]：(ORDER_STATUSES as readonly string[]).includes(x)，這時參數型別是 string，傳 x 就不會報錯。
  • 你確實比編譯器知道得多，而且這件事剛剛在附近檢查過。這時通常改寫成守衛更好，因為守衛把檢查和型別綁在一起。

不合理的：API 資料寫 as Product、用 ! 消掉 find 的 undefined。前者用守衛或斷言函式在邊界檢查；後者用 if 或 ?? 處理找不到的情況。

回到開場的任務：菜單 JSON 用 unknown 接、用 isProduct 檢查每一筆；點餐表單的數量從 unknown 轉成 1～99 的整數；request body 的狀態用 assertOrderStatus 擋下拼錯的值；catch 的 e 用共用函式取訊息。做到這些，後端再把 price 改成字串，錯誤會在 API 模組裡出現，而不是在合計欄。商品只有三、四個欄位時手寫守衛還應付得來；欄位多、巢狀深的資料，第 26 課會用 zod 這類驗證套件，從同一份定義同時得到型別和執行時的檢查。下面的練習依序把這幾道門寫出來。

練習

練習 1：寫 parseQuantity(input: unknown): number，用在點餐表單的「數量」欄。接受 1～99 的整數，或內容剛好是 1～99 整數的字串（例如 '3'，不能有空白、正負號、小數點、指數 e 或其他字元）；其他一律丟 RangeError。參數型別保持 unknown，不能改成 any。提示：Number(' 3')、Number('1e1') 都會成功轉換，字串要先用第 6 課的正規表示式確認格式。

練習 2：寫型別守衛 isProduct(x: unknown): x is Product。Product 已經定義好了。每個欄位都要檢查：id 是數字、name 是字串、price 是有限的數字（NaN、Infinity 不算）、category 是字串或 null（欄位一定要存在）。任何輸入都只能回傳 true／false，不能丟錯。

練習 3：寫 ORDER_STATUSES（四種訂單狀態的唯讀陣列）和斷言函式 assertOrderStatus(x: unknown)：x 不是四種狀態之一就丟 RangeError；呼叫之後，呼叫端的 x 要被縮小成 OrderStatus。

練習 4：寫 errorMessage(e: unknown): string：Error（包括子類別）回傳它的 message；字串回傳字串本身；有字串 message 屬性的物件回傳那個 message；其他一律回傳 '未知錯誤'。再修好 loadMenu 裡 catch 直接讀 e.message 的地方，改用 errorMessage。

練習 5：const p = JSON.parse(text) as Product。text 的內容是 {"name": "拿鐵"}（少了 id 和 price）時，會發生什麼事？

✓ as 編譯後完全消失，執行時沒有任何檢查；編譯時 TypeScript 也看不到 text 的內容（JSON.parse 回傳 any）。錯誤會在之後用到 p.price 的地方才出現。要檢查就用型別守衛或斷言函式。

練習 6：x 宣告成哪一個型別時，x.foo.bar() 不會有型別錯誤？

✓ any 關掉檢查，什麼操作都放行，而且 x.foo、x.foo.bar() 也都是 any。unknown 在檢查之前不能讀屬性，會報 TS18046。兩者都能接住任何值，差別在用之前要不要檢查。

練習 7：const isProduct = (x: any): x is Product => 'name' in x 有什麼問題？

✓ TypeScript 不驗證型別守衛的內容，回傳 true 就當成 Product。這個守衛太鬆，又用 any 讓 'name' in x 對 null、字串也能編譯，執行時 'name' in null 會丟 TypeError。TS2775 是斷言函式（asserts）的規則，型別守衛寫成箭頭函式沒有問題。

常見錯誤

  • 讓 any 從邊界一路流進程式：JSON.parse、res.json() 的結果直接拿來用，any 會擴散，錯誤在很遠的地方出現（開場的合計欄）。拿到就指定給 unknown，檢查過再用。
  • 用 as 處理 API 資料：data as Product 編譯後消失，執行時什麼都不檢查，只是把 any 換了個名字。用型別守衛、斷言函式，或第 26 課的驗證套件。
  • 用 ! 讓「可能是 undefined」閉嘴：錯誤沒有消失，只是延後到執行時。用 if、?? 處理找不到的情況。
  • 型別守衛只檢查一個欄位：TypeScript 完全相信守衛，用到的每個欄位都要檢查型別，數字還要排除 NaN。
  • catch (e: any)：throw 可以丟任何值，e.message 遇到字串是 undefined、遇到 null 會當掉。保持 unknown，用共用的 errorMessage 取出訊息。
  • 用箭頭函式寫斷言函式卻沒標註型別：呼叫時報 TS2775。改用 function 宣告，或替變數寫上函式型別。
  • 以為 Array.isArray 之後元素已經檢查過：得到的是 any[]，每個元素都還沒驗證。改成 unknown[] 再逐一檢查。

補充與查表

in 之後讀到的屬性為什麼是 unknown

TypeScript 4.9 起，'price' in data 會把型別裡沒列出的 price 屬性加成 unknown，所以通過 in 之後就能讀 data.price，但值的型別還要再檢查。

自動推論型別謂詞的版本與限制

TypeScript 5.5 起，簡單的箭頭函式不用自己寫 x is T：items.filter(x => typeof x === 'number') 得到 number[]，[p1, undefined, p2].filter(p => p !== undefined) 會直接推論成 Product[]。舊版只會得到原本的元素型別（例如 unknown[]）。

推論有限制：filter(x => !!x) 在元素是 number | undefined 時不會推論。型別謂詞的意思是「true 時是 number，false 時不是 number」，但回傳 false 時 x 也可能是 0，後半句不成立，所以 TypeScript 不推論。

catch 變數是 unknown 的設定

catch 的 e 是 unknown，是 useUnknownInCatchVariables 的作用。這個選項在 TypeScript 4.4 加入，屬於 strict 的一部分，開了 strict 就會開啟。

小結

  • 信任邊界是外部資料第一次進入程式的地方。any 關掉檢查而且會擴散，事故會出現在離原因很遠的地方；unknown 接得住任何值，但用之前要先檢查。
  • 在邊界立刻換成 unknown，再用 typeof、!== null、in 一步一步縮小。Array.isArray 會縮小成 any[]，要立刻改回 unknown[]。
  • 型別守衛 x is T 回傳 boolean，讓呼叫端分支；斷言函式 asserts x is T 不合就丟錯，呼叫之後直接用。兩者 TypeScript 都完全相信，檢查寫太鬆就是說謊。
  • strict 下 catch 的 e 是 unknown；用 e instanceof Error 取訊息，或寫成共用的 errorMessage。
  • as 和 ! 編譯後消失，執行時不檢查。往寬的方向轉安全，往窄的方向轉是在對編譯器保證它查不了的事；as unknown as X 是警訊。
  • filter(p => p !== undefined) 這類簡單的 callback，TypeScript 會自動推論型別謂詞（版本與限制見補充與查表）。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：咖啡店後台的部署流程只跑 vite build。某個 PR 合併後，main 上其實有一個 TS2322，網站卻照常建置、上線。為什麼沒被擋下？

✓ 檢查型別和擦掉型別是兩件獨立的事，Vite 只做後者，有型別錯誤照樣產生 JS。修法是把 vue-tsc（或 tsc --noEmit）放進 CI 和 build 指令，沒過就不能合併。b 錯在 strict 控制的是 noImplicitAny、strictNullChecks 這類額外檢查，值的型別跟目標不符不管有沒有 strict 都會報。（第 13 課）

練習 9：staff 表有 password_hash。下面這段編譯沒有錯誤，上線後哪裡會出事？

type StaffDto = { id: number; name: string }
async function getStaff(id: number): Promise<StaffDto> {
  const row = await findStaffRow(id)  // 整筆：id、name、passwordHash…
  return row
}
// 路由裡：res.json(await getStaff(6))

✓ 結構型別只看形狀：row 有 id、name 就相容，多出的欄位照樣存在；型別在執行時已經擦掉，不會幫你挑欄位。修法是回傳時明確挑 { id: row.id, name: row.name }，或查詢只 SELECT 需要的欄位。c 錯在多餘屬性檢查只抓當場寫的物件字面值，row 是變數，不會被檢查。（第 14 課）

練習 10：「編輯顧客」的 PATCH /customers/6 這樣處理。客服回報：有顧客要求刪掉電話，但怎麼存都刪不掉。問題在哪？

type CustomerPatch = { name?: string; phone?: string | null }
function applyPatch(c: Customer, patch: CustomerPatch) {
  if (patch.phone) c.phone = patch.phone
  if (patch.name) c.name = patch.name
}

✓ 沒傳是 undefined、要清空是 null，兩個都是 falsy，if (patch.phone) 把它們當成同一件事。改成 if (patch.phone !== undefined)，null 才寫得進去。b 錯在沒傳的屬性讀出來是 undefined 不是 null，這正是 ? 和 | null 要分開的原因。（第 14、15 課）

練習 11：新的訂單服務要用 Node 24 直接執行 .ts。訂單狀態（待付款、已付款、完成、取消）的型別怎麼寫最恰當？

✓ 字面值聯合是純型別、可以直接擦掉，打錯的 'payed' 在寫程式時就被擋下；外部寫進來的值再由資料庫的 enum／CHECK 擋。a 錯在 enum 會產生執行時物件，Node 只擦掉型別、不支援它，執行時才報錯；開 erasableSyntaxOnly 會在編譯時報 TS1294。（第 15 課）

練習 12：商品卡片顯示庫存，stock 是 number | null（null 表示沒有庫存資料）。哪裡會出事？

function stockLabel(stock: number | null) {
  if (!stock) return '—'
  if (stock === 0) return '已售完'
  return `剩 ${stock} 杯`
}

✓ 真值檢查擋的是所有 falsy 值，0 也在裡面；TypeScript 不會報錯，因為縮小後的型別都是 number。第一行改成 if (stock === null)。看到數字或字串放進 if、||，先問「0 或空字串是不是合法的值」。b 錯在 !stock 已經同時擋掉 null，問題是擋得太多，不是太少。（第 16 課）

練習 13：訂單列表的標籤這樣寫。PM 要求 OrderStatus 加上 'refunded'，型別改好後跑 tsc，會發生什麼事？

function statusLabel(s: OrderStatus): string {
  switch (s) {
    case 'pending': return '待付款'
    case 'paid': return '已付款'
    case 'done': return '完成'
    case 'cancelled': return '已取消'
    default: return '其他'
  }
}

✓ default 回傳預設值，把新的情況悄悄吞掉了：型別上沒錯、執行時也不丟錯。改成 default: return assertNever(s)，新增狀態時這一行報錯，所有漏掉的地方就是待辦清單。a 錯在 TypeScript 不會要求 switch 寫滿，只有剩下的型別被指派給 never 時才報錯。（第 16 課）

練習 14：訂單資料用 paid、shipped、cancelled 三個布林表示，資料庫裡出現了「已取消又已出貨」的訂單。怎麼改最恰當？

✓ 三個布林能組出 8 種，合理的只有幾種；改成可辨識聯合，不可能的狀態根本寫不出來，檢查標籤就縮小到其中一種。a 錯在檢查散在各處，漏掉一個寫入路徑就又出現壞資料，型別本身還是允許它。（第 16 課）

練習 15：api/orders.ts 寫 return (await res.json()) as Order[]。後端把 total 改名成 amount，前端沒跟著改。錯誤會在哪裡出現？

✓ res.json() 回傳 any，as 編譯後消失，執行時沒人檢查，錯誤在離來源很遠的地方才出現。修法是在信任邊界把資料當成 unknown，用型別守衛或斷言函式檢查過再回傳 Order[]，畫面元件拿到的就是驗證過的資料。a 錯在 TypeScript 編譯時看不到 API 實際回了什麼，any 轉成什麼都不會報錯。（第 13、17 課）
