階段 1：JavaScript 的核心機制 · 第 4 課

錯誤處理：throw、Error 與 cause

王小明在咖啡店的 App 下單 3 個可頌，按下結帳。後端收到這個請求，要依序做三件事：檢查並扣掉庫存、向金流扣款、寫入訂單。可頌只剩 1 個，第一步就做不下去。這時程式必須停下來，不能繼續扣款和寫訂單；還要讓收到請求的那一層知道「做不到，原因是可頌只剩 1 個」，才能回給 App 一個王小明看得懂的訊息。

這件事寫錯，後端會出現三種很難查的問題：訂單看起來成功、其實沒扣款；log 裡只寫著 Error，不知道是哪裡壞的；或是庫存被扣了一半。這一課從這筆失敗的訂單出發，把下單流程的錯誤處理一步一步寫對：讓流程停得下來、說得清楚原因、查得到根源、不留下做到一半的資料，最後決定錯誤該由哪一層接住。用到的工具是 throw、try／catch／finally、自訂錯誤類別和 cause。

這課的路線：
  1. 庫存不夠時，怎麼讓下單流程停下來；丟出去的應該是什麼：throw 怎麼中斷函式、錯誤怎麼沿著呼叫一路往上找 catch（開場問題的最小答案），為什麼要丟 Error 物件，從 stack trace 看出是哪裡壞的。
  2. 邊界怎麼分辨「庫存不足」和 bug：自訂錯誤類別帶上商品和數量，用 instanceof 分辨，轉成給 App 的回應。
  3. 底層丟上來的錯誤看不懂時：用 cause 包裝成看得懂的錯誤，同時保留原本的原因，記 log 時整條留下來。
  4. 錯誤跳出去之後，做到一半的事怎麼收拾：finally 保證清理一定執行；先檢查、再修改，庫存才不會只扣一半。
  5. 這個錯誤該在哪一層接住：哪些就地補救、哪些包裝再丟、哪些讓它往上，最後在邊界轉成回應。
這課會用到：
  • 第 3 課的 class、extends、instanceof：extends 讓子類別接上父類別的原型，instanceof 沿著原型鏈檢查「是不是這一種」。自訂錯誤就是繼承 Error。

庫存不夠時，怎麼讓下單流程停下來？

先看下單流程的形狀。收到請求的 handleRequest 呼叫 placeOrder；placeOrder 先呼叫 reserveStock 檢查並扣庫存，成功了才扣款、寫入訂單。問題出在最裡面那一層：reserveStock 發現庫存不夠，要怎麼讓整條流程停下來？

一個想法是讓 reserveStock 回傳一個代表失敗的值，例如 false。這行得通，但每一層都要記得檢查：placeOrder 要檢查 reserveStock 的回傳值，handleRequest 要檢查 placeOrder 的回傳值。只要有一層忘了，流程就帶著失敗繼續往下走，扣款照扣、訂單照寫。層數越多，忘記的機會越大。

JavaScript 提供另一條路：例外（exception）。例外是「這件事做不下去了」的訊號，用 throw 丟出。throw 會立刻中斷目前的函式，後面的程式都不執行。中間的每一層不用寫任何檢查，錯誤會自己往外走，直到遇到願意接住它的地方。接住的寫法是 try { … } catch (e) { … }：try 區塊裡任何地方丟出錯誤，包括它呼叫的函式裡面，就跳到 catch，e 是被丟出來的那個值。

「往外走」要說精確，需要一個名詞。函式一層呼叫一層時，執行環境會記下「現在在哪個函式裡、是誰呼叫它的」。它像一疊盤子：呼叫一個函式就疊上一層，函式結束就拿掉最上面那層。這份紀錄叫呼叫堆疊（call stack），第 7 課會再用到它。錯誤丟出來之後，會沿著呼叫堆疊往上，一層一層找最近的 catch，中間每一層還沒執行的程式都被跳過。

如果一路往上都沒有 catch 呢？那就是未捕捉的錯誤（uncaught error）。先認識一個名詞：作業系統裡每一個正在執行的程式叫一個程序（process），你用 node server.js 啟動的伺服器就是一個程序。在 Node 的程式裡，未捕捉的錯誤會讓整個程序結束，伺服器就停了。在練習區則會看到 Uncaught，後面的程式不再執行：

丟出去的應該是什麼？Error 物件與 stack trace

JavaScript 允許 throw 任何值，字串、數字、物件都可以，catch 拿到的就是那個值。所以 throw '庫存不足' 語法上完全合法，流程一樣會停下來。差別要等到出問題、需要查的時候才看得出來。下面同樣的訊息丟兩次，一次丟字串、一次丟 Error，比較兩行印出的內容：

  • name：錯誤的種類，Error 預設是 'Error'。

  • stack：堆疊追蹤，下面馬上講。

丟字串會失去兩樣東西。一是 stack：不知道錯誤是從哪裡丟的。二是種類：下一節會看到，程式要分辨「這是哪一種錯誤」，靠的是錯誤的類別，字串沒有類別可分。所以一律丟 Error 或它的子類別。

💡 實務上：客服回報「結帳壞了」，第一步是找到那一筆 stack trace
上線後你看不到使用者的畫面，能依靠的就是錯誤發生當下留下的訊息與 stack。團隊通常會接一個錯誤追蹤服務（例如 Sentry），前端和後端的未捕捉錯誤都自動送過去，附上時間、網址、哪個使用者。前端的程式上線前會經過打包壓縮，stack 會指向一行看不懂的程式碼；所以部署時要一起上傳 source map，它是一份把壓縮後的位置對回原始碼的對照檔，有了它 stack 才對得回原始檔案。資深工程師收到 bug 回報，會先問「有沒有錯誤紀錄或 stack？什麼時間、哪個帳號？」，而不是先猜。

到這裡，handleRequest 接到的是有 stack 的 Error 物件，出事時查得到是哪一行。但回頭看開場：App 要的不只是「失敗了」，而是「可頌只剩 1 個」；而且庫存不足和 order.total 讀到 undefined 這種 bug，應該回不同的東西給客人。兩者都是 Error，handleRequest 要怎麼分辨？

邊界怎麼分辨「庫存不足」和 bug？自訂錯誤類別

要回答這個問題，先把 handleRequest 的工作說清楚：它要回給 App 什麼，以及它在整個程式裡站在什麼位置。

App 呼叫後端的 API，後端的回應除了內容，還會帶一個三位數的結果代碼，叫 HTTP 狀態碼（status code），讓呼叫的一方不用讀內容就知道結果屬於哪一類。這課先認識四個：400 輸入錯誤、404 找不到、409 跟目前的狀態衝突（例如庫存不足）、500 伺服器自己的 bug。Node 課第 12 課會完整講。庫存不足要回 409，App 才知道該請客人改數量；order.total 讀到 undefined 是我們的 bug，要回 500。

handleRequest 這種位置叫邊界（boundary）：程式和外界交接的地方，例如收到 HTTP 請求的 API handler。邊界以內的函式（placeOrder、reserveStock）只負責在做不下去時丟出有意義的錯誤，不碰 HTTP；到了邊界，才統一決定每種錯誤要回哪個狀態碼、給客人看什麼。這樣分工，reserveStock 之後被排程工作或後台工具呼叫時也能直接用，它不需要知道自己是被誰呼叫的。

所以邊界拿到一個 Error，要判斷它是不是「庫存不足」。直覺的寫法是比對訊息：e.message === '庫存不足'。這個寫法會在某天默默失效：有人把文字改成「庫存不夠」、加上商品名稱、或翻成英文，比對就不成立，所有庫存不足都掉進 500。訊息是給人看的，隨時會改。而且 App 要顯示「可頌只剩 1 個」，需要商品和剩餘數量，從訊息字串裡切出數字更脆弱。程式判斷需要的是一個不會因為改文案而變的東西，還要能帶資料。

做法是寫一個自訂錯誤類別（custom error class）。「庫存不足」是咖啡店的業務規則，不是 JavaScript 內建的錯誤，所以自己定義一種：用第 3 課的 extends Error 繼承 Error，它就有 message 和 stack；在建構子裡設定 name，再把程式要用的資料（哪個商品、要幾個、剩幾個）存成欄位。下面的 toResponse 就是邊界上的轉換：收到錯誤，回傳狀態碼和給客人的訊息。執行後看 name、兩個 instanceof，以及兩種錯誤分別轉成什麼：

結果由上到下：

  • name 是 OutOfStockError，訊息帶著商品和數量。name 要自己設，沒設的話會沿用 Error，log 裡所有錯誤都叫 Error，分不出種類。
  • 兩個 instanceof 都是 true：instanceof 沿著原型鏈檢查（第 3 課），OutOfStockError 的原型接在 Error 上，所以它的實例既是 OutOfStockError 也是 Error。
  • toResponse 對 OutOfStockError 回 409，用 e.available 組出給客人的訊息；TypeError 不是 OutOfStockError，掉到 500，只回「系統錯誤」。

這就是用 instanceof、不比對訊息的理由：類別和欄位是給程式用的，改訊息文字完全不影響判斷；訊息留給人看。開場的需求到這裡都有了：reserveStock 丟 OutOfStockError，流程停下，邊界用 instanceof 認出它，回 409 和剩餘數量。

💡 實務上：API 回給前端的錯誤要有穩定的代碼，不要靠訊息文字
咖啡店的 App 收到 409 時，要顯示「可頌只剩 1 個」並讓客人改數量；前端分辨錯誤靠的是回應裡固定的欄位，例如 { code: 'OUT_OF_STOCK', productId: 2, available: 1 }，道理和邊界用類別、不比對訊息一樣。這個代碼一旦前端用了就是約定，改名要前後端一起改。另外要注意資安：500 的時候只回「系統錯誤」，不要把 message、stack、SQL 原文送到客人瀏覽器，那些只寫進伺服器的 log。

我們自己丟的錯，可以自己設計類別和欄位。但下單流程裡也會碰到別人丟上來的錯誤，那些錯誤的訊息往往太底層，到了上層沒人看得懂。

底層丟上來的錯誤看不懂時，怎麼包裝又不弄丟原因？

舉一個下單流程裡的例子。placeOrder 要算金額，得先知道價格；咖啡店的菜單存成一份 JSON 設定，用 loadMenu 讀進來。這份設定是人手動編輯的，少一個括號，JSON.parse 就會丟出 SyntaxError: Unexpected end of JSON input。

這個訊息對 JSON.parse 來說很精確，但它往上傳到 handleRequest 時，看 log 的人只知道「某處的 JSON 不完整」：是菜單壞了？是客人送來的請求壞了？還是其他設定檔？JSON.parse 不知道自己在解析什麼，知道的是呼叫它的 loadMenu。

所以要在知道脈絡的那一層包裝（wrap）：loadMenu 用 catch 接住底層的錯誤，丟一個說明脈絡的新錯誤「菜單設定格式錯誤」。但只丟新錯誤有代價：原本的 SyntaxError 和它的 stack 就不見了，log 只剩「菜單設定格式錯誤」，查不到是第幾個字元壞掉。解法是讓新錯誤記住「是哪個底層錯誤造成的」：new Error(message, { cause: e })，第二個參數的 cause 放原本的錯誤物件本身，之後從新錯誤的 e.cause 就拿得到它。目前的瀏覽器和 Node 都支援這個選項，版本見課末「補充與查表」。

包裝可以一層疊一層。每個錯誤的 cause 指向造成它的下一層錯誤，串起來就是一條錯誤鏈（error chain）。例如扣款：「付款失敗」的 cause 是「連線逾時」，「連線逾時」的 cause 是「socket hang up」（Node 的訊息，意思是連線被對方中斷）。從最外層看到「付款失敗」，沿著 cause 一路往下走，就能找到最底層的原因。練習 3 會寫一個把整條鏈走完的函式。

包裝之外還有一種情況：這一層接住錯誤，只認得其中一種，其他的處理不了。假設咖啡店決定，庫存不足時不要整筆失敗，而是改成部分出貨：placeOrder 接住 reserveStock 丟出的錯誤，如果是 OutOfStockError，就用 e.available 改成只訂剩下的數量。但同一個 catch 也會接到別的錯誤，例如菜單讀不到的「菜單設定格式錯誤」或某個 bug 造成的 TypeError，這些 placeOrder 不知道怎麼補救。這時要把原本的錯誤原封不動再丟出去，叫重新丟出（rethrow）：

try {
  reserveStock(productId, qty)
} catch (e) {
  if (!(e instanceof OutOfStockError)) throw e  // 不是庫存不足：照樣往上丟
  reserveStock(productId, e.available)           // 庫存不足：改成部分出貨
}

第一行的判斷意思是「只處理庫存不足，其他錯誤照樣往上」。重新丟出的是同一個物件，name、message、stack 都沒變，邊界拿到的就和沒有這層 catch 時一樣，該回 500 的還是回 500。如果少了 throw e，catch 執行完就算處理好了，程式會繼續往下走：菜單壞掉或 bug 造成的錯誤在這裡消失，placeOrder 照樣回傳一筆看起來成功的訂單，log 裡什麼都沒有，這種錯誤最難查。

到這裡，錯誤丟得出去、說得清楚、查得到根源。但錯誤跳出函式的那一刻，函式裡已經做到一半的事怎麼辦？

錯誤跳出去之後，做到一半的事怎麼收拾？

throw 會跳過後面所有的程式，包括本來寫在最後的收尾工作。後端最常見的收尾是歸還借來的資源。placeOrder 寫入訂單時，要向連線池借一條資料庫連線，用完要還；如果中間丟錯，還連線的那行被跳過，這條連線就一直被占著。連線池的連線數量有限，被占住的越多，後面的請求就越得排隊等。PostgreSQL 課第 25 課的 client.release() 就是這個情況。

解法是 finally。try 後面可以接一個 finally 區塊，不管 try 是正常結束、return，還是丟出錯誤，finally 一定會執行；有 catch 的話，finally 在 catch 之後執行。它的用途就是清理：把借來的資源還回去、把狀態歸位。先用最小的例子看它的執行時機，注意 try 裡已經 return 了：

印出的順序是「沖咖啡」「清理咖啡機」「拿到：拿鐵」。try 裡的 return '拿鐵' 先記下要回傳的值，等 finally 跑完才真的離開函式。把「清理咖啡機」換成 client.release()，就是保證連線一定歸還的寫法；練習 4 的收銀機 register.busy 也是用這個方式保證付款結束後一定歸位。

不要在 finally 裡 return。finally 裡的 return 會蓋掉 try／catch 原本要丟的錯誤，錯誤就這樣消失了，呼叫的人以為成功。finally 只放清理的程式。

先檢查，再修改

finally 能保證清理一定執行，但它解決不了另一件事：已經做完的修改不會因為丟錯而自動復原。throw 只是跳過後面的程式，前面已經改掉的資料就停在改到一半的樣子。看一張有兩項商品的訂單，第二項庫存不足時：

拿鐵少了 2、可頌變成 -2，訂單卻沒成立。這就是開場說的「庫存被扣了一半」。問題在順序：迴圈每一項都是先改庫存才檢查，等發現可頌不夠時，拿鐵已經扣掉了。

修法：先把所有條件檢查完，全部通過才開始修改。對這張訂單來說，就是先跑一輪檢查每項商品都夠，再跑第二輪扣庫存；任何一項不夠，第一輪就丟錯，庫存一個都沒動。資料在資料庫裡時，對應的工具是PostgreSQL 課第 18 課的交易：把多個修改綁成一組，中途出錯就 ROLLBACK，整組復原。練習 1 的 reserve 會用到這個原則。

現在每個函式都知道怎麼丟錯、怎麼包裝、怎麼清理。最後一個問題反過來問：錯誤一路往上時，到底該由哪一層接住？

這個錯誤該在哪一層接住？

新手常見的反應是「每個函式都包 try／catch 比較安全」，結果反而把錯誤藏起來。catch 了卻什麼都不做，或只 console.log 就繼續，叫吞掉錯誤（swallow）。下面的 checkout 把刷卡失敗吞掉了，執行看它回傳什麼：

回傳 { ok: true }。信用卡被拒，checkout 卻回報成功：訂單成立、店家沒收到錢，而且沒有任何 log，要等對帳才會發現。所以 catch 不是越多越安全。判斷一個 catch 該不該寫，問一個問題：「這一層接住之後，能做什麼有用的事？」答案只有四種，後三列的例子都是這課寫過的程式：

這一層的情況做法例子
能補救catch，處理掉推薦清單讀取失敗 → 改顯示熱銷商品
只能補充脈絡包一層、帶 cause、再丟loadMenu 把 SyntaxError 包成「菜單設定格式錯誤」
不能處理不要 catch，讓它往上reserveStock 裡不需要 try／catch
邊界（API handler、按鈕事件、排程工作的最外層）統一轉成回應或畫面訊息，並記 log上面的 toResponse：OutOfStockError → 409，其他 → 500

「能補救」那一列要特別小心：能不能在原地補救，取決於錯誤是哪一類。錯誤分兩大類，處理方式完全不同：

  • 預期中的失敗（expected／operational error）：庫存不足、找不到商品、輸入格式錯。業務上本來就會發生，程式要有對應的處理，例如回 409 並告訴客人剩幾個。
  • 程式錯誤（programmer error，也就是 bug）：TypeError: Cannot read properties of undefined。原地 catch 給個預設值，例如折扣算不出來就當成 0，只會讓錯誤的資料繼續往下流，金額錯了還照樣結帳。應該讓它往上到邊界，回 500、記 log、通知工程師，然後修程式。

用這兩類回頭看 toResponse：OutOfStockError 是預期中的失敗，回 409；其他所有錯誤都當成 bug，回 500。王小明那筆 3 個可頌的訂單，從 reserveStock 丟出、流程停下、邊界回 409，到這裡整條路都寫對了。

後面的課會延續這條線：第 9 課是 await 的錯誤與沒有人處理的 rejection；第 27 課把預期中的失敗放進函式的回傳型別；Node 課第 18 課與 NestJS 課第 8 課是整個服務的錯誤策略。

💡 實務上：code review 看到空的 catch，一定會被問「這裡出錯時會怎樣？」
吞掉錯誤的程式在測試時看起來都正常，要等到對帳發現「訂單成立但沒收到錢」才會被發現，而且很難追。審查時資深工程師會逐一看每個 catch：是補救、補脈絡，還是只是讓錯誤消失？兩類錯誤在維運上也分開：庫存不足是日常，記成一般 log 就好；bug 才該觸發通知讓值班的人處理，否則告警太多，大家就習慣性忽略了。

練習

練習 1：完成 OutOfStockError 和 reserve(stock, productId, qty)。

  • OutOfStockError 繼承 Error，name 是 'OutOfStockError'，有 productId、requested、available 三個欄位，訊息格式是 庫存不足：商品 2 需要 3，剩 1。
  • stock 是 Map（商品編號 → 數量），沒有這個商品時當作剩 0。
  • qty 不是正整數（例如 0、-1、1.5、字串）時丟 RangeError；庫存不夠時丟 OutOfStockError。先檢查 qty：輸入本身不合法，就不必去看庫存。丟錯時 stock 不能有任何改變。
  • 成功時扣掉庫存，回傳剩下的數量。

練習 2：完成 loadMenu(text)：用 JSON.parse 解析菜單設定，回傳其中的 items 陣列。解析失敗時丟出 new Error('菜單設定格式錯誤', …)，而且 cause 必須是原本的 SyntaxError 物件。

練習 3：寫 errorChain(err)：從 err 開始沿著 cause 往下走，把每一層的訊息收成陣列，例如 ['付款失敗', '連線逾時', 'socket hang up']。規則：

  • 是 Error 的就收 message，再往它的 cause 走；cause 是 undefined 就結束。
  • 碰到不是 Error 的值（例如字串），收 String(值) 之後結束。
  • 可能有環狀參照（a.cause = b、b.cause = a）：看過的錯誤不再走第二次，每個只列一次。

練習 4：checkout 在 finally 裡 return 'done'，所以成功時拿不到收據，付款失敗時錯誤也被吃掉了。改成：成功時回傳 pay 給的收據；pay 丟錯時，原本那個錯誤物件要丟給呼叫者；兩種情況結束後 register.busy 都要變回 false（付款進行中要是 true）。

練習 5：下面的程式會印出 B 嗎？f() 回傳什麼？

function f() {
  try {
    return 'A'
  } finally {
    console.log('B')
  }
}
console.log(f())

✓ finally 一定會執行，try 裡的 return 'A' 會等 finally 跑完才生效，所以先印 B，f() 回傳 A。只有 finally 自己 return 時才會蓋掉原本的回傳值或錯誤，這正是不該在 finally 裡 return 的原因。

練習 6：邊界程式要把庫存不足轉成 409。為什麼寫 e instanceof OutOfStockError，而不是 e.message === '庫存不足'？

✓ 比對訊息字串的程式，會在某次「只是改個文案」之後默默失效，所有庫存不足都變成 500。速度不是重點；message 也不會被移除。用類別判斷種類，用欄位（productId、available）拿資料。

練習 7：線上的 log 出現 TypeError: Cannot read properties of undefined (reading 'total')，來自你寫的計算折扣函式。最好的處理是？

✓ TypeError 是程式錯誤，不是業務上預期會發生的失敗。回傳 0 或只印 log 都是吞錯：錯誤的金額會繼續往下算，問題被藏起來更難查。能補救、業務上預期的失敗（例如庫存不足）才在原地處理。

常見錯誤

  • throw 字串或物件字面值：沒有 stack，instanceof 也分不出種類。一律 throw Error 或它的子類別。
  • catch 之後什麼都不做，或只 console.log 就繼續：錯誤被吞掉，失敗看起來像成功。處理不了就不要 catch。
  • 包裝錯誤時沒帶 cause：原始原因和它的 stack 消失。寫 new Error('…', { cause: e })，cause 要放錯誤物件本身，不是 e.message。
  • 用 message 字串判斷錯誤種類：改文案就壞。用 instanceof 加自訂類別。
  • 在 finally 裡 return：會蓋掉原本的錯誤與回傳值。finally 只放清理。
  • 先改資料再檢查：丟錯時資料只改了一半。先檢查完所有條件，再修改；在資料庫裡用交易。
  • 自訂錯誤沒設定 name：log 裡全都叫 Error，分不出是哪一種。
  • 用 JSON.stringify(err) 記錄錯誤：只得到 {}。自己挑出 name、message、stack 與 cause。

補充與查表

  • stack 的格式：課文看到的是 Chrome 與 Node（都是 V8 引擎）的格式。Firefox 和 Safari 的 stack 沒有第一行的「名稱: 訊息」，格式也不同，所以程式不要解析 stack 字串。
  • cause 的支援：new Error(message, { cause }) 是 ES2022 加入的選項，Chrome、Firefox、Safari 與 Node 都支援。
  • 自訂錯誤也能帶 cause：建構子多收一個參數，交給 super(message, { cause })，Error 的建構子會把它存成 cause。例如 OutOfStockError 若是包裝資料庫錯誤而來，就能把原本的錯誤一起帶上。
  • Error.isError(值)：較新的方法，可以判斷一個值是不是真正的 Error（Chrome 134、Firefox 138、Node 24.3 起支援，Safari 18.4 只有部分支援），本課沒有用到。

小結

  • 庫存不夠就 throw：目前的函式立刻中斷，錯誤沿著呼叫堆疊往上找最近的 catch，中間每一層不用寫檢查；一路都沒有就是未捕捉的錯誤，在 Node 會讓程序結束。
  • 丟 Error 物件，不丟字串：Error 有 name、message、stack。stack 在建立時記下呼叫堆疊，第一個 at 是丟出錯誤的地方。
  • 邊界（API handler）負責把錯誤轉成回應。要分辨種類，寫自訂錯誤類別：extends Error、設定 name、帶上程式要用的欄位，用 instanceof 判斷，不比對訊息文字。
  • 底層錯誤看不懂時，在知道脈絡的那一層包裝，用 { cause: e } 保留原因；記 log 時把整條錯誤鏈留下來，不要直接 JSON.stringify(err)。
  • finally 一定會執行，用來清理；不要在裡面 return。丟錯不會復原已經做的修改，所以先檢查、再修改。
  • 能補救才 catch，只能補充脈絡就包裝再丟，不能處理就讓它往上；預期中的失敗回給使用者，bug 要告警並修程式。
