階段 3：型別基礎 · 第 15 課

聯合型別與字面值型別

咖啡店的出貨流程裡有一個函式 ship(order)：只有已付款的訂單才出貨，判斷寫成 if (order.status === 'paid')。某天同事在建立訂單的程式裡，把狀態寫成了 'payed'。訂單型別裡的 status 是 string，'payed' 也是字串，所以 TypeScript 一聲不吭。接下來要看運氣：資料庫有限制的話，寫入時才失敗；沒有的話，這張訂單的狀態永遠不等於 'paid'，客人付了錢，訂單卻一直沒出貨。

這一課的任務是把訂單的型別寫緊，讓這類錯誤在寫程式的當下就畫紅線：狀態只能是那四個值、放進物件裡的狀態不會悄悄變回 string、可能是空的備註和電話不會讓程式當掉或被誤判、尺寸清單選對寫法。最後再準備一個工具，讓下一課能檢查「每一種狀態都處理到了」。

這課的路線：
  1. 狀態怎麼只收四個值：字面值型別加上聯合型別，讓 'payed' 當場畫紅線（開場問題的最小答案），以及這道防線擋得到什麼、擋不到什麼。
  2. 聯合型別的值能拿來做什麼：string | number 為什麼只能用兩種都有的方法。
  3. 明明寫了 'paid'，物件裡的 status 為什麼變成 string：型別放寬，以及三種保住它的寫法。
  4. 備註、電話可能是空的：用 ?.、?? 安全地讀取和給預設值，不把 0 元的贈品和刻意留白的備註吃掉。
  5. 尺寸清單要不要用 enum，以及下一課檢查「狀態全部處理到了嗎」要用的空集合 never。
這課會用到：
  • 第 13 課的推論：const size = 'M' 推論成 "M"，let drink = '拿鐵' 推論成 string。
  • 第 13 課的 strictNullChecks：開著時 null 不能混進一般的型別，string 不包含 null。
  • 第 14 課的物件型別與 Record<K, V>：用 type 描述物件有哪些欄位；Record 是鍵為 K、值為 V 的物件。
這一頁的練習區開著 erasableSyntaxOnly 選項，第 5 節講 enum 時會用到它，現在先不用管。

訂單狀態怎麼只收這四個值？

問題出在 string 太寬。型別描述的是「這個位置允許放哪些值」，string 允許所有字串，'paid'、'payed'、'拿鐵'、空字串都算。我們要的是一個只允許 'pending'、'paid'、'done'、'cancelled' 這四個值的型別。TypeScript 用兩個工具把它組出來。

第一個工具是字面值型別（literal type）：把一個具體的值直接當成型別。寫在型別位置的 'paid' 不是字串值，而是「只允許字串 'paid'」的型別。宣告 const s: 'paid' = 'paid' 可以，把 'done' 指定給它就會報錯。一個字面值型別只能表示一種狀態，訂單有四種，所以還不夠。

第二個工具是聯合型別（union type）：寫成 A | B，意思是「這個值是 A 或 B 其中一種」，中間的 | 可以讀成「或」。把四個字面值型別用 | 接起來，就得到「只能是這四個值之一」的型別。付款方式和尺寸也是固定幾種，下面一起用同樣的寫法：

為什麼 'paid' 可以、'payed' 不行？把型別想成「允許的值的集合」就清楚了：string 包含所有字串，OrderStatus 只有四個，'paid' 只有一個。TypeScript 判斷「這個值能不能放到這裡」，就是看它屬不屬於那個集合。

從圖上可以讀出一條規則：小的可以放進大的，反過來不行。'paid' 可以給 OrderStatus，OrderStatus 可以給 string，因為小集合裡的每個值都在大集合裡。反過來，一個 string 可能是 'payed'，不保證落在四個值裡，所以不能給 OrderStatus。第 3 節的錯誤就是這條規則造成的，到時候回來看這張圖。

這道防線有它的範圍。型別只存在寫程式和編譯的時候，程式執行時已經被擦掉了，所以它擋得到「自己程式裡寫錯的值」，擋不到「執行時從外面進來的資料」。開場提到的資料庫是另一道防線：PostgreSQL 課第 13 課的 order_status enum 就是同樣四個值，第 12 課的 CHECK 約束也能限制欄位的值。兩者擋的時間點和範圍不同：

什麼時候擋擋得到什麼
TypeScript 字面值聯合寫程式時（編輯器、tsc）自己程式裡寫錯的值；擋不到執行時從外面進來的資料
PostgreSQL enum／CHECK寫入資料庫時所有寫入，不管是哪個程式、哪個人寫的

所以兩道防線都要有：TypeScript 讓你在寫程式時最早發現，資料庫保證最後存進去的一定合法。資深工程師的習慣是讓兩邊的值清單一致：資料庫多了 'refunded'，TypeScript 的型別也要跟著加（用 Prisma 這類工具時，型別直接從資料庫結構產生）。

💡 實務上：狀態一改，前後端好幾個地方要跟著動
咖啡店後台的訂單列表會依狀態顯示不同顏色的標籤、篩選下拉選單、「可以取消嗎」的按鈕判斷，這些地方都靠同一個 OrderStatus。把對照表寫成 Record<OrderStatus, string>，之後加 'refunded' 時沒補上文字的地方會直接報錯，不會在畫面上出現空白標籤。要注意的是，前端從 API 收到的 JSON 型別只是「你宣稱的」，後端真的回了 'refunded'，TypeScript 不會發現（第 26 課處理這件事）。資深工程師在 PM 提出「多一種狀態」時，會先問：資料庫、API、前端畫面、報表，哪些地方要一起改、誰負責上線順序。

拿到聯合型別的值，函式裡能拿它做什麼？

OrderStatus 的四個成員都是字串，所以拿到 status 時，用字串的方法不會有問題。但聯合的成員不一定是同一種東西。訂單模組裡就有一個例子：商品編號在資料庫裡是數字 2，從網址 /products/2 拿到的卻是字串 '2'。函式想兩種都收，參數就寫成 string | number。問題是：函式裡面能對這個 id 做什麼？執行下面這格，看第二行和第三行的待遇有什麼不同：

return id.toUpperCase() 那一行報錯 TS2339：「string | number 上沒有 toUpperCase」。上一行的 toString() 卻沒事。差別在於 toString 是 string 和 number 都有的方法，toUpperCase 只有 string 有。

TypeScript 這樣判斷的理由是：它在寫程式時檢查，不知道這一次呼叫傳進來的是哪一種，只知道「可能是 string，也可能是 number」。只要有一種可能會出事，它就報錯。執行結果也證明它對：productLabel('2') 正常，productLabel(2) 真的當掉了，因為數字沒有 toUpperCase。如果 TypeScript 放行，這個錯誤要等到有人用數字編號呼叫時才會在正式環境出現。

所以記住這條規則：聯合型別在縮小之前，只能用所有成員共同的部分。要用 string 才有的方法，得先檢查「現在是 string」，例如 if (typeof id === 'string')，TypeScript 會在 if 裡把型別縮小成 string，這叫型別縮小，第 16 課整課在講。這一課的 OrderStatus 都是字串，用 === 比對就夠了，暫時不需要縮小。

到這裡，狀態的型別寫好了。接下來把它套到真正的訂單物件上，傳給 ship，會遇到一個意外。

明明寫了 'paid'，ship 為什麼說它是 string？

有了 OrderStatus，ship 的參數就能要求 status 必須是四個值之一。現在建立一張已付款的訂單，傳進去：

錯誤 TS2345：status 是 string，不能給 OrderStatus。這正是第 1 節集合圖的規則：大的 string 放不進小的 OrderStatus。可是程式裡明明寫的是 'paid'，為什麼變成了 string？

原因是 TypeScript 推論型別時，會考慮這個值之後還能不能被改。第 13 課看過：const size = 'M' 推論成 "M"，因為 const 變數不能重新指定，它永遠是 'M'；let drink = '拿鐵' 推論成 string，因為之後可能改成 drink = '美式'，如果推論成 '拿鐵'，這行正常的程式就會報錯。字面值被推論成較寬的 string、number，叫做型別放寬（widening）。

物件屬性屬於「之後還能改」的那一類。const 只鎖住 order 這個變數，不能讓它指向別的物件，但物件裡的屬性照樣可以改：order.status = 'whatever' 是合法的 JavaScript。所以 TypeScript 把 status 推論成 string。這個預設是合理的：大部分物件建立後確實會被修改，如果每個屬性都推論成字面值，order.status = 'done' 這種正常的寫法反而會報錯。

問題是在這裡，我們心裡知道 status 是訂單狀態，TypeScript 卻不知道。要讓它知道，有三種寫法，都不用動 ship：

三種寫法各自的意思：

  1. 註記型別：const a: Order = … 直接告訴 TypeScript「這是一張訂單」。它會用 Order 的定義檢查右邊的物件，status 寫成 'payed' 的話，錯誤就出現在建立訂單的這一行，而不是傳給 ship 的時候。這是最常用、意圖也最清楚的寫法。
  2. as const：叫 const assertion，告訴 TypeScript「這個值不會再改，照字面推論」。整個物件的每個屬性都保留字面值，而且變成 readonly，所以 b 的型別是 { readonly id: 8; readonly status: "paid" }。它屬於小集合，放得進 Order。
  3. 直接寫在呼叫的地方：ship({ id: 9, status: 'paid' }) 的物件沒有先存進變數，TypeScript 推論時已經知道它要給 ship 的參數，會照參數型別來推論，status 就不會放寬。適合只用一次的值。

as const 也能用在陣列上。一般的 ['S', 'M', 'L'] 推論成 string[]，長度和內容都可以改。加上 as const 後，它變成唯讀的 tuple：tuple 是長度固定、每一格型別也固定的陣列，這裡的型別是 readonly ["S", "M", "L"]，SIZES.push('XL') 會報錯。要注意 as const 只影響型別，執行時沒有凍結任何東西，這點跟第 2 課的 Object.freeze 不同。第 20 課會用 as const 的陣列推導出尺寸的型別，第 5 節的 enum 替代寫法也會用到它。

不要用 as Order 讓錯誤閉嘴。as Order 這種寫法叫型別斷言（type assertion）：它不是請 TypeScript 檢查，而是告訴 TypeScript「我說這是 Order，照我的意思辦」。ship(order as Order) 看起來也能過，但問題就在這裡：order 裡寫的如果是 'payed'，status 已經放寬成 string，TypeScript 判斷 string「有可能」是 OrderStatus 就放行，打錯字的保護就沒了。as const 名字裡有 as，但它不放寬也不騙編譯器，可以放心用。

狀態這個欄位到這裡處理完了。不過訂單和顧客資料上還有一種欄位，麻煩不在「值寫錯」，而在「可能根本沒有值」：備註可以留白，顧客可能沒留電話。

備註可能留白、電話可能沒留：可能是空的值怎麼處理？

先回顧型別怎麼寫。第 13 課的 strictNullChecks（包含在 strict 裡）開著時，string 不包含 null：let note: string = null 會報錯。值可能是空的，就要在型別上明說，寫成聯合 string | null，這也是一種聯合型別。第 14 課的約定：資料庫欄位可以是 NULL 就寫 | null；物件可以沒有這個屬性就寫 ?。

型別寫對之後，讀這種值會碰到兩個麻煩。第一個是往下讀會當掉：用名字找顧客可能找不到（得到 undefined），找到了 phone 也可能是 null，這時直接寫 find(name).phone.slice(-4)，在 undefined 或 null 上讀屬性會丟出 TypeError。第二個是給預設值會誤判：沒有值時想顯示「（沒有電話）」，但寫法不對的話，0、空字串這些合法的值也會被換掉。JavaScript 為這兩個麻煩各準備了一個運算子：

  • 可選串連（optional chaining, ?.）：a?.b，a 是 null 或 undefined 時，不去讀 b，整串直接得到 undefined，不會當掉；a 有值時就跟 a.b 一樣。一串裡可以接好幾個，任何一環是空的，後面都跳過。
  • 空值合併（nullish coalescing, ??）：a ?? b，只有 a 是 null 或 undefined 時才換成 b，其他值都原樣保留。

在 ?? 出現以前，大家用 || 給預設值，第二個麻煩就是它造成的。|| 看的不是「是不是空的」，而是「是不是 falsy」。falsy 值是在 if、|| 這類需要真假的地方會被當成 false 的值：false、0、''、null、undefined、NaN（還有少見的 -0、0n）。對 || 來說這些都是「沒有」。可是 0 元的贈品、刻意留白的備註都是合法的值，用 || 給預設值會被換掉。

💡 實務上：null 和 undefined 的意思要統一
常見的團隊約定：undefined 表示「沒有提供」（API 沒傳這個欄位、可選屬性），null 表示「明確是空的」（資料庫的 NULL、使用者清空了備註）。更新 API 裡這個差別很重要：沒傳 note 是不改，傳 note: null 是清空。混著用的話，後端分不出使用者到底想做什麼。

尺寸清單能不能用 enum 寫？

訂單上還剩一個固定幾種值的欄位：尺寸。第 1 節已經把它寫成 'S' | 'M' | 'L'，但很多人看到「一組固定的值」，第一個反應是 enum（列舉）：Java、C# 等語言都用它，TypeScript 也有。你在舊專案和不少教學文章裡會看到這種寫法：

按執行：輸出正常，但錯誤清單有兩個 TS1294：「開了 erasableSyntaxOnly 時不允許這種語法」。這就是課首提到的選項。它為什麼要擋 enum？要看編譯後的 JavaScript：

var Size;
(function (Size) {
    Size["S"] = "S";
    Size["M"] = "M";
    Size["L"] = "L";
})(Size || (Size = {}));
var Status;
(function (Status) {
    Status[Status["Pending"] = 0] = "Pending";
    Status[Status["Paid"] = 1] = "Paid";
})(Status || (Status = {}));

這課到目前為止的寫法，像 type OrderStatus = …、: Order、as const，編譯時直接擦掉就好，剩下的就是一般的 JavaScript。enum 不一樣：它會產生一個真的物件，執行時存在（數字 enum 還多了反查：Status[1] 是 'Paid'）。所以 TypeScript 的語法分成兩類：拿掉型別之後就是合法 JavaScript 的，叫可擦除語法（erasable syntax）；拿掉型別之後不是合法 JavaScript、必須轉換成別的程式碼的，叫不可擦除的語法，enum 就是後者。

這個區分在後端很實際。Node 24 可以直接執行 .ts 檔，但它的做法只是把型別擦掉（type stripping），不會幫你產生程式碼，所以遇到 enum 會直接丟錯：

$ node order.ts
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode

要加實驗性的旗標才跑得起來（見課末）。而這個錯誤要到執行時才出現。erasableSyntaxOnly 選項就是為此而生：專案裡用到 enum 這類不可擦除的語法，編譯時就報 TS1294，在編輯器裡就看得到，不用等到執行才發現。哪些語法算不可擦除、這個選項從哪個版本開始有，見課末「補充與查表」。

不用 enum，尺寸清單怎麼寫？

  • 字面值聯合：type Size = 'S' | 'M' | 'L'。大多數情況這樣就夠了，值本身就是字串，存資料庫、放進 JSON 都不用轉換。
  • 需要在執行時列出所有值（例如畫下拉選單）：字面值聯合是型別，執行時不存在，沒辦法拿來跑迴圈。這時用 as const 的陣列或物件，再從它推導出型別，第 20 課細講。

你可能也會在 Prisma 的 schema 看到 enum 關鍵字，但它產生的 TypeScript 不是 enum，而是 as const 物件，正好就是上面的第二種替代寫法（產生的樣子見課末）。舊程式的 enum 不用急著改，讀得懂就好：字串 enum 的 Size.M 就是字串 'M'。新寫的程式用字面值聯合。

💡 實務上：接手有 enum 的專案，先別急著全改
前端專案大多經過 Vite 這類打包工具轉譯，enum 照常能跑；會出事的是後端想改用 node xxx.ts 直接執行，或在專案裡開 erasableSyntaxOnly 的時候。資深工程師的做法通常是：新程式一律用字面值聯合，舊的 enum 等到要動那個檔案時再順手換，不開一個橫跨幾十個檔案的大 PR。換的時候要搜尋所有 Size.M 這類用法，數字 enum 特別小心，資料庫或 API 裡存的可能是 0、1 而不是字串，換成字串會讓舊資料對不上。

四種狀態都處理到了嗎？沒有任何值的型別 never

現在訂單的狀態、尺寸都是字面值聯合了。回到第 1 節的 💡：後台依狀態顯示標籤、判斷能不能取消，這些程式要對每一種狀態都有處理。哪天加了 'refunded'，怎麼知道哪些地方漏了？要讓 TypeScript 回答這個問題，需要先認識一個特別的型別。

第 1 節說型別是值的集合。集合可以很大（string），可以只有一個值（'paid'），也可以是空的。never 就是那個空集合：沒有任何值屬於它，任何值都放不進去。它常在型別運算的結果裡出現，下面兩個例子都是。先回顧符號：第 14 課的 & 要求「同時是兩者」，| 是「其中一種」。這一課先看它怎麼在運算裡冒出來；下一課會親手把它寫成註記，用來做檢查。

滑鼠移到 Both、WithNever 上看看。'S' & 'M' 要一個值同時等於 'S' 和 'M'，不可能，所以是 never；impossible 那一行報錯，因為沒有任何值能放進空集合。'S' | never 是「'S' 或空集合裡的某個值」，空集合什麼都沒有，聯合起來就只剩 'S'。所以 never 可以想成「零個選項的聯合」。

這聽起來沒什麼用，但它正好能回答本節開頭的問題。第 16 課會用它做窮舉檢查：程式把 OrderStatus 的四種一個一個處理掉，處理完剩下的可能性就是空的，也就是 never；哪天新增 'refunded' 卻忘了處理，剩下的就是 'refunded' 而不是 never，TypeScript 會指出漏掉的地方。

練習

練習 1：把 OrderStatus 改成四種狀態的字面值聯合（'pending'、'paid'、'done'、'cancelled'），定義 PaymentMethod（'cash'、'card'、'linePay'），再完成 canCancel：待付款和已付款的訂單可以取消，其他不行。

練習 2：ship(order) 報 TS2345，因為 order.status 被放寬成 string。不要改 ship 的參數型別，也不要用 as Order 或 any，讓 order.status 保持精確的型別。

練習 3：完成 describeItem，回傳「名稱｜價格｜備註」：

  • price 是 null 時寫「時價」，否則寫「80 元」這種格式（0 元就是「0 元」）。
  • note 沒有或是 null 時寫「（無備註）」；空字串 '' 就保持空字串。

例如 { name: '贈品咖啡', price: 0, note: '' } 要得到 '贈品咖啡｜0 元｜'。

練習 4：起始程式用 enum Size，在這一頁報 TS1294（Node 直接執行也會失敗）。改寫成：

  • Size 是字面值聯合 'S' | 'M' | 'L'（不能用 enum 或 const enum）。
  • SIZE_PRICE_DELTA 記錄每個尺寸的加價：S 0、M 10、L 20。它的型別要保證每個尺寸都有，少一個就報錯。
  • priceFor(size, basePrice) 回傳加價後的價格，例如 priceFor('L', 110) 是 130。

練習 5：const order = { status: 'paid' } 之後，order.status 的型別是什麼？

✓ const 只鎖住 order 這個變數，屬性還能被改成別的字串，所以 status 放寬成 string。要保留字面值，註記型別或加 as const。TypeScript 不會自己猜出 OrderStatus，型別名稱一定要你寫出來才有。

練習 6：0 || 50 和 0 ?? 50 各是多少？

✓ || 遇到任何 falsy 值（0、''、false、null、undefined、NaN）都換成右邊，?? 只在 null、undefined 時才換。0 元的贈品用 || 給預設價格，會被當成沒有價格。

練習 7：一個 .ts 檔裡有 enum Size { S = 'S', M = 'M' }，用 Node 24 直接 node order.ts 執行會怎樣？

✓ enum 編譯後是一個真的物件，不是能直接擦掉的型別，Node 預設的 type stripping 處理不了，要加實驗性的 --experimental-transform-types。b 錯在 enum 不是純型別；c 錯在 Node 從不做型別檢查（第 13 課）。開 erasableSyntaxOnly 可以在編譯時就發現。

常見錯誤

  • 狀態欄位寫成 string：打錯字的 'payed' 沒人擋，if (status === 'paid') 永遠不成立。固定幾個值的欄位一律寫成字面值聯合，跟資料庫的 enum／CHECK 保持一致。
  • 用 as 讓放寬的字面值閉嘴：as Order 連打錯字都一起放行。註記型別或用 as const。
  • 聯合裡忘了 null：資料庫欄位可以是 NULL，型別卻寫 string，查出 null 時程式以為是字串。可以是 NULL 的欄位要寫 string | null。
  • 用 || 給預設值：0 元、空字串、false 都被換掉。要「沒有值才用預設」就用 ??；判斷 null 寫 === null，不要用 if (price)。
  • null 和 undefined 混著用：同一個欄位有時 null、有時 undefined，更新 API 就分不出「沒傳」和「要清空」。團隊先約定意思再寫。
  • 在要給 Node 直接執行的程式裡用 enum：Node 預設不支援，執行時才炸。改用字面值聯合，並在 tsconfig 開 erasableSyntaxOnly。

補充與查表

  • erasableSyntaxOnly 的版本：TypeScript 5.8 加入。開著時，enum、const enum、類別的參數屬性（第 23 課）這類不可擦除的語法都會報 TS1294。本機實測 5.9.3 和 7.0.2 都一樣。
  • Node 執行含 enum 的 .ts：Node 24 預設只擦掉型別，要加 --experimental-transform-types 才跑得起來，而且這個旗標還是實驗功能。
  • Prisma 產生的「enum」：依 Prisma 6、7 的文件，schema 裡的 enum 產生的是 export const Size = { S: 'S', M: 'M', L: 'L' } as const 這種形式的物件，Size.M 就是字串 'M'。

小結

  • 字面值型別只允許一個特定值；用 | 接成聯合，'pending' | 'paid' | 'done' | 'cancelled' 讓打錯的狀態在寫程式時就被擋下。型別是值的集合，小的可以放進大的，反過來不行。
  • 型別擋不到執行時從外面進來的資料；資料庫的 enum／CHECK 是第二道防線，兩邊的值清單要一致。
  • A | B 的值是其中一種；縮小之前只能用所有成員共有的東西。
  • let 和物件屬性會放寬成 string；用型別註記、as const，或直接在呼叫處寫字面值保住它，不要用 as 斷言。
  • strict 下 string 不含 null；用 ?. 安全地往下讀，用 ?? 給預設值，|| 和 if (值) 看的是 falsy，會吃掉 0 和空字串。
  • enum 會產生執行時物件，不是可擦除語法：Node 直接執行不支援，erasableSyntaxOnly 報 TS1294。新程式用字面值聯合，舊程式的 enum 讀得懂就好。
  • never 是沒有任何值的型別，也是空的聯合；下一課用它檢查每一種狀態都處理到了。
