階段 2：非同步、迭代與並發 · 第 12 課

競態與並發控制：過期回應、插隊與重複送出

咖啡店的線上點餐頁上線後，第一個週五中午的尖峰一過，客服一口氣收到三張單。王小明說：「我在搜尋框打『拿鐵』，畫面卻顯示『拿』的結果。」店長說：「拿鐵只剩最後一杯，系統卻同時賣給了王小明和陳美華。」林志豪說：「我結帳時按了兩下，被建了兩張訂單。」你在本機怎麼試都試不出來，每一行程式單獨看也都沒有錯。

這三個 bug 的原因是同一個：好幾件非同步工作同時在進行，程式的結果取決於它們完成的先後順序。這種「結果取決於誰先完成」的 bug 叫競態（race condition）。開發時 API 都很快、只有你一個人在點，順序幾乎固定，所以看不到；上線後網路有快有慢、很多人同時下單，順序一變，bug 就冒出來，而且很難重現。這一課沿著點餐流程，從搜尋、結帳扣庫存、加入購物車到送出訂單，把這三張客服單一張一張修掉，同時學會分辨哪些修法在前端就夠、哪些一定要交給後端。

這課的路線：
  1. 只有一條執行緒，為什麼結果會取決於誰先完成：三張單共同的原因是 await，競態有兩種基本形狀（開場問題的最小答案）。
  2. 第一張單，搜尋框：用請求序號和 AbortController 讓畫面只採用最新的結果；為什麼 debounce 不夠。
  3. 第二張單，最後一杯拿鐵：讓「檢查庫存＋扣庫存」不被插隊；後面的步驟失敗時，庫存怎麼正確還回去。
  4. 點餐流程裡做不到的一處，加入購物車：讀和寫中間一定要 await，沒辦法把 await 搬走時，改用依 key 排隊的鎖；伺服器開好幾個程序時，這把鎖為什麼擋不住。
  5. 第三張單，按兩下送出：用單一飛行讓同一件事只做一次，後端再用冪等鍵把關；最後整理成一張選擇表，以及上線後怎麼查。
這課會用到：
  • 第 7 課的 event loop：同一時間只跑一段同步程式，一段跑完才從佇列拿下一個工作。
  • 第 8 課的 then 鏈：每個 then 回傳新的 Promise；catch 處理完之後，鏈恢復成功。
  • 第 9 課的 async/await：await 只暫停目前的函式，別的流程可以先跑；沒人接的失敗叫 unhandled rejection；finally 不論成功或失敗都執行。
  • 第 11 課的 AbortController：abort() 發出取消，工作透過 signal 收到通知，以 AbortError 失敗。

只有一條執行緒，為什麼結果會取決於誰先完成？

先處理一個常見的誤會。第 7 課講過，JavaScript 只有一條執行緒：同一時間只跑一段程式，一段同步程式一旦開始，就會一路跑到結束，中間不會被別的程式打斷。很多人因此以為 JavaScript 不會有競態，兩個請求「自然會排隊」。

問題出在 await。第 9 課講過，函式執行到 await 時會暫停，把執行緒讓出來；等到在等的 Promise 有了結果，函式才從 await 的下一行繼續。暫停的這段時間，event loop 會去跑別的工作：另一個請求的處理函式、使用者的下一次輸入。它們可能讀、也可能改你這個函式正在用的同一份資料。所以這課把程式裡的每一個 await 叫作插隊點：函式在這裡停下，等它回來時，外面的世界可能已經被別人改過了。單執行緒真正保證的只有一件事：兩個 await 之間的同步程式不會被打斷。

有了插隊點這個觀念，三張客服單可以歸成兩種形狀。下面這張圖把前兩張單畫成時間軸，橫軸是時間；先看上半部的搜尋框，再看下半部的庫存。

第三張單（結帳按兩下）是同一件事被觸發了兩次，不是讀寫順序被打亂，但根源一樣：第一次送出還停在 await 等伺服器回應時，第二次送出已經開始了。第 5 節再處理它。

到這裡，開場問題有了最小答案：單執行緒不代表沒有競態，每一個 await 都是插隊點；在 await 之前讀到的東西，到 await 之後可能已經過期。修法要依形狀來選。下一節從最容易看見的第一張單開始：搜尋框怎麼只採用最新的結果？

搜尋框：怎麼讓畫面只採用最新的結果？

過期回應的問題不在請求本身，而在結果回來時，沒有確認自己還是不是最新的那一個。所以第一個修法，是讓每次搜尋記得自己的身分。

修法一：給每次搜尋一個序號

準備一個所有搜尋共用的計數器 latest。每次搜尋一開始就把它加 1，並把加完的值存進這次搜尋自己的區域變數 id。結果回來時比一下：id 已經不等於 latest，表示等待期間又有新的搜尋開始了，這個結果過期，直接丟掉。這能成立靠的是第 1 課的閉包：函式記得它被建立時周圍的變數，每次呼叫 search 都有自己的一份 id，就算 await 了 600ms，回來時拿到的還是當初那個號碼；latest 則永遠是最新那次搜尋的號碼。執行後看「丟掉過期的…」那一行，以及使用者最後看到什麼：

修法二：送出新請求前取消上一個

第 11 課的 AbortController 就是做這件事的。每次搜尋開一個新的 controller，把它的 signal 交給 api；下一次搜尋開始時，先對上一個 controller 呼叫 abort()。支援 signal 的 api 收到通知後停下工作（下面的模擬是 clearTimeout，真實的 fetch 會中斷連線），並讓自己回傳的 Promise 失敗。失敗用的錯誤是 signal.reason：abort() 沒給原因時，它是名稱為 AbortError 的 DOMException（MDN）。執行後看三件事：「拿」有沒有被叫停、畫面更新成什麼、第一次 search 最後怎麼結束：

最後一行印出第一次 search 以 AbortError 失敗：被取消的那次搜尋沒有安靜消失。這是我們自己要求的結果，不是真的出錯；但搜尋框的事件處理函式通常不會去接 search 回傳的 Promise，沒人接的失敗就變成第 9 課講過的 unhandled rejection。所以被取消時要安靜結束：在 catch 裡判斷是不是自己取消的（例如看 signal.aborted），是就 return；其他錯誤，例如伺服器回 500，照樣丟出去讓呼叫者處理，不能一起吞掉。

有了取消，為什麼還要序號？

取消只在 api 理會 signal 時才有效，不是每個 api 都會理會。就算理會，結果也可能剛好在 abort() 之前就已經回來、排在 microtask 裡等著，abort() 改變不了一個已經回來的結果。這時能擋住舊結果的只有序號（或在寫進畫面前檢查 signal.aborted）。反過來，只有序號的話，舊請求會白白跑完。所以兩個修法要一起用，各管一件事：取消負責減少浪費，序號負責保證畫面正確。練習 1 會把兩個合在一起寫成 createSearch。

加了 debounce 還不夠嗎？

很多搜尋框已經有去抖動（debounce）：使用者打字時先不送，等他停下來一段時間（例如 300ms）都沒再輸入，才送出一次搜尋。它的目的是減少請求數：連續打五個字只送一次，不是五次。所以常有人以為加了 debounce 就不會有過期回應。

debounce 控制的只是「什麼時候送」。只要使用者打字中途停頓超過 300ms，前一個字一樣會送出去，兩個請求誰先回來還是看伺服器。下圖是王小明打了「拿」、停了 400ms 才打完「拿鐵」：「拿」在 300ms 送出，900ms 才回來；「拿鐵」在 700ms 送出、750ms 就回來，畫面一樣被「拿」蓋掉：

所以 debounce 是減輕伺服器負擔的好工具，可以跟序號、取消一起用，但不能取代它們。Vue 的 watch 也有對應的清理機制可以搭配取消，寫法和限制見課末「補充與查表」。

💡 實務上：凡是「條件一變就重新載入」的畫面都有過期回應
不只搜尋框：咖啡店後台的訂單列表切換「今天／本週」篩選、商品頁快速切換分頁、詳細頁從訂單 A 點到訂單 B，都是同一個問題。它在本機幾乎不會出現（API 都很快），上線後碰到慢網路或慢查詢才冒出來，客服回報常是「畫面顯示的不是我選的那個」。實務上多半交給資料請求套件（例如 TanStack Query 這類會依查詢條件管理結果的工具）或框架的清理機制處理，自己寫 fetch 時才要手動加序號和取消。資深工程師 code review 看到「await 回來就直接寫進畫面狀態」，會先問一句：這段等待期間，使用者可能已經換條件了嗎？

最後一杯拿鐵：怎麼讓檢查和扣減不被插隊？

搜尋框的過期結果還沒造成傷害，丟掉就好。第二張單不一樣：過期的庫存已經被拿來做了決定，賣出去的拿鐵收不回來，所以要從源頭讓它不被插隊。回到第 1 節那個賣出兩杯的 buy。直覺的修法是「await 回來之後，重新讀一次最新的庫存再扣」，這樣看起來就不會用到舊值了。執行後看兩個人的結果和庫存：

lost update 消失了：陳美華在第 4 步重新讀到王小明扣完的 0，沒有蓋掉他的扣減。但庫存變成 −1，因為兩個人的檢查都發生在第 1、2 步，也就是 await 之前；回來後重新讀到的值只拿來算扣減，沒有人再檢查它夠不夠。只要檢查和扣減之間隔著一個 await，就有一段時間讓別人插進來，在哪一步重新讀都一樣。

要讓檢查和扣減不被插隊，它們必須是一段中間沒有 await 的同步程式。一組操作不會被別人從中間插進來，這個性質叫原子性（atomicity），PostgreSQL 課第 18 課的交易保證的也是這件事。在 JavaScript 裡不需要額外的工具：第 1 節講過，同步程式一旦開始就會跑完，所以一段沒有 await 的同步程式天生就是原子的。修法是把扣減搬到 await 之前，和檢查放在一起，扣完才去寫稽核紀錄。執行後看誰買到、庫存剩多少：

王小明買到，陳美華得到「賣完了」，庫存 0。稽核紀錄照樣寫，只是改在扣完之後；陳美華在王小明的 await 期間插進來時，看到的已經是扣過的庫存。

但順序一改，產生了一個新問題：庫存先扣了，稽核紀錄要是寫失敗呢？

扣完之後稽核失敗了：庫存怎麼還回去？

咖啡店規定沒有稽核紀錄的購買不算數，所以稽核失敗時這次購買要算失敗，扣掉的庫存要還回去。這種「後面的步驟失敗了，就把前面已經做過的事反向做回來」的做法叫補償（compensation）。直覺的寫法是扣之前先記下當時的庫存 before，失敗時把庫存設回 before。下面的程式讓兩種補償寫法各跑一次同樣的情境：庫存 10 杯，有人買 2 杯（稽核 40ms 後失敗），同時有人買 3 杯（稽核 10ms 後成功）。執行後比較兩行印出的庫存：

正確答案是 7：只有買 3 杯的成功，10 − 3。「寫回舊值」得到 10，因為買 2 杯的那位記下 before = 10 之後，停在 await 的 40ms 裡，買 3 杯的那位扣掉了 3 杯；把庫存設回 10，就連那 3 杯一起抹掉了。這跟第 1 節的 lost update 是同一個錯：before 是 await 之前讀到的值，await 回來時它已經過期。補償要做反向操作：扣了多少就以當下的庫存為準加回多少，而不是還原快照。練習 2 會把「檢查＋扣減放在同一段同步程式」和「失敗時加回數量」寫進同一個 reserve。

這一節的庫存都存在程式的 Map 裡；正式環境的庫存在資料庫，下面說明怎麼對應。

伺服器同時處理很多請求，每個請求都可能在 await db.query(…) 的地方被插隊，所以這種情況在資料庫上更常見。PostgreSQL 課第 19 課的解法對應到這裡：UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1 把「檢查＋扣減」交給資料庫用一句完成（條件式 UPDATE）。庫存不夠時 WHERE 的 stock >= $1 不成立，這句 UPDATE 影響 0 列、庫存不變；程式看到回傳的影響列數是 0，就當作賣完，是 1 才算扣成功。需要先讀出來、在程式裡算完再寫回時，用 SELECT … FOR UPDATE 鎖住那一列，其他交易要改同一列就得等這筆交易結束。

把 await 搬走這一招有個前提：檢查和修改之間本來就不需要等待。點餐流程裡有一處做不到，就是加入購物車。

加入購物車：讀和寫中間一定要 await 時怎麼辦？

加入購物車要做三件事：讀出目前的購物車、問價格服務這樣商品多少錢、把商品和新的總額寫回去。問價格那一步必須 await，而新的總額又要用到那個價格，所以沒辦法像扣庫存那樣，把 await 搬到修改之後。王小明在 App 上幾乎同時點了拿鐵和可頌，兩個 addItem 同時開始。執行後看購物車裡有幾樣：

購物車只剩一樣。兩個 addItem 都在 await 之前讀到空的購物車；可頌的價格先回來，先寫入；拿鐵的價格後回來，用它當初讀到的空購物車算出新內容寫入，蓋掉了可頌。又是 lost update。

既然這段程式非 await 不可，就換個方向：不讓兩個 addItem 同時進行。同一台購物車的修改排隊，前一個連同它的 await 整段做完，下一個才開始讀，這樣每次讀到的都是前一個寫完的結果。這種「同一時間只讓一個流程進入某段程式」的機制叫鎖（lock），其他語言常叫它 mutex。

JavaScript 沒有內建的鎖，但第 8 課的 Promise 鏈就能做出來。想法是：用一個變數 tail 記住「目前排在最後的工作」的 Promise；新工作來的時候，用 then 接在 tail 後面，then 的 callback 要等 tail 完成才會執行，於是自然排在它後面；接著把 tail 換成這個新工作，下一個再接在它後面。執行後看購物車是不是兩樣都在、總額對不對：

withLock 裡有兩個寫法要看懂。第一，tail 存的是 result.catch(() => {})，不是 result。前一個工作失敗時，result 是失敗的 Promise，如果直接存它，下一個 tail.then(…) 的 callback 不會執行，會直接跟著失敗，後面排隊的工作全部不做。第 8 課講過 catch 之後鏈恢復成功，所以加上 catch，失敗也算「做完了」，後面照常輪到。第二，回傳給呼叫者的仍是原本的 result：吞掉錯誤只發生在內部的 tail 上，呼叫者照樣知道自己的工作成功還是失敗。

這個版本還不能上線，因為整個程式只有一條隊伍。王小明的購物車和陳美華的購物車毫不相干，卻要互相等。實際上要依 key 排隊：每台購物車（用購物車 id 當 key）各自一條隊伍，不同購物車互不等待，做法是用 Map 記住每個 key 的最後一個工作。還要記得清理：一個 key 的隊伍空了，就要把它從 Map 刪掉；不刪的話，伺服器跑幾天，Map 裡就是幾百萬台早就結帳的購物車，記憶體一直長。練習 3 實作這個依 key 排隊的鎖。

伺服器開了好幾個程序，這把鎖還擋得住嗎？

上面的鎖、Map、tail，全都存在這個 Node 程式的記憶體裡。作業系統裡每一個正在執行的程式叫一個程序（process），每個程序有自己的一份記憶體，看不到別的程序的變數。正式環境為了分擔流量，常常把同一個 Node 伺服器開成好幾個程序，或放在好幾台機器上（Node 課第 24 課、部署課第 13 課）。王小明加拿鐵的請求可能被分到 A 程序，加可頌的請求被分到 B 程序；A、B 各有一份 Map、各有一把鎖，A 程序的鎖擋不住 B 程序，兩個請求照樣同時讀寫。

多個程序要共用的資料（庫存、購物車）通常存在資料庫，排隊也就要交給資料庫：條件式 UPDATE、SELECT … FOR UPDATE 列鎖（PostgreSQL 課第 19 課），或 advisory lock，也就是由應用程式自己決定鎖什麼、由資料庫保管的鎖（PostgreSQL 課第 33 課）。程式裡的鎖只管得到一個程序裡的東西。

就算只有一個程序，後端還有一個前端工程師容易忽略的地方。在 Vue 裡，每個使用者的瀏覽器各跑一份程式，元件裡的變數只屬於那一位使用者；後端剛好相反，一個程序同時服務所有使用者。NestJS 的 service 預設是單例：整個應用程式只建立一個實例，所有請求共用它的欄位（NestJS 課第 3 課）。在 service 的欄位上做「讀 → await → 寫」，就是本課的插隊問題，而且同時有幾十個請求在插。

💡 實務上：前端的「自動儲存」最常需要排隊
後台編輯商品說明時每停頓一下就自動儲存，如果兩次 PATCH 同時在路上、舊的比較晚到，伺服器最後存的就是舊內容，使用者重新整理才發現字不見了。這種「每次都要生效、而且順序要對」的修改，排隊送出（前一個回來才送下一個）是最直接的修法。反過來，查詢類的請求不要排隊，那只會讓畫面變慢，用上一節的「只採用最新的」就好。真正在意資料不能被蓋掉時，資深工程師會再問：別的分頁、別的同事同時改同一筆怎麼辦？那已經超出前端的鎖，要靠後端比對版本或資料庫的鎖。

結帳按兩下：同一件事被觸發兩次，怎麼只做一次？

前兩張單修好了，剩下林志豪的第三張：結帳按了兩下，建了兩張訂單。這種情況叫重複送出（double submit）。它跟購物車不一樣：加入兩樣商品是兩個都要生效的修改，所以排隊各做一次；按兩下結帳，使用者只想要一張訂單，第二次根本不該做。下面模擬使用者在 10ms 內按了兩下，createOrder 被呼叫兩次。執行後看建出幾張訂單：

第一個想到的修法是送出後把按鈕停用（disabled）。它擋得住大部分的連點，應該要做，但不夠：會觸發結帳的不只有按鈕，還有使用者在表單裡按 Enter、程式在逾時後自動重試、畫面沒反應時使用者重新整理再按一次，這些都繞過按鈕的狀態。所以在「呼叫結帳」這一層也要擋：不管誰呼叫、呼叫幾次，同一台購物車同時只能有一個結帳在進行。

這個做法叫單一飛行（single-flight），意思是同一個 key 同時只有一個請求「在飛」。第一次呼叫時真的去執行，並把執行中的 Promise 依 key 記下來；在它結束之前再呼叫，不再執行，直接拿到同一個 Promise，所以兩次點擊的呼叫者都會等到同一張訂單。工作結束（成功或失敗）就清掉紀錄，下一次呼叫重新開始。

寫的時候有兩個坑。第一，失敗也要清掉紀錄。只在成功時清的話，第一次結帳失敗之後，這個 key 的紀錄永遠留著，以後每次呼叫都拿到同一個舊的失敗，使用者再也結不了帳；用第 9 課的 finally，成功或失敗都會清。第二，不要用布林旗標「進行中就忽略」。第二個呼叫者會拿到 undefined，它的畫面不知道訂單成立了沒有；共用同一個 Promise，兩邊都拿得到訂單結果。練習 4 實作這個 singleFlight。

單一飛行和上一節的鎖都用 key 記住一個 Promise，看起來很像，用途不同：

鎖（排隊）單一飛行
第二個呼叫等前一個做完，自己再做一次不做，共用前一個的結果
適合每次都要生效的修改：加入購物車兩樣商品做一次就夠的事：建立訂單、重新整理 token、載入同一份設定
結束後隊伍空了刪掉 key完成就刪掉 key，下一次重新執行

前端的單一飛行只擋得住同一個分頁、同一份程式裡的重複。手機在隧道裡斷線、App 自動重送，請求還是會到伺服器兩次，而且可能落在不同程序上；上一節講過，程序之間看不到彼此的記憶體。所以最後一道防線在後端，靠的是冪等（idempotency）：同一個請求做幾次，結果都跟做一次一樣。建立訂單本身不是冪等的，每做一次就多一張訂單。常見的做法是客戶端每次結帳產生一個冪等鍵（idempotency key），放在請求標頭；伺服器看到用過的 key，就回傳第一次的結果，不建第二張訂單。設計細節在 Node 課第 14 課，系統設計課第 9 課會再深入。

💡 實務上：token 重新整理是單一飛行的經典場景
登入用的 access token 過期時，畫面上同時發出的五個 API 可能一起拿到 401，各自拿 refresh token 去換新的，結果換了五次。很多後端會「輪替」refresh token：每換一次就作廢舊的，這時只有第一個換得到，其他四個拿著作廢的 refresh token 失敗，使用者莫名其妙被登出（細節在 Auth 課第 10 課）。常見做法是在 HTTP 客戶端統一處理 401 的地方（例如 axios 的 interceptor）用單一飛行：第一個 401 去換，其他的等同一個 Promise，拿到新 token 再重送。結帳的重複送出也一樣要前後端一起擋，串金流時先查金流商的 API 是否支援冪等鍵。上線前資深工程師會親手試：結帳按兩下、送出後馬上重新整理、在弱網路下按，看會不會出現兩張訂單。

下次遇到競態：選哪個修法，上線後怎麼找出來？

三張客服單都修完了。回頭看，每個做法各管一種症狀，也各有極限。下次遇到競態，先判斷症狀屬於哪一列：

症狀工具極限
舊結果蓋掉新結果請求序號＋取消上一個只處理「同一個畫面只要最新的」
先檢查再修改被插隊檢查＋修改放同一段同步程式；失敗就補償資料在記憶體裡才有效；資料在資料庫就用條件式 UPDATE
讀和寫中間一定要 await依 key 排隊的鎖只在一個程序裡有效；排隊會變慢
同一件事被觸發兩次單一飛行只在一個程序裡有效；後端要冪等鍵

選對工具之前，得先確定問題真的是競態，修完也要能確認它不再出現。這很難，因為競態取決於時間：同一份程式，順序剛好對了就沒事，開場那三張單在本機才會怎麼試都試不出來。下面三個習慣讓它變得可以重現、可以追查。

第一，讓延遲可以從外面傳入。本課的練習都把 api、audit 當參數傳進去，測試就能故意讓「拿」比較慢，每次重現同一個順序。寫成直接呼叫 fetch 的函式，就只能靠運氣。

第二，log 帶上請求的識別碼和時間。兩筆 log 都寫「庫存 1 → 0」時，有了識別碼和時間，你才看得出那是兩個請求交錯，而不是同一個請求跑了兩次（Node 課第 19 課的 request context）。

第三，用並發測試重現。同時送 20 個相同的請求，數數看賣出幾杯；NestJS 課第 14 課會在 API 上做這個測試。

下面的練習把這課的四個做法各寫一次：搜尋框、扣庫存、依 key 排隊的鎖、單一飛行。

練習

練習 1：createSearch(api, render) 回傳 search(text)。api(text, signal) 回傳搜尋結果的 Promise。要求：只把最新一次搜尋的結果交給 render；送出新搜尋前取消上一個請求；被取消的那次 search 要安靜地完成（不丟錯、不呼叫 render）；其他錯誤要讓 search 以同一個錯誤失敗。注意：有些 api 不理會 signal，被取消了還是會回傳結果。

練習 2：createInventory(initial, { audit })：initial 是 [商品 id, 庫存] 的陣列，回傳 { stockOf(id), reserve(id, qty) }。起始程式的 reserve 先讀庫存、await audit(id, qty) 寫稽核紀錄、再寫回 left - qty，兩個人同時買最後一杯會賣出兩杯。修好它：同時有很多 reserve 時不能超賣、庫存不能變負數；庫存不足丟 OutOfStockError（不呼叫 audit）；只有扣到庫存的才寫稽核紀錄；audit 失敗時 reserve 以同一個錯誤失敗，並把這次扣的數量加回去（不能寫回當初讀到的值）。

練習 3：createKeyedLock() 回傳 { run(key, fn), size }。run(key, fn) 等同一個 key 前面的工作都結束（成功或失敗）才執行 fn，回傳 fn 的結果（Promise）；不同 key 互不等待；前一個失敗不能卡住後面的；size（getter）是目前還有工作在跑或在排隊的 key 數量，全部結束後要回到 0。用 Promise 鏈實作：每個 key 記住最後一個工作。

練習 4：singleFlight(fn) 回傳 run(key)。fn(key) 回傳 Promise。同一個 key 進行中時，再呼叫 run(key) 拿到同一個 Promise、fn 不會再執行；結束（成功或失敗）後同一個 key 可以重新開始；不同 key 互不影響。

練習 5：搜尋框加了 300ms 的 debounce。還會出現舊結果蓋掉新結果嗎？

✓ debounce 只決定「什麼時候送」：打「拿」、停 400ms、再打「拿鐵」，兩個請求都會送出，慢的「拿」照樣可以最後回來。它沒有讓前一個請求停下，所以 a 錯；HTTP 請求各自獨立，回來的順序取決於伺服器處理多久，瀏覽器不會幫你排序，所以 c 錯。debounce 減少請求數，順序要靠請求序號加上取消上一個。

練習 6：JavaScript 只有一條執行緒。async 函式裡「讀庫存 → await 寫稽核紀錄 → 扣庫存」，同時有兩個請求進來時會怎樣？

✓ 單執行緒只保證兩個 await 之間的同步程式不會被打斷。函式停在 await 時，event loop 會去跑別的工作（第 7 課），第二個請求就在這時讀到還沒扣的庫存。整個 async 函式不會自動排隊，所以 a 錯；這跟 Worker 無關，一般的 Node 伺服器就會發生，所以 b 錯。修法：檢查和扣減放在同一段同步程式，或讓資料庫用條件式 UPDATE 一句完成。

練習 7：你用 Promise 鏈做了依 key 排隊的鎖，保護「讀購物車 → await 查價格 → 寫購物車」。部署時伺服器開成 3 個程序，購物車存在 PostgreSQL。這樣還安全嗎？

✓ Map 和 Promise 都存在單一程序的記憶體裡，程序之間不共用（同一台機器也一樣，所以 b、c 錯）。同一台購物車的兩個請求如果被分到不同程序，各自拿到自己的鎖，照樣同時讀寫。資料在資料庫，就讓資料庫把關：SELECT … FOR UPDATE、條件式 UPDATE，或 advisory lock。

常見錯誤

  • 以為單執行緒就不會有競態：每個 await 都是插隊點，函式暫停時別的流程可以讀寫同一份資料。
  • 以為 debounce 能解決過期回應：它只減少請求數，使用者一停頓，兩個請求照樣都送出。用請求序號只採用最新的，並取消上一個請求。
  • 取消之後把 AbortError 丟給呼叫者：自己取消的請求要安靜結束，不然變成 unhandled rejection；但其他錯誤不能一起吞掉。
  • 在 await 之前讀、await 之後寫共用的狀態：寫回去的值根據的是過期的資料。檢查和修改放在同一段同步程式；中間一定要 await 時用鎖，或交給資料庫。
  • 失敗時把舊值寫回去：會蓋掉別人在這段時間的修改。補償要做「反向操作」（加回扣掉的數量），不是「還原快照」。
  • 用程式裡的鎖保護多個程序共用的資料：每個程序各有一份鎖。共用的資料用資料庫的列鎖、條件式 UPDATE 或 advisory lock。
  • 鎖或去重的 Map 沒在失敗時清掉，或永遠不刪：失敗沒清，這個 key 永遠卡住或永遠拿到同一個錯誤；永遠不刪，長時間執行的伺服器記憶體一直長。用 finally 或 .catch 之後清。
  • 只在前端擋重複送出：重試和網路重送會繞過按鈕。後端用冪等鍵認出重送的請求。

補充與查表

Vue 的 watch 怎麼搭配取消

Vue 的 watch 也在處理過期回應：Vue 3.5 起可以在 watch callback 裡呼叫 onWatcherCleanup(() => controller.abort())，監看的值改變、callback 要重跑之前會先取消上一次的請求；它必須在 callback 同步執行的時候呼叫，不能寫在 await 之後（Vue 官方文件）。細節在 Vue 課第 5 課和第 17 課。

小結

  • 競態是「結果取決於誰先完成」。JavaScript 單執行緒，但每個 await 都是插隊點：await 之前讀到的東西，回來時可能已經過期。
  • 搜尋框的過期回應：請求序號只採用最新的，加上 AbortController 取消上一個；被取消的安靜結束。debounce 只決定什麼時候送，不保證順序。
  • 最後一杯拿鐵的先檢查再行動：檢查和修改放在同一段沒有 await 的同步程式；後面的步驟失敗用補償（加回去），不寫回舊值。
  • 購物車這種讀和寫中間一定要 await 的修改，用 Promise 鏈做依 key 排隊的鎖：失敗不能卡住後面，隊伍空了要刪 key。
  • 結帳按兩下用單一飛行共用同一個 Promise，結束後在 finally 清掉；鎖是排隊各做一次，單一飛行是共用一次的結果。
  • 程式裡的鎖和去重只在一個程序裡有效。多個程序、多台伺服器要靠資料庫（條件式 UPDATE、列鎖、advisory lock）和冪等鍵。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：店長按下「匯出整年訂單」之後，同一時間點餐、結帳的 API 全部變慢。這支匯出 API 在一個大迴圈裡組 CSV 字串，同事提議「把迴圈包進 new Promise 就不會擋到別人」。怎麼回應？

✓ executor 是同步執行的，Promise 不會多出一條執行緒，迴圈跑多久，所有請求就等多久。切塊時讓出到 task（setTimeout），或交給 worker、背景工作。b 錯在 await Promise.resolve() 只排進 microtask，event loop 會先清空 microtask 才輪到下一個 task，新請求、計時器還是等不到。（第 7 課）

練習 9：結帳寫成 await Promise.all([charge(card, total), deductStock(items)])。扣庫存因為缺貨失敗了，會怎樣？

✓ Promise.all 遇到第一個失敗就跟著失敗，但其他工作照樣跑完，扣款、寄信這類副作用照樣發生。會改資料而且有先後關係的動作要依序做，或交給後端用交易處理。b 錯在 Promise 只是代表結果的物件，沒有取消的能力；要停下工作得自己傳 AbortSignal。（第 8 課）

練習 10：後台要把 3000 個商品同步到外送平台，每個商品呼叫一次對方的 API，對方文件寫了限流規定。該怎麼排？

✓ 數量大、互不相依時用工作池：同時最多 N 個，做完一件立刻接下一件，實務上多半用 p-limit 這類套件。a 錯在 3000 個請求同時打出去，會被對方限流，也會佔滿自己的連線。（第 9 課）

練習 11：Node 24 的結帳 API 這樣寫，lint 沒有報錯，程式也沒有註冊 unhandledRejection 監聽器。sendReceipt 因為信箱打錯而失敗時，會怎樣？

  return { ok: true }
}

✓ void 只是讓 no-floating-promises 閉嘴，不處理 rejection，也不改變執行時的行為；Node 15 起預設會讓程序結束，正在處理的請求一起中斷。射後不理要寫 sendReceipt(order).catch(err => log.error(err))；收據一定要寄到，就先寫進工作佇列由背景工作重試。a 錯在把「不等」當成「處理過了」。（第 9 課）

練習 12：每晚把金流的交易一頁一頁拉回來對帳，共 200 頁。程式先把所有頁放進陣列再處理，資料量變大後程序開始記憶體不足。怎麼改最直接？

✓ 全部載入陣列，所有頁同時在記憶體，第一筆也要等全部抓完。非同步產生器是拉取模式：消費者不拿，生產者就不動，記憶體只有目前這一頁，這就是背壓。b 錯在同時抓 200 頁，記憶體裡一樣是 200 頁，還多了 200 個同時進行的請求。（第 10 課）

練習 13：結帳 API 在入口建立 AbortSignal.timeout(3000)，時間到就回 504。上線後發現：回了 504 的訂單，事後在金流後台常常看到扣款成功。最可能的原因是？

✓ 逾時只會通知收到 signal 的那一層；中間任何一層沒把 signal 交給下一層，最底層的請求就照樣跑完。每一層都把 signal 傳下去，直到真正在等的那一層。d 錯在這裡的請求根本沒被中斷：它沒收到 signal，所以照樣跑完、照樣扣款。（第 11 課）

練習 14：下面的程式在稽核紀錄寫入失敗時「還原庫存」。單獨測試都正常，上線後偶爾庫存會變多。哪裡出事？

const before = stock.get(id)
if (before < qty) throw new Error('庫存不足')
stock.set(id, before - qty)
try {
  await writeAudit(id, qty)
} catch (e) {
  stock.set(id, before)
  throw e
}

✓ 停在 await writeAudit 的期間，別的請求可能扣過庫存；寫回當初讀到的值，就把它們的扣減一起抹掉了。補償做反向操作：stock.set(id, stock.get(id) + qty)。a 錯在講反了：檢查和扣減放在同一段沒有 await 的同步程式，正是不會被插隊的寫法。（第 12 課）

練習 15：訂單列表切換「今天／本週」時，你已經在送出新請求前 abort() 上一個。同事說「既然取消了，就不用再比對請求序號」。對嗎？

✓ 取消減少浪費，但結果可能早一步回來，也不是每個 api 都理會 signal；序號（或檢查 signal.aborted）才保證畫面只採用最新的。被取消的請求以 AbortError 失敗，要安靜結束。a 錯在忽略了時間差：結果已經回來、在佇列裡等著時，abort() 改變不了它。（第 12 課）
