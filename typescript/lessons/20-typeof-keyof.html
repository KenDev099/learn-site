階段 4：函式、泛型與型別運算 · 第 20 課

從值推導型別：typeof、keyof、as const、satisfies

第 17 課的斷言函式裡，訂單狀態寫了兩次：一次是 type OrderStatus = 'pending' | …，一次是 ORDER_STATUSES 陣列。現在店裡要支援退款，得加一個 'refunded' 狀態。如果有人只改了型別、忘了改陣列，驗證就會把合法的退款訂單擋掉；反過來只改陣列，型別又不認得它。兩種情況都不會出現任何紅線，要等客人或客服回報才知道。

回頭盤點咖啡店後台的訂單模組，同樣「一份資訊寫兩次」的地方其實有四處：狀態的型別和狀態陣列；排序、表格欄位用 string 收欄位名稱；狀態、付款方式、尺寸各有一張對照表；查詢函式回傳的形狀，呼叫端又手抄一份型別。這一課的任務是把這四處都改成只寫一次，其他從它推導：加 'refunded' 時只改一個地方，其餘的不是自動跟上，就是由 TypeScript 用紅線指出漏改的位置。第一處的答案只要一行：

type OrderStatus = (typeof ORDER_STATUSES)[number]   // 型別從陣列推出來，陣列改了型別跟著改

這一行用了三個你還沒學過的型別寫法。前兩節把它拆開來，後面幾節再用同樣的工具處理另外三處。

這課的路線：
  1. 型別位置的 typeof、keyof 與索引存取：怎麼向 TypeScript 要「這個值的型別」，再從型別裡取出一部分；讀完就看得懂開場那一行（開場問題的最小答案）。
  2. 第一處，狀態清單：為什麼要加 as const，怎麼讓型別、驗證、下拉選單共用同一份陣列。
  3. 第二處，欄位名稱：用 keyof 加泛型，讓 getField、排序函式只收物件真的有的鍵。
  4. 第三處，對照表：satisfies 怎麼在漏了一個鍵時立刻報錯，又保留精確的值。
  5. 第四處，查詢結果：用 ReturnType、Awaited 從函式推出型別、什麼時候不該這樣做，以及為什麼方向只能是值 → 型別。
這課會用到：
  • 第 15 課的字面值型別與 as const：as const 讓陣列變成唯讀 tuple，'paid' 不會被放寬成 string。
  • 第 17 課的 ORDER_STATUSES 與斷言函式 asserts x is T：用陣列驗證外部送來的狀態；includes 不接受 unknown，所以改用 some。
  • 第 19 課的泛型約束：T extends { id: number } 限制 T 至少要有什麼。
  • 第 14 課的 Record<K, V>（鍵是 K、值是 V 的物件），以及 Object.keys 回傳 string[]。

怎麼向 TypeScript 要「這個值的型別」？型別位置的 typeof

要讓狀態型別從陣列推出來，第一步是能對 TypeScript 說：「這個值是什麼型別，直接給我。」先用一個比陣列更容易看清楚的例子。後台有一份預設訂單 defaultOrder，建立訂單的表單從它複製一份開始填。如果另外手寫一份 type Order = { … }，就跟開場一樣：預設訂單多了欄位，型別沒跟著改，兩邊遲早不一致。

要讀懂接下來的寫法，先分清楚 TypeScript 檔案裡的兩種位置。一種是值的位置：變數、函式呼叫、if 的條件，這些是執行時真的會跑的運算式，編譯成 JavaScript 之後還在。另一種是型別的位置：冒號後面的型別註記、type X = 的右邊、<> 裡的型別參數，這些只給編譯器檢查用，編譯後整個刪掉。同一個關鍵字放在不同位置，意思可以完全不同，typeof 就是這樣。

你在 Vue 裡寫過 typeof x === 'string'。那是值位置的 typeof，也就是 JavaScript 本來就有的 typeof：執行時才算，結果是 'object'、'string' 這類字串。把 typeof 寫在型別的位置，例如 type Order = typeof defaultOrder，意思變成「把 defaultOrder 在編譯時推論出的型別整個拿出來」。這個用法叫型別查詢（type query）。它拿到的不是一個字串，而是完整的物件型別，每個欄位、每個欄位的型別都在。

執行下面這格後看兩個地方：滑鼠移到 Order 上，看編譯器推出的型別；Console 印出的 object 則是同一個關鍵字在執行時的結果。

注意 note: null as string | null 這一段。從值推導型別，值寫得多精確，型別就多精確。如果只寫 note: null，推出來的 note 型別就只有 null，之後要填「少冰」會報錯。值本身沒表達出來的事（這個欄位之後會放字串），要在值上補清楚，推出來的型別才會對。

型別位置的 typeof 能接哪些東西，有一些限制，細節見課末「補充與查表」。現在對 ORDER_STATUSES 寫 typeof ORDER_STATUSES，拿到的是整個陣列的型別。但開場要的不是整個陣列，而是「陣列裡任一個元素」的型別。這需要從型別裡取出一部分。

怎麼從型別裡取出一部分？keyof 與索引存取

拿到整個型別之後，下一步是從裡面取出需要的那一塊。JavaScript 裡你常對物件做兩件事：列出它有哪些鍵、用鍵取出某個屬性的值。型別的位置也有對應的兩個工具，寫法刻意跟 JavaScript 很像。

這節改用前幾課一直在用的商品型別 Product。它的欄位型別各不相同（string、number、boolean），取出不同欄位時，拿到的型別差別最容易看出來。

第一個是 keyof T：物件型別 T 所有鍵的名稱，組成一個字面值聯合。例如 Product 有 id、name、price、isAvailable 四個欄位，keyof Product 就是 'id' | 'name' | 'price' | 'isAvailable'。它回答的是「這個型別有哪些鍵」。

第二個是索引存取型別（indexed access type）：在型別位置寫 Product['price']，得到 price 這個欄位的型別 number。寫法跟執行時的 product['price'] 一模一樣，差別在於執行時拿到的是值 110，型別位置拿到的是型別 number。方括號裡也可以放聯合：Product[keyof Product] 等於把四個鍵一次放進去，得到所有欄位型別的聯合。

陣列也能用索引存取。陣列的鍵是數字，所以在型別位置寫 [number]，意思是「用任何一個數字索引，取到的東西是什麼型別」，也就是元素的型別。下面這格的 MENU 是一個菜單陣列，(typeof MENU)[number] 就是先用上一節的 typeof 拿到陣列型別，再用 [number] 取出一個菜單品項的型別。

執行前先看每一行右邊的註解，再把滑鼠移到型別名稱上對照；倒數第二行是故意寫錯的，看它的紅線。

倒數第二行的錯誤很常見。keyof 只能接型別，latte 卻是一個值（執行時存在的變數），所以 TypeScript 報 TS2749，提醒你這裡要的是型別。要對值取鍵，先用 typeof 把值轉成型別，再取鍵：keyof typeof latte。這個「先 typeof 再 keyof」的組合後面會一直出現。

到這裡就拆得開開場那一行了。(typeof ORDER_STATUSES)[number] 由內往外讀：typeof ORDER_STATUSES 拿到陣列的型別，[number] 再取出「任一個元素」的型別。陣列多一個 'refunded'，元素的型別就多一個，不用再手寫。

但如果陣列是用一般的方式寫的，沒有加 as const，這一行推出來的只會是 string，什麼都擋不住。為什麼會這樣、怎麼修，就是下一節要解決的第一處重複。

第一處：狀態清單怎麼只寫一次？as const 加 typeof

先看上一節留下的問題。TypeScript 推論 const LOOSE = ['pending', 'paid', …] 的型別時，要猜你之後會怎麼用這個陣列。陣列可以 push、可以改其中一格，之後放進去的可能是任何字串，所以它推論成 string[]，而不是只允許這四個值。這個從字面值變成寬型別的過程叫放寬（widening）。放寬發生在推論陣列的那一刻，字面值的資訊就丟了；之後再怎麼用 [number] 取，取到的也只是 string。

第 15 課的 as const 就是用來告訴 TypeScript「這個陣列不會變」：陣列變成唯讀的 tuple，每個元素保留自己的字面值型別。tuple 是長度固定的陣列，每一格的型別各自記住，不會合併成同一個型別。既然不能 push、不能改，TypeScript 就不必為了未來的變動而放寬。

下面這格把兩種寫法並排。執行前先比較 LooseStatus 和 OrderStatus 兩個型別；執行後 Console 印出的下拉選單，是同一份陣列在執行時的用途。

加了 as const 之後，再拆一次 (typeof ORDER_STATUSES)[number]：typeof ORDER_STATUSES 是 readonly ['pending', 'paid', 'done', 'cancelled']，[number] 取出「用任何數字索引拿到的元素」，也就是四個字面值的聯合。

這種做法叫單一來源（single source of truth）：同一份資訊只寫在一個地方，其他都從它推導。訂單狀態需要同時存在於兩個世界：執行時要一個陣列，用來驗證 API 送來的值、畫下拉選單；編譯時要一個聯合型別，用來檢查程式。為什麼從陣列出發，而不是從型別出發？因為型別編譯後就消失了，生不出執行時的陣列；陣列卻能透過 typeof 推出型別。這個方向的理由，最後一節會再完整講一次。

回到開場的退款需求：現在新增 'refunded' 只要在陣列加一個字串。OrderStatus 自動多一個成員，用 ORDER_STATUSES.some(…) 寫的驗證自動認得它，用 ORDER_STATUSES.map(…) 畫的選單自動多一個選項。

清單有時不只是一串名字，每個名字還帶著對應的資料，例如付款方式要顯示中文標籤。這時把清單寫成物件，鍵就是付款方式，值是標籤，同樣加 as const。要取鍵就用上一節的 keyof typeof，要取值就用索引存取。執行後看 labelOf('linePay') 印出的標籤，以及滑鼠移到 PaymentMethod、PaymentLabel 上的型別：

💡 實務上：先問「這份清單歸程式管，還是歸資料庫管」
訂單狀態、付款方式這類跟程式邏輯綁在一起的清單，用 as const 寫在程式裡：後台的篩選下拉選單、API 收到狀態時的驗證、狀態對應的中文標籤，全部讀同一份。但如果店長要能在後台自己新增商品分類，那份清單就該放在資料庫，從 API 取得，寫死成 as const 反而每次新增都要改程式、重新部署。前後端都在同一個 repo 時，常把這類常數放在共用的模組，兩邊 import 同一份，避免前端的選單比後端多一個狀態。

狀態清單有了單一來源。第二處重複在欄位名稱：排序、表格欄位設定都用 string 收欄位名，打錯字一樣沒有紅線。

第二處：排序和取欄位的函式，怎麼只收真的有的鍵？

後台的訂單列表、商品列表都要能排序，排序函式常寫成 sortBy(list, key: string)。key 宣告成 string，任何字串都收：傳 'pirce'（price 拼錯）不會報錯，執行時每一筆取到的都是 undefined，排序結果就是亂的。我們要的是「key 只能是這個物件真的有的欄位名稱」。

上一節的 keyof 正好描述「真的有的鍵」。如果函式只處理 Product，參數寫成 key: keyof Product 就夠了。但排序、取欄位這類函式要給商品、訂單、顧客共用，物件的型別不固定，所以要結合第 19 課的泛型：用型別參數 T 代表「傳進來的物件是什麼型別」，再宣告第二個型別參數 K extends keyof T，意思是「K 必須是 T 的某一個鍵」。先從最小的版本 getField(obj, key) 開始，它只做一件事：回傳 obj[key]。

執行前看兩件事：price、name 兩個變數各是什麼型別，以及 'pirce' 那一行的紅線。

呼叫 getField(latte, 'price') 時，TypeScript 從第一個引數推出 T 是 Product，從第二個引數推出 K 是字面值 'price'，並檢查 'price' 確實屬於 keyof Product。回傳型別寫成 T[K]，代入後就是 Product['price']，也就是 number。傳 'pirce' 時，它不屬於 keyof Product，約束不成立，所以報 TS2345。

為什麼要另外宣告一個 K，而不是直接寫 key: keyof T？因為 K 會記住你傳的是哪一個鍵。如果參數寫成 key: keyof T，回傳就只能寫 T[keyof T]，也就是所有欄位型別的聯合 string | number | boolean；明明取的是價格，呼叫者拿到的卻可能是字串或布林，還得自己再縮小一次。練習 2 會讓你把同樣的寫法用在 pluck 上。

keyof 描述的是「這個物件至少有這些鍵」。所以 Object.keys 的回傳型別還是 string[]，不是 (keyof Product)[]，原因見課末「補充與查表」。

💡 實務上：表格欄位、排序參數最常用到 keyof
咖啡店後台的訂單列表，欄位設定常寫成 { key: keyof Order; title: string }[]，排序函式寫成 sortBy(list, key)；有人把 createdAt 改名成 created_at，所有用到舊名稱的欄位設定立刻出現紅線，不用等客服回報「某一欄變空白」。要注意的是 keyof 只管編譯時：網址上的 ?sort=price 是使用者送來的字串，還是要先用執行時的白名單檢查，不能直接當成 keyof Order 用。

欄位名稱也接上了來源。第三處重複是各種對照表：每個狀態的標籤顏色、每種付款方式的文字、每個尺寸的加價。加 'refunded' 時最容易漏改的，就是這些散在各處的表。

第三處：對照表漏了一個鍵，怎麼在寫的當下就知道？satisfies

對照表需要同時做到三件事：每個鍵都要有、不能多出別的鍵，而且值要精確，TypeScript 要知道某個鍵對應的就是那個值。這一節用飲料尺寸的加價表當例子：只有 S、M、L 三個鍵，值是數字，最容易看出值的字面值有沒有留下來。節尾再把同樣的寫法套回訂單狀態。

先釐清一個名詞。型別註記就是在變數名稱後面寫冒號和型別，例如 const x: T = …。它的意思是「這個變數的型別就是 T」：TypeScript 會檢查右邊的值符合 T，然後變數的型別就定為 T，值本來推論出的精確型別被丟掉。這個「丟掉」正是對照表的麻煩所在。

下面是兩種常見的寫法，各缺一樣東西。執行前看 A、B 兩個型別；執行後看 Console 印出的 xl。

  • 寫法一，註記成 Record<Size, number>：鍵有檢查，少了 L 或多了 XL 都會報錯。但變數的型別被註記定成「每個值都是 number」，EXTRA_A['M'] 只知道是 number，不知道是 10。
  • 寫法二，註記成 Record<string, number>：任何字串鍵都收，L 拼成 LL 也不報錯。取不存在的 EXTRA_B.XL 時，型別說是 number，執行時卻是 undefined；keyof 也只剩 string，具體的鍵全丟了。

我們要的是寫法一的檢查，加上不被丟掉的精確型別。這就是 satisfies T 做的事：它寫在值的後面，意思是「檢查這個值符合 T，但變數的型別照樣用推論出來的」。檢查和推論被拆開了：T 只用來驗收形狀，不會蓋掉值本來的型別。

執行前看 M、Keys、PlainM 三個型別，再看 BAD 那一行的紅線。看完之後，試著把 EXTRA 裡的 L 刪掉，確認少一個鍵也會報錯。

PLAIN 只有 satisfies，PlainM 卻是 number，因為 satisfies 不改變推論，而一般的推論本來就會把物件屬性的 10 放寬成 number（屬性之後可以被改）。要留下字面值 10，還是要靠 as const。所以 as const satisfies 的順序是：先用 as const 鎖住字面值，再拿去檢查形狀；兩個合起來，同時得到「鍵剛好是這幾個」和「值是精確的字面值」。四種寫法的差別：

寫法少鍵、多鍵會報錯值保留字面值keyof
: Record<string, V>不會不會string
: Record<Size, V>會不會Size
satisfies Record<Size, V>會不會（照一般推論）Size
as const satisfies Record<Size, V>會會，而且唯讀Size

把 Size 換成第一處推出的 OrderStatus，就是退款需求要的效果：每一張以狀態為鍵的表都寫成 as const satisfies Record<OrderStatus, …>，陣列加了 'refunded' 之後，OrderStatus 多一個成員，每一張還沒補上退款的表都會報「少了 refunded」。練習 3 用商品分類的標籤表練同一個寫法：表裡漏了一個分類，你要讓 TypeScript 當場報錯。

💡 實務上：寫死的設定表用 as const satisfies，會變的變數用註記
常見的對照表：訂單狀態對應的標籤顏色、路由名稱對應的路徑、各環境的 API 網址。用 as const satisfies Record<OrderStatus, string>，新增 'refunded' 狀態時，每一張漏掉它的表都會報錯，不會等到畫面上出現沒有顏色的標籤才發現。變數之後會被重新指定、或你本來就要它是寬的型別（例如 let draft: Order），用註記就好。satisfies 對 TypeScript 版本有要求，舊專案先看 package.json 的版本再用，版本見課末。

對照表也接上了。最後一處重複在函式：查詢函式回傳什麼形狀由它的實作決定，呼叫端卻又手抄一份型別。

第四處：查詢結果的型別，能不能不要手抄？ReturnType、Parameters、Awaited

同樣的重複也發生在函式上。createOrder 的參數型別寫在函式簽章裡，呼叫它的 controller 要先組好一份同樣形狀的資料，如果再手寫一次型別，就是兩份。查詢函式也一樣：它回傳的形狀由查詢內容決定，呼叫端手抄一份，查詢多選一個欄位時，手抄的那份就過期了。

解法還是第一節的 typeof。函式在 JavaScript 裡也是值，所以 typeof createOrder 拿得到它的函式型別，裡面包含參數和回傳值的型別。接著需要的是從函式型別裡取出一部分，就像第二節從物件型別取出一個欄位。TypeScript 內建三個工具型別做這件事，它們跟第 19 課的 Paginated<T> 一樣，是收一個型別、產生另一個型別的泛型型別：

  • ReturnType<F>：函式型別 F 的回傳型別。
  • Parameters<F>：F 的參數型別，依順序排成一個 tuple。[0] 取第一個參數，寫法就是第二節的索引存取。
  • Awaited<T>：T 是 Promise 時，取出它完成後的值的型別；巢狀的 Promise 也會一層層拆開，跟 await 的行為一樣。

為什麼需要 Awaited？async 函式一定回傳 Promise，所以對 async 函式用 ReturnType，拿到的是 Promise<…>。但呼叫端真正拿來用的是 await 之後的值，所以要再用 Awaited 拆掉 Promise 這一層。

下面這格有兩個函式：createOrder 代表寫入，loadMenu 是一個模擬查詢菜單的 async 函式，它回傳什麼形狀由查詢內容決定。執行前把滑鼠逐一移到四個型別上，特別比較 MenuPromise 和 Menu 差了哪一層。

後端常見的用法：ORM 查詢的回傳型別由查詢內容決定（選了哪些欄位、join 了什麼），手寫很累也容易寫錯，就用 Awaited<ReturnType<typeof findOrderWithItems>> 拿。Prisma 這類工具常這樣用，NestJS 課也會看到。陣列裡的一筆再用第二節的 [number] 取出來，練習 4 的 SummaryItem 就是這樣寫。

不過，從實作推導出來的型別有一個代價：它會跟著實作悄悄改變。這在模組內部是優點，在對外的地方卻可能是事故。

資深取捨：對外的型別寫明確。從實作推導的型別，會跟著實作悄悄變：有人在 loadMenu 的查詢多選了 cost_price，推導出來的 Menu 就多一個欄位，前端也收得到成本價，沒有任何紅線。模組內部、測試、一次性的輔助函式，放心推導；API 回應、套件對外的函式、跨團隊的合約，回傳型別寫明確，讓實作改壞時錯誤出現在函式裡。下一課會再談推導與獨立定義的取捨。

四處重複都處理完了。回頭看會發現，這一課每個工具都是從值推出型別。那能不能反過來，從型別做出值？

為什麼方向只能是值 → 型別？

這一課所有的工具都是同一個方向：從值得到型別。反過來不行。type OrderStatus = 'pending' | 'paid' 是寫在型別位置的東西，編譯後整個消失（第 13 課），執行時沒有任何東西可以拿來 .map 或 .includes。這就是第一處為什麼從陣列出發：只有值能活到執行時。

所以遇到一份清單或一種形狀時，先問它在執行時需不需要存在，再決定從哪裡出發：

需要的東西                            從哪裡出發
只在編譯時檢查                        寫 type 就好
編譯時要檢查，執行時也要列舉／驗證     寫 as const 的值，用 typeof 推出型別
執行時要驗證複雜的物件                 用 zod 這類 schema 函式庫，再 z.infer 推出型別

第三列是同一個想法的延伸（第 26 課）：API 收到的整個請求物件，光靠 some 檢查一個字串不夠，要逐欄驗證。schema 是值，執行時能驗證；型別從它推導，兩邊永遠一致。

回到開場的退款需求，現在的狀態是：加 'refunded' 只改 ORDER_STATUSES 一處；OrderStatus、驗證、下拉選單自動跟上；每一張 as const satisfies Record<OrderStatus, …> 的對照表會報錯，提醒你補上退款的那一格；欄位名稱和查詢結果的型別，則從物件與查詢函式推出來。下面四題動手題依序對應這四處。

練習

練習 1：起始程式的訂單狀態只是 string，守衛也只檢查是不是字串。改成單一來源：

  • ORDER_STATUSES 的型別是 readonly ['pending', 'paid', 'done', 'cancelled']。
  • OrderStatus 從 ORDER_STATUSES 推導出來（四個字面值的聯合），不要再手寫一次。
  • isOrderStatus 用同一份陣列判斷：四種狀態回傳 true，其他任何值（包括拼錯的 'payed'）回傳 false。

練習 2：寫兩個泛型函式，對任何物件都能用：

  • getField(obj, key)：回傳 obj[key]。
  • pluck(items, key)：回傳每一筆的 key 欄位組成的新陣列，例如 pluck(menu, 'name') 是 ['美式咖啡', '拿鐵', '可頌']。

key 只能是物件真的有的鍵，回傳型別要跟著那個鍵走：pluck(menu, 'price') 是 number[]，不是 (string | number | boolean)[]。

練習 3：CATEGORY_LABEL 註記成 Record<string, string>，漏了餐點（food: '餐點'）也沒人發現，labelOf('food') 回傳 undefined。改寫成：三個分類剛好都有（少一個或多一個都會報錯），而且 CATEGORY_LABEL.coffee 的型別是字面值 '咖啡'。labelOf 的參數型別保持 Category。

練習 4：loadOrderSummary 的回傳型別是推論出來的，不要手抄它的形狀：

  • OrderSummary：loadOrderSummary 完成後拿到的值的型別。
  • SummaryItem：OrderSummary 裡 items 陣列的一個元素。
  • formatSummary(s: OrderSummary)：回傳 #1 王小明（台北）拿鐵×2、可頌×1；city 是 null 時括號裡寫「自取」。

練習 5：type T = typeof price 和 if (typeof price === 'number') 裡的 typeof 有什麼不同？

✓ 寫在型別位置的 typeof 是型別查詢，只在編譯時存在，結果可以是完整的物件型別。寫在運算式裡的是 JavaScript 的 typeof，執行時回傳八種字串之一。a 錯在型別不存在於執行時；b 把兩者講反了。

練習 6：const SIZES = ['S', 'M', 'L']（沒有 as const），type Size = (typeof SIZES)[number] 是什麼？

✓ 陣列之後可以 push 別的字串，所以推論成 string[]，取元素型別得到 string。要得到 a，陣列要加 as const。c 是加了 as const 之後 typeof SIZES 本身的型別，還沒有取 [number]。

練習 7：const PRICES: Record<string, number> = { latte: 110 }，接著寫 PRICES.mocha * 2 會怎樣？

✓ Record<string, number> 說「任何字串鍵都對應 number」，所以 mocha 也是 number，型別檢查完全放行（第 14 課）。註記越寬，TypeScript 知道的越少，不是越安全。c 要開 noUncheckedIndexedAccess 才會發生（第 25 課）。要抓拼錯的鍵，用 as const satisfies Record<Drink, number> 這類寫法，把鍵限定在 Drink 這個聯合。

常見錯誤

  • 忘了 as const：陣列推論成 string[]，(typeof X)[number] 就只是 string，型別看起來有、其實什麼都沒擋。
  • 型別和清單各寫一份：久了一定不同步。從 as const 的值推導型別，只改一個地方。
  • 對值寫 keyof：keyof latte 報 TS2749，要寫 keyof typeof latte。
  • key 參數寫成 keyof T 而不是另一個型別參數 K：回傳只能是 T[keyof T]，所有欄位型別混在一起。
  • 用寬的註記（Record<string, …>）：具體的鍵全丟了，拼錯、漏掉都不報錯。對照表用 as const satisfies Record<K, V>。
  • 對 async 函式用 ReturnType 卻忘了 Awaited：拿到的是 Promise<…>，要再包一層 Awaited。
  • 公開 API 的型別完全從實作推導：實作一改，對外的形狀就悄悄跟著變。對外的回傳型別寫明確。

小結

  • 型別位置的 typeof x 在編譯時取得變數的型別；運算式裡的 typeof 是執行時的字串。
  • keyof T 是所有鍵的聯合；T['price']、T[K]、T[number] 取出成員型別。對值取鍵要寫 keyof typeof x。
  • 第一處，狀態清單：const X = [...] as const，type T = (typeof X)[number]；物件用 keyof typeof X。沒有 as const，字面值在推論時就被放寬成 string。
  • 第二處，欄位名稱：<T, K extends keyof T> 只收真的有的鍵，回傳 T[K] 跟著鍵走。
  • 第三處，對照表：satisfies 檢查但不改變推論的型別；as const satisfies Record<K, V> 同時得到正確的鍵和字面值，來源多一個成員時每張漏掉的表都會報錯。
  • 第四處，函式：Awaited<ReturnType<typeof f>>、Parameters<typeof f>[0] 從函式推導；對外的型別寫明確。
  • 方向永遠是值 → 型別。執行時也需要的東西，從值出發。

補充與查表

主線用不到、但查資料或遇到問題時會用到的細節，查表用，不用背。

  • 型別位置的 typeof 能接什麼：型別位置的 typeof 只能接值的名稱（變數、函式、屬性路徑如 typeof config.db），不能接 typeof 110 或函式呼叫。
  • 為什麼 Object.keys(latte) 是 string[]：第 14 課講過，結構型別允許傳進形狀更大的物件，執行時的鍵可能比型別寫的多。keyof 描述「至少有這些鍵」，不保證「只有這些鍵」。
  • 版本：satisfies 是 TypeScript 4.9 加入的，Awaited 是 TypeScript 4.5 加入的。舊專案先看 package.json 的 typescript 版本再用。
