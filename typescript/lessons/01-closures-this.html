階段 1：JavaScript 的核心機制 · 第 1 課

閉包與 this：函式記得什麼

咖啡店的點餐系統加了兩個小功能，上線第一天就收到兩張 bug 單。第一張來自吧台：叫號螢幕應該依序叫「第 1 杯」「第 2 杯」「第 3 杯」，結果三次都叫成「第 4 杯」。第二張來自櫃台：按下「10 秒後自動結帳」，10 秒後沒有結帳，主控台多了一行 TypeError: Cannot read properties of undefined (reading 'length')。兩段程式都很短，寫的人看了好幾遍都覺得沒錯。

兩個 bug 的形狀一樣：程式把一個函式交給 setTimeout，由 setTimeout 在之後呼叫它。這種交給別人、之後由別人呼叫的函式叫 callback（回呼函式）。你在 Vue 裡天天寫 callback：事件處理函式、watch 的處理函式、交給 setTimeout 的函式都是。這一課要回答的問題是：函式被交出去、晚一點才在別的地方執行時，它裡面用到的變數和 this 是從哪裡來的？答案是兩條規則：

  • 變數看函式在哪裡出生，也就是寫在哪裡。
  • this 看函式怎麼被呼叫。

學完你能修好這兩張 bug 單，看懂 Vue 的 composable 為什麼每次呼叫都有自己的一份狀態，也知道把方法交出去之前該檢查什麼。後面的課都建立在這兩條規則上：第 12 課處理「兩個請求誰先回來不一定」的問題，要靠閉包記住請求編號；後端框架 NestJS 的 class 要靠 this 拿到框架幫你準備好的物件。這兩條規則沒弄懂，bug 會出在「有時候對、有時候錯」的地方，最難查。

這課的路線：
  1. 函式在別處被呼叫時，它用的變數是哪一個：看寫在哪裡，不看在哪裡被呼叫。
  2. 外層函式都執行完了，變數為什麼還在：閉包，用集點卡看每次呼叫怎麼各有一份狀態；Vue 的 composable 也是這樣。
  3. 叫號螢幕為什麼三杯都叫成第 4 杯：閉包記住的是變數不是值，var 和 let 差在哪裡。修好第一張單。
  4. 自動結帳為什麼讀不到 cart：this 看呼叫方式，交出去的方法為什麼找不到原本的物件。
  5. 方法非交出去不可時，怎麼保住 this：三種修法各在什麼時候用。修好第二張單。
這一課的練習區跑的是 JavaScript，在瀏覽器的背景執行緒（Web Worker）裡執行，所以沒有 window、document。程式跟 Vite 專案一樣以 ES module 執行，會影響 this 的地方講到時再說明。

函式在別處被呼叫時，它用的變數是哪一個？

要回答兩張 bug 單，先從變數開始：一個函式裡寫了 shop，執行時它怎麼知道是哪一個 shop？

先認識一個名詞。函式的大括號會圍出一塊範圍，在裡面宣告的變數只有這塊範圍裡的程式看得到，外面看不到。這塊「變數看得到的範圍」叫作用域（scope）。函式可以寫在另一個函式裡，所以作用域會一層包一層，最外層是整個檔案。用 let／const 宣告時，if、for 的大括號也會圍出一層作用域；用 var 宣告時只有函式才算。這個差別第三節修叫號螢幕時會用到。

函式用到一個變數時，先在自己的作用域裡找；找不到，就往寫這個函式的地方的外一層找，一層一層往外，直到最外層。看的是函式「寫在哪裡」，不是「在哪裡被呼叫」。下面的 whereAmI 寫在最外層，卻在 branch 裡被呼叫，而 branch 裡剛好也有一個 shop：

印出來的是 總店。whereAmI 自己沒有 shop，就往它出生的那一層，也就是檔案最外層找，找到 '總店'。branch 裡的 shop 只在 branch 的作用域裡看得到，whereAmI 不是寫在 branch 裡面，所以看不到它。在哪裡被呼叫，對結果沒有影響。

這套「看寫在哪裡」的規則叫詞法作用域（lexical scope）。「詞法」指的是程式碼的文字本身：只看原始碼裡函式寫在哪個位置，不用等到執行就能確定每個變數是哪一個。這是刻意的設計。如果變數改成看「在哪裡被呼叫」，你把 callback 交給一個函式庫，callback 裡的 shop 可能被函式庫內部剛好也叫 shop 的變數搶走，同一個函式在不同地方被呼叫就有不同結果，讀程式碼也看不出來。有了詞法作用域，你看著程式碼就知道 callback 用的是哪個變數，不管之後誰呼叫它。

上面的 whereAmI 被呼叫時，它出生的那一層還在。交給 setTimeout 的 callback 就不一樣了：它真正執行時，建立它的那個函式通常早就執行完了。那時候它要找的變數還在嗎？

外層函式都執行完了，變數為什麼還在？

照一般的想法，函式執行時建立的變數，函式執行完就用不到了。JavaScript 會自動找出程式再也碰不到的資料，把它占用的記憶體收回來，這個機制叫垃圾回收（garbage collection）。你不用自己釋放記憶體，但也代表：一個變數會留多久，取決於還有沒有程式碰得到它。

關鍵就在「碰得到」。如果外層函式在裡面建立了另一個函式，而且把這個內層函式回傳出去，依照上一節的規則，內層函式之後不管在哪裡被呼叫，都還要往外層找變數。所以只要內層函式還有人拿著，外層的變數就還碰得到，不會被回收。你可以想成函式出生時背了一個背包，裡面裝著它用得到的外層變數，走到哪裡都帶著。函式加上它背著的外層變數，就叫閉包（closure）。

用咖啡店的集點卡來看：makeStampCard() 每呼叫一次就發一張新卡，回傳的 stamp 函式負責蓋章，每張卡各自記著自己的點數。

amy 蓋了三次，印出 3；ben 蓋了一次，印出 1。makeStampCard 每次執行完就結束了，但它回傳的 stamp 還被 amy、ben 拿著，所以各自背包裡的 points 一直都在，每次蓋章都接著上一次的點數。

amy 和 ben 的點數互不影響，是因為每次呼叫 makeStampCard 都會建立一個新的 points。呼叫兩次就有兩個 points，分別裝進兩個 stamp 的背包。這是閉包最常見的用途：像 makeStampCard 這種專門用來產生東西的函式叫工廠函式（factory function），每呼叫一次就產生一份獨立的狀態。

另一個效果是外面的程式碰不到 points。points 只存在於 makeStampCard 的作用域裡，外面沒有任何變數指到它，唯一能改它的就是 stamp。所以沒有人能直接把點數改成 100，只能一次蓋一個章。在 class 有 #private 之前，JavaScript 就是用閉包做私有狀態。

反過來，背包會讓變數活得比預期久：只要 stamp 還有人拿著，points 就不會被回收。一個點數沒什麼，但如果背包裡裝的是一大份訂單資料，而 callback 被註冊到某個事件上一直沒移除，那份資料就一直占著記憶體。這種「用不到了卻一直占著記憶體」的情況叫記憶體洩漏，第 2 課講記憶體時會再遇到。

你在 Vue 裡寫的 composable（useXxx()）就是集點卡這個模式：每次呼叫都在函式裡建立一份新的狀態，回傳的函式和 ref 記著它，所以兩個元件各自呼叫 useCart()，就各有一台購物車。

💡 實務上：狀態寫在 useXxx 裡面還是外面，結果完全不同
Vue 的 composable，還有 debounce（搜尋框停止輸入一陣子才送出請求）這類工具函式，都是靠閉包讓每次呼叫拿到自己的一份狀態。常見的坑是把 const items = ref([]) 寫到 useCart() 外面：同一個頁面裡所有用到 useCart() 的元件就共用同一份購物車。這有時正是你要的（全站共用的登入狀態），有時是 bug（點餐頁同時開兩張訂單，品項卻混在一起）。到了伺服器上更危險：用 Nuxt 這類在伺服器先產生頁面的框架時，模組最外層的變數會被所有使用者的請求共用，王小明可能看到陳美華的購物車。所以看到 composable，資深工程師會先問：「這份狀態該是每次呼叫一份，還是全站一份？」

叫號螢幕為什麼三杯都叫成「第 4 杯」？

閉包讓 callback 晚一點執行時還找得到外層的變數。叫號螢幕的 callback 也找得到 i，問題是它印出的是 4。要看懂這個 bug，先確認一件事：背包裡裝的到底是變數，還是建立那一刻的值。

答案是變數本身。可以把變數想成一個格子，背包裡放的是這個格子，不是格子裡當下的值抄下來的複本。之後有人改了格子裡的值，函式執行時看到的就是新值：

showPrice 建立時價格是 80，執行時印出的是 90。這不是特例，上一節的集點卡就靠這一點運作：stamp 每次 points++ 改的都是背包裡同一個 points，所以點數能累加；如果背包裡放的是複本，每次蓋章都會從 0 開始。

現在看叫號螢幕的程式。它用迴圈排了三個 setTimeout，每個 callback 印出自己是第幾杯：

三次都印出「第 4 杯」。照時間順序拆開來看：

  1. 迴圈先一口氣跑完三圈，排好三個 callback。交給 setTimeout 的 callback 就算等待時間是 0，也要等目前這段程式全部跑完才輪得到，原因第 7 課會講。
  2. 用 var 宣告的變數，作用域是整個函式（不在函式裡就是整個檔案），不是迴圈的每一圈。所以整個迴圈從頭到尾只有一個 i，每一圈 i++ 改的都是它。
  3. 三個 callback 背包裡放的是同一個 i。迴圈跑到 i 變成 4，i <= 3 不成立才結束，這時 i 停在 4。
  4. 三個 callback 終於執行，去看那個 i，都是 4。

修法是把 var 改成 let。let 的作用域是它所在的那對大括號，叫區塊作用域。for 迴圈的條件用 let 宣告時，JavaScript 會讓每一圈都有一個新的 i：進入下一圈時建立新變數，把上一圈的值帶過來再加 1。第一圈的 callback 背著值是 1 的那個 i，第二圈的背著值是 2 的那個，彼此不共用。

注意閉包的規則沒有變：callback 記住的仍然是變數，不是值。改用 let 有效，是因為每個 callback 背的是不同的變數，而且那些變數之後不會再被改。這就是練習 1：把叫號螢幕修好。

第一張 bug 單解決了。第二張的錯誤訊息不太一樣：讀不到的是 this 上的東西，而 this 不是變數，不照作用域的規則找。

自動結帳為什麼讀不到 cart 的 items？

先看第二張 bug 單的程式。checkout 是 cart 的方法，用 this.items 讀購物車裡的品項，然後交給 setTimeout 在 10 秒後執行：

const cart = {
  items: ['拿鐵', '可頌'],
  checkout() {
    console.log(`結帳：${this.items.length} 件`)
  },
}

setTimeout(cart.checkout, 10000)

方法裡為什麼要寫 this.items，而不是直接寫 cart.items？因為同一個函式可以掛在不同物件上給大家用（練習 4 就會把 checkout 借給另一台購物車），函式不能把物件寫死。this 的意思是「這次呼叫我的那個物件」，函式被呼叫的那一刻才決定是誰。

所以 this 的規則跟變數相反，不看函式寫在哪裡，而是看呼叫的那一刻。最常見的情況只要記一句：點號前面是誰，this 就是誰。下面同一個函式呼叫兩次，差別只在有沒有點號：

第一次印出 2，第二次出錯了：Cannot read properties of undefined (reading 'items')。count 和 cart.count 是同一個函式，把函式指定給另一個變數，不會順便記住它原本掛在哪個物件上。第二次呼叫時前面沒有點號，沒有「呼叫它的物件」，this 就是 undefined，讀 undefined.items 就丟出錯誤。

前面沒有點號時 this 會是 undefined，是因為程式跑在嚴格模式（strict mode）。嚴格模式是 JavaScript 比較嚴格的一套執行規則，有些舊的寬鬆行為會改成出錯或得到 undefined，「沒有物件時 this 是 undefined」就是其中之一。用 import／export 的 ES module 一律是嚴格模式，Vite 專案和這頁的練習區都是；Node 裡哪些檔案算 ES module，見課末的補充。

點號是最常見的情況，但 this 還有其他幾種決定方式。下表列出常見的幾種，規則都是同一條：看呼叫的那一刻。

cart.count()cart：點號前面是誰就是誰

setTimeout(cart.count, 10)不是 cart。交出去的只是函式本身，之後由別人呼叫，this 也由呼叫的人決定（各環境給什麼見課末）

call 和 bind 都是函式本身就有的方法，用來指定 this。差別在時間：cart.count.call(other) 立刻呼叫一次；cart.count.bind(other) 不呼叫，回傳一個 this 永遠固定是 other 的新函式，之後誰呼叫它都一樣，連再 bind 一次也改不了。

箭頭函式是表裡唯一的例外：它根本沒有自己的 this，在箭頭函式裡寫 this，就照第一節找變數的規則，往它出生的外一層找。下一節的修法會用到這一點。

現在回到 bug 單。setTimeout(cart.checkout, 10000) 交給 setTimeout 的只有函式本身，cart 沒有跟著去。10 秒後 setTimeout 呼叫它時，前面不是 cart.，this 由 setTimeout 決定，在瀏覽器裡是全域物件。全域物件是整個執行環境最外層的那個物件，在瀏覽器裡就是 window（各環境通用的名字是 globalThis）。window 上沒有 items，this.items 是 undefined，再讀 .length 就出錯，這就是 bug 單上那行錯誤訊息；它說的是 'length' 而不是上面範例的 'items'，正是因為這次 this 不是 undefined，而是另一個錯的物件。

原因找到了：方法被交出去時，原本的物件沒有跟著去。但交給 setTimeout、事件處理、陣列的 .map 是每天都要做的事，接下來看怎麼交出去又不弄丟 this。

方法非交出去不可時，怎麼保住 this？

上一節的表裡已經藏著答案：讓呼叫發生時「前面有 cart」，或者事先把 this 固定住。下面的 later 模擬「把函式交給別人，由別人在 10 毫秒後呼叫」，跟 setTimeout 一樣是不加點號直接呼叫 fn()。第一行重現 bug，接著是三種修法：

第一行出錯，原因跟 bug 單一樣。三種修法為什麼有效：

  • 修法 1，用箭頭函式包一層：交出去的是外面那個箭頭函式，later 呼叫的是它；它裡面照樣用 cart.count() 呼叫，點號前面是 cart，this 就是 cart。cart 是背包裡的變數，靠的是閉包。
  • 修法 2，用 bind：bind 產生一個 this 固定是 cart 的新函式，不管 later 怎麼呼叫都一樣。
  • 修法 3，class 欄位寫成箭頭函式：箭頭函式在建立實例時出生，外層的 this 就是那個實例，所以不管怎麼傳都不會丟失。代價是每個實例都有自己的一份函式，不像一般方法所有實例共用一份。

這裡先借用 class 的寫法，class 的完整語法（欄位、建構子、原型）在第 3 課。

怎麼選：只交出去一次的 callback，用箭頭函式包一層最直覺，第二張 bug 單就這樣修：setTimeout(() => cart.checkout(), 10000)；練習 4 用 10 毫秒做同一件事。要註冊後再移除的監聽器又不一樣。例如結帳頁掛了 window 的 resize 監聽器，離開頁面（元件卸載）時要移除，不然每進一次頁面就多一個。removeEventListener 必須拿到同一個函式才移得掉，所以先 const handle = obj.handle.bind(obj) 存起來，註冊和移除都用它；每次現寫一個箭頭函式或 bind，都是新的函式，移不掉。常被當 callback 傳出去的 class 方法，才考慮寫成欄位箭頭函式。

既然箭頭函式能保住 this，會有人想乾脆把物件的方法都寫成箭頭函式。這是反效果：

物件方法不要寫成箭頭函式。{ count: () => this.items.length } 裡的 this 不是這個物件，而是外層的 this，在 module 最外層是 undefined。要用到 this 的方法，就用一般的方法寫法 count() { … }。

差別在箭頭函式「出生」的地方。修法 3 的箭頭函式寫在 class 欄位裡，在建立實例時出生，外層的 this 是實例；物件字面值的大括號不是函式，不會產生新的 this，所以寫在物件裡的箭頭函式，外層就是 module 最外層。

💡 實務上：this 的 bug 幾乎都出在「把方法交出去」的那一刻
寫 Vue 3 的 <script setup> 或 React 函式元件時，平常很少碰到 this；會碰到的是用 class 寫的程式碼，例如後端的 service、第三方 SDK 的 client 物件。出事的場景很固定：把 api.fetchOrders 這種方法沒加括號，交給 setTimeout、陣列的 .map、Promise 的 .then，或當成事件處理函式。另一個坑跟上面的 bind 有關：註冊時寫 .bind(this)、移除時又 bind 一次，拿到的是兩個不同的函式，監聽器根本沒被移掉；在單頁應用裡元件每次掛載就多一個，同一個事件會被處理好幾次。Code review 看到「方法沒加括號就當參數傳出去」，就值得停下來確認它裡面有沒有用到 this。

練習

練習 1：serveCups(n, log) 用迴圈排了 n 個 setTimeout 叫號，結果每一杯都叫成「第 n+1 杯」。修好它，讓 log 依序收到「第 1 杯」到「第 n 杯」，而且仍然是每一杯各排一個 setTimeout，之後才叫號。最後一行 serveCups(3, console.log) 可以直接執行看結果。

練習 2：完成 makeStampCard()。它要回傳一個物件，物件上只有兩個方法：

  • stamp()：蓋一個章，回傳目前的點數
  • reset()：點數歸零

每張卡的點數各自獨立。點數要藏在閉包裡，不能放在回傳的物件上；所以把方法拿出來單獨呼叫（const { stamp } = card）也要照樣能用。

練習 3：寫 once(fn)。它回傳一個新函式：第一次呼叫時執行 fn 並記住結果，之後再呼叫都直接回傳第一次的結果，不再執行 fn。結帳按鈕被連點兩下時，就需要這種保護。

練習 4：下面把 cart.checkout 交給 setTimeout，結果 this 不是 cart。只改最後一行，讓 cart 在 10 毫秒後正確結帳。

練習 5：下面印出什麼？

const shop = {
  name: '總店',
  hi() { return this?.name },
}
const hi = shop.hi
console.log(hi())

✓ hi() 前面沒有點號，this 是 undefined（嚴格模式），所以 this?.name 是 undefined。a 錯：hi 雖然是從 shop 拿出來的，但函式不會記得原本的物件，this 只看呼叫的樣子。c 錯：this 不會是函式自己，變數名稱也不影響 this。如果沒有 ?.，this.name 會直接丟出 TypeError。

練習 6：下面印出什麼？

const shop = {
  name: '總店',
  hi: () => this?.name,
}
console.log(shop.hi())

✓ 箭頭函式沒有自己的 this，用的是出生地外層的 this，而 module 最外層的 this 是 undefined。a 錯：「點號前面是誰」只適用一般函式，用 shop.hi() 呼叫對箭頭函式沒有影響；物件字面值的大括號也不會產生新的 this。b 錯：this 不會是屬性名稱。要拿到「總店」，改用方法寫法 hi() { return this.name }。

練習 7：makeStampCard() 執行完、把 stamp 回傳之後，裡面的 points 還在嗎？

✓ 閉包讓變數活得比外層函式還久：只要 stamp 還被引用，它記住的 points 就不會被 JavaScript 自動回收記憶體的機制（垃圾回收）清掉。a 錯：沒有被任何函式記住的區域變數才會在之後被回收。c 錯：每次呼叫 makeStampCard 都會產生新的 points，所以不是共用的。這也是記憶體洩漏（用不到的東西一直占著記憶體）的常見來源：事件註冊了卻沒移除，callback 背包裡的東西就一直不會被回收。

常見錯誤

  • 以為閉包記的是當下的值：它記的是變數，變數之後被改，函式看到的就是新值。
  • 迴圈裡用 var 搭配 callback：整個迴圈只有一個變數，所有 callback 共用它。改用 let，每一圈各有一個。
  • 把方法直接交出去：setTimeout(cart.checkout)、addEventListener('click', obj.handle) 之後，this 就不是原本的物件了。
  • 物件方法寫成箭頭函式：this 不會是那個物件。
  • 對 bind 過的函式再 bind 一次：第一次 bind 就固定了 this，第二次 bind 改不了 this。

小結

  • 變數看出生地：函式往寫它的地方一層層往外找變數，這叫詞法作用域，跟在哪裡被呼叫無關。
  • 函式會帶著外層變數的背包，外層函式執行完，變數也還在，這就是閉包。每次呼叫外層函式，都會產生一份新的變數，集點卡和 Vue 的 composable 都靠這一點。
  • 閉包記的是變數本身，不是當下的值。var 迴圈只有一個變數，所有 callback 共用；let 每一圈一個，叫號螢幕就是這樣修好的。
  • this 看呼叫方式：點號前面是誰就是誰；單獨呼叫是 undefined（嚴格模式）。
  • 方法交出去會丟失 this。修法：用箭頭函式包一層、用 bind，或寫成 class 欄位的箭頭函式；要移除的監聽器先把 bind 好的函式存起來。
  • 箭頭函式沒有自己的 this，用的是出生地的 this，所以物件方法不要寫成箭頭函式。
