階段 5：寫後端需要的 TypeScript · 第 25 課

模組、.d.ts 與 tsconfig

到目前為止，練習區的程式都是一個檔案自己跑。這一課的任務是把咖啡店的收據功能搬進後台：後台是新開的 NestJS 12 專案，有上百個檔案、幾十個套件，還有一份 tsconfig.json 決定 TypeScript 怎麼檢查、怎麼輸出。這份 tsconfig 是同事用 TypeScript 6.0 的 tsc --init 產生的，它預設就開了 verbatimModuleSyntax、noUncheckedIndexedAccess、exactOptionalPropertyTypes，types 是空陣列 []；團隊規範要求這幾個設定保留不動。收據功能要用收據機廠商的套件 coffee-pos，要讀環境變數決定 port，要知道是哪位店員登入，上線後出錯時還要查得到是哪一行。

搬家第一天，你會依序撞到四件事：import { Receipt } from 'coffee-pos' 被編譯器擋下；明明裝了 @types/node，process.env.PORT 還是報「找不到 process」；想在 req.user 放登入的店員，TypeScript 說 Request 沒有這個欄位；上線後客服回報結帳出錯，log 卻指向 dist/orders/orders.service.js:118，對不回原始碼。四件事都出在三個地方：模組怎麼匯入、型別從哪裡來、tsconfig 怎麼設。學完這課，你能寫出不會在執行時出事的型別匯入、讀懂並擴充第三方套件的型別、逐行解釋 NestJS 12 的 tsconfig，也知道 TypeScript 7 現在能不能用、舊專案怎麼一步一步調嚴格。

這課的路線：
  1. 只為了型別的 import，為什麼會被編譯器擋下？模組、import type 與 verbatimModuleSyntax，以及要注入的 class 為什麼是例外（第一件事的答案）。
  2. 收據機的型別從哪裡來？.d.ts、declare、@types，以及裝了 @types/node 為什麼還找不到 process（第二件事的答案）。
  3. 怎麼替 Express 的 Request 加上登入的店員？用 module augmentation 與 declare global 擴充別人的型別（第三件事的答案）。
  4. strict 開了，為什麼還要再多開兩個旗標？strict 包含哪些檢查，noUncheckedIndexedAccess、exactOptionalPropertyTypes 多擋了什麼。
  5. NestJS starter 的 tsconfig 每一行在做什麼？包括 source map 怎麼讓錯誤行號對回 .ts（第四件事的答案）。
  6. 能換 TypeScript 7 嗎？舊後台怎麼一次開一個旗標，調到跟新專案一樣嚴格。
這課會用到：
  • 第 13 課的「型別檢查與擦掉型別是兩件事」：tsc 會檢查型別，Vite、Node 只把型別擦掉就執行，不檢查。

這一頁的練習區多開了三個選項：verbatimModuleSyntax、noUncheckedIndexedAccess、exactOptionalPropertyTypes，下面會一個一個講。頁面還放了一個只有型別、執行時不存在的假套件 'coffee-pos'（咖啡店的收據機），裡面有 Receipt 和 PrinterOptions 兩個 interface。

只為了型別的 import，為什麼會被編譯器擋下？

搬家的第一步，是把練習區寫好的收據程式貼進新專案。它第一行要從收據機套件拿到 Receipt 這個型別，於是我們寫了 import。要看懂這一行為什麼被擋下，先把「模組」是什麼講清楚。

模組（module）是有 import 或 export 的檔案。模組裡宣告的名稱只屬於這個檔案，不會跑到全域；別的檔案要用，得自己 import。你每天寫的 .vue、.ts 檔都是模組。沒有 import、export 的檔案叫腳本（script），裡面宣告的名稱會變成全域共用，這個差別在第 3 節擴充型別時還會用到。

模組在執行時怎麼載入、ESM 和 CommonJS 的差別，在 Node 課第 4 課。這裡只需要記住一件事：執行時遇到一行 import，就會去載入那個模組、執行它的頂層程式，再從它的匯出裡找你要的名稱。import 不只是告訴編譯器「我要用這個」，它在執行時是一個真的動作。

TypeScript 在這裡多出一個問題：匯入的東西可能只是型別。型別在編譯後會被擦掉（第 13 課）。Receipt 是一個 interface，編譯成 JavaScript 後不存在。如果編譯後的程式還留著 import { Receipt } from 'coffee-pos'，執行時就會去載入 coffee-pos，再找一個叫 Receipt 的匯出，而那個匯出根本不存在。

所以 TypeScript 提供型別匯入（type-only import）：在 import 後面標上 type，告訴編譯器「這行只為了型別，編譯後整行刪掉」。下面這格執行後看一件事：'coffee-pos' 在執行時根本不存在，這段卻正常印出收據摘要。

跑得起來，是因為那一行 import 編譯後消失了，執行時沒有人去找 coffee-pos。type 可以標在整行，也可以標在個別名稱上，兩者編譯後的結果不一樣。這一頁開著 verbatimModuleSyntax，三種寫法編譯成什麼（TypeScript 官方文件的說明，本機用 5.9.3 和 7.0.2 實測相同）：

寫法編譯後執行時
import type { Receipt } from 'coffee-pos'整行刪掉不會載入 coffee-pos
import { type Receipt } from 'coffee-pos'import {} from 'coffee-pos'仍會載入：套件不存在就出錯，存在就執行它的頂層程式
import { Receipt } from 'coffee-pos'（Receipt 只是型別）編譯錯誤 TS1484—

第三列就是搬家第一天撞到的錯誤。verbatimModuleSyntax（TypeScript 5.0 加入）的規則只有一句：沒標 type 的 import 原樣保留，標了 type 的刪掉。它不替你猜。所以用一般 import 匯入純型別時，它直接報 TS1484，意思是「這是型別，開了 verbatimModuleSyntax 時必須用型別匯入」，不讓你產生一個執行時會壞的 import。修法是把那一行改成 import type。

為什麼需要這麼死板的規則？以前 tsc 會看完整個專案，自己判斷哪些 import 只用在型別，再偷偷刪掉。tsc 做得到，是因為它讀得到每一個檔案，知道 Receipt 在別的檔案裡宣告成 interface 還是 class。

但現在很多工具一次只看一個檔案：Vite 用的 esbuild、Node 直接執行 .ts（Node 課第 5 課）都是這樣，因為不讀整個專案才轉得快。它們看到 import { Receipt } from './receipt'，不知道 Receipt 是 interface 還是 class。猜成 class 而保留，執行時找不到匯出；猜成型別而刪掉，真正的 class 就不見了。把「是不是型別」寫在 import 上，每個檔案就能單獨轉譯，不必看別的檔案。

舊一點的選項 isolatedModules 擋的是同一類問題：它要求每個檔案都能單獨轉譯，遇到單獨轉譯會出錯的寫法就報錯。NestJS 12 的 tsconfig 開著它，第 5 節逐行讀 tsconfig 時會再看到。

💡 實務上：import type 不是越多越好，要注入的 class 是例外
收據功能裡，ReceiptController 會在建構子注入 ReceiptService。第 24 課看過，emitDecoratorMetadata 會把建構子參數的型別寫進 metadata，DI 容器靠它知道要注入誰。如果寫成 import type { ReceiptService }，class 在執行時消失，metadata 只剩 Function，編譯不報錯，啟動時注入才失敗。規則是：要注入的 class 用一般 import；只當型別用的 interface（像 Receipt）才用 import type。lint 的自動修正會把「看起來只當型別用」的匯入改成 import type，review 這種大量修改時，要特別看建構子注入的那幾行。

匯入的問題解決了，但 import type 只告訴編譯器「這行只要型別」。coffee-pos 執行時不存在，TypeScript 卻知道 Receipt 有 id、total、items，這些形狀總要寫在某個地方。下一節看型別到底從哪裡來。

收據機的型別從哪裡來？為什麼裝了 @types/node 還找不到 process？

上一節的 Receipt 能用，是因為這一頁放了一份只描述形狀、沒有任何實作的宣告。這種檔案叫宣告檔（declaration file），副檔名是 .d.ts：只寫型別、不寫實作，編譯後不產生任何 JavaScript。

為什麼需要這種檔案？因為很多東西在執行時存在，TypeScript 卻看不到它的原始碼：用 JavaScript 寫的套件、執行環境提供的全域變數（Node 的 process）、打包工具在建置時塞進來的常數。TypeScript 只能靠別人寫好的描述，知道它們長什麼樣子。

.d.ts 裡的宣告前面常有 declare，意思是環境宣告（ambient declaration）：「這個東西執行時已經存在，由別人提供，你相信我就好」。編譯器讀到 declare，會把它加進型別檢查，但不會為它產生任何程式碼。

你在 Vue 專案其實碰過這種情況。Vite 的 define 設定會在打包時把程式裡的 __APP_VERSION__ 換成版本字串。TypeScript 不知道 Vite 會做這件事，看到 __APP_VERSION__ 只會說找不到這個名稱，所以要你自己宣告。下面這格執行後看：型別檢查沒報錯，印出來的卻是 'undefined'。

型別檢查完全沒報錯，執行時卻是 undefined。declare 寫錯，TypeScript 不會發現：它只是照你說的相信，不會去確認執行時真的有這個東西。宣告檔描述現實，不製造現實；描述和現實不一致時，錯誤會在執行時才出現。這是 .d.ts 的風險所在。

那第三方套件的宣告由誰寫？有兩個來源。多數新套件（像 zod、NestJS）自己附 .d.ts，裝了就有型別。只有 JavaScript 的套件，則由社群在 DefinitelyTyped 專案替它寫型別，發布成 @types/套件名，例如 @types/express。Node 本身的 API（process、fs）的型別也在這裡，套件名是 @types/node。

裝了 @types/node，搬家第一天為什麼還是找不到 process？因為裝了不等於載入。tsconfig 的 types 選項決定要自動載入哪些 @types 套件。TypeScript 6.0 把它的預設值改成 []，也就是什麼都不自動載入，7.0 沿用。所以新專案裝了 @types/node，寫 process.env.PORT 還是會報 TS2591「Cannot find name 'process'」，要在 tsconfig 寫 "types": ["node"]，明確列出要載入的型別套件。

練習區沒有載入 Node 的型別，正好重現這個錯誤。執行後看兩件事：編輯器裡的 TS2591，以及執行時的錯誤。

兩個錯誤的原因不同。型別錯誤是因為 TypeScript 沒有載入 process 的宣告；執行時的錯誤，是因為練習區跑在瀏覽器的 Worker 裡，Worker 真的沒有 process。在 Node 專案裡則相反：process 執行時一定存在，只是 TypeScript 不知道，在 types 加上 "node" 就好。

💡 實務上：skipLibCheck 開著，自己的型別就寫在 .ts 裡
開了 skipLibCheck，TypeScript 不檢查所有 .d.ts，編譯快很多，也避開不同 @types 套件彼此衝突的錯誤。NestJS 12 和多數專案都開著，通常合理。代價是它連你自己寫的 .d.ts 也跳過：自己的宣告寫錯了不會報。所以收據功能自己的型別（例如列印設定、收據的資料庫欄位）寫在一般的 .ts 檔裡，讓它被檢查；只有真的要描述「執行時已經存在的東西」時才寫 .d.ts。

型別從哪裡來已經清楚了。下一件事是登入：守衛驗證完店員之後，想把店員資料放在 req.user，後面的收據程式才知道是誰結的帳。可是 Express 的 Request 型別寫在 @types/express 裡，裡面沒有 user，而我們不能去改別人的套件。

怎麼替 Express 的 Request 加上登入的店員？

改不了別人的原始碼，還能加欄位，靠的是第 14 課的宣告合併：同名的 interface 寫兩次，TypeScript 會把兩份的欄位合成一個 interface。所以只要在自己的檔案裡，對「同一個」interface 再寫一次，就能替它加上欄位。問題只剩下：怎麼讓 TypeScript 知道，你寫的 Request 就是 express 套件裡的那個 Request？

答案是模組擴充（module augmentation）：在你的模組檔案裡寫 declare module '套件名' { … }，裡面的 interface 會跟那個套件原本的同名 interface 合併。替 Express 的 Request 加上登入的使用者長這樣，認證課第 21 課會實際用到：

// src/types/express.d.ts
import 'express'

declare module 'express' {
  interface Request {
    user?: { id: number; role: 'staff' | 'admin' }
  }
}
// 之後任何地方的 req.user 都有型別

逐行看。第一行 import 'express' 讓這個檔案成為模組，在模組檔案裡寫 declare module 'express'，TypeScript 才會把它當成「擴充已經存在的 express 模組」。大括號裡的 interface Request 跟 express 原本的 Request 同名，兩者合併，Request 就多了 user。user 是可選的，因為不是每個請求都登入了，沒登入時就沒有這個欄位。練習 2 會用同樣的方法替 'coffee-pos' 的 Receipt 加上會員編號。

為什麼一定要第一行那個 import 'express'？少了它，這個檔案沒有任何 import、export，就是第 1 節說的腳本。在腳本裡寫 declare module 'express'，TypeScript 會把它當成「宣告一個叫 express 的新模組」，而不是擴充原本那個：express 原本的型別被這份取代，Request 只剩你寫的 user，Router 等其他匯出都不見了。所以擴充別人的模組，檔案本身一定要是模組。

有些東西不屬於任何套件，而是掛在全域上，這時用全域擴充（declare global）：在模組檔案裡用 declare global { … } 替全域的東西加型別。你的 Vue 專案 src/env.d.ts（或 vite-env.d.ts）裡的 interface ImportMetaEnv 也是在擴充全域，原理同樣是宣告合併：Vite 先定義了全域的 ImportMetaEnv，你再寫一次同名 interface 加上 VITE_API_URL，import.meta.env.VITE_API_URL 才有型別。差別在那個檔案通常沒有 import，是腳本，裡面的 interface 本來就是全域的，直接寫就會合併，不用 declare global。一旦檔案有了 import、變成模組，裡面的 interface 只屬於這個檔案，就要包進 declare global { } 才能擴充全域。

後台常見的全域例子是每個請求的追蹤編號：log 系統在執行環境裡放了一個全域的 requestId，讓每一行 log 都帶著它，客服回報問題時就能用它查出同一個請求的所有紀錄。TypeScript 不知道這個變數存在，要用 declare global 補上型別。下面這格替全域加上它，執行後看：印出 req-42。注意裡面要用 var：用 let、const 宣告的全域變數不會變成 globalThis 的屬性，var 才會，所以要寫成 var，globalThis.requestId 才對得上型別。

💡 實務上：擴充只改型別，值要有人真的放進去
替 Request 加上 user，只是讓 req.user 有型別；執行時要靠登入的守衛真的把店員資料放上去，沒放就是 undefined，跟第 2 節的 declare 一樣只是承諾。所以 user 寫成可選，用之前先檢查。declare global 更要節制：每個全域名稱都是整個專案共用的，誰都能改、誰都能讀，出事很難追。只用在「執行環境真的提供了這個全域」的情況；收據功能自己的共用資料，用模組匯出。

到這裡，型別從哪裡來、缺了怎麼補都處理完了。下一個問題是 TypeScript 檢查得多嚴：新專案的 tsconfig 寫了 strict: true，tsc --init 卻還多開了兩個旗標，這一頁也開著。strict 不是已經全開了嗎？

strict 開了，為什麼還要再多開兩個旗標？

檢查得多嚴，由 tsconfig 決定。"strict": true 不是一個檢查，是一整組旗標的總開關（TypeScript 6.0 起沒寫就是 true）。它打開的旗標，你在前面的課幾乎都碰過，下表查表用，不用背：

noImplicitAny推不出型別的參數變成隱含 any（TS7006）第 13 課
strictNullChecksnull／undefined 不能當一般值用第 13 課、第 16 課
strictFunctionTypes函式參數型別要逆變第 18 課
strictBindCallApplybind／call／apply 的參數也要檢查第 18 課
noImplicitThisthis 的型別是 any 時報錯第 18 課

strict 全開之後，還有兩種常見的錯誤它擋不住，要靠 strict 以外的旗標自己打開。這一頁開著其中兩個，一個管「用索引讀值」，一個管「可選的欄位」。

先看用索引讀值。arr[0]、record[key] 這種用位置或鍵去讀的寫法，叫索引存取。strict 預設假設索引一定讀得到東西：sizes[3] 的型別就是 string，即使陣列只有三個元素。收據也一樣，receipt.items[0].name 在空收據上會讀到 undefined 再取 .name，執行時直接炸掉，編譯器卻一聲不吭。

noUncheckedIndexedAccess 修的就是這件事：用索引讀出來的值，型別一律加上 | undefined，逼你處理「讀不到」的情況。for...of 不受影響，因為迴圈只會走過真的存在的元素。下面這格把滑鼠移到 fourth 上看型別，執行後印出「沒有這個尺寸」和三個小寫尺寸：

再看可選的欄位。nickname?: string 預設同時代表兩件事：可以沒有這個鍵，也可以有這個鍵、值是 undefined。在 JavaScript 裡這兩者是不一樣的物件：Object.hasOwn 一個回傳 false、一個回傳 true；把它展開蓋到舊資料上時，後者會把舊值蓋成 undefined。

對後端，這個差別有實際的意義。第 21 課的 PATCH 裡，沒傳某個欄位代表「不要動」。資料庫套件也是這樣分的：ORM 是把資料表對應成物件、讓你用函式查詢資料庫的套件，Node 後端常用的 Prisma 就是一種 ORM，它把 undefined 當成「不要動」、null 當成「清空」。{ nickname: undefined } 混在中間，到底是要清空還是不要動，意思就模糊了。

exactOptionalPropertyTypes 把這兩件事分開：開了之後，nickname?: string 只代表「可以沒有這個鍵」，不再接受明寫的 undefined。要表達清空，就在型別上明確允許 null。下面這格執行後看：c 那一行報 TS2375，console 印出 a 沒有 nickname 這個鍵、c 有。

💡 實務上：新專案第一天就開，修法比旗標本身重要
咖啡店後台常見 orders[0].total、prices[productName] 這種寫法，查不到資料的那一天就是 noUncheckedIndexedAccess 會提醒你的地方。收據功能搬進新專案的現在就打開，等程式寫多了才開，會一次冒出一大堆錯誤。代價是程式裡多了 ?.、?? 和「找不到怎麼辦」的處理，團隊要有共識接受這種寫法。Code review 時資深會盯修法：到處補 ! 或 as 等於把旗標關掉；找不到時該給預設值、丟錯還是回 404，要看業務意義決定，像查不到的商品用 ?? 0 當價格，等於免費賣出去。

每個旗標的意思都清楚了。tsc --init 產生的是通用設定，NestJS 還需要裝飾器、輸出資料夾這些設定，最好的對照是 NestJS 官方 starter 的 tsconfig。它每一行都有理由，開場那個對不回原始碼的錯誤行號，答案也在裡面。

NestJS starter 的 tsconfig，每一行在做什麼？

照抄別人的 tsconfig 很常見，出事時卻不知道該改哪一行。前四節已經把大部分的零件講過了，現在把它們放回原位。下面是 NestJS 官方 starter（2026-10-31 的 master）的 tsconfig，你在 NestJS 課第一天就會看到它：

{
  "compilerOptions": {
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "resolvePackageJsonExports": true,
    "esModuleInterop": true,
    "isolatedModules": true,
    "declaration": true,
    "removeComments": true,
    "emitDecoratorMetadata": true,
    "experimentalDecorators": true,
    "importHelpers": true,
    "allowSyntheticDefaultImports": true,
    "target": "ES2023",
    "sourceMap": true,
    "outDir": "./dist",
    "incremental": true,
    "skipLibCheck": true,
    "strict": true,
    "strictPropertyInitialization": false,
    "types": ["vitest/globals", "node"]
  }
}

先拿它對照開場的四件事。starter 已經寫好 "types": ["vitest/globals", "node"]，所以第二件事在 starter 裡不會發生。它沒開 verbatimModuleSyntax，只開了 isolatedModules：只為型別的 import { Receipt } 會被編譯器安靜地刪掉，不報 TS1484，所以第一件事也不會發生。我們搬家第一天用的還是 tsc --init 那份，所以四件事都會發生；把 starter 這些行補進去（types 加上 "node"），同時保留 tsc --init 開的三個嚴格選項，就是新專案最後的 tsconfig。

逐行的說明在下表。前面幾列決定「輸出什麼樣的 JavaScript、怎麼找到檔案」，後面幾列是前幾節講過的檢查與型別來源；sourceMap 放在最後，表格之後單獨講。

設定做什麼、為什麼
target: ES2023輸出的 JavaScript 用到哪一版的語法；比它新的語法會被改寫。Node 24 支援 ES2023，不用改寫。
lib（沒寫）可以用哪些內建 API 的型別，沒寫就跟著 target。lib 只影響型別，不會幫你補上不存在的 API。練習區是 target ES2022、lib es2024＋webworker，所以有 Worker 的 API、沒有 DOM。
module／moduleResolution: nodenext輸出哪種模組格式、怎麼找到 import 的檔案，照 Node 的規則。後果：相對匯入要寫 .js（import { x } from './orders.service.js'），因為 Node 執行的是編譯後的 .js。前端專案交給打包工具，用 bundler，不用寫副檔名。
resolvePackageJsonExports照套件 package.json 的 exports 欄位找檔案（nodenext 本來就會這樣做）。
outDir: ./dist編譯結果放 dist。輸出時，TypeScript 會從原始碼的根資料夾 rootDir 開始照搬資料夾結構；這份沒寫 rootDir，TypeScript 6.0 起預設是 tsconfig 所在的資料夾，src/main.ts 會輸出成 dist/src/main.js。所以 starter 另外有一份建置用的 tsconfig.build.json，繼承這份、寫了 "rootDir": "./src" 並排除測試檔，輸出才是 dist/main.js，package.json 的 start:prod 就是 node dist/main。
experimentalDecorators、emitDecoratorMetadataNestJS 的裝飾器和 DI 靠這兩個（第 24 課）。
strict＋strictPropertyInitialization: false全開，只關掉一個：DI 注入的欄位、DTO 的欄位不是在建構子裡給值，開著會到處報 TS2564（第 23 課）。
isolatedModules每個檔案都要能單獨轉譯，讓 SWC 這類快速編譯器能用（第 1 節）。
importHelpers需要的輔助函式（例如裝飾器的 __decorate）從 tslib 匯入，不要每個檔案各貼一份。
declaration同時輸出 .d.ts。應用程式其實用不到，發布成套件時才需要。
removeComments、incremental輸出時刪註解；記下上次編譯的結果，下次只重編有變的檔案。
skipLibCheck不檢查 .d.ts，取捨見第 2 節。
types: ["vitest/globals", "node"]只載入這兩個（第 2 節）：Node 的 API，以及測試裡不用 import 就能寫的 describe、it、expect。
esModuleInterop、allowSyntheticDefaultImports讓 import express from 'express' 能匯入 CommonJS 套件。TypeScript 6.0 起不能設成 false，等於一直開著，寫不寫都一樣。
sourceMap輸出 .js.map，下面說明。

最後一列 sourceMap 回答開場的第四件事：為什麼正式環境的錯誤對不回原始碼。正式環境跑的是 dist/*.js，不是 .ts。程式出錯時，錯誤的 stack trace（第 4 課）記錄的是「正在執行的檔案」的行號，也就是 .js 的行號。編譯會改寫程式、刪掉型別和註解，.js 的第 118 行跟 .ts 的第 118 行通常不是同一行，對著 .ts 原始碼根本找不到。

source map 就是為了這件事存在的檔案：它記錄「編譯後第幾行第幾欄，對應原始碼的哪個檔案第幾行第幾欄」。開了 sourceMap，tsc 每輸出一個 .js，就在旁邊多輸出一個 .js.map。但 Node 預設不會去讀它，要用 node --enable-source-maps dist/main.js 執行，Node 才會在產生 stack trace 時查 source map，把行號翻回 src/orders/orders.service.ts:42。

你可能會問：Node 24 能直接執行 .ts，只擦掉型別（Node 課第 5 課），那何必編譯、何必 source map？NestJS 專案做不到。Node 只擦型別、不轉換語法，NestJS 到處都是裝飾器，Node 遇到裝飾器直接語法錯誤；emitDecoratorMetadata 要的 metadata 也只有編譯器產生得出來；常用的參數屬性（第 23 課）也不是可擦除語法。所以 NestJS 專案還是先編譯，再靠 source map 對回原始碼。不編譯的專案 tsconfig 要怎麼設，見課末「補充與查表」。

💡 實務上：正式環境的錯誤要能對回原始碼
客服回報「結帳時出錯」，log 裡卻只有 dist/orders/orders.service.js:118，沒有 source map 就只能對著編譯後的程式猜。後端部署時把 .js.map 一起帶上，啟動指令加 --enable-source-maps（寫在 Dockerfile 或 package.json 的 start:prod）。前端不一樣：.map 跟著網站公開，任何人都能還原你的原始碼，常見做法是只上傳到錯誤追蹤服務（例如 Sentry），不放在公開網站上。上線前資深會故意丟一個錯誤，確認 log 的行號真的指向 .ts。另外，網路上舊文章的 tsconfig 常有 TypeScript 7.0 已經刪掉的選項，照抄會直接報錯，清單見課末。

新專案的 tsconfig 讀完了，它寫給的是 TypeScript 6 以後的編譯器。剩下兩個團隊一定會問你的問題：能不能直接換到更快的 TypeScript 7？手上那個 strict: false 的舊後台，又要怎麼調到跟新專案一樣嚴格？

能換 TypeScript 7 嗎？舊後台怎麼調到一樣嚴格？

先回答第一個問題。TypeScript 7.0（2026-07）把編譯器改用 Go 重寫成原生程式，型別檢查快很多，官方說型別檢查的結果跟 6.0 相容。只用 tsc 指令建置的專案（例如只跑 tsc 的 Node 服務）可以直接換，同一份程式會報出一樣的錯誤，只是更快。

但「檢查結果相容」不代表所有工具都能換。有些工具不是執行 tsc 指令，而是把 TypeScript 編譯器當成函式庫，在自己的程式裡呼叫它的函式，例如 Vue 的 vue-tsc（Volar）要靠它讀懂 .vue 檔裡的 TypeScript。編譯器提供給其他程式呼叫的這組函式，就是它的 API。7.0 沒有提供這個 API，所以內嵌 TypeScript 的工具還不能用它：Vue 的 vue-tsc、Svelte、Astro 的專案要暫時留在 6.0。NestJS 也在名單上：@nestjs/cli 的 nest build 不是執行 tsc 指令，而是在程式裡載入 typescript 套件、呼叫它的 API 來編譯，所以本課程的 NestJS 專案固定用 6.0.3。7.1 beta（2026-10-20）加入了新 API，Vue、Svelte 的支援還在各自的 pull request 裡。兩版要並存的做法見課末。

再回答第二個問題。接手一個 strict: false、甚至還是 JavaScript 的舊後台時，最大的誘惑是一次把所有旗標打開。結果通常是一次冒出幾千個錯誤，改不完，最後全部關掉。比較可行的做法，是把「調嚴格」拆成很多個小步驟。

拆成小步驟要靠兩個團隊工具，先講清楚。PR（pull request）是一次修改的提案：你把修改推上去，請同事 review，通過後才合併進主線。CI（continuous integration，持續整合）是每次推送程式碼時，自動在伺服器上跑檢查與測試的流程；檢查沒過，PR 就不能合併。有了這兩樣，每一步都能獨立 review，也不會有人不小心把錯誤合併回去。步驟如下：

  1. JavaScript 專案先開 allowJs（讓 .js 和 .ts 共存）與 checkJs（對 .js 也做型別檢查），一個檔案一個檔案改成 .ts。
  2. 一次只開一個旗標，從錯誤最少的開始（常見順序：noImplicitAny → strictNullChecks → 其他），改完、合併，再開下一個。
  3. 一時改不完的地方用 // @ts-expect-error 原因 標起來，不要用 @ts-ignore。兩者都會讓下一行的型別錯誤不報，差別在問題修好之後：@ts-ignore 會一直默默留著，@ts-expect-error 發現下一行已經沒有錯誤，會反過來報錯，提醒你刪掉它。定期搜尋、清掉。
  4. 在 CI 裡跑 tsc --noEmit（只檢查、不輸出檔案；Vue 專案是 vue-tsc --noEmit），型別錯誤就不能合併（部署課第 15 課）。
💡 實務上：調嚴格是一連串小 PR，不是一次大改
接手咖啡店的舊後台時，先用 tsc --noEmit --strictNullChecks 這種方式臨時加上旗標，看每個旗標各會冒出多少錯誤，再決定順序。每開一個旗標就是一個獨立的 PR，範圍小、好 review，也不會跟同事正在做的功能大量衝突。這種工作不會產生新功能，要先跟 PM 或主管說清楚換來什麼：少一類執行時錯誤、改功能時比較有把握。也可以跟功能開發穿插，例如約定「動到的檔案順手修好」，收據功能搬進來時動到的那幾個檔案，就是第一批。

✓ c。6.0 起 types 預設不自動載入任何 @types 套件，7.0 沿用，裝了也要列出來。a 版本不合會是別的錯誤，不會整個找不到 process。b 不用 import，process 是 @types/node 宣告的全域。d skipLibCheck 只是不檢查 .d.ts，不會決定載入哪些。

練習 6：開著 verbatimModuleSyntax，import { type Receipt } from 'coffee-pos' 編譯後剩下什麼？

✓ b。標在個別名稱上的 type 只刪掉那個名稱，import 語句本身保留，套件仍會被載入；套件不存在就出錯，存在就會執行它的頂層程式。a 是 import type（標在整行）的行為。c 是沒標 type 時才會留下的。d TS1484 是完全沒標 type 時的錯誤。

練習 7：TypeScript 7 檢查速度快很多。現在（2026-10）能把 Vue 專案的 vue-tsc 換成 TypeScript 7 嗎？

✓ a。「型別檢查相容」指的是 tsc 對同一份程式報出一樣的錯誤，不代表內嵌 TypeScript 的工具能換：vue-tsc 要呼叫編譯器的 API，7.0 沒有。b 混淆了這兩件事。c target 跟這件事無關。d 說反了，7.0 是不懂 .vue，不是只懂 .vue。

常見錯誤

  • 以為 import { type X } 等於 import type { X }：前者還會留下 import {} from '…'，套件照樣被載入。整行都是型別就把 type 寫在 import 後面。
  • 替要注入的 class 用 import type：class 在執行時消失，DI 的 metadata 只剩 Function。要注入的 class 用一般 import。
  • 以為 .d.ts 會產生程式碼：declare const X 只是承諾，執行時沒有人提供就是不存在。宣告檔描述現實，不製造現實。
  • 用 skipLibCheck 或 any 掩蓋自己寫錯的宣告：錯誤只是被藏起來，執行時照樣出事。自己的型別寫在 .ts 裡，讓它被檢查。
  • 用 declare global 到處塞全域變數：全專案共用、誰都能改。只用來描述執行環境真的提供的全域。
  • nodenext 的相對匯入忘了寫 .js：import './orders.service' 在 nodenext 下報錯，要寫 './orders.service.js'；寫的是編譯後的檔名。
  • 照抄別人的 tsconfig 卻不知道每一行在做什麼：出事時不知道改哪裡，也可能抄到 7.0 已經刪掉的舊選項。每一行都要說得出理由。
  • 舊專案一次打開所有嚴格旗標：幾千個錯誤改不完，最後全部關掉。一次開一個，改完合併再開下一個。

小結

  • 收據程式搬進新專案的第一個錯誤 TS1484：只為了型別的匯入用 import type，編譯後整行消失；import { type X } 仍會載入模組。verbatimModuleSyntax 要求你標清楚，讓一次看一個檔案的工具也能正確轉譯。要注入的 class 例外，用一般 import。
  • 型別從哪裡來：.d.ts 和 declare 只有形狀、沒有實作，寫錯了 TypeScript 不會發現；第三方型別來自套件本身或 @types/*。找不到 process，是因為 TypeScript 6／7 的 types 預設 []，要列出 "node"。
  • 替 Request 加上登入的店員：靠 interface 的宣告合併，用 declare module 擴充別人的模組、用 declare global 擴充全域。擴充只改型別，值要有人真的放進去。
  • strict 是一組旗標；noUncheckedIndexedAccess 讓索引讀取加上 undefined，exactOptionalPropertyTypes 分開「沒有這個鍵」和「值是 undefined」。修法要看業務意義，不是補 ! 讓錯誤消失。
  • tsconfig 的每一行都要說得出理由：nodenext 要寫 .js、types 決定載入哪些型別、sourceMap 加 --enable-source-maps 讓 stack trace 對回 .ts。NestJS 要先編譯，因為 Node 只擦型別、處理不了裝飾器。
  • TypeScript 7 是原生編譯器，但 7.0 沒有 API，Vue 工具和 NestJS 的 nest build 暫時留在 6.0；舊專案一次開一個旗標，每個旗標一個 PR，CI 跑 tsc --noEmit。

練習 8：咖啡店後台的 GET /me 直接 return user，User class 裡有 private passwordHash。code review 時最該怎麼改？

練習 10：CheckoutService 的建構子寫 private readonly gateway: PaymentGateway，PaymentGateway 是 interface，module 裡也登記了 LinePayGateway。啟動時報 Nest can't resolve dependencies，怎麼修？

✓ interface 編譯後不存在，design:paramtypes 裡只剩 Object，容器不知道要給什麼。用 token 加 @Inject，或把契約改成 abstract class，它是值，metadata 留得下來。b 錯在 implements 只在編譯時檢查，執行時沒有留下任何痕跡。（第 23、24 課）

練習 11：同事跑了 lint 的自動修正，把「只當型別用」的匯入都改成 import type。編譯沒有任何錯誤，Nest 啟動時卻解析不了 OrdersService 的依賴。先查什麼？

✓ 建構子參數的型別在 metadata 裡是執行時的值；import type 讓 class 在執行時消失，metadata 只剩 Function，編譯不報錯，啟動才失敗。要注入的 class 一律用一般 import。a 是新加服務時常見的原因，但這次只動了匯入，module 沒變。（第 24、25 課）

練習 12：舊的 NestJS 專案正式環境一切正常，測試從 Jest 換成 Vitest 之後，所有有注入的測試都報 Nest can't resolve dependencies。原因是？

✓ design:paramtypes 是編譯時產生的，轉譯工具不做，容器就讀不到參數型別。NestJS 文件的做法是讓 Vitest 改用 SWC（unplugin-swc）。換建置或測試工具前先問它支不支援裝飾器 metadata，並跑一個有注入的測試確認。b 錯在 Nest 的 DI 靠參數裝飾器和 metadata，標準裝飾器兩個都沒有。（第 24 課）

練習 13：同事想省掉建置，用 Node 24 直接執行 node src/main.ts 跑 NestJS 專案，會怎樣？

✓ Node 只做型別剝除：參數屬性要多產生欄位宣告和賦值，丟 ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX；裝飾器它不處理，是語法錯誤。所以 NestJS 專案要先編譯。c 錯在根本走不到注入那一步，語法就先被擋下。（第 23、24 課）

練習 14：開了 noUncheckedIndexedAccess 之後 prices[name] 報可能是 undefined，同事這樣修。哪裡會出事？

function lineTotal(prices: Record<string, number>, name: string, qty: number) {
  return (prices[name] ?? 0) * qty
}

✓ 錯誤消失了，但「找不到」被當成合法的價格。找不到時該丟錯、回 404 還是給預設值，要看業務意義決定；code review 盯的是修法，不是旗標有沒有過。b 錯在 ?? 只在 null 或 undefined 時用右邊，會把 0 也換掉的是 ||。（第 25 課）

這個階段的重點整理成一頁圖解。

補充與查表

主線用不到、但在別的專案或讀舊文章時會遇到的細節，查表用，不用背。

  • TypeScript 6.0 改了預設值，7.0 刪了舊選項：6.0（2026-03）的新預設：strict: true、module: esnext、target 是最新規格（es2025）、types: []、rootDir 是 tsconfig 所在資料夾。6.0 棄用、7.0 不再支援：target: es5、moduleResolution: node（node10）與 classic、baseUrl、outFile、module: amd／umd／systemjs，以及把 esModuleInterop 設成 false。網路上舊文章的 tsconfig 常有這些，照抄進新專案會直接報錯。
  • 不編譯、用 Node 直接執行 .ts 的專案：Node 24 只擦掉型別就執行（Node 課第 5 課）。這時 tsconfig 建議開 erasableSyntaxOnly（第 15 課）、verbatimModuleSyntax，加上 rewriteRelativeImportExtensions 讓你在原始碼寫 ./x.ts、輸出時改成 ./x.js。NestJS 專案不適用，原因見第 5 節。
  • noImplicitOverride：另一個 strict 以外常見的旗標，覆寫父類別方法必須寫 override（第 23 課）。
  • TypeScript 6 與 7 並存：需要兩版並存時，可以裝 @typescript/typescript6，它提供 tsc6 指令。
  • 型別檢查抓不到、要靠 lint 的錯誤：lint 是照規則掃描程式碼、找出可疑寫法的工具，像你在 Vue 專案用的 ESLint。NestJS 12 starter 的 lint 用 oxlint；像 no-floating-promises（呼叫 async 函式卻沒 await，第 9 課）這種需要型別資訊的規則，要加 --type-aware 並安裝 oxlint-tsgolint 才會檢查。
