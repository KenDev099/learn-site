階段 6：實戰 · 第 27 課

用型別設計狀態與錯誤：Result、branded type、狀態機

咖啡店的訂單模組上線一個月，出了三件事故。第一件：「庫存不足」的錯誤沒人處理，一路丟到最外層，客人看到的是 500。第二件：店員把顧客編號當成訂單編號傳進「取消訂單」，取消到別人的單。第三件：一筆已經完成的訂單被改回「已取消」，又退了一次款。三件事的共同點是：程式都能編譯，型別也都「對」，只是型別寫得太寬，number、string、一堆可選欄位，沒有把業務規則寫進去，編譯器就沒有東西可以檢查。

這一課的任務是把這個訂單模組的型別改寫到「這三件事故寫不出來」：能失敗的函式在簽章上寫明會怎麼失敗，不同意義的編號不能互換，訂單只能照規定的順序換狀態，每個狀態該有的資料一定在。用型別描述業務規則，叫做設計領域模型（domain model）；領域指的是這個系統服務的業務，這裡就是咖啡店的下單、付款、取消。

這課的路線：
  1. 第一件事故：「庫存不足」該丟例外還是放進回傳值？寫出 Result，讓呼叫者不處理失敗就編譯不過；錯誤種類變多時，再用 ok() 和窮舉確保每一種都有人處理。
  2. 第二件事故：訂單編號和顧客編號都是 number，用 branded type 讓傳錯在編譯時就報錯。
  3. 第三件事故：已完成的訂單為什麼改不回已取消？用狀態機把允許的轉換寫成資料，在編譯時、執行時、資料庫三層擋下非法的轉換。
  4. 收尾：每個狀態帶自己的資料，讓「已完成卻沒有付款時間」這種組合寫不出來。
  5. 取捨：這些型別各有成本，什麼時候值得，資料庫的列、領域型別、API 回應在哪裡轉換。
這課會用到：
  • 第 4 課的「預期中的失敗 vs 程式錯誤」：庫存不足是業務上會發生的事，要好好處理；讀到 undefined 的屬性是 bug，該讓它爆出來修掉。
  • 第 16 課的可辨識聯合與 assertNever：用共同的欄位（像 kind）區分每一種情況，switch 的 default 呼叫 assertNever，漏處理一種就編譯不過。
  • 第 19 課的 Result<T, E>：成功時帶值、失敗時帶錯誤的泛型聯合 { ok: true; value: T } | { ok: false; error: E }。
  • 第 20 課的 as const satisfies：as const 保留字面值，satisfies 檢查形狀但不改推論，資料寫一次、型別從它推出來。

「庫存不足」該丟例外，還是放進回傳值？

從第一件事故開始。下單的第一步是保留庫存：reserve(商品編號, 數量) 檢查庫存夠不夠，夠就回傳扣完後剩下的數量。原本的寫法是庫存不夠就丟例外。先看它的簽章：reserve(productId: number, quantity: number): number，只說「回傳 number」，完全看不出它會失敗。執行下面這格，注意兩件事：程式裡沒有任何紅線，以及錯誤是在哪裡被接住的。

這裡有 try／catch，所以錯誤被接住了。但這個 try／catch 是寫的人「記得」要加的，編譯器不會提醒。事故當天的呼叫者看簽章以為一定成功，沒有加，例外就一路往上丟，丟到 API 最外層，變成 500。問題的根源在於：例外不是函式型別的一部分。TypeScript 的函式型別只描述參數和回傳值，不記錄「會丟出什麼」，所以編譯器沒辦法檢查呼叫者有沒有處理。

庫存不足是每天都會發生的事，呼叫者不只要處理，還要依「是哪一種失敗」決定怎麼回應：商品不存在回 404，庫存不夠回 409 並告訴客人剩幾杯。既然回傳值是編譯器看得到的，就把失敗也放進回傳值。用第 19 課的 Result：成功時是 { ok: true, value }，失敗時是 { ok: false, error }。錯誤本身也寫成可辨識聯合，用 type 欄位區分種類，每一種帶它需要的資料（庫存不足要帶剩幾杯）。執行下面這格，先看第一個 console.log 的紅線：

差別在簽章：Result<number, ReserveError> 直接寫出「可能失敗，失敗時是這兩種之一」。它怎麼逼呼叫者處理？r 的型別是兩種物件的聯合，只有 ok: true 那一種有 value，所以沒先檢查就讀 r.value 會報 TS2339。寫了 if (r.ok) 之後，TypeScript 依 ok 的值把 r 縮小成成功的那一種，才讀得到 value；else 分支裡 r 是失敗的那一種，再依 r.error.type 縮小，out_of_stock 分支才讀得到 available。這就是第 16 課的縮小，只是現在用來保證「失敗一定被看到」。

那是不是所有錯誤都要改成 Result？不是。分法延續第 4 課，關鍵問題是「呼叫者能不能、該不該處理它」：

失敗的種類做法例子
預期中的錯誤（expected error）：業務上本來就會發生，呼叫者要依種類處理回傳 Result庫存不足、優惠碼過期、訂單狀態不允許這個操作
程式錯誤（bug）丟例外（exception），讓它往上到邊界、記 log、修程式讀 undefined 的屬性、assertNever 收到沒列出的值
基礎設施故障丟例外，邊界回 500 或重試資料庫斷線、外部 API 逾時

為什麼資料庫斷線不包成 Result？因為呼叫鏈上幾乎每一層都沒辦法處理它：reserve 不能修資料庫，checkout 也不能。包進 Result 只會讓每個函式的錯誤型別都多一種，每一層都要寫「收到就往上傳」，最後還是傳到最外層。程式錯誤也一樣，正確的處理是修程式，不是在執行時繞過它。

這兩種失敗最後在邊界會合。邊界指的是程式和外界交接的地方，對 API 來說就是收到 HTTP 請求、決定回什麼的 handler。handler 把 Result 的錯誤種類對應成 404、409、422 這類有意義的狀態碼，例外則統一轉成 500 並記 log。NestJS 用 exception filter 集中做這件事（NestJS 課第 8 課）。

同一種失敗只用一種方式表示。庫存不足在 reserve 回傳 err、在 checkout 卻 throw，呼叫者兩種都得處理，遲早漏掉一種。一個模組先決定好：哪些是 Result 的錯誤種類，其他的一律是例外。
💡 實務上：錯誤種類要和前端一起定
Result 的錯誤種類最後會變成 API 回應，前端靠它決定畫面：咖啡店 App 收到 out_of_stock 就顯示「只剩 1 杯，要改數量嗎？」，收到 coupon_expired 就把優惠碼欄位標紅。所以回應裡要有穩定的錯誤代碼（code）和需要的資料（剩幾杯），不要只給一句中文訊息讓前端去比對字串。開新 API 時，資深工程師會先和前端、PM 對一份清單：「哪些失敗使用者要看到不同的提示？」清單外的一律當例外，回 500 加一個 request id，讓客服回報時能在 log 查到；堆疊追蹤（stack trace）不要回給使用者。第一件事故如果當初有這份清單，「庫存不足」就會是清單上的一項，而不是一個沒人接的例外。

第一件事故的最小答案有了：失敗寫進回傳型別，呼叫者不檢查就編譯不過。但這只解決了「忘記檢查 ok」。錯誤種類會隨需求變多，某天新增了一種錯誤，所有判斷錯誤種類的地方都要跟著改，誰來提醒？

錯誤種類變多時，怎麼確保每一種都有人處理？

結帳流程保留完庫存，下一步是套用優惠碼。優惠碼的失敗比庫存多一種：找不到、已過期、未達最低消費。三種錯誤比較能看出「新增一種時會漏掉」的問題，所以這一節換成優惠碼示範。這格同時做兩件事：用一個小函式 ok() 省掉每次手寫 { ok: true, value }，以及在把錯誤轉成訊息的 toMessage 裡用 switch 加 assertNever 窮舉。執行後看輸出的三行，各對應一種情況：

assertNever 怎麼做到「漏處理就編譯不過」？switch 每處理一個 case，TypeScript 就把那一種從 e 的型別裡扣掉。三種都處理完，走到 default 時 e 已經沒有任何可能，型別是 never，正好符合 assertNever(x: never) 的參數。假設下個月加了第四種錯誤 { type: 'used_up' }，卻忘了在 toMessage 加 case：走到 default 時 e 還剩 used_up 那一種，不是 never，呼叫 assertNever(e) 就報錯，編譯器把每個漏改的 switch 都標出來。萬一執行時真的收到沒列出的值（例如資料庫裡有舊資料），assertNever 會丟例外，這屬於程式錯誤，正好照上一節的分法往上丟。

如果 default 寫成 return '未知錯誤'，e 不必是 never 也能編譯，新增錯誤種類時編譯器就不會提醒，使用者只會看到一句含糊的訊息。

再看 ok 的回傳型別為什麼寫 Result<T, never>。ok(200) 只知道成功的值是 number，不知道呼叫它的函式失敗時會是哪一種錯誤，applyCoupon 是 CouponError，reserve 是 ReserveError。never 是沒有任何值的型別，「一個不可能存在的值」放到哪裡都不會出錯，所以 never 可以指派給任何型別：Result<number, never> 放得進 Result<number, CouponError>，也放得進 Result<number, ReserveError>。一個 ok 就能在每個回傳 Result 的函式裡用。對應的 err 反過來，回傳 Result<never, E>，練習 1 會寫。這種形狀不是這課自創的，第 26 課的 zod 也用類似的回傳值，細節見課末「補充與查表」。

到這裡，第一件事故擋住了：失敗寫在簽章上，每一種錯誤都被窮舉處理。第二件事故的性質不同，函式沒有失敗，它成功執行了，只是收到的是錯的值：兩個意義不同的編號，型別都是 number。

訂單編號和顧客編號都是 number，傳錯了怎麼讓編譯器發現？

先重現第二件事故。cancelOrder 要的是訂單編號，呼叫的人卻傳了顧客編號。執行後看兩個地方：沒有任何紅線，以及印出來的是哪一筆訂單：

為什麼沒報錯？第 14 課說過，TypeScript 是結構型別：只看值的形狀，不看它叫什麼名字。就算寫了 type OrderId = number、type CustomerId = number，這兩個也只是 number 的別名，形狀一模一樣，互相傳來傳去都合法。所以要讓它們不相容，就得讓兩者的形狀真的不同。

做法叫 branded type（品牌型別）：在 number 上「貼一個標籤」，這個標籤只有型別系統看得到，執行時不存在。寫法是第 14 課的交集型別：number & { 標籤屬性 }，意思是「既是 number，又有這個屬性」。一般的數字沒有這個屬性，放不進來；貼了標籤的值仍然是 number，能做加法、能傳給要 number 的地方。訂單編號貼 'OrderId'，顧客編號貼 'CustomerId'，兩者的形狀就不同了。

標籤屬性的鍵要用什麼？這課用 unique symbol。它是 symbol 的一種型別，特別之處是每一次宣告都是一個獨一無二、和其他都不相容的型別，只能用在 const 宣告（和類別的 static readonly 屬性）上。宣告時前面加 declare：declare 的意思是「只告訴型別系統有這個值，不產生任何程式碼」，編譯後整行消失，所以這個 symbol 從頭到尾只存在型別裡。

最後一個問題：普通的 number 要怎麼變成貼了標籤的型別？只能用型別斷言 as。但如果每個人都能隨手寫 n as OrderId，標籤就沒有意義了。所以把 as 集中到一個函式裡：先驗證這個數字真的是合法的編號，通過了才貼標籤回傳。這種「驗證完才給你更精確型別」的建構函式叫 smart constructor，它是產生品牌型別的唯一入口。

逐行對照：

  • number & { readonly [brand]: 'ProductId' }：[brand] 是第 14 課的計算屬性名稱，用變數 brand 當鍵。quantity 是一般的 number，沒有這個屬性，所以 priceOf(quantity) 報 TS2345；toProductId(2) 回傳的值有，所以放得進去。
  • 最後一行印出 3 number {"id":2}：declare const 編譯後消失，n as ProductId 也只是會被擦掉的型別斷言，執行時沒有包裝物件，typeof 還是 'number'，JSON 也是普通數字。品牌在執行時零成本。
  • 標籤的值決定品牌是否不同。兩個品牌如果都寫 'Id'，形狀又一樣了，會互相相容。

smart constructor 是第 26 課「parse, don't validate」的延伸：檢查完不是回傳 true／false，而是回傳一個型別更精確的值，之後的程式不用再檢查。拿到 ProductId，就代表它已經驗證過是正整數。

品牌的保護只到 as 為止。到處寫 123 as OrderId 等於繞過驗證，型別說它是合法的訂單編號，實際上沒人檢查過。把 as 限制在 smart constructor 裡，code review 時看到別的地方出現 as OrderId 就要問。

品牌不是越多越好。適合加的地方有一個共通點：搞混了會出事，而且型別本來分不出來。例如各種 ID、以最小單位整數表示的金額（第 5 課）、已驗證過的 Email、已經跳脫過的 HTML 字串。

💡 實務上：從最容易傳錯的 ID 開始加品牌
最常出事的是一個函式同時收好幾個同型別的 ID，例如 refund(orderId, customerId, staffId)，或路由 /customers/:customerId/orders/:orderId。ID 是 UUID 字串時一樣會傳錯，品牌照樣適用。既有專案不必一次全改：通常是出過一次「ID 傳錯」的事故後，先從那個 ID 加品牌，讓編譯器列出所有要改的地方，一個 PR 改一種。咖啡店這次就該從 OrderId 和 CustomerId 開始。導入時也要先說好在哪裡轉換：資料進來的地方（API handler 解析路由參數、資料庫查詢回傳時）就呼叫 smart constructor，往內的函式只收品牌型別。

第二件事故擋住了：編號不會再傳錯。第三件事故又是另一種問題，訂單編號是對的，錯的是「時機」：一筆已完成的訂單，不該再被改成已取消。這不是某個值的型別錯了，而是狀態改變的順序錯了。

已完成的訂單，怎麼讓它改不回已取消？

訂單在任何時刻都處於幾種狀態之一：待付款、已付款、已完成、已取消。從一個狀態變到另一個狀態叫轉換（transition），而業務規則規定了只有某些轉換是允許的：待付款可以付款或取消，已付款可以完成或取消退款，已完成和已取消就是終點。把「有哪些狀態、允許哪些轉換」明確定義出來的設計，叫做狀態機（state machine）。畫成圖就是：

第三件事故就是走了一條圖上沒有的箭頭。原本的程式只有一個 order.status = to，任何狀態都能改成任何狀態，規則只存在於 PM 的腦袋裡。要擋住它，先把箭頭寫成資料：一個物件，鍵是狀態，值是那個狀態可以去的地方。再用第 20 課的方法從這份資料推導出型別，「哪些轉換合法」就只有這一份定義，型別檢查和執行時檢查都讀它，不會兩邊不一致。

下面用吧檯的製作單示範。客人付款後，吧檯會為每杯飲料開一張製作單，它有五個狀態（排隊 → 製作中 → 完成 → 已取杯，排隊時可以取消），比訂單多一個，方便看出推導出來的型別；訂單版本留給練習 3，做法完全相同。執行後看三個地方：advance(t2, 'picked_up') 的紅線，以及輸出的兩行錯誤訊息：

這格分三層讀。第一層是資料：NEXT 用 as const 保留每一格的字面值和唯讀，satisfies Record<TicketStatus, readonly TicketStatus[]> 檢查五個狀態都列到、每一格只放合法的狀態，但不改變推論出來的型別。這兩個缺一不可：沒有 as const，陣列不唯讀，誰都能在執行時 push 一條新轉換進去；改用型別註記 const NEXT: Record<…> = … 取代 satisfies 更糟，每一格的型別都變成「所有狀態」，型別擋不住任何轉換。

第二層是推導：NextOf<S> 是 (typeof NEXT)[S][number]，先用狀態 S 取出那一格的唯讀 tuple，再用 [number] 取出所有元素的聯合，所以 NextOf<'queued'> 是 'brewing' | 'cancelled'，終點的 NextOf<'picked_up'> 是 never。advance 的第二個參數型別是 T extends NextOf<S>：t2 的狀態是 'brewing'，下一步只能是 'ready'，傳 'picked_up' 就報 TS2345。

第三層是執行時檢查。advance 裡面還是查了一次 NEXT，因為型別擋住的只有「寫在程式裡、狀態已知」的呼叫。最後兩行的 fromDb 是從資料庫讀出來的，型別只知道它是五種狀態之一，NextOf<TicketStatus> 是所有可能的下一步，所以 advance(fromDb, 'brewing') 編譯得過，要靠執行時的檢查擋下來。不只資料庫，其他服務送來的資料、使用者請求帶的狀態也一樣，型別只知道是某一種狀態，都要靠執行時檢查。這一行裡 allowed 特意標成 readonly TicketStatus[]：NEXT[t.status] 是好幾種 tuple 的聯合，直接呼叫 includes 會報錯，先放寬成一般的唯讀陣列再檢查。這是型別註記，不是 as，寫錯了照樣會報錯。

型別和執行時檢查都有了，同一類事故還有第二種成因：就算轉換規則都對，兩個請求同時取消同一筆 paid 訂單，仍會退兩次款。想像這個情境：店員按了「取消並退款」，同一時間客人在 App 上也按了取消。兩個請求各自從資料庫讀到 paid，各自檢查「paid 可以變 cancelled」都通過，各自退款、各自寫回，後寫的蓋掉先寫的。程式裡的檢查發生在讀取之後、寫入之前，中間這段時間別人可能已經改了資料，所以最後一層要交給資料庫：在寫入的那一刻再確認一次狀態。做法是條件式 UPDATE（PostgreSQL 課第 19 課），把「目前狀態必須是哪些」寫進 WHERE，影響 0 列就代表狀態已經被別人改掉了，這時不要退款，回 409：

UPDATE orders SET status = 'cancelled'
WHERE id = $1 AND status IN ('pending', 'paid');   -- 影響 0 列：已經是 done 或 cancelled，回 409

三層各擋一種情況：型別擋住寫在程式裡的非法轉換，執行時檢查擋住外來資料，資料庫擋住並發寫入。資料庫這一層還有另一種寫法，見課末。

開發前要先確認每條箭頭是誰觸發的：客人、店員、排程（例如待付款太久自動取消），還是金流。金流付款完成後，會主動呼叫我們的 API 通知結果，這種「對方在事件發生時呼叫你」的機制叫 webhook。金流為了確保通知送到，同一個通知可能送兩次以上。

💡 實務上：狀態圖是和 PM、客服對齊規則的文件
上面那張狀態圖 PM 和客服也看得懂，開發前拿它確認規則，比事後讀程式碼有效。資深工程師會逐條箭頭問：誰觸發的？可以觸發幾次？以金流 webhook 為例，第二次收到「付款完成」時訂單已經是 paid，應該當成功忽略，而不是報錯讓金流一直重試。另外通常會多一張狀態變更紀錄表（誰、什麼時間、從哪個狀態到哪個狀態），客服查「為什麼這筆被取消」時就靠它，查這類事故時，也是靠這張表才查得出是哪個請求、什麼時間改的狀態。

轉換的順序擋住了，但訂單型別本身還有漏洞：status 只是一個欄位，付款時間、完成時間、取消原因都是可選欄位，跟 status 沒有關係。狀態是 done 的訂單可能沒有付款時間，退款程式讀 paidAt 時只能祈禱它有值。

每個狀態帶的資料不同，怎麼讓錯誤的組合寫不出來？

先看目前的訂單型別能寫出什麼。第 16 課看過：一個型別塞滿可選欄位，錯誤的組合照樣寫得出來。執行後看兩件事：weird 這個「已完成卻有取消原因、沒有付款時間」的訂單沒有任何紅線，以及讀 paidAt 時只能用 ?. 和預設值應付：

問題出在型別描述的是「所有欄位的聯集」，而不是「每個狀態實際長什麼樣子」。三個可選欄位、四種狀態，型別允許的組合有 4×2×2×2＝32 種，業務上合法的只有四種。剩下的組合雖然不該出現，但只要型別允許，就會有某段程式（某次手動修資料、某個漏改的分支）把它寫出來，而每個讀訂單的地方都得防著它。

反過來想：如果型別只允許那四種合法的組合，錯誤的組合寫都寫不出來，就不用到處檢查。這個原則叫讓不合法的狀態無法表示（make illegal states unrepresentable）。做法是把每個狀態寫成一個獨立的型別，各自帶自己必填的資料，再組成可辨識聯合。函式也只收它需要的那一種狀態。下面這格只寫了兩種狀態，先看形狀，四種的完整版本是練習 4。執行後看最後一行的紅線：

receipt 的參數是 PaidOrder，所以它裡面讀 order.paidAt 不用判斷 undefined，型別保證一定有值。orders[1] 的型別是 Order，可能是待付款，直接傳進去就報 TS2345。要從 Order 拿到 PaidOrder，得經過 asPaid：它檢查 status，不是 paid 就丟例外，是的話 TypeScript 已經把 order 縮小成 PaidOrder，直接回傳，不需要 as。

這裡又看到「parse, don't validate」。比較 isPaid(order): boolean 和 asPaid(order): PaidOrder：前者回傳 true 之後，「已經檢查過」這個資訊就丟了，下一個函式拿到的還是 Order，還得再檢查一次；後者把「已經檢查過」記在型別上，往下傳的每一層都看得到。這和上一節的 smart constructor 是同一個想法：檢查的結果不是一個布林值，而是一個更精確的型別。

💡 實務上：前端的載入狀態也是同一招
前端最常見的寫法是 isLoading、error、data 三個獨立欄位，結果出現「isLoading 是 true 但 error 也有值」這種畫面不知道該顯示什麼的組合。改成 { status: 'loading' } | { status: 'error'; error: Error } | { status: 'success'; data: Order[] }，元件裡用 switch (state.status) 分別畫骨架畫面、錯誤提示和列表，每個分支只拿得到該有的資料。咖啡店訂單頁依訂單狀態顯示不同按鈕（待付款顯示「付款」、已付款顯示「取消並退款」）也一樣：每個狀態一個元件或分支，不要一堆 if (order.paidAt && !order.cancelReason)。

三件事故都有了對應的型別：Result、品牌 ID、狀態轉換表加上每個狀態一個型別。但訂單模組的型別也因此多了好幾倍。下一個問題是資深工程師一定會問的：這些型別值得嗎？該用在哪裡、不該用在哪裡？

這些型別值得寫嗎？成本與邊界

每一招都有代價，而且代價通常落在「資料進出」的地方：

技巧成本值得用在
Result每一層都要判斷、往上傳；和只會 throw 的函式庫混用時要轉換呼叫者真的要依錯誤種類做不同處理的業務失敗
branded type每個進入點都要呼叫 smart constructor：資料庫的列、JSON、ORM 回傳的都是普通 number；錯誤訊息比較長；新人要學ID、金額、已驗證的字串
每個狀態一個型別型別變多；JSON 往返後 Date 變字串，進來時要重新 parse（第 26 課）狀態錯了會出事的流程：訂單、付款、退款

表裡的成本有一個共同點：都發生在資料跨越模組邊界的時候。資料庫回傳的列是普通的 number 和字串，對外的 API 回應也只能是 JSON，品牌和 Date 都留不住。所以實務做法是只在模組邊界轉換一次，讓品牌和狀態型別只活在模組內部：

  1. 資料進來：repository 是專門負責讀寫資料庫的那一層，其他程式透過它拿資料，不直接寫 SQL。資料庫的列（普通型別）在 repository 裡 parse 成領域型別，ID 呼叫 smart constructor 貼上品牌，status 和對應的欄位組成狀態聯合。
  2. 業務邏輯：只碰領域型別，下單、付款、取消都在這一層，享受前面所有的檢查。
  3. 資料出去：轉成 DTO。DTO 是 data transfer object 的縮寫，指專門用來在系統之間傳遞的資料形狀，例如 API 回應的 JSON；第 21 課用 Pick 從完整型別推導過它。

這樣外面的人（前端、其他服務、資料庫）不用知道品牌和狀態型別的存在，轉換的程式碼也只有兩處，不會散落在每個函式裡。

反過來，不是每個地方都值得。商品名稱、備註這種搞混了也不會出事的字串，不需要品牌；只有兩種狀態、沒有額外資料的布林旗標，也不需要狀態機。判斷標準是：這裡出錯的代價，比多寫的型別貴嗎？咖啡店的三件事故分別造成了 500、取消錯單、重複退款，都是值得的地方。接下來的練習，你會親手把這三件事故的型別各寫一次。

練習

練習 1：寫 ok()、err()，回傳型別分別寫成 Result<T, never>、Result<never, E>。再寫 placeOrder(stock, items)：stock 是「商品編號 → 庫存」，不在裡面的商品庫存當 0；依序檢查「購物車是空的」→「每一筆的數量是不是正整數」→「每一筆的庫存夠不夠」（同一個商品出現在好幾筆時，要把前面幾筆的數量加起來一起比，不然兩筆各點 1 杯會騙過只剩 1 杯的庫存），遇到第一個問題就回傳對應的 OrderError；都沒問題回傳 { lines: 筆數, totalQuantity: 總數量 }。這一步只檢查，不能改 stock（扣庫存是確定下單之後的事）。最後寫 describeError，三種訊息是「購物車是空的」「商品 1 的數量不正確」「商品 2 庫存不足，只剩 1 個」，用 switch 加 assertNever：資料裡出現沒列出的錯誤種類時要丟錯。

練習 2：起始程式的 OrderId、CustomerId 都只是 number，最後一行把顧客編號傳給 findOrder 卻沒報錯。把它們改成兩個不同的品牌型別（用 unique symbol 當鍵），並讓 toOrderId、toCustomerId 變成 smart constructor：不是正整數就丟 RangeError。改好之後，最後一行會出現紅線，把它改成傳 order.id。

練習 3：把上面的訂單狀態圖寫成程式。TRANSITIONS 用 as const satisfies Record<OrderStatus, readonly OrderStatus[]>，列出每個狀態可以去哪裡（順序照圖：pending 是 paid、cancelled；paid 是 done、cancelled）；NextStatus<S> 從 TRANSITIONS 推導出 S 的下一步；canTransition(from, to) 回傳能不能轉換；transition(order, to) 回傳狀態改變後的新訂單，原訂單不能變。已知狀態的非法轉換要在編譯時報錯；執行時遇到（資料來自資料庫，型別只知道是 OrderStatus）要丟 IllegalTransitionError。

練習 4：起始程式的 Order 用可選欄位表示不同狀態，complete 連待付款的訂單都收。改成四個型別的聯合，每個都有 status、id、total，另外：PaidOrder 有 paidAt: Date；DoneOrder 有 paidAt 和 doneAt: Date；CancelledOrder 有 cancelReason: string；PendingOrder 沒有額外欄位。再改寫 pay(order: PendingOrder, at) 回傳 PaidOrder、complete(order: PaidOrder, at) 回傳 DoneOrder，都回傳新物件，不改傳入的訂單。

練習 5：查詢商品時「找不到這個商品」和「資料庫連線斷掉」，各自該怎麼表示？

✓ 找不到商品是業務上每天都會發生的事，呼叫者要處理，放進回傳型別才不會被忘記。資料庫斷線是基礎設施故障，路上每一層都處理不了，包成 Result 只會讓每個函式多一種要往上傳的錯誤。a 讓呼叫者從簽章看不出會失敗；c 把處理不了的錯誤也塞給每一層。

練習 6：把 orderId: number 改成品牌型別 OrderId，執行時的成本是什麼？

✓ declare const brand 和 as OrderId 在編譯後都被擦掉，typeof 還是 'number'，JSON 也一樣。a、b 描述的是「把值包進物件」的做法（例如 class OrderId），那才有包裝和拆開的成本。真正的成本在開發端：每個進入點都要呼叫 smart constructor。

練習 7：transition 的型別已經擋住 done → cancelled，執行時的檢查和資料庫的條件式 UPDATE 還需要嗎？

✓ 型別只檢查寫在程式裡的呼叫，擋不住外來的資料（b 錯）。執行時檢查擋得住外來資料，但擋不住並發：兩個請求都讀到 pending、都檢查通過，後寫的蓋掉先寫的（c 不夠）。UPDATE … WHERE status IN (…) 讓資料庫在寫入的那一刻再確認一次，三層各擋一種情況。

常見錯誤

  • 同一種失敗有時 throw、有時回傳 err：呼叫者要同時寫 try／catch 和 if (!r.ok)，遲早漏一個。模組先決定好哪些失敗是 Result 的種類，其他一律丟例外。
  • 錯誤用字串表示：err('庫存不足') 讓呼叫者只能比對字串，改一個字就壞，也帶不了剩幾個這種資料。用帶 type 的可辨識聯合。
  • 窮舉時寫 default: return '未知錯誤'：新增錯誤種類時編譯器不會提醒，資料錯了也被吞掉。default 交給 assertNever。
  • 到處用 as 製造品牌型別：123 as OrderId 繞過驗證，品牌就失去意義。as 只出現在 smart constructor 裡。
  • 狀態轉換只在前端擋：按鈕藏起來不代表 API 不會收到請求。後端在型別、執行時、資料庫三層都要擋。
  • 用一堆可選欄位表示不同狀態：paidAt?、doneAt?、cancelReason? 可以任意組合，每個使用的地方都要判斷 undefined。改成每個狀態一個型別的聯合。
  • 每個字串都做成品牌型別：商品名稱、備註也加品牌，程式到處是轉換，錯誤訊息又長又難讀。只用在搞錯會出事的地方：ID、金額、狀態。

補充與查表

  • zod 的 safeParse 也是 Result：第 26 課的 safeParse 回傳 { success: true, data } 或 { success: false, error }，欄位名稱不同，概念和這課的 Result 一樣。
  • Result 函式庫：社群有專門的 Result 函式庫，提供 map、andThen 這類串接方法。自己寫十幾行通常就夠；團隊大、整個專案都用 Result 串接時，再考慮引入函式庫，讓大家用同一套寫法。
  • 為什麼品牌的鍵用 unique symbol 而不是字串鍵 __brand：symbol 鍵不會和真的欄位撞名；只要 brand 不 export，模組外的程式也寫不出這個型別，只能透過 smart constructor 取得。字串鍵誰都能手寫出同樣的形狀。
  • 用 trigger 檢查狀態變更：除了條件式 UPDATE，也可以用 trigger 在資料庫裡檢查每一次狀態變更（PostgreSQL 課第 23 課），連手動改資料庫都擋得住。

小結

  • 第一件事故（庫存不足變 500）：預期中的業務失敗放進回傳型別 Result<T, E>，錯誤寫成可辨識聯合，用 switch＋assertNever 窮舉；bug 與基礎設施故障繼續丟例外，到邊界再統一轉成 HTTP 回應。
  • ok() 回傳 Result<T, never>、err() 回傳 Result<never, E>，never 能放進任何型別，所以同一個 ok 能用在每個回傳 Result 的函式。
  • 第二件事故（編號傳錯）：branded type number & { readonly [brand]: 'OrderId' }，用 unique symbol 當鍵，區分意義不同的 number；只透過會驗證的 smart constructor 產生，執行時零成本。
  • 第三件事故（完成的訂單被取消）：允許的轉換寫成 as const satisfies 的資料，再推導出 NextStatus<S>；已知狀態的非法轉換編譯時就報錯，外來資料靠執行時檢查，並發靠資料庫的條件式 UPDATE。
  • 讓不合法的狀態無法表示：每個狀態一個型別、帶自己的資料，函式只收它需要的狀態；檢查完回傳更精確的型別，而不是 boolean。
  • 這些技巧有成本，只用在搞錯會出事的地方，並在模組邊界轉換：資料庫的列 → 領域型別 → DTO。
