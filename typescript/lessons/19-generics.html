階段 4：函式、泛型與型別運算 · 第 19 課

泛型

咖啡店的後端有商品、訂單、顧客三種資料。前幾課你替每一種資料寫了型別，上一課也學會替函式寫型別。現在後台要做三個列表頁，每一種資料都需要同一組操作：取第一筆、依 id 找一筆、用分頁格式回傳；寫測試時，還需要一個不用連資料庫的假儲存區。

照目前會的寫法只有兩條路。第一條是每種資料各寫一份：三份幾乎一樣的程式，修一個 bug 要改三個地方，總有一份會忘記。第二條是只寫一份、參數收 any：程式不重複了，但拿出來的東西也是 any，把 price 打成 prise 不會有任何紅線，要等畫面上的價格欄變成空白才發現。這課的任務是走第三條路：把這組操作收成一份共用工具，三種資料都能用，型別檢查一個都不少。做到這件事的工具叫泛型（generics）。我們從最小的 first 開始，一路做到 findById、分頁外殼、InMemoryRepository，再換一個杯型設定的例子看推論怎麼修正，最後回頭檢查哪些地方其實不該用泛型。

這課的路線：
  1. first：any 和 unknown 都不好用時，怎麼讓傳進商品陣列就拿回商品（開場問題的最小答案）。
  2. T 是誰決定的：推論怎麼運作、什麼時候要自己寫 <Product>，以及 api.get<Order>() 藏著的風險。
  3. findById：函式裡要讀 item.id 時，怎麼用約束 T extends { id: number } 限制 T。
  4. 分頁外殼與 InMemoryRepository：泛型型別、泛型類別，以及類別把內部陣列交出去的陷阱。
  5. 杯型設定與收尾：const 型別參數、NoInfer 怎麼修正推論，以及什麼時候不該用泛型。
這課會用到：
  • 第 17 課的 any 與 unknown：any 關掉檢查；unknown 接得住任何值，但要先檢查才能用。
  • 第 18 課的函式型別與 overload：(p: Product) => boolean；overload 為不同輸入列出不同的回傳型別。
  • 第 14 課的結構型別與 readonly 陣列：欄位夠就能放進去；readonly T[] 不能 push。
  • 第 15 課的字面值型別與 as const：'S' 本身就是型別；as const 讓陣列變成唯讀 tuple、保留字面值。

first：怎麼讓傳進商品陣列就拿回商品？

從工具裡最小的一個開始：first，回傳陣列的第一個元素。三種資料都要用，所以參數不能寫死成 Product[]。目前手上「什麼都收」的型別只有第 17 課的兩個：any 和 unknown。下面各寫一版，執行後看最後兩個 console.log：一個沒有錯誤卻印出 undefined，一個直接報錯。

any 那一版的問題是檢查被關掉了。參數是 any[]，回傳值也跟著是 any，之後對它做什麼 TypeScript 都不管，a.prise 拼錯也照樣通過，執行時拿到 undefined。放到列表頁上，就是價格欄一片空白，直到使用者回報才有人發現。

unknown 那一版是安全的，但不好用。呼叫的人明明傳進去 Product[]，函式的簽章卻宣稱「回傳的東西型別未知」，每次拿出來都得再檢查一次或寫型別斷言，三種資料就要寫三套檢查，等於把重複搬到了呼叫端。

兩版的共同問題在簽章：參數和回傳值的型別各寫各的，彼此沒有關係。函式內部是 return items[0]，回傳值顯然跟陣列元素同一個型別，但簽章沒有把這層關係寫出來，而 TypeScript 檢查呼叫端時只看簽章。我們缺的是一種寫法，能在簽章裡說：「回傳的型別就是傳進來的陣列元素的型別，不管那是什麼。」

這種寫法叫型別參數（type parameter）。一般的參數是「值」的空位：寫函式時不知道 items 會是哪個陣列，呼叫時才填進來。型別參數是「型別」的空位：寫函式時不知道元素是什麼型別，先用一個名字代表它，習慣上叫 T，呼叫時才決定 T 是什麼。型別參數宣告在函式名稱後面的角括號裡，寫成 function first<T>(…)；宣告之後，T 就能用在參數和回傳值的型別裡。有型別參數的函式叫泛型函式。

呼叫的時候，T 通常不用你填。TypeScript 會拿你傳進去的值，對照參數的型別反推出 T：傳進 Product[]，對上參數的 readonly T[]，T 就是 Product。宣告時的空位 T 叫型別參數；呼叫時實際填進去的 Product 叫型別引數（type argument），就像一般函式的參數和引數。所以這個反推的過程叫型別引數推論（type argument inference），下一節細看它怎麼運作。下面這格執行後，把滑鼠移到 p 和 o 上，看 TypeScript 推出的型別：

同一份 first，傳商品陣列拿回 Product，傳訂單陣列拿回 Order，而且拿回來的值一樣受檢查，打錯欄位會有紅線。可以把泛型想成保鮮盒：盒子本身不管裝什麼，但裝什麼進去，拿出來就是什麼。關鍵是 T 同時出現在參數和回傳值兩個位置，把兩邊連起來；泛型的用處就是這個「連起來」，這一點在最後一節判斷「該不該用泛型」時會再用到。

這個簽章還有兩個刻意的選擇，拿掉任何一個都會出問題。第一個是參數寫 readonly T[] 而不是 T[]。first 只讀不改，把參數宣告成 readonly，等於對呼叫的人承諾「我不會改你的陣列」。有了這個承諾，readonly 陣列也能傳進來，例如第 15 課用 as const 做出來的唯讀 tuple；寫成 T[] 的話，TypeScript 不會讓「可能改陣列的函式」拿到唯讀陣列，呼叫就會報錯。一般陣列傳給 readonly 參數則沒有問題。

第二個是回傳寫 T | undefined 而不是 T。空陣列的 items[0] 就是 undefined。只寫 T 的話，型別等於宣稱「一定拿得到一筆」，呼叫的人就不會檢查，等到哪天列表是空的，執行時才在讀 .name 的地方出錯。型別要描述真實會發生的情況，包括拿不到的那一種。

到這裡，開場的問題已經有了最小的答案：用型別參數把輸入和輸出連起來，寫一次就適用三種資料。不過 first(menu) 裡的 T 是 TypeScript 自己推出來的。它靠什麼推？推不出來的時候會發生什麼事？

T 是誰決定的？推論不夠用時怎麼辦

上一節呼叫 first(menu) 時沒有寫 T，TypeScript 從引數 menu 推出 T 是 Product。你也可以自己寫成 first<Product>(menu)，結果一樣；但推論推得出來時不需要寫，多寫一份只是多一個要跟著改的地方。滑鼠移到呼叫上，就能看到 TypeScript 推出的 T。

其實你每天都在用泛型。內建的 Array、Map、Set、Promise 都有型別參數：Product[] 是 Array<Product> 的簡寫，Promise<Order> 是「將來會拿到 Order 的 Promise」。你用 menu.find(…) 拿到 Product | undefined，就是 Array 的型別參數在幫你把元素型別帶出來。

推論需要材料，材料就是傳進去的值。沒有值可以推的時候，例如建立一個空的 Map 當快取，TypeScript 沒有任何線索知道鍵和值會是什麼。Map 在這種情況下會把型別參數當成 any，變成 Map<any, any>，之後放什麼進去都不會報錯，拿出來的也是 any，跟開場第二條路的問題一樣。這時就要自己把型別寫在角括號裡。執行下面這格，看 cache1.set 那一行沒有報錯，而 cache2.set('2', …) 報錯：

💡 實務上：api.get<Order>() 是承諾，不是檢查
前端專案幾乎都會包一個 fetchJson<T>(url) 或用 axios 的 get<T>()，呼叫時手動寫 <Order>。這裡的 T 沒有材料可以推，等於你告訴編譯器「相信我，回來的是 Order」，效果跟型別斷言一樣：後端改了欄位名稱，畫面壞掉，編譯卻全過。內部、自己能控制的 API 這樣寫通常可以接受；第三方 API、使用者上傳的資料，資深工程師會在邊界先當成 unknown（第 17 課），驗證過再交給泛型。Code review 看到 get<T> 時可以問一句：「這個 T 有人在執行期確認過嗎？」

findById：函式裡要讀 item.id，T 要怎麼限制？

工具裡的第二個是 findById：在陣列裡找出 id 相符的那一筆。它跟 first 有一個關鍵差別：first 從頭到尾沒碰元素的內容，只是拿出來交回去；findById 必須讀每一筆的 id 來比對。照 first 的寫法加上比對，會報錯：

從函式內部看，T 是一個還沒填的空位，呼叫的人可以填任何型別：Product、Order，也可以是 number 或 string，而 number 沒有 id。TypeScript 檢查函式內部時不知道之後會填什麼，只能放行「不管 T 是什麼都成立」的操作，所以 item.id 被擋下來。這個限制是對的：如果放行，有人呼叫 findById(['拿鐵'], 1)，每一筆的 id 都是 undefined，函式會靜靜回傳 undefined，沒有人知道是呼叫錯了。

要讀 id，就得先縮小 T 的範圍，告訴 TypeScript：「T 可以是任何型別，但至少要有 number 型別的 id。」這叫約束（constraint），寫成 T extends { id: number }。這裡的 extends 讀成「至少要符合這個形狀」。加上約束後兩邊都受影響：函式內部可以安全地讀 item.id，因為每個可能的 T 都有它；呼叫的人傳進沒有 id 的資料，會在呼叫的那一行報錯。執行下面這格，看最後一行報錯：

T extends { id: number } 只要求 T 至少有 number 型別的 id，Product 多出 name、price，Order 多出 customerId、total 都沒關係，這是第 14 課的結構型別。更重要的是，回傳的仍然是完整的 T。對照另一種看起來也行的寫法：參數直接寫成 readonly { id: number }[]，商品和訂單一樣傳得進去，但回傳型別只能寫 { id: number } | undefined，拿回來只剩 id 一個欄位可以用，讀 .name 就報錯。泛型版本的 T 記得呼叫時傳進來的完整型別，約束只限制範圍，不會把資訊丟掉。

約束要寫多寬，看函式內部用到什麼。寫成 T extends Product 太窄：訂單就傳不進來了，可是函式根本只用到 id。完全不加約束又太寬：函式裡什麼都不能用，最後只好用 any 繞過，又回到沒有檢查的狀態。原則是：函式裡用到什麼，約束就寫什麼。

這個原則在後面會反覆用到。例如練習 3 的 groupBy 會依分類把商品分組：groupBy(menu, p => p.category) 會得到 { coffee: [...], tea: [...] }，第二個參數是一個函式，負責從每筆資料取出分組用的值，而這個值要拿來當物件的鍵。函式用到的是「能當物件鍵」這件事，所以約束寫成 K extends PropertyKey。PropertyKey 是內建型別，等於 string | number | symbol，也就是所有可以當物件鍵的型別。另一個常見的約束是 K extends keyof T，意思是 K 必須是 T 的欄位名稱，第 20 課講 keyof 時再看。

現在 first 和 findById 都能處理三種資料了。但列表 API 回傳的不是單獨一筆，而是一個外殼包著資料，例如分頁的 items 和 nextCursor。外殼也要能套用到三種資料，而這次要泛型的不是函式，是型別本身。

API 的外殼：分頁與成功／失敗，怎麼寫一次套到所有資料？

回想第 10 課的游標分頁：每一頁回傳這頁的資料 items，加上 nextCursor，表示下一頁從哪裡開始，沒有下一頁時是 null。商品列表、訂單列表、顧客列表的外殼完全一樣，只有 items 裡的元素不同。如果各寫一個 ProductPage、OrderPage、CustomerPage，就又回到開場的三份重複。

型別別名和介面也能宣告型別參數，這叫泛型型別。寫法是在型別名稱後面加角括號：type Paginated<T> = { items: T[]; nextCursor: string | null }。可以把它想成一個產生型別的模板：填進 Product，就得到 { items: Product[]; nextCursor: string | null }。它跟泛型函式有一個差別：泛型函式呼叫時有引數可以推論，泛型型別拿來註記變數時沒有東西可推，所以要自己寫成 Paginated<Product>。

分頁不是唯一需要外殼的地方：後台收到表單送來的價格文字時，要先轉成數字，而這一步可能失敗。失敗時可以 throw，但 throw 不會出現在函式簽章上，呼叫的人看型別看不出這個函式會失敗，很容易忘了 try/catch。改成回傳一個外殼，裡面標明成功或失敗，型別就會逼呼叫的人先檢查 ok 才拿得到 value，這就是下面的 Result。執行後看輸出：parsePrice('11O') 的最後一個字是英文字母 O，不是數字 0，所以走失敗的分支。

Result 是第 16 課的可辨識聯合：先用 ok 判斷，才拿得到 value 或 error，成功的值型別是 T，失敗的錯誤型別是 E。E = Error 是預設型別參數（default type parameter）：使用時沒寫 E 就用 Error，所以 Result<number> 的錯誤是 Error；寫了 Result<number, string>，錯誤就是 string。跟函式參數的預設值一樣，有預設值的型別參數要放在後面。Result 怎麼用來設計錯誤處理，第 27 課會深入。

💡 實務上：回應外殼整個團隊只定義一次
咖啡店的後台有訂單列表、商品列表、顧客列表，如果每支 API 的分頁格式都不一樣（有的叫 items、有的叫 data，有的用 nextCursor、有的用 page），前端就得為每一支各寫一份處理。常見做法是在共用的型別檔定義一次 Paginated<T>，後端回應和前端的列表元件都用它，改格式時編譯器會指出所有要跟著改的地方。

InMemoryRepository：泛型類別要防什麼？

外殼解決了「回傳什麼形狀」，剩下「資料存在哪、怎麼存取」。後端常見的做法是 repository：專門負責存取某一種資料的物件，對外提供 create、findById、list、remove，呼叫的人不必知道資料是存在資料庫還是記憶體裡。正式環境的 repository 接資料庫；寫測試時換成把資料存在記憶體裡的版本，不用啟動資料庫就能測商業邏輯。NestJS 課第 18 課的分層就是這個形狀。

類別也能有型別參數，寫在類別名稱後面：class InMemoryRepository<T extends { id: number }>。宣告之後，整個類別的欄位和方法都能用 T：create 收 T、findById 回傳 T | undefined、list 回傳 T 的陣列。約束沿用 findById 的理由：repository 要用 id 找資料。建立物件時沒有引數可以推論，跟第二節的 new Map() 一樣，要自己寫成 new InMemoryRepository<Product>()。商品、訂單共用同一份類別，就是開場要的那份共用工具。

型別到這裡都對了，但寫這種類別有一個型別擋不住的陷阱。第 2 課講過，物件和陣列傳的是參考，兩個變數會指向同一份資料。如果類別把內部的陣列或物件直接交出去，外面一改，裡面存的資料就跟著變。下面是一個簡化的儲存區，只有 add 和 list。執行後看最後印出的陣列：拿鐵被改名，還多了一筆不該有的資料。

這裡有兩條洩漏的路。第一條在存進去的時候：add 存的是 latte 這個物件本身，所以外面改 latte.name，改到的就是儲存區裡那一筆。第二條在拿出來的時候：list 回傳的是內部陣列本身，外面對它 push，等於直接往儲存區塞資料。型別完全正確，因為 TypeScript 檢查的是「形狀對不對」，不管「這是不是同一份」。放在測試裡，後果是一個測試改了拿到的物件，下一個測試讀到的資料已經被改過，測試結果時好時壞。

修法是存進去時存複本，拿出來時也給複本。第 2 課的 structuredClone 會連裡面的物件一起複製；展開 [...arr] 只複製陣列這一層，元素還是同一批物件，所以元素也要保護時要用 structuredClone。#items 是第 3 課的 private 欄位，class 外面讀不到，但它只擋得住別人直接存取欄位，擋不住你自己把它交出去。練習 4 會寫一個不洩漏的版本。

💡 實務上：InMemoryRepository 換掉資料庫，也換掉了資料庫的保證
InMemoryRepository<T> 常出現在單元測試：不必啟動資料庫就能測商業邏輯，但它不會有資料庫的唯一限制（例如同一個 email 不能註冊兩次）、交易這些行為，最後仍要有接真資料庫的測試。

杯型設定：怎麼讓型別記住清單裡只有哪幾個值？

前面的工具處理的是一筆筆資料。商品還有一份設定要處理：每種飲品提供哪些杯型，例如 ['S', 'M', 'L']，以及預設杯型是哪一個。我們想寫一個共用的小函式來宣告這份清單，要求是型別要記住清單裡到底是哪幾個字串，之後有人傳了不存在的杯型才報得出來。這裡要處理的是推論本身的行為，商品陣列示範不出來，所以換成杯型清單這個例子。

先看一般的泛型會怎麼推。TypeScript 推論陣列的型別時，預設你之後可能會修改這個陣列，所以把 'S' 這種字面值放寬成 string，推出 string[]。型別於是不知道清單只有這三個，之後把 'XL' 當杯型傳進去也不會報錯。呼叫的人可以自己加 as const，但每個呼叫的地方都要記得加，忘了就默默退回 string[]。比較好的做法是由函式負責：在型別參數前加 const，推論時就會像呼叫的人加了 as const 一樣，保留字面值和 tuple。這個寫法叫 const 型別參數，TypeScript 5.0 起才有。執行後把滑鼠移到 a 和 b 上比較：

注意約束寫的是 readonly string[]。加了 const 之後，推論出來的是 readonly tuple；如果約束寫成可變的 string[]，readonly tuple 放不進去，T 就會退回 string[]，const 等於沒寫。官方的 5.0 版本說明特別提醒了這一點，練習 5 的 defineSizes 會用到。

清單的型別記住了，接著是預設杯型：它必須是清單裡的其中一個。直覺的寫法是讓清單和預設值共用同一個型別參數 S，但這樣會出錯：

問題出在推論怎麼收集材料。S 同時出現在 sizes 和 d 兩個位置，TypeScript 會從所有出現 S 的位置收集候選，再合成一個型別。'XL' 也被當成候選，S 就被推成 'S' | 'M' | 'XL'，d 自然合格。我們要的其實是：S 只從 sizes 推，d 只拿來檢查。NoInfer<S>（TypeScript 5.4 起）就是在標記「這個位置不要拿來推論，只拿來檢查」：S 只從 sizes 推出 'S' | 'M'，再用它檢查 d，'XL' 就報錯了。官方文件用紅綠燈示範同一件事，連結見課末。

這兩個寫法跟前面幾節不同：它們沒有讓泛型多做什麼事，只是修正推論的結果，讓推出來的 T 更接近你的本意。

💡 實務上：const 與 NoInfer 多半是讀得懂就好
一般的業務程式碼（訂單 API、表單、頁面）很少需要自己寫 const T 或 NoInfer；它們比較常出現在團隊共用的工具函式和套件的型別定義裡，例如「設定選項只能從前面宣告的清單裡挑」這類 API。實際會遇到的情況是：用某個套件時傳錯值卻沒報錯，或滑鼠移上去看到這些關鍵字，知道它在做什麼就能判斷是自己寫錯還是型別沒寫好。要自己用時，先確認專案的 TypeScript 版本（const 要 5.0、NoInfer 要 5.4），舊專案升級前用不了。

工具寫完了：哪些地方其實不該用泛型？

回頭看這課寫出來的整組工具，每一個型別參數都在連起兩個位置：first 和 findById 連起參數和回傳值，Paginated 連起外殼和裡面的 items，InMemoryRepository 連起 create 收進來的和 findById 拿出去的，pickStrict 連起清單和預設值。這就是判斷要不要用泛型的標準：泛型的用處是連起兩個位置的型別，型別參數只出現一次，就沒有東西可以連：

function log<T>(x: T): void { console.log(x) }   // T 只出現一次，沒有作用
function log(x: unknown): void { console.log(x) }  // 一樣的效果，更好讀

第一行的 log<T> 什麼都收、回傳 void，T 沒有把任何資訊帶到別的地方。第二行的 unknown 一樣什麼都收，效果完全相同，而且讀的人不必去想「這個 T 是要連到哪裡」。

過度泛型的代價很實際：簽章難讀、錯誤訊息一長串看不懂、同事不敢改。所以資深工程師寫共用工具時，會照這幾條判斷：

  • 先寫具體型別。如果開場只有商品需要依 id 查詢，就寫 findProduct(id)。
  • 出現第二個真實的使用情境，再抽成泛型。等訂單也需要時，你已經知道兩邊的共同點是 id，約束也就寫得準。
  • 檢查每個型別參數是否至少出現兩次（例如一次在參數、一次在回傳值）。只出現一次的，改成 unknown 或具體型別。
  • 能用聯合型別或第 18 課的 overload 清楚表達的，不一定要硬用泛型。反過來，「輸出型別跟著輸入走」的情況，泛型通常比 overload 簡單。

到這裡，開場的三份重複程式已經收成一份共用工具，三種資料都能用，型別檢查一個都沒少。接下來用練習自己把這組工具寫一遍。

練習

練習 1：寫 first 和 last，回傳陣列的第一個／最後一個元素，空陣列回傳 undefined。要接受 readonly 陣列，回傳型別要跟元素型別連起來（傳 Product[] 進去就得到 Product | undefined）。

練習 2：寫 findById(items, id)：在任何「有 number 型別 id」的物件陣列（包括 readonly 陣列）裡找出那一筆，找不到回傳 undefined。商品和訂單都要能用，回傳的型別要是完整的 Product 或 Order。

練習 3：寫 groupBy(items, keyOf)：依 keyOf(item) 的結果把資料分組。回傳型別要誠實：某一組可能一筆都沒有、根本不存在，所以是 Partial<Record<K, T[]>>，鍵的型別 K 要保留（依分類分組時是 'coffee' | 'tea' | 'food'，不是 string）。可以用內建的 Object.groupBy(items, keyOf)（ES2024）實作：它對每一筆呼叫 keyOf，把回傳值相同的放進同一個陣列，回傳一個沒有原型的物件。鍵也可能是數字，例如依顧客 id 分組訂單。提示：K 要約束成可以當物件鍵的型別。

練習 4：寫 class InMemoryRepository<T extends { id: number }>，把資料存在記憶體裡：

  • create(item)：存一份複本並回傳；id 已經存在時丟出 Error。
  • findById(id)：回傳 T | undefined。
  • list()：回傳全部資料。
  • remove(id)：回傳是否真的刪掉了（boolean）。

外面不管改了原本傳進來的物件、list() 回傳的陣列和元素，還是 findById 拿到的物件，都不能影響存著的資料。

練習 5：寫 defineSizes(sizes)：原樣回傳陣列，但型別要保留成 readonly tuple（defineSizes(['S', 'M', 'L']) 是 readonly ['S', 'M', 'L']，呼叫的人不用寫 as const）。再寫 pickDefault(sizes, d)：回傳 d，但 d 只能是 sizes 裡的值，傳清單外的值要報錯。

練習 6：function log<T>(x: T): void { console.log(x) } 需要寫成泛型嗎？

✓ 泛型的用處是讓兩個位置的型別互相關聯（例如參數和回傳值）。這裡回傳 void，T 只用一次，unknown 一樣什麼都收、而且更好讀。a 錯在「接受任何型別」不需要泛型；c 的 any 會關掉檢查，函式裡誤用 x 也不會報錯。

練習 7：下面這段為什麼報錯？

function findById<T>(items: T[], id: number) {
  return items.find(i => i.id === id)
}

✓ 沒有約束時，TypeScript 只讓你做所有型別都能做的事。加上 T extends { id: number } 之後 i.id 才合法，而且回傳的仍然是完整的 T。a 錯，find 沒問題；b 是在呼叫的地方指定，但錯誤在函式定義裡，跟呼叫無關。

練習 8：const cache = new Map() 的型別是什麼？

✓ 沒有任何材料可以推論，型別參數就變成 any，之後放什麼都不會報錯，取出來也是 any。空的容器要自己寫：new Map<number, Product>()。b 是空陣列 const ids = [] 的行為，Map 沒有；c 不對，TypeScript 這裡給的是 any。

常見錯誤

  • 型別參數只用一次：沒有東西可以連，改成 unknown 或具體型別。
  • 用 any 代替泛型：first(items: any[]) 回傳 any，拿出來的東西打錯欄位也不報錯。
  • 約束太窄或太寬：T extends Product 讓訂單用不了；沒有約束時函式裡什麼都不能用。函式用到什麼，約束就寫什麼。
  • 回傳 T 卻可能找不到：find、陣列索引在找不到時是 undefined，回傳型別要寫 T | undefined，否則型別在說謊。
  • 參數寫 T[] 而不是 readonly T[]：函式不改陣列時寫 readonly，as const 的資料才傳得進來。
  • 泛型類別把內部陣列或物件直接交出去：外面一改，裡面跟著變。存進去和拿出來都用複本。
  • 空容器不寫型別：new Map() 是 Map<any, any>。
  • 手動寫 get<Order>() 就以為資料被檢查過：沒有材料可推的 T 只是宣稱，外部資料要先當成 unknown 驗證。
  • 一開始就把東西寫得很泛用：先寫具體型別，出現第二個真實的使用情境再抽象。

小結

  • 開場的問題：商品、訂單、顧客三份重複的存取程式，用泛型收成一份，型別檢查不減少。
  • 型別參數（<T>）是型別的空位，把輸入和輸出的型別連起來：first 傳 Product[] 進去，拿到 Product | undefined。參數寫 readonly T[]、可能拿不到時回傳 T | undefined。
  • T 通常交給推論；空的容器（new Map<number, Product>()）、空陣列推不出來，要自己寫。手動寫的 T 是承諾，不是檢查。
  • T extends { id: number } 是約束：函式裡用到什麼就約束什麼，回傳的仍是完整的 T。PropertyKey 是可以當物件鍵的型別。
  • 型別和類別也能是泛型：Paginated<T>、Result<T, E = Error>、InMemoryRepository<T>；泛型類別要用複本保護內部狀態。
  • <const T extends readonly …>（5.0）保留字面值與 tuple；NoInfer<T>（5.4）讓某個位置只檢查、不參與推論。
  • 型別參數只出現一次就不需要泛型；先寫具體的，有第二個使用情境再抽象。
