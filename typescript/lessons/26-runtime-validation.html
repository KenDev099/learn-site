階段 6：實戰 · 第 26 課

驗證外部資料：自製迷你 schema，再看 zod

咖啡店接上外送平台的第一週，後台出了三件事。第一件：對帳時，平台的一筆訂單對到了我們這邊另一筆訂單。平台的訂單編號是 "9007199254740993"，我們的程式把它 Number() 成數字，變成了 9007199254740992。第二件：有人沒經過 Vue 點餐頁，直接用 curl 呼叫 POST /orders，body 裡多帶了 "total": 0，後端把整個 body 交給負責存資料庫的套件（ORM）存檔，這筆訂單變成 0 元。第三件：平台改版，訂單明細的 items 欄位改了名字，收訂單時沒人發現，直到晚上產報表讀 order.items.length 才丟 TypeError，錯誤訊息跟真正的原因隔了好幾個檔案。

三段程式都通過了型別檢查，Order 型別寫得清清楚楚。問題出在同一個地方：我們相信了送進來的 JSON。這一課的任務，是在訂單進門的地方（POST /orders 和外送平台送來的訂單）蓋一道驗證閘門：資料一進來就檢查，不合格的回 400 並說清楚哪個欄位錯，合格的才變成真正的 Order 往下傳。先手寫一次，看清楚閘門裡每一步在做什麼；再把它整理成可以重用的 schema；最後對照工作上實際用的 zod 和 NestJS。

這課的路線：
  1. 型別都寫了，為什麼三件事都沒被擋下：型別在執行時不存在，資料從哪些入口進來，閘門該長什麼形狀（parse, don't validate）。
  2. 閘門裡面怎麼寫：手寫第一個 parser，錯誤帶路徑、一次列出所有問題、只複製認得的欄位，擋下 total: 0（開場問題的最小答案）。
  3. 訂單時間和編號在 JSON 裡都是字串，該怎麼驗：日期、大整數、null 經過 JSON 之後怎麼處理，第一件事故怎麼擋。
  4. 用正規表示式檢查格式，哪裡會出事：沒有錨點、共用 g 旗標、把使用者輸入放進去、ReDoS。
  5. 欄位一多，怎麼讓型別和驗證規則只寫一份：迷你 schema 把規則寫成資料，型別從規則推出來。
  6. 工作上怎麼做：用 zod 4 寫同一道閘門，在 NestJS 裡接上去。
這課會用到：
  • 第 17 課的 unknown 與型別守衛：unknown 不能直接用，要先檢查；回傳 x is T 的函式通過後，TypeScript 就把 x 當成 T。

型別都寫了，為什麼三件事都沒被擋下？

先回顧型別在什麼時候存在。第 13 課說過，TypeScript 的型別檢查發生在編譯時，編譯完型別就被擦掉，執行的是沒有型別的 JavaScript。編譯器檢查的是「程式碼」，它看得到你怎麼使用一個變數，但看不到程式執行時才送來的「資料」。所以 JSON.parse 只能回傳 any，fetch 的 res.json() 是 Promise<any>；你寫 as Order，只是告訴編譯器「相信我」，編譯後這幾個字也消失了（第 17 課）。

後端一樣。Express 的 req.body、NestJS 的 @Body() body: CreateOrderDto，型別都只是你對這份資料的「希望」：沒有另外接上驗證，執行時沒有人檢查 body 是不是真的長這樣。開場第二件事就是這樣發生的：型別裡沒有 total 這個輸入欄位，但 body 裡有，程式照樣把它傳給 ORM。

用咖啡店進貨來想。送貨單寫「鮮奶 20 瓶」，店員還是要在後門點一次數量、看保存期限，因為送貨單只是對方說的，箱子裡才是實際送來的。程式裡的型別就是送貨單；在程式執行時真的去檢查資料，叫做執行時驗證（runtime validation），就是點貨。

點貨要在後門點，不是等鮮奶上架、做成拿鐵賣出去之後才發現過期。程式也一樣：外部資料進入程式的那個位置，叫做信任邊界（trust boundary），邊界外的資料誰都能送、格式誰都能改，邊界內的程式則假設資料已經符合型別。驗證要放在邊界上，資料一進來就檢查一次。咖啡店後端的信任邊界不只 HTTP body：

邊界例子會出什麼事
HTTP bodyPOST /orders 的 JSON任何人都能用 curl 直接呼叫 API，跳過你的前端表單
query string、路徑參數?page=2、/orders/42永遠是字串，'2' 不是 2
外部 API 的回應金流、外送平台對方改版、欄位改名，你的程式在別處當掉
資料庫的 JSONB商品的客製選項（PostgreSQL 第 14 課）舊資料是三年前的格式，資料庫不幫你檢查 JSON 內部
環境變數process.env.PORT是 string | undefined，拼錯名稱就是 undefined
localStorage、檔案、訊息佇列前端存的購物車、佇列裡的工作舊版程式寫進去的格式

閘門的函式要長什麼形狀？直覺的寫法是 validate(x): boolean：檢查通過回傳 true，呼叫端再自己 as Order。這個寫法有兩個破口。第一，「檢查過」和「型別是 Order」是兩件分開的事，有人忘了呼叫 validate、或寫錯了 if 條件，照樣 as Order 得到一個 Order，編譯器不會發現。第二，通過檢查後拿去用的仍是原本那個物件，裡面多出來的 total: 0 還在。

比較好的寫法叫 parse, don't validate：寫成 parse(x: unknown): Order，參數是 unknown（不能直接用），驗證完回傳一個型別精確的新值，不合格就丟錯。這樣一來，程式裡拿到 Order 型別的唯一途徑就是通過 parse，「驗證過」這件事被記在型別上；而回傳的是新物件，只有 parse 認得的欄位會被放進去。這就是開場三件事的解法的形狀。

形狀有了，下一個問題是 parse 裡面到底怎麼寫：要檢查什麼、錯了怎麼告訴呼叫端是哪個欄位錯。

💡 實務上：除了請求 body，最常漏掉的是環境變數和第三方 API 的回應
咖啡店後端啟動時，先用 schema 檢查一次 process.env（資料庫網址、金流金鑰、PORT），少一個就直接啟動失敗並印出缺哪個，比上線後第一筆訂單才炸好查得多。外送平台、金流的 webhook 和回應也要驗證，失敗時記下錯誤路徑（例如 items[0].price）並通知值班的人，不要讓格式不對的資料流進訂單表，開場第三件事就是少了這一步。反過來，自己程式剛寫進資料庫、欄位有型別約束的資料，不需要每次查詢都再驗一次；只有 JSONB 這種資料庫不檢查內容的欄位才值得驗。資深的人接手專案會先問：外部資料從哪幾個入口進來，每個入口有沒有 parse？

閘門裡面怎麼寫？手寫第一個 parser

上一節定下了 parse 的形狀：unknown 進、型別精確的新物件出。動手之前，先決定「錯了怎麼回報」，因為這會決定整個函式的結構。有三個設計決定：

  1. 錯誤帶路徑：每個問題都記下是哪個欄位出錯，這個位置叫錯誤路徑（issue path），例如 price，或明細第二筆的數量 items[1].quantity。只回「資料格式錯誤」，前端不知道要把紅字標在哪個欄位旁邊，接外送平台時你也不知道對方改了哪裡；有了路徑，兩邊都能直接定位。
  2. 收集完再丟：遇到第一個錯就停的話，使用者改好名稱再送出，才發現價格也錯，要來回好幾次。所以每個欄位都檢查完，把問題收集成一個陣列，最後一次丟出 ValidationError（第 4 課的自訂錯誤類別），它的 issues 屬性列出每個問題。
  3. 只複製認得的欄位：回傳一個新物件，只放 parse 檢查過的欄位，不是把輸入原封不動傳下去。開場第二件事的 total: 0 就靠這一點擋掉。

訂單有五個欄位，還有一個明細陣列，一次寫完會看不清骨架。先用只有 name、price 兩個欄位的菜單品項示範；商品的完整版本是練習 1，訂單（含明細陣列）是練習 2，骨架完全一樣，只是欄位比較多。執行後看兩件事：第一行印出的物件沒有 isAdmin；第二次呼叫一次列出 name 和 price 兩筆 issue，不是只有第一筆。

照順序讀 parseMenuItem：

  • 先確認是物件：typeof null 也是 'object'，陣列也是物件，所以三個條件都要寫。連物件都不是，後面的欄位沒得檢查，直接丟一筆 path 是空字串的 issue，代表「整筆資料」錯了。
  • 每個欄位同一個節奏：用 field 讀出原始值（型別是 unknown），檢查型別和規則；合格就存進變數，不合格就推一筆 issue，變數留著佔位用的初始值。
  • 最後才決定：issues 不是空的就丟錯，佔位值永遠不會被回傳；是空的才組出新物件 { name, price }。

field 這個小函式做了兩件事。第一，它用 Object.hasOwn 只讀物件「自己」的屬性，不會讀到原型鏈上繼承來的東西（原因在下面原型污染那段）。第二，它裡面的 as Record<string, unknown> 是往寬的方向轉：讀出來的值仍是 unknown，還是得檢查才能用，所以這個 as 不是在對編譯器說謊，跟 as MenuItem 性質不同。

第 3 個設計決定「只複製認得的欄位」看起來只是整潔，其實擋下了兩種攻擊。

第一種是大量指派（mass assignment），也就是開場第二件事。ORM 是把資料表對應成物件的套件，例如 Prisma（第 25 課提過）；它的 create、update 收到一個物件，就把裡面每個欄位寫進資料庫。後端如果把整個 body 交給它，客戶端多送的 isAdmin: true、total: 0 也會被寫進去，而這些欄位本來只有後端自己能決定。整理常見網站與 API 資安風險的非營利組織 OWASP，在它的 API Top 10 把這類問題歸在 API3「物件屬性層級授權失效」（認證課第 19 課）。parse 只把列出的欄位放進新物件，多送的欄位根本到不了 ORM。

第二種是原型污染（第 3 課）。JSON.parse('{"__proto__": {…}}') 產生的物件，有一個名字叫 __proto__ 的自有屬性；拿這種物件去做深層合併，合併函式會沿著 __proto__ 改到 Object.prototype，從此所有物件都多了攻擊者指定的屬性。parse 只讀你列出的鍵，又用 Object.hasOwn 只讀自有屬性，這類欄位進不來。

這個 parser 能用，但很囉嗦：每個欄位四行，欄位一多就難維護。先記住這個感覺，後面「欄位一多」那一節的迷你 schema 會解決它；練習 1 先手寫一次完整的 parseProduct。在那之前還有一個更急的問題：開場第一件事的訂單編號，型別檢查會過（它是字串），出錯的是我們之後把它轉成數字。訂單的時間、編號這類值，經過 JSON 之後要怎麼驗、轉成什麼？

💡 實務上：400 回應的格式要跟前端先約定好
咖啡店後台有新增商品、編輯菜單、建立優惠券好幾張表單，後端回 400 時，整個專案都用同一種 body：issues 陣列，每一項帶 path 和 message，前端寫一次共用的處理就好。路徑格式（items.1.quantity 還是 items[1].quantity）也要講好，不然前端對不上欄位。要注意的是錯誤訊息不要把使用者送來的原始值整段回傳或寫進 log，裡面可能有密碼、電話這類個資。資深的人 review 新 API 時，會故意送一個缺欄位、型別錯的請求，看回應是不是前端真的能用。

訂單時間和編號在 JSON 裡都是字串，該怎麼驗？

上一節的 parser 檢查欄位在不在、型別對不對。訂單還有另一類問題：值的種類在 JSON 裡變少了。JSON 只有字串、數字、布林、null、陣列、物件六種值，程式裡的型別比它豐富，所以 Date、超大的整數這類值，送的一方要先換成 JSON 有的種類，收的一方 parse 時再換回來。換回來的規則要寫清楚：

程式裡JSON 裡parse 時要做的事
DateISO 字串 "2026-10-31T09:30:00+08:00"檢查格式、日期真的存在，再轉成 Date
bigint 的 id字串 "9007199254740993"檢查只有數字，保持字串（或轉 BigInt）；不能轉成 Number
string | nullnull，或整個欄位不存在兩者意義不同，要分開處理
number120，有時候是 "120"要不要轉，看資料從哪裡來

下面一列一列看。

訂單時間：外送平台送來的 orderedAt 是字串，我們要的是 Date。直接 new Date(字串) 會踩到第 6 課說過的三個問題。執行後看每一列箭頭右邊的結果：

  • 月份 13：變成 Invalid Date，用 isNaN(d.getTime()) 擋得住。
  • 2 月 30 日：在 Chrome 和 Node 上被滾成 3 月 2 日，是一個「合法」的 Date，isNaN 擋不住。訂單時間就這樣悄悄差了兩天。
  • 只有日期：被當成 UTC 的午夜，在台北其實是早上 8 點。

所以驗證日期時間要三步。第一，用正規表示式要求完整的日期、時間和時區（Z 或 +08:00），沒有時區的字串不收，因為你無法知道它指的是哪裡的時間。第二，用第 6 課的往返檢查確認日期真的存在：把年月日交給 Date.UTC 建一個日期，再讀回來，2 月 30 日會溢位成 3 月，讀回來的月份和日期對不上就是不存在。第三，前兩步都過了，才 new Date。練習 2 的 orderedAt 就照這三步寫。

大整數的編號：這是開場第一件事。JavaScript 的 number 用 64 位元浮點數表示，能精確表示的整數只到 Number.MAX_SAFE_INTEGER（9007199254740991，第 5 課），超過之後只能存成最接近的那個值。PostgreSQL 的 bigint 最大到 9.2 × 1018，遠超過這個範圍，所以 Number('9007199254740993') 會變成 9007199254740992，拿去查就查到別人的訂單。對方如果直接在 JSON 裡寫數字 9007199254740993，用一般的 JSON.parse 讀進來的那一刻就已經失真，你拿到的已經是錯的數字。所以這類編號在 JSON 裡一律用字串傳；parse 時檢查它只含數字（/^\d+$/），再限制長度（bigint 最多 19 位），然後保持字串往下傳。

null 與缺欄位：{"category": null} 是「明確說沒有分類」，{} 是「沒提到分類」。在 PATCH 更新時差別最大：null 代表把分類清空，缺欄位代表分類不要動。混在一起，使用者只想改價格，分類卻被清掉。所以型別寫 Category | null 時，缺欄位要算錯，不能悄悄當成 null；練習 1 的測試會檢查這一點。

強制轉型（coercion）：把字串 '120' 轉成數字 120。要不要接受，不是技術問題，是 API 合約的決定，判斷依據是「這個入口能不能表示數字」：

  • query string、路徑參數、表單：這些地方只有字串，?page=2 收到的一定是 '2'，必須轉。轉之前先用正規表示式檢查格式，因為 Number('') 是 0（第 5 課），空字串會被當成第 0 頁。
  • JSON body：JSON 本來就能表示數字，客戶端送 "120" 代表它的程式有 bug。回 400 讓它早點發現，不要幫它轉；幫它轉，bug 就被藏起來，哪天它送 "一百二" 才爆。

訂單時間要用正規表示式檢查格式，編號也是 /^\d+$/。閘門越來越依賴正規表示式，而正規表示式寫錯，閘門會放進不該進的東西，甚至讓整台伺服器停擺。

💡 實務上：「只有日期」的欄位不要轉成 Date
咖啡店的預約日期、營業日、會員生日，意思是「台灣的那一天」，不是某個時間點。這類欄位驗證成 YYYY-MM-DD 字串（加上往返檢查確認日期存在）就保持字串傳下去，資料庫用 date 型別存；轉成 Date 會帶上時區，換到 UTC 的伺服器或海外使用者的瀏覽器，就可能差一天。訂單建立時間、付款時間這類「真的發生在某一刻」的欄位，才用帶時區的完整時間。資深的人設計新欄位時會先問：這是一個時間點，還是日曆上的一天？

用正規表示式檢查格式，哪裡會出事？

上一節的日期和編號都靠正規表示式把關。外送平台的訂單還附上外送員的手機號碼，我們要檢查它是 09xx-xxx-xxx。第 5 課學過 ^、$，這一節用這個手機號碼，看四個在正式環境出過事的陷阱。

陷阱 1：沒有錨點。test 的意思是「字串裡有沒有任何一段符合」，不是「整個字串符合」。沒有 ^（開頭）和 $（結尾）把範圍釘住，前後多了什麼都會通過。執行後每一列印出三樣：字串、沒錨點的結果、有錨點的結果：

第二、三列都不是合法號碼，沒錨點的版本卻都回 true：abc…xyz 中間有一段符合，6789 的前三位也符合。驗證用的正規表示式一定要 ^…$。

陷阱 2：共用一個有 g 旗標的正規表示式。g（global）旗標是給「在一段文字裡找出所有符合的片段」用的。為了能一段一段往下找，有 g 的正規表示式物件會用 lastIndex 屬性記住上次比對結束的位置，下次 test 從那裡開始找；找不到時才把 lastIndex 歸零。驗證用的正規表示式通常宣告在模組最上層讓大家共用，加了 g，這個位置就在每次呼叫之間被帶著走。執行後看每一列的 true／false 和 lastIndex：

同一個合法號碼，結果是 true、false 交替：第一次比對成功，lastIndex 停在字串結尾；第二次從結尾開始找，當然找不到，於是歸零；第三次又成功。這種 bug 在測試裡常常抓不到，因為每個測試只呼叫一次；上線後同一個模組被許多請求共用，才隨機出現。驗證用的正規表示式不要加 g；g 只在「找出字串裡所有符合的片段」時用，例如 matchAll。練習 3 的起始程式就有這個坑。

陷阱 3：把使用者輸入放進正規表示式。驗證手機號碼時，正規表示式是我們寫死的，不會出這個問題；換到另一個常見情境，正規表示式的內容來自使用者時才會出事。例如後台的商品搜尋如果寫成 new RegExp(keyword)，使用者輸入的文字會被當成正規表示式的語法：輸入 .* 就搜到全部，輸入 ( 直接丟 SyntaxError。要先跳脫（escape），也就是把 . * ( ) 這類有特殊意義的字元變成普通字元。更常見的情況是你根本不需要正規表示式：只是要找某段文字時，用 includes 就好。標準的 RegExp.escape 能不能用，要看執行環境和 TypeScript 設定，細節見課末。

陷阱 4：ReDoS（regular expression denial of service，正規表示式阻斷服務）。JavaScript 的正規表示式引擎比對失敗時，會回溯：退回去換一種拆法再試，所有拆法都試過才回答「不符合」。大多數寫法的拆法只有幾種，但巢狀量詞，也就是量詞裡面又有量詞，例如 (a+)+，會讓同一串 a 有指數多種拆法：aaaa 可以是一組 (aaaa)，也可以是 (aaa)(a)、(a)(aaa)、(aa)(a)(a)…。字串如果「差一點就符合」（最後多一個 !），引擎要把每一種拆法都試完才放棄。按執行，看字串每長一點，時間怎麼變：

每多 2 個字，時間約變成 4 倍。本機用 Node 24 實測：30 個字約 7 秒。這 7 秒是同步程式，整個 event loop 被卡住（第 7 課），這段期間所有人的請求一起停，不只是送惡意字串的那一個。攻擊者只要送幾個請求，伺服器就停擺。所以閘門要這樣防：

  • 不寫巢狀量詞（(a+)+、(\w+\s?)*）；同一段文字不要有兩種以上的比對方式。
  • 先限制輸入長度再比對：手機號碼不會超過 20 個字，email 不會超過 254 個字。長度檢查很便宜，放在最前面；練習 2 的答案在比對日期前先檢查長度，就是這個原因。
  • email、URL 這類複雜格式，用寫好、測過的驗證函式庫，不要自己寫（Node 課第 25 課）。

到這裡，閘門該檢查的東西都齊了：型別、必填、日期、大整數、格式。但回頭看手寫的 parser，問題也很明顯：每個欄位四行，訂單有五個欄位加明細，parser 比型別定義長好幾倍。

欄位一多，怎麼讓型別和驗證規則只寫一份？

手寫 parser 除了囉嗦，還有一個更危險的問題：型別和規則各寫一份。type Order 寫一份欄位清單，parseOrder 又寫一份。哪天訂單加了「備註」欄位，你改了型別、忘了改 parser，型別說有 note，執行時卻從來沒檢查過它；反過來，parser 改了規則、型別沒跟上，兩邊也會不一致。兩份東西靠人記得同步，久了一定會漏。第 20 課的解法是「寫一次，其他推導」，這裡也一樣：只寫驗證規則，型別從規則推出來。

要讓型別能從規則推出來，規則就不能散在 if 裡，要寫成一個值。這個描述「合法的資料長什麼樣子」的值，叫做 schema。我們的迷你版本是這樣設計的：每個 schema 都是一個物件，有一個 check(x, path, issues) 方法，檢查 x，有問題就把 { path, message } 推進 issues，再回傳整理好的值。路徑和 issues 陣列都由呼叫的人傳進來，這是為了讓小 schema 能組成大 schema 時，一路共用同一個 issues 陣列、一層一層把路徑接下去。

先看最小的一塊：只有 s.string()，和一個把 issues 收集起來、有問題就丟錯的 parse。執行後看兩行輸出：合法的字串原樣回傳，42 變成一筆 issue；再把滑鼠移到 name 上，看它的型別。

name 的型別是 string，而我們從頭到尾沒寫過 : string：型別來自 s.string() 回傳的 Schema<string>，parse<T> 把 T 帶到回傳值。check 失敗時回傳的空字串只是佔位，跟手寫 parser 的佔位值一樣，issues 不是空的就不會被拿去用。

有了單一欄位的 schema，再用兩個「組合用」的 schema 把它們拼成整筆訂單：

  • s.array(item)：確認 x 是陣列，對第 i 個元素呼叫 item.check(元素, `${path}[${i}]`, issues)。元素的路徑就是在自己的路徑後面加上 [i]。
  • s.object(shape)：確認 x 是物件，對 shape 的每個鍵呼叫 shape[key].check(欄位值, 路徑.key, issues)，把結果放進一個新物件。不在 shape 裡的鍵不會被複製，所以大量指派不用另外處理，自然被擋掉。

這樣，訂單明細第二筆的數量錯了，路徑會經過 items → items[1] → items[1].quantity 一層層接起來，正好是前面手寫 parser 時要的錯誤路徑。

剩下型別怎麼推出來。s.string() 的型別是 Schema<string>，T 就包在裡面；用第 22 課的 infer 把它拿出來：

type Infer<S> = S extends Schema<infer T> ? T : never

const productSchema = s.object({ id: s.number(), name: s.string() })
type Product = Infer<typeof productSchema>   // { id: number; name: string }

關鍵在 s.object 的回傳型別，它用 第 22 課的 mapped type（走過一個型別的每個鍵，產生新的型別）寫成 Schema<{ [K in keyof Shape]: Infer<Shape[K]> }>：對 shape 的每個鍵，把那個鍵上的 schema 換成它推導出來的型別。id 上是 Schema<number>，就變成 id: number。訂單加備註欄位時，只要在 schema 加一行，型別自動跟著變，不會再有兩份不一致。這是練習 4。

練習 4 的 s.object 需要一個 as：用 for 迴圈填出來的物件，TypeScript 證明不了每個鍵都填好了。這是函式庫內部的取捨：as 只寫在一個地方，由「issues 是空的才回傳」保護，所有使用 schema 的程式都不用再寫 as。zod 這類函式庫內部也是這樣做的。

迷你 schema 讓閘門的規則只寫一份，但它還缺很多東西：enum、日期、最小長度、選填欄位、自訂錯誤訊息。工作上不會自己維護這一整套，而是用現成的函式庫。

工作上怎麼做：用 zod 寫同一道閘門，接進 NestJS

上一節的迷你 schema，就是 zod 的核心想法。zod 是 TypeScript 生態最常用的 schema 驗證函式庫：規則寫成 schema 物件、型別從 schema 推導、錯誤帶路徑全部收集，都跟我們做的一樣，只是規則多很多、也測得更完整。練習區不能 import 套件，所以這裡用對照的方式看（本課程用 zod 4，確切版本見課末）：

迷你 schemazod 4

用 zod 寫開場那道訂單閘門，大約是這樣。customerId 和每筆明細的數量是正整數，status 只能是四種狀態之一，orderedAt 要帶時區，items 至少一筆：

import { z } from 'zod'

const ORDER_STATUSES = ['pending', 'paid', 'done', 'cancelled'] as const

export const orderSchema = z.object({
  customerId: z.number().int().positive(),
  status: z.enum(ORDER_STATUSES),
  orderedAt: z.iso.datetime({ offset: true }),
  items: z.array(z.object({
    productId: z.number().int().positive(),
    quantity: z.number().int().positive(),
  })).min(1),
})
export type CreateOrderInput = z.infer<typeof orderSchema>

// 外送平台送來的訂單：多一個編號，以字串驗證（只含數字、最多 19 位）
export const platformOrderSchema = z.object({
  ...orderSchema.shape,
  id: z.string().regex(/^\d{1,19}$/),
})

const result = orderSchema.safeParse(body)
if (!result.success) {
  console.log(z.prettifyError(result.error))
  // ✖ Invalid input: expected number, received string
  //   → at items[1].quantity
} else {
  result.data.items   // 型別精確
}

前面手寫 parser、處理時間和編號、檢查格式、寫迷你 schema 做的每一件事，這段裡都有對應。用的時候要知道這幾個行為：

  • safeParse 不丟錯，回傳 { success: true, data } 或 { success: false, error }。這個「成功或失敗都放在回傳值」的形狀，就是第 27 課的 Result。
  • 未知欄位：z.object 預設剝掉，跟我們的 s.object 一樣，開場的 total: 0 進不來；z.strictObject 拒絕整個請求（錯誤訊息 Unrecognized key）；z.looseObject 保留。
  • z.iso.datetime() 預設拒絕 +08:00 這種偏移，只收 Z；要加 { offset: true }。它驗證的是字串，輸出仍是字串，要 Date 得再轉（做法見課末）。
  • z.coerce.number() 就是 Number(x)，z.coerce.boolean() 就是 Boolean(x)：'false' 會變成 true。照前面強制轉型的原則，只用在 query string，而且要知道它多寬鬆。

schema 寫好了，最後一步是讓它真的站在門口：每個請求進到 controller 之前就被檢查。NestJS 有兩條路，做的是同一件事（NestJS 課第 7 課詳細教）。第二條路用到 Standard Schema：它是一份共用的驗證介面，zod、valibot、ArkType 這些 schema 函式庫都實作它；框架只要支援這個介面，就能接任何一套 schema 函式庫，不用每一套各寫一份整合。

ValidationPipe ＋ class-validatorStandardSchemaValidationPipe ＋ zod
規則寫在哪DTO class（第 23 課）的屬性裝飾器（@IsInt()、@Min(1)），需要第 24 課的 metadataschema 物件，型別用 z.infer 推導
接上去app.useGlobalPipes(new ValidationPipe({ whitelist: true }))app.useGlobalPipes(new StandardSchemaValidationPipe())，參數寫 @Body({ schema: orderSchema })
未知欄位whitelist 剝掉，再加 forbidNonWhitelisted 就拒絕由 schema 決定：z.object 剝掉、z.strictObject 拒絕

選哪個：專案已經是 class-validator 就沿用；新專案、而且前後端想共用同一份 schema（Vue 表單和 API 用同一個 zod schema），用 zod。不要在同一個專案兩套混用。不管哪一套，都要確認未知欄位會被剝掉或拒絕。

回到開場的三件事，要分兩個入口看。POST /orders 是客戶端打進來的請求，用 orderSchema：多帶的 total 不在 schema 裡，被剝掉（z.strictObject 則整個請求回 400）。外送平台送來的訂單用 platformOrderSchema，這時我們是接收端：編號以字串驗證、保持字串，不再被轉成數字；平台把 items 改名，parse 時就因為缺 items 失敗，記下錯誤路徑 items 並通知值班的人，不會等到晚上產報表才丟 TypeError。

前端已經驗證過，後端還是要驗證。前端驗證是為了使用者體驗（即時顯示紅字）；API 可以被任何人用 curl、Postman 直接呼叫，開場第二件事就是這樣來的，後端的驗證才是安全防線。

練習

練習 1：寫 parseProduct(x: unknown): Product。規則：id 正整數；name 非空字串（只有空白也不算）；price 0 以上的整數（字串 '120' 不接受）；category 是 'coffee' | 'tea' | 'food' 或 null（欄位一定要存在）；isAvailable 布林。全部檢查完才丟 ValidationError，每個問題一筆 issue，path 是欄位名稱；x 本身不是物件時丟一筆 path 為 '' 的 issue。用起始程式的 field 讀欄位（只讀自有屬性）；回傳新物件，只包含這五個欄位，不能改到輸入物件。

練習 2：外送平台回傳的訂單要轉成 Order。寫 parseOrderResponse(json: unknown): Order：id 是只含數字的字串（bigint，保持字串）；customerId 正整數；orderedAt 必須是 YYYY-MM-DDTHH:mm:ss（可以有 1～3 位小數秒）加上 Z 或 +08:00 這種時區的字串，日期要真的存在（第 6 課的往返檢查），轉成 Date；status 是四種狀態之一；items 是陣列，每筆的 productId、quantity 是正整數、unitPrice 是 0 以上的整數。所有問題收集完才丟 ValidationError，明細的錯誤路徑要有索引，例如 'items[1].quantity'。

練習 3：寫 isTaiwanMobile(s: string): boolean：只接受 09xx-xxx-xxx 這種格式（09 開頭、全部是數字、用兩個 - 分成 4、3、3 位）。同一個號碼不管呼叫幾次，結果都要一樣。

練習 4：起始程式已經有 Schema<T>、ValidationError、parse、s.string()、s.number()、s.boolean()。完成 s.array(item)、s.object(shape) 和 type Infer<S>：錯誤要一路帶上路徑（tags[2]、items[1].quantity），所有問題都收集起來；陣列和物件本身型別不對時，path 是它自己的路徑；s.object 用起始程式的 field 讀欄位（只讀自有屬性），回傳新物件，只包含 shape 裡有的鍵。type Product = Infer<typeof productSchema> 要推導出正確的型別。

練習 5：NestJS 的 controller 寫了 const body = req.body as CreateOrderInput。執行時，body 一定符合 CreateOrderInput 嗎？

✓ as 只是告訴編譯器「相信我」，編譯後的 JavaScript 裡沒有它，執行時什麼都不檢查。編譯時 TypeScript 也看不到請求的內容（它在程式執行時才送來）。欄位名稱、值都不會被檢查。要在邊界用 parse 函式或 zod 這類 schema 驗證，拿到的才是真的 CreateOrderInput。

練習 6：zod 4 的 z.object({ name: z.string() }) 收到 { "name": "拿鐵", "isAdmin": true }，parse 的結果是什麼？

✓ z.object 預設剝掉未知欄位，跟 NestJS ValidationPipe 的 whitelist 一樣，大量指派因此被擋掉。想拒絕整個請求要用 z.strictObject（錯誤訊息 Unrecognized key），想保留要用 z.looseObject。原封不動保留是 looseObject 的行為，不是預設。

練習 7：Vue 的點餐表單已經用同一份 zod schema 驗證過，送出前就會擋下錯誤。後端還需要驗證嗎？

✓ 攻擊者不需要經過你的前端，直接送請求就好。HTTPS 只保護傳輸過程不被第三方竊聽、竄改，送請求的人本身送什麼都可以。共用 schema 的好處是規則一致、錯誤訊息一致，不是讓後端可以省略驗證。

常見錯誤

  • 用 as 把 JSON 變成型別：req.body as CreateOrderInput 執行時什麼都不檢查。在邊界用 parse 函式或 schema，拿到型別精確的新值。
  • 只在前端驗證：API 可以被直接呼叫。前端驗證給使用者體驗，後端驗證才是安全防線。
  • 遇到第一個錯就停：使用者要來回送好幾次才看到所有問題。收集所有 issue，帶路徑一次回傳。
  • 把未知欄位一起存進資料庫：isAdmin、total 被大量指派。只複製認得的欄位，或用會剝掉未知欄位的 schema（z.object、whitelist）。
  • new Date(字串) 沒有檢查：無效日期變成 Invalid Date，2 月 30 日被滾成 3 月 2 日，只有日期的字串被當 UTC。要求完整的日期時間加時區，做往返檢查。
  • 把大整數的編號轉成 Number：超過 Number.MAX_SAFE_INTEGER 就失真，查到別人的訂單。JSON 裡用字串傳，驗證只含數字並限制長度，保持字串。
  • 什麼都自動轉型：'120'、'true' 一律接受，客戶端的 bug 被藏起來；Boolean('false') 還是 true。只在 query string 這類一定是字串的地方轉，而且先檢查格式。
  • 正規表示式沒有錨點，或共用一個有 g 旗標的正規表示式：前者讓多出來的字元通過，後者讓同一個值 true、false 交替。
  • 型別與驗證規則各寫一份：久了一定不一致。從 schema 推導型別（Infer、z.infer）。
  • 正規表示式用巢狀量詞，或不限制輸入長度：ReDoS 一個請求就能卡住整個 event loop。先檢查長度，不寫 (a+)+ 這類寫法，複雜格式用測過的函式庫。

小結

  • 型別在執行時不存在，as 和 @Body() 的型別都只是希望。HTTP body、query、外部 API、JSONB、環境變數、localStorage 都是信任邊界，資料進來時驗證一次。
  • parse, don't validate：parse(x: unknown): T 回傳型別精確的新物件，只包含認得的欄位，大量指派與原型污染因此進不來。
  • 錯誤帶路徑（items[1].quantity），全部收集完一次丟出，前端和對接的平台才能直接定位。
  • JSON 只有六種值：日期是字串（要求時區、做往返檢查）、bigint 編號是字串（不能轉 Number）、null 不等於缺欄位；JSON body 不自動轉型，query string 才轉。
  • 正規表示式：一定要 ^ $；驗證用的不加 g；使用者輸入要跳脫，或改用 includes；避開巢狀量詞並先限制長度。
  • schema 把規則寫成資料，Infer<typeof schema> 推導型別，規則與型別一份來源。zod 4 是同樣的設計；NestJS 用 ValidationPipe 或 StandardSchemaValidationPipe 把它接在門口。

  • 日期字串轉成 Date：z.iso.datetime() 輸出仍是字串；zod 4 有 z.codec 做雙向轉換（例如字串 ↔ Date）。
