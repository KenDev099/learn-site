階段 4：函式、泛型與型別運算 · 第 22 課

型別運算：mapped、conditional、infer、template literal

咖啡店後台的訂單詳細頁上線後，客服回報了兩個 bug。第一個：頁面一打開就壞掉，Console 寫著 order.orderedAt.getTime is not a function。前端直接拿後端的 Order 型別來用，型別說 orderedAt 是 Date，但訂單經過 JSON.stringify 送到瀏覽器時，Date 已經變成字串（第 6 課），編譯器卻沒有任何紅線。第二個：有人改了組網址的程式，呼叫 buildPath('/orders/:orderId/items/:itemId', { orderId: '12' }) 時漏了 itemId，網址組錯，要等後端回 404 才發現。兩個 bug 的原因一樣：型別沒有跟著真實的資料走。

這一課的任務是寫出兩個型別，讓前端的型別從現有的東西自動推出來，不再手抄：DatesToStrings<Order> 從後端的 Order 推出「經過 JSON 之後」的形狀（練習 5），RouteParams<'/orders/:orderId'> 從路由字串推出參數物件，少給參數在編譯時就報錯（練習 4）。第 21 課的 Partial、Pick 做不到這些，要自己「計算型別」。一路上會用到 TypeScript 計算型別的四個工具：mapped type、conditional type、infer、template literal 型別。內建的 Partial、Exclude、ReturnType 都是用它們寫成的，學完你也看得懂、寫得出來。

這課的路線：
  1. 手抄一份 JSON 版的 Order 會不同步，怎麼「對每個欄位做同一件事」？mapped type。
  2. 怎麼只把 Date 換成 string？條件型別，加上前兩節就是 DatesToStrings 的最小版本（開場問題的最小答案），再看 Date | null 為什麼會漏掉。
  3. JSON 也會丟掉方法，怎麼把整個鍵去掉？mapped type 的 as。接著用 infer 直接取後端函式的回傳型別，連 Order 都不用手寫。
  4. 路由少給參數怎麼在編譯時抓到？template literal 型別，從 '/orders/:orderId' 拆出參數名稱。
  5. 巢狀的 Date 和第二個路由參數都要「再做一次」：遞迴型別。最後替型別寫測試，並判斷什麼時候該停手。
這課會用到：
  • 第 21 課的工具型別：Partial、Pick、Exclude 從一個型別推出另一個，而且 Partial、Readonly 只作用一層。
  • 第 20 課的 keyof 與 T[K]：keyof T 是所有鍵組成的聯合，T[K] 取出鍵 K 的屬性型別。
  • 第 19 課的泛型約束：T extends … 的意思是「T 要能指定給右邊」。

手抄一份 JSON 版的 Order 會怎樣？mapped type：每個鍵過同一個模具

先處理第一個 bug。最直覺的修法是在前端另外寫一份型別，例如 OrderJson，把每個 Date 欄位手動改成 string。今天能用，問題在之後：後端在 Order 加了 paidAt: Date | null，前端的 OrderJson 沒人記得改，編譯器也不會提醒，因為兩份型別之間沒有任何關係。這就是開場的 bug 換個時間再發生一次。

要讓兩份型別有關係，OrderJson 就得從 Order 推出來：把 Order 的每個欄位拿出來，Date 的換成 string，其他照抄，組成新型別。「把物件的每個鍵拿出來各做一次」這件事，TypeScript 有專門的寫法。第 21 課最後看過 Partial 的原始碼 { [P in keyof T]?: T[P] }，就是這種寫法，叫做映射型別（mapped type）。

它的運作分三步。第一，keyof T 給出所有鍵的聯合，例如 'id' | 'name' | 'price'。第二，[K in …] 把聯合裡的每個鍵輪流放進 K，每個鍵各產生一個屬性。第三，冒號右邊決定那個屬性的型別，可以用 T[K] 讀出原本的型別再加工。用 JavaScript 比喻，它像 Object.fromEntries(Object.keys(t).map(…))，只是處理的是型別，而且只發生在編譯時。

下圖用最簡單的模具示範：冒號右邊寫 T[K] | null，每個欄位都多了 null，這個型別叫做 Nullable（練習 1 會自己寫一次）。等一下 Date 換 string 用的是同一個結構，只是模具換成「是 Date 就變 string」的判斷。

屬性除了型別，還可能帶著 ?（可選）和 readonly（唯讀）這兩個標記，它們合稱修飾子（modifier）。推導 JSON 版的 Order 時要先想清楚：原本可選的欄位，JSON 版也應該可選；原本唯讀的，也應該唯讀。所以要知道 mapped type 怎麼處理修飾子。規則是：可以在 [K in keyof T] 前後加上修飾子，也可以在前面寫 - 拿掉：

寫法效果內建的例子
{ [K in keyof T]: T[K] }照抄，原本的 ?、readonly 保留（第 4 題用來攤平交集）
{ [K in keyof T]?: T[K] }每個屬性變可選Partial
{ [K in keyof T]-?: T[K] }拿掉可選，變必填Required
{ readonly [K in keyof T]: T[K] }每個屬性變唯讀Readonly
{ -readonly [K in keyof T]: T[K] }拿掉唯讀（沒有內建，練習 1 自己寫）

重點在 C：右邊完全沒寫修飾子，結果 id 仍然是 readonly、note 仍然是可選。[K in keyof T] 這種「直接走過某個型別的鍵」的寫法，TypeScript 知道每個 K 來自 T 的哪個屬性，會把那個屬性原本的 ? 和 readonly 自動抄過來。這對我們的任務是好消息：JSON 版的 Order 只要專心處理「型別怎麼換」，修飾子不用管，原本可選的照樣可選。練習 5 的測試也會檢查這一點。

反過來，如果改寫成 [K in 'id' | 'name'] 這種直接列出鍵的寫法，TypeScript 不知道它們來自哪個型別，修飾子就不會被保留。推導型別時，請盡量從 keyof T 出發。

💡 實務上：表單和 API 型別從同一個 Product 推出來
咖啡店後台的「編輯商品」表單，常要一個「每個欄位各一則錯誤訊息」的物件：{ [K in keyof Product]?: string }，Product 加了欄位，錯誤物件自動多一格，不會漏掉。同樣的手法也用在「每個欄位使用者改過沒有」的狀態、只送出改過欄位的 PATCH 請求。先找現成的：React Hook Form、VeeValidate 這類表單函式庫通常已經有這種型別，不用自己寫。只有一個地方用到的型別，直接手寫一個物件型別反而比較好讀。

mapped type 解決了「跟 Order 同步」，但它的模具對每個欄位都做同一件事。JSON 版的 Order 不是這樣：Date 欄位要換成 string，number、string 欄位要照抄。模具裡需要一個判斷。

怎麼只把 Date 換成 string？條件型別：型別的 if／else

上一節的模具需要寫出「這個欄位如果是 Date 就換成 string，不然照舊」。TypeScript 表達這種判斷的寫法叫條件型別（conditional type）：T extends U ? X : Y。T 可以指定給 U 時，結果是 X；不行時，結果是 Y。這裡的 extends 跟第 19 課泛型約束的意思一樣，是「可以指定給」，不是 class 的繼承。所以 '拿鐵' extends string 成立，因為字面值型別 '拿鐵' 可以放進 string 的位置。

執行前把滑鼠移到 A、B 上看判斷結果，C 先跳過，下面會解釋：

把條件型別放進上一節的模具，就是第一個 bug 的最小答案：

type OrderJsonV1<T> = { [K in keyof T]: T[K] extends Date ? string : T[K] }

type Order = { id: number; orderedAt: Date; paidAt: Date | null; customer: { name: string; joinedAt: Date } }
// OrderJsonV1<Order>：
// { id: number; orderedAt: string; paidAt: Date | null; customer: { name: string; joinedAt: Date } }

orderedAt 變成 string 了，開場那行 order.orderedAt.getTime() 現在會有紅線。但結果裡還有兩個 Date 沒換掉：paidAt 和 customer.joinedAt。customer.joinedAt 漏掉的原因很直接：模具只走過第一層的鍵，customer 整個物件被「照抄」了。這要等到後面的遞迴型別才處理得了。paidAt 漏掉的原因比較深：Date | null 這個聯合整塊拿去問「可以指定給 Date 嗎」，null 不行，所以整塊判定為「不是」，原樣保留。我們要的其實是「聯合裡的每個成員各判斷一次」：Date 換成 string，null 留著，得到 string | null。

上面那格的 C 正好就是「每個成員各判斷一次」。ToArray<string | number> 的結果不是 (string | number)[]，而是 string[] | number[]：條件型別遇到聯合時，會把聯合拆開，每個成員各算一次，再把結果聯合起來。這個行為叫分配（distributive）：

ToArray<string | number>
= ToArray<string> | ToArray<number>
= string[] | number[]

分配有一個前提：extends 左邊必須是「光禿禿的型別參數」，也就是單獨一個 T，而且呼叫時 T 收到的是聯合。ToArray 符合這個前提。OrderJsonV1 不符合：它的左邊是 T[K]，是從 T 讀出來的型別，不是型別參數本身，所以 Date | null 被當成一整塊判斷。

知道規則之後，修法就是把判斷抽成一個以型別參數為左邊的小型別，讓它有機會分配：

type DateToString<V> = V extends Date ? string : V
type OrderJsonV2<T> = { [K in keyof T]: DateToString<T[K]> }
// paidAt：DateToString<Date | null> = DateToString<Date> | DateToString<null> = string | null

分配不一定都是你要的。想把聯合當成一整塊判斷時（例如判斷「T 是不是聯合」），就把兩邊用 [] 包起來，變成比較兩個 tuple；左邊不再是光禿禿的型別參數，分配就關掉了。下面這格的 D 是關掉分配的版本；MyExclude 則是分配最常見的應用：

MyExclude 每個成員各自判斷：可以指定給 U 的變成 never，其他留下。never 是「沒有任何值」的型別，聯合裡的 never 會直接消失，所以結果就是「去掉某些成員的聯合」。第 21 課 lib 裡的 Exclude 就是這一行。

分配還有一個容易出乎意料的地方：傳進 never 時，因為 never 是「空的聯合」，拆開之後沒有任何成員可以算，結果直接是 never，不會走進任何一個分支。用條件型別判斷「整個型別」而得到奇怪的 never 時，先檢查是不是被分配了。

到這裡，orderedAt 和 paidAt 都處理好了。但 JSON 改變的不只有 Date：值是函式的屬性，經過 JSON 之後整個鍵都不見了。型別也要能「去掉鍵」，而這是目前的模具做不到的。

JSON 還會丟掉方法：怎麼把整個鍵去掉？mapped type 的 as

上一節的模具只能改「值的型別」，鍵的清單永遠跟 keyof T 一樣。但 JSON.stringify 只輸出能變成 JSON 的資料：值是函式的屬性會被略過，class 的方法放在 prototype 上，本來就不會出現。後端如果把一個有 total() 方法的購物車物件送出去，前端收到的 JSON 裡沒有 total。前端的型別如果還留著 total: () => number，呼叫它一樣是執行時才爆。

所以模具要能決定「這個鍵要不要留下」。mapped type 的鍵後面可以接 as，寫成 [K in keyof T as 新的鍵]，把每個鍵換成別的東西，這叫鍵重新對應（key remapping）。換成的東西如果是 never，那個屬性就不會出現在結果裡。搭配上一節的條件型別，「依值的型別決定要不要留這個鍵」就寫得出來了。

每個鍵 K 輪流經過 as 後面的條件型別：值是 string 的，結果是 K 自己，鍵留下；不是的，結果是 never，鍵消失。category 是 string | null，整塊判斷不能指定給 string，所以也被去掉了。這裡 T[K] 不是光禿禿的型別參數，不會分配，正好符合「整個欄位都是字串才留」的意思。

把條件換成「值是不是函式」，就是 JSON 會丟掉方法的版本，練習 2 的 DataOnly 就是要你寫這個。過濾一定要寫在 as 後面，也就是鍵的位置：

過濾要寫在 as 後面（鍵的位置）。寫在右邊（值的位置）像 { [K in keyof T]: T[K] extends string ? T[K] : never }，鍵還在，只是值變成 never，而 never 型別的屬性沒有值可以給，這個物件根本做不出來。

JSON 版的型別現在會換 Date、會去掉方法。但它的輸入 Order 還是手寫的：如果後端的查詢函式回傳的形狀改了，手寫的 Order 一樣會落後。最好連 Order 都直接從後端的函式取出來。

Order 能不能不手寫？infer：從函式和 Promise 裡取出一塊

後端查訂單的函式長得像 async function findOrder(id: number)，回傳的型別是 Promise<{ … }>。我們要的是 Promise 裡面那個物件的型別。這需要「拆開」一個型別：先從函式型別裡取出回傳型別，再從 Promise<X> 裡取出 X。

條件型別可以做到。在 extends 右邊的某個位置寫 infer X，意思是「這個位置的型別先不管是什麼，比對成功之後把它叫做 X」，在 ? 後面的分支就能用 X。它像 JavaScript 的解構賦值 const [first] = arr：寫出形狀，再從形狀裡的某一格取出值，只是 infer 拆的是型別。比對失敗時走 : 後面的分支，那時 X 不存在。

下面用一個查商品的函式示範，查訂單的寫法完全一樣。執行前把滑鼠移到 R、P、N 上，看每一步拆出了什麼：

  • R：typeof findProduct 是函式型別，符合「任何參數、回傳 R」的形狀，R 就是回傳型別 Promise<…>。
  • P：Promise<…> 符合 Promise<infer V>，V 就是裡面的物件。
  • N：number 不符合 Promise 的形狀，走到 : T，原樣回傳。

這兩個就是內建的 ReturnType、Awaited 的原理（第 20 課用過它們），Parameters 則是把 infer 放在參數的位置 (...args: infer P) => …。infer 可以放在任何位置：陣列元素 (infer E)[]、tuple 的第一格 [infer A, ...unknown[]]、函式參數。所以任務裡的 Order 可以寫成 Awaited<ReturnType<typeof findOrder>>，再交給 DatesToStrings：後端改了回傳形狀，前端的型別跟著改。

自己寫 infer 時要記得：比對的規則就是「可以指定給」，所以前面學過的指定規則全部會影響結果。有兩條規則特別容易讓 infer 得到意外的答案。

第一條：readonly 陣列不能指定給一般陣列（第 19 課）。as const 做出來的陣列是 readonly 的，拿 readonly string[] extends (infer E)[] 去比對會失敗，結果走到 : never。要寫成 readonly (infer E)[]：一般陣列可以指定給 readonly 陣列，所以兩種都接得住。

第二條：參數少的函式可以放進參數多的位置（第 18 課）。呼叫的人多給的引數，函式不讀就好，所以零參數的函式也符合「有第一個參數」的函式型別。這時 infer 在那個位置取不到任何東西，得到的是 unknown，而不是 never。執行前把滑鼠移到 B 上：

得到 unknown 的後果是錯誤被藏起來：unknown 什麼值都收，原本該報錯的地方全部通過。修法的方向是先把整個參數列表取出來（它是一個 tuple），再判斷這個 tuple 是不是空的。練習 3 自己寫。

💡 實務上：infer 多半是「用」，很少「寫」
日常最常見的是拿內建的 ReturnType、Parameters、Awaited 去借別人的型別：某個 SDK 的 createOrder(options) 沒有匯出 options 的型別，就寫 Parameters<typeof createOrder>[0]；API 函式回傳什麼，就用 Awaited<ReturnType<typeof fetchOrders>> 接，函式改了型別跟著改。要自己寫 infer 的情況通常在共用的工具型別裡，寫的時候順手測 readonly 陣列和零參數函式這兩個坑。Code review 看到一長串 infer，先問：這個型別能不能從函式庫直接 import？

回應那一頭的工具到齊了。接著處理第二個 bug：路由參數。infer 能從函式、Promise 裡取出一塊，它也能從字串裡取出一塊，前提是先學會在型別裡描述字串的格式。

路由少給參數怎麼在編譯時抓到？template literal 型別：組字串，也拆字串

第二個 bug 的路由 '/orders/:orderId/items/:itemId'，參數名稱藏在字串裡。要讓 buildPath 知道該收哪些參數，型別得能讀懂字串的格式：找到 :，取出後面的名字。描述字串格式的工具叫樣板字面值型別（template literal type），寫法跟 JavaScript 的樣板字串一樣是反引號加 ${}，只是放在型別的位置，${} 裡面放的是型別。

先看比較單純的方向：用它「組」字串。${} 裡放聯合時，結果是所有組合。咖啡店的事件名稱就是這種格式，執行前看 emit('order:payed') 那一行的紅線：

組合數是各聯合大小相乘，2 × 2 = 4 種。聯合越大，組合數長得越快，編譯也會變慢，上限見課末「補充與查表」。

在回到路由之前，先看組字串的另一個用途，練習 2 的 Getters 會用到：組出來的字串可以拿來當鍵名，這正是第三節 mapped type 的 as 的另一個用途：不是去掉鍵，而是把鍵改名。執行前把滑鼠移到 ProductSetters 上：

Capitalize 是內建的字串型別轉換，把第一個字母變大寫（同類的還有幾個，列在課末）。它只接受字串型別，這就是 string & K 存在的原因：keyof T 不一定是字串，物件的鍵也可以是 number（{ 0: 'a' }）或 symbol。直接寫 Capitalize<K> 會報 TS2344：Type 'K' does not satisfy the constraint 'string'。string & K 的意思是「K 裡面屬於 string 的部分」，number、symbol 的鍵交集之後變成 never，在 as 的位置就順便被去掉了。練習 2 的 Getters 用的就是這個寫法。

要取出每一個參數，得在 :name 後面找 /：/ 前面的是這一個參數的名字，/ 後面剩下的字串，可能還有更多參數，要再用同一個型別拆一次。一個型別在定義裡用到自己，這就是下一節的遞迴。

💡 實務上：適合「格式固定、選項有限」的字串
常見的用途：事件名稱（order:paid）、多語系的翻譯鍵（menu.latte.name）、設計系統的元件尺寸（btn-sm、btn-lg）：打錯字在編譯時就抓到，編輯器還會自動補完。路由參數這類「拆字串」的型別，Express、Hono 這些框架已經做好，應用程式裡通常是直接享受成果，不用自己重寫。要注意型別只管編譯時：字串如果來自使用者輸入或後端回應，執行時還是要先檢查（例如比對是不是在允許的清單裡），才能當成這個型別用。選項如果會隨資料變動，例如商品 ID 從資料庫來，就用 string，不要硬寫成聯合。

現在兩個 bug 各剩一塊：JSON 版的 Order 碰不到 customer.joinedAt 這種第二層的 Date，路由型別取不到第二個參數。兩個缺口的解法是同一個：對剩下的部分再做一次。

巢狀的 Date 和第二個參數：遞迴型別，再做一次

兩個缺口都需要「對剩下的部分再做一次」：JSON 版的 Order 遇到 customer 這種物件，要對它的每個屬性再套一次同一個轉換；路由型別遇到 / 後面剩下的字串，要再拆一次。型別定義裡用到自己，叫遞迴型別（recursive type），跟遞迴函式的想法一樣：處理眼前這一層，剩下的交給同一個型別。

先看一個跟 DatesToStrings 結構完全一樣、但更單純的例子：DeepReadonly，把每一層都變唯讀。第 21 課的 Readonly 只管一層，這裡用遞迴補上。執行前看最後兩行的紅線，它們都在第二層以下：

讀法是由上往下：T 如果是物件，就用 mapped type 走過它的每個鍵，每個屬性的型別交給 DeepReadonly 再算一次；不是物件（string、number 這類），就原樣回傳，遞迴在這裡停下來。customer 是物件，所以它的 name 也變成唯讀；id 是 number，直接停。

items 是陣列，結果卻還是陣列（只是變成 readonly 陣列，沒有 push），而不是一個有 length、push 鍵的怪物件。這是 mapped type 對陣列的特別處理：[K in keyof T] 遇到陣列或 tuple 時，TypeScript 只對每個元素套用轉換，結果仍然是陣列。所以 DatesToStrings 遇到 items: { addedAt: Date }[] 不用特別處理，陣列裡每筆的 addedAt 都會被轉換。

把這個結構套到任務上，要多一個判斷：遇到 Date 換成 string。這時條件的順序決定結果。Date、Map、函式也都是 object，如果 T extends object 寫在前面，Date 會先被當成一般物件拆開，變成一個有 getTime、toISOString… 的物件型別，永遠走不到「換成 string」那一支。所以 T extends Date 必須寫在 T extends object 前面。另外，這裡的 T 是光禿禿的型別參數，Date | null 傳進來會被分配，第二節的 paidAt 問題順便解決了。練習 5 把這些組起來。

路由那一邊的結構一樣：比對 ${string}:${infer Name}/${infer Rest}，Name 是這一個參數，Rest 交給同一個型別再拆；比對不到 / 時，就是最後一個參數；連 : 都沒有時，就沒有參數了，遞迴停下來。練習 4 把它寫完，再用 mapped type 把參數名稱的聯合變成 { orderId: string; itemId: string }。@types/express（Express 的型別套件）就是用這個技巧，讓 app.get('/orders/:orderId', (req) => …) 裡的 req.params.orderId 有型別。

遞迴一定要有終止條件，而且每算一次都要更接近它：DeepReadonly 每次往下一層，物件總有底；路由每次少一段字串，字串總會拆完。如果某個輸入讓遞迴永遠停不下來，TypeScript 不會無限算下去，它對型別展開的深度有上限，超過就報 TS2589。下面這格的 Tuple 每次多放一格，長度等於 N 就停；執行前看 Never 那一行：

兩個型別都寫得出來了。但開場的 bug 告訴我們一件事：錯的型別不會當掉，只會安靜地讓該報的錯不報。DatesToStrings 如果漏了一個 Date，我們怎麼會知道？

怎麼確認型別算對了？型別測試，以及什麼時候停手

型別也是程式，寫錯一樣會出事，而且更難發現：一般程式寫錯，測試會失敗或執行時會當掉；型別寫錯，最常見的結果是「該報的錯沒報」，畫面上什麼都看不出來。第二節的 OrderJsonV1 就是例子：它漏掉 paidAt，但沒有任何紅線提醒你。所以複雜的型別也要測試。

型別測試的意思是：寫一行「我預期這個型別算出來是某某型別」，算錯時編譯就報錯。這門課每一題的隱藏測試都是型別測試（type-level test），用的是 globals.d.ts 裡這兩行：

type Expect<T extends true> = T
type Equal<X, Y> =
  (<T>() => T extends X ? 1 : 2) extends (<T>() => T extends Y ? 1 : 2) ? true : false
  • Expect 只接受 true，傳進 false 就報 TS2344，所以 type _1 = Expect<Equal<A, B>> 在 A、B 不同時會有紅線。
  • Equal 不直接比較 X、Y，而是比較兩個泛型函式型別。裡面的條件型別因為 T 還沒決定而無法計算，TypeScript 只好看兩邊的 X、Y 是不是完全相同，比「互相可以指定」更嚴格。

為什麼要繞這麼一圈，不用簡單的「A 可以指定給 B，B 也可以指定給 A」？因為 any 可以跟任何型別互相指定。型別寫壞時最常算出來的就是 any，而測試工具如果分不出 any，等於什麼都沒測。執行前看 T1 和 T2 的差別：

T3 說明 Equal 連 readonly 都分得出來，所以練習 5 能檢查「原本的 readonly 和 ? 有沒有保留」。T4 說明交集 & 和攤平後的物件不算相同，所以練習 4 的測試先用 { [K in keyof T]: T[K] }（第一節表格的第一列）把結果攤平再比。Equal 也有分不出來的情況，列在課末。

型別測試有兩種寫法，各測一個方向：

  • Expect<Equal<…>> 確認「結果是這個型別」，例如 DatesToStrings<Order> 的每一層 Date 都變成 string。
  • // @ts-expect-error 確認「這樣寫要報錯」。它放在某一行上面，下一行必須有型別錯誤，沒有錯誤時它自己會報 TS2578。這種常被忽略，但它測的正是型別存在的目的：開場的第二個 bug，buildPath 少給參數要報錯，練習 4 就用它測。

在自己的專案裡不用手寫 Equal，測試框架有現成的工具，用法見課末。

任務完成了，但這一課的工具很容易越用越多。最後要練的是判斷：什麼時候值得寫，什麼時候該停手。

資深判斷：什麼時候停手。型別運算主要是給函式庫用的：一次寫好，很多人用，值得花力氣。應用程式碼裡要克制：
  • 一個型別超過三層巢狀的條件，就拆成幾個有名字的小型別，各自寫測試。
  • 錯誤訊息看不懂的型別，對同事等於沒有型別。寫完故意傳錯一次，看看紅線說了什麼。
  • 複雜型別會拖慢編輯器和 CI 的型別檢查；TS2589 是最明顯的訊號。
  • 一份手寫的介面、加上一個單元測試，常常比一個精巧的推導型別好維護。

套回這一課的任務：DatesToStrings 只有三個分支、一個遞迴，錯誤訊息也看得懂，而且前後端共用、每次後端改型別都會受益，值得寫；RouteParams 如果你用的框架已經提供，就直接用框架的。

補充與查表

主線用不到、但查資料或遇到問題時會用到的細節，查表用，不用背。

  • 版本：mapped type 的 as（鍵重新對應）和 template literal 型別都是 TypeScript 4.1 加入的。舊專案先看 package.json 的 typescript 版本再用。
  • 內建的字串型別轉換：Capitalize（第一個字母大寫）、Uncapitalize（第一個字母小寫）、Uppercase（全部大寫）、Lowercase（全部小寫）。都只接受字串型別。
  • template literal 的組合上限：組合數是各聯合大小相乘，3 個 10 種的聯合就是 1000 種，編譯會明顯變慢；組合數達到 100,000 種就報 TS2590（Expression produces a union type that is too complex to represent）。
  • Equal 分不出來的地方：方法寫法 { f(): void } 和屬性寫法 { f: () => void } 會判成相同，雖然第 18 課看過兩者的參數檢查不一樣嚴格。
  • 專案裡的型別測試：Vitest 有 expectTypeOf(x).toEqualTypeOf<Order>()，但執行時它什麼都不做，要加 --typecheck 參數，Vitest 才會用 tsc 檢查型別。

練習

練習 1：寫兩個 mapped type。Nullable<T>：每個屬性都可以是 null，原本的 readonly 和可選保留。Mutable<T>：拿掉 readonly，原本的可選保留。

練習 2：用 as 寫兩個型別。Getters<T>：每個鍵變成 get 加首字大寫的方法名，沒有參數、回傳原本的值型別（name → getName: () => string）。DataOnly<T>：去掉值是函式的屬性，其他照舊。

練習 3：用 infer 寫三個型別。ElementType<T>：陣列的元素型別，readonly 陣列也要能用，不是陣列時是 never。MyAwaited<T>：拆開 Promise，幾層都拆到底，不是 Promise 時原樣回傳。FirstArg<F>：函式第一個參數的型別，函式沒有參數時是 never。三個都要自己用 infer 寫，不要直接套內建的 Awaited、Parameters。

練習 4：寫 RouteParams<P>，從路由字串推出參數物件：'/orders/:orderId/items/:itemId' → { orderId: string; itemId: string }，沒有參數時是 {}。參數名稱只會是英數字。再改寫 buildPath(path, params)：把每個 :name 換成參數值（用 encodeURIComponent 編碼），而且少給參數要在編譯時報錯。

練習 5：寫 DatesToStrings<T>：把型別裡所有的 Date（包括巢狀物件和陣列裡的）換成 string，其他不變。用它描述 Order 經過 JSON 之後的形狀。

練習 6：type ToArray<T> = T extends unknown ? T[] : never，ToArray<string | number> 是什麼？

✓ T 是光禿禿的型別參數，條件型別遇到聯合會分配：string、number 各算一次再聯合起來。要得到 (string | number)[]，寫成 [T] extends [unknown] 關掉分配。聯合本身可以指定給 unknown，不會變成 never；T[] 用的是 T，不是 unknown。

練習 7：某個型別寫錯了，回傳 any。用 MutualEqual<A, B> = [A] extends [B] ? ([B] extends [A] ? true : false) : false 測試 MutualEqual<結果, number>，會發生什麼事？

✓ any 可以指定給 number，number 也可以指定給 any，互相指定的檢查兩邊都成立。課程用的 Equal 比較的是兩個泛型函式型別，要求 X、Y 完全相同，Equal<any, number> 是 false。型別測試的目的之一就是抓 any 漏進來，所以測試工具本身必須分得出 any。

練習 8：同事用五層巢狀的條件型別，從資料庫 schema 自動推導所有 API 的請求與回應型別，在應用程式裡用。最大的成本是什麼？

✓ 型別編譯後完全消失，不影響執行速度或打包大小。成本在人和工具：紅線說不出哪裡錯、新同事看不懂、修改一處牽動全部，嚴重時還有 TS2589 和很慢的型別檢查。應用程式碼裡把複雜型別拆成有名字的小型別並寫型別測試，或乾脆手寫介面；精巧的推導留給函式庫。

常見錯誤

  • 手抄一份 JSON 版、表單版的型別：原本的型別一改，手抄的那份不會跟著改，編譯器也不提醒。從原本的型別用 mapped type 推出來。
  • 沒注意到條件型別會分配，或以為它一定會分配：左邊是光禿禿的型別參數時，聯合會拆開各算一次；左邊是 T[K] 這類讀出來的型別時，聯合被當成一整塊，Date | null 就不會變成 string | null。要分配就把判斷抽成小型別，要整塊判斷就包成 [T] extends [U]。
  • 過濾鍵寫在值的位置：{ [K in keyof T]: … ? never : T[K] } 只是讓值變成 never，鍵還在。過濾要用 as … ? never : K。
  • infer 只寫了可變陣列的版本：T extends (infer E)[] 遇到 readonly 陣列和 as const 得到 never。寫 readonly (infer E)[]，兩種都接得住。
  • 用「有第一個參數的函式」去比對零參數函式：零參數函式也符合，infer 得到 unknown。先取出整個參數 tuple 再判斷是不是空的。
  • template literal 的鍵忘了 string &：Capitalize<K> 報 TS2344，因為 keyof T 可能是 number 或 symbol。寫成 Capitalize<string & K>。
  • 遞迴型別的條件順序錯誤，或沒有終止條件：Date、Map、函式也是 object，特別處理的要寫在 T extends object 前面；停不下來的遞迴會報 TS2589。
  • 寫了複雜的型別卻沒有型別測試：錯的型別不會當掉，只會讓該報的錯不報。用 Expect<Equal<…>> 測結果，用 @ts-expect-error 測「該報錯的有報錯」。
  • 在應用程式碼裡過度使用型別運算：看不懂的錯誤訊息等於沒有型別。超過三層就拆成有名字的型別，或改成手寫的介面。

小結

  • 開場的兩個 bug 都是型別沒跟著真實資料走。修法是從現有的東西推出型別：DatesToStrings<Order> 描述經過 JSON 的訂單，RouteParams<P> 從路由字串推出參數，少給參數編譯時就報錯。
  • mapped type { [K in keyof T]: … } 對每個鍵套用同一個轉換，從 keyof T 出發時原本的 ?、readonly 會保留；-?、-readonly 拿掉修飾子；陣列經過它還是陣列。
  • 條件型別 T extends U ? X : Y 是型別的 if／else。左邊是光禿禿的型別參數時，聯合會分配，所以 Date | null 能變成 string | null；[T] extends [U] 關掉分配；Exclude 就是分配的應用。
  • mapped type 的 as 可以改鍵名，對應到 never 就去掉那個鍵，例如去掉 JSON 不會帶的方法。
  • infer 在比對成功時取出一塊型別，Awaited<ReturnType<typeof findOrder>> 讓 Order 也不用手寫；比對的規則是「可以指定給」，readonly 陣列和零參數函式是常見的坑。
  • template literal 型別可以展開所有組合，也可以搭配 infer 把字串拆開；要拆出每個路由參數，得把剩下的字串遞迴再拆。
  • 遞迴型別要有終止條件，條件的順序決定結果（Date 要在 object 之前）；停不下來會報 TS2589。
  • Equal 要求兩個型別完全相同，分得出 any 和 readonly；@ts-expect-error 測該報錯的有報錯。應用程式碼裡克制使用型別運算，精巧的推導留給函式庫。

階段檢核：面試會問的觀念

練習 9：共用工具這樣寫，型別檢查全部通過。今天還沒有任何訂單時，first(orders).total 會怎樣？

function first<T>(items: readonly T[]): T {
  return items[0]
}

✓ 空陣列的 items[0] 是 undefined，但索引存取的型別是 T，回傳型別寫 T 等於型別在說謊，編譯器不會擋。回傳型別寫 T | undefined，呼叫的人就被逼著處理找不到。c 錯在讀 undefined 的屬性會丟 TypeError，不是安靜地拿到 undefined。（第 19 課）

練習 10：findById 要給商品和訂單共用，同事寫成 function findById(items: readonly { id: number }[], id: number)，沒有型別錯誤。跟 <T extends { id: number }> 的版本比，差在哪？

✓ 泛型把輸入和輸出連起來：傳 Product[] 進去就拿回 Product | undefined，約束只要求「至少要有 id」。參數直接寫成 { id: number }[]，拿回來就只剩 id 可以用。b 錯在結構型別多的欄位不管，Product 傳得進去，問題出在拿回來的那一頭。（第 19 課）

練習 11：通知模組這樣定義，有人放進只會寄 Email 的函式。哪裡會出事？

type Email = { channel: 'email'; address: string }
type Sms = { channel: 'sms'; phone: string }
interface Notifier {
  send(to: Email | Sms): void
}
function emailOnly(to: Email) { console.log(`寄到 ${to.address}`) }
const notifier: Notifier = { send: emailOnly }
notifier.send({ channel: 'sms', phone: '0912345678' })

✓ 介面用方法寫法 send(to): void 宣告時參數是雙變，往窄也放行；strictFunctionTypes 只對函式型別寫法做逆變檢查。改成屬性寫法 send: (to: Email | Sms) => void，第 7 行就會報錯。b 正是改成屬性寫法之後的結果，方法寫法下不會發生。（第 18 課）

練習 12：訂單付款後要寄收據，事件處理函式的型別是 (o: Order) => void，同事寫成 bus.on('order:paid', async o => { await sendReceipt(o) })。sendReceipt 偶爾失敗時會怎樣？

✓ 回傳 void 的位置可以放回傳任何東西的函式，包括 Promise，所以型別檢查不報；呼叫的人丟掉回傳值，失敗就變成 unhandled rejection。開 typescript-eslint 的 no-misused-promises 抓這種寫法。a 錯在 void 的意思是「呼叫者不會使用回傳值」，不是「只能回傳 undefined」。（第 18 課）

練習 13：專案裡已經有 type OrderStatus = 'pending' | 'paid' | 'cancelled'。現在 API 要檢查網址上的 ?status= 是不是這三個之一，最好的做法是？

✓ 型別編譯後整個消失，執行時沒有東西可以拿來比對，所以方向只能是值 → 型別：as const 的陣列同時給執行時檢查和 (typeof X)[number] 推型別。d 執行起來沒問題，但清單和型別各寫一份，之後加 'refunded' 遲早有一邊忘了改。（第 20 課）

練習 14：STATUS_COLOR 是訂單狀態對應標籤顏色的表。要求：OrderStatus 之後加了 'refunded'，這張表要報錯；STATUS_COLOR.paid 的型別要是 'green'。怎麼宣告？

✓ satisfies 檢查形狀，但不改變推論出來的型別：少了 refunded 會報錯，值仍是 as const 的字面值。b、d 缺鍵時也會報錯，但 b 的註記蓋掉了推論，d 少了 as const 照一般推論，STATUS_COLOR.paid 都只剩 string。（第 20 課）

練習 15：Product 的 id 是 readonly id: number，repo.save 依 id 存檔。型別檢查通過的 updateProduct(7, { id: 8, price: 120 }) 會怎樣？

type UpdateProductInput = Partial<Product>

function updateProduct(id: number, patch: UpdateProductInput) {
  const p = repo.findById(id)!
  repo.save({ ...p, ...patch })
}

✓ Partial<Product> 讓 id 也變成可選欄位，型別就允許 PATCH 帶 id；展開後 id 換成 8，存檔蓋掉別的商品。先去掉不該改的欄位再 Partial：Partial<Omit<Product, 'id'>>。b 錯在 readonly 只在編譯時擋「對屬性賦值」，執行時展開照樣複製過去。（第 21 課）
