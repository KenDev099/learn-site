階段 5：寫後端需要的 TypeScript · 第 23 課

類別：存取修飾子、implements 與抽象類別

前端寫 Vue 很少用到 class，後端卻到處都是：NestJS 的 controller、service、repository 全是 class。打開一個 NestJS 專案，第一眼看到的多半是這一行：

constructor(private readonly productsService: ProductsService) {}

這一行同時做了三件事：宣告一個欄位、限制外面不能讀寫它、把建立物件的人傳進來的東西存進去。這課的任務是把咖啡店的下單服務 OrderService 寫成這個樣子：它要查商品價格，正式環境向資料庫查，寫測試時換成記憶體裡的假資料，而 OrderService 本身一行都不用改。這課要學的 class 語法，都是在完成這個任務的路上遇到的。

這課的路線：
  1. 商品寫成 class：欄位型別怎麼寫，TypeScript 為什麼逼你一定要初始化每個欄位。
  2. 金流金鑰存在欄位裡：private 和 #private 差在哪、為什麼前者擋不住人，並讀懂開場那一行（開場問題的最小答案）。
  3. 參數屬性：開場那一行怎麼一次做完三件事，代價是 NestJS 專案一定要先編譯。
  4. implements 與抽象類別：怎麼讓資料庫版和記憶體版 repository 符合同一份規格，幾個實作共用的流程放哪裡。
  5. 依賴注入與「class 是值也是型別」：OrderService 怎麼在測試時換掉 repository，NestJS 的容器又為什麼只認得 class。
這課會用到：
  • 第 3 課的 class：extends 繼承、super 呼叫父類別，#private 欄位在 class 外面讀不到。
  • 第 14 課的 interface 與結構型別：TypeScript 只看形狀、不看名字，欄位和方法夠就符合。
這一頁的練習區開著 noImplicitOverride，第 5 節會講它在擋什麼。

商品寫成 class，TypeScript 為什麼逼你初始化每個欄位？

任務從最底層開始：OrderService 要查的是商品，先把商品寫成 class。欄位、建構子參數、方法加型別的方式跟函式一樣，名稱後面加冒號寫型別。下面的 Product 照這個方式寫，但漏了一件事：price 宣告了，卻沒有人給它值。執行後看印出來的價格，再看編輯器在 price 那一行畫的紅線。

型別說 price 是 number，執行時它卻是 undefined，所以印出「拿鐵 undefined 元」。如果這個值被拿去算小計，結果是 NaN，而且一路上沒有任何錯誤告訴你是哪裡出事。

紅線來自 strict 模式裡的 strictPropertyInitialization 檢查。它的規則是：型別裡不含 undefined 的欄位，一定要在宣告的地方或建構子裡給值，否則報 TS2564。為什麼只看這兩個地方？因為它們是「物件建好的那一刻」一定會執行到的程式碼；兩處都沒給值，new 出來的物件就一定缺這個欄位。TS2564 擋的就是這種型別說謊：型別保證有，實際上沒有。

修法有三種，差別在「值由誰提供」：

寫法例子什麼時候用
給初始值price = 0有合理的預設值時
建構子賦值this.price = price值一定要由建立的人提供時（最常見）
明確賦值斷言 !price!: number確定有別人會填值，例如框架在建立物件後才把資料放進去

第三種叫明確賦值斷言（definite assignment assertion）：在欄位名稱後面加 !，意思是「我保證有人會填值，不用檢查」。它跟第 17 課的非空斷言 ! 一樣，只是叫編譯器閉嘴，執行時什麼也不做；保證錯了，就回到上面印出 undefined 的狀況，而且這次連紅線都沒有。

所以自己寫的 class，優先用建構子賦值：值由建立物件的人提供，忘了傳時，錯誤會出現在呼叫 new 的那一行，而不是好幾層之後算出 NaN 的地方。

💡 實務上：NestJS 關掉這個檢查，是為了 DTO
NestJS 用一種 class 描述「請求內容長什麼樣子」，叫做 DTO（Data Transfer Object）。NestJS 12 官方 starter 的 tsconfig 開著 strict，但把 strictPropertyInitialization 設成 false，原因是 DTO 的值是框架在收到請求後才填進去的，開著這個檢查，每個欄位都要加 !。這是框架的取捨，不是「一般程式也該關」的理由：關掉之後，你自己寫的 service 忘記初始化欄位也不會被抓到。只有「值由框架填」的欄位才有這個理由；值由程式自己提供的 class，照樣用建構子賦值。練習 2 的 CreateOrderDto 名字雖然叫 DTO，但它是程式自己 new 出來的，值由建立它的人傳進來，所以用建構子賦值，不用 !。

商品的欄位有了著落。但下單流程裡不只有商品：OrderService 還要向金流收款，金流的 API 金鑰也會存在某個 class 的欄位裡。上面的欄位誰都能讀寫，金鑰這種欄位要怎麼擋住外面？

金流金鑰存在欄位裡，怎麼不讓外面讀到？

上一節的 Product，任何拿到實例的程式都能讀、也能改 latte.price。商品名稱這樣沒關係，金鑰就不行。TypeScript 用存取修飾子（access modifier）限制成員的讀寫範圍，寫在欄位或方法前面：

  • public：誰都可以（預設就是 public，通常不寫）。
  • private：只有這個 class 裡面可以（TS2341）。
  • protected：這個 class 和它的子類別可以，外面不行（TS2445）。

另外 readonly 管的是「能不能改」而不是「誰能讀」：欄位只能在宣告處或建構子裡賦值，之後再改就報 TS2540。

這些修飾子有一個關鍵特性：它們只在編譯時檢查。第 13 課講過，TypeScript 編譯成 JavaScript 時會擦掉型別；修飾子也一起被擦掉，private 欄位在執行時就是普通屬性。第 3 課的 #private 不一樣，它是 JavaScript 本身的語法，私有是執行環境保證的。下面的 PaymentGateway 用兩種寫法各存一個金鑰，按執行，看每一行印出的東西哪些拿得到：

對照輸出，由上到下：

  • as any 繞過型別檢查之後，apiKey 直接拿到。
  • JSON.stringify 和 Object.keys 都列出 apiKey，沒有 #secret。寫進 log 或回應時，前者會跟著出去。
  • 用字串 '#secret' 去讀，拿到的是 undefined：#secret 不是一般屬性，從 class 外面沒有任何寫法讀得到。

比喻：TS 的 private 是門上貼「員工專用」，守規矩的人不會進去，但門沒鎖；#private 是上鎖的保險箱。完整的比較：

TS private#private
檢查時間只在編譯時執行時（語言本身）
as any 讀得到嗎讀得到讀不到
JSON.stringify、Object.keys會出現不會出現
子類別能用嗎不能（要用 protected）不能
結構型別有 private 成員的 class，只有它自己（和子類別）的實例才符合同左
能當安全機制嗎不能可以擋住同一個程序裡的其他程式碼

選擇的原則：要藏起來的狀態（購物車內容、金鑰）用 #；只是想提醒同事「這是內部細節，不要從外面碰」，TS 的 private 就夠。NestJS 的程式碼大量用 TS 的 private，因為它要擋的是誤用，不是攻擊。

表格倒數第二列在第 6 節會回來：class 只要有 private 或 #private 成員，就不能用形狀相同的普通物件代替它，這會影響測試時能不能塞假物件。練習 3 也會用到。原因是 TypeScript 比對兩個型別時，private／#private 成員不只看名字和型別，還要求它們來自同一個 class 宣告；普通物件就算有同名欄位也不算數，所以只有這個 class（和它的子類別）的實例才符合。

到這裡已經讀得懂開場那一行：constructor(private readonly productsService: ProductsService) {} 等於宣告一個 private、唯讀、型別是 ProductsService 的欄位，再把建立物件的人傳進來的 service 存進去。private 讓外面的程式碼不會誤用它，readonly 讓它建好之後不會被換掉。

💡 實務上：別把 class 實例直接當 API 回應
咖啡店後台的 User class 可能有 private passwordHash，型別上「外面讀不到」，但 controller 直接 return user 時，框架會 JSON.stringify 它，雜湊值就跟著回應送到前端。改成 #passwordHash 雖然不會被序列化，但靠這點藏欄位很脆弱，哪天有人改回 private 就漏了。實務做法是回應時明確挑欄位（或另外定義回應用的 DTO），只送前端需要的東西。資深在 code review 看到「把資料庫查出來的物件原封不動回傳」，會先問：裡面有沒有不該出去的欄位？

意思讀懂了，寫法卻還沒解釋。PaymentGateway 為了存兩個金鑰，欄位宣告一次、建構子參數一次、賦值一次，同一個名字寫了三遍；開場那一行只寫一遍。它是怎麼做到的？

開場那一行怎麼一次宣告欄位、接收參數、完成賦值？

在建構子參數前面加上 public／private／protected／readonly 任一個，這個參數就變成參數屬性（parameter property）：TypeScript 會替你宣告同名的欄位，並在建構子一開始把參數存進去。先用一個最陽春的商品目錄試：建立時把商品清單傳進來，之後用 id 查價格，這正是 OrderService 需要的能力，下一節再把它正式化成 repository。下面的 ProductCatalog 用一行收下商品清單。執行後看 Object.keys 印出的名稱，products 真的成了實例上的欄位：

參數屬性很方便，但它跟前面學過的型別語法有一個根本差異。型別註記、private 修飾子，編譯時「刪掉就好」；參數屬性刪掉之後，欄位和賦值也跟著不見了，所以編譯器必須多產生程式碼。把 ProductCatalog 編譯成 ES2022 的 JavaScript，結果是：

class ProductCatalog {
    products;
    constructor(products) {
        this.products = products;
    }
    …
}

原始碼裡沒有的 products; 欄位宣告和 this.products = products，都是編譯器補上的。這種「不能只靠刪掉型別得到 JavaScript」的語法叫不可擦除的語法，第 15 課的 enum 也是。

這件事會影響程式怎麼執行。Node 24 可以直接執行 .ts 檔，但它只做 type stripping：把型別的部分刪掉，不產生任何新程式碼。遇到參數屬性，Node 不會默默跑出一個少了欄位的物件，而是直接丟出 ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX（Node 課第 5 課）。NestJS 專案到處是參數屬性（還有第 24 課的裝飾器），所以一定要先用 tsc 或 SWC 編譯再執行，不能交給 Node 直接跑（NestJS 課第 1 課）。反過來，想讓 Node 直接執行的小工具，就寫成一般欄位加建構子賦值。編譯器有選項能提前擋下這類語法，見課末「補充與查表」。

OrderService 的建構子寫法有了：用參數屬性接收它需要的 repository。但「它需要的 repository」是什麼？正式環境查資料庫、測試時查記憶體，這是兩個不同的 class。怎麼確定兩個都提供 OrderService 要用的方法？

資料庫版和記憶體版 repository，怎麼保證符合同一份規格？

先說 repository。第 19 課出現過這個詞：repository 是專門負責存取某一種資料的物件，例如 ProductRepository 只管商品的查詢和儲存。資料存取集中在它身上，OrderService 就不用知道商品到底存在 PostgreSQL 還是記憶體裡。

要讓兩種實作可以互換，先寫一份規格：用 interface 列出 repository 一定要有的方法。每個實作的 class 再用 implements 宣告「我符合這份規格」。少了方法或簽章不對，TypeScript 就在 class 這裡報 TS2420，而不是等到某個呼叫端把它傳進 OrderService 時才報。錯誤出現在寫錯的地方，比出現在使用的地方好查得多。

下面是記憶體版的 repository。執行結果正常，但看 findById(id) 那一行的紅線：

這是 implements 最容易誤會的地方：它只檢查、不推論。介面裡寫了 findById(id: number)，class 裡的 id 也不會因此變成 number；參數沒寫型別就是隱含的 any，報 TS7006。implements 做的只是最後比對「這個 class 的形狀符不符合介面」，參數型別照樣要自己寫。把 id 改成 id: number，紅線就消失。

介面解決了「規格」的問題，但它只有形狀、沒有程式碼。如果幾個實作之間有一段一模一樣的流程，介面幫不上忙，每個 class 都得各寫一次。這時要用另一個工具。

幾個實作共用同一段流程時，程式碼放哪裡？

這裡換一個例子，因為 repository 的兩個實作剛好沒有共用的流程。下單完成後要通知顧客取餐，可以走簡訊或 LINE。不管走哪個管道，「組出『訂單 42 可以取餐了』這句話、再送出去」的流程都一樣，只有「送出去」那一步各管道不同。這種「流程共用、其中一步各自實作」的情況，用抽象類別（abstract class）：

  • 前面加 abstract，不能直接 new（TS2511），只能被繼承。
  • 可以有寫好的方法（共用骨架），也可以有 abstract 方法：只寫簽章，子類別一定要實作，沒實作就報錯。
  • abstract 也能用在屬性上，例如 abstract readonly label: string：父類別只宣告「一定有這個欄位」，子類別一定要給值（readonly label = '現金'）。練習 4 會用到。

執行看 orderReady 怎麼呼叫到子類別的 send，再看 SmsNotifier 裡 describe 那一行的紅線：

orderReady 寫在父類別，裡面呼叫的 this.send 卻是 SmsNotifier 實作的那一個：共用的流程放父類別，各管道不同的那一步交給子類別。父類別宣告了 abstract send，TypeScript 就保證每個子類別都有實作，新增 LINE 通知時忘了寫 send，在 class 這裡就會報錯。

describe 的紅線是另一回事。SmsNotifier 的 describe 蓋掉了父類別的 describe，這叫覆寫。override 關鍵字明確標示「這個方法是覆寫父類別的」。這一頁開著 noImplicitOverride：覆寫卻沒寫 override 就報 TS4114；寫了 override 但父類別根本沒有這個方法，也會報錯。它擋的是這種事故：父類別把 describe 改名成 label，子類別的 describe 沒人發現，悄悄變成一個沒人呼叫的新方法，畫面上顯示的變回父類別的「通知」。實作 abstract 方法不算覆寫，所以 send 不用寫。把 SmsNotifier 的 describe 加上 override，錯誤就消失。

到這裡有兩個工具都能描述「一組 class 該長什麼樣子」。差別整理成表：

interfaceabstract class
有實作嗎沒有，只有形狀可以有共用方法與欄位
執行時存在嗎不存在存在，可以 instanceof
一個 class 能用幾個implements A, B 好幾個只能 extends 一個
普通物件能符合嗎能（結構型別）沒有 private 成員時也能，但 instanceof 不成立

資深的判斷：只需要約定形狀就用 interface；真的有多個子類別共用的流程（像所有付款方式都是「金額＋手續費」，練習 4 會寫）才用抽象類別。繼承最多一兩層，越疊越深時，改一個父類別會影響一大串子類別，這時改用「把物件傳進來組合」，也就是下一節的依賴注入。

💡 實務上：介面依「呼叫端需要什麼」來定，不要照抄廠商 SDK
咖啡店要接信用卡和 LINE Pay，常見做法是定一個 PaymentGateway 介面（例如 charge(orderId, amount)），每家廠商各寫一個 class 去 implements。常見的坑是照第一家廠商的 SDK 參數設計介面，第二家接進來時發現欄位對不上，只好改介面、連帶改所有呼叫端。資深會先問：OrderService 真正需要的是哪幾個動作？廠商特有的細節（簽章、回呼格式）關在各自的實作裡。只有一種實作、也不需要在測試換掉的東西，不必硬抽一個介面。

回到 OrderService。規格（ProductRepository 介面）和實作（記憶體版、資料庫版）都準備好了，最後一步是把 repository 交給 OrderService。交的方式有兩種，其中一種會讓測試寫不下去。

OrderService 怎麼拿到 repository，測試時才換得掉？

物件做事需要用到的其他物件，叫做依賴（dependency）。OrderService 要查商品價格，ProductRepository 就是它的依賴。依賴從哪裡來有兩種寫法。下面兩個 OrderService 算的是同一個小計：A 在欄位裡自己 new 資料庫版，B 從建構子接收。DbProductRepository 用丟錯模擬「測試環境沒有資料庫」。執行看 A 和 B 各印出什麼：

A 一呼叫就丟錯：「用哪個 repository」被寫死在它裡面，測試沒有任何辦法換掉，只能真的準備一個資料庫。B 用的是測試傳進去的 fakeRepo，算出兩杯拿鐵 220 元。

寫法二叫做依賴注入（dependency injection, DI）：依賴由建立物件的人從外面傳進來，而不是物件自己 new。好處有三個：

  • 好測試：測試傳一個假的 repository（記憶體版本，甚至一個物件字面值），不用真的資料庫。
  • 好替換：從 PostgreSQL 換成別的儲存方式，OrderService 一行都不用改。
  • 依賴看得見：建構子的參數清單就是「它需要什麼」的完整清單。

注意 B 的參數型別寫的是介面 ProductRepository，而不是某個具體的 class。這是第 2 節表格「結構型別」那一列的後果：介面只看形狀，所以只有 findById 的物件字面值 fakeRepo 也放得進去；如果參數型別寫成有 #products 的 InMemoryProductRepository，物件字面值就不符合了，測試只能用那一個 class。

💡 實務上：什麼該注入、什麼直接 import
會碰到外部世界的東西才值得注入：資料庫 repository、金流、寄信、目前時間（測「優惠到期」時要能固定時間）。純計算的函式，例如算折扣、四捨五入金額，直接 import 呼叫就好，不需要包成 class 再注入。code review 時兩個常見訊號：service 裡出現 new DbProductRepository()，代表測試換不掉；建構子參數多到七八個，通常代表這個 class 管太多事，該拆了。

任務的形狀完成了，但還剩一個問題：誰來 new？正式環境裡 OrderService 要 ProductRepository，ProductRepository 要資料庫連線，一層層手動組起來很快就失控。NestJS 的 DI 容器幫你做這件事：讀建構子需要什麼、依序建立、同一個只建一次（NestJS 課第 3 課）。可是容器是在執行時工作的，而型別在執行時都不見了。容器能靠什麼知道「這個參數要給什麼」？

NestJS 的容器在執行時看得到什麼？class 同時是值也是型別

容器在執行時只看得到「值」。OrderService、DbProductRepository 這些 class 擦掉型別後還在，ProductRepository 這個 interface 卻什麼都不剩。為什麼？因為 interface 和 class 雖然都能寫在冒號後面當型別，但只有 class 能 new：寫 class Product {} 會同時產生兩樣東西：

  • 值：執行時真的存在的建構子函式，可以 new、可以 instanceof、可以當參數傳。
  • 型別：這個 class 的實例長什麼樣子，寫在冒號後面。

interface 只產生型別，擦掉後什麼都不剩。所以執行時要用到的東西，只能是 class。下面用一個最小的 ProductService 把兩種身分分開看。執行看 instanceof 的結果；最後一行註解拿掉後，會看到拿 interface 當值的錯誤：

程式中間多了兩個寫法，下一課自己做 DI 容器時會用到：

  • 建構子型別（constructor type）：new (...args: any[]) => T，描述「可以用 new 呼叫、產生 T」的東西。上面的 create 收的就是這種參數。create(ProductService) 就是容器最核心的動作：拿到 class 本身，自己 new。DI 容器、外掛系統也一樣：它們收的是 class 本身，自己決定什麼時候 new。
  • InstanceType<typeof C>：typeof C 不是實例的型別，而是 class 這個值（建構子）本身的型別；InstanceType 再從建構子型別取出「它 new 出來的東西」的型別。

這直接決定了 NestJS 的寫法：

  • DTO 要寫成 class：ValidationPipe（NestJS 負責驗證請求內容的元件）要在執行時讀 DTO 上的驗證規則，interface 執行時不存在，什麼都讀不到（NestJS 課第 7 課）。
  • 注入的目標要是 class 或 token：框架要在執行時知道「這個參數要給它什麼」，interface 擦掉了，沒辦法當鑰匙。token 是註冊時自訂的一把鑰匙，例如字串或 Symbol（'PRODUCT_REPOSITORY'），讓 interface 型別的參數也能指定要注入什麼，詳見 NestJS 課第 3 課。下一課會看到 interface 參數在執行時變成 Object。

回到任務：OrderService 已經寫成開場那一行的樣子，建構子用參數屬性接收 ProductRepository，測試時傳假的進去就能測。剩下的缺口是正式環境：參數型別寫的是 interface，容器在執行時看不到它。下一課看 NestJS 怎麼把型別資訊留到執行時，以及 interface 參數要怎麼補救。

練習

練習 1：寫 class Cart：

  • 建構子收 id（字串），之後不能改。
  • 品項存在 #items（商品 id → 杯數），實例上除了 id 不能有別的屬性，JSON.stringify 也不能看到品項。
  • add(productId, qty)：同一個商品加兩次要累加；qty 不是正整數時丟 RangeError。
  • total(prices)：prices 是 Record<number, number>（商品 id → 單價），回傳總金額；有商品查不到價格時丟 RangeError。
  • get count：目前總杯數。

練習 2：CreateOrderDto 的三個欄位都報 TS2564。不要用 ! 跳過檢查，改成用建構子初始化：

  • new CreateOrderDto(customerId, items, note?)，備註可以不傳。
  • 加一個 static from(input)，從普通物件（例如解析好的 JSON）建立真的 CreateOrderDto 實例。

用一般欄位加建構子賦值，或用參數屬性都可以。

練習 3：已經有 ProductRepository 介面和 NotFoundError（第 4 課的自訂錯誤類別）。寫：

  • InMemoryProductRepository implements ProductRepository：商品存在 #products 裡。
  • OrderService：建構子注入一個 ProductRepository；placeOrder(productId, qty) 回傳小計（單價 × 數量），找不到商品時丟 NotFoundError。

測試會傳入假的 repository，OrderService 要能接受任何符合介面形狀的東西，包括物件字面值。

練習 4：從零寫付款方式：

  • abstract class PaymentMethod：抽象屬性 label（字串）、抽象方法 fee(amount)（回傳手續費）；寫好的 charge(amount) 回傳「金額＋手續費」，describe() 回傳 label。
  • CashPayment：label 是「現金」，手續費 0。
  • CardPayment：label 是「信用卡」，手續費是金額的 2%，四捨五入到整數元（第 5 課）；describe() 覆寫成「信用卡（手續費 2%）」。

本頁開著 noImplicitOverride。

練習 5：class User { private passwordHash = 'x1y2' }，在執行時 (user as any).passwordHash 和 JSON.stringify(user) 會怎樣？

✓ 型別擦掉後 private 就是普通屬性，as any、JSON.stringify、Object.keys 都看得到，回應或 log 裡就會出現密碼雜湊。a、c 描述的是 #private 的行為。真的不能外流的欄位用 #，回傳給前端的資料另外挑欄位組成。

練習 6：用 Node 24 直接執行 node order.service.ts，檔案裡有 constructor(private readonly repo: ProductRepository) {}，會怎樣？

✓ Node 預設只做 type stripping，參數屬性編譯後要多出欄位宣告和 this.repo = repo，屬於不可擦除語法，Node 直接報錯而不是默默跑錯，所以 b 不對；a 要加實驗性的 --experimental-transform-types 才會發生。NestJS 專案要先編譯；想讓 Node 直接執行的程式就開 erasableSyntaxOnly，編譯時就擋下（TS1294）。

練習 7：為什麼 NestJS 不能只靠 constructor(private repo: ProductRepository) 裡的 interface 決定要注入哪個實作？

✓ interface 只是型別，擦掉之後什麼都不剩；DI 是在執行時發生的，框架只能用執行時存在的東西（class 或自訂的 token）當鑰匙。b 錯：參數型別寫 interface 完全合法，練習 3 就是這樣寫。c 錯在前提：interface 在執行時不存在。下一課會看到它在 metadata 裡變成 Object，以及 NestJS 用 token 加 @Inject 的解法。

常見錯誤

  • 到處用 ! 讓 TS2564 消失：錯誤不見了，欄位照樣是 undefined。優先用建構子賦值；只有框架真的會填值時才用 !。
  • 把 TypeScript 的 private 當安全機制：執行時就是普通屬性，as any、JSON.stringify 都看得到。要真的藏起來用 #private。
  • 以為 implements 會幫方法參數推論型別：implements 只檢查、不推論，參數沒寫型別就是 TS7006。
  • 覆寫方法沒寫 override：父類別改名後，子類別的方法悄悄變成沒人呼叫的新方法。在 tsconfig 開 noImplicitOverride。
  • 繼承層級越疊越深：改父類別會牽動一整串子類別。共用流程才用抽象類別，其他用組合（把物件傳進來）。
  • 在服務裡自己 new 依賴：測試換不掉、要換實作得改程式。從建構子接收，參數型別寫介面。
  • 用 interface 當注入的目標或 DTO：interface 執行時不存在，框架讀不到。DTO 寫成 class，注入的鑰匙用 class 或 token。

小結

這課把 OrderService 寫成 NestJS 的樣子，一路用到的東西：

  • 欄位要在宣告處或建構子裡初始化（TS2564），否則型別說有、執行時是 undefined；! 只在框架會填值時用。NestJS starter 關掉 strictPropertyInitialization 是為了 DTO，不是一般做法。
  • public／private／protected／readonly 只在編譯時檢查；#private 才是執行時真的私有。開場那一行是 private、唯讀的欄位，值由建立物件的人傳進來。
  • 參數屬性一次宣告、接收、賦值，是 NestJS 的標準寫法；它會產生程式碼，不是可擦除語法，所以要先編譯。
  • implements 讓資料庫版和記憶體版 repository 在 class 這裡就被檢查，但不推論參數型別；幾個實作共用流程時用抽象類別，它不能 new；覆寫寫 override，實作抽象成員不用。
  • 依賴注入：依賴從建構子傳進來，參數型別寫介面，測試時就能換成假的實作。
  • class 同時是值和型別，interface 只是型別；執行時要用到的東西（DTO、DI 的鑰匙）只能是 class。

補充與查表

主線用不到、但寫 class 或換執行環境時會遇到的細節，查表用，不用背。

  • 在建構子以外的方法裡賦值：TypeScript 只看建構子本身裡的賦值。在建構子裡呼叫 this.init()、在 init 裡賦值，仍然會報 TS2564：子類別可能覆寫 init，不保證會賦值。
  • 提前擋下不可擦除的語法：開了 erasableSyntaxOnly，參數屬性、enum 這類語法會報 TS1294。想讓 Node 直接執行的程式開這個選項，編譯時就知道哪裡不能用。
