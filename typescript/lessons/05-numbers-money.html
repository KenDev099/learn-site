階段 1：JavaScript 的核心機制 · 第 5 課

數字與金額：浮點數、四捨五入與大整數

月底對帳，會計拿著一張單來找你：客人點了拿鐵 110、卡布奇諾 110、可頌 70，用會員價打 85 折。收銀機印給客人的收據是 248 元，後台報表記的是 247 元。同一張單差了 1 元，而且這種單一個月有上百張。更麻煩的是，隔天這位客人退了一杯拿鐵，客服問你：該退他多少？

這一課你要接手這段結帳程式，跟著這張單走完它的一生：算出總額、記下每一行的折扣以便退款、把店長在後台輸入的價格字串變成數字、存進資料庫拿到訂單編號，最後回傳給 App 顯示。每一站都有一個 JavaScript 數字的陷阱，平常測不出來，等到對帳、退款、客人點開訂單時才爆。學完你能用整數精確算錢、把四捨五入寫成一條明確的規則、把折扣分攤到每一行且加總不變、安全地把外部字串轉成數字，也知道資料庫的大整數為什麼到了 Node 會變成字串。

這課的路線：
  1. 0.1 + 0.2 為什麼不等於 0.3：程式裡的數字本身準不準，哪些數字算得準、哪些算不準。
  2. 這張單該收 247 還是 248：金額用整數算，四捨五入定成一條規則（開場問題的最小答案）。
  3. 客人退一杯拿鐵該退多少：把 43 元折扣分攤到三行明細，加總還要剛好是 43。
  4. 價格從表單和 API 進來是字串：先檢查格式再轉換，怎麼用正規表示式描述「合法的金額」。
  5. 訂單編號為什麼會變成別人的單：安全整數、資料庫的 bigint 與 BigInt；最後把金額格式化印到收據上。

為什麼 0.1 + 0.2 不等於 0.3？

要知道 247 和 248 哪個對，得先確定一件更基本的事：程式裡的數字本身算得準不準。先跑下面四行，猜猜看會印出什麼，再看結果。

你會看到 0.30000000000000004、false、1989.9999999999998、434.99999999999994。這不是 bug，是 JavaScript 存數字的方式造成的。

JavaScript 一般用的數字只有一種型別，叫 number。它是浮點數：電腦用二進位、固定的 64 個位元來存一個數字，其中一部分存有效數字，一部分存小數點的位置。「浮點」指的就是小數點的位置可以移動，所以同一種格式既能存 0.001 也能存一百萬。

問題出在「十進位寫得完的小數，二進位不一定寫得完」。用我們熟悉的十進位想：1/3 寫成 0.3333…，永遠寫不完，只能在某一位截斷，存進去的就不是真正的 1/3。二進位也一樣，只是寫不完的數字不同：0.5 是 1/2，二進位寫得完；0.25 是 1/4，也寫得完；但 0.1 是 1/10，在二進位是無限循環小數。位元數有限，只好截斷，存進去的是一個非常接近、但不等於 0.1 的數。

那為什麼 console.log(0.1) 印出來還是 0.1？因為 JavaScript 印數字時，會挑「最短、而且能對回同一個存值」的十進位寫法。單獨的 0.1 印回 0.1，看起來沒事；但兩個有誤差的數加起來，誤差疊在一起，結果就對不回 0.3 了，誤差才被你看見。19.9 * 100 也是同一回事：19.9 本來就存得不精確，乘以 100 之後，差距大到印得出來。

這在算錢時會出什麼事？假設程式要把 19.9 美元換成「分」，寫了 Math.floor(19.9 * 100)，得到的是 1989，少了一分錢。一筆少一分看不出來，一個月幾萬筆就是對不上的帳。

整數不會有這個問題。整數在二進位一定寫得完，所以在一定範圍內（最後一節會講是多大），整數的加、減、乘都是精確的。這給了算錢的第一條規則：不要拿帶小數的數字來算錢。

那用 toFixed 四捨五入不就好了？

很多人看到 0.30000000000000004，第一個反應是用 toFixed(2)「四捨五入到兩位」把尾巴切掉。它有兩個問題：回傳的是字串，而且它處理的是已經失真的二進位數，結果會跟你在紙上算的不同。

1.005 實際存的是 1.00499999…，所以 toFixed(2) 誠實地捨成 1.00。誤差在存進去的那一刻就發生了，事後再怎麼捨入都救不回來。再加上它回傳字串，拿去 + 1 會變成接字串。所以 toFixed 只適合在最後「顯示」時用，不要拿來算。

既然小數存進去就不準，事後捨入也救不了，那算錢只剩一條路：從一開始就不讓小數進來。下一節用這個想法回到開場那張單。

這張單該收 247 還是 248？

上一節的結論是「不要拿帶小數的數字來算錢」。具體做法是用最小單位的整數（integer minor units）來存和算：選一個這個幣別不會再往下切的單位，所有金額都用這個單位的整數表示。台幣、日圓實際上不用小數，最小單位就是「元」，拿鐵存成 110；美元有小數，最小單位是「分」，4.35 美元存成 435。這樣存進去、加總、比較都是整數，第一節的誤差沒有機會出現。資料庫那一端也一樣，PostgreSQL 課的 orders.total 是 integer（PostgreSQL 課第 13 課）。

但整數擋不住所有的小數。打 85 折時，拿鐵 110 × 85% = 93.5，結果天生就有小數。這時候一定要捨入成整數，而「怎麼捨」不是程式自己決定得了的，要定一條四捨五入規則（rounding rule）：在哪一步捨入、用什麼方式捨入。開場那 1 元的差距，就是兩段程式用了不同的規則。把那張單用兩種規則各算一次：

商品規則 A：每行先捨入規則 B：整張最後捨入
拿鐵、卡布奇諾、可頌（110、110、70）94 + 94 + 60 = 248290 × 0.85 = 246.5 → 247
拿鐵、可頌（110、70）94 + 60 = 154180 × 0.85 = 153 → 153

差距從哪裡來？規則 A 裡，三行打折後都剛好是 .5（93.5、93.5、59.5），每一行都往上捨，等於多收了三次 0.5 元，共 1.5 元。規則 B 只在整張單的 246.5 捨一次，只多了 0.5 元。所以收銀機用的是規則 A（248），報表用的是規則 B（247），開場的謎底就是這個。第二列的拿鐵加可頌也一樣：規則 A 捨了兩次，規則 B 的 153 根本不用捨。

哪一個才對？兩種規則都說得通，各有店家採用。真正的錯誤是系統裡同時存在兩種規則：收銀機、發票、退款、報表只要有一處不同，對帳一定對不上。所以這條規則要跟會計或產品一起訂好、寫進文件，所有算錢的程式都照它。這一課的練習用規則 B。

寫成程式時還有兩個細節，都是為了不讓小數提早進來。第一，打幾折用整數百分比表示：折扣寫成 15（代表減 15%），而不是 0.85，因為 0.85 在二進位一樣存不精確，一乘下去誤差就跟著進來。第二，先乘再除，只捨入一次：寫成 Math.round(價格 × (100 − 折扣) ÷ 100)。先乘，中間值 290 × 85 = 24650 還是整數；最後除以 100 才出現小數，馬上交給 Math.round 捨成整數，小數只存在一瞬間。捨入的方式（遇到 .5 往哪邊捨）也是規則的一部分，退款這種負數金額尤其要先講好，細節見課末的補充與查表。

💡 實務上：捨入規則是規格，要在寫程式前問清楚
咖啡店上線會員折扣、滿額折、優惠券時，PM 通常只寫「打 85 折」，不會寫在哪一步捨入。資深工程師會先問：每行先捨入還是整張最後捨入？多張優惠券怎麼疊加、先後順序是什麼？發票、退款、報表是不是同一套規則？問到的答案寫進文件，再用幾張固定的範例訂單（像上面的 247 和 248）寫成測試，之後誰改了計價程式，測試會先抓到差 1 元。最常見的坑是前端購物車自己算一次、後端結帳又算一次，兩邊規則不同，客人看到的金額和實際扣款不一樣；金額以後端算的為準，前端只顯示後端回傳的結果。

統一成規則 B 是往後的修正。開場那張單已經照收據收了 248 元，退款要以客人實際付的金額為準，差的 1 元由會計決定怎麼處理，不能拿新規則回頭改舊單。以下假設收銀機也已經改用規則 B：這張單收 247 元，折扣是 290 − 247 = 43 元。總額的問題解決了，但開場客服的問題還沒有：客人只退一杯拿鐵時，這 43 元裡有多少屬於拿鐵？

客人退一杯拿鐵，該退多少？

要回答客服，就得知道 43 元的折扣在三行明細上各佔多少。拿鐵原價 110，如果它分到 16 元折扣，退款就是 110 − 16 = 94 元。所以下單時就要把 43 元記到每一行上。最直覺的寫法是依金額比例分，每行各自四捨五入：

43 元分完只剩 42 元，100 元分三份只剩 99 元。原因跟上一節一樣是捨入：每一份 16.31、16.31、10.38 各自捨掉一點零頭，捨掉的零頭加起來接近 1 元，就這樣不見了。這 1 元不見會怎樣？三杯都退完，客人拿回的錢比當初少付的多 1 元，帳又對不上了。

所以這裡需要的不是捨入，而是分攤（allocation）：把一個整數總額拆成好幾個整數，拆完加總必須剛好等於原本的總額。常用的做法是最大餘數法（largest remainder method），它的想法是「先全部少給，再把少給的零頭補給最該拿的人」：

  1. 每一份先無條件捨去（Math.floor）。這樣每份都只會少給、不會多給。
  2. 算出還差幾元：總額 − 捨去後的加總。因為每份少給不到 1 元，差的錢一定比份數少。
  3. 把這幾元一元一元分給小數部分最大的那幾份，也就是被捨掉最多的那幾份；一樣大時，給排在前面的。

結果是拿鐵 16、卡布奇諾 16、可頌 11，加總剛好 43。回到客服的問題：退一杯拿鐵，退 110 − 16 = 94 元。

還剩一個問題：比「小數部分」時，不要真的拿 0.31 和 0.38 這種小數去比，它們本身也有第一節的浮點數誤差。兩份的餘數理論上一樣大時，浮點數可能算出一個 0.30999… 一個 0.31000…，零頭就給錯人了。解法是全部用整數算，改比「整數除法的餘數」。% 是取餘數的運算子，a % b 是 a 除以 b 剩下的整數。拿鐵這一份是 43 × 110 ÷ 290：先算 43 × 110 = 4730，Math.floor(4730 / 290) = 16 是商，4730 % 290 = 90 是餘數。可頌的餘數是 43 × 70 % 290 = 110，比 90 大，所以那 1 元給可頌。餘數除以 290 就是那個小數部分（90 ÷ 290 ≈ 0.31），所以比餘數和比小數部分是同一件事，但整數除整數、整數取餘數，在安全範圍內都是精確的。這就是練習 3。

💡 實務上：部分退款、優惠券分攤都會用到
整張單的折價券、運費、會員折扣，只要之後可能「只退其中一項」，就要在下單當下把金額分攤到每一行明細並存進資料庫（例如 order_items 多一欄折扣金額）。不要等到退款時才重算：那時商品可能已經改價、優惠活動已經結束，重算的結果會跟當初收的錢對不上。上線前資深工程師會檢查一件事：每張訂單的明細折扣加總，是不是剛好等於整張單的折扣，可以寫成測試，也可以定期跑一條 SQL 對帳。如果系統只賣單品、從不部分退款，就不需要分攤，別先做。

到這裡，總額和每一行的折扣都算對了。但這兩節都假設一件事：價格本來就是乾淨的整數 110、70。實際上，這些價格是店長在後台表單裡打進來的，到後端時是字串。

價格從表單、API 進來是字串，怎麼安全地變成整數？

拿鐵的 110 從哪裡來？店長在後台「修改商品價格」的表單輸入、POS 匯入的 CSV 檔、網址參數，或是外部服務的 API（例如練習 1 那種給美元金額字串 '4.35' 的 API）。這些來源送到後端時，金額常常是字串。所以算錢之前，一定有一步「字串轉數字」。JavaScript 有好幾種轉換方式，對「不完全是數字」的字串反應都不一樣，先跑一次看看：

輸出裡的 NaN 是轉換失敗時得到的值，意思是 Not a Number（不是一個數字）。它的型別卻還是 number，而且不等於任何值，包括自己：NaN === NaN 是 false，所以不能用 === NaN 判斷，要用 Number.isNaN(x)。另外兩個常用的檢查：Number.isFinite(x) 檢查它是數字、不是 NaN 也不是 Infinity；Number.isInteger(x) 檢查它是整數。

放回咖啡店想：店長不小心把價格欄位清空送出，Number('') 是 0，拿鐵就變成 0 元；匯入的 CSV 裡寫著 '110元'，parseInt 照收成 110，看起來沒事，但寫著 '1,100' 時它只讀到 1。這些都不會報錯，錯誤的價格會安靜地存進資料庫。

但 NaN 只擋得住「完全不像數字」的字串，擋不住上面那些被誤收的情況：'' 變成 0、'12px' 變成 12，都不是 NaN。結論是：這些轉換函式都太寬鬆，不能拿來當「驗證」。順序要反過來，先檢查格式，再轉換：先描述合法的金額長什麼樣子，字串符合了才轉。描述字串格式的工具，是正規表示式。

怎麼描述「合法的金額」？正規表示式入門

正規表示式（regular expression，常簡稱 regex）是一種描述字串格式的小語言。它寫在兩條斜線之間，用 .test(字串) 檢查一個字串符不符合，回傳 true 或 false。

正規表示式裡有兩類符號要先認識。一類叫錨點（anchor）：^ 代表字串的開頭，$ 代表字串的結尾，它們不比對任何字元，只把比對的位置固定住。另一類叫量詞（quantifier）：+、?、{1,2} 接在某個東西後面，說「前一個東西出現幾次」。其餘的符號多半就是比對它自己，或是一種字元。下面把「最多兩位小數的金額」一段一段拆開：

/^\d+(\.\d{1,2})?$/

^          從字串開頭開始比對
\d         一個數字（0–9）
+          前一個東西出現一次以上：\d+ 就是「一串數字」
(  )       把裡面當成一組
\.         一個真的小數點（單獨的 . 代表「任何字元」，要加 \ 才是小數點）
\d{1,2}    一到兩個數字
?          前一個東西（這裡是整組）可有可無
$          比對到字串結尾

合起來讀：從開頭起，一串數字，後面可以接「小數點加一到兩位數字」，然後就必須結束。下面用它檢查一批字串，再看少了錨點會怎樣：

只有 '120'、'4.35'、'19.9' 通過，上一張表裡那些被誤收的寫法全部被擋下。少了 ^ 和 $ 時，正規表示式的意思變成「字串裡某一段符合就算通過」，所以 'abc12'、'12abc' 都會過，等於沒驗證。驗證格式時一定要兩個錨點都寫。

格式通過之後才轉換，而且轉換本身也不能碰浮點數：'4.35' 通過驗證，直接 Number('4.35') * 100 還是第一節的 434.99999999999994。練習 1 要你處理這一步。正規表示式還有 g 旗標、效能陷阱（ReDoS）等主題，第 26 課驗證外部資料時再講；第 6 課會用它檢查日期字串。

💡 實務上：在資料進來的地方驗證一次，之後就信任它
咖啡店後台的「修改商品價格」表單、POS 匯入的 CSV、金流服務打回來的付款通知（webhook），都是外部字串進來的地方。前端的 <input type="number"> 只是方便使用者輸入，送到後端的仍然是字串，而且任何人都能繞過前端直接打 API，所以後端一定要再驗證一次。做法是在 API 的入口把字串驗證、轉成整數，之後程式裡流動的都是乾淨的整數，不要每個函式各自 parseFloat 一次。格式不對時回 400 和看得懂的錯誤訊息（例如「價格最多兩位小數」），而不是靜靜存成 0 元。手機號碼、Email 這類規則複雜的格式不要自己從頭寫正規表示式，第 26 課會用驗證套件處理。

現在進到結帳程式的每個金額都是驗證過的整數。這張單算好、存進資料庫，資料庫回給你一個訂單編號。這個編號也是一個數字，而它會出另一種完全不同的問題。

訂單編號為什麼會變成別人的單？

假設咖啡店的訂單編號是資料庫的 bigint 主鍵（例如由多台 POS 依 Snowflake 規則產生後寫入），這張單拿到的是 9007199254740993。App 點開這張訂單，卻顯示另一張單的內容。金額都是整數，為什麼還會出錯？因為第一節說「整數是精確的」時，加了一個條件：在一定範圍內。現在要講這個範圍。

number 用來存有效數字的位元數是固定的，相當於 53 個二進位位數。整數只要用得到的位數不超過這個長度，就能精確存下來；超過了，不是每個整數都存得下：相鄰的整數開始共用同一個存值，只有部分整數（例如 253、260）能被精確表示。這個上限是 Number.MAX_SAFE_INTEGER，也就是 253 − 1 = 9007199254740991。±(253 − 1) 以內的整數叫安全整數（safe integer），在這個範圍內每個整數都有自己的存值；超過之後，相鄰的整數會存成同一個數。

你寫的是 …993，印出來是 …992，而且兩個不同的編號比較起來相等。最後一行是開場問題的原因：App 收到 JSON 回應，JSON.parse 把 id 轉成 number，沒有任何錯誤，就悄悄變成了 …992，App 拿著這個錯的編號去查，查到的是另一張單。

資料庫那一端的整數範圍比 JavaScript 大得多。PostgreSQL 的 bigint（也叫 int8）可以到 9223372036854775807，遠超過安全整數。所以 Node 的 pg 套件（node-postgres，Node 課用的 8.23.1，用法見 PostgreSQL 課第 25 課）預設把 int8 回傳成字串。count(*) 的型別也是 bigint，所以 SELECT count(*) 拿到的是 '3' 而不是 3。numeric 在 pg 套件裡沒有預設的轉換，也是字串。這不是 bug：套件不知道你的值會不會超過安全範圍，選擇不冒失真的風險，把要不要轉、怎麼轉交給你決定。開場那張單出錯，就是後端在這裡做錯了決定：為了讓前端拿到數字，它把 pg 給的字串做了 Number(row.id)（或用會把 bigint 寫成 JSON 數字的序列化方式）才回傳，App 的 JSON.parse 收到的就是超過安全範圍的數字，讀出來的已經是失真的編號。後面的「ID 保持字串」修的就是這一步。決定的方式如下：

PostgreSQL 型別pg 套件預設給你建議做法
integer（int4）number直接用
bigint（int8）、count(*)字串ID 保持字串；確定很小的計數可以 Number()；要運算才轉 BigInt
numeric字串金額改用整數欄位；真的要小數就用十進位運算套件，不要轉成 number 再算

大多數時候 ID 只拿來比較、當 key，保持字串就夠了。真的要對大整數做運算時（例如練習 4 的「下一號」），用 BigInt：JavaScript 另一種專門存整數的型別，大小沒有上限，運算永遠精確。寫法是數字後面加 n（123n），或用 BigInt('123') 從字串轉。它跟 number 是兩種不同的型別，所以有幾個限制，跑一次看看：

  • BigInt 只存整數，所以除法會把小數捨去：7n / 2n 是 3n。
  • BigInt 和 number 不能直接混算，1n + 1 會丟 TypeError，要先把其中一邊轉成另一種。
  • JSON.stringify 遇到 BigInt 會丟錯，因為 JSON 沒有對應的格式。
  • BigInt('') 是 0n，BigInt(' 12 ') 是 12n，跟上一節 Number('') 是 0 一樣寬鬆。

最後一點代表順序跟金額一樣：先用正規表示式檢查格式，再轉換。而第三點決定了回傳的方式：回給前端時用 toString() 轉回字串，JSON 裡的大整數 ID 一律是字串，前端的 JSON.parse 也就不會把它轉成 number 而失真。開場那個「點開變成別人的單」就是這樣修好的。

💡 實務上：API 的 ID 欄位一開始就用字串
訂單、會員、交易的 ID 一旦用 bigint，或是用多台伺服器各自產生的長整數 ID（例如 X（前 Twitter）的 Snowflake ID，它的 API 因此另外提供字串版的 id_str），前端的 JSON.parse 一樣會失真，而且不會報錯，只會在「點開訂單卻跑出別人的資料」時才被發現。所以設計 API 時，ID 欄位在規格裡就訂成字串，前後端、App 都照這個約定，比上線後再改型別容易得多（改型別等於改 API，所有呼叫端都要跟著改）。ID 本來就不需要加減，用字串比較、當 key 都沒問題；真的要做運算的情況很少，例如本課練習 4 的「下一號」，而且那是後端的事。

這張單的 API 回應現在是 { id: '9007199254740993', total: 247 }：ID 是字串、金額是整數元。剩下最後一站：把 247 印到收據上。

收據上怎麼印出「$247」？

一路下來金額都是整數，到了畫面才變成「$1,234」這種有貨幣符號、千分位的樣子。這一步叫格式化，用內建的 Intl.NumberFormat 依地區做，不要自己拼千分位和符號：

同一個數字，地區不同寫法就不同：zh-TW 顯示成 $1,234，en-US 才會加上 NT$。另外，台幣在這套格式裡的預設小數位數是 2，所以要自己設 maximumFractionDigits: 0，否則 110 會顯示成 $110.00。

練習

練習 1：寫 toCents(text)：把 API 給的美元金額字串（最多兩位小數，例如 '4.35'、'19.9'、'120'）精確轉成「分」的整數。格式不對（''、' 10'、'12abc'、'1.005'、'-3'、'1e3'…）一律丟 RangeError。

提示：先用正規表示式檢查，再轉換。轉換可以把整數部分和小數部分分開處理，也可以乘 100 之後四捨五入。

練習 2：寫 orderTotal(items, discountPercent)。items 是 { unitPrice, quantity } 的陣列（整數元），discountPercent 是 0～100 的整數（15 代表打 85 折）。依照這一課的規則 B：先加總，再套折扣，最後只用 Math.round 四捨五入一次，回傳整數元。discountPercent 不是 0～100 的整數時丟 RangeError。

練習 3：寫 allocate(total, weights)：把整數金額 total（元）依 weights（每一行的金額）的比例分攤成整數陣列，加總必須剛好等於 total。用最大餘數法：每份先無條件捨去，剩下的零頭一元一元分給餘數最大的那幾份，餘數一樣大時給前面的。餘數用整數的 % 算。不要改到傳進來的 weights（第 2 課：回傳新陣列，不改傳進來的資料）。

這些情況丟 RangeError：total 不是 ≥ 0 的整數；weights 是空陣列、有負數或小數、或全部是 0。

練習 4：資料庫的訂單 id 是 bigint，pg 套件給你的是字串。寫 nextOrderId(id)，回傳下一號（字串），任何大小都要精確。id 不是正整數的字串（例如 ''、'0'、'-1'、'1.5'、' 12 '、'abc'）時丟 RangeError。開頭多了 0 的 '007' 也不是資料庫會給的 id，一樣丟錯。

練習 5：0.1 * 3 === 0.3 的結果是什麼？

✓ 0.1 在二進位是無限循環小數，存進去就已經有誤差，運算後誤差被放大到看得見。所以 a 錯：十進位寫得完的小數，二進位不一定寫得完。c 錯：number 本來就能存小數，乘法不會丟錯，只是結果有誤差。這不是 JavaScript 特有的，所有用 IEEE 754（浮點數的國際標準）的語言都一樣。算錢要改用整數。

練習 6：100 元的折扣要分攤到三行明細，每一行用 Math.round(100 / 3)，三行加總是多少？

✓ 33.33 捨成 33，三份是 99，所以 a 錯。b 的 101 要每份都往上進位（34）才會出現，33.33 四捨五入是往下捨。每一份各自四捨五入，加總就可能多 1 或少 1。要用分攤規則（例如最大餘數法）把零頭補回去，加總才會剛好是 100。

練習 7：用 pg 套件執行 SELECT count(*) FROM orders，拿到的是字串 '3'。為什麼？

✓ 這是刻意的設計。bigint 最大到 9223372036854775807，轉成 number 會失真。b 錯：這是刻意的預設，升級不會變。c 錯：integer 欄位就會是 number，所以不是「所有數字」。確定很小的計數可以自己 Number()，ID 保持字串，要運算才用 BigInt。

常見錯誤

  • 用小數算錢：price * 0.85、19.9 * 100 都帶著二進位誤差。改用最小單位的整數和整數百分比，最後只捨入一次。
  • 用 toFixed 四捨五入：它回傳字串，+ 1 會變成接字串；而且 (1.005).toFixed(2) 是 '1.00'。只在顯示時用，或改用 Intl.NumberFormat。
  • 沒講好四捨五入規則：每行先捨入和整張最後捨入，結果差 1 元。規則要跟會計一起訂好，全系統只用一種。
  • 分攤時每一份各自四捨五入：加總會差 1 元。用最大餘數法，餘數用整數的 % 算。
  • 用 parseInt／parseFloat 驗證輸入：'12abc' 會變成 12。先用正規表示式檢查格式，再轉換。
  • 以為 Number('') 會失敗：它是 0，空白欄位被當成 0 元；BigInt('') 也是 0n。
  • 正規表示式沒有 ^ 和 $：只要字串裡某一段符合就通過。
  • 把 bigint 的 id 轉成 number：超過 9007199254740991 就失真，兩筆不同的訂單會變成同一個 id。ID 保持字串，要運算才轉 BigInt。

補充與查表

負數怎麼捨入

捨入方式也是捨入規則的一部分。Math.round 遇到剛好 .5 時是往正無限大的方向捨：Math.round(2.5) 是 3，Math.round(-2.5) 是 −2，不是 −3。退款金額如果用負數表示，同一個 .5 在收款和退款時會捨往不同方向，金額就不對稱。所以要先決定負數怎麼捨，常見做法是先用正數算，最後再加負號。

JSON.parse 怎麼精確讀出大整數

進階：JSON.parse 的第二個參數 reviver 會對每個值呼叫一次。新的規格讓 reviver 收到第三個參數 context，context.source 是那個值的原始文字，還沒變成 number，所以可以精確轉成 BigInt。Chrome 114、Node 21 起支援，下面的範例在不支援的環境會印出提示。

小結

  • number 是二進位浮點數，0.1 這種十進位小數存不精確，toFixed 事後捨入也救不回來；安全範圍內的整數加減乘是精確的。
  • 金額用最小單位的整數（台幣用元），折扣用整數百分比，先乘再除、只在一處 Math.round。捨入規則（每行先捨入或整張最後捨入）要跟會計訂好、全系統只用一種，差 1 元就是規則不一致。
  • 折扣要能部分退款，就在下單時分攤到每一行。分攤用最大餘數法：先捨去，零頭依整數餘數由大到小一元一元分，加總不變。
  • Number、parseInt、parseFloat 都太寬鬆。先用有 ^、$ 的正規表示式檢查格式，再轉換；失敗時丟 RangeError。
  • 超過 Number.MAX_SAFE_INTEGER 的整數會失真。pg 套件把 bigint、numeric 回傳成字串；ID 保持字串，要運算用 BigInt，它不能跟 number 混算，也不能直接 JSON.stringify。
  • 顯示金額用 Intl.NumberFormat，只在最後一步格式化；存檔、回傳 API 的永遠是整數。
