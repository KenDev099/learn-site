階段 1：JavaScript 的核心機制 · 第 6 課

日期與文字：時區、Intl 與 Unicode

咖啡店的後台原本跑在店裡的電腦上，這個月搬到美國紐約的雲端伺服器。上線第一週，客服接到三件回報：

  1. 店長說 10 月 31 日的日報表少了單。少掉的那筆是台北時間 10 月 31 日凌晨 0:30 下的，報表把它算進了 10 月 30 日。
  2. 會員王小明的生日是 5 月 20 日，生日優惠卻在 5 月 19 日就寄出去了。
  3. 陳美華把暱稱設成 4 個帶膚色的 emoji，系統說超過 10 個字的上限。

程式一行都沒改，在你自己的電腦上（剛好在台北）也測不出來。這一課把這三件事一件一件追到底：前兩件出在 JavaScript 怎麼表示時間，第三件出在 JavaScript 怎麼表示文字。修完你能說出 Date 裡面到底存了什麼、用 Intl.DateTimeFormat 算出「台北的哪一天」、安全地解析日期字串並擋掉 2 月 30 日、正確地替日曆日期加月份，也能正確算出使用者看得到的字數。

這課的路線：
  1. 同一筆訂單，為什麼紐約的伺服器算成 30 日：Date 只存一個毫秒數，「幾號」是讀的時候用時區算出來的。
  2. 怎麼指定用台北的時區算：用 Intl.DateTimeFormat 修好日報表（第一件事的答案），以及為什麼不能自己加 8 小時。
  3. 時間在資料庫和 API 之間怎麼存、怎麼傳，收到的日期字串怎麼讀才不會差一天、怎麼擋掉 2 月 30 日。
  4. 生日為什麼早一天：日曆日期不是瞬間，不該變成 Date；加一個月遇到月底怎麼辦（第二件事）。
  5. 暱稱的字數：length 算的不是看得到的字，怎麼算才對、怎麼比對才不會漏（第三件事）。
這課會用到：
  • 第 4 課的 throw new RangeError(…)：輸入不對就丟錯，不要回傳奇怪的值。
  • 第 5 課的「先檢查格式再轉換」：先用有 ^、$ 的正規表示式確認字串長得對，再轉成數字。

同一筆訂單，為什麼紐約的伺服器算成 10 月 30 日？

先看日報表怎麼決定一筆單算哪一天：它拿訂單的下單時間（一個 Date），呼叫 getDate() 讀出「幾號」。要知道為什麼讀出來是 30，得先知道 Date 裡面存了什麼。

Date 物件裡面只存一個數字：從 1970-01-01T00:00:00Z 這個固定起點算起，過了幾毫秒。這個數字叫 epoch 毫秒（epoch milliseconds），epoch 就是「起點」的意思。它沒有存時區，也沒有存「幾月幾號、幾點」。

為什麼只存一個數字？因為時間軸上的某一刻，全世界只有一個。不管你在台北還是紐約，「從起點過了多少毫秒」都是同一個數，要比較先後、算兩個時間相隔多久，用減法就好。執行下面的範例：

  • getTime() 印出的大數字，就是 Date 裡真正存的東西。
  • 用同一個數字再建立一個 Date，得到的是同一個時間。
  • Date.now()（現在這一刻）也只是一個數字。

那「幾號」是哪裡來的？getDate()、getHours()、toString() 每次被呼叫時，拿這個毫秒數，用執行環境的時區臨時換算出來。執行環境的時區就是程式跑在哪台機器上、那台機器設定的時區，最後一行印出的就是它。所以同一行程式在你的電腦和雲端的伺服器上，會印出不同的結果。

要看懂差在哪裡，先把幾個名詞講清楚：

  • 下單的那一刻是時間軸上的一個點，叫瞬間（instant）。Date 存的就是瞬間。
  • 同一個瞬間，各地牆上的時鐘顯示不同的日期時間，因為各地用不同的時區（time zone）。
  • 所有時區的基準叫 UTC（世界協調時間）。某個時區的時鐘比 UTC 快或慢多少，叫 UTC 偏移（offset）：台北是 UTC+8，比 UTC 快 8 小時。
  • 程式裡的時區不寫「+8」，而是寫名稱，例如 Asia/Taipei、America/New_York。這些名稱來自 IANA 時區資料庫：一份記錄全世界各時區規則的公開資料，由管理網際網路編號的組織 IANA 維護。

修法的方向因此很清楚：回答「這是哪一天」的時候，不要讓伺服器所在地決定，而是明確指定用台北的時區。下一節看怎麼指定。

怎麼指定用台北的時區算出日期？

getDate() 這一類方法沒有參數可以指定時區，只會用執行環境的。要指定時區，用 JavaScript 內建的 Intl。Intl 是國際化（internationalization）API，負責把同一份資料依不同地區的習慣顯示出來，第 5 課用過它的 NumberFormat 顯示金額。

這裡用的是 Intl.DateTimeFormat(地區, 選項)。地區決定顯示的語言和格式，'zh-TW' 是台灣中文；選項裡的 timeZone 決定用哪個時區換算。把開場那筆單交給三個時區：

同一個 Date，指定 Asia/Taipei 就得到 10 月 31 日，而且不管這段程式跑在哪台機器上，結果都一樣。這就是第一件事的最小答案：要回答「這是哪一天、幾點」，就把時區名稱明確傳給 Intl.DateTimeFormat。

不過日報表要的不是給人看的字串，而是年、月、日這些值，拿來分組、比較。format 的輸出會依地區變化（例如「凌晨12:30」），讓程式去切這種字串很容易壞。要拿值，改用 formatToParts：它把結果拆成一個陣列，每一段都有 type（year、month、day、hour、minute，分隔符號是 literal）和 value。

範例裡有兩個選項，都是為了讓拿到的值固定、好處理：

  • '2-digit'：月、日、時、分都補零，例如 9 月是 09。
  • hourCycle: 'h23'：小時用 0～23。小時有四種制度（h11、h12、h23、h24），h24 會把午夜寫成 24 點；不寫的話由地區決定。程式要拿數字來用時，一定寫清楚。範例刻意換成 16:00Z，台北剛好是午夜：有 h23 印出 00，不寫的話有些地區會印成 24 或 12。

把這段包成函式，輸入一個 UTC 時間和時區名稱、回傳那個時區的日期和時間，就是練習 1 的 toLocalParts。日報表用它算出每筆單的台北日期，凌晨 0:30 的單就回到 31 日了。

為什麼不自己加 8 小時就好？

看到「台北是 UTC+8」，很容易想到更省事的寫法：把毫秒數加上 8 小時，再用 getUTCDate() 這類只照 UTC 讀的方法取日期。台北這樣算剛好是對的，但這個想法只要換一個時區就會出錯，原因是夏令時間。

夏令時間（daylight saving time，DST）是有些地區夏天把時鐘撥快一小時的制度。紐約夏天是 UTC−4、冬天是 UTC−5（2026 年在 11 月 1 日切換）；台灣現在沒有夏令時間。下面用 timeZoneName: 'shortOffset' 讓格式器把偏移也印出來，比較紐約 10 月和 12 月的同一個時刻：

同一個城市，兩個月份的偏移差了一小時。如果寫一張「台北 +8、紐約 −4」的時差表自己加減，一到冬天紐約就差一小時；各國也會改夏令時間的規則，你的表不會跟著更新。IANA 時區資料庫記錄了每個時區歷年的規則，Intl 用的就是它。所以程式只傳時區名稱，換算交給 Intl。

💡 實務上：先問「這個時間要給誰看、用誰的時區」
前端畫面上的訂單時間，通常直接用使用者瀏覽器的時區就好，不必指定 timeZone。但只要是伺服器產生的東西：寄給客人的取餐通知信、半夜跑的日報表、推播「您的訂單 10:30 可取餐」，伺服器不知道看的人在哪裡，就一定要明確傳入時區，常見來源是門市設定或會員資料裡存的 IANA 名稱。另一個常見坑在「伺服器先產生畫面、瀏覽器再接手」的網站（Nuxt、Next.js 的伺服器端渲染）：伺服器在 UTC 算出「10 月 30 日」，台北的瀏覽器接手後算成「10 月 31 日」，兩邊對不上，畫面會閃一下，框架也會在 console 發出警告。資深工程師看到時間顯示的需求，會先確認「以誰的時區為準」，並把答案寫進規格。

日報表修好了，但只修了「讀」的這一端。訂單時間在系統裡還會被存進資料庫、經過 API 傳來傳去，每經過一站都有機會被換錯時區。下一節先定下存和傳的規則。

時間在資料庫和 API 之間，要怎麼存、怎麼傳？

時間在資料庫、JSON、網址參數裡都是字串。先認識它的標準寫法：ISO 8601 是表示日期時間的國際標準格式，例如 2026-10-30T16:30:00.000Z。前面是日期，T 分隔日期和時間，結尾的 Z 代表 UTC。結尾也可以寫偏移，例如 2026-10-31T00:30:00+08:00，意思是「UTC+8 的 0:30」，跟前一個是同一個瞬間。只要帶著 Z 或偏移，字串就精確指向一個瞬間，誰來讀都一樣。

有了這個格式，上一節的結論可以整理成後端處理時間的三條原則。它們是同一個想法：系統內部只流通瞬間，時區到最後一步才出現。

  • 存 UTC：資料庫用 timestamptz（PostgreSQL 課第 13 課），它存的就是瞬間。日後要換成哪個時區顯示都可以。
  • 傳 ISO：API 裡的時間用 Z 結尾（或帶偏移）的 ISO 字串，接收的一方不用猜時區。toISOString() 和 JSON.stringify 都輸出這種格式。
  • 顯示時才換時區：只有要給人看、或要回答「這是哪一天」時，才指定時區換算，就是上一節的做法。

反過來想就知道為什麼：如果資料庫存的是「台北的牆上時間」卻沒標時區，換到另一個時區的程式來讀，它無從得知這是哪一個瞬間。看一筆訂單經過 JSON 會變成什麼：

於是問題變成：拿到一個日期字串，new Date(字串) 能不能放心用？下一節會看到，答案取決於字串怎麼寫。

API 送來的日期字串，怎麼讀才不會差一天？

同樣是 ISO 格式，new Date(字串) 會依字串有沒有時間、有沒有時區，有三種解讀：

字串當成結果
'2026-10-31'（只有日期）UTC 的午夜在紐約是 10 月 30 日晚上 8 點
'2026-10-31T08:00:00'（有時間、沒時區）執行環境時區的 8 點台北和紐約的伺服器差 12 小時
'2026-10-31T08:00:00Z'、'…+08:00'寫明的時區到哪裡都是同一個時間

第二列的問題剛好相反：有時間、沒時區的字串，每台機器都用自己的時區解讀，同一個字串在台北和紐約的伺服器上變成相差 12 小時的兩個瞬間。只有第三列，寫明 Z 或偏移的字串，到哪裡都是同一個瞬間。所以 API 規格裡的時間欄位，要求一定帶 Z 或偏移。不是 ISO 格式的字串怎麼解讀，見課末。

只有日期的字串會被當成 UTC 午夜，這件事下一節的生日 bug 還會再遇到。先處理字串的另一個問題：格式對了，內容卻是假的。

格式對了，日期就一定存在嗎？

第 5 課說過「先檢查格式再轉換」。日期多了一層：格式對，日期不一定存在。'2026-02-30' 完全符合 YYYY-MM-DD，日曆上卻沒有這一天。看 new Date 怎麼處理幾個這樣的字串：

  • 超出範圍不會報錯，直接往後進位：2 月 31 日變成 3 月 3 日。

溢位讓錯誤的日期悄悄通過，反過來卻能拿來檢查：日期不存在就一定會溢位，溢位之後讀回來的年、月、日就跟原本的不一樣。這個做法叫往返檢查（round-trip check）：

  1. 用正規表示式確認格式剛好是 YYYY-MM-DD，拆出年、月、日三個數字。
  2. 用 Date.UTC(年, 月 − 1, 日) 組成時間。它回傳 epoch 毫秒，跟 new Date(年, 月, 日) 一樣會溢位，但一律用 UTC，不受執行環境時區影響。
  3. 用 getUTCFullYear()、getUTCMonth()、getUTCDate() 讀回來。日期不存在時已經溢位，讀回來的數字就跟原本的不一樣。

2 月 30 日讀回來是 3 月 2 日，跟原本對不上，就知道這一天不存在。這就是練習 2。

到這裡，訂單時間這種瞬間，從讀、存、傳到解析都處理好了。但開場的第二件事，生日早一天，用「存 UTC」反而修不好，因為生日根本不是一個瞬間。

生日優惠為什麼早一天寄出？

王小明的生日 5 月 20 日是日曆日期（calendar date）：只有「某年某月某日」，本身沒有時區。他的生日在台北和紐約都是 5 月 20 日，不是「台北 5 月 20 日 0 點的那一瞬間」。會員到期日、營業日也都是日曆日期。

出錯的程式用 new Date('1990-05-20') 把生日存成 Date。上一節的表格說過，只有日期的字串會被當成 UTC 的午夜，等於把生日釘在「UTC 5 月 20 日 0 點」這個瞬間。換到紐約看，那個瞬間還是 5 月 19 日晚上：

這不是時區沒指定好的問題。日曆日期一旦變成 Date，就得選某個時區的午夜當代表，而不管選哪一個，換到別的時區都可能差一天。修法是根本不讓它變成 Date：日曆日期在程式裡保持 'YYYY-MM-DD' 字串（或 { year, month, day }），資料庫用 date 型別，不要用 timestamptz。練習 2 的 parseDateOnly 做的就是這件事：讀進 'YYYY-MM-DD'，回傳 { year, month, day }，全程不讓 Date 決定日期。

日曆日期也需要計算，例如月費會員的到期日要「加一個月」。這時候還是得借 Date 來算，接下來兩個小節看怎麼借才安全。

月費會員 1 月 31 日加入，下個月幾號到期？

2 月沒有 31 日。直接加月份會溢位，跟上一節的 2 月 30 日是同一件事：

1 月 31 日加一個月變成 3 月 3 日，會員平白多了好幾天。常見的規則是夾到月底：新的月份沒有那一天，就用那個月的最後一天（1/31 → 2/28，閏年 2/29）。算法：

  1. 先算出目標的「年、月」：Date.UTC(年, 月 − 1 + n, 1)，用 1 號就不會溢位，月份超過 12 或是負數時 Date.UTC 會自動進位到別的年份。
  2. 算那個月有幾天：Date.UTC(年, 下個月, 0)，第 0 天就是上個月的最後一天。
  3. 日取 Math.min(原本的日, 那個月的天數)，再組回 'YYYY-MM-DD'（補零）。

第 2 步是借溢位的反方向：第 0 天往前退，剛好退到上個月的最後一天，那一天的日期就是上個月的天數：

💡 實務上：日期欄位從表單到資料庫都保持字串
後台的 <input type="date"> 給你的值本來就是 'YYYY-MM-DD' 字串，最常見的 bug 來自日期選擇器元件：它常給你本地午夜的 Date，送 API 前呼叫 toISOString()，台北的 5 月 20 日 00:00 就變成 UTC 的 5 月 19 日 16:00，生日存進去少一天。保持字串一路傳到 date 欄位，只有要做加減時才像上面那樣用 Date.UTC 計算。月費到期、試用期、優惠券「領取後 30 天內有效」這類規則，測試一定要包含 1/31、閏年 2/29、12/31 跨年這幾個日期。實際專案也可以用成熟的日期函式庫（例如 date-fns 的 addMonths 也是夾到月底），但「月底怎麼算」仍然要跟 PM 確認，函式庫只是幫你實作決定好的規則。

日報表和生日都修好了。剩下開場的第三件事：暱稱。

4 個 emoji 的暱稱，為什麼超過 10 個字？

暱稱驗證的程式寫的是 name.length <= 10。問題在 length 算的不是「字」。要知道它算的是什麼，得先知道 JavaScript 怎麼存字串。

電腦替每個字都編了一個號碼，全世界共用的那份對照表叫 Unicode，表裡的每個號碼叫 code point（字元碼），例如「拿」和「👍」各有一個。JavaScript 存字串時，再把每個 code point 編成一個或兩個 16 位元的單位，這種編法叫 UTF-16，每個單位叫 UTF-16 code unit。常用的中文字 1 個 code unit 就裝得下，emoji 的號碼比較大，常常要 2 個。length 算的是 code unit 的數量。

麻煩還不只這樣。有些 emoji 是好幾個 code point 組合起來的：'👍🏽' 是「讚」加上一個膚色，家庭 emoji 是爸爸、媽媽、女兒用看不見的連接字元黏起來。使用者眼中的「一個字」叫字素（grapheme）。三種算法放在一起比：

  • length：UTF-16 code unit 的數量。'👍' 是 2。
  • [...w]：展開字串是依 code point 切，'👍' 變成 1，但 '👍🏽'（讚＋膚色）是 2，家庭 emoji 是 5。
  • Intl.Segmenter 的 granularity: 'grapheme'：依 Unicode 規則切成字素，也就是使用者眼中的「一個字」。上面三個 emoji 都是 1。

回到陳美華：她用的是 4 個帶膚色的 '👍🏽'，每個是讚加膚色兩個 code point，各佔 2 個 code unit，所以一個的 length 是 4，4 個加起來 16，超過 10；用 Intl.Segmenter 數是 4。「暱稱最多 10 個字」說的是使用者看到的字，要用 Intl.Segmenter 切成字素再數。這是練習 4。

還有第三種長度別搞混：資料庫欄位、網路傳輸限制的是位元組，要用 TextEncoder、Buffer 算，在 Node 課第 11 課。驗證規則寫「幾個字」時，先問清楚說的是哪一種。

💡 實務上：前端的字數計數器和後端驗證要用同一套算法
暱稱、商品評論、訂單備註都有字數限制。常見的坑是前端顯示「還可以輸入 2 個字」，送出後後端用 length 算卻說超過，客服就會收到「明明沒超過」的回報；HTML 的 maxlength 也是依 length 算，不是看得到的字數。另一個坑是用 slice(0, 20) 截斷推播預覽或列表摘要，剛好切在 emoji 中間，畫面出現 � 這種亂碼符號。做法是把「怎麼算一個字」寫成一個共用函式，前後端都用它；截斷文字時也用 Intl.Segmenter 切，再取前幾段。

字數算對了，暱稱還有一關：不能跟別人重複。比對兩個暱稱是否相同，也有一個跟編碼有關的陷阱。

看起來一樣的暱稱，為什麼比較起來不相等？

「é」有兩種編碼：一個字元 é，或 e 加上一個組合用的重音符號 ́。從不同鍵盤、不同系統貼進來的文字可能是任一種，看起來一模一樣，=== 卻是 false：

第一行兩個字串看起來一樣，=== 是 false，length 也不同。Unicode 正規化（normalization）把它們轉成同一種形式，normalize() 預設用 NFC（盡量合成一個字元），轉完之後第二行就相等了。

所以比對帳號、搜尋商品名稱、檢查重複暱稱之前，先把兩邊 normalize()；更好的做法是寫進資料庫之前就統一正規化，資料庫裡只會有一種形式。練習 4 的測試把「e 加組合重音」算成一個字，也是這個原因：它在使用者眼中就是一個字。

三件事都修好了：訂單時間用 Intl 指定時區換算，生日保持日曆日期不經過 Date，暱稱用字素計數、比對前先正規化。下面的練習把這些修法各寫一次；後台列表要依中文排序時用的 Intl.Collator，放在課末。

練習

練習 1：寫 toLocalParts(iso, timeZone)：把 '2026-10-30T16:30:00Z' 這類 UTC 時間，換成指定時區的 { date: 'YYYY-MM-DD', time: 'HH:mm' }（24 小時制，午夜是 00:00）。iso 不是有效的時間時丟 RangeError。不管程式在哪個時區的機器上執行，結果都要一樣。

提示：用 Intl.DateTimeFormat 的 timeZone、hourCycle: 'h23' 和 formatToParts。

練習 2：寫 parseDateOnly(s)：會員生日、到期日這類「只有日期」的值，格式必須剛好是 YYYY-MM-DD（月、日都是兩位數）。回傳 { year, month, day }（month 從 1 開始）；格式不對、或日期不存在（'2026-02-29'、'2026-02-30'、'2026-04-31'、'2026-13-01'…）一律丟 RangeError。

提示：正規表示式加上括號可以用 exec 拿到每一組：/^(\d{4})-(\d{2})$/.exec('2026-10') 回傳 ['2026-10', '2026', '10']，不符合時回傳 null。

練習 3：寫 addMonths(date, n)：date 是 'YYYY-MM-DD' 的日曆日期（起始程式附了正確的 parseDateOnly），回傳加上 n 個月（可以是負數）之後的 'YYYY-MM-DD'。新的月份沒有那一天時夾到那個月的最後一天（1/31 加一個月是 2/28，閏年 2/29）。用 Date.UTC 與 getUTC* 計算；n 不是整數時丟 RangeError。

練習 4：寫 isValidNickname(name)：暱稱要是 1～10 個「看得到的字」（emoji、膚色組合、家庭 emoji 都算一個字），而且前後不能有空白。合法回傳 true，否則 false。

練習 5：伺服器的時區是紐約（2026 年 10 月是 UTC−4），執行 new Date('2026-10-31').getDate() 得到什麼？

✓ 只有日期的 ISO 字串被當成 UTC，getDate() 卻用執行環境的時區讀，所以差一天。不是「一律當本地時間」：有時間、沒時區的 '2026-10-31T00:00:00' 才當本地時間。日曆日期不要經過 Date，保持 'YYYY-MM-DD'。

練習 6：在 Chrome 或 Node 執行 new Date('2026-02-30T00:00:00Z')，會得到什麼？

✓ 不存在的日（2 月 30 日）會往後溢位，只有月份 13 這種才變成 Invalid Date；new Date 不會丟錯。所以 isNaN 擋不住，要自己做往返檢查：拆出年月日、用 Date.UTC 組回去、讀回來比對。

練習 7：會員生日 1990-05-20，程式用 new Date('1990-05-20') 存起來。紐約的伺服器用 getDate() 顯示，是幾號？該怎麼存？

✓ Date 只存瞬間（UTC 的 5 月 20 日 0 點），在紐約是 5 月 19 日晚上。生日沒有時區，不該變成任何時區的午夜；timestamptz 也是存瞬間，一樣會差一天。用 date 型別或 'YYYY-MM-DD' 字串。

常見錯誤

  • 伺服器上用 getHours()、不指定 timeZone 的 toLocaleString()：結果取決於伺服器在哪裡。要給人看的時間都明確傳時區。
  • 用 iso.slice(0, 10) 取「哪一天」：拿到的是 UTC 的日期，台北凌晨的單會算到前一天。用 Intl.DateTimeFormat 指定時區。
  • 寫死時差表：夏令時間讓紐約的時差在 −4 和 −5 之間變動，規則也會改。只傳時區名稱給 Intl。
  • 以為 new Date 會拒絕不存在的日期：2 月 30 日變成 3 月 2 日。用正規表示式加往返檢查。
  • 用 new Date(年, 月, 日) 時忘了月份從 0 開始：而且超出範圍會溢位，不會報錯；它還用執行環境的時區。計算改用 Date.UTC 加 getUTC*。
  • 把生日、到期日存成某個時區的午夜：換時區就差一天。保持 'YYYY-MM-DD'，資料庫用 date。
  • 直接改傳進來的 Date：setDate 會改到所有參考它的人。先 new Date(d.getTime()) 複製。
  • 直接 setMonth 加月份：1/31 加一個月變成 3/3。先算目標月份，再夾到月底，規則跟產品確認。
  • 用 length 限制字數：emoji 會被算成 2～8 個。用 Intl.Segmenter 算字素。
  • 直接比較使用者輸入的文字：同一個字可能有兩種編碼。比較前先 normalize()。

不是 ISO 格式的日期字串

Date.parse 的三種解讀規則只適用於 ISO 格式。不是 ISO 格式的字串（例如 '2026/10/31'）怎麼解讀由各家引擎決定，不要依賴。

Temporal 的支援現況

支援現況（MDN browser-compat-data）：Chrome 144、Firefox 139、Node.js 26.0.0 起支援，Safari 只在 Technology Preview。本課程後端用的 Node 24 還沒有（typeof Temporal 是 'undefined'），TypeScript 也要 6.0 起才有它的型別。

小結

  • Date 只存一個 epoch 毫秒（瞬間），而且是可變物件；「幾月幾號、幾點」是用某個時區臨時算出來的，getDate() 這類方法用的是執行環境的時區。
  • 要回答「這是哪一天」，把時區名稱傳給 Intl.DateTimeFormat，用 formatToParts、hourCycle: 'h23' 拿值。夏令時間讓時差不是固定值，不能自己加減。
  • 存 UTC、傳 ISO、顯示時才換時區；JSON.parse 不會把字串變回 Date。
  • 只有日期的字串當 UTC、有時間沒時區當本地時間，有 Z 或偏移才明確；不存在的日期會溢位，要用往返檢查擋。
  • 瞬間和日曆日期是兩種東西：生日、到期日保持 'YYYY-MM-DD'；加月份要決定月底規則，計算只用 Date.UTC 和 getUTC*。Temporal 把這些分成不同型別、不可變，Node 24 還沒有，後端目前用 Date＋Intl。
  • 字串的 length 是 UTF-16 code unit；看得到的字數用 Intl.Segmenter，比較前 normalize()，中文排序用 Intl.Collator。

練習 8：點餐頁同時開兩張訂單，各自用 useCart()，品項卻混在一起。問題出在哪裡？

const items = ref([])

export function useCart() {
  function add(product) { items.value.push(product) }
  return { items, add }
}

✓ 變數看函式在哪裡出生：items 在模組最外層，模組只執行一次，每個 add 的背包裡都是同一個變數。把 const items = ref([]) 移進 useCart 裡，每次呼叫才各有一份；在 Nuxt 伺服器上，同樣的寫法會讓不同使用者共用購物車。a 錯在 add 確實每次都是新的，但它們記住的是同一個 items。（第 1 課）

練習 9：每 5 秒要抓一次新訂單，第一次執行就丟出 TypeError。原因與修法是？

class OrderPoller {
  constructor(api) { this.api = api }
  poll() { return this.api.fetchOrders() }
}
const poller = new OrderPoller(api)
setInterval(poller.poll, 5000)

✓ this 看函式怎麼被呼叫：poller.poll 沒加括號，交出去的只是函式，之後由 setInterval 呼叫，this 是它給的值，不是 poller。用箭頭函式包一層、bind(poller)，或把 poll 寫成 class 欄位的箭頭函式。c 錯在 constructor 早就執行完了，問題不在時間點，而在呼叫方式。（第 1 課）

練習 10：這個函式算會員價並回傳新訂單。執行之後哪裡會出事？

function applyMemberPrice(order) {
  const copy = { ...order }
  copy.items.forEach(item => {
    item.price = Math.round(item.price * 85 / 100)
  })
  return copy
}

✓ { ...order } 是淺複製，只複製第一層；copy.items 和 order.items 是同一個陣列。改哪一層就展開到哪一層：items: order.items.map(item => ({ ...item, price: … }))。a 錯在展開只複製號碼牌，巢狀的陣列和物件照樣共用。（第 2 課）

練習 11：購物車是 Cart class，存進 localStorage 前先 JSON.stringify。重新整理後用 JSON.parse(saved) 讀回來，呼叫時出現 cart.addItem is not a function，為什麼？

✓ 經過 JSON 或 structuredClone，class 實例都會變回普通物件，原型是 Object.prototype。在資料進來的那一個地方用 static fromJSON 還原，或狀態只放純資料、計算寫成獨立函式。a 錯在函式本來就不會被 JSON 存下來，箭頭函式欄位一樣會丟掉。（第 3 課）

練習 12：createOrder 呼叫的資料庫查詢丟出錯誤。這一層沒辦法補救，只想讓 log 看得出是哪張訂單失敗，該怎麼寫？

✓ 只能補充脈絡就包一層、帶 cause、再丟：原始錯誤和它的 stack 都還在，到邊界（API handler）再統一轉成 500 並記 log。b 錯在只抄了 message，原始錯誤的種類與 stack 不見了；cause 要放錯誤物件本身。（第 4 課）

練習 13：會員打 85 折，客人在購物車看到應付 248 元，結帳實際扣了 247 元。前後端都用整數算、都用 Math.round，最可能的原因是？

✓ 拿鐵、卡布奇諾、可頌打 85 折，每行先捨入是 248、整張最後捨入是 247。捨入規則是規格，跟 PM、會計確認後全系統只用一種；金額以後端算的為準，前端只顯示後端回傳的結果。c 錯在分攤是把已經算好的折扣記到各行，不會改變應付總額，而且用最大餘數法加總不變。（第 5 課）

練習 14：訂單 id 是 PostgreSQL 的 bigint。API 為了讓前端好用，回傳前寫成 id: Number(row.id)。哪裡會出事？

✓ 超過 Number.MAX_SAFE_INTEGER 的整數存成 number 會變成相鄰的數，而且不報錯，等到點開訂單跑出別人的資料才發現。ID 在 API 規格裡就訂成字串，真的要運算才轉 BigInt。a 錯在 pg 把 bigint 回傳成字串，正是因為 number 裝不下。（第 5 課）

練習 15：台北的咖啡店，日報表跑在 UTC 時區的伺服器上，用 createdAt.toISOString().slice(0, 10) 決定訂單算哪一天。每天凌晨 0 點到 8 點的訂單都算到前一天，怎麼修？

✓ toISOString 一律輸出 UTC，切出來的是 UTC 的日期。存 UTC、傳 ISO、顯示時才換時區：要知道「台北的哪一天」，就把時區名稱傳給 Intl.DateTimeFormat，用 formatToParts 取年、月、日。a 錯在資料庫裡的瞬間被改錯了，所有用到它的地方都偏 8 小時。（第 6 課）
