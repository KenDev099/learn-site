階段 2：非同步、迭代與並發 · 第 9 課

async/await：依序、平行與錯誤

這一課要寫咖啡店的結帳流程。顧客按下「結帳」，伺服器要做三件事：查出每樣商品的價格算總額、向金流服務刷卡、寄出電子收據。每一件都要等別人回應：查價格等資料庫，刷卡等金流，寄信等郵件伺服器。後端程式大部分的時間都花在這種等待上，等的方式寫錯，就會出事：

  • 三樣商品一樣一樣查價，每次 100ms，結帳要 300ms；同時查，100ms 就好。
  • 改成同時查之後，總額卻算出 0 元。
  • 月底補寄 1000 張收據，一口氣全部送出，資料庫連線被用光，郵件服務開始拒絕。
  • 刷卡失敗，catch 卻沒接到；收據寄失敗，整台 Node 伺服器直接結束。

這課沿著結帳流程一步一步寫，每一節處理其中一個事故。學完你會知道每個 await 該怎麼排、失敗時錯誤會跑到哪裡，並且在 code review 時認得出這幾種 bug。

這課的路線：
  1. async 函式和 await 是什麼，await 的時候誰在等：只有一條執行緒，為什麼等刷卡時還能接下一位客人。
  2. 三樣商品查價：依序還是同時（開場問題的最小答案），以及改成同時之後總額變 0 的幾個經典 bug。
  3. 月底補寄 1000 張收據：為什麼不能全部同時、怎麼限制同時 N 個，失敗的那幾封怎麼找出來。
  4. 刷卡失敗：try／catch／finally 在 async 函式裡怎麼運作，為什麼 try 裡要寫 return await。
  5. 寄收據不拖慢結帳：故意不等的工作失敗了誰接，沒人接為什麼會讓 Node 程序結束。
這課會用到：
  • 第 8 課的 Promise：then 鏈一步接一步；Promise.all 等全部成功（一個失敗就整個失敗），Promise.allSettled 等全部定案，每一個的結果都拿得到。
  • 第 4 課的 try／catch／finally：catch 接住 try 裡丟出的錯誤，finally 不論成功或失敗都會執行。

結帳的每一步都要等：async/await 怎麼寫？

第 8 課用 then 串接非同步的步驟：每一步寫成一個 callback，等上一步的 Promise 定案才執行。步驟一多、後面又要用到前面好幾步的結果時，then 鏈就得一層包一層，或把中間結果存到外面的變數。async/await 是同一套 Promise 的另一種寫法，讓這種程式讀起來像同步程式一樣由上往下。

它由兩個關鍵字組成。在 function 前面加上 async，這個函式就是 async 函式，它有兩個特性：

  • 一定回傳 Promise。函式裡 return 值，Promise 就以這個值成功（fulfilled）；函式裡 throw，Promise 就失敗（rejected）。就算函式裡面沒有任何非同步的事，呼叫者拿到的也是 Promise，不是值。
  • 裡面可以用 await。await 某個 Promise 會等它定案：成功就拿到值，失敗就在這一行丟出錯誤，跟同步程式的 throw 一樣能用 try／catch 接住。

await 的時候，伺服器是不是整個停下來？

刷卡可能要等上一兩秒。如果 await 讓整個程式停住，這一兩秒裡其他客人的請求都進不來，伺服器一次只能服務一個人。實際上不會這樣：await 暫停的只是目前這個 async 函式。函式把後半段交給 Promise 之後就先讓出執行權；Promise 定案時，後半段被排成 microtask，等目前的程式跑完再繼續執行（第 7 課）。呼叫它的人拿到一個還沒完成的 Promise，可以馬上往下做自己的事。

這就是一間咖啡店只有一位咖啡師（一條執行緒，第 7 課的比喻）也能服務很多人的原因：王小明等咖啡的時候，咖啡師照樣幫陳美華點餐。要分清楚的是，JavaScript 可以同時「等」很多件事，但不是同時「算」很多件事。等待的時間交給資料庫、網路、計時器去跑；計算本身還是一件一件來，一段很久的同步計算照樣會卡住所有人（第 7 課）。

這一節的結論會一直用到：呼叫 async 函式時，工作就已經開始了；await 只決定「我現在要不要停下來等它」。既然可以先讓好幾件工作開始、之後再一起等，結帳查三樣商品的價格，就不必一件等完才開始下一件。

三樣商品的價格，要一個一個查嗎？

購物車裡有三樣商品，每查一個價格要 100ms。有好幾件非同步工作時，排法有三種：

  • 依序（sequential）：一件做完才開始下一件。寫法是在 for…of 迴圈裡 await，每一圈都停下來等，三件就是 100 + 100 + 100 = 300ms。
  • 全部同時（concurrent）：全部先開始，再一起等。寫法是 Promise.all(items.map(fn))：map 對每個 id 呼叫一次 getPrice，三個查詢在這一刻就都送出去了，map 回傳三個 Promise；Promise.all 再等三個都成功，結果陣列的順序跟輸入的順序一樣。三件一起等，總時間約等於最慢的那一件，100ms。
  • 限制同時 N 個：同時進行的工作最多 N 個，這個數字叫併發上限（concurrency limit）。數量很大時才需要，下下節的 1000 張收據會用到。

那是不是所有 await 都該改成同時？不是。依序有它必要的時候：

  • 後一步需要前一步的結果：上一節「先查顧客，才能查他的上一筆訂單」，第二個查詢的參數來自第一個的結果，沒辦法同時開始。
  • 順序本身有意義：例如照下單順序扣庫存，先下單的人要先扣到。

三個商品的價格互不相依，誰先查到都不影響別人，所以用 Promise.all。這就是開場第一個事故的答案：互不相依的工作，先全部開始，再一起等。

💡 實務上：先找「其實互不相依」的依序 await
最常見的效能問題不是演算法，而是一串本來可以同時的 await。例如咖啡店會員頁：載入時依序查會員資料、點數、最近訂單，三個請求互不相依，排成一列就是三段等待相加。前端打開 DevTools 的 Network 面板，看到請求一個接一個排成階梯狀（常叫 request waterfall），就是這個訊號；後端則是一支 API 裡連續好幾個彼此無關的查詢。資深工程師 review 時會問：「這幾個 await 之間真的有相依嗎？」沒有就包進 Promise.all；有相依（要先拿到顧客 id 才能查訂單）就維持依序，不要為了快而硬改。

改成同時查價之後，總額為什麼變成 0？

知道查價要同時之後，最常見的第一版是用 forEach 對每樣商品查價、累加到 total。這一節有四個 bug，其中三個出在同一件事：上一節說過，呼叫 async 函式拿到的是 Promise，工作已經開始，但只要沒有人等這個 Promise，程式就會直接往下走。另一個是同時進行的工作互相蓋掉結果。

1. forEach(async …) 不會等。forEach 對每個元素呼叫你的函式，但完全不理會函式回傳什麼。你的 async 函式跑到第一個 await 就暫停、回傳一個 Promise，forEach 把這個 Promise 丟掉，接著處理下一個元素。所以 forEach 結束時，裡面的 await 一個都還沒完成。執行後看印出來的 total：

2. map(async …) 得到的是 Promise 陣列。改用 map 時，回傳值被收集起來了，但 async 函式回傳的是 Promise，所以結果是一排 Promise，不是價格。要用 Promise.all 等它們變成值。執行後比較兩行：

3. 同時進行的工作一起改同一個變數。就算用 Promise.all 等全部完成，在每個工作裡寫 total += await getPrice(id) 還是錯的。total += x 等於 total = total + x，JavaScript 由左往右算，先讀出 total，才執行右邊的 await，等價格回來再把「當初讀到的 total 加上價格」寫回去。拿鐵（110）和可頌（70）同時查價：

月底補寄 1000 張收據，也能全部同時送出嗎？

月底發現有 1000 張收據沒寄出去，要補寄。照上一節的寫法 Promise.all(orders.map(sendReceipt))，1000 個寄信工作會在同一刻全部開始。商品查價只有三個，同一刻多三個請求沒有影響；1000 個就不一樣了，會撞上三種上限：

  • 資料庫連線池有上限。每次跟資料庫建立連線都要花時間，所以伺服器會把建立好的連線留著重複使用，並規定最多同時開幾條，這組連線叫連線池（connection pool）。PostgreSQL 課第 25 課的 max: 10 表示最多 10 條連線。1000 個查詢同時送出，990 個在池子裡排隊，網站上其他使用者的請求也要排在它們後面，等太久就逾時了。
  • 第三方 API 通常有限流。郵件服務、金流這類別人的服務，會規定一段時間內最多能呼叫幾次，這叫限流（rate limit）。超過就回 429 錯誤，你的請求被拒絕。
  • 每個進行中的請求都佔記憶體。請求內容、等待中的連線、還沒處理的回應，在完成前都留在記憶體裡。

所以數量大或數量不固定時，要用第三種排法：限制同時 N 個。N 讓你自己決定給對方多大的壓力。

分批：直覺的寫法，但會等最慢的那個

工作池：誰有空誰就拿下一件

工作池（worker pool）的做法不一樣：開 N 個「工人」，每個工人做完一件，就立刻從同一個佇列拿下一件，直到沒有工作。同樣的六張收據，一個工人寄那張 400ms 的，另一個工人一路接著寄完其他五張（5 × 50 = 250ms），總時間就是最慢那張的 400ms：

工人之間要怎麼分工，才不會兩個人寄同一張？它們共用一個「下一件是第幾個」的索引 next，每個工人用 const i = next++ 拿到自己的編號再開始寄。這一行在多個工人之間是安全的，原因是第一節「await 的時候，伺服器是不是整個停下來？」講過的：JavaScript 一次只有一段程式在執行，工人只會在 await 的地方讓出執行權。讀出 next 和把它加一之間沒有 await，別的工人就插不進來，所以不會有兩個工人拿到同一件。練習 2 會讓你自己寫出工作池。

還有一點要分清楚：限制同時 N 個，限制的是「同一刻有幾個在進行」；第三方的限流通常算的是「每秒幾次」。每個請求很快時，同時 2 個每秒也可能打出幾十次。對方規定每秒次數時，還要另外控制送出的速度。

1000 封裡有 3 封失敗，怎麼知道是哪 3 封？

寄得出去之後，下一個問題是寄失敗的那幾封。Promise.all 的規則是：只要有一個失敗，它就立刻失敗，catch 只拿到最先失敗的那一個錯誤；其他工作也不會因此停下來，照樣繼續跑（第 8 課）。對補寄收據來說，這等於只知道「有東西失敗了」，不知道哪幾封寄出去、哪幾封沒有。

需要每一個的結果時，改用 Promise.allSettled：它等全部定案，回傳每一個的狀態，成功的是 { status: 'fulfilled', value }，失敗的是 { status: 'rejected', reason }。下面三封信，陳美華和林志豪的會失敗。執行後比較兩行：all 只拿到最早失敗的陳美華（10ms），allSettled 兩封失敗都拿得到：

💡 實務上：批次工作先問「對方承受得了多少」
後台「匯入商品 CSV」、「月底補寄收據」、「同步訂單到會計系統」都是這種數量大的工作。N 不是越大越好：要留連線給線上正在點餐的客人，也要符合第三方 API 文件寫的限流規定，先查文件、再小量試跑，觀察錯誤率後再調。實際專案通常直接用 p-limit 這類「限制同時幾個」的套件，而不是自己維護工作池。工作量大到要跑好幾分鐘時，也別塞在一個 HTTP 請求裡等，改成背景工作：不綁在請求上、在伺服器另外慢慢跑的程式，前端顯示進度即可。
💡 實務上：批次結果要讓人看得懂、補得回來
批次補寄 1000 封收據，有 3 封因為信箱打錯而失敗，用 Promise.all 只會得到一個錯誤，你不知道其他 999 封寄出去沒有。用 allSettled 整理成「成功 997、失敗 3，失敗的是哪幾筆、原因是什麼」，後台就能顯示給店長，並提供「重寄失敗的」按鈕。反過來，結帳頁要同時載入購物車、運費、可用優惠，少一個就沒辦法結帳，這種「缺一不可」的情況就用 Promise.all，一失敗就直接顯示錯誤。選哪個，先問 PM：部分成功對使用者有沒有意義？

刷卡失敗，catch 為什麼沒接到？

批次工作的失敗處理好了，回到結帳本身。總額算出來之後要刷卡：付款期間把收銀機標成「使用中」（register.busy = true），付款結束不論成功失敗都要設回可用，失敗時還要包成「付款失敗」的錯誤往上丟。

這正是 try／catch／finally 的用途。await 失敗會在那一行丟出錯誤，所以 try／catch 跟同步程式一樣能用；finally 不論成功或失敗都會執行，適合放收尾的事：把收銀機設回可用、把前端的 loading 關掉、把資料庫連線還回連線池。

問題出在一個很常見、又很難看出來的寫法：在 try 裡直接 return chargeCard()，沒有 await。看起來刷卡在 try 裡面，失敗應該會被 catch 接住，實際上不會：

  1. return chargeCard() 拿到一個還沒定案的 Promise，函式立刻帶著它離開 try。這時候沒有任何錯誤丟出來，catch 不會執行。
  2. 離開 try 時 finally 馬上執行，收銀機在刷卡還沒結束時就被設回可用。
  3. 之後刷卡失敗，這個 Promise 被 reject，錯誤直接交給呼叫者。函式早就離開 try 了，catch 沒有機會接。

加上 await 就不一樣：return await chargeCard() 會停在 try 裡等刷卡定案，失敗時錯誤在這一行丟出，catch 接得到，finally 也在刷卡結束後才執行。下面兩個函式只差一個 await。執行後比較兩組輸出：各自的 catch 有沒有印、finally 在付款結束前還是後：

規則：在 try 裡面一律寫 return await。不在 try 裡時，return p 和 return await p 拿到的值和錯誤一樣，但 stack trace 不一樣，下面接著看。練習 3 的 placeOrder 就是收銀機這個 bug。

出錯時，log 看得出是哪個流程嗎？

return await 還有另一個好處：錯誤的 stack trace 比較完整。stack trace 是錯誤物件上的 stack，記錄錯誤發生時是哪些函式一層一層呼叫到這裡，線上出錯時主要靠它找原因。

同步程式的呼叫關係一直留在呼叫堆疊上，非同步程式不是：函式在 await 暫停時已經讓出執行權，原本的呼叫堆疊早就清空了。Chrome 和 Node 共用的 JavaScript 引擎叫 V8，它的做法是在 await 的地方記下「是誰在等這個 Promise」，錯誤的 stack 就會多出「at async 呼叫者」這幾行，這叫非同步 stack trace（async stack trace）。直接 return Promise 或用 then 串接時，這一層函式沒有在等，就從 stack 裡消失了。

第一種看得到 chargeCard → payAwait → checkoutA，第二種只剩 chargeCard（測試過的版本見課末）。換成線上的情況：log 裡只有「卡片被拒、在 chargeCard」，你不知道是結帳、補扣款還是哪個流程呼叫的。讀 stack trace 的方法在 Node 課第 6 課。

所以 async 函式要回傳另一個 async 呼叫的結果時，一律寫 return await：在 try 裡是為了正確性，在 try 外是為了查錯。

刷卡的錯誤現在接得住、查得到了。結帳流程只剩最後一步：寄收據。

寄收據不想拖慢結帳，失敗了誰接？

刷卡成功後要寄電子收據。顧客在等結帳畫面，不該連寄信的時間一起等，所以寄收據不 await：呼叫之後直接回傳結帳結果。這種故意不等結果的工作叫射後不理（fire-and-forget）。

問題是寄信失敗時，這個 Promise 被 reject，卻沒有任何人 await 或 catch 它。一個失敗了、但從頭到尾沒有人處理的 Promise，叫未處理的 rejection（unhandled rejection）。執行後看 console：「結帳完成」先印出來，20ms 後出現一個沒人接的錯誤：

這個錯誤的後果，在瀏覽器和 Node 差很多：

  • 瀏覽器：觸發 unhandledrejection 事件，在 console 印出 Uncaught (in promise)，頁面繼續執行。練習區也一樣。
  • Node：預設把 unhandled rejection 當成未捕捉的例外。沒有註冊 unhandledRejection 監聽器時，整個程序直接結束，所有正在處理的請求一起中斷（Node 文件；預設值與版本見課末）。一張收據寄失敗，同一刻其他正在結帳的客人全部失敗。伺服器上的整體策略在 Node 課第 18 課。

正確的射後不理是「不等，但處理失敗」。.catch 會回傳一個新的 Promise，原本的 rejection 被它接住，就不再是 unhandled：

sendReceipt(order).catch(err => log.error(err))   // 不 await，但失敗會被記下來

沒有 await、沒有 catch、也沒有 return 出去的 Promise 叫 floating promise，也就是這裡的 sendReceipt()。靠眼睛找很容易漏，要交給 lint 規則。lint 是在執行前分析程式碼、抓出可疑寫法的工具，每一條檢查叫一條規則。抓 floating promise 的規則叫 no-floating-promises，typescript-eslint 和 oxlint 都有。它要讀型別資訊才知道哪個呼叫回傳 Promise，所以要額外開啟讀型別的模式，設定方式見課末。

規則預設允許在前面寫 void sendReceipt()，表示「我是故意不等的」。typescript-eslint 文件寫得很清楚：void 不會處理 rejection，也不改變執行時的行為，失敗照樣是 unhandled rejection。它只是讓規則閉嘴。射後不理一定要 .catch。

練習 4 會把整個結帳流程寫完：等刷卡、不等收據、收據失敗要記下來。

💡 實務上：射後不理之前，先問「失敗了誰會知道」
寄通知信、送推播、記錄分析事件，是最常見的射後不理場景，因為它們不該拖慢主流程。.catch(log.error) 只保證程序不會掛、錯誤有留紀錄；它不會重試，伺服器重新部署時，進行中的工作也會直接消失。所以要分清楚：分析事件掉幾筆可以接受，但「收據一定要寄到」這種需求，就不適合射後不理，應該先把「待寄的收據」寫進資料庫或工作佇列（記錄待辦工作的地方），由背景工作負責寄送和重試。資深工程師 review 時看到沒有 await 的呼叫，會問兩件事：失敗有沒有被處理？這件事能不能接受偶爾遺失？

補充與查表

主線用不到、但在 Node 專案裡設定或查問題時會遇到的細節。

頂層 await 能用在哪

頂層 await 只能用在 ES module：

  • 可以用：練習區（它是 module，第 1 課提過）、Node 的 .mjs 或 "type": "module" 專案。
  • 語法錯誤：CommonJS 檔案（.cjs 或 "type": "commonjs"）。
  • 沒寫 type 的 .js：Node 24 實測會印出警告、改當 ES module 重新解析。所以專案還是明確寫上 "type": "module"。

Node 的 unhandled rejection 預設值

Node 用 --unhandled-rejections 決定怎麼處理 unhandled rejection，預設模式是 throw（v15.0.0 起）：沒有註冊 unhandledRejection 監聽器時，rejection 會被當成未捕捉的例外，程序結束（Node 文件）。

no-floating-promises 的設定

  • typescript-eslint 的 no-floating-promises（8.72.1）：await、return、.catch(…)、兩個參數的 .then(…) 才算處理。它要讀型別資訊，所以要開 typed linting，包含在 recommended-type-checked 設定裡。
  • oxlint（NestJS 12 官方 starter 用的 lint 工具）的 typescript/no-floating-promises：要加 --type-aware 並安裝 oxlint-tsgolint。

非同步 stack trace 的測試版本

本機實測 Node 24.22.1 與 Chrome 156 結果相同：return await 的版本看得到 chargeCard → payAwait → checkoutA，直接 return 的版本只剩 chargeCard。

練習

練習 1：calcTotal(items, getPrice) 要回傳訂單總額（每個品項是 { productId, quantity }，getPrice(productId) 回傳 Promise），現在永遠回傳 0。修好它：可以同時查價格；空陣列回傳 0；getPrice 失敗時，calcTotal 要以同一個錯誤失敗，不能變成 unhandled rejection。

練習 2：寫 mapWithLimit(items, limit, fn)：對每個 item 呼叫 fn(item)（回傳 Promise），同時最多 limit 個在進行，有空位就立刻開始下一個（工作池，不是分批）。回傳的結果陣列依輸入順序排列；空陣列回傳 []；任何一個失敗就以那個錯誤失敗（進行中的不需要取消）。

練習 3：placeOrder(order, pay, register) 付款期間要把 register.busy 設成 true，結束後（成功或失敗）設回 false；付款失敗時丟出 new Error('付款失敗', { cause: 原本的錯誤 })（第 4 課：cause 記下是哪個原本的錯誤造成的）；成功時回傳 pay 的結果。現在的版本失敗時 catch 接不到，busy 也太早變回 false。修好它。

練習 4：寫 checkout(order, { charge, sendReceipt, log })：一定要等 charge(order) 完成，回傳它的結果；接著呼叫 sendReceipt(order) 寄收據，但不要等它（不能拖慢結帳）；寄收據失敗時要呼叫 log.error(錯誤)，不能變成 unhandled rejection。charge 失敗時 checkout 以同一個錯誤失敗，而且不寄收據。

練習 5：async function f() { return 1 }，接著 console.log(f()) 印出什麼？

✓ async 函式一定回傳 Promise，就算裡面直接 return 普通的值，也會被包成以這個值成功的 Promise。要拿到 1，得 await f() 或 f().then(…)。不會是 undefined：函式有回傳東西，只是回傳的是 Promise。

練習 6：checkStock 是 async 函式，回傳 true 或 false。if (checkStock(id)) { 出貨() } 什麼時候會出貨？

✓ 沒有 await 時，if 判斷的是 Promise 物件本身。任何物件都是 truthy，所以條件永遠成立，缺貨也會出貨。if 不會等 Promise，所以 a 不對；b 把 Promise 當成 falsy，也不對。這種 bug 用 lint 規則 no-misused-promises（typescript-eslint、oxlint 都有）可以抓出來。

練習 7：Node 24 的伺服器裡，一個射後不理的 sendReceipt() 失敗了，程式沒有任何 catch，也沒有註冊 unhandledRejection 監聽器。預設會怎樣？

✓ Node 從 v15.0.0 起，--unhandled-rejections 的預設模式是 throw：沒有監聽器時，unhandled rejection 等同未捕捉的例外，程序結束，正在處理的所有請求一起中斷。「只印警告」是 Node 14 以前的行為。正確做法是 sendReceipt().catch(err => log.error(err))。

常見錯誤

  • 互不相依的請求寫成依序 await：總時間變成相加。先開始、再一起等。
  • forEach(async …)：forEach 不等回傳的 Promise。依序就用 for…of 加 await，同時就用 Promise.all(items.map(…))。
  • map(async …) 之後忘了 Promise.all：拿到的是 Promise 陣列，拿去加總會變成字串串接。
  • 同時進行的工作一起改同一個變數：total += await … 先讀後寫，結果會被蓋掉。每個工作回傳自己的值，最後再加總。
  • 忘了 await：if (checkStock(id)) 永遠成立；拿到的值是 Promise 而不是資料。開 no-floating-promises 與 no-misused-promises 讓 lint 幫你抓。
  • 大量工作全部同時開始：打爆資料庫連線池、被第三方 API 限流。數量大或不固定時，用工作池限制同時 N 個。
  • 在 try 裡 return 沒有 await 的 Promise：catch 接不到、finally 提早執行、stack trace 少一層。寫 return await。
  • 射後不理卻沒有 catch：瀏覽器印 Uncaught (in promise)，Node 預設讓程序結束。加上 .catch(err => log.error(err))。
  • 用 void 讓 lint 閉嘴，以為錯誤被處理了：void 只是忽略結果，rejection 依然沒人處理。

小結

  • async 函式一定回傳 Promise：return 值是成功、throw 是失敗。await 只暫停目前這個函式，呼叫者照樣往下跑；呼叫時工作就開始了，await 只決定要不要停下來等。
  • 查價這種互不相依、數量小的工作用 Promise.all 同時進行；後一步需要前一步的結果才依序。
  • 同時之後的經典 bug 都是「沒有人等這個 Promise」：forEach(async …)、map 後忘了 Promise.all、忘了 await；同時進行的工作不要一起改同一個變數。
  • 補寄 1000 張收據這種數量大的工作，用工作池限制同時 N 個。工作池比分批快，因為不用等每一批最慢的那個。Promise.all 只給第一個錯誤，要每一個的結果用 allSettled。
  • 刷卡這類在 try 裡的呼叫寫 return await：catch 接得到、finally 時機正確、stack trace 保留呼叫者。
  • 寄收據這種射後不理的工作也要 .catch；用 no-floating-promises 自動抓沒人處理的 Promise，void 不算處理。
