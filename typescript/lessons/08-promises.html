階段 2：非同步、迭代與並發 · 第 8 課

Promise：未來才會有的值

你接手咖啡店的下單流程。一張訂單進來，程式要依序做三件事：查庫存、扣款、印收據。這三件事的答案都不在程式手上：庫存在資料庫裡，扣款要問金流服務，收據要等收據服務回應。快的話幾毫秒，慢的話好幾秒。

在前端，你多半寫一行 await fetch(…) 就過去了，不太需要想背後發生什麼。到了後端，這段程式寫錯的代價很具體：沒等扣款完成就印收據，客人拿到收據、錢卻沒扣到；扣款失敗的錯誤沒有人接，客服接到客訴時查不到任何紀錄。第 7 課講過，JavaScript 只有一條執行緒，程式不能停下來乾等。這課要回答的就是：結果還沒來的時候，函式要回傳什麼？拿到之後，怎麼讓三步依序執行，而且任何一步失敗都有人負責？JavaScript 的答案是 Promise。下一課的 async/await 只是 Promise 的另一種寫法，這課的規則全部照用。

這課的路線：
  1. 結果還沒來，函式要回傳什麼：Promise 的三種狀態、只定案一次，怎麼用 then／catch 拿到結果（開場問題的最小答案）。
  2. 要等的東西不回傳 Promise 怎麼辦：用 new Promise 把計時器和舊式 callback 的咖啡機包成 Promise。
  3. 查庫存 → 扣款 → 印收據怎麼一步接一步，其中一步失敗時錯誤會跑到哪裡：then 鏈、catch 的位置、finally。
  4. 互不相關的工作為什麼不用排隊：同時等很多個時，all、allSettled、race、any 各在什麼時候成功或失敗。
  5. 結果由店員按按鈕決定時，怎麼把 resolve 拿到外面：withResolvers。
這課會用到：
  • 第 7 課的 microtask：同步程式全部跑完之後，才輪到 microtask 佇列裡的 callback；then 的 callback 就排在這裡。
  • 第 4 課的 throw 與 try／catch：throw 之後，錯誤往外找最近的 catch；要丟 Error 物件而不是字串，才有 stack trace。
  • 第 1 課的 callback：交給別人、由別人之後才呼叫的函式。

結果還沒來，函式要回傳什麼？

先看下單的第一步 checkStock(order)。它要問資料庫「拿鐵還有沒有」，資料庫可能 5 毫秒後才回答。這個函式只有兩條路可走，兩條都不行：

  • 等資料庫回答才 return：等待的這段時間，唯一的那條執行緒被佔住，伺服器上其他客人的請求全部停住（第 7 課「被卡住的 event loop」）。
  • 不等，馬上 return：可是答案還沒來，沒有東西可以回傳。

所以需要第三種做法：馬上回傳一個「代表之後的結果」的東西，讓呼叫的人先拿著，等結果來了再處理。這就是 Promise。

咖啡店裡有現成的例子。點完餐，店員不會讓你站在櫃檯前等，而是給你一張號碼牌。號碼牌現在換不到咖啡，但它代表「之後會有一杯咖啡，或是一個壞消息」。你拿著它可以先去找位子，店員也可以繼續招呼下一位客人。Promise 就是這張號碼牌：一個物件，代表一個之後才會有的結果。

號碼牌在不同時間點有不同的狀態，Promise 也一樣，一共三種：

  • pending（等待中）：剛拿到號碼牌，還沒叫號。Promise 剛建立時都是這個狀態。
  • fulfilled（成功）：叫號了，拿到咖啡。成功時 Promise 帶著一個值（value），例如查到的庫存數量。
  • rejected（失敗）：店員說賣完了。失敗時 Promise 帶著一個原因（reason），通常是一個 Error 物件。

成功和失敗這兩種結局有一個統稱，叫做定案（settled）。這課會常說「等 Promise 定案」，意思是等它變成成功或失敗，不管是哪一種。

Promise 有一條很重要的規則：只會定案一次。一張號碼牌叫到號、拿到咖啡之後，不會再變成「賣完了」；反過來也一樣。這條規則讓拿到結果的人可以放心：扣款的結果一旦確定是成功，就不會在之後某個時間點被改寫成失敗。

拿到號碼牌之後，怎麼在叫號時做事？Promise 不讓你直接讀出結果（結果可能還沒來），而是讓你登記「結果來了要做什麼」：用 then 登記成功時要執行的 callback，callback 會收到成功的值；用 catch 登記失敗時要執行的 callback，callback 會收到失敗的原因。

登記的 callback 什麼時候執行？規則是：一定是之後才執行，就算 Promise 在登記的當下早就定案了也一樣。Promise 定案後，登記的 callback 會被排進第 7 課的 microtask 佇列，等目前的同步程式全部跑完才輪到它。這個規則讓程式的行為一致：寫 then 的人不必去管「這個 Promise 現在是不是已經有結果」，callback 執行的時機永遠是同一種。

到這裡，開場問題有了最小版本的答案：會花時間的函式，馬上回傳一個 Promise；呼叫的人用 then 登記成功時要做的事、用 catch 登記失敗時要做的事。checkStock、charge、printReceipt 都應該長這樣。

可是這一節的 Promise 是 Promise.resolve 現成做出來的，一開始就有結果。咖啡店真正要等的東西，例如「過 100 毫秒」的計時器、只接受 callback 的舊式咖啡機 API，本身都不回傳 Promise。下一節自己做一個 Promise，把它們包起來。

要等的東西不回傳 Promise 時，怎麼自己做一個？

自己做 Promise 用 new Promise(…)。括號裡要傳一個函式，這個函式叫做 executor，它的工作是「啟動要等的那件事，並在結果出來時通知 Promise」。怎麼通知？new Promise 呼叫 executor 時，會傳兩個函式給它：

  • resolve：呼叫 resolve(值)，Promise 就用這個值成功。
  • reject：呼叫 reject(錯誤)，Promise 就用這個錯誤失敗。

換句話說，Promise 本身不知道什麼時候算完成，是你在 executor 裡決定「什麼時候、用什麼結果」呼叫 resolve 或 reject。

最常見的第一個例子是 sleep(ms)：回傳一個 Promise，ms 毫秒後才成功。要等的那件事是計時器，所以 executor 裡設一個計時器，時間到了由計時器呼叫 resolve。執行後看三行輸出的順序，以及最後印出的經過時間：

「executor 立刻執行」印在最前面，比 new Promise 回傳之後的那行還早。這代表 executor 是同步執行的：new Promise 一被呼叫，就立刻把 executor 從頭跑到尾，跑完才回傳 Promise。真正「之後」才發生的只有計時器：它在 100 毫秒後呼叫 resolve，Promise 這時才成功，then 的 callback 才執行。

這個事實有一個實際的後果：把很重的同步計算放進 executor，例如在 executor 裡跑一個算一萬筆訂單報表的迴圈，一樣會卡住整個程式。包成 Promise 不會讓它變成在背景執行，因為 executor 就是在這條唯一的執行緒上同步跑的（第 7 課）。Promise 只是「結果的容器」，等待本身要靠計時器、網路這類宿主環境提供的功能。

resolve 呼叫兩次會怎樣？

前面號碼牌的比喻說過，Promise 只會定案一次。落到程式上就是：resolve 或 reject 第一次被呼叫時，Promise 就定案了，之後再呼叫都沒有作用，也不會報錯。執行後看 Promise 的結果是哪一個，以及最後那行 console.log 有沒有印出來：

也注意最後一行照樣印出來了。resolve 只是把 Promise 定案，不是 return，函式會繼續往下跑。要在 resolve 之後停下來，自己寫 return。

  1. resolve('拿鐵') 後面有括號，代表現在就呼叫它，Promise 立刻成功。
  2. 交給 setTimeout 的是這次呼叫的回傳值 undefined，不是函式。setTimeout 要的是「之後要呼叫的函式」，它拿到的卻是一個已經算好的結果。
  3. 練習區和 Node 的 setTimeout 收到 undefined 會丟出 TypeError。這個錯誤發生在 executor 裡、Promise 已經定案之後，所以被吞掉了，畫面上什麼都看不到。

正確的寫法是交出一個函式，讓計時器之後再呼叫：setTimeout(() => resolve('拿鐵'), 100)，或用 setTimeout 的第三個參數，計時器到時會把它當成參數傳給 resolve：setTimeout(resolve, 100, '拿鐵')。

第 3 步提到「executor 裡的錯誤」，這裡把規則講完整。executor 裡同步丟出的錯誤，會讓 Promise 變成 rejected（前提是它還沒定案）。但如果 executor 只是排了一個計時器，錯誤是在計時器的 callback 裡丟出的，那時 executor 早就跑完了，Promise 接不到這個錯誤，它會變成一個沒有人接的錯誤，而 Promise 永遠停在 pending。所以在計時器、舊式 API 這類非同步 callback 裡要表示失敗，一律呼叫 reject，不要 throw。

舊式 callback 的咖啡機 API 怎麼包？

Promise 出現之前，非同步函式用 callback 回報結果：呼叫時多傳一個函式進去，事情做完時，它會呼叫這個函式。Node 有一個固定的慣例，叫做 error-first callback：

  • callback 是最後一個參數。
  • callback 的第一個參數是錯誤：成功時是 null，失敗時是 Error 物件；成功的結果放在第二個參數。

咖啡店的咖啡機 SDK 就是這種舊寫法：brewCoffee(order, (err, cup) => …)。錯誤放第一個，是為了逼呼叫的人先檢查錯誤再用結果。很多還在用的舊套件仍然是這樣寫，而下單流程的其他步驟都回傳 Promise，咖啡機不一致，就沒辦法跟它們串在一起。

解法是寫一個包裝函式：在 executor 裡呼叫舊 API，把它的 callback 接到 resolve 和 reject。err 有值就 reject，沒有就用結果 resolve。這個「把 callback 風格的函式變成回傳 Promise 的函式」的動作，叫做 promisify。執行後看兩個呼叫各走到哪一條路：

失敗時 reject 的是咖啡機給的同一個 Error 物件，不是新建一個。原本的錯誤帶著發生地點的 stack trace，換成新的就丟掉了查錯最需要的線索。練習 2 會寫一個通用的 promisify，任何 error-first 的函式都能包。Node 其實內建了這個工具，細節見課末「補充與查表」。

💡 實務上：自己寫 new Promise 的機會不多，通常只在「包裝」的時候
日常工作多半是在用 Promise：fetch、axios、ORM 的查詢都已經回傳 Promise。會自己寫 new Promise 的，通常是把 callback 或事件風格的 API 包起來，例如等圖片的 onload／onerror、讀取使用者上傳的檔案（FileReader）、還沒支援 Promise 的舊 SDK，就像這裡的咖啡機。包的時候要確認成功和失敗兩條路都有接到，只接 onload 忘了 onerror，圖片壞掉時這個 Promise 就永遠 pending。另一個 code review 常見的寫法是 new Promise(resolve => fetch(url).then(resolve))：本來就是 Promise 還再包一層，失敗也沒有 reject 出去，直接 return fetch(url) 就好。

現在下單的每一步都能回傳 Promise 了。下一個問題是把它們串起來：扣款要等查庫存完成才能開始，印收據要用到扣款的結果。

查庫存 → 扣款 → 印收據：怎麼一步接一步？

下單的三步有先後關係：查庫存成功才扣款，扣款成功才印收據，而且印收據要拿扣款的結果（付款編號、金額）。第一節學到用 then 登記「成功之後做什麼」，直覺的寫法是在 then 裡呼叫下一步。問題是：下一步本身也要等，它的結果要怎麼交給再下一步？

答案藏在 then 的回傳值裡：每次呼叫 then，都會回傳一個新的 Promise。這個新的 Promise 代表「then 的 callback 執行完之後的結果」。因為它也是 Promise，可以再對它呼叫 then，一直接下去。這樣一個接一個的 then，叫做 Promise 鏈（promise chain）。

新的 Promise 什麼時候定案、帶什麼結果，由 then 的 callback 決定。這張表是整條鏈能運作的關鍵：

then 的 callback 裡then 回傳的新 Promise
return 值用這個值成功，下一個 then 收到它
return 另一個 Promise等那個 Promise 定案，跟它同一個結果
沒有 return用 undefined 成功，而且不會等裡面的非同步工作
throw 錯誤用這個錯誤失敗

第二列最重要：callback 回傳 charge(order) 這個 Promise 時，then 產生的新 Promise 會等扣款完成，並且用扣款的結果成功。下一個 then 收到的就是付款資料本身，而不是一個 Promise。這就是「下一步等上一步」的機制。

忘了 return 會怎樣？

表格第三列「沒有 return」看起來無害，卻是 Promise 鏈最常見的 bug。同一條鏈，第一個 then 用了大括號卻沒寫 return。執行後看兩件事：下一步收到什麼，以及「扣款完成」和它誰先印：

下一步馬上收到 undefined，而且比「扣款完成」還早執行。原因是：callback 雖然呼叫了 charge(order)，扣款也真的開始了，但它沒有把那個 Promise 回傳出去，then 看不到它，只看到 callback 結束、回傳 undefined，於是新的 Promise 立刻用 undefined 成功。扣款的 Promise 從此跟這條鏈斷開了。

在正式環境，這會變成「收據印出來了，扣款其實失敗」，而且扣款失敗的錯誤沒有人接，因為已經沒有任何一段程式在等那個 Promise。防範的方法很簡單：箭頭函式寫成 order => charge(order)，不加大括號就會自動回傳；用了大括號，就確認每一條路都有 return。

then 寫在 then 裡面：把巢狀攤平

剛學 Promise 的人，常把下一步的 then 寫在上一步的 callback 裡面，越寫越往右縮，中間某一層也很容易漏掉 return（練習 3 的起始程式就是這樣）。因為 then 會等 callback 回傳的 Promise，巢狀的寫法都可以攤平成一條：

// 巢狀：難讀，也容易漏 return
checkStock(order).then(() => {
  return charge(order).then(payment => {
    return printReceipt(payment)
  })
})

// 攤平：每一步一行
checkStock(order)
  .then(() => charge(order))
  .then(payment => printReceipt(payment))

巢狀只有一個合理的用途：後面的步驟同時需要前面好幾步的結果。下一課的 async/await 用一般的變數就能解決這件事。

三步都成功時，這條鏈會把收據一路送到最後。但真實的下單常常失敗：庫存不足、信用卡被拒、收據服務逾時。失敗的時候，後面的步驟還會不會執行？錯誤會跑到哪裡去？

其中一步失敗了，錯誤會跑到哪裡？

規則是：鏈上任何一步 throw，或回傳一個失敗的 Promise，後面的 then 都會被跳過，錯誤一路往下找最近的 catch。這跟第 4 課的 throw 往外找 try／catch 是同一個概念，只是 Promise 鏈裡錯誤是沿著鏈「往下」走。

為什麼 then 會被跳過？因為 then 只登記了「成功時」要做的事。前一個 Promise 失敗時，then 的 callback 不會執行，then 產生的新 Promise 直接用同一個錯誤失敗，於是錯誤原封不動傳到再下一個 then，一直傳到有人登記了「失敗時」要做的事，也就是 catch。執行後看哪幾行有印、哪幾行沒印：

catch 放在中間還是最後？

catch 跟 then 一樣，也會回傳一個新的 Promise。catch 的 callback 正常 return（沒有再 throw）時，這個新的 Promise 是成功的，意思是「錯誤已經處理好了」，於是後面的 then 照樣執行。所以 catch 放在哪裡，決定錯誤之後哪些步驟還會跑。執行後比較兩條鏈，看「扣款」有沒有被執行：

第一條鏈庫存不足還是扣了錢。中間的 catch 只適合「這一步失敗也能繼續」的情況，例如推薦商品載入失敗，就回傳空陣列，頁面照樣顯示。下單這種不能繼續的流程，catch 放在最後；或者乾脆不要 catch，把整條鏈 return 給呼叫的人，讓真正知道該怎麼處理的那一層決定（第 4 課「在哪一層處理錯誤」）。練習 3 要的就是後者。

不論成功失敗都要收尾：finally

下單時，前台通常會顯示「處理中」並鎖住結帳按鈕。不管最後成功或失敗，都要把這個狀態關掉。如果在 then 和 catch 裡各寫一次，很容易漏掉一邊。finally 就是為這種收尾設計的：不論 Promise 成功或失敗，它的 callback 都會執行。

finally 的設計重點是不改變結果：它的 callback 收不到值（它本來就不該關心成功或失敗），回傳值也會被忽略，原本的結果原封不動往下傳。唯一的例外是 finally 自己丟錯，或回傳失敗的 Promise，這時結果會變成那個錯誤。執行後看兩條鏈的 then 和 catch 各收到什麼：

沒有人接的錯誤

反過來想：如果一條鏈失敗了，鏈的最後卻沒有 catch，也沒有被 return 給任何人，會怎樣？這個失敗的 Promise 從頭到尾沒有人處理，叫做 unhandled rejection。瀏覽器的 console 會出現 Uncaught (in promise)，除此之外什麼都不會發生：沒有人知道下單失敗了。前面「忘了 return」的扣款，就是製造 unhandled rejection 最常見的方式。在 Node 裡它的後果更嚴重，第 9 課會講。

reject 和 throw 都用 Error，不要用字串。reject('賣完了') 沒有 stack trace，查 log 時不知道是哪裡出的錯，e.message 也是 undefined。理由跟第 4 課「丟 Error，不要丟字串」相同。
💡 實務上：每條鏈最後都要有人負責錯誤
咖啡店前台按下「結帳」，最外層通常會有一個 catch：顯示「付款失敗，請再試一次」，並把錯誤送到 log 或錯誤追蹤服務（例如 Sentry）。最常見的壞習慣是 .catch(() => {}) 或只 console.log：畫面看起來沒事，客服接到「扣了錢卻沒訂單」的回報時，卻查不到任何紀錄。資深的人 review 時會沿著每條鏈看一遍：它是被 return 給呼叫的人，還是最後有 catch？中間的 catch 是刻意的降級（例如推薦商品載入失敗就顯示空的），還是不小心把錯誤吞掉了？

到這裡，下單流程完整了：三步依序執行，任何一步失敗，後面的步驟都不會跑，錯誤會交給負責的人。但鏈的前提是「後一步要用到前一步的結果」，所以只能一步等一步。如果幾件工作彼此無關，還要讓它們排隊嗎？

互不相關的工作，為什麼不用排隊？

下單的三步互相依賴，只能排隊。換一個場景就不一樣了：店長打開後台首頁，要載入三個區塊：今日營收（100ms）、庫存（300ms）、評論（200ms）。這三個請求誰都不需要誰的結果。用 then 鏈一個一個等，要 100 + 300 + 200 = 600ms；三個同時送出，總時間只取決於最慢的那個，300ms。

為什麼「同時」做得到？關鍵在於：呼叫函式拿到 Promise 的那一刻，工作就已經開始了。Promise 只是那份工作的號碼牌。所以「同時」的寫法分兩步：先把三個請求都送出去，手上拿著三個 Promise；再用一個工具一起等它們。

這個「一起等」的工具，Promise 提供了四個，統稱組合函式。它們都接收一個 Promise 陣列，回傳一個新的 Promise，差別在於這個新的 Promise 什麼時候成功、什麼時候失敗。要選哪一個，取決於你怎麼回答「其中一個失敗時，整體算不算失敗」。

組合函式成功失敗適合
Promise.all全部成功：值的陣列，順序跟傳入的相同任何一個失敗就立刻失敗，原因是第一個失敗的錯誤缺一不可，例如結帳需要的商品、會員、優惠券資料
Promise.allSettled全部定案就成功（永遠不會失敗）：{ status: 'fulfilled', value } 或 { status: 'rejected', reason } 的陣列—部分失敗也要顯示，例如後台首頁的各個區塊
Promise.race第一個定案的是成功第一個定案的是失敗「誰先回來就用誰」，不管成敗
Promise.any第一個成功的值全部失敗：AggregateError問好幾個來源，有一個成功就好

表格 any 那一列的 AggregateError 是一種 Error，一次裝很多個錯誤，個別的錯誤放在它的 errors 陣列裡，順序跟傳入的 Promise 相同。any 全部失敗時，沒有單一的「那個錯誤」可以回報，所以把所有錯誤裝在一起交出來。

Promise.all 失敗了，其他請求會停下來嗎？

Promise.all 遇到失敗會「立刻失敗」，很容易讓人以為其他請求也跟著停了。實際上不會：已經送出的其他請求還在跑，結果只是沒有人要了。回到號碼牌的比喻，Promise 只是號碼牌，你把號碼牌丟掉，正在做飲料的人並不會因此停手。race 和 any 也一樣。執行後看 all 失敗之後，另外兩個工作有沒有印出「做完了」：

這在後端很重要：Promise.all 在 20ms 就失敗了，但「寄通知信」照樣寄出、「扣庫存」照樣扣掉。對讀取資料的請求來說，只是浪費一點資源；對會改資料的動作來說，就是資料不一致。真的要停下其他工作，要用 AbortController 把取消訊號傳進每個工作；用 race 做逾時也有同樣的問題（逾時了，原本的請求還在跑）。這兩件事在第 11 課。

還有一點要記得：組合函式只能等「已經開始的工作」，它本身不會幫你啟動任何東西。要同時，就要先把每個請求都送出去，再把 Promise 交給它。一次送多少個才安全，在第 9 課。

💡 實務上：先問「缺一個行不行」，再挑組合函式
後台儀表板的各個區塊用 allSettled，評論服務掛了，營收和庫存照樣顯示，壞掉的區塊顯示「暫時無法載入」（練習 4）；結帳前要的商品、會員、優惠券缺一不可，用 all。要小心的是把「會改資料」的動作放進 Promise.all，例如同時扣款和扣庫存：一個失敗時另一個可能已經做完，又不會自動回復。這種動作要依序做，或交給資料庫的交易處理：交易把幾個寫入綁成一組，全部成功才算數，任何一個失敗就全部不算。另一個坑是對幾百筆 id 一次 Promise.all(ids.map(fetchOrder))，等於同時打幾百個請求給 API，限制同時數量的做法在第 9 課。

到目前為止，每個 Promise 的結果都由一件非同步工作自己決定：計時器到了、咖啡機回應了、API 回來了。還有一種情況，決定結果的是程式外面的「人」。

結果由店員按按鈕決定時，resolve 要怎麼拿到外面？

客人點了手沖。手沖要現場慢慢做，沒有 API 可以問「好了沒」，程式要等店員在吧台的平板上按下「完成」，才通知客人取餐。

這跟前面的例子有一個根本的差別。sleep 和咖啡機的例子裡，決定結果的計時器和 callback 都寫在 executor 裡面，resolve 就在手邊。這裡決定結果的是「完成」按鈕的處理函式，它寫在程式的別處，而 resolve 只存在於 executor 裡。要讓按鈕能讓 Promise 成功，就得想辦法把 resolve 拿到 executor 外面。

以前的寫法是在 executor 裡把 resolve 存到外面的變數。ES2024 加入了 Promise.withResolvers()，一次回傳 { promise, resolve, reject } 三樣東西，不必再繞這一圈。下面兩種寫法並排，用計時器模擬店員按下按鈕，執行後看兩個 Promise 都在「按下按鈕」時才成功：

💡 實務上：自訂確認視窗就是 withResolvers 的典型用途
前端常見的寫法是 const ok = await confirmDialog('確定取消這張訂單？')：開視窗時建立 Promise，把 resolve 交給「確定」和「取消」兩個按鈕。其他場景還有等 WebSocket 伺服器回覆某個訊息、等 iframe 用 postMessage 回應。要考量的是 resolve 拿到外面之後，誰都可能沒呼叫它：使用者按 Esc 或點遮罩關掉視窗、元件被卸載、店員忘了按，這個 Promise 就永遠 pending，等它的程式永遠卡住，也不會報錯。所以每一條「結束」的路都要 resolve 或 reject，等外部回應的還要搭配逾時（第 11 課）。

練習

練習 1：寫 sleep(ms) 和 delay(value, ms)。兩個都回傳 Promise，ms 毫秒之後才成功；delay 成功時的值是 value。

練習 2：寫 promisify(fn)。fn 的最後一個參數是 callback (err, result)。回傳一個新函式，呼叫它時把參數交給 fn、再加上 callback，並回傳 Promise：

  • err 有值時，用同一個錯誤物件 reject；否則用 result resolve。
  • 要保留呼叫時的 this：把包好的函式放到物件上當方法呼叫，fn 拿到的 this 要是那個物件。提示：箭頭函式沒有自己的 this（第 1 課：一般 function 的 this 看它怎麼被呼叫），回傳的函式要怎麼寫、fn 要怎麼呼叫，才能把 this 傳下去？

練習 3：placeOrder(api, order) 要依序做三步：api.checkStock(order) → api.charge(order)（成功時得到付款資料）→ api.printReceipt(付款資料)（成功時得到收據字串），最後回傳的 Promise 要用收據完成。現在的寫法有好幾個問題，修好它：

  • 每一步都要等上一步完成，收據要傳回給呼叫的人。
  • 任何一步失敗，後面的步驟都不能執行（庫存不足不能扣款），而且錯誤要原封不動傳給呼叫的人，不能在這裡吞掉。

練習 4：loadDashboard(loaders) 載入後台首頁。loaders 是 { sales, stock, reviews } 三個函式，各自回傳 Promise。要求：

  • 三個同時開始。
  • 回傳的 Promise 用 { sales, stock, reviews, errors } 完成：成功的那一項放值，失敗的那一項放 null。
  • errors 是失敗的錯誤訊息（message），依 sales、stock、reviews 的順序排列；全部成功時是 []。

練習 5：firstAvailable(stores, check) 同時問每一家分店有沒有貨。check(store) 回傳 Promise，有貨時成功、沒貨時失敗。要求：

  • 用第一家有貨的分店名稱完成（不是 check 的回傳值）。最快回應的分店沒貨時，要繼續等下一家有貨的。
  • 全部都沒貨時，丟出 Error('所有分店都沒貨')，cause 是包著每家錯誤的那個 AggregateError（第 4 課：new Error(訊息, { cause }) 把原本的錯誤包在新錯誤裡）。

練習 6：const p = new Promise(r => setTimeout(r(1), 100))，p 什麼時候定案？

✓ r(1) 有括號，在 executor 裡立刻被呼叫，p 當下就成功了；交給 setTimeout 的是 r(1) 的回傳值 undefined。之後 setTimeout 就算出錯，Promise 也已經定案。要延遲就交出函式：setTimeout(() => r(1), 100)。

練習 7：Promise.all([扣庫存(), 查會員(), 寄通知信()])，查會員最先失敗。另外兩個請求怎麼了？

✓ Promise 只是代表結果的物件，沒有「取消」的能力。Promise.all 立刻失敗，但扣庫存和寄通知信已經送出，會照樣完成，所以可能出現「庫存扣了、訂單卻失敗」。要取消必須自己把 AbortController 的訊號傳進每個工作（第 11 課）。

練習 8：p.then(a).catch(b).then(c)，a 丟出錯誤、b 正常 return。c 會執行嗎？

✓ catch 也回傳新的 Promise，b 正常 return 時它就成功，鏈恢復正常。所以 catch 放在中間，後面的步驟會在錯誤之後照樣執行；不希望這樣，就把 catch 放在最後，或在 b 裡再 throw。

常見錯誤

  • then 裡忘了 return：下一步收到 undefined，而且不會等裡面的非同步工作，它的錯誤也沒人接。用不加大括號的箭頭函式 x => next(x)，或確認每一個大括號裡都有 return。
  • setTimeout(resolve(x), ms)：立刻呼叫了 resolve，沒有延遲。交出函式：() => resolve(x)。
  • 部分失敗也要顯示，卻用 Promise.all：一個失敗就全部拿不到。改用 allSettled，自己決定每一項失敗時顯示什麼。
  • 以為 Promise.all／race 會取消其他工作：其他工作照樣跑完，副作用（扣款、寄信）照樣發生。
  • catch 放在鏈的中間：catch 之後鏈恢復成功，後面的步驟在錯誤之後照樣執行。不能繼續的流程，catch 放最後或交給呼叫的人。
  • reject 字串：沒有 stack trace、沒有 message。一律 reject(new Error(…))。
  • 在 executor 裡做很重的同步工作，以為會在背景跑：executor 是同步執行的，照樣卡住整個程式。
  • 在計時器或 callback 裡 throw，以為 Promise 接得到：那時已經離開 executor，錯誤沒人接。要失敗就呼叫 reject。

Node 內建的 promisify

在 Node 裡不用自己寫 promisify：內建的 util.promisify 做的是同一件事，而且 fs 等內建模組大多已經有 Promise 版（例如 node:fs/promises）。練習 2 自己寫一次通用的 promisify，是為了看懂它在做什麼。

then(ok, fail) 不等於 then(ok).catch(fail)

then 可以收第二個參數，處理「前一步」的失敗。它也是 unhandled rejection 的來源之一：看起來跟 catch 一樣能接錯誤，卻會漏接一種錯誤。差別在於：then(ok, fail) 的 fail 接不到 ok 自己丟出的錯誤，因為 fail 登記在「前一個 Promise」上，ok 的錯誤發生在 then 產生的新 Promise 上；then(ok).catch(fail) 的 catch 接在新 Promise 後面，所以接得到。執行後看哪一行接到了錯誤：

Promise.withResolvers 的支援

Promise.withResolvers 的支援：Chrome 119、Firefox 121、Safari 17.4、Node 22 起；TypeScript 要 lib 包含 es2024 才有型別。要支援更舊的環境時，用正文的舊寫法。

小結

  • 結果還沒來，函式要回傳什麼：回傳 Promise。它代表之後才會有的結果：pending → fulfilled 或 rejected，只定案一次；用 then／catch 登記結果來了要做的事，callback 一定之後才執行。
  • 要等的東西不回傳 Promise：用 new Promise((resolve, reject) => …) 包起來。executor 立刻同步執行；定案之後再呼叫 resolve／reject 都無效；非同步 callback 裡要失敗就呼叫 reject，不要 throw。
  • 舊式 callback API：用 new Promise 包起來（promisify），失敗時 reject 同一個錯誤物件，要保留 this 就用 function 加 fn.call(this, …)。
  • 一步接一步：每個 then 回傳新的 Promise：return 值往下傳、return Promise 會被等待、忘了 return 就斷掉。
  • 其中一步失敗：錯誤跳過後面的 then，找最近的 catch；catch 處理完之後鏈恢復成功，所以不能繼續的流程 catch 放最後或交給呼叫的人；finally 不改變結果。最後沒人處理的失敗是 unhandled rejection。
  • 互不相關的工作：先全部送出再一起等。缺一不可用 all、部分失敗也要結果用 allSettled、誰先定案用 race、有一個成功就好用 any。它們都不會取消其他工作。
  • 結果由外部決定：Promise.withResolvers()（ES2024）把 resolve 拿到 executor 外面；每一條結束的路都要 resolve 或 reject。
