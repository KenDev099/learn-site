階段 2：非同步、迭代與並發 · 第 7 課

Event loop：程式執行的順序

週五晚上的尖峰時段，咖啡店後台同時出了兩件事。第一件：店長按下「匯出整年訂單」，接下來好幾秒，所有門市的結帳畫面都在轉圈圈，大家以為資料庫掛了。第二件：一位客人付款成功，拿到的收據卻印著 undefined。兩段程式都沒有語法錯誤，在測試環境也都正常。

兩件事的根源是同一個：JavaScript 決定「哪一行先跑、哪一行要排隊等」的規則，也就是 event loop。前端寫 setTimeout、fetch、await 時很少需要想這件事，但後端一台伺服器同時服務上百個請求，順序想錯就是線上事故。這一課從零把這套規則講清楚，再用它解釋並修好這兩個事故。學完你能預測 console.log、setTimeout、Promise、await 混在一起時的輸出順序，知道為什麼不能靠「等一下」排先後，也會把很久的工作切塊，不讓它卡住別人。

這課的路線：
  1. 只有一位咖啡師：同步程式為什麼一口氣跑到底，連 0ms 的計時器都插不進來。
  2. 誰先印、await 停住的是誰：task 與 microtask 兩個佇列的排隊規則（開場問題的最小答案），順便解開第 1 課 var 迴圈的謎。
  3. 收據為什麼印出 undefined：用這套規則修好第一個事故，改成「等前一步完成」而不是「等一段時間」。
  4. 一個匯出為什麼卡住所有結帳：什麼叫阻塞、包成 Promise 為什麼沒用、怎麼切塊讓出執行緒。
  5. 上線之後怎麼確認：瀏覽器和 Node 各自怎麼量 event loop 有沒有被卡住。
這課會用到：
  • 第 1 課的 callback 與「var 迴圈加 setTimeout」陷阱：callback 是交給別人、之後由別人呼叫的函式；迴圈裡交給 setTimeout 的三個 callback 都印出 4，當時說原因在這一課。
這頁的範例跑在瀏覽器另開的一條背景執行環境裡（Web Worker，後面講 task 時會再提到）：它沒有畫面，event loop 規則跟一般網頁相同。每次執行最多 3 秒，超過會被強制停止。

只有一位咖啡師：為什麼同步程式沒人插得進來？

要解釋開場的兩個事故，得先知道 JavaScript 一次能做幾件事。答案是一件。

電腦執行程式時，是沿著一條路線一行一行往下做，這條路線叫執行緒（thread）。有些語言的程式可以同時開好幾條執行緒，各做各的。JavaScript 程式本身只有一條：同一時間，只會有一行 JavaScript 在執行。

想像咖啡店裡只有一位咖啡師。他在手沖一杯咖啡時，手是滿的，其他客人只能等他沖完。這位咖啡師就是那一條執行緒。

咖啡師手上「正在做的事」也有結構。沖咖啡的途中要磨豆，他會先放下沖煮、去磨豆，磨完再回來接著注水。程式也一樣：函式 A 裡呼叫函式 B，就要先做完 B，再回到 A 剛才停下的地方。JavaScript 用一個呼叫堆疊（call stack）記住「做完之後要回到哪裡」：呼叫一個函式，就把它疊到最上面；函式回傳，就把它拿掉，回到下面那一層繼續。堆疊最上面那一個，永遠是咖啡師此刻手上的事。第 4 課看過，錯誤丟出來之後，會沿著這個堆疊一層一層回到呼叫它的函式，找最近的 catch。

只有一位咖啡師，為什麼店還能同時等烤箱、接外送電話？因為等待的事不是他在等。店裡還有外場人員：烤箱計時、外送電話、收款機都交給外場，不佔咖啡師的手。程式裡的外場叫宿主環境（host），就是執行 JavaScript 的那個環境，瀏覽器或 Node。計時器、網路、讀寫檔案這些功能是宿主環境提供的，不是 JavaScript 引擎本身；等待它們的時候，JavaScript 執行緒是空著的。

這帶出兩種寫法的差別。同步（synchronous）是「馬上做完才往下」，像磨豆，咖啡師親手做完才做下一步。非同步（asynchronous）是「先登記，之後再做」，像跟外場說「烤箱好了叫我」，自己馬上去做別的。setTimeout(fn, 100) 就是非同步：它只是請外場 100ms 後把 fn 交回來，呼叫的當下立刻往下執行。

外場把事情交回來時，不能直接塞進咖啡師手裡，他手上可能正在忙。所以外場會把一張工作單放進待辦籃，程式裡叫佇列（queue），先放進去的先處理。咖啡師手上的事全部做完、呼叫堆疊空了，才從籃子裡拿下一張。籃子其實有兩個，圖裡的 microtask 佇列和 task 佇列，差別下一節講。

計時器要排隊這件事清楚了。可是開場的收據 bug 裡還有 Promise：Promise 的後續也要排隊嗎？它跟計時器擺在一起，誰先？

setTimeout、Promise 混在一起時，誰先印？

上一節說待辦籃有兩個，這一節講它們的差別，這就是 Promise 和計時器順序不同的原因。

先認識 Promise。Promise 是一個物件，代表「之後才會有的結果」，像點餐後拿到的取餐號碼牌：餐還沒好，但你手上有一個憑證，餐好了可以用 then 登記「拿到之後要做什麼」。await 則是在 async 函式裡等這個結果好了再往下。這一課只需要知道它們代表「之後」，第 8 課和第 9 課會完整說明。

兩個籃子的差別在「什麼時候輪到」：

  • task（工作，也叫 macrotask）是一整件獨立的工作，排到下一輪才做，一次只拿一個來執行。來源有：setTimeout／setInterval 到期、使用者事件、網路回應，還有 Worker 傳來的訊息。Worker 是第 1 課提過的另一條執行緒，它做完事會用訊息通知主執行緒。
  • microtask（微任務）是「目前這件事一做完，就馬上接著做」的收尾工作，插在兩個 task 中間。來源有：Promise 的 then／catch／finally、await 之後的程式、queueMicrotask(fn)（直接排一個 microtask 的函式）。

咖啡師從籃子拿工作的規則，就叫 event loop（事件迴圈）。它是一個永遠重複的迴圈：

  1. 執行一個 task（一開始的主程式本身也算一個 task），直到呼叫堆疊空了。
  2. 清空 microtask 佇列：一個接一個執行，途中新排進來的 microtask 也要在這一輪做完。
  3. （瀏覽器）需要的話更新畫面。
  4. 回到 1，拿下一個 task。

重點在第 2 步：每做完一個 task，microtask 籃子一定先清空，才輪到下一個 task。用這條規則先猜下面的輸出，再執行：

回頭看第 1 課的 var 迴圈

同一條規則可以解開第 1 課留下的謎。for (var i = 1; i <= 3; i++) setTimeout(() => console.log(i), 0) 印出三個 4：迴圈是主程式這個 task 的一部分，三個 callback 都排在 task 佇列裡，要等迴圈跑完、主程式結束才輪到。那時唯一的 i 已經是 4。

規則到這裡已經可以先回答開場的兩個事故，細節後面三節再補：

  • 收據印出 undefined：用 setTimeout「等一下」再印，只保證排在目前這個 task 之後，不保證付款已經完成。付款結果還沒回來，收據變數當然是空的。
  • 匯出卡住所有結帳：咖啡師只有一位。匯出如果是一段很久的同步程式，它沒做完，其他請求的 task 全部輪不到。

不過後端最常寫的不是 then，而是 await。修收據 bug 之前，要先確定一件事：await 在等的時候，程式停在哪裡？

這張表有兩個容易誤會的地方。第一，async 函式並不是「整個都非同步」：第一個 await 之前的程式（印 2）是同步執行的，跟一般函式沒有兩樣。第二，await 停住的只有這個 async 函式本身，不是整個程式：order() 一遇到 await 就回傳了，主程式照樣往下印 3。

這裡 await 的是 null，結果馬上就有，所以後半段立刻排進 microtask。如果 await 的是一個要 2 秒才回來的網路請求，這 2 秒裡等待的是外場；後半段要等結果回來才會排進 microtask，咖啡師在這段時間可以去做別的 task，例如處理其他客人的請求。

所以 await 是「這件事接在那個結果後面」，而且等待時不佔執行緒。開場的收據 bug，正是有人沒用這種「接在後面」的寫法，而是用時間去猜。

收據為什麼印出 undefined？用順序，不用時間

現在可以把第一個事故拆開來看。付款要呼叫外部的金流服務，工程師覺得「等一下就好了」，用 setTimeout 延後印收據。下面是簡化版，執行後比較兩行：✗ 那行的收據是什麼。

用前兩節的規則跑一次 checkoutBuggy：

  1. pay(order) 請外場 30ms 後回覆付款結果，then 登記「付款好了就把收據存進 receipt」。這時付款還沒完成，then 的 callback 還沒排進任何佇列。
  2. setTimeout(…, 0) 登記一個 0ms 後的 task。
  3. 主程式結束。0ms 的計時器比 30ms 的付款先到期，印收據的 task 先執行，這時 receipt 還沒被賦值，印出 undefined。
  4. 30ms 後付款才回來，receipt 才有值，但收據已經印完了。

checkout 用 await pay(order)，印收據這一行被接在付款結果後面：付款沒回來，這一行就不會執行，付款回來多晚都一樣。

有人會想：把 0 改成 100 不就好了？試試看，看起來修好了。但金流服務哪天慢到 150ms，又會壞。這段假服務的註解寫著，實際上可能 5ms，也可能 3 秒。用固定的等待時間安排先後，只是把 bug 藏到比較少發生，而且在測試環境幾乎重現不了，因為測試環境的外部服務通常很快。開場說「測試環境都正常」，原因就在這裡。

資深觀點：「B 要在 A 之後」就讓 B 接在 A 的結果後面（await 或 then），不要猜 A 要多久。看到程式碼裡有 sleep(500) 或 setTimeout(…, 1000) 用來「等某件事好」，就是值得追問的地方。真正需要時間的情境（逾時、重試間隔、輪詢）才用計時器，第 11 課會講。

收據的事故修好了：等外部服務時用 await 接在結果後面，執行緒也同時空出來給別人。可是第二個事故不一樣，匯出整年訂單的時候，程式沒有在「等」誰，而是一直在算。

匯出整年訂單，為什麼讓所有結帳一起變慢？

上一節的 await 能讓出執行緒，是因為等待的是外場。如果工作本身就是咖啡師親手在做，例如一個跑很久的迴圈，就沒有東西可以交給外場了。

咖啡師只有一位，所以一段很久的同步程式，會讓所有計時器、事件、其他 callback 全部延後，因為堆疊一直沒空，event loop 的第 1 步一直沒結束。這叫阻塞（blocking）：執行緒被一件事佔住，其他事都輪不到。

伺服器上同樣的事更嚴重。Node 也只有一條 JavaScript 執行緒，每個 HTTP 請求進來，都是排進佇列的一個 task。一個請求在做 1 秒的同步計算，這 1 秒裡所有其他請求都在等，不只是這位店長的匯出。這就是開場「所有門市的結帳都在轉圈圈」的原因。Node 課的 第 9 課會用 worker_threads 把重的計算搬到別的執行緒。

包成 Promise 不會變成背景執行

看到這裡，常見的直覺是「把匯出包進 Promise，它就會在背景跑」。要檢查這個想法，先認識 new Promise 的寫法：new Promise(resolve => { … }) 收一個函式，這個函式叫 executor，裡面放產生結果的程式，結果好了就呼叫 resolve。問題是 executor 什麼時候執行？答案是 new Promise 的當下就立刻、同步執行。執行後看 new Promise 回傳時已經過了多久：

executor 裡的迴圈照樣佔住同一條執行緒，new Promise 要等它跑完才回傳，計時器也一起被拖到 300ms 之後。Promise 只是「結果之後才拿得到」的包裝，它不會多出一條執行緒。async 函式也一樣：上一節看過，第一個 await 之前的程式都是同步的，在那裡跑重活一樣會卡住所有人。

💡 實務上：「整台伺服器一起變慢」常是某個請求在做同步重活
開場的匯出事故是典型：店長一按匯出，同一時間點餐、結帳的 API 全部變慢，看起來像資料庫出問題，其實是那個請求在跑大迴圈、組超大字串，或 JSON.parse 一個很大的檔案。同步版的 API 也是常見原因，例如 Node 的 fs.readFileSync 或同步的密碼雜湊（例如 bcrypt 的 hashSync）。資深工程師看到「所有 API 同時變慢」會先問：這個時段有沒有人觸發大量計算？請求的處理流程裡有沒有 Sync 結尾的呼叫？找到之後不是包成 Promise 就好，而是切塊、搬到 worker，或改成背景工作，做完再通知使用者。

所以修匯出事故有兩條路：讓這件事在別的地方算（資料庫、worker、背景工作），或者真的必須在這條執行緒上算時，把它切成小塊，中間讓別人插進來。下一節講切塊。

非得在這條執行緒上算時，怎麼讓別人插進來？

假設匯出前要在 JavaScript 裡逐筆處理 1000 筆訂單，而且只能在這條執行緒上做。一口氣做完會卡住其他事，解法是切成小塊：做完一塊，就把執行緒還回去，讓佇列裡排著的其他工作先跑，再繼續下一塊。這個「主動把執行緒還回去」的動作叫讓出（yield）。

在 JavaScript 裡，讓出的做法是在 async 函式裡 await 某個東西，讓函式先暫停、堆疊清空，之後再從暫停的地方繼續。但不是 await 什麼都有效，關鍵在後半段被排進哪個佇列：排進 microtask，它會在其他 task 之前就接著跑，別人還是插不進來；排進 task，佇列裡先排好的工作才輪得到。下面對照兩種寫法，每處理 50 筆讓出一次：一種 await 一個已完成的 Promise（後半段排成 microtask），另一種 await 一個 setTimeout（後半段排成 task）。執行後看先排好的計時器執行時，已經處理了幾筆：

用 await Promise.resolve() 切塊，計時器執行時 200 筆已經全部處理完了，等於沒切。回到 event loop 的規則：每次讓出都只是排一個 microtask，而 microtask 永遠在下一個 task 之前清空，所以函式的後半段馬上又接著跑，計時器一直插不進來。只有讓出到 task（setTimeout），函式的後半段才會排到計時器後面，別人才插得進來。

但也不要每一筆都讓出

既然 setTimeout 讓出有效，那每一筆都讓出一次，不是最不會卡住別人嗎？問題是 setTimeout(0) 不是零成本。HTML 規範規定：計時器巢狀超過 5 層（計時器的 callback 裡又排計時器，一直下去）、延遲又小於 4ms 時，延遲至少 4ms。切塊的寫法剛好就是一層接一層的計時器。執行後看每次實際等了多久，跟寫的 0ms 比一比：

每一筆都 await 一個 setTimeout(0)，1000 筆光是等待就要約 4 秒，工作本身可能只要幾十毫秒。

所以要一批一批讓出：每 50～100 筆讓出一次，或每做 10ms 左右就讓出一次。批太大會卡住別人，批太小會浪費在等待上。

讓出到 microtask 的極端：無限排 microtask 會卡死

前面看到用 microtask 讓出沒有用。更糟的情況是 microtask 自己一直排新的 microtask：event loop 規定途中新排的 microtask 也要在這一輪清完，所以這一輪永遠清不完，task 永遠輪不到。這叫飢餓（starvation）：其他工作一直排隊，卻永遠拿不到執行緒。下面讓它只跑 200ms 就停，否則整個程式會卡死，練習區 3 秒後強制停止：

💡 實務上：切塊是手段，先想這件事該不該在這裡算
前端最常用到：一次渲染幾千筆訂單、匯入使用者上傳的 CSV 時畫面凍住，切塊再加上進度條，使用者就知道還在跑、也還能捲動頁面。後端要先退一步：加總營收這類工作，交給資料庫用 SQL 的 SUM、GROUP BY（在資料庫裡直接加總、分組）算，通常比把資料全撈進 JavaScript 迴圈好；產生 PDF、壓縮圖片這種真正吃 CPU 的工作，放到 worker 或獨立的背景工作。批次大小沒有標準答案，用 performance.now() 量過再調。也要想到切塊的副作用：處理到一半時資料可能被別人改了，使用者也可能想中途取消。

上線之後，怎麼確認 event loop 有沒有被卡住？

兩個事故的原因和修法都有了。最後一個問題是：下次再有人回報「卡卡的」，怎麼知道是不是 event loop 被卡住，而不是別的原因？

先確認一件事：這課的規則在瀏覽器和 Node 都成立，兩邊都是「做一個 task，清空 microtask，再拿下一個 task」，只是被卡住時的症狀不同。在瀏覽器，event loop 清完 microtask 之後才有機會更新畫面，所以卡住 event loop 就是這個分頁點不動、畫面凍結。在 Node，每個請求都排在同一條執行緒上，所以卡住 event loop 就是這個程序的所有請求一起變慢，也就是開場的匯出事故。兩邊各自還有一些額外的佇列與時機（Node 的 process.nextTick、setImmediate），這課用不到，整理在課末。

知道了症狀，查的方向就是量「執行緒有沒有被一大塊同步程式佔住」。怎麼量？其實前面已經量過一次了。

Event loop 延遲：計時器實際晚了多久

回想匯出那一節的範例：排一個 100ms 的計時器，再跑 1 秒的同步迴圈，結果印出「說好 100ms，實際過了一千多 ms」。多出來的那段時間，就是計時器到期之後、還在佇列裡排隊等咖啡師空出手的時間。這段「該執行卻還沒輪到」的時間，叫 event loop 延遲（event loop delay，也常叫 event loop lag）。執行緒很閒時，計時器一到期就被拿去執行，延遲接近 0；執行緒被同步程式佔住多久，延遲就差不多有多久。

所以量 event loop 有沒有被卡住，做法就是那個範例的持續版：每隔一小段時間排一個計時器，記下它實際晚了多久，再把一段時間內的結果整理成統計，例如平均值和最慢的那幾次。Node 內建的 perf_hooks.monitorEventLoopDelay() 做的就是這件事，監控工具上的 event loop lag 指標也是同一個概念。看的時候不要只看平均：大部分時間都很閒，偶爾卡 2 秒，平均值會很好看，但那 2 秒裡進來的請求全都在等。

Long task：瀏覽器那一側的阻塞

瀏覽器這邊換一個角度量：直接看主執行緒上「一次連續佔住多久」。主執行緒一次連續執行超過 50ms 的工作，叫 long task。這條線的用意是：使用者按下按鈕時，如果剛好碰上一個 long task，就要等它跑完才有反應，工作越長，使用者感覺到的「卡一下」就越明顯。瀏覽器 DevTools 的 Performance 面板可以錄下一段時間內主執行緒做了什麼，Chrome 會把超過 50ms 的工作標成 long task，點進去就看得到是哪個函式。

兩種量法是同一件事的兩面：long task 看的是「誰佔住了執行緒、佔多久」，event loop 延遲看的是「其他人因此多等了多久」。

判讀：卡在 event loop，還是在等外部服務？

「卡卡的」不一定是 event loop 被卡住。請求慢有兩種很不一樣的原因，要搭配 CPU 使用率一起看：

  • 延遲升高，CPU 又滿：咖啡師一直在親手做事，沒空處理別人。這代表有同步程式卡住執行緒，就是開場的匯出事故：所有請求一起變慢，修法是前面講的切塊、搬到 worker 或背景工作。
  • 延遲正常，CPU 很閒：咖啡師其實沒事做，只是在等外場回報。請求很慢多半是在等資料庫或外部服務，問題不在 event loop，要去查那個外部服務或查詢本身。

開場的另一個事故，收據印出 undefined，兩個指標都不會異常：它不是變慢，而是順序寫錯，要靠前面講的「等前一步完成」來修，監控量不出來。先分清楚是哪一種，才不會修錯地方，例如把等資料庫的問題拿去切塊，或把同步重活誤判成資料庫太慢。

💡 實務上：「卡卡的」要先量，不要先猜
客服回報「點餐頁按下去要等一下才有反應」，第一步是用 Performance 面板錄一段操作，看有沒有 long task、是哪個函式；後端回報「API 全部變慢」，先打開監控看 event loop 延遲和 CPU，再決定往哪個方向查。

練習

練習 1：checkout(order, pay, print) 用 setTimeout(…, 0)「等一下」再印收據，付款一慢就印出 undefined。改成：

  • pay(order) 回傳 Promise；付款完成後，才用收據呼叫 print，而且只呼叫一次。
  • checkout 要回傳一個 Promise，在 print 執行之後才完成。
  • 付款失敗時，checkout 回傳的 Promise 以同一個錯誤失敗，不能呼叫 print。
  • 不准用固定的等待時間。

練習 2：processOrders(orders, handle) 用同步迴圈處理所有訂單，處理 1000 筆時其他事情都動不了。把它改成 async 函式：

  • 仍然依序對每一筆呼叫 handle(order)，全部完成時回傳的 Promise 才完成。
  • 每處理 100 筆（或更少）就用 setTimeout 讓出一次，讓先排好的計時器有機會執行。
  • 1000 筆要在 2 秒內做完。

練習 3：waitForBarista(isReady) 要回傳一個 Promise，在 isReady() 變成 true 時完成。現在的寫法用 queueMicrotask 反覆檢查，結果整個程式卡死，3 秒後被強制停止（按「執行」看看）。修好它：每 10ms 檢查一次；一開始就準備好時，不用等就完成。

練習 4：依序執行下面五行，印出的順序是？

console.log('A')
setTimeout(() => console.log('B'), 0)
Promise.resolve().then(() => console.log('C'))
queueMicrotask(() => console.log('D'))
console.log('E')

✓ 同步的 A、E 先印；主程式這個 task 結束後先清空 microtask（C、D，依排入順序）；最後才輪到下一個 task B。a 和 b 都以為 setTimeout 0 會馬上或優先執行；d 以為 then 會插進同步程式中間。

練習 5：new Promise(resolve => { heavyLoop(); resolve() }) 裡的 heavyLoop() 要算 2 秒。這段程式會怎樣？

✓ 傳給 new Promise 的 executor 是同步執行的，Promise 不會多出一條執行緒。要真的平行計算，要用 Worker（Node 是 worker_threads）。只有 then、await 之後的程式才是 microtask，executor 本身不是。

練習 6：async 函式裡 await fetch(…) 一個要 2 秒的請求。這 2 秒裡，其他按鈕的點擊事件和計時器還能執行嗎？

✓ 等網路的是宿主環境，不是 JavaScript 執行緒。await 會讓 async 函式先回傳，後面的程式等結果好了再以 microtask 繼續；這段期間點擊事件、計時器都照常執行。會卡住大家的是長時間的同步程式，不是 await。

常見錯誤

  • 以為 setTimeout(fn, 0) 會馬上執行：它最快也要等目前的 task 和所有 microtask 做完；巢狀超過 5 層還會被拉到 4ms。
  • 用固定的等待時間安排先後：對方一慢就壞，例如付款還沒回來就印收據。把後一步接在前一步的結果後面（await、then）。
  • 以為包成 Promise 或寫成 async 就會在背景執行：executor 和第一個 await 之前的程式都是同步的，重的計算照樣卡住執行緒。
  • 伺服器上用同步迴圈處理大量資料：這段時間所有請求都在等。切塊讓出，或交給 worker。
  • 用 await Promise.resolve() 切塊：那只是 microtask，計時器、事件、網路回應還是等不到。要讓出到 task（setTimeout）。
  • 在 microtask 裡無限排新的 microtask：task 永遠輪不到，整個程式卡死。輪詢要用計時器。
  • 依賴計時器的精確時間：計時器只保證「至少」，主執行緒忙的時候會晚很多。

小結

  • JavaScript 程式只有一條執行緒，呼叫堆疊記住正在做什麼；計時器、網路由宿主環境等待，好了再排進佇列。
  • event loop：執行一個 task → 清空所有 microtask（包括途中新排的）→ 下一個 task。
  • task：setTimeout、事件、訊息。microtask：then／catch／finally、await 之後的程式、queueMicrotask。
  • await 只停住所在的 async 函式，等待時執行緒空出來給別人；第一個 await 之前的程式是同步的。
  • 先後順序靠「等前一步完成」，不靠「等一段時間」：收據要接在付款結果後面。
  • 同步程式跑太久會阻塞一切，在伺服器上就是所有請求一起變慢；Promise 和 async 不會把它變成背景執行。
  • 長工作一批一批做，中間用 setTimeout 讓出；用 microtask 讓出沒有用，每一筆都讓出又太慢。
  • 「卡卡的」先量：瀏覽器看 long task，Node 看 event loop 延遲，再決定是同步程式卡住，還是在等外部服務。
