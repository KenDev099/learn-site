階段 1：JavaScript 的核心機制 · 第 2 課

值與參考：相等、複製與不可變更新

客服轉來一張單：後台的「編輯訂單」頁面上，店員幫王小明 190 元的訂單按了「試算 9 折」，看完金額按「取消」，回到訂單列表，這張訂單卻變成 171 元，而且之後被存進了資料庫。程式裡沒有任何一行寫「把原訂單改成 171」，折扣函式只是「算一下」。

這一課從這個事故出發，把編輯訂單這個功能一路修好：試算不能改到原訂單、按取消要能復原、改數量不能偷改別人在用的資料、列表要正確合併顧客資料、後端的收據快取不能把記憶體吃光。這幾個問題看起來各不相干，根源卻是同一句話：物件變數裡存的不是物件本身，而是「物件在哪裡」。

學完這一課，你能判斷一行程式是在複製值還是在共用同一個物件，寫出不會偷改原資料的更新，選對比較與去重的方法，知道資料量變大時查詢該怎麼寫才不會慢下來，也知道哪些參考會讓記憶體回收不掉。後端的快取、Vue 的 props 與 Pinia 狀態，都建立在這些規則上。

這課的路線：
  1. 試算折扣為什麼改到原訂單：變數裡存的是什麼，物件交給函式時傳的是什麼（開場問題的最小答案）。
  2. 編輯頁怎麼判斷「有沒有改過」：===、==、Object.is 各比的是什麼。
  3. 按「取消」要能復原：淺複製、深複製各複製到哪一層，JSON 往返為什麼不能拿來複製。
  4. 改數量、排序都不碰原訂單：不可變更新怎麼只複製有變的部分；const、Object.freeze 擋得住什麼。
  5. 列表要合併顧客資料：Map、Set 怎麼認定「同一個」，資料一多怎麼建索引讓查詢不變慢。
  6. 收據快取越長越大：物件什麼時候才會被回收。
這課會用到：
  • 第 1 課的「閉包記住的是變數本身」：不是當下的值的複本，變數之後被改，函式看到的就是新值。

試算折扣為什麼會改到原訂單？先看變數裡存的是什麼

要查這個事故，得先知道 = 這個最基本的動作到底做了什麼。答案取決於右邊是哪一類值。JavaScript 的值分成兩大類：

  • 原始值（primitive）：string、number、bigint、boolean、undefined、null、symbol 七種。原始值本身不能被修改，'拿鐵'.toUpperCase() 是產生新字串，原本的字串沒變。
  • 物件：其他全部，包括陣列、函式、Date、Map、Set。訂單、購物車、顧客資料都是物件。

兩類值最大的差別出現在指定（=）的時候。原始值像寫在便條上的價錢：let b = a 是抄一張新便條，之後改 b，a 那張便條不受影響。物件不一樣：物件本身放在記憶體的某個地方，變數拿到的只是一張置物櫃號碼牌，上面寫著櫃子在哪裡。const same = cart 不會做出第二個購物車，只是多印一張同號碼的牌子，兩張牌打開的是同一個櫃子。

這個「物件在哪裡」的號碼，叫做參考（reference）。之後說「兩個變數參考同一個物件」，意思就是兩張號碼牌寫著同一個號碼。

JavaScript 為什麼要這樣設計？物件可能很大（一張訂單帶著幾十筆明細），每次 = 都整份複製，既慢又耗記憶體；而且很多時候你本來就希望大家看的是同一份資料。代價是：只要有兩個地方拿著同一張號碼牌，任何一邊改了內容，另一邊都會看到。這就是開場那幾個怪現象的共同根源。

在程式裡要分辨一個值屬於哪一類，可以用 typeof，但它有兩個例外（例如 typeof null 也是 'object'），對照表放在課末。

回到事故：same.items.push 會改到 cart，是因為兩個變數拿著同一張號碼牌。但折扣函式裡沒有寫 =，它只是收了一個參數。參數又是怎麼傳的？

交給函式之後呢？參數傳的也是號碼牌

呼叫函式時，參數的傳法跟 = 完全一樣：傳原始值是抄一張便條，傳物件就是把號碼牌交出去。所以函式裡改物件的內容，呼叫端拿著的那個物件也被改了。下面這格是編輯頁折扣函式的簡化版，執行後看第二行：原本的訂單也變成 171。

同一格的後半段說明了一個容易混淆的地方。order.total = … 是拿號碼牌打開櫃子、改裡面的內容，所有拿著這張牌的人都看得到；order = … 只是把函式自己手上的號碼牌換成另一張，外面的變數手上那張完全沒變。JavaScript 沒有辦法讓函式換掉呼叫端變數手上的牌子，但可以透過牌子改櫃子裡的東西。

現在可以完整解釋開場的事故了：編輯頁把列表上那張訂單物件直接交給 applyDiscount，函式改了 order.total，等於改了列表和之後要存檔的同一個物件。按「取消」只是關掉畫面，被改掉的金額不會自己變回來。

修法的方向是：函式不改參數，要改就回傳一個新物件。最小的寫法先借用展開語法（後面「按取消要能復原」那節會細講它複製到哪一層）：

function applyDiscount(order) {
  return { ...order, total: Math.round(order.total * 0.9) }   // 新物件，原訂單不動
}

這種「函式偷偷改了傳進來的資料」是很難查的 bug：呼叫的人以為只是在算折扣，結果資料庫存進去的金額也變了，而出錯的地方（存檔）離真正的原因（折扣函式）很遠。所以後端的習慣是：函式不改參數，要改就回傳新的物件。

改成回傳新物件之後，編輯頁手上同時有「原訂單」和「試算後的訂單」兩個物件。接下來的需求是：店員離開頁面前，要提示「有未儲存的修改」。這就得比較兩個物件，而比較的規則，也是由號碼牌決定的。

編輯頁怎麼判斷「有沒有改過」？=== 比的是什麼

最直覺的寫法是 edited === original。要知道它可不可靠，先看 JavaScript 判斷相等的三種方式各在比什麼。

嚴格相等（===）：型別不同就不相等，不會偷偷轉型。寬鬆相等（==）：兩邊型別不同時，先把它們轉成同一型別再比。轉型的規則很多，結果常常出乎意料，例如表單送來的空字串 '' 會跟數字 0 寬鬆相等，「沒填」和「填了 0」就分不出來。Object.is 跟 === 幾乎一樣，只在 NaN 和正負零兩個特例上不同。

下表是會讓人踩坑的組合，查表用，不用背：

所以團隊規範通常是：一律用 ===，唯一例外是 x == null。它剛好等於 x === null || x === undefined，用來判斷「沒有值」，寫起來比較短，意思也明確。

表的最後一列才是編輯頁的重點。對物件來說，=== 比的是號碼牌，問的是「是不是同一個物件」，不是「內容一不一樣」。兩個欄位完全相同的物件，只要是分別建立的，=== 就是 false。這帶來兩個結論：

  • 要判斷「是不是同一位顧客」，不能比物件本身，要自己決定比什麼，通常是比 id。測試裡要逐欄比內容，則用 deepEqual 這類工具。
  • 反過來，如果程式遵守「沒改就回傳原物件，有改才產生新物件」，=== 就變成最便宜的「有沒有改過」檢查：不用逐欄比對，比一次號碼牌就知道。後面「改數量時不碰原訂單」那節的不可變更新就是靠這一點。

=== 只能告訴你「是不是同一個」。編輯頁還缺一樣東西：一份跟原訂單完全分開的物件，店員在上面怎麼改都不影響原訂單，按「取消」時原訂單還是原樣。既然 = 只複製號碼牌，要怎麼真的複製出一份？

按「取消」要能復原：怎麼複製出真正獨立的一份？

最常見的複製寫法是展開語法 { ...order }，或等價的 Object.assign({}, order)。它們會建立一個新的外層物件，把原物件第一層的每個欄位抄過去。問題在「抄過去」的是什麼：total: 190 是原始值，抄的是便條；items 是陣列，陣列是物件，抄的還是號碼牌。所以這種複製叫淺複製（shallow copy）：只有第一層是新的，第二層以下照樣共用。

執行後看 order：total 還是 190（第一層各自一份），items 卻多了可頌（第二層共用）。

訂單的明細就在第二層，所以淺複製不夠用。編輯頁需要的是深複製（deep copy）：整棵資料，一層一層往下全部複製一份。內建的 structuredClone(x) 會這樣做，而且認得 Date、Map、Set、RegExp、Error，複製出來還是同樣的型別；連環狀參考（物件裡有屬性指回自己）也能處理。它也有限制（MDN 的 structured clone algorithm 頁面）：

  • 函式不能複製，會丟 DataCloneError。
  • 不會複製原型鏈：class 的實例會變回普通物件，instanceof 不再成立，方法也不見了（原型第 3 課會講）。
  • getter、setter 和屬性的設定（例如唯讀）不會保留；物件自己的 getter 會被讀一次，變成普通的資料欄位。

下面的範例要示範這些限制，所以先借用兩個之後才細講的語法。class Cup { … } 是建立同一種物件的樣板，new Cup('大') 做出一個實例（instance），instanceof 檢查某個值是不是用這個樣板做的（第 3 課）。try { … } catch (e) { … } 是：try 裡的程式丟出錯誤時，跳到 catch 繼續執行，e 是錯誤物件，e.name 是錯誤的種類、e.message 是說明（第 4 課）。

執行後依序看：改原訂單的數量，快照還是 1；快照裡的 Date、Set 型別都還在；Cup 實例複製後不再是 Cup；帶函式的物件直接丟錯。

網路上常見的另一種深複製是 JSON.parse(JSON.stringify(x))：先把物件轉成 JSON 字串，再解析回物件。字串裡沒有號碼牌，解析回來當然是全新的一份，看起來很合理。問題是 JSON 只有字串、數字、布林、null、陣列、物件這幾種型別，其他型別在轉成字串時就變了樣，解析回來也回不去。執行後看 orderedAt 的型別與 note 欄位：

需要深複製時用 structuredClone。JSON.parse(JSON.stringify(x)) 會把 Date 變字串、讓 undefined 欄位消失、把 Map 和 Set 變成 {}，遇到 BigInt 直接丟錯。它真正的用途是「把資料送出去再收回來」，例如 API 的請求與回應。
💡 實務上：深複製最常用在「留一份原樣」
編輯表單是典型場景：從 API 拿到訂單後，structuredClone 一份給表單改，使用者按「取消」就丟掉，按「儲存」才送出，要判斷「有沒有改過」也能拿原樣來比。常見的坑是 Vue 的 reactive 與 Pinia 狀態其實是 Proxy（包在原物件外面、攔截讀寫的一層），直接交給 structuredClone 會丟出 DataCloneError，要先用 Vue 的 toRaw 取出原始物件。資深的人會先問：真的需要整棵複製嗎？大部分更新用下一節的不可變更新就夠了，對大量資料反覆深複製只會拖慢畫面。

改數量時不碰原訂單：只複製有變的那條路

快照解決了「取消」，但編輯頁上店員會一直改：把拿鐵改成 3 杯、加一個可頌、調整排序。如果每改一次就 structuredClone 整張訂單，不只浪費，還會讓前面「編輯頁怎麼判斷有沒有改過」那節用 === 判斷有沒有改過的那招失效：每次都是全新的物件，連沒改的明細也全換了號碼牌，看不出到底哪裡變了。

先把兩種改法分清楚。直接改物件本身，例如 order.total = 171、items.push(x)，叫變更（mutation）。不改原物件、產生一個改好的新物件，叫不可變更新（immutable update）。開場的事故就是變更造成的。為什麼值得多花幾行寫不可變更新？

  • 同一個物件常被很多地方共用：快取裡的資料、Vue 父元件傳給子元件的 props、Pinia 的狀態。有人直接改，別的地方就出現「沒人改它，它卻變了」，而且查不出是誰改的。
  • 不改原物件，就能用 === 一眼判斷「有沒有變」：沒變就是同一個物件，有變就是新物件。很多快取與畫面更新的機制都靠這一點省下工作。

不可變更新不等於深複製。改一筆明細的數量時，只有「從外層走到被改的那筆明細」這條路上的物件需要換新：外層訂單、items 陣列、被改的那筆明細。其他明細沒變，新訂單直接沿用原本的物件（同一張號碼牌）。這叫結構共享（structural sharing），比整個 structuredClone 省記憶體也省時間，而且沒變的部分 === 仍然成立。

排序除了會改原陣列，還有兩個陷阱。第一，沒給比較函式時，sort 會把元素轉成字串再比，所以 10 會排在 9 前面。第二，比較函式必須回傳數字：負數表示 a 在前、正數表示 a 在後、0 表示維持原順序。回傳 true／false 是錯的：false 會被當成 0、true 當成 1，「a 比 b 小」永遠不會得到負數，排出來的結果依瀏覽器而定，在 Chrome 裡常常完全沒動。從 ES2019 起，sort 保證比較結果為 0 的元素維持原本的順序（稱為穩定排序），所以價格相同的商品不會被打亂。執行後看四行輸出：字串排序的錯誤結果、正確結果、原陣列沒動、回傳布林值時沒排序。

寫到這裡，你可能會想：與其每次小心翼翼地不去改，能不能直接把原訂單鎖起來？常見的第一個念頭是 const，但 const 不代表不可變。const 只是「這個變數不能重新指定」：號碼牌不能換，櫃子裡的東西照樣可以改。Object.freeze(obj) 才會讓物件本身不能改，但它只凍一層，第二層的陣列或物件還是改得動。這裡的範例跑在第 1 課講過的嚴格模式，所以改凍結的物件會丟錯，不是默默沒改：

💡 實務上：共用的資料不要改，自己的區域變數可以改
Pinia 的狀態、父元件傳下來的 props、快取裡的物件，都有很多地方在看，改它們一律產生新物件。Vue 在開發模式下會對直接重新指定 props 發出警告，但改 props 物件裡面的內容不會警告，這是最容易漏掉的地方。反過來，函式裡自己剛建立、還沒交給別人的陣列，用 push 組資料完全沒問題，不必為了「不可變」每一步都展開複製。巢狀很深、展開寫到很冗長時，團隊常用 Immer 這類套件，用看起來像直接修改的寫法產生新物件。code review 看到 sort、splice 或 arr[i] = 作用在參數或 store 的資料上，要停下來問：這份資料還有誰在用？

列表要合併顧客資料：Map、Set 怎麼認「同一個」，怎麼查得快？

編輯頁修好了，回到訂單列表。訂單 API 只給 customerId，顧客名字在另一支 API；有些訂單資料是從兩個來源合併的，同一位顧客可能是兩個內容相同、但分別建立的物件。要把名字合上去、要列出「不重複的顧客」，就會用到兩個內建的集合：Map 是「鍵 → 值」的對照表，Set 是不重複的集合。

它們怎麼判斷兩個鍵是「同一個」？規則叫 SameValueZero：跟 === 一樣，物件看的是號碼牌而不是內容；唯一的差別是 NaN 等於 NaN。所以前面比較 === 那節的結論在這裡原封不動地成立：內容一樣的兩個物件，在 Map 和 Set 裡是兩個不同的鍵。執行後看：用另一個 { id: 1 } 拿不到值；兩位王小明丟進 Set 還是 2 位；改用 id 當鍵，才變成 1 位。

這格最後一行比較了陣列的 includes 和 indexOf 找 NaN 的差別，原因見課末。

去重的關鍵是「自己選鍵」：要依什麼判斷同一位顧客，就拿那個原始值（通常是 id）當鍵。Map 的另一個用途是查詢速度。把顧客名字合到每張訂單上，直覺寫法是在每張訂單裡對顧客陣列 find。陣列的 find、includes 是從頭一筆一筆比，比到找到為止；Map 則是先建一份「鍵 → 資料」的索引（index），查詢時用 Map.get、Set.has 直接拿，不管裡面有幾筆，幾乎都是直接查到。為什麼不用一筆一筆比？Map、Set 內部用雜湊表（hash table）存放：放入時依鍵算出一個位置，查詢時用同一個鍵算出同一個位置直接去拿，不用從頭比，所以查一筆的平均成本不會隨筆數變多（規格只要求平均查詢時間低於線性，所以說「平均」）。

差別有多大，用時間複雜度來描述：資料量變成 n 倍時，工作量變成幾倍，常寫成大 O（big O）。一萬張訂單、每張都在一萬位顧客的陣列裡 find，平均每次比五千次，總共約五千萬次，這是 O(n²)：資料量多 10 倍，工作量多 100 倍。先建 Map 只要一萬次放入加一萬次查詢，這是 O(n)：資料量多 10 倍，工作量也只多 10 倍。執行後比較兩行印出的次數：

💡 實務上：合併兩份 API 資料時先建 Map
咖啡店後台的訂單列表常見這種寫法：一支 API 拿訂單、另一支拿顧客，再把顧客名字合到每張訂單上。在 orders.map 裡對顧客陣列 find，測試資料幾十筆沒感覺，正式資料一多畫面就卡；先 new Map(customers.map(c => [c.id, c])) 再查，幾乎沒有成本，可以當成習慣。但資深的人會多問一句：前端為什麼要拿到全部顧客？通常應該由後端用 JOIN 一次回傳，或分頁只拿這一頁需要的資料。

收據快取越長越大：物件什麼時候才會被回收？

索引用的 Map 在函式結束後就沒人用了，但後端常把 Map 放在模組最外層，當成整個程序共用的快取。這時要問：Map 裡的東西什麼時候會被清掉？

JavaScript 會自動回收記憶體，這叫垃圾回收（garbage collection，GC）：一個物件只要沒有任何地方參考它（沒有任何人拿著它的號碼牌），記憶體就會在之後某個時間被收回。反過來說，只要還有一張號碼牌在某人手上，物件就一直活著。放進 Map 的東西，Map 本身就拿著它的號碼牌。

後端最常見的記憶體問題就長這樣：在模組最外層放一個 Map 當快取，每個請求都往裡面放東西，卻從來不刪。瀏覽器分頁關掉記憶體就釋放了，但伺服器程序一跑就是好幾天，這個 Map 會一直長大，直到記憶體用完。

// 每個請求都放一筆，從不刪除：記憶體只會一直變大
const cache = new Map()
function getReceipt(order) {
  if (!cache.has(order.id)) cache.set(order.id, renderReceipt(order))
  return cache.get(order.id)
}

修法有兩種方向。一種是幫快取設上限或過期時間（之後的課會用到）。另一種適用於「資料跟著某個物件走」的情況，例如收據跟著訂單物件：改用 WeakMap。它的鍵必須是物件，而且 WeakMap 拿著鍵的號碼牌不算數：鍵物件沒有別人參考時照樣會被回收，對應的值也一起消失。代價是 WeakMap 不能列出全部內容、也沒有 size。第 24 課做裝飾器的 metadata 會用到它。執行後看：收據照常查得到，而 receipts.size 是 undefined。

怎麼用工具找出記憶體一直長大的地方，在 Node 課第 23 課。

💡 實務上：程序裡的快取先決定上限與過期
Node 服務最常快取的是商品清單、店家設定這類讀多寫少的資料，放在模組層級的 Map 很方便。上線前要先回答三個問題：最多放幾筆、多久過期、資料改了怎麼讓快取失效。自己寫容易漏，通常直接用 lru-cache 這類成熟套件設定 max 與 ttl。另外，服務部署成多個容器時，每個程序各有一份快取、彼此不同步；需要共用或一改就要全部生效時，就該改用 Redis 這類外部快取。

練習

練習 1：addItem(order, item) 目前直接把品項 push 進 order.items，還改了 order.total。改寫成回傳一張新訂單（新品項加在最後、total 加上 price × quantity），原訂單和它的 items 完全不變。

練習 2：changeQuantity(order, productId, quantity)：回傳新訂單，只把該商品的數量改掉並重算 total。

  • 沒變的明細要沿用原本的物件（=== 相同），只有被改的那一筆是新物件。
  • 找不到 productId，或數量跟原本一樣時，什麼都沒變，直接回傳原本的 order，呼叫端才能用 === 判斷有沒有變。

練習 3：uniqueCustomers(orders)：訂單是從兩支 API 合併來的，同一位顧客可能是兩個不同的物件。依第一次出現的順序，回傳不重複的顧客（以 id 判斷），保留第一次出現的那個物件。訂單可能有上千筆，要用 O(n) 的寫法。

練習 4：snapshotOrder(order)：在修改訂單之前，先做一份「復原用」的快照。訂單裡有 orderedAt（Date）、items（陣列，裡面是明細物件）與 tags（Set）。之後不管怎麼改原訂單，快照都不能跟著變；而且快照裡的 Date 要還是 Date、Set 要還是 Set。

練習 5：sortByPrice(products)：回傳依價格由低到高排好的新陣列，價格相同時保留原本的順序；傳進來的陣列不能被改到。

練習 6：執行完下面的程式，a.price 是多少？

const a = { price: 80 }
const b = a
b.price = 90

✓ const b = a 複製的是參考（號碼牌），a 和 b 打開的是同一個物件，從哪邊改都一樣。const 只擋「重新指定變數」，不擋改物件的內容。要複本得自己寫 { ...a } 或 structuredClone(a)。

練習 7：下面印出什麼？

const s = new Set()
s.add({ id: 1 })
console.log(s.has({ id: 1 }))

✓ Set 和 Map 比對鍵時看參考，兩個 { id: 1 } 字面值是兩個不同的物件。Set 可以放物件，只是要用同一個物件才查得到。要依內容去重，就自己選鍵，例如 new Set(list.map(c => c.id))。

練習 8：const menu = ['拿鐵'] 之後執行 menu.push('可頌')，會怎樣？

✓ const 只讓變數不能重新指定（menu = [] 才會錯），陣列本身照樣可以改。要讓陣列不能改得用 Object.freeze(menu)，這時在嚴格模式下 push 會丟 TypeError；但 freeze 只凍一層，陣列裡如果放的是物件，那些物件還是改得動。

常見錯誤

  • 函式偷偷修改傳進來的參數：呼叫的人不知道資料被改了。不改參數，回傳新物件。
  • 以為 { ...order } 是完整複製：只複製第一層，巢狀的陣列和物件還是共用。要改哪一層，就展開到哪一層；要整份獨立就用 structuredClone。
  • 用 JSON.parse(JSON.stringify(x)) 深複製：Date 變字串、undefined 欄位消失、Map／Set 變 {}、BigInt 直接丟錯。
  • arr.sort() 改到原陣列，還把數字當字串排：要新陣列用 toSorted，數字一定要給 (a, b) => a - b。
  • 比較函式回傳布林值：(a, b) => a.price > b.price 不會正確排序，要回傳數字。
  • 用 x === NaN 判斷 NaN：永遠是 false，用 Number.isNaN(x)。
  • 用物件當 Map／Set 的鍵，期待「內容一樣就是同一個」：它們看參考。依內容判斷時，自己選一個原始值當鍵（例如 id）。
  • 在迴圈裡對另一個大陣列 find／includes：O(n²)，資料一多就慢。先建 Map 或 Set 索引。
  • 模組層級的 Map 當快取卻從不刪除：伺服器跑越久記憶體越大。設上限或過期時間，或用 WeakMap 讓資料跟著物件一起被回收。

補充與查表

typeof 的結果：typeof 回傳值的型別名稱字串，有兩個例外要記（null 和函式），另外陣列也回 'object'，要用 Array.isArray 判斷。查表用，不用背：

運算式結果說明
typeof 80'number'
typeof '拿鐵''string'
typeof 10n'bigint'大整數，第 5 課會用
typeof undefined'undefined'
typeof null'object'歷史包袱，null 不是物件。判斷 null 要寫 x === null
typeof [1, 2]'object'陣列也是物件。判斷陣列用 Array.isArray(x)
typeof (() => 1)'function'函式是物件，但 typeof 特別回傳 function

不改原陣列的新方法：toSorted、toReversed、toSpliced、with 是 ES2023 加入的，Chrome 110、Firefox 115、Safari 16、Node 20 起支援。

includes 與 indexOf 找 NaN：陣列的 includes 跟 Map、Set 一樣用 SameValueZero，所以找得到 NaN；indexOf 用 ===，所以找不到 NaN。

Map 還是普通物件：兩者都能當對照表。Map 的鍵可以是任何型別（物件、數字不會被轉成字串）、保留放入的順序、有 size，而且使用者提供的鍵不會撞到 __proto__ 這類特殊名稱（第 3 課講原型時會看到這有多危險）。普通物件的好處是可以直接轉成 JSON。資料是「任意的鍵、會一直增減」時用 Map；資料是「欄位固定的一筆紀錄」時用普通物件。

小結

  • 原始值指定時複製值本身；物件指定或傳參數時複製的是參考（號碼牌），兩邊看到同一個物件。開場的事故就是折扣函式透過參數改到了原訂單。
  • 函式不改參數，要改就回傳新物件。
  • 比較一律用 ===，只有 x == null 例外；NaN 用 Number.isNaN；物件的 === 比的是「是不是同一個」，判斷同一筆資料要自己選鍵（例如 id）。
  • 展開和 Object.assign 是淺複製；structuredClone 是深複製，適合「取消」要用的快照，但不能複製函式、會丟掉 class 的原型；JSON 往返會遺失型別。
  • 不可變更新只複製有變的那條路，其他部分沿用（結構共享），所以能用 === 判斷有沒有變；排序用 toSorted 並回傳數字。
  • const 不等於不可變，Object.freeze 只凍一層。
  • Map、Set 用 SameValueZero：物件看參考。依內容去重自己選鍵；查詢多的時候先建 Map 索引，把 O(n²) 變成 O(n)。
  • 沒人參考的物件才會被回收；只進不出的快取會讓記憶體一直長大，要設上限與過期，或用 WeakMap。
