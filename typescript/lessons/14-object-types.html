階段 3：型別基礎 · 第 14 課

物件型別：type、interface 與結構型別

咖啡店後台上週上架新品「抹茶拿鐵」，前台菜單卻顯示「抹茶拿鐵 undefined 元」。追下去發現，後台的「新增商品」是用 JavaScript 寫的，同事呼叫 addProduct({ name: '抹茶拿鐵', pirce: 130 })，把 price 拼成了 pirce。JavaScript 不知道商品「應該」有哪些欄位，這個物件照樣存進去，等到菜單讀 price 才拿到 undefined。

後端程式整天在搬物件：從資料庫讀出一筆顧客、組成 API 回應、收下前端送來的訂單。這一課的任務是把咖啡店後台會用到的資料（商品、顧客、訂單、庫存、會員）一一寫成 TypeScript 型別，讓上面這種錯在存檔當下就畫紅線。過程中你也會看到型別擋不住哪些錯，那些地方要靠別的方法守住。學完你能：

  • 用 type 或 interface 描述物件，分清楚 ? 和 | null
  • 說出為什麼多打一個欄位有時會被抓、有時不會
  • 描述鍵不固定的物件（庫存表），並處理找不到的鍵
  • 組合型別，為團隊選定 type 或 interface
這課的路線：
  1. 商品長什麼樣子：用 type 或 interface 替物件的形狀取名字，少寫 price 當場報錯（開場問題的最小答案）；snake_case 欄位怎麼變成 camelCase 屬性。
  2. 顧客的電話可能是空的，主鍵不該被改：資料庫允許 NULL 的欄位該寫 ? 還是 | null，readonly 擋得住什麼、擋不住什麼。
  3. 拼錯的 pirce 為什麼有時抓得到、有時抓不到：TypeScript 怎麼判斷兩個物件型別相容（結構型別），以及只抓當場寫的物件的多餘屬性檢查。
  4. 庫存表的鍵事先不知道：索引簽章與 Record 怎麼寫，找不到的鍵怎麼處理。
  5. 會員是「顧客加上點數」：用 extends 或 & 組合，不重抄欄位；最後決定團隊統一用 type 還是 interface。
這課會用到：
  • 第 13 課的型別註記與推論：型別寫在名稱後的冒號之後，沒寫的由 TypeScript 從值推論；錯誤附有代碼，像 TS2322。
  • PostgreSQL 課第 2 課的表、欄位、主鍵：一張表由欄位組成，主鍵是每一列不重複的編號（像 id）。
  • PostgreSQL 課第 13 課的 NULL：欄位允許 NULL 時，那一列還是有這個欄位，只是值是空的。

第一步：商品長什麼樣子？替物件的形狀取名字

開場的錯之所以溜過去，是因為程式裡沒有任何地方寫下「商品應該有 name 和 price」。要讓 TypeScript 幫你檢查，第一步就是把這個形狀寫出來。描述「一個物件有哪些屬性、各是什麼型別」的型別叫物件型別（object type）。第 13 課你已經在參數上直接寫過 { name: string; price: number }，那就是一個物件型別。

直接寫在參數上的問題是：同一個形狀在新增商品、修改商品、列出菜單的函式裡都會用到，每個地方重寫一次，哪天商品多一個欄位，就要找出所有地方一起改，漏一處就不一致。所以要替形狀取一個名字，之後各處都用這個名字。TypeScript 有兩種取名的寫法：

  • 型別別名（type alias）：type Product = { … }。type 可以替任何型別取名字，物件只是其中一種。
  • 介面（interface）：interface Product { … }。專門用來描述物件的寫法，沒有等號。

拿 PostgreSQL 課的 products 表來寫。資料表的欄位名稱慣例是 snake_case（is_available），TypeScript 的屬性慣例是 camelCase（isAvailable），兩邊的名稱不會自動對上：轉換由存取資料庫的那一層負責，例如 Prisma 在 schema 用 @map("is_available") 宣告程式裡的 isAvailable 對應哪一欄（NestJS 課第 14 課）。本課的型別描述的是轉換之後、程式裡看到的 camelCase 物件。下面這格用 type 寫商品、用 interface 寫顧客，執行後看印出的上架商品名稱：

現在回到開場。把 latte 那一行的 price: 110 刪掉，latte 底下會出現紅線，錯誤代碼是 TS2741，訊息說 Product 要求的 price 不見了。開場的 { name: '抹茶拿鐵', pirce: 130 } 正是少了 price 的物件，只要 addProduct 的參數標上商品的型別，存檔當下就會被擋下。實際傳進去時，TypeScript 會先指出「多了 pirce，你是不是要寫 price」（TS2561），而不是 TS2741；為什麼會這樣，第三節再說明。這就是本課問題的最小答案：把形狀寫成型別，TypeScript 就能拿它比對每一個物件。

這一格裡 type 和 interface 效果完全一樣，兩者的差別要等學完組合型別才看得清楚，留到最後一節。屬性之間可以換行，也可以用分號或逗號分隔，課程統一用換行。

物件也可以包物件。後台的「訂單明細」頁要把一張訂單連同它的明細一起回傳給前端；資料庫裡 order_items 用外鍵指向 orders（PostgreSQL 課第 8 課），到了 TypeScript，就是一個訂單物件裡有一個明細陣列。屬性的型別可以是另一個物件型別，型別也就跟著巢狀。執行後看印出的金額，是明細逐筆加總出來的：

💡 實務上：先問「這個型別描述的是哪一側的資料」
後端從資料庫讀出的 orderedAt 是 Date，但同一筆資料變成 JSON 送到前端之後是字串（第 6 課）。常見的坑：前端把後端的 OrderWithItems 型別直接拿來用，寫了 order.orderedAt.getTime()，型別檢查通過，畫面一打開就噴錯。所以「資料庫那一側的型別」和「API 那一側的型別」通常分開寫，之後的課會這樣做。Code review 看到一個型別被前後端共用時，先確認裡面有沒有 Date 這類經過 JSON 會變樣的欄位（bigint 更糟，JSON.stringify 直接丟錯）。

商品和訂單的每個欄位都一定有值，寫起來很直接。下一張表就沒這麼單純：顧客不一定留電話，資料庫裡的 phone 欄位允許 NULL。「可能沒有值」在型別裡要怎麼寫？

顧客的電話可能是空的：該寫 ? 還是 | null？主鍵怎麼防止被改？

customers 表的 phone 欄位允許 NULL，也就是說查出來的某些顧客，phone 的值是空的。TypeScript 裡有兩種寫法看起來都像「可能是空的」，意思卻不一樣，差別在於「屬性在不在」：

寫法意思用在哪裡
phone?: string可選屬性（optional property）：這個屬性可以不存在，讀出來是 string | undefinedAPI 輸入「可以不傳」，例如更新顧客時只傳要改的欄位
phone: string | null屬性一定在，值可能是 null資料庫的 NULL：SELECT 出來的每一筆都有 phone 這一欄，只是值是空的

為什麼要分這麼細？因為 JavaScript 裡「沒有這個屬性」和「屬性在、值是 null」是兩件事：前者讀出來是 undefined，後者讀出來是 null，=== undefined 和 === null 的判斷結果不同。資料庫查出來的一筆顧客永遠有 phone 這一欄，所以是第二種。下面這格同時寫了「資料庫讀出來的一筆」和「更新時傳進來的資料」，執行前先看第三行 bad 的紅線：

bad 報 TS2741：CustomerRow 說 phone 一定在，bad 卻沒有。這正是我們要的保護：從資料庫組出顧客資料時，忘了帶 phone 會當場被抓。反過來 patch 只有 phone 沒有 name，卻沒有錯，因為 CustomerPatch 的屬性全部是可選的。

如果把資料庫的 NULL 寫成 phone?: string 會怎樣？型別說的是「可能沒有這個欄位，或是 undefined」，不包含 null，但資料庫給你的是 null。結果寫 { id: 6, name: '黃淑芬', phone: null } 反而報錯，而程式裡用 phone === undefined 判斷「沒有電話」，永遠抓不到資料庫給的 null，沒電話的顧客會被當成有電話處理。

💡 實務上：更新 API 要分清「沒傳」和「傳 null」
咖啡店後台的「編輯顧客」表單送出 PATCH /customers/6：沒傳 phone 代表「不改」，傳 phone: null 代表「把電話清掉」。兩件事意思完全不同，所以上面的 CustomerPatch 寫成 phone?: string | null。後端如果用 if (!patch.phone) 一起判斷，顧客就永遠清不掉電話。設計 API 時先跟前端說好這個約定，寫進 API 文件，比事後查 bug 省事得多。

到這裡，型別已經能說清楚每個欄位「可能是什麼值」。還有一類錯不是值不對，而是不該動的東西被動了。主鍵 id 由資料庫產生，是這一列的身分；程式裡如果有人把它改掉，之後拿這個物件去更新資料庫，就會改到別筆資料。在屬性前面加 readonly，這個屬性就不能被重新指定。執行前先看哪幾行有紅線，執行後看印出的 id 和 tags：

只有 latte.id = 99 報錯，TS2540。但執行結果是 id: 99，tags 也多了「冰」。兩行都在執行時生效了，原因有兩個。第一個是 readonly 只在編譯時檢查：第 13 課說過，型別在執行前會被擦掉，readonly 也是型別的一部分，擦掉之後什麼都不剩。紅線提醒你寫錯了，但程式照樣執行，執行時沒有任何東西擋住修改。

第二個是 readonly 只管一層：它管的是「tags 這個屬性不能換成別的陣列」，不管陣列裡面的內容，所以 push 不會畫紅線。這跟第 2 課的 Object.freeze 一樣，巢狀的陣列和物件照樣改得動。

所以 readonly 的定位是「寫程式時的提醒」：團隊裡沒人會不小心改到 id。要讓執行時真的改不動，還是要靠 freeze，或乾脆用不可變更新，也就是不改原物件、做一個新物件（第 2 課）。

到這裡，商品、顧客、訂單的每個欄位都有型別了，少寫欄位會被抓。但開場的 pirce 不只是「少了 price」，它還「多了 pirce」。如果同事兩個都寫了，或者物件不是當場寫的，而是從別處傳進來的，TypeScript 還抓得到嗎？要回答這個問題，得先知道 TypeScript 怎麼判斷一個物件「放得進」某個型別。

拼錯的 pirce 為什麼有時抓得到、有時抓不到？

先看 TypeScript 判斷相容的基本規則。把一個值放進某個型別的位置，例如指定給有型別的變數、傳給有型別的參數，TypeScript 會檢查這個值放不放得進去，放得進去就叫可指派（assignable）。它檢查的方式是只看形狀，不看型別叫什麼名字：位置要求的屬性，值都有，而且型別都對，就可以放進去；值多出來的屬性不影響。這種規則叫結構型別（structural typing）。

可以想成咖啡店的杯架：杯架只在乎杯子的尺寸放不放得進去，不在乎杯子是哪個牌子。舉個後台的例子：有一個問候顧客的函式 greet，參數要求 name 和 phone。店員資料 Employee 的型別名字不叫 Customer，還多了一個 role，傳進去行不行？

執行下面這格，確認沒有紅線、問候正常印出：

沒有錯。greet 要求 name 和 phone，mei 兩個都有、型別也對；多出的 role greet 根本不會讀，對它沒有任何影響，所以 TypeScript 放行。你在 Vue 裡把一個大物件傳給只要其中幾個欄位的 props，也是同一個規則。

為什麼特別強調「不看名字」？因為 Java、C# 這類語言用的是另一種規則，叫名目型別（nominal typing）：型別名字不同就不相容，就算欄位一模一樣也一樣。TypeScript 不是這樣，Customer 和 Employee 名字不同，照樣可以互傳。有時你會希望「名字不同就不能混用」，例如顧客 id 和商品 id 都是 number，不該互相傳錯，第 27 課會講怎麼做。

這個規則對開場的問題是個壞消息：既然多出的屬性不影響相容，多了一個拼錯的 pirce 也不影響。只要物件同時有正確的 price，pirce 就只是一個「多出的屬性」，照規則會被放行。

多餘屬性檢查：當場寫的物件才會被抓

如果結構型別是唯一的規則，拼錯欄位名稱的錯幾乎都會溜過去。所以 TypeScript 另外加了一條規則，叫多餘屬性檢查（excess property check），專門抓打錯字。它只在一種情況生效：物件是新鮮的物件字面值（fresh object literal），也就是用大括號當場寫在指定或傳參數的位置，還沒先放進變數的物件。這時物件多出型別沒有的屬性，就會報錯。

為什麼只抓當場寫的物件？因為當場寫的物件沒有別人在用，它唯一的用途就是放進這個位置，多出的屬性永遠不會被讀到，幾乎一定是打錯字。先放進變數的物件就不同了，那個變數可能還在別處被使用，多出的屬性也許是有用的（像前面 Employee 的 role），TypeScript 不能把它當錯。下面這格用的是開場的情境，執行前先看兩次呼叫各有沒有紅線：

第一次呼叫有紅線：當場寫的字面值多了 pirce、少了 price，被抓。第二次呼叫沒有紅線：draft 先放進變數，有正確的 price，多出的 pirce 不影響形狀。要記住的是，多餘屬性檢查只是「幫你抓打錯字」的額外保護，不是型別相容的規則本身；相容與否，還是由結構型別決定。錯誤代碼與版本的細節見課末。

回到開場：addProduct({ name: '抹茶拿鐵', pirce: 130 }) 是當場寫的字面值，有了型別就會被抓；但如果物件同時有正確的 price 和拼錯的 pirce，又是先組成變數、或從前端的請求內容拿到的，多出的 pirce 就不會報錯；而從外部進來的資料，連少了 price 都要等執行時才知道。從外部進來的資料，型別檢查不了，得在執行時驗證（第 26 課）。

💡 實務上：型別擋不住「多回傳了欄位」
假設 staff 表有 password_hash，查出來的那一筆直接 res.json(row)，就算函式的回傳型別寫成沒有密碼欄位的 StaffDto（DTO：專門給 API 回傳用的型別），TypeScript 也不會報錯：多了屬性照樣相容，密碼雜湊就這樣送到前端。這是真實會發生的資料外洩。資深工程師的習慣是回傳時明確挑欄位，例如 { id: row.id, name: row.name }，或查詢時只 SELECT 需要的欄位，而不是把整筆資料丟出去。

到這裡，欄位固定的物件都寫得出來，也知道型別在哪裡擋得住錯、在哪裡擋不住。但後台還有一份資料不是這種形狀：各商品的庫存表。它的鍵是商品 id，商品有幾個鍵就有幾個，沒辦法在型別裡一個個列出來。

庫存表的鍵事先不知道：索引簽章與 Record

前面的物件型別都是把每個屬性名稱寫死：id、name、price。庫存表 { 1: 12, 2: 0, 5: 8 } 的鍵卻是資料：商品 1 有 12 個、商品 5 有 8 個，明天上架商品 7，就多一個鍵 7。寫型別時你不知道會有哪些鍵，只知道「鍵是商品 id（數字），值是庫存（數字）」。

描述這種物件的寫法叫索引簽章（index signature）：{ [productId: number]: number }，讀作「任何數字鍵，對應的值都是數字」。方括號裡的 productId 只是給人看的名字，換成別的名字意思一樣。TypeScript 也內建了一個等價的寫法 Record<K, V>，意思是「鍵是 K、值是 V 的物件」，Record<number, number> 就是同一個型別，比較好讀，課程之後多用 Record。執行後看三個值，並把滑鼠移到 matcha 上看它的型別：

印出 8 undefined NaN。商品 42 不在庫存表裡，stock[42] 執行時是 undefined，但滑鼠移上去，型別卻說是 number；matcha + 1 算出 NaN，TypeScript 和執行時都沒有任何錯誤。

原因是索引簽章只說「有的話，值是 number」，沒說「每個鍵都有」。在預設設定下，TypeScript 讀索引簽章或 Record 的值時，不會把 undefined 加進型別。這跟開場的事故是同一種症狀：型別說有值，執行時拿到 undefined，一路算下去才出錯。所以這條要記住：讀索引簽章或 Record 的值時，型別裡沒有 undefined，找不到的情況要自己處理。第 25 課的 noUncheckedIndexedAccess 選項會讓讀出來的型別變成 number | undefined，逼你處理。

練習 3 要處理的就是這件事。找不到時給 0，用的是空值合併（nullish coalescing）a ?? b：a 是 null 或 undefined 時改用 b，a 是 0 時照樣用 0。所以 stock[id] ?? 0 只在找不到時給 0，「庫存是 0」不會被當成「找不到」；寫成 || 結果在這裡剛好也是 0，但 || 會把 0、空字串都當成沒有值，換到其他預設值時就會出錯。

補貨時不能改到傳進來的庫存表，要用第 2 課的不可變更新 { ...stock, [id]: n }，複製一份 stock 再改其中一個鍵，不動原物件。方括號裡的 [id] 叫計算屬性名稱（computed property name），表示用變數 id 的值當鍵，不是叫做 id 的鍵。

鍵不固定的資料，也可以用第 2 課的 Map 存。什麼時候選物件、什麼時候選 Map，見課末。

到這裡，四張表和庫存都有型別了。接下來後台要加會員功能：會員就是顧客，再多點數和入會日。最直接的做法是把 Customer 的欄位抄一份再加兩個，但這正是第一節想避免的「同一個形狀寫好幾次」。

會員是顧客加上點數：怎麼不重抄欄位？

為什麼不能抄？假設 Member 把 Customer 的 id、name、phone 抄過去。之後 customers 表加了 city 欄位，有人改了 Customer，卻沒想到 Member 也要改，會員資料就少了 city，而 TypeScript 不會提醒你，因為兩個型別彼此沒有關係。要讓 Member 跟著 Customer 一起變，就要在型別裡寫明「Member 是從 Customer 來的」。有兩種寫法，執行後確認 m2 讀得到 name 和 points：

interface 的寫法是 interface Member extends Customer，意思是「Member 有 Customer 的全部屬性，再加上這裡寫的」。type 的寫法是 Customer & { points: number }，叫交集型別（intersection type）：A & B 的意思是「同時是 A 也是 B」，一個值要同時符合兩邊，就得有兩邊的全部屬性。

兩者在這裡的結果一樣，所以 m2: Member2 = m 能互相指派（結構型別：形狀一樣就相容）。Customer 之後多了欄位，兩種寫法的 Member 都會自動跟著有，練習 4 會檢查這一點。

差別出現在兩邊的屬性衝突時。假設有人想做「訪客」，沿用 Customer 但把 name 改成數字編號。執行前先看哪一行有紅線：

extends 在宣告的地方就報 TS2430：Guest 宣稱自己是一種 Customer，name 卻改成 number，跟 Customer 不相容，當場指出問題。& 在宣告時沒報錯，它把兩邊的 name 合在一起：name 要同時是 string 也是 number，世界上沒有這種值，結果就是 never，也就是「沒有任何值的型別」（第 15 課會講）。宣告不會錯，等到真的要建立 Guest2 的值時，name: 1 放不進 never，才在使用的地方報錯。錯誤離真正的原因很遠，比較難查。這是 TypeScript Handbook 列出的兩者主要差別。

既然 type 和 interface 都能描述物件、都能組合，只在衝突時表現不同，團隊寫新程式時該統一用哪一種？

團隊該統一用 type 還是 interface？

第一節說差別留到最後。現在你已經看過兩者的組合方式，可以把差別整理成一張表：

typeinterface
描述物件可以可以
聯合 'S' | 'M' | 'L'、tuple、型別運算可以不行，interface 只能描述物件
組合&，衝突時變成 neverextends，衝突時當場報錯
同名宣告兩次報錯 TS2300宣告合併：自動合在一起

第二列的聯合 'S' | 'M' | 'L' 表示「只能是這三個值之一」，下一課會正式教；這裡只要知道它不是物件，所以只能用 type 寫。型別運算指的是用 keyof、條件型別這類寫法從既有型別算出新型別，第 20–22 課會教，結果不一定是物件，所以也只能用 type。

最後一列需要多解釋。宣告合併（declaration merging）指的是：同名的 interface 寫兩次，TypeScript 不會報錯，而是把兩次的屬性合成一個 interface。type 不行，同名寫兩次就是重複宣告。這個功能有正當用途：第 25 課會用它擴充別人套件的型別，例如幫 Express 的 Request 加上 user 屬性，不用改套件的原始碼。反過來看，它也代表你的 interface 可能在別的檔案被加了欄位，而你看原本的宣告看不出來。執行前先看 o 的紅線：

o 報 TS2741，說少了 note。只看第一個 interface Order，會以為有 id 和 total 就夠了，實際上第二個宣告把 note 合併了進來。

💡 實務上：物件型別團隊選一種，交給 lint 統一
物件型別用 type 或 interface 都可以，重點是團隊選一種、保持一致，不要讓每個人各寫各的，code review 時還要爭論。用 lint 規則（例如 typescript-eslint 的 consistent-type-definitions）自動統一，比靠人記得可靠。另外兩個情況不用選：聯合、tuple 這些只能用 type；要讓別人擴充的公開型別（例如套件提供的設定型別）用 interface，使用者才能用宣告合併加欄位。咖啡店後台的商品、顧客、訂單、會員型別，選定一種寫完就好。

回頭看開場的抹茶拿鐵。替商品寫了型別之後，當場寫錯的 pirce、漏寫的 price、把 NULL 寫成 ?、改到主鍵 id、會員漏了顧客的欄位，都會在存檔當下畫紅線。型別擋不住的也很清楚：先放進變數或從外部進來的物件多了欄位、庫存表找不到的鍵、執行時真的去改 readonly 的屬性。這些要靠挑欄位回傳、?? 0 這類處理、freeze 或不可變更新，外部資料則要在執行時驗證。

練習 1：依 PostgreSQL 課的四張表寫出型別（type 或 interface 都可以）。Customer：id（唯讀）、name、phone 和 city（資料庫允許 NULL）。Product：id（唯讀）、name、category（允許 NULL）、price、isAvailable。Order：id（唯讀）、customerId、orderedAt（Date）、total。OrderItem：orderId、productId、quantity、unitPrice。數字欄位都是 number。

練習 5：下面這段會報錯嗎？

function greet(c: { name: string; phone: string | null }) {
  return `${c.name} 您好`
}
const e = { name: '小美', phone: null, role: 'barista' }
greet(e)

✓ 多餘屬性檢查只對「當場寫的物件字面值」生效。e 先放進變數之後，只看形狀：需要的 name、phone 都有，多出的 role 不影響。b 要寫成 greet({ name: '小美', phone: null, role: 'barista' }) 才會報錯；c 是名目型別的想法，TypeScript 不看名字。

練習 6：資料庫 customers.phone 欄位允許 NULL，讀出來的顧客型別該怎麼寫？

✓ 查出來的每一筆都有 phone 這一欄，值可能是 null，所以是「屬性一定在、值可能是 null」。? 的意思是「屬性可以不存在」，讀出來是 string | undefined，不包含 null，把 null 指定進去會報 TS2322。? 適合 API 輸入「可以不傳」的欄位。

練習 7：下面哪一個只能用 type 寫，不能用 interface？

✓ interface 只能描述物件，聯合、tuple、型別運算都要用 type。a 兩者都行；b 用 interface Member extends Customer 或 type Member = Customer & { … } 都行。d 不對：除了聯合，兩者在宣告合併和衝突處理上也不同。

常見錯誤

  • 用 ? 表示資料庫的 NULL：? 是「可以沒有這個屬性」，讀出來是 undefined；資料庫給的是 null。允許 NULL 的欄位寫 string | null。
  • 以為多出的屬性永遠會被抓：只有當場寫的物件字面值會被檢查，先放進變數、或來自 API 回應的物件，多什麼都不會報錯。要擋住外部資料多出的欄位，得在執行時驗證（第 26 課）。
  • 以為 readonly 是深層的，或執行時也有效：它只在編譯時檢查，而且只管一層。執行時要真的不能改，用 Object.freeze 或不可變更新。
  • 為了讓錯誤消失加上 [key: string]: any：等於宣告「任何欄位都可以」，打錯字的保護全部沒了。正確做法是修好呼叫的地方，或把真的需要的欄位加進型別。
  • 以為型別名稱不同就不相容：TypeScript 只看形狀。Employee 和 Customer 形狀相容就能互傳，名字不同不會擋。
  • 讀 Record／索引簽章的值時，沒想過鍵不存在：型別說 number，執行時是 undefined，算下去就是 NaN。用 ?? 0 這類寫法處理找不到的情況。

補充與查表

多餘屬性檢查的錯誤代碼

多餘屬性檢查是「幫你抓打錯字」的額外保護，不是型別相容的規則本身，TypeScript Handbook 的 Object Types 一章就是這樣描述的。本課程在 TypeScript 5.9.3 和 7.0.2 實測，錯誤代碼都是 TS2353；找得到相近的屬性名稱時是 TS2561，訊息會猜你要寫哪個。

Object.keys 為什麼回傳 string[]

結構型別也解釋了一件常讓人困惑的事：Object.keys(product) 的型別是 string[]，不是 ('id' | 'name' | …)[]。因為傳進來的物件可能是形狀更大的值（像多餘屬性檢查那一格的 draft），執行時的鍵可能比型別寫的多。

鍵不固定的資料：一般物件還是 Map

什麼時候改用第 2 課的 Map？鍵會頻繁新增刪除、鍵不是字串或數字（例如物件）、需要知道筆數或保持插入順序時用 Map；要直接 JSON.stringify 送出去的資料用一般物件。

小結

  • 把形狀寫成 type 或 interface，TypeScript 就能比對每個物件，少寫欄位當場報錯；資料表的 snake_case 欄位寫成 camelCase 屬性，主鍵加 readonly。
  • ? 是「可以沒有這個屬性」，| null 是「屬性在、值可能是空」；資料庫的 NULL 對應後者，更新 API 的「沒傳」和「傳 null」要分開。
  • readonly 只在編譯時、只有一層。
  • 結構型別：只看形狀、不看名字，多出的屬性不影響相容。多餘屬性檢查只抓新鮮的物件字面值；外部進來的資料多了欄位，型別擋不住。
  • 索引簽章和 Record 描述鍵不固定的物件，讀出來的型別沒有 undefined，找不到的鍵要自己處理。
  • extends 衝突時當場報錯，& 衝突時變成 never；聯合只能用 type，宣告合併只有 interface。物件型別團隊選一種保持一致。
