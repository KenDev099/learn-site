階段 5：寫後端需要的 TypeScript · 第 24 課

裝飾器與 metadata：自己做迷你 DI

NestJS 的程式長這樣：類別上面掛 @Controller('/orders')，方法上面掛 @Get(':id')，建構子只寫 constructor(private products: ProductsService) {}，從來沒有人 new ProductsService()，物件卻自己出現了。平常這層魔法很方便，直到它壞掉：咖啡店後端的同事新增了一個 OrdersService，建構子要一個 ProductsService 和一個 Clock。Clock 是一個 interface，只規定「能取得現在時間」。結果一啟動就停在「Nest can't resolve dependencies」。他重排了 providers、改了幾次 import，錯誤還是一樣。不懂背後的機制，就只能這樣亂試。

這一課跟著這個錯誤走。我們把 Nest 啟動時做的兩件事拆開，自己用幾十行程式做出來：一是 @Get() 怎麼變成路由表，二是建構子要的物件怎麼自己出現。做完之後回頭看，那個錯誤最常見的三種原因都能從自己寫的容器裡看出來，你也會知道每一種該怎麼修。

這課的路線：
  1. @Log 到底是什麼？裝飾器就是函式，在類別定義的那一刻執行一次。順便說明 TypeScript 有兩套裝飾器，這一頁和 NestJS 用的是哪一套。
  2. @Get(':id') 帶參數，框架怎麼用它記下路由？裝飾器工廠、登記表與執行順序。到這裡可以先回答開場兩件事的一半：路由表怎麼來，以及注入需要哪份紀錄。
  3. 型別在執行時不存在，Nest 怎麼知道建構子要 ProductsService？emitDecoratorMetadata 把參數型別寫成執行時讀得到的紀錄。
  4. 自己做 DI 容器：讀這份紀錄、遞迴建立依賴、同一個只建一次，以及容器解析不了時會發生什麼事。
  5. 「Nest can't resolve dependencies」的三個常見原因：interface 參數、import type、宣告順序與循環依賴，NestJS 用 token、@Inject、forwardRef 怎麼解。
這課會用到：
  • 第 23 課的參數屬性與依賴注入：constructor(private repo: Repo) {} 一次宣告欄位並接收依賴，依賴由外面 new 好傳進來。
  • 第 23 課的「class 是值也是型別」：class 執行時還在，可以當參數傳；interface 擦掉後什麼都不剩。建構子型別 new (...args: any[]) => T 代表「能被 new 出 T 的東西」。
這一頁的練習區開著 experimentalDecorators 和 emitDecoratorMetadata，跟 NestJS 12 官方 starter 的 tsconfig 一樣。這兩個選項做什麼，第 1 節和第 3 節會講。

第一步：@Log 到底是什麼？什麼時候執行？

在看 Nest 的 @Get() 之前，先從最小的裝飾器開始，而且自己寫一個：咖啡師每次做飲料，就記一筆 log。寫過一次就會發現，@ 後面接的東西沒有魔法，只是一個普通的函式。

裝飾器（decorator）是寫成 @名稱、放在類別、方法、屬性或參數前面的函式。它在類別定義的那一刻被呼叫一次，拿到被裝飾的東西，可以把資訊記下來，也可以把被裝飾的東西換掉。它不是在每次呼叫方法時執行，也不是在 new 的時候執行。這一點是本課所有東西的基礎：Nest 能在啟動時就知道全部的路由和依賴，正是因為這些資訊在類別定義時就已經記好了。

可以把它想成咖啡店商品上貼的「熱門」「需冷藏」標籤。標籤本身不做任何事，是收銀系統、冰箱管理讀了標籤才去處理。NestJS 的 @Get() 也一樣：它只把「這個方法處理 GET」記下來，真正建路由表的，是 Nest 啟動時讀這些紀錄的程式。

動手寫之前要先知道一件事：TypeScript 有兩套裝飾器，參數不同、互不相容。tsconfig 開了 experimentalDecorators，用的是 TypeScript 很早就提供的舊版；沒開，就是 TypeScript 5.0 起支援的標準版。標準版由 TC39 制定，TC39 是負責 JavaScript 標準的委員會，所以也叫 TC39 標準裝飾器。NestJS 用舊版，原因跟這課後半的兩樣東西有關：第 3 節的 emitDecoratorMetadata 和第 5 節的參數裝飾器，標準版都沒有。這一頁也開著舊版，所以下面的範例全是舊版寫法。你在網路上搜到參數是 (method, context) 的範例，就是標準版；兩套的對照放在課末「補充與查表」。

舊版的方法裝飾器收三個參數：

  • target：方法所在的物件。一般方法放在類別的 prototype 上（第 3 課），所以這裡拿到的是 Barista.prototype。
  • key：方法名稱，例如 'brew'。
  • descriptor：屬性描述器（property descriptor），{ value, writable, enumerable, configurable }。value 就是方法本身，換掉它就等於換掉方法。

下面的 Log 做兩件事：定義時印一行「套用 @Log」，再把 descriptor.value 換成一個會先印 log、再呼叫原方法的新函式。執行後看「套用 @Log」出現在哪裡、出現幾次。

「套用 @Log」出現在第 1 行和第 2 行之間，而且只有一次。呼叫兩次 brew，裝飾器本身沒有再跑；每次呼叫跑的是它換上去的那個新函式。要每次呼叫都做的事（記 log、計時），一定寫在這個新函式裡，不是寫在裝飾器本體。

新函式用 function 而不是箭頭函式，因為它要用呼叫當下的 this（a.brew() 的 a），再用 apply 傳給原本的方法。換成箭頭函式，this 會固定成裝飾器函式那一層的 this（模組裡是 undefined），this.name 就會丟 TypeError。這就是第 1 課的 this 陷阱。

為什麼裝飾器會在類別定義時執行？看 TypeScript 把 @Log 編譯成什麼就明白了：它只是在類別後面多一行函式呼叫。

class Barista {
    name;
    constructor(name) { this.name = name; }
    brew(drink) { return `${this.name} 做了 ${drink}`; }
}
__decorate([
    Log,
    __metadata("design:type", Function),
    __metadata("design:paramtypes", [String]),
    __metadata("design:returntype", void 0)
], Barista.prototype, "brew", null);

__decorate 是 TypeScript 產生的小工具函式：拿到描述器，依序交給陣列裡的裝飾器，再把結果寫回 Barista.prototype.brew。這一行緊接在 class Barista 後面，所以類別一定義好就執行。那幾行 __metadata 先略過，它們是開了 emitDecoratorMetadata 才有的，是第 3 節的主角。

也因為裝飾器要靠編譯器改寫成這種函式呼叫，有裝飾器的 .ts 一定要先經過 tsc（或 Nest CLI）編譯才能執行，不能直接交給 Node 跑。原因見課末「補充與查表」。

💡 實務上：大多時候是「用」框架的裝飾器，很少自己寫
工作中你每天會寫 @Get()、@Injectable()，但自己寫裝飾器的機會不多，常見的是記錄耗時、統一記 log 這類每個方法都要、又跟業務無關的包裝。要自己寫之前先問：框架有沒有現成的機制？NestJS 有兩個常用的：攔截器（interceptor）包住方法執行的前後，守衛（guard）決定請求能不能進來。它們就是為這種需求設計的，團隊也比較熟，NestJS 課會教。不要把業務邏輯藏進裝飾器，例如「結帳前自動扣庫存」：讀程式的人只看到一行 @，出錯時很難追。Code review 看到新的自製裝飾器，資深工程師會先確認它有沒有保留 this 和回傳值，以及 async 方法的錯誤有沒有被吞掉。

但 @Log 沒有括號，也沒有設定。Nest 的 @Get(':id') 有括號、帶著路徑，而且它不包裝方法，只是讓 Nest 知道「這個方法處理 GET」。這是怎麼做到的？

@Get(':id') 帶參數：框架怎麼用它記下路由？

@Get(':id') 多了括號，代表它是先被呼叫一次的函式。Get(':id') 本身不是裝飾器，而是裝飾器工廠（decorator factory）：一個回傳裝飾器的函式。執行時先呼叫 Get(':id')，得到真正的裝飾器，再把那個裝飾器套到方法上。工廠的用處是讓同一種裝飾器帶不同的設定：@Get()、@Get(':id') 回傳的是兩個不同的裝飾器，各自記得自己的路徑。

拿到路徑之後做什麼？框架的裝飾器大多只做一件事：把資訊記進某個登記表，例如一個 Map 或陣列，等框架啟動時再讀出來處理。它們不會像 @Log 那樣換掉方法。

下面用咖啡店的標籤當例子：@Tag() 是類別裝飾器工廠，把標籤記進 tags 這張登記表；@Note() 是方法裝飾器工廠，只印出自己什麼時候被套用。執行後照輸出由上往下讀，注意三件事：工廠和裝飾器各在什麼時候印、方法和類別誰先、登記表裡兩個標籤的順序。

從輸出可以讀出三條規則：

  1. 方法（成員）的裝飾器先執行，類別的裝飾器最後。成員之間照宣告順序。
  2. 同一個位置疊了好幾個裝飾器時，工廠由上往下呼叫，裝飾器由下往上套用（離類別近的先套），所以登記表裡 '需冷藏' 在 '熱門' 前面。
  3. 全部發生在類別定義時，跟有沒有建立實例無關：上面從頭到尾沒有 new Cheesecake()。

第 1 條對做路由有直接影響：@Get() 執行時，@Controller('/orders') 還沒執行，方法裝飾器不知道前綴是什麼，只能先把路徑記著，等類別裝飾器執行時再補上前綴。練習 2 要你自己處理這件事。

到這裡，開場的兩件事已經能先回答一半。路由表：@Controller()、@Get() 在類別定義時把「哪個類別、哪個方法、什麼路徑」記進登記表，Nest 啟動時讀出來建路由。注入：@Injectable() 一樣是在類別定義時往登記表記一筆「這個類別要交給容器管理」。開了 emitDecoratorMetadata，TypeScript 還會替掛了裝飾器的類別多記一筆「建構子參數的型別是 ProductsService」。Nest 啟動時讀這筆紀錄，先建立 ProductsService，再把它傳進 OrdersService 的建構子。

最後那一句藏著一個問題：第 13 課說過型別在編譯後會被擦掉，執行時不存在。「建構子參數的型別」要怎麼記？

型別在執行時不存在，Nest 怎麼知道建構子要 ProductsService？

先把問題講清楚。constructor(private products: ProductsService) 編譯成 JavaScript 後只剩 constructor(products)，: ProductsService 被擦掉了。容器在執行時拿到 OrdersService 這個 class，看不到參數該是什麼，也就不知道要先建立誰。總得有人在型別被擦掉之前，把這份資訊用執行時讀得到的值另外記下來。

這就是 emitDecoratorMetadata 做的事。metadata 是「描述資料的資料」，在這裡指附在類別上、描述這個類別的紀錄，例如「建構子有兩個參數，型別分別是什麼」。開了 emitDecoratorMetadata，TypeScript 會在有裝飾器的類別、方法旁邊多產生幾行程式，把型別資訊寫成這種紀錄。用同事的 OrdersService 來看：

// 原始碼
@Injectable()
class OrdersService {
  constructor(private products: ProductsService, private clock: Clock) {}   // Clock 是 interface
}

// tsc 5.9.3 編譯後（target ES2022）
let OrdersService = class OrdersService {
    products;
    clock;
    constructor(products, clock) {
        this.products = products;
        this.clock = clock;
    }
};
OrdersService = __decorate([
    Injectable(),
    __metadata("design:paramtypes", [ProductsService, Object])
], OrdersService);

design:paramtypes 是 TypeScript 用來記錄「建構子參數型別」的鍵，值是一個陣列，一個參數一格，放的是執行時真的存在的值：

  • ProductsService 是 class，class 是值（第 23 課），所以陣列裡就是那個 class 本身。容器拿到它，就能 new。
  • Clock 是 interface，編譯後不存在，TypeScript 只能寫 Object。型別資訊在這裡已經丟了，而且編譯不會有任何提示。
  • string、number 會寫成 String、Number。

注意 Clock 那一格：同事的錯誤已經埋在這裡了，第 5 節回來處理。

這份紀錄存到哪裡？__metadata 只是去呼叫 Reflect.metadata(鍵, 值)，而且只在 Reflect.metadata 存在時才呼叫。JavaScript 內建的 Reflect 沒有這個方法，要靠 reflect-metadata 套件（目前 0.2.2）補上：import 'reflect-metadata' 之後，Reflect.metadata、Reflect.getMetadata 才存在，前者寫入紀錄，後者讀回來。NestJS 的 @nestjs/common 第一行就 import 它，所以 Nest 12 starter 的 main.ts 不用自己寫；不經過 Nest、自己用裝飾器加 metadata 的程式，要在進入點最前面 import。少了它不會報錯，metadata 就悄悄地不見了。

練習區不能 import 套件，這一頁用 10 行 WeakMap 做一個迷你版：metadata(鍵, 值) 寫入，getMetadata(鍵, 類別) 讀回來（真正的套件是 Reflect.getMetadata），只記類別本身的 metadata。範例裡的 OrdersService 多了一個 string 參數，另外有一個沒掛裝飾器的 NoDecorator 對照。執行後看兩行輸出：有裝飾器的類別拿到什麼陣列，沒有裝飾器的拿到什麼。

第一行的陣列依序是 ProductsService、Object、String，跟上面講的三種情況一一對應；第二行是 undefined。後者解釋了 NestJS 的規定：要被注入的類別必須掛 @Injectable()。迷你版的 Injectable 什麼都不做，但它必須存在，因為 TypeScript 只替有裝飾器的類別產生 design:paramtypes；不掛，就沒有紀錄可以讀。

用 WeakMap 而不是 Map，是因為鍵是類別：類別不再被用到時，它的 metadata 可以跟著被回收（第 2 課）。

現在也看得出第 1 節說 NestJS 停在舊版的第一個原因有多關鍵：整個 DI 靠 emitDecoratorMetadata 產生的這份紀錄，而它只能跟 experimentalDecorators 一起用，標準裝飾器不相容。

💡 實務上：metadata 要靠編譯工具產生，換工具時最容易壞
design:paramtypes 是編譯時產生的，但除了 tsc，專案裡常見更快的轉譯工具 esbuild、SWC，不是每個都會做，同一個工具的不同版本也可能不一樣。測試工具 Vitest 就是例子：它靠 Vite 轉譯 TypeScript。Vite 7 以前用 esbuild，esbuild 不支援 emitDecoratorMetadata，所以舊專案常見的結果是正式執行好好的，測試卻全部報「Nest can't resolve dependencies」，當時的做法是改用 SWC（unplugin-swc 外掛）轉譯。Vite 8 改用 Oxc，會讀 tsconfig 的這兩個選項並產生 metadata，但 Vite 文件註明只是部分支援：完整的 metadata 需要 TypeScript 編譯器的型別推論，Oxc 做不到。本課程的 NestJS 練習用的是 Vite 8.3.5、Vitest 5.0.5，沒有另外裝 SWC。所以專案要換建置或測試工具時，資深工程師會先問一句：「它支不支援裝飾器 metadata？」，並且先跑一個有注入的測試確認，而不是只看編譯有沒有過。

現在 OrdersService 身上掛著一份參數型別的紀錄。但光有紀錄，物件還不會自己出現：要有人讀它、決定先建立誰、照順序 new。這個「有人」就是 DI 容器。

自己做 DI 容器：怎麼讀 metadata，把一串 new 自動寫出來？

先看容器要取代的是什麼。第 23 課的依賴注入是手動的：你在程式最外面自己把所有物件 new 好、一個一個傳進去。下面三個類別裡，ProductsService 和 OrdersService 都需要 Db，而且應該共用同一個。執行後看最後一行：從 orders.products.db 讀得到從 orders.db 寫進去的資料，代表兩邊拿到的是同一個 Db。

三個類別還應付得來，但手動組裝有兩個負擔，服務一多就會出錯。第一是順序：要先有 Db 才能建 ProductsService，先有 ProductsService 才能建 OrdersService，這個順序得靠人排。第二是共用：Db 只能建一個，每個需要它的地方都要記得傳同一個；不小心多 new 一個，兩個服務就看不到彼此寫的資料。

DI 容器（DI container）把這兩件事接手過去。你只說「我要 OrdersService」，它讀出建構子要哪些參數，自己找出要先建立誰、照順序建好，並保證共用的東西只建一次。講容器之前，先認識三個名詞，NestJS 的文件和錯誤訊息都會用到：

  • provider：容器裡的一筆登記，說明「某個依賴怎麼產生」，例如「用 new ProductsService()」或「呼叫這個函式」。NestJS 模組裡的 providers: [OrdersService, ProductsService] 就是在登記 provider。
  • token：provider 的識別鍵，容器用它查表，找到對應的 provider。最常見的 token 就是 class 本身，這也是為什麼 design:paramtypes 裡放的是 class：拿到 class，就能直接查表。interface 沒辦法當 token，第 5 節會看到怎麼辦。
  • 單例（singleton）：同一個容器裡，同一個類別只建立一個實例，大家共用。這就解決了上面「共用」的負擔。NestJS 的 provider 預設就是單例。

容器的核心是一個函式 resolve(OrdersService)，意思是「給我一個建好的 OrdersService」。它要做的事：

  1. 已經建過了？直接回傳快取裡的那一個（單例）。
  2. 讀 design:paramtypes，知道建構子要哪些參數（沒有就當作不要參數）。
  3. 每個參數型別：如果是 Object 或 undefined，代表型別資訊已經丟了，丟出清楚的錯誤；否則對它遞迴呼叫 resolve。
  4. new OrdersService(...依賴)，存進快取，回傳。

第 3 步的遞迴解決了「順序」：要建 OrdersService 得先有 ProductsService，就先去 resolve 它，它又需要 Db，就再往下 resolve，一路走到不需要參數的類別再一層層回來。第 1 步的快取解決了「共用」：Db 第二次被需要時直接拿快取。下圖是 resolve(OrdersService) 實際走過的路：

動手寫這個容器是練習 3 和練習 4，兩題都標成選讀：練習 3 寫出 resolve，練習 4 替它加上 token。跳過不影響後面的課，但寫過一次，之後看到 Nest 的 DI 錯誤會清楚很多。

Nest 啟動時做的事跟這個 resolve 是同一件事：模組裡的 providers 是登記，Nest 讀每個 provider 的 design:paramtypes，遞迴建立、預設單例。真正的 Nest 多了模組的可見範圍、生命週期等功能（NestJS 課第 3 課、第 4 課）。

💡 實務上：單例代表「所有請求共用同一個物件」
DI 在工作中最直接的好處是測試：咖啡店的結帳服務依賴 PaymentGateway，測試時讓容器換成假的金流，不用真的刷卡。但要記住 provider 預設是單例，所有使用者的請求都共用同一個 OrdersService。新手常犯的錯是把「目前登入的使用者」或「這張訂單」存在服務的欄位上，兩個請求同時進來就會互相蓋掉，王小明可能看到陳美華的訂單。服務裡只放大家共用、不會變的東西（資料庫連線、設定），每個請求的資料一律用參數傳進方法。

回到同事的錯誤，關鍵在第 3 步。我們的容器遇到 Object 或 undefined 時，會丟出「無法解析 OrdersService 的第 2 個參數」。Nest 的「Nest can't resolve dependencies」是同一類錯誤：容器走到某個參數，卻沒辦法把它變成一個物件。

所以查這種錯誤，問題就變成：design:paramtypes 裡哪一格不是容器能用的 class？為什麼會變成那樣？實務上最常見的原因有三種。

「Nest can't resolve dependencies」：三個常見原因怎麼查、怎麼修？

三種原因的共同點是：原始碼的型別看起來都對，編譯也通過，但寫進 metadata、或容器讀到的那一格，不是一個可以 new 的 class。第一種就是同事遇到的那一種。

原因一：參數型別是 interface

第 3 節看到了，Clock 是 interface，在 metadata 裡變成 Object，容器不知道要給什麼。可是用 interface 當參數型別是好的設計（第 23 課：參數型別寫介面，測試時就能換成假的實作），不該為了容器放棄它。NestJS 文件建議兩種解法：

  • Symbol token 加 @Inject：自己定一個 token，登記 provider 時用它，注入時用 @Inject(TOKEN) 告訴容器「這個參數不要看 metadata，去拿 TOKEN」。Symbol 每個都是獨一無二的，不會像字串 token 那樣不小心撞名。
  • abstract class 同時當契約與 token：abstract class 跟 interface 一樣能描述「要有哪些方法」，但它是 class，是值，metadata 裡留得下來，建構子不用多寫 @Inject。

回到同事的 OrdersService，用 Symbol token 修好是這樣。Clock 介面照常用在型別上，容器則靠 CLOCK 這個 token 找到 SystemClock：

// NestJS 的寫法
export interface Clock { now(): Date }
export const CLOCK = Symbol('CLOCK')

@Module({ providers: [{ provide: CLOCK, useClass: SystemClock }, ProductsService, OrdersService] })
export class OrdersModule {}

@Injectable()
export class OrdersService {
  constructor(private products: ProductsService, @Inject(CLOCK) private clock: Clock) {}
}

修好後 design:paramtypes 那一格仍然是 Object，但容器看到 @Inject(CLOCK) 就不讀它，直接去拿 CLOCK 登記的物件。

@Inject(CLOCK) 掛在建構子的參數上，這是一種新的裝飾器：參數裝飾器。標準裝飾器不允許裝飾參數，這就是第 1 節說的、NestJS 停在舊版的第二個原因（@Body()、@Param('id') 也都是參數裝飾器）。舊版的參數裝飾器收三個參數：

  • target：裝飾建構子參數時，是類別本身。
  • propertyKey：方法名稱。建構子參數沒有方法名稱，所以是 undefined，型別要寫 string | symbol | undefined（寫成 string 會報錯，見課末）。
  • index：第幾個參數，從 0 開始。

容器要的正是「哪個類別的第幾個參數用哪個 token」，這三個參數剛好給齊。下面的範例換成結帳服務，是為了同時示範 abstract class 和 Symbol token 兩種解法。CheckoutService 同時用了兩種解法：gateway 的型別是 abstract class，不用 @Inject；logger 用 Symbol token。執行後看印出的那一行：@Inject 只套在第二個參數上，方法名稱是 undefined，index 是 1。

印 symbol 用 String(token)，會得到 'Symbol(LOGGER)'。寫成 `${token}` 會丟 TypeError：模板字串不會自動把 symbol 轉成字串。練習 4 的錯誤訊息會用到這一點。

原因二：用 import type 匯入要注入的 class

第二種原因的參數型別明明是 class，卻還是解析不了。下一課會教 import type：只匯入型別，編譯後整行消失。可是要注入的 class 必須在執行時存在，metadata 才寫得出它。實測 tsc 5.9.3 和 7.0.2：

import type { ProductsService } from './products.service.js'

@Injectable()
export class OrdersService {
  constructor(private products: ProductsService) {}
}

// 編譯後：class 已經拿不到，只剩 Function，而且編譯不會有任何錯誤
__metadata("design:paramtypes", [Function])

為什麼是 Function，不像 interface 那樣變成 Object？TypeScript 從型別知道 ProductsService 是一個可以 new 的 class，所以不會寫 Object。可是 import type 只帶進型別、沒有帶進值，編譯後的 JS 裡沒有 ProductsService 這個變數可寫，只好退回寫 Function。

容器拿到的是所有函式共用的 Function，無法知道要 new 哪一個 class，所以一樣解析失敗。跟 interface 不同的是，這裡的原始碼看起來完全正確，參數型別確實是一個 class，所以更難發現。

Nest 啟動時才會發現解析不了。要注入的 class 一律用一般的 import；編輯器的自動修正或 lint 規則把它改成 import type 時要特別注意。

原因三：宣告順序與循環依賴

第三種原因跟 import 的寫法無關，而是讀的時機。__metadata("design:paramtypes", [Late]) 是在類別定義時執行的程式，會真的去讀 Late 這個變數。如果 Late 宣告在後面，就會碰到第 3 課的 TDZ（暫時性死區）：class 和 let/const 一樣，在宣告那一行執行之前讀它會丟 ReferenceError。下面範例裡，Early 的 metadata 在定義 Early 時就去讀 Late，這時 Late 那一行還沒跑到。執行後看錯誤訊息，以及最後一行有沒有印出來：

在單一檔案裡把類別順序調一下就好。分成多個檔案時，同樣的事情會以循環依賴（circular dependency）的形式出現：orders.service.ts 匯入 products.service.ts，products.service.ts 又匯入 orders.service.ts，其中一邊載入時另一邊還沒初始化，metadata 就讀不到那個 class。NestJS 的解法是 forwardRef：傳一個函式而不是 class 本身，等容器真的要建立物件時才呼叫它取得 class，那時兩個檔案都已經載入完了。

@Injectable()
export class OrdersService {
  constructor(
    @Inject(forwardRef(() => ProductsService))
    private products: ProductsService,
  ) {}
}
// ProductsService 那一邊也要同樣寫 forwardRef(() => OrdersService)

資深一點的判斷：forwardRef 讓程式跑得起來，但沒有解決設計問題。NestJS 文件也提醒兩邊誰先建立是不保證的，另外要小心 barrel 檔案。barrel 檔案是一個資料夾裡集中 export 所有東西的 index.ts，它很容易意外造成循環。遇到循環依賴，先問「是不是有一塊邏輯該抽成第三個服務」，讓依賴變成單向（NestJS 課第 26 課的模組邊界）。

💡 實務上：遇到「Nest can't resolve dependencies」，照這個順序查
先看錯誤訊息指的是哪個類別的哪個參數，再對著本課的機制一個一個排除：那個參數的型別是 interface 嗎？改用 token 加 @Inject 或 abstract class。它是用 import type 匯入的嗎？改回一般 import。兩個服務互相 import 嗎？先想能不能拆開，不行才用 forwardRef。被注入的類別有沒有掛 @Injectable()？沒掛就沒有 metadata。只有測試壞、正式執行沒事？檢查測試的轉譯工具支不支援裝飾器 metadata。同事那個 OrdersService 屬於第一種：替 Clock 定一個 token，問題就解決了。

練習

練習 1：寫方法裝飾器 Log（舊版簽章 (target, key, descriptor)）。被裝飾的方法每次被呼叫時：

  • 先把 類別名.方法名(參數) 推進 calls，參數用 ', ' 連接，例如 'Register.charge(拿鐵, 2)'。
  • 再呼叫原本的方法，回傳它的結果。原方法裡的 this 要正常。
  • 原方法丟出錯誤時，紀錄仍然要在，錯誤照樣丟出去。

練習 2：做一個迷你路由。寫裝飾器工廠 Controller(prefix) 和 Get(path = '')，把每個路由登記到 routes：{ method: 'GET', path: 前綴 + path, handler: 方法名 }，順序跟方法宣告的順序一樣。

提示：方法裝飾器比類別裝飾器先執行，Get 執行時還不知道前綴。多個 controller 的路由不能互相混在一起。

練習 3（選讀，對應「自己做 DI 容器」）：起始程式已經有迷你 reflect-metadata 和 @Injectable()。寫出 resolve(target)：

  • 讀 design:paramtypes（沒有就當作沒有參數），對每個參數型別遞迴 resolve，再 new target(...依賴)。
  • 單例：同一個類別只建立一次，存在 instances。
  • 參數型別是 Object 或 undefined 時，丟出 new Error('無法解析 BadService 的第 1 個參數')（換成實際的類別名稱，第幾個從 1 開始），不能悄悄塞一個 {} 進去。

練習 4（選讀，對應「自己做 DI 容器」）：替容器加上 token。起始程式已經放好練習 3 的 resolve。

  • 寫參數裝飾器工廠 Inject(token: symbol)：記錄「哪個類別的第幾個參數用哪個 token」。參數裝飾器的三個參數是 (target, propertyKey, index)，型別自己寫，記得建構子參數的 propertyKey 是 undefined。
  • 擴充 resolve：有 token 的參數改從 providers 取得（呼叫登記的函式），同一個 token 也只建立一次；沒有 token 的參數照舊用 design:paramtypes。
  • token 沒有登記時丟出 Error，訊息要包含 String(token)，例如 '沒有註冊 Symbol(PAYMENT)'。

練習 5：OrdersService 的 place 方法掛了 @Log（像練習 1 那樣包裝方法）。程式啟動後，place 被呼叫了 100 次。Log 這個裝飾器函式本身被呼叫了幾次？

✓ c。裝飾器在類別定義時執行一次，它把 descriptor.value 換成包裝函式，之後 100 次呼叫跑的都是包裝函式（a、b 錯）。它跟建立實例無關，沒有 new 也照樣會執行（d 錯），第二節的 Cheesecake 範例從頭到尾沒有 new。

練習 6：開著 emitDecoratorMetadata，@Injectable() class ReceiptService { constructor(private clock: Clock) {} }，其中 Clock 是 interface。ReceiptService 的 design:paramtypes 是什麼？

✓ b。metadata 裡放的是執行時的值，interface 沒有對應的值，所以寫成 Object（a 錯）。參數不會被略過，陣列長度仍然等於參數個數（c 錯）。編譯完全正常（d 錯），所以要靠容器在執行時檢查，或改用 token 加 @Inject。

練習 7：TypeScript 5.0 已經支援 TC39 標準裝飾器。NestJS 12 的 starter 為什麼還開著 experimentalDecorators？

✓ a。標準裝飾器不允許裝飾參數，也不相容 emitDecoratorMetadata，Nest 的 DI 和請求參數都建立在這兩件事上。b 錯：瀏覽器和 Node 目前都還沒有原生裝飾器，兩套都要經過編譯。c 錯：兩套的參數、型別檢查和編譯結果都不同。d 錯：標準裝飾器沒有被移除。

常見錯誤

  • 以為裝飾器在每次呼叫時執行：它在類別定義時執行一次。要每次呼叫都做的事，寫在它換上去的函式裡。
  • 包裝方法時用箭頭函式：this 不是呼叫當下的物件，原方法裡的 this.x 會壞掉。用 function 加 original.apply(this, args)。
  • 混用兩套裝飾器：網路上的範例有 (target, key, descriptor) 也有 (method, context)，先看專案的 tsconfig 有沒有開 experimentalDecorators，再挑對應的寫法。NestJS 專案一律是舊版。
  • 用 Node 直接執行有裝飾器的 .ts：型別剝除不處理裝飾器，會是語法錯誤。先編譯再執行。
  • 沒有 import 'reflect-metadata'：__metadata 找不到 Reflect.metadata 就什麼都不做，不會報錯，容器讀不到參數型別。Nest 專案由 @nestjs/common 載入；不經過 Nest 自己用 metadata 的程式，要在進入點最前面 import。
  • 建構子參數用 interface 卻沒有 token：metadata 是 Object。用 Symbol token 加 @Inject(TOKEN)，或改成 abstract class。
  • 用 import type 匯入要注入的 provider：metadata 變成 Function，編譯不會報錯，啟動時才解析失敗。要注入的 class 用一般的 import。
  • 用 forwardRef 掩蓋該拆開的循環依賴：它讓程式跑得起來，但兩個服務仍然緊緊綁在一起。先試著把共用的邏輯抽成第三個服務。

補充與查表

兩套裝飾器對照

第 1 節提到 TypeScript 有兩套互不相容的裝飾器：

  • experimentalDecorators：TypeScript 很早就提供的舊版，照的是多年前的提案。tsconfig 開了 "experimentalDecorators": true 才使用。本課的範例都是這一套。
  • TC39 標準裝飾器（standard decorators）：TC39 是制定 JavaScript 標準的委員會，這是它們正在推的新版。TypeScript 5.0 起，沒開 experimentalDecorators 時就用這一套。

標準裝飾器的方法裝飾器長這樣（這一頁開著舊版，所以只能用 <pre> 展示）：

// TC39 標準裝飾器：收到「原本的方法」和 context，回傳新的方法
function log(original: Function, context: ClassMethodDecoratorContext) {
  const name = String(context.name)
  return function (this: unknown, ...args: unknown[]) {
    console.log(`呼叫 ${name}`)
    return original.apply(this, args)
  }
}

查表用，不用背：

experimentalDecorators（舊版）TC39 標準
怎麼開tsconfig "experimentalDecorators": trueTypeScript 5.0 起，沒開上面的旗標就是它
方法裝飾器的參數(target, key, descriptor)(method, context)
參數裝飾器 constructor(@Inject(X) a)有沒有（寫了會報 TS1206）
emitDecoratorMetadata可以一起用不相容
誰在用NestJS 12（starter 的 tsconfig 開著）、TypeORM、class-validator新寫的、不依賴參數裝飾器的函式庫

NestJS 不換成標準版的原因就在表格中間兩列：@Body()、@Param('id')、@Inject(TOKEN) 都是參數裝飾器，DI 靠的是 emitDecoratorMetadata，標準版兩個都沒有。TypeScript 5.0 的發行說明也寫了 experimentalDecorators 會繼續存在。

為什麼有裝飾器的程式一定要先編譯

裝飾器一定要經過編譯。瀏覽器和 Node 目前都還不支援原生的裝飾器語法；Node 24 直接執行 .ts 用的型別剝除（type stripping，Node 課第 5 課）只會刪掉型別，遇到裝飾器是語法錯誤。所以 NestJS 專案一定先用 tsc（或 Nest CLI）編譯，再執行 dist/ 裡的 JavaScript。

參數裝飾器的 propertyKey 型別

TypeScript 5.0 起，舊版參數裝飾器第二個參數的型別要寫 string | symbol | undefined，寫成 string 會在套用到建構子參數時報 TS1239。

小結

  • 裝飾器是在類別定義時被呼叫一次的函式；方法裝飾器拿到 (target, key, descriptor)，換掉 descriptor.value 就能包裝方法，包裝時要保留 this。
  • 裝飾器工廠回傳裝飾器；框架的裝飾器大多只是把資訊記進登記表，啟動時再讀出來。成員的裝飾器先執行，類別的最後。
  • emitDecoratorMetadata 把建構子參數型別寫成 design:paramtypes：class 留得下來，interface 變成 Object，import type 的 class 變成 Function。只有掛了裝飾器的類別才有，而且要有 Reflect.metadata 才會記錄。
  • TypeScript 有兩套裝飾器。NestJS 12 用 experimentalDecorators，因為它需要參數裝飾器和 emitDecoratorMetadata。
  • DI 容器就是：讀 metadata → 遞迴建立依賴 → 單例快取；解析不了時給出清楚的錯誤。「Nest can't resolve dependencies」代表某個參數變不成物件：interface 用 token 加 @Inject，import type 改回一般 import，循環依賴先從設計上拆開，不得已才用 forwardRef。
