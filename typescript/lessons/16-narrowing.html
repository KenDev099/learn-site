階段 3：型別基礎 · 第 16 課

型別縮小與可辨識聯合

這一課你接手咖啡店的結帳模組。它要處理的值都不太乾淨：價格可能是菜單裡的數字，也可能是店員在表單輸入的字串；數量和備註可能沒填，是 null；折扣有「打折、折現金、送贈品」三種，每種帶的資料不一樣；結帳按鈕還有「編輯中、送出中、完成、失敗」幾種狀態。老闆也已經說了：下個月要加「會員價」。

上一課的聯合型別剛好能描述這些值，例如價格是 number | string。但它留下一個問題：在 TypeScript 確定是哪一種之前，只能用所有成員共有的部分，input.toFixed() 會報錯。這一課從這個問題出發，一路回答三件事：拿到「可能是好幾種」的值，怎麼安全地用它；怎麼把型別設計成錯的組合根本寫不出來；老闆加需求時，怎麼讓編譯器列出每一個要改的地方。

這課的路線：
  1. 價格是數字或字串：檢查過 typeof 之後，TypeScript 怎麼知道它是 number（開場問題的最小答案）。
  2. 備註和數量可能沒填：typeof null 和 if (qty) 這兩種檢查怎麼騙你；接著看物件要用 in、instanceof、Array.isArray 分辨。
  3. 折扣有三種：用一個 kind 欄位分辨，這叫可辨識聯合；再用它設計結帳按鈕的狀態，讓「送出中又失敗」寫不出來。
  4. 老闆加了會員價：用 never 做窮舉檢查，讓編譯器列出每個漏改的 switch。
  5. 檢查過了，為什麼 callback 裡又說可能是 null：縮小什麼時候失效，怎麼改寫。
這課會用到：
  • 第 15 課的聯合型別與字面值型別：A | B 表示值是其中一種，確定是哪一種之前只能用共同的部分；'paid' 當成型別時只允許這一個值。
  • 第 15 課的 never：沒有任何值的型別，可以想成零個選項的聯合。

價格是數字或字串：檢查過 typeof，TypeScript 怎麼知道它是 number？

結帳模組第一個要處理的是價格。formatPrice 把價格變成「NT$110」這樣的文字，收到的可能是數字，也可能是表單送來的字串。先照直覺寫：

TypeScript 在 toFixed 那一行報錯，而且擋得對。number | string 的意思是「這個值可能是兩種裡的任何一種」，TypeScript 不知道這一次是哪一種，所以只允許兩種都能做的操作。toFixed 只有 number 有，傳進 '80' 時執行到這一行真的會丟 TypeError。型別檢查在寫程式時就把這個執行時的當機指出來。

怎麼修？寫 JavaScript 時你本來就會這麼做：先檢查它是哪一種，再用那一種的方法。

執行後兩行都正常輸出。在編輯器裡把滑鼠移到 if 裡的 input，型別顯示 number；移到最後一行的 input，顯示 string。同一個變數，在不同位置的型別不一樣。這個現象叫型別縮小（narrowing）：一個值的型別原本是好幾種的聯合，經過檢查後，TypeScript 在檢查成立的範圍裡把它當成範圍較小的型別。能造成縮小的檢查，例如這裡的 typeof input === 'number'，叫型別守衛（type guard）。

if 裡面是 number 好理解，那 if 的下面為什麼只剩 string？TypeScript 讀程式時不只看變數宣告的型別，還會沿著程式可能走的每一條路，記下每條路上變數可能是什麼。走到 if 時路分成兩條：是 number 的那條執行了 return，離開函式，不會再往下走；所以能走到 if 下面的，只剩「不是 number」的情況，number | string 去掉 number 就是 string。這種分析叫控制流程分析（control flow analysis）。會讓路分岔或中斷的語法都算：return、throw 截斷一條路，else 和 switch 的每個 case 各自是一條路。

為什麼可以相信縮小的結果？因為縮小只影響型別檢查，不會改變程式做的事。編譯後的 JavaScript 裡，那就是一個普通的 if，typeof 在執行時真的會跑；TypeScript 只是把檢查的結果記下來。型別上說「這裡是 number」，執行時也真的只有 number 走得進來。這跟之後會學的 as 不一樣：as 只改型別，執行時什麼都不檢查。

開場問題的最小答案就在這裡：先用 JavaScript 本來就有的檢查分出是哪一種，TypeScript 會跟著算出每一行的型別。但結帳模組的值不只有 number 和 string，還有 null、物件、陣列、錯誤。檢查方式選錯了，有時 TypeScript 會擋，有時它根本不會報錯。下一節先看兩個最常踩的。

備註和數量可能沒填：哪些檢查會騙你？

訂單的備註是一個字串陣列，例如 ['少冰', '半糖']，沒填時是 null。陣列是物件，所以直覺上會用 typeof notes === 'object' 確認「有備註」：

TypeScript 在 notes.length 報 TS18047，說 notes 可能是 null。原因是 JavaScript 有一個早期留下來的錯誤：typeof null 的結果是 'object'。這個行為改掉會讓大量既有的網頁壞掉，所以一直保留到現在。TypeScript 知道這件事，所以通過 typeof notes === 'object' 之後，notes 仍然是 string[] | null。這次 TypeScript 救了你：如果它不報錯，傳進 null 時執行會丟 TypeError。

修法是直接寫出你要排除的東西：if (notes !== null)。!== 是精確比對，通過之後 TypeScript 從 string[] | null 拿掉 null，只剩 string[]。

第二個陷阱方向相反：TypeScript 完全不報錯，程式卻算錯。數量 qty 沒填時是 null，很多人習慣寫 if (qty) 檢查「有沒有填」：

看第一行輸出：qtyLabel(0) 顯示「未填」，可是客人明明填了 0 杯。if (qty) 檢查的不是「有沒有值」，而是把 qty 轉成布林看是真是假。第 15 課教過 falsy 值：0、''、NaN、null、undefined、false 轉成布林都是 false。所以 0 和 null 在這個 if 裡被當成同一件事。第二個函式寫 qty !== null，只排除 null，0 就能正常顯示「0 杯」。

TypeScript 為什麼不報？兩種寫法通過檢查後，qty 的型別都是 number，型別完全正確；錯的是「哪些值走得進來」，這是邏輯錯誤，型別檢查看不到。所以要靠寫法習慣：數字和字串要明確寫出你要排除的是什麼，只排除 null 寫 !== null，只排除 undefined 寫 !== undefined，兩個都要排除寫 != null（第 2 課說過，這是 ==／!= 唯一建議的用法）。真值檢查留給「物件或 null」這種型別：物件永遠是 truthy，不會有「正常值卻被當成沒有」的問題。

💡 實務上：if (數字) 是 code review 常抓到的 bug
真實案例長這樣：咖啡店後台的「免費招待」品項價格是 0，if (item.price) 把它當成「沒填價格」，結帳時跳出錯誤；庫存剩 0 的商品被判成「沒資料」，畫面顯示「—」而不是「已售完」。TypeScript 不會報這種錯，只能靠習慣：看到數字或字串放進 if、&&、||，就問一句「0 或空字串是不是合法的值」。預設值也一樣，qty || 1 會把 0 改成 1，要保留 0 就用 qty ?? 1。想讓工具幫忙抓，可以開 typescript-eslint 的 lint 規則，設定見課末〈補充與查表〉。

null 和數字處理好了。結帳模組裡還有另一類值：「可能是幾種物件的其中一種」。取餐方式是外送或自取，兩種物件長得不一樣；下單失敗時，可能是庫存不足，也可能是系統錯誤；品項可能是一個，也可能是一串。這些用 typeof 全都是 'object'，分不出來，要換工具。

外送還是自取、哪一種錯誤：物件要怎麼分？

JavaScript 有三個檢查專門用來分辨物件，TypeScript 都看得懂，各自適合一種情況。

in 看物件有沒有某個鍵。外送 Delivery 有 address 和 fee，自取 Pickup 只有 pickupAt。'address' in o 成立，表示 o 只可能是 Delivery，TypeScript 就把它縮小成 Delivery；不成立的那條路剩下 Pickup。要注意它看的是「有沒有這個鍵」，不是值是什麼。

instanceof 看物件是不是某個 class 建出來的。它沿著原型鏈往上找（第 3 課），所以很適合分辨自訂錯誤類別（第 4 課）：下單時庫存不足丟 OutOfStockError，畫面要告訴客人改點別的；其他錯誤是系統問題。限制是只對 class 有效。type 和 interface 只存在於型別檢查，編譯後就消失，執行時沒有東西可以拿來比，所以不能寫 x instanceof Delivery。

Array.isArray 分辨陣列。typeof [] 也是 'object'，要知道收到的是一個品項還是一串，就用它。

執行後看四行輸出：外送和自取各走自己的分支；庫存不足的錯誤拿得到 e.product，一般錯誤只用 e.message；字串和陣列最後都變成陣列。每個分支裡能用的屬性，都是縮小後那一種才有的。

折扣有三種，用 in 分會越來越亂：怎麼設計成一看就分得出來？

換個做法：不靠「有沒有某個鍵」分辨，而是讓每一種都有同一個欄位，專門寫「我是哪一種」，值是不同的字面值。這種聯合叫可辨識聯合（discriminated union），那個欄位叫標籤欄位（discriminant）。咖啡店的三種折扣寫成這樣，標籤欄位是 kind：

縮小是怎麼發生的？走進 case 'percent' 時，TypeScript 拿 'percent' 去比聯合裡每一種的 kind。只有第一種的 kind 型別是 'percent'，另外兩種是 'amount' 和 'gift'，不可能等於 'percent'，所以這個 case 裡 d 只剩第一種。結果是 d.percent 可以直接用，d.amount 反而會報錯，因為打折那一種根本沒有 amount。

最後一行也被擋下來了：{ kind: 'amount', percent: 10 } 想表達「折 20 元」，卻寫成打折的欄位。這個物件要符合聯合裡的某一種，kind 是 'amount' 的那一種要求 amount、沒有 percent，對不上，所以寫的當下就報錯。錯誤的組合不用等到執行，根本寫不出來。

這個設計成立的前提是：標籤一定要是字面值型別。如果寫成 kind: string，三種的標籤都是 string，拿 'percent' 去比，哪一種都「可能相等」，TypeScript 一種也排除不了，縮小就不會發生。練習 2 的起始程式就是類似的情況：只有一個型別，method 是 string，其他欄位都可選，TypeScript 沒有東西可以拿來分辨，錯的組合照樣寫得出來。

可辨識聯合不是前端專用的技巧。後端的 API 回應、佇列裡的訊息、事件紀錄，常見 type、kind、status 這種欄位，就是同一個設計：收到訊息先看標籤，就知道其他欄位該怎麼讀。

折扣是資料，寫錯了是某個人寫錯一行。結帳畫面的狀態也是同一種問題，而且更容易出事：常見的寫法裡，型別本身就允許錯誤的組合。

結帳按鈕：怎麼讓「送出中又失敗」寫不出來？

客人按下「送出訂單」後，按鈕要依狀態顯示不同文字。很多人第一次會這樣表示狀態：一個布林記錄是不是送出中，再加兩個可選欄位放結果：

這個物件型別完全正確，可是它代表什麼？送出中，又成功拿到訂單編號，又付款失敗。算一下：一個布林有 2 種值，兩個可選欄位各有「有／沒有」2 種，合起來是 2 × 2 × 2 = 8 種組合。真正合理的只有 4 種：編輯中（全部沒有）、送出中、完成（有訂單編號）、失敗（有錯誤訊息）。其他 4 種是不可能的狀態（impossible state）：業務上不會發生，型別卻允許。

型別允許，就總有一天會有人寫出來。典型的情況是重新送出時把 submitting 設回 true，卻忘了清掉上一次的 error，畫面就同時顯示轉圈和錯誤訊息。這種 bug 不在任何一行程式裡，而在型別的設計裡。

💡 實務上：看到一堆 isXxx 布林，先把組合列出來
前端最常見的是 isLoading、isError、data 三個欄位並存，後端則是訂單同時有 paid、shipped、cancelled 三個布林，最後出現「已取消又已出貨」的資料，客服很難解釋。判斷方式：把所有組合列出來，有沒有不合理的？有，就改成聯合。狀態之間有共同欄位（例如每種都有 startedAt），就放進每一種，或用交集組起來。真的只是兩個彼此無關的開關（「深色模式」和「顯示價格」），用兩個布林就好，不需要可辨識聯合。改既有程式時，資深工程師通常先從新功能或最常出 bug 的那個元件開始，不會一次改整個專案。

折扣和結帳狀態現在都用 switch 把每一種處理一遍。下個月老闆要加會員價，型別多加一行很容易；難的是處理折扣的 switch 散在各處：結帳金額、收據文字、報表統計。漏改一個，會員價就在那個地方算錯或顯示錯。

老闆加了會員價：怎麼讓編譯器找出每個漏改的 switch？

答案要用到 第 15 課的 never。先回顧它的兩個性質：never 是沒有任何值的型別；沒有任何型別能指派給 never，只有 never 自己可以。

再把上一節的縮小接上來。switch 的每個 case 都會從聯合裡拿掉一種：處理完 percent，剩下 amount 和 gift；處理完 amount，剩下 gift；處理完 gift，什麼都不剩。走到 default 時，d 的型別就是「剩下還沒處理的那些」。三種都處理了，剩下的是空的聯合，也就是 never；漏了一種，剩下的就是那一種。

所以在 default 裡把 d 傳給一個參數型別是 never 的函式：全部處理完時，傳進去的是 never，合法；漏了一種時，傳進去的是那一種，不能指派給 never，當場報錯。下面的 Discount 已經加了 member，switch 還沒補：

報錯的那一行就是要補的地方，錯誤訊息還會告訴你漏的是 member 那一種。新增一種情況之後，不用自己全文搜尋 kind，跑一次型別檢查，每個漏改的 switch 都會在自己的 default 報錯。

assertNever 的函式本體還做了第二件事：真的被呼叫時丟錯。照理說型別檢查通過後，default 永遠走不到，為什麼還要丟錯？因為型別擋不住外部資料。資料庫裡多了一個新狀態、舊版 App 送來的值，型別都說不可能，執行時卻真的會出現，走進 default。這時丟錯比悄悄回傳錯的結果好查。範例最後一行就是這個情況：switch 沒補 member，執行時 assertNever 丟出「沒有處理到的情況」。

如果只需要寫程式時的檢查、不需要執行時丟錯，也可以在 default 寫 const _exhaustive: never = d，原理一樣：漏了一種，d 就不能指派給 never。

不要讓 default 吞掉新的情況：default: return '未知' 看起來比較「安全」，其實新增 member 之後完全不會報錯，畫面默默顯示「未知」，可能好幾週才有人發現。default 應該留給「真的不該發生」的情況，並且大聲失敗。
💡 實務上：PM 說「訂單要多一個『退款中』狀態」
訂單狀態會散在很多地方：列表的標籤顏色、篩選選單、通知文字、報表統計。有窮舉檢查，加完型別後跑一次 tsc，錯誤清單就是待辦清單，估工時也有依據。要考量的是資料比程式先變：後端已經回傳新狀態，前端還沒部署，assertNever 在畫面上丟錯可能讓整頁白掉。所以畫面顯示常改成「型別上照樣窮舉，執行時顯示『其他』並回報到錯誤監控」，金額、權限這類算錯會出事的邏輯，才讓它直接丟錯。

到這裡，縮小一直很可靠，因為每次都是檢查完馬上用。但結帳的最後一步，要把訂單備註印到每個品項的杯貼上。用 forEach 一寫，TypeScript 卻說剛檢查過的備註又可能是 null。

檢查過了，為什麼 callback 裡又說可能是 null？

先看程式。printNotes 已經檢查過 order.note !== null，進到 forEach 的 callback 裡卻又報錯：

關鍵在 callback 什麼時候執行。TypeScript 沿著程式往下讀，只要在同一個函式裡沒看到有人重新指定 order.note，就沿用縮小的結果（它不會檢查中間呼叫的函式有沒有偷改，這是刻意的取捨）。callback 不一樣，它是之後才會執行的另一個函式，TypeScript 看不到它執行前發生了什麼：forEach 會馬上呼叫，換成 setTimeout 就是好幾毫秒之後，中間別的程式可能已經把 order.note 改成 null。物件的屬性任何拿到這個物件的程式都能改，TypeScript 無法保證它在 callback 執行時還是原樣，所以在 callback 裡不保留縮小。

printNotesFixed 的改法是先把值放進 const。const 宣告之後不能重新指定，檢查過 note !== null，它在任何時候都不會變回 null，TypeScript 就能在 callback 裡保留縮小。let 變數和函式參數介於兩者之間，TypeScript 5.4 起有一套比較寬的規則，細節見課末〈補充與查表〉；碰到問題時，放進 const 一定有效。

資深一點的看法：縮小靠的是程式結構。檢查和使用離得越近、中間越少重新指定，TypeScript 和讀程式的人都越容易看懂。碰到縮小失效，先想「這個值真的不會變嗎」，再用 const 把它固定下來；不要直接寫 as 或 ! 讓錯誤閉嘴，那只是把檢查關掉（第 17 課細講）。

回到結帳模組：價格、數量、備註用正確的檢查縮小；折扣、結帳狀態設計成可辨識聯合（練習 2 會用同樣的方法處理付款方式）；每個 switch 用 assertNever 收尾，老闆加會員價時編譯器會列出待辦清單。下面的練習把這幾件事各做一次。

練習

練習 1：完成 formatPrice(input)。數字回傳 'NT$110'；只含數字的字串（例如 '110'）也回傳 'NT$110'；其他字串（包括空字串）丟 RangeError（「只含數字」可以用第 5 課的正規表示式 /^\d+$/ 檢查）；null 回傳 '時價'。注意 0 元的贈品要是 'NT$0'。

練習 2：起始程式把三種付款方式塞進同一個型別，錯的組合（刷卡卻有 received）照樣寫得出來。把 Payment 改成可辨識聯合，標籤欄位是 method：現金 'cash' 帶 received: number（收了多少錢）、信用卡 'card' 帶 last4: string、LINE Pay 'linePay' 帶 transactionId: string。再改寫 paymentSummary，回傳「現金，收 500 元」「信用卡末四碼 1234」「LINE Pay 交易 TX-9」。

練習 3：OrderStatus 新增了 'refunded'（已退款），三個函式的 default: return assertNever(s) 都報錯了，這正是要補的地方。補上 refunded 的處理：標籤是「已退款」、不能取消、沒有下一步（空陣列）。不准拿掉或改掉 assertNever：資料庫裡出現沒列出的狀態時，三個函式都要丟錯。

練習 4：第 12 課的搜尋框，畫面要顯示「還沒搜尋、搜尋中、結果、錯誤」其中一種。起始程式用一個布林和兩個可選欄位表示這個狀態。把 RequestState 改寫成可辨識聯合，標籤欄位是 status：'idle'（還沒搜尋）、'loading'、'success' 帶 data: Product[]、'error' 帶 message: string。再改寫 render：idle 顯示「請輸入關鍵字」、loading 顯示「搜尋中…」、success 用「、」連接商品名稱（空陣列顯示「找不到商品」）、error 顯示「錯誤：」加上訊息。

練習 5：typeof null 的結果是什麼？

✓ 這是 JavaScript 早期的錯誤，為了相容一直保留。所以 typeof x === 'object' 不代表 x 一定是物件，TypeScript 縮小後仍然留著 | null。要排除 null，直接寫 x !== null。typeof 從來不會回傳 'null'；'undefined' 是 typeof undefined 的結果。

練習 6：qty 的型別是 number | null | undefined。if (qty) { … } 會擋掉哪些值？

✓ if 擋的是所有 falsy 值。數字裡的 0 和 NaN 也是 falsy，所以「點了 0 杯」會被當成「沒填」。只想排除 null 和 undefined，要寫 qty != null。TypeScript 不會因為這個報錯，因為縮小後的型別都是 number。a 是最常見的誤解，漏掉了 0 和 NaN；c 更少，undefined 也是 falsy。

練習 7：OrderStatus 多了 'refunded'。某個 switch 處理了原本的四種，default 寫 const _x: never = s。會發生什麼事？

✓ 處理完的狀態被一個一個縮掉，default 裡剩下的就是還沒處理的 'refunded'。'refunded' 不能指派給 never，所以在寫程式時就報錯，告訴你這裡要補。b 錯在：default 確實會「接住」剩下的值，但接住不等於處理對了，這正是窮舉檢查要擋的事。c 錯在：never 檢查就是為了在型別檢查時發現，執行時才丟錯的是 assertNever 的第二道防線。

常見錯誤

  • 用 if (x) 檢查數字或字串：0、'' 也會被當成「沒有」。明確寫 x !== null、x !== undefined 或 x != null。
  • typeof x === 'object' 卻沒排除 null：typeof null 是 'object'。先寫 x !== null。
  • 標籤欄位寫成 string：每一種的標籤都是 string，TypeScript 分不出來，不會縮小。標籤要是字面值型別。
  • 用好幾個布林和可選欄位表示狀態：組合數會爆炸，大部分是不可能的狀態。列出真正的狀態，寫成可辨識聯合。
  • default 回傳預設值，把新的情況悄悄吞掉：新增狀態之後不會有任何錯誤。default 寫 assertNever(x)，寫程式時報錯、執行時丟錯。
  • 用 as 或 ! 強迫縮小：(p as CardPayment).last4、assertNever(s as never) 只是讓編譯器閉嘴，執行時沒有任何檢查。用真正的型別守衛。
  • 在 callback 裡用 obj.prop 的縮小：物件屬性在 callback 裡不保留縮小。先放進 const。

let 變數和參數在 callback 裡的縮小（TypeScript 5.4 起）

TypeScript 5.4 起，如果 callback（箭頭函式或函式運算式；function 宣告會被提升，不算）建立在這個變數最後一次被指定之後，縮小會保留；之後還會被重新指定、或在某個 callback 裡被指定，就不保留：

switch (true) 的縮小（TypeScript 5.3 起）

TypeScript 5.3 起也看得懂 switch (true) { case typeof x === 'string': … }，每個 case 的條件都會縮小。條件很多、if／else 排成一長串時可以考慮。

用 lint 抓 if (數字)

typescript-eslint 的 strict-boolean-expressions 規則可以抓這類錯誤，跟 no-floating-promises 一樣要開 typed linting。預設會擋 number | undefined 這類可能沒值的數字和字串；連一般數字、字串都要寫明確比較，就把 allowNumber、allowString 設成 false。

小結

  • 型別縮小：經過 typeof、=== null、in、instanceof、Array.isArray 這些檢查後，TypeScript 依照程式的執行路線（控制流程分析）算出更小的型別。return、throw 也算。縮小背後是執行時真的會跑的檢查，所以安全。
  • typeof null === 'object'；真值檢查會擋掉 0 和 ''，而且 TypeScript 不會報；!= null 同時排除 null 和 undefined。
  • 可辨識聯合：每一種都有同一個標籤欄位、值是不同的字面值。檢查標籤就能縮小到其中一種。標籤寫成 string 就不會縮小。
  • 狀態寫成可辨識聯合，不可能的狀態就寫不出來，每種狀態只帶它需要的資料。
  • 窮舉檢查：default 呼叫 assertNever(x: never): never。新增情況時，報錯的位置就是要補的地方；執行時遇到意外的值會丟錯。
  • 縮小在 callback 裡可能失效：物件屬性不保留，let 和參數的規則見課末。先放進 const。
