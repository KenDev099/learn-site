階段 4：函式、泛型與型別運算 · 第 18 課

函式的型別

咖啡店後台上週出了一張怪收據：顧客刷卡結帳，收據卻印出「現金，收 undefined 元」。追下去發現，付款模組有一個 PaymentHandler 介面，規定 handle 要能處理所有付款方式。幾個月前重構付款模組時，同事把舊的、只會處理現金的 cashOnly 直接接到新的 handle 上；當時店裡只收現金，一切正常，上週開放刷卡就出事了。介面明明寫了型別，tsc 卻沒有報任何錯。

這類 bug 的共同點是「把函式交給別人用」：篩選條件交給 filter、付款處理器交給結帳流程、存檔函式交給 forEach。前幾課替資料寫型別，這一課替函式本身寫型別，目標是讓同事放錯函式、傳錯參數時，在存檔當下就看到紅線，而不是等客服拿著收據來問。學完你能：

  • 寫出「收一個商品、回傳 boolean」這種函式的型別，並設計好讀的參數
  • 分辨回傳型別 void、never、Promise<T>
  • 判斷一個函式能不能放進某個位置，認出 TypeScript 放過的不安全寫法
  • 用 overload 和 this 參數把錯誤提早到編譯時
這課的路線：
  1. 傳進來的函式怎麼寫型別：用 (p: Product) => boolean 寫出位置的要求，any 和 Function 為什麼等於沒寫（開場問題的最小答案）。
  2. 箭頭的兩邊：呼叫的人怎麼不傳錯參數（可選、預設、選項物件）；函式交回的 void、never、Promise<T> 各承諾什麼，forEach(async …) 為什麼能通過檢查。
  3. 什麼樣的函式可以放進去：回到收據事故，參數的方向為什麼跟回傳值相反，方法寫法為什麼讓 cashOnly 混了進去。
  4. overload 與 this 參數：傳一個回一個、傳一串回一串怎麼寫；方法被拿出去當 callback、this 不見時，怎麼提早到編譯時發現。
這課會用到：
  • 第 1 課的 callback 與 this：this 看函式怎麼被呼叫，方法單獨拿出來呼叫 this 就不見了。
  • 第 9 課的 async：async 函式一律回傳 Promise；forEach(async …) 不會等它完成。
  • 第 14 課的結構型別：只看形狀，欄位夠就能放進去。
  • 第 16 課的可辨識聯合 Payment：現金、信用卡、LINE Pay 三種付款，用 method 區分。

篩選條件、付款處理器：傳進來的函式怎麼寫型別？

先從最簡單的「傳進來的函式」開始：菜單篩選。後台要一個 filterMenu(items, rule)，rule 是同事傳進來的篩選條件，例如「100 元以下」。rule 不寫型別會報 TS7006（第 13 課：自己宣告的函式，參數要寫型別）。很多人這時隨手補上 any，紅線消失了，問題卻只是換了地方：同事傳進 p => p.prise < 100，把 price 拼成 prise，TypeScript 不會報錯，因為 any 表示「這個值是什麼都可以」，傳進來的函式和它的參數 p 也跟著不檢查。執行時 p.prise 是 undefined，undefined < 100 是 false，篩出來永遠是空陣列，而且沒有任何錯誤訊息。

要擋下這種錯，TypeScript 得知道「rule 是一個函式，收一個商品、回傳 true 或 false」。JavaScript 的函式是值：可以存進變數、當參數傳、當回傳值，所以它也跟數字、物件一樣能有型別。函式型別（function type）的寫法長得像箭頭函式，箭頭左邊是參數，右邊是回傳型別：(p: Product) => boolean 讀作「收一個 Product、回傳 boolean」。參數名稱 p 只是給人看的說明，(item: Product) => boolean 是同一種型別。

cheap 的 p 沒寫型別，卻是 Product，也沒有報 TS7006。原因是 cheap 被宣告成 Predicate：TypeScript 知道這個位置要的是「收 Product 的函式」，就把 Product 填給 p。這叫情境推論（contextual typing）：箭頭函式被放進一個型別已知的位置時，參數型別從那個位置推出來。filter 和 map 裡的 p 也是這樣得到 Product，因為陣列的 filter 在型別定義裡已經寫好「我會傳一個元素給你」。所以分工很清楚：自己宣告的函式（像 priceAbove）參數要寫型別；交給別人呼叫的 callback，參數通常不用寫，交給位置去推。回頭看拼錯的例子：只要 filterMenu 的 rule 標成 Predicate，同事寫的 p 就會被推成 Product，p.prise 當場報「Product 上沒有這個屬性」。

同一格的 priceAbove 示範另一個方向：函式也能回傳函式。priceAbove(100) 先決定門檻，回傳一個 Predicate，之後才拿去篩選；回傳的函式透過閉包記住 min（第 1 課）。接收函式或回傳函式的函式叫高階函式（higher-order function），filter 和 priceAbove 都是。「先給設定、回傳一個函式」在後端很常見，練習 1 的 applyDiscount 就是這個形狀：先決定折扣，再拿回傳的函式去套用每個商品。

你可能會想：只是要說「這是一個函式」，TypeScript 不是有內建的 Function 型別嗎？它看起來能描述函式，實際上等於沒寫。執行下面這格，看 getPrice 被亂傳參數時有沒有紅線：

沒有紅線。Function 只代表「這個值可以呼叫」，不記得參數有幾個、是什麼型別，也不記得回傳什麼，所以亂傳參數不報錯，呼叫結果是 any；any 又能放進 string 變數，錯誤一路傳下去，執行時印出 undefined。它跟前面的 any 是同一種問題，只是看起來比較正式。callback 的型別一律寫成 (…) => …。

到這裡可以先回答開場問題的一半：要讓放錯的函式被擋下，位置本身必須用函式型別寫清楚它要什麼，例如付款處理器的位置寫成 (p: Payment) => string；寫成 any 或 Function，TypeScript 沒有東西可以比對，什麼都放行。但開場那個介面明明寫了 Payment，還是放過了 cashOnly，可見光有型別還不夠，還要知道 TypeScript 怎麼拿兩個函式型別互相比較。比較的就是箭頭的兩邊：左邊的參數、右邊的回傳值。接下來兩節先把這兩邊各自看清楚。下一節先看左邊：參數不只有型別，也決定呼叫的人一定要給什麼、可以省略什麼，這是你自己寫函式時天天要做的設計；其中「參數有幾個」也是第三節判斷放不放得進去的第一個檢查。

呼叫的人怎麼不傳錯？可選、預設、剩餘參數與選項物件

先看箭頭左邊。參數除了型別，還決定了呼叫的人「一定要傳什麼、可以省略什麼」。TypeScript 有三種寫法處理「不一定要傳」的參數：

  • 可選參數：名稱後面加 ?。不傳時值是 undefined，所以型別自動變成 string | undefined，函式裡要自己處理 undefined，下面用 ?? 補上 NT$。
  • 預設參數：寫 = 1。不傳時用預設值，型別從預設值推出來，函式裡不用再處理 undefined。
  • 剩餘參數：寫 ...prices。把後面不定數量的引數收成一個陣列。

執行後對照每一行輸出，看「有傳」和「沒傳」各得到什麼：

剩餘參數的型別寫成陣列 number[]，因為函式裡拿到的 prices 就是一個陣列，sum(80, 110, 70) 進到函式時是 [80, 110, 70]。它前面可以有一般參數（例如 function log(level: string, ...msgs: string[])），但它必須是最後一個參數：它會把「後面所有」引數收走，放在中間的話，後面的參數永遠拿不到值。這跟下面可選參數的限制是同一個原因：引數是照位置對應的。

可選參數只能放在最後面。function f(a?: number, b: number) 會報 TS1016，因為引數是照位置對應的：呼叫 f(1) 時，1 是給 a 還是 b，分不出來。想讓前面的參數可以省略，要嘛把它挪到後面，要嘛改用下面的選項物件。

照位置對應還有一個更常見的問題：參數一多，呼叫處就看不懂了。咖啡店的 createOrder 一開始只收商品，後來陸續加了外帶、印收據、桌號：

createOrder(items, true, false, 2)              // true 是外帶？false 是不印收據？2 是什麼？
createOrder(items, { takeout: true, printReceipt: false, tableNo: 2 })

第一行的 true, false, 2 要回去翻函式定義才知道意思；兩個布林傳反了，型別檢查也不會發現，因為兩個都是 boolean。第二行叫選項物件（options object）：把參數收進一個物件，呼叫處每個值都帶著名字，順序也不重要；之後要加優惠碼，只是物件多一個可選欄位，舊的呼叫處不用改。

函式那一側通常用解構來接選項物件，並在解構時給每個欄位預設值，函式裡就直接拿到 sortBy、limit，不用一個一個寫 options.limit ?? 2。這裡有一個很常見的坑。下面的 listMenu 每個欄位都有預設值，看起來整個選項物件都可以不傳；執行後看第二次呼叫發生什麼事：

第二次呼叫在編譯時報 TS2554（少一個參數），執行時也真的丟出 TypeError。要把兩層分開看：sortBy = 'id'、limit = 2 是欄位的預設值，只在物件存在、但缺那個欄位時生效；整個選項物件本身沒有預設值，所以它還是必填。不傳時參數的值是 undefined，JavaScript 要從 undefined 解構出 sortBy，就丟出 TypeError。修法是在參數最後加上 = {}：不傳時先換成空物件，再從空物件解構，每個欄位都拿到預設值；TypeScript 看到 = {}，也會把整個參數當成可選。練習 2 的 paginate 就要這樣寫。

💡 實務上：參數一多、或出現布林值，就改用選項物件
你每天用的 API 多半長這樣：fetch(url, { method, headers, body })、各種套件的 createClient({ ... })。咖啡店後台的 createOrder 一開始可能只有 items，之後陸續加外帶、桌號、優惠碼；如果每次都往後加一個位置參數，舊的呼叫處要一起改，也容易傳錯順序。實務上的經驗法則：超過兩三個參數，或有任何布林值，就改成選項物件。只有一兩個意思很明顯的參數（getOrder(id)）就不用硬包成物件。code review 看到 f(x, true, false) 時，資深工程師通常會請你改寫。

函式交回什麼？void、never、Promise 各自的承諾

參數管的是「呼叫的人要給什麼」，箭頭右邊的回傳型別管的是「函式交回什麼、呼叫的人能拿它做什麼」。一般的回傳型別很直觀，number 就是交回一個數字；這節看三個比較特別、後端天天遇到的：void、never、Promise<T>。

void 的意思是「呼叫者不該使用回傳值」，不是「函式一定沒有回傳值」。這個差別放在函式型別上才看得出來：記錄 log、事件處理、forEach 的 callback，這些位置都標成回傳 void，意思是「你回傳什麼我都不會用」。所以放進來的函式就算有回傳值也合法，回傳值只是被忽略。這是刻意的設計（TypeScript Handbook〈More on Functions〉）：src.forEach(x => dst.push(x)) 這種寫法很常見，而 push 會回傳新的長度；如果 void 位置不接受有回傳值的函式，這行就會報錯。

never 的意思是「這個函式不會正常結束」：它一定丟錯，或永遠不停，所以不會有值交回來。這聽起來沒用，其實很好用：TypeScript 知道呼叫 never 函式之後的程式不會執行，就能據此縮小型別。後端常見的是 throwNotFound(id) 這種「找不到就丟錯」的輔助函式。

下面這格兩個都示範。執行後先看 log：logs.push 回傳 number，照樣能放進回傳 void 的位置。再看 priceOf：find 的結果是 Product | undefined，經過 if (!p) throwNotFound(id) 之後，下一行的 p.price 沒有報「p 可能是 undefined」。

priceOf 的 if 後面沒有 return，也沒有 else，TypeScript 卻知道走到 return p.price 時 p 一定存在：唯一讓 p 是 undefined 的那條路，已經被回傳 never 的呼叫截斷了。這個縮小有條件，throwNotFound 要用 function 宣告，細節見課末〈補充與查表〉。

Promise<T> 是 async 函式的回傳型別。第 9 課講過，async 函式一律回傳 Promise：就算本體 return 的是一個陣列，呼叫的人拿到的也是「之後才會給出陣列的 Promise」，要 await 才拿到陣列。所以讀菜單的函式寫成 async function loadMenu(): Promise<Product[]>，回傳型別寫 Promise<Product[]>，不是 Product[]。

三個整理成一張表：

void呼叫者不該使用回傳值記錄 log、事件處理、forEach 的 callback

把 void 和 Promise 放在一起，就會出現一個型別檢查抓不到的 bug。void 位置「回傳什麼都接受」，Promise 也是「某個值」，所以 async 函式可以放進回傳 void 的位置。第 9 課的 bug 就這樣通過了型別檢查。執行後看「forEach 之後」印出的陣列：

印出來是空陣列。forEach 對每個元素呼叫 callback，拿到 callback 回傳的 Promise 就直接丟掉，不會等它完成，所以 console.log 執行時兩筆都還沒存進去。型別上完全合法：forEach 的 callback 回傳 void，Promise 被當成「不會被用到的回傳值」。比「還沒存」更麻煩的是錯誤：Promise 被丟掉了，裡面丟出的錯誤也沒有人 catch。

型別檢查抓不到被丟掉的 Promise。回傳 void 的 callback 位置（forEach、addEventListener、setTimeout）收到 async 函式時，Promise 沒有人等，裡面丟的錯也沒有人接。這要靠第 9 課介紹過的 lint 規則：typescript-eslint 的 @typescript-eslint/no-misused-promises（預設開啟 checksVoidReturn）。依序處理用 for…of 加 await，同時處理用 Promise.all(items.map(…))。

到這裡，箭頭兩邊都看過了：參數決定呼叫的人要給什麼，回傳型別決定函式交回什麼。void 的例子也透露一件事：「放得進去」不要求兩邊型別一模一樣，有回傳值的函式就能放進 void 的位置。那一個只會處理現金的函式，能不能放進「所有付款方式」的位置？下一節回到開場的收據事故。

什麼樣的函式可以放進去？收據印出 undefined 的原因

把函式放進某個位置（傳成參數、指定給變數、放進物件的屬性）時，TypeScript 要判斷「這個函式能不能勝任這個位置」。把位置想成一份工作說明：「我會給你 X，你要交回 Y」。應徵的函式要通過三個檢查，前兩個是放寬，第三個是開場事故的關鍵：

  1. 參數比較少，可以。forEach 每次會傳（元素, 索引, 陣列）三個引數，你的 callback 只收第一個也沒關係：JavaScript 呼叫函式時，多給的引數本來就會被忽略。反過來，callback 多要了位置不提供的必填參數，才會報錯，因為多要的那個永遠拿不到；多出來的如果是可選參數，拿不到就是 undefined，函式本來就得處理，所以不會報錯。
  2. 回傳值更具體，可以。位置要的是 number | null，你一定回傳 number：呼叫者本來就準備好處理 number 和 null，只收到 number 當然沒問題。這跟上一節 void 的規則同一個方向，交回的東西只要呼叫者處理得了就好。
  3. 參數的方向是反的。位置說「我會給你任何一種付款方式」，你的函式卻只會處理現金。結帳流程不會因為你只會現金就只丟現金給你，它照樣會丟信用卡進來，這時你的函式去讀 received，讀到的是 undefined。所以參數只能跟位置一樣寬或更寬：能處理現金、信用卡、LINE Pay，甚至連 null 都能處理的函式，丟什麼進來都不怕。

第 2 點和第 3 點的方向相反：回傳值可以往「更窄」走，參數只能往「更寬」走。參數這種跟回傳值方向相反的規則，叫參數逆變（contravariance）。名字不用背，記住下圖的判斷就好：放進去的函式，要能處理位置會給的「每一種」值。

照這個規則，開場的 cashOnly 應該被擋下。下面這格把它放進兩種寫法的位置：Handle 是函式型別寫法，LooseHandler 是介面的方法寫法，兩個描述的都是「收 Payment、回傳 string」。執行後看最後一行印出什麼：

第一個指派如預期被擋下（TS2322），第二個卻通過了，最後一行印出開場那張收據：「現金，收 undefined 元」。兩者的差別只在宣告的寫法。

TypeScript 對這兩種寫法的檢查不一樣。逆變檢查由 strictFunctionTypes 這個選項負責，它是 strict 的一部分，但只檢查函式型別寫法，也就是 handle: (p: Payment) => string 這種「屬性的值是一個函式型別」的寫法，也叫屬性寫法。用方法寫法 handle(p: Payment): string 宣告時，TypeScript 改用比較鬆的規則：參數比位置寬可以，比位置窄也可以。這種兩個方向都放行的規則叫方法雙變（method bivariance）。

這個洞是刻意留的，原因出在陣列。陣列也是一個介面，它的方法都用方法寫法宣告，例如 push(...items: T[]): number。把 T 代進去：Payment[] 的 push 收 Payment，CashPayment[] 的 push 只收 CashPayment。

現在想像一個很常見的寫法：function totalOf(list: Payment[])，呼叫時傳進一個 CashPayment[]。TypeScript 要判斷 CashPayment[] 能不能放進 Payment[] 的位置，就要逐一比對兩邊的成員，push 也在其中。如果照上面的逆變規則，CashPayment[] 的 push 參數比 Payment[] 的窄，比對失敗，整個陣列就放不進去。結果是「把子型別的陣列傳給收父型別陣列的函式」這種到處都是的程式碼，全部報錯。方法雙變就是為了讓這些程式碼照舊編譯：方法的參數兩個方向都放行，CashPayment[] 就能放進 Payment[]。

代價是同一個洞不分對象：TypeScript 沒辦法只替陣列開這個例外，所有用方法寫法宣告的介面都適用，你自己寫的 PaymentHandler 也一樣。cashOnly 就是從這裡混進去的。這個設計的來由見課末〈補充與查表〉。

開場的事故到這裡完整了：PaymentHandler 用方法寫法宣告 handle，strictFunctionTypes 不檢查它，只會處理現金的 cashOnly 就混了進去。修法有兩層：介面改成屬性寫法，讓逆變檢查生效；放進去的函式真的要處理三種付款方式。練習 4 就是這個修法。

💡 實務上：替「要放函式進來」的介面用屬性寫法
這種介面在專案裡很常見：咖啡店的付款處理器、通知發送器（Email／簡訊）、各種 callback 設定。自己定義這類介面時，寫成屬性寫法 handle: (p: Payment) => string，逆變檢查才會生效；之後有人放進只會處理現金的函式，編譯時就會被擋下。class 裡的方法照常寫就好，要注意的是「定義型別、讓別人把函式放進來」的時候。想讓整個團隊一致，可以開 typescript-eslint 的 @typescript-eslint/method-signature-style 規則，它會要求介面一律用屬性寫法。

傳一個回一個、傳一串回一串：overload 怎麼寫？

前面幾節檢查的都是「函式放進位置」的那一側：放進去的函式勝不勝任。反過來，你寫給別人呼叫的函式，如果交回的型別太含糊，呼叫的人一樣會吃虧，得自己再檢查一次。這一節換一個例子，因為訂單的版本（findOrders：傳一個 id 回一筆、傳一串 id 回一串）留給練習 3 自己寫。

前面每個函式都只有一種形狀：一組參數、一個回傳型別。宣告上「參數列加回傳型別」的這一行叫簽章（signature），也就是函式型別寫在宣告上的樣子。但後台有些函式傳不同的東西，會回不同的東西。例如商品標籤的整理：傳一個標籤，回一個字串；傳一串標籤，回一個陣列。只寫一個簽章的話，參數寫成 string | readonly string[]，回傳就只能寫 string | string[]；呼叫者明明傳的是單一標籤，拿到的卻是「字串或陣列」，每次都得自己再縮小一次。這個型別沒有說謊，只是太含糊：它沒有記下「輸入是什麼，輸出就是什麼」的對應。

函式多載（overload）就是把這個對應寫出來：先列出幾個只有簽章、沒有本體的宣告，每個叫呼叫簽章，各自描述一種「這樣呼叫，就拿到這個」；最後再寫一個有本體的真正實作。執行後把滑鼠移到 one 和 many 上，看它們各自的型別：

one 是 string、many 是 string[]，呼叫者不用再縮小。但最後的 fromForm 報了 TS2769，這是 overload 最容易卡住的地方。overload 的三條規則：

  • 實作簽章（implementation signature）是最後那個有函式本體的簽章，外面看不到。所以就算它寫著 string | readonly string[]，用聯合型別的引數呼叫還是報 TS2769。需要的話，再多寫一個接受聯合的 overload。
  • TypeScript 從上往下挑第一個符合的 overload，所以比較窄的寫在前面。
  • 實作簽章要涵蓋所有 overload，但 TypeScript 不會檢查實作「傳字串時真的回傳字串」，這部分要靠你自己和測試。

第三條代表 overload 會在實作裡留下沒被檢查的地方，所以它是最後手段。回傳型別不隨輸入改變時，一個聯合型別的參數就夠了（formatPrice(price: number | string): string）；「傳什麼型別進來、就回什麼型別出去」用第 19 課的泛型比較簡單。只有輸入和輸出的對應真的不一樣，像「一個對一個、一串對一串」，才用 overload。

💡 實務上：overload 多半是「讀到」，比較少自己寫
最常遇到 overload 的地方是函式庫的型別定義：滑鼠移到 document.createElement 或 addEventListener 上，會看到「+1 overload」之類的提示，傳 'canvas' 就拿到 HTMLCanvasElement，正是 overload 帶來的好處。看到呼叫報 TS2769 時，先去看有哪幾個簽章、你的引數卡在哪一個。自己寫的業務程式碼，像咖啡店的 findOrders，只在「傳單一值回單一值、傳陣列回陣列」這種對應真的有用時才寫；寫了就要配測試，因為實作是否符合每個簽章，TypeScript 不會替你檢查。

方法被拿出去當 callback：this 不見怎麼提早發現？

最後一種「把函式交給別人」的 bug，第 1 課已經在執行時看過：this 看函式怎麼被呼叫，方法從物件上拿下來、單獨交出去，呼叫時點號前面沒有物件，this 就不見了。前面幾節的檢查都只看參數和回傳值，看不到 this，所以 TypeScript 另外提供 this 參數：在參數列的第一個位置寫 this: Cart，宣告「呼叫我的時候，this 必須是 Cart」。它只存在於型別，編譯後會被擦掉，也不佔真正參數的位置，呼叫時不用傳。執行後看 later() 那一行，在編譯時和執行時各發生什麼事：

cart.total() 點號前面是 cart，this 符合 Cart，算出 290。later() 前面沒有物件：函式不是透過物件呼叫時，點號前面沒有東西可以當 this，TypeScript 就把這時的 this 視為 void，跟宣告的 Cart 不符，報 TS2684。執行時，嚴格模式（ES module 預設就是嚴格模式）下這時的 this 是 undefined，讀 this.items 就丟出 TypeError。原本要等執行到那一行才發現的 bug，現在存檔就看得到。

這個保護要你主動寫 this 參數才有。沒有寫 this 參數的一般函式裡用到 this，會報 TS2683（this 隱含 any），這由 strict 裡的 noImplicitThis 負責。但物件或 class 裡沒寫 this 參數的方法，拿出來單獨呼叫（第 1 課的 const count = cart.count; count()）不會報錯（實測紀錄見課末）。所以會被拿去當 callback 的方法，要嘛寫上 this 參數，要嘛用第 1 課的 bind 或箭頭函式把 this 固定住。

回頭看這課處理過的錯：篩選條件寫成 any、選項物件少了 = {}、async 函式丟進 forEach、cashOnly 混進付款處理器、overload 的輸入輸出對應、方法丟掉 this。做法都一樣：把「這個函式該怎麼被用」寫進型別，讓用錯的人在存檔當下看到紅線；型別寫不到的部分（被丟掉的 Promise、overload 的實作），交給 lint 和測試。下面的練習把這幾種各做一次。

練習

練習 1：寫 applyDiscount(percent)，回傳一個 (p: Product) => Product 的函式：產生打折後的新商品，價格四捨五入到整數元（第 5 課的 Math.round），不能改到原本的商品。percent 不是 0～100 的整數時，要在呼叫 applyDiscount 的當下就丟 RangeError，不要等到套用在商品上才發現。

練習 2：寫 paginate(items, options)，把菜單分頁。options 可以不傳，也可以只傳 page 或 size（預設第 1 頁、每頁 2 筆），回傳 { items, page, size, totalPages }。page 不是 ≥ 1 的整數時丟 RangeError；超過總頁數時 items 是空陣列。用選項物件加解構預設值來寫。

練習 3：起始程式的 findOrders 只有一個簽章，呼叫者拿到的型別永遠是 Order | Order[] | undefined。改成 overload：傳一個 id 回傳 Order | undefined；傳 id 陣列（包括 readonly 陣列）回傳 Order[]，順序跟傳入的 id 相同，找不到的 id 略過。

練習 4：PaymentHandler 的 handle 用屬性寫法宣告，起始程式把只會處理現金的 cashOnly 放進去而報錯。不改介面、保留 cashOnly，讓 handler.handle 能處理三種付款方式，回傳「現金，收 500 元」「信用卡末四碼 1234」「LINE Pay 交易 TX-9」這樣的文字。

練習 5：items.forEach(async item => { await save(item) }) 為什麼沒有型別錯誤？

✓ forEach 的 callback 型別回傳 void，而「回傳 void 的位置可以放有回傳值的函式」，所以 async 函式照樣放得進去。forEach 不會等 Promise（a 錯），TypeScript 也不會改你的程式（b 錯，它只擦掉型別）。這種 bug 要靠 @typescript-eslint/no-misused-promises，改寫成 for…of 加 await 或 Promise.all。

練習 6：overload 的實作簽章寫著 (input: number | number[])，兩個 overload 分別是 (id: number) 和 (ids: number[])。手上有一個 number | number[] 的值，能直接傳進去嗎？

✓ 呼叫者只看得到 overload 簽章，實作簽章只給函式本體用，所以「實作簽章接受聯合」不算數（a 錯）。TypeScript 不會合併 overload（c 錯），而是一個一個比對，都不符合就報 TS2769。真的需要時，再多寫一個 (input: number | number[]): Order | Order[] | undefined 的 overload。

練習 7：forEach 會傳三個引數（元素、索引、陣列），menu.forEach(p => console.log(p.name)) 的 callback 只收一個，為什麼合法？

✓ 函式忽略多的引數在 JavaScript 本來就沒問題，所以 TypeScript 允許「參數比較少」的函式放進去。反過來，callback 要求比位置提供的更多參數才會報錯。TypeScript 不會改寫你的函式（b 錯），forEach 的型別也不是 any（c 錯），滑鼠移到 p 上就看得到 Product。

常見錯誤

  • callback 型別寫成 Function：參數、回傳值都不檢查，呼叫結果是 any。寫成 (p: Product) => boolean。
  • 可選參數放在必填參數前面：報 TS1016。把可選的移到最後，或整組改成選項物件。
  • 一排布林參數：createOrder(items, true, false) 沒人看得懂，也很容易傳反。改成選項物件。
  • 解構的選項參數忘了 = {}：每個欄位有預設值，整個物件卻還是必填，不傳就是 TypeError。
  • 一律用 overload：回傳型別不變就用聯合參數，輸入輸出型別一樣就用泛型（第 19 課）。overload 越多，實作裡沒有被檢查的地方越多。
  • 介面用方法寫法描述要放進來的函式：handle(p: Payment): string 會放過只處理一部分情況的函式。用屬性寫法 handle: (p: Payment) => string。
  • 把 async 函式交給回傳 void 的 callback：forEach、事件處理不會等 Promise，錯誤也沒人接，而且型別檢查不會報。開 no-misused-promises。

補充與查表

never 讓後面的程式縮小的條件

呼叫回傳 never 的函式之後會縮小型別，條件是那個函式用 function 宣告，或變數本身有明確的型別註記。寫成箭頭函式指定給變數、變數本身沒有型別註記時，呼叫之後不會縮小。本機實測 TypeScript 5.9.3 與 7.0.2 結果相同。

strictFunctionTypes 為什麼不檢查方法寫法

strictFunctionTypes 是 TypeScript 2.6 加入的，屬於 strict 的一部分。TypeScript 2.6 的 release notes 說明，方法寫法維持雙變，是為了讓 Array<T> 這類泛型介面照舊運作：Array 的 push(...items: T[]) 是方法寫法，所以 CashPayment[] 還能放進要 Payment[] 的位置。

其他 lint 工具

oxlint 的 type-aware 規則也有同名的 no-misused-promises。

沒寫 this 參數的方法拿出來呼叫

物件或 class 裡沒寫 this 參數的方法，拿出來單獨呼叫不會報錯：本機實測 TypeScript 5.9.3 與 7.0.2 相同。

小結

  • 函式型別寫成 (p: Product) => boolean；callback 的參數靠情境推論，不用自己寫；不要用 Function 或 any，它們讓位置沒有東西可以比對。
  • 可選參數放最後；參數多或有布林值時改用選項物件，解構時記得 = {}。
  • void：回傳值不該被使用，放進來的函式回傳什麼都會被忽略，包括 Promise；never：不會正常結束，呼叫之後的程式會被縮小；async 函式回傳 Promise<T>。被丟掉的 Promise 要靠 lint 抓。
  • 可指派規則：參數少可以、回傳值更具體可以、參數要一樣寬或更寬（逆變）。方法寫法是例外（雙變），收據印出 undefined 就是這樣來的；寫介面時用屬性寫法。
  • overload 描述「不同輸入、不同輸出」，實作簽章外面看不到；能用聯合或泛型就不用 overload。
  • this 參數讓「this 不對」在編譯時報 TS2684；class 方法沒寫 this 參數時抓不到。
