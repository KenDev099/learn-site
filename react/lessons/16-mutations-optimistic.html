階段 4：狀態與資料 · 第 16 課

寫入資料：mutation、樂觀更新與 useOptimistic

咖啡店後台上線第二週，店長回報：把拿鐵改成 125 元，按「儲存」沒反應，又按了兩下，後端收到三次改價；存好之後菜單列表還是 110 元，重新整理才變。客人那邊也有問題：按收藏要等一秒愛心才亮，網路斷掉時愛心亮了又沒存到；連續收藏拿鐵和可頌，拿鐵失敗了，可頌的愛心也跟著不見。

第 15 課處理「讀」：把伺服器資料當成快取。這課處理「寫」，以 TanStack Query 5.106.1 與 React 19.3.1 為準。

這課的路線：
  1. useMutation 與失效：送出中鎖住按鈕、成功後讓列表那格快取重抓，改價只送一次、列表馬上變 125 元（開場問題的最小答案）。
  2. 樂觀更新：按收藏愛心立刻亮，伺服器失敗再改回來。
  3. 好幾個樂觀更新同時進行：拿鐵失敗時，可頌的愛心為什麼不該跟著消失。
  4. variables 與 useOptimistic：不碰快取、只改這個元件畫面的另一種寫法。
  5. 怎麼選：收藏、按讚可以樂觀，改價、下單、付款為什麼要等伺服器確認。
這課會用到：
  • 第 3 課的不可變更新與 updater function：不改原本的陣列或物件，做出新的；setX(prev => …) 從最新的值算出下一個值。
  • 第 15 課的 QueryClient 與 invalidateQueries：伺服器資料以 queryKey 為地址存在 QueryClient；invalidateQueries 用 key 的前綴找出相關的快取，標成過期並重抓正在顯示的那些。

useMutation：寫入不是另一個 query

mutation（變更）是會改到伺服器資料的請求：改價、收藏、新增備註。它跟 query 有三個根本差別：

useQuery（讀）useMutation（寫）
什麼時候執行元件掛載、key 改變、過期時自動執行只有你呼叫 mutate() 才執行
結果放哪依 queryKey 存進快取，大家共用只屬於這次呼叫，不進 query 快取
失敗重試（官方預設）瀏覽器 3 次0 次：寫入重送可能變成重複下單

開場的改價表單原本長這樣：await api.updatePrice(id, price)，沒有「送出中」的狀態，失敗也沒人接。換成 useMutation：

const mutation = useMutation({
  mutationFn: (price: number) => api.updatePrice(productId, price),   // 真正送出的請求
})

// 事件處理函式裡
mutation.mutate(Number(price))

// 畫面
<button disabled={mutation.isPending}>{mutation.isPending ? '儲存中…' : '儲存'}</button>
{mutation.isError && <p role="alert">儲存失敗：{mutation.error.message}</p>}
  • mutate(variables)：送出。variables 是傳給 mutationFn 的參數，只能有一個，要多個值就包成物件 { productId, on }。
  • status：'idle'（還沒送）、'pending'、'success'、'error'，對應 isIdle、isPending…；data 是伺服器回傳的結果，error 是錯誤，variables 是這次送出的參數。
  • 再呼叫一次 mutate，狀態從頭開始，上一次的 error 就清掉了；reset() 可以手動清回 idle。
  • mutateAsync 回傳 Promise，失敗會 reject，要自己 try/catch；只是要觸發時用 mutate，錯誤一律從 mutation.error 讀，不會有沒接住的 rejection。

disabled={mutation.isPending} 同時解決了「連按三次送出三次」。只把按鈕文字改成「儲存中…」不夠，按鈕還能按（練習 1 會擋）。

對照 Vue：@tanstack/vue-query 也有同名的 useMutation，選項一樣，回傳的欄位是 ref。

寫完之後：讓快取失效

改價成功了，菜單列表為什麼還是 110 元？因為列表讀的是 ['products', 'list'] 那格快取，mutation 的結果不會自動進去。最常用的做法是第 15 課的 invalidateQueries，放在 mutation 的生命週期回呼裡：

const queryClient = useQueryClient()
const mutation = useMutation({
  mutationFn: (price: number) => api.updatePrice(productId, price),
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['products'] }),
})

['products'] 是前綴：列表 ['products', 'list'] 和售價 ['products', 'detail', 2] 都會被選到，畫面上正在用的立刻重抓。加了 exact: true，或只寫 ['products', 'list']，售價那一格就漏了（練習 1 會擋）。

注意這裡是回傳了 invalidateQueries 的 Promise。官方文件：回呼回傳 Promise 時，TanStack Query 會等它完成才進到下一步，mutation 在這段期間仍是 pending。所以按鈕會一直顯示「儲存中…」到列表重抓完，店長看到按鈕恢復時，畫面上已經是新價格。寫成 onSuccess: () => { queryClient.invalidateQueries(…) }（大括號、沒有 return），按鈕會先恢復、價格晚一點才變。兩種都合理，差在你要不要讓使用者等到畫面一致。

回呼的執行順序：

回呼可以寫在兩個地方，行為不一樣。官方文件說明：寫在 useMutation 選項裡的，每次 mutate 都會執行，而且先執行；寫在 mutate(vars, { onSuccess }) 的，元件在請求完成前卸載了就不會執行，連續呼叫好幾次時也只對最後一次執行。所以讓快取失效這種「一定要做」的事放在 useMutation；關掉對話框、跳轉頁面這種「元件還在才有意義」的事，放在 mutate 的第二個參數。

還有一個選擇：伺服器回傳了更新後的商品，可以 queryClient.setQueryData(['products', 'detail', 2], saved) 直接寫進快取，省一次請求。代價是你要自己找出所有受影響的快取（列表、搜尋結果、分類…）並一一改對；invalidate 只要選對前綴。一般先用 invalidate，請求真的太貴再考慮。千萬不要拿使用者輸入的值寫進快取當結果，那份資料沒經過伺服器確認（伺服器可能四捨五入、拒絕、或同時被別人改了）。

💡 實務上：每個 mutation 都要回答「改了之後誰會變」
咖啡店後台改價，會影響菜單列表、商品詳細、搜尋結果，可能還有購物車的小計和今日營收報表。寫 mutation 時順手列出受影響的 key，code review 時看到沒有 invalidate 的 mutation 就該問一句。key 用第 15 課的 key factory 產生，失效時寫 productKeys.all，不會因為少打一個字漏掉。範圍拿不準時寧可寬一點：多重抓一次是一個請求，漏掉的代價是客人看到舊價格。

樂觀更新：先改快取，失敗再改回

收藏按鈕照上面的寫法：按下去 → 等伺服器 → 重抓收藏清單 → 愛心才亮。網路慢時客人以為沒按到，又按一次，結果取消了收藏。Vue 課第 17 課說過，樂觀更新（optimistic update）是先假設伺服器會成功、立刻改畫面；失敗了再回復（rollback）。用 TanStack Query 時，「畫面」就是快取，所以是在 onMutate 裡先改快取：

const mutation = useMutation({
  mutationFn: (on: boolean) => api.setFavorite(productId, on),
  onMutate: async on => {
    await queryClient.cancelQueries({ queryKey: ['favorites'] })            // ① 取消進行中的重抓
    const previous = queryClient.getQueryData<number[]>(['favorites'])      // ② 記下改之前的值
    queryClient.setQueryData<number[]>(['favorites'], old =>                 // ③ 先改快取
      old && (on ? [...old, productId] : old.filter(id => id !== productId)))
    return { previous }                                                     // ④ 交給後面的回呼
  },
  onError: (_error, _on, context) => {
    queryClient.setQueryData(['favorites'], context?.previous)              // ⑤ 失敗：改回去
  },
  onSettled: () => {
    void queryClient.invalidateQueries({ queryKey: ['favorites'] })         // ⑥ 不管成敗，跟伺服器對齊
  },
})

每一步都有理由，少一步就有對應的 bug：

  1. cancelQueries：按下去之前，可能正好有一個重抓在跑（例如視窗剛回到前景）。它讀到的是還沒收藏的資料，晚一點回來就會蓋掉你剛寫進去的愛心。這課實測：沒有 cancel，舊重抓回來後愛心熄掉；有 cancel，TanStack Query 會丟掉那個結果，就算 API 沒理會 signal 也一樣。官方範例因此都 await 它。
  2. 先記下再改：順序反了，存到的就是改過的值，失敗時「改回去」等於沒改。
  3. setQueryData 要不可變：官方文件寫明更新必須是 immutable。old.push(id) 會把②存的那份也一起改掉（兩個是同一個陣列），畫面看起來正常，失敗時卻改不回去。練習的假後端把資料凍結了，push 會直接丟 TypeError。updater 收到 undefined（快取還沒有資料）時回傳 undefined，TanStack Query 就不寫入。
  4. onMutate 的回傳值：會以第三個參數傳給 onSuccess、onError、onSettled（官方文件稱為 onMutateResult，上面取名 context）。
  5. onError 改回去：只靠⑥的重抓也會回到正確的值，但要等一個請求的時間，這段期間畫面是錯的；網路斷了的話重抓也失敗，就一直錯下去。
  6. onSettled 重抓：成功時確認伺服器真的是這樣；失敗時也要，因為「失敗」可能只是回應沒收到，伺服器其實已經存了。

這裡的 onSettled 刻意不回傳 Promise，跟上一節相反。這課實測：寫成 onSettled: () => queryClient.invalidateQueries(…)，失敗時 mutation 要等重抓完成才變成 error，「收藏失敗」的訊息晚了一個請求才出現。樂觀更新的畫面已經先變了，不需要讓 mutation 等重抓。

對照 Vue 課第 17 課：那裡自己存「伺服器最後確認過的值」並在 catch 裡改回去；這裡快取就是那份狀態，onMutate／onError／onSettled 是三個固定的位置。

好幾個樂觀更新同時進行

上一節是官方範例的寫法，只按一個沒問題。客人在菜單上連續按拿鐵、可頌（兩個請求都還沒回來），會出兩種事：

  • 整份還原蓋掉別人：按拿鐵時存的 previous 是 []；按可頌時快取已經是 [2]，改成 [2, 5]。拿鐵失敗，onError 把整份還原成 []，可頌的愛心也不見了，但可頌的請求還在跑、之後可能成功。
  • 太早重抓造成閃爍：拿鐵先成功，onSettled 馬上重抓。伺服器這時只有拿鐵，重抓回來的 [2] 蓋掉快取，可頌的愛心熄掉；等可頌成功、再重抓一次，又亮回來。

修法有兩個，分別對應兩個問題：

const favoriteKey = ['favorite']

function setOne(list: number[], productId: number, on: boolean) {
  if (on) return list.includes(productId) ? list : [...list, productId]
  return list.filter(id => id !== productId)
}

useMutation({
  mutationKey: favoriteKey,
  mutationFn: ({ productId, on }: Vars) => api.setFavorite(productId, on),
  onMutate: async ({ productId, on }) => {
    await queryClient.cancelQueries({ queryKey: ['favorites'] })
    queryClient.setQueryData<number[]>(['favorites'], old => old && setOne(old, productId, on))
  },
  onError: (_error, { productId, on }) => {
    // 只改回「這一次」改的那個商品，別人改的原封不動
    queryClient.setQueryData<number[]>(['favorites'], old => old && setOne(old, productId, !on))
  },
  onSettled: () => {
    // 自己還算在裡面：等於 1 代表這是最後一個
    if (queryClient.isMutating({ mutationKey: favoriteKey }) === 1) {
      void queryClient.invalidateQueries({ queryKey: ['favorites'] })
    }
  },
})
  • 回復用 variables，不用快照：onError 的第二個參數就是這次的 variables，反向套用只影響這個商品。
  • 最後一個結束才重抓：queryClient.isMutating(filters) 回傳符合條件、還在 pending 的 mutation 數量。要用 mutationKey 篩選，useMutation 就得設 mutationKey（官方文件：要讓 isMutating、useMutationState 比對到它，就需要 key）。這課實測兩個收藏同時進行時，第一個的 onSettled 裡讀到 2：自己還算在裡面，所以條件是 === 1，寫 === 0 就永遠不會重抓。

這跟 Vue 課第 17 課「用序號、以最後一次為準」是同一個問題的兩種解法：Vue 那邊是同一個按鈕連點，所以只讓最新一次回復；這裡是不同商品同時進行，所以每次只回復自己那一格，並且等全部結束才和伺服器對齊。

另一條路是讓請求排隊：useMutation 的 scope: { id: 'favorite' }，官方文件說明同一個 scope id 的 mutation 會照開始的順序一個接一個執行。不會互相交錯，代價是後面的要等前面的，連按十個就是十倍的時間。

💡 實務上：測樂觀更新要測「失敗」與「同時」
樂觀更新的 bug 在開發時幾乎看不到：本機的 API 又快又不會失敗。QA 或客服回報的是「網路不穩時愛心忽亮忽暗」「收藏清單少了一個」。資深工程師寫測試時會讓假 API 手動決定每個請求何時、以什麼結果完成（這課練習的 resolve()／reject()），至少測三種：失敗回復、兩個同時進行一個失敗、先完成的那個觸發的重抓。

只改畫面：variables 與 React 19 的 useOptimistic

不一定要改快取。TanStack Query v5 的文件提供第二種樂觀更新：不碰快取，直接用 mutation 的 variables 和 isPending 畫出「送出中的那一筆」：

const add = useMutation({
  mutationFn: (text: string) => api.addNote(text),
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['notes'] }),
})

<ul>
  {notes.map(n => <li key={n.id}>{n.text}</li>)}
  {add.isPending && <li style={{ opacity: 0.5 }}>{add.variables}（送出中）</li>}
</ul>

失敗時 isPending 變回 false，那一列自然消失，不需要回復；onSettled 回傳了 Promise，所以成功時那一列會撐到列表重抓完才消失，不會閃一下空白。官方文件說這種做法適合「只有一個地方要顯示樂觀結果」；要讓好幾個元件都看到（例如頁首的收藏數），還是改快取。

React 19 內建了同樣想法的 hook：useOptimistic，不需要 TanStack Query。交班備註不放在任何快取裡，只是元件的 state：

const [notes, setNotes] = useState<Note[]>(initialNotes)          // 伺服器確認過的
const [shown, addPending] = useOptimistic(
  notes,                                                            // 沒有進行中的 Action 時，就是它
  (current, note: Shown) => [...current, note],                     // reducer：怎麼把樂觀的那筆加上去
)

function handleSubmit(e: FormEvent) {
  e.preventDefault()
  const value = text.trim()
  setText('')
  startTransition(async () => {                                     // Action
    addPending({ id: tempId(), text: value, pending: true })
    try {
      const saved = await api.addNote(value)
      startTransition(() => setNotes(list => [...list, saved]))      // await 之後要再包一層
    } catch {
      setError(`「${value}」沒有送出，請再試一次`)
    }
  })
}

官方文件對 useOptimistic(value, reducer?) 的說明：回傳的 shown 在沒有進行中的 Action 時等於 value；Action 進行中，等於 reducer 算出來的結果。Action 是在 Transition 裡執行的函式，這裡是傳給 startTransition 的 async 函式（第 17 課的 <form action> 也是）。Action 結束時樂觀的值自動消失，畫面回到 value：

  • 成功：await 之後 setNotes 把伺服器的那筆加進 notes，Action 結束，shown 變成新的 notes，「送出中」換成確認過的那筆。
  • 失敗：notes 沒變，Action 結束，送出中的那筆自己消失。官方文件：Action 丟錯時 Transition 照樣結束，畫面回到目前的 value。不用寫任何回復的程式，這是它比手寫 useState 好的地方。

三個容易踩的地方，都在 React 19.3.1 實測過：

寫法結果
在 startTransition 外面呼叫 addPendingConsole 出現 An optimistic state update occurred outside a transition or action；這次的實測裡，送出中的那筆在全部結束後還留在畫面上
await 之後直接 setNotes，沒有再包 startTransition官方文件說明 await 之後的更新不會被當成 Transition（JavaScript 目前做不到跨 await 追蹤）。實測同一筆短暫出現兩次：確認過的一筆加上還沒消失的送出中那筆
沒有 try/catch錯誤從 Action 丟出去，畫面上沒有任何訊息；實測（沒有 Error Boundary）只在 Console 印出錯誤。官方文件說明 useTransition 回傳的 startTransition 丟出的錯誤會交給最近的 Error Boundary（第 13 課），那會換掉整塊畫面，送出失敗這種預期中的錯誤還是自己 catch

還有一個文件寫明的限制：好幾個 Transition 同時進行時，React 目前會把它們合在一起。實測連續送出兩筆，第一筆成功了，畫面上仍是「送出中」，要等第二筆也結束才一起換成確認過的版本。所以一個永遠不回應的請求，會讓所有樂觀的值都卡著，請求要有逾時（timeout）。

reducer 和直接給值的差別：官方文件建議要帶資料進去（加哪一筆）時用 reducer，因為 Action 進行中 value 改變的話，React 會用新的 value 重新跑 reducer，樂觀的那筆會加在最新的列表上。

對照 Vue：Vue 沒有對應的內建 API，Vue 課第 17 課是用 ref 手寫「先改、失敗改回」。useOptimistic 省掉的就是「改回」那一半。

選哪一種，以及什麼時候不要樂觀

做法樂觀的值放哪失敗時適合
只 invalidate（不樂觀）沒有，等伺服器顯示錯誤改價、下單、付款：要等確認的操作
onMutate 改快取query 快取，所有讀這個 key 的元件都看得到onError 自己改回收藏、按讚、勾選；好幾個地方要同步顯示
mutation 的 variables這個元件的 render 裡自然消失新增一筆、只有一個地方顯示
useOptimistic這個元件，Action 期間自然消失沒用 TanStack Query 的 state、第 17 課的表單 Action

什麼時候不要樂觀更新，判斷方式跟 Vue 課一樣：失敗了回復畫面，挽不挽得回現實。付款、送出訂單、退款、刪除會員，畫面先顯示「完成」，客人可能已經離開櫃台，店員可能已經開始做飲料。這類操作顯示「處理中」、停用按鈕、等伺服器確認，就是練習 1 的寫法。還有一種是伺服器會改寫結果的：改價時後端可能四捨五入或拒絕，樂觀顯示一個之後會被推翻的數字，不如老實等。

💡 實務上：樂觀與否是產品決定，失敗的文案要先想好
這件事要跟 PM 和設計師一起決定，不是工程師自己覺得快就好。開工前會先問：失敗機率多高？失敗了要怎麼告訴使用者（toast、按鈕旁的紅字、送出中的那筆變紅色加「重試」）？使用者連續操作時怎麼辦？設計稿通常只畫成功的樣子，回復時愛心「閃一下又熄掉」對使用者是困惑的，要搭配看得到的錯誤訊息。後台這種店員一天用八小時、操作有後果的介面，多半選擇不樂觀，換來畫面上的每個數字都可信。

練習

在 learn/ 執行 node check.mjs react 16。四題都用 shop-api.ts 的假後端：它記得伺服器上的資料，寫入要等測試呼叫 resolve() 才真的存進去，reject() 就是伺服器沒存；回傳的資料是凍結的，就地修改會丟錯。每個測試一個新的 QueryClient（關掉 retry），請求完成後用 settle() 等 TanStack Query 通知元件。練習 3 從練習 2 的寫法出發，練習 4 不用 TanStack Query。

練習 1：改 PriceEditor，用 useMutation 呼叫 api.updatePrice(productId, 價格)，價格是輸入框的數字。送出中按鈕 disabled、文字是「儲存中…」，連按只送出一次；伺服器還沒存好之前不能讓快取失效；成功後讓 ['products'] 開頭的 query 全部失效，菜單列表（['products', 'list']）和售價（['products', 'detail', id]）都重抓、顯示新價格，而且重抓完成之前按鈕仍是「儲存中…」。失敗時顯示 <p role="alert">儲存失敗：錯誤訊息</p>，再送出、成功後訊息消失。

練習 2：把 FavoriteButton 改成樂觀更新。按下去呼叫 api.setFavorite(productId, 按下去之後的狀態)，不等伺服器就反轉 aria-pressed（在 onMutate 用 setQueryData 改 ['favorites']，建立新陣列）；改之前先 cancelQueries，按下去之前就在跑的重抓晚回來也不能蓋掉；失敗時馬上改回原本的狀態並顯示 <p role="alert">收藏失敗，請再試一次</p>；不管成功或失敗都重抓一次 ['favorites']。收藏、取消收藏、不同商品都要對。

練習 3：FavoriteMenu 是整份菜單的收藏按鈕，共用一個 useMutation，起始程式是練習 2 的寫法。改成能同時進行好幾個：失敗時只改回那一次的商品，其他還在進行的收藏不受影響；還有收藏請求在進行時不重抓，最後一個結束時（成功或失敗）重抓一次。按下去立刻改、失敗改回這些練習 2 的要求都要保留。

練習 4：ShiftNotes 用 useOptimistic 讓交班備註送出後立刻出現在列表最後，文字後面加「（送出中）」，輸入框清空，只有空白時不送出。在 startTransition 的 Action 裡加樂觀的那一筆（不能有 React 的 optimistic 警告）；成功後把伺服器回傳的備註加進 notes，任何時候同一筆都不能出現兩次；失敗時送出中的那筆消失，顯示 <p role="alert">「備註文字」沒有送出，請再試一次</p>，下一次送出時清掉這個訊息。

練習 5：收藏的 onMutate 沒有先 await queryClient.cancelQueries(…)。客人切回分頁（觸發背景重抓）的同時按了收藏，會怎樣？

✓ 重抓在按下去之前就送出了，讀到的是還沒收藏的伺服器資料，它回來時照常寫進快取。cancelQueries 讓 TanStack Query 丟掉那個進行中的結果，樂觀的值才留得住。a 搞反了時間順序：setQueryData 雖然在請求送出之後執行，但重抓的「回應」比它晚到。c 不存在，mutation 和 query 預設互不等待。

練習 6：改價成功後要關掉對話框，也要讓菜單失效。下面哪種安排對？

✓ 官方文件：mutate 的回呼在元件卸載後不會執行，連續呼叫時也只對最後一次執行。失效是「一定要做」的事，放在 mutate 的話，使用者送出後馬上離開頁面，快取就不會失效（a 的問題）。關對話框是「元件還在才有意義」的事，適合放在 mutate。b 也能動，但這個 mutation 在別處重用時，每個呼叫的地方都會被關對話框。

練習 7：useOptimistic 版的交班備註，送出後 api.addNote 失敗了。你的程式只在 catch 裡設定錯誤訊息，沒有改任何 state。送出中的那筆會怎樣？

✓ useOptimistic 的值只在 Action 進行中存在，Action 結束（不管成功或失敗）就回到傳進去的 value。失敗時 notes 沒變，所以那筆自然消失，這就是不用寫回復程式的原因。b 是用 useState 直接加進 notes 時才需要的回復。c 只會發生在還有別的 Action 沒結束時（React 會把同時進行的 Transition 合在一起），全部結束後還是會消失。

常見錯誤

  • mutation 成功後沒有讓快取失效：列表和詳細頁一直是舊資料。在 useMutation 的 onSuccess／onSettled 裡 invalidate，用前綴選到所有受影響的 key。
  • 拿使用者輸入的值寫進快取當結果：沒經過伺服器確認。用伺服器回傳的資料，或 invalidate 重抓。
  • 送出中沒有停用按鈕：連按送出好幾次。disabled={mutation.isPending}；付款、下單這類操作伺服器也要防重複。
  • 一定要做的事寫在 mutate 的回呼：元件卸載後不會執行。失效寫在 useMutation 的選項。
  • 樂觀更新沒有先 cancelQueries：進行中的舊重抓回來蓋掉樂觀的值。
  • 先改快取才存原本的值，或就地修改快取：回復時改不回去。先 getQueryData，再用建立新陣列的 updater 改。
  • 失敗時只靠重抓、或什麼都不做：畫面錯一段時間或一直錯。onError 立刻改回，再加上看得到的錯誤訊息。
  • 同時進行時整份還原、每次結束都重抓：別的商品的樂觀結果被蓋掉、愛心閃爍。用 variables 只改回自己那一格；isMutating({ mutationKey }) === 1 才重抓。
  • useOptimistic 的 set 在 Action 外面呼叫、await 後的 setState 沒包 startTransition：React 警告、樂觀的值卡住或同一筆出現兩次。
  • 對不可逆的操作樂觀更新：付款、下單要等伺服器確認。

小結

  • useMutation 只在 mutate() 時執行、預設不重試，提供 isPending、error、variables；送出中停用按鈕。
  • 寫入之後在 useMutation 的回呼裡 invalidateQueries；回傳它的 Promise，mutation 會等重抓完才結束。一定要做的事放 useMutation 的選項，元件相關的放 mutate 的第二個參數。
  • 快取式樂觀更新：onMutate 先 cancelQueries、存下原值、不可變地改快取；onError 改回；onSettled 重抓對齊。
  • 好幾個同時進行時，用 variables 只回復自己的那一格，用 mutationKey 加 isMutating() === 1 只在最後一個結束時重抓。
  • 只在一個地方顯示時，可以不碰快取：TanStack Query 的 variables，或 React 19 的 useOptimistic，Action 結束就自動回到真正的 state。
  • 樂觀更新適合失敗機率低、回復無妨的操作；付款、下單、會被伺服器改寫的值，老實等確認。
