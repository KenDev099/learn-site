階段 6：品質與期末專題 · 第 24 課

錯誤處理、無障礙與前端監控

咖啡店的線上點餐做週末促銷，星期一收到三則回報。客人說按了「結帳」沒有任何反應，又按了好幾次；一位用讀螢幕軟體的熟客說，點了「購物車」之後什麼都沒唸，按掉一杯拿鐵之後就不知道自己在頁面的哪裡；客服轉來一張截圖，首頁的推薦區塊寫著「這個區塊暫時無法顯示」，工程師打開監控，週末一筆錯誤都沒有。

三則回報是同一條線上的三個缺口：出錯時客人看到什麼、每個客人都用得了嗎、我們怎麼知道出事了。前面的課各處理過一段（第 13 課的 Error Boundary、第 17 課表單的錯誤訊息、第 18 課路由的 ErrorBoundary），這課把它們串起來，補上 React 特有的無障礙工作，再接到正式環境的監控。版本以 React 19.3.1、React Router 8.5.1 為準。

這課的路線：
  1. 錯誤的地圖：每一種錯誤落在哪裡、客人看到什麼、有沒有人知道。
  2. 事件處理函式的錯誤：Error Boundary 攔不到，預期中的顯示、預期外的回報。
  3. 換頁之後：單頁應用要自己移動焦點、換分頁標題。
  4. 畫面局部改變：狀態訊息、移除之後焦點去哪、用 useId 關聯說明文字。
  5. 接上監控：createRoot 的三個錯誤選項與 window 事件，以及正式環境該收什麼、效能也要量。
這課會用到：
  • 第 13 課的 Error Boundary：攔下子孫元件 render 時的錯誤、改畫 fallback；攔不到事件處理函式與非同步 callback 的錯誤。
  • 第 17 課的錯誤分類：預期中的錯誤（驗證沒過、庫存不足）放進 state 顯示，預期外的錯誤（程式錯誤）丟出去；欄位用 aria-invalid、aria-describedby 關聯訊息。
  • 第 7 課的 ref 與焦點：ref 指到 DOM 節點，在事件或 effect 裡呼叫 focus()；一串節點用 ref callback 加清理函式收進 Map。
  • Web 課第 5 課的無障礙基礎：tabindex="-1" 讓程式能聚焦、Tab 不會停；live region 在內容改變時唸出來，而且要先存在。這課不重講，只講 React 要多做的事。
練習不安裝監控服務與 axe：錯誤交給一個自己定義的 Reporter 介面，當作監控服務的替身；無障礙用 Testing Library 的角色查詢與 jest-dom 的 toHaveAccessibleName 檢查名稱與焦點。happy-dom 沒有讀螢幕軟體，實際唸出來的效果要在瀏覽器裡手動確認。

錯誤的地圖：每一種錯誤落在哪裡

先把開場的三則回報放進一張地圖。一個錯誤從丟出來到被處理，要回答兩個問題：客人看到什麼、工程師怎麼知道。React 19 依錯誤發生的位置，交給不同的地方：

錯誤發生在誰接到客人看到怎麼回報
元件 render、effect、use 讀到失敗的 Promise，外面有 Error Boundary最近的 Error Boundary（第 13 課）；路由的 loader 是路由的 ErrorBoundary（第 18 課）那一塊換成 fallbackcreateRoot 的 onCaughtError
同上，但沒有 Error Boundary沒有人整個 UI 被移除，空白頁onUncaughtError
React 自己恢復的錯誤（例如第 22 課的 hydration 不一致）React可能閃一下onRecoverableError
事件處理函式、setTimeout 裡丟的錯沒有人什麼都沒變window 的 error 事件
沒有人接的 Promise 失敗（async 的 onClick 沒有 catch）沒有人什麼都沒變window 的 unhandledrejection 事件
預期中的錯誤：驗證沒過、庫存不足、404你自己 catch，放進 state（第 15～18 課）寫給客人看的訊息通常不回報

開場的三則回報各落在一格：

  • 結帳沒反應：onClick 是 async 函式，await api.checkout() 失敗了沒人接，落在「沒有人接的 Promise」那一格。客人什麼都看不到，又沒有監聽 unhandledrejection，工程師也不知道。
  • 推薦區塊無法顯示：Error Boundary 做好了，客人至少看到 fallback；但沒有設定 onCaughtError，React 19.3.1 預設只把它印在瀏覽器的 console，監控收不到。
  • 熟客不知道到了哪裡：這不是程式丟錯，畫面在一般人眼裡完全正常，所以更難被發現。後面的「換頁之後」「畫面局部改變」兩節處理它。

這就是開場問題的最小答案：每一格都要有人接。預期中的錯誤自己接住、顯示給客人；預期外的錯誤顯示通用的訊息，同時交給監控；Error Boundary 只管畫面，回報交給 createRoot 的三個選項和 window 的兩個事件（最後兩節）。

React 19 的預設行為（react.dev 的 createRoot 文件說 render 的錯誤不再往外丟、改交給這三個選項；預設做什麼看 react-dom 19.3.1 的原始碼）：沒人攔的錯誤、可恢復的錯誤，以及事件處理函式裡丟的錯，都交給瀏覽器的 reportError()，所以會觸發 window 的 error 事件；被 Error Boundary 攔下的錯誤只用 console.error 印出來，不會觸發任何事件。所以只監聽 window 的事件，會漏掉所有被攔下的錯誤，開場的第三則回報就是這樣漏的。

對照 Vue 課第 21 課：Vue 的 app.config.errorHandler 連事件處理函式的錯誤都收得到；React 的三個選項只管 render 這一側，事件處理函式要靠 window 的事件或自己 catch。

事件處理函式的錯誤：預期中的顯示，預期外的回報

地圖裡最常被漏掉的是事件處理函式。結帳按鈕原本只寫了成功：

async function checkout() {
  const result = await api.checkout()     // 失敗了：沒人接，畫面不變
  setOrderId(result.orderId)
}

Error Boundary 只攔 render 的錯誤（第 13 課），這裡要自己 catch。catch 之後的問題是「這個錯誤是哪一種」，分法跟第 17、18 課一樣：

錯誤例子給客人看回報
預期中：伺服器說這個要求不行（4xx）409 庫存不足、422 欄位錯誤伺服器給的說明：「拿鐵庫存不足」不回報
預期外：伺服器壞了（5xx）503、閘道逾時通用訊息：「結帳失敗，請稍後再試」回報
預期外：網路或程式錯誤TypeError: Failed to fetch、讀到 undefined 的屬性通用訊息回報
const [pending, setPending] = useState(false)
const [error, setError] = useState<string | null>(null)

async function checkout() {
  setPending(true)
  setError(null)                                        // 再按一次時清掉上一次的訊息
  try {
    const result = await api.checkout()
    setOrderId(result.orderId)
  } catch (e) {
    if (e instanceof ApiError && e.status >= 400 && e.status < 500) {
      setError(e.message)                               // 預期中：伺服器的說明
    } else {
      reporter.capture(e, { source: 'handler' })        // 預期外：回報原本的錯誤
      setError('結帳失敗，請稍後再試')
    }
  } finally {
    setPending(false)                                   // 成功、失敗都要恢復按鈕
  }
}

<button type="button" onClick={checkout} disabled={pending}>{pending ? '結帳中…' : '結帳'}</button>
{error && <p role="alert">{error}</p>}

這段程式裡的 reporter 是練習用的監控替身：capture(錯誤, { source })，source 記下錯誤從哪裡來（這裡是 'handler'，自己 catch 到的）。正式環境換成監控服務的 SDK，呼叫的地方長得一樣。

幾個寫法上的選擇：

  • 預期外的錯誤不顯示原文：Cannot read properties of undefined 對客人沒有意義，5xx 的訊息還可能洩漏伺服器的內部資訊。原文交給監控，畫面給通用訊息。
  • catch 之後不要再 throw：想「交給 Error Boundary」也沒用，async 函式裡丟出去的錯誤變成沒人接的 Promise 失敗，回到地圖的最後一格。
  • 想讓整塊換成 fallback：第 16 課提過，useTransition 的 startTransition 裡丟出的錯誤會交給 Error Boundary。適合真的不該發生的錯誤，代價是那一塊畫面連同客人的輸入一起換掉；送出失敗這種常見的情況，還是像上面一樣接住。
  • 表單用 useActionState 也是同樣的分法（第 17 課）：預期中的錯誤回傳成 state，預期外的回報、顯示通用訊息。

role="alert" 在這裡用 {error && …} 條件 render 是可以的：WAI-ARIA 的 Authoring Practices Guide（APG）說動態出現的 alert 大部分讀螢幕軟體會自動唸出來，第 15～17 課的寫法也是這樣。下一種狀態訊息（role="status"）就不行，後面會講。

💡 實務上：錯誤訊息要和 PM、後端一起定
「哪些錯誤是預期中的、客人看到什麼字」是產品決定。開工前跟後端確認錯誤格式：哪些狀態碼帶著可以給客人看的 message、哪些只是除錯用；跟 PM 確認每一種失敗的文案和下一步（重試、回購物車、聯絡門市）。code review 時看三件事：async 的事件處理函式有沒有 catch、catch 裡有沒有分類、預期外的有沒有回報。只寫 catch (e) { setError(e.message) } 的程式，兩個缺點都有：客人看到看不懂的英文，監控什麼都沒收到。

到這裡，客人在出錯時看得到發生什麼事。下一個問題是：不是每個客人都用眼睛看畫面。

換頁之後：焦點與分頁標題

上一節讓錯誤看得到；這一節讓換頁「聽得到」。熟客用讀螢幕軟體點了「購物車」：傳統的多頁網站，瀏覽器載入新頁面，焦點回到頁面開頭，讀螢幕軟體唸出新的分頁標題，使用者馬上知道換頁了。單頁應用的換頁只是 React 換掉 <Outlet /> 裡的元件，焦點留在剛剛點的連結上，分頁標題也沒變，讀螢幕軟體沒有任何東西可唸。

React Router 的無障礙文件寫明，它接手路由之後不對 UI 做任何假設：換頁時焦點要移到哪裡、要不要用 live region 宣告，都由你決定。常見的做法是兩件事：換分頁標題、把焦點移到新頁面的 <h1>。

分頁標題：React 19 的 <title>

React 19 起，元件裡 render 的 <title> 不管寫在哪一層，React 都會把它放進 document.head（react.dev 的 <title> 文件），React Router 的文件也建議 React 19 直接這樣寫。每一頁共用一個 Page 元件：

export function Page({ title, children }: { title: string; children?: ReactNode }) {
  return (
    <section>
      <title>{`${title}｜好咖啡`}</title>      {/* children 必須是一個字串 */}
      <h1 tabIndex={-1}>{title}</h1>           {/* 程式能聚焦，Tab 不會停 */}
      {children}
    </section>
  )
}

看註解那兩行。第一行：文件寫明 <title> 的 children 必須是單一字串，<title>{title}｜好咖啡</title> 在 JSX 裡是兩個 children（變數和文字），文件說會出錯；react-dom 19.3.1 實測沒有任何警告，分頁標題直接變成空的。所以用樣板字串組成一個字串。文件也提醒同時只能 render 一個 <title>，兩個都會被放進 head，瀏覽器用哪個沒有定義，所以標題只放在 Page 這一層。第二行：tabIndex={-1} 是 Web 課第 5 課的 tabindex="-1"，寫成 tabIndex={0} 的話，h1 會出現在 Tab 順序裡，鍵盤使用者每頁都要多按一次。

焦點：pathname 換了才移動

export function ShopLayout() {
  const { pathname } = useLocation()
  const mainRef = useRef<HTMLElement>(null)
  const shownPath = useRef(pathname)             // 上一次處理過的 pathname

  useEffect(() => {
    if (shownPath.current === pathname) return   // 第一次載入、StrictMode 多跑的那次：不動
    shownPath.current = pathname
    mainRef.current?.querySelector<HTMLElement>('h1')?.focus()
  }, [pathname])

  return (<><nav aria-label="主選單">…</nav><main ref={mainRef}><Outlet /></main></>)
}

effect 在 commit 之後執行（第 5 課），這時新頁面的 h1 已經在 DOM 裡。三個判斷各擋一種錯：

  • 比較 pathname，不比較整個 location：菜單頁的搜尋框每打一個字就改一次 ?q=（第 14 課的 URL 狀態），location 和 location.key 都會變。依賴它們，客人打一個字，焦點就被搶到 h1。
  • 第一次載入不移動：剛打開網站時瀏覽器已經從頁面開頭開始，搶到 h1 會跳過頁首和導覽。
  • 用「上一次的 pathname」判斷，不用「是不是第一次」的旗標：第 3 課的 StrictMode 在開發時會把 effect 多跑一次（掛載、清理、再掛載）。寫 firstRender.current = false 的旗標，第二次執行時旗標已經是 false，第一次載入就把焦點移走了。比較 pathname 不受影響：兩次看到的都是同一個值。

焦點移到 h1 之後，讀螢幕軟體會唸出標題，鍵盤使用者從新頁面的內容繼續按 Tab。另一種做法是保留焦點、用 live region 唸「已前往購物車」；React Router 的文件把這兩種都列為要考慮的事，選哪一種跟團隊的設計決定一起定，重點是一個網站統一。

💡 實務上：無障礙的驗收要有人真的用鍵盤走一遍
換頁的焦點、移除之後的焦點，自動檢查工具（axe、Lighthouse）都抓不到，因為它們只看某一刻的 DOM。上線前的驗收清單加一項：只用鍵盤走完「選商品 → 加入購物車 → 結帳」，再開 VoiceOver（macOS）或 NVDA（Windows）走一次，注意每次換頁、每次按完按鈕有沒有唸出東西。設計稿也要畫 :focus-visible 的樣子，包括程式聚焦的 h1。這類問題被客訴之後才修，往往是好幾頁一起改，前期由前端主動提出最省事。

換頁處理好了，但很多變化不換頁：按掉一杯拿鐵，只是清單少了一列。

畫面局部改變：狀態訊息、移除之後的焦點與 useId

上一節是整頁換掉，這一節是一小塊改變。購物車的每一列有一個「✕」移除按鈕，熟客遇到三個問題：讀螢幕軟體把按鈕唸成「乘號，按鈕」；按下去之後那一列消失，焦點跟著不見；移除了什麼也沒有任何提示。

只有圖示的按鈕：aria-label

按鈕的名稱（accessible name，讀螢幕軟體唸出來、Testing Library 的 getByRole('button', { name }) 比對的那個字）預設來自按鈕裡的文字，這裡只有「✕」。加上 aria-label={`移除${item.name}`}，畫面不變，名稱變成「移除拿鐵」。每一列都是「✕」，所以名稱要帶品名，不然清單裡十個按鈕都叫「移除」。

狀態訊息：區域要先存在

Web 課第 5 課講過，role="status" 這類 live region 要在內容改變之前就在 DOM 裡，讀螢幕軟體才會監聽它。在 React 裡這條規則有兩種常見的違反方式：

{message && <p role="status">{message}</p>}           // ✗ 有訊息時才出現：出現的那一刻沒人在聽
<p role="status" key={message}>{message}</p>             // ✗ key 換了就是新的元素（第 6 課），一樣沒人在聽
<p role="status">{message}</p>                           // ✓ 一直在，只換文字

這跟上一節的 role="alert" 不一樣：APG 說動態出現的 alert 大部分讀螢幕軟體會唸，status 沒有這個保證。所以錯誤用 {error && <p role="alert">}，成功、進度這類 status 讓區域一直在。

移除之後焦點去哪

按下「移除卡布奇諾」時焦點在那個按鈕上，React 把那一列從 DOM 拿掉，焦點就回到 body，鍵盤使用者要從頁首重新 Tab。被移除的元素消失前，要先決定焦點的下一站：下一列的移除按鈕；沒有下一列就上一列；購物車空了就移到標題。

const buttons = useRef(new Map<number, HTMLButtonElement>())
const headingRef = useRef<HTMLHeadingElement>(null)

function remove(item: CartItem) {
  const index = items.findIndex(i => i.id === item.id)
  const next = items[index + 1] ?? items[index - 1]
  setItems(items.filter(i => i.id !== item.id))
  setMessage(`已移除${item.name}`)
  if (next) buttons.current.get(next.id)?.focus()   // 下一站現在就在畫面上
  else headingRef.current?.focus()                  // <h2 ref={headingRef} tabIndex={-1}>購物車</h2>
}

<button type="button" aria-label={`移除${item.name}`}
  ref={el => { if (el) buttons.current.set(item.id, el); return () => { buttons.current.delete(item.id) } }}
  onClick={() => remove(item)}>✕</button>

先看 focus() 的時機。下一列的按鈕和標題在這次更新之前就在 DOM 裡，所以 setState 之後直接聚焦就好，不用等 render。如果下一站是這次更新才會出現的元素（例如移除後才顯示的「復原」按鈕），就要用第 7 課的 flushSync 先讓 DOM 更新，或在 effect 裡聚焦。按鈕的 ref callback 和清理函式也是第 7 課的寫法：一串節點收進 Map，列被移除時從 Map 刪掉。

useId：關聯說明文字

同一張購物車的數量欄位常有一行說明「每種最多 10 杯」，讀螢幕軟體要在聚焦欄位時一起唸出來，就用 aria-describedby 指到說明的 id。這跟第 17 課 aria-describedby 指向錯誤訊息是同一件事，id 用 第 4 課的 useId() 產生，同一個元件在一頁出現好幾次也不會重複：

const id = useId()
<label htmlFor={`${id}-qty`}>{item.name} 數量</label>
<input id={`${id}-qty`} type="number" aria-describedby={`${id}-hint`} />
<p id={`${id}-hint`}>每種最多 10 杯</p>

react.dev 的 useId 文件補充兩點：同一頁有好幾個 React root（例如舊頁面裡嵌了兩塊 React 畫面）時，用 createRoot 的 identifierPrefix 選項讓兩邊的 id 不會撞；useId 不能拿來當列表的 key，key 要從資料來。

這些行為都能在元件測試裡檢查：getByRole('button', { name: '移除拿鐵' }) 找得到，名稱就對了；jest-dom 的 toHaveAccessibleName、toHaveAccessibleDescription、toHaveFocus 檢查名稱、說明與焦點。第 23 課用角色查詢寫測試，也就同時在檢查無障礙：用角色和名稱找不到的元素，讀螢幕軟體多半也找不到。

💡 實務上：元件庫的無障礙要先驗，不要假設
對話框、下拉選單、分頁這種複雜元件，正式專案通常用元件庫，焦點陷阱、鍵盤操作由它處理，比自己寫可靠。導入前用鍵盤和讀螢幕軟體試一次它的範例；用了之後，你自己的部分（按鈕名稱、移除之後的焦點、狀態訊息）還是你的責任。code review 看到 <div onClick>、只有圖示的按鈕、條件 render 的 role="status"，可以直接留言。團隊想自動化，在 E2E 測試裡加 axe（Web 課第 27 課），抓得到缺名稱、對比不足這類靜態問題，焦點的流程仍然要人走。

到這裡，出錯時客人看得到，每個客人也都用得了。剩下開場的第三則回報：錯誤發生了，工程師要知道。

接上監控：createRoot 的錯誤選項與 window 事件

前兩節處理的是客人那一端；這一節處理工程師這一端。地圖上「怎麼回報」那一欄只有五個出口：createRoot 的三個選項，加上 window 的兩個事件。把它們都接到 reporter，開場「監控一筆都沒有」就不會再發生。

import type { RootOptions } from 'react-dom/client'

export function rootErrorOptions(reporter: Reporter): Pick<RootOptions, 'onCaughtError' | 'onUncaughtError' | 'onRecoverableError'> {
  return {
    onCaughtError: (error, info) => reporter.capture(error, { source: 'caught', componentStack: info.componentStack }),
    onUncaughtError: (error, info) => reporter.capture(error, { source: 'uncaught', componentStack: info.componentStack }),
    onRecoverableError: (error, info) => reporter.capture(error, { source: 'recoverable', componentStack: info.componentStack }),
  }
}

export function listenGlobalErrors(target: Window, reporter: Reporter) {
  const onError = (e: ErrorEvent) => reporter.capture(e.error ?? e.message, { source: 'window' })
  const onRejection = (e: PromiseRejectionEvent) => reporter.capture(e.reason, { source: 'promise' })
  target.addEventListener('error', onError)
  target.addEventListener('unhandledrejection', onRejection)
  return () => {
    target.removeEventListener('error', onError)             // 同一個函式才移除得掉
    target.removeEventListener('unhandledrejection', onRejection)
  }
}

// main.tsx
listenGlobalErrors(window, reporter)
createRoot(document.getElementById('root')!, rootErrorOptions(reporter)).render(<App />)

依 react.dev 的 createRoot 文件與 react-dom 19.3.1 的型別：

  • 三個選項都收到 (error, errorInfo)：error 是丟出來的值，throw '逾時' 就是字串，照原樣交給監控（第 13 課：型別是 unknown）；errorInfo.componentStack 是元件堆疊，看得出是哪個元件、在哪些元件裡面出錯。
  • onRecoverableError 的 error 可能帶著 error.cause：文件說有些可恢復的錯誤會把原本的錯誤放在 cause。監控服務多半會一起顯示 cause，自己寫的 reporter 要記得一起送。
  • hydrateRoot 收同一組選項：第 22 課 SSR 的 hydration 不一致，就是從 onRecoverableError 這裡送進監控。
  • 設了選項就取代預設行為：實測設了 onUncaughtError 之後，React 不再呼叫 reportError()，window 的 error 事件不會觸發，同一個錯誤不會從兩邊各送一次。反過來，沒設 onUncaughtError、只靠 window 監聽，收得到但沒有 componentStack，也分不出是 render 的錯誤還是事件處理函式的。
  • Error Boundary 的 componentDidCatch 照樣會被呼叫：第 13 課的 ErrorBoundary 用 onError prop 回報；改成在 root 統一回報之後，兩邊都送就是重複，選一邊。統一在 root 的好處是每個邊界不用各自記得傳 onError。

react.dev 的範例在註解裡提醒：開發時最好移除這些選項，保留 React 預設的處理（在 console 印出完整的錯誤與元件堆疊）。常見的寫法是只在正式環境傳入，例如 createRoot(el, import.meta.env.PROD ? rootErrorOptions(reporter) : {})。開發時查錯還有 captureOwnerStack()：依 react.dev，它回傳目前的 Owner Stack（哪些元件一路把這個元件 render 出來），只在開發版本有作用，正式環境永遠是 null，正式版本的套件甚至沒有匯出它。所以它是開發時的除錯工具，不要依賴它送正式環境的回報；同一份檔案兩種環境都會打包時，文件建議用 import * as React from 'react' 再判斷環境後呼叫。

window 的兩個事件和 Vue 課第 21 課一樣：error 的錯誤在 event.error，跨網域的 script 出錯時瀏覽器只給 "Script error."，event.error 是 null，所以退回 event.message；unhandledrejection 的錯誤在 event.reason。

💡 實務上：用監控服務的 SDK 時，確認它接了哪些出口
公司多半用 Sentry 這類服務，它的 React SDK 會幫你掛上 window 的事件，也提供給 createRoot 用的錯誤處理函式與 Error Boundary 元件。導入時對照這一節的五個出口逐一確認：被 Error Boundary 攔下的錯誤有沒有進來（最常漏的就是它）、SSR 的 hydrateRoot 有沒有傳同一組選項、自己 catch 的預期外錯誤有沒有呼叫 capture。驗收方法很直接：在測試環境故意讓一個元件 render 時丟錯、一個按鈕的 onClick 丟錯、一個 Promise 不接，三筆都要在監控裡看到，而且帶著 release 和元件堆疊。

正式環境：回報什麼，以及效能也要量

上一節讓錯誤送得出去；送出去的東西有沒有用，取決於帶了什麼。Vue 課第 21 課整理過一筆有用的回報要回答的問題，框架換成 React 都適用，這裡只列 React 多出來的部分：

收集為什麼
錯誤本身、stack、componentStack、source什麼錯、在哪個元件；source 分出是 Error Boundary 攔下的、沒人攔的，還是事件處理函式的
release（這次部署的版本）知道從哪一版開始出現；監控服務靠它找到同一版上傳的 source map
使用者操作的脈絡：最近幾次點擊、換頁、請求重現步驟。監控服務多半叫它 breadcrumbs（麵包屑），SDK 會自動記錄點擊和網址變化
路由、瀏覽器、匿名使用者 id影響範圍：多少人、哪幾頁、是不是只有某個瀏覽器
不收：手機、地址、token、表單內容、整份 store個資與憑證不能離開你的系統。用欄位名稱遮罩，只送需要的欄位

React 有兩件事要特別注意。第一，正式版本的訊息被壓縮：第 22 課看過 hydration 錯誤變成代碼 418，元件堆疊裡的元件名稱也會被壓縮成一兩個字母，要靠 source map 還原（Vue 課第 21 課：用 hidden 產生、上傳並標上同一個 release、從部署的檔案裡刪掉）。第二，render 的錯誤很容易大量重複：一個在 render 裡丟錯的元件，每次重新 render 都丟一次，要去重；量大時再抽樣（取樣，只送一定比例），兩者都在建立 reporter 時設定，呼叫 capture 的地方不用管。

效能也是監控的一部分：Web Vitals

錯誤之外，「很慢」也是客人遇到的問題，而且不會丟錯。Web 課第 20 課教過用 Google 的 web-vitals 函式庫收真實使用者的資料。依 web-vitals 6.2 的 README，三個 Core Web Vitals 的門檻（等於門檻算比較好的那一邊）：

指標量什麼好差
LCP主要內容多久出現≤ 2500 ms> 4000 ms
INP點擊、按鍵到畫面更新多久≤ 200 ms> 500 ms
CLS版面亂跳的程度≤ 0.1> 0.25

INP 在 2024 年取代了 FID，舊文章、舊的監控設定還在看 FID 的，要換掉。React 應用最常出問題的是 INP：點一下按鈕後的 render 太慢，就是第 19 課的量測、第 21 課的 Transition 要處理的事。web-vitals 的 attribution 版本（web-vitals/attribution）會在 INP 的資料裡附上互動的元素（attribution.interactionTarget），收集時一起送，才知道是哪個按鈕慢。送資料用 README 的寫法，navigator.sendBeacon() 在頁面關閉時也送得出去：

import { onCLS, onINP, onLCP } from 'web-vitals'

function send(metric: { name: string; value: number; id: string }) {
  navigator.sendBeacon('/analytics', JSON.stringify({ name: metric.name, value: metric.value, id: metric.id, release, route: location.pathname }))
}
onCLS(send); onINP(send); onLCP(send)

注意 route 是在送出當下讀的：單頁應用換頁不會重新載入，同一筆 INP 可能發生在客人換過幾頁之後，README 的範例也提醒要自己帶目前的網址。

💡 實務上：監控接好了，還要有人看、有人接
最常見的失敗不是沒接監控，而是沒人看：新錯誤沒有通知、通知到一個沒人看的頻道、也沒說誰負責。資深工程師會先跟團隊約好：哪種錯誤要即時通知（結帳、登入相關的、新版本第一次出現的），哪些每週看一次報表；每次部署後的頭一段時間打開監控，依 release 篩選，和上一版比錯誤數與 INP，有異常就決定修或回滾。對 PM 報告時用「影響多少客人、哪個流程」講，比「有 300 筆錯誤」有用。

這三個主題合起來，就是開場那條線的三段：出錯時客人看得到發生什麼事、每個客人都用得了、出事時工程師第一時間知道。

練習

在 learn/ 執行 node check.mjs react 24，檔案在 react/practice/work/24/。reporter.ts 定義監控的替身 Reporter，測試傳入一個把每次 capture 記下來的版本。練習 1 的假 API 由測試決定何時成功或失敗；練習 2 用 createMemoryRouter 在 StrictMode 下跑真的路由。四題互不相依，標了「不用改」的檔案不要改。

練習 1：完成 CheckoutButton 的錯誤處理。按下「結帳」呼叫 api.checkout() 一次，等待時按鈕 disabled、文字是「結帳中…」，成功或失敗後都恢復成「結帳」；成功顯示 <p role="status">訂單 #編號 已成立</p>。4xx 的 ApiError 是預期中的錯誤：顯示 <p role="alert"> 伺服器給的 message，不回報。其他錯誤（5xx 的 ApiError、TypeError）是預期外的：顯示 <p role="alert">結帳失敗，請稍後再試</p>，不能出現原始的錯誤訊息，並呼叫 reporter.capture(原本的錯誤, { source: 'handler' }) 剛好一次。錯誤不能再往外丟；再按一次時清掉上一次的訊息。

練習 2：換頁之後的分頁標題與焦點。Page 用 <title> 把分頁標題設成「{title}｜好咖啡」，<h1> 加 tabIndex={-1}。ShopLayout 在 pathname 改變之後，把焦點移到 <main> 裡的 h1；第一次載入不移動（StrictMode 下也一樣）；在菜單頁的搜尋框打字只改了 ?q=，焦點要留在搜尋框。不要改 pages.tsx、routes.tsx。

練習 3：購物車的移除按鈕。每個按鈕畫面上顯示 ✕，名稱是「移除{品名}」（例如「移除拿鐵」）。<p role="status"> 一開始就在畫面上、內容是空的，移除後同一個元素的內容變成「已移除{品名}」。移除之後焦點移到下一列的移除按鈕；移除的是最後一列，就移到上一列的；購物車空了，就移到 <h2>購物車</h2>（加 tabIndex={-1}），並顯示「購物車是空的」。

練習 4：把錯誤接到監控。rootErrorOptions(reporter) 回傳給 createRoot／hydrateRoot 的三個選項：被 Error Boundary 攔下的錯誤 source 是 'caught'、沒人攔的是 'uncaught'、React 自己恢復的是 'recoverable'，error 照原樣交出去（丟出字串就交字串），並帶上 errorInfo.componentStack。listenGlobalErrors(target, reporter) 監聽 error（source 'window'，交 event.error，它是 null 時交 event.message）與 unhandledrejection（source 'promise'，交 event.reason），回傳的函式移除兩個監聽。兩邊都裝好時，render 的錯誤只能回報一次。

練習 5：首頁的推薦區塊包了 Error Boundary，出錯時顯示「這個區塊暫時無法顯示」。團隊只在 window 上監聽 error 與 unhandledrejection，沒有設定 createRoot 的選項。推薦區塊出錯時，監控會收到嗎？

✓ React 19 的預設：沒人攔的錯誤交給 reportError()，所以會觸發 window 的 error；被攔下的只印在 console，不觸發任何事件。a 對沒人攔的、可恢復的、事件處理函式的錯誤成立，對被攔下的不成立；b 錯在 unhandledrejection 只跟沒人接的 Promise 有關；d 錯在 createRoot 的 onCaughtError 就是拿到它的地方（Error Boundary 的 componentDidCatch 也拿得到）。

練習 6：同事寫了換頁聚焦的 effect：useEffect(() => { if (first.current) { first.current = false; return } h1.focus() }, [pathname])。上線後正式環境正常，但開發時一打開網站焦點就在 h1 上。原因是？

✓ StrictMode 只在開發時多跑一次 effect，用來找出沒寫好清理的程式；「第一次」的旗標在第二次執行時已經被改掉。改成記住「上一次處理過的 pathname」，兩次看到的都是同一個值，就不會誤判。a 沒有這回事；c 反了，依賴 location 會讓只改搜尋參數時也搶焦點。

練習 7：加入購物車後要顯示「已加入拿鐵」給讀螢幕軟體聽。哪種寫法最可靠？

✓ live region 要在內容改變之前就存在，讀螢幕軟體才會監聽它。b 的區域跟訊息同時出現，出現的那一刻沒人在聽；c 換 key 等於每次都換一個新元素，問題一樣。動態出現的 role="alert" 例外：APG 說大部分讀螢幕軟體會唸，所以錯誤訊息常用條件 render。

常見錯誤

  • async 的事件處理函式沒有 catch：失敗變成沒人接的 Promise，客人看不到、Error Boundary 攔不到。try/catch 接住，分類後顯示與回報。
  • catch 之後再 throw，想交給 Error Boundary：事件處理函式的錯誤它攔不到，又變回沒人接的失敗。在 catch 裡處理完；真的要換掉整塊才用 useTransition 的 startTransition。
  • 把錯誤的原文顯示給客人（setError(e.message)）：程式錯誤看不懂，5xx 還可能洩漏內部資訊。只有預期中的 4xx 顯示伺服器的說明，其他顯示通用訊息。
  • 所有 ApiError 都當成預期中：5xx 是伺服器壞了，既不該給客人看原文，也要回報。用狀態碼分。
  • 預期中的錯誤也送到監控：庫存不足、404 很正常，全送上去會淹沒真正的問題。只回報預期外的。
  • 預期外的錯誤只顯示、不回報：客人看到「請稍後再試」，工程師什麼都不知道。顯示和 capture 要一起做。
  • 失敗時沒有恢復 pending、再按一次沒清掉舊訊息：按鈕一直 disabled，或成功之後還掛著上一次的錯誤。pending 在 finally 裡恢復，送出前清掉訊息。
  • 單頁應用換頁後不處理焦點與標題：讀螢幕軟體什麼都不唸。每頁 render <title>，pathname 換了把焦點移到 h1。
  • <title>{title}｜好咖啡</title>：兩個 children，19.3.1 實測分頁標題變成空的。用樣板字串組成一個字串。
  • h1 沒有 tabIndex，或寫成 tabIndex={0}：前者在真的瀏覽器裡聚焦不了，後者讓每一頁的 Tab 多停一站。用 tabIndex={-1}。
  • 第一次載入也移動焦點，或用「第一次」的旗標擋：前者跳過頁首；後者在 StrictMode 第二次執行 effect 時失效。記住上一次處理過的 pathname 來比較。
  • 換頁聚焦的 effect 依賴 location 或 location.key：只改 ?q= 也會觸發，打一個字焦點就被搶走。只看 pathname。
  • 只有圖示的按鈕沒有名稱：讀螢幕軟體唸「乘號，按鈕」。加 aria-label，而且帶上是哪一個（「移除拿鐵」）。
  • role="status" 有訊息才 render，或給它會變的 key：區域出現的那一刻沒人在聽。讓它一直在，只換文字。
  • 移除之後不管焦點、或一律移到標題：前者焦點掉回 body；後者每移除一杯都要從標題重新 Tab 回清單。依序找下一列、上一列，最後才是標題（標題要 tabIndex={-1}）。
  • 移除最後一列時只找下一列：沒有下一列，焦點又掉回 body。items[index + 1] ?? items[index - 1]。
  • 只監聽 window 的事件：被 Error Boundary 攔下的錯誤收不到，沒人攔的收到了也沒有 componentStack。createRoot 的三個選項都要接。
  • 漏了 onCaughtError 或 onRecoverableError：有 fallback 的錯誤、hydration 不一致都不會進監控。三個都接，hydrateRoot 傳同一組。
  • 回報時沒帶 componentStack，或把丟出的值包成新的 Error：前者不知道是哪個元件；後者丟出字串時原本的值不見了、stack 指到你的回報程式。照原樣交出 error，帶上 errorInfo.componentStack。
  • error 事件只交 event.error：跨網域 script 的錯誤 event.error 是 null，回報變成空的。退回 event.message。
  • unhandledrejection 讀 event.error：它沒有這個屬性，錯誤在 event.reason。
  • removeEventListener 傳了新的箭頭函式：移除不掉，監聽一直在，測試之間或熱更新後重複回報。保留 addEventListener 時的同一個函式。
  • ErrorBoundary 的 componentDidCatch 和 onCaughtError 都回報：同一個錯誤送兩次。選一邊，通常統一在 root。
  • 正式環境的回報依賴 captureOwnerStack()：它只在開發版本有作用，正式環境是 null。它是開發時的除錯工具。

小結

  • 每一種錯誤都要回答兩件事：客人看到什麼、工程師怎麼知道。render 的錯誤交給 Error Boundary 換畫面，回報交給 createRoot 的 onCaughtError（攔下的）、onUncaughtError（沒人攔的）、onRecoverableError（React 自己恢復的）；事件處理函式、計時器、沒人接的 Promise 要靠 window 的 error 與 unhandledrejection。
  • React 19 預設：沒人攔的錯誤交給 reportError()（會觸發 window 的 error），攔下的只印在 console；設了選項就取代預設，不會重複。開發時保留預設，正式環境再接監控；captureOwnerStack() 只在開發時有用。
  • 事件處理函式自己 catch：4xx 這類預期中的錯誤顯示伺服器的說明、不回報；5xx、網路、程式錯誤顯示通用訊息、回報原本的錯誤；不要再 throw。
  • 單頁應用換頁：每頁 render <title>（children 是一個字串），pathname 換了把焦點移到 tabIndex={-1} 的 h1；第一次載入不動，用「上一次的 pathname」判斷才不怕 StrictMode。
  • 局部改變：只有圖示的按鈕用 aria-label；role="status" 一直存在、只換文字（動態出現的 role="alert" 例外）；元素被移除前決定焦點的下一站；說明文字用 useId 加 aria-describedby 關聯。
  • 正式環境的回報帶 componentStack、release、操作脈絡，不帶個資；用 source map 還原壓縮過的名稱，去重與抽樣在 reporter 設定。效能用 web-vitals 收 LCP、INP、CLS，INP 已取代 FID。
