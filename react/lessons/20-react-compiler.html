階段 5：效能與渲染 · 第 20 課

React 的規則與 React Compiler

上一課手動加了 memo、useMemo、useCallback，團隊覺得每個元件都要判斷一次太累，決定在 staging 打開 React Compiler，讓它自動做。打開後前台購物車壞了：第二次加拿鐵，畫面還是「拿鐵 × 1」。把 Compiler 關掉，購物車又「好了」。查的過程中還翻出兩個老問題：購物車元件把菜單排序後，同一份菜單在別的區塊順序也跟著變了；吧台等候螢幕的「已等 N 分鐘」常常停住不動，有人點了別的按鈕才突然跳一大段。

這不是 Compiler 的 bug。這些元件本來就違反了 React 的規則（Rules of React）：直接改 props 和 state、在 render 裡讀時鐘。沒有記憶化的時候，每次都整個重算，問題被蓋住；記憶化一開，問題就浮出來。

這課的路線：
  1. Compiler 做什麼、它假設什麼：為什麼關掉就「好了」。
  2. 規則一：props 和 state 不可變。購物車與菜單的修法，以及「只換變了的那一列」。
  3. 規則二：render 是純的。時間、亂數放進 state，等候清單的修法。
  4. ESLint：Compiler 的診斷怎麼回報，實測抓得到與抓不到的寫法。
  5. 導入 Compiler：安裝、確認有沒有生效、"use no memo" 與手寫的 memo 怎麼辦。
這課會用到：
  • 第 19 課的 memo、useMemo、useCallback：用 Object.is 比較 props 或依賴，沒變就沿用上一次的結果（畫面、計算值、函式）。
  • 第 3 課的不可變更新：不改原本的物件，做出新的；只複製改到的那條路徑，沒改到的沿用原本的參考。
  • 第 1 課的「render 必須是純函式」：同樣的 props、state，回傳同樣的畫面；不改 render 之前就存在的東西。
  • 第 5 課的 effect 與清理：跟外部系統（例如計時器）同步，回傳清理函式在卸載時復原。
練習的 package.json 沒有安裝 Compiler。練習 1 用 memo 包住子元件，模擬開了 Compiler 之後「參考沒變就沿用」的行為；兩題都用 eslint-plugin-react-hooks 7.1.1 的規則檢查。

React Compiler：自動記憶化，前提是程式遵守規則

React Compiler 是一個 build 時執行的工具（Babel 外掛），讀你的元件和 hook，自動加上記憶化（memoization）：輸入沒變，就沿用上一次算好的結果。依 react.dev 的 Introduction，它主要做兩件事：

  • 跳過連帶的重新 render：父元件 render 時，props 沒變的子元件不用跟著 render，等於自動幫每個元件包了 memo。
  • 跳過昂貴的計算：元件裡呼叫的計算，輸入沒變就不再算，等於自動加了 useMemo。

Compiler 在 2025 年 10 月 7 日發布第一個穩定版 v1.0（React 官方部落格）。它沒有魔法，判斷「沒變」用的就是第 19 課的參考比較。概念上，CartLine 被編譯後像這樣：

// 示意，不是 Compiler 真正的輸出
function CartLine({ line }) {
  if (line !== 上次的line) {                        // 參考比較
    上次的畫面 = <li>{line.name} × {line.qty}</li>
    上次的line = line
  }
  return 上次的畫面
}

開場的購物車就卡在這裡。原本的程式第二次加拿鐵時寫 hit.qty += 1：改的是同一個 line 物件，參考沒變，CartLine 拿出「拿鐵 × 1」的舊畫面。沒有 Compiler 時，CartLine 每次都重新執行，讀到被改過的 qty，畫面碰巧是對的。

直接改之後還是「× 1」，換成內容一樣的新物件才顯示「× 2」。所以開場問題的最小答案是：Compiler 假設 props、state 不會被改、render 是純的；違反的程式在沒有記憶化時看起來正常，開了才壞。修法不是關掉 Compiler，是讓程式遵守規則。

react.dev 的 Rules of React 把規則分成三組，這課處理第一組，第二、三組在前面的課教過：

規則內容在哪裡教
元件與 hook 必須是純的同樣的輸入同樣的輸出；副作用不在 render 裡做；props、state、傳給 hook 和 JSX 的值不可變本課；第 1 課
由 React 呼叫元件與 hook元件只在 JSX 裡用（<Article />），不要當一般函式呼叫（Article()），那樣會繞過 React，裡面的 hook 也容易違反 Hook 的規則；不要把 hook 當值傳來傳去這裡帶過；寫法照第 2 課
Hook 的規則只在元件或 hook 的最上層呼叫第 9 課

對照 Vue：Vue 的 computed 用 Proxy 追蹤你讀了哪些屬性，直接改 line.qty 正是它期待的寫法，改了就重算。React 的記憶化（不管手寫還是 Compiler）不追蹤屬性，只比較參考；React 知道「變了」的唯一方式，是你給它一個新的物件。

💡 實務上：先讓程式遵守規則，再打開 Compiler
Compiler 的效果是「本來要手寫的 memo 不用寫了」，它不會修好違反規則的程式，反而會讓藏著的 bug 現形。導入前先開 ESLint 規則（下面會講）把回報的地方修掉，確認主要流程有測試；打開後在 staging 跑一輪，重點看購物車、表單這種「點了要更新」的畫面。跟 PM 溝通時說清楚：這是效能優化，使用者不會看到新功能，但可能踩到舊 bug，所以要排測試時間。

規則一：props 與 state 不可變

知道 Compiler 靠參考判斷之後，回頭看開場購物車的原始程式。它違反了兩次「不可變」：

export function CartPanel({ menu, onCartChange }: Props) {
  const [lines, setLines] = useState<Line[]>([])
  const sorted = menu.sort((a, b) => a.price - b.price)   // ✗ 改到 props：父元件的陣列被排好了

  function add(p: Product) {
    const hit = lines.find(l => l.id === p.id)
    if (hit) hit.qty += 1                                  // ✗ 改到 state 裡的物件
    else lines.push({ id: p.id, name: p.name, qty: 1 })    // ✗ 改到 state 的陣列
    const next = [...lines]                                // 外層是新的，畫面會 render
    setLines(next)
    onCartChange?.(next)
  }
  …
}

先看 menu.sort()。sort 會改原本的陣列再回傳它，而 menu 是父元件的資料：父元件、其他也拿到這份 menu 的元件，順序全被改了，這就是開場「別的區塊順序也變了」。父元件如果把 menu 凍結過（Object.freeze），sort 會直接丟 TypeError。改用回傳新陣列的 toSorted（ES2023），或先 [...menu] 再排：

const sorted = menu.toSorted((a, b) => a.price - b.price)   // menu 不變
// 價格相同的維持原本順序：sort、toSorted 都是穩定排序（ES2019 起規定）

再看 add。外層有 [...lines]，畫面也會 render，看起來像是做了不可變更新，但裡面的物件還是舊的：

  • hit.qty += 1：拿鐵那一列是同一個物件，CartLine 被記憶化時跳過它，畫面停在「× 1」。
  • lines.push(…)：改的是目前 state 那個陣列，也就是上一次交給 onCartChange 的那一份。父元件存起來的「上一次的購物車」，被你事後偷偷多加一列。

正確的寫法是第 3 課的 map：變了的那一列換成新物件，其他列原樣回傳。

function add(p: Product) {
  const next = lines.some(l => l.id === p.id)
    ? lines.map(l => (l.id === p.id ? { ...l, qty: l.qty + 1 } : l))   // 沒變的列沿用原本的物件
    : [...lines, { id: p.id, name: p.name, qty: 1 }]
  setLines(next)
  onCartChange?.(next)
}

「沿用原本的物件」跟「換成新物件」一樣重要。每一列都複製一份（lines.map(l => ({ ...l }))、structuredClone(lines)），內容是對的，但每一列的參考都換了，記憶化全部失效，加一杯拿鐵讓整台購物車重新 render。目標是：變了的換新，沒變的沿用，參考是否相同剛好等於內容有沒有變。

幾個看起來像修好、其實沒有的寫法：

寫法問題
lines.map(l => { if (l.id === p.id) l.qty += 1; return l })外層陣列是新的，但拿鐵那一列被直接改，參考沒變
lines[i] = { ...lines[i], qty: … } 再 [...lines]那一列是新物件，但塞回了舊的 state 陣列，上一次交出去的購物車被改了
lines.push(新的列) 再 [...lines]同上：舊的 state 陣列多了一列
每一列都 { ...l }內容對，但沒變的列也換了參考，記憶化全部失效
拿掉 CartLine 的 memo畫面看起來對了，但 state 還是被改；開了 Compiler 一樣會壞

最後一列值得多說一句：拿掉 memo 讓畫面「好了」，跟開場「關掉 Compiler 就好了」是同一件事，都只是把重算的次數加回去，蓋住問題。react.dev 的 Debugging 頁也建議用這個方式判斷：拿掉所有記憶化後 bug 還在，就是違反了規則。

「不可變」的範圍比 props 和 state 大。依 Rules of React，傳給 hook 的參數、hook 回傳的值、已經放進 JSX 的值，之後都不能再改。反過來，在這次 render 裡自己建立的值可以隨便改（文件叫 local mutation）：先 const rows = [] 再 push、toSorted 之後再 push，都沒問題，因為下次 render 會重新建立一份。

💡 實務上：code review 時找「改原本東西」的方法
從 Vue 轉過來的團隊，最常見的是在 props 上 sort、reverse、splice，或是共用的工具函式（例如 sortByPrice(list)）偷偷就地排序，呼叫端完全看不出來。review 時看到這幾個方法，先問「這個陣列是誰的」。型別上可以把 props 和 state 寫成 readonly Line[]、Readonly<Line>，push、sort、賦值在 TypeScript 就會報錯（第 3 課提過）。巢狀很深的更新（例如分類裡的商品裡的選項）手寫容易漏，Immer 這類函式庫可以代勞，它產生的也是「只換變了的路徑」的新物件。

規則二：render 是純的，時間不在 render 裡讀

不可變管的是「不要改別人的東西」，純函式還有另一半：同樣的輸入，同樣的輸出。依 react.dev，元件的輸入是 props、state 和 context；在 render 裡呼叫 Date.now()、Math.random()，等於多了一個 React 不知道的輸入。吧台的等候清單就是這樣寫的：

export function WaitingList({ orders }: { orders: WaitingOrder[] }) {
  const now = Date.now()   // ✗ render 裡讀時鐘
  return (
    <ul aria-label="等候中">
      {orders.map(o => (
        <li key={o.id}>{o.customer}：已等 {Math.floor((now - o.placedAt) / 60000)} 分鐘</li>
      ))}
    </ul>
  )
}

它有兩個症狀，都是因為「現在時間」不是 state：

  • 不會自己更新：時間流逝不會觸發 render。沒有人讓它重新 render，分鐘數就停住；有人點了別的東西，才突然跳一大段。
  • 同樣的 props 結果不一樣：父元件重新 render、傳入同樣的 orders，畫面卻變了。用 Compiler 或 memo 時，「什麼時候重算」由記憶化決定，畫面上的時間就變成看運氣。

修法是把時間變成 state：掛上時讀一次，之後由計時器更新。計時器是外部系統，放在 effect，卸載時清掉（第 5 課）：

export function WaitingList({ orders }: { orders: WaitingOrder[] }) {
  const [now, setNow] = useState(() => Date.now())   // 初始值函式：只在掛上時執行

  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 60_000)   // callback 不在 render 裡
    return () => clearInterval(id)
  }, [])

  return …   // 畫面只用 state 裡的 now 算
}

從上到下看三個決定：

  1. useState(() => Date.now())，不是 useState(Date.now())：後者每次 render 都會呼叫 Date.now()，只是結果被丟掉，它仍然是 render 裡的呼叫。初始值函式只在掛上時執行（第 3 課），讀時鐘放在這裡、計時器的 callback、事件處理函式裡都可以。
  2. 整張清單一個計時器：如果讓每一列各自管時間，10 位客人就是 10 個計時器，而且各列更新的時間點不一樣，同一個畫面上的分鐘數會不同步。時間放在清單這一層，算出來的分鐘數一定一致。
  3. 每 60 秒，不是每秒：畫面只顯示分鐘，每秒 setNow 會讓清單一分鐘 render 60 次，其中 59 次畫面完全沒變。代價是分鐘數最多晚 59 秒才跳，等候螢幕可以接受。

還有一種「只修一半」的寫法：計時器每分鐘 setTick(t => t + 1) 觸發 render，時間還是在 render 裡 Date.now()。分鐘數會動了，但 render 依然不純：父元件在兩次計時之間重新 render，分鐘數就提早跳。同理，state 裡放了時間，算的時候又寫 Math.max(now, new Date().getTime())，也是 render 裡讀時鐘。

Vue 的 computed 也有同樣的限制：Date.now() 不是響應式的，computed 不會因為時間過去而重算，Vue 的做法一樣是用 ref 存現在時間、setInterval 更新它。

💡 實務上：「現在時間」是一種要管理的狀態
咖啡店的等候螢幕、訂單的「3 分鐘前」、優惠倒數，都會遇到這件事。常見做法是寫一個自訂 hook useNow(intervalMs)（第 9 課），放在要顯示的那一層，間隔依畫面精度決定（顯示分鐘就不要每秒更新）。伺服器端 render 時，render 裡讀時鐘會讓伺服器和瀏覽器算出不同的文字，react.dev 的 purity 規則把 hydration 不一致列為後果之一（第 22 課）。測試時用假計時器（Vitest 的 vi.useFakeTimers 加 setSystemTime）把時間固定住，練習 2 就是這樣測的。

ESLint：Compiler 的診斷，在寫程式時就看到

前兩節的規則靠人記容易漏，所以 React 把 Compiler 的檢查做進了 eslint-plugin-react-hooks。react.dev 的說明：Compiler 的診斷會自動透過這個外掛回報，專案還沒導入 Compiler 也能用。7.x 的 recommended 設定已經包含這些規則（7.1.1 的 README）：

// eslint.config.js
import reactHooks from 'eslint-plugin-react-hooks'
import { defineConfig } from 'eslint/config'

export default defineConfig([
  reactHooks.configs.flat.recommended,
])

第 9 課的 rules-of-hooks、exhaustive-deps 之外，7.1.1 的 recommended 還有十幾條 Compiler 規則，跟這門課最相關的幾條（查表用，不用背）：

規則擋什麼
immutability改 props、state、hook 的參數與回傳值
purityrender 裡呼叫已知不純的函式（Date.now、Math.random 等）
refsrender 裡讀寫 ref.current（第 7 課）
set-state-in-effecteffect 裡同步呼叫 setState（第 6 課的衍生值）
set-state-in-renderrender 裡呼叫 setState
globalsrender 裡改全域變數
preserve-manual-memoization手寫的 useMemo、useCallback 沒辦法被 Compiler 保留

等候清單的原始程式，lint 的回報長這樣（7.1.1 實測，節錄）：

14:15  error  Error: Cannot call impure function during render

`Date.now` is an impure function. Calling an impure function can produce unstable
results that update unpredictably when the component happens to re-render.
  react-hooks/purity

這種回報除了「寫錯了」，還有一層意思。react.dev 的說明：Compiler 回報診斷，代表它靜態看出了違反規則或不支援的寫法，這時它會自動跳過那個元件或 hook，其他元件照樣編譯。所以 lint 的錯不用一次全修完，修一個，被優化的元件就多一個。

反過來，沒有回報不代表沒問題。在練習環境用 7.1.1 的 recommended 實測：

寫法回報
item.url = 'x'（改 props 的屬性）✓ immutability
事件裡 user.name = 'b'（改 state 的物件）✓ immutability
事件裡 lines[i] = …（用索引改 state 陣列）✓ immutability
render 裡 Date.now()、Math.random()、useState(Date.now())✓ purity
menu.sort(…)（props 的陣列就地排序）✗ 沒有回報
事件裡 lines.push(…)✗ 沒有回報
lines.find(…) 拿到的物件再 .qty += 1✗ 沒有回報
render 裡 new Date()✗ 沒有回報

開場購物車的三個錯，lint 一個都沒抓到。這正是 react.dev Debugging 頁說的情況：大部分 Compiler 的問題是執行時的問題，原因是程式以 Compiler 偵測不到的方式違反了規則，它就照樣編譯了。lint 回報的就是 Compiler 的診斷，lint 看不出來的，Compiler 也看不出來。所以練習的測試除了跑 lint，還會把 props 凍結、檢查交出去的購物車有沒有被改。

用註解關掉規則（// eslint-disable-next-line react-hooks/purity）只是讓 lint 不說話，程式還是不純。另外，7.1.1 實測在元件開頭加了 "use no memo"（下一節），lint 照樣回報 purity，這個指令只影響編譯，不影響檢查。

導入 Compiler：安裝、確認、"use no memo"

規則和 lint 都準備好之後，才輪到 Compiler 本身。依 react.dev 的 Installation：

npm install -D babel-plugin-react-compiler@latest

這門課的 Vite 專案用 @vitejs/plugin-react 6，它的 6.2.1 README 說明 Babel 版的 Compiler 要另外裝 @rolldown/plugin-babel 和 @babel/core，再用套件附的 reactCompilerPreset：

npm install -D @rolldown/plugin-babel @babel/core babel-plugin-react-compiler

// vite.config.ts
import { defineConfig } from 'vite'
import react, { reactCompilerPreset } from '@vitejs/plugin-react'
import babel from '@rolldown/plugin-babel'

export default defineConfig({
  plugins: [react(), babel({ presets: [reactCompilerPreset()] })],
})

幾個設定與行為（react.dev 的 Compiler Reference）：

  • target：預設 '19'，React 19 不用另外裝執行時套件（編譯後的程式用 React 內建的 react/compiler-runtime）；React 17、18 要裝 react-compiler-runtime 並設定 target。
  • compilationMode：預設 'infer'，編譯「名字像元件（大寫開頭）或 hook（use 開頭），而且有 JSX 或呼叫 hook」的函式，一般的工具函式不碰。設成 'annotation' 時只編譯開頭寫了 "use memo" 的函式，適合大專案一個一個開。
  • 確認有沒有生效：開發模式下，React DevTools 的元件樹裡，被編譯的元件旁邊會出現「Memo ✨」標記。

plugin-react 6.2.1 的 README 另外有用 Rust 實作的 react({ compiler: true })，README 標示為實驗性，正式專案先用 Babel 版。

打開之後某個畫面壞了，用 "use no memo" 讓這個元件不被編譯：

function CartPanel(props: Props) {
  "use no memo"   // TODO: 修好直接改 state 的地方後移除（issue #123）
  …
}

react.dev 的 Debugging 流程：加上它之後問題消失，幾乎可以確定這個元件違反了規則；接著去找違反的地方（多半是上面那張「沒有回報」表裡的寫法），修好，再把指令拿掉。文件把它定位為除錯時暫時用的逃生口，不是長期的設定。

手寫的 memo、useMemo、useCallback 怎麼辦？react.dev 的建議：

  • 新的程式：交給 Compiler，需要精準控制時才手寫。典型例子是當成 effect 依賴的值：要確保「內容沒實質改變時 effect 不重跑」，就自己用 useMemo 固定它。
  • 既有的程式：先留著。拿掉可能改變編譯結果，要拿掉就先測過。preserve-manual-memoization 會在 Compiler 沒辦法保留你手寫的記憶化時回報。

第 19 課「先量測再優化」仍然成立：Compiler 讓記憶化不用手寫，但它解決不了演算法本身太慢、一次 render 幾千列這種問題。

💡 實務上：分批打開，每一批都能回頭
大型專案常見的導入順序：先在 CI 加上 recommended 的 lint 規則，把 error 修完；用 compilationMode: 'annotation' 從測試完整的頁面開始加 "use memo"；穩定後換成 'infer'，對還沒修好的元件加 "use no memo"，每一個都附 TODO 和 issue 編號，定期清。上線後的 bug 回報如果是「某個畫面不更新」，第一步是在那個元件加 "use no memo" 驗證是不是記憶化造成的，不是把整個 Compiler 關掉。

練習

在 learn/ 執行 node check.mjs react 20，檔案在 react/practice/work/20/。測試會把傳進去的 props 凍結（Object.freeze 每一層），元件改到就丟 TypeError；最後一項用 eslint-plugin-react-hooks 7.1.1 檢查，檔案裡不能出現 eslint-disable。練習 2 用假計時器固定時間，用 Profiler 數重新 render 的次數。練習 3 在瀏覽器裡做。

練習 1：CartPanel 用 menu.sort() 排菜單，加入時 hit.qty += 1、lines.push()，第二次加拿鐵畫面還是「拿鐵 × 1」（CartLine 用 memo 模擬 Compiler 的記憶化）。改成：菜單依價格由低到高顯示，價格相同的維持原本順序，傳進來的 menu（陣列和裡面的物件）不能被改；按「加入X」時沒有這個品項就新增「X × 1」，有就把數量加 1；每次加入後用新的購物車陣列呼叫 onCartChange，之前交出去的購物車之後不能再被改；沒變的那幾列沿用原本的物件，只有數量變了的那一列換成新物件。不能拿掉 CartLine 的 memo，要通過 react-hooks/immutability。

練習 2：WaitingList 在 render 裡呼叫 Date.now()，沒有人重新 render 時分鐘數停住，父元件重新 render 時又提早跳。改成：每位客人顯示「名字：已等 N 分鐘」（現在時間減 placedAt，以分鐘為單位無條件捨去）；現在時間放進 state，掛上時讀一次，之後整張清單共用一個計時器每 60 秒更新，一分鐘只造成一次重新 render；同樣的 props 和 state，重新 render 的結果一樣；卸載時清掉計時器。render 過程中不能呼叫 Date.now()、new Date()（初始值函式和計時器的 callback 可以），要通過 react-hooks/purity。

練習 3：後台的「標成售完」按鈕呼叫 markSoldOut(menu, id)，現在的寫法直接改商品的 soldOut，再回傳 { ...menu }。開了 Compiler 之後，菜單畫面的分類區塊（被記憶化，參考沒變就沿用）不會更新。改成不可變的寫法：

  • 回傳新的 menu，那個商品的 soldOut 是 true；傳進來的 menu 一點都不能改（測試會傳入凍結的物件）。
  • 從 menu 到那個商品的路徑上，每一層都是新的物件或陣列：menu、categories 陣列、那個分類、它的 items 陣列、那個商品。
  • 其他分類、同一個分類裡的其他商品，沿用原本的物件。
  • 找不到這個 id 時什麼都沒變，回傳原本的 menu（同一個參考）。

練習 4：打開 Compiler 後，購物車第二次加拿鐵畫面不更新；在 CartPanel 開頭加上 "use no memo" 就正常了。接下來該怎麼做？

✓ 加了 "use no memo" 就好，代表問題跟記憶化有關，react.dev 的 Debugging 頁說這幾乎都是程式以 Compiler 偵測不到的方式違反了規則。a 只是把 bug 藏起來，這個元件也失去優化，文件把這個指令定位為暫時的逃生口；b 搞錯了方向；d 讓所有元件都失去優化，違反規則的程式還在。

練習 5：下面哪一段寫在元件的 render 過程（元件函式本體）裡，沒有違反 React 的規則？

✓ rows 是這次 render 自己建立的陣列，改它是 local mutation，下次 render 會重新建立，文件明講沒問題。b 就地排序父元件的陣列；c 每次 render 都呼叫 Date.now()，只是結果被丟掉，要寫成 useState(() => Date.now())；d 讓同樣的輸入產生不同的輸出。

練習 6：開場的 CartPanel（menu.sort()、hit.qty += 1、lines.push()）用 eslint-plugin-react-hooks 7.1.1 的 recommended 檢查，一個錯誤都沒有。這代表什麼？

✓ lint 回報的就是 Compiler 的診斷，有回報的元件 Compiler 才會跳過。這三個寫法實測都沒有回報，所以 Compiler 會編譯它，記憶化之後畫面就不更新。c 把順序弄反了：是「有回報」才跳過。所以練習的測試會凍結 props、檢查交出去的購物車有沒有被改。

練習 7：專案打開了 Compiler，既有程式裡的 useMemo、useCallback 該怎麼處理？

✓ 這是 react.dev 的建議：拿掉既有的記憶化可能改變編譯結果，所以先留著或測過再拿；手寫的 useMemo、useCallback 仍然是控制記憶化的逃生口，例如讓 effect 不要因為依賴換了參考就重跑。c 錯在 Compiler 會自己分析，不需要提示。

常見錯誤

  • 把 Compiler 打開後才出現的 bug 當成 Compiler 的 bug：多半是本來就違反規則，記憶化讓它現形。先加 "use no memo" 確認，再找違反的地方。
  • 在 props 上 sort：改到父元件的陣列，凍結過的會直接丟 TypeError。用 toSorted 或 [...menu].sort。
  • 外層 [...lines] 是新的，裡面 qty += 1：那一列參考沒變，被記憶化的子元件不會更新。變了的那一列 { ...l, qty: l.qty + 1 }。
  • push 或用索引賦值改 state 陣列，再複製一份：上一次交出去的資料被事後改掉。用 [...lines, 新的列]、map 產生新陣列。
  • 每一列、每個分類都複製一份（{ ...l }、structuredClone）：內容對，但記憶化全部失效。只換變了的路徑。
  • 拿掉 memo 讓畫面「好了」：只是多重算幾次蓋住問題，開了 Compiler 一樣壞。修好不可變更新。
  • render 裡呼叫 Date.now()、new Date()、Math.random()：同樣的 props 結果不同，時間也不會自己更新。現在時間放進 state。
  • useState(Date.now())：每次 render 都呼叫一次。寫成初始值函式 useState(() => Date.now())。
  • 計時器只負責觸發 render，時間還在 render 裡讀：分鐘數會動，但 render 依然不純。計時器的 callback 裡 setNow(Date.now())，畫面只用 state 的 now。
  • 只在掛上時讀一次時間，沒有計時器：分鐘數永遠不變。用 setInterval 更新。
  • 畫面只顯示分鐘，卻每秒更新時間：一分鐘 render 60 次。間隔跟著顯示的精度走。
  • 每一列各開一個計時器：計時器數量跟著列數長，各列跳動的時間點也不同步。時間放在清單這一層。
  • effect 沒有回傳 clearInterval：卸載後計時器還在跑。
  • 用 eslint-disable 關掉 purity、immutability：程式還是違反規則，只是 lint 不說了。
  • lint 沒錯就當成遵守規則：sort、push、透過 find 改物件、new Date() 在 7.1.1 實測都不會回報。靠測試（凍結輸入、檢查參考）補上。

小結

  • React Compiler（v1.0 起穩定）在 build 時自動記憶化元件與計算，判斷「沒變」用參考比較；它假設程式遵守 React 的規則。
  • 規則一：props、state、傳給 hook 和 JSX 的值不可變。排序用 toSorted；更新時變了的換新、沒變的沿用原本的參考。render 裡自己建立的值可以改。
  • 規則二：render 是純的。Date.now()、Math.random() 不在 render 裡呼叫；現在時間放進 state，用初始值函式讀一次、計時器更新，間隔跟著顯示精度走。
  • eslint-plugin-react-hooks 7.x 的 recommended 包含 Compiler 的診斷，沒導入 Compiler 也能用；有回報的元件 Compiler 會跳過，沒回報不代表遵守規則，要靠測試補。
  • 導入：裝 babel-plugin-react-compiler（Vite 用 reactCompilerPreset），React 19 不用另外設定 target；用 DevTools 的 Memo ✨ 確認；出問題用 "use no memo" 暫時隔離再修；既有的 useMemo、useCallback 先留著。
