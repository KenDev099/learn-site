階段 4：狀態與資料 · 第 17 課

表單進階：Actions、useActionState 與驗證

咖啡店的外帶訂單表單是照第 4 課寫的：四個欄位各一個 useState，onSubmit 裡 preventDefault、手動切換 'submitting'、try/catch、成功後一格一格清空。能用，但每張表單都要重寫一遍這些流程。改版後又出了新問題：「訂閱優惠通知」按鈕送出的 topic 是 null；後端回「這個時段已額滿」，畫面只寫「送出失敗」；有人把送出按鈕抽成共用元件，結果按鈕不知道表單正在送出，客人連按兩次。

React 19 把「送出表單」做成內建的流程：把函式交給 <form action>，React 會收集 FormData、追蹤送出中、成功後重設欄位。範例以 React 19.3.1、zod 4.6.7 為準。

這課的路線：
  1. <form action>：把送出函式交給表單，React 收集 FormData、追蹤送出中、成功後清空欄位；「訂閱優惠通知」的 topic 為什麼不再是 null（開場問題的最小答案）。
  2. useFormStatus：抽成共用的送出按鈕，它自己知道表單在送出，送出中停用，客人連按也只送一次。
  3. useActionState 與 zod：送出的結果變成 state，「這個時段已額滿」顯示在對的欄位旁邊；驗證的寫法跟寫後端 API 一樣。
  4. 保留輸入：回傳驗證錯誤時，客人打的字為什麼會被清空、怎麼留住。
  5. 選哪一種：受控表單、Action、useMutation 各適合什麼表單。
這課會用到：
  • 第 4 課的受控、非受控與 FormData：受控欄位的值放在 state，非受控欄位的值留在 DOM、用 defaultValue 給初始值；FormData 讀出來的值都是字串，沒勾的 checkbox 不存在。
  • 第 16 課的 Action：傳給 startTransition 的函式，可以是 async，Promise 結束之前都算進行中；await 之後的 setState 要再包一層 startTransition。
  • 第 13 課的 Error Boundary：攔下底下元件丟出的錯誤，改畫備用畫面，只換掉它包住的那一塊。

<form action>：把函式交給表單

第 4 課的送出寫法，和 React 19 的寫法並排：

// 第 4 課：onSubmit
async function handleSubmit(e: SubmitEvent<HTMLFormElement>) {
  e.preventDefault()
  const data = new FormData(e.currentTarget)
  await subscribe(String(data.get('email')), data.get('topic') as Topic)
}
<form onSubmit={handleSubmit}>…</form>

// React 19：action 收到的就是 FormData
async function subscribeAction(formData: FormData) {
  await subscribe(String(formData.get('email')), formData.get('topic') as Topic)
}
<form action={subscribeAction}>
  <label>Email <input type="email" name="email" /></label>
  <button type="submit" name="topic" value="new">訂閱新品通知</button>
  <button type="submit" name="topic" value="sale">訂閱優惠通知</button>
</form>

HTML 的 action 本來是網址；React 19 讓它也可以是函式。依 react.dev 的 <form> 文件，傳函式時 React 會：

  • 收集每個有 name 的欄位，用 FormData 呼叫你的函式；不用 preventDefault，也不用 value／onChange（欄位可以是非受控）。
  • 在 Transition 裡執行它，也就是第 16 課說的 Action。函式可以是 async，Action 一直進行到 Promise 結束。
  • 讓表單裡的元件用 useFormStatus 讀到「送出中」。
  • 函式丟出的錯誤交給最近的 Error Boundary。
  • 函式成功結束（沒有丟錯）後，重設表單裡的非受控欄位，回到 defaultValue。

開場的「topic 是 null」也解決了：new FormData(form) 不會包含按下去的那顆按鈕；React 給 action 的 FormData 會包含（文件：送出的按鈕的 name 和 value 會放進 FormData）。在輸入框按 Enter 時，瀏覽器等於按第一顆送出按鈕（HTML 規格的 implicit submission，隱式送出），所以 topic 是 new。本機用 happy-dom 21.0.4 實測過這兩件事。

「成功後重設」要特別注意：action 一定要 await（或回傳）那個 Promise。寫成 subscribe(…) 不等它，Action 立刻結束，欄位馬上被清空，失敗時也沒人接得到錯誤。反過來，在 await 之前自己 form.reset()，送出中使用者就看不到自己打了什麼。

onSubmit<form action={fn}>
拿到什麼submit 事件，要自己 preventDefaultFormData（含送出的按鈕）
送出中自己用 state 記React 追蹤（Transition），子元件用 useFormStatus 讀
成功後自己清空自動重設非受控欄位
丟錯async 處理函式的錯誤沒人接（只在 Console）交給最近的 Error Boundary

兩個可以一起寫：文件說明 onSubmit 先執行，它沒有呼叫 preventDefault 時才接著執行 action。Vue 沒有對應的東西：@submit.prevent 之後的流程（送出中、清空、錯誤）都是自己寫，跟 React 的 onSubmit 一樣（Vue 課第 18 課）。

丟錯交給 Error Boundary 會換掉整塊畫面，使用者打的字也跟著不見。它適合「不該發生」的錯誤（程式錯誤）。網路失敗、時段額滿這種預期中的錯誤，要接起來顯示在表單上，下面的 useActionState 就是做這件事的。

useFormStatus：送出按鈕自己知道表單在送出

送出中要停用按鈕、換文字，這件事每張表單都要做，適合抽成共用的 SubmitButton。useFormStatus（從 react-dom import）讓按鈕自己讀「包住它的那個 <form>」的狀態，不用從父元件傳 props：

import { useFormStatus } from 'react-dom'

function SubmitButton({ children, pendingText }: { children: ReactNode; pendingText: string }) {
  const { pending } = useFormStatus()
  return <button type="submit" disabled={pending}>{pending ? pendingText : children}</button>
}

<form action={checkoutAction}>
  …
  <SubmitButton pendingText="結帳中…">結帳</SubmitButton>
</form>

回傳值有四個欄位（react.dev 與 @types/react-dom 19.3）：pending、data（正在送出的 FormData，沒在送出時是 null）、method、action。用 data.get('name') 可以顯示「正在替王小明結帳…」。

最常見的錯，是在 render <form> 的同一個元件裡呼叫它：

function CheckoutForm() {
  const { pending } = useFormStatus()   // ✗ 永遠是 false
  return <form action={checkoutAction}>…</form>
}

文件寫明：它只回報父層的 <form>，不包含同一個元件或子元件裡 render 的 form。概念上像 Context（第 11 課）：<form> 是 Provider，只有它裡面的元件讀得到。所以同一頁有兩張表單時，各自的按鈕只反映自己那張。

按鈕 disabled 之後，在輸入框按 Enter 也不會再送出：HTML 規格規定隱式送出只在預設按鈕「不是 disabled」時觸發。但它只擋得住使用者，程式呼叫 form.requestSubmit() 還是會送出，所以真正的防重複仍然要靠伺服器（Vue 課第 18 課的冪等鍵）。

Vue 的對照：子元件要知道表單狀態，一般是父元件用 props 傳 submitting，或用 provide／inject。React 的 <form> 等於內建了一個 provide。

💡 實務上：SubmitButton 是設計系統裡最值得先做的表單元件
咖啡店前台的結帳、會員資料、後台的商品編輯，每張表單都需要「送出中停用、換文字」。做成一個讀 useFormStatus 的 SubmitButton，所有用 <form action> 的表單放進去就有，不用每張各傳一次 pending。要注意它只認 <form action>，或 onSubmit 裡用 startTransition 執行的 Action（文件有這個用法）；純 onSubmit ＋ useState 的舊表單讀不到，混用時要在元件文件寫清楚。

useActionState：把送出的結果變成 state

<form action> 管送出中與重設，但沒有地方放「這次送出的結果」：錯誤訊息、訂單編號。useActionState 補上這一塊：

const [state, formAction, isPending] = useActionState(orderAction, initialOrderState)

async function orderAction(prev: OrderState, formData: FormData): Promise<OrderState> {
  …                       // 驗證、呼叫 API
  return 新的 state       // 下一次 render 的 state
}

<form action={formAction}>…</form>

依 react.dev：你給它一個函式和初始值，它回傳三個東西：目前的 state、交給 <form action> 的函式、是否有 Action 進行中的 isPending。表單送出時，React 用「上一次的 state」和 FormData 呼叫你的函式，回傳值就是新的 state。

幾個從文件與實測確認的行為：

  • 像 useReducer，但可以有副作用：官方文件把這個函式叫 reducer action。第 8 課的 reducer 必須是純函式；這裡可以 await API。文件的區分：useReducer 管 UI 的 state，useActionState 管 Action 的結果。
  • FormData 是第二個參數：從 <form action={fn}> 改成 useActionState 時，最常忘了函式多了第一個參數 prev，結果拿 state 去呼叫 .get()。
  • 依序執行：連續送出好幾次，React 把它們排隊，前一個回傳了才執行下一個，因為下一個需要前一個的結果當 prev。要平行就不適合用它。
  • 不在 Action 裡呼叫會被警告：交給 <form action> 或 <button formAction> 時 React 自動包 Transition；自己在 onClick 呼叫要包 startTransition。實測沒包時 Console 印出 An async function with useActionState was called outside of a transition.，isPending 也不會更新。
  • 回傳的形狀每次都一樣：文件建議成功和失敗都回傳同一種物件，畫面只看 state 的欄位，不用另外記「上一次成功過」。

錯誤分兩種處理，文件的「Handling errors」寫得很明確：預期中的錯誤（驗證沒過、庫存不足）放進回傳的 state 顯示；預期外的錯誤（程式錯誤）丟出去，React 取消排隊中的 Action，交給最近的 Error Boundary。要和第 16 課的 useOptimistic 一起用也可以：在傳給 <form action> 的函式裡先加樂觀的值，再呼叫 useActionState 給的函式（文件的範例就是這樣），規則和第 16 課一樣。

驗證放進 Action：zod 與伺服器的錯誤

Action 是 (prev, formData) => 新的 state，不需要 import React，可以放在獨立的檔案、不掛元件就能測試。它的寫法跟伺服器端的處理函式一樣：React 的 Server Function（第 22 課）就是這樣接表單的。所以驗證寫在這裡，就像寫後端 API：讀原文 → 驗證 → 呼叫 API → 回傳結果。

第一步是把 FormData 讀成固定形狀的原文。formData.get 給的是字串，欄位不存在時是 null，直接 Object.fromEntries(formData) 會少欄位，zod 會給英文的 Invalid input: expected string, received undefined（zod 4.6.7 實測）：

const FIELDS = ['name', 'phone', 'quantity', 'pickupTime'] as const

function readValues(formData: FormData): OrderValues {
  const values = { name: '', phone: '', quantity: '', pickupTime: '' }
  for (const field of FIELDS) {
    const v = formData.get(field)
    values[field] = typeof v === 'string' ? v : ''    // 缺少的欄位當成 ''
  }
  return values
}

第二步用 zod 驗證。Vue 課第 18 課用過同一套 API：safeParse 不丟錯，z.flattenError(error).fieldErrors 整理成「欄位 → 訊息陣列」（zod 文件 Formatting errors）。表單多一件事要處理：數量是字串。

const QUANTITY = '數量要是 1～20 的整數'

const orderSchema = z.object({
  name: z.string().trim().min(1, '請輸入姓名'),
  phone: z.string().regex(/^09\d{8}$/, '手機要是 09 開頭的 10 碼數字'),
  quantity: z.coerce.number({ error: QUANTITY }).int(QUANTITY).min(1, QUANTITY).max(20, QUANTITY),
  pickupTime: z.string().regex(/^([01]\d|2[0-3]):[0-5]\d$/, '取餐時間要是 HH:mm'),
})

z.coerce.number() 先用 Number() 轉型再驗證。實測 zod 4.6.7：'' 變成 0、' 4 ' 變成 4，'abc' 變成 NaN，NaN 會得到 expected number, received NaN 的英文訊息，所以 coerce.number 本身也要給 { error: … }。.trim() 會改寫輸出：parsed.data.name 是去掉空白的姓名，送給 API 的就是它。

第三步把結果和 API 的錯誤都變成 state：

export function createOrderAction(api: OrderApi) {
  return async function orderAction(_prev: OrderState, formData: FormData): Promise<OrderState> {
    const values = readValues(formData)
    const parsed = orderSchema.safeParse(values)
    if (!parsed.success) {
      return { ...initialOrderState, values, fieldErrors: z.flattenError(parsed.error).fieldErrors }
    }
    try {
      const { id } = await api.placeOrder(parsed.data)     // quantity 已經是 number
      return { ...initialOrderState, orderId: id }          // values 是空字串：表單會清空
    } catch (error) {
      if (error instanceof ServerValidationError) {         // 422：時段已額滿
        return { ...initialOrderState, values, fieldErrors: error.fieldErrors }
      }
      return { ...initialOrderState, values, formError: '送出失敗，請再試一次' }
    }
  }
}
  • 一次回傳所有錯誤：safeParse 會檢查每個欄位，flattenError 整理好，不要遇到第一個錯就 return。
  • values 放原文：失敗時回傳使用者打的字（不 trim），下一節會用它放回欄位。
  • 每次從 initialOrderState 開始：不要寫 { ...prev, orderId }，上一次的錯誤會留下來。prev 在需要累計的情況才用（例如文件的購物車數量）。
  • 伺服器的欄位錯誤和前端的同一個形狀：ServerValidationError 就是 Vue 課第 16 課 API 層把 422 轉出來的那種錯誤，放進 fieldErrors，畫面不用分辨錯誤是誰給的。
💡 實務上：前端的 Action 驗證是體驗，伺服器的驗證才是規則
這裡的 Action 跑在瀏覽器，使用者打開 DevTools 就能繞過，所以 API 一定要自己再驗一次（Vue 課第 18 課「前端驗證只是為了體驗」）。前後端都用 TypeScript 時，常見做法是把 orderSchema 放進共用套件，表單和 API 用同一份規則；「時段額滿」這種要查資料庫的規則只能在後端，靠 422 帶回來。跟後端先對好錯誤格式：欄位名稱要跟表單的 name 一樣，前端在 API 層轉成 fieldErrors 一次，每個 Action 就不用各自解析。

保留輸入：自動重設與 defaultValue

文件的 Troubleshooting 有一條「送出後欄位被清空」：Action 成功結束後，React 把非受控欄位重設成 defaultValue；回傳驗證錯誤也算成功結束（只有丟錯才不算）。所以只顯示錯誤不夠，使用者打的字會全部消失。

做法是讓 defaultValue 跟著 state 走，這也是文件的範例：

const [state, formAction, isPending] = useActionState(orderAction, initialOrderState)
const error = state.fieldErrors.phone?.[0]

<input
  id={`${id}-phone`}
  name="phone"
  defaultValue={state.values.phone}             // 失敗：這次的原文；成功：''
  aria-invalid={error ? true : undefined}
  aria-describedby={error ? `${id}-phone-error` : undefined}
/>
{error && <p role="alert" id={`${id}-phone-error`}>{error}</p>}

文件的說法是 React 會先套用新的 defaultValue 再重設，所以失敗時欄位「重設」成剛剛送出的值，看起來就是保留；成功時 values 是空字串，欄位清空。本機實測（React 19.3.1、happy-dom）文字框、textarea、checkbox 的 defaultChecked、數字欄位都會照新的預設值重設。其他控制重設的方式（文件 Other ways to control form resets）：

想要做法
失敗保留、成功清空defaultValue 用 state 裡的 values（本課）
成功也保留（編輯頁）回傳存好的值，defaultValue 用它
完全不要自動重設改用 onSubmit ＋ preventDefault，在 startTransition 裡執行 Action
在 Action 裡某個時間點重設requestFormReset(form)（react-dom）
連元件的 state 一起重來換元件的 key（第 4 課）

受控欄位不受影響：重設只動非受控的欄位，實測受控的輸入框在 Action 後保留原值。但受控就回到每打一個字重新 render，失去用 Action 的一半好處；需要邊打邊驗證的欄位才受控，其他保持非受控。

錯誤訊息的可近用性和 Vue 課第 18 課一樣：有錯的欄位加 aria-invalid="true" 與指向訊息的 aria-describedby。React 會把 aria-invalid={false} 輸出成 aria-invalid="false"（aria-* 屬性照字串輸出），沒有錯時要給 undefined 才會移除屬性。

💡 實務上：從受控表單搬到 Action 時，先檢查三件事
舊表單常見的寫法是全部受控，再加一個 onSubmit。搬到 <form action> 時：每個欄位要有 name，不然 FormData 裡沒有它；失敗要保留的欄位，defaultValue 要接到 state；select、日期這類元件先實測重設後的值對不對，不確定的欄位留成受控或換 key。code review 時看 Action 有沒有把預期中的錯誤接起來，沒接的話一次網路失敗就會讓整張表單變成 Error Boundary 的畫面。

選哪一種送出方式

這門課到這裡有三套送出的工具，它們可以並存：

受控 ＋ onSubmit（第 4 課）<form action> ＋ useActionStateTanStack Query useMutation（第 16 課）
欄位state，每個字重新 render非受控，送出時讀 FormData都可以，送出時呼叫 mutate
送出中、錯誤自己寫isPending、useFormStatus、回傳的 stateisPending、error
適合邊打邊驗證、依輸入切換欄位、即時摘要送出時才需要值的表單；會用到 Server Function 的專案寫完要讓快取失效、要樂觀更新快取
Vue 對照v-model ＋ @submit.prevent沒有內建對應Vue 版的 TanStack Query 也有 useMutation

它們不互斥：useMutation 的 mutateAsync 可以在 Action 裡 await，表單照樣用 useFormStatus 顯示送出中。邊打邊顯示錯誤的需求（第 4 課、Vue 課第 18 課的 touched）Action 做不到，Action 只在送出時驗證；兩者可以混用，送出前的即時提示用受控欄位，最終的驗證放在 Action。

💡 實務上：先選團隊的預設，再看例外
同一個專案裡，一半表單用 Action、一半用受控 ＋ onSubmit、再有幾張用表單函式庫，新人每次都要先猜這張是哪一種。資深工程師會定一個預設（例如「送出才驗證的表單用 Action ＋ zod，SubmitButton 共用」），把例外寫進文件：需要即時驗證、拖拉排序明細列、多步驟精靈這類，再選受控或函式庫。導入表單函式庫前，確認它對 React 19 Actions 的支援程度與版本。

練習 5：OrderForm 裡寫 const { pending } = useFormStatus()，同一個元件 return <form action={formAction}>…<button disabled={pending}>。送出時按鈕會怎樣？

✓ useFormStatus 只回報父層的 <form>，不包含同一個元件 render 的 form。它不會丟錯，只是讀不到，所以永遠是 false。把按鈕抽成 form 裡面的子元件，或在這個元件直接用 useActionState 的 isPending。

練習 6：Action 驗證失敗時回傳 { fieldErrors }，欄位是 <input name="phone" />（沒有 defaultValue）。使用者按送出後會看到什麼？

✓ 文件寫明「回傳驗證錯誤而不是丟錯，也會觸發重設」。要保留，就把送出的原文放進回傳的 state，當成 defaultValue。a 是常見的誤解；c 錯在 useActionState 的回傳值就是新的 state，不用另外存。

練習 7：顧客網路很慢，連按了兩次「送出」（按鈕沒有停用），useActionState 的 Action 會怎麼執行？

✓ 文件說明 useActionState 會把呼叫排隊，每一次拿前一次的結果當 prev，所以是依序執行。兩次都會真的送出，c 錯；要防重複，用 isPending 或 useFormStatus 停用按鈕，伺服器再用冪等鍵擋。b 是自己用 useState ＋ 兩個 fetch 才會遇到的競態。

常見錯誤

  • action 沒有 await 那個 Promise：Action 立刻結束，欄位馬上被清空，失敗也沒人接。await 或回傳 API 的 Promise。
  • 用 new FormData(form) 讀送出按鈕的值：拿不到 submitter。用 <form action>，或 new FormData(form, e.nativeEvent.submitter)。
  • 在 render form 的元件裡呼叫 useFormStatus：pending 永遠是 false。寫成 form 裡的子元件。
  • useActionState 的函式只寫一個參數：第一個參數是 prev，FormData 在第二個。
  • 預期中的錯誤丟出去：整張表單換成 Error Boundary，輸入全沒了。驗證錯誤、422、網路失敗回傳成 state，只有程式錯誤才丟。
  • 回傳錯誤卻沒有回傳原文：React 照樣重設欄位。原文放進 state，defaultValue 接上去。
  • 新的 state 寫成 { ...prev, … }：上一次的錯誤或訂單編號留下來。每次從初始值開始組。
  • 直接驗 Object.fromEntries(formData)：缺少的欄位、NaN 會得到 zod 的英文訊息。先讀成固定形狀的字串，coerce.number 也要給 error。
  • aria-invalid={false}：輸出成 "false"。沒有錯時給 undefined。

小結

  • <form action={fn}>：fn 收到 FormData（含送出的按鈕），在 Transition 裡執行；成功後重設非受控欄位，丟錯交給 Error Boundary。fn 要 await 它的 Promise。
  • useFormStatus（react-dom）讓表單裡的子元件讀到 pending 與 data，適合做共用的 SubmitButton；在 render form 的同一個元件裡讀不到。
  • useActionState(fn, initial) 回傳 [state, 給 form 的函式, isPending]；fn 是 (prev, formData) => 新的 state，可以 await、依序執行；預期中的錯誤回傳成 state，預期外的丟出去。
  • 驗證放在 Action：讀成固定形狀的原文 → zod safeParse（coerce、flattenError）→ 呼叫 API → 422 轉成同樣的 fieldErrors。伺服器仍要自己驗。
  • 保留輸入：回傳驗證錯誤也會重設，defaultValue 接到 state 裡的原文；錯誤用 role="alert"、aria-invalid、aria-describedby 關聯到欄位。
