階段 2：Hooks 與副作用 · 第 6 課

你可能不需要 effect：衍生值、事件與 key

咖啡店的點餐頁剛上線，客服就收到三種回報：菜單一打開會閃一下「共 0 項」；客人在拿鐵的卡片按了一次「加入」，切到別的頁面再回來，購物車多了一杯；店員在顧客備註寫了「少冰半糖」，點到下一位顧客，那段備註短暫出現在對方名下。三個 bug 都來自同一個習慣：把 useEffect 當成「某個東西變了就做點事」的萬用工具，就像在 Vue 裡什麼都用 watch。

這課的路線：
  1. 先問三個問題：這段程式是要一個值、回應使用者的操作，還是跟外部同步，各該放在哪裡（開場問題的最小答案）。
  2. 能算出來的值、使用者做的事：篩選後的菜單、合計金額直接在 render 算，「加入購物車」放在事件處理函式，都不經過 effect。
  3. 通知父元件、用 key 重設：數量改了怎麼告訴父元件，換顧客時怎麼讓表單整個重來，不殘留上一位的備註。
  4. 只調整部分 state、真的需要 effect 的時候：只想重設一部分 state 的寫法，以及刪完之後 effect 還剩哪些工作。
這課會用到：
  • 第 5 課的 useEffect：在畫面更新之後執行，用來跟外部系統同步；依賴陣列列出它讀到的值，值變了就重新執行。
  • 第 3 課的 state：state 是快照，同一個事件裡的多次 set 只 render 一次；state 跟著元件在樹上的位置走，換 key 就整個重建。

先問：要一個值、回應一個操作，還是跟外部同步

第 5 課說過，effect 是 React 給你的逃生口（escape hatch）：在畫面更新之後執行，用來讓元件跟 React 管不到的外部系統同步，例如瀏覽器分頁標題、計時器、WebSocket、第三方地圖元件。React 官方文件〈You Might Not Need an Effect〉的說法是：沒有外部系統參與時，通常就不需要 effect。

寫一段程式之前，先問它為什麼要執行：

它為什麼要執行放哪裡咖啡店的例子Vue 的對應
畫面需要一個從 props、state 算得出來的值render 中直接算（慢才加 useMemo）篩選後的菜單、合計金額、按鈕能不能按computed
使用者做了某個操作事件處理函式按「加入」、送出訂單、通知父元件數量改了事件處理函式裡 emit
props 換成另一個東西，整個元件要重來父元件給它 key換顧客時清空備註表單:key
元件顯示在畫面上，要跟外部保持一致useEffect同步分頁標題、訂閱訂單狀態、記錄「看過這個商品」watch、onMounted

這張表跟 Vue 課第 5 課「要一個值用 computed，要對外做事才用 watch」是同一條判斷。差別在 React 沒有 computed：元件函式本身每次 render 都會重新執行，算得出來的值寫成普通的 const 就好。

能算出來的值：在 render 中直接算

菜單頁有分類按鈕和「便宜的排前面」勾選框。第一版把每一步的結果都放進 state，用 effect 一個接一個同步：

// ✗ 三份多餘的 state、三個 effect 串成一條鏈
const [filter, setFilter] = useState<Filter>('all')
const [cheapFirst, setCheapFirst] = useState(false)
const [filtered, setFiltered] = useState<readonly Product[]>([])
const [visible, setVisible] = useState<readonly Product[]>([])
const [count, setCount] = useState(0)

useEffect(() => {
  setFiltered(filter === 'all' ? products : products.filter(p => p.category === filter))
}, [products, filter])
useEffect(() => {
  setVisible(cheapFirst ? filtered.toSorted((a, b) => a.price - b.price) : filtered)
}, [filtered, cheapFirst])
useEffect(() => {
  setCount(visible.length)
}, [visible])

effect 在畫面更新之後才執行，裡面的 setState 又排一次 render。在這課的練習環境（React 19.3.1）用 <Profiler> 記下每次 commit（真的寫進 DOM）時畫面上的內容，第一次顯示總共 commit 了 4 次：

原因是多餘的 state（redundant state）：filtered、visible、count 都是 products、filter、cheapFirst 的函式，存成 state 就多了三份要「追著同步」的資料，追的過程中畫面就是錯的。修法是刪掉它們，在 render 中直接算：

// ✓ state 只留使用者真正能改的東西
const [filter, setFilter] = useState<Filter>('all')
const [cheapFirst, setCheapFirst] = useState(false)

const filtered = filter === 'all' ? products : products.filter(p => p.category === filter)
const visible = cheapFirst ? filtered.toSorted((a, b) => a.price - b.price) : filtered
// 件數就是 visible.length，連變數都不用

每次 render 都從來源重新算，值永遠跟來源一致，也沒有「忘了同步某種情況」的機會。排序用第 3 課的 toSorted()：它回傳新陣列，sort() 會改到 props 傳進來的陣列。

判斷一個值該不該是 state：它能不能從現有的 props 或 state 算出來？能就不是 state。剩下的 state 通常很少，就是使用者的選擇（選了哪個分類、勾了什麼）和從伺服器拿到的資料。同樣的道理也適用於「選中的那一筆」：存 selectedId，每次 render 用 items.find(i => i.id === selectedId) 找出物件，清單更新後選取不會指到舊物件。練習 4 的 CustomerNotes 就是這樣寫的。

跟 Vue 的 computed 比

Vue 的 computed 會快取：依賴沒變時再讀，直接回傳上次的結果（Vue 官方文件〈Computed Caching vs. Methods〉，你在 Vue 課第 3 課自己寫過）。React 的寫法沒有快取，元件每 render 一次就算一次。篩選幾十個商品的成本可以忽略；真的量到很慢（例如幾千筆資料、別的 state 一改就重算），才用 useMemo 把結果留到依賴改變為止：

const visible = useMemo(
  () => (cheapFirst ? filtered.toSorted((a, b) => a.price - b.price) : filtered),
  [filtered, cheapFirst],   // 依賴用 Object.is 比較，少寫一個就會拿到舊的結果
)

React 文件寫明 useMemo 只是效能優化：拿掉它程式要照樣正確。什麼時候值得加、怎麼量，留到第 19 課；第 20 課的 React Compiler 會自動做這類快取。不管哪一種，都不是「state 加 effect」。

💡 實務上：看到 effect 裡只有 setState，先問「這能不能算出來」
接手的 React 專案很常看到 useEffect(() => setTotal(...), [items]) 這種寫法，效果和 Vue 專案裡用 watch 維護 total 一樣：多一份 state、多一次 render、偶爾畫面閃一下。eslint-plugin-react-hooks 7 的 recommended 設定有一條 react-hooks/set-state-in-effect，會擋下在 effect 本體裡同步呼叫 setState（7.1.1 實測，錯誤訊息是 Calling setState synchronously within an effect can trigger cascading renders）。團隊升級 lint 時這條常一次冒出幾十個錯誤，資深的做法是逐個分類：能算的改成 render 中算，因操作而起的搬進事件，真的在跟外部同步的才保留，不要整批加 eslint-disable。

使用者做的事：放在事件處理函式

商品卡有「加入」按鈕。第一版用一個 added state 記「按過了」，讓 effect 去加入購物車：

// ✗ 用 state 當開關，讓 effect 替使用者做事
const [added, setAdded] = useState(false)

useEffect(() => {
  logView(product.id)
  if (added) {
    onAdd(product.id)
    notify(`已加入 ${product.name}`)
  }
}, [product, added, onAdd, notify, logView])

return <button type="button" onClick={() => setAdded(true)}>加入</button>

依賴陣列寫得很完整，lint 也沒抱怨，行為卻全錯：

  • 連按三次只加入一次：第二次 setAdded(true) 時值沒變，React 跳過這次更新，effect 不會再跑。
  • 父元件重新 render，傳進新的 onAdd 函式（inline 寫法每次都是新的），依賴變了，effect 重跑，added 還是 true：客人沒按，購物車多一杯。開頭客服回報的 bug 就是這個。
  • 換成別的商品，product 變了，effect 重跑：沒按過的可頌也被加入。

問題出在原因放錯地方。加入購物車的原因是「客人按了按鈕」，那是一個特定的時刻；effect 的原因是「畫面顯示成這樣了」，只要依賴變了就會再發生。React 文件的判斷方式：由某個操作造成的邏輯放事件處理函式；因為使用者看到這個元件而要做的事才放 effect。

// ✓ 一個原因一個位置
useEffect(() => {
  logView(product.id)          // 原因：卡片顯示了這個商品
}, [product.id, logView])

function handleAdd() {
  onAdd(product.id)            // 原因：客人按了「加入」
  notify(`已加入 ${product.name}`)
}

return <button type="button" onClick={handleAdd}>加入</button>

改完之後 added 也不需要了：按按鈕不再改 state，元件不會因此重新 render。logView 的依賴寫 product.id 而不是整個 product：重新抓資料後商品是新的物件，但 id 一樣就是同一個商品，不該重記一次（第 5 課講過依賴用 Object.is 比較）。

第 5 課的 StrictMode 會在開發時多跑一輪 setup → cleanup，所以 logView 開發時會被呼叫兩次，正式環境不會。React 文件對統計事件的建議是保持原樣，不要為了開發時的雙重呼叫把它搬到別處。
💡 實務上：會改資料的請求永遠從事件出發
送出訂單、加入購物車、扣點數、退款，這些 POST 只能在「使用者按了」的那一刻發出。放在 effect 裡，任何讓依賴改變的事（父元件重新 render、資料重新抓取、StrictMode 的重新掛載、路由回到這頁）都可能再送一次，結果就是重複扣款或重複訂單，而且只在某些操作順序下出現，很難重現。code review 看到 effect 裡有 POST、PUT、DELETE，或有一個「flag state 變 true 就去做事」的寫法，就該問：這件事是哪個使用者操作造成的？答得出來就搬進那個操作的事件處理函式。後端仍然要做冪等或重複檢查，前端放對位置只是第一道防線。

通知父元件：在同一個事件裡一起更新

購物車每一列有數量選擇器，自己記著 qty，數量改變時呼叫 onChange 讓父元件更新小計。用 effect「qty 變了就通知」看起來很自然：

// ✗ 用 effect 通知父元件
const [qty, setQty] = useState(defaultValue)

useEffect(() => {
  onChange(qty)
}, [qty, onChange])

在練習環境實測，父元件寫 onChange={n => setQty(n)}（inline 函式）時：

  • 一掛載就呼叫 onChange(1)：客人什麼都沒按，父元件卻收到「數量改變」。effect 在掛載時一定會跑。
  • 按一次「增加」，onChange(2) 被呼叫兩次，整列 commit 3 次：子元件先更新 → effect 通知 → 父元件更新、傳進新的 onChange → 依賴變了，effect 再通知一次。就算父元件傳的是穩定的函式，也要 commit 2 次。

修法是：造成改變的是這次點擊，就在點擊的處理函式裡同時更新自己、通知父元件：

// ✓ 一個事件，兩個元件一起更新
function change(next: number) {
  if (next < 1 || next > 20) return   // 數量沒變就不更新、不通知
  setQty(next)
  onChange(next)
}

<button type="button" aria-label="增加" onClick={() => change(qty + 1)}>+</button>

第 3 課講過，同一個事件裡的多個 setState 會被批次（batch）成一次 render，React 文件寫明不同元件的更新也一樣，所以子元件的 setQty 和父元件在 onChange 裡的 setState 一起處理，只 render 一輪。

注意 onChange(next) 要直接寫在事件處理函式裡，不能寫進 updater：

// ✗ updater 必須是純函式
setQty(q => {
  const next = Math.min(20, q + 1)
  onChange(next)    // StrictMode 開發時 updater 會被呼叫兩次，這裡就通知兩次
  return next
})

第 3 課講過，StrictMode 在開發時會多呼叫一次 updater（練習環境實測點一次執行 2 次），事件處理函式則不會。所以「算出下一個值」放 updater 或直接用這次 render 的 qty，「對外通知」放事件處理函式。

Vue 這邊是一樣的習慣：子元件在 @click 的處理函式裡 emit('change', next)（Vue 課第 9 課），很少有人寫「watch 自己的 qty 再 emit」。React 的 onChange prop 就是 emit 的對應物，只是它就是一個普通的函式 prop。

還有一個變化：如果父元件本來就要記數量，子元件可以完全不留 state，改成 value 加 onChange 的受控元件（第 4 課），只剩一份 state，連同步都不用。React 文件把這叫「狀態提升」（lifting state up），兩份 state 要保持一致時，先考慮這個。

props 變了要重設 state：用 key

顧客備註頁左邊是顧客清單，右邊是 NoteForm。第一版用 effect 在換顧客時清空草稿：

// ✗ 在 NoteForm 裡用 effect 重設
const [draft, setDraft] = useState('')
const [urgent, setUrgent] = useState(false)

useEffect(() => {
  setDraft('')
}, [customer.id])

實測換顧客時 commit 了 2 次，第一次的畫面是「給 陳美華 的備註」加上王小明的「少冰半糖」，effect 跑完才清空。而且只清了 draft：後來加的「急件」勾選框忘了重設；「回電時間」是第 4 課的非受控欄位（defaultValue），值存在 DOM 裡，根本沒有 setState 可以重設它。

回到第 3 課的規則：state 屬於元件在樹上的位置。同一個位置、同一種元件、同一個 key，React 就沿用原本的實例和它的 state；key 不同，React 當成另一個元件，卸載舊的、掛載新的，裡面所有 state 和 DOM 都從頭來。所以重設整個表單不需要在 NoteForm 裡做任何事，在父元件給它一個跟著顧客變的 key：

// ✓ 父元件：一位顧客一個 NoteForm
<NoteForm key={customer.id} customer={customer} />

刪掉 effect，換顧客只 commit 1 次，畫面一開始就是空白表單；以後 NoteForm 多加幾個欄位也不用記得補重設。key 的選法跟第 2 課列表的 key 一樣：

  • 用能代表「這是哪一位」的穩定 id：customer.id。
  • 不要用名字：兩位同名的顧客會共用同一個表單。
  • 不要用 Math.random()、Date.now()：父元件每次 render key 都不同，客人打字到一半、父元件因為別的原因重新 render，表單就被清空。

Vue 也有一樣的機制：官方文件說 key 除了用在 v-for，也能「強制替換元素或元件，而不是重用」，寫法是 <NoteForm :key="customer.id" :customer="customer" />。在 Vue 裡用 watch(() => props.customer.id, reset) 手動重設，會有一樣的漏網之魚；React 文件把 key 列為 props 改變時重設 state 的第一選擇。

💡 實務上：「換一筆資料時表單殘留上一筆的內容」幾乎都用 key 解
後台的編輯面板（換一張訂單、換一位會員）、聊天室換聯絡人、多步驟表單換一筆申請，都是同一種 bug：元件位置沒變，state 就沿用了。修法是在外層給它 key={id}。要考量的是成本：key 一換，整棵子樹都重建，裡面如果有昂貴的圖表或已經抓好的資料也會重來，這時把「要重設的部分」切成小元件，只給那一塊 key。另一個常見的坑是 key 放錯層：放在表單裡面某個 input 上，只會重設那個 input，表單本身的 state 還在。

只想調整部分 state：在 render 中比較上一次

有時候 props 改變時只想調整一部分 state，例如菜單換了一份（items 換了），選取要清掉，但「排序方式」要留著，用 key 會連排序一起重設。React 文件給的做法是在 render 中記住上一次的 props，自己比較：

const [selection, setSelection] = useState<Product | null>(null)
const [prevItems, setPrevItems] = useState(items)

if (items !== prevItems) {   // 一定要有條件，而且條件裡要更新 prevItems，否則無限迴圈
  setPrevItems(items)
  setSelection(null)
}

在 render 中呼叫 setState 時，React 會丟掉這次回傳的 JSX，在畫子元件和改 DOM 之前立刻重新 render 這個元件，所以畫面不會出現過期的值。實測 items 換掉時只 commit 1 次；用 effect 重設（像上一節的 NoteForm）是 2 次。規則（React 文件〈useState〉）：

  • 只能更新正在 render 的這個元件的 state，更新別的元件會報錯。
  • 必須包在條件裡。eslint-plugin-react-hooks 7.1.1 的 set-state-in-render 會擋下沒有條件的 setState（訊息 Cannot call setState during render），上面這種有條件的寫法實測不會被擋。
  • 其他副作用（改 DOM、設計時器）仍然只能放事件或 effect。

這個寫法不好讀，React 文件也說大多數元件不該需要它。先試前面兩招：能不能改存 id、在 render 中算出來（上面的例子改存 selectedId，商品還在清單裡就維持選取，不在就自然是 null）；能不能整個用 key 重設。都不行才用這招。

真的需要 effect 的時候

刪掉這麼多 effect 之後，剩下的才是 effect 真正的工作：讓元件跟外部系統保持同步，而且這件事的原因是「元件顯示在畫面上」。

  • 同步瀏覽器 API：分頁標題、localStorage、第三方地圖元件（第 5 課的練習 1）。
  • 訂閱與連線：訂單推播、WebSocket、計時器，一定要寫清理函式。
  • 依目前的參數抓資料：要處理競態（第 5 課的練習 5），實務上多半交給 TanStack Query（第 15 課）。
  • 因為「看到了」而送的統計事件：練習 2 的 logView。

一個簡單的自我檢查：把 effect 裡的程式唸出來，如果句子是「當 X 變了，就把 Y 設成…」，Y 多半能在 render 中算；如果是「當 X 變了，就去做 Z」，先找出是哪個使用者操作讓 X 變的，Z 多半屬於那個操作；只有「只要畫面顯示著 X，外面的 W 就要跟著是 X」才是 effect。

練習

在 learn/ 執行 node check.mjs react 06。測試用 <Profiler> 數元件 commit 了幾次，所以「畫面最後對了」不夠，中間多 render 的寫法也會被擋下；也會用 eslint-plugin-react-hooks 檢查依賴陣列與 set-state-in-effect，不能用 eslint-disable 關掉。測試傳進去的商品與顧客陣列是凍結的，改到它們會丟 TypeError。

練習 1：MenuList 把篩選後的清單、排序後的清單、件數各自存成 state，用三個 effect 串起來。改成 state 只留 filter 和 cheapFirst，清單與件數在 render 中從 products、filter、cheapFirst 算出來。勾「便宜的排前面」時價格由低到高、同價維持原本順序，取消後回到 products 原本的順序（用 toSorted()，不能改 props）。完成的標準：第一次顯示只 commit 一次（不能有「共 0 項」的中間畫面）；按分類、勾排序、父元件換一份 products 各只多 commit 一次；檔案裡沒有在 effect 裡 setState。

練習 2：ProductCard 用 added state 加 effect 去加入購物車。改成：onAdd(product.id) 與 notify(`已加入 ${product.name}`) 放在「加入」按鈕的事件處理函式，按幾次就呼叫幾次，沒按不能呼叫，父元件重新 render 或換商品都不能替客人加入；按按鈕不需要任何 state，元件不能因此重新 render。logView(product.id) 留在 effect：顯示時記一次，換成 id 不同的商品再記一次，同一個商品換成新物件不重記。依賴陣列要完整（會跑 exhaustive-deps）。

練習 3：QuantityStepper 用 effect「qty 變了就呼叫 onChange」。改成在「增加」「減少」的事件處理函式裡同時更新 qty 並呼叫 onChange(新的數量)：掛載時不呼叫；每按一次恰好呼叫一次；數量範圍 1～20，到邊界再按數量不變、也不呼叫；父元件在 onChange 裡 setState 時按一次只 commit 一輪；父元件傳 inline 函式、或在 StrictMode 下，都不能重複通知（不能把 onChange 寫進 updater）。

練習 4：CustomerNotes 的 NoteForm 用 effect 在換顧客時清空草稿，結果急件和非受控的「回電時間」都沒重設，畫面還會先閃過上一位顧客的備註。刪掉 effect，改用 key 讓換顧客時 NoteForm 整個重來。完成的標準：換顧客後備註、急件、回電時間全部空白，而且輸入框是新的 DOM 節點；換顧客只 commit 一輪；同名但 id 不同的兩位顧客也要重設；父元件重新 render、或再點一次同一位顧客時，已經輸入的內容要留著。

練習 5：結帳頁有下面四件事，哪一件該放在 useEffect？

✓ 統計事件的原因是「這個頁面顯示了」，跟哪個操作無關，這正是 effect 的用途（開發時 StrictMode 會送兩次，正式環境不會）。送出訂單和通知父元件是某個使用者操作造成的，放事件處理函式；放在 effect 裡，依賴一變就會重送。合計金額能從購物車算出來，在 render 中直接算，不用 state 也不用 effect。

練習 6：QuantityStepper 寫成 useEffect(() => { onChange(qty) }, [qty, onChange])，父元件傳 onChange={n => setQty(n)}。客人按一次「增加」（1 → 2）之後，會發生什麼？

✓ 子元件 setQty(2) → commit → effect 呼叫 onChange(2) → 父元件 setState → 父元件 render 時建立新的箭頭函式 → 子元件的 onChange 依賴變了 → effect 再跑一次 onChange(2)。第二次父元件 setState 同一個值，所以停下來，不是無限迴圈（這課實測：呼叫兩次、commit 3 次）。effect 在掛載時也會跑，所以掛載時還多呼叫了一次 onChange(1)。在事件處理函式裡呼叫，就沒有「依賴變了」這回事。

練習 7：菜單有 5000 個品項，篩選很慢，每次打字（別的 state）都重算一次，畫面卡頓。最合適的處理是？

✓ 問題是「重算太多次」，useMemo 正好解決這件事：依賴沒變就回傳上次的結果，程式的意思不變，拿掉也照樣正確。state 加 effect 也只在依賴改變時算，但多了一份 state，每次改變多 render 一次，中間還會出現舊的清單。key 是用來重設 state 的，跟計算成本無關，重建整個清單只會更慢。要不要加 useMemo 應該先量測，第 19 課會教怎麼量。

常見錯誤

  • 把能算出來的值存成 state，用 effect 同步：多一次 render，畫面會短暫顯示舊值，effect 串起來更多次。刪掉那份 state，在 render 中算；慢才 useMemo。
  • 用「flag state 變 true」觸發 effect 去做事：連按只觸發一次，依賴變了又重做一次。直接在事件處理函式裡做。
  • 用 effect 呼叫父元件的 onChange：掛載時就通知，多 render 一輪，inline 函式還會讓它重複通知。在造成改變的事件裡同時 setState 和呼叫 onChange。
  • 把副作用寫進 updater 函式：StrictMode 開發時 updater 會被呼叫兩次。updater 只算下一個值，通知寫在事件處理函式。
  • 用 effect 一個一個重設 state：先閃一次舊資料，新加的 state 和非受控欄位會漏掉。給元件 key={id}。
  • key 用名字、index 或 Math.random()：同名的會共用 state；亂數讓父元件每次 render 都清空表單。用穩定且唯一的 id。
  • effect 依賴整個物件：重新抓資料後物件是新的，effect 又跑一次。依賴寫用得到的基本型別欄位，例如 product.id。
  • 在 render 中無條件 setState：無限迴圈。「比較上一次」的寫法一定要包在條件裡，而且只能改自己這個元件的 state。

小結

  • 寫之前先問「這段程式為什麼要執行」：要一個值 → render 中算；使用者做了操作 → 事件處理函式；元件顯示著、要跟外部一致 → effect。
  • 能從 props、state 算出來的就不是 state。React 沒有 computed，寫成普通的 const；Vue 的 computed 會快取，React 要快取時才用 useMemo。
  • effect 裡同步 setState 會多一次 render，畫面短暫是錯的；eslint-plugin-react-hooks 7 的 set-state-in-effect 會擋。
  • 通知父元件和更新自己放在同一個事件裡，React 會把兩個元件的更新批次成一次 render；updater 要是純函式。
  • props 換成另一筆資料時，用 key 重設整個元件（含非受控欄位的 DOM），key 用穩定的 id。
  • 只調整部分 state 時，可以在 render 中有條件地 setState，但先試「改存 id 再算」和 key。
