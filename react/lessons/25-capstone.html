階段 6：品質與期末專題 · 第 25 課

期末專題：咖啡店線上點餐（React 版）

咖啡店要上線點餐 App：顧客在手機上看菜單、選大小和甜度、結帳、看訂單做到哪了；店員在吧台用平板看自己門市的訂單，把做好的標成「可以取餐」。這是 Vue 課第 26 課的同一個 App，這次用 React 做。要同時成立的條件也一樣：分類要能分享、購物車重新整理不能不見、網路慢的時候不能下兩次單、店員不能看別間門市的訂單。

這課不介紹新的 API。要練的是資深工程師每天在做的事：從需求開始，決定每一塊狀態放哪裡；遇到兩三種都能用的做法時選一個，說得出代價；收到同事的程式時，對照需求找出問題。版本以 React 19.3.1、React Router 8.5.1、TanStack Query 5.106.1、Zustand 5.0.16、zod 4.6.7 為準（react/practice/package.json）。

這課的路線：
  1. 需求與規劃：把需求寫成驗收條件，決定每塊狀態與程式碼放哪裡（這是開場問題的答案）。
  2. 菜單與購物車：分類放網址、菜單交給查詢快取；換分類不閃該用哪個工具；購物車的持久化要驗證。
  3. 結帳：React 會把連續的送出排隊，加上冪等鍵，怎麼做到不下兩次單；錯誤怎麼分類。
  4. 店員區：守衛、「可以取餐」的寫入，以及好幾顆一樣的按鈕怎麼讓讀螢幕軟體分得出來。
  5. 審查同事的 PR，再替守衛寫檢查：對照需求找問題，確認測試抓得到錯。
這課會用到：第 14～24 課的工具。不用先複習：每一步用到哪一課，會在那一步連回去，並用一句話回顧要用的觀念。做過 Vue 課期末專題的，第二節有一張兩邊做法的對照表。

需求與驗收條件

需求常常只有一句話：「顧客可以結帳」。這句話判斷不了做完了沒有。驗收條件（acceptance criteria）是需求完成的具體標準，寫成「在什麼情況下、做什麼、應該得到什麼結果」，例如「送出失敗時購物車不變、留在結帳頁」。好的驗收條件可以直接改寫成測試，這課每一題練習檔案開頭的註解就是它的驗收條件，隱藏測試照著它寫。

功能驗收條件（節錄）
菜單分類在網址上，分享、上一頁都還原；換分類時舊菜單留著，不閃載入畫面；載入中、錯誤加重試、沒有結果三種畫面
購物車同商品不同甜度是兩列；重新整理後還在；storage 裡的壞資料不讓 App 當掉；頁首徽章只在件數變了才重新 render
結帳連按兩次只建立一筆訂單；網路斷了重送不會變成兩筆；「時段額滿」顯示在取餐時間下面；失敗不清空購物車
訂單狀態換訂單不會看到上一筆的資料；重新整理失敗時留著上次的狀態；明細壞掉只壞明細
店員區只有店員、店長能進，而且只能進自己門市的；「可以取餐」等伺服器確認才算數，讀螢幕軟體分得出每顆按鈕

一條驗收條件通常同時寫出「做對的樣子」和「最常見的做錯方式」。「失敗不清空購物車」會出現在清單上，是因為把清空寫在 finally 裡是真的常見的 bug。

規劃：狀態放哪裡、程式碼放哪裡

有了驗收條件，動手之前先列出 App 裡有哪些資料，再用第 14 課的兩個問題（誰要讀、正本在哪）決定每一塊放哪裡。先自己填一次再往下看：分類、搜尋關鍵字、菜單、購物車、結帳表單、訂單、登入的使用者。

資料放哪裡為什麼
分類網址 ?category=（useSearchParams）要能分享、上一頁要還原；網址就是正本，不要再存一份 state
搜尋關鍵字元件的 useState打字中的暫時狀態，寫進網址每個字都多一筆歷史紀錄；只篩選已經抓到的菜單
菜單、訂單TanStack Query 的快取正本在伺服器，前端手上的是會過期的副本，要能重抓、失效（第 15 課）
購物車Zustand ＋ persist客戶端的全域狀態：頁首、菜單、結帳頁都要用，重新整理還要在
結帳表單非受控欄位 ＋ useActionState 的 state只有結帳頁用；送出時才需要值（第 17 課）
登入的使用者路由外面的 auth 物件，交給 middleware守衛在 render 之前就要讀到（第 18 課）

最常見的錯誤是「全部丟進 store」。菜單放進 Zustand 之後，誰負責重抓？價格改了怎麼失效？兩個元件同時要菜單會不會抓兩次？這些是查詢快取幫你處理的事，store 不會。

兩邊的做法對照

做過 Vue 版的話，差別集中在這幾處（查表用，不用背）：

表上看得出一個規律：Vue 版很多流程是自己寫的（watch ＋ abort、外掛、進行中旗標），React 版多半交給函式庫或 React 本身（查詢快取、persist、Action 的佇列）。程式比較短，代價是要清楚每個工具的預設行為，例如 persist 不驗證內容、useActionState 會排隊而不是丟掉第二次送出。下面每一步都會碰到這種「預設行為」的判斷。

步驟一、二：菜單與購物車

規劃定好之後，從顧客最先看到的菜單開始。菜單（練習 1）把三課接在一起：分類用第 14 課的 useSearchParams（網址是正本，不合法的值當成預設）；點分類時用 setSearchParams(prev => …) 只改自己的鍵，桌號這類別人的參數保留；菜單用第 15 課的 useQuery，queryKey 是 ['menu', category]（快取的地址，每個分類各存一份，看過的分類回去直接有資料）。

「換分類時不要閃成載入中」這條驗收條件，前面教過三個看起來都能用的工具，這裡要選一個：

工具前提放在這裡
placeholderData: keepPreviousData（第 15 課）資料由 TanStack Query 管✓ 新 key 還沒資料時先給舊的，isPlaceholderData 拿來設 aria-busy
startTransition（第 21 課）新畫面會暫停（用 use() 讀、外面包 Suspense）✗ 這個 useQuery 沒有用 Suspense，新 key 沒快取時同一次 render 就回傳 isPending，沒有東西讓 Transition 等
useDeferredValue（第 21 課）慢的是 render 本身✗ 慢的是網路，不是 render；延後的那次 render 一樣拿到 isPending

判斷的順序是「資料由誰管、慢在哪裡」。菜單已經交給 TanStack Query，就用它的選項；第 21 課的 CategoryMenu 是自己用 use() 讀 Promise，才輪到 Transition。搜尋框也是一樣的判斷：六個商品篩選一下不到一毫秒，不需要 useDeferredValue；等商品格真的量到很慢（第 19 課：先量測），才加延後的值和 memo。

購物車（練習 2）的關鍵是「什麼算同一列」。只比商品 id，一杯正常甜、一杯無糖的拿鐵會合併成「拿鐵 ×2」，吧台只做了一種。key 要是商品加上所有會影響製作的選項：

export const lineKey = (productId: number, { size, sugar }: CartOptions) => `${productId}-${size}-${sugar}`

持久化用第 14 課的 persist（存到 localStorage，格式是 { state, version }）。第 14 課說過它不驗證內容：存的是 lines: null，讀回來就是 null，selectCount 一呼叫 reduce 整頁就壞了。Zustand 文件也在 createJSONStorage 寫了警告：讀出來的值直接當成你的型別，不做執行時檢查。驗證放在 merge，它拿到讀回來的資料和目前的 state，回傳要用的 state：

merge: (persisted, current) => {
  const parsed = persistedCartSchema.safeParse(persisted)
  return parsed.success ? { ...current, lines: parsed.data.lines } : current
},

在練習環境實測 Zustand 5.0.16 的 persist：

  • localStorage 是同步的，建立 store（或呼叫 persist.rehydrate()）時就讀完、merge 完。
  • 版本不同又沒給 migrate：Console 印出錯誤，merge 收到的 persisted 是 undefined，驗證不過，維持空車。
  • JSON 壞掉：錯誤交給 onRehydrateStorage，不會呼叫 merge，state 維持初始值；壞掉的字串留在 storage，下一次 set 寫入時才被蓋掉。

頁首徽章 CartBadge 只要件數，用 useCartStore(selectCount) 只訂閱這個數字。寫成 useCartStore() 拿整個 state，購物車任何一點變化都讓它重新 render；練習用第 19 課的 <Profiler> 數 commit 次數確認。

💡 實務上：先問「資料由誰管、慢在哪」，再挑工具
React 生態系對同一個症狀常有好幾個解法，code review 時最常看到的是「用錯層」：資料已經在 TanStack Query 裡，卻在外面再包 Transition；或網路慢，卻加了 useDeferredValue 和 memo，量起來沒有任何改善。資深工程師看到「畫面會閃」的回報，會先問三件事：資料是誰抓、誰快取的？慢的是網路還是 render（Profiler 看得出來）？已經顯示的內容是被誰換掉的？答案決定用哪一層的工具，PR 描述也寫得出為什麼選它。

步驟三：結帳不能下兩次單

購物車有了之後，結帳頁要把它變成一筆訂單。結帳頁（CheckoutPage.tsx，已經寫好）照第 17 課寫：欄位非受控，useActionState 接 Action，Action 讀 FormData、用 zod 驗證、呼叫 API、回傳新的 state。練習 3 寫的是 Action 裡「呼叫 API 之後」的部分，也是最容易出事的部分。

先看「連按兩次」。第 17 課說過 useActionState 會把呼叫排隊依序執行，不會丟掉第二次。送出按鈕用 useFormStatus 停用，擋得住第二次點擊，但第 17 課也說過，程式呼叫 requestSubmit()、或在按鈕停用前那一刻按的 Enter 還是會進來。排在後面的那一次，會在第一次成功之後才執行，這時購物車已經清空了。所以 Action 在呼叫 API 前先看一眼購物車：

const lines = deps.cart.lines()
if (lines.length === 0) return { ...initialCheckoutState, values, formError: '購物車是空的' }

這是跟 Vue 版最大的不同。Vue 版自己寫 if (submitting) return 直接丟掉第二次；React 版第二次一定會執行，要讓它「執行了也沒事」。

再看「網路斷了」。最危險的情況是伺服器其實建立了訂單，只是回應在路上斷了：前端以為失敗，客人再按一次。冪等鍵（idempotency key，同一次結帳的每次嘗試都帶同一個字串，伺服器看到重複的鍵就回傳第一次的結果，不建立第二筆）解決這個問題。前端要決定的是鍵什麼時候換：

這次的結果伺服器有沒有建立訂單下一次送出
網路斷線、5xx不知道沿用同一個鍵
4xx（422 時段額滿、409 售完）沒有，伺服器明確拒絕了換新的鍵：客人改了內容再送，是新的嘗試
成功有換新的鍵：下一次結帳是另一筆訂單

為什麼 4xx 不沿用：被拒絕之後客人通常會改內容（換個時段、拿掉售完的拿鐵），同一個鍵配上不同的內容，對伺服器來說是可疑的請求，常見的冪等實作會直接拒絕。鍵要跨過好幾次送出，所以放在 Action 外面（createCheckoutAction 的閉包），結帳頁用 useState(() => createCheckoutAction(…)) 只建立一次 Action。

最後是錯誤分類，沿用第 24 課：4xx 是預期中的，顯示伺服器的說明（422 放進 fieldErrors，顯示在取餐時間下面），不回報；網路、5xx、程式錯誤是預期外的，顯示通用訊息並 reporter.capture(錯誤, { source: 'handler' })。兩種都回傳成 state，不丟出去：丟出去整張表單會換成 Error Boundary 的畫面，客人打的字全沒了（第 17 課）。清空購物車只能放在 await 成功之後，順序是「清空 → onPlaced(訂單編號) 換頁」。

還有一件「不做」的事：下單不做樂觀更新。第 16 課的結論是付款、下單這種失敗不能回復、而且會被伺服器改寫的操作，老實等確認。

💡 實務上：重複下單通常是客服先發現的
這類 bug 很少在測試環境出現，常見的是客服轉來「客人說按一次卻收到兩筆訂單」，而且多半發生在網路不穩的手機上。牽涉金額的流程（結帳、付款、退款、儲值），資深工程師會先確認後端有沒有冪等處理，而不是只在前端停用按鈕；真正擋住重複的是伺服器記住看過的鍵（系統設計課第 9 課、NestJS 課期末專題）。冪等鍵如果有寫進錯誤回報和請求紀錄，查問題時後端就能直接比對是不是同一次結帳。

步驟四：店員區

顧客那一側做完，換到吧台。店員區（練習 4）有兩半：誰進得來，以及「可以取餐」這個寫入。誰進得來用第 18 課的 middleware（在 loader 和 render 之前執行，擋下時頁面一次都不會出現），三層保護各自負責不同的事：

層次做什麼擋得住什麼
路由 middleware沒登入 throw redirect 去登入頁並帶 redirect；顧客、別間門市 throw data(…, { status: 403 })顧客或別間店的店員誤入看板
畫面已經好的訂單不顯示按鈕按了只會失敗的按鈕
伺服器標成可以取餐的 API 再檢查身分、角色、門市改網址、改 JavaScript、直接打 API 的人

前兩層在瀏覽器裡執行，使用者改得到，它們是體驗；安全只靠第三層。門市比較有一個陷阱：params.storeId 是字串、user.storeId 是數字，用 !== 直接比永遠不相等，自己門市也進不去；改成 Number(params.storeId) !== user.storeId，/staff/1.0 又會被當成 1 號店。先確認是整數字串，再轉數字比較。

「可以取餐」是第 16 課的 useMutation：成功後 invalidateQueries 讓看板重抓，並且回傳它的 Promise，重抓完成之前 mutation 都還是 pending，按鈕不會先恢復讓店員再按一次。客人會收到取餐通知，所以也不做樂觀更新。等待中只停用那一顆按鈕：用 mutation.variables === o.id 判斷是哪一筆。

看板上每一列都有一顆畫面上寫著「可以取餐」的按鈕。看得到畫面的人知道是哪一列，讀螢幕軟體逐一唸按鈕時，只會聽到一串一樣的「可以取餐，按鈕」。照第 24 課，用 aria-label 給每顆按鈕完整的名稱「王小明的訂單可以取餐」，名稱裡包含畫面上的字，用語音控制說「可以取餐」也找得到；成功訊息放在一開始就存在的 <p role="status">，只換文字。

步驟五：審查同事的 PR

前面四步是自己寫。實際工作中同樣常見的是看別人寫的：同事送來訂單狀態頁的 PR（練習 5 的起始檔），說「畫面都正常」。資深工程師審查時不是從頭讀到尾挑語法，而是拿驗收條件一條一條對：這條在程式的哪裡做到？什麼情況下會做不到？

const { data: order, isPending, isError, refetch } = useQuery({

const [count, setCount] = useState(0)

if (isPending) return <p>載入訂單中…</p>

const lines = order.lines.sort((a, b) => b.quantity - a.quantity)

先自己列一次再往下看：這段程式有六個問題，各自違反哪一課的觀念？

問題後果出處與修法
queryKey: ['order'] 沒有 id從 1 號訂單換到 2 號，畫面先顯示 1 號的快取；signal 也沒傳第 15 課：queryFn 用到的變數都放進 key，['orders', id]
effect 裡 setCount第一次 commit 是「共 0 件」，多一次 render第 6 課：衍生值在 render 裡算
if (isError) 擺在前面重新整理失敗時，畫面上的訂單整個換成錯誤第 15 課：isError 也可能是背景重抓失敗，先看有沒有 data
order.lines.sort(…)就地改了快取裡的陣列，其他用到這份快取的元件跟著變；資料被凍結時直接丟 TypeError第 20 課：用 toSorted

六個問題裡，eslint-plugin-react-hooks 7.1.1 的 recommended 規則全部打開，只回報一個：effect 裡的 setState（set-state-in-effect，練習環境實測）。就地 sort 不會被回報，第 20 課的表就列過；queryKey、role="status" 的 key、少了錯誤邊界，都不是 lint 管的事。lint 過了代表「沒有它認得的錯」，其他的要靠審查的人對照需求，以及把這些情況寫進測試。

💡 實務上：審查留言寫出「後果」和「出處」
「這裡怪怪的」「建議改一下」很難讓人動手。好的留言長這樣：「queryKey 少了 id：從 1 號訂單點到 2 號時會先顯示 1 號的資料（重現：打開 /orders/1 再改網址）。照我們的 key factory 寫成 orderKeys.detail(id)。」也就是後果、怎麼重現、建議的改法。再標出哪些是一定要改（會出錯、違反需求），哪些是可以之後再說（命名、風格），對方知道先處理什麼。同一類問題第二次出現，就該變成 lint 規則或測試，而不是每次靠人眼抓（系統設計課第 20 課）。

步驟六：替守衛寫檢查

審查找到的問題要變成測試才不會再發生，最後一步回到第 23 課：測試要在錯誤版本上失敗、在換了寫法的正確版本上通過。練習 6 給你店員區的守衛，起始的檢查只有「店員進自己門市看得到看板」，步驟四的錯誤寫法放進來全都會通過。你要補上的情境，正好對應步驟四講過的每一種錯：沒帶 redirect、顧客進得來、別間門市進得來、字串和數字比較讓自己門市也進不去、403 卻導去登入頁、在元件裡用 effect 擋（看板先閃一下）。

判分時你的 checkStaffGuard() 會跑在兩個正確版本上：一個用 middleware、一個用 loader 擋，錯誤訊息的文字也不同。所以檢查只能依賴規格寫的東西：網址、role="alert"、看板的標題，不能依賴「沒有權限」這幾個字。寫得出抓錯的檢查，代表你知道規格的每一條在防什麼。

練習

在 learn/ 執行 node check.mjs react 25，檔案在 react/practice/work/25/。六題互相獨立，可以照任何順序做；每一題先讀檔案開頭的註解（那就是驗收條件），再看測試失敗的訊息。shared/、test-utils.tsx 和標著「已經寫好」的檔案不用改。假後端的每個呼叫都等著，由測試決定何時成功或失敗；它回傳的資料是凍結的，直接改會丟 TypeError。

練習 1：菜單頁。分類只存在網址的 ?category=（沒有、不合法、重複都當成 coffee），點分類只改 category、保留其他 query，並新增一筆歷史紀錄；菜單用 useQuery，queryKey 包含分類、signal 傳給 API；第一次載入顯示「載入菜單中…」，失敗顯示 role="alert" 加「重試」；換分類時舊菜單留著、<section aria-label="菜單"> 是 aria-busy="true"；搜尋關鍵字只放在 state，去掉空白後篩選目前的菜單，沒有結果顯示「找不到符合的商品」。

練習 2：購物車。商品＋大小＋甜度都一樣才是同一列，大杯 +20 元，數量最多 20，changeQty 到 0 移除那一列，全部不可變更新；用 persist 存到 localStorage 的 cart、version 1，在 merge 裡用 persistedCartSchema 驗證，lines 是 null、數量是負的、少了欄位、舊版本、JSON 壞掉都從空車開始而且不丟錯；CartBadge 只訂閱件數，件數沒變不重新 render。

練習 3：結帳的 Action。購物車是空的就回傳「購物車是空的」、不呼叫 API；冪等鍵在第一次真的要呼叫 API 時產生，網路錯誤與 5xx 之後沿用，4xx 與成功之後換新的；送出去的明細只有 productId、size、sugar、quantity；成功才清空購物車並呼叫 onPlaced(訂單編號)；422 放進 fieldErrors、其他 4xx 顯示伺服器的 message、都不回報；其他錯誤顯示「送出失敗，請再試一次」並回報原本的錯誤；失敗都保留原文、不丟出錯誤。結帳頁的測試會連續送出兩次，只能建立一筆訂單。

練習 4：店員區。/staff/:storeId 加上 middleware：沒登入導到 /login?redirect=原本的路徑與 query，顧客和別間門市（storeId 不是整數字串也算）throw 403，擋下時看板一次都不出現、不抓訂單；「可以取餐」用 useMutation，名稱是「{顧客}的訂單可以取餐」，等待時只停用那一顆，成功後讓 ['staff-orders', storeId] 失效並等重抓完，一開始就存在的 role="status" 顯示「已通知{顧客}取餐」；失敗顯示 role="alert"，再按時先消失；不做樂觀更新。

練習 5：審查並修好同事的訂單狀態頁。先對照檔案開頭的驗收條件列出問題，再改：每筆訂單各自的快取、signal 傳給 API；role="status" 一直是同一個元素；「共 N 件」第一次出現就是對的；重新整理失敗時留著舊的訂單並顯示「更新失敗，顯示的是上次的狀態」；明細依數量由多到少而且不改快取的資料；明細壞掉只換成「明細暫時無法顯示」；react-hooks 的 lint 沒有回報。

練習 6：完成 checkStaffGuard()：用 open() 打開各種情境（沒登入、顧客、別間門市、自己門市），在守衛不符合規格時用 expect 丟錯。它要讓 middleware 與 loader 兩個正確版本通過，並抓到 6 個錯誤版本。錯誤訊息的文字不固定，用角色找；看板「一閃而過」用 everShown 檢查。

練習 7：菜單已經用 useQuery 抓，queryKey 是 ['menu', category]。換分類時整個菜單閃成「載入菜單中…」，要讓舊菜單留著，該用哪個？

✓ 資料由 TanStack Query 管，就用它的選項：新 key 還沒有資料時先給上一個 key 的資料。b、c 是第 21 課的工具，它們讓 React 在背景 render 新畫面、遇到暫停時留著舊畫面；但這個 useQuery 沒有用 Suspense，新 key 沒快取時同一次 render 就回傳 isPending，沒有東西會暫停，畫面照樣閃。d 只是晚一點閃，還讓每次點擊都慢 300ms。

練習 8：結帳的冪等鍵什麼時候換新的？

✓ 冪等鍵防的是「伺服器其實建立了，前端卻以為失敗」：結果不明的時候（斷線、5xx）重送一定要沿用。4xx 是伺服器明確拒絕、沒有建立，客人改了內容再送是新的嘗試；成功之後下一次是另一筆訂單。a、d 讓結果不明之後的重送變成新訂單，等於沒有冪等鍵。b 讓成功之後的下一筆訂單拿到上一筆的結果，也讓改過內容的重送被伺服器當成可疑的請求。

練習 9：同事的訂單狀態頁有六個問題，eslint-plugin-react-hooks 7.1.1 會回報哪些？

✓ 練習環境實測只回報 set-state-in-effect。就地 sort 違反了第 20 課的「不可變」，但第 20 課的表就列過它不會被回報；其他三個是 TanStack Query、無障礙、錯誤邊界的問題，不在 lint 的範圍。a 是常見的誤解：沒有回報不代表遵守規則。c 忽略了 7.x 的 recommended 包含 Compiler 規則，set-state-in-effect 就是其中之一。

驗收：自我檢查清單

測試全過之後，用這張清單再看一次自己的程式。測試只能檢查寫得出來的條件，下面這些要靠你的判斷：

  • 狀態：每塊狀態放在規劃時決定的地方；網址是正本的就不另存 state；衍生值在 render 裡算；store 只存客戶端自己擁有的資料。
  • 伺服器狀態：queryKey 包含 queryFn 用到的每個變數，signal 傳下去；寫入之後讓對的 key 失效；有舊資料時背景失敗不換掉整頁。
  • 錯誤處理：每個抓資料的地方都有載入中、空狀態、錯誤加重試；預期中的錯誤顯示說明，預期外的回報；render 錯誤有範圍剛好的 Error Boundary（第 24 課）。
  • 可近用性：每個欄位有 label；重複的按鈕有分得出來的名稱；role="status" 一開始就存在；錯誤用 aria-describedby 連到欄位（第 17 課）。
  • 效能：先量測再優化；selector 只選需要的值；沒有量到慢就不加 memo、useDeferredValue（第 19 課）。
  • 安全：守衛和隱藏按鈕只為體驗，API 一定再檢查；persist 的資料讀回來先驗證，token、手機、地址不放進 localStorage（第 14 課）。

常見錯誤

  • 所有狀態都丟進同一個 store：伺服器資料沒有失效機制、表單的暫時狀態離開頁面還留著。先分類：網址、元件、客戶端全域、伺服器狀態，各放各的地方。
  • 分類同時存在網址和 state：兩份會不一致，上一頁、分享連結都壞掉。網址是正本，每次 render 從網址算。
  • 用錯層的工具解「畫面會閃」：資料在 TanStack Query 裡卻包 Transition、慢在網路卻加 useDeferredValue。先問資料由誰管、慢在哪裡。
  • persist 讀回來直接用：壞資料讓整頁壞掉。給 version，在 merge 裡驗證，不合法就用初始值。
  • 以為 useActionState 會丟掉第二次送出：它會排隊依序執行。讓第二次執行了也沒事：購物車空了就停，加上冪等鍵。
  • 每次送出都換冪等鍵，或失敗後全部沿用：結果不明時要沿用，伺服器明確拒絕或成功之後換新的。
  • 購物車在 finally 裡清空：失敗時客人要重新點一次。只在成功之後清空。
  • params 的字串直接和數字比：'1' !== 1，自己門市也進不去；Number() 又放過 1.0。先確認是整數字串再比。
  • lint 過了就當成沒問題：react-hooks 的規則只抓得到一部分。審查時對照驗收條件，把找到的問題寫成測試。

小結

  • 先寫驗收條件，它同時說明「做對的樣子」和「最常見的做錯方式」，而且可以直接變成測試。
  • 規劃時先決定每塊狀態的位置：分類在網址、購物車在 Zustand 加驗證過的 persist、菜單與訂單在 TanStack Query、表單在 Action 的 state。
  • 同一個症狀有好幾個工具時，先問資料由誰管、慢在哪裡：TanStack Query 的資料用 keepPreviousData，use() 加 Suspense 才用 Transition，render 慢才用 useDeferredValue。
  • 防重複下單：useActionState 會排隊，第二次要「執行了也沒事」；冪等鍵在結果不明時沿用、明確拒絕或成功後換新；失敗不清空購物車；預期中的錯誤顯示、預期外的回報。
  • 守衛和隱藏按鈕是體驗，伺服器才是安全；寫入等伺服器確認，回傳失效的 Promise；重複的按鈕給完整的名稱，狀態區一直存在。
  • 審查別人的程式時拿驗收條件一條一條對，lint 只抓得到一部分；找到的問題寫成測試，並用錯誤版本確認測試抓得到。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 10：店員看板的測試如下，api 是測試傳入的假 API，陳美華是看板上的第二筆訂單。這個測試最大的漏洞是什麼？

const user = userEvent.setup()
render(<StaffBoard api={api} storeId={1} />)
await user.click(await screen.findByRole('button', { name: '陳美華的訂單可以取餐' }))
expect(api.markReady).toHaveBeenCalled()

✓ toHaveBeenCalled() 只證明有呼叫，參數錯了一樣綠。改成 toHaveBeenCalledWith(陳美華的單號) 加 toHaveBeenCalledTimes(1)，而且故意挑不是第一列的那筆。a 錯在用角色加名稱找，正好同時檢查讀螢幕軟體分得出每顆按鈕；test id 抓不到按鈕沒有名稱。（第 23 課）

練習 11：同事的結帳 Action 這樣接住所有失敗。審查時最該留哪一則留言？

} catch (e) {
  return { ...state, values, formError: (e as Error).message }
}

✓ 先分類：4xx 是預期中的，顯示伺服器的說明、不回報；5xx、網路、程式錯誤顯示通用訊息，並回報原本的錯誤。顯示和回報要一起做，只顯示的話工程師什麼都不知道。b 錯在 Action 丟出錯誤，整張表單換成 Error Boundary 的畫面，客人打的字全沒了；回傳成 state 才對。（第 24 課）

練習 12：看板每一列都有一顆畫面上寫著「可以取餐」的按鈕，讀螢幕軟體逐一唸按鈕時只聽到一串一樣的「可以取餐，按鈕」。該怎麼改？

✓ 重複的按鈕要有分得出來的完整名稱，aria-label 取代畫面上的字成為按鈕的名稱。名稱裡保留「可以取餐」，用語音控制說畫面上的字才找得到它。b 錯在名稱不含畫面上的字，看得到畫面、用語音操作的店員說「可以取餐」叫不到這顆按鈕。（第 24 課）

練習 13：菜單用 useQuery({ queryKey: ['menu', category], … })，category 從網址讀。點到還沒看過的分類時，整份菜單先閃成「載入中…」，驗收條件要求不能閃。該用哪一個？

✓ 先問資料由誰管、慢在哪：菜單由 TanStack Query 管、慢在網路，就用它的選項，再拿 isPlaceholderData 設 aria-busy。a 是最常見的用錯層：這個 useQuery 沒有用 Suspense，新 key 沒快取時同一次 render 就回傳 isPending，沒有東西讓 Transition 等。b 錯在慢的不是 render，延後的那次 render 一樣拿到 isPending。（第 15、21、25 課）

練習 14：期末專題裡，下面哪一件事適合寫成 useEffect？

✓ effect 是讓元件跟 React 管不到的東西同步，原因是「畫面顯示成這樣了」；焦點在瀏覽器的 DOM 上，新頁面顯示了就該移過去。c 是最常見的錯：網址已經是正本，另存一份會不同步，還多一次 render，每次 render 從網址算就好。a 同理在 render 裡算；d 是使用者的操作，放在事件處理函式，放進 effect 會漏送或多送。（第 6 課）

練習 15：結帳 Action 呼叫訂單 API 時都帶冪等鍵。客人按下送出後網路斷了，畫面顯示「連線失敗」，客人再按一次。這一次的鍵該怎麼處理？

✓ 斷線、5xx 時不知道伺服器有沒有建立訂單，沿用同一個鍵，伺服器看到重複的鍵就不會建第二筆；伺服器明確拒絕（4xx）或成功之後才換新的鍵。b 是最多人選的：以為失敗就是沒建立，結果客人收到兩筆訂單。c 錯在購物車只能在成功之後清空，訂單真的沒建立時客人要重新點一次。（第 25 課）

練習 16：店員按「可以取餐」，API 成功了，看板上那一筆卻還是「製作中」，切到別的分頁再回來才變。程式如下，原因是？

useQuery({ queryKey: ['staff-orders', storeId], queryFn: … })

useMutation({
  mutationFn: (id: number) => api.markReady(id),
  onSuccess: () => { queryClient.invalidateQueries({ queryKey: ['orders'] }) },
})

✓ invalidateQueries 用 key 的前綴選出要失效的快取，選錯 key 等於什麼都沒做；回到分頁會變，是視窗聚焦時過期的資料背景重抓。改成 ['staff-orders', storeId]，並 return 它的 Promise，讓按鈕等到看板重抓完才恢復。a 錯在沒有 return 照樣會失效、重抓，差別只是 mutation 不等它完成。（第 15、16 課）

練習 17：頁首的徽章已經包了 memo。客人移除拿鐵、再加一杯美式，件數一樣是 2，Profiler 卻顯示 CartBadge 又 render 了。為什麼？

export const CartBadge = memo(function CartBadge() {
  const lines = useCartStore((s) => s.lines)

✓ Zustand 用 Object.is 比較 selector 的結果，不可變更新之後 lines 是新陣列，徽章就 render。改成 useCartStore(selectCount) 選一個數字，件數沒變就跳過。b 錯在這次列的內容真的變了（拿鐵換成美式），淺比較也不相同；而且先用 Profiler 量到它真的慢，才值得處理。（第 14、19 課）
