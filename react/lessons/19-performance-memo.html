階段 5：效能與渲染 · 第 19 課

效能：先量測，再用 memo、useMemo、useCallback

咖啡店的點餐機上線一週，店員回報三件事：在「備註」欄打字會頓一下；畫面角落的時鐘每秒跳一次，舊平板上整個菜單跟著閃；店長的銷售排行頁，在「店長備註」打字也卡。同事的反應是把每個元件都包一層 memo，結果收據預覽明明包了 memo，店員打桌號時它照樣每個字都重新 render，程式還多了一堆依賴陣列要顧。

問題出在順序：還不知道慢在哪，就先選了工具。這課先教你量：用 React DevTools 的 Profiler 和 <Profiler> 找出哪個元件 render、為什麼 render、花了多久，再依原因決定修法：搬動 state 或用 children、memo 加 useCallback、useMemo。版本以 React 19.3.1 為準。

這課的路線：
  1. 先量測：用 Profiler 看出誰在 render、為什麼，量完怎麼選工具。
  2. 不用 memo 的修法：state 往下放、慢的內容用 children 傳進去。
  3. memo 加 useCallback：讓清單的每一列在 props 沒變時跳過。
  4. useMemo：慢的計算只在依賴改變時重算；讓傳給 memo 元件的物件保持同一個。
  5. 什麼時候不要加，以及下一課的 React Compiler 會改變什麼。
這課會用到：
  • 第 1 課的 render 與 commit：父元件 render，子元件預設全部跟著 render；render 只是呼叫函式，commit 才改 DOM。
  • 第 3 課的 Object.is 與 updater function：物件比的是參考，內容一樣的兩個物件也算不同；setX(prev => …) 不用讀外面的 state。
  • 第 9 課的 useCallback 與第 11 課的 useMemo：依賴沒變，就回傳上一次的函式或值。
  • 第 14 課的「往下放」：只有一個元件用的 state，搬進那個元件，改動時重新 render 的範圍就變小。
量時間要在你自己的瀏覽器裝 React DevTools（Chrome、Firefox、Edge 的擴充功能）。練習的測試不量毫秒（每台電腦不同），改成數「元件被呼叫幾次」「計算函式被呼叫幾次」。

先量測：誰在 render、為什麼、花多久

「感覺卡」不夠用來決定修法。要先回答三個問題：這次操作讓哪些元件 render、它們為什麼 render、各花多久。React 有兩個量的工具。

React DevTools 的 Profiler 分頁

裝好擴充功能後，瀏覽器開發者工具會多出 Components 和 Profiler 兩個分頁。在 Profiler 按錄製、做一次卡的操作（例如在備註欄打兩個字）、按停止。依 React 19.3.1 原始碼裡的 DevTools 說明，錄製期間它記下每一次 commit 的時間與長度、這次 commit render 了哪些元件；在設定裡打開記錄變化的選項（預設關閉）後，還會記下哪些 props、state 變了，也就是點選一個元件時看到的「為什麼 render」。

在點餐機錄一次，會看到：

  1. 打備註：每個字一次 commit，MenuBoard 和底下每一個 ProductRow 都 render。ProductRow 的原因是「父元件 render」，它自己的 props 沒變。
  2. 時鐘跳一秒：KioskPage 的 state 變了，底下很慢的 SlowMenu 跟著 render，菜單一個字都沒變。
  3. 收據預覽：已經包了 memo，打桌號時還是 render，原因寫著 props 裡的 customer、lines 變了。

<Profiler>：在程式裡量

同樣的數字也能在程式裡拿到。用 <Profiler> 包住要量的一段，React 每次 commit 這段時呼叫 onRender：

import { Profiler } from 'react'

<Profiler id="menu" onRender={(id, phase, actualDuration, baseDuration) => {
  console.log(id, phase, actualDuration.toFixed(2), baseDuration.toFixed(2))
}}>
  <MenuBoard products={products} />
</Profiler>

看兩個時間（react.dev 的 Profiler 文件）：

  • actualDuration：這次更新實際花在 render 這段的毫秒數。
  • baseDuration：假設這段全部重新 render、完全沒有跳過，估計要花多久（最差情況）。
  • 兩者接近，代表這段每次都整片重算；加了 memo 之後，actualDuration 應該明顯比 baseDuration 小。

某段計算慢不慢，react.dev 建議直接用 console.time 包住它，做一次操作，累計時間到 1ms 以上才值得快取。

這些數字在開發模式下不準：StrictMode 會把元件呼叫兩次，開發版本本身也比較慢。開發模式適合找「誰、為什麼」，毫秒數要另外確認（react.dev 的 useMemo、Profiler、React Performance tracks 文件）：

  • 正式版本（production build），在跟使用者一樣的裝置上量；手邊的電腦太快時，用 Chrome 的 CPU 降速（CPU throttling）。
  • <Profiler> 的計時在正式版本預設關閉。要在正式環境量，改用 React 的 profiling 版本：把 react-dom/client 換成 react-dom/profiling，通常用打包工具的 alias 設定。
  • 開發版本預設會在 Chrome Performance 分頁的錄製結果裡加上 React 的軌道（React Performance tracks），可以和網路、版面計算排在同一條時間軸上看。

不用 memo 的修法：state 往下放、內容用 children 傳進去

上一節量到的第 2 個問題是位置問題：SlowMenu 跟時鐘、深色模式無關，只因為那兩個 state 放在它的父元件。react.dev 的 memo 文件也把這類結構調整列在 memo 之前：很多記憶化只要 state 放對、外框元件收 children 就不需要。

export function KioskPage({ products }: { products: readonly Product[] }) {
  const [now, setNow] = useState(() => new Date())   // 每秒變一次
  const [dark, setDark] = useState(false)
  useEffect(() => { … setInterval(() => setNow(new Date()), 1000) … }, [])
  return (
    <main>
      <p role="timer">現在 {formatTime(now)}</p>
      <button aria-pressed={dark} onClick={() => setDark(d => !d)}>深色模式</button>
      <section aria-label="菜單區" className={dark ? 'dark' : 'light'}>
        <SlowMenu products={products} />     {/* 每秒、每次切換都 render */}
      </section>
    </main>
  )
}

兩個 state 要用兩種方法處理。

時鐘：往下放。時間只有時鐘自己顯示，把 state 和計時器一起搬進 Clock。每秒只有 Clock render，effect 的清理照第 5 課寫，卸載時 clearInterval。

深色模式：內容往上提。開關改的是包住菜單的 <section>，菜單在它裡面，沒辦法把 state 往下放到菜單旁邊。做法是讓外框元件收 children：

function ThemePanel({ children }: { children: ReactNode }) {
  const [dark, setDark] = useState(false)
  return (
    <>
      <button type="button" aria-pressed={dark} onClick={() => setDark(d => !d)}>深色模式</button>
      <section aria-label="菜單區" className={dark ? 'dark' : 'light'}>{children}</section>
    </>
  )
}

export function KioskPage({ products }: { products: readonly Product[] }) {
  return (
    <main>
      <Clock />
      <ThemePanel>
        <SlowMenu products={products} />    {/* KioskPage 建立的 element */}
      </ThemePanel>
    </main>
  )
}

看 <SlowMenu /> 是誰建立的。它寫在 KioskPage 裡，KioskPage 現在沒有 state，切換深色模式時不會 render，所以 ThemePanel 收到的 children 還是同一個 element 物件，React 就跳過 SlowMenu。這跟第 11 課「Provider 用 children 收子樹，不讀 context 的元件會被跳過」是同一件事。

兩個方法要一起用，只做一半都擋不住：

  • 只搬時鐘：dark 還在 KioskPage，切換時 KioskPage render，SlowMenu 跟著 render。
  • 只抽 ThemePanel：時鐘還在 KioskPage，每秒 render 一次，每次都建立一個新的 <SlowMenu /> element 傳進去，children 變了。
  • ThemePanel 自己寫 <SlowMenu products={products} />：state 搬過去了，但 element 是 ThemePanel 建立的，它 render 時就是新的。

不要為了「同一個 element」把 <SlowMenu /> 存進 useState 或 ref：它永遠是第一次的 products，換了菜單畫面不會更新。這題用 memo(SlowMenu) 也擋得住，但 state 仍然放錯，之後每加一個子元件都要記得包，跟第 14 課的提醒一樣。

💡 實務上：每秒更新的東西，一律包成自己的小元件
點餐機的時鐘、叫號螢幕的倒數、後台「3 分鐘前更新」的相對時間，都是高頻 state 放錯位置的常見來源。code review 看到頁面最上層有 setInterval、捲動位置、滑鼠座標、輸入框的草稿，先問「誰真的要讀它」。這種修法沒有依賴陣列要維護，元件拆開後也比較好測，通常比 memo 便宜。

memo 加 useCallback：讓清單的每一列跳過

結構調整解決不了所有情況。量到的第 1 個問題，備註和購物車都是 MenuBoard 真的要用的 state，沒有地方可以搬，但每打一個字，每個 ProductRow 都跟著 render。想像菜單有 200 個商品，每列有圖片和選項，這就是 memo 的場景。

memo(元件) 回傳一個新的元件：父元件 render 時，React 用 Object.is 逐一比較新舊 props，全部相同就跳過它（react.dev 的 memo 文件）。在模組層級包一次：

import { memo, useCallback, useState } from 'react'

const Row = memo(ProductRow)        // 寫在元件外面，只包一次

export function MenuBoard({ products }: { products: readonly Product[] }) {
  const [note, setNote] = useState('')
  const [lines, setLines] = useState<Line[]>([])

  const add = useCallback((productId: number) => {
    setLines(prev =>                 // updater function：不讀外面的 lines
      prev.some(l => l.productId === productId)
        ? prev.map(l => (l.productId === productId ? { ...l, quantity: l.quantity + 1 } : l))
        : [...prev, { productId, quantity: 1 }],
    )
  }, [])                              // 沒有用到任何響應值，依賴是空陣列

  …
  {products.map(p => <Row key={p.id} product={p} onAdd={add} />)}
}

ProductRow 收兩個 props：product 和 onAdd。product 是 products 陣列裡的同一個物件，打字時不會變；onAdd 如果寫成普通的 function add，每次 render 都是新的函式，Object.is 判定不同，memo 永遠不會跳過。文件的說法是：props 每次都不同時，memo 完全沒用，所以 memo 常要搭配 useCallback。反過來，只包 useCallback、不包 memo 也沒用：ProductRow 沒有 memo 時根本不比 props，父元件 render 它就 render。

依賴陣列是最容易錯的地方：

  • 依賴寫 [lines]：函式裡讀了 lines 就得列它，lint 也會這樣要求。但每加一個商品 lines 就換新，onAdd 跟著換新，每一列又全部 render。改用 updater function，函式不再讀 lines，依賴就是空的。
  • 讀了 lines 卻寫 []：onAdd 永遠是第一次 render 的那個函式，裡面的 lines 永遠是空陣列。加入拿鐵、再加可頌，拿鐵就不見了。這種「過期的閉包」lint 的 exhaustive-deps 會抓到，不要關掉它。

還有兩種看起來有包 memo 的寫法：

  • 在元件裡寫 const Row = memo(ProductRow)：每次 render 都得到一個新的元件型別。React 看到同一個位置換了型別，會把舊的整列卸載、重新掛載。本機實測（React 19.3.1、happy-dom）點一次按鈕之後，列表的 <li> 已經不是原本的 DOM 節點，比沒包還慢，列裡的 state 也會重來。
  • 第二個參數寫 memo(ProductRow, () => true)：自訂比較函式回傳 true 代表「一樣，跳過」。永遠回傳 true，拿鐵改價時那一列還是舊價格。文件要求自訂比較要比較每一個 prop（包括函式），也提醒深層比較可能比重新 render 更慢；能讓 props 本身穩定，就不要寫比較函式。

修好之後，拿鐵改價時只有拿鐵那一列 render：新的 products 陣列裡，其他商品還是原本的物件。這要靠第 3 課的「只複製改到的路徑」；整份 structuredClone 會讓每個商品都變成新物件，memo 全部失效。

同一個元件裡的 count、subtotal 是每次 render 都算的 reduce，不需要 useMemo：購物車只有幾行，算一次遠低於 1ms，包起來只多了一個依賴陣列要維護。

useMemo：慢的計算只在依賴改變時重算

memo 跳過的是整個元件；但有時候慢的不是元件，而是 render 裡的一行計算。店長的排行頁就是這樣：

export function SalesReport({ orders, products }: Props) {
  const [category, setCategory] = useState<Filter>('all')
  const [showRevenue, setShowRevenue] = useState(false)
  const [note, setNote] = useState('')

  const rows = rankProducts(orders, products, category)   // 掃過整個月的訂單
  …
}

用 console.time 包住 rankProducts，在店長備註打字，會看到每個字都印一次計時：備註跟排行無關，計算卻每次都跑。第 6 課說過，Vue 的 computed 會快取，React 的寫法預設不會；要快取就用 useMemo：

const rows = useMemo(
  () => rankProducts(orders, products, category),
  [orders, products, category],          // 計算真的用到的值
)

React 會記住上一次的依賴和結果，下次 render 時用 Object.is 逐一比較依賴，都沒變就直接回傳上一次的結果（react.dev 的 useMemo 文件）。所以：

  • 打備註、切換「顯示營收」：依賴沒變，不重算。showRevenue 只影響怎麼顯示，不要放進依賴，放了就每次切換都重算。
  • 換分類：category 變了，在同一次 render 裡重算，畫面直接是新的排行。
  • 只記最後一次：從咖啡切到茶再切回咖啡，咖啡會重算一次。
  • 第一次 render 一樣要算：文件寫明 useMemo 不會讓第一次 render 變快，只幫你跳過之後不必要的計算。

幾種常見的錯，大多是把「快取」想成要自己保存什麼：

  • 存成 state、用 effect 更新：useEffect(() => setRows(rankProducts(…)), [category])。換分類時先 commit 一次舊排行，effect 再 set 一次，多一次 render，畫面短暫是錯的（第 6 課）。
  • 依賴少了 category：換分類還是舊排行。lint 會抓到。
  • 依賴是每次 render 新建的物件：const filter = { category } 再把 filter 放進依賴，每次都不同，每次都重算。文件的建議是把物件的建立移進計算函式，依賴改放 category 這種原始值。
  • 自己在模組層級做快取：let cache 寫在元件外面，同一頁兩個 SalesReport 共用一份，orders 換了也不知道。useMemo 的快取跟著每個元件實例，各算各的。
  • 用 memo 包整個 SalesReport：memo 只擋「父元件 render、props 沒變」；備註是 SalesReport 自己的 state，自己的 state 變了照樣 render、照樣重算（文件：memo 元件在自己的 state 或讀的 context 改變時仍會 render）。

開發模式的 StrictMode 會把計算函式呼叫兩次來檢查它是不是純函式，計時看到兩次是正常的。文件也寫明 useMemo 只是效能優化：拿掉它，程式要照樣正確。

讓傳給 memo 元件的物件保持同一個

useMemo 還有第二個用途。量到的第 3 個問題：ReceiptPreview 已經 memo 了，打桌號時「為什麼 render」寫著 customer、lines 變了：

<ReceiptPreview
  customer={{ name: customerName, vip }}                 // 每次 render 都是新物件
  lines={cart.flatMap(l => { … })}                      // 每次 render 都是新陣列
/>

這兩個值算起來一點都不慢，問題是參考：Object.is({}, {}) 是 false。這時用 useMemo 不是為了省計算，而是讓值在依賴沒變時保持同一個參考：

const customer = useMemo(() => ({ name: customerName, vip }), [customerName, vip])
const lines = useMemo(
  () => cart.flatMap(l => {
    const p = products.find(x => x.id === l.productId)
    return p ? [{ name: p.name, price: p.price, quantity: l.quantity }] : []
  }),
  [cart, products],
)
<ReceiptPreview customer={customer} lines={lines} />

文件說的「一個永遠是新的值，就足以讓整個元件的記憶化失效」在這裡最明顯：

  • 只穩定其中一個：另一個還是每次新的，memo 照樣判定 props 變了。
  • 依賴寫 []：改了名稱、勾了 VIP，收據還是第一次的值。
  • 依賴多放 tableNo：打桌號又換新物件，回到原點。
  • 依賴只放 cart.length，再用 eslint-disable 壓掉警告：同一杯加一杯，長度沒變，收據不更新。lint 抓到的就是這種錯，壓掉它等於把 bug 留下。
  • 用 ref 保存同一個物件、每次 render 改它的欄位：參考一直相同，memo 以為沒變，收據停在舊的名稱。這也違反第 7 課「render 過程中不讀寫 ref.current」和第 3 課的不可變更新。

如果收據元件是你能改的，文件建議更簡單的做法：props 只收需要的原始值（name、vip 分開傳），字串和布林用 Object.is 比的是值，不用 useMemo。練習 4 規定不能改 ReceiptPreview 的 props，所以用 useMemo。

💡 實務上：memo 是一條鏈，斷一環就全部白做
一個 memo 元件要真的跳過，它的每個物件、陣列、函式 prop 都得從上面一路穩定下來；中間任何人改成 inline 的 {{ … }} 或箭頭函式，memo 就默默失效，測試也不會失敗。所以 memo 只放在量過、真的值得的地方（長清單的列、很重的圖表），而且在旁邊寫註解說明它依賴哪些 props 穩定；重要的地方像練習一樣寫測試數 render 次數，或在 PR 附上 Profiler 前後的截圖。

什麼時候不要加，以及下一課會改變什麼

前面四個情況都是先量到原因才動手。反過來，沒量就加，常見的結果是多了程式、沒有變快。react.dev 的 memo 與 useMemo 文件列出值得記憶化的條件：

  • memo：元件常常用完全相同的 props 重新 render，而且它的 render 很重。重新 render 沒有感覺得到的延遲，就不需要。
  • useMemo：計算明顯很慢且依賴很少變；或值要傳給 memo 元件；或值要當另一個 hook 的依賴（例如 effect 的依賴）。
  • 像換頁、換整個區塊這種「粗」的操作，記憶化通常沒必要；像繪圖編輯器拖動圖形這種「細」的操作，記憶化才常常有用。

加了也沒效果、甚至更糟的情況，前面都遇過，集中看一次：

情況結果
memo 元件收到 inline 的物件、陣列、函式每次都不同，memo 白做，還多了比較 props 的成本
memo 元件自己的 state 變了，或它讀的 context、store 變了照樣 render，memo 只管父元件傳來的 props（第 11、14 課）
依賴陣列少寫、寫空、用 eslint-disable 壓掉畫面停在舊資料：比慢更糟的 bug
自訂比較函式漏比某個 prop，或做深層比較畫面停在舊資料，或比較本身比 render 還慢
在元件裡呼叫 memo()每次都是新元件，整段卸載再掛載
拿掉 memo 程式就壞了文件：這是 bug，先修 bug，memo 只能當效能優化

文件也提醒，React 應用的效能問題很多來自 effect 裡 set state 引起的連鎖更新，這種情況要做的是刪掉 effect（第 6 課），不是加 memo。

手動記憶化的成本主要在維護：每個依賴陣列都要跟著程式改，一個沒穩定的 prop 就讓整條鏈失效。React Compiler 就是為這件事做的：它在建置時分析元件，自動加上記憶化。官方文件建議新程式靠 Compiler 記憶化，useMemo、useCallback 留給需要精確控制的地方。有了它，這課很多手動的 memo 不必寫；但「先量測」和「state 放對位置」不會因此改變。Compiler 怎麼運作、需要你遵守哪些規則，是下一課的內容。

💡 實務上：團隊的預設是「不加」，例外要附數字
沒有 Compiler 的專案，常見的兩種極端是「全部包 memo」和「完全不管」。比較穩的約定是：預設不加；清單列、圖表、編輯器這類量過很重的元件才加，PR 附 Profiler 前後對照；給別人用的自訂 hook 回傳的函式照第 9 課包 useCallback，因為你不知道呼叫端會不會放進依賴陣列。lint 的 exhaustive-deps 設成 error，不允許用 disable 壓掉。

練習

在 learn/ 執行 node check.mjs react 19，檔案在 react/practice/work/19/。測試把 ProductRow、SlowMenu、ReceiptPreview、rankProducts 換成會記數的版本（畫面和結果不變），檢查它們被呼叫幾次；練習 3 另外用 <Profiler> 數 commit 次數。練習 1、3、4 會用 eslint-plugin-react-hooks 7.1.1 的 exhaustive-deps 檢查依賴陣列。四題互不相依，標了「不用改」的檔案不要改。

練習 1：MenuBoard 在備註欄打字時，每個 ProductRow 都重新 render。在 MenuBoard.tsx 用 memo 包住 ProductRow（在模組層級包一次，不要改 ProductRow.tsx、不要用 memo 的第二個參數），用 useCallback 讓 onAdd 每次 render 都是同一個函式。完成時：打備註、按任何一列的「加入」、外層 render 但 products 是同一個陣列，ProductRow 都一次不 render；購物車件數與小計正確（同一個商品再按一次是數量加一，加第二個商品時第一個不能不見）；products 換成新陣列、只有拿鐵是新物件（改價）時，只有拿鐵那一列 render，畫面和小計用新價格。依賴陣列要通過 exhaustive-deps。

練習 2：KioskPage 的時鐘每走一秒、深色模式每切換一次，很慢的 SlowMenu 都跟著 render。不用 memo、useMemo、useCallback、useRef，也不直接改 DOM，只靠元件結構修好：時鐘的 state 和計時器搬進自己的元件（<p role="timer">「現在 10:00:05」，用 formatTime），卸載後不留計時器；深色模式的按鈕（aria-pressed）和 <section aria-label="菜單區">（class 是 dark 或 light）抽成收 children 的元件，<SlowMenu /> 寫在 KioskPage、當 children 傳進去。完成時時鐘走 3 秒、切換兩次，SlowMenu 都沒有 render；products 換了，菜單顯示新的內容。

練習 3：SalesReport 每次 render 都呼叫很慢的 rankProducts。用 useMemo 包住它（不要改 report.ts，也不要自己另寫一份排行）：在店長備註打字、切換「顯示營收」時不呼叫；按分類按鈕時剛好呼叫一次，而且這次更新只 commit 一次（不能存成 state 再用 effect 更新）；外層 render、orders 和 products 都是同一個陣列時不呼叫，任一個換成新陣列時重算。同一頁放兩個 SalesReport 要各算各的。畫面維持原樣：排行每項「品名 N 杯」，勾了顯示營收加「 $營收」，沒有資料顯示「沒有銷售紀錄」。依賴陣列要通過 exhaustive-deps。

練習 4：ReceiptPreview 已經用 memo 包好（不要改它），但在「桌號」打字時每個字都重新 render。讓傳給它的 customer（{ name, vip }）和 lines（{ name, price, quantity }[]）在依賴沒變時保持同一個參考，props 的型別不變：打桌號、外層 render 但 products 沒變時，收據不 render；改顧客名稱每個字、勾 VIP、按「加一杯品名」（同一個商品是數量加一）、products 換了（改價）時，收據各 render 一次並顯示最新內容。不能直接改舊物件來保持參考。依賴陣列要通過 exhaustive-deps，不能用 eslint-disable。

練習 5：Profiler 顯示 memo 包過的 ReceiptPreview 在打桌號時仍然 render，原因是 props 的 customer、lines 變了；兩個都是在 render 裡直接寫的物件和陣列。最合適的修法是？

✓ b：問題是每次 render 都建立新的物件、陣列，Object.is 判定不同。useMemo 讓它們在依賴沒變時保持同一個參考。a 能擋住，但文件提醒深層比較可能比 render 還慢，之後資料結構一改就更慢，漏比還會停在舊資料；c 跟收據的 props 無關；d 只穩定一半，lines 每次還是新陣列，memo 照樣失效。

練習 6：排行頁在店長備註打字時，每個字都會呼叫很慢的 rankProducts。同事把整個 SalesReport 包上 memo。打字還會重算嗎？

✓ c：memo 只擋「父元件 render、props 沒變」這一種情況，元件自己的 state 或讀的 context 變了仍然 render。要跳過的是 render 裡的那行計算，用 useMemo(() => rankProducts(…), [orders, products, category])。b 把 memo 和 useMemo 混在一起了，memo 不會快取元件內部的任何值。

練習 7：菜單外面包了 <Profiler onRender>。替 ProductRow 加上 memo 和 useCallback 之前，在備註打字時 actualDuration 和 baseDuration 差不多；加了之後，actualDuration 變得比 baseDuration 小很多。這代表什麼？

✓ a：actualDuration 是這次更新實際花在 render 的時間，baseDuration 是估計整段不做任何跳過要花多久。兩者接近代表每次都整片重算；actual 明顯變小，代表很多元件被跳過了。兩個數字都在同一個版本裡量，c 錯；開發版本的數字要再用正式版本確認。

常見錯誤

  • 沒量就加 memo：不知道原因，常常加在不慢的地方，或加了也擋不住。先用 Profiler 看誰 render、為什麼。
  • 用開發模式的毫秒數下結論：StrictMode 會呼叫兩次，開發版本比較慢。用正式版本、CPU 降速或使用者的裝置確認。
  • state 放錯位置，用 memo 補：每秒更新的時鐘、深色模式放在頁面最上層。state 往下放；包住慢內容的外框收 children。
  • 只搬一個 state，或外框元件自己建立慢的子元件：element 還是每次新建，照樣 render。慢的 element 要由沒有這些 state 的元件建立。
  • 把 element 存進 state 或 ref：props 換了畫面不更新。
  • 計時器的 effect 沒有清理：卸載後還在跑。回傳 () => clearInterval(id)。
  • 只包 memo，函式 prop 每次新建：memo 永遠判定變了。函式用 useCallback。
  • 只包 useCallback，子元件沒有 memo：子元件不比 props，照樣 render。
  • useCallback 依賴放會常變的 state：依賴一變函式就換新。用 updater function 讓函式不讀那個 state。
  • 讀了 state 卻把依賴寫成 []：函式永遠讀到第一次的值，加第二個商品時第一個不見。照 exhaustive-deps 列完整。
  • 在元件裡呼叫 memo()：每次 render 是新的元件型別，整段卸載再掛載。在模組層級包一次。
  • memo 的比較函式永遠回傳 true 或漏比 prop：資料改了畫面不變。讓 props 本身穩定，不寫比較函式。
  • 算出來的值存成 state、用 effect 更新：多 commit 一次，畫面先顯示舊值。在 render 裡用 useMemo。
  • useMemo 依賴多放只影響顯示的值、或少放計算用到的值：多放就多算，少放就是舊結果。只放計算真的用到的值。
  • 依賴放每次 render 新建的物件：每次都重算。物件移進計算函式，依賴放原始值。
  • 在模組層級自己做快取：所有實例共用一份，資料換了也不知道。用 useMemo，快取跟著元件實例。
  • 用 memo 包元件來省內部的計算：自己的 state 變了照樣 render、照樣算。用 useMemo。
  • 只穩定 memo 元件的一部分 props：一個每次都新的 prop 就讓 memo 失效。每個物件、陣列、函式 prop 都要穩定。
  • 依賴放 .length 再用 eslint-disable 壓掉：內容變了長度沒變，畫面不更新。依賴放整個陣列。
  • 用 ref 保存同一個物件、直接改欄位：參考沒變，memo 以為沒變，畫面停在舊的。每次產生新物件，用 useMemo 控制什麼時候產生。

小結

  • 先量測再修：React DevTools 的 Profiler 看每次 commit render 了哪些元件、為什麼、花多久；<Profiler onRender> 在程式裡拿 actualDuration、baseDuration；計算用 console.time，1ms 以上才值得快取。結論用正式版本或 profiling 版本確認。
  • 先試結構：只有一個元件用的 state 往下放；外框元件有 state 時，慢的內容用 children 從沒有那個 state 的元件傳進去。
  • memo 在父元件 render、props 都 Object.is 相同時跳過；函式 props 用 useCallback（搭配 updater function），物件、陣列 props 用 useMemo，一個每次新的 prop 就讓它失效。在模組層級包，不寫比較函式。
  • useMemo 讓計算只在依賴改變時重算，在同一次 render 給出結果；依賴只放計算用到的值，照 exhaustive-deps 列完整。不要用 state 加 effect，也不要自己做模組層級的快取。
  • memo 擋不住元件自己的 state、context、store 的更新；拿掉記憶化程式就壞了代表有 bug。預設不加，量過才加。
