階段 1：心智模型：從 Vue 到 React · 第 3 課

state 與事件：useState、快照與不可變更新

咖啡店的集點卡有個「買三杯」按鈕，程式呼叫了三次「加 1 點」，客人卻只拿到 1 點。購物車按「加入拿鐵」，資料明明 push 進陣列了，畫面卻沒動。這兩個 bug 在 Vue 裡不會發生：React 的 state 不是會通知畫面的響應式物件，而是「這一次 render 的一張快照」。

這課的路線：
  1. useState 與 state 是快照：值存在哪裡，為什麼 set 之後讀到的還是舊值，「買三杯」該怎麼寫（開場問題的最小答案）。
  2. 不可變更新與 StrictMode：為什麼 push 進陣列畫面不動，開發時函式被呼叫兩次是在抓什麼 bug。
  3. state 放哪裡：菜單和購物車要看同一份資料時，state 該放在哪個元件、子元件怎麼往上通知。
  4. 初始值函式與 key：state 什麼時候建立、什麼時候重設，後台換一筆資料、表單卻留著上一筆內容的 bug 怎麼修。
這課會用到：
  • 第 1 課：呼叫 set 函式後，React 重新呼叫整個元件函式，並用 Object.is 比較新舊 state，一樣就跳過。
  • 第 2 課的 props、key 與練習環境：父元件用 props 把資料和函式傳給子元件，列表靠 key 認出新舊的同一項；練習用 node check.mjs react 編號 判分。
  • TS 課第 2 課的參考與展開：物件變數存的是參考，{ ...obj } 做出新物件但只複製一層。

useState：在每次 render 之間記住值

第 1 課講過，state 一變，React 會重新呼叫整個元件函式，所以區域變數每次都重新建立，記不住東西：

function StampCard() {
  let stamps = 0   // ✗ 每次 render 都從 0 開始，stamps++ 也不會觸發 render
  return <button onClick={() => { stamps++ }}>已集 {stamps} 點</button>
}
// 放到元件外面也不行：兩張卡共用同一個數字，改了一樣不會 render

state（狀態）是 React 幫每個元件「實例」保存、跨 render 留著的資料。useState 是一個 hook（以 use 開頭、只能在元件函式最上層呼叫的函式，第 9 課深入）：

import { useState } from 'react'

function StampCard() {
  const [stamps, setStamps] = useState(0)   // [這次 render 的值, 設定函式]
  return <button onClick={() => setStamps(stamps + 1)}>已集 {stamps} 點</button>
}

setStamps(1) 告訴 React「下一次 render 時 stamps 是 1」，React 再呼叫一次 StampCard()，這次 useState 回傳 1。每張卡各有自己的 state。跟 Vue 對照：

Vue refReact useState
元件程式執行幾次setup 只執行一次每次 render 都執行整個函式
怎麼改count.value++，直接改呼叫 setCount(新值)，不能直接改
改完立刻讀讀到新值（畫面晚一點更新）讀到舊值，新值要等下一次 render
怎麼知道要更新畫面Proxy 追蹤讀寫（Vue 課第 2 課）你呼叫了 set 函式

state 是快照：set 不會改眼前的變數

回到開場的「買三杯」：

function handleBuyThree() {
  setStamps(stamps + 1)
  setStamps(stamps + 1)
  setStamps(stamps + 1)
}

這就是第 1 課的快照（snapshot）：這次 render 的 stamps 是 const，永遠是 0，中間有沒有 await 都一樣，三次呼叫都是「設成 1」。

修法是傳 updater 函式（第 1 課的更新函式）：setStamps(s => s + 1)。傳值等於「換成這個值」，傳函式等於「拿目前排到的值再算」，兩者可以混用：

按一次執行佇列下一次 render 的值（從 0 開始）
setN(n + 1) ×3換成 1、換成 1、換成 11
setN(n => n + 1) ×3+1、+1、+13
setN(n + 5)，再 setN(n => n + 1)換成 5、+16

以上在 React 19.3.1 的練習環境實際跑過，三次 set 都只 render 一次，這是第 1 課的批次更新（batching），跟 Vue 課第 6 課的排程器目的一樣。實測 await 之後連續 set 兩個 state，也只更新一次畫面。

快照在 await 之後最容易出事。「集 1 點」要先存到伺服器：

async function handleStamp() {
  await save()
  setStamps(stamps + 1)   // ✗ 這裡的 stamps 是按下當時那次 render 的值
}

客人連按三下：save 還沒回來、state 沒變，三次點擊手上的 stamps 都是 0，實測結果是 1 點。改成 setStamps(s => s + 1) 就從最新的值算。原則：新值跟舊值有關（加減、切換、往陣列加一筆）用 updater；跟舊值無關（輸入框的內容、API 回來的資料）直接傳值。

💡 實務上：await 之後的 set 幾乎都該用 updater
表單送出後更新計數、WebSocket 收到訊息往列表加一筆，這些 set 執行時手上的 state 早就過期。這類 bug 本機重現不了，客人連點或網路慢時才出現。Code review 看到 await 或 callback 之後寫 setX(x + …)、setList([...list, item])，就問「這時候的 x 是哪一次的」。updater 不會阻止重複送出：結帳按鈕送出中要 disabled，伺服器端也要擋。

不可變更新：給 React 一個新的物件

第 1 課講過，React 用 Object.is 比較新舊 state，一樣就跳過這次 render。放到真的購物車：

const [lines, setLines] = useState<CartLine[]>([])

function add(productId: number) {
  lines.push({ productId, quantity: 1 })   // ✗ 改了原陣列
  setLines(lines)                          // 同一個參考：Object.is 判定沒變，不 render
}

實測按兩次，畫面還是 0，元件一次都沒重新 render。Vue 的 reactive 物件就是要你直接改（Vue 課第 4 課）；React 的 state 要當成唯讀的，每次都做出新的物件或陣列，這叫 不可變更新（immutable update）。

要做的事不要用（會改原陣列）改用（回傳新陣列）
加一筆push、unshift[...arr, item]
刪除splice、popfilter
改其中一筆arr[i].qty = 2map，只有符合的那筆回傳新物件
排序、反轉sort、reversetoSorted、toReversed（ES2023），或先 [...arr] 再排

巢狀的資料要從改到的那一層一路往上都複製，沒改到的部分沿用原本的參考：

type Order = { customer: { name: string; phone: string }; note: string; items: OrderItem[] }

// 改電話：order 和 customer 都是新的，items 沿用原本的陣列
const next = { ...order, customer: { ...order.customer, phone } }

// 拿鐵數量 +1：items 是新陣列，只有拿鐵那一列是新物件，其他列沿用
const next2 = {
  ...order,
  items: order.items.map(i => (i.productId === 2 ? { ...i, quantity: i.quantity + 1 } : i)),
}

為什麼不整份 structuredClone 再改？內容對，但每一層都換了參考。第 19 課的 memo 靠「參考沒變」跳過子元件，第 5 課的 effect 依賴也用 Object.is 比較，全部換新就都失效。展開只複製一層，剛好只複製改到的那條路徑。巢狀很深時社群常用 Immer 代勞（React 官方文件有介紹），這門課先手寫。

💡 實務上：從 Vue 轉過來，最常見的 bug 就是直接改 state
徵兆是「資料有進去，畫面要點別的東西才出現」。先用 React DevTools（瀏覽器擴充功能，可以看元件的 props 與 state）確認 state 內容，再找更新的程式裡有沒有 push、sort、splice、直接賦值。在練習環境試過，eslint-plugin-react-hooks 7.1.1 抓不到「push 後 set 回同一個陣列」，不能只靠 lint。團隊可以約定 state 型別寫成 readonly CartLine[]，push、sort 在 TypeScript 就會報錯。

StrictMode：為什麼你的函式被呼叫兩次

第 1 課講過，元件函式、初始值函式和 updater 都要是純函式；<StrictMode> 在開發模式會故意多呼叫一次這三種函式、只用其中一次的結果，不純的寫法就會現形。Vite 的 React 範本預設用 StrictMode 包住整個 App；正式環境不會多呼叫，事件處理函式也不會。真的寫 React 時，最常被它抓到的是 updater：

// ✗ updater 裡改了舊的那一列：產生了新陣列，畫面會動，但不純
setLines(prev => {
  const line = prev.find(l => l.productId === productId)!
  line.quantity += 1
  return [...prev]
})

實測在 StrictMode 裡按一次，數量從 1 變成 3：兩次呼叫改的是同一個舊物件。沒有 StrictMode 時是 2，看起來正常，問題只是被藏起來。改成 prev.map(…) 回傳新的那一列，呼叫幾次都是 2。練習 3 的測試就在 StrictMode 裡跑。

state 放哪裡：提升到共同父元件

點餐頁的菜單（Menu）和購物車（CartSummary）各放一份 state，菜單按「加入」，購物車看不到：state 屬於宣告它的元件，兄弟之間不共用。做法是 提升 state（lifting state up）：移到最近的共同父元件，props 往下傳資料，函式 props 讓子元件往上通知。

const [lines, setLines] = useState<CartLine[]>([])   // 在 OrderPage
const remove = (id: number) => setLines(prev => prev.filter(l => l.productId !== id))

<Menu products={products} lines={lines} onAdd={add} />
<CartSummary products={products} lines={lines} onRemove={remove} />

onAdd、onRemove 對應 Vue 的 emit（Vue 課第 9 課）：React 沒有 emit，父元件把函式當 prop 傳下去，子元件呼叫它。慣例是 prop 叫 onXxx，處理函式叫 handleXxx。第二個原則：能算出來的就不要存。件數、小計、合計都從 lines 算：

const count = lines.reduce((sum, l) => sum + l.quantity, 0)   // 每次 render 重算，就是 Vue 的 computed

存成 state 就得在每個改 lines 的地方同步，漏一處就對不上。React 不需要 computed：元件每次 render 都重新執行，區域變數就是最新的；真的很貴的計算再用第 19 課的 useMemo。同理，state 存 productId，不要複製整個商品物件：店長改了價格，複製進 state 的那份還是舊價格。

💡 實務上：state 越少，bug 越少
接手的專案常看到 total、isValid、selectedItem 存成 state 再用 effect 追著同步，這是「畫面偶爾對不上」的主要來源（第 6 課專門處理）。新增 state 前先問：能不能從現有的 props 或 state 算出來？是不是別的資料的複本？哪些元件需要它？放太高會讓不相關的元件跟著 render；第 14 課再談 URL 與全域 store。

初始值函式與用 key 重設 state

櫃台的點單從草稿讀初始杯數：

const [cups, setCups] = useState(loadDraft(customer.id))   // ✗ 每次 render 都呼叫 loadDraft

useState 的參數只在第一次 render 有用，但 loadDraft(…) 在呼叫 useState 之前就執行了，每次 render 都跑、結果被丟掉。實測按三次「加一杯」，它被呼叫 4 次。傳函式本身：useState(() => loadDraft(customer.id))，React 只在第一次 render 呼叫（StrictMode 開發時兩次）。Vue 沒有這個問題，setup 只執行一次。

第二個問題：換顧客後杯數還是上一位的。React 依元件在樹上的位置保存 state：同位置、同元件，就當成同一個實例，只更新 props（實測換到陳美華，顯示的是王小明的杯數）。給它一個跟著顧客變的 key：

<OrderPad key={customer.id} customer={customer} loadDraft={loadDraft} />

key 不同，React 就丟掉舊的 OrderPad 連同 state，在原位置建新的，初始值函式再跑一次。第 2 課的列表 key 是同一個機制；Vue 的 :key 也一樣（Vue 課第 7 課）。三種錯法：

  • 用 effect 在 render 後把 state 改回來：先畫出舊杯數再 render 第二次，畫面閃一下（第 5、6 課）。
  • key={Math.random()}：每次 render 都不同，父元件任何一次 render 都會把杯數清掉。
  • 把 OrderPad 定義在 ServiceDesk 函式裡：每次 render 都是新的函式，React 當成不同元件，state 被清掉（實測父元件 render 一次就歸零）。
💡 實務上：換一筆資料，表單卻留著上一個人的內容
後台的編輯面板換一張訂單、換一位會員時最常見這種 bug，原因就是上面的「同位置保留 state」，修法是外層加 key={id}。key 該放哪一層、重建的成本怎麼控制，第 6 課會完整講。

練習

用第 2 課裝好的環境，在 learn/ 執行 node check.mjs react 03，改 react/practice/work/03/ 裡的檔案，檔案開頭的註解有完整要求。測試靠畫面上的文字、按鈕名稱與 aria-label 找元素，不要改它們。

練習 1：修好集點卡 StampCard。「買三杯」一次加 3 點（再按是 6 點）。「集 1 點」先呼叫 save()，完成後才加 1 點；連按三下、三個 save 都完成後是 3 點。滿 10 點顯示 <p>可以兌換一杯</p>、「兌換」才能按，按了扣 10 點（13 變 3）；不到 10 點按鈕 disabled、不顯示提示。能不能兌換從點數算，不另外放 state；點數不能放在元件外（兩張卡各自計數）。

練習 2：order.ts 的五個函式都直接改傳進來的訂單（測試傳凍結的物件，改到就丟錯）。改成回傳新的 order：setNote 換備註；setPhone 換 customer.phone；addItem 已有的商品那列數量加 1，沒有就加到最後（{ productId, quantity: 1, unitPrice: product.price }）；setQuantity 改數量，小於等於 0 移除那列；sortByPrice 依單價由低到高、同價維持原順序。沒變的部分沿用原本的參考（setNote 後 next.items === order.items、沒改到的列是原本的物件），不能整份 structuredClone。

練習 3：OrderPage 的菜單和購物車各有一份 state。把購物車提升到 OrderPage，state 只存 { productId, quantity }[]，props 往下、onAdd／onRemove 往上。菜單每項顯示「品名 $單價」、「加入品名」按鈕，購物車有它時加 <span>已選 N</span>。購物車標題「購物車（總件數）」，每列「品名 × 數量 = $小計」與「移除品名」（移除整列），最後「合計 $N」，空的時候 <p>購物車是空的</p>。同商品加兩次是同一列數量 2，順序依第一次加入。件數、小計、合計在 render 時算；品名、單價從 props 的 products 查（不要 import 假資料），換了價格要用新單價。測試在 StrictMode 裡跑、products 是凍結的。

練習 4：櫃台 ServiceDesk 上面是顧客按鈕，下面是點單 OrderPad，初始杯數由 loadDraft(customerId) 讀。loadDraft 只在點單第一次出現時呼叫，按「加一杯」不能再呼叫；換顧客時杯數是新顧客草稿的值，換回原顧客也回到他草稿的值；換顧客畫面只更新一次（不能用 effect 事後改回來）；沒換顧客（再按目前的顧客、父元件重新 render）時杯數要留著。

練習 5：count 目前是 0。按鈕的 onClick 是 setCount(count + 1); console.log(count); setTimeout(() => console.log(count), 1000)。印出什麼？

✓ set 只決定下一次 render 的值。setTimeout 的 callback 在這次 render 建立，閉包抓到的也是這次的 count，一秒後畫面已經是 1，它讀到的還是 0。c 是 Vue ref 的想法：count.value 每次讀都是最新的；React 的 state 是快照。

練習 6：order 是 { customer, note, items } 的 state，要把備註改成 note。哪一個寫法最好？

✓ a 只複製最外層，customer、items 沿用原本的參考。b 內容對，但每一層都換了參考，依賴參考比較的 memo、effect 全部失效。c 的 useState 不會自動合併物件，customer 和 items 不見了。d 畫面會更新，但先改了舊物件，這次 render 的快照也被改掉，不是純粹的更新。

練習 7：<ProfileForm user={selectedUser} /> 裡用 useState(user.name) 當輸入框的初始值。切換到另一位使用者，輸入框還是上一位的名字。最直接的修法是？

✓ 元件還在同一個位置，React 保留了 state，初始值只在第一次 render 用。key 換成新使用者的 id，React 丟掉舊元件、建立新的，初始值重新計算。b 只是少算幾次，第一次以後一樣被忽略。c 讓父元件每次 render 都重建表單，正在打的字也會被清掉。

常見錯誤

  • set 之後馬上讀 state，以為是新值：set 只影響下一次 render。要用新值就先算好存在區域變數。
  • 同一個事件裡多次、或 await 之後 setX(x + 1)：x 是快照。用 updater setX(prev => prev + 1)。
  • 改了 state 再 set 回同一個參考：push、sort、splice、直接賦值之後，React 判定沒變。用展開、map、filter、toSorted。
  • updater 裡改舊物件：畫面會動，但 StrictMode 呼叫兩次就加兩次。updater 只讀 prev、回傳新值。
  • 整份 structuredClone 再改：沒變的部分也換了參考，memo 與依賴比較失效。只複製改到的路徑。
  • 把算得出來的值或物件複本存成 state：合計、能不能兌換在 render 時算；存 id，不存商品物件。
  • useState(expensive())：每次 render 都執行再丟掉。傳函式 useState(() => expensive())。
  • 以為換了 props 就會重設 state：同位置的同元件會保留 state。換 key；不要用 Math.random()，元件也不要定義在別的元件裡。

小結

  • useState 讓元件跨 render 記住值；普通變數每次重建，元件外的變數會被所有實例共用，兩者都不會觸發 render。
  • state 是快照：這次 render 裡的值永遠不變，set 只決定下一次 render 的值。
  • 新值依賴舊值時用 updater s => s + 1；React 批次處理佇列，一個事件只 render 一次。
  • React 用 Object.is 判斷 state 有沒有變：更新要做出新物件、新陣列，只複製改到的路徑，其他沿用原本的參考。
  • StrictMode 在開發時多呼叫一次元件、初始值與 updater 函式，抓出不純的寫法。
  • 多個元件要共用的 state 提升到共同父元件，props 往下、函式 props 往上；能算的不存，存 id 不存複本。
  • 貴的初始值傳函式；state 跟著位置走，要重設就換 key。
