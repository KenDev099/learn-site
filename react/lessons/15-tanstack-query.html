階段 4：狀態與資料 · 第 15 課

伺服器狀態：TanStack Query 的快取與失效

咖啡店的點餐頁用第 9 課的寫法，每個元件在 effect 裡自己抓資料。上線後：側欄和主畫面同時顯示拿鐵，Network 面板裡有兩個一樣的請求；客人在菜單和商品頁之間來回，每次回到菜單都要再看一次「載入中…」；店長在後台把拿鐵改成 120 元，商品頁更新了，列表還是 110 元。

根源是伺服器上的資料被當成元件自己的 state。這課用 TanStack Query 5.106.1（@tanstack/react-query）把它當成快取來管。

這課的路線：
  1. 伺服器狀態是一份快取：資料交給 QueryClient，兩個元件要同一份只送一個請求（開場問題的最小答案）。
  2. 兩個載入狀態：「還沒有資料」和「背景重抓中」差在哪，什麼時候才該顯示「載入中…」。
  3. queryKey、staleTime 與 gcTime：快取的地址怎麼設計，回到菜單為什麼不用再等一次。
  4. 換參數與失效：搜尋時保留舊結果不閃；店長改價後，列表和商品頁一起更新。
  5. 測試：每個測試一個 QueryClient，快取不會從上一個測試漏過來。
這課會用到：
  • 第 5 課的競態與 AbortController：舊請求比新請求晚回來會蓋掉畫面，參數一換就用 abort() 取消舊的。
  • 第 9 課的 useMenu：在 effect 裡抓資料、存進 state，loading 從「目前關鍵字的結果回來了沒」算出來。這課拿它當對照。

伺服器狀態是一份快取

伺服器狀態（server state）是真正的版本在伺服器上、前端只拿到某個時間點複本的資料：菜單、訂單、會員點數。它跟購物車、目前分頁這種前端自己擁有的客戶端狀態不同（第 14 課），別人隨時可能改它。所以要回答的問題不是「存在哪個 state」，而是快取的問題：

  • 好幾個元件要同一份資料，該送幾個請求？（一個：合併請求，dedupe）
  • 資料抓回來多久之後算舊、需要重抓？（新鮮時間，staleTime）
  • 伺服器上的資料改了，前端誰負責更新？（失效，invalidation）
  • 沒有人在看的資料，多久從記憶體清掉？（回收時間，gcTime；gc 是垃圾回收 garbage collection）

Vue 課第 17 課用一個 Map 自己做過這些，最後的結論是「多頁面共用伺服器資料時改用套件」。TanStack Query 就是那個套件，React 版和 Vue 版（@tanstack/vue-query）共用同一個核心 @tanstack/query-core，選項名稱一樣。

先在 App 最外層放一個 QueryClient（存放所有快取的物件），用 QueryClientProvider 透過 Context（第 11 課）交給底下的元件：

import { QueryClient, QueryClientProvider } from '@tanstack/react-query'

const queryClient = new QueryClient()   // 在元件外面建立一次

export function App() {
  return (
    <QueryClientProvider client={queryClient}>
      <MenuPage />
    </QueryClientProvider>
  )
}

寫在元件函式裡直接 new，每次 render 都是一份新的空快取。元件裡用 useQuery 讀資料（外面沒有 Provider 時會丟出 No QueryClient set）：

import { useQuery } from '@tanstack/react-query'

function ProductCard({ id }: { id: number }) {
  const { data, error, isPending, isError } = useQuery({
    queryKey: ['products', 'detail', id],                       // 快取的地址
    queryFn: ({ signal }) => api.getProduct(id, { signal }),    // 怎麼抓
  })
  if (isPending) return <p>載入中…</p>
  if (isError) return <p role="alert">{error.message}</p>
  return <p>{data.name} ${data.price}</p>
}

跟第 9 課的 useMenu 比，useEffect、「結果屬於哪一次請求」的比對都搬進了 QueryClient：

第 9 課 effect 裡抓Vue 課第 17 課自己做TanStack Query
資料放哪每個元件自己的 state模組裡的 Map<key, entry>QueryClient 的快取，以 queryKey 區分
兩個元件要同一份送兩次共用進行中的 Promise同一個 key 只送一次
競態abort 加比對 keyabort 加檢查是否被取代每個 key 各存各的，畫面只讀目前的 key
參數改變列進依賴陣列watch(() => toValue(key))放進 queryKey
多久算舊、失效沒有staleTime、invalidate(key)staleTime、invalidateQueries，加上聚焦、重連時重抓與失敗重試

Vue 版的差別只在響應式：@tanstack/vue-query 的 queryKey 可以放 ref 或 getter，它會追蹤變化自動重抓；React 每次 render 都重新呼叫 useQuery，直接放這次 render 的值就好。

兩個狀態：有沒有資料、有沒有在抓

Vue 課第 17 課最後把狀態分成兩個欄位：資料是什麼狀態、現在有沒有在抓。TanStack Query 也是：

欄位值回答的問題
status'pending'：還沒有資料
'error'：最近一次失敗
'success'：有資料		畫面上能顯示什麼
fetchStatus'fetching'：queryFn 正在執行
'paused'：想抓但沒網路，暫停中
'idle'：沒在抓		現在有沒有請求在跑

布林值從這兩個推出來：isPending、isError、isSuccess 看 status；isFetching 看 fetchStatus；isLoading 是 isPending && isFetching（第一次抓、而且正在抓）。實測一個 query 的一生（React 19.3.1）：

第一次抓：  status pending / fetching   isPending true   isFetching true   isLoading true
抓回來：    status success / idle       isPending false  isFetching false
背景重抓：  status success / fetching   isPending false  isFetching true   ← 有資料，又在抓
enabled 為 false：status pending / idle  isPending true   isLoading false   ← 沒資料，也不會抓

常見的錯是用 isFetching 決定要不要顯示「載入中…」，背景重抓時有資料卻整塊被換掉。規則是：沒有資料（isPending）才顯示大的載入畫面；有資料又在抓（isFetching）只加一個小的「更新中…」。

失敗也分兩種。第一次就失敗，沒有資料，只能顯示錯誤；背景重抓失敗時 status 變成 'error'，但 data 還是上一次成功的資料。只看 isError 就把整個畫面換成錯誤，客人原本看得到的菜單就消失了：

if (isPending) return <p>載入中…</p>
if (isError && !data) return <p role="alert">{error.message}</p>   // 完全沒有資料
return (
  <section>
    {isFetching && <p role="status">更新中…</p>}
    {isError && <p role="alert">{error.message}</p>}            {/* 背景重抓失敗：保留清單 */}
    <ul>{data.map(p => <li key={p.id}>{p.name}</li>)}</ul>
  </section>
)

回傳值是可辨識聯合（TS 課第 16 課）：檢查過 isPending、isError 之後，TypeScript 知道 data 有值。

💡 實務上：載入指示要分兩層
咖啡店後台的訂單列表整天開著、常在背景重抓，每次都閃骨架畫面，店員正在看的那一列就會跳走。常見做法：第一次載入用骨架畫面，背景更新只在標題旁放小圖示，失敗時保留舊清單、加一條「資料可能不是最新的」。review 看到 if (isFetching) return <Spinner /> 就該提出來。

queryKey：快取的地址

queryKey 是一個陣列，TanStack Query 把它轉成字串（hash）當成快取的地址。官方文件的規則：queryFn 用到的每個變數都要放進 queryKey。key 一樣就是同一份資料，所以：

  • key 少放參數：['product'] 但 queryFn 用了 id，換商品時 key 沒變，畫面停在上一個商品。
  • 物件的屬性順序不影響：['products', { page: 1, sort: 'price' }] 和 ['products', { sort: 'price', page: 1 }] 實測 hash 相同；陣列的順序則有影響。
  • 同一個 key 同時被好幾個元件用：只送一個請求，大家拿到同一份資料。

競態也因為 key 而消失：「拿」和「茶」的結果存在兩個地址，畫面只讀目前關鍵字的那個；「拿」比較晚回來只填好自己那格（練習 4 實測，API 不理會 signal 也一樣）。

取消請求則要靠你把 signal 傳下去。queryFn 收到的參數裡有 signal（AbortSignal），官方文件說明：query 過期或沒人使用時，這個 signal 會被 abort。原始碼的細節是：queryFn 有讀取 signal，最後一個使用者離開時才會真的取消進行中的請求；沒讀就讓它跑完、結果照樣存進快取。所以 queryFn 寫成 ({ signal }) => api.getProduct(id, { signal })，換商品時舊請求才會停（練習 1 實測舊請求的 signal 被 abort）。

key 通常由大到小排：先是資料種類，再來是列表或詳細，最後是參數。整個專案共用一個 key factory（產生 key 的函式集合），每個地方都從這裡拿 key，失效時才找得到：

export const productKeys = {
  all: ['products'] as const,
  lists: () => [...productKeys.all, 'list'] as const,
  list: (keyword: string) => [...productKeys.lists(), keyword] as const,
  details: () => [...productKeys.all, 'detail'] as const,
  detail: (id: number) => [...productKeys.details(), id] as const,
}
// productKeys.list('拿')  → ['products', 'list', '拿']
// productKeys.detail(2)   → ['products', 'detail', 2]

官方的 queryOptions({ queryKey, queryFn }) 可以把 key 和 queryFn 綁成一組重用，getQueryData(options.queryKey) 也拿得到正確的資料型別。

新鮮、過期與回收：staleTime 與 gcTime

每份快取有兩個計時：多久之後算過期（stale），沒人使用多久之後清掉。過期的資料先顯示、背景重抓，就是 Vue 課第 17 課的 stale-while-revalidate。

TanStack Query 5.106.1 在瀏覽器裡的預設值（官方文件 Important Defaults，括號裡是這課實測）：

選項預設意思
staleTime0一抓回來就算過期，單位是毫秒
gcTime5 分鐘最後一個使用者離開後 5 分鐘清掉（實測差 1ms 還在，滿 5 分鐘就不見）
refetchOnMounttrue元件掛載時，資料過期就重抓
refetchOnWindowFocustrue視窗回到前景（visibilitychange）時，過期就重抓
refetchOnReconnecttrue網路恢復時，過期就重抓
retry瀏覽器 3 次，伺服器 0 次失敗後重試，間隔 min(1000 × 2^次數, 30000) 毫秒（實測第 0、1、3、7 秒各呼叫一次，共 4 次才顯示錯誤）

staleTime 是 0 的後果：元件一掛載，快取裡早就抓好的資料也算過期，會再背景重抓（練習 1 換回看過的商品就是這樣）；切換分頁回來也重抓，開發時常以為是 bug。官方文件形容這些預設是「積極但合理」（aggressive but sane），並建議要減少重抓時優先設定 staleTime，而不是逐一關掉 refetchOnWindowFocus 這些觸發點。staleTime 設成 Infinity 是「除非手動失效，否則不重抓」。

staleTime 可以在 QueryClient 設全域預設，個別 query 覆寫：

const queryClient = new QueryClient({
  defaultOptions: { queries: { staleTime: 30_000 } },   // 全站預設 30 秒
})

useQuery({ queryKey: ['products', 'menu'], queryFn: getMenu, staleTime: 60_000 })   // 菜單 60 秒

staleTime 只決定要不要自動重抓，gcTime 才決定資料留多久。

💡 實務上：staleTime 依資料的變動頻率來定
菜單、營業時間一天改幾次，設幾分鐘；訂單狀態、庫存幾秒就變，維持 0 或很短，修改後再 invalidate。拿不準時問後端「這份資料多常變、誰會改它」。除錯時用 Devtools（另外安裝 @tanstack/react-query-devtools，預設只在開發模式打包）看每個 key 是 fresh 還是 stale、重抓了幾次。

換參數時：enabled 與 placeholderData

搜尋框是空的時候不該送請求。enabled: false 讓 query 不自動抓，這時 status 是 'pending'、fetchStatus 是 'idle'（上一節實測），所以「沒有關鍵字」要自己先判斷，不能只靠 isPending：

const q = keyword.trim()
const { data, isPending, isPlaceholderData } = useQuery({
  queryKey: productKeys.list(q),
  queryFn: ({ signal }) => api.search(q, { signal }),
  enabled: q !== '',                    // 空字串不抓
  placeholderData: keepPreviousData,    // 新的 key 還沒資料時，先顯示上一個 key 的
})
if (q === '') return <p>輸入關鍵字開始搜尋</p>
if (isPending) return <p>搜尋中…</p>

同樣的條件也可以寫成 queryFn: q ? () => api.search(q) : skipToken，型別上更嚴謹；官方文件提醒，用 skipToken 時 refetch() 不能用，需要手動觸發時改用 enabled。

換關鍵字時新的 key 還沒有資料，清單消失、變成「搜尋中…」，每打一個字閃一次。placeholderData: keepPreviousData 先顯示上一個 key 的資料（不寫進快取），isPlaceholderData 是 true，用它加上「更新中…」，免得客人以為「茶」的結果是拿鐵。這跟 Vue 課第 17 課 loading 帶著 previous 是同一個想法，分頁列表最常用。

失效：invalidateQueries

店長把拿鐵改成 120 元。畫面上可能同時有「全部商品」、搜尋「拿」的列表和拿鐵的詳細，看過的頁面也還在快取裡。queryClient.invalidateQueries 用 key 的前綴比對找出它們：

function onPriceChanged(queryClient: QueryClient, productId: number) {
  return Promise.all([
    queryClient.invalidateQueries({ queryKey: productKeys.lists() }),
    queryClient.invalidateQueries({ queryKey: productKeys.detail(productId) }),
  ])
}

被選中的 query 會發生兩件事（官方文件的 refetchType，預設 'active'）：

  • 畫面上有元件在用的（active）：標成過期，立刻背景重抓。
  • 沒有元件在用的（inactive，例如看過的「茶」列表）：只標成過期，不送請求；下次有元件掛載時，因為已經過期，自動重抓。不替沒人看的畫面浪費請求。

回傳的 Promise 等重抓完才完成，所以呼叫端可以 await，確定畫面已經是新價格再關掉對話框（第 16 課的 mutation 會用到這點）。加 exact: true 只選 key 完全相同的那一個。

Vue 課第 17 課的迷你快取有個洞：invalidate 時剛好有請求在跑，會共用那個可能讀到舊價格的請求。TanStack Query 預設 cancelRefetch: true，先取消進行中的再送新的（實測連續 invalidate 兩次，第一次的請求被 abort）。

其他看起來類似的方法，結果不一樣：

方法畫面上的 query沒人用的 query什麼時候用
invalidateQueries標成過期並重抓標成過期，下次使用時重抓伺服器資料改了（最常用）
refetchQueries重抓預設（type: 'all'）也立刻重抓；加 type: 'active' 就不碰，也不會標成過期只想立刻重抓，例如「重新整理」按鈕
removeQueries從快取刪掉，正在用的元件不會重抓刪掉，下次從載入中開始登出時清掉使用者的資料
💡 實務上：失效範圍寧可大一點，key 要先設計好
productKeys.lists() 一次選到所有關鍵字的列表，不用記得有哪些搜尋條件。拿不準時範圍寧可寬一點：多重抓的代價是一個請求，漏掉的代價是客人看到舊價格。專案初期就定好 key factory，review 看到元件裡手寫 ['product', id] 就請對方改用 factory，不然改價時漏掉的畫面要等客服回報才發現。

測試：每個測試一個 QueryClient

測試之間共用 QueryClient，上一個測試的快取會影響下一個。官方的測試指南建議：

function renderWithClient(ui: ReactNode) {
  const client = new QueryClient({
    defaultOptions: { queries: { retry: false } },   // 失敗馬上顯示，不用等 1、2、4 秒的重試
  })
  return render(<QueryClientProvider client={client}>{ui}</QueryClientProvider>)
}
  • 每個測試一個新的 QueryClient，關掉 retry：不然錯誤要等重試，findBy… 預設 1 秒就逾時。元件裡別寫死 retry，會蓋過測試的設定。
  • TanStack Query 用 setTimeout(0) 批次通知元件更新（notifyManager 原始碼）：請求完成後用 findBy…，或像練習的 settle() 多等一個 setTimeout(0)。
  • 測 staleTime 只需要假造時間：staleTime 用 Date.now() 判斷，vi.useFakeTimers({ toFake: ['Date'] }) 加 vi.setSystemTime() 就能跳到 61 秒後，計時器照常運作（練習 2）。

練習

在 learn/ 執行 node check.mjs react 15。每個測試都建立新的 QueryClient、關掉 retry，用 QueryClientProvider 包住你的元件；假 API 由測試決定每個請求何時、以什麼結果回來，abort 時像 fetch 一樣失敗。練習 2 只假造 Date，用 vi.setSystemTime 跳到 30 秒、61 秒後；練習 3 的 QueryClient 把 staleTime 設成 Infinity，只有失效才會重抓。

練習 1：把 effect 裡抓資料的 ProductCard({ api, id }) 改成 useQuery。兩張卡片顯示同一個商品只呼叫 api.getProduct 一次，不同商品各自呼叫（QueryClient 由外面的 Provider 提供，元件裡不要自己建立）；id 改變時抓新的商品；呼叫 api.getProduct(id, { signal })，signal 用 queryFn 收到的，id 改變時還沒回來的舊請求要被取消。還沒有資料時顯示「載入中…」，換回看過的商品要直接顯示快取，不能出現「載入中…」；失敗時顯示 role="alert"，內容有錯誤訊息，裡面的「重試」按鈕呼叫 refetch()；成功時顯示「品名 $價格」，例如「拿鐵 $110」。

練習 2：MenuList({ api }) 每次回到菜單頁都重抓，重抓時整份清單換成「載入中…」。改成：菜單抓回來後 60 秒內算新鮮，再回到菜單頁直接顯示快取、不送請求；超過 60 秒先顯示舊清單，同時背景重抓，重抓時另外顯示 role="status" 的「更新中…」，抓完換成新清單、「更新中…」消失；第一次載入只顯示「載入中…」，不顯示「更新中…」。背景重抓失敗時清單保留，另外顯示 role="alert" 的錯誤訊息；完全沒有資料時失敗，只顯示錯誤訊息。清單是 <ul>，每個商品一個 <li>，內容是品名。

練習 3：重新設計 productKeys，並寫 onPriceChanged(queryClient, productId)。所有商品的 key 都以 productKeys.all（['products']）開頭；不同關鍵字的 list(keyword)、不同 id 的 detail(id) 都是不同的 key，列表和詳細不會撞到。onPriceChanged：所有列表（任何關鍵字）和那個商品的詳細失效，畫面上正在顯示的立刻重抓；其他商品的詳細、門市 ['stores'] 不動；現在沒在畫面上的不立刻重抓，下次顯示時才重抓；回傳的 Promise 等畫面上的 query 重抓完才完成。

練習 4：把手寫 effect 的 ProductSearch({ api, keyword }) 改成 useQuery。關鍵字前後的空白不算，去掉空白後是空字串時不送請求，顯示「輸入關鍵字開始搜尋」；有關鍵字時呼叫 api.search(關鍵字, { signal })，queryKey 包含去掉空白後的關鍵字。第一次搜尋、還沒有結果時顯示「搜尋中…」；換關鍵字、新結果還沒回來時保留上一次的結果，另外顯示 role="status" 的「更新中…」，不能顯示「搜尋中…」；換回搜尋過的關鍵字直接顯示快取；舊的回應比較晚回來也不能蓋掉新的結果。結果是 <ul>，每個商品一個 <li>，內容是品名；沒有符合時顯示「沒有符合的商品」；失敗時顯示 role="alert" 的錯誤訊息。

練習 5：商品詳細頁寫成 useQuery({ queryKey: ['product'], queryFn: () => api.getProduct(id) })。客人從拿鐵點到可頌，會怎樣？

✓ TanStack Query 只看 queryKey 判斷「這是哪一份資料」，不會去分析 queryFn 用了什麼。key 一樣，快取裡就有現成的資料，畫面停在拿鐵，所有用 ['product'] 的畫面也都共用這一格。規則是 queryFn 用到的變數都要放進 key：['products', 'detail', id]。TypeScript 不會檢查這件事；官方的 ESLint 外掛有 @tanstack/query/exhaustive-deps 規則可以檢查。

練習 6：菜單的 staleTime 是 60 秒、gcTime 是預設的 5 分鐘。客人看完菜單，去結帳頁待了 3 分鐘再回來。會看到什麼？

✓ 3 分鐘還沒超過 gcTime，資料還在；但超過 staleTime，已經過期：掛載時先顯示，同時背景重抓。a 搞混了兩個時間：staleTime 決定要不要重抓，gcTime 決定資料留多久。b 是 60 秒內回來的情況。

練習 7：拿鐵改價後呼叫 invalidateQueries({ queryKey: ['products', 'list'] })。畫面上開著「全部商品」列表，客人稍早看過的「茶」列表已經離開。這兩個列表會怎樣？

✓ queryKey 是前綴比對，兩個列表都被選中、都標成過期。refetchType 預設 'active'：只有畫面上正在用的立刻重抓，沒人看的等下次使用時再抓，不浪費請求。b 是 refetchType: 'all' 的行為；c 是 removeQueries；d 要加 exact: true 才是完全比對。

常見錯誤

  • queryKey 沒放 queryFn 用到的變數：換參數時畫面停在舊資料，不同參數共用一格快取。用到什麼就放什麼，用 key factory 產生。
  • 在元件裡 new QueryClient：每次 render 或每個元件一份新的快取，合併請求、快取都失效。在元件外建立一次，用 Provider 提供。
  • 用 isFetching 決定要不要顯示載入畫面：背景重抓時有資料卻被蓋掉。沒資料看 isPending，背景更新看 isFetching 加小提示。
  • 只看 isError 就換成錯誤畫面：背景重抓失敗時 data 還在。有資料就保留，另外顯示錯誤。
  • 沒把 signal 傳給 API：換參數、離開頁面時舊請求停不下來。queryFn 寫成 ({ signal }) => api.xxx(…, { signal })。
  • staleTime 寫成秒，或乾脆 Infinity：單位是毫秒；永遠新鮮的資料，伺服器改了畫面也不會跟上。依資料變動頻率設定，修改後 invalidate。
  • 換參數時結果整個消失：每打一個字閃一次。placeholderData: keepPreviousData 加上 isPlaceholderData 的「更新中…」。
  • 測試共用一個 QueryClient、沒關 retry：結果看執行順序，失敗的測試要等重試逾時。每個測試一個新的 QueryClient，retry: false。

小結

  • 伺服器狀態是快取，不是元件的 state：TanStack Query 把合併請求、新鮮時間、失效、回收放進 QueryClient，用 Provider 交給元件。
  • status（有沒有資料）和 fetchStatus（有沒有在抓）是兩件事：沒資料才顯示載入畫面，背景更新只加小提示，背景失敗保留舊資料。
  • queryKey 是快取的地址：放進 queryFn 用到的每個變數，由大到小排，用 key factory 產生；每個 key 各存各的，競態自然消失；signal 傳下去，舊請求才會被取消。
  • staleTime（預設 0）決定多久之後重抓，gcTime（預設 5 分鐘）決定沒人用多久清掉；過期資料先顯示、背景重抓。
  • enabled 讓條件不足時不抓，placeholderData: keepPreviousData 讓換參數時不閃。
  • invalidateQueries 用前綴選出要失效的快取：畫面上的立刻重抓，沒人用的標成過期、下次使用時重抓。
  • 測試時每個測試一個新的 QueryClient，關掉 retry。
