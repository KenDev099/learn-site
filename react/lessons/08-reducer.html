階段 2：Hooks 與副作用 · 第 8 課

useReducer：把狀態轉換寫成純函式

咖啡店的購物車有六個按鈕：加入、加一、減一、移除、清空、套用折扣碼，每個事件處理函式各自算下一個 state。上線後客服回報：拿鐵可以加到 22 杯（上限 20）；清空購物車後折扣碼還掛著；空的購物車也能套用折扣碼。每個 bug 都是某個函式漏了一條規則，規則散在六個地方，修一個漏一個。

這課把「state 怎麼變」從事件處理函式裡搬出來，集中寫成一個純函式。

這課的路線：
  1. 規則散在事件處理函式裡：杯數上限、清空時一併清掉折扣碼這類規則為什麼修一個漏一個，集中到一個函式長什麼樣（開場問題的最小答案）。
  2. reducer 是純函式、action 的型別：reducer 要守的三條規則，用可辨識聯合讓打錯的 action、漏處理的情況在編譯時就報錯，規則也能不 render 直接測。
  3. 狀態機：訂單只有幾種狀態，reducer 只接受合法的轉換，不合法的操作不算數。
  4. dispatch 與什麼時候用 useReducer：dispatch 跟 set 一樣不會改到眼前的 state，以及 useState 和 useReducer 怎麼選。
這課會用到：
  • 第 3 課的不可變更新：不改原物件，做出新的物件、陣列，只複製改到的那條路徑，React 用 Object.is 才看得出有變。
  • TS 課第 16 課的可辨識聯合與 never：每一種情況用同一個字面值欄位（例如 type）區分，switch 漏處理的情況會在指定成 never 的那行報錯。

規則散在事件處理函式裡

先看練習 3 的起始程式（節錄）。每個函式都在算「下一個 state 是什麼」：

const [lines, setLines] = useState<CartLine[]>([])
const [coupon, setCoupon] = useState<string | null>(null)

function add(p: Product) { /* 沒檢查上限 20 */ }
function dec(productId: number) { /* 減到 0 會移除，但忘了清折扣碼 */ }
function remove(productId: number) { /* 有清折扣碼 */ }
function clear() { setLines([]) }            // 忘了清折扣碼
function apply() { setCoupon(code.trim()) }  // 空的購物車也能套用

「購物車空了，折扣碼就要清掉」這條規則跟 lines、coupon 兩個 state 都有關，卻要每個會改 lines 的函式各記一次。reducer 的做法是把它們合成一份 state，交給一個函式統一決定怎麼變：

  • action：一個描述「發生了什麼」的普通物件，例如 { type: 'added', product }。
  • reducer：(state, action) => 下一個 state 的純函式。名字來自陣列的 reduce：把一串 action 依序「折」進 state，就得到現在的樣子。
  • dispatch：useReducer 給你的函式。事件處理函式只呼叫 dispatch(action)，不再自己算。
import { useReducer } from 'react'
import { cartReducer, EMPTY_CART } from './cartReducer.ts'

const [cart, dispatch] = useReducer(cartReducer, EMPTY_CART)

<button onClick={() => dispatch({ type: 'added', product: p })}>加入{p.name}</button>
<button onClick={() => dispatch({ type: 'cleared' })}>清空購物車</button>

對照 Vue：Vue 課第 15 課的 Pinia 也要求元件只呼叫 action、規則只寫在 action 裡，第 12 課的 composable 也把 ref 和修改它的函式包在一起。差別在形式：Pinia 的 action 是直接改 reactive state 的函式（items.value.push(…)）；React 的 action 是一筆資料，reducer 不改任何東西，而是回傳一個新的 state。

reducer 是純函式

純函式（pure function）：同樣的輸入一定得到同樣的輸出，而且不改外面的任何東西。對 reducer 來說有三條：

  1. 不改傳進來的 state 和 action：有變的那一層換新的物件或陣列，沒變的沿用（TS 課第 2 課的「只複製有變的那條路」）。
  2. 不做副作用：不打 API、不設計時器、不寫 localStorage。
  3. 不讀會變的外部來源：Date.now()、Math.random()、crypto.randomUUID() 都不行。需要時間或 id，由事件處理函式產生、放進 action 帶進來。

第一條違反時會怎樣？下面的 reducer 直接 push 再回傳同一個物件：

function cartReducer(state: CartState, action: CartAction): CartState {
  if (action.type === 'added') {
    state.lines.push({ …, quantity: 1 })   // ✗ 改了目前的 state
    return state                           // ✗ 回傳同一個參考
  }
  …
}

React 用 Object.is 比較回傳的 state 和目前的 state，一樣就跳過這次更新（react.dev 的 useReducer 文件）。React 19.3.1 實測：元件函式又被呼叫了一次，但結果被丟掉，畫面上的數量還是 0，陣列裡卻已經有一筆。

反過來用：什麼都沒變的時候，就故意回傳原本的 state。找不到那個商品、已經 20 杯還按加入、空的購物車再清空，都 return state，React 就能跳過更新。如果每次都回傳 { ...state }，就算內容一樣，參考也不同，每次都會重新 render。

case 'cleared':
  return state.lines.length > 0 ? { lines: [], coupon: null } : state   // 本來就空：回傳原本的

// 只有那一列換成新的物件，其他列沿用原本的
return { ...state, lines: state.lines.map(l => (l.productId === id ? { ...l, quantity } : l)) }

整包 structuredClone(state) 再改也不對：每一列都變成新物件，第 19 課的 memo 就跳不過沒變的列，沒變時也回傳新參考。

第 3 課的 <StrictMode> 對 reducer 和初始化函式也一樣：開發模式各多呼叫一次、丟掉其中一次的結果（react.dev；React 19.3.1 實測一次 dispatch 呼叫 reducer 2 次）。reducer 裡 push 進傳進來的陣列，商品就被加兩次；送統計事件，就送兩次。

練習 1、2 的測試會用 deepFreeze 把 state 和 action 每一層都 Object.freeze，任何一處偷改都會丟 TypeError。

💡 實務上：reducer 是最好測的程式
reducer 不依賴元件、不碰 DOM，測試就是「給 state 和 action，比對回傳值」，一個測試幾毫秒。購物車、結帳流程、多步驟表單這類規則多的地方，資深工程師會把規則全部收進 reducer，用單元測試把每條規則（上限、空車清折扣碼、找不到商品不動）寫成一個案例，元件測試只確認「按鈕 dispatch 了對的 action、畫面顯示 reducer 的結果」。客服回報 bug 時，把使用者的操作寫成一串 action，用 actions.reduce(cartReducer, EMPTY_CART) 就能重播出當時的購物車。

action 的型別：可辨識聯合與窮舉檢查

action 用 TS 課第 16 課的可辨識聯合（discriminated union）來寫：每一種 action 用 type 欄位分辨，各自帶需要的資料。

export type CartAction =
  | { type: 'added'; product: Product }
  | { type: 'incremented'; productId: number }
  | { type: 'removed'; productId: number }
  | { type: 'cleared' }
  | { type: 'coupon_applied'; code: string }

export function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case 'added': {
      const { id, name, price } = action.product   // 這裡 action 已縮小成 added，一定有 product
      …
    }
    case 'cleared':
      …
    default: {
      const _exhaustive: never = action   // 每一種都處理了，這裡就是 never
      return state
    }
  }
}

好處有三個：dispatch({ type: 'cleard' }) 打錯字會是型別錯誤；{ type: 'added' } 少帶 product 也是；之後新增一種 action 卻忘了在 switch 處理，default 裡的 action 就不是 never，那一行會報錯，編譯器幫你找出漏掉的地方。

型別不用另外告訴 useReducer：@types/react 19.3.0 從 reducer 的參數推導 state 和 action 的型別，dispatch 的參數自動就是 CartAction。只要 reducer 的參數不是 any。

命名：action 描述發生了什麼（added、coupon_applied），不是要怎麼改（set_lines）。{ type: 'set_lines', lines } 的 lines 還是在元件裡算的，規則又回到元件。一個使用者操作對應一個 action：「清空購物車」是一個 cleared，不是每一列各 dispatch 一次 removed。

狀態機：只接受合法的轉換

TS 課第 27 課把訂單寫成狀態機（state machine）：只有幾種狀態，狀態之間只允許某些轉換。reducer 剛好是寫狀態機的地方：它同時拿到「現在的狀態」和「發生了什麼」，由它決定這件事在現在的狀態下算不算數。

現在的狀態合法的 action → 下一個狀態
pending（等待付款）paid → paid；cancelled → cancelled
paid（已付款）started → preparing；cancelled → cancelled
preparing（製作中）finished → ready
ready（可以取餐）picked_up → completed
completed、cancelled沒有：終點

表上沒有的組合（pending 收到 started、completed 收到 cancelled）都不合法。

export function orderReducer(state: OrderState, action: OrderAction): OrderState {
  switch (action.type) {
    case 'paid':
      return state.status === 'pending' ? { status: 'paid', paidAt: action.at } : state
    case 'started':
      return state.status === 'paid' ? { ...state, status: 'preparing' } : state
    …
  }
}

幾個設計決定：

  • 不合法的轉換回傳原本的 state，不丟錯。React 19.3.1 實測：dispatch 只把 action 排進佇列，reducer 在下一次 render 時才被呼叫，在那裡丟錯就是 render 時丟錯，畫面會壞掉（第 13 課的 Error Boundary 才接得住）。進度來自外部、順序可能亂，忽略才是對的。
  • 付款時間放在 action 裡（{ type: 'paid', at }）。reducer 裡寫 new Date() 就不純，測試也寫不出預期值。
  • 每個狀態只帶自己的欄位。cancelled 只有 status 和 reason；從 paid 取消時如果寫 { ...state, status: 'cancelled', reason }，舊的 paidAt 會被帶過去，變成 TS 課第 27 課說的「不合法的狀態」。
  • 規則只寫一份。畫面上「取消訂單」按鈕要不要 disabled，和 reducer 接不接受 cancelled，是同一條規則。把它寫成 canCancel(state)，reducer 和元件都呼叫它，不要在 JSX 裡再寫一次 status === 'pending' || …。

前端的狀態機只保護這個畫面。真正決定訂單能不能取消的是伺服器（TS 課第 27 課講的條件式 UPDATE），前端擋的是「畫面不要顯示不可能的狀態、不要送出一定會失敗的請求」。

💡 實務上：推送來的訊息會亂序、會重複
WebSocket、伺服器推送送來的訂單進度，重連時可能重送，也可能比使用者的操作晚到：客人剛按了取消，櫃檯的「開始製作」才到。收到什麼就顯示什麼，畫面會從「已取消」跳回「製作中」；交給狀態機 reducer，不合法的轉換一律忽略，畫面就不會倒退。資深工程師會跟後端確認：推送的訊息有沒有版本號或時間，前端只接受比現在新的；重連之後要不要重新抓一次完整狀態。

dispatch：快照、批次與穩定的參考

dispatch 跟第 3 課的 set 函式一樣，不會改到正在執行的程式裡的 state：

function handleAdd() {
  dispatch({ type: 'added', product: latte })
  console.log(cart.lines.length)   // 還是舊的：cart 是這次 render 的快照
}

真的需要知道下一個 state，官方文件建議自己呼叫一次 reducer：cartReducer(cart, action)，因為它是純函式。

同一個事件裡 dispatch 好幾次，React 會批次處理：全部排進佇列，下一次 render 時依序交給 reducer，每一個都拿到前一個的結果，只 render 一次。實測：一個事件裡連續 dispatch 三次加一，元件只多 render 一次，畫面直接是 3。這跟 setCount(c => c + 1) 的更新函式是同一個機制，reducer 永遠拿到最新的 state。

第三個特性對 effect 特別重要：dispatch 的參考永遠不變（stable identity）。官方文件寫明它可以不放進 effect 的依賴陣列，放了也不會讓 effect 重跑。回想第 5 課的過期閉包：

// ✗ listener 讀的 status 永遠是第一次 render 的 'pending'
useEffect(() => source.subscribe(action => {
  if (action.type === 'started' && status === 'paid') setStatus('preparing')
}), [])   // 把 status 加進依賴：每次進度改變都退訂、重新訂閱

// ✓ listener 只把 action 交給 dispatch，由 reducer 用最新的 state 判斷
useEffect(() => source.subscribe(dispatch), [source])

listener 不讀 state，就不會有過期的問題；dispatch 不會變，effect 只依賴 source，進度改變時不會重新訂閱。「判斷能不能轉換」需要最新的 state，這件事交給 reducer 做，React 呼叫 reducer 時一定給它最新的。這是 useReducer 最實際的用途之一：effect 或計時器裡要根據目前的 state 更新時，送出 action 就好。

Vue 沒有這個問題：callback 讀 status.value，讀到的永遠是 ref 現在的值，沒有快照。

什麼時候用 useReducer

react.dev 的說法：useState 和 useReducer 是等價的，可以互相轉換，同一個元件也可以兩個都用。選擇依據是規則多不多：

情況用什麼
獨立的值，沒有規則：開關、輸入框的草稿、目前選的分頁useState：程式最少
幾個 state 一起變，彼此有規則（lines 和 coupon、status 和 reason）useReducer：規則集中在一處
有明確的狀態與轉換（訂單、上傳、多步驟流程）useReducer 寫成狀態機
effect、計時器、訂閱裡要根據目前的 state 更新useReducer：送出 action，不讀 state
伺服器來的資料（菜單、訂單列表）都不是：第 15 課的 TanStack Query

練習 3 就是混用：lines 和 coupon 有規則，進 reducer；折扣碼輸入框的草稿沒有規則，留在 useState；總金額照第 6 課在 render 中用 cartTotal(cart) 算。

初始值要花力氣算時（例如從 localStorage 讀回購物車），用第三個參數初始化函式：useReducer(cartReducer, storageKey, loadCart)，React 只在第一次 render 呼叫 loadCart(storageKey)。寫成 useReducer(cartReducer, loadCart(storageKey)) 的話，每次 render 都會讀一次再丟掉。

useReducer 的 state 只屬於這個元件。要讓很多元件共用同一台購物車，可以把 state 和 dispatch 放進 Context（第 11 課），或用 Zustand 這類 store（第 14 課），那時才是真正對應 Pinia 的東西。reducer 本身不用改，這也是先把規則寫成純函式的好處。

💡 實務上：code review 看到一長串 setState 就該想到 reducer
一個事件處理函式裡連續呼叫三、四個 set 函式，或者好幾個函式都在處理「某個值變了另一個也要跟著變」，通常就是該收進 reducer 的訊號。反過來，只有一個布林值的開關硬寫成 reducer，只是多了樣板程式碼。換成 reducer 時順手檢查三件事：action 名稱是不是「發生了什麼」、沒變的情況有沒有回傳原本的 state、時間和 id 是不是從 action 帶進來。

練習

在 learn/ 執行 node check.mjs react 08（環境在第 2 課裝好）。建議照順序做：練習 3 用到練習 1 的 cartReducer，練習 4 用到練習 2 的 orderReducer。練習 1、2 的型別測試用 tsc 檢查一段標了 @ts-expect-error 的程式，訊息出現「Unused '@ts-expect-error'」代表那一行該報錯卻沒有，通常是型別寫成了 any。練習 3、4 的測試會記錄元件 dispatch 了哪些 action。

練習 1：完成 cartReducer.ts。把 CartAction 改成六種 action 的可辨識聯合：added（帶 product）、incremented、decremented、removed（都帶 productId）、cleared（沒有其他欄位）、coupon_applied（帶 code）。規則：added 時沒有這個商品就在最後面加一列（數量 1），有就數量 +1；decremented 到 0 時移除那一列；數量上限 MAX_QUANTITY（20）；cleared 清空 lines 並把 coupon 設回 null；coupon_applied 在購物車是空的或 code 是空字串時不套用；只要 lines 變成空的，coupon 就變回 null。不能修改傳進來的 state 和 action（測試會凍結它們），沒變的列沿用原本的物件；什麼都沒變時（找不到商品、到上限、空車再清空、套用同一個折扣碼）回傳原本的 state。switch 的 default 用 never 做窮舉檢查。總金額已經由 cartTotal 算，不要放進 state。

練習 2：完成 orderReducer.ts 的訂單狀態機。合法的轉換只有：pending 收到 paid → paid（paidAt 用 action.at）、paid 收到 started → preparing、preparing 收到 finished → ready、ready 收到 picked_up → completed、pending 或 paid 收到 cancelled → cancelled（reason 用 action.reason）。paid 之後每個狀態保留 paidAt；cancelled 只有 status 和 reason。其他轉換一律回傳原本的 state（同一個參考），不要丟錯。寫好 canCancel(state)（只有 pending、paid 是 true），reducer 處理 cancelled 時也用它。reducer 不能讀時鐘、不能改傳進來的物件；default 用 never 窮舉；不要改 OrderState、OrderAction 的定義，也不要用 any。

練習 3：把 Cart.tsx 的 lines、coupon 改成 useReducer(cartReducer, EMPTY_CART)，刪掉自己算下一個 state 的程式。每個操作只 dispatch 一個 action：「加入○○」是 added（帶整個 product，不要在元件裡判斷已經有沒有）、+／−／移除是 incremented／decremented／removed（帶 productId）、「清空購物車」是一個 cleared、「套用」是 coupon_applied（code 去掉前後空白），套用後清空輸入框。輸入框的草稿留在 useState；總金額在 render 中用 cartTotal(cart) 算，每個操作只能讓畫面 commit 一次。按鈕文字和 aria-label 不要改。

練習 4：OrderTracker.tsx 的 listener 讀到的是第一次 render 的狀態，付款之後的進度全被忽略。改用 useReducer(orderReducer, { status: 'pending' })，effect 只把收到的 action 交給 dispatch：掛載時訂閱一次，進度改變時不能重新訂閱，source 換了才退訂舊的、訂閱新的（訂單狀態保留），卸載時退訂。依賴陣列照實列出，不能用 eslint-disable，也不能用 ref 存最新狀態繞過。「取消訂單」dispatch { type: 'cancelled', reason: '顧客取消' }，disabled 用 canCancel(order) 決定；已取消時多顯示「原因：顧客取消」。

練習 5：事件處理函式裡寫 dispatch({ type: 'cleared' })，下一行 console.log(cart.lines.length)，購物車原本有 2 列。印出什麼？

✓ dispatch 只是把 action 排進佇列、要求下一次 render，不會改到正在執行的函式裡的 cart 變數（第 3 課的快照）。reducer 甚至要到下一次 render 才被呼叫。需要預先知道結果時，自己呼叫 cartReducer(cart, action)。

練習 6：reducer 的 added 寫成 state.lines.push(newLine); return state。按「加入拿鐵」之後會怎樣？

✓ React 比較的是參考，不是內容：回傳同一個物件就被當成沒變而跳過，資料已經改了，畫面卻停在舊的。React 不檢查你有沒有改物件，所以不會丟錯；StrictMode 只會讓問題更明顯（可能 push 兩次）。

練習 7：訂單付款時要記錄付款時間。new Date().toISOString() 應該寫在哪裡？

✓ reducer 要純：同樣的 state 和 action 得到同樣的結果，在裡面讀時鐘，測試寫不出預期值。元件本體每次 render 都會跑，也必須是純的。事件處理函式本來就是做副作用的地方，在那裡產生時間、id，帶進 action。

常見錯誤

  • 在 reducer 裡改 state 再回傳：React 用 Object.is 判定沒變，畫面不更新。有變的那一層換新物件，沒變的沿用。
  • 什麼都沒變也回傳 { ...state }：參考不同，每次都重新 render。沒變就 return state。
  • 在 reducer 裡讀時鐘、產生 id、打 API：reducer 會被呼叫兩次（StrictMode）、在 render 時執行。時間和 id 放進 action，副作用放在事件處理函式或 effect。
  • action 寫成 set_xxx：下一個值又在元件裡算，規則回到元件。action 描述發生了什麼，由 reducer 決定怎麼變。
  • action 型別寫成 any 或 string：打錯字、少帶欄位都不會報錯。用可辨識聯合，default 用 never 窮舉。
  • 不合法的轉換在 reducer 裡丟錯：reducer 在 render 時執行，丟錯會讓畫面壞掉。回傳原本的 state，忽略它。
  • JSX 裡再寫一份規則：按鈕 disabled 的條件和 reducer 的判斷分開寫，遲早不一致。抽成 canCancel 這類函式兩邊共用。
  • effect 裡讀 state 再 set，依賴陣列用 eslint-disable 蓋掉：過期閉包。改成送出 action，讓 reducer 用最新的 state 判斷；dispatch 不會變，不用重新訂閱。

小結

  • useReducer(reducer, initialArg, init?) 回傳 [state, dispatch]；事件處理函式只 dispatch 一個描述「發生了什麼」的 action，「state 怎麼變」集中在 reducer。
  • reducer 是純函式：不改傳進來的 state 和 action、不做副作用、不讀時鐘與亂數。開發模式的 StrictMode 會呼叫它兩次。
  • React 用 Object.is 比較新舊 state：有變的那一層換新參考，沒變的沿用；什麼都沒變就回傳原本的 state。
  • action 寫成可辨識聯合，default 用 never 窮舉；型別從 reducer 推導，不用另外給 useReducer。
  • reducer 適合寫狀態機：不合法的轉換回傳原本的 state，規則（canCancel）只寫一份。
  • dispatch 不會改到目前的快照，同一個事件裡的多次 dispatch 批次處理；dispatch 的參考不變，effect 裡送 action 就不用依賴 state。
  • 簡單、獨立的值用 useState；有規則、會一起變的用 useReducer；兩者可以混用。對照 Vue，Pinia 的 action 直接改 state，React 的 reducer 回傳新的 state。
