階段 3：元件設計與型別 · 第 11 課

Context：跨層傳遞與重新 render 的代價

咖啡店後台可以切換門市，價格標籤、訂單標題都要顯示目前是哪一家。門市在最外層選，用到它的 PriceTag 在第 4 層，中間的 Layout、MenuPage、ProductList 用不到門市，卻都得收一個 store prop 再往下傳。改用 Context 之後，同事又回報：菜單有 200 個商品，每加一杯拿鐵，200 顆「加入」按鈕全部重新 render。

這課學 React 的 Context：祖先元件提供一個值，任何一層後代直接讀，並對照 Vue 課第 13 課的 provide／inject。兩者用途一樣，代價不一樣：Vue 只更新讀到變動欄位的元件，React 在 value 換掉時讓每個讀它的元件都重新 render。

這課的路線：
  1. 逐層傳遞與 children：門市要一路傳到第 4 層時，先試著用 children 少掉中間層，不夠再用 context（開場問題的最小答案）。
  2. createContext、Provider 與 useXxx()：建立、提供、讀取三步，以及把 context 包成一個 Provider 元件加一個自訂 hook，忘了包 Provider 就直接報錯。
  3. 重新 render 的代價與控制：value 換了誰會 render，200 顆按鈕一起 render 怎麼用穩定的 value、拆開 context 解決。
  4. 依賴注入與怎麼選：用 context 換掉 API client，讓測試和展示頁不發真的請求，以及 props、children、context、store 各用在哪。
這課會用到：
  • 第 1 課：父元件 render 時，子元件預設全部跟著 render；React 用 Object.is 判斷值有沒有變，新建的物件永遠算「變了」。
  • 第 9 課的自訂 hook 與 useCallback：自訂 hook 是 use 開頭、裡面呼叫其他 hook 的函式；useCallback 讓函式在依賴沒變時維持同一個參考。
  • 第 10 課的 compound components：Tabs、Tab 這種一組一起用的元件，由外層擁有 state，透過 context 交給裡面的元件。

問題：逐層傳遞，以及先試試 children

逐層傳遞（prop drilling）是指：為了讓很深的元件拿到資料，中間每一層都要接收一個 prop、再傳給下一層。中間的元件因此知道了它不需要知道的東西。

React 官方文件在介紹 Context 之前，先建議兩件事：

  1. 先傳 props。兩三層、而且中間的元件本來就會用到時，props 最清楚，看元件的宣告就知道它需要什麼。
  2. 用 children 減少層數（第 10 課）。中間層只是排版時，讓它收 children，由上層直接把需要資料的元件放進去：
// ✗ Layout、MenuPage 只是轉手
<Layout store={store} />

// ✓ 中間層只管排版，store 直接交給用的人
<Layout>
  <MenuPage>
    <PriceTag store={store} />
  </MenuPage>
</Layout>

都不夠用時才輪到 Context：同一份資料很多地方要讀（目前門市、登入的店員、主題、語系），而且分散在不同層、不同分支。

createContext、Provider 與 use

Context 分三步：建立、提供、讀取。

import { createContext, use, useState } from 'react'

type Store = { id: number; name: string }

// 1. 建立：在元件外面呼叫，參數是預設值
const StoreContext = createContext<Store | null>(null)

// 2. 提供：React 19 直接把 context 當元件用，value 是要給後代的值
function App() {
  const [store, setStore] = useState<Store>({ id: 1, name: '總店' })
  return (
    <StoreContext value={store}>
      <Layout />
    </StoreContext>
  )
}

// 3. 讀取：任何一層後代
function PriceTag() {
  const store = use(StoreContext)
  return <p>價格標籤：{store?.name}</p>
}
  • context 物件本身不存資料（官方文件），只代表「哪一個 context」；值放在元件樹上的 Provider（提供者）裡，同一個 context 可以在不同地方提供不同的值。
  • <StoreContext value> 是 React 19 的寫法（第 10 課的 Tabs 用過）。舊專案會看到 <StoreContext.Provider value>，在 19.3.1 裡 StoreContext.Provider === StoreContext（實測），效果相同。
  • use(StoreContext) 效果跟 useContext(StoreContext) 一樣，差別是 use 可以寫在 if 和迴圈裡（官方文件；第 9 課的其他 hook 都不行）。它只能在元件或自訂 hook 裡呼叫，Server Components（第 22 課）不支援用它讀 context。這門課統一寫 use。

找值的規則（React 19.3.1 實測，與官方文件一致）：

  • 往上找最近的 Provider：好幾層都提供同一個 context 時，拿離自己最近的那一個，中間層可以替自己的子樹蓋掉上面的值。兄弟元件提供的值讀不到。
  • 看不到自己 render 的 Provider：元件裡先 use(Theme) 再 return <Theme value="dark">，讀到的是上面的值（或預設值），不是 dark。Provider 要在讀的元件「上面」。
  • 預設值只在上面完全沒有 Provider 時使用，而且固定不變。官方文件建議：沒有合理的預設值就給 null。
Vue provide／injectReact Context
key字串或 InjectionKey（Symbol）createContext() 回傳的物件，比的是同一個物件
提供setup 裡 provide(KEY, value)render 裡回傳 <Ctx value={…}>

最大的差別在「值怎麼更新」。Vue 交出 ref，之後改 .value 就好；React 的 value 跟 props 一樣是這次 render 的快照，要換值就讓 Provider 重新 render，通常是把值放在 Provider 所在元件的 state。直接改 value 物件的屬性，畫面不會變（實測：store.name 改成分店，畫面還是總店），跟第 3 課直接改 state 一樣。

Provider 元件與 useXxx()：把 context 藏起來

上面的 PriceTag 每次都要處理 null（store?.name），忘了放 Provider 時也只會靜靜顯示空白。資深的寫法跟 Vue 課的 provideCurrentStore()／useCurrentStore() 一樣：一個功能一個檔案，context 不 export，只公開一個 Provider 元件和一個自訂 hook。

// current-store.tsx
type CurrentStore = { store: Store; switchStore: (id: number) => void }

const CurrentStoreContext = createContext<CurrentStore | null>(null)   // 不 export

export function CurrentStoreProvider({ initialId, children }: { initialId: number; children: ReactNode }) {
  const [store, setStore] = useState(() => findStore(initialId))
  const value = { store, switchStore: (id: number) => setStore(findStore(id)) }
  return <CurrentStoreContext value={value}>{children}</CurrentStoreContext>
}

export function useCurrentStore(): CurrentStore {
  const current = use(CurrentStoreContext)
  if (!current) throw new Error('useCurrentStore() 必須在 <CurrentStoreProvider> 之下使用')
  return current   // 型別是 CurrentStore，呼叫的人不用再檢查 null
}
  • state 放在 Provider 元件裡：跟第 10 課的 Tabs 一樣，每個 Provider 各有一份；放在模組層級的變數會共用一份，改了也不會 render。
  • 修改只透過 switchStore：後代拿到的是快照，改不到 state，相當於 Vue 課的 readonly 加修改函式，React 不用另外包。驗證 id、記錄 log、同步到網址都只改這裡。findStore 找不到就丟錯，要在 setStore 之前丟，門市才不會變成 undefined。
  • 錯誤在源頭爆：不要拿總店或空函式當預設值，忘了放 Provider 時畫面照樣顯示總店、按切換沒反應，很難發現。

第 10 課的 <Tabs> 就是這個結構：Tabs 擁有選取狀態並提供 context，Tab 用找不到 Provider 就丟錯的 useTabs() 讀它。

💡 實務上：你每天用的 useXxx() 很多就是 context
React Router 的 useNavigate()（第 18 課）、TanStack Query 的 useQueryClient()（第 15 課）都要在對應的 Provider 底下才能用，忘了包就會丟錯，例如 React Router 8.5.1 的 useNavigate() may be used only in the context of a <Router> component.、TanStack Query 5.106.1 的 No QueryClient set, use QueryClientProvider to set one。看到這種錯誤，先檢查元件樹上有沒有對應的 Provider、是不是放到讀的元件下面或旁邊了。自己寫時只 export Provider、hook 和型別；review 時看到元件直接 use(SomeContext)，可以請對方改走 hook。

重新 render 的代價：value 換了，誰會 render

官方文件寫得很直接：Provider 收到不同的 value（用 Object.is 比較）時，React 會重新 render 底下所有讀這個 context 的元件，而且 memo 擋不住。

拿這段程式實測（React 19.3.1）。App 有一個跟登入無關的計數器，value 直接寫在 JSX 裡：

const Reader = memo(function Reader() { use(SessionContext); return … })
const Plain = memo(function Plain() { return … })   // 不讀 context

function App() {
  const [n, setN] = useState(0)
  return (
    <SessionContext value={{ staff: '王小明' }}>   {/* 每次 render 都是新物件 */}
      <button onClick={() => setN(n + 1)}>+</button>
      <Reader />
      <Plain />
    </SessionContext>
  )
}

按兩次按鈕：Plain 只 render 1 次（memo 生效），Reader render 了 3 次。staff 一直是王小明，但 {{ staff: '王小明' }} 每次都是新物件，Object.is 判定不同，讀它的元件就重新 render，memo 只比 props，不管 context。

反過來，Provider 的 state 變了，底下沒讀 context 的元件不一定會 render。關鍵在 children 是誰建立的：

實測：<Provider><Layout><Reader /></Layout><Footer /></Provider>，Provider 內部的 state 改變之後，Reader render 2 次，Layout、Footer 都只有 1 次。但如果把同樣的子樹直接寫在 Provider 元件的 return 裡，三個都 render 2 次，這是第 1 課的「父元件 render，子元件跟著 render」，跟 context 無關。這就是 Provider 元件都寫成 {children} 的原因。

對照 Vue：提供的是 ref，只有讀了 store.value.name 的元件被追蹤、被更新。React 的 use(Ctx) 一次拿整個 value，不能只訂閱其中一個欄位。所以 React 的 context 要注意兩件事：value 沒變時要是同一個參考，以及變化頻率不同的東西不要放在同一個 value。

控制代價：穩定的 value、拆開 context

value 用 useMemo 包住

登入狀態的 Provider 除了 staff，還有一個跟登入無關的公告 state：

function SessionProvider({ children }: { children: ReactNode }) {
  const [staff, setStaff] = useState<string | null>(null)
  const [noticeOpen, setNoticeOpen] = useState(true)

  // staff 沒變就回傳上一次的物件
  const value = useMemo(
    () => ({ staff, login: (name: string) => setStaff(name), logout: () => setStaff(null) }),
    [staff],
  )

  return (
    <SessionContext value={value}>
      {noticeOpen && <Notice onClose={() => setNoticeOpen(false)} />}
      {children}
    </SessionContext>
  )
}

useMemo(計算函式, 依賴陣列) 快取計算結果，依賴沒變就回傳上一次的值（第 9 課的 useCallback 是它快取函式的特例）。關閉公告、或外層元件讓 SessionProvider 重新 render 時，staff 沒變，value 是同一個物件，讀 session 的元件都不 render；登入之後 staff 變了，value 換新，每個讀它的元件各 render 一次。

  • setStaff 的參考在元件的整個生命期都不變（React 19.3.1 實測，跟第 8 課的 dispatch 一樣），所以 login、logout 不用另外包 useCallback，依賴陣列也不用列它；lint 的 exhaustive-deps 知道這件事。
  • 半套修法：只把 login、logout 包 useCallback，value 還是 {{ staff, login, logout }}，外層物件每次都新。
  • 依賴多放 noticeOpen，關公告又換新；寫成空陣列，登入後讀到的 staff 還是 null。照 lint 列出真正用到的值。

state 與 dispatch 分成兩個 context

購物車用第 8 課的 useReducer，把 { lines, dispatch } 用 useMemo 包起來提供。問題是 lines 本來就會變：每加一杯，value 換新，連只需要 dispatch 的「加入」按鈕也跟著 render，菜單 200 個商品就是 200 顆按鈕。

官方文件的做法是拆成兩個 context。第 8 課說過 dispatch 的參考不會變，直接當 value：

const CartContext = createContext<readonly CartLine[] | null>(null)
const CartDispatchContext = createContext<Dispatch<CartAction> | null>(null)

export function CartProvider({ children }: { children: ReactNode }) {
  const [lines, dispatch] = useReducer(cartReducer, [])
  return (
    <CartContext value={lines}>
      <CartDispatchContext value={dispatch}>{children}</CartDispatchContext>
    </CartContext>
  )
}
// useCart() 讀 CartContext；useCartDispatch() 只讀 CartDispatchContext

現在加入商品時，只有讀 lines 的購物車摘要 render，200 顆按鈕都不動。要守住這個效果：dispatch 不能再包成 {{ dispatch }} 或 action => dispatch(action)（每次 render 都是新的）；useCartDispatch() 裡也不能為了檢查 Provider 去讀 CartContext，use 讀了哪個 context 就訂閱了哪個。

同樣的想法可以推廣：依變化頻率拆 context。主題、語系一天變不到一次，可以放一起；每秒更新的叫號、輸入框的文字不適合放 context，放在用它的元件裡就好。

💡 實務上：先量，再拆
小型後台裡，沒包 useMemo 的 context 多 render 幾個元件，使用者感覺不到；官方文件也把它歸為效能優化。值得處理的是：讀它的元件很多（列表的每一列）或 render 很重，而且 value 常換。先量（這課的練習用計數器數 render 次數，Profiler 在第 19 課），再決定包 useMemo、拆 context 或改用有 selector 的 store。拆太細，一個功能包五層 Provider，閱讀成本也是代價。

依賴注入：用 context 換掉 API client

依賴注入（dependency injection，DI）：元件需要的東西不是自己 import 或建立，而是由外部交給它。看這個元件：

import { realClient } from './real-client.ts'   // ✗ 寫死用哪個 client

export function MenuCount() {
  useEffect(() => {
    realClient.getMenu({ signal }) …
  }, [])
}

它和「真的連到後端」綁死了：測試會真的發請求，展示頁想用假資料也得改元件。Vue 課用 app.provide 和外掛解決；React 沒有 app 層級的 provide，做法是在最外層包一個 Provider：

const ApiContext = createContext<MenuApi | null>(null)

export function ApiProvider({ api, children }: { api: MenuApi; children: ReactNode }) {
  return <ApiContext value={api}>{children}</ApiContext>
}
export function useApi(): MenuApi { /* use(ApiContext)，null 就丟錯 */ }

// main.tsx：正式環境
<ApiProvider api={realClient}><App /></ApiProvider>

// 測試：換成假的
render(<ApiProvider api={fakeApi}><MenuCount /></ApiProvider>)
// 或 render(<MenuCount />, { wrapper: ({ children }) => <ApiProvider api={fakeApi}>{children}</ApiProvider> })
  • value 直接用 prop 的 api：它本身就是穩定的參考。不要複製到 state，useState(api) 只採用第一次的值（第 6 課）。
  • effect 要把 api 列進依賴：useApi() 拿到的是響應值。Provider 換了 api，effect 要清掉舊請求、用新的 api 重抓。
  • 不要拿 realClient 當預設值：忘了放 ApiProvider 時，測試會偷偷連到正式環境。
  • 巢狀就是覆寫：展示區塊外面再包一層 <ApiProvider api={demoApi}>，只有那一塊用假資料。存在模組變數就做不到。
💡 實務上：哪些東西值得注入
值得注入的是會碰外部世界、或不同環境要換掉的東西：API client、記錄器（正式環境送到監控服務，開發時印在 console）、功能開關、多語系。formatPrice() 這種純函式直接 import。判斷時問一句：寫測試或做展示頁時，我需要把它換掉嗎？TanStack Query 的 QueryClientProvider 就是這個模式，用了它就不要再把伺服器資料自己放進 context。

怎麼選：props、children、context、store

工具適合代價
props一兩層、中間元件本來就會用層數多時每層都要改
children／組合中間層只是排版上層的 JSX 變長
Context很多地方要讀、很少變的值：目前門市、登入者、主題、語系、注入的 API client；compound components 的共享狀態value 一換，所有讀它的元件都 render；資料從哪來要往上找 Provider
Zustand 這類 store（第 14 課）常變、很多元件各讀一小部分的前端狀態多一個套件與它的寫法
TanStack Query（第 15 課）從伺服器來的資料要學它的快取與失效規則

Zustand 讓元件用 selector 只取需要的欄位，那個欄位變了才 render，補上 context 缺的那一塊。Context 對應的是 Vue 的 provide／inject，不是 Pinia；第 8 課提過的「context 加 reducer」適合狀態不大、讀的元件不多的情況。

練習

在 learn/ 執行 node check.mjs react 11。測試會用計數器數每個元件被呼叫幾次，檢查 value 穩不穩定；練習 1 會跑 tsc，練習 2、4 會跑 react-hooks 的 lint，各要 1～2 秒。

練習 1：完成 CurrentStoreProvider 與 useCurrentStore()。用 createContext 建立 context，預設值給 null。<CurrentStoreProvider initialId={1}> 用 state 記住目前門市（用 initialId 從 STORES 找），把 { store, switchStore } 提供給底下所有元件。useCurrentStore() 回傳最近一層 Provider 的值，回傳型別是 CurrentStore（不含 null、不是 any）；上面沒有 Provider 時丟出 Error('useCurrentStore() 必須在 <CurrentStoreProvider> 之下使用')。switchStore(id) 換成那一家門市，所有讀它的元件都更新；STORES 裡沒有這個 id 時丟出 Error(`找不到門市 ${id}`)，目前門市不變。巢狀時讀最近的那一層，並排的兩個 Provider 各自獨立（不能用模組層級的變數，也不能直接改門市物件的屬性）。

練習 2：SessionProvider 每次 render 都新建 value 物件。修改它：staff 沒變時 value 要是同一個物件，按「關閉公告」、外層重新 render，都不能讓呼叫 useSession() 的元件重新 render；login(name)、logout() 之後，每個讀 session 的元件都拿到新的 staff（各 render 一次）。公告一開始顯示、按「關閉公告」後消失；兩個 SessionProvider 各自獨立；沒有 Provider 時照舊丟錯。react-hooks 的 lint 要通過，不能用 eslint-disable，也不能把 value 放在 ref 或模組層級的變數。

練習 3：把購物車拆成兩個 context：一個放 lines、一個放 dispatch，CartProvider 兩個都提供，useCart() 回傳 lines，useCartDispatch() 回傳 dispatch。只呼叫 useCartDispatch() 的元件（加入、清空按鈕），購物車變了也不能重新 render；CartProvider 自己重新 render、購物車沒變時，讀任一個 context 的元件都不 render。加入、移除、清空要正確；兩個 CartProvider 各自獨立。上面沒有 Provider 時，兩個 hook 分別丟出 Error('useCart() 必須在 <CartProvider> 之下使用') 與 Error('useCartDispatch() 必須在 <CartProvider> 之下使用')。不能把 dispatch 包成物件或箭頭函式當 value，useCartDispatch() 不能讀放 lines 的 context；cart-reducer.ts 不用改。

練習 4：完成 ApiProvider 與 useApi()，再讓 MenuCount 改用 useApi()，不再 import realClient。<ApiProvider api={…}> 把 api 提供給底下所有元件，api 這個 prop 換了，底下拿到的也要換；巢狀時用最近的一層，兩個 ApiProvider 互不影響（不能存在模組層級的變數）。useApi() 上面沒有 Provider 時丟出 Error('useApi() 必須在 <ApiProvider> 之下使用')，不能用 realClient 當預設值。MenuCount 其他行為不變：「載入中…」、「共 N 項商品」、失敗時 role="alert" 的「載入失敗」，呼叫 getMenu 時傳 { signal }，卸載或換 api 時 abort 上一個請求，被取消的請求不能改畫面；ApiProvider 換了 api 要用新的 api 重新載入。react-hooks 的 lint 要通過，不能用 eslint-disable。

練習 5：Reader 用 memo 包起來，沒有任何 props，裡面呼叫 use(SessionContext)。Provider 寫成 <SessionContext value={{ staff }}>，它所在的元件因為別的 state 重新 render，staff 沒變。Reader 會怎樣？

✓ React 用 Object.is 比較新舊 value，{{ staff }} 每次 render 都是新物件，所以每個讀這個 context 的元件都重新 render。memo 只比較 props，官方文件明確寫了它擋不住 context。b 錯在 React 不比較物件內容。修法是用 useMemo(() => ({ staff }), [staff])。

練習 6：CartProvider 寫成 return <CartContext value={lines}>{children}</CartContext>，App 寫 <CartProvider><Header /><CartSummary /></CartProvider>，只有 CartSummary 讀 context。加入一杯拿鐵時，誰會重新 render？

✓ state 在 CartProvider，它會 render；Header、CartSummary 是 App 建立、透過 children 傳進來的 element，CartProvider 重新 render 時拿到同一個 element，React 不會因此 render 它們。value 換了，React 再找出讀 context 的 CartSummary 讓它 render。a 是子樹直接寫在 CartProvider 的 return 裡才會發生；c 錯在 state 所在的元件一定會 render。

練習 7：ThemeArea 先寫 const theme = use(ThemeContext)，再 return <ThemeContext value="dark"><p>{theme}</p></ThemeContext>。上面沒有任何 Provider，預設值是 'light'。畫面顯示什麼？

✓ 官方文件：讀 context 時只看呼叫它的元件「上面」的 Provider，不看自己回傳的。這裡上面沒有 Provider，所以拿到預設值 light；包在這個 Provider 裡的子元件才讀得到 dark。這種寫法不會丟錯，只是讀不到，所以 c 也不對。

常見錯誤

  • 還沒試 props 和 children 就用 context：資料從哪來變得要往上找。兩三層用 props，中間層只排版就用 children。
  • value 直接寫 {{ … }}，或只把裡面的函式包 useCallback：外層物件每次都新，所有讀的元件跟著 render，memo 也擋不住。用 useMemo 包住整個 value。
  • 直接改 value 物件的屬性、或把 value 放在 ref 裡改：參考沒變，React 不會通知任何人。要換值就換 state。
  • 常變的和不常變的放在同一個 value：只需要 dispatch 的元件也跟著 render。拆成兩個 context，dispatch 直接當 value。
  • 拿「看起來合理」的東西當預設值（總店、空函式、正式環境的 API client）：忘了放 Provider 也不會發現。預設值給 null，在 hook 裡丟錯。
  • 把 state 或 api 存在模組層級的變數：並排、巢狀的 Provider 互相蓋掉，改了也不會 render。放在 Provider 元件的 state 或 props。

小結

  • Context 解決逐層傳遞；先試 props 和 children，很多地方要讀同一份、很少變的值時才用。
  • React 19：createContext(預設值) 建立，<Ctx value={…}> 提供，use(Ctx) 讀；往上找最近的 Provider，看不到自己 render 的那一個；Ctx.Provider 是舊寫法。
  • 一個功能一個檔案：context 不 export，只公開 Provider 元件與 useXxx()；預設值給 null，沒有 Provider 就丟錯；state 放在 Provider 元件裡，修改透過它提供的函式。
  • value 用 Object.is 比較，換了就讓所有讀它的元件 render，memo 擋不住；Provider 用 children 收子樹時，不讀 context 的元件會被跳過。
  • value 沒變時要是同一個參考（useMemo）；常變的與不常變的拆成不同 context，dispatch 直接當 value。
  • context 也是 React 的依賴注入：用 Provider 換掉 API client，元件的 effect 把注入的值列進依賴。
  • 跟 Vue 的差別：Vue 追蹤到欄位；React 以整個 value 為單位，要「只訂閱一部分」就改用有 selector 的 store。
