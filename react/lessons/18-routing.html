階段 4：狀態與資料 · 第 18 課

路由：React Router 的巢狀路由、loader 與守衛

咖啡店的網站一直只有一個網址：不管看菜單、看商品還是進後台，網址都是 /，客人沒辦法把「今日推薦」的商品頁傳給朋友。後來加了路由，又冒出三個問題：商品頁先閃一下「載入中…」才出現，網址是 /menu/abc 也照樣打 API，商品不存在時畫面一直停在「載入中…」；沒登入的人打開 /admin/orders，訂單已經抓了、後台也先畫出來一下，才被導去登入頁；被導走之後按上一頁，又回到後台再被導走一次。

這些問題的共同答案是：把版面、資料、守衛都掛在路由上，讓路由器在畫面出現之前就決定好「顯示哪些版面、資料是什麼、可不可以進來」。版本以 React Router 8.5.1 為準。

這課的路線：
  1. 一張路由表怎麼回答開場的三個問題，導航時路由器依序做哪些事（開場問題的最小答案）。
  2. 巢狀路由：版面為什麼換頁不重建，index 與 404 放哪裡。
  3. loader 與錯誤：資料抓完才進頁面、換頁時取消舊請求，抓不到時用 404 換掉這一塊。
  4. 守衛：用 middleware 在 loader 之前擋下，分清楚「去登入」和「沒有權限」。
  5. 搜尋放網址：loader 讀 ?q=，用 <Form> 送出，等待時保留舊畫面。
這課會用到：
  • 第 5 課的抓資料與競態：effect 裡抓資料，舊的回應可能蓋掉新的，要用 AbortController 取消。
  • 第 13 課的 Error Boundary：攔下底下元件丟出的錯誤，改顯示備用畫面，只換掉它包住的那一塊。
  • 第 14 課的 URL 狀態：要分享、按上一頁要還原的狀態放進網址的 query，畫面從網址算出來。
  • 第 4 課的 key：key 換了，React 丟掉舊元件、重新建立，非受控欄位會重新套用 defaultValue。

一張路由表：版面、資料、守衛都掛在路由上

開場的三個問題，各自對應路由物件上的一個屬性。最小版本長這樣：

import { createBrowserRouter } from 'react-router'
import { RouterProvider } from 'react-router/dom'

const router = createBrowserRouter([
  {
    path: '/',
    Component: Layout,                 // 版面：頁首一直在，頁面顯示在它的 <Outlet />
    children: [
      { index: true, Component: Home },
      {
        path: 'menu/:id',
        loader: productLoader,          // 資料：進頁面前先抓
        Component: ProductPage,
        ErrorBoundary: ProductError,    // 抓不到：只換掉這一塊
      },
      {
        path: 'admin',
        middleware: [requireUser],      // 守衛：在 loader 之前檢查
        Component: AdminLayout,
        children: [ … ],
      },
    ],
  },
])

createRoot(root).render(<RouterProvider router={router} />)

這種寫法在官方文件叫 Data Mode：路由表是一個陣列，交給 createBrowserRouter 建立路由器（router），再用 RouterProvider 放進畫面。React Router 8 拿掉了 react-router-dom 套件，全部從 react-router import；changelog 寫明 RouterProvider 在瀏覽器裡要從 react-router/dom import（它會用到 react-dom）。

巢狀路由：版面用 Outlet，換頁不重建

上一節的路由表裡，children 是巢狀路由。巢狀有兩層意思：網址一段一段接起來（/ ＋ admin ＋ orders），畫面也一層一層包起來（Layout 包 AdminLayout 包 OrdersPage）。外層元件用 <Outlet /> 標出「子路由顯示在這裡」：

import { NavLink, Outlet } from 'react-router'

function Layout() {
  return (
    <>
      <header>
        <nav aria-label="主選單">
          <NavLink to="/">首頁</NavLink>
          <NavLink to="/menu">菜單</NavLink>
        </nav>
        <input aria-label="搜尋草稿" />
      </header>
      <main>
        <Outlet />          {/* 子路由的頁面顯示在這裡 */}
      </main>
    </>
  )
}

const routes: RouteObject[] = [
  {
    path: '/',
    Component: Layout,
    children: [
      { index: true, Component: Home },          // 剛好是 /
      { path: 'menu', Component: MenuPage },     // /menu
      { path: 'menu/:id', Component: ProductPage },
      {
        path: 'admin',
        Component: AdminLayout,                  // 第二層版面，裡面也有 <Outlet />
        children: [
          { index: true, Component: AdminHome }, // 剛好是 /admin
          { path: 'orders', Component: OrdersPage },
        ],
      },
      { path: '*', Component: NotFound },        // 其他網址，頁首還在
    ],
  },
]

從 /menu 換到 /menu/2，兩次比對到的路由都是「Layout → 某一頁」。Layout 在元件樹上的位置和型別都沒變，React 就沿用它（第 1 課的規則），頁首搜尋框裡打到一半的字還在，只有 Outlet 裡的頁面換掉。這也是 :id 換了、ProductPage 被沿用的原因（Vue 課第 19 課「參數改變時，元件被重用」是同一件事）。

每個屬性的規則：

  • 子路由的 path 不以 / 開頭：寫相對路徑 'orders'，自動接在父路由後面。在 admin 底下寫 '/orders'，8.5.1 會丟出 Absolute route path "/orders" nested under path "/admin" is not valid.。
  • index: true：「剛好是父路由的網址」時顯示的子路由，例如 /admin 的總覽。不要把 AdminHome 直接寫在 AdminLayout 裡，那樣 /admin/orders 也會出現它。
  • 要共用版面的頁面放進同一個父路由的 children：把 { path: 'admin/orders' } 寫成和 admin 平行，網址對得到，但它不在 AdminLayout 裡，後台選單不見了。
  • '*' 放在 Layout 的 children：放在最外層、和 / 平行，找不到頁面時連頁首也沒有。/admin/nope 在 admin 底下對不到任何子路由，也會落到這個 '*'。
  • 元件用 Component 指定：給元件本身（Component: Home），不是 JSX。

從 Vue 來最容易寫出的錯，是不用巢狀路由，讓每一頁自己包版面：

// ✗ 每一頁各包一次
{ path: '/menu', Component: () => <Frame><MenuPage /></Frame> },
{ path: '/menu/:id', Component: () => <Frame><ProductPage /></Frame> },

畫面看起來一樣，但兩條路由的 Component 是不同的函式，換頁時 React 看到的是另一種元件，整個 Frame 連同頁首被丟掉重建，搜尋草稿跟著清空。版面只寫一次，放在父路由。

💡 實務上：路由表就是網站的地圖，先畫版面的層次
咖啡店的前台（頁首＋頁尾）、後台（左側選單）、結帳流程（只有步驟條）各是一層版面。開新頁面前先問「它在哪一層版面裡」，答案就是它在路由表的位置。code review 看到頁面元件自己 import 頁首，或同一個版面在好幾條路由各包一次，通常就是少了一層父路由。後台的 404 想顯示在後台選單旁邊時，在 admin 的 children 再放一個 '*'：比對時會選最深、最具體的那一條。

loader：資料抓完才進頁面

版面有了，接著處理商品頁的「先閃載入中」。原本的寫法是第 5 課的模式：元件先 render，effect 再抓資料，所以一定先畫出「載入中…」；id 是 abc 也照樣呼叫 getProduct(NaN)。loader 把抓資料移到路由上：

import { data, useLoaderData, type LoaderFunctionArgs } from 'react-router'

async function productLoader({ params, request }: LoaderFunctionArgs) {
  const id = params.id ?? ''
  if (!/^\d+$/.test(id)) throw data('找不到商品', { status: 404 })   // 不是編號就不打 API
  return api.getProduct(Number(id), { signal: request.signal })
}

function ProductPage() {
  const product = useLoaderData<typeof productLoader>()   // 一定已經有資料
  return <article><h1>{product.name}</h1><p>${product.price}</p></article>
}

loader 收到一個物件，這課用到的欄位：

  • params：路徑參數，值都是字串（或 undefined）。Number('abc') 是 NaN、Number('2.5') 是 2.5，所以先用 /^\d+$/ 確認是純數字，跟第 14 課說的 query 一樣當成外部輸入驗證。
  • request：一個標準的 Request。request.signal 是這次導航的 AbortSignal：使用者在 loader 還沒完成時又換到別頁，路由器會取消這次導航，signal 變成 aborted。把它傳給 fetch 或 API，舊請求就真的被取消，不用自己寫第 5 課的 AbortController。
  • url：要前往的網址（URL 物件），讀 query 用 url.searchParams。7.15 起從 unstable_url 改成正式的 url；也可以自己寫 new URL(request.url)。
  • context：middleware 放進去的值，守衛那一節會用到。

元件用 useLoaderData() 讀 loader 的回傳值。型別參數給 loader 函式本身（typeof productLoader），React Router 會取出它 resolve 的型別；loader 是由工廠函式產生時，寫 ReturnType<typeof 工廠> 拿到 loader 的型別。路由器等 loader 完成才 render 頁面，所以元件裡不需要 if (!product)，也不該出現「載入中…」。

幾個行為（官方文件，加上本機用 8.5.1 實測）：

  • 同一次導航的 loader 同時跑：進 /admin/orders 時，admin 和 orders 的 loader 一起開始，不會等父路由的 loader 先完成。實測父路由的 loader 還沒 resolve，子路由的 loader 已經執行了。
  • 不是每次導航都重跑每個 loader：Data Mode 預設只在「這條路由的參數變了」或「query 變了」時重跑（文件 shouldRevalidate）；從 /admin 點到 /admin/orders，admin 的 loader 不會再跑。實測從 /a 換到 /b，共同父路由的 loader 只跑過一次。
  • 第一次載入：loader 還沒完成時沒有任何頁面可以顯示，路由可以設 HydrateFallback 元件撐住這段時間；沒設時畫面是空的，Console 印出 No `HydrateFallback` element provided to render during initial hydration（實測）。練習的測試外層就用它顯示「準備中…」。之後的換頁不會用到它：舊頁面留著，直到新資料到齊。

Vue Router 沒有內建 loader，Vue 課第 19 課在元件裡抓資料。兩種做法的差別，就是開場那一下「載入中」：在元件裡抓，畫面先出現再等資料；用 loader，等資料到了才換頁。

💡 實務上：loader 決定「什麼時候抓」，快取還是交給 TanStack Query
loader 本身沒有快取：每次重跑都會打 API，回到上一頁也一樣。咖啡店的菜單這種很多頁共用、需要失效與樂觀更新的資料，常見做法是 loader 裡 await queryClient.ensureQueryData(…)（快取裡有新鮮的資料就直接用，沒有才抓），元件照第 15 課用 useQuery 讀同一個 queryKey：loader 管「進頁面前先開始抓」，Query 管快取與失效（TanStack Query 文件的 Router Integration 也提到這種整合）。只有一頁用、每次都要最新的資料（例如結帳前的庫存），直接在 loader 抓就好。loader 也會讓換頁變慢：一個慢的 API 擋住整頁，這時把次要的資料留給元件自己抓。

錯誤：throw data 與路由的 ErrorBoundary

loader 能保證資料到了才進頁面，那抓不到的時候呢？loader 或 middleware 丟出任何東西，路由器就不 render 這條路由的 Component，改 render 最近的 ErrorBoundary：先看這條路由自己有沒有，沒有就往父路由找。它是第 13 課 Error Boundary 的路由版，不用自己寫 class，錯誤用 useRouteError() 讀：

import { isRouteErrorResponse, Link, useRouteError } from 'react-router'

function ProductError() {
  const error = useRouteError()
  const message = isRouteErrorResponse(error) && error.status === 404
    ? '找不到商品'
    : `載入失敗：${error instanceof Error ? error.message : '未知的錯誤'}`
  return (
    <div role="alert">
      <p>{message}</p>
      <Link to="/menu">回菜單</Link>
    </div>
  )
}

{ path: 'menu/:id', loader: productLoader, Component: ProductPage, ErrorBoundary: ProductError }

錯誤分兩種，跟第 17 課「預期中與預期外」的分法一樣：

  • 預期中的「沒有這個東西」：throw data('找不到商品', { status: 404 })。官方文件把 404 列為少數「應該故意丟出」的情況。isRouteErrorResponse(error) 對它是 true，error.status 是 404，error.data 是第一個參數。
  • 預期外的錯誤（網路斷線、程式錯誤）：不要接，原樣丟出去，它就是一般的 Error，ErrorBoundary 顯示 error.message。

所以 API 的錯誤要分辨：只有「商品不存在」轉成 404，其他照樣丟出。

try {
  return await api.getProduct(Number(id), { signal: request.signal })
} catch (error) {
  if (error instanceof NotFoundError) throw data('找不到商品', { status: 404 })
  throw error                       // ✗ 不要全部當成 404：斷線時客人會以為商品下架了
}

不轉的話，NotFoundError 是一般的 Error，畫面顯示「載入失敗：找不到商品 99」，對客人來說像是系統壞了。

顯示時判斷 status，不要直接印 statusText。官方範例常寫 {error.status} {error.statusText}，但 data() 沒給 statusText 時，8.5.1 實測 404 的 statusText 是 Internal Server Error，畫面會出現「404 Internal Server Error」。給客人看的文字自己依 status 決定。

ErrorBoundary 要放在出錯的那條路由上。商品頁沒有自己的 ErrorBoundary，錯誤會一路往上冒到最外層，整個 Layout 連頁首都被換掉。放在商品頁的路由上，只有 <Outlet /> 那一塊變成錯誤畫面；點「回菜單」換到別的路由，錯誤畫面就消失。

💡 實務上：每一層版面都放一個 ErrorBoundary
常見的放法是最外層一個（整個 app 壞掉時至少有「重新整理」按鈕）、每個主要區塊一個（後台壞了，左側選單還在，店員可以去別頁）、重要的頁面再各一個。錯誤畫面一定要有離開的路：連結回列表或首頁。預期外的錯誤要送到監控（第 24 課），404 則通常不用：客人亂打網址很正常，全送上去會淹沒真正的錯誤。

守衛：middleware 在 loader 之前擋下

loader 解決了資料，後台的守衛還沒解決。原本寫在 AdminLayout 的 effect 裡：

function AdminLayout() {
  const navigate = useNavigate()
  useEffect(() => {
    if (!auth.user) navigate('/login')     // ✗ 太晚了
  })
  return …
}

effect 在 render 與 commit 之後才執行（第 5 課），這時路由器已經跑完 orders 的 loader（訂單已經抓了），後台也畫出來一次，網址 /admin/orders 已經進了歷史紀錄。navigate('/login') 再新增一筆，按上一頁回到 /admin/orders，又被導走一次。useNavigate 本身沒錯，它適合「使用者做了某件事之後換頁」，例如登入成功後；它和其他 React Router 的 hook 一樣要在 Router 底下才能用（第 11 課）。

改成 admin 路由上的 middleware：在這條路由與它所有子路由的 loader 之前執行的函式。React Router 7.9 把它變成正式 API，8.0 起一律啟用，不用再開 future flag（8.0.0 changelog）。

import { createContext, redirect, type MiddlewareFunction } from 'react-router'

// 路由的 context（不是 React 的 createContext）：middleware 放進去，底下的 loader 拿出來
const userContext = createContext<User>()

const requireUser: MiddlewareFunction = ({ url, context }) => {
  const user = auth.user
  if (!user) {
    const params = new URLSearchParams({ redirect: url.pathname + url.search })
    throw redirect(`/login?${params}`)
  }
  context.set(userContext, user)
}

{
  path: 'admin',
  middleware: [requireUser],
  Component: AdminLayout,
  children: [
    { index: true, Component: AdminHome },
    {
      path: 'orders',
      loader: ({ request, context }) =>
        api.getOrders(context.get(userContext).storeId, { signal: request.signal }),
      Component: OrdersPage,
    },
  ],
}

官方文件說明的行為，對應開場的問題：

  • 在 loader 之前，由外到內：父路由的 middleware 先跑，再到子路由的，全部通過才執行 loader。throw redirect(…) 之後，orders 的 loader 和整個後台都不會執行。
  • 每次導航都跑：文件寫明 client middleware 在每次導航都執行，不管有沒有 loader 要跑。在後台登出（例如在別的分頁），再點後台選單的「總覽」，還是會被擋下。
  • 被擋下的網址不進歷史紀錄：導航還沒完成就轉去 /login，/admin/orders 從來沒有成為目前的網址，按上一頁回到進後台之前的頁面（練習 3 的測試會確認）。
  • 用 context 傳給 loader：createContext<User>() 建立一把有型別的鑰匙，context.set 放、context.get 拿（沒放過又沒有預設值時，get 會丟錯）。loader 拿到的一定是通過檢查的那個使用者。

為什麼不放在別的地方：

放在問題
元件的 effect頁面先 render、loader 先跑完，網址已經進了歷史紀錄
admin 的 loader子路由的 loader 同時在跑，擋不住；在後台子頁之間切換時它不重跑（上一節的兩個行為）。官方文件明講父路由的 loader 不能「保護」子路由
每個子路由各放一次 middleware沒放到的就沒擋，例如沒有 loader 的 /admin 總覽；新加的頁面也容易忘記
admin 的 middleware✓ 底下每一頁、每次導航都會先經過它

redirect 參數有兩個細節。一是要包含 query：店員打開的是 /admin/orders?status=ready&page=2，只記 url.pathname，登入後回去篩選就不見了。二是要編碼：直接接成 /login?redirect=/admin/orders?status=ready&page=2，瀏覽器把 &page=2 當成 /login 自己的參數，redirect 只剩 /admin/orders?status=ready。new URLSearchParams({ redirect: … }) 會把它編碼成 redirect=%2Fadmin%2Forders%3Fstatus%3Dready%26page%3D2。登入頁讀到之後，要確認它是以 / 開頭的站內路徑再導過去，不然別人可以做一個登入後跳到釣魚網站的連結（開放式重新導向，open redirect）。

403：知道你是誰，但你不能做

價目表只有店長能改。店員已經登入了，把他導去登入頁沒有用（登入後還是店員，還可能形成迴圈）。這是 403，丟給 ErrorBoundary 顯示：

const requireManager: MiddlewareFunction = ({ context }) => {
  if (context.get(userContext).role !== 'manager') throw data('沒有權限', { status: 403 })
}

{ path: 'prices', middleware: [requireManager], loader: …, Component: PricesPage }
// admin 路由加上 ErrorBoundary：403 顯示「沒有權限」，外層頁首還在

requireManager 從 context 讀使用者，因為父路由的 requireUser 一定先跑過；它丟出 403 時，prices 的 loader 不會執行，價目表的 API 一次都沒被呼叫。在 PricesPage 裡寫 role === 'manager' ? <PricesPage /> : 沒有權限 擋不住：loader 已經把價目表抓回來了。

💡 實務上：前端守衛是體驗，權限要由後端判斷
middleware 讓沒權限的人看不到畫面、不會白打 API，但它跑在瀏覽器，改一下程式就繞過了。訂單、價目表的 API 一定要自己檢查登入與角色，前端收到 401 時導去登入、收到 403 時顯示沒有權限（和這裡同一套 ErrorBoundary）。登入狀態通常在 middleware 裡向後端確認一次（例如呼叫 /me），放進 context 給底下的 loader 用，不要讓每個 loader 各自查一次。資安會問的兩件事：redirect 參數有沒有限制在站內，以及登出後按上一頁會不會看到快取的後台畫面。

搜尋放網址：loader 讀 ?q=，送出用 <Form>

最後把 loader 和第 14 課的 URL 狀態接起來。第 14 課說搜尋字要放網址才能分享、按上一頁才會還原；現在搜尋結果也交給 loader，畫面完全從網址算出來：

import { Form, useLoaderData, useNavigation, type LoaderFunctionArgs } from 'react-router'

async function menuLoader({ url, request }: LoaderFunctionArgs) {
  const q = (url.searchParams.get('q') ?? '').trim()
  const products = q
    ? await api.search(q, { signal: request.signal })
    : await api.getMenu({ signal: request.signal })
  return { q, products }                 // q 也回傳，給輸入框當預設值
}

function MenuSearch() {
  const { q, products } = useLoaderData<typeof menuLoader>()
  const navigation = useNavigation()
  return (
    <section>
      <Form role="search">
        <input key={q} name="q" aria-label="搜尋商品" defaultValue={q} />
        <button>搜尋</button>
      </Form>
      {navigation.state === 'loading' && <p role="status">更新中…</p>}
      {products.length === 0
        ? <p>沒有符合的商品</p>
        : <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>}
    </section>
  )
}

從上到下看：

  1. <Form>：React Router 的表單元件，預設是 GET。送出時把有 name 的欄位變成 query，導航到 /menu?q=茶：新增一筆歷史紀錄，query 變了所以 loader 重跑。和 HTML 原本的 GET 表單一樣，只是不重新載入整頁。
  2. trim 在 loader 裡做：?q=%20拿%20 搜尋「拿」，只有空白的 q 當成沒搜尋。網址是使用者可以亂改的輸入，整理放在讀網址的地方，不是送出的地方。
  3. key={q}：defaultValue 只在輸入框第一次建立時套用（第 4 課）。按上一頁回到 ?q=拿，loader 給了新的 q，但同一個輸入框還顯示剛剛打的「可頌」。key 跟著 q，q 一變就重建輸入框，顯示網址上的值。
  4. useNavigation().state：'idle'、'loading' 或 'submitting'（POST 這類表單送出時）。GET 的 Form 和點連結一樣是 loading。等待新結果時，舊的清單還是 loader 上一次的資料，加一行 role="status" 的「更新中…」就好；用它換掉整個清單，畫面會一閃一閃。
  5. request.signal：連續搜尋兩次，第二次導航開始時第一次被取消，第一次的 search 請求跟著中止，不會出現舊結果蓋掉新結果。

這裡沒有任何 useState 或 useEffect。如果改成「q 放網址、但在 effect 裡抓」，分享沒問題了，但又回到每次先畫空的再等資料，取消、競態也要自己處理。

練習

在 learn/ 執行 node check.mjs react 18，檔案在 react/practice/work/18/。測試用 createMemoryRouter（網址只存在記憶體裡的路由器，用法和 createBrowserRouter 一樣）建立路由器，外面包一層測試用的版面：頁首寫「測試頁首」、顯示目前的網址，第一次載入時顯示「準備中…」（HydrateFallback），還有 / 首頁和 /login 登入頁。練習 2、4 的假 API 由測試決定什麼時候回傳，並記錄每次呼叫收到的 signal。四題互不相依。

練習 1：routes.tsx 只有一條 '/' 路由，不管網址是什麼都只看到頁首。寫出路由表（頁面元件在 pages.tsx，不用改）：/ 用 Layout 當版面，頁面顯示在它的 <main> 裡：/ 是 Home、/menu 是 MenuPage、/menu/:id 是 ProductPage。/admin 是 Layout 裡的第二層版面 AdminLayout，內容顯示在它的 <section> 裡：/admin 是 AdminHome、/admin/orders 是 OrdersPage。其他任何網址（包括 /admin/nope）顯示 NotFound，頁首還在。換頁時版面不能重建：在頁首的搜尋草稿打到一半，點選單換頁後打的字還在；在後台兩頁之間切換，後台選單是同一個元素。

練習 2：ProductPage 在 effect 裡抓資料。改寫 productRoute(api)，回傳這條路由的 { loader, Component, ErrorBoundary }：loader 從 params.id 讀商品編號，不是純數字（abc、-1、2.5）時不呼叫 API，throw data('找不到商品', { status: 404 })；否則呼叫 api.getProduct(編號, { signal: request.signal })，換到別的商品時還沒回來的舊請求要被取消。API 丟出 NotFoundError 時一樣丟 404，其他錯誤原樣丟出。Component 用 useLoaderData 顯示 <h1>品名</h1> 和「$價格」，整個過程不能出現「載入中…」。ErrorBoundary 顯示 role="alert"：404 是「找不到商品」，其他錯誤是「載入失敗：錯誤訊息」，裡面放一個連到 /menu 的「回菜單」連結；錯誤只換掉商品頁這一塊，測試的頁首要還在。

練習 3：後台的守衛寫在 AdminLayout 的 effect 裡。改寫 adminRoute(auth, api)（回傳 path 是 'admin' 的路由，auth.user 是 null 代表沒登入，測試會直接改它）：/admin 底下每一頁都要登入，沒登入時導到 /login?redirect=原本的路徑和查詢字串（用 URLSearchParams 編碼），被擋下時後台的畫面一次都不能出現、API 也不能被呼叫；每次導航都要重新檢查（在後台登出後點後台選單也會被擋下）；被導去登入頁後按上一頁，回到進後台之前的頁面。/admin/orders 的 loader 呼叫 api.getOrders(登入者的 storeId, { signal: request.signal })。/admin/prices 只有 role 是 'manager' 的人能進，其他人不呼叫 api.getPrices，網址留在 /admin/prices，顯示 role="alert" 的「沒有權限」，測試的頁首還在。

練習 4：菜單搜尋的結果放在元件的 state、在 effect 裡抓。改寫 menuRoute(api)，回傳 { loader, Component }：loader 從網址讀 ?q= 並去掉前後空白，空字串時呼叫 api.getMenu({ signal })，否則呼叫 api.search(q, { signal })，signal 用 request.signal（快速搜尋兩次時，第一次的請求要被取消）。元件用 useLoaderData 讀結果：<ul> 裡每個商品一個 <li>（品名），沒有結果時顯示「沒有符合的商品」。搜尋表單用 <Form role="search">，輸入框 name="q"、aria-label="搜尋商品"，按「搜尋」後網址變成 ?q=… 並新增一筆歷史紀錄。新結果還沒回來時保留目前的清單，另外顯示 role="status" 的「更新中…」，回來後消失。按上一頁時，清單和輸入框都回到上一次的搜尋。

練習 5：同事把登入檢查寫在 admin 路由的 loader：沒登入就 throw redirect('/login')。沒登入的人直接打開 /admin/orders，會發生什麼？

✓ 同一次導航要跑的 loader 是同時開始的，父路由的 loader 擋不住子路由的 loader；而且在後台子頁之間切換時，admin 的 loader 不會重跑。守衛要放在 middleware，它在所有 loader 之前、每次導航都執行。a 是最常見的誤解；loader 可以丟 redirect，b 錯；loader 有丟錯或 redirect 時頁面不會 render，d 錯。

練習 6：店員（已登入）打開只有店長能看的 /admin/prices，middleware 該怎麼處理？

✓ 403 是「知道你是誰，但你不能做」，導去登入頁不會改變什麼，登入後還可能又被導回來形成迴圈；401（沒登入）才導去登入頁。c 的畫面看起來對，但 loader 已經呼叫了價目表的 API，資料也到了瀏覽器。

練習 7：搜尋框寫成 <input name="q" defaultValue={q} />（q 來自 useLoaderData）。客人先搜「拿」，再搜「可頌」，然後按上一頁。輸入框顯示什麼？

✓ loader 重跑、清單回到 ?q=拿 的結果，但輸入框是同一個非受控元素，defaultValue 改了也不會影響目前的值。給它 key={q}，q 一變就重建，顯示網址上的值。b 是把 defaultValue 當成 value 的誤解；React Router 的上一頁不會重新載入整頁，c 錯。

常見錯誤

  • 版面裡沒有 <Outlet />：子路由對到了，但沒有地方顯示，只看到版面。
  • 每一頁各包一次版面：每條路由的 Component 是不同的元件，換頁時版面整個重建，裡面的 state 跟著重來。版面放在父路由，頁面放在它的 children。
  • 子路由的 path 以 / 開頭：在 admin 底下寫 '/orders' 會丟錯。寫相對路徑 'orders'。
  • 要共用版面的頁面沒有放進 children：'admin/orders' 和 admin 平行，網址對得到，但後台選單不見了。
  • 首頁內容直接寫在版面裡：每一頁都會出現它。用 index: true 的子路由。
  • '*' 和 '/' 平行：找不到頁面時連頁首也沒有。放進 Layout 的 children。
  • loader 改了，元件還在 effect 裡抓：畫面先出現再等資料、多打一次 API。資料只從 useLoaderData 讀。
  • 沒有把 request.signal 傳給 API：換頁或連續搜尋時，舊請求照樣跑完、浪費流量。每個 loader 都傳。
  • 沒驗證 params：Number('abc') 是 NaN，照樣打 API。先確認格式，不對就丟 404。
  • API 的「不存在」沒轉成 404：顯示成「載入失敗」，像是系統壞了。
  • 所有錯誤都當成 404：斷線也顯示「找不到商品」。只轉不存在的錯誤，其他原樣丟出。
  • 出錯的路由沒有 ErrorBoundary：錯誤冒到最外層，整個畫面被換掉。
  • 錯誤畫面直接印 statusText：data() 沒給 statusText 時，404 也會顯示 Internal Server Error。依 status 決定文字。
  • 在元件的 effect 裡守衛：頁面先 render、loader 先跑、網址進了歷史紀錄。用 middleware。
  • 守衛放在父路由的 loader：子路由的 loader 同時在跑，切換子頁時它也不重跑。
  • 每個子路由各放一次守衛：漏掉沒有 loader 的頁面和新加的頁面。放在 admin 這一層。
  • redirect 參數只記 pathname，或沒有編碼：查詢條件不見，或 & 後面變成登入頁自己的參數。用 URLSearchParams 包 url.pathname + url.search。
  • 沒有權限時導去登入頁：已登入的人登入也沒用。丟 403 給 ErrorBoundary。
  • 在頁面元件裡判斷角色：loader 已經把資料抓回來了。在 middleware 擋。
  • 搜尋字沒有 trim：?q=%20拿%20 搜不到東西。在 loader 整理。
  • 非受控輸入框沒有 key={q}：按上一頁時清單回去了，輸入框還是剛剛打的字。
  • 載入中換掉整個清單，或完全沒有提示：用 useNavigation().state === 'loading' 另外顯示「更新中…」，舊清單留著。

小結

  • Data Mode：路由物件陣列交給 createBrowserRouter，RouterProvider 放進畫面（8.x 從 react-router/dom import）。一次導航：比對 → middleware（由外到內）→ loader（同時）→ render。
  • 巢狀路由：子路由寫相對 path，顯示在父元件的 <Outlet />；index: true 是剛好父路由的網址，'*' 放在版面底下。版面只寫一次，換頁時不重建。
  • loader：用 params（先驗證）、url.searchParams 讀輸入，把 request.signal 傳給 API，元件用 useLoaderData 讀；預設只在參數或 query 改變時重跑。
  • 錯誤：預期中的「不存在」throw data(…, { status: 404 })，其他原樣丟出；ErrorBoundary 放在出錯的路由，用 isRouteErrorResponse 與 status 判斷，給離開的連結。
  • 守衛：middleware 放在要保護的那一層，每次導航、在 loader 之前執行；沒登入 throw redirect（redirect 參數編碼），沒權限 throw 403；用路由的 createContext 把使用者交給 loader。真正的權限檢查在後端。
  • 搜尋放網址：GET 的 <Form> 送出、loader 讀 ?q=，輸入框 key={q}，等待時用 useNavigation 顯示更新中。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 8：菜單頁用 useQuery 抓到商品後，同事再把它存進 Zustand 的 store，讓購物車和結帳頁都讀 store。之後店長改了拿鐵的價格，會出什麼問題？

✓ 正本在伺服器的資料交給 TanStack Query，每份狀態只有一份；複製一份到 store，就要自己負責同步，通常會漏。購物車和結帳頁直接用同一個 queryKey 的 useQuery 讀，失效時一起更新。a 錯在選 s.products 拿到的是同一個參考，Object.is 相等；只有每次建立新物件或新陣列的 selector 才會無限迴圈。（第 14、15 課）

練習 9：在 Vue 裡用 Pinia，元件只讀購物車件數，改備註不會讓它更新。React 的元件寫 const { lines } = useCartStore() 算件數，改備註卻會重新 render，差別在哪？

✓ React 沒有依賴追蹤：store 一變就用 Object.is 比較每個元件選的值，選整個 state 時任何欄位變都是新物件。改成 useCartStore(selectCount)，只有件數改變時才重新 render。c 錯在 store 的通知直接送到訂閱的元件，memo 擋不了。（第 14 課）

練習 10：分類清單從 effect 抓資料改成 useQuery，queryKey 含分類，但 queryFn 還沒把 signal 傳給 API。店員從「咖啡」快速點到「茶」，咖啡的回應比較晚回來，畫面為什麼不會被蓋成咖啡？

✓ queryKey 是快取的地址，每個 key 各存各的，競態自然消失，不用自己寫 ignore 旗標。b 錯在 signal 要傳給 API 才會真的取消；沒傳的話舊請求會跑完，結果照樣存進咖啡那一格，只是畫面不讀它。（第 15 課）

練習 11：改價的 mutation 成功後，菜單列表顯示新價格，但剛才看過的拿鐵詳細頁再點進去，還是舊價格。先查什麼？

✓ 寫入之後要回答「改了之後誰會變」，失效用前綴選到整棵樹：productKeys.all 同時選到列表和詳細。寫成 ['products', 'list'] 或加 exact: true，詳細那一格就漏了。a 錯在被失效的 query 不管 gcTime 多長都會標成過期，下次顯示時重抓。（第 15、16 課）

練習 12：下面哪一個操作最適合做樂觀更新（先改畫面，失敗再改回）？

✓ 判斷方式是：失敗了回復畫面，挽不挽得回現實。收藏失敗時愛心熄掉、顯示訊息就好。a 是最多人會選的：下單成功率很高，但失敗時客人可能已經離開櫃台、店員已經開始做飲料，要停用按鈕等確認；b 會先顯示一個之後被伺服器推翻的數字。（第 16 課）

練習 13：結帳表單用 useActionState，Action 在手機格式不對時寫 throw new Error('手機格式錯誤')。客人填錯手機按送出，會看到什麼？

✓ Action 丟出的錯誤交給最近的 Error Boundary。驗證錯誤、422 這種預期中的錯誤要回傳成 state，連同原文一起回傳，讓 defaultValue 保留輸入；只有程式錯誤才丟。c 錯在回傳值才會成為新的 state，丟出的錯誤不會。（第 17 課）

練習 14：商品頁原本在 effect 裡抓資料，同事評估要不要改成路由的 loader。改了之後，下面哪個是他可以期待的結果？

✓ effect 是先 render 再抓，一定先閃一下；loader 把抓資料移到導航裡，舊頁面留著直到新資料到齊。代價是慢的 API 會擋住整次換頁，次要資料可以留給元件自己抓。a 錯在 loader 本身沒有快取，要快取就在 loader 裡用 TanStack Query 的 ensureQueryData；c 錯在同一次導航的 loader 是同時開始的。（第 18 課）

練習 15：後台已經用 middleware 擋掉非店長進 /admin/prices，改價表單也用 zod 驗證。後端同事說「前端都擋了，改價 API 不用再檢查角色和格式」。哪裡會出事？

✓ 前端的守衛和驗證都是體驗：讓沒權限的人看不到畫面、讓填錯的人馬上知道，真正的規則要在後端檢查。API 回 401 時前端導去登入，回 403 時顯示沒有權限。c 錯在 middleware 在所有 loader 之前執行，丟出 redirect 或 403 時 loader 不會跑；b 錯在每次導航都會執行。（第 17、18 課）
