階段 6：品質與期末專題 · 第 23 課

元件測試：Testing Library，測行為不測實作

線上點餐的「外帶預訂」表單有一個測試，跑了半年都是綠的。這週發生兩件事。設計師把按鈕的 class 從 preorder__submit 改成 btn-primary，畫面和功能都沒變，測試紅了。另一位同事把 <button> 換成 <div onClick>（class 照抄），又讓數量以字串 "2" 送給後端：用鍵盤的客人送不出表單，後端把 2 杯算成 0 杯，測試卻是綠的。

這個測試在檢查「程式現在怎麼寫」，不是「客人看到什麼、能做什麼」。從第 2 課開始，每一題練習都在跑我們寫的 Testing Library 測試；這課把那些寫法講清楚，然後換你寫：用角色與文字找元素、像使用者一樣操作、只檢查看得到的結果和元件交給外面的東西、等非同步的畫面、只替換網路和時間，最後用「好幾個故意寫壞的元件」檢查你的測試到底有沒有用。版本以 @testing-library/react 16.3.3、@testing-library/user-event 14.6.8、@testing-library/jest-dom 7.0.1、Vitest 5.0.5 為準。

這課的路線：
  1. 一個綠燈卻沒用的測試：Testing Library 的三個動作，和這課的最小答案。
  2. 查詢：角色與名稱優先；getBy、queryBy、findBy 的差別；用 within 縮小範圍。
  3. 測使用者看到與做到的事：哪些是實作細節，callback 的參數為什麼可以測。
  4. 非同步的畫面：findBy、「已經消失」怎麼檢查，以及 act 警告從哪裡來。
  5. 只替換網路和時間；假計時器的寫法；最後整理「寫了等於沒寫」的測試，用錯誤版本檢查自己的測試。
這課會用到：
  • 第 2 課「練習環境」的測試骨架：render 把元件畫進 happy-dom，screen 找元素，userEvent 操作，expect 檢查。
  • 第 5 課的 effect 抓資料：掛載後送請求，回應回來才 setState，用 ignore 旗標擋掉過期的回應。
  • 第 7 課的 ref 存計時器 id：setTimeout 回傳的 id 放在 ref，取消時拿得到。
  • 第 9 課的 act：會改 state 的操作包在 act() 裡，React 才會在它結束前把更新處理完。
測試跑在 Node 裡的 happy-dom 21.0.4：有 DOM 和事件，沒有版面與 CSS（Vue 課第 22 課說過什麼時候要用真的瀏覽器）。練習專案的 Vitest 沒有開 globals，所以 React 的 act 警告不會印出來，第 4 節說明這代表什麼。

一個綠燈卻沒用的測試

先看開場那個測試長什麼樣子：

test('送出預訂', () => {
  const onSubmit = vi.fn()
  const { container } = render(<PreorderForm onSubmit={onSubmit} />)
  fireEvent.change(container.querySelector('.preorder__name')!, { target: { value: '王小明' } })
  fireEvent.click(container.querySelector('.preorder__submit')!)
  expect(onSubmit).toHaveBeenCalled()
})

它的每一行都靠「程式現在怎麼寫」：用 class 找欄位和按鈕，所以改 class 就紅；最後只問 onSubmit「有沒有被呼叫」，不管收到什麼，所以數量變成字串也是綠的；<div onClick> 只要 class 還在，它照樣點得到，鍵盤用不了這件事它看不見。

Testing Library 的做法是讓測試只用使用者拿得到的東西。測試分三個動作：

  1. 找：用角色（role）、label、看得到的文字找元素，例如 screen.getByRole('button', { name: '送出預訂' })：「一顆寫著送出預訂的按鈕」。
  2. 做：用 userEvent 像使用者一樣點、打字、選選項。
  3. 看：檢查畫面上出現或消失了什麼，以及元件交給外面的東西（例如 onSubmit 收到的參數）。

同一個測試照這三個動作改寫：

test('送出預訂：姓名去掉空白、數量是數字', async () => {
  const user = userEvent.setup()                       // 文件建議在 render 之前建立
  const onSubmit = vi.fn()
  render(<PreorderForm onSubmit={onSubmit} />)

  await user.type(screen.getByLabelText('姓名'), '  王小明 ')
  await user.selectOptions(screen.getByLabelText('品項'), '拿鐵')
  await user.clear(screen.getByLabelText('數量'))
  await user.type(screen.getByLabelText('數量'), '2')
  await user.click(screen.getByRole('button', { name: '送出預訂' }))

  expect(onSubmit).toHaveBeenCalledTimes(1)
  expect(onSubmit).toHaveBeenCalledWith({ name: '王小明', productId: 2, quantity: 2 })
})

這就是開場問題的最小答案：改 class 不會讓它紅，因為它沒用 class；換成 <div onClick> 會紅，因為 div 沒有 button 這個角色，getByRole('button') 找不到；數量變成字串也會紅，因為它檢查了參數。後面四節分別展開「找」「看」「等」和「換掉什麼」。

對照 Vue 課第 22 課的 Vue Test Utils（VTU）：觀念完全一樣，差在 API。

Vue Test UtilsReact Testing Library差別
const wrapper = mount(C, { props })render(<C {...props} />)，之後用 screen 查RTL 不回傳元件實例，查詢對整個 document
wrapper.get('button') 加文字過濾screen.getByRole('button', { name: '重試' })角色加名稱一次到位
await wrapper.get('button').trigger('click')await user.click(按鈕)user-event 會依序觸發一連串事件，接近真人操作
await flushPromises()await screen.findByRole(…)不是「等 Promise 跑完」，而是「等畫面出現某個東西」
wrapper.vm.submitting沒有對應RTL 故意不提供讀 state 的方法

最後一列是 Testing Library 的設計：它的指導原則是「測試越像軟體被使用的方式，越能給你信心」，所以只給你使用者拿得到的東西。toBeInTheDocument、toHaveTextContent、toBeDisabled 這類檢查 DOM 的 matcher 來自 jest-dom，練習專案在 helpers/setup.ts 裡載入，每個測試檔都能用。

查詢：角色與名稱優先

上一節的「找」用了 getByRole 和 getByLabelText。Testing Library 的文件（Queries／About）排了一個優先順序，現在你已經看過它們的用法，可以查這張表（查表用，不用背）：

順序查詢什麼時候用
1getByRole(角色, { name })幾乎所有東西：按鈕、連結、標題、清單、表格的列、對話框、role="alert"。文件說它找不到的東西，常常代表介面本身不無障礙
2getByLabelText表單欄位：使用者靠 label 找欄位
3getByPlaceholderText只有 placeholder 時的退路；placeholder 不能取代 label
4getByText非互動的內容：段落、提示文字
5getByDisplayValue用欄位目前的值找
6getByAltText、getByTitle圖片的 alt；title 不一定會被讀出來
7getByTestId使用者看不到也聽不到，只在角色和文字都不適用時用（例如內容是動態的）

name 是元素的可存取名稱（accessible name）：螢幕閱讀器唸出來的名字，依 W3C 的規則計算。按鈕的名稱來自它的文字或 aria-label，欄位的名稱來自關聯的 <label>，表格的列（row）的名稱來自整列的文字。所以 <button aria-label="移除拿鐵">✕</button> 用 getByRole('button', { name: '移除拿鐵' }) 找得到，用 getByText('移除拿鐵') 找不到。

開場的兩種錯誤就是這樣被抓到的：<div onClick> 沒有 button 角色；只寫 placeholder、沒有 label 的欄位，getByLabelText 找不到。測試順便替你做了一部分無障礙檢查。

getBy、queryBy、findBy

每種查詢都有三種前綴，差別在「找不到」和「找到好幾個」時怎麼辦（Testing Library 文件）：

找不到找到超過一個用在
getBy…丟錯丟錯現在就該在畫面上的東西
queryBy…回傳 null丟錯檢查「不在畫面上」
findBy…回傳的 Promise 在 1000ms 後失敗失敗等一下才會出現的東西（第 4 節）

每一種都有 …AllBy… 版本，回傳陣列，用在預期有好幾個的時候。「找到好幾個就丟錯」是刻意的：畫面上有三顆「完成」按鈕，getByRole('button', { name: '完成' }) 會丟錯，逼你說清楚要哪一顆。

說清楚的方法是先找到範圍，再在範圍裡找。櫃台的待取餐表格每一列都有「完成」按鈕，要完成陳美華那一筆：

const table = screen.getByRole('table', { name: '待取餐' })
const row = within(table).getByRole('row', { name: /陳美華/ })    // 列的名稱來自整列的文字
await user.click(within(row).getByRole('button', { name: '完成' }))

expect(within(table).queryByRole('row', { name: /陳美華/ })).not.toBeInTheDocument()

within(元素) 回傳一組只在那個元素裡找的查詢。最後一行也用了 within：完成的訂單會出現在「已完成」清單裡，如果用 screen.queryByText(/陳美華/) 檢查「消失了」，正確的元件也會失敗。改用 getAllByRole('button', { name: '完成' })[0] 也能讓測試過，但它永遠只按第一列；元件寫成「不管按哪一列都完成第一筆」，這種測試抓不到。

💡 實務上：找不到角色時，先修元件，不是先加 test id
咖啡店後台常見的圖示按鈕（✕、⋯、垃圾桶）沒有文字，測試用 getByRole('button', { name: … }) 找不到。這時加上 aria-label="移除拿鐵"，測試找得到，螢幕閱讀器的使用者也知道這顆按鈕在做什麼，一次修好兩件事。團隊裡可以約定：data-testid 只用在角色和文字真的不適用的地方（例如畫布、第三方元件），code review 看到新增的 test id 就問一句「這裡有沒有可以用的角色或 label」。設計系統的元件更要注意：它包了一層 div 或把 label 畫成純文字，整個專案的測試和無障礙都會跟著壞。

測使用者看到與做到的事

找對元素之後，下一個問題是「看什麼」。實作細節（implementation detail）是使用者和父元件都拿不到、重構時可能改變的東西。測試依賴它，就會出現開場的兩種狀況：重構時誤報，真正壞掉時漏報。

實作細節（不要測）對應的行為（要測）
某個 state 的值、reducer 的 action畫面上的文字、按鈕是不是停用、錯誤訊息有沒有出現
class、DOM 的巢狀結構、第幾欄第幾個元素角色、label、文字
元件 render 了幾次、子元件收到什麼 props使用者最後看到的結果
直接呼叫元件內部的函式點按鈕、打字、按 Enter

那 expect(onSubmit).toHaveBeenCalledWith(…) 算不算實作細節？不算。onSubmit 是 props，是元件跟父元件之間的約定：父元件靠它拿到訂單資料，換一種寫法也不能改它。判斷的問題是：這個東西，元件外面的人（使用者、父元件、伺服器）看得到嗎？看得到就可以測，而且要測得精確：

  • 只寫 toHaveBeenCalled()，等於只檢查「有呼叫」，參數錯了照樣通過。用 toHaveBeenCalledWith(預期的參數)，再加 toHaveBeenCalledTimes(1) 確認沒有重複送出。
  • 「不該呼叫」也要檢查：姓名只有空白時，除了錯誤訊息出現，還要 expect(onSubmit).not.toHaveBeenCalled()，不然「顯示錯誤但還是送出」的元件會通過。
  • 輸入要能分辨對錯：姓名故意多打前後空白、品項選預設以外的、數量改成 2。全部用預設值送出，「沒去掉空白」「不管選什麼都送美式咖啡」都抓不到。

同樣的道理，自己的子元件不要換成假的。測菜單頁時把 MenuItem 用 vi.mock 換成空殼，測試就只能檢查「有沒有把 props 傳給 MenuItem」，又回到測實作；MenuItem 自己壞了，這個測試也不會紅。React Testing Library 本來就沒有 Vue 的 shallowMount（只渲染一層），預設把整棵子樹都畫出來。

快照測試（expect(container).toMatchSnapshot()）把整段 HTML 存起來，之後每次比對。任何一個 class、一層 div 改了都會紅，大家很快就養成「更新快照」直接按過的習慣，它就什麼都抓不到了。要用的話，只用在小而穩定、而且「長相改了就該有人看一眼」的輸出上。
💡 實務上：重構時紅了一片，先懷疑測試
把元件從 useState 改成 useReducer、把一個大元件拆成三個，畫面和行為完全沒變，測試卻紅了十幾個：這是測試綁在實作上的訊號，該改的是測試。反過來，客服回報「選了拿鐵，訂單變成美式咖啡」，先寫一個用使用者操作重現它的測試，看它紅，再修元件，這個 bug 就不會在下次重構時回來。PR review 時可以問兩個問題：這次改的行為，壞了的話哪個測試會紅？這次只是重構，為什麼要改測試？

非同步的畫面：findBy 與 act

上一節的表單按下去畫面馬上就變了。菜單頁不一樣：掛載後送請求，回應回來才畫菜單（第 5 課的寫法）。測試要能決定「回應什麼時候回來、成功還是失敗」，工具是練習專案的假 API（helpers/fake-api.ts）：createFakeMenuApi({ manual: true }) 的每次呼叫都會等著，記在 api.callsOf('getMenu') 裡，由測試呼叫 .resolve() 或 .reject(錯誤)。執行後看最後兩行怎麼等畫面：

const api = createFakeMenuApi({ manual: true })
render(<MenuPage api={api} />)
expect(screen.getByRole('status')).toBeInTheDocument()      // 載入中

api.callsOf('getMenu')[0].resolve()                          // 讓第一次呼叫成功
const menu = await screen.findByRole('list', { name: '菜單' })
expect(within(menu).getAllByRole('listitem')).toHaveLength(6)
expect(screen.queryByRole('status')).not.toBeInTheDocument()  // 載入訊息消失了

為什麼要 findBy：resolve() 只讓 Promise 完成，元件的 .then(setState) 和接下來的 render 還沒跑。實測在 resolve() 的下一行直接 getByRole('list')，找不到。findBy… 是 getBy… 加上 waitFor：DOM 有變化時、以及每 50ms 重新查一次，查到就成功，1000ms 還查不到就失敗（文件寫的預設值）。

檢查「已經消失」用 queryBy…：上面最後一行換成 getByRole('status')，載入訊息不在時 getBy 直接丟錯，正確的元件反而失敗。要等某個東西消失，用文件的兩種寫法：

await waitForElementToBeRemoved(() => screen.queryByRole('status'))   // 一開始必須在畫面上，不然直接丟錯
await waitFor(() => expect(screen.queryByRole('status')).not.toBeInTheDocument())

waitFor(callback) 會一直重跑 callback，直到它不丟錯為止。文件特別寫明：callback 回傳 false 不算失敗，要用 expect 讓它丟錯才會重試。所以 waitFor(() => screen.queryByRole('list')) 不是在等清單出現。

不要用 await new Promise(r => setTimeout(r, 100)) 等。它沒說清楚在等什麼；CI 機器忙的時候 100ms 不夠，測試時好時壞；幾百個測試每個多等 100ms，加起來就是好幾分鐘。讓測試決定 API 什麼時候完成，再用 findBy 等畫面。

act 警告從哪裡來

第 9 課說過，會改 state 的操作要包在 act() 裡。依 react.dev 的 act 文件，act 是一個「單位」：裡面觸發的 render、effect、state 更新，會在 act 結束前全部處理完、套用到 DOM，之後的 expect 看到的就是使用者會看到的畫面。React Testing Library 已經把 render、fireEvent 包在 act 裡，也把 Testing Library 的事件包裝設成 act，所以 user.click 這些操作也在 act 裡，平常不用自己寫。

在 act 外面發生的更新，React 不會等你。測試環境設了 IS_REACT_ACT_ENVIRONMENT = true 時，React 會在 console 印出：

An update to MenuPage inside a test was not wrapped in act(...).

常見的成因是「測試結束後，或下一個 expect 之前，還有更新在跑」：API 晚一點才回來、計時器到了、Promise 的 then 在測試沒等的時候 setState。修法不是到處包 act，而是等那個更新造成的畫面：用 findBy… 或 waitFor。只有在推進假計時器（下一節）、或直接呼叫 hook 回傳的函式（第 9 課）這類 Testing Library 沒有包到的地方，才自己寫 act。

這個警告在練習專案裡看不到：@testing-library/react 16.3.3 只在測試框架有全域的 beforeAll 時才設定 IS_REACT_ACT_ENVIRONMENT（Jest，或開了 globals: true 的 Vitest），練習專案沒有開。實測同一段程式，手動設定後就會印出上面的警告；沒設定時不印，但畫面一樣還沒更新。所以在這個專案裡，忘了等的症狀是「找不到元素」或「畫面還是舊的」，原因一樣。

💡 實務上：CI 上 findBy 逾時，先別把 timeout 調大
「本機會過、CI 偶爾 Unable to find role="list"」是很常見的不穩定測試。把 findBy 的 timeout 從 1 秒調到 5 秒，通常只是把問題藏起來。先看錯誤訊息後面印出的 DOM：畫面停在載入中，代表假 API 沒有被 resolve，或 resolve 的是另一次呼叫（例如測試之間共用了同一個假 API）；畫面停在錯誤，代表請求真的失敗了，可能是測試不小心連到真的網路。每個測試建立自己的假 API、QueryClient（第 15 課）和 store，是最有效的預防。

只替換網路和時間

上一節的假 API 是一種測試替身（test double）：測試裡代替真實依賴的假東西。該換掉的是「測試控制不了、或會讓結果每次不同」的東西，其他保持真的：

依賴換不換怎麼換
網路（API、fetch）換元件從 props 或 context 拿 API client（第 11 課的依賴注入），測試傳假的；或用 vi.stubGlobal('fetch', vi.fn(…)) 換掉全域的 fetch
時間（setTimeout、Date）換vi.useFakeTimers()，見下面
亂數換當參數傳進去，測試給固定值
自己的子元件不換照樣 render，測試看最後的畫面
React、hooks、自己的 store不換每個測試建立新的 store 或 Provider

還有一種換法是 vi.mock('./menu-api.ts', …)：把整個模組換掉。它讓測試知道「元件 import 了哪個檔案」，這也是實作細節，所以能用參數或 context 傳進去，就不要用它。真的要用時注意，Vitest 5 的遷移指南寫明：vi.mock 會被提到檔案最前面執行，寫在 describe、test 或函式裡會直接丟錯，只能寫在檔案最外層。

假計時器

購物車的「移除」做成可以復原：按下移除，品項先從畫面消失，出現「已移除拿鐵 · 復原」；5 秒內沒按復原，才呼叫 onRemove 真的刪除。測試不可能真的等 5 秒，而且要精確檢查「4999ms 還沒刪、5000ms 刪了」。vi.useFakeTimers() 把 setTimeout、setInterval、Date 換成假的（Vitest 文件），時間只在你呼叫 vi.advanceTimersByTime(ms) 時往前走。執行後看兩次 pass 之間 onRemove 的變化：

vi.useFakeTimers()
const onRemove = vi.fn()
render(<RemovableCart items={items} onRemove={onRemove} />)
const pass = (ms: number) => act(() => { vi.advanceTimersByTime(ms) })

fireEvent.click(screen.getByRole('button', { name: '移除拿鐵' }))
pass(4999)
expect(onRemove).not.toHaveBeenCalled()
pass(1)
expect(onRemove).toHaveBeenCalledWith(2)
expect(screen.queryByRole('status')).not.toBeInTheDocument()

這段有兩個跟平常不同的地方：

  • 推進時間要包 act：計時器的 callback 會 setState，而 vi.advanceTimersByTime 不是 Testing Library 的函式，沒有包 act。實測拿掉 act，onRemove 照樣被呼叫，但提示還留在畫面上，最後一行失敗。
  • 用 fireEvent.click，不用 userEvent：實測在這個專案開著假計時器時，await user.click(…) 會卡到測試逾時，照 user-event 文件加上 userEvent.setup({ advanceTimers: vi.advanceTimersByTime }) 也一樣。原因在 @testing-library/react 16.3.3 的原始碼：每次操作結束後它會等一個 setTimeout(0)，只在偵測到 Jest 的假計時器時才自動推進，Vitest 的假計時器它認不出來，那個 setTimeout 就永遠不會到。fireEvent 是同步送出一個事件並包好 act，不受影響；第 7 課的練習也是這樣寫的。

同一個原因，開著假計時器時 findBy 也不會在 1 秒後失敗：它的逾時本身就是一個 setTimeout，東西一直沒出現就會一直等到測試逾時。需要假時間的測試，畫面的變化都靠 act 加推進時間，用 getBy／queryBy 同步檢查。練習專案的 helpers/setup.ts 會在每個測試結束時 vi.useRealTimers()，不會漏到下一個測試。

💡 實務上：依賴從外面傳進來，測試才不用 vi.mock
一個元件的測試要 vi.mock 五六個模組才跑得起來，代表它直接 import 了 API、store、時間，依賴全藏在裡面。這時該改的常常是元件：API client 用 props 或 context 傳進來（第 11 課），「現在幾點」當參數，計算抽成純函式另外測。另一個常見的坑是假 API 和真的後端慢慢對不上：後端改了欄位名稱，假資料沒改，測試全綠、上線卻壞。讓假資料使用和正式程式碼同一份型別，再用少數連真後端（或測試用後端）的 E2E 測試兜底。

寫了等於沒寫：用錯誤版本檢查你的測試

前面四節各提到一種「看起來有測、其實抓不到錯」的寫法。測試也是程式，也會寫錯，而且寫錯的測試通常是綠的，沒人會發現。整理起來：

寫法抓不到什麼
只 render，或只檢查「畫面上有東西」任何行為錯誤
toHaveBeenCalled() 不檢查參數送錯資料、送錯 id
只測成功的路徑驗證、錯誤訊息、重試、復原
全部用預設值、只按第一列「不管選什麼都用預設」「不管按哪列都處理第一筆」
只檢查時間到了之後太早執行（按下就刪除、4 秒就刪除）
復原之後沒有再推進時間計時器沒被取消

另一類是反過來，正確的元件也會讓它失敗：用 class、test id、第幾欄找元素；用 getBy 檢查不存在；resolve 之後沒有等就 getBy；測試之間共用假 API。這類測試在重構時會誤報，久了大家就不信紅燈。

怎麼知道自己的測試屬於哪一類？兩個條件：元件壞掉時它要失敗；元件換一種寫法但行為一樣時它要通過。故意把程式改錯、看測試抓不抓得到，叫做變異測試（mutation testing），有工具會自動產生大量變異版本；手動做也很有效：改完一個元件，把關鍵的那一行刪掉或改錯，跑一次測試，確認它會紅。

這課的練習就這樣判分，跟 Vue 課第 22 課的做法一樣。你寫的不是一般的測試檔，而是一個「檢查函式」：接收一個元件，render 它、操作它，不符合規格就丟錯（expect 沒過就會丟錯）。函式的內容就是你平常會寫在 test() 裡的東西，只是每個情境開頭要自己 cleanup()（平常 Testing Library 會在每個 test 結束時做）。判分的測試把你的函式套在兩個內部寫法不同的正確版本上（都要通過），再套在好幾個錯誤版本上（每個都要丟錯）。所有版本的元件名稱都一樣，你只能從行為分辨。

練習

在 learn/ 執行 node check.mjs react 23，檔案在 react/practice/work/23/。四題都是寫「檢查函式」（exN.checks.tsx）：PreorderForm.tsx、PickupQueue.tsx、MenuPage.tsx、RemovableCart.tsx 是寫好的正確版本，開頭的註解就是規格，你的檢查只能依賴規格寫到的東西，元件本身不要改。結果會列出哪個正確版本沒通過（你的檢查太依賴實作）、哪個錯誤版本沒被抓到（少了一個 expect）。

練習 1：完成 checkPreorderForm(Form)，替外帶預訂表單寫三個情境：正確填寫（姓名前後多打空白、品項選拿鐵、數量改成 2）後送出，檢查 onSubmit 只呼叫一次、參數是 { name: '王小明', productId: 2, quantity: 2 }、沒有錯誤訊息；姓名只有空白時有 role="alert"、onSubmit 沒被呼叫，補上姓名再送出後錯誤消失；數量是 0 時有 alert、onSubmit 沒被呼叫。欄位用 getByLabelText、按鈕用 getByRole 找，用 userEvent 操作，不能用 class、placeholder、data-testid。另一個正確版本是非受控的、錯誤文字不同；九個錯誤版本（包括 <div onClick> 的按鈕、沒有 label 的欄位、數量送字串）都要抓到。

練習 2：完成 checkPickupQueue(Queue)：用起始檔的三筆訂單 render，用列的名稱找到「陳美華」那一列，within 那一列按「完成」。檢查陳美華從「待取餐」表格消失、另外兩筆還在、陳美華出現在「已完成」清單、標題從「待取餐（3）」變成「待取餐（2）」、onComplete 只呼叫一次而且收到 102。不能靠第幾顆按鈕、第幾欄找東西（另一個正確版本的欄位順序不同、沒有單號欄）；「消失」要限定在表格裡檢查。五個錯誤版本都要抓到。

練習 3：完成 checkMenuPage(Page, makeApi)，每個情境用 makeApi() 拿新的假 API。情境 1：一開始有 role="status"、getMenu 呼叫一次；讓它成功後，「菜單」清單有全部 6 個商品，status 和 alert 都不在。情境 2：讓第一次失敗，等到 role="alert" 出現、status 消失；按「重試」後 alert 消失、回到 status、getMenu 呼叫了第 2 次；讓第 2 次成功後列出全部商品、沒有 alert。等畫面用 findBy…，檢查不存在用 queryBy…，不能用 setTimeout。六個錯誤版本都要抓到。

練習 4：完成 checkRemovableCart(Cart)，每個情境開頭 cleanup()、vi.useFakeTimers() 再 render，用 fireEvent.click 操作、act(() => { vi.advanceTimersByTime(ms) }) 推進時間。情境 1：按「移除拿鐵」後拿鐵不在「購物車」清單、有含「拿鐵」的 status、onRemove 還沒呼叫；4999ms 時還沒呼叫；5000ms 時呼叫一次而且收到 2、提示消失、拿鐵沒有回來。情境 2：移除後過 3 秒按「復原」，拿鐵回到清單、提示消失；再過 10 秒 onRemove 一次都沒被呼叫。每個版本 2 秒內要跑完（不能等真的時間）；七個錯誤版本（包括 4 秒、8 秒、按下就刪、復原沒取消計時器）都要抓到。

練習 5：菜單頁成功之後，測試寫了 expect(screen.getByRole('status')).not.toBeInTheDocument() 檢查載入訊息消失了。元件是對的，測試卻失敗。為什麼？

✓ getBy 的設計是「現在就該在畫面上」，找不到就丟錯；queryBy 才是「可能不在」，找不到回傳 null，交給 .not.toBeInTheDocument() 判斷。a 錯在消失之後的檢查是同步的，不需要 await；b 錯在 jest-dom 的 matcher 接受任何元素或 null；d 錯在 status 是正常的角色，getByRole 找得到。

練習 6：「5 秒後刪除」的測試開了 vi.useFakeTimers()，接著 await user.click(移除按鈕)，測試一直卡到逾時。在這個 Vitest 專案裡，最好的改法是？

✓ @testing-library/react 16.3.3 每次操作結束都會等一個 setTimeout(0)，只有 Jest 的假計時器會被自動推進，Vitest 的不會，所以 user.click 永遠等不到。fireEvent 同步送出事件並包好 act，不受影響。a 不會改變任何事，那個 setTimeout 永遠不會到；c 讓每個測試慢 5 秒，也沒辦法精確檢查 4999ms；d 是 user-event 文件明說不建議的寫法，而且卡住的那個 setTimeout 不在 user-event 裡。

練習 7：MenuPage 從 props 拿 api，裡面用自己的 MenuItem 元件畫每個商品。下面哪一種測試替身的用法最合理？

✓ 網路是測試控制不了、結果會變的邊界，換成假的；MenuItem 是自己的程式，保持真的，測試才看得到使用者真正看到的東西。b 把測試綁在「元件用哪個子元件、傳什麼 props」上，MenuItem 壞了也不會紅；c 讓結果依賴網路和伺服器的資料，時好時壞，那是少數 E2E 測試的工作；d 測的是 state 這個實作細節，換成 useReducer 就壞。

常見錯誤

  • 用 class、DOM 結構、第幾個元素找東西：改樣式、多包一層、換欄位順序就壞。依序用角色加名稱、label、文字；有好幾個時先用 within 縮小範圍。
  • 先加 data-testid：使用者看不到，也就抓不到「按鈕沒有名稱」「欄位沒有 label」。只在角色和文字都不適用時用。
  • 用 getByText 找按鈕：<div onClick> 也找得到，鍵盤用不了這件事測不出來。按鈕用 getByRole('button', { name })。
  • 用 placeholder 找欄位：沒有 label 的欄位也會通過。用 getByLabelText。
  • 只寫 toHaveBeenCalled()：參數錯了照樣通過。用 toHaveBeenCalledWith 加 toHaveBeenCalledTimes；不該呼叫的情境寫 not.toHaveBeenCalled()。
  • 只測成功的路徑、只用預設值、只按第一列：驗證、錯誤、重試、「選了別的」「按了別列」最常出事。輸入要能分辨對錯。
  • 讀 state、mock 自己的子元件、檢查 render 次數：重構就壞，元件壞了反而不紅。只檢查畫面和元件交給外面的東西。
  • 用 getBy 檢查不存在：找不到就丟錯。用 queryBy… 加 .not.toBeInTheDocument()。
  • 非同步更新之後沒有等就 getBy：resolve 只完成 Promise，畫面還沒更新。用 await findBy…；findBy 沒有 await 等於沒等。
  • waitFor 的 callback 只回傳值：回傳 false 不會重試。在 callback 裡寫 expect。
  • 用 setTimeout 等：慢又不穩定。讓測試決定假 API 何時完成，再用 findBy 等畫面。
  • 情境之間共用假 API、沒有 cleanup：呼叫紀錄和畫面會疊在一起。每個情境建立新的替身，檢查函式裡每個情境先 cleanup()。
  • 推進假計時器沒有包 act：callback 執行了，畫面卻沒更新。act(() => { vi.advanceTimersByTime(ms) })。
  • 開著假計時器用 userEvent：在 Vitest 會卡到逾時。用 fireEvent。
  • 只檢查時間到了之後：抓不到太早執行。檢查邊界的兩邊（4999ms、5000ms）；復原之後再推進一段時間，確認計時器真的取消了。
  • 在 describe 或 test 裡寫 vi.mock：Vitest 5 直接丟錯。寫在檔案最外層，而且能用參數或 context 傳替身就不要用它。
  • 大段快照測試：什麼改動都紅，最後大家直接更新快照。只用在小而穩定的輸出上。

小結

  • Testing Library 的測試只用使用者拿得到的東西：用角色、label、文字找，用 userEvent 做，看畫面和元件交給外面的東西（callback 的參數）。
  • 查詢優先順序：getByRole(角色, { name }) → getByLabelText → 文字，test id 最後；找不到角色常代表無障礙有問題。getBy 要它在、queryBy 檢查不在、findBy 等它出現；好幾個時用 within 縮小範圍。
  • 實作細節（state、class、結構、render 次數、子元件的 props）不測；props 的 callback 是約定，要測參數和次數，也要測「不該呼叫」。
  • 非同步：測試決定假 API 何時完成，再用 findBy 等畫面；waitFor 的 callback 要丟錯才會重試；不 sleep。act 警告表示有更新發生在測試沒等的地方，修法是等那個畫面。
  • 只替換網路、時間、亂數；自己的元件和 hooks 保持真的。假計時器用 act 推進，這個專案裡配 fireEvent。
  • 好的測試在錯誤版本上失敗、在換了寫法的正確版本上通過；故意改錯程式，確認測試會紅。
