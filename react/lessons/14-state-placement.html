階段 4：狀態與資料 · 第 14 課

狀態放哪裡：元件、提升、URL 與 Zustand

咖啡店的點餐頁越寫越慢：客人在搜尋框打一個字，整份菜單就重新 render 一次。店長把「只看茶」的網址傳給同事，對方打開看到的卻是全部商品。購物車要出現在頁首、菜單和結帳頁，有人把它塞進 Context，結果客人改個備註，200 顆「加入」按鈕全部重新 render。

三個問題的根源都是狀態放錯了地方。每一段都對照 Vue，範例使用 React 19.3.1、React Router 8.5.1、Zustand 5.0.16。

這課的路線：
  1. 先問誰要讀、正本在哪：一張表決定任何一份狀態該放哪裡（開場問題的最小答案）。
  2. 往下放：搜尋框打一個字為什麼整份菜單重新 render，把草稿搬進用它的元件。
  3. 網址也是狀態：「只看茶」的連結要能分享、按上一頁要還原，用 useSearchParams 讀寫並驗證。
  4. Zustand 與 selector：購物車放進 store，每個元件只訂閱自己要的那一塊，改備註不再讓 200 顆按鈕重新 render。
  5. store 的實例：測試之間不互相影響、SSR 每個請求一份、重新整理後購物車還在。
這課會用到：
  • 第 3 課的提升 state 與不可變更新：兄弟元件要共用的 state 搬到共同父元件，用 props 傳下去；更新時做出新物件，不改原本的。
  • 第 11 課的 Context：Provider 把 value 傳給整棵子樹；value 一換，所有讀它的元件都重新 render。

先問兩件事：誰要讀、正本在哪

狀態（state）是會隨時間改變、而且畫面要跟著它變的資料。決定放哪裡，先回答兩個問題：哪些元件要讀它，以及它的正本在哪裡。正本在伺服器的資料（菜單、訂單紀錄）叫伺服器狀態（server state），前端拿到的只是某一刻的副本，會過期、別人也可能改了它，交給下一課的 TanStack Query 處理。這課處理的是正本就在前端的狀態。

原則是從最小的範圍開始，不夠才往外擴：

情境React 放哪裡Vue 的對應咖啡店的例子

Context 和 Zustand 的差別在重新 render 的範圍：Context 的 value 一換，所有讀它的元件都重新 render（第 11 課），不能只訂閱一個欄位。所以 Context 放很少變的東西；購物車一直變、很多元件只關心一小塊，用 store 加 selector。

💡 實務上：新增狀態前先問「誰要讀、正本在哪、誰負責清掉」
接到「結帳頁要顯示優惠券」這類需求，先決定狀態放哪裡，不要直接開全域 store。表單草稿留在元件裡，離開頁面就消失通常剛好；PM 要求「切到別頁再回來還在」，才往外放。放到全域的狀態要想好生命週期：登出、切換門市時購物車要不要清、由誰清。code review 看到新的 store，可以直接問「這只有一頁用嗎？」，很多時候答案是「是」，留在元件裡就好。

往下放：state 離用它的元件越近越好

點餐頁的寫法常常是這樣：搜尋框的草稿放在頁面元件，因為「搜尋結果要用到它」。

function MenuPage({ products }: { products: readonly Product[] }) {
  const [draft, setDraft] = useState('')       // ✗ 每打一個字，MenuPage 整個重新 render
  const [keyword, setKeyword] = useState('')
  const shown = products.filter(p => p.name.includes(keyword.trim()))
  return (
    <main>
      <form role="search" onSubmit={e => { e.preventDefault(); setKeyword(draft) }}>
        <input value={draft} onChange={e => setDraft(e.target.value)} />
      </form>
      <ProductList products={shown} />   {/* 跟著重新 render，裡面每一張卡片也是 */}
    </main>
  )
}

第 1 課說過，state 一改，那個元件和底下整棵子樹都重新 render。草稿只有輸入框需要，卻放在最上層，每打一個字，每張商品卡片都重新 render。

修法不是 memo，而是把 state 往下放，放到真正用它的元件裡：把輸入框和草稿抽成 SearchBox，送出時才用函式 props 通知父元件。

function SearchBox({ onSearch }: { onSearch: (text: string) => void }) {
  const [draft, setDraft] = useState('')       // ✓ 打字只重新 render SearchBox
  return (
    <form role="search" onSubmit={e => { e.preventDefault(); onSearch(draft) }}>
      <label>搜尋商品 <input value={draft} onChange={e => setDraft(e.target.value)} /></label>
      <button type="submit">搜尋</button>
    </form>
  )
}
// MenuPage 只留「送出的關鍵字」：<SearchBox onSearch={setKeyword} />

草稿只屬於輸入框；送出的關鍵字清單也要讀，放在共同父元件。這同時用了「往下放」和第 3 課的「提升」：

  • 往下放：只有一個元件用的 state，從上層搬進那個元件。
  • 提升：兄弟元件都要用的 state，放到最近的共同父元件，props 往下、函式 props 往上。分類按鈕和清單各存一份 category，點了「茶」按鈕亮了、清單沒變，就是該提升卻沒提升。

目標一樣：每份狀態只有一份，放在所有用到它的元件最近的共同祖先。太高，重新 render 範圍太大；放兩份就要同步，遲早會漏。

先別急著加 memo（第 19 課）：它能擋住這次，但 state 仍然放錯，之後每加一個子元件都要記得包。

URL 也是狀態：useSearchParams

使用者會想分享、收藏，或按上一頁要還原的狀態應該放在網址，例如菜單的分類、搜尋字、頁碼。放在 useState 裡，網址傳出去就沒有篩選，按上一頁回來也回到預設值。

query string 是網址 ? 後面的鍵值，例如 /menu?category=tea&q=拿。React Router 的 useSearchParams() 回傳 [searchParams, setSearchParams]：前者是瀏覽器內建的 URLSearchParams，後者會導航到新的網址。

Vue RouterReact Router 8.5.1
讀route.query.category（字串、null 或陣列）searchParams.get('category')（字串或 null）、getAll（陣列）
寫並保留其他鍵router.replace({ query: { ...route.query, category } })setSearchParams(prev => { prev.set('category', c); return prev }, { replace: true })
刪掉一個鍵從物件裡拿掉prev.delete('category')

query 是使用者可以亂改的外部輸入，要像 API 回應一樣驗證（TS 課第 26 課）：值一律是字串，可能是 <script>，同一個鍵也可能出現兩次（get 只拿第一個，getAll 拿全部）。包成自訂 hook，每次 render 都從網址算出來：

const CATEGORIES: readonly string[] = ['coffee', 'tea', 'food']
const isCategory = (v: string): v is Category => CATEGORIES.includes(v)

export function useMenuQuery() {
  const [params, setParams] = useSearchParams()
  const values = params.getAll('category')
  // 只接受白名單、而且只有一個值；其他一律當成 all
  const category: 'all' | Category = values.length === 1 && isCategory(values[0]) ? values[0] : 'all'

  function setCategory(c: 'all' | Category) {
    setParams(prev => {
      if (c === 'all') prev.delete('category')
      else prev.set('category', c)
      return prev                    // 其他鍵（q、page）原樣保留
    }, { replace: true })            // 篩選不新增歷史紀錄
  }
  return { category, setCategory }
}
  • 保留其他鍵：setParams({ category: c }) 會把 q、page 一起清掉。用函式形式，收到的是目前參數的複本（8.5.1 原始碼），改它再回傳。官方文件提醒：它不像 setState 會排隊，同一個事件裡呼叫兩次，第二次不會建立在第一次的結果上；要改兩個鍵就在同一個函式裡改完。
  • replace：不加的話每切一次分類就新增一筆歷史紀錄，客人按上一頁會一格一格退回之前的篩選。
  • 單一資料來源：不要「進入時從網址讀一次存進 useState，之後改 state 再同步回網址」。使用者按上一頁、點了另一個帶 query 的連結時，state 不會跟著變，畫面和網址就對不上。網址是唯一的真相，畫面從網址算出來（第 6 課的「能算出來的就不存」）。

回到上一段的搜尋框：輸入框的文字是還沒送出的草稿，留在 SearchBox 的 useState；送出後才寫進網址。如果每打一個字就寫網址，等於每個字觸發一次導航。這也是 Vue 課第 19 課的建議。

💡 實務上：後台列表的篩選放網址，客服回報就能直接重現
咖啡店後台的訂單列表有日期區間、狀態、頁碼，店長常常貼一個網址說「你看這個」。篩選放在 query，你打開就是同一個畫面。網址會留在歷史紀錄、log 和聊天訊息裡，個資不要放進 query。另一個常見 bug：換了篩選條件卻保留 page=5，新條件只有兩頁結果，畫面變成空的；篩選改變時要不要把頁碼刪掉，寫 hook 時就要決定。

Zustand：一台購物車 store

Zustand 是 React 常見的狀態管理套件，角色對應 Pinia（Vue 課第 15 課，沒學過也能跟上）：把共用的狀態和修改它的函式集中在一個 store。create 回傳一個自訂 hook，元件呼叫它讀 store，值變了就重新 render。

import { create } from 'zustand'

type CartState = {
  lines: CartLine[]
  orderType: 'here' | 'togo'
  add: (productId: number) => void
  setOrderType: (type: 'here' | 'togo') => void
  clear: () => void
}

// TypeScript 要寫成 create<T>()(…)：先給型別、再傳初始化函式
export const useCartStore = create<CartState>()((set, get, store) => ({
  lines: [],
  orderType: 'here',
  add: productId => set(state => ({
    lines: state.lines.some(l => l.productId === productId)
      ? state.lines.map(l => (l.productId === productId ? { ...l, quantity: l.quantity + 1 } : l))
      : [...state.lines, { productId, quantity: 1 }],
  })),
  setOrderType: orderType => set({ orderType }),
  clear: () => set(store.getInitialState()),
}))

初始化函式收到 set、get 和 store 本身，回傳的物件就是初始 state，裡面的函式就是 action。關鍵行為（zustand 5.0.16 原始碼）：

  • set 只合併第一層：set({ orderType }) 等於 Object.assign({}, state, { orderType })，lines 和 action 都保留。巢狀的部分要自己展開，跟第 3 課的不可變更新一樣：不能 state.lines.push()，要回傳新陣列。
  • set(…, true) 是整個取代：傳的物件沒有 action，action 就不見了。實測 setState({ note: 'r' }, true) 之後 state 只剩 note 一個鍵。
  • 同一個物件不通知：set 先用 Object.is 比較，直接改舊物件再 set(state)，元件不會更新。
  • store.getInitialState() 回傳初始 state。重設時合併它，之後新增的欄位也不會漏，不用像 Pinia setup store 手寫 $reset。

對照 Pinia：

defineStore('cart', () => { … })create<CartState>()(set => ({ … }))，不用 id

元件裡用 storeToRefs 取 state元件裡用 selector 選值：useCartStore(selectCount)

件數、小計這類從 lines 算得出來的值，不要存成 state（第 6 課的原則）：存了就得在每個 action 裡記得同步，changeQty 忘了改 count 就出錯。寫成 store 外面的純函式，元件和測試都能用：

export const selectCount = (s: CartState) => s.lines.reduce((sum, l) => sum + l.quantity, 0)

const count = useCartStore(selectCount)   // 元件裡
selectCount(useCartStore.getState())      // 測試或事件處理函式裡

Zustand 的 hook 底層是第 9 課的 useSyncExternalStore：set 通知訂閱者，React 再讀一次 snapshot 決定要不要重新 render。

selector：只訂閱需要的部分

最直覺的寫法是把整個 store 拿出來解構：

function AddButton({ productId }: { productId: number }) {
  const { add } = useCartStore()      // ✗ 沒給 selector：訂閱整個 state
  return <button onClick={() => add(productId)}>加入</button>
}

畫面是對的，但不給 selector 等於選了整個 state，而 set 每次都產生新的 state 物件。實測改了備註，這顆按鈕也重新 render。這跟 Vue 正好相反：Pinia 的 store 直接解構會失去響應性，要用 storeToRefs；Zustand 直接解構「有」響應性，只是太多了。

修法是傳 selector（選擇函式）：從 state 選出這個元件需要的值。Zustand 用 Object.is 比較這次和上次 selector 的回傳值，相同就不重新 render。

寫法什麼時候重新 render
useCartStore() 或 useCartStore(s => s)store 任何欄位變了
useCartStore(s => s.add)幾乎不會：action 的參考一直是同一個
useCartStore(selectCount)件數這個數字變了
useCartStore(s => s.lines)lines 換成新陣列（改備註時不會，set 保留了原本的 lines）
useCartStore(s => ({ count: …, subtotal: … }))✗ 每次都是新物件，Zustand 5 會無限迴圈

最後一列是從 Zustand 4 升級最常踩的坑：Object.is 永遠不相等，React 每次讀 snapshot 都以為變了。實測 React 19.3.1 先印出 The result of getSnapshot should be cached to avoid an infinite loop，接著丟出 Maximum update depth exceeded。Zustand 5 的遷移指南明寫這是 v5 的行為改變。要一次選好幾個值，有兩種做法：

// 1. 分開選，每個 selector 回傳一個原始值
const count = useCartStore(selectCount)
const subtotal = useCartStore(selectSubtotal)

// 2. useShallow：逐一比較物件的每個屬性，都沒變就回傳上一次的物件
import { useShallow } from 'zustand/react/shallow'
const { count, subtotal } = useCartStore(
  useShallow(s => ({ count: selectCount(s), subtotal: selectSubtotal(s) })),
)

useShallow 在 5.0.16 用 ref 記住上一次的結果，這次跟它淺比較（每個屬性用 Object.is）相同就回傳上一次的物件；陣列也可以。

memo 只在「父元件重新 render、props 沒變」時跳過；store 的通知直接送到訂閱的元件。實測解構整個 store 的元件包上 memo，改備註照樣重新 render。

💡 實務上：store 的 hook 一律帶 selector，團隊用 lint 或 review 守住
常見的事故是：頁面一開始很小，大家都寫 const { … } = useCartStore()，等到菜單有幾百個商品、購物車有動畫，才發現打字會卡。用 React DevTools 的 Profiler 錄一次「改備註」，會看到一整排不相關的元件亮起來。有些團隊只 export useCartCount() 這類寫好 selector 的小 hook，元件就選不到整個 state。升級到 Zustand 5 時，先搜尋回傳物件或陣列的 selector，都要包 useShallow。

store 的實例：測試、SSR 與持久化

create 建的 store 存在模組裡，整個程式只有一份。在瀏覽器裡這通常剛好，但有三個地方要注意。

測試：每個測試共用這一份，上一個測試的拿鐵會留到下一個。官方文件的做法是每個測試前設回初始值：

beforeEach(() => {
  useCartStore.setState(useCartStore.getInitialState(), true)   // true：整個取代，不是合併
})

伺服器端渲染（SSR，第 22 課）：伺服器的模組只載入一次，同時服務很多顧客，模組層級的 store 會讓 A 顧客的購物車出現在 B 顧客的頁面上。Zustand 的 Next.js 指南明寫「不要用全域 store，每個請求建立一個」。做法是用 createStore 建一個「還沒綁 hook」的 store，放進 Context，元件用 useStore(store, selector) 讀：

import { createStore, useStore } from 'zustand'

const createCartStore = (initial: CartLine[] = []) =>
  createStore<CartState>()(set => ({ lines: initial, /* … */ }))

const CartStoreContext = createContext<ReturnType<typeof createCartStore> | null>(null)

export function CartStoreProvider({ initial, children }: { initial?: CartLine[]; children: ReactNode }) {
  const [store] = useState(() => createCartStore(initial))   // 每個 Provider 只建一次
  return <CartStoreContext value={store}>{children}</CartStoreContext>
}

export function useCart<T>(selector: (s: CartState) => T): T {
  const store = use(CartStoreContext)
  if (!store) throw new Error('useCart() 必須在 <CartStoreProvider> 之下使用')
  return useStore(store, selector)
}

Context 的 value 是 store 本身，建好就不換，重新 render 的範圍仍由 selector 決定。這就是 Pinia「每個請求一個 pinia 實例」在 React 的寫法；要用 props 決定初始值、或畫面上要兩台獨立的購物車時，也用這個模式。

持久化：重新整理後購物車還在，Zustand 內建 persist 中介層（middleware），對應 Vue 課第 15 課自己寫的 Pinia 外掛：

import { persist } from 'zustand/middleware'

export const useCartStore = create<CartState>()(persist(set => ({ /* … */ }), {
  name: 'cart',                                // storage 裡的 key
  version: 1,                                  // 格式改了就加 1
  partialize: s => ({ lines: s.lines }),       // 只存 lines
}))

預設存在 localStorage，格式是 { state, version }。在 5.0.16 用假的同步 storage 實測：建立 store 時就讀回來，之後每次 set 都寫入；version 不同又沒給 migrate 時印出錯誤、維持初始值；JSON 壞掉時錯誤交給 onRehydrateStorage，也維持初始值。但格式不對不會被擋下：存的是 { state: { lines: null }, version: 1 }，讀回來 lines 就是 null，selectCount 一呼叫 reduce 就整頁壞掉。persist 不驗證內容，要自己在 merge 選項裡檢查（TS 課第 26 課）。

💡 實務上：持久化的資料是外部輸入，上線後格式就很難改
部署新版本不會清掉使用者電腦裡的舊資料：上線後幫購物車加「甜度」欄位，舊格式還在幾萬台電腦上。第一版就要有 version，改格式時寫 migrate，並驗證讀回來的內容。localStorage 是明文，同網站的任何 JavaScript 都讀得到，token、手機、地址不要放進持久化的 store。

練習 1：MenuPage 把搜尋草稿放在頁面最上層，打字時每張卡片都重新 render；分類按鈕和清單又各存一份 category，點「茶」清單不變。修正它：草稿只放在 SearchBox，打字時 ProductCard 不能重新 render；送出表單（按鈕或 Enter）時用 onSearch 通知 MenuPage，清單只顯示品名包含關鍵字（去掉前後空白）的商品，未送出的草稿不影響清單。category 只留一份、放在 MenuPage，兩個條件同時生效。其餘畫面要求寫在檔案開頭的註解；不要改 ProductCard.tsx、不要用 memo。

練習 2：把 useMenuQuery() 從 useState 改成 useSearchParams，回傳 { category, keyword, setCategory, setKeyword }。category 只接受 coffee、tea、food，沒有、不合法、重複都是 'all'；keyword 讀 ?q= 並去掉前後空白。設成 'all' 或空字串時刪掉那個鍵；寫入時保留其他鍵、用 replace（切換兩次後按上一頁直接回到進菜單之前的頁面）。點了帶 query 的連結、按上一頁，回傳值都要跟著網址變。setCategory('cake') 要是型別錯誤。

練習 3：用 Zustand 的 create 完成 useCartStore。state 是 lines（{ productId, quantity }[]，依第一次加入的順序）和 orderType（預設 'here'）。add 同商品數量加一、新商品加在最後；changeQty 改數量，0 或負數移除那一列；上限 20。clear() 讓所有 state 回到初始值，action 還能用。另外 export selectCount、selectSubtotal（單價從 PRODUCTS 查）。要不可變更新（測試會凍結舊 state），件數、小計不能存成 state。

練習 4：CartWidgets.tsx 的四個元件都寫 const { … } = useOrderStore()，改個備註全部重新 render。改用 selector：AddButton 怎樣都不重新 render；CartBadge 只在件數改變時、OrderTypeSwitch 只在 orderType 改變時重新 render；CartTotals 同時要件數和小計，改備註、內用外帶不重新 render，也不能無限迴圈。用 selectCount、selectSubtotal 算；不要改 order-store.ts、不要另建 store、不要用 memo。

練習 5：後台的訂單列表可以依狀態（待製作、已完成）篩選，店長常把畫面傳給同事看。篩選條件該放哪裡？

✓ c：「要能分享給別人看」是放網址的訊號，打開網址就是同一個畫面，上一頁也能還原。a、b、d 都不在網址裡，傳給同事的連結不帶篩選。

練習 6：升級到 Zustand 5 後，const { count, note } = useCartStore(s => ({ count: selectCount(s), note: s.note })) 這個元件一掛載就出錯。原因是？

✓ b：Zustand 5 的 hook 建立在 useSyncExternalStore 上，用 Object.is 比較 snapshot；每次都是新物件，React 會丟出 Maximum update depth exceeded。用 useShallow 包住 selector，或拆成兩個各回傳一個值的 selector。c 是 Pinia 的概念。

練習 7：AddButton 裡寫 const { add } = useCartStore()，外面再包 memo，props 是不會變的 productId。客人改了備註，AddButton 會重新 render 嗎？

✓ a：memo 只擋「父元件重新 render、props 沒變」。store 的通知直接送到訂閱的元件，它選的是整個 state，備註一改就是新物件。改成 useCartStore(s => s.add) 就不會重新 render，也不需要 memo。c 錯在它選的是整個 state。

常見錯誤

  • 只有一個元件用的 state 放在頁面最上層：每次改動整頁重新 render。往下放到用它的元件；不要先用 memo 補。
  • 同一份資料存兩份：分類按鈕和清單各有 state，或網址和 useState 各存一份，遲早不同步。只留一份，放在共同祖先或網址。
  • 寫 query 時覆蓋其他鍵、沒用 replace、不驗證值：用函式形式加 { replace: true }，只接受白名單。
  • 在 action 裡 push 或改舊物件：set 收到同一個物件不會通知，畫面不更新。回傳新陣列、新物件。
  • 用 set(…, true) 重設 state：整個取代會把 action 也刪掉。重設用 set(store.getInitialState())。
  • 沒給 selector，或 selector 回傳新物件：前者任何欄位變都重新 render，後者在 Zustand 5 無限迴圈。選原始值，或用 useShallow。
  • SSR 用模組層級的 store：所有請求共用一份。用 createStore＋Context。
  • persist 不驗證、沒有 version：壞資料讓整頁壞掉。加 version、migrate，自己檢查內容。

小結

  • 先問誰要讀、正本在哪：一個元件用就放元件內，兄弟共用就提升，可分享的放網址，跨頁面又常變的放 Zustand，很少變的放 Context，正本在伺服器的交給 TanStack Query。
  • 每份狀態只有一份，放在所有用到它的元件最近的共同祖先：太高會擴大重新 render，兩份會不同步。
  • 網址用 useSearchParams 讀寫，驗證白名單、保留其他鍵、篩選用 replace；網址是唯一的來源，草稿另外放。
  • Zustand 的 set 只合併第一層，要不可變更新；set(…, true) 整個取代；重設用 getInitialState()；衍生值寫成 selector。
  • 元件一律用 selector 選需要的值；Zustand 用 Object.is 比較，多個值用 useShallow；memo 擋不了 store 的通知。
  • 模組層級的 store 在測試要每次重設，在 SSR 要改成 createStore＋Context；persist 要有 version，讀回來的資料要自己驗證。
