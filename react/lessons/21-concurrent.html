階段 5：效能與渲染 · 第 21 課

並行功能：useTransition、useDeferredValue 與 Suspense

第 19 課修好了點餐機的大部分卡頓，還剩兩個問題。第一個：「篩選商品」輸入框底下是很慢的商品格，每個商品都有大圖和加購選項。商品格真的要跟著關鍵字換內容，memo 擋不住，舊平板上打一個字要等一下才出現在輸入框裡。第二個：前台菜單照第 13 課的寫法用 use() 加 Suspense 讀資料，每次換分類，整份菜單都先變成「載入菜單中…」再出現，畫面一直閃。

兩個問題的共同點是：有些更新很急（輸入框的字、按下去的按鈕），有些可以晚一點（商品格、新分類的菜單），但 React 預設把它們當成一樣急。這課教你告訴 React 哪些不急：useDeferredValue 讓畫面的一部分晚一拍跟上，useTransition 把一次 setState 標成不急，兩者再和 Suspense 搭配，讓已經顯示的內容在等資料時留著。學完你也會知道它們和 debounce 差在哪，以及什麼時候它們幫不上忙。版本以 React 19.3.1 為準。

這課的路線：
  1. 急的更新與不急的更新：React 怎麼先畫輸入框、再畫慢的部分。
  2. useDeferredValue：打字不卡，慢的商品格晚一拍跟上；為什麼還是要 memo。
  3. 和 debounce 的差別，以及計算本身太慢時它們幫不上忙。
  4. useTransition：換分頁時按鈕先有反應，舊畫面留著。
  5. 加上 Suspense：換分類、搜尋時不再閃載入畫面；最後整理什麼情況用哪一個。
這課會用到：
  • 第 13 課的 Suspense 與 use()：元件讀還沒完成的 Promise 時暫停，最近的 <Suspense> 顯示 fallback；已經顯示過的內容再暫停，預設會被藏起來、換回 fallback。
  • 第 16 課、第 17 課的 startTransition 與 Action：傳給 startTransition 的函式叫 Action，可以是 async；Action 進行中 isPending 是 true。
  • 第 19 課的 memo 與 Profiler：props 用 Object.is 比都沒變就跳過 render；先量出誰慢、為什麼慢再動手。
  • 第 20 課的「render 必須是純的」：同樣的輸入同樣的輸出，render 裡不做副作用。
練習的測試不量毫秒（每台電腦不同），改成記錄每一次 commit 當下的畫面，檢查「輸入框已經更新、慢的部分還沒跟上」的那一刻有沒有出現。

急的更新與不急的更新

先看第一個問題為什麼卡。照第 1 課的模型，打一個字是一次 setState，React 重新 render 整個元件：輸入框和商品格在同一次 render 裡，商品格算完之前，這次 render 結束不了，輸入框的新字也就出不來。商品格越慢，打字越卡。

React 可以把一次更新標成不急。React 的文件把這種更新叫 Transition（轉換）：第 16、17 課的 Action 就是「在 Transition 裡執行的函式」，當時只用到它的 isPending，這課看它真正改變的事。依 react.dev 的 useTransition 與 useDeferredValue 文件：

  • 急的更新先處理：打字、點擊這類事件造成的更新照常立刻 render、commit。
  • 不急的 render 可以被打斷：React 正在 render 不急的更新（例如很慢的商品格）時，使用者又打了一個字，React 會先處理這個字，再從頭重新 render 不急的部分。
  • 舊畫面先留著：不急的更新還沒 render 完（或在等資料）時，畫面上維持舊的內容，完成後一次換上。

要把哪個更新標成不急，有兩個工具，差別在你手上有什麼（react.dev 的 startTransition 文件）：

  • 你能呼叫那個 state 的 set 函式：在 startTransition(() => setX(…)) 裡呼叫，這次 setState 就是 Transition。
  • 你只拿到一個值（props、自訂 hook 的回傳值），或那個 state 必須立刻更新（輸入框）：用 useDeferredValue(值) 拿到一個「晚一拍」的版本，交給慢的那一塊。

這就是開場兩個問題的最小答案：打字卡，輸入框的 state 不能延後，所以把延後的值交給商品格；換分類閃載入畫面，換分類的 setState 由你呼叫，所以包進 startTransition。後面各用一節展開。

「render 會被丟掉重來」也是第 20 課說 render 必須是純的另一個原因。背景的 render 可能跑了一半就被放棄、用新的值重跑；render 裡如果改了外面的變數、送了請求，被放棄的那次也已經做了。React 只會 commit 最後完成的那次，effect 也只在 commit 之後才執行（useDeferredValue 文件：背景 render 在 commit 之前不會觸發 effect）。

對照 Vue：Vue 3 的更新是同步排進同一個佇列，沒有「急、不急」的區分，也沒有可以打斷的 render。在 Vue 遇到同樣的卡頓，常見的做法是用 lodash 的 debounce 或 VueUse 的 refDebounced 延後更新，第 3 節會比較它和 useDeferredValue 的差別。

useDeferredValue：讓慢的那一塊晚一拍跟上

先處理打字卡的商品格。上一節說了，輸入框的 state 必須立刻更新，所以不動它，而是另外拿一個延後的版本給商品格：

import { memo, useDeferredValue, useState } from 'react'

const Grid = memo(ProductGrid)                     // 模組層級包一次（第 19 課）

export function MenuFilter({ products }: { products: readonly Product[] }) {
  const [keyword, setKeyword] = useState('')
  const deferredKeyword = useDeferredValue(keyword)   // 晚一拍的版本
  const stale = keyword !== deferredKeyword           // 兩個不一樣 = 商品格還沒跟上

  return (
    <>
      <label>篩選商品 <input value={keyword} onChange={e => setKeyword(e.target.value)} /></label>
      <section aria-label="商品" aria-busy={stale}>
        <Grid products={products} keyword={deferredKeyword} />
      </section>
    </>
  )
}

依 react.dev 的 useDeferredValue 文件，打了「拿」之後 React 分兩步：

  1. 先用新的 keyword、舊的 deferredKeyword render：輸入框顯示「拿」，交給商品格的還是空字串，commit。
  2. 在背景用兩個都是「拿」的值再 render 一次：完成就 commit，商品格跟上；這段期間又打了字，就放棄重來，永遠用最新的值。

練習的測試在每次 commit 時記下畫面，React 19.3.1 實測打一個字剛好兩次 commit：

commit 1：輸入框「拿」  商品格：全部 6 項   aria-busy="true"
commit 2：輸入框「拿」  商品格：拿鐵 $110    aria-busy="false"

stale 是 react.dev 示範的寫法：值和延後的值不一樣，代表畫面上的商品格還是舊的，可以用來讓它變淡或加上 aria-busy，讓使用者（和讀螢幕軟體）知道內容還在更新。

為什麼還要 memo

拿掉 memo 試試看：第 1 步「先用舊的值 render」時，MenuFilter 自己 render 了，沒包 memo 的 ProductGrid 照第 19 課的規則跟著 render，用的是舊的 keyword，但一樣慢，輸入框還是被它擋住。實測打兩個字，ProductGrid 從 2 次變成 4 次 render。react.dev 的文件明寫這個做法要搭配 memo：useDeferredValue 讓第 1 步傳給商品格的 props 跟上一次相同，memo 才能讓它在急的那次 render 跳過。

同樣的道理，交給商品格的每一個值都要是延後的。在父元件先 products.filter(p => p.name.includes(keyword)) 再傳下去，急的那次 render 就已經算出新的陣列，商品格的 props 變了，又回到每個字都要等它。

還有幾個文件寫明的行為：

  • 值要是原始值或在 render 外建立的物件：useDeferredValue({ keyword }) 每次 render 都是新物件，Object.is 永遠不同，每次 render 都會多排一次背景 render。
  • 第二個參數 initialValue（19.3.1 的型別是 useDeferredValue<T>(value: T, initialValue?: T)）：第一次 render 時回傳它，再在背景用真正的值 render。沒給時，第一次 render 不延後，因為還沒有「舊的值」可以先畫。適合第一次就很重的畫面，例如 useDeferredValue(query, '') 先畫空的結果。
  • 沒有固定的延遲：急的 render 一結束，React 馬上開始背景 render。在快的電腦上幾乎看不出延遲，慢的裝置上才會看到商品格晚一點跟上。
💡 實務上：先確認慢的是 render，再拿 useDeferredValue
咖啡店後台的訂單篩選、報表的圖表、上百列的商品表，都是常見的使用位置：一個輸入控制一大塊很重的畫面。動手前先用第 19 課的 Profiler 錄一次：打字時花時間的是不是某個元件的 render。是，就把延後的值交給它並包 memo；如果時間花在 effect、事件處理函式或網路請求，useDeferredValue 一點用都沒有，因為它只延後 render。PR 裡附上前後的 Profiler 截圖，reviewer 才看得出 memo 和延後的值有沒有接對。

和 debounce 的差別，以及它們幫不上忙的時候

上一節的需求，很多人第一個想到的是 debounce：等使用者停手 300ms 才更新商品格。react.dev 的 useDeferredValue 文件專門比較了這件事：

debounce／throttleuseDeferredValue
多久之後更新自己選固定的時間（停手 300ms、每秒最多一次）沒有固定延遲，看裝置多快：快的電腦幾乎立刻，慢的才晚一點
慢的 render 開始之後擋住主執行緒，那時打的字一樣卡，只是卡的時間點往後移可以被打斷：又打字就先處理字，再從頭 render
打完字之後至少再等那段固定時間馬上開始跟上
能不能減少網路請求能不能，它只延後 render

所以兩者不是互相取代。文件的結論是：要優化的工作不在 render 裡時，debounce 和 throttle 仍然有用，例如減少送出的請求；兩種也可以一起用。練習 1 的商品格是純 render 的工作，用 debounce 反而讓打完字還要多等 300ms。

Transition 和 useDeferredValue 都不會讓 render 本身變快，只是決定先後順序。下面這幾種情況它們幫不上忙，要回到別的做法：

  • 計算本身太慢，而且每個操作都要它：例如商品格每次 render 都要排序上萬筆資料。延後只是讓它晚一點卡，換分類時一樣要等。回到第 19 課：用 Profiler 找出慢的元件，useMemo 快取計算、memo 跳過不必要的 render，或者只 render 看得到的那幾列。
  • 第一次 render：沒有舊畫面可以留，該等的還是要等（initialValue 只能先畫一個便宜的版本）。
  • 慢的工作不在 render 裡：事件處理函式裡的同步迴圈、effect 裡的計算，React 沒辦法打斷你的 JavaScript。
  • 網路慢：等資料的時間不會變短。它們能做的是等待時保留舊畫面（後面兩節），請求要不要取消、要不要合併，還是 TanStack Query、debounce 這類工具的事。
💡 實務上：搜尋框常常 debounce 和 useDeferredValue 一起用
線上點餐的搜尋框：每打一個字送一次請求，伺服器和行動網路都吃不消，所以請求用 debounce（或 TanStack Query 的快取）控制次數；結果清單很長、render 很重，就再用 useDeferredValue 讓輸入框不卡。code review 看到 debounce 包住純 render 的更新（例如篩選一份已經在記憶體裡的清單），可以建議換成 useDeferredValue：使用者不用多等那段固定時間，也少了計時器要清理。

useTransition：換分頁時按鈕先有反應

前面處理的是「拿到一個值」的情況。換分頁不一樣：分頁的 state 由你自己 set，可以直接把這次 setState 標成 Transition。店長後台的報表有「今日／本週／本月」三個分頁，SlowReport 每換一次區間都要重算上千筆訂單。按下「本月」之後整個頁面要等報表算完才有反應，店長以為沒按到，又多按好幾次。

import { useState, useTransition } from 'react'

export function ReportTabs() {
  const [range, setRange] = useState<Range>('today')
  const [isPending, startTransition] = useTransition()

  return (
    <div>
      {RANGES.map(r => (
        <button key={r.value} type="button" aria-pressed={range === r.value}
          onClick={() => startTransition(() => setRange(r.value))}>{r.label}</button>
      ))}
      {isPending && <p role="status">切換中…</p>}
      <SlowReport range={range} />
    </div>
  )
}

按下「本月」，實測同樣是兩次 commit：

commit 1：選中「今日」  切換中…   今日的銷售報表     ← 急的：只有 isPending 變了
commit 2：選中「本月」  （沒有）  本月的銷售報表     ← Transition 完成

第一次 commit 只有 isPending 變成 true，這是急的更新，所以店長按下去馬上看到反應；range 的改變在 Transition 裡，報表和選中的按鈕一起留在「今日」，直到本月的報表 render 完才一起換。這也是 react.dev 示範的分頁寫法：按鈕顯示 pending，選中的分頁等內容好了才換。

依 react.dev 的 useTransition 與 startTransition 文件，寫的時候要注意：

  • 傳給 startTransition 的函式會立刻執行，執行期間同步呼叫的 setState 才是 Transition。寫在 setTimeout 裡的不算；async 函式 await 之後的 setState 也不算，要再包一層 startTransition（第 16 課遇過的限制）。
  • 不能用 Transition 控制輸入框：onChange={e => startTransition(() => setText(e.target.value))} 是文件列出的錯誤寫法。輸入框的 state 要用一般的 setState，慢的部分改用上一節的 useDeferredValue。
  • 需要 isPending 就用 useTransition：直接 import { startTransition } from 'react' 也能標成 Transition，而且可以在元件外面呼叫（例如資料函式庫裡），但它沒有 isPending，畫面上就沒辦法顯示「切換中」。
  • Action 進行中 isPending 一直是 true：傳 async 函式時，isPending 會維持到 Action 結束、最後的 state 畫上去為止，這就是第 17 課 useActionState、第 16 課 useOptimistic 用到的那個 pending。
  • 同時有好幾個 Transition 時，React 目前會把它們合在一起：第 16 課看過「全部結束才一起換」的現象，文件說這個限制未來可能移除。

同樣的事也可以用 useDeferredValue(range) 做：按鈕立刻換成「本月」，報表用延後的值晚一點換。差別在畫面上會有一段時間「選中本月，報表還是今日」，也沒有 isPending 可用。分頁這種「你自己 set、按鈕和內容要一致」的情況，用 useTransition。

加上 Suspense：已經顯示的內容不再換成 fallback

報表慢在 render；開場的第二個問題慢在等資料。前台菜單的寫法跟第 13 課練習 2 一樣：Promise 在點擊時建立、存進不會暫停的父元件的 state，MenuList 用 use() 讀：

function select(next: Category) {
  setCategory(next)
  setItemsPromise(api.getCategory(next))   // 新的 Promise：MenuList 暫停
}

<Suspense fallback={<p role="status">載入菜單中…</p>}>
  <MenuList itemsPromise={itemsPromise} />
</Suspense>

第 13 課說過：已經顯示過的內容再暫停，React 會把它藏起來、顯示 fallback。所以每換一次分類，咖啡的菜單就消失，換成「載入菜單中…」，茶的資料到了才出現。react.dev 的 Suspense 文件說這種「把看得到的畫面換成 fallback」的體驗很突兀，解法是把這次更新標成 Transition：

const [isPending, startTransition] = useTransition()

function select(next: Category) {
  const promise = api.getCategory(next)   // 在事件裡建立，不在 render 裡
  startTransition(() => {                 // 分類和菜單一起換
    setCategory(next)
    setItemsPromise(promise)
  })
}

{isPending && <p role="status">切換中…</p>}
<Suspense fallback={…}>…</Suspense>

文件的規則是：在 Transition 裡，React 會等到資料夠了，避免把已經顯示的內容藏起來。所以按「茶」之後，咖啡的菜單留在畫面上，isPending 讓「切換中…」出現；茶的資料到了，分類按鈕和菜單一起換。連按「茶」再按「點心」，兩個 Transition 合在一起，茶先回來也不會閃出茶的菜單，等點心到了才換。

這條規則有兩個邊界，都是文件寫明的：

  • 只有不急的更新才會等：React 只在 startTransition 或 useDeferredValue 的更新裡避免出現 fallback，一般的 setState 照樣立刻換成 fallback。
  • 新出現的 Suspense 邊界照樣顯示 fallback：等的是「已經顯示的內容」。第一次載入、或者給 Suspense 一個會變的 key（<Suspense key={category}>），都是新的邊界，Transition 也擋不住它顯示 fallback。第 13 課用 key 重設 Suspense，正是為了「換成不同的內容時要顯示 fallback」；換分類不想閃，就不要加。

反過來，有時你想要顯示 fallback：文件的例子是從一個人的個人頁換到另一個人的，留著上一個人的資料會誤導。這時在內容上加 key，React 會把它當成不同的元件、重設裡面的 Suspense 邊界。

搜尋框：useDeferredValue 加 Suspense

搜尋框不能用 startTransition（上一節：輸入框的 state 不能是 Transition），所以換 useDeferredValue。文件寫明它和 Suspense 整合：延後的值造成的背景 render 暫停時，使用者看不到 fallback，會繼續看到舊的內容，直到資料到了。

const [query, setQuery] = useState('')
const deferredQuery = useDeferredValue(query)
const keyword = deferredQuery.trim()        // 結果區只看延後的值
const stale = query !== deferredQuery

<input value={query} onChange={e => setQuery(e.target.value)} />
<div role="region" aria-label="搜尋結果區" aria-busy={stale}>
  <Suspense fallback={<p role="status">搜尋中…</p>}>
    {keyword ? <SearchResults cache={cache} keyword={keyword} /> : <p>輸入品名開始搜尋</p>}
  </Suspense>
</div>

打「卡」等結果時，畫面留著上一次的內容、aria-busy 是 true；結果回來才換。SearchResults 用 use(cache.read(keyword))，cache 讓同一個關鍵字永遠拿到同一個 Promise（第 13 課：傳給 use 的 Promise 要被快取），刪字回到搜尋過的「卡」時，結果立刻出現、不再送請求。文件也提醒：useDeferredValue 本身不會減少請求，每個字還是一次請求，延後的是「顯示結果」。

如果把搜尋的 setQuery 放進 startTransition，React 19.3.1 實測更糟：Transition 在等資料，輸入框的值也跟著不 commit，打了「拿」，輸入框還是空的，等結果回來字才出現。這就是文件說 Transition 不能控制輸入框的實際後果。

第 18 課的路由器也用了 Transition：依 React Router 8.5.1 的型別說明，RouterProvider 預設把路由的 state 更新包在 React.startTransition 裡（可以用 useTransitions 這個 prop 關掉），文件也提醒你自己再包 startTransition 可能造成問題。換頁時舊頁面留著、useNavigation 顯示「更新中…」，則是路由器自己的 loader 機制。react.dev 的 Suspense 文件也寫明，整合 Suspense 的路由器應該自動把換頁包成 Transition。

💡 實務上：載入狀態分兩種，大的 fallback 和小的「更新中」
這跟第 15 課 TanStack Query 的 isPending／isFetching 是同一個設計：沒有內容時顯示大的 fallback（Suspense），有舊內容又在等時留著它、加一個小提示（isPending、aria-busy、變淡）。咖啡店的菜單分頁、訂單篩選、分頁的下一頁都屬於後者。設計稿只畫了一種「載入中」時，資深工程師會主動跟設計師確認第二種長什麼樣子；code review 看到「每次切換都整塊換成 spinner」，先問這次更新能不能放進 Transition，再看 Suspense 是不是包太大或加了會變的 key。

練習

在 learn/ 執行 node check.mjs react 21，檔案在 react/practice/work/21/。練習 1、2 的測試用 <Profiler> 在每次 commit 時記下畫面，檢查「急的先 commit、慢的後 commit」的那一刻；練習 1 另外把 ProductGrid 換成會記數的版本。練習 3、4 的假 API 由測試決定什麼時候回傳，Suspense 藏起來的內容（display: none）不算看得到。四題互不相依，標了「不用改」的檔案不要改。

練習 1：MenuFilter 每打一個字，很慢的 ProductGrid 都跟輸入框在同一次 render 裡。用 useDeferredValue 讓商品格晚一拍：每打一個字剛好兩次 commit，第一次輸入框已經是新的字、商品格還是舊的結果，第二次商品格跟上；商品格還沒跟上時 <section aria-label="商品"> 是 aria-busy="true"，跟上了是 "false"。每打一個字 ProductGrid 只能 render 一次（在背景那次），所以要在 MenuFilter.tsx 的模組層級用 memo 包住它（不要改 ProductGrid.tsx），交給它的 props 都要是延後的值。不要用 setTimeout 做 debounce：打完字商品格要馬上是最新的結果。

練習 2：ReportTabs 按下分頁按鈕後，要等很慢的 SlowReport 算完才有反應。用 useTransition 改成：按下後第一次 commit 顯示 <p role="status">切換中…</p>，舊的報表留在畫面上，選中的按鈕（aria-pressed="true"）也還是舊的分頁；第二次 commit 換成新的報表與新的按鈕，「切換中…」消失。一次切換剛好兩次 commit。不要改 SlowReport.tsx。

練習 3：CategoryMenu 每次換分類，整份菜單都被換成 Suspense 的「載入菜單中…」。第一次載入維持顯示這個 fallback；之後換分類時，舊的菜單留在畫面上（不能被藏起來），不顯示「載入菜單中…」，改顯示 <p role="status">切換中…</p>，選中的按鈕仍是舊的分類，新分類的資料到了才和按鈕一起換，「切換中…」消失。每按一次分類在按下時呼叫 api.getCategory 一次，父元件重新 render 不能再呼叫；連按茶和點心，不管哪個請求先回來，中途都不能閃出茶的菜單，最後顯示點心。不要改 menu-api.ts。

練習 4：MenuSearch 每打一個字，結果區就換成「搜尋中…」。用 useDeferredValue 改成：輸入框永遠立刻顯示打的字；等新結果時畫面留著上一次的內容（上一次的結果，或一開始的「輸入品名開始搜尋」），不顯示「搜尋中…」，這段期間 <div role="region" aria-label="搜尋結果區"> 是 aria-busy="true"，結果回來後換掉並回到 "false"。交給 SearchResults 的關鍵字用延後的值去掉前後空白，是空字串時不搜尋、顯示提示；刪字回到搜尋過的關鍵字，直接顯示快取的結果，不再呼叫 api.search。不要改 search-cache.ts、SearchResults.tsx。

練習 5：同事在篩選框加了 const deferred = useDeferredValue(keyword)，把 deferred 交給很慢的 ProductGrid，但 ProductGrid 沒有包 memo。舊平板上打字還是卡，為什麼？

✓ useDeferredValue 讓急的那次 render 傳給 ProductGrid 的值跟上一次一樣，但「一樣」只有 memo 才會拿來跳過 render；沒有 memo，父元件 render 它就 render。a 錯在它沒有固定延遲，不用等停手；c 反了，文件建議傳原始值，每次新建的物件才有問題；d 是文件列出的錯誤寫法，輸入框的 state 不能是 Transition。

練習 6：線上點餐的搜尋框，每打一個字送一次 api.search，結果清單也很長。下面哪個說法正確？

✓ 文件寫明 useDeferredValue 本身不會減少網路請求，並且說要優化的工作不在 render 裡時（例如請求），debounce 仍然有用，兩者可以一起用。a 錯在它延後的是顯示結果；b 錯在 debounce 之後的 render 一樣會擋住主執行緒，只是卡的時間點往後移，useDeferredValue 的背景 render 才能被打斷。

練習 7：菜單換分類時已經用 startTransition 包住 setCategory 和 setItemsPromise，但每次換分類還是先閃出「載入菜單中…」。程式裡寫的是 <Suspense key={category} fallback={…}>。原因是？

✓ 文件：Transition 期間 React 避免把已經顯示的內容藏起來，但新 render 出來的 Suspense 邊界會立刻顯示 fallback。key 一變，舊的邊界連同內容被丟掉，新的邊界沒有可以保留的東西。拿掉 key 就好；只有「換成不同的內容、不該留著舊的」時才用 key 重設。b 錯在文件的示範就是兩者一起用；c 錯在 Transition 中暫停時，已經顯示的內容會留著。

常見錯誤

  • 只包 memo，商品格直接收輸入框的值：商品格的 props 每個字都變，memo 擋不住，打字一樣卡。交給它的值用 useDeferredValue。
  • 用了 useDeferredValue，慢的元件沒有 memo：急的那次 render 它跟著用舊的值 render，一樣慢。在模組層級用 memo 包住它。
  • 在父元件用新的值先算好再傳下去（例如 products.filter(… keyword …)）：急的那次 render 就給了新的 props。交給慢的元件的每一個值都要從延後的值算。
  • 用 setTimeout 做 debounce 來處理慢的 render：打完字還要多等固定的時間，慢的 render 開始之後一樣擋住輸入。純 render 的工作用 useDeferredValue；debounce 留給減少請求。
  • 把輸入框的 setState 放進 startTransition：文件列出的錯誤寫法；搭配 Suspense 時輸入框會停在舊的值，資料回來字才出現。輸入框用一般的 setState，慢的部分用延後的值。
  • 延後或 Transition 期間沒有任何提示：畫面上的內容跟輸入或按下的按鈕不一致，使用者不知道還在更新。用 value !== deferredValue 或 isPending 加上 aria-busy、變淡或「切換中…」。
  • 需要 pending 時用 react 直接匯出的 startTransition：它沒有 isPending。元件裡用 useTransition。
  • 用 isPending 把舊內容換掉（isPending ? 載入中 : 內容）：Transition 本來就是為了留著舊內容，這樣寫又回到閃一下。isPending 只用來加一個小提示。
  • 按鈕的 state 立刻更新、內容晚一點換（分頁用 useDeferredValue、或 setCategory 放在 startTransition 外面）：有一段時間選中的分頁和畫面上的內容對不起來。你自己 set 的分頁，兩個 setState 放進同一個 startTransition。
  • 換分類時沒有用 Transition：已經顯示的菜單被藏起來、換成 fallback，畫面一直閃。換分類的 setState 放進 startTransition。
  • 給 Suspense 一個會變的 key：每次都是新的邊界，Transition、useDeferredValue 都擋不住 fallback。只有「換成不同的內容、要清掉舊的」時才加 key。
  • 在 render 裡呼叫 API 建立要給 use() 的 Promise：每次重試 render 都是新的 Promise，畫面永遠等不到（第 13 課）。在事件裡建立、存進 state，或用快取。
  • 交給會暫停的元件的是即時的值，延後的值只拿來算提示：等資料時一樣顯示 fallback。會暫停的元件收延後的值。
  • 把 Transition、useDeferredValue 當成效能修正：它們不讓 render 變快，第一次 render、每次都慢的計算、事件或 effect 裡的工作都幫不上忙。先量測，照第 19 課修。
  • await 之後的 setState 沒有再包 startTransition、或在 setTimeout 裡 set：那次更新不算 Transition。只有 startTransition 的函式執行期間同步呼叫的 setState 才算。

小結

  • React 可以把更新分成急的和不急的（Transition）：急的先 render、commit；不急的在背景 render，可以被新的輸入打斷、從頭重來，完成前畫面留著舊的。render 可能被丟掉重來，所以必須是純的。
  • 手上是 set 函式就用 useTransition：startTransition(() => setX(…))，isPending 在急的那次 commit 就變成 true，Action 結束才變回 false。輸入框不能用 Transition 控制；await 之後的 setState 要再包一層。
  • 手上是一個值、或輸入框必須立刻更新，就用 useDeferredValue：延後的值交給慢的元件並包 memo；value !== deferredValue 表示還沒跟上；initialValue 讓第一次 render 也能延後。
  • 和 Suspense 搭配時，Transition 與延後的值會避免把已經顯示的內容換成 fallback；新的 Suspense 邊界（包括 key 換了）照樣顯示 fallback。
  • 和 debounce 的差別：沒有固定延遲、背景 render 可以被打斷，但不會減少請求。並行功能只調整先後，不讓計算變快；計算本身慢回到第 19 課的量測與記憶化。
