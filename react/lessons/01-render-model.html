階段 1：心智模型：從 Vue 到 React · 第 1 課

重新 render 是什麼：UI 是 state 的函式

在 Vue 裡，你寫 qty.value++，用到 qty 的畫面就自己更新。換到 React，同樣的需求要寫 setQty(qty + 1)。看起來只是換個寫法，背後的模型卻不一樣：Vue 記下你讀了哪些資料，資料一改就去通知讀過它的地方；React 不追蹤讀取，你呼叫 set 函式之後，它把整個元件函式重新呼叫一次，拿新的結果跟上一次比，再把差異更新到 DOM。

從 Vue 轉過來的人最常見的 bug 都出在這個差異上：改了物件畫面沒動、set 完馬上讀到舊值、元件裡的變數每次都歸零。

這課的路線：
  1. 同一個購物車，兩種更新方式：Vue 記下誰讀了資料、寫入時通知；React 不追蹤，你呼叫 set，它就重新呼叫整個元件函式（開場問題的最小答案）。
  2. 一次更新的三步、元件每次從頭執行：set 之後 React 依序做了哪些事，為什麼元件裡的變數每次都歸零。
  3. state 是快照、React 只看 set 和 Object.is：為什麼 set 完馬上讀到舊值，直接改物件畫面卻不動。
  4. 父元件 render 與純函式：父元件 render 時子元件怎麼辦，副作用為什麼不能寫在元件本體，Strict Mode 為什麼把元件呼叫兩次。
這課會用到：
  • Vue 課第 1 課的依賴追蹤：讀取資料時記下誰用了它，寫入時通知那些地方更新。
  • TS 課第 1 課的閉包：函式記得它被建立時那個範圍裡的變數。
  • TS 課第 2 課的參考與 Object.is：物件和陣列的變數存的是參考，Object.is 比的是「是不是同一個」，不比內容。
這一課的範例和練習是在瀏覽器裡執行的 TypeScript，沒有載入 React，用一般函式模擬 React 的行為；真正的 React 程式碼（React 19.3.1）只用 <pre> 展示。從第 2 課開始，練習在你的電腦上用真的 React 跑。

同一個購物車，兩種更新方式

咖啡店的點餐頁有一個購物車：小計、右上角的件數徽章、結帳按鈕（購物車空的時候不能按）。Vue 課第 1 課講過，手動更新每一個地方很容易漏，所以框架都走宣告式（declarative）：你只描述「畫面 = f(狀態)」，由框架負責更新。Vue 和 React 都是這樣，差在「框架怎麼知道該更新」。

Vue 的寫法：

<script setup lang="ts">
import { ref, computed } from 'vue'

const qty = ref(1)
const subtotal = computed(() => qty.value * 80)
console.log('setup 執行')   // 只在元件建立時印一次
</script>

<template>
  <p>小計 {{ subtotal }} 元</p>
  <button @click="qty++">再一杯</button>
</template>

React 的寫法（React 元件是一個回傳畫面描述的函式；裡面像 HTML 的語法叫 JSX，編譯後是一般的函式呼叫，回傳描述畫面的物件，第 2 課細講）：

import { useState } from 'react'

export function CartPanel() {
  const [qty, setQty] = useState(1)
  const subtotal = qty * 80
  console.log('CartPanel 執行')   // 每次 render 都會印
  return (
    <>
      <p>小計 {subtotal} 元</p>
      <button onClick={() => setQty(qty + 1)}>再一杯</button>
    </>
  )
}

按三次「再一杯」，Vue 的 setup 執行 只印一次：<script setup> 只在元件建立時執行，之後是 Vue 追蹤到 qty 被改，重跑模板的 render 函式。React 的 CartPanel 執行 印四次：初次顯示一次、按鈕三次。subtotal 不需要 computed，整個函式每次都重新執行，它每次都用最新的 qty 算。

在 React 裡，「呼叫你的元件函式」就叫 render（渲染）。重新 render（re-render）就是再呼叫一次。把元件想成純粹的計算：

一次更新的三步：trigger、render、commit

React 官方文件把畫面的每一次更新分成三步：

  1. 觸發（trigger）：有兩種情況會觸發 render。一是 App 啟動時的初次 render（呼叫 createRoot(…) 再 .render(<App />)）；二是某個元件的 state 被 set 函式更新。
  2. 渲染（render）：React 呼叫元件函式，拿到新的畫面描述。初次呼叫根元件；之後呼叫 state 改變的元件和它底下的元件。
  3. 提交（commit）：把結果套用到 DOM。初次把所有節點放上去；之後只對跟上一次不同的地方做最少的 DOM 操作。

下面用一般函式模擬這三步。注意第二次 setState：元件被呼叫了，但算出來的字一樣，DOM 就不用動。

這就是「render 不等於更新 DOM」。Vue 也有比對新舊虛擬 DOM 的步驟（Vue 課第 7 課），差在決定「哪些元件要重跑」的方式，第 6 節再比較。

💡 實務上：render 次數多，不等於畫面慢
剛轉到 React 的人看到元件印了好幾次 log，常會急著加 memo、useMemo。大部分元件的 render 只是跑一個函式、產生幾個物件，很便宜；真正花時間的通常是大量 DOM 變動，或在 render 裡做很重的計算（例如把後台上千筆訂單排序、分組）。資深的做法是先用 React DevTools 的 Profiler 量出哪個元件慢、慢多少，再決定要不要優化（第 19 課）。

元件每次都從頭執行：區域變數留不住

既然每次 render 都重新呼叫函式，函式裡的區域變數每次都是新的。從 Vue 過來最容易踩的坑，就是把 <script setup> 裡「宣告一次、一直存在」的習慣帶過來：

改區域變數有兩個問題：值在下一次 render 就不見了，而且改它不會觸發 render。所以 React 提供 useState：值存在 React 那邊（元件函式外面），每次 render 再交給你，set 函式負責「存新值＋觸發 render」。極簡的模擬：

state 是快照：set 不會改到這次 render 的變數

上面的 onStamp 是某一次 render 建立的閉包，記住的是那一次 render 的 stamps。React 官方文件把這叫做 state 的快照（snapshot）：一次 render 裡的 props、state、事件處理函式，都是用那一刻的 state 算出來的。set 函式只影響下一次 render。

咖啡店的「+3 杯」按鈕：

function CupCounter() {
  const [cups, setCups] = useState(0)
  return (
    <button onClick={() => {
      setCups(cups + 1)
      setCups(cups + 1)
      setCups(cups + 1)
      console.log(cups)
    }}>
      {cups} 杯
    </button>
  )
}

按一下，console 印出 0，按鈕變成 1 杯，不是 3。在這次 render 裡 cups 就是 0，三行其實都是 setCups(0 + 1)。另外，React 會等事件處理函式全部跑完才處理這些更新，一次事件只 render 一次，這叫批次更新（batching）。用模擬看清楚：

要在同一個事件裡根據前一個結果連續更新，傳一個函式給 set，叫更新函式（updater function）：

setCups(n => n + 1)
setCups(n => n + 1)
setCups(n => n + 1)   // 按一下變成 3 杯

下一次 render 時 React 依序處理佇列：值直接取代，函式就把「目前算到的結果」傳進去、拿回傳值當新的結果。所以 setCups(cups + 5) 接著 setCups(n => n + 1)，從 0 開始得到 6；再接 setCups(42) 就是 42。練習 2 會讓你寫出這個處理佇列的函式。

對照 Vue：qty.value++ 之後馬上讀 qty.value 就是新值，只有 DOM 等到下一個 tick 才更新（Vue 課第 6 課）。React 連你手上的變數都還是舊的，它就是這次 render 的一個常數。

💡 實務上：set 完要用新值，就自己先算出來
咖啡店的點餐頁按「加入購物車」後，要同時更新購物車、把新的件數送去後端。常見的錯誤寫法是 setCount(count + 1) 之後接著 api.save(count)，送出去的是舊值，客服就會收到「購物車少一杯」的回報。正確做法是先 const next = count + 1，再 setCount(next)、api.save(next)。

React 怎麼知道 state 變了：只看 set 和 Object.is

Vue 用 Proxy 攔截每一次寫入，所以 order.items.push('可頌') 也會更新畫面。React 沒有攔截任何東西，它只在你呼叫 set 函式時，用 Object.is 比較新值和目前的 state：一樣就跳過這次 render（連子元件一起跳過），不一樣才 render。

function OrderPanel() {
  const [order, setOrder] = useState({ items: ['拿鐵'] })

  function addCroissant() {
    order.items.push('可頌')   // 🚩 改的是舊物件
    setOrder(order)            // 🚩 同一個物件，Object.is 判定沒變，什麼都不會發生
  }

  function addCake() {
    setOrder({ ...order, items: [...order.items, '起司蛋糕'] })   // ✓ 新物件
  }
  // …
}

更糟的是，畫面暫時沒變，等別的 state 觸發 render 時，那筆改動才突然出現，看起來像隨機的 bug。React 的規則是：放進 state 的物件和陣列都當成唯讀，要改就建立新的。只要遵守這條，資料有變就一定是新的參考，比較一次參考就夠了，不用逐層比內容。Object.is 跟 === 幾乎一樣，差在 NaN 等於 NaN、0 不等於 -0（TS 課第 2 課）。第 3 課會練巢狀物件和陣列的不可變更新（immutable update）。

💡 實務上：code review 時找 state 上的 push、sort、直接賦值
從 API 拿到訂單列表放進 state 之後，最常見的錯誤是 orders.sort(…) 或 order.status = 'done'：改到原本的資料，畫面時好時壞。資深工程師看到 state 變數後面接 push、splice、sort、reverse 或屬性賦值，會要求改成產生新值的寫法，例如 [...orders, newOrder]、orders.toSorted(…)（ES2023，回傳新陣列）、orders.map(o => o.id === id ? { ...o, status: 'done' } : o)。同時寫 Vue 和 React 的團隊特別容易把「直接改」的習慣帶過來。

父元件 render，子元件預設也跟著 render

React 文件寫明：預設情況下，元件重新 render 時，React 會遞迴地重新 render 底下所有子元件，不管 props 有沒有變。Vue 的子元件只有在收到的 props 有變時才更新。

Menu 跟 qty 無關，還是被呼叫了；不過結果一樣，commit 時不會動到菜單的 DOM。這是 React 的取捨：模型簡單（state 變了就從那裡往下重算），代價是多做一些 render。真的量到某個子元件很慢，可以用 memo 讓它在 props 沒變時跳過（第 19 課），或讓 React Compiler 自動記憶化（第 20 課）。反過來說，state 放得越上層，一改受影響的子樹就越大，這是「狀態放哪裡」（第 14 課）和 Context（第 11 課）要一直考慮的事。

render 必須是純函式

因為 React 隨時可能呼叫你的元件、呼叫幾次也不一定，元件函式必須是純函式（pure function）。React 文件的兩個條件：

  • 同樣的輸入，同樣的輸出：同樣的 props、state，回傳同樣的畫面描述。
  • 只管自己的事：render 時不能改 render 之前就存在的變數或物件，包括 props、state 和外部變數。在 render 裡新建的陣列、物件，自己改沒關係。

為了幫你抓出不純的元件，Strict Mode（把元件包在 <StrictMode> 裡）在開發模式下會把元件函式、傳給 useState 的初始值函式、更新函式都呼叫兩次。Vite 的 React 範本預設就用它包住整個 App（第 3 課會在真的 React 裡看到它抓出的 bug）。純函式呼叫兩次結果一樣；不純的元件就會露出馬腳，例如上面的杯子編號跳號。這只發生在開發模式，正式環境（production build）不會。事件處理函式不會被呼叫兩次，副作用（發請求、改 DOM、寫 localStorage）就該放在那裡，或放在 第 5 課的 useEffect。

💡 實務上：log 印兩次，不要拿掉 StrictMode
新人在開發時看到 console.log 印兩次、updater 被呼叫兩次，第一個反應常是把範本裡的 <StrictMode> 拿掉。這等於把警報器關掉：被雙重呼叫抓出來的，通常是 render 裡改了外部陣列、updater 裡 push 了 state，這些 bug 在正式環境會變成「偶爾多一筆訂單明細」這類很難重現的問題。正確做法是把元件和 updater 改成純函式；真的需要只做一次的事，放進事件處理函式。

練習

練習 1：把購物車畫面寫成 state 的純函式 cartView(cart)。現在的寫法有兩個問題：用函式外的變數快取上一次的結果（品項數一樣就直接回傳舊的），還會順手改掉傳進來的 cart。改成每次都只從 cart 算出結果：

  • badge：`${總杯數} 件`，總杯數是每一列 qty 的加總。
  • rows：qty 大於 0 的列，照原本的順序，每列 `${品名} × ${數量} = ${單價 × 數量} 元`。
  • total：`合計 ${N} 元`，N 是小計總和減掉 discount，最少是 0。
  • canCheckout：總杯數大於 0 才是 true。
  • 不能改 cart（測試會傳入凍結的物件），不能用函式外的變數記住上一次的結果；同樣的 cart 呼叫幾次，結果都一樣。

練習 2：寫出 React 處理 state 更新佇列的方法 getFinalState(base, queue)。base 是目前的杯數，queue 是一次事件裡依序呼叫 setCups(…) 傳進去的東西，回傳下一次 render 的杯數：

  • 從 base 開始，照順序處理每一項。
  • 數字：直接取代目前算到的結果（等於 setCups(5)）。
  • 函式：把目前算到的結果傳進去，拿回傳值當新的結果（等於 setCups(n => n + 1)）。每個函式只能呼叫一次。
  • 不能改 queue（測試傳入凍結的陣列）。

練習 3：寫一個迷你的 createRoot(component, initial)，模擬 trigger → render → commit。component 是元件：收到 state，回傳畫面上的字。回傳的物件有：

  • screen()：目前畫面上的字；renders()：元件被呼叫的次數；commits()：畫面被更新的次數。
  • 建立時就 render 一次並 commit（renders()、commits() 都是 1）。
  • setState(next)：next 跟目前的 state 用 Object.is 比較，一樣就什麼都不做（不呼叫元件）；不一樣就存起來、用新的 state 呼叫元件一次，算出來的字跟畫面上不同才更新畫面並把 commits 加一。
  • 每個 root 的計數各自獨立。

練習 4：把練習 3 的 root 改成用「點擊」觸發，加上快照與批次更新。click(handler) 模擬使用者按下按鈕：

  • 把這次 render 的 state（快照）和 setState 傳給 handler。
  • handler 裡呼叫 setState 只是排進佇列，不能在 handler 還沒結束前呼叫元件。
  • handler 結束後一次處理整個佇列，規則跟練習 2 一樣（值直接取代、函式拿前一個結果算）。判斷是不是函式用 action instanceof Function，TypeScript 才能正確縮小型別。
  • 算出來的結果跟目前的 state 用 Object.is 比較：一樣就不 render；不一樣就存起來、呼叫元件一次、更新畫面。
  • 處理完的佇列不能留到下一次點擊。

範例寫 createRoot<number>(…)：不寫的話，TypeScript 會從初始值 0 把 state 的型別推成字面值型別 0，之後 setCups(cups + 1) 就會出現型別錯誤。

練習 5：cups 目前是 0。按鈕的 onClick 依序執行 setCups(cups + 1) 三次，再 console.log(cups)。console 印出什麼？畫面最後顯示幾杯？

✓ b。cups 是這次 render 的快照，在 handler 裡永遠是 0，三行都是 setCups(1)，console.log 也讀到 0；下一次 render 的 cups 是 1。a 是 Vue 的直覺（.value++ 之後馬上讀到新值）；c 要用 setCups(n => n + 1) 才會是 3 杯；d 錯在 set 不會改到這次 render 的變數。

練習 6：點餐頁 OrderPage 有一個 state note（備註），底下有一個完全沒用到 note 的子元件 <Menu products={products} />（products 沒變）。使用者輸入備註時，下面哪一個描述正確？

✓ c。React 預設遞迴 render 所有子元件，不看 props；commit 時發現菜單一樣，就不動 DOM。Vue 的子元件只在 props 有變時才更新。a、b 把 React 想成 Vue 的模型（要跳過得用 memo，第 19 課）；d 錯在 render 不等於重建 DOM。

練習 7：const [order, setOrder] = useState({ items: ['拿鐵'] })。按鈕執行 order.items.push('可頌'); setOrder(order)，畫面沒有出現可頌。原因與修正是？

✓ a。React 不追蹤物件內部的改動，只在 set 時用 Object.is 比較；同一個參考就當成沒變。b 錯在 state 可以放任何值；c 錯在這次根本沒有安排 render，之後別的 state 觸發 render 時可頌才「突然」出現；d 把 state 換成另一種形狀，而且 items 也是同一個參考。

常見錯誤

  • 在元件裡用 let 變數記住要跨 render 的值：每次 render 都重新宣告，改它也不會觸發 render。放進 useState。
  • set 完馬上讀 state，以為是新值：set 只影響下一次 render。需要新值就先存進區域變數。
  • 連續 setX(x + 1) 以為會加好幾次：每一行讀到的都是同一個快照。用 setX(n => n + 1)。
  • 直接改 state 裡的物件、陣列再 set 同一個參考：Object.is 判定沒變，畫面不更新。建立新的物件或陣列。
  • 以為 render 就是重建 DOM：commit 才改 DOM，而且只改有差異的地方。多 render 幾次先量測再決定要不要優化。
  • 在 render 裡改外部變數、發請求：元件必須是純函式。副作用放在事件處理函式或 effect。

小結

  • Vue 追蹤 render 時讀了什麼，寫入時通知；React 不追蹤，你呼叫 set 函式，它就重新呼叫元件函式。
  • 一次更新三步：trigger（初次 render 或 set state）→ render（呼叫元件）→ commit（只把差異套用到 DOM）。
  • 元件函式每次 render 都從頭執行：區域變數不會留下來，衍生值直接在函式裡算。
  • state 是快照：set 只影響下一次 render；一次事件裡的更新會批次處理，更新函式 n => n + 1 拿前一個結果算。
  • React 用 Object.is 比較新舊 state，一樣就跳過；改舊物件不會被發現，所以 state 要當成唯讀。
  • 父元件 render 時，子元件預設全部跟著 render；元件要是純函式，Strict Mode 在開發模式會呼叫兩次來檢查。
