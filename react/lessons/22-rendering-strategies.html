階段 5：效能與渲染 · 第 22 課

渲染策略：CSR、SSR、Server Components 與 Next.js

咖啡店的點餐網站一直是 Vite 做的單頁應用。行銷想讓菜單被 Google 搜到、貼到 LINE 有預覽圖；同事提議「整個搬到 Next.js，全部伺服器渲染」。測試版上線一週，回報了一串問題：門市橫幅的「營業中」閃一下變「休息中」、結帳頁點電話欄位的標籤不會聚焦、菜單在伺服器抓一次、瀏覽器又抓一次；另一位同事把「加入購物車」的 onClick 從頁面傳給按鈕，Next.js 直接報錯；店員的訂單後台也跟著改成伺服器渲染，伺服器帳單多了一筆，卻沒有人覺得後台變快。

問題出在沒有先回答：每一頁的 HTML 該在哪裡、什麼時候產生，代價由誰付。這課是選型與判斷，不是 Next.js 的教學；Next.js 的部分以 Next.js 16（文件版本 16.4.5）為準。

這課的路線：
  1. 先選渲染方式：每一頁的 HTML 該在哪裡產生，React 多了什麼選項。
  2. hydration：React 版的 renderToString 與 hydrateRoot，不一致時 React 19 怎麼處理、怎麼修。
  3. 伺服器的資料怎麼交給瀏覽器，不抓兩次、不被注入。
  4. Server Components 與 'use client' 邊界：誰在哪裡執行、什麼能跨過去；Server Functions。
  5. Next.js 16 的預設：哪些頁面預先產生、什麼會被快取，以及整理成一張選型表。
這課會用到：
  • Vue 課第 24 課的 CSR、SSR、SSG 與 hydration：三種產生 HTML 的時機、TTFB 與 SEO 的取捨，以及瀏覽器第一次渲染必須和伺服器的 HTML 一樣。這課不重講，只講 React 不同的地方。
  • 第 5 課的 effect：在 commit 之後執行，用來跟外部系統同步。
  • 第 9 課的 useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot)：訂閱 React 以外的資料，第三個參數當時先跳過。
  • 第 13 課的 Suspense 與 use：元件讀一個還沒完成的 Promise 時暫停，外層顯示 fallback。
練習不安裝 Next.js：用 react-dom 19.3.1 的 renderToString、hydrateRoot，在同一個 Vitest 程序裡模擬伺服器和瀏覽器。Server Components 需要框架的打包工具，這課只讀程式範例，不在本機執行。

先選渲染方式：誰需要這份 HTML

CSR、SSR、SSG 的定義和 TTFB、SEO 的取捨，Vue 課第 24 課的表格完全適用，框架換成 React 也不變。這裡直接用它來回答開場的問題，先看咖啡店的四種頁面：

頁面誰要看 HTML資料多常變選擇
門市介紹、關於我們搜尋引擎、LINE 預覽幾個月改一次SSG：建置時產生，CDN 直接回傳
商品頁 /menu/latte搜尋引擎、分享連結的人價格、售完狀態每天會變SSR，或預先產生再定時重新產生（ISR）
購物車、結帳只有登入的顧客每個人不同SSR 的外框加瀏覽器裡的互動，或 CSR
店員訂單後台只有店員一直在變CSR：維持 Vite 的單頁應用

表裡的 ISR（Incremental Static Regeneration，增量靜態重新產生）是 Next.js 文件的名詞：建置後再依設定重新產生某一頁的 HTML，介於 SSG 和 SSR 之間；Vue 課 Nuxt 的 swr 是同一類做法。開場「全部 SSR」的問題就在最後一列：後台不需要被搜尋，SSR 只多了一台要維運的伺服器、每個請求的 CPU，和這課後面那一整類 hydration 的 bug。

React 比 Vue 課多一個選項：Server Components（伺服器元件，下面第 4 節）。它跟 CSR、SSR、SSG 不在同一個維度上：

  • CSR／SSR／SSG 回答「HTML 什麼時候、在哪裡產生」。
  • Server Component／Client Component 回答「這個元件的程式碼要不要送到瀏覽器」。Server Component 只在伺服器（或建置時）執行，程式碼不進瀏覽器的 bundle；Client Component 在伺服器 render 出 HTML 之後，還會在瀏覽器執行一次（hydration）。

所以「用了 Server Components」不代表「這頁是 SSR」：Next.js 可以在建置時就執行 Server Component 產生靜態頁，也可以每個請求執行。最小的答案是：先依「誰要看 HTML、資料多常變」選產生 HTML 的時機；再依「這塊要不要互動」決定哪些元件送到瀏覽器。所以「要不要上 Next.js」也是先列頁面再決定：表裡全是後台與登入後的工具，Vite 的 CSR 就夠了；對外頁面多、首屏指標（LCP，見 Web 課第 20 課）要顧，才值得付 Node 伺服器、部署平台和團隊學習的成本。同一個產品也常拆成兩個專案：對外網站用 Next.js，後台維持 SPA。

hydration：renderToString 與 hydrateRoot

選了 SSR 或 SSG 之後，開場的前兩個 bug 都發生在同一個步驟：瀏覽器接手伺服器的 HTML。React 的寫法跟 Vue 的 createSSRApp 一樣分兩半。伺服器用 react-dom/server 把元件變成 HTML 字串：

// server.tsx（Node，每個請求執行一次；SSG 則在建置時執行）
import { renderToString } from 'react-dom/server'

const html = renderToString(<StoreBanner now={Date.now()} />)
// 放進頁面範本的 <div id="root">…</div>，再加上 <script src="/client.js">

瀏覽器用 react-dom/client 的 hydrateRoot，不是第 2 課的 createRoot：

// client.tsx（瀏覽器）
import { hydrateRoot } from 'react-dom/client'

hydrateRoot(document.getElementById('root')!, <StoreBanner now={…同一個值…} />)

createRoot 會清掉容器、自己建 DOM；hydrateRoot 照樣執行元件，但認領伺服器已經建好的 DOM 節點、掛上事件。react.dev 的 hydrateRoot 文件要求：傳給它的元件樹，第一次 render 要產生跟伺服器一樣的輸出。正式專案很少直接用 renderToString：它不支援串流，也不等 Suspense 裡的資料，Next.js 這類框架用的是串流版的 API。但 hydration 的規則一樣，這課的練習用它最直接。

不一樣的時候，React 19 怎麼處理

開場的門市橫幅就是不一樣的例子：營業狀態用 new Date().getHours() 算，伺服器在 UTC、渲染時間也跟瀏覽器不同；寬度用 typeof window 判斷，伺服器沒有、瀏覽器有。在練習環境（react-dom 19.3.1，開發版本）實測兩種不一致，結果不同：

不一致的地方React 怎麼回報畫面
文字或節點（「營業中」對「休息中」、多一個 <p>）丟出錯誤交給 hydrateRoot 的 onRecoverableError：「Hydration failed because the server rendered text didn't match the client. As a result this tree will be regenerated on the client.」丟掉伺服器的 DOM，在瀏覽器重新 render：畫面會閃，首屏的好處沒了
屬性（className、id、title）只在 console 印出「A tree hydrated but some attributes of the server rendered HTML didn't match the client properties. This won't be patched up.」不修正：DOM 留著伺服器的值，React 卻以為是自己算的值

兩則訊息後面都附上常見原因的清單，跟 react.dev 列的一樣：

  • render 裡用 typeof window !== 'undefined' 分支。
  • render 裡用 window.matchMedia 這類瀏覽器才有的 API。
  • Date.now()、Math.random() 這種每次呼叫都不同的值，以及依使用者地區格式化日期。
  • 伺服器和瀏覽器拿到不同的資料；根節點裡伺服器 HTML 前後多了空白、換行。

文件的態度很明確：React 能從某些不一致恢復，但要當 bug 修；最好的情況是變慢，最壞的情況是事件掛到錯的元素上。正式版本的訊息會被壓成錯誤代碼（hydration 是 418），要貼到 react.dev 的錯誤解碼頁才看得到全文，所以要在 onRecoverableError 把錯誤送進監控（第 24 課）。

修法：第一次 render 用同一份輸入

三種情況，三個修法：

  1. 時間、亂數：由參數傳入同一個值。營業狀態用伺服器決定的 now，隨 HTML 帶到瀏覽器（下一節）；算小時要指定時區，不用執行環境的。這跟第 20 課「render 裡不讀時鐘」是同一條規則。
  2. id：用 useId()。它依元件在樹裡的位置產生 id，react.dev 的前提是伺服器和瀏覽器 render 同一棵樹。練習環境實測，同一頁兩個欄位得到 _R_1_、_R_2_，hydration 後完全相同。模組層級的計數器不行：伺服器程序處理過別的請求，計數器早就不是從 1 開始。
  3. 只有瀏覽器知道的值：hydration 之後才讀。React 文件叫它兩階段渲染（two-pass rendering）：第一次 render 用跟伺服器一樣的值，effect 裡再改。

第 3 種有兩個寫法。用 effect（第 5 課：effect 只在瀏覽器、commit 之後執行，伺服器上不執行）：

const [width, setWidth] = useState<number | null>(null)   // 伺服器和 hydration 都是 null
useEffect(() => {
  setWidth(window.innerWidth)                          // hydration 之後才執行
}, [])
return width === null ? null : <p>螢幕寬度：{width}px</p>

或用第 9 課的 useSyncExternalStore，這次用上第三個參數。文件說 getServerSnapshot 只在兩個時候執行：伺服器產生 HTML 時，和瀏覽器 hydration 時；之後 React 改用 getSnapshot 的值重新 render，而且之後視窗縮放也會更新：

const width = useSyncExternalStore(
  subscribe,                    // 監聽 resize
  () => window.innerWidth,      // 瀏覽器：hydration 之後
  () => null,                   // 伺服器與 hydration：兩邊一樣
)

兩種寫法都有同一個代價：使用者先看到沒有寬度的畫面，下一刻才出現。只有瀏覽器知道的東西，伺服器的 HTML 裡就不會有。常見的半套修法：

  • useState(() => typeof window === 'undefined' ? 0 : window.innerWidth) 再加 effect：初始值在兩邊還是不同，effect 救不了第一次 render。初始值一律用兩邊相同的值。
  • render 裡直接讀 window：Node 沒有 window，伺服器上直接丟 ReferenceError，整頁 500。
  • suppressHydrationWarning：只讓單一元素（往下一層）的文字或屬性不一致不再報錯，文件寫明 React 不會修正那段文字。實測寬度那一行停在伺服器的空字串。只用在真的無法避免、也無所謂的地方，例如顯示使用者當地格式的時間戳。它對應 Vue 的 data-allow-mismatch。
💡 實務上：hydration 錯誤要從使用者的環境開始查
客服收到的會是「時間閃一下就變了」「只有國外的客人看到怪怪的」「按鈕第一下沒反應」。查法：先用正式建置在本機重現，看 console 或監控裡的 418；再對照四個來源：時間與時區（伺服器多半在 UTC）、亂數與 id、瀏覽器 API、伺服器和瀏覽器的資料不同。瀏覽器的翻譯、廣告阻擋擴充功能也會在 hydration 前改 DOM，先用無痕視窗排除。修好之後在 CI 加一個像練習這樣的測試：伺服器 render、hydrate、斷言沒有任何 recoverable error。

伺服器的資料怎麼交給瀏覽器

上一節的修法 1 說「隨 HTML 帶到瀏覽器」，這正是開場「菜單抓兩次」的原因。伺服器 render 菜單時手上有商品資料，HTML 裡有完整的清單；但瀏覽器 hydrate 時，元件寫的是 useState([]) 加 effect 抓資料：

function ClientMenu() {
  const [products, setProducts] = useState<Product[]>([])   // 第一次 render 是空的
  useEffect(() => { fetchMenu().then(setProducts) }, [])
  return <MenuPage products={products} />
}

第一次 render 是空清單，伺服器的 HTML 有六個商品：節點不一致，React 丟掉伺服器的 DOM，畫面閃成空的，再等一次 API。修法是把伺服器用的那份資料序列化進頁面，瀏覽器先讀它、用同一份資料 hydrate，不再抓：

// 伺服器
const json = JSON.stringify(products).replace(/</g, '\\u003c')
return `<div id="root">${renderToString(<MenuPage products={products} />)}</div>
<script type="application/json" id="menu-data">${json}</script>`

// 瀏覽器
const products = JSON.parse(document.getElementById('menu-data')!.textContent!)
hydrateRoot(container, <MenuPage products={products} />)

type="application/json" 的 <script> 不會被執行，只是一塊資料。那行 replace 是資安：商品名稱、顧客備註都是別人輸入的，HTML 解析器在 script 裡看到 </script> 就結束這個標籤，後面的字變成新的、會執行的程式。執行後看兩行輸出的差別：

沒跳脫的那行裡有完整的 </script>；跳脫後 < 變成 JSON 的 <，HTML 解析器看不到標籤，JSON.parse 讀回來又是原本的字。換成 HTML 實體 &lt; 是錯的：script 裡的內容不會解碼實體，讀回來的名稱就變了，hydration 照樣不一致。

這段「抓資料、序列化、跳脫、還原」是自己做 SSR 最麻煩的部分之一，框架會代勞：Next.js 把 Server Component 的結果和傳給 Client Component 的 props 放進 RSC Payload（下一節），隨 HTML 一起送出；TanStack Query（第 15 課）也有把伺服器的快取交給瀏覽器的機制。另一個 SSR 的老問題也在伺服器這一側：伺服器的模組只載入一次、同時服務所有顧客，模組層級的 store 會讓 A 的購物車出現在 B 的頁面，做法是每個請求建立一份（第 14 課的 Zustand、Vue 課第 24 課的跨請求狀態污染）。

Server Components：只在伺服器執行的元件

上一節的 SSR 有個代價沒消失：菜單頁的每個元件，伺服器執行一次產生 HTML，瀏覽器還要下載同一份程式碼再執行一次。可是 MenuPage 裡只有「加入」按鈕需要互動，商品清單、分類標題、把 Markdown 介紹轉成 HTML 的套件，在瀏覽器再跑一次只是浪費。Server Components 就是讓這些元件只在伺服器執行，瀏覽器只收到結果。依 react.dev：

  • Server Component 可以是 async 函式，直接 await 資料庫或檔案；Client Component 不行，要用 use 讀 Promise（第 13 課）。
  • 它不會送到瀏覽器，所以不能用 useState 這類互動的 API；要互動，就組合一個 Client Component 進來。
  • 它可以在建置時執行（讀檔案、讀 CMS），不一定需要一台伺服器一直開著。
  • Server Components 在 React 19 是穩定的；但框架、打包工具用來實作它的底層 API 不遵守 semver，所以要靠 Next.js 這類框架用，不要自己接。

在 Next.js 16 的 App Router，app/ 底下的 layout 和 page 預設就是 Server Component。菜單頁會長這樣：

// app/menu/page.tsx：Server Component（沒有任何標記）
import { db } from '@/lib/db'
import { AddToCartButton } from './add-to-cart-button'

export default async function MenuPage() {
  const products = await db.product.findMany()        // 直接查資料庫，帳號密碼不會到瀏覽器
  return (
    <ul>
      {products.map(p => (
        <li key={p.id}>
          {p.name} ${p.price}
          <AddToCartButton productId={p.id} name={p.name} />
        </li>
      ))}
    </ul>
  )
}

// app/menu/add-to-cart-button.tsx：Client Component
'use client'
import { useState } from 'react'

export function AddToCartButton({ productId, name }: { productId: number; name: string }) {
  const [added, setAdded] = useState(false)
  return <button onClick={() => { addToCart(productId); setAdded(true) }}>{added ? '已加入' : `加入${name}`}</button>
}

「Client Component」這個名字容易誤會，Next.js 的文件用一張表說明在哪裡執行：

在伺服器在瀏覽器
Server Component是（產生 RSC Payload）否：程式碼不送到瀏覽器
Client Component是（第一次載入時 render 成 HTML）是（hydration 與之後的互動）

第一次打開頁面時的流程（Next.js 16 文件）：

  1. 伺服器把 Server Components render 成 RSC Payload：一種序列化的元件樹，內容是 Server Component 的結果、Client Component 的位置與 JavaScript 檔的參照，以及傳給 Client Component 的 props。
  2. 伺服器用 RSC Payload 加上 Client Components 產生 HTML；瀏覽器先顯示這份 HTML（還不能互動）。
  3. 瀏覽器用 RSC Payload 對齊元件樹，再用 JavaScript hydrate Client Components。之後在站內換頁，只抓新頁的 RSC Payload，Client Components 直接在瀏覽器 render。

所以 Client Component 在第一次載入時仍然會在伺服器執行一次，上一節的 hydration 規則對它完全適用：AddToCartButton 的 render 裡讀 window，一樣會讓伺服器丟錯。

💡 實務上：Server Component 的好處是「少送 JavaScript」，不是「比較快」
Next.js 文件列的理由是：在離資料近的地方抓資料、密鑰不外流、減少送到瀏覽器的 JavaScript、改善首次內容繪製（FCP）。所以它最有價值的是內容多、互動少的頁面（菜單、文章、商品頁），以及用了大型套件（Markdown、語法高亮、日期處理）只為了產生畫面的元件。互動密集的頁面（拖拉排班表、即時訂單看板）大部分都得是 Client Component，好處就小。評估時看 bundle 大小和 LCP 的實際數字，不要假設「伺服器的一定快」。

'use client' 邊界：什麼能跨過去

上一節的例子只在一個檔案開頭寫了 'use client'。它標記的不是「這個元件」，而是一條邊界。依 react.dev 的 'use client' 文件：

  • 寫在檔案最上面（import 之前），把這個模組和它 import 的所有模組都標成客戶端程式碼。add-to-cart-button.tsx import 的 formatPrice，就算自己沒寫 'use client'，也會送到瀏覽器。
  • 邊界畫在模組的 import 關係上，不是畫面的父子關係。Server Component 可以當 children 傳給 Client Component，它仍然在伺服器執行，Client Component 只收到它 render 好的結果。
  • 不是每個檔案都要寫：從 Client Component 裡 import 的模組自動在客戶端，再寫一次沒有作用。

所以 'use client' 要放在「真的需要互動的葉子」，不要放在 layout：

// ✗ app/layout.tsx 寫 'use client'：整個網站的元件都變成客戶端程式碼，Server Components 的好處全沒了
// ✓ 只有 Header 裡的搜尋框、購物車按鈕是 Client Component

// 需要開關狀態的對話框是 Client Component，裡面的購物車明細仍是 Server Component
export default function Page() {
  return (
    <Modal>              {/* 'use client'：收 children */}
      <CartSummary />    {/* Server Component：在伺服器查購物車，結果當 children 傳進去 */}
    </Modal>
  )
}

這跟第 19 課「慢的內容用 children 從上面傳進去」是同一個技巧：有 state 的外框收 children，children 由外面決定。

props 要能序列化

Server Component 傳給 Client Component 的 props，要寫進 RSC Payload 送過網路，所以必須能序列化。react.dev 列出可以傳的：

可以不可以
string、number、bigint、boolean、undefined、null；用 Symbol.for 註冊的 symbol沒註冊的 symbol（Symbol('x')）
內容可序列化的 Array、Map、Set、TypedArray、ArrayBuffer；Date一般函式（包括 onClick 的箭頭函式）
用物件字面值建立的一般物件class 的實例（內建的以外）、null prototype 的物件
Server Functions、JSX 元素、Promiseclass 本身

開場「傳 onClick 就報錯」就在右欄：函式是程式碼，不是資料，沒辦法從伺服器送到瀏覽器。修法是讓事件處理函式留在 Client Component 裡（像上面的 AddToCartButton 自己寫 onClick），Server Component 只傳 productId 這種資料；真的要讓瀏覽器呼叫伺服器的程式，用下面的 Server Function。常見的另一個坑是 ORM 回傳的物件或 new Money(110) 這類 class 實例，傳之前轉成一般物件，只挑 Client Component 需要的欄位。

表裡的 Promise 對應第 13 課的 use：Server Component 開始查詢但不 await，把 Promise 當 prop 傳下去，Client Component 用 use 讀，外面包 Suspense。react.dev 的例子是文章內容先 await，留言用 Promise 傳下去：重要的先出現，次要的串流進來。這也是第 13 課說「Promise 不能在 render 裡建立」在 Next.js 裡的解法：由 Server Component 建立。

反方向也要防：只該在伺服器的模組（查資料庫、讀密鑰）被 Client Component import，就會被打包送到瀏覽器。Next.js 文件建議在這種檔案開頭 import 'server-only'，被客戶端 import 時建置直接失敗。Server Component 也不能用 useState、useEffect，讀 context 也不行（第 11 課提過 use 在 Server Components 不支援讀 context），Provider 要放在 Client Component 裡。

Server Functions：'use server'

資料的另一個方向是瀏覽器要叫伺服器做事（加入購物車、送出訂單）。在 async 函式開頭或檔案開頭寫 'use server'，它就成為 Server Function：瀏覽器呼叫它時，React 把參數序列化、發一個網路請求到伺服器執行，再把回傳值送回來（react.dev 的 'use server' 文件）。第 17 課的 Action 可以直接換成它：

// app/menu/actions.ts
'use server'

export async function addToCart(prev: CartState, formData: FormData): Promise<CartState> {
  const user = await currentUser()                         // 先確認是誰
  if (!user) return { error: '請先登入' }
  const parsed = cartSchema.safeParse(Object.fromEntries(formData))   // 再驗證參數
  if (!parsed.success) return { error: '資料不正確' }
  await db.cart.add(user.id, parsed.data)
  return { error: null }
}

// Client Component 裡：const [state, formAction] = useActionState(addToCart, { error: null })

文件對 Server Function 有三點要求，都跟「它其實是一支 API」有關：

  • 參數完全由客戶端控制：一律當成不可信的輸入，驗證、跳脫；每個 Server Function 都要檢查登入的使用者有沒有權限做這件事。它跟你寫的 REST API 一樣會被直接呼叫，不會因為「頁面上沒有那顆按鈕」就安全。
  • 用來改資料，不用來抓資料：框架通常一次只處理一個，回傳值也不快取。讀資料在 Server Component 裡做。
  • 要在 Transition 裡呼叫：交給 <form action> 或 formAction 時自動如此，這正是第 17 課的寫法。
💡 實務上：review 時沿著邊界看三件事
Server／Client 混寫的專案，code review 最常抓到的問題都在邊界上。往下看：Client Component 收到的 props 是不是只有它需要的欄位（整個 user 物件傳下去，email、權限、內部 id 都進了 RSC Payload，打開開發者工具就看得到）。往上看：每個 'use server' 函式開頭有沒有驗證身分與參數，資安會把它們當成 API 清單來審。看邊界本身：'use client' 是不是越放越高，bundle 是不是越來越大。
💡 實務上：Next.js 一手包前後端，還是前端＋獨立的 NestJS API
Next.js 16.4 除了 Server Function，還有 Route Handler：在 app/api/orders/route.ts 匯出 export async function GET(request: Request)、POST 等函式，回傳 Web 標準的 Response，就是一支一般的 HTTP API。只有一個網站、團隊就是同一批人時，Server Function 處理表單、Route Handler 接 webhook，一個專案、一次部署，最省事。下面幾種情況就該拆出獨立的 API（例如 NestJS 課）：手機 App、POS、外部合作夥伴也要用同一套 API（Server Function 的網址與格式是框架內部的，不是給別人呼叫的契約）；前後端是不同團隊、要各自發版；有排程、重試、長時間的工作（Next.js 的 after() 只是在回應送出後再跑一段程式，不是佇列，背景工作要交給 NestJS 課第 20 課這種 worker）；API 要獨立擴充或部署在不同地方。面試被問到時，從「誰會呼叫這支 API、誰維護、有沒有背景工作」三點回答。

Next.js 16 的預設：預先產生與快取

邊界畫好之後，剩下開場的最後一個問題：這一頁到底是建置時產生、每次請求產生，資料會不會被快取。這是 Next.js 改最多次的地方，網路上的文章常常是舊版的行為，一律以你專案的版本對照官方文件。以下是 Next.js 16.4.5 的文件：

  • 15 版起，fetch 預設不快取（升級到 15 的指南）。在 Server Component 裡 await fetch(...)，每次都會真的發請求；要快取就明寫 fetch(url, { cache: 'force-cache' })。GET 的 Route Handler 也從 15 版起預設不快取。
  • 不開 Cache Components 時（文件稱為舊模型）：路由預設盡量預先產生；用到 cookies()、headers() 這類請求時才有的 API，那個路由就改成每次請求 render。export const dynamic = 'force-dynamic' 之類的路由設定可以強制指定。
  • 開了 Cache Components（next.config.ts 設 cacheComponents: true）：資料抓取預設是動態的，要快取的頁面、元件或函式自己標 'use cache'。建置時產生一份靜態外殼，沒快取的部分包在 <Suspense> 裡，請求時再串流進來，文件稱為 Partial Prerendering（部分預先產生）。

用咖啡店的菜單頁看開了 Cache Components 的寫法：

export default function Page() {
  return (
    <main>
      <Menu />                                     {/* 'use cache'：進靜態外殼，CDN 直接回傳 */}
      <Suspense fallback={<p>載入你的購物車…</p>}>
        <MyCart />                                 {/* 讀 cookie 才知道是誰：請求時串流 */}
      </Suspense>
    </main>
  )
}

async function Menu() {
  'use cache'
  const products = await db.product.findMany()
  return <MenuList products={products} />
}

這段把第 1 節的選型表搬進同一頁：菜單像 SSG，購物車像 SSR，邊界由 Suspense 畫出來。Vue 課 Nuxt 的 routeRules 是逐條路由選；Next.js 開了 Cache Components 之後是逐個元件選。

回到第 1 節，加上這課後面的判斷，整張選型表（查表用，不用背）：

需求選擇代價

對外、內容少變SSG（或快取進靜態外殼）資料只到上次產生；要有重新產生的機制

💡 實務上：快取設定寫進 PR 描述，而且要能說出「多久會看到新資料」
「改了價格，網站還是舊的」和「每個請求都打資料庫，帳單爆了」是同一個設定的兩面。新增或修改頁面時，PR 描述寫清楚：這頁是預先產生還是每次請求、資料快取多久、改了資料之後怎麼更新（重新產生、清快取）。升級 Next.js 大版本時，先讀官方的升級指南裡快取的段落，14 到 15、15 到 16 的預設都改過，照舊文章寫的設定可能剛好反過來。

練習

在 learn/ 執行 node check.mjs react 22，檔案在 react/practice/work/22/。測試用 ssr-utils.tsx 模擬兩端：伺服器 render 時把 window、document 拿掉再呼叫 renderToString；瀏覽器端把 HTML 放進容器、呼叫 hydrateRoot，收集 onRecoverableError 和 console.error，任何一則都算失敗。三題互不相依，標了「不用改」的檔案不要改。練習 4 在瀏覽器裡做。

練習 1：StoreBanner 用 new Date().getHours() 判斷營業中、用 typeof window 決定要不要顯示寬度，hydration 時不一致。改成：伺服器上沒有 window 也能 render；營業狀態只由 props.now 決定，營業時間是台北時間 07:00（含）到 19:00（不含），不能依賴執行環境的時區；伺服器的 HTML 和 hydration 時都不顯示寬度，hydration 之後才顯示「螢幕寬度：1024px」（useEffect 或 useSyncExternalStore 都可以）。測試讓伺服器在 UTC、瀏覽器在紐約，兩邊的系統時間也不同；hydration 不能有任何錯誤，不能用 suppressHydrationWarning。

練習 2：PhoneField 用 Math.random() 產生 id，伺服器和瀏覽器各算一次。改成兩邊一致的 id：<label htmlFor> 連到 <input type="tel">，input 的 aria-describedby 連到說明文字「格式：0912-345-678」。測試在同一頁放三個 PhoneField（其中兩個 label 一樣），id 不能重複；也會先讓伺服器渲染別的頁面再渲染這一頁，hydration 後的 id 要和伺服器 HTML 裡的一樣、沒有錯誤。props 維持只有 label，不能用亂數。

練習 3：page.tsx 的瀏覽器端先用空陣列 hydrate 再呼叫 fetchMenu()，造成 hydration 錯誤、菜單抓兩次。改成：renderPage(products) 回傳 <div id="root">（MenuPage 的 HTML）接著 <script type="application/json" id="menu-data">（同一份 products 的 JSON，把 < 換成 <，商品名稱裡有 </script> 也不能多出標籤）；hydratePage(container, options) 從 #menu-data 讀出資料，用同一份資料 hydrateRoot，options 原樣交給它。完成時 hydration 沒有錯誤、不呼叫 fetchMenu、伺服器的 <li> 節點被沿用（不能用 createRoot 重建），之後按「加入X」能累計件數；換一份菜單也要照樣交接。

練習 4：Server Component 要把 props 傳給 Client Component 之前，先用 findUnserializable(value, path) 檢查。依這課「props 要能序列化」那張表，回傳第一個不能傳的值的路徑，全部可以傳就回傳 null：

  • 路徑從 'props' 開始，物件的屬性接 .名稱，陣列的元素接 [索引]，例如 'props.cart.lines[1].format'；依屬性與元素的順序，回傳第一個。
  • Map、Set 裡面有不能傳的鍵或值時，回傳 Map／Set 自己的路徑。
  • 可以傳：string、number、bigint、boolean、undefined、null、Symbol.for 註冊的 symbol（Symbol.keyFor 拿得到名字）、Date、Promise、ArrayBuffer 與 TypedArray、內容都可以傳的陣列、Map、Set 與一般物件（prototype 是 Object.prototype）。
  • 不能傳：函式、沒註冊的 symbol、其他 class 的實例、null prototype 的物件。

練習 5：咖啡店有四種頁面：門市介紹（幾個月改一次）、商品頁（要被搜尋，價格每天會改）、顧客的購物車、店員的訂單後台（要登入，不需要被搜尋）。哪一組選擇最合理？

✓ 選擇依「誰要看 HTML、資料多常變」決定。a 讓不需要搜尋的後台也付伺服器成本與 hydration 的 bug，SSR 的 TTFB 也比較晚，不是一定快；c 產生不出每個人不同的購物車，價格每天改也不能每天重新部署整站；d 搞錯了 Server Components 的角色，它決定元件的程式碼要不要送到瀏覽器，要有 HTML 還是得在伺服器或建置時產生。

練習 6：Next.js 的 app/menu/page.tsx（Server Component）寫 <AddToCartButton product={p} onAdded={() => console.log('加入', p.id)} />，AddToCartButton 的檔案開頭有 'use client'。會發生什麼事，該怎麼改？

✓ 傳給 Client Component 的 props 要能序列化，函式是程式碼，只有 Server Function 例外。b 能讓錯誤消失，但整個頁面和它 import 的東西都變成客戶端程式碼，失去 Server Component 的好處，也不能再直接查資料庫；d 錯在可以傳 props，只要能序列化。

練習 7：專案用 Next.js 16，沒有開 cacheComponents。同事照一篇舊文章說「Server Component 裡的 fetch 預設會快取，所以菜單 API 不會被一直打」。實際上呢？

✓ 依 Next.js 的升級指南，fetch 從 15 版起不再預設快取。開了 Cache Components 之後，資料抓取預設是動態的，要快取的地方標 'use cache'。這是常見的「照舊文章寫，行為剛好相反」：以專案的版本查官方文件。

練習 8：actions.ts 開頭寫 'use server'，裡面 export async function cancelOrder(orderId: number) { await db.order.cancel(orderId) }。後台頁只有店長看得到「取消訂單」按鈕。這段程式有什麼問題？

✓ react.dev 寫明 Server Function 的參數完全由客戶端控制，要當成不可信的輸入，每個 Server Function 都要檢查登入的使用者有沒有權限。a 把畫面上的按鈕當成權限控管；b 錯在 number 可以序列化；c 錯在 Server Function 就是讓客戶端呼叫的，問題不在誰呼叫，在沒有檢查。

常見錯誤

  • 每一頁都上 SSR：後台、登入後的工具不需要被搜尋，只多了伺服器成本和 hydration 的 bug。先依「誰要看 HTML、資料多常變」逐頁選。
  • 把 Server Components 當成 SSR 的同義詞：它決定元件的程式碼要不要送到瀏覽器；HTML 什麼時候產生是另一個決定。
  • render 裡讀 window、localStorage：伺服器上丟錯，整頁失敗。只有瀏覽器知道的值，hydration 之後才讀。
  • render 裡用 typeof window 分支：伺服器不丟錯了，但兩邊第一次 render 不同。第一次 render 用相同的值，用 effect 或 useSyncExternalStore 的 getServerSnapshot。
  • 初始值在兩邊不同，再用 effect 更新：effect 在 hydration 之後才跑，救不了第一次 render。初始值用兩邊相同的值（例如 null）。
  • render 裡用 Date.now()、new Date()、getHours()：伺服器和瀏覽器的時間、時區不同。時間由參數傳入同一個值，計算時指定時區。
  • id 用 Math.random()、crypto.randomUUID()，或放進 useState 的初始值：兩邊各算一次，一定不同；屬性不一致 React 只警告、不修正，label 就連不到 input。用 useId()。
  • id 用模組層級的計數器：伺服器上所有請求共用，瀏覽器從頭數。用 useId()。
  • id 寫死或用 label 組出來：兩邊一致了，但同一頁兩個欄位會重複。
  • 用 suppressHydrationWarning 蓋掉不一致：只讓警告閉嘴，React 不修正文字，畫面停在伺服器的值。只用在確定無法避免、也無所謂的單一元素。
  • 瀏覽器先用空資料 hydrate 再抓：節點不一致、畫面閃、同一份資料抓兩次。把伺服器的資料序列化進頁面，用同一份 hydrate。
  • JSON 放進 <script> 沒跳脫：資料裡的 </script> 提早結束標籤，造成 XSS。把 < 換成 <；換成 &lt; 會讓讀回來的資料變了。
  • 瀏覽器用 createRoot 接伺服器的 HTML：整段 DOM 丟掉重建，首屏的好處沒了。用 hydrateRoot。
  • 瀏覽器用自己 import 的資料 hydrate：跟伺服器這次 render 的資料不一定一樣。從頁面裡讀伺服器送來的那份。
  • 'use client' 寫在 layout 或頁面最上層：它標記的是整棵 import 樹，全部變成客戶端程式碼。放在需要互動的葉子，Server Component 用 children 傳進去。
  • 把函式、class 實例傳給 Client Component：不能序列化。事件處理留在 Client Component；資料轉成一般物件、只挑需要的欄位。
  • 整個 user、訂單物件傳給 Client Component：所有欄位都進了 RSC Payload，瀏覽器看得到。只傳需要的。
  • Server Function 沒有驗證身分與參數：它是任何人都能直接呼叫的 API。每個都檢查登入的人有沒有權限，參數當成不可信的輸入。
  • 用 Server Function 抓資料：它是為了改資料設計的，回傳值不快取。讀資料在 Server Component 裡做。
  • 照舊文章設定 Next.js 的快取：fetch 從 15 版起預設不快取，16 版的 Cache Components 又是另一套。以專案的版本讀官方文件。

小結

  • 先依「誰要看 HTML、資料多常變」逐頁選：後台 CSR、少變的對外頁 SSG、常變或因人而異的 SSR（或 ISR）。Server Components 是另一個維度：元件的程式碼要不要送到瀏覽器。
  • React 的 SSR：伺服器 renderToString（框架用串流版），瀏覽器 hydrateRoot 認領 DOM。第一次 render 必須和伺服器一樣；react-dom 19.3.1 實測文字、節點不一致會交給 onRecoverableError 並在瀏覽器重新 render，屬性不一致只在 console 警告、不修正。
  • 修法：時間由參數傳入並指定時區；id 用 useId()；只有瀏覽器知道的值用 effect 或 useSyncExternalStore 的 getServerSnapshot 兩階段渲染；suppressHydrationWarning 只用在無法避免的單一元素。
  • 伺服器的資料序列化進頁面（< 換成 <），瀏覽器用同一份 hydrate、不再抓；框架用 RSC Payload 代勞。伺服器上不要有模組層級的使用者狀態。
  • Server Component 可以 async、直接查資料、不送程式碼到瀏覽器，不能用 state、effect、context；Next.js 16 的 App Router 預設就是它。Client Component 第一次載入也在伺服器 render。
  • 'use client' 標記整棵 import 樹，放在互動的葉子；props 要能序列化（函式、class 實例不行，Promise、Date、Map 可以）；Server Component 可以當 children 傳進 Client Component。
  • 'use server' 的 Server Function 是任何人都能呼叫的 API：驗證身分與參數，用來改資料、不用來抓資料。
  • Next.js：15 版起 fetch 預設不快取；16 版開 cacheComponents 後資料預設動態，用 'use cache' 選擇快取，沒快取的部分用 Suspense 串流。以專案的版本查官方文件。

練習 9：點餐機的深色模式 state 搬進收 children 的 ThemePanel，<SlowMenu products={products} /> 寫在沒有 state 的 KioskPage、當 children 傳進去。SlowMenu 沒有包 memo，切換深色模式時卻不再 render，為什麼？

✓ 重新 render 從 state 變了的元件開始；ThemePanel render 時，children 還是上一次那個 element 物件，React 就跳過它。這是不用 memo 的修法：state 往下放、慢的內容由沒有那個 state 的元件建立。b 錯在要看 element 是誰建立的：ThemePanel 自己寫 <SlowMenu />，或 KioskPage 還留著每秒更新的時鐘，SlowMenu 照樣跟著 render。（第 19 課）

練習 10：ProductRow 已經在模組層級用 memo 包好，MenuBoard 這樣傳 onAdd。哪裡會出事？

const [cart, setCart] = useState<Line[]>([])
const onAdd = useCallback((p: Product) => {
  setCart([...cart, { id: p.id, qty: 1 }])
}, []) // eslint-disable-line react-hooks/exhaustive-deps

return products.map(p => <ProductRow key={p.id} product={p} onAdd={onAdd} />)

✓ 依賴寫 []，函式就停在第一次 render，裡面的 cart 一直是空陣列。改成 updater function setCart(prev => [...prev, …])，函式不讀 cart，依賴是 [] 也正確；不要用 eslint-disable 壓掉 exhaustive-deps。b 剛好相反：空依賴讓函式永遠是同一個，memo 擋得住，問題是畫面停在舊資料，比慢更糟。（第 19 課）

練習 11：打開 React Compiler 之後，購物車第二次加拿鐵還是顯示「拿鐵 × 1」。CartLine 被記憶化，加入的程式是這樣，為什麼不更新？

const next = [...lines]
const hit = next.find(l => l.name === name)
if (hit) hit.qty += 1
else next.push({ name, qty: 1 })
setLines(next)

✓ 記憶化判斷「沒變」用參考比較，所以 props、state 必須不可變：變了的那一列換新 { ...l, qty: l.qty + 1 }，其餘沿用原本的物件。這段程式本來就違反規則，記憶化只是讓它現形。a 錯在 [...lines] 是新陣列，CartPanel 有 render，是被記憶化的那一列跳過了。Vue 的 Proxy 追蹤屬性，直接改 qty 是它期待的寫法，React 不是。（第 20 課）

練習 12：商品頁用 SSR，StoreBanner 在 render 裡用 new Date().getHours() 判斷「營業中／休息中」。國外的客人回報文字閃一下就變了，原因和修法是？

✓ hydration 時瀏覽器的第一次 render 必須和伺服器一樣，文字不一致時 React 19 會在瀏覽器重新 render，畫面就閃了。時間由參數傳入同一個值，跟第 20 課「render 裡不讀時鐘」是同一條規則。c 錯在 suppressHydrationWarning 只讓警告閉嘴，React 不修正文字，畫面停在伺服器的值；d 的 effect 在 hydration 之後才跑，救不了第一次 render。（第 22 課）

練習 13：MenuFilter 裡的 keyword state 同時給輸入框和很慢的 ProductGrid，舊平板上每打一個字都卡。怎麼改，輸入框才會立刻顯示新字？

✓ 輸入框的 state 必須立刻更新，所以延後的是交給慢元件的值：急的那次 render 傳給 ProductGrid 的值沒變，memo 讓它跳過；背景再用新值 render，可以被下一個字打斷。a 是文件列出的錯誤寫法：輸入框不能由 Transition 控制。b、d 都擋不住：keyword 每個字都變，篩選照樣重算，ProductGrid 的 props 也每次都不同。（第 21 課）

練習 14：報表頁每次切分頁，Profiler 都量到 SlowReport render 300ms。同事把切換的 setState 包進 startTransition，跟 PM 說「報表變快了」。哪個說法正確？

✓ 並行功能只調整先後：急的先 commit，不急的在背景 render、可以被打斷，CPU 的總工作量沒變，被打斷重來還會更多。所以它放在量測之後，用在本來就該花時間的部分。b 錯在沒有另一個執行緒，背景 render 一樣在主執行緒，只是可以被新的輸入打斷。（第 21 課）

練習 15：Next.js 專案的 app/layout.tsx import 了 Header、Footer，Header 裡有一個需要 state 的搜尋框。同事為了讓它能用 useState，在 layout.tsx 最上面加了 'use client'。會怎樣？

✓ 'use client' 標記的是一條模組 import 的邊界，不是單一元件：寫在 layout，整棵 import 樹都送到瀏覽器，Server Components 的好處就沒了。所以放在需要互動的葉子。b 錯在被 Client Component import 的模組自動是客戶端程式碼，不用自己寫，也擋不住。（第 22 課）

練習 16：app/account/page.tsx（Server Component）從資料庫查出 user（name、email、phone、role、內部備註，都是一般物件），交給 'use client' 的 <Greeting user={user} />，Greeting 只顯示 user.name。有什麼問題？

✓ 傳給 Client Component 的 props 要送過網路，Client Component 也會在瀏覽器再執行一次，所以每個欄位都在頁面裡。邊界上只傳它需要的欄位。a 把「在伺服器 render」當成「資料留在伺服器」：Client Component 要 hydration，props 一定跟著送過去。（第 22 課）
