階段 4：資料與機密 · 第 9 課

機密與加密：KMS、envelope encryption、Secrets Manager 與 Parameter Store

咖啡店的 cafe-api 上了 ECS 之後，資安顧問做了一次檢查，抓到兩件事。第一件：資料庫密碼直接寫在 task definition 的 environment 裡，任何有權限看 task definition 的人（包括只負責看 log 的外包）都能在主控台讀到它，而且 task definition 的每一個舊版本都留著同一個密碼。第二件：上個月離職的工程師筆電裡有一份 .env，裡面是正式環境的資料庫密碼和外送平台的 API token；那個密碼兩年沒換過，換的話要重新部署所有服務，所以沒人敢動。

這一課處理「機密放哪裡、怎麼用、怎麼換」。學完你能：用 KMS 的資料金鑰在程式裡加密資料（信封加密）並用 encryption context 綁定租戶；把密碼放進 Secrets Manager，讓程式帶快取地讀取、在密碼輪替時自動換用新的；分辨 Secrets Manager 與 Parameter Store；知道 ECS 與 Lambda 各自怎麼拿到機密。

這課的路線：

  • 最小解法：機密離開程式碼與 task definition，放進 Secrets Manager；加密用的金鑰放進 KMS。
  • KMS 金鑰：誰能用它由 key policy 決定；金鑰怎麼刪、為什麼刪不得。
  • 用 KMS 做信封加密：GenerateDataKey、Decrypt 與 encryption context（練習 1）。
  • Secrets Manager：版本與 staging label、程式端快取、輪替的四個步驟（練習 2、3）。
  • Parameter Store 與怎麼選；機密怎麼進到 ECS task 與 Lambda。
這課會用到：信封加密的觀念（認證課第 23 課：主金鑰留在 KMS 只加密「資料金鑰」，資料由程式用資料金鑰加密；AES-256-GCM 每次要新的 IV、解密前要驗 auth tag）；機密不該放環境變數、外洩後先輪替（devops 課第 11 課）；policy 的評估（第 2 課：預設拒絕、明確 Deny 優先，資源型與身分型政策一起決定）；ECS 的 execution role 與 task role（第 5 課：前者是 ECS 替你拉映像、讀 secret，後者是你的程式呼叫 AWS 用的）。
練習環境：模擬器的 KMS 會真的加解密，encryption context 不符也會拒絕；但它不檢查 key policy 與 IAM，也接受真的 AWS 會拒絕的參數（例如刪除等待期設 3 天）。Secrets Manager 的輪替要另外跑 Lambda，模擬器不執行，所以輪替的流程用頁面裡的練習推演。

最小解法：機密不進程式碼、不進 task definition

開場兩件事的共同問題是：機密的副本散落在很多地方，每多一份就多一個外洩的地方，而且換密碼時要一份份找出來改。解法是只留一份正本，放在一個有權限控管、有存取紀錄、能換版本的地方，程式在執行時才去拿：

機密的種類放哪裡程式怎麼用
資料庫密碼、第三方 API token、JWT 簽章金鑰Secrets Manager（存機密的代管服務，可以版本化與自動輪替）啟動時由 ECS 注入，或程式自己呼叫 GetSecretValue 並快取
要加密存進資料庫的欄位（客人的手機、外送平台的 token）金鑰放 KMS（Key Management Service，管理加密金鑰的服務），資料存你自己的資料庫程式向 KMS 要資料金鑰，自己加密（信封加密）
非機密的設定（功能開關、外部 API 的網址）環境變數，或 Parameter Store直接讀

用 AWS CLI 存一個 secret、再讀出來，就是 Secrets Manager 最基本的用法（在設好 env.sh 的視窗可以對模擬器試）：

aws secretsmanager create-secret --name cafe/prod/db \
  --secret-string '{"username":"pf_app","password":"…","host":"cafe-db.internal","port":5432,"dbname":"cafe"}'
aws secretsmanager get-secret-value --secret-id cafe/prod/db --query SecretString --output text

secret 的值可以是任意字串，慣例是放 JSON，一個 secret 存一組會一起用的值（帳號、密碼、主機）。之後誰讀過它、什麼時候讀的，都會出現在 CloudTrail（第 2 課）；要換密碼，只改這一份，所有服務下一次讀就拿到新的。離職員工筆電上的那份 .env 之所以危險，是因為它是一份沒人管得到的副本：正式環境的機密原則上不該出現在任何人的電腦上，開發用另一套只給開發環境用的 secret。

KMS 金鑰：誰能用它，由 key policy 決定

Secrets Manager 裡的值也是加密存放的，加密用的金鑰就在 KMS。所以先認識 KMS。KMS 金鑰（KMS key）是 KMS 裡的一個資源，有自己的 ARN；它的金鑰材料在 KMS 的硬體安全模組裡產生與使用，不會以明文離開（認證課第 23 課講過 HSM）。你只能用 API 請它做事：加密、解密、產生資料金鑰。

KMS 金鑰依誰管理分三種：

種類誰建立、誰管例子你能改它的 key policy 嗎
AWS 擁有的金鑰（AWS owned key）AWS 自己用，不在你的帳號裡S3 預設加密 SSE-S3 背後的金鑰不能，也看不到
AWS 代管金鑰（AWS managed key）服務第一次需要時自動在你的帳號建立aws/secretsmanager、aws/ssm不能，只能看
客戶管理金鑰（customer managed key）你自己建立咖啡店建的 alias/cafe-data能，並且能控制輪替與刪除

需要決定「誰能解密」時（例如收據 bucket 只能讓 cafe-api 讀、跨帳號分享），就要用客戶管理金鑰。alias（別名，例如 alias/cafe-data）是指向某把金鑰的好記名稱，程式裡寫 alias，換金鑰時只要改 alias 指向。

KMS 的權限跟其他服務不同：key policy（金鑰政策，每把金鑰一定有一份的資源型政策）是主要的授權來源。IAM 政策要能對這把金鑰生效，前提是 key policy 允許了帳號本身。建立金鑰時沒有自己寫 key policy，KMS 給的預設政策就是這一句（模擬器建的金鑰也是）：

{
  "Sid": "Enable IAM User Permissions",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::123456789012:root" },
  "Action": "kms:*",
  "Resource": "*"
}

這裡的 root 不是 root 使用者，而是「這個帳號」：意思是把這把金鑰的授權交給這個帳號的 IAM 政策決定。拿掉這一句，帳號裡任何 IAM 政策寫了 kms:Decrypt 都沒用；如果 key policy 裡也沒有任何人能管理這把金鑰，它就變成沒人能改的金鑰，只能找 AWS Support 處理。所以自己寫 key policy 時，這一句或明確的管理者一定要留著。

另外兩個常見的機制：grant（授權）是給某個身分一組暫時的、可撤銷的權限，AWS 服務常用它代替改 key policy（例如 EBS 掛載加密磁碟）；自動輪替可以替客戶管理金鑰開啟，換的是用來加密新資料的金鑰材料，舊材料保留，舊資料照樣解得開。

最後是刪除。依 KMS API 文件（2026-11-20 查證），ScheduleKeyDeletion 不會立刻刪，而是進入等待期，7 到 30 天，預設 30 天；期間金鑰不能用，可以 CancelKeyDeletion 取消。等待期一過，用這把金鑰加密的所有資料都永遠解不開。只是想停用，用 DisableKey。

💡 實務上：刪 KMS 金鑰前先「停用一陣子」
清理帳號時，看到一把「好像沒人用」的客戶管理金鑰，資深工程師不會直接排程刪除。做法是先 DisableKey，觀察 CloudTrail 和應用程式的錯誤一兩週，看有沒有人因為它解不開東西；確定沒有，再排程刪除並設最長的等待期。要記得的是：刪掉的不只是金鑰，是所有用它加密的資料（含備份）。另外，kms:ScheduleKeyDeletion 這個權限應該只給極少數人。

用 KMS 做信封加密

知道金鑰放哪裡、誰能用之後，開始用它。認證課第 23 課用 Web Crypto 模擬過信封加密：主金鑰只加密資料金鑰，資料由程式用資料金鑰加密。在 AWS 上，主金鑰就是 KMS 金鑰，流程對應兩個 API：

  1. 加密：呼叫 GenerateDataKey（KeySpec: 'AES_256'），拿到兩個東西：資料金鑰的明文 Plaintext（32 bytes）和用 KMS 金鑰加密過的同一把資料金鑰 CiphertextBlob。程式用明文加密資料，存「CiphertextBlob＋IV＋auth tag＋密文」，明文金鑰用完就清掉。
  2. 解密：把 CiphertextBlob 交給 Decrypt，拿回資料金鑰的明文，再解資料。對稱的 KMS 金鑰會把「是哪一把金鑰」記在 CiphertextBlob 裡，所以 Decrypt 不用指定金鑰。

為什麼不直接用 KMS 的 Encrypt 加密資料？依 KMS API 文件，對稱金鑰的 Encrypt 最多只收 4,096 bytes，文件也說它是給「少量資料，例如資料庫密碼」用的；而且每加密一筆就是一個網路請求、一筆計費。信封加密只有拿資料金鑰時呼叫 KMS，資料多大都在程式裡加密。

第二個重點是 encryption context（加密內容）：一組不是機密的鍵值對，例如 { tenant: 't-001' }。加密時帶了它，解密時就要帶完全相同（大小寫也要一樣）的一組，否則 KMS 回 InvalidCiphertextException。它的作用是把密文綁在某個情境上：多租戶的系統裡，就算有人把 A 租戶的密文複製到 B 租戶的資料列，B 的程式用 B 的 context 也解不開。context 會以明文出現在 CloudTrail 的紀錄裡，所以只能放識別用的值，不能放機密；反過來，它也讓稽核時看得出「誰在解哪個租戶的資料」。

用 SDK 寫起來是這樣（練習 1 要你寫完整的 seal／open）：

import { createCipheriv, randomBytes } from 'node:crypto'
import { GenerateDataKeyCommand } from '@aws-sdk/client-kms'

const dk = await kms.send(new GenerateDataKeyCommand({
  KeyId: 'alias/cafe-data', KeySpec: 'AES_256', EncryptionContext: { tenant: 't-001' },
}))
const iv = randomBytes(12)
const cipher = createCipheriv('aes-256-gcm', Buffer.from(dk.Plaintext!), iv)
const ciphertext = Buffer.concat([cipher.update('外送平台 token', 'utf8'), cipher.final()])
// 存：dk.CiphertextBlob、iv、cipher.getAuthTag()、ciphertext；dk.Plaintext 用完就清掉

每個請求都呼叫一次 GenerateDataKey，請求量大時會碰到 KMS 的請求配額，也會增加費用。常見的做法是在記憶體裡重用同一把資料金鑰一小段時間或一定的筆數；AWS Encryption SDK 有現成的快取機制。這是「呼叫次數」和「明文金鑰在記憶體多久」之間的取捨，練習 1 先不做快取。

💡 實務上：S3、RDS 的加密打勾就好，欄位加密才要自己寫
RDS 的儲存加密、S3 的 SSE-KMS（第 7 課）背後都是 KMS 的信封加密，由服務替你做，你只要選金鑰並給對權限。它們擋的是「磁碟或備份被拿走」；資料庫帳號被盜、SQL injection 時，資料庫照樣回傳明文。所以只有特別敏感、而且程式之外的人不該讀到的欄位（第三方 token、身分證字號）才值得在應用層自己加密，代價是那些欄位不能搜尋、不能排序。決定前先問：要防的是誰？

Secrets Manager：版本、staging label 與程式端快取

加密資料的金鑰交給 KMS 之後，回到開場的資料庫密碼。Secrets Manager 裡的每個 secret 可以有好幾個版本（version），每個版本有一個 VersionId，並掛著零到多個 staging label（階段標籤），用來表示這個版本現在的角色：

  • AWSCURRENT：目前的值。GetSecretValue 沒指定版本時拿到的就是它。
  • AWSPENDING：輪替途中產生、還在測試的新值。
  • AWSPREVIOUS：上一個 AWSCURRENT，保留「最後一個確定能用的值」，出事時可以退回。
aws secretsmanager describe-secret --secret-id cafe/prod/db --query VersionIdsToStages
# {"76c2db7b-…": ["AWSPREVIOUS"], "11111111-…": ["AWSCURRENT"]}

程式讀 secret 時要帶快取：每個請求都呼叫 GetSecretValue 會多一次網路延遲，Secrets Manager 也依 API 呼叫次數計費、有請求配額。但快取不能永遠有效，否則密碼換了程式還用舊的。快取要處理三件事，練習 2 會全部寫到：

  • TTL（存活時間）：超過時間就重新讀。時間由參數 now() 傳入，測試才能控制。
  • 同時的請求只送一次：服務剛啟動時幾十個請求同時要密碼，只送一個 GetSecretValue，其他人等同一個 Promise。
  • 失敗不快取：讀失敗就把錯誤丟出去，下一次重新讀；不能把失敗的 Promise 留在快取裡，否則一次網路抖動會讓程式一直失敗到 TTL 過期。

AWS 也有官方的快取套件（各語言的 Secrets Manager caching client）與 Lambda 用的 extension，觀念相同。這課自己寫一次，是為了理解它們在解決什麼問題。

輪替：四個步驟與「密碼剛換掉」的那幾秒

有了版本和快取，就能做開場那件「兩年沒換、沒人敢動」的事：輪替（rotation），定期把密碼換成新的。Secrets Manager 的輪替由一個 Lambda 函式執行（RDS 等服務有 AWS 提供的範本，也有由 AWS 直接代管的輪替）。依 Secrets Manager 使用者指南「Lambda rotation functions」（2026-11-20 查證），每次輪替依序呼叫這個函式四次，每次帶同一個 ClientRequestToken（就是新版本的 VersionId）：

步驟做什麼標籤的變化
createSecret產生新密碼，存成新版本新版本掛 AWSPENDING；AWSCURRENT 不動
setSecret到資料庫把密碼改成 AWSPENDING 的值不變
testSecret用 AWSPENDING 的值實際連一次資料庫不變
finishSecret把 AWSCURRENT 移到新版本Secrets Manager 自動把 AWSPREVIOUS 加到原本的 AWSCURRENT 版本

順序的意義是：新密碼測試通過之前，AWSCURRENT 一直指著舊的，所有程式都用舊密碼，任何一步失敗都不影響線上。Lambda 失敗會重試，所以每一步都要冪等（同一件事做很多次，效果跟做一次相同）：createSecret 發現這個 token 的版本已經是 AWSPENDING，就什麼都不做；finishSecret 發現它已經是 AWSCURRENT，也什麼都不做。練習 3 寫這兩步的標籤變化。

問題出在 setSecret 到 finishSecret 之間：資料庫的密碼已經改了，程式快取裡還是舊的。依資料庫帳號的用法，有兩種輪替策略：

策略做法舊密碼什麼時候失效程式要處理什麼
單一使用者（single user）直接改這個帳號的密碼setSecret 的那一刻認證失敗（PostgreSQL 的錯誤碼 28P01）時強制刷新快取，重試一次
交替使用者（alternating users）準備兩個權限相同的帳號，每次輪替改「目前沒在用的那個」，再把 AWSCURRENT 指過去下一次輪替才改到它不太需要處理，快取的舊值在這段期間仍然有效

交替使用者需要另一組有權限建立帳號的憑證，設定也比較多；單一使用者簡單，但要求程式自己會「認證失敗就刷新一次」。練習 2 的 withDbSecret 就是這個：只在 28P01 時刷新，而且只重試一次；連線被拒、逾時這類錯誤跟密碼無關，刷新只會多打一次 API。已經建立的連線不受改密碼影響，PostgreSQL 只在登入時檢查密碼，所以連線池裡的舊連線會繼續用到被回收為止。

💡 實務上：先輪替一次，才知道你的程式撐不撐得住
很多團隊開了自動輪替，第一次真的輪替時才發現有一支排程程式在啟動時讀一次密碼就永遠不再讀，半夜開始認證失敗。資深的做法是：開自動輪替之前，先在 staging 手動觸發一次（aws secretsmanager rotate-secret --secret-id …），看所有用到這個 secret 的服務（API、worker、排程、BI 工具）都能自己換過去；並在告警裡加上「認證失敗次數」，輪替出問題時第一時間知道。

Parameter Store 與怎麼選

Secrets Manager 之外，AWS 還有另一個常被拿來放設定與機密的地方：Systems Manager 的 Parameter Store。它存的是一個個具名的參數，名稱可以用 / 分成階層，例如 /cafe/prod/db/password；型別有 String、StringList，以及用 KMS 加密的 SecureString。階層讓你一次讀一整個環境的設定：

aws ssm put-parameter --name /cafe/prod/api/payment-url --type String --value https://pay.example.test
aws ssm put-parameter --name /cafe/prod/db/password --type SecureString --value '…'
aws ssm get-parameters-by-path --path /cafe/prod --recursive --with-decryption

沒加 --with-decryption 時，SecureString 回傳的是密文；IAM 也可以依路徑授權（arn:aws:ssm:…:parameter/cafe/prod/*），讓 staging 的服務讀不到 prod 的參數。兩者怎麼選，查表用，不用背（依兩個服務的使用者指南，2026-11-20 查證）：

Secrets ManagerParameter Store（標準）
主要用途機密：密碼、token、金鑰設定，也能放加密的值
自動輪替有（Lambda 或代管輪替）沒有，要自己做
版本與標籤AWSCURRENT／AWSPENDING／AWSPREVIOUS有版本號與自訂標籤
大小與數量—每個值 4 KB、每個帳號每個 region 10,000 個（進階層 8 KB、100,000 個，要收費）
費用依 secret 數量按月計費，加上 API 呼叫次數標準層不另外收費
跨帳號分享可以（resource policy）標準層不行，進階層可以

咖啡店的做法：會輪替的資料庫密碼、外送平台 token 放 Secrets Manager；功能開關、外部 API 網址、不會輪替的少量設定放 Parameter Store 標準層。兩邊混用很常見，重點是團隊有共同的規則，讓人知道東西去哪裡找。

機密怎麼進到 ECS 與 Lambda

最後把機密送到程式手上。ECS：task definition 的 container definition 裡用 secrets（不是 environment），ECS 在啟動容器時讀出值、設成環境變數。依 ECS 開發者指南（2026-11-20 查證），valueFrom 可以指到整個 secret，或用這個格式只取 JSON 裡的一個鍵：

arn:aws:secretsmanager:region:account:secret:secret-name:json-key:version-stage:version-id

"secrets": [
  { "name": "DB_PASSWORD", "valueFrom": "arn:aws:secretsmanager:ap-northeast-1:123456789012:secret:cafe/prod/db-AbCdEf:password::" },
  { "name": "PAYMENT_URL", "valueFrom": "arn:aws:ssm:ap-northeast-1:123456789012:parameter/cafe/prod/api/payment-url" }
]

後面三段可以省略，但冒號要留著（上面的 :password::）。三個要注意的地方：

  • 讀 secret 的是 execution role：注入發生在容器啟動之前，由 ECS 代理去讀，所以 secretsmanager:GetSecretValue（或 ssm:GetParameters）要給 execution role，不是 task role（第 5 課）。給錯了，task 會停在啟動階段。
  • 只在啟動時注入一次：文件寫明，secret 之後被更新或輪替，容器不會自動拿到新值，要開新的 task（service 用 force new deployment）。所以「單一使用者輪替＋只靠 ECS 注入」會在 setSecret 之後到下一次部署之間認證失敗：要嘛程式自己讀並處理 28P01（練習 2），要嘛用交替使用者。
  • 環境變數仍然看得到：容器裡的程式、子程序、除錯工具都讀得到（devops 課第 11 課）。比寫在 environment 好的地方是：task definition 裡只有 ARN，沒有值。

Lambda（第 6 課）：函式的環境變數雖然靜態加密，但有權限讀函式設定的人都看得到明文，所以機密不要放在 Lambda 的環境變數。做法是在 handler 外面（冷啟動時）讀 secret 並快取，或用 AWS 提供的 Parameters and Secrets Lambda Extension 幫你快取。讀 secret 的權限給函式的 execution role。

💡 實務上：開場的兩件事怎麼收尾
task definition 裡的明文密碼：改成 secrets 之後，舊的 task definition 版本還留著明文，所以除了改設定，還要把那個密碼換掉，並把舊的版本 deregister。離職員工的 .env：當成已經外洩，先輪替資料庫密碼與外送平台 token（新的上線、確認、再撤銷舊的），再查 CloudTrail 與資料庫的連線紀錄有沒有可疑的使用。之後正式環境的機密只存在 Secrets Manager，人要看得到它，得有 IAM 權限並留下紀錄。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。用第 1 課建議的獨立練習帳號與第 2 課建立的 learn-sandbox profile，不要用公司的帳號。

費用：客戶管理的 KMS 金鑰按月計費，加上 API 請求次數；Secrets Manager 依 secret 數量按月計費，加上 API 呼叫次數；Parameter Store 標準層的參數不另外收費。金額以官方定價頁為準：AWS KMS 定價、Secrets Manager 定價、Systems Manager 定價。做完照「清除」刪掉。
# 1. 建一把客戶管理金鑰，記下輸出的 KeyId，再取一個 alias
aws kms create-key --description cafe-learn-09 --profile learn-sandbox --region ap-northeast-1
aws kms create-alias --alias-name alias/cafe-learn-09 --target-key-id <KeyId> --profile learn-sandbox --region ap-northeast-1

# 2. 看預設的 key policy：找到 Principal 是 arn:aws:iam::<帳號>:root 的那一句
aws kms get-key-policy --key-id alias/cafe-learn-09 --policy-name default --output text --profile learn-sandbox --region ap-northeast-1

# 3. 產生資料金鑰（帶 encryption context），把加密過的資料金鑰存成檔案
aws kms generate-data-key --key-id alias/cafe-learn-09 --key-spec AES_256 --encryption-context tenant=t-001 \
  --query CiphertextBlob --output text --profile learn-sandbox --region ap-northeast-1 | base64 --decode > dk.bin

# 4. 用對的 context 解開（成功），再用錯的 context 解（看到 InvalidCiphertextException）
aws kms decrypt --ciphertext-blob fileb://dk.bin --encryption-context tenant=t-001 --query KeyId --profile learn-sandbox --region ap-northeast-1
aws kms decrypt --ciphertext-blob fileb://dk.bin --encryption-context tenant=t-002 --query KeyId --profile learn-sandbox --region ap-northeast-1

# 5. 建 secret、放新版本，看標籤怎麼移動
aws secretsmanager create-secret --name cafe-learn-09/db --secret-string '{"password":"v1"}' --profile learn-sandbox --region ap-northeast-1
aws secretsmanager put-secret-value --secret-id cafe-learn-09/db --secret-string '{"password":"v2"}' --profile learn-sandbox --region ap-northeast-1
aws secretsmanager describe-secret --secret-id cafe-learn-09/db --query VersionIdsToStages --profile learn-sandbox --region ap-northeast-1

# 6. Parameter Store：一個 String、一個 SecureString，用路徑一次讀出
aws ssm put-parameter --name /cafe-learn-09/api/url --type String --value https://pay.example.test --profile learn-sandbox --region ap-northeast-1
aws ssm put-parameter --name /cafe-learn-09/db/password --type SecureString --value v1 --profile learn-sandbox --region ap-northeast-1
aws ssm get-parameters-by-path --path /cafe-learn-09 --recursive --with-decryption --profile learn-sandbox --region ap-northeast-1

# 7. 到 CloudTrail 的 Event history 找剛才的 Decrypt、GetSecretValue：看得到 encryption context 與呼叫者
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=Decrypt --max-results 5 --profile learn-sandbox --region ap-northeast-1

put-secret-value 沒指定標籤時，新版本會成為 AWSCURRENT，舊的變成 AWSPREVIOUS。CloudTrail 的事件可能要幾分鐘才出現。

清除

aws ssm delete-parameter --name /cafe-learn-09/api/url --profile learn-sandbox --region ap-northeast-1
aws ssm delete-parameter --name /cafe-learn-09/db/password --profile learn-sandbox --region ap-northeast-1
aws secretsmanager delete-secret --secret-id cafe-learn-09/db --force-delete-without-recovery --profile learn-sandbox --region ap-northeast-1
aws kms delete-alias --alias-name alias/cafe-learn-09 --profile learn-sandbox --region ap-northeast-1

rm dk.bin
# 確認：參數清單是空的、金鑰狀態是 PendingDeletion
aws ssm get-parameters-by-path --path /cafe-learn-09 --recursive --profile learn-sandbox --region ap-northeast-1
aws kms describe-key --key-id <KeyId> --query KeyMetadata.KeyState --profile learn-sandbox --region ap-northeast-1

--force-delete-without-recovery 立刻刪除、不能復原，只在練習用；正式環境用預設的復原期。金鑰最短也要等 7 天才真的刪掉，期間可以 cancel-key-deletion。

練習

本機練習在 aws/practice/work/09/。練習 1、2 會連到模擬器；練習 2 的資料庫是測試裡的假函式，不用開 PostgreSQL。

練習 1：完成 envelope.ts 的 seal(kms, keyId, plaintext, context) 與 open(kms, sealed, context)。seal：送 GenerateDataKeyCommand（KeyId、KeySpec: 'AES_256'、EncryptionContext: context），用回傳的 Plaintext 當金鑰、randomBytes(12) 當 IV，以 createCipheriv('aes-256-gcm', …) 加密，回傳 { encryptedKey, iv, tag, ciphertext }（都是 base64；encryptedKey 是 CiphertextBlob）。open：用 DecryptCommand（同樣帶 EncryptionContext）解開資料金鑰，setAuthTag 後解密。測試會檢查：回傳的物件裡沒有明文資料金鑰、沒有呼叫 EncryptCommand、每次的 IV 不同、20 KB 的資料可以加解密、別的租戶的 context 解不開、密文或 tag 被改一個 byte 就丟錯。

練習 2：完成 get-secret.ts。secretCache(sm, secretId, { ttlMs, now }) 回傳 { get({ force }) }：在 TTL 內回傳快取（時間用 now()，不要用 Date.now()）；同時好幾個 get 只送一次 GetSecretValueCommand；force: true 一定重新讀；讀失敗時把錯誤丟出去，而且下一次 get 要重新送請求。SecretString 是 JSON，回傳解析後的物件。withDbSecret(cache, run)：用快取的值呼叫 run；run 丟出 code === '28P01'（PostgreSQL 認證失敗）的錯誤時，get({ force: true }) 拿新的值再呼叫一次，第二次再失敗就把錯誤丟出去；其他錯誤直接丟出，不刷新、不重試。

練習 3：寫輪替函式的兩個步驟對 staging label 的處理。versions 是「版本 ID → 標籤陣列」（就是 describe-secret 的 VersionIdsToStages），兩個函式都回傳新的物件、不能改傳進來的物件，沒有任何標籤的版本要從結果裡移除。

  • createSecret(versions, token)：token 的版本已經有 AWSPENDING 就原樣回傳（Lambda 重試）；token 已經是別的版本（有其他標籤）就丟錯；否則先把其他版本身上殘留的 AWSPENDING 拿掉（上一次輪替失敗留下的），再新增 token: ['AWSPENDING']。AWSCURRENT 不能動。
  • finishSecret(versions, token)：token 已經有 AWSCURRENT 就原樣回傳；token 沒有 AWSPENDING 就丟錯（還沒建立、測試過的版本不能切換）；否則把舊的 AWSCURRENT 換成 AWSPREVIOUS（其他版本身上的 AWSPREVIOUS 拿掉，只留一個），token 拿掉 AWSPENDING、加上 AWSCURRENT。

練習 4：咖啡店要存兩樣東西：每 30 天要自動換一次的資料庫密碼，以及金流商的 API 網址（不是機密）。哪個分法最合理？

✓ b。要自動輪替的機密用 Secrets Manager：它有輪替流程與版本標籤；不是機密的設定不需要它的功能，也不用多付每個 secret 的月費。c 的加密確實一樣，但 Parameter Store 沒有自動輪替，30 天換一次要自己做整套流程。d 會讓密碼出現在 task definition 的每一個版本裡。

練習 5：同事替收據加密建了一把客戶管理金鑰，為了「最小權限」，自己寫的 key policy 只允許 cafe-api 的 task role 使用，拿掉了預設那句 arn:aws:iam::<帳號>:root。之後會發生什麼事？

✓ c。KMS 的 key policy 是主要授權來源，IAM 政策要生效，key policy 必須先允許帳號（那句 root 指的是帳號，不是 root 使用者）。拿掉後，只有 key policy 裡明確列出的身分能用它，a 的 AdministratorAccess 也一樣沒用。要最小權限，做法是保留那句並在 IAM 端收窄，或在 key policy 裡明確列出金鑰管理者。

練習 6：cafe-api 用信封加密存外送平台的 token，encryption context 是 { tenant: 租戶 ID }。有人把 A 租戶那一列的密文整段複製到 B 租戶的資料列，再用 B 租戶的身分讀取。結果是？

✓ a。encryption context 在加密時被綁進密文，Decrypt 一定要帶完全相同的一組，所以密文被搬到別的租戶就失效。b 是沒用 encryption context 時的結果。c 錯在 auth tag 只保護密文本身沒被改過，整段搬走的密文 tag 完全正確；要讓 GCM 也綁住資料列，要另外用 AAD。

常見錯誤

  • 密碼寫在 task definition 的 environment：每個舊版本都留著明文。改用 secrets 指向 ARN，改完還要把那個密碼換掉。
  • 讀 secret 的權限給了 task role：ECS 注入是 execution role 在讀，task 會停在啟動階段。程式自己呼叫 API 讀的才給 task role。
  • 以為輪替後容器會自動拿到新值：ECS 只在啟動時注入。單一使用者輪替時，程式要能在認證失敗時刷新，或改用交替使用者。
  • 每個請求都讀一次 secret，或讀一次就永遠快取：前者慢又花錢，後者輪替後一直用舊密碼。用 TTL，並在認證失敗時強制刷新一次。
  • 用 KMS Encrypt 加密整份資料：最多 4,096 bytes，每筆都是一次網路請求。用 GenerateDataKey 做信封加密。
  • 把明文資料金鑰跟密文存在一起：等於沒加密。只存 CiphertextBlob。
  • encryption context 放機密：它會以明文出現在 CloudTrail。只放租戶 ID、用途這類識別值。
  • 直接排程刪除 KMS 金鑰：等待期結束後，用它加密的資料與備份都永遠解不開。先停用觀察，再刪。
  • key policy 拿掉帳號那一句：IAM 政策對這把金鑰全部失效，可能變成沒人能管理的金鑰。

小結

  • 機密只留一份正本：密碼、token 放 Secrets Manager，加密用的金鑰放 KMS，程式在執行時才拿；正式環境的機密不出現在程式碼、task definition 與任何人的電腦上。
  • KMS 的 key policy 是主要授權來源，預設那句 …:root 把授權交給帳號的 IAM。客戶管理金鑰能自訂 key policy、輪替與刪除；刪除有 7～30 天等待期，刪掉後資料永遠解不開，先用 DisableKey。
  • 信封加密：GenerateDataKey 拿明文與加密過的資料金鑰，資料在程式裡用 AES-256-GCM 加密，只存 CiphertextBlob。KMS Encrypt 最多 4,096 bytes，只用在很小的資料。
  • encryption context 是加解密都要完全相同的鍵值對，把密文綁在租戶或用途上；它會出現在 CloudTrail，不能放機密。
  • Secrets Manager 的版本用 AWSCURRENT、AWSPENDING、AWSPREVIOUS 標示角色。程式端快取要有 TTL、合併同時的請求、失敗不快取。
  • 輪替四步：createSecret（AWSPENDING）→ setSecret → testSecret → finishSecret（移 AWSCURRENT，舊版自動變 AWSPREVIOUS），每一步都要冪等。單一使用者輪替時，程式在 28P01 時刷新一次；交替使用者讓舊值多撐一個週期。
  • Parameter Store 放設定（標準層不另外收費、每個值 4 KB），會輪替的機密放 Secrets Manager。ECS 用 secrets 在啟動時注入，權限給 execution role；Lambda 不把機密放環境變數，在 handler 外讀並快取。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 7：咖啡店的 Vue 官網要放上 S3。同事為了讓網頁打得開，關掉 bucket 的 Block Public Access，加了一條 Principal: "*"、s3:GetObject 的 bucket policy。這個 bucket 裡還有 receipts/ 資料夾。比較好的做法是？

✓ c。CloudFront＋OAC 讓 bucket 完全不必公開，bucket policy 只允許那個 distribution（條件比對 SourceArn），收據也該放在另一個 bucket。b 是把安全建立在「猜不到」上，網址一旦出現在 log、轉寄或瀏覽紀錄就外洩。d 錯在 website endpoint 本身就要求 bucket 公開。（第 7 課）

練習 8：開了版本控制的 bucket，有人執行 aws s3 rm s3://cafe-menu/latte.jpg，網站的拿鐵圖片不見了。怎麼救回來？

✓ a。版本控制下，沒有指定版本的刪除只是在最上面放一個 delete marker，原本的資料版本還在。刪掉 delete marker 就還原，不產生新的資料版本。c 也看得到圖片，但多存了一份一樣的資料、版本歷史變亂，大量還原時又慢又要付下載與上傳的費用。d 是 RDS 的功能，S3 沒有。（第 7 課）

練習 9：收據 bucket 用 SSE-KMS 加密（客戶管理金鑰，key policy 是預設的）。cafe-api 的 task role 有 s3:GetObject on receipts/*，讀檔卻收到 AccessDenied。先查什麼？

✓ d。SSE-KMS 的物件要兩把鑰匙：S3 的讀取權限和 KMS 的解密權限。key policy 是預設的（允許帳號），所以在 task role 加上對這把金鑰的 kms:Decrypt 就會生效。a 錯在同帳號的身分型與資源型政策取聯集，task role 自己有 s3:GetObject 就夠。b 只擋公開存取，不擋帳號內有權限的 role。（第 7、9 課）

練習 10：為了減輕主資料庫的負擔，cafe-api 把所有 SELECT 都改送 read replica。上線後客服接到「結帳完，訂單頁面一片空白，重新整理又出現了」。原因是？

✓ b。replica 有複寫延遲，「自己剛寫的東西馬上要讀」的查詢要走 primary（read-your-writes）：例如寫入後同一個使用者幾秒內的讀、交易內的讀。a 混淆了 Multi-AZ（同步備援、平常不接讀取）與 read replica。c 的逾時會是錯誤，不會是空結果。（第 8 課）

練習 11：開幕活動時，收據的 Lambda 擴到幾百個同時執行，RDS 開始回 too many connections，連 cafe-api 也連不上資料庫。最直接的修法是？

✓ c。每個 Lambda 執行環境各自開連線，並行數就是連線數；RDS Proxy 把大量短暫的連線合併到少量真正的資料庫連線。a 只是把上限推高，流量再大一點又會撞到，而且所有服務一起陪葬。d 讓每次呼叫都要重新建立連線，延遲變高，同時執行的數量不變，連線數照樣爆。（第 8 課）

練習 12：工程師下午誤刪了一批訂單，你用 PITR 還原到刪除前一分鐘。還原完成後，cafe-api 還是看不到那批訂單。為什麼？

✓ a。PITR 永遠還原成一個新的執行個體，原本的不會被覆蓋。接著要決定：把 app 的連線設定（secret 裡的 host）改到新的那台，或只從新的那台把被刪的資料搬回原本的資料庫。b 錯在 PITR 用自動備份加交易紀錄，可以還原到保留期間內的任一時間點，不只是每天一次。（第 8 課）

練習 13：資料庫密碼用單一使用者策略每 30 天自動輪替，cafe-api 在 ECS 上用 task definition 的 secrets 注入密碼。輪替那天的 setSecret 之後，所有新的資料庫連線都認證失敗。根本原因是？

✓ d。注入是啟動時的一次性動作，輪替後要開新的 task 才拿得到新值；單一使用者策略下，舊密碼在 setSecret 那一刻就失效。修法是程式自己讀 secret 並在 28P01 時刷新一次，或改用交替使用者。a 不會等到輪替那天才出事：task 一開始就啟動不了。（第 9 課）
