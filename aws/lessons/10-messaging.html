階段 5：事件與上線 · 第 10 課

SQS、SNS、EventBridge 與 S3 事件：visibility timeout、DLQ、fan-out 與冪等

咖啡店的結帳成功後要做三件事：寄電子收據、替會員加點數、通知廚房做飲料。一開始全部寫在結帳 API 裡，郵件服務一慢，結帳就跟著慢。改成丟訊息給背景程式處理之後，新的問題出現了：有客人收到兩封一樣的收據；有一筆點數一直沒加上去，訊息也找不到了；門市每晚上傳到 S3 的銷售 CSV，檔名有空白的那幾家永遠沒被匯入，也沒有人發現。

這一課是 AWS 上「服務之間怎麼傳話」：SQS（佇列）、SNS（推播）、EventBridge（事件匯流排）各自做什麼、怎麼選，以及每一種都會遇到的同一件事：訊息會重複、會失敗、會靜默地沒送到。學完你能設定 visibility timeout 與 DLQ、寫出冪等的消費者、用 SNS 做 fan-out、讀懂 EventBridge 的 event pattern，並正確處理 S3 事件。

這課的路線：

  • 三個服務一句話，以及開場三件事各自錯在哪。
  • SQS：visibility timeout、long polling、DLQ；消費者用 DynamoDB 做冪等（練習 1）。
  • SNS fan-out：一則訊息推給好幾個佇列，各自過濾（練習 3）。
  • EventBridge：用 event pattern 把事件送到對的地方（練習 2）。
  • S3 事件經過 SQS 送到 Lambda：URL 編碼的 key、測試訊息、部分失敗（練習 4）；最後一段 Step Functions 與 EventBridge Scheduler。
這課會用到：佇列的送達語意（系統設計課第 12 課：先處理再 ack 是「至少一次」，visibility timeout 是租約，超過接收次數進 DLQ）；冪等（系統設計課第 9 課：同一件事做很多次，效果跟做一次相同）；DynamoDB 的條件寫入（資料儲存課第 14 課：attribute_not_exists 讓「不存在才寫入」變成一個原子動作）；Lambda 的 handler 與 batchItemFailures（第 6 課）。
練習環境：模擬器的 SQS 會真的照 visibility timeout 重新送出、超過次數移到 DLQ，SNS 的過濾與 S3 事件也會真的送到佇列，所以練習 1、3、4 會等幾秒。模擬器不檢查 queue policy，也不會執行 Lambda：handler 由測試直接呼叫。

三個服務各做什麼

三個服務都在「一方送出、另一方之後再處理」，差別在訊息怎麼流：

服務模型一則訊息給幾個人咖啡店的例子
SQS（Simple Queue Service）佇列：訊息放著，消費者自己來拉（poll），處理完刪掉一個：同一則訊息只有一個消費者在處理寄收據的工作，由 worker 一則則處理
SNS（Simple Notification Service）發布／訂閱：發布到 topic，SNS 推給每個訂閱者每個訂閱者一份「訂單成立」同時推給收據、點數、廚房
EventBridge事件匯流排：事件送到 bus，rule 依內容（event pattern）決定送給哪些目標符合 rule 的每個目標一份AWS 服務的事件、跨帳號的事件、依欄位細分的路由

SNS 和 EventBridge 都不保存訊息給你慢慢處理：消費者忙不過來或暫時掛掉，訊息就要有地方放。所以常見的組合是前面用 SNS 或 EventBridge 分送，每個消費者前面各放一個 SQS，由佇列吸收尖峰、負責重試。

開場三件事對應這課的三個重點：

  • 收據寄兩封：SQS 標準佇列保證「至少一次」送達，同一則訊息可能被收到兩次；處理太久超過 visibility timeout，也會被另一個 worker 再拿一次。消費者必須冪等。
  • 點數漏加、訊息不見：worker 一收到就把訊息刪掉，接著加點數時程式掛了，訊息已經沒了。要「處理成功才刪」，失敗的留在佇列重試，一直失敗的進 DLQ，並且對 DLQ 告警。
  • 有空白的檔名沒被匯入：S3 事件裡的 key 是 URL 編碼的，門市 A.csv 變成 %E9%96%80%E5%B8%82+A.csv，直接拿去讀 S3 會找不到；錯誤又被吞掉，所以沒人發現。

SQS：visibility timeout、long polling 與 DLQ

先把 SQS 的三個設定看清楚，開場的前兩件事都出在這裡。消費者用 ReceiveMessage 拉訊息時，訊息不會從佇列消失，只是在 visibility timeout（可見性逾時）這段時間內別人看不到；消費者處理完要自己 DeleteMessage。時間到了還沒刪，訊息重新出現，別的消費者會再拿到它。依 SQS 開發者指南（2026-11-20 查證），預設 30 秒，從第一次收到算起最長 12 小時。

  • visibility timeout 要比處理時間長：處理要 40 秒、timeout 30 秒，第 30 秒時訊息重新出現，另一個 worker 也開始處理，收據就寄了兩封。不確定要多久時，處理期間用 ChangeMessageVisibility 定期延長（heartbeat）。Lambda 讀 SQS 時，Lambda 文件建議佇列的 visibility timeout 至少是函式 timeout 的 6 倍。
  • long polling：ReceiveMessage 帶 WaitTimeSeconds（最多 20 秒），佇列是空的時候等到有訊息或時間到才回應。不帶（short polling）會立刻回傳空結果，worker 在空佇列上不停打 API，浪費請求費用。
  • DLQ（dead-letter queue，死信佇列）：在來源佇列設 RedrivePolicy（DLQ 的 ARN＋maxReceiveCount），同一則訊息被接收超過這個次數還沒刪，SQS 就把它移到 DLQ，不再一直重試。修好程式後，可以把 DLQ 裡的訊息 redrive 回原本的佇列。
aws sqs create-queue --queue-name cafe-receipts-dlq
aws sqs create-queue --queue-name cafe-receipts --attributes '{
  "VisibilityTimeout": "60",
  "ReceiveMessageWaitTimeSeconds": "20",
  "RedrivePolicy": "{\"deadLetterTargetArn\":\"arn:aws:sqs:ap-northeast-1:123456789012:cafe-receipts-dlq\",\"maxReceiveCount\":\"5\"}"
}'

ReceiveMessageWaitTimeSeconds 是佇列層級的 long polling 預設值，請求裡的 WaitTimeSeconds 會蓋過它。

佇列分兩種：標準佇列（standard）吞吐量高，至少一次送達、順序盡量但不保證；FIFO 佇列在同一個 message group 內保證順序，並在 5 分鐘的去重間隔內，同一個 deduplication ID 的 SendMessage 不會產生重複的訊息。FIFO 的「exactly-once processing」指的是「佇列裡不會多出重複的訊息」，你的 worker 處理到一半當機、訊息重新出現，照樣會處理第二次，所以消費者仍然要冪等。

💡 實務上：DLQ 不告警，等於訊息被丟進垃圾桶
DLQ 最常見的狀態是：設好了，三個月後才有人發現裡面躺了兩千則訊息。資深的做法是對 DLQ 的 ApproximateNumberOfMessagesVisible 大於 0 設 CloudWatch 告警，對主佇列的 ApproximateAgeOfOldestMessage（最老的訊息等了多久）設告警，前者告訴你「有東西一直失敗」，後者告訴你「處理跟不上」。值班手冊寫清楚：DLQ 有訊息時，先看訊息內容與錯誤 log，修好之後再 redrive，不要直接清空。

冪等的消費者：重複一定會發生

visibility timeout 與 DLQ 解決了「失敗的不要丟」，但「至少一次」代表重複一定會發生：網路斷在 DeleteMessage 之前、處理超時、生產者自己重送。系統設計課第 9、12 課講過觀念，這裡用 AWS 的元件做出來：

  1. 每則訊息找出一個業務上的冪等鍵：寄收據就是訂單 ID。不要用 SQS 的 MessageId，生產者重送同一張訂單時，MessageId 是新的。
  2. 處理前，用 DynamoDB 查這個鍵有沒有「完成標記」（GetItem，ConsistentRead: true）；有的話是重複的，直接刪訊息。
  3. 處理。失敗就不要刪，讓它在 visibility timeout 之後重新出現。
  4. 成功後寫完成標記，用條件寫入 attribute_not_exists(pk)：兩個 worker 同時做完時，只有一個寫得進去，另一個收到 ConditionalCheckFailedException，一樣當成完成。最後刪訊息。

順序很重要：先寫完成標記再處理，處理失敗時標記已經在了，重試會被當成重複而跳過，這封收據永遠不會寄出（就是點數漏加的另一種版本）。完成標記記在程式的記憶體（一個 Set），worker 重啟或有第二台 worker 就失效。

這個做法還有一個縫：處理成功、寫標記之前程序當機，下次會再處理一次。所以副作用本身最好也冪等：寄信時把訂單 ID 當成郵件服務的冪等鍵、加點數用「這筆訂單的點數紀錄」這種有唯一約束的寫入，而不是「點數 + 10」。更嚴謹的做法是先寫一筆有到期時間的「處理中」紀錄當租約，AWS 的 Powertools for AWS Lambda 有現成的 idempotency 工具採用這種做法。練習 1 先做最基本的版本。

DynamoDB 的 GSI 與部分讀取是最終一致的；完成標記要用主表的 ConsistentRead 查。模擬器寫完立刻讀得到，不會暴露這個差異。

SNS fan-out：一則訊息，好幾個消費者

寄收據的 worker 寫好之後，加點數、通知廚房也要收到同一張訂單。不要讓結帳 API 分別送三次，那樣結帳要知道所有下游，加一個下游就要改結帳。fan-out（扇出）的做法：結帳只發布一次到 SNS topic cafe-orders，三個佇列各自訂閱。

三個設定決定 fan-out 會不會動、收到的是什麼：

  • queue policy：SQS 佇列預設不讓別人送訊息進來。要在佇列的 Policy 屬性允許 sns.amazonaws.com 做 sqs:SendMessage，並用條件 aws:SourceArn 限定只有這個 topic；少了條件，任何帳號的任何 topic 都能把訊息塞進你的佇列。
  • RawMessageDelivery：預設 SNS 會把訊息包在一層 JSON 信封裡（Type、TopicArn、Message…），消費者要解兩次。訂閱時設 RawMessageDelivery: true，佇列收到的就是原本的訊息。
  • filter policy（過濾政策）：每個訂閱可以只收符合條件的訊息，例如廚房只要飲料。預設比對的是 message attributes（訊息的附加屬性）；要比對訊息內容（JSON body）的欄位，訂閱屬性要加 FilterPolicyScope: MessageBody。寫錯範圍不會報錯，只會什麼都收不到。
aws sns subscribe --topic-arn arn:aws:sns:ap-northeast-1:123456789012:cafe-orders \
  --protocol sqs --notification-endpoint arn:aws:sqs:ap-northeast-1:123456789012:cafe-kitchen \
  --attributes '{"RawMessageDelivery":"true","FilterPolicyScope":"MessageBody","FilterPolicy":"{\"type\":[\"drink\"]}"}'

過濾放在 SNS 而不是在 worker 裡丟掉不要的訊息，好處是不要的訊息根本不會進佇列，不佔處理量也不用付佇列的請求費用。

💡 實務上：先問「要不要保證送到」
SNS 推給 SQS 時，訊息有佇列接著；推給 HTTP 端點或 email 時，對方掛太久，重試用完訊息就沒了（可以替訂閱設 DLQ 接住）。所以團隊內部的服務間溝通，資深工程師幾乎都用「SNS → 每個消費者自己的 SQS」，而不是讓 SNS 直接打服務的 HTTP API。另外，新增一個消費者時只要新增一個訂閱，不用改發布端，這也是 code review 時判斷「這個功能該不該改結帳程式」的依據。

EventBridge：用 event pattern 路由事件

SNS 的過濾是「每個訂閱一條規則」；當事件的種類、來源越來越多，或要接 AWS 服務自己發出的事件（例如 ECS task 停止、S3 物件建立），就用 EventBridge。事件送到一條 event bus（事件匯流排；每個帳號有一條 default bus 接 AWS 服務的事件，也可以自己建），rule（規則）用 event pattern 比對事件，符合的送給 rule 的目標（SQS、Lambda、Step Functions、另一個帳號的 bus…）。

// 結帳發出的事件（PutEvents）
{ "source": "cafe.orders", "detail-type": "OrderPaid",
  "detail": { "orderId": "o-1", "total": 190, "channel": "app", "store": "taipei-01", "items": ["latte", "croissant"] } }

// rule 的 event pattern：台北門市、App 下單、金額 100 以上
{ "source": ["cafe.orders"],
  "detail": { "store": [{ "prefix": "taipei-" }], "channel": ["app"], "total": [{ "numeric": [">=", 100] }] } }

依 EventBridge 使用者指南的比較運算子一節（2026-11-20 查證），規則是：

  • pattern 裡不同的欄位是 AND；同一個欄位的陣列是 OR（"channel": ["app", "kiosk"]）。
  • 巢狀的物件一層層往下比對；最底層（leaf）一定寫成陣列。
  • 事件裡的值是陣列時，只要有一個元素符合就算符合（items 含 croissant）。
  • prefix 只比對字串；numeric 只比對數字（事件裡的 "190" 是字串，不會符合）；exists: false 比對「沒有這個欄位」；anything-but 是「不是這些值」。

event pattern 最大的風險是寫錯不會報錯：大小寫不同、數字寫成字串、欄位放錯層，rule 照樣建立成功，只是永遠不觸發。所以上線前用 aws events test-event-pattern --event-pattern … --event … 拿真的事件測，並對 rule 的 TriggeredRules／目標的 FailedInvocations 指標設監控。練習 2 寫一個 pattern 比對函式，把這些規則練一次。

EventBridge 還有兩個 SNS 沒有的功能：archive／replay（把 bus 上的事件存起來，修好消費者後重播一段時間的事件），以及跨帳號、跨 region 把事件轉送到另一條 bus。代價是設定比 SNS 多、延遲通常也比較高；只是「一則訊息推給幾個佇列」的話，SNS 就夠了。

S3 事件：URL 編碼的 key、測試訊息與部分失敗

最後是開場第三件事。S3 可以在物件建立、刪除時發出事件通知（event notification），送到 SQS、SNS、Lambda，或打開 EventBridge 整合送到 default bus。設定時可以用前綴、後綴過濾，例如只要 sales/ 底下的檔案：

aws s3api put-bucket-notification-configuration --bucket cafe-sales --notification-configuration '{
  "QueueConfigurations": [{
    "QueueArn": "arn:aws:sqs:ap-northeast-1:123456789012:cafe-sales-import",
    "Events": ["s3:ObjectCreated:*"],
    "Filter": { "Key": { "FilterRules": [{ "Name": "prefix", "Value": "sales/" }] } }
  }]
}'

為什麼中間放 SQS，而不是讓 S3 直接觸發 Lambda？佇列吸收尖峰（月底一次上傳幾百個檔案），失敗的訊息有 visibility timeout 重試、有 DLQ 接住，Lambda 也能一次拿一批處理。消費端要處理的事，依 S3 使用者指南「Event message structure」（2026-11-20 查證）：

  • key 是 URL 編碼的：文件的例子是 red flower.jpg 變成 red+flower.jpg，中文與括號會變成 %XX。解法是先把 + 換成空白，再 decodeURIComponent；順序反過來，檔名裡真正的 +（編碼成 %2B）會被解成 + 再被換成空白。
  • 測試訊息：設定通知後，S3 會送一則 {"Service":"Amazon S3","Event":"s3:TestEvent",…}，格式跟一般事件不同、沒有 Records。把它當錯誤，它就會一直重試、最後進 DLQ。
  • 至少一次、不保證順序：同一個事件可能送兩次。冪等鍵用 bucket＋key＋versionId（開了版本控制時才有；沒有時用 eTag），同一個 key 被重新上傳也能分辨。同一個 key 的先後順序看 sequencer。
  • SQS 的 body 是 S3 事件：一則 SQS 訊息的 body 是字串，解析後的 Records 陣列才是一個個物件。

Lambda 從 SQS 拿到一批訊息時，預設整批成功或整批失敗：一個檔案壞掉，同一批的其他檔案也回到佇列重做。在 event source mapping 開啟 ReportBatchItemFailures，handler 回傳 { batchItemFailures: [{ itemIdentifier: messageId }] }，只有列出的訊息回到佇列（第 6 課）。練習 4 用模擬器真的上傳檔案、從佇列拿到真實格式的事件，交給你的 handler。

💡 實務上：吞掉錯誤的匯入程式最難查
開場的 CSV 沒被匯入，真正的問題不是編碼，而是「找不到物件」的錯誤被 catch {} 吞掉、訊息被刪掉，所以 DLQ 也是空的。檢查匯入類程式時，資深工程師會看三件事：失敗會不會留在佇列（或進 DLQ）、有沒有對失敗數量告警、每天有沒有一個對帳（例如「今天 S3 上有 42 個檔案、資料庫匯入了 42 份」）。最後這個對帳，往往是唯一能抓到「事件根本沒送出來」這種靜默錯誤的方法。

Step Functions 與 EventBridge Scheduler

兩個常跟佇列一起出現的服務，這課不出題。Step Functions 用狀態機描述多步驟的流程（付款 → 扣庫存 → 通知外送），每一步可以設 Retry 與 Catch，失敗時走補償的分支（系統設計課第 13 課的 saga）。依 Step Functions 開發者指南（2026-11-20 查證），Standard 工作流程最長一年、每次執行 exactly-once，適合不能重複的步驟；Express 最長五分鐘、非同步執行是 at-least-once，適合量大、可以冪等的處理。EventBridge Scheduler 用來排定一次性或週期性（cron、rate）的呼叫，例如每天凌晨觸發對帳；比起自己開一台機器跑 cron，它不用維護主機，也能直接呼叫 SQS、Lambda、Step Functions 等目標。

三者怎麼選，一句話：工作要排隊、要重試用 SQS；同一件事要通知很多人用 SNS（或 EventBridge，事件種類多、要依內容路由、接 AWS 服務事件時）；好幾步要依序完成、失敗要補償用 Step Functions。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。用第 1 課建議的獨立練習帳號與 learn-sandbox profile。

費用：SQS、SNS 依請求次數計費，S3 依儲存量與請求次數計費；這一節的量很小，但仍以官方定價為準：SQS 定價、SNS 定價、S3 定價。這幾項沒有按小時計費的部分，做完照「清除」刪掉即可。
# 0. 這一節的指令都用同一組設定；先把帳號 ID 存起來
export AWS_PROFILE=learn-sandbox AWS_REGION=ap-northeast-1
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)

# 1. 建 DLQ 與主佇列：visibility timeout 10 秒、接收 2 次失敗就進 DLQ
aws sqs create-queue --queue-name cafe-learn-10-dlq
aws sqs create-queue --queue-name cafe-learn-10 --attributes "{\"VisibilityTimeout\":\"10\",\"RedrivePolicy\":\"{\\\"deadLetterTargetArn\\\":\\\"arn:aws:sqs:ap-northeast-1:$ACCOUNT:cafe-learn-10-dlq\\\",\\\"maxReceiveCount\\\":\\\"2\\\"}\"}"
Q=$(aws sqs get-queue-url --queue-name cafe-learn-10 --query QueueUrl --output text)

# 2. 送一則訊息，收兩次但不刪（每次間隔超過 10 秒），第三次收的時候它已經在 DLQ
aws sqs send-message --queue-url $Q --message-body '{"orderId":"o-1"}'
aws sqs receive-message --queue-url $Q --wait-time-seconds 20 --attribute-names ApproximateReceiveCount

練習

本機練習在 aws/practice/work/10/，都會連到模擬器。練習 1 要等 visibility timeout（每次約 1 秒），整題約 10 秒。

練習 1：完成 worker.ts 的 pollOnce(sqs, ddb, { queueUrl, table, waitSeconds }, handle)。送 ReceiveMessageCommand（MaxNumberOfMessages: 10、WaitTimeSeconds: waitSeconds）。每則訊息的 body 是 { orderId, email }，完成標記的 key 是 pk = receipt#<orderId>：先用 GetCommand（ConsistentRead: true）查，有標記就刪訊息、算 duplicates；沒有就呼叫 handle，失敗算 failed、不刪、繼續下一則；成功就用 PutCommand 加 ConditionExpression: 'attribute_not_exists(pk)' 寫標記（ConditionalCheckFailedException 當成已完成），再刪訊息、算 done。回傳 { done, duplicates, failed }。測試的佇列 visibility timeout 是 1 秒、maxReceiveCount 是 2，會檢查重複只處理一次、失敗的會重試、一直失敗的進 DLQ。

練習 2：寫 matchPattern(pattern, event)，照上面 EventBridge 的規則判斷事件符不符合。這題支援的寫法：

  • pattern 的每個欄位都要符合（AND）。值是物件就往下一層比對（事件裡沒有那一層、或那一層不是物件，就不符合）；值是陣列就是這個欄位的比對條件，任一個符合即可（OR）。
  • 比對條件：字串、數字、null 用 === 比；{ prefix } 只對字串；{ numeric: [運算子, 數字, 運算子?, 數字?] } 只對數字，運算子是 =、>、>=、<、<=，全部成立才算；{ exists: true/false } 看欄位在不在；{ 'anything-but': 值或值的陣列 } 是字串或數字、而且不在清單裡。
  • 事件裡沒有這個欄位時，只有 { exists: false } 會符合。事件裡的值是陣列時，任一個元素符合任一個條件就算符合。

練習 3：完成 fanout.ts 的 setupFanout(sns, sqs, name)：建 topic name、兩個佇列 <name>-kitchen 與 <name>-receipts。每個佇列的 queue policy 只有一條 Statement：Principal: { Service: 'sns.amazonaws.com' }、Action: 'sqs:SendMessage'、Resource 是佇列 ARN、Condition: { ArnEquals: { 'aws:SourceArn': topic ARN } }（用 SetQueueAttributesCommand 設 Policy）。兩個訂閱都設 RawMessageDelivery: 'true'；廚房另外設 FilterPolicy 為 {"type":["drink"]} 與 FilterPolicyScope: 'MessageBody'（訂閱屬性的值都是字串）。回傳 { topicArn, kitchenUrl, receiptsUrl }。測試會發布一杯拿鐵、一個可頌，看兩個佇列各收到什麼，並再執行一次確認不會多出訂閱。

練習 4：完成 ingest.ts 的 makeHandler(deps)，回傳 SQS 觸發的 Lambda handler。每則 SQS 訊息：body 解析成 JSON，Event 是 's3:TestEvent' 就略過；否則對 Records 裡每個物件，bucket 是 s3.bucket.name，key 先把 + 換成空白再 decodeURIComponent；冪等的 id 是 `${bucket}/${key}#${versionId ?? eTag}`，deps.isDone(id) 是 true 就跳過，否則 deps.importCsv(bucket, key)，成功後 deps.markDone(id)。一則訊息出任何錯（JSON 壞掉、匯入失敗），把它的 messageId 放進回傳的 batchItemFailures，繼續處理下一則。測試會在模擬器真的上傳 sales/門市 A/2026-11-20 (1).csv 與 sales/a+b.csv，把佇列收到的訊息交給你的 handler。

練習 5：寄收據的 worker 平均 20 秒處理一則，尖峰時 45 秒；佇列的 visibility timeout 是預設的 30 秒。最可能看到什麼？

✓ d。visibility timeout 只是「別人暫時看不到」，到期沒刪，訊息就重新出現；第一個 worker 並不知道，仍然繼續做完。修法是把 timeout 設得比最長處理時間長，或處理期間用 ChangeMessageVisibility 延長，並讓消費者冪等。c 錯在 SQS 不會中斷你的程式；b 要等接收次數超過 maxReceiveCount 才會發生。

練習 6：同事說：「我們改用 FIFO 佇列，它有 exactly-once processing，所以點數的 worker 不用再做冪等了。」你怎麼回？

✓ b。FIFO 的去重發生在「送進佇列」這一端（5 分鐘的去重間隔內同一個 deduplication ID 只收一次），管不到「消費者處理完、刪除前當機」的情況。所以加點數要用訂單 ID 當冪等鍵，或寫成有唯一約束的紀錄。c 只是去重 ID 的產生方式；d 錯在 FIFO 確實保證同一個 message group 內的順序。

練習 7：門市的銷售 CSV 上傳到 S3 後要匯入資料庫。月底結算時幾百家門市同時上傳，匯入的 Lambda 偶爾因為資料庫忙而失敗。S3 直接觸發 Lambda，和中間放一個 SQS，差在哪？

✓ a。佇列把「事件發生」和「處理」拆開：處理端慢或暫時失敗，事件留在佇列裡，不會打爆資料庫，也不會丟掉。b 錯在非同步呼叫的重試有次數上限，用完就丟（要另外設 destination 或 DLQ）。c 錯在 SQS 標準佇列仍是至少一次，S3 事件本身也可能重複。

常見錯誤

  • 收到就刪訊息：處理失敗時訊息已經沒了，DLQ 也是空的。處理成功才刪。
  • visibility timeout 比處理時間短：同一則訊息被兩個 worker 同時處理。設長一點，或處理中用 ChangeMessageVisibility 延長。
  • 用 SQS 的 MessageId 當冪等鍵：生產者重送時是新的 MessageId。用業務上的 ID（訂單 ID、物件版本）。
  • 先寫完成標記再處理：處理失敗的訊息重試時被當成重複跳過。成功之後才寫。
  • 以為 FIFO 讓消費者不用冪等：FIFO 去重的是送進佇列的訊息，不是你的處理。
  • DLQ 沒有告警：失敗的訊息靜靜地堆著。對 DLQ 的訊息數與主佇列最老訊息的年齡告警。
  • SNS 訂閱沒有 RawMessageDelivery：消費者收到 SNS 的信封，要多解一層。
  • filter policy 比對 body 卻沒設 FilterPolicyScope：預設比對 message attributes，結果什麼都收不到，而且不會報錯。
  • queue policy 沒限定 aws:SourceArn：任何 topic 或 bucket 都能把訊息送進你的佇列。
  • event pattern 寫錯：大小寫、數字寫成字串、放錯層都不會報錯，只會永遠不觸發。用 test-event-pattern 拿真的事件測。
  • S3 事件的 key 沒有解碼，或先 decode 再換 +：有空白、中文、+ 的檔名找不到。先把 + 換成空白，再 decodeURIComponent。
  • 把 s3:TestEvent 當錯誤：它會一直重試、最後進 DLQ。認出來，略過。
  • 一筆失敗就讓整批失敗：成功的也要重做。用 batchItemFailures 只回報失敗的那幾則。

小結

  • SQS 是佇列（一則訊息一個消費者、消費者自己拉）、SNS 是發布／訂閱（推給每個訂閱者）、EventBridge 是依 event pattern 路由的事件匯流排。常見組合是 SNS 或 EventBridge 分送、每個消費者前面各放一個 SQS。
  • visibility timeout 是租約：預設 30 秒，要比處理時間長，處理中可以延長；Lambda 讀 SQS 時建議至少是函式 timeout 的 6 倍。用 long polling（WaitTimeSeconds 最多 20 秒）。
  • 處理成功才刪訊息；一直失敗的由 RedrivePolicy 的 maxReceiveCount 移到 DLQ，DLQ 一定要告警。
  • 至少一次代表重複一定會發生，FIFO 也一樣。冪等鍵用業務 ID；處理前查 DynamoDB 的完成標記，成功後用 attribute_not_exists 條件寫入，再刪訊息。副作用本身也盡量冪等。
  • SNS fan-out：queue policy 允許 sns.amazonaws.com 並限定 aws:SourceArn；RawMessageDelivery 拿到原本的訊息；filter policy 預設比 message attributes，比 body 要設 FilterPolicyScope: MessageBody。
  • EventBridge 的 pattern：欄位之間 AND、陣列裡 OR、事件陣列任一元素符合即可；prefix 只對字串、numeric 只對數字、exists: false 比對欄位不存在。寫錯不會報錯，上線前用 test-event-pattern 測。
  • S3 事件：key 是 URL 編碼（先換 + 再 decode）、設定時會先送 s3:TestEvent、至少一次而且不保證順序（冪等鍵用 bucket＋key＋versionId）。中間放 SQS 吸收尖峰與重試，Lambda 用 batchItemFailures 只回報失敗的訊息。
  • 多步驟、要補償的流程用 Step Functions（Standard 最長一年、exactly-once；Express 最長五分鐘）；排程用 EventBridge Scheduler。
