階段 1：帳號與身分 · 第 1 課

雲端與 AWS 全貌：region、責任分工、三種操作方式與帳單

咖啡店決定把點餐系統搬上 AWS。第一週就出了事：工程師想在測試環境清掉一個舊的 bucket，終端機裡還留著前一天 export AWS_PROFILE=prod 設下的環境變數，指令送到了正式環境的帳號；另一位同事在東京 region 找不到前一天建的機器，以為被刪了，其實他建在新加坡。兩件事的原因一樣：不知道自己的請求送到了哪個帳號、哪個 region。

AWS（Amazon Web Services）是 Amazon 的雲端平台：你用 API 向它租用運算、儲存、資料庫、網路，按用量付費，不用自己買機器。這一課先建立整張地圖：一個 AWS 請求由哪些部分組成、region 與可用區是什麼、怎麼讀資源的全名（ARN）、程式的憑證從哪裡來、哪些事是 AWS 負責哪些是你負責、帳單怎麼算。最後在你的 Mac 上啟動這門課的 AWS 模擬器，用 AWS CLI 和 SDK 做第一次呼叫。

這課的路線：

  • 一個請求的組成：主控台、CLI、SDK 其實都在呼叫同一組 API，送到哪裡由 endpoint、region、憑證決定。
  • region 與可用區：資源放在哪裡、為什麼兩個帳號的「1a」可能不是同一個機房。
  • ARN 與憑證鏈：讀懂資源的全名；SDK 依什麼順序找憑證，AWS_PROFILE 為什麼會讓你打錯帳號。
  • 責任分工、服務地圖與帳單：哪些事要自己做、這門課會用到哪些服務、錢花在哪裡。
  • 練習環境：本機的 AWS 模擬器 Moto，以及它跟真的 AWS 不一樣的地方。
這課會用到：Docker 容器與映像（devops 課第 7 課：映像是打包好的程式與環境，容器是把它跑起來的程序），這課用一個容器跑 AWS 模擬器；終端機與環境變數（devops 課第 2 課：export X=… 只影響目前這個終端機視窗）。
練習環境：本機題連到你電腦上的 AWS 模擬器（Moto），不需要 AWS 帳號、不花錢。模擬器預設不檢查權限、部分檢查比 AWS 寬鬆，測試通過不代表在真的 AWS 一定成功；遇到差異的地方課文會標出來。

一個 AWS 請求由什麼組成

操作 AWS 有三種方式：網頁的主控台（AWS Management Console）、終端機的 AWS CLI、程式裡的 SDK（這門課用 AWS SDK for JavaScript v3）。三種方式最後做的事完全一樣：送一個 HTTPS 請求給 AWS 的 API。主控台的按鈕背後是 API 呼叫，CLI 的每個子指令對應一個 API 動作（action），SDK 的每個 Command 也是。所以「主控台點得到、CLI 卻失敗」的時候，要比的是這兩邊送出的請求哪裡不同。

每個請求都由四個部分決定：

部分是什麼CLI 從哪裡讀
服務與動作要哪個服務做什麼，例如 S3 的 CreateBucket子指令：aws s3api create-bucket
region送到哪個地區的機房，決定 endpoint，例如 s3.ap-northeast-1.amazonaws.com--region 參數 → AWS_REGION 環境變數 → 設定檔
憑證（credentials）你是誰：一組 access key ID 與 secret access key，臨時憑證再加一個 session token環境變數、~/.aws/credentials、SSO 登入的快取……（後面「憑證從哪裡來」細講）
簽章（signature）用 secret key 對請求內容算出的雜湊，證明請求真的是你送的、內容沒被改過。secret key 本身不會送出去CLI／SDK 自動算，這個演算法叫 Signature Version 4（SigV4）

帳號（AWS account）是 AWS 裡的帳單與資源邊界：每個帳號有一個 12 位數的帳號 ID，資源都建在某個帳號裡，帳單也以帳號為單位。你送的憑證屬於哪個帳號，請求就作用在哪個帳號。請求本身不會寫「我要對正式環境做這件事」，AWS 只看憑證。

所以開場那兩件事的最小解法是：動手之前，先問 AWS「我現在是誰、在哪裡」。CLI 有一個不需要任何權限、永遠可以呼叫的指令：

aws sts get-caller-identity          # 這組憑證屬於哪個帳號、哪個身分
aws configure get region             # CLI 預設送到哪個 region（AWS_REGION 環境變數會蓋過它）

sts get-caller-identity 回傳三個欄位：Account（帳號 ID）、Arn（你的身分的全名，下一節讀它）、UserId。STS（Security Token Service）是發臨時憑證的服務，第 2 課細講。寫會刪東西、改東西的腳本時，開頭先比對帳號 ID，不對就停下來：練習 1 就是寫這個。

💡 實務上：腳本開頭先確認帳號
公司裡一個人常同時有開發、測試、正式三個帳號的權限，終端機的環境變數、上一次登入的 profile 都會留著。資深工程師寫維運腳本時，開頭會用 sts get-caller-identity 比對預期的帳號 ID，再印出帳號與 region 讓人確認；CI 的部署腳本也一樣。這比「小心一點」可靠，因為它不靠人記得。

region 與可用區：資源放在哪裡

上一節說 region 決定請求送到哪裡。region（地區）是 AWS 在某個地理位置的一群機房，例如東京 ap-northeast-1、台北 ap-east-2、美國維吉尼亞北部 us-east-1。每個 region 各自獨立：在東京建的機器，切到新加坡的主控台就看不到，這就是開場第二件事。

每個 region 裡有好幾個可用區（Availability Zone，簡稱 AZ）：彼此距離夠遠、各自有獨立電力與網路的一個或多個機房，名稱是 region 加一個字母，例如 ap-northeast-1a。AZ 是故障的單位：一個 AZ 停電，同一個 region 的其他 AZ 照常運作。所以要高可用的服務，至少放在兩個 AZ（第 4、8、12 課會一層一層做到）。

有一個容易踩的細節：AZ 名稱在不同帳號可能對應到不同的實體位置。你的 ap-northeast-1a 和另一個帳號的 ap-northeast-1a 不保證是同一個機房。要跨帳號對齊，看 AZ ID（例如 apne1-az4），它在所有帳號都指同一個實體位置。aws ec2 describe-availability-zones 會同時列出兩者。按執行，看兩個帳號的「1a」是不是同一個地方：

服務也分兩種範圍。大多數服務是區域服務（regional）：EC2、RDS、Lambda、SQS 的資源屬於某個 region。少數是全球服務（global）：IAM（帳號的使用者與權限）、Route 53（DNS）、CloudFront（CDN）不分 region。S3 介於中間：資料存在你選的 region，但 bucket 名稱預設在所有帳號之間共用，別人用過的名稱你就不能用（練習 4 會遇到）。

選 region 時考慮四件事：離使用者近不近（延遲）、法規要求資料放在哪裡、需要的服務在那個 region 有沒有提供、價格（同一個服務在不同 region 價格不同）。台灣的團隊常用東京或台北；新服務、新功能通常最早出現在 us-east-1。這門課的練習統一用 ap-northeast-1。

ARN：每個資源的全名

知道請求送到哪個帳號、哪個 region 之後，還要能指出「哪一個資源」。AWS 裡每個資源都有一個全名叫 ARN（Amazon Resource Name），權限設定（第 2 課）、事件來源、錯誤訊息裡到處都是它。格式是用冒號分成六段：

arn:partition:service:region:account-id:resource
arn:aws:sqs:ap-northeast-1:123456789012:receipts                 SQS 佇列 receipts
arn:aws:iam::123456789012:role/cafe-api                         IAM role（全球服務，region 是空的）
arn:aws:lambda:ap-northeast-1:123456789012:function:receipt:prod  Lambda 函式 receipt 的 prod 版本
arn:aws:s3:::cafe-menu/latte.jpg                                S3 物件（region 和帳號都是空的）
  • partition：AWS 的分區，一般是 aws；中國是 aws-cn、美國政府區是 aws-us-gov。
  • service：服務的代號（s3、iam、lambda）。
  • region、account-id：全球服務沒有 region；S3 的 ARN 連帳號都沒有，因為 bucket 名稱本身就是唯一的。
  • resource：第五個冒號之後的全部。通常是「類型 + 分隔符號 + 名稱」，分隔符號依服務是 / 或 :；名稱本身也可能含 / 或 :（IAM 的路徑 role/service-role/x、Lambda 的版本 receipt:prod）。

最後一點是解析 ARN 時最常出錯的地方：用 split(':') 再取第 6 個元素，會把 function:receipt:prod 截成 function。練習 2 會寫一個正確的解析函式。

憑證從哪裡來：SDK 的憑證鏈

ARN 說的是「哪個資源」，憑證說的是「你是誰」。開場的事故就出在這裡：程式沒有明確給憑證時，CLI 和 SDK 會依一個固定順序去找，找到第一個就用，這個順序叫憑證鏈（credential provider chain）。你不知道它找到的是哪一個，就不知道請求作用在哪個帳號。

先認識幾個憑證來源：

  • 環境變數：AWS_ACCESS_KEY_ID、AWS_SECRET_ACCESS_KEY（臨時憑證再加 AWS_SESSION_TOKEN）。
  • profile：設定檔 ~/.aws/config 與 ~/.aws/credentials 裡的一個具名區段，例如 [profile prod]。區段裡可以是金鑰、SSO 登入設定（第 2 課）或「用另一組憑證去 assume 某個 role」（第 2 課）。沒有指定時用 default。指定的方式是程式裡的 profile 選項、CLI 的 --profile，或環境變數 AWS_PROFILE。
  • web identity：AWS_WEB_IDENTITY_TOKEN_FILE 加 AWS_ROLE_ARN，用一個外部發的 token 換臨時憑證（GitHub Actions 的 OIDC、EKS 的 Pod 會用）。
  • container：跑在 ECS 的容器裡時，環境變數 AWS_CONTAINER_CREDENTIALS_RELATIVE_URI（或 …_FULL_URI）指向一個本機端點，從那裡拿 task role 的臨時憑證（第 5 課）。
  • instance metadata：跑在 EC2 上時，從機器內部的 metadata 服務拿 instance profile 的臨時憑證（第 5 課）。AWS_EC2_METADATA_DISABLED=true 會關掉這一項。

AWS SDK for JavaScript v3 在 Node.js 的預設順序（這門課鎖的版本 3.1161.0，裡面的 @aws-sdk/credential-provider-node 是 3.972.97，以下照它的原始碼）：

  1. 環境變數：兩個變數都有才算。但只要有指定 profile（程式的 profile 選項或 AWS_PROFILE），這一步整個跳過，SDK 會印出警告並改用 profile。
  2. profile：指定的 profile，沒指定就用 default；設定檔裡沒有這個 profile，或它沒有任何憑證設定，就往下找。
  3. web identity：兩個環境變數都有才算。
  4. container：有 container 的環境變數就用它，不再看 instance metadata。
  5. instance metadata：沒被 AWS_EC2_METADATA_DISABLED 關掉、而且真的跑在 EC2 上才拿得到。

第 1 步的例外就是開場事故的另一種版本：CI 給了環境變數金鑰（測試帳號），但同一台機器的環境裡還有 AWS_PROFILE=prod，SDK 會用 prod。AWS CLI 也有自己的順序，規則寫在 CLI 文件的「Configuration and credential file settings」，兩者不保證完全相同；這課的練習 3 只照 SDK 的規則。最可靠的做法還是：一個環境只放一種憑證來源，程式啟動時印出 sts get-caller-identity 的帳號。

用 SDK 呼叫 API 的寫法都一樣：建立某個服務的 client，再 send 一個 Command：

import { STSClient, GetCallerIdentityCommand } from '@aws-sdk/client-sts'

const sts = new STSClient({ region: 'ap-northeast-1' })          // 沒給 credentials：走憑證鏈
const me = await sts.send(new GetCallerIdentityCommand({}))
console.log(me.Account, me.Arn)
💡 實務上：正式環境的程式不放金鑰
跑在 AWS 上的程式（EC2、ECS、Lambda）一律用 role 的臨時憑證，由憑證鏈的後幾步自動取得，程式碼和環境變數裡都不出現金鑰；開發者的電腦用 SSO 登入（第 2 課）。看到 .env 裡有 AWS_SECRET_ACCESS_KEY，資深工程師的第一個問題是「這把金鑰屬於誰、能做什麼、多久沒換了」。

責任分工與這門課的服務地圖

知道請求怎麼送、送給誰之後，下一個問題是：資源放上 AWS 以後，哪些事 AWS 會幫你做？AWS 用共同責任模型（Shared Responsibility Model）回答：AWS 負責「雲端本身的安全」，也就是機房、硬體、網路、虛擬化層，以及代管服務的底層軟體；你負責「放進雲端的東西的安全」，也就是你的資料、權限設定、網路規則、作業系統與程式。

分界線隨服務移動：越是代管的服務，你要管的越少。

你要負責的事EC2（虛擬機）ECS Fargate（容器）Lambda（函式）
作業系統修補你AWSAWS
容器映像裡的套件你你—
程式與它的 npm 套件你你你
權限（IAM）、網路規則、資料加密的設定你你你

最後一列永遠是你的：AWS 不會替你決定 bucket 要不要公開、資料庫要不要開給網際網路。很多雲端資安事故都是設定錯誤，而不是 AWS 被攻破。

帳單怎麼算

責任分清楚之後，最後一塊是錢。AWS 沒有月租的「方案」，每個服務各自計費，帳單是全部加起來。計費方式大致三種：

  • 按時間：資源存在就計費，不管有沒有在用。EC2 執行個體、RDS 資料庫、NAT gateway、負載平衡器、公開 IPv4 位址都是。忘了關的測試機器是新手帳單爆掉的頭號原因。
  • 按用量：用多少付多少。S3 依存放量與請求次數、Lambda 依呼叫次數與執行時間、DynamoDB on-demand 依讀寫次數。
  • 資料傳輸：從 AWS 傳出到網際網路要錢，跨 AZ、跨 region 的流量也要錢；傳進 AWS 大多不收費。

價格依 region 不同，也會調整，所以這門課不背金額：需要估算時查各服務的官方定價頁，或用 AWS Pricing Calculator。新帳號的免費方案內容也改過好幾次，以官方的 Free Tier 頁面為準。

開帳號的第一件事是設預算警示（AWS Budgets）：花費或預測花費超過門檻時寄信通知你。依官方定價頁（2026-11 查證），只做監看與通知的預算不收費。要注意預算只會通知，不會自動停掉任何資源，收到信之後還是要你自己去處理。第 2 課會把帳號的第一天完整做一次，期末專題（第 11 課）部署作品時再談 Cost Explorer 與成本分攤標籤。

💡 實務上：先看帳單明細，再猜原因
帳單比預期高時，不要先猜「是不是流量變大」：到 Billing 的帳單明細或 Cost Explorer 依服務、依用量類型展開，常見的元兇是按時間計費、沒人在用的資源（測試完沒刪的 NAT gateway、資料庫、未掛載的磁碟），以及沒設保存天數的 log。devops 課第 18 課有一份成本估算的練習，可以當延伸。

這門課的練習環境：AWS 模擬器

前面講的請求、region、帳號、憑證，接下來要親手操作。真的 AWS 要帳號、會花錢、打錯指令會出事，所以這門課的本機練習連到一個跑在你電腦上的 AWS 模擬器：Moto（開源的 AWS 模擬服務，這門課用 5.2.5 版的 Docker 映像）。它接受跟 AWS 一樣格式的 API 請求，CLI 和 SDK 只要把 endpoint 指向它就能用。

第一次使用，在 learn 資料夾執行：

aws --version                                                  # 要是 aws-cli/2.x；沒有的話 brew install awscli
npm --prefix aws/practice ci                                   # 安裝 AWS SDK for JavaScript v3（版本鎖在 3.1161.0）
docker compose -f aws/practice/compose.yaml up -d --wait       # 啟動模擬器，容器名稱 learn-aws-moto

第一次要下載映像，約一分鐘。模擬器只聽 127.0.0.1:4580，佔用記憶體約一兩百 MB。不讀書時用 docker compose -f aws/practice/compose.yaml stop 停掉；down 會刪掉容器，模擬器裡的資料也一起清空（它只存在記憶體裡）。

測試怎麼保證不會碰到你真的 AWS：測試的共用程式 aws/practice/helpers/aws.ts 一開始就清掉所有 AWS_ 開頭的環境變數，換成假的金鑰和模擬器的位址；執行你的 shell 腳本時，HOME 換成一個空的暫存資料夾，CLI 讀不到你的 ~/.aws。就算某個指令漏了 endpoint，假金鑰也不可能通過真的 AWS 的驗證。

想自己在終端機對模擬器下 CLI 指令，開一個新的終端機視窗，在 learn 資料夾執行：

source aws/practice/env.sh                  # 清掉這個視窗的 AWS_ 環境變數，改成假金鑰＋模擬器
aws sts get-caller-identity                 # Account 是 123456789012：模擬器的預設帳號
aws ec2 describe-availability-zones --query 'AvailabilityZones[].[ZoneName,ZoneId]' --output text

env.sh 只影響那一個視窗，關掉就恢復；要對真的 AWS 下指令時，用另一個沒有 source 過它的視窗，不要混用。

測試也會替每個題目資料夾準備一個獨立的模擬帳號（12 位數的帳號 ID 從資料夾名稱算出來），所以你在 work/01 建的東西不會跟出題檢查或別的練習互相影響。練習 1 的「預期帳號」就是要從 sts get-caller-identity 查到的這個帳號。

模擬器跟真的 AWS 有幾個重要差異，課文遇到時都會再提：

項目模擬器真的 AWS
權限預設不檢查，任何憑證都能做任何事每個請求都依 policy 判斷允許或拒絕（第 2 課）
參數檢查部分比較寬鬆，例如在東京建 bucket 不帶 LocationConstraint 也會成功會拒絕（練習 4）
執行EC2、ECS、RDS 只記錄設定，不會真的開機器或跑資料庫真的執行、真的計費

所以這門課的測試除了看「模擬器有沒有成功」，也會檢查你送出的內容是不是真的 AWS 要的。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。之後每一課都有這一節，讓你在真的 AWS 上把重點做一遍。開始之前：另外開一個自己的練習帳號，不要用公司的帳號，公司帳號可能有正式環境的資料，帳單也不是你的。

費用：這一節的步驟不建立任何會計費的資源。開帳號需要綁信用卡；只做監看與通知的 Budgets 預算不收費（AWS Budgets 定價頁，2026-11 查證）。之後各課的這一節會在開頭寫出那一課的計費項目。

第 1 課只做兩件事，都在主控台完成（這時帳號只有 root 使用者，還沒有適合給 CLI 用的身分，第 2 課會建立）：

  1. 到 AWS 官網註冊新帳號，用的 email 最好是只給這個帳號用的。註冊完的登入身分叫 root 使用者，它能做任何事、權限無法被限制。
  2. 用 root 登入後，先替 root 開啟 MFA（多因素驗證：登入時除了密碼，還要手機驗證器 App 的一次性代碼。認證課有講 MFA 的原理）。
  3. 到 Billing and Cost Management 的 Budgets 建一個每月成本預算，金額設一個你能接受的小數字，通知門檻設「實際花費 80%」與「預測花費 100%」，收件人填你的 email。

主控台的畫面會改版，找不到時用主控台上方的搜尋列搜「Budgets」。第 2 課設好 CLI 之後，可以用下面這一行確認預算還在（learn-sandbox 是第 2 課會建立的 profile 名稱，<帳號ID> 換成你的 12 位數帳號）：

aws budgets describe-budgets --account-id <帳號ID> --profile learn-sandbox --query 'Budgets[].BudgetName'

清除

預算建議一直留著。真的要刪：

aws budgets delete-budget --account-id <帳號ID> --budget-name <預算名稱> --profile learn-sandbox
aws budgets describe-budgets --account-id <帳號ID> --profile learn-sandbox --query 'Budgets[].BudgetName'   # 確認：清單裡沒有它

練習

本機練習的流程：在 learn 資料夾執行頁面上的指令，第一次會把起始檔複製到 aws/practice/work/01/，你改那裡的檔案、存檔、再執行一次，切回這一頁就看得到結果。測試會先確認模擬器在跑，沒有的話會告訴你要執行哪個指令。

練習 1：完成 whoami.sh，用法是 bash whoami.sh <預期的帳號 ID>。先用 aws sts get-caller-identity 查出目前憑證的帳號 ID（用 --query Account --output text 只取帳號）。跟參數不同時，把錯誤訊息印到 stderr（echo "…" >&2）並 exit 1，之後不能再呼叫任何 aws 指令。相同時，第 1 行印出帳號 ID，接著用 aws ec2 describe-availability-zones 每個可用區印一行「名稱 AZ-ID」，例如 ap-northeast-1a apne1-az4（--query 'AvailabilityZones[].[ZoneName,ZoneId]' --output text 會用 tab 分隔，再用 tr '\t' ' ' 換成空白）。不要寫 --region：測試會用 AWS_REGION 換成 us-east-1 再跑一次，可用區要跟著換。測試也會記錄你的腳本呼叫了哪些 aws 指令，只能讀、不能建立或修改任何東西。想先手動試：在設好 env.sh 的視窗執行 bash aws/practice/work/01/whoami.sh 123456789012（模擬器的預設帳號），再換一個帳號號碼看它停下來。

練習 2：寫 parseArn(arn)，把 ARN 拆成 { partition, service, region, account, resourceType, resourceId }，不是合法的 ARN 就回傳 null。規則：

  • 要以 arn: 開頭，而且至少有 6 段（5 個冒號）；partition、service 不能是空的，否則回傳 null。region、account 可以是空字串。
  • resource 是第 5 個冒號之後的全部（可能還有冒號和 /）。
  • 一般服務：resource 在第一個 / 或 :（哪個先出現就用哪個）切開，前面是 resourceType、後面全部是 resourceId；兩個都沒有時 resourceType 是空字串、resourceId 是整段。
  • S3（service 是 s3）不切：含 / 時 resourceType 是 'object'，不含是 'bucket'，resourceId 都是整段 resource。

練習 3：照上面「憑證從哪裡來」的 SDK 順序，寫 credentialSource(input)，回傳 SDK 最後會用哪一個來源：'env'、'profile:<名稱>'、'web-identity'、'container'、'instance'，或都找不到時 'none'。input.env 是環境變數；input.profileOption 是程式裡給 client 的 profile 選項（可能沒有）；input.profiles 是設定檔裡有哪些 profile，值是 true 代表有憑證設定、false 代表區段存在但沒有憑證設定；input.onEc2 表示程式是不是跑在 EC2 上。環境變數的值是空字串時當成沒設。

練習 4：完成 menu-bucket.ts 的 ensureMenuBucket(s3, sts)：替目前的帳號與 region 建一個放菜單圖片的 bucket，重複執行也安全。用 sts 送 GetCallerIdentityCommand 取得帳號 ID，用 await s3.config.region() 取得 client 設定的 region；名稱是 cafe-menu-<帳號>-<region>。用 CreateBucketCommand 建立：us-east-1 以外的 region 要帶 CreateBucketConfiguration: { LocationConstraint: region }，us-east-1 不能帶。建立成功回傳 { name, created: true }；錯誤的 name 是 'BucketAlreadyOwnedByYou'（已經是你的）時回傳 { name, created: false }；其他錯誤（例如 'BucketAlreadyExists'：名稱被別的帳號用走了）照樣丟出去。測試會記下你送出的 CreateBucket 參數，因為模擬器在東京不帶 LocationConstraint 也會成功，真的 AWS 不會。

練習 5：咖啡店的帳號和金流商的帳號各有一個子網路，都在 ap-northeast-1a。同事說：「同一個 AZ，兩邊互連不會有跨 AZ 的延遲和流量費。」你怎麼回？

✓ AZ 名稱可能依帳號對應到不同的實體機房，跨帳號對齊要用 AZ ID（例如 apne1-az4），describe-availability-zones 會列出來。a 是最常見的誤解；b 錯在不同帳號也可以在同一個實體 AZ；d 的 region 已經都是 ap-northeast-1，問題不在這裡。

練習 6：咖啡店的收據服務跑在 Lambda 上。安全公告說它用的一個 npm 套件有漏洞，Lambda 的 Node.js runtime 本身也有一個修補。哪些是你的責任？

✓ 共同責任模型：越代管，AWS 管得越多，但你放進去的程式與它的套件永遠是你的。a 忽略了程式碼這一層；d 錯在執行環境新不新，跟你打包進去的套件有沒有漏洞無關。

練習 7：你在本機模擬器上測試上傳收據的程式：程式用的 role 沒有任何 S3 權限，上傳卻成功了，測試全部通過。這代表什麼？

✓ 這門課用的模擬器預設不做權限評估，任何憑證都能做任何事。在真的 AWS 上這個請求會回 AccessDenied。c 是最危險的結論：把模擬器的行為當成 AWS 的行為。第 2 課會用頁面裡的練習判斷 policy 允不允許。

常見錯誤

  • 不看帳號就下指令：環境變數、上次登入的 profile 都會留著。先 aws sts get-caller-identity，腳本開頭比對帳號 ID，不對就停。
  • 以為 AWS_PROFILE 和金鑰環境變數可以同時設：SDK v3 遇到這種情況會用 profile、跳過金鑰（只印一行警告）。一個環境只放一種憑證來源。
  • 找不到昨天建的資源：多半是 region 不同。主控台右上角、CLI 的 aws configure get region 與 AWS_REGION 都看一下。
  • 用 AZ 名稱跨帳號對齊：名稱可能對應不同的實體位置，用 AZ ID。
  • 用 split(':')[5] 取 ARN 的資源：resource 裡可能還有冒號（Lambda 版本、log group）。取第 5 個冒號之後的全部。
  • 以為設了預算就不會超支：Budgets 只通知，不會停掉資源。收到警示要自己處理，測試完的資源要刪。
  • 把模擬器的成功當成 AWS 的成功：模擬器不檢查權限、部分參數比較寬鬆，也不會真的跑 EC2 或資料庫。

小結

  • 主控台、CLI、SDK 都在呼叫同一組 API。每個請求由服務與動作、region、憑證、SigV4 簽章組成；請求作用在憑證所屬的帳號。
  • region 是一群機房，資源各自屬於某個 region；AZ 是 region 裡獨立供電與網路的故障單位，高可用至少兩個 AZ。跨帳號對齊 AZ 用 AZ ID。IAM、Route 53、CloudFront 是全球服務；S3 bucket 名稱跨帳號共用。
  • ARN 是 arn:partition:service:region:account-id:resource；resource 是第 5 個冒號之後的全部，S3 沒有 region 和帳號。
  • SDK v3 的憑證鏈：環境變數（有指定 profile 就跳過）→ profile → web identity → container → instance metadata。一個環境只放一種來源，動手前先 sts get-caller-identity。
  • 共同責任：AWS 管雲端本身，你管放進去的資料、權限、網路規則與程式；越代管的服務你管得越少，但設定永遠是你的。
  • 計費分按時間、按用量、資料傳輸；開帳號先設 Budgets，它只通知、不停機。
  • 練習用本機的 Moto 模擬器：不花錢、每個題目資料夾一個模擬帳號；它不檢查權限、部分參數較寬鬆，測試會另外檢查你送出的內容。
