階段 5：事件與上線 · 第 11 課

期末專題：把作品部署上 AWS

你在作品專案課做出了一個多租戶 SaaS 後台 my-saas：NestJS＋Prisma＋PostgreSQL（RLS）＋Redis（限流與 BullMQ 匯出佇列），用 docker compose --profile app up 就能在本機跑起來。作品專案課第 17 課留了一句話：部署到哪裡是你的選擇，想上 AWS 的話，就是這一課。

這一課把整門課組起來：先把 compose 裡的每個服務對應到 AWS 的服務，依需求做取捨並寫下理由；再用一支可以重複執行的部署程式，在模擬器裡建出 ECR、RDS、S3、Secrets Manager、ALB、ECS 與 CloudWatch 告警；接著處理「上線第一晚」埋好的四個事故並寫事後檢討；最後談成本，以及在真的帳號上部署一次的步驟與清除順序。

這課的路線：

  • 從 compose 到 AWS：每個服務換成什麼、程式要改哪幾個地方。
  • 架構與取捨：依需求選每一層（練習 1）。
  • 部署的順序與冪等：一支可以重複執行的部署程式（練習 2）。
  • 上線第一晚的四個事故與事後檢討（練習 3）。
  • 看得到、算得出：CloudWatch 告警、成本分攤標籤與每小時計費的資源。
這課會用到：作品的部署方式（作品專案課第 17 課：映像用 commit SHA 標記、migration 用 build 階段的映像獨立執行、只有 migration 拿得到擁有者帳號，api 用 pf_app）；execution role 與 task role（第 5 課）；ECS 注入 secret（第 9 課：secrets 的 valueFrom，由 execution role 在啟動時讀）；OpenTofu（devops 課第 20 課：宣告式描述基礎設施，plan 之後再 apply）。
練習環境：模擬器會記下 RDS、ECS、ALB 的設定，但不會真的開資料庫、跑容器或接流量；它也不檢查 IAM 權限。所以練習 3 的事故，測試檢查的是 policy 文件與 task definition 本身；「真的跑得起來」交給選做的真實帳號部署與課末的自評清單。

先回答開場的問題：本機的每一樣東西，在 AWS 上由誰負責。左邊是參考實作 nestjs/practice/portfolio-ref/saas 的 compose.yaml 與 .env.example：

程式本身大部分不用改，因為設定都從環境變數來（devops 課第 11 課的「同一個映像，不同的設定」）。要改的是這幾個地方：

  • 檔案改存 S3：StorageService 的 put／get／delete 換成 PutObjectCommand、GetObjectCommand、DeleteObjectCommand，key 照舊是 tenants/<tenantId>/files/<隨機 id>；env.ts 的 STORAGE_DIR 換成 S3_BUCKET。程式用 task role 的憑證（第 1 課的憑證鏈 container 那一步），不需要任何金鑰。這是一個新的決定，寫一份 ADR「0007 正式環境的檔案存 S3」。
  • pf_app 的密碼：參考實作的 migration 用 CREATE ROLE pf_app LOGIN PASSWORD 'pf_app' 建角色，密碼寫死在 git 裡。正式環境在第一次 migration 之後，要用擁有者執行一次 ALTER ROLE pf_app PASSWORD …，換成 Secrets Manager 裡 APP_DATABASE_URL 的那個密碼（例如寫一支只在部署時執行的小程式，兩個連線字串都由 secret 注入）。
  • 信任 ALB 這一層代理：參考實作的 app.setup.ts 設了 trust proxy: 'loopback'，只信任本機的代理。放到 ALB 後面，req.ip 會變成 ALB 節點的私有 IP，log 裡就看不到客戶端的 IP。因為 app-sg 只允許 alb-sg 進來，可以改成只信任最近一跳（1）。
💡 實務上：先列「要改的程式」，再開始建資源
資深工程師接到「把這個服務搬上雲」時，第一份產出通常不是架構圖，而是這張對照表加上「程式要改的地方」清單：檔案存哪、密碼從哪來、代理信任幾層、健康檢查打哪裡。每一項都是一個小 PR，可以在本機先做完、測完（例如 S3 的部分用這門課的模擬器測）。等到真的部署時，剩下的只是設定，出事時也比較好判斷是程式還是設定的問題。

架構與取捨：依需求選每一層

對照表說的是「可以換成什麼」，但每一層都有好幾種選法。決定之前先把需求寫清楚。my-saas 正式環境的需求：

  • 可用性：一個 AZ 故障時，15 分鐘內恢復服務（RTO，recovery time objective，可以容忍的停機時間）。
  • 資料：最多遺失 5 分鐘的資料（RPO，recovery point objective，可以容忍遺失多久的資料），而且能還原到過去 7 天內的任一時間點。
  • 團隊：兩個人，沒有專職維運，不想自己修補作業系統。
  • 現有設計：租戶隔離靠 PostgreSQL 的 RLS（ADR 0001、0002）；匯出 worker 用 BullMQ、跟 API 同一個程序（ADR 0005）；每租戶限流用 Redis（ADR 0006）；檔案經過 API 上傳下載（ADR 0004）。
  • 檔案與機密：檔案可能含客戶資料；log 依規定至少保留 30 天。

逐層對照需求：

把選擇與理由寫進 design.json，就是練習 1。測試檢查的是違反需求的硬限制（例如 Lambda、單一 AZ 的資料庫、少了 Redis），理由由你寫。這份 JSON 之後可以改寫成作品 repo 裡的 ADR（系統設計課第 18 課），面試時被問「為什麼這樣部署」，答案就在裡面。

部署的順序與冪等

選好了，接著把它們建出來。資源之間有相依關係，順序大致是：

  1. 網路：VPC、子網路、NAT、安全群組（第 3 課）與 ACM 憑證（第 4 課）。練習裡由測試先準備好。
  2. 不依賴別人的資源：ECR repository、CloudWatch log group、KMS 金鑰、S3 bucket。
  3. 資料庫：先把擁有者的密碼產生好放進 Secrets Manager（GetRandomPassword，排除標點，連線字串才不用處理跳脫），再用它建 RDS；拿到端點後，組出 migration 與 api 的連線字串，各放一個 secret。
  4. IAM：execution role（拉映像、寫 log、讀 secret）與 task role（存取 S3 與 KMS 金鑰）。
  5. 入口：target group、ALB、HTTPS 與轉址的 listener。
  6. 應用程式：兩個 task definition（api、migrate）、cluster、service；最後是告警。

部署程式一定會重跑：第一次跑到一半失敗、修好再跑；每次發新版本也要跑。所以每一步都寫成 ensure（確保存在）：先查，存在就沿用，不存在才建。最容易出事的是機密：secret 已經存在時，絕對不能重新產生值覆寫，資料庫的密碼還是舊的，覆寫之後所有服務都連不上。練習 2 的測試會把部署跑兩次，檢查第二次沒有多建任何東西、沒有改掉任何機密。

這門課用 SDK 一步步寫，是為了讓你看清楚每個資源與它們之間的關係。真的專案用 OpenTofu（devops 課第 20 課）：你描述「最後要長什麼樣子」，工具算出要建、改、刪哪些，冪等是它內建的；變更先 plan 給人審查再 apply。要注意的是，用 OpenTofu 產生並寫入 secret 的值時，那個值也會出現在 state 裡，state 要加密、權限要收緊（devops 課第 20 課）。

部署一個新版本時，順序是：build 兩個映像（最後的 stage 標 <SHA>、build stage 標 <SHA>-build）並推到 ECR → 用 migrate 的 task definition run-task，等它結束、確認 exit code 是 0 → 註冊新的 api task definition、更新 service → 等 service 穩定 → 跑冒煙測試。migration 失敗就停在這裡，舊版的 api 照常服務；新版的 task 起不來，service 的 circuit breaker 會自動回滾到上一個 task definition（第 5 課）。

💡 實務上：在 Mac 上 build 的映像，Fargate 跑不起來
Apple Silicon 的 Mac 預設 build 出 linux/arm64 的映像，Fargate 預設的 CPU 架構是 x86_64，task 一啟動就失敗，log 裡是 exec format error。兩個解法：build 時加 --platform linux/amd64，或在 task definition 設 runtimePlatform: { cpuArchitecture: 'ARM64', operatingSystemFamily: 'LINUX' } 改跑 ARM。更好的做法是不要從自己的電腦推映像：讓 CI（作品專案課第 17 課的 GitHub Actions）在固定的平台 build、用 OIDC（devops 課第 19 課）拿臨時憑證推到 ECR，線上的每一個映像都能對回一個 commit。

上線第一晚：四個事故

練習 2 的部署程式是從一份「已經在模擬器上跑過」的版本改來的，但它在真的 AWS 上第一次部署時，出了四件事。模擬器不檢查權限、不真的跑容器，所以這四件事在本機都沒有現形。每一件先看症狀，再找原因：

症狀原因修法
atask 一直停在啟動階段，ECS 事件是 ResourceInitializationError: unable to pull secretssecretsmanager:GetSecretValue 給在 task role。注入 secret 發生在容器啟動前，是 execution role 在讀移到 execution role，task role 拿掉多的權限
btask 起來了，target group 顯示 unhealthy，部署被 circuit breaker 回滾健康檢查路徑寫成 /api/v1/health/ready。參考實作的 HealthController 沒有 /api/v1 前綴，打到的是 404HealthCheckPath 改成 /health/ready，也確認 port 跟容器一樣是 3100
c沒有錯誤訊息；code review 時發現 api 的 task definition 注入了 DATABASE_URL為了「方便在容器裡手動跑 migration」把擁有者的連線字串也給了 api。擁有者不受 RLS 限制，api 被攻破時等於整個資料庫外洩api 只注入 APP_DATABASE_URL 與 JWT_SECRET；migration 只在獨立的 task definition 執行
d上傳、下載檔案都回 500，log 是 S3 的 AccessDeniedbucket 用 SSE-KMS，task role 只有 S3 的權限，少了這把金鑰的 kms:Decrypt（讀）與 kms:GenerateDataKey（寫）task role 補上這兩個動作，Resource 只寫這把金鑰的 ARN

a 和 b 是「起不來」，會被發現；c 是「跑得起來但不安全」，只有讀設定的人看得到；d 要等到有人用了某個功能才會出現。這也是為什麼冒煙測試（作品專案課第 17 課）除了 /health/ready，還要真的走過一次註冊、登入、建立資料、上傳檔案。

修好之後寫事後檢討（postmortem，devops 課第 25 課）：影響、時間線、根本原因、修正、改善項目（每一項有負責人與期限）。不究責：寫發生了什麼、為什麼會發生，不寫誰的錯。這四件事有一個共同的改善方向：模擬器測不到的東西，要在部署前用別的方法檢查，例如把練習 3 的測試（檢查 policy 與 task definition）放進 CI。

💡 實務上：ECS 部署失敗，先看這三個地方
task 起不來時，資深工程師的查找順序是：一、service 的 Events 分頁與停止的 task 的 stoppedReason（aws ecs describe-tasks），拉映像、讀 secret、記憶體不足都寫在這裡；二、task 有啟動的話看 CloudWatch Logs，程式自己的錯誤（環境變數驗證失敗、連不上資料庫）在這裡；三、task 跑著但被判定不健康，看 target group 的健康檢查設定與回應碼。分清楚是「ECS 沒把容器開起來」、「程式起來後自己掛了」還是「程式活著但 ALB 不認」，就知道要查 IAM、程式還是網路。

看得到、算得出：告警與成本

上線之後，要能在客人抱怨之前知道出事，也要知道錢花在哪。log、指標、告警的觀念 devops 課第 21～25 課教過，這裡只做 AWS 上的設定。練習 2 建三個告警，都通知一個 SNS topic（訂閱你的 email，或接到聊天工具）：

告警指標重點
5xx 變多AWS/ApplicationELB 的 HTTPCode_Target_5XX_Count，Sum，5 分鐘裡有 3 分鐘超過 10沒有流量時 ALB 不送資料，TreatMissingData 設 notBreaching
有 target 不健康UnHealthyHostCount，Minimum，連續 2 分鐘大於 0ALB 文件建議用 Minimum：每個 ALB 節點都認為它不健康才算
資料庫空間不足AWS/RDS 的 FreeStorageSpace，小於 2 GiB單位是 bytes

ALB 指標有一個常見的坑：維度 LoadBalancer 與 TargetGroup 的值不是整個 ARN，而是 ARN 的最後一段，app/my-saas-prod/50dc6c495c0c9188 與 targetgroup/my-saas-prod/73e2d6bc24d8a067（ALB 使用者指南，2026-11-20 查證）。寫成整個 ARN，PutMetricAlarm 照樣成功，只是這個告警永遠收不到資料。設好告警之後，用 aws cloudwatch set-alarm-state 手動把它設成 ALARM 一次，確認通知真的會送到。

成本的部分，先看哪些資源沒有流量也在計費，查表用，不用背（各服務定價頁，2026-11-20 查證計費方式；金額以定價頁為準）：

資源怎麼計費這個架構有幾個
NAT gateway每小時＋每 GB 處理量2（每個 AZ 一個）
ALB每小時＋用量（LCU）1
RDS執行個體每小時（Multi-AZ 多一台備援）＋儲存＋超過免費額度的備份1 組
ElastiCache節點每小時依節點數
Fargate依 task 的 vCPU 與記憶體，按執行時間計費2 個 task 一直在跑
公開 IPv4 位址每個每小時（ALB、NAT 都會用到）好幾個
Secrets Manager、KMS 客戶管理金鑰每個每月＋API 呼叫次數3 個 secret、1 把金鑰
CloudWatch Logs寫入量＋保存量保留 30 天就不會一直累積

小流量的作品，帳單主要是前四列這些「開著就算錢」的資源，跟流量幾乎無關。所以給面試官看的 demo 環境，常見的省法是：單一 AZ 的 RDS、一個 NAT、一個 task，並在 README 寫明「demo 環境為了成本是單一 AZ，正式環境的設計見 ADR」；這本身就是一個能在面試時講的取捨。

每個資源都帶 Project 與 Environment 兩個標籤（練習 2 會檢查），到 Billing 的 Cost allocation tags 頁面啟用這兩個標籤鍵之後，Cost Explorer 才能依專案、依環境拆帳單。依 Billing 使用者指南（2026-11-20 查證），標籤鍵最多要 24 小時才會出現在可以啟用的清單，啟用後最多再 24 小時才生效，所以第一天就要打上標籤。用 OpenTofu 的話，AWS provider 的 default_tags 可以一次替所有資源加上。

💡 實務上：部署完先算一次「一個月要多少」
資深工程師上線一個新環境後，會用 AWS Pricing Calculator 依實際建出來的資源估一次月費，寫進 README 或 ADR，並設一個比它高一點的 Budgets 警示（第 1 課）。月底帳單跟估算差很多時，到 Cost Explorer 依服務、再依用量類型展開，最常見的意外是 NAT 的處理量（例如 task 經由 NAT 從 ECR 拉映像、存取 S3，可以改走 VPC endpoint，第 3 課）和沒設保存天數的 log。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。用第 1 課建議的獨立練習帳號與 learn-sandbox profile，把作品真的部署一次，最後一定要清除。需要一個自己的網域與 Route 53 hosted zone、已驗證的 ACM 憑證（第 4 課）。

費用：這一節會建立按小時計費的資源：NAT gateway（每小時＋每 GB 處理量）、ALB（每小時＋LCU）、RDS 執行個體（Multi-AZ 多一台備援）、ElastiCache 節點、Fargate task（vCPU 與記憶體依執行時間）、公開 IPv4 位址（每個每小時），另有 Secrets Manager、KMS、CloudWatch Logs 的月費與用量費。開著一天就會產生明顯的費用，做完當天就清除。金額查各服務的官方定價頁，或用 AWS Pricing Calculator 估算；建議先把 RDS 改成單一 AZ、NAT 改成一個，再估一次。

1. 建基礎設施（OpenTofu）。照練習 2 deploy.ts 的資源清單，在作品 repo 的 infra/ 用 OpenTofu 寫一份設定（devops 課第 20 課），對應的資源類型是：aws_vpc、aws_subnet、aws_nat_gateway、aws_security_group、aws_ecr_repository、aws_cloudwatch_log_group、aws_kms_key、aws_s3_bucket（加上 aws_s3_bucket_public_access_block、aws_s3_bucket_server_side_encryption_configuration）、aws_db_subnet_group、aws_db_instance、aws_elasticache_parameter_group、aws_elasticache_replication_group、aws_secretsmanager_secret、aws_iam_role、aws_iam_role_policy、aws_lb、aws_lb_target_group、aws_lb_listener、aws_ecs_cluster、aws_ecs_task_definition、aws_ecs_service、aws_sns_topic、aws_cloudwatch_metric_alarm。provider 設 default_tags。RDS 先把 deletion_protection 設成 false，不然清除時刪不掉。

cd infra
tofu init
tofu plan -out plan.bin           # 讀一遍：+ 建立了哪些資源，有沒有你沒預期的

2. 推映像、跑 migration、部署 api。以下的 <…> 換成你的值（tofu output 可以印出來）：

# 登入 ECR，build 兩個映像（Fargate 預設 x86_64），標籤用 commit SHA
SHA=$(git rev-parse --short HEAD)
REPO=<帳號>.dkr.ecr.ap-northeast-1.amazonaws.com/my-saas-prod
aws ecr get-login-password --region ap-northeast-1 --profile learn-sandbox | docker login --username AWS --password-stdin <帳號>.dkr.ecr.ap-northeast-1.amazonaws.com
docker build --platform linux/amd64 -t $REPO:$SHA .
docker build --platform linux/amd64 --target build -t $REPO:$SHA-build .
docker push $REPO:$SHA
docker push $REPO:$SHA-build

# 跑一次 migration，等它結束，看 exit code（要是 0）
TASK=$(aws ecs run-task --cluster my-saas-prod --task-definition my-saas-prod-migrate --launch-type FARGATE \
  --network-configuration 'awsvpcConfiguration={subnets=[<私有子網路1>,<私有子網路2>],securityGroups=[<app-sg>],assignPublicIp=DISABLED}' \
  --query 'tasks[0].taskArn' --output text --profile learn-sandbox --region ap-northeast-1)
aws ecs wait tasks-stopped --cluster my-saas-prod --tasks $TASK --profile learn-sandbox --region ap-northeast-1
aws ecs describe-tasks --cluster my-saas-prod --tasks $TASK --query 'tasks[0].containers[0].exitCode' --profile learn-sandbox --region ap-northeast-1

# 更新 api 並等它穩定；看 log
aws ecs update-service --cluster my-saas-prod --service api --task-definition my-saas-prod-api --force-new-deployment --profile learn-sandbox --region ap-northeast-1
aws ecs wait services-stable --cluster my-saas-prod --services api --profile learn-sandbox --region ap-northeast-1
aws logs tail /ecs/my-saas-prod --since 10m --profile learn-sandbox --region ap-northeast-1

# 冒煙測試：健康檢查，再跑作品專案課第 17 課練習 3（在 work/portfolio.json 填 deployUrl）
curl -sS https://api.<你的網域>/health/ready

# 確認告警真的會通知：手動把一個告警設成 ALARM
aws cloudwatch set-alarm-state --alarm-name my-saas-prod-alb-5xx --state-value ALARM --state-reason 'test notification' --profile learn-sandbox --region ap-northeast-1

第一次 migration 完成後，別忘了上面「程式要改的地方」裡的 pf_app 密碼。部署成功後，把網址與示範帳號寫進作品的 README（作品專案課第 19 課）。

練習

本機練習在 aws/practice/work/11/。練習 2、3 的測試會先建好網路（VPC、兩個 AZ 的公有與私有子網路、alb-sg／app-sg／db-sg）與 ACM 憑證，再呼叫你的 deploy；每次執行用一個新的環境名稱（例如 my-saas-ex2-mf3k），重跑不會撞到上一次建的資源。

練習 1：照「架構與取捨」的需求填 design.json。compute.choice 是 ecs-fargate／lambda／ec2；worker.choice 是 same-process／separate-service；database 有 engine、multiAz、backupRetentionDays；redis 有 choice（elasticache／none）與 maxmemoryPolicy；files 有 choice、publicAccess、encryption（sse-s3／sse-kms）；secrets.choice 是 secrets-manager／environment；network 有 azs 與 natGateways；logs.retentionDays 是 CloudWatch Logs 接受的天數（null 代表永久）。除了 logs，每一層的 reason 至少 10 個字，寫出為什麼。

練習 2：讀懂 deploy.ts，完成四個標了「練習 2」的函式。ensureLogGroup：log group 不存在才建（tags 轉成物件），保留天數設 30。ensureSecret：DescribeSecretCommand 找得到就回傳 ARN，不呼叫 makeValue、不覆寫；找不到（ResourceNotFoundException）才 CreateSecretCommand（帶 Tags）。ensureDatabase：找不到（DBInstanceNotFoundFault）才先建 DB subnet group（私有子網路），再建 RDS：Engine: 'postgres'、DBName: 'my_saas'、帳號密碼用 owner、MultiAZ、BackupRetentionPeriod: 7、StorageEncrypted、PubliclyAccessible: false、DeletionProtection、VpcSecurityGroupIds: [net.dbSg]、Tags；回傳 Endpoint 的 { host, port }。ensureAlarms：照「看得到、算得出」的表建三個告警，名稱是 <name>-alb-5xx、<name>-unhealthy-hosts、<name>-db-free-storage，AlarmActions 與 OKActions 都是 [topic]，帶 Tags；ALB 的維度值用 ARN 的最後一段。測試會把整個部署跑兩次。

練習 3：修好 deploy.ts 裡「上線第一晚」的四個事故：讀 secret 的權限移到 execution role（task role 拿掉）；健康檢查路徑改成 /health/ready；api 只注入 APP_DATABASE_URL 與 JWT_SECRET；task role 加上對 bucket 金鑰的 kms:Decrypt 與 kms:GenerateDataKey（Resource 只寫 keyArn）。再完成 postmortem.md：## 影響、## 時間線（至少 4 行有 HH:MM 時間）、## 根本原因（四個事故都要寫到）、## 修正、## 改善項目（至少 3 項，每項有「負責人」與 YYYY-MM-DD 的期限）。練習 2 沒寫完時，這題的部署也跑不起來。

練習 4：你在 M 系列晶片的 Mac 上 docker build、推到 ECR，task definition 沒設 runtimePlatform。Fargate 上的 task 一啟動就停止，log 只有一行 exec format error。原因是？

✓ c。exec format error 是「這個執行檔不是這顆 CPU 的指令集」。Apple Silicon 預設 build 出 arm64 映像，Fargate 沒指定時用 x86_64。a 的症狀是拉不到映像（CannotPullContainerError），容器根本不會開始執行；d 錯在映像裡的 Node 跟 Fargate 無關，Fargate 只負責跑容器。

練習 5：my-saas 上線一個月後，偶爾有客戶回報「匯出一直卡在處理中」。查 log 發現那些匯出的 job 根本不在 BullMQ 的佇列裡，而 ElastiCache 的記憶體使用率常常接近上限。最可能的原因是？

✓ a。BullMQ 文件寫明 maxmemory-policy 一定要是 noeviction，只有它能保證佇列的資料不會被清掉；ElastiCache 預設是 volatile-lru。改成 noeviction 後，記憶體滿時寫入會失敗而不是默默丟資料，所以還要對記憶體使用率告警。c 的「同一個程序」只會讓匯出變慢，job 仍然在佇列裡。

練習 6：部署時每個資源都帶了 Project=my-saas 標籤，但隔天在 Cost Explorer 依標籤分組，my-saas 的費用是 0，全部歸在「No tag key」。最可能的原因是？

✓ d。資源上的標籤要先在 Billing 啟用成成本分攤標籤，帳單才會依它拆分，而且出現在清單、啟用生效各可能要 24 小時，所以第一天就要打標籤並啟用。a 錯在標籤鍵不限大小寫寫法，只要跟啟用的那個一致；b 錯在 Fargate、RDS 這些支援標籤的資源都能分攤。

自評清單

測試檢查的是設定寫對沒有，真的跑得起來要自己確認。部署到真的帳號之後：

  • 從另一台電腦（或手機網路）打開 https://api.<你的網域>/health/ready 是 200，http:// 會被 301 轉到 https。
  • 作品專案課第 17 課練習 3 的冒煙測試對線上環境全部通過（註冊、登入、建立 project、別的租戶 404）。
  • 上傳一個檔案再下載回來（驗證 task role 的 S3 與 KMS 權限）；S3 主控台裡物件的加密是 SSE-KMS。
  • 觸發一次匯出並下載結果（驗證 Redis 與 worker）。
  • RDS 主控台：Multi-AZ 是 Yes、自動備份保留 7 天、Publicly accessible 是 No；從你的電腦直接連 5432 連不上。
  • api 的 task definition 裡只有 APP_DATABASE_URL 與 JWT_SECRET 兩個 secret，environment 裡沒有任何密碼；pf_app 的密碼已經不是 migration 裡寫死的那個。
  • 手動把一個告警設成 ALARM，通知有送到；log group 的保留天數是 30。
  • 部署第二個 commit，再把上一個 SHA 的 task definition 部署回去，冒煙測試照樣通過（回滾演練）。
  • 用 Pricing Calculator 估過月費，寫進 README；Budgets 警示已設好；做完後清除並在隔天確認費用停止增加。

常見錯誤

  • 讀 secret 的權限給 task role：注入是 execution role 在讀，task 停在啟動階段。
  • 健康檢查路徑照抄 API 的前綴：作品的 /health/ready 沒有 /api/v1，所有 task 都被判定不健康。
  • 把擁有者的連線字串給 api：RLS 被繞過的風險。只有 migration 的 task definition 拿得到。
  • SSE-KMS 的 bucket 只給 S3 權限：讀要 kms:Decrypt、寫要 kms:GenerateDataKey。
  • 重新部署時重新產生密碼：資料庫還是舊密碼，所有服務連不上。secret 已存在就沿用。
  • migration 放在 api 的啟動指令：多個 task 同時跑 migration，而且最後的映像裡沒有 prisma CLI。用獨立的 task definition 與 run-task。
  • ElastiCache 用預設參數群組跑 BullMQ：volatile-lru 會在記憶體滿時清掉 key。用 noeviction。
  • ALB 告警的維度寫整個 ARN：告警建立成功但永遠收不到資料。用 ARN 的最後一段，並手動觸發一次確認。
  • log 沒設保存天數：預設永久保存，費用一直累積。
  • 只放一個 NAT gateway 卻宣稱跨 AZ 高可用：NAT 所在的 AZ 故障，另一邊的 task 出不去。
  • 在 Mac 上 build 映像直接推：arm64 的映像在預設的 Fargate 上 exec format error。指定平台，或交給 CI。
  • 練習帳號的資源沒清：NAT、ALB、RDS、ElastiCache、公開 IPv4 沒流量也在計費。

小結

  • 從 compose 到 AWS：api → ECR＋ECS Fargate（兩個 AZ）；migrate → build 階段的映像、獨立的 task definition、部署前 run-task；db → RDS PostgreSQL Multi-AZ；redis → ElastiCache（noeviction）；檔案 → S3（SSE-KMS）；機密 → Secrets Manager 注入；入口 → ALB＋ACM；log → CloudWatch Logs。
  • 程式要改的只有幾處：檔案改存 S3、pf_app 換掉寫死的密碼、trust proxy 信任 ALB 這一跳。每一項是一個小 PR，寫成 ADR。
  • 每一層的選擇對照需求寫下理由：RTO 決定 Multi-AZ 與每 AZ 一個 NAT，RPO 決定自動備份，團隊大小決定 Fargate，現有設計決定 Redis 不能拿掉。
  • 部署程式每一步都是「先查、沒有才建」，可以重複執行；已經存在的 secret 絕對不覆寫。真的專案用 OpenTofu，state 裡的機密要保護。
  • 新版本的順序：推兩個 SHA 標籤的映像 → run-task 跑 migration 並確認 exit code → 更新 service → 等穩定 → 冒煙測試；起不來時 circuit breaker 回滾。
  • 部署失敗依序看 ECS 事件與 stoppedReason、CloudWatch Logs、target group 健康檢查；事後檢討寫影響、時間線、根本原因、修正、有負責人與期限的改善項目。
  • 告警通知 SNS：5xx（沒資料不算異常）、UnHealthyHostCount（Minimum）、FreeStorageSpace；ALB 的維度用 ARN 的最後一段。小流量時帳單主要是 NAT、ALB、RDS、ElastiCache、公開 IPv4 這些按小時計費的資源；成本分攤標籤要在 Billing 啟用。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：加點數的 worker 拉到訊息後，第一行就呼叫 DeleteMessage，接著才寫資料庫。某次部署重啟時有幾筆點數沒加上，DLQ 卻是空的。為什麼？

✓ b。先刪再處理是「至多一次」：處理失敗就永遠失去這則訊息，它也不會進 DLQ，因為 DLQ 只接「被收了很多次還沒刪」的訊息。修法是處理成功才刪，並讓處理冪等。a 錯在訊息已經被刪，根本不會再被接收。d 錯在 SQS 不會遺失訊息，是程式自己刪的。（第 10 課）

練習 8：結帳把訂單 JSON 發布到 SNS，廚房的佇列訂閱時設了 FilterPolicy {"type":["drink"]}，沒有設其他訂閱屬性。上線後廚房一杯飲料的訊息都沒收到，也沒有任何錯誤。先查什麼？

✓ d。filter policy 預設看 message attributes，發布時沒帶 type 屬性，所以沒有任何訊息符合，SNS 也不會報錯。設 FilterPolicyScope: MessageBody，或發布時把 type 放進 message attributes。另一個也要查的是 queue policy 有沒有允許這個 topic，但在這個情境裡，其他沒過濾的訂閱者有收到的話，問題就在過濾。（第 10 課）

練習 9：寄收據的 worker 用 SQS 的 MessageId 當冪等鍵，在 DynamoDB 記下處理過的 MessageId。結果還是有客人收到兩封收據。最可能的原因是？

✓ a。重複不只來自 SQS 重送，也來自生產者自己重送；MessageId 是 SQS 替每一次 SendMessage 產生的，認不出「同一個業務意圖」。冪等鍵要用業務上的 ID。b 錯在條件寫入在單一 item 上是原子的；c 錯在 SQS 重送的是同一則訊息，MessageId 不變（變的是 receipt handle）。（第 10 課）

練習 10：門市上傳 sales/門市 A.csv，匯入的 Lambda 用事件裡的 key 呼叫 GetObject，收到 NoSuchKey。程式碼是 const key = decodeURIComponent(record.s3.object.key)。哪裡錯了？

✓ c。S3 事件的 key 是 form 編碼：空白是 +、真正的 + 是 %2B。所以先換 + 再 decodeURIComponent，順序不能反。a 錯在 S3 是強一致的，收到建立事件時物件已經讀得到；b 錯在文件寫明 key 是 URL 編碼的。（第 10 課）

練習 11：my-saas 第一次部署，ECS 的 task 一直停在啟動階段，事件是 ResourceInitializationError: unable to pull secrets or registry auth。task role 的 policy 裡有 secretsmanager:GetSecretValue。先改哪裡？

✓ b。execution role 是 ECS 替你做事用的（拉映像、寫 log、注入 secret），task role 是你的程式呼叫 AWS 用的。容器還沒啟動，task role 根本還沒派上用場。d 在私有子網路沒有 NAT 或 VPC endpoint 時確實也會出現同樣的訊息，但這個情境的 policy 給錯 role 是先要修的；不要為了繞過去把 task 放到公有子網路。（第 5、11 課）

練習 12：同事建了「5xx 太多」的告警，Dimensions 寫 LoadBalancer = arn:aws:elasticloadbalancing:…:loadbalancer/app/my-saas-prod/50dc…。PutMetricAlarm 成功了，告警狀態一直是 INSUFFICIENT_DATA，昨晚 API 大量 500 時也沒響。原因是？

✓ a。CloudWatch 用「名稱＋維度」找指標，維度值不一致就是另一個不存在的指標，API 不會報錯。設好後用 set-alarm-state 手動觸發一次、並看告警圖上有沒有資料。c 只會讓它變成一直告警，掩蓋了真正的問題；d 錯在 HTTPCode_Target_5XX_Count 的有意義統計就是 Sum。（第 11 課）

練習 13：為了省事，有人把 api 的啟動指令改成 npx prisma migrate deploy && node dist/main.js，service 有 2 個 task。哪裡會出事？

✓ d。作品專案課第 17 課的做法是 migration 用 build 階段的映像、獨立一步、只有它拿得到擁有者帳號；在 ECS 上就是獨立的 task definition＋run-task，跑完確認 exit code 再更新 service。c 的「給 api 擁有者的連線字串」正是第一晚的事故 c，等於讓 api 繞過 RLS。（第 11 課）

練習 14：作品上線一個月，幾乎沒有人用，帳單卻比預期高很多。用 Cost Explorer 依服務展開之前，你最先懷疑哪一類資源？

✓ c。小流量時，帳單主要是「開著就算錢」的固定費用，跟使用量幾乎無關；demo 環境常見的取捨是單一 AZ、一個 NAT，並在 README 說明。d 錯在 Fargate 依 task 的 vCPU 與記憶體按執行時間計費，不是按請求；a、b 在沒什麼人用時金額很小。（第 1、11 課）
