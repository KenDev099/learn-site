階段 1：帳號與身分 · 第 2 課

帳號與 IAM 延伸：SSO 設定檔、CloudTrail、跨帳號 role、permission boundary 與提權路徑

咖啡店請外包做會員系統。店長為了省事，把 root 使用者的 access key 寫進 .env 交給外包；幾週後金鑰外洩，帳號一夜之間被開了幾十台機器。事後老闆問了三個問題：是誰、在什麼時候、做了哪些事？同一週，合作的會計事務所要讀咖啡店 bucket 裡的月報表，同事直接在 bucket policy 寫了對方帳號可以 s3:*、Resource *。

devops 課第 19 課已經把帳號的第一天、同一個帳號裡的權限評估、role 與 OIDC 做完。這一課接著往下：開發者電腦上的憑證怎麼放才安全、出事後怎麼用 CloudTrail 查、別的帳號要用你的資源時權限怎麼算、怎麼讓開發者自己建 role 又不會替自己升級成管理員。

這課的路線：

  • 開發者電腦上的憑證：讀懂 ~/.aws/config 的 SSO profile，找出設定檔裡的風險（練習 1）。
  • CloudTrail：事情發生之後，怎麼查出誰做了什麼，哪些事查不到。
  • 跨帳號的權限：為什麼兩邊都要允許，完整的評估順序（練習 2）。
  • 把 role 交給另一個帳號：信任政策、ExternalId、session 的長度（練習 3）。
  • 提權路徑與 permission boundary：哪些權限組合等於管理員，怎麼放權又不失控（練習 4）。
這課會用到：devops 課第 19 課的 policy 評估（同一個帳號裡：明確拒絕優先，身分型與資源型政策取聯集）、role 與信任政策（誰可以 assume 這個 role）、IAM Identity Center（人員的單一登入）；第 1 課的憑證鏈與 profile（SDK 依固定順序找憑證，AWS_PROFILE 指定用哪個 profile）。
練習環境：模擬器不檢查權限，任何憑證都能做任何事。所以「允不允許」的判斷都在頁面上的練習做；本機練習只檢查你建出來的 role 與政策文件寫得對不對。

開發者電腦上的憑證：SSO profile

開場的事故，根源是一把長期金鑰（access key：一組不會自己過期的 ID 加 secret）被放在檔案裡傳來傳去。devops 課第 19 課說過人員應該走 IAM Identity Center 登入；這一節看它落到你電腦上長什麼樣子，以及怎麼檢查一台電腦的設定有沒有問題。

執行 aws configure sso，照提示輸入公司的 SSO 入口網址（start URL）、選帳號與權限，CLI 會在 ~/.aws/config 寫下兩種區段：

[profile cafe-dev]                 # 一個 profile：用哪個 SSO 登入、進哪個帳號、拿哪個權限
sso_session = cafe
sso_account_id = 111122223333
sso_role_name = Developer          # Identity Center 的 permission set 名稱
region = ap-northeast-1

[sso-session cafe]                 # SSO 登入本身：入口網址與 Identity Center 所在的 region
sso_start_url = https://cafe.awsapps.com/start
sso_region = ap-northeast-1
sso_registration_scopes = sso:account:access
  • profile 區段在 config 檔寫成 [profile 名稱]，只有 [default] 例外；同一個 profile 在 ~/.aws/credentials 檔裡寫成 [名稱]，沒有 profile 前綴。CLI 會把兩個檔案裡同名的 profile 合在一起看。
  • sso-session 區段可以被好幾個 profile 共用：同一個入口登入一次，就能用 dev、staging 兩個 profile。sso_region 是 Identity Center 所在的 region，跟 profile 自己的 region（資源在哪）是兩回事。

每天開始工作時執行 aws sso login --profile cafe-dev，瀏覽器會打開讓你確認登入。成功後 CLI 把 SSO 的 token 快取在 ~/.aws/sso/cache/，之後 CLI 與 SDK 用這個 token 換到的都是會過期的臨時憑證。電腦被偷、檔案外洩，攻擊者拿到的也只是短時間內有效的東西，而且公司在 Identity Center 停用你的帳號後就換不到新的。

沒有 Identity Center 的個人帳號，AWS CLI 2.32.0 起還有 aws login：在瀏覽器用主控台的身分（root、IAM user 或聯合登入）登入，CLI 拿到臨時憑證並自動更新，最長 12 小時，config 裡會寫下一行 login_session = …（官方「Login for AWS local development using console credentials」，2026-11-20 查證；這門課的 CLI 是 2.36.37）。公司帳號有 Identity Center 時，官方建議用 aws configure sso。

所以檢查一台電腦的設定，要找的是這幾件事，練習 1 會寫成程式：

看到什麼為什麼是風險
某個 profile 有 aws_access_key_id長期金鑰，外洩就一直有效，要換成 SSO
[default] 指向正式環境的帳號忘了加 --profile 的指令全部打到正式環境（第 1 課的憑證鏈）
sso_session 指到不存在的 [sso-session]這個 profile 登入不了，常見於複製別人的設定檔
[sso-session] 沒有 sso_regionCLI 不知道去哪個 region 的 Identity Center 登入
兩個 profile 名稱指向同一個帳號＋同一個權限同一個身分有兩個名字，有人以為自己在用 staging，其實是同一個帳號
💡 實務上：新人拿到的是 SSO 入口網址，不是金鑰
成熟的團隊替新人開帳號時，給的是 Identity Center 的入口網址和一段 ~/.aws/config 範本，權限依職務分成幾個 permission set（例如 Developer、ReadOnly）；離職時在 Identity Center 停用一個人，所有帳號的存取一起收回。接手舊專案時，先在團隊裡問「誰的電腦上還有 aws_access_key_id」，再搭配 devops 課第 19 課的 credential report 找出帳號裡的長期金鑰，逐一換掉。

CloudTrail：事情發生之後查得到什麼

上一節讓金鑰不容易外洩；這一節處理開場老闆的三個問題。CloudTrail 是 AWS 的操作紀錄服務：每一個 API 呼叫（不管來自主控台、CLI 還是 SDK）都會留下一筆事件（event），寫明誰、什麼時候、從哪個 IP、呼叫了什麼、成功或失敗。

不用設定就有的是 Event history（事件歷史）。依官方文件（2026-11-20 查證）：

  • 保留最近 90 天，看 Event history 不收費。
  • 只有管理事件（management events）：對資源本身的操作，例如建立 bucket、刪除 bucket、改 security group、建 IAM role。資料事件（data events）不在裡面：讀寫 S3 物件（GetObject、PutObject）、呼叫 Lambda 函式這類「用資源」的操作。
  • 一次只查一個 region、一個帳號，而且只能用一個條件篩選（例如事件名稱或資源名稱）加時間範圍。IAM 這類全球服務的事件，大多記在 us-east-1。

要超過 90 天、要看資料事件、要集中多個帳號，就要自己建 trail（把事件持續寫進一個 S3 bucket）或 CloudTrail Lake 的 event data store。資料事件要在 trail 上另外開，依事件數計費（CloudTrail 定價頁）。「誰下載了收據」這種問題，事前沒開資料事件，事後就查不到。

查「誰刪了 cafe-menu 這個 bucket」：

aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=ResourceName,AttributeValue=cafe-menu \
  --query 'Events[].CloudTrailEvent' --output text

💡 實務上：事故調查第一步是 CloudTrail，第二步才是修
發現金鑰外洩時，先把那把金鑰設成 Inactive 止血，接著用 CloudTrail 以金鑰 ID 查出它做過的事：建了哪些機器、開了哪些新的 user 或金鑰（攻擊者常留後門）、改了哪些權限，每一項都要清掉。公司帳號通常會在第一天就建一個組織層級的 trail，寫進一個專門的 log 帳號，一般開發者刪不掉，因為入侵者第一件事常常是關掉 trail。

跨帳號：兩邊都要允許

知道怎麼查之後，回到開場的第二件事：會計事務所的帳號要讀咖啡店的 bucket。這是跨帳號存取：發出請求的身分（principal）在一個帳號，資源在另一個帳號。

devops 課第 19 課的規則是同一個帳號內的版本：身分型政策（掛在 user、role 上）和資源型政策（掛在資源上，例如 bucket policy）取聯集，任一邊允許、沒有明確拒絕就放行。跨帳號時不一樣，AWS 會在兩個帳號各評估一次，兩邊都要允許（官方「Cross-account policy evaluation logic」）：

所以同事的寫法錯在兩個地方：bucket policy 給了對方 s3:* 與 *，對方帳號的管理員又可以把這個權限轉給他們帳號裡的任何人。正確的做法是 bucket policy 只列對方指定的 role、只給 s3:GetObject、Resource 只到 reports/*；或是下一節的做法：在咖啡店帳號建一個 role 給對方 assume。

把所有政策類型放在一起，官方「Policy evaluation logic」的評估順序是（2026-11-20 查證）：

  1. 明確拒絕：所有相關政策裡只要有一條符合的 Deny，就拒絕。
  2. RCP（resource control policy）、SCP（service control policy）：AWS Organizations 對整個帳號設的上限，前者管帳號裡的資源、後者管帳號裡的身分。有設定時，它們沒允許的就拒絕。
  3. 資源型政策：同一個帳號內，它直接允許某些身分時可以單獨放行；跨帳號時它只是兩個必要條件之一。
  4. 身分型政策：沒有任何一條允許，就是隱含拒絕。
  5. permission boundary：掛在 user 或 role 上的「上限」，它沒允許的就拒絕。
  6. session policy：assume role 時另外傳入的政策，同樣只能再收窄。

第 2、5、6 步都只能收窄，本身不給任何權限：boundary 寫了 s3:*，身分型政策沒寫，還是什麼都不能做。同一個帳號內，資源型政策直接列出某個 user 或 role session 時，boundary 的隱含拒絕擋不住它，細節在官方文件；練習 2 的同帳號情況不會出現 boundary。

把 role 交給另一個帳號：信任政策與 ExternalId

bucket policy 只適用 S3 這類有資源型政策的服務。更通用的跨帳號做法是：在咖啡店帳號建一個 role，讓對方 assume 進來。一個 role 由兩份政策組成：

  • 信任政策（trust policy）：誰可以 assume 我。它本身就是 role 的資源型政策，Principal 寫對方的帳號（arn:aws:iam::222222222222:root，代表「那個帳號，由它自己決定給誰」）或對方指定的 role。
  • 權限政策（permissions policy）：assume 進來之後能做什麼，就是一般的身分型政策。

對方那邊還要有 sts:AssumeRole 這個 role 的權限，又是「兩邊都要允許」。assume 成功後拿到的是臨時憑證，身分變成 arn:aws:sts::111111111111:assumed-role/角色名稱/session 名稱，CloudTrail 裡會看到這個 session 名稱，所以要求對方用有意義的名字。

如果對方是一家替很多客戶服務的公司（例如報表 SaaS），還有一個陷阱叫 confused deputy（被混淆的代理人）：SaaS 用自己的帳號替每個客戶 assume 客戶的 role。另一個客戶只要在 SaaS 的設定頁填上你的 role ARN，SaaS 就會替他去讀你的資料，因為 SaaS 的帳號確實被你信任。解法是 ExternalId：SaaS 替每個客戶產生一個不重複的字串，你在信任政策加上條件，assume 時必須帶這個字串：

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::222222222222:root" },
    "Action": "sts:AssumeRole",
    "Condition": { "StringEquals": { "sts:ExternalId": "cafe-reports-7f3a" } }
  }]
}

別的客戶填你的 role ARN 時，SaaS 帶的是那個客戶的 ExternalId，條件不成立。ExternalId 不是密碼，它的作用是讓 SaaS 分得清「這次是替誰做」，所以由 SaaS 產生、客戶不能自己改。

對方的 CLI 設定長這樣，source_profile 是他們自己的身分，CLI 會自動帶 ExternalId 去 assume：

[profile cafe-reports]
role_arn = arn:aws:iam::111111111111:role/cafe-reporting
source_profile = accounting-sso
external_id = cafe-reports-7f3a
role_session_name = accounting-monthly-report

session 的長度：role 的 MaxSessionDuration 可以設 1 到 12 小時（預設 1 小時），assume 時用 DurationSeconds 要求不超過它的長度；從一個 role 的臨時憑證再 assume 另一個 role（role chaining）最長只有 1 小時。assume 時也可以傳一份 session policy，讓這一次拿到的權限比 role 本身更小。

💡 實務上：跨帳號給 role，不給 IAM user
合作廠商、外包、另一個部門要用你的資源，資深工程師的做法是建一個 role、信任政策只列對方的帳號（或對方指定的 role）、加 ExternalId（對方是多客戶的服務時一定要）、權限只開需要的動作與路徑，再把 role ARN 給對方。不要在自己帳號替對方開 IAM user 和金鑰：金鑰會被存在對方的系統裡，你看不到、也無法要求輪替。合作結束時刪掉 role，存取立刻結束。

提權路徑與 permission boundary

跨帳號處理的是「外面的人能做什麼」；最後一節看「裡面的人會不會替自己加權限」。提權（privilege escalation）是指一個身分利用手上的權限，間接拿到比原本更大的權限。devops 課第 19 課已經點出 iam:PassRole 給 * 的危險，這裡把常見的路徑列完整：

手上的權限怎麼變成管理員
iam:PassRole（Resource 涵蓋管理員 role）＋ec2:RunInstances開一台機器，instance profile 掛管理員 role，從機器上拿 role 的憑證
iam:PassRole（同上）＋lambda:CreateFunction建一個用管理員 role 執行的函式，在函式裡做任何事
iam:CreatePolicyVersion替自己身上的受管政策建一個新版本，內容改成 "Action": "*" 並設為預設版本
iam:AttachUserPolicy（Resource 涵蓋自己）把 AdministratorAccess 掛到自己身上

要注意這些權限常常不是明寫出來的：iam:*、iam:Pass*、"Action": "*" 都包含它們；"NotAction": "s3:*" 搭配 Allow 的意思是「S3 以外全部允許」，也包含它們。只用字串比對找 iam:PassRole 的審查會漏掉，練習 4 就是處理這些寫法。

可是平台團隊不可能每次都替開發者建 role：開發者做 Lambda 時，自己就需要建 role、把 role 交給 Lambda。permission boundary 解決這個矛盾。它是掛在 user 或 role 上的一份政策，代表「這個身分最多能有多少權限」；實際能做的是身分型政策與 boundary 的交集。做法是給開發者建 role 的權限，但加一個條件：建出來的 role 一定要掛上指定的 boundary。

{
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:PutRolePolicy", "iam:AttachRolePolicy"],
  "Resource": "arn:aws:iam::111111111111:role/app-*",
  "Condition": {
    "StringEquals": { "iam:PermissionsBoundary": "arn:aws:iam::111111111111:policy/app-boundary" }
  }
}

這樣開發者建的 app-* role 就算掛了 AdministratorAccess，實際權限也不會超出 app-boundary。完整的設計還要用 Deny 擋住開發者修改、刪除 boundary 本身，以及移除 role 上的 boundary（iam:DeleteRolePermissionsBoundary）。

這些組合靠人眼很難看全。IAM Access Analyzer 的政策驗證會在你存政策時提出安全警告（devops 課第 19 課介紹過），團隊裡也常在 CI 檢查 IAM 的變更。

💡 實務上：審 IAM 的 PR 時，先問「這能不能變成管理員」
IaC 的 PR 裡出現 IAM 變更，資深工程師會先找四樣東西：Action 有沒有萬用字元或 NotAction、iam:PassRole 的 Resource 是不是具體的 role、有沒有能改政策或掛政策的 iam: 動作、建 role 的權限有沒有綁 boundary。需要給開發者自建 role 的權限時，跟資安一起定一份 boundary，寫進團隊的平台文件。

這課的練習怎麼對應真的 AWS

前面的判斷規則都在 AWS 的權限評估裡發生，模擬器不做這件事：它不會因為信任政策沒列你就拒絕 assume，也不會因為缺 ExternalId 就擋下。所以這課分成兩種練習：

  • 頁面上的練習（1、2、4）：把規則寫成程式，判斷設定檔與政策有沒有問題、請求會不會被允許。
  • 本機練習（3）：用 SDK 在模擬器建 role，測試把 role 與政策讀回來檢查內容。IAM 回傳的政策文件是 URL 編碼的 JSON，要先 decodeURIComponent 再 JSON.parse。最後用另一個模擬帳號 assume 一次，確認 role 可以被使用，但這一步在模擬器一定成功，不能拿來證明信任政策是對的。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。用第 1 課開的獨立練習帳號，不要用公司帳號。這一節替你建好之後每一課都會用的 learn-sandbox profile，再試一次 ExternalId 與 CloudTrail。

費用：這一節不建立計費的資源。IAM Identity Center 與 IAM 不另外收費；CloudTrail 的 Event history 查詢不收費（CloudTrail 文件，2026-11-20 查證）。

先在主控台用 root 登入，搜尋「IAM Identity Center」並啟用（主控台會引導你一起啟用 AWS Organizations），建一個使用者給自己、建一個 permission set（練習帳號可以用 AdministratorAccess），把使用者與 permission set 指派到這個帳號。記下設定頁上的 AWS access portal URL（https://…awsapps.com/start）。之後全部用 CLI：

# 1. 建立 profile：照提示輸入 SSO session 名稱、剛才的 portal URL、Identity Center 所在的 region，再選帳號與 permission set
aws configure sso --profile learn-sandbox

# 2. 看 ~/.aws/config 多了 [profile learn-sandbox] 與 [sso-session …] 兩個區段
cat ~/.aws/config

# 3. 之後每天開始前登入一次，再確認身分：Arn 應該是 assumed-role/AWSReservedSSO_…
aws sso login --profile learn-sandbox
aws sts get-caller-identity --profile learn-sandbox

# 4. 建一個要求 ExternalId 的 role，這裡用自己的帳號扮演合作夥伴（<帳號ID> 換成你的 12 位數帳號）
cat > trust.json <<'EOF'
{ "Version": "2012-10-17", "Statement": [{ "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::<帳號ID>:root" }, "Action": "sts:AssumeRole",
  "Condition": { "StringEquals": { "sts:ExternalId": "cafe-learn-demo" } } }] }
EOF
aws iam create-role --role-name cafe-learn-02-partner --assume-role-policy-document file://trust.json --profile learn-sandbox

# 5. 不帶 ExternalId：應該回 AccessDenied
aws sts assume-role --role-arn arn:aws:iam::<帳號ID>:role/cafe-learn-02-partner --role-session-name try --profile learn-sandbox

# 6. 帶 ExternalId：拿到 assumed-role/cafe-learn-02-partner/try 的臨時憑證

練習

練習 1：寫 auditConfig(configText, credentialsText, prodAccounts)，讀 ~/.aws/config 與 ~/.aws/credentials 的內容，回傳排序過的風險清單。解析規則：一行一個設定，前後空白去掉；空行和 #、; 開頭的行是註解；[…] 是區段；key = value 在第一個 = 切開。config 的 [default] 與 [profile X] 都是 profile（名稱是 default、X），[sso-session X] 是 SSO 登入設定；credentials 的 [X] 是 profile X，跟 config 的 [profile X] 合在一起看。要回報的風險：

  • static-key:X：profile X 有 aws_access_key_id（兩個檔案都算）。
  • default-prod：default profile 的帳號在 prodAccounts 裡。帳號看 sso_account_id，沒有時看 role_arn 裡的 12 位數帳號。
  • missing-sso-session:X：profile X 的 sso_session 指到不存在的 [sso-session]。
  • missing-sso-region:S：[sso-session S] 沒有 sso_region。
  • duplicate:A,B：兩個以上的 profile 有相同的 sso_account_id＋sso_role_name，名稱排序後用逗號接起來。

練習 2：完成 evaluate(input, req)，判斷呼叫者能不能對 bucket 做這個請求，回傳 'allowed'、'explicit-deny' 或 'implicit-deny'。covers(statement, req)（Action、Resource 有沒有涵蓋這個請求）與 names(statement, caller)（bucket policy 的 Principal 有沒有包含呼叫者）已經寫好。規則照上面「跨帳號：兩邊都要允許」：

  • 身分型政策、boundary、bucket policy（只看 Principal 包含呼叫者的那幾條）裡，任何一條符合的 Deny → 'explicit-deny'。
  • 身分那一側通過＝身分型政策有符合的 Allow，而且沒有 boundary 或 boundary 也有符合的 Allow。資源那一側通過＝bucket policy 有包含呼叫者且符合的 Allow。
  • 呼叫者的帳號等於 bucketAccount：任一側通過就允許（這種情況題目不會給 boundary）。不同帳號：兩側都要通過。都不符合 → 'implicit-deny'。

練習 3：完成 setup-reporting.ts 的 setupReporting(iam, { partnerAccount, externalId, bucket })，讓會計事務所的帳號讀咖啡店的月報表。用 CreateRoleCommand 建立名為 ROLE_NAME 的 role，AssumeRolePolicyDocument 是信任政策的 JSON 字串：只有一條 Allow，Principal 是 { AWS: 'arn:aws:iam::<partnerAccount>:root' }，Action 是 sts:AssumeRole，條件 StringEquals 的 sts:ExternalId 等於 externalId。再用 PutRolePolicyCommand 加一份 inline policy：只能 s3:GetObject，Resource 是 arn:aws:s3:::<bucket>/reports/*，不要掛其他政策。回傳 role 的 ARN。測試會把 role 與政策讀回來檢查（IAM 回傳的是 URL 編碼的 JSON），再用另一個模擬帳號帶 ExternalId assume 一次。模擬器不檢查信任政策，所以讀回來的內容才是判分依據。

練習 4：審查一份要給開發者的政策。完成 can(policy, action, resource) 與 escalationPaths(policy)。can：有任何涵蓋這個請求的 Deny 就是 false；否則有涵蓋的 Allow 才是 true。一條 statement 涵蓋請求的條件是 Resource 符合，而且有 Action 時其中一個符合請求的動作，有 NotAction 時其中沒有任何一個符合。比對都用寫好的 like（Action 不分大小寫）。escalationPaths 回傳排序過的清單，可能的項目：

  • 'passrole-ec2'：能 iam:PassRole ADMIN_ROLE，而且能 ec2:RunInstances NEW_INSTANCE。
  • 'passrole-lambda'：能 iam:PassRole ADMIN_ROLE，而且能 lambda:CreateFunction NEW_FUNCTION。
  • 'create-policy-version'：能 iam:CreatePolicyVersion ANY_POLICY。
  • 'attach-user-policy'：能 iam:AttachUserPolicy SELF。

練習 5：客服說有顧客的收據 PDF 出現在網路上。你到 CloudTrail 的 Event history 用 bucket 名稱查最近一週，只看到幾筆 PutBucketPolicy、ListBuckets，沒有任何下載紀錄。這代表什麼？

✓ Event history 保留 90 天的管理事件，GetObject 這類資料事件不在裡面，要事先在 trail 開資料事件（另外計費）才查得到。a 是最常見的誤判：查不到不代表沒發生。那幾筆 PutBucketPolicy 反而值得先看：是不是有人改了 bucket policy 讓物件變成公開。d 的天數錯了。

練習 6：平台團隊給 role app-receipt 掛了一個 permission boundary，內容是 Allow s3:* on *。這個 role 的身分型政策只有 logs:PutLogEvents。它能讀 cafe-receipts bucket 的物件嗎（同一個帳號，bucket policy 沒有列它）？

✓ boundary 本身不給權限，只把身分型政策能給的範圍再收窄；這裡身分型政策沒有任何 S3 動作，交集是空的。a 把 boundary 當成另一份 Allow，是最常見的誤解。d 錯在 boundary 並不會讓資源型政策全部失效。

練習 7：會計事務所說：「你們的 bucket policy 已經允許我們的 role analyst 讀 reports/*，可是我們一直收到 AccessDenied。」咖啡店這邊的設定你檢查過是對的。最可能的原因是？

✓ 跨帳號時兩邊各評估一次：資源所在帳號的 bucket policy 要允許，請求方帳號的身分型政策也要允許。請對方在自己的 role 加上 s3:GetObject 咖啡店 bucket 的 reports/*。b 錯在 bucket policy 本來就可以列其他帳號的 principal；d 是最不該做的做法。

常見錯誤

  • 把長期金鑰給外包或寫進 .env：外洩就一直有效。人員用 Identity Center 的 SSO，外部合作用跨帳號 role。
  • 以為 CloudTrail 什麼都記：Event history 只有 90 天的管理事件，S3 物件讀寫、Lambda 呼叫這類資料事件要事先在 trail 開。
  • 以為查不到就是沒發生：先確認查的 region 對不對（IAM 事件大多在 us-east-1）、事件類型有沒有被記錄。
  • 跨帳號只改一邊：bucket policy 允許了，對方的身分型政策也要允許；反過來也一樣。
  • 信任政策的 Principal 寫 *：任何 AWS 帳號都能來 assume，只剩條件在擋。列出對方的帳號或 role。
  • 給多客戶的 SaaS 信任卻不要求 ExternalId：別的客戶可以借 SaaS 的手讀你的資料（confused deputy）。
  • 把 boundary 當成給權限：boundary 只設上限，實際權限是交集。
  • 審 IAM 只搜尋字串 iam:PassRole：iam:*、*、NotAction 都包含它。用評估規則判斷，或交給 Access Analyzer。
  • 用模擬器的成功證明權限正確：模擬器不檢查信任政策與權限，要檢查政策文件本身。

小結

  • 開發者電腦用 SSO profile：[profile X] 指向一個 [sso-session]，aws sso login 之後拿到的是會過期的臨時憑證；config 的 [profile X] 與 credentials 的 [X] 是同一個 profile。沒有 Identity Center 的個人帳號可以用 aws login（CLI 2.32.0 起）。
  • CloudTrail Event history 免費保留 90 天的管理事件、一次查一個 region；長期保存、資料事件、跨帳號集中要建 trail。事故調查用金鑰 ID 與身分 ARN 查出做過的所有事。
  • 同一個帳號內身分型與資源型政策取聯集；跨帳號兩邊各評估一次，都要允許。評估順序：明確拒絕 → RCP／SCP → 資源型 → 身分型 → permission boundary → session policy，後面這些上限只能收窄。
  • role＝信任政策（誰能 assume）＋權限政策（能做什麼）。跨帳號給 role 不給 user；多客戶的服務要求 ExternalId；session 長度 1～12 小時，role chaining 最長 1 小時。
  • 提權路徑：PassRole（能交出高權限 role）＋能建 EC2 或 Lambda、CreatePolicyVersion、替自己掛政策。萬用字元與 NotAction 都要算。讓開發者自建 role 時，用條件強制掛 permission boundary。
  • 模擬器不做權限評估：允不允許用規則推論，本機題檢查政策文件本身。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 8：同事寫了一支清除舊 bucket 的維運腳本，昨天在他的電腦上把正式環境的 bucket 刪了。他說他明明在腳本裡寫了 --region ap-northeast-1。下一版腳本最該加什麼？

✓ 請求作用在憑證所屬的帳號，region 管不到帳號。腳本開頭查出目前的帳號並比對，不符就在動手前停下來，這不靠人記得切換。b 是最多人會選的：人在趕時間時一樣會按 y，而且畫面上也看不出是哪個帳號。d 錯在 SDK 一樣走憑證鏈。（第 1 課）

練習 9：CI 的環境變數裡設了測試帳號的 AWS_ACCESS_KEY_ID、AWS_SECRET_ACCESS_KEY，同一台 runner 的環境裡還留著 AWS_PROFILE=prod，runner 的設定檔也有 prod 這個 profile。部署程式用 SDK v3 的預設憑證鏈，會用哪一組？

✓ SDK v3 的憑證鏈第一步是環境變數，但指定了 profile（AWS_PROFILE 或程式裡的 profile 選項）時整步跳過，只印一行警告。a 是最常見的答案，也是這種事故的來源。修法是一個環境只放一種憑證來源，程式啟動時印出目前的帳號。（第 1 課）

練習 10：咖啡店開帳號第一天設了每月 50 美元的 Budgets 預算與通知。月中測試用的機器忘了關，月底帳單是 400 美元。為什麼預算沒擋住？

✓ 預算只做監看與通知，不會自動停機器。通知寄出後沒人處理，按時間計費的資源會一直累積。a 是常見的誤解：預測門檻讓你更早收到信，但一樣只是信。防範方式是測試完立刻刪資源，並確認通知的收件人會看信。（第 1 課）

練習 11：會計事務所的工程師說：「我們自己的 role 已經允許 s3:GetObject 你們的 cafe-reports/*，為什麼還是 AccessDenied？」你最先要檢查咖啡店這邊的什麼？

✓ 跨帳號存取是兩次評估：對方帳號的身分型政策允許之外，資源所在帳號也要允許，S3 就是 bucket policy 要列出對方。d 是對方那一側的事，不是咖啡店這邊要查的；b 錯在 SCP 管的是咖啡店自己帳號裡的身分，不是別人帳號的身分。（第 2 課）

練習 12：三個月前離職的工程師被懷疑在離職前刪掉了一個 bucket。你到 CloudTrail Event history 查那個 bucket 名稱，什麼都沒有。帳號裡沒有建過任何 trail。接下來怎麼做最實際？

✓ 沒有 trail 時只有 90 天的 Event history，超過就沒了。事件調查的能力要事前準備：建 trail 寫進別人刪不掉的地方。a、b 換 region 或換條件查，一樣受 90 天限制。（第 2 課）

練習 13：這段政策要掛給實習生，讓他部署 Lambda。哪裡會出事？

{ "Effect": "Allow",
  "Action": ["lambda:CreateFunction", "lambda:UpdateFunctionCode", "iam:PassRole"],
  "Resource": "*" }

✓ PassRole 加上能建 Lambda，就能讓函式以任何 role 的身分執行，等於間接拿到那個 role 的權限。修法是 PassRole 的 Resource 寫具體的 role ARN，並加 iam:PassedToService 條件只能交給 Lambda。a 是最常見的誤解：他雖然不直接拿到憑證，但函式裡的程式是他寫的。（第 2 課）

練習 14：咖啡店改用一家報表 SaaS，對方給了他們的 AWS 帳號 ID，請你建一個 role 讓他們 assume。你為什麼還要在信任政策加上 sts:ExternalId 條件？

✓ 這是 confused deputy：被信任的是 SaaS 的整個帳號，ExternalId 讓 SaaS 分清楚「這次替哪個客戶做」。b 是最多人會選的錯誤：ExternalId 不是秘密，它的作用是區分客戶，不是驗證身分。c 錯在沒有條件的信任政策一樣能 assume。（第 2 課）
