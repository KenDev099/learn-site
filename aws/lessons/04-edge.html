階段 2：網路與入口 · 第 4 課

對外入口：Route 53、ACM、ALB 與 CloudFront

咖啡店的官網與 API 要用 cafe.example.com 與 api.cafe.example.com 對外。上線三個月後的某個早上，整站打不開，瀏覽器顯示憑證過期：當初有人清理 DNS 時，刪掉了一筆「看不懂用途」的 CNAME 記錄。同一週，海外的顧客反映菜單圖片要等好幾秒才出現；工程師切換新版 API 時改了 DNS，半小時後還有人連到舊的機器。

上一課處理 VPC 裡面的路；這一課處理從顧客的瀏覽器到你的 VPC 這一段。它由四個服務組成：Route 53（DNS：把名稱查成位址）、ACM（AWS Certificate Manager：申請與續約 TLS 憑證）、ALB（Application Load Balancer：依規則把請求分給後面的程式）、CloudFront（CDN：在離顧客近的地方快取內容）。學完你能解釋上面三件事的原因，並寫出一個能重複執行的 DNS 切換程式。

這課的路線：

  • 一個請求從網址到程式：四個服務各自負責哪一段。
  • Route 53：記錄類型、alias 與 CNAME、TTL、routing policy（練習 1、3）。
  • ACM：DNS 驗證、自動續約的條件、CloudFront 為什麼要 us-east-1。
  • ALB：listener、規則、target group、健康檢查；什麼時候改用 NLB（練習 2）。
  • CloudFront：快取、cache key、invalidation 的代價。
這課會用到：DNS 與記錄類型（devops 課第 4 課：A 記錄把名稱對到 IPv4、CNAME 把名稱對到另一個名稱、TTL 是快取多久）；TLS 憑證與自動續期（devops 課第 5 課）；反向代理（devops 課第 12 課：一個入口依網域與路徑轉給不同的後端）；第 3 課的公有子網路（ALB 放在那裡）。
練習環境：模擬器的 Route 53 只存記錄，不會真的回應 DNS 查詢，也不會依權重挑記錄。DNS 怎麼解析、ALB 怎麼比對規則，在頁面練習裡依規則推論；本機練習檢查你送出的記錄設定。

一個請求從網址到程式

顧客打開 https://api.cafe.example.com/v1/menu，依序經過：

  1. DNS：瀏覽器問 api.cafe.example.com 在哪。查詢最後問到 Route 53，Route 53 回答 ALB 的 IP。
  2. TLS：瀏覽器連到 ALB 的 443，ALB 出示 ACM 簽發的憑證，瀏覽器確認憑證有效、網域相符，才繼續。
  3. 規則：ALB 依 Host、路徑等條件決定這個請求交給哪一組後端（target group），轉給其中一個健康的 cafe-api task。

菜單圖片則多一層：img.cafe.example.com 指到 CloudFront，CloudFront 在世界各地的節點快取圖片，快取裡沒有才回到來源（S3 或 ALB）拿。

所以開場三件事的最小答案：憑證過期是第 2 步，ACM 自動續約需要的 DNS 驗證記錄被刪了；海外很慢是因為圖片沒有經過 CloudFront，每次都回到東京；切換後還連到舊機器是第 1 步，DNS 的答案被快取了 TTL 那麼久。接下來每一節展開一段。

Route 53：記錄、alias 與 TTL

hosted zone（託管區域）是 Route 53 裡一個網域的所有記錄，例如 cafe.example.com 這個 zone。建立 public hosted zone 時，Route 53 會給你四台 name server（NS 記錄），你要到網域註冊商把網域的 NS 設成它們，網際網路上的查詢才會問到 Route 53。

devops 課第 4 課的 A、AAAA、CNAME 在這裡都一樣。Route 53 多了一種 alias 記錄，用來指向 AWS 的資源（ALB、CloudFront、S3 網站、API Gateway，或同一個 zone 裡的另一筆記錄）：

CNAMEalias（類型仍寫 A 或 AAAA）
回答什麼另一個名稱，客戶端的 resolver 要再查一次直接回答目標現在的 IP，客戶端看到的就是 A 記錄
能不能放在 zone 的頂端（apex，例如 cafe.example.com 本身）不能：DNS 規定 apex 要有 SOA、NS 記錄，CNAME 不能和其他記錄共存能
TTL自己設不能自己設，跟著目標
查詢費一般計費指向 ALB、CloudFront 等 AWS 資源時不收查詢費（Route 53 定價頁，2026-11-20 查證）

ALB 的 IP 會變，所以不能把 ALB 的 IP 寫進 A 記錄；子網域可以 CNAME 到 ALB 的 DNS 名稱，apex 只能用 alias。實務上兩者都用 alias。

TTL 是 resolver 可以快取這個答案多久（秒）。改了記錄，已經快取舊答案的人要等 TTL 過完才會再問。開場第三件事就是這樣：記錄的 TTL 是 3600，改完之後最多一小時內還有人連到舊的。所以要換 IP 的記錄，提前（至少一個舊 TTL 的時間之前）把 TTL 調低到 60，切換、觀察穩定之後再調回來。

💡 實務上：DNS 切換前一天先把 TTL 調低
搬機房、換 ALB、換 CDN，都是改 DNS。資深工程師的步驟是：前一天把相關記錄的 TTL 從 3600 調到 60（要等舊的 3600 秒過完才全面生效）；切換當天先改一小部分流量（下面的 weighted），看錯誤率與延遲；確定沒問題再全部切過去，舊環境留著一段時間方便回滾；最後把 TTL 調回較長的值，減少查詢量。也要知道有些 resolver 與應用程式（例如 JVM 的 DNS 快取設定）不完全照 TTL，舊環境不要切完馬上關。

Route 53：routing policy 與健康檢查

同一個名稱可以有好幾筆記錄，由 routing policy（路由政策）決定回答哪一筆：

policy怎麼選用在哪
simple只有一筆，照回大多數記錄
weighted每筆有權重（0～255），依「自己的權重 ÷ 全部的權重」的比例回答；權重 0 的不回答，除非整組都是 0新版 API 先切 10%、藍綠部署
failoverPRIMARY 健康就回它，不健康改回 SECONDARY主站掛了切到維護頁或備援 region
latency回答對查詢者延遲最低的那個 region 的記錄多 region 部署

同名、同類型的多筆記錄靠 SetIdentifier 區分，同一組裡不能重複。failover 要搭配 Route 53 健康檢查：Route 53 從多個地點定期打你的端點，連續失敗就標成不健康。weighted 也可以掛健康檢查，不健康的記錄不會被回答。

改記錄用 ChangeResourceRecordSets，一次送一個 change batch：裡面的每一筆是 CREATE（已存在就失敗）、DELETE，或 UPSERT（不存在就建、存在就改）。同一個 batch 裡的變更一起生效，所以「blue 改成 90、green 改成 10」要放在同一個 batch；分兩次送，中間會有一段時間權重比例不是你要的。練習 3 就是這樣一支切換程式。

練習 1 會把這一節與上一節寫成一個簡化的解析器。先看 weighted 怎麼用一個 0～1 的亂數挑記錄：

ACM：憑證怎麼來、為什麼會過期

DNS 讓瀏覽器找到 ALB，接下來是 TLS（devops 課第 5 課）。ACM 替你申請公開憑證，用在 ALB、CloudFront 這些整合的服務時不收費（ACM 定價頁，2026-11-20 查證；可以匯出私鑰的憑證另外計費）。私鑰留在 AWS 裡，你拿不到，也就不會外洩。

申請時要證明你擁有這個網域，建議用 DNS 驗證：ACM 給你一筆 CNAME 記錄（名稱與值都是一串亂碼），你把它加到 zone 裡，ACM 查得到就簽發。這筆記錄要一直留著，因為續約時 ACM 會再查一次。依官方「Renewal for domains validated by DNS」（2026-11-20 查證）：

  • 目前的憑證有效期 198 天，到期前 45 天 ACM 檢查續約條件（較早簽發、有效期 395 天的憑證是到期前 60 天）。
  • 條件有兩個：憑證正被 AWS 服務使用中（例如掛在 ALB 上），而且每個網域的驗證 CNAME 還在、公開 DNS 查得到。
  • 條件不符時，ACM 會在到期前 30、15、7、3、1 天發 AWS Health 與 EventBridge 事件通知你，不會自己修好。

開場的事故就是第二個條件：那筆「看不懂用途」的 CNAME 就是驗證記錄。另外，你自己匯入 ACM 的憑證（從別的 CA 買的）ACM 不會續約，要自己在到期前重新匯入。

還有一個 region 的規則：CloudFront 用的 ACM 憑證必須在 us-east-1 申請（官方「Requirements for using SSL/TLS certificates with CloudFront」），因為 CloudFront 是全球服務。ALB 用的憑證則要在 ALB 所在的 region。所以一個同時有 CloudFront 與東京 ALB 的網站，常常要申請兩張憑證。

💡 實務上：憑證續約失敗，多半是驗證記錄被刪了
DNS 驗證的 CNAME 名稱長得像 _3f9a….cafe.example.com，清理 DNS 的人很容易當成垃圾刪掉。資深工程師會用 IaC 管理這些記錄（和憑證放在同一個模組，刪不掉也不會被忘記），並訂閱 ACM 的到期事件送到團隊的告警頻道。收到「無法自動續約」的通知時，先查兩件事：驗證記錄還在不在、憑證是不是還掛在服務上。

ALB：listener、規則與 target group

TLS 在 ALB 結束之後，ALB 要決定把請求交給誰。它的角色跟 devops 課第 12 課的 nginx 反向代理一樣，只是由 AWS 代管、跨 AZ。ALB 放在公有子網路（第 3 課），由這幾個部分組成：

  • listener：聽一個 port 與協定，例如 HTTPS:443（掛 ACM 憑證）、HTTP:80。
  • 規則（rule）：listener 底下的一組「條件 → 動作」，每條有一個 priority（1～50000），數字小的先比對，第一條符合的生效；都不符合時用 listener 的預設動作。
  • target group：一組後端（Fargate task 的 IP、EC2 執行個體、Lambda），ALB 對它們做健康檢查，只把請求送給健康的。

規則的條件常用的有四種，同一條規則裡的不同條件要全部符合，同一個條件給多個值時任一個符合即可（官方「Condition types for listener rules」，2026-11-20 查證）：

條件比對什麼大小寫萬用字元
host-headerHost，例如 *.cafe.example.com（不含 cafe.example.com 本身）不分* 任意多個字元、? 一個字元
path-pattern路徑，不含 query string分*、?
http-request-methodGET、POST……分不支援
source-ip來源 IP 的 CIDR—不支援

萬用字元不是正規表示式：/v1/* 的 * 是「任意字元」，. 就是一個點。ALB 另外也支援正規表示式的比對（設定欄位是 RegexValues，跟萬用字元的 Values 分開），練習 2 只處理萬用字元。動作常用的是 forward（轉給 target group）、redirect（例如 HTTP:80 的預設動作轉址到 HTTPS）、fixed-response（直接回固定的狀態碼與內容，例如維護中）。

target group 的健康檢查與 deregistration delay 在 devops 課第 18 課看過：預設每 30 秒打一次健康檢查路徑，連續失敗 2 次標成不健康、連續成功 5 次才恢復；部署移除 task 時，ALB 會等 deregistration delay（預設 300 秒）讓進行中的請求做完。ALB 的 idle timeout 預設 60 秒：連線上 60 秒沒有資料往來就關掉，長時間的 SSE、WebSocket 或慢的報表 API 會被切斷，要調高它或讓伺服器定期送資料。

什麼時候不用 ALB，改用 NLB（Network Load Balancer）？NLB 在 L4 工作，只看 TCP／UDP 的 IP 與 port，不解析 HTTP：

ALBNLB
層級L7（HTTP、HTTPS、gRPC）L4（TCP、UDP、TLS）
能依什麼分流Host、路徑、標頭、方法只有 port
IP會變，要用 DNS 名稱每個 AZ 一個固定 IP，可以指定自己的 Elastic IP
適合一般的 Web、API對方防火牆只允許固定 IP、非 HTTP 的協定（例如 MQTT、遊戲伺服器）、極高的連線數
💡 實務上：ALB 的 idle timeout 與長連線
咖啡店的廚房看板用 SSE 推新訂單，上線後每隔一分鐘斷一次，就是 ALB 60 秒的 idle timeout。做法有兩個：伺服器每 20～30 秒送一個註解行當心跳，或把 ALB 的 idle timeout 調高。後端（Node 的 HTTP server）的 keep-alive timeout 也要比 ALB 的 idle timeout 長，否則後端先關連線，ALB 會偶發 502。這類設定寫進部署文件，換 ALB 時才不會遺失。

CloudFront：把內容放到顧客附近

ALB 在東京，海外的顧客每張圖片都要跨洋。CloudFront 是 AWS 的 CDN：在世界各地有節點（edge location），顧客連到最近的節點，節點有快取就直接回，沒有才回到你設定的來源（origin，例如 S3 bucket 或 ALB）拿，拿到後依規則快取。

  • cache key：決定「哪些請求算同一份內容」。預設只看路徑；把 query string、cookie、標頭加進 cache key，快取會被切得很碎、命中率下降。只放真的會改變內容的部分。
  • TTL：快取多久，由來源回應的 Cache-Control 與 CloudFront 的 cache policy（最小、預設、最大 TTL）一起決定。檔名帶版本雜湊的靜態檔（Vite 的 build 產物）可以快取很久。
  • invalidation（失效）：要求節點丟掉某些路徑的快取。它不是即時的，要一段時間才會在所有節點完成；而且每個帳號每月前 1,000 個路徑免費，之後每個路徑計費，/* 這種萬用字元算一個路徑（官方「Pay for file invalidation」，2026-11-20 查證）。日常部署靠檔名帶版本，不要靠 invalidation。

來源是 S3 時，bucket 不必公開：CloudFront 用 OAC（Origin Access Control）以自己的身分讀私有 bucket，第 7 課部署 Vue 網站時會完整做一次。

這課的練習怎麼對應真的 AWS

DNS 解析、ALB 比對規則、CloudFront 快取都是真的 AWS 在跑的行為，模擬器只存設定：

  • 頁面上的練習（1、2）：把 Route 53 的解析規則與 ALB 的規則比對寫成程式。
  • 本機練習（3）：用 SDK 在模擬器建 hosted zone、改 weighted 記錄，測試讀回記錄，並記下你送出的 change batch。模擬器有些檢查比真的 Route 53 寬鬆（例如同一批裡重複的 SetIdentifier），所以測試直接檢查送出的內容。模擬器也允許同名的 hosted zone 建很多個，這一點跟真的 Route 53 一樣，所以「先找再建」要你自己寫。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。用第 2 課建立的 learn-sandbox profile。建一個 hosted zone、放 weighted 記錄，用 Route 53 的 test-dns-answer 直接問 Route 53 會怎麼回答（不需要真的擁有這個網域，也不用改註冊商的 NS），做完馬上刪掉。網域名稱換成一個你自己的、不容易撞名的名字。

費用：hosted zone 每個月計費，但建立後 12 小時內刪除不收費；DNS 查詢依次數計費（Route 53 定價頁，2026-11-20 查證）。這一節在 12 小時內清除就不會產生 hosted zone 的費用。不建 ALB（每小時計費）、不建 CloudFront。
# 1. 建 hosted zone，記下 Id（/hostedzone/Z…）
aws route53 create-hosted-zone --name cafe-learn-04-<你的名字>.com --caller-reference "$(date +%s)" \
  --profile learn-sandbox --query HostedZone.Id --output text

# 2. 準備一個 change batch：blue 90、green 10，TTL 60（192.0.2.x 是文件專用的位址）
cat > weighted.json <<'EOF'
{ "Changes": [
  { "Action": "UPSERT", "ResourceRecordSet": { "Name": "api.cafe-learn-04-<你的名字>.com", "Type": "A",
    "SetIdentifier": "blue", "Weight": 90, "TTL": 60, "ResourceRecords": [{ "Value": "192.0.2.10" }] } },
  { "Action": "UPSERT", "ResourceRecordSet": { "Name": "api.cafe-learn-04-<你的名字>.com", "Type": "A",
    "SetIdentifier": "green", "Weight": 10, "TTL": 60, "ResourceRecords": [{ "Value": "192.0.2.20" }] } }
] }
EOF

# 3. 一次送出兩筆變更；回傳的 ChangeInfo.Status 從 PENDING 變成 INSYNC 就生效了
aws route53 change-resource-record-sets --hosted-zone-id <Id> --change-batch file://weighted.json --profile learn-sandbox

# 4. 看 zone 裡的記錄：NS、SOA 是 Route 53 自動建的，加上剛才的 blue、green
aws route53 list-resource-record-sets --hosted-zone-id <Id> --profile learn-sandbox \
  --query 'ResourceRecordSets[].[Name,Type,SetIdentifier,Weight]' --output table

# 5. 問 Route 53 會怎麼回答，看 RecordData；多執行幾次觀察
aws route53 test-dns-answer --hosted-zone-id <Id> --record-name api.cafe-learn-04-<你的名字>.com --record-type A \
  --profile learn-sandbox --query RecordData

# 刪記錄：DELETE 的內容要跟現有記錄完全一樣，所以用同一份檔案把 UPSERT 換成 DELETE

練習

練習 1：寫 resolve(zone, name, random)，模擬 Route 53 怎麼回答 A 記錄的查詢，回傳 { ips, cnames }。zone.aws 是 AWS 資源（ALB、CloudFront）的 DNS 名稱與它們目前的 IP。規則：

  • 先檢查：zone 的頂端（名稱等於 zone.apex）有 CNAME 記錄時，丟出錯誤。
  • 查一個名稱：名稱在 zone.aws 裡就回答那些 IP。否則找同名的記錄，沒有就回答空的 ips。
  • 是 CNAME：把目標名稱加進 cnames，繼續查目標名稱。
  • 是 A 記錄：有 weight 的是 weighted，依權重用 random() 挑一筆（權重 0 不選，除非全部是 0，那就平均挑）；有 failover 的，PRIMARY 的 healthy 不是 false 就用它，否則用 SECONDARY；其他只有一筆。挑到的記錄有 alias 就繼續查 alias 的目標（不加進 cnames），否則回答它的 values。
  • 連續查了超過 8 次就丟錯（避免記錄互相指向造成無限迴圈）。

練習 2：寫 wildcard(pattern, value, ignoreCase) 與 matchListener(rules, fallback, req)，模擬 ALB 的 listener 規則。wildcard：* 是任意多個字元、? 是一個字元，其他字元都照字面比對（包括 .），要整個字串相符。matchListener：規則依 priority 由小到大比對，第一條符合的回傳它的 then，都不符合回傳 fallback。一條規則符合的條件是 if 裡每一種有寫的條件都符合，同一種條件的多個值任一個符合即可：

  • host：比對 req.host，不分大小寫。
  • path：比對路徑，req.path 裡 ? 之後的 query string 不算，分大小寫。
  • method：跟 req.method 完全相同（分大小寫，不支援萬用字元）。

練習 3：完成 dns-cutover.ts 的兩個函式，把 api.cafe-04.test 的流量從 blue 慢慢切到 green。ensureZone(r53, name)：用 ListHostedZonesByNameCommand({ DNSName: name }) 找名稱剛好是 name + '.' 的 hosted zone（Route 53 回傳的名稱結尾多一個點），有就回傳它的 Id，沒有才用 CreateHostedZoneCommand 建立（CallerReference 每次要不同）。shiftTraffic(r53, zoneId, { name, blueIp, greenIp, greenWeight })：只送一個 ChangeResourceRecordSetsCommand，ChangeBatch.Changes 放兩筆 UPSERT：A 記錄、SetIdentifier 分別是 'blue' 與 'green'、權重分別是 100 - greenWeight 與 greenWeight、TTL: 60、ResourceRecords: [{ Value: ip }]。測試會呼叫 ensureZone 兩次確認沒有多建，切到 10%、再切到 100% 兩次，讀回記錄並檢查你送出的 change batch。

練習 4：咖啡店的 ALB 在東京，前面要加一個 CloudFront，網域都是 cafe.example.com。你在東京（ap-northeast-1）的 ACM 申請了憑證，掛到 ALB 沒問題，CloudFront 的設定畫面卻選不到它。為什麼？

✓ CloudFront 是全球服務，只讀 us-east-1 的 ACM 憑證；ALB 用的則要在 ALB 所在的 region。所以這個網站要申請兩張。c 錯在題目說憑證已經掛到 ALB，代表已經簽發；b 錯在一張 ACM 憑證可以給同一個 region 的多個服務使用。

練習 5：你把 api.cafe.example.com 的 A 記錄從舊 ALB 改到新 ALB，Route 53 顯示已經生效（INSYNC）。半小時後，仍有一部分顧客連到舊的。記錄原本的 TTL 是 3600。最可能的原因？

✓ resolver 依 TTL 快取答案，改記錄之前已經查過的人，在 TTL 內不會再問。所以要切換的記錄要提前把 TTL 調低。a 是常見的說法，但 Route 53 本身的變更通常幾十秒內就同步到它所有的 name server，慢的是外面的快取。d 錯在一般的 simple 記錄沒有掛健康檢查。

練習 6：合作的金流商要求：「回呼你們的 webhook 時，我們的防火牆只能放行固定的 IP。」咖啡店的 API 目前在 ALB 後面。怎麼做？

✓ NLB 每個 AZ 有一個固定 IP，可以指定自己的 Elastic IP，適合對方只能用 IP 設定白名單的情況。b 是最危險的做法：ALB 的 IP 會隨擴展與維護改變，某天回呼就會失敗。c 管的是「誰能連進來」，題目要的是對方防火牆放行你的固定位址。

常見錯誤

  • apex 用 CNAME 指向 ALB 或 CloudFront：不合法。用 alias。
  • 把 ALB 的 IP 寫進 A 記錄：ALB 的 IP 會變。用 alias 指向 ALB。
  • 要切換時才調低 TTL：舊的 TTL 要先過完，調低要提前做。
  • weighted 切換分兩次請求、或用 CREATE：中間比例不對；CREATE 在記錄已存在時失敗。同一個 change batch、用 UPSERT。
  • 同名的 hosted zone 建了兩個：只有註冊商指向的那個會生效，改另一個沒有用。建之前先找。
  • 刪掉 ACM 的驗證 CNAME：下次續約失敗，憑證過期。驗證記錄要一直留著，用 IaC 管。
  • CloudFront 的憑證申請在 ALB 的 region：CloudFront 只看 us-east-1。
  • ALB 規則以為照建立順序比對：依 priority，數字小的先；比較廣的規則（/api*）的 priority 要比特定的規則大。
  • 把 path-pattern 當正規表示式：它是萬用字元，. 是字面上的點；要正規表示式用另外的 RegexValues。
  • SSE、WebSocket 每分鐘斷一次：ALB idle timeout 預設 60 秒，送心跳或調高。
  • 每次部署都 invalidate /*：不即時，超過免費額度要錢。靜態檔名帶版本雜湊。

小結

  • 請求的路：Route 53 回答位址 → ALB 用 ACM 憑證做 TLS → 依規則轉給 target group；靜態內容經過 CloudFront。
  • Route 53：hosted zone 的 NS 要設到註冊商；alias 指向 AWS 資源、可以放在 apex、不收查詢費；CNAME 不能放 apex。TTL 是快取時間，切換前提前調低。
  • routing policy：weighted（權重比例，0 不回答，除非全部是 0）、failover（搭配健康檢查）、latency。改記錄用 change batch，同一批一起生效，UPSERT 可以重複執行。
  • ACM：DNS 驗證，驗證記錄要一直留著；自動續約要「使用中」且驗證記錄查得到；匯入的憑證不會自動續約；CloudFront 的憑證要在 us-east-1。
  • ALB：listener → 依 priority（小的先）比對規則 → target group 健康檢查。host 不分大小寫、path 分大小寫且不含 query，萬用字元 *、?。要固定 IP 或非 HTTP 協定用 NLB。
  • CloudFront：cache key 越少命中率越高；invalidation 不即時、超過免費額度計費，部署靠檔名版本。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 7：cafe-api 在私有子網路，呼叫外部 API 逾時。你查了它的 route table，0.0.0.0/0 確實指向 nat-0abc，安全群組的出站也全開。下一步查什麼？

✓ NAT 只是第一層，它自己也要有路出去：NAT 必須在公有子網路，那裡的路由指向 internet gateway。NAT 被放進私有子網路時，第一層看起來完全正常。a 是最常見的錯誤：安全群組有狀態，回應自動放行。b 錯在 NAT gateway 本身不掛安全群組。（第 3 課）

練習 8：cafe-api 連 RDS 時 log 立刻出現 ECONNREFUSED 10.20.20.5:5433，不是等很久才失敗。這告訴你什麼？

✓ 被拒絕代表對方主機回了 RST：網路是通的，問題在目的地沒有程式聽那個 port。這裡多半是設定檔把 port 寫成 5433。b、c 是最多人會選的：安全群組與 NACL 擋下時是直接丟掉封包，你看到的會是逾時，不是被拒絕。（第 3 課）

練習 9：資安要求 db 的子網路改用自訂的 NACL：進站只允許來自 app 子網路的 5432、出站只允許到 app 子網路的 5432。套用後 cafe-api 連資料庫全部逾時。為什麼？

✓ 回應封包的目的 port 是客戶端的臨時 port，不是 5432。NACL 不會記得「這是剛才那條連線的回應」，所以出站要開到 app 子網路的 1024–65535。c 剛好說反：NACL 可以寫允許與拒絕，安全群組才只能寫允許。（第 3 課）

練習 10：上個月替 S3 建了 gateway endpoint，這個月的 NAT 處理費只降了一半。cafe-api 跑在兩個 AZ。最可能的原因？

✓ gateway endpoint 是 route table 裡的一條路由，只有掛到的 route table 所屬的子網路會用它。兩個 AZ 各有一張私有 route table，就兩張都要掛。c 錯在 gateway endpoint 不收費；d 是多花錢的做法，從 VPC 內存取不需要 interface endpoint。（第 3 課）

練習 11：要讓 cafe.example.com（沒有 www）指向 ALB。哪個做法正確？

✓ zone 的頂端不能放 CNAME，alias 可以，而且直接回答 ALB 目前的 IP，指向 AWS 資源也不收查詢費。b 是最多人會做的：今天能用，ALB 的 IP 一變就整站掛掉。a 在 apex 不合法。（第 4 課）

練習 12：ACM 寄來通知：api.cafe.example.com 的憑證無法自動續約，30 天後到期。憑證是半年前用 DNS 驗證申請的，正掛在 ALB 上。先查什麼？

✓ 自動續約的條件是憑證使用中、而且每個網域的驗證 CNAME 在公開 DNS 查得到；題目說憑證掛在 ALB 上，剩下就是驗證記錄。這筆記錄名稱像亂碼，常被清理 DNS 的人刪掉。d 錯在 us-east-1 是 CloudFront 的要求，跟續約無關；c 錯在給 ALB 用的 ACM 公開憑證不收費。（第 4 課）

練習 13：ALB 的 HTTPS listener 有這兩條規則。上線後，所有 /api/admin 的請求都進到一般的 API，管理後台的 target group 一個請求都沒收到。哪裡錯了？

priority 100   path-pattern /api/*         → forward tg-api
priority 200   path-pattern /api/admin/*   → forward tg-admin

✓ ALB 依 priority 由小到大比對，第一條符合就停，不會挑「最具體」的。把 admin 那條改成比 100 小的 priority。d 是最多人會選的：最長相符是 route table 的規則（第 3 課），ALB 規則不是這樣算。（第 4 課）
