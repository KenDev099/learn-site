階段 2：網路與入口 · 第 3 課

VPC 與「為什麼連不到」：route table、NAT、安全群組、NACL、VPC endpoint 與排查順序

cafe-api 搬到 AWS 的私有子網路後，一週內來了三張單：結帳時呼叫金流商的 API 一直逾時；staging 環境的 cafe-api 連 RDS 也逾時，可是同一個 VPC 裡另一台機器連得上；月底帳單上 NAT gateway 的「資料處理費」比 RDS 還貴，查下去發現上傳到 S3 的收據圖片全部繞過 NAT。

三件事的共同點是：網路設定在 AWS 裡是好幾層各自獨立的規則，任何一層沒對上，結果都是「連不到」，錯誤訊息卻幾乎一樣。這一課把封包從私有子網路出去要經過的每一關講清楚，給你一個固定的排查順序，最後用 VPC endpoint 讓 S3 的流量不再經過 NAT。

這課的路線：

  • 一個封包要過哪幾關：先拿到排查清單的最小版本。
  • route table：最長前綴、local 路由、沒關聯的子網路用哪一張（練習 1）。
  • NAT gateway：放在哪裡、為什麼要每個 AZ 一個、2025 年起的 regional NAT。
  • 安全群組與 NACL：有狀態與無狀態，回程的臨時 port（練習 2）。
  • VPC endpoint：gateway 與 interface 兩種，怎麼讓 S3 流量不走 NAT（練習 4）。
  • 排查順序、Reachability Analyzer 與 Flow Logs（練習 3）。
這課會用到：devops 課第 18 課的 VPC 架構（公有子網路的 route table 有 0.0.0.0/0 → internet gateway，私有子網路改指 NAT gateway；安全群組有狀態、只寫允許、來源可以寫另一個安全群組）；devops 課第 4 課的 CIDR、port、TCP 連線與逐層排查（客戶端從一個臨時的 port 連到伺服器的固定 port）。
練習環境：模擬器裡的 VPC、route table、安全群組只是資料，沒有真的封包在跑。所以「連不連得到」都在頁面練習裡依規則推論；本機練習只檢查你建的設定對不對。

一個封包要過哪幾關

先看 cafe-api（私有子網路裡的 Fargate task）呼叫金流商 API 時，封包依序經過的地方。每一關都可能是「逾時」的原因：

開場第一張單的最小答案：私有子網路連外逾時，最常見的是 ③ 這個子網路的 route table 沒有 0.0.0.0/0 → NAT，或 ④ NAT 被放進了私有子網路，它自己也出不去。剩下的 ①②⑤ 是安全群組、NACL 與對方。後面每一節講一關，最後再把它們排成固定的排查順序。

關卡掛在哪裡決定什麼
route table子網路封包往哪裡送（有沒有路）
NACL（network ACL）子網路進出子網路的封包放不放行，進、出各自判斷
安全群組（security group，SG）網路介面（ENI）連線准不准建立，回應自動放行
NAT gateway、internet gateway、endpointroute table 的目標出了子網路之後往哪裡去

route table：封包往哪裡送

上面的第 ③ 關。每個子網路都關聯一張 route table（路由表）。表裡每一條路由是「目的地 CIDR → 目標」，目標可以是 local（VPC 內部）、internet gateway（igw-…）、NAT gateway（nat-…）、VPC endpoint、peering（pcx-…）等。三條規則決定封包走哪一條：

  • 最長前綴優先：一個目的地 IP 可能同時符合好幾條，挑前綴最長（網段最小、最具體）的那一條，跟路由在表裡的順序無關。/32 比 /24 優先，0.0.0.0/0 永遠最後。
  • local 路由：每張表都有一條 VPC 自己的 CIDR → local，刪不掉。VPC 裡的機器互相連線走它。
  • 沒有明確關聯的子網路用 main route table：建 VPC 時會自動建一張 main table。新建的子網路如果忘了關聯，就默默用它；很多「這個子網路明明設好了」的問題，都是它其實還在用 main table。

另一個常見的盲點是只看第一層：私有子網路的路由指向 NAT 沒錯，但 NAT 自己所在的子網路也有一張 route table，那張表要有 0.0.0.0/0 → igw，NAT 才出得去。NAT 被誤放進私有子網路時，第一層看起來一切正常，封包卻到 NAT 就停了。

NAT gateway：放在哪裡、放幾個

route table 把封包交給 NAT 之後，NAT 用自己的公開 IP 替私有子網路的機器連外，回應再轉回來；外面無法主動連進來（devops 課第 4 課的 NAT）。傳統的 NAT gateway（官方現在稱為 zonal NAT gateway）有三個要點：

  • 放在公有子網路，那個子網路的 route table 要指向 internet gateway。
  • 它只存在於一個 AZ。兩個 AZ 共用一個 NAT 時，NAT 所在的 AZ 出事，另一個 AZ 的程式也連不出去，而且跨 AZ 的流量另外收費。所以常見的做法是每個 AZ 一個 NAT，每個 AZ 的私有 route table 指向自己 AZ 的 NAT。
  • 計費是每小時（存在就收）加上每 GB 處理量，再加一般的資料傳輸費（VPC 定價頁）。經過 NAT 的每一個位元組都算，包括送到同一個 region 的 S3。

2025 年 11 月 AWS 推出 regional NAT gateway：建立時選 regional 模式並指定 VPC，不需要公有子網路，它會依你的工作負載出現在哪些 AZ 自動擴展，私有子網路的 route table 都指向同一個 NAT ID。限制是擴展到新的 AZ 可能要花上 60 分鐘（這段期間流量跨 AZ 處理），也不支援 private NAT；計費改成每個有它的 AZ 每小時，加上處理量（官方「Regional NAT gateways」文件與定價頁，2026-11-20 查證）。新架構可以優先考慮它；這課的練習與 devops 課第 18 課的架構圖都是 zonal 的做法，因為現有的系統大多還是這樣建。

💡 實務上：NAT 只放一個 AZ，是成本與可用性的取捨
staging、內部工具這類可以停一下的環境，團隊常只放一個 NAT 省每小時的費用，這是合理的取捨，但要寫進文件：那個 AZ 出問題時，所有私有子網路都連不出去。正式環境至少每個 AZ 一個 zonal NAT，或改用 regional NAT。資深工程師看帳單時會把 NAT 拆成「每小時」與「處理量」兩項：處理量高，先查是誰在大量經過 NAT，S3、ECR 拉映像是最常見的兩個，下面的 VPC endpoint 就是解法。

安全群組與 NACL：有狀態與無狀態

路由說的是「有沒有路」，接下來兩關說的是「准不准過」，也就是開場第二張單：連 RDS 逾時，同 VPC 的另一台卻連得上，路由一定沒問題（都是 local），問題在這兩關。

安全群組NACL
掛在哪網路介面（每個 task、每台機器、RDS）子網路（子網路裡所有東西共用）
狀態有狀態：允許了連線，回應自動放行無狀態：去程、回程是兩個不相干的封包，各自判斷
規則只能寫允許；所有規則一起看，有一條允許就過可以寫允許與拒絕；依規則編號由小到大，第一條符合的決定結果；都不符合就被最後的 * 規則拒絕
來源CIDR 或另一個安全群組只能 CIDR
預設新建的群組沒有進站規則（全擋）、出站全開VPC 預設的 NACL 進出全開；自己新建的 NACL 全擋

NACL 無狀態的後果是回程要另外開。cafe-api 從自己的臨時 port（例如 49152）連到 RDS 的 5432，RDS 回應的封包目的 port 是 49152。RDS 所在子網路的 NACL 出站規則若只寫了 5432，回應就被擋掉；cafe-api 那邊看到的是逾時。臨時 port 的範圍依作業系統與服務不同，常見的做法是 NACL 的回程規則開 1024–65535。按執行，看只開 5432 的 NACL 怎麼擋住回應：

安全群組就沒有這個問題：db 的安全群組允許了來自 app 安全群組的 5432，回應自動放行，出站規則是空的也一樣。所以大多數團隊保留預設全開的 NACL，只用安全群組控制；NACL 用在「封鎖某一段 IP」這種需要拒絕規則的場合。真的要自訂 NACL 時，練習 2 的雙向檢查就是你要在腦中跑的流程。

開場那台連不上 RDS 的 staging cafe-api，最後查到的原因是 db 的安全群組來源寫了 production app 的安全群組，staging 的 task 掛的是另一個群組。來源寫安全群組的好處（task 換 IP 不用改規則，devops 課第 18 課）同時也是排查時要對的東西：對的是群組 ID，不是名稱。

💡 實務上：VPC 的 CIDR 撞到，之後就接不起來
NACL、安全群組之外，跨 VPC 的連線還有一關在規劃階段就決定了：兩個 VPC 的 CIDR 重疊就不能 peering，透過 Transit Gateway 也會有路由衝突。公司收購另一家、或要把 staging 接到公司 VPN 時，最常卡在這裡。資深工程師開新 VPC 前會先查公司的位址規劃表（devops 課第 18 課），這比事後重建網路便宜得多。

VPC endpoint：S3 的流量不走 NAT

前面三關處理的是「連不到」；開場第三張單是「連得到，但很貴」。私有子網路連 S3，預設的路是 0.0.0.0/0 → NAT，每 GB 都要付 NAT 處理費。VPC endpoint 讓 VPC 內的流量直接到 AWS 的服務，不經過 NAT 與 internet gateway。有兩種：

gateway endpointinterface endpoint（PrivateLink）
支援的服務只有 S3 與 DynamoDB大多數 AWS 服務（SQS、ECR、Secrets Manager……），S3 也有
怎麼運作在你指定的 route table 加一條路由：目的地是該服務的 prefix list（pl-…，AWS 維護的一組 IP 範圍），目標是 endpoint在子網路裡建一張網路介面（ENI），有私有 IP；開了私有 DNS 時，服務原本的網域名稱在 VPC 裡會解析到這個私有 IP
費用不收費每個 AZ 每小時＋每 GB 處理量
從哪裡用得到只有掛了它的 route table 所屬的子網路VPC 內、以及透過 VPN 或 Direct Connect 連進 VPC 的地方

所以 S3 從 VPC 內存取時用 gateway endpoint：免費，而且 S3 流量從此不經過 NAT。要注意它是掛在 route table 上的：兩個 AZ 有兩張私有 route table，就兩張都要掛，漏掉的那個 AZ 照樣走 NAT。interface endpoint 用在 gateway endpoint 沒有的服務，或要從公司內網透過 VPN 存取 S3 的時候。

每個 endpoint 還可以掛一份 endpoint policy，控制「透過這個 endpoint 能存取哪些資源」。不設的話預設允許全部。把 Resource 限定在自己的 bucket，就算 VPC 裡的程式被入侵，攻擊者也不能透過這條路把資料寫到他自己的 bucket：

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
    "Resource": ["arn:aws:s3:::cafe-uploads-prod", "arn:aws:s3:::cafe-uploads-prod/*"]
  }]
}

endpoint policy 是另一道上限，不會給權限：程式的 role 還是要有自己的 S3 權限（第 2 課的「只能收窄」）。Principal 在 endpoint policy 裡常寫 *，因為要限制的是「經過這裡能碰什麼」，誰能做什麼交給 IAM。

💡 實務上：S3 走 gateway endpoint，是 VPC 開好後的第一件事
上傳收據、存菜單圖片、拉部署檔，這些流量走 NAT 時每 GB 都在付處理費，改走 gateway endpoint 不用改任何程式碼，只是在 route table 多一條路由，也不收費。資深工程師會在建 VPC 的 IaC 模組裡直接帶上 S3 與 DynamoDB 的 gateway endpoint，並在 endpoint policy 列出允許的 bucket。ECR 拉映像需要的是 interface endpoint（另外計費），要不要建，看拉映像的流量經過 NAT 的費用有多少。

排查順序：逾時先查網路，被拒絕先查程式

每一關都看過之後，把它們排成一個固定的順序。連線失敗時，先看錯誤長什麼樣子：

  • 逾時（timeout）：封包送出去沒有任何回應。安全群組、NACL 擋下封包時是直接丟掉、不回應，路由不通也一樣，所以逾時多半是網路層的問題。
  • 連線被拒絕（connection refused）：對方主機收到了，回了 TCP RST，代表網路是通的，但那個 port 上沒有程式在聽。查目的地的程式有沒有啟動、聽在哪個位址（devops 課第 4 課的 127.0.0.1 與 0.0.0.0）。

逾時就照這個順序，從離自己近的查起：

  1. DNS：名稱解析成什麼 IP？RDS 的端點名稱在 VPC 裡應該解析成私有 IP；解析成公開 IP 或解析不出來，後面都不用查。
  2. 路由：來源子網路的 route table（記得檢查是不是在用 main table）對這個 IP 走哪一條？目標是 NAT 的話，NAT 所在子網路的路由也要看。
  3. NACL，雙向：來源子網路的出站與回程進站、目的子網路的進站與回程出站。
  4. 安全群組：來源的出站、目的地的進站（來源寫的是 CIDR 還是安全群組 ID，對得上嗎）。
  5. 目的地的程式：有沒有在聽、聽在哪個位址與 port。
  6. 作業系統的防火牆：EC2 上自己開的 iptables 之類的規則（Fargate、RDS 沒有這一層）。

AWS 有兩個工具幫你做前四步：

  • VPC Reachability Analyzer：給一個來源（例如某個 task 的網路介面）與目的地，它分析設定（不送真的封包），告訴你路徑通不通，不通的話卡在哪一個元件。每做一次分析計費一次。
  • VPC Flow Logs：記錄網路介面上實際流過的連線，寫到 CloudWatch Logs 或 S3。預設格式（版本 2）每一行依序是：version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes start end action log-status。action 是 ACCEPT 或 REJECT；log-status 是 NODATA（這段時間沒有流量）或 SKIPDATA（有紀錄被跳過）時，其他欄位是 -。也可以自訂欄位與順序，讀之前先確認格式。

讀 Flow Logs 判斷是哪一關擋的，靠的是「有狀態與無狀態」的差別。看 db 那張網路介面上同一條連線的兩個方向：

去程（app → db:5432）回程（db:5432 → app 的臨時 port）代表什麼
REJECT（沒有）進站被擋：db 的安全群組或 NACL 進站規則
ACCEPTREJECT回程被擋：只可能是 NACL（安全群組會自動放行回應）
ACCEPTACCEPT網路通了；連不上要查程式本身

官方文件提醒，連線關閉後才抵達的封包也可能被記成 REJECT，所以看的是重複出現的模式，不是單一一行。練習 3 會把這張表寫成程式。

💡 實務上：先問「是逾時還是被拒絕」，再開 Flow Logs
同事說「連不到資料庫」時，資深工程師第一個問題是錯誤訊息原文：timeout 與 connection refused 的查法完全不同。接著用 Reachability Analyzer 跑一次 app 到 db 的路徑，通常幾分鐘內就能指出是哪一條規則。Flow Logs 適合事後與長期觀察（例如誰在掃你的 port），但要先開才有，寫到 CloudWatch Logs 也會產生 log 的費用，記得設保存天數。

這課的練習怎麼對應真的 AWS

前面的每一關在真的 AWS 都是實際的封包處理；模擬器只存設定，不會依規則擋任何東西。所以：

  • 頁面上的練習（1～3）：把路由、NACL＋安全群組、Flow Logs 的判斷寫成程式，餵給它設定或 log，推論連不連得到、卡在哪。
  • 本機練習（4）：用 SDK 在模擬器建安全群組與 gateway endpoint，測試把設定讀回來檢查。模擬器建 gateway endpoint 時，也會在 route table 加上指向 S3 prefix list 的路由，跟真的 AWS 一樣，可以在 DescribeRouteTables 看到。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。用第 1 課開的獨立練習帳號與第 2 課建立的 learn-sandbox profile。做完看 route table 裡多出來的 prefix list 路由，再把東西清掉。

費用：VPC、route table、安全群組與 gateway endpoint 都不收費（VPC 定價頁，2026-11-20 查證）。這一節刻意不建 NAT gateway（每小時＋每 GB 處理量）、interface endpoint（每個 AZ 每小時＋每 GB）、Reachability Analyzer（每次分析計費）。
# 1. 建 VPC，記下 VpcId
aws ec2 create-vpc --cidr-block 10.30.0.0/16 --profile learn-sandbox \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=cafe-learn-03}]' --query Vpc.VpcId --output text

# 2. 建一張私有 route table，記下 RouteTableId
aws ec2 create-route-table --vpc-id <VpcId> --profile learn-sandbox --query RouteTable.RouteTableId --output text

# 3. 建 S3 gateway endpoint 掛到這張 route table，記下 VpcEndpointId
aws ec2 create-vpc-endpoint --vpc-id <VpcId> --vpc-endpoint-type Gateway \
  --service-name com.amazonaws.ap-northeast-1.s3 --route-table-ids <RouteTableId> \
  --profile learn-sandbox --query VpcEndpoint.VpcEndpointId --output text

# 4. 看路由：除了 local，多了一條 DestinationPrefixListId 是 pl-… 、GatewayId 是 vpce-… 的路由
aws ec2 describe-route-tables --route-table-ids <RouteTableId> --profile learn-sandbox --query 'RouteTables[].Routes'

# 5. 建 app 與 db 兩個安全群組，db 只允許來自 app 群組的 5432
aws ec2 create-security-group --group-name cafe-learn-03-app --description 'cafe-api' --vpc-id <VpcId> --profile learn-sandbox --query GroupId --output text
aws ec2 create-security-group --group-name cafe-learn-03-db --description 'postgres' --vpc-id <VpcId> --profile learn-sandbox --query GroupId --output text
aws ec2 authorize-security-group-ingress --group-id <db 的 GroupId> --profile learn-sandbox \
  --ip-permissions 'IpProtocol=tcp,FromPort=5432,ToPort=5432,UserIdGroupPairs=[{GroupId=<app 的 GroupId>}]'

# 6. 確認 db 的規則來源是安全群組，不是 CIDR
aws ec2 describe-security-groups --group-ids <db 的 GroupId> --profile learn-sandbox --query 'SecurityGroups[].IpPermissions'

清除

aws ec2 delete-vpc-endpoints --vpc-endpoint-ids <VpcEndpointId> --profile learn-sandbox
aws ec2 delete-security-group --group-id <db 的 GroupId> --profile learn-sandbox
aws ec2 delete-security-group --group-id <app 的 GroupId> --profile learn-sandbox
aws ec2 delete-route-table --route-table-id <RouteTableId> --profile learn-sandbox
aws ec2 delete-vpc --vpc-id <VpcId> --profile learn-sandbox
aws ec2 describe-vpcs --filters Name=tag:Name,Values=cafe-learn-03 --profile learn-sandbox --query 'Vpcs[].VpcId'   # 確認：回傳 []

endpoint 刪除需要一點時間，刪 route table 或 VPC 時出現仍有相依資源的錯誤，等一下再執行一次。

練習

練習 1：完成 routeFor(vpc, subnet, ip) 與 diagnoseEgress(vpc, subnet, ip)。inCidr 與 prefix 已經寫好。routeFor：找出子網路用的 route table（subnets 裡有它的那一張，沒有就用 main: true 的那張），在符合 ip 的路由裡挑前綴最長的，回傳它的 target；沒有符合的回傳 null。diagnoseEgress：私有子網路裡沒有公開 IP 的程式要連到網際網路上的 ip，回傳：

  • 'no-route'：沒有符合的路由，或目標不是 internet gateway（igw- 開頭）也不是 NAT（nat- 開頭）。
  • 'igw-without-public-ip'：直接指向 internet gateway，但這個程式沒有公開 IP，出不去。
  • 指向 NAT 時，到 vpc.nats 找出 NAT 所在的子網路，再用那個子網路的 route table 查同一個 ip：目標是 igw- 開頭就是 'ok'，否則是 'nat-without-igw'。

練習 2：cafe-api（client）從臨時 port clientPort 連到 db（server）的 port，兩者在不同的子網路。完成 naclAllows 與 roundTrip。naclAllows(rules, ip, port)：規則依編號 n 由小到大，第一條 cidr 包含 ip、port 在 from～to 之間的規則決定結果，都不符合就是 false。sgAllows 已經寫好。roundTrip 依序檢查，回傳第一個擋下的關卡，全部通過回傳 'ok'：

  1. 'client-sg-out'：client 的安全群組出站，允許連到 server 的 port。
  2. 'client-nacl-out'：client 子網路的 NACL 出站，目的地 server 的 IP、port。
  3. 'server-nacl-in'：server 子網路的 NACL 進站，來源 client 的 IP、目的 port。
  4. 'server-sg-in'：server 的安全群組進站，來源 client、port。
  5. 'server-nacl-out'：回程，server 子網路的 NACL 出站，目的地 client 的 IP、clientPort。
  6. 'client-nacl-in'：回程，client 子網路的 NACL 進站，來源 server 的 IP、目的 clientPort。

安全群組有狀態，回程不檢查。

練習 3：寫 parseFlowLogs(text)，從 Flow Logs 找出被擋的連線。text 的第一行是欄位名稱（空白分隔，順序可能是自訂的），之後每行一筆紀錄。log-status 不是 OK 的行整行跳過。對每一筆 action 是 REJECT 的紀錄：

  • 如果有一筆 ACCEPT 的紀錄剛好是它的反方向（對方的 srcaddr、dstaddr、srcport、dstport 跟它的 dstaddr、srcaddr、dstport、srcport 一樣），它是那條連線的回程被擋：{ src, dst, port } 用那筆 ACCEPT 的 srcaddr、dstaddr、dstport，verdict 是 'return-rejected'。
  • 否則是進站被擋：用它自己的 srcaddr、dstaddr、dstport，verdict 是 'inbound-rejected'。

相同 src、dst、port、verdict 的合成一項，count 是 REJECT 的筆數；結果依 src、dst、port 排序（字串用 localeCompare，port 用數字）。

練習 4：完成 lockdown.ts 的 lockdown(ec2, { vpcId, privateRouteTableIds, bucket })，把開場的三件事在設定上做對。用 CreateSecurityGroupCommand 在 vpcId 建三個安全群組 cafe-03-alb、cafe-03-app、cafe-03-db（Description 必填，用英文），再用 AuthorizeSecurityGroupIngressCommand 各加一條進站規則：alb 允許 tcp 443 來自 0.0.0.0/0；app 允許 tcp 3000，來源用 UserIdGroupPairs: [{ GroupId: alb 的 ID }]；db 允許 tcp 5432，來源是 app 的安全群組。然後用 CreateVpcEndpointCommand 建 S3 的 gateway endpoint：VpcEndpointType: 'Gateway'、ServiceName 是 com.amazonaws.<region>.s3（region 用 await ec2.config.region()）、掛到 privateRouteTableIds 的每一張、PolicyDocument 只允許 s3:GetObject、s3:PutObject、s3:ListBucket 這個 bucket（Resource 同時列 bucket 本身與 bucket/*）。回傳四個 ID。測試每次會建一個新的 VPC 與兩張私有 route table 傳給你，再把設定讀回來檢查。

練習 5：cafe-api 呼叫金流商 API，log 裡是 ETIMEDOUT。同事馬上去看 cafe-api 有沒有在聽 3000 port。你會先查什麼？

✓ 逾時代表封包沒有得到任何回應，多半是網路層：從離自己近的路由查起，連外要經過 NAT 兩層路由。a 是查「connection refused」的方法，而且查的是自己的 port，跟連出去無關；d 錯在主動連出去看的是出站規則，回應會自動放行。

練習 6：cafe-api 在私有子網路，每天上傳大量收據到同一個 region 的 S3，NAT 的處理費很高。要讓這些流量不經過 NAT，選哪個？

✓ gateway endpoint 不收費，在 route table 加一條到 S3 prefix list 的路由，S3 流量就不走 NAT。要記得每一張私有 route table 都掛。a 也能讓流量不走 NAT，但 interface endpoint 每個 AZ 每小時加每 GB 計費，從 VPC 內存取時沒有必要；它適合從公司內網透過 VPN 存取。d 只限制來源，不會改變流量走的路。

練習 7：db 的安全群組允許來自 app 安全群組的 5432 進站，出站規則被同事全部刪光了。cafe-api 連得上資料庫嗎？

✓ 安全群組追蹤連線狀態，回應屬於已允許的連線，不看出站規則。出站規則只管 db 主動發起的連線。c 是把 NACL 的規則套到安全群組上，這是最常見的混淆：無狀態、要開臨時 port 的是 NACL。

常見錯誤

  • 用路由在表裡的順序判斷：route table 依最長前綴挑路由，跟順序無關。
  • 新子網路忘了關聯 route table：它會用 main table，看起來設好了其實沒有。建子網路時一起明確關聯。
  • NAT 放進私有子網路：私有子網路的路由指向它沒問題，它自己卻沒有到 internet gateway 的路由。zonal NAT 一定放公有子網路，或改用不需要公有子網路的 regional NAT。
  • 兩個 AZ 共用一個 NAT 卻沒寫進文件：那個 AZ 出事時全部連不出去，還多了跨 AZ 流量費。
  • NACL 的出站照抄進站規則：回應的目的 port 是對方的臨時 port，要另外開（常見 1024–65535）。
  • 以為 NACL 跟安全群組一樣，有一條允許就過：NACL 依編號第一條符合的決定，排在前面的拒絕會擋掉後面的允許。
  • db 的安全群組來源寫 VPC 的 CIDR：VPC 裡任何一台被入侵的機器都能連資料庫。來源寫 app 的安全群組。
  • S3 流量走 NAT：每 GB 付處理費。建 gateway endpoint，每張私有 route table 都掛，endpoint policy 只列自己的 bucket。
  • 逾時時去查程式有沒有在聽：逾時先查網路層；connection refused 才是程式沒在聽。

小結

  • 封包出私有子網路要過：安全群組 → NACL → route table → NAT（以及 NAT 自己的路由）→ internet gateway。任何一關不通都是逾時。
  • route table 依最長前綴挑路由；每張表都有 VPC CIDR → local；沒有明確關聯的子網路用 main table。
  • zonal NAT gateway 放公有子網路、只在一個 AZ，正式環境每個 AZ 一個；2025-11 起的 regional NAT 不需要公有子網路、自動跨 AZ。NAT 依小時與處理量計費。
  • 安全群組掛在網路介面、有狀態、只寫允許；NACL 掛在子網路、無狀態、依編號第一條符合的決定，回程要開臨時 port。
  • gateway endpoint（S3、DynamoDB）免費、掛在 route table；interface endpoint 是子網路裡的 ENI、計費。endpoint policy 只能收窄。
  • 排查：先分逾時與被拒絕；逾時照 DNS → 路由 → NACL 雙向 → 安全群組 → 程式 → OS 防火牆。Reachability Analyzer 分析設定，Flow Logs 記錄實際流量：去程 ACCEPT、回程 REJECT 是 NACL 擋了回程。
