階段 3：運算 · 第 5 課

容器上 AWS：ECR、ECS Fargate、task role 與 execution role

咖啡店的多租戶後台（作品專案課做的 NestJS API，以下叫 cafe-api）已經有 Dockerfile，在本機用 docker compose up 跑得好好的。搬上 AWS 的第一次部署，主控台一直顯示 task 從 PENDING 變成 STOPPED，再自動補一個，又 STOPPED。第一次的訊息是 CannotPullContainerError … i/o timeout，修好之後換成 ResourceInitializationError: unable to pull secrets or registry auth … AccessDeniedException。同事把 S3 權限加進「那個 role」，還是不行。

這一課把容器放上 AWS 的那一段補完整：映像放在 ECR，用 ECS 的 Fargate 跑起來，讀懂 task definition 與 service 的每個重要欄位，分清楚兩個長得很像的 role，學會 task 停下來時先看哪裡。最後比較「自己管 EC2 機器」與 Fargate 的取捨。

這課的路線：

  • ECS 的四個名詞與 ECR：從 compose 對應過來，映像要用不會變的參照。
  • task definition：CPU 與記憶體、網路模式、log、secret 怎麼寫。
  • execution role 與 task role：誰在什麼時候用哪一個；task STOPPED 時怎麼判斷是哪一層的問題。
  • service：維持 N 個 task、滾動部署的 100／200、circuit breaker 自動回滾。
  • EC2 還是 Fargate：自己管機器要多做哪些事（instance profile、IMDSv2、Session Manager）。
這課會用到：devops 課第 18 課的 ECS 對照表（ECR＝映像倉庫、task definition＝compose 的 service 定義、service＝維持 N 個 task、ALB＋target group＝反向代理）；devops 課第 19 課的 role（信任政策說誰能扮演、權限政策說能做什麼）；第 3 課的私有子網路（對外要經過 NAT gateway 或 VPC endpoint）；第 4 課的 ALB target group 與健康檢查。
練習環境：模擬器只記錄 ECS 的設定，不會真的拉映像、跑容器，也不檢查 role 的權限。所以本機題檢查「設定寫對沒有」，task 會不會停下來用頁面上的練習推論。

從 compose 到 ECS：四個名詞與 ECR

devops 第 18 課已經把 compose 和 ECS 一一對上，這裡只補上這課要用的精確定義：

名詞是什麼compose 裡對應的東西
cluster一群 task 的邏輯分組，用 Fargate 時它只是個名字，沒有機器要管一個 compose 專案
task definition描述「怎麼跑」的 JSON：映像、CPU、記憶體、port、環境變數、log、role。每次修改都產生新的 revision（cafe-api:1、cafe-api:2），舊的不會被覆蓋services.api 那一段
task照某個 revision 跑起來的一份實體（裡面可以有一個或多個容器）一個執行中的容器
service讓 N 個 task 一直活著：掛掉就補、部署時逐步換版、把 task 註冊進 ALB 的 target group--scale api=3 加上 restart: always

Fargate 是 ECS 的一種執行方式（launch type）：你只說「這個 task 要 0.5 vCPU、1 GB」，AWS 找地方跑它，你看不到也不用修補底下的機器。另一種是 EC2 launch type，task 跑在你自己管的 EC2 機器上，最後一節比較。

映像放在 ECR（Elastic Container Registry），每個應用程式一個 repository，網址長這樣：

123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/cafe-api:2026-11-20-a1b2c3d     用 tag
123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/cafe-api@sha256:3f8a…          用 digest

tag 是可以移動的標籤，digest 是映像內容的雜湊（devops 課第 16 課）。task definition 裡寫 :latest 的問題是：同一個 revision 在不同時間啟動的 task 可能拉到不同的映像，出事時說不清楚正式環境跑的是哪一版，回滾到「上一個 revision」也拉回同一個 latest。repository 有三個設定值得一開始就開：

  • tag 不可變（imageTagMutability: IMMUTABLE）：已經存在的 tag 不能再被推上不同的映像，:2026-11-20-a1b2c3d 永遠指同一個東西。要部署新版就推新 tag。
  • push 時掃描（scanOnPush）：推上去時檢查作業系統套件的已知漏洞。結果在 aws ecr describe-image-scan-findings 看，CI 可以在發現嚴重漏洞時擋下部署。
  • lifecycle policy：自動刪舊映像，例如「沒有 tag 的映像 7 天後刪除」「只保留最新 30 個」。不設的話，每次 CI 推一版，儲存費用就一直累積。
import { CreateRepositoryCommand } from '@aws-sdk/client-ecr'

await ecr.send(new CreateRepositoryCommand({
  repositoryName: 'cafe-api',
  imageTagMutability: 'IMMUTABLE',
  imageScanningConfiguration: { scanOnPush: true },
}))
💡 實務上：CI 推映像、部署用 digest
常見的做法是 CI 用 git commit 當 tag 推到 ECR（作品專案課第 17 課的流程），推完從回應拿到 digest，註冊新的 task definition 時寫 repository@sha256:…。這樣 task definition 的每個 revision 都精確對應一個映像，回滾就是「service 改回上一個 revision」。被問「線上現在跑哪一版」時，aws ecs describe-services 查 revision、再查它的 image，一路追得到 commit。

task definition：CPU、記憶體、網路、log 與 secret

有了映像，接著寫「怎麼跑它」。下面是 cafe-api 的 task definition（只列這課要講的欄位）：

{
  "family": "cafe-api",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "512",                      ← 0.5 vCPU（1024 單位＝1 vCPU）
  "memory": "1024",                  ← MiB
  "executionRoleArn": "arn:aws:iam::123456789012:role/cafe-api-execution",
  "taskRoleArn": "arn:aws:iam::123456789012:role/cafe-api-task",
  "containerDefinitions": [{
    "name": "api",
    "image": "123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/cafe-api@sha256:3f8a…",
    "portMappings": [{ "containerPort": 3100 }],
    "environment": [{ "name": "PORT", "value": "3100" }],
    "secrets": [{ "name": "APP_DATABASE_URL",
                  "valueFrom": "arn:aws:secretsmanager:ap-northeast-1:123456789012:secret:cafe/db-AbCdEf" }],
    "logConfiguration": { "logDriver": "awslogs", "options": {
      "awslogs-group": "/ecs/cafe-api", "awslogs-region": "ap-northeast-1", "awslogs-stream-prefix": "api" } }
  }]
}

由上往下：

  • cpu 與 memory：Fargate 只接受規定的組合，寫錯會在註冊時被拒絕。下表照官方「Task CPU and memory」（2026-11-20 查證），查表用，不用背；練習 2 會用到：
    cpu可以搭配的 memory
    256（.25 vCPU）512 MiB、1 GB、2 GB
    512（.5 vCPU）1 GB～4 GB，每次 1 GB
    1024（1 vCPU）2 GB～8 GB，每次 1 GB
    2048（2 vCPU）4 GB～16 GB，每次 1 GB
    4096（4 vCPU）8 GB～30 GB，每次 1 GB
    8192（8 vCPU）16 GB～60 GB，每次 4 GB（Linux 平台 1.4.0 以上）
    16384（16 vCPU）32 GB～120 GB，每次 8 GB（Linux 平台 1.4.0 以上）
    32768（32 vCPU）60 GB、120 GB、244 GB（Linux 平台 1.4.0 以上）
  • networkMode: awsvpc：Fargate 只能用這個模式。每個 task 拿到自己的網路介面（ENI，Elastic Network Interface）和私有 IP，所以安全群組直接套在 task 上，跟第 3 課的 EC2 一樣判斷。
  • environment 與 secrets：environment 是明文，寫在 task definition 裡，任何能讀 task definition 的人都看得到。密碼、連線字串放 secrets：valueFrom 寫 Secrets Manager 的 secret 或 Parameter Store 參數的 ARN，task 啟動時 ECS 去讀出來，變成容器裡的環境變數。程式完全不用改，process.env.APP_DATABASE_URL 照樣讀得到。Secrets Manager 本身留到第 9 課。
  • logConfiguration：awslogs 把容器的 stdout／stderr 送到 CloudWatch Logs 的 /ecs/cafe-api。沒設的話 task 一停，最後那幾行錯誤就跟著消失，下一節的除錯就斷了線索。log group 記得設保留天數，不然 log 永遠留著、永遠收費。

同一個 family 再註冊一次就是新 revision，service 指向哪個 revision，跑的就是哪一份設定。

execution role 與 task role：誰在什麼時候用哪一個

上面的 task definition 有兩個 role，開場事故就卡在這裡。差別在於是誰在呼叫 AWS：

execution role（executionRoleArn）task role（taskRoleArn）
誰用ECS／Fargate 的代理程式（agent），在你的容器啟動之前你的程式，在容器裡執行時
用來做什麼從私有 ECR 拉映像、把 log 寫進 CloudWatch Logs、讀 secrets 裡的值上傳收據到 S3、送訊息到 SQS、呼叫任何 AWS API
權限從哪來官方的 AmazonECSTaskExecutionRolePolicy（ECR 與 Logs），讀 secret 要另外加 secretsmanager:GetSecretValue；用自訂 KMS key 加密的 secret 再加 kms:Decrypt你依程式需要寫的最小權限
沒給或權限不夠時task 起不來：STOPPED，原因是 CannotPullContainerError 或 ResourceInitializationErrortask 跑得起來，程式呼叫 AWS 時拿到 AccessDenied，看程式自己的 log

兩個 role 的信任政策都是讓 ecs-tasks.amazonaws.com 扮演（devops 第 19 課）。程式怎麼拿到 task role 的憑證，就是第 1 課憑證鏈的 container 那一步：ECS 在容器裡設好 AWS_CONTAINER_CREDENTIALS_RELATIVE_URI，SDK 自動去那裡拿臨時憑證，程式碼 new S3Client({}) 不用寫任何金鑰。execution role 的憑證則只給代理程式用，容器裡拿不到（官方文件明講）。

所以開場的同事加錯地方了：ResourceInitializationError … unable to pull secrets 是 execution role 讀不到 Secrets Manager，跟 task role 的 S3 權限無關。分清楚兩個 role 之後，task STOPPED 時照這個順序判斷：

  1. 看 stoppedReason：aws ecs describe-tasks --cluster cafe --tasks <id> --query 'tasks[0].[stoppedReason,containers[0].reason,containers[0].exitCode]'，或主控台 task 頁面的 Stopped reason。STOPPED 的 task 只保留一段時間就查不到，部署出錯時要盡快看。
  2. 記憶體：OutOfMemoryError: Container killed due to memory usage，或容器的 exit code 是 137（被 SIGKILL 砍掉，devops 課第 3 課）：程式用的記憶體超過 task 的 memory。
  3. 啟動前失敗：CannotPullContainerError、ResourceInitializationError。訊息裡有 AccessDenied、not authorized 是 execution role；是 i/o timeout、context deadline exceeded 這類逾時是網路（下一段）；網路與權限都對，多半是映像名稱或 tag 打錯。
  4. 啟動後才停：Essential container in task exited，表示程式自己結束了。去 CloudWatch Logs 看最後幾行：程式呼叫 AWS 被拒（AccessDenied）是 task role，其他是程式本身的錯（連不上資料庫、設定缺漏）。

啟動前的「網路」要多想一步：拉映像、讀 secret、寫 log 都是 task 對 AWS 服務發出的 HTTPS 請求，走的是 task 所在子網路的路由（第 3 課）。task 要能連到這些服務，有三種情況：

  • 公有子網路：task 必須拿到公開 IP（assignPublicIp: ENABLED），才能經過 internet gateway 出去。設成 DISABLED 就連不出去，這是最常見的拉不到映像。
  • 私有子網路＋NAT gateway：經過 NAT 出去，不需要公開 IP。
  • 私有子網路、沒有 NAT：要有 VPC endpoint。拉 ECR 映像需要 ecr.api、ecr.dkr 兩個 interface endpoint，加上 S3 的 gateway endpoint（ECR 的映像層存在 S3）；用 awslogs 還要 logs，有 secrets 還要 secretsmanager（或 ssm）。少一個就卡在那一步。

練習 1 把這整套判斷寫成函式。

💡 實務上：兩個 role 搞混是最常見的 STOPPED 原因
新手最常見的修法是「把所有權限都加到同一個 role，兩個欄位填同一個」。能動，但等於讓應用程式的程式碼也拿得到讀所有 secret 的權限；應用程式被打進去時，損害範圍一起變大。資深的做法是兩個分開、各自最小：execution role 只能讀這個服務自己的 secret（Resource 寫到那幾個 ARN），task role 只有程式真的會呼叫的動作。資安審查會問的就是「這個 task 被攻破，攻擊者拿得到什麼」。

service：維持 N 個 task、滾動部署與自動回滾

task definition 說怎麼跑一個 task，service 負責「一直有 N 個在跑」。cafe-api 的 service：

await ecs.send(new CreateServiceCommand({
  cluster: 'cafe', serviceName: 'cafe-api',
  taskDefinition: 'arn:aws:ecs:ap-northeast-1:123456789012:task-definition/cafe-api:7',
  desiredCount: 4,
  launchType: 'FARGATE',
  networkConfiguration: { awsvpcConfiguration: {
    subnets: ['subnet-private-a', 'subnet-private-c'],     // 兩個 AZ 的私有子網路
    securityGroups: ['sg-app'],                           // 只允許 ALB 的 SG 連進來（第 3 課）
    assignPublicIp: 'DISABLED',
  } },
  loadBalancers: [{ targetGroupArn: '…/cafe-api', containerName: 'api', containerPort: 3100 }],
  healthCheckGracePeriodSeconds: 60,
  deploymentConfiguration: {
    minimumHealthyPercent: 100, maximumPercent: 200,
    deploymentCircuitBreaker: { enable: true, rollback: true },
  },
}))
  • subnets：給兩個 AZ 的子網路，ECS 會把 task 分散放，一個 AZ 出事還有另一半。
  • loadBalancers：service 自動把每個 task 的 IP 註冊進第 4 課的 target group，task 停掉時先移出、等 deregistration delay 再停（devops 第 18 課）。healthCheckGracePeriodSeconds 是剛啟動的 task 有多久不被 ALB 健康檢查判死，NestJS 啟動要連資料庫、跑初始化時要給夠。
  • minimumHealthyPercent／maximumPercent：滾動部署時，健康的 task 數不能低於 desiredCount 的百分之幾（無條件進位），所有 task 加起來不能超過百分之幾（無條件捨去）。
  • deploymentCircuitBreaker：新版的 task 一直起不來或健康檢查一直失敗，累積到門檻就把這次部署標成 FAILED；rollback: true 會自動退回最近一次成功（COMPLETED）的部署。預設門檻是 desiredCount 的 50%、最少 3 次、最多 200 次（官方文件，2026-11-20 查證）。沒開的話，壞掉的版本會一直被重啟，停在一半舊一半新。

按執行，看 desiredCount 4、100／200 的部署怎麼進行（簡化：每一步新 task 都健康）：

100／200 是「先開新的、再關舊的」，部署中服務容量不會下降，代價是那段時間要付雙倍的 task 費用。改成 50／100 就是「先關一半舊的、再開新的」，不用多付錢，但部署中只剩一半容量。尖峰時段部署選前者。

💡 實務上：部署卡住時先看 service 的 events
CI 顯示「部署中」一直不結束，先跑 aws ecs describe-services --cluster cafe --services cafe-api --query 'services[0].events[:5]'：ECS 會寫出「已啟動 task」「task 健康檢查失敗」「無法放置 task」這類事件，比翻主控台快。deployments[0].rolloutState 是 IN_PROGRESS、COMPLETED 或 FAILED，CI 的部署腳本可以等它變成 COMPLETED 才算成功，FAILED 就讓 pipeline 變紅。這也是為什麼 circuit breaker 要開：沒開的話部署永遠不會「失敗」，只會一直卡著。

EC2 還是 Fargate

上面都是 Fargate。ECS 也可以把 task 放在你自己的 EC2 機器上（devops 第 18 課介紹過 EC2）。差別在於機器這一層歸誰管：

FargateEC2 launch type
作業系統修補、機器擴充AWS你：要管 AMI 更新、Auto Scaling group、機器數量跟 task 數量一起調
計費依 task 的 vCPU、記憶體與執行時間依機器，不管上面塞了多少 task
適合大多數 API 與背景工作、團隊沒有專人管機器需要 GPU、特殊機型、能長期把機器塞滿以壓低成本

選 EC2 就多了三件 Fargate 不用管的事：

  • instance profile：把 role 掛在機器上，機器上的程式從 IMDS（instance metadata service，169.254.169.254）拿臨時憑證，就是第 1 課憑證鏈的最後一步。注意它是整台機器共用的：機器上每個容器預設都拿得到，所以 ECS on EC2 仍然要給每個 task 自己的 task role。
  • IMDSv2：舊的 IMDSv1 一個 GET 就拿得到憑證，有 SSRF 漏洞（Auth 課第 22 課）的程式會被騙去讀它。IMDSv2 要先用 PUT 帶特定標頭拿 session token，之後的 GET 都要帶 token，一般 SSRF 只能控制 GET 的網址，做不到這一步。設定 --http-tokens required 強制只用 v2。另一個設定 HttpPutResponseHopLimit 是 token 回應能經過幾個網路跳點，限制它可以讓容器拿不到機器的 token（容器多經過一層網路）；反過來，容器裡的程式真的需要時要調高。
  • Session Manager：要進機器查問題時，用 Systems Manager 的 Session Manager（aws ssm start-session --target i-…）取代 SSH：不用開 22 port、不用管 SSH 金鑰，誰在什麼時候進去都記在 CloudTrail（第 2 課）。Fargate 的容器則用 ECS Exec 進去。
# 要求這台機器只能用 IMDSv2（指令照官方文件，2026-11-20 查證）
aws ec2 modify-instance-metadata-options --instance-id i-0abc… \
    --http-tokens required --http-endpoint enabled

還有一個選項是 EKS（AWS 代管的 Kubernetes，Kubernetes 課第 15 課）。ECS 是 AWS 自己的編排器，概念少、跟 IAM、ALB 整合得緊；EKS 是標準的 Kubernetes，生態系大、可攜，但多了控制平面的費用與升級工作。團隊已經熟 Kubernetes、或要跨雲時選 EKS，否則 ECS 加 Fargate 是負擔最小的起點。

💡 實務上：先問「誰會在半夜被叫起來修機器」
選 EC2 的理由常是「比較便宜」，但只算了機器的錢。自己管機器要有人負責 AMI 修補、機器擴充、磁碟滿了、ECS agent 版本，這些都是人力。小團隊的資深工程師通常先用 Fargate 上線，等帳單上 Fargate 真的佔很大一塊、流量也穩定可預測，再評估換成 EC2 或買 Savings Plans。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。用第 1 課建議的獨立練習帳號，不要用公司帳號。這次用公開的 nginx 映像，在預設 VPC 的公有子網路跑一個 task，再故意關掉公開 IP，親眼看到 STOPPED 的原因。

費用：會產生費用。計費項目：Fargate task 依 vCPU 與記憶體的執行時間、task 的公開 IPv4 位址每小時、CloudWatch Logs 的寫入與儲存量。做完馬上清除。金額依 region 不同，見 Fargate 定價頁與 VPC 定價頁的公開 IPv4 位址部分。

先在目前資料夾建兩個檔案。ecs-trust.json：

{ "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow", "Principal": { "Service": "ecs-tasks.amazonaws.com" }, "Action": "sts:AssumeRole" }] }

td.json（把 <帳號ID> 換成你的帳號，region 換成你 profile 的 region）：

{ "family": "cafe-learn", "requiresCompatibilities": ["FARGATE"], "networkMode": "awsvpc",
  "cpu": "256", "memory": "512",
  "executionRoleArn": "arn:aws:iam::<帳號ID>:role/cafe-learn-ecs-exec",
  "containerDefinitions": [{ "name": "web", "image": "public.ecr.aws/nginx/nginx:stable", "essential": true,
    "portMappings": [{ "containerPort": 80 }],
    "logConfiguration": { "logDriver": "awslogs", "options": {
      "awslogs-group": "/ecs/cafe-learn", "awslogs-region": "ap-northeast-1", "awslogs-stream-prefix": "web" } } }] }
# 1. execution role：讓 ECS 代理程式能寫 log（這個映像是公開的，不需要 ECR 權限也拉得到）
aws iam create-role --role-name cafe-learn-ecs-exec --assume-role-policy-document file://ecs-trust.json --profile learn-sandbox
aws iam attach-role-policy --role-name cafe-learn-ecs-exec --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy --profile learn-sandbox

練習

練習 1：寫 canReachAws(net, td) 與 diagnoseStopped(s, td, net)。canReachAws：公有子網路要 assignPublicIp 是 'ENABLED'；私有子網路有 NAT gateway 就可以，沒有的話 endpoints 要包含 ecr.api、ecr.dkr、s3，td.usesAwslogs 時還要 logs，td.usesSecrets 時還要 secretsmanager。diagnoseStopped 依序判斷，回傳第一個成立的：

  1. exit code 是 137，或 stoppedReason 含 OutOfMemoryError → 'memory'
  2. stoppedReason 以 CannotPullContainerError 或 ResourceInitializationError 開頭（啟動前失敗）：沒有 execution role，或訊息含 AccessDenied、not authorized（不分大小寫）→ 'execution-role'；canReachAws 是 false → 'network'；都不是 → 'image'
  3. 容器的最後一行 log（lastLog，可能沒有）含 AccessDenied 或 not authorized → 'task-role'
  4. 其他 → 'app'

練習 2：上線前的 task definition 檢查。寫 validateTaskDef(td)，回傳問題代碼的陣列（不重複、依字母排序），沒問題回傳 []：

  • 'cpu-memory'：cpu 不在表裡，或 memory 不是那個 cpu 可以搭配的值（FARGATE 表的值是陣列時要在陣列裡；是範圍時要在 min～max 之間，而且 (memory - min) 是 step 的倍數）。cpu、memory 都是 MiB 字串。
  • 'network-mode'：networkMode 不是 awsvpc。
  • 'image-tag'：某個容器的 image 沒有用 digest（不含 @sha256:），而且 tag 是 latest 或沒寫 tag。tag 是最後一個 / 之後、冒號後面的部分：localhost:5000/cafe-api 的 5000 是 port，這個 image 沒有 tag。
  • 'secret-in-env'：某個容器的 environment 有名稱含 PASSWORD、SECRET、TOKEN 或 DATABASE_URL 的變數（不分大小寫）。
  • 'secret-arn'：某個 secret 的 valueFrom 不是以 arn: 開頭（團隊規定一律寫完整 ARN）。
  • 'no-logs'：某個容器沒有 logConfiguration。

練習 3：完成 deploy-api.ts 的 deployApi({ ecr, ecs }, opts)，把 cafe-api 部署到 Fargate。repository、cluster、task definition 的 family、service 都用 opts.name。步驟：(1) CreateRepositoryCommand 建 repository，tag 不可變、push 時掃描；已經存在（錯誤的 name 是 RepositoryAlreadyExistsException）就用 DescribeRepositoriesCommand 拿它的 repositoryUri。(2) RegisterTaskDefinitionCommand：FARGATE、awsvpc、cpu '512'、memory '1024'，兩個 role 照 opts 分開填；一個名稱是 api 的容器，image 是 <repositoryUri>@<opts.digest>、port 3100、APP_DATABASE_URL 用 secrets 從 opts.dbSecretArn 注入、awslogs 寫到 /ecs/<name>（region 用 await ecs.config.region()，stream prefix 自訂）。(3) CreateClusterCommand。(4) 用 DescribeServicesCommand 看 service 在不在（services 裡有 status 為 ACTIVE 的就是在）：不在就 CreateServiceCommand（FARGATE、opts 的子網路與安全群組、assignPublicIp: 'DISABLED'、circuit breaker 開啟並回滾、100／200），在就 UpdateServiceCommand 換成這次註冊的 task definition ARN。回傳 { imageUri, taskDefinitionArn, serviceArn }。測試會用新的 digest 再部署一次，確認第二次是換版而不是重建。

練習 4：cafe-api 部署成功、task 都是 RUNNING，但客人上傳收據時 API 回 500，log 寫著 AccessDenied … is not authorized to perform: s3:PutObject。同事說「execution role 已經有 AmazonECSTaskExecutionRolePolicy 了，再加 S3 權限給它就好」。你怎麼做？

✓ task 已經跑起來、是程式呼叫 S3 被拒，所以是 task role 的權限不夠。a 改了也沒用，容器拿不到 execution role 的憑證；b 能動，但讓應用程式也拿到讀 secret 的權限，擴大被攻破時的損害；d 把長期金鑰放進明文的 task definition，是最不該做的事。

練習 5：cafe-api 的 service 是 desiredCount 4、minimumHealthyPercent 100、maximumPercent 200，現在要部署新版。部署過程中會發生什麼？

✓ minimumHealthyPercent 100 是下限：健康的 task 不能少於 4 個，所以不能先停；maximumPercent 200 是上限：最多同時 8 個，所以可以先開 4 個新的。a 是 0／100 這類設定的行為；d 把上限當成目標，部署完成後仍是 desiredCount 4 個。

練習 6：資安要求所有 EC2 機器都設成 IMDSv2 required。主管問：「SSRF 能讓伺服器去 GET 任何網址，為什麼改成 v2 就擋得住偷憑證？」

✓ IMDSv2 把「拿憑證」變成兩步：PUT 拿 token、帶 token 的 GET。SSRF 通常只控制得了一個 GET 的網址。b 錯，位址一樣是 169.254.169.254；c 錯，拿到 token 的程式讀到的就是可用的臨時憑證，所以重點是不讓攻擊者拿到 token。

常見錯誤

  • task definition 寫 :latest：同一個 revision 可能跑出不同映像，回滾也回不去。用 digest，或搭配 IMMUTABLE repository 的固定 tag。
  • 兩個 role 填同一個：能動，但應用程式拿到讀 secret、拉映像的權限。分開、各自最小。
  • 啟動前失敗卻去改 task role：CannotPullContainerError、ResourceInitializationError 發生在容器跑起來之前，跟 task role 無關，先看 execution role 與網路。
  • 公有子網路的 task 沒給公開 IP：連不到 ECR，一直 STOPPED。要嘛給公開 IP，要嘛放私有子網路走 NAT 或 VPC endpoint。
  • 只建 ECR 的 endpoint、忘了 S3：映像層存在 S3，沒有 S3 gateway endpoint 一樣拉不下來；用 awslogs、secrets 還要對應的 endpoint。
  • 密碼放 environment：task definition 是明文，放 secrets，由 execution role 在啟動時讀出來。
  • 沒開 circuit breaker：壞掉的版本一直重啟，部署永遠不會失敗也不會結束。
  • 只看機器費用就選 EC2：還有修補、擴充、IMDS 設定的人力成本。

小結

  • ECS 的四個名詞：cluster、task definition（每次修改是新 revision）、task、service。Fargate 讓你只管 task 的 vCPU 與記憶體，不管機器。
  • ECR repository 開 tag 不可變、push 時掃描、lifecycle policy；task definition 的 image 用 digest。
  • Fargate 的 cpu 與 memory 只能用官方表裡的組合；networkMode 一定是 awsvpc，每個 task 有自己的 ENI 與安全群組。
  • execution role 是 ECS 代理程式在啟動前用的（拉映像、寫 log、讀 secrets）；task role 是你的程式在執行時用的。密碼放 secrets，不放 environment。
  • task STOPPED 的判斷順序：記憶體（OOM、137）→ 啟動前失敗（權限是 execution role、逾時是網路、其他多半是映像參照）→ 啟動後結束（看 log，AccessDenied 是 task role）。
  • service 維持 N 個 task、整合 ALB；100／200 先開新再關舊；circuit breaker 開啟並回滾。
  • EC2 launch type 要自己管機器、instance profile、IMDSv2（http-tokens required）與 Session Manager；團隊沒有專人管機器時先用 Fargate。ECS 與 EKS 的差別在概念數量與可攜性。
