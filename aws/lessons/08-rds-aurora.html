RDS 與 Aurora：Multi-AZ、read replica、備份與 PITR、RDS Proxy、連線數

開幕活動那天，第 6 課的訂單 Lambda 擴到幾百個環境，RDS for PostgreSQL 回 too many connections。會議上有三個提案：「Multi-AZ 有兩台，叫另一台分擔流量」「加一個 read replica，讀取都去那裡」「把 max_connections 調大」。結果加了 replica 之後，客服開始接到「結帳完馬上查訂單，卻說查無訂單」。隔週又有人在正式資料庫執行少了 WHERE 的 DELETE，要還原到十分鐘前。

RDS 與 Aurora：一台執行個體與一個叢集

RDS（Relational Database Service）是 AWS 代管的關聯式資料庫：你選引擎（這門課用 PostgreSQL）、機型、儲存空間，AWS 負責安裝、修補、備份、故障切換；你仍然負責 schema、索引、查詢、連線數與參數。它的單位是一台DB 執行個體（DB instance），資料放在掛給它的磁碟上。

Aurora 是 AWS 自己做的、相容 PostgreSQL（與 MySQL）的資料庫，架構不一樣：它的單位是一個 DB 叢集（DB cluster），運算與儲存分開。依官方文件（2026-11-20 查證）：

  • 資料放在叢集磁碟區（cluster volume），它在 region 內的三個 AZ 都有副本，跟有幾台執行個體無關。
  • 一台寫入執行個體（writer）負責所有寫入；最多 15 台 Aurora Replica（reader）連到同一個叢集磁碟區，只能讀。
  • writer 掛掉時，Aurora 自動把一台 reader 升成新的 writer。

應用程式連的是端點（endpoint，一個 DNS 名稱），不是某台機器的 IP。RDS 執行個體有自己的端點；Aurora 叢集有叢集端點（永遠指向目前的 writer）與讀取端點（reader endpoint，把連線分散到各台 reader）。切換時 AWS 改的是 DNS 背後指向誰，所以端點名稱不變，但既有的連線會斷（devops 第 18 課）。

Multi-AZ 與 read replica：可用性和讀取擴充是兩件事

回到會議上的第一個提案。RDS 的兩種「多一台」常被搞混：

Multi-AZ（單一備援）read replica
目的可用性：主機或 AZ 出事時自動切換讀取擴充：把讀取分出去
複寫方式同步：寫入要兩邊都完成才算 commit，所以不會掉資料，寫入延遲略增非同步：主機 commit 之後再傳過去，會有延遲（replica lag）
能不能讀不能：官方文件明講備援不能拿來分擔讀取能，它有自己的端點
出事時自動切換，端點不變、連線會斷不會自動接手；要手動升格（promote）成獨立的資料庫

所以第一個提案行不通：Multi-AZ 的備援平常不收任何連線。第二個提案（read replica）能分擔讀取，但帶來新問題：客人結帳（寫入主機）後馬上查訂單（讀 replica），replica 還沒追上那筆 commit，就查不到。這叫讀不到自己的寫入（read-your-writes，系統設計課第 6 課的複寫延遲異常）。

常見的讀寫分流規則：

  1. 寫入（INSERT、UPDATE、DELETE、DDL）一律走主機。
  2. 交易裡的所有語句走主機：交易要在同一條連線上，而且常常是「先讀再寫」，讀的必須是最新值。
  3. SELECT … FOR UPDATE 這類要上鎖的讀取走主機，replica 是唯讀的，不能上這種鎖。
  4. 同一個工作階段寫入後的一段時間內（例如 5 秒，要比平常的 replica lag 長），這個工作階段的讀取也走主機，之後才回到 replica。這叫 sticky（黏住主機）。
  5. 其他讀取走 replica。

練習 1 把這套規則寫成路由函式。要看 replica 實際落後多少，看 CloudWatch 的 ReplicaLag 指標；它平常幾乎是 0，但大量寫入、replica 機型太小或長時間的查詢都會讓它拉長，sticky 的時間要依它來定。

💡 實務上：加 replica 之前先問兩個問題
資深工程師面對「資料庫太忙，加個 read replica 吧」時，會先問：忙的是讀還是寫？讀的部分能不能先用索引、快取（系統設計課第 5 課）解決？真的要加，再問：哪些畫面一定要讀到剛寫入的資料（結帳結果、訂單明細）？這些路徑要走主機或 sticky，報表、菜單、歷史紀錄這類可以接受幾秒延遲的才走 replica。另外，Multi-AZ 不是讀取擴充、replica 也不是備份：replica 會忠實地複寫你的誤刪。

連線數：max_connections 從哪來，以及 RDS Proxy

接著是第三個提案「把 max_connections 調大」。PostgreSQL 每條連線是一個程序、要吃記憶體（PostgreSQL 第 36 課），RDS 的預設值因此跟機型的記憶體綁在一起。依官方配額頁（2026-11-20 查證），RDS for PostgreSQL 的預設是：

max_connections = LEAST({DBInstanceClassMemory/9531392}, 5000)

DBInstanceClassMemory 以 byte 計，而且已經扣掉作業系統與 RDS 管理程序用的記憶體，所以比機型標示的記憶體小。實際值以連上去執行 SHOW max_connections; 為準。在參數群組裡硬調大，連線多到記憶體不夠時，執行個體反而會出問題；要多少條連線，答案通常是換大機型或減少連線，而不是改數字。

連線的帳要用尖峰算，不是平均：

  • ECS 服務：task 數 × 每個 task 的連線池大小。部署時 task 數會暫時變成 desiredCount × maximumPercent（第 5 課的 100／200 就是兩倍），要用這個數字。
  • Lambda：同時的環境數 × 每個環境的連線池大小。沒有設 reserved concurrency 的函式，環境數可能長到帳號上限，這筆帳根本算不出來。
  • 維運：migration、排程工作、人用 psql 連進來查問題，要預留幾條。PostgreSQL 本身也替超級使用者保留了幾條（superuser_reserved_connections）。

練習 2 把這筆帳寫成函式。開場的情況：ECS 後台 3 個 task × 10 ＝ 30（部署時 60），Lambda 沒設上限 × 每個環境 5，第 6 課算過，尖峰 200 個環境就是 1,000 條。

RDS Proxy 是放在應用程式與資料庫之間的代管連線池。依官方文件（2026-11-20 查證）：

  • 它維持一組到資料庫的連線並重複使用，應用程式的大量連線被多工到少數資料庫連線上；連線池用完時，新的請求排隊或被拒絕，而不是把資料庫打爆。
  • 資料庫故障切換時，它連到新的主機，並盡量保持應用程式那一端的連線不斷。
  • 可以要求應用程式用 IAM 認證連到 Proxy，Proxy 再用 Secrets Manager 裡的帳密（或 IAM）連資料庫，程式裡不用放資料庫密碼。
  • 它必須跟資料庫在同一個 VPC，而且不能設成公開存取。
  • 改變工作階段狀態的語句（例如 SET）會讓那條應用程式連線被綁定（pinning）在某一條資料庫連線上，多工的效果就沒了；詳細條件見官方的「Avoiding pinning」。

Lambda 這種「環境數會暴增、每個環境各自連線」的用法，RDS Proxy 幾乎是必備；ECS 上 task 數穩定、應用程式自己有連線池時，不一定需要。

💡 實務上：上線前先做一張連線數預算表
每個會連資料庫的服務列一行：最多幾份（task 數乘 maximumPercent、Lambda 的 reserved concurrency）、每份的連線池大小、相乘的結果；加總後跟 max_connections 減掉維運保留的數字比。這張表放在設計文件裡，新服務要連同一個資料庫時就加一行。超過時的選項依序是：縮小每份的連線池、替 Lambda 設上限並加 RDS Proxy、換大機型。CloudWatch 的 DatabaseConnections 指標設告警，接近上限時就要處理，不要等到 too many connections。

備份與 PITR：還原一定是新的執行個體

開場最後一件事是少了 WHERE 的 DELETE。RDS 的自動備份每天做快照，並持續保存交易紀錄（PostgreSQL 的 WAL）。保留天數（BackupRetentionPeriod）設成 0 就沒有自動備份，也不能做時間點還原。依官方文件（2026-11-20 查證），RDS 每五分鐘把交易紀錄上傳到 S3，所以最晚可還原時間（LatestRestorableTime）通常在幾分鐘前；最早可以回到保留天數之內（也不會早於執行個體建立的時間），確切的範圍在主控台的 Automated backups 或 aws rds describe-db-instance-automated-backups 的 RestoreWindow 看。

時間點還原（PITR，point-in-time recovery，原理在 PostgreSQL 第 37 課）在 RDS 上有三個一定要知道的行為：

  1. 還原出來的是一台新的執行個體，名稱要另取，原本那台完全不動。所以還原之後，應用程式要改連新的端點，或者把舊的改名、新的改成舊名稱；更常見的是不切換，只從新那台把被刪的資料查出來、補回原本的資料庫。
  2. 網路與參數設定不會自動沿用：官方文件寫明，還原出來的執行個體預設使用預設的參數群組與選項群組；安全群組也可以選預設的 VPC 安全群組。要跟原本一樣，就要在還原時指定 DB 子網路群組、安全群組、參數群組。沒指定的話，應用程式連不上（安全群組不對），或者調過的參數全部回到預設。
  3. 還原需要時間，資料量越大越久，完成後的一段時間磁碟還在背景載入資料，效能還沒到最好。
await rds.send(new RestoreDBInstanceToPointInTimeCommand({
  SourceDBInstanceIdentifier: 'cafe-db',
  TargetDBInstanceIdentifier: 'cafe-db-pitr-202611200605',     // 新名稱
  RestoreTime: new Date('2026-11-20T06:05:00Z'),               // 誤刪前一刻，用 UTC
  DBSubnetGroupName: 'cafe-db-private',
  VpcSecurityGroupIds: ['sg-db'],
  DBParameterGroupName: 'cafe-pg17',
  PubliclyAccessible: false,
}))

時間要特別小心：誤刪的時間常常是人說的「下午 2 點 5 分」（台灣時間），API 要的是一個確切的時間點。用 UTC 寫（台灣是 UTC+8，所以是 06:05Z），或帶時區的 ISO 字串，不要用沒有時區的字串讓程式自己猜。練習 3 寫一個先檢查範圍、再用正確設定還原的函式。

💡 實務上：PITR 要演練，而且要記下花了多久
「我們有自動備份」不等於「我們還原得回來」。資深的團隊每季在測試帳號演練一次：選一個時間點還原、確認資料正確、量出從決定還原到應用程式能用花了多久（這就是 RTO，devops 課第 24 課），並把步驟寫成 runbook：還原的指令、要帶哪些參數、怎麼把資料補回去、誰有權限做。真的出事時照 runbook 做，而不是在壓力下臨時查文件。另外記得自動備份跟著執行個體走：刪除執行個體時可以選擇保留，最好再定期複製快照到另一個帳號或 region。

參數群組、維護時段與 Aurora Serverless v2

最後三個每天會碰到的設定：

  • 參數群組（parameter group）：postgresql.conf 的設定都改在這裡（devops 第 18 課）。預設的參數群組不能修改，所以一開始就建自己的、掛上去。參數分兩種：動態的改了立即生效，靜態的（例如 shared_buffers）要重新開機才生效，參數群組會顯示 pending-reboot。
  • 維護時段（maintenance window）：AWS 套用修補與小版本升級的每週時段。選在離峰時間；Multi-AZ 的執行個體會先維護備援再切換，仍然會有一次連線中斷，應用程式要能重連（devops 第 18 課）。大版本升級（例如 PostgreSQL 16 到 17）不會自動做，要自己規劃與測試。
  • Aurora Serverless v2：Aurora 的一種執行個體類型，容量以 ACU（Aurora capacity unit）為單位，依負載在你設定的最小與最大值之間自動調整，適合負載起伏大、不想自己選機型的情況。它調整的是 CPU 與記憶體，max_connections 仍然跟容量有關，連線數的帳一樣要算。

在真的 AWS 帳號上做一次（選做）

這一節不判分，也不影響進度。用第 1 課建議的獨立練習帳號。建一台最小的 RDS for PostgreSQL，做一次時間點還原，看還原出來的執行個體用了哪個安全群組與參數群組。整個過程要等二三十分鐘。

費用：會產生費用。計費項目：兩台 DB 執行個體的執行時數（還原出來的那台也算）、儲存空間、超過免費額度的備份儲存、Secrets Manager 每個 secret 每月與 API 呼叫（--manage-master-user-password 會建一個）。做完馬上刪除。金額見 RDS for PostgreSQL 定價頁與 Secrets Manager 定價頁。
# 1. 建最小的執行個體：單一 AZ、保留 1 天備份、不公開，主帳號密碼交給 Secrets Manager 管理
aws rds create-db-instance --db-instance-identifier cafe-learn-db --engine postgres \
  --db-instance-class db.t4g.micro --allocated-storage 20 --master-username cafe \
  --manage-master-user-password --backup-retention-period 1 --no-multi-az --no-publicly-accessible \
  --profile learn-sandbox

# 2. 等它可以用（約 10 分鐘），再看可還原的最晚時間
aws rds wait db-instance-available --db-instance-identifier cafe-learn-db --profile learn-sandbox
aws rds describe-db-instances --db-instance-identifier cafe-learn-db \
  --query 'DBInstances[0].[LatestRestorableTime,DBParameterGroups[0].DBParameterGroupName,VpcSecurityGroups[0].VpcSecurityGroupId]' --profile learn-sandbox

# 3. 還原到最晚可還原時間，成為新的執行個體（這裡故意不指定任何網路與參數設定）
aws rds restore-db-instance-to-point-in-time --source-db-instance-identifier cafe-learn-db \
  --target-db-instance-identifier cafe-learn-db-pitr --use-latest-restorable-time --profile learn-sandbox
aws rds wait db-instance-available --db-instance-identifier cafe-learn-db-pitr --profile learn-sandbox

# 4. 比較兩台：端點不同；參數群組與安全群組是不是第 2 步看到的那個？
aws rds describe-db-instances --db-instance-identifier cafe-learn-db-pitr \
  --query 'DBInstances[0].[Endpoint.Address,DBParameterGroups[0].DBParameterGroupName,VpcSecurityGroups[0].VpcSecurityGroupId]' --profile learn-sandbox

清除

aws rds delete-db-instance --db-instance-identifier cafe-learn-db-pitr --skip-final-snapshot --delete-automated-backups --profile learn-sandbox
aws rds delete-db-instance --db-instance-identifier cafe-learn-db --skip-final-snapshot --delete-automated-backups --profile learn-sandbox

練習

練習 1：寫 createRouter(stickyMs)，回傳 route(session, sql, now)，決定一個語句送到 'primary' 還是 'replica'。規則（SQL 先去掉前後空白、不分大小寫）：

  • BEGIN 或 START TRANSACTION 開頭：這個 session 進入交易，走 primary。
  • COMMIT 或 ROLLBACK 開頭：結束交易、走 primary。交易裡有過寫入時，這個 session 的「最後寫入時間」記成 COMMIT 的時間（資料到 commit 才看得到）。
  • 交易裡的其他語句一律走 primary；是寫入的話，記下「這個交易有寫入」。
  • 交易外：讀取是 SELECT 開頭、而且不含 FOR UPDATE、FOR SHARE；其他都算寫入，走 primary 並把最後寫入時間記成 now。
  • 交易外的讀取：這個 session 的最後寫入時間存在，而且 now - 最後寫入時間 < stickyMs，走 primary；否則走 replica。

每個 session 各自記錄，互不影響。

練習 2：連線數預算。寫 defaultMaxConnections(memoryBytes)：照上面 RDS for PostgreSQL 的公式（無條件捨去）。再寫 connectionBudget(input)，回傳 { peaks, total, limit, ok, unbounded }：

  • ECS 服務的尖峰：Math.floor(desiredCount × maximumPercent / 100) × poolSize（部署時的 task 數）。
  • Lambda 的尖峰：reservedConcurrency × poolSize；沒設 reservedConcurrency 的函式尖峰是 Infinity，名稱放進 unbounded。
  • peaks 是 { 服務名稱: 尖峰 }，total 是加總，limit 是 maxConnections - reservedForOps，ok 是 total <= limit。

練習 3：完成 restore-plan.ts 的 restoreToPoint(rds, sourceId, time)。(1) 用 DescribeDBInstancesCommand 讀來源；BackupRetentionPeriod 是 0 就丟錯。(2) 可還原範圍：最晚是 LatestRestorableTime；最早是「InstanceCreateTime」與「LatestRestorableTime 往前推 BackupRetentionPeriod 天」兩者較晚的那個（真的 AWS 直接看 automated backups 的 RestoreWindow，模擬器沒有這個欄位，所以這題用推算的）。time 不在範圍內就丟 RangeError，而且不能送出還原請求。(3) 新名稱是 <sourceId>-pitr-<UTC 年月日時分>，例如 cafe-db-pitr-202611200605（time.toISOString() 取到分鐘、去掉 -、:、T）。(4) RestoreDBInstanceToPointInTimeCommand：RestoreTime 用 time，沿用來源的 DBInstanceClass、DB 子網路群組名稱、安全群組 ID（VpcSecurityGroupIds）、第一個參數群組名稱，PubliclyAccessible: false。回傳 { id, endpoint }，endpoint 是新執行個體的 Endpoint.Address。

練習 4：咖啡店的 RDS 開了 Multi-AZ。報表查詢讓主機 CPU 很高，同事提議「Multi-AZ 不是有另一台嗎，把報表連到備援那台」。你怎麼回？

✓ 官方文件明講單一備援的 Multi-AZ 不能拿來分擔讀取。a、b 是最常見的誤解：以為「多一台」就能讀；c 的理由不是重點，問題在於備援根本不收連線。報表這種可以接受幾秒延遲的讀取正適合 read replica。

練習 5：有人在 14:05（台灣時間）誤刪了 orders 的資料，你用 PITR 把 cafe-db 還原到 14:04。還原完成後，下列哪件事是對的？

✓ PITR 一定是建新的執行個體，原本那台不動。b 是最多人以為的「覆蓋還原」；c 錯，參數群組預設用預設的，安全群組也要自己指定；d 錯，新執行個體只有到 14:04 為止的資料，之後的新訂單只在原本那台，所以常見的做法是把被刪的資料查出來補回原資料庫。

練習 6：訂單 Lambda 直接連 RDS，每個執行環境建一個大小 5 的連線池。平常很順，活動當天資料庫回 too many connections。下列哪個說法最正確？

✓ 每個執行環境各自一個連線池，所以連線數跟著並行數長。a 錯在連線池建在最外層時，熱啟動會重用連線，不是每次重連；b 是開場的第三個提案，max_connections 跟記憶體綁在一起，硬調大會讓執行個體記憶體不足；d 讓總連線數變成四倍。

常見錯誤

  • 把 Multi-AZ 當成讀取擴充：備援不收連線。讀取擴充用 read replica 或 Aurora reader。
  • 把 read replica 當成備份：誤刪會被忠實地複寫過去。備份是自動備份與快照。
  • 所有 SELECT 都丟 replica：讀不到自己剛寫的資料、交易被拆到兩條連線、FOR UPDATE 失敗。寫入後 sticky、交易與鎖定讀取走主機。
  • 硬調大 max_connections：連線吃記憶體，數字跟機型綁在一起。減少連線或換機型。
  • 用平常的 task 數算連線：部署時是 desiredCount × maximumPercent；Lambda 沒設 reserved concurrency 就沒有上限。
  • 以為 PITR 會覆蓋原資料庫：它建新的執行個體，端點不同；之後的新資料只在原本那台。
  • 還原時不指定安全群組與參數群組：新執行個體用預設的設定，應用程式連不上或行為不同。
  • 用沒有時區的時間字串還原：可能差了 8 小時。用 UTC 或帶時區的 ISO 字串。
  • BackupRetentionPeriod 設 0：沒有自動備份，也不能做時間點還原。

小結

  • RDS 的單位是一台執行個體；Aurora 的單位是叢集：一個跨三個 AZ 的叢集磁碟區、一台 writer、最多 15 台 reader，有叢集端點與讀取端點。應用程式連端點，切換時端點不變、連線會斷。
  • Multi-AZ 是同步備援、只為了可用性、不能讀；read replica 是非同步、能讀、會延遲。讀寫分流：寫入、交易、FOR UPDATE 走主機，寫入後一段時間 sticky，其他讀取走 replica。
  • RDS for PostgreSQL 的 max_connections 預設是 LEAST(DBInstanceClassMemory/9531392, 5000)。連線預算用尖峰算：ECS 用部署時的 task 數、Lambda 用 reserved concurrency，扣掉維運保留。
  • RDS Proxy 共用並多工連線、在切換時保持應用程式的連線，可用 IAM 認證；同 VPC、不能公開；改變工作階段狀態的語句會造成 pinning。Lambda 連 RDS 幾乎必備。
  • 自動備份加交易紀錄支撐 PITR；還原一定是新的執行個體，要自己指定子網路群組、安全群組、參數群組，時間用 UTC；要定期演練並記錄 RTO。
  • 自己建參數群組（靜態參數要重開機）、維護時段選離峰、大版本升級自己規劃；Aurora Serverless v2 依負載自動調整容量，連線數的帳一樣要算。
