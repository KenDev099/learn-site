階段 1：CRUD（增查改刪） · 第 7 課

統計：COUNT、SUM、GROUP BY

10 月結束了，店長想在後台看一份月報，上面有四個問題：「這個月營業額多少？」「有幾位會員來消費過？」「菜單上每個分類各有幾樣商品？」「哪幾位會員這個月消費滿 300 元，要送他們集點卡？」另外，月報底下還想附上兩個小欄位：菜單平均價格和退款金額。

到目前為止，你寫的查詢回傳的都是「一列一列的資料」：哪幾筆訂單、哪幾樣商品。但這四個問題要的不是一列一列，而是把很多列算成一個數字，或是「每個分類各一個數字」。這一課從第一個問題開始，一題一題把月報做出來，途中學會 COUNT、SUM、GROUP BY、HAVING，最後用 SQL 的執行順序解釋途中撞到的每一條規則。

這課會用到：
  • 第 4 課的 WHERE 和 NULL：WHERE 只留下條件是 true 的列；任何值跟 NULL 比較都是 unknown。
  • 第 4 課的別名：AS 幫結果欄位取名字，後端拿到的物件 key 就是它。
  • 第 4 課的 DISTINCT：同樣的值只留一個。
  • 第 5 課的 ORDER BY、LIMIT：排序、只取前幾筆；並列的列誰先誰後不固定。
  • 第 5 課的子句處理順序：FROM → WHERE → SELECT → ORDER BY → LIMIT，所以 ORDER BY 能用別名、WHERE 不能。
這課的路線：
  1. 10 月營業額多少？用 SUM 一句算出來（開場問題的最小答案），認識聚合函式。
  2. 有幾位會員來消費過？三種 COUNT 遇到 NULL 差在哪，順便處理平均的小數和「查不到」的情況。
  3. 每個分類各有幾樣商品？GROUP BY 先分堆、再每一堆各算一次。
  4. 哪幾位會員消費滿 300 元？針對分組結果的條件要寫在 HAVING，不能寫在 WHERE。
  5. GROUP BY 和 HAVING 排在哪一步？把第 5 課的處理順序補完整，解釋 WHERE 不能放 COUNT、HAVING 不能用別名。

10 月營業額多少？一句 SUM 算出來

先想想前端會怎麼做。如果後端給你一個「所有訂單」的 API，你大概會在 Vue 裡這樣算：

const revenue = orders
  .filter(o => o.status === 'paid')
  .reduce((sum, o) => sum + o.total, 0)

這樣算得出來，但代價是整張訂單表都要先從資料庫傳到後端、再傳到瀏覽器。咖啡店一個月幾百筆還好，一年後有幾萬筆，每次打開後台首頁就要搬幾萬筆資料，只為了得到一個數字。資料本來就在資料庫裡，讓資料庫自己算完、只回傳那個數字，傳輸量從幾萬列變成一列。

SQL 裡專門做這件事的函式叫聚合函式（aggregate function）：輸入很多列，輸出一個值。它的運作方式跟 reduce 很像：資料庫一列一列看過去，邊看邊更新一個累計值（加總、計數、目前最大值），看完最後一列就得到結果。差別是你不用寫累加的邏輯，只要說「我要加總 total」。執行後看兩件事：結果只有一列，四個欄位各是一個數字。

這句的執行過程跟上面的 JavaScript 一模一樣：WHERE 先把已付款的訂單挑出來（相當於 filter），剩下 13 筆；聚合函式再把這 13 列壓成一列（相當於 reduce）：13 筆訂單、營業額 2170 元、最小一筆 70 元、最大一筆 340 元。月報的第一個問題答完了。

注意 WHERE status = 'paid' 這行不是可有可無。訂單表裡還有取消（cancelled）和未付款（pending）的訂單，拿掉這行，它們的金額也會被加進「營業額」，數字變大但是錯的，而且不會有任何錯誤訊息提醒你。

剛剛用了四個聚合函式。常用的就是下面這幾個，查表用，不用背：

函式算什麼
COUNT(*)有幾列
COUNT(欄位)這個欄位不是 NULL 的有幾列
COUNT(DISTINCT 欄位)這個欄位有幾種不同的值（不含 NULL）
SUM(欄位)加總
AVG(欄位)平均
MIN(欄位)、MAX(欄位)最小、最大

表裡光是 COUNT 就有三種寫法，而且差別都跟 NULL 有關。月報的第二個問題「有幾位會員來消費過」，正好會踩到這個差別。

有幾位會員來消費過？COUNT 遇到 NULL 會少算

直覺的寫法是「數一數訂單上的 customer_id」。但訂單表有兩個特性會讓這個直覺出錯：

  • 有些訂單是沒登入會員的散客買的，customer_id 是 NULL。
  • 同一位會員可能來好幾次，他的 customer_id 會出現在好幾筆訂單上。

先在整張訂單表上，把三種 COUNT 並排比較。執行後看三個數字為什麼不一樣：

  • COUNT(*)：18 筆訂單，每一列都算。
  • COUNT(customer_id)：15 筆，跳過 customer_id 是 NULL 的列。
  • COUNT(DISTINCT customer_id)：9 位不同的會員下過單。

「有幾位會員」的答案是第三個：DISTINCT 讓同一位會員只算一次，NULL 不算進去，散客自然被排除。第二個數字常被誤當成會員人數，但它算的是「有記名的訂單有幾筆」，常客來三次就被算三次。不過這 9 位裡，有人的訂單是取消或還沒付款，月報要的是「真的來消費過」的會員，所以跟上一節一樣加上 WHERE status = 'paid'：SELECT COUNT(DISTINCT customer_id) FROM orders WHERE status = 'paid' 得到 5 位，這才是月報第二題的答案。示範資料的 18 筆訂單全是 10 月的，所以這課先不加日期條件；正式環境的月報還要再加上日期範圍。

為什麼 COUNT(customer_id) 會跳過 NULL？第 4 課說過，NULL 的意思是「不知道」。聚合函式遇到「不知道」的值，不會去猜它是 0 還是別的，而是直接跳過。這條規則不只 COUNT 有：除了 COUNT(*)，所有聚合函式都會忽略 NULL。COUNT(*) 是例外，因為它數的是「列」本身，不看任何欄位的值。

這條規則對平均值的影響最大。AVG(欄位) 算的是「有值的那些」的平均：分母是不是 NULL 的列數，NULL 不會被當成 0 拉低平均。反過來說，如果你真的想把「沒填」當成 0 來平均，要自己先換掉 NULL，資料庫不會幫你做：用第 15 課的 COALESCE(欄位, 0) 把 NULL 換成 0，再交給 AVG，也就是 AVG(COALESCE(欄位, 0))。所以兩個結論：想算「有幾列」就用 COUNT(*)，不要用 COUNT(某個可能是 NULL 的欄位)；看到平均值時，要知道它沒有算到 NULL 的那些列。

第二題答完了。接下來處理開場提到的兩個附帶欄位，放在這裡是因為它們都跟 NULL 和聚合函式的規則有關。先看平均值的顯示問題。月報想附上「菜單平均價格」，但 AVG 的結果常常有一長串小數，直接放上後台很難看。ROUND(值) 四捨五入到整數，ROUND(值, 1) 留一位小數。執行後比較三欄：

原始平均是 115.588…，ROUND 之後分別是 116 和 115.6。四捨五入在資料庫做完，後端和前端就不用各自處理一次，也不會兩邊規則不一樣。

最後還有一種情況要先想好：條件篩完之後一列都沒有。月報的另一個附帶欄位「退款金額」就是這樣：這個月沒有退款的訂單。這時 COUNT 和其他聚合函式的回答不一樣：

沒有任何列符合時，COUNT 是 0，但 SUM、AVG、MAX 是 NULL，不是 0。例如 SELECT SUM(total) FROM orders WHERE status = 'refunded' 會得到 NULL。後端拿到之後要記得處理，不然畫面可能顯示「營業額：null 元」。（第 15 課的 COALESCE 可以把 NULL 換成 0。）

道理跟前面一樣：沒有列可以數，「有幾列」的答案很確定是 0；但沒有任何金額可以加，「加總是多少」就沒有值，資料庫回 NULL 表示「沒有東西可以算」。

💡 實務上：後台的統計數字在資料庫算好再回傳
咖啡店後台首頁的「今日營業額、訂單數、最大筆訂單」就是一句聚合查詢，不要把整張訂單表撈到 Node.js 再 reduce。後端接結果時注意：Node.js 最常用的 node-postgres（pg）預設會把 COUNT、SUM、AVG 的結果回傳成字串（為了不讓大數字失去精度），前端拿到的是 "18" 不是 18，要自己轉成數字。金額用整數或 numeric 存，不要用浮點數，加總才不會冒出小數誤差。資深工程師寫報表前會先跟 PM 確認「營業額」的定義：含不含取消、未付款、退款？同一個詞各算各的，是報表最常見的爭議。

到這裡，月報上「全店一個數字」的問題都能回答了。但第三個問題「每個分類各有幾樣商品」要的不是一個數字，而是每個分類各一個數字。用目前學的，只能寫 WHERE category = '咖啡' 算一次、改成 '茶' 再算一次，有幾個分類就跑幾次查詢，以後新增分類還要記得多跑一次。

每個分類各有幾樣商品？GROUP BY 先分堆再各算一次

在前端，你會用 lodash 的 groupBy 先把商品依分類分成幾堆，再對每一堆算長度。SQL 的 GROUP BY 做的是同一件事，只是一句就完成：

  1. 分堆：把 GROUP BY 後面那個欄位的值相同的列，放進同一組。
  2. 每一堆各算一次：SELECT 裡的聚合函式不再算整張表，而是對每一組各算一次。
  3. 一組變成一列：結果裡每一組只剩一列。

上一節的聚合查詢沒有 GROUP BY，可以想成「整張表就是一組」，所以結果只有一列。加了 GROUP BY 之後有幾組，結果就有幾列。把它寫成查詢，順便算每組的平均價格。執行後看：結果有幾列、NULL 那一列在不在。

咖啡 7 樣最多、甜點 4 樣，茶、輕食和沒分類的各 2 樣（並列的三組誰先誰後不固定，第 5 課提過）。category 是 NULL 的「季節特調」和「熱可可」沒有被丟掉，而是自成一組。這跟第 4 課 DISTINCT 把所有 NULL 當成同一個值是同樣的規則。月報的第三個問題答完了，新增分類時這句查詢也不用改。

分組的依據也可以不只一個欄位。店長追問：「每個分類裡，上架和下架的各有幾樣？」把兩個欄位都寫進 GROUP BY，「分類和上架狀態兩個都相同」的列才會在同一組：

例如咖啡分成「咖啡、上架」和「咖啡、下架」兩組。組合越細，組就越多，結果的列數也越多。

分完組之後，很自然會想在每個分類旁邊順便列出商品名稱。試試看：

報錯了：column "products.name" must appear in the GROUP BY clause or be used in an aggregate function。想想看就合理：「咖啡」這一組有 7 樣商品，結果只有一列，那 name 要顯示哪一個？資料庫不會幫你亂挑。所以 SELECT 裡的每個欄位只能是：

  • 寫在 GROUP BY 裡的欄位（每組只有一個值），或
  • 包在聚合函式裡的（例如 MAX(price)、COUNT(name)）。

這條規則的判斷方法只有一個：問自己「這個欄位在每一組裡是不是只有一個值」。category 是分組依據，同一組的值一定一樣；MAX(price) 把一組算成一個數字；name 在一組裡有好幾個，所以不行。至於「每個分類最貴的是哪一樣」這種每組挑出一整列的需求，GROUP BY 做不到，要用後面的課，見課末「補充與查表」。

💡 實務上：圖表和排行榜背後幾乎都是 GROUP BY
後台的「各分類銷售佔比」圓餅圖、「每日營業額」折線圖、「熱銷商品排行」，都是一句 GROUP BY，後端把結果陣列直接交給圖表套件。分組要用 id 這種唯一的欄位，不要用名字：兩位同名的顧客會被算成同一個人，要顯示名字再用第 9 課的 JOIN 接上。依日期分組時要注意時區，台灣的「10/1」和 UTC（世界標準時間）的 10/1 切點差 8 小時（日期函式在第 15 課）。

月報只剩最後一個問題：「哪幾位會員這個月消費滿 300 元」。依上面的做法，訂單依 customer_id 分組、每組 SUM(total)，就有每位會員的消費額。問題是，要怎麼只留下「總額 300 以上」的那幾組？直覺是把 SUM(total) >= 300 寫進 WHERE，但這行不通。

哪幾位會員消費滿 300 元？HAVING 篩選分組後的結果

先用上一節熟悉的分類結果看清楚問題出在哪。假設要「列出商品有 3 樣以上的分類」，條件是 COUNT(*) >= 3。照習慣寫進 WHERE，執行後看錯誤訊息：

錯誤是 aggregate functions are not allowed in WHERE。原因在 WHERE 的工作方式：它是一列一列判斷要不要留下，判斷某一列「美式咖啡」時，資料庫還沒分組，更還沒算出「咖啡這組有 7 樣」。COUNT(*) >= 3 要等分完組、算完數量才知道，WHERE 那時候根本拿不到這個數字。

所以 SQL 另外提供了 HAVING：它在分組、計算之後才執行，判斷的對象是一組一組，而不是一列一列。這種針對分組結果的條件，要寫在 HAVING：

結果只剩咖啡（7 樣）和甜點（4 樣）。HAVING 把茶、輕食和 NULL 那三組丟掉了，被丟掉的是整組，而不是組裡的某幾樣商品。

WHERE 和 HAVING 都是「篩選」，差別在篩的時間點和篩的對象：

WHEREHAVING
篩選的是分組之前的每一列分組之後的每一組
能用聚合函式嗎不能可以
例子status = 'paid'SUM(total) >= 300

回到月報的問題。「已付款訂單裡，消費總額 300 元以上的會員」需要兩種篩選一起用，每一步各做一件事：

  1. WHERE 先丟掉沒付款的訂單和散客的訂單：這是針對每一列的條件。
  2. GROUP BY customer_id 把剩下的訂單依會員分組，SUM(total) 算出每位會員的消費額。
  3. HAVING 再丟掉總額不到 300 的組：這是針對每一組的條件。

執行後看：每一列是一位會員，spent 都在 300 以上。

結果有 5 位會員，消費最多的是 1 號（3 筆、500 元）。月報的四個問題全部答完。

寫這種查詢時還有一個原則：能寫在 WHERE 的條件就寫在 WHERE。越早把不要的列丟掉，後面要分組、計算的資料就越少。HAVING 只放「非得等分組算完才知道」的條件。

💡 實務上：會員分級、行銷名單就是 WHERE＋GROUP BY＋HAVING
行銷說「近 30 天消費滿 1000 元的會員發優惠券」：日期範圍和付款狀態寫在 WHERE，門檻寫在 HAVING。最常見的坑是漏了 status = 'paid'，取消的訂單也被算進消費額，券就發錯人。門檻和天數會常常改，做成 API 參數，用 $1、$2 這種參數化查詢傳進 SQL（第 25 課），不要自己拼字串，否則會有 SQL injection 的風險。名單要拿去發券或寄信之前，先看一下筆數和幾個樣本，確認跟預期差不多再執行。

月報做完了，但回頭看，這一路撞到好幾條看似零散的規則：WHERE 不能放 COUNT；上面那句 HAVING 要寫完整的 SUM(total)，寫成別名 spent >= 300 會報錯。第 5 課用子句的處理順序解釋過 ORDER BY 能用別名、WHERE 不能，但當時的順序裡還沒有 GROUP BY 和 HAVING。要解釋這課的新規則，得先知道它們插在這個順序的哪裡。

GROUP BY 和 HAVING 排在哪一步？完整的 SQL 執行順序

第 5 課看過，資料庫處理子句的順序跟寫的順序不一樣：寫的時候 SELECT 開頭，處理時是 FROM → WHERE → SELECT → ORDER BY → LIMIT，當時用它解釋了 ORDER BY 能用別名、WHERE 不能。這課多了 GROUP BY 和 HAVING，它們插在 WHERE 和 SELECT 之間。原因是照資料流動的方向：先要有資料，才能篩選；篩完才能分組；分完組才算得出每組的值；最後才決定要輸出哪些欄位、怎麼排序：

用月報最後那句查詢走一遍，每一步都只拿得到前面幾步做好的東西：

  1. FROM orders：拿出整張訂單表，18 列。
  2. WHERE：丟掉沒付款和散客的列，剩下 10 列。
  3. GROUP BY customer_id：分成 5 組，一位會員一組。
  4. HAVING SUM(total) >= 300：每組算出總額，丟掉不到 300 的組。這份資料裡 5 組都超過 300，所以一組都沒丟；門檻提高，就會有組被丟掉。
  5. SELECT：算出要輸出的欄位，到這一步 spent 這個別名才誕生。
  6. ORDER BY spent DESC：依消費額排序，這時已經有 spent 可以用。
  7. LIMIT：這句沒寫，不取前幾筆，全部輸出。

有了這張圖，途中遇到的規則都不用死背：

  • WHERE 不能用聚合函式：WHERE 在第 2 步，那時還沒分組，沒有東西可以 COUNT。
  • WHERE 和 HAVING 都不能用 SELECT 的別名：別名在第 5 步才出現。所以 HAVING spent >= 300 會報錯，要寫完整的 HAVING SUM(total) >= 300。
  • ORDER BY 可以用別名：第 6 步時，別名已經有了。
  • LIMIT 在最後：先排好、再取前幾筆，所以「最貴的 3 樣」才會正確。

以後遇到「這裡能不能用某個東西」的疑問，先問：它在第幾步產生、我現在在第幾步用它。產生得比較晚，就不能用。這是「邏輯上」的順序，用來理解規則；資料庫實際怎麼做可能不一樣，細節見課末。

補充與查表

  • 每組挑出一整列：「每個分類最貴的是哪一樣商品」這種問題，要的不是一個數字，而是每組裡的某一列（包含它的 name）。GROUP BY 每組只剩一列聚合結果，做不到；這要用第 17 課的視窗函式。
  • 邏輯順序和實際執行：上面的執行順序是「邏輯上」的順序。資料庫實際執行時可能會調整做法（例如用索引），但結果一定跟照這個順序算出來的一樣。

練習

練習 1：用一句查詢算出三個數字，依序是：訂單總共幾筆、其中有記名會員（customer_id 不是 NULL）的有幾筆、總共有幾位不同的會員下過單。

練習 2：算出已付款（status = 'paid'）訂單的筆數和營業額（total 加總），依序兩個欄位。

練習 3：每個分類各有幾樣商品？顯示 category 和商品數，沒有分類（NULL）的也要算成一組。

練習 4：只看上架中的商品，算出每個分類的平均價格，用 ROUND 四捨五入到整數。顯示 category 和平均價格。

練習 5：找出 VIP：只看已付款、有記名會員的訂單，依 customer_id 分組，列出消費總額 340 元以上的會員。依序顯示 customer_id、訂單筆數、消費總額。

練習 6：想找出「平均價格超過 100 元的分類」，條件 AVG(price) > 100 要寫在哪裡？

✓ AVG 要分完組才算得出來，而 WHERE 在分組之前執行，不能用聚合函式。分組之後的條件寫在 HAVING。

練習 7：SELECT category, name FROM products GROUP BY category; 會怎樣？

✓ 每組只會有一列結果，但一組裡有很多個 name，資料庫不知道要顯示哪個，所以直接報錯。（有些資料庫如舊版 MySQL 會隨便挑一個，PostgreSQL 不會。）

常見錯誤

  • 用 COUNT(欄位) 算列數：除了 COUNT(*)，聚合函式都會跳過 NULL，遇到散客這種 NULL 會少算。算列數用 COUNT(*)；算「幾位不同的人」用 COUNT(DISTINCT 欄位)。
  • 聚合函式寫在 WHERE：aggregate functions are not allowed in WHERE。WHERE 在分組之前一列一列判斷，拿不到每組的數字，改寫到 HAVING。
  • HAVING 用了別名：HAVING spent >= 300 會出現 column "spent" does not exist，因為別名在 SELECT 那一步才產生，比 HAVING 晚。要寫完整的運算式 HAVING SUM(total) >= 300。
  • SELECT 了沒分組的欄位：must appear in the GROUP BY clause or be used in an aggregate function，因為一組裡有很多個值，資料庫不知道顯示哪個。把欄位加進 GROUP BY，或包進聚合函式。
  • 以為 SUM 找不到資料會是 0：其實是 NULL，沒有列可以加就沒有值。後端要處理，或用第 15 課的 COALESCE 換成 0。

小結

  • 聚合函式把很多列算成一個值，像資料庫裡的 reduce：COUNT、SUM、AVG、MIN、MAX。統計在資料庫算好再回傳，不要整張表撈出來自己加。
  • COUNT(*) 算列數；其他聚合函式都會忽略 NULL；COUNT(DISTINCT 欄位) 算有幾種不同的值；ROUND 處理小數；一列都沒有時 COUNT 是 0，SUM、AVG 是 NULL。
  • GROUP BY 把值相同的列分成一組，每組各算一次，一組在結果裡一列；SELECT 只能放分組欄位和聚合函式。
  • WHERE 篩列（分組前），HAVING 篩組（分組後）；能寫在 WHERE 的就寫在 WHERE。
  • 執行順序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。某個東西能不能用，看它在第幾步產生。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 8：行銷要「不住台北的會員」名單發簡訊，你寫了 WHERE city <> '台北'。行銷說名單少了幾個人，為什麼？

✓ 任何值跟 NULL 比較都是 unknown，WHERE 只留 true 的列，這些人就安靜地消失了，不會報錯。先問行銷沒填城市的要不要算，要就加 OR city IS NULL。a 錯在空字串是一個值，'' <> '台北' 是 true，會留下來。（第 4 課）

練習 9：結帳 API 把前端表單整包寫進 orders，INSERT 有列出 status，前端沒選狀態時送 null。建表時是 status text DEFAULT 'pending'，新訂單的 status 是什麼？

✓ 預設值只在欄位沒寫進 INSERT（或寫 DEFAULT）時才生效。後端要挑出允許的欄位，沒帶值就不列出那個欄位，不要整包照收。b 錯在資料庫分得出「沒寫」和「寫了 NULL」，後者照你說的存 NULL。（第 3 課）

練習 10：商品列表用 ORDER BY price LIMIT 5 OFFSET 5 查第 2 頁。翻頁期間沒有人改資料，客服卻回報有商品在第 1、2 頁都出現，另一個商品從沒出現過。原因是？

✓ ORDER BY 只保證你寫的欄位有順序，同價的商品誰前誰後不保證，兩次查詢可以不一樣。分頁的排序最後加主鍵：ORDER BY price, id。c 錯在 LIMIT 最後才執行，先排好再取前幾筆。（第 5 課）

練習 11：拿鐵要漲 10 元，店員寫了這句。哪裡會出事？

UPDATE products
SET price = price + 10
WHERE name LIKE '%拿鐵%';

✓ WHERE 的範圍比想的大，不報錯也不確認。用 id 指定最安全，動手前先用 SELECT 跑同一個 WHERE 看會改到哪幾列。b 錯在每一列都用自己原本的值計算，跟其他列無關。（第 6 課）

練習 12：老闆說「已取消的訂單不要再出現在後台」。資深工程師通常怎麼做？

✓ 訂單這類資料要留給報表和對帳，用軟刪除標記而不真的刪。代價是每個查詢都要記得加 WHERE deleted_at IS NULL。b 錯在 DELETE 沒有復原按鈕，先 SELECT 只確認了範圍，資料刪了還是沒了。（第 6 課）

練習 13：後台首頁要顯示「有幾位會員下過單」。orders 裡有散客的訂單，customer_id 是 NULL。該用哪一個？

✓ 問的是「幾位」：同一位會員下好幾次只算一次，DISTINCT 也不算 NULL，散客自然不算進來。示範資料是 9 位。b 錯在它算的是「有記名的訂單有幾筆」（15 筆），常客會被重複算。（第 7 課）

練習 14：要列出消費滿 300 元的會員，這句執行時報錯。問題在哪？

SELECT customer_id, SUM(total) AS spent
FROM orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING spent >= 300
ORDER BY spent DESC;

✓ 會出現 column "spent" does not exist：執行順序是 WHERE → GROUP BY → HAVING → SELECT，別名在 SELECT 才產生。改成 HAVING SUM(total) >= 300。c 錯在 ORDER BY 在 SELECT 之後執行，可以用別名。（第 7 課）
