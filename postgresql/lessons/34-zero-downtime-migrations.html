階段 10：資深必備｜上線與維運 · 第 34 課

零停機 migration：DDL 的鎖與安全步驟

咖啡店的 orders 已經有 4,000 萬筆。產品經理開了三張單：訂單加上「來源管道」channel 而且不能是空的、顧客的手機不能重複、訂單編號從 integer 換成 bigint（快用完了）。在自己電腦上，每一件都是一句 ALTER TABLE 或 CREATE INDEX，按下去就好。照樣在正式環境執行，其中兩句會把 orders 整張鎖住好幾分鐘，連查詢都要等；另一句讓顧客資料在建索引的期間寫不進去。網站跟著停擺。

這一課要把這三張單做成零停機（zero downtime）的 migration：改 schema 的過程中，網站的讀寫都不中斷。做法不是找一句更聰明的 SQL，而是先判斷每個 DDL 會拿什麼鎖、要做多少事，再把危險的那一句拆成一連串各自安全的小步驟。學完你能替自己的 migration 做同樣的判斷與拆解。

這課的路線：
  1. 這三張單為什麼會讓網站停擺？每個 DDL 先問「拿什麼鎖、要做多少事」，並替每個 DDL 加上 lock_timeout 與重試。
  2. 第一張單：「channel 不能是空的」怎麼加，才不會在強鎖底下掃全表（NOT VALID＋VALIDATE）；舊的空值怎麼分批補。
  3. 第二張單：「手機不能重複」的唯一索引怎麼建，才不擋寫入（CREATE INDEX CONCURRENTLY），失敗後留下的殘骸怎麼清。
  4. 第三張單：訂單編號換成 bigint，怎麼讓新舊版程式同時能跑（expand／contract）。
  5. 整份計畫上線前，怎麼確定它在正式資料量下也安全。
這課會用到：
  • 第 32 課的表級鎖與等待佇列：ACCESS EXCLUSIVE 連 SELECT 都擋；拿不到鎖的請求會排隊，後來的請求又排在它後面。這課還會用到其他幾種鎖，由弱到強對照：ROW EXCLUSIVE 是一般寫入（INSERT／UPDATE／DELETE）拿的鎖；SHARE UPDATE EXCLUSIVE 讀寫都不擋，只和其他 DDL、VACUUM 互斥；SHARE 擋寫入但不擋讀；SHARE ROW EXCLUSIVE 也擋寫入、不擋讀；ACCESS EXCLUSIVE 連讀取都擋。
  • 第 22 課的 migration 與 expand／contract：schema 的變更寫成依序執行的檔案；新舊版程式要同時能跑時，先擴充（加新的）、再收斂（移除舊的）。
  • 第 12 課的約束：CHECK、NOT NULL、UNIQUE 讓資料庫擋掉不合規則的資料，CONSTRAINT 名稱 替約束取名。
  • 第 20 課的索引：查詢不必掃全表；UNIQUE 索引同時保證不重複；外鍵欄位要自己建索引。
這頁的環境：這頁只有一條連線，看不到別人：讀著表的同事用停在交易裡的 prepared transaction 模擬。lock_timeout 在這頁不會觸發，「拿不到就放棄」改用 NOWAIT。帶 CONCURRENTLY 的指令要單獨一格執行。

這頁的資料：customers（6 位顧客，林志豪和李建國的 phone 一樣）、products、orders（3,001 筆，channel 約 1/7 是 NULL、分散在各處；customer_id 還沒有外鍵，而且第 3001 筆參照了不存在的顧客 99）。

這三張單為什麼會讓網站停擺？每個 DDL 先問兩件事

要回答開場的問題，先替這類指令取個名字。改資料的指令是 INSERT、UPDATE、DELETE；改「結構」的指令，例如 ALTER TABLE、CREATE INDEX、DROP COLUMN，統稱 DDL（Data Definition Language）。三張單都是 DDL。DDL 在小表上幾乎都是瞬間完成，所以在開發機上看不出差別；在大表上會不會出事，取決於兩個問題：

  1. 拿什麼鎖？DDL 執行前要先拿表級鎖，鎖拿到交易結束才放。大多數 ALTER TABLE 拿最強的 ACCESS EXCLUSIVE，期間連 SELECT 都要等（第 32 課的衝突表）。
  2. 要做多少事？PostgreSQL 用一組內部表記錄有哪些表、每張表有哪些欄位，這組表叫系統目錄（catalog）。有的 DDL 只改系統目錄，不管表多大都瞬間完成。有的要掃全表，讀過每一列確認舊資料符合規則；有的要重寫表，把每一列都改寫一遍。後兩種的時間跟資料量成正比。

兩個問題要合起來看。強鎖本身不可怕，只要拿得很短；大量工作本身也不可怕，只要不擋別人。真正讓網站停擺的組合是「強鎖＋大量工作」：鎖會一直拿到工作做完，4,000 萬筆要做幾分鐘，網站就停幾分鐘。

「重寫表」需要多解釋一點，因為它是最重的一種。一張表在磁碟上是一組檔案。重寫表（table rewrite）是 PostgreSQL 建一組新檔案，把每一列轉換後寫進去，連同所有索引一起重建，最後換掉舊檔案。表目前用的檔案編號叫 relfilenode，用 pg_relation_filenode('表') 查得到；重寫之後換成新檔案，編號就變了。所以「filenode 有沒有變」就是「有沒有重寫」的直接證據，不必靠猜。

拿第三張單 integer 改 bigint 量一次：在 BEGIN … ROLLBACK 裡改型別（量完就撤銷），前後各查一次 filenode，再從 pg_locks（第 32 課）查自己（pg_backend_pid()）在 orders 上拿的鎖。執行後比較兩張結果的編號，再看「鎖」欄：

編號變了，表被重寫了。「鎖」欄裡的 AccessExclusiveLock 是 pg_locks 的寫法，也就是 ACCESS EXCLUSIVE（兩種寫法的對照在第 32 課的表）。

兩個答案放在一起，就是第三張單的問題：integer 改 bigint 會在 ACCESS EXCLUSIVE 底下重寫整張表和它的索引。每一列的編號都從 4 bytes 變成 8 bytes，存放格式不同，只能逐列重寫。4,000 萬筆可能要好幾分鐘，這段時間 orders 完全不能讀寫。

每次都這樣手動量太慢。seed 裡的 ddl_probe(ddl, 表) 把上面那格包成一個函式：在一個會被取消的子交易裡執行 DDL，回傳這張表有沒有被重寫，以及 DDL 在這張表上拿到的最強的鎖（已經轉成 ACCESS EXCLUSIVE 這種寫法）。執行完就撤銷，不會改到資料。用它一次量 9 句常見的 DDL，執行後逐列看「重寫」和「最強的鎖」兩欄：

先看鎖：除了 CREATE INDEX，其他每一句都拿 ACCESS EXCLUSIVE。所以「拿什麼鎖」大多數時候答案一樣，真正把 DDL 分成安全與危險的，是第二個問題「要做多少事」。

再看重寫：四句 ADD COLUMN 裡，只有預設值是 gen_random_uuid() 的那句重寫了表。同樣是「加一個有預設值的欄位」，差別在預設值固不固定。

從 PostgreSQL 11 起，加欄位時如果預設值是固定的，PostgreSQL 不去改每一列，而是只在目錄裡記下「這個欄位的預設值是 'pos'」。舊的列被讀到、發現自己沒有這個欄位時，就拿目錄裡記的值補上。這叫 fast default，所以 4,000 萬筆也是瞬間完成。now() 看起來每次不同，但它在同一個交易裡回傳同一個時間，加欄位時只會算一次，所以也算固定。

反過來，有些函式每次呼叫的結果都可能不同，叫 volatile 函式，例如 gen_random_uuid()、clock_timestamp()、random()。用它當預設值時，每一列都要各自算一個不同的值，目錄裡記不下「一個值」，只能把整張表重寫一遍，替每一列填上自己的值。真的需要這種欄位時，拆成三步：先加沒有預設值的欄位（瞬間）、再分批替舊資料補值（後面教）、最後 SET DEFAULT（只影響之後的新列，也是瞬間）。

「掃全表」的 DDL 不會換檔案，filenode 量不出來，要看文件。把量到的結果加上 PostgreSQL 18 的 ALTER TABLE 文件整理成下表。這張表查表用，不用背，寫 migration 時回來對照：

對照這張表，開場的三張單各卡在哪裡，以及這課接下來怎麼解：

  • channel 不能是空的：SET NOT NULL 要在 ACCESS EXCLUSIVE 底下掃全表。改用 NOT VALID 先擋新資料，回填舊資料後再 VALIDATE，讀寫照常。
  • 手機不能重複：一般的 CREATE INDEX 拿 SHARE，唯一索引建好之前所有寫入都要等。改用 CREATE INDEX CONCURRENTLY。
  • 訂單編號換成 bigint：改型別會重寫表和索引。改用 expand／contract：加一個新欄位、分批回填，最後在一個很短的交易裡切換。

這三個解法有一個共同點：把「強鎖＋大量工作」拆開，讓強鎖只出現在瞬間完成的步驟裡。

💡 實務上：review migration 時看的是 SQL，不是 ORM 的程式碼
Prisma、TypeORM 這類工具會替你產生 migration，在 schema 裡把 Int 改成 BigInt 只是改一個字，背後可能就是一次重寫表。資深工程師 review 時會打開產生出來的 SQL，逐句問「拿什麼鎖、要不要掃表或重寫」，並先問一句「這張表現在多大」。小表（設定表、幾千筆的商品表）直接 ALTER 沒問題，不必每次都拆成五步；真正要小心的是訂單、日誌這類持續長大、又一直有人寫入的表。團隊可以把「大表清單」寫進 PR 範本，碰到就多一道檢查。

不過，「只留下瞬間完成的強鎖」還不夠安全。上表標成「瞬間」的那些 DDL，都藏著一個前提：馬上拿得到鎖。下一節先處理這個前提，因為後面每一個安全步驟都會用到它。

就算 DDL 瞬間完成，為什麼還會卡住網站？lock_timeout 與重試

「瞬間完成」指的是拿到鎖之後的那一段。拿到鎖之前，DDL 要排隊。第 32 課的事故就是這樣：ALTER 排在一個跑了兩分鐘的報表後面等 ACCESS EXCLUSIVE，而等待佇列是先來後到，後面進來的每一個 SELECT 都和排在前面的 ACCESS EXCLUSIVE 衝突，只好排在 ALTER 後面。ALTER 本身只要幾毫秒，網站卻停了兩分鐘。也就是說，對網站來說，鎖等待比鎖本身危險。

解法是替 DDL 的等待設上限。lock_timeout 是 PostgreSQL 的設定，規定一句指令最多等鎖多久，超過就放棄並回傳錯誤 55P03（拿不到鎖）。DDL 一放棄，就從佇列裡離開，排在它後面的查詢立刻放行；migration 稍後再試一次，碰到報表剛好跑完的空檔就成功。代價從「網站停擺兩分鐘」變成「部分查詢多等幾秒、migration 多試幾次」。

來模擬一次。同事開了一份報表，讀著 orders（拿著 ACCESS SHARE），然後暫停：PREPARE TRANSACTION 讓這個交易停住，手上的鎖一直留著，就是第 32 課的「暫停的同事」。

這頁的 lock_timeout 不會觸發（第 32 課實測），改用 NOWAIT：它等於「一秒都不等」，拿不到鎖就立刻失敗，同樣回傳 55P03。下面用 seed 裡的 try_sql(sql) 各試一次 LOCK TABLE … NOWAIT：它執行一句 SQL，成功回傳「成功」，失敗回傳錯誤碼和訊息，不會讓整句查詢中斷（第 32 課用過）。左欄是 ALTER 要的 ACCESS EXCLUSIVE，右欄是一般寫入要的 ROW EXCLUSIVE，執行後看哪一欄失敗：

ACCESS EXCLUSIVE 和報表衝突，拿不到；一般寫入要的 ROW EXCLUSIVE 不衝突，成功。換成正式環境，左欄的 ALTER 就是「放棄、讓出佇列、等一下再試」，而不是排在那裡擋住右欄的每一個寫入。結束模擬，撤銷同事的交易：

放棄之後要有人負責重試。正式環境的 migration 會把 DDL 交給一個這樣的函式執行：每次只做一個 DDL、在交易裡 SET LOCAL lock_timeout（只在這個交易有效，不影響這條連線之後的查詢）、收到 55P03 就等一下重試（用第 25 課的 pg）：

async function runDdl(pool: Pool, ddl: string, maxAttempts = 10) {
  for (let attempt = 1; ; attempt++) {
    const client = await pool.connect()
    try {
      await client.query('BEGIN')
      await client.query("SET LOCAL lock_timeout = '2s'")   // 最多擋住別人 2 秒
      await client.query(ddl)
      await client.query('COMMIT')
      return
    } catch (err: any) {
      await client.query('ROLLBACK').catch(() => {})
      if (err.code !== '55P03' || attempt >= maxAttempts) throw err   // 不是等鎖失敗，或試太多次：交給人處理
      await new Promise(r => setTimeout(r, 1000 * attempt))          // 讓卡住的查詢有機會跑完
    } finally {
      client.release()
    }
  }
}

逐一看這段程式的三個決定：

  • lock_timeout = '2s'：DDL 排隊的這 2 秒裡，排在它後面的查詢也跟著等。所以這個數字的意思是「最壞情況下，App 的查詢多等 2 秒」。依網站能忍受的延遲設定，常見 1～5 秒。
  • 每次只做一個 DDL：前面拿到的鎖會一直拿到 COMMIT。一個交易裡塞好幾個 DDL，第二句在等鎖時，第一句拿到的 ACCESS EXCLUSIVE 還握在手上，照樣擋住所有人，lock_timeout 就只保護了一半。
  • 等待時間逐次拉長：第 1 次等 1 秒、第 2 次等 2 秒，給擋路的長查詢時間跑完。試到上限還失敗就丟出錯誤，交給人處理，不要無限重試。

注意 lock_timeout 只限制「等鎖」。拿到鎖之後，掃全表、重寫表要花多久，它管不到。那一半要靠接下來三節的寫法，把大量工作移出強鎖。

💡 實務上：lock_timeout 設在 migration 工具，不靠每個人記得
實際做法是在 migration 的執行流程統一設 lock_timeout（連線參數或每個檔案的開頭），而不是期待每個寫 migration 的人自己加。上線前先看有沒有長時間的查詢或「開著交易沒結束」的連線（第 32 課查 pg_stat_activity），常見元兇是直接連正式資料庫跑的報表、BI 工具，或忘了關的管理工具視窗。重試到上限還失敗時，部署要明確失敗並通知值班的人，不要默默跳過。大型變更通常也會挑離峰時段，例如咖啡店打烊後。

有了 lock_timeout，每個瞬間完成的 DDL 都安全了。接下來輪到不是瞬間完成的那些，從第一張單開始。

第一張單：「channel 不能是空的」怎麼加，才不會在強鎖底下掃全表？

直覺的寫法是 ALTER COLUMN channel SET NOT NULL。上一節的表說它要在 ACCESS EXCLUSIVE 底下掃全表。為什麼要掃？資料庫加上一條規則之前，必須先證明現有的每一列都符合這條規則，否則表裡會同時存在「規則」和「違反規則的資料」。為什麼要拿強鎖掃？因為規則還沒生效，掃描進行中如果有人寫入新的 NULL，掃描就白做了；最簡單的保證是掃描期間誰都不准動這張表。CHECK、外鍵也是同一個道理。

拆解的關鍵在於：規則其實管兩批資料，一批是之後寫進來的新資料，一批是已經在表裡的舊資料。新資料只要規則一生效就會被逐筆檢查，不用掃表；需要掃表的只有舊資料。NOT VALID 就是把這兩件事分開做：

  1. ADD CONSTRAINT … NOT VALID：約束立刻生效，但先不掃舊資料，所以只改目錄、瞬間完成。但它仍要拿一個短暫的強鎖：CHECK 和 NOT NULL 是 ACCESS EXCLUSIVE，外鍵是兩張表各拿 SHARE ROW EXCLUSIVE（第一節的表），所以一樣交給上一節的 lock_timeout。從這一刻起，新寫入或修改的列都要符合。
  2. VALIDATE CONSTRAINT：掃舊資料，確認都符合。它只拿 SHARE UPDATE EXCLUSIVE，讀寫照常。文件的理由正好接回上面的推論：新資料已經由約束把關，掃描期間不會再有人寫進違規的資料，所以不必擋住別人。

先用外鍵看一次完整的過程。選外鍵是因為這頁的 orders 剛好有一筆舊的髒資料：第 3001 筆參照了不存在的顧客 99，能讓你看到「舊資料不合規則」時 VALIDATE 會怎樣。NOT VALID 對 CHECK、外鍵、NOT NULL 的行為都一樣。下面在 BEGIN … ROLLBACK 裡加上 NOT VALID 的外鍵，再用 try_sql 插入一筆壞資料、驗證舊資料。最後一欄來自系統目錄 pg_constraint：每個約束一列，convalidated 表示舊資料驗證過沒有。執行後由左到右看三欄：

  • 新資料：約束加上去的那一刻就擋住了新的壞資料（23503，外鍵違規）。
  • 驗證舊資料：VALIDATE 因為舊的第 3001 筆失敗。
  • 已驗證：convalidated 還是 false，約束仍然在擋新資料，只是還不能保證舊資料。

這個結果說明了 NOT VALID 的第二個用處：先止血。發現資料有問題時，先讓新的壞資料進不來，舊的慢慢修，修完再 VALIDATE。VALIDATE 失敗不會刪掉約束，修好資料後再跑一次就好。

回到 channel。PostgreSQL 18 起，NOT NULL 也是一個具名的約束，可以照同樣的兩步走：

ALTER TABLE 表 ADD CONSTRAINT 約束名 NOT NULL 欄位 NOT VALID;   -- 瞬間；新的 NULL 立刻被擋
-- 回填舊的 NULL …
ALTER TABLE 表 VALIDATE CONSTRAINT 約束名;                     -- SHARE UPDATE EXCLUSIVE，讀寫照常

加上之後怎麼確認狀態？要看兩個系統目錄。pg_constraint 裡，這個約束的 contype 是 'n'（not-null），還沒驗證時 convalidated 是 false。另一個是 pg_attribute：它每個欄位一列，其中 attnotnull 表示這個欄位是不是 NOT NULL。還沒驗證時它就已經是 true，因為新資料從這一刻起已經不能是 NULL。練習 2、3 會實際做一次。舊專案裡你還會看到 18 以前的繞路寫法（先加 CHECK 再轉成 NOT NULL），見課末「補充與查表」。

NOT VALID 期間的陷阱：約束管的是「新寫入或修改的列」。舊的 NULL 訂單被任何 UPDATE 改到（例如改狀態）時，PostgreSQL 寫出的新版本列還是 NULL，一樣被擋（23502）。所以順序是：先部署「寫入時一定會填 channel」的程式 → 加 NOT VALID → 緊接著回填 → VALIDATE，別讓中間的空窗拖太久。

兩步中間那一行「回填舊的 NULL」，在這頁是 429 筆，一句 UPDATE 就好；在正式環境，是 4,000 萬筆裡的 600 萬筆。它不拿強鎖，卻是整份計畫裡最容易出事的一步，下一節專門處理。

舊的 NULL 怎麼補？大量回填要拆成小批次

替新欄位或新規則補上舊資料的值，叫回填（backfill）。這課有兩處會用到：channel 的舊 NULL 要補成 'pos'；第一節的 volatile 預設值欄位、以及第三張單的 bigint 新欄位，都是先加空欄位再補值。最直覺的寫法是一句：

UPDATE orders SET channel = 'pos' WHERE channel IS NULL;   -- 4,000 萬筆裡的 600 萬筆

它只拿 ROW EXCLUSIVE，不擋讀取，看起來無害。但在大表上，一句 UPDATE 改 600 萬列，就是一個改了 600 萬列的交易，會帶來四個問題：

  • 一個很長的交易：被改到的每一列都拿著列鎖，直到整句結束。這段時間 App 要改其中任何一筆訂單（例如更新狀態），都要等。中途失敗就全部撤銷，從頭再來。
  • 大量死版本：PostgreSQL 更新一列時不是原地改，而是寫一個新版本、留下舊版本（第 30 課）。600 萬個舊版本要等交易結束後 VACUUM 才清得掉，在那之前表和索引一直膨脹。
  • WAL 暴增：PostgreSQL 每一筆修改寫進資料檔之前，會先寫進 WAL（Write-Ahead Log）這份日誌，當機時靠它復原（第 18 課提過）。600 萬筆更新就會產生同等份量的 WAL，磁碟、備份和複寫都要消化它。
  • replica 延遲：正式環境常有唯讀副本（replica），靠重播主機的 WAL 保持同步。一次湧入大量 WAL，副本跟不上，讀副本的使用者就會看到舊資料（第 37 課詳談）。

四個問題的根源都是「一次做太多」，所以解法是拆小：每批 1,000～5,000 列、每批自己一個交易、批次之間休息一下。每批的交易很短，列鎖很快放掉；VACUUM 在批次之間就能清掉前一批的死版本；WAL 和副本有時間消化。中途失敗只損失一批。

拆批次要先決定「這一批是哪幾列」。有兩種挑法：

  • 主鍵範圍：WHERE id BETWEEN 1 AND 5000 AND channel IS NULL，下一批 5001～10000。每批改到的筆數不固定（看那一段有多少 NULL），但每次只走主鍵索引的一小段，很好預估。
  • 挑固定筆數：UPDATE 沒有 LIMIT，要先用子查詢挑出「還沒處理、依 id 排在最前面的 N 筆」的 id，再更新這些 id。子查詢一定要寫 ORDER BY：沒有 ORDER BY 的 LIMIT 會拿到資料檔裡的實體順序，不是 id 順序（練習 5）。

正式環境由一支腳本跑迴圈。它可以中斷再續跑：條件裡有 channel IS NULL，處理過的列不會再被選到，腳本重啟後自然從還沒做的地方接著做。

let total = 0
for (;;) {
  const { rowCount } = await pool.query(`
    UPDATE orders SET channel = 'pos'
    WHERE id IN (/* 還沒處理、依 id 最前面的 2000 筆 */)`)
  total += rowCount
  if (rowCount === 0) break
  await sleep(200)                 // 讓 VACUUM、複寫、其他查詢喘口氣
  // 監控 replica 延遲，太大就暫停（第 37 課）
}

迴圈跑到 rowCount 是 0，表示舊的 NULL 補完了，這時再執行上一節的 VALIDATE CONSTRAINT，第一張單就完成了：整個過程只有加約束那一下拿了強鎖，而且是瞬間的。

💡 實務上：回填是一支獨立的 job，不是 migration 的一部分
回填可能跑好幾個小時，放進部署流程裡會卡住整個上線，而且失敗時很難判斷要不要回滾。常見做法是 migration 只做瞬間完成的 DDL，回填另外寫成可以續跑的腳本或背景 job，跑的時候記錄進度（處理到哪個 id、剩多少筆）。批次大小和休息時間先在演練環境試出來，正式跑時看資料庫 CPU 和 replica 延遲再調整。上線前也要跟維運或值班的人說一聲：這段時間 WAL 和磁碟用量會上升，是預期中的。

第一張單靠的是「約束可以先生效、後驗證」。第二張單的「手機不能重複」要靠唯一索引，而索引沒有 NOT VALID 這種選項：索引不建完，就沒辦法保證不重複。它需要另一種拆法。

第二張單：「手機不能重複」的唯一索引，怎麼建才不擋寫入？

保證欄位不重複的是唯一索引（第 20 課）。一般的 CREATE INDEX 拿 SHARE 鎖：讀照常，但所有寫入都要等。原因是它要掃過整張表、把每一列排序後建成索引，建的過程中如果有人插入或修改，新的列可能被漏掉，索引就不完整。最簡單的保證是建索引期間不准寫。顧客表小的時候這只是一瞬間；表大的時候，建索引的幾分鐘裡沒有人能註冊、沒有人能改資料。

CREATE INDEX CONCURRENTLY（以下簡稱 CIC）換一種方式保證完整：它只拿 SHARE UPDATE EXCLUSIVE，讓寫入照常進行，再用多做幾輪工作補上建索引期間被改到的列。代價有兩個：

  • 比較慢：要掃表兩次，還要等開始前已經在跑的交易全部結束，才能確定沒有漏掉的資料。
  • 不能放在交易裡：它內部會自己分成好幾個交易一段一段提交，所以不能被包進外層的 BEGIN … COMMIT。

第二個代價最常在部署時踩到。這頁同一格寫兩句就會被當成一個交易（所以課首說 CONCURRENTLY 要單獨一格），正好重現這個錯誤，執行後看錯誤碼：

正式環境更常見的情況是：migration 工具預設把每個檔案包在 BEGIN … COMMIT 裡，CIC 一跑就得到 25001 cannot run inside a transaction block。解法是讓這個檔案不包交易（工具通常有設定，例如在檔案開頭加註記），並且這個檔案只放這一句。DROP INDEX CONCURRENTLY、REINDEX CONCURRENTLY 也一樣。

還有一個問題：唯一索引建到一半，發現資料裡已經有重複的手機，會怎樣？

失敗會留下 INVALID 索引

一般的 CREATE INDEX 失敗時整個撤銷，什麼都不留下。CIC 不一樣：它是分段提交的，失敗時前面幾段已經提交了，所以會留下一個 INVALID 索引。查詢不會用它，但它還在：佔著這個名稱，讓下一次 CREATE INDEX 因為名稱重複而失敗，也讓人看 schema 時以為索引已經建好。

它還可能繼續影響寫入，看失敗在哪個階段（PostgreSQL 18 的 CREATE INDEX 文件）：如果失敗時它已經進入「寫入要維護」的階段，每次寫入都要多維護它；失敗發生在第二次掃表時，唯一索引還會繼續擋重複值。也就是說，一個查詢用不到的索引，可能還在拖慢寫入，甚至擋下資料。

要看出這些狀態，要查系統目錄 pg_index：每個索引一列，indisvalid 表示查詢能不能用，indisready 表示寫入時要不要維護它。這頁的 seed 重現了一次失敗：有人想替 customers.phone 建唯一索引，但林志豪和李建國的手機一樣。執行後看 customers_phone_uniq 那一列：

第三張單：訂單編號換成 bigint，怎麼讓新舊版程式同時能跑？

既然 ALTER COLUMN … TYPE bigint 一定會在強鎖底下重寫，就不要改原本的欄位，而是在旁邊建一個新的、慢慢把資料搬過去，最後一刻再切換。這就是第 22 課提過的 expand／contract：先擴充（新舊並存）、搬資料、最後收斂（移除舊的）。

為什麼要「新舊並存」一段時間，而不是搬完就切？因為正式環境的程式不會一瞬間全部換新。多台伺服器的服務，部署時通常是一台一台換成新版，這叫滾動部署（rolling deploy），好處是任何時刻都有伺服器在服務使用者。代價是部署期間，新舊兩版程式同時連著同一個資料庫，所以每一刻的 schema 都要讓兩版都能用。只要有一刻 schema 只認得其中一版，另一版就會報錯。

bigint 的步驟比較多，先用一個更簡單、但骨架相同的例子走一遍：把 customers.phone 改名為 mobile。改名本身是瞬間完成的（第一節的表），但只要一改，還在讀 phone 的舊版程式就全部壞掉，所以同樣不能一步完成。逐步播放，每一步注意 v1、v2 兩欄是不是都能運作：

步驟資料庫舊版程式（v1）新版程式（v2）
① expandADD COLUMN mobile＋同步 trigger讀寫 phone
② 回填分批 UPDATE … SET mobile = phone讀寫 phone
③ 部署 v2（不變）讀寫 phone（逐台下線）讀寫 mobile
④ contractDROP TRIGGER、DROP COLUMN phone（已全部下線）讀寫 mobile

這張時間軸能成立，靠的是第 ① 步的同步 trigger：任何一邊寫進來的值，都會被複製到另一欄，所以 v1 和 v2 同時在跑時看到的資料一致。trigger（第 23 課）長這樣。下面在 BEGIN … ROLLBACK 裡做完 expand 和回填，再模擬 v1 改 phone、v2 改 mobile、v2 新增顧客。執行後看最後的結果：每一列的 phone 和 mobile 都一樣：

回到訂單編號。integer 改 bigint 走的是同一個骨架，只是多了「換主鍵」這個切換動作，而這一路用到的正是前面三節的工具：

  1. expand：ADD COLUMN id_new bigint（沒有預設值，只改目錄、瞬間），同時建 trigger，讓新寫入的列自動把 id 複製到 id_new。
  2. 回填：照「舊的 NULL 怎麼補？」那一節的寫法，分批 UPDATE … SET id_new = id。
  3. 準備新主鍵：主鍵欄位必須是 NOT NULL。如果切換時 id_new 還沒標成 NOT NULL，PostgreSQL 會在那一刻補做 SET NOT NULL，在強鎖底下掃全表（ALTER TABLE 文件）。所以先用第一張單的 NOT VALID＋VALIDATE 讓它成為已驗證的 NOT NULL，再用 CREATE UNIQUE INDEX CONCURRENTLY 建好新主鍵要的唯一索引。
  4. 切換：在一個很短的交易裡改名、換主鍵（用建好的索引 PRIMARY KEY USING INDEX，跟上一節的 UNIQUE USING INDEX 同一個思路）、改序號。這一步仍然要 ACCESS EXCLUSIVE，但只改目錄、幾毫秒，配上 lock_timeout 就安全。

「改序號」值得多說幾句。訂單編號不是程式算的，而是由掛在舊 id 欄位上的 identity（第 2 課，底層是一個 sequence 計數器）發號；id_new 只是普通欄位，本身不會發號。切換時要讓 id_new 接手發號，而且起點要設在目前最大的編號之後。少了前者，新訂單的 INSERT 拿不到編號，撞上主鍵的 NOT NULL 而失敗；少了後者，計數器從頭發號，發出已經存在的編號，撞上主鍵的唯一性而失敗。這些也都放在同一個短交易裡，只改目錄。

  1. contract：確定沒有程式再用舊欄位後，刪掉 trigger 和舊欄位。

參照 orders.id 的外鍵欄位（例如訂單明細的 order_id）也要一起規劃：它們的型別要跟著換，外鍵也要改成參照新的主鍵。這類切換牽涉的物件多、順序重要，通常要寫好腳本、在正式資料量的副本上演練過才上線。

💡 實務上：先問「真的要改名嗎」，再記得收尾
expand／contract 要三到四次部署、跨好幾天，成本不低。欄位只是名字不好看時，很多團隊選擇不改，在程式裡用 ORM 的欄位對應換個名字就好（例如 Prisma 的 mobile String @map("phone")）。真的要做時，最常見的問題是 contract 一直沒做：trigger 和舊欄位留了半年，新人不知道哪個才是對的。所以開工時就把 contract 開成一張單、排進時程，PR 說明裡寫清楚「這是第幾步、下一步是什麼、什麼時候能退回」。

三張單都拆成了安全的步驟。但「安全」到目前為止都是在這頁 3,000 筆的資料上推論出來的，正式環境是 4,000 萬筆。上線前還差最後一道確認。

上線前，怎麼確定這份計畫在正式環境也安全？

前面每一個判斷，例如「瞬間完成」「讀寫照常」，都可以先在別的環境證明，而不是上線時才知道。上線前要過三關：

  • CI 從零跑一遍：用真的 PostgreSQL（同版本）從空資料庫跑完全部 migration，抓出語法錯誤與順序問題（DevOps 課第 15 課）。PostgreSQL 18 才有的寫法（例如 NOT NULL 的 NOT VALID），在舊版會直接報錯，版本不同就驗不出來。
  • 在正式資料量上演練：在接近正式資料量的副本（例如還原昨天的備份）上照順序跑一次，記下每一步的耗時和拿的鎖。3,000 筆瞬間完成的 VALIDATE，4,000 萬筆可能要十分鐘；這個數字決定了要不要挑離峰時段、回填要拆多小。
  • 和部署流程對好順序：哪些 migration 在新程式上線前跑（expand）、哪些在之後跑（contract），見 DevOps 課第 16 課（部署策略）與第 17 課（部署時的 migration）。

過了這三關，開場那三句會讓網站停擺的 ALTER TABLE，就變成了一份每一步都知道拿什麼鎖、要多久、失敗了怎麼辦的上線計畫。

補充與查表

PostgreSQL 18 以前怎麼零停機加 NOT NULL

18 以前 NOT NULL 不能 NOT VALID，要借 CHECK 繞路。你會在舊專案的 migration 看到：

ALTER TABLE orders ADD CONSTRAINT orders_channel_check CHECK (channel IS NOT NULL) NOT VALID;
-- 回填 …
ALTER TABLE orders VALIDATE CONSTRAINT orders_channel_check;
ALTER TABLE orders ALTER COLUMN channel SET NOT NULL;   -- 有已驗證的 CHECK 證明沒有 NULL，跳過掃描（文件）
ALTER TABLE orders DROP CONSTRAINT orders_channel_check;

NOT ENFORCED：名字很像 NOT VALID，意思完全不同

PostgreSQL 18 另外新增了 NOT ENFORCED（CHECK 與外鍵可用）：

新寫入的資料舊資料用途
NOT VALID檢查還沒檢查，之後 VALIDATE零停機加約束
NOT ENFORCED不檢查不檢查（也不能 VALIDATE，會報錯）只當文件或給工具看的宣告

分割表

分割表的父表不能用 CIC，第 35 課會講替代做法。

版本備註
  • PostgreSQL 11：固定預設值的 ADD COLUMN 不再重寫表；volatile 預設值仍然會重寫（ALTER TABLE 文件）。
  • PostgreSQL 18：NOT NULL 約束可以 NOT VALID 再 VALIDATE；CHECK 與外鍵可以宣告 NOT ENFORCED（和 NOT VALID 不同）。
  • 這頁的 PGlite 0.5.13（PostgreSQL 18.6）只有一條連線：lock_timeout 不會觸發、CIC 不用等別的交易，所以耗時和等待只能用文件與時間軸說明；鎖、重寫、indisvalid、錯誤碼都是在這裡實測的。

練習

練習 1：量出 ALTER TABLE orders ADD CONSTRAINT orders_customer_fk FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID 對兩張表拿了什麼強鎖。在同一次執行裡先執行它，再查自己（pg_backend_pid()）在 orders、customers 上的鎖，排除 AccessShareLock 與 RowShareLock，回傳表名（relation::regclass::text）與 mode，依表名排序。（不寫 BEGIN 時，同一格的多句會在同一個交易裡執行，鎖還在。）

練習 2：營業時間要先做到「新寫入的訂單不能沒有 channel」，但不能掃整張表，舊的 NULL 之後再處理。用 PostgreSQL 18 的寫法加上名為 orders_channel_not_null 的 NOT NULL 約束。

練習 3：接續上一題，orders_channel_not_null 已經以 NOT VALID 加上。把舊的 NULL 補成 'pos'，再讓這個約束變成已驗證，過程中讀寫都不能被擋。（這裡只有 429 筆，一句 UPDATE 就好；正式環境要照前面教的分批。）

練習 4：有人在營業時間跑 CREATE UNIQUE INDEX CONCURRENTLY 失敗了（這頁的 seed 重現了它）。寫一句可以放進每日健康檢查的查詢，列出資料庫裡所有 INVALID 的索引：索引名稱、所屬的表（都轉成文字），依索引名稱排序。這題的資料庫裡另外有一個建到最後一步才失敗的索引（indisready 是 true），所以不能寫死名稱。

練習 5：回填 orders.channel 的第一批：在 channel IS NULL 的訂單裡，把 id 最小的 100 筆設成 'pos'，用一句 UPDATE 完成。注意 NULL 分散在各處，而且資料檔裡的實體順序和 id 順序不同。這題的資料庫和頁面不同：另外有一些訂單（id 是 50 的倍數）的 channel 也是 NULL，所以不能靠這頁的資料算出 id 範圍。

練習 6：orders 有 1 億列，下面哪一句幾乎瞬間完成（假設馬上拿得到鎖）？

✓ 固定的預設值只記在目錄裡（fast default，PostgreSQL 11 起）。b：gen_random_uuid() 是 volatile，每列要各自算值，整張表重寫；「ADD COLUMN DEFAULT 都很快」只對固定值成立。c：改型別重寫表和索引。d：要在 ACCESS EXCLUSIVE 底下掃全表確認沒有 NULL。

練習 7：部署時 migration 失敗：CREATE INDEX CONCURRENTLY cannot run inside a transaction block。原因和解法？

✓ CIC 要在交易外執行，而很多 migration 工具預設把每個檔案包在交易裡，不會替你處理。a：每個版本都有這個限制。b：沒有 CONCURRENTLY 會拿 SHARE，建索引期間所有寫入都被擋。d：硬塞 COMMIT 會打亂工具的交易管理（之後的記錄可能不在交易裡）；工具若把整個檔案當成一次多句的查詢送出，CIC 仍在隱含的交易裡，照樣 25001。正確做法是用工具提供的「這個檔案不包交易」設定。另外記得：失敗的 CIC 可能留下 INVALID 索引，要先清掉再重來。

練習 8：營業時間要替 4,000 萬筆的 orders 加上參照 customers 的外鍵。哪個做法對？

✓ NOT VALID 瞬間加上、立刻檢查新資料；VALIDATE 只拿 SHARE UPDATE EXCLUSIVE（另外對被參照的表拿 ROW SHARE），讀寫照常。a：NOT ENFORCED 連新資料都不檢查，也不能 VALIDATE，等於沒有外鍵。c：SHARE ROW EXCLUSIVE 和寫入的 ROW EXCLUSIVE 衝突，掃全表的期間兩張表都不能寫。d：約束要先存在才能驗證。別忘了替 orders.customer_id 建索引（用 CONCURRENTLY）。

常見錯誤

  • DEFAULT 用 volatile 函式、直接改欄位型別：整張表在 ACCESS EXCLUSIVE 底下重寫。先加沒有預設值的欄位再分批回填；改型別用 expand／contract。
  • 直接 ADD CONSTRAINT 或 SET NOT NULL：大表上長時間掃描、擋住讀寫。用 NOT VALID＋VALIDATE。
  • 以為瞬間完成的 DDL 不用 lock_timeout：它會排在長查詢後面，再擋住後面所有人。每個 DDL 都設 lock_timeout 並重試。
  • 把 CONCURRENTLY 放進交易；失敗後留下 INVALID 索引沒清：殘骸可能拖慢寫入、繼續擋重複值，也佔著名稱讓重建失敗。健康檢查定期查 pg_index.indisvalid，DROP INDEX CONCURRENTLY 後重建。
  • 一句 UPDATE 回填整張表：長交易、膨脹、WAL 暴增、replica 落後。每批幾千列、各自提交、可以續跑。
  • 舊程式還在讀的欄位就先改名或刪掉：滾動部署期間舊版程式全部報錯。先 expand、部署、確認沒人用，再 contract。
  • 沒有在接近正式資料量的環境演練：開發機上 3 毫秒的 migration，正式環境可能 10 分鐘。演練並記下耗時與鎖。
  • 新的外鍵欄位忘了建索引：刪除顧客時要掃整張 orders 找參照（第 20 課）。

小結

  • 每個 DDL 先問：拿什麼鎖、要做多少事（只改目錄、掃全表、重寫表）。危險的是「強鎖＋大量工作」；用 pg_locks 與 pg_relation_filenode() 自己量。
  • 固定預設值的 ADD COLUMN 瞬間完成（fast default）；volatile 預設值與改型別會重寫表。
  • 鎖等待比鎖本身危險：每個 DDL 都設 lock_timeout，拿不到就放棄、稍後重試，一個交易只放一個 DDL。
  • 加規則（CHECK、外鍵、18 起的 NOT NULL）：先 NOT VALID 擋新資料，回填後 VALIDATE（SHARE UPDATE EXCLUSIVE，讀寫照常）。NOT ENFORCED 是另一回事。
  • 回填分批、每批一個交易、依 id 挑列、可以續跑，當成獨立的 job。
  • 建索引用 CREATE INDEX CONCURRENTLY，不能在交易裡；失敗會留下 INVALID 索引，查 pg_index.indisvalid。唯一約束用 UNIQUE USING INDEX 升級。
  • 改名與改型別用 expand／contract 配合滾動部署：新欄位＋同步 trigger、回填、在短交易裡切換、最後收尾。上線前在正式資料量上演練。
