階段 9：資深必備｜並發與正確性 · 第 33 課

用 PostgreSQL 做工作佇列：SKIP LOCKED、advisory lock 與 outbox

顧客在 App 下單之後，後端還有一串事要做：寄電子收據、印製作單給吧台、把營收同步到會計系統。如果全部塞在下單的 HTTP 請求裡，顧客要多等好幾秒；會計系統一掛，連下單都跟著失敗。實務做法是下單只負責「記下要做什麼」，真正的工作交給背景程式慢慢做。

這一課的任務就是把咖啡店下單後的這串事交給背景程式，而且要做到：工作不會漏、兩個背景程式不會搶同一件、程式當掉或外部服務壞掉時工作還收得回來、每天的報表只產生一份，最後連「通知資料庫以外的系統」也不會和訂單對不上。全程用 PostgreSQL 本身當工作佇列，一步一步做出來。

第一輪只要記住：
  • 多個 worker 取件用 FOR UPDATE SKIP LOCKED；標成 running 就提交，寄信這類慢的事在交易外做。
  • 佇列只保證「至少一次」：worker 可能做完、還沒標記完成就當掉，工作會被重做，所以處理方式要冪等。
  • 寫資料庫又要通知外部系統時，用 outbox：事件和訂單寫在同一個交易。專案裡先用現成的套件（例如 pg-boss），不要從頭寫。
這課的路線：
  1. 下單後的那串事，要怎麼交給背景做？設計 jobs 表，先講清楚佇列能保證什麼、不能保證什麼。
  2. 兩個 worker 同時取件，怎麼不重複也不排隊？FOR UPDATE 為什麼會讓大家排隊，SKIP LOCKED 怎麼讓每個 worker 各拿各的。
  3. 取走的工作做失敗、或 worker 當掉怎麼辦？租約、退避重試、dead letter。
  4. 回收程式和每日報表開了兩台，怎麼只跑一份？advisory lock。
  5. 沒工作時，worker 要多久查一次？LISTEN／NOTIFY。
  6. 要通知資料庫以外的系統，怎麼不會只成功一半？outbox。
  7. 什麼時候該換專門的佇列？流量、扇出、排程這幾條界線。
這課會用到：
  • 第 19 課的 FOR UPDATE 與 lost update：FOR UPDATE 讀的同時鎖住選到的列，直到交易結束；lost update 是兩個交易都先讀再寫，後寫的蓋掉先寫的。
  • 第 32 課的列鎖與 NOWAIT：拿不到列鎖的交易會排隊等；加上 NOWAIT 就不等，立刻報錯（55P03）。
  • 第 30 課的死版本與 VACUUM，以及「暫停的同事」：UPDATE 會留下舊版本，由 VACUUM 清掉；PREPARE TRANSACTION 讓一個交易停住、手上的鎖一直留著。
  • 第 31 課的 ON CONFLICT：INSERT 撞到 UNIQUE 時改成什麼都不做或更新，不報錯。
這頁的環境：這頁只有一條連線，看不到別人：另一個 worker 用停在交易裡的同事模擬，兩個 worker 搶件用時間軸示範。等鎖超過 5 秒，這頁會判定「在等鎖」並重置資料庫；ROLLBACK PREPARED 要單獨一格執行。LISTEN 和 NOTIFY 在同一條連線上，收到的通知在輸出區顯示成灰色的一行。

這頁的資料：jobs（10 件工作，第一節逐欄說明）、outbox（6 個事件，outbox 一節用）、orders（訂單 1001、1002）。

下單後的那串事，要怎麼交給背景做？

做法是讓下單 API 不自己寄收據，而是在資料庫裡留一筆待辦，例如「訂單 1001 要寄收據」，然後馬上回應顧客。另外有一支一直在執行的背景程式，定期來看有沒有待辦，有就拿去做，做完記下「完成」。

存放這些待辦的地方叫工作佇列（job queue），一筆待辦叫一件工作（job）。放工作進去的程式叫 producer，這裡就是下單 API；把工作取出來執行的背景程式叫 worker，也有人叫 consumer。worker 可以同時開好幾個，工作一多就平行處理。

佇列可以用專門的系統來做，這一課先用 PostgreSQL 的一張表。好處有兩個。第一，工作和訂單可以寫在第 18 課的同一個交易裡：訂單成立，工作就一定在；訂單 ROLLBACK，工作也跟著消失，不會留下一件「替不存在的訂單寄收據」的工作。第二，少維護一套系統。代價是流量很大時撐不住，這課最後一節再談界線在哪裡。

在動手設計之前，先講清楚佇列能保證什麼。佇列幾乎都只能保證 at-least-once，也就是「至少一次」：每件工作一定會被做到，但可能被做到兩次。原因是「做事」和「記下做完了」是兩個動作，中間可能當掉。例如 worker 寄出收據之後、還來不及在表裡標記「完成」就當掉了；從資料庫看，這件工作沒做完，只能交給別的 worker 重做，顧客就收到第二封收據。第三節會一步一步看到這件事怎麼發生。

既然重做擋不掉，就要讓重做無害。一件事做一次和做好幾次，結果都一樣，這種性質叫冪等（idempotent）。「把訂單 1001 標成已寄收據」是冪等的，做兩次還是同一個狀態；「寄一封收據」不是，做兩次顧客就收到兩封，要另外處理，例如寄之前先查這張訂單寄過沒。這一課每一節都會回到這個問題。

接著設計 jobs 表。worker 拿到一件工作，要知道做什麼、什麼時候可以做、現在是誰在做、失敗過幾次。這一頁的 jobs 表就是照這幾個問題設計的：

欄位用途
kind、payload jsonb工作種類與參數（第 14 課的 JSONB），例如 send_receipt、{"order_id": 1001}
statusqueued（等待中）、running（有人在做）、done、dead（放棄，等人工處理）
run_at最早什麼時候可以執行：延遲工作和重試都靠它
attempts、max_attempts已經嘗試幾次、最多幾次
locked_until租約到期時間（第三節解釋）
last_error上次失敗的原因，查問題用
dedupe_key UNIQUE去重鍵：同一張訂單的收據只能有一筆工作

最後一欄 dedupe_key 處理的是另一種重複。前面說的重做發生在 worker 那一端；producer 這一端也可能重複放工作。例如結帳 API 回應太慢，前端或閘道逾時後重送同一個請求，下單 API 就會跑第二次，又放一筆「訂單 1001 要寄收據」。這兩筆工作各自被做完，顧客一樣收到兩封收據。

擋法是讓同一件事只能有一筆工作：給每件工作一個由業務資料組成的去重鍵，例如 receipt:1001，欄位加上 UNIQUE。第二次放工作時撞到同一個鍵，搭配第 31 課的 INSERT … ON CONFLICT (dedupe_key) DO NOTHING，就安靜地什麼都不做，同一張訂單的收據工作只會有一筆。完整寫法留給練習 5。

表設計好，再想 worker 怎麼查它。worker 取件的查詢永遠是同一句：「status = 'queued'、run_at 已經到了，依 run_at 排序取前幾筆」。佇列表跑久了，裡面大部分是已完成的工作，真正在等的只佔一小部分。如果索引收了每一列，大部分空間都花在 worker 永遠不會查的 done 上。

第 27 課的部分索引正好解決這件事：建索引時加上 WHERE，只收符合條件的列。這裡只收 queued 的列，索引小、取件快；工作改成 running 或 done 之後，新的版本不符合條件，就不會進這個索引。

CREATE INDEX jobs_ready_idx ON jobs (run_at, id) WHERE status = 'queued';

💡 實務上：先分清楚哪些事可以晚一點做
開發新功能時，常要決定一件事放在請求裡同步做，還是丟進佇列。判斷方式是問：「這件事晚 30 秒完成，顧客或店員會不會發現？」寄收據、同步會計可以晚；扣庫存、確認付款通常要在請求裡就有結果。丟進佇列的工作，資深工程師會先問兩件事：重做一次會不會出事（冪等），以及一直失敗時誰會知道。這兩個問題沒答案，就先別急著非同步化。

表有了，下一步是讓 worker 來取件。只有一個 worker 時很單純；為了消化尖峰時段的工作開兩個以上，問題就來了：兩個 worker 會不會拿到同一件？

兩個 worker 同時取件，怎麼不重複也不排隊？

先試最直覺的寫法：「先查出一筆 queued，再把它改成 running」。兩個 worker 同時跑時，照時間軸一步一步看：

步驟worker Aworker B
1SELECT id … WHERE status = 'queued' LIMIT 1
拿到 1 號
2SELECT id … WHERE status = 'queued' LIMIT 1
也拿到 1 號
3UPDATE … SET status = 'running' WHERE id = 1
寄收據
4UPDATE … SET status = 'running' WHERE id = 1
又寄一次收據
5結果：1 號被處理兩次

問題出在查和改之間有空檔，這和第 19 課的 lost update 是同一類問題。第 19 課的解法是 FOR UPDATE：讀的同時鎖住那一列，別人要鎖同一列就得等。照第 19 課的習慣，拿著鎖把工作做完才 COMMIT。這樣不會重複了，但看看兩個 worker 在做什麼：

步驟worker Aworker B
1BEGIN;
SELECT … LIMIT 1 FOR UPDATE
鎖住 1 號，寄收據
2BEGIN;
SELECT … LIMIT 1 FOR UPDATE
等待中…
3UPDATE …; COMMIT;等待中…
41 號已經不是 queued，跳過
鎖住 2 號

重複處理解決了，換成排隊：每個 worker 都排序到同一件、排在同一列後面等，開再多 worker 也只有一個在做事。我們要的其實是第三種行為：遇到別人鎖著的工作，不要等，也不要報錯，直接換下一件。

這就是 SKIP LOCKED：加在 FOR UPDATE 後面，遇到被別人鎖住的列就跳過，當作它不在結果裡。A 鎖了最前面幾件，B 的查詢就自動略過它們，拿下一批，大家各做各的。

剛才 B 只是查出來並鎖住，還沒把工作標成 running。如果分成「先 SELECT … SKIP LOCKED，再 UPDATE」兩句，又得自己包交易，否則查和改之間又出現空檔。實務上取件寫成一句 UPDATE：子查詢用 SKIP LOCKED 選出並鎖住要的列，外層把它們標成 running，RETURNING（第 6 課）把工作內容交給 worker。一句就是一個交易，選和改之間沒有空檔：

UPDATE jobs
SET status = 'running', …
WHERE id IN (
  SELECT id FROM jobs
  WHERE …取件條件…
  ORDER BY …
  LIMIT n
  FOR UPDATE SKIP LOCKED
)
RETURNING id, kind, payload;

練習 1 會把 … 補完整。SKIP LOCKED 能這樣用，是因為佇列有一個特性：哪一件先被哪個 worker 拿走都沒關係，只要每件都有人做、沒有人重複做。反過來，需要看到完整資料的查詢就不能用它：

💡 實務上：先用現成的套件，不要自己從頭寫
這一課的寫法是為了讓你看懂原理；專案裡通常會用現成、以 PostgreSQL 為底的佇列套件，例如 Node.js 的 pg-boss、Graphile Worker，Go 的 River，它們底層同樣是 SKIP LOCKED，也已經處理好重試、排程和清理。懂原理的好處是：出問題時看得懂它的表、知道去查哪個欄位。評估套件時看維護是否活躍、能不能配合你用的連線池（第 25 課），以及能不能和訂單寫在同一個交易裡新增工作（後面 outbox 一節會說明為什麼重要）。

取件不重複、也不排隊了。但上面那句只把工作標成 running 就結束，真正寄信是在之後。這留下兩個問題：取件的交易應該多長？工作被標成 running 之後，worker 當掉怎麼辦？

取走的工作做失敗、或 worker 當掉怎麼辦？

先回答第一個問題：取件的交易要短，標成 running 就提交，寄信、呼叫 API 這些慢的事在交易外做。上一節第二張時間軸的寫法，是在交易裡把整件工作做完，等於拿著列鎖好幾秒，甚至好幾分鐘。交易一長有兩個代價：這段期間產生的舊版本不能被 VACUUM 清掉（第 30 課），而佇列表偏偏是一直在 UPDATE 的表，會越長越大；每個進行中的交易還各佔一條連線，worker 一多就可能把連線池佔滿。

可是交易一提交，列鎖就放開了，「這件工作是誰在做」再也沒有鎖在保護。worker 如果在寄信途中當掉，工作會永遠卡在 running：沒人在做，也沒有人會再去取它，因為取件只看 queued。

解法是租約（lease）。租約是一段有期限的使用權：worker 取件時順便寫下 locked_until = now() + interval '5 minutes'，意思是「5 分鐘內這件歸我」。期限內別人不會動它；期限過了還沒做完，就當作這個 worker 已經不在了，工作可以交給別人。有些佇列服務把同一個概念叫 visibility timeout。worker 做完就標成 done：

UPDATE jobs SET status = 'done', locked_until = NULL
WHERE id = $1 AND status = 'running';

租約過了還是 running，就代表 worker 大概掛了，由一個定期執行的回收程式把它改回 queued，你會在練習 2 寫出這句。租約要設得比工作正常需要的時間長，否則工作還在做，就被回收給別人，變成兩個 worker 同時在做。真的會做很久的工作，worker 要在做的過程中定期把 locked_until 往後延，這叫 heartbeat（心跳），用來告訴大家「我還活著」。

有了租約，把一件工作從取件到完成拆開，看 worker 在每一步當掉會怎樣：

worker 在哪一步當掉結果怎麼收拾
取件的交易提交前交易回滾，工作還是 queued別的 worker 直接取走，沒有影響
取件提交後、寄信前工作卡在 running，信還沒寄租約到期後被改回 queued，重做一次
寄信後、標成 done 前信已寄出，工作卡在 running租約到期後重做，信再寄一次：這就是 at-least-once，工作要冪等
標成 done 之後沒有影響不用收拾

第三列就是第一節說的「至少一次」實際發生的地方：寄信在資料庫外，資料庫的交易包不住它，所以重做擋不掉，只能讓寄信本身冪等。

租約處理的是 worker 當掉。另一種情況是 worker 好好的，工作本身失敗了，例如寄信伺服器逾時。這時不要馬上重試：對方可能還沒恢復，立刻重試只會再失敗一次，還給已經很吃力的對方增加負擔。做法是退避（backoff）：每多失敗一次就等更久再試，例如等 2 的 attempts 次方秒，第 1 次等 2 秒、第 3 次等 8 秒。實務上還會在等待時間上加一點隨機的抖動（jitter），因為同一個原因一起失敗的一批工作，如果等待時間完全相同，就會在同一秒一起重試，又一起撞上對方。

重試也要有上限。有些工作再試幾次都不會成功，例如資料本身就有錯。超過 max_attempts 就改成 dead，不再佔用 worker，留給人看 last_error 處理。這種放棄重試、等人處理的工作叫 dead letter（死信）。

💡 實務上：dead letter 要有人看得到
常見的事故是：寄信服務的金鑰過期，收據工作全部進了 dead，直到客服接到「沒收到收據」的抱怨才被發現。上線前至少要有兩個監控：dead 的數量，以及最舊一筆 queued 工作已經等了多久（佇列塞住時它會一直變大）。再準備一個讓人能查看 last_error、修好原因後把工作改回 queued 的方式，後台頁面或一段寫好的 SQL 都可以。

到這裡，咖啡店的佇列多了一支定期執行的回收程式。問題是，後端為了不停機部署通常開兩台以上，回收程式、每天早上產生前一天營業報表的排程，每台都會各跑一份。回收跑兩次還無害，報表產生兩份就麻煩了。要怎麼讓它們只跑一份？

回收程式和每日報表開了兩台，怎麼只跑一份？

前兩節用的鎖都鎖在 jobs 表的某一列上。「每日報表只能有一台在產生」這種需求，卻沒有一列可以鎖：報表還沒產生，表裡沒有它的列。我們需要的是一把「名字叫每日報表」的鎖，誰先拿到誰做。

PostgreSQL 的 advisory lock（建議鎖）就是這種鎖。它不屬於任何表或列，PostgreSQL 只管一件事：「key 是某個數字的鎖，同時只能一個人拿」。這個數字代表什麼，由你的程式自己決定，所以叫「建議」：資料庫不知道它保護的是什麼，只有大家都照約定先拿鎖再做事，它才有效。

key 是 bigint，但我們想用 'daily-report' 這種名稱，所以要把名稱轉成數字。hashtextextended(文字, 種子) 把文字算成一個 64 位元的雜湊值，同一段文字、同一個種子，永遠算出同一個數字，兩台排程器各自算，就會拿同一把鎖。

拿鎖用 pg_try_advisory_xact_lock(key)。名字裡的 try 是「不等待」：拿到回 true，被別人拿著就立刻回 false；xact 是「交易級」，交易結束時自動放掉。執行後看 got：

排程器的寫法：開交易，拿到鎖就產生報表，拿不到就代表另一台在做，直接結束。

BEGIN;
SELECT pg_try_advisory_xact_lock(hashtextextended('daily-report', 0));
-- true：產生報表；false：ROLLBACK，這次不做
COMMIT;   -- 交易結束，鎖自動釋放

為什麼用 hashtextextended，而不是名字更短的 hashtext？hashtext 只算出 32 位元的數字，值域小，不同名稱比較容易撞到同一個數字。一旦撞號，兩個毫無關係的排程會共用一把鎖，互相擋住，而且很難查出原因。

上面用的是交易級。advisory lock 還有另一種 session 級。session 是一條連線從連上到斷開的整段期間，session 級的鎖就跟著連線走，不跟著交易走。兩種的差別：

交易級（…_xact_lock）session 級（pg_advisory_lock 等）
什麼時候釋放交易結束時自動釋放，沒有 unlock 函式呼叫 pg_advisory_unlock，或連線斷開
ROLLBACK 時跟著放掉不受交易影響，ROLLBACK 之後還拿著
連線池 transaction 模式可以用不能用（下面解釋）

忘了 unlock，這把鎖會留到連線斷開。後端程式的連線通常來自連線池、會一直重用，「連線斷開」可能是好幾天以後。

更麻煩的是連線池本身。PgBouncer 的 transaction 模式（第 25 課）在每個交易結束時，就把連線交給下一個請求。官方文件寫明這個模式下不能用 session 級的功能，session 級 advisory lock 和下一節的 LISTEN 都在其中。原因是：你的鎖拿在一條連線上，交易一結束，那條連線就屬於別的請求了，鎖也跟著「被繼承」；你自己之後送出的 unlock，又可能經過另一條連線，放不掉原本那把。

所以經過 transaction 模式的連線池時，一律用交易級的版本：鎖和交易同生同滅，不管連線之後交給誰都不受影響。第 36 課會再談連線池。

💡 實務上：服務一開多台，排程就會重複跑
為了不停機部署或分散流量，後端通常會開兩台以上；如果每台都內建 cron（定時自動執行的排程），每日報表、到期提醒、優惠券發送就會各跑一次。常見的解法有兩種：排程交給只有一份的外部排程器（例如雲端的排程服務），或是像這裡用 advisory lock 讓搶到的那台執行。用鎖時要記得「拿不到就跳過」也可能代表那台卡住了，所以工作本身仍要冪等，並記錄每次執行的結果，事後才查得到哪天沒跑。

排程只跑一份了。回到 worker 本身，還有一個一直沒處理的問題：前面的 worker 都是自己去查佇列，那沒工作的時候，要多久查一次？

沒工作時，worker 要多久查一次？

這個問題兩頭為難。每秒查一次，幾個 worker 整天對資料庫送查詢，絕大多數都查不到東西；每分鐘查一次，顧客下單後最久要等一分鐘才收到收據。我們想要的是：平常不查，有新工作時有人「叫一聲」。

PostgreSQL 內建這個功能，叫 LISTEN／NOTIFY。worker 先執行 LISTEN jobs，表示「我在聽 jobs 這個頻道」；之後任何連線執行 NOTIFY jobs, '…'，所有在聽這個頻道的連線都會收到這則通知。執行後看輸出區上方灰色的那一行：

通知有一個重要的性質：要等交易提交才送出，ROLLBACK 的話就不送。這正是我們要的：下單交易如果回滾，工作沒有寫進去，也就不該叫醒 worker。下面這格不會收到通知：

接下來讓「新增工作」自動發通知，不必每個 producer 都記得寫 NOTIFY。做法是第 23 課的 trigger：jobs 每新增一列，就自動送一則通知，內容放這件工作的 id。這格用到三樣新東西：

  • pg_notify(頻道, 文字) 是 NOTIFY 的函式版本，內容可以放 NEW.id 這類執行時才知道的值。
  • PL/pgSQL 裡呼叫函式但不需要它的回傳值時，用 PERFORM 取代 SELECT（直接寫 SELECT 會報錯「沒有地方放結果」）。
  • CREATE OR REPLACE TRIGGER 是「沒有就建立、有就取代」，這格重複執行也不會出錯。

看起來很理想，但 NOTIFY 有一個決定性的限制：沒人在聽，通知就消失。PostgreSQL 不會替你保存，worker 重啟的那幾秒送出的通知，之後不會補發。所以 NOTIFY 只能當「提示」，不能當佇列本身：工作一定要存在 jobs 表裡，worker 也還是要定期輪詢，例如每 30 秒查一次，把漏掉通知的工作撿起來。通知的作用是讓 worker「現在就去查」，平常的延遲從 30 秒縮到幾乎即時。

也因為工作本身放在表裡，通知的內容只要放 id，不必放整件工作的資料。另外，worker 要一直佔著一條連線 LISTEN；LISTEN 是上一節說的 session 級功能，這條連線不能經過 transaction 模式的連線池，要直連資料庫。payload 的大小限制見課末「補充與查表」。

到這裡，咖啡店的工作都在同一個資料庫裡，工作和訂單可以寫進同一個交易，所以「訂單成立、工作卻沒放進去」不會發生。但開場那串事裡，有些要通知的對象根本不在這個資料庫裡。

要通知資料庫以外的系統，怎麼不會只成功一半？

下單後要通知其他服務，例如外送平台、會員點數系統。這些服務不會來讀咖啡店的 jobs 表，通常的做法是送一則事件到訊息系統（Kafka、RabbitMQ 等），由各個服務自己去收。事件是一則「發生了什麼事」的訊息，例如「訂單 1003 成立了」。

問題是「寫訂單」和「送事件」分屬兩個系統，沒辦法放進同一個交易：PostgreSQL 的 ROLLBACK 收不回已經送到 Kafka 的訊息，Kafka 也不知道 PostgreSQL 的交易有沒有提交。不管先做哪一件，中間當掉都會只成功一半。這叫雙寫問題（dual write）：

順序中間當掉的結果
先 COMMIT 訂單，再送事件訂單成立了，事件沒送出：外送平台永遠不知道有這張單
先送事件，再 COMMIT 訂單事件送出了，訂單卻 ROLLBACK：外送平台去送一張不存在的單

解法借用這課前面的做法：既然 jobs 表能和訂單寫在同一個交易，事件也可以先當成一列資料寫進資料庫。這叫 transactional outbox：不要直接送事件，把它寫進 outbox 表，和訂單放在同一個交易。訂單成立，事件就一定在；訂單 ROLLBACK，事件也跟著消失。然後由另一支叫 relay 的程式，從 outbox 取出還沒送的事件，送到訊息系統，送完再標記 published_at。relay 做的事和 worker 一樣，只是它的「工作」是轉送事件。

先做 producer 這一半。用一句 CTE 同時寫訂單和 outbox，一句就是一個交易。第 16 課的 CTE 裡放的是 SELECT；WITH 裡也可以放 INSERT … RETURNING，外層就能用它剛產生的訂單 id。執行後看 payload 裡的 order_id：

再看整張 outbox：新事件排在最後，published_at 是空的，等 relay 來取。

relay 這一半，取件方式和 worker 一模一樣：用 SKIP LOCKED 批次取出，多個 relay 可以同時跑而不重複，你會在練習 4 寫出這句。

outbox 解決的是「只成功一半」，不是重複。它仍然是 at-least-once：relay 把事件送出之後、標記 published_at 之前當掉，下一次會再送一次，和第三節寄兩次收據是同一回事。所以每個事件要帶唯一的 id，消費端（例如外送平台）收到時用它去重，做到冪等。

更完整的 relay 架構在系統設計課第 12 課；不用輪詢 outbox 的另一種做法，見課末「補充與查表」。

jobs 表和 outbox 都建在 PostgreSQL 上，咖啡店目前的流量用得很順。最後一個問題是：什麼時候這樣做會不夠？

什麼時候該換專門的佇列？

PostgreSQL 佇列適合中小流量、而且工作和業務資料要一致的場景。判斷要不要換，看的是前面每一節付出的代價會不會被放大。下面這些情況就該考慮專門的工具：

  • 每秒上千件以上：每件工作至少一次 INSERT 和兩次 UPDATE，每次 UPDATE 都留下死版本。佇列表會快速膨脹，要調 autovacuum（第 30 課），或依日期分割、整個分區丟掉（第 35 課）。
  • 一個事件要給很多消費者，而且每個消費者有自己的進度：例如「訂單成立」要同時給外送平台、會員點數、報表系統，各自讀到哪裡不一樣。這種一對多的發送叫扇出（fan-out）。jobs 表做不到，因為一件工作被做完就標成 done，只適合給一個消費者。Kafka 這類 log 型系統的做法不同：事件依序附加保存，不會因為被讀過就刪掉，每個消費者各自記住自己讀到第幾筆（這個位置叫 offset）。所以同一則事件可以給很多消費者，各自照自己的速度往前讀。
  • 大量延遲工作、需要排程、優先順序、限流：Redis 上的 BullMQ（NestJS 課第 20 課）、SQS、RabbitMQ 都內建。

換掉佇列不代表丟掉 outbox：只要「寫資料庫」和「送訊息」要一致，outbox 仍然是把兩者接起來的方法。

補充與查表

  • SKIP LOCKED 的版本：PostgreSQL 9.5 起提供。
  • advisory lock 的另一種 key：除了一個 bigint，也可以用兩個 int 參數的版本，例如 (表的編號, 列的 id)。
  • 不要在有 LIMIT 的查詢裡直接呼叫鎖函式：文件提醒，LIMIT 不保證在呼叫之前套用，可能鎖到你沒預期的 key；先用子查詢取好 id 再上鎖。
  • PgBouncer transaction 模式的限制：上面「不能用 session 級的功能」依據的是 PgBouncer 1.26.1 的官方文件。
  • NOTIFY 的 payload 大小：預設設定下要小於 8000 bytes，文件建議放 id，資料本身放在表裡。
  • CDC（change data capture）：relay 不輪詢 outbox，改成直接讀資料庫的變更紀錄，在系統設計課第 12 課。

練習 1：worker A 已經取走 1、2 號並停在交易裡（題目已設定好）。寫 worker B 的一句取件：最多 2 件、status = 'queued' 而且已到執行時間、依 run_at 再依 id 先進先出、跳過被鎖住的；把它們標成 running、attempts 加 1、locked_until 設成 5 分鐘後，回傳 id 與 kind。

練習 2：有 worker 當掉了。寫一句 UPDATE 回收租約已過期（locked_until < now()）的 running 工作：attempts 還沒到 max_attempts 的改回 queued，已經到了的改成 dead；兩種都要清掉 locked_until。租約還沒到期的工作不能動。每件工作的上限不一定都是 5，題目另外加了幾件當掉的工作。

練習 3：另一台排程器已經拿到每日報表的交易級 advisory lock，並停在交易裡（題目已設定好）。寫第二台排程器要執行的一句查詢：不等待地嘗試拿同一把交易級的鎖（key 用 hashtextextended('daily-report', 0)），回傳一欄 got。

練習 4：relay A 已經取走 outbox 的 1 號事件，正停在交易裡送出（題目已設定好）。寫 relay B 的一句批次：最多 3 筆還沒送出（published_at IS NULL）的事件、依 id、跳過被鎖住的，標記 published_at = now()，回傳 id 與 topic。判分看最後哪些事件被標記。

練習 5：同一張訂單的寄收據工作只能有一筆，dedupe_key 有 UNIQUE，格式是 receipt:訂單編號。結帳 API 被重試了，要再替訂單 1001 和 1002 各放一筆寄收據工作（kind 是 send_receipt，payload 是 {"order_id": 訂單編號}）。1001 已經有了（而且已經寄出）。寫一句 INSERT：已經有的就什麼都不做，不能出錯，也不能讓已完成的工作重新排隊。

練習 6：開了 10 個 worker，每個都是 BEGIN、SELECT … ORDER BY run_at LIMIT 1 FOR UPDATE（沒有 SKIP LOCKED）、處理完再 COMMIT。佇列裡有 1000 件工作，吞吐量會怎樣？

✓ c：FOR UPDATE 防住了重複，但 10 個 worker 都排序到同一件、排在同一列後面等；前一個提交後，下一個才跳過它、去鎖下一件。加了鎖不等於能平行處理，要 SKIP LOCKED 才會各拿各的。a 錯在忽略了等待；b 錯在每個交易只鎖一列、順序一致，沒有互相等待的環，不會死結；d 錯在鎖正好防住了重複處理。

練習 7：新增工作時 trigger 執行 pg_notify('jobs', …)。剛好那時所有 worker 都在重啟，沒有人在 LISTEN。這則通知會怎樣？

✓ NOTIFY 只送給「當下」在聽的連線，不會保存。所以它只能當「有新工作，快去查」的提示，真正的工作要存在表裡，worker 仍要定期輪詢。INSERT 不受影響。

練習 8：worker 寄出收據後、標記 done 之前當掉。租約到期後工作被回收，另一個 worker 又寄了一次。該往哪個方向修？

✓ 寄信是資料庫外的動作，資料庫的交易包不住它，所以只要有重試，就可能做兩次。正確方向是讓處理冪等。租約永不過期的話，worker 當掉的工作就永遠卡在 running。

練習 9：排程器經過 PgBouncer（transaction 模式）連資料庫，用 pg_advisory_lock（session 級）當互斥鎖，做完再 pg_advisory_unlock。會怎樣？

✓ transaction 模式下，每個交易結束後連線就回到池子。session 級的鎖跟著「連線」，不跟著你的程式，所以可能拿著不放、或被別的請求「繼承」。PostgreSQL 不知道前面有連線池，不會報錯。改用 pg_try_advisory_xact_lock，交易結束自動釋放。

常見錯誤

  • 取件後在同一個交易裡做完整件工作：交易拉長、一直拿著列鎖、擋住 VACUUM 清理。取件交易只做「標記 running、寫租約」，工作在交易外做。
  • 沒有租約：worker 當掉，工作永遠卡在 running。取件時寫 locked_until，定期回收過期的。
  • 無限重試、沒有 dead letter：壞掉的工作一直重試，佔滿 worker。設 max_attempts、退避，超過就 dead，並設告警。
  • 把 NOTIFY 當成可靠的佇列：沒人在聽就消失，ROLLBACK 也不送。通知只是提示，工作要存在表裡。
  • 佇列表不管 autovacuum：大量 UPDATE、DELETE 造成表和索引膨脹，取件越來越慢。調整這張表的 autovacuum 參數，或依日期分割（第 30、35 課）。
  • advisory lock 的 key 用 32 位元 hashtext：容易撞號，讓無關的工作互相擋住。用 hashtextextended 或兩個 int 的版本。
  • 經過 transaction 模式的連線池用 session 級 advisory lock 或 LISTEN：連線會換人。用交易級的鎖；LISTEN 用一條直連的專用連線。
  • 以為 outbox 能做到剛好一次：relay 送出後、標記前當掉，事件會重送。消費端要依事件 id 去重。

小結

  • 工作佇列把慢的、會失敗的事移出請求：下單 API 只留一筆待辦，worker 在背景做。用 PostgreSQL 當佇列，工作和訂單能寫在同一個交易。
  • 佇列只保證 at-least-once：「做事」和「記下做完」之間可能當掉，所以處理要冪等。
  • jobs 表：狀態、run_at、嘗試次數、租約、去重鍵；用部分索引 WHERE status = 'queued' 支撐取件。
  • 取件寫成一句 UPDATE … WHERE id IN (SELECT … ORDER BY … LIMIT n FOR UPDATE SKIP LOCKED) RETURNING …：不重複、不互等。
  • 取件交易要短；用租約回收當掉的工作，失敗時退避重試，超過上限進 dead letter。
  • advisory lock 讓排程只跑一份；經過連線池時用交易級的 pg_try_advisory_xact_lock，key 用 hashtextextended。
  • LISTEN／NOTIFY 只在提交時送出、沒人聽就消失，只當叫醒 worker 的提示，worker 仍要定期輪詢。
  • outbox 把事件和業務資料寫在同一個交易，再由 relay 送出，解決雙寫問題；它仍是 at-least-once，消費端要去重。

INSERT INTO coupon_claims (coupon_id, customer_id) VALUES (7, $1);
COMMIT;

✓ 規則是「先數別的列，再寫自己的列」，兩人寫的是不同的列，REPEATABLE READ 不報錯，這就是寫入偏差。修法是 SERIALIZABLE 加重試，或先 FOR UPDATE 鎖住共同的父列（那張優惠券）再數。b 錯在 REPEATABLE READ 只在改到別人剛改過的同一列時才得到 40001，這裡兩人新增的是不同的列。（第 31 課）

練習 12：扣庫存寫成 UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1。同事說預設的 READ COMMITTED 不安全，要改 SERIALIZABLE，你怎麼回？

✓ READ COMMITTED 的 UPDATE 遇到別人正在改的列會等，對方提交後拿最新版本重新檢查 WHERE，不成立就影響 0 列，程式看影響列數判斷。改 SERIALIZABLE 只是多了重試的成本。a 錯在重新檢查用的是最新版本，不是句子開始時的快照；要小心的是條件讀別的列，那才需要 SERIALIZABLE 或鎖父列。（第 31 課）

練習 13：接收第三方 webhook 同步會員資料，同一筆可能同時送來兩次。現在的寫法是先 SELECT … WHERE external_id = $1，沒有就 INSERT、有就 UPDATE。怎麼改最可靠？

✓ 兩個請求同時查到「沒有」就會都新增：重複兩筆，或撞 23505。讓唯一約束當裁判：ON CONFLICT 遇到正在新增同一個 key 的交易會等它結束，提交就改做 UPDATE。c 錯在 MERGE 同時新增同一個 key 時會直接撞唯一約束錯誤，它適合單一程序的批次同步。（第 31 課）

練習 14：結帳交易用 SERIALIZABLE，包在共用的 withRetry 裡（收到 40001 或 40P01 就 ROLLBACK、從頭重做）。哪裡會出事？

await withRetry(async (tx) => {
  const order = await createOrder(tx, cart);
  await sendReceiptEmail(order);
  await addPoints(tx, order);
});

✓ 會被重試的交易可能執行好幾次，寄信撤不回，重做一次就多一封；等外部服務也讓交易變長、衝突變多。寄信移到提交之後，或做成冪等。b 錯在重試的範圍是資料庫交易：重做整個請求，裡面的外部呼叫也跟著重做，例如重複扣款。（第 31 課）

練習 15：營業時間要對 orders 執行 ALTER TABLE orders ADD COLUMN note text，這句本身幾毫秒就完成。怎麼做最安全？

✓ 危險的不是 ALTER 本身，是等鎖：它排在長查詢後面等 ACCESS EXCLUSIVE，後面所有讀寫又排在它後面，整個網站卡住。設了 lock_timeout，等不到就放棄，佇列跟著解開，晚點再試。d 錯在大多數 ALTER TABLE 拿的是 ACCESS EXCLUSIVE，連 SELECT 都會被擋。（第 32 課）

練習 16：同步會計的 worker 這樣取件和處理，開了 5 個。哪裡會出事？

BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'queued' ORDER BY run_at
LIMIT 1 FOR UPDATE SKIP LOCKED;
-- 呼叫會計系統 API：平常 3 秒，慢的時候 1 分鐘
UPDATE jobs SET status = 'done' WHERE id = $1;
COMMIT;

✓ 取件交易去等外部 API，交易被拉長，期間 VACUUM 清不掉死版本，而佇列表正是大量 UPDATE 的表。取件交易只做「標記 running、寫租約」就 COMMIT，工作在交易外做，失敗靠租約回收。a 錯在 SKIP LOCKED 直接跳過被鎖的列，其他 worker 不會排隊。（第 33 課）

練習 17：下單後要送事件到 Kafka 通知外送平台。哪個做法不會出現「訂單成立、事件沒送」或「事件送了、訂單卻不存在」？

✓ 寫訂單和送事件是兩個系統，放不進同一個交易（雙寫問題）；事件當成一列資料和訂單一起提交，就一起成立或一起消失。relay 送出後、標記前當掉會重送，消費端要依事件 id 去重。a 錯在程式剛 COMMIT 完就當掉時，重試的程式碼根本沒機會執行，事件就永遠沒送。（第 33 課）

這個階段的重點整理成一頁圖解。
