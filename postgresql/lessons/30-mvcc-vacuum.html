階段 9：資深必備｜並發與正確性 · 第 30 課

MVCC 內部：列的版本、VACUUM 與表膨脹

咖啡店的集點卡表 stamp_cards 只有兩千位會員，每位會員一列，每買一杯咖啡就把那一列的 stamps 加 1。列數幾乎沒變，資料表的檔案卻一天比一天大，查詢也越來越慢；明明每晚都有排程跑 VACUUM，空間就是收不回來。這一課從頭到尾都在查這張表：它裡面實際存了什麼、空間為什麼收不回來、是什麼擋住了清理，最後動手修好它。

要回答這些問題，得先知道 PostgreSQL 在表裡實際存了什麼。第 19 課說過 MVCC 讓「讀不擋寫」，代價是每次修改都留下舊版本。這一課打開資料頁，看版本怎麼產生、誰決定看得到哪一個、什麼時候能清掉、為什麼有時候清不掉。學完你能判斷一張表為什麼膨脹，找出擋住清理的交易，並調整表讓更新少產生垃圾。

第一輪只要記住：
  • UPDATE 不會原地改，而是寫一個新版本，舊版本變成死版本。VACUUM 讓死版本的空間能重複使用，但不會讓檔案變小。
  • 只要有一個交易開著不收尾（例如程式忘了 COMMIT），整個資料庫的死版本都清不掉，表會一直膨脹。
  • 常被更新的欄位不要隨手建索引；autovacuum 不要關。
快照的格式、pageinspect、凍結的門檻這些細節，工作上遇到再回來查。
這課的路線：
  1. UPDATE 之後，舊的那一列去哪了？打開資料頁，看 UPDATE、ROLLBACK 留下了什麼。
  2. 舊版本誰來清？VACUUM 做了什麼、為什麼檔案不會變小（開場問題的最小答案）。
  3. 「沒有交易看得到」是誰說了算？快照與可見性規則。
  4. VACUUM 為什麼清不掉？用可見性規則推出清理界線，找出擋住清理的交易。
  5. 能不能讓更新少產生垃圾？HOT 更新與 fillfactor，找出集點卡表垃圾特別多的原因和修法。
  6. 正式環境誰來跑 VACUUM？autovacuum 什麼時候觸發，以及交易編號用完之前會發生什麼事（凍結）。
這課會用到：
  • 第 18 課的交易：BEGIN 開始，COMMIT 或 ROLLBACK 結束，中間的修改一起生效或一起取消。
  • 第 19 課的 MVCC 與 FOR UPDATE：修改一列時寫一個新版本，正在讀的人繼續看舊版本，所以讀不擋寫；FOR UPDATE 讀的同時鎖住選到的列，直到交易結束。
這頁的環境：資料庫是 PGlite 0.5.13（PostgreSQL 18.6），只有一條連線、看不到別人，「另一個人的交易」用暫停的同事模擬；有句子在等鎖時，約 5 秒後引擎會重置頁面資料庫。沒有 autovacuum 在背景跑，VACUUM 都手動執行；每次執行後統計立刻更新，正式環境會延遲。

這頁的資料：products（6 項商品）、big（2 萬列，膨脹實驗用）、stamp_cards（開場的集點卡表，2,000 張），以及練習用的 orders、sessions、order_items、coupons。

UPDATE 之後，舊的那一列去哪了？

集點卡表列數沒變、檔案卻變大，表示表裡存的東西比 SELECT 看到的多。第一步先弄清楚一次 UPDATE 在表裡留下了什麼。這一節用 products 示範，不直接用 stamp_cards：商品只有 6 列，全部放在同一頁裡，每個變化都看得清楚；集點卡的每次集點也是一次 UPDATE，機制完全一樣，第 5 節會回到它。

先認識表在磁碟上的樣子。PostgreSQL 把每張表存成一個檔案，檔案切成一個個 8 kB 的資料頁（page），讀寫都以頁為單位。每一頁裡有很多格，一格放一列資料的一個版本。為什麼說「一個版本」？第 19 課講過，有人修改一列時，正在讀的人要能繼續看到修改前的樣子，所以 PostgreSQL 不能直接把舊值蓋掉，同一列會同時存在新舊好幾份。表裡一列資料的某一個版本，叫列版本（tuple）。

既然同一列有好幾個版本，PostgreSQL 就要記下每個版本是誰建立的、是誰刪掉的，才能判斷某個讀取的人該看哪一份。記錄的單位是交易編號（transaction ID，簡稱 XID）：會寫資料的交易，在第一次寫入時拿到一個流水號，越新的交易號碼越大。只讀不寫的交易不會拿號碼。每個列版本都帶著幾個隱藏欄位記錄這些資訊，平常 SELECT * 看不到，指名就看得到：

xmin建立這個版本的交易編號
xmax刪除（或鎖住）這個版本的交易編號；0 代表沒有

  • xmin 變成這次 UPDATE 的交易編號。

拿鐵為什麼搬家？因為 PostgreSQL 的 UPDATE（第 6 課）不會原地改。它做兩件事：把舊版本的 xmax 填上自己的交易編號，表示「這個版本被我刪掉了」；再寫一個新版本到空的格子，新版本的 xmin 是自己。DELETE 只做前一半：填上舊版本的 xmax，不寫新版本。SELECT 只回傳「你看得到的」版本，所以結果裡 (0,2) 消失了，但那個 110 元的拿鐵還在頁裡。

如果做到一半反悔，交易最後 ROLLBACK 呢？舊版本的 xmax 已經填上了，新版本也寫出去了，PostgreSQL 要把它們改回去嗎？執行後看美式咖啡那一列：

  • 價格還是 80 元，位置還是 (0,1)。
  • xmax 不是 0 了：那是被取消的交易留下的編號。PostgreSQL 另外記錄每個交易最後是提交還是取消，看到這個 xmax 時會去查，知道它沒有提交，所以這個舊版本仍然有效。

被取消的交易寫出的新版本（999 元）則沒有人看得到。ROLLBACK 不會把頁面改回原樣，它只是讓那些版本永遠無效。這樣 ROLLBACK 才能很快完成，不管交易改了多少列，代價是頁裡又多了一個沒用的版本。

到這裡，「舊版本還在頁裡」都還是推論，因為 SELECT 不會給你看看不到的版本。要親眼確認，用 pageinspect：它是 PostgreSQL 附帶的擴充套件，直接讀出某一頁的原始內容，不管誰看得到、看不到，每一格都列出來。它是學習和診斷用的工具，平常寫程式不會用到。讀第 0 頁：

  • lp 是格子編號，t_xmin、t_xmax 就是前面的 xmin、xmax。
  • t_ctid 指向「下一個版本」在哪：第 2 格的拿鐵指向第 7 格，第 1 格的美式咖啡指向第 8 格（那個被取消的 999 元）。
  • 最後兩欄是 HOT 標記，第 5 節會用到，先不管。

所以集點卡表變大的第一個原因找到了：每集一次點就是一次 UPDATE，每次都在表裡多留下一個舊版本。兩千位會員集了幾千次點，表裡就有幾千個沒人要看的舊版本。下一個問題是：這些舊版本會一直留著嗎？誰負責清掉它們？

舊版本誰來清？為什麼 VACUUM 之後檔案沒變小？

上一節第 2 格那個 110 元的拿鐵，已經沒有交易看得到，卻還佔著頁裡的位置。沒有任何交易還看得到的版本叫死版本（dead tuple）；反過來，還有交易看得到的叫活版本。「看得到」的精確規則第 3 節再講，這裡先用直覺理解：舊的價格已經被新的取代、而且沒有人還在讀舊價格，它就死了。

PostgreSQL 不會在交易提交的當下就把舊版本清掉。提交的那一刻，可能還有別的交易正在讀舊版本，現在清掉它們就讀不到了；而且每次提交都去整理頁面，寫入會變慢。所以清理延後，交給一個獨立的工作：VACUUM。一次 VACUUM 大致做這幾件事：

  1. 掃過表，找出死版本。
  2. 把每個索引裡指向這些死版本的紀錄移除，再把死版本佔的格子空出來。
  3. 把每一頁還剩多少空位記進 free space map。它是每張表旁邊的一份小紀錄，之後要寫入新版本時，PostgreSQL 查它就知道哪一頁有空位，不用一頁頁去找。
  4. 更新 visibility map：記下哪些頁裡的版本全部對所有交易都可見。第 21 課的 Index Only Scan 靠它判斷能不能不回表；下次 VACUUM 也靠它跳過不需要處理的頁。

接下來用 big 這張 20,000 列的表做實驗，觀察 VACUUM 前後的變化。products 太小，大小的變化看不出來。要觀察，需要兩種數字：表的檔案多大，以及表裡有幾個活版本、幾個死版本。後者在 pg_stat_user_tables：它是一個系統視圖（system view），也就是 PostgreSQL 內建、可以像表一樣查詢的資訊，每張使用者建立的表一列，記錄這張表被新增、更新、刪除了幾次、現在大約有幾個活版本和死版本。執行後看三欄：

  • size：pg_relation_size 是表本身的大小，不含索引。
  • n_live_tup、n_dead_tup：活版本數和死版本數。它們來自累計統計，是 PostgreSQL 一邊執行一邊累加的估計值，不是現場數出來的；正式環境要等一下才看得到最新的數字（見課首「這頁的環境」）。

常見情境：維運說磁碟快滿，你把半年前的 sessions 刪掉，結果雲端主控台上的用量一點都沒降。這是預期行為：autovacuum 跑過後，空間被標成可重用，新寫入的資料會先填進這些空位，填滿之前表不會再長大。資深會先問「它還在長，還是只是沒縮？」；還在長才是問題，通常代表 VACUUM 跟不上或被擋住，集點卡表就是這種情況。確定那些空間不會再被填回（例如一次性清掉大量歷史資料）才考慮在離峰用 pg_repack 重整；固定要清舊資料的表，可以改用分區直接丟掉整個分區（第 35 課）。

所以要查集點卡表，第一個問題是：VACUUM 有沒有被擋住？VERBOSE 裡有一行 dead but not yet removable，代表「死了但還不能清」。一個版本明明沒用了，為什麼會不能清？要回答這個，得先把「沒有交易看得到」講精確：誰看得到哪個版本，是由什麼決定的？

「沒有交易看得到」是誰說了算？

前兩節的「看得到」「沒有交易看得到」都還只是直覺。要看清楚規則，需要另一個正在進行、還沒提交的交易，讓「你」和「別人」看到的不一樣。這頁只有一條連線（見課首），沒辦法真的開兩個人，所以借用 PREPARE TRANSACTION 來模擬。

PREPARE TRANSACTION 是兩階段提交（two-phase commit）的第一步。兩階段提交用在一筆工作要同時寫進好幾個資料庫的時候：先讓每個資料庫都「準備好」，確認大家都能提交，再一起提交。準備好的交易會停在「已準備、還沒提交」的狀態，跟原本的連線脫鉤，連線本身可以繼續做別的事，之後再由任何一條連線 COMMIT PREPARED 或 ROLLBACK PREPARED 收尾。對我們來說，它就像一位做到一半、被按了暫停的同事：他改的東西你看不到，他鎖住的列你拿不到。

PostgreSQL 文件明說 PREPARE TRANSACTION 不是給應用程式或互動操作用的，它是外部交易協調器（transaction manager）跨資料庫做原子提交的工具。prepared transaction 會一直佔著鎖和交易編號，連線斷了、伺服器重啟了都還在，直到有人收尾。忘了收尾，下一節會看到它擋住整個資料庫的清理。這頁的實驗一定要用 COMMIT PREPARED／ROLLBACK PREPARED 結束。

同事還沒提交，這時你查拿鐵，看 price 和 xmax：

你看到的仍是 115 元，但這個版本的 xmax 已經是同事的交易編號。xmax 有值，不代表這個版本對你失效。PostgreSQL 還要問一個問題：在你開始查詢的那一刻，同事的交易算完成了嗎？

回答這個問題的，是快照（snapshot）。快照是一句查詢（或 REPEATABLE READ 交易）開始時，PostgreSQL 記下的一份「哪些交易算已完成」的名單。為什麼需要它？一句查詢可能要讀好幾秒，期間別人不斷提交；如果每讀一列都用「現在」的狀態判斷，前半段和後半段會看到不同時間點的資料，例如轉帳只看到扣款、沒看到入帳。有了快照，整句查詢都用同一份名單判斷，看到的是同一個時間點的資料。

pg_current_snapshot() 會把快照印成 xmin:xmax:進行中清單。注意這裡的 xmin、xmax 是快照的欄位，跟列版本上的同名欄位是兩回事：

  • 編號小於 xmin 的交易都已結束；
  • 編號大於或等於 xmax 的交易在快照之後才開始，一律當作還沒完成；
  • 中間的，列在進行中清單的就是還沒完成。

VACUUM 為什麼清不掉？找出擋住清理的交易

上一節的結論是：只要還有交易可能要看某個舊版本，VACUUM 就不能清它。把這個條件推到整個資料庫，就是清理界線（xmin horizon）：資料庫裡最舊的那個仍在進行的交易或快照，決定了界線在哪裡。在界線之前就被刪掉的版本，所有交易都看不到，可以清；在界線之後才被刪掉的版本，最舊的那個交易可能還要看，一律不能清。

為什麼是「整個資料庫」，而不是只看那個交易碰過的表？因為 VACUUM 無從知道一個進行中的交易接下來會查哪張表。一個交易可以在任何時候 SELECT 任何表，它的快照又是開始時就定好的，所以 VACUUM 只能保守地假設：它可能要看任何表的任何舊版本。結果是一個卡住的交易，會讓所有表的死版本一起累積。

💡 實務上：code review 時看交易裡有沒有 await 外部服務
咖啡店結帳的常見寫法：開交易、寫訂單、呼叫金流 API、等回應、再 COMMIT。金流慢個幾秒，這條連線就一直 idle in transaction；遇到逾時或程式例外沒收尾，它可能卡上好幾個小時，整個資料庫的清理都停住。review 時看到交易範圍裡有 HTTP 呼叫、寄信、讀檔，就請作者移到交易外，或拆成「先寫待付款訂單 → 呼叫金流 → 再開一個短交易更新狀態」。另外替應用程式用的資料庫帳號設好 idle_in_transaction_session_timeout，監控面板放一張「最久的交易開了多久」，超過門檻就通知值班的人。

擋住清理的交易處理掉之後，VACUUM 跟得上，表就不會無限長大。但集點卡表每集一次點，還是產生一個死版本，每個索引也各多一筆紀錄，VACUUM 每晚都要清一大堆。能不能從源頭下手，讓更新一開始就少產生垃圾？

能不能讓更新少產生垃圾？HOT 更新與 fillfactor

先看一次一般的 UPDATE 到底產生了多少垃圾。第 1 節看到新版本會換到另一格，ctid 改變了。而第 27 課的索引，每一筆紀錄存的正是列版本的位置。位置變了，索引就得跟著更新：一般的 UPDATE 寫出新版本後，每個索引都要加一筆指向新位置的紀錄，即使索引的欄位根本沒變。一張表有三個索引，改一個跟索引無關的欄位，也要寫一個新版本加三筆索引紀錄，舊的那三筆之後也要 VACUUM 去清。

PostgreSQL 為此有一個最佳化，叫 HOT 更新（Heap-Only Tuple，只寫在表裡的版本）：新版本放在同一頁，索引完全不用動。索引繼續指向舊版本那一格，舊版本的 t_ctid 指向新版本，同一列的版本在頁裡串成一條鏈，查詢經由索引找到舊格子後，沿著鏈走到看得到的那個版本。鏈中間的死版本，連一般查詢讀到這一頁時都能順手清掉，不必等 VACUUM。第 1 節 pageinspect 看到的 hot_updated、heap_only 就是這條鏈的標記：products 只有 id 上有索引，改價格就是 HOT。

不是每次更新都能走 HOT。PostgreSQL 18 文件列的條件有兩個：

  1. 這次更新沒有改到任何索引用到的欄位（BRIN 這種摘要型索引除外）；
  2. 舊版本所在的那一頁還有空間放新版本。

第一個條件很好理解：索引欄位的值變了，索引本來就得改，沒辦法省。第二個條件要靠 fillfactor：每一頁只填到幾成，剩下的留給之後的更新。預設 100，也就是新增資料時把頁填滿，之後的更新就找不到同一頁的空位。先驗證第二個條件。建兩張一樣的表，一張 fillfactor 100、一張 70：

正式環境誰來跑 VACUUM？autovacuum 與凍結

答案是 autovacuum：PostgreSQL 內建的背景程序，定期檢查每張表，死版本夠多就自動 VACUUM，資料變動夠多就自動 ANALYZE（第 21 課）。開場的每晚排程是額外加的一層，平常讓表維持健康的是 autovacuum。這頁沒有 autovacuum（見課首），所以前面都手動執行，但它的設定看得到。先從 pg_settings（每個設定一列的系統視圖）看相關設定：

就會 VACUUM。reltuples 是 pg_class 裡的估計列數（上次 VACUUM／ANALYZE 時的值）。先看括號裡的後半：

預設 50 + 0.2 × 列數，也就是死版本超過兩成才動手。一萬列的表等 2,050 個死版本還好；一億列的表要等 2,000 萬個，期間表一直膨脹。外層的 autovacuum_vacuum_max_threshold 是 PostgreSQL 18 新增的上限，只對非常大的表有作用，細節見課末。所以大表通常各自覆寫比例，讓它早一點清：

只新增、從不更新的表（例如日誌）沒有死版本，靠另一組門檻觸發，見課末。它們也需要 VACUUM，原因是 VACUUM 還有一個工作：凍結。

要理解凍結，先回到第 1 節的交易編號。交易編號只有 32 位元，大約 42 億個號碼，用完就繞回來從頭用。繞回來之後，「號碼越大越新」就不成立了，所以 PostgreSQL 比較新舊時用的是環狀的比法：以現在為中心，前約 21 億個算過去，後約 21 億個算未來。一個版本的 xmin 如果舊到超過這個範圍，它會突然從「過去」變成「未來」，依第 3 節的可見規則，建立它的交易「還沒發生」，整列資料就看不見了。這叫 wraparound。

防止的方法是凍結（freeze）：VACUUM 把夠舊的版本標成「凍結」，意思是永遠可見，判斷時不再比較它的交易編號。每張表最舊的未凍結編號記在 relfrozenxid，age(relfrozenxid) 就是這張表離危險還有多遠的指標。凍結前後各查一次，看 age 欄：

products 的 age 變成 0。正式環境不用手動凍結，autovacuum 會處理，但要監控 age(relfrozenxid)，因為一旦凍結跟不上，後果是逐級加重的：

  • 超過 autovacuum_freeze_max_age（預設 2 億）時，就算關掉 autovacuum，系統也會強制啟動防 wraparound 的 VACUUM。
  • 文件寫明，離 wraparound 只剩 4,000 萬個交易時開始發出警告。
  • 剩不到 300 萬時，資料庫拒絕任何新的寫入交易，只剩唯讀，直到 VACUUM 完成。

凍結也是 VACUUM 的一部分，所以第 4 節那些擋住清理的元兇，同樣會讓凍結無法前進。一個忘了收尾的交易，短期讓表膨脹，放得夠久就會一路走到資料庫拒絕寫入。這也是為什麼 autovacuum 不能關：它同時負責清死版本、更新統計、凍結三件事。

補充與查表

主線用不到、但查問題或調設定時會用到的細節。

為什麼 count(*) 在大表上很慢

常見疑問：為什麼 SELECT count(*) FROM orders 在一億列的表上要跑好幾秒，PostgreSQL 不直接記一個總數？因為每個交易的快照不同，看得到的列數也不同，沒有一個數字對所有人都正確，只能逐列檢查可見性。只要大概的數字，看 pg_class.reltuples（統計估計值）；要精確又快，就自己維護一張計數表。

💡 實務上：後台的「共幾筆」先問需不需要精確
咖啡店後台的訂單列表常有「共 123,456 筆、第 1／6173 頁」，每次翻頁都跑一次 count(*)，資料一多列表就變慢。先問 PM：顯示「約 12 萬筆」或「1,000+ 筆」可以嗎？多數列表可以：沒有篩選條件的整表總數看 reltuples，有篩選就用 LIMIT 1001 數到上限就停。真的要精確（例如對帳），計數表要跟寫入放在同一個交易裡更新，而且所有訂單都搶同一列，會變成鎖競爭的熱點。能用「下一頁」取代總頁數，通常最省事。

autovacuum 觸發門檻的細節

PostgreSQL 18 新增的 autovacuum_vacuum_max_threshold（預設 1 億）是觸發門檻的上限，表超過約 5 億列時才會生效，對中大型表幫助有限，所以大表仍然要各自覆寫 autovacuum_vacuum_scale_factor。

只新增、從不更新的表（例如日誌）沒有死版本，靠另一組門檻觸發：autovacuum_vacuum_insert_threshold（預設 1000）＋ autovacuum_vacuum_insert_scale_factor（預設 0.2）× 列數 × 還沒凍結的比例。這種 VACUUM 的目的是設定 visibility map 和凍結。

版本備註

PostgreSQL 18 新增 autovacuum_vacuum_max_threshold，VACUUM 也會順便積極凍結一部分全可見的頁（VERBOSE 裡的 eagerly scanned，由 vacuum_max_eager_freeze_failure_rate 控制）。transaction_timeout 是 PostgreSQL 17 新增的。這頁的 PGlite 0.5.13（PostgreSQL 18.6）是單人模式：沒有 autovacuum，pg_stat_* 要強制送出統計才會更新，有 pageinspect、pg_visibility、pg_freespacemap，沒有 pgstattuple。

練習

練習 1：seed 裡幾張表做過不同程度的更新和刪除。列出死版本比例超過 0.2 的表：表名、n_live_tup、n_dead_tup、比例（死版本 ÷ 全部版本，0～1 的小數，四捨五入到小數點 2 位），依比例由高到低。注意：n_dead_tup 是整數，PostgreSQL 裡整數除以整數的結果還是整數，小數會被捨去（1 / 3 得到 0）；有一張空表，除數是 0 會報錯，第 15 課的 NULLIF 可以避開。

練習 2：凌晨的匯出程式把一個交易 PREPARE 之後就當掉了，它改的商品價格是錯的，products 的死版本也因此一直清不掉。起始內容可以查到它的 gid。寫出處理它的指令：放棄這個交易，讓價格維持原樣。

練習 3：stamp_cards 每天被更新上萬次，統計卻顯示沒有 HOT 更新。調整這張表：fillfactor 設成 70，並刪掉那個從沒被查詢用過、又讓更新無法走 HOT 的索引。其他索引和資料都要留著。起始內容可以看每個索引的使用次數。

練習 4：寫一句查詢，算出每張使用者表的 autovacuum 觸發門檻：表名、門檻（四捨五入成整數），依表名排序。用 current_setting() 讀 autovacuum_vacuum_threshold 與 autovacuum_vacuum_scale_factor（回傳文字，要轉型）；使用者表從 pg_stat_user_tables 取（它的 relid 就是 pg_class 的 oid），reltuples 在 pg_class；有每表覆寫設定的（seed 裡不只一張表、不只一種設定），以覆寫值為準。這幾張表都很小，autovacuum_vacuum_max_threshold 的上限不會生效，可以不管。

練習 5：一次 UPDATE 了 100 萬列，COMMIT 之後也跑了 VACUUM，表的檔案卻幾乎沒有變小。為什麼？

✓ 一般 VACUUM 只截掉表尾整頁空掉的部分，其餘空間留在檔案裡給之後的新版本用。要縮小檔案得重寫整張表（VACUUM FULL 要拿全表的重鎖，正式環境改用 pg_repack）。COMMIT 之後交易就已提交；ANALYZE 只更新統計，不碰空間。

練習 6：某個 worker 早上 9 點開了交易、更新了一列，之後就停在 idle in transaction，直到下午 5 點。它只改了一列，影響有多大？

✓ 清理界線看的是全資料庫最舊的進行中交易，跟它碰過哪張表無關，所以 c 錯。閒著不代表無害：它拿著交易編號和列鎖。用 idle_in_transaction_session_timeout 讓伺服器結束這種連線，程式也要確保每個交易都會 COMMIT／ROLLBACK。

練習 7：資料庫很忙，有人提議「把 autovacuum 關掉省資源」。可以嗎？

✓ autovacuum 是必要的維護，不是可有可無。查詢時的頁面清理只處理一部分情況（例如 HOT 鏈），不更新 visibility map、也不凍結；VACUUM FULL 每次都鎖住整張表。負載太重時應該調整 autovacuum（每表的比例、成本限制），而不是關掉。

常見錯誤

  • 正式環境直接 VACUUM FULL：整張表 ACCESS EXCLUSIVE，連 SELECT 都卡住。日常靠一般 VACUUM，要縮表用 pg_repack 這類線上工具。
  • 關掉 autovacuum，或大表沿用預設的 20%：大表等到死版本兩成才清，早就膨脹了。大表各自設定較小的 autovacuum_vacuum_scale_factor。
  • 放著長交易不管：跑很久的查詢、idle in transaction、忘了收尾的 prepared transaction 或 replication slot，會讓整個資料庫都清不掉。監控 age(backend_xmin) 和 pg_prepared_xacts，設定逾時。
  • 一句 UPDATE 整張大表：一次產生和表一樣多的死版本，交易期間也都清不掉。要分批更新（第 34 課）。
  • 在常更新的欄位上隨手建索引：每次更新都不能走 HOT，表和所有索引一起長大。
  • 把 n_dead_tup 當即時、精確的數字：它是累計統計，會延遲，也只是估計。
  • 把 PREPARE TRANSACTION 當成應用程式的功能：它是給外部交易協調器用的，這頁拿它模擬「另一位同事」而已。

小結

  • 表裡存的是列版本：UPDATE 寫新版本、把舊版本的 xmax 填上自己的交易編號；DELETE 只填 xmax；ROLLBACK 讓寫出的版本永遠無效，不會改回頁面。集點卡每集一次點，就多一個舊版本。
  • VACUUM 清死版本、讓空間可重用，但不縮小檔案，所以每晚 VACUUM 後檔案沒變小是正常的；VACUUM FULL 重寫整張表、拿最重的鎖，正式環境改用線上重整工具。
  • 快照記下哪些交易已完成；xmin 已提交、xmax 未提交（或沒有）的版本才看得到。所以 count(*) 要逐列檢查。
  • 最舊的進行中交易決定整個資料庫的清理界線；VERBOSE 的 dead but not yet removable 不是 0，就去查 pg_stat_activity、pg_prepared_xacts、replication slot。
  • HOT 更新不碰索引：被改的欄位不在索引裡，加上 fillfactor 留下的空間。集點卡表的修法是刪掉 stamps 上沒人用的索引、把 fillfactor 降到 70。
  • autovacuum 門檻是 50 + 0.2 × reltuples（有上限、可每表覆寫）；它也負責凍結，防止交易編號繞回造成 wraparound，所以不能關。
