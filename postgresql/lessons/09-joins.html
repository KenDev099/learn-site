階段 2：表與表之間的關係 · 第 9 課

JOIN：把表接起來

上一課把顧客和訂單拆成兩張表，訂單只存 customer_id，顧客的名字只存在 customers 一個地方。資料不再重複了，但店長馬上來要兩份東西：

  1. 後台訂單列表：12 張訂單一張都不能少，每張要顯示顧客名字和經手店員的名字，跟收銀機的筆數對得起來。
  2. 顧客報表：每位顧客下了幾張單、總共花多少，連從沒下過單的人也要列出來，行銷要發優惠券給他們。

兩份資料都需要「訂單」和「顧客」同時出現在一列結果裡，但它們分在兩張表。這一課學 JOIN：一句查詢就把兩張表接在一起，並且一路把這兩份資料做出來。

這課會用到：第 8 課的外鍵（orders.customer_id 存的是 customers.id 的值，指向這張訂單的主人）；第 4 課的 NULL（跟 NULL 比較的結果是 unknown，WHERE 只留下 true 的列）；第 7 課的 GROUP BY 與 COUNT(欄位)（分組統計，COUNT(欄位) 不數 NULL）。
這課的路線：
  1. 訂單上只有編號，怎麼一句查詢接上顧客名字：JOIN 怎麼配對，以及替表取短名字的別名。
  2. 列表少了兩張訂單，去哪了：INNER JOIN 和 LEFT JOIN 的差別，怎麼讓配不到的列留下來。
  3. 行銷要的「從沒下過單的顧客」：利用 LEFT JOIN 補上的 NULL 把他們找出來。
  4. 訂單列表還要篩選、排序、接上店員：JOIN 之後接 WHERE、ORDER BY，以及一次接三張表。
  5. 每位顧客下了幾單、花多少：JOIN 之後再 GROUP BY，以及最後順帶認識 RIGHT JOIN、FULL JOIN。

訂單上只有顧客編號，怎麼一句查詢接上顧客名字？

沒有 JOIN 的話，後端得先查出 12 張訂單，再拿每張訂單的 customer_id 去 customers 查名字，一張訂單一次，或者把兩邊的資料都撈回程式裡自己比對。資料庫其實很擅長做這件比對，只是你要告訴它「怎麼配」。

想像店長把訂單紙一張一張拿起來，看上面的顧客編號，到會員名冊裡翻到同編號的那一頁，把名字抄在訂單旁邊。JOIN 做的就是這件事：依照你給的條件，把兩張表的列配成一對，拼成一列更寬的結果。這列結果同時有訂單的欄位和顧客的欄位，所以 SELECT 可以從兩邊挑想要的欄位。

「怎麼配」寫在 ON 後面。第 8 課的外鍵已經說了兩張表的關係：orders.customer_id 的值，就是某位顧客的 customers.id。所以配對條件幾乎都是「外鍵 = 對方的主鍵」：

SELECT 要的欄位
FROM 表A
JOIN 表B ON 表A.外鍵 = 表B.主鍵;

套到訂單列表上。執行後看兩件事：每一列的名字是不是對的人，以及總共有幾列：

欄位前面多了表名，例如 orders.id。原因是兩張表都有 id 欄位，只寫 id 資料庫不知道你要訂單編號還是顧客編號，會直接報錯。表名.欄位 就是在講清楚「哪一張表的哪一欄」。只有一張表有的欄位（例如 name）可以不寫表名，但寫上之後，讀查詢的人不用回頭查表結構就知道它從哪來，所以習慣上都會寫。

表名每次都要寫全名嗎？替表取別名

每個欄位都寫 orders.、customers.，查詢很快就變得又長又難讀，等一下要接第三張表會更明顯。SQL 讓你在 FROM 和 JOIN 後面替表取一個短名字，叫做別名，之後整句查詢都用這個短名字指那張表：

orders AS o 的意思是「這句查詢裡，o 就代表 orders」。AS 可以省略，寫成 FROM orders o 也一樣。慣例是用表名的第一個字母，別名只在這一句查詢裡有效，不會改到表本身。

想看 JOIN 拼出來的完整一列長什麼樣子，可以用 SELECT *，它會把兩張表的欄位全部依序列出來。執行後注意有兩個 id：前面的是 o.id（訂單編號），後面的是 c.id（顧客編號）。兩個欄位名字一樣、意義不同，這就是前面一定要寫表名或別名的原因：

回到列表本身。前面的結果只有 10 列，但 orders 有 12 張訂單，這份列表跟收銀機對不起來。少掉的兩張去哪了？

列表少了兩張訂單，去哪了？INNER JOIN 和 LEFT JOIN

少掉的是訂單 4 和 10，兩張都是非會員的現場客人，customer_id 是 NULL。這頁的 orders.customer_id 刻意允許 NULL，就是為了重現這個情況，真實的咖啡店也常有不加入會員的客人。

拿訂單 4 去配對時，條件是 NULL = customers.id。第 4 課講過，任何值跟 NULL 比較，結果都是 unknown，不是 true。ON 跟 WHERE 一樣只接受 true，所以訂單 4 跟哪位顧客都配不起來。

配不起來之後的處理方式，就是 JOIN 種類的差別。只寫 JOIN 其實是 INNER JOIN 的簡寫，規則是兩邊都配得到的列才留下：訂單找不到顧客就丟掉，顧客找不到訂單也丟掉。這個規則不會報錯也不會警告，所以列表少了兩張，資料庫卻覺得一切正常。

需要「某一張表的每一列都要出現」時，改用 LEFT JOIN。寫在 FROM 後面的表叫左表，寫在 LEFT JOIN 後面的表叫右表。左表的每一列都保留，配得到就接上右表的資料，配不到就在右表的欄位補上 NULL。訂單列表要的是「每張訂單都在」，所以訂單當左表：

SELECT o.id, c.name, o.total
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.id
ORDER BY o.id;

這樣會得到 12 列，訂單 4 和 10 的 c.name 是 NULL。可以把這段貼到上面任何一個框框執行確認。

💡 實務上：先想清楚「哪些列一定要出現」，再選 INNER 或 LEFT
咖啡店後台的訂單列表要顯示顧客名字，如果寫成 orders JOIN customers，非會員的現場訂單會悄悄消失，列表筆數和收銀機對不起來，而且不會有任何錯誤訊息。寫列表或報表時，先問「這份結果應該有幾列？以哪張表為主？」，以那張表當左表，關聯資料可能沒有的就用 LEFT JOIN。上線前用 SELECT COUNT(*) FROM orders 對一下筆數，是很便宜的檢查。

LEFT JOIN 補上的 NULL 不只是「沒資料」的佔位，它本身就是資訊：哪一列的右表欄位是 NULL，就代表那一列沒配到。行銷要的名單正好可以從這裡撈出來。

行銷要的「從沒下過單的顧客」怎麼撈？

上一節的結果裡，從沒下過單的顧客有一個共同特徵：訂單欄位全是 NULL。所以只要在 LEFT JOIN 之後，再用 WHERE 篩出 o.id IS NULL 的列（判斷 NULL 要用 IS NULL，用 = NULL 永遠是 unknown，第 4 課講過）：

執行順序是這樣：先 LEFT JOIN，每位顧客至少一列，沒訂單的補 NULL；再 WHERE，只留下訂單編號是 NULL 的列。剩下的就是李建國和吳佩珊。

為什麼用 o.id 判斷，而不是 o.staff_id 或其他訂單欄位？因為 o.staff_id 本來就可能是 NULL（線上訂單沒有店員），用它判斷會把「有下單、但沒有店員」的顧客也當成沒下單。右表的主鍵一定有值，它是 NULL 只有一種可能：這一列是 LEFT JOIN 補出來的。所以判斷要用右表的主鍵，或任何宣告成 NOT NULL 的欄位。

這個寫法的用途比這份名單廣：凡是「找出 A 裡面，在 B 沒有對應資料的」，例如沒下過單的會員、沒有人買過的商品，都是同一個模式。

💡 實務上：「A 有、B 沒有」是行銷和資料檢查的常客
行銷想發優惠券給「註冊後從沒下單」的會員、PM 想知道哪些商品上架後沒人買，都是這個寫法。排查資料問題時也會用它找「孤兒資料」，例如在沒設外鍵的舊表裡，找出指向不存在訂單的紀錄，那通常是程式 bug 留下的髒資料（第 8 課的外鍵就是在預防這種事）。要撈名單給別人用之前，先跟對方確認條件的邊界，例如「已取消的訂單算不算下過單」，不同答案會撈出不同的人。

行銷的名單有了。回到第一份資料：訂單列表能顯示顧客名字了，但後台列表通常還要能篩選、排序，而且店長還要看到店員名字。

訂單列表還要篩選、排序、接上店員：JOIN 之後還能接什麼？

第 7 課講過，資料庫執行一句查詢時最先處理的是 FROM。JOIN 是 FROM 的一部分：資料庫先把兩張表配對成一張更寬的暫時結果，之後的 WHERE、ORDER BY、LIMIT 都是在這張寬表上做。所以它們照樣能用，而且兩張表的欄位都能拿來篩、拿來排。

例如店長想看台北顧客的已完成訂單，金額大的排前面。城市在顧客表、狀態和金額在訂單表，JOIN 之後一句就能同時用到：

接下來是店員名字。訂單還有 staff_id，指向店員表 staff。JOIN 可以一直接下去：前兩張表接好的寬表，再拿去跟第三張表配對。每接一張表就多寫一組 JOIN … ON …：

這句查詢裡有三個決定要看懂：

  • 每一個 JOIN 各自決定 INNER 或 LEFT。顧客用 JOIN，所以這份結果只有會員訂單；店員用 LEFT JOIN，因為線上訂單（例如訂單 5、8、12）沒有店員，但訂單本身還是要列出來，店員欄位顯示 NULL。
  • 同名欄位要在結果裡改名。顧客和店員都有 name，不改名的話結果會有兩個 name 欄位分不清，所以用 AS customer、AS staff 給結果欄位取不同的名字。
  • 要 12 張訂單都在，顧客也要改 LEFT JOIN。店長要的完整列表就是把上面的 JOIN customers 換成 LEFT JOIN customers，兩個 JOIN 都以訂單為主。

完整的查詢長這樣：

SELECT o.id, c.name AS customer, s.name AS staff, o.total
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.id
LEFT JOIN staff s ON o.staff_id = s.id
ORDER BY o.id;

執行後是 12 列，一張訂單都沒少：訂單 4、10 是非會員，customer 是 NULL；訂單 5、8、12 是線上訂單，staff 是 NULL。把它貼到上方的框框執行，對一下這五列。

LEFT JOIN 搭配 WHERE 時要特別小心一件事：WHERE 是在 JOIN 之後才執行。假設店長要「不是阿傑經手的訂單」，直覺會在上面的完整查詢後面加 WHERE s.name <> '阿傑'。訂單 5、8、12 沒有店員，LEFT JOIN 幫它們補上的 s.name 是 NULL，而 NULL <> '阿傑' 的結果是 unknown，不是 true，這三張就被 WHERE 丟掉了。但它們明明不是阿傑經手的，應該出現在結果裡。LEFT JOIN 辛苦保留的列，被右表欄位的條件又篩掉了，效果跟 INNER JOIN 一樣，而且不會有任何錯誤訊息。

這個需求要把「沒有店員」也明確算進去，寫成 WHERE s.id IS NULL OR s.name <> '阿傑'：s.id IS NULL 接住補出來的列（用右表主鍵判斷，理由跟上一節一樣），s.name <> '阿傑' 處理有店員的列。下一節做報表時會再遇到同一個坑，那裡會看到另一種處理方式：把條件移進 ON。

💡 實務上：列表 API 通常一句 JOIN 就把資料備齊
前端的訂單列表要顯示顧客名字和店員名字，後端常見的做法是用一句 JOIN 查好再回傳，而不是先查 20 張訂單、再一張一張去查顧客（多打 20 次資料庫，這就是第 25 課會講的 N+1 問題）。AS 取的欄位名稱通常就是 API 回傳的 JSON 欄位，取 customer、staff 這種清楚的名字，前端拿到才不會兩個 name 撞在一起。但也不要一口氣接上七八張表把所有欄位都撈回來，畫面用不到的欄位就別 JOIN。

訂單列表完成了。剩下顧客報表：每位顧客幾張單、花多少。JOIN 之後，王小明有三張訂單就是三列，報表卻要他只佔一列，這就要把多列再收回一列。

每位顧客下了幾單、花了多少？JOIN 之後再 GROUP BY

把多列收成一列，正是第 7 課 GROUP BY 的工作。既然 JOIN 只是讓 FROM 變成一張更寬的表，GROUP BY 一樣能接在後面：先 LEFT JOIN 讓每位顧客都在，再依顧客分組，每組算訂單數和金額總和。

這裡用 COUNT(o.id)，不用 COUNT(*)。原因要回到 LEFT JOIN 補的那一列：李建國沒有訂單，但 LEFT JOIN 之後他還是有一列，只是訂單欄位全是 NULL。COUNT(*) 數的是「有幾列」，會把這列數成 1，報表就說他下過一張單；COUNT(o.id) 只數非 NULL 的值，補出來的那列 o.id 是 NULL，不算，結果才是正確的 0。規則一樣是「用右表的主鍵」，跟上一節找沒下單顧客的理由相同。

再看 spent 欄：李建國和吳佩珊的 SUM 是 NULL，不是 0。SUM 會略過 NULL，一個值都沒有的時候就回傳 NULL。報表上想顯示 0 要用 COALESCE，第 15 課會講。

另外注意張雅婷的 2 張訂單裡有 1 張是 'cancelled'，她的金額也算進去了。店長如果說「只算已完成的」，直覺會在後面加 WHERE o.status = 'done'，但上一節說過，WHERE 在 JOIN 之後執行：李建國那列的 o.status 是 NULL，NULL = 'done' 是 unknown，他就從報表上消失了。要保留每位顧客、又只配已完成的訂單，條件要寫進 ON，讓它成為配對條件的一部分：

SELECT c.id, c.name, COUNT(o.id) AS order_count, SUM(o.total) AS spent
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'done'
GROUP BY c.id, c.name
ORDER BY c.id;

這樣已取消的訂單在配對時就配不上，沒有完成訂單的顧客仍然保留一列、訂單數是 0。分辨的方法：右表的條件放 ON，是「哪些右表列可以配上來」；放 WHERE，是「整列結果要不要留下」。

💡 實務上：JOIN 之後再加總，先確認列有沒有變多
JOIN 一對多的表時，左表的一列會變成好幾列。如果訂單再接上「付款紀錄」，一張訂單分兩次付款就會出現兩列，這時 SUM(o.total) 會把這張訂單的金額算兩次，營收報表就虛胖了。資深工程師做金額報表時會拿一個單純的 SELECT SUM(total) FROM orders 當對照，數字對不上就是 JOIN 讓列重複了。下一課的多對多會更常遇到這個狀況。

順帶認識：RIGHT JOIN 與 FULL JOIN

兩份資料都完成了，用到的只有 INNER JOIN 和 LEFT JOIN，實務上絕大多數的查詢也是這兩種。另外兩種你會在別人的查詢裡看到，認得就好。

RIGHT JOIN 是反過來保留右表的每一列。A RIGHT JOIN B 跟 B LEFT JOIN A 意思一樣。大家習慣把「要保留的表」寫在左邊、一律用 LEFT JOIN，讀查詢的人只要記一種方向，所以很少看到 RIGHT JOIN。

FULL JOIN 兩邊都保留：配不到的左表列、配不到的右表列都會出現。它適合用在對帳，一次看到兩邊各有哪些配不起來的資料。下面同時列出沒下單的顧客，和沒有顧客的非會員訂單：

FULL JOIN 本身會回傳所有配對成功的列，再加上兩邊配不到的列。對帳只想看配不起來的，所以用 WHERE 把配對成功的列濾掉，判斷方式就是第 3 節的「主鍵是 NULL，代表這一列是補出來的」：c.id IS NULL 撈出沒有顧客的訂單（訂單 4、10），o.id IS NULL 撈出沒有訂單的顧客（李建國、吳佩珊）。執行後應該看到 4 列。拿掉 WHERE 再執行一次，會多出所有配對成功的訂單。

補充與查表

寫法左表配不到的列右表配不到的列這課的用途
JOIN（INNER JOIN）丟掉丟掉只看會員訂單
LEFT JOIN保留，右表欄位補 NULL丟掉訂單列表、顧客報表、沒下單名單
RIGHT JOIN丟掉保留，左表欄位補 NULL少用，改寫成 LEFT JOIN
FULL JOIN保留保留對帳：兩邊配不到的都列出來
  • 「A 有、B 沒有」的另一種寫法：第 16 課會學到 NOT EXISTS，可以寫出跟 LEFT JOIN … WHERE 右表.主鍵 IS NULL 相同需求的查詢。
  • 舊式逗號寫法：在舊的程式碼裡會看到 FROM orders, customers WHERE …，把配對條件寫在 WHERE。漏寫條件時，每張訂單會跟每位顧客都配一次（見「常見錯誤」）。新寫的查詢用 JOIN … ON，條件跟 JOIN 寫在一起，不容易漏。

練習 5：customers 有 3 列：A 有 2 張訂單、B 有 1 張、C 沒有訂單。SELECT * FROM customers c LEFT JOIN orders o ON o.customer_id = c.id 會回傳幾列？

✓ A 配到 2 張訂單產生 2 列、B 產生 1 列、C 沒配到但 LEFT JOIN 會保留並補 NULL，共 4 列。如果是 INNER JOIN 就是 3 列（C 消失）。

練習 6：想列出所有顧客和他們「已完成」的訂單，寫了 … FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.status = 'done'。結果沒下過單的顧客不見了，為什麼？

✓ WHERE 在 JOIN 之後才執行，補上的 NULL 列會被右表條件篩掉，效果就跟 INNER JOIN 一樣。要保留它們，把條件移進 ON：LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'done'。

常見錯誤

  • 欄位名稱不明確：兩張表都有 id，只寫 SELECT id 會出現 column reference "id" is ambiguous。加上表名或別名。
  • ON 條件寫錯：例如寫成 o.id = c.id（訂單編號對顧客編號），不會報錯，但結果完全錯。ON 幾乎都是「外鍵 = 主鍵」。
  • 忘了 ON：舊式寫法 FROM orders, customers 沒有條件時，會把每張訂單和每位顧客都配一次（12 × 6 = 72 列）。用 JOIN … ON 就不會漏寫條件。
  • 該保留的列用了 INNER JOIN：非會員訂單、沒下單的顧客會安靜地消失，不會報錯。先決定以哪張表為主，那張表當左表、用 LEFT JOIN。
  • LEFT JOIN 後用 COUNT(*)：沒有配到的列也會被數成 1。改用 COUNT(右表.主鍵)。
  • LEFT JOIN 後在 WHERE 篩右表欄位：補上的 NULL 列會被篩掉（練習 6）。條件要移進 ON。

小結

  • JOIN 表 ON 條件 把兩張表的列依條件配對，拼成一列更寬的結果；條件通常是「外鍵 = 主鍵」。同名欄位用 表名.欄位 或別名分清楚。
  • JOIN（INNER）只留兩邊都配得到的列；LEFT JOIN 保留左表每一列，配不到的補 NULL。要哪張表的每一列都出現，它就當左表。
  • JOIN 的結果列數是配對成功的組數：左表一列配到幾列，就變成幾列。
  • LEFT JOIN … WHERE 右表.主鍵 IS NULL 找出「沒有對應資料」的列。
  • 多表就多寫幾個 JOIN，每個各自決定 INNER 或 LEFT。JOIN 後面照常接 WHERE、GROUP BY、ORDER BY；LEFT JOIN 後統計用 COUNT(右表.主鍵)，右表的篩選條件放 ON。
