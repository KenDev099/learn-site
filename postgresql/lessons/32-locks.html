為什麼一句瞬間完成的 ALTER 能讓整站停擺？

要回答檢討的第一題，先要知道 PostgreSQL 怎麼讓同時進來的操作不互相弄壞。它用的是鎖（lock）：一個交易要動一張表之前，先向資料庫登記「我要怎麼用這張表」，例如「我要讀」或「我要改結構」。登記的用法有強有弱：弱的只防最危險的事，強的什麼都防。兩個人登記的用法互相牴觸，叫做衝突（conflict），晚到的人就得等。

以整張表為單位的鎖，叫表級鎖（table-level lock）。它回答的是「這張表現在能不能做某類操作」，例如能不能讀、能不能改結構。第 19 課的列鎖是以一列為單位，後面「列級鎖與外鍵」那一節會再回來談。有了這兩個詞，事故可以用三句話解釋：

  1. 每個指令都會先拿表級鎖，拿到的鎖留到交易結束。一般讀取（SELECT）拿最弱的 ACCESS SHARE；大多數 ALTER TABLE 拿最強的 ACCESS EXCLUSIVE。
  2. 兩把鎖衝突時，後到的人要等先拿到的人的交易結束。讀取只怕改結構：ACCESS SHARE 只和 ACCESS EXCLUSIVE 衝突。
  3. 拿不到鎖的請求進入等待佇列（lock queue），依先來後到排隊。新來的請求不只要跟「已經拿到」的鎖比，也要跟「排在前面、還在等」的鎖比。所以排在前面的強鎖，會擋住後面所有和它衝突的弱鎖，即使這些弱鎖和目前拿著的鎖完全不衝突。

第三句是事故的關鍵。少了它，報表和 App 的 SELECT 都只是讀，本來可以同時進行。把三句套回事故，逐步播放，每一步注意 App 那一欄：

所以網站停擺不是因為 ALTER 慢，而是它在佇列裡等的那兩分鐘，把後面每個請求一起拖住。要修的是「等待」：讓 ALTER 等不到鎖就放棄，它一離開佇列，後面的查詢就能跟報表一起讀。

改表結構的指令，例如 CREATE、ALTER、DROP，統稱資料定義語言（DDL，Data Definition Language）。修法是在 DDL 前設 lock_timeout，也就是等鎖的上限：超過就讓這一句失敗、交易被取消。SET LOCAL 讓這個設定只在目前的交易有效，不會影響同一條連線之後的查詢：

BEGIN;
SET LOCAL lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN note text;
COMMIT;
-- 等超過 2 秒：ERROR 55P03 canceling statement due to lock timeout
-- 交易被取消，App 最多被擋 2 秒；migration 腳本等一下再重試

代價是 migration 可能失敗，所以腳本要能重試。這段在這頁不會生效（見課首「這頁的環境」）；第 34 課會把每種 DDL 的鎖和安全步驟整理成一套 migration 流程。

檢討的第一題有了最小答案。但這個答案建立在「ALTER 拿最強的鎖」這句話上，今晚的清單裡還有 CREATE INDEX 和 VALIDATE CONSTRAINT，它們拿什麼鎖？與其憑印象，下一節教你自己量。

今晚的 migration 每句拿什麼鎖？用 pg_locks 自己量

上一節的模型只用到兩種鎖。PostgreSQL 的表級鎖其實有 8 種，要知道某個指令拿哪一種，最可靠的方法是在交易裡執行它，再看資料庫記下了哪些鎖。這需要先認識兩個工具。

第一個是 pid。PostgreSQL 的每條連線由伺服器上一個獨立的程序（process）服務，程序有編號，叫 pid。pg_backend_pid() 回傳「服務我這條連線的程序」的編號，用來從所有連線的鎖裡挑出自己的。

第二個是 pg_locks。它是一個系統視圖（system view），也就是 PostgreSQL 內建、可以像表一樣查詢的狀態資訊。pg_locks 列出資料庫裡目前所有的鎖，包括已經拿到的和正在等的。常用欄位：

relation被鎖的表的內部編號（oid）。轉成 regclass 型別就會顯示成表名：relation::regclass

判斷 migration 會擋住誰之前，要先知道 App 平常拿什麼鎖。量兩種 App 最常做的事：會鎖列的 SELECT … FOR UPDATE，和下單的 INSERT。執行後看兩張結果的「模式」欄：

這些鎖會擋住誰？衝突表與「暫停的同事」

知道每句拿什麼鎖之後，下一步是判斷它會擋住誰。第一節的模型只用到其中一格（ACCESS SHARE 對 ACCESS EXCLUSIVE），完整的是 PostgreSQL 18 文件的衝突表（conflict matrix）。列是「我想拿的鎖」，欄是「別人已經拿著的鎖」，編號對應上一節表格的 #，✕ 表示衝突。查表用，不用背：

表很大，但今晚的 migration 和 App 平常的操作只碰到其中幾格，記三句就能應付大部分情況：

  • 一般讀取只怕 ACCESS EXCLUSIVE。所以 ALTER TABLE、TRUNCATE、一般的 REFRESH 會擋住讀。今晚的 ADD COLUMN 屬於這一類。
  • 寫入（ROW EXCLUSIVE）怕 SHARE 以上。所以沒有 CONCURRENTLY 的 CREATE INDEX（SHARE）會擋住所有寫入，但不擋讀。上一節留下的問題答案是：會，結帳的 INSERT 要等索引建完。
  • SHARE 和自己不衝突，SHARE UPDATE EXCLUSIVE 和自己衝突。兩個人可以同時 CREATE INDEX；同一張表同時只能有一個 VACUUM、ANALYZE 或 VALIDATE。

實驗：請一位「暫停的同事」拿著鎖

衝突表可以自己驗證，但這頁只有一條連線（見課首）。要看「被別人擋住」，需要一個不會結束的別人：沿用第 30 課的「暫停的同事」，用 PREPARE TRANSACTION 'gid' 把交易暫停並保存起來。連線變回空閒，交易拿的鎖卻全部留著，直到有人執行 COMMIT PREPARED 'gid' 或 ROLLBACK PREPARED 'gid'。

PREPARE TRANSACTION 是給分散式交易管理器用的，不是給應用程式用的。正式環境沒有交易管理器時，max_prepared_transactions 應該維持 0（預設），這頁是為了教學才打開。

下單前先鎖住顧客，會不會反而卡住結帳？列級鎖與外鍵

檢討會上有人提議：App 下單時先用 SELECT … FOR UPDATE 把顧客那一列鎖住，確保下單期間顧客資料不會被改。這個提議好不好，要看列級鎖之間怎麼互相阻擋。

前面用 pg_locks 量鎖時，SELECT … FOR UPDATE 在表上只拿了 ROW SHARE，這把表級鎖幾乎不擋人。真正擋住別人改那一列的，是另外加在列上的列級鎖（row-level lock）。兩者分工：表級鎖管「整張表能不能做某類操作」，列級鎖管「這一列能不能改」。

列鎖存放的位置也和表級鎖不同。第 30 課說過每個列版本有 xmax 欄位，記下刪除這個版本的交易；鎖住一列時，PostgreSQL 把鎖記在這一列本身的 xmax，不佔共享記憶體，所以一次鎖一百萬列也不會耗盡鎖表。代價是 pg_locks 不會逐列列出列鎖：要等列鎖的人，在 pg_locks 裡看到的是它在等對方的 transactionid，也就是等對方的交易結束。

列鎖有 4 種強度，由強到弱。最後一種是這節的重點：外鍵檢查拿的是最弱的那一把。

列鎖誰會拿擋住誰
FOR UPDATEDELETE；改到可以被外鍵參照的欄位（主鍵、唯一鍵）的 UPDATE；手寫 SELECT … FOR UPDATE其他三種全部
FOR NO KEY UPDATE沒改到鍵的 UPDATE（最常見的修改）FOR UPDATE、FOR NO KEY UPDATE、FOR SHARE
FOR SHARE手寫 SELECT … FOR SHARE：我要讀，讀完前別人不准改FOR UPDATE、FOR NO KEY UPDATE
FOR KEY SHARE外鍵檢查：新增訂單時，PostgreSQL 對被參照的那位顧客拿這把鎖，確保顧客在交易結束前不會被刪掉或改主鍵只有 FOR UPDATE

回到檢討會的提議。它想要的是「下單期間顧客資料不會被改」，但「不會被改」其實分成幾種需求，答案各不相同：

  • 只需要確保顧客存在、不會被刪掉：外鍵檢查已經替下單拿了 FOR KEY SHARE，顧客在交易結束前不會被刪掉、主鍵不會被改，不需要再手動鎖。
  • 真的需要顧客資料在下單期間不變：例如依會員等級算折扣，算到一半等級被改掉就會算錯。FOR KEY SHARE 擋不住這種情況，剛才的實驗才示範過改名可以同時成功。這時用 SELECT … FOR SHARE：它會擋住改名、改等級這類 UPDATE 拿的 FOR NO KEY UPDATE，但不擋外鍵檢查的 FOR KEY SHARE，所以別人仍然能同時幫這位顧客下單。
  • 之後要改顧客的非鍵欄位（例如扣點數、改狀態）：手寫鎖時用 FOR NO KEY UPDATE 就夠了。

原提議用的 FOR UPDATE 是四種裡最強的，連外鍵檢查的 FOR KEY SHARE 都擋：鎖著顧客時，同一位顧客的其他訂單都要排隊。它想防止顧客資料被改，卻順便讓結帳互相等待，反而製造了新的等待。

不管用哪一種，列鎖終究會讓人等。第一節替 migration 的等待設了 lock_timeout，App 的交易等太久、或拿著鎖不放太久時，又該由誰設上限？

等待要有上限：四個逾時護欄

第一節的 lock_timeout 只管「等鎖」這一件事。實際上會讓別人卡住的情況還有幾種：一句查詢跑太久、交易開著卻什麼都不做、整個交易拖太久。PostgreSQL 各有一個設定，各自擋一種「拿著或等著太久」，預設都是 0（不限制）：

設定管什麼超過時
lock_timeout單次等鎖的時間那一句失敗（55P03）
statement_timeout單一句的總執行時間（包含等鎖）那一句失敗（57014）
idle_in_transaction_session_timeout交易開著、卻沒有在執行任何查詢的時間。專門處理「程式 BEGIN 之後忘了 COMMIT」或「交易中間去呼叫外部 API」，這類連線拿著鎖卻什麼都沒做斷開整條連線
transaction_timeout（17+）整個交易的總時間（含單句的隱含交易）斷開整條連線

前兩個只讓那一句失敗，連線還在；後兩個直接斷線，因為它們針對的是「整個交易該結束了」。執行後看 setting 欄（deadlock_timeout 下一節會用到）：

兩個一起設時，lock_timeout 要設得比 statement_timeout 短才有意義，否則永遠是 statement_timeout 先到。

💡 實務上：替應用程式的角色設上限，不要寫進全域設定
這些設定可以設在資料庫、角色、連線、交易（SET LOCAL）上。文件不建議寫進 postgresql.conf，因為會影響所有連線，包括維運和 migration。實務上替應用程式的角色設上限，例如 ALTER ROLE app_user SET statement_timeout = '5s'；今晚的 migration 則在自己的交易裡 SET LOCAL lock_timeout。第 36 課會完整規劃。

逾時處理的是「等得到、只是太久」。還有一種等待，等再久也等不到，逾時只能把它切斷，不能預防它。下一節處理它。

兩個交易互相等，誰讓步？死結

等再久也等不到的情況，是第 19 課看過的死結（deadlock）：兩個交易各拿一把鎖、互相等對方的那一把。事故裡的 ALTER 是單向排隊，等報表結束就能前進，不會繞成一圈；死結出現在 App 自己的交易之間，最典型的地方是結帳扣庫存，所以這節換到 products 表。一張訂單買拿鐵和可頌，另一張買可頌和拿鐵，程式依購物車順序扣庫存：

步驟訂單 A（拿鐵＋可頌）訂單 B（可頌＋拿鐵）
1UPDATE products SET stock = stock - 1 WHERE id = 2;
2UPDATE products SET stock = stock - 1 WHERE id = 5;
3UPDATE … WHERE id = 5;
等 B…
4等 B…UPDATE … WHERE id = 2;
等 A…
5等 B…ERROR 40P01: deadlock detected
整個交易回滾
6拿到鎖，COMMIT ✓程式重試整個交易 → 成功

PostgreSQL 不會一開始等鎖就檢查死結：一個交易等鎖超過 deadlock_timeout（預設 1 秒），才去檢查等待有沒有繞成一圈，也就是第 5 步發生的事。所以它是「等多久之後才去檢查」，不是「多久算死結」。檢查死結要鎖住共享的鎖資訊，成本不低，所以 PostgreSQL 先樂觀地等一下。把它調大不會減少死結，只會讓死結晚一點被發現。

既然調參數沒用，死結要從寫法預防。三個做法：

  • 固定順序上鎖：多列一起改時，先依主鍵排序再鎖。例如一次鎖住整張訂單要用的商品：SELECT id FROM products WHERE id IN (5, 2) ORDER BY id FOR NO KEY UPDATE，再逐一扣庫存。兩張訂單都先鎖 2 再鎖 5，後到的只會排隊，不會互等。
  • 先拿需要的最強鎖：假設 A、B 兩個交易都先用 SELECT … FOR SHARE 讀拿鐵那一列，打算確認庫存後再扣。兩把 FOR SHARE 互不衝突，兩邊都拿到。接著 A 要 UPDATE 拿鐵，需要 FOR NO KEY UPDATE，被 B 的 FOR SHARE 擋住；B 也要 UPDATE，被 A 的 FOR SHARE 擋住，於是在同一列上繞成一圈。確定要改，就一開始用 FOR NO KEY UPDATE，後到的交易只會排隊等前一個結束。
  • 交易要短：拿鎖到放鎖的時間越短，撞在一起的機會越小。

預防只能降低機率，死結無法百分之百避免。程式收到 40P01 時，處理方式和 40001 一樣：從 BEGIN 開始重試整個交易，次數要有上限（第 31 課的 withRetry）。只重送失敗的那一句不行，因為整個交易已經回滾了。

💡 實務上：死結多半藏在「一次改很多列」的程式裡
常見來源：結帳時依購物車順序扣庫存、後台「批次修改訂單狀態」用迴圈逐筆 UPDATE、兩個排程同時整理同一批資料。發生 40P01 時，伺服器 log 會記下互等的連線各自在執行哪一句，排查時先看 log，就知道是哪兩段程式碼在搶。用迴圈或 ORM 批次更新時，送出前先把資料依 id 排序，是成本最低的預防。偶爾一兩次死結靠重試就好；同一組查詢反覆出現，才代表上鎖順序該改了。

到這裡，檢討報告的預防措施都有了：migration 有 lock_timeout、App 有逾時上限、扣庫存有固定順序。剩下最後一題：如果下次網站還是卡住，怎麼在現場找出是誰造成的？

下次再卡住，怎麼在現場找到根源？線上診斷

前面各節都在事前預防。事故已經發生時，要依序回答三個問題：誰在等？在等誰？最源頭是誰？回答它們需要兩個工具。

第一個是 pg_stat_activity，一個系統視圖，每條連線一列，記錄它目前在做什麼。常用欄位：

pg_stat_activity 欄位意思
stateactive（正在執行）、idle（閒置、沒有交易）、idle in transaction（交易開著、卻沒在執行任何查詢）
wait_event_type、wait_event在等什麼；Lock 代表在等鎖，Client／ClientRead 代表在等程式送下一句
xact_start目前交易開始的時間；越早代表交易開越久
query正在執行的那一句；閒置的連線顯示最後一句執行過的 SQL

第二個是函式 pg_blocking_pids(pid)：給它一條連線的 pid，它回傳擋住這條連線的所有 pid，型別是陣列；沒被擋就是空陣列。兩個合起來，正式環境的查詢長這樣：

SELECT pid, state, wait_event_type, now() - xact_start AS 交易時間,
       pg_blocking_pids(pid) AS blocked_by, left(query, 60) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY xact_start;

在這頁跑，只會看到自己這條連線（見課首），pg_blocking_pids 永遠是空陣列：

所以這頁準備了一份事故當下的快照 activity_snapshot，blocked_by 欄就是當時 pg_blocking_pids(pid) 的結果。現場和開頭的事故類似：一條 ALTER 卡在 orders 上，後面排著 App 的查詢，但這次擋住 ALTER 的不是報表：

要找的是根源（root blocker）：擋住別人、自己卻沒被任何人擋住的那一條。只有處理它，整條等待鏈才會解開；處理中間的人沒有用，因為它自己也在等。從受害者往上追，依結果由上到下：

  • 2101：blocked_by 是空的，卻擋住了 2205，它就是根源。它的狀態是 idle in transaction，從 13:41 開著交易，最後一句是 FOR UPDATE，之後就沒動靜，很可能是程式在交易中途去呼叫外部 API，或是錯誤處理漏了 ROLLBACK。
  • 2205（那條 ALTER）：在等 2101。
  • 2310～2313：在等 2205。2310 要的 ACCESS SHARE 和 2101 的鎖其實不衝突，卻被列為被 2205 擋住：pg_blocking_pids 會同時列出「持有衝突鎖的人」和「排在前面、要的鎖和我衝突的人」，這就是第一節的等待佇列。
  • 2402：交易比 2101 更早開始，但它沒有擋住任何人。「最老的交易」不一定是根源。

找到根源之後，有兩個工具，差別在處理的範圍是「一句查詢」還是「整條連線」：

pg_cancel_backend(pid)pg_terminate_backend(pid)
做什麼取消那條連線正在執行的查詢直接斷開整條連線
交易那一句失敗，交易進入失敗狀態，等程式 ROLLBACK交易回滾，鎖全部放開
適合active 的長查詢idle in transaction：它沒有正在執行的查詢，cancel 沒有東西可取消，鎖也不會放

2101 是 idle in transaction，所以要用 terminate。動手前先確認它是誰、在做什麼：terminate 會把那條連線還沒提交的工作全部回滾。如果它是一個跑了 40 分鐘、快完成的資料搬移，斷掉它代價很高；如果是一條忘了提交的 App 連線，斷掉通常比讓整個網站等下去好。斷掉之後也要回頭修程式，否則明天還會發生。根源也可能是沒有連線的 prepared transaction，這兩個函式都處理不了，做法見課末補充。

💡 實務上：事故當下先存證、再動手、事後修根源
網站卡住時，先把 pg_stat_activity 的查詢結果存下來（貼進事故頻道或存成檔案）；用 pg_terminate_backend 斷線之後現場就消失了，事後檢討會找不到證據。動手前在頻道說一聲要斷哪個 pid、它屬於哪個服務，讓負責的人有機會喊停，例如它其實是正在跑的資料搬移。雲端代管的資料庫（例如 AWS RDS）通常不給真正的 superuser。要斷別的角色的連線，帳號需要內建角色 pg_signal_backend，它允許取消、斷開其他角色的連線，最好事前確認值班帳號拿得到。事後檢討要回答的是「那條連線為什麼開著交易不放」：修好程式並設 idle_in_transaction_session_timeout，同樣的事故才不會重演。

補充與查表

materialized view 的 REFRESH：兩種寫法的鎖差很多

第 23 課的 materialized view 要定期 REFRESH。兩種寫法拿的鎖不同，同樣看最強的那一把：

  • 一般的 REFRESH 拿到 ACCESS EXCLUSIVE：更新期間連讀 product_menu 都要等。
  • CONCURRENTLY 最強只到 EXCLUSIVE，讀取照常；代價是比較慢，而且 materialized view 上要有唯一索引（這頁的 seed 已經建好 product_menu (id) 的唯一索引）。

根源是 prepared transaction 時

prepared transaction 沒有連線，在 pg_locks 的 pid 是 NULL，在 pg_blocking_pids 的結果裡顯示成 0，所以 cancel 和 terminate 都找不到對象。只能從 pg_prepared_xacts 找到它的 gid，再 COMMIT PREPARED 或 ROLLBACK PREPARED。

被遺忘的 prepared transaction 會一直拿著鎖，連重啟資料庫都不會消失；它也不受 transaction_timeout 限制（文件），只能靠人工處理。

版本備註
  • PostgreSQL 17：新增 transaction_timeout。
  • PostgreSQL 18：新增 log_lock_failures，可以把 SELECT … NOWAIT 拿不到列鎖的情況記進 log（目前只支援這一種）。
  • PostgreSQL 19（目前是 RC，以正式版說明為準）：log_lock_waits 預設開啟（等鎖超過 deadlock_timeout 就記 log）、新增 pg_stat_lock 視圖、max_locks_per_transaction 預設改為 128。

練習

練習 1：夜間批次程式開了一個交易，PREPARE TRANSACTION 'night_batch' 之後就沒再理它（題目已經準備好）。寫一句查詢，列出這個交易拿著的表級鎖：表名（relation::regclass::text）與 mode，依表名、模式排序。提示：查 pg_locks 這個動作本身也會拿鎖，不能算進去；交易編號那類不是表的鎖也不要；索引和序號也屬於 relation，要一起列出。

練習 2：月底盤點時要凍結 products：別人可以讀（一般 SELECT），但不能新增、修改、刪除。開一個交易，用 LOCK TABLE 拿最弱但足夠的鎖，然後 PREPARE TRANSACTION 'stocktake'，讓判分程式看得到這把鎖。對照衝突表：哪幾種模式擋得住 ROW EXCLUSIVE？其中誰最弱？

練習 3：一個幫顧客 1 改名的交易已經 PREPARE 了（題目已經準備好）。客服想知道：現在幫顧客 1 新增訂單，外鍵檢查會不會被擋？寫一句不會等待的查詢，用外鍵檢查實際使用的那種列鎖去鎖顧客 1，成功時回傳顧客的 id。

練習 4：把「找根源」存成 view blocking_roots：列出擋住了別人、自己卻沒被任何人擋住的連線，欄位依序是 pid、state、xact_start、query。判分會在 activity_snapshot 裡再加入另一組事故鏈，然後查這個 view，所以要寫成通用的條件，不能看資料寫死。提示：「x 在陣列裡」寫成 x = ANY (陣列)，陣列長度用 cardinality(陣列)。

練習 5：一份 2 分鐘的報表正在讀 orders。你執行只要幾毫秒的 ALTER TABLE orders ADD COLUMN note text（沒有設 lock_timeout）。接下來 App 對 orders 的一般 SELECT 會怎樣？

✓ ALTER 要 ACCESS EXCLUSIVE，得等報表結束，於是進入等待佇列；後來的 SELECT 雖然和報表不衝突，卻和排在前面的 ALTER 衝突，只好排在它後面。a 忽略了佇列；b 把「執行時間短」誤當「等待時間短」；d：PostgreSQL 不會為了 DDL 中斷別人的查詢。解法是 DDL 前 SET lock_timeout。

練習 6：系統一天出現好幾次 deadlock detected（40P01）。最好的長期解法是？

✓ 固定順序讓互等繞不成一圈，重試處理剩下的少數情況。a：deadlock_timeout 只是「多久之後才檢查」，調大只會讓死結更晚被發現。c：40P01 時整個交易已經回滾，只重送一句會在沒有前面那些修改的狀態下執行。d：更嚴格的隔離等級不會減少鎖的互等，還會多出 40001。

練習 7：診斷發現根源是一條 idle in transaction 的連線，已經拿著鎖 20 分鐘。對它執行 pg_cancel_backend(pid) 有用嗎？

✓ cancel 只取消「正在執行的那一句」，idle in transaction 的連線正在等程式送下一句，沒有東西可以取消。terminate 斷開整條連線，交易回滾、鎖放開，但它還沒提交的工作也會消失，所以動手前要先確認它是誰。長期解法是修程式，並設定 idle_in_transaction_session_timeout。

常見錯誤

  • DDL 沒有設 lock_timeout：ALTER 排在長查詢後面，又擋住後面所有查詢。每個 DDL 前 SET LOCAL lock_timeout，失敗就稍後重試。
  • 在交易外 LOCK TABLE，或以為交易外的 FOR UPDATE 有保護作用：LOCK TABLE 會直接報 25P01；FOR UPDATE 會在那一句結束時就放開鎖。鎖要在 BEGIN 之後拿。
  • 只需要 FOR NO KEY UPDATE 卻寫 FOR UPDATE：不改主鍵的話，用 FOR UPDATE 會額外擋住子表的外鍵檢查，顧客被鎖著時連下單都要等。
  • 多列更新沒有固定順序：依購物車、依輸入順序上鎖，遲早死結。先依主鍵排序再鎖。
  • 交易裡呼叫外部 API、等使用者回應：鎖跟著一起等。外部呼叫移到交易外，並設 idle_in_transaction_session_timeout。
  • 看到卡住就 terminate：會回滾那條連線所有未提交的工作。先用 pg_stat_activity 確認它是誰、在做什麼、開了多久。
  • 以為 SELECT … NOWAIT（以及第 33 課的 SKIP LOCKED）也管表級鎖：它們只管列鎖；表被別人用 ACCESS EXCLUSIVE 鎖住時，它要的表級 ROW SHARE 照樣會排隊等（文件明寫）。要「表也不等」，用 LOCK TABLE … NOWAIT 或 lock_timeout。
  • 營業時間跑沒有 CONCURRENTLY 的 REFRESH MATERIALIZED VIEW：更新期間所有讀取都卡住。加唯一索引、改用 CONCURRENTLY。

小結

回到事故檢討的四個問題：

  • 為什麼整站停擺：每個指令都會拿表級鎖並留到交易結束；拿不到的請求依序排隊，排在前面的強鎖會擋住後面所有和它衝突的弱鎖。ALTER 本身只要幾毫秒，是它在佇列裡等報表的那段時間拖住了全站。DDL 前設 lock_timeout，等不到就放棄、稍後重試。
  • 今晚每句會擋住誰：SELECT 是 ACCESS SHARE、寫入是 ROW EXCLUSIVE、CREATE INDEX 是 SHARE、大多數 ALTER TABLE 是 ACCESS EXCLUSIVE。在交易裡查 pg_locks WHERE pid = pg_backend_pid() 就能自己量。衝突表的口訣：讀只怕 ACCESS EXCLUSIVE，寫怕 SHARE 以上；需要時用 LOCK TABLE … NOWAIT 驗證。
  • App 的交易之間：列鎖有四種，改非鍵欄位拿 FOR NO KEY UPDATE，外鍵檢查拿 FOR KEY SHARE，所以改顧客名字不會擋住幫他下單；手寫鎖時別用過強的 FOR UPDATE。四個逾時設定各管等鎖、單句、閒置交易、整個交易。死結由 PostgreSQL 偵測並讓一方得到 40P01；固定順序上鎖、交易要短，並重試整個交易。
  • 下次怎麼在現場處理：pg_stat_activity＋pg_blocking_pids 找出「擋住別人、自己沒被擋」的根源；active 的查詢用 cancel，idle in transaction 要 terminate（會回滾），prepared transaction 要 ROLLBACK PREPARED。
