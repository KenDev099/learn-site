階段 1：CRUD（增查改刪） · 第 3 課

新增資料：INSERT

咖啡店的後台要上線第一批「建立」功能：新會員註冊、開店前上架新品、客人結帳時建立訂單。在前端，這三件事是三個表單和三個 POST 請求；到了後端，每一個最後都會變成一句 SQL，把一筆新資料寫進第 2 課建好的表。那句 SQL 就是 INSERT。

這一課沿著這三個功能，一路寫到結帳 API 的最後一步：訂單寫進去之後，把新訂單的編號回給前端，讓畫面跳到訂單頁。途中會遇到每個寫後端的人都會碰到的問題：表單沒送的欄位會變成什麼、值的順序寫錯會怎樣、資料庫擋下來時錯誤訊息怎麼讀。後端的資料操作常被統稱為 CRUD，也就是 Create（新增）、Read（查詢）、Update（修改）、Delete（刪除）；這一課是第一個字母 C。

這課會用到：
  • 第 2 課的 GENERATED ALWAYS AS IDENTITY：每新增一列，資料庫自動給下一個編號，你不用也不能自己填。
  • 第 2 課的 NOT NULL：寫在欄位上的規則，意思是「這欄一定要有值」。
這課的路線：
  1. 新會員註冊：一句 INSERT 由哪幾個部分組成，欄位和值怎麼配對。
  2. 開店前上架三樣新品：一句 INSERT 新增多列，為什麼它們會一起成功或一起失敗。
  3. 結帳的 INSERT 只寫顧客和金額：沒寫到的欄位，資料庫用什麼規則補上（預設值、NULL）。
  4. 值的順序寫錯、資料庫擋下的錯：哪些錯會報錯，哪些會默默把資料放錯，錯誤訊息怎麼讀。
  5. 訂單寫進去之後：用 RETURNING 直接拿回新訂單的 id，完成結帳 API。

新會員註冊：一句 INSERT 長什麼樣？

第一個功能最單純：一位新客人黃淑芬填了註冊表單，送來名字、電話、城市三個欄位，後端要把她存進 customers 表。寫成 SQL 是這樣：

INSERT INTO customers (name, phone, city)
VALUES ('黃淑芬', '0911-222-333', '台北');

這句由三個部分組成：

  • INSERT INTO customers：要把新的一列放進 customers 表。
  • (name, phone, city)：欄位清單，說明這次要填哪幾欄。
  • VALUES (...)：值清單，每個欄位要放的值。文字用單引號包起來，數字不用。

欄位清單和值清單是依位置一個對一個：第 1 個值放進第 1 個欄位，第 2 個值放進第 2 個欄位，依此類推。資料庫不會去看值「像不像」名字或電話，它只看位置。這一點後面會反覆用到，先記住下面這張圖的上半部；下半部是沒寫到的欄位怎麼辦，第三節會講。

開店前上架三樣新品：要寫三句 INSERT 嗎？

店長早上要一次上架焦糖瑪奇朵、抹茶拿鐵、布朗尼三樣新品。照上一節的寫法，就是三句 INSERT。不過 VALUES 後面可以放好幾組括號，用逗號隔開，每一組是一列，一句就能新增三列：

結果區會顯示影響 3 列，表的最後多了三樣新品。寫成一句有兩個好處：

  • 比較快：後端和資料庫之間每送一句 SQL 就是一次來回。三句是三次來回，一句只要一次。筆數一多，差距就很明顯。
  • 一起成功或一起失敗：這三列是同一句 SQL 寫進去的，只要其中一列有錯（例如價格不是數字），整句就失敗，三列都不會寫進去。不會出現「前兩樣上架了、第三樣沒有」的半套狀態。

第二點是資料庫的一個重要保證：單一一句 SQL 不會只做一半。如果你寫的是三句各自送出的 INSERT，每一句就各自成功或失敗，第三句出錯時前兩句已經寫進去了。要讓好幾句 SQL 也像一句那樣全有或全無，得用交易（transaction）把它們綁成一組，這是第 18 課的主題，現在只要知道有這個工具就好。

💡 實務上：後台「匯入商品」要先決定全有還是全無
咖啡店後台常有「上傳 Excel／CSV 批次上架」的功能，背後常常就是一句多列 INSERT。後端常用 ORM 這類函式庫，讓你用 JS 物件和方法操作資料庫，它再替你產生 SQL；在 ORM 裡，這種一次新增多列的方法通常叫 createMany 或 bulk insert，送到資料庫的就是上面這種多列 INSERT。一起成功或一起失敗是優點，也是要先跟 PM 講好的規則：上傳 200 筆、第 137 筆價格空白，是整批退回並指出錯在哪一列，還是先寫入其他 199 筆？整批退回比較好收拾，「匯了一半」最麻煩。資料量很大時常會分批送（例如每次幾百筆），但每批是各自成功或失敗的；想要整份檔案全有或全無，得把這幾批包在同一個交易裡。

上架的結果裡還有一件事值得注意：我們只填了名字、分類、價格，is_available 卻自動是 true。下一個功能「結帳建立訂單」會把這件事推到極致，因為前端只會送來兩個欄位。

結帳的 INSERT 只寫顧客和金額：沒填的欄位會變成什麼？

客人結帳時，前端送到後端的是「誰買的」和購物車內容。總金額由後端依資料庫裡的商品價格算出來，不收前端傳來的總額，因為前端送來的任何數字都可能被改過。所以結帳的 INSERT 只帶 customer_id 和 total 兩欄。可是一筆訂單除了這兩欄，還有下單時間和訂單狀態。這兩欄該由誰填？如果每個寫 INSERT 的地方都要記得帶時間和 'pending'，總有一處會忘記。資料庫的解法是在建表時寫好預設值。

預設值（DEFAULT）是寫在欄位定義上的一個值：INSERT 沒提到這個欄位時，資料庫就自動放進這個值。這一課的 products 和 orders 建表時就加了預設值：

CREATE TABLE products (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  category text,
  price integer NOT NULL,
  is_available boolean DEFAULT true   -- 沒填就是 true（上架中）
);

CREATE TABLE orders (
  id integer GENERATED ALWAYS AS IDENTITY (START WITH 101) PRIMARY KEY,
  customer_id integer,
  ordered_at timestamptz DEFAULT now(),  -- 沒填就是「現在」
  status text DEFAULT 'pending',         -- 沒填就是待付款
  total integer NOT NULL
);

這裡有兩個新東西要先說清楚：

  • now() 是 PostgreSQL 內建的函式，回傳「現在的時間」。寫在 DEFAULT 裡，意思是每次新增時取當下的時間，而不是建表那一刻的時間。
  • START WITH 101 讓訂單編號從 101 開始，所以訂單 id 是 101、102……而不是從 1 開始。

沒寫到的欄位還有一種可能：既不是 IDENTITY，也沒有預設值。這時資料庫會放 NULL。NULL 在 SQL 裡代表「沒有值」，它不是 0、不是空字串 ''，就是這一格空著。把這幾種情況合起來，就是上面那張圖下半部的規則，順序固定：

  1. 是 IDENTITY → 給下一個編號。
  2. 有 DEFAULT → 放預設值。
  3. 都沒有 → 放 NULL。如果這欄是 NOT NULL，空著就違反規則，整句報錯。

  • id 是 106：IDENTITY 從 101 開始，前面已經有 5 筆。
  • ordered_at 是你按下執行的時間：來自 DEFAULT now()。
  • status 是 pending：來自 DEFAULT 'pending'。

後端很常這樣分工：建立時間、初始狀態這類「每一筆都一樣的規則」交給資料庫，程式只送使用者真正輸入的東西。這樣就算有新的程式路徑（例如批次匯入腳本）忘了帶，資料也不會缺。

規則的第 3 條也試一次。上架一樣新品「季節特調」，分類還沒決定，所以不填 category：

category 沒有 DEFAULT，所以是 NULL；is_available 有 DEFAULT，所以是 true。

欄位寫進清單，但想要預設值或 NULL

到目前為止，用預設值的方法都是「不寫那個欄位」。有時候欄位已經在清單裡（例如程式固定用同一組欄位清單），這時可以在值的位置寫關鍵字 DEFAULT，意思是「這格用預設值」；想明確放「沒有值」，就寫 NULL。兩個都不加引號：加了引號的 'NULL' 是四個英文字母組成的文字，跟「沒有值」完全不同。

肉桂捲的 category 是 NULL，is_available 是預設的 true。

這裡藏著結帳 API 一個常見的坑：預設值只在欄位沒出現在 INSERT 裡時才會生效。只要欄位寫進清單、值給了 NULL，資料庫就照你說的放 NULL，不會改用預設值。

💡 實務上：建立時間交給資料庫，但小心前端送來的 null
訂單的 ordered_at、會員的註冊時間，實務上幾乎都用 DEFAULT now()，不信任前端送的時間：使用者的手機時鐘可能不準，也可能被改過。常見的坑是：如果結帳 API 把前端表單原封不動傳下來，status: null 會被當成「明確放 NULL」，預設的 pending 就不會出現。所以後端通常會挑出允許的欄位再寫入，而不是整包照收。接手專案時也值得看一下哪些欄位有 DEFAULT，才知道程式沒帶時會發生什麼。

到這裡，三個功能的 INSERT 都寫得出來了。不過每一句都依賴同一件事：值的順序要跟欄位清單對上。如果順序寫錯，會發生什麼？

值的順序寫錯會怎樣？

先說好消息：欄位清單的順序不必跟建表時一樣。資料庫只要求值清單跟著欄位清單的順序走。下面把 city 寫在 name 前面，照樣成功：

壞消息是同一件事的反面：資料庫只看位置，所以值的順序一寫錯，資料就會放進錯的欄位。這時有兩種結果：

  • 型別不合，被擋下來：例如把 '拿鐵' 對到 integer 的價格欄，資料庫轉不成數字就報錯。這是運氣好的情況，你當場就知道寫錯了。
  • 型別剛好相容，默默放錯：name 和 city 都是 text，寫反了資料庫也照收，結果顧客名字叫「高雄」、住在「吳家豪」。沒有任何錯誤訊息，要等有人在畫面上看到才會發現。

第二種比第一種危險得多。防它的方法就是每次都明確寫出欄位清單，讓讀程式的人（包括 code review 的同事）一眼對得出每個值放到哪一欄。

為什麼不要省略欄位清單

欄位清單其實可以整個省略。這時值必須按照建表時的欄位順序排列，而且每一欄都要給，IDENTITY 的 id 也要寫 DEFAULT 佔位：

能跑，但很脆弱：這句依賴「表現在剛好是這四欄、這個順序」。哪天表多了一個欄位（第 22 課會教怎麼加），這句就會出錯；更糟的是欄位順序變了、型別又剛好相容，值就默默放錯欄。實務上一律寫出欄位清單。

上面提到「型別不合會被擋下來」。資料庫會擋的不只這一種，而且擋下來時給的錯誤訊息，就是你之後在後端 log 裡會看到的東西。下一節把常見的三種實際跑一次。

資料庫擋下來時，錯誤訊息怎麼讀？

結帳 API 上線後，某天 log 出現一行 PostgreSQL 的錯誤。能不能很快看懂它在說什麼，決定你要花五分鐘還是一小時找問題。下面三個框框各故意犯一種錯，依序執行，讀讀每個錯誤訊息：

三則訊息依序對應三種錯：

  1. INSERT has more target columns than expressions：target columns 指欄位清單，expressions 指值清單。欄位有 3 個、值只有 2 個，資料庫不知道第 3 欄要放什麼，乾脆整句拒絕。反過來值比欄位多，訊息是 more expressions than target columns。
  2. invalid input syntax for type integer: "拿鐵"：「拿鐵」要放進 integer 欄位，但轉不成整數。訊息會把型別和出問題的值都寫出來，看到它就去找「哪個值被放進了數字欄」，通常是順序寫錯，或前端送來的格式不對。
  3. null value in column "name" of relation "products" violates not-null constraint：relation 在 PostgreSQL 裡就是表。整句意思是「products 表的 name 欄收到 NULL，違反了 NOT NULL 規則」。INSERT 沒寫 name，它又沒有預設值，照規則第 3 條會放 NULL，於是被擋下。

這三種錯都在資料寫進去之前就被擋下，表裡不會留下半筆壞資料。這正是第 2 課說的「型別和規則是最後一道防線」：就算前端表單漏了檢查，錯的資料也進不了資料庫。

💡 實務上：在 log 裡看到這三種訊息，先往哪裡查
後端的 log 通常只會留下這一行錯誤訊息，加上出錯的 API 路徑。看到 more target columns than expressions，多半是程式組 SQL 時欄位和值的數量沒對齊；看到 invalid input syntax，先看前端或匯入檔送來的值是不是格式不對（例如價格欄收到「八十」）；看到 violates not-null constraint，先查前端是不是漏送必填欄位。回報給前端時，不要把資料庫原文直接丟給使用者，而是轉成「商品名稱必填」這類看得懂的訊息。

錯誤擋得住、預設值也補得上，結帳的 INSERT 已經能穩定寫進去了。剩下最後一步：訂單寫進去之後，前端要跳到訂單頁，它需要知道這筆訂單的 id。

訂單寫進去了，怎麼把 id 回給前端？

新訂單的 id 是資料庫的 IDENTITY 產生的，後端在送出 INSERT 之前並不知道它是多少。一種做法是 INSERT 完再查一次，但「查剛剛那一筆」並不好寫：如果同一時間有別的客人也在結帳，「最新的一筆」可能是別人的。

PostgreSQL 的解法是在 INSERT 最後加上 RETURNING，後面列出要拿回的欄位。資料庫寫完那一列後，會把那一列的這些欄位直接回傳，就像 SELECT 的結果一樣：

結果區出現一列：新訂單的 id、資料庫補上的 pending 和下單時間。這三個值都是資料庫決定的，後端在送出前不知道，現在一次全拿回來了，而且保證是「剛剛這一筆」的值，不會跟別人的訂單混在一起。

你在 Strapi 或 ORM 裡呼叫「建立」後拿到一個帶 id 的物件，背後通常就是這樣來的。RETURNING 也能接在 UPDATE、DELETE 後面，第 6 課會再細講。

RETURNING 拿回的 id 是 106、107 這種資料庫編的號碼，前端常會想直接拿來顯示，但它有一個特性要先知道：

編號可能會跳號。IDENTITY 發出去的號碼不會收回：新增失敗、或這筆資料後來被刪掉，那個號碼就空著，下一筆繼續往後編。所以 id 只用來「認出某一列」，不要拿它來算「總共有幾筆」，也不要期待它連續。
💡 實務上：「建立」API 的典型流程
前端送出結帳 → 後端 POST /orders 執行 INSERT … RETURNING → 把新訂單（含 id、狀態、時間）回給前端，前端再跳到訂單頁。要考量的是：使用者連按兩次送出，就會建立兩筆訂單，所以前端會先把按鈕停用，後端也會再擋一層（例如 UNIQUE 規則，第 12 課會教）。另外，除了上面說的會跳號，內部 id 又是依序遞增（別人看編號就能猜出你一天有幾筆訂單），不適合直接當成給客人看的訂單編號，很多系統會另外產生一組對外的編號。

到這裡，三個「建立」功能都完成了：註冊、上架、結帳都能寫進資料庫，結帳還能把新訂單回給前端。

補充與查表

  • 數字加了引號也會成功：INSERT INTO products (name, price) VALUES ('可頌', '70') 其實會成功。PostgreSQL 看到要放進 integer 欄位的 '70'，會試著把它轉成數字，轉得過就接受；'七十' 轉不過才報錯。但數字還是不要加引號，意思才清楚。
  • now() 取的是交易開始的時間：now() 回傳的是目前這個交易開始的時間，同一個交易裡呼叫多次都會得到同一個值。單句 INSERT 自己就是一個交易，所以這一課感覺不出差別；把多句包進同一個交易時，裡面每一列的 DEFAULT now() 都會是同一個時間。交易的細節見第 18 課。

✓ 沒列出的欄位會用 DEFAULT；只有在沒有 DEFAULT 時才會是 NULL，而只有 NOT NULL 又沒 DEFAULT 的欄位才會報錯。

練習 6：INSERT INTO products (price, name) VALUES ('拿鐵', 110); 會發生什麼事？

✓ 值是依位置對到欄位清單的：第一個值 '拿鐵' 對到第一個欄位 price，轉不成整數就被擋下來（invalid input syntax for type integer）。

常見錯誤

  • 文字用了雙引號：VALUES ("拿鐵", 110) 會被當成欄位名稱，出現 column "拿鐵" does not exist。文字一律用單引號，雙引號是用來包名稱的（第 2 課）。
  • 值和欄位數量不一樣：INSERT has more target columns than expressions（值太少）或 more expressions than target columns（值太多）。逐一對齊欄位清單和值清單。
  • 自己填 IDENTITY 的 id：GENERATED ALWAYS 不讓你填，會出現 cannot insert a non-DEFAULT value into column "id"。把 id 從欄位清單拿掉就好。
  • 把 'NULL' 加了引號：放進去的是文字 NULL，不是真的沒有值，之後用第 4 課的 IS NULL 會找不到它。
  • 以為傳 null 會用預設值：欄位寫進 INSERT、值是 NULL，資料庫就放 NULL。要用預設值，就不要寫這個欄位，或在值的位置寫 DEFAULT。
  • 多列 INSERT 最後多一個逗號：('布朗尼', '甜點', 85),; 會出現 syntax error。

小結

  • 後台的每個「建立」功能，最後都是一句 INSERT INTO 表 (欄位, …) VALUES (值, …);，欄位和值依位置一對一。
  • VALUES 後面放多組括號可以一次新增多列，比多句快，而且整句一起成功或一起失敗；多句之間要全有或全無得用交易（第 18 課）。
  • 沒寫到的欄位：IDENTITY 自動編號 → 有 DEFAULT 用預設值 → 其他放 NULL（NOT NULL 會報錯）。明確寫 NULL 不會觸發預設值。
  • 順序寫錯時，型別不合會報錯，型別相容就默默放錯欄，所以永遠寫出欄位清單。
  • 三種常見錯誤訊息：值和欄位數量不符、invalid input syntax、violates not-null constraint，都在寫入前擋下。
  • INSERT … RETURNING 直接拿回剛新增那一列由資料庫產生的值（id、預設值），結帳 API 用它把新訂單回給前端。
