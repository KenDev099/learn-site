階段 3：資料品質 · 第 14 課

JSONB 與陣列

咖啡店的點餐 App 要加上「客製」：點拿鐵時可以選甜度、冰塊，加一份濃縮，或把牛奶換成燕麥奶（加 20 元）。前端的選單已經做好，送到後端的是一包 JSON，例如 {"sugar": "半糖", "ice": "少冰", "milk": {"type": "燕麥奶", "extra": 20}}。你要決定這包資料怎麼存進 order_items，而且存好之後有三個地方等著用：吧台出單要印出「半糖、少冰」，後台要能篩出「無糖」的明細，訂單列表 API 要把結果組成 JSON 回給前端。同一次改版，菜單的商品卡片也要加上「熱門」「季節限定」標籤，讓使用者點標籤篩選。

第 11 課說「一格只放一個值」，照這條規則，每個選項都該開一個欄位。這一課會用到 PostgreSQL 刻意提供的兩個例外：JSONB（一格放一整個 JSON 物件）和陣列（一格放一串值），學會怎麼存、怎麼取、怎麼查。這課最後會走到上線一個月後：老闆要看甜度分布，你會親眼看到把資料放進 JSONB 的代價，學會判斷什麼資料不該放進去。前端工程師對 JSON 很熟，最容易犯的錯正是「什麼都往 JSON 塞」，所以最後這段判斷和語法一樣重要。

這課會用到：
  • 第 11 課的正規化：一格只放一個值，不把好幾個值塞進同一格。
  • 第 12 課的 CHECK：寫入時檢查值符不符合規則，不符合就擋下。
  • 第 13 課的型別轉換 ::：'42'::integer 把文字當成整數使用。
  • 第 7 課的 GROUP BY 和聚合函式：把同一組的很多列算成一個值，例如 COUNT。
這課的路線：
  1. 選項每杯都不一樣，要怎麼存：為什麼整包放進一個 jsonb 欄位，而不是開幾十個大多是 NULL 的欄位。
  2. 吧台出單：用 -> 和 ->> 從 jsonb 取出一個值，兩者差在拿回來的型別。
  3. 後台篩選：用 ->> 比較一個值，或用 @> 問「有沒有包含這些選項」；再看 API 寫入時，資料庫檢查了什麼、沒檢查什麼。
  4. 菜單標籤與訂單列表：一串值用陣列存；array_agg 和 jsonb_build_object 把多列整理成 API 要的形狀。
  5. 上線一個月後：老闆要看甜度分布，哪些資料不該放進 JSONB 或陣列。

每杯飲料的選項都不一樣，要怎麼存？

先試最直覺的做法：每個選項開一個欄位，sugar、ice、extra_shot、milk_type、milk_extra……問題馬上出現：選項跟著商品走。咖啡有甜度和冰塊，可頌只有「要不要加熱」，南瓜派什麼選項都沒有。於是可頌那一列的 sugar、ice、milk_type 全是 NULL，咖啡那一列的 heat 是 NULL。店裡有幾十種選項時，order_items 就有幾十個欄位，每一列只用到其中兩三個。更麻煩的是每推出一個新選項，例如冬季限定的「加肉桂粉」，就要改一次表結構。

再看這些選項怎麼被使用：吧台出單、前端顯示訂單時，幾乎都是整包讀出來照著印，很少有人單獨拿「冰塊」去計算。這類資料有三個特徵：每一列的結構不一樣、主要是整包存取、很少單獨查詢。PostgreSQL 為這種資料準備了 jsonb 型別：一個欄位存一整個 JSON 物件，每一列的 key 可以不同，新增選項也不用改表。這頁的 order_items 就是這樣設計的，執行後看 options 那一欄：

可頌（product_id 6）只有 heat，南瓜派是空物件 {}，拿鐵有 sugar、ice，有幾列還多了一層巢狀的 milk。欄位宣告是 options jsonb NOT NULL DEFAULT '{}'：沒有選項就存空物件而不是 NULL，讀的人少處理一種情況。

這張 order_items 用自己的 id 當主鍵，不是第 10 課的複合主鍵 (order_id, product_id)，原因也出在客製選項：同一張訂單可能點兩杯拿鐵，一杯半糖、一杯無糖。這是兩個不同的品項，必須是兩列；複合主鍵會把它們當成重複而擋下第二杯。

有了 jsonb，不代表所有欄位都該收進去。同一張表裡的 order_id、product_id、quantity、unit_price 仍然是一般欄位：每一列都有、要外鍵、要 NOT NULL，結帳時要拿來加總。這些是資料庫必須「理解」的值，放在一般欄位，資料庫才能替你把關。分工如下圖：

吧台出單要印「半糖」：怎麼從 jsonb 取出一個值？

在 JavaScript 裡你會寫 options.sugar。PostgreSQL 用兩個運算子做這件事：-> 和 ->>。兩個都是「取出某個 key 的值」，差別在拿回來的型別：

  • options -> 'sugar' 回傳 jsonb：取出來的東西還是 JSON，可以繼續往下取。
  • options ->> 'sugar' 回傳 text：把 JSON 值轉成一般文字，可以拿來顯示、比較、轉型別。多一個 >，記成「取到底，變成文字」。

為什麼要分兩種？因為 JSON 的值不只有字串，還可能是數字、true／false，或另一個物件。-> 保留「這是一個 JSON 值」的身分，你還能對它做 JSON 的操作；->> 用在已經取到最後一層、要交給一般 SQL 使用的時候。

這頁的結果表格會用 JSON.stringify 顯示 JSON 值，所以兩者在畫面上看起來差不多。為了看出差別，下面多查兩樣東西：pg_typeof() 是回傳「這個值是什麼型別」的函式，(…)::text 把 jsonb 轉成資料庫實際存的文字。執行後比較 arrow_raw 和 double_arrow 兩欄：

  • arrow_type 是 jsonb，double_arrow_type 是 text。
  • arrow_raw 是 "半糖"，帶著雙引號：這是 JSON 字串的寫法，引號是值的一部分。double_arrow 是 半糖，沒有引號，就是一般文字。
  • 第 2 列是可頌，它沒有 sugar 這個 key，兩種寫法都回傳 NULL，不會出錯。

出單機要印的是給人看的文字，所以用 ->>；用 -> 印出來會多一對引號。

燕麥奶的資訊多了一層：milk 本身又是一個物件 {"type": "燕麥奶", "extra": 20}。這時就看得出 -> 的用處：先用 -> 取出 milk，拿到的還是 jsonb，所以能繼續往下取，最後一層再用 ->> 取出文字。規則是中間每一層用 ->，最後一層用 ->>。執行後看 milk_type 欄，WHERE 只留下有 milk 的列：

吧台和收銀都讀得到選項了。接下來後台要的不是讀出某一筆，而是篩選：「列出所有無糖的明細」「哪些加了濃縮」。

後台要篩出「無糖」「加濃縮」：用 ->> 比較，還是用 @>？

上一節的 ->> 可以直接放進 WHERE。用 ->> 而不是 -> 的理由跟出單一樣：右邊的 '去冰' 是一般文字，左邊也要是文字才能比較。執行後看回傳的列是否都是去冰：

如果寫成 options -> 'ice' = '去冰'，左邊是 jsonb，PostgreSQL 會試著把右邊的 '去冰' 也當成 JSON 解析。去冰 沒有雙引號，不是合法的 JSON，查詢直接出錯；要讓它變成合法的 JSON 字串得寫成 '"去冰"'，多一層引號要顧。所以和一般值比較時，一律用 ->>。

->> 適合比較一個 key 的文字值。但後台的篩選常常是「符合這幾個選項」，而且有些值不是文字：extra_shot 存的是 JSON 的 true，用 ->> 取出來會變成文字 'true'。每寫一個條件，你都得記得那個 key 存的是什麼型別、要怎麼比。PostgreSQL 為 jsonb 準備了另一個運算子 @>，讓你直接用 JSON 描述要找的內容。

A @> B 讀作「A 包含 B」：B 裡的每一個 key 和值，A 都要有，而且值要相同；A 多出來的 key 不影響結果。所以 options @> '{"sugar": "無糖"}' 會找出甜度是無糖的明細，不管它還有沒有冰塊、濃縮這些其他選項。執行後看回傳的 4 列，它們的其他選項各不相同：

右邊寫的是 JSON，比對時也照 JSON 的型別規則。找加了濃縮的明細，要寫 true（JSON 的布林值），不是 "true"（JSON 字串）：

回傳 3 列。如果寫成 '{"extra_shot": "true"}'，一列都找不到：存的是布林值 true，和字串 "true" 不相等。要同時符合好幾個條件，就寫進同一個物件，例如 '{"sugar": "無糖", "extra_shot": true}'。

兩種寫法怎麼選：比較單一個文字值，->> … = 最直覺；要比對「包含這些選項」，或值是數字、布林、巢狀物件時，@> 比較不容易寫錯。@> 另一個好處是能用索引加速，細節見課末。

這次會出錯，資料寫不進去。jsonb 在寫入時就會解析整段文字，格式不合法就拒絕。

問題是，這就是資料庫替你做的全部檢查：它只確認「這是不是合法的 JSON」，不知道你的選單長什麼樣。{"Sugar": "half"} 是完全合法的 JSON，所以 key 的大小寫拼錯、值用了英文、多出一個沒人認得的 key，資料庫都照收。一般欄位有欄位名稱和型別，INSERT 寫錯欄位名稱會直接報錯；JSON 裡的 key 只是資料，你沒有告訴資料庫任何規則，它就不會檢查。這些寫錯的資料不會立刻出事，要等到有人拿它來統計才會浮現，這課最後一節會看到。

💡 實務上：資料庫只檢查「是不是 JSON」，內容要在 API 把關
咖啡店的點餐 API 收到前端送來的客製選項，資料庫只會擋下格式壞掉的 JSON，{"Sugar": "half"} 這種拼錯的照樣寫得進去。所以實務上會在後端先做 schema 驗證：事先寫好「允許哪些 key、每個 key 可以是哪些值」，不符合就回錯誤（TypeScript 專案常用 Zod 這類函式庫），通過才寫入資料庫。前端送選項時也盡量從固定的選單產生，不要讓使用者自由輸入 key。Code review 看到「直接把 request body 整包存進 jsonb」時，資深工程師會先問：這包內容誰來驗證？

客製選項的存、讀、查、寫都有了。開場提到的改版還有另一半：菜單商品卡片上的標籤。

菜單上的「熱門」「季節限定」：一串值為什麼用陣列？

新版菜單的商品卡片要顯示「熱門」「季節限定」這類標籤，使用者點一下標籤就能篩選。標籤和客製選項的形狀不同：選項是一個物件，每個值有自己的 key（甜度是半糖、冰塊是少冰）；標籤只是一串同型別的文字，沒有 key。用 jsonb 也存得下 ["熱門", "冰飲"]，但對「一串同型別的值」，PostgreSQL 有更直接的型別：陣列。

任何型別後面加 [] 就是那個型別的陣列，例如 text[]、integer[]。陣列裡每個元素都是同一個型別，資料庫會檢查，integer[] 放不進文字；這是陣列比 JSON 多的一層保護。products 的 tags 就是 text[]，執行後看 tags 欄：

拿鐵有兩個標籤，可頌是空陣列。寫入陣列有兩種寫法：SQL 語法 ARRAY['熱門', '冰飲']，或陣列的文字格式 '{熱門,冰飲}'，這頁建立範例資料的 SQL（頁尾的 seed）用的是前者。

菜單的篩選就是「tags 裡有沒有某個標籤」。寫法是 值 = ANY (陣列)：只要陣列裡有任何一個元素等於這個值，條件就成立，這是查陣列最常用的寫法。下面篩出有「熱門」標籤的商品，順便取出第一個標籤和標籤數量：

  • WHERE '熱門' = ANY (tags) 留下美式咖啡、拿鐵、抹茶拿鐵三個商品。
  • tags[1] 取第一個元素。PostgreSQL 的陣列從 1 開始數，不是 JavaScript 的 0；寫 tags[0] 不會報錯，只會拿到 NULL，所以這個錯不容易發現。
  • cardinality(tags) 是陣列的元素個數，相當於 JavaScript 的 length。

要「兩個標籤都要有」時，陣列也能用後台篩選時學過的 @>：tags @> ARRAY['熱門', '冰飲'] 表示右邊的每個元素，左邊都要有，意思和用在 jsonb 上時一樣。

💡 實務上：標籤用陣列，還是開一張表？
後台只要「顯示標籤、用標籤篩選」時，text[] 很省事。但如果 PM 接著要「改標籤名稱一次套用到全部商品」「列出所有標籤和各有幾個商品」「標籤要有顏色和排序」，標籤就變成有自己屬性的東西，該拆成 tags 表加中間表（第 10 課）。開發前先問 PM 標籤之後會不會被管理，比上線後再搬資料便宜得多。

陣列除了存在欄位裡，還有一個常見的用法：查詢時把很多列收成一個陣列。這正是訂單列表 API 需要的。

訂單列表 API 要一張訂單一列：怎麼把多列收成陣列、組成 JSON？

後台的訂單列表要顯示「訂單 3：抹茶拿鐵、南瓜派」。品項在 order_items，一張訂單有好幾列。如果在程式裡先查出訂單，再對每張訂單各查一次明細，一頁 50 張訂單就是 51 次查詢。更好的做法是讓資料庫直接把同一張訂單的多列收成一格。

array_agg 就是做這件事的聚合函式。第 7 課的 COUNT、SUM 把一組列算成一個數字；array_agg 把一組列的值收集成一個陣列，同樣搭配 GROUP BY。陣列有順序，所以括號裡可以加 ORDER BY 決定元素的排列。訂單版本要先 JOIN products 才拿得到商品名稱，為了先單獨看清楚 array_agg 做了什麼，這裡先用不需要 JOIN 的 products 示範，執行後每個分類一列，names 是該分類的商品名稱，依 id 排列：

換成訂單也是同一個寫法：order_items JOIN products 取得商品名稱，再依 order_id 分組。原本一張訂單好幾列，收完就是一張訂單一列，練習 4 會寫這一句。

資料整理好了，API 最後要回傳 JSON。可以把列查回程式再組，也可以讓資料庫直接組好：jsonb_build_object('key', 值, 'key', 值, …) 依序接收 key 和值，把一般欄位組成一個 JSON 物件。它和前面的 -> 方向相反：-> 把 JSON 拆開，jsonb_build_object 把欄位組起來。執行後每一列都是一個 JSON 物件：

值也可以是陣列：把 tags 放進去，會變成 JSON 陣列，練習 5 會用到。

兩個工具合起來，就回到開場的訂單列表 API。一張訂單最後要長成 {"order_id": 3, "items": ["抹茶拿鐵", "南瓜派"]}：在依 order_id 分組的查詢裡寫 jsonb_build_object('order_id', order_id, 'items', array_agg(…))。array_agg 算出來的陣列本身就是一個值，所以可以直接當成 jsonb_build_object 的值放進去，查詢結果每一列就是一張訂單的 JSON，API 拿到後幾乎不用再加工。

💡 實務上：列表 API 用一次查詢整理好，不要在迴圈裡查
array_agg 常出現在列表 API：訂單列表要附上每張訂單的品項名稱時，一次查詢就能整理好，不必在程式裡對每張訂單再查一次。後者在開發時資料少看不出問題，上線後一頁的訂單一多，查詢次數跟著翻倍，列表就變慢。Code review 看到「迴圈裡呼叫資料庫」時，先想能不能用 JOIN 加 array_agg 改成一次查詢。

到這裡，存、讀、查、寫、回傳都做完了，App 也上線了。一個月後，問題從報表那一側冒出來。

上線一個月後，老闆要看甜度分布：什麼資料不該放進 JSONB？

老闆想知道大家都點幾分糖，好決定要不要調整預設甜度。這個需求看起來只是一句 GROUP BY：用 ->> 取出甜度，依甜度分組計數。只看咖啡類（product_id 1、2、3），執行後看各甜度的數量：

結果有兩個問題。第 12 號明細的 key 被拼成 Sugar（大寫 S），->> 'sugar' 找不到這個 key，回傳 NULL，於是它被算進 NULL 那一組；第 11 號明細的值寫成 half，自成一類，沒有算進「半糖」。這不是查詢寫錯，而是資料在寫入時就已經不一致：可能是舊版 App 送的，可能是有人手動補的，資料庫都照收了，因為它們都是合法的 JSON。

對照一般欄位：如果甜度是 sugar 欄位，加上 CHECK (sugar IN ('正常', '少糖', '半糖', '微糖', '無糖'))，half 在寫入那一刻就會被擋下；欄位名稱拼成 sugr 的 INSERT 也會直接報錯。大小寫不同的 Sugar 反而不會出事：SQL 的識別字沒加雙引號時會自動轉成小寫，本來就對得上同一個欄位；JSON 的 key 卻是區分大小寫的字串，Sugar 和 sugar 是兩個不同的 key，這正是 JSON 比一般欄位容易出錯的地方。JSON 裡的內容，資料庫不會幫你檢查。甜度一開始被當成附帶資訊放進 options，等它變成老闆每週要看的數字，它就成了核心業務資料，該搬出來了。

回到第一節的分工圖，現在可以把判斷原則講完整。符合下面任何一點，就應該是一般欄位（或一張獨立的表），不要放進 JSONB 或陣列：

  • 需要約束：必填、值的範圍、只能是幾種選項。這些是第 12 課的工作。
  • 需要外鍵：例如把 customer_id 放進 JSON，資料庫就擋不住不存在的顧客；陣列 product_ids integer[] 也不能加外鍵。這種多對多就該用第 10 課的中間表。
  • 經常查詢、篩選、加總、JOIN：例如每天都要統計甜度，那它就是一個重要的業務欄位。
  • 每一列都有、結構固定：那就是普通的欄位，沒有理由包進 JSON。

這和第 11 課的正規化是同一件事：JSONB 和陣列是「一格裡放多個值」的有意識的例外，適合附帶的、結構多變的、整包存取的資料，例如客製選項、第三方 API 的原始回應、使用者的介面偏好設定、簡單的標籤。資料一旦變成核心業務資料，就把它拆成欄位。

💡 實務上：設計審查時先問「之後會不會拿它來查」
新功能的資料表設計時，常有人提議「先放 JSONB，之後比較好改」。但「好改」只是寫入的人方便，讀的人要自己處理各種格式。資深工程師會用上面的清單逐項確認，再多問一句：前端以外還有誰要讀這份資料（報表、客服後台）？只要有人要拿它來查，就開成一般欄位。如果已經放在 JSON 裡、後來才變成要統計的業務資料（例如這一節老闆想看每週甜度分布），就寫一份 migration，也就是一支有版本紀錄、會在每個環境依序執行的改表腳本，第 22 課會教，用它把甜度拆成欄位並補上 CHECK，而不是在每個報表查詢裡各自處理拼錯的 key。

補充與查表

json 和 jsonb

這課一直用 jsonb，但 PostgreSQL 其實有兩種 JSON 型別。同一段文字分別轉成兩種型別，再用 ::text 看資料庫實際存的內容（結果表格會用 JSON.stringify 顯示 JSON 值，所以要轉成文字才看得到原貌）：

  • json：把原始文字原封不動存起來（空白、key 的順序、重複的 key 都保留），每次查詢都要重新解析。
  • jsonb：寫入時就解析成二進位格式，重複的 key 只留最後一個、key 會重新排序。寫入稍慢，但查詢快，而且支援 @> 和索引。

幾乎都用 jsonb。只有在需要保留原始文字（例如存下外部 API 的原始回應做稽核）時才用 json。

讓 @> 變快：GIN 索引

@> 可以搭配 GIN 索引，資料多的時候不用一列一列檢查。第 20 課先講一般的索引，GIN 在第 28 課。

這課的運算子與函式（查表用，不用背）

練習 1：找出冰塊選「少冰」的明細，欄位依序是 id、甜度（sugar 的值，文字），依 id 排列。

練習 2：用 @> 算出有幾筆明細加了濃縮（"extra_shot": true）。

練習 3：列出有「季節限定」標籤的商品 name，依商品 id 排列。

練習 4：每張訂單一列，列出訂單 id 和這張訂單買的商品名稱陣列（陣列裡依明細 id 排序），依訂單 id 排列。需要 JOIN products。

練習 5：用 jsonb_build_object 把茶類（category = 'tea'）的商品組成 {"name": 名稱, "tags": 標籤陣列}，只要這一欄，依商品 id 排列。

練習 6：下面哪一個最適合放進 jsonb 欄位？

✓ 介面偏好結構會變、資料庫不需要理解內容、整包存取。customer_id 需要外鍵；價格需要 NOT NULL、CHECK 和加總，都該是一般欄位。

練習 7：WHERE options -> 'ice' = '去冰' 和 WHERE options ->> 'ice' = '去冰'，哪一個是一般的正確寫法？

✓ -> 回傳 jsonb，右邊的 '去冰' 會被當成 JSON 來解析，而 去冰 不是合法的 JSON（要寫成 '"去冰"'），會出錯。和一般值比較時用 ->>；要比對 JSON 結構時用 @>。

常見錯誤

  • 用 -> 跟文字比較：-> 回傳 jsonb，右邊的文字會被當成 JSON 解析而出錯。和一般值比較時改用 ->>，要比對 JSON 結構時用 @>。
  • ->> 的結果直接當數字：->> 一定是文字，要加總或比大小時先 ::integer／::numeric，否則 '9' > '10' 會成立（文字比較）。
  • 用 @> 找布林值時寫成字串：'{"extra_shot": "true"}' 找不到存成 true 的資料，JSON 的布林值不加引號。
  • 陣列從 0 開始取：tags[0] 會得到 NULL，第一個元素是 tags[1]。
  • JSON 裡的 key 拼錯：資料庫不會報錯，查詢時默默變成 NULL。內容要在 API 寫入前驗證。
  • 什麼都往 JSONB 塞：「這樣就不用改 schema」聽起來很方便，代價是失去約束、外鍵和型別檢查，最後要在程式裡自己處理各種格式不一致的資料。

小結

  • 每列結構不同、整包存取的客製選項放進 jsonb 欄位；要外鍵、約束、加總的欄位留在一般欄位。
  • 取值：-> 取出 jsonb、可以繼續往下取，->> 取出文字；巢狀的值中間用 ->、最後一層用 ->>，當數字用要先轉型別。
  • 篩選：比較一個文字值用 ->> … =，比對「包含這些選項」用 @>，右邊照 JSON 的型別寫。
  • 寫入：資料庫只檢查是不是合法的 JSON，key 和值的內容要在 API 驗證。幾乎都用 jsonb 而不是 json。
  • 陣列 text[] 存一串同型別的值：值 = ANY (陣列) 查詢、索引從 1 開始；array_agg 把多列收成陣列，jsonb_build_object 把欄位組成 API 要的 JSON。
  • 需要約束、外鍵、經常查詢的資料，拆成一般欄位或獨立的表。JSONB 是正規化的有意識例外，不是取代 schema 設計的捷徑。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 8：註冊 API 先 SELECT 查這支手機有沒有人用，沒有才 INSERT，前端也擋了連點。上線後還是出現手機相同的兩位會員，最可能的原因是？

✓ 「先查再寫」中間有空檔，同時進來的請求都會通過檢查；前端擋得住連點，擋不住其他入口或直接呼叫 API。在 phone 加 UNIQUE，直接 INSERT，撞到 23505 再轉成「這支手機已經註冊過」回 409。a 錯在問題不是讀到舊資料，而是兩邊查的時候另一筆都還沒寫進去。（第 12 課）

練習 9：後台新增商品時沒填價格，API 把 null 照樣傳進 INSERT，等同下面最後一行。結果是？

CREATE TABLE products (
  name  text NOT NULL,
  price integer DEFAULT 0 CHECK (price >= 0)
);
INSERT INTO products (name, price) VALUES ('拿鐵', NULL);

✓ 明確寫了 NULL 就不會套用 DEFAULT；CHECK 的條件算出來是 NULL 不是 false，所以通過。這欄要加 NOT NULL，要用預設值時 INSERT 不寫這一欄，或寫 DEFAULT。a 錯在 DEFAULT 只在「沒寫到這一欄」時才填，傳 null 也算有寫。（第 12 課）

練習 10：集點規則是「每位會員每天只能集一次」，同事這樣建表。上線後會出什麼事？

CREATE TABLE stamps (
  member_id  integer NOT NULL UNIQUE,
  stamp_date date    NOT NULL UNIQUE
);

✓ 兩欄各自 UNIQUE 是兩條規則：每位會員一輩子只能集一次、每天只有一個人能集點。要限制的是「會員＋日期」的組合，寫成表約束 CONSTRAINT stamps_once_per_day UNIQUE (member_id, stamp_date)。b 把兩條欄位約束當成了一條組合約束，實際上任一欄重複就會被擋。（第 12 課）

練習 11：Node 後端用 pg 查 numeric(10,2) 的 price，拿到的是字串 '110.00'。同事提議把欄位改成 double precision，API 就能直接回 number。怎麼回應？

✓ 浮點數連 0.1 + 0.2 都算不準，金額存成浮點，加總、折扣、月底對帳都會差幾分錢。JS 的 number 就是浮點數，所以 pg 把 numeric 當字串回傳；前端顯示前也別 parseFloat 再相乘。a 錯在資料庫是對帳的依據，存成浮點，連 SUM 出來的營收都可能對不上。（第 13 課）

練習 12：orders.ordered_at 是 timestamp（無時區）。門市 POS 寫入 14:30+08，雲端點餐服務寫入同一瞬間的 06:30+00，報表上線上訂單都早了 8 小時。為什麼？

✓ timestamp 只記牆上時鐘的數字，+08、+00 寫入時直接丟掉，事後也分不出哪筆是哪個時區。事件時間用 timestamptz：存的是絕對時間點，讀出時依連線時區顯示。b 描述的換算是 timestamptz 的行為，而 timestamptz 讀出時會換回連線的時區。（第 13 課）

練習 13：甜度一直放在 order_items.options（jsonb），資料裡已經混進 Sugar、half 這種寫法。老闆現在要每週看甜度分布，該怎麼做？

✓ 要約束、要統計的資料是核心業務欄位，不該留在 JSONB；資料庫只檢查「是不是 JSON」，拼錯的 key 會一直進來。拆成欄位後，CHECK 從寫入就擋下 half。a 錯在每個報表都要各自補一次，出現新的拼法又要再改。（第 14 課）
