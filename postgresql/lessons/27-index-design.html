階段 8：資深必備｜查詢效能 · 第 27 課

索引設計進階：複合、部分、運算式與覆蓋索引

第 20 課學會了「哪一欄常被查，就幫它建索引」，第 26 課的期末專題也在上線前替外鍵補了索引。回到咖啡店 App：上線幾個月、訂單累積到 3 萬筆之後，回報進來的問題不再是「少了一個索引」這麼單純：同一張 orders 表，有的畫面要篩兩個條件再依時間排序，有的畫面只看 1% 的資料，有的列表往下捲會看到重複的訂單。每一條查詢的「形狀」不一樣，適合的索引也不一樣，照第 20 課「哪欄常查就建哪欄」的做法，有時建了也沒用。

這一課你接手一張工單清單：App 上線後回報的幾個效能與資料問題，都落在 orders、customers、payments 這三張表上。我們一張一張處理，每一張都先用 EXPLAIN ANALYZE 看清楚慢在哪裡，再設計剛好能解決它的索引，最後用 EXPLAIN ANALYZE 證明它真的有效，不靠感覺。處理完之後，你會有一套設計索引的方法：先拆解查詢，再決定欄位順序、索引要收哪些列、要存什麼值、要不要附帶欄位，以及哪些索引其實不該存在。

這課的路線（也是這課的工單）：
  1. 工單 1「我的訂單」很慢：複合索引的欄位該怎麼排。
  2. 工單 2 訂單列表往下捲會看到重複的訂單：OFFSET 為什麼會錯位，keyset 分頁怎麼修。
  3. 工單 3、4 咖啡師的「待製作」畫面、手機號碼不能重複但刪除帳號的不算：只索引需要的那部分列（部分索引）。
  4. 工單 5 email 大小寫不同就能重複註冊：讓索引存運算後的值（運算式索引）。
  5. 工單 6、7 報表要加總、收款表寫入越來越慢：讓查詢只讀索引（覆蓋索引），再算索引的成本，刪掉不該留的。
這課會用到：
  • 第 20 課的 B-tree 與複合索引：B-tree 是一棵排好序的樹；複合索引 (a, b) 對「a」或「a 加 b」的條件有效，只查 b 時幫助很小（最左前綴）。UNIQUE 索引擋下重複的值。
  • 第 21 課的 EXPLAIN ANALYZE：實際執行查詢，印出計畫和每一步做了多少事；計畫由縮排最深的那一層先做。Index Scan 在索引裡找到位置，再回表（回到表裡）拿整列資料。
  • 第 18 課的 BEGIN … ROLLBACK：交易裡做的修改，ROLLBACK 後全部取消。
這頁的環境：範例直接改這頁的資料庫（PGlite），不會自動回滾；VACUUM 必須單獨一格執行。這頁的字串排序規則（collation）是 C，跟正式環境常見的設定不同，影響見課末「補充與查表」。

這頁的資料：customers 5,000 位；orders 30,000 筆，每 13 分鐘一筆，5 間分店（store_id 1～5），狀態 paid 約 90%、cancelled 約 9%、pending（待製作）約 1%。顧客 42 是常客，大約每 10 筆就有 1 筆是他的（約 3,000 筆）。orders 上除了主鍵沒有任何索引。payments 是收款紀錄，每筆已付款訂單一筆，約 2 萬 7 千筆，連主鍵共有 5 個索引（工單 7 才用到）。

每一層的結果裡都有 Buffers，它是這一步讀了幾個資料頁。資料頁是 PostgreSQL 在磁碟和記憶體之間搬資料的單位，讀的頁越多，做的事越多。毫秒數會受電腦當下忙不忙影響，同一句跑兩次就不一樣；Buffers 只跟做了多少事有關，所以這課都拿它比較索引的效果（PostgreSQL 18 的 EXPLAIN ANALYZE 會自動印出它，細節見課末「補充與查表」）。

接下來要替這句查詢試好幾種索引，每次都要重看計畫，還要換不同的顧客比較。為了不用每次重打整句，seed 準備了小工具 my_orders_plan(顧客 id)：它就是上面那句 EXPLAIN ANALYZE，只是顧客 id 換成參數。

先拆解查詢：四個問題

索引怎麼建，取決於查詢怎麼使用這些欄位。設計之前，先把查詢拆成四個問題：

問題「我的訂單」查詢的答案
哪些欄位用 = 比對？（等號欄位，equality column）customer_id、status
哪些欄位用 <、>、BETWEEN 比對？（範圍欄位，range column）沒有
依什麼排序？ordered_at DESC，而且只要前 5 筆
要回傳哪些欄位？id、ordered_at、total

為什麼要這樣拆？因為 B-tree 索引是一份排好序的清單，而複合索引的排法跟電話簿一樣：先依第一欄排，第一欄相同的再依第二欄排，以此類推。這帶來一個關鍵性質：前面的欄位都固定成一個值之後，後面那一欄在這一段裡就是排好序的。電話簿裡「姓王的」是連續的一段，這一段裡的名字又是排好的；但如果只知道名字、不知道姓，就得翻遍整本。

把這個性質套到四個問題上：等號欄位能把要讀的範圍縮成連續的一段，所以放前面；縮完之後，下一欄在這一段裡已經排好，正好拿來做範圍比對或排序。反過來，如果範圍欄位或排序欄位放在前面，等號欄位的值就散落在整個索引裡，沒辦法一次跳到。規則是：等號欄位放前面，範圍欄位或排序欄位放後面。

「我的訂單」還有一個特點：它只要排在最前面的 5 筆。ORDER BY … LIMIT N 這種「只要排在最前面 N 筆」的查詢叫 Top-N 查詢（top-N query）。如果索引的順序正好就是 ORDER BY 要的順序，資料庫從正確的位置開始讀，讀到 N 筆就能停，不用排序，也不用看後面的資料。這就是工單 1 的目標：計畫裡沒有 Sort，Buffers 降到個位數。

三種常見但錯誤的索引

接下來會試好幾種索引。如果每試一種就留下一個，下一次測試時規劃器可能挑到前一次留下的那個，結果就看不準。所以範例都包在 BEGIN; … ROLLBACK; 裡：交易裡建的索引，在同一個交易裡就能用，ROLLBACK 後索引跟著消失，表回到沒有索引的狀態。正式環境也可以這樣在交易裡試索引，但 CREATE INDEX 會擋住這張表的寫入直到交易結束，這段時間下單會卡住；不擋寫入的做法是第 34 課的主題。

先看三種常見但錯誤的索引，看懂它們各缺什麼，正確的索引就自然出來了。第一種，只幫等號欄位 customer_id 建索引。執行後看 Sort 和它下面的兩層：

由上往下（執行順序相反，從縮排最深的那層做起）：

  • Sort：把剩下的 2,700 多筆排序，最後只留 5 筆。
  • Bitmap Heap Scan：把這些位置一筆筆回表讀出來（Heap Blocks 約 250 頁），Rows Removed by Filter 丟掉不是 paid 的。
  • Bitmap Index Scan：在索引裡找到顧客 42 的 3,005 筆。

索引確實幫上了忙：不用再讀整張表，只讀顧客 42 的那幾百頁。但它只解決了「找到」，沒有解決「排序」。(customer_id) 索引只依顧客排，同一位顧客的訂單在裡面不是依時間排的，所以還是要把 2,700 多筆全部取出來排序，才知道哪 5 筆最新。常客的訂單越多，這一步越慢，而常客正是最常打開「我的訂單」的人。

既然缺的是排序，第二種想法是把時間放進索引，而且放在最前面：(ordered_at, customer_id)。這格跑兩次：上面是常客 42，下面是總共只有 7 筆訂單的顧客 7。執行後比較兩張結果的 Buffers：

兩張的計畫都是 Index Scan Backward：從最新的時間往回讀索引，邊讀邊檢查是不是這位顧客。由上往下：

  • Index Cond（在索引裡比對的條件）雖然出現 customer_id = 42，但第一欄 ordered_at 沒有條件，這個條件只能在索引裡一筆一筆比對，沒辦法直接跳到顧客 42。
  • Index Searches: 1：只跳進索引一次，從頭讀到湊滿 5 筆為止。
  • Buffers：顧客 42 每 10 筆就有 1 筆，很快湊滿 5 筆，只有 6 頁左右；顧客 7 要往回讀 70 多頁才湊滿 5 筆，是常客的十幾倍。

這個索引依時間排好了，所以 Sort 不見了；但等號欄位落到第二欄，沒辦法用它縮小範圍，只能從最新的訂單一路往回讀、邊讀邊挑。顧客的訂單越舊越稀，讀得越多，快不快全看這位顧客的資料分布。這種索引最危險的地方是：拿常客測會覺得很快，上線後遇到訂單少的顧客才慢。

第三種想法是把兩個等號欄位都放進去：(customer_id, status)。這次能直接定位到「顧客 42 的已付款訂單」，不必再丟掉 cancelled 的列，但同一段裡的訂單一樣沒有依時間排好，Sort 還在。你可以把上面第一格的索引改成這個試試。

還有人會建兩個單欄索引 (customer_id) 和 (status)，讓規劃器自己組合。規劃器確實可以把兩個索引找到的位置取交集（計畫裡叫 Bitmap AND），但交集出來的是一堆資料位置，沒有任何順序，還是要回表、還是要 Sort。兩個單欄索引不等於一個複合索引。

💡 實務上：列表頁的篩選器越多，越要挑重點建索引
咖啡店後台的訂單列表常有一排篩選器：分店、狀態、日期、付款方式，再加上可點的排序欄。組合有幾十種，不可能每種都建一個複合索引。實務上會先看哪幾種組合最常被用、哪幾種最慢（例如「某分店＋今天＋待製作，依時間排序」），為它們設計一兩個索引，讓其他組合共用開頭幾欄。資深工程師在加篩選器之前會先問 PM：「這個條件真的常用嗎？可以設預設值或限制日期範圍嗎？」很少人用的組合，慢一點通常可以接受。

工單 1 的「我的訂單」只顯示第一頁的 5 筆。工單 2 是另一種列表：後台的訂單列表可以一直往下翻，翻到後面不只變慢，還會看到重複的訂單。這跟索引的欄位順序無關，問題出在翻頁的寫法。

工單 2：訂單列表往下翻會重複，OFFSET 錯在哪？

後台的訂單列表依時間由新到舊排，每頁 20 筆，用的是第 5 課的 LIMIT 20 OFFSET 40 這種寫法：要第 3 頁，就跳過前 40 筆。這個寫法有兩個問題。

第一個是越後面越慢。OFFSET 是「跳過」，但資料庫沒辦法憑空知道第 20,001 筆在哪裡，只能把前 20,000 筆依序讀出來、數過、丟掉，再回傳接下來的 20 筆。頁數越後面，丟掉的越多，有索引也一樣。

第二個就是工單回報的現象：翻頁期間有新資料進來，頁面會錯位。OFFSET 記的是「跳過幾筆」，而「第幾筆」是每次查詢當下重新算的。使用者看第 1 頁時排在第 18 名的訂單，等他按下一頁時，可能已經被新訂單擠到第 21 名。按「下一步」看一次：

2新訂單 29998、29999、30000 寫入
3LIMIT 20 OFFSET 20第 2 頁開頭：29978、29977、29996 …
4結果重複了 3 筆

keyset 分頁：記住最後一筆，而不是跳過幾筆

修法是改記一個不會變的東西：上一頁的最後一筆本身。keyset 分頁（keyset pagination，也叫游標分頁 cursor pagination）的想法是：不記「跳過幾筆」，而是記「上一頁最後一筆的排序值」，下一頁從排序上緊接在它後面的那一筆開始拿。不管前面插進了多少新訂單，「比這一筆更舊的訂單」都是同一批，所以不會重複，也不會漏。前端常見的「無限捲動」API 回傳的 nextCursor，存的就是這個值。寫成 SQL：

WHERE (ordered_at, id) < (上一頁最後一筆的 ordered_at, 上一頁最後一筆的 id)
ORDER BY ordered_at DESC, id DESC
LIMIT 20

WHERE 裡的 (ordered_at, id) < (…, …) 叫列值比較（row value comparison）：先比 ordered_at，時間不同就由時間決定大小；時間相同，再比 id。跟字典排序一樣，先比第一個字，相同才比第二個字。

為什麼不只用時間，寫成 WHERE ordered_at < 上一頁最後一筆的時間 就好？因為兩筆訂單可能在同一個時間成立。這頁的資料就有：第 1 頁的最後一筆是 id 29996，訂單 29976 跟它同一個時間，排在第 2 頁的開頭。只比時間的話，< 會把 29976 一起排除，它就被跳過了；改成 <= 又會把 29996 再拿一次。加上 id 之後，每一筆在排序裡都有唯一的位置，起點就不會模糊。這個用來打破平手、本身不會重複的欄位叫同分決勝欄位（tie-breaker），通常就是主鍵。ORDER BY 也要同樣寫成 ordered_at DESC, id DESC，排序和起點的定義才一致。

keyset 分頁要快，還需要一個順序完全相同的索引 (ordered_at DESC, id DESC)：資料庫在索引裡直接跳到起點，往後讀 20 筆就停，跟工單 1 的 Top-N 查詢是同一個道理。這格跑兩次：上面是 keyset，下面是 OFFSET 的第 1001 頁。執行後比較兩個計畫讀了多少：

  • keyset 那句：Index Only Scan，Index Cond 直接用列值比較定位，讀 3 個資料頁。
  • OFFSET 那句：實際讀了 20,020 列（rows=20020）才丟掉前 20,000 筆。

keyset 讀的量跟第幾頁無關，永遠是「跳到起點、讀 20 筆」；OFFSET 讀的量跟頁數成正比。索引的方向要和 ORDER BY 一致：兩欄都 DESC，或兩欄都 ASC（倒著讀也行）。

keyset 也有代價：它只知道「接在某一筆後面」，不能直接跳到「第 37 頁」，只能一頁接一頁。所以它適合無限捲動、「載入更多」、匯出全部資料、背景批次處理；需要頁碼的後台表格，資料量不大時用 OFFSET 仍然可以。

💡 實務上：cursor 是 API 合約的一部分
做「載入更多」的 API 時，常見做法是把最後一筆的 ordered_at 和 id 編碼成一個字串回傳成 nextCursor，前端只負責原封不動帶回來，不去解析它。這樣後端以後改排序欄位，前端不用跟著改。要注意排序欄位最好不會被修改：如果依「最後更新時間」排序，使用者捲動期間有訂單被更新，它就會跳到別的位置。後端也要驗證收到的 cursor 格式，被亂改時回 400，而不是丟出 500。

到這裡，每個索引收的都是整張表的每一列。工單 3 的查詢卻只關心 1% 的訂單：為另外 99% 也建索引，划算嗎？

工單 3：「待製作」只佔 1%，能不能只索引這 1%？

咖啡師的平板上有一個「待製作」畫面，依下單時間列出還沒做的訂單：WHERE status = 'pending' ORDER BY ordered_at LIMIT 20。照工單 1 的規則，等號欄位在前、排序欄位在後，(status, ordered_at) 就能讓它不用 Sort。可是這個索引收了全部 3 萬筆，其中 99% 是 paid 和 cancelled，「待製作」畫面永遠不會查它們。這 99% 的索引項目不只佔空間，每寫入一筆已付款訂單，也都要在這個索引裡插一筆。

部分索引（partial index）就是為這種情況設計的：在 CREATE INDEX 後面加一個 WHERE，只有符合條件的列才會進索引。ON orders (ordered_at) WHERE status = 'pending' 只收待製作的訂單、依時間排好；條件已經寫在索引的定義裡，索引本身就不用再存 status。下面建一個部分索引和一個一般索引，執行後比較三個索引的大小：

status 用參數傳進來時，部分索引還用得上嗎？

上面的查詢把 'pending' 直接寫在 SQL 裡。實際的後端程式通常不這樣寫：ORM 和第 25 課的 pg 套件會送出 WHERE status = $1，值另外傳。而「推不推得出」是在規劃時判斷的，這裡就有一個陷阱。

先認識一個名詞。prepared statement 是預先解析好、之後只換參數重複執行的 SQL：SQL 的 PREPARE、驅動程式的具名查詢、PL/pgSQL 函式裡的查詢都是。同一句 SQL 重複執行時，PostgreSQL 可以重用之前的成果，不必每次從頭來。

計畫怎麼重用，有兩種做法。一種是每次都依這次傳進來的實際值重新規劃，叫 custom plan；另一種是規劃一份不看參數值、所有參數共用的計畫，叫 generic plan（第 29 課詳談）。PostgreSQL 18 文件寫的規則是：預設前 5 次依實際的值規劃，之後如果 generic plan 估計的成本差不多，就改用它。

generic plan 要對任何參數值都正確，它不知道 $1 是不是 'pending'，所以不能用只收 pending 的部分索引。下面同一個 prepared statement 跑兩次：上面強制用 generic plan，下面是預設。執行後比較兩個計畫有沒有用索引：

generic plan 是 Seq Scan 加 Sort；看得到值的計畫才用上索引。照上面的規則，同一個 prepared statement 前幾次都很快，換成 generic plan 之後才可能變慢，所以這種問題在測試時不容易發現。對策：部分索引的條件在 SQL 裡寫成常數（WHERE status = 'pending'），不要當參數傳。「待製作」畫面本來就只查 pending，寫死不會少任何彈性。

工單 4：手機不能重複，但刪除帳號的不算

部分索引除了讓查詢變快，還能表達「只對一部分列成立」的規則。工單 4 是會員系統的新規則：手機號碼不能重複，但已經刪除帳號的會員，手機號碼要能讓新會員使用。

難處在第 6 課的軟刪除：刪除帳號時不真的 DELETE，而是在 deleted_at 記下刪除時間，資料還留在表裡。一般的 UNIQUE 約束對整張表的每一列成立，已刪除會員的手機號碼會一直佔著那個值，新會員就寫不進去。我們要的規則是「沒被刪除的會員，手機不能重複」。部分唯一索引正好表達這件事：CREATE UNIQUE INDEX … ON customers (phone) WHERE deleted_at IS NULL，只有還沒刪除的列進索引，唯一性也只在它們之間檢查。

工單 5：email 大小寫不同就能重複註冊，索引能不能存運算後的值？

會員的 email 是自己輸入的，同一個信箱可能寫成 User42@Example.com，也可能寫成 user42@example.com。使用者認為這是同一個信箱，但對 UNIQUE 索引來說是兩個不同的字串，所以同一個人可以註冊兩次。登入也一樣：用 email = 輸入值 比對，大小寫打得不一樣就找不到人。

直覺的修法是在查詢裡兩邊都轉小寫：WHERE lower(email) = lower($1)。結果對了，但一般的 (email) 索引用不上：索引裡存的是原本的 email，也是依原本的字串排序，資料庫沒辦法在裡面找「轉小寫之後等於某個值」的列，只能整張表每一列算一次 lower 再比。

運算式索引（expression index）就是為這種情況設計的：索引裡存的不是欄位原本的值，而是運算結果。CREATE INDEX ON customers (lower(email)) 在寫入時就把每一列的 lower(email) 算好、排好存起來，查詢 WHERE lower(email) = … 就能直接在索引裡找。第 21 課的練習已經建過這個索引。

運算式索引也可以是唯一索引：CREATE UNIQUE INDEX 加上運算式，唯一性就以運算結果為準，User42@Example.com 和 USER42@EXAMPLE.COM 轉小寫後相同，第二筆就寫不進去。一個索引同時解決工單 5 的兩件事：擋下重複、加速登入（練習 4）。

用運算式索引有一個前提：查詢要寫成同一個運算式才用得上。索引是 lower(email)，查詢寫 email ILIKE 'user42@example.com' 或 upper(email) = …，意思接近，但不是同一個運算式，都用不上。團隊要約定一種寫法，最好包在後端的同一個函式裡，讓所有用 email 找會員的地方都經過它。email 的前綴搜尋（LIKE 'abc%'）在正式環境還有排序規則的問題，見課末。

為什麼「依日期查訂單」的運算式索引建不起來？

運算式索引還有第二個限制，和 email 無關，但很常踩到。索引運算式只能用 IMMUTABLE 函式：相同輸入永遠得到相同結果，不受任何設定影響。原因是索引裡的值是寫入時算好的；如果同一個輸入今天算出 A、換個設定算出 B，索引裡存的 A 就和查詢時算出的 B 對不上了。

最常踩到的情境是報表要依日期查訂單，於是想把 ordered_at 轉成日期建索引。ordered_at 是第 13 課的 timestamptz：它記錄一個絕對的時間點，讀出時才依連線設定的時區顯示。執行後看錯誤碼：

不過，只是要查某一天的訂單，其實不需要運算式索引：第 20 課教過的範圍寫法 ordered_at >= '2026-10-01 00:00+08' AND ordered_at < '2026-10-02 00:00+08' 用一般索引就夠，也不用約定運算式的寫法。運算式索引留給沒辦法改寫成範圍的情況，例如 lower(email)。

到這裡的索引都只負責「找到」列，找到之後，查詢要的其他欄位還得回表去讀。工單 6 的報表一次要讀幾千列，回表成了主要的成本：能不能讓查詢只讀索引就好？

工單 6：報表要加總，能不能只讀索引、不回表？

後台有一張報表：列出一批顧客各自的消費總額。查詢只用到 customer_id 和 total 兩欄。如果只有 (customer_id) 索引，資料庫在索引裡找到每一筆訂單的位置後，還要逐筆回表讀 total；符合的訂單有幾千筆，就要回表幾千次。

第 21 課提過 Index Only Scan：查詢要的欄位都在索引裡，就不用回表。覆蓋索引（covering index）就是刻意讓索引「蓋住」查詢需要的每一個欄位，讓它走 Index Only Scan。

做法要回到 B-tree 的結構：第 1 張工單看過，葉節點是最底層一筆一筆存放索引項目的那一層。customer_id 要用來搜尋，放在索引的欄位裡；total 不用來搜尋、只要回傳，用 INCLUDE 附在葉節點上。這格的索引不在交易裡，建好會留著，後面幾格接著用。執行後看掃描方式和 Heap Fetches：

Index Only Scan、Heap Fetches: 0：完全沒碰表。

INCLUDE 和直接寫 (customer_id, total) 的差別：INCLUDE 的欄位只存在葉節點、不參與排序，所以不能當搜尋條件（WHERE total > 400 用不上它），也不影響 UNIQUE 的判斷，例如 UNIQUE (email) INCLUDE (name) 仍然只保證 email 不重複。

Index Only Scan 為什麼還會回表？

「Index Only」這個名字容易讓人以為保證不讀表，其實不是。PostgreSQL 的索引不記錄「這一列對哪些交易可見」：一列被更新或刪除後，有些交易還該看到舊的樣子，有些不該，這個資訊只存在表裡（第 30 課的 MVCC 會講原因）。所以光看索引，不知道這一列對目前的交易算不算存在。

為了不必每一筆都回表確認，PostgreSQL 維護一份可見性地圖（visibility map）：每個資料頁一個標記，表示「這一頁裡的資料對所有交易都可見」，由 VACUUM 設定。Index Only Scan 讀到一筆索引項目時，先看它所在的資料頁有沒有這個標記：有，就直接相信索引；沒有，就回表確認。回表的次數就是 Heap Fetches。這頁的 seed 最後跑過 VACUUM，所以剛才是 0。

工單 7：寫入越來越慢，索引的成本是什麼、哪些該刪？

每個索引都是一份額外的、要跟表保持同步的資料。讀的時候它替你省事，寫的時候就換你付出代價：

  • 寫入變慢：每次 INSERT，每個索引都要插一筆；UPDATE 改到索引欄位時也要。
  • 佔空間：索引常常比表還大，也和表搶記憶體快取。
  • 讓 HOT 更新失效：沒改到任何索引欄位的 UPDATE 可以不必動索引，叫 HOT 更新（Heap-Only Tuple）。如果幫一個常被更新的欄位（例如 status）建了索引，這些更新就都不能走 HOT 了。第 30 課詳談。

payments 是收款紀錄，每筆已付款訂單一筆，上線以來不同的人為了不同需求各加了索引，連主鍵一共 5 個。用它把成本算出來：同樣的 2 萬多筆收款，寫進沒有索引的表和有 5 個索引的表。執行後比較兩個 Execution Time，和最後一張結果的總大小：

有索引的那張，寫入時間大約是好幾倍，總大小也將近 3 倍。所以看到慢查詢，第一個念頭不該是「再加一個索引」，而是「能不能調整現有的索引來涵蓋它」；已經存在的索引，也要定期檢查還值不值得留。

怎麼找出可以刪的索引？

要判斷一個索引值不值得留，先要知道它有沒有被用到。PostgreSQL 會自動累計各種使用次數，放在 pg_stat_* 統計視圖裡。pg_stat_user_indexes.idx_scan 是每個索引被用來掃描過幾次，從上次重設統計以來一直累加。這頁的 seed 模擬了 payments 上線以來的使用情況：一開始只有 (order_id) 索引，查詢都用它；後來為了查某筆訂單最近一次付款，有人加了 (order_id, paid_at DESC)。執行後看每個索引的 idx_scan、is_unique 和定義：

兩種索引可以考慮刪：

  • 被涵蓋的索引：A 的欄位正好是 B 的開頭幾欄（例如 (order_id) 和 (order_id, paid_at DESC)）。B 是先依 order_id 排的，所以能用 A 的查詢都能用 B。A 就算 idx_scan 不是 0 也可以刪，用過它的查詢 B 都能接手。反過來不行，B 能做的 A 做不到。
  • 從沒被用過的索引：idx_scan = 0，每次寫入都在付它的成本，卻沒有任何查詢受益。
刪之前先確認三件事：① 唯一索引和主鍵在保護資料正確性，idx_scan = 0 也不能刪（它每次 INSERT 都在檢查重複，只是不算「掃描」）。② 統計可能剛被重設過（看 pg_stat_database.stats_reset），也可能沒涵蓋月底報表這種低頻但重要的查詢。③ 統計只記錄在這一台：分擔讀取的唯讀副本 replica（第 37 課）上的查詢，不會算進主資料庫的 idx_scan。
💡 實務上：每個新索引都要說得出是為哪一條查詢
在 code review 看到 migration 新增索引時，資深工程師會問：這是為了哪一條查詢（最好附上 EXPLAIN ANALYZE）？現有的索引調整一下能不能涵蓋？這張表寫入頻繁嗎？刪索引則反過來，要在 PR 說明上面那三項都確認過了。另外，直接在正式環境的大表上 CREATE INDEX 會擋住寫入，安全的做法第 34 課會講。

補充與查表

  • Buffers 自動出現：PostgreSQL 18 的 EXPLAIN ANALYZE 會自動附上 Buffers（讀了幾個資料頁），不必再寫 BUFFERS 選項；工單 7 的範例用 BUFFERS OFF 把它關掉，只看時間。
  • LIKE 前綴搜尋與 collation：這頁的 PGlite 用 C collation，所以 email LIKE 'User42%' 能直接用一般 B-tree 索引。正式環境的資料庫常用 en_US.UTF-8 之類的 collation，這時一般索引幫不了 LIKE 'abc%'，要建 CREATE INDEX ON customers (email text_pattern_ops) 或指定 COLLATE "C" 的索引。上線前在真正的資料庫用 EXPLAIN 確認。

第一欄沒有條件時：PostgreSQL 18 的 skip scan

工單 1 的查詢都對第一欄有等號條件。第一欄沒有條件時呢？第 20 課說過：複合索引 (status, ordered_at) 只查 ordered_at 時幫助很小，因為違反最左前綴；那一課也提到 PostgreSQL 18 新增的 skip scan，這裡實際看一次。skip scan 是在第一欄沒有條件時，對第一欄的每個值各跳進索引找一次，等於自動改寫成「store_id = 1 AND ordered_at >= …、store_id = 2 AND ………」。執行後看 Index Searches（跳進索引找了幾次）：

Index Searches 不是 1，而是 6：5 間分店各一次，再加上一次找「下一間分店」、發現已經沒有了（換成只有 3 種值的欄位會是 4 次）。

這只在第一欄的種類很少（這裡只有 5 間店）時划算；如果第一欄是 customer_id（5,000 種），跳 5,000 次還不如全表掃描。所以 skip scan 是補救，設計索引時仍然以最左前綴為準。

練習

練習 1、3、4、5 在另開的全新資料庫裡判分，上面範例建的索引不會影響結果；第一次按「檢查答案」要等幾秒建資料庫。

練習 2：訂單列表依 ordered_at DESC, id DESC 排序、每頁 20 筆。第 1 頁的最後一筆是 ordered_at = '2026-10-29 22:48+08'、id = 29996。之後進來了 3 筆新訂單，店員也補登了一筆時間較早的紙本訂單（id 比較大）。不用 OFFSET，寫出第 2 頁的查詢，回傳 id, ordered_at。注意：有另一筆訂單和第 1 頁最後一筆同一個時間。

練習 3：咖啡師的「待製作」畫面：SELECT id, ordered_at FROM orders WHERE status = 'pending' ORDER BY ordered_at LIMIT 20。建一個部分索引，讓計畫沒有 Sort，而且 orders 上主鍵以外的索引都小於 64 kB。不能刪改資料。

練習 4：會員用 email 登入，不分大小寫。建一個索引同時做到：① 只差大小寫的重複 email（例如已有 User42@Example.com，再寫入 USER42@EXAMPLE.COM）寫不進去；② 登入查詢 WHERE lower(email) = lower($1) 用得上索引。判分會嘗試寫入這兩種 email，並檢查 WHERE lower(email) = 'user42@example.com' 的計畫。

練習 5：payments 上有 5 個索引，seed 也跑過一段工作量。先執行起始內容看每個索引的定義和 idx_scan，再用 DROP INDEX 刪掉「被另一個索引完全涵蓋」的索引，和「從沒被用過、也不是用來保證唯一」的索引，其他保留。判分會檢查剩下哪些索引和它們的定義。

練習 6：查詢是 WHERE store_id = $1 AND ordered_at >= $2 ORDER BY ordered_at，哪個索引最適合？

✓ 等號欄位 store_id 在前，固定之後 ordered_at 在這一段裡是排好的，範圍條件和排序都直接用上。(ordered_at, store_id) 要掃過所有分店在這段時間的資料再過濾。兩個單欄索引合併（Bitmap AND）得到的是沒有順序的位置，還要 Sort。

練習 7：ORM 送出 prepared statement WHERE status = $1，參數是 'pending'，表上有部分索引 … WHERE status = 'pending'。這個索引一定會被用到嗎？

✓ 部分索引能不能用，是在規劃時判斷的。依實際值規劃（custom plan）時用得上；generic plan 要適用所有參數值，所以用不上。一般索引不受影響。要穩定用上部分索引，條件寫成 SQL 裡的常數。

練習 8：計畫顯示 Index Only Scan using orders_customer_total_idx，下面卻是 Heap Fetches: 18000。最可能的原因？

✓ 欄位不夠的話根本不會選 Index Only Scan。它只能跳過「已被 VACUUM 標記為全部可見」的資料頁，其他頁要回表確認可見性，次數就是 Heap Fetches。VACUUM（或 autovacuum 跟上）之後會降下來。

常見錯誤

  • 把範圍或排序欄位放在等號欄位前面：(ordered_at, customer_id) 對「某位顧客最近的訂單」幾乎沒幫助，訂單少的顧客要讀完整個索引。等號欄位在前。
  • keyset 分頁只用時間、沒有 id 決勝：同一時間的訂單會被跳過或重複。用 (ordered_at, id) < (…, …)，ORDER BY 和索引都加上 id。
  • 查詢的寫法和索引運算式不一致：索引是 lower(email)，查詢卻寫 email ILIKE …，索引用不上。
  • 索引運算式用了不是 IMMUTABLE 的東西：timestamptz::date、now() 會得到 42P17。把時區寫死（AT TIME ZONE 'Asia/Taipei'），或改用範圍條件。
  • 部分索引的條件用參數傳：generic plan 用不上部分索引。條件寫成常數。
  • 看到慢查詢就加新索引：每個索引都拖慢寫入、佔空間、讓 HOT 更新失效。先看能不能調整既有的索引。
  • 只看 idx_scan = 0 就刪：唯一索引與主鍵在保護資料；統計可能剛重設；replica 上的查詢不算在主資料庫。
  • 以為有 skip scan 就不用在意欄位順序：只有第一欄種類很少時才划算。

小結

  • 設計索引先拆解查詢：等號欄位、範圍欄位、排序、回傳欄位。複合索引像電話簿，前面的欄位固定後，後面那欄在這一段裡已經排好，所以等號欄位在前，範圍或排序欄位在後；用 EXPLAIN ANALYZE 確認 Sort 消失、Buffers 變少，並用「最常見、最慢」的參數測（工單 1）。
  • OFFSET 用位置記錄讀到哪裡，越後面越慢，資料變動時會重複或漏掉。keyset 分頁改記上一頁最後一筆：WHERE (ordered_at, id) < (…) 配 (ordered_at DESC, id DESC) 索引，id 負責同分決勝；代價是不能跳頁（工單 2）。
  • 部分索引只收需要的列，又小又不拖慢其他寫入；查詢要推得出索引條件，條件用參數傳時 generic plan 用不上它，所以寫成常數。部分唯一索引可以表達「未刪除的才不能重複」（工單 3、4）。
  • 運算式索引存運算結果，查詢要寫成同一個運算式；只能用 IMMUTABLE 函式，timestamptz::date 要先把時區寫死，能改寫成範圍條件就不必建（工單 5）。
  • INCLUDE 做覆蓋索引，讓 Index Only Scan 不必回表；Heap Fetches 高代表可見性地圖還沒被 VACUUM 設好（工單 6）。
  • 索引有寫入、空間、HOT 的成本；用 pg_stat_user_indexes 和欄位前綴找出可刪的索引，但保留唯一索引（工單 7）。第一欄沒有條件時，PostgreSQL 18 的 skip scan 只在第一欄種類少時能補救（見補充）。
