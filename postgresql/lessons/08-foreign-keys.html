階段 2：表與表之間的關係 · 第 8 課

一對多與外鍵

到目前為止，你都只在一張表裡操作。真實的系統一定有好幾張表，而且彼此有關係：一位顧客會下很多張訂單。第 1 課留下一個問題：訂單為什麼只存 customer_id，不直接存顧客名字？

這一課的任務是替咖啡店後台把「顧客」和「訂單」的關係設計好，並且讓它在三種狀況下都不出錯：王小明換了手機、後端程式寫錯了顧客編號、有人要刪除顧客或店員。學完你會知道編號該放在哪張表，也會用外鍵（foreign key）讓資料庫替你守住這層關係，並決定「被刪掉時要怎麼辦」。

這課會用到：
  • 第 2 課的主鍵：每一列都有一個不重複的編號（這裡是自動產生的 id），用來指定「就是這一列」。
  • 第 6 課的 DELETE … WHERE 與 RETURNING：刪除符合條件的列，並把刪掉的列回傳出來。
這課的路線：
  1. 王小明換手機：把名字電話抄進每張訂單會出什麼事，所以訂單只存 customer_id（開場問題的答案）。
  2. 編號該放哪一張表：一對多的關係怎麼判斷，以及哪些值反而要直接存在訂單裡。
  3. 程式寫錯編號：外鍵怎麼讓資料庫擋下「沒有主人」的訂單，錯誤怎麼回給前端。
  4. 刪除被參照的顧客：資料庫預設為什麼擋下來。
  5. ON DELETE：顧客的地址、店員的訂單，被刪時各該擋下、跟著刪，還是斷開關係。

王小明換手機了：訂單裡抄著他的電話會怎樣？

先看最直覺的設計。如果沒學過資料庫，很多人會讓訂單表長這樣，每一筆都寫上顧客的名字和電話，跟手寫的訂單紙一樣：

idcustomer_namecustomer_phonetotal
1王小明0912-345-678190
2王小明0912-345-67880
3陳美華0922-111-222230
4王小明0912-345-678110

店剛開時這張表看起來沒問題，查訂單時名字電話都在眼前。問題出在時間一長、資料一多：

  • 資料重複：王小明下了 300 張訂單，他的名字和電話就被抄了 300 次。同一件事記了 300 份。
  • 改一個人要改很多處：王小明換手機，你得把 300 列全部改掉。只要漏改一列，資料庫裡就同時存在兩支「王小明的電話」，你不知道哪支才對。客服打錯電話、簡訊發到舊號碼，都是從這裡開始的。
  • 同名的人分不開：如果有兩位王小明，光看名字無法分辨訂單是誰的。名字不是唯一的，不能拿來當「這是哪一個人」的依據。

三個問題的根源相同：「王小明是誰、電話幾號」這件事被記在很多地方。解法是讓它只記一次：顧客資料只存一份，放在 customers 表；訂單不抄名字電話，只記「是哪一位顧客」，記法是寫下那位顧客的主鍵 id，欄位取名 customer_id。要知道名字，再拿這個編號去 customers 查。

這樣王小明換手機，只要改 customers 裡他那一列；所有訂單都指向同一列，下次查到的自然是新電話。兩位王小明也不會混在一起，因為他們的 id 不同。這就是第 1 課問題的答案：訂單只存 customer_id，是為了讓每件事只存一份，改一處就全部正確。

但這引出下一個設計問題：為什麼是訂單記顧客的編號，而不是反過來讓顧客記下自己的訂單編號？

顧客和訂單，編號該放在哪一張表？

上一節決定用編號把顧客和訂單接起來，接下來要決定編號寫在哪一邊。先把兩者的數量關係說清楚：一位顧客可以下零到很多張訂單，一張訂單只屬於一位顧客。這種關係叫一對多。下圖是同一份資料拆成兩張表之後的樣子：

試著把編號反過來放，就知道為什麼只能放在訂單這邊。如果讓 customers 存一個 order_id 欄位，王小明有三張訂單，一格卻只能放一個值，你只能把他複製成三列，又回到上一節「同一個人記很多次」的問題。反過來，每張訂單只有一位顧客，orders 每一列放一個 customer_id 剛好放得下。所以判斷方法是：「多」的那一邊放「一」那邊的主鍵。訂單是多的那邊，customer_id 就放在 orders。

圖裡標成「外鍵」的 customer_id，目前只是一個存編號的普通欄位，資料庫還不會檢查它的值對不對；下一節會說明怎麼讓資料庫真的把它當成外鍵來檢查。

注意圖裡的李建國：他還沒下過單，orders 裡沒有任何一列指向他，這完全合法。一對多的「多」包含零筆。

💡 實務上：設計新功能時，先畫出「誰對誰是一對多」
接到「一張訂單有多項商品明細」「一間店有多位店員」這類需求，資深工程師會先用一句話確認關係：一個 A 有幾個 B、一個 B 屬於幾個 A，再決定編號放哪張表。但也有例外：訂單上的「當時售價」「當時的收件地址」應該直接存在訂單裡，因為那是下單當下的事實，之後顧客改地址、商品調價，舊訂單都不該跟著變。判斷方式是問自己：這個值要「跟著最新的變」，還是「凍結在當時」？王小明的電話屬於前者，所以只存在 customers。

編號放對地方了，但到這一步，customer_id 對資料庫來說還只是一個普通的整數欄位。萬一後端程式寫錯，存進一個根本不存在的顧客編號，會發生什麼事？

程式寫進不存在的顧客編號，資料庫擋得住嗎？

光是把欄位取名叫 customer_id 不夠。名字是給人看的，資料庫不會因為欄位叫這個名字，就知道它跟 customers 表有關。假設後端有 bug，把一張訂單的 customer_id 寫成 99，而 customers 裡根本沒有 99 號。資料庫照樣收下，這張訂單就成了「沒有主人」的資料，通常叫孤兒資料。之後報表算不出它是誰買的，客服也找不到人，而且往往要等到很久以後才會有人發現。

要讓資料庫知道這層關係，得在建表時明白宣告。這個宣告就是外鍵：在一個欄位上註明「這欄的值必須是另一張表裡真的存在的主鍵」。宣告之後，每次新增或修改這一欄，資料庫都會去對方的表確認那個值存在，不存在就拒絕寫入。

講外鍵時會用到兩個稱呼。被指向的那張表（這裡是 customers）叫父表，放外鍵欄位、去指向別人的那張表（這裡是 orders）叫子表。父表要先建好，子表才能參照它，因為建子表時資料庫就會檢查對方存不存在。

外鍵的寫法是在欄位後面加上 REFERENCES。這頁的資料庫已經這樣建好：

CREATE TABLE orders (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id integer NOT NULL REFERENCES customers (id),
  staff_id integer REFERENCES staff (id) ON DELETE SET NULL,
  ordered_at timestamptz NOT NULL,
  status text NOT NULL,
  total integer NOT NULL
);
  • REFERENCES customers (id)：customer_id 必須是 customers.id 裡有的值。
  • NOT NULL：每張訂單一定要有顧客。外鍵只檢查「有填的值存不存在」，不管「有沒有填」，所以要不要允許空白，另外用 NOT NULL 決定。
  • staff_id 也是外鍵，指向店員表 staff。它沒有 NOT NULL，因為線上點餐沒有經手的店員，可以是 NULL。後面的 ON DELETE SET NULL 是本課最後一節的主題，先略過。
  • 外鍵欄位的型別要跟對方的主鍵一致，這裡兩邊都是 integer。

先看看資料長什麼樣。執行後注意 customer_id 和 staff_id 兩欄：它們都只是數字，沒有名字。

資料庫拒絕了這次寫入，訊息裡的 violates foreign key constraint "orders_customer_id_fkey" 意思是違反了外鍵規則。orders_customer_id_fkey 是這條規則的名字，建表時沒有自己取名，資料庫就用「表名_欄位名_fkey」自動命名，看到它就知道是哪張表的哪一欄出問題。把 99 改成 2 再執行，就能成功寫入。

💡 實務上：外鍵錯誤要在 API 層轉成看得懂的回應
前端送來一個已經不存在的商品或顧客編號時，PostgreSQL 會丟出外鍵錯誤（錯誤代碼 23503）。後端如果沒處理，使用者只會看到「500 伺服器錯誤」。常見做法是攔下這個錯誤代碼，回傳 400 或 404 並附上「找不到這位顧客」之類的訊息。程式裡先查一次再寫入也行，但外鍵才是最後一道防線：就算程式有 bug 或有人直接改資料庫，孤兒資料也進不來。

寫入這個方向擋住了。但孤兒資料還有另一個來源：訂單本來指向一位存在的顧客，後來那位顧客被刪掉了。

刪掉還有訂單的顧客，訂單會變成什麼？

上一節的孤兒是寫入時產生的；這一節反過來，從父表那一側製造孤兒。王小明（1 號）有好幾張訂單，如果直接刪掉他，那些訂單的 customer_id = 1 就指向一個不存在的人，跟寫入 99 號的結果一模一樣。所以外鍵也會檢查這個方向。試著刪掉王小明，執行後看錯誤訊息：

訊息變成 update or delete on table "customers" violates foreign key constraint：還有訂單指向王小明，所以不能刪。外鍵守的是同一條規則「子表的每個編號都要找得到父表的列」，不管是從子表寫入、還是從父表刪除，只要會打破這條規則就擋下。訊息裡的 update 指的是另一種情況：把王小明的 id 從 1 改成別的數字，那些訂單的 customer_id 一樣會找不到人，所以也會被擋。主鍵本來就不該改，實務上很少遇到。

真的要刪，就得先處理掉指向他的訂單，再刪他本人，練習 2 會讓你做一次。這是外鍵的預設行為：寧可擋下，也不替你決定子資料的去留。對訂單來說這是對的，訂單是營業紀錄，不該因為某個操作順手消失。

但不是每種子資料都該這樣處理。顧客的外送地址呢？顧客被刪了，地址留著毫無用處，每次都要先手動刪地址再刪顧客只是麻煩。店員離職呢？他經手過的訂單要留著，但經手人那一欄已經指不到人。這兩種情況需要不同的處理方式，外鍵讓你在建立時就寫清楚。

地址跟著刪、訂單斷開經手人：ON DELETE 怎麼選？

上一節看到預設行為是擋下刪除，也看到地址和店員需要別的處理方式。建立外鍵時可以加上 ON DELETE，指定「父表的列被刪掉時，子表指向它的列要怎麼辦」。常用的有三種：

寫法刪除父表的列時適合的場景
不寫（預設 NO ACTION）或 RESTRICT只要還有子表的列指向它，就拒絕刪除顧客 → 訂單。訂單是營業紀錄，不能因為刪顧客就跟著消失
ON DELETE CASCADE子表指向它的列一起刪掉顧客 → 外送地址、訂單 → 訂單明細。子資料離開父資料就沒有意義
ON DELETE SET NULL子表的外鍵欄位改成 NULL，列本身保留店員 → 訂單。店員離職、資料刪除，訂單還在，只是不知道經手人

第一列就是上一節看到的行為，orders.customer_id 沒寫 ON DELETE，所以用的是它。NO ACTION 和 RESTRICT 的細微差別、以及另一個少用的選項，放在課末的補充。下面分別示範另外兩種。

CASCADE：外送地址跟著顧客一起刪

CASCADE 的意思是「連鎖」：刪掉父表的一列時，子表裡指向它的列也一起刪掉。這頁的 orders 沒有設 CASCADE（也不該設），所以要另外建一張真的「依附」在顧客身上的表來示範：外送地址表。地址屬於顧客，顧客刪掉了地址留著也沒用，所以 customer_id 用 ON DELETE CASCADE。執行後看最後一個 SELECT 的結果，應該有三筆地址：

DROP TABLE IF EXISTS：表存在才刪，不存在也不會報錯。放在最前面，這個範例就能重複執行。

李建國（5 號）沒有訂單，只有兩筆地址，所以 orders 的外鍵不會擋他。刪掉他，再看一次地址表：

第一個結果是 RETURNING 回傳的、被刪掉的李建國；第二個結果裡，他的兩筆地址被一起刪掉了，陳美華的地址不受影響。資料庫自動做完了「先刪地址、再刪顧客」，你只下了一句 DELETE。

這不會讓舊訂單失去送貨地址：前面提過，下單當下的收件地址應該抄進訂單裡。addresses 表只是顧客「目前常用」的地址清單，所以可以跟著顧客一起刪。

這種方便也是它危險的地方。CASCADE 不會提示你連帶刪了多少列：如果把「顧客 → 訂單」設成 CASCADE，刪一位顧客就會無聲無息地刪掉他所有的營業紀錄；如果訂單底下又有用 CASCADE 的訂單明細，連鎖還會再往下一層。只在子資料真的「依附」父資料時才用。

SET NULL：店員離職，訂單留著、經手人清空

店員的情況跟地址不同：訂單要保留，只是「經手人」這個關係要斷開。ON DELETE SET NULL 做的就是這件事：刪掉父表的列時，子表指向它的列留下來，只把外鍵欄位改成 NULL。orders.staff_id 建表時就設了它。店員小芳（2 號）離職，刪掉她，比較刪除前後兩個結果的 staff_id 欄：

原本 staff_id = 2 的訂單都還在，只是 staff_id 變成了 NULL，表示「不知道經手人」。這也說明為什麼 staff_id 沒有 NOT NULL：SET NULL 要把欄位改成 NULL，如果欄位同時規定不能是 NULL，兩條規則互相矛盾，刪除就會失敗。

到這裡，三種狀況都有答案了：王小明換手機只改一列；寫錯的編號被外鍵擋下；刪除時，訂單預設擋下、地址跟著刪、店員的訂單斷開經手人。剩下最常被問到的那個情境：顧客自己要求刪除帳號。

💡 實務上：「刪除帳號」很少真的把資料刪光
客服轉來「顧客要求刪除帳號」時，訂單通常是帳務紀錄，不能跟著消失，所以很多系統改用「標記為已刪除」或把姓名、電話做去識別化，而不是真的 DELETE。這正是 orders.customer_id 保持預設「擋下」的好處：有人想直接刪顧客，資料庫會先攔住，逼團隊想清楚。code review 時看到新的 ON DELETE CASCADE，資深工程師會先問：子表的資料是不是真的離開父資料就沒用？刪一筆父資料最多會連帶刪掉多少列？選哪種 ON DELETE 也是產品決定，不確定時去問 PM 或負責帳務的人，比自己猜安全。

補充與查表

  • REFERENCES customers 可以省略欄位：括號裡的 (id) 可以不寫，省略時就是指對方的主鍵。
  • NO ACTION 和 RESTRICT：只在進階情況（延遲檢查）有差別，初學可以當成一樣。另外還有 SET DEFAULT，很少用到。
  • 外鍵不會自動建立索引：主鍵會自動有索引，但 orders.customer_id 這種外鍵欄位不會。「查某位顧客的所有訂單」很常用，通常要自己替外鍵欄位建索引，第 20 課會講。

練習

練習 2、3 每次檢查都會用一個全新的資料庫，不受上面範例刪過資料的影響。

練習 1：建立顧客評論表 reviews，依序有四個欄位：id（自動編號主鍵）、customer_id（整數、不能是 NULL、參照 customers，顧客被刪除時評論要跟著刪除）、rating（整數）、comment（文字）。

練習 2：王小明（id = 1）要求刪除帳號。orders.customer_id 沒有設 ON DELETE，所以直接刪會被擋。請用兩句 DELETE，先刪掉他的訂單、再刪掉他本人。其他人的訂單不能動到。

練習 3：店員阿傑（staff 的 id = 1）離職，刪除他。接著查出所有 staff_id 是 NULL 的訂單 id，由小到大排列（線上訂單本來就是 NULL，也要算進去）。

練習 4：訂單表 orders 和訂單明細表 order_items（一張訂單有很多項明細）。order_items.order_id 的 ON DELETE 最適合設成什麼？

✓ 沒有訂單的明細（「某張不存在的訂單買了兩杯拿鐵」）沒有任何用途，跟著刪是合理的。SET NULL 會留下一堆找不到主人的明細。第 10 課會實際建這張表。

練習 5：訂單表只存 customer_id、不存顧客名字和電話，最主要的好處是什麼？

✓ 重點是「同一件事只記一次」。查詢反而要多做一次對照（JOIN），但換來資料不會互相矛盾。一張訂單屬於很多位顧客是另一種關係（多對多），第 10 課會講。

常見錯誤

  • 先建子表再建父表：REFERENCES customers 時 customers 還不存在，會出現 relation does not exist。建表順序是父表 → 子表；刪表順序反過來。
  • 刪除順序反了：先刪顧客再刪他的訂單會被外鍵擋下。要先刪子表的列，再刪父表的列。
  • 到處都用 CASCADE 省事：刪一筆資料可能連鎖刪掉好幾張表的資料，而且不會有任何提示。預設的「擋下來」通常比較安全。
  • SET NULL 的欄位又加了 NOT NULL：兩個規則互相矛盾，刪除父表的列時會失敗。
  • 外鍵型別不一致：主鍵是 bigint、外鍵用 integer，雖然能建立，但編號超過 integer 上限時會出問題。兩邊用同一個型別。

小結

  • 同一件事只存一份：訂單只記 customer_id，王小明換手機只改 customers 一列，不會出現前後矛盾。
  • 一對多的關係，在「多」的那一邊放「一」那邊的主鍵（例如 orders.customer_id）；要凍結在下單當時的值（售價、收件地址）則直接存在訂單裡。
  • REFERENCES 表 (欄位) 建立外鍵：寫入不存在的編號會被擋，刪除還被參照的資料也會被擋，兩個方向守的是同一條規則。
  • ON DELETE 決定父資料被刪時子資料怎麼辦：預設擋下（訂單）、CASCADE 跟著刪（地址）、SET NULL 斷開關係（店員）。
  • 外鍵欄位不會自動有索引（第 20 課）。
