階段 4：進階查詢 · 第 15 課

常用函式：字串、日期、CASE

月底了，店長交給你三件事。行銷要寄 11 月的新品通知，需要一份顧客名單：email 要能直接拿去寄、電話要是純數字，沒留資料的人要標出來。會計要每個月的訂單數和營收。店長自己想知道訂單裡大單、小單各有哪些，以及每位顧客付了多少、取消了幾次。

資料都在 customers 和 orders 裡，但沒有一份能直接交出去：email 有人打大寫、有人前後多了空白；電話中間有橫線；訂單時間精確到分鐘，會計要的卻是「2026-10」這樣的月份；金額只是一個數字，表裡沒有「大單」這一欄。這課要學的，是怎麼在 SQL 裡把存著的值加工成報表要的樣子。工具是資料庫內建的函式和 CASE，學完你可以各用一句查詢交出這三份東西。

這課會用到：
  • 第 4 課的 NULL：NULL 是「不知道」，不是 0 也不是空字串 ''。
  • 第 7 課的 GROUP BY 與聚合函式：先把列分組，每組用 sum、count 算出一個值。
  • 第 13 課的 timestamptz 與 interval：timestamptz 存的是一個絕對的時間點，讀出時換成連線設定的時區顯示；interval 代表一段時間。
這課的路線：
  1. 加工要在哪裡做：為什麼報表的加工通常放在 SQL，函式在 SELECT 裡怎麼每一列各套一次。
  2. 行銷的名單：用字串函式清理 email 和電話，再用 COALESCE、NULLIF 處理沒資料的格子。
  3. 會計的月報：用 to_char、date_trunc 把訂單時間變成月份再按月加總；用 interval 算到期日，用固定時間讓報表能重跑。
  4. 店長的分級與統計：用 CASE WHEN 分出大單小單，再把 CASE 放進 SUM（或改用 FILTER），一次算出好幾種統計。

這頁的 customers 比平常多了 email 欄，故意放了一些「髒」資料：大小寫混雜、前後有空白、空字串、NULL。orders 有 status 欄，值是 paid（已付款）、cancelled（已取消）或 pending（處理中）。

加工要在哪裡做？函式在 SELECT 裡怎麼運作

三份東西都要「加工」，第一個要決定的是在哪裡加工。你很熟的做法是把資料撈回後端，用 JavaScript 處理：email.trim().toLowerCase()，再自己把訂單按月份分堆加總。另一個做法是在 SQL 裡就處理好，後端拿到的已經是報表要的樣子。

以行銷的名單來說，兩種做法都行，顧客就幾百幾千人。會計的月報就不一樣了：要「按月份加總」，GROUP BY 需要一個「同一個月的訂單都相同」的值。如果月份只能在程式裡算，就得把所有訂單撈回後端再自己分組；訂單累積到幾十萬筆時，光是傳輸和放進記憶體就是負擔。在 SQL 裡先算出月份，資料庫分組加總完，只回傳十幾列結果。所以報表類的加工，通常直接寫在 SQL 裡。

做這件事的工具就是函式。SQL 的函式跟 JavaScript 的函式一樣：給它輸入，它回傳一個輸出。lower('Latte') 回傳 latte，就像 JS 的 'Latte'.toLowerCase()。差別在於寫在 SELECT 裡、輸入是一個欄位的時候，例如 lower(email)，每一列都會各套一次：第一列的 email 進去、出來一個小寫的 email，第二列再來一次，結果放在查詢結果的新一欄。

咖啡店的比喻：店長拿到一疊手寫的顧客卡，請工讀生「每一張都把電話的橫線劃掉、重抄一次」。工讀生就是函式，每一張卡（每一列）處理一次，處理完的結果寫在旁邊新的一欄。原本那疊卡沒有被改掉：函式只改變這次查詢的結果，表裡存的值不變。真的要把存著的值改掉，要用第 6 課的 UPDATE。

第 7 課的 COUNT、SUM 也叫函式，但它們是聚合函式：把很多列合成一個值。這一課的函式大多是一列進、一列出，查詢結果有幾列，套完函式還是幾列。

函式還可以一層包一層，像 JS 的 f(g(x))，從最裡面開始算。另外要先記住一個規則：像 lower、replace 這類函式，輸入是 NULL 時，回傳的也是 NULL。「不知道」的值轉成小寫，還是不知道。這個規則等一下在名單上會一直碰到。

有了函式，就可以開始做第一份交付物：行銷的名單。先從最髒的 email 下手。

行銷的名單：怎麼把 email 和電話整理成能用的樣子？

上一節說函式每一列各套一次，現在拿它來整理 email。看種子資料：陳美華存的是 ' Meihua.Chen@Gmail.com '，前後有空白；李建國存的是 'JianGuo@Example.COM'，大小寫混雜。行銷系統通常拿 email 判斷是不是同一個人，JianGuo@Example.COM 和 jianguo@example.com 會被當成兩個人；前後的空白則可能讓寄信失敗。所以要做兩件事：去掉頭尾空白，再統一轉成小寫。

用到的函式：

  • trim(s)：去掉頭尾的空白，中間的空白不動。trim(' a b ') → a b。
  • lower(s)／upper(s)：轉小寫／大寫。
  • length(s)：字數。中文一個字算 1，length('美式咖啡') → 4。這裡用它看出「看不見的空白」。
  • split_part(s, 分隔, 第幾段)：用分隔符號切開，取第幾段（從 1 開始數）。用 '@' 切開取第 2 段就是網域，行銷可以看顧客多半用哪家信箱。

執行後，對照每一欄由左到右的變化，特別看陳美華、林志豪、張雅婷三列：

  • 陳美華：Meihua.Chen@Gmail.com 本身是 21 個字元，原始長度卻是 24，多出來的 3 個就是前後的空白。lower(trim(email)) 由內往外算：先 trim 去空白，再 lower 轉小寫，最後 split_part 取網域。
  • 林志豪：email 是 NULL，每一欄都是 NULL，就是上一節說的「輸入 NULL、輸出 NULL」。
  • 張雅婷：email 是空字串 ''，它是一個確實存在的值，所以各欄都照常算出空字串，長度是 0。

接著是電話。行銷的簡訊系統要純數字，種子資料裡卻是 0912-345-678 這種格式。兩個函式：

  • replace(s, 舊, 新)：把所有出現的「舊」換成「新」。這點跟 JS 不同：JS 的 '0912-345-678'.replace('-', '') 只換掉第一個橫線，要換全部得用 replaceAll。
  • substring(s, 起點, 長度)：從「起點」開始擷取「長度」個字。SQL 的位置從 1 開始數，不是 JS 的 0。substring('0912-345-678', 1, 4) → 0912。

李建國的 city 是 NULL。|| 只要碰到一個 NULL，整串都變 NULL，連他的名字都不見了；concat 則會跳過 NULL 的參數，等於把它當成空字串，得到 李建國（）。道理跟第 4 課一樣：NULL 是「不知道」，把一段已知的文字接上一段不知道的文字，結果整串都不知道。JS 不會這樣，'李建國' + null 得到 '李建國null'，所以前端工程師很容易在這裡踩坑。

💡 實務上：髒資料最好在寫入時就整理好
最常見的場景是登入和註冊：使用者打 Ming@Example.com ，資料庫存的是 ming@example.com，比對前就要先 lower(trim(...))，不然會出現「同一個人註冊兩次」或「明明有帳號卻登不進去」。比較穩的做法是後端在寫入前就統一格式，資料庫裡存的永遠是乾淨的值；查詢時才臨時清理，每次都要記得包函式，而且 WHERE lower(email) = ... 用不到一般的索引（第 20 課會講）。這一課的函式最適合用在兩個地方：一次性清理舊資料，以及匯出報表時的格式整理。這次行銷的名單屬於後者，在查詢裡清理沒問題；但如果發現髒資料一直進來，該回頭修的是寫入的那一段程式。

email 和電話整理好了，名單卻還有空白的格子：林志豪沒有 email 也沒有電話、張雅婷的 email 是空字串、李建國的城市是 NULL。行銷希望這些格子顯示「未提供」，而不是空著讓人猜。

名單上沒有資料的格子，怎麼顯示「未提供」？COALESCE 和 NULLIF

上一節留下兩種「沒有值」：NULL（林志豪的電話、李建國的城市）和空字串（張雅婷的 email）。第 4 課講過它們不是同一件事：NULL 是「不知道」，空字串是一個確實存在、長度為 0 的值。處理它們要用兩個函式。

COALESCE(a, b, c, …) 從左到右檢查參數，回傳第一個不是 NULL 的值。COALESCE(phone, '未提供') 的意思是：有電話就用電話，電話是 NULL 就用 '未提供'。它最常用來給預設值，作用很像 JS 的 phone ?? '未提供'：?? 只在 null／undefined 時才換成右邊的值，空字串不會被換掉；COALESCE 也一樣，只換 NULL，不換空字串。

所以空字串要先變成 NULL，這就是 NULLIF(a, b) 的工作：a 等於 b 時回傳 NULL，否則原樣回傳 a。NULLIF(trim(email), '') 的意思是：去掉空白後如果是空字串，就當成 NULL。它把「假的空值」變成真正的 NULL，之後就能跟真正的 NULL 一起處理。

林志豪的電話和李建國的城市都換成了預設文字。張雅婷的 email 欄是空字串，它不是 NULL，如果直接交給 COALESCE，不會被換掉；但在 空字串變NULL 那一欄，NULLIF 已經把它變成 NULL。把這一欄再交給 COALESCE，NULL 和空字串這兩種「沒有值」就能一起換成「未提供」。名單的最後一步就是把上一節的 lower(trim(...)) 和這兩個函式組起來，留給練習 4。

💡 實務上：「未提供」該由 SQL 還是前端來寫？
這次的名單是交給行銷的匯出檔，直接在 SQL 寫「未提供」沒問題。但如果查詢結果是給 API 回傳的，通常保留 NULL，讓前端決定顯示「未提供」「—」或英文版的文字；在 SQL 裡寫死中文，之後做多語系或換文案都要改後端。COALESCE 真正好用的地方是計算：假設訂單另有一個可以是 NULL 的外送費欄位 delivery_fee，算總額時寫 total + COALESCE(delivery_fee, 0)，避免一個 NULL 讓整個金額變 NULL。NULLIF 防除以零則常見在儀表板的「轉換率」「平均客單價」：新開的分店還沒有訂單時，頁面應該顯示「無資料」，而不是整個 API 回 500。

會計的月報：怎麼把訂單時間變成「2026-10」並按月加總？

上一節結尾的問題是：GROUP BY 需要一個「同一個月的訂單都相同」的值。2026-09-02 08:40 和 2026-09-18 16:45 是兩個不同的時間，但它們屬於同一個月。我們要的是一個函式，把它們都變成同一個值。下面這張圖是其中一種做法 date_trunc，它把「月」以下的部分全部砍掉：

PostgreSQL 有三個函式都能從時間裡取出「月」，差別在回傳的東西是什麼型別：

寫法作用例子 → 結果
date_trunc('month', t)砍到月初（還是時間型別）→ 2026-10-01 00:00:00+08
extract(month FROM t)取出其中一個數字→ 10
to_char(t, 'YYYY-MM')照格式轉成文字→ 2026-10

  • extract 只取出一個數字。用它按月分組要小心：它只看「月」，2025 年 10 月和 2026 年 10 月都是 10，資料跨年時會被加在一起。

這句查詢裡，to_char 先把每一列的時間變成月份文字，GROUP BY 再把相同月份的列分成一組，count 和 sum 各算一次。PostgreSQL 允許在 GROUP BY 和 ORDER BY 裡直接用 SELECT 取的別名（這裡的 month），不用把 to_char(...) 再抄一次。'YYYY-MM' 這種格式年在前、月補滿兩位，照文字排序剛好就是照時間排序；如果寫成 'MM/YYYY'，排序就會把不同年份的同月份排在一起。

💡 實務上：做月報之前，先問「用哪個時區算」
後台的「本月營收」「每日訂單數」幾乎都是這種寫法，但半夜的訂單算哪一天，取決於資料庫連線的時區設定。伺服器常設成 UTC，台灣早上 8 點前的訂單就會被算到前一天，財務對帳時才發現數字對不上。資深工程師接到報表需求會先確認：以台灣時間還是 UTC 為準、日期由前端傳還是後端算，並把時區寫明（例如連線時設定 timezone，或用 AT TIME ZONE 'Asia/Taipei' 轉換）。另外，篩選某個月請用時間範圍 ordered_at >= 起 AND ordered_at < 迄，不要寫 WHERE to_char(...) = '2026-10'，前者才用得到索引（第 20 課）。

月報交出去之後，會計追加了兩個需求：已付款的訂單會送一張 30 天內有效的折價券，要列出到期日；另外希望每天早上自動產生「昨天」的營收報表。這兩件事都要對時間做加減，第二件還要知道「現在」是什麼時候。

到期日和「昨天」：時間怎麼加減？為什麼報表不該依賴 now()？

先處理到期日。第 13 課介紹過 interval：它代表「一段時間」，而不是一個時間點。時間點加上一段時間，得到另一個時間點，所以「下單時間加 30 天」直接寫 ordered_at + interval '30 days'。interval 的寫法很口語：'30 days'、'1 month'、'2 hours 30 minutes' 都可以。反過來，兩個時間點相減，得到的是它們之間的一段時間，也就是一個 interval。

執行後，前兩個新欄位看加減的結果，後兩欄比較「相減」和 age 這兩種算經過多久的方式。後兩欄的 timestamptz '2026-10-29 00:00+08' 是在字串前面寫上型別，告訴 PostgreSQL 這段文字是一個 timestamptz 時間點（和上面 interval '7 days' 是同一種寫法）。這裡把它當成「今天」，算每張訂單下單到今天過了多久；為什麼不用「現在」，本節後半會說明。

直接相減的結果用「幾天又幾時幾分幾秒」表示；age 會換算成「幾個月又幾天」，給人看比較好讀。折價券的到期日只要把 interval '7 days' 換成 '30 days'，再用上一節的 to_char 轉成日期格式，這是練習 6。

再來是「昨天的報表」。直覺的寫法是拿「現在」往回推，PostgreSQL 用 now() 取得現在的時間點，current_date 取得今天的日期。多執行幾次，你會發現 now() 每次都不一樣：

這正是問題所在。如果報表寫成 WHERE ordered_at >= now() - interval '1 day'，它算的是「執行當下往回 24 小時」，不是「昨天」：排程晚跑 10 分鐘，涵蓋的範圍就跟著挪 10 分鐘；會計說「上週三那天的數字怪怪的，幫我重跑」，你也沒辦法，因為重跑時的「現在」已經不同了。

now() 會隨時間改變，所以寫報表或測試時最好用固定的時間，例如 timestamptz '2026-10-29 00:00+08'，結果才能重現。這一課的練習全部用固定時間。

可靠的做法是讓報表接收兩個固定的時間點：開始（昨天 00:00）和結束（今天 00:00），寫成 ordered_at >= 開始 AND ordered_at < 結束。每天的排程由程式算出這兩個值傳進來；要補跑哪一天，就傳那一天的起訖時間。結束用 < 而不是 <=，今天 00:00 整的訂單才不會同時被算進昨天和今天。上面 interval 的範例用 timestamptz '2026-10-29 00:00+08' 而不是 now()，也是同樣的理由：結果每次都一樣，才能驗證。now() 還有一個跟交易有關的細節，放在課末。

會計的兩份需求都完成了。最後輪到店長：他想把訂單分成大單、中單、小單，但表裡只有 total 這個數字，沒有「級別」這一欄，要讓 SQL 依照金額做判斷。

店長的分級：怎麼在 SQL 裡寫 if／else？CASE WHEN

上一節留下的需求是「依照條件給出不同的值」，在 JS 裡你會寫 if／else if／else。SQL 裡對應的是 CASE WHEN：

CASE
  WHEN 條件1 THEN 值1
  WHEN 條件2 THEN 值2
  ELSE 其他情況的值
END

它跟 JS 的 if 有一個關鍵差別：CASE 是一個會產生值的運算式，比較像 JS 的三元運算子 a ? b : c，而不是一段陳述式。所以它可以放在任何能放「一個值」的地方：SELECT 的一欄、ORDER BY，甚至聚合函式的參數裡，下一節會用到這一點。和函式一樣，寫在 SELECT 裡時每一列各算一次。

分級做好了，店長接著問：「那每位顧客到底付了多少錢、取消過幾次？」這要在同一張表裡同時算兩種狀態的訂單，而 WHERE 一次只能留下一種。

一張表同時看「已付款」和「已取消」：CASE 放進 SUM，或用 FILTER

上一節的問題是：要已付款的金額，就得寫 WHERE status = 'paid'，取消的訂單就被過濾掉了；要取消次數，又得寫另一句 WHERE status = 'cancelled'。跑兩次查詢、再在程式裡依顧客合併，可以做到，但很繞。上一節說過 CASE 是會產生值的運算式，可以放進聚合函式裡，這就是解法：不過濾任何一列，而是讓每一列在被加總之前，先決定自己要貢獻多少。

原理：GROUP BY customer_id 先把同一位顧客的訂單分成一組，組裡每一列先經過 CASE。算已付款金額時，已付款的列貢獻自己的 total，其他列貢獻 0，全部加起來就等於「只加已付款的」。算取消次數時，取消的列貢獻 1，其他列貢獻 0，加起來就是取消了幾筆。一次掃過資料，兩種統計都算好了。

PostgreSQL 還有更直白的寫法 FILTER：在聚合函式後面加 FILTER (WHERE 條件)，只讓符合條件的列參與這一個聚合，其他欄位不受影響。

結果幾乎一樣，只有一個差別：某位顧客完全沒有已付款訂單時，FILTER 版的 sum 是 NULL，因為沒有任何一列可以加；CASE ... ELSE 0 版是 0，因為每一列都貢獻了 0。看林志豪（customer_id 3）：他有一筆取消、一筆已付款，兩版都有值；如果他只有取消的訂單，FILTER 版就會是 NULL。需要 0 的話，用前面學的 COALESCE 包起來：COALESCE(sum(total) FILTER (WHERE status = 'paid'), 0)。

💡 實務上：後台儀表板的「一次查出好幾個數字」
咖啡店後台首頁常有一排卡片：今日已付款、處理中、已取消。新手常會打三次 API、跑三個查詢；用 FILTER 或 CASE 一次掃過資料就能全部算完，程式也比較好維護。要注意的是像「300 元以上算大單」這種門檻屬於商業規則，PM 可能下個月就改；如果同一個門檻散落在好幾支 SQL 裡，改的時候很容易漏，最好集中在一個地方定義（例如後端的一個常數，或第 23 課會教的檢視表（view））。另外 NULL 和 0 對前端意義不同（「沒資料」vs「真的是零」），先跟前端講好要回哪一種。

到這裡，店長的三件事都有了對應的查詢：行銷的名單用字串函式加 COALESCE／NULLIF，會計的月報用 to_char 加 GROUP BY，店長的分級和統計用 CASE 和 FILTER。下面的練習就是把它們實際交出來。

常見錯誤

  • 用 || 接到 NULL：整串變 NULL。不確定欄位會不會是 NULL，用 concat 或先 COALESCE。
  • CASE 條件順序寫反：寬的條件（>= 150）放前面，嚴的條件（>= 300）永遠輪不到。
  • to_char 把分鐘寫成 MM：MM 是月份，分鐘是 MI。'HH:MM' 會印出「時:月」。
  • 以為空字串是 NULL：'' 和 NULL 不一樣，COALESCE 不會換掉空字串。需要時用 NULLIF(x, '')。
  • 用 extract(month ...) 按月分組：它只取出月份數字，不同年份的同一個月會被加在一起。按月統計用 to_char(t, 'YYYY-MM') 或 date_trunc('month', t)。
  • 報表依賴 now()：結果每次不同、沒辦法驗證。報表和測試用固定時間。
  • substring 從 0 開始數：SQL 的位置從 1 開始，不是 0。

小結

  • 報表類的加工通常寫在 SQL 裡：函式在 SELECT 裡每一列各套一次，只改變查詢結果，不改表裡的值；按月加總這類需求，月份必須先在資料庫裡算出來才能 GROUP BY。
  • 行銷的名單：trim、lower、replace 清理 email 和電話；|| 碰到 NULL 整串變 NULL，concat 會跳過 NULL。COALESCE 給預設值，NULLIF 把空字串或 0 變成 NULL。
  • 會計的月報：to_char 轉成看得懂的月份文字、date_trunc 切到月初、extract 只取數字（會跨年混在一起）；切月份依照連線的時區。interval 做加減，age 算經過多久；報表用固定的起訖時間，不依賴 now()。
  • 店長的分級：CASE WHEN 由上往下、第一個成立就停，條件從嚴到寬排；它是會產生值的運算式，放進 SUM 裡（或改用 FILTER）可以在一次查詢中做多種條件統計。
