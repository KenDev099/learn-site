階段 7：實務 · 第 26 課

期末專題：會員集點＋預約座位

這是基礎篇（第 1～26 課）的最後一課，不教新語法。整課只有一個任務：咖啡店老闆想做「會員集點」和「預約座位」，交給你一頁需求，你要把它變成一個可以上線的資料庫。

做法是照實務上的順序一步一步走：讀需求、決定要哪些表、畫成圖給人確認、寫成 CREATE TABLE、放資料確認約束有在擋、寫出老闆要的報表，最後在資料變多之前補上索引。每一步都會用到前面某一課，旁邊會標出是第幾課，忘了可以回去翻。這個順序本身也是這課要學的：跳過前面的步驟直接建表，代價通常是上線後要寫 migration 改 schema、補舊資料。

這課的路線：
  1. 步驟一：需求裡哪些東西要存進資料庫、彼此是什麼關係？「每位會員有幾點」該怎麼存？
  2. 步驟二、三：怎麼把結論畫成 ER 圖給人確認，再寫成帶約束的 CREATE TABLE？
  3. 步驟四：約束真的擋得住錯誤的資料嗎？新會員的 id 還不知道時，點數紀錄怎麼寫進去？
  4. 步驟五：老闆要的五張報表怎麼查，每一張的陷阱在哪裡？
  5. 步驟六與上線前：資料變多之前要補哪些索引、還有哪條規則沒擋住，最後用一張檢查清單把設計對一遍。
這頁一開始已經自動建好一份參考版本的四張表和資料（這份預先放好的資料稱為 seed），步驟四以後的查詢都用它。步驟三的練習會讓你在另一個叫 draft 的空間裡自己建一份，不會跟參考版本撞名，做法到時候再說明。

老闆的需求長什麼樣？

任務從這一頁需求開始：

咖啡店老闆的需求：

  1. 客人可以加入會員，登記姓名和手機號碼。手機號碼用來登入，不能重複。
  2. 店裡有幾張桌子，每張有桌號（A1、B2……）和可坐的人數。
  3. 會員可以預約座位：選一張桌子、一個時間、幾位。每筆預約有狀態：已預約、已取消、已完成。每次預約佔用 2 小時。
  4. 消費可以集點，點數也可以兌換商品。老闆想知道每一筆點數是怎麼來、怎麼用掉的。
  5. 老闆想看：某一天有哪些預約、每位會員現在有幾點、誰是常客、某個時段還有哪些大桌空著。

這份需求是用老闆的語言寫的：裡面沒有表、沒有欄位，只有他想做的事和想看的報表。前 4 點說明要記錄什麼，第 5 點說明之後要查什麼。兩者都要顧到：資料存的方式決定了查不查得出來，例如老闆要「每一筆點數怎麼來的」，如果只存一個點數總和，之後無論怎麼寫 SQL 都查不回明細。所以後面每做完一步，都要回頭對照這 5 點。

第一個問題是：這段文字裡，到底有哪些東西需要存進資料庫？

步驟一：需求裡有哪些東西要記錄？它們之間是什麼關係？

先從文字裡找名詞：會員、姓名、手機號碼、桌子、桌號、人數、預約、時間、狀態、點數、商品。名詞不一定都要變成一張表。要分辨的是：它是「一種會獨立存在、有好幾項自己資料的東西」，還是「用來描述別的東西的一項資料」。

前一種叫實體（entity），也就是要記錄的東西本身，每個實體對應一張表（第 8 課、第 11 課）。後一種是某個實體的欄位。用這個標準過一遍：

  • 會員是實體，姓名、手機號碼是描述會員的欄位。
  • 桌子是實體，桌號、可坐人數是描述桌子的欄位。
  • 預約是實體：每一筆都有自己的時間、人數、狀態，而且同一位會員會預約很多次。
  • 商品在需求裡只出現在「兌換商品」，老闆沒有要管理商品清單，所以先不開表，兌換了什麼寫在點數紀錄的原因裡就好。

接著找實體之間的關係。第 8 課的一對多是這樣判斷的：一邊的一筆資料，對應另一邊的很多筆；而外鍵放在「多」的那一邊，因為那一邊的每一列只需要記一個「我屬於誰」。

  • 一位會員可以有很多筆預約，一筆預約只屬於一位會員：一對多，預約記著是哪位會員。
  • 一張桌子可以被預約很多次，一筆預約只用一張桌子：一對多，預約記著是哪張桌子。

把兩條合起來看：會員和桌子之間其實是多對多，一位會員會坐過很多張桌子，一張桌子也會被很多會員坐過。第 10 課處理多對多的方法是加一張中間表，兩邊各一個外鍵；「預約」正好就是這張中間表，只是它多了自己的資料（時間、人數、狀態），所以它同時是一個實體。

還剩「點數」沒有決定。它看起來像會員的一項資料（「王小明有 65 點」），但需求第 4 點說老闆想知道「每一筆點數是怎麼來、怎麼用掉的」。先想想看該怎麼存：

思考題 1：「每位會員現在有幾點」要怎麼存？

✓ 需求第 4 點說要知道「每一筆點數是怎麼來、怎麼用掉的」，所以要保留每一筆紀錄（像銀行的交易明細）。只存一個數字就失去了歷史；用逗號串起來違反第一正規化（第 11 課），沒辦法查詢和加總。資料量很大時，可以再另外存一份「目前餘額」加快查詢，但明細一定要有。

選 b 之後，點數就變成第四個實體：點數紀錄，每一列是一次點數的變化，有點數、原因、時間。它跟會員也是一對多：一位會員有很多筆點數紀錄，每一筆記著是誰的。這跟銀行存摺是同一個道理：存摺上留的是每一筆存提，餘額是從明細加出來的。反過來，如果在會員表另外存一個「目前點數」欄位，每次集點都要同時改兩個地方，只要有一條程式路徑漏改一次，兩份資料就再也對不上，你也說不出哪一份才是對的。真的因為效能要另外存餘額時，明細仍是唯一的依據：餘額要在同一個交易裡跟著明細一起更新（或用第 23 課的 trigger），兩邊對不上時，以明細重新算出餘額。

到這裡，需求變成了四個實體：會員、桌子、預約、點數紀錄，以及三條一對多的關係。

💡 實務上：需求一定有沒講清楚的地方，先問再畫表
老闆或 PM 給的需求很少是完整的。以這份需求為例，資深工程師會先問：會員換手機號碼怎麼辦？點數會不會過期？預約可以改時間嗎？沒來的客人要不要另外一個狀態？這些答案會直接改變 schema，例如「點數會過期」可能就要多一個到期時間欄位。把問題和答案寫進需求文件或 issue，之後有爭議時才有依據；上線後才發現漏問，通常要寫 migration 加欄位、補舊資料。

不過，這些結論現在只存在你的腦袋和幾行條列裡。老闆、同事要怎麼確認你理解得對？下一步把它畫出來。

步驟二：怎麼把表和關係畫出來，讓大家確認？

條列文字很難一眼看出「哪張表連到哪張表、誰記著誰的 id」。實務上會畫一張 ER 圖：E 是實體（entity）、R 是關係（relationship），也就是把上一步找出的實體和關係畫成圖。它的用途是溝通和檢查：在圖上改一條線只要幾秒，表建好、有了資料之後再改，就要寫 migration。

畫法：

  • 每個實體畫一個方框，框頂寫表名，裡面列出欄位。
  • 標出主鍵（PK，每一列的唯一編號）和外鍵（FK，記著另一張表某一列的 id）。
  • 有關係的表之間連一條線，線的兩端標 1 和 N：標 N 的那一端是「多」的一邊，外鍵就在那張表裡。

先自己在紙上畫，再打開下面的參考解答對照。對照時注意兩件事：每一條線的 N 端，表裡都要有一個 FK 欄位；需求裡提到的每一項資料，都要在某個方框裡找得到。

看 ER 圖參考解答

圖上看得出每張表有哪些欄位，但還看不出欄位是什麼型別、哪些必填、哪些不能重複。這些規則要寫進 SQL，資料庫才會幫你守住。

步驟三：圖怎麼變成 SQL？每個欄位的型別和約束

把 ER 圖變成 CREATE TABLE，每個欄位都要回答兩個問題：存的是什麼型別（第 13 課），以及有哪些規則必須永遠成立（第 12 課）。規則寫成約束，資料庫會在每一次寫入時檢查，不管資料是從後端 API、後台工具還是有人手動下 SQL 寫進來的。

下面是完整的規格。每一項都對應需求或前面的課：

  • id 用自動編號的主鍵（第 2 課）：編號由資料庫產生，不會重複，也不會因為會員改名、換手機而改變。
  • phone 加 UNIQUE：需求第 1 點說手機號碼用來登入、不能重複。只靠後端先查再寫，兩個請求同時進來時兩邊都會查到「沒有重複」（第 19 課），由約束擋才可靠。
  • 時間一律用 timestamptz：它存的是一個絕對的時間點，不管伺服器或使用者在哪個時區都不會算錯（第 13 課）。
  • capacity、party_size 加 CHECK (… > 0)：0 人的桌子、0 位客人的預約在現實中不存在，寫進來一定是程式有 bug。
  • status 只能是三種值，對應需求第 3 點的已預約、已取消、已完成；預設 'booked'，因為新建立的預約一定是已預約。
  • points 用正負號表示方向：集點是正數、兌換是負數，這樣目前點數就是一個 sum。CHECK (points <> 0) 擋掉沒有意義的 0 點紀錄。

請依照表名、欄位名、順序、型別、約束一字不差地建立（第 2、8、12、13 課）：

表欄位（依序）
membersid 自動編號主鍵；name text 必填；phone text 必填、不能重複；joined_at timestamptz 必填、預設 now()
cafe_tablesid 自動編號主鍵；label text 必填、不能重複；capacity integer 必填、CHECK (capacity > 0)
reservationsid 自動編號主鍵；member_id integer 必填、參照 members；table_id integer 必填、參照 cafe_tables；reserved_at timestamptz 必填；party_size integer 必填、CHECK (party_size > 0)；status text 必填、預設 'booked'、CHECK (status IN ('booked', 'cancelled', 'done'))
point_transactionsid 自動編號主鍵；member_id integer 必填、參照 members；points integer 必填、CHECK (points <> 0)；reason text 必填；created_at timestamptz 必填、預設 now()

為什麼 status 用 text 加 CHECK，而不用 enum？第 13 課教過，兩者都能把值限制在固定的幾種。差別在之後要改的時候：CHECK 只是一條約束，要加新狀態時刪掉舊的、加一條新的就好，比較容易改，所以這裡選它。

動手之前，先說明練習的環境。這頁的 seed 已經建好一份參考版本的表和資料，給後面的步驟使用；你在這裡建同名的表會撞名。所以練習的起始內容會先建一個叫 draft 的 schema。schema 是資料庫裡的命名空間，就像資料夾：不同資料夾裡可以有同名的檔案，不同 schema 裡也可以有同名的表。接著 SET search_path TO draft 告訴資料庫「之後沒寫 schema 的表名，都到 draft 裡找」，所以你建的表都會放在 draft 裡面。起始內容那兩行不要刪。判分時會檢查 draft 裡每張表的欄位（名稱、順序、型別、是否必填）和約束（主鍵、外鍵、UNIQUE、CHECK 的數量）。

練習 1：依照規格，建立 members 和 cafe_tables。

練習 2 的兩張表有外鍵，要注意建立順序：外鍵參照的表必須已經存在，所以 members、cafe_tables 要先建好，起始內容已經幫你放在前面。

練習 2：依照規格，建立 reservations 和 point_transactions。注意外鍵和 CHECK。

表建好了，約束也寫上了。但「寫了約束」不等於「約束有在擋」：欄位名打錯、CHECK 條件寫反，CREATE TABLE 一樣會成功。要確認，就得真的放資料進去試。

💡 實務上：開發用的假資料要刻意放邊界情況
團隊通常會維護一份 seed 檔，讓每個人在本機、測試環境都能一鍵建出同樣的資料。好的 seed 不只放「正常」的資料，還會刻意放容易出錯的情況：沒有任何點數的會員（黃淑芬）、已取消的預約、剛好在時段邊界上的預約。報表或查詢寫錯時，這些資料會讓錯誤馬上現形，而不是上線後才被客人發現。seed 只放假資料，不要從正式環境複製真實的姓名和手機。

資料進來了，而且約束有在守。接下來回到需求第 5 點：老闆真正要看的是報表。

步驟五：老闆要的報表怎麼查？

需求第 5 點有四件事：某一天的預約、每位會員的點數、誰是常客、某個時段的空桌；再加上點數的明細，共五個查詢。每一題都自動判分。這一步最容易錯的地方通常不是語法，而是漏了需求裡沒明說的條件：取消的預約算不算、沒有點數的會員要不要出現、「某一天」是哪個時區的一天。所以每題前面先把這件事講清楚。

查詢 1：某一天的預約。預約、桌子、會員分在三張表，要用外鍵 JOIN 起來才拿得到桌號和姓名。「11 月 1 日」用半開區間表示：大於等於 11/1 0 點、小於 11/2 0 點，這樣 11/1 23:59 不會漏、11/2 00:00 不會多算。字串 '2026-11-01' 沒寫時區，會用目前連線的時區解讀，這頁的連線時區是台北，所以正好是台灣時間的 11/1（第 13 課）。取消的預約不是老闆要看的，要排除。

查詢 1（JOIN，第 9 課）：列出 2026 年 11 月 1 日（台灣時間）所有沒有取消的預約，依序回傳預約時間、桌號、會員姓名、人數，依預約時間、桌號排序。

查詢 2：每位會員目前的點數。點數 = 這位會員所有點數紀錄的 sum。陷阱是黃淑芬：她沒有任何點數紀錄，用一般的 JOIN 她會整個消失。要用 LEFT JOIN 保留左表的每一位會員，沒對到的那一列，點數欄位是 NULL；而 sum 加總全是 NULL 的值，結果還是 NULL，不是 0，所以要再用 COALESCE 把 NULL 換成 0。GROUP BY 要包含 m.id：兩位會員可能同名，但他們是不同的人，只依姓名分組會把兩個人的點數加在一起。

查詢 2（LEFT JOIN、GROUP BY、COALESCE，第 7、9、15 課）：每位會員目前的點數，依序回傳姓名、點數。沒有任何點數紀錄的會員也要列出、點數是 0。依點數由高到低排序，點數相同時依會員 id 由小到大。

查詢 3：誰是常客。這裡有兩個篩選條件，作用的時間點不同：「沒有取消」是對每一筆預約篩，在分組之前做，用 WHERE；「至少 2 筆」是對分組後的筆數篩，要等 count 算出來才能判斷，用 HAVING（第 7 課）。

查詢 3（HAVING，第 7 課）：誰是常客？找出沒有取消的預約至少 2 筆的會員，依序回傳姓名、預約筆數。

查詢 4：點數存摺。老闆要看王小明的每一筆明細，旁邊還要有「到這一筆為止的餘額」。用 GROUP BY 加總會把所有明細併成一列，明細就不見了；第 17 課的視窗函式可以保留每一列，同時在每一列算出依時間累加的總和。關鍵在 OVER 裡的 ORDER BY：OVER () 裡沒寫 ORDER BY 時，每一列的 sum 都是全部明細的總和；寫了 ORDER BY created_at，每一列只加到排在它前面（含自己）的那些列，所以就是存摺上「到這一筆為止的餘額」。如果兩筆的 created_at 完全相同，它們會被當成同一個位置一起加進去，兩列顯示的餘額一樣；真的會發生時，改用 ORDER BY created_at, id 讓順序唯一。

查詢 4（視窗函式，第 17 課）：王小明（member_id = 1）的點數明細，像存摺一樣，依序回傳時間、點數、原因、到這一筆為止的累計餘額，依時間排序。

查詢 5：某個時段還有哪些大桌空著。先想清楚「被佔用」是什麼意思：一筆預約佔用 reserved_at 起的 2 小時，只要跟客人想來的 14:00～16:00 有任何一點重疊，那張桌子就不能給。重疊的條件是「預約開始 < 客人結束，而且預約結束 > 客人開始」。拿 seed 的資料驗證（seed 裡只寫 table_id，對照桌子表：3 是 B1、4 是 B2、5 是 B3、6 是 C1）：B1（table_id 3）那筆 13:00 開始、15:00 結束，13:00 < 16:00 而且 15:00 > 14:00，重疊，要排除；B3（table_id 5）那筆 11:30 開始、13:30 結束，13:30 > 14:00 不成立，不重疊，B3 可以給。C1（table_id 6）那筆 14:30 開始，重疊，要排除；B2（table_id 4）15:00 那筆也重疊，但已經取消，所以 B2 仍然可以給。結束和開始剛好碰在一起（例如 A1 16:00 開始的那筆，雖然 A1 本來就不是大桌）也不算重疊，因為用的是 < 而不是 <=。題目要你先用 CTE 把「被佔用的桌子」找出來，再從所有大桌裡排除它們（第 16 課）。

查詢 5（CTE，第 16 課）：有一組 4 位客人想在 11 月 1 日 14:00～16:00（台灣時間）來店。找出可坐 4 人以上、而且這段時間沒有被佔用的桌子，依序回傳桌號、可坐人數，依桌號排序。每筆預約佔用 2 小時（從 reserved_at 到 reserved_at + interval '2 hours'），取消的不算。提示：兩段時間 [A開始, A結束) 和 [B開始, B結束) 重疊的條件是「A開始 < B結束 而且 A結束 > B開始」。

💡 實務上：寫報表前，先跟提需求的人對齊定義
「常客」是 2 次以上還是 5 次以上？算最近 30 天還是全部？取消的算不算？「某一天」用台灣時間還是 UTC？同一個詞，老闆、行銷、工程師心裡的定義常常不一樣，數字對不上時大家會先懷疑程式。資深的做法是把定義寫在查詢旁邊的註解或文件裡，交付時附上幾筆可以人工核對的資料，請對方確認「這幾個人是不是你說的常客」。

步驟六：資料變多之前，要先補哪些索引？

系統上線一年後，預約和點數紀錄會變成幾十萬筆。回頭看上一步的查詢：查詢 4 用 member_id = 1 篩選；之後 API 常見的「某位會員的預約」「某位會員的點數明細」也一樣；刪除會員時，資料庫要檢查還有沒有預約參照他。這些都是依外鍵欄位找資料。主鍵和 UNIQUE 會自動建索引，但外鍵不會自動建索引（第 20 課）。沒有索引，每次依外鍵找資料都要把整張表掃一遍，表越大越慢。

查詢 1、5 則不一樣：它們先依 reserved_at 的時間範圍篩選預約，再用 cafe_tables.id、members.id 這兩個主鍵 JOIN 回去，主鍵本來就有索引。它們要變快，靠的是 reserved_at 的索引，這屬於第 27 課的索引設計；練習 4 先只處理外鍵。

練習 4：幫 reservations 和 point_transactions 的三個外鍵欄位，各建一個單欄索引。

建好之後，可以用第 21 課的 EXPLAIN 看查詢有沒有用到。不過現在資料只有十幾列，規劃器多半還是選 Seq Scan，這是正常的：資料少的時候全表掃描最快。索引是為一年後的資料量準備的，現在看不出差別。

索引顧好了速度。但回頭看需求第 3 點，還有一條規則，目前的 schema 有沒有守住，值得檢查一下。

上線前：還有哪條規則沒被擋住？

老闆說每筆預約佔用 2 小時，意思是同一張桌子的兩筆預約時間不能重疊。前面加的約束裡，有哪一條管得到這件事嗎？

思考題 2：老闆說「同一張桌子同一時段不能被預約兩次」。目前的 schema 有擋住這件事嗎？

✓ 這種「跨列」的規則，簡單的 CHECK 做不到。可以在後端下單時用交易加 SELECT … FOR UPDATE 檢查（第 18、19 課），或用 trigger（第 23 課）。PostgreSQL 還有更進階的 EXCLUDE 約束，可以直接宣告「同一張桌子的時間區間不能重疊」，有興趣可以查官方文件。

這條規則跟前面的約束不一樣。CHECK 檢查的是一列自己的資料，例如這一列的 party_size > 0；而「時段不能重疊」要拿新的這一列，去跟同一張桌子的其他預約比，是跨列的規則。這類規則要另外設計，上面解答裡列了幾種做法；在動手之前，至少要知道 schema 還有這個缺口，不要以為建好表就什麼都擋住了。

以後端下單時用交易加 FOR UPDATE 為例，要鎖的是「那張桌子」，不是既有的預約。兩個請求同時要訂 B1 14:00，如果只鎖 B1 現有的預約列，兩邊都鎖得到、查詢結果也都是「沒重疊」，接著各自 INSERT，就訂出兩筆重疊的預約：問題出在還沒寫進去的那筆新預約，根本鎖不到。正確的順序是在交易裡先 SELECT … FROM cafe_tables WHERE id = $1 FOR UPDATE 鎖住桌子那一列，讓同一張桌子的下單排隊一個一個來；拿到鎖之後再查有沒有重疊的預約，沒有才 INSERT，最後 COMMIT 放開鎖。不同桌子的下單鎖的是不同列，彼此不會互等。另一條路是 EXCLUDE 約束，由資料庫直接擋下重疊，說明放在課末的「補充與查表」。

這也說明了一件事：設計完成時很容易漏掉東西，靠記憶檢查不可靠。最後用一張清單把整個設計對一遍。

補充與查表

想再挑戰的話

下面幾題把這個專題往前推一步，會用到第 23、24 課的 trigger、View 和 RLS：

  • 寫一個 trigger，讓點數餘額不能變成負數（兌換時檢查 sum）。
  • 寫一個 trigger 或 CHECK 相關的機制，擋下「預約人數超過桌子可坐人數」。
  • 建一個 View member_balances，讓「每位會員目前點數」變成一句 SELECT * FROM member_balances。
  • 幫 reservations 開 RLS，讓會員只看得到自己的預約。

時段不能重疊：EXCLUDE 約束

UNIQUE 擋的是「兩列的值相等」，EXCLUDE 約束把「相等」換成你指定的運算子，例如「同一張桌子（=）而且時間範圍重疊（&&）的兩列不能同時存在」。這樣不管是哪個程式、哪條路徑寫入，資料庫都會擋下重疊的預約，不用靠後端記得上鎖。要用它，時間要存成範圍型別（例如 tstzrange），而且「桌子相等」這部分要靠 btree_gist 擴充才能放進同一個約束。實際寫法請先查 PostgreSQL 官方文件的 Exclusion Constraints 與 btree_gist 章節，並確認你用的環境（例如這頁的 PGlite）有沒有提供 btree_gist。

常見錯誤

  • 一開始就寫 CREATE TABLE：先找實體和關係、畫圖，比寫完再改 schema 省事得多。表有了資料之後再改，就要寫 migration、補舊資料。
  • 把可以算出來的值存起來：例如在 members 存「預約次數」，很快就會跟 reservations 對不上。需要快取時要想清楚怎麼保持同步。
  • 時間範圍用 BETWEEN 或 ::date：BETWEEN '2026-11-01' AND '2026-11-02' 會包含 11/2 00:00 整；用 >= 開始 AND < 結束 的半開區間最安全，也用得上索引。
  • 統計時忘了排除已取消的資料：每寫一個報表，都想一下 status 該不該過濾。
  • LEFT JOIN 之後用 count(*)：沒有資料的那一列也會被算成 1，要用 count(右表.id)。

小結

  • 設計資料庫的順序：需求 → 實體與關係 → ER 圖 → CREATE TABLE（含約束）→ 資料 → 查詢 → 索引。越前面發現的問題，改起來越便宜。
  • 找實體看名詞，但要分辨「獨立的東西」和「描述別的東西的欄位」；一對多的外鍵放在多的那一邊。
  • 需要保留歷史的資料（點數、金流）存成一筆一筆的明細，目前狀態用查詢算出來。
  • 寫了約束要放資料測過；跨列的規則（例如時段不能重疊）約束管不到，要另外設計。
  • 每個查詢都對照需求檢查：要不要排除取消的？沒有資料的要不要出現？時間是哪個時區？排序是什麼？
  • 外鍵不會自動建索引，資料變多之前補上；上線前用檢查清單確認主鍵、外鍵、約束、型別、交易、索引、migration、權限、後端連線都有照顧到。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 5：一支 migration 包在 BEGIN … COMMIT 裡，依序是：加 points 欄位、UPDATE 補既有會員的點數、SET NOT NULL。最後一句因為還有一列是 NULL 而失敗，資料庫現在是什麼狀態？

✓ PostgreSQL 的 DDL 也能放進交易，第三句失敗，前兩句一起取消，資料庫不會停在改到一半。b 錯在那是 MySQL 的行為，PostgreSQL 的 ALTER TABLE 一樣受交易控制。（第 22 課）

練習 6：orders 開了 RLS，policy 用 app 的 role 測過沒問題；上線時 API 改用建表的 migration 帳號連線，結果每位顧客都看得到全部訂單。為什麼？

✓ 超級使用者永遠繞過 RLS，表的擁有者預設也繞過（加 FORCE 才受限），policy 寫得再對也不會檢查。API 用只有日常讀寫權限的 role 連線，建表、改欄位的權限只給 migration 帳號。b 錯在問題不在 policy 套用到誰，擁有者根本不經過 policy 檢查。（第 24 課）

練習 7：想讓商品每次被修改就自動更新 updated_at，同事寫了下面這個 trigger。哪裡會出事？

CREATE FUNCTION touch_updated_at() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE products SET updated_at = now() WHERE id = NEW.id;
  RETURN NEW;
END $$;
CREATE TRIGGER products_touch AFTER UPDATE ON products
  FOR EACH ROW EXECUTE FUNCTION touch_updated_at();

✓ AFTER UPDATE 裡又 UPDATE 同一張表，每次都再觸發自己。要改當前這一列，用 BEFORE UPDATE trigger 直接設 NEW.updated_at := now() 再 RETURN NEW。a 錯在 UPDATE 的 AFTER trigger 也讀得到 NEW（改完的列）和 OLD。（第 23 課）

練習 8：起司蛋糕的庫存變成 -2。查下去發現 API 下單時會檢查並扣庫存，但店長從後台工具直接新增了 order_items。怎麼改最能避免再發生？

✓ 保護資料正確性、不能被繞過的規則放資料庫：不管從哪條路徑寫進來都會執行，庫存不夠時同一個交易的明細也一起失敗。a 錯在只要有一條路徑忘了呼叫就被繞過，下一個新工具或手動 SQL 又會出事。（第 23 課）

練習 9：後端用 connection pool。登入的請求先在借到的連線上執行 set_config('app.user_id', 使用者id, false) 再查訂單，未登入的請求不設定。orders 有依 app.user_id 過濾的 RLS，偶爾卻有未登入的訪客看到別人的訂單，為什麼？

✓ 第三個參數 false 讓設定在整條連線期間都有效，而 pool 會把同一條連線借給下一個請求。改成在交易裡用 set_config(…, true)，交易結束就失效。b 錯在 USING 正是管查詢看得到哪些列，WITH CHECK 管的是寫進去的新資料。（第 24、25 課）

練習 10：「我的訂單」讓使用者切換新到舊、舊到新。customer_id 已經用參數傳了，這段程式哪裡會出事？

const dir = req.query.dir   // 'ASC' 或 'DESC'
const { rows } = await pool.query(
  `SELECT id, total FROM orders
   WHERE customer_id = $1 ORDER BY ordered_at ${dir}`,
  [customerId]
)

✓ 任何從請求來的值拼進 SQL 字串都是 SQL injection，攻擊者直接呼叫 API 就能塞任何東西。排序方向、表名、欄位名無法參數化，只能用白名單比對成固定的值。d 錯在參數只能代表「值」，ORDER BY ordered_at $2 會是語法錯誤。（第 25 課）

練習 11：下單 API 這樣寫交易。上線後偶爾因為庫存不足走到 ROLLBACK，幾天後整個 API 卡住，每個請求都在等連線。哪裡會出事？

const client = await pool.connect()
try {
  await client.query('BEGIN')
  await client.query('UPDATE products SET stock = stock - 1 WHERE id = $1', [8])
  await client.query('COMMIT')
  client.release()
} catch (err) {
  await client.query('ROLLBACK')
  throw err
}

✓ 只有成功時才 release()，每出錯一次 pool 就少一條連線，借光之後所有請求都在等。release() 放在 finally 裡，成功、失敗都會還。c 錯在漏掉的連線不會回來，調大 max 只是晚幾天卡住。（第 25 課）

練習 12：後台訂單列表上線半年後越來越慢，本機卻秒開。查詢 log 顯示打開一次列表送出 201 句 SQL，每句都在 1 毫秒內。怎麼修？

✓ 這是 N+1：一句查 200 筆訂單，再每筆查一次顧客，句數跟著資料筆數一起長，每句都多一次來回。改成固定的一兩句就好；ORM 用 Prisma 的 include。b 錯在每句已經很快了，慢的是句數，不是單句。（第 25 課）
