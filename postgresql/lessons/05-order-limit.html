階段 1：CRUD（增查改刪） · 第 5 課

排序與分頁：ORDER BY、LIMIT

這一課你要替咖啡店後台寫列表頁背後的 SQL。前端已經做好兩個畫面：商品列表有「依價格由高到低」的排序選單，會員列表一頁 5 人、底下有頁碼可以翻。前端送來的請求長得像 GET /products?sort=price&order=desc 和 GET /customers?page=3&pageSize=5，後端要把它們換成 SQL。同時客服轉來一張舊單：「重新整理後順序會跳，翻頁時同一筆資料在兩頁都出現。」這一課做完，你會寫出排序和分頁都正確的查詢，也會知道那張客服單的原因。

這課會用到：
  • 第 4 課的 WHERE（只留下條件成立的列），例如 WHERE is_available 只拿上架中的商品。
  • 第 4 課的別名（AS member_price 幫查詢當場算出的值取名字）。
  • 第 4 課的 NULL（「不知道」，沒填的城市就是 NULL）。
這課的路線：
  1. 沒寫 ORDER BY 時順序是誰決定的：客服單上「順序會跳」的原因。
  2. ORDER BY 與 LIMIT：商品依價格由高到低、只拿前幾筆，這就是排序選單的最小答案。
  3. 價格一樣時誰先、沒填的值排哪裡：多欄位排序、NULL 的位置，以及前端傳來的排序欄位怎麼安全地接。
  4. OFFSET 分頁：?page=3&pageSize=5 怎麼換成 SQL，以及「同一筆在兩頁都出現」的原因與修法。
  5. 翻到很後面為什麼變慢、子句要照什麼順序寫：把查詢完整組起來。

沒寫 ORDER BY，列表的順序是誰決定的？

先處理客服單的前半句「重新整理後順序會跳」。最早的商品列表 API 只寫了 SELECT，沒有指定順序。查一次看看，執行後看 id 的順序：

看起來照 id 排得整整齊齊，開發時大家就以為「資料庫預設照 id 排」。其實不是。表的資料存在磁碟上，沒有指定順序時，資料庫怎麼讀方便就怎麼回傳；最常見的讀法是從頭到尾掃一遍，所以你看到的是資料在磁碟上擺放的順序。這張表剛建好、資料照 id 依序寫入，擺放順序剛好跟 id 一樣，結果才「看起來」排好了。

擺放順序會變。下面這格先把美式咖啡的價格「改成跟原本一樣」，等於什麼都沒改（UPDATE 是第 6 課的內容，這裡先借用），再用同一句查一次，看 id 1 在哪：

id 1 跑到最後面了。原因是 PostgreSQL 修改一列時，不是在原位置改寫，而是把修改後的新版本寫到別的位置，舊版本之後才清掉。從頭掃到尾的讀法會在最後才遇到新版本，美式咖啡就排到最後。內容完全沒變，順序卻變了。

正式環境的資料會一直被修改，資料多、有索引、多人同時寫入時，資料庫選擇的讀法和擺放位置都會變，順序變動得更頻繁。這就是客服單前半句的原因：查詢沒有指定順序，每次回傳的順序是資料庫當下方便的順序。開發時資料少、沒被修改過，所以一直沒發現。

規則：只要你在乎順序，就一定要寫 ORDER BY。SQL 標準和 PostgreSQL 都只保證「有寫 ORDER BY 的部分」照順序，其他一律不保證。
💡 實務上：每個列表 API 都要有明確的預設排序
Code review 時看到有 LIMIT 卻沒有 ORDER BY 的查詢，就直接標出來。API 文件也要寫清楚預設排序（例如「依建立時間新到舊」），前端才不會自己猜。開場那張客服單，就是兩邊都沒做到的結果。

所以修正的第一步，是在查詢裡明確告訴資料庫要照什麼排。

依價格由高到低、只拿前幾筆：ORDER BY 與 LIMIT

上一節的結論是要自己寫 ORDER BY。先接排序選單的「依價格由高到低」。ORDER BY 寫在 WHERE 後面，接著寫要依哪個欄位排、往哪個方向排：

  • ASC（ascending，遞增）：由小到大。這是預設方向，不寫就是 ASC。
  • DESC（descending，遞減）：由大到小。

商品列表只顯示上架中的商品，所以保留第 4 課的 WHERE is_available，再加上排序。執行後看 price 欄是不是由大到小：

資料庫先用 WHERE 篩掉下架的商品，再把剩下的列依 price 由大到小排好。換成 ORDER BY price（或 ORDER BY price ASC）就是由便宜到貴。文字欄位也能排序，例如 ORDER BY name，但中文排出來的順序不是筆畫也不是注音，原因見課末「補充與查表」。

排好之後，常見的下一個需求是「只要前幾筆」：後台首頁的「精選商品」只放最貴的 3 樣。LIMIT n 的意思是「最多回傳 n 筆」，它作用在排好的結果上，所以「先排序、再取前 3 筆」就是「最貴的 3 樣」。執行後看是不是只剩 3 列：

這格沒有寫 WHERE，所以下架的季節特調、冰滴咖啡也被算進去了。真的要放上首頁，要加回 WHERE is_available，練習 2 會讓你寫這種查詢。

反過來想：如果拿掉 ORDER BY 只留 LIMIT 3，資料庫會照上一節說的「當下方便的順序」讀，讀到 3 筆就停。這 3 筆是哪 3 筆沒有任何保證，可能今天是 id 1、2、3，資料被改過後就換成別的。LIMIT 一定要搭配 ORDER BY，否則「前 3 筆」就是「隨便 3 筆」。

到這裡，排序選單的最小答案已經有了：ORDER BY price DESC。但仔細看上面上架商品的結果，Espresso Tonic 和鮪魚三明治都是 140 元，焦糖瑪奇朵和抹茶拿鐵都是 130 元。價格一樣的商品，誰排前面？

價格一樣時誰先？多欄位排序與 NULL 的位置

只寫 ORDER BY price DESC 時，資料庫只保證價格高的在前面；同樣 140 元的兩個商品之間沒有規定順序，回到了第一節的情況：誰先誰後由資料庫當下決定，可能每次不同。要讓它們有固定的先後，就再給一個比較的依據。

多個欄位排序：第一個比不出來，再比第二個

ORDER BY 可以寫好幾個欄位，用逗號隔開。資料庫先依第一個欄位排；第一個欄位相同的，再依第二個欄位排；還是相同，再看第三個，以此類推。每個欄位可以各自指定方向。

後台的商品管理頁通常想「依分類分組，同分類裡貴的在前」，同價格再依 id 固定下來。執行後看「咖啡」分類裡，同樣 110 元的拿鐵和卡布奇諾誰在前：

結果由上到下可以這樣讀：

  • 分類照 category 由小到大排（沒寫方向，就是 ASC）。
  • 同一個分類裡，price DESC 讓貴的在前。
  • 拿鐵（id 2）和卡布奇諾（id 3）都是咖啡、都是 110 元，最後由 id 決定，拿鐵在前。

注意 DESC 只作用在它前面那一個欄位。ORDER BY category, price DESC 是「分類由小到大、價格由大到小」，不是兩個都由大到小。想要兩個都由大到小，要寫 ORDER BY category DESC, price DESC。

最後一個欄位 id 是主鍵，每一列都不一樣，所以加上它之後，任何兩列都比得出先後，整個排序結果每次都一樣。這件事在下一節分頁時會變成必要條件。

沒填的值排在哪裡：NULLS FIRST、NULLS LAST

上面的結果裡還有一個現象：季節特調和熱可可沒有分類，category 是 NULL，它們排在最後。PostgreSQL 排序時把 NULL 當成比任何值都大，所以：

  • ASC（由小到大）時，NULL 在最後。
  • DESC（由大到小）時，NULL 在最前面。

第二種情況在列表頁常常不是你要的。換到會員列表看：有兩位會員沒填城市。如果依城市 DESC 排，這兩位會被排到第一頁最上面，畫面一打開就是兩個空白欄位。想自己決定 NULL 的位置，就在方向後面加 NULLS FIRST（NULL 放最前）或 NULLS LAST（NULL 放最後）。執行後看沒填城市的吳家豪和鄭佩珊在哪裡：

他們被放到最後了。把 NULLS LAST 刪掉再執行一次，會看到他們跑回最前面。依某個可能是空的欄位排序時（例如最後登入時間，從沒登入過的會員是 NULL），通常希望 NULL 放最後，就加上 NULLS LAST。反過來，店員要先補齊資料時，會希望沒填的排最前面，這就是練習 5 的情境。

💡 實務上：讓前端選排序欄位時要用白名單
回到開場的排序選單：前端會傳 ?sort=price&order=desc。上一課提到的 $1 參數只能帶「值」（例如價格、關鍵字），不能帶欄位名稱，所以很多人會直接把 sort 字串拼進 SQL，這就留下了 SQL injection 的洞。正確做法是後端準備一份對照表，例如 { price: 'price', newest: 'created_at' }，只接受表裡有的 key，方向也只接受 asc／desc，其他一律用預設值。

排序選單的 SQL 完成了。接下來是會員列表的頁碼：第 1 頁拿前 5 人可以用 LIMIT，但第 2 頁、第 3 頁要怎麼拿？

第 2 頁怎麼拿？用 OFFSET 分頁

LIMIT 5 只能拿到「排好之後的前 5 筆」。第 2 頁要的是第 6～10 筆，也就是「先跳過前 5 筆，再拿 5 筆」。OFFSET n 就是「先跳過 n 筆」，跟 LIMIT 一起用，就能拿到任何一頁。下圖是依 id 排好的 12 位會員，一頁 5 筆時每一頁的寫法：

規律是 OFFSET =（頁碼 − 1）× 每頁筆數：第 1 頁跳過 0 筆，第 2 頁跳過 5 筆，第 3 頁跳過 10 筆。執行下面這格，看拿到的是不是 id 6～10：

所以前端傳來 ?page=3&pageSize=5，後端算出 OFFSET = (3 − 1) × 5 = 10，送出 LIMIT 5 OFFSET 10。第 3 頁只剩 id 11、12 兩人，因為 LIMIT 是「最多」幾筆，不足時有幾筆就回幾筆，不會出錯。像 Strapi 這類後台框架，pagination[page]、pagination[pageSize] 背後就是這樣轉的。

同一筆在兩頁都出現：分頁的排序要「唯一」

現在可以回答客服單的後半句「翻頁時同一筆資料在兩頁都出現」。關鍵在前面「價格一樣時誰先？」那一節提過的問題：價格一樣的列，先後沒有規定。

假設商品列表依 ORDER BY price 由便宜到貴、每頁 4 筆。排好之後第 4、5 名都是 90 元：Espresso 和伯爵紅茶。第 1 頁的最後一筆和第 2 頁的第一筆，就要從這兩個裡決定。問題是翻頁時前端會送出兩次獨立的查詢：第 1 頁的查詢和第 2 頁的查詢各自排序一次，資料庫在兩次裡對這兩個 90 元商品的先後可以不一樣。兩次查詢的 OFFSET／LIMIT 不同，資料庫可能選用不同的方式排序；對同分的列，它只保證不違反你寫的 ORDER BY，不保證兩次的先後相同。而且兩次點擊之間如果資料被修改（第一節的情況），擺放順序也會跟著變。如果第 1 次把 Espresso 排在第 4 名、第 2 次把伯爵紅茶排在第 4 名，結果就是：

  • 第 1 頁的最後一筆是 Espresso。
  • 第 2 頁跳過前 4 筆，跳掉的是伯爵紅茶，第一筆又是 Espresso。
  • 伯爵紅茶在哪一頁都看不到。

重複和遺漏是同一件事的兩面。修法是讓每一列的位置都確定：分頁時，ORDER BY 最後加上主鍵，例如 ORDER BY price, id。主鍵不會重複，任何兩列都比得出先後，每次查詢排出來的順序就一模一樣，跳過幾筆、拿哪幾筆也就固定了。實際列表每頁 5 筆，下面是加上 id 之後的第 2 頁；你也可以把它改成 LIMIT 4 OFFSET 4，看 Espresso 和伯爵紅茶照 id 固定分在第 1、2 頁。

OFFSET 分頁到這裡已經正確了。但它還有一個在資料少時看不出來的成本：頁碼越後面，查詢越慢。

翻到很後面的頁，為什麼越來越慢？

直覺上 OFFSET 10000 像是「直接跳到第 10001 筆」，但資料庫沒辦法直接跳。它不知道排好之後的第 10001 筆是誰，只能把前面的列排好、一筆一筆數過去、再丟掉，數完 10000 筆才開始拿你要的那 5 筆。被丟掉的 10000 筆一樣要讀、一樣要排，只是不回傳而已。

所以 OFFSET 的成本跟頁碼成正比：幾百萬筆資料時，第 1 頁很快，第 5000 頁可能要好幾秒。咖啡店的會員只有 12 人感覺不到，資料長大後才會出現。

常見的替代做法是「記住上一頁最後一筆，從它後面接著拿」：前端把上一頁最後一筆的 id 傳回來，後端寫成 WHERE id > 上一頁最後的 id ORDER BY id LIMIT 5。它不用數過前面的列，所以不管翻到多後面都差不多快。為什麼這樣比較快，要等第 20 課講索引時才說得清楚。這種做法的代價是只能「下一頁」，沒辦法直接跳到第 8 頁。

💡 實務上：先看畫面需求，再決定分頁方式
後台管理頁要「跳到第 8 頁」、顯示總頁數，用 LIMIT／OFFSET 最直覺，資料量不大時完全夠用。手機 App 的無限捲動、通知或動態牆只需要「再載入更多」，就適合「記住最後一筆」的做法，資料一直新增時也比較不會重複或漏掉。不管哪一種，後端都要限制 pageSize 上限（例如最多 100），不然有人傳 ?pageSize=1000000 就等於一次撈整張表。跟 PM 討論時，可以先問「使用者真的需要跳頁嗎？」，答案常常決定了做法。

排序、取前幾筆、分頁都有了。最後把它們組成一句完整的查詢，並弄清楚子句的順序。

把查詢組起來：子句要照什麼順序寫？

到目前為止學過的子句，寫的時候一定要照這個順序，順序錯了會出現 syntax error：

SELECT 欄位
FROM 表
WHERE 條件
ORDER BY 排序
LIMIT 筆數 OFFSET 跳過幾筆;

例如商品列表「上架中、依價格由高到低、同價格依 id、第 2 頁」就是 SELECT name, price FROM products WHERE is_available ORDER BY price DESC, id LIMIT 5 OFFSET 5;。

不過資料庫處理這些子句的順序跟寫的順序不一樣。照邏輯上的步驟，它是：

  1. FROM：找到要查的表。
  2. WHERE：一列一列判斷，只留下條件成立的列。
  3. SELECT：算出每一列要回傳的欄位，包括 price * 0.9 這種運算式和別名。
  4. ORDER BY：把結果排好。
  5. LIMIT／OFFSET：從排好的結果裡跳過幾筆、拿幾筆。

這個順序解釋了這一課的幾條規則。LIMIT 在 ORDER BY 之後，所以「先排序再取前 3 筆」才會是「最貴的 3 樣」。ORDER BY 在 SELECT 之後，所以它看得到 SELECT 取的別名，可以直接用：

WHERE 在 SELECT 之前，那時別名還不存在，所以第 4 課說 WHERE 不能用別名。第 7 課加上 GROUP BY 之後，會把完整的執行順序畫出來。

補充與查表

  • 中文為什麼不是照筆畫或注音排：文字怎麼比大小、怎麼排序，由排序規則（collation）決定。這個頁面的資料庫用的是最單純的 C 排序規則：英文照字母、中文照 Unicode 編碼排，不是筆畫也不是注音，所以上面的分類排成咖啡、甜點、茶、輕食。正式環境的排序規則依建立資料庫時的設定而定，第 20 課會再談它對索引的影響。

練習

這一課的練習會檢查順序，排錯也算錯。

練習 1：列出所有商品的 name、price，價格由高到低；價格相同的，依 id 由小到大。

練習 2：找出上架中最便宜的 3 個商品，顯示 name、price，便宜的在前。

練習 3：找出最新的 5 筆已付款（status = 'paid'）訂單，顯示 id、ordered_at、total，最新的在前。

練習 4：會員列表每頁 5 人、依 id 由小到大。請查出第 3 頁，顯示 id、name。

練習 5：店員要先補齊會員的城市資料。列出所有顧客的 name、city，依 city 由小到大，但city 是 NULL 的排最前面；city 相同的依 id 由小到大。

練習 6：商品依 category 由小到大、同分類價格由高到低、同價格依 id 由小到大排序，每頁 5 筆。請查出第 2 頁，顯示 name、category、price。

練習 7：SELECT * FROM products LIMIT 3; 會回傳哪 3 筆？

✓ 沒有 ORDER BY 時，資料庫用它覺得最方便的順序回傳。剛建好的表常常「看起來」照 id 排，但只要資料被修改過就可能不一樣。

練習 8：每頁 20 筆，要查第 4 頁，OFFSET 應該是多少？

✓（4 − 1）× 20 = 60：跳過前 3 頁共 60 筆，取第 61～80 筆。

常見錯誤

  • 以為不寫 ORDER BY 就是照 id 排：小資料時看起來對，上線後資料一多、一被修改就亂掉。在乎順序就寫 ORDER BY。
  • 分頁沒有唯一的排序：ORDER BY price 分頁時，同價格的列在兩次查詢裡先後可能不同，會重複或漏掉資料。最後加上 id。
  • 以為 DESC 作用在所有欄位：ORDER BY a, b DESC 只有 b 是由大到小。
  • OFFSET 算錯：第 1 頁是 OFFSET 0，不是 OFFSET 1（那會跳過第一筆）。
  • 子句順序寫錯：ORDER BY 寫在 WHERE 前面、或 LIMIT 寫在 ORDER BY 前面，都會出現 syntax error。

小結

  • 沒有 ORDER BY 就沒有保證的順序，資料被修改後順序就可能變，這是「重新整理後順序會跳」的原因。
  • ORDER BY 欄位 [ASC|DESC] [NULLS FIRST|LAST], …：多欄位依序比，方向只作用在前面那一個欄位；NULL 預設當成最大值。
  • LIMIT n 是最多 n 筆，一定要搭配 ORDER BY。
  • LIMIT n OFFSET m：OFFSET =（頁碼 − 1）× 每頁筆數；分頁的排序最後加主鍵讓它唯一，才不會「同一筆在兩頁都出現」。
  • OFFSET 越大越慢，因為前面的列還是要排好、數過一遍；只需要「下一頁」時可以改成記住最後一筆。
  • 寫的順序是 SELECT → FROM → WHERE → ORDER BY → LIMIT；處理的順序是 FROM → WHERE → SELECT → ORDER BY → LIMIT，所以 ORDER BY 能用別名。
