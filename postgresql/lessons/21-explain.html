階段 6：效能 · 第 21 課

EXPLAIN：讀懂查詢計畫

客服回報：咖啡店後台的「顧客訂單」頁，點開一位顧客要轉好幾秒。這一頁背後的查詢很單純，就是「顧客 42 的所有訂單」，再配上顧客姓名。上一課你學會建索引，也看過建了索引之後 Execution Time 變小。但現在的狀況反過來：你手上只有一句慢的查詢，不知道它慢在哪裡，也不知道該建什麼索引，甚至不確定問題是不是出在索引。

猜是沒有用的。這一課要學的是直接問資料庫：「你打算怎麼執行這句查詢？」PostgreSQL 回答這個問題的指令叫 EXPLAIN。整課都繞著這個慢頁面走：先看懂資料庫的回答，找出慢的原因並修好，再確認修好之後的數字是真的，最後整理成下次接到「這支 API 很慢」時照著走的步驟。

這課會用到：
  • 第 20 課的索引：另外存的一份排好序的目錄，讓資料庫直接跳到要的列；主鍵會自動建索引，外鍵不會。
  • 第 18 課的 BEGIN … ROLLBACK：在交易裡做的修改，ROLLBACK 之後全部取消。
這課的路線：
  1. 資料庫怎麼決定執行方式、第一個 EXPLAIN：顧客 42 的訂單為什麼慢，輸出裡的 cost、rows 代表什麼（開場問題的最小答案）。
  2. 多層的計畫怎麼讀、建了索引之後計畫變成什麼：計畫是一棵樹，Seq Scan、Index Scan 這些掃描方式各代表什麼。
  3. 配上顧客姓名時兩張表怎麼配對：JOIN 的三種做法，規劃器什麼時候選哪一種。
  4. 估計準不準：用 EXPLAIN ANALYZE 看實際數字，估計和實際差很多時用 ANALYZE 修正。
  5. 把整個過程整理成檢查步驟，並在 PR 裡證明你真的修好了。

同一句 SQL，資料庫怎麼決定怎麼執行？

要問資料庫「你打算怎麼做」，得先知道它為什麼會有「打算」。你寫的 SQL 只描述要什麼：「orders 裡 customer_id = 42 的列」。它沒有說怎麼拿：要從第一列讀到最後一列一個個檢查？還是有目錄可以翻、直接跳到那幾列？兩張表要配對時，先讀哪一張？這些「怎麼拿」的決定，由 PostgreSQL 裡一個叫查詢規劃器（planner）的元件負責。

規劃器收到一句查詢後，會列出好幾種可行的做法，替每一種估算成本，挑估計最便宜的那一種。被挑中的那一套具體步驟，叫做查詢計畫（query plan）。同一句 SQL，結果永遠一樣，但不同的計畫花的時間可以差上百倍，所以查詢慢的時候，幾乎都是在問「它選了哪個計畫、為什麼選這個」。

用咖啡店來想：店長接到一張「10 杯拿鐵外送到 3 樓」的單，可以一杯一杯做、做一杯送一杯，也可以 10 杯一起做、一次送上去。結果一樣，花的時間差很多。店長會依照「現在有幾台咖啡機、幾個店員」決定怎麼做。規劃器做的就是這件事，而它手上的「現況」叫統計資訊：每張表大約有幾列、每一欄的值大致怎麼分布（例如 status 有六成是 paid）。規劃器不會為了做決定而把整張表讀一遍，它只看這份事先算好的統計資訊來估計，所以估計有可能不準，這一點到這課後半會變成關鍵。

知道了計畫是規劃器挑出來的，下一步就是請它把挑中的計畫印出來看。

第一個 EXPLAIN：顧客 42 的訂單為什麼慢？

在查詢前面加上 EXPLAIN，PostgreSQL 就不回傳資料，而是回傳它打算用的計畫。這頁的資料：customers（5000 位）、orders（10 萬筆），除了主鍵以外還沒有任何索引，跟慢頁面的狀況一樣。執行這一格，看回傳的那一行開頭寫了什麼做法：

輸出大概長這樣：

Seq Scan on orders  (cost=0.00..1986.00 rows=20 width=26)
  Filter: (customer_id = 42)

一行一行拆開看：

片段意思
Seq Scan on orders這一步的做法：對 orders 做全表掃描
cost=0.00..1986.00估計成本。前面是「吐出第一列之前」的成本，後面是「全部做完」的成本。單位是規劃器自己的相對單位，不是毫秒，只拿來互相比較
rows=20估計這一步會輸出幾列
width=26估計每一列平均幾個 bytes，通常不用管
Filter: …每讀一列就檢查這個條件，不符合就丟掉

把這幾個片段合起來，答案已經出來了：為了找出估計只有 20 列的訂單，資料庫打算把 orders 的 10 萬列從頭讀到尾，每讀一列就用 Filter 檢查一次 customer_id = 42，不符合的丟掉。99,980 列白讀了。原因也很清楚：customer_id 上沒有索引，資料庫沒有目錄可翻，只能全部讀。這就是慢頁面的最小答案：缺一個 customer_id 的索引。

關於 cost 要多說一句：1986 不代表 1986 毫秒，也不代表任何時間單位。它是規劃器用來比較「做法 A 比做法 B 貴多少」的分數。單看一個 cost 沒有意義，要拿兩個計畫的 cost 互相比，等一下建了索引，你就會看到同一句查詢的 cost 掉了一大截。

另一件要知道的事：EXPLAIN 只規劃、不執行。它不會真的去讀那 10 萬列，所以就算是要跑好幾分鐘的查詢，也能馬上看到計畫。這讓它可以安心地拿來看任何查詢。

💡 實務上：先拿到「真正送出的 SQL」，再 EXPLAIN
工作中常見的情況就像這課的開場：客服回報「咖啡店後台的訂單列表要轉好幾秒」，或監控顯示某支 API 變慢。如果你用 ORM，第一步是打開它的 SQL log（或從慢查詢紀錄）拿到實際送出的那句 SQL 和參數，因為 ORM 產生的查詢常常跟你想像的不一樣。在那句前面加上 EXPLAIN 到資料庫執行，問題才有具體的討論對象。資深工程師在 code review 看到新的列表或搜尋查詢時，也會順手 EXPLAIN 一次，而不是等上線後才發現。

不過後台那一頁不只查 orders，還要配上顧客姓名，也就是要 JOIN customers。一旦查詢牽涉兩張表，計畫就不再只有一行。

查詢牽涉兩張表時，多層的計畫怎麼讀？

查詢一複雜，規劃器就得把工作拆成好幾步：先掃 orders、再掃 customers、把兩邊配對、最後排序。每一步在計畫裡是一行，叫做一個節點（node）。節點之間有上下關係：下層節點把結果交給上層節點繼續處理，所以整個計畫是一棵樹。文字輸出用縮排和 -> 表示這棵樹，讀法是：縮排最深的先做，結果往上交給外層。

下圖用的是「全部訂單配上顧客姓名、再排序」這句查詢的計畫，不是只查顧客 42 的慢頁面。選它是因為它層數多，掃描、配對、排序都有，適合練習讀樹；只查顧客 42 時計畫長什麼樣，到後面「兩張表怎麼配對」那一節再看。圖的左邊是計畫文字，右邊是它實際的執行順序：

照圖上的編號讀一次：最內層的兩個掃描先把 orders 和 customers 的列讀出來；Hash 把 customers 整理成方便查找的形式；Hash Join 拿兩邊的結果配對；最外層的 Sort 拿到配對好的列，排序後輸出。第一行的 Sort 雖然寫在最上面，卻是最後才完成的那一步。直覺上很容易把第一行當成第一步，這是讀計畫最常見的誤會。

每一層的 cost 都包含它底下所有子節點的成本。所以最上面那一行的總成本，就是整句查詢的估計成本；要找出貴在哪裡，就往下層看，哪個子節點的 cost 佔了大部分，問題就在那裡。

這棵樹最底下的葉子，永遠是「從表裡把資料拿出來」的那一步，也就是剛才看到的 Seq Scan。修慢頁面就是要換掉這一步。那麼建了索引之後，這一步會變成什麼？

建了索引之後，計畫會換成哪一種掃描？

從表裡把資料拿出來，叫掃描（scan）。Seq Scan 是其中一種，有了索引之後，規劃器會多出幾種選擇。先看兩個實例，再整理成表。

第一個實例：用主鍵查一筆訂單。主鍵本來就有索引，這是最典型的 Index Scan，執行後看第一行的做法名稱：

Index Scan 的做法是：先在索引裡找到 id = 500 這一列存在表裡的哪個位置，再到表裡那個位置把整列讀出來。索引裡只存欄位值和位置，不存整列資料，所以「回到表裡拿整列」這一步省不掉，這個動作叫回表。查一筆的時候，回表一次就結束，非常快。

第二個實例才是慢頁面的修法：幫 customer_id 建索引，再看同一句「顧客 42 的訂單」。執行後看第一行的做法名稱，和最右邊的總成本：

總成本從 1986 降到 70 多，計畫換掉了，慢頁面的主因解決了。但這次出現的不是 Index Scan，而是 Bitmap Heap Scan，裡面包著 Bitmap Index Scan on orders_customer_id_idx。原因在於顧客 42 有 20 筆訂單，散落在表的各處。如果用 Index Scan，每找到一筆就回表一次，在表裡跳來跳去 20 次。規劃器判斷「先用索引把 20 個位置全部收集起來、記成一張地圖，再照表的存放順序一次讀回來」比較划算，這就是 Bitmap 的做法（底下的 Bitmap Index Scan 負責收集位置，上面的 Bitmap Heap Scan 負責回表讀資料）。

把目前看過的掃描方式整理起來，加上下面馬上要看的第四種：

名稱做法什麼時候出現
Seq Scan從頭到尾讀整張表沒有可用的索引，或要讀大部分的列
Index Scan在索引裡找到位置，一列一列回表裡拿資料只要少數幾列，例如用主鍵查一筆
Index Only Scan盡量只讀索引；只有還沒被 VACUUM 標記為「全部可見」的資料頁才回表確認（計畫裡的 Heap Fetches）需要的欄位全部都在索引裡
Bitmap Heap Scan
配合 Bitmap Index Scan		先用索引把所有符合的位置記成一張「地圖」，再照表的存放順序一次讀回來符合的列不只幾筆、又不到大部分，介於中間

這張表的右欄說明了一件事：掃描方式不是「有索引就用索引」，而是看要拿的列佔整張表多少。拿一筆用 Index Scan，拿幾十筆用 Bitmap Heap Scan，要拿大半張表時，就算有索引，Seq Scan 從頭讀反而最快，因為一筆筆回表的成本會超過直接讀完整張表。

連表都不用碰：Index Only Scan

前面的掃描都要回表，因為查詢要的欄位（SELECT *）不全在索引裡。慢頁面要顯示訂單的每個欄位，需要整列資料，所以一定得回表。但不是每個查詢都要整列：假設後台報表只要顯示「前 100 位顧客總共有幾筆訂單」，需要的只有 customer_id 這個欄位，而它就在剛建的索引裡。答案在索引裡就全部有了，理論上連表都不用碰，這就是 Index Only Scan。慢頁面的查詢用不上它，所以這裡換一個例子來看。

實際上有一個前提。PostgreSQL 的表存在一個個固定大小的區塊裡，這種區塊叫資料頁（page）。同一列資料可能有舊版本和新版本並存（UPDATE、DELETE 之後，舊版本會先留在表裡，直到 VACUUM 清理；細節在第 30 課 MVCC），而索引本身不記錄「這一列現在對誰看得見」。所以資料庫只能在確定某個資料頁裡的列「對所有人都看得見」時，才跳過回表。這份「哪些資料頁全部可見」的紀錄，由 VACUUM 維護。VACUUM 是 PostgreSQL 的清理指令，正式環境會由一個叫 autovacuum 的背景程序自動執行；這頁剛建好資料，所以先手動跑一次（VACUUM 不能跟其他句子一起執行，所以單獨放一格）：

回到慢頁面：計畫從 Seq Scan 換成 Bitmap Heap Scan、cost 從 1986 掉到 70 多，你就有證據說「是缺索引」。反過來，如果建了索引，計畫還是 Seq Scan，不要急著再建一個，先問兩個問題：這句查詢是不是要拿大半張表（那 Seq Scan 本來就對）？查詢有沒有對欄位套函式，讓索引對不上（第 20 課）？只有在「大表、只要少數幾列、卻在 Seq Scan」時，才是真的有問題。

葉子節點的掃描修好了，但慢頁面還要配上顧客姓名。兩邊的列都拿到之後，上一層要把它們配對起來，這一步同樣有好幾種做法可以選。

配上顧客姓名時，兩張表怎麼配對？

JOIN 的意思是：把 orders 的每一列，跟 customers 裡 id 相同的那一列接在一起。規劃器有三種做法可以選，名字會出現在計畫的 JOIN 那一層。用「把訂單單據和會員卡配對」來想：

名稱白話適合
Nested Loop拿起一張訂單，去找對應的會員卡；再拿下一張……兩層迴圈外層只有少數幾列，內層有索引可以快速找
Hash Join先把會員卡全部放進一個依編號分格的收納盒（hash 表），再把訂單一張張拿去對應的格子找兩邊都很多列、沒有事先排好序，最常見
Merge Join兩疊都先按會員編號排好，像拉拉鍊一樣同時往下對兩邊都已經排好序（例如都有索引），或查詢本來就要排序

三種做法的差別在於「外層有幾列」和「資料是不是已經排好」。Nested Loop 是兩層迴圈：外層每一列，內層都要找一次。外層只有 1 列時，內層用主鍵索引找一次就結束，比什麼都快；外層有 10 萬列時，內層就要找 10 萬次。Hash Join 先花一次功夫把一邊整理成 hash 表，之後另一邊每一列都能直接找到對應的格子，適合兩邊都多。Merge Join 要求兩邊都照 JOIN 的欄位排好序，排好之後一路往下對就好，如果資料本來就有序（從索引讀出來），或查詢本來就要排序，它就划算。

同樣是 orders JOIN customers，條件不同，規劃器會選不同做法。依序執行這三格，每格看 JOIN 那一層的名稱：

第二格就是慢頁面的形狀：只看一位顧客，外層只有 1 列，所以是 Nested Loop。你不需要、也不應該指定 JOIN 做法，規劃器依成本決定，資料量或設定不同，選擇就可能不同，所以上面三格的註解都寫「通常」。你要做的是看得懂它選了什麼，並判斷這個選擇合不合理。

判斷合不合理，靠的是規劃器估計的列數：它選 Nested Loop，是因為它估計外層很少。到目前為止看到的全是估計值，EXPLAIN 從頭到尾沒有真的執行查詢。如果估計錯了，規劃器就會依錯誤的前提選錯做法。所以下一個問題是：怎麼知道估計對不對？

估計準不準？EXPLAIN ANALYZE 看實際數字

在 EXPLAIN 後面加上 ANALYZE，PostgreSQL 就會真的執行查詢，並在每一層旁邊多附一組實際量到的數字。同一個節點上，估計和實際並排，差多少一眼就看得出來。對修好的慢頁面查詢跑一次，看第一行括號裡的兩組數字：

Bitmap Heap Scan on orders  (cost=4.45..74.81 rows=20 width=26)
                            (actual time=0.025..0.049 rows=20.00 loops=1)

第一組括號是熟悉的估計值，第二組 actual 是實際值，由左到右：

  • actual time=0.025..0.049：實際花的毫秒數（第一列..全部）。這才是真正的時間，cost 不是。
  • rows=20.00（actual 裡的）：實際輸出幾列。拿來跟前面估計的 rows=20 比較，這裡完全一樣，代表規劃器估得準。
  • loops=1：這一步執行了幾次。Nested Loop 的內層會執行很多次，實際總時間要乘上 loops。

估計 20、實際 20，慢頁面這一關的判斷是對的。loops 這個數字值得記住：actual time 是每執行一次的時間，一個內層節點如果顯示 0.01 毫秒、loops=40000，實際就花了 400 毫秒。只看時間不看 loops，會漏掉真正慢的那一層。

還有一行只有 EXPLAIN ANALYZE 才會出現：如果節點有 Filter，底下會多附一行 Rows Removed by Filter，意思是實際讀了、但因為不符合條件被丟掉的列數。這次的 Bitmap Heap Scan 只讀索引指到的列，所以沒有這一行；但回到這課一開始還沒建索引的 Seq Scan，如果當時用 EXPLAIN ANALYZE，Filter: (customer_id = 42) 底下這個數字會接近 10 萬，正是「白讀了大半張表」的證據。

EXPLAIN ANALYZE 會真的執行。對 UPDATE、DELETE 用的話，資料真的會被改掉。要分析這類語句，先 BEGIN，看完再 ROLLBACK（第 18 課）。
💡 實務上：在資料量接近正式環境的地方看計畫
本機開發資料庫通常只有幾十筆資料，規劃器幾乎都會選 Seq Scan，計畫看起來沒問題，上線後面對大量資料才變慢。所以要在資料量接近正式環境的 staging（上線前的測試環境）上看計畫。要在正式環境跑 EXPLAIN ANALYZE 時要更小心：它會真的執行，本身就很慢的查詢會再拖一次資料庫，最好挑離峰時間、並先跟維運或 DBA 說一聲。

這次估計和實際一致。但估計是根據統計資訊算的，統計資訊一旦跟不上資料的變化，兩者就會差很多。下一節就讓這件事真的發生一次。

估計和實際差很多怎麼辦？ANALYZE 更新統計資訊

回想第一節：規劃器不讀整張表，只看事先算好的統計資訊來估計。統計資訊是在某個時間點抽樣算出來的，之後資料怎麼變，它不會自己即時跟上。如果在這中間大量寫入資料，規劃器腦中的「現況」就是過時的，估計就會錯，然後依錯的估計選出很爛的計畫。

模擬一個常見的情境：有人一口氣匯入 3 萬筆金額 5000 的大訂單，然後馬上查這些訂單。執行後比較第一行的估計 rows 和 actual 裡的 rows：

估計的 rows 只有幾百，實際卻是 30000。規劃器還以為「沒有人的訂單是 5000 元」，因為它的統計資訊是在這些資料新增之前算的。這裡查詢本身簡單，估錯還不至於出事；但在 JOIN 裡，估錯列數會讓規劃器選錯做法，例如以為外層只有幾十列而選了 Nested Loop，結果內層跑了幾萬次。

修正的方法是叫資料庫重新抽樣、重算統計資訊，指令是 ANALYZE 表名。執行後再看一次估計的 rows：

估計值變成接近 30000 了。正式環境的 autovacuum 會在資料變動夠多時自動 ANALYZE，但它要等變動累積到一定程度才會觸發，剛匯入完到它跑之前的這段時間，查詢就是依過時的統計資訊在規劃。所以大量匯入資料之後，自己手動跑一次是好習慣。

注意這裡出現了兩個 ANALYZE：ANALYZE orders 是「更新統計資訊」，EXPLAIN ANALYZE 是「實際執行查詢並量時間」。兩件事完全不同，只是剛好用了同一個字。

💡 實務上：匯入或批次作業之後，先 ANALYZE 再看效能
常見的事故是：晚上跑完一批資料匯入或 migration，隔天早上某支 API 突然變慢，程式碼一行都沒改。這時先跑 EXPLAIN ANALYZE，看估計和實際的 rows 有沒有差 10 倍以上；有的話，先對那張表 ANALYZE，再看一次計畫，往往就恢復了。資深工程師寫匯入腳本時，會直接在最後加一句 ANALYZE。

到這裡，慢頁面從頭到尾用到的工具都齊了：看計畫、讀樹、認得掃描和 JOIN、比對估計和實際、更新統計資訊。最後把它們排成一個固定的順序。

下次接到「這支 API 很慢」，照什麼順序查？

回顧這課處理慢頁面的過程，可以整理成五個步驟。順序有道理：先量到真實數字，再找出最貴的那一層，最後才決定是缺索引還是估計錯了，避免一看到慢就亂建索引：

  1. 用 EXPLAIN ANALYZE 跑那句慢的查詢。
  2. 找出花最多時間的那一層（看 actual time 乘上 loops）。
  3. 那一層是不是一張大表的 Seq Scan，而且 Rows Removed by Filter（見「EXPLAIN ANALYZE 看實際數字」那一節）很大？那就是缺索引。
  4. 估計的 rows 跟實際差了 10 倍以上？先 ANALYZE 那張表。
  5. 建索引後再跑一次，確認計畫真的換了。

第 5 步不能省：建了索引不代表規劃器會用它，要親眼看到計畫換了才算修好。

💡 實務上：把「改之前／改之後」的計畫附在 PR 裡
修慢查詢的 PR，資深工程師會在描述裡貼上改之前和改之後的 EXPLAIN ANALYZE 片段，讓 reviewer 一眼看到 Seq Scan 換成 Index Scan、時間從多少降到多少，而不是只寫「優化效能」。也別看到慢就加索引：每多一個索引，INSERT／UPDATE 都要多維護一份，寫入很頻繁的表（例如訂單）要衡量值不值得。

補充與查表

  • Recheck Cond：出現在 Bitmap Heap Scan 底下，是讀回來之後再確認一次條件，讀計畫時可以先不管。
  • Buffers：讀了多少個資料頁，shared hit 是在記憶體裡就找到的，數字越小越好。

練習 1：SELECT * FROM customers WHERE phone = '0912-345-678' 目前是 Seq Scan。建立一個索引，讓這句查詢的計畫改用索引。判分會檢查這句查詢的計畫裡有沒有出現 Index。

練習 2：登入時 email 不分大小寫，所以查詢寫成 WHERE lower(email) = 'user42@example.com'。建一個索引讓這句查詢不再是 Seq Scan。提示：上一課講過「對欄位套函式」的解法。

練習 3：起始內容新增了 2 萬筆 8000 元的訂單，接著用 EXPLAIN 看計畫，但第一行估計的 rows 嚴重偏低。在 INSERT 之後補上一句，讓估計值接近實際的 2 萬筆。判分會檢查計畫第一行估計的 rows 是否超過 10000。

練習 4：下面這個計畫，最先執行的是哪一步？

Hash Join
  -> Seq Scan on orders o
  -> Hash
       -> Seq Scan on customers c

✓ 計畫是一棵樹，由內往外讀：先做縮排最深的掃描，外層拿到子節點的輸出才能繼續。第一行是最後才完成、輸出最終結果的那一步。

練習 5：EXPLAIN ANALYZE 顯示某一層 rows=3（估計），但 actual … rows=48000.00。最可能的原因和第一步處理是？

✓ 估計和實際差這麼多，通常是統計資訊還停留在舊的資料分布。ANALYZE 表名 重新抽樣後，規劃器才能做出正確的選擇。cost 是相對單位，不是毫秒。

練習 6：查詢「全部 10 萬筆訂單，配上每一筆的顧客姓名」，而且不需要排序。規劃器最可能選哪一種 JOIN？

✓ 兩邊都是大量資料、又不需要排序時，先把較小的一邊（customers）建成 hash 表、再讓 orders 逐列去對，最划算。Nested Loop 適合外層只有少數幾列；Merge Join 需要兩邊都排好序。

常見錯誤

  • 把 cost 當成毫秒：cost 是相對單位，只能拿來比較不同計畫。真正的時間要看 EXPLAIN ANALYZE 的 actual time。
  • 從第一行開始當成第一步讀：計畫是一棵樹，縮排最深的先執行，第一行是最後才完成的那一步。
  • 只看第一行：慢的常常是某個內層節點，例如一個執行了幾千次（loops 很大）的內層掃描。
  • 對 UPDATE／DELETE 直接跑 EXPLAIN ANALYZE：它會真的執行。包在 BEGIN … ROLLBACK 裡。
  • 看到 Seq Scan 就覺得一定有問題：小表、或要讀大部分資料時，Seq Scan 本來就是最快的。要看的是「大表、只要少數幾列、卻在 Seq Scan」。
  • 建了索引卻沒換計畫就放棄：先檢查查詢有沒有對欄位套函式、統計資訊是不是過時。
  • 在本機的小資料庫看計畫就下結論：資料少時規劃器幾乎都選 Seq Scan，要在資料量接近正式環境的地方看。

小結

  • SQL 只說要什麼，規劃器依統計資訊估算成本、挑出查詢計畫；查詢慢的時候，問的就是「它選了哪個計畫、為什麼」。
  • EXPLAIN 顯示規劃器選的計畫（只估計、不執行）；EXPLAIN ANALYZE 會真的執行，並附上實際時間和列數。
  • 計畫是一棵樹，由內往外讀；cost 是相對成本，rows 是估計列數，上層的 cost 包含所有子節點。
  • 掃描方式：Seq Scan、Index Scan、Index Only Scan、Bitmap Heap Scan，取決於要拿的列佔整張表多少。
  • JOIN 方式：Nested Loop（外層少）、Hash Join（兩邊都多）、Merge Join（兩邊都排好序）。
  • 估計和實際差很多時，用 ANALYZE 表名 更新統計資訊；大量匯入之後主動跑一次。
  • 修慢查詢的順序：EXPLAIN ANALYZE → 找最貴的一層 → 判斷缺索引還是估計錯 → 修完再看一次計畫，並把前後對照附在 PR。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 7：後台刪除一個從沒賣出過的新品，竟然要好幾秒。order_items.product_id 是外鍵，指向 products.id，明細表有幾十萬筆。先查什麼？

✓ 刪除父表資料時，資料庫要去明細表找「還有沒有人參照這個商品」；外鍵不會自動建索引，主鍵 (order_id, product_id) 的第一欄也不是它，只能掃整張明細表。補 CREATE INDEX ON order_items (product_id)。c 錯在 products.id 是主鍵，本來就有索引，慢的是被參照的那一邊。（第 20 課）

練習 8：orders 有 10 萬筆，一天約 300 筆，ordered_at 已經有索引。店長查某一天的訂單，計畫卻是 Seq Scan，哪裡出了問題？

SELECT id, total FROM orders
WHERE ordered_at::date = '2026-03-01';

✓ 索引排的是欄位原本的值，對欄位做轉換之後的結果不在索引裡。改成範圍：ordered_at >= '2026-03-01' AND ordered_at < '2026-03-02'，讓欄位保持「裸的」。c 錯在改寫後的範圍一樣用字串寫日期，索引照樣用得上，問題出在左邊的欄位被轉換了。（第 20 課）

練習 9：後台「待處理訂單」列表寫成 WHERE status = 'pending' AND ordered_at >= $1 ORDER BY ordered_at。只建一個索引，選哪個？

✓ 複合索引先按第一欄排，第一欄相同再按第二欄排。status 固定之後，符合的時間是連續的一段而且已經排好，篩選和排序一次解決。a 錯在第一欄是範圍條件時，那段時間裡各種狀態混在一起，只能邊讀邊丟掉不是 pending 的列。（第 20 課）

練習 10：orders.status 有索引，六成訂單是 paid。WHERE status = 'paid' 的計畫卻是 Seq Scan，為什麼？

✓ 索引適合挑出少數幾列；要讀大部分的列時，Seq Scan 本來就最快，規劃器依成本選它是對的，不用處理。同一個索引查 pending 這種少數的狀態時照樣用得上。a 錯在正因為統計資訊準確，規劃器知道六成是 paid，才選了 Seq Scan。（第 20、21 課）

練習 11：想知道清理已取消訂單為什麼這麼慢，同事在正式資料庫跑了這句。哪裡會出事？

EXPLAIN ANALYZE
DELETE FROM orders WHERE status = 'cancelled';

✓ EXPLAIN ANALYZE 要真的執行，才量得到實際時間。要分析 UPDATE、DELETE，包在 BEGIN … ROLLBACK 裡；只想看計畫就用不加 ANALYZE 的 EXPLAIN。a 錯在 DELETE 也能 EXPLAIN ANALYZE，正因為能跑才危險。（第 21 課）

練習 12：大量匯入訂單後，「今天的訂單配上顧客姓名」從幾十毫秒變成好幾秒。EXPLAIN ANALYZE 節錄如下，最先該做什麼？

Nested Loop  (rows=40) (actual rows=40000.00 loops=1)
  -> Seq Scan on orders o  (rows=40) (actual rows=40000.00 loops=1)
  -> Index Scan using customers_pkey on customers c
       (rows=1) (actual rows=1.00 loops=40000)

✓ 估計 40 列、實際 4 萬列，統計資訊還停在匯入之前。規劃器以為外層很少才選 Nested Loop，內層就跑了 4 萬次（loops=40000）。ANALYZE orders 後再看一次，估計對了，規劃器會依成本改選適合兩邊都多的做法。c 錯在 JOIN 做法不用自己指定，估計錯了才是根源。（第 21 課）
