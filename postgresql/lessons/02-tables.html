階段 0：基本觀念 · 第 2 課

表、列、欄、主鍵

老闆把咖啡店的菜單整理在一張 Excel 裡：一欄品名、一欄價格、一欄「現在有沒有在賣」。線上點餐系統上線後，前台要列出菜單、後台要能改價，這份菜單得搬進資料庫。交給你的任務是：在 PostgreSQL 建一張 products 表放菜單，而且要建得夠嚴，之後不管是誰、從哪裡寫入，都不會出現「價格是八十」這種資料，也不會發生「後台改價，卻不確定改到哪一筆」。

上一課你查的 customers 是別人建好的表。這一課先把它拆開，看懂一張表由哪些零件組成；接著替菜單的每一欄決定型別、選出主鍵；最後用 CREATE TABLE 把 products 建出來，再故意寫錯資料，親眼看資料庫怎麼擋。

這課的路線：
  1. 菜單要變成一張表，表由什麼組成？拆開 customers，看懂表、欄、列，還有圖上那個 NULL。
  2. 價格欄能不能打「八十」？為什麼建表時就要決定每一欄的型別，菜單的三欄各該用哪一種。
  3. 後台要改拿鐵的價格，資料庫怎麼知道是哪一筆？主鍵，以及為什麼讓資料庫自動編號。
  4. 把設計寫成 CREATE TABLE，建出 products，再故意寫錯兩次，看資料庫怎麼擋。
  5. 表名怎麼取？為什麼用雙引號建的 "Staff"，之後寫 Staff 會找不到。

菜單要變成一張表：表由哪些零件組成？

要建 products，先看一張現成的表長什麼樣。下面是上一課查過的 customers，這個頁面的資料庫裡已經有它：

對照圖，一張表有四個零件：

零件意思對照 Excel
表（table）同一種東西的集合，例如所有顧客一張工作表
欄（column）每筆資料都有的一項屬性，有固定的名稱和型別一欄
列（row）一筆資料，例如一位顧客一列
主鍵（primary key）用來唯一認出某一列的欄位Excel 沒有，最接近的是列號

套到菜單上：customers 是「所有顧客」，一列是一位顧客；products 會是「所有商品」，一列是一樣商品，例如美式咖啡。customers 的每一列都有 id、name、phone 三欄；菜單的每一列則會有品名、價格、有沒有在賣這幾欄。表、欄、列這三個零件跟 Excel 幾乎一一對應，從 Excel 搬過來時，工作表變成表、標題列變成欄名、每一列資料變成一列。第四個零件主鍵在 Excel 裡沒有真正對應的東西（列號最接近，但刪掉一列後號碼就會跟著變），第 3 節改拿鐵價格時會講它為什麼需要。

圖上林志豪的電話寫著 NULL。NULL 的意思是「這一格沒有值」：林志豪沒留電話，所以那一格什麼都沒放。它不是 0，也不是空字串 ''。這個區分在實務上有意義：空字串代表「確定是空的」，NULL 代表「沒有資料、不知道」；放到菜單上，一杯定價 0 元的贈品，和一樣還沒定價的新品，是兩回事，資料庫要能分得出來。哪些欄可以是 NULL、哪些一定要有值，是建表時要決定的事，第 4 節建 products 時會用到。

表、欄、列都能從 Excel 類推，但圖的左邊寫著「欄位名稱 ＋ 型別」：資料庫的每一欄除了名字，還綁了一個型別。這是資料庫跟 Excel 最大的差別，也是這張菜單表能不能「建得夠嚴」的第一步。

價格欄能不能打「八十」？每一欄先決定型別

Excel 的任何格子都能打任何東西。資料庫不行：建表的時候就要決定每一欄放什麼型別。型別就是「這一欄只收哪一種值」，例如只收整數、只收文字。之後每次寫入，資料庫都會先檢查值合不合這一欄的型別，不合就整句拒絕，一筆都不會寫進去。

這看起來很嚴格，其實是在保護你。想像價格欄可以放文字：Excel 菜單裡有人把伯爵紅茶的價格打成「九十」，表格看起來沒什麼問題；等到月底算營業額，加總時這一格不是數字，你的程式要嘛報錯，要嘛默默把它當成 0，結果少算了一筆。這種錯最麻煩的地方是發生和被發現隔了很久，到時已經不知道是誰、什麼時候、從哪裡寫進來的。讓資料庫在寫入的那一刻擋下來，寫錯的人當場就會收到錯誤，比事後找錯容易得多。

型別有很多種，先記住這五個最常用的就夠了（第 13 課會深入）：

型別放什麼例子
integer整數80、-3
numeric(10,2)精確的小數，用在金額（總共 10 位、小數 2 位）1234.50
text任意長度的文字'王小明'
boolean是或否true、false
timestamptz日期加時間（含時區）'2026-10-29 14:30+08'

拿這張表替菜單的三欄挑型別：

  • 品名：文字，長短不一，用 text。
  • 價格：咖啡店的價格都是整數元（80、110），沒有角，用 integer 就夠。如果價格會有小數，就用 numeric(10,2) 這種精確的小數；不要用 float，原因見課末「常見錯誤」。
  • 有沒有在賣：只有是或否兩種答案，用 boolean。

寫值的時候要注意引號：SQL 的文字一律用單引號，例如 '美式咖啡'。雙引號在 SQL 裡是另一種用途，最後一節會講；把文字包在雙引號裡，資料庫會把它當成欄位的名字，而不是一段文字。

💡 實務上：前端驗證擋不住所有資料，型別是最後一道防線
你在表單上做的檢查只保護「從畫面進來」的資料；實際上資料還會從後台匯入 CSV、維運跑的修正腳本、其他服務的 API 寫進來，這些都繞過前端。這張菜單表也一樣：老闆的 Excel 很可能某天整批匯入。所以前端驗證是為了使用者體驗，資料庫的型別（和第 12 課的規則）才是真正擋錯的地方。開新欄位時，資深工程師會先問：這欄可能出現哪些值？金額要不要小數？時間要不要時區？一開始選錯型別，等資料量大了再改會很麻煩，所以值得在建表時多想一分鐘。

三欄的型別決定了，壞資料進不來。但還有一個問題：後台要改某一樣商品時，要怎麼指名是「這一列」？

後台要改拿鐵的價格，資料庫怎麼知道是哪一筆？主鍵

老闆說拿鐵要從 110 漲到 120。直覺的做法是「找品名是拿鐵的那一列，把價格改掉」。用名字當作找一列的依據，會遇到兩個問題：

  • 名字會重複：冬天推出季節限定的「拿鐵」，菜單上就有兩列都叫拿鐵，「改拿鐵的價格」會兩列一起改。顧客表也一樣，咖啡店可能有兩位顧客都叫王小明，「改王小明的電話」說不清是哪一位。
  • 名字會變：老闆把「美式咖啡」改名「經典美式」，所有拿名字記住這樣商品的地方，例如訂單裡記著買了什麼、前端購物車裡放著什麼，就全部對不上了。

所以每張表都需要一個專門用來認出某一列的欄位，它要滿足三個條件：每一列的值都不一樣、一定有值、而且永遠不變。這個欄位就是主鍵。把一欄宣告成主鍵後，資料庫會負責前兩個條件：寫入重複的值或 NULL，它會直接拒絕。第三個條件「永遠不變」資料庫管不到，要靠你選對欄位。

什麼值符合這三個條件？品名、電話這些有業務意義的值都不行：品名會重複、會改名；電話會換，也可能沒有。最好的選擇是一個跟業務意義無關的編號：它只負責認出這一列，不代表任何東西，所以永遠沒有理由改它。最常見的做法是加一個 id 欄位，讓資料庫自動編號：1、2、3……

為什麼要讓資料庫編號，而不是後端自己算「目前最大號加一」？因為第 1 課講過，會有兩台收銀機、兩個請求同時寫入。兩邊同時讀到最大號是 5，就會都拿 6 去寫，撞號。交給資料庫發號，它保證每次發出去的號碼都不一樣。寫法是這一行：

id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY
  • integer：編號是整數。
  • GENERATED ALWAYS AS IDENTITY：每新增一列，資料庫自動給下一個號碼，你不用（也不能）自己填。「不能」是故意的，第 4 節會親手試。
  • PRIMARY KEY：這欄是主鍵，資料庫保證不重複、不會是 NULL。

有了 id，改價就變成「把 id 是 2 的那一列改成 120」。就算菜單上有兩列都叫拿鐵、就算拿鐵改了名，id 2 永遠指同一樣商品。至於手機、Email 這種業務上也不能重複的值，做法是另外加 UNIQUE 規則（第 12 課），而不是拿來當主鍵。

💡 實務上：主鍵常常會出現在網址裡
像 /orders/123 這種網址，123 通常就是主鍵；菜單也一樣，前台的商品頁可能是 /products/2。要注意：連號的 id 很好猜，別人把 123 改成 124 就可能看到別人的訂單，所以後端查資料時一定要檢查「這筆是不是目前登入者的」，不能以為別人不知道網址就安全。也因為連號會透露訂單量，有些團隊對外改用不好猜的 UUID（第 13 課會提到這個型別）。

欄位、型別、主鍵都設計好了。接下來把這份設計寫成資料庫看得懂的一句 SQL。

把設計寫成 CREATE TABLE：建出菜單表

建表的語法是 CREATE TABLE，形狀如下：

CREATE TABLE 表名 (
  欄位名 型別 [額外規則],
  欄位名 型別 [額外規則],
  ...
);

括號裡一行一欄，每一欄先寫名字、再寫型別，後面可以接額外的規則；欄與欄之間用逗號隔開，最後一欄後面不加逗號；整句用分號結尾。

欄名用英文小寫：品名叫 name、價格叫 price、有沒有在賣叫 is_available。為什麼用小寫和底線，第 5 節會講。

這次會用到一條新規則 NOT NULL：「這欄一定要有值」，寫入時沒給值、或給了 NULL，資料庫都會拒絕。第 1 節說過，哪些欄可以是 NULL 要在建表時決定。菜單的判斷是：沒有品名、沒有價格的商品不該上架，所以 name 和 price 加上 NOT NULL；「有沒有在賣」暫時允許留空，代表還沒決定。第 12 課會講更多這類規則。

💡 實務上：正式環境不會手打 CREATE TABLE
在團隊裡，建表的 SQL 會寫成 migration 檔案，跟程式碼一起放進 git、在 PR 裡被 review，部署時再自動執行，這樣每個環境的表結構才會一致（第 22 課會教）。這張菜單表在真實專案裡，也會是一個 migration 檔，而不是有人在正式資料庫手打。DROP TABLE 只在自己的電腦或測試環境用；對正式資料庫下這句，資料就沒了，只能靠備份救回。養成習慣：下任何會刪東西的指令前，先確認自己連的是哪個資料庫。

表名怎麼取？大小寫與雙引號

我們的表叫 products，全小寫。習慣寫 JavaScript 的人，很可能想把店員表取名 Staff、欄位取名 createdAt。這在 PostgreSQL 會碰到一個規則：它會把沒加引號的名稱一律轉成小寫。所以 CREATE TABLE Staff 實際建出來的是 staff，之後寫 staff、Staff、STAFF 都會先轉成 staff，所以都找得到。

但如果你用雙引號 CREATE TABLE "Staff"，大小寫就會被保留，表名真的就是大寫 S 的 Staff。之後每次都必須寫 "Staff"（含引號）；寫 SELECT * FROM Staff，沒加引號的 Staff 會先被轉成 staff，錯誤訊息是 relation "staff" does not exist，明明建過了卻找不到。這就是雙引號的用途：包住名稱，讓名稱保留原本的大小寫；文字值用的是單引號，第 2 節講過。

慣例：表名和欄位名全部小寫、單字用底線連接（snake_case），例如 order_items、created_at。這樣永遠不需要雙引號。
💡 實務上：資料庫用 snake_case，前端用 camelCase
前端 JavaScript 習慣寫 createdAt，資料庫欄位是 created_at，兩邊不一樣很正常。常見做法是在後端統一轉換。後端通常用 ORM 存取資料庫：ORM 是把資料表對應成程式物件的函式庫，例如 NestJS 篇會用到的 Prisma，對應時可以設定欄名怎麼轉換。轉換交給後端或 ORM，而不是為了配合前端把欄位建成 "createdAt"，否則之後每句 SQL 都得加雙引號。進新團隊時先看現有的表怎麼命名、照著做，一致比個人喜好重要。

補充與查表

  • serial：舊教學常看到 id serial PRIMARY KEY，效果差不多，是比較舊的自動編號寫法。新專案用 IDENTITY。
  • 真的需要指定 id 時：例如從舊系統搬資料、要保留原本的編號。PostgreSQL 對第 4 節第二句的錯誤其實附了一句提示（HINT）：Use OVERRIDING SYSTEM VALUE to override.，但這個頁面只顯示錯誤和說明，看不到這句。意思是在 INSERT 加上 OVERRIDING SYSTEM VALUE，就能強制寫入指定的 id，例如 INSERT INTO products (id, name, price) OVERRIDING SYSTEM VALUE VALUES (1, '可頌', 70);。這是搬資料時才用的例外，平常不要用。

練習

練習 1：建立店員表 staff，依序有三個欄位：id（自動編號的主鍵）、name（文字）、hourly_wage（時薪，整數）。

練習 2：建立菜單表 menu_items，依序有：id（自動編號主鍵）、name（文字）、price（金額，總共 10 位、小數 2 位）、is_seasonal（是否為季節限定）、created_at（建立時間，含時區）。

練習 3：咖啡店的會員表，哪個欄位最適合當主鍵？

✓ 手機號碼會換、可能沒有；姓名會重複。自動編號永遠不重複、不會變。手機號碼若要求不能重複，可以另外加 UNIQUE 規則（第 12 課）。

練習 4：執行了 CREATE TABLE Staff (...)（沒有引號），接著執行 SELECT * FROM staff; 會怎樣？

✓ 沒有引號時 Staff 和 staff 是同一個名稱。只有用雙引號建立的 "Staff" 才會區分大小寫。

常見錯誤

  • 最後一個欄位後面多一個逗號：hourly_wage integer,) 會出現 syntax error。逗號只放在欄與欄之間。
  • 文字用了雙引號：VALUES ("拿鐵", 110) 會被當成欄位名稱，出現 column does not exist。文字值一律用單引號。
  • 用 float 存金額：浮點數有誤差（0.1 + 0.2 ≠ 0.3），金額一律用 numeric 或以「元」為單位的 integer。
  • 把 NULL 當成 0 或空字串：NULL 是「沒有值、不知道」，0 元和還沒定價是兩回事。一定要有值的欄位，建表時就加 NOT NULL。

小結

  • 表由欄（屬性）和列（一筆資料）組成；Excel 的工作表、標題列、每一列，分別對應表、欄名、列。
  • NULL 是「這一格沒有值」，不是 0 也不是空字串；NOT NULL 規定這欄一定要有值。
  • 每一欄有固定的型別，資料庫在寫入的那一刻就擋下錯的資料，錯的那一句整句不會寫進去。
  • 主鍵唯一認出每一列，要不重複、一定有值、永遠不變；用 integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY 讓資料庫自動編號，而且不允許自己填號。
  • 文字用單引號；名稱一律小寫加底線，不用雙引號。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 5 件事。先在心裡回答，再選。

練習 5：朋友的咖啡店要做會員集點：兩台收銀機同時幫客人加點數，月底要查「某位會員上個月買了什麼」。資料該放哪？

✓ 會不會有兩個人同時寫、資料丟了要不要賠、之後要不要查紀錄，只要一題答「會」就該用資料庫：它自己協調同時進來的修改，型別擋下髒資料，權限管誰看得到什麼。d 錯在問題第一天就存在：兩台收銀機同時讀改寫回，後寫的會蓋掉先寫的點數，不是等資料多了才出事。（第 1 課）

練習 6：同事為了省掉寫 API，把 DATABASE_URL 放進 Vue 專案的 .env，讓前端直接查菜單。他說 .env 沒有 commit 進 Git，所以很安全。你怎麼回？

✓ 前端打包出來的 JS 在使用者的瀏覽器執行，裡面的連線字串誰都看得到。帳密只放在後端的環境變數或雲端 secret 設定，前端透過後端 API 拿資料。d 錯在唯讀帳號一樣看得到整個資料庫，包括顧客電話；前端能拿到什麼，要由後端 API 決定。（第 1 課）

練習 7：從舊系統匯入商品 CSV 時一直報錯，原因是 price integer 欄位收到了「八十」。同事提議把 price 改成 text，讓匯入順利。你怎麼回？

✓ CSV 匯入、修正腳本、其他服務的 API 都不經過前端表單，資料庫的型別是最後一道防線，在寫入的那一刻擋下錯的值。b 錯在前端驗證只保護從畫面進來的資料，是為了使用者體驗，不是保證資料正確。（第 2 課）

練習 8：訂單詳細頁的網址是 /orders/123，後端拿網址上的 id 到 orders 表查主鍵，查到就回傳。已登入的顧客把網址改成 /orders/124，會怎樣？

✓ 連號的 id 很好猜，網址上的 id 誰都能改。後端查訂單時要一起檢查「這筆是不是目前登入者的」，不能以為別人不知道網址就安全。b 錯在主鍵只保證每一列不重複、不是 NULL，不管查的人是誰。（第 2 課）

練習 9：同事開的訂單表如下，code review 時哪一欄該改？

CREATE TABLE orders (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  total float NOT NULL,
  created_at timestamptz
);

✓ 浮點數有誤差（0.1 + 0.2 ≠ 0.3），金額加總可能對不上帳。金額用 numeric，或以「元」為單位的 integer。a 錯在 serial 是比較舊的寫法，新專案用 IDENTITY。（第 2 課）
