階段 3：資料品質 · 第 12 課

約束：NOT NULL、UNIQUE、CHECK、DEFAULT

咖啡店下個月要上線會員集點：客人報手機加入會員，每次消費集一點，點數可以折抵，累積夠了會升等。你負責設計資料表。PM 先給了一張「上線後絕對不能發生的事」：

  1. 會員資料沒有名字。
  2. 同一支手機註冊成兩位會員。
  3. 點數被扣成負的。
  4. 會員等級出現 'gloden' 這種打錯的值。
  5. 同一位會員一天集了兩次點。

前幾課學的工具擋不住這張清單。型別擋得住「把文字放進數字欄」，但 -50 是合法的整數，'gloden' 是合法的文字；外鍵擋得住「不存在的顧客」，但管不到同一支手機出現兩次。這一課學約束（constraint）：寫在表定義裡的規則，資料庫在每一次寫入時都會檢查，違反規則的資料寫不進去。你用過的主鍵和外鍵其實也是約束，這課補上另外三種：NOT NULL、UNIQUE、CHECK，以及常跟它們寫在一起的 DEFAULT。學完，PM 清單上的每一條都會變成資料庫自己擋得住的規則。

這課會用到：
  • 第 2 課的 CREATE TABLE 和 NOT NULL：建表時宣告每一欄的型別，NOT NULL 表示這欄一定要有值。
  • 第 4 課的 NULL：NULL 代表「不知道」，拿它跟任何值比較，結果也是「不知道」，既不是 true 也不是 false。
  • 第 8 課的外鍵 REFERENCES：這欄的值必須存在於另一張表。
  • 第 10 課的複合主鍵：用兩欄的組合當主鍵，組合不能重複。
這課的路線：
  1. 前端已經檢查過，資料庫為什麼還要擋：寫進資料庫的路有好幾條，有些檢查只有資料庫做得對。
  2. 建會員表：NOT NULL 擋住沒名字的會員，DEFAULT 替沒填的欄位補值（清單第 1 條）。
  3. UNIQUE 與 CHECK：重複的手機、負的點數、打錯的等級怎麼被擋下（清單第 2～4 條）。
  4. 為約束命名：被擋下時，後端怎麼知道違反哪一條、該回給使用者哪一句話。
  5. 多欄位 UNIQUE：「每天只能集一次點」這種看組合的規則（清單第 5 條），最後看舊表補約束時會遇到什麼。

前端表單已經檢查過，資料庫為什麼還要再擋一次？

寫 Vue 的直覺是：表單上把名字設成必填、手機格式不對就不給送出，PM 的清單在前端擋掉就好。問題在於前端檢查只保護「從這個表單送出的資料」。資料庫不知道一筆資料是從哪裡來的，而會員表上線後，寫入它的路不只一條：

第一個問題是每個入口都要記得檢查。店長會在後台手動補點數；開幕前要把紙本會員卡整理成 CSV 一次匯入；半年後同事可能再寫一支 API，讓客人用其他管道綁定會員。如果規則寫在每個入口的程式裡，就要寫好幾次、改的時候也要改好幾次，只要有一個入口漏了，髒資料就進去了。而且髒資料寫進去的當下不會有任何錯誤，通常要等報表算錯、客人來抱怨點數不對，才會被發現，那時已經很難查出是哪個入口寫的。

第二個問題是前端的檢查可以被繞過。前端程式跑在使用者的瀏覽器裡，任何人都能打開 DevTools 改掉送出的內容，或乾脆不經過網頁，直接呼叫你的 API。後端 API 收到資料時當然要再驗一次，但 API 的驗證也只保護經過那一支 API 的寫入，CSV 匯入腳本、後台介面都不會經過它。

第三個問題最不直覺：有些檢查只有資料庫做得對。「手機不能重複」常見的寫法是程式先查「這支手機有沒有人用」，沒有才新增。平常沒事，但客人連點兩下「加入會員」時，兩個請求幾乎同時到達後端：請求 A 去查，沒有人用；請求 B 也去查，這時 A 還沒寫進去，所以也是沒有人用；接著兩邊各自新增一筆，同一支手機就變成兩位會員。「查」和「寫」之間有一段空隙，程式碼寫得再小心，這段空隙都在。UNIQUE 約束是資料庫在寫入那一刻自己判斷，兩筆同時寫入同一支手機，最多只有一筆成功（為什麼做得到，第 31 課會講）。

所以三層檢查各有分工，不互相取代：前端檢查是為了使用者體驗，填錯當下就提示，不用等送出；後端驗證讓 API 能回給呼叫者清楚的錯誤；資料庫約束是最後一道，保證表裡的資料正確，不管它從哪條路進來。PM 清單上的每一條，都要寫進表的定義裡。接下來就把會員表建出來，看這些規則怎麼寫。

DEFAULT：沒寫到這欄時，自動填一個值

同一支手機註冊兩次，怎麼擋？UNIQUE

UNIQUE 的規則是：這一欄的值在整張表裡不能重複。每次寫入時，資料庫會拿新的值去比對表裡已經有的值，撞到就拒絕。用王小明的手機再註冊一次：

被 members_phone_key 擋下了。這是資料庫自動替這條 UNIQUE 約束取的名字，格式是「表名_欄位名_key」。先記住錯誤訊息裡會出現約束名稱，後面「被擋下之後，後端怎麼知道違反哪一條？」那一節會用到。

UNIQUE 聽起來跟第 2 課的主鍵很像。主鍵等於 NOT NULL 加 UNIQUE，而且一張表只能有一個，它的工作是「識別這一列」；UNIQUE 一張表可以有很多個，欄位也可以是 NULL。那手機既然不能重複，為什麼不拿來當主鍵？因為主鍵要穩定、一定有值，其他表會用外鍵指向它；手機會換（第 6 課的王小明就換過號碼），也可能沒留。所以 id 當主鍵負責識別，手機用 UNIQUE 負責不重複，兩件事分開。

沒問題。回想第 4 課：NULL 代表「不知道」，兩個不知道的值，不能說它們相等。UNIQUE 判斷重複時也照這個邏輯，不把兩個 NULL 當成重複。這通常就是你要的行為：「沒留電話」不該跟「另一位也沒留電話」衝突。真的需要「NULL 也只能有一個」時，另有寫法，見課末「補充與查表」。

點數扣成負的、等級打錯字，怎麼擋？CHECK

CHECK 後面放一個條件，寫法跟 WHERE 一樣。每次 INSERT 或 UPDATE，資料庫都會拿寫入後的新值算這個條件，結果是 false 就拒絕，整句失敗。會員表的 CHECK (points >= 0) 就是「點數不能小於 0」。

CHECK 的陷阱：NULL 會通過。CHECK 只擋「條件結果是 false」的資料。NULL >= 0 的結果是 NULL（不知道），不是 false，所以會被放行。這跟上一節 UNIQUE 放過 NULL 是同一個道理：NULL 不會讓規則判定「違反」。如果欄位不能是 NULL，要另外加 NOT NULL，這就是 points 同時加了 CHECK 和 NOT NULL 的原因。
💡 實務上：CHECK 放「不可能合理」的規則，商業政策放程式
積分不能是負的、價格要大於 0、人數至少 1 人，這些不管老闆怎麼改政策都成立，很適合寫成 CHECK。「單筆最多折 300 元」「金卡門檻 5000 點」這種行銷常調整的規則，寫進 CHECK 的話每次改都要動 schema，放在程式或設定表比較好。等級、狀態這種清單如果常新增，或需要存顯示名稱、排序，可以改成一張獨立的表再用外鍵參照。資深工程師加 CHECK 前會先問：這條規則半年後還會一樣嗎？

到這裡清單前四條都擋住了，每次被擋，錯誤訊息裡都有一個名字：members_phone_key、members_points_check、members_level_check。這些名字是資料庫自動取的，上線之後，後端程式會靠它們決定該跟使用者說什麼。

被擋下之後，後端怎麼知道違反哪一條？為約束命名

約束擋下寫入時，資料庫回給後端的錯誤裡有兩樣東西可以用來判斷：

  • 錯誤代碼：PostgreSQL 給每一類錯誤一個固定的 5 碼代號，叫做 SQLSTATE。例如違反 UNIQUE 是 23505，違反 CHECK 是 23514。它告訴你「哪一類」違規。各種約束的代碼整理在課末「補充與查表」。
  • 約束名稱：例如 members_phone_key。它告訴你「哪一條」約束。一張表常有好幾條同類的約束，例如手機和 Email 都不能重複，光看 23505 分不出是哪一欄重複，要看名稱。

所以約束名稱要一看就懂。自動產生的名字在單純的情況下還算清楚，但一個欄位有好幾條 CHECK 時，名字會變成 members_points_check1 這種，看錯誤訊息時猜不出是哪一條。解法是用 CONSTRAINT 名稱 自己取名。

會員方案還有一項：菜單上要標會員特價，規則是「特價一定要比原價低」。這條規則同時看兩個欄位，會員表裡沒有這種規則，所以換到菜單表 menu 示範。先看兩種寫約束的位置：前面都把約束寫在欄位後面，叫做欄位約束，它只能管自己那一欄；也可以把約束寫在欄位清單的最後，叫做表約束，它可以同時用到好幾欄。sale_price < price 牽涉兩欄，只能寫成表約束。如果這條表約束不命名，PostgreSQL 會自動取名 menu_check：牽涉好幾欄的 CHECK，自動名稱不會帶欄位名，只有「表名_check」。錯誤訊息只寫 menu_check，看不出是哪條規則，表上再多一條多欄 CHECK 就更分不清。所以下面兩條都寫成表約束，並用 CONSTRAINT 命名：

💡 實務上：約束錯誤要轉成使用者看得懂的訊息
會員註冊時手機重複，資料庫回的是 UNIQUE 違規錯誤（23505）。後端常見的作法是直接 INSERT，撞到錯誤再依錯誤代碼和約束名稱轉成「這支手機已經註冊過」，用 HTTP 409 回給前端，而不是先查再寫。409 是 Conflict 的狀態碼，意思是這次請求和伺服器上現有的資料衝突，正好對應「手機已被註冊」。不要把資料庫原始錯誤訊息直接丟給前端，裡面有表名和欄位名，使用者看不懂，也會讓外人知道你的 schema。這也是約束要好好命名的實際理由：程式靠名稱判斷該回哪一句話。

PM 清單只剩最後一條：同一位會員一天只能集一次點。這條規則跟前面的都不一樣，單看任何一欄都判斷不了。

同一位會員一天只能集一次點，怎麼擋？多欄位 UNIQUE

集點要一張新表 stamps，一列代表「某位會員在某一天集了一點」。想想哪個東西不能重複：member_id 會重複，因為王小明每天都會來；日期也會重複，因為每天有很多人來。不能重複的是「會員 ＋ 日期」這個組合。上一節說過，牽涉兩欄的規則要寫成表約束，UNIQUE 也一樣：把兩個欄位一起放進括號，寫成 UNIQUE (member_id, stamp_date)，意思是這兩欄的值合起來不能重複。

💡 實務上：多欄位 UNIQUE 是防重複的最後一道防線
同類需求很常見：每位會員每天集點一次、同一位使用者對同一篇文章只能按一次讚、同一位會員對同一個商品只能留一則評價。使用者連點兩下按鈕、網路不穩重送請求時，這條約束能保證資料不會多一筆。寫之前先跟 PM 確認規則的細節，例如「每天」是以台灣時間還是 UTC 換日、作廢的集點紀錄還要不要算進「今天已集過」。規則講不清楚就建約束，之後很可能擋到正常的資料。

到這裡，PM 清單的五條都變成了約束。不過會員表和集點表都是新建的，裡面還沒有資料。咖啡店還有一張早就在用的舊商品表，想替它補上約束時，會遇到新表沒有的問題。

舊的商品表也想補上約束，為什麼會失敗？

這頁的資料庫裡有一張 products，是咖啡店早期建的，當時一條約束都沒加，價格可以是 0、負數或 NULL，商品名稱也可能重複。老闆看完這課，想替它補上「價格必填且大於 0」和「名稱不能重複」。

替已經有資料的表加約束，用 ALTER TABLE … ADD CONSTRAINT，第 22 課會講。重點是加的那一刻，資料庫會拿新規則檢查表裡現有的每一列，只要有一列違反，整句就失敗，約束加不上去。資料庫不會幫你決定髒資料該怎麼處理：價格是 0 的卡布奇諾是忘了填，還是真的免費招待？重複的兩筆拿鐵該留哪一筆？這些要跟老闆確認。

所以順序是：先用 SELECT 把會違反規則的資料找出來，跟老闆確認怎麼修，修完再加約束。下面練習 2、3 就是在做「找出來」這一步。

補充與查表

約束違規的錯誤代碼，查表用，不用背。程式判斷錯誤要比對代碼和約束名稱，不要比對錯誤訊息的文字：

約束規則違反時的錯誤代碼
NOT NULL一定要有值23502
UNIQUE不能重複（NULL 不算重複）23505
CHECK (條件)條件不能是 false（NULL 會通過）23514
DEFAULT 值沒寫到這欄時自動填（不是限制，但常一起用）—
PRIMARY KEYNOT NULL ＋ UNIQUE，一張表一個23502／23505
REFERENCES值必須存在於另一張表（第 8 課）23503
  • NULL 也只能有一個：如果真的要「NULL 也只能有一個」，PostgreSQL 15 以後可以寫 UNIQUE NULLS NOT DISTINCT。很少用到，知道有這個選項就好。

練習

練習 1：建立優惠券表 coupons：

  • id：自動編號主鍵
  • code：文字，必填、不能重複
  • discount：折扣百分比，整數、必填，用 CHECK (discount BETWEEN 1 AND 100) 限制範圍
  • is_active：是否啟用，boolean、必填，預設 true

練習 2：老闆想替 products.price 加上 NOT NULL 和 CHECK (price > 0)，但現有資料裡有違規的商品，加約束會失敗。找出所有會違反這兩條規則的商品 id，由小到大排列。

練習 3：老闆也想讓 products.name 不能重複。找出目前重複的商品名稱，欄位依序是 name、出現次數。

練習 4：訂位表 reservations 已經建好（同一張桌子同一天只能訂一次、人數 1～8、status 預設 'booked'）。新增一筆訂位：6 號桌、'2026-11-01'、4 人、電話 '0922-111-222'，status 使用預設值。可以先執行 SELECT * FROM reservations; 看看現有資料，也可以故意試試違反規則的值。

練習 5：phone text UNIQUE，表裡已經有一位會員的 phone 是 NULL。再新增一位 phone 也是 NULL 的會員，會怎樣？

✓ NULL 代表不知道，兩個不知道的值不算相等，所以 UNIQUE 允許多個 NULL。需要「NULL 也只能一個」時才用 UNIQUE NULLS NOT DISTINCT（PostgreSQL 15+）。

練習 6：前端註冊表單已經檢查「手機不能重複」（先查有沒有人用，沒有才送出）。資料庫還需要加 UNIQUE 嗎？

✓ 前端可以被繞過，其他寫入路徑可能漏掉檢查，「先查再寫」在同時請求下也會失效。只有資料庫的約束保證不管從哪裡寫入都不會重複。前端檢查留著，用來即時提示使用者。

常見錯誤

  • 只加 CHECK 沒加 NOT NULL：CHECK (price > 0) 擋不住 NULL，因為 NULL > 0 的結果是「不知道」，不是 false。欄位不能空就另外加 NOT NULL。
  • 以為 DEFAULT 會取代 NULL：明確寫 NULL 時不會套用預設值；要用預設值就不要寫那一欄，或寫 DEFAULT。
  • 用 UNIQUE 分別加在兩欄：member_id integer UNIQUE, stamp_date date UNIQUE 意思是「每位會員一輩子只能集一次」而且「每天只能有一個人集點」。組合不重複要寫 UNIQUE (member_id, stamp_date)。
  • 只在程式裡驗證：其他入口可能漏掉檢查，「先查再寫」在兩個請求同時進來時也擋不住重複。規則寫在資料庫才可靠，程式裡的驗證是給使用者看的提示。
  • 不替約束命名：錯誤訊息只看到 xxx_check1，除錯時要回頭翻 schema，後端也無法靠名稱回給使用者對應的訊息。

小結

  • 約束是寫在表上的規則，每一次寫入都會檢查。前端檢查給使用者體驗，資料庫約束保證資料正確，不管資料從哪條路進來。
  • NOT NULL 必填；DEFAULT 在沒寫到這欄時自動填，明確寫 NULL 時不會套用，所以常和 NOT NULL 一起用。
  • UNIQUE 拿新值跟其他列比，不能重複；CHECK (條件) 看這一列的值合不合理。兩者都會放過 NULL，需要時搭配 NOT NULL。
  • 用 CONSTRAINT 名稱 命名，後端靠錯誤代碼和約束名稱把錯誤轉成使用者看得懂的訊息。
  • 牽涉兩欄以上的規則寫成表約束：UNIQUE (a, b) 讓組合不重複，CHECK (a < b) 比較兩欄。
  • 替舊表補約束時，現有資料只要有一列違反就會失敗，先把髒資料找出來處理。
