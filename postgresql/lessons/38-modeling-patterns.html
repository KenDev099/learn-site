階段 11：資深必備｜資料建模與期末專題 · 第 38 課

資料建模模式：軟刪除、稽核、時間區間、多租戶

咖啡店從一家店擴展成台北、台中、高雄三家分店，三家共用同一套系統、同一個資料庫。上線前，老闆和店長們交來一張需求清單：

  • 會員刪除帳號後，要能在一段時間內「復原」。
  • 價格出問題時，要查得到「是誰、在什麼時候，把拿鐵改成 150 元」。
  • 訂位不能把同一張桌子的同一個時段賣給兩組人。
  • 台中店的店員絕對不能看到台北店的訂單。

這一課的任務：你是負責資料層的後端工程師，要把這四條需求做進資料庫，最後寫一份測試，證明最危險的那一條（分店之間的隔離）真的成立。四條需求有一個共通點：它們都是「每一次寫入、每一個查詢都必須遵守」的規則。只寫在程式裡、靠每支 API 記得檢查，總有一條路會忘記：新同事寫的報表、直接連資料庫修資料的 SQL、另一支背景服務。所以這課每一節都在回答同一個問題：怎麼讓資料庫自己守住這條規則，程式忘了也不會出事？用到的是前面學過的約束、trigger、RLS，再加上幾個新工具：範圍型別與排除約束、固定 search_path 的 SECURITY DEFINER 函式、複合外鍵，以及用「故意改壞」驗證測試真的有效的做法。

這課的路線：照需求清單的順序走，每一節解決一條需求，也留下下一節要處理的問題。
  1. 會員刪除後要能復原，怎麼刪除又不真的刪？軟刪除，以及它讓唯一約束、外鍵出的問題。
  2. 是誰把拿鐵改成 150 元？用 trigger 記下每一次修改，並讓應用程式改不掉這份紀錄。
  3. 同一張桌子、同一時段，怎麼只賣一次？範圍型別加排除約束，讓資料庫在寫入時擋下重疊。
  4. 台中店怎麼看不到台北店？店的 id 進主鍵、外鍵、索引，RLS 依每個交易設定的店過濾。
  5. 怎麼證明隔離真的有效？用 SQL 寫測試，再故意改壞 policy 確認測試抓得到；最後對照四個模式的代價。
這課會用到：
  • 第 23 課的 view 與 trigger：view 把一句查詢存成虛擬表；trigger 是一個 RETURNS trigger 的 function 加上 CREATE TRIGGER … AFTER … FOR EACH ROW，用 NEW、OLD 讀新舊資料。
  • 第 24 課的 role 與 RLS：GRANT 把權限給某個 role，SET ROLE 暫時切換成另一個 role；超級使用者和表的擁有者預設繞過 RLS；set_config(…, true) 設一個只在這個交易有效的值，讓 RLS 知道現在是誰。
  • 第 26 課的 schema 與 search_path：schema 是表的命名空間，就像資料夾；名字沒寫 schema 時，依 search_path 列出的 schema 去找。
  • 第 36 課的連線池與應用程式的 role：transaction 模式的連線池每個交易結束就把連線還回去，下一個交易不一定拿到同一條；應用程式用不是表擁有者的 role 連線，RLS 才對它有效。
這頁的環境：會改資料的範例都包在 BEGIN; … ROLLBACK; 裡，不會改到頁面上的資料。練習在全新的資料庫裡判分。

這頁的資料：三家分店 stores（台北店 1、台中店 2、高雄店 3）；軟刪除用的會員 members；稽核用的空表 audit_log；時間區間用的訂位 reservations；多租戶用的 products、orders、order_items；應用程式用的 role app_user。每一節開頭再說明用到的表。

會員刪除後要能復原：怎麼刪除又不真的刪？

從清單的第一條開始。真的執行 DELETE，那一列就從表裡消失了：會員一週後反悔想回來，資料已經沒有了。如果有訂單引用這位會員，還會碰到第 8 課的外鍵：要嘛被擋住刪不掉，要嘛設了 ON DELETE CASCADE，連他的訂單一起消失，營收報表跟著少一截。

軟刪除（soft delete）的做法是不執行 DELETE，改成 UPDATE，在 deleted_at 欄記下刪除的時間（第 6 課提過）。deleted_at 是 NULL 的是現役會員，有時間的就是已刪除。復原只要把它改回 NULL；想知道上個月刪除了哪些會員，查 deleted_at 的範圍就好；訂單引用的會員也還在。這頁的 members 有 6 位會員，執行後看 deleted_at 欄：

陳美華和李建國的 deleted_at 有值，代表已經刪除，但他們還在表裡。這就是軟刪除的代價：這張表從此有兩種列，每一個查詢都要記得排除已刪除的。忘了加 WHERE deleted_at IS NULL 是軟刪除最常見的 bug：後台的會員列表、寄行銷簡訊的名單，已刪除的會員又出現了。

不要指望每個人都記得，把條件集中在一個地方：建一個 view，名字就表明它只有現役會員，程式一律查這個 view，不直接查 members。執行後看陳美華和李建國還在不在：

另一種集中的方式是第 24 課的 RLS：替應用程式的 role 加一條 policy，讓它根本讀不到 deleted_at 有值的列，連「查錯表」的機會都沒有。代價是後台要看「已刪除的會員」時，得換一個不受這條 policy 限制的 role。

過濾解決了「讀」的問題。但已刪除的列還留在表裡，表上的約束也看得到它們，第一個出問題的是唯一約束。

已刪除會員的手機，能不能給新會員註冊？

手機號碼要唯一，否則簡訊驗證、用手機找會員都會對到兩個人。但這條規則只該限制「現役會員」：已刪除的會員不會再用這支手機登入，號碼可能被電信公司回收、給了別人，新的主人應該能註冊。資料裡就有這個情況：陳美華刪除帳號後，她的手機 0922-111-222 被張雅婷拿去註冊。

直覺的兩種寫法都不對。下面用 seed 裡的 try_sql(sql) 各試一次：它執行一句 SQL，成功回傳 ok，失敗回傳錯誤碼和訊息，不會讓整格中斷（第 32 課用過）。執行後由左到右看三欄：

  • UNIQUE (phone) 建不起來：陳美華（已刪除）和張雅婷用同一支手機。就算建得起來，刪除帳號的人的手機也永遠不能再註冊。
  • UNIQUE (phone, deleted_at) 建得起來，卻擋不住重複（第三欄）：還沒刪除的會員 deleted_at 都是 NULL，而唯一約束預設把兩個 NULL 當成不相等，所以 ('0912-345-678', NULL) 可以出現很多次。

第二種寫法看起來最合理，失敗的原因要多想一步。NULL 在 SQL 裡的意思是「不知道」，兩個不知道的值無法判定相等，所以唯一約束不把它們算成重複。結果是：這條約束只在「已刪除的會員之間」有作用，偏偏我們要管的是現役會員。

正確的工具是第 27 課的部分唯一索引（partial unique index）。部分索引只收錄符合 WHERE 條件的列；在 CREATE UNIQUE INDEX 後面加上 WHERE 條件，就只在這些列之間要求不重複。條件寫「還沒刪除」，已刪除的會員根本不在索引裡，他們的手機不跟任何人比；會員一被軟刪除，他那一列就離開索引，手機立刻可以給別人用。練習 1 由你寫出來。PostgreSQL 15 起還有另一種寫法，取捨見課末的「補充與查表」。

唯一約束修好了。另一個會被「已刪除但還在表裡」影響的約束是外鍵。

外鍵和 CASCADE 還管得到已刪除的會員嗎？

管不到。外鍵只檢查「被引用的那一列存在」，它不知道 deleted_at 代表什麼。軟刪除的會員還在表裡，所以新訂單照樣可以掛在已刪除的會員身上。要擋，就在寫入的程式或 trigger 裡檢查，或者在子表也記一個狀態。

反方向也一樣：ON DELETE CASCADE 只在真的 DELETE 時觸發（第 8 課），軟刪除是 UPDATE，不會觸發。會員的集點卡、地址都還在，刪除帳號時要自己決定這些子資料怎麼辦：一起軟刪除、保留，還是清掉。

到這裡，軟刪除的成本都是「要多做一點」。但有一種情況，軟刪除本身就不合格。

個資必須真的刪除時怎麼辦？

使用者依個資法要求刪除個人資料時，「標記已刪除」不算刪除：姓名和手機還完整地存在資料庫裡。常見的做法是去識別化：保留這一列（訂單統計還要用到它），把姓名、手機改掉或清空，讓這一列再也對應不到一個真人。

另一個方向是乾脆不用軟刪除，改成把資料搬到封存表：刪除時把那一列搬到另一張 members_archive，主表永遠只有現役的資料。這樣查詢不用過濾、唯一約束也不用特別處理，前面兩個問題一起消失；代價是復原時要從封存表搬回來。DELETE … RETURNING（第 6 課）配上 CTE，可以用一句完成「刪除並搬走」。執行後看封存表裡的會員，以及主表剩下幾筆：

會員、商品下架、文章這類「使用者可能後悔」或「訂單還在引用」的資料，常用軟刪除；草稿、暫存、log 類的資料通常直接刪就好。很多 ORM 有內建的軟刪除（例如 Laravel 的 SoftDeletes、Sequelize 的 paranoid），會自動幫查詢加條件，但手寫的 SQL、報表、資料匯出不會經過它，已刪除的資料最常從這些地方漏出來。資深工程師會先跟 PM 確認：誰可以復原、保留多久、報表要不要算已刪除的，再決定用軟刪除、封存表還是直接刪除。

第一條需求做完了：過濾集中在 view，唯一性用部分唯一索引，外鍵和 CASCADE 管不到的要自己補。但軟刪除只留下「最後的狀態」：陳美華的 deleted_at 告訴你她在 3 月 1 日被刪除，卻看不出是誰按的刪除、刪除前資料長什麼樣。老闆的第二個問題正是這種「表裡看不出來」的事。

是誰把拿鐵改成 150 元？讓每次修改都留下紀錄

拿鐵現在賣多少，查 products 就知道；它昨天賣多少、是誰改的，表裡沒有，因為 UPDATE 直接蓋掉了舊值。要回答老闆，就得在每次修改時另外記一筆稽核紀錄（audit log）：哪張表、什麼操作、改之前、改之後、誰改的、什麼時候。

紀錄寫在哪裡？最直覺的是寫在程式裡：每支修改資料的 API 自己 INSERT 一筆稽核。這和上一節「忘了過濾」是同一種漏洞：只要有一條路沒經過這些 API，就沒有紀錄。有人直接連資料庫下 SQL 修資料、另一支服務改了價格、新寫的 API 忘了記，都會留下空白，而出事時要查的往往就是這些不尋常的路。所以用第 23 課的 trigger：它掛在表上，不管修改從哪裡來，資料庫都會呼叫它。這一節把紀錄寫進這頁空的 audit_log，範例改 members，練習 2 改 products。

trigger 怎麼知道改了什麼、是誰改的？

我們希望一個 trigger 函式就能給很多張表用，不必每張表各寫一個。trigger 函式執行時，可以讀到幾個特別的變數和函式，靠它們拿到這次修改的資訊：

  • TG_OP：觸發的操作，'INSERT'、'UPDATE' 或 'DELETE'。TG_TABLE_NAME：表名。
  • to_jsonb(OLD)、to_jsonb(NEW)：把整列轉成 JSONB 物件（第 14 課）。INSERT 時 OLD 是 NULL，DELETE 時 NEW 是 NULL。用 JSONB 存，表加了欄位也不必改稽核表。
  • current_setting('app.user_id', true)：資料庫不知道「哪位店員」在操作，因為應用程式都用同一個 app_user 連線。所以由後端在每個交易開頭用 set_config('app.user_id', …, true) 告訴它（第 24 課的做法）。第二個參數 true 表示沒設定時回傳 NULL，而不是報錯。

整列存下來很完整，但不好讀：要回答「改了哪個欄位」，得自己比對兩大段 JSON。這件事可以交給 SQL：用 jsonb_object_keys 把 new_row 的每個鍵（也就是欄位名）展開成一列，再只留新舊值不同的鍵。比較時用 IS DISTINCT FROM，不用 <>：NULL <> 值 的結果是 NULL，會被 WHERE 濾掉，像 deleted_at 從 NULL 變成有值這種修改就會漏掉；IS DISTINCT FROM 把 NULL 也當成一個值來比。

應用程式碰不到稽核表，trigger 要怎麼寫進去？

如果應用程式的 role 可以改、刪 audit_log，有人改了價格之後，順手把那筆紀錄刪掉，稽核就失去意義。所以這頁的 app_user 可以讀和改 members，對 audit_log 沒有任何權限。

問題是 trigger 函式預設用觸發它的人的權限執行。app_user 一改會員，trigger 就以 app_user 的身分寫 audit_log，沒有權限而失敗；trigger 失敗，整個 UPDATE 也跟著失敗。執行後看錯誤碼：

把 INSERT 權限給 app_user 可以解決，但這樣應用程式也能自己塞假紀錄。更好的做法是 SECURITY DEFINER：函式以擁有者（通常是建立它的人）的權限執行，而不是呼叫者的。app_user 自己碰不到 audit_log，只能透過這個函式、照函式寫好的方式寫進去。

SECURITY DEFINER 等於把擁有者的權限借給呼叫者。借出去之前要確認：呼叫者只能用這份權限做函式寫好的事。這裡有一個不明顯的漏洞。

SECURITY DEFINER 函式要防什麼？

函式裡寫的是 audit_log，沒有標 schema。PostgreSQL 依照呼叫當下的 search_path 去找這個名字（第 26 課），而 search_path 是呼叫者能影響的。函式卻是以擁有者的權限執行，所以呼叫者只要能讓 audit_log 這個名字指到別的東西，就能決定「擁有者的權限」被用在哪裡。這叫 search_path 劫持（search_path hijacking）。

最容易被利用的是暫存表。任何人都能建暫存表，暫存表放在每條連線專屬的 schema pg_temp 裡；而找表名時，pg_temp 如果沒寫在 search_path 裡，就排在最前面。install_audit(true) 建的是同一個函式加上 SECURITY DEFINER，沒有設定 search_path。看 app_user 怎麼讓自己的修改不留紀錄，執行後比較兩欄的筆數：

紀錄寫進了攻擊者的暫存表，真的稽核表一筆都沒有；暫存表在連線結束時就消失，證據也跟著不見。如果 search_path 裡還有攻擊者能建立物件的 schema，連函式和運算子都能被換成同名的假貨，讓攻擊者的程式碼以擁有者的權限執行（哪些 schema 屬於這種，見課末）。

PostgreSQL 18 文件的建議：用 SET 子句固定 search_path，只放可信任的 schema，pg_temp 明確寫在最後：

CREATE FUNCTION audit_row() RETURNS trigger
  LANGUAGE plpgsql
  SECURITY DEFINER
  SET search_path = public, pg_temp      -- 只在這個函式執行期間生效
AS $$ … $$;

只寫 SET search_path = public 不夠：沒列出來的 pg_temp 還是排在最前面，上面的攻擊照樣成功（pg_catalog, public 也一樣）。另一種做法是函式裡每個表名都寫完整（public.audit_log），但很容易漏掉一個。練習 2 會以 app_user 的身分、帶著一張同名的暫存表，檢查你寫的稽核函式。

寫入的路徑安全了。最後要算的是稽核的成本。

稽核表會越長越大，哪些表該記？

稽核表長得很快：每修改一列，它就多一列。可以依月份分割，舊的分區整個搬到便宜的儲存或刪掉（第 35 課）。更根本的是只記需要的表：高頻寫入的表（例如計數器）每次都多寫一列 JSONB，成本不小；如果只想知道「最後一次是什麼時候改的」，加一個 updated_at 欄就夠了。程式端也有辦法拿到新舊值，但它取代不了 trigger，見課末。

💡 實務上：稽核紀錄是出事時拿來查的，平常就要確認查得到
常見的場景是客服或老闆問「拿鐵的價格是誰改的」、「這筆訂單的金額為什麼變了」，工程師去稽核表查 changed_by 和新舊值。所以要確認每條寫入路徑都有設定 app.user_id，背景工作也給一個固定的名稱（例如 job:nightly-sync），否則紀錄一堆 NULL，查了也沒用。另一個坑：稽核表存的是整列，會員的姓名、手機也在裡面，使用者要求刪除個資時，稽核表也要一併處理。給使用者看的「操作紀錄」頁面通常另外設計，不要直接把這張表的 JSONB 丟給前端。

第二條需求做完了：trigger 記下每條路徑的修改，SECURITY DEFINER 加上固定的 search_path，讓應用程式只能透過它寫入稽核表。但稽核是事後追查，它告訴你錯誤已經發生了。第三條需求不能等事後：同一張桌子賣給兩組客人，客人到店才發現，查到是誰訂的也來不及。這種錯誤要在寫入的當下擋住。

同一張桌子、同一時段，怎麼只賣一次？

這是第 26 課留下的問題。先看為什麼前面學過的工具都不夠：

  • CHECK 約束只看得到正在寫入的那一列，「時段重疊」卻是兩列之間的關係。
  • UNIQUE 管得到兩列之間，但它只比「相等」。用 starts_at、ends_at 兩欄存時段時，UNIQUE (table_id, starts_at) 只擋開始時間完全相同的兩筆；18:00–19:30 和 19:00–20:30 的開始時間一個是 18:00、一個是 19:00，是不同的值，UNIQUE 不擋，兩段時間卻明明重疊。
  • 用程式先查「這段時間有沒有人訂」再寫入：兩個請求同時進來，兩邊都查到「沒有」，然後一起寫入（第 19 課的並發問題）。

PostgreSQL 的答案分兩步：先用範圍型別把「一段時間」存成一個值，再用排除約束讓資料庫拒絕「同一張桌子、時段重疊」的兩列。

怎麼把「一段時間」存成一個值？

用 starts_at、ends_at 兩個欄位也能存時段，但每次判斷重疊都要自己寫成「a 的開始早於 b 的結束，而且 b 的開始早於 a 的結束」，邊界很容易寫錯。範圍型別（range type）把「一段區間」存成一個值，重疊、包含這些判斷由資料庫提供。常用的有 tstzrange（帶時區的時間）、daterange（日期）、int4range（整數）。

區間的寫法是 [開始, 結束)：[ 表示包含這一端，) 表示不包含。tstzrange(a, b) 預設就是 [a, b)，叫半開區間。常用的運算子有兩個：&& 判斷兩段有沒有重疊，@> 判斷是否包含某個時間點或某一段。執行後先比較前兩欄：同樣是前一段 19:30 結束、下一段 19:30 開始，兩種寫法的答案不同：

  • 半開區間：false。前一段不包含 19:30，下一段從 19:30 開始，兩段只是相鄰。
  • 包含結尾的 []：true。兩段共用 19:30 這一點，被當成重疊。
  • 後兩欄：19:00 落在 18:00–19:30 之內；upper() 取出區間的結束時間。

訂位的時段一定是一組接一組：前一組 19:30 離開，下一組 19:30 入座。用包含結尾的寫法，這兩組會被誤判成衝突，只能硬把結束時間改成 19:29:59 這類奇怪的值。半開區間讓「結束等於下一段的開始」剛好接上，所以時段一律用 [)。

這頁的 reservations 就是用 tstzrange 存訂位：during 是時段，status 是 booked 或 cancelled。執行後看 3 號桌：陳美華取消之後，林志豪訂了和她重疊的時段：

怎麼讓資料庫拒絕重疊的兩列？

排除約束（exclusion constraint）是唯一約束的一般化。UNIQUE (a) 的意思是「任兩列的 a 不能 =」；EXCLUDE 讓你自己指定每個欄位用哪個運算子比，所有運算子同時成立的兩列就不准共存：

ALTER TABLE 表 ADD CONSTRAINT 約束名
  EXCLUDE USING gist (欄位1 WITH =, 欄位2 WITH &&)
  WHERE (條件);      -- 選用：只在符合條件的列之間檢查，跟部分唯一索引一樣

套到訂位上：「同一張桌子（table_id WITH =）而且時段重疊（during WITH &&）」的兩列不准共存；已取消的不算，就用 WHERE 排除，和第一節的部分唯一索引是同一個想法。

資料庫要在每次寫入時快速找出「可能重疊的列」，需要一個索引幫忙，所以排除約束靠索引實作。B-tree 把值排成一條直線，只能回答「等於、大於、小於」，沒辦法回答「這兩段有沒有交集」。能處理重疊的是 GiST 索引（Generalized Search Tree，第 28 課提過的另一種索引）：它把資料分成一層層的外框，每個外框記下底下所有值涵蓋的範圍；查「有沒有和 19:00–20:30 重疊」時，外框整個落在範圍之外的，底下的資料就整框跳過，不用一列一列比。所以這裡寫 USING gist。GiST 是為範圍、幾何這類型別設計的，PostgreSQL 內建時並沒有替一般整數準備 GiST 版的 =，table_id WITH = 就沒辦法用。要靠 btree_gist 擴充套件替一般型別加上 GiST 的比較方法；這頁的 seed 已經 CREATE EXTENSION btree_gist。下面在交易裡先把它移除，執行後看沒有它時的錯誤碼（42704）：

約束加上之後，違反它的寫入會得到錯誤碼 23P01（exclusion_violation），後端可以接住它，回應「這個時段已經有人訂了」。因為檢查發生在資料庫寫入的當下，兩個請求同時搶同一個時段，也只有一個會成功，這正是「先查再寫」做不到的。練習 3 由你替 reservations 加上它；注意已取消的訂位不該擋人。PostgreSQL 18 還把這類規則做成主鍵和外鍵的語法（WITHOUT OVERLAPS、PERIOD），適合「某段期間有效」的資料，見課末。

💡 實務上：凡是「預約」都該讓資料庫擋重疊
訂位、會議室、看診時段、員工排班、租借設備，都是「同一個資源、同一時段只能一筆」。前端先查空位、把滿的時段反灰只是讓使用者好用，真正把關的是排除約束；後端收到 23P01 就回「這個時段剛被訂走，請重新選擇」，並重新載入空位。時間一律用帶時區的型別，前端送 ISO 8601 加上時區（例如 2026-11-14T18:00:00+08:00），不要送「當地時間字串」讓後端猜。

第三條需求做完了：時段用半開區間存成範圍型別，重疊交給排除約束在寫入時擋下。不過到這裡的每一條規則，都默默假設只有一家店：3 號桌是哪家店的 3 號桌？拿鐵是哪家店的拿鐵？三家店共用同一批表之後，最後一條需求要回答的就是「這一列屬於哪家店，誰看得到它」。

三家店共用一套系統，台中店怎麼看不到台北店？

多租戶（multi-tenant）是一套系統服務多個客戶，每個客戶叫一個租戶（tenant），彼此的資料要隔離。這裡的租戶是分店；如果做的是給很多公司訂閱的線上服務（SaaS），租戶就是每家公司。

第一個要決定的是資料放在哪裡。有三種做法，差別在隔離靠什麼、要付什麼代價：

做法隔離代價適合
共用表，每列帶 store_id靠 WHERE 與 RLS寫錯一個條件就外洩；大租戶會影響小租戶的效能大多數 SaaS、租戶很多
每個租戶一個 schema靠 search_pathmigration 要對每個 schema 跑一遍；上千個 schema 時系統目錄很大、備份與監控變慢租戶不多、要客製表結構
每個租戶一個資料庫最強連線池、監控、升級都要乘上租戶數；跨租戶報表很難少數大客戶、合約要求實體隔離

咖啡店是同一間公司的三家分店，表結構一樣，總部還要看跨店報表，所以用第一種：共用表，每列帶 store_id。它的代價寫在表格第一列：隔離完全靠條件，寫錯一個就外洩。所以接下來要讓 store_id 出現在三個地方，每個地方擋一種錯誤：

  • 主鍵與外鍵：擋「寫錯的引用」，例如台北店的訂單掛上台中店的商品。
  • RLS：擋「看到別家的列」，程式忘了加條件也一樣。
  • 索引：每個查詢都帶 store_id，索引要配合它才查得快。

誰屬於哪個租戶、怎麼從登入資訊拿到租戶 id，是授權的設計，見認證課第 20 課；這裡只管資料庫這一層。這一節用到的表：

  • products：三家店各 6 樣商品，台北店是 1～6 號、台中店 7～12 號、高雄店 13～18 號。主鍵是 (store_id, id)，另外有一個舊的 UNIQUE (id)。
  • orders：每家店 10 筆（台北 1～10、台中 11～20、高雄 21～30），已開啟 RLS。order_items：每筆訂單一個品項。
  • app_user 可以讀寫 orders、products。

台北店的訂單，能不能掛上台中店的商品？

先看第一個位置。order_items 有 store_id，但它的商品外鍵只用 product_id 參照 products (id)。外鍵只確認「有這個商品」，不管是哪家店的。下面替台北店寫兩筆明細，執行後看兩欄：

  • 第一筆寫進去了：台北店的訂單掛上了台中店的商品，報表會算錯、價格也可能不同。
  • 第二筆被擋（23503），因為訂單的外鍵已經是複合外鍵（composite foreign key）：FOREIGN KEY (store_id, order_id) REFERENCES orders (store_id, id)。兩個欄位要一起對上，「明細的店」就必須等於「訂單的店」。

複合外鍵把「同一家店」這條規則變成外鍵的一部分：明細的 (store_id, order_id) 這一對值，必須在 orders 找到完全相同的一對。外鍵要求被參照的那邊有涵蓋這些欄位的主鍵或唯一約束，所以 orders 有 UNIQUE (store_id, id)、products 的主鍵是 (store_id, id)。練習 4 替商品補上同樣的保護。

複合外鍵擋的是寫錯的引用。但每家店查訂單時看得到哪些列，外鍵管不到，那是 RLS 的工作。

怎麼讓每家店只看得到自己的訂單？

第 24 課的 RLS 在表上加 policy：USING 決定看得到哪些列，WITH CHECK 決定寫入的列要符合什麼。policy 要知道「現在是哪家店」，做法和上一節稽核的 app.user_id 一樣：後端在每個交易開頭用 set_config 設定 app.store_id，policy 用 current_setting 讀出來。orders 的 policy：

CREATE POLICY orders_tenant ON orders TO app_user
  USING (store_id = current_setting('app.store_id')::int)        -- 看得到哪些列
  WITH CHECK (store_id = current_setting('app.store_id')::int);  -- 寫入的列要符合

台中店的身分只看得到台中店的 10 筆；替別家店寫入被 WITH CHECK 擋下（42501）。查詢裡沒寫任何 WHERE store_id，過濾是 RLS 加上的，程式忘了寫也不會外洩。

這個 policy 有一個前提：app.store_id 一定要是「這個請求」的店。上面用的是 set_config(…, true)，設定只在目前的交易有效。這個 true 不能省，原因要從連線池說起。

租戶設定為什麼只能在交易內有效？

第 36 課講過，transaction 模式的連線池會讓每個交易借到不一定相同的連線。如果租戶設定跟著連線走，它就可能被下一個借到這條連線的請求用到。下面一步一步看：

RLS 只保護開了它的表，也只對不能繞過它的 role 有效。正式專案裡，每張租戶的表都要有 policy：這頁只替 orders 開了 RLS，products、order_items 也要。也要記得誰會繞過 RLS（第 24 課）：超級使用者、有 BYPASSRLS 的 role、表的擁有者（除非 FORCE ROW LEVEL SECURITY）；所以應用程式要像第 36 課那樣，用不是擁有者的 app_user 連線。

租戶 id 的第三個位置是索引：幾乎每個查詢都帶 store_id = …（RLS 會自動加上），所以索引以 store_id 開頭，例如 (store_id, ordered_at)。

到這裡，表本身守住了。但還有一條常見的漏洞，不是出在表上，而是出在為了方便建的 view。

加了 view 之後，RLS 還有效嗎？

有人替應用程式建了一個 view，方便查訂單。view 預設用擁有者的身分和 RLS 去查底層的表（PostgreSQL 18 的 CREATE VIEW 文件），不是用查詢者的。擁有者是超級使用者或表的擁有者時，RLS 對它無效，於是 app_user 透過 view 拿到了它自己拿不到的列。執行後先比較前兩欄，再看加上 security_invoker 之後的筆數：

直接查 10 筆，經由 view 30 筆，三家店的訂單全部外洩。security_invoker = true（PostgreSQL 15 起）讓 view 改用查詢者的權限和 policy。在有 RLS 的表上建 view，一律加上它：CREATE VIEW … WITH (security_invoker = true) AS …。第一節為軟刪除建的 active_members，如果 members 也開了 RLS，同樣要加。

💡 實務上：多租戶的外洩，多半出在「新加的那一條路」
主要的 API 通常都測過，出事的常是後來加的東西：新的一張表忘了開 RLS、為了報表建的 view、背景工作或匯出 CSV 沒設定租戶、客服後台用了能繞過 RLS 的帳號。資深工程師 review 這類 PR 時會逐項問：新表有沒有 store_id 和 policy？外鍵、索引有沒有帶 store_id？新的 view 有沒有 security_invoker？這段程式用哪個 role 連線、在哪裡設定租戶？客服或總部真的需要跨店查詢時，給一個專用的 role，並把它的操作記進稽核紀錄，而不是共用最高權限的帳號。

第四條需求的規則都寫好了：store_id 進主鍵、外鍵、索引，RLS 依每個交易設定的店過濾，view 用查詢者的身分。但「寫好」不等於「有效」：一個寫錯的 policy，在開發時看起來可能一切正常。交件前的最後一步，是證明它。

怎麼證明分店之間真的隔離？

隔離規則寫在資料庫裡，就在資料庫裡測。測試是一個 PL/pgSQL 函式，用 ASSERT 檢查：ASSERT 條件, '訊息'，條件不成立（或是 NULL）就丟出 P0004（assert_failure）錯誤。測試通過，就是函式正常結束。

測試要用應用程式的 role 測。在函式裡寫 SET LOCAL ROLE app_user，之後的查詢都以 app_user 執行，交易結束就恢復。用超級使用者測，永遠看到全部，測試永遠不準。

測試寫好、也通過了，怎麼知道它真的在保護什麼？做法是故意把被測的東西改壞，看測試會不會失敗。改壞了測試還通過，代表它根本沒在檢查這件事。這就是變異測試（mutation testing）的想法。這頁的 mutation_check('SELECT 測試函式()') 依序把 orders_tenant 的 USING 換成五種：正確的、true（全部外洩）、store_id = 1（寫死台北店）、store_id = 2（寫死台中店）、false（誰都看不到），每種跑一次測試，回報通過與否，最後把 policy 改回來。好的測試只有第一列通過。

測試函式裡要呼叫 set_config 但不需要它的結果，PL/pgSQL 規定用 PERFORM 取代 SELECT（第 33 課）。先看一個常見的「半套」測試：只用台北店、只檢查「看不到別家」。執行後由上到下看「測試通過」欄：

  • 正確的 policy：通過。
  • USING (true)（全部外洩）：失敗，抓到了。
  • USING (store_id = 1)（寫死台北店）：通過。這個測試只用台北店測，寫死台北店時，台北店看起來一切正常。
  • USING (store_id = 2)（寫死台中店）：失敗，抓到了。
  • USING (false)（誰都看不到）：通過。這個測試只檢查「看不到別人」，沒檢查「看得到自己」。每家店都看不到自己的訂單，顯然是壞的，測試卻放行。

兩個漏網的錯誤，對應測試少做的兩件事：只測一家店，就分不出「正確」和「寫死這家店」；只測「看不到別人」，就分不出「正確」和「誰都看不到」。所以好的隔離測試要測兩家以上的店，每家都同時檢查兩個方向。練習 5 由你寫出能抓到全部四種錯誤的測試。正式專案可以用 pgTAP（PostgreSQL 的測試框架，提供 is()、results_eq() 等斷言），並在 CI 用跟正式環境同版本的 PostgreSQL 跑（DevOps 課第 15 課）。每次改 policy 或 migration，測試都會跑一遍。

四條需求都做進資料庫了，最危險的隔離也有測試證明。最後退一步看：這四個模式都有代價，不是每個專案都該全部用上。

這四個模式，什麼時候該用、什麼時候不該用？

每個模式都是用一些成本，換「程式忘了也不會出事」。判斷要不要用，就是比較這兩邊：不用這個模式時，規則會在哪條路上破掉、破掉的代價多大；用了之後，每天要多付什麼。對照這張表：

模式解決什麼代價什麼時候不要用
軟刪除（deleted_at）可復原、保留歷史與關聯每個查詢都要過濾；唯一約束要改成部分索引；外鍵不知道已刪除資料必須真的消失（個資）；刪除很頻繁的表（改用封存表）
稽核 trigger任何來源的修改都有紀錄每次寫入多一筆 JSONB；表很快變大高頻寫入的計數類資料；只需要「最後修改時間」時加一個 updated_at 就夠
範圍型別＋EXCLUDE／WITHOUT OVERLAPS時段不重疊，並發時也成立GiST 索引寫入較慢；要 btree_gist時段是固定格子（例如每小時一格）時，用 UNIQUE (table_id, slot) 更簡單
共用表＋store_id＋RLS一套 schema 服務所有租戶每張表、每個鍵、每個索引都帶租戶 id；要測試隔離合約要求實體隔離；只有一個租戶

另一個常被問到、但不屬於這四種的需求是「發票號碼要連續」，做法放在課末。

部分唯一索引的另一種寫法：NULLS NOT DISTINCT

PostgreSQL 15 起可以寫 UNIQUE NULLS NOT DISTINCT (phone, deleted_at)，讓 NULL 被當成相等。但它也會要求「同一支手機、同一個刪除時間」不重複，語意比較繞，一般用部分唯一索引。

search_path 劫持：哪些 schema 危險

攻擊者能建立物件的 schema 才危險。PostgreSQL 15 以前，public schema 人人可寫；15 起，新資料庫的 public schema 預設不再讓所有人建物件，所以攻擊者通常只剩 pg_temp 可以用，這正是主線示範的。

程式端拿新舊值：RETURNING old／new

PostgreSQL 18 起 RETURNING 可以寫 old.欄位、new.欄位。適合把變更送到訊息系統，但它不能取代稽核 trigger：直接下 SQL 的修改不會經過你的程式。執行後看「改之前」「改之後」兩欄：

PostgreSQL 18：WITHOUT OVERLAPS 與 PERIOD 外鍵

訂位之外，「某段時間內有效」的資料也很常見：商品的歷史價格、員工的職位、合約的期間。PostgreSQL 18 把這類規則做成了時間性約束（temporal constraint）。這裡換成歷史價格的例子，因為它要的是主鍵和外鍵，訂位表用不到：

  • PRIMARY KEY (product_id, valid_at WITHOUT OVERLAPS)：同一個商品的有效期間不能重疊。文件說明它等於 EXCLUDE USING gist (product_id WITH =, valid_at WITH &&)，一樣需要 btree_gist。
  • FOREIGN KEY (product_id, PERIOD during) REFERENCES product_prices (product_id, PERIOD valid_at)：參照的那一段期間，必須被對方的期間完全涵蓋（可以由好幾列接起來）。

PERIOD 外鍵在 PostgreSQL 18 只支援預設的 NO ACTION：寫 ON DELETE CASCADE、SET NULL，連 RESTRICT 都會得到 0A000。這是 18 才有的新功能，ORM 和 migration 工具不一定認得，用之前先確認團隊的工具鏈。歷史價格表適合用來查「某天的定價」；但訂單本身仍要存下單當下的單價，不要每次都回頭查價格表算金額。

發票號碼要連續

第 31 課看過 IDENTITY 和序列在 ROLLBACK 時會跳號，它們只保證不重複、不保證連續。要連續就用一張計數表，在開發票的同一個交易裡更新：

CREATE TABLE invoice_counters (store_id integer PRIMARY KEY, last_no integer NOT NULL);

-- 開發票的交易裡：
UPDATE invoice_counters SET last_no = last_no + 1 WHERE store_id = $1 RETURNING last_no;

UPDATE 鎖住這家店的那一列，同一家店的開票排隊進行（第 19 課）；交易 ROLLBACK 時號碼也一起退回，所以不會跳號。代價是同一家店的開票不能並行，交易要短。

練習

練習 1：members 用 deleted_at 做軟刪除。建一個索引，讓未刪除的會員手機不能重複，但已刪除會員（例如李建國）的手機可以被新會員使用。之後有會員刪除帳號，他的手機也要能馬上給別人用。不要改動現有的資料。

練習 2：替 products 寫稽核。每次 UPDATE 一列商品，就在 audit_log 記下 table_name、op、old_row、new_row（整列的 JSONB）和 changed_by（current_setting('app.user_id', true)）。改價要照常生效。檢查時會用 app_user 的身分、以兩位不同的店員改價兩次，而 app_user 對 audit_log 沒有權限，也不能給它；改價之前它還會先建一張同名的暫存表 audit_log，紀錄必須照樣寫進真的稽核表。

練習 3：替 reservations 加上約束：同一張桌子、時段重疊的訂位不能同時存在，但已取消的訂位不算（3 號桌陳美華取消後，林志豪訂了重疊的時段，這是合法的）。剛好相鄰的時段（前一組 20:00 結束、下一組 20:00 開始）要能訂，不同桌子同一時段當然也可以。不要改動現有的資料。

練習 4：台北店的訂單明細可以引用台中店的商品（前面示範過）。替 order_items 加上一個外鍵，讓明細的商品一定和明細屬於同一家店；同一家店的商品（包括之後才新增的商品）要照常可以寫入。

練習 5：寫測試函式 test_tenant_isolation()（RETURNS void、LANGUAGE plpgsql）：以 app_user 的身分，分別設定台北店（1）與台中店（2），用 ASSERT 確認每家店看得到自己的訂單、看不到別家的。policy 正確時正常結束，有問題就丟出錯誤。檢查時會用 mutation_check 跑它：正確的 policy 要通過，四種壞掉的 policy 都要失敗。

練習 6：稽核用的 trigger 函式加了 SECURITY DEFINER，讓沒有 audit_log 權限的 app_user 也能留下紀錄，但沒有設定 search_path。風險是什麼？

✓ 函式裡沒標 schema 的表名依呼叫當下的 search_path 找，而沒列出來的 pg_temp 排第一、任何人都能建暫存表；稽核紀錄會被導到攻擊者的表。search_path 裡若有攻擊者可寫的 schema，連函式、運算子都能被換掉，以擁有者的權限執行。解法是 SET search_path = 可信任的 schema, pg_temp（pg_temp 明確放最後）。a：SECURITY DEFINER 是把擁有者的權限借出去，借出去就要限制它能碰到什麼。b：效能不是重點。d：誰能呼叫由 EXECUTE 權限決定，跟 SECURITY DEFINER 無關。

練習 7：API 經過 transaction 模式的連線池連到資料庫，每個請求一開始執行 SELECT set_config('app.store_id', $1, false)，RLS 依它過濾。會發生什麼事？

✓ false 是 session 層級，跟著連線走；transaction 模式的連線池把同一條連線輪流借給不同請求。改用 set_config(…, true) 或 SET LOCAL，並在同一個交易裡查詢：交易結束設定就消失，忘了設定時 policy 報錯而不是外洩。a：請求和連線不是一對一。c：RLS 不在乎設定的層級。d：transaction 模式的連線池不會替你清 session 設定（第 36 課）。

練習 8：orders 有租戶 RLS。DBA 用 postgres（超級使用者）建了 CREATE VIEW v_orders AS SELECT * FROM orders 並 GRANT SELECT 給 app_user。app_user 設定台北店後查 v_orders，會看到什麼？

✓ view 預設以擁有者的權限與 policy 存取底層的表（CREATE VIEW 文件），擁有者是超級使用者或表的擁有者時 RLS 不生效。PostgreSQL 15 起加上 WITH (security_invoker = true)，改用查詢者的權限和 policy，才會是 b 的結果。c：已經 GRANT SELECT。d：view 照常運作，問題是「用誰的身分」。

常見錯誤

  • 軟刪除後有些查詢忘了過濾：已刪除的資料又出現在列表、報表裡。用 view 或 RLS 集中處理過濾條件。
  • 軟刪除的唯一約束寫成 UNIQUE (phone, deleted_at)：NULL 彼此不相等，未刪除的重複擋不住。用部分唯一索引 WHERE deleted_at IS NULL。
  • 以為外鍵會擋住指向已刪除資料的寫入：軟刪除的列還在，外鍵照樣通過，ON DELETE CASCADE 也不會觸發。在程式或 trigger 處理。
  • 稽核只寫在程式裡：直接下 SQL 或別的服務改資料就沒有紀錄。用 trigger。
  • SECURITY DEFINER 函式沒有固定 search_path：呼叫者可以用暫存表或同名函式劫持。加上 SET search_path = …, pg_temp（pg_temp 明確放最後，只寫 public 不夠），或表名都寫完整的 schema。
  • 時段用包含結尾的 [] 區間：相鄰的時段被當成重疊。一律用 [)。
  • 用 UNIQUE 或「先查再寫」防止時段重疊：UNIQUE 只擋完全相同的值，先查再寫在並發時會一起通過。用 EXCLUDE 或 18 的 WITHOUT OVERLAPS。
  • 多租戶的表有 store_id，卻沒放進主鍵、外鍵、索引：跨租戶的引用寫得進去、查詢走不到好的索引。用複合鍵，索引以 store_id 開頭。
  • 租戶設定用 session 層級：經過連線池串到下一個請求。用 set_config(…, true) 或 SET LOCAL。
  • 在有 RLS 的表上建 view 卻沒設 security_invoker：view 以擁有者的身分查表，RLS 被繞過。
  • 用超級使用者或擁有者測 RLS；只測「看不到別人」：前者永遠看到全部，後者抓不到「誰都看不到」。用應用程式的 role 測兩個方向，並故意改壞 policy 確認測試會失敗。

小結

這課把三家分店的四條需求做進資料庫，每一條都讓資料庫自己守住，程式忘了也不會出事：

  • 會員要能復原 → 軟刪除：deleted_at＋view 集中過濾；唯一性用部分唯一索引（NULL 彼此不相等）；外鍵與 CASCADE 不知道「已刪除」；個資要真的刪除或去識別化，或改用封存表。
  • 誰改了拿鐵的價格 → 稽核 trigger：通用函式用 TG_OP、TG_TABLE_NAME、to_jsonb(OLD/NEW)、current_setting('app.user_id', true)；應用程式碰不到稽核表，函式用 SECURITY DEFINER 並固定 search_path（pg_temp 放最後）。
  • 同一時段只賣一次 → 範圍型別用半開區間 [)；EXCLUDE USING gist (… WITH =, … WITH &&) 在寫入時擋重疊（23P01），可加 WHERE，需要 btree_gist；PostgreSQL 18 另有 WITHOUT OVERLAPS 與 PERIOD 外鍵。
  • 分店彼此看不到 → 租戶 id 進主鍵、複合外鍵、索引；RLS＋每個交易 set_config(…, true)；應用程式不能用擁有者或超級使用者連線；view 要 security_invoker = true。
  • 證明隔離有效 → 用 SQL 測：以應用程式的 role、測兩家以上的店、同時測「看得到自己」與「看不到別人」，再故意改壞 policy 確認測試會失敗。
