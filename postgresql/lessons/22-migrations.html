階段 7：實務 · 第 22 課

改 schema 與 migration

咖啡店後台已經上線半年。當初趕著開店，products 表建得很隨便：price 存成文字，後台想算「漲價 10 元」直接報錯；有些商品的 category 是空的，分類篩選漏掉它們；還有一個早就沒人用的 legacy_code 欄位。現在老闆又要一個新功能：商品可以暫時下架。你接到的任務是把這張表整理好，並讓這次整理安全地送到同事的電腦、測試環境和正式環境。

難處在於表裡已經有真實資料，網站也一直有人在用，不能 DROP TABLE 重建。這一課整課都在完成這個任務：先在自己電腦上用 ALTER TABLE 一步步把表改好，再把這些修改寫成 migration 檔，讓每個環境做一模一樣的修改，最後處理上線那一刻的風險。

這課會用到：
  • 第 12 課的約束：NOT NULL、CHECK 讓資料庫擋掉不合規則的資料。
  • 第 18 課的交易與 DDL：BEGIN … COMMIT 包起來的語句全做或全不做，CREATE TABLE、ALTER TABLE 這類改結構的語句也一樣。
  • 第 19 課的鎖：一個交易拿著鎖時，想碰同一份資料的其他交易要排隊等。
這課的路線：
  1. 表已經有資料，怎麼改結構：ALTER TABLE 原地修改，以及整個任務的最小答案。
  2. 在自己電腦上把 products 改好：加「是否供應中」、把 price 改成整數、補上規則、改名和刪欄位，每一步都在問「既有的資料怎麼辦」。
  3. 同事和正式環境怎麼做一樣的修改：migration 檔、up／down，以及一支 migration 跑到一半失敗時為什麼不會留下半套結構。
  4. 工作中誰幫你管 migration：Supabase、Prisma、Strapi 的做法差在哪。
  5. 上線那一刻：一句 ALTER 為什麼可能讓網站停擺，欄位非改名不可時怎麼拆成幾次部署。

表裡已經有資料，要怎麼改它的結構？

先把「結構」和「資料」分開。資料庫的 schema 指的是結構：有哪些表、每張表有哪些欄位、每個欄位是什麼型別、有哪些約束和索引。資料是放進這個結構裡的內容。schema 決定資料能長什麼樣子，例如 price 是 text，資料庫就只把它當文字看待，不會讓你拿來加減。

用咖啡店的菜單板來想：板子上畫好了「品名、價格」兩欄，每一行寫著一個商品。現在要多一欄「是否供應中」。你不會把整塊板子連同上面寫好的商品一起丟掉，而是在旁邊畫一欄，替已經寫好的每一行補上一個值。改結構的時候，最需要想清楚的永遠是這件事：已經在裡面的資料要怎麼辦。

如果把表刪掉重建，結構是乾淨了，但半年來的商品資料也沒了；就算先匯出再匯回，這段時間網站也沒辦法用。所以 SQL 提供了 ALTER TABLE：在原本的表上修改結構，資料留在原地。加欄位、改型別、加約束、改名、刪欄位，都是 ALTER TABLE 後面接不同的動作。

這也是開場任務的最小答案，分成三件事：

  1. 用 ALTER TABLE 原地修改，每一步先想好既有的資料怎麼處理。
  2. 把這些 ALTER 寫成 migration 檔放進 git，讓每個環境照順序執行一樣的修改。
  3. 上線時注意 ALTER 會鎖住整張表；改名、刪欄位這類會讓舊程式壞掉的修改，拆成幾次部署。

接下來照這個順序做。第一件事，先看看要整理的這張表現在長什麼樣子。

這也說明了為什麼 NOT NULL 能跟著一起加。NOT NULL 規定這一欄不能是空的，而既有的列都已經被填上 true，沒有一列違反。如果只寫 ADD COLUMN is_available boolean NOT NULL、沒寫 DEFAULT，既有的列在新欄位上會是 NULL，跟 NOT NULL 互相矛盾，整句就會失敗（表是空的除外）。所以要加一個必填欄位時，要先決定舊資料該填什麼：「所有商品預設都在供應中」是合理的值，就把它寫成 DEFAULT。

在大表上加欄位會不會很慢，要看 PostgreSQL 的版本，細節見課末。

還有一個保證要知道：只要有一列轉不過去，整個 ALTER 就會失敗，表維持原樣，不會出現「前一半是數字、後一半還是文字」。所以在正式資料上改型別之前，先用 SELECT 找出轉不過去的值，比在部署時才看到錯誤好得多。

改名和刪欄位共同的教訓是：schema 不只屬於資料庫，所有讀寫它的程式都依賴它。這一點到這課最後一節會變成關鍵。不過在那之前有一個更直接的問題：剛才這一連串 ALTER 都只在你的電腦上跑過，同事的資料庫、正式環境的資料庫都還是舊的。

同事和正式環境，怎麼做一模一樣的修改？

最直覺的做法是把剛才的 SQL 存起來，到每台機器手動貼一次。只有你一個人、只改一次的時候還行，但團隊裡每個人都在改 schema，幾個月下來會累積幾十次修改。誰記得正式環境跑到哪一次了？同事休假兩週回來，他的資料庫缺了哪幾次？漏跑一次，程式就會在某個環境找不到欄位。

解法是把每一次 schema 的修改寫成一個檔案，這個檔案叫 migration。migration 的原意是遷移，指把資料庫從一個版本的結構搬到下一個版本。這課的整理工作，寫成 migration 會像這樣：

migrations/
  001_create_customers.sql
  002_create_orders.sql
  003_add_is_available_to_products.sql
  004_change_price_to_integer.sql

這幾個檔案要能取代「到每台機器手動貼 SQL」，靠的是四個規則：

  • 有編號、照順序執行：004 一定在 003 之後跑，因為後面的修改可能依賴前面的。例如 003 建了 is_available，之後若有一支要替它加索引，就必須排在 003 後面。
  • 進版本控制（git）：schema 的修改跟程式碼一起 review、一起部署。看 git 記錄就知道「這個欄位是誰、為什麼加的」。
  • 只往後加、不改舊的：已經在別的環境跑過的 migration 不能再修改。那個環境不會再跑一次，改了舊檔只會讓各環境變得不一致。要修正就寫一支新的。
  • 資料庫自己記得跑到哪：migration 工具會在資料庫裡建一張表（例如 schema_migrations），記錄已經執行過哪些編號，部署時只跑還沒跑過的。

第四點回答了「誰記得跑到哪」：不靠人記，靠每個資料庫裡的那張記錄表。下圖是同一組 migration 檔遇到兩個進度不同的資料庫：

有了往前的路，自然會問：如果某一支 migration 寫錯了，能不能退回去？

migration 寫錯了，能退回去嗎？up 和 down

有些工具要求每支 migration 寫兩個方向：up 是套用這次的修改，down 是把它撤銷。以 003 為例：

-- 003_add_is_available_to_products
-- up
ALTER TABLE products ADD COLUMN is_available boolean NOT NULL DEFAULT true;

-- down
ALTER TABLE products DROP COLUMN is_available;

開發時 down 很好用：在自己電腦上試一個新欄位，發現設計不對，跑 down 退回去、改好再跑 up。但正式環境很少真的跑 down。看看上面的 down 做了什麼：DROP COLUMN。如果 003 上線後已經有店員把幾個商品設成下架，跑 down 就會把這些資料一起刪掉，而且刪掉之後無法復原。很多修改的 down 只能還原結構，還原不了資料。

所以實務上，正式環境的 migration 出問題時，通常是再寫一支新的 migration 往前修：例如預設值寫錯了，就新增一支把預設值改對，而不是退回去。這也跟上一節「只往後加、不改舊的」一致：正式環境的歷史只往前長。

💡 實務上：migration 檔要和程式碼一起被 review
團隊裡加一個「會員點數」功能，PR 通常同時包含 migration 檔和用到新欄位的程式碼。review 時資深工程師會特別看 migration：有沒有 DROP 或 RENAME、在大表上會不會鎖很久、加 NOT NULL 前有沒有先補資料，也就是這課前半每一步問過的問題。很多團隊也會設定 CI，也就是每次推 PR 時自動執行的檢查，讓它從空資料庫把所有 migration 跑一遍，確認一個新同事 clone 下來就能建出完整的 schema。

還有一種出錯更麻煩：不是寫錯，而是一支 migration 裡有好幾句，執行到一半失敗了。

一支 migration 跑到一半失敗，資料庫會停在半套結構嗎？

假設一支 migration 有三句：建記錄表、加欄位、寫入記錄。前兩句成功、第三句失敗，資料庫就停在「欄位加了，但記錄表說沒跑過」的狀態。下次部署時工具會再跑一次這支，第二句因為欄位已經存在而失敗，從此卡住，只能有人手動進資料庫收拾。

PostgreSQL 避開了這個問題。第 18 課看過，CREATE TABLE、ALTER TABLE 這些改結構的語句也能包在交易裡：任何一句失敗，前面的也一起取消，資料庫不會停在改到一半的狀態。products 的修改前面已經在這頁跑過了，再加一次會因為欄位已存在而失敗，所以這裡用下一支還沒跑過的 migration：替會員加 email 欄位。這一格把它連同「寫入記錄表」包在同一個交易裡，模擬 migration 工具會做的事：

第一次執行，記錄表裡多了 005_add_email_to_customers。再執行一次會失敗，因為 email 欄位已經存在；而且因為三句在同一個交易裡，schema_migrations 也不會多出重複的記錄。「修改結構」和「記錄跑到哪」要嘛一起成功、要嘛一起不算，這就是 migration 工具在 PostgreSQL 上做的事，本質上就是這一格。不是每種資料庫都有這個保證，比較見課末。

到這裡為止，migration 檔、記錄表、交易都是手寫的。工作中通常不會自己寫這套機制，而是交給工具。

工作中，誰幫你建 migration 檔、記錄跑到哪？

工具做的事跟上一節的手寫版本一樣：產生有順序的 migration 檔、在資料庫裡記錄跑到哪一支、部署時只跑缺的。差別在 migration 檔從哪裡來。你可能會遇到這三種：

工具migration 長什麼樣特點
Supabasesupabase/migrations/20261029083000_add_points.sql檔名用時間戳當編號，內容就是純 SQL。supabase migration new 名稱 建檔、supabase db push 套用到遠端
Prismaprisma/migrations/20261029083000_add_points/migration.sql你改 schema.prisma，prisma migrate dev 比對差異、自動產生 SQL 檔；部署用 prisma migrate deploy
Strapi沒有 migration 檔（schema 部分）你在 Content-Type Builder 改欄位，Strapi 啟動時自動同步 schema 到資料庫

Supabase 和 Prisma 的編號都是時間戳，不是 001、002。原因是團隊裡好幾個人同時在不同分支建 migration，用流水號很容易兩個人都建了 005；時間戳幾乎不會撞，排序也照建立的先後。兩者的差別在誰寫 SQL：Supabase 由你手寫，Prisma 由工具比對 schema.prisma 的差異幫你產生。Prisma 產生的檔案仍然是看得到的 SQL，提交前應該打開讀一遍，確認它做的是你想要的事。

Strapi 走的是另一條路：沒有 schema 的 migration 檔，它在啟動時把 Content-Type Builder 裡的設定同步到資料庫。很方便，代價是你看不到、也控制不了它下了什麼 SQL。回想前面「改名和刪欄位」那節的教訓：你想的是「把欄位改名」，它做的可能是「刪掉舊欄、建新欄」，舊資料就不見了。所以對資料需要更多控制時，很多團隊會選擇 Supabase、Prisma 這種「每一步都是看得到的 SQL」的做法。Strapi 其實也有放自訂腳本的地方，見課末。

不管用哪個工具，最後送進資料庫的都是 ALTER TABLE。工具解決了「每個環境跑一樣的修改」，但沒有解決另一件事：這些 ALTER 在正式環境執行的那一刻會發生什麼。

上線那一刻：為什麼一句 ALTER 可能讓網站停擺？

在自己電腦上，前面每一格都是一按就完成。正式環境的差別有兩個：表大得多，而且隨時有人在讀寫它。這兩件事加在一起，問題出在鎖。第 19 課看過，修改一列時會鎖住那一列，其他想改同一列的交易要排隊。ALTER TABLE 鎖的範圍大得多：大部分的 ALTER TABLE 會對整張表加最強的鎖，執行期間其他人連 SELECT 都要排隊。道理很直接：表的結構正在改，資料庫不能讓別人在這時候用舊的結構讀資料。

鎖住整張表多久，取決於這句 ALTER 要做多少事。回頭看這課做過的動作：

  • ALTER COLUMN … TYPE：通常要改寫整張表，因為每一列的值都要換成新型別。一千萬列可能要好幾分鐘，這段時間整張表都不能用。
  • SET NOT NULL、ADD CONSTRAINT … CHECK：「補上規則」那節說過，加規則前要檢查既有的每一列，所以要掃過整張表。

這課沒做、但很常跟 migration 一起出現的 CREATE INDEX 也一樣：建索引期間不能寫入這張表。正式環境用 CREATE INDEX CONCURRENTLY，比較慢但不會擋住寫入。

就算 ALTER 本身很快，例如只改個預設值，還有一個陷阱：排隊。如果表上有一個跑很久的查詢，ALTER 拿不到鎖，只能排隊等它；而 ALTER 後面進來的所有查詢，又排在 ALTER 後面。結果是一句本來一瞬間就做完的 ALTER，讓整張表在那個慢查詢結束之前都沒辦法用。實務上會在 migration 開頭設 SET lock_timeout = '3s'，意思是等鎖最多等 3 秒，等不到就放棄這次、晚點再試，寧可 migration 失敗重跑，也不要讓網站跟著排隊。

鎖的問題可以靠挑時間、設 lock_timeout 處理。但改名和刪欄位還有另一個問題，跟鎖無關：就算 ALTER 一瞬間完成，程式還是會壞。

欄位非改名不可時，怎麼拆成幾次部署？

前面的 name 只是示範，改完又改回來了。換一個真的要改的：客服希望 customers.phone 改叫 mobile，因為現在只收手機號碼。直接 RENAME 會出什麼事，要先看部署是怎麼進行的。

部署不是瞬間完成的。24 小時都有人用的服務，通常跑在好幾台伺服器上，部署時一台一台換成新版程式。換到一半時，有幾台還是舊版、有幾台已經是新版，兩個版本的程式同時連著同一個資料庫。如果在這時候把 phone 改名成 mobile，舊版程式找不到 phone，全部報錯；如果先不改名，新版程式又找不到 mobile。不管 RENAME 放在部署前還是部署後，總有一個版本會壞。

解法是讓 schema 在每一刻都同時滿足兩個版本，把一次改名拆成好幾次部署：

逐步看為什麼每一步都安全：

  1. 加新欄位：只多了 mobile，舊程式根本不知道它存在，照常讀寫 phone。
  2. 雙寫並搬資料：部署一版同時寫 phone 和 mobile 的程式，再用 UPDATE 把舊會員的 phone 複製到 mobile。這時兩欄的資料一致，不管哪一版程式在讀都拿得到正確的號碼。
  3. 改讀新欄位：部署只用 mobile 的程式。如果新版有問題，退回上一版也沒關係，因為 phone 還在、而且資料是同步的。
  4. 刪舊欄位：確定已經沒有任何程式、報表、排程在讀 phone，才 DROP COLUMN。這是唯一無法退回的一步，所以放在最後、等觀察夠久再做。

改型別、拆表也是同樣的思路：永遠讓「舊版程式」和「新版程式」在同一個 schema 上都能跑，因為部署的那段時間，兩個版本會同時存在。這也回答了開場任務的最後一塊：這課對 products 做的修改裡，加有 DEFAULT 的欄位可以直接上；補規則在小表上可以直接上，大表要先設 lock_timeout、挑離峰時段（不擋寫入的做法見第 34 課）；改名、刪欄位、改型別這類會讓舊程式壞掉的修改，要先想好新舊版程式怎麼共存。

💡 實務上：先問「能不能停機」再決定要不要拆步驟
expand / contract 要多部署好幾次，成本不低。內部用的後台、資料量小、可以公告半夜停機維護幾分鐘的系統，停機、跑 migration、換上新版程式，通常就夠了。真正需要拆步驟的是 24 小時都有人在用的服務：這類服務部署時常是多台伺服器輪流換成新版，有一段時間新舊程式會同時連著同一個資料庫。資深工程師會先問「能不能停機」「部署時新舊版會不會同時在跑」，再決定做法，並在 PR 裡寫明每一步的部署順序。

各種 ALTER 拿什麼鎖、怎麼在不擋住寫入的情況下加約束和回填大量資料，第 32 課和第 34 課會深入。

補充與查表

  • 加有預設值的欄位會不會很慢：PostgreSQL 11 之後，加一個有固定 DEFAULT 的欄位不需要改寫整張表，就算有上億列也幾乎是瞬間完成。
  • 其他 ALTER COLUMN 動作：ALTER COLUMN … DROP NOT NULL 可以拿掉必填的規則；ALTER COLUMN … SET DEFAULT … 可以改預設值。
  • DDL 放進交易：PostgreSQL 可以把 CREATE TABLE、ALTER TABLE 包在交易裡整批撤銷，MySQL 就做不到，這是 PostgreSQL 很受歡迎的原因之一。
  • Strapi 的自訂腳本：Strapi 有 database/migrations 資料夾可以放自訂的資料搬移腳本，但 schema 本身仍由它自動管理。

練習

練習 1：咖啡店要推出會員集點。幫 customers 加一個欄位 points（整數、不能是 NULL），既有的會員都從 0 點開始。

練習 2：orders.ordered_at 當初被建成 text，裡面存著像 '2026-10-01 09:30' 的字串（都是台灣時間）。把它改成 timestamptz，既有的資料要保留。

練習 3：要讓 customers.city 變成必填（NOT NULL），但有幾位舊會員的 city 是 NULL。先把這些 NULL 改成 '未知'，再加上 NOT NULL。

練習 4：要幫 orders 加一個名為 orders_total_check 的約束，規定 total >= 0。但有一筆訂單的金額被打成負數（多打了負號）。先把它改成正確的正數，再加上約束。

練習 5：正式環境的 customers 有 500 萬列，網站 24 小時都有人用。要把 phone 改名為 mobile，哪個做法最安全？

✓ 部署期間新舊兩版程式會同時存在，任何一刻 schema 都要讓兩版都能跑。a 在部署空窗期舊程式會壞；b 新程式一上線就找不到欄位。分步驟的 expand / contract 每一步都可以退回。

練習 6：同事發現上週已經部署到正式環境的 20261020_add_points.sql 裡，DEFAULT 寫成了 10（應該是 0）。正確的處理方式是？

✓ 已經跑過的 migration 不會再被執行，改了也沒用，還會讓各環境不一致。手動改則沒有留下記錄，其他環境不會跟著改。往前寫一支新的 migration 才能讓每個環境都正確。

常見錯誤

  • 加 NOT NULL 或 CHECK 時沒先清資料：加約束時會檢查既有的每一列，只要有一列不符合就會失敗。先用 SELECT 找出不合格的列，修好再加。
  • 改型別忘了 USING：text 轉數字或日期，PostgreSQL 不會替你猜，要寫 USING 欄位::新型別；資料比較髒時，在 USING 裡先整理再轉。
  • 修改已經部署的 migration：跑過的環境不會再跑一次，改了只會讓各環境不一致。永遠往後加新的。
  • 直接在正式資料庫手動改 schema：其他環境和 migration 檔都跟著對不上，下次部署可能出錯。
  • 以為 RENAME、DROP 只影響資料庫：所有讀那個欄位的程式、報表、排程都會壞掉；部署期間新舊版程式並存時，要用先加、再搬、最後刪的做法。

小結

  • 表裡有資料時用 ALTER TABLE 原地改結構，每一步先想「既有的資料怎麼辦」：ADD COLUMN 用 DEFAULT 替舊列填值、ALTER COLUMN … TYPE … USING 說明舊值怎麼轉、ADD CONSTRAINT 和 SET NOT NULL 前先修好不合格的資料。
  • RENAME 和 DROP COLUMN 在資料庫裡一瞬間完成，但用到舊名稱的程式會立刻壞掉，刪掉的資料無法復原。
  • migration 檔讓每個環境做一樣的修改：有編號、照順序、進 git、只往後加，資料庫用記錄表記得跑到哪一支。
  • down 在開發時好用，正式環境出問題通常寫一支新的 migration 往前修。
  • PostgreSQL 的 DDL 可以放在交易裡，一支 migration 失敗會整支撤銷，不會留下半套結構。
  • 正式環境的 ALTER TABLE 會鎖整張表，用 lock_timeout 避免整張表跟著排隊；新舊版程式會同時存在時，用「先加、再搬、最後刪」讓兩版都能跑。
