階段 0：基本觀念 · 第 1 課

資料庫是什麼

朋友開的咖啡店請你做點餐系統。你是前端工程師，最熟悉的做法是寫一個小小的 Node 後端，把顧客和訂單存成伺服器上的一個 orders.json：收到新訂單就讀檔、把新訂單加進陣列、寫回去。開店第一個月一切正常。第一次週末尖峰，兩台收銀機同時在點單，月底對帳時發現少了一筆訂單：店員記得有收錢，檔案裡卻找不到。

這一課從這筆消失的訂單出發，回答三件事：資料為什麼會不見、資料庫怎麼避免它、咖啡店的資料搬進 PostgreSQL 之後長什麼樣子。最後你會在這個頁面上對一個真正的 PostgreSQL 下第一句 SQL，查出咖啡店的顧客名單。

這課的路線：
  1. 週末那筆訂單為什麼不見：把資料存成 JSON 檔，多人同時寫、寫到一半當機時會發生什麼事。
  2. 資料庫替你做了哪些事：DBMS 是什麼，它怎麼一一解決上面的問題（開場問題的答案）。
  3. 資料庫放在系統的哪裡：為什麼 Vue 前端不能直接連資料庫，帳密只放在後端。
  4. 資料在 PostgreSQL 裡長什麼樣、怎麼跟它要資料：表格、用編號連起來的關聯，以及只說「要什麼」的 SQL。
  5. 為什麼選 PostgreSQL，然後動手：SELECT * FROM customers; 每個字在做什麼。

週末那筆訂單為什麼不見了？

先把後端存訂單的流程寫清楚。每收到一筆新訂單，程式做三步：

  1. 把整個 orders.json 讀進記憶體，變成一個陣列。
  2. 把新訂單 push 進這個陣列。
  3. 把整個陣列寫回 orders.json，覆蓋原本的檔案。

只有一台收銀機時，這三步一次只會有一組在跑，不會出錯。週末兩台收銀機幾乎同時送出訂單。你可能會想：Node 是單執行緒，兩組流程怎麼會同時跑？關鍵在讀檔和寫檔是非同步的：A 在 await readFile 等磁碟回應的空檔，Node 不會閒著，而是去處理 B 的請求。於是兩組「讀、改、寫」穿插執行，流程就交錯了：

  1. 收銀機 A 讀檔，拿到 100 筆訂單。
  2. 收銀機 B 也讀檔，同樣拿到 100 筆，因為 A 還沒寫回去。
  3. A 加上自己的訂單，寫回 101 筆。
  4. B 加上自己的訂單，也寫回 101 筆。B 手上的陣列是第 2 步讀到的舊版本，裡面沒有 A 的那筆。

最後檔案裡只有 101 筆，A 的訂單被 B 整個蓋掉了。兩邊的程式都沒有報錯，所以當下沒人發現，要到對帳才知道。這就是那筆消失的訂單。這種「讀出來、改、寫回去」的流程，只要有兩個人同時做，後寫的就會蓋掉先寫的；把資料存成 Excel 讓兩個店員同時編輯，也是同一個問題。

同時寫入只是第一個問題。資料一直存在 JSON 檔裡，接下來還會遇到這些：

  • 寫到一半當機：下單要做兩件事：扣掉一杯拿鐵的庫存，再新增一筆訂單。程式扣完庫存、還沒寫訂單時伺服器斷電，重開之後庫存少了一杯，卻沒有任何訂單對應。更糟的情況是寫檔寫到一半斷電，orders.json 只剩前半段，整個檔案都解析不了。
  • 資料變髒：JSON 檔不管你放進什麼。有人在價格打了「八十」，有人把電話打成 09l2…（小寫 L），檔案都照收。等到月底加總營業額時程式才出錯，這時已經不知道是哪一天、誰寫進去的。
  • 資料變多變慢：累積到十萬筆訂單，要找「王小明上個月買了什麼」，程式得把整個檔案讀進記憶體，一筆一筆比對。每多一筆訂單，每次查詢就慢一點。
  • 誰都能看全部：工讀生只需要看今天的訂單，但能讀這個檔案的人，也就能讀整份顧客電話名單。檔案只有「能讀」和「不能讀」，沒辦法說「這個人只能看這幾個欄位」。

這些問題每一個都能自己寫程式解決：同時寫入要自己加鎖，寫到一半要自己設計復原，髒資料要自己寫檢查，查詢慢要自己建目錄，權限要自己做。每一項要寫對都很難，而且出錯時往往不會報錯，像那筆消失的訂單一樣，靜靜地讓資料變得不正確。那有沒有人已經把這些難題解好了？

資料庫到底替你做了哪些事？

有，這就是資料庫管理系統。先把兩個常混在一起的名詞分清楚：

  • 資料庫（database）：一堆有組織的資料本身，例如咖啡店所有的顧客、商品和訂單。
  • 資料庫管理系統（DBMS，database management system）：負責存放、查詢、保護這些資料的軟體。PostgreSQL 就是一套 DBMS。

日常講話常把兩者都叫「資料庫」，看上下文就知道指的是哪一個。這門課後面說「資料庫會擋下來」，指的是 DBMS 這套軟體在做事。

換成資料庫之後，後端程式不再自己讀檔寫檔，而是把「新增這筆訂單」這個要求送給 PostgreSQL，由它決定怎麼寫進磁碟。上一節的五個問題，對應到它替你做的五件事：

JSON 檔遇到的問題資料庫替你做的事哪一課細講
兩台收銀機同時寫，後寫的蓋掉先寫的所有修改都由資料庫經手，它自己協調同時進來的修改。每一筆改動不是被保留，就是被明確地拒絕，不會默默消失。第 18 課、第 19 課
扣了庫存、訂單沒寫進去就當機可以把好幾個動作綁成一組，結果只有全部完成或全部不算兩種；當機重開後，資料庫會回到一致的狀態。第 18 課
價格欄被打成「八十」每一欄事先宣告型別和規則，不合規則的資料在寫入那一刻就被拒絕。第 2 課、第 12 課
十萬筆訂單，找一個人的紀錄要整份讀完可以預先建好查找用的目錄，不用每次從頭比對。第 20 課
工讀生也能看到全部顧客電話內建帳號與權限，可以細到「這個帳號只能讀這張表」，甚至「只能看到自己的那幾列」。第 24 課

回到那筆消失的訂單：如果兩台收銀機是把訂單交給 PostgreSQL，兩筆新增會由資料庫排好先後，各自寫進去，不存在「誰把誰的整份資料蓋掉」這件事。這就是開場問題的答案：資料不見，是因為兩個程式各自讀寫同一份檔案、沒有人在中間協調；資料庫的工作就是站在中間當那個協調者，同時擋下壞資料、守住權限。

不過有個前提：要把「改」這個動作交給資料庫做，例如直接 INSERT，或寫成 UPDATE ... SET stock = stock - 1。如果後端還是先 SELECT 讀出庫存、在程式裡算好、再 UPDATE 寫回去，這個「讀出來、改、寫回去」的空檔一樣會讓後寫的蓋掉先寫的，換成資料庫也救不了。這個坑叫 lost update，正確做法在第 19 課。

這也說明了資料庫和「比較大的 Excel」的差別。表格的樣子很像，但重點不在樣子，而在這五件事：同時多人存取、當機不壞資料、型別檢查、快速查詢、權限。

💡 實務上：只要有「多人用、要留紀錄」，就該上資料庫
會員、訂單、預約、後台管理這類系統，第一天就會放進資料庫，沒有人等出事才搬，咖啡店的點餐系統也是。反過來，只有自己用的小工具、一次性的資料整理，用 JSON 或試算表反而省事。判斷時可以問自己三題：會不會有兩個人同時寫？資料丟了要不要賠？之後要不要查「某人上個月買了什麼」？只要有一題答「會」，就用資料庫。

決定要用資料庫之後，下一個問題是它要裝在哪裡、誰可以連它。你寫了好幾年 Vue，可能會想：前端直接連資料庫，少寫一層 API 不是比較快嗎？

資料庫放在系統的哪裡？Vue 前端可以直接連嗎？

不行。先看咖啡店的系統搬進資料庫之後，各個部分怎麼互相溝通：

從左到右讀這張圖。收銀機的畫面是前端，它用 HTTP 呼叫後端 API，例如送出「新增一筆訂單」。後端收到之後，用 SQL 這種語言請 PostgreSQL 把訂單寫進去。PostgreSQL 再自己決定怎麼把資料存成磁碟上的檔案。

為什麼中間一定要隔著後端？要連上資料庫，需要帳號和密碼。前端程式會被打包成 JS，下載到每一位使用者的瀏覽器裡執行，打開開發者工具就看得到內容。如果連線用的帳密寫在前端，等於把它發給每一位訪客，任何人都能直接連進資料庫，想查什麼就查什麼，包括整份顧客電話名單，甚至直接刪資料。

所以資料庫的帳密只放在後端。後端像櫃檯：前端只能透過它開出來的 API 提出要求，後端先檢查這個人是誰、有沒有權限，再決定要對資料庫下什麼 SQL、回傳哪些欄位。前端能拿到什麼，由後端決定。有些服務（例如 Supabase）看起來像讓前端直連，背後其實另有一套權限機制擋著，細節見課末。

圖的右半邊還說明了另一件事：你不用管資料怎麼存在磁碟上。第一節自己處理檔案時遇到的鎖、寫到一半當機、查找目錄，還有檔案格式和快取，現在全部是 PostgreSQL 內部的事。你只需要用 SQL 跟它說「我要什麼」。

💡 實務上：資料庫帳密只存在後端的環境變數
實際專案裡，連線資訊會寫成一行 DATABASE_URL，放在後端伺服器的環境變數或雲端的 secret 設定裡，不會 commit 進 Git，更不會出現在前端打包出來的 JS。常見的坑是把 .env 推上 GitHub，或把資料庫的連接埠（port）直接開放到網路上，讓任何人都能嘗試連線。咖啡店的點餐系統也一樣：收銀機畫面只認得後端 API 的網址，DATABASE_URL 只有後端知道。Code review 時看到前端程式出現資料庫連線字串，一定要擋下來。

資料庫的位置清楚了：後端用 SQL 跟它溝通。可是 SQL 要怎麼寫，得先知道資料在 PostgreSQL 裡是什麼樣子。

咖啡店的資料搬進 PostgreSQL 之後長什麼樣子？

PostgreSQL 屬於關聯式資料庫（relational database）。這種資料庫把所有資料都存成表格：一張表放一種東西，例如一張放顧客、一張放訂單。表的每一欄是一個屬性（名字、電話），每一列是一筆資料（一位顧客）。欄和列的細節，第 2 課會自己建一張表時再講。

咖啡店原本塞在 orders.json 裡的顧客和訂單，搬進來之後大概長這樣：

customers（顧客）
idnamephonecity
1王小明0912-345-678台北
2陳美華0922-111-222新北
orders（訂單）
idcustomer_idtotal
1011190
102280
1031230

每一列都有一個 id，是這筆資料的編號，同一張表裡不會重複。注意訂單表裡沒有寫「王小明」，只寫了 customer_id = 1。要知道訂單 101 是誰買的，就拿這個 1 去顧客表找 id = 1 的那一列，找到王小明。訂單 103 的 customer_id 也是 1，所以同樣是王小明買的。

這種「表格之間用編號連起來」的關係，就是「關聯式」這個名字的由來。對照 JSON 的寫法，你可能會想直接把顧客名字和電話放進每一筆訂單物件裡，不是比較直覺嗎？為什麼要拆成兩張表再用編號接起來，第 8 課和第 11 課會詳細回答。這一課先記住：資料是一張張表格，表格之間用編號關聯。

知道資料長這樣之後，就可以開始跟資料庫要資料了。問題是，要怎麼開口？

怎麼跟資料庫要資料？SQL 只說「要什麼」

跟關聯式資料庫溝通的語言叫 SQL（Structured Query Language）。前面那張圖裡，後端和 PostgreSQL 之間那條線上寫的就是它。SQL 的寫法跟你熟悉的 JavaScript 很不一樣。同樣是「找出住在台北的顧客名字」，兩邊的寫法對照如下：

JavaScript（告訴電腦怎麼做）SQL（告訴資料庫要什麼）
const result = []
for (const c of customers) {
  if (c.city === '台北') {
    result.push(c.name)
  }
}
 
SELECT name
FROM customers
WHERE city = '台北';

JavaScript 那邊是一步一步的指令：準備一個空陣列、一筆一筆看、符合就放進去。你決定了「怎麼找」。這跟第一節 JSON 檔變慢的原因一樣：程式只會照你寫的方式，從頭比到尾。

SQL 這邊沒有迴圈、沒有變數。你只描述想要的結果：「從 customers 表，挑出 city 是台北的，給我 name 欄位」。這種只說結果、不說步驟的寫法叫宣告式（declarative）。至於要怎麼找，由 PostgreSQL 自己決定。

把「怎麼找」交給資料庫，好處是它可以挑最快的方法。資料少的時候，它就從頭掃一遍。資料多的時候，如果有人事先替 city 這一欄建了索引，它就會改用索引。索引像書末的索引頁，按欄位的值排好，記著每個值在哪幾列，查「台北」時可以直接翻到那裡，不用整張表看完。你寫的 SQL 一個字都不用改，同一句查詢就變快了。PostgreSQL 怎麼在兩種做法之間選擇，第 20 課和第 21 課會看到。

到這裡，咖啡店需要的東西都齊了：一套 DBMS、存成表格的資料、用來查詢的 SQL。剩下最後一個選擇：會講 SQL 的 DBMS 不只一套，為什麼這門課選 PostgreSQL？

那麼多資料庫，為什麼選 PostgreSQL？

MySQL、SQLite 這些也都是關聯式資料庫，也都用 SQL 溝通，九成的觀念和語法是共通的。所以先學哪一套，學到的東西大部分都帶得走。這門課選 PostgreSQL，理由有三個：

  • 免費、開源，發展超過 30 年，非常穩定。
  • 功能完整：前面對照表裡的那些能力，嚴格的資料型別、交易、權限控制，加上 JSON、全文搜尋，都是內建的，不用另外裝東西。
  • 到處都在用：Supabase、Neon、AWS RDS、Google Cloud SQL 這些雲端服務，底層都是 PostgreSQL。學會它，換平台也通用。
💡 實務上：團隊通常用託管服務，不自己架
咖啡店真的上線時，多半不會自己找一台主機裝 PostgreSQL，而是直接開 Supabase、Neon 或 AWS RDS 這類託管的 PostgreSQL，備份、升級、硬體故障交給平台處理，團隊專心寫功能。本機開發則常用 Docker 跑一個 PostgreSQL。Docker 是把軟體連同它需要的環境一起裝進獨立容器的工具，可以指定跟正式環境相同的版本，避免「我這邊可以跑」的問題。選平台時，資深工程師會先問：每天自動備份嗎？能還原到某個時間點嗎？主機放在哪個地區、離使用者近不近？費用怎麼隨資料量成長？

這門課不用你先裝任何東西。這個頁面上已經跑著一個 PostgreSQL，咖啡店的資料也放好了，下一節就直接對它下第一句 SQL。

✓ 資料庫允許很多人同時連線，並由它自己負責排好同時進來的修改，不會「默默蓋掉」。怎麼做到的會在第 18、19 課（交易與鎖）講。

練習 4：哪一個說法是對的？

✓ 資料庫帳密只放在後端；SQL 是描述「要什麼」的語言，不用寫迴圈。

常見錯誤

  • 以為資料庫就是比較大的 Excel：表格長得像，但資料庫多了型別檢查、同時多人存取、當機不壞資料、權限、快速查詢，這些才是重點。把資料放在共用試算表讓大家同時改，週末那筆訂單消失的事一樣會發生。
  • 以為用 ORM（例如 Prisma）或 Strapi 這類框架就不用懂 SQL：ORM 是讓你用程式裡的物件操作資料庫的工具，全名是物件關係對應（Object-Relational Mapping）。它只是幫你產生 SQL；Strapi 這類框架底層也是這樣做。查詢變慢、資料出錯的時候，還是要看懂它產生了什麼 SQL 才查得出原因。
  • 以為 SQL 關鍵字一定要大寫：select * from customers 也能跑。大寫只是慣例，方便一眼分出哪些是關鍵字、哪些是表和欄位的名稱。

小結

  • 把資料存成檔案、自己讀寫，兩個人同時「讀出來、改、寫回去」時，後寫的會蓋掉先寫的；寫到一半當機、髒資料、查詢變慢、權限也都要自己處理。
  • 資料庫管理系統（DBMS）替你處理這些事：協調同時進來的修改、當機不壞資料、檢查資料正確性、加快查詢、控管權限。PostgreSQL 是一套 DBMS。
  • 前端 → 後端 → 資料庫。資料庫帳密只放在後端，前端只能透過後端 API 拿資料。
  • PostgreSQL 是關聯式資料庫：資料存成表格，表格之間用編號關聯。
  • SQL 描述「要什麼」，怎麼找由資料庫決定；SELECT 欄位 FROM 表; 是最基本的查詢。
