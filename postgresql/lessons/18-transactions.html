階段 5：正確性 · 第 18 課

交易：BEGIN、COMMIT、ROLLBACK

咖啡店推出儲值卡：會員先儲值，之後可以用卡付款，也可以把餘額轉給朋友。第一個要上線的功能是轉帳。「王小明轉 100 元給陳美華」在資料庫裡是兩句 SQL：一句扣王小明的錢，一句加陳美華的錢。第 1 課列過的問題在這裡會真的發生：第一句寫進去了，第二句還沒寫，程式就出錯，100 元就從系統裡消失了。

這一課要讓轉帳和儲值卡付款不可能只做一半。用的工具是交易（transaction）：把好幾句 SQL 綁成一個整體，結果只有兩種，全部生效，或全部當作沒發生。學完你會寫出安全的轉帳，知道交易中途出錯時資料庫怎麼反應、程式該怎麼收尾，也能說清楚面試常問的 ACID。

這課會用到：
  • 第 12 課的 CHECK：寫在欄位上的規則，違反規則的 INSERT／UPDATE 會被拒絕。
  • 第 6 課的「忘了 WHERE 的災難」：UPDATE 沒寫 WHERE 會改到整張表。
這課的路線：
  1. 王小明為什麼少了 100 元：沒有交易時，資料庫怎麼處理一句一句送來的 SQL。
  2. BEGIN、COMMIT、ROLLBACK：怎麼告訴資料庫「這幾句是一組」，自己發現不對時怎麼整批取消（開場問題的答案）。
  3. 中途有一句失敗：交易進入中止狀態，為什麼只能取消，程式要怎麼收尾。
  4. ACID 與 SAVEPOINT：把前面得到的保證整理成面試用語；只想取消最後一步時怎麼辦。
  5. 建表、改表也能取消：儲值卡的表建到一半失敗，PostgreSQL 怎麼整批取消。
這一頁的執行框共用同一條資料庫連線，照你按的順序改資料。某個框 BEGIN 之後沒有結束（或中途出錯），交易會一直開著，影響後面每一個框。看到 current transaction is aborted 或結果怪怪的，先單獨執行一次 ROLLBACK;，或按上方「重置資料庫」。

王小明轉 100 元給陳美華，錢為什麼會憑空消失？

先看資料。這一課的 wallets 表一列是一張儲值卡，balance 是餘額。balance 上有一條 CHECK (balance >= 0)：任何讓餘額變成負數的修改都會被拒絕。後面「餘額不足」的情境就是靠它擋下來的。另外還有一張 purchases 表，一列是一筆用卡消費的紀錄（哪張卡、買了什麼、多少錢）。用卡付款也是兩句：扣 wallets 的餘額，再新增一筆 purchases，跟轉帳一樣必須一起成功。這節先用轉帳說明問題，付款留到練習自己寫。

王小明要轉 100 元給陳美華，需要兩句：

UPDATE wallets SET balance = balance - 100 WHERE id = 1;  -- 王小明扣款
UPDATE wallets SET balance = balance + 100 WHERE id = 2;  -- 陳美華入帳

後端程式送 SQL 的方式，通常是送出一句、等資料庫回應、再送下一句。兩次送出之間，程式可能出錯：程式有 bug、伺服器重開、網路斷線。下面三個執行框模擬這件事：第一個框是第一次送出；第二個框是第二次送出，表名故意打錯，代表程式在這一步出錯；第三個框查結果。依序執行，最後看王小明和陳美華的餘額：

王小明少了 100 元，陳美華卻沒有多 100 元。這 100 元不在任何人手上。

原因在 PostgreSQL 預設的運作方式。沒有特別指定時，每一句 SQL 自己就是一個獨立的單位，執行成功就立刻永久寫下，這種模式叫自動提交（autocommit）。第一句扣款成功，當下就寫定了；第二句失敗時，資料庫只知道「這一句失敗」，不知道它和剛才的扣款是同一件事的兩半，也就沒有理由去動已經寫定的扣款。

每一句單獨看都照規則執行了。問題是「這兩句必須一起成功」只存在你的腦中，資料庫不知道。真實系統裡，這種半套資料最難收拾：客服要從紀錄裡找出哪一筆少了另一半，再手動補上。先把錢還給王小明，讓資料回到原狀：

要避免這種情況，得有辦法告訴資料庫：這兩句是一組，要嘛都成功，要嘛都不算。

怎麼告訴資料庫「這兩句是一組」？

這個「一組」就是交易。寫法是用 BEGIN 開頭、COMMIT 結尾，中間放要綁在一起的 SQL：

BEGIN;      -- 開始一個交易
  …好幾句 SQL…
COMMIT;     -- 全部確定，正式生效
-- 或
ROLLBACK;   -- 全部取消，回到 BEGIN 之前的樣子

執行 BEGIN 之後，這條連線不再自動提交。後面每一句照常執行，也照常檢查 CHECK 這類規則，但修改不會立刻永久寫下，而是處於「暫定」狀態：自己這條連線看得到，其他連線看不到（別人看到什麼是下一課的主題）。執行 COMMIT 時，所有暫定的修改才一次正式生效。在 COMMIT 之前，任何時候都可以執行 ROLLBACK，把整個交易的修改丟掉，資料回到 BEGIN 之前的樣子。

先看成功的情況。把轉帳的兩句包進交易，執行後看王小明是否少 100、陳美華是否多 100：

結果和沒有交易時一句一句執行一樣。交易的差別只在失敗的時候顯現：交易裡只要有一句沒成功，扣款就不會單獨留下來。失敗有兩種：你自己發現不對、決定不要了；或者資料庫執行到一半報錯。先看第一種。

💡 實務上：直接改正式資料庫，先打 BEGIN
客服回報「這位會員的儲值金額錯了」，有時得連進正式資料庫手動修正。資深工程師的習慣是：先 BEGIN，執行 UPDATE，看回應的筆數（例如 UPDATE 1）是否符合預期，再用 SELECT 確認結果，沒問題才 COMMIT，筆數不對就 ROLLBACK。很多團隊還會要求這類 SQL 先貼給另一個人看過再執行。確認完要馬上結束交易，不要開著交易去吃午餐，那段時間你改過的那幾列，別人想再修改都得一直等你結束。

交易中間有一句失敗，資料庫會怎麼處理？

ROLLBACK 是你自己決定取消。另一種情況是你沒發現問題，資料庫在執行某一句時報錯。這次林志豪要轉 200 元給陳美華，但他的卡只有 100 元。程式先幫陳美華入帳 200 元，再從林志豪扣 200 元；扣完會變成負數，CHECK 會擋下這一句：

第二句 UPDATE 報錯之後，同一格裡後面的 COMMIT 根本沒有執行到。所以這時候交易還開著，陳美華的 +200 還處於暫定狀態。接著隨便執行一句查詢，看回來的訊息：

錯誤訊息是 current transaction is aborted, commands ignored until end of transaction block，意思是「目前的交易已經中止，在交易結束之前，送來的指令都會被忽略」。

這就是交易的中止狀態（aborted）。交易裡只要有一句失敗，PostgreSQL 就把整個交易標記為中止：之後送來的每一句都直接拒絕，直到你結束這個交易為止。這樣設計的理由是交易的承諾：全做或全不做。現在有一句沒做成，這個交易已經不可能「全做」了。如果資料庫讓你繼續執行，甚至讓你把它提交，就等於讓你把半套結果寫下去，回到第一節的問題。

所以中止的交易只剩一條路：結束它，而結束的結果只會是取消。執行 COMMIT 也沒用，它會被當成 ROLLBACK，任何修改都不會保存。執行 ROLLBACK，再看兩個人的餘額：

陳美華先加的 200 元也一起被取消了，兩個人的餘額都回到轉帳之前。這正是我們要的：轉帳的兩半要嘛一起成功，要嘛一起取消。

放到後端程式裡，這代表一個固定的寫法：開了交易之後，只要有任何一句出錯，就送出 ROLLBACK 結束交易，再把錯誤回給前端。不要在出錯之後繼續送 SQL，那些 SQL 全部會被拒絕。第 25 課會看到在程式裡怎麼寫。

回頭看第一節：兩句一起送出會怎樣？

你可能會想：第一節的半套資料，是因為兩句分成兩次送出；那把兩句一起送，是不是就不用寫 BEGIN 了？來試試看。如果把兩句放在同一次送出（同一個執行框），第二句一樣打錯表名，結果會不同嗎？執行後看王小明的餘額：

王小明的錢沒有被扣。PostgreSQL 收到一次送來的好幾句 SQL、裡面又沒有寫 BEGIN 時，會自動把它們包在一個隱含的交易裡：全部成功就自動提交，有一句失敗就全部取消。

但不要依賴這個行為。它只在「同一次送出」時成立，而後端程式的 ORM 和資料庫套件大多是一句送一次，例如先 UPDATE、拿到結果、再 INSERT，從程式碼很難看出哪幾句剛好被一起送出。需要綁在一起的操作，就明確寫 BEGIN／COMMIT。

💡 實務上：先問「做到一半失敗，會留下什麼？」
咖啡店的結帳要扣庫存、建立訂單、新增訂單明細、扣儲值金，任何一步失敗都不該留下半套，這就是一個交易的範圍。只有一句 SQL 的操作（例如改暱稱）不需要另外包交易，它本身就是全做或全不做。要注意的是交易只管得到資料庫：寄確認信、推播通知這類外部動作沒辦法 ROLLBACK，應該放在 COMMIT 成功之後才做，否則可能信寄出去了、訂單卻被取消。Code review 看到「好幾句寫入卻沒有包交易」，通常是值得提出來的問題。

交易到底保證了什麼？用 ACID 說清楚

到這裡，轉帳已經做對了。資料庫領域把交易提供的保證整理成四個字母 ACID，面試問到交易幾乎一定會問。四項裡有兩項你剛才已經親眼看到，一項留到下一課，一項這個頁面沒辦法示範：

字母名稱保證什麼在這課的哪裡
AAtomicity 原子性整個交易是一個不可分割的單位：全做或全不做入帳失敗，扣款跟著取消：轉帳不會只扣款沒入帳
CConsistency 一致性交易前後，資料都符合所有規則（主鍵、外鍵、CHECK…）CHECK 擋下負餘額，整筆轉帳被拒絕：餘額永遠不會變成負數
IIsolation 隔離性同時進行的交易不會看到彼此做到一半的狀態你轉帳到一半時，別人查不到「錢已扣、還沒入帳」的中間狀態（下一課細講）
DDurability 持久性COMMIT 成功之後，資料就確定寫下了，當機也不會不見收銀機顯示「完成」之後就算停電，紀錄還在（這頁示範不了，原因見課末）

記的時候抓住每一項管的範圍：A 和 C 管一個交易自己，不留半套、不違反規則；I 管好幾個交易同時執行；D 管 COMMIT 之後。

回到原子性：它讓轉帳出錯時整筆取消，但取消的是「整筆」，前面做對的部分也一起丟掉。有時候這太重了，你只想取消最後一步。

只想取消最後一步，不想整個重來：SAVEPOINT

情境：陳美華轉 50 元給林志豪，轉帳做完後，同一個交易裡要再送林志豪一筆紅利，但紅利金額多打了一個 0。轉帳是對的，只有紅利錯了。這時執行 ROLLBACK 會連轉帳一起丟掉，你得從頭再做一次轉帳。

存檔點（savepoint）解決這個問題。它在交易中間記下一個位置：

  • SAVEPOINT 名字：在目前的位置建立存檔點。
  • ROLLBACK TO SAVEPOINT 名字：取消存檔點之後的所有修改，存檔點之前的修改保留。交易沒有結束，可以繼續執行，最後照常 COMMIT。

林志豪只多了轉帳的 50 元，沒有那筆 1000 元紅利；陳美華少了 50 元，轉帳保留下來了。退回之後存檔點本身還在，需要的話可以再退回它一次。

存檔點在出錯時一樣有用。上一節說中止的交易只能取消，更精確的說法是只能退回去：如果出錯的那一句在某個存檔點之後，ROLLBACK TO SAVEPOINT 會讓交易回到存檔點那一刻，脫離中止狀態，存檔點之前的修改保留、交易繼續。沒有設存檔點，就只能整個 ROLLBACK。

💡 實務上：你很少親手寫 SAVEPOINT，但 ORM 常幫你寫
不少 ORM 和資料庫套件支援「巢狀交易」（在交易裡再開一個交易），底層通常就是 SAVEPOINT：內層失敗只退回內層，外層繼續。常見用法是「下單成功後順便加集點，集點失敗不該讓整筆訂單失敗」。日常開發多半一個交易就夠，看到巢狀交易時，要先弄清楚內層失敗後外層到底會不會一起取消，這是容易誤會的地方。

建表、改表做到一半失敗，也能整批取消嗎？

到目前為止，交易保護的都是資料：餘額、消費紀錄。但儲值卡上線之前，得先建出 wallets 和 purchases 兩張表。改變資料庫結構的語句，例如 CREATE TABLE、ALTER TABLE、DROP TABLE，統稱 DDL（Data Definition Language）。上線時通常一次要執行好幾句 DDL；如果第一張表建好了、第二張失敗，資料庫就停在一個不完整的結構上，程式一啟動就會出錯。

在 PostgreSQL 裡，DDL 也能放進交易、也能 ROLLBACK。這頁的兩張表已經建好了，沒辦法重演「建到一半」，所以改用最危險的 DDL 來證明：把兩張表整個刪掉。如果連刪表在交易裡都只是暫定的，CREATE TABLE 和 ALTER TABLE 的情況也完全相同。下面這格在交易裡把兩張表整個刪掉，再 ROLLBACK，最後查 wallets 還在不在：

兩張表和裡面的資料都還在。DROP TABLE 在交易裡一樣是暫定的，ROLLBACK 之後就像沒發生過。不是每種資料庫都能這樣，比較見課末。

這讓改結構也有全做或全不做的保證：一次上線的幾句 DDL 包在同一個交易裡，任何一句失敗，前面的也一起取消，資料庫不會停在改了一半的結構上。實務上，結構變更會用 migration 管理：把每一次結構變更寫成一個檔案，依序執行，並記錄目前跑到哪一個，第 22 課會細講。migration 能做到每次變更全做或全不做，靠的就是 DDL 可以放進交易。

補充與查表

  • 持久性怎麼做到、為什麼這頁看不到：PostgreSQL 靠 WAL（Write-Ahead Log，先寫日誌再改資料）做到持久性。這個頁面的 PGlite 把資料放在瀏覽器記憶體裡，關掉分頁就沒了，所以只能體驗 A、C、I；真正的 PostgreSQL 伺服器四項都有。
  • 其他資料庫的 DDL：DDL 能放進交易不是每種資料庫都有的能力，例如 MySQL 執行 DDL 時會自動 commit。換資料庫時，migration 失敗後的處理方式要重新確認。
  • 練習判分怎麼重來：第 2 課的 CREATE TABLE 練習之所以能反覆「檢查答案」而不會出現「表已經存在」，就是因為判分時把你的 SQL 包在 BEGIN…ROLLBACK 裡執行，建好的表檢查完就取消掉了。

練習

下面的練習要你自己寫 BEGIN／COMMIT，每次判分都會用一個全新的資料庫，不會影響上面的範例。如果你忘了 COMMIT，交易還開著，判分會直接告訴你「交易還沒結束」。

練習 1：用一個交易完成轉帳：張雅婷（id = 4）轉 300 元給林志豪（id = 3），最後確定生效。

練習 2：陳美華（id = 2）用儲值卡買一杯 110 元的拿鐵。在同一個交易裡做兩件事並確定生效：從她的錢包扣 110 元，並在 purchases 表新增一筆消費紀錄（wallet_id 是 2、item 是 '拿鐵'、amount 是 110）。

練習 3：下面的交易前兩句是正確的轉帳，第三句手滑把所有餘額歸零。不要刪掉任何一句，在最後補上兩句：只取消手滑的那一句、保留轉帳，並讓交易確定生效。

練習 4：交易中某一句出錯了，接著執行任何查詢都出現 current transaction is aborted。下一步應該做什麼？

✓ aborted 的交易只接受 ROLLBACK。這時候執行 COMMIT 也只會得到 ROLLBACK 的效果，出錯前的修改不會被保存。

練習 5：收銀機顯示「付款完成」（交易已 COMMIT）之後一秒，店裡停電。恢復供電後，這筆付款紀錄還在。這是 ACID 的哪一項？

✓ 持久性：COMMIT 成功就代表資料已經安全寫下，之後當機也不會遺失。

常見錯誤

  • 忘了 COMMIT：修改只在自己的交易裡看得到，別人看不到；連線一斷，整個交易就被取消。在後端程式裡，交易改過的列還會一直被鎖住（鎖是下一課的主題），別人要改同一列都得等。
  • 出錯後繼續送 SQL：交易已經中止，後面每一句都會失敗。程式裡要用 try／catch：出錯就 ROLLBACK。
  • 以為 COMMIT 能救回出錯前的部分：中止的交易 COMMIT 等於 ROLLBACK。只想保留一部分，要事先設 SAVEPOINT。
  • 交易開太久：在交易裡等使用者輸入、呼叫外部 API，交易一開就是好幾秒，鎖住的資料別人都動不了。交易要短，只包住真正需要一起成功的 SQL。
  • 以為 ROLLBACK 能還原已經 COMMIT 的資料：不行。COMMIT 之後要修正，只能再寫一個新的交易改回來。

小結

  • 沒有交易時是自動提交：每一句執行完立刻寫定，分開送出的兩句中途出錯，會留下半套資料。
  • 交易把多句 SQL 綁成一個整體：BEGIN 開始，COMMIT 確定，ROLLBACK 全部取消；COMMIT 之前的修改都是暫定的。
  • 交易裡有一句出錯，整個交易進入中止狀態，只能 ROLLBACK（或回到 SAVEPOINT）；這時 COMMIT 也等於 ROLLBACK。
  • 一次送出的多句會被包進隱含的交易，但程式通常一句送一次，要綁在一起就明確寫 BEGIN／COMMIT。
  • ACID：全做或全不做、永遠符合規則、互不干擾、COMMIT 後不會遺失。
  • SAVEPOINT 讓你只取消最後幾步，交易繼續；ORM 的巢狀交易底層多半就是它。
  • PostgreSQL 的 DDL（CREATE、ALTER、DROP）也能 ROLLBACK，migration 靠這點做到全做或全不做。
