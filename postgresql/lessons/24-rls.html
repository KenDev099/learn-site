階段 7：實務 · 第 24 課

權限與 Row Level Security

咖啡店要推出顧客 App：王小明登入之後，可以看自己的歷史訂單，也可以自己下單。同一週，後台來了新工讀生 amy，她要能查商品和顧客，但不該碰到訂單。到目前為止，你在這個頁面都用資料庫的最高管理員身分操作，想看什麼就看什麼、想刪什麼就刪什麼。上線之後不能這樣：顧客 App 送進資料庫的每一句查詢，都要有一個身分，而這個身分能做的事要剛好夠用。

最讓人擔心的情境是這個：後端某支 API 查訂單時忘了寫 WHERE customer_id = …，王小明打開 App，看到的是全店每一位顧客的訂單。這一課的任務，是在資料庫這一端把權限設好，讓就算程式寫漏了，顧客也只看得到、只寫得進自己的訂單。用到兩層權限：表層級的 GRANT／REVOKE 決定一個身分能不能碰某張表；列層級的 Row Level Security 決定碰得到的那張表裡，它看得到哪幾列。最後你會看懂 Supabase 為什麼敢讓前端直接查資料庫。

這課會用到：
  • 第 1 課的「前端不直接連資料庫」：資料庫的帳號密碼只放在後端，前端透過 API 拿資料。
  • 第 18 課的交易：用 BEGIN…COMMIT 包起來的一組 SQL，中途出錯就整組取消。
  • 第 23 課的 CREATE FUNCTION：把一段 SQL 存成資料庫裡可以重複呼叫的函式。
這課的路線：
  1. 顧客 App 用誰的身分查資料庫：PostgreSQL 的帳號叫 role，怎麼用 SET ROLE 模擬不同的人（開場問題的最小答案在這節）。
  2. 這個身分能碰哪些表：GRANT／REVOKE 讓 amy 只拿到工作需要的權限，也就是最小權限原則。
  3. 能查 orders，怎麼只看到自己的列：開啟 RLS、告訴資料庫「現在是哪位顧客」、寫第一條 policy。
  4. 顧客下單時怎麼擋住冒用別人的 customer_id：WITH CHECK；接著看誰會繞過 RLS，測試時要換成哪個身分。
  5. 連後端都省掉：Supabase 讓前端直接查資料庫，靠的就是前面這兩層。
這一頁的執行框共用同一條連線，照你按的順序改資料。範例用 SET ROLE 切換身分，最後都會 RESET ROLE 切回來。看到莫名其妙的 permission denied，先單獨執行一次 RESET ROLE;，或按上方「重置資料庫」。

顧客 App 的查詢，該用誰的身分送進資料庫？

先看你現在是誰，以及這個資料庫裡有哪些帳號。執行後看兩個結果：第一個是目前的身分，第二個是帳號清單，注意「超級使用者」和「可登入」兩欄。

你現在是 postgres，它是超級使用者（superuser）。超級使用者的意思是：PostgreSQL 的所有權限檢查對它都不算數，任何表都能讀、能改、能刪，包括這課後面要設的每一道限制。安裝資料庫時預設就有這個帳號，用來管理資料庫本身。如果顧客 App 也用它連線，後端任何一個 bug 或漏洞，影響範圍就是整個資料庫。

帳號清單裡的其他名字是這頁的 seed 建的。PostgreSQL 把「帳號」叫做 role，而且沒有把「使用者」和「群組」分成兩種東西，兩者都是 role，差別在設定：

  • 有 LOGIN 屬性、可以拿來連線的 role，就是一般說的使用者。
  • 沒有 LOGIN、不能連線，只拿來集中設定權限的 role，就是群組。
  • 把 role A 加進 role B（寫成 GRANT B TO A），A 就繼承 B 的所有權限。

這樣設計的好處是權限只要設一次。咖啡店的 seed 建了三個 role：staff 是店員群組，設定「店員可以看商品和顧客」；新來的工讀生只要加進 staff 就有一樣的權限，離職時把她移出群組就好，不用一張表一張表去改。customer 是顧客 App 查資料庫用的身分。cafe_owner 是 orders 這張表的擁有者，後面講「誰會繞過限制」時會用到。

開場問題的最小答案也就在這裡：顧客 App 不用 postgres，而是用 customer 這個權限很少的 role 查資料庫。表層級用 GRANT 限制它只能碰哪些表、做哪些操作；列層級用 RLS 規定每位顧客只看得到自己的列。兩層都是資料庫自己檢查，不依賴後端程式有沒有寫對。Supabase 用的也是同一套做法，最後一節細講。

要驗證這些限制有沒有效，得用不同的身分實際查查看。正式環境裡，不同的程式用不同的帳號密碼連線；這個頁面只有一條連線，所以改用 SET ROLE 名稱：超級使用者可以用它暫時「變成」另一個 role，之後的每一句都以那個 role 的權限執行，直到 RESET ROLE 變回原本的身分。這也是為什麼每格範例最後都有 RESET ROLE：忘了切回來，後面所有範例都會用那個權限很少的 role 執行，到處出現 permission denied。

還有一個規則跟第 18 課的交易有關：在這個頁面按一次「執行」，整格的句子會被當成一組，只要其中一句出錯，整格都會被取消，包括裡面的 SET ROLE 和 CREATE ROLE。所以出錯的範例不會留下切換後的身分，但也不會留下它建的東西。下一節第一個範例就會遇到。

身分有了，接下來的問題是：一個剛建好的 role，到底能做什麼？

新來的工讀生 amy，能碰哪些表？

新建的 role 什麼權限都沒有。建一個工讀生 amy，讓她去查訂單，執行後看錯誤訊息：

permission denied。PostgreSQL 在讀任何一列之前，先檢查這個 role 有沒有這張表的 SELECT 權限；沒有，就直接拒絕整句查詢。這正是我們要的：amy 的工作用不到訂單，她就不該看得到。

上一格出錯，依照上一節講的規則，CREATE ROLE amy 也一起被取消了，所以下一格要再建一次。這次把她加進 staff 群組。seed 已經讓 staff 能查 customers 和 products，執行後看 amy 能不能讀到商品：

查得到。amy 本身沒有被直接給過任何權限，她能查 products，是因為 GRANT staff TO amy 讓她繼承了 staff 的權限。之後店員要多一張表的權限，只要給 staff，每位店員都會一起拿到。

權限的寫法只有三種形狀：

GRANT SELECT, INSERT, UPDATE, DELETE ON 表名 TO role;   -- 給
REVOKE DELETE ON 表名 FROM role;                       -- 收回
GRANT 群組 TO 使用者;                                  -- 加入群組

SELECT、INSERT、UPDATE、DELETE 分開給，所以可以做到「能查、能改，不能刪」這種組合。給錯了用 REVOKE 收回。下面這格先給 staff 查詢和修改商品的權限，再把修改收回，最後查系統裡記錄的權限。執行後看結果剩下哪幾種權限：

只剩 SELECT，UPDATE 已經收回了。information_schema.role_table_grants 是 PostgreSQL 記錄「誰對哪張表有什麼權限」的地方，懷疑權限設錯時，第一步就是查它。

為什麼要這樣一項一項給，而不是給 amy 全部權限省事？因為有一條資安的基本原則，叫最小權限原則（principle of least privilege）：每個帳號只給它完成工作所需的最少權限。理由很實際：帳號被濫用時，損害的上限就是這個帳號的權限。有一種常見攻擊叫 SQL injection：攻擊者在輸入欄位塞進一段 SQL，讓你的程式替他執行，下一課會細講。後端一旦被這樣攻擊，攻擊者能做的事，就是後端連線用的那個帳號能做的事；只有 SELECT 權限的帳號，至少刪不掉你的表。同樣的道理，報表系統只需要讀，就給一個唯讀帳號；只有跑 migration 時才用有 ALTER 權限的帳號。

其中最重要的一條是：應用程式不要用超級使用者連線。前面說過超級使用者跳過所有權限檢查，這包括下一節要設的 RLS。後端用 postgres 連線，這課設的每一道限制都等於沒設。

💡 實務上：正式環境通常會有好幾個資料庫帳號，各管各的事
常見的分法：後端 API 用的帳號只有日常讀寫需要的權限；跑 migration 的帳號才能建表、改欄位；報表或資料分析工具用唯讀帳號；工程師查線上問題時用個人的唯讀帳號。不要整個團隊共用一組管理員密碼，出事時查不出是誰改的，有人離職也只能全部換密碼。新服務要接資料庫時，資深工程師會先問「它需要哪幾張表、哪幾種操作」，再照這個開權限，而不是先給全部、出問題再收。咖啡店的顧客 App 也一樣：它要看菜單、查訂單和訂位、下單，就只給 products、orders、reservations 的 SELECT，加上 orders 的 INSERT，其他表、其他操作一律不給。

可是 GRANT 只能回答「能不能查 orders 這張表」，答案是整張表全部或完全沒有。顧客 App 需要查 orders，但每位顧客只能看到自己的那幾列，表層級的權限做不到這件事。

顧客可以查 orders，怎麼讓他只看到自己的那幾列？

先看問題有多嚴重。seed 已經 GRANT SELECT ON orders TO customer，也就是顧客 App 用的身分可以查訂單。切換成 customer 查，執行後看出現了哪些 customer_id：

每位顧客的訂單都看得到。這就是開場擔心的情境：表層級的權限一旦開了，整張表都開了。傳統的做法是靠後端在每一句查詢加上 WHERE customer_id = 目前登入的人，只要有一支 API 忘了加，資料就外洩。

PostgreSQL 的 Row Level Security（列層級安全，簡稱 RLS）把這個 WHERE 從後端搬進資料庫。它的運作方式是：在一張表上開啟 RLS 之後，你可以為這張表寫好幾條政策（policy），每條政策規定「某個 role 做某種操作時，哪些列算數」。之後這個 role 對這張表下的每一句查詢，資料庫都會自動加上政策裡的條件，不管查詢本身有沒有寫 WHERE。

第一步是在 orders 上開啟 RLS。還沒寫任何政策，直接用 customer 查，執行後看剩幾列：

一列都沒有。開啟 RLS 之後，預設是全部拒絕：沒有任何政策允許的列，一律看不到。這是刻意設計的安全預設值：忘了寫政策，後果頂多是「看不到」，有人會來回報 bug；如果預設是全部開放，忘了寫政策的後果就是全部外洩，而且沒有人會發現。

接下來要寫一條政策，意思是「customer_id 等於目前登入的顧客」。但資料庫怎麼知道目前登入的是哪位顧客？顧客 App 的所有請求都用同一個 customer role 連線，role 只說明「這是顧客 App」，不說明「這是王小明」。不可能替每位顧客建一個 role，顧客有幾萬人，而且隨時有人註冊。

所以要由後端在每次請求開始時告訴資料庫：這次是誰。PostgreSQL 允許你在連線上存自訂的設定值，名稱裡要有一個點，例如 app.user_id。用 set_config(名稱, 值, 是否只在這個交易內有效) 寫入，用 current_setting(名稱) 讀出。執行後看讀出來的值：

讀出 1。使用這個設定時要注意三件事：

  • 第三個參數 false 表示設定在整個連線期間都有效；true 則只在目前的交易內有效，交易結束就消失。這頁用 false 是為了讓範例好操作，正式環境一定要用 true，原因跟連線池有關。第 19 課講過，後端會預先開好幾條連線放在池子裡，每個請求借一條來用、用完還回去，下一個請求可能借到同一條。false 設的 app.user_id 是黏在連線上的，請求結束、連線還回池子時它還在。如果下一個借到這條連線的請求因為某支 API 漏寫、或出錯提早跳過，沒有重新設定，它就會帶著上一位顧客的身分去查，RLS 會很盡責地把上一位顧客的訂單交給他。正式環境的寫法是：每個請求的查詢都包在 BEGIN … COMMIT 裡（第 18 課），開頭先執行 set_config('app.user_id', 目前顧客編號, true)。交易一結束（不論 COMMIT 或 ROLLBACK），設定就自動消失，連線還回池子時是乾淨的，沒設定的請求只會落到預設的 '0'，什麼都查不到。也因為這樣，true 一定要在交易裡用：沒有 BEGIN 時，每一句自己就是一個交易，設定在那一句結束就消失了。
  • 設定的值一律是文字，跟整數欄位比較前要轉型：current_setting('app.user_id')::integer。
  • seed 已經把它預設為 '0'，代表「沒有登入」。沒有顧客的編號是 0，所以沒登入的人符合不到任何一列。

現在可以寫政策了。完整的語法長這樣：

CREATE POLICY 名稱 ON 表名
  FOR SELECT | INSERT | UPDATE | DELETE | ALL
  TO role
  USING (條件)          -- 哪些「既有的列」可以被看到／修改／刪除
  WITH CHECK (條件);    -- 新增或修改後的「新資料」必須符合

FOR 指定這條政策管哪一種操作，TO 指定它套用在哪個 role，USING 是篩選既有列的條件。WITH CHECK 下一節才用到。顧客查訂單只需要 FOR SELECT 和 USING。下面這格建立政策、切換成 customer、設定目前是顧客 1，再查一次。執行後看剩下哪些訂單：

只剩王小明（顧客 1）的訂單。把 '1' 改成 '2' 再執行，就變成陳美華的訂單。查詢本身完全沒變，還是 SELECT * FROM orders，是資料庫自動幫這句加上了 USING 裡的條件。就算後端寫漏了 WHERE，顧客也只看得到自己的訂單，開場的擔心在查詢這一側解決了。

不過這條政策寫的是 FOR SELECT，只管查詢。顧客 App 還要讓顧客自己下單，而新增訂單的時候，資料庫要檢查的是另一件事。

顧客自己下單時，怎麼擋住「幫別人下單」？

查詢時，資料庫是從既有的列裡挑出符合條件的；新增時，還沒有任何既有的列可以挑，要檢查的是「即將寫進去的這一列」。所以政策有兩種條件：USING 管「能看到、能改、能刪哪些既有的列」，WITH CHECK 管「寫進去的新資料必須符合什麼」，不符合就整句拒絕。

顧客下單要過兩層：先用 GRANT INSERT 讓 customer 能新增到 orders（表層級），再用 FOR INSERT 的政策規定新訂單的 customer_id 必須是自己（列層級）。每條政策只管 FOR 指定的那種操作，所以這條新政策不會影響上一節查詢用的那條。執行後看王小明能不能幫自己下單：

成功。再讓王小明試著冒充陳美華（顧客 2）下一筆 9999 元的單：

錯誤訊息是 new row violates row-level security policy，意思是新資料不符合 WITH CHECK，整句被擋下來，訂單沒有寫進去。後端就算有 bug，把前端傳來的 customer_id 原封不動寫進 SQL，資料庫也不會讓這筆訂單掛到別人名下。

💡 實務上：RLS 是「後端忘了加 WHERE」時的最後一道防線
假設咖啡店系統變成賣給很多家店用的 SaaS，每張表都有 shop_id。只要後端有一支 API 忘了寫 WHERE shop_id = …，A 店就看得到 B 店的營收；在表上加一條依 shop_id 過濾的 policy，就算程式寫漏了也不會外洩。代價是權限邏輯分散到資料庫，查「為什麼這筆資料查不到」時要記得看 policy，policy 用到的欄位也要有索引。設定目前使用者時，記得用前面講的交易內 set_config(…, true)。很多傳統後端專案不用 RLS、只靠後端程式和測試把關，這也是常見的選擇。

政策寫好了，自然會想驗收一次：切回平常的 postgres 身分查 orders，看看是不是真的被過濾了。結果會出乎意料。

為什麼用 postgres 驗收，還是看得到全部訂單？

回到 postgres 身分，數一下看得到幾筆訂單：

全部都看得到。政策沒有壞，是 postgres 根本不受 RLS 限制。有兩種身分預設會繞過 RLS：

  • 超級使用者，以及有 BYPASSRLS 屬性的 role：永遠繞過，沒有辦法改變。
  • 表的擁有者（owner，通常是建表的那個 role）：預設也繞過。理由是擁有者本來就能改表的結構、甚至關掉 RLS，限制它的讀取意義不大。

seed 已經把 orders 的擁有者設為 cafe_owner。切換成它，執行後看數字：

一樣是全部。如果希望連擁有者也受 RLS 限制，例如後端程式剛好用建表的帳號連線，要再加 FORCE。這跟前面「限制擁有者意義不大」不衝突：FORCE 防的不是擁有者刻意關掉 RLS，那要明確下 ALTER TABLE … DISABLE ROW LEVEL SECURITY，是另一回事；它防的是後端剛好用建表帳號連線時，一般的查詢不知不覺就繞過了 policy。執行後看擁有者看到幾筆：

變成 0 筆，因為沒有任何政策是給 cafe_owner 的，而 RLS 預設全部拒絕。超級使用者則不受 FORCE 影響，仍然看得到全部。

這解釋了為什麼測試 RLS 一定要切換成應用程式實際使用的那個 role：用超級使用者或擁有者測，永遠看到全部資料，會誤以為「policy 沒效」；反過來，如果只用管理員驗收、從沒用一般 role 跑過，政策寫錯了也不會發現。同樣的道理決定了正式環境的設定：後端連線用的帳號，既不能是超級使用者，最好也不是表的擁有者，否則 RLS 對它不起作用。

到這裡，咖啡店的權限都是由資料庫把關，後端只負責告訴資料庫「現在是誰」。如果連這一步都交給別人處理，前端是不是就能直接查資料庫了？

如果連後端都省掉：Supabase 為什麼敢讓前端直接查資料庫？

第 1 課說過前端不直接連資料庫，因為帳號密碼放在前端，等於公開給所有人。Supabase 看起來是例外：前端用 supabase.from('orders').select() 就能查。它能這樣做，靠的正是這一課的兩層權限。

先講一個要用到的名詞。使用者登入 Supabase 之後，前端會拿到一張 JWT：一段經過簽章的文字，裡面寫著使用者的 id 等資訊。簽章讓伺服器能確認這張 JWT 是自己發的、內容沒被改過，所以前端沒辦法自己偽造「我是別人」。JWT 的結構和簽章原理在認證課第 8 課。有了這個，Supabase 的流程是：

  1. 前端拿到的 anon key 不是資料庫密碼。請求先到 Supabase 的 API 伺服器，它看請求有沒有帶登入後的 JWT，用 anon（沒登入）或 authenticated（已登入）這兩個 role 去查資料庫。這兩個 role 跟我們的 customer 一樣，權限很少。
  2. 每次請求開始時，它把 JWT 裡的使用者資訊設定到連線上，跟我們用 set_config 設 app.user_id 是同樣的概念。auth.uid() 這個函式會讀出目前使用者的 id。
  3. 表都開啟 RLS，policy 寫成 USING (auth.uid() = user_id)。

用這頁的資料庫模擬一遍。orders 上已經有我們前面加的政策和 FORCE，所以換一張乾淨的表 reservations（訂位），把整套設定放在同一格從頭做一次：建一個 auth.uid() 函式、建 authenticated role 並給它表層級權限、開啟 RLS、寫政策。執行後看林志豪（顧客 3）查得到哪些訂位：

只剩林志豪自己的那一筆訂位。這格的每一行都對應到前面學過的東西：auth.uid() 是用第 23 課的 CREATE FUNCTION 包起來的 current_setting，GRANT 是表層級，ENABLE ROW LEVEL SECURITY 和 CREATE POLICY 是列層級。

真正的 Supabase 裡，auth.uid() 回傳的是 uuid，從 JWT 讀出來；這裡簡化成整數。概念完全相同：安全性不是靠「前端拿不到資料庫」，而是靠資料庫自己檢查每一列。所以在 Supabase 上，忘了開 RLS 的表等於對全世界公開。

💡 實務上：用 Supabase 時，每張新表都要過一次 RLS 檢查
建表的同一個 migration 就開啟 RLS，不要想著「之後再補」。查詢、新增、修改、刪除分開想：誰能做、條件是什麼；修改的 policy 只寫 USING 時，PostgreSQL 會拿同一個條件檢查改完的新資料，所以顧客沒辦法把自己的訂單改成別人的 customer_id；改完的資料要符合另一個條件時，才另外寫 WITH CHECK。上線前用兩個不同的測試帳號實際登入，確認彼此看不到對方的資料。會繞過 RLS 的 service_role key 只能放在後端或伺服器端函式，code review 時看到它出現在前端程式碼就要擋下來。

補充與查表

  • 每種操作用哪個條件（查表用，不用背）：FOR SELECT 和 FOR DELETE 用 USING 挑出既有的列；FOR INSERT 用 WITH CHECK 檢查新資料；FOR UPDATE 兩個都用，USING 決定能改哪些列，WITH CHECK 檢查改完的資料，只寫 USING 時改完的資料也要符合同一個條件；FOR ALL 一次套用到全部操作。
  • 只開放部分欄位：GRANT SELECT (id, name) ON customers TO 某role，對方查得到編號和姓名，查不到電話。欄位權限是加上去的：如果這個 role 已經有整張表的 SELECT（例如這頁的 staff），它本來就看得到所有欄位，要先 REVOKE SELECT ON customers FROM staff 收回整張表的權限，再用欄位的寫法給。
  • 查權限：誰對哪張表有什麼權限，查 information_schema.role_table_grants；想直接問「某個 role 能不能做某件事」，用 has_table_privilege('staff', 'orders', 'UPDATE')，回傳 true 或 false。練習 1 的判分就是用它。

練習

判分時會在交易裡執行，結束後自動還原（包括 SET ROLE 和 set_config），不用擔心影響頁面上的資料。

練習 1：店員需要查訂單，也需要修改訂單（例如改狀態），但不能新增或刪除訂單。給 staff 對 orders 剛好這兩種權限。

練習 2：讓 customer 查 reservations（訂位）時，只看得到 customer_id 等於 current_setting('app.user_id') 的訂位。判分會切換成 customer，分別以顧客 2 和顧客 3 的身分查詢。

練習 3：讓 customer 可以新增自己的訂位，但不能用別人的 customer_id 新增。這題只需要處理 INSERT。判分會分別以顧客 3 和顧客 1 的身分，各試一次「幫自己訂位」和「幫對方訂位」，前者要成功、後者要被擋下。（判分用的 succeeds('SQL') 是 seed 準備的小工具，執行成功回傳 true、出錯回傳 false。）

練習 4：你幫 orders 開了 RLS、寫好 policy，用 postgres 身分查詢，卻還是看到全部的訂單。最可能的原因是？

✓ 超級使用者和有 BYPASSRLS 的 role 一定會繞過 RLS；表的擁有者預設也會（除非 FORCE ROW LEVEL SECURITY）。測試 RLS 時，一定要用實際上應用程式會用的那個 role。

練習 5：同事說「Supabase 的 anon key 寫在前端程式碼裡，誰都看得到，所以資料一定不安全」。哪個說法最正確？

✓ 前端拿到的只是「以 anon 或 authenticated 身分發請求」的能力。真正把關的是資料庫的 GRANT 和 RLS policy。反過來說，忘了開 RLS 的表，任何人都查得到。絕對不能放到前端的是 service_role key，它會繞過 RLS。

常見錯誤

  • 用超級使用者或表的擁有者測試 RLS：一定看到全部資料。用 SET ROLE 切換成一般 role 再測。
  • 開了 RLS 卻沒寫 policy：一般使用者什麼都看不到。這不是 bug，是安全的預設值。
  • 只寫了 USING，以為也擋住了寫入：FOR SELECT 的 policy 只管查詢；INSERT 要另外寫 FOR INSERT … WITH CHECK，或用 FOR ALL。
  • 有 RLS 就忘了 GRANT：RLS 是在「有表的權限」之後才進一步過濾。沒有 GRANT，連表都進不去（permission denied）。
  • 切了 SET ROLE 沒有 RESET：之後的操作都用那個 role 執行，到處 permission denied。
  • 應用程式用超級使用者連線：所有權限和 RLS 都失效，一個 SQL injection 就能拿走所有資料。

小結

  • 使用者和群組都是 role；GRANT 群組 TO 使用者 讓使用者繼承權限。應用程式用權限很少的 role 連線，不用超級使用者。
  • GRANT／REVOKE 管「能不能對這張表做某件事」，答案是整張表；遵守最小權限原則，帳號被濫用時損害才有上限。
  • RLS 管「能看到、能改哪些列」：ENABLE ROW LEVEL SECURITY 後預設全部拒絕，再用 CREATE POLICY 開放；USING 篩既有的列，WITH CHECK 檢查寫進去的新資料。
  • 政策靠連線上的設定知道「現在是誰」：後端每次請求用 set_config 寫入，搭配連線池時用交易內有效的 true。
  • 超級使用者永遠繞過 RLS；表的擁有者預設繞過，加 FORCE 才會受限。測試 RLS 要切換成應用程式實際用的 role。
  • Supabase 用 anon／authenticated role 加上 auth.uid() 和 RLS，讓前端直連也安全；忘了開 RLS 的表等於公開。
