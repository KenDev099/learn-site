階段 8：資深必備｜查詢效能 · 第 29 課

查詢調校：統計資訊、執行計畫與慢查詢

咖啡店的後台上線半年，老闆說「最近有點慢」。你打開程式碼，看到一句很長的報表查詢，直覺就想優化它。但它一天只跑兩次；真正拖垮資料庫的，可能是一句每秒被呼叫幾百次、每次只花 3 毫秒的查詢。憑感覺挑，很可能花一個下午改好一句對整體沒有影響的查詢。

這一課從頭到尾都在處理老闆這句「有點慢」：先量測，找出真正佔掉資料庫時間的查詢；再看它的計畫，判斷慢在哪裡；修完再量一次；最後讓資料庫自己把慢查詢記下來，下次有人說「剛剛很慢」時有證據可查。學完你會有一套固定的排查順序，而不是每次從猜開始。

這課的路線：
  1. 該先修哪一句？用 pg_stat_statements 找出總成本最高的查詢，並列出慢的四種原因（開場問題的最小答案）。
  2. 計畫為什麼會選錯？規劃器怎麼用 pg_stats 估列數；兩個相關的欄位為什麼會估錯 4 倍、怎麼修。
  3. 統計資訊沒問題，為什麼 App 呼叫還是慢？預備陳述式重用了不適合的計畫。
  4. 計畫選對了，為什麼還慢？排序放不進記憶體，寫到磁碟上。
  5. 資料庫這一側都沒問題時，改寫 SQL 本身；最後讓資料庫在慢的當下留下計畫。
這課會用到：
  • 第 21 課的 EXPLAIN：規劃器依統計資訊估算成本、挑出計畫；EXPLAIN ANALYZE 真的執行，附上每一步的實際列數；ANALYZE 表名 重新抽樣、更新統計資訊。
  • 第 18 課的交易：BEGIN 開始，COMMIT 或 ROLLBACK 結束，中間的修改一起生效或一起取消。
  • 第 27 課的複合索引與 Top-N：(city, id) 這種索引先依第一欄、再依第二欄排好；ORDER BY … LIMIT N 只取排在最前面的 N 筆。
這頁的環境：資料庫跑在瀏覽器裡，執行時間會隨瀏覽器忙不忙而跳動，讀取頁數不會。pg_stat_statements 已經裝好，work_mem 設成 1MB；沒有伺服器 log 檔，log 訊息直接顯示在結果上方。

這頁的資料：customers 2 萬位（city 4 個城市、district 每個城市 5 區）、orders 3 萬筆、coupons 優惠券。頁面啟動時已經模擬了一段「App 送來的查詢」，第一節要從裡面找出最該修的那一句。

該先修哪一句？先量測，不要憑感覺

開場的問題是「該先修哪一句」。要回答它，得先想清楚「慢」指的是什麼。使用者覺得後台慢，是因為資料庫忙：它的時間被所有查詢分掉了，輪到你的請求時要等。所以一句查詢對整體的影響，不是它跑一次要多久，而是它總共佔掉多少時間，也就是「執行次數 × 平均時間」。一句每次 2 秒、一天跑 2 次的報表，一天佔 4 秒；一句每次 0.3 毫秒、一天跑 100 萬次的查詢，一天佔 300 秒。後者才是該先修的那一句，但光看程式碼看不出來，因為程式碼不會告訴你每一句被呼叫了幾次。

要知道每一句的次數和時間，需要資料庫替你記帳。pg_stat_statements 就是做這件事的工具：它是 PostgreSQL 附帶的擴充功能（extension），會記錄每一句執行過的查詢花了多少時間、讀了多少資料。這頁已經替你裝好；正式環境的安裝要改設定檔、重新啟動資料庫，步驟見課末「補充與查表」。

如果它把每一句都分開記，WHERE id = 1、WHERE id = 2…… 一直到 WHERE id = 60 會變成 60 列，每列都只跑一次、看起來都很便宜，你就看不出「這種查詢一共被叫了 60 次」。所以它把只差常數的查詢合併成一列：常數換成參數符號，寫成 WHERE id = $1。這種常數被換掉之後的查詢文字，叫正規化查詢（normalized query）。每一列累計這個形狀的查詢被執行的次數與成本，常用的欄位是：

欄位意思
calls執行了幾次
total_exec_time所有執行加起來花了幾毫秒（＝次數 × 平均）
mean_exec_time平均一次幾毫秒
shared_blks_hit／shared_blks_read讀了幾個資料頁（blks 是 blocks，就是第 21 課的資料頁）：在記憶體快取裡找到的／要從磁碟（或作業系統快取）讀的，兩個相加就是這課說的讀取頁數

這頁的時間會跳動（見課首），每次重新整理排名都可能不同。讀取頁數不會：同樣的資料、同樣的計畫，每次讀的頁數都一樣，所以練習 1 用讀取頁數排序。正式環境兩個都看：時間反映使用者的感受，頁數反映資料庫做了多少工作。

老闆或客服說「後台很慢」時，先打開 pg_stat_statements 依 total_exec_time 列出前五名，討論就從「感覺」變成「這三句查詢佔了大部分時間」。多數雲端託管的 PostgreSQL 都支援這個擴充功能，通常在參數設定裡開啟。合併後的 SQL（常數換成 $1）常是 ORM 產生的，不容易對回程式碼；先用表名和 WHERE 條件在專案裡搜尋。修完把前後的數字貼在 PR 說明裡，審查的人和之後接手的人都看得到效果。

計畫為什麼會選錯？規劃器怎麼估列數

找出最貴的查詢之後，下一步是看它的計畫。第 21 課說過，規劃器會先估計每一步會出幾列，再依估計挑計畫。估計決定了計畫：以為只會找到幾百列，用索引一筆一筆去讀很划算；以為會找到幾萬列，整張表掃一遍反而比較快。估計錯了，挑出來的計畫就可能是錯的。所以看計畫時，第一件事是比較估計和實際；要看懂為什麼估錯，就得知道估計是怎麼算出來的。

規劃器不會為了估計而真的去數資料，那樣估計本身就跟執行一樣貴。它靠的是 ANALYZE 事先抽樣算好的摘要：每一欄有多少 NULL、有幾種不同的值、哪些值最常出現、其他的值怎麼分布。這些摘要存起來，可以從 pg_stats 這個視圖查到。估計時主要用兩樣：

  • 最常見值（MCV，most common values）：這一欄出現最多次的那些值，和各自佔全表的比例。等號條件查這張清單。
  • 直方圖（histogram）：把 MCV 以外的值排序後，切成筆數相同的幾個區間，記下每個區間的邊界。範圍條件查這些區間。

估計時還會用到一個詞：條件會留下全表多少比例的列，叫選擇率（selectivity）。選擇率乘上表的總列數，就是估計的列數。

某一欄的值種類很多、分布特別不平均，100 個值和 100 個區間不夠描述它時，估計就會常常不準。這時不用改全域設定，只提高那一欄：ALTER TABLE orders ALTER COLUMN total SET STATISTICS 500;，之後要再 ANALYZE 才會生效。pg_stats 的其他欄位（例如 n_distinct、correlation）整理在課末的查表。

到這裡的條件都只有一欄，估計都準。但後台的查詢常常不只一個條件，兩個條件的選擇率要怎麼合起來，就是下一節估錯 4 倍的原因。

統計資訊是新的，為什麼還估錯 4 倍？相關的欄位

上一節的摘要是一欄一欄存的，規劃器不知道兩欄之間有什麼關係。條件有兩個時，它預設兩個條件互不相關，把兩個選擇率直接相乘。這叫獨立性假設（independence assumption）。兩欄真的無關時，這樣算是對的；兩欄相關時，就會算錯。

咖啡店的顧客資料就有一對相關的欄位：district 決定了 city，「台北市第1區」一定在台北市。行銷要撈這一區的顧客發活動簡訊，查詢同時寫了城市和行政區。執行後比較估計的 rows= 和實際的 actual … rows=：

差 4 倍在這裡看起來無害，但估計會一路往上傳：如果這個結果還要 JOIN 別的表，規劃器以為只有 250 列，可能選 Nested Loop 去逐列查另一張表，實際卻要跑 1000 次；在更大的表上，這就是「明明有索引卻突然慢 100 倍」的常見原因。

問題出在規劃器缺少「兩欄之間的關係」這項資訊，所以修法是把這項資訊補給它。延伸統計（extended statistics）就是做這件事的：你指定幾個欄位，ANALYZE 時 PostgreSQL 會額外收集它們之間的關係，估計時拿來修正相乘的結果。

CREATE STATISTICS 統計名稱 (dependencies) ON 欄位1, 欄位2 FROM 表名;
ANALYZE 表名;   -- 建立之後要 ANALYZE，統計才會真的算出來

括號裡的 dependencies 是要收集的種類：功能相依（functional dependency），也就是「知道 A 就幾乎知道 B」，正好對應城市和行政區的關係，改善的是多個欄位的 = 條件同時出現時的估計。延伸統計還有另外兩種，整理在課末的查表。

直覺的修法在這裡沒有用。建一個 (city, district) 複合索引，改變的是讀資料的方式，不是估計；提高兩欄各自的統計目標，規劃器還是一欄一欄估，再相乘。練習 2 會讓你親手修好這個估計。

💡 實務上：計畫怪怪的，先比「估計」和「實際」
查詢突然變慢時，新手的第一反應常是再加一個索引；資深工程師會先看 EXPLAIN ANALYZE 每一步的估計列數和實際列數差多少。差距大，問題通常在統計資訊（剛匯入大量資料還沒 ANALYZE、欄位彼此相關），加索引救不了。容易相關的欄位在真實系統裡很常見：城市和行政區、商品大類和子類、多租戶系統的租戶 id 和其他欄位。延伸統計只在你看到估計明顯錯、而且錯在這幾個欄位時才建，不需要預先到處加。

到這裡，統計資訊已經修好了。但有一種慢，統計資訊完全正確也會發生，而且只在 App 呼叫時出現，你手動跑同一句卻很快。

手動跑很快，App 呼叫卻慢？預備陳述式重用了計畫

正式環境常見的劇本是這樣：後台「依狀態列訂單」的 API，前幾次都很快，之後查某些值（例如很少見的狀態、或訂單特別多的大客戶）突然變慢。你把同一句 SQL 貼進 psql 手動跑，又很快，查不出問題。統計資訊是新的，SQL 也一樣，差別在於查詢送進資料庫的方式。

第 25 課說過，後端程式送 SQL 時用參數（$1）而不是把值拼進字串。很多驅動程式與 ORM 會更進一步，在背後使用預備陳述式（prepared statement）：先把帶參數的 SQL 送給資料庫，讓它解析、準備好；之後每次只送參數值。同一句查詢一秒被呼叫幾百次時，這省下了每次重新解析、重新規劃的時間。用 SQL 也能手動做：

PREPARE 名稱(參數型別) AS 查詢;   -- 準備
EXECUTE 名稱(值);                 -- 執行
DEALLOCATE 名稱;                  -- 丟掉

問題在「準備好」之後的計畫。預備陳述式執行時，資料庫可以用兩種計畫：

  • custom plan：每次依這次的參數值重新規劃，例如看到 'pending' 就查 MCV，知道只有 1%。
  • generic plan：不看參數值、規劃一次就一直重用，連規劃的時間都省下來；但因為不知道參數是什麼，它只能用「平均」的估計。

資料庫會自己決定用哪一種。PostgreSQL 18 文件寫的規則（plan_cache_mode = auto，預設）：前五次用 custom plan，並記下它們的平均估計成本；之後規劃一次 generic plan，如果它的成本沒有比平均高太多，就改用 generic plan。

下面重現開場的劇本。準備一句 by_status，先用 'paid' 執行五次，第六次換成 'pending'。執行後先看 pg_prepared_statements 的兩個計數，再看 EXPLAIN 的條件和 rows=：

  • pg_prepared_statements：五次 'paid' 都是 custom plan，第六次已經換成 generic plan（generic_plans 變成 1）。
  • EXPLAIN EXECUTE 的條件寫著 status = $1 而不是 'pending'，這就是 generic plan 的記號。
  • 它估的是 10000 列（三種值平均一下，30000 × 1/3），而 pending 實際只有 300 列、paid 有 27000 列，兩邊都估錯。

這解釋了開場的劇本：App 用預備陳述式，前五次是 custom plan 所以快，之後換成用平均估計的 generic plan，碰到特別常見或特別少見的值就選錯計畫；你在 psql 手動跑，每次都是一句新的查詢，用的是 custom plan，所以重現不出來。這份資料小，錯的代價不大；在大表上，就是 API 突然慢好幾倍。

確定是這個原因時，用設定參數 plan_cache_mode 強迫每次重新規劃。但不要全域改，只在需要的地方設定，例如那一個交易，或那一個資料庫角色。這就要先知道改設定參數的兩種範圍：

  • SET 名稱 = 值：改的是「這條連線」，之後所有的交易都受影響，直到連線關閉。
  • SET LOCAL 名稱 = 值：只改「這個交易」，COMMIT 或 ROLLBACK 之後自動還原。第 24 課的 set_config('名稱', '值', true) 效果相同。

後端程式裡幾乎都用 SET LOCAL，原因在連線池（connection pool）：後端不會為每個請求開新連線，而是從池子借一條、用完還回去。用 SET 改的設定會跟著連線留下來，下一個借到這條連線的請求，在不知情的情況下也套用了這個設定。

規則很簡單：一般的請求裡不要寫沒有 LOCAL 的 SET。下一節調整記憶體設定時，會再碰到這個問題。

前面三節的慢都出在計畫選錯。計畫選對了，執行時還是可能慢：計畫要排序，但排序的資料放不進記憶體。

計畫選對了，為什麼還慢？排序放不進記憶體

咖啡店的月報要把所有顧客依姓名排序後匯出。排序（ORDER BY）要把資料放在記憶體裡比較、搬動；雜湊（Hash Join、GROUP BY 的 HashAggregate）也要在記憶體裡建一張雜湊表。每個排序或雜湊步驟最多能用多少記憶體，由設定參數 work_mem 決定（PostgreSQL 預設 4MB）。資料放得下，整個排序在記憶體裡完成；放不下時，資料庫把資料分批寫到暫存檔，在磁碟上排序再合併，讀寫磁碟比讀寫記憶體慢很多。雜湊步驟的上限算法略有不同，見課末。

這頁啟動時把 work_mem 設成了 1MB（見課首），模擬一台設定保守的伺服器。執行後看 Sort Method 那一行和下面的 Buffers：

  • Sort Method: external merge：在磁碟上排序。
  • Disk: …kB：寫了多少暫存檔。
  • temp read／written：讀寫暫存檔的頁數。

單一句查詢用 EXPLAIN ANALYZE 看得到；要知道整個資料庫平常有多常發生這種事，可以從 pg_stat_database 看累計寫過多少暫存檔：

直覺的修法是把 work_mem 調大，但要先想清楚它的計算方式：它不是整個資料庫共用的總量，而是每個排序或雜湊步驟各自可以用這麼多。一句複雜的查詢可能同時有好幾個這樣的步驟，而且每條連線都各自在用。

設成 1GB、100 條連線同時跑報表，最多可能要 100 GB 以上；記憶體用光時，作業系統會強制終止資料庫的程序，所有連線一起斷掉。所以正確的做法是用上一節的 SET LOCAL，只在需要的報表交易裡調大。執行後看 Sort Method，以及最後 SHOW 的值：

  • Sort Method: quicksort Memory: …kB：全部在記憶體裡完成。Memory 的數字就是這次排序實際需要的量，調整時設得比它大一點就夠了。
  • Memory 比剛才的 Disk 大：同樣的資料放在記憶體裡要多存一些管理資訊，所以不能拿 Disk 的數字直接當 work_mem。
  • 最後的 SHOW work_mem 回到 1MB：交易結束，SET LOCAL 的設定自動還原。
💡 實務上：報表和一般 API 分開對待
咖啡店的月報、匯出 Excel 這類查詢要排序大量資料，和每秒很多次的點餐 API 需求完全不同。常見做法是讓報表用專門的資料庫角色連線（例如 ALTER ROLE report_user SET work_mem = …），或把報表放到唯讀副本上跑，不影響線上交易。調整前先看 EXPLAIN ANALYZE 的 Memory 數字決定要多大，調整後觀察 pg_stat_database 的 temp_bytes 有沒有下降。要調全域設定時，先和負責維運的人一起算過最多連線數乘上去的記憶體用量。

到這裡修的都是資料庫這一側：統計資訊和設定參數。但有些查詢，統計資訊和設定都沒問題，慢（或錯）的原因出在 SQL 本身的寫法。

資料庫這一側都沒問題時：改寫 SQL 本身

這一節看後台三段常見的寫法，每一段都是規劃器救不了、只能改 SQL 的情況：一段結果是錯的，一段做了多餘的排序，一段被舊習慣擋住了最佳化。

「沒領過優惠券的顧客」名單是空的：NOT IN 遇到 NULL

第一種不是慢，是錯，而且不會報錯。行銷要發券給從來沒領過優惠券的顧客，程式寫成 WHERE id NOT IN (SELECT customer_id FROM coupons)，結果一筆都沒有。第 16 課提醒過這個陷阱，這裡把原因講完整。

第 4 課說過，跟 NULL 比較的結果不是 true 也不是 false，而是「不知道」（NULL）。x NOT IN (a, b, NULL) 展開來等於 x <> a AND x <> b AND x <> NULL，最後一項永遠是 NULL；AND 串起來的條件只要有一項是「不知道」，整體就不可能是 true，WHERE 只留下 true 的列，於是一列都不留。執行後比較兩欄：

咖啡店的 coupons 裡有一張發給臨時客人的券，customer_id 是 NULL，就足以讓整個 NOT IN 失效。改用 NOT EXISTS：它問的是「對這位顧客，找不找得到對應的券」，答案只有找得到或找不到，NULL 不會讓它失靈。修好的名單是：

SELECT c.id FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM coupons k WHERE k.customer_id = c.id);

NOT EXISTS 不只結果對，規劃器也處理得好。它會把這種寫法變成 anti join（反連接）：一種專門找「在另一張表沒有對應資料」的列的連接方式，兩張表配對時，配不到的才留下。同樣的寫法套在資料量比較大的 orders 上，計畫比較容易看出 Anti Join：下面找從來沒下過單的顧客，執行後找計畫裡的 Anti Join：

每一組只要最新幾筆：LATERAL

後台常有「每位顧客最近 3 筆訂單」、「每個城市最新的 2 位顧客」這類需求。第 17 課的 row_number() OVER (PARTITION BY …) 可以做，但它要先把每一組的所有列都讀出來、排好、編號，最後才丟掉大部分。一個城市有 5000 位顧客，只要 2 位，卻要排 5000 位。

更省的做法是：對每一組各跑一次第 27 課的 Top-N 查詢，每次讀到 N 筆就停。問題是一般的子查詢放在 FROM 裡時，看不到同一個 FROM 裡前面那張表的欄位，沒辦法寫「這一組的城市」。LATERAL 就是解除這個限制的關鍵字：加了它，FROM 裡的子查詢可以引用前面那張表的欄位，資料庫會對前面的每一列各跑一次子查詢。執行後看每個城市各列出 2 位顧客：

  • Nested Loop：外層每一列，內層跑一次。
  • 內層是 Limit＋索引掃描：這頁的 customers 有 (city, id) 複合索引，同一個城市的顧客在索引裡依 id 排好，所以從尾端往回讀，讀到 2 筆就停。

每組資料很多、只要前幾筆、又有符合「分組欄位＋排序欄位」的索引（第 27 課的複合索引）時，LATERAL 讀得最少。每組只有幾筆，或要的是整組的排名時，視窗函式一樣好，也比較好讀。

舊程式碼裡的 CTE：有沒有被內嵌

第三種常出現在比較舊的專案。第 16 課的 WITH（CTE）讓長查詢可以分段寫，但它在執行時有兩種處理方式：

  • 內嵌：把 CTE 的內容直接展開進主查詢，和直接寫子查詢一樣，規劃器可以把主查詢的條件推進去，用得上索引。PostgreSQL 12 起，沒有副作用、只被引用一次的 CTE 預設就是這樣處理。
  • 物化：先把整個 CTE 算完、存起來，主查詢再從存起來的結果裡篩。寫 AS MATERIALIZED 會強迫這樣做，主查詢的條件就推不進去了。

PostgreSQL 11 以前，CTE 一律先算完，有些人刻意拿它當「擋住最佳化」的工具。從那時候升上來的舊程式碼，現在要那個效果得明寫 MATERIALIZED；而沒有充分理由時不要寫，否則就是上面第二個計畫。

還有一種寫法：條件用 OR 連接兩個不同的欄位，有時也會讓索引用不上，整理在課末。

到這裡，四種慢的原因都有了修法。但這些修法有一個共同的前提：你要能在現場重跑那句查詢。

使用者說「剛剛很慢」，怎麼看到當時的計畫？auto_explain

前面的工具都要你在現場重跑查詢。可是使用者回報「剛剛很慢」時，你再跑 EXPLAIN ANALYZE，資料和快取可能都變了，參數值也不一定知道，看到的不一定是當時的計畫。所以正式環境會讓資料庫在查詢慢的當下自己記錄，有兩個工具：

  • log_min_duration_statement = '500ms'：執行超過 500 毫秒的 SQL，連同時間寫進伺服器 log。伺服器 log 是 PostgreSQL 寫錯誤與事件的文字紀錄檔。這樣你知道哪一句、什麼時候慢。
  • auto_explain 模組：超過 auto_explain.log_min_duration 的查詢，把計畫也寫進 log，你就知道它當時為什麼慢。auto_explain.log_analyze = on 時附上實際列數與時間；但開啟後每一句查詢都要量測，不只超過門檻的那些，所以負擔和門檻無關。正式環境常搭配 auto_explain.log_timing = off（只記列數、不記每一步的時間），或用 auto_explain.sample_rate 只抽樣一部分查詢。

正式環境通常在設定檔用 session_preload_libraries 或 shared_preload_libraries 載入 auto_explain。這頁沒有 log 檔可以看（見課首），所以用 LOAD 載入，再把 client_min_messages 設成 log，log 訊息就會直接顯示在結果上方：

💡 實務上：上線前就把慢查詢紀錄開好
慢查詢 log 是事後追查最有用的證據，等出事才開就晚了，所以新專案上線前就該設定好。門檻依使用者能接受的回應時間來定，設太低 log 會大量增加，重要的訊息反而被淹沒。要注意 log 裡可能出現查詢的參數值，例如顧客的 email 或電話，存放和保存期限要符合公司的資安與個資規定。追查時把 log 的時間點和 App 的錯誤回報、部署紀錄對在一起看，常常能直接找到是哪一次改版造成的。

回到開場老闆那句「有點慢」，現在的排查順序是：用 pg_stat_statements 依總成本找出該修的查詢；用 EXPLAIN ANALYZE 看計畫，依第一節的表判斷是估計錯、計畫重用錯、記憶體不夠，還是寫法的問題；修完用同一個指標再量一次；平常開著慢查詢 log 與 auto_explain，下次有人說「剛剛很慢」時直接查紀錄。

補充與查表

主線用不到、但查問題或調設定時會用到的細節。查表用，不用背。

在正式環境安裝 pg_stat_statements

pg_stat_statements 需要額外的共享記憶體，所以要先在設定檔的 shared_preload_libraries 加上它、重新啟動資料庫，再對資料庫執行 CREATE EXTENSION pg_stat_statements;。雲端託管的資料庫通常在參數設定裡開啟。

雜湊步驟能用的記憶體

排序步驟最多用到 work_mem；雜湊步驟可以用到 work_mem × hash_mem_multiplier，後者預設 2.0。

練習 6：EXPLAIN ANALYZE 顯示某一步估計 250 列、實際 1000 列，條件是兩個高度相關的欄位（例如城市和行政區）。統計資訊是剛 ANALYZE 過的。最該做什麼？

✓ 估錯的原因是獨立性假設：規劃器把兩個條件的選擇率直接相乘。延伸統計讓它知道欄位之間的相依關係，建完要 ANALYZE 才會算出來。索引改變的是讀取方式，不改變估計；work_mem 跟估計無關；統計資訊已經是新的，再 ANALYZE 一次結果一樣。

練習 7：同一句查詢在 psql 手動跑很快，從 App 呼叫時前幾次也快，之後某些參數值突然變慢。最可能的原因是？

✓ 預備陳述式前五次用 custom plan，之後可能改用 generic plan；generic plan 用平均估計，對特別常見或特別少見的值可能選錯計畫。psql 手動執行每次都是 custom plan，所以重現不出來。用 EXPLAIN EXECUTE 看是否出現 $1，再考慮在需要的地方設 plan_cache_mode = force_custom_plan。網路與 ORM 的問題不會只影響某些參數值。

練習 8：報表的排序一直出現 external merge Disk，同事提議把 work_mem 全域調成 1GB。這樣好嗎？

✓ 文件明寫一句查詢可能同時有好幾個排序與雜湊步驟，每個都能用到 work_mem，而且每條連線都各自在用，總量可能是 work_mem 的很多倍。全域調到 1GB，尖峰時可能用光記憶體。它不是總量，也跟 shared_buffers 無關。

常見錯誤

  • 憑感覺調校：先用 pg_stat_statements 找出總成本（次數 × 平均）最高的查詢，再動手。
  • 清空 pg_stat_statements 前沒記下基準：修完之後無從比較。先把數字存下來，再 reset。
  • 大量匯入或 CREATE STATISTICS 之後忘了 ANALYZE：統計資訊不會自己出現，估計維持原樣。
  • 只比 EXPLAIN ANALYZE 的時間：時間受快取、機器忙碌程度影響，會跳動。比較讀取頁數（Buffers）和估計／實際列數更可靠。
  • 對 UPDATE／DELETE 直接跑 EXPLAIN ANALYZE：它會真的執行，包在 BEGIN … ROLLBACK 裡。
  • NOT IN 用在可能有 NULL 的子查詢：一筆都不回、不會報錯。改用 NOT EXISTS。
  • 全域加大 work_mem：每個步驟、每條連線各自使用，總量會放大很多倍。在需要的交易裡 SET LOCAL。
  • 在一般請求裡用沒有 LOCAL 的 SET：設定跟著連線留在連線池裡，下一個請求也會套用。用 SET LOCAL。
  • 到處加 AS MATERIALIZED：會擋住條件下推，主查詢用不到索引。只在確定需要「先算完一次」時才用。

小結

  • 調校的流程：量測 → 找總成本最高的 → 看計畫 → 修 → 再量測。pg_stat_statements 把只差常數的查詢合併累計，依 total_exec_time（次數 × 平均）或讀取頁數排序。
  • 看計畫先比估計和實際。規劃器用 pg_stats 估計列數：等號條件查 MCV，範圍條件查直方圖；多個條件預設互不相關、選擇率相乘。
  • 相關欄位會被低估，用 CREATE STATISTICS 加 ANALYZE 修正；加索引、提高單欄統計目標都沒用。
  • 預備陳述式前五次 custom plan，之後可能換成用平均估計的 generic plan；EXPLAIN EXECUTE 出現 $1 就是 generic；必要時局部設定 plan_cache_mode。
  • external merge Disk 代表 work_mem 不夠；它是每個步驟、每條連線各自的量，只在需要的交易裡 SET LOCAL 調大。
  • NOT IN 遇到 NULL 改 NOT EXISTS；每組前 N 筆用 LATERAL；CTE 預設內嵌，MATERIALIZED 會擋住最佳化。
  • log_min_duration_statement 與 auto_explain 讓慢查詢在發生的當下留下紀錄。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 9：「我的訂單」查顧客最近 5 筆已付款訂單（WHERE customer_id = $1 AND status = 'paid' ORDER BY ordered_at DESC LIMIT 5），同事建了 (ordered_at, customer_id) 索引。常客很快，只有 7 筆訂單的顧客卻慢了十幾倍，為什麼？

✓ B-tree 要前面的欄位固定，後面那一欄才是排好的；第一欄沒有條件，customer_id 只能邊讀邊比對，訂單越少的顧客讀得越多。改成等號欄位在前、排序欄位在後：(customer_id, status, ordered_at DESC)，Sort 消失、讀 5 筆就停。b 錯在索引可以倒著讀（Index Scan Backward），方向不是問題，欄位順序才是。（第 27 課）

練習 10：「載入更多」API 這樣寫，$1 是上一頁最後一筆的 ordered_at，表上有 (ordered_at DESC) 索引。哪裡會出事？

SELECT id, ordered_at FROM orders
WHERE ordered_at < $1
ORDER BY ordered_at DESC
LIMIT 20;

✓ 只拿時間當 cursor，和上一頁最後一筆同一時間、還沒顯示的訂單也不符合 < $1，就被跳過了。要加同分決勝欄位：(ordered_at, id) < ($1, $2)，ORDER BY 和索引都加上 id。c 是 OFFSET 的問題，keyset 從上一頁最後一筆之後開始，新資料不會讓它錯位。（第 27 課）

練習 11：同事要清理 payments 的索引，idx_scan 分別是：(order_id) 1200、(order_id, paid_at DESC) 800、UNIQUE (transaction_no) 0。統計沒有剛重設過，哪一個最適合刪？

✓ 每個索引都讓寫入變慢、佔空間。(order_id) 被 (order_id, paid_at DESC) 涵蓋，能用它的查詢都能用後者，idx_scan 不是 0 也可以刪。b 錯在唯一索引每次 INSERT 都在檢查重複，只是不算「掃描」，刪了重複的交易編號就寫得進來。（第 27 課）

練習 12：products.options（JSONB）有 GIN 索引，後台篩「燕麥奶」寫成 WHERE options ->> 'milk' = 'oat'。結果正確，EXPLAIN 卻是 Seq Scan，為什麼？

✓ 索引能不能用看運算子，不是語意；陣列的 = ANY (…) 也是同樣的道理。改寫成 options @> '{"milk":"oat"}'，或這個 key 非常常查時另建運算式 B-tree ((options ->> 'milk'))。a 錯在 GIN 也收錄值，@> '{"milk":"oat"}' 就用得上，問題出在寫法。（第 28 課）

練習 13：老闆說後台很慢，pg_stat_statements 裡有三句：A 每次 2 秒、一天 2 次；B 每次 0.3 毫秒、一天 100 萬次；C 每次 80 毫秒、一天 500 次。先修哪一句？

✓ 依 total_exec_time（次數 × 平均）排序：B 一天約 300 秒，C 約 40 秒，A 只有 4 秒。修完再量測，跟修之前的數字比。a 錯在平均最慢的不一定最該修，一天兩次的查詢修好了，整體負載幾乎不變。（第 29 課）

練習 14：同事把報表裡的 CTE 都加上 AS MATERIALIZED，說「先算好比較快」。orders 有 customer_id 的索引，下面這句改完後從幾毫秒變成好幾百毫秒，為什麼？

WITH o AS MATERIALIZED (SELECT * FROM orders)
SELECT * FROM o WHERE customer_id = 42;

✓ PostgreSQL 12 起，CTE 預設內嵌到主查詢，和子查詢一樣能把條件推進去、用上索引。AS MATERIALIZED 強迫先把整個 CTE 算完，主查詢的條件推不進去，計畫變成 Seq Scan 加上 CTE Scan。沒有充分理由不要寫它。c 錯在 REFRESH 是 Materialized View 的事，CTE 每次執行本來就是重新查詢。（第 29 課）

練習 15：已經用 EXPLAIN EXECUTE 確認，某個 API 對少見的狀態變慢，是因為改用了 generic plan（條件裡出現 $1）。怎麼修最恰當？

✓ generic plan 不看參數值，只能用平均估計，對特別少見的值會選錯計畫；強迫 custom plan 就會依實際值規劃。只在需要的地方設定。b 錯在每次執行都要重新規劃，簡單又頻繁的查詢，規劃時間可能比執行時間還長。（第 29 課）

練習 16：後台用 WHERE name ILIKE '%' || $1 || '%' 搜尋顧客，一年後每次搜尋都要好幾秒。客服通常打三到五個字，name 上已經有一般的 B-tree 索引，怎麼改最恰當？

✓ 兩邊都是 % 的樣式，一般 B-tree 幫不上，只能掃整張表。pg_trgm 從樣式抽出三連字，用 GIN 找出候選列，三個字以上的關鍵字就走得了索引；兩個字的抽不出 trigram，幫不上。c 錯在內建全文檢索不會中文斷詞，一段中文被當成一個詞，打名字的一部分會找不到。（第 28 課）
