階段 6：效能 · 第 20 課

索引

咖啡店的 App 上線快一年，orders 已經累積到 10 萬筆。客服開始轉來回報：「App 的『我的訂單』要轉好一陣子才出來」，店長也說後台用手機號碼找會員、刪除下架商品、搜尋顧客名字都變慢了。前面幾課的查詢都很快，是因為資料只有十幾列；資料一多，同一句 SQL 就會慢下來。

這一課就把這批慢查詢一個一個修好。主要的工具是索引（index）：你會親眼看到同一句查詢，加了索引之後快上百倍。學完你會知道一句慢查詢該建什麼索引、什麼時候不該建，以及為什麼有時候建了也沒用。

這課會用到：
  • 第 8 課的外鍵：order_items.product_id 指向 products.id，資料庫保證被參照的那一列存在。
  • 第 12 課的 UNIQUE 約束：某一欄的值不能重複，重複時資料庫直接拒絕寫入。
這課的路線：
  1. 「我的訂單」為什麼慢：用 EXPLAIN ANALYZE 看資料庫把 10 萬筆訂單一筆一筆看過去。
  2. 索引是什麼、B-tree 怎麼直接跳到要的列，然後動手建一個，比較前後差多少（開場問題的答案）。
  3. 「我的訂單」還要照時間排、篩狀態：複合索引能顧到好幾個欄位，但欄位順序決定它幫不幫得上忙。
  4. 手機號碼不能重複、刪商品變慢：UNIQUE 索引順便擋重複，外鍵欄位則要自己建索引。
  5. 每一欄都建好不好、建了為什麼沒用到：索引的代價，以及讓索引白建的查詢寫法。

「我的訂單」為什麼慢？先讓資料庫說它做了什麼

要修慢查詢，第一步不是猜，而是看資料庫實際怎麼執行它。先認識一下這頁的資料：customers（5000 位顧客）、products（8 種商品）、orders（10 萬筆訂單）、order_items（10 萬筆明細）。執行下面這格，確認資料量：

App 的「我的訂單」背後，最核心的一句是「找出某位顧客的所有訂單」。以顧客 42 為例，就是 SELECT * FROM orders WHERE customer_id = 42。

在查詢前面加上 EXPLAIN ANALYZE，資料庫會真的執行這句查詢，然後回報它怎麼做的和花了多久，而不是回傳查詢結果。輸出有好幾行，這一課只看三個地方，其他內容下一課會細講。執行下面這格：

  • 第一行的 Seq Scan on orders：資料庫做的是全表掃描（sequential scan），從 orders 的第一列讀到最後一列，每一列都拿 customer_id 跟 42 比對。
  • Rows Removed by Filter: 99980：比對不符合、被丟掉的列數。為了找 20 筆，資料庫看了 10 萬筆、丟掉 99980 筆。
  • 最後一行的 Execution Time：這句查詢實際花的時間，等一下建完索引要拿它來比。

資料庫為什麼只能這樣做？因為表裡的列是照寫入的順序存放的。顧客 42 的 20 筆訂單是在不同時間下的，散落在整張表的各處，資料庫事先不知道它們在哪裡，只好每一列都看過。這種做法的時間跟表的大小成正比：訂單變成 10 倍，要看的列也變成 10 倍。

10 萬筆在瀏覽器裡全表掃描也只要幾毫秒，看起來沒差。但正式環境的表常有幾千萬列、每秒被查幾百次，差一百倍就是「網站正常」和「網站掛掉」的差別。

要讓資料庫不必全部看過，它就得事先知道「customer_id 是 42 的列在哪裡」。這正是索引要做的事。

怎麼不用一筆一筆看？索引就像書末的索引頁

你手上有一本 500 頁的咖啡百科，想找「冷萃」在哪一頁。有兩種做法：

  1. 從第 1 頁翻到第 500 頁，每頁掃一遍。一定找得到，但很慢。這就是剛才的全表掃描。
  2. 翻到書末的索引頁：詞條照筆畫排好，很快找到「冷萃……p.213、p.347」，直接翻過去。

第二種做法快，是因為有人事先把詞條排好序，並記下每個詞條在哪一頁。資料庫的索引是同一個做法：把 customer_id 的值事先排好序，每個值旁邊記著「這一列在表裡的位置」。查 customer_id = 42 時，資料庫先在這份排好序的目錄裡找到 42，再直接去拿那幾列，這叫用索引查找（index scan）。

索引是一份額外的資料：它把某一欄的值排好序，每個值旁邊記著「這一列在表裡的位置」。表本身不會被重新排列，索引是另外存的。所以索引可以建很多個，也可以隨時刪掉，不會影響表裡的資料。

「排好序的目錄」實際上長什麼樣子？PostgreSQL 預設的索引叫 B-tree，你可以把它想成一本有「目錄的目錄」的字典。圖裡的「第 3 頁」指的是那一列在表裡的位置：PostgreSQL 把表切成一塊塊固定大小的頁（page）存放，索引記下的就是「在哪一頁的哪一筆」。

照著圖找 customer_id = 42：根節點寫著 1700 和 3400，42 比 1700 小，往最左邊走；中間節點寫著 20、40……，42 落在 40 之後，往對應的葉節點走；葉節點裡有「42 → 第 3 頁」，資料庫就直接去表的第 3 頁拿那一列。整個過程只看了 3 個節點，不管表有多少列。

B-tree 的三個特性，決定了它能幫上哪些查詢：

  • 排好序：所以等於（=）、範圍（<、BETWEEN）、ORDER BY 都能用得上。
  • 很矮：每個節點可以存幾百個值，所以就算幾百萬列，樹也只有 3～4 層。表變大 10 倍，查找只多讀一兩個節點，不像全表掃描要多讀 10 倍。
  • 葉節點互相串連：找「3 月 1 日到 3 月 7 日」時，找到起點後沿著葉節點往右走就好。

理論上會快很多。實際差多少？幫 customer_id 建一個索引，再跑一次同一句查詢。

💡 實務上：索引通常是「查詢變慢之後」才回頭補的
常見的情境就像這課開場：上線初期一切正常，半年後客服回報「後台訂單列表要轉好幾秒」，或監控顯示某支 API 變慢。這時先找出是哪一句 SQL 慢、它的 WHERE 和 ORDER BY 用了哪些欄位，再決定索引，而不是憑感覺加。對正式環境的大表建索引要寫進 migration、挑離峰時段，因為一般的 CREATE INDEX 在建立期間會擋住這張表的寫入（第 22 課會講怎麼避開）。加完記得用同一句查詢比對前後，確認真的有用到。

不過，「我的訂單」實際上不只 WHERE customer_id = 42：它還要照下單時間排序、只顯示最新的 20 筆，有時還要篩狀態。單欄的索引只顧到 customer_id，其他欄位怎麼辦？

「我的訂單」還要照時間排：一個索引能顧到兩個欄位嗎？

App 的「我的訂單」完整的查詢長這樣：

SELECT * FROM orders
WHERE customer_id = 42
ORDER BY ordered_at DESC
LIMIT 20;

只有 customer_id 的索引，能幫資料庫找到顧客 42 的訂單，但找到之後還要另外照 ordered_at 排一次序，才知道最新的 20 筆是哪些。這位顧客的訂單越多，排序的工作越重。

索引可以包含多個欄位，叫複合索引（composite index）：

CREATE INDEX orders_customer_id_ordered_at_idx ON orders (customer_id, ordered_at);

它的排序方式就像電話簿：先按第一欄排，第一欄相同再按第二欄排。所以在這個索引裡，顧客 42 的所有訂單排在連續的一段，而且這一段裡面已經照 ordered_at 排好了。資料庫找到這一段的尾端，往回讀 20 筆就是最新的 20 張訂單，篩選、排序、分頁一次解決，不用另外排序。

反過來，這個索引不是什麼查詢都幫得上忙。用電話簿來想，它先按姓、再按名排：

  • 找「姓王、名小明」：很快，先翻到「王」，再在裡面找「小明」。
  • 找「所有姓王的」：也很快，「王」那一段全部都是。
  • 找「所有名叫小明的」：很慢，小明散落在每個姓裡面，只能整本翻。

這就是最左前綴原則：(customer_id, ordered_at) 這個索引，對「customer_id」或「customer_id 加 ordered_at」的條件有效；只查 ordered_at 時，幫助很小（PostgreSQL 18 開始有例外，見課末「補充與查表」）。也因為如此，有了 (customer_id, ordered_at) 之後，上一節單欄的 (customer_id) 索引就重複了，只查 customer_id 的查詢用複合索引的第一欄就夠。

所以欄位順序很重要。一般原則：用 = 比對的欄位放前面，範圍條件（>、BETWEEN）的欄位放後面。原因跟剛才一樣：customer_id = 42 固定之後，「這位顧客 3 月的訂單」在索引裡是連續的一段，找到起點往後讀到終點就好。如果順序反過來寫成 (ordered_at, customer_id)，3 月那一段裡所有顧客的訂單混在一起，資料庫只能把那段全部讀過，再丟掉不是 42 的列。

💡 實務上：從列表頁的篩選和排序回推複合索引
「我的訂單」這種 WHERE customer_id = 42 ORDER BY ordered_at DESC LIMIT 20，一個 (customer_id, ordered_at) 就能同時幫上篩選、排序和分頁。設計前先問前端或 PM：這個列表有哪些篩選條件、預設照什麼排序、哪些組合最常用。不要為每一種篩選組合各建一個索引，挑最常用的一兩種就好，其他冷門組合慢一點通常可以接受。

會員用手機號碼登入：索引能不能順便擋掉重複？

要讓 phone 查得快，建一般索引就行。但「不能重複」也要顧到，這時在 CREATE INDEX 加上 UNIQUE：索引除了加速查詢，還會擋掉重複的值，效果跟第 12 課的 UNIQUE 約束一樣。這兩件事可以由同一個索引完成，是因為檢查重複本來就是在排好序的目錄裡找「這個值有沒有出現過」，跟查詢做的是同一件事。

刪一個商品要好幾秒：外鍵欄位為什麼要自己建索引？

這是初學者最常漏掉的一件事：PostgreSQL 會幫主鍵建索引，但不會幫外鍵建索引。外鍵只是一條規則（「參照的那一列要存在」），宣告它不會順便產生索引。

拿 order_items 來看。它的主鍵是 (order_id, product_id)，所以有一個主鍵索引。依照上一節的最左前綴，「訂單 3 有哪些品項」只查 order_id，可以用主鍵索引；但「拿鐵出現在哪些訂單」只查 product_id，它是主鍵的第二欄，主鍵索引幫不上忙。執行下面這格，看看第一行是不是 Seq Scan：

除了刪除，外鍵欄位也幾乎一定會被拿來 JOIN 或篩選，例如「某個商品賣出了幾份」。所以建外鍵時，順手幫它建索引是好習慣。

💡 實務上：審 migration 時順手問「這個 _id 有索引嗎？」
新增一個 xxx_id 外鍵欄位，是 code review 時最值得多看一眼的地方。不要假設 ORM 或框架會幫你建，打開它產生的 migration SQL 確認有沒有 CREATE INDEX。如果這個欄位已經是某個複合索引的第一欄（像 order_items 的 order_id），就不用再另外建。

到這裡，每個慢查詢都靠多建一個索引解決了。那何不一開始就每一欄都建好，省得以後再補？

那每一欄都先建索引不就好了？索引的代價

因為索引不是免費的。它是一份額外的資料，要有人維護、要有地方存：

  • 寫入變慢：每次 INSERT、UPDATE、DELETE，資料庫除了改表，還要改每一個相關的索引，讓它們保持排好序。一張表有 8 個索引，新增一列就要寫 9 個地方。訂單表是寫入很頻繁的表，每多一個索引，每一筆下單都要多付一點成本。
  • 佔空間：索引是額外存的資料，大小常常跟表本身差不多。

所以原則是：為實際會跑、而且慢的查詢建索引，不要先猜。很少查、資料又很少的表（像 8 種商品的 products）根本不需要額外的索引，全表掃描 8 列比走索引還快。

代價看完，還有另一面：就算為某個欄位建了索引，也不保證每句查詢都會用它。店長說的最後一件事「搜尋顧客名字很慢」，就是這種情況。

建了索引，查詢為什麼還是慢？用不上索引的三種情況

索引能不能用，取決於查詢條件能不能對應到「索引裡排好序的那些值」。對應不上，資料庫就只能退回全表掃描。常見的三種情況：

情況例子為什麼
對欄位套函式或運算WHERE lower(name) = 'abc'
WHERE total * 2 > 500		索引排的是 name 原本的值，不是 lower(name) 的結果
LIKE 以 % 開頭WHERE name LIKE '%明'就像在電話簿裡找「名字最後一個字是明」，排序幫不上忙
條件會選到大部分的列WHERE status = 'paid'（六成都是）反正要讀大半張表，直接全表掃描反而比較快

第三種情況不是錯誤，而是資料庫的判斷。走索引時，每找到一筆都要再回到表裡對應的那一頁拿整列；要拿的列只有幾筆時很划算，要拿六成的列時，在索引和表之間來回跳，反而不如從頭到尾把整張表順著讀一遍。這種情況不用處理。

第一種情況則是寫法的問題，有兩個解法：

  1. 改寫查詢，讓欄位保持「裸的」：條件左邊只放欄位本身，運算移到右邊的值上。例如「3 月 1 日的訂單」不要寫 WHERE ordered_at::date = '2026-03-01'，改成範圍：WHERE ordered_at >= '2026-03-01' AND ordered_at < '2026-03-02'。
  2. 建表達式索引（expression index）：索引直接存函式的結果，CREATE INDEX ON customers (lower(name));，之後 WHERE lower(name) = … 就用得上。

第二種情況要看 % 在哪裡。LIKE 以固定文字開頭（LIKE '王%'）通常用得上 B-tree 索引，因為「姓王的」在排好序的目錄裡是從「王」開始的連續一段；% 在開頭時，符合的名字散落在整個目錄裡，排序幫不上忙。（正式伺服器上 LIKE '王%' 能不能直接用一般索引，還跟排序規則有關，見課末「補充與查表」。）

💡 實務上：後台的「搜尋框」最容易踩到這些坑
後台常有「輸入顧客名字或電話搜尋」，最直覺的寫法是 LIKE '%關鍵字%'，索引完全用不上。顧客只有幾千筆時全表掃描也很快，不用急著處理；表變大、搜尋又常用時，才考慮全文搜尋或專用索引（第 28 課）。另一個常見情況是 email 登入：與其每次查詢都寫 lower(email)，不如在寫入時就統一轉小寫存起來，查詢保持「裸的」欄位，一般索引就用得上。

補充與查表

主線用不到，但在正式環境設計索引時會遇到的兩個細節。

PostgreSQL 18 的新功能：skip scan

從 PostgreSQL 18 開始，如果複合索引的第一欄只有少數幾種值（例如後台用的 (status, ordered_at)，status 只有 3 種），資料庫可以「每種 status 各跳進去找一次」，所以只查 ordered_at 時有時候還是會用這個索引。但這比專門的索引慢，設計索引時還是照最左前綴的原則想。

排序規則與 LIKE '王%'

排序規則（collation）決定字串怎麼比大小、怎麼排序，B-tree 索引裡的值就是照它排好的。C 排序規則最單純，直接比字元的位元組，所以「以王開頭」的字串在索引裡一定排成連續的一段，LIKE '王%' 可以換算成「從王開始的一段範圍」去索引裡找。en_US.UTF-8 這類語系排序規則則依照該語言的習慣排序，比較時不是單純逐字元比，「以某段文字開頭」不保證對應到索引裡的連續範圍，所以 PostgreSQL 不會拿一般索引來做 LIKE 的前綴比對。text_pattern_ops 是一種特殊的運算子類別（operator class），讓這個索引改用逐字元比較的方式排序，LIKE 前綴查詢就用得上它；但一般的 <、> 比較和 ORDER BY 用不上這種索引，需要的話要另外建一個一般索引。

這個瀏覽器裡的資料庫用 C 排序規則，LIKE '王%' 可以直接用一般索引。正式伺服器如果用 en_US.UTF-8 這類排序規則，要建 CREATE INDEX … (name text_pattern_ops) 才行。實務上，可以先在 psql 用 \l 看清單裡的 Collation 欄，或查 SELECT datcollate FROM pg_database WHERE datname = current_database();，確認正式資料庫用的是哪一種排序規則。

練習

判分方式：查 pg_indexes，比對這張表上所有索引的定義（欄位與順序、是否 UNIQUE），不比對索引名稱，也不比對執行時間。每次判分完都會還原，所以不會留下你在題目裡建的索引。

練習 1：店長每天都要看「某一天的所有訂單」，查詢條件是 ordered_at 的範圍。幫 orders 建一個索引，讓這種查詢變快。

練習 2：App 的「我的訂單」頁面有兩種查詢：WHERE customer_id = ?，以及 WHERE customer_id = ? AND status = ?。請只建一個複合索引，讓兩種查詢都能好好利用它。

練習 3：會員用手機號碼登入，所以 customers.phone 要能快速查找，而且不能重複。建一個索引同時做到這兩件事。

練習 4：order_items 的主鍵是 (order_id, product_id)。「某個商品賣出了幾份」這類查詢只用到 product_id，目前很慢。幫它補上缺少的索引（只要一個欄位）。

練習 5：customers 已經有 name 的 B-tree 索引。下面哪一句用不到這個索引？

✓ 索引存的是 name 原本的值，對欄位套了 lower() 就對不上了。要用的話得另外建 CREATE INDEX ON customers (lower(name))。LIKE '王%' 是一段範圍、ORDER BY name 正好利用索引已經排好的順序，兩者都用得上。

練習 6：同事說「為了保險，orders 每一欄都建一個索引吧」。最主要的問題是什麼？

✓ 索引不會讓結果出錯，也沒有三個的限制，但每個索引都要在寫入時一起維護。訂單表是寫入很頻繁的表，只為真正需要的查詢建索引。

常見錯誤

  • 以為建了外鍵就有索引：外鍵只是規則，不會自動建索引。JOIN 和刪除父表資料（例如刪商品時檢查明細）都會因此變慢。
  • 複合索引欄位順序放反：(status, customer_id) 對「只查 customer_id」的幫助遠不如 (customer_id, status)。用 = 比對、最常出現的欄位放前面。
  • 在 WHERE 裡對欄位做轉換：WHERE ordered_at::date = …、WHERE lower(email) = … 會讓一般索引失效。改寫成範圍，或建表達式索引。
  • 為小表或很少跑的查詢建索引：只增加寫入成本，查詢也快不了多少。
  • 用執行時間判斷要不要建索引卻只跑一次：第一次執行常常比較慢（資料還沒進快取），多跑幾次再比。

小結

  • 查詢變慢先用 EXPLAIN ANALYZE 看：Seq Scan 加上大量 Rows Removed by Filter，表示資料庫在全表掃描。
  • 索引是另外存的一份排好序的目錄，讓資料庫直接跳到要的列；PostgreSQL 預設的 B-tree 支援 =、範圍、ORDER BY、LIKE '開頭%'。
  • CREATE INDEX 名稱 ON 表 (欄位)；主鍵和 UNIQUE 會自動建索引，外鍵不會，要自己補。UNIQUE 索引同時加速查詢和擋掉重複。
  • 複合索引看「最左前綴」：= 的欄位放前面，範圍或排序的欄位放後面，一個索引就能顧到篩選、排序和分頁。
  • 索引讓寫入變慢、佔空間，只為實際會跑又慢的查詢建；對欄位套函式、LIKE '%…'、條件選到大部分資料時，索引用不上。
