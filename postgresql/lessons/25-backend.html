階段 7：實務 · 第 25 課

從後端程式連資料庫

前面 24 課，你都在這個頁面裡直接打 SQL、按執行、看結果。真正的系統不是這樣運作的：店長打開的是咖啡店後台的網頁，網頁呼叫後端 API，SQL 是後端程式送給資料庫的。店長從頭到尾不會看到 SQL，也不該碰得到資料庫。

這一課你要從零寫出咖啡店後台的兩個功能：「顧客查詢」，店長在搜尋框輸入顧客姓名，API 回傳這位顧客的電話；以及「訂單總覽」，列出所有訂單，每筆附上顧客姓名。這些 API 要能上線給整間店用，寫的過程會依序遇到四個問題：後端怎麼連上資料庫、店長輸入的字怎麼安全地放進 SQL、很多人同時用的時候連線怎麼管理、列表資料一多怎麼不變慢。每解決一個，下一個就會冒出來。

這課會用到：
  • 第 24 課的 role 與最小權限：資料庫帳號就是 role，每個帳號只給它需要的權限。
  • 第 18 課的交易：BEGIN 到 COMMIT 之間的幾句，要嘛全部生效，要嘛全部取消。
  • 第 9 課的 JOIN：用一句查詢把兩張表的列依照條件配對起來。
這課的路線：
  1. 後端要知道什麼才連得上資料庫：連線字串是什麼、為什麼放在環境變數；接著用 pg 套件送出第一句查詢。
  2. 店長輸入的名字可以直接拼進 SQL 嗎：SQL injection 怎麼發生，參數化查詢為什麼能一次擋掉（這支 API 安全版的答案在這裡）。
  3. 每個請求都連一次線，店裡一忙會怎樣：connection pool 怎麼重複使用連線；有了 pool 之後，交易要怎麼寫。
  4. 訂單總覽要列出所有訂單、每筆附上顧客姓名，為什麼上線後越來越慢：N+1 查詢，以及用 JOIN 一次查完。
  5. 這些 SQL 都要自己手寫嗎：ORM 和 query builder 幫你做了什麼，什麼時候還是要直接寫 SQL。

後端要知道什麼，才連得上資料庫？

先想清楚「連上資料庫」是什麼意思。PostgreSQL 是一個在某台主機上執行、守在某個 port 等待連線的伺服器程式。後端程式要跟它說話，得先建立一條連線（connection）：一條持續開著的網路通道。連線建立時，資料庫會檢查帳號密碼、決定你能用哪個資料庫；之後後端在這條通道上一句一句送出 SQL，資料庫把結果從同一條通道送回來。這個頁面的執行框也是這樣，只是那條連線已經替你開好了。

所以建立連線之前，後端要知道五件事：用哪個帳號、密碼是什麼、資料庫在哪台主機、哪個 port、連哪個資料庫。這五件事通常寫成一行，叫做連線字串（connection string），格式跟網址一樣：

圖裡的帳號 cafe_app 就是第 24 課的 role。咖啡店的後端要用一個專屬的帳號，只授予它需要的權限（例如讀寫訂單、不能改表結構），不要用 postgres 這個超級使用者。原因是後端程式是最常被攻擊的地方：萬一程式有漏洞被利用，攻擊者能做的事不會超過這個帳號的權限。下一節的 SQL injection 就會用到這道防線。

連線字串裡有密碼，所以它不能寫在程式碼裡。寫在程式碼裡，就會跟著程式 commit 進 git，所有能看到這個 repository 的人、以及之後每一個 clone 下來的副本，都拿得到資料庫的密碼；git 會保留歷史，事後刪掉那一行也還查得到。正確的做法是放在環境變數：作業系統提供給程式的一組「名稱＝值」設定，程式執行時才讀進來，習慣上取名 DATABASE_URL，Node 用 process.env.DATABASE_URL 讀。本機開發時把它寫在 .env 檔，並把 .env 加進 .gitignore；正式環境則填在部署平台的環境變數設定裡。

這樣做還有第二個好處：同一份程式碼，在你的電腦上讀到的是本機資料庫的連線字串，部署到正式環境讀到的是正式資料庫的，程式碼一行都不用改。你在 Vue 專案用過 .env，但要分清楚：Vite 會把 VITE_ 開頭的變數打包進前端程式，任何人打開瀏覽器都看得到。DATABASE_URL 只能存在後端，絕對不能出現在前端。

雲端資料庫的連線字串通常還會在最後加上 ?sslmode=require，要求這條連線用 SSL 加密。這層加密現在的正式名稱是 TLS（SSL 是它的舊名，PostgreSQL 的參數沿用 ssl 這個字）。後端和資料庫之間的網路不一定是你能控制的，不加密的話，帳號密碼和查詢結果會以明文在網路上傳。

💡 實務上：每個環境一組連線字串，外洩就換密碼
咖啡店系統通常有本機、staging（上線前的測試環境）、正式三個環境，各自有自己的 DATABASE_URL，正式環境的那組只放在部署平台的環境變數或 CI（自動測試、部署的流程）的 secrets 設定裡，大部分工程師平常碰不到。應用程式和跑 migration 的帳號也常分開：應用程式只能讀寫資料，改表結構的權限只給 migration 用。另一個常見的坑是錯誤處理把整個設定物件印進 log，連線字串就跟著密碼一起出現在 log 系統裡。萬一密碼真的外洩（誤 commit、貼到聊天群組），從 git 刪掉不夠，要直接換密碼，再更新各環境的設定。

用 pg 套件送出第一句查詢

有了連線字串，接下來要有一個套件負責「建立連線、送出 SQL、把結果轉成 JavaScript 物件」。Node 最常用的 PostgreSQL 套件是 pg（又叫 node-postgres）。下面的程式碼是片段，這個頁面不會執行它們。最直接的用法是建立一個 Client，它代表一條連線：

// npm install pg
import pg from 'pg'

const client = new pg.Client({ connectionString: process.env.DATABASE_URL })
await client.connect()   // 建立連線：連到主機、驗證帳號密碼

const { rows } = await client.query('SELECT name, phone FROM customers WHERE name = \'王小明\'')
console.log(rows)        // [{ name: '王小明', phone: '0912-345-678' }]

await client.end()       // 關閉連線

rows 是一個陣列，每一列結果是一個物件，物件的 key 就是 SELECT 出來的欄位名稱。後端再把它轉成 JSON 回給前端，你在 Vue 元件裡讀到的 customer.phone，就是從這裡來的。

這句查詢把「王小明」寫死在 SQL 裡。真正的 API 要查的是店長在搜尋框輸入的名字，也就是 HTTP 請求帶進來的 req.query.name。最直覺的寫法是把它接進 SQL 字串裡，而後端最危險的漏洞，就是從這個寫法開始的。

店長輸入的名字，可以直接拼進 SQL 嗎？

先照直覺寫，把使用者的輸入用字串接起來：

// ✗ 危險：把使用者輸入直接拼進 SQL 字串
const sql = "SELECT name, phone FROM customers WHERE name = '" + req.query.name + "'"
const { rows } = await client.query(sql)

店長輸入「王小明」，拼出來的是 WHERE name = '王小明'，一切正常。問題在於：資料庫收到的是一整串文字，它會把整串當成 SQL 語法重新解析一次，分不出哪一段是你寫的、哪一段是使用者打的。SQL 用單引號標出字串的開頭和結尾，所以只要輸入裡有單引號，就能提早結束字串，後面的內容就變成 SQL 語法了。

假設有人在搜尋框輸入 ' OR '1'='1，拼出來的 SQL 會變成：

SELECT name, phone FROM customers WHERE name = '' OR '1'='1'

逐段看：輸入開頭的 ' 把 name = ' 的字串關掉，變成「名字等於空字串」；接著的 OR '1'='1 是使用者塞進來的新條件；結尾少的那個單引號，剛好由程式原本寫好的 "'" 補上。'1'='1' 永遠成立，所以 WHERE 對每一列都成立，所有顧客的電話都被查出來了。

這就是 SQL injection（SQL 注入）：使用者的輸入改變了 SQL 的結構，讓資料庫執行了開發者沒有寫的查詢。查出全部電話還算輕的，攻擊者可以用 UNION（把另一句查詢的結果接在後面）讀其他表，例如員工的帳號和密碼雜湊；帳號權限夠的話，也能改資料、刪資料。

按「✗ 字串拼接」時，第一個攻擊輸入查出了全部 6 位顧客；第二個用 UNION 把 staff_accounts 的帳號和密碼雜湊接在結果後面，最後的 -- 是 SQL 的註解符號，把程式原本補上的那個單引號註解掉，語法才不會出錯。按「✓ 參數化查詢」時，兩個攻擊輸入都只查到 0 列。差別只在程式的寫法：


// ✓ 參數化查詢：SQL 和值分開送
const { rows } = await client.query(
  'SELECT name, phone FROM customers WHERE name = $1',
  [req.query.name]
)


參數化查詢（parameterized query）的做法是：SQL 字串裡要放值的地方寫成 $1、$2（第幾個參數），值放在第二個引數的陣列裡，依序對應。pg 會把 SQL 原封不動、跟參數分開送給資料庫，由資料庫自己把值代進去。


為什麼這樣就安全？因為順序反過來了。資料庫先解析 WHERE name = $1，這時候結構已經確定：「找 name 等於某個值的列」。之後才拿到 ' OR '1'='1，而它只能被當成那「一個值」，整串文字拿去跟 name 比對。不管輸入裡有幾個單引號、OR、UNION，都不會再被解析成 SQL 語法，沒有一位顧客叫這個名字，所以查到 0 列。


你在 SQL 裡也能親眼看到同一件事。PostgreSQL 的 PREPARE 先準備好一句有參數的查詢，EXECUTE 再帶值執行，pg 套件背後做的就是類似的事。執行後看第二個 EXECUTE 的結果：




第二個 EXECUTE 傳入的就是 ' OR '1'='1 這串文字（SQL 字串裡的單引號要寫兩次），結果是 0 列。最後的 DEALLOCATE 把準備好的查詢刪掉，這格才能重複執行。



  規則只有一條：使用者的輸入永遠用參數傳，絕不拼進 SQL 字串。

  自己「跳脫」單引號（把 ' 換成 ''）不是解法，總有漏掉的寫法。表名、欄位名、ORDER BY 的方向這類無法參數化的部分，要用白名單（只允許幾個固定的值）。另外，上一課的最小權限也是第二道防線：就算被注入，唯讀帳號也刪不掉資料。



白名單的意思是：程式先準備好允許的幾個寫法，使用者的輸入只用來「選」其中一個，從來不會直接進到 SQL 字串。例如讓店長切換訂單的排序方向：


// 參數只能放「值」，ASC／DESC 是語法，不能用 $1
const dir = req.query.dir === 'asc' ? 'ASC' : 'DESC'   // 只可能是這兩個字之一
const { rows } = await client.query(
  `SELECT id, total FROM orders WHERE customer_id = $1 ORDER BY ordered_at ${dir}`,
  [customerId]
)


這裡的模板字串是安全的，因為 ${dir} 只可能是程式自己寫的 'ASC' 或 'DESC'，使用者輸入什麼都影響不了；值（customerId）照樣用參數傳。


💡 實務上：最容易出事的是後台的搜尋、篩選和排序
一般的「用 id 查一筆」大家都會用參數，真正容易漏的是咖啡店後台訂單列表這種功能：關鍵字搜尋、多個可選的篩選條件、讓使用者點欄位排序，寫的人為了動態組條件，很容易順手用模板字串拼起來。code review 時，看到 query( 裡面出現 ${ 或 + 就該停下來問；本課最後一節會介紹的 ORM 工具裡，名稱帶 Unsafe、raw 的方法（例如 Prisma 的 $queryRawUnsafe）也要特別看。動態條件的正確做法是：條件的「有無」用程式決定要不要加上 AND city = $2 這段固定的 SQL，值一樣用參數傳。


到這裡，顧客查詢 API 已經是安全的了。但它還沒準備好上線：目前的寫法是每次查詢都 new Client()、連線、查詢、斷線。店裡只有你一個人測試時看不出問題，整間店的店員同時在用時就不一樣了。



每個請求都連一次線，店裡一忙會怎樣？


「每個 API 請求都 new Client()、連線、查詢、斷線」聽起來很單純，但實際上行不通，原因有兩個：


    
  
  • 建立連線很貴：建立連線時雙方要先來回交換幾次訊息確認身分、協商加密（TLS），才能開始送 SQL，PostgreSQL 還要為每條連線開一個新的程序（process）。一次常常要幾十毫秒，比查詢本身還久。
    • 
  
  • 連線數有上限：PostgreSQL 的 max_connections 預設是 100，每條連線都佔記憶體。網站一忙，請求一多，連線數超過上限，新的請求就會直接失敗。
    • 



換成咖啡店的情境：顧客查詢 API 一次查詢只要幾毫秒，卻每次都先花幾十毫秒建立連線，大部分時間浪費在「打招呼」上。到了尖峰時段，同時進來的請求多到超過上限，有些店員的畫面就會直接出現錯誤，而不是慢一點而已。


解法是 connection pool（連線池）：保留一批連線重複使用。需要時才建立，數量最多到上限（例如 max: 10），用完不關掉；請求來了就「借」一條，用完「還」回去給下一個請求用。連線都被借走時，新來的請求排隊等別人還，而不是再開新的連線。就像咖啡店不會每來一位客人就僱一個店員，而是固定幾個店員輪流服務。


const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,                 // 最多 10 條連線
  idleTimeoutMillis: 30000 // 閒置 30 秒的連線就關掉
})


pool 在程式啟動時建立一次，整個後端共用，不要每個請求各建一個。查詢的寫法幾乎不變：


// $1、$2 是參數的位置，值放在第二個參數的陣列裡
const { rows } = await pool.query(
  'SELECT name, phone FROM customers WHERE name = $1',
  [req.query.name]
)
console.log(rows)  // [{ name: '王小明', phone: '0912-345-678' }]


pool.query 的參數寫法跟 client.query 完全一樣，差別在背後：它會自動借一條閒置的連線，送出這一句，拿到結果就還回去，你不用自己管借和還。上一節安全版的顧客查詢，只要把 client.query 換成 pool.query，就能交給整間店同時使用。


💡 實務上：pool 的 max 要用「全部實例加起來」來算
後端部署時通常不只一個實例：咖啡店 API 跑 3 個容器、每個 max: 10，資料庫那邊最多就會有 30 條連線，再加上排程工作、後台管理工具，總數要留在資料庫的上限內。上線後如果 API 變慢，查下去發現請求都卡在等 pool 給連線，不要第一時間把 max 調大：先查有沒有借了沒還的連線，或是有沒有慢查詢把連線佔太久。連線數開太多反而會讓資料庫變慢，pool 的監控和調校之後的課會再談。部署在 serverless 平台時還有另一個問題，見課末「補充與查表」。



有了 pool，好幾句要一起成功的操作怎麼寫？


「每一句自動借、自動還」對單句查詢很方便，碰到交易就出問題了。假設後台要讓店長幫顧客補登一筆訂單：新增一筆 orders，再新增它的 order_items，兩句必須一起成功，這正是第 18 課的交易。


關鍵在於：交易是「一條連線」上的狀態。在某條連線上執行 BEGIN，資料庫記住的是「這條連線現在在交易裡」，之後同一條連線送來的句子才算進這個交易。如果每句都用 pool.query，每句各自借一條閒置的連線，BEGIN 可能跑在 A 連線、INSERT 跑在 B 連線、COMMIT 跑在 C 連線，三句彼此無關，交易形同沒寫；A 連線還會帶著一個沒結束的交易被還回 pool，下一個借到它的請求就莫名其妙在交易裡了。


所以交易要用 pool.connect() 手動借出同一條連線，所有句子都用它送，用完一定要還回去：


const client = await pool.connect()
try {
  await client.query('BEGIN')
  const { rows } = await client.query(
    'INSERT INTO orders (customer_id, ordered_at, total) VALUES ($1, now(), $2) RETURNING id',
    [1, 190]
  )
  await client.query(
    'INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4), ($1, $5, $6, $7)',
    [rows[0].id, 1, 1, 80, 2, 1, 110]
  )
  await client.query('COMMIT')
} catch (e) {
  await client.query('ROLLBACK')
  throw e
} finally {
  client.release()   // 還給 pool，忘了就會「漏」連線
}


這段的三個部分各有用處。try 裡依序送出 BEGIN、兩句 INSERT、COMMIT，全部在同一個 client 上。任何一句出錯就跳到 catch，送出 ROLLBACK 把已經做的取消，再把錯誤往外丟給 API 處理。finally 不管成功或失敗都會執行，在這裡 release() 把連線還給 pool。


為什麼 release() 一定要放在 finally？手動借出的連線，pool 不會自己收回。只在成功的路徑上還，每出錯一次 pool 就少一條連線，max: 10 的 pool 出錯 10 次就被借光，之後所有請求都卡在排隊，整個 API 停擺，重啟程式之前都不會恢復。這種「借了沒還」叫做連線洩漏，是上一個💡提到「先查有沒有借了沒還的連線」的原因。


連線會被重複使用還有一個後果：在連線上做的設定會留著。例如用 SET 改了某個設定、或交易沒結束就還回去，下一個借到這條連線的請求會接手這些狀態。所以借出去的連線，還回去之前要回到乾淨的狀態，交易一定要 COMMIT 或 ROLLBACK 收尾。


現在顧客查詢 API 安全了，連線也管好了。接下來要做後台的另一個畫面：訂單總覽，列出所有訂單、每筆附上顧客姓名。它在本機測試時很快，上線幾個月後卻會越來越慢。



訂單列表附顧客姓名，為什麼上線後越來越慢？


「列出所有訂單，每筆附上顧客姓名」，訂單表只有 customer_id，姓名在 customers 表。從前端轉過來的人，很自然會寫成「先拿列表、再一筆一筆補資料」：


const orders = (await pool.query('SELECT id, customer_id, total FROM orders')).rows  // 1 次
for (const o of orders) {
  const c = await pool.query('SELECT name FROM customers WHERE id = $1', [o.customer_id])  // 每筆訂單 1 次
  o.customerName = c.rows[0].name
}


這段程式結果完全正確，參數也用對了，問題在查詢的次數：先查 1 次訂單，有 N 筆訂單，迴圈裡就再查 N 次顧客，總共送出 1 + N 次查詢，這就叫 N+1 查詢。


為什麼次數多就慢？每一句查詢都要走完一次完整的來回：後端把 SQL 送過網路、資料庫解析和執行、結果再送回來，而且迴圈裡的 await 讓它們一句接一句排隊，前一句回來了才送下一句。資料庫查一筆顧客本身很快，時間主要花在網路來回上。就算每次只要 1 毫秒，1000 筆訂單就是 1 秒多；資料庫在另一個機房時，一次來回更久。



解法是把配對的工作交給資料庫，一次做完：用第 9 課的 JOIN。後端只送出一句，資料庫在內部把每筆訂單跟它的顧客配對好，整份結果一次送回來。執行下面這格，看每筆訂單是不是都帶著顧客姓名：




一句 SQL 取代了 1 + N 次查詢，而且不管訂單有 8 筆還是 8 萬筆，來回都只有 1 次。如果因為某些原因必須分兩次查（例如顧客資料在另一個服務），也不要在迴圈裡一筆一筆查，而是先收集所有需要的 id，用 WHERE id = ANY($1) 把整個陣列當一個參數傳進去，一次查回全部，總共 2 次查詢。


💡 實務上：N+1 在本機很快，上線資料一多才爆
本機只有幾筆測試訂單，N+1 的頁面一樣秒開，所以它常常是上線幾個月後，客服回報「後台訂單列表越來越慢」才被發現。開發時把 ORM 或 pg 的查詢 log 打開，看一個 API 請求送出幾句 SQL：數量跟著資料筆數一起增加，就是 N+1。前端列表每一列各自呼叫一次 API 拿資料，是同一個問題搬到前端的版本。review 時看到迴圈裡有 await 查詢，資深工程師會先問：「這個列表最多會有幾筆？」


到這裡，顧客查詢 API 的每一句 SQL 都是你手寫的：寫 SQL 字串、排參數順序、把結果欄位接到物件上。功能一多，這些重複的工作會很繁瑣，所以實務上很多團隊會用工具代勞。問題是，這些工具會不會讓前面三節的問題消失？



這些 SQL 都要自己手寫嗎？ORM 和 query builder


手寫 SQL 字串，再把結果的每一列轉成程式裡的物件，寫多了很繁瑣。所以有兩類工具：


    
  
  • ORM（Object-Relational Mapping，物件關聯對應）：把一張表對應成程式裡的一種物件，你用物件和方法描述想要的資料，它幫你產生 SQL、執行，再把結果轉回物件。幾乎不用寫 SQL。
    • 
  
  • query builder：用一連串函式「組」出 SQL，結構還是 SQL 的樣子（where、select、join），只是換成函式呼叫，比手寫字串不容易拼錯。
    • 






  
類型工具長什麼樣

  
ORMPrisma、TypeORM、SequelizePrisma 寫法：
prisma.order.findMany({ where: { customerId: 1 }, include: { customer: true } })

  
query builderKnex、Drizzle、KyselyKnex 寫法：
knex('orders').where('customer_id', 1).select('id', 'total')






你熟悉的 Strapi 底層就是用 Knex 跟資料庫溝通。你在 Strapi 寫 strapi.documents('api::order.order').findMany({ populate: ['customer'] })，它在背後幫你組成 SQL。


用這些工具，前面三節的問題各會變成什麼樣子：


    
  
  • SQL injection：這些工具全部都會自動使用參數化查詢，所以只要不用它們提供的「原生 SQL」功能拼字串，就不會有 SQL injection。
    • 
  
  • 連線：它們背後一樣用連線字串連線、一樣有 pool，交易也一樣要在同一條連線上，只是由工具的交易 API 幫你借和還。
    • 
  
  • N+1：ORM 有對應的寫法，Prisma 的 include、Strapi 的 populate，它們會用 JOIN 或「一次查回所有需要的 id（WHERE id IN (…)）」來避免 N+1。但如果你在迴圈裡對每筆資料各呼叫一次 ORM 的查詢方法，寫出來的就是 N+1，ORM 擋不住。
    • 



什麼時候該直接寫 SQL？


    
  
  • 用 ORM：一般的新增、查詢、修改，有型別檢查、寫起來快、不容易寫錯。
    • 
  
  • 直接寫 SQL：複雜的報表（視窗函式、CTE、多層 GROUP BY）、效能關鍵的查詢、ORM 產生的 SQL 太慢時。各工具都有寫原生 SQL 的方式，例如 Prisma 的 prisma.$queryRaw，記得用它提供的參數寫法。
    • 



不管用哪一種，都要懂 SQL。工具只是替你產生 SQL，送到資料庫的仍然是 SQL：ORM 產生的查詢慢了，你還是要把它印出來，用第 21 課的 EXPLAIN 去看它到底下了什麼；N+1 也要看查詢 log 才發現得了。這也是這門課前 24 課的用處。



補充與查表


    
  
  • Serverless 與共用的 pooler：Serverless（不自己管伺服器，由雲端依請求啟動函式，例如 Vercel、Lambda）的情況更麻煩：每個函式實例都有自己的 pool，同時有 200 個實例就可能開出幾千條連線。所以會在資料庫前面再放一個共用的 pooler。Supabase 提供的 pooler（Supavisor）就是這個角色：連線字串裡的 port 用 6543 是「transaction 模式」，每個交易結束就把連線還回去給別人用，適合 serverless；直連資料庫則是 5432。其他常見的 pooler 還有 PgBouncer。
    • 
  
  • 密碼裡有特殊符號：連線字串的格式跟網址一樣，密碼裡有 @、:、/ 這類符號時要先做 URL 編碼（例如 @ 寫成 %40），不然會被當成分隔符號，解析出錯誤的主機或帳號。
    • 




練習




  
練習 1：下面這段程式有 N+1 問題。改寫成一句 SQL，結果要跟程式一樣（只要台北的顧客），依序回傳 orders.id、顧客姓名、total，依訂單 id 排序。


const orders = (await pool.query('SELECT * FROM orders ORDER BY id')).rows
for (const o of orders) {
  const c = (await pool.query('SELECT name, city FROM customers WHERE id = $1', [o.customer_id])).rows[0]
  if (c.city === '台北') result.push({ id: o.id, name: c.name, total: o.total })
}






  
練習 2：這段程式算每位顧客的訂單數，也是 N+1。改寫成一句 SQL，依序回傳顧客姓名、訂單數，依顧客 id 排序。注意：沒有訂單的顧客也要出現，訂單數是 0。


const customers = (await pool.query('SELECT * FROM customers ORDER BY id')).rows
for (const c of customers) {
  const r = await pool.query('SELECT count(*) FROM orders WHERE customer_id = $1', [c.id])
  result.push({ name: c.name, orderCount: Number(r.rows[0].count) })
}






  
練習 3：「王小明（customer_id = 1）的訂單明細」頁面原本是：查他的訂單 → 每筆訂單查明細 → 每筆明細查商品名稱，兩層 N+1。改寫成一句 SQL，依序回傳 order_id、商品名稱、quantity，依 order_id、商品 id 排序。






  
練習 4：搜尋 API 寫成 pool.query("SELECT * FROM products WHERE name LIKE '%" + keyword + "%'")。最正確的修法是？

  
  
  
  
✓ 參數化查詢讓輸入永遠只是「值」。前端檢查可以被繞過（攻擊者直接呼叫 API）；自己跳脫容易漏掉邊界情況。注意 % 是放在參數的值裡，而不是拼在 SQL 字串裡。






  
練習 5：為什麼後端通常用 connection pool，而不是每個請求都建立一條新連線？

  
  
  
  
✓ pool 重複使用少量的連線，省下建立連線的時間，也避免連線數爆掉。它不會快取查詢結果；PostgreSQL 也可以同時有很多條連線（預設上限 100）。






  
練習 6：哪一種情況最適合直接寫 SQL，而不用 ORM 的一般方法？

  
  
  
  
✓ 牽涉 GROUP BY、視窗函式（第 17 課）的複雜報表，用 SQL 寫最清楚，也最容易用 EXPLAIN 調校。簡單的 CRUD 用 ORM 比較快、比較安全。





常見錯誤


    
  
  • 用字串拼接或模板字串組 SQL：`… WHERE id = ${id}` 跟用 + 拼接一樣危險，使用者的輸入會被當成 SQL 語法解析。值要用參數傳；排序方向、欄位名這類不能參數化的部分用白名單。
    • 
  
  • 連線字串寫死在程式碼、commit 進 git：密碼外洩，而且 git 歷史會一直留著。用環境變數；已經外洩就換密碼。
    • 
  
  • 從 pool 借了連線沒還：pool.connect() 之後沒有在 finally 裡 release()，每出錯一次就少一條連線，很快被借光，整個服務卡住。
    • 
  
  • 交易的每一句用不同的連線：直接用 pool.query('BEGIN')，下一句可能跑在另一條連線上。交易要用 pool.connect() 借出的同一個 client。
    • 
  
  • 在迴圈裡查資料庫：幾乎都是 N+1。改成 JOIN，或用 WHERE id = ANY($1) 一次查回所有需要的資料。
    • 




小結


    
  
  • 後端透過連線和資料庫說話；連線字串 postgres://帳號:密碼@主機:5432/資料庫 放在環境變數，不進 git，帳號用權限最小的專屬 role。
    • 
  
  • 使用者輸入一律用參數傳（$1、$2）：資料庫先確定 SQL 的結構，再把輸入當成值代入，所以不會有 SQL injection。
    • 
  
  • 用 connection pool 重複使用連線，一般查詢用 pool.query；交易用 pool.connect() 借出同一條連線，在 finally 裡 release()。serverless 環境再加上 Supabase pooler、PgBouncer 這類共用的 pooler。
    • 
  
  • 在迴圈裡查詢會造成 N+1，次數跟著資料筆數增加；改用 JOIN 一次查完。
    • 
  
  • ORM（Prisma）和 query builder（Knex、Drizzle）幫你組 SQL、自動參數化，但擋不住在迴圈裡查詢；複雜報表和效能關鍵的查詢直接寫 SQL。
