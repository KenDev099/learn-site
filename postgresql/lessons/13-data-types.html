階段 3：資料品質 · 第 13 課

選對資料型別

咖啡店要推出禮物卡：顧客在線上買一張卡，拿到一個兌換網址，之後在店裡或線上點餐時從卡片餘額扣款。上一位工程師留下了一份資料表草稿，PM 請你在上線前看過一遍：

CREATE TABLE gift_cards (
  id          integer,           -- 卡號，自動編號 1、2、3…，放在兌換網址裡
  balance     double precision,  -- 餘額
  is_active   varchar(1),        -- 'Y' 或 'N'
  expires_on  varchar(255),      -- 到期日，例如 '2026/12/31'
  created_at  timestamp,         -- 建立時間
  note        varchar(255)       -- 備註
);

這張表建得起來，測試時存幾筆也都正常。問題要等上線幾個月才會浮現：月底對帳時，餘額加總跟收款金額差了幾分錢；在紐約的顧客說 App 上的購買時間差了 12 小時；有人把兌換網址裡的 1024 改成 1025，看到了別人的卡。這些都不是程式邏輯寫錯，而是欄位的型別選錯了。

型別決定一欄能存什麼值、怎麼比較、怎麼計算。第 2 課先記了五個型別，這一課用這份草稿當主線，一欄一欄檢查：每種資料該選哪個型別、選錯會出什麼事。型別也是一種約束，選對了，很多錯誤根本寫不進來。改完的版本，就是練習 4 要你親手寫出的 gift_cards。

這課會用到：
  • 第 2 課的型別（建表時每一欄都要決定存什麼種類的值，例如 integer、text）。
  • 第 12 課的 CHECK（寫在表上的規則，不符合的值寫不進去）。
這課的路線：
  1. 先學一個檢查工具 ::，再看草稿的 note varchar(255)：在 PostgreSQL 限制長度有沒有意義。
  2. 自動編號的 id 會不會用完（integer 和 bigint），餘額為什麼對不上帳（浮點數和 numeric）。
  3. 購買時間為什麼差 12 小時（timestamptz），到期日存成文字會怎樣、「10 月 20 日一整天」怎麼查（date、interval）。
  4. is_active 的 'Y'／'N' 和被猜到的卡號：boolean 與 uuid。
  5. 卡片狀態這種固定選項：enum 還是 text 加 CHECK，最後是課末的型別速查表。
第一輪只要記住：
  • 文字一律 text，不用煩惱 varchar(255)。
  • 金額用 numeric 或以元／分為單位的整數，不要用浮點數；數量和 id 用 integer，會大量成長的表的 id 用 bigint。
  • 事件發生的時間用 timestamptz，只有日期（生日、到期日）用 date。
  • 訂單狀態這種固定選項用 text 加 CHECK。
interval、uuid、enum 這些細節先看過有印象，要用時再回到課末「補充與查表」裡的型別速查。

要檢查草稿，先學一個工具：怎麼把一個值當成某個型別？

檢查型別最直接的方法，是拿一個值餵給那個型別，看資料庫怎麼處理它：存得進去嗎？算出來對嗎？比較的結果是什麼？為了做這件事，不必每次都建一張表，只要能在 SELECT 裡說「把這個值當成某個型別」就好。這就是型別轉換。

PostgreSQL 的寫法是 值::型別。例如 '2026-10-29' 用單引號包起來，本來只是一串文字，資料庫不知道它是日期，也就不能拿來加減天數；加上 ::date 之後，它才是一個日期，+ 1 會得到隔天：

第三個值用的 CAST(值 AS 型別) 是 SQL 標準寫法，效果和 :: 一樣；:: 是 PostgreSQL 自己的簡寫，因為短，實務上比較常見。兩種寫法你都會在別人的程式裡看到。

這個「轉不過去就報錯」的行為，正是型別能當約束的原因：一欄宣告成 integer，'abc' 就永遠寫不進去。接下來每一節都會用 :: 拿值去試型別，第一個要試的是草稿最後一欄 note varchar(255)。

備註欄寫 varchar(255)，有必要嗎？

varchar(n) 的意思是「最多 n 個字的文字」。它和 text 一樣存文字，差別只在多了一個長度上限，超過就報錯。下面把一個 11 個字的代碼放進最多 5 個字的欄位：

那為什麼到處都看得到 varchar(255)？因為在 MySQL 等資料庫，varchar 和 text 的儲存方式不同，選錯會影響效能，varchar(255) 就成了很多人的習慣寫法，也跟著教學和 ORM 的預設值流傳下來。但在 PostgreSQL 裡，text、varchar、varchar(n) 的儲存和效能完全一樣，差別只在 varchar(n) 寫入時多檢查一次長度。

所以在 PostgreSQL，長度上限只剩下「業務規則」的意義，沒有效能上的理由。這樣判斷就清楚了：

  • 沒有明確長度限制的欄位（名字、地址、備註）直接用 text。草稿的 note 屬於這種。
  • 真的有業務上的上限（例如統一編號 8 碼）才加限制。varchar(n) 可以；也可以用 text 加 CHECK (char_length(欄位) <= n)，日後要放寬時改 CHECK 比較單純。
  • 不要為了「看起來比較專業」隨手寫 varchar(255)：255 這個數字沒有意義，還會讓第 256 個字的地址存不進去。

文字欄的問題，最壞是某天有人存不進一段長備註。下一欄 id integer 的問題比較隱蔽：它今天完全正常，要等到某一天才會讓整張表無法新增資料。

id 用 integer 自動編號，會不會有用完的一天？

整數型別有三種，差別在能存多大的數字，以及每個值佔多少空間：

型別範圍大小用在
smallint約 ±3 萬2 bytes很少用，省不了多少空間
integer約 ±21 億4 bytes數量、杯數、一般的 id
bigint約 ±922 京8 bytes可能非常多列的表的 id、以「分」為單位的大金額

integer 的上限是 2147483647。超過上限不會自動變成更大的型別，而是直接報錯。先看 integer 加 1，再看同一個數字轉成 bigint 後加 1：

第一格出錯，第二格正常。換到 id 上：自動編號每新增一列就加 1，編到 2147483647 之後，下一筆 INSERT 一樣會因為超出範圍而失敗，而且是之後的每一筆都失敗，直到你把欄位改成 bigint。這時要改已經很痛：表裡已經有二十多億列，改型別要重寫整張大表，外鍵參照它的欄位也得一起改。

21 億聽起來很多，但要看這張表長得多快。禮物卡本身不會賣到 21 億張，integer 綽綽有餘；可是每次扣款都要記一筆的使用紀錄表，或記錄每次點擊的 log 表，成長速度是另一個量級。判斷規則是：會持續大量成長的表（log、事件、訂單明細），id 直接用 bigint；顧客、商品這種不會到億的表用 integer 就好。外鍵型別要跟著主鍵一致：主鍵是 bigint，參照它的欄位也要是 bigint。

禮物卡的 id 不會用完，但它放在兌換網址裡，還有另一個問題，留到後面講 uuid 時處理。草稿下一欄 balance double precision 的問題就沒這麼遙遠了：它從第一筆資料開始就不精確。

餘額用 double precision，為什麼月底對不上帳？

real 和 double precision 是浮點數，跟 JavaScript 的 number 是同一種東西。浮點數用二進位存小數，而很多十進位的小數換成二進位是除不盡的，就像 1/3 寫成十進位是 0.333… 沒有盡頭。0.1 就是這種數，存進浮點數時只能存一個非常接近 0.1 的近似值。直接看結果：

浮點數算出 0.30000000000000004，而且跟 0.3 比較是 false。你在瀏覽器的 console 打 0.1 + 0.2 會看到一模一樣的結果。一筆差一點點看不出來，但禮物卡餘額每天被扣款、加值好幾次，加總十萬筆、算稅、對帳時就會出現對不起來的零頭；更麻煩的是 balance = 0 這種判斷，可能因為剩下 0.0000000000001 而永遠不成立。

解法是 numeric：精確的十進位數字，0.1 存進去就是 0.1，加減乘都照十進位算，不會有近似值。numeric(10,2) 代表總共 10 位、其中小數 2 位，超過的小數會四捨五入。下面三個值分別看：超過兩位小數怎麼處理、浮點數乘法的誤差、同樣的乘法用 numeric 的結果：

三個結果分別是：12.345 存進 numeric(10,2) 變成 12.35（第三位小數四捨五入）；浮點數 1.1 × 3 得到 3.3000000000000003；numeric 剛好是 3.3。乘法跟加法一樣會出現零頭，所以算折扣、算稅時也不能用浮點數。

所以選型別的規則是：

  • 金額、匯率、任何要對帳的數字：numeric。禮物卡的 balance 改成 numeric(10,2)。
  • 新台幣通常沒有小數，像這門課一樣用 integer（或 bigint）存「元」也很常見；有小數的幣別也可以用整數存「分」。重點是不要用浮點數。
  • 浮點數適合「本來就是近似值」的資料，例如感測器讀數、經緯度、科學計算。
💡 實務上：金額要從資料庫一路精確到畫面
咖啡店的結帳、發票、月底對帳都靠金額欄位，資料庫存對了，後端和前端也不能偷偷轉回浮點數。JavaScript 的 number 就是浮點數，所以很多 Node.js 連資料庫的套件（例如 pg）會把 numeric、bigint 當成字串回傳，前端顯示前別隨手 parseFloat 再相乘。開欄位前先問清楚：有沒有外幣、要不要小數、折扣後的零頭在「每一項」還是「整筆」四捨五入，這些通常要跟 PM 或會計確認，不是工程師自己決定。

金額改對了，對帳的數字就不會憑空多出零頭。但對帳還要知道「每一筆是什麼時候發生的」，草稿的 created_at timestamp 就是紐約顧客那張客服單的來源。

紐約的顧客，為什麼看到差 12 小時的購買時間？

要看懂這個問題，先講清楚時區。同一個瞬間，台北的時鐘是下午 2:30，紐約的時鐘是凌晨 2:30。為了不用每次都說「哪裡的幾點」，大家約定一個基準時鐘叫世界協調時間（UTC），同一瞬間它是早上 6:30；其他地方用「比 UTC 快或慢幾小時」表示：台北是 +08，所以 14:30+08 和 06:30+00 是同一瞬間。

資料庫的每條連線也有自己的時區設定，決定時間要用哪裡的時鐘顯示。PostgreSQL 存時間有兩個名字很像、行為完全不同的型別：

  • timestamptz（timestamp with time zone）：記錄的是一個絕對的時間點。寫入時依時區換算成 UTC 存起來，讀出時再換算成「目前連線設定的時區」顯示。
  • timestamp（without time zone）：只記「牆上時鐘的數字」，不知道是哪個時區的 14:30。如果寫入的值帶了 +08，這個時區資訊會被直接丟掉。

把同一個值寫進兩種欄位，再切換連線的時區看看。這頁一開始的時區是台北（Asia/Taipei），SHOW TIME ZONE 會印出目前的設定，SET TIME ZONE 會換掉它：

比較三次查詢的結果：

  • with_tz 每次顯示都不一樣（14:30+08、06:30+00、02:30-04），但它們是同一個時間點，只是用不同地方的時鐘來說。
  • without_tz 永遠是 14:30，而且沒有時區。紐約的同事看到 14:30，會以為是紐約的下午兩點半，差了 12 個小時。

這就是客服單的原因：草稿的 created_at 是 timestamp，存進去的只剩「14:30」，App 把它當成使用者當地的時間顯示，紐約的顧客就看到差了 12 小時的購買時間。更糟的是事後無法修正，因為資料裡已經沒有「這是台北時間」的線索。最後一行把時區設回台北，後面的範例才不會受影響。

規則：記錄「某件事發生的時間」一律用 timestamptz。訂單時間、建立時間、登入時間都是，禮物卡的 created_at 也是。伺服器搬到別的時區、使用者在國外、夏令時間，timestamptz 都不會出錯。timestamp 只在「刻意不綁時區的當地日期時間」才用，例如「各分店都在當地時間 2026-12-31 22:00 開始跨年活動」。

建立時間解決了。草稿裡還有一個跟時間有關的欄位：expires_on varchar(255)，到期日只有日期、沒有幾點幾分，而且被存成了文字。

到期日存成文字會怎樣？date 和 interval

把日期存成文字，一開始看不出問題。等不同的人、不同的程式寫進 '2026/12/31'、'12-31-2026'、'2026-1-5'，資料庫只把它們當成一串字，排序會照字元一個一個比，「哪些卡下個月到期」也沒辦法計算。資料庫也擋不住 '2026-02-30' 這種不存在的日期。

只有日期的資料用 date，適合生日、訂位日、到期日。它只接受真正的日期，而且可以直接做運算。另一個常一起出現的型別是 interval，表示「一段時間長度」，例如 2 小時、1 天 3 小時。下面四個值分別是：日期加 30 天、兩個日期相差幾天、時間點加 2 小時、時間長度乘 2：

  • date + 整數 是加幾天，結果還是 date；date - date 得到相差的天數（整數）。禮物卡「購買後一年到期」、點數「30 天後到期」都是這種計算。
  • timestamptz + interval 得到另一個時間點。實務上常寫 WHERE ordered_at >= now() - interval '7 days' 找最近七天的訂單。

時間型別最常用在「查某一段時間的資料」。月底對帳時，會計會要「10 月 20 日一整天」的訂單，這頁的 orders 表裡刻意放了 23:50、00:10、23:59、00:00 這些跨日附近的時間：

上面找出 10 月 20 日（台北時間）一整天的訂單。字串 '2026-10-20' 沒寫時區，就用目前連線的時區（台北）解讀成當天 0 點。用「大於等於當天 0 點、小於隔天 0 點」是查一整天最穩的寫法：19 日 23:50 和 21 日 00:00 都不會被算進來，20 日 23:59 也不會漏掉。

💡 實務上：「今天」是哪裡的今天，要先講好
後台的「今日營收」「近 7 天訂單」都是時間區間查詢，跨日的那幾筆最容易算錯，例如 23:50 和 00:10 的訂單該算哪一天。資料庫存 timestamptz，前端送 ISO 格式（像 2026-10-20T14:30:00+08:00）就不會有歧義；真正要決定的是報表用哪個時區切日，有海外分店或海外使用者時要先問 PM。測試時刻意塞幾筆 23:59、00:00 的資料，比上線後被客服回報「昨天的單跑到今天」好處理得多。

時間欄位都改好了。草稿還剩 is_active varchar(1)：一個只有「是」或「否」的欄位，被存成了一個字的文字。

is_active 存 'Y'／'N' 有什麼問題？boolean

用 'Y'／'N' 或 integer 的 0／1 存是非題，資料庫看到的是一般的文字或數字，所以 'y'、'是'、2 都寫得進去，每個查詢還得記得寫 = 'Y'。boolean 就是專門存是非的型別，只有 true、false（加上 NULL），本身就不會出現第三種值。

因為 boolean 欄位本身就是條件，WHERE 可以直接放它，不用寫 = true。這頁的 products 用 is_available 記錄商品有沒有上架：

還有一個細節：boolean 欄位通常也要加 NOT NULL，不然就有「是、否、不知道」三種狀態，WHERE is_active 和 WHERE NOT is_active 都撈不到 NULL 那幾列。禮物卡的 is_active 改成 boolean NOT NULL，新卡預設可用，再加上 DEFAULT true。

到這裡，草稿只剩最開頭的 id：它不會用完，但開場那張「改網址看到別人的卡」的客服單，就是它造成的。

兌換網址裡的卡號被猜到了：要不要改用 uuid？

自動編號的 id 是 1、2、3 依序往上加。這對資料庫很好，但只要 id 出現在網址或給外部看，就有兩個問題：/gift-cards/1024 讓人猜得到 /gift-cards/1025，而且最新的編號直接透露了你一共賣了幾張卡。

uuid 是 128 位元的隨機識別碼，長得像 4be9d8d9-312b-47ae-8ee7-56e45495d59c。它大到隨機產生的兩個值幾乎不可能撞在一起，所以不需要一個中央的計數器來分配。用 gen_random_uuid() 產生，每次執行結果都不同：

那什麼時候該用 uuid 當主鍵，而不是自動編號？

  • id 會出現在網址或給外部看：禮物卡的兌換網址就是這種，uuid 猜不到，也不透露數量。（猜不到不等於安全，權限還是要檢查，第 24 課。）
  • 資料在資料庫以外的地方產生：例如 App 離線時先建立資料、之後才同步，可以在 App 端先產生 uuid，不怕撞號。

代價是比較大（16 bytes，integer 是 4），也比較難用眼睛辨認：客服電話裡唸一個 uuid 很痛苦。另一個代價跟索引有關。主鍵一定會有索引，索引像書末依值排好的目錄（第 1 課提過，第 20 課細講）。遞增的編號每次都比上一個大，新的一筆永遠加在目錄最後面，資料庫只要一直寫同一個區域；隨機的 uuid 每次都要插進目錄中間不同的位置，資料量大時要讀寫的頁面變多，寫入就比遞增的編號慢（課末的 uuidv7() 依時間遞增，又回到「加在最後面」的情況）。所以一般的內部資料表用 IDENTITY 自動編號就好，只有像禮物卡這種會對外露出的 id 才換成 uuid。

草稿上的每一欄都檢查過了。但禮物卡上線後，PM 很快會要求一個草稿沒有的欄位：卡片狀態，例如未啟用、可用、已用完、作廢。這種「只能是幾個固定值」的欄位，有兩種做法。

卡片狀態只能是幾種值：enum 還是 text 加 CHECK？

關鍵在第三列。業務上的狀態很少一次定好：今天加「退款中」，明年把「已付款」拆成兩種，舊的狀態不再使用。enum 新增容易，但不支援刪除選項，要整個型別重建；CHECK 只是一條規則，改掉重寫就好。

所以選項很穩定、幾乎不會變（例如星期幾）時 enum 很好用；業務狀態常常會調整，多數情況用 text 加 CHECK 比較好維護，禮物卡的狀態也是。如果選項還需要附帶資料（顯示名稱、排序、是否啟用），就做成一張獨立的表，用外鍵參照。

💡 實務上：狀態清單是前後端共用的約定
訂單狀態不只存在資料庫，前端的篩選下拉選單、狀態標籤顏色、後端的流程判斷都會用到同一份清單。新增「退款中」時，順序通常是先放寬資料庫的 CHECK，前端也先能顯示它，最後才讓程式開始寫入新值，不然列表會出現空白或「未知」；要移除選項則反過來，先確認沒有程式和舊資料還在用。資深工程師改狀態前會先搜尋整個專案用到這個值的地方，這類改動怎麼安全上線，第 22 課會再談。

草稿的六欄和新增的狀態欄都有答案了：id 用 uuid、balance 用 numeric(10,2)、is_active 用 boolean、expires_on 用 date、created_at 用 timestamptz、note 用 text、狀態用 text 加 CHECK。練習 4 會請你把修正後的 gift_cards 親手寫出來。

  • char(n)：固定長度的文字，不足會補空白，幾乎用不到，看到時知道是什麼就好。
  • numeric 的速度：numeric 比 integer 慢一些，但對一般應用來說差異可以忽略，正確比較重要。
  • time：「每天 09:00 開店」這種沒有日期的時刻，用的是 time。
  • uuidv7()：PostgreSQL 18 新增了 uuidv7()，產生的 uuid 依時間遞增，可以改善隨機 uuid 寫入索引時位置分散的問題。
  • 轉成整數會四捨五入：3.7::integer 得到 4，不是無條件捨去的 3。

練習 1：會員點數 30 天後到期。算出 2026-10-29 加 30 天是哪一天，結果要是 date 型別（只有日期，沒有時間）。

練習 2：國外的合作夥伴想看 UTC 時間。把連線時區設成 'UTC'，再查出訂單 1 的 id 和 ordered_at。（判分會在結束後自動還原時區，不會影響這頁的其他範例。）

練習 3：price_import 是從 CSV 匯入的商品表，價格欄 price_text 被存成了文字。用型別轉換算出所有價格的總和（整數）。

練習 4：建立禮物卡表 gift_cards，依序有：

  • id：uuid 主鍵，預設用 gen_random_uuid() 產生
  • balance：餘額，精確小數，總共 10 位、小數 2 位，必填
  • is_active：是否可用，必填，預設 true
  • expires_on：到期日（只有日期），可以是 NULL
  • created_at：建立時間（含時區），必填，預設 now()

練習 5：要存商品的美金售價（例如 3.99），哪個型別最適合？

✓ 浮點數是近似值，0.1 + 0.2 都算不準，金額要用精確的 numeric（或以「分」為單位的整數）。存成文字就無法計算，也擋不住 '三塊九'。

練習 6：台北的伺服器寫入一筆 timestamptz 訂單時間 14:30+08。東京的同事（時區 Asia/Tokyo，比台北快一小時）查詢時會看到什麼？

✓ timestamptz 存的是絕對時間點，顯示時依查詢者的時區換算。台北 14:30 和東京 15:30 是同一瞬間。如果是 timestamp（無時區），就會顯示沒有時區的 14:30，造成誤會。

練習 7：訂單狀態未來可能會新增「退款中」、也可能把「已付款」拆成兩種。用哪種方式比較好維護？

✓ enum 要刪除或改名選項很麻煩；CHECK 直接改規則就好。完全不限制則會讓 'Done'、'done '、'完成' 全部混進來。

常見錯誤

  • 金額用 real／double precision：浮點數是近似值，誤差會累積，對帳對不起來。用 numeric 或以元／分為單位的整數。
  • 時間用 timestamp（無時區）：伺服器或使用者換時區時，時間就錯了，而且事後無法判斷原本是哪個時區。事件時間用 timestamptz。
  • 日期存成文字：'2026/10/29'、'10-29-2026' 混在一起，排序和計算都會錯。用 date。
  • 是非存成 'Y'／'N' 或 0／1：擋不住 'y'、2 這種第三種值。用 boolean NOT NULL。
  • 到處寫 varchar(255)：在 PostgreSQL 沒有效能好處，只多了一個沒有根據的上限。
  • 高成長的表用 integer 當 id：用完 21 億之後，新增會全部失敗。
  • 以為 3.7::integer 會無條件捨去：它會四捨五入成 4。

小結

  • 型別決定一欄能存什麼、怎麼算、怎麼比較，選對了很多錯誤寫不進來。:: 把值轉成某個型別，轉不過去就報錯。
  • text 和 varchar(n) 在 PostgreSQL 效能一樣，沒有明確的業務上限就用 text。
  • integer 超過約 21 億就報錯，會大量成長的表 id 用 bigint。金額用 numeric 或整數，不要用浮點數。
  • 事件時間用 timestamptz：存的是絕對時間點，依連線時區顯示。date 存日期、interval 存時間長度；查一整天用「大於等於當天 0 點、小於隔天 0 點」。
  • boolean NOT NULL 存是非、uuid 當對外的識別碼；固定選項多半用 text 加 CHECK。
