階段 11：資深必備｜資料建模與期末專題 · 第 39 課

資深期末專題：上線前審查與事故演練

咖啡店的線上點餐上線三個月了，三家分店共用同一個資料庫，就是第 38 課的台北、台中、高雄三家店，這一課用店名稱呼它們：信義店（台北）、公益店（台中）、美術館店（高雄）。這週你收到五則回報：週五晚上點餐頁變慢、資料庫的磁碟一直長、集點偶爾被重複兌換、咖啡師的平板偶爾卡住不動，還有老闆要在營業時間加上「取餐碼」。你是負責這個系統的資深工程師，週末前要交出兩樣東西：五件事都處理好，以及一份往後每次上線前都能照著檢查、讓同樣的事不再發生的清單。

這一課就是這一週。前面 12 課的工具會全部用上，但重點不在背指令，而在處理的順序：每一件事都先量測、找出根本原因、只改一個地方、再量一次證明有效，最後補上告警或測試。每處理完一件，清單上就多一列該例行檢查的事；最後把它們收成一份上線前審查的清單，再替其中最嚴重的那次事故寫一份事後檢討。

這課的路線：
  1. 五則回報從哪裡下手：所有事故共用的處理順序，以及「根本原因」到底要找到多深。
  2. 步驟一、二（點餐頁變慢）：先找出最貴的那句查詢並記下基準，再設計索引，用同一把尺證明有效。
  3. 步驟三（磁碟一直長）：空間為什麼回收不了、是誰擋住清理，以及查清楚之前不能做什麼。
  4. 步驟四、五（重複兌換、平板卡住）：兩個並發問題，一個讓資料錯、一個讓人等，都改成讓資料庫一句完成判斷與修改。
  5. 步驟六、七與收尾：營業中改 schema 不停擺、資料保留與還原能力，最後收成上線前審查清單與事後檢討。
這課會用到：第 27～38 課的工具。不用先複習：每個步驟用到前面哪一課，會在那一步連回去，並用一句話回顧要用的觀念；第一節的表也列了每則回報對應的課。
這頁的環境：PGlite 0.5.13（PostgreSQL 18.6），只有一條連線、沒有 autovacuum，lock_timeout 這類逾時設定不會觸發。「另一位同事」「另一台平板」是暫停在 PREPARE TRANSACTION 的交易，去等它的鎖時，引擎約 5 秒後中止並顯示在等鎖。VACUUM、COMMIT PREPARED／ROLLBACK PREPARED、… CONCURRENTLY 要單獨一格執行。

這頁的資料：stores（3 家分店）、customers（2,000 位，前 6 位是王小明、陳美華、林志豪、張雅婷、李建國、黃淑芬）、products（6 項商品）、orders（30,000 筆，三家店輪流，pending 約 1%）、stamp_cards（集點卡，CHECK (stamps >= 0)）、tickets（咖啡師的製作單佇列）、order_events（訂單事件，依月分區）。頁面啟動時已經模擬了一段「App 送來的查詢」，也刪過一批舊的製作單。

五則回報，該從哪一件、用什麼順序處理？

五則回報看起來互不相關：一則是效能、一則是空間、兩則是並發、一則是新需求。直覺的做法是哪一則最吵就先修哪一則，想到什麼就試什麼。這樣修完，你說不出到底是哪個修改有效，也不知道下個月會不會再來。資深工程師處理每一件事，都走同一個順序：

每一格都有它存在的理由。量測放在最前面，因為「變慢」「一直長」是使用者的感受，沒辦法直接拿來改；先用數字描述它，例如「這句查詢每次讀 250 頁」，這個數字就是基準，修完拿來比。只改一處是為了讓因果清楚：一次只動一個地方，數字變好就是它的功勞，變差就撤回它。再量測要用跟基準一樣的方法，不然比較沒有意義。最後的防止再發生最常被省略，但它決定了同樣的事下次是在第一天就被告警抓到，還是又拖到客訴才發現。

流程中間的根本原因（root cause）最容易做錯。它是讓問題發生的最底層原因，不是表面的症狀。拿磁碟那則回報來說，可以一路往下問「為什麼」：

  • 磁碟為什麼一直長？因為表越來越大。這是比較近的原因，但還不是底。
  • 表為什麼越來越大？因為刪掉的舊資料一直清不掉。
  • 為什麼清不掉？因為有個交易停了兩週沒人收尾，而且沒有任何告警發現它。這才是根本原因。

只處理症狀，例如把磁碟加大，問題下個月會再來；只處理近因，例如手動清一次，擋住清理的交易還在，清了也沒用。往下問到「改了這裡，同樣的事就不會再發生」為止，才算找到根本原因。

如果點餐頁已經完全打不開，第一步是讓服務恢復：撤回剛上線的版本、取消那句跑不完的查詢，這些止血動作不需要先找到根本原因。服務穩住之後，再照上面的流程慢慢量測、修正。處理時指定一個人負責對外更新，定時告訴 PM 和客服「影響哪些店、正在做什麼、下次什麼時候更新」，其他人才能專心排查。你執行的每一句指令和時間都隨手記下來，事後檢討的時間軸就是從這裡來的。

步驟一：點餐頁變慢，資料庫的力氣花在哪一句？

照這個順序，從第一則回報開始。「週五晚上點餐頁變慢」是症狀，不能直接拿來改：點餐頁背後有好幾句查詢，你不知道是哪一句慢，也不知道是查詢本身慢，還是執行次數太多把資料庫拖垮。所以第一步是量測，看資料庫實際把力氣花在哪裡。

工具是第 29 課的 pg_stat_statements。它是 PostgreSQL 的擴充套件，會記下執行過的每一句查詢，並把「形狀相同、只有常數不同」的查詢合成同一種：WHERE store_id = 1 和 WHERE store_id = 2 會合成 WHERE store_id = $1。合併之後，它替每一種查詢累計執行了幾次、總共花多少時間、讀了多少資料頁。

合在一起看是關鍵。一句每次只要 5 毫秒的查詢，如果一分鐘執行一萬次，它對資料庫的負擔比一句每天跑一次、每次 2 秒的報表還大。只盯著「單次最慢」的查詢，會找錯對象。

排序要用哪個欄位？正式環境通常看 total_exec_time（總執行時間）。這個練習區的執行時間每次都不一樣，所以照第 29 課的做法，改用讀取的資料頁數排序：同一份資料、同一個計畫，讀的頁數每次都一樣，你看到的結果才會跟課文對得上。WHERE 那一行只是排除引擎自己送出的統計同步指令，跟咖啡店無關。執行後看第一名和它的 blocks_per_call：

  • query：第一名是咖啡師畫面的「待製作訂單」，WHERE store_id = $1 AND status = $2 ORDER BY ordered_at LIMIT $3。常數換成了 $1、$2、$3，原本的 status 是 'pending'、LIMIT 是 20。
  • blocks_per_call：它每次讀約 250 頁，其他查詢每次只讀個位數。

單次 250 頁本身不算誇張，問題在次數：咖啡師的平板每幾秒就重新整理一次，週五晚上三家店一起忙，這句的總量就壓過其他所有查詢。要修的就是它。

知道是哪一句之後，下一個問題是它為什麼要讀這麼多頁。這要看執行計畫：第 21 課的 EXPLAIN ANALYZE 會真的執行查詢，列出資料庫實際走了哪些步驟（每一步叫一個節點）、每一步處理了幾列。PostgreSQL 18 的 EXPLAIN ANALYZE 預設就會列出 Buffers，也就是讀了幾頁。執行後由上往下看每個節點：

  • Limit 下的 Buffers: shared hit=250：讀的頁數。
  • Sort：符合條件的列要先排序，才能取前 20 列。
  • Seq Scan：掃了整張 orders，Rows Removed by Filter: 29900 表示 30,000 列只留下 100 列。

三個節點連起來讀，就是原因：資料庫沒有任何捷徑可以直接找到「店 2 的 pending 訂單」，只能把 30,000 列整張掃過一遍、丟掉 29,900 列，再把剩下的排序後取前 20 列。訂單只會越來越多，這句只會越來越慢。

這就是要修的基準：250 頁、有 Sort。先記下來，下一步改完才有東西可以比。

步驟二：怎麼讓這句不必掃整張表，並證明真的有效？

步驟一找到的原因是沒有捷徑，只好整張掃再排序。捷徑就是索引。照第 27 課設計複合索引的順序想：等號條件的欄位放前面（store_id），排序的欄位接在後面（ordered_at）。這樣索引裡同一家店的訂單已經依時間排好，資料庫從店 2 的開頭往下讀就好，不用再排序。

先試這個最直覺的版本，看它的效果，也看它的代價。範例包在 BEGIN … ROLLBACK 裡，執行完就撤回，不會留下索引。執行後先看計畫，再看最後的 index_size：

  • Buffers：讀取的頁數（hit 加 read）從 250 降到 60 左右。
  • Sort 不見了：Limit 下面直接是 Index Scan。
  • Filter: (status = 'pending') 還在：它沿著店 2 的索引一筆一筆往下讀，遇到不是 pending 的就丟掉，Rows Removed by Filter 約 1,900，為了 20 筆 pending 讀了將近兩千筆。pending 越少、越晚出現，要丟的就越多。
  • index_size：大約 936 kB，裡面 99% 是咖啡師永遠不會查的已完成訂單，每一次寫入訂單都要維護它。

這個版本解決了排序，卻留下兩個問題，而且根源相同：索引收了所有訂單，這句查詢卻永遠只要 pending 的。因為什麼狀態都收，資料庫只能邊讀邊丟；也因為什麼狀態都收，索引大到 936 kB，每寫一筆訂單都要多維護一次。第 27 課有一種索引只收「符合條件的列」，用在這裡剛好：pending 只佔 1%，索引會小得多，讀到的每一筆也都是要的。練習 1 讓你設計它。

改完之後怎麼證明有效？要用跟基準同一把尺：同一句查詢、同樣的參數，比 Buffers 和計畫的形狀，不比單次的執行時間。時間會受快取和機器忙不忙影響，同一句跑兩次就可能差很多；讀取頁數和計畫形狀不會。

到了正式環境還有兩件事。第一，建索引本身會擋住寫入：一般的 CREATE INDEX 建立期間，新訂單寫不進去。要改用 CREATE INDEX CONCURRENTLY，它花得比較久，但不擋寫入（第 34 課）。第二，上線後過一段時間再看 pg_stat_statements，確認這句的總量真的下降，也沒有別的查詢因為多了一個索引而變慢。它的累計值可以清空重算，清空之前先把舊的數字存下來，不然就沒有東西可以比。PostgreSQL 18 的計畫還多了一個跟索引有關的數字，見課末。

點餐頁修好了，清單上也多了效能那一列：主要查詢都有適合的索引，而且有量過。下一則回報換成空間。

步驟三：磁碟一直長，是誰擋住了清理？

第二則回報是資料庫的磁碟用量一直長。先回顧第 30 課的一件事：PostgreSQL 改或刪一列時，不會當場把舊資料抹掉，而是留下舊版本，讓還在讀它的交易繼續看得到。等到沒有任何交易還需要它，這個舊版本就成了死版本：沒人看得到，卻還佔著位置。死版本要等 VACUUM 清掉，空間才能給新資料重用；清不掉，表就只會長大。

所以照同樣的順序先量：哪張表的死版本比例最高？系統視圖 pg_stat_user_tables 每張表一列，記錄活版本和死版本的大約數量。執行後看 dead_ratio：

tickets 有一半是死版本。這不難解釋：每天打烊後，系統會刪掉已完成的製作單，而刪除只是把它們標成死版本。正式環境由 autovacuum 在背景自動清理；這頁沒有 autovacuum，所以手動執行 VACUUM，加上 VERBOSE 讓它報告清了多少、有多少清不掉。執行後看 dead but not yet removable 那一段：

這頁的結果是 dead but not yet removable 為 0，因為沒有人擋著。正式環境的 VERBOSE 輸出卻是「1490 are dead but not yet removable」，而且天天如此。這行字的意思是：這些版本已經死了，但現在還不能清。第 30 課說過原因：VACUUM 只能清掉所有進行中的交易都不需要的版本，而最老的那個還沒結束的交易決定了這條界線，它開始之後產生的死版本一律要留著等它。這條界線是整個資料庫共用的，所以一個停住的交易，會讓每一張表的死版本都清不掉。

這就是根本原因要往下找的方向：autovacuum 有在跑，只是被擋住了，要找的是誰把清理界線卡住了。擋住清理界線的東西通常有三種，依常見程度排列：

  • 一般連線開了交易沒結束：例如程式 BEGIN 之後出錯沒收尾，連線停在 idle in transaction。
  • prepared transaction：執行過 PREPARE TRANSACTION、停在「已準備、未提交」的交易。它用在兩階段提交：先讓每個參與的系統都準備好，再一起提交（第 30 課）。它不屬於任何連線，連線斷了、伺服器重啟了都還在，直到有人用 COMMIT PREPARED 或 ROLLBACK PREPARED 收尾。程式要是在準備之後、收尾之前當掉，它就一直停在那裡。
  • 沒人在用的複寫槽（第 37 課）：它不是交易，但效果一樣。複寫槽會記下它的 replica 還需要的最老交易（pg_replication_slots 的 xmin／catalog_xmin），VACUUM 不能清掉比它新的死版本；槽同時保留 WAL，所以磁碟會從兩個方向一起長。replica 不見了，槽卻還在，兩種保留就一直不放。

事故中不要做的事：
  • 直接 VACUUM FULL：它要 ACCESS EXCLUSIVE 鎖，會去排隊等那個交易，後面所有讀寫跟著排在它後面，整張表停擺；就算拿到鎖，擋住清理的交易還在，死版本照樣清不掉。
  • 還沒查清楚就 pg_terminate_backend()：結束連線會讓它的交易回滾，可能是一筆正在處理的付款；而 prepared transaction 根本沒有連線，結束任何連線都沒用。
  • 不看內容就 COMMIT PREPARED：把錯的資料寫進去。

收尾之後，下一輪 autovacuum 就能把死版本清掉。表的檔案不會因此變小，但清出來的空間可以重用，磁碟就不再長。這只是止住症狀，還差流程的最後一格：補上告警，讓同樣的事在第一天就被發現。要監控的是原因，不是結果：最老的交易年齡、prepared transaction 的數量與年齡、死版本的成長（第 36 課的健康檢查）。磁碟用量的告警也要有，但它要等膨脹累積到很大才會響。

設定上也可以先擋住。沒有使用兩階段提交的系統，max_prepared_transactions 應該維持預設的 0，這樣根本建不出 prepared transaction。一般連線的閒置交易則可以設逾時上限，細節見課末。

前兩則回報是效能和空間，清單多了告警那一列。接下來兩則換成並發：同時有兩個請求進來時才會出事。

步驟四：集點被重複兌換，沒有錯誤訊息，資料怎麼會錯？

第三則回報是正確性問題：資料錯了，卻沒有任何錯誤訊息，也沒有任何查詢變慢。這種問題用 pg_stat_statements 找不到，量測的方式是重現它：把兩個請求的每一步攤開，看資料庫裡的值怎麼變。

兌換一杯飲料要 10 點。目前的程式是先讀、在程式裡判斷、再寫回：

const { stamps } = await db.query('SELECT stamps FROM stamp_cards WHERE customer_id = $1', [id])
if (stamps >= 10) {
  await db.query('UPDATE stamp_cards SET stamps = $1 WHERE customer_id = $2', [stamps - 10, id])
  // 出一杯免費飲料
}

林志豪有 12 點，在 App 上連按了兩次「兌換」。兩個請求幾乎同時抵達，各自走上面這段程式：

步驟請求 A請求 B資料庫的 stamps
1SELECT stamps …
讀到 12		12
2SELECT stamps …
讀到 12		12
3UPDATE … SET stamps = 22
4UPDATE … SET stamps = 22
5結果：兌換 2 杯2（應該只能換 1 杯）

根本原因在程式的形狀：「判斷夠不夠」發生在程式裡，「扣點」發生在資料庫裡，兩者之間有一段空檔。另一個請求只要在這段空檔讀到同一個舊值，就會做出同樣的判斷，寫回同樣的結果。這叫讀後寫競態（lost update，第 19、31 課）：每一句 SQL 單獨看都對，合起來卻錯。CHECK (stamps >= 0) 也擋不住，因為寫進去的 2 本身是合法的值。

修法是消掉這段空檔：把「判斷」和「扣點」合成資料庫裡的一句，條件寫進 WHERE，讓 UPDATE 自己決定扣不扣。一句為什麼就安全？第 31 課講過，UPDATE 會鎖住它要改的那一列。第二個請求的 UPDATE 碰到同一列時要等第一個提交，等到之後，它會拿最新的值重新檢查 WHERE：此時只剩 2 點，條件不成立，這一列就不改。程式不再自己判斷，只看這句影響了幾列：1 列就出飲料，0 列就回「點數不夠」。

用黃淑芬來試，她有 15 點，夠換一杯，不夠換兩杯。為了看清楚每次扣點前後的值，這裡用 PostgreSQL 18 的 RETURNING 寫法：同一句可以同時回傳改之前（old）和改之後（new）的值。同一格執行兩次，看 before 和 after：

第一次從 15 變 5；第二次 0 列，因為 5 點不符合條件。連按兩次只換到一杯。

集點功能裡還有一個同樣形狀的 bug：新顧客第一次集點時，程式先查「有沒有卡」，沒有才 INSERT。兩個請求同時進來，兩邊都查到「沒有」，都去 INSERT，後到的那個撞上主鍵，得到 23505（違反唯一約束），App 就顯示錯誤。修法一樣是合成一句：第 31 課的 UPSERT，也就是 INSERT … ON CONFLICT，沒有這一列就新增，撞到唯一約束就改成更新。顧客 7 還沒有卡，執行兩次，看 before 從 NULL 變成 1：

💡 實務上：看到「先查再改」就問「同時兩個請求會怎樣」
集點只是其中一種，庫存、優惠券剩餘張數、帳戶餘額、座位或預約時段都是同一個形狀：先 SELECT、在程式裡判斷、再 UPDATE。前端把按鈕停用不算修好，網路重送、使用者開兩個裝置、App 自動重試都會讓請求重複進來。資深工程師在 code review 看到這種寫法，會直接問「兩個請求同時進來，結果還對嗎？」，並要求把條件寫進同一句 SQL 或用唯一約束擋住。這類 bug 在本機手動點幾下幾乎測不出來，常常要等客服收到「點數不對」的客訴才被發現。

步驟五：咖啡師平板卡住，沒有重複，為什麼還要排隊？

第四則回報也是兩個請求同時進來，但這次資料沒錯，症狀是等待。每家店有兩台平板，各自從 tickets 取下一批製作單來做。程式是：

BEGIN;
SELECT id FROM tickets
WHERE store_id = $1 AND status = 'queued'
ORDER BY id LIMIT 3
FOR UPDATE;               -- 鎖住，免得兩台平板做同一杯
UPDATE tickets SET status = 'making' WHERE id = ANY($2);
COMMIT;

這段程式其實考慮過並發。FOR UPDATE 是第 19 課教過的鎖：讀的同時鎖住選到的列，直到交易結束，別的交易想鎖同一列就得等。有了它，兩台平板不會拿到同一張單，步驟四那種重複不會發生。

問題出在「等」。兩台平板要的是同一批列：都想拿這家店最前面的三張單。平板 A 先鎖住它們，平板 B 的查詢也選到同樣的三張，只能停下來等 A 提交。平常 A 的交易很短，B 等一下就過去了；但只要 A 的平板在交易中途斷線，A 的鎖就一直不放，B 就一直卡著，這正是咖啡師回報的「偶爾卡住不動」。正式環境連線很多，等鎖的請求會一路排隊直到逾時。

先量測確認是鎖。用第 32 課查鎖的方法：pg_stat_activity 裡 B 的 wait_event_type 是 Lock，代表它在等鎖；pg_blocking_pids(B 的 pid) 回傳擋住它的連線，也就是 A 的 pid。這頁只有一條連線，沒有人會擋自己，所以執行後 blocked_by 永遠是空陣列，這格只是讓你看過寫法：

確認是鎖之後，修法要從需求想。製作單是佇列，「哪一台做哪一張」不重要，重要的是兩件事：不重複、不等待。FOR UPDATE 做到了第一件，卻犧牲了第二件。第 33 課的答案是加上 SKIP LOCKED：碰到別人鎖住的列就跳過，改拿下一張沒被鎖的，B 就不必等 A。再把查詢和更新合成一句 UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING id，也順便消掉了原本「查完、更新前」的空檔，跟步驟四是同一個道理。

子查詢有兩個條件不能少。store_id 每一句都要帶：三家店共用一張 tickets，這就是第 38 課的多租戶，漏了它，信義店的平板就會拿到公益店的單。ORDER BY 也一定要有：沒有它，資料庫照實體儲存的順序回傳，先點的人不一定先拿到。練習 4 讓你寫出來。

兩則並發問題的修法是同一個方向：讓資料庫一句完成判斷與修改。清單上多了正確性與並發兩列。最後一則回報不是 bug，是新需求。

步驟六：營業中加取餐碼，怎麼改 schema 而不讓點餐停擺？

老闆要每筆訂單都有取餐碼 pickup_code，以後不能是空的，也不能重複。難的不是語法，而是時間：店不打烊，改 schema 的時候還有人在點餐。第 34 課講過，很多 ALTER TABLE 要拿 ACCESS EXCLUSIVE 鎖，這是最強的鎖，拿著它的期間連讀都不行。這個鎖拿多久，點餐就停擺多久。

先看三種直覺寫法為什麼都不行：

  • 直接 ADD COLUMN pickup_code text NOT NULL：會失敗。舊訂單沒有取餐碼，新欄位在它們身上都是 NULL，一加上 NOT NULL 就違反。
  • 加上固定的 DEFAULT：可以成功，但所有舊訂單共用同一個碼，之後要建唯一索引時就失敗。
  • 改用 gen_random_uuid() 這種每列不同的預設值：每一列都要算出新值寫進去，等於重寫整張表，期間 ACCESS EXCLUSIVE 鎖擋住所有讀寫。

三者的共同問題是想一步做完。第 34 課的做法是拆成幾個小步驟。先說一個會用到的詞：系統目錄（system catalog）是 PostgreSQL 記錄「有哪些表、每張表有哪些欄位」的內部表。只改目錄就像改欄位清單，不用碰到 30,000 筆訂單本身，所以一瞬間就好。拆開之後，每一步要嘛只改系統目錄，要嘛拿的是不擋讀寫的鎖：

步驟做什麼鎖與代價
1ADD COLUMN pickup_code text（可以是 NULL、沒有預設值）ACCESS EXCLUSIVE，但只改目錄、不重寫，一瞬間；記得配 lock_timeout 與重試
2部署新版程式：新訂單一律寫入取餐碼沒有鎖；這一步一定在下一步之前
3ADD CONSTRAINT … NOT NULL pickup_code NOT VALID（PostgreSQL 18）不掃描舊資料；之後的新資料一定要有取餐碼
4分批回填舊訂單每批一個短交易，批與批之間讓 autovacuum 跟上
5VALIDATE CONSTRAINTSHARE UPDATE EXCLUSIVE：要掃表，但讀寫照常
6CREATE UNIQUE INDEX CONCURRENTLY不擋寫入；失敗會留下 INVALID 索引，要檢查

第 1 步雖然一瞬間就做完，但它要先拿到 ACCESS EXCLUSIVE 鎖。只要有一個還沒結束的交易碰過 orders，它就得排隊；它一排隊，後面所有點餐的讀寫也跟著排在它後面。lock_timeout 讓它等太久就放棄、讓出位置，稍後再重試（第 34 課）。

第 2 步和第 3 步的順序最容易做反。NOT VALID 的意思是加約束時不檢查已經存在的列，但之後每一筆新寫入都照樣檢查。如果先加約束、後部署程式，這段期間舊版程式寫入的新訂單沒有取餐碼，會全部被 23502（違反 NOT NULL）擋下，等於讓點餐停擺。所以一定是先讓程式寫新欄位，再加約束。

第 4 步分批回填。為什麼要分批？一句 UPDATE 改 30,000 列，就是一個很長的交易：改到的列一直鎖到它結束，而它執行的這段時間，就像步驟三那個沒收尾的交易，擋著整個資料庫的清理。分成好幾個短交易，每批結束就放掉鎖。這裡依 id 的範圍切成兩批，每批是自己的一個短交易，兩格都要執行。正式環境每批更小（例如 1,000～5,000 筆），由程式迴圈一批一批跑，中間稍微停一下，讓 autovacuum 和複寫跟得上：

步驟七：沒人回報的風險，舊資料怎麼清、出事時救得回來嗎？

審查不能只看有人抱怨的地方。還有兩件事沒人回報，卻遲早會出事：資料只進不出，以及資料庫真的壞掉時，資料能不能還原。

先看資料只進不出。order_events 記錄每筆訂單的每個事件，老闆決定只保留 3 個月。它是第 35 課的分區表：依 created_at 把資料切成每個月一張子表（每一張叫一個分區），查詢時看起來還是一張表。執行後看每個分區的 bound（範圍）與 rows：

範圍顯示成 +08，是因為這個連線的時區是台北。分區的界線是一個時間點，不同時區的人看到的字不同，指的是同一刻。

依月分區的好處，要到每個月維護時才看得出來。維護有兩個動作。第一個是移除到期的分區：用 DROP TABLE 分區名稱 整塊移除，不要用 DELETE。差別在底層發生的事。DELETE 要逐列把資料標成死版本，等於自己再製造一次步驟三的膨脹，之後還要 VACUUM，表的檔案也不會變小。它還會寫出大量 WAL。WAL 是第 18 課提過的預寫日誌：每個修改都先寫進這份日誌，備份和複寫都要處理它，所以 WAL 暴增會連帶拖累備份和 replica。DROP 則是直接刪掉那個分區的檔案。

第二個動作是提前建好下個月的分區。沒有對應的分區時，新資料會落進 DEFAULT 分區。DEFAULT 分區裡一旦有了 12 月的資料，之後要建 12 月的分區時，PostgreSQL 會因為那些資料而拒絕。練習 6 讓你做這個月的維護；先 DETACH 再處理的寫法見課末。

保留期限處理的是「刪掉不要的」，另一半是「確保要的不會丟」。這要先問老闆兩個數字（第 37 課），因為備份要做到多嚴密、花多少成本，取決於生意能承受多少損失：

  • RPO（Recovery Point Objective）：最多能接受遺失多久的資料。
  • RTO（Recovery Time Objective）：最多能接受停機多久。

拿到數字後，再對照目前的做法能做到多少 RPO：

  • 每天一次 pg_dump：RPO 是 24 小時。
  • 實體備份加上持續的 WAL 封存：可以還原到任一時間點（PITR），RPO 取決於 WAL 多久送出去一次。PostgreSQL 只封存寫滿的 WAL 檔，流量小的時段可能很久才封存一次，所以要設 archive_timeout 強迫定期切換（文件建議一分鐘左右）。
  • replica：不是備份，誤刪的 DELETE 會在幾毫秒內複寫過去。

RTO 沒辦法用算的。還原要花多久，取決於資料量、網路、機器，以及負責的人熟不熟步驟，只有一種方法知道：真的還原一次並計時，把步驟寫成手冊，定期演練。

清單上多了資料生命週期與還原能力兩列：大表有保留期限、未來分區提前建好；RPO／RTO 寫下來，還原演練有計時紀錄。

七個步驟走完，每一步都留下了一項以後該例行檢查的事。最後一節把它們收起來。

怎麼讓這一週的工作，下次不用再做一次？

這一週修好的每件事都有一個共同點：上線前要是有人檢查過，它根本不會發生。把這些檢查寫下來，就是上線前審查（production readiness review）的清單：新功能上線前、或接手一個既有系統時，逐項確認效能、正確性、維運與還原能力都過關。下表是七個步驟用到的檢查，加上這門課其他的內容：

💡 實務上：清單要放進流程裡才會被用到
常見的做法是把跟這次修改有關的幾項放進 PR 範本，例如有 migration 的 PR 一定要回答「拿什麼鎖、會不會重寫表」，不必每個 PR 都跑完整張表。接手一個既有系統時，則是整張跑一遍，把發現的問題依「出事的影響有多大」排優先順序，先處理沒有可用備份這種一出事就無法挽回的項目，再處理沒有告警這種會讓問題拖很久才被發現的項目。清單也要持續更新：每次事後檢討的改善事項，常常就是清單上新的一列。

清單是事前預防；事故已經發生時，要做的是事後學習。處理完一次事故，寫一份事後檢討（postmortem）：整理時間軸、影響、根本原因與改善事項，讓整個團隊知道發生了什麼、系統要怎麼改。它的前提是不怪罪個人（blameless）：人一定會犯錯，要問的是「系統為什麼讓這個錯誤造成事故，又為什麼沒有更早發現」。怪罪個人的檢討只會讓下一次大家隱瞞細節。以步驟三為例：

  10/30 09:40  磁碟用量告警（85%）
  10/30 10:05  VACUUM (VERBOSE) 確認原因；pg_prepared_xacts 找到 pos_sync 交易
  10/30 10:20  確認它寫入的是錯誤價格，ROLLBACK PREPARED；autovacuum 開始回收

影響
  磁碟多用 40%；products 的這幾列被鎖兩週，後台改價格的功能逾時

根本原因
  同步程式用兩階段提交，卻沒有交易管理器在當機後收尾；
  資料庫沒有「prepared transaction 年齡」與「最老交易年齡」的告警，
  所以問題在第一天就存在，直到磁碟快滿才被發現。

改善事項（每一項都有負責人與期限）
  1. 新增告警：prepared transaction 存在超過 10 分鐘、最老交易超過 1 小時
  2. 同步程式改成一般交易＋冪等重試，max_prepared_transactions 改回 0
  3. 上線審查清單加入「是否使用 2PC，誰負責收尾」

讀的時候注意三個地方。時間軸來自處理當下隨手記下的指令和時間，就是第一節燈泡區塊說的那份紀錄。根本原因那一段沒有寫「某某忘了處理」，寫的是系統缺了什麼：缺當機後的收尾機制、缺告警。改善事項每一項都對應根本原因裡的一個缺口，第 3 項則直接成了清單上新的一列。設計文件與決策紀錄怎麼寫，見系統設計課第 18 課；告警、值班與事故處理的完整流程，見 DevOps 課第 25 課。

補充與查表

  • 計畫裡的 Index Searches（步驟二）：PostgreSQL 18 的計畫在索引掃描節點多了 Index Searches，表示這次掃描在索引裡「從頭找」了幾次。1 次代表一路順著讀完；數字很大時，可能是 18 新增的 skip scan 在跳著找，值得看一下索引的欄位順序對不對。
  • 閒置交易的逾時（步驟三）：一般的閒置交易用 idle_in_transaction_session_timeout 與 transaction_timeout（PostgreSQL 17 起）設上限，這兩個管不到 prepared transaction。
  • 先 DETACH 再處理到期分區（步驟七）：要移除的分區可以先 DETACH 成獨立的表，但 DETACH … CONCURRENTLY 在有 DEFAULT 分區時不能用（第 35 課）。

練習

練習 2、4、5 每次都在全新的資料庫裡跑，按「執行」或「檢查答案」要等幾秒。

練習 1：pg_stat_statements 的第一名是 SELECT id, ordered_at FROM orders WHERE store_id = $1 AND status = 'pending' ORDER BY ordered_at LIMIT 20。只建一個索引，讓計畫沒有 Sort、用到的索引第一欄是等號條件的 store_id，而且索引小於 64 kB（提示：pending 只佔 1%）。判分會對三家店（store_id 1、2、3）的版本檢查：新增的索引數、有沒有 Sort、用到的索引第一欄、索引大小。起始程式的 plan_nodes('查詢') 是第 27 課的小工具：把步驟一那種 EXPLAIN 計畫攤平，每個節點一列：節點類型、表、用到的索引、條件。

練習 2：事故重現。VACUUM (VERBOSE) tickets 一直顯示 dead but not yet removable。有一個沒收尾的 prepared transaction，題目不告訴你它叫什麼。先用「執行」調查（每次執行都是重現好的現場）：從 pg_prepared_xacts 查出它的 gid 與 prepared 時間，從 pg_locks（pid IS NULL 的那些）看它鎖住哪張表。已知 POS 同步程式當掉前，把商品價格以「分」為單位寫錯了（放大 100 倍）。確認是它之後，送出處理它的一句指令：放棄這個交易，讓價格維持原樣。

練習 3：兌換一杯飲料要扣 10 點。林志豪（顧客 3）有 12 點、李建國（顧客 5）有 7 點，兩人同時按了兌換。用一句 UPDATE 同時處理兩人：點數夠的扣 10 點並回傳 customer_id 與剩餘的 stamps，不夠的不能被扣，也不能讓整句失敗。判分看兩人最後的點數。

練習 4：信義店（store_id = 1）的平板 A 已經拿走 2 張製作單，停在交易裡（題目已設定好）。寫平板 B 的一句取件：該店最多 3 張 queued 的製作單，依 id 先來先做，跳過被鎖住的，標成 making，回傳 id。判分看每張製作單最後的狀態。沒有跳過鎖的寫法會去等平板 A，按「執行」大約 5 秒後會顯示在等鎖。

練習 5：營業時間替 orders 加上取餐碼（新版程式已經部署，新訂單都會寫入取餐碼）：新增 pickup_code text 欄位，並用 PostgreSQL 18 的寫法加上名為 orders_pickup_code_not_null 的 NOT NULL 約束，讓新訂單一定要有取餐碼，但不掃描、不改寫舊資料（舊訂單的回填之後再分批做）。判分會檢查約束的種類與是否已驗證、試著寫入一筆沒有取餐碼的訂單，並數舊訂單有幾筆還沒有取餐碼。

練習 6：order_events 的保留期限是 3 個月。做這個月的維護：把 2026 年 8 月的分區 order_events_2026_08 整個刪掉，並建立 2026 年 12 月的分區（台北時間 12/1 00:00 到 2027/1/1 00:00，名稱自訂）。判分看 8 月的分區還在不在，以及所有分區的範圍。

練習 7：步驟三的事故（prepared transaction 停了兩週，死版本清不掉）最後是磁碟告警才發現的。下面哪一組告警最早能發現它？

✓ 這個問題第一天就存在：最老的交易年齡開始上升、pg_prepared_xacts 多了一列、死版本只增不減。CPU 和每秒查詢數幾乎不受影響；磁碟告警要等膨脹累積到很大才響，就是這次的情況；慢查詢可能要很久之後才出現，也看不出原因。看 CPU 和磁碟只能發現結果，要發現原因得監控資料庫內部的狀態。

練習 8：預計明年製作單的量會成長 10 倍。同事提議把 tickets 佇列換成 Redis／BullMQ。資深工程師的第一步應該是？

✓ 先用數字確定瓶頸在哪裡。SKIP LOCKED 的佇列在很多系統撐得住大量工作，常見的瓶頸是索引與死版本，調 autovacuum、部分索引往往就夠了。換成 Redis 要多維護一套系統，還會失去「訂單和製作單在同一個交易裡」的保證（第 33 課的 outbox 問題）。UNLOGGED 表當機後會被清空，製作單會不見。

練習 9：老闆說「資料最多只能掉 5 分鐘、出事後 2 小時內要恢復營業」。哪個方案符合？

✓ RPO 5 分鐘需要持續送出變更：WAL 封存加上 archive_timeout，或再加上串流複寫讓資料更快離開主機。RTO 只能用實際演練證明。每天一次 pg_dump 最多會掉 24 小時的資料，大資料庫的還原也可能超過 2 小時。replica 會在幾毫秒內複寫誤刪的 DELETE，不能取代可以回到過去某個時間點的備份。

練習 10：步驟三的事後檢討，「根本原因」該怎麼寫？

✓ 根本原因要指出系統哪裡讓錯誤變成事故、又為什麼沒被早點發現，改善事項才會是告警、設計與流程，而不是「下次小心」。怪罪個人（a）不會讓系統更安全，下次換一個人還會發生。autovacuum 再積極也清不掉被擋住的死版本（b）。磁碟大小（d）是症狀，加大只會延後爆發。

常見錯誤

  • 沒量測就改，改完也沒再量：憑感覺挑查詢、憑感覺說變快了。先記下基準（讀取頁數、計畫形狀），改完用同一把尺比較。
  • 一次改很多東西：同時加索引、調設定、改 SQL，不知道哪一個有效，也不知道哪一個帶來副作用。一次一個。
  • 事故中直接 terminate 或 VACUUM FULL：terminate 可能回滾重要的交易，而且對 prepared transaction 沒用；VACUUM FULL 會排隊等鎖並擋住所有人，擋住清理的交易還在就照樣清不掉。先找出元兇並確認它做了什麼。
  • 索引建得太大：只查 1% 的資料卻替整張表建索引，每次寫入都要維護它。查詢條件固定時用部分索引。
  • 在程式裡算好再寫回：讀和寫之間會被插隊。讓一句 UPDATE … WHERE 條件 同時判斷與修改，看影響的列數。
  • 先加約束、後部署程式：舊版程式寫入的資料全被擋下。先讓程式寫新欄位，再加 NOT VALID 約束。
  • 用 DELETE 處理資料保留：產生大量死版本與 WAL。分區表直接 DROP 到期的分區，並提前建好未來的分區。
  • 修好了卻沒加告警或測試：同樣的問題會再發生，而且一樣要等到很嚴重才被發現。
  • 事後檢討變成怪罪個人：大家開始隱瞞細節，系統的漏洞沒被補上。寫系統缺了什麼。

小結

  • 每個事故都照同一個順序：量測、找根本原因、只改一處、再量測、補上告警或測試。根本原因要往下問到「改了這裡，同樣的事就不會再發生」為止。
  • 效能：pg_stat_statements 找總量最大的查詢，EXPLAIN (ANALYZE) 看原因，部分索引讓索引小又剛好；比較讀取頁數與計畫形狀，不比一次的時間。
  • 膨脹：dead but not yet removable 代表有還沒結束的交易擋著整個資料庫的清理界線；查 pg_stat_activity、pg_prepared_xacts、pg_replication_slots，用 pg_locks 確認它做了什麼再收尾，並監控原因而不只是磁碟。
  • 並發：「先查、在程式裡判斷、再寫回」會被插隊。判斷與修改寫成一句條件式 UPDATE；開卡用 UPSERT；佇列用 FOR UPDATE SKIP LOCKED，並帶上租戶條件與 ORDER BY。
  • migration：ADD COLUMN → 部署程式 → NOT NULL … NOT VALID → 分批回填 → VALIDATE → CREATE UNIQUE INDEX CONCURRENTLY。
  • 資料生命週期：DROP 到期的分區、提前建未來的分區；RPO／RTO 寫下來，用實際還原演練證明。
  • 上線審查清單把這些變成例行檢查；事後檢討寫時間軸、影響、根本原因與改善事項，不怪罪個人。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 11：members 用 deleted_at 做軟刪除，同事建了下面的索引，要讓未刪除的會員手機不重複。結果兩位都沒刪除的會員用同一支手機註冊成功了，為什麼？

CREATE UNIQUE INDEX members_phone_key ON members (phone, deleted_at);

✓ 唯一性比對時 NULL 不等於 NULL，未刪除的列 deleted_at 都是 NULL，所以永遠不算重複。改用部分唯一索引 ON members (phone) WHERE deleted_at IS NULL，只在未刪除的列之間要求不重複。a 錯在唯一索引本身就會擋重複，問題出在 NULL。（第 38 課）

練習 12：訂位系統要保證同一張桌子、同一時段不會賣給兩組客人，而且兩組客人同時按下訂位時也要成立。該選哪個做法？

✓ 排除約束讓資料庫拒絕「同一張桌子而且時段重疊」的兩列，並發時也成立，違反時得到 23P01；半開區間讓 20:00 結束和 20:00 開始剛好接上。a 錯在預設的 READ COMMITTED 下，兩個交易都查到「沒有重疊」，然後一起寫入；包在交易裡也擋不住。b 只擋完全相同的時段。（第 38 課）

練習 13：租戶隔離的測試以 app_user 的身分，分別設定台北店和台中店，各自 ASSERT 看不到另一家的訂單。下面哪一種壞掉的 policy，這個測試會照樣通過？

✓ false 讓誰都看不到任何訂單，「看不到別家」當然成立，測試通過，上線後卻每家店都是空的。要同時 ASSERT「看得到自己的」，再故意改壞 policy 確認測試會失敗。b 錯在設定台中店時會看到台北店的訂單，測兩家店就抓得到寫死。（第 38 課）

練習 14：商品下架改用 deleted_at 軟刪除，order_items.product_id 有外鍵指向 products。後台卻還是能把已下架的商品加進新訂單，為什麼？

✓ 外鍵只確認「有這一列」，不知道 deleted_at 代表什麼。要擋就在寫入的程式或 trigger 檢查，或在子表也記一個狀態。b 錯在 CASCADE 只在真的 DELETE 時觸發，軟刪除是 UPDATE，它也不會動。（第 38 課）

練習 15：營業中替 orders 加取餐碼，同事的順序是：ADD COLUMN → ADD CONSTRAINT … NOT NULL pickup_code NOT VALID → 部署新版程式 → 分批回填。第二步一上線，新訂單全部寫入失敗，為什麼？

✓ NOT VALID 不檢查已經存在的列，但之後每一筆寫入都照樣檢查，舊版程式沒寫取餐碼，全被 23502 擋下。先部署會寫取餐碼的程式，再加約束。a 錯在既有的 NULL 正是 NOT VALID 跳過的，要到 VALIDATE 才檢查。（第 39 課）

練習 16：order_events 依月分區、只保留 3 個月，同事每月跑一次 DELETE … WHERE created_at < 三個月前。表的檔案沒變小，那天的 WAL 也暴增，怎麼改最恰當？

✓ DELETE 要逐列標記死版本、寫大量 WAL，之後還要 VACUUM，表的檔案也不會變小；DROP 分區直接刪掉檔案。下個月的分區要先建好，不然新資料落進 DEFAULT 分區，之後建分區會被拒絕。b 錯在 VACUUM 只讓空間能重複使用，不縮小檔案。（第 39 課）
