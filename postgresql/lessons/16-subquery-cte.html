階段 4：進階查詢 · 第 16 課

子查詢與 CTE

十月第一週結束，店長要開檢討會，交給你一張問題清單：

  1. 定價：哪些商品比全店平均價格貴？
  2. 首購券：哪些會員註冊後從沒下過單？行銷要發首購優惠券給他們。
  3. 回購：有下單的會員，平均每人下了幾張單？
  4. 招牌品：每個分類裡最貴的是哪一樣？
  5. VIP：哪些會員的已付款消費高於會員平均？
  6. 營收圖：10/01～10/07 每天的營收，沒生意的日子要顯示 0，前端才能畫折線圖。

這六題有一個共同點：一句普通的查詢回答不了。以第一題來說，你得先知道「平均是多少」，才能拿每樣商品去跟它比；第五題更要先算每個人花多少、再算這些金額的平均、最後才挑人。這一課學兩種把查詢拆成好幾步的寫法：把一個查詢放進另一個查詢的括號裡，讓它先算出中間結果，這叫子查詢（subquery）；用 WITH 把每一步拉到最前面、各取一個名字，這叫 CTE。我們照清單一題一題做，做完你會知道哪一種問題該用哪一種寫法。

這課會用到：第 4 課的 NULL（跟 NULL 比較的結果是 unknown，WHERE 只留下 true 的列）；第 7 課的聚合與執行順序（WHERE 先一列一列篩，GROUP BY 和聚合函式在它之後）；第 9 課的 JOIN 與 LEFT JOIN（把兩張表的列配對，LEFT JOIN 讓配不到的左表列留下、右表欄位補 NULL）；第 15 課的 COALESCE（遇到 NULL 時換成指定的值）。
這課的路線：
  1. 定價：WHERE price > avg(price) 為什麼會報錯，怎麼用子查詢先算出平均再比（開場問題的最小答案）。
  2. 首購券：子查詢回傳一整份名單時怎麼用，為什麼 NOT IN 會安靜地回傳空名單，改用 NOT EXISTS。
  3. 回購與招牌品：把子查詢的結果當成一張表再聚合；讓子查詢看著外層那一列算（相關子查詢）。
  4. VIP 與營收圖：用 WITH 把三步驟的報表由上往下寫；用 WITH RECURSIVE 產生一張每天都有的日期表。
  5. 收尾：同一題用 JOIN、子查詢、CTE 都寫得出來時，怎麼選。

哪些商品比平均價格貴？為什麼 WHERE 寫不出來

清單第一題。直覺的寫法是把「平均價格」直接寫進條件：

SELECT name, price FROM products WHERE price > avg(price);
-- ERROR: aggregate functions are not allowed in WHERE

資料庫拒絕執行。原因要回到第 7 課的執行順序：WHERE 是一列一列決定「這一列要不要留下」，它在處理美式咖啡這一列的時候，眼前只有美式咖啡這一列，手上並沒有「全部商品的平均」這個數字。聚合函式要等所有列都篩選完、分好組之後才會算，比 WHERE 晚。所以在 WHERE 裡要求平均，等於要它用一個還沒算出來的值。

人工怎麼做這題？工讀生會先拿計算機把所有價格平均一次，記下答案，再回頭一樣一樣比。SQL 也能照這個順序寫：先把「算平均」這件事單獨寫成一個查詢，執行看看：

結果是一列一欄：102.22…。接著把這整個查詢用括號包起來，放到原本寫 avg(price) 的位置：

括號裡的查詢就是子查詢。資料庫先執行它，得到 102.22 這個值，外層的 WHERE 再拿每一列的價格跟這個值比。它跟外層無關，所以只需要算一次。執行後看結果：摩卡、拿鐵、卡布奇諾、抹茶拿鐵、起司蛋糕這五樣高於平均，第一題答完了。

這種寫法有一個前提：子查詢要剛好回傳一個值（一列一欄），因為 >、=、< 這類比較，兩邊都只能是一個值。如果子查詢回傳了好幾列，例如 price = (SELECT price FROM products WHERE category = '咖啡')，咖啡有四樣、四個價格，資料庫不知道要跟哪一個比，就會報錯 more than one row returned by a subquery。反過來，子查詢一列都沒查到時不會報錯，而是得到 NULL；跟 NULL 比較的結果是 unknown，外層就一列都不留。

第二題要的卻不是一個值。「從沒下過單的會員」要拿每位會員去對一份「下過單的人」名單，名單裡有好幾個 customer_id，用 > 這類比較接不起來。下一節處理子查詢回傳一整欄的情況。

首購券要發給誰？拿一份名單來篩選

子查詢回傳一整欄（好幾列、一欄）時，它就是一份名單，外層用 IN 判斷「這一列的值在不在名單裡」。先從反面做起：哪些會員有已付款的訂單？

子查詢先從 orders 撈出所有已付款訂單的 customer_id，得到一份名單（王小明的 1 出現三次、散客那筆是 NULL，重複和 NULL 都沒關係，IN 只問「在不在裡面」）。外層再拿每位顧客的 id 去比對。林志豪唯一一張單被取消了，所以不在結果裡。

直覺的反面寫法：NOT IN，結果是空的

首購券要的是「從沒下過任何訂單」的會員，看起來只要把 IN 改成 NOT IN、拿掉付款條件：

執行後一個人都沒有，也沒有報錯。但黃淑芬和吳俊傑明明沒下過單。問題出在訂單裡那一筆散客：沒有會員的客人結帳時，customer_id 是 NULL，所以子查詢回傳的名單裡有一個 NULL。

把黃淑芬這一列（id 是 6）代進去算。6 NOT IN (1, 2, 1, NULL, …) 的意思是「6 不等於名單裡的每一個值」，展開就是 6 <> 1 AND 6 <> 2 AND … AND 6 <> NULL。前面幾項都是 true，但最後一項是「6 跟一個未知的值不相等嗎」，答案是 unknown（第 4 課的三值邏輯）。一串 AND 裡只要有一個 unknown、又沒有 false，整個條件就是 unknown，WHERE 只留下 true 的列，於是黃淑芬被排除。每一列都會碰到同一個 NULL，所以全部被排除。名單裡只要混進一個 NULL，NOT IN 就永遠不會成立。

改問「有沒有」：EXISTS 與 NOT EXISTS

換一個問法就不會碰到 NULL。與其問「這位會員的 id 在不在名單裡」，不如對每一位會員直接問：「訂單表裡，有沒有至少一筆是他的？」這就是 EXISTS：

這裡有兩件新東西。第一，子查詢裡寫了 c.id，指的是外層正在處理的那位顧客。外層處理王小明時，子查詢找的是 customer_id = 1 的訂單；處理黃淑芬時，找的是 customer_id = 6。為了分清楚哪個欄位屬於外層、哪個屬於內層，兩張表各取一個別名 c 和 o。第二，EXISTS (子查詢) 只看子查詢有沒有查到任何一列，查到一列以上就是 true，一列都沒有就是 false，不會是 unknown。它完全不看子查詢選了哪些欄位，所以慣例上寫 SELECT 1，表示「選什麼都無所謂」。

把 EXISTS 前面加上 NOT，就是首購券要的名單：

黃淑芬和吳俊傑出現了。散客那筆訂單的 customer_id 是 NULL，o.customer_id = c.id 對它永遠不是 true，它只是「不算任何人的訂單」，不會像 NOT IN 那樣污染整個判斷。所以規則很簡單：「不在名單裡」一律寫 NOT EXISTS。第 9 課用 LEFT JOIN … WHERE 右表.主鍵 IS NULL 找過同一份名單，那個寫法也正確，NOT EXISTS 則是把「沒有」直接寫成條件，讀起來更接近需求本身。

💡 實務上：看到 NOT IN (子查詢) 就改成 NOT EXISTS
首購券這類「找出沒有……的人」是行銷和資料清理的日常：沒下單的會員、三個月沒人點的商品、沒有對應付款紀錄的訂單。NOT IN 的坑特別難發現：開發時的測試資料可能剛好沒有 NULL，結果正常；上線後出現一筆散客訂單，名單突然變成空的，也不會報錯，行銷只會發現「這次一張券都沒發出去」。所以資深工程師在 code review 看到 NOT IN (子查詢) 會直接請你改成 NOT EXISTS，不必先去確認那一欄會不會有 NULL。

到這裡，子查詢回傳的不是一個值就是一份名單，都是拿來給 WHERE 判斷用的。第三題「平均每人下幾張單」不一樣：它要先算出「每個人各幾張」這樣一張有好幾列、好幾欄的結果，再對它取平均。下一節把子查詢的結果當成一張表。

會員平均每人下幾張單？把子查詢的結果當成一張表

這題分兩步：先算每位會員下了幾張單，再對這些數字取平均。第一步是熟悉的 GROUP BY，問題在第二步。直接把兩個聚合疊在一起寫 avg(count(*)) 是不行的，資料庫會報錯 aggregate function calls cannot be nested：一層 GROUP BY 只能算一次聚合，它算出「每人幾張」之後就結束了，沒有第二輪可以再取平均。

解法是把第一步整個寫成子查詢、放在 FROM 後面。FROM 原本接的是一張表，現在接的是「一個查詢的結果」，資料庫會把這份結果當成一張臨時的表來查。這種放在 FROM 裡的子查詢叫衍生表（derived table）。習慣上在括號後面用 AS 替它取一個名字，就像替表取別名，外層要指它的欄位時就用這個名字，這裡叫 per_customer：

由內往外讀。內層把散客的訂單排除（散客不是會員，不該算進「每位會員」），再依 customer_id 分組，得到五列：王小明 3、陳美華 2、林志豪 1、張雅婷 2、李建國 1。外層對這五個數字取平均，(3 + 2 + 1 + 2 + 1) ÷ 5 = 1.8。這就是「聚合之後再聚合」的標準做法：每多一層聚合，就多包一層子查詢。

注意這個 1.8 的分母。內層是從 orders 分組出來的，沒下過單的黃淑芬和吳俊傑在 orders 裡一列都沒有，所以不在這五列裡。這正好符合題目「有下單的會員平均幾張」；如果店長要的是「全體會員」的平均，就得讓 0 張的人也出現，那需要從 customers 出發，下一節會看到做法。

到目前為止，每個子查詢都能單獨拿出來執行，跟外層無關。第四題「每個分類最貴的是哪一樣」做不到這點：「最貴」要看這樣商品是哪一類，咖啡要跟咖啡的最高價比，甜點要跟甜點的最高價比，子查詢得知道外層現在處理的是哪一列。

每個分類的招牌品是哪一樣？讓子查詢看著外層那一列算

第 7 課用 GROUP BY category 算得出每個分類的最高價（咖啡 130、茶 120、甜點 120），但查不出那是哪一樣：每組只剩一列聚合結果，name 在一組裡有好幾個，不能放進 SELECT。換個想法：對每一樣商品問「我的價格等不等於我這一類的最高價？」等於就是招牌品。

子查詢裡的 p.category 指向外層那一列，所以每一列算出來的最高價都不一樣。外層看到美式咖啡（咖啡）時，子查詢算的是咖啡類的最高價 130，80 不等於 130，排除；看到摩卡時，130 等於 130，留下；看到可頌（甜點）時，子查詢改算甜點類的最高價 120。p 和 p2 是同一張 products 的兩個別名，一個代表外層正在檢查的商品，一個代表子查詢裡被拿來算最高價的商品。如果同一類有兩樣並列最貴，兩樣都會等於最高價，都會出現。

這種用到外層欄位的子查詢叫相關子查詢（correlated subquery），因為它的結果跟外層那一列相關，觀念上外層每一列都要重算一次。首購券那一節的 EXISTS (… WHERE o.customer_id = c.id) 其實也是相關子查詢，只是當時還沒替它取名字。

相關子查詢也能放在 SELECT 裡，替每一列多算一欄。這就是上一節留下的「全體會員」問題：從 customers 出發，替每位會員數他的訂單：

這次七位會員都在，黃淑芬和吳俊傑是 0。因為外層是 customers，每位會員都會產生一列；子查詢對沒下單的人數到 0 筆，count(*) 回傳 0。放在 SELECT 裡的子查詢跟第一節拿來比較平均價的子查詢一樣，必須剛好回傳一個值（一列一欄）。

「每列重算一次」聽起來很慢，實際上 PostgreSQL 常會自己改成更有效率的做法，細節見課末。目前的問題不是速度，而是可讀性：第五題 VIP 要先算每人消費、再算平均、再挑人，如果全用子查詢寫，括號會一層包一層。下一節換一種寫法。

消費高於平均的 VIP 是誰？用 WITH 把步驟由上往下排

先把第五題拆成步驟：

  1. 算每位會員的已付款總消費（散客不算）。
  2. 算這些總消費的平均。
  3. 挑出總消費高於平均的會員，接上名字。

只用前面學過的子查詢寫（FROM 裡的衍生表，加上回傳一個值的子查詢），第一步要寫兩次（一次拿來挑人，一次拿來算平均），而且得從最內層的括號往外讀：

SELECT c.name, s.total_spent
FROM (SELECT customer_id, sum(total) AS total_spent FROM orders
      WHERE status = 'paid' AND customer_id IS NOT NULL GROUP BY customer_id) AS s
JOIN customers c ON c.id = s.customer_id
WHERE s.total_spent > (
  SELECT avg(total_spent) FROM (
    SELECT customer_id, sum(total) AS total_spent FROM orders
    WHERE status = 'paid' AND customer_id IS NOT NULL GROUP BY customer_id) AS s2);

它能跑，但人讀起來很吃力，改的時候還要記得兩個地方一起改。WITH 解決這兩個問題：把一個步驟拉到整句查詢的最前面，替它取一個名字，後面的查詢就像使用一般的表一樣使用這個名字。這種「有名字、只在這一句查詢裡存在的暫時結果」叫 CTE（Common Table Expression，通用資料表運算式），格式是：

WITH 步驟名 AS (
  SELECT …
)
SELECT … FROM 步驟名 …;

先只做第一步，把每人消費取名叫 spend，接上名字看看：

spend 裡是什麼，跟回購那一節 FROM 裡的衍生表 per_customer 一樣，差別只在位置：它被拉到最前面，有了一個讀得懂的名字。執行後看四位會員：張雅婷 690、陳美華 470、王小明 340、李建國 90。林志豪唯一一張單被取消，不在裡面。

第二步、第三步：多個 CTE 串起來

多個步驟用逗號隔開，寫在同一個 WITH 裡，後面的步驟可以使用前面的步驟。第二步 avg_spend 直接從 spend 算平均，第三步的 SELECT 同時用到 spend 和 avg_spend：

四人的平均是 (690 + 470 + 340 + 90) ÷ 4 = 397.5，高於它的是陳美華和張雅婷，這就是 VIP 名單。最後一行的 (SELECT v FROM avg_spend) 是第一節學的「回傳一個值的子查詢」，CTE 和子查詢可以混著用。

跟前面那段子查詢版本比，邏輯完全一樣，差別在讀法：CTE 由上往下讀就是思考的順序，每一步都有名字，spend 只寫一次。更實用的是，每一步都能單獨檢查：把最後的 SELECT 換成 SELECT * FROM spend，就能看到中間結果對不對。寫複雜報表時，先寫第一個 CTE、確認結果對了，再往下加下一步，錯了也知道是哪一步錯。

💡 實務上：報表 SQL 幾乎都寫成一串 CTE
店長要「每月回購率」、PM 要「新客與舊客的客單價比較」，這類查詢常常有四五個步驟，寫成 CTE 每一步都有名字，同事接手或 code review 時能一步一步看懂。最實用的時刻是「數字對不上」：財務說營收少了一千元，你可以把每個 CTE 單獨拿出來跑，找出是哪一步把散客或取消的訂單漏掉、或多算了。不過 CTE 是為了好讀，不是為了變快；兩三行就能寫完的查詢不必硬拆，真的慢了再用第 21 課的 EXPLAIN 看原因。

清單只剩最後一題：每日營收折線圖。前面每一題的材料都在表裡，只是要分步驟算；這一題缺的卻是表裡根本沒有的資料。

營收圖少了 10/4？產生一張每天都有的日期表

先照第 7 課的做法算每天的已付款營收。ordered_at 是時間戳（到秒），要按「天」分組，得先把它轉成只有年月日的日期，ordered_at::date 就是第 13 課的型別轉換 ::：

執行後看日期那一欄：10/03 之後直接跳到 10/05。10/04 沒有任何訂單，GROUP BY 只會替「存在的列」分組，沒有列就沒有那一組，這一天就從報表上消失了。前端拿這份資料畫折線圖，會從 10/03 直接連線到 10/05，看起來像 10/04 也有生意。

要讓 10/04 出現並顯示 0，思路跟第 9 課的顧客報表一樣：拿一張「每一天都有」的表當左表，LEFT JOIN 每日營收，配不到的日子補 NULL，再用 COALESCE 換成 0。問題是資料庫裡沒有這張日期表，得用查詢產生出來。

先認識 UNION ALL：把兩個查詢的結果上下接起來

產生日期表要用到一個新的運算子。查詢 A UNION ALL 查詢 B 會把兩個查詢的結果上下疊在一起，變成一份結果：A 有 1 列、B 有 1 列，合起來就是 2 列。兩邊的欄位數要一樣、型別要相容。另一個寫法 UNION（不加 ALL）會再把重複的列去掉；這裡每一列都不會重複，用 UNION ALL 省掉去重的工作。

WITH RECURSIVE：用上一輪的結果算下一輪

日期表的規律很單純：從 10/01 開始，每一列是上一列加一天，到 10/07 停。WITH RECURSIVE 讓 CTE 引用自己，正好能表達「用上一列算下一列」：

這個 CTE 由 UNION ALL 分成上下兩半。上半部是起點，只執行一次：date '2026-10-01' 寫出一個日期值，產生第一列 10/01。下半部是遞迴部分，裡面的 FROM days 指的不是整張 days，而是上一輪剛產生的那些列；日期加上整數 1 就是隔天。執行過程是這樣：

  1. 第一輪：起點產生 10/01。
  2. 第二輪：拿上一輪的 10/01，符合 day < 10/07，算出 10/02。
  3. 之後每一輪都拿上一輪那一列加一天……直到拿到 10/07：10/07 < 10/07 不成立，這一輪沒有產生新的列。
  4. 沒有新的列就停止，把每一輪的結果用 UNION ALL 接起來，得到 10/01～10/07 七列。

那個 WHERE 就是停止條件。少了它，每一輪都會產生新的一天，查詢永遠停不下來。

有了日期表，剩下的就是前面說的：再加一個 CTE 算每日營收，日期表 LEFT JOIN 它，COALESCE 把 NULL 換成 0。這就是練習 6，最後一題留給你親手接起來。

💡 實務上：補零的日期表與多層分類
補零可以在 SQL 做，也可以在前端畫圖前做，重點是團隊約定好只在一個地方做，不然很容易一邊補了、一邊又補一次，或兩邊都以為對方會補。產生日期序列在 PostgreSQL 還有更短的寫法，見課末。WITH RECURSIVE 在工作中最常見的用途是樹狀資料：電商的多層商品分類、留言的回覆串、公司組織圖（「列出某位主管底下所有的人」），原理跟日期表一樣，每一輪用上一輪找到的節點去找下一層。要注意資料如果被改壞成互相指向（A 的上層是 B、B 的上層又是 A），查詢會停不下來，所以實務上常會多算一欄「第幾層」，在 WHERE 加上「超過某個層數就停」的條件當保險。

清單上的六題都有寫法了。回頭看會發現，同一題常常有好幾種寫法：首購券用 NOT EXISTS 和第 9 課的 LEFT JOIN 都做得到，VIP 用子查詢和 CTE 都做得到。最後一節整理怎麼選。

同一題 JOIN、子查詢、CTE 都寫得出來，該選哪個？

先看一個最容易選錯的情況。第二節用 EXISTS 找「下過單的顧客」，改用 JOIN 寫看起來也行：

執行後看王小明：他出現了三次，陳美華和張雅婷各兩次。原因在兩者做的事情不同。JOIN 是「把兩張表的列配對起來」，王小明有三張訂單，就配成三列，配到幾次就出現幾次。EXISTS／IN 是「篩選」，對每位顧客只回答是或否，每位顧客最多出現一次。所以判斷的方法是問自己：結果需要另一張表的欄位嗎？需要，就要 JOIN 把欄位帶出來；只是要拿另一張表來篩選，就用 EXISTS／IN，不會有重複的問題。

練習

練習 1：列出價格高於「全部商品平均價格」的商品，兩欄：name、price。

練習 2：下面這段想找出「從來沒下過任何訂單（不論狀態）的顧客」，但結果是空的。改寫成正確的版本，只列出 name。

練習 3：列出「訂單裡曾經出現過起司蛋糕」的顧客名字（不論訂單狀態），只要一欄 name，每個人只出現一次。提示：哪張訂單有起司蛋糕要看 order_items。

練習 4：列出每個分類裡最貴的商品。三欄：category、name、price。

練習 5：用 CTE 找出「已付款總消費」高於「有消費會員的平均」的會員。兩欄：name、總消費金額。只算 status = 'paid' 的訂單，散客（customer_id 是 NULL）不算。

練習 6：做出 10/01～10/07 每天的已付款營收，兩欄：日期、營收，沒有營收的日子顯示 0，依日期排序。起始內容已經幫你產生日期序列了。提示：再加一個 CTE 算每日營收，然後 LEFT JOIN。

練習 7：orders.customer_id 裡有 NULL。SELECT name FROM customers WHERE id NOT IN (SELECT customer_id FROM orders) 為什麼查不到任何人？

✓ x NOT IN (…, NULL) 等於一連串 x <> … 用 AND 接起來，其中 x <> NULL 是 NULL，整個條件就不會是 true。改用 NOT EXISTS。

練習 8：要列出「每張訂單的編號，加上下單顧客的名字」，最適合用哪一種？

✓ IN 和 EXISTS 只能篩選，沒辦法把另一張表的欄位（名字）帶出來。需要欄位就用 JOIN。

常見錯誤

  • 聚合函式寫在 WHERE：WHERE price > avg(price) 會報錯，因為 WHERE 執行時平均還沒算出來。把平均寫成子查詢 (SELECT avg(price) FROM products)。
  • 用 NOT IN 做「沒有」的篩選：子查詢裡只要有一個 NULL，結果就是空的，而且不會報錯。用 NOT EXISTS。
  • 比較運算後面的子查詢回傳多列：price = (SELECT price FROM products WHERE category = '咖啡') 會報錯 more than one row returned by a subquery。要嘛改用 IN，要嘛讓子查詢只回傳一個值（例如用 max）。
  • 用 JOIN 做篩選卻沒注意重複：一對多 JOIN 會讓「一」的那邊重複出現，例如王小明出現三次。只是要篩選時用 EXISTS／IN。
  • FROM 子查詢沒取別名：舊版 PostgreSQL 會報錯，新版雖然允許，但取個名字比較好讀。
  • 相關子查詢的欄位沒寫清楚是哪張表的：WHERE category = category 永遠成立。內外層是同一張表時，一定要用別名區分，例如 p2.category = p.category。
  • WITH RECURSIVE 忘了停止條件：沒有 WHERE day < … 就會無限產生下去。

小結

  • 一句查詢回答不了、要先算出中間結果的問題，就拆成好幾步：子查詢是寫在括號裡、先執行的查詢。
  • 子查詢回傳一個值，接在比較運算後面（高於平均價）；回傳一欄，用 IN 篩選；放在 FROM 裡就是一張衍生表，可以「聚合之後再聚合」。
  • EXISTS 只問「有沒有」；「沒有」的篩選用 NOT EXISTS，別用 NOT IN，名單裡一個 NULL 就會讓它回傳空結果。
  • 相關子查詢會用到外層那一列的值，觀念上每列算一次，用來解「每個分類最貴的是哪一樣」這種要跟自己那一組比的問題。
  • WITH 把步驟拉到前面、取名字，由上往下讀，每一步都能單獨檢查；WITH RECURSIVE 用上一輪的結果算下一輪，可以產生日期序列或走訪樹狀資料。
  • 需要另一張表的欄位用 JOIN，只要篩選用 EXISTS／IN，步驟多就用 CTE。
