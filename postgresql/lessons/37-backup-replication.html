階段 10：資深必備｜上線與維運 · 第 37 課

備份、還原、複寫與高可用

星期五傍晚 18:10，有位同事想清掉二號分店的測試訂單，執行了 DELETE FROM orders WHERE store_id = 2，忘了加日期條件，二號分店整天的 100 筆訂單一起不見了。18:40 店長發現報表不對時，這半小時裡又進來了新訂單、也有一筆退款。同一個月，另一間店的資料庫主機硬碟壞掉，整台開不起來，店裡一整晚不能結帳。這兩件事都需要「把資料拿回來」，但用的工具完全不同。

這課把這兩起事故當成一次事故檢討來做：先把二號分店的訂單救回來，而且不能抹掉 18:10 之後的新訂單和退款；再替咖啡店設計一套方案，讓下一次硬碟壞掉時不用停一整晚。過程中會學到 PostgreSQL 保護資料的底層機制 WAL，以及建在它上面的三種工具：備份、複寫、故障轉移。學完你能從 WAL 裡找出誤刪資料的那個交易、把還原出來的資料補回正式資料庫，並判斷 replica 落後了多少。

這課的路線：
  1. 先問兩個數字：能掉多少資料、能停多久？兩起事故各要用哪一種工具。
  2. 資料怎麼「確定寫下」？WAL 是備份和複寫共用的底層，誤刪的那個交易也記在裡面。
  3. 怎麼回到誤刪前一刻？備份的兩種做法、PITR，以及怎麼把缺的列補回正式資料庫、又不抹掉之後的訂單。
  4. 硬碟壞掉時怎麼不用等還原？串流複寫、replica 落後多少、primary 要不要等它；primary 壞掉時誰來接手。
  5. replica 能不能順便分擔讀取？以及換新主機時，怎麼用邏輯複寫順便升級大版本。
這課會用到：
  • 第 2 課的 GENERATED ALWAYS AS IDENTITY：每新增一列，資料庫自動給下一個號碼，你不用（也不能）自己填。
  • 第 18 課的持久性（ACID 的 D）：COMMIT 成功之後，資料就確定寫下了，當機也不會不見。
  • 第 30 課的 MVCC 與 VACUUM：每次 UPDATE 都寫一個新版本，舊的變成死版本等 VACUUM 清掉；還開著的長交易可能還要讀舊版本，會擋住清理。會寫資料的交易都有一個交易編號（XID）。
  • 第 36 課的監控與告警：用 pg_stat_* 系統視圖看資料庫的狀態，指標超過門檻就通知人。

先問兩個數字：能掉多少資料、能停多久？

事故檢討會上，最常聽到的一句話是「我們不是有備份嗎？」。這句話其實沒有回答任何事：備份是幾點的？還原要多久？還原之後，備份時間點到出事之間的資料去哪了？要把這些問題問清楚，業界用兩個數字描述一套方案「最壞會怎樣」：

  • RPO（Recovery Point Objective，復原點目標）：出事之後，最多能接受遺失多久的資料。RPO 是 24 小時，代表最壞情況下一整天的訂單都沒了。
  • RTO（Recovery Time Objective，復原時間目標）：出事之後，最多能接受停機多久才恢復服務。

套到開場：二號分店的誤刪考驗的是 RPO，能不能回到 18:10 之前、少掉的訂單能不能全部拿回來；硬碟壞掉那間店考驗的是 RTO，店裡要多久不能結帳。這兩個數字由老闆和產品決定（掉一小時的訂單要賠多少錢、停一小時少賺多少），工程師負責挑方案、算成本、證明做得到。

保護資料的工具分兩類，後面各節會一一細講，這裡先知道它們各自做什麼。備份是把某個時間點的資料另外存一份，出事時拿那一份回來。複寫是讓另一台資料庫持續跟著主機改資料，這台叫 replica（複本），主機壞掉時可以換它上場。常見的組合和它們做得到的程度：

方案RPO（掉多少資料）RTO（停多久）救得了誤刪嗎
每天 02:00 跑一次 pg_dump最多 24 小時資料大時好幾小時（要重建索引）可以，但只能回到 02:00
實體備份＋WAL 封存（PITR）幾分鐘以內（看 WAL 多久封存一次）還原備份＋重播 WAL 的時間可以，回到誤刪前一刻
非同步串流複寫＋自動故障轉移主機壞掉時可能掉最後幾筆幾十秒不行
同步複寫＋自動故障轉移主機壞掉時不掉已提交的資料幾十秒不行

表裡的名詞（pg_dump、WAL 封存、PITR、同步與非同步、自動故障轉移）後面都會講，先看最重要的最後一欄：為什麼複寫救不了誤刪？因為 replica 會忠實地照做主機做的每一件事，DELETE 也一樣，幾毫秒後 replica 上的資料也沒了。所以複寫防的是「機器壞掉」，備份防的是「資料被改壞」（誤刪、程式 bug、被入侵），兩者都要有，不能拿一個代替另一個。

這就是兩起事故的最小答案：二號分店的誤刪要靠 PITR 備份回到 18:10 之前；硬碟壞掉的那間店，有複寫加自動故障轉移就能幾十秒內換一台繼續營業，只有備份就要等還原（比較表裡備份兩列和複寫兩列的 RTO）。不管哪一種，備份都要放在別台機器、別的區域：跟資料庫放在同一顆硬碟上的備份，會和資料庫一起消失。

💡 實務上：小團隊先從託管資料庫的自動備份＋PITR 開始
咖啡店剛起步、訂單一天幾百筆時，雲端託管資料庫（例如 AWS RDS）內建的自動備份加 PITR 通常就夠了，不需要一開始就架複寫叢集。資深工程師跟 PM 或老闆談的時候會多問一題：備份要保留多久（帳務、個資相關的法規可能有要求）？談完把 RPO、RTO 和保留期限寫進文件，附上每個方案的每月成本讓對方選。RPO 要求越接近零、RTO 越短，成本和維運複雜度都會跳一級，沒有需求就別花這筆錢。

表裡的備份和複寫看起來是兩回事，底下搬的卻是同一樣東西。要知道備份為什麼能停在「誤刪前一刻」、replica 為什麼會跟著誤刪，得先看 PostgreSQL 怎麼把一筆修改寫下來。

資料怎麼「確定寫下」？WAL：先記帳再改資料

第 18 課說過，COMMIT 成功之後就算馬上停電，資料也不會消失（持久性）。最直接的做法是每次 COMMIT 都把改過的資料頁寫回磁碟，但一個交易改到的列可能散在很多個資料頁，每一頁都要等它寫完，COMMIT 會很慢。

PostgreSQL 的做法是 WAL（Write-Ahead Log，預寫日誌）：修改任何資料頁之前，先把「要怎麼改」寫成一筆紀錄，附加到 WAL 檔的尾端。COMMIT 時只要確定 WAL 寫進磁碟就回應成功；資料頁本身留在記憶體裡（第 36 課的 shared_buffers，PostgreSQL 自己的資料頁快取），晚一點再寫回。就像店員先在帳本上記一筆，貨架晚點再整理：只要帳本在，貨架亂了也能照帳本整理回來。

「晚一點寫回」總要有個時間點。PostgreSQL 會定期做一次 checkpoint（檢查點）：把記憶體裡所有改過的資料頁寫回磁碟。checkpoint 完成後，它之前的 WAL 已經沒有用處，可以回收，WAL 才不會無限長大。當機重新啟動時，PostgreSQL 從最近一次 checkpoint 開始重播 WAL，把還沒寫回的變更補上，這就是當機復原。

WAL 是一條只往後長的紀錄，每個位置都有編號，叫 LSN（Log Sequence Number），寫成 0/1783198 這種十六進位格式，越寫越大。兩個 LSN 相減，就是中間寫了多少位元組的 WAL；後面算 replica 落後多少，用的就是這個減法。實際存放時，WAL 切成一個個檔案（segment，預設 16 MB）。

WAL 記下了每一個修改，而且依時間排好，所以它不只用來當機復原：把寫完的 WAL 檔複製到別處保存，就是封存，備份靠它回到任意時間點；把 WAL 即時傳給另一台、讓它照著重播，就是複寫。上一節表裡的工具，底下都是在「搬 WAL」。

怎麼回到誤刪前一刻？備份與 PITR

回到誤刪前一刻需要兩樣東西：一份起點的資料，和從起點到 18:10 之間的所有變更。先看起點，也就是備份本身。

邏輯備份與實體備份：複製的是什麼？

備份分成兩大類，差別在「複製的是什麼」：

  • 邏輯備份（logical backup）：把資料匯出成 SQL 或資料檔，工具是 pg_dump。內容是 CREATE TABLE、CREATE INDEX，以及用 COPY 匯入的資料。COPY 是大量匯入／匯出資料的指令，比逐筆 INSERT 快很多。
  • 實體備份（physical backup）：直接複製資料目錄裡的檔案（就是磁碟上的資料頁），工具是 pg_basebackup。
# 邏輯備份：自訂格式（-Fc），之後可以用 pg_restore 只還原部分表、平行還原
pg_dump -Fc -d coffee -f coffee.dump
pg_restore -d coffee_new -j 4 coffee.dump
pg_restore -d coffee_new -t orders coffee.dump      # 只還原 orders

# 實體備份：整個 cluster（所有資料庫）＋備份期間的 WAL
pg_basebackup -D /backup/base -Fp -X stream -c fast

上面的 cluster 指的是一個 PostgreSQL 伺服器管理的整組資料庫。兩種備份的差別：

pg_dump（邏輯）pg_basebackup（實體）
一致性在一個快照裡匯出，備份過程中別人照常讀寫，不會被擋（但會擋住 ALTER TABLE 這類要排他鎖的 DDL）複製期間檔案在變，靠備份期間的 WAL 修正成一致
範圍一個資料庫，可以只選某些表整個 cluster，不能只挑一張表
跨大版本可以：輸出可以匯入比 pg_dump 新的版本，大版本升級常用只能還原到同一個大版本
還原速度慢：要重新寫入每一列、重建每個索引、重新驗證約束快：檔案複製回去就能啟動
還原到任意時間點不行，只能回到匯出那一刻可以，搭配 WAL 封存（下一小節）

資料只有幾 GB 時，每天 pg_dump 很合理；到了幾百 GB，pg_restore 可能要好幾個小時，RTO 撐不住，這時主力就要換成實體備份。pg_dump 還有一個代價：整段期間是同一個快照，等於一個很長的交易。第 30 課說過，長交易會擋住 VACUUM 清理死版本，所以大資料庫的 dump 通常在 replica 或低峰時段跑。

套回事故：如果咖啡店只有每天 02:00 的 pg_dump，還原後只會回到 02:00，今天 02:00 到 18:10 的所有訂單也一起沒了，比誤刪本身還糟。要回到 18:10 之前的那一刻，得用表格最後一列：實體備份搭配 WAL 封存。（增量備份、雲端磁碟快照等其他做法，見課末「補充與查表」。）

PITR：基礎備份＋連續的 WAL

PITR（Point-In-Time Recovery，時間點還原）就是把上面兩樣東西接起來：一份實體備份當起點，叫基礎備份，加上從那之後連續不斷的 WAL。還原時先放回基礎備份，再照著 WAL 重播，停在你指定的那一刻。

要做到 PITR，primary 要開啟封存，還原的那台要知道去哪拿 WAL、停在哪裡。正式環境的設定大概是：

# postgresql.conf（primary）
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'   # %p 是 WAL 檔路徑，%f 是檔名

# 還原的那台機器：放回基礎備份後，設定停止點，再建立 recovery.signal 檔案啟動
restore_command = 'cp /archive/%f %p'
recovery_target_xid = '…'             # 或 recovery_target_time、recovery_target_name、recovery_target_lsn（只能選一個）
recovery_target_inclusive = off       # off：停在這個交易「之前」；預設 on 是包含它

套到二號分店：recovery_target_xid 填上一節從 WAL 找到的那個 xid，recovery_target_inclusive = off 讓重播停在它之前，誤刪就不會被重做。

整條 PITR 能不能用，取決於 WAL 有沒有一個不漏地封存下來，而這件事全看 archive_command。每寫完一個 WAL 檔，PostgreSQL 就呼叫一次這個指令，看它的回傳值決定下一步。archive_command 只能在真的成功時回傳 0（官方文件特別強調）：回傳 0，PostgreSQL 就當作已經封存、把原檔回收掉；如果指令其實失敗卻回傳 0，那個 WAL 檔就永遠不見了，PITR 從那裡斷掉，而且要等到真的需要還原時才會發現。

反過來，archive_command 一直失敗（回傳非 0）時，PostgreSQL 會不斷重試，還沒封存的 WAL 不能回收，全部堆在 pg_wal 目錄裡，最後塞滿磁碟。兩種情況都要監控：pg_stat_archiver 的 failed_count、last_failed_time。正式環境通常不自己寫 cp，而是交給專門的工具處理封存（見課末）。

還原到另一台，再把缺的列補回來

直覺的做法是把正式資料庫整台倒回 18:10 之前，但這樣會把之後的正常寫入（這頁的訂單 12 退款、新訂單 303）一起抹掉，等於為了救 100 筆訂單又弄丟另外幾筆。實務流程是：在另一台機器還原到誤刪前一刻，把缺的列補回正式資料庫（練習 2）。這頁的 orders_restored 就是那台機器還原出來、再搬過來的副本。

補回時有一個障礙：orders.id 是 GENERATED ALWAYS，第 2 課說過不能自己填值。但補回資料時必須保留原本的訂單編號，收據、付款紀錄都參照它，換了編號就對不上。這時用 OVERRIDING SYSTEM VALUE 明確表示「我知道，就用我給的值」：

INSERT INTO 表 OVERRIDING SYSTEM VALUE
SELECT … FROM 還原出來的表 WHERE …;

自己填的值不會推進 identity 背後的序號。補回的 id 都比序號目前的值小就沒事（這頁是這樣）；如果補回的 id 比序號還大，之後要用 setval() 把序號調上去，否則新訂單會撞到補回來的編號。

💡 實務上：沒演練過的備份不算備份
這次能救回來，前提是基礎備份能用、WAL 一個不缺、有人知道怎麼還原。實際上備份檔可能是壞的、少了 WAL、密碼找不到、還原程序沒人會。定期（例如每季）真的還原一次到另一台機器，量出實際的 RTO，跑幾句查詢確認資料正確。DevOps 課第 24 課會把它做成固定的流程。

二號分店的訂單救回來了。另一間店的問題卻不一樣：硬碟壞掉時，就算 PITR 能把資料還原到幾分鐘前，找機器、放回基礎備份、重播一整天的 WAL 都要時間，這段期間店裡不能結帳。要縮短停機，得在出事之前就準備好另一台資料庫。

硬碟壞掉時，怎麼不用等還原？串流複寫

如果另一台機器平常就一直跟著主機改資料，主機壞掉時它手上已經是最新的資料，不需要還原。這就是串流複寫（streaming replication）：一台 primary（可寫入的主機）把 WAL 即時傳給一台或多台 replica，replica 收到就重播，保持和 primary 幾乎一樣的資料。它用的就是 WAL 一節的機制：當機復原是「重播自己的 WAL」，複寫是「重播別人傳來的 WAL」。

PostgreSQL 的文件和設定名稱把 replica 叫做 standby（例如後面的 synchronous_standby_names），指的是同一種機器，這課統一叫 replica。

replica 落後了多少？

「幾乎一樣」的「幾乎」就是風險：primary 壞掉那一刻 replica 還沒收到的 WAL，就是會掉的資料。所以第一件要會看的事，是 replica 落後多少。primary 上的 pg_stat_replication 每個 replica 一列，用四個 LSN 表示一段 WAL 走到哪一步：

flush_lsnreplica 已經寫進磁碟

primary 要不要等 replica？非同步與同步

預設是非同步：primary 寫進自己的磁碟就回應 COMMIT 成功，不等 replica。好處是 replica 慢不會拖慢寫入；代價是 primary 突然壞掉時，最後幾筆還沒送到 replica 的交易會遺失，就是 RPO 表裡「可能掉最後幾筆」那一格。

如果咖啡店連最後幾筆都不能掉，就用同步複寫（synchronous replication）：在 synchronous_standby_names 指定 replica 之後，COMMIT 要等它們回報才回應。要等到哪一步，由 synchronous_commit 決定，對應上一小節的四個 LSN（PostgreSQL 18 文件）：

synchronous_commitCOMMIT 等到保證
remote_applyreplica 重播完不掉資料，而且 COMMIT 之後馬上在 replica 查得到；延遲最大
on（預設）replica 寫進磁碟primary 和 replica 不會同時掉這筆資料
remote_writereplica 寫進作業系統replica 的 PostgreSQL 當掉不會掉，但作業系統當掉可能掉
local只等自己的磁碟不等 replica
off什麼都不等當機時可能掉最近幾筆（狀態仍一致）

同步的代價有兩個：每次 COMMIT 多一趟網路往返（跨區域就是幾十毫秒）；而且唯一的同步 replica 掛掉時，primary 上的 COMMIT 會一直等下去，寫入全部卡住，等於為了防 primary 壞掉，反而多了一個會讓寫入停擺的點。所以同步複寫通常會配兩台以上的 replica，設定成「任一台回報就好」（ANY 1 (s1, s2)）。

synchronous_commit 也可以只對某些交易設定，例如付款用 on、記錄點擊用 off，只在真的不能掉的資料上付延遲的代價。

不管同步還是非同步，都假設 replica 一直連著。但 replica 也會重開機、網路也會斷，斷線期間的 WAL 要怎麼辦？

replica 斷線再回來，WAL 還在嗎？replication slot

WAL 一節說過，checkpoint 之後舊的 WAL 會被回收。replica 斷線一陣子再回來時，它需要的 WAL 如果已經被 primary 回收，就接不上了，只能整台重建。replication slot 解決這件事：primary 替某個 replica 記住「它收到哪裡了」，在那之後的 WAL 一律保留，等它回來接。

primary 壞了，誰來接手？故障轉移

故障轉移（failover）就是在 primary 壞掉時，把一台 replica 升級（promote）成新的 primary。PostgreSQL 本身只提供「升級」這個動作（pg_promote()），不會自己判斷要不要升級。硬碟壞掉那天如果只有 replica、沒有自動故障轉移，還是要等有人半夜被叫醒、確認狀況、手動升級，RTO 一樣是好幾十分鐘以上。

自動切換要靠外部的管理程式。常見的是 Patroni，它搭配 etcd 這類共識服務：幾台機器用投票決定「現在誰是 primary」，少數幾台斷線也不會選出兩個。不想自己架的團隊，用雲端託管資料庫的 Multi-AZ：在同一區域的另一個機房放一台 replica，壞掉時自動切換（DevOps 課第 18 課）。不管哪一種，都要解決三件事：

  • 判斷 primary 真的掛了：只是網路抖一下就切換，會造成不必要的停機。
  • 避免 split-brain（腦分裂）：舊 primary 其實還活著、只是連不到，結果兩台都以為自己是 primary、各自接受寫入，資料從此分岔，很難合併。管理程式要確保舊的那台被隔離（fencing）、不再接受寫入。
  • 讓應用程式找到新的 primary：做法見下面兩段。

讓應用程式找到新 primary，常見的做法是 DNS 名稱指向新主機，或改由 pooler、負載平衡器轉送。另一種是在連線字串列出多台主機，加上 target_session_attrs=read-write，讓驅動程式依序連線、自動挑可寫入的那台：

postgresql://app@db1:5432,db2:5432/coffee?target_session_attrs=read-write

這個寫法由 libpq 處理。libpq 是 PostgreSQL 官方的 C 函式庫，psql 和 Python 的 psycopg 都建在它上面。第 25 課用的 node-postgres（pg）不支援：它只連一台主機，連線字串裡的 target_session_attrs 會被默默忽略，所以 Node 專案通常靠 DNS 或 pooler 指向新主機。換驅動前先查它的文件。

資料庫換好了，應用程式這邊還有一段：切換的那幾十秒內，正在跑的交易會斷線、新連線會失敗。連線池要能丟掉壞連線、重新連線，交易要像第 31 課那樣整個重試（而且要冪等，避免重複扣款）。沒有重試的 App，資料庫切換成功了，使用者還是會看到一堆 500。

再提醒一次：自動故障轉移把 RTO 縮短到幾十秒，但對誤刪完全無效，新 primary 上的資料一樣是被刪過的，PITR 備份一樣要做。

💡 實務上：大多數團隊不自己架 Patroni
沒有專職 DBA 的團隊，通常直接用雲端託管資料庫的 Multi-AZ，把判斷故障、隔離舊主機、切換 DNS 交給廠商。但上面說的 App 那一側（重連、重試、冪等）廠商不會幫你做。資深工程師會在測試環境實際觸發一次故障轉移（託管服務通常有「重新開機並故障轉移」之類的操作），看 App 斷線多久、錯誤有沒有自己恢復，而不是只看廠商文件寫的秒數。做完把結果和處理步驟寫進值班手冊，下次硬碟壞掉時才不用現場摸索。

到這裡，兩起事故都有了對策。但 replica 平常只是待命等故障，檢討會上一定有人問：既然它的資料幾乎和 primary 一樣，能不能讓它順便分擔查詢？

replica 能不能順便分擔讀取？

可以。replica 開著 hot standby 這個功能時，可以一邊重播 WAL、一邊接受唯讀查詢，報表、搜尋這類只讀的流量就可以分過去，減輕 primary 的負擔。replica 只能讀：INSERT、UPDATE、DDL、SELECT … FOR UPDATE、nextval() 都不行。分過去之前，要先知道兩個坑，它們都來自前面講過的事：replica 會落後，而且它在重播 primary 的 WAL。

剛寫完就讀，卻讀到舊資料

第一個坑來自延遲。把讀取分到 replica 之後，最常見的 bug 是這個：

步驟Appprimaryreplica
1UPDATE orders SET status = 'cancelled' WHERE id = 42status = cancelledstatus = paid
2收到 COMMIT 成功WAL 送出中…還沒重播
3SELECT status … WHERE id = 42（走 replica）回傳 paid
4畫面顯示「已付款」還沒重播
5status = cancelled

修法：寫完要立刻讀的查詢走 primary（例如同一個請求、或使用者剛改過資料的幾秒內一律讀 primary）；只有能接受稍舊資料的查詢（報表、列表、搜尋）才走 replica。把 synchronous_commit 設成 remote_apply 也能讓 replica 馬上查得到，但每次 COMMIT 都要多等，通常不值得。系統設計課第 6 課會把這類一致性問題講完整。

replica 上的長查詢，為什麼會被取消？

第二個坑來自重播。把報表分到 replica 之後，長查詢可能和重播衝突，過程是這樣：

  1. primary 的 VACUUM 清掉了死版本（第 30 課），這個清理也寫進 WAL。
  2. replica 重播這個清理時，replica 上還在讀那些舊版本的查詢就得讓路。
  3. 重播等超過 max_standby_streaming_delay（預設 30 秒），查詢就被取消。

開 hot_standby_feedback 可以讓 replica 告訴 primary「這些舊版本還有人在讀」，查詢就不會被取消。代價是 primary 延後清理、表開始膨脹，等於把第 30 課的「長交易擋住清理」搬到 primary 上。反過來，把 max_standby_streaming_delay 調大，查詢不容易被取消，但重播會被卡住，replica 落後變大，故障轉移時可能掉更多資料。兩個設定都在 replica 上：

# postgresql.conf（replica）
max_standby_streaming_delay = 30s   # 預設：重播最多等查詢 30 秒，之後取消查詢
hot_standby_feedback = off          # on：請 primary 保留還有人在讀的舊版本，代價是 primary 膨脹

所以同一台 replica 很難同時當「隨時能接手的備援」又跑「十幾分鐘的大報表」，常見的做法是兩種用途分開放在不同台。

💡 實務上：先別急著加 read replica
咖啡店後台變慢時，先查是不是少了索引、查詢寫法有問題（第 21 課的 EXPLAIN），這些修好通常就夠了；replica 是 primary 真的忙不過來時才加。加了之後最常分過去的是後台報表、匯出 CSV、資料分析這類「慢一點也沒關係」的讀取，很多 ORM 和框架有讀寫分離的設定，接上前先確認團隊知道哪些查詢會走 replica。上線後在第 36 課的監控加一條「replica 延遲超過幾秒就告警」，不然延遲變大時只會收到「資料怪怪的」客訴。

到這裡的複寫都是整台照抄：串流複寫複製的是整個 cluster 的 WAL，replica 一定是同一個大版本、一模一樣的內容。檢討會的最後一題就卡在這裡：硬碟壞掉那間店要換新主機，資料庫也跑在舊的大版本上，能不能趁換機時順便升級，又不停機？

換新主機時，能不能順便升級大版本？邏輯複寫

串流複寫做不到，因為 WAL 記的是「哪個資料頁的哪幾個位元組改成什麼」，不同大版本的資料頁格式不一定相同。邏輯複寫（logical replication）改用「列的變更」為單位，例如「orders 的 id 42 這一列，status 改成 cancelled」，所以可以只複寫指定的表，對方也可以是不同的大版本。來源叫 publisher，用 PUBLICATION 宣告要送哪些表；目的地叫 subscriber，用 SUBSCRIPTION 訂閱：

-- 來源（publisher）
CREATE PUBLICATION coffee_pub FOR TABLE orders, customers;
-- 目的地（subscriber），表要先自己建好
CREATE SUBSCRIPTION coffee_sub
  CONNECTION 'host=old-db dbname=coffee user=replicator'
  PUBLICATION coffee_pub;

要從 WAL 還原出「哪一列變成什麼」，WAL 得多記一些資訊，所以它需要 wal_level = logical。這頁的 wal_level 是 replica（WAL 一節第一格看過），試著建立邏輯複寫用的 slot 會失敗，執行後看錯誤訊息：

邏輯複寫有兩個限制，升級前一定要處理（PostgreSQL 18 文件）。第一，DDL 不會被複寫：schema 變更要兩邊自己同步，而且先改訂閱端（第 22 課的 schema 變更），否則新欄位的資料送過去會沒地方放。第二，序號（sequence）的值不會被複寫：新主機上 orders 的資料雖然都到了，背後的序號還停在起點，切換前要手動把目的地的序號調到比來源大，不然第一筆新訂單就撞號。

大版本升級有三種方式，停機時間和複雜度依序取捨（PostgreSQL 每個大版本支援 5 年，過了就沒有安全修補，遲早要升；各版本的支援期限見課末）：

方式停機說明
pg_dump → pg_restore長（和資料量成正比）最單純，小資料庫可以
pg_upgrade短（--link 模式幾分鐘內）直接轉換資料目錄；PostgreSQL 18 起的改進見課末
邏輯複寫幾乎零停機新版本當 subscriber 追上之後，切換連線；要處理 DDL 與序號

pg_upgrade 把舊版的資料目錄轉成新版能用的格式，不用像 pg_dump 一樣逐列重新寫入。--link 模式不複製資料檔，而是用硬連結讓新版直接沿用舊檔，所以幾分鐘就能完成；代價是新版啟動之後，舊版的叢集就不能再安全啟動，升級前一定要先有備份。

套回咖啡店：新主機裝新版本、當 subscriber 追上舊主機，確認資料一致、調好序號之後，把連線切過去，停機只有切換那一下。

同一套「把列的變更送出去」的機制還有另一個常見用途，叫 CDC（Change Data Capture，變更資料擷取）：把每一筆資料變更送到別的系統。例如 第 28 課的全文搜尋做不到時，把變更送去更新搜尋引擎；送進資料倉儲（專門做分析報表的資料庫）做報表；或發事件給其他服務，這是 第 33 課 outbox 之外的另一種做法。常見工具是 Debezium。

補充與查表

  • data_checksums：PostgreSQL 18 的 initdb 預設開啟 data checksums，每個資料頁帶一個檢查碼，讀到被磁碟弄壞的頁時會報錯，而不是默默給你錯的資料。舊版升級上來的 cluster 不一定有開。
  • WAL 檔名：24 個十六進位字元。前 8 個是時間線（timeline），每次 PITR 或故障轉移升級之後加一，用來區分「分岔」之後的歷史；後面是檔案編號。
  • 增量備份（PostgreSQL 17 起）：pg_basebackup --incremental=上一次的 backup_manifest 只複製改過的資料頁，還原前用 pg_combinebackup 把完整備份和增量合併成一份。伺服器要開 summarize_wal。
  • 雲端磁碟快照：RDS 等託管服務（雲端廠商替你管理的資料庫）的自動備份就是磁碟快照＋WAL（DevOps 課第 18 課）。
  • 這頁的 PGlite 也有實體備份：它的 dumpDataDir() 把整個資料目錄打包（實測約 4.6 MB），loadDataDir 再載入成新的資料庫。
  • 封存工具：正式環境通常用 pgBackRest、WAL-G 這類工具處理封存、壓縮、上傳到別的區域與保留期限，而不是自己寫 cp。
  • idle_replication_slot_timeout（PostgreSQL 18 新增）：閒置超過這段時間的 slot 在 checkpoint 時自動失效（預設 0 不啟用）。
  • 邏輯複寫與序號：PostgreSQL 19（目前只有 RC 版）會開始支援複寫序號。
  • pg_upgrade 與統計：PostgreSQL 18 起會保留規劃器統計（延伸統計除外），升級完不用等 ANALYZE 跑完查詢才變快。
  • 版本備註：截至 2026-10-31 最新正式版是 18.6，PostgreSQL 14 在 2026-11-12 停止支援，之後不再有安全修補。

練習

練習 1：從 markers 裡 'before' 的 LSN 掃到 pg_current_wal_lsn()，找出所有「一個交易裡刪了不只一列」的交易：每個交易一列，回傳交易編號 xid 和它刪除的列數。只刪一列的交易不能出現。

結果會有兩個交易。看列數和它們在 WAL 裡的提交時間，判斷哪一個是誤刪：那個 xid 就是 PITR 設定 recovery_target_xid（搭配 recovery_target_inclusive = off）要填的值。實務上「刪了很多列」只是線索，還要對照回報的時間和那段時間的部署、批次工作再確認。

練習 2：orders_restored 是在另一台機器上 PITR 還原到誤刪前一刻、再搬過來的副本（欄位和 orders 完全一樣）。寫一句 INSERT … SELECT，只把 orders 裡不見的列補回來，保留原本的 id。誤刪之後的正常工作（訂單 12 退款、新訂單 303）要留著。

練習 3：監控要在 replica 落後太多時告警。從 replica_status 列出每個 replica 的名稱、重播落後的位元組數（從 sent_lsn 算起）、以及是否超過 16 MB（16 × 1024 × 1024 位元組；剛好等於不算超過，true／false），依落後量由大到小排序。

練習 4：咖啡店有一台非同步 replica。有人在 primary 誤執行了沒有 WHERE 的 DELETE FROM orders，五分鐘後才發現。replica 能救回資料嗎？

✓ c：replica 會重播 primary 的每一筆 WAL，包括 DELETE，通常幾毫秒內就跟上了。a 錯：五分鐘後 replica 上的訂單早就一起被刪了，升級它只是換一台一樣空的主機。b 錯：串流複寫複製的是整份 WAL，不會挑掉哪一種變更。複寫防的是機器壞掉，不是資料被改壞；只有基礎備份＋WAL 封存才能回到「誤刪前一刻」。

練習 5：每天 02:00 跑一次 pg_dump 並上傳到另一個區域，沒有 WAL 封存。某天 18:00 主機硬碟壞掉，最多會遺失多少資料？

✓ b：pg_dump 只能還原到匯出那一刻，02:00 到 18:00 的變更只存在壞掉的那顆硬碟上。a 錯：備份只保護到備份那一刻，之後的資料要靠 WAL 封存或複寫。c 錯：那是 WAL 封存或同步複寫才做得到的程度；這裡沒有 WAL 封存。要把 RPO 縮到分鐘級，需要實體備份＋持續的 WAL 封存（PITR），或再加上複寫。

練習 6：把 synchronous_commit 設成 remote_apply（並設定了同步 replica），保證了什麼？代價是什麼？

✓ a：remote_apply 是最強的等級：資料不會遺失，而且在同步 replica 上讀得到剛寫的資料。代價是 COMMIT 延遲（多一趟網路加上重播時間），以及同步 replica 不可用時 COMMIT 會一直等。b 錯：它只涵蓋同步 replica，其他非同步 replica 照樣會落後，而且每次 COMMIT 都要付延遲。c 錯：replica 會重播誤刪，同步只會讓它刪得更快。

常見錯誤

  • 把 replica 當備份：誤刪和程式 bug 會被立刻複寫過去。複寫防機器壞掉，備份防資料被改壞，兩者都要。
  • 備份和資料庫放在同一台機器或同一個區域：硬碟壞掉、區域故障、帳號被入侵時一起消失。備份要放在別的區域，最好連權限也分開。
  • 只有 pg_dump：資料變大後還原要好幾小時，而且只能回到匯出那一刻。資料大或 RPO 要求高時，改用實體備份＋WAL 封存。
  • archive_command 失敗沒人發現：WAL 堆積塞滿磁碟，或 PITR 從某處斷鏈。監控 pg_stat_archiver；指令只能在真的成功時回傳 0。
  • 把正式資料庫整台倒回去：會抹掉誤刪之後的正常寫入。還原到另一台，再把缺的資料補回來。
  • 從來沒演練過還原：真的出事才發現備份壞了、少了 WAL、沒人會還原。定期還原到另一台機器，量出實際 RTO。
  • 忘了刪除不用的 replication slot：primary 會一直保留 WAL 直到磁碟滿。監控 inactive slot，設定 max_slot_wal_keep_size 或 18 的 idle_replication_slot_timeout。
  • 故障轉移後 App 沒有重連與重試：資料庫切換成功，使用者仍看到錯誤。連線池要能重連，交易要能整個重試。
  • 剛寫完就從 replica 讀：非同步複寫有延遲，會讀到舊資料。寫完要立刻讀的查詢走 primary。
  • 大版本過了支援期還在跑：沒有安全修補。PostgreSQL 14 在 2026-11-12 停止支援，提早規劃升級。

小結

  • 先定 RPO（最多掉多少資料）與 RTO（最多停多久），再選方案。複寫防機器壞掉、備份防資料被改壞，replica 救不了誤刪；備份要放在別的區域。
  • WAL 先記帳再改資料：COMMIT 時 WAL 進磁碟就算數，資料頁在 checkpoint 時寫回，當機後從 checkpoint 重播。備份和複寫都是在搬 WAL。fsync 在正式環境絕對不能關。
  • 每刪一列就是一筆 WAL 紀錄，用 pg_walinspect 數「一個交易刪了幾列」，再對照提交時間，就能找出誤刪的 xid。
  • pg_dump：一致快照、可跨大版本、可只還原部分表，但還原慢、只能回到匯出那一刻；pg_basebackup：還原快、只能同大版本。
  • PITR = 基礎備份＋連續的 WAL 封存，可以停在某個時間、交易或具名還原點。還原到另一台，再用 OVERRIDING SYSTEM VALUE 把缺的列補回來，保留之後的正常寫入。
  • 串流複寫預設非同步；同步複寫用 synchronous_commit 決定等到哪一步。replica 落後看 replay_lsn。replication slot 會保留 WAL，沒人用的 slot 會塞滿磁碟。
  • PostgreSQL 不會自己故障轉移，要靠 Patroni 或雲端服務，並防 split-brain；App 要能重連與重試。
  • replica 可以分擔讀取，但寫完要立刻讀的查詢走 primary；長查詢可能被重播取消，hot_standby_feedback 的代價是 primary 膨脹。
  • 邏輯複寫只複寫指定的表、可跨大版本，但不複寫 DDL 與序號；它是幾乎零停機升級與 CDC 的基礎。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 7：晚上部署 ALTER TABLE orders ADD COLUMN note text，這句本來瞬間完成，網站卻卡了 10 分鐘，剛好有一份跑了 10 分鐘的報表在讀 orders。為什麼？

✓ ALTER 要 ACCESS EXCLUSIVE，跟報表的 ACCESS SHARE 衝突，只能排隊；排隊中的 ALTER 又擋住後面所有人，連 SELECT 都進不來。修法是交易裡 SET LOCAL lock_timeout，等不到就放棄、稍後重試。b 錯在 ACCESS SHARE 只跟 ACCESS EXCLUSIVE 衝突，平常報表不擋寫入。（第 34 課）

練習 8：orders 有 4,000 萬列，營業時間執行下面這段 migration。哪裡會出事？

BEGIN;
SET LOCAL lock_timeout = '3s';
ALTER TABLE orders
  ADD CONSTRAINT orders_total_nonneg CHECK (total >= 0);
COMMIT;

✓ 直接加 CHECK 要確認每一列都符合，在強鎖底下掃全表。拆成兩步：ADD CONSTRAINT … NOT VALID 瞬間加上，再 VALIDATE CONSTRAINT，它只拿 SHARE UPDATE EXCLUSIVE，讀寫照常。a 錯在 lock_timeout 只限制等鎖的時間，拿到鎖之後掃多久它管不到。（第 34 課）

練習 9：API 有 6 台、滾動部署。這次要把 customers.phone 改名為 mobile，做法是先跑 RENAME COLUMN phone TO mobile，再部署讀寫 mobile 的新版。哪裡會出事？

✓ 滾動部署期間新舊兩版同時在跑，schema 要兩版都能用。用 expand／contract：先加 mobile 並用 trigger 同步、回填，部署新版，舊版全部下線後才刪 phone。a 錯在 RENAME 只改目錄、瞬間完成，問題出在還在用舊名稱的程式。（第 34 課）

練習 10：上線前 review 設定：API 平常 4 台、自動擴展上限 20 台，每台 pool max 10；worker 2 台、每台 pool max 5；max_connections 是 100。平常只用到約 50 條連線。你的判斷？

✓ 連線預算要用擴展上限算：20 × 10 ＋ 2 × 5 = 210，還要留位置給 migration 和自己登入查問題。不夠就縮小 pool 或加 pooler，讓很多客戶連線共用少量伺服器連線。c 錯在每條連線一個程序、各有記憶體，同時在做事的連線太多，吞吐量反而下降。（第 36 課）

練習 11：每日結帳的 worker 透過 PgBouncer 的 transaction 模式連線，用 advisory lock 確保只有一台在跑。下面每一句各自是一個交易，哪裡會出事？

SELECT pg_try_advisory_lock(42);   -- 拿到才結帳
UPDATE orders SET settled = true WHERE …;
INSERT INTO settlements …;
SELECT pg_advisory_unlock(42);

✓ session 級的鎖跟著伺服器連線，transaction 模式每個交易都可能換一條，鎖就留在那條被別人借走的連線上，隔天可能再也拿不到。改成把結帳放在同一個交易裡，用 pg_try_advisory_xact_lock，交易結束自動釋放。b 錯在交易結束才釋放的是 xact 版本，pg_try_advisory_lock 會一直留到明確解鎖或連線斷掉。（第 36 課）

練習 12：上線時用 postgres 執行過 ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user。這次 migration 由 migrator 建了 gift_cards，App 一查就 permission denied。原因是？

✓ 省略 FOR ROLE 時，預設權限屬於執行這句的角色。要寫 ALTER DEFAULT PRIVILEGES FOR ROLE migrator …，並寫進 migration 進版控。b 把它和 GRANT … ON ALL TABLES 弄反了：只管現有表的是後者，預設權限管的是之後建的表。（第 36 課）

練習 13：顧客在會員頁改了電話，按儲存後頁面重新載入，顯示的還是舊號碼，過幾秒再整理就對了。App 的讀取走非同步 replica。怎麼修最恰當？

✓ 非同步複寫有延遲，COMMIT 回應時 replica 可能還沒重播，剛寫完就去讀會讀到舊資料。同一個請求、或使用者剛改過資料的幾秒內一律讀 primary。a 錯在 on 只等 replica 寫進磁碟，要等到重播完、查得到是 remote_apply，代價是每次 COMMIT 都更慢。（第 37 課）

練習 14：18:10 有人誤刪了二號分店的訂單，18:40 才發現，這 30 分鐘裡還有新訂單和退款。有基礎備份和連續的 WAL 封存，怎麼救？

✓ 用 recovery_target_xid 加 recovery_target_inclusive = off 停在誤刪的交易之前，再用 INSERT … OVERRIDING SYSTEM VALUE SELECT … 補回原本的 id。a 錯在整台倒回去，18:10 之後的新訂單和退款也一起不見了。（第 37 課）
