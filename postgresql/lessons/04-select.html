階段 1：CRUD（增查改刪） · 第 4 課

查詢入門：SELECT、WHERE、NULL

店長下個月要辦「外縣市會員回饋週」：寄優惠券給不住台北的會員，活動菜單只放平價的咖啡和茶。他傳來一張需求清單：會員列表只要姓名和城市、菜單上要標會員價、哪些飲品符合活動價位、會員分布在哪些城市，最後是一份「不住台北的會員名單」，要拿去寄優惠券。另外，活動要先通知中南部的會員，店員也常要用片段的名字找會員或商品。

第 1 課用 SELECT * FROM 表 把整張表拿出來，但這張清單上沒有一項是要「全部」。這一課照著清單一項一項做，學會怎麼只挑出需要的欄和列。做到最後一項時，你會寫出一句看起來完全正確、執行也沒報錯的查詢，名單卻少了兩個人。原因是 SQL 裡最容易踩的坑：NULL。

這課會用到：
  • 第 1 課的 SELECT * FROM customers;（從一張表拿出所有欄、所有列）。
  • 第 3 課的「沒填的欄位會變成 NULL」（新增時沒給值、又沒有預設值的欄位，資料庫會放 NULL）。
這課的路線：
  1. 會員列表只要姓名和城市：SELECT 怎麼只拿需要的欄、當場算出會員價，別名為什麼就是後端拿到的物件 key。
  2. 住台北的會員有誰：WHERE city = '台北' 怎麼一列一列過濾（「不住台北」的最小答案也在這裡）。
  3. 咖啡或茶裡 100 元以下的：用 AND、OR 組合條件，為什麼兩者混用一定要加括號。
  4. 中南部會員、價格區間、搜尋框：IN、BETWEEN、LIKE 讓常見條件更好寫；DISTINCT 列出會員分布在哪些城市。
  5. 名單為什麼少了兩個人：NULL 是什麼，為什麼 = NULL、<>、NOT IN 都會安靜地漏掉資料。

會員列表只要姓名和城市：怎麼只拿需要的欄？

清單第一項是後台的會員列表，畫面上只顯示姓名和城市。SELECT * 的 * 意思是「所有欄位」；要只拿其中幾欄，就把 * 換成欄位名稱，用逗號隔開，例如 SELECT name, city FROM customers。結果的欄位順序就是你寫的順序，跟表裡的順序無關。下面這格的 SELECT name, price 就是只挑兩欄（用商品表示範），第三欄則是接下來要講的運算式。

SELECT 後面不只能寫欄位名稱，也能寫運算式：一段用欄位算出新值的式子，像 JavaScript 的 price * 0.9。清單第二項「菜單上要標會員價」就是這種需求：會員價是售價打九折，表裡沒有這一欄，但可以在查詢時當場算出來。

算出來的欄位需要一個名字，不然結果的欄位標題會是資料庫自動取的（PostgreSQL 會叫它 ?column?），後端程式很難用。AS 就是幫結果欄位取名字，這個名字叫做別名（alias）。執行下面這格，看結果最右邊那一欄的標題：

member_price 不是表裡的欄位，是這次查詢當場算出來的。它不會寫回 products，下一次查詢不寫這段運算式，就不會有這一欄。所以 SELECT 只是「讀」，不管你在裡面怎麼算，都不會改到資料。

別名為什麼重要？後端用 Node 查資料庫時，每一列結果會變成一個物件，物件的 key 就是結果的欄位名稱。上面這句查詢，後端拿到的每一列都是一個有 name、price、member_price 三個 key 的物件，再轉成 JSON 回給前端。換句話說，你在 SQL 裡取的別名，就是前端 Vue 元件裡讀的屬性名稱。別名中文可以直接寫，例如 AS 會員價；想保留大寫或含空白時的寫法見課末「補充與查表」。

💡 實務上：API 只拿畫面要用的欄位
咖啡店後台的會員列表只顯示姓名和城市，後端就只 SELECT name, city。用 SELECT * 的風險是：之後有人在表裡加了密碼雜湊或內部備註欄位，API 會默默一起回傳給前端，變成資料外洩。ORM（用物件操作資料庫、幫你產生 SQL 的函式庫，如 Prisma、TypeORM）預設常常是撈整列，code review 時值得看一下它實際送出的 SQL。練習或在終端機查資料時用 * 看全貌沒關係。

現在欄位挑好了，但結果還是每一位會員、每一樣商品都在。店長的下一個問題是「住台北的會員有誰」：要挑的不再是欄，而是列。

住台北的會員有誰：WHERE 怎麼一列一列過濾？

挑列用 WHERE。它接在 FROM 後面，寫一個條件，例如 city = '台北'。資料庫的做法可以想成咖啡店門口有一位店員：表裡的每一列輪流走過來，店員拿這一列的值代進條件算一次，算出來是 true 的才放進結果，其他的丟掉。

圖裡除了 true 和 false，還有第三種結果 unknown：吳家豪沒有填城市，他的 city 是 NULL。這條路先記著，最後一節會回來解釋它為什麼存在。先執行看看台北的會員：

結果只剩 city 是台北的那幾列。寫法的順序固定是 SELECT 欄位 FROM 表 WHERE 條件，WHERE 不能寫在 FROM 前面。從 JavaScript 過來要注意兩件事：

  • 比較「等於」是一個 =，不是 ===。SQL 的 WHERE 裡沒有「指定」這回事，所以一個等號就夠了。
  • 文字要用單引號包起來：'台北'。雙引號在 SQL 裡是用來包欄位名稱、表名稱的，寫成 "台北" 會被當成一個叫「台北」的欄位，報錯 column "台北" does not exist。

= 只是比較運算子的其中一個。條件可以用的比較方式有這些：

寫法意思例子
=等於city = '台北'
<>（或 !=）不等於category <> '咖啡'
<、>小於、大於price < 100
<=、>=小於等於、大於等於price >= 130

開場那份「不住台北的會員名單」，照這張表就是 WHERE city <> '台北'。這是最小版本的答案，最後一節會發現它少了兩個人。

咖啡或茶裡 100 元以下的：多個條件怎麼組合？

把多個條件接起來用三個邏輯運算子，意思跟 JavaScript 的 &&、||、! 一樣，只是寫成英文字：

  • A AND B：兩個都成立，這一列才留下。
  • A OR B：至少一個成立就留下。
  • NOT A：反過來，上一節的 NOT is_available 就是它。

130 元的焦糖瑪奇朵、150 元的冰滴咖啡怎麼也跑出來了？查詢沒報錯，問題出在資料庫怎麼「斷句」。跟數學的先乘除後加減一樣，SQL 的邏輯運算子也有優先順序：AND 比 OR 先算（JavaScript 的 && 也比 || 先算）。所以資料庫實際理解成：

category = '咖啡' OR (category = '茶' AND price < 100)

也就是「所有咖啡」加上「100 元以下的茶」。焦糖瑪奇朵是咖啡，左邊的 category = '咖啡' 已經成立，OR 只要一邊成立就留下，價格根本沒被檢查到。要讓 OR 先算，就像數學一樣加括號：

只要 AND 和 OR 寫在同一個 WHERE，就加括號。這種錯誤不會報錯，只會多出一些不該有的列，很難發現；就算你記得優先順序，下一個讀程式的人也不一定記得。

條件組得出來了，但寫法越來越長。如果店長要的是「台中、台南、高雄的會員」，就得寫三個 city = … 再用 OR 接起來；要找價格區間、要找名字裡有某個字的商品，用目前的工具也很難寫。這些常見的條件有更短的寫法。

中南部會員、價格區間、搜尋框：常見條件有沒有更好寫的寫法？

這一節的四個工具，前三個（IN、BETWEEN、LIKE）都是「寫在 WHERE 裡的條件」，各自取代一種用 AND／OR 寫起來很囉唆的模式；最後一個 DISTINCT 處理的是另一個問題：結果裡的重複值。

店員忘了全名：LIKE 用萬用字元比對文字

有位會員打電話來報名，店員只記得他姓林。= 要整個字串一模一樣才成立，這時派不上用場；LIKE 可以只比對一部分，用兩個萬用字元（代表「任意字」的符號）描述你知道的那一部分：

  • %：任意長度的任意字，包括 0 個字。
  • _：剛好一個任意字。
寫法找到

name LIKE '%拿鐵'拿鐵結尾：拿鐵、抹茶拿鐵
name LIKE '%咖啡%'任何位置含「咖啡」
name LIKE '林__'林開頭、剛好三個字

💡 實務上：搜尋框的關鍵字不要直接拼進 SQL
商品管理頁的搜尋框，後端通常寫成 WHERE name ILIKE $1，$1 是預留給參數的位置，再把 '%' + 關鍵字 + '%' 當參數傳進去。不要用字串把使用者輸入直接接進 SQL：那樣使用者打的文字有機會被當成 SQL 指令執行，這種攻擊叫 SQL injection（SQL 注入），第 25 課會實作參數化的寫法。另外要先想好：關鍵字是空字串時要回傳全部還是不查？使用者打的 %、_ 也會被當成萬用字元，需不需要跳脫成普通字元？

NULL 是「不知道」，不是空值

NULL 的意思是「不知道」：這一格沒有值，我們不曉得它應該是什麼。它不是 0，也不是空字串 ''。吳家豪的 city 是 NULL，意思不是「他沒有住的地方」，而是「我們不知道他住哪」；空字串則是一個確實存在的值，只是長度為 0。第 3 課看過，新增時沒填、又沒有預設值的欄位就會是 NULL，所以 NULL 在真實資料裡非常常見。

既然是「不知道」，拿它來比較會得到什麼？吳家豪住台北嗎？不知道。吳家豪不住台北嗎？也不知道。所以 SQL 規定：任何值跟 NULL 用 =、<>、< 這類運算子比較，結果都不是 true 也不是 false，而是 unknown。連 NULL = NULL 也是 unknown：兩個不知道的東西，你沒辦法說它們相等。這跟 JavaScript 很不一樣，JS 的 null === null 是 true。

所以 SQL 的條件結果有三種：true、false、unknown，這叫三值邏輯。再回頭看第二節的圖：WHERE 只留下 true 的列，false 和 unknown 都被丟掉。NULL <> '台北' 是 unknown，吳家豪和鄭佩珊就這樣被丟掉了。

unknown 遇到 AND、OR、NOT 時怎麼算，接下來的修正都會用到。判斷的方法是問：「把 unknown 換成 true 或 false，結果會不會變？」不會變就是確定的答案，會變就還是 unknown：

運算結果原因
true OR unknowntrueOR 只要一邊成立，另一邊是什麼都一樣
false OR unknownunknown結果全看那個不知道的值
false AND unknownfalseAND 只要一邊不成立，另一邊是什麼都一樣
true AND unknownunknown結果全看那個不知道的值
NOT unknownunknown不知道的反面還是不知道

這也解釋了為什麼第二節的 WHERE NOT is_available 沒問題：is_available 是 NOT NULL 的欄位，不會出現 unknown。有了三值邏輯，下面三個陷阱就都能用同一個道理解釋。

陷阱 1：= NULL 永遠找不到東西

優惠券要用簡訊寄，沒留電話的會員收不到，店長想知道是哪些人。要找「沒填」的資料，直覺會寫成 = NULL：

0 列。phone = NULL 對每一列都是 unknown，連 phone 真的是 NULL 的那幾列也一樣（NULL = NULL 是 unknown），所以沒有任何一列留下。它沒有報錯，只是安靜地回傳 0 列，這正是它危險的地方：你會以為「沒有人沒留電話」。

要問「這一格是不是 NULL」，得用專門的運算子 IS NULL，反過來是 IS NOT NULL。它們不是在「比較值」，而是在檢查「這一格有沒有值」，所以結果一定是 true 或 false，不會是 unknown：

陷阱 3：NOT IN 的清單裡有 NULL

同一個道理還會以更隱密的方式出現。假設店長改成要排除雙北，排除的城市清單不是手寫的，而是從別的資料整理出來的，裡面混進了一個 NULL。用 NOT IN 來寫：

一列都沒有！上一節說過 IN 是一串 OR 的簡寫；加上 NOT 之後，city NOT IN ('台北', '新北', NULL) 就等於 city <> '台北' AND city <> '新北' AND city <> NULL。最後那一項對每一列都是 unknown。用三值邏輯表看：住台北的人前面已經是 false，false AND unknown 是 false；住台中的人前面都是 true，true AND unknown 是 unknown。不管是誰，整個條件都不可能是 true。

你可能覺得「誰會在清單裡寫 NULL」。手寫的確不會，但清單常常是另一個查詢查出來的（第 16 課的子查詢），只要裡面混進一個 NULL，整個查詢就默默變成 0 列。記住：用 NOT IN 之前，確定清單裡沒有 NULL。

💡 實務上：先問清楚「不知道」要不要算進去
PM 說「幫我拉不住台北的會員名單」，資深工程師會先反問：沒填城市的人要不要算？這是業務決定，不是 SQL 決定，問清楚再決定寫 <> 還是加上 OR city IS NULL。前端也要分清楚：API 回傳的 null 代表「沒填」，畫面上通常顯示「未提供」，不要跟空字串混用。建表時就決定每個欄位能不能是 NULL（第 12 課的 NOT NULL），不該缺的欄位就加上 NOT NULL，這類坑自然少很多。

店長的清單到這裡全部做完了。不過每份結果的順序都是資料庫自己決定的，還沒有照價格或姓名排好，這是下一課要處理的事。

補充與查表

  • 別名的大小寫與引號：別名跟表名一樣，沒加引號會轉成小寫，AS MemberPrice 拿到的欄位名稱是 memberprice。想保留大寫或含空白，才需要用雙引號包起來，例如 AS "Member Price"。中文不受影響，可以直接寫 AS 會員價。
  • IS DISTINCT FROM：PostgreSQL 的 city IS DISTINCT FROM '台北' 把 NULL 當成一般的值來比，結果只會是 true 或 false。它的效果和 city <> '台北' OR city IS NULL 一樣，反過來的 IS NOT DISTINCT FROM 則是「把 NULL 也當成值的等於」。

練習

練習 1：找出價格在 100 到 130 元之間（含 100 和 130）的商品，顯示 name、price。

練習 2：店員想打電話通知會員，先找出沒有留電話的顧客，只顯示 name。預填的寫法有問題，修好它。

練習 3：找出不住台北的顧客，以及不知道住哪（city 是 NULL）的顧客，兩種都要，顯示 name、city。

練習 4：找出名稱裡有「拿鐵」兩個字的商品，顯示 name、price。

練習 5：找出上架中、分類是咖啡或甜點、而且價格低於 100 元的商品，顯示 name、category、price。（小心 AND 和 OR 的優先順序。）

練習 6：商品總共分成哪些分類？列出 category，每種只出現一次（沒有分類的 NULL 也算一種）。

練習 7：SELECT * FROM customers WHERE city = NULL; 會得到什麼？

✓ 任何值跟 NULL 用 = 比較都是 unknown，WHERE 只留 true，所以一列都沒有。要用 city IS NULL。

練習 8：WHERE category = '咖啡' OR category = '茶' AND price < 100 實際的意思是？

✓ AND 比 OR 先算，等於 category = '咖啡' OR (category = '茶' AND price < 100)。想要 a 的意思就要加括號。

常見錯誤

  • 用 = NULL、<> NULL：跟 NULL 比較永遠是 unknown，一列都不會留下，而且不報錯。判斷是不是 NULL 要用 IS NULL、IS NOT NULL。
  • 以為 <> 會包含 NULL：「不等於台北」不包含「不知道住哪」。先問清楚沒填的要不要算，要的話加上 OR city IS NULL。
  • NOT IN 的清單裡混進 NULL：整個條件不可能是 true，結果變成 0 列。清單來自另一個查詢時特別容易發生。
  • AND 和 OR 混用不加括號：AND 先算，結果多出一堆不該有的列，而且不會報錯。
  • 文字條件用了雙引號：WHERE city = "台北" 會把「台北」當成欄位名稱，報錯 column "台北" does not exist。文字一律用單引號。
  • 以為 BETWEEN 不含尾端：BETWEEN 90 AND 110 兩端都包含；要不含尾端就寫 price >= 90 AND price < 110。
  • 在 WHERE 裡用 SELECT 的別名：SELECT price * 0.9 AS member_price … WHERE member_price < 100 會報錯，因為 WHERE 比 SELECT 先執行，那時別名還不存在（第 7 課會畫出執行順序）。WHERE 裡要寫完整的 price * 0.9 < 100。

小結

  • SELECT 欄位或運算式 AS 別名 FROM 表 WHERE 條件。SELECT 挑欄、WHERE 挑列；運算式當場算、不改資料；別名就是後端拿到的物件 key。
  • WHERE 對每一列算一次條件，只留下 true 的列。文字用單引號，等於是一個 =。
  • 組合條件用 AND OR NOT，AND 比 OR 先算，兩者混用就加括號。
  • IN 是一串 OR 的簡寫、BETWEEN 含頭尾、LIKE 用 % 和 _、ILIKE 不分大小寫；DISTINCT 對結果去重複。
  • NULL 是「不知道」，跟任何值比較都是 unknown，WHERE 會丟掉它。判斷 NULL 用 IS NULL；<> 和 NOT IN 會安靜地漏資料，寫之前先問「沒填的要不要算」。
