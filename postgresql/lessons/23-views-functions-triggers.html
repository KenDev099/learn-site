階段 7：實務 · 第 23 課

View、Function、Trigger

週一早上店長傳訊息來：「系統說起司蛋糕還有 3 個，可是冰櫃裡只剩 1 個。」你追了一下，原因是週末有一位同事在後台直接用 SQL 補了一筆漏掉的訂單明細。扣庫存的程式寫在 Node 後端的「下單 API」裡，只有走這支 API 下單才會扣；同事直接 INSERT 進 order_items，那段程式根本沒有執行，庫存就這樣對不上了。

回頭檢查，類似的狀況不只一處：「訂單明細附上顧客姓名和商品名稱」這句四張表的 JOIN，後端 API、報表工具、匯出 CSV 的腳本各抄了一份。報表工具指的是像 Metabase 這種開源軟體，它直接連資料庫，讓店長自己拉報表。會員等級「消費滿多少算金卡」的公式，後端和報表各寫一次，上次改門檻只改到其中一邊；訂單對帳時，明細加總的算法也各寫了一份。這些問題的根源相同：規則散在每一支讀寫資料的程式裡，只要有一條路沒照做，資料就錯。這一課學 PostgreSQL 讓你把查詢和規則存進資料庫本身的三個工具：View、Function、Trigger，用它們把這三個問題一個一個收回來。最後回答一個常被問到的問題：邏輯到底該放資料庫，還是後端程式？

這課會用到：
  • 第 9 課的 JOIN：用 ON 條件把兩張表的列配對起來，四張表就連續 JOIN 三次。
  • 第 12 課的 CHECK 約束：寫入的資料不符合條件，資料庫直接拒絕並報錯。
  • 第 18 課的交易：一組修改要嘛全部成功，要嘛一個錯就全部撤銷。
  • 第 22 課的 migration 檔：對資料庫結構的每一次修改都寫成有編號的檔案，進 git、照順序執行。
這課的路線：
  1. 規則散在各處，資料庫能幫什麼忙：三個工具各對應開場的哪個問題，以及「邏輯放哪裡」的簡短答案（開場問題的最小答案）。
  2. 同一句 JOIN 抄了三份：用 View 把查詢存進資料庫，大家查同一個名字；報表太慢時，用 Materialized View 連結果一起存下來，代價是要自己更新。
  3. 會員等級的公式抄了兩份：把需要參數和判斷的計算寫成 Function。
  4. 手動補單也要扣庫存：用 Trigger 讓資料庫在資料變動時自己執行規則，修好開場的事故。
  5. 是不是所有邏輯都該搬進資料庫：兩邊在可靠性、除錯、版本管理上的取捨，團隊實際怎麼分工。

規則散在各處，資料庫能幫什麼忙？

開場的三個問題性質不一樣：第一個是「同一句查詢」被抄到好幾個地方，第二個是「同一段計算」被抄到好幾個地方，第三個是「資料一變動就該發生的事」被某一條路跳過。PostgreSQL 剛好各有一個工具對應：

  • View：存在資料庫裡的一句 SELECT，取了名字，可以像一張表一樣查。像店長貼在牆上的「今日報表格式」：每次看都照同一個格式、用最新的數字算出來。它解決 JOIN 抄好幾份的問題。
  • Function：存在資料庫裡的一段邏輯，有參數、有回傳值，跟 JavaScript 的 function 一樣。像一張標準作業卡：「計算會員等級的方法」寫一次，誰要用都照著做。它解決公式抄好幾份的問題。
  • Trigger：告訴資料庫「這張表一有 INSERT、UPDATE 或 DELETE，就自動呼叫某個 function」。像收銀機的自動動作：每結一筆帳，庫存就自動扣掉，不用店員記得去改。它解決規則被繞過的問題。

三樣東西的共同點是：它們存在資料庫裡，而不是存在某一支程式裡。不管是後端 API、報表工具，還是同事開著命令列直接下 SQL，大家碰到的都是同一份。這正是開場事故缺的東西：扣庫存的規則只存在後端程式裡，繞過後端，就沒有規則。

那是不是什麼都搬進資料庫就好？先給簡短答案：保護資料正確性、一定不能被繞過的規則（例如扣庫存、每次修改都更新 updated_at）放資料庫；常常改的業務流程、要呼叫外部服務的事（寄信、付款）放後端程式。為什麼這樣分，要等三個工具都看過才講得清楚，放在最後一節〈那是不是所有邏輯都該搬進資料庫？〉。

先從最單純、只讀不寫的問題開始：那句被抄了三份的 JOIN。

同一句 JOIN 抄了三份：怎麼只寫一次？

先看那句查詢本身。它要回答「每張訂單買了什麼、誰買的、小計多少」，但這些資料分在四張表：orders 記誰下的單，customers 有顧客姓名，order_items 記每項商品的數量和單價，products 有商品名稱，所以要連續 JOIN 三次。執行後看結果：每一列是「一張訂單裡的一項商品」。

這句有六行。抄到三個地方之後，任何一邊要改，例如小計要扣掉折扣，就得記得三邊一起改，漏一邊，三個地方算出來的數字就不一樣。

View 的做法是：把這句 SELECT 取個名字存進資料庫，之後大家都查這個名字。寫法是 CREATE VIEW 名稱 AS，後面接原本的查詢。下面這格先建立 order_details，接著像查一張普通的表一樣，算出每位顧客的消費總額。看第二句：它沒有寫任何 JOIN，只是對 order_details 做 GROUP BY。

View 是怎麼運作的？它沒有存任何一列資料，存的只是那句 SELECT。你查 order_details 時，PostgreSQL 會把這個名字展開成原本那句查詢，跟你在外面寫的 WHERE、GROUP BY 合在一起再執行。這帶來兩個結果：

  • 結果永遠是最新的：底層的表一改，下一次查 View 就看得到，不需要任何同步。
  • View 不會讓查詢變快：它執行的就是原本那句四張表的 JOIN，原本慢，包成 View 一樣慢。

因為查起來跟表一樣，View 上面可以再加 WHERE、GROUP BY，也可以再跟別的表 JOIN。View 還有另一個用途：只讓某些人查 View、不讓他們查底層的表，就能藏起不該給他們看的欄位，下一課講權限時會用到。View 建好之後要修改或刪除，語法見課末〈補充與查表〉。

💡 實務上：View 常當成報表和後台的「固定窗口」
在咖啡店，可以讓後端 API、匯出腳本、報表工具都改查 order_details，不必各自寫一次 JOIN。之後底層的表拆欄位或改名，只要改 View 的定義，查它的地方都不用動。要注意兩件事：別一層 View 疊一層 View，出問題時很難看出到底執行了什麼；有 View 依賴的欄位，DROP COLUMN 會被擋下來，寫 migration（第 22 課）時要記得先處理 View。

銷量排行太慢、又不需要即時：能不能把結果存下來？

上一節說 View 不會讓查詢變快，每次查都把整句重跑一次。店長的後台首頁有一張「各商品累計銷量」，要把所有訂單明細加總；店開得越久，明細越多，每個人打開首頁都重算一次，這張圖就越來越慢。可是店長看它只是想知道哪些商品賣得好，晚一小時更新也沒關係。

這種「很慢、但不需要即時」的查詢，用 Materialized View。materialized 是「實體化」的意思：它跟 View 一樣存了一句查詢，但建立的時候會真的執行一次，把結果像一張表一樣存起來。之後查它是直接讀存好的結果，不再重算。下面建立一個各商品銷量的 Materialized View，執行後記下拿鐵的 sold：

兩種 View 的差別整理如下：

VIEWMATERIALIZED VIEW

選擇的順序是：一般 View 夠快就用一般 View，資料永遠正確；只有在查詢真的慢、使用者又能接受數字晚一點時，才換成 Materialized View，同時安排好什麼時候 REFRESH。

💡 實務上：先問清楚「數字可以晚多久」
典型用途是後台的「本月各商品銷量」「各分店營收排行」：資料量大、查的人多，但晚一點更新沒關係。用之前先跟 PM 或店長確認數字可以接受晚多久，再決定多久 REFRESH 一次；通常由後端的排程工作定時下這句指令。排程工作（cron job）是照固定時間自動執行的程式，例如每小時整點跑一次。REFRESH 的過程中，別人查這個 View 預設會被擋住，需要邊更新邊查的做法見課末。資料量還小、一般 View 加上索引就夠快時，不必急著用它：多一個「要記得更新」的東西，就多一個出錯的地方。

會員等級的公式抄了兩份：有參數的計算怎麼共用？

View 和 Materialized View 解決的是「同一句查詢」。開場的第二個問題不一樣：會員等級是「給我一位顧客，算出他的等級」，訂單對帳是「給我一張訂單，算出明細的加總」。這種計算要先傳一個參數進來，有時還要用 IF 判斷，View 做不到。Function 就是為這種事準備的：它跟 JavaScript 的 function 一樣有參數、有回傳值，只是存在資料庫裡，任何能下 SQL 的地方都能呼叫。

最簡單的 function：一句有參數的 SQL

會員等級要先算總額、再用 IF 判斷，這是純 SQL 寫不出來的，所以先用一個不需要判斷的例子看清楚 function 的骨架：訂單對帳。先寫對帳用的那個：給一個訂單 id，回傳這張訂單所有明細 quantity * unit_price 的加總，拿來跟 orders.total 比對。範例裡每一段的意思：

  • CREATE FUNCTION order_total(p_order_id integer)：函式名稱是 order_total，有一個參數 p_order_id，型別是 integer。
  • RETURNS integer：回傳值的型別。
  • LANGUAGE sql：函式內容是純 SQL。
  • AS $$ … $$：函式的內容。對 CREATE FUNCTION 來說，函式內容是一個字串，見下一段。

函式內容要包成字串，最直覺的是用單引號，但內容裡只要出現 '台北' 這種字串，每個單引號都得寫兩次，變成 ''台北''，很難讀。錢字號引號（dollar quoting）是 PostgreSQL 另一種包字串的寫法：兩個 $$ 之間的內容原樣當成字串，裡面的單引號不用另外處理。寫 function 時幾乎都用它。

參數名稱加 p_ 前綴，是為了不跟欄位名稱撞名。如果參數也叫 order_id，函式裡寫 WHERE order_id = order_id，兩邊都會被當成欄位，條件永遠成立，這張訂單就會加總到所有明細。

需要變數和判斷：用 PL/pgSQL 寫會員等級

會員等級的公式是：訂單總額 400 以上金卡、200 以上銀卡，其他是一般會員。這要先算出總額、存在某個地方，再拿它做判斷；純 SQL 的 function 只能放查詢，沒有變數，也沒有 IF。PostgreSQL 內建一個程式語言叫 PL/pgSQL，它在 SQL 的基礎上加了變數、IF 判斷和迴圈，專門用來寫資料庫裡的 function。範例裡新出現的部分：

  • LANGUAGE plpgsql：函式內容用 PL/pgSQL 寫。
  • DECLARE 區塊宣告變數，這裡是 spent integer；BEGIN … END 之間是程式本體。這個 BEGIN 是 PL/pgSQL 的區塊開頭，跟交易的 BEGIN 無關。
  • SELECT … INTO spent：把查詢結果存進變數 spent。COALESCE(sum(total), 0) 讓沒下過單的顧客算成 0，不是 NULL。
  • IF … ELSIF … ELSE … END IF 依 spent 判斷，RETURN 回傳等級。

不過 function 有一個前提：要有人呼叫它，它才會執行。就算把「扣庫存」也寫成 function，開場的事故還是會發生，因為手動補單的同事不會記得在 INSERT 之後再呼叫一次。我們需要的是反過來：資料一變動，資料庫自己去呼叫。

手動補單也要扣庫存：怎麼讓資料庫在資料變動時自動執行？

這就是 Trigger：你告訴資料庫「某張表發生 INSERT、UPDATE 或 DELETE 時，幫我呼叫這個 function」。之後不管資料是從後端 API、報表工具，還是同事開命令列寫進來，只要動到那張表，資料庫都會照做，沒有任何一條路能跳過。

建立 trigger 分兩步：

  1. 先寫一個 RETURNS trigger 的 function，裡面是要自動做的事。
  2. 再用 CREATE TRIGGER 指定：哪張表、哪種操作、在寫入之前還是之後，要呼叫這個 function。

trigger function 不從參數拿資料，而是靠兩個特別的變數：NEW 是「改完之後的那一列」（INSERT、UPDATE 才有），OLD 是「改之前的那一列」（UPDATE、DELETE 才有）。例如 order_items 新增一列時，NEW.product_id、NEW.quantity 就是剛新增那筆明細的商品和數量。

「之前還是之後」決定 trigger 能做什麼：

  • BEFORE：在這一列真正寫入之前執行。function 可以修改 NEW，最後回傳的那一列才是真正寫進去的；回傳 NULL 則等於告訴資料庫「這一列不要寫」。適合修改正在寫入的這一列。
  • AFTER：在這一列寫入之後執行。這時資料已經寫好，回傳值會被忽略。適合依照這次的修改，去改別的表。

先看最簡單的：自動更新 updated_at

扣庫存要動到另一張表，先用一個只改「正在寫入的這一列」的例子看清楚 trigger 的結構。products 有一個 updated_at 欄位，記錄每一列最後修改的時間。它跟扣庫存是同一類問題：靠每支程式記得去設，總有一條路會忘記。執行後看結果：只有被改價的美式咖啡，updated_at 變成現在的時間。

對照範例逐段看：

  • BEFORE UPDATE ON products：products 每次 UPDATE，在寫入之前執行，所以可以修改 NEW。
  • FOR EACH ROW：每改一列就執行一次。一句 UPDATE 改了 10 列，function 就執行 10 次。
  • NEW.updated_at := now();：把即將寫入的那一列的 updated_at 改成現在時間，:= 是 PL/pgSQL 的指定運算子。
  • RETURN NEW;：把改過的那一列交回去，資料庫就寫入這一列。

💡 實務上：trigger 是「看不見」的程式碼
trigger 擋住了繞過後端的寫入，但它的坑也在同一個地方：翻後端程式碼找不到它。下次同事在後台手動補一筆明細，庫存跟著被扣，新來的工程師可能查半天才發現是 trigger 做的。所以 trigger 要寫在 migration 檔裡、取看得懂的名字（例如 order_items_decrease_stock），接手專案時先查每張表掛了哪些 trigger（指令見課末）。另外，FOR EACH ROW 代表一次匯入一萬筆資料就會執行一萬次，大量匯入前要想到它；如果 ORM 已經會自動設 updated_at，也不必再加 trigger 重複做。

那是不是所有邏輯都該搬進資料庫？

扣庫存搬進 trigger 之後，事故修好了。很自然會接著想：既然放資料庫這麼可靠，寄確認信、算折扣是不是也搬進去？先看同一件事的另一種做法：在 Node 後端把「寫入明細」和「扣庫存」兩句 SQL 包在一個交易裡，一樣不會超賣，前提是每一條寫入路徑都經過那段程式。兩種做法的取捨：

放在資料庫（trigger、function）放在後端程式
可靠性不管資料從哪裡寫進來（後端、管理後台、手動 SQL），規則一定會執行只要有一條路徑忘了呼叫，規則就被繞過
效能在資料庫內完成，少了來回傳輸多一次網路往返
可讀性邏輯「藏」在資料庫裡，看後端程式碼看不出來跟其他業務邏輯放在一起，好找好懂
測試與除錯需要連資料庫才能測，錯誤訊息較難追可以用熟悉的工具寫單元測試、下中斷點
版本管理要靠 migration 檔管理（上一課）跟著程式碼一起 commit

這張表裡互相拉扯的是第一列和後三列：放在資料庫最不會被繞過，但也最不容易被看見、被測試、被修改。所以判斷一條規則放哪裡，可以問兩個問題：這條規則如果被某條路繞過，資料會不會錯？它多久會改一次？實務上常見的分工是：

  • 放資料庫：保護資料正確性的規則，例如約束、updated_at、扣庫存，以及稽核記錄。稽核記錄（audit log）是記下「誰在什麼時候改了什麼」的表，練習 3 的調價記錄就是一種。這些事情一定不能被繞過，而且很少改。
  • 放後端：會常常改的業務流程、要呼叫外部服務的事（寄信、付款）、需要複雜測試的邏輯。

套回咖啡店：扣庫存和 updated_at 放資料庫；寄訂單確認信要呼叫郵件服務、失敗時要重試，留在後端；每週變動的行銷折扣也留在後端，用單元測試保護。

也有一種架構會大量使用 function 和 trigger：Supabase 這類服務讓前端透過自動產生的 API 直接讀寫資料表，中間沒有一層自己寫的後端，所以資料規則大多放在資料庫裡的 function 和 trigger。前端這樣直接讀寫資料表還能保持安全，靠的是下一課的權限與 Row Level Security。

補充與查表

修改與刪除的語法，查表用，不用背：

修改刪除
ViewCREATE OR REPLACE VIEW：只能在最後面加欄位，不能改既有欄位DROP VIEW 名稱
FunctionCREATE OR REPLACE FUNCTIONDROP FUNCTION 名稱
  • 邊更新邊查 Materialized View：一般的 REFRESH 期間會擋住別人查這個 View；改用 REFRESH MATERIALIZED VIEW CONCURRENTLY 可以邊更新邊查，但它要求 View 上有唯一索引。
  • 只在某些欄位變動時觸發：寫成 BEFORE UPDATE OF price ON products，只有 UPDATE 的 SET 裡有 price 時才執行。
  • 查一張表掛了哪些 trigger：psql 是 PostgreSQL 的命令列工具，在裡面輸入 \d 表名，會列出這張表的欄位、索引和 trigger。

練習

練習 1：建立一個 View 叫 customer_spending，依序有三欄：顧客姓名、訂單數、訂單 total 的總和。只要列出有下過訂單的顧客。

練習 2：寫一個 SQL function product_revenue(p_product_id integer)，回傳這個商品在 order_items 裡的營收（每筆明細 quantity * unit_price 的總和）。沒有賣出過的商品要回傳 0，不是 NULL。

練習 3：店長想保留每次調價的記錄。寫一個 trigger：products 每更新一列，就在 price_history 新增一筆，填入 product_id、old_price（改之前的價格）、new_price（改之後的價格）。price_history 已經建好，id 和記錄時間會自動產生。判分時會實際改幾次價格，檢查記錄對不對。

練習 4：CREATE MATERIALIZED VIEW daily_report AS … 之後，又新增了 50 筆訂單。此時 SELECT * FROM daily_report 會看到什麼？

✓ Materialized View 存的是建立（或上次 REFRESH）時的結果。一般的 View 才會每次重新計算。

練習 5：下面哪一件事最適合用 trigger 放在資料庫裡做？

✓ updated_at 是單純、固定、「不管誰改資料都該發生」的規則，放在資料庫最可靠。寄信要呼叫外部服務、失敗時要重試；行銷規則常常改、需要測試，這兩件事放在後端程式比較好管理。

常見錯誤

  • 以為 View 能讓慢查詢變快：一般 View 只存查詢，每次查都重跑原本那句。真的慢、又能接受晚一點更新，才用 Materialized View。
  • 以為 Materialized View 會自動更新：要自己 REFRESH（通常用排程定時跑）。
  • BEFORE trigger 忘了 RETURN NEW：回傳 NULL 等於告訴資料庫「這一列不要寫了」，資料會默默地沒寫進去。
  • 參數名稱跟欄位名稱一樣：WHERE product_id = product_id 永遠成立。參數加 p_ 前綴。
  • trigger 裡更新同一張表：AFTER UPDATE 的 trigger 又去 UPDATE 同一張表，會再觸發自己，變成無限遞迴。要改當前這一列，用 BEFORE trigger 直接改 NEW。
  • 把太多業務邏輯塞進 trigger：一句 INSERT 背後連鎖觸發一堆事，除錯時很難想到。保持 trigger 簡單、取個看得懂的名字。

小結

  • 開場的事故來自規則散在各支程式裡：只要有一條路沒照做，資料就錯。View、Function、Trigger 把查詢和規則存進資料庫，每條路碰到的都是同一份。
  • CREATE VIEW 把查詢存成虛擬表，結果永遠最新，但不會變快；MATERIALIZED VIEW 存下結果，查詢很快，要 REFRESH 才會更新。
  • CREATE FUNCTION：簡單的用 LANGUAGE sql，需要變數和判斷用 plpgsql；內容用 $$ … $$ 包起來，參數加 p_ 前綴。Function 要有人呼叫才會執行。
  • Trigger = 一個 RETURNS trigger 的 function ＋ CREATE TRIGGER … BEFORE/AFTER … FOR EACH ROW；用 NEW、OLD 讀取新舊資料。BEFORE 改正在寫入的這一列，AFTER 去改別的表；trigger 失敗，原本的修改一起撤銷。
  • 保護資料正確性、不能被繞過的規則放資料庫；常變動、要呼叫外部服務的流程放後端。
