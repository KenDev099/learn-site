階段 9：資深必備｜並發與正確性 · 第 31 課

隔離等級深入：快照、寫入偏差、重試與 UPSERT

週一早上，信義店（A 店）的店長打電話來：昨天下午有半小時店裡沒有咖啡師，客人排到門外。咖啡店有一條規則：每家店至少要有一位咖啡師值班。排班 App 的「我要下班」會先數同店還有幾人值班，至少 2 人才讓你下班。查 log 發現，阿明和小美幾乎同時按下「我要下班」，兩個請求各自數到「2 人值班」、各自通過檢查、各自把自己改成下班。兩個交易都成功提交，每一句 SQL 都合法，資料庫沒有報任何錯，A 店卻變成沒有人。

這一課的任務是查清這次事故、修好它，然後把同樣的檢查套到咖啡店後端其他「先讀資料、判斷、再寫入」的規則上：值班規則、集點兌換、第一次消費時開集點卡、每週同步總部價目表。每一條都要回答同一個問題：兩個請求同時進來時，這條規則由誰保證？第 19 課的原子更新和 FOR UPDATE 救不了值班事故，因為阿明和小美改的是不同的列；要修好它，得先弄清楚交易到底「看得到什麼」，再看隔離等級、重試、鎖與唯一約束各自能擋住哪一種情況。

第一輪只要記住：
  • 規則牽涉「別的列」時（每家店至少一人值班、限量 100 張），預設的 READ COMMITTED 和 REPEATABLE READ 都擋不住，叫寫入偏差。解法是先鎖住共同的父列，或改用 SERIALIZABLE 加重試。
  • 收到 40001（序列化失敗）或 40P01（死結），從 BEGIN 重做整個交易、重新讀取；會被重試的交易裡不要寄信、扣款。
  • 「有就更新、沒有就新增」用唯一約束加 INSERT … ON CONFLICT，不要先查再新增。
課末的「補充與查表」第一輪可以跳過。
這課的路線：
  1. 兩個人為什麼都看到 2 人值班、這種錯叫什麼：快照與隔離等級，以及開場事故的名字「寫入偏差」和擋得住它的等級（開場問題的最小答案）。
  2. 親手重現事故：REPEATABLE READ 放過、SERIALIZABLE 擋下，它怎麼發現的。
  3. 被拒絕的交易怎麼辦、有沒有不用重試的修法：重試整個交易，以及先鎖住共同的那家店。
  4. 集點兌換：為什麼同一列的規則一句 UPDATE 就夠。
  5. 開卡與價目表同步：列還不存在時讓唯一約束當裁判（UPSERT），整批同步用 MERGE；最後整理成一張審查表。
這課會用到：
  • 第 19 課的 lost update 與兩種解法：lost update 是兩個人「先讀再寫」同一列，後寫的蓋掉先寫的；原子更新把讀和寫合成一句 UPDATE … SET stock = stock - 1；FOR UPDATE 讀的同時鎖住選到的列，直到交易結束。
  • 第 19 課的隔離等級：決定交易看得到別人多少修改，預設是 READ COMMITTED；用 REPEATABLE READ 或 SERIALIZABLE 時，資料庫寧可讓交易失敗，程式要能重試。
  • 第 30 課的快照與「暫停的同事」：快照記下「哪些交易算已完成」，查詢只看得到已完成交易寫的版本；PREPARE TRANSACTION 讓交易停在已準備、還沒提交的狀態。
  • 第 27 課的 SQLSTATE：每種錯誤固定的 5 碼代號，例如 23505 是「值重複」；程式判斷錯誤要比對代號，不比對訊息文字。
這頁的環境：這頁只有一條連線，看不到別人：同時發生的事用時間軸示範，另一個人的交易用「暫停的同事」模擬。收尾的 COMMIT PREPARED／ROLLBACK PREPARED 要單獨一格。有句子去等暫停交易的鎖，會一直等下去，引擎約 5 秒後中斷並重置頁面資料庫。

這頁的資料：stores（A、B 兩家店）、shifts 值班表（每家店兩位咖啡師）、stamp_cards 集點卡、products（6 項商品，name 不可重複）、hq_menu 總部價目表（價目表同步那節用）。

兩個人為什麼都看到「2 人值班」？交易看得到什麼

事故的關鍵畫面是：阿明已經把自己改成下班了，小美數的時候卻還是 2 人。要知道這是不是資料庫「看錯了」，得先知道一個交易在執行查詢時，到底看得到哪些資料。

第 30 課講過，PostgreSQL 修改一列時不會直接蓋掉舊資料，而是寫一個新版本，所以同一列在某個時刻可能同時有好幾個版本：已提交的舊版本、某個交易剛寫還沒提交的新版本。查詢要決定看哪一個版本，靠的是快照（snapshot）：一份「此刻哪些交易已經提交」的紀錄。查詢只看得到快照裡已提交的交易寫的版本，其他的一律當作不存在。

快照解決了「看哪個版本」，但留下一個選擇：快照多久拍一次？拍得勤，交易能看到別人最新提交的修改；拍得少，交易看到的資料前後一致，但會越來越舊。這個選擇就是隔離等級（isolation level）在決定的事情之一。每個交易開始時可以指定隔離等級，不指定就用預設的 READ COMMITTED。三個等級的快照拍法：

等級快照結果
READ COMMITTED（預設）每一句 SQL 開始時拍一張新的同一個交易裡，兩句之間別人提交的修改，第二句看得到
REPEATABLE READ、SERIALIZABLE交易裡第一句非交易控制的 SQL 開始時拍一張，之後整個交易都用它整個交易看到同一份資料，別人之後提交的修改都看不到

「第一句」三個字容易被忽略：快照不是在 BEGIN 那一刻拍的，而是在交易裡第一句真正讀寫資料的 SQL 開始時。BEGIN 之後、第一句之前別人提交的東西，你看得到。值班事故裡每個人只讀一次，看不出快照是什麼時候拍的、之後還會不會變，所以這裡先借一個會讀兩次的例子：店長跑報表、店員同時改拿鐵的價格。逐步看一次：

2UPDATE … SET price = 120;
COMMIT;		120
3SELECT price … → 120120
4UPDATE … SET price = 130;

讀到的都沒錯，結果卻錯了：這叫寫入偏差，哪個等級擋得住？

多個交易同時執行時，即使每個交易單獨看都正確，合起來仍可能得到錯的結果。這些錯誤結果有固定的名字，資料庫文件就是用這些名字說明每個隔離等級防住什麼。用咖啡店的情境各看一次，最後一列是開場的事故：

異常咖啡店情境
髒讀（dirty read）店長看到店員還沒提交、後來又取消的 999 元。PostgreSQL 在任何等級都不會發生
lost update兩位店員「先讀再寫」同一列庫存，後寫的蓋掉先寫的（第 19 課）
不可重複讀（non-repeatable read）同一個交易讀拿鐵價格兩次，一次 110、一次 120
幻讀（phantom read）同一個交易用同樣的條件數「今天的訂單」兩次，第二次多出一筆別人剛提交的
寫入偏差（write skew）阿明和小美都讀到「A 店有 2 人值班」，各改自己那一列為下班，合起來違反「至少 1 人值班」

前四種跟上一節的快照直接相關。髒讀剛才已經驗證不會發生。不可重複讀和幻讀，都是「同一個交易兩次讀取之間，別人提交了修改」：READ COMMITTED 每句拍新快照，所以會發生；REPEATABLE READ 整個交易用同一張快照，兩次讀到的一定相同，就是上一節時間軸步驟 5 看到的 120。

寫入偏差不一樣，它跟「看到的資料會不會變」無關。阿明和小美各自只讀一次，讀到的也都是正確的快照；問題在於兩人都根據「同一份資料」做判斷，然後各自改了不同的列。因為改的不是同一列，兩人之間沒有任何列鎖衝突，沒有人需要等誰，資料庫看不到它們之間有任何關係。

要判斷一個等級擋不擋得住寫入偏差，標準是可序列化（serializable）：幾個交易同時執行的結果，必須跟「把它們以某種順序一個一個排隊執行」的結果相同。違反這個標準的情況統稱序列化異常，寫入偏差是其中最典型的一種。PostgreSQL 18 文件的對照表（✗ 代表不會發生）：

等級髒讀不可重複讀幻讀序列化異常（含寫入偏差）
READ COMMITTED✗可能可能可能
REPEATABLE READ✗✗✗（SQL 標準允許，PostgreSQL 不會）可能
SERIALIZABLE✗✗✗✗

關鍵在最後一欄：PostgreSQL 的 REPEATABLE READ 給你一份不變的快照，但不保證結果跟排隊執行一樣。它有檢查一種衝突：兩個交易改到同一列時，後改的交易會先等前一個交易結束；如果前一個交易提交了，後改的就收到 could not serialize access due to concurrent update（40001）；如果前一個回滾，就照常更新。所以 lost update 不會悄悄發生。可是寫入偏差改的是不同的列，這個檢查不會觸發。

這就是開場問題的答案：阿明和小美遇到的是寫入偏差。預設的 READ COMMITTED 和 REPEATABLE READ 都擋不住；SERIALIZABLE 擋得住，做法是讓其中一個交易失敗，由程式重試。不改隔離等級的另一條路，是先鎖住兩人共同的那家店，後面會示範。表上的結論要親眼看過才算數，下一節把事故在這頁重現一次。

同樣的流程改用 SERIALIZABLE。在看結果之前，先了解它怎麼抓到這種「改不同列」的衝突，因為它的做法決定了程式之後要怎麼寫。

PostgreSQL 實作 SERIALIZABLE 的方法叫 SSI（Serializable Snapshot Isolation）。它不讓交易排隊，而是讓交易照常用快照執行，跟 REPEATABLE READ 一樣，同時在旁邊記帳：每個 SERIALIZABLE 交易讀過哪些資料，都會留下一筆紀錄，叫 SIReadLock（也叫述詞鎖，predicate lock）。名字裡有 Lock，在列出所有鎖的系統視圖 pg_locks 裡也看得到它，但它只是紀錄，不會擋住任何人。之後有交易修改資料時，SSI 會對照這些紀錄：「我要改的資料，有沒有別的交易讀過？」

用這個帳本看事故：阿明讀了 A 店的值班名單，裡面包含小美那一列；小美讀了同一份名單，裡面包含阿明那一列。接著阿明改了小美讀過的資料，小美也改了阿明讀過的資料。這兩個交易如果真的排隊執行：阿明先做，小美應該數到 1 人；小美先做，阿明應該數到 1 人。但兩人實際上都數到 2，不管排哪個順序都對不上，結果不可能等同排隊執行。SSI 發現這種情況時，就讓其中一個交易失敗。

💡 實務上：規則牽涉「別的列」時，就要想到寫入偏差
這類規則在產品裡很常見：會議室同一時段不能重複預約、每家店至少一人值班、一張優惠券全店限量 100 張、帳號至少保留一位管理員。它們的共同點是「先數別的列，再改自己的列」，平常測試一個人點不會出事，上線後兩個請求剛好同時到才會出現，而且資料庫不會報錯，常常是客服回報「怎麼兩個人都訂到同一間」才發現，就像這次店長打來的電話。資深工程師在看需求或 code review 時會多問一句：「這條規則是誰在保證？兩個請求同時進來會怎樣？」答案如果是「程式裡先查再判斷」，就要改成這課講的鎖住共同的父列、唯一約束或 SERIALIZABLE。

改成 SERIALIZABLE 之後，A 店不會再變成沒有人，但小美按下「我要下班」會收到一個錯誤。使用者不該看到這個錯誤，程式收到 40001 之後該做什麼？

小美的請求被拒絕了，程式該怎麼辦？重試整個交易

SERIALIZABLE 擋下寫入偏差的方式就是讓一個交易失敗，所以用了它，40001 一定會發生，程式一定要接住。40001 的意思不是「資料庫壞了」，而是「這個交易如果繼續，結果就不正確了，請重來」。正確的處理是從 BEGIN 開始重做整個交易，而且要重新讀取：用新的快照重新數值班人數、重新判斷。只重送失敗的那句 UPDATE 沒有用，交易已經中止；沿用第一次讀到的「2 人」再寫一次，更是把造成衝突的判斷原封不動做一遍。

上一節提過 REPEATABLE READ 改到同一列時的 could not serialize access due to concurrent update，它的 SQLSTATE 也是 40001，處理方式相同。

這次小美得到的是一個正確的業務結果：「A 店只剩你一位，不能下班」，而不是錯誤訊息。後端程式要自動做到這件事，就把「開交易 → 做事 → 提交」包成一個會重試的函式。下面用第 25 課的 node-postgres 寫法：

async function withRetry<T>(pool: Pool, work: (c: PoolClient) => Promise<T>, maxAttempts = 5): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    const client = await pool.connect()
    try {
      await client.query('BEGIN ISOLATION LEVEL SERIALIZABLE')
      const result = await work(client)   // 每次重試都重新執行：重新讀、重新判斷
      await client.query('COMMIT')        // COMMIT 本身也可能得到 40001
      return result
    } catch (err) {
      await client.query('ROLLBACK').catch(() => {})
      const code = (err as { code?: string }).code   // pg 的錯誤物件帶著 SQLSTATE
      const retryable = code === '40001' || code === '40P01'
      if (!retryable || attempt >= maxAttempts) throw err
      const wait = 50 * 2 ** (attempt - 1)              // 退避：50、100、200 ms…
      await new Promise(r => setTimeout(r, wait + Math.random() * wait))  // 加一點隨機量
    } finally {
      client.release()
    }
  }
}

這個函式有三個決定，各自對應一個問題：

  • 哪些錯誤值得重試（retryable 那一行）：除了 40001，還有 40P01，它是第 19 課死結（deadlock detected）的 SQLSTATE。死結時資料庫也是取消其中一個交易，處理方式一樣是重試整個交易。其他錯誤（例如違反約束）重試也不會變好，直接往上丟。
  • 重試幾次：重試（retry）要有上限（maxAttempts），超過就把錯誤往上丟，否則衝突一直發生時請求會永遠卡著。
  • 隔多久再試：退避（backoff）是每次等久一點並加一點隨機量（wait 那兩行）。衝突的兩個請求如果立刻同時重來，很可能又撞在一起；錯開時間才能讓其中一個先做完。細節見 系統設計第 8 課。

還有一個後果要注意：work 可能被執行好幾次，所以會被重試的交易裡不要做撤不回的事，例如寄信、呼叫金流扣款。資料庫的修改在 ROLLBACK 時會一起取消，寄出去的信不會；交易重來兩次，信就寄兩封。把這些事放到提交之後，或讓它們冪等。冪等（idempotent）是指同一件事做一次和做很多次結果相同，例如扣款時帶著同一個請求編號，金流收到重複的編號就不再扣，見 系統設計第 9 課。只讀的長報表和 SERIALIZABLE 搭配的兩個調整，見課末「補充與查表」。

💡 實務上：重試寫一次、放在共用的地方
專案裡通常只有一個 withRetry（用 ORM 時就包在它的交易 API 外面），所有需要 SERIALIZABLE 的程式都經過它，不要每支 API 各寫一套。重試的範圍是資料庫交易，不是整個 HTTP 請求：請求裡如果還呼叫了外部 API，重做整個請求就可能重複扣款。上線後在 log 記下重試次數，40001 突然變多，通常代表某個交易變長了或熱門資料衝突變多，是該檢查的訊號。測試時可以照上面的實驗，用兩個連線故意製造衝突，確認重試路徑真的會被走到。

值班事故用 SERIALIZABLE 加重試修好了。代價是每個會碰到這條規則的交易都要改隔離等級、都要經過重試函式。有沒有辦法留在預設的 READ COMMITTED，不用重試也防得住？

不改隔離等級也能防：先鎖住兩人共同的那家店

回想寫入偏差為什麼溜得過去：阿明和小美改的是不同的列，兩人之間沒有任何一列是共同的，所以列鎖從頭到尾沒有機會發生衝突。那就製造一個共同的列。兩人都屬於 A 店，stores 表裡 A 店那一列就是他們共同的「父列」。規定每個下班請求都要先用 FOR UPDATE 鎖住自己那家店，再數人數、再修改。這個做法叫鎖住共同的父列。英文常叫 materialize the conflict，意思是把原本看不見的衝突，變成一把實際存在、大家都要搶的鎖。

鎖上之後，同一家店的下班請求就會排隊：第一個人拿到店的鎖，第二個人在 FOR UPDATE 那一句等待，直到第一個人提交才拿到鎖。READ COMMITTED 每一句都拍新快照，所以第二個人拿到鎖之後的下一句「數人數」，看到的已經是第一個人提交後的結果：只剩 1 人，不能下班。不用 SERIALIZABLE 也防得住寫入偏差。

兩種修法的取捨：鎖住共同的父列要求每一段會影響規則的程式都記得先鎖，漏一處就破功，例如後台有人直接改排班卻沒先鎖店；SERIALIZABLE 不用記得鎖什麼，但每個交易都要能重試，衝突多時重試成本變高。規則只在一兩支 API 裡用到、而且有明顯的父列時，鎖父列比較直接；規則牽涉的列沒有共同的父列，或碰到它的程式很多時，SERIALIZABLE 比較不會漏。

值班規則有了兩種修法，審查清單上的下一條是集點兌換：顧客點數夠才能兌換，也是「先看點數夠不夠，再扣」。它需要 SERIALIZABLE 或鎖嗎？

集點兌換也是先判斷再扣，為什麼一句 UPDATE 就夠？

集點兌換和值班規則看起來很像，都是「條件成立才修改」。差別在條件讀的是哪一列：兌換的條件「點數 ≥ 5」讀的就是要修改的那一列，值班的條件讀的是同店別人的列。這個差別決定了預設的 READ COMMITTED 夠不夠用。

在 READ COMMITTED 下，UPDATE 遇到別人正在改的列，會等對方提交，然後拿那一列的最新版本重新檢查 WHERE 條件，條件還成立才更新（PostgreSQL 文件 13.2.1）。所以把判斷寫進 UPDATE 的 WHERE，兌換就是安全的。顧客 5 有 9 點，兩台收銀機同時兌換 5 點：

步驟收銀機 A收銀機 B已提交的點數
1UPDATE stamp_cards SET stamps = stamps - 5
WHERE customer_id = 5 AND stamps >= 5;		9
2同一句
等待中…		9
3COMMIT;等待中…4
4重新檢查最新版本：4 ≥ 5 不成立
影響 0 列		4 ✓

程式只要檢查「影響了幾列」：1 列代表兌換成功，0 列代表點數不足。反過來，「先 SELECT 點數、在程式裡判斷、再 UPDATE … SET stamps = 4」就是第 19 課的 lost update：兩台收銀機都讀到 9、都判斷夠、都寫入 4，顧客兌換了兩次卻只扣一次。

這個重新檢查只看被更新的那一列。值班規則的條件讀的是同店別人的列，那些列沒被鎖，也不會重新檢查。所以就算把值班規則寫成一句 UPDATE … WHERE (SELECT count(*) …) >= 2，在 READ COMMITTED 下兩個同店的人仍可能同時通過。判斷原則是：條件只讀要修改的那一列，一句原子 UPDATE 就夠；條件讀到別的列，就回到上兩節的 SERIALIZABLE 或鎖父列。

到這裡處理的都是已經存在的列：有列可以鎖、有列可以重新檢查。審查清單上的下一條卻是列還不存在的情況：顧客第一次消費要開集點卡。

第一次消費要開卡：列還不存在時，誰來當裁判？

集點卡的規則：顧客消費一次，沒有卡就開卡（1 點），有卡就加 1 點。這種「有就更新、沒有就新增」的操作叫 UPSERT（update 和 insert 合起來的說法）。直覺的寫法是先查再新增（check-then-insert）：先查有沒有卡，沒有才新增。顧客 7 還沒有卡，兩台收銀機同時替他結帳：

步驟收銀機 A收銀機 B顧客 7 的卡
1SELECT … WHERE customer_id = 7 → 0 列沒有
2SELECT … WHERE customer_id = 7 → 0 列沒有
3INSERT … (7, 1); COMMIT;1 點
4INSERT … (7, 1);
23505 或兩張卡		✗

前面的工具在這裡都使不上力。FOR UPDATE 只能鎖住查到的列，查到 0 列就什麼都沒鎖；READ COMMITTED 的重新檢查也只對已存在的列有效。列還不存在時，能當裁判的是唯一約束（第 12 課的 UNIQUE，主鍵也算）：資料庫保證同一個值只能有一列，兩個交易同時新增同一個 key，不管誰先誰後，最多只有一個成功。stamp_cards 的 customer_id 是主鍵，所以裁判已經在了，時間軸步驟 4 的 23505 就是它在攔。

剩下的問題是：被攔下的那一方，不應該收到錯誤，而應該改成「加 1 點」。INSERT … ON CONFLICT 就是做這件事的：先嘗試新增，撞到唯一約束時改做指定的動作。先看沒有它的情況。顧客 3 已經有 4 點，直接 INSERT 會撞 23505，執行後看錯誤碼：

並發時它為什麼安全？在 READ COMMITTED 下，文件保證每一列「不是新增就是更新」：另一個交易正在新增同一個 key 時，這句會等它結束，對方提交就改做 UPDATE，對方回滾就新增。上面時間軸的步驟 4 會變成「B 等 A 提交，然後把顧客 7 加到 2 點」，沒有錯誤，也不會有兩張卡。

有時候撞到了只想跳過，例如按讚、收藏：已經存在就什麼都不做。這時用 DO NOTHING。要注意 RETURNING 不會回傳被跳過的那一列，程式拿到 0 列，不代表出錯，而是「已經存在、這次沒動」：

💡 實務上：先有唯一約束，UPSERT 才有裁判
常見用途：購物車「再加一杯就數量 +1」、每日銷售統計表累加、按讚或收藏（DO NOTHING）、接收第三方 webhook 同步會員資料（同一筆可能送好幾次）。上線前要先確認唯一約束真的存在；對既有的表補加時，舊資料如果已經有重複，migration 會失敗，得先清掉重複資料。用 ORM 時看一下它的 upsert 實際產生的 SQL，有些寫法其實是「先查再新增」，就回到上面的競態。批次匯入前先在程式或 SQL 裡去重，避免 21000。

開卡處理的是一列一列的新增。審查清單的最後一條是一整份資料的同步：總部每週發的價目表，門市要照著有的更新、沒有的新增、停售的刪除。ON CONFLICT 只會在新增時改做更新，不會刪除，這需要另一個工具。

總部價目表同步：一整份資料有的更新、沒有的新增、停售的刪除

總部每週發一份價目表 hq_menu：拿鐵漲到 120、新增燕麥拿鐵、伯爵紅茶停售。門市的 products 要跟著同步。用 ON CONFLICT 做得到新增和更新，刪除還得另寫一句。MERGE（PostgreSQL 15 起）可以一句做完：拿一份來源資料（USING）和目標表比對（ON），比對到的叫 MATCHED，比對不到的叫 NOT MATCHED，每種情況各自指定要更新、刪除還是新增。

同步完通常要留一份紀錄：每一列做了什麼。PostgreSQL 17 起可以 RETURNING merge_action() 回傳每一列的動作。RETURNING 本身不能 ORDER BY，要排序就得把它放進資料修改 CTE。第 16 課的 CTE 在 WITH 裡放的是 SELECT；資料修改 CTE 是在 WITH 裡放 INSERT、UPDATE、DELETE 或 MERGE 加上 RETURNING，外層再查詢它回傳的列，就能排序、篩選。執行後看 action 欄，每一列做的是新增、更新還是刪除：

MERGE 長得像 UPSERT，但並發時不一樣。文件寫明：MERGE 要新增時，如果別的交易同時新增了同一個 key，它會直接得到唯一約束錯誤，不會像 ON CONFLICT 那樣改做更新。兩者不能互換：多人同時寫入的「有就更新、沒有就新增」用 ON CONFLICT；MERGE 適合單一程序跑的批次同步。

價目表同步每週只由一支排程跑一次，沒有別人同時新增同一個商品，所以用 MERGE 合適；開卡是多台收銀機同時寫入，就要用 ON CONFLICT。清單上的四條規則都有答案了，最後把結果整理成下次審查可以直接套用的表。

SERIALIZABLE 的兩個調整

交易越長越容易失敗。只讀的長報表可以用 BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE：開始時可能等一下，之後不會因序列化衝突失敗，也不會害別人失敗。另外，改用 SERIALIZABLE 之後，文件建議拿掉不再需要的 FOR UPDATE、FOR SHARE 與明確的鎖，它們只會增加等待。

練習

練習 1：A 店的阿明已經在 SERIALIZABLE 交易裡數過值班人數（2 人）、把自己改成下班，並按下暫停（PREPARE TRANSACTION 'amin'，已經在這題的資料庫裡準備好）。起始內容是小美的交易：數 A 店的值班人數、把自己改成下班、提交。選一個隔離等級，讓 PostgreSQL 拒絕這個交易（得到 40001），而不是讓兩人都下班。

練習 2：阿明已經提交下班（這題的資料庫已準備好）。小美（A 店）與小芳（B 店）的下班批次剛才收到 40001，現在重試：開一個新的 SERIALIZABLE 交易，用一句 UPDATE 讓兩人「只有在自己那家店除了自己以外還有人值班」時才改成下班，然後提交。

練習 3：顧客 3（已經有卡）和顧客 7（還沒有卡）各消費一次。用一句 SQL 完成：沒有卡就開卡（1 點），有卡就加 1 點。

練習 4：同樣是顧客 3、7 各集 1 點的 UPSERT，這次要回傳三欄：customer_id、這次是不是新開的卡（is_new，布林值）、集點後的點數，並依 customer_id 排序。用 PostgreSQL 18 的 RETURNING old／new。提示：RETURNING 不能排序，用資料修改 CTE。

練習 5：BEGIN ISOLATION LEVEL REPEATABLE READ 的交易，快照在什麼時候拍？

✓ 快照在第一句真正的查詢開始時拍，BEGIN 之後、第一句之前別人提交的修改看得到。b 是 READ COMMITTED 的行為；d 不對，提交時不拍快照。

練習 6：PostgreSQL 的 REPEATABLE READ 下，還可能出現哪一種異常？

✓ PostgreSQL 的 REPEATABLE READ 用同一份快照，所以不會幻讀（a 錯），任何等級都不會髒讀（c 錯）。但它不檢查讀寫依賴，寫入偏差這類序列化異常只有 SERIALIZABLE 擋得住（d 錯）。

練習 7：交易在 UPDATE 時收到 40001。程式該怎麼做？

✓ 收到 40001 後交易已中止，同一個交易裡的任何句子都會得到 25P02（b 錯）。40001 是預期中的衝突，不是故障（c 錯）。沿用舊資料等於把造成衝突的判斷再做一次（d 錯）。

練習 8：INSERT INTO stamp_cards … ON CONFLICT (customer_id) DO NOTHING RETURNING customer_id 回傳 0 列，代表什麼？

✓ DO NOTHING 跳過的列不會出現在 RETURNING。程式要把 0 列當成「已存在」處理；需要拿到既有那一列，就改用 DO UPDATE 或另外查詢。

常見錯誤

  • 以為包在 BEGIN／COMMIT 裡就不會有競態：交易保證全做或全不做，不保證兩個交易不互相影響。預設的 READ COMMITTED 擋不住 lost update，REPEATABLE READ 擋不住寫入偏差。
  • 以為條件寫進一句 UPDATE 就不會寫入偏差：重新檢查只看被更新的那一列。條件讀的是別人的列時，要 SERIALIZABLE 或先鎖住共同的父列。
  • 用了 SERIALIZABLE 卻沒寫重試：40001 一定會發生，沒有重試就是把它變成使用者看到的錯誤。重試時要重新讀取，不能沿用舊資料。
  • 會被重試的交易裡做撤不回的事：寄信、扣款放到提交之後，或做成冪等。
  • 很長的 SERIALIZABLE 交易：越長越容易衝突。交易保持短小；只讀的長報表用 READ ONLY DEFERRABLE。
  • 鎖父列只在一部分程式裡做：後台或批次程式沒先鎖同一家店，就會繞過保護。每一段會影響規則的程式都要先鎖；做不到就改用 SERIALIZABLE。
  • 先查再新增：兩個人同時查到「沒有」就會重複或撞 23505。加唯一約束，用 INSERT … ON CONFLICT。
  • ON CONFLICT 的欄位沒有唯一約束（42P10）、同一句裡 key 重複（21000）：先建好約束，批次資料先去重。
  • 期待 IDENTITY 連號：ROLLBACK 和 ON CONFLICT 都會跳號。
  • 把 MERGE 當成並發安全的 UPSERT：同時新增同一個 key 時 MERGE 會撞唯一約束錯誤，多人寫入用 ON CONFLICT。

小結

  • 快照決定交易看得到什麼：READ COMMITTED 每一句拍新快照；REPEATABLE READ／SERIALIZABLE 在第一句拍一張，整個交易都用它。別人還沒提交的修改，任何等級都看不到。
  • 值班事故是寫入偏差：兩個交易讀同一份資料、各改不同的列。PostgreSQL 的 REPEATABLE READ 不會幻讀，但擋不住寫入偏差；只有 SERIALIZABLE 保證結果等同排隊執行。
  • SERIALIZABLE 用 SSI 記錄讀過什麼（SIReadLock 不擋人），發現無法排成順序就讓一個交易得到 40001；收到 40001 或 40P01 就 ROLLBACK 後從頭重試、重新讀取，有上限、有退避。
  • 不改隔離等級的修法是先 FOR UPDATE 鎖住共同的父列（那家店），讓同店的請求排隊；代價是每段程式都要記得鎖。
  • READ COMMITTED 的 UPDATE 會用最新版本重新檢查 WHERE，所以集點兌換這種條件只讀同一列的原子更新是安全的；條件讀別人的列時就不夠。
  • 列還不存在時（開卡），交給唯一約束與 INSERT … ON CONFLICT；RETURNING old／new（18 起）分辨新增或更新；MERGE 適合價目表這種單一程序的批次同步，不能取代 ON CONFLICT。
