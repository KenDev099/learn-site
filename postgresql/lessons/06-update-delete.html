階段 1：CRUD（增查改刪） · 第 6 課

修改與刪除：UPDATE、DELETE

前幾課你一直在「讀」咖啡店的資料。這週店長丟來一張後台維護工單，全部都是要「改」資料：美式咖啡從 80 元調成 85 元、季節特調重新上架、甜點全面漲價 10%、一筆一直沒付款的訂單要清掉、王小明換了手機號碼。這些在後台介面上都只是按一下「儲存」或「刪除」，背後是 CRUD 的最後兩個字母：U（UPDATE，修改）和 D（DELETE，刪除）。

這兩個指令的語法很短，難的是「只改到你想改的那幾列」。SELECT 寫錯，頂多查出一堆不要的資料；UPDATE 和 DELETE 寫錯，資料就真的被改掉了，資料庫不會跳確認視窗，也沒有「復原」按鈕。這一課照著工單一張一張做，學完你會寫出修改和刪除的 SQL，也會養成一套動手前確認範圍、動手後確認結果的習慣。

這課會用到：
  • 第 4 課的 WHERE：寫一個條件，只留下符合條件的列；判斷 NULL 要用 IS NULL。
  • 第 3 課的 INSERT … RETURNING：新增之後，讓資料庫把剛寫進去的那一列回傳給你。
這課的路線：
  1. 美式咖啡調價：UPDATE 怎麼寫，怎麼確定只改到那一列；接著用同一招處理上架和甜點漲價。
  2. 少寫一行 WHERE 會怎樣：用交易當保護罩，安全地看一次整張表被改掉。
  3. 刪掉沒付款的訂單：DELETE 怎麼寫，以及訂單這種資料該不該真的刪。
  4. 改完之後怎麼知道改了什麼：RETURNING 讓 API 直接拿到結果，還能留下修改前的值。
  5. 要清空整張表時：沒有 WHERE 的 DELETE、TRUNCATE、DROP TABLE 差在哪。

美式咖啡要調成 85 元，怎麼只改到那一列？

工單第一張：美式咖啡從 80 元調成 85 元。修改既有資料用 UPDATE，它的形狀是這樣：

UPDATE 表
SET 欄位 = 新值, 欄位 = 新值
WHERE 條件;

三個部分各管一件事：UPDATE 後面寫要改哪張表；WHERE 決定改哪些列；SET 決定這些列的哪些欄位改成什麼值。WHERE 的寫法跟第 4 課 SELECT 用的完全一樣，所以你已經會一半了。

差別在後果。SELECT 的 WHERE 寫得太寬，只是多查出幾列；UPDATE 的 WHERE 寫得太寬，那些多出來的列會被真的改掉。所以在按下執行之前，先做一件不會改到任何東西的事：用 SELECT 加上同一個 WHERE，看看會被改到的是哪幾列。美式咖啡的 id 是 1，先查一次：

執行後先看結果區的「UPDATE，影響 1 列」，再看下面查到的價格是 85。影響列數是資料庫告訴你「我剛剛實際改了幾列」，這是事後確認範圍第一個該看的線索：預期改 1 列卻看到 17，就知道 WHERE 出事了。

為什麼這裡用 id 指定，而不是寫 WHERE name = '美式咖啡'？因為 id 是主鍵，資料庫保證每個值只會出現在一列，用它當條件，最多就改到一列。名稱沒有這個保證，哪天有人新增一個同名商品，兩列就會一起被改。用 LIKE '%拿鐵%' 這種模糊比對更危險，它會連抹茶拿鐵一起改到。後端 API 也是這樣設計的：前端呼叫 PATCH /products/1（PATCH 代表只改傳來的欄位，這裡就是價格），路徑裡的 1 就是 id，後端組成 WHERE id = 1。

季節特調重新上架：一次改兩個欄位

第二張工單：季節特調要重新上架，價格同時改成 170。上架和調價是同一列的兩個欄位，不用寫兩句 UPDATE，在 SET 後面用逗號把它們隔開就好。這裡用名稱當條件，是因為示範資料裡季節特調只有一列；真實的後台會用 id。

兩個欄位在同一句裡一起改好。分隔用的是逗號，不是 AND：寫成 AND 不一定會報錯，卻會存進錯的值，原因放在「常見錯誤」。

甜點全部漲價 10%：用欄位自己的值計算

第三張工單比較麻煩：分類是甜點的商品每一樣都漲 10%。每樣甜點的原價都不一樣，沒辦法寫成一個固定的 SET price = 某個數字。SET 的右邊可以是運算式，而且可以用到欄位本身：price = price * 1.1 的意思是「每一列都拿自己原本的價格乘以 1.1，再存回去」。各列只看自己的值，不會受其他列影響。

💡 實務上：批次調價是一份要給人看過的 SQL
咖啡店全面調價時，常見的做法是把 UPDATE 連同「SELECT 預覽的結果、預期影響幾列」貼到工單或 PR，請另一位同事看過再執行。動手前先跟 PM 確認：什麼時候生效？已成立的訂單要不要跟著變？通常不要，所以訂單會自己存一份當時的金額（像 orders.total），改商品價格不會影響舊訂單。漲 10% 之後 93.5 要算 93 還是 94，是業務規則，要跟 PM 或會計講好，不要交給資料型別碰運氣決定。

三張工單都靠同一個 WHERE 把範圍框住。那如果 WHERE 寫錯，甚至整行忘了寫呢？

少寫一行 WHERE 會怎樣？

前面三句 UPDATE 都寫了 WHERE，但 UPDATE 和 DELETE 的 WHERE 其實是可以省略的，省略的意思是「整張表每一列」。這不是語法錯誤，資料庫也不會問「確定嗎？」，它會直接照做。

最常見的出事方式不是不懂語法，而是手滑：在資料庫工具裡寫到一半，WHERE 那行還沒打完就按了執行；或是選取要執行的 SQL 時，只選到上面兩行。這一頁直接執行這種 SQL，整間店的價格就真的變成 0 了。要安全地看一次會發生什麼事，需要一個能「反悔」的機制。

這個機制叫交易（transaction）。平常每一句 SQL 執行完就立刻正式生效；先執行 BEGIN 開始一段交易之後，接下來的修改都先算「暫定」，最後用 COMMIT 確認寫入，或用 ROLLBACK 把這段期間的修改全部撤銷，回到 BEGIN 之前的樣子。交易還有很多能力，第 18 課會細講，這一課只用它的「撤銷」。下面這格故意忘了 WHERE，再用 ROLLBACK 救回來：

看兩個結果：第一個 SELECT 是在交易裡查的，所有商品的價格都是 0；ROLLBACK 之後的第二個 SELECT，價格又全部回來了。

真實世界通常沒有這個保護罩。你沒有先寫 BEGIN，在資料庫工具裡直接按下執行，改動在那一刻就已經寫進去了。這時唯一的辦法是從備份把資料救回來，而備份到出事之間的新資料（例如這段時間的新訂單）可能就跟著不見了。所以真正的保護不是事後補救，而是動手前的習慣：

保命習慣
  1. 先寫 WHERE，再寫前面的 UPDATE … SET／DELETE FROM。
  2. 先用 SELECT 跑同一個 WHERE，確認列數和內容。
  3. 執行後看「影響幾列」跟預期一不一樣。
  4. 在正式資料庫手動改資料時，先 BEGIN，確認無誤才 COMMIT。

第 1 條的意思是：就算手滑在半途按了執行，沒寫完的 SQL 也只會是語法錯誤，不會變成沒有條件的 UPDATE。這四條對 DELETE 一樣有效，而且更重要：UPDATE 改錯了，至少列還在；DELETE 刪錯了，列就整個不見了。下一張工單就是刪除。

沒付款的訂單 118，怎麼刪掉？該不該真的刪？

工單第四張：訂單 118 一直是 pending（未付款）狀態，店長要把它刪掉。刪除整列用 DELETE：

DELETE FROM 表
WHERE 條件;

跟 UPDATE 比，DELETE 少了 SET，也不用寫欄位。因為 DELETE 的單位是整列：一列要嘛整列留下，要嘛整列消失，沒有「刪掉某一欄」這回事。如果你想清掉的是某一欄的值（例如顧客要求不要留電話），那是修改，要用 UPDATE 把它設成 NULL。

確認是那筆 pending 訂單，再把 SELECT * 換成 DELETE，執行後再查一次：

第二次查已經是 0 列，這筆訂單不在了。跟 UPDATE 一樣，WHERE 省略就是全部：DELETE FROM orders; 會把整張訂單表的資料刪光，表本身還在，只是變成空表。

語法學會了，但這張工單本身值得多想一下。訂單被刪掉之後，月底的營業額報表、和金流對帳時就再也找不到它；如果客人之後來問「我那筆訂單呢」，也查不到任何紀錄。所以實務上，重要的資料多半不會真的 DELETE。

那不 DELETE，要怎麼讓它「消失」？做法叫軟刪除（soft delete）：資料列留著，只是在某個欄位上做記號。做記號就是改一個欄位的值，所以軟刪除其實就是一句 UPDATE。常見寫法是在表上加一個 deleted_at 欄位，平常是 NULL，「刪除」時填入當下的時間：

UPDATE orders
SET deleted_at = now()
WHERE id = 118;

（本課的練習資料沒有 deleted_at 這個欄位，這句只是示意，不能在上面執行；加欄位的方法在後面的課會教。）now() 是取得當下時間的函式，填時間而不是填 true，好處是順便記下了「什麼時候刪的」。

資料還在表裡，所以之後每個要給前台、報表看的查詢，都要自己把它排除：

SELECT * FROM orders
WHERE deleted_at IS NULL;

判斷 NULL 要用 IS NULL，不能寫 = NULL，這是第 4 課講過的規則。回到訂單 118 這張工單：在真實系統裡，比較可能的處理是把它的 status 改成 'cancelled'（訂單本來就有狀態欄位，「取消」也是一種狀態），或寫入 deleted_at，而不是像上面那樣 DELETE。上面直接刪，是為了讓你學會 DELETE 的語法和它的後果。

💡 實務上：軟刪除的代價，以及什麼時候必須真的刪
軟刪除的代價是：之後每一個查詢都要記得加 WHERE deleted_at IS NULL，漏一個，前台就會冒出已刪除的商品，報表也會多算。反過來，會員要求刪除個資時，留著記號不算刪除，就要真的刪掉或把個資抹除，這時要問法務和資安該保留什麼、刪到什麼程度。

到這裡，工單的 SQL 都會寫了。但這些 SQL 在真實系統裡不是你手動執行的，而是後端 API 收到前端請求後去執行。API 執行完 UPDATE，要回給前端什麼？它又怎麼知道有沒有真的改到東西？

改完之後，API 怎麼知道改了什麼？RETURNING

最後一張工單：王小明換了手機號碼。在真實的系統裡，這是王小明自己在會員頁按「儲存」，前端呼叫 PATCH /customers/1，後端執行一句 UPDATE。前端畫面接著要顯示更新後的資料，所以 API 要把最新的那一列回傳給前端。

直覺的做法是 UPDATE 完再 SELECT 一次，但這樣要跟資料庫來回兩趟。第 3 課在 INSERT 用過的 RETURNING，在 UPDATE 和 DELETE 也能用：寫在句尾，資料庫會把被改到、被刪掉的那些列直接回傳給你，欄位可以挑，寫 RETURNING * 就是整列。

結果直接是改完之後的那一列，電話已經是新號碼。一句 SQL 同時完成「修改」和「拿到最新資料」。

RETURNING 還順便回答了「有沒有改到」：它回傳幾列，就代表改到了幾列。如果回傳 0 列，代表 WHERE 沒有對到任何一列，也就是這個 id 不存在，或已經被別人刪掉了。這時 API 應該回 404，而不是回一個空的成功。

💡 實務上：old／new 寫進異動紀錄表
上面拿到的 old.／new. 值，實務上會寫進一張異動紀錄表（常叫 audit log）。這張表通常有這幾個欄位：改了哪張表、哪一列（表名和 id）、哪個欄位、舊值、新值、操作者（哪個員工或會員帳號）、時間。會來查它的人，是客服（「客人說他沒改過電話」）、老闆或店長（「這價格是誰改的」），以及出問題時要追原因的工程師。重點是在修改的同一時間寫進去，事後才補就不可信了。

工單到這裡都做完了，每一句都只改、只刪特定的幾列。但有一種情況是真的想要「全部」：例如測試環境的訂單表要整個清空重來。這時有三種寫法，結果看起來很像，差別卻很大。

真的要清空整張表時：DELETE、TRUNCATE、DROP TABLE 差在哪？

第一種你已經知道了：沒有 WHERE 的 DELETE FROM orders;，它會一列一列把資料刪掉。第二種是專門用來清空的指令：

TRUNCATE orders;

效果跟沒有 WHERE 的 DELETE 一樣，表還在、資料全沒了。差別在做法：TRUNCATE 不逐列刪除，而是直接丟掉整份資料，所以表很大的時候快很多。它也沒有 WHERE 可以寫，只能整張清空。

第三種是 DROP TABLE，它跟前兩種不是同一件事：TRUNCATE 清空資料、表還在；DROP TABLE 連表一起刪掉，欄位定義也沒了，之後要用得重新 CREATE TABLE。四種寫法整理如下：

指令刪什麼表還在嗎
DELETE FROM t WHERE …符合條件的列在
DELETE FROM t全部的列（逐列刪）在
TRUNCATE t全部的列（整批丟掉）在
DROP TABLE t整張表，連結構一起不在

表裡後三種都是「全部」，在正式環境都很危險。清空測試資料時，先確認自己連的是哪一個資料庫，不是正式環境，再執行。

補充與查表

  • old.／new. 的版本要求：RETURNING 裡的 old.、new. 是 PostgreSQL 18 才開始有的寫法。要拿它寫異動紀錄之前，先確認公司資料庫已經是 PostgreSQL 18，雲端託管的版本常常會落後幾版。

常見錯誤

  • 忘了 WHERE：整張表被改掉或刪光，而且不會報錯。先寫 WHERE，再寫前面的 UPDATE … SET／DELETE FROM。
  • WHERE 範圍比想的大：用 LIKE '%拿鐵%' 連抹茶拿鐵一起改到。先用 SELECT 跑同一個 WHERE 看一下，能用 id 就用 id。
  • WHERE phone = NULL：跟查詢一樣永遠不成立，結果是「影響 0 列」。用 IS NULL。
  • SET 多個欄位用了 AND：SET price = 150 AND name = '…' 會被當成「把 150 AND name = '…' 這整個運算式的結果放進 price」，出現 argument of AND must be type boolean 這種看不太懂的錯誤。更糟的是第一個欄位剛好是 boolean 時，它不會報錯，只會默默存進錯的值、另一欄也沒改到。多個欄位要用逗號分隔。
  • DELETE 寫了欄位：DELETE name FROM customers 是語法錯誤；要清掉某一欄的值，用 UPDATE … SET name = NULL。
  • 以為 RETURNING 能復原：它只回傳被改到、被刪掉的列給你看。能撤銷的是交易的 ROLLBACK，而且要在 COMMIT 之前。

小結

  • UPDATE 表 SET 欄 = 值, … WHERE 條件;：WHERE 決定改哪些列，SET 決定改哪些欄位；多個欄位用逗號，右邊可以用欄位自己原本的值計算（price = price * 1.1）。
  • DELETE FROM 表 WHERE 條件; 刪除整列；只想清掉某一欄的值，用 UPDATE 設成 NULL。訂單、會員這類資料多半用軟刪除。
  • WHERE 省略就是全部，資料庫不會確認：先寫 WHERE、先用 SELECT 跑同一個 WHERE、執行後看影響列數；正式環境手動改資料時，先 BEGIN，確認無誤才 COMMIT，錯了就 ROLLBACK。
  • RETURNING 回傳被改到或刪掉的列，API 不用再查一次，回傳 0 列就是沒對到（回 404）；PostgreSQL 18 可以用 old.／new. 拿到修改前後的值。
  • 清空整張表：TRUNCATE 整批丟掉資料、表還在；DROP TABLE 連表一起刪掉。
