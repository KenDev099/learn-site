階段 10：資深必備｜上線與維運 · 第 36 課

連線、權限與監控：資料庫的上線設定

咖啡店的 API 要正式上線了。開發時一切順利：一台筆電、一個資料庫、App 用 postgres 帳號連線，什麼都做得了。上線後的頭幾週卻接連出了三件事：

  1. 週末尖峰：App 開始回錯誤，log 裡寫著 sorry, too many clients already。
  2. 某次部署之後：migration 新增了 gift_cards 表，App 一查就 permission denied。
  3. 某天晚上 21:30 左右：整個網站變慢，大家盯著 CPU 圖看了半小時，CPU 卻很閒；最後才發現是一條忘了 COMMIT 的連線。

三件事都跟 SQL 寫得好不好無關，而是資料庫的上線設定沒做好：該開幾條連線、App 用哪個帳號連線、替它加哪些限制、出事時去哪裡看。這一課把三件事故依序查到根因、修好，再留下讓它不再發生的設定。學完你手上會有一份上線檢查清單：連線預算、三個角色與預設權限、設在角色上的逾時護欄，以及一組出事時先跑的健康檢查 SQL 和告警門檻。

這課的路線：
  1. 事故一：連線為什麼會用完、該開幾條（第 1 節），以及在資料庫前面放了 pooler 之後，哪些寫法會悄悄出錯（第 2 節）。
  2. 事故二：App 該用哪個角色連線，下一張新表怎麼自動帶權限（第 3 節）。
  3. 事故三：怎麼從 pg_stat_activity 找出那條沒 COMMIT 的連線（第 4 節），再用角色上的逾時設定讓它不再發生（第 5 節）。
  4. 平常就該看的數字：快取命中率、暫存檔、沒用的索引、凍結年齡，以及數字不好時調哪個記憶體參數（第 6 節）。
  5. 告警：哪些指標超過門檻要自動通知人，出事時先跑哪幾句（第 7 節）。
這課會用到：
  • 第 25 課的 connection pool 與 pooler：connection pool（連線池）保留一批連線重複借用，數量最多到上限（例如 max: 10）；Supabase 的 6543 port 是 transaction 模式的 pooler，每個交易結束就把連線還給別人用。
  • 第 24 課的 role 與 RLS：GRANT 把權限給某個 role，SET ROLE 暫時切換成另一個 role；超級使用者和表的擁有者預設繞過 RLS；set_config(…, true) 設一個只在這個交易有效的值，讓 RLS 知道現在是誰。
  • 第 29 課的設定參數與 pg_stat_statements：SET 改這條連線之後的所有交易，SET LOCAL 只改這個交易；work_mem 是每個排序、雜湊步驟可用的記憶體；pg_stat_statements 累計每句查詢的執行次數與時間。
  • 第 32 課的逾時設定與 pg_stat_activity：statement_timeout、lock_timeout 這類設定替執行和等待設上限；pg_stat_activity 每列是一條連線，idle in transaction 是交易開著卻沒在執行查詢。
這頁的環境：資料庫是 PGlite 0.5.13（PostgreSQL 18.6），只有一條連線：max_connections 顯示 100 但沒有意義，連線狀態用快照表看。逾時設定不會觸發；角色層級設定要真的登入才套用，這頁只看得到設定、看不到效果。

這頁的資料：customers、products、orders（2 萬筆，有好幾個索引，其中幾個從來沒被用過）；三個角色 migrator、app_user、report_reader；以及兩張監控快照表：activity_samples（事故三那晚 21:30 的 pg_stat_activity，第 4 節用）和 db_stats_samples（同一晚 21:00 與 22:00 兩次 pg_stat_database，第 6 節用）。頁面啟動時已經跑過一小段固定的工作量，讓統計有東西可看。

事故一：連線為什麼會「用完」？

週末尖峰的錯誤訊息是 too many clients already：資料庫說「客戶太多了」，拒絕了新的連線。要知道連線為什麼會用完、為什麼不能無限開，得先看 PostgreSQL 收到一條連線時做了什麼。

作業系統每執行一個程式，就替它開一個程序：程序有自己的一塊記憶體，由作業系統安排輪流使用 CPU。你寫的 Node API 通常就是一個程序，裡面靠事件迴圈同時處理很多請求。PostgreSQL 的做法不同：它每接受一條連線，就另外開一個新的程序專門服務這條連線，一直到連線斷開為止。100 條連線，資料庫主機上就有 100 個這樣的程序。

所以一條連線不是一個便宜的「通道」，而是一個真的在主機上佔資源的程序。它的代價有三個層面。

第一，每條連線都有自己的記憶體。閒置時佔得不多，但查詢開始排序、雜湊時，每個排序或雜湊步驟各自可以用到 work_mem（第 29 課），雜湊步驟還可以用得更多（細節見課末「補充與查表」）。一句報表查詢可能有好幾個這種步驟，100 條連線同時跑報表時，用量大約是「連線數 × 每句查詢的步驟數 × work_mem」。連線開得越多，最壞情況下的記憶體用量就跟著乘上去。

第二，同時在做事的連線多了，反而變慢。一台 8 核心的機器，同一瞬間只能真的執行 8 件事。第 9 個以後的程序只能排隊等 CPU；作業系統在程序之間切換本身也要花時間；這些程序還會搶同一批磁碟、同樣的資料頁、同樣的鎖。想像咖啡店吧台只有兩位咖啡師：讓 20 位客人一起擠進吧台，不會多做出咖啡，只會讓大家互相卡住。資料庫也一樣，超過某個數量之後，每秒能完成的交易數（吞吐量）會下降，而不是持平。

第三，總數有硬上限。這個上限是設定參數 max_connections，預設 100。連線數到上限時，新的連線直接被拒絕，錯誤訊息就是事故一看到的 too many clients already。上限裡另外保留了 superuser_reserved_connections 條（預設 3）給超級使用者，讓你在連線被占滿時還能登入處理；所以一般角色在只剩最後 3 條時就已經被拒絕，看到的是 remaining connection slots are reserved for roles with the SUPERUSER attribute。兩種訊息意思相同：連線用完了。

該開幾條連線？算出事故一的連線數

既然連線多了反而慢，那「同時在做事」的連線該有幾條？PostgreSQL wiki 給的起點公式是 (CPU 核心數 × 2) + 有效磁碟數：8 核心、SSD 的機器大約 17～20 條。注意它算的是同時在執行查詢的連線，不是開著的連線總數；這只是起點，要用壓力測試調整。重點是這個數字遠比直覺小。

事故一的問題在乘法。第 25 課的 new pg.Pool({ max: 10 }) 是每個程序各自一個池子：一個 API 容器裡有一個池子，最多開 10 條；容器變多，池子就跟著變多。把咖啡店的部署一行一行加起來：

部署方式連線數
API 跑 6 個容器，每個 max: 1060
再加上 2 個 worker（第 33 課的工作佇列），每個 max: 1080
尖峰時自動擴展成 12 個 API 容器140，超過 100，新連線被拒絕
Serverless 函式，同時 300 個實例、每個 max: 1300

第三列就是事故一：平常 6 個容器加 worker 只有 80 條，週末自動擴展成 12 個容器，連線數跟著衝到 140，超過 max_connections。每個容器自己看都只開了 10 條，沒有人覺得自己開太多。

直覺的修法是把 max_connections 調到 2000，但這正好踩中前面的第一、第二點：程序更多、記憶體更多、互相搶得更兇，資料庫反而更慢。真正的解法是讓「App 那邊的連線」和「資料庫實際的連線」脫鉤：在資料庫前面放一個 pooler。

pooler 是一個獨立的程式，站在 App 和資料庫中間。App 以為自己連的是資料庫，其實連的是 pooler；pooler 自己只對資料庫開少量的連線，誰需要就借給誰。為了說清楚，這課把 App 連到 pooler 的叫客戶連線，pooler 連到資料庫的叫伺服器連線。客戶連線可以很多、很便宜；伺服器連線才是資料庫上真的程序。常見的 pooler 有 PgBouncer，以及 Supabase 的 Supavisor。放了 pooler 之後，max_connections 設得比 pooler 開出的伺服器連線總數大一些，留給維運工具、migration 和你自己登入查問題。

💡 實務上：上線前先列一張「連線預算」
咖啡店 API 要上線或改自動擴展設定時，資深工程師會先把所有會連資料庫的東西列出來：API、worker、排程、報表工具、migration、自己登入查問題的那條，各乘上「最多幾個實例 × pool max」，用的是擴展上限，不是平常的實例數。加總超過資料庫能承受的數量，就該放 pooler 或調小每個 pool，而不是先去調 max_connections。用 Supabase、Neon 這類託管服務時，控制台通常會給兩組連線字串（經過 pooler 的和直連的），API 和 serverless 用 pooler 那組，migration 和需要 LISTEN 的 worker 用直連。改部署設定的 PR 裡看到容器數量（replicas）或 pool 的 max 變了，就該順手問一句：連線數算過了嗎？

pooler 能省下連線，是因為它會把同一條伺服器連線輪流借給不同的客戶。但「輪流借」也有代價：有些東西是跟著伺服器連線走的，換人時會留給下一位，下一節就看哪些寫法會因此出錯。

放了 pooler 之後，哪些寫法會悄悄出錯？

上一節說 pooler 會把伺服器連線輪流借給不同的客戶。它在什麼時間點把連線收回、交給下一位，由 pooler 的模式決定：

模式伺服器連線什麼時候換人省連線的效果限制
session客戶斷線時小：客戶連著不放就一直佔一條幾乎沒有，行為和直連一樣
transaction每個交易結束時大：只有「交易進行中」才佔連線下一張表
statement每一句結束時最大不能用多句的交易，很少用

session 模式省不了多少：App 的連線池本來就會一直連著，等於每條客戶連線還是佔一條伺服器連線，事故一照樣會發生。所以最常用的是 transaction 模式（Supabase 的 6543 port 就是）：App 的連線大部分時間在等下一個請求，只有交易進行中才真的需要資料庫，transaction 模式就只在這段時間借出伺服器連線。

代價是：你這個交易和下一個交易，不一定拿到同一條伺服器連線。PostgreSQL 有一些東西是記在「連線」上、跨交易一直留著的，因為每條連線就是一個程序，程序會記得自己之前做過什麼。在 transaction 模式下，這些東西會留在那條伺服器連線上，你的下一個交易卻可能已經到了別條。PgBouncer 文件列出 transaction 模式下不能用的功能：

不能用為什麼改成
SET／RESET設定留在那條伺服器連線上，會「漏」給下一個客戶SET LOCAL 或 set_config(…, true)，交易結束自動還原
LISTEN通知送到那條伺服器連線，你下一個交易可能已經不在上面聽通知的 worker 直連資料庫或走 session 模式（第 33 課）
session 級 advisory lock鎖跟著連線，交易結束後會留在別人的連線上pg_try_advisory_xact_lock（第 33 課）
WITH HOLD cursor跨交易保留結果改用分頁查詢
SQL 的 PREPARE／DEALLOCATE預備陳述式存在連線上用驅動程式的協定層預備陳述式（見課末）

這張表裡，LISTEN 和 advisory lock 用錯時通常會很快壞掉、被發現。最危險的是第一列的 SET：它本身不會報錯，卻可能讓資料跑錯人。

用咖啡店接下來的計畫說明。咖啡店準備開分店，每間分店的店員只能看自己分店的訂單。做法和第 24 課相同：第 24 課用 set_config('app.user_id', …) 告訴 RLS 現在是哪位顧客；分店版改成 app.store_id，RLS 條件寫 store_id = current_setting('app.store_id')::int（第 38 課會完整做出來）。每個請求開頭先告訴資料庫「現在是哪間店」，再查 orders。如果這一步寫成連線層級的 SET，在 transaction 模式下會這樣：

步驟請求 A（分店 5）請求 B（分店 7）伺服器連線
1SET app.store_id = '5';A 借 S1 → 還回
2SELECT * FROM orders;
報錯		A 借 S2（沒有設定）
3SELECT * FROM orders;
看到分店 5 的訂單		B 借 S1（還留著 5）
4BEGIN;
SELECT set_config('app.store_id', '7', true);
SELECT * FROM orders;
COMMIT;		B 整個交易都在 S2，結束後設定清掉

回頭看這四步，同一個錯誤產生了兩種後果。第 2 步是「吵的」：A 的請求直接報錯，至少會被看見。第 3 步是「安靜的」：B 拿到了別間分店的資料，沒有任何錯誤訊息，log 裡什麼都沒有。安靜的那種才可怕，它可能要等客戶抱怨才被發現。

修法是第 4 步：設定和查詢放在同一個交易，設定用 set_config(…, true)（等於 SET LOCAL）。整個交易都在同一條伺服器連線上，COMMIT 時設定自動消失，不會漏給下一位。所以第 38 課做多租戶時，app.store_id 一律在每個交易開頭用 set_config(…, true) 設定。

到這裡事故一處理完了：連線數用 pooler 控制，transaction 模式下改用交易內的設定。不過分店的資料能不能真的被 RLS 隔開，還有一個前提：App 連線用的那個角色，RLS 管不管得到它。這就是事故二的起點。

事故二：App 該用哪個角色連線？

上一節靠 RLS 隔開各分店的資料，但 RLS 只對「受它管的角色」有效。咖啡店開發時，大家都用 postgres 連線，因為什麼都能做；上線時照搬這個設定，就是最危險的做法。有兩種角色 RLS 管不到：

  • 超級使用者跳過所有權限檢查，也永遠繞過 RLS。一個 SQL injection（第 25 課）就能 DROP TABLE，甚至在伺服器上執行指令。
  • 表的擁有者，也就是建立那張表的角色，能 ALTER、DROP、TRUNCATE，而且預設也繞過 RLS（第 24 課）。如果 App 用擁有者連線，RLS 等於沒開。

所以「建表的人」和「用表的人」要分開。常見的做法是分成三個角色，每個只拿到它的工作需要的權限：

角色誰用權限
migrator部署時跑 migration（第 22 課）擁有所有表，可以改結構；密碼只放在 CI／部署環境
app_userAPI 和 worker只能讀寫資料（SELECT、INSERT、UPDATE、DELETE）；不是擁有者，所以 RLS 對它有效
report_reader報表工具、資料分析只能 SELECT

這頁的 seed 已經照這個分法建好：表的擁有者是 migrator，現有的表也 GRANT 給了另外兩個角色。要確認權限設得對不對，不用真的切換成每個角色去試，PostgreSQL 有兩個函式直接回答「某個角色有沒有某種權限」：has_table_privilege(角色, 表, 權限) 問表，has_schema_privilege(角色, schema, 權限) 問 schema，回傳 true 或 false。執行後先看第一個結果的 tableowner，再看第二個結果每個角色能做什麼：

「可建表」那一欄跟 schema 的權限有關。schema 是表的資料夾，public 是預設的那一個。角色要使用一個 schema 裡的東西，先要有那個 schema 的 USAGE 權限；要在裡面建表，還要有 CREATE。現在的 PostgreSQL 預設不讓一般角色在 public 建立物件（從哪一版開始見課末版本備註），所以這裡只有被明確給了 CREATE 的 migrator 能建表。

下一張新表為什麼 permission denied？預設權限

事故二是這樣發生的：上線時有人執行了 GRANT … ON ALL TABLES IN SCHEMA public，把現有的表都給了 app_user，當時一切正常。下個月 migration 新增 gift_cards，App 一查就 permission denied。原因是 ON ALL TABLES 只處理執行當下已經存在的表，它不是一條「以後都這樣」的規則。下面這格先 GRANT，再模擬下一次 migration 建表，執行後比較兩張表的 report_reader_可讀：

orders 可讀、gift_cards 不可讀，事故二重現了。要讓「之後建立的物件」自動帶權限，要用另一種設定：預設權限（default privileges）。寫法是 ALTER DEFAULT PRIVILEGES … GRANT 權限 ON TABLES TO 角色，意思是「以後建立的表，一建好就自動 GRANT」。

它有一個陷阱：預設權限是綁在「建立物件的那個角色」身上的，只有那個角色建的表才會套用。下面這格由 postgres 執行，沒有指定是誰建的表，執行後看兩個結果：

表是 migrator 建的，預設權限卻掛在 postgres 身上，所以沒有作用。要讓它套用在 migrator 建立的表，要寫 ALTER DEFAULT PRIVILEGES FOR ROLE migrator …。練習 1 會用到。（defaclacl 欄位的讀法見課末。）

上線時兩個一起用：對現有的表 GRANT … ON ALL TABLES 一次，同時設定 ALTER DEFAULT PRIVILEGES FOR ROLE migrator 管之後的表。一個管過去、一個管未來，事故二就不會再發生。

💡 實務上：權限設定寫進 migration，本機也用 app_user 跑
建角色、GRANT、ALTER DEFAULT PRIVILEGES 應該和建表一樣寫成 migration 進版控（密碼除外，密碼由部署環境另外設定），不要在正式機上手動下指令，否則換一台新環境（測試機、災難復原）就少了這些權限。另一個常見的坑是本機開發一律用 postgres 連線，權限問題要到上線才爆；讓本機和 CI 的 App 也用 app_user 連線，新表忘了給權限時測試就會失敗。migrator 的密碼只放在部署環境的密鑰管理裡，工程師平常查資料用 report_reader，需要改資料時走有紀錄的流程。資安稽核或客戶問卷常問「誰能刪資料」，這三個角色的表就是答案。

角色解決的是「連上之後能做什麼」。連線本身在網路上怎麼加密、密碼怎麼驗證，也是上線設定的一部分，但跟這次的事故無關，放在課末「補充與查表」。

事故三：網站變慢時，怎麼找到那條沒 COMMIT 的連線？

前兩件事故都有明確的錯誤訊息；第三件沒有。那天晚上網站變慢，大家先看 CPU 圖，看了半小時卻看不出問題，因為 CPU 只告訴你機器忙不忙。這次的狀況是很多請求在「等」：等一把被別人拿著的鎖。等待中的程序不吃 CPU，所以 CPU 圖很平靜。要看的是每條連線此刻在做什麼，也就是第 32 課看過的 pg_stat_activity。

先查這頁真的 pg_stat_activity，執行後看有幾列：

只有一列（standalone backend）：這頁只有一條連線（課首的環境說明），看不出事故。所以下面改用快照表 activity_samples，它是事故那晚 21:30 的 pg_stat_activity，欄位相同，多了取樣時間 captured_at。

拿到這份清單，先看 state 欄。它是這條連線此刻的狀態，最常見的三種：

  • active：正在執行一句查詢。
  • idle：連線開著，在等 App 送下一句。連線池裡的連線平常就是這樣，正常。
  • idle in transaction：交易已經 BEGIN 了，卻沒在執行任何查詢，也還沒 COMMIT。可能是 App 在交易中間去做別的事（呼叫外部 API、等使用者），也可能是程式某條路徑忘了 COMMIT。

前兩種是正常的；第三種是要找的。它只要開著，交易裡拿到的鎖就一直不放，別的請求碰到同一列只能排隊等；它也擋住 VACUUM 清理死版本（第 30 課）。執行後看各狀態的連線數：

欄位意思

第二列和第三列正好說明為什麼要分清楚兩個時間欄位：只看 xact_start，兩條看起來差不多；看 state_change 才知道哪一條是真的卡住。usename 和 application_name 告訴你這條連線屬於誰：app_user 加 cafe-api，就知道要去翻 API 的程式。application_name 是 App 連線時自己報的名字，在連線字串加上 ?application_name=cafe-api 就會出現在這裡；沒設的話所有服務看起來都一樣，出事時很難分辨是誰。練習 3 會用 state_change 列出所有閒置超過 5 分鐘的連線。

找到禍首之後，當下的止血方法是 SELECT pg_terminate_backend(pid)：結束那條連線，它的交易被回滾，鎖跟著釋放，排隊的請求就能繼續。

但結束連線只是止血。App 某處漏了 COMMIT 的程式還在，下次還會再犯；而且這次是人盯了半小時才找到的。能不能讓資料庫自己把這種連線清掉？

怎麼讓它不再發生？替 app_user 設逾時護欄

上一節的問題，資料庫自己就有對應的設定。第 32 課介紹過四個逾時設定。第四個是 PostgreSQL 17 新增的 transaction_timeout，限制整個交易的總時間；這課先設另外三個，因為它們直接對應事故三的閒置交易、慢查詢和等鎖。其中跟事故三最直接相關的是 idle_in_transaction_session_timeout：交易開著、閒置超過這個時間，資料庫就結束那條連線，交易回滾、鎖釋放，等於自動做了上一節的 pg_terminate_backend。另外兩個也該一起設：statement_timeout 限制一句查詢最多跑多久，lock_timeout 限制等鎖最多等多久。

問題是設在哪裡。寫進 postgresql.conf 會影響所有連線，包括要跑 20 分鐘的 migration 和月報，它們會一起被砍。我們想要的是「只管 App」，而上一節已經讓 App 有了自己的角色 app_user，所以設在角色上：

ALTER ROLE app_user SET statement_timeout = '5s';

ALTER ROLE … SET 叫做角色層級設定（per-role setting）：該角色每次登入時自動套用，存在系統表 pg_db_role_setting。同一個設定可以出現在好幾個層級，越具體的越優先：

層級（由低到高）寫法影響誰
伺服器postgresql.conf、ALTER SYSTEM所有連線
資料庫ALTER DATABASE cafe SET …連到這個資料庫的所有角色
角色ALTER ROLE app_user SET …這個角色之後的每次登入
角色＋資料庫ALTER ROLE app_user IN DATABASE cafe SET …這個角色連到這個資料庫時
連線SET …這條連線之後的交易
交易SET LOCAL …、set_config(…, true)只有這個交易

有了這張表，例外情況也好處理：App 遇到確實需要比較久的查詢，在那個交易裡 SET LOCAL statement_timeout = '30s' 臨時放寬，不必改角色的設定。migrator 則不設 statement_timeout，但每次 DDL 前要 SET LOCAL lock_timeout（第 32、34 課）。

💡 實務上：資料庫逾時要比 HTTP 逾時短
假設咖啡店的 API 前面有負載平衡器，30 秒沒回應就回 504 給使用者。如果 statement_timeout 比 30 秒長，使用者早就看到錯誤、可能還按了重試，資料庫卻還在跑原本那句，重試又多開一句，越塞越嚴重。所以設逾時時要把整條路徑一起看：前端 → 負載平衡器 → API → 資料庫，越往後越短。被逾時取消的查詢會收到錯誤碼 57014（query_canceled），App 要把它當成「查太久」記錄下來並回傳合理的錯誤，不要直接當成 500 吞掉；這類錯誤突然變多，通常代表某句查詢變慢了，正好是去看 pg_stat_statements 的時機。

到這裡三件事故都有了根因和防範。但它們都是使用者先感受到、才被人發現的。下一節要做的，是在使用者抱怨之前就看到徵兆。

平常要看哪些數字，才能在出事前發現？

事故三靠 pg_stat_activity 找到禍首，它回答的是「此刻每條連線在做什麼」。要提早發現徵兆，還要看資料庫這段時間整體過得怎樣：記憶體夠不夠、哪張表被反覆整張掃、哪些索引白白拖慢寫入。PostgreSQL 把這些記在一組 pg_stat_* 視圖裡。看之前要先分清楚兩種數字：

  • 現況：pg_stat_activity 的每一列就是此刻的一條連線，查一次就是當下的樣子。
  • 累計值：pg_stat_database、pg_stat_user_tables、pg_stat_user_indexes 大多是「從上次重設以來一直累加」的計數。

累計值不能直接拿來回答「今天怎麼樣」。假設統計三個月沒重設，今天快取命中率很差，但前三個月都很好，算出來的總命中率還是很漂亮，今天的問題被稀釋掉了。所以要隔一段時間取樣兩次、相減，看變化量。

先看整個資料庫的累計值 pg_stat_database，常用的欄位：

欄位意思
blks_hit要讀的資料頁已經在 shared_buffers 裡的次數
blks_read要向作業系統讀的次數（可能來自作業系統的快取，不一定真的讀磁碟）
temp_files、temp_bytes查詢寫過的暫存檔數量與大小，通常是 work_mem 不夠的排序或雜湊
deadlocks偵測到的死結次數
xact_commit、xact_rollback提交與回滾的交易數；回滾比例突然升高常代表 App 在大量出錯
stats_reset上次重設統計的時間，累計值從這裡開始算

shared_buffers 是 PostgreSQL 自己在記憶體裡的資料頁快取（下一小節細談）。從前兩欄可以算出快取命中率（cache hit ratio）：blks_hit / (blks_hit + blks_read)，也就是要讀的資料頁有多少比例已經在這塊快取裡，不用再向作業系統要。寫成 SQL 時，100.0 讓運算變成小數，否則整數相除只會得到 0 或 1；nullif(…, 0) 讓分母是 0 時得到 NULL，不會除以零。執行後看這頁真實累計值的 hit_pct：

命中率低、暫存檔多：該調哪個記憶體參數？

上面兩個數字各自指向一個記憶體參數：命中率跟 shared_buffers 有關，暫存檔跟 work_mem 有關。上線前最常被問的是這四個參數：

參數是什麼預設常見起點
shared_buffersPostgreSQL 自己的資料頁快取，所有連線共用128MB專用主機約 RAM 的 25%；文件說超過 40% 不太可能更好，因為 PostgreSQL 也靠作業系統的檔案快取
work_mem每個排序／雜湊步驟可用的記憶體（第 29 課）4MB保守；個別報表在交易裡 SET LOCAL 調大
maintenance_work_memVACUUM、CREATE INDEX 等維護工作可用的記憶體64MB可以比 work_mem 大很多，同時跑的維護工作很少；但 autovacuum 的每個 worker 各用一份（預設最多 3 個）

為什麼 work_mem 預設這麼保守？回到事故一的第一點：它是「每個步驟」的上限，不是整台機器的上限。全域調成 64MB，100 條連線同時跑有三個排序步驟的報表，最壞就是約 19GB。所以 work_mem 全域保持小，只在確定需要的報表交易裡 SET LOCAL 調大。

調整時的原則：

  • 先量測，一次改一個。網路上的「最佳設定」是別人的機器、別人的工作量。改之前記下基準（第 29 課的 pg_stat_statements、這一節的指標），改完比較。
  • 算最壞情況：shared_buffers ＋ 連線數 × 每句的排序／雜湊步驟 × work_mem ＋ 維護工作，要放得進機器的記憶體，否則尖峰時程序會被作業系統終止。
  • shared_buffers 改了要重啟資料庫才生效；work_mem 這類可以即時調整。雲端服務（例如 AWS RDS）不能直接改設定檔，要在「參數群組」裡改（DevOps 課第 18 課）。

整個資料庫的數字只能告訴你「有地方不好」。要知道是哪張表、哪個索引，得往下一層看。

往下一層：哪張表、哪個索引有問題？

從整個資料庫往下看到每張表，pg_stat_user_tables 記錄每張表被怎麼讀、有多少死版本。執行後看 seq_scan 和 n_dead_tup：

  • 大表的 seq_scan 一直增加：可能少了索引（第 20、27 課）。
  • n_dead_tup 很高、last_autovacuum 很久以前：autovacuum 跟不上或被長交易擋住（第 30 課），事故三那種開著不放的交易就會造成這個現象。

索引的問題方向相反：不是缺，而是多。每個索引在每次寫入時都要跟著更新，還佔空間和快取；沒人用的索引只有成本。索引的使用次數記在 pg_stat_user_indexes，執行後看 idx_scan 欄：

  • idx_scan = 0 的索引從統計重設以來沒被用過，卻在每次寫入時都要更新、佔空間和快取。
  • customers_pkey 的次數很大，是因為每新增一筆訂單，外鍵檢查都要用它找顧客。
  • orders_customer_id_idx 沒被用過，因為 (customer_id, ordered_at) 的複合索引已經涵蓋了它（第 20 課的最左前綴）。

但 idx_scan = 0 不等於可以刪。刪索引前要確認三件事：統計已經累積夠久（涵蓋月報這類低頻查詢）；它不是主鍵或唯一索引，因為它們在保證資料正確，就算沒被查詢用過也不能刪；唯讀副本（第 37 課）上也沒被用到，因為每台伺服器的統計是分開的。

第二件要查的「是不是唯一索引」，記在系統表 pg_index：indexrelid 是索引本身、indisunique 是否唯一、indisprimary 是否主鍵。練習 5 會把它和 pg_stat_user_indexes 接起來。

凍結年齡：慢慢逼近的上限

最後一個要定期看的數字不會讓網站變慢，卻會在拖到最後時讓資料庫拒絕寫入：第 30 課的 wraparound。先回顧它是什麼：每個會寫入的交易都會拿到一個交易編號，這個編號只有 32 位元，大約 42 億個用完就繞回來從頭用。繞回來之後，舊資料列上記的編號可能被誤判成「未來」的交易，整列就看不見了。所以 VACUUM 要定期把夠舊的資料列凍結：標成永遠可見，之後判斷時不再看它的交易編號。

datfrozenxid 記的是這個資料庫裡最舊、還沒凍結的交易編號，age(datfrozenxid) 算的是它離現在隔了多少個交易。新交易不斷產生，這個數字就會一直長；VACUUM 凍結完舊資料列，它才降下來。這裡又連回事故三：長交易開著時，VACUUM 不能凍結比它新的資料列，所以 age 只會一直往上爬。執行後看 距上次凍結的交易數：

age(datfrozenxid) 就是第 30 課說的那個年齡。它持續上升、超過 autovacuum_freeze_max_age（預設 2 億）還降不下來，就代表凍結被擋住了，常見的原因又是長交易；離上限只剩 4,000 萬個交易時開始出現警告，只剩 300 萬時資料庫拒絕分配新的交易編號。寫入量相關的 checkpoint 與 I/O 統計放在課末。

這一節的查詢都很有用，但它們有個共同的弱點：要有人記得去跑。事故三那晚就是沒有人在看。

哪些指標要自動通知人？

上一節的查詢要有人去跑；告警（alert）則是讓指標自己找人：監控系統定期跑這些查詢，數字超過門檻就自動通知值班的人。原則是只對「需要有人處理」的狀況告警，否則通知太多，大家很快就會全部忽略，真正的事故也一起被忽略。門檻依自己的系統定，下面是起點：

指標怎麼查為什麼
連線使用率pg_stat_activity 筆數 ÷ max_connections到 100% 時新的請求全部失敗；例如超過 80% 就通知
最長交易、idle in transactionnow() - xact_start、now() - state_change拿著鎖、擋住 VACUUM；第 32 課的事故都從這裡開始
replication lag第 37 課唯讀副本落後主資料庫的程度；落後太多，讀到的是舊資料，切換時會遺失資料
wraparound 年齡age(datfrozenxid)拖到最後資料庫會拒絕寫入
磁碟用量主機或雲端的指標磁碟滿了資料庫會停止寫入
死結、回滾、錯誤率deadlocks、xact_rollback 的變化量從 0 變成每分鐘好幾次，代表程式或資料出了問題
慢查詢數量pg_stat_statements、慢查詢 log（第 29 課）使用者感受到的延遲

對照三件事故：第一列會在事故一之前響（使用率爬到 80%），第二列會在事故三的那條連線閒了幾分鐘時就響。第一列的使用率可以這樣算：SELECT count(*) * 100.0 / current_setting('max_connections')::int FROM pg_stat_activity WHERE backend_type = 'client backend'。只看 CPU 不夠：事故三 CPU 很閒，問題在一條 idle in transaction 的連線。指標怎麼收集、告警怎麼通知和值班，在 DevOps 課第 22 課和第 25 課。

💡 實務上：「網站變慢」時先跑的三句
客服轉來「網站很慢」或告警響起時，資深工程師不會先盯 CPU 圖，而是準備好一份固定的查詢清單（常叫 runbook），依序看：連線數和 state 分布、最老的交易和 idle in transaction、pg_stat_statements 裡這段時間最耗時的查詢。三句跑完通常就知道是連線滿了、有人拿著鎖、還是某句查詢變慢，再決定要 pg_terminate_backend、退回上一版部署還是加索引。這份清單平常就該放在團隊文件裡，值班的人半夜被叫起來時照著跑，不用臨時想。託管服務（例如 AWS RDS、Supabase）的監控頁會把這些畫成圖，但底層還是這幾個視圖，看得懂 SQL 版才知道圖在說什麼。

補充與查表

連線本身的保護：TLS、SCRAM

第 3 節的角色管的是連上之後能做什麼；連線本身也有三件事要設好：

  • 加密連線：資料庫和 App 不在同一台機器時，連線會經過網路，要用 TLS 加密（DevOps 課第 5 課講憑證）。連線字串的 sslmode=require 只要求加密，不驗證對方是誰；sslmode=verify-full 還會檢查伺服器憑證和主機名稱，才擋得住冒充的主機。
  • 密碼驗證用 SCRAM-SHA-256：PostgreSQL 14 起是預設的密碼雜湊方式；PostgreSQL 18 把 MD5 密碼驗證列為棄用。伺服器端有一個設定檔 pg_hba.conf，決定「誰、從哪裡、用什麼方式」可以連線；在裡面指定 hostssl … scram-sha-256，只接受加密且用 SCRAM 驗證的連線。
  • 標上身分：連線字串加 application_name，出事時在 pg_stat_activity 一眼看出是哪個服務（第 4 節）。
DATABASE_URL=postgres://app_user:密碼@db.cafe.internal:5432/cafe?sslmode=verify-full&application_name=cafe-api

其他細節

  • 雜湊步驟的記憶體：雜湊步驟預設可以用到 work_mem 的 2 倍（hash_mem_multiplier = 2.0），估最壞情況時要算進去。
  • pooler 與預備陳述式：預備陳述式（prepared statement，第 29 課）有兩種：SQL 指令 PREPARE，以及驅動程式透過連線協定送出的版本（pg 套件傳 name 參數時就是後者）。PgBouncer 從 1.21.0 起支援協定層的預備陳述式（設定 max_prepared_statements），1.24.0 起預設是 200，等於預設開啟；SQL 的 PREPARE 仍然不支援。
  • defaclacl 的讀法：report_reader=r/postgres 裡，r 是 SELECT、a INSERT、w UPDATE、d DELETE、D TRUNCATE；斜線後是授權者。
  • 自動編號的權限：用 GENERATED … AS IDENTITY 的自動編號，app_user 新增資料時不需要另外給序號（sequence）的權限。

pg_stat_checkpointer（17 起）記錄 checkpoint 的次數。checkpoint 是定期把記憶體裡改過的資料頁寫回磁碟的時間點，第 37 課詳談。執行後比較 num_timed 和 num_requested：

num_requested 比 num_timed 多很多，代表寫入量大到 checkpoint 一直被提前觸發。更細的 pg_stat_io（16 起）依程序類型、用途分開統計讀寫次數，18 起也包含 WAL。

版本備註
  • PostgreSQL 14：password_encryption 預設 scram-sha-256。15：public schema 預設不再讓所有人建立物件。16：新增 pg_stat_io。17：新增 pg_stat_checkpointer、transaction_timeout。18：MD5 密碼驗證列為棄用、pg_stat_io 加入 WAL、io_method 非同步 I/O。
  • PgBouncer 1.26.1（2026-10）；協定層預備陳述式 1.21.0 起支援、1.24.0 起 max_prepared_statements 預設 200。
  • 這頁的 PGlite 0.5.13（PostgreSQL 18.6）只有一條連線：max_connections 顯示 100 但沒有意義、計時器類設定不會觸發、io_method 是 sync，所以連線與取樣用快照表練習。

練習

練習 1：migration 一律由 migrator 執行。起始的寫法只照顧到現有的表。改成：之後 migrator 在 public 建立的表，app_user 自動有 SELECT、INSERT、UPDATE、DELETE（不多不少），report_reader 只有 SELECT。其他角色（PUBLIC）不能因此拿到任何權限。判分會用 migrator 建一張新表，檢查 app_user、report_reader、PUBLIC 的權限。（這題在全新的資料庫裡跑。）

練習 2：替 app_user 加上護欄：statement_timeout 5 秒、idle_in_transaction_session_timeout 30 秒、lock_timeout 2 秒，而且它每次登入都自動套用。migrator 和其他角色不能受影響。起始的寫法只影響目前這條連線。（判分讀 pg_db_role_setting，數值會換算後比較，'5s' 和 '5000ms' 都算對。）

練習 3：activity_samples 是 21:30（captured_at）的連線快照。列出 idle in transaction 超過 5 分鐘的連線：pid、usename、application_name、閒置多久（idle_for），依閒置時間由長到短。這是快照，時間要以取樣當下為準。

練習 4：db_stats_samples 有 21:00 與 22:00 兩次取樣的累計值。算出這一小時之間的快取命中率 hit_pct（百分比，四捨五入到小數點後 2 位）與新增的暫存檔數 temp_files_delta，結果是一列。起始的寫法用的是 22:00 的累計值。提示：同一張表可以在 FROM 裡用兩個別名各取一列。

練習 5：找出可以考慮刪掉的索引：idx_scan = 0，而且不是主鍵、也不是唯一索引。列出表名 relname、索引名 indexrelname、大小 size（pg_size_pretty），依實際大小由大到小。（這題在全新的資料庫裡跑，看到的是頁面啟動時那段工作量留下的統計。）

練習 6：週末尖峰時 App 開始出現 sorry, too many clients already。最好的處理方向是？

✓ 連線滿了通常是乘法算錯（擴展後實例變多）或連線被佔著不放（idle in transaction、漏還）。先查清楚是誰，再減少實際的伺服器連線數。a：每條連線一個程序，連線越多記憶體越多、互相搶得越兇，吞吐量反而下降。c：pool 越大，乘起來越多。d：只是暫時清掉，原因還在。

練習 7：App 透過 PgBouncer 的 transaction 模式連線。程式在每個請求開頭執行 SET app.store_id = '5'（不在交易裡），接著查詢 orders，靠 RLS 只看自己分店。可能發生什麼事？

✓ transaction 模式每個交易結束就換人，SET 自己是一個交易，設定留在那條伺服器連線上。不會報錯，所以很難發現。a 把「客戶連線」當成「伺服器連線」；b：PgBouncer 不會擋 SET，只是不保證它的效果。改用交易內的 set_config('app.store_id', '5', true)。

練習 8：監控顯示快取命中率 99.9%，但使用者說網站很慢。下列哪個說法正確？

✓ 任何單一指標都只看到一面。第 32 課的鎖事故、idle in transaction、缺索引的全表掃描（資料全在記憶體裡也一樣慢），命中率都可能很漂亮。要一起看連線狀態、最長交易、pg_stat_statements 的總時間。b 下結論太早；c 和效能問題無關。另外，累計的命中率混進了很久以前的數字，看變化量才準。

常見錯誤

  • 每個 App 實例都開很大的 pool：擴展時連線數跟著乘上去，超過 max_connections。先算「實例數 × pool 上限」，不夠就加 pooler，而不是調大 max_connections。
  • transaction 模式下用 SET、LISTEN、session 級 advisory lock：狀態留在伺服器連線上，會漏給別人或在你下一個交易消失。改用 SET LOCAL／set_config(…, true)、交易級 advisory lock，聽通知的程式直連。
  • 應用程式用擁有者或超級使用者連線：RLS 失效，一個 SQL injection 就能改表結構。App 用不是擁有者的 app_user。
  • 只 GRANT … ON ALL TABLES：下一次 migration 新增的表，App 就 permission denied。加上 ALTER DEFAULT PRIVILEGES FOR ROLE migrator。
  • 只看 CPU：長交易、等鎖、連線滿了，CPU 都可能很閒。一起看 pg_stat_activity。
  • 全域設定很短的 statement_timeout：migration、報表、VACUUM 前的維護工作一起被砍。設在 app_user 角色上，需要時在交易裡 SET LOCAL 放寬。
  • 逾時設定沒寫單位：沒寫單位時當毫秒，statement_timeout = 5 是 5 毫秒，App 的每一句都會失敗。一律寫 '5s' 這種帶單位的字串。
  • 拿累計值當目前的狀況：pg_stat_database、pg_stat_user_* 是從重設以來的總和，要兩次取樣相減。
  • 照抄網路上的設定值、一次改很多參數：出了問題不知道是哪一個造成的。先量測，一次改一個。
  • 看到 idx_scan = 0 就刪索引：主鍵、唯一索引在保證資料正確；統計可能才剛重設；副本上可能有人在用。

小結

  • 事故一（連線用完）：每條連線是資料庫主機上的一個程序、各有記憶體；同時在做事的連線超過硬體能處理的量，吞吐量反而下降。連線數是「實例數 × pool max」的乘法，用擴展上限算；用 pooler 控制伺服器連線數，max_connections 留一點給維運。
  • transaction 模式的 pooler 每個交易換一條伺服器連線：SET、LISTEN、session 級 advisory lock、WITH HOLD cursor、SQL 的 PREPARE 都不可靠；設定改用交易內的 SET LOCAL／set_config(…, true)，否則可能安靜地把一間分店的資料給另一間。
  • 事故二（新表 permission denied）：三個角色，migrator 擁有表、app_user 只讀寫資料（RLS 對它有效）、report_reader 唯讀。ON ALL TABLES 只管現有的表，ALTER DEFAULT PRIVILEGES FOR ROLE migrator 管之後的表。
  • 事故三（沒 COMMIT 的連線）：看 pg_stat_activity 的 state，idle in transaction 閒了多久用 state_change 算、交易開了多久用 xact_start；止血用 pg_terminate_backend。
  • 防範設在角色上：ALTER ROLE app_user SET idle_in_transaction_session_timeout／statement_timeout／lock_timeout，登入時套用、存在 pg_db_role_setting；越具體的層級越優先，交易裡可以 SET LOCAL 放寬。資料庫逾時要比 HTTP 逾時短。
  • 平常看的數字：pg_stat_database 的命中率、暫存檔、死結要看兩次取樣的變化量；pg_stat_user_indexes 找沒用的索引，但主鍵、唯一索引不能刪；age(datfrozenxid) 看 wraparound。
  • 記憶體：shared_buffers 約 RAM 25%、work_mem 要乘上連線數估、maintenance_work_mem 給維護工作、effective_cache_size 只是估計。先量測，一次改一個。
  • 告警只對需要有人處理的狀況：連線使用率、最長交易與 idle in transaction、replication lag、wraparound、磁碟、死結與回滾、慢查詢。出事時先跑 runbook 的三句，不要先盯 CPU。
