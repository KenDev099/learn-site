階段 4：進階查詢 · 第 17 課

視窗函式

店長要一頁「10 月第一週營運週報」，放在後台給他每週一早上看。他要四塊內容：每項商品比同類平均貴多少；每個分類挑兩項最貴的當招牌；每位顧客的第一筆訂單（首購那天買了多少）；每天的營收，旁邊加上「到這天為止累計多少」和「比前一天多或少多少」。

這四塊有一個共同點：結果裡每一列都還是一筆細節（一項商品、一張訂單、一天），但旁邊要多一個跟同組其他列比較出來的數字。第 7 課的 GROUP BY 做不到，因為它會把同組的列合併成一列，細節就不見了。這一課用視窗函式（window function）把週報從第一塊做到最後一塊：它保留每一列，同時替每一列算出同組的平均、排名、累計，或拿前一列來比。

這課會用到：
  • 第 7 課的 GROUP BY 與執行順序：GROUP BY 把同組的列合併成一列；資料庫照 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY 的順序執行，某個東西能不能用，看它在第幾步產生。
  • 第 16 課的 CTE：用 WITH 名字 AS (…) 先算出一步的結果並取名字，後面的查詢把它當成一張表來用。
這課的路線：
  1. 第一塊「比同類平均貴多少」：為什麼 GROUP BY 做不到，在函式後面加上 OVER 怎麼做到（開場問題的最小答案）。
  2. OVER 的括號裡放什麼：OVER ()、PARTITION BY、ORDER BY 各自決定每一列看得到哪些列。
  3. 第二塊「每類的招牌」：同價的商品算第幾名，以及為什麼「只要前兩名」不能直接寫在 WHERE；同一招也解決第三塊「每位顧客的第一筆訂單」。
  4. 第四塊「每日營收」：到這天為止的累計怎麼算，「比前一天」怎麼拿到前一列，沒開店的日子要怎麼處理。

第一塊：每項商品比同類平均貴多少，為什麼 GROUP BY 做不到？

先用已經會的 GROUP BY 試試看。要「同類平均」，就照分類分組再取平均。執行後看列數：

平均算出來了，咖啡類 108、茶類 100、甜點類 100，可是只剩 3 列，11 項商品都不見了。週報要的是「摩卡 130 元，比同類平均貴 22 元」這種一項商品一列的結果，商品名稱和價格都得留著。

直覺的修法是把 name、price 也加進 GROUP BY，讓它們可以出現在 SELECT。但這樣每一組就只剩一項商品，平均就是那項商品自己的價格，差額全部是 0。問題出在 GROUP BY 的本質：分組和合併是同一個動作，「分幾組」就決定了「剩幾列」。週報需要的是另一件事：列數不變，但每一列計算時能看到同組的其他列。

用咖啡店的價目卡比喻這兩件事：

  • GROUP BY category 像是把同類的價目卡疊成一疊，只在最上面寫平均價。卡片合併了，個別商品看不到。
  • 視窗函式像是讓每張卡片都留在桌上，然後在每張卡片旁邊寫上「同類平均」。卡片數量不變，只是多了一欄。

SQL 的寫法是在聚合函式後面加上 OVER (…)。avg(price) 單獨出現時是聚合函式，會讓整個查詢合併列；寫成 avg(price) OVER (PARTITION BY category) 時，它變成視窗函式：資料庫替每一列找出「跟它同一個分類的那些列」，對這些列算平均，把答案寫回這一列旁邊，列本身不合併。括號裡的 PARTITION BY category 就是在說「同組的定義是同一個分類」。執行後看兩件事：還是 11 列，而且同類的商品旁邊是同一個平均：

週報第一塊完成了：摩卡旁邊是咖啡類平均 108，差 22 元；可頌旁邊是甜點類平均 100，差 -30 元。「一列一筆細節，旁邊多一個同組算出來的數字」就是視窗函式的全部概念，這課後面的排名、累計、前後比較，都只是換函式、換括號裡的寫法。

每一列計算時看得到的那群列，叫做這一列的視窗（window），這也是這種函式名稱的由來。這一節的視窗是「同分類的列」，但週報後面幾塊需要的視窗不一樣：排名要知道誰在前面，累計要知道從第一天到今天。下一節看 OVER 的括號裡還能放什麼。

OVER 的括號裡放什麼？它決定每一列看得到哪些列

上一節的 PARTITION BY category 只是其中一種寫法。資料庫算視窗函式時，對每一列都做同一件事：先依括號裡的規則找出這一列的視窗，再對視窗裡的列執行函式。所以括號裡寫什麼，就決定每一列看得到哪些列。常用的寫法有三種：

寫法意思
OVER ()視窗＝整張結果。每一列看到的都是全部的列。
OVER (PARTITION BY 欄位)依欄位分組，每一列只看得到同組的列（像 GROUP BY，但不合併）。
OVER (ORDER BY 欄位)視窗內排好順序。排名、累計、前後比較都要靠它。

前兩種可以一起看。下面這格在同一個查詢裡放了空括號和 PARTITION BY，執行後比較後兩欄：

  • 商品總數：每一列都是 11。空括號沒有分組，每一列的視窗都是全部 11 列。
  • 全店最高價：每一列都是 130（摩卡），理由同上。
  • 同類最高價：咖啡類的列是 130，茶類是 120，甜點類是 120。每一列只看得到同類的列。

第三種 ORDER BY 寫在 OVER 裡，跟查詢最後的 ORDER BY 是兩回事。查詢最後的 ORDER BY 只決定結果怎麼顯示；OVER 裡的 ORDER BY 決定視窗裡面的列誰先誰後，函式才知道「第幾名」「前一列是誰」。兩者可以不同，例如照價格排名、最後卻照分類顯示。PARTITION BY 和 ORDER BY 也可以同時寫：先分組，組內再排序。

週報第二塊「每類的招牌」正好要用到後者：先依分類分組，組內依價格由高到低排出名次。下一節就用它來排名。

第二塊：每類的招牌要排名次，同價的商品算第幾名？

排名需要順序，所以要用上一節的 OVER (ORDER BY …)。排名最常用的是三個函式：row_number()、rank()、dense_rank()。它們括號裡都不放欄位，名次完全由 OVER 裡的排序決定；三者的差別只在遇到同分時怎麼處理。這間店有好幾項商品同價（三項 120 元、兩項 110 元、三項 90 元），剛好拿來比較。先不分組，看全店的排名：

看三項 120 元的商品：row_number 給了 2、3、4；rank 都給 2，下一項 110 元的直接跳到 5；dense_rank 也都給 2，下一項是 3。用更短的例子整理：

函式同分時價格 130、120、120、110
row_number()硬是排出先後，每列號碼都不同1、2、3、4
rank()同分同名次，下一名跳號（像運動比賽）1、2、2、4
dense_rank()同分同名次，下一名不跳號1、2、2、3

row_number() 有一個陷阱。三項 120 元的商品，排序依據只有價格，資料庫沒有理由把誰排前面，所以同分的列誰拿 2、誰拿 3 不保證，資料量變了或執行計畫不同，每次執行都可能不一樣。要結果穩定，就在 OVER 的 ORDER BY 最後多加一個不會重複的欄位，例如 ORDER BY price DESC, id：價格相同時 id 小的在前，順序就只有一種。

週報要的是每類各自的名次，加上 PARTITION BY category，每個分類就從 1 開始各排各的。執行後看甜點類：起司蛋糕和提拉米蘇同為 120 元，都是第 1 名，布朗尼跳到第 3：

名次有了，但週報只要每類前兩名，不要整份名單。下一節要把名次 2 以後的列篩掉。

只要每類前兩名：為什麼不能直接寫在 WHERE？

篩選列的工具是 WHERE，直覺會把排名直接寫進條件。執行看看：

錯誤訊息是 window functions are not allowed in WHERE。原因是第 7 課的執行順序。資料庫先做 FROM，再用 WHERE 篩掉不要的列，然後 GROUP BY、HAVING；視窗函式要等這些都做完，在 SELECT 那一步才算。這個順序是必要的：視窗看的是「篩選、分組之後剩下的列」，名次要等所有參賽的列都確定了才排得出來。所以 WHERE 執行的時候，名次還不存在，自然沒辦法拿來比較。同樣的道理，在 SELECT 裡給名次取別名 AS rn，再寫 WHERE rn <= 2 也不行，錯誤會變成 column "rn" does not exist，因為別名也是在 SELECT 那一步才產生。

解法是把工作拆成兩步：第一步把名次算好，變成一個普通的欄位；第二步再拿這個欄位篩選。拆成兩步正是第 16 課的 CTE 擅長的事。在 WITH 裡算出 rn，對外層查詢來說 ranked 就是一張已經有 rn 欄位的表，它的 WHERE 就能用了：

這裡用 row_number 加上 id，保證每類剛好 2 項：咖啡類是摩卡和拿鐵（拿鐵、卡布奇諾同價，拿鐵 id 小）。如果改用 rank，同價的商品會一起入選：咖啡類的拿鐵和卡布奇諾都是第 2 名，rn <= 2 會選出 3 項。哪個才對要看需求：「推薦兩項招牌」用 row_number，「價格前兩高的所有商品」用 rank。

第三塊：每位顧客的第一筆訂單，套路一樣嗎？

週報第三塊「每位顧客的第一筆訂單」是同一個套路，只是換了資料：分組的依據從分類換成顧客，排序的依據從價格換成下單時間。先看編號的結果，每位顧客的訂單依時間各自從 1 開始編：

王小明（customer_id 1）有 4 筆訂單，編號 1 的是 10/1 那筆 150 元，就是他的首購。把這段放進 CTE、外層取編號 1，就是每位顧客的第一筆訂單，練習 3 會讓你自己寫完。

💡 實務上：「每組取最新一筆」幾乎每個後台都會遇到
咖啡店後台的「顧客列表＋各自最近一筆訂單」、商品的「目前售價」（價格歷史表取最新一筆）、清理重複匯入的資料（同 email 只留最早那筆），都是「PARTITION BY 分組、row_number 編號、外層取 rn = 1」這個套路。寫之前先問 PM：同分或同時間時要顯示一筆還是全部？這決定用 row_number 還是 rank，也要在排序最後補上 id，免得同時間的資料每次查詢挑到不同筆、畫面跟著跳。資料量大時這種查詢要搭配索引，第 20 課會講。

前三塊都是「跟同組比」。週報最後一塊不一樣：每日營收是一條時間序列，要的是「從第一天加到今天」和「跟前一天比」，視窗得跟著日期往前走。

第四塊：每天營收旁邊加上「到這天為止累計多少」

先要有每日營收。第 16 課做過：ordered_at::date 把下單時間轉成日期（只留年月日），再依日期 GROUP BY 加總。把這一步放進 CTE daily，每天一列。

累計要用到上一節沒碰過的一條規則：OVER 裡寫了 ORDER BY 時，每一列的視窗不是整組，而是「從第一列到目前這一列」。原因是有了順序，「到目前為止」才有意義；資料庫就把這當成預設的視窗範圍。所以 sum(revenue) OVER (ORDER BY day) 在 10/1 那列只加 10/1，在 10/2 那列加 10/1、10/2，依此類推，結果就是累計。執行後看第三欄每一列是不是等於上一列的累計加上當天營收：

10/1 營收 370，累計 370；10/2 營收 270，累計 640；一路加到 10/7，累計 2260，就是這週的總營收。注意 GROUP BY 和視窗函式在同一個查詢裡各司其職：daily 裡的 GROUP BY 把訂單合併成每天一列，外層的視窗函式再保留這 7 列、替每一列算累計。

「從第一列到目前這一列」的「目前這一列」有一個細節：排序值跟目前這列相同的列，會被當成同一個位置一起算進去。daily 每天只有一列，不會遇到；但如果直接對訂單依日期累計，同一天的兩筆訂單會顯示同一個累計值。解法列在課末的「常見錯誤」。

再加上 PARTITION BY，就是每個人各自從頭累計。例如每位顧客的累計消費：視窗先依顧客分組，組內再依下單時間從第一筆加到目前這筆。執行後看王小明的 4 筆：150、260、340、470：

💡 實務上：累計放在 SQL 算，不要等前端自己加
營收報表的「本月累計」、會員「累計消費滿 3000 升等」的進度條，都適合用 sum() OVER 在資料庫算好再回傳。前端常見的坑是把列表撈回來在 JS 裡自己加總：一旦 API 有分頁，第二頁的累計就從 0 開始，數字整個錯。週報的累計欄也一樣，在 SQL 裡算好，前端只負責顯示。::date 切日期還牽涉到時區，做日報前要先確認，細節見課末「補充與查表」。

累計看的是從第一天到今天的一整段。週報的最後一欄「比前一天」只需要前一列的一個值，視窗函式另外有專門拿前後列的函式。

「比前一天多賣多少」：怎麼拿到前一列的值？

lag(欄位) 回傳前一列的那個欄位，lead(欄位) 回傳後一列的。哪一列算「前」，由 OVER (ORDER BY …) 的順序決定，所以這兩個函式一定要配 ORDER BY。有了前一天的營收，「比前一天」就是當天減前一天。第一列沒有前一列，lag 得到 NULL，相減的結果也是 NULL；最後一列沒有後一列，lead 也是 NULL。執行後看 10/2 那列：前一天 370、比前一天 -100、後一天 240：

週報的四塊到這裡都做出來了。這週剛好每天都有訂單，所以「前一列」就是「前一天」。只要哪天公休，兩者就不再相同，下面的實務提醒就是在講這件事。

💡 實務上：「比前一天」要小心沒開店的日子
儀表板上的「比昨天 +12%」、顧客的「距離上次消費幾天」（拿來找快流失的熟客），都是 lag 的典型用法。要注意 lag 拿的是前一列，不是前一個日曆日：公休日沒有訂單就沒有那一列，週二會直接跟上週日比。做日報時，先產生完整的日期清單再 LEFT JOIN 營收（沒營業的日子補 0），比較結果才對得上。另外算百分比時，前一天是 0 或 NULL 要先處理，否則會除以零報錯，或那一列結果變成 NULL。

補充與查表

  • ::date 依連線時區切日期：ordered_at 是 timestamptz，轉成日期時用的是資料庫連線的時區。連線時區是 UTC 時，台灣早上 8 點前的訂單會被算到前一天；做日報前先確認時區設定（第 15 課）。
  • 自己指定視窗範圍：移動平均：視窗的範圍可以不用預設的「從第一列到目前這一列」。ROWS BETWEEN 2 PRECEDING AND CURRENT ROW 表示「前兩列加上自己」，用來算三日移動平均，讓起伏比較平滑：

練習

練習 1：列出每項商品，四欄：name、category、price、該商品所屬分類的最高價。每項商品都要出現（共 11 列）。

練習 2：每個分類內依價格由高到低排名，同價同名次、下一名跳號。四欄：category、name、price、名次。結果依 category、名次、name 排序。

練習 3：找出每位顧客的第一筆訂單（依 ordered_at 最早）。四欄：customer_id、訂單 id、ordered_at、total。

練習 4：每個分類挑出價格最高的 2 項商品當招牌，同價時 id 小的優先，每類剛好 2 項。三欄：category、name、price，依 category 排序，同類內價格高的在前。

練習 5：在每日營收旁邊加上第三欄「到這天為止的累計營收」，依日期排序。

練習 6：看王小明（customer_id = 1）每次消費的變化。四欄：訂單 id、total、他上一筆訂單的 total、這筆減上一筆的差額。依下單時間排序；第一筆沒有上一筆，後兩欄是 NULL。

練習 7：顧客消費排行榜。三欄：顧客 name、總消費金額、名次。名次依總消費由高到低，同額同名次、下一名不跳號。結果依名次、name 排序。

練習 8：四位顧客的分數是 100、90、90、80，用 rank() OVER (ORDER BY 分數 DESC) 排名，結果是？

✓ rank 同分同名次，下一名跳號（兩個第 2 名之後是第 4 名）。dense_rank 是 1、2、2、3；row_number 是 1、2、3、4。

練習 9：products 有 11 列、3 個分類。SELECT name, avg(price) OVER (PARTITION BY category) FROM products; 會回傳幾列？

✓ 視窗函式不會合併列，有幾列進來就有幾列出去。想要每分類一列，才用 GROUP BY category。

常見錯誤

  • 在 WHERE 裡用視窗函式：會報錯。先在 CTE 或子查詢裡算好，外層再篩選。
  • 在 WHERE 裡用 SELECT 取的別名：WHERE rn = 1 會說 column "rn" does not exist，原因同上，WHERE 比 SELECT 早執行。
  • 以為 row_number 遇到同分會照某種順序：不保證。要穩定就在 ORDER BY 加上 id 之類不重複的欄位。
  • 累計時 ORDER BY 的值有重複：預設的視窗會把「排序值相同」的列一起算進去，所以同一天的兩筆訂單會顯示同一個累計值。要逐筆累計，就用不重複的欄位排序（例如 ORDER BY ordered_at, id），或寫 ROWS UNBOUNDED PRECEDING。
  • 忘了 OVER 的 ORDER BY：lag(total) OVER () 沒有定義順序，「前一列」是哪一列就不確定。

小結

  • 週報的四塊都是「每列保留一筆細節，旁邊多一個跟同組比出來的數字」：GROUP BY 會合併列，做不到；視窗函式在 OVER (…) 定義的範圍裡計算，不合併列。
  • OVER 的括號決定每一列看得到哪些列：空的 OVER () 是整張結果，PARTITION BY 分組，ORDER BY 決定視窗裡的先後。
  • 排名：row_number 不重複、rank 同分跳號、dense_rank 同分不跳號。row_number 同分時順序不保證，排序最後補上 id。
  • 視窗函式在 WHERE、GROUP BY、HAVING 之後才算，所以要篩選排名（每組前 N 名、每組第一筆），先在 CTE 裡算好，外層再 WHERE。
  • OVER 裡有 ORDER BY 時，視窗是「從第一列到目前這一列」，sum() OVER (ORDER BY …) 就是累計；lag／lead 拿前後列，不是前後一天，沒營業的日子要先補上。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 8 件事。先在心裡回答，再選。

練習 10：顧客清單這樣整理 email。林志豪（email 是 NULL）正確顯示「（無）」，張雅婷（email 是 ''）卻是一格空白，為什麼？

SELECT name, COALESCE(lower(trim(email)), '（無）') AS email
FROM customers;

✓ '' 是有值的字串，COALESCE 回傳第一個不是 NULL 的值，所以留下空字串。改成 COALESCE(NULLIF(lower(trim(email)), ''), '（無）')，兩種「沒有值」一起處理。b 錯在 COALESCE 看的是參數算出來的值：lower(trim(NULL)) 是 NULL，所以林志豪那一列才會顯示「（無）」。（第 15 課）

練習 11：財務對帳發現，台北時間 10/1 00:30 下單的 240 元被算進 9 月營收。報表用 to_char(ordered_at, 'YYYY-MM') 分組，ordered_at 是 timestamptz。先查什麼？

✓ to_char、date_trunc 都依連線的時區切；伺服器常設成 UTC，台北 10/1 00:30 是 UTC 的 9/30 16:30，就落在 9 月。先約定以台灣時間算，連線時設定 timezone 或用 AT TIME ZONE 'Asia/Taipei'。c 錯在格式碼寫錯會讓每一筆都分錯，不會只有半夜的訂單換月。（第 15 課）

練習 12：要發首購券給「註冊後從沒下單的會員」，同事的 SQL 在測試環境結果正確，上線前請你 code review。你的意見是？

SELECT name FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);

✓ 散客訂單的 customer_id 是 NULL，id <> NULL 是「不知道」，整個 NOT IN 不會是 true，也不會報錯。NOT EXISTS 只問「找不找得到對應的列」，不受 NULL 影響。a 錯在測試資料剛好沒有 NULL，上線後才出事，所以看到 NOT IN (子查詢) 就直接改。（第 16 課）

練習 13：會員日要傳簡訊給「10 月下過單的會員」，名單用下面這句。王小明 10 月下了三張單，結果收到三封簡訊，為什麼？

SELECT c.name, c.phone
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.ordered_at >= '2026-10-01';

✓ JOIN 是把兩張表的列配對，三張訂單就配出三列。只是要篩選「有沒有」，改成 WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.ordered_at >= '2026-10-01')，每位會員最多出現一次。a 錯在 customers 裡只有一個王小明，重複是 JOIN 產生的。（第 16 課）

練習 14：商品列表的每一項商品旁邊，要顯示「比同類平均貴多少」，每項商品各一列。哪個寫法對？

✓ 視窗函式不合併列，每項商品都還在；PARTITION BY 讓每一列只看得到同類的列。a 錯在 GROUP BY 加上 name 後每組只剩一項商品，平均就是自己的價格，差額全是 0。（第 17 課）

練習 15：要取每位顧客最近一筆訂單，這句報錯 column "rn" does not exist。怎麼修？

SELECT customer_id, id, ordered_at,
  row_number() OVER (PARTITION BY customer_id ORDER BY ordered_at DESC) AS rn
FROM orders
WHERE rn = 1;

✓ WHERE 比 SELECT 早執行，那時視窗函式還沒算出來，別名也還不存在。先在 CTE 裡算出 rn，外層再篩選。d 錯在視窗函式本身也不能放進 WHERE，會報 window functions are not allowed in WHERE，原因相同。（第 17 課）

練習 16：後台「顧客列表＋最近一筆訂單」每位顧客一列，用 row_number() OVER (PARTITION BY customer_id ORDER BY ordered_at DESC) 取 rn = 1。王小明有兩筆同一秒的訂單，每次重新整理顯示的那筆都不一樣，怎麼修？

✓ 同分時 row_number 誰先誰後不保證，每次查詢可能挑到不同筆；補上不重複的欄位，順序就唯一。a 錯在 rank 讓兩筆都是第 1 名，rn = 1 會取出兩筆，王小明在列表上出現兩次。（第 17 課）

練習 17：儀表板的「比前一天」用每日營收算 revenue - lag(revenue) OVER (ORDER BY day)，每日營收是依日期 GROUP BY 出來的。週一公休，週二那一列算出來的是什麼？

✓ lag 拿前一列，不是前一個日曆日；沒有訂單的日子在 GROUP BY 結果裡沒有列。先產生完整的日期清單（第 16 課）LEFT JOIN 每日營收、沒對到的補 0，再算 lag。a 錯在只有整個結果的第一列，lag 才是 NULL。（第 17 課）
