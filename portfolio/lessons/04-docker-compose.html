階段 A：小專案走完一次 · 第 4 課

Docker 化：映像、Compose 與 migration

到目前為止，報名 API 只在你自己的電腦上用 npm run start:dev 跑。它能跑，靠的是三樣只有你的電腦才有的東西：你裝的 Node 版本、你 node_modules 裡的套件、你 .env 裡的連線字串。面試官 clone 你的 repo 時，這三樣他都沒有，或者版本跟你不一樣；你要把它部署到伺服器時也一樣。「在我電腦上能跑」證明不了它在別的地方也能跑。

這課的任務：讓任何人 clone 之後，只打一個指令 docker compose --profile app up -d --build --wait，就依序得到一個健康的資料庫、套用好的 migration、通過健康檢查的 API，換哪台機器結果都一樣。做到這件事的路上，有三個地方最容易做錯：映像裡留著編譯工具與原始碼、用 root 執行、migration 跟著 API 一起啟動。每一節都是在解決上一步留下的問題。

做完這課，你的 repo 會多出多階段的 Dockerfile、.dockerignore，compose.yaml 多一組「類正式」設定：資料庫健康之後跑一次 migration，跑完才啟動 API。

這課會用到：
  • DevOps 課第 9 課的多階段建置（一個 Dockerfile 好幾個 FROM，最後的映像只複製需要的檔案）與非 root 執行。
  • DevOps 課第 10 課的 depends_on 條件（service_healthy、service_completed_successfully）與一次性服務。
  • NestJS 課第 24 課的 enableShutdownHooks()（收到 SIGTERM 時先關連線池再結束）。
  • 沒學過 DevOps 課也做得完：這課會把需要的部分講到夠用。
練習 1、2 讀你 repo 裡的檔案（Dockerfile、.dockerignore、compose.yaml），不用啟動 API。練習 3 打你用 compose 啟動的 API，要先在 work/portfolio.json 的 small 加 "composeApi": "http://localhost:3001"。

這課的路線：

  • 先寫一個最簡單、跑得起來的 Dockerfile，看它把哪些不該有的東西帶進映像；再用多階段建置把它們留在外面。
  • 映像裡不能有秘密：建置時沒有 DATABASE_URL 怎麼辦、.env 怎麼擋在外面；映像乾淨了，再決定用誰的身分跑。
  • 映像要跟資料庫一起跑：同一份 compose.yaml 怎麼兼顧開發與類正式，容器之間怎麼連。
  • 啟動順序：API 怎麼等到資料庫真的能連、migration 真的跑完；migration 為什麼要自己一個服務。
  • 同一個映像到了別的環境怎麼拿設定，要被停掉時怎麼好好離開。

第一版 Dockerfile 跑得起來，問題在哪？

要讓別人在他的機器上跑出跟你一樣的 API，就要把「跑這個 API 需要的一切」打包成一份帶得走的東西。這份東西叫映像（image）：裡面有一個精簡的 Linux 檔案系統、指定版本的 Node、你的程式與它的套件，以及「啟動時要執行哪個指令」。把映像跑起來，得到的那個正在執行的實體叫容器（container）。同一個映像可以同時跑出好幾個容器，就像同一份 .vue 元件可以在頁面上用好幾次。

映像是照 Dockerfile 一行一行做出來的。Dockerfile 從 FROM 指定的映像開始，每一個 RUN、COPY 都會在前一步的結果上疊一層檔案變更，這一層叫層（layer）；最後的映像就是這些層疊起來的結果。ENV、CMD 這類指令則是改映像的設定，不改檔案。先記住「RUN 和 COPY 各是一層」，等一下快取和秘密外洩都跟它有關。

最直覺的寫法，就是把你在自己電腦上做的事照抄一遍：

# Dockerfile（第一版：跑得起來，但不要用）
FROM node:24.22.1-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npx prisma generate && npm run build
CMD ["node", "dist/main.js"]

逐行看：FROM 選一個已經裝好 Node 24 的 Linux（alpine 是很小的 Linux 發行版）當起點；WORKDIR 指定之後的指令在 /app 裡執行；接著複製檔案、裝套件、產生 Prisma client、編譯 TypeScript；CMD 是容器啟動時要執行的指令。

它真的跑得起來。問題在於最後的映像裡留著什麼：npm ci 裝了全部的套件，包括 TypeScript 編譯器、Vitest、Prisma CLI 這些只有開發與建置時才用的 devDependencies；COPY . . 把整份原始碼也放了進去。執行 API 只需要編譯好的 dist/ 和正式依賴，其餘的都是多帶的，而多帶的東西會造成三個實際的問題：

  • 映像比較大：每次部署、每台機器 pull 都要多傳這些檔案。
  • 要掃描的套件比較多：資安掃描工具會掃映像裡每一個套件，devDependencies 的弱點也會被報出來，雖然它們在執行時根本沒被用到。
  • 攻擊者能用的工具比較多：API 有漏洞被打進容器時，裡面有編譯器、有 CLI、有原始碼，對方能做的事就多。

所以問題變成：建置時需要編譯工具，執行時不需要，怎麼讓同一個 Dockerfile 在建置時什麼都有、做出來的映像卻只剩執行要的東西？

怎麼讓最後的映像只剩執行需要的東西？

答案是多階段建置（multi-stage build）。一個 Dockerfile 可以寫好幾個 FROM，每個 FROM 開始一個獨立的階段（stage），可以用 AS 名字 幫它命名。前面的階段想裝什麼都可以，它們只是工作台；只有最後一個階段會成為真正的映像，而它可以用 COPY --from=階段名稱 從前面的階段挑檔案過來。沒被挑的東西，就不會出現在最後的映像裡。

參考實作分三個階段：

# Dockerfile
# 多階段建置：build 階段有編譯工具，最後的映像只有正式依賴與編譯結果，用非 root 執行
FROM node:24.22.1-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npx prisma generate && npm run build

FROM node:24.22.1-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev

FROM node:24.22.1-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package.json ./
USER node
EXPOSE 3000
CMD ["node", "dist/main.js"]
stage做什麼留到最後的映像嗎
build裝全部依賴、prisma generate（產生 src/generated/prisma）、nest build（編譯到 dist/，產生的 client 也一起編譯進去）只複製 dist/
depsnpm ci --omit=dev：只裝 dependencies只複製 node_modules/
最後一個執行就是它

為什麼要分出一個 deps 階段，而不是直接從 build 複製 node_modules？因為 build 的 node_modules 是裝了全部套件的那一份，複製過來就把 devDependencies 又帶回來了。deps 從頭用 npm ci --omit=dev 另外裝一份只有 dependencies 的，最後的映像拿這一份。產生出來的 Prisma client 程式碼不在 node_modules，而在 src/generated/prisma（第 1 課的設定），nest build 會把它跟你的程式一起編譯進 dist/。它執行時用到的 @prisma/client runtime 是正式依賴，deps 階段那份 node_modules 裡就有。所以 build 階段只要複製 dist/，不用複製它的 node_modules。

這份 Dockerfile 還有三個寫法上的決定，每一個都對應一個你不這樣寫就會遇到的狀況。

先 COPY package*.json、npm ci，再 COPY 其他檔案。前面說每個指令是一層。Docker 建置時會檢查：這個指令和它用到的檔案跟上次一樣嗎？一樣就直接用上次的結果（快取），不重跑；某一層變了，它之後的每一層都要重跑。你平常改的是 src/ 裡的程式，package.json 很少動。把套件清單先單獨複製、先裝套件，只改程式碼時 npm ci 那層就能用快取，建置從幾分鐘變成幾秒。如果一開始就 COPY . .，改任何一個檔案都會讓 npm ci 重跑（DevOps 課第 8 課）。

npm ci 需要 package-lock.json。第 1 課說 lockfile 一定要 commit，原因之一就在這裡。npm install 會在 package.json 允許的範圍內挑版本，可能裝到比你本機新的套件；npm ci 完全照 lockfile 裝，沒有 lockfile 或兩者對不上就直接失敗，不會偷偷裝到別的版本。映像要「換哪台機器都一樣」，套件版本就不能每次建置時重新挑。

版本寫死。寫 node:24.22.1-alpine 而不是 node:latest：latest 指向的版本會隨時間改變，下個月重新 build 可能就換了一個 Node 大版本。寫死版本，今天和下個月建出來的是同一個 Node；要升級時改這一行，升級本身就成了一個看得見、可以 review 的變更。

最後一行 CMD 用陣列寫法 ["node", "dist/main.js"]，原因跟容器怎麼被停掉有關，最後一節講關機時再說明。

多階段處理了「編譯工具不進最後的映像」，但 build 階段那行 COPY . . 和 prisma generate 還藏著另一個問題：建置映像時，Docker 手上到底有哪些檔案、又缺了哪些設定？

映像裡不能有秘密：建置時沒有 DATABASE_URL 怎麼辦？

先看缺了什麼。build 階段要執行 prisma generate，它會讀 prisma.config.ts，而設定檔裡有資料庫連線字串 DATABASE_URL。建置映像時沒有這個環境變數，也不應該有：映像要能在本機、staging、正式環境用不同的資料庫跑，連線字串是執行時才給的。

這就是第 1 課的 prisma.config.ts 寫 process.env.DATABASE_URL、不用 Prisma 提供的 env('DATABASE_URL') 的原因。兩者在變數存在時結果一樣，差別在變數不存在時：process.env.DATABASE_URL 只是 undefined，prisma generate 不需要連資料庫，照樣成功；env() 則會直接丟錯，連 generate 都失敗。錯誤訊息與官方文件的說法見課末「補充與查表」。如果你照別的教學寫成了 env()，改回第 1 課的寫法：

// prisma.config.ts
import 'dotenv/config'
import { defineConfig } from 'prisma/config'

export default defineConfig({
  schema: 'prisma/schema.prisma',
  migrations: { path: 'prisma/migrations' },
  // 用 process.env 而不是 env()：env() 在變數不存在時連 prisma generate 都會失敗，
  // 而 Docker 建置映像時沒有 DATABASE_URL。migrate 時沒設照樣會報錯
  datasource: { url: process.env.DATABASE_URL },
})

build 失敗時，很多人的第一反應是在 Dockerfile 加一行 ENV DATABASE_URL=… 讓它過。不要這樣做。ENV 會寫進映像的設定，之後誰拿到這個映像，用 docker image inspect 就看得到這組連線字串；而且映像從此綁死一個資料庫，失去「同一個映像、不同環境」的意義。

再看進了什麼。COPY . . 複製的是「建置環境」（build context）裡的全部檔案。執行 docker build 時，Docker 會先把你指定的資料夾（這裡是 repo 根目錄）整個送給建置程式，這份檔案集合就是建置環境，COPY 只能從這裡拿檔案。沒有特別設定的話，你資料夾裡有什麼就送什麼，包括 node_modules 和 .env。

.dockerignore 的作用就是決定哪些檔案不送進建置環境，寫法跟 .gitignore 一樣：

# .dockerignore
node_modules
dist
src/generated
.env
.git
coverage

最重要的是這兩行：

  • node_modules：有些套件裡帶著用 C／C++ 寫、針對特定作業系統編譯好的程式，叫原生模組（native addon）。你電腦上那份 node_modules 是在 macOS 上裝的，這些原生模組在 Linux 容器裡跑不起來；而且 npm ci 本來就會在容器裡照 lockfile 重裝一份。送進去只會讓 COPY . . 用錯誤的版本蓋掉剛裝好的套件。
  • .env：裡面是你的密碼。COPY . . 會把它寫進 build 階段的那一層。最後的映像雖然沒從 build 複製它，但只要它進了建置環境，就可能留在建置快取、或在你哪天改 Dockerfile 時被不小心複製進去。不該進映像的東西，從一開始就不要讓它進建置環境。

其他幾行排除的是會在容器裡重新產生、或執行時用不到的檔案，各自的原因見課末「補充與查表」。設定要在執行時用環境變數給，怎麼給、怎麼驗證，最後一節會講。

💡 實務上：映像是會被別人拿到的東西
映像會推到 registry（存放映像的倉庫，例如 Docker Hub、GitHub Container Registry）、被 CI 快取、被同事 pull 下來除錯。放進映像的東西要當成「半公開」：docker history 看得到每一層的指令，docker image inspect 看得到 ENV。資安掃描工具（DevOps 課第 9 課）掃的是映像裡每一個套件，devDependencies 留在最後的映像裡，就會多出一堆跟執行無關的弱點警告。你的報名 API 映像下一課就會在 CI 裡被建出來，所以現在就該確認它裡面沒有 .env、沒有寫死的連線字串。

映像乾淨了，容器要用誰的身分跑？

前兩節處理的是「映像裡有什麼」，還有一件事沒處理：容器跑起來時，程式用哪個使用者的身分執行。沒有特別指定的話，容器裡的程式是 root，也就是那個 Linux 系統裡權限最大的帳號。

為什麼這是問題：你的程式（或它依賴的某個套件）有漏洞被打進去時，攻擊者拿到的就是程式的身分。如果是 root，他可以改映像裡的任何檔案、安裝工具、讀所有檔案；在某些設定錯誤的容器環境下，容器裡的 root 離主機的 root 也不遠。換成一般使用者，他能做的事就少很多。

做法很簡單。Node 官方映像已經建好一個叫 node 的使用者（uid 1000），最後一個 stage 加一行 USER node 就好，放在 COPY 之後、CMD 之前：COPY 需要寫入檔案，所以要在切換身分之前做完；USER 之後的 CMD 就會用 node 的身分執行。

切換之後，node 使用者連 /app 都寫不了，因為裡面的檔案是用 root 的身分複製進來的。這不是要修的問題，反而正好：API 本來就不該在執行時改自己的程式碼，被打進來的人也一樣改不了。之後把服務跑起來，可以這樣確認：

docker compose --profile app exec api id    # uid=1000(node) gid=1000(node)

這行用到了 compose，但我們還沒有把 API 放進 compose。映像本身已經做好了：乾淨、不帶秘密、不用 root。可是光有 API 的映像跑不起來，它還需要資料庫，資料表也還沒建。下一步是把它們接起來。

映像要跟資料庫一起跑：同一份 compose 怎麼兼顧開發與類正式？

你在第 1 課已經用過 compose：compose.yaml 描述要開哪些容器、各自用什麼映像、什麼設定，docker compose up 一次把它們開起來。檔案裡每一個要開的容器叫一個服務（service）。第 1 課的 compose.yaml 只有 db 一個服務，開發時你用 npm run start:dev 在本機跑 API，因為這樣可以熱重載、下中斷點。

現在要加兩個服務：用剛剛的 Dockerfile 建出來的 api，以及等一下會解釋的 migrate。但開發時你不想要它們：每天 docker compose up 只想開資料庫，不想每次都建一次映像。要讓同一份檔案有兩種用法，就用 profile：服務標上 profiles: [app]，平常的 docker compose up 會略過它，只有加上 --profile app 才會啟動。沒有標 profile 的 db 兩種情況都會開。

# compose.yaml
# 開發：docker compose up -d --wait db（只開資料庫，API 用 npm run start:dev）
# 類正式：docker compose --profile app up -d --build（db → migrate 跑完 → api）
name: event-signup
services:
  db:
    image: postgres:18.6-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: event_signup
    ports:
      - "127.0.0.1:5434:5432"
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d event_signup"]
      interval: 2s
      timeout: 3s
      retries: 30
  # migration 是一次性的工作：跑完就結束。不放在 api 啟動時跑，多個副本才不會搶著改 schema
  migrate:
    profiles: [app]
    build:
      context: .
      target: build   # prisma CLI 是 devDependency，只在 build 階段；正式映像裡沒有
    command: ["npx", "prisma", "migrate", "deploy"]
    environment:
      DATABASE_URL: postgresql://app:app@db:5432/event_signup
    depends_on:
      db:
        condition: service_healthy
  api:
    profiles: [app]
    build: .
    environment:
      PORT: "3000"
      DATABASE_URL: postgresql://app:app@db:5432/event_signup
    ports:
      - "127.0.0.1:3001:3000"
    depends_on:
      db:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/health/ready').then(r => process.exit(r.ok ? 0 : 1), () => process.exit(1))"]
      interval: 5s
      timeout: 3s
      retries: 10
volumes:
  pgdata:

這份檔案很長，這一節先只看「容器之間怎麼連、外面怎麼連進來」，啟動順序那幾行留到下一節。

先注意 api 的 DATABASE_URL 寫的是 db:5432，不是你開發時用的 127.0.0.1:5434。原因要分開看主機和容器兩側。每個容器有自己的網路環境，容器裡的 127.0.0.1（localhost）指的是容器自己，不是你的電腦，也不是別的容器；api 容器裡連 127.0.0.1 找不到 PostgreSQL。compose 會為這份檔案的所有服務建一個共用的網路，在這個網路裡，服務名稱就是主機名稱，所以 api 用 db 就連得到資料庫容器，port 用的是 PostgreSQL 在容器裡聽的 5432。

ports 管的則是「主機連進容器」。"127.0.0.1:5434:5432" 的意思是：把主機的 127.0.0.1:5434 接到容器的 5432。所以你在電腦上跑 start:dev 時用 5434，容器之間則直接用 5432，兩邊不衝突。前面的 127.0.0.1 讓這個 port 只開給你自己的電腦，同一個網路的其他機器連不進來。

同樣的道理，api 對外是 3001:3000：容器裡的 API 照樣聽 3000，主機這一側用 3001，避開開發時 start:dev 佔用的 3000，兩個可以同時開。練習 3 要你填的 composeApi 就是這個 3001。

現在三個服務連得上彼此了。但「連得上」還不夠：docker compose up 是同時把容器開起來的，api 開起來的那一刻，資料庫可能還在初始化，資料表也可能還沒建。API 怎麼知道該等多久？

API 怎麼知道資料庫能連了、資料表建好了？

最直覺的做法是 depends_on: [db]，但它只保證 db 的容器先「啟動」。容器啟動了，代表裡面的 PostgreSQL 程序開始執行，不代表它已經能接受連線：PostgreSQL 第一次啟動要初始化資料目錄、建立資料庫，這段時間連過去會被拒絕。只寫 depends_on: [db]，api 有時剛好在資料庫準備好之後才連（沒事），有時太早（失敗），這種「偶爾壞、重啟一次就好」的問題最難查。

要等的不是「容器啟動」，而是「服務準備好」。compose 用 healthcheck（健康檢查）回答這件事：在服務上寫一個檢查指令，compose 定期執行它，指令成功（結束碼 0）就把服務標成 healthy。結束碼是程式結束時回報給系統的數字，0 代表成功、非 0 代表失敗，shell 和 Docker 都靠它判斷一個指令有沒有成功。

回到 compose 檔：

  • db 的 healthcheck 用 pg_isready：PostgreSQL 附的小工具，資料庫能接受連線時回傳 0。interval: 2s 每 2 秒檢查一次，timeout: 3s 單次檢查最多等 3 秒，retries: 30 連續失敗 30 次才判為 unhealthy。
  • condition: service_healthy：寫在依賴的那一方，意思是「等 db 變成 healthy 才啟動我」。這樣就不靠運氣，也不用寫「sleep 10 秒」這種猜時間的做法。

資料庫能連了，下一個問題是資料表。報名 API 需要第 1 課建的那些表，在新的資料庫裡它們還不存在，要先執行 prisma migrate deploy 把 prisma/migrations/ 裡的 migration 套用上去。這件事由 migrate 服務負責，它是一個一次性服務：不像 db 和 api 一直執行，它跑完 migrate deploy 就結束。

  • api 對 migrate 寫 service_completed_successfully：等 migrate 跑完、而且結束碼是 0，api 才啟動。migration 失敗時，api 根本不會啟動，不會用舊的 schema 跑起來、接請求再出錯。
  • migrate 用 target: build：prisma migrate deploy 需要 Prisma CLI（prisma 套件是 devDependency）與 prisma/migrations/，這兩樣只在 Dockerfile 的 build 階段有。target 讓 compose 只建到那個階段為止，拿它來跑 migration；api 用的正式映像保持乾淨。
  • api 也有 healthcheck：用 node 自己打 /health/ready（第 1 課做的、會檢查資料庫的那個端點）。不用 curl 是因為 alpine 映像沒有裝 curl，而 Node 24 內建 fetch。指令裡 r.ok 時用 process.exit(0)，否則 exit(1)，就是把 HTTP 的結果翻成 healthcheck 看得懂的結束碼。

整條啟動順序就是：db 變 healthy → migrate 跑完並回傳 0 → api 啟動 → api 變 healthy。指令的最後加上 --wait，docker compose up 會等到服務都 healthy（一次性服務則是跑完）才回來；任何一步失敗，指令就以失敗結束。這正是開場說的「一個指令跑起來」：

docker compose --profile app up -d --build --wait    # build 映像、依序啟動、等 api healthy
docker compose --profile app ps                       # migrate 是 Exited (0)，db 與 api 是 healthy
curl -s http://localhost:3001/health/ready
docker compose --profile app logs migrate             # 看套用了哪些 migration
docker compose --profile app down                     # 停掉並刪除容器（資料在 volume，加 -v 才會刪）

執行後先看 ps：migrate 顯示 Exited (0) 是正常的，代表它做完該做的事、成功結束了。練習 2 會用 docker compose --profile '*' config --format json 解析你的檔案（'*' 代表所有 profile，這樣標了 profile 的服務也會被列出來），檢查這三個服務與它們的條件。

到這裡，任務其實已經完成了。但 migrate 這個服務看起來多此一舉：為什麼不直接在 api 啟動前順便跑 migration？

migration 為什麼不在 API 啟動時順便跑？

把 api 的 command 寫成 npx prisma migrate deploy && node dist/main.js，少一個服務，看起來更簡單。只有一個 API 容器時它確實能用，問題出在你之後一定會遇到的情況。

多個副本同時啟動。正式環境為了分擔流量、某個容器掛掉時還有別的頂著，常常用同一個映像同時跑好幾個 API 容器，每一個叫一個副本（replica）。部署新版時，3 個副本會一起啟動，也就一起執行 migration。Prisma 有防這件事：migrate deploy 開始前會先拿 PostgreSQL 的 advisory lock。advisory lock 是一種由程式自己決定意義的鎖，PostgreSQL 只保證同一把鎖同一時間只有一個連線拿得到。所以 migration 不會被套用兩次（DevOps 課第 17 課），但另外兩個副本要排隊等鎖，等太久就逾時失敗、被重啟。一個要跑 2 分鐘的 migration，會讓所有副本的啟動都卡住，啟動時間變得不確定。

migration 失敗時。寫在 command 裡，migration 失敗會讓容器結束，平台把它重啟，又跑同一個失敗的 migration，再結束、再重啟。log 裡是一長串重複的錯誤，跟 API 的 log 混在一起。獨立的服務失敗一次就停，ps 看到非 0 的結束碼，logs migrate 看到原因，api 也不會啟動。

權限。改 schema（建表、加欄位）需要比較大的資料庫權限，API 執行時只需要讀寫資料。兩件事綁在同一個程序裡，API 就得一直帶著改 schema 的權限；分開之後，第 9 課才能讓 API 用權限比較小的帳號連線，被打進來時能做的事也少。

映像。migration 要 Prisma CLI，放進 api 的 command，正式映像就得帶著這個 devDependency，前面多階段建置省下來的又加回去了。

部署平台上也是同一個想法：migration 是部署流程裡的一個獨立步驟（平台上一次性的 job，或 CI 裡的一步），跑完而且成功，才換上新版 API。下一課的 CI 會用到。

💡 實務上：migration 是部署裡風險最高的一步
程式部署錯了可以退回上一版映像，migration 刪了欄位就退不回來。所以團隊會把它單獨拿出來：先看 SQL（code review 時看 migration.sql，不只看 schema.prisma）、先在 staging 跑、記錄跑了多久。報名 API 雖然小，也照這個習慣做；面試被問「你怎麼部署資料庫變更」時，你的 compose.yaml 就是答案：獨立步驟、先於新版程式、失敗就不啟動新版。

同一個映像換了環境，怎麼拿設定、怎麼被停掉？

現在的映像會被帶到很多地方：你的 compose、下一課的 CI、之後的正式環境。最後還有兩件事要處理，才算是一個可以放心交出去的映像：它到了新環境怎麼拿到設定，以及它要被停掉時怎麼好好離開。

設定從環境變數讀，啟動時驗證。「映像裡不能有秘密」那一節說過映像裡不放 .env、不寫 ENV DATABASE_URL，那設定從哪來？答案是執行容器時給環境變數，像 compose 檔裡 api 的 environment:。同一個映像在本機 compose、staging、正式環境，用不同的環境變數跑（DevOps 課第 11 課）。第 1 課的 src/config/env.ts 已經在驗證這些變數：

// src/config/env.ts：少了或格式錯就直接不啟動，不要等到第一個請求才爆
const schema = z.object({
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.url(),
})

在容器裡這更重要。設定不在你眼前的 .env，而是散在 compose 檔或部署平台的設定頁裡，少寫一個很常見。有驗證的話，容器一啟動就結束，docker compose logs api 第一行就是「環境變數設定錯誤：DATABASE_URL …」；沒有驗證的話，它會 healthy 地跑著，直到第一個請求用到資料庫才 500，而那可能是部署完好幾分鐘後、使用者先發現的。

收到 SIGTERM 時好好關機。容器會被停掉的時機很多：你執行 docker stop、部署新版要換掉舊容器、平台在流量低時減少副本。這些情況下，Docker 都是先送一個訊號給容器的主程序。訊號是作業系統通知程序的方式，SIGTERM 的意思是「請你結束」，程式可以接住它、做完收尾再離開；如果一段時間內（Docker 預設 10 秒）還沒結束，就改送 SIGKILL，直接把程序砍掉，程式沒有機會做任何事。被砍掉時，處理到一半的請求會斷線，資料庫連線也沒有正常關閉。

要接住 SIGTERM，有兩件事要同時成立：

  • 訊號要送得到 node。Docker 把訊號送給容器的主程序，也就是 CMD 啟動的那一個。CMD 用陣列寫法 ["node", "dist/main.js"] 時，node 直接就是主程序；寫成字串 CMD node dist/main.js 時，Docker 會先啟動一個 shell 再由 shell 執行 node，主程序變成 shell，訊號可能傳不到 node。多階段那一節留到這裡說明的那一行，原因就在這裡。
  • node 收到後要知道怎麼收尾。main.ts 的 app.enableShutdownHooks() 讓 Nest 收到 SIGTERM 時停止接新連線、呼叫各模組的 onApplicationShutdown（PrismaService 在這裡 $disconnect()），然後結束（Node 課第 21 課）。

自己確認：docker compose --profile app stop api 應該很快結束，而不是等滿 10 秒才被強制關掉。等滿 10 秒，代表上面兩件事至少有一件沒成立。到這裡，開場的任務完整了：一個指令建出乾淨的映像、依序啟動、到了別的環境換環境變數就能跑，被停掉時也會好好離開。

練習

練習 1：repo 根目錄的 Dockerfile 至少兩個 FROM（多階段），最後一個 stage 有 USER 而且不是 root 或 0；.dockerignore 排除 node_modules 與 .env。

練習 2：compose.yaml 有三個服務：postgres 映像的 db（有 healthcheck）、只跑 prisma migrate deploy 的一次性服務（等 db healthy）、api（等 db service_healthy 與 migrate service_completed_successfully，自己的 command 裡沒有 migrate）。服務放在 profile 裡也可以，測試用 --profile '*' 解析。

練習 3：在你的 repo 執行 docker compose --profile app up -d --build --wait，把 "composeApi": "http://localhost:3001" 加進 work/portfolio.json 的 small。測試打 composeApi 的 /health/ready，要 200 且資料庫是 up（composeApi 不能跟 api 一樣：要測的是容器，不是 start:dev）。

練習 4：同事把 api 的 command 改成 npx prisma migrate deploy && node dist/main.js，拿掉 migrate 服務，理由是「少一個服務比較簡單」。正式環境開 3 個 API 副本、這次部署有一個要跑 2 分鐘的 migration。會發生什麼？

✓ migrate deploy 有 advisory lock，不會重複套用（a 錯），但其他副本會卡在等鎖，等不到就失敗、被平台重啟，啟動時間跟 migration 綁在一起。b 是常見的誤解：沒有人「挑一個」，是大家搶同一把鎖。獨立的一次性服務跑完、成功才啟動 API，副本數多少都一樣。（第 4 課）

練習 5：api 寫成 depends_on: [db]，沒有 condition。docker compose up 時偶爾看到 api 的 log：「Can't reach database server」，重啟一次就好。原因是什麼？

✓ 「容器啟動了」與「服務準備好了」是兩件事。db 要有 healthcheck（pg_isready），api 寫 condition: service_healthy，compose 才會等到資料庫真的能連。b 錯：depends_on 控制啟動順序，只是預設只等到 started。（第 4 課）

練習 6：同事說：「.env 放進 .dockerignore 太麻煩，反正 repo 是私有的、映像也只推到公司的 registry。」把 .env 包進映像的主要問題是什麼？

✓ 映像會被複製到很多地方，而且同一個映像應該在不同環境用不同設定。秘密在執行時用環境變數或 secret 給，不進映像。a 的大小差異很小，不是重點；c 錯：Docker 不會檢查。（第 4 課、DevOps 課第 11 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • 最後的映像裡沒有原始碼與 devDependencies：docker compose --profile app exec api ls /app 只有 dist、node_modules、package.json；ls /app/node_modules/.bin 裡沒有 tsc、vitest。
  • 非 root：docker compose --profile app exec api id 是 uid=1000(node)。
  • migration 失敗時 API 不啟動：暫時把 migrate 的 DATABASE_URL 密碼改錯，up --wait 要失敗、api 沒有啟動（ps 裡 migrate 是非 0 的 Exited）。改回來。
  • 少一個環境變數就不啟動：暫時拿掉 api 的 DATABASE_URL，docker compose --profile app logs api 第一行說得出缺了什麼。改回來。
  • 關機很快：time docker compose --profile app stop api 遠小於 10 秒。
  • 從零開始一個指令跑得起來：docker compose --profile app down -v 之後，docker compose --profile app up -d --build --wait 成功、練習 3 通過。

常見錯誤

  • 只有一個 stage：編譯工具、devDependencies、原始碼都留在最後的映像。分 build、deps、執行三個 stage。
  • 沒有 USER：容器用 root 跑。最後一個 stage 加 USER node。
  • 沒有 .dockerignore：本機的 node_modules 被 COPY 進去、.env 進了建置環境。
  • build 時 prisma generate 因為沒有 DATABASE_URL 失敗，就在 Dockerfile 寫 ENV DATABASE_URL=…：連線字串留在映像裡。prisma.config.ts 改用 process.env.DATABASE_URL。
  • migrate 服務用最後的映像：正式映像沒有 Prisma CLI，npx prisma 會嘗試從網路下載（版本不受控）或直接失敗。用 target: build。
  • 容器之間用 localhost 連資料庫：容器裡的 localhost 是自己。用服務名稱 db:5432。
  • depends_on 不寫 condition：只等容器啟動，資料庫可能還不能連。db 加 healthcheck，api 寫 service_healthy。
  • CMD npm run start:prod：主程序變成 npm，訊號要靠它轉送給 node，多一層就多一個可能出錯的地方（Node 官方的 Docker 建議也是直接執行 node）。用 CMD ["node", "dist/main.js"]，再用自評清單的 stop 計時確認。

小結

  • 「在我電腦上能跑」靠的是本機的 Node、套件與 .env；映像把執行需要的一切打包，換哪台機器都一樣。
  • 多階段 Dockerfile：build 裝全部依賴並 prisma generate＋nest build，deps 只裝正式依賴，最後的映像只複製 dist 與 node_modules。先 COPY package*.json 再 COPY 程式，改程式時 npm ci 用快取；npm ci 需要 commit 過的 package-lock.json；版本寫死。
  • 秘密不進映像：prisma.config.ts 用 process.env.DATABASE_URL 讓建置不需要連線字串，不寫 ENV DATABASE_URL；.dockerignore 排除 node_modules、.env。最後的映像用 USER node 執行。
  • compose 用 profile 分開發（只開 db）與類正式（db → migrate → api）；容器之間用服務名稱 db:5432 連，ports 管主機連進來的那一側。
  • 順序靠健康，不靠時間：service_healthy 等 healthcheck 通過，service_completed_successfully 等一次性服務成功結束；--wait 讓一個指令等到整套 healthy。
  • migration 是獨立的一次性服務，不在 API 啟動時跑：副本多時不搶鎖、失敗原因清楚、API 不用改 schema 的權限、正式映像不帶 Prisma CLI。
  • 設定在執行時用環境變數給、啟動時驗證；CMD 用陣列寫法讓 node 收到 SIGTERM，enableShutdownHooks() 關掉連線池再結束。
