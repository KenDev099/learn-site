階段 B3：上線與作品 · 第 19 課

包裝作品：README、架構圖、ADR 與 demo

你花了 18 課做出一個多租戶 SaaS 後台：兩道租戶隔離的防線、refresh token 輪替、RBAC、稽核、檔案、背景匯出、方案上限、可觀測性、CI/CD、資安檢查。下週你要把 repo 連結放進履歷投出去。問題是，面試官看它的時間通常只有5～10 分鐘：打開 README、看一張圖、點一兩份設計文件、也許試一下 demo，然後在面試時問你幾個問題。他在這 10 分鐘裡看不到的東西，對他來說就不存在，不管你在程式裡花了多少心思。

這是最後一課，任務只有一個：把作品準備成「面試官 10 分鐘內看得懂、看得出你的判斷」的樣子。整課照面試官實際走的路線往下：他先打開 README，所以先決定 README 怎麼排；README 的架構節需要圖；圖說明「是什麼」，他想知道「為什麼」時會點 ADR；這些東西在 repo 設成 public 的那一刻全部公開，所以公開前要檢查 git 歷史；面試時他會說「demo 一下」，所以要有一條排練過的路線；demo 完他會追問，所以最後準備怎麼講，以及怎麼把同樣的內容寫進履歷。

這課會用到：

面試官打開 repo 的第一分鐘：README 要怎麼排？

面試官點開你的 repo，GitHub 首頁顯示的就是 README。他不會先讀程式碼，也很少真的 git clone；README 是他唯一一定會讀的東西，而且是從上往下讀，讀到失去興趣就關掉。所以 README 的問題不是「要寫什麼」，而是「照什麼順序寫」：照讀者想知道的順序，最想知道的放最上面。

職涯課第 3 課的 README 骨架是「簡介 → 架構 → 快速開始 → 測試 → 設計決定 → 已知限制」，就是照這個原則排的。SaaS 作品沿用同一個原則，但多兩樣東西要放在很前面：demo 連結與示範帳號，以及分成平台與業務的功能清單。先看整體長相，再逐段說為什麼：

# My SaaS：多租戶團隊後台

一句話：給小型團隊用的 SaaS 後端，多租戶隔離（Prisma extension＋PostgreSQL RLS）、
成員與角色、稽核、檔案、背景匯出、方案上限。NestJS 12、Prisma 7、PostgreSQL 18、Redis。

## Demo
https://…（第一次開啟約 30 秒喚醒）
| 帳號 | 角色 | 可以看到什麼 |
|---|---|---|
| owner@demo.example.test | owner | 全部，包括方案與稽核 |
| member@demo.example.test | member | 建立與編輯 project、上傳檔案、匯出 |
| viewer@demo.example.test | viewer | 只能讀，試試看建立 project 會 403 |
密碼：demo-pass-2026（資料每天 03:00 重設）。API 文件：/docs

## 架構            ← 元件圖（Mermaid），連到 docs/architecture.md 的時序圖
## 功能            ← 平台（契約裡的那些）與業務（你的題目）分開列
## 設計決定        ← ADR 表：編號、一句話決定、連結
## 如何執行        ← 從 clone 到啟動不超過 5 步，照著打就能跑：npm ci → cp .env.example .env
                  → npx prisma generate → npm run dev:up → npx prisma migrate deploy && npm run start:dev
## 測試            ← npm test；有幾個測試、跨租戶測試在哪個檔
## 已知限制與下一步

這個順序對應面試官心裡依序出現的四個問題：

  • 「這是什麼、能不能直接玩？」所以一句話說明與 Demo 在最上面。一句話裡同時交代產品（給小型團隊的 SaaS 後端）、最核心的技術點（兩道隔離防線）和技術棧，讓他在 10 秒內決定要不要繼續看。示範帳號分成三種角色，並寫出每種角色「可以看到什麼」，是在邀請他自己驗證你的 RBAC：用 viewer 建立 project 真的會 403。
  • 「做得多深？」所以接著是架構與功能。功能清單分平台與業務列，是因為多租戶 SaaS 的難處在「平台」：租戶隔離、成員、角色、稽核、方案這些每個 SaaS 都要有的底層。分開列，面試官一眼就看出你懂平台是什麼；業務模組則展示你把一條流程做到有深度（第 6 課的範圍決定）。混在一起列，十幾項功能看起來就只是一份很長的清單。
  • 「為什麼這樣做？」有興趣的人才會點設計決定，所以它在功能之後，只放一張 ADR 表，細節在連結裡。
  • 「我能自己跑嗎？」「如何執行」與「測試」放後面，因為大部分人不會真的 clone。但它要寫到照打就能跑，願意 clone 的那一位通常是最認真看的人。

Demo 這一節是整份 README 最能留住人的地方，所以就算還沒部署（第 17 課的部署是選做），它也要有：放一段 1～2 分鐘的錄影或幾張截圖（走一次後面「demo」那一節的路線），再寫本機怎麼用示範帳號跑起來。面試官看不到「能玩」，至少要看到「它真的會動」。

最後一節「已知限制與下一步」常被當成扣分項而省略，其實是加分項：它說明你知道作品跟正式產品差在哪。參考實作寫的是「沒有接金流」「檔案存本機磁碟，正式環境要換 S3 相容儲存」「worker 跟 API 同一個程序」，第 15 課還可以加「成功回應沒有寫進 OpenAPI」。每一條都是面試時可以展開的題目，最後一節會用到它們。

README 的骨架定了，但「架構」那一節現在只有一個標題。面試官讀到這裡想知道系統長什麼樣子，用文字描述「API 連資料庫、Redis、物件儲存，worker 從 Redis 拿工作」他很難在腦中組起來。這一節需要圖。

💡 實務上：README 的順序就是寫給忙碌讀者的順序
工作上的 README、設計文件、事故報告都適用同一條規則：先回答讀者最想知道的事，細節往後放。新同事打開服務的 README，最想知道「這是做什麼的、我要怎麼在本機跑起來」；PM 打開設計文件，最想知道「結論是什麼、要多久」。寫之前先問「誰會讀、他最先想知道什麼」，再決定順序，這跟工程實務課第 7 課的「先給結論」是同一件事。你的作品 README 就是第一個練習對象。

README 的架構節：要畫哪兩張圖，各回答什麼問題？

架構節要畫圖，第一個決定是用什麼畫。這個作品用 Mermaid：一種用文字描述圖的語法，寫在 Markdown 的 ```mermaid 程式碼區塊裡，GitHub 顯示 README 時會直接把它畫成圖。選它而不是畫圖軟體輸出的圖片，理由有兩個：一是它就在 README 裡，面試官不用另外開檔案；二是它是文字，架構改了，你在同一個 PR 裡改程式也改圖，review 的人看得到圖的 diff。圖片檔做不到這點，改一次架構就得重新開畫圖軟體，久了就沒人更新，圖跟程式對不上。

第二個決定是畫幾張。常見的失敗是畫一張大圖，把每個模組、每條連線都放上去，結果什麼都畫了、什麼都看不出來。原則是一張圖只回答一個問題。面試官對架構有兩個問題，所以畫兩張就夠。

第一個問題：「有哪些東西、誰連誰？」這用元件圖回答（參考實作的 docs/architecture.md）。flowchart LR 是從左到右的流程圖，方框是元件，箭頭是連線方向，[( )] 畫成圓柱，代表存資料的地方：

```mermaid
flowchart LR
  web[Vue 前端] -->|HTTPS| api[NestJS API]
  api --> db[(PostgreSQL)]
  api --> redis[(Redis)]
  api --> storage[(物件儲存)]
  api --> mail[SMTP]
  redis --> worker[匯出 worker]
  worker --> db
  worker --> storage
```

看這張圖，面試官知道系統有一個 API、一個匯出 worker、三種儲存和一個寄信服務，也看得出 worker 不經過 API，直接從 Redis 拿工作、自己讀寫資料庫與物件儲存。這最後一點會引出很好的追問：「worker 讀資料庫時，租戶隔離還在嗎？」（答案在第 13 課，也是階段檢核的練習 11。）

第二個問題：「一個請求怎麼被限制在自己的租戶裡？」這是整個作品的核心，也是面試最常被問的「租戶怎麼隔離」。元件圖回答不了它，因為隔離發生在請求經過的每一步，需要按時間順序看。這用時序圖（sequenceDiagram）回答：上面一排是參與者，往下每一個箭頭是一步，越下面越晚發生。

```mermaid
sequenceDiagram
  participant C as 前端
  participant M as RequestIdMiddleware
  participant G as AccessGuard
  participant S as Service
  participant D as TenantDb
  participant P as PostgreSQL
  C->>M: GET /api/v1/projects（Bearer token）
  M->>G: ALS 開一個 { requestId }
  G->>G: 驗 JWT，取 sub、tid 放進 ALS
  G->>D: 查 membership（角色以資料庫為準）
  G->>S: 權限符合
  S->>D: project.findMany()
  D->>P: BEGIN; set_config(app.tenant_id); SELECT … WHERE tenant_id = …; COMMIT
  P-->>C: 只有這個租戶的資料（RLS 再擋一次）
```

由上往下讀，就是一個請求的一生：middleware 為它開一個帶 requestId 的上下文（圖上的 ALS 是 Node 的 AsyncLocalStorage，讓同一個請求裡的程式都讀得到這份上下文，見第 8 課）；guard 驗 token、把使用者與租戶放進上下文，再到資料庫確認角色；service 查資料時不用自己寫租戶條件，TenantDb 在交易裡設好 app.tenant_id 並自動加上 WHERE tenant_id；最後 PostgreSQL 的 RLS 再擋一次。面試時被問到隔離，指著這張圖從上講到下就好。

注意圖裡的名字：AccessGuard、TenantDb、RequestIdMiddleware 都是程式裡真正的類別名稱，不是「驗證層」「資料層」這種泛稱。面試官對某一步有興趣，拿名字去 repo 搜尋就找得到程式，圖與程式之間沒有翻譯成本。

兩張圖讓面試官看懂系統「是什麼」，但一個認真的面試官看完時序圖，會冒出下一個問題：「為什麼要兩道防線？為什麼不每個租戶一個資料庫？」圖回答不了「為什麼」，這要靠設計決定。

💡 實務上：圖是給別人用的
工作上新同事加入、或要跟 PM 解釋為什麼某個需求要兩週，你會用的就是這兩張圖。元件圖回答「改這個會影響誰」，時序圖回答「這個請求在哪一步可能出錯」。圖跟程式放在同一個 repo、同一個 PR 更新，就不會變成三年前的投影片。code review 時看到新增了服務或改了請求的流程，卻沒動 docs/architecture.md，就是該留言的地方。

面試官想知道「為什麼」：ADR 要有哪幾份、怎麼維護？

圖說明「是什麼」，ADR 說明「為什麼」。系統設計課第 18 課教過，ADR（Architecture Decision Record，架構決策紀錄）是一個決定一份的短文件，分成狀態、背景、決定、後果四節。面試官點開一份 ADR，看的不是你選了什麼，而是你有沒有比較過別的選項、有沒有寫出這個決定的代價。所以「後果」這一節一定要寫代價：只寫好處的 ADR 看起來像在辯護，寫出代價的才看得出你知道自己在取捨什麼。

這門課做到這裡，你在幾個轉折點都做過有取捨的決定，每一個都該有一份 ADR。下面是參考實作的編號；最右欄是面試官讀完會追問的問題，寫 ADR 時就先把答案寫進去：

ADR決定哪一課面試會追問
0001共用資料表＋tenant_id6為什麼不用每租戶一個資料庫
0002Prisma extension 與 RLS 兩道防線9只用一道為什麼不夠；效能代價
0003短效 access token＋輪替的 refresh token7成員被移除後 token 還有效嗎

你在第 16 課（指標與追蹤要不要做）、第 17 課（部署目標）做的決定也值得各寫一份。這些 ADR 加起來（表上 6 份，加上第 16、17 課的就是 0007、0008），等於把整門課最重要的判斷都留下了書面紀錄，面試官點哪一份都有東西可看。

ADR 寫好之後，真正容易出錯的是維護。作品會繼續長，決定會被推翻，這時有兩條規則（練習 2 會檢查第一條的編號，練習 1 檢查第二條）：

第一條，編號連續，不刪舊的。假設半年後你把 worker 拆成獨立服務，0005「worker 跟 API 同程序」就不再成立。直覺的做法是改 0005 的內容讓它符合現況，或刪掉它；兩種都會讓歷史斷掉。ADR 的價值正在於保留「當時為什麼這樣選」：當時只有一個人維護、流量小，同程序部署最簡單。這個理由消失了，後來的人就看不出一開始為什麼不拆，甚至可能在條件又變回來時做出錯誤的判斷。正確的做法是寫一份新的 ADR（例如 0009：拆出 worker 服務），說明是什麼條件變了；0005 內容不動，只把狀態改成「被 0009 取代」。

第二條，README 連到的每一份都存在。README 的設計決定那一節是一張連到 docs/adr/ 的表，檔名改過、連結沒跟著改，是作品裡最常見的壞連結。面試官點下去看到 404，前面建立的「這個人很仔細」的印象就打了折扣。

到這裡，README、圖、ADR 都準備好了，repo 可以設成 public 了。但按下去的那一刻，repo 裡的一切都會公開，而「一切」不只是你現在看得到的檔案。

按下 public 之前：git 歷史、示範資料、授權要檢查什麼？

職涯課第 3 課列過公開前要找的東西。這個 SaaS 作品比一般作品多了幾樣敏感的東西，有三件事要特別檢查。

第一件，也是最重要的：git 歷史，不只是現在的檔案。這個作品有 JWT_SECRET、兩組資料庫密碼，也許還有部署平台的金鑰。很多人會說「那個金鑰我後來刪掉了」，但 git 保存的是每一次 commit 的完整內容：你在第 5 個 commit 加進 .env、第 6 個 commit 刪掉，任何人 clone 下來切到第 5 個 commit，金鑰就在那裡。repo 一公開，就有自動掃描 GitHub 找金鑰的程式在跑，被找到的時間可能比你想像的短。

所以檢查要掃整段歷史。練習 3 對 git log -p --all（印出所有分支每個 commit 的完整變更）掃描 AWS access key、私鑰、sk_live_、GitHub 與 Slack 的 token。找到了，處理的順序是：

  1. 先到那個服務撤銷這把金鑰、換一把新的。已經進過 git 的金鑰要當成已經被別人用過，因為你無法證明沒有。
  2. 再用 git filter-repo 從歷史移除。它是改寫 git 歷史的工具，會重寫含有那個檔案的 commit，以及之後的每一個 commit，它們的雜湊值都會改變，所以要 force push 覆蓋遠端的歷史，其他人手上的舊 clone 也要重新 clone。

順序不能反。只改寫歷史而不撤銷，等於假設沒有人複製過那把金鑰；如果 repo 曾經公開過哪怕一下子，或有人 fork 過，那份舊歷史就不在你的控制內，金鑰照樣能用。撤銷才是真正讓外洩失效的一步，改寫歷史只是不讓它繼續被看到。

同樣在這一步，.env.example 也要再看一次。它是會被 commit 的範本檔，告訴別人需要哪些環境變數。參考實作裡的 JWT_SECRET=dev-only-… 是刻意寫成一看就知道是開發用的值，CI 用的也是 ci-only-…；真正的值只存在部署平台的 secret 設定裡（第 17 課）。這樣就算有人照抄範本，也不會拿到能用在正式環境的值。

第二件：示範資料沒有真實個資。README 裡放了示範帳號，等於邀請陌生人進你的 demo 環境操作，而這個作品會寄邀請信。如果 seed 裡用了真實的 email，有人在 demo 裡按一下「邀請」，信就寄到一個陌生人的信箱。seed 與 demo 的資料一律用 @example.test 的 email 與假名字：.test 是保留給測試用的網域，信不會真的寄到任何人手上。第 17 課的每日重設也要確認只會載入這份示範資料，不會把正式資料帶進來。

第三件：授權。repo 加一個 LICENSE 檔（作品常用 MIT），README 寫明「個人練習專案」。沒有授權的公開程式，別人在法律上不能使用；這對求職作品影響不大，但它說明你知道開源授權這件事，也讓 README 對作品性質的交代是完整的。

檢查完，repo 可以安心公開。面試官看完 README，到了面試當天，下一個請求通常是：「可以 demo 一下嗎？」

💡 實務上：外洩的 secret 先撤銷，這條在工作上一樣適用
工作上最常見的情境是同事不小心把 .env 推上公司的 repo，或把金鑰貼在 PR 留言裡。資深的處理順序永遠是：先撤銷換新、確認服務改用新的值後正常運作，再清理歷史，最後在事後檢討裡補上防呆（例如 CI 加 secret 掃描、.gitignore 加 .env）。只清歷史不換金鑰，是把「沒被看到」當成「沒被用到」。你的作品在公開前跑一次練習 3，就是在演練這個流程。

「可以 demo 一下嗎？」：3 分鐘的路線，為什麼也是回歸測試？

面試時被說「可以 demo 一下嗎」，最常見的失敗是即興：打開網站，想到哪點到哪，點到一半發現忘了準備第二個租戶的帳號，或某個功能剛好壞了。面試官只看到一堆畫面切換，看不出你想展示什麼。你要的是一條排練過的路線：3 分鐘內走完，而且每一步都在展示一個判斷，不只是一個功能。

這條路線的設計方式，是從作品最想讓人記住的判斷倒推：租戶隔離、角色權限、稽核、方案上限，每個判斷安排一步讓它被看見：

  1. owner 登入，邀請一位 member（30 秒）：打開 Mailpit（第 10 課的假郵件伺服器）看邀請信，連結來自設定的網址、token 一次性（第 10 課）。
  2. member 建立 project、上傳檔案、匯出 CSV（60 秒）：匯出回 202，輪詢到 done（第 12、13 課）。
  3. 換成另一個租戶的帳號，把網址上的 id 貼過去（30 秒）：404。這是整個 demo 最重要的一刻，講兩道防線（第 8、9 課）。
  4. owner 打開稽核紀錄（30 秒）：剛才的每個動作都在，帶著 requestId（第 11、16 課）。
  5. viewer 試著建立 project（30 秒）：403；再用 owner 連續建立到第 4 個：PLAN_LIMIT_REACHED（第 10、14 課）。

第 3 步是整條路線的高潮。面試官看過很多「功能都做出來」的作品，但「把別家公司的 id 貼進網址，拿到的是 404 而不是資料」，直接展示了多租戶系統最重要的那個保證。這時停下來，指著上面的時序圖講兩道防線，demo 就從「展示功能」變成「展示判斷」。

這條路線還有第二個用途。仔細看，它從邀請、建立、上傳、匯出、跨租戶、稽核到方案上限，幾乎碰到了每一個平台功能。這正是回歸測試需要的形狀：回歸測試是用來確認「以前能動的東西，改了程式之後還能動」的測試。這個作品的功能彼此相連，第 16 課改了 requestId 的傳遞方式，可能讓第 11 課的稽核少了欄位；第 18 課改了錯誤處理、不再把內部訊息原樣回傳，可能讓錯誤回應少了 requestId。單元測試只看各自的模組，抓不到這種跨模組的壞掉；一條走過全部功能的路線抓得到。更實際的是，如果你只在面試前手動走一次，發現壞了也來不及修。

所以練習 4 把這條路線寫成自動化測試，對啟動中的 API 實際跑一次。它還多檢查三樣東西：「同時建立 10 個 project，免費方案恰好停在 3 個」的併發檢查（手動 demo 示範不出同時送出的請求）；面試官打開網址時第一眼看到的 health 與 /openapi.json；以及錯誤回應裡的 requestId。在你自己的 repo 也放一份（例如 test/demo.e2e-spec.ts），部署前跑它，面試前一天也跑它；它通過，你就知道明天的 demo 不會在第 3 步出意外。

demo 走完，面試不會就此結束。面試官看過 404、看過 PLAN_LIMIT_REACHED，接下來會問：「你為什麼這樣做？」「還差什麼才能上正式？」這些問題沒辦法用 demo 回答，要用講的。

demo 之後的追問：怎麼把作品講出判斷，再寫進履歷？

職涯課第 10 課教過怎麼把作品放進事實表、作品卡與故事庫。這一節是那套方法套到這個作品上的具體內容：開場怎麼講、挑哪兩個取捨講深、兩個必定會被問的問題怎麼答，最後把同樣的內容壓縮成履歷上的幾行。

先準備 30 秒的開場。面試官最常的第一句是「介紹一下這個作品」。很多人會從第一個功能開始一路講下去，講了三分鐘面試官還不知道重點在哪。照「是什麼 → 最難的地方 → 怎麼證明」三句講完，然後停下來，讓他選要追問哪裡：

「這是一個給小型團隊用的多租戶 SaaS 後端，NestJS 加 PostgreSQL。
最難的是租戶隔離：我用應用層的 Prisma extension 加資料庫的 RLS 兩道防線，
每個資源都有跨租戶的 E2E 測試，CI 每次都跑。也處理了方案上限的併發問題，
可以展開講其中一個。」

開場只放鉤子，不講細節。最後那句「可以展開講其中一個」是把主導權交給面試官，同時把他引到你準備得最好的兩個題目上。

接著，挑兩個取捨講深，不要列十個功能。面試官面試完記得住的，不是你做了幾個功能，而是「他為什麼這樣選」。一個講得出決定、代價和踩過的坑的取捨，比十個功能名稱有說服力。這個作品最好講的兩個：

  • 租戶隔離的兩道防線：「我用共用資料表加 tenant_id，因為租戶多、資料小（ADR 0001）。代價是漏一個條件就外洩，所以應用層用 Prisma extension 自動加條件，資料庫層用 RLS 再擋一次。實作時發現 extension 包交易的 client 不能開互動式交易，否則回滾不了，所以另外做了 tx()。」這段有決定、代價、踩過的坑（tx() 的來由見第 9 課）。
  • 用量上限的競態：「免費方案 3 個 project。兩個請求同時建立第 3 個時，先 count 再 insert 會變成 4 個。我在同一個交易裡 FOR UPDATE 鎖租戶那一列，測試是同時送 10 個、最後恰好 3 個。」這段有一個具體的 bug、一個修法，和一個能證明修好的測試數字。

講完取捨，有兩個問題幾乎一定會出現。

被問「為什麼不用每租戶一個資料庫」：這是在測試你是否真的比較過替代方案。不要說「因為比較簡單」，這會讓取捨聽起來像偷懶。要說條件：「這個產品的租戶是小團隊，數量多、每家資料小；每租戶一個資料庫，migration 要跑幾千次、連線池無法共用。如果有大客戶要求實體隔離，我會為他另開資料庫，寫一份新的 ADR 取代 0001。」這段回答的結構可以套到任何「為什麼不用 X」的問題：先講在什麼條件下你的選擇成立，再講代價，最後講什麼條件出現時會改變它。最後一句也呼應了前面 ADR 的維護規則：決定會變，變的時候寫新的。

被問「還差什麼才能上正式環境」：這是在看你知不知道作品與產品的差距，也是 README 那一節「已知限制」派上用場的時候。照它講，並排出順序：金流與帳務（目前是模擬的升級）、檔案改存 S3 相容儲存、備份與還原演練（DevOps 課第 24 課）、監控與告警（指標、on-call）、worker 拆成獨立服務與追蹤。能說出「我會先做哪一個、為什麼」，比清單本身重要：例如金流排第一，因為沒有它產品就沒有收入；備份排在監控前，因為資料丟了無法挽回，而監控缺了只是發現問題比較慢。

最後，把同樣的內容寫進履歷。履歷是面試官打開 repo 之前讀的東西，它的工作是讓人想點開連結。用職涯課第 2 課的「動作＋範圍＋結果」，每一行對應上面講過的一個取捨或一個平台功能：

多租戶 SaaS 後台（個人專案，NestJS／Prisma／PostgreSQL／Redis）
・以 Prisma extension＋PostgreSQL RLS 兩道防線實作租戶隔離，每個資源都有跨租戶 E2E 測試
・設計 refresh token 輪替與重用偵測、資料庫為準的 RBAC，被移除的成員 token 立即失效
・用量上限以交易＋列鎖處理競態，併發測試 10 個同時建立恰好通過 3 個
・CI 跑真實 PostgreSQL／Redis 與 RLS，映像以 commit SHA 標記，部署後自動冒煙測試

每一行都要經得起追問：寫進去的，面試官問「怎麼做的」你都要能講 3 分鐘，而且 repo 裡找得到對應的程式與測試。做不到的就不要寫，因為履歷上每一行都是在邀請面試官追問。上面的範例是參考實作的版本：數字（10 個、3 個）換成你自己測試裡的，業務模組做了什麼也加一行，例如「工單狀態機以 409 擋下不合法的轉換」。

到這裡，面試官的整條路線都準備好了：履歷讓他點開連結，README 讓他 10 秒內知道這是什麼，兩張圖讓他看懂系統，ADR 讓他看到判斷，demo 讓他親眼看到 404，最後的追問你都有答案。

💡 實務上：「先講條件、再講代價、最後講什麼會改變它」不只用在面試
工作上的技術討論、設計審查、跟主管解釋為什麼不用某個新技術，都是同一個結構。資深工程師很少說「X 比較好」，而是說「在我們現在的條件下 X 比較合適，代價是 Y；如果之後出現 Z，就該重新評估」。這樣的回答讓別人知道你的判斷什麼時候會失效，也讓決定可以被檢查。面試時把作品講成這個結構，面試官看到的就是你在工作上會怎麼討論技術。

補充與查表

  • 模組之間的依賴方向：第 6 課定下的「哪個模組可以 import 哪個」用表格比用圖清楚，因為它是一組規則，不是一條流程。參考實作把它放在 docs/architecture.md 的「模組與依賴方向」，跟兩張圖在同一個檔案。
  • 這課用到的 Mermaid 語法：flowchart LR 從左到右的元件圖，a --> b 箭頭，-->|文字| 箭頭上的標籤，[( )] 圓柱（存資料的地方）；sequenceDiagram 時序圖，participant X as 名稱 參與者，->> 請求，-->> 回應。查表用，不用背。

練習

練習 1：README 有 Demo、架構、功能、設計決定、如何執行、測試、已知限制這幾節（## 標題）；README 或 docs/architecture.md 有 Mermaid 的 flowchart（元件圖）與 sequenceDiagram（帶租戶的請求）；README 連到 docs/adr/，而且每個相對連結指到的檔案都存在。

練習 2：docs/adr/ 至少 5 份 NNNN-標題.md，每份都有狀態、背景、決定、後果四節，編號從 0001 開始連續。

練習 3：git log -p --all 裡沒有常見的 secret 樣式（AWS access key、私鑰、Stripe 正式金鑰、GitHub token、Slack token）。

練習 4：對你啟動中的 API 跑一次 demo 腳本：owner 註冊、邀請 member；member 建立 project、上傳 PNG、匯出到 done；另一個租戶讀這三樣都 404；稽核有對應的 action；/billing 的用量是 1 個 project、2 位成員。再加上 10 個同時建立 project 恰好成功 3 個，以及 /health/ready、/openapi.json，以及錯誤回應 body 的 requestId 等於標頭的 x-request-id。

練習 5：README 的開頭要放什麼？你有一張很完整的架構圖、一段 5 步的安裝說明、一個 demo 網址。

✓ README 照讀者的順序：先知道是什麼、能不能直接玩，再看做得多深。大部分面試官不會 clone 你的專案，安裝說明放最前面等於讓他們先讀最用不到的部分（a）。架構圖要有，但在知道「這是什麼」之後才看得懂（b）；功能清單太長反而看不出重點（d）。（第 19 課）

練習 6：面試官看完你的作品，問：「你的 SaaS 為什麼不讓每個租戶用自己的資料庫？那樣隔離不是更徹底嗎？」最好的回答是？

✓ 好的回答先講條件（租戶多、資料小）、再講代價與怎麼補、最後講什麼條件會讓決定改變。a 把取捨說成偷懶；c 說得比事實肯定，實體隔離在「備份還原單一租戶」「吵鬧鄰居」上確實不同；d 沒有自己的理由。（第 19 課，第 6 課 ADR 0001）

練習 7：你的 ADR 0005 寫「worker 跟 API 同一個程序」。現在要把 worker 拆成獨立服務。ADR 怎麼處理？

✓ ADR 是決定的歷史，價值在於看得到「當時為什麼這樣選、後來為什麼改」。改內容（b）或刪掉重寫（c）都會讓這段歷史消失，後來的人看不出一開始不拆的理由，可能又改回去。d 錯在架構一直在變，重要的改變都值得一份。（第 19 課）

自評清單

  • 10 分鐘測試：請一個沒看過作品的朋友（最好是工程師）只看 README 10 分鐘，再請他說出「這是什麼、租戶怎麼隔離、你做過最難的取捨」。說不出來的，就是 README 要改的地方。
  • 圖在 GitHub 上畫得出來：推上去後打開 README 與 docs/architecture.md，兩張 Mermaid 圖都正常顯示。
  • 「如何執行」照打跑得起來：在另一個資料夾重新 git clone，只照 README 的步驟打，不靠你本機已有的 node_modules、.env 或資料庫，/health/ready 回 200。
  • demo 走過三次：照 3 分鐘的路線計時走三次，每一步你都說得出它在展示什麼。
  • 示範帳號可用：用 README 寫的帳密登入 demo 環境，三種角色看到的東西不一樣。
  • 履歷的每一行都找得到證據：每一行對到 repo 裡的一個檔案或測試，面試前把連結整理在一份筆記。
  • LICENSE 與「個人練習專案」：repo 有授權檔，README 寫明作品性質。
  • 換進求職包：照職涯課第 10 課，把這個作品換進事實表、作品卡與故事庫。

常見錯誤

  • README 從安裝步驟開始：大部分面試官不會 clone，最先想知道的是「這是什麼、能不能直接玩」。一句話與 demo 放最上面，如何執行放後面。
  • 沒部署就省略 Demo 那一節：面試官看不到它會動。放錄影或截圖，再寫本機怎麼用示範帳號跑起來。
  • 架構圖畫成一張大圖：每個模組、每條線都在，看不出重點。一張圖回答一個問題，名字用程式裡的名字。
  • ADR 被推翻就改內容或刪掉：「當時為什麼這樣選」的歷史就斷了。寫新的 ADR，舊的內容不動、狀態改成被取代。
  • 只刪掉現在的 secret 檔：git 歷史裡還在。先到服務撤銷換新，再用 git filter-repo 改寫歷史。
  • demo 環境用真的 email：邀請信寄到陌生人的信箱。示範資料一律 @example.test。
  • demo 即興、面試前沒跑過：點到一半才發現壞了。把路線寫成測試，部署前與面試前一天各跑一次。
  • 列十個功能、一個取捨都沒講：面試官看不出判斷。挑兩個講深，其他放功能清單。
  • 履歷寫了做不到的事：面試官一追問就露餡。只寫 repo 裡找得到證據的。

小結

  • 整課照面試官的 10 分鐘走：README → 圖 → ADR →（公開前檢查）→ demo → 追問與履歷。他看不到的東西，對他來說就不存在。
  • README 照讀者想知道的順序：一句話、demo 與示範帳號、架構、功能（平台／業務分開）、設計決定、如何執行、測試、已知限制。
  • 兩張 Mermaid 圖各回答一個問題：元件圖回答「有哪些東西、誰連誰」，時序圖回答「租戶怎麼被隔離」；名字用程式裡的名字，跟程式在同一個 PR 更新。
  • ADR 說明「為什麼」，後果一定寫代價；至少涵蓋隔離、兩道防線、token、檔案、背景工作、方案與限流；編號連續，被推翻就寫新的、舊的改狀態。
  • 公開前掃整段 git 歷史，不只現在的檔案；外洩的 secret 先撤銷換新，再改寫歷史。示範資料用 @example.test，加 LICENSE。
  • 3 分鐘的 demo 路線每一步展示一個判斷，跨租戶 404 是高潮；它碰到每個平台功能，所以也是最好的回歸測試。
  • 面試挑兩個取捨講深；被問替代方案時先講條件、再講代價、最後講什麼會讓決定改變。履歷的每一行都要在 repo 裡找得到證據。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 8：你的 SaaS 的 access token 裡有 tid（租戶）。前端在切換團隊的下拉選單，送 x-tenant-id 標頭指定要操作的租戶，看起來更彈性。為什麼作品不這樣做？

✓ 租戶是授權的根，不能來自使用者能控制的輸入。要支援多個租戶，就讓伺服器在 switch-tenant 檢查 membership，再簽一個新的 token。b 是最常見的錯誤：格式合法不代表你是那個租戶的成員。（第 7、8、10 課）

練習 9：有了 Prisma extension 自動加 tenantId，為什麼還要 RLS？

✓ 兩道防線管的範圍不同：extension 是應用層、只管經過它的程式；RLS 是資料庫層、只要連線角色對就管得到。c 錯在 RLS 需要每個操作包交易＋set_config，不會比較快，而且拿掉 extension 後，RLS 擋下的查詢只會靜靜回空陣列，比較難查。兩道都在，再加跨租戶測試確認它們真的有效。（第 8、9 課）

練習 10：PrismaService 用擁有者帳號連線，資料表都 ENABLE＋FORCE 了 RLS。哪裡會出事？

// .env
APP_DATABASE_URL=postgresql://owner:owner@db:5432/my_saas   # 擁有者，也是 POSTGRES_USER

✓ FORCE 讓一般的擁有者也受 policy 限制，但 superuser 與有 BYPASSRLS 的角色永遠繞過（b 只對了一半，是最多人會選的）。所以執行時要用另一個角色：不是 superuser、沒有 BYPASSRLS、不是表的擁有者，也就是作品的 pf_app。擁有者帳號只給 migrate 用。（第 9、17 課）

練習 11：匯出的 worker 從 BullMQ 拿到 job，要讀這個租戶的 projects。哪個做法對？

✓ worker 裡沒有請求，AsyncLocalStorage 是空的；用 job 裡的 tenantId 重建同一個上下文，extension 與 RLS 照樣兩道都在。a 是最多人會選的「系統身分」：等於在 worker 裡關掉兩道防線，只剩一個手寫的條件。b 讓 Redis 存著一份可能過期的資料。d 在沒有上下文時，參考實作的 TenantDb 會直接丟錯（fail closed）。（第 13 課）

練習 12：免費方案最多 3 個 project。下面的程式在單一請求的測試都通過，上線後卻出現有 4 個 project 的免費租戶。為什麼？

const count = await tx.project.count()
if (count >= 3) throw planLimit('project 數')
await tx.project.create({ data: { name } })

✓ 先查再寫是經典的競態：兩個交易各自看到 2，都通過。鎖租戶列讓第二個交易等第一個 commit 後再數。c 是常見的直覺：REPEATABLE READ 只讓同一個交易讀到一致的快照，兩個交易仍然各自看到 2，照樣多建一個。驗證的方法是同時送 10 個請求、最後恰好 3 個。（第 14 課）

練習 13：稽核紀錄的寫法有兩個提案：(甲) 業務改完資料、交易 commit 之後，發一個事件，由 listener 寫稽核；(乙) 在同一個交易裡呼叫 audit.record(tx, …)。作品選乙，因為甲會出什麼事？

✓ 稽核的價值在於「改了就一定有紀錄」，所以它要跟業務寫入在同一個交易。兩個寫入次數一樣（a 錯）；actor 可以放進事件（b 不是根本問題）；c 反了，commit 之後才發事件，失敗的操作不會到這一步。（第 11 課）

練習 14：團隊每加一個有 :id 的端點，就要在跨租戶 E2E 的 ENDPOINTS 加一列。新同事問：「我們有 extension、有 RLS、CI 還有 SAST，這張表是不是多餘的？」怎麼回答？

✓ 測試檢查結果，不管程式怎麼寫，所以它能抓到「繞過防線」這類 code review 容易放過的寫法（第 18 課的錯誤寫法就是一條另開的連線）。b 錯在 CI 也應該跑 RLS（第 17 課）；d 跟 BOLA 無關。這張表放在 E2E 層，每個新端點一列，寫進 PR 範本。（第 8、18 課）
