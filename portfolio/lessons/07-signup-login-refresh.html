階段 B1：多租戶 SaaS 的平台地基 · 第 7 課

帳號、租戶與 token

第 6 課開好的 my-saas 已經有錯誤格式、requestId 和健康檢查，但它還不認識任何人：誰都能打每一個路由，API 也不知道請求是誰送的。多租戶系統的每個請求都要回答兩個問題：你是誰、你現在在哪個租戶。這一課讓 my-saas 回答得出來。

這一課跟著一位使用者走完整條路。林雅婷是會計師，她在你的 SaaS 註冊，替自己的事務所開一個租戶；之後她的客戶公司會邀請她加入（第 10 課），所以她會同時屬於好幾個租戶，在每個租戶的角色也不同。她登入、帶著 token 打 /me、15 分鐘後 token 過期要自動換新、筆電上的 refresh token 可能被偷、有人拿她的 email 一直猜密碼。這條路的每一步 my-saas 都要做對，驗收測試也是照這條路打你的 API。

雜湊密碼、簽 JWT、輪替 refresh token 這些零件在 auth 課都單獨做過。這一課的重點是把它們放進你自己的模組結構，並把多租戶多出來的決定做對：一個人屬於好幾個租戶時資料表怎麼設計，租戶要寫在哪裡才不會被使用者竄改。

這課的路線：
  1. 林雅婷會屬於好幾個租戶：資料表怎麼存「誰、在哪個租戶、什麼角色」。
  2. 註冊要寫三筆資料：為什麼要一個交易、email 重複怎麼擋。
  3. 登入之後每個請求怎麼證明「我是誰、在哪個租戶」：access token 放什麼；15 分鐘後怎麼用 refresh token 換新，被偷了怎麼發現。
  4. token 發出去了，誰在每個路由檢查它：全域 guard，預設要登入，例外要明講。
  5. 登入端點誰都能打：怎麼不洩漏帳號存不存在、怎麼擋猜密碼；最後把取捨寫成 ADR。
這課會用到：
  • auth 課第 21 課：在 NestJS 裡用 argon2id 雜湊密碼、JwtModule 寫死演算法與 issuer、audience，全域 guard 搭配 @Public()。
  • auth 課第 10 課：refresh token 資料庫只存雜湊、每用一次就換一張（輪替）、用過的再出現就撤銷整個家族（重用偵測）。
  • auth 課第 16 課：登入失敗不洩漏帳號存不存在，以帳號計數的限流。
  • auth 課第 4 課的 cookie 屬性：HttpOnly、SameSite、Path、Secure，各自限制瀏覽器什麼時候讓誰讀到、送出這個 cookie。

林雅婷會屬於好幾個租戶：資料表怎麼存「誰、在哪、什麼角色」？

註冊、登入、token 最後都要讀寫資料庫，所以先決定資料怎麼存。要存的資訊有三樣：這個人是誰（email、密碼雜湊、名字）、有哪些租戶，以及「誰在哪個租戶、擔任什麼角色」。

直覺的設計是在 users 表上放 tenant_id 和 role 兩個欄位：一個人屬於一個租戶，角色也只有一個。用林雅婷走一遍就會撐不住。她註冊時，tenant_id 填她的事務所、role 是 owner，到這裡都沒問題。下個月客戶「好日子咖啡」邀請她加入，在那裡她是 viewer，只能看帳。這時 tenant_id 那一格只放得下一個值，role 也是。

硬撐的做法有兩種，都很糟。第一種是要她用另一個 email 再註冊一個帳號：會計師、顧問、外包工程師常常同時服務好幾家公司，每家一個帳號、一組密碼，體驗很差；而且「這個人做過什麼」會散在好幾個帳號裡，第 11 課的稽核紀錄就串不起來。第二種是把 tenant_id 改成陣列：租戶存得下了，但「在事務所是 owner、在好日子咖啡是 viewer」這種每個租戶不同的角色還是沒地方放。

問題的根源是：人和租戶是多對多的關係。一個人可以屬於好幾個租戶，一個租戶也有好幾個成員。關聯式資料庫表達多對多的標準做法，是在兩張表中間多放一張表，每一列記錄一組配對。這張中間表就是 memberships（成員身分）：一列代表「某個人是某個租戶的成員」。角色是這組配對的屬性，不是人的屬性，所以放在這一列上。林雅婷在資料庫裡會是 users 一列，加上 memberships 兩列：一列寫事務所、owner，一列寫好日子咖啡、viewer。

表一列代表唯一性有沒有 tenant_id
users一個人，全系統只有一個帳號email 全域唯一（存小寫）沒有：人不屬於任何單一租戶
tenants一個租戶（一家公司、一間事務所）id沒有：它自己就是租戶
memberships誰在哪個租戶、什麼角色同一個人在同一個租戶只有一列有

寫成 Prisma schema。第四張表 refresh_tokens 先一起建好，等講到 refresh token 時再解釋它的欄位：

// prisma/schema.prisma（節錄）
model Tenant {
  id        String   @id @db.Uuid
  name      String
  plan      String   @default("free")        // 第 14 課
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  @@map("tenants")
}

// email 全域唯一（存小寫）；角色不放這裡，放在 membership
model User {
  id           String   @id @default(uuid()) @db.Uuid
  email        String   @unique
  passwordHash String   @map("password_hash")
  name         String
  createdAt    DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  @@map("users")
}

model Membership {
  tenantId  String   @map("tenant_id") @db.Uuid
  userId    String   @map("user_id") @db.Uuid
  role      String                            // owner、admin、member、viewer
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  @@id([tenantId, userId])                    // 同一個人在同一個租戶只有一筆
  @@index([userId])                           // 登入時「這個人屬於哪些租戶」
  @@map("memberships")
}

// refresh token 只存雜湊；同一次登入換出來的是同一個家族
model RefreshToken {
  id        String    @id @default(uuid()) @db.Uuid
  userId    String    @map("user_id") @db.Uuid
  tenantId  String    @map("tenant_id") @db.Uuid
  familyId  String    @map("family_id") @db.Uuid
  tokenHash String    @unique @map("token_hash")
  createdAt DateTime  @default(now()) @map("created_at") @db.Timestamptz(3)
  expiresAt DateTime  @map("expires_at") @db.Timestamptz(3)
  usedAt    DateTime? @map("used_at") @db.Timestamptz(3)
  revokedAt DateTime? @map("revoked_at") @db.Timestamptz(3)
  @@index([familyId])
  @@map("refresh_tokens")
}

Membership 的兩行設定把上面那張表的規則交給資料庫執行。@@id([tenantId, userId]) 是複合主鍵：兩個欄位合起來不能重複，所以林雅婷在同一個租戶不會出現兩列、兩個角色。@@index([userId]) 是給登入用的：登入時要問「這個人屬於哪些租戶」，查詢條件是 userId，而複合主鍵的第一個欄位是 tenantId，幫不上這個查詢，所以另外建一個索引。

users 與 tenants 沒有 tenant_id，因為它們不屬於任何一個租戶。第 9 課開 RLS 時，這兩張表的處理方式也會跟其他表不同。另外注意 Tenant.id 沒有 @default，不讓資料庫產生 id，原因在下一節。產生並套用第一個 migration：

npx prisma migrate dev --name auth    # 產生並套用第一個 migration
npx prisma generate

表建好了。林雅婷按下「註冊」時，要一口氣寫進三張表：users 一列、tenants 一列、memberships 一列。三次寫入，中間任何一次失敗會留下什麼？

註冊要寫三筆資料：中途失敗會留下什麼？

假設三次寫入各自執行。users 寫好了，寫 tenants 時資料庫連線斷了，或租戶名稱違反了某個限制，請求回 500。這時資料庫裡留下一個沒有任何租戶的帳號：林雅婷登得進去，但沒有任何租戶，什麼都不能做。她想重新註冊，email 已經被這個殘缺的帳號占用，會收到「這個 email 已經註冊」。最後只能寫信給客服，由工程師手動刪資料。

這三筆資料必須一起成功或一起失敗，這正是交易的用途：交易裡的寫入，只要中間有一步失敗，前面已經寫的全部撤回，資料庫回到交易開始前的樣子。Prisma 的寫法是 $transaction(async tx => { … })：函式裡用 tx 而不是 this.prisma 寫入，這些寫入就屬於同一個交易；函式丟出例外，整個交易就撤回。

// src/auth/auth.service.ts（第 7 課的版本）
async signup(dto: SignupDto) {
  const tenantId = randomUUID(), userId = randomUUID()
  const passwordHash = await this.passwords.hash(dto.password)   // 雜湊在交易外：慢，不要占著連線
  try {
    return await this.prisma.$transaction(async tx => {
      const user = await tx.user.create({ data: { id: userId, email: dto.email, name: dto.name, passwordHash } })
      const tenant = await tx.tenant.create({ data: { id: tenantId, name: dto.tenantName } })
      await tx.membership.create({ data: { tenantId, userId, role: 'owner' } })
      return { user: { id: user.id, email: user.email, name: user.name }, tenant: { id: tenant.id, name: tenant.name, plan: tenant.plan }, role: 'owner' }
    })
  } catch (e) {
    if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2002') throw new ApiError(409, 'EMAIL_TAKEN', '這個 email 已經註冊')
    throw e
  }
}

這段程式除了交易，還藏著四個決定，每個都對應一種出錯的方式。

密碼雜湊放在交易外面。argon2id 是刻意設計得很慢的雜湊，目的是讓攻擊者拿到雜湊後很難一個一個猜密碼。交易從開始到結束都占著一條資料庫連線，而連線池的連線數量有限。如果在交易裡算雜湊，這條連線就在等 CPU 算完，什麼事都沒做；註冊的人一多，其他請求就排不到連線。所以先把雜湊算好，交易裡只做三次寫入。

email 重複交給唯一約束擋，不先查再寫。先查「這個 email 有沒有人用過」、沒有才寫入，看起來很合理，但併發時會失守。林雅婷手滑按了兩次註冊，兩個請求幾乎同時到：請求 A 查到沒有人用，請求 B 也查到沒有人用（A 還沒寫入），兩邊都去寫，最後出現兩個同 email 的帳號。能同時看到兩個請求的只有資料庫本身：email 上的唯一約束保證第二筆寫入一定失敗。Prisma 遇到唯一約束衝突時丟出錯誤碼 P2002 的例外，這裡把它轉成 409 EMAIL_TAKEN。大小寫的問題在進來時就處理：DTO 用 @Transform 把 email 轉小寫（跟第 2 課一樣），Ya@x.com 和 ya@x.com 存進去都是同一個值，唯一約束就等於不分大小寫。

回應自己挑欄位。Prisma 回傳的 user 物件包含 passwordHash，直接回給前端就把雜湊送出去了。回傳時明確列出要的欄位，之後 users 表加了新欄位，也不會不小心多回一個。

ID 在程式裡先產生。這回答了上一節 Tenant.id 為什麼沒有 @default。第 9 課開了 RLS 之後，資料庫在寫入 memberships 前要先知道「現在是哪個租戶」，而註冊的當下這個租戶還不存在。如果讓資料庫產生 id，要寫完 tenants 才知道它；先在程式裡產生 tenantId，就能在任何寫入之前把上下文設成這個新租戶。參考實作的 signup 已經是第 9 課的版本，跟這裡的差異見課末補充。

林雅婷有了帳號，也有了自己的事務所租戶。接下來她登入，之後每個請求 API 都要知道「這是林雅婷，她現在在事務所」。HTTP 不會記得上一個請求是誰送的，每個請求要帶什麼來證明？

登入之後，每個請求怎麼證明「我是誰、在哪個租戶」？

HTTP 是無狀態的：伺服器處理完一個請求就忘了它，下一個請求進來，不知道它跟上一個是同一個人。所以登入成功時，API 要發給前端一份憑證，前端之後每個請求都帶著它，API 看憑證認人。auth 課教過兩種憑證：session（伺服器存資料，每個請求查一次）與 token（資料寫在 token 裡並簽章，API 驗簽章就好，不用查）。my-saas 的前端是 Vue SPA，我們選 token，理由在本課最後一節寫進 ADR 時回答。

token 有一個天生的缺點：發出去之後收不回來。API 只驗簽章，不查資料庫，所以只要簽章對、還沒過期，就一律放行。為了把這個缺點的影響壓小，登入時發的是兩種 token，分工不同（auth 第 10 課）：

  • access token：每個請求都帶，API 只驗簽章。效期很短，被偷或該撤銷時，最多也只能再用這麼久。
  • refresh token：只用來換新的 access token。效期長，存在資料庫裡，所以可以撤銷；換的時候查資料庫，撤銷了就換不到。

在多租戶系統裡，還要多決定一件事：租戶寫在哪裡。一個做法是前端在每個請求加一個 header，例如 X-Tenant-Id，說「我現在在這個租戶」。問題是 header、body、query 都是使用者送來的，他可以隨便改：林雅婷把 header 改成別家公司的 id，API 如果沒有每次都檢查她是不是那家公司的成員，就把別人的資料給她看了。auth 第 20 課的結論是：租戶只從驗過簽章的 token 來。簽章保證 token 的內容是伺服器寫的、沒被改過，所以登入時伺服器把「目前的租戶」寫進 access token，之後就能信任它。

JWT 的內容（payload）是一組欄位，叫做 claim。sub 是標準 claim，代表這張 token 屬於誰，這裡放使用者 id；tid 是我們自己定義的 claim，放目前的租戶 id。林雅婷要從事務所切到好日子咖啡時，呼叫 switch-tenant，伺服器確認她是那裡的成員後，發一張 tid 不同的新 token（第 10 課）。

那角色要不要也放進 token？放進去可以每個請求少查一次資料庫，代價是角色變了 token 不知道。假設好日子咖啡有一陣子讓林雅婷當 admin 幫忙整理帳目，結束後把她降回 viewer，她手上那張寫著 admin 的 token 在過期前照樣有 admin 的權限。所以這裡不放角色。第 10 課會讓 guard 每個請求查 membership，那時再回來看這個取捨。

兩種 token 的設計整理成一張表，refresh token 那一欄下一節會一格一格做出來：

access token（JWT）refresh token
內容sub（使用者 id）、tid（目前的租戶 id）；不放角色userId.隨機 32 bytes，資料庫只存 SHA-256
效期15 分鐘14 天，每用一次就換一張
放哪裡前端記憶體，Authorization: Bearer …HttpOnly、SameSite=Strict、Path=/api/v1/auth 的 cookie
怎麼撤銷撤不了，等它過期；第 10 課讓每個請求查 membership，補上這個洞標記 revokedAt，整個家族一起

access token 用 JwtModule 簽發與驗證。auth 第 21 課的規則是：簽的時候用什麼，驗的時候就只接受什麼，全部寫死在設定裡。演算法要寫死，因為 JWT 的 header 裡有一個 alg 欄位，由送 token 的人填；驗證端如果照著 header 選演算法，攻擊者就能填 none（不簽章），或換成別的演算法來偽造。issuer 與 audience 也要寫死：issuer 是「誰發的」、audience 是「發給誰用的」，驗證時比對這兩個，別的系統發的 token 就算剛好用了同一把金鑰，也進不來。

// src/auth/auth.module.ts
JwtModule.registerAsync({
  inject: [ConfigService],
  useFactory: (config: ConfigService<Env, true>) => {
    const issuer = config.get('JWT_ISSUER', { infer: true }), audience = config.get('JWT_AUDIENCE', { infer: true })
    return {
      secret: config.get('JWT_SECRET', { infer: true }),
      signOptions: { algorithm: 'HS256', expiresIn: '15m', issuer, audience },
      verifyOptions: { algorithms: ['HS256'], issuer, audience },   // 擋下 alg: none 與換演算法的攻擊
    }
  },
}),

// src/auth/auth.service.ts
issueAccessToken(userId: string, tenantId: string) {
  return this.jwt.signAsync({ sub: userId, tid: tenantId })
}

signOptions 決定簽出去的 token 長什麼樣，verifyOptions 決定收到的 token 要符合什麼條件。issueAccessToken 只需要給 sub 與 tid，效期、issuer、audience 都由設定自動加上。JWT_SECRET 的長度檢查見課末補充。

到這裡林雅婷登入後拿得到一張 access token，裡面寫著她和她的事務所。但它 15 分鐘就過期，她一天要工作 8 小時，不可能每 15 分鐘重新登入一次。接手的是 refresh token，可是它一活就是 14 天，被偷的代價比 access token 高得多。它要怎麼存、怎麼換？

15 分鐘後怎麼換新？refresh token 被偷了怎麼發現？

先看它怎麼產生。refresh token 是一段 userId.隨機 32 bytes 的字串，真正的秘密是後面那段隨機值，32 bytes 的隨機值沒有人猜得到。資料庫不存原文，只存它的 SHA-256 雜湊：資料庫的內容可能因為備份、唯讀帳號或 SQL injection 外洩，存原文的話，拿到資料表的人可以直接用裡面每一張 token 登入；存雜湊的話只能看不能用。這裡用 SHA-256 而不是 argon2id，因為慢雜湊是用來保護「人取的、容易猜」的密碼，隨機值本來就猜不到，用快的雜湊就夠了。

再看它怎麼換。每次前端拿 refresh token 來換 access token，伺服器把這張標成「已使用」，同時發一張新的 refresh token 給前端，這叫輪替。從同一次登入一路換出來的 token 串成一個家族，它們共用一個 familyId。林雅婷在筆電登入是一個家族，在手機登入是另一個家族。

輪替的價值在於能發現 token 被偷，這叫重用偵測。假設有人從林雅婷的筆電偷走了 refresh token T1。接下來會有兩種順序：

  • 攻擊者先用：他拿 T1 換到 T2。過一陣子林雅婷的瀏覽器也拿 T1 來換，T1 已經用過了。
  • 林雅婷先用：她換到 T2，T1 標成已使用。攻擊者之後拿 T1 來換，同樣是用過的。

不管哪一種，一張已使用的 token 又出現，就表示它被複製過。伺服器分不出哪一邊是攻擊者，所以把整個家族撤銷：雙方手上最新的那張都失效。林雅婷重新登入一次就好，攻擊者沒有密碼，回不來。如果只拒絕那張舊的、不撤銷家族，攻擊者手上換出來的 T2 還能一直換下去。

「標成已使用」這一步還有併發的問題。前端兩個分頁同時拿同一張 token 來換，如果寫成「先查這張有沒有用過，沒用過再標記」，兩個請求可能都查到沒用過，兩邊都換到新 token。跟上一節 email 的情況一樣，解法是讓資料庫一次判斷：用一句條件式更新，只有「還沒用過、沒被撤銷、沒過期」的 token 會被標成已使用。兩個更新碰到同一列時，後到的會等先到的完成，再重新檢查條件；這時 usedAt 已經有值，條件不成立。所以兩個請求裡只有一個拿到 count 為 1，另一個是 0。

下面的節錄取自參考實作的最終版本，裡面的 this.db.client 是第 8 課才做的 TenantDb（會自動加租戶條件的 Prisma client）。這一課先把它當成 this.prisma 讀，寫法一樣。

// src/auth/refresh.service.ts（節錄）
async issue(userId: string, tenantId: string, familyId: string = randomUUID()) {
  const token = `${userId}.${randomBytes(32).toString('base64url')}`
  await this.db.client.refreshToken.create({
    data: { userId, tenantId, familyId, tokenHash: sha256(token), expiresAt: new Date(Date.now() + REFRESH_TTL_MS) },
  })
  return token
}

async rotate(token: string): Promise<Rotated> {
  const userId = token.split('.')[0]
  if (!UUID.test(userId)) return null
  const now = new Date(), tokenHash = sha256(token)
  const { count } = await this.db.client.refreshToken.updateMany({
    where: { tokenHash, usedAt: null, revokedAt: null, expiresAt: { gt: now } }, data: { usedAt: now },
  })
  const row = await this.db.client.refreshToken.findUnique({ where: { tokenHash } })
  if (!row) return null
  if (count === 0) {
    if (row.usedAt) {                       // 已經換過的又被拿來用：有人偷了它
      await this.revokeFamily(row.familyId)
      return { reused: true }
    }
    return null                             // 過期或已撤銷
  }
  return { userId, tenantId: row.tenantId, token: await this.issue(userId, row.tenantId, row.familyId) }
}

issue 沒給 familyId 時產生一個新的，這是登入時開新家族；輪替時傳入舊的 familyId，新 token 就留在同一個家族。rotate 依 updateMany 的結果分成下面三種情況：

  • count 是 1：條件式更新成功，這張是有效的，發同一家族的下一張。
  • count 是 0 而且 usedAt 有值：用過的又出現，撤銷家族，回傳 { reused: true }。
  • count 是 0 但沒用過，或資料庫查不到：過期、已撤銷或根本是亂填的，回傳 null。

token 開頭放 userId 不是秘密，是給第 9 課用的：refresh_tokens 的 RLS 只讓人看到自己的列，要先知道「是誰」才查得到這一列。

新的 refresh token 要交給瀏覽器保管，這裡用 cookie，而且每個屬性都在限制它被誰拿到。HttpOnly 讓頁面上的 JavaScript 讀不到它，就算網站有 XSS 漏洞，注入的程式碼也偷不走。SameSite=Strict 讓瀏覽器在別的網站發起的請求裡不帶這個 cookie，擋掉跨站偽造請求。Path=/api/v1/auth 讓瀏覽器只在 refresh、logout 這幾個路徑帶上它，一般的 API 請求不會帶著長命的 token 到處跑。Secure 讓它只走 HTTPS。controller 依 rotate 的結果回 200、401 REFRESH_REUSED 或 401 UNAUTHENTICATED：

// src/auth/auth.controller.ts（節錄）
export const REFRESH_COOKIE = 'refresh_token'

this.cookie = { httpOnly: true, secure: config.get('COOKIE_SECURE', { infer: true }), sameSite: 'strict', path: '/api/v1/auth' }

@Public()
@Post('refresh')
@HttpCode(200)
async rotate(@Req() req: Request, @Res({ passthrough: true }) res: Response) {
  const old: unknown = req.cookies?.[REFRESH_COOKIE]
  const r = typeof old === 'string' ? await this.refresh.rotate(old) : null
  if (r && 'reused' in r) throw new ApiError(401, 'REFRESH_REUSED', 'refresh token 被重複使用，請重新登入')
  if (!r) throw unauthenticated()
  res.cookie(REFRESH_COOKIE, r.token, { ...this.cookie, maxAge: REFRESH_TTL_MS })
  return { accessToken: await this.auth.issueAccessToken(r.userId, r.tenantId) }
}

新的 refresh token 寫進 cookie，新的 access token 放在回應 body，由前端放進記憶體。REFRESH_REUSED 和一般的 UNAUTHENTICATED 分開回，是讓前端知道「這不是過期，是可能被偷了」。讀 req.cookies 需要的套件與 COOKIE_SECURE 的設定見課末補充。

logout 是同一套機制的另一種用法：撤銷這張 token 所屬的家族並清掉 cookie。林雅婷在筆電登出，手機上的登入是別的家族，不受影響。

💡 實務上：前端怎麼配合
Vue 前端把 access token 放在記憶體（例如 Pinia store），不放 localStorage；重新整理頁面後呼叫一次 /auth/refresh 拿新的。API 回 401 時攔截器呼叫 refresh 再重送原本的請求，而且同時只發一個 refresh（auth 第 10 課的競態：兩個分頁同時 refresh 會觸發重用偵測）。前後端要先講好：refresh 回 401 REFRESH_REUSED 時前端直接導去登入頁，不要重試。這些約定寫進 README 的 API 段落，第 15 課會放進 OpenAPI。林雅婷一天工作 8 小時，感覺不到 access token 每 15 分鐘換一次，靠的就是這個攔截器。

token 能發、能換、能撤銷了。但到目前為止，API 的路由還沒有任何一個會檢查 access token：不帶 token 的請求照樣通過。

token 發出去了，誰在每個路由檢查它？

上一節留下的洞是：token 發得出去，路由卻沒有在檢查。最直接的補法是在每個 controller 加上 @UseGuards(…)。問題是它依賴每個人每次都記得加：之後有人新增一個 controller 忘了加，那個路由就對全世界開放，而且開發時什麼錯都不會出現，因為不帶 token 也能正常回應。

auth 第 21 課的做法是把方向反過來：guard 註冊在全域（用 APP_GUARD 這個 provider 登記一次，每個路由執行前都會先經過它），預設必須登入，不用登入的路由明確標 @Public()。這樣忘了標的後果是「太嚴」而不是「沒保護」：新路由在開發時就回 401，馬上會被發現；反過來的「沒保護」要等到出事才知道。

路由要怎麼告訴 guard「我不用登入」？NestJS 的做法是 metadata：decorator 用 SetMetadata 在 handler 或 controller 上貼一個標籤，guard 執行時用 Reflector 讀這個標籤。參考實作把每個路由要什麼寫成三種宣告，放在 src/auth/decorators.ts：

export const ACCESS = 'access'
export type Access = { public: true } | { authenticated: true } | { permissions: Permission[] }
export const Public = () => SetMetadata(ACCESS, { public: true } satisfies Access)
export const Authenticated = () => SetMetadata(ACCESS, { authenticated: true } satisfies Access)
export const Permissions = (...permissions: Permission[]) => SetMetadata(ACCESS, { permissions } satisfies Access)

三種宣告對應三種路由。@Public() 給不可能先登入的路由：註冊、登入、refresh、健康檢查。@Authenticated() 給「登入就好，不看角色」的路由，例如 /me、列出自己的租戶。@Permissions(…) 是第 10 課的租戶內權限，例如只有 admin 能邀請成員。三種都寫在同一個 metadata key 底下，guard 對每個路由最後只會讀到一種。

guard 在 src/tenancy/access.guard.ts。這一課先做到「驗 token、把使用者與租戶放進請求上下文」：

// src/tenancy/access.guard.ts（第 7 課做到這裡）
async canActivate(context: ExecutionContext) {
  const access = this.reflector.getAllAndOverride<Access | undefined>(ACCESS, [context.getHandler(), context.getClass()])
  if (access && 'public' in access) return true
  const req = context.switchToHttp().getRequest()
  const [scheme, token] = String(req.headers.authorization ?? '').split(' ')
  if (scheme !== 'Bearer' || !token) throw unauthenticated()
  let payload: { sub: string; tid: string }
  try {
    payload = await this.jwt.verifyAsync(token)   // 演算法、iss、aud 寫死在 JwtModule 的 verifyOptions
  } catch {
    throw unauthenticated()
  }
  const store = this.ctx.store!
  store.userId = payload.sub
  store.tenantId = payload.tid                  // 第 8 課的資料庫擴充從這裡讀租戶
  // 第 10 課：查 membership、比對 @Permissions
  …
}

由上往下讀：

  • getAllAndOverride 先看方法上的宣告，再看 controller 上的，方法上的優先。這樣整個 controller 可以標 @Authenticated()，其中一個方法再單獨標 @Public()。
  • 不是 public，就從 Authorization: Bearer … 標頭拿 token，沒有就 401。
  • verifyAsync 驗簽章、效期、演算法、issuer、audience，任何一項不對都轉成 401。
  • 驗過之後，把 sub 和 tid 寫進第 6 課放 requestId 的那個請求上下文，同一個請求後面的 service 都讀得到。

guard 放在 tenancy 模組而不是 auth，因為它的工作不只認證：第 8 課的資料庫擴充從它填的 tenantId 知道租戶，第 10 課它還要檢查租戶內的權限。/me 也在 tenancy（src/tenancy/me.controller.ts），回 { user, tenant, role }。林雅婷登入後打 /me，看到的是她自己、她的事務所，以及 owner。

guard 擋得住沒帶 token 的人，但註冊和登入一定是 @Public()：還沒登入的人才需要它們。這讓登入端點成了攻擊者不用任何 token 就能直接碰到帳號的地方。

登入端點誰都能打：怎麼不洩漏帳號、怎麼擋猜密碼？

登入端點是整個系統最常被攻擊的地方，攻擊者拿它做兩件事：一是查出哪些 email 有註冊，二是對特定帳號一直猜密碼。驗收測試會檢查你兩件都擋得住，以及擋的方式本身沒有再洩漏資訊。

先看第一件。如果帳號不存在時回「帳號不存在」、密碼錯時回「密碼錯誤」，攻擊者拿一份外洩的 email 名單打登入 API，就能篩出哪些人在你的系統有帳號，例如林雅婷，再拿去做釣魚信或猜密碼。所以帳號不存在與密碼錯回一模一樣的東西（auth 第 16 課）：都是 401 INVALID_CREDENTIALS，訊息也一樣。

回應內容一樣還不夠，回應時間也會洩漏。帳號不存在時，程式查不到使用者就直接回，幾毫秒就結束；帳號存在但密碼錯時，要先算一次 argon2id 才知道錯，慢了不少。攻擊者量一下時間就分得出來。參考實作的做法是帳號不存在時，拿一個不屬於任何帳號的假雜湊照樣算一次，兩條路花的時間就差不多：

// src/auth/auth.service.ts
const DUMMY_HASH = '$argon2id$v=19$m=19456,t=2,p=1$…'   // 不屬於任何帳號

async verifyCredentials(email: string, password: string) {
  const user = await this.db.client.user.findUnique({ where: { email } })
  const ok = await this.passwords.verify(password, user?.passwordHash ?? DUMMY_HASH)
  return user && ok ? user : null
}

再看第二件：有人知道林雅婷的 email，一直猜她的密碼。擋法是限流：同一個 email 連續失敗太多次，就暫時拒絕。要以 email 計數，不以 IP 計數，因為攻擊者換 IP 很容易，而這裡要保護的是單一帳號。參考實作的門檻是：從第一次失敗起算 15 分鐘的視窗內累積失敗 10 次，就回 429 RATE_LIMITED，直到這個視窗結束；回應帶上 Retry-After 標頭，值就是視窗剩下的秒數；登入成功就清掉計數。

計數放在 Redis，因為正式環境的 API 通常有好幾台，計數放在某一台的記憶體裡，攻擊者的請求分散到各台就各算各的；放在 Redis，大家看到的是同一個數字。寫法是每次失敗 INCR（把計數加 1，回傳新的值），第一次失敗時再 EXPIRE（設定這個 key 幾秒後自動刪掉），計數就會在時間到後自動歸零。INCR 為什麼好幾台同時加也不會少算，auth 第 16 課講過。帳號不存在也照樣計數：不然「會不會被限流」本身又洩漏了帳號存不存在。

// src/auth/login-throttle.service.ts（節錄）
const MAX_FAILURES = 10
const WINDOW_SECONDS = 15 * 60

async retryAfter(email: string) {
  const key = this.redis.key('login-fail', email)
  const failures = Number(await this.redis.client.get(key) ?? 0)
  return failures >= MAX_FAILURES ? Math.max(await this.redis.client.ttl(key), 1) : 0
}

async recordFailure(email: string) {
  const key = this.redis.key('login-fail', email)
  if (await this.redis.client.incr(key) === 1) await this.redis.client.expire(key, WINDOW_SECONDS)
}

// src/auth/auth.controller.ts 的 login
const wait = await this.throttle.retryAfter(dto.email)
if (wait) {
  res.setHeader('Retry-After', String(wait))
  throw new ApiError(429, 'RATE_LIMITED', '嘗試次數太多，請稍後再試')
}
const user = await this.auth.verifyCredentials(dto.email, dto.password)
if (!user) {
  await this.throttle.recordFailure(dto.email)
  throw invalid()
}
await this.throttle.reset(dto.email)
return this.issue(res, user.id, await this.auth.defaultTenant(user.id))

login 的順序是：先看這個 email 是不是在限流中，是的話直接回 429，連密碼都不驗；不是的話驗帳密，失敗就計數並回 401，成功就清掉計數並發 token。retryAfter 用 ttl 讀出這個 key 還剩幾秒，就是 Retry-After 的值。

門檻（10 次、15 分鐘）是你決定的，契約只要求「連續錯 20 次至少出現一次 429」。這個限流跟第 14 課的「每租戶每分鐘 300 個請求」是兩件事：登入時還沒有租戶，要保護的是單一帳號不被猜密碼。

最後一行的 defaultTenant 回答「登入後在哪個租戶」：取最早加入的那個 membership。林雅婷先註冊了事務所、後來才加入好日子咖啡，所以登入後在事務所；要看客戶的帳，再用 switch-tenant 換（第 10 課）。

💡 實務上：登入限流的副作用
以帳號計數的限流擋得住對單一帳號猜密碼，但也讓攻擊者能故意把別人鎖住（auth 第 16 課）：所以用「暫時」而不是「永久」，回 429 而不是「帳號已鎖定」，並且在 log 記下來。它擋不住的是撞庫：同一個 IP 對幾千個不同帳號各試一次。那需要另一層以 IP 或裝置計數的限流、或在登入前加驗證碼，作品裡寫進「已知限制」就好。面試被問「怎麼防暴力破解」時，講出這兩種攻擊的差別比講演算法有用。

半年後有人問「token 為什麼這樣設計」，答案在哪？

這一課做了好幾個有代價的決定：用 token 不用 session、角色不放進 token、access token 撤銷不了只能靠 15 分鐘效期。半年後新同事問「為什麼不每個請求查 session 就好」，或面試官問「成員被移除後多久失效」，答案不能只在你腦子裡。第 6 課寫過第一份 ADR，這裡用同樣的格式再寫一份。

先回答新同事那個問題。session 的做法是：伺服器有一套 session 儲存，登入時寫一筆，每個請求拿 cookie 裡的 session id 去查，登出或過期時刪掉，還要定期清理過期的資料；API 有好幾台時，大家都要連到同一套儲存才認得人。token 的做法是：身分寫在 access token 裡並簽章，任何一台 API 拿到 token 只要驗簽章就知道是誰、在哪個租戶，不用維護也不用清理 session 儲存。token 撤銷不了的缺點，由 refresh token 補上：它每用一次就換、存在資料庫、可以整個家族撤銷，被偷時還能靠重用偵測發現。

但要老實寫出代價：第 10 課的 guard 每個請求還是會查一次 membership，所以「token 不用查資料庫」的優勢縮小了。差別在查的東西：那是用 (tenantId, userId) 複合主鍵查一列，確認這個人現在還是這個租戶的成員、是什麼角色，不是維護一整套會過期、要清理、要跨台共用的 session 儲存。所以這裡選 token，主因是本課這幾項需求：SPA 前端、能撤銷登入、能偵測 refresh token 被偷、多台 API 不用共用 session。換一個需求組合，選 session 一樣合理。

這些決定寫成 docs/adr/0003-token-design.md（0002 留給第 9 課的 RLS）：背景是「前端是 Vue SPA，要能撤銷登入、偵測 refresh token 被偷，同時不要每個請求查 session 表」，決定是上面那張 token 設計表，後果寫「成員被移除要立刻生效，所以每個請求查一次 membership（第 10 課）」與「正式環境一定要 HTTPS」。

後果那一段最容易漏寫代價。「access token 撤銷不了，靠短效期」就是本課練習 5 要你想清楚的事：林雅婷被客戶移出租戶後，她手上的 access token 還能用多久。寫進 ADR，這個洞就有人知道、有地方追蹤，第 10 課補上時再更新後果。

練習

練習 1：做出 POST /api/v1/auth/signup、POST /api/v1/auth/login、GET /api/v1/me。註冊回 201 { user, tenant, role: "owner" }，同一個 email（不分大小寫）409 EMAIL_TAKEN，缺欄位 400；登入時密碼錯與帳號不存在都回 401 INVALID_CREDENTIALS，兩個回應除了 requestId 完全一樣。

練習 2：做出 POST /api/v1/auth/refresh 與 POST /api/v1/auth/logout。refresh 每次都換一張新的 cookie；用過的舊 token 再用回 401 REFRESH_REUSED，之後同一家族最新的 token 也要 401；logout 回 204，之後那張 token 401，同一個人另一次登入（別的家族）不受影響。

練習 3：全域 guard 讓 GET /api/v1/me 對這些 token 都回 401：沒有 token、亂碼、alg: none、別的金鑰簽的、改過 payload 沿用原簽章的。refresh cookie 要有 HttpOnly、SameSite（Strict 或 Lax）、Path=/api/v1/auth。

練習 4：同一個 email 連續登入失敗會被限流：測試最多錯 20 次，要至少出現一次 429 RATE_LIMITED，並且有 Retry-After 標頭。門檻自己決定。

練習 5：access token 裡有 tid，guard 驗完簽章就把它當成目前的租戶，沒有再查資料庫。owner 把一位成員移出租戶之後，會發生什麼？

✓ JWT 是自帶內容的：驗簽章只證明「這張 token 是我發的」，不知道發出之後成員身分變了。撤銷 refresh token 只擋得住「換新的」，手上這張 access token 要等過期。補法是 guard 每個請求查 membership（第 10 課），或在 token 帶版本號與資料庫比對。a 是最常見的誤解：refresh token 撤銷了，已經發出的 access token 不會跟著失效。（第 7 課，auth 第 11 課）

練習 6：同事問：refresh token 已經放在 HttpOnly cookie、前端讀不到了，資料庫為什麼還要存雜湊，不能直接存原文？

✓ HttpOnly 保護的是瀏覽器這一端；資料庫是另一個會外洩的地方。refresh token 等於 14 天的登入權，跟密碼一樣只存雜湊，外洩的資料表就不能直接拿來登入。它是 32 bytes 的隨機值，不怕暴力猜，所以用 SHA-256 就夠，不需要 argon2id 那種慢雜湊。c 把輪替與雜湊混在一起：輪替是每次發一張新的隨機 token，跟怎麼存無關。（第 7 課，auth 第 10 課）

練習 7：PM 抱怨「每 15 分鐘就要換 token 很麻煩」，提議 access token 改成 24 小時、拿掉 refresh token。主要的代價是什麼？

✓ access token 撤銷不了，效期就是「出事之後最長的曝險時間」；refresh token 輪替還能偵測重用。15 分鐘的麻煩由前端的攔截器自動處理，使用者感覺不到。效期不影響 token 大小，也跟簽章演算法的強度無關（a、b 錯）。d 錯：拿掉 refresh token 後 access token 放哪裡是另一個問題，不是「24 小時」造成的。（第 7 課，auth 第 10 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • 註冊真的是一個交易：在 tenant.create 前面暫時加一行 throw new Error('x')，註冊回 500 之後，users 表裡不能留下那個 email。
  • 資料庫裡沒有 refresh token 原文：SELECT token_hash FROM refresh_tokens LIMIT 3 看到的是 64 個十六進位字元，跟瀏覽器裡的 cookie 值對不上。
  • 回應時間不洩漏帳號：用 curl -w '%{time_total}' 各打 10 次「帳號不存在」與「密碼錯」，兩者的時間差不多（都有算一次 argon2id）。
  • JWT_SECRET 不在 repo 裡：.env.example 只有開發用的假值，git log -p | grep JWT_SECRET 只看得到假值。
  • 每個 controller 都有宣告：grep -L "@Public\|@Authenticated\|@Permissions" src/**/*.controller.ts 沒有結果（第 10 課的 guard 會讓沒宣告的路由一律 403）。
  • ADR 0003 寫了代價：「後果」裡有「每個請求查一次 membership」與「access token 撤銷不了，靠短效期」。

常見錯誤

  • 角色或租戶放在 users 表：一個人只能屬於一個租戶，之後要支援多租戶就是一次大改。角色放在 membership。
  • 註冊分三次寫入、沒有交易：中間失敗會留下沒有租戶的帳號，而且 email 被占用。用一個交易，雜湊放在交易外。
  • 先查 email 有沒有人用、再寫入：併發時兩邊都查到沒有。讓唯一約束擋，P2002 轉 409。
  • 帳號不存在時直接回：錯誤碼不同、或回應快很多，都會洩漏帳號存不存在。一律 INVALID_CREDENTIALS，帳號不存在也算一次雜湊。
  • guard 用 jwt.decode()：decode 只解開 base64，不檢查簽章與期限，任何人都能自己做一張 token。一律 verifyAsync，並在 verifyOptions 寫死 algorithms。
  • refresh 沒有輪替，或輪替了但用過的只是拒絕：前者讓偷來的 token 能用 14 天；後者偵測到了重用卻沒撤銷家族，攻擊者手上那張新的照樣能用。
  • refresh cookie 沒有 Path：每個 API 請求都帶著長命的 token。限在 /api/v1/auth。
  • 登入限流以 IP 計數：攻擊者換 IP 就繞過；要保護的是帳號，以 email 計數。

小結

  • 人和租戶是多對多：users（全域、email 唯一）、tenants、memberships（user×tenant×role）三張表；角色放在 membership，林雅婷在每個租戶可以有不同角色。
  • 註冊＝一個交易建立 user、tenant、owner membership，中途失敗不留下殘缺帳號；雜湊在交易外算；ID 在程式產生；email 重複交給唯一約束，P2002 轉 409 EMAIL_TAKEN。
  • access token 15 分鐘、只放 sub 與 tid，演算法、issuer、audience 寫死；租戶只從驗過簽章的 token 來，角色不放進 token。
  • refresh token 存雜湊、每用一次就換、用過的再出現就撤銷整個家族；「標成已使用」用條件式更新，讓資料庫判斷併發；cookie 是 HttpOnly、SameSite=Strict、Path=/api/v1/auth。
  • 全域 guard 預設要登入，例外用 @Public()、@Authenticated() 明講；驗過的 sub、tid 放進請求上下文。
  • 登入失敗不洩漏帳號（錯誤碼、訊息、時間都一樣）；以 email 計數限流，回 429＋Retry-After；取捨寫進 ADR 0003，後果要寫代價。

下一課開始做租戶隔離：guard 放進請求上下文的 tid，怎麼變成每個查詢自動加上的 tenantId 條件，讓「忘了加條件」變得很難發生。
