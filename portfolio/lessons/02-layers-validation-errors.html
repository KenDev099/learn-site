階段 A：小專案走完一次 · 第 2 課

分層 API、驗證與錯誤格式

上一課的 repo 只有健康檢查。這一課的任務：把契約裡的五個端點（建立活動、列表、查一筆、報名、取消）做到前端同事可以放心串接。整課用同一個情境推進：你建立一場名額 3 的「手沖咖啡入門」，前端同事開始串報名頁。他會碰到三件事，你的 API 都要給出穩定的答案：表單送錯資料時，回應有沒有清楚說錯在哪；每一種失敗（找不到、已報名、名額滿）是不是同一個格式，讓他寫一個錯誤處理函式就夠；活動開放報名那一秒有 10 個人同時按「報名」，會不會收進第 4 個人。

做完這課，你的 repo 會有 src/common/（錯誤格式與 requestId）與 src/events/（controller、service、DTO、游標），通過練習 1～4 的驗收測試：驗證、404／409、併發報名、翻頁途中有人新增資料。

這課會用到：
  • NestJS 課第 7 課的 DTO＋全域 ValidationPipe：在 DTO 的欄位上用 class-validator 的裝飾器宣告規則，pipe 在請求進 controller 之前檢查。
  • NestJS 課第 8 課的 exception filter：所有丟出來的錯誤最後經過它，由它決定 HTTP 回應長什麼樣子。
  • NestJS 課第 15 課的條件式更新（updateMany 加 where 條件，再看回傳的 count 改到幾列）與互動式交易 $transaction(async tx => …)。
  • NestJS 課第 16 課的游標分頁：用上一頁最後一筆的排序值＋id 當游標，查詢時 take: limit + 1。
判分照第 1 課的方式：在你的專案 npm run start:dev，再在 learn 執行 node check.mjs nestjs pf02。測試會在你的開發資料庫建立活動與報名（名稱帶執行編號，可以重複跑）。

這課的路線：

  • 五個端點的程式各放哪裡：controller、service、Prisma 三層，為什麼先不切 repository。
  • 壞輸入怎麼在進 service 之前擋掉：DTO 與全域 ValidationPipe，壞掉的 id 為什麼回 404。
  • 每一種錯誤怎麼回同一個格式：ApiError、filter、requestId，以及資料庫錯誤在哪裡翻成業務錯誤。
  • 10 個人同時報名，名額 3 怎麼不超賣：條件式 UPDATE 與 FOR UPDATE 的取捨；取消時還名額。
  • 列表翻頁途中有人新增活動，怎麼不重複也不漏：游標分頁。

五個端點的程式各放哪裡？

前端同事看到的是五個 URL，但在你的 repo 裡，一個請求會經過好幾段程式：讀路徑與參數、檢查輸入、判斷業務規則、讀寫資料庫、決定狀態碼。這些全部寫在 controller 的一個方法裡也跑得動，問題是之後：要寫單元測試時得先模擬一個 HTTP 請求；名額規則要改時，得在一堆讀參數、設狀態碼的程式碼裡找它在哪。

NestJS 課第 18 課的分層就是在解這件事：每一層只回答一種問題。controller 只管 HTTP（哪個路徑、哪些參數、成功回幾號），service 一個方法對應一個用例（「報名」「取消」各是一個方法，業務規則都寫在這裡），最下面是資料存取。套到這個專案，src/events/ 裡是這幾個檔案：

檔案做什麼不做什麼
events.controller.ts路徑、參數、狀態碼（@HttpCode(204)）不碰 Prisma，不寫 if 判斷業務規則
events.dto.ts輸入的形狀與格式（長度、範圍、email）不查資料庫
events.service.ts用例：建立、列表、報名、取消；交易；把資料庫錯誤翻成業務錯誤不讀 req、不設狀態碼
cursor.ts游標的編碼與解碼（純函式，第 3 課寫單元測試）

「不做什麼」那一欄跟「做什麼」一樣重要。service 不讀 req、不設狀態碼，所以第 3 課可以直接 new 一個 service、呼叫 register() 來測，不用啟動 HTTP；controller 不碰 Prisma，所以換掉資料存取的方式時，controller 一行都不用改。

第 18 課還提過一層 repository：在 service 與 Prisma 之間再包一層介面，service 呼叫 eventRepo.findById() 而不是直接呼叫 Prisma。這個專案先不切，service 直接用 PrismaService。原因是它現在沒有要解決的問題：只有兩張表、每個查詢只被一個方法用到，多一層 repository 只是把 prisma.event.findMany(…) 換個名字包起來，讀程式的人要多跳一個檔案。值得切的時機是：同一個複雜查詢被好幾個 service 重複寫，或者真的要換資料來源。到那時再抽，改動也只在 service 裡，因為 controller 本來就不知道 Prisma 存在。

controller 的工作，就是把 HTTP 的東西取出來交給 service。程式裡的 ApiError 是這課自己定義的錯誤類別（第三節寫），開頭那個 id() 函式在下一節解釋，先看整體形狀：每個方法都只有一行，呼叫 service。

// src/events/events.controller.ts
// id 不是 UUID 時直接 404（不存在），不要讓壞掉的 id 跑到資料庫變成 500
const id = (code: string) => new ParseUUIDPipe({ exceptionFactory: () => new ApiError(404, code, '找不到') })

@Controller('events')
export class EventsController {
  constructor(private readonly events: EventsService) {}

  @Post()
  create(@Body() dto: CreateEventDto) {
    return this.events.create(dto)
  }

  @Get()
  list(@Query() q: ListEventsQuery) {   // ?cursor=…&limit=…，最後一節講游標
    return this.events.list(q.cursor, q.limit)
  }

  @Get(':id')
  get(@Param('id', id('EVENT_NOT_FOUND')) eventId: string) {
    return this.events.get(eventId)
  }

  @Post(':id/registrations')
  register(@Param('id', id('EVENT_NOT_FOUND')) eventId: string, @Body() dto: RegisterDto) {
    return this.events.register(eventId, dto)
  }

  @Delete(':id/registrations/:regId')
  @HttpCode(204)
  cancel(@Param('id', id('REGISTRATION_NOT_FOUND')) eventId: string, @Param('regId', id('REGISTRATION_NOT_FOUND')) regId: string) {
    return this.events.cancel(eventId, regId)
  }
}

寫好之後還要接線，路由才會生效：用 events.module.ts 把 controller 與 service 接起來（@Module({ controllers: [EventsController], providers: [EventsService] })），再把 EventsModule 加進第 1 課 app.module.ts 的 imports。忘了這一步的症狀是每個 /events 路徑都回 404，而且程式完全沒有報錯。

層分好了，但 controller 現在照單全收：前端同事建立「手沖咖啡入門」時如果 capacity 送成 "三"、或者多送一個 remaining，這些東西會原封不動地進到 service。下一節在入口擋住它們。

壞輸入怎麼在進 service 之前擋掉？

擋輸入的地方是 DTO。DTO 是一個 class，每個欄位用裝飾器寫出規則；全域 ValidationPipe 在每個請求進 controller 之前，把 body 或 query 跟對應的 DTO 對一次，不合規則就直接回 400，controller 的方法根本不會被呼叫。這樣 service 拿到的輸入一定是形狀正確的，不用每個方法自己再檢查一次型別。

這個專案有三個 DTO：建立活動、報名、列表的 query：

// src/events/events.dto.ts
export class CreateEventDto {
  @IsString() @Length(1, 100)
  title: string

  @IsISO8601({ strict: true })   // 是不是「未來」由 service 判斷：要跟現在的時間比
  startsAt: string

  @IsInt() @Min(1) @Max(500)
  capacity: number
}

export class RegisterDto {
  // 存小寫：Ann@x.com 與 ann@x.com 是同一個人，唯一約束才擋得住
  @Transform(({ value }) => typeof value === 'string' ? value.trim().toLowerCase() : value)
  @IsEmail()
  email: string

  @IsString() @Length(1, 100)
  name: string
}

export class ListEventsQuery {
  @IsOptional() @IsString()
  cursor?: string

  // query string 的值都是字串，@Type 先轉成數字再驗證
  @IsOptional() @Type(() => Number) @IsInt() @Min(1) @Max(100)
  limit?: number
}

RegisterDto 的 @Transform 值得多看一眼。第 1 課用 @@unique([eventId, email]) 讓同一場活動、同一個 email 只能報一次，但資料庫比對字串時分大小寫：Ann@x.com 與 ann@x.com 對它來說是兩個不同的值。在 DTO 先轉小寫、去掉頭尾空白，所有寫進資料庫的 email 都是同一種寫法，唯一約束才真的擋得住同一個人報兩次。

DTO 寫好，還要讓 pipe 對每個請求生效。全域 pipe 寫在 src/app.setup.ts 的 configureApp()：第 1 課開的那個函式，main.ts 與第 3 課的 E2E 測試都呼叫它，所以兩邊的行為一樣。

app.useGlobalPipes(new ValidationPipe({
  whitelist: true,              // 去掉 DTO 沒宣告的欄位
  forbidNonWhitelisted: true,   // 有多餘欄位就 400，而不是默默忽略
  transform: true,
  exceptionFactory: errors => new ApiError(400, 'VALIDATION_FAILED',
    errors.flatMap(e => Object.values(e.constraints ?? {})).join('；') || '輸入不正確'),
}))

三個選項各擋一件事：

  • whitelist：DTO 沒宣告的欄位不會進到 service。少了它，有人在報名或建立活動時多送 { "remaining": 999 }，而 service 剛好寫了 data: { ...dto }，他就能自己改剩餘名額。這種「把請求整包寫進資料庫，結果連不該讓使用者改的欄位也被改掉」的漏洞叫大量賦值（mass assignment）。
  • forbidNonWhitelisted：多餘欄位直接 400。只開 whitelist 的話，欄位被默默拿掉、請求成功，前端同事把 capacity 拼成 capasity 也不會知道，只會覺得「名額怎麼沒存進去」。
  • transform：把 body 轉成 DTO 的實例。沒有它，上面的 @Transform（轉小寫）不會生效，query 的 limit 也沒辦法用 @Type(() => Number) 從字串轉成數字。

最後的 exceptionFactory 決定驗證失敗時丟出什麼錯誤。不設的話，Nest 會丟它內建的 400，回應的形狀跟我們其他錯誤不一樣；設成我們自己的 ApiError，驗證失敗就是 errorCode: "VALIDATION_FAILED"，跟其他錯誤同一個格式（下一節定義）。

body 之外，路徑上的 id 也是使用者的輸入。回頭看上一節 controller 開頭的 id()：它用 ParseUUIDPipe 檢查 id 是不是 UUID，不是就丟 404。如果不檢查，/events/abc 的 abc 會直接進 Prisma，PostgreSQL 回「不是合法的 uuid」，變成 500，前端同事看到的是「伺服器壞了」。那為什麼是 404 而不是 400？對呼叫的人來說，「abc 這個活動」就是不存在，跟 /events/<一個沒人用過的 UUID> 沒有差別；契約也這樣寫。

有一條規則 DTO 判斷不了：「startsAt 要在未來」。DTO 只看輸入本身，而這條規則要跟「現在」比，所以放在 service。service 的方法收一個 now 參數、預設 new Date()，平常不用傳；第 3 課的單元測試傳一個固定時間進去，結果就不會因為哪天執行而不同。原則是：看輸入本身就判斷得出來的規則放 DTO，要查資料庫或要跟外部狀態（現在時間、其他資料）比的放 service。service 的開頭長這樣（PAGE 是列表預設一頁幾筆，最後一節的列表才用到）：

// src/events/events.service.ts
import { Prisma, type Event } from '../generated/prisma/client.js'   // 第 1 課 prisma generate 產生的 client

const PAGE = 20   // 列表預設一頁幾筆
// 回應只挑契約上的欄位，時間轉成 ISO 字串
const view = (e: Event) => ({ id: e.id, title: e.title, startsAt: e.startsAt.toISOString(), capacity: e.capacity, remaining: e.remaining })
const notFound = () => new ApiError(404, 'EVENT_NOT_FOUND', '找不到這個活動')

async create(dto: CreateEventDto, now = new Date()) {
  const startsAt = new Date(dto.startsAt)
  if (startsAt <= now) throw new ApiError(400, 'VALIDATION_FAILED', 'startsAt 要是未來的時間')
  return view(await this.prisma.event.create({ data: { title: dto.title, startsAt, capacity: dto.capacity, remaining: dto.capacity } }))
}

async get(id: string) {
  const e = await this.prisma.event.findUnique({ where: { id } })
  if (!e) throw notFound()
  return view(e)
}

注意 create 的 data 是一個欄位一個欄位寫的，不寫 { ...dto }。這是大量賦值的第二道防線：就算哪天有人把 pipe 的 whitelist 關掉，remaining 也只會等於 capacity，不會等於使用者送來的值。出口也一樣：回應經過 view() 只挑契約上的欄位，資料表以後多了內部欄位（例如 createdAt），也不會自己跑到 API 上。

💡 實務上：DTO 就是 API 契約的程式版本
前端最常回報的不是 500，而是「我送了這個欄位，怎麼沒效果」：多餘欄位被默默忽略，或者型別不對被自動轉掉。forbidNonWhitelisted 讓這種問題在開發時就變成 400，訊息指出是哪個欄位。code review 時看到 data: { ...dto } 或 data: body，就問一句：「這個 DTO 以後多一個欄位，它會不會直接寫進資料庫？」

到這裡，壞輸入都在入口被擋下了。但前端同事現在會收到好幾種錯誤：驗證失敗的 400、壞 id 的 404、找不到活動的 404，以後還有已報名、名額滿。如果它們的形狀各不相同，他就得為每一種寫一段判斷。下一節讓它們長得一模一樣。

每一種錯誤怎麼回同一個格式？

先定目標。契約規定錯誤回應一律是這四個欄位：

{ "statusCode": 409, "errorCode": "EVENT_FULL", "message": "名額已滿", "requestId": "3f0c…" }

每個欄位有不同的讀者。statusCode 給 HTTP 層與監控看。errorCode 給前端的程式看：前端用它判斷要顯示什麼（例如 EVENT_FULL 就把按鈕改成「已額滿」），所以它一旦公開就不能隨便改。message 給人看，可以隨時改字。requestId 給你自己看：使用者回報問題時附上它，你拿去 log 找那一次請求。

要讓所有錯誤都長這樣，需要三塊程式，都放在 src/common/：一個錯誤類別讓 service 丟出帶 errorCode 的錯誤、一個 middleware 幫每個請求配一個 requestId（middleware 是請求進到 Nest 的路由、pipe、controller 之前先執行的函式，每個請求都會經過，所以適合在最前面配 requestId，後面的 log 和 filter 都拿得到）、一個 filter 負責把任何錯誤轉成上面的格式。前兩塊：

// src/common/api-error.ts：預期內的錯誤一律用它丟
export class ApiError extends HttpException {
  constructor(status: number, readonly errorCode: string, message: string) {
    super({ statusCode: status, errorCode, message }, status)
  }
}

// src/common/request-id.ts：每個請求一個 id，放進 req 與回應標頭。收到格式合法的就沿用
// 告訴 TypeScript：Express 的 Request 多了 requestId 欄位，不然 req.requestId 會型別錯誤
declare module 'express-serve-static-core' {
  interface Request { requestId: string }
}

const VALID = /^[A-Za-z0-9_-]{1,64}$/
export function requestId(req: Request, res: Response, next: NextFunction) {
  const incoming = req.get('x-request-id')
  req.requestId = incoming && VALID.test(incoming) ? incoming : randomUUID()
  res.setHeader('x-request-id', req.requestId)
  next()
}

HttpException 是 Nest 內建的錯誤類別，建構時帶狀態碼和回應內容，filter 用 getStatus()／getResponse() 取出來。ApiError 繼承它，只是多帶一個 errorCode。前兩節已經在用它：ParseUUIDPipe 的 404、ValidationPipe 的 400、service 的「找不到這個活動」。requestId 的 middleware 如果請求本來就帶了 x-request-id（例如前面的閘道已經配過），格式合法就沿用，讓同一個請求在不同服務的 log 裡是同一個 id；沒有就自己產生一個。

第三塊是 filter，所有錯誤最後都從這裡出去：

// src/common/error.filter.ts：所有錯誤都從這裡出去
const CODE_BY_STATUS: Record<number, string> = { 400: 'VALIDATION_FAILED', 404: 'NOT_FOUND', 413: 'PAYLOAD_TOO_LARGE', 503: 'SERVICE_UNAVAILABLE' }

@Catch()
export class ErrorFilter implements ExceptionFilter {
  private readonly logger = new Logger('Errors')

  catch(exception: unknown, host: ArgumentsHost) {
    const req = host.switchToHttp().getRequest<Request>()
    const res = host.switchToHttp().getResponse<Response>()
    if (exception instanceof HttpException) {
      const status = exception.getStatus()
      const body = exception.getResponse() as { errorCode?: string; message?: string | string[] }
      const message = typeof body === 'string' ? body : [body.message ?? exception.message].flat().join('；')
      res.status(status).json({ statusCode: status, errorCode: body.errorCode ?? CODE_BY_STATUS[status] ?? `HTTP_${status}`, message, requestId: req.requestId })
      return
    }
    // 非預期的錯誤：細節只進 log，回應不帶 stack 與資料庫訊息
    this.logger.error(`requestId=${req.requestId}`, exception instanceof Error ? exception.stack : String(exception))
    res.status(500).json({ statusCode: 500, errorCode: 'INTERNAL_ERROR', message: '伺服器發生錯誤', requestId: req.requestId })
  }
}

這個 filter 把錯誤分成三種處理：

  • 我們丟的 ApiError：已經帶 errorCode，照原樣輸出，補上 requestId。
  • Nest 自己丟的 HttpException：例如路徑不存在的 404、body 太大的 413，它們沒有 errorCode，filter 依狀態碼從 CODE_BY_STATUS 補一個。所以 @Catch() 不帶參數：不帶參數就是「什麼都接」，連這些不是我們丟的錯誤也接得到。
  • 不是 HttpException 的錯誤（程式 bug、資料庫斷線）：一律 500 INTERNAL_ERROR。stack 只寫進 log，連同 requestId，回應裡不帶。

兩樣東西都要在 configureApp() 登記才會生效：app.use(requestId)、app.useGlobalFilters(new ErrorFilter())。

還剩一類錯誤沒處理：資料庫丟的錯誤。同一個 email 第二次報名「手沖咖啡入門」時，第 1 課的唯一約束會擋下來，Prisma 丟出錯誤碼 P2002，代表違反唯一約束（NestJS 課第 14 課）。它不是 HttpException，如果沒人接，filter 會把它當成非預期錯誤回 500。前端同事要的是 409 ALREADY_REGISTERED。

那要在哪裡翻譯？在 service，不在 filter。同一個 P2002，在報名代表「已經報名過」，在別的表可能代表「名稱重複」；只有正在執行用例的 service 知道是哪一個，filter 只看得到一個錯誤碼。所以 service 自己 try/catch，認得的翻成 ApiError，認不得的原樣往上丟：

} catch (e) {
  if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2002') throw new ApiError(409, 'ALREADY_REGISTERED', '這個 email 已經報名過')
  throw e   // 其他錯誤往上丟，filter 變成 500
}

分工就清楚了：service 決定「這是什麼業務錯誤」，filter 決定「錯誤長什麼樣子」，以及「沒人認得的錯誤一律 500」。另一個常見的 Prisma 錯誤 P2025 這個專案用不到，原因見課末「補充與查表」。

💡 實務上：requestId 是客服與工程師之間的橋
使用者回報「報名失敗」，客服只能轉一張截圖。如果錯誤畫面印出 requestId，你在 log 搜那個 id，就能看到那次請求的輸入、走到哪一步、資料庫回了什麼。所以 500 的回應要帶 requestId，但不帶 stack：stack 會透露檔案路徑、套件版本與 SQL，對攻擊者比對你有用。收到外面送來的 x-request-id 要先驗證格式（長度、字元），不然有人可以塞換行字元偽造 log 行（第 16 課再談）。

現在輸入擋好了、錯誤格式一致了，前端同事一個一個點都會看到正確的結果。剩下開場的第三件事：報名開放那一秒，10 個人同時按下去。

10 個人同時報名，名額 3 怎麼不超賣？

這是這個專案唯一真正的業務規則，也是最容易寫錯的地方。最直覺的寫法是「先查還有沒有名額，有就新增」，通常叫 check-then-insert：

// 錯誤：check-then-insert
const e = await this.prisma.event.findUnique({ where: { id: eventId } })
const taken = await this.prisma.registration.count({ where: { eventId } })
if (taken >= e.capacity) throw new ApiError(409, 'EVENT_FULL', '名額已滿')
await this.prisma.registration.create({ data: { … } })

一次一個請求時它完全正確。你自己點、前端同事一個一個點、一般的 E2E 一個一個送，都會看到「前 3 個成功、第 4 個 409」，所以它很容易通過 review。

問題出在請求同時到的時候。每個請求都是獨立執行的，count 與 create 之間有一段空檔，別的請求可以在這段空檔裡做事。「手沖咖啡入門」開放報名的那一秒，10 個請求幾乎同時到：10 個都先執行 count，都數到「0 個人報名」；10 個都通過 if；10 個都執行 create。名額 3 的活動收了 10 個人，而且沒有任何一句 SQL 出錯。這跟 PostgreSQL 課第 19 課的 lost update 是同一類問題：兩個請求都根據同一個舊值做決定，其中一個的結果等於被蓋掉。練習 3 的驗收測試就是同時送 10 個報名。

病因是「判斷」和「寫入」分成兩句，中間可以被插隊。所以修法是讓它們變成同一句 SQL。參考實作的寫法：

// src/events/events.service.ts
async register(eventId: string, dto: RegisterDto) {
  try {
    return await this.prisma.$transaction(async tx => {
      const { count } = await tx.event.updateMany({ where: { id: eventId, remaining: { gt: 0 } }, data: { remaining: { decrement: 1 } } })
      if (count === 0) {
        if (!(await tx.event.findUnique({ where: { id: eventId }, select: { id: true } }))) throw notFound()
        throw new ApiError(409, 'EVENT_FULL', '名額已滿')
      }
      const r = await tx.registration.create({ data: { eventId, email: dto.email, name: dto.name } })
      return { id: r.id, eventId, email: r.email, name: r.name, createdAt: r.createdAt.toISOString() }
    })
  } catch (e) {
    if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2002') throw new ApiError(409, 'ALREADY_REGISTERED', '這個 email 已經報名過')
    throw e
  }
}

這段程式有三個重點，一個一個看。

第一，為什麼不會超賣。updateMany 送出的是 UPDATE events SET remaining = remaining - 1 WHERE id = $1 AND remaining > 0：「還有名額嗎」寫在 WHERE 裡，「扣一個」寫在 SET 裡，是同一句。在 PostgreSQL 預設的 READ COMMITTED 隔離等級下（Prisma 沒另外設定時就是它），對同一列的 UPDATE 會排隊，後面的人要等前一個交易結束，再用最新的值重新檢查 remaining > 0（PostgreSQL 課第 19 課）。10 個請求同時到，前 3 個依序把 remaining 從 3 扣到 0；第 4 個以後重新檢查時看到 0，WHERE 不成立，改到 0 列，count 是 0，回 409。

第二，為什麼要包在交易裡。扣名額和新增報名是兩句 SQL，它們要一起成功或一起失敗。想像同一個 email 第二次報名：updateMany 已經扣了一個名額，接著 create 撞到唯一約束（第 1 課的 @@unique([eventId, email])）丟出 P2002。在交易裡，這個錯誤讓整個交易回滾，剛剛扣掉的名額也回來了；不在交易裡，名額就白白少了一個，報名的人越多、活動越早「額滿」。練習 2 會檢查「重複報名不會多扣名額」。P2002 被丟出交易之後，外層的 catch 照上一節的方式翻成 409。

第三，count === 0 時為什麼還要查一次。改到 0 列有兩種原因：活動不存在，或名額滿了。前端同事需要分得出來（404 跟 409 顯示的東西不同），所以這時才多查一次活動在不在。正常報名的路上只有兩句 SQL，多出來的查詢只發生在失敗的時候。

條件式 UPDATE 不是唯一的解法。另一種寫法是先把活動那一列鎖住，再慢慢判斷：

await tx.$queryRaw`SELECT remaining FROM events WHERE id = ${eventId}::uuid FOR UPDATE`
// 拿到鎖之後判斷 remaining、新增報名、扣名額；別的交易要等這個交易結束才鎖得到這一列

FOR UPDATE 讓同一場活動的報名一個一個進行：其他也要 SELECT … FOR UPDATE（或 UPDATE）這一列的交易必須等鎖釋放，也就是拿到鎖的交易 commit 之後才能繼續，所以它們判斷時看到的一定是最新的值。普通的 SELECT 不受影響，隨時讀得到已 commit 的值。兩種寫法的取捨：

寫法優點代價
條件式 UPDATE … WHERE remaining > 0一句 SQL，判斷與寫入不可能被插隊；用 Prisma 的 updateMany 就寫得出來判斷只能寫成 WHERE 條件；規則變複雜（例如會員優先、候補名單）就塞不下
SELECT … FOR UPDATE 再判斷拿到鎖之後可以寫任意複雜的判斷要寫 raw SQL；鎖住的時間是整個交易，交易裡不能做慢的事（寄信、呼叫外部 API）

這個專案的規則「還有名額就扣一個」一句 WHERE 寫得完，所以選條件式 UPDATE。把「為什麼選它」寫進 README 的設計決定（第 5 課），面試時這就是一個講得出取捨的故事。

有報名就有取消，取消要把名額還回去，同樣有「兩件事要一起成功」與「同一件事做兩次」的問題。所以它也在交易裡：刪報名、加回名額。刪除用 deleteMany，where 同時寫報名 id 與活動 id，再看回傳的 count：0 就丟 404，不會往下加名額。這樣同一筆取消兩次，第二次刪不到東西、直接 404，名額不會多加一次；拿 A 活動的 id 配 B 活動的報名 id，也刪不到、也是 404。

async cancel(eventId: string, registrationId: string) {
  await this.prisma.$transaction(async tx => {
    const { count } = await tx.registration.deleteMany({ where: { id: registrationId, eventId } })
    if (count === 0) throw new ApiError(404, 'REGISTRATION_NOT_FOUND', '找不到這筆報名')
    await tx.event.update({ where: { id: eventId }, data: { remaining: { increment: 1 } } })
  })
}

最後還有一道保險在資料庫裡：第 1 課 migration 手寫的 CHECK ("remaining" BETWEEN 0 AND "capacity")。程式哪天寫錯，讓名額要變成負的，資料庫會拒絕這次寫入。使用者看到的是 500，log 裡看得到原因，而不是錯的資料默默存進去、等客服來回報。

💡 實務上：「同時」比你想的常見
熱門活動開放報名的那一秒、前端按鈕沒有防連點、手機網路不穩自動重送，都會讓同一個資源同時收到好幾個請求。這類 bug 在開發時幾乎不會出現，上線後才以「名額 30 收了 32 個人」的形式被客服回報，而且很難重現。看到「先查再寫」的程式碼，先問：兩個請求同時走到這裡會怎樣？能不能把判斷寫進 WHERE、交給唯一約束，或先鎖住？

報名與取消都穩了。前端同事的最後一個頁面是活動列表，而列表有它自己的「同時」問題：使用者在翻頁，別人在新增活動。

列表翻頁途中有人新增活動，怎麼不重複也不漏？

列表一次回 20 筆，要分頁。最直覺的是 offset 分頁：第二頁就是 skip: 20, take: 20，「跳過前 20 筆，再拿 20 筆」。NestJS 課第 16 課比較過它的問題：它是用「第幾筆」來記位置，而資料在翻頁途中會變。

用這個專案想一次。活動依 startsAt 由早到晚排，使用者看完第一頁的 20 場。這時有人建立了一場時間比較早的活動，它排進了第一頁的範圍，原本的第 20 場被擠到第 21 個位置。使用者按下一頁，skip: 20 從第 21 個開始拿，於是第一頁看過的最後一場又出現了一次。反過來，第一頁範圍內有活動被刪掉，後面的資料往前移，就會有一場在兩頁之間被跳過、誰都沒看到。活動的 startsAt 可以是任何時間，新活動可能排在任何位置，所以這個問題在這裡一定會發生。

游標分頁改用「最後看到哪一筆」來記位置：第一頁回傳時，順便給一個游標，記著這一頁最後一筆的 (startsAt, id)；前端要下一頁時把游標送回來，查詢條件是「排在這一筆後面的」。前面插進多少新資料都不影響，因為位置是用值記的，不是用筆數。游標的編碼與解碼放在 cursor.ts：

// src/events/cursor.ts：游標＝上一頁最後一筆的 (startsAt, id)，編成 base64url。排序鍵要唯一，所以加上 id
export const encodeCursor = (c: Cursor) => Buffer.from(JSON.stringify([c.startsAt.toISOString(), c.id])).toString('base64url')

export function decodeCursor(raw: string): Cursor {
  try {
    const [s, id] = JSON.parse(Buffer.from(raw, 'base64url').toString('utf8'))
    const startsAt = new Date(s)
    if (typeof id !== 'string' || !/^[0-9a-f-]{36}$/.test(id) || Number.isNaN(startsAt.getTime())) throw new Error()
    return { startsAt, id }
  } catch {
    throw new ApiError(400, 'VALIDATION_FAILED', 'cursor 格式不正確')
  }
}

游標是前端送回來的字串，所以它跟 body 一樣是使用者的輸入：可能被截斷、被亂改。decodeCursor 把解碼包在 try/catch 裡，任何一步失敗都回 400 VALIDATION_FAILED，不能讓 JSON.parse 的例外穿出去變成 500。

service 用游標組出查詢：

// src/events/events.service.ts
async list(cursor?: string, limit = PAGE) {
  const c = cursor ? decodeCursor(cursor) : null
  const rows = await this.prisma.event.findMany({
    where: c ? { OR: [{ startsAt: { gt: c.startsAt } }, { startsAt: c.startsAt, id: { gt: c.id } }] } : {},
    orderBy: [{ startsAt: 'asc' }, { id: 'asc' }],
    take: limit + 1,   // 多拿一筆，才知道還有沒有下一頁
  })
  const items = rows.slice(0, limit)
  return { items: items.map(view), nextCursor: rows.length > limit ? encodeCursor(items[items.length - 1]) : null }
}

這段程式要看四個地方：

  • 排序加上 id：兩場活動同一個時間開始時，只按 startsAt 排，它們誰先誰後是不固定的，每次查可能不一樣。加上 id 之後，每一筆在排序裡的位置都唯一，游標才指得準。
  • where 是「時間比游標晚，或時間一樣但 id 比較大」：只寫 startsAt > 游標 的話，跟游標同一時間開始的其他活動會被整批跳過。
  • take: limit + 1：多拿一筆，拿得到就代表還有下一頁，回傳 nextCursor；拿不到就是最後一頁，nextCursor 是 null。這樣不用另外 count 一次。
  • 索引：第 1 課 schema 的 @@index([startsAt, id]) 正好對應這個排序與 where，讓查詢走索引，翻到第幾頁都一樣快。

跟前端同事要講清楚一件事：游標對前端是一個不透明的字串，不要解析它、不要自己組，拿到什麼就原樣送回來。這樣你之後改排序或改編碼方式，前端不用跟著改。到這裡，五個端點都做完了，前端同事遇到的三件事都有穩定的答案。

補充與查表

為什麼用不到 P2025：P2025 是 Prisma 在 update／delete 找不到那一列時丟的錯誤（要改的那一列不存在）。這個專案的取消用 deleteMany，看回傳的 count 是不是 0，直接丟 REGISTRATION_NOT_FOUND，不用等 Prisma 丟錯再接。這比 delete 再接 P2025 好讀，而且 where 可以同時寫 id 與 eventId：拿 A 活動的 id 配 B 活動的報名 id，也是 404。

練習

四題都是對你啟動中的 API 打 HTTP。一題一題做：每做完一個端點就跑一次 node check.mjs nestjs pf02。

練習 1：輸入驗證與錯誤格式。建立活動、報名、列表的每一種壞輸入（title 空字串或超過 100 字、startsAt 不是 ISO 或是過去、capacity 不是 1～500 的整數、email 格式不對、多餘欄位、壞掉的 cursor、limit 超出 1～100）都回 400 VALIDATION_FAILED；錯誤回應是 { statusCode, errorCode, message, requestId }，requestId 等於回應標頭 x-request-id。

練習 2：404 與 409。不存在或格式不對的活動 id 回 404 EVENT_NOT_FOUND、取消不存在的報名回 404 REGISTRATION_NOT_FOUND；報名成功的回應 email 是小寫；同一個 email（換大小寫也算）再報名回 409 ALREADY_REGISTERED，而且不會多扣名額。

練習 3：名額。名額 3 的活動同時收到 10 個報名，恰好 3 個 201、7 個 409 EVENT_FULL，remaining 是 0；取消回 204、名額加回 1、空出來的名額可以再報；同一筆取消兩次，第二次 404，名額不會多加。

練習 4：游標分頁。測試建立 12 場活動，用 limit=5 一頁一頁走完整個列表，途中在已經看過的位置插入 2 場新活動。要求：沒有活動重複出現、12 場都出現、順序依 startsAt（相同時依 id）由早到晚、最後一頁的 nextCursor 是 null。

練習 5：同事的報名寫成「先 count 已報名人數，小於名額才 create」。他說：「我寫了 E2E，報 3 個成功、第 4 個 409，測試是綠的。」為什麼測試會過，上線卻會超賣？

✓ check-then-insert 只在「判斷」與「寫入」之間沒有別人插進來時才正確，一次一個的測試剛好永遠是這樣。要測到它，就要同時送多個請求（練習 3）。修法是把判斷放進寫入那一句（條件式 UPDATE）或先鎖住活動列。a 錯在問題跟資料量無關，兩個請求就能重現。（第 2 課）

練習 6：重複報名時 Prisma 丟出 P2002。同事想在全域 exception filter 裡寫「所有 P2002 一律回 409 ALREADY_REGISTERED」，這樣 service 就不用 try/catch。這個做法的問題是什麼？

✓ 同一個資料庫錯誤在不同用例代表不同的業務錯誤，只有 service 知道當下在做什麼，所以在 service 翻成 ApiError。filter 只負責格式與「沒人接的錯誤一律 500」。a 錯：@Catch() 不帶參數什麼都接得到；b 錯：錯誤從 $transaction 丟出來時交易已經回滾。（第 2 課）

練習 7：另一個同事提議：「check-then-insert 不用改寫法，把那個交易的隔離等級設成 SERIALIZABLE 就不會超賣了。」這樣夠嗎？

✓ SERIALIZABLE 不會讓交易排隊，而是偵測到「結果跟依序執行不一樣」時讓其中一個失敗，失敗的要由程式重試（有上限）。所以它能用，但要加重試迴圈，衝突多時重試也多。b 是最常見的誤解：它不是排隊。這個專案的規則一句 WHERE 寫得完，條件式 UPDATE 更簡單。（第 2 課、PostgreSQL 課第 31 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • controller 裡沒有業務規則：events.controller.ts 沒有 import PrismaService，也沒有判斷名額的 if。
  • 沒有 data: { ...dto }：搜尋 ...dto，寫進資料庫的欄位都是一個一個列出來的。
  • 500 不洩漏內部訊息：暫時在某個 service 方法第一行 throw new Error('boom')，打那個端點，回應只有 INTERNAL_ERROR 與 requestId，終端機的 log 有 stack 與同一個 requestId。改回來。
  • 超賣真的被擋：把 remaining: { gt: 0 } 這個條件拿掉，練習 3 要失敗（CHECK 約束會讓多出來的報名變成 500）。改回來。
  • 錯誤代碼有清單：README 或契約裡列出每個 errorCode 與狀態碼，跟程式裡用到的一致（grep -rn "new ApiError" src 對一次）。

常見錯誤

  • 只開 whitelist、沒開 forbidNonWhitelisted：多餘欄位被默默拿掉，前端打錯欄位名稱永遠不會知道。兩個一起開。
  • 用 findUnique 檢查 email 有沒有報過，再 create：兩個請求同時查到「沒有」。重複交給唯一約束，接 P2002 轉 409。
  • email 沒轉小寫就存：Ann@x.com 與 ann@x.com 被當成兩個人，唯一約束擋不到。在 DTO 用 @Transform 轉，所有寫入路徑都經過它。
  • 扣名額與新增報名分成兩個請求或兩個交易：新增失敗（重複報名）時名額已經扣了，名額越報越少。放在同一個 $transaction。
  • 取消時忘了還名額，或用 delete 不看結果就 increment：取消兩次會多出一個名額。用 deleteMany 看 count，0 就 404。
  • 壞掉的 id 或游標變成 500：ParseUUIDPipe 讓壞 id 變 404，decodeCursor 包 try/catch 變 400。500 只留給真正沒預期到的錯誤。
  • 游標只用 startsAt：同一時間開始的活動會在翻頁時漏掉。排序與游標都加上 id。

小結

  • 小專案的分層是 controller → service → Prisma：controller 只管 HTTP、service 一個方法一個用例；repository 等到查詢真的重複、或要換資料來源再抽。
  • 壞輸入在入口擋掉：DTO＋全域 ValidationPipe（whitelist、forbidNonWhitelisted、transform），路徑 id 用 ParseUUIDPipe 轉成 404；要跟現在時間比的規則放 service。
  • 所有錯誤從同一個 filter 出去：{ statusCode, errorCode, message, requestId }；資料庫錯誤（P2002）在 service 翻成業務錯誤，沒人接的一律 500 且不帶 stack。
  • 名額用交易裡的條件式 UPDATE … WHERE remaining > 0：判斷與寫入是同一句，不會超賣；重複報名時唯一約束讓整個交易回滾。
  • check-then-insert 一次一個請求時是對的，所以要用併發測試才抓得到。
  • 游標分頁用 (startsAt, id) 記位置，翻頁途中有人新增資料也不重複、不漏；壞掉的游標回 400。
