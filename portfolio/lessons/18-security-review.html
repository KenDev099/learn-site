階段 B3：上線與作品 · 第 18 課

資安檢查：用探針攻擊自己的作品

你的 SaaS 已經能部署、有 CI、有 demo 網址。下一步是把連結放進履歷，交給面試官，甚至交給第一個真的客戶。在那之前要回答一個問題：一個登入的使用者，能不能拿到不屬於他的東西？到目前為止，每一課的驗收測試都是課程寫好的，它們只認得契約裡的平台端點（projects、members、files…）。你自己選的業務模組（工單、預約、庫存）從來沒有被人用「另一家公司的帳號」打過。

這一課的任務是：在作品公開前，對它做一次完整的資安審查，以客服工單為例（選預約或庫存的人，把工單換成你的主資源）。你會換到攻擊者的位置，先畫一頁威脅模型決定查哪裡，再用測試證明業務模組沒有跨租戶漏洞、多送的欄位不會生效、設定沒有開後門，最後對照業界的清單確認沒有漏項，並把找到的問題寫成 issue 與修補的 commit。面試時，「我找到並修了」比「我寫得很安全」有說服力得多。

這課會用到：
  • auth 課第 19 課的 BOLA：授權要檢查到「這一筆」資料，查不到就 404，不透露存在。
  • auth 課第 24 課的 OWASP API Top 10（2023）與一次安全審查的做法。
  • auth 課第 25 課的威脅模型：資料流程圖、信任邊界、STRIDE、風險排序。
  • auth 課第 5 課的 CORS：Access-Control-Allow-Origin 是伺服器允許哪些網站的 JavaScript 讀回應。
  • 第 8、9 課的 TenantDb（掛了 tenant extension、在交易裡設定目前租戶的資料存取入口）與 pf_app（受 RLS 限制的 API 連線帳號）。
這課的練習 1 要先在 work/portfolio.json 的 saas.bolaProbes 登記你的業務模組（格式在契約最後）。練習 2 會用到 Mailpit 收邀請信，跟第 10 課一樣。

這課的路線：

  • 從哪裡開始查：一頁威脅模型，排出最值得攻擊的地方（跨租戶讀寫排第一）。
  • 怎麼證明工單模組沒有跨租戶漏洞：BOLA 探針，以及探針打出 200 時漏洞通常長什麼樣。
  • 探針只在 learn 裡，自己的 repo 怎麼一直保有這個保護：跨租戶 E2E 表。
  • 拿不到別人的資料，還能不能改自己不該改的欄位：mass assignment。
  • 業務邏輯守住了，設定會不會漏；有沒有漏項：安全標頭、CORS、body 上限、錯誤訊息，再用 OWASP API Top 10 對照。
  • 找到的問題怎麼處理、怎麼變成作品的一部分；套到你的題目。

從哪裡開始查？先畫一頁威脅模型

資安檢查最常見的失敗，是拿一份清單從頭做到尾：每一項都花一樣的時間，最後在「錯誤訊息透露框架名稱」上花了一下午，真正會讓客戶資料外洩的地方卻沒看。所以審查的第一步不是動手，而是先回答「這個系統裡，什麼東西被拿走或改掉會出事、別人從哪裡進來、哪裡是我不能相信輸入的地方」。這三個問題的答案合起來，就是auth 課第 25 課教的威脅模型。

三個問題分別對應資產、入口、信任邊界；再加上第四項威脅，也就是攻擊者在這些入口上能做的壞事，下面的表就照這四項填：

  • 資產：被讀走或被改掉會造成損失的東西。不只是資料，也包括能拿來取得資料的鑰匙，例如 secret 與 token。
  • 入口：外面的人能送東西進來的地方。每一個 API 端點都是入口，不用登入就能打的入口特別要注意，因為攻擊者連帳號都不用。
  • 信任邊界：資料從「你控制不了的地方」流進「你控制的地方」的那條線。跨過這條線的每一個值，都要當成攻擊者可能改過的。
  • 威脅：攻擊者在入口上能做的壞事，例如讀到不該讀的、改到不該改的、讓服務停擺。

填到你的作品上，一頁就夠：

項目這個 SaaS 的答案
資產（被拿走或改掉會出事的）每個租戶的業務資料、檔案、成員名單與 email；refresh token；JWT_SECRET 與兩組資料庫密碼
入口所有 /api/v1/*；不用登入的 signup、login、接受邀請、refresh；檔案上傳；邀請信裡的連結
信任邊界瀏覽器 → API（任何輸入都不可信，包括 body 裡的 tenantId、role）；API → 資料庫（pf_app 只能動自己租戶的列）；API → worker（job 資料只放 id）
最在意的威脅租戶 A 讀寫租戶 B 的資料（資訊外洩、竄改）；低權限的成員做高權限的事（權限提升）；一個租戶把服務拖垮（阻斷服務）

三個威脅裡，跨租戶讀寫在多租戶系統排第一。原因是它的後果跟其他兩個不同等級：權限提升影響的是同一家公司內部，服務被拖垮之後會恢復；但「A 公司的客戶資料給了 B 公司」一發生就收不回來，要通報、要調查影響了哪些資料、從什麼時候開始。

前面的課已經用兩道防線擋這個威脅：第 8 課的 Prisma extension 在每個查詢自動加上 tenantId 條件，第 9 課的 RLS 讓資料庫本身只給目前租戶的列。但防線有一個前提：它只保護有走進防線的程式。查詢如果沒經過 extension，就不會被加條件；連線如果用的是不受 RLS 限制的資料庫帳號，資料庫也不會擋。所以這次審查的第一個問題很具體：你後來才加的業務模組（以下用工單示範），有沒有每一個查詢都走進防線？這張表先放進 repo 的 docs/threat-model.md，README 連過去，後面還會在同一份檔案補一張對照表。

怎麼證明工單模組沒有跨租戶漏洞？用 BOLA 探針打它

上一節留下的問題是「工單模組有沒有走進防線」。最直覺的做法是讀程式碼，一個一個查詢看過去。這有兩個問題：程式會一直改，今天看過不代表下個月還對；而且漏洞常常藏在「看起來很正常」的程式裡，讀的人不一定看得出來。比較可靠的做法是反過來：不管程式怎麼寫，直接用另一家公司的帳號去打，看結果。

這種「改網址上的 id 就讀到別人的資料」的漏洞，OWASP 叫它 BOLA（Broken Object Level Authorization，物件層級授權失效）：系統檢查了「你有沒有登入」「你能不能用工單功能」，卻沒有檢查「這一張工單是不是你的」。它在 OWASP API Top 10 排第一，而且最常出現在後來才加、沒人回頭檢查的模組，正好是你的業務模組。

learn 的驗收測試準備好了一個打它的工具，叫探針：你寫給驗收測試的一筆設定，告訴它「怎麼建立一筆資料」與「這筆資料的網址」，測試就自己開租戶、開帳號，用不同租戶、不同角色去打那個網址。在 work/portfolio.json 登記你的業務端點：

"bolaProbes": [
  { "name": "工單", "create": { "path": "/api/v1/tickets", "body": { "title": "測試" } },
    "item": "/api/v1/tickets/:id", "update": { "body": { "title": "改" } } },
  { "name": "預約資源", "create": { "path": "/api/v1/resources", "body": { "name": "會議室 A" } },
    "item": "/api/v1/resources/:id", "update": { "body": { "name": "會議室 B" } } }
]
  • create：建立一筆的 POST 路徑與 body，回應要是 201 且有 id。
  • item：單筆的網址，:id 會換成剛建立的 id。
  • update：PATCH 時送的 body。

測試每次都開全新的租戶，所以 create 必須不靠任何既有資料就能成功。拿工單來說，POST /api/v1/tickets 只要一個標題就能建立，符合這個條件。

每個探針，測試都這樣打：

  1. 開兩個新租戶 A、B；A 邀請一位 member、一位 viewer。
  2. A 的 member 用 create 建立一筆，拿到 id。
  3. B 的 owner 對 item 送 GET、PATCH、DELETE：都要 404（不是 403：403 等於告訴對方「這個 id 存在」）。
  4. A 的 viewer 送 PATCH、DELETE：要 403（權限矩陣：viewer 只能讀）。
  5. 沒登入 GET：401。
  6. A 的 member 前後各 GET 一次：200，確認探針本身是有效的，而且 B 的 PATCH、DELETE 沒有真的改到、刪到。

這幾步各自在測不同的事：

  • B 的 owner 拿 404：這是 BOLA 本身。用 owner 是故意的，它是 B 租戶權限最大的角色；如果最大的角色都碰不到 A 的資料，比它小的角色更碰不到。回 404 而不是 403，是因為 403 的意思是「東西在，但你不能看」，攻擊者就能用它一個一個試 id，確認哪些存在。404 讓「別人的」與「不存在的」看起來一模一樣。
  • A 的 viewer 拿 403：這是同一家公司內部的權限，屬於威脅模型裡的「權限提升」。viewer 知道這張工單存在（它本來就讀得到），所以這裡回 403 不洩漏任何東西。
  • 沒登入拿 401：確認端點有被全域 guard 保護，沒有被誤標成公開。
  • A 的 member 前後都拿 200：這一步保護的是測試本身。如果 item 路徑寫錯了，B 打下去也會是 404，測試就會「假通過」；先確認 A 自己讀得到，B 的 404 才有意義。最後再讀一次，則是確認 B 的 PATCH、DELETE 沒有在回 404 的同時偷偷生效。

探針只看 HTTP 回應，不看你的程式長什麼樣，所以它不管漏洞藏在哪裡都抓得到。那麼，當探針真的打出一個 200，漏洞通常長什麼樣子？

探針打出 200 時，漏洞通常長什麼樣？

你的工單模組課程看不到，所以先用參考實作裡同樣形狀的 tags 模組，示範探針抓到的漏洞長什麼樣；看完再回到工單。參考實作登記了 projects 與 tags 兩個探針。tags 是專門為這一課加的第二個業務模組，跟 projects 同一套寫法：service 只用 TenantDb、權限用 @Permissions('tags:write')。這課準備的錯誤寫法之一，就是在 tags 的 service 裡「為了效能」開一條另外的連線讀單筆。理由聽起來很合理：每個查詢都要開交易、設定租戶，單筆讀取好像不需要這麼麻煩：

// 錯誤：讀單筆用一條「不受 RLS 限制」的連線，省掉每個查詢的交易
const raw = new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })

async get(id: string) {
  const t = await raw.tag.findUnique({ where: { id } })   // 沒有租戶條件，也沒有 RLS
  …
}

這幾行同時繞過了兩道防線：

  • 第一道（extension）：raw 是自己 new 出來的 PrismaClient，沒有掛第 8 課的 extension，所以查詢不會被自動加上 tenantId。where 裡只有 id，任何租戶的 tag 都查得到。
  • 第二道（RLS）：DATABASE_URL 是 migration 用的帳號，由 compose 的 POSTGRES_USER 建立，是 superuser。RLS 對 superuser 無效，所以資料庫也不擋。第 9 課讓 API 改用 pf_app 連線，就是為了讓 RLS 生效；這條連線把那個安排抵銷了。

麻煩的是，這段程式看起來很正常：型別對、測試（如果只測自己租戶）會過、code review 很容易放過。但 B 的 owner GET 這張 tag，會拿到 200 和 A 的資料。探針就是為這種程式寫的：它不看你怎麼寫，只看結果。

回到你的工單模組，探針打出 200 時，先查的就是這一類問題：這個模組的查詢有沒有走 TenantDb，還是用了另開的 PrismaClient、直接注入的 PrismaService、或 extension 管不到的 $queryRaw；連線用的是不是不受 RLS 限制的帳號。只有一個模組漏、其他模組都是 404 時，通常不是防線本身壞了，而是這個模組沒走進去。

探針解決了「現在有沒有漏」。但它只在 learn 的驗收測試裡跑，你的 repo 下個月加一個新端點時，誰來打它？

探針只在 learn 裡，自己的 repo 怎麼一直保有這個保護？

你自己的 repo 也要有同樣的保護，而且要跟著程式一起長：每加一個有 :id 的端點，就多一個跨租戶測試。參考實作的 test/tenant-isolation.e2e-spec.ts 用一張表列出每個有 :id 的資源，迴圈產生測試：

// test/tenant-isolation.e2e-spec.ts（節錄）
const ENDPOINTS = [
  { create: '/api/v1/projects', item: '/api/v1/projects/:id', body: { name: 'p' } },
  { create: '/api/v1/tags', item: '/api/v1/tags/:id', body: { name: 't' } },
  // 每加一個有 :id 的端點，就在這裡加一列
]

describe('別的租戶的資料一律 404', () => {
  for (const e of ENDPOINTS) {
    it(e.item, async () => {
      const a = await signup(), b = await signup()
      const { body } = await http().post(e.create).set(a).send(e.body).expect(201)
      const path = e.item.replace(':id', body.id)
      await http().get(path).set(b).expect(404)
      await http().patch(path).set(b).send(e.body).expect(404)
      await http().delete(path).set(b).expect(404)
      await http().get(path).set(a).expect(200)
    })
  }
})

寫成一張表，是為了讓「加一個端點」與「加一個測試」變成同一個動作：新增端點的人只要在 ENDPOINTS 多寫一行，不用重新想一遍測試怎麼寫。表格的好處還有一個：review 時一眼就看得出哪個端點沒有在表裡。把規則寫進 PR 範本：「新增有 :id 的端點，ENDPOINTS 加了一列嗎？」。

這個測試一定要放在 E2E 這一層：真的 HTTP、真的 guard、真的資料庫。如果寫成 service 的單元測試，會 mock 掉資料庫，測到的只是「service 呼叫 Prisma 的方式」；上一節的漏洞恰好是查詢走了另一條連線，mock 根本不會經過那條連線，測試照樣綠。BOLA 問的是「實際送到資料庫的查詢有沒有租戶條件」，只有真的打到資料庫才答得出來。

表格也補上探針做不到的事。探針每次都開全新的租戶，所以只能描述「不靠既有資料就能建立」的資源。工單留言這種要先有一張工單的巢狀資源，路徑裡寫死的工單 id 屬於你開發時的租戶，新租戶去建立只會得到 404；這種探針表達不了，就在自己 repo 的 E2E 寫：先在 A 建工單、再在那張工單下建留言，最後讓 B 去讀。

💡 實務上：掃描工具抓不到 BOLA
SAST（掃程式碼）看不懂「這個查詢應該要有租戶條件」；DAST（從外面打）只有一個帳號時，打不出「用 B 的身分讀 A 的資料」。所以兩種掃描都是綠的，BOLA 照樣在。抓得到它的是知道業務規則的測試：兩個租戶、互相讀寫。這也是面試時很好的一句話：「我的 CI 裡每個資源都有跨租戶測試，新端點沒加測試的 PR 會被 review 擋下」。

拿不到別人的資料，能不能改掉自己不該改的欄位？

到這裡，工單模組已經證明「拿不到別家公司的那一筆」。但威脅模型的第二名威脅「權限提升」還沒查：攻擊者不碰別人的資料，只改自己這一筆，卻改了一個他不該改的欄位，例如把自己的角色改成 owner。這種漏洞叫 mass assignment，OWASP 把它歸在 API3（物件屬性層級的授權）。BOLA 是「拿到不該拿的那一筆」，mass assignment 是「改了不該改的那個欄位」。

它的成因通常是把 body 整包寫進資料庫。前端的個人資料頁只送 name，但 HTTP 請求是使用者可以自己組的，他用 DevTools 或 curl 多送一個 role: "owner"，如果 service 寫成 update({ data: body })，這個欄位就真的寫進去了。這就是威脅模型裡「瀏覽器 → API」那條信任邊界：body 裡的每一個欄位都可能被改過。

參考實作用兩層擋：

  • DTO 只列出可以改的欄位，全域的 ValidationPipe 開 whitelist＋forbidNonWhitelisted（第 2 課）：多送的欄位直接 400。UpdateMeDto 只有 name，送 role 就被拒絕。
  • 敏感的值只來自伺服器：租戶來自 token、角色來自 membership 或邀請、方案只有 owner 能透過 /billing/plan 改。就算哪天 DTO 多了一個欄位，service 也不會拿 body 的值寫這些欄位。

第一層擋的是「不在名單上的欄位」，第二層擋的是「名單本身被加錯」。為什麼需要第二層？因為第一層的名單是人在維護的，而第二層最容易在「方便前端」時被破壞。這課的另一個錯誤寫法：

// members.dto.ts：讓前端在接受邀請的頁面也可以選角色
export class AcceptInvitationDto {
  @IsString() @Length(1, 200) token: string
  @IsOptional() @IsString() @Length(1, 100) name?: string
  @IsOptional() @IsString() @Length(8, 128) password?: string
  @IsOptional() @IsIn(ROLES) role?: Role
}

// invitations.service.ts
create: { tenantId, userId: user.id, role: dto.role ?? inv.role }

欄位有驗證、型別也對，whitelist 擋不住它，因為它就在白名單裡。被邀請成 viewer 的人送 role: "owner"，就成了 owner。更麻煩的是回應還寫著 role: inv.role（viewer），只看回應的測試會被騙過；所以練習 2 是登入之後看 /me 的角色，檢查的是伺服器真正存下來的狀態。

原則：授權相關的值，一律從伺服器存的資料來（這裡是邀請上記的角色），不從 body 來。檢查你的工單模組時也照這條看：工單的 tenantId、建立者、狀態這類決定「誰能做什麼」的欄位，service 有沒有從 body 拿值。

前兩種漏洞都在業務邏輯裡，要靠測試打出來。但有一類漏洞跟你寫的業務程式無關，只要一行設定沒寫對，所有端點同時受影響。

業務邏輯守住了，設定會不會開後門？

這一類 OWASP 叫 API8（安全設定錯誤）：程式本身沒寫錯，但框架、伺服器的設定讓攻擊者有機可乘。它們在這個專案裡集中在一個地方，configureApp()（src/app.setup.ts），每個請求進來都會先經過這幾行：

app.use(requestId.use.bind(requestId))
app.use(helmet())                                   // 安全標頭；放在 body parser 之前，被它拒絕的回應也有
express.useBodyParser('json', { limit: '1mb' })     // 超過回 413
app.use(cookieParser())
app.enableCors({ origin: config.get('CORS_ORIGINS', { infer: true }), credentials: true })

下面看其中跟資安直接相關的三項：helmet、body 上限、CORS，再加上一項不在這段程式裡、但同屬設定層的錯誤訊息。

安全標頭：叫瀏覽器幫你擋

有些攻擊不是打你的 API，而是利用瀏覽器的預設行為，例如把你的頁面嵌進別人網站的 iframe，騙使用者在看不見的按鈕上點擊（clickjacking）。伺服器能做的，是在回應裡加上安全標頭，告訴瀏覽器「這份回應不要這樣用」。helmet 是一個 Express 中介軟體，一行就加上一組常用的安全標頭：

  • X-Content-Type-Options: nosniff：瀏覽器不要自己猜內容類型，照 Content-Type 處理，避免一份 JSON 被當成腳本或 HTML 執行。
  • X-Frame-Options 與 CSP 的 frame-ancestors：不准別的網站把你的回應嵌進 iframe，擋 clickjacking。
  • Strict-Transport-Security：瀏覽器記住「這個網域只用 HTTPS 連」。
  • 拿掉 X-Powered-By：Express 預設會在回應裡寫出自己的名字，攻擊者就知道該找哪個框架的已知漏洞。

順序很重要。第 16 課把 helmet 與 requestId 移到 body parser 之前，因為 body parser 遇到壞掉的 JSON 會直接回 400，排在它後面的中介軟體根本不會執行；放在前面，連這種被拒絕的回應也有安全標頭與 requestId。練習 3 會同時檢查一般回應與壞掉 JSON 的 400。這個版本的 helmet 預設加了哪些標頭，整理在課末。

CORS：只讓你的前端讀回應

瀏覽器有同源政策：A 網站的 JavaScript 不能讀 B 網站 API 的回應，除非 B 在回應裡用 Access-Control-Allow-Origin 明確允許 A。這就是 CORS。請求帶 cookie 時（這個 SaaS 的 refresh token 就在 cookie 裡），伺服器還要回 Access-Control-Allow-Credentials: true，瀏覽器才會把回應交給 JavaScript；而且這時 Access-Control-Allow-Origin 必須是確切的網址，不能是 *。

參考實作用白名單：CORS_ORIGINS 是逗號分隔的前端網址，由第 6 課的 zod 設定驗證。最常見的錯誤是開發時嫌麻煩寫成 origin: true：它把請求的 Origin 原樣回傳，等於「誰問就允許誰」。配上 credentials: true，瀏覽器對 * 的那道限制就被繞過了：任何網站的 JavaScript 都能帶著使用者的 cookie 呼叫你的 API、讀回應。使用者只要在登入狀態下打開一個惡意網頁，那個網頁就能以他的身分讀他公司的資料。

CORS 是瀏覽器端的保護，所以測試要看兩種請求：一般請求，以及瀏覽器在送非簡單請求（例如帶 JSON 的 PATCH）之前先送的 OPTIONS 預檢。不在白名單的 Origin，兩種都不能拿到 Access-Control-Allow-Origin（練習 3）；在白名單的，兩個標頭都要有（自評清單）。

body 上限：一個請求不能吃光記憶體

JSON body 要整個讀進記憶體才能解析。沒有上限（或為了方便設成 50 MB），攻擊者送幾個大請求就能吃光記憶體，所有租戶一起停擺，這是威脅模型的第三名「一個租戶把服務拖垮」，OWASP 歸在 API4（資源無上限）。參考實作把 JSON 限制在 1 MB，超過回 413。上傳檔案是另一條路：它走 multipart，第 12 課另外限制 5 MB，所以不需要為了上傳把 JSON 的上限調大。

錯誤訊息：不要把內部細節送給攻擊者

第 16 課處理了 500 的回應，但 4xx 也會洩漏。例子：註冊時 email 重複，把 Prisma 例外的 e.message 當成 message 回傳，回應就會出現「Invalid `prisma.user.create()` invocation … Unique constraint failed on the fields: (`email`)」，攻擊者知道了你用 Prisma、資料表叫 users。單看不嚴重，但這些資訊會幫他縮小下一步要試的範圍。做法很簡單：message 一律自己寫給人看的句子，原始例外只進 log。

到這裡，威脅模型的三個威脅都查過了。但「我想得到的都查了」不等於「該查的都查了」，還需要一份外部的清單來對照。

還有沒有漏掉的？用 OWASP API Top 10 逐項對照

威脅模型是從你的系統出發往外想，難免有盲點。OWASP API Top 10（2023）是反方向：業界整理出 API 最常出事的十類問題。拿它逐項問「我的作品怎麼擋、證據在哪」，就能找出威脅模型沒想到的地方。每一項都要指到作品裡的測試或 ADR，只寫「有處理」不算。這張表也放進 docs/threat-model.md：

表裡有些項目的證據是「以後要回來看」，例如 API7、API10。這是誠實的寫法：審查的結論不一定是「全部擋住了」，也可以是「目前沒有這個入口，加的時候要做什麼」。面試官看到這種註記，知道你清楚系統的邊界在哪。

依賴掃描（npm audit）與映像掃描（trivy）在第 17 課的 CI 裡；它們找的是「已知漏洞的套件版本」，跟上面這張表互補，不能取代它。這張表找的是你自己的程式與設定的問題，掃描工具不知道你的業務規則。

對照完，你手上多半會有幾個「這裡不對」。最後要決定的是：找到的問題怎麼處理，才算這次審查真的完成。

找到的問題怎麼處理，才算審查完成？

檢查一定會找到東西（寫這門課時，參考實作就被找到「壞掉的 JSON 沒有 requestId 與安全標頭」「cookie 的 security scheme 名字對不上」）。默默改掉是最差的處理方式：沒有人知道問題存在過，也沒有東西防止它再出現。在你的 repo 照這個順序做：

  1. 開 issue：標題寫現象（「業務模組 X 的 GET /:id 可讀到別的租戶」），內容寫怎麼重現、影響範圍（哪些資料、從什麼時候開始）、嚴重度。
  2. 先寫會失敗的測試：在 ENDPOINTS 加一列，CI 變紅。
  3. 修補的 commit 連到 issue（Fixes #12），CI 變綠。
  4. 修法如果改變了設計，寫一份 ADR。

第 2 步是整個流程的核心。先讓測試變紅，證明這個測試真的抓得到這個漏洞；修完變綠，證明修好了；之後它一直留在 CI 裡，誰再寫出同樣的程式都會被擋下。少了這一步，「修好了」只是一句話。

時間只夠修一個的時候，排序看影響 × 可能性（auth 課第 25 課）：影響是出事時損失多大，可能性是攻擊者要多少門檻才做得到。跨租戶讀取影響所有客戶，而且只要一個帳號、改一個 id 就能做到，兩項都高，永遠排在「錯誤訊息透露框架名稱」前面。作品裡留著這幾個 issue 與 commit，面試官點進去就看得到你的判斷過程。

💡 實務上：資安發現的溝通
工作上找到跨租戶漏洞，不是默默修掉就好。先確認影響範圍（log 裡有沒有人真的這樣讀過，第 16 課的 tenantId 欄位這時就派上用場）、通知主管與資安窗口，再決定要不要通知客戶。修補的 PR 描述寫清楚「為什麼這是漏洞、怎麼確認修好了」，但公開的 repo 不要寫出可以直接照抄的攻擊步驟，直到確定所有環境都修好。

你的題目還有哪些探針打不到的地方？

前面用工單示範的都是最標準的形狀：探針格式只描述「JSON body 建立、:id 讀寫刪」這種資源。每個題目都還有一些端點不是這個形狀，卻一樣會跨租戶洩漏。三個題目各有探針表達不了、要自己在 E2E 補的地方：

題目探針之外要補的跨租戶測試
客服工單「指派給成員」：A 的工單指派給 B 租戶的 userId，要被拒絕（第 8 課提過 user 是全域的，外鍵擋不住）。附件走 multipart，探針表達不了，在 E2E 寫。
預約排程「查空檔」這類不是 :id 的端點：A 查詢資源的空檔，不能看到 B 的預約佔用的時段（看到時段被佔，也洩漏了 B 的營運資訊）。
進銷存報表用 $queryRaw（extension 管不到）：建立 A、B 各自的異動，A 的月報加總不能包含 B 的數字。出庫時參照 B 的品項 id，要 404 不是 409。

這三種的共同點是：洩漏不是發生在「讀某一筆」，而是發生在「引用了別人的 id」「彙總時混進別人的資料」「用不同的查詢方式」。找它們的方法跟這課一樣，先問「這個端點的查詢有沒有走進防線」，再寫兩個租戶互相打的測試。

練習

練習 1：在 work/portfolio.json 的 saas.bolaProbes 登記至少 2 個你的業務模組端點。每個探針：A 的 member 建立後，B 的 owner GET／PATCH／DELETE 都 404、A 的 viewer PATCH／DELETE 都 403、沒登入 401、A 的 member 前後都讀得到。

練習 2：mass assignment：member 對 PATCH /me 送 role、tenantId、isPlatformAdmin，owner 對 PATCH /members/:userId 送 tenantId，POST /projects 送 plan、tenantId：被拒絕或被忽略，角色、租戶、方案都沒變。被邀請成 viewer 的人接受邀請時送 role: "owner"，登入後仍是 viewer。

練習 3：一般回應與壞掉 JSON 的 400 都有 X-Content-Type-Options: nosniff、防 iframe 的標頭（X-Frame-Options 或 CSP 的 frame-ancestors），沒有 X-Powered-By；設定以外的 Origin 在一般請求與預檢都拿不到 Access-Control-Allow-Origin；超過 1 MB 的 JSON 回 413 PAYLOAD_TOO_LARGE。

練習 4：404（id 格式不對、不存在）、400（驗證失敗）、409（email 已註冊）的回應不含 Prisma、stack、資料表或約束名稱。

練習 5：你的作品開了 RLS，CI 的 SAST 也是零個發現。BOLA 探針卻顯示：B 的 owner 讀「工單匯出紀錄」GET /api/v1/ticket-exports/:id 得到 200。其他探針都是 404。最先查什麼？

✓ 只有一個模組漏，其他都 404，代表防線本身是好的，問題是這個模組沒走進防線：沒有 extension 的 client 不會加租戶條件，superuser 或擁有者（沒有 FORCE 時）的連線不受 RLS 限制。a 是最多人會先懷疑的，但 policy 錯的話其他模組也會漏；c 錯在 SAST 不知道你的授權規則；d 的話 A 的 member 也會讀不到，探針會先在「確認有效」那一步失敗。（第 18 課）

練習 6：你的業務模組新增了 GET /api/v1/tickets/:id/history。跨租戶測試應該加在哪裡？

✓ BOLA 測試要經過真的 HTTP、guard 與資料庫，才測得到「查詢實際上有沒有租戶條件」，所以放在 E2E，每個新端點一列。a 的 mock 只驗證你呼叫的方式，history 可能是另一個查詢、甚至是 $queryRaw；b 是最常見的假設，新路由常常是不同的查詢；c 的探針只在 learn 的驗收裡，你的 CI 跑不到。（第 18 課）

練習 7：資安檢查找到三個問題，這週只夠修一個：(1) 錯誤回應的 message 透露了 Prisma 的錯誤原文；(2) 業務模組的匯出端點，用別的租戶的 id 可以下載 CSV；(3) /docs 在正式環境是開著的。先修哪個？

✓ 排序看影響 × 可能性：(2) 是正在發生的跨租戶資料外洩，利用門檻只是一個帳號。(1) 是要修的，但它是輔助資訊；(3) 藏起文件不會讓 (2) 消失（c 是「藏起來就安全」的想法）。修完 (2) 之後還要查 log，確認有沒有人真的這樣讀過。（第 18 課）

自評清單

  • 威脅模型在 repo 裡：docs/threat-model.md 有資產、入口、信任邊界、前三名的威脅，以及 OWASP API Top 10 的對照表，每一項指到測試或 ADR。
  • 每個 :id 都有跨租戶測試：grep -rn "@Get(':id\|@Patch(':\|@Delete(':" src 列出的每一個路由，ENDPOINTS 裡都有對應的一列。
  • 故意改壞會被抓到：把業務模組 service 的某個查詢改成用 PrismaService 直接查，npm test 至少一個跨租戶測試失敗；改回來。
  • 沒有繞過 TenantDb 的地方：grep -rn "PrismaService\|new PrismaClient\|\$queryRaw" src 列出的每一處，你都說得出為什麼可以（健康檢查、登入前的流程），或已經自己加了租戶條件。
  • CORS 的正向也對：從你設定的前端網址（例如 http://localhost:5173）發請求，有 Access-Control-Allow-Origin 與 Access-Control-Allow-Credentials: true。
  • 至少一個「找到並修了」：repo 裡有一個資安 issue 與連到它的修補 commit。

常見錯誤

  • 為了效能或報表另開一條連線：沒有 extension、可能也不受 RLS 限制，兩道防線一起被繞過。需要不同的查詢方式時，仍然走 TenantDb，或自己加租戶條件並寫測試。
  • 別的租戶回 403：等於告訴對方「這個 id 存在」。一律 404。
  • 授權相關的欄位放進 DTO：role、tenantId、plan 在白名單裡，whitelist 就擋不住。這些值只從 token、membership、邀請這類伺服器的資料來。
  • origin: true：把任何網站的 Origin 原樣允許，配上 credentials: true 更危險。用設定裡的白名單。
  • body 上限開很大：為了上傳把 JSON 上限調到 50 MB。檔案走 multipart 另外限制，JSON 維持小的上限。
  • 把例外的 message 原樣回傳：Prisma 的訊息含資料表、欄位、約束名稱。message 自己寫。
  • 只靠掃描工具：SAST、DAST、依賴掃描都抓不到 BOLA。

補充與查表

主線用不到、但調整設定時會查的細節。查表用，不用背。

helmet 的預設標頭

課程練習用的是 helmet 8.3.0（nestjs/practice/package.json）。它的預設會加上 X-Content-Type-Options: nosniff、X-Frame-Options、CSP（含 frame-ancestors，擋 clickjacking）、Strict-Transport-Security，並拿掉透露框架的 X-Powered-By。升級 helmet 時，對照它的 changelog 確認預設沒有變，練習 3 也會替你檢查這幾個標頭還在。

小結

  • 資安審查從威脅模型開始：資產、入口、信任邊界、威脅；多租戶系統的第一名威脅是跨租戶讀寫，先查它。
  • 防線只保護走進防線的程式。BOLA 探針用另一個租戶、不同角色去打，只看結果：別的租戶 404、viewer 寫入 403、沒登入 401，並先確認自己讀得到，測試才有效。
  • 探針打出 200，先查那個模組是不是繞過了 TenantDb（另開的 client、PrismaService、$queryRaw）或用了不受 RLS 限制的帳號。
  • 自己的 repo 用 E2E 的 ENDPOINTS 表保護：每個 :id 端點一列，寫進 PR 範本；單元測試 mock 掉資料庫，測不到 BOLA。
  • mass assignment：DTO 白名單擋多餘欄位；授權相關的值只來自伺服器的資料，不來自 body。
  • 設定的防線在 configureApp()：helmet 與 requestId 在 body parser 之前、CORS 白名單、JSON 1 MB、錯誤 message 自己寫。
  • OWASP API Top 10 逐項對照到測試或 ADR；找到的問題寫成 issue、先寫失敗的測試、再修，排序看影響 × 可能性。
