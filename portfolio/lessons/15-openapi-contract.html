階段 B3：上線與作品 · 第 15 課

OpenAPI：把契約交給前端

到第 14 課為止，你的 SaaS 已經有二十幾個端點，契約寫在 CONTRACT-saas.md 這份給人讀的表格裡。現在前端同事要開始寫 Vue 後台的「建立 project」頁面（三個月後，這個同事也可能就是你自己），他傳來三個問題：

  1. 送出表單時 body 要放哪些欄位？哪些必填、長度限制多少？
  2. 按下「建立」之後可能失敗成什麼樣子？403 要顯示「沒有權限」還是「方案上限」？
  3. 這個請求要帶哪種 token？token 過期時打 /auth/refresh 又要帶什麼？

表格回答得了，但只能給人看：前端還是要自己把欄位抄成 TypeScript 型別，你哪天把欄位改名，他的畫面就默默變成 undefined，直到有人回報才發現。這一課的任務是讓你的 API 自己回答這三個問題，而且答案從程式產生、機器讀得懂：在 repo 打開 /openapi.json 與 /docs，前端可以直接產生型別、在網頁上按按鈕試打；最後把「契約有沒有被改壞」放進 CI，讓這份答案不會在下一個 PR 悄悄變掉。面試官打開你的 demo 網址，/docs 常常是他第一個看的頁面。

這課會用到：
  • NestJS 課第 23 課的 @nestjs/swagger：CLI 外掛只在 nest build 時替 .dto.ts 的類別補上文件、applyDecorators 把錯誤回應包成一個裝飾器、哪些修改會弄壞客戶端。
  • API 風格課第 10 課的契約演進：新增可以、刪除與改名要先 deprecate；把「契約有沒有被改壞」交給 CI 檢查。
  • 第 6 課定下的錯誤格式 { statusCode, errorCode, message, requestId }，與第 7 課的兩種憑證：Bearer access token、放在 cookie 的 refresh token。
判分照舊：先啟動你的 API，在 learn 資料夾執行 node check.mjs nestjs pf15。測試讀你的 /openapi.json，只看契約有沒有寫進文件，不管你用外掛還是手寫 @ApiProperty。

這課的路線：

  • OpenAPI 文件長什麼樣；第一個問題（送什麼）：打開 /openapi.json，讓 DTO 自動變成文件，再看外掛管不到的地方。
  • 第二個問題（會失敗成什麼）：一個共用的 ErrorResponse、一個 @ApiErrors()。
  • 第三個問題（帶什麼 token）：Bearer 與 refresh cookie 兩種 security scheme，名稱要對得上。
  • 交給前端：產生型別，以及文件公開出去時裡面不能有什麼。
  • 守住答案：在 CI 抓出契約被改壞，再把同樣的規則套到你的業務模組。

機器讀得懂的契約長什麼樣？

先把要做出來的東西講清楚。OpenAPI 是描述 HTTP API 的標準格式：一份 JSON（或 YAML）文件，寫出這個 API 有哪些路徑、每個路徑接受哪些方法、請求要送什麼、回應會長什麼樣、要帶什麼憑證。因為格式是標準的，同一份文件可以交給很多工具：Swagger UI 把它畫成可以按按鈕試打的網頁，openapi-typescript 這類工具把它轉成 TypeScript 型別，CI 可以拿新舊兩份比對差異。你在後端寫一次，前端、測試、資安審查都讀同一份。

前端同事的三個問題，剛好對到文件的三塊。下面是建立 project 這個端點在文件裡的骨架（簡化過，省略了一些欄位，箭頭是註記），先看結構就好，每一塊後面各有一節：

{
  "openapi": "3.0.0",
  "paths": {
    "/api/v1/projects": {
      "post": {
        "requestBody": { … "$ref": "#/components/schemas/CreateProjectDto" },   ← 問題 1：送什麼
        "responses": {
          "403": { … "$ref": "#/components/schemas/ErrorResponse" }             ← 問題 2：會失敗成什麼
        },
        "security": [{ "bearer": [] }]                                          ← 問題 3：帶什麼 token
      }
    }
  },
  "components": {
    "schemas": { "CreateProjectDto": { … }, "ErrorResponse": { … } },
    "securitySchemes": { "bearer": { … } }
  }
}

兩個地方先記住。第一，paths 底下每個「路徑＋方法」叫一個 operation，它不直接寫欄位，而是用 $ref 指到 components 裡有名字的定義；同一個 ErrorResponse 被一百個端點引用，只要定義一次。第二，引用靠的是名字：security 裡寫的 bearer 必須在 securitySchemes 裡找得到，找不到時文件照樣產生，但工具會不知道它是什麼。這兩點後面都會回來。

這份 JSON 你不會手寫。NestJS 的 @nestjs/swagger 掃描 controller 與 DTO，把它產生出來。問題是：要怎麼讓它掃到正確的東西，而且不用把每個欄位再寫一遍？

問題 1「要送什麼」：怎麼讓 DTO 自動變成文件？

先讓文件出現。NestJS 課第 23 課教過 SwaggerModule；在作品裡它放在第 3 課就開始共用的 configureApp()（src/app.setup.ts），E2E 測試與正式啟動用同一份設定，兩邊的文件才會一樣：

// src/app.setup.ts（節錄）
const doc = new DocumentBuilder().setTitle('My SaaS API').setVersion('1.0')
  .addBearerAuth().addCookieAuth('refresh_token', { type: 'apiKey' }, 'refresh_token').build()
SwaggerModule.setup('docs', app, () => SwaggerModule.createDocument(app, doc), { jsonDocumentUrl: 'openapi.json' })

逐行看：

  • DocumentBuilder 寫的是整份文件共用的部分：標題、版本，以及上一節骨架裡 securitySchemes 的那兩種憑證（addBearerAuth、addCookieAuth，第三個問題那一節會解釋為什麼參數這樣給）。
  • SwaggerModule.setup('docs', …) 開出兩個路徑：/docs 是 Swagger UI 網頁，/openapi.json（jsonDocumentUrl）是給工具讀的 JSON。這兩個路徑不受 setGlobalPrefix('api/v1') 影響（SwaggerModule.setup 預設不套前綴），跟 /health/* 一樣放在根目錄，CONTRACT-saas.md 開頭的共通規則（OpenAPI /openapi.json、/docs 不加前綴）也是這樣寫的。
  • 第三個參數傳的是函式，不是文件本身：文件在第一次被請求時才產生，啟動不用等它掃完所有 controller。

文件出現了，但前端的第一個問題是「欄位有哪些、哪些必填」。最直接的做法是每個欄位寫一個 @ApiProperty，可是 DTO 上已經有 class-validator 的 @IsString()、@Length(1, 100) 了，同一條規則寫兩次，遲早有一邊忘了改。所以參考實作在 nest-cli.json 開了 CLI 外掛：nest build 編譯時，它讀 TypeScript 型別與 class-validator 的裝飾器，替 .dto.ts 結尾的類別補上文件。

// nest-cli.json
{ "compilerOptions": { "deleteOutDir": true, "plugins": ["@nestjs/swagger"] } }

// src/projects/projects.dto.ts：沒有任何 @ApiProperty
export class CreateProjectDto {
  @IsString() @Length(1, 100) name: string
  @IsOptional() @IsString() @Length(0, 2000) description?: string
}

nest build 之後打開 /openapi.json，看 components.schemas 裡的 CreateProjectDto：

// /openapi.json 裡的 CreateProjectDto（nest build 之後）
{ "type": "object",
  "properties": { "name": { "type": "string", "minLength": 1, "maxLength": 100 },
                  "description": { "type": "string", "minLength": 0, "maxLength": 2000 } },
  "required": ["name"] }

對照兩段：沒有問號的 name 進了 required，@Length 變成 minLength／maxLength。前端同事的第一個問題就這樣回答了：name 必填、1 到 100 字，description 選填、最多 2000 字。更重要的是，驗證規則與文件現在寫在同一個地方：產品說名稱上限改成 50 字，你改 @Length(1, 50)，API 擋人的規則和文件寫的數字一起變。這就是「DTO 即文件」。

💡 實務上：文件跟程式不同步，比沒有文件更糟
手寫的 API 文件（Notion、Word）幾乎一定會過期：後端改了欄位，沒人記得改文件，前端照文件寫，上線才發現。從程式產生文件之後，「文件對不對」變成「程式對不對」，code review 看的是同一份東西。前端同事問「這個欄位是必填嗎」時，你可以直接丟 /docs 的連結；他照著文件寫出錯，那是後端的 bug，不是溝通的問題。

不過「從程式產生」有個前提：外掛真的有處理到那個 DTO。它是在編譯時動手腳的工具，有它看不到的地方。

外掛在哪裡會漏掉欄位？

外掛不是在執行時讀你的類別，而是在 nest build 把 TypeScript 編譯成 JavaScript 的那一步，挑出特定的檔案，替裡面的類別插入文件用的資訊。這句話直接推出它的兩個邊界，參考實作各踩到一次：

第一個邊界：只處理檔名是 .dto.ts、.entity.ts 的檔案。tags 模組為了示範，把 DTO 跟 controller 寫在同一個 tags.module.ts。外掛看檔名就跳過它，結果文件裡的 TagDto 是空的 { "properties": {} }：路由在、request body 也引用了 TagDto，但前端產生出來的型別裡什麼欄位都沒有。修法有兩個：那個欄位手寫 @ApiProperty({ minLength: 1, maxLength: 50 })，或把 DTO 移到 tags.dto.ts。

第二個邊界：只在 nest build 時有效。Vitest 執行 TypeScript 時不經過 Nest 的 tsc 編譯，外掛沒有機會插手，所以在 E2E 測試裡呼叫 createDocument 產生的文件，所有 DTO 都是空的。路由、@ApiResponse 這些執行時就存在的裝飾器照樣看得到，只有外掛補的欄位不見，這讓錯誤很難察覺：文件「看起來」完整。結論是：「檢查文件」一定要對 nest build 之後的程式跑。這課的驗收測試啟動的是 node dist/main.js，後面 CI 那一節也一樣。

也可以完全不用外掛。NestJS 課第 23 課選的就是另一邊：全部手寫 @ApiProperty，在哪裡執行都一樣，沒有上面兩個邊界，代價是欄位與驗證要寫兩次。作品用哪一邊都可以，把理由寫在 README 的設計決定裡；重點是知道自己選的那一邊的盲點在哪。

到這裡，前端知道成功時要送什麼了。但他寫畫面時，花更多時間處理的是失敗：文件目前對「按下去會失敗成什麼」一個字都沒說。

問題 2「會失敗成什麼」：怎麼把錯誤寫進契約？

DTO 只描述成功的那條路。建立 project 至少有三種失敗：沒登入（401）、沒有 projects:write 權限（403 FORBIDDEN）、免費方案已經有 3 個 project（第 14 課的 403 PLAN_LIMIT_REACHED）。後兩個狀態碼一樣，畫面卻要顯示不同的東西：一個叫使用者找管理員，一個引導他升級方案。前端能分辨它們，靠的是第 6 課定下的 errorCode。文件沒寫，前端只能猜，或是去翻你的 service 程式。

所以錯誤要在文件裡寫出兩件事：形狀（每個錯誤回應都是 { statusCode, errorCode, message, requestId }）與可能的值（這個狀態碼代表哪些 errorCode）。參考實作先把形狀寫成一個只給文件用的類別，再用 applyDecorators（NestJS 課第 23 課）包成一個裝飾器，每個狀態碼對到一句說明：

// src/common/openapi.ts
export class ErrorResponse {
  @ApiProperty({ example: 404 }) statusCode: number
  @ApiProperty({ example: 'NOT_FOUND', description: 'SCREAMING_SNAKE；程式判斷用這個，不要比對 message' }) errorCode: string
  @ApiProperty() message: string
  @ApiProperty({ description: '跟回應標頭 x-request-id 相同' }) requestId: string
}

const DESCRIPTIONS: Record<number, string> = {
  400: '輸入不正確（VALIDATION_FAILED）', 401: '沒有登入或 token 無效', 403: '沒有權限（FORBIDDEN）或已達方案上限（PLAN_LIMIT_REACHED）',
  404: '不存在，或屬於別的租戶（NOT_FOUND）', 409: '跟現有資料衝突', /* … */
}

export const ApiErrors = (...statuses: number[]) =>
  applyDecorators(...statuses.map(status => ApiResponse({ status, description: DESCRIPTIONS[status], type: ErrorResponse })))

ErrorResponse 放在 openapi.ts，不是 .dto.ts，所以外掛不會處理它，欄位一律手寫 @ApiProperty；這正好是上一節的第一個邊界。ApiErrors(401, 403) 展開後就是兩個 @ApiResponse，每個都指向同一個 ErrorResponse，在文件裡變成第一節骨架那種 $ref。

用的時候，整個 controller 都會有的錯誤放在類別上，個別路由才有的放在方法上，兩者會合併：

@ApiTags('projects')
@ApiBearerAuth()
@ApiErrors(401, 403)            // 每個路由：沒登入、沒權限
@Controller('projects')
export class ProjectsController {
  @Permissions('projects:read')
  @Get(':id')
  @ApiErrors(404)               // 有 :id 的才有 404
  get(@Param('id', UUID) id: string) { … }
}

哪個端點該列哪些狀態碼，照這條規則：要登入的端點列 401、有路徑參數的列 404、有 body 的列 400，其他照業務規則加（409、410、413、415）。建立 project 有 body、要登入、會碰到權限與方案上限，所以是 400、401、403。

兩個細節是刻意的。第一，type: ErrorResponse 不能省：省了，文件裡只剩一句說明、沒有 schema，前端產生的型別裡錯誤回應是 unknown，他還是不知道 errorCode 在哪，練習 2 會擋下這種寫法。第二，404 的說明寫「不存在，或屬於別的租戶」：第 8 課讓別的租戶的資料一律回 404，文件照實寫，前端就不會為「403 別人的資料」寫一個永遠不會出現的畫面。

前兩個問題回答了。上面的 controller 還有一行還沒解釋的 @ApiBearerAuth()：它回答的是第三個問題，也是這課最容易「看起來對、其實壞了」的地方。

問題 3「要帶什麼 token」：security scheme 的名字怎麼對上？

這個 SaaS 有兩種憑證（第 7 課）：大部分端點帶 Authorization: Bearer <access token>；/auth/refresh、/auth/logout 不看 access token，只看放在 cookie 的 refresh token。前端要在文件裡看到「哪個端點帶哪一種」，Swagger UI 的 Authorize 按鈕也要知道「輸入的 token 要放到標頭還是 cookie」。

OpenAPI 的做法分兩步，就是第一節說的「靠名字引用」：

  1. 定義：在 components.securitySchemes 寫「有哪幾種憑證、各叫什麼名字、放在哪裡」。Nest 裡由 DocumentBuilder 的 addBearerAuth()、addCookieAuth() 產生。
  2. 引用：每個 operation 的 security 寫它用哪個名字。Nest 裡由 @ApiBearerAuth()、@ApiCookieAuth() 產生。

兩邊各自產生名字，對不對得上要你自己確認：

定義（DocumentBuilder）產生的名字引用（裝飾器）
.addBearerAuth()bearer@ApiBearerAuth()
.addCookieAuth('refresh_token')cookie（第三個參數的預設值）@ApiCookieAuth('refresh_token') 引用的是 refresh_token → 對不上
.addCookieAuth('refresh_token', { type: 'apiKey' }, 'refresh_token')refresh_token@ApiCookieAuth('refresh_token') → 對上了

addCookieAuth 的第一個參數是 cookie 的名字，第三個參數才是 scheme 的名字，不給就是 cookie。第二列是參考實作原本的寫法：文件照樣產生、Swagger UI 照樣打得開，只是 refresh 端點引用了一個不存在的 scheme，於是 Swagger UI 的 Authorize 對它沒作用，產生 client 的工具會報錯或略過。這種錯沒有人會注意到，直到前端產生 SDK 那天。第一節 configureApp() 把第三個參數也給成 refresh_token，就是這個原因。練習 2 會檢查每個被引用的名字都有定義。

名字對上之後，還要確認標記的範圍對。@ApiBearerAuth() 放在 controller 類別上，整個 controller 的路由都有 security。不用登入的路由（signup、login、接受邀請）放在沒有 @ApiBearerAuth() 的 controller，或在方法上不加。

這裡要分清楚：文件的 security 只是說明，它不會擋任何請求，真正擋人的是第 7 課的全域 guard。如果文件說 signup 要登入、guard 卻放行，前端會白白帶 token；反過來，文件說不用登入、guard 卻擋，前端照文件寫就會拿到 401。兩者要說同一件事，所以練習 2 會檢查兩個方向：要登入的都有標、不用登入的沒有標。

💡 實務上：文件是攻擊面盤點的起點
資安審查（第 18 課）的第一步是列出「有哪些端點、哪些不用登入」。從程式產生的 OpenAPI 就是這張清單：把 security 是空的端點挑出來，每一個都要說得出為什麼可以不登入。OWASP API Top 10 的 API9（不當的資產管理）講的就是「你不知道自己有哪些 API」，舊版、測試用、忘了關的端點最常出事。文件跟程式同步，這張清單才可信。

三個問題都寫進文件了。接下來把文件交給前端：他會怎麼用它？而文件一旦交出去，就可能被任何人看到，裡面有沒有不該出現的東西？

交給前端：型別怎麼產生，文件裡不能有什麼？

文件接上了，前端就不用手寫型別。NestJS 課第 23 課示範過 openapi-typescript：它讀 /openapi.json，把 components.schemas 裡的每個定義轉成 TypeScript 型別。在你的 Vue 專案執行（這門課的練習環境沒有安裝它）：

npx openapi-typescript http://localhost:3100/openapi.json -o src/api/schema.d.ts
import type { components } from './api/schema'
type CreateProject = components['schemas']['CreateProjectDto']   // { name: string; description?: string }
type ApiError = components['schemas']['ErrorResponse']           // errorCode 有型別，畫面依它分支

這兩行就是前端同事前兩個問題的答案，以型別的形式出現：表單的型別直接來自 CreateProjectDto，錯誤處理依 ErrorResponse 的 errorCode 分支。後端改了欄位，前端重新產生一次，TypeScript 會在編譯時指出哪裡要改，而不是等畫面出現 undefined。

型別產生出來後，你會發現少了一塊：參考實作目前只把請求與錯誤寫進文件；成功回應（例如 project 的 { id, name, … }）在文件裡只有 "description": ""。原因是 service 回傳的是一般物件，外掛只認得類別，它不知道回傳值長什麼樣。要補的話，為回應寫一個類別（例如 ProjectView，放在 .dto.ts），路由加 @ApiOkResponse({ type: ProjectView })。這是作品 README「已知限制」可以誠實寫的一條：哪些有、哪些還沒有、補的方法是什麼。

型別解決了「前端怎麼用」。另一面是：文件也是會公開的東西。/docs 開在正式環境，等於任何人都拿得到這份清單；不開的話，至少 staging 要有，前端才有得用（要不要開見課末）。不管開不開，文件都會被複製、轉寄、貼進前端的 repo，所以裡面不能有這兩種東西：

  • 內部網址：.addServer('http://api.internal:3100')、description 裡寫的 localhost:5432、內網 IP。它告訴攻擊者你的內網長什麼樣子。servers 不寫時，Swagger UI 用目前的網址，通常就是你要的。
  • 看起來像真的 secret：從開發環境複製來當 example 的 JWT、API key。example 一律用明顯的假值（'NOT_FOUND'、'pf-demo@example.test'）。

這兩種東西最常從「方便」混進來：本機測試時加了 addServer 忘了拿掉，或是想讓範例看起來真實，就貼了一段真的 token。練習 3 會掃描 /openapi.json 的全文找這兩種東西。

現在前端手上的文件是對的、乾淨的。但它只在今天是對的：下個月有人把 description 改名，文件會跟著程式一起變，前端照舊的型別寫的畫面就壞了。「文件跟程式同步」保證了文件不會過期，卻沒有保證契約不會被改壞。

下次有人改壞契約，怎麼在 PR 就看到？

先分清楚兩件事。文件從程式產生，所以「改程式」一定等於「改契約」；問題是改的人常常不知道自己改到了契約。他只是重新命名一個欄位、把一個選填欄位改成必填，覺得是重構。NestJS 課第 23 課列過哪些修改會弄壞客戶端（刪欄位、改名、選填改必填、改型別），API 風格課第 10 課把同樣的檢查放進 CI。我們要的是：改到契約時，PR 裡一定看得見。

作品裡最小的做法是把文件本身 commit 進 repo，當成「目前承諾給前端的契約」，CI 每次產生一份新的跟它比：

作品的 CI workflow 要到第 17 課才建立。這一課先在本機把第 1、2 步跑通，並故意改一個 DTO 欄位，確認第 2 步的 git diff 會失敗；第 17 課寫 workflow 時，再把第 2 步原封不動放在 build 與啟動 API 之後。

# 1. 在本機產生一份，commit 進 repo（docs/openapi.json）
npm run build && node dist/main.js &
curl -s http://localhost:3100/openapi.json | npx prettier --parser json > docs/openapi.json

# 2. CI（第 17 課的 workflow，build 之後、API 啟動之後）：產生一份新的，跟 repo 裡的比
curl -s http://localhost:3100/openapi.json | npx prettier --parser json > openapi.new.json
git diff --no-index --exit-code docs/openapi.json openapi.new.json   # 不一樣就失敗

每一步的用意：

  • 先 npm run build、再跑 node dist/main.js：外掛只在 build 時有效（「外掛在哪裡會漏掉欄位」那一節），從 src/ 產生的文件 DTO 是空的。
  • prettier --parser json 把 JSON 排成固定的多行格式，diff 才會一個欄位一行，看得懂改了什麼。
  • git diff --no-index 比對兩個不在 git 裡的檔案，加上 --exit-code 有差異時結束碼是 1，CI 就會失敗。

效果是：任何改到契約的 PR，都必須同時改 docs/openapi.json，否則 CI 紅燈；reviewer 在 diff 裡直接看到「CreateProjectDto 少了 description」。這一步不判斷「相不相容」，只保證沒有人會不小心改到契約；相不相容由 reviewer 判斷，或再接 oasdiff 這類工具自動判斷（NestJS 課第 23 課提過）。

產生文件要用 nest build 之後的程式，不要在 Vitest 裡呼叫 createDocument 做快照：Vitest 沒有外掛，產生的 DTO 是空的，快照會跟正式環境不一樣。

平台的端點（auth、members、projects、billing）到這裡都照規則寫好、也被 CI 守住了。剩下的是你自己的業務模組：它們有平台沒有的業務規則，文件要特別把這些規則寫出來。

套到你的業務模組：哪些規則要寫進文件？

基本規則照前面做：DTO 放 .dto.ts、controller 加 @ApiBearerAuth() 與 @ApiErrors(401, 403)、有 :id 的路由加 404。除此之外，問自己跟前端同事一樣的問題：「這個按鈕按下去，還可能因為什麼業務規則失敗？」三個題目各有一個文件特別值得寫清楚的地方：

題目文件要寫清楚
客服工單狀態機：status 用 enum（@IsIn(STATUSES)，外掛會變成 enum），不合法的轉換回 409，errorCode 例如 INVALID_TRANSITION，description 寫出允許的轉換。前端產生的型別就是一個字串聯集，按鈕要不要顯示可以直接判斷。
預約排程時段重疊回 409 SLOT_TAKEN；時間欄位寫明是 ISO 8601、含時區。前端最常在時區上出錯，文件寫清楚比事後查 log 便宜。
進銷存庫存不足 409 INSUFFICIENT_STOCK；異動只能新增不能修改，所以文件裡沒有 PATCH /movements/:id，這本身就是在說明規則。報表匯出走第 13 課的 202＋輪詢，文件寫出 status 的四個值。

寫完後回到開場的三個問題，對你的每個業務端點各問一次：送什麼、會失敗成什麼、帶什麼 token，答案都要能從 /docs 直接讀到。下面的練習就是用程式檢查這三件事。

練習

練習 1：在你的專案打開 GET /openapi.json（OpenAPI 3.x，路徑不加 /api/v1）。契約的每個路徑與方法都要在文件裡（路徑參數的名字不限），而且 signup、建立 project、邀請的 request body 有欄位與必填（開 CLI 外掛，或手寫 @ApiProperty）。

練習 2：受保護的端點有 security、signup／login／接受邀請沒有；被引用的 security 名稱都有定義。要登入的端點文件化 401、有路徑參數的文件化 404；所有 4xx 回應都引用同一個錯誤 schema（含 statusCode、errorCode、message、requestId）。

練習 3：/openapi.json 的全文裡沒有內部網址（localhost、127.0.0.1、內網 IP、.internal）與看起來像真的 secret 的值（JWT、sk_live_、AKIA…、私鑰）。

練習 4：你用 CLI 外掛產生文件，又在 Vitest 的 E2E 測試裡寫了「文件快照」：呼叫 SwaggerModule.createDocument，跟 repo 裡的 docs/openapi.json 比。本機與 CI 的測試都過了。這個快照擋得住什麼？

✓ 外掛是 tsc 的轉換步驟，Vitest 不經過 tsc，所以快照裡每個 DTO 都是 { "properties": {} }，欄位怎麼改快照都一樣。路由、@ApiResponse 這些是執行時的裝飾器，照樣看得到（c 錯）。d 錯在 Vitest 跑的是 src/ 的 TypeScript，不會讀 dist/。要對正式的文件做檢查，就對 nest build 之後啟動的 API 抓 /openapi.json。（第 15 課）

練習 5：前端照你的文件產生了型別。下面哪一個修改，前端不改程式也不會壞？

✓ 回應多一個欄位，舊的前端不讀它就好。改名等於刪掉舊欄位，畫面拿到 undefined（a）；選填改必填，舊的前端沒送就被 400 擋下（b）；errorCode 是前端分支用的值，改了它，「找不到時跳回列表」的那段程式就不會執行（c，很多人以為錯誤碼只是給人看的）。不得不改時，先新增、標 deprecated、等前端換掉再刪。（第 15 課）

練習 6：你的 demo 環境把 /docs 開著，方便面試官試打。同事說：「文件把所有端點都列出來了，等於把攻擊地圖送人，關掉比較安全。」比較好的回應是？

✓ 把端點藏起來不是防線：前端的 JavaScript、瀏覽器的網路面板就看得到大部分路徑，攻擊者也會直接猜。真正的防線是 guard、權限與租戶條件；文件要檢查的是它不該帶出去的東西。b 是常見的「藏起來就安全」想法；d 錯在 Swagger UI 可以帶 token 真的送出請求。正式產品要不要開 /docs 是另一個取捨（給外部開發者用的 API 通常會開）。（第 15 課）

自評清單

測試判不出來、但前端同事用了就知道的事。每一項自己確認：

  • Swagger UI 真的打得通：打開 /docs，按 Authorize 貼上 access token，試打 GET /api/v1/projects 得到 200；再試 POST /api/v1/auth/refresh，cookie 的 Authorize 也有作用。
  • 產生型別跑得過：在任何一個資料夾執行上面的 openapi-typescript 指令，沒有錯誤；打開產生的檔案，你的業務模組的 DTO 有欄位，不是 Record<string, never>。
  • 外掛的盲點：執行 grep -rn "class .*Dto" src | grep -v "\.dto\.ts:"，列出不在 .dto.ts 檔裡的 DTO 類別（寫在 controller 或 module 檔裡的）；每一個在文件裡都要有欄位。
  • 契約進了 repo：docs/openapi.json 有 commit；故意把一個 DTO 欄位改名，CI 的比對步驟會失敗。
  • 錯誤碼寫得出來：你的業務模組每個自訂的 errorCode，都出現在某個 description 裡。

常見錯誤

  • DTO 寫在 controller 檔裡，以為外掛會處理：外掛只看 .dto.ts、.entity.ts。移到 .dto.ts，或手寫 @ApiProperty。
  • 錯誤回應只寫 description：ApiResponse({ status: 404, description: '找不到' }) 沒有 type，前端的型別裡錯誤是 unknown。一律 type: ErrorResponse，包成 @ApiErrors() 就不會忘。
  • addCookieAuth 只給第一個參數：定義出來的名字是 cookie，@ApiCookieAuth('refresh_token') 引用不到。第三個參數給同一個名字。
  • 用 include 只放幾個模組：createDocument(app, doc, { include: [...] }) 漏掉的模組在文件裡不存在，前端以為沒有那些 API。要排除的只有健康檢查這類端點，用 @ApiExcludeController()。
  • 在 Vitest 裡做文件快照：沒有外掛，DTO 全是空的，快照什麼都沒保護到。對 nest build 後的 API 產生。
  • example 用真的值：從開發環境複製的 token、內網的網址會跟著文件公開。example 用明顯的假值。

小結

  • 前端的三個問題對到 OpenAPI 的三塊：送什麼是 request body 的 schema、會失敗成什麼是 responses 的錯誤 schema、帶什麼 token 是 security；operation 用名字引用 components 裡的定義。
  • /openapi.json 從程式產生，放在 configureApp()，跟 /health/* 一樣不加 /api/v1。
  • CLI 外掛讓 DTO 即文件，但只處理 .dto.ts、只在 nest build 時有效；檢查文件一律對 build 之後的程式。
  • 錯誤是契約的一半：一個 ErrorResponse、一個 @ApiErrors()；要登入的列 401、有 :id 的列 404。
  • security scheme 定義與引用的名字要對得上；文件的 security 只是說明，擋人的是 guard，兩者要說同一件事。
  • 文件會公開：不放內部網址與像真的 secret。
  • docs/openapi.json commit 進 repo，CI 比對，改到契約的 PR 一定看得見。

下一課處理上線之後的事：使用者回報「剛剛出錯了」，你怎麼從一個 requestId 查到那個請求做了什麼。
