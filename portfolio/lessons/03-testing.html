階段 A：小專案走完一次 · 第 3 課

測試：單元與 E2E

上一課的 API 已經通過 learn 的驗收測試，但那些測試在 learn 裡，不在你的 repo。想像三個月後：同事（或三個月後的你）要調整報名流程，把 service 改寫成「先查剩幾個名額，大於 0 就新增報名」，順手把條件式 UPDATE 裡的 remaining: { gt: 0 } 刪掉了。他自己用 curl 報名一次、取消一次，一切正常，於是 push 上線。開放報名那天，10 個人同時按下「報名」，3 個名額的活動收了 5 筆報名。

這課的任務：讓你的 repo 在這種修改 push 之前就變紅。你要在 repo 裡寫自己的測試，npm test 一個指令跑完；刪掉 remaining: { gt: 0 } 的那一刻，至少有一個測試失敗。這也是面試官打開你的 GitHub 會看的東西：test/ 資料夾有沒有東西、CI 是不是綠的、測試在保護哪些規則。

做完這課，你的 repo 會有 vitest.config.ts、一個測試專用的資料庫設定、游標的單元測試、一份連真的 PostgreSQL 的 E2E 測試（含併發報名），通過練習 1～2：learn 會在你的 repo 執行 npm test，檢查全部通過、沒有 skip、至少 8 個測試、有 E2E。

這課會用到：
  • NestJS 課第 5 課的 Vitest（describe 把測試分組、it 寫一個測試、expect 檢查結果；globals: true 讓它們不用 import）。
  • NestJS 課第 10 課的 Test.createTestingModule＋supertest（在測試裡啟動整個應用程式、不開 port 就能打 HTTP）。
  • NestJS 課第 17 課的整合測試：測試資料庫用 migrate deploy 建表、每個測試前清空。
  • Node 課第 22 課的測試金字塔（單元多、整合少一點、端到端最少）。
這課的驗收測試不打你的 API，而是在你的 repo 執行 npm test。所以開發用資料庫要先開著（docker compose up -d --wait db），API 不用開。判分：在 learn 執行 node check.mjs nestjs pf03。

這課的路線：

  • 要擋住「名額規則被改壞」，該寫哪一種測試：單元測試與 E2E 各負責什麼，為什麼不 mock Prisma。
  • 先寫最簡單的：游標的單元測試，以及怎麼把測試名稱寫成規格。
  • E2E 要連真的資料庫，連哪一個才不會清掉開發資料：_spec 資料庫、globalSetup、每個測試前清空。
  • 在測試裡啟動 API：怎麼確定它跟 main.ts 啟動的是同一個應用程式，檢查要檢查到哪裡。
  • 「10 人同時搶 3 個名額」怎麼測才穩定；最後接成 npm test，親手改壞一次，確認它抓得到開場那個 bug。

要擋住名額規則被改壞，該寫哪一種測試？

先把兩種測試講清楚，後面整課都會用到這兩個名字。

單元測試只呼叫一個函式（或一個類別的方法），給它輸入、檢查它的回傳值或丟出的錯誤。它不啟動 HTTP 伺服器、不連資料庫，所以幾毫秒就跑完，同一個函式可以一口氣列幾十種輸入。代價是它只看得到那個函式本身：函式外面的東西（資料庫怎麼執行 SQL、pipe 有沒有掛上）它都看不到。

E2E（end-to-end，端到端）從最外面打進去：送一個真的 HTTP 請求，讓它經過全域前綴、ValidationPipe、controller、service、Prisma，一路到 PostgreSQL，再檢查回應和資料庫裡的結果。它慢一些（要啟動整個應用程式、要清資料），但它測到的就是使用者會碰到的那條路。

拿開場的 bug 來對照。被刪掉的是 updateMany 的 where 條件 remaining: { gt: 0 }。這條規則是誰在執行？不是你的 JavaScript，而是 PostgreSQL：上一課的條件式 UPDATE 只在剩餘名額大於 0 時才改到那一列，而且同一列的 UPDATE 會排隊，所以 10 個請求同時到也只有 3 個改得到。要判斷這條規則還在不在，就得讓 PostgreSQL 真的執行那句 SQL。單元測試不連資料庫，看不到；能抓到它的只有連真資料庫的 E2E。

這時常有人想到另一條路：mock。mock 是在測試裡用一個假的物件代替真的依賴，例如做一個假的 PrismaService，讓 updateMany 被呼叫時直接回傳 { count: 0 }，就能在不連資料庫的情況下測 service。它測到的是「service 收到 count 0 時會丟 EVENT_FULL」。但這個專案真正會出錯的地方是：where 條件寫錯讓 count 永遠是 1、唯一約束沒建、交易沒包好讓名額沒回滾。mock 全部看不到。拿開場的 bug 來說，where 條件被刪了，假的 updateMany 根本不讀 where，照樣回你設定好的值，測試照樣綠。而且每次改 SQL 都要跟著改 mock，維護成本一直在。NestJS 課第 17 課的結論在這裡一樣成立：有資料庫規則的程式，就連真的資料庫測。

照這個標準看這個專案，程式碼分成兩種：

程式例子用什麼測為什麼
不碰 I/O 的純函式cursor.ts 的編碼與解碼單元測試（src/**/*.spec.ts）輸入輸出就能判斷對錯，幾毫秒跑完，邊界情況（壞掉的游標）可以一次列很多
正確性取決於資料庫的程式名額、重複報名、分頁、錯誤格式E2E（test/**/*.e2e-spec.ts）：HTTP＋真的 PostgreSQL規則是靠唯一約束、條件式 UPDATE、交易擋的；不連資料庫，測到的只是你對資料庫的想像

這個專案的業務規則幾乎都在資料庫裡，所以測試的分布跟 Node 課第 22 課畫的金字塔不太一樣：單元測試少（只有游標），E2E 是主力。這不是做錯了，而是測試要放在「規則實際被執行的地方」。等第 6 課開始的 SaaS 有了更多純邏輯（權限矩陣、方案上限的計算），單元測試才會變多。

結論是：開場的 bug 要靠 E2E 抓。不過 E2E 要準備的東西比較多，先從單元測試開始，順便把整課都會用到的一個習慣定下來：測試名稱怎麼寫。

游標的單元測試要測什麼？

游標是上一課 cursor.ts 做的東西：把上一頁最後一筆的 (startsAt, id) 編成一段 base64url 字串交給前端，前端要下一頁時再帶回來，由 decodeCursor 解開。它只做字串轉換，不碰資料庫也不碰網路，正是單元測試最適合的對象。

要保證的有兩件事。第一，編出去的游標解得回同一個值，不然下一頁會從錯的地方開始。第二，前端送回來的字串不可信：可能被截斷、被手動改過，或者根本是別人亂填的。這些情況都要回上一課定好的 400 VALIDATION_FAILED，而不是讓 JSON.parse 的例外一路衝成 500。參考實作的單元測試就只有這兩個：

// src/events/cursor.spec.ts
import { decodeCursor, encodeCursor } from './cursor.js'

describe('游標', () => {
  it('編碼後解得回同一個 (startsAt, id)', () => {
    const c = { startsAt: new Date('2027-01-01T10:00:00.000Z'), id: '00000000-0000-4000-8000-000000000001' }
    expect(decodeCursor(encodeCursor(c))).toEqual(c)
  })

  it('壞掉的游標是 400 VALIDATION_FAILED，不是 500', () => {
    for (const raw of ['abc', Buffer.from('[1,2]').toString('base64url'), Buffer.from('["x","y"]').toString('base64url')]) {
      expect(() => decodeCursor(raw)).toThrow(expect.objectContaining({ errorCode: 'VALIDATION_FAILED' }))
    }
  })
})

第一個測試是「來回」：編碼後再解碼，用 toEqual 比對整個物件。第二個測試用一個迴圈列出三種壞輸入：'abc' 解開後不是 JSON；[1,2] 是合法 JSON，但元素型別不對；["x","y"] 型別對了，內容卻不是日期與 id。三種分別會在 decodeCursor 的不同地方失敗，一個測試就把每條失敗路徑都走過一次。

注意第二個測試的名稱寫出了 VALIDATION_FAILED 和「不是 500」。測試失敗時，Vitest 印出來的是 describe 加 it 的名稱，所以名稱要寫成規格：讀名稱就知道哪條契約壞了，不用先打開程式碼。「游標測試 2」失敗了，你得去翻程式才知道它在測什麼；「壞掉的游標是 400 VALIDATION_FAILED，不是 500」失敗了，一看就知道前端會開始收到 500。練習 2 會檢查你的測試名稱有沒有涵蓋三種錯誤。

游標測好了，但開場的 bug 不在游標裡。要抓到它，下一步是讓 E2E 連上真的 PostgreSQL，而第一個問題是：連哪一個資料庫？

E2E 要連真的資料庫，連哪一個？

E2E 測試要能重複跑、每次結果一樣，所以每個測試開始時，資料庫都要是空的：上一個測試建的活動如果還在，「列表有幾筆」「剩幾個名額」這類檢查就會跟著上一個測試的結果變動。做法是每個測試前執行 TRUNCATE registrations, events，一次把兩張表的所有資料刪光（下一節會看到它寫在哪裡）。

這就決定了測試不能連開發用的 event_signup：每跑一次 npm test，你手動建來試 API 的活動就會被清掉。測試需要一個自己的資料庫。參考實作在 vitest.config.ts 把資料庫名稱自動加上 _spec：

// vitest.config.ts
import { config } from 'dotenv'
import { defineConfig } from 'vitest/config'

// 測試永遠不碰開發用的資料：資料庫名稱加上 _spec（event_signup → event_signup_spec）
config({ quiet: true })
if (!process.env.DATABASE_URL) throw new Error('沒有 DATABASE_URL：複製 .env.example 成 .env')
const url = new URL(process.env.DATABASE_URL)
url.pathname = url.pathname.replace(/(_test|_spec)?$/, '_spec')
process.env.DATABASE_URL = url.href

export default defineConfig({
  test: {
    globals: true,
    include: ['src/**/*.spec.ts', 'test/**/*.e2e-spec.ts'],
    globalSetup: ['test/support/global-setup.ts'],
    fileParallelism: false,   // 測試檔共用同一個資料庫，一個一個跑
    testTimeout: 20_000,
    hookTimeout: 30_000,
  },
})

這段設定在 Vitest 啟動時、任何測試執行之前就會跑。它讀進 .env 的 DATABASE_URL，把路徑裡的資料庫名稱換成 _spec 結尾（正規表示式先拿掉原本可能有的 _test 或 _spec，所以不會疊成 _spec_spec），再寫回 process.env.DATABASE_URL。改的是環境變數本身，所以之後所有讀它的地方，包括應用程式的 ConfigModule、Prisma CLI、測試程式，全都連到 event_signup_spec，不會有某個角落還連著開發資料庫。

defineConfig 裡的選項，include 同時列了單元測試與 E2E 的檔名規則，最後一節會用到；fileParallelism 在這節最後解釋；其餘的整理在課末「補充與查表」。這裡先看 globalSetup：它指定一個檔案，Vitest 在所有測試檔開始前執行它一次，適合放「整個測試只需要做一次」的準備工作。這個專案用它做三件事：

// test/support/global-setup.ts
import { spawnSync } from 'node:child_process'
import pg from 'pg'

export default async function setup() {
  const url = new URL(process.env.DATABASE_URL ?? '')
  const name = url.pathname.slice(1)
  if (!/^[a-z0-9_]+_spec$/.test(name)) throw new Error(`測試只能用 *_spec 資料庫，現在是「${name}」`)
  const admin = new pg.Client({ connectionString: url.href.replace(`/${name}`, '/postgres') })
  await admin.connect()
  try {
    const { rowCount } = await admin.query('SELECT 1 FROM pg_database WHERE datname = $1', [name])
    if (!rowCount) await admin.query(`CREATE DATABASE "${name}"`)
  } finally {
    await admin.end()
  }
  const r = spawnSync('npx', ['prisma', 'migrate', 'deploy'], { encoding: 'utf8', env: { ...process.env, PRISMA_HIDE_UPDATE_MESSAGE: '1' } })
  if (r.status !== 0) throw new Error(`prisma migrate deploy 失敗：\n${r.stdout}${r.stderr}`)
}

依序來看：

  • 檢查名稱：資料庫名稱不是 _spec 結尾就直接丟錯、不往下跑。前面的設定已經把名稱換掉了，這道檢查是第二層保險：萬一哪天有人改了 vitest.config.ts，或用別的方式啟動測試，也不會清到開發或正式資料庫。
  • 不存在就建立：要執行 CREATE DATABASE，得先連上某個資料庫；但 event_signup_spec 還不存在，連不上。所以先連 PostgreSQL 預設就有的 postgres 資料庫，在那裡查 pg_database，不存在才建立。第一次跑、或你把它刪掉之後再跑，都會自動重建。
  • 建表：用 npx prisma migrate deploy 套用 migration，失敗就把輸出印出來並停止。

建表為什麼用 migrate deploy，而不是更快的 db push？db push 直接把資料庫改成 schema 現在的樣子，不看 prisma/migrations/ 裡的 migration 檔；而正式環境部署時跑的是 migrate deploy，照順序套用那些檔案。測試用 migrate deploy 建表，就順便確認了「migration 檔從頭套用得起來」：有人改了 schema 卻忘了產生 migration，或 migration 檔寫壞了，測試這一步就會失敗，而不是等到部署才發現。第 5 課的 CI 也是這樣。

最後是 fileParallelism: false。Vitest 預設會同時執行好幾個測試檔來加快速度，但這裡所有測試檔共用同一個 _spec 資料庫，而每個測試前都會 TRUNCATE：A 檔案的測試正在報名，B 檔案的 TRUNCATE 就把活動清掉了，結果時好時壞。關掉之後測試檔一個接一個跑，代價是不能平行；這個大小的專案全部跑完只要幾秒，值得。

💡 實務上：測試資料庫的名字就是一道安全鎖
「測試把正式資料清空」是真的會發生的事故：某人的 .env 指到正式環境，跑了一次 npm test。防法不是「大家小心」，而是讓測試程式自己拒絕：資料庫名稱不是 _spec 結尾就不啟動。同樣的思路用在任何會刪資料的腳本：先檢查環境，不對就停。你的 repo 有這兩道檢查，接手的同事就算 .env 設錯，最壞也只是測試跑不起來。

資料庫準備好了：獨立、自動建立、表是用 migration 建的。接下來要在測試裡把 API 啟動起來，而這裡藏著一個不容易察覺的問題。

在測試裡啟動的 API，跟正式環境是同一個嗎？

E2E 用 Test.createTestingModule 建出應用程式，它建的是沒有經過 main.ts 的應用程式：main.ts 裡設定的全域前綴 /api/v1、ValidationPipe、錯誤格式的 filter、requestId middleware 都不在。直接拿它來測，路徑會找不到、壞輸入會直接進 service、錯誤格式也跟正式環境不同，你測的是另一個應用程式。

最直覺的補法是在 E2E 裡把這些設定再寫一次，但這會留下一個慢慢發作的問題：哪天 main.ts 加了一行設定、測試沒加，兩邊就分岔了，測試綠燈不再代表正式環境沒問題。所以第 1 課就把全域設定集中在 configureApp()，main.ts 和 E2E 都呼叫它，設定只有一份：

// test/events.e2e-spec.ts
import type { INestApplication } from '@nestjs/common'
import { Test } from '@nestjs/testing'
import request from 'supertest'
import { AppModule } from '../src/app.module.js'
import { configureApp } from '../src/app.setup.js'
import { PrismaService } from '../src/prisma/prisma.service.js'

let app: INestApplication
const http = () => request(app.getHttpServer())
const future = (days = 7) => new Date(Date.now() + days * 86_400_000).toISOString()
const newEvent = async (capacity = 3) => (await http().post('/api/v1/events').send({ title: '讀書會', startsAt: future(), capacity }).expect(201)).body

beforeAll(async () => {
  const ref = await Test.createTestingModule({ imports: [AppModule] }).compile()
  app = ref.createNestApplication({ logger: false })
  configureApp(app)   // 跟 main.ts 同一套設定
  await app.init()
})
beforeEach(async () => {
  await app.get(PrismaService).$executeRawUnsafe('TRUNCATE registrations, events')
})
afterAll(() => app?.close())

這段是整個 E2E 檔案的共用準備，逐行看：

  • http() 包住 supertest，每次呼叫都對同一個應用程式發請求，不用開 port。
  • future() 產生 N 天後的時間：上一課規定活動不能建在過去，測試資料要永遠合法，所以用「現在加幾天」而不是寫死日期。
  • newEvent() 是測試資料的工廠函式：它用預設值建一場活動、確認回 201，再把回應的活動傳回來；名額可以覆寫。每個測試一行就有一場乾淨的活動，不用重複寫建立活動的請求。
  • beforeAll 建好應用程式並呼叫 configureApp(app)；logger: false 讓測試輸出不被 Nest 的啟動訊息淹沒。
  • beforeEach 就是上一節說的 TRUNCATE，每個測試前清空；afterAll 關掉應用程式，連線池才會釋放，Vitest 才能正常結束。

準備好之後，每個測試都照「準備 → 動作 → 檢查」三步寫：先建出需要的資料，再送出要測的請求，最後檢查結果。以重複報名為例：

it('ALREADY_REGISTERED：同一個 email 換大小寫也算重複，而且不會多扣名額', async () => {
  const e = await newEvent(3)
  await http().post(`/api/v1/events/${e.id}/registrations`).send({ email: 'ann@example.com', name: 'Ann' }).expect(201)
  const res = await http().post(`/api/v1/events/${e.id}/registrations`).send({ email: 'ANN@Example.com', name: 'Ann' }).expect(409)
  expect(res.body.errorCode).toBe('ALREADY_REGISTERED')
  expect((await http().get(`/api/v1/events/${e.id}`)).body.remaining).toBe(2)
})

準備是一場 3 個名額的活動；動作是同一個 email 報名兩次，第二次故意換成大小寫不同，因為上一課規定 email 不分大小寫；檢查有兩層。第一層是第二次回 409、errorCode 是 ALREADY_REGISTERED。第二層是最後一行：再查一次活動，remaining 要是 2。這一行檢查的是副作用，也就是請求對資料庫造成的改變。回 409 只代表「回應對了」，不代表「資料對了」：如果扣名額與新增報名不在同一個交易，重複報名會先扣掉一個名額、再因為唯一約束失敗，回應照樣是 409，名額卻少了一個。只檢查狀態碼的測試抓不到上一課講的這種 bug。

參考實作的 E2E 共 8 個測試：建立活動、三種驗證錯誤、404、分頁走完不重複、報名與取消、重複報名、併發搶名額、取消不存在的報名。完整檔案在 nestjs/practice/portfolio-ref/small/test/events.e2e-spec.ts，可以對照，但自己寫一遍：寫測試的過程會逼你想清楚每條規則。

💡 實務上：E2E 的檢查要寫到「資料」而不只是「回應」
code review 時看到只有 .expect(201) 的測試，資深工程師會問：「這個請求成功之後，資料庫應該長什麼樣？」名額、餘額、庫存這類會被扣減的數字，每個改到它的請求後面都值得再查一次。這也是你的 repo 給接手同事的保證：他改報名流程時，測試會告訴他名額有沒有算錯，而不只是 API 有沒有回 201。

到這裡的測試都是一次送一個請求。但開場的 bug 有個特性：一次一個人報名時，它完全正常。要抓到它，就得讓請求同時到。

「10 人同時搶 3 個名額」怎麼測，才會每次結果都一樣？

上一課講過，「先查剩幾個、大於 0 再新增」這種先檢查再寫入（check-then-insert）的寫法，一次一個請求時永遠是對的。兩個請求同時查到「剩 1 個」，才會兩個都寫進去。所以這條規則的測試必須真的同時送出請求。寫法是同時送出全部請求、等全部回來，只檢查最後的結果：

it('EVENT_FULL：同時 10 個人搶 3 個名額，恰好 3 個成功', async () => {
  const e = await newEvent(3)
  const results = await Promise.all(Array.from({ length: 10 }, (_, i) =>
    http().post(`/api/v1/events/${e.id}/registrations`).send({ email: `u${i}@example.com`, name: `U${i}` })))
  expect(results.filter(r => r.status === 201).length).toBe(3)
  expect(results.filter(r => r.status === 409 && r.body.errorCode === 'EVENT_FULL').length).toBe(7)
  expect((await http().get(`/api/v1/events/${e.id}`)).body.remaining).toBe(0)
})

Array.from({ length: 10 }, …) 一口氣建出 10 個請求，交給 Promise.all：10 個請求一起出發，不會等前一個回來才送下一個；Promise.all 等這 10 個全部回應，才把結果交給後面的檢查。檢查有三個：成功 3 個、EVENT_FULL 7 個、最後 remaining 是 0。

併發測試最常見的問題是時好時壞，大部分時候綠、偶爾紅，重跑又好了。這種測試比沒有測試還糟，因為大家很快就學會「紅了就重跑」，真的 bug 出現時也被當成雜訊。這個測試有三個寫法讓它穩定：

第一，不檢查「誰」成功，只檢查「幾個」成功。10 個請求同時到，PostgreSQL 讓哪 3 個先拿到那一列的鎖，每次都不一樣；如果寫成「前 3 個請求成功」，測試就會隨機失敗。

第二，每個請求用不同的 email（u0@example.com 到 u9@example.com）。如果有兩個請求用同一個 email，其中一個會因為重複報名回 409 ALREADY_REGISTERED，「7 個 EVENT_FULL」的數字就對不上了，而且這個錯跟名額規則無關。

第三，等全部結束再查 remaining。Promise.all 保證查的時候 10 個請求都已經回應；如果一邊送一邊查，查到的是中間狀態，數字每次不同。

這樣寫，在正確的程式上這個測試永遠是綠的；在 check-then-insert 的程式上，10 個請求同時到，幾乎每次都會超賣。反過來說，如果「10 人搶 3 個」的測試偶爾才失敗，通常是測試本身寫錯（資料重複、測試之間共用資料、沒等完），而不是程式時好時壞，選擇題會再問。

這個測試看起來抓得到開場的 bug。但「看起來」還不夠：要把所有測試接成一個指令，再親手把那行刪掉，看它是不是真的會紅。

npm test 跑完全部，而且真的抓得到開場那個 bug？

先把測試接成一個指令，第 5 課的 CI 只要執行它：

// package.json
"scripts": {
  "test": "vitest run",
  "test:watch": "vitest"
}

vitest run 跑一次就結束，CI 要的是這個；vitest 會停在監看模式，存檔就重跑相關測試，寫測試時用 npm run test:watch。單元測試與 E2E 由同一個 vitest.config.ts 的 include 一起跑，不分兩個指令：分開的話，總有一天有人只跑其中一個，另一半的保護就形同虛設。

docker compose up -d --wait db    # 開發用 PostgreSQL（測試會在裡面建 event_signup_spec）
npm test

全部通過之後，做這課最後、也最重要的一步：故意改壞。把 events.service.ts 裡的 remaining: { gt: 0 } 刪掉，這是開場那個修改裡真正拿掉保護的那一行。不用另外加「先查再新增」：少了這個條件，UPDATE 不再檢查剩餘名額，每個請求都扣得到，同時到的 10 個請求會全部成功。跑一次 npm test，併發測試應該變紅：成功的不再是 3 個。再把它改回來，換成把 E2E 裡的 configureApp(app) 拿掉，這次幾乎所有 E2E 都會變紅：連 /api/v1 前綴都不在了，newEvent() 建活動就先 404。這正好說明沒有 configureApp() 時，測的是另一個應用程式。兩次都確認之後，記得改回來。

這種「故意在程式裡放一個錯，看測試有沒有發現」的做法叫突變測試（mutation testing），這裡做的是手動版。它回答的是覆蓋率回答不了的問題：覆蓋率只告訴你哪些程式碼被執行過，不告訴你那段程式碼錯了測試會不會發現。改壞之後測試沒變紅，就表示那條規則沒有被保護，要回頭補測試。課後的自評清單裡有這兩項。

💡 實務上：測試要能抓到你最怕的 bug
寫測試時先問「這個功能最怕出什麼錯」，再確認有測試會因為那個錯變紅。對這個專案來說，最怕的是超賣與設定漏掉，所以改壞的就是這兩處。面試時被問「你怎麼知道測試有用」，答案就是：我把名額條件刪掉，併發測試紅了。這句話比「覆蓋率 90%」更有說服力。

到這裡，開場的任務完成了：三個月後有人刪掉 remaining: { gt: 0 }，npm test 會在 push 之前變紅。設定檔裡還有幾個這節沒展開的選項，以及專案變大後的替代做法，整理在下面。

補充與查表

主線用不到、但調整設定或專案變大時會查的細節。查表用，不用背。

vitest.config.ts 的選項

選項這個專案的值作用
globalstruedescribe、it、expect、beforeAll 等不用 import
includesrc/**/*.spec.ts、test/**/*.e2e-spec.ts單元測試與 E2E 用同一個設定一起跑
globalSetuptest/support/global-setup.ts所有測試前跑一次：檢查名稱、建立資料庫、migrate deploy

hookTimeout30_000（毫秒）beforeAll 等 hook 的時間上限；啟動整個 Nest 應用程式比一般測試慢

測試檔要平行跑怎麼辦

專案變大、測試變慢時，可以改成每個 worker 一個資料庫，各自 TRUNCATE 不會互相干擾。NestJS 課第 17 課提過做法：PostgreSQL 的 CREATE DATABASE x TEMPLATE y 可以從一個已經套用好 migration 的資料庫複製出新的，比每次跑 migration 快。這個專案的測試幾秒就跑完，用不到。

驗收測試怎麼讀你的結果

node check.mjs nestjs pf03 會在你的 repo（portfolio.json 的 small.repo）執行 npm test -- --reporter=json，讀結果檔判分，用的是你 repo 的 .env 與 vitest.config.ts。所以你本機 npm test 能過，驗收測試就跑得起來。

練習

練習 1：在你的 repo 寫好單元測試與 E2E，npm test 要：全部通過、沒有 skip／todo（也不能留 .only）、至少 8 個測試、至少一個 test/**/*.e2e-spec.ts 有跑到。

練習 2：測試名稱涵蓋契約的三種錯誤：有通過的測試，名稱（describe＋it）分別寫到 VALIDATION_FAILED、ALREADY_REGISTERED、EVENT_FULL。這是用文字比對的提示，重點是那三個測試真的檢查了對應的錯誤與副作用。

練習 3：同事的報名 service 有 12 個單元測試，全部 mock Prisma，覆蓋率 100%。上線第一天，重複報名回的是 500。最可能的原因是什麼？

✓ mock 測到的是「你以為資料庫會怎樣」。重複報名靠的是唯一約束與 P2002 的轉換，只有連真的資料庫才會走到。覆蓋率只說明每一行被執行過，不說明執行時的輸入跟正式環境一樣。b 的覆蓋範圍不是重點：就算 controller 也算進去，mock 還是看不到真的 P2002。（第 3 課）

練習 4：E2E 測試裡自己寫了 app.useGlobalPipes(new ValidationPipe({ whitelist: true }))，沒有呼叫 configureApp()。後來有人在 configureApp() 加了 forbidNonWhitelisted: true。會發生什麼事？

✓ createTestingModule 只建模組，不會執行 main.ts（c 錯），測試要自己套全域設定。各寫一份就會分岔，測試綠燈不再代表正式環境沒問題。把設定集中在 configureApp()，main.ts 與 E2E 都呼叫它。（第 3 課）

練習 5：「10 個人搶 3 個名額」的測試大部分時候綠，偶爾紅，紅的時候是成功 2 個、ALREADY_REGISTERED 1 個。先懷疑什麼？

✓ 出現 ALREADY_REGISTERED 表示有兩個請求用了同一個 email，這是測試資料的問題，不是名額邏輯的問題。併發測試偶爾失敗時，先懷疑測試本身：資料是否唯一、測試之間是否共用資料、是否等全部請求結束才檢查。a 是最常見的誤判：條件式 UPDATE 的行為是確定的，不會「偶爾失效」。（第 3 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認，前兩項就是最後一節「故意改壞」的步驟：

  • 測試抓得到超賣：把 events.service.ts 的 remaining: { gt: 0 } 刪掉，npm test 至少一個測試失敗。改回來。
  • 測試抓得到設定漏掉：把 E2E 的 configureApp(app) 註解掉，E2E 要大量失敗（至少路徑與驗證相關的測試）。改回來。
  • 開發資料不受影響：npm test 前後，用 curl http://localhost:3000/api/v1/events 看開發資料庫的活動還在。
  • 從零開始也跑得起來：docker compose exec db psql -U app -d postgres -c 'DROP DATABASE event_signup_spec'，再 npm test，globalSetup 會重建它。
  • 測試名稱讀起來像規格：只看 npm test 印出的測試名稱，不看程式，說得出這個 API 有哪些規則。

常見錯誤

  • 測試連到開發資料庫：每次 npm test 都把你手動建的資料清掉。在 vitest.config.ts 換資料庫名稱，globalSetup 檢查名稱結尾。
  • 測試資料庫用 db push 或手動建表：測試通過，正式環境的 migrate deploy 卻失敗。用 migrate deploy，順便測 migration。
  • E2E 沒呼叫 configureApp()：路徑沒有 /api/v1、驗證沒開、錯誤格式不同，測的是另一個應用程式。
  • 只檢查狀態碼：重複報名回 409，但名額被多扣了，測試看不到。動作之後再查一次狀態。
  • 併發測試檢查「第幾個請求成功」：誰先拿到鎖每次不同，測試會時好時壞。只檢查數量與最後狀態。
  • 留著 it.skip 或 .only：CI 是綠的，但有測試根本沒跑。.only 會讓同一個檔案的其他測試全部變成 skipped。
  • 測試檔平行跑卻共用一個資料庫：一個檔案的 TRUNCATE 清掉另一個檔案正在用的資料。設 fileParallelism: false，或每個 worker 一個資料庫。

小結

  • 這課的任務是讓「刪掉 remaining: { gt: 0 }」這種修改在 push 前就被 npm test 抓到。
  • 測試放在規則實際被執行的地方：純函式（游標）用單元測試，靠資料庫擋的規則（名額、重複報名）用 E2E 連真的 PostgreSQL。
  • 不 mock Prisma：mock 看不到唯一約束、條件式 UPDATE、交易回滾，而這些正是會出錯的地方。
  • 測試名稱寫成規格：失敗時讀名稱就知道哪條契約壞了。
  • 測試資料庫跟開發資料分開（名稱加 _spec）、globalSetup 自動建立並 migrate deploy、每個測試前 TRUNCATE，所以測試檔不平行跑。
  • E2E 與 main.ts 共用 configureApp()，測的才是同一個應用程式；動作之後再查一次資料，檢查副作用。
  • 併發測試同時送出、等全部結束、只檢查數量與最後狀態；每個請求的資料要唯一。
  • 故意改壞一行看測試有沒有變紅，才知道測試有沒有用；npm test 一個指令跑完全部。
