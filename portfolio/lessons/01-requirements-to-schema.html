階段 A：小專案走完一次 · 第 1 課

從需求到 schema：開一個新專案

到目前為止，每個練習都有人幫你開好專案：資料夾已經切好、package.json 已經鎖好版本、資料庫已經在跑。工作上接到一個新服務時，這些都要自己決定，而且一開始決定錯，後面每一課都要繞路：名額規則寫在程式裡卻忘了資料庫也要擋、.env 跟著第一個 commit 進了 git、開發用的資料庫對整個網路開著。

這一課你會接到這樣一段需求：

社團要辦讀書會與工作坊，想要一個報名系統。主辦人可以建立活動，填標題、時間與名額。參加的人用 email 和名字報名，名額滿了就不能再報；同一個人不能報名同一場兩次。報名後可以取消，名額會釋出給別人。先不用登入，主辦人之後再加。

任務是在你自己的 GitHub repo 開一個 NestJS 專案「活動報名 API」，做到「可以交給同事的第一天」：每條規則都決定好由誰擋、資料庫一個指令就開得起來、表格與約束都寫在 migration 裡、有一個端點能證明程式真的連得上資料庫、第一個 commit 裡沒有任何秘密。報名、取消這些業務端點留到第 2 課；這課做的是讓第 2 課能放心往上蓋的地基。這個 repo 會陪你走完階段 A，第 5 課結束時是一個可以放在履歷上的完整小專案。

這課會用到：
  • NestJS 課第 1 課的 nest new 與專案結構（ESM＋Vitest，nest build 會檢查型別）。
  • NestJS 課第 12 課的 docker compose up -d --wait（用 compose 開資料庫，等健康檢查通過才回來）。
  • NestJS 課第 13 課的 prisma.config.ts、migrate dev --create-only（只產生 migration 檔、先不套用）與 PrismaPg adapter。
  • PostgreSQL 課第 12 課的 UNIQUE 與 CHECK 約束（資料庫拒絕不合規則的資料）。
這門課的程式寫在你自己的 repo，不在 learn 資料夾裡。判分時你先啟動自己的 API，再在 learn 資料夾執行 node check.mjs nestjs pf01：測試對你的 API 打 HTTP，或讀你 repo 裡的檔案。課程的 PostgreSQL、Mailpit 借用 NestJS 課的練習環境（learn/nestjs/practice 的 docker compose up -d --wait）。

這課的路線：

  • 需求只有一段話：要存什麼、要擋什麼、要對外承諾什麼？把它拆成三張清單，決定每條規則由資料庫還是程式擋。
  • 規則要有地方落地：開新 repo 時，怎麼讓版本和課程一致、資料夾怎麼切？
  • 有一半的規則要靠資料庫擋，資料庫從哪來？寫進 compose.yaml，以及 port 為什麼只綁本機。
  • 怎麼把實體和規則寫進資料庫？Prisma schema、第一個 migration，以及 Prisma 寫不出來、要手寫的 CHECK。
  • 怎麼證明整條路是通的、怎麼安全地 commit、怎麼知道做對了？健康檢查、.env 不進 git、接上驗收測試。

需求只有一段話：要存什麼、要擋什麼、要對外承諾什麼？

拿到上面那段需求，最直覺的做法是開一個 controller 開始寫。問題在於需求裡的規則是散在句子裡的：「名額滿了就不能再報」「同一個人不能報名同一場兩次」「取消後名額釋出」。邊寫邊想，規則會想到哪寫到哪，有的漏掉，有的在三個地方各寫一半。所以開工前先把需求拆成三張清單，每張回答一個問題：

  • 實體：系統要記住什麼？
  • 規則：什麼情況要拒絕？由誰拒絕？
  • API 契約：外面的人（前端、其他服務）看到什麼？

實體：系統要記住什麼

實體就是需求裡需要被存下來的東西。找法是把需求裡的名詞挑出來，一個一個問「要不要存」：活動要存；報名要存；主辦人「之後再加」，現在不存；參加的人沒有帳號，只在報名時留 email 和名字，所以直接存在報名上，不需要另一張「人」的表。剩下兩個實體：

實體欄位說明
eventsid、title、starts_at、capacity、remaining、created_atremaining 是剩下的名額，報名時扣、取消時加回
registrationsid、event_id、email、name、created_at一筆報名屬於一個活動

remaining 值得多看一眼。剩餘名額其實算得出來：capacity 減掉這場的報名筆數。另外存一個欄位，是因為報名時最常問的就是「還有沒有名額」，有了這個欄位，「判斷還有名額」和「扣掉一個」可以寫成同一句 SQL（第 2 課）。代價是同一件事存了兩份，remaining 有可能被改成不合理的數字，例如負數，或比名額還大。這就是下一張清單要守住的東西。

規則：什麼情況要拒絕，由誰拒絕

規則是這一課真正要想清楚的地方。擋住一筆壞資料有兩個地方可以做：

  • 資料庫的約束（constraint）：寫在表格定義裡的規則。任何寫入只要違反，資料庫就拒絕，不管是 API、以後寫的管理腳本，還是有人用 psql 手動改資料。
  • 程式裡的檢查：寫在 DTO 或 service 裡的 if。只擋得住經過那段程式的寫入。

只靠程式檢查，有兩個漏洞。第一個是剛才說的：繞過這段程式的寫入擋不住。第二個比較隱蔽，是兩個請求同時進來。以「同一個 email 不能報名兩次」為例，如果程式寫成「先查有沒有報過，沒有才新增」：

  1. 使用者連按兩次報名，請求 A 和請求 B 幾乎同時到達。
  2. A 查詢：這個 email 還沒報過。
  3. B 查詢：這個 email 還沒報過（A 還沒寫進去）。
  4. A 新增一筆，B 也新增一筆。資料庫裡有兩筆一樣的報名。

一次只來一個請求時，這段程式完全正確，所以平常測不出來。換成資料庫的唯一約束 UNIQUE (event_id, email)，資料庫在寫入的那一刻檢查，兩筆裡只會有一筆成功，另一筆收到錯誤。

所以每條規則都先問一句：資料庫能不能自己擋？能的話就讓資料庫擋，程式再檢查一次（或把資料庫的錯誤翻譯過來）是為了給使用者好懂的錯誤訊息；資料庫擋不了的，才只靠程式。資料庫能擋什麼，取決於約束能看到什麼：

  • CHECK 只看正在寫入的那一列：同一列的欄位可以互相比較（remaining <= capacity），但數不到別的列。
  • UNIQUE 會跨列比較，但只能回答「有沒有重複」。
  • 「名額滿了不能報名」原本要數 registrations 裡這場有幾筆，這是數別的列，CHECK 和 UNIQUE 都做不到。

名額這條規則要分兩步想。第一步，資料庫數不了列，所以前面才多存一個 remaining 欄位，把「數報名筆數」換成「看同一列的一個數字」。這樣 CHECK (remaining BETWEEN 0 AND capacity) 就寫得出來，扣到負數時資料庫會拒絕。

第二步，remaining 跟實際的報名筆數對不對得上，資料庫並不知道。它只看得到 remaining 這個數字合不合範圍，看不到「名額 50、已有 3 筆報名，所以應該剩 47」。要讓兩邊一致，得靠程式每次報名都同時做兩件事：扣 remaining、新增一筆報名。CHECK 擋得住「扣過頭」的 bug，擋不住「新增了報名卻忘了扣」或「取消了報名卻忘了加回」，這些情況下數字仍在 0 到 capacity 之間，資料庫看不出錯。所以這條規則的主責在程式，CHECK 只是最後一道保險。

「同時做兩件事」還有一個坑：兩個寫入中間可能失敗。例如先扣了 remaining，接著新增報名時撞到 UNIQUE (event_id, email)（這個 email 已經報過）而失敗，結果名額少了一個，卻沒有人報名成功。解法是交易（transaction）：把幾個寫入包成一組，全部成功才真正寫進去；中途任何一個失敗，整組還原，像什麼都沒發生。上面的例子放進交易裡，新增報名失敗時，扣掉的名額會一起還原。交易的細節在 PostgreSQL 第 18 課，這個專案的報名流程在第 2 課實作。

照這個標準，四條規則分配如下：

規則放在哪為什麼
同一場活動，同一個 email 只能報名一次（大小寫不同也算同一個）資料庫：UNIQUE (event_id, email)，email 存小寫兩個請求同時送來時，程式「先查有沒有報過」兩邊都會查到沒有；唯一約束只會讓一個成功
名額 1～500、剩餘名額不能是負的、不能超過名額資料庫：CHECK只看同一列的欄位，CHECK 擋得住；任何程式（包括以後的管理腳本）寫進壞資料都會被拒絕
名額滿了不能報名程式：條件式 UPDATE … SET remaining = remaining - 1 WHERE remaining > 0（第 2 課）要數報名筆數，約束做不到，所以改存 remaining；但它跟實際報名筆數是否一致，資料庫不知道，要靠程式在同一個交易裡「扣 remaining＋新增報名」。CHECK 只擋得住扣過頭，是最後一道保險
活動時間要在未來、標題長度程式：DTO 驗證「未來」要跟現在的時間比，放在資料庫的 CHECK 裡會讓舊資料在時間過了之後變成「不合法」

最後一列是唯一「資料庫做得到、但不該做」的。CHECK (starts_at > now()) 寫得出來，問題是 CHECK 的條件應該對一列資料永遠成立，而「在未來」今天成立、活動辦完就不成立了。CHECK 在每次 UPDATE 那一列時都會重新檢查，所以活動結束後，連修改它的標題都會被拒絕。「現在」這種會隨時間變的條件，只在建立的那一刻檢查，放在程式裡。

API 契約：外面的人看到什麼

第三張清單是 API 契約：每個端點的路徑、方法、成功時回什麼、失敗時回什麼。失敗的回應裡除了狀態碼，還會帶一個 errorCode：一個固定不變、給程式判斷用的字串，例如 EVENT_FULL。前端看到 409 還不知道是「名額滿了」還是「已經報過」，看 errorCode 就能決定顯示哪一句提示，不用去解析給人看的 message 文字。

這門課已經寫好一份：小專案契約。驗收測試只照契約檢查狀態碼與 errorCode，不管你的程式怎麼寫。工作上這份契約是你跟前端、PM 一起定的，定好之後兩邊可以同時開工。

💡 實務上：先寫契約，再寫程式
需求單通常只有一段話。資深工程師開工前會先回一份「實體、規則、端點」的清單請 PM 確認，順便問出需求沒寫的事：名額滿了要不要候補？取消有沒有截止時間？同一個 email 不同名字算不算同一個人？這些問題在寫程式前問是一則訊息，上線後才發現是一次資料修正。契約也讓前端不用等後端寫完：照契約做假資料就能先做畫面。

三張清單把「要做什麼」定下來了。但清單只是文件，規則要真的生效，得有一個專案讓它們落地。

規則要有地方落地：開新 repo，怎麼讓版本和課程一致？

落地的第一步是把 NestJS 專案開起來。NestJS 課第 1 課看過 nest new 產生的檔案；這次在你自己的工作資料夾執行，不要放在 learn 裡面，因為 learn 是課程的 repo，你的作品要能獨立放上 GitHub：

cd ~/code                                            # 你放專案的地方
npx @nestjs/cli@12.0.11 new event-signup --no-observe   # 套件管理選 npm，模組系統選 ESM（Vitest）
cd event-signup

為什麼要鎖版本

nest new 裝的是執行當下最新的套件版本。課文的範例、判分用的參考實作，都是用 learn 的 nestjs/practice 那一組版本跑過的；你裝到的版本不同，課文寫的指令輸出、錯誤訊息就可能對不上，卡住時分不清是自己寫錯還是版本不同。

版本會飄的原因在 package.json 的寫法。npm i 預設寫進去的是 "^12.3.2"，^ 的意思是「12.x.x 裡任何不比 12.3.2 舊的版本都可以」。今天裝和下個月裝，可能拿到不同的版本，同事 clone 下來裝到的也可能跟你不一樣。解法有兩層：

  • --save-exact：讓 package.json 寫死版本，不寫 ^。這鎖住你直接用到的套件。
  • package-lock.json（lockfile）：記錄整棵依賴樹實際裝了哪個版本，包括套件自己依賴的套件。npm ci 會完全照它裝。所以 lockfile 一定要 commit。

把版本鎖成跟 nestjs/practice 一樣：

npm i --save-exact @nestjs/common@12.3.2 @nestjs/core@12.3.2 @nestjs/platform-express@12.3.2 \
  @nestjs/config@12.0.1 @nestjs/terminus@12.1.0 \
  @prisma/client@7.10.1 @prisma/adapter-pg@7.10.1 pg@8.23.1 \
  class-validator@0.15.1 class-transformer@0.5.1 zod@4.6.7 dotenv@18.0.9
npm i -D --save-exact @nestjs/cli@12.0.11 @nestjs/schematics@12.0.12 @nestjs/testing@12.3.2 \
  prisma@7.10.1 typescript@6.0.3 vitest@5.0.5 supertest@7.3.1 @types/supertest@7.2.1

這些套件分成幾組：NestJS 本體、讀設定與健康檢查、Prisma 與 PostgreSQL 驅動、輸入驗證、測試。每個套件做什麼、在 NestJS 課哪一課教過，整理在課末的補充與查表。版本升級是你自己的決定，驗收測試只看 HTTP 行為，不受影響。

資料夾照功能切

專案開好之後，先決定程式放哪裡。這個專案的資料夾照功能切：src/events/ 裡放活動相關的 controller、service、DTO；不照種類切，也就是不開 src/controllers/、src/services/。理由很實際：改一個功能時，要動的檔案都在同一個資料夾；照種類切的話，改一個「報名」要在三、四個資料夾之間跳來跳去，功能一多就找不到東西。

nest new 產生的 app.controller.ts、app.service.ts 與它們的測試只是範例，刪掉；app.module.ts 留著，之後在這裡 import 各功能的模組。這一課會新增的檔案：

event-signup/

  .env.example  .env  .gitignore       ← 環境變數的範本、真的值、不進 git 的清單

  prisma/schema.prisma

第 5 課結束時整個 repo 的樣子（第 2～5 課會加哪些資料夾），放在課末。

專案的骨架有了。但規則清單裡有一半要靠資料庫擋，而這台電腦上還沒有一個屬於這個專案的資料庫。

有一半的規則要靠資料庫擋，資料庫從哪來？

最省事的做法是用電腦上已經裝好的 PostgreSQL，再建一個資料庫。問題是每個人電腦上的 PostgreSQL 版本、設定都不一樣，同事 clone 下來要先照一份說明自己裝，裝到別的版本就可能出現你沒遇過的錯誤。所以把資料庫寫進 repo 的 compose.yaml：版本、帳號、資料庫名稱都寫死，任何人 clone 下來執行一個指令，就有一個跟你一模一樣的資料庫。

name: event-signup
services:
  db:
    image: postgres:18.6-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: event_signup
    ports:
      - "127.0.0.1:5434:5432"
    volumes:
      - pgdata:/var/lib/postgresql   # PostgreSQL 18 的映像掛這裡（NestJS 課第 12 課）
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d event_signup"]
      interval: 2s
      timeout: 3s
      retries: 30
volumes:
  pgdata:

由上往下：image 鎖定 PostgreSQL 的版本；environment 讓容器第一次啟動時建好帳號與資料庫；volumes 把資料存在 Docker 管理的 volume，容器刪掉重建，資料還在；healthcheck 用 pg_isready 確認資料庫真的能接受連線，--wait 就是等這一項通過才回來（NestJS 課第 12 課）。

ports：為什麼前面要加 127.0.0.1

ports 這一行最容易寫錯，也最容易出事。"5434:5432" 的意思是：把你電腦的 5434 port 接到容器裡的 5432 port（PostgreSQL 預設的 port）。選 5434 是因為電腦上的 5432 可能已經有別的 PostgreSQL，learn 的練習環境用 5433，這個專案用 5434，三個可以同時開。

前面的 127.0.0.1: 決定的是「誰連得到」。一台電腦通常有好幾個網路介面：127.0.0.1（loopback）只有這台電腦自己連得到；連上 Wi-Fi 時還有一個區網 IP，同一個網路的其他人連的是這個。只寫 "5434:5432" 的話，Docker 會綁在電腦所有的網路介面上，同一個 Wi-Fi 的人都連得到你的資料庫，而帳號密碼是 app／app。前面加 127.0.0.1: 就只綁在 loopback，只有你自己的電腦連得到。

docker compose up -d --wait db     # 等健康檢查通過才回來
docker compose config              # 看 Docker 解析出來的完整設定（ports 有沒有 host_ip: 127.0.0.1）

docker compose config 會把 compose.yaml 解析成完整的設定印出來，寫錯縮排或欄位時會直接報錯，ports 也會拆成 host_ip、published、target 讓你確認。練習 3 的驗收測試就是用它讀你的 compose 檔。

💡 實務上：開發環境也是資安範圍
開發用的資料庫裡常常有從正式環境複製來的資料，密碼又是 postgres／postgres 這種。在咖啡廳或共用辦公室的網路上，綁在所有介面的資料庫等於公開在區網裡。資安稽核時會掃描員工電腦開了哪些 port。養成習慣：開發用的服務一律綁 127.0.0.1，需要讓同事連的才另外開，而且用不同的密碼。

資料庫開起來了，但裡面是空的：沒有 events、registrations，規則清單裡的 UNIQUE 和 CHECK 也還沒寫進去。

怎麼把實體和規則寫進資料庫？

把表格寫進資料庫，靠的是 migration：一個 SQL 檔，記錄資料庫結構的一次變更。migration 依序存在 repo 裡，任何一台空的資料庫照順序套用，就會變成一樣的結構；同事的電腦、CI、正式環境都是這樣建出表格的。NestJS 課第 13 課教過 Prisma 的分工：你在 schema.prisma 描述表格，migrate dev 比對出差異、產生 migration 並套用，generate 產生帶型別的 Prisma Client 給程式用。這一節照這個順序，把實體清單和規則清單寫進去。

讓 Prisma 找到資料庫

Prisma 要先知道連哪一個資料庫。連線網址裡有帳號密碼，所以放在 .env，不進 git；同樣的變數名稱、配上開發用的值放在 .env.example，進 git，讓下一個人知道要設哪些變數。兩個檔案的分工在 commit 那一節會再談。

# .env.example：複製成 .env
PORT=3000
DATABASE_URL=postgresql://app:app@127.0.0.1:5434/event_signup
cp .env.example .env

prisma.config.ts 告訴 Prisma schema、migration 放在哪、連哪個資料庫。Prisma 7 不會自己讀 .env，所以第一行要自己載入。

import 'dotenv/config'
import { defineConfig } from 'prisma/config'

export default defineConfig({
  schema: 'prisma/schema.prisma',
  migrations: { path: 'prisma/migrations' },
  // 用 process.env 而不是 env()：變數不存在時 env() 連 prisma generate 都會失敗（第 4 課建映像時會遇到）
  datasource: { url: process.env.DATABASE_URL },
})

把實體清單寫成 schema

prisma/schema.prisma 裡，每個實體是一個 model。PostgreSQL 的慣例是表格與欄位用 snake_case，TypeScript 的慣例是 camelCase；@@map、@map 讓兩邊各用各的慣例，程式裡寫 startsAt，資料庫裡是 starts_at。

generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

model Event {
  id            String         @id @default(uuid()) @db.Uuid
  title         String
  startsAt      DateTime       @map("starts_at") @db.Timestamptz(3)
  capacity      Int
  remaining     Int
  createdAt     DateTime       @default(now()) @map("created_at") @db.Timestamptz(3)
  registrations Registration[]

  @@index([startsAt, id])        // 第 2 課的游標分頁依 (starts_at, id) 排序
  @@map("events")
}

model Registration {
  id        String   @id @default(uuid()) @db.Uuid
  eventId   String   @map("event_id") @db.Uuid
  event     Event    @relation(fields: [eventId], references: [id], onDelete: Cascade)
  email     String                // 存小寫
  name      String
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)

  @@unique([eventId, email])      // 同一場活動，同一個 email 只能一筆
  @@map("registrations")
}

這份 schema 裡有幾個選擇，都是從前面的清單來的：

  • ID 用 UUID 而不是自動編號：網址上的 /events/3 會讓人猜到 /events/4，也透露了你有多少活動；UUID 猜不到。
  • 時間一律 timestamptz（PostgreSQL 課第 13 課）：存的是一個時間點，不會因為伺服器的時區設定而變。
  • @@unique([eventId, email])：規則清單的第一條，會變成資料庫的唯一約束。
  • onDelete: Cascade：活動被刪掉時，它的報名一起刪掉，不會留下指向不存在活動的報名。

Prisma 寫不出來的 CHECK：先產生草稿，手寫，再套用

規則清單裡還有兩條 CHECK：名額 1～500、剩餘名額在 0 和名額之間。這兩條 Prisma schema 寫不出來：Prisma 7.10.1 的 schema 語言沒有 CHECK 約束的語法。

做法是利用 migration 本身就是 SQL 檔這一點：讓 Prisma 先產生 migration 草稿、先不套用，打開檔案手動加上 CHECK，再套用。順序不能反過來：migration 一旦套用，資料庫就記下它已經執行過，事後再改那個檔案，資料庫與 migration 記錄就對不上（見常見錯誤）。

npx prisma migrate dev --create-only --name init   # 只產生 prisma/migrations/<時間>_init/migration.sql
# 打開 migration.sql，在 CREATE TABLE "events" 裡加上兩個 CHECK（下面）
npx prisma migrate dev                              # 套用
npx prisma generate                                 # 產生 Prisma Client（Prisma 7 的 migrate dev 不會順便產生）
CREATE TABLE "events" (
    "id" UUID NOT NULL,
    "title" TEXT NOT NULL,
    "starts_at" TIMESTAMPTZ(3) NOT NULL,
    "capacity" INTEGER NOT NULL,
    "remaining" INTEGER NOT NULL,
    "created_at" TIMESTAMPTZ(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "events_pkey" PRIMARY KEY ("id"),
    -- 手寫：Prisma schema 寫不出 CHECK
    CONSTRAINT "events_capacity_check" CHECK ("capacity" BETWEEN 1 AND 500),
    CONSTRAINT "events_remaining_check" CHECK ("remaining" BETWEEN 0 AND "capacity")
);

接著自然會擔心：Prisma 比對 schema 與資料庫時，發現資料庫多了 schema 裡沒有的東西，下一次 migrate dev 會不會把手寫的約束刪掉？不會：Prisma 比對時不管 CHECK 約束（7.10.1 實測：套用上面的 migration 後執行 prisma migrate diff，結果是空的 migration）。代價是 schema.prisma 看不到它們，所以在 model 上方寫一行註解，提醒後來的人 migration 裡還有約束。

約束有沒有真的生效，用最直接的方法確認：用 psql 手動寫一筆 capacity = 0 的活動，應該被拒絕（指令在下面的自評清單）。

email 的「不分大小寫」放在哪裡

規則清單說大小寫不同的 email 也算同一個人，但一般的 UNIQUE 是逐字比較，Amy@x.tw 和 amy@x.tw 會被當成兩個不同的值。這一課的做法是存之前轉成小寫（第 2 課在 DTO 裡做），資料庫裡只會有小寫的 email，唯一約束就自然不分大小寫。另一個做法是 PostgreSQL 的 citext 型別，把「不分大小寫」放進資料庫；兩者的取捨在練習 5 比較。

migrate dev 只在開發機用：它發現資料庫跟 migration 對不上時會要求重設資料庫（刪光資料）。CI 與正式環境一律用 prisma migrate deploy，只套用還沒套用的 migration（PostgreSQL 課第 22 課、第 4 課會再講）。

表格和約束都進資料庫了，Prisma Client 也產生了。可是到目前為止，Nest 程式本身還沒碰過資料庫：它讀得到 .env 嗎？連線字串對嗎？

程式、設定、資料庫，怎麼證明它們串得起來？

要證明整條路是通的，需要一個真的會經過「程式啟動 → 讀設定 → 連資料庫 → 回 HTTP」的端點。業務端點要等第 2 課，而且它們出錯時，你分不清是業務邏輯寫錯還是連線有問題。所以第一個端點只做健康檢查：它最小，只回答「服務好了沒」，而之後每一課（Docker、CI、部署）都會用它判斷服務能不能用。

live 與 ready：同一個「好了沒」，兩個不同的問題

健康檢查端點不是給人看的，主要是給部署平台看的。部署平台（例如 Kubernetes 或雲端的容器服務）會每隔幾秒打一次這些端點，依結果做兩件完全不同的事：

  • 判定程序壞了，重啟它。
  • 判定程序暫時不能服務，先不把請求送過來。負責分配請求的是負載平衡器（load balancer）：它站在多個 API 程序前面，把進來的請求分給其中一個。

這兩件事要用兩個端點分開回答（NestJS 課第 24 課）：

  • GET /health/live：程序還活著嗎？不查任何依賴，只要程序能回應就是 200。資料庫斷了也不能讓它失敗，否則平台會一直重啟其實沒壞的程序。
  • GET /health/ready：現在能接流量嗎？要連得上資料庫才是 200，否則 503，負載平衡器就先不把請求送過來。

為什麼不合成一個？想像資料庫維護 5 分鐘。如果唯一的健康檢查要查資料庫，平台會判定所有程序都壞了，把它們全部重啟，而且重啟後資料庫還沒回來，又會再被判定壞掉，一直重啟到資料庫恢復。重啟解決不了資料庫的問題，只是多了啟動的負擔。分開之後，資料庫斷線時 ready 失敗、live 照常：程序留著，只是暫時不收請求，資料庫一回來就能立刻服務。

// src/health/health.controller.ts
import { Controller, Get } from '@nestjs/common'
import { HealthCheck, HealthCheckService, PrismaHealthIndicator } from '@nestjs/terminus'
import { PrismaService } from '../prisma/prisma.service.js'

@Controller('health')
export class HealthController {
  constructor(private readonly health: HealthCheckService, private readonly db: PrismaHealthIndicator, private readonly prisma: PrismaService) {}

  @Get('live')
  live() {
    return { status: 'ok' }
  }

  @Get('ready')
  @HealthCheck()
  ready() {
    return this.health.check([() => this.db.pingCheck('database', this.prisma, { timeout: 1000 })])
  }
}

live 什麼都不查，直接回 ok。ready 交給 @nestjs/terminus：pingCheck 透過 Prisma 對資料庫送一個最小的查詢，1 秒內沒有回應就算失敗；health.check 把結果整理成固定格式，有任何一項失敗就回 503。

controller 背後要接的東西

controller 要用到 PrismaService，而 PrismaService 要從設定讀連線網址。下面把這條線接起來，寫法都是 NestJS 課教過的：第 13 課的 PrismaService、第 11 課的 ConfigModule。其中 env.ts 負責在啟動時驗證環境變數，原因寫在程式碼後面。

// src/config/env.ts：啟動時驗證環境變數，少了或格式錯就不啟動
import { z } from 'zod'

const schema = z.object({
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.url(),
})
export type Env = z.output<typeof schema>

export function validateEnv(raw: Record<string, unknown>): Env {
  const r = schema.safeParse(raw)
  if (!r.success) throw new Error(`環境變數設定錯誤：\n${z.prettifyError(r.error)}`)
  return r.data
}

// src/prisma/prisma.service.ts：Prisma 7 透過 adapter 連線；關機時斷開連線池
import { Injectable, type OnApplicationShutdown } from '@nestjs/common'
import { ConfigService } from '@nestjs/config'
import { PrismaPg } from '@prisma/adapter-pg'
import { PrismaClient } from '../generated/prisma/client.js'
import type { Env } from '../config/env.js'

@Injectable()
export class PrismaService extends PrismaClient implements OnApplicationShutdown {
  constructor(config: ConfigService<Env, true>) {
    super({ adapter: new PrismaPg({ connectionString: config.get('DATABASE_URL', { infer: true }), connectionTimeoutMillis: 5_000 }) })
  }
  async onApplicationShutdown() {
    await this.$disconnect()
  }
}

// src/prisma/prisma.module.ts：@Global() 讓每個模組都能注入 PrismaService，不用各自 import
@Global()
@Module({ providers: [PrismaService], exports: [PrismaService] })
export class PrismaModule {}

// src/health/health.module.ts
@Module({ imports: [TerminusModule], controllers: [HealthController] })
export class HealthModule {}

// src/app.module.ts：nest new 產生的檔案改成這樣（AppController、AppService 已刪掉）
@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true, validate: validateEnv }),
    PrismaModule,
    HealthModule,
  ],
})
export class AppModule {}

app.module.ts 的 validate: validateEnv 讓環境變數在啟動時就驗證：DATABASE_URL 不是網址、PORT 不是數字，就丟錯、程式不啟動（NestJS 課第 11 課）。不驗證的話，少了 DATABASE_URL 程式照樣啟動，要等第一個請求進來、Prisma 嘗試連線時才 500，錯誤訊息還不一定指向環境變數。在啟動那一刻就失敗，訊息直接寫出缺了哪個變數，好查得多。

最後是 main.ts，以及一個新檔 app.setup.ts。全域設定（現在只有路徑前綴，第 2 課再加驗證與錯誤格式）集中寫在 configureApp 這個函式，main.ts 與第 3 課的 E2E 測試都呼叫它。如果全域設定直接寫在 main.ts，測試建立的 app 就不會有這些設定，測試通過不代表正式啟動的程式也對。

// src/app.setup.ts：main.ts 與第 3 課的 E2E 測試共用
import type { INestApplication } from '@nestjs/common'

export function configureApp(app: INestApplication) {
  app.setGlobalPrefix('api/v1', { exclude: ['health/live', 'health/ready'] })   // 健康檢查不加前綴
}

// src/main.ts
const app = await NestFactory.create(AppModule)
configureApp(app)
app.enableShutdownHooks()
await app.listen(process.env.PORT ?? 3000)

驗證：把資料庫停掉看看

啟動之後，先確認兩個端點都是 200，再把資料庫停掉：

npm run start:dev
curl -i http://localhost:3000/health/live
curl -s http://localhost:3000/health/ready     # {"status":"ok","info":{"database":{"status":"up"}},"error":{},"details":{"database":{"status":"up"}}}
docker compose stop db && curl -i http://localhost:3000/health/ready   # 503；live 還是 200
docker compose start db

最後兩行值得真的做一次：資料庫停掉後 ready 變成 503、live 還是 200。這就是兩個端點分開的理由，也證明了 ready 真的有去問資料庫，不是寫死回 200。

在你的電腦上，整條路通了。下一步是 commit，但工作資料夾裡現在有一個絕對不能進 git 的檔案：裝著資料庫密碼的 .env。

第一次 commit：怎麼確定秘密沒有跟著進 git？

為什麼特別在意第一次 commit？因為秘密一旦進了 git，就很難真正拿掉。git 的每個 commit 都是整個專案在那一刻的快照，下一個 commit 刪掉 .env，只是新的快照裡沒有它，舊的快照照樣留在歷史裡，任何 clone 下來的人都翻得到。push 到 GitHub 之後更糟：公開的 repo 會被專門找金鑰的程式自動掃描。

防線是 .gitignore：列在裡面的檔案，git add . 會略過。nest new 產生的已經有 node_modules、dist，確認有這幾行：

# .gitignore（nest new 產生的已經有 node_modules、dist；確認有這幾行）
node_modules/
dist/
src/generated/      # prisma generate 的輸出，每台電腦自己產生
.env

src/generated/ 也不進 git：它是 prisma generate 從 schema 產生的，每台電腦自己產生，放進 git 只會在每次改 schema 時多出一大片 diff。

commit 前後各確認一次：

git status                      # 列出的檔案裡不能有 .env
git add . && git commit -m "開專案：schema、第一個 migration、健康檢查"
git ls-files .env               # 什麼都沒印出來才對
gh repo create event-signup --private --source . --push   # 選用：用 GitHub CLI 建 repo 並推上去

如果 .env 已經被 commit 了，只補 .gitignore 沒有用：.gitignore 只對還沒被追蹤的檔案有效。要先 git rm --cached .env（從 git 移除、檔案留在硬碟），把它加進 .gitignore 再 commit。裡面的密碼要當成已經外洩，全部換掉；只刪檔案不夠，歷史裡還在。

💡 實務上：.env.example 是給下一個人的說明書
新同事 clone 專案後，第一個問題通常是「要設哪些環境變數」。.env.example 列出每個變數、配上能在本機跑的假值與一行註解，他複製一份就能啟動。每次程式多讀一個環境變數，同一個 commit 就要更新 .env.example；code review 時看到 process.env.X 或 zod schema 多一個欄位、卻沒改 .env.example，就是該留言的地方。

repo 安全地有了第一個 commit。剩下最後一個問題：你做出來的東西，跟契約和規則清單要求的一樣嗎？

怎麼知道做出來的東西符合要求？接上驗收測試

這門課用 learn 的驗收測試回答這個問題：它對你的 API 打 HTTP、讀你 repo 裡的檔案，照契約檢查。所以要先告訴它你的 API 在哪、repo 在哪。第一次執行會在 learn/nestjs/practice/work/ 建立一份 portfolio.json 範本並顯示失敗：

# 在 learn/nestjs/practice（第一次才要）
npm ci
docker compose up -d --wait

# 在 learn
node check.mjs nestjs pf01

打開 learn/nestjs/practice/work/portfolio.json，填上 small 區段：

{
  "small": { "api": "http://localhost:3000", "repo": "/Users/你的名字/code/event-signup" }
}

repo 要寫絕對路徑（pwd 印出來的那個）。先在你的專案 npm run start:dev，再執行一次 node check.mjs nestjs pf01。測試失敗時，訊息會分得出是「連不到 API」「網址或路徑填錯」還是「行為不對」。之後每一課都用同一份 portfolio.json，只要換題號。

練習

練習 1：在你的專案做出 GET /health/live（200）與 GET /health/ready（資料庫連得上時 200，body 是 @nestjs/terminus 的格式，details.database.status 是 "up"）。兩個路徑都不加 /api/v1 前綴。

練習 2：寫好 schema.prisma，用 --create-only 產生第一個 migration，手動加上跟 capacity 有關的 CHECK，再套用。測試讀你 repo 裡的 prisma/migrations/*/migration.sql：要有 (event_id, email) 的 UNIQUE、跟 capacity 有關的 CHECK；也檢查 .env.example 存在、.gitignore 有 .env、.env 沒有被 git 追蹤。

練習 3：repo 根目錄的 compose.yaml 有一個 postgres:… 映像的服務，port 只綁 127.0.0.1。測試用 docker compose config --format json 解析你的檔案。

練習 4：同事建議：「不要 remaining 欄位了，名額規則寫成 CHECK：報名數不能超過 capacity，這樣完全不用寫程式。」為什麼不行？

✓ CHECK 是「這一列自己合不合法」，不能查別的列或別的表，所以「報名數 ≤ 名額」要靠程式（第 2 課用交易＋條件式 UPDATE）。同一列的欄位互相比較是可以的，這課的 remaining BETWEEN 0 AND capacity 就是（d 錯）。a 錯在前提：CHECK 根本寫不出跨列的計數，談不上效能。（第 1 課）

練習 5：要讓「同一場活動不能用同一個 email 報名兩次」不分大小寫。這課選「存之前轉小寫＋一般的 UNIQUE」，不用 citext 型別。這個選擇的代價是什麼？

✓ 規則放在程式，資料庫只看到「已經轉好的字串」，所以每條寫入路徑都要守規矩。citext（或 lower(email) 的唯一索引）把規則放進資料庫，任何寫入都擋得住，代價是 Prisma schema 要用 Unsupported 或手寫 migration。b 錯：UNIQUE 一定會建立唯一索引。（第 1 課）

練習 6：部署平台每 10 秒打一次健康檢查，連續失敗 3 次就重啟容器。同事把 /health/live 也改成「要連得上資料庫才回 200」，理由是「資料庫斷了，服務本來就不能用」。資料庫維護 5 分鐘時會發生什麼？

✓ live 失敗的意思是「這個程序壞了，重啟它」。把外部依賴放進 live，依賴一出事，所有副本會同時被判定壞掉而一起重啟。依賴的狀態放在 ready：失敗時只是暫停送流量，程序留著等資料庫回來。b 把兩者的用途說反了。（第 1 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • 規則清單寫進 README 或 issue：每條規則標出放在資料庫還是程式。自己確認：拿給沒參與的人看，他能說出「名額滿了」是誰擋的。
  • CHECK 真的有效：用 psql（docker compose exec db psql -U app -d event_signup）手動 INSERT 一筆 capacity = 0 的活動，要被拒絕（23514 check_violation）。
  • ready 與 live 分得開：docker compose stop db 之後 ready 是 503、live 還是 200。
  • 少一個環境變數就不啟動：把 .env 的 DATABASE_URL 註解掉，npm run start:dev 要在啟動時就失敗，錯誤訊息說得出缺了哪個變數。
  • 版本鎖死：package.json 的版本沒有 ^ 或 ~，package-lock.json 有 commit。
  • git 歷史乾淨：git log --all --oneline -- .env 什麼都沒印出來。

常見錯誤

  • 直接 migrate dev、事後才想到 CHECK：第一個 migration 已經套用，再改它的 SQL 會讓資料庫與 migration 記錄對不上。要加約束就用 --create-only 另外產生一個新的 migration 手寫進去；還沒 push 的話，也可以刪掉 migration 資料夾、重設開發資料庫重來。
  • compose 的 port 寫成 "5434:5432"：綁在所有網路介面上，同一個網路的人連得到你的資料庫。寫 "127.0.0.1:5434:5432"。
  • live 也去查資料庫：資料庫一斷，平台會把所有程序一起重啟。live 只看程序本身，依賴放 ready。
  • .env 進了 git 才補 .gitignore：.gitignore 對已經追蹤的檔案無效。要 git rm --cached .env，並且換掉裡面所有的密碼。
  • 改完 schema 忘了 prisma generate：Prisma 7 的 migrate dev 不會產生 Client，程式裡找不到新欄位的型別。
  • 把專案開在 learn 資料夾裡：learn 是課程的 repo，你的作品要在自己的 repo，才能放上 GitHub、寫進履歷。

小結

  • 開工前把需求整理成三張清單：實體、規則、API 契約。每條規則先問「資料庫能不能自己擋」：程式的「先查再寫」擋不住同時進來的兩個請求，也擋不住繞過程式的寫入。
  • 同一列能判斷的規則用 CHECK、「不能重複」用 UNIQUE；跨列的規則（名額）靠程式加交易，CHECK 當最後一道保險；跟「現在」比的規則不放 CHECK。
  • 版本用 --save-exact 鎖死、lockfile 要 commit；資料夾照功能切。
  • 開發用的服務寫在 repo 的 compose.yaml，port 只綁 127.0.0.1。
  • Prisma schema 寫不出 CHECK：migrate dev --create-only 產生草稿、手寫、再套用；Prisma 7.10.1 比對時不管 CHECK，不會被刪掉。
  • 第一個端點是健康檢查：live 只看程序、ready 看依賴；環境變數在啟動時驗證。
  • .env 不進 git，.env.example 進 git；秘密進了歷史就當成已經外洩。
