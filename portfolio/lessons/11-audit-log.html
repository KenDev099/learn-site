階段 B2：平台功能 · 第 11 課

稽核紀錄

你的 SaaS 上線一個月，客戶的管理員寫信來：「我們有一個 project 不見了，是誰刪的？什麼時候？」你打開伺服器的 log，裡面有幾十萬行，沒有租戶欄位，而且保留 7 天的那份已經被輪替掉了。就算找到了，也只能截圖貼給客戶，客戶自己查不到。

這一課就是要讓這封信有答案，而且下一次客戶不用寫信，自己打開後台就查得到。做法是在你的 SaaS 加上 audit 模組，存一份稽核紀錄（audit log）：每一列回答「誰、在什麼時候、對什麼、做了什麼」。整課都圍繞這個「誰刪了 project」的問題推進。B2 階段之後的每個功能（檔案、匯出、方案）都會寫稽核，所以它排在 B2 的第一課。

這課會用到：
  • 第 9 課的 TenantDb.tx()：開一個互動式交易，裡面的每個操作用同一條連線、一起 commit 或一起回滾；開頭用 set_config 設好租戶與使用者。也會用到那課的兩個資料庫角色：migration 用擁有者，API 執行時用受 RLS 限制的 pf_app。
  • 第 10 課的 @Permissions()：在 controller 方法上宣告需要的權限，權限矩陣決定哪些角色有，沒宣告就拒絕。
  • 第 6 課的 x-request-id 與 RequestContext：每個請求一個 id，存在 AsyncLocalStorage 裡；第 8 課再把 tenantId、userId 放進同一個 store，同一個請求裡任何地方都讀得到。
  • 第 8 課的游標分頁：用上一頁最後一筆的 (createdAt, id) 當下一頁的起點。
程式寫在你自己的 SaaS repo。判分時先啟動你的 API，在 learn 資料夾執行 node check.mjs nestjs pf11。練習 4 會用 work/portfolio.json 的 saas.appDatabaseUrl 直連你的資料庫，只查權限、不寫資料。

這課的路線：

  • log 為什麼回答不了客戶的問題，稽核的一筆要存哪些欄位、哪些絕對不能存（第 1–2 節）。
  • 什麼時候寫才不會跟業務對不上：同一個交易；以及由誰負責呼叫：service、Prisma extension 還是 trigger（第 3–4 節）。
  • 寫進去之後怎麼保證沒人改得掉：在資料庫收回 UPDATE、DELETE（第 5 節）。
  • 客戶的管理員怎麼自己查、資料要存多久，最後套到你的業務模組（第 6–7 節）。

為什麼伺服器的 log 回答不了「誰刪的」？

先看開場那份 log 為什麼派不上用場。伺服器的 log 是寫給工程師除錯用的：哪個請求進來、花了多久、丟了什麼錯。它的設計目標是「出事時工程師查得到細節」，所以有幾個特性，剛好跟客戶的需求相反。

第一，log 會被刪。log 寫得很快、量很大，為了不塞爆磁碟，會定期把舊的檔案切掉、只留最近幾天，這叫輪替（rotation）。客戶一個月後才發現 project 不見，那天的 log 早就沒了。第二，log 的格式隨時會改：哪天有人調整了 log 的欄位，沒有人會覺得這是破壞相容。第三，log 沒有租戶隔離：一行 log 裡混著所有租戶的請求，就算加上 tenantId，你也不可能把整份 log 開給客戶查。所以就算找到那一行，你也只能截圖貼給客戶。

稽核紀錄是另一種東西：它是產品功能，不是除錯工具。它存在資料庫的一張表裡，有固定的欄位與 action 名稱（寫在契約裡，不能隨便改），依租戶隔離，有權限控管（誰能看），有明確的保存期限，客戶的管理員可以自己在後台查。它只記「已經成功的、有業務意義的事」，例如「某人刪除了某個 project」，不記請求花了幾毫秒。

兩者不是二選一，而是分工，靠 requestId 串起來。客戶在稽核裡看到「12:03 某人刪除 project」，回報說「我們沒有人按刪除」；你拿那一筆的 requestId 去 log 查，就找得到同一個請求的所有細節：從哪個 IP 來、帶的是哪個 token、經過哪些步驟（log 怎麼查是第 16 課）。前提是那天的 log 還在；就算不在了，稽核那一筆仍然回答了「誰、什麼時候」。

所以要回答客戶，需要一張專門的表。下一個問題是：這張表的每一列要存什麼？

一筆稽核紀錄要存哪些欄位，哪些絕對不能存？

從客戶的問題倒推：「誰刪的、什麼時候」需要做事的人與時間，「刪了什麼」需要動作與被操作的東西，再加上隔離用的租戶，以及串到 log 的 requestId。每一列代表一件已經成功的事。契約（SaaS 契約的「稽核 action」）規定了欄位與 action 名稱：

欄位存什麼回答哪個問題
tenantId哪個租戶隔離用，API 不回傳
actorId做這件事的使用者 id誰
action<資源>.<動作>，例如 project.deleted、member.role_changed做了什麼
targetType、targetId被操作的東西，例如 project 與它的 id對什麼
requestId那次請求的 x-request-id從哪個請求來：拿它去 log 查細節（第 16 課）
createdAt寫入時間什麼時候

開場那封信，有了這張表就是一列：action = 'project.deleted'、targetId 是那個 project 的 id、actorId 是按下刪除的人、createdAt 是時間。客戶要的答案全在裡面，而且這一列會一直留到保存期限。

不記的東西跟記的東西一樣重要：密碼、token、個資的值都不能進稽核。原因在稽核的三個特性：它保存得比業務資料還久、會被客戶的管理員讀、會被匯出成檔案帶走。裡面只要有一個密碼雜湊或 refresh token，就多了一個外洩的地方，而且這個地方存得最久、看得到的人最多（auth 課第 23 課）。

所以稽核只記 id。member.role_changed 記被改的那個人的 userId，不記他的 email；後台要顯示名字時，查的時候再用 userId JOIN 使用者表。這樣那個人改了 email 或刪了帳號，稽核裡也不會留著他的個資。同樣的道理，要記「改了什麼」時只記欄位名稱（["name", "archived"]），不記舊值與新值：舊值本身可能就是個資。

action 的名稱是契約的一部分，客戶會拿它篩選、寫進自己的流程，拼錯一個字就等於少記一種操作。參考實作把所有 action 寫成一個 TypeScript 型別，拼錯就編譯不過：

// src/audit/audit.service.ts
export type AuditAction =
  | 'project.created' | 'project.updated' | 'project.deleted'
  | 'member.role_changed' | 'member.removed'
  | 'invitation.created' | 'invitation.revoked' | 'invitation.accepted'
  | 'file.uploaded' | 'file.deleted' | 'export.requested' | 'billing.plan_changed'
  | …                                        // tag.*：示範用的第二個業務模組

欄位定好了，但表格上面那句「每一列代表一件已經成功的事」還沒有保證。刪除失敗了卻留下 project.deleted，或刪除成功了卻沒有紀錄，客戶拿到的答案都是錯的。下一節處理「什麼時候寫」。

稽核什麼時候寫，才不會跟業務對不上？

「什麼時候寫」是這一課最容易做錯的地方。先看一個看起來很合理的寫法：先記稽核，再做事，兩者各自開一個交易：

// 錯誤：稽核在自己的交易裡先 commit 了
await this.db.tx(tx => this.audit.record(tx, 'project.updated', 'project', id))
return this.db.tx(async tx => { … if (!count) throw notFound() … })

PATCH 一個不存在的 id：第一個交易已經 commit，稽核裡多了一筆 project.updated；第二個交易找不到資料，客戶收到 404。稽核說「改了」，實際上什麼都沒改。

那反過來，先做事、交易 commit 之後再記呢？大部分時候沒問題，但 commit 和記稽核之間只要程序掛掉（部署重啟、記憶體不足被系統砍掉），或記稽核那一步丟錯，資料已經刪了，稽核卻沒有這一筆。偏偏這種「少一筆」最難發現：沒有錯誤畫面、沒有人抱怨，直到客戶來問「誰刪的」，你才發現答不出來。

兩種寫法的毛病一樣：業務與稽核是兩次獨立的寫入，中間任何一步失敗，兩邊就對不上。所以規則只有一條：業務改了、稽核沒寫，或稽核寫了、業務沒改，兩種都不能發生。資料庫剛好提供這個保證：把兩次寫入放進同一個交易，它們就一起 commit 或一起回滾，不會只成功一半。這就是第 9 課 TenantDb.tx() 給你的東西。

規則有了，接下來要讓它「不可能被寫錯」。參考實作的 AuditService.record() 第一個參數只收交易物件 tx，不收一般的 client：手上沒有 tx 就呼叫不了，也就不可能在交易外面記稽核。誰做的、哪個請求，從 RequestContext 拿，呼叫的人只要給 action 與目標：

// src/audit/audit.service.ts
@Injectable()
export class AuditService {
  constructor(private readonly ctx: RequestContext) {}

  async record(tx: Tx, action: AuditAction, targetType: string, targetId: string) {
    await tx.auditLog.create({
      data: { tenantId: this.ctx.tenantId!, actorId: this.ctx.userId!, action, targetType, targetId, requestId: this.ctx.requestId },
    })
  }
}

@Global()
@Module({ providers: [AuditService], exports: [AuditService] })
export class AuditCoreModule {}

AuditCoreModule 標成 @Global()，是因為每個業務模組都要寫稽核，這樣不用在每個模組各 import 一次；模組怎麼拆見課末「補充與查表」。業務的 service 這樣用，record 放在交易的最後一步：

// src/projects/projects.service.ts
async update(id: string, dto: UpdateProjectDto) {
  return this.db.tx(async tx => {
    const { count } = await tx.project.updateMany({ where: { id }, data: { … } })
    if (!count) throw notFound()              // 不存在或別的租戶的：丟錯，整個交易回滾
    await this.audit.record(tx, 'project.updated', 'project', id)   // 最後一步：前面都成功才寫
    return projectView(await tx.project.findUniqueOrThrow({ where: { id } }))
  })
}

放在最後一步，是讓「前面都成功才寫」在讀程式時一眼看得出來。真正的保證還是交易：就算 record 之後的那行出錯，稽核也會跟著回滾。用這個寫法再看一次失敗的請求，三種情況都不會留下紀錄：

  • 400 驗證失敗、403 沒有權限：ValidationPipe 與 AccessGuard 在 controller 之前就擋下，service 根本沒執行。
  • 404、409 這類業務錯誤：在交易裡丟錯，稽核還沒寫；就算寫了也一起回滾。
  • commit 失敗（死結、連線斷了）：兩者一起消失，客戶收到 500，稽核也沒有這件事，這是對的。

練習 3 測的就是這張清單：送一堆會失敗的請求，之後稽核裡不能有任何 project.*。

record() 一定要用 db.tx() 給的 tx。第 9 課講過，db.client（每個操作各自包一個交易的那個 client）不能拿來開互動式交易：在它的 $transaction(async tx => …) 裡，每個操作仍會各自開交易、各拿一條連線，回滾不了。
💡 實務上：稽核是業務需求，不是除錯工具
B2B 的客戶在採購時常會問「有沒有稽核紀錄、保存多久、能不能匯出」。很多客戶也會要求供應商提供 SOC 2 報告：那是第三方會計師依一套標準檢查公司資安控管後出的報告，裡面同樣會問稽核紀錄。所以 PM 會關心 action 的命名（客戶看得懂嗎），資安會關心裡面有沒有個資。寫新功能時把「這個操作要不要記、action 叫什麼」放進需求清單；code review 時看到改資料的 service 方法沒有 audit.record 就留言：這正是開場那封信答不出來的原因。

寫的時機解決了。但這個寫法要求每個改資料的 service 方法都記得呼叫 record，下一節看能不能讓它自動發生。

誰負責呼叫 record：service、Prisma extension 還是 trigger？

上一節的寫法靠人記得：新增一個刪除端點卻忘了 record，那種刪除就永遠查不到是誰做的。能不能讓稽核自動發生？有兩個自動的位置可以考慮。

一個是 Prisma extension：第 8 課用 $extends 攔下每個查詢、自動加上 tenantId 條件，同樣的機制也能在每個 create、update、delete 之後自動寫一筆稽核。另一個是 PostgreSQL 的 trigger（PostgreSQL 課第 23 課）：掛在資料表上、資料一變動就由資料庫自動執行的函式，連應用程式以外的寫入都攔得到。三種位置各有代價：

做法優點代價
service 明確呼叫 audit.record(tx, …)（參考實作）action 是業務語言（invitation.accepted，不是「invitations 表 UPDATE」）；看程式就知道記了什麼新功能可能忘了寫，要靠 code review 與練習 1 這類測試
Prisma extension 在每個 create／update／delete 後自動記不會忘只知道「哪張表、哪個操作」，不知道業務意思；$queryRaw 與 updateMany 拿不到每一列的 id；一個業務動作會變成好幾筆
PostgreSQL trigger連手動 SQL、別的服務寫的資料都記得到拿不到 actor 與 requestId，除非應用程式先 set_config；邏輯分散在 migration 裡

表中「業務意思」的差別，拿接受邀請來看最清楚。這一個動作至少會改邀請的狀態、新增一筆成員。extension 與 trigger 看到的是兩張表各一次寫入，記成「邀請表 UPDATE」「成員表 INSERT」這樣的好幾筆；客戶要的是一筆 invitation.accepted，actor 是新成員。這層翻譯只有 service 做得到，因為只有它知道這幾次寫入合起來是什麼意思。

trigger 拿不到 actor 的問題，你在第 9 課其實已經鋪好了解法：TenantDb 每個交易開頭除了 app.tenant_id，也設了 app.user_id（src/prisma/tenant-db.ts 的 setContext）。trigger 裡讀 current_setting('app.user_id', true) 就是這次操作的人。所以 trigger 不是做不到，而是它記到的是「資料表變了」，不是「使用者做了什麼」。

作品選 service 明確呼叫：要的是客戶看得懂的紀錄，「忘了寫」這個代價用練習 1 這類測試與 code review 來補。現在稽核會在對的時機、用業務語言寫進去了；但寫進去之後，誰能把它改掉或刪掉？

寫進去的紀錄，怎麼保證沒人改得掉？

稽核寫進去了，還要確定沒有人改得掉，包括你自己的程式。一個條件寫錯的 deleteMany、一段被 SQL injection 的查詢，都可能把紀錄刪掉。更麻煩的是：會想刪稽核的人，通常就是做了壞事的那個人。如果開場那個刪 project 的人也能刪掉 project.deleted 那一筆，稽核就失去意義。

「程式裡不寫刪除稽核的程式碼」擋不住這些情況：bug 與 injection 本來就不照你的約定走。規則要放在比程式更底層的地方，也就是資料庫的權限。PostgreSQL 的每個角色，對每張表有哪些操作可以做，是用 GRANT（給權限）與 REVOKE（收回權限）決定的；沒有權限的操作，不管 SQL 從哪裡來，資料庫都直接拒絕。所以做法是：應用程式執行時用的角色（第 9 課的 pf_app；練習題裡寫成 app_user 的，指的也是這個角色）對稽核表只有 SELECT 與 INSERT，能讀、能新增，不能改、不能刪。這叫「只能追加」（append-only）。

參考實作寫在 migration 最後的手寫段落：

-- prisma/migrations/20261119000000_init/migration.sql（手寫段落）
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO pf_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO pf_app;
-- 稽核紀錄只能追加
REVOKE UPDATE, DELETE ON "audit_logs" FROM pf_app;

第一行把四種權限給到目前所有的表。第二行讓之後由同一個角色建立的新表，也自動給 pf_app 這四種權限，不用每加一張表就補一次 GRANT。第三行才是重點：只對 audit_logs 收回 UPDATE 與 DELETE。

順序不能反。權限是依序套用的，先 REVOKE、再寫 GRANT … ON ALL TABLES，後面那行會把稽核表的 UPDATE、DELETE 加回去。同樣的事也會發生在以後：哪天另一個 migration 又寫了 GRANT … ON ALL TABLES，稽核表的權限也會一起被給回去，所以那個 migration 結尾要再 REVOKE 一次。

另外，四種權限是一個一個列出來的，沒有用 GRANT ALL。GRANT ALL 除了這四種，還會一起給 TRUNCATE（以及 REFERENCES、TRIGGER 等這課用不到的權限）。TRUNCATE 是一次清空整張表，不用逐列刪除。上面的 REVOKE 只收回 UPDATE、DELETE，如果一開始用了 GRANT ALL，pf_app 仍然可以一句話清空整張稽核表。只列四種，TRUNCATE 從一開始就沒給。

寫好之後要驗證，不要只相信 migration 跑過了。用 app 角色連上資料庫，直接問 PostgreSQL 這個角色有沒有權限（練習 4 的測試就是這樣查）：

SELECT has_table_privilege('audit_logs', 'INSERT'),          -- t
       has_any_column_privilege('audit_logs', 'UPDATE'),     -- f（連單一欄位都不能改）
       has_table_privilege('audit_logs', 'DELETE');          -- f

這個保護還有一個前提：API 真的用 app 角色連線。superuser 跳過所有權限檢查；表的擁有者天生擁有自己表上的全部權限，對 pf_app 做的 REVOKE 管不到它。如果 PrismaService 用的是擁有者的 DATABASE_URL，權限收得再乾淨也沒用。怎麼確認？PostgreSQL 有一個系統視圖 pg_stat_activity，列出目前每一條連線與它用的角色（第 9 課用過）。練習 4 第二個測試會先打一次 API 讓它建立連線，再查這個視圖：連著你的資料庫的，只能是 appDatabaseUrl 的那個角色。

擁有者還是刪得掉，這是故意的：保存期限到了要清舊資料，是一個用擁有者身分跑的排程（或直接丟掉整個分割，見練習 7），不是 API。這樣「誰能刪稽核」就縮小成「誰拿得到擁有者的密碼」，那是基礎設施的權限管理（devops 課第 11 課）。

資料現在寫得對、改不掉。接下來回到開場：客戶不想寫信問你，想自己查。

客戶的管理員怎麼自己查？

契約是 GET /api/v1/audit-logs?action=&cursor=：新的在前，可以用 action 篩選，admin 以上可讀。客戶的管理員打開後台的「稽核紀錄」頁，篩選 project.deleted，就看到開場那封信的答案。

稽核只會一直變多，一個租戶一年可能有幾萬筆，所以一定要分頁。這裡沿用第 8 課的游標分頁：游標是上一頁最後一筆的 (createdAt, id)，下一頁從它之後接著拿。共用的三個函式是 decodeCursor()（把客戶傳來的游標字串解回 (createdAt, id)）、after()（產生「在這筆之後」的 where 條件）與 page()（組出回應與下一頁的游標）。查詢時多拿一筆（take: limit + 1），是為了知道還有沒有下一頁：拿到 limit + 1 筆就代表還有。參考實作整個 controller：

// src/audit/audit.controller.ts
export class AuditQuery {
  @IsOptional() @Matches(/^[a-z_]+\.[a-z_]+$/) action?: string
  @IsOptional() @IsString() cursor?: string
  @IsOptional() @Type(() => Number) @IsInt() @Min(1) @Max(100) limit?: number
}

@Controller('audit-logs')
export class AuditController {
  constructor(private readonly db: TenantDb) {}

  @Permissions('audit:read')
  @Get()
  async list(@Query() q: AuditQuery) {
    const limit = q.limit ?? PAGE
    const rows = await this.db.client.auditLog.findMany({
      where: { ...(q.action ? { action: q.action } : {}), ...after(decodeCursor(q.cursor), 'desc') },
      orderBy: [{ createdAt: 'desc' }, { id: 'desc' }],
      take: limit + 1,
    })
    return page(rows, limit, r => ({ id: r.id, actorId: r.actorId, action: r.action, … }))
  }
}

這段程式短，但每一行都對應一個要求：

  • 隔離：用 TenantDb，AuditLog 在它的自動條件清單裡，RLS 再擋一次。查詢沒有寫 tenantId，這是對的；寫了 PrismaService 才是錯的（練習 2）。
  • 權限：audit:read 只在 admin 與 owner 的清單裡（src/tenancy/permissions.ts）。稽核裡有「誰把誰降級」，member 看得到就洩漏了管理動作。
  • 分頁：跟 projects 共用 src/common/cursor.ts，只是方向是 desc。schema 的 @@index([tenantId, createdAt, id]) 讓「這個租戶、最新的 20 筆」不用掃全表。
  • 篩選：action 用正規表示式驗證格式，不合法的 400，而不是查出空陣列讓人以為沒有紀錄。

「只會一直變多」也帶出最後一個問題：要存多久？這一課不實作保存期限與匯出，但要把決定寫進你的 ADR（例如 docs/adr/000N-audit-log.md）：保存多久（常見是 1 年，看客戶合約與法規）、過期怎麼刪（擁有者身分的排程，或依月份分割後丟掉舊分割）、客戶要怎麼拿走（匯出，第 13 課的機制可以重用）。面試時被問「稽核表很大怎麼辦」，ADR 裡有答案。

💡 實務上：稽核會被拿來當證據
開場那封「誰刪的」只是最輕微的版本。客戶之間的糾紛（「不是我刪的」）、離職員工的權限爭議、資安事件調查，最後都會回到稽核。到那時候才發現少記一種操作、或 actor 記成系統帳號，已經補不回來。資深工程師上線前會列一張「改資料的端點 × 有沒有稽核」的表，並問客服與 PM：「客戶最常問哪三種『誰做的』？」先保證那三種一定記得到。

平台的稽核到這裡完整了：寫得對、改不掉、查得到。剩下的是讓你自己的業務模組也照這個方式記。

你的業務模組要記哪些 action？

規則跟 projects 一樣：每個改資料的 service 方法，在 db.tx() 的最後一步 audit.record，新的 action 加進 AuditAction 型別。三個建議題目各有一個要想清楚的地方：

  • 客服工單：狀態機的每一步都是一個 action（ticket.assigned、ticket.status_changed）。SLA 到期的自動升級是背景工作做的，actor 是誰？不要用一個假的使用者 id 冒充，第 13 課會講 worker 的上下文怎麼帶；稽核表的 actorId 可以改成允許空值、另加 actorType（user／system）。
  • 預約排程：取消是客戶最常爭議的操作，booking.cancelled 要記是誰取消的（本人、管理員），取消原因如果有個資就不記內容。
  • 進銷存：庫存異動表（入庫、出庫）本身就是只追加的帳本，它是業務資料，不是稽核；稽核記的是「誰建立了這筆異動」。不要把兩者合成一張表：帳本要能做庫存計算，稽核要能長期保存與匯出，需求不一樣。

練習

練習 1：加上 audit 模組，讓建立、修改、刪除 project，修改成員角色，建立與接受邀請，各寫一筆契約規定的 action。測試會檢查每種恰好一筆、actorId 是做這件事的人（接受邀請的 actor 是新成員）、targetId 正確、project.created 的 requestId 等於那次回應的 x-request-id、列表新的在前、?action= 只回那一種。

練習 2：GET /api/v1/audit-logs 只回自己租戶的紀錄（另一個剛註冊的租戶看到空陣列），owner 與 admin 200，member、viewer 403 FORBIDDEN，沒登入 401。

練習 3：失敗的操作不能留下紀錄。測試會送空白名稱（400）、viewer 建立（403）、修改與刪除不存在的 id 與別的租戶的 project（404），之後稽核裡不能有任何 project.*。

練習 4：在 migration 收回 app 角色對稽核表的 UPDATE、DELETE（TRUNCATE 也不能有）。在 work/portfolio.json 填好 saas.appDatabaseUrl（第 9 課），測試會用它連線檢查權限，並確認 API 實際也是用這個角色連線。

練習 5：同事提議把稽核改成事件：service 在交易 commit 之後 eventEmitter.emit('project.deleted', …)，由 listener 寫稽核，「這樣 service 比較乾淨」。這個改法會漏掉什麼？

✓ 稽核與業務分成兩次寫入，中間任何失敗都會讓兩者不一致，而缺的那一筆剛好是最需要的。要分開寫就得用 outbox（同一個交易寫進 outbox 表、再非同步處理），複雜度比直接在交易裡 record(tx, …) 高很多。d 不對：listener 在同一個請求的 ALS 裡同步執行時讀得到上下文，問題不在這裡。（第 11 課）

練習 6：你的進銷存模組有些庫存調整是營運同事用 SQL 腳本直接改的，service 的 audit.record 記不到。你想加一個 trigger 補記，但 trigger 裡要知道是誰改的。哪個做法可行？

✓ 交易層級的設定是應用程式與資料庫之間傳上下文的標準做法，參考實作的 setContext 已經同時設了 app.tenant_id 與 app.user_id。b 錯在前提：API 所有請求共用同一個 app_user 角色，current_user 永遠是它，分不出使用者。（第 11 課）

練習 7：一年後 audit_logs 有 3 億列，合約規定保留 13 個月。每晚 DELETE … WHERE created_at < now() - interval '13 months' 跑了好幾個小時，還讓資料表膨脹。比較好的做法是？

✓ 丟掉一個分割是改目錄資訊，不會逐列刪除、也不會留下要 VACUUM 的死列（PostgreSQL 課第 35 課），而且一樣不需要把刪除權限還給應用程式。a 讓「只能追加」的保護失效。c 只讓找到要刪的列變快，3 億列的逐列刪除與膨脹還在。d 會把還在保存期限內的紀錄一起刪掉。（第 11 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • 每個改資料的端點都有 action：列出你所有的 POST／PATCH／DELETE，每個對到一個 action 或寫明為什麼不記。業務模組的 action 也在 AuditAction 型別裡。
  • 稽核真的跟業務一起回滾：在 projects.service.ts 的 audit.record 之後暫時加一行 throw new Error()，呼叫一次，資料庫裡 project 沒變、稽核也沒有新的一筆。
  • 沒有個資與秘密：SELECT DISTINCT target_type, action FROM audit_logs 看一遍，沒有任何欄位存了 email、密碼雜湊、token。
  • 測試抓得到漏記：把 members.service.ts 改角色的 audit.record 刪掉，你自己的 npm test 至少有一個測試失敗。
  • ADR 寫了保存期限：保存多久、怎麼刪、客戶怎麼匯出。

常見錯誤

  • 稽核寫在交易外：先記再做、或 commit 之後才記，失敗或當機時兩邊對不上。record() 只收 tx，放在交易的最後一步。
  • 用 db.client 開互動式交易再呼叫 record：每個操作各自一個交易，回滾不了。用 db.tx()。
  • 查詢用 PrismaService：沒有自動的租戶條件；如果 API 又用 superuser 連線，RLS 也擋不到，別的租戶的稽核全部看得到。
  • 只在程式裡「不呼叫」刪除：只能追加要靠資料庫權限，程式的約定擋不住 bug 與 injection。REVOKE 寫在 migration，之後的 GRANT … ON ALL TABLES 後面再 REVOKE 一次。
  • 收回了權限，API 卻用擁有者連線：擁有者不受 GRANT 限制。API 一律用 app 角色，擁有者只給 migration 與保存期限的排程。
  • 把 email、舊值新值整包記進去：稽核保存得比業務資料久，個資會在這裡留到過期。記 id 與欄位名稱。

補充與查表

  • 稽核的模組怎麼拆：寫入用的 AuditService 放在 @Global() 的 AuditCoreModule，每個業務模組直接注入、不用 import。查詢的 controller 放在另一個 AuditModule，這樣業務模組只依賴「寫稽核」這一小塊，平台模組的依賴方向不變（docs/architecture.md）。
  • 這課用到的資料表權限（查表用，不用背）：SELECT 讀、INSERT 新增、UPDATE 修改、DELETE 逐列刪除、TRUNCATE 一次清空整張表。GRANT ALL 會連 TRUNCATE（還有 REFERENCES、TRIGGER 等）一起給，所以參考實作逐一列出。
  • ADR 要回答的三件事：保存多久（看客戶合約與法規）、過期怎麼刪（擁有者身分的排程，或依月份分割後丟掉舊分割，見練習 7 與 PostgreSQL 課第 35 課）、客戶怎麼匯出（第 13 課的背景工作）。

小結

  • log 是給工程師除錯的，會被輪替、沒有租戶隔離、客戶看不到；稽核是產品功能，存在資料庫、依租戶隔離、有權限與保存期限，兩者用 requestId 串起來。
  • 稽核回答「誰、什麼時候、對什麼、做了什麼」：actorId、action（<資源>.<動作>）、target、requestId、時間。只記 id，不記密碼、token、個資的值。
  • 稽核跟業務在同一個交易：record(tx, …) 只收交易物件，放在最後一步；失敗的操作一起回滾，不會留下成功的紀錄。先記再做、或 commit 之後才記，都會讓兩邊對不上。
  • service 明確呼叫記得到業務意思；extension 與 trigger 不會忘，但只知道資料表變了。trigger 要 actor 就靠 set_config('app.user_id', …, true)。
  • 只能追加靠資料庫：migration 先 GRANT、再 REVOKE UPDATE, DELETE，不用 GRANT ALL；而且 API 真的要用 app 角色連線。
  • 查詢 API 用 TenantDb、admin 以上、游標分頁新的在前；保存期限與刪除方式寫進 ADR。
