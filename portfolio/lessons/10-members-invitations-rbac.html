階段 B1：多租戶 SaaS 的平台地基 · 第 10 課

成員、邀請與租戶內 RBAC

到第 9 課為止，每個租戶只有一個人：註冊時建立它的 owner。真實的團隊不是這樣。好日子咖啡的老闆陳美華在 my-saas 開了租戶，她是 owner。月底要結帳，她想請會計師林雅婷（第 7 課註冊、自己開了事務所租戶的那位）以 admin 的身分進來整理帳目一個月；店長黃淑芬也要進來，以 member 的身分建專案、上傳檔案。林雅婷已經有帳號，黃淑芬還沒有。一個月後合作結束，陳美華會把林雅婷移出租戶。

這一課的任務：讓陳美華安全地走完這整件事。一路上要回答五個問題：怎麼把人拉進來，又不讓邀請連結被冒用；林雅婷同時屬於兩個租戶時怎麼切換；進來之後誰能做什麼；身為 admin 的林雅婷能不能把自己升成 owner；陳美華移除她的下一秒，她手上那張還沒過期的 access token 是不是真的失效了。最後一個問題是第 7 課留下的洞：access token 撤銷不了。這一課補洞的做法是 guard 每個請求都查一次成員身分，角色以資料庫為準，不信 token。這是階段 B1 的最後一課，最後有階段檢核。

這課會用到：
  • auth 課第 18 課：角色不是權限，程式只問「有沒有這個權限」；每個路由都要有政策，沒宣告就拒絕。
  • auth 課第 16 課的一次性 token 四個條件：只存雜湊、用過就失效、會過期、可以撤銷；信裡的連結不用請求的 Host。
  • auth 課第 11 課：JWT 撤銷不了，要嘛縮短效期、要嘛每個請求查一次狀態。
  • 第 7 課的全域 guard 與 @Public()、@Authenticated()、@Permissions() 三種宣告；第 9 課「還沒有租戶的路徑」怎麼設上下文。

這課的路線：

  • 陳美華要邀請林雅婷：邀請連結要防什麼？信寄失敗時邀請算不算數？
  • 林雅婷點了連結：已有帳號和沒有帳號的人怎麼加入，同一個連結怎麼保證只能用一次？
  • 林雅婷現在屬於兩個租戶：怎麼從事務所切到好日子咖啡？
  • 進來之後誰能做什麼：權限矩陣、每個請求查角色的 guard；admin 能不能把自己升成 owner？
  • 一個月後移除林雅婷，她手上的 token 會立刻失效嗎？最後套到你的業務模組，做階段檢核。

陳美華要邀請林雅婷：邀請連結要防什麼？

最直覺的做法是讓陳美華輸入林雅婷的 email，系統直接替那個帳號建一筆 membership。問題是系統不知道這個 email 背後是不是陳美華以為的那個人：她可能打錯一個字，把好日子咖啡的帳目開放給一個陌生人；對方也沒有機會說「我不要加入」。所以加入要由被邀請的人自己完成，而且要先證明「這個信箱是我的」。

證明信箱屬於誰，標準做法是寄一封信過去，信裡帶一個只有系統知道的隨機值，也就是 token。能點開信裡連結的人，就是收得到這個信箱的人。整個流程是：

  1. admin 以上的人（這裡是陳美華）輸入 email 與角色。
  2. 系統產生 token、把它的雜湊存進 invitations 表、把 token 原文放進連結寄出。
  3. 林雅婷點信裡的連結，打開前端的接受邀請頁，前端把 token 送到 POST /api/v1/auth/invitations/accept。
  4. API 確認 token 有效，建立 membership，林雅婷成為成員。

這個 token 等於一把「以 admin 身分加入好日子咖啡」的臨時鑰匙。誰拿到它，誰就能用它指定的角色進來。所以它要滿足 auth 第 16 課重設密碼 token 的四個條件，每一條都對應一種被冒用的方式：

條件沒做到會怎樣參考實作怎麼做
只存雜湊資料庫或備份外洩，所有還沒接受的邀請都能被拿去冒用invitations.token_hash 存 SHA-256；資料庫外洩也拿不到能用的連結
用過就失效同一封信可以一直用；被移除的人點舊連結就回來了接受時條件式更新 acceptedAt（只有 acceptedAt IS NULL 的列會被改到），再用一次回 410 INVITATION_USED
會過期半年前寄出、沒人點的信，任何時候被翻出來都還能用expiresAt 是 72 小時後；過期回 410 INVITATION_EXPIRED
可以撤銷寄錯人或改變主意時，只能等它過期DELETE /api/v1/invitations/:id 設 revokedAt；同一個 email 重新邀請時舊的自動撤銷；撤銷後回 410 INVITATION_REVOKED

為什麼這裡用 SHA-256 這種快雜湊，而不是密碼用的慢雜湊？auth 第 16 課講過：token 是 32 bytes 的安全亂數，不像密碼可以拿字典猜，快雜湊就夠了。

建立邀請的程式會用到兩個還沒介紹的東西，先說明。me: Principal 代表「目前是誰、在哪個租戶、什麼角色」，內容是 { userId, tenantId, role }。guard 驗完 token 之後把它放進 req.auth，controller 用參數 decorator @CurrentUser() 取出來傳給 service；guard 怎麼填它，在後面「誰能做什麼」那一節。rank(role) 把角色換成一個數字，viewer 最小、owner 最大，用來比較兩個角色誰高；它也定義在那一節。

// src/members/invitations.service.ts（節錄）
const TTL_MS = 72 * 60 * 60 * 1000

async create(me: Principal, dto: InviteDto) {
  if (rank(dto.role) > rank(me.role)) throw forbidden('不能邀請比自己高的角色')
  const token = `${me.tenantId}.${randomBytes(32).toString('base64url')}`
  const invitation = await this.db.tx(async tx => {
    const limits = await lockTenant(tx, me.tenantId)                       // 第 14 課：成員數上限
    const existing = await tx.user.findUnique({ where: { email: dto.email } })
    if (existing && await tx.membership.findFirst({ where: { tenantId: me.tenantId, userId: existing.id } })) {
      throw new ApiError(409, 'ALREADY_MEMBER', '這個人已經是成員')
    }
    // 同一個 email 重新邀請：舊的撤銷，只留最新的一封有效
    await tx.invitation.updateMany({ where: { email: dto.email, acceptedAt: null, revokedAt: null }, data: { revokedAt: new Date() } })
    …
    return tx.invitation.create({
      data: { tenantId: me.tenantId, email: dto.email, role: dto.role, tokenHash: sha256(token), invitedBy: me.userId, expiresAt: new Date(Date.now() + TTL_MS) },
    })
  })
  // 連結的網址來自設定，不來自請求的 Host 標頭
  const link = `${this.appUrl}/invitations/accept?token=${encodeURIComponent(token)}`
  await this.mail.send(dto.email, '你被邀請加入團隊', `點這個連結接受邀請（72 小時內有效）：\n${link}\n`)
  return view(invitation)
}

由上往下讀：

  • 第一行先擋「邀請比自己高的角色」：admin 不能發一封「以 owner 加入」的邀請。這是後面「角色規則」一節的第一條規則，邀請時就要檢查，否則 admin 邀一個自己的分身當 owner，就繞過了所有規則。
  • lockTenant 鎖住租戶列，第 14 課會用它檢查成員數上限，這裡先放著。
  • 對方已經是這個租戶的成員，回 409 ALREADY_MEMBER。
  • 同一個 email 還有沒接受、沒撤銷的舊邀請，一律撤銷，只留最新的一封有效。陳美華第一次填錯角色、重發一次，舊信就作廢了。
  • 存進資料庫的是 sha256(token)，token 原文只出現在信裡。

token 的格式和連結的網址，是這段程式裡兩個只有 SaaS 才會遇到的決定。

第一個決定：token 開頭是 tenantId，例如 <好日子咖啡的 id>.<隨機值>。原因在接受邀請的那一刻。林雅婷點連結時，可能還沒登入好日子咖啡，黃淑芬甚至還沒有帳號，請求裡沒有任何 access token，API 不知道這個請求屬於哪個租戶。而 invitations 表開了 RLS（第 9 課）：沒有租戶上下文時一列都不給。只拿雜湊去查，會查到 0 筆。所以 token 自己帶著租戶：API 先從 token 取出租戶設進上下文，再用雜湊在這個租戶裡找。tenantId 不是秘密，看到它也不能做什麼；秘密是後面的隨機值。

第二個決定：連結的網址來自設定的 APP_URL，不來自請求。一個理由是前端網址跟 API 的網址本來就不一樣。更重要的理由是安全：Host、X-Forwarded-Host 這些標頭是發請求的人自己填的。如果連結用請求的 Host 組，攻擊者用自己的帳號、帶著 Host: evil.example 發一個邀請請求，系統就會從正牌的寄件地址寄出一封信，連結卻指向攻擊者的網站。收信的人看到寄件人可信，點下去，token 就送到攻擊者手上。這叫 host header injection。驗收測試會用 Host: evil.example 發邀請，檢查信裡的網址。

邀請存好了、連結也組好了，最後一步是把信寄出去。寄信要連到另一個系統（郵件伺服器），它跟資料庫不在同一個交易裡，所以要決定：寄信失敗時，這筆邀請算不算數？

信要怎麼寄出去？寄信失敗時邀請算不算數？

寄信用 nodemailer，它透過 SMTP（寄信用的協定）把信交給郵件伺服器。開發時交給第 6 課 compose 裡的 Mailpit：它是假的郵件伺服器，收下所有信、顯示在自己的網頁上，不會真的寄到任何人的信箱，你可以在那裡點開邀請信、拿到連結。正式環境只要把 SMTP_URL 換成寄信服務商的位址，程式不用改：

// src/members/mail.service.ts（節錄）
constructor(config: ConfigService<Env, true>) {
  this.transport = createTransport(config.get('SMTP_URL', { infer: true }))   // 開發：smtp://127.0.0.1:1027
  this.from = config.get('MAIL_FROM', { infer: true })
}
async send(to: string, subject: string, text: string) {
  await this.transport.sendMail({ from: this.from, to, subject, text })
}

回頭看上一節的 create：mail.send 寫在 this.db.tx(…) 結束之後，不在交易裡。這個順序決定了兩種失敗的後果：

  • 交易失敗（例如對方已經是成員，回 409 ALREADY_MEMBER）：交易回滾、邀請沒有建立，信也不會寄出。如果反過來先寄信、再寫資料庫，就可能寄出一封指向不存在邀請的信，對方點了只會看到 404。
  • 交易成功、寄信失敗（例如郵件伺服器暫時連不上）：邀請已經存在，只是對方沒收到信。陳美華可以重新邀請，舊的那封會被自動撤銷，不會留下兩個有效的邀請。

第二種情況要使用者自己重發，作品專案可以接受。想要自動重試、不讓 API 等郵件伺服器回應，做法見課末「補充與查表」。

信寄到了林雅婷的信箱，她點下連結。接下來要處理的是接受邀請：她已經有帳號，黃淑芬沒有，兩個人要走的路不一樣。

林雅婷點了連結：已有帳號和沒有帳號的人怎麼加入？

接受邀請有兩條路：

  • 已經有帳號的人（林雅婷，她是自己事務所的 owner）只送 token。token 能從她的信箱點出來，已經證明了 email 是她的，直接加入，不用再輸入密碼。
  • 還沒有帳號的人（黃淑芬）要多送 name 與 password，API 在同一個交易裡建立使用者與 membership。兩筆要一起成功：只建了使用者、沒建 membership，她就會有一個登得進去卻不屬於任何租戶的殘缺帳號，跟第 7 課註冊時避開的情況一樣。
// src/members/invitations.service.ts 的 accept（節錄）
const tenantId = dto.token.split('.')[0]
if (!UUID.test(tenantId)) throw new ApiError(404, 'INVITATION_NOT_FOUND', '邀請不存在')
this.ctx.store!.tenantId = tenantId                          // 明確的上下文（第 9 課）
const inv = await this.db.client.invitation.findUnique({ where: { tokenHash: sha256(dto.token) } })
if (!inv) throw new ApiError(404, 'INVITATION_NOT_FOUND', '邀請不存在')
if (inv.revokedAt) throw new ApiError(410, 'INVITATION_REVOKED', '邀請已經被撤銷')
if (inv.acceptedAt) throw new ApiError(410, 'INVITATION_USED', '邀請已經用過')
if (inv.expiresAt <= new Date()) throw new ApiError(410, 'INVITATION_EXPIRED', '邀請已經過期')
let user = await this.db.client.user.findUnique({ where: { email: inv.email } })
if (!user && (!dto.name || !dto.password)) throw new ApiError(400, 'VALIDATION_FAILED', '新帳號要填 name 與 password')
…
return this.db.tx(async tx => {
  // 條件式更新：同一個 token 同時被用兩次，只有一個成功
  const { count } = await tx.invitation.updateMany({ where: { id: inv.id, acceptedAt: null, revokedAt: null }, data: { acceptedAt: new Date() } })
  if (!count) throw new ApiError(410, 'INVITATION_USED', '邀請已經用過')
  user ??= await tx.user.create({ data: { email: inv.email, name: dto.name!, passwordHash } })
  await tx.membership.upsert({ where: { tenantId_userId: { tenantId, userId: user.id } }, create: { tenantId, userId: user.id, role: inv.role }, update: {} })
  …
})

由上往下讀：

  • 從 token 取出 tenantId，先確認它是 UUID 格式，不是就當成邀請不存在。接著把它設進請求上下文，這是第 9 課「還沒有租戶的路徑要明確設上下文」的做法；設了之後 RLS 才讓這個請求看到好日子咖啡的邀請。
  • 用 token 的雜湊找邀請，依序檢查撤銷、用過、過期，各自回不同的錯誤碼。
  • 用邀請上的 email 找使用者。找不到又沒給 name、password，就是新帳號沒填完，回 400。
  • 交易裡先把邀請標成已接受，再建使用者（需要時）與 membership。

這裡有一個容易看錯的地方：前面已經有 if (inv.acceptedAt)，為什麼交易裡又用條件式更新再檢查一次？因為「先查、再改」中間有空檔。林雅婷手滑點了兩次連結，兩個請求幾乎同時到：兩個都先查到 acceptedAt 是空的、都通過前面的檢查，如果接著直接寫入，兩個都會成功。條件式更新把「檢查」和「寫入」合成一句交給資料庫：updateMany 的 where 裡寫了 acceptedAt: null，資料庫只會改到還沒被接受的那一列，回傳實際改到幾列。第一個請求改到 1 列；第二個請求執行時那一列已經不符合條件，改到 0 列，就回 410。第 7 課把 refresh token 標成已使用，用的是同一招。所以前面的 if 只負責給使用者看得懂的錯誤訊息，真正保證「只能用一次」的是交易裡那句條件式更新。

錯誤碼為什麼分 404 和 410？404 是「沒有這個邀請」，可能是連結抄錯了；410（Gone）是「有這個邀請，但已經不能用了」，不管是用過、撤銷還是過期。前端看到 410 可以直接顯示「請管理員重新邀請」，看到 404 則請使用者檢查連結。

林雅婷加入了，資料庫裡她現在有兩筆 membership：事務所的 owner、好日子咖啡的 admin。但她手上的 access token 寫的還是事務所，她要怎麼進到好日子咖啡？

林雅婷現在屬於兩個租戶：怎麼從事務所切到好日子咖啡？

第 7 課的 access token 只裝一個 tid，代表「這張 token 在哪個租戶有效」；登入時取最早加入的租戶，所以林雅婷登入後在事務所。租戶寫在簽過名的 token 裡，使用者改不了，這是第 7 課刻意的設計。所以換租戶不能靠前端在請求上加一個「我要去哪個租戶」的標頭，而是換一張 token：前端告訴 API 想去哪個租戶，API 確認她是那裡的成員，再發一張 tid 是好日子咖啡的新 token。

// src/auth/auth.controller.ts（節錄）
@Authenticated()
@Get('tenants')
tenants(@CurrentUser() me: Principal) {
  return this.auth.tenantsOf(me.userId)              // { items: [{ id, name, role }] }
}

@Authenticated()
@Post('switch-tenant')
@HttpCode(200)
async switchTenant(@CurrentUser() me: Principal, @Body() dto: SwitchTenantDto, @Res({ passthrough: true }) res: Response) {
  if (!(await this.auth.isMember(me.userId, dto.tenantId))) throw forbidden('你不是這個租戶的成員')
  return this.issue(res, me.userId, dto.tenantId)    // 新的 access token＋新的 refresh 家族
}

兩個端點都標 @Authenticated()，不是 @Permissions(…)：它們問的是「你是誰、你屬於哪些租戶」，跟你在目前這個租戶的角色無關。switchTenant 先查 membership，不是成員就拒絕；是成員就發新的 access token，並開一個新的 refresh 家族（第 7 課的 refresh token 輪替）。

不是成員時回 403 而不是 404。一般查資料時回 404 是為了不透露「這筆資料存在」；但這裡的 tenantId 是使用者自己送來、說「我想去這裡」的，回 403 只說明他不能去，沒有透露任何別人的資料。

Vue 前端的做法：租戶下拉選單呼叫 /auth/tenants 列出選項，林雅婷選了好日子咖啡，就呼叫 switch-tenant、換掉記憶體裡的 token，再重新載入頁面資料，因為畫面上的專案、檔案都屬於上一個租戶。

現在林雅婷在好日子咖啡裡，角色是 admin；黃淑芬也進來了，角色是 member。下一個問題：她們各自能做什麼，API 又在哪裡檢查？

進來之後，誰能做什麼？權限矩陣與 guard

最直覺的寫法是在每個路由裡判斷角色名稱，例如 if (role === 'admin' || role === 'owner')。auth 第 18 課講過它的問題：哪天要加一個新角色，就得翻遍整個專案找這些判斷。所以分成兩件事：權限是「能做哪一類動作」，例如 projects:delete；角色只是一組權限的名字。程式只問「這個人有沒有 projects:delete」，角色和權限的對應集中在一個地方。

那個地方就是契約（CONTRACT-saas.md）裡的權限矩陣，寫成一個常數。角色往上累加權限：member 有 viewer 的全部再多一些，admin 有 member 的全部再多一些：

// src/tenancy/permissions.ts
export const ROLES = ['viewer', 'member', 'admin', 'owner'] as const
export type Role = (typeof ROLES)[number]
export const rank = (r: Role) => ROLES.indexOf(r)

const viewer = ['projects:read', 'tags:read', 'files:read', 'exports:read', 'members:read', 'billing:read'] as const
const member = [...viewer, 'projects:write', 'tags:write', 'files:write', 'exports:create'] as const
const admin = [...member, 'projects:delete', 'tags:delete', 'members:write', 'invitations:read', 'invitations:write', 'audit:read'] as const
const owner = [...admin, 'billing:write'] as const

export type Permission = (typeof owner)[number]
export const PERMISSIONS: Record<Role, readonly Permission[]> = { viewer, member, admin, owner }

ROLES 由低到高排列，rank 就是角色在陣列裡的位置，前面邀請時用的比較就是它。Permission 是從陣列推出來的字串聯集，@Permissions('projetcs:write') 拼錯會直接編譯失敗。照這個矩陣，黃淑芬（member）可以建專案、上傳檔案，不能刪專案；林雅婷（admin）還可以刪專案、管理成員、看稽核紀錄；只有陳美華（owner）能改方案與付款。

controller 的每個路由宣告它要的權限：

@Permissions('projects:write') @Post()        create(…)
@Permissions('projects:read')  @Get(':id')    get(…)
@Permissions('projects:delete') @Delete(':id') remove(…)

宣告只是貼在路由上的標籤，真正檢查的是第 7 課的全域 guard。第 7 課的版本只做到「驗 token、把使用者和租戶放進請求上下文」，留了一句「第 10 課：查 membership、比對 @Permissions」。現在把它補完：驗完 token 之後，查資料庫裡現在的 membership，用它的角色比對權限：

// src/tenancy/access.guard.ts（接在第 7 課之後）
// 每個請求都查 membership：被移除的成員，手上還沒過期的 token 立刻失效；角色以資料庫為準
const membership = await this.db.client.membership.findUnique({ where: { tenantId_userId: { tenantId: payload.tid, userId: payload.sub } } })
if (!membership || !isRole(membership.role)) throw unauthenticated()
req.auth = { userId: payload.sub, tenantId: payload.tid, role: membership.role }
if (!access) throw forbidden('這個路由沒有宣告權限')
if ('authenticated' in access) return true
const granted = PERMISSIONS[membership.role]
if (!access.permissions.every(p => granted.includes(p))) throw forbidden()
return true

由上往下讀：

  • 用 token 裡的 tid 與 sub 查 membership。查不到代表這個人已經不屬於這個租戶，回 401：token 本身沒問題，但它指的身分已經不存在了。
  • isRole 確認資料庫裡的角色字串是四種之一。auth 第 18 課講過，資料庫裡的角色名稱不能直接相信，不認得的值不能拿去查權限表。
  • 把 { userId, tenantId, role } 放進 req.auth，這就是前面 @CurrentUser() 取出的 Principal。角色來自剛查到的 membership，不是 token。
  • 路由沒有任何宣告就 403；@Authenticated() 的路由到這裡就放行；@Permissions(…) 要求的每一個權限，這個角色都要有。

「沒宣告就 403」值得多看一眼。新的路由忘了加 @Permissions，所有人都用不了，開發時馬上發現。反過來寫成「沒宣告就放行」，忘了加的路由是所有登入的人都能用，連 viewer 都能打；而且沒有人會抱怨，因為大家都用得了，要等出事才知道。這跟第 7 課「預設要登入，例外要明講」是同一個方向。

guard 管的是「這個角色能不能做這類動作」。「這一筆資料能不能被你動」是另一層，放在 service 的查詢裡：租戶條件（第 8 課），以及業務模組自己的規則（本課後面的「套到你的業務模組」一節）。guard 不讀業務資料，才不會隨著每個模組越長越大。

權限矩陣說 admin 有 members:write，可以改別人的角色。那林雅婷能不能用它把自己改成 owner？矩陣本身擋不住，因為它只回答「能不能改角色」，不回答「能改成什麼」。

林雅婷是 admin：她能不能把自己升成 owner？

如果只看權限矩陣，答案是可以：她有 members:write，改角色的 API 就會放行。升成 owner 之後，她能改付款方式，也能把陳美華降級，好日子咖啡就換了主人。所以「管理成員」要有邊界。三條規則都在 src/members/members.service.ts：

  • 不能指派或邀請比自己高的角色：admin 只能給 viewer、member、admin。林雅婷可以把黃淑芬升成 admin，不能升成 owner，也不能升自己。
  • 不能管理比自己高的人：admin 不能降級或移除 owner。林雅婷動不了陳美華。
  • 最後一位 owner 不能被降級或移除（409 LAST_OWNER）：租戶沒有 owner，就沒人能改方案、沒人能指定新的 owner。陳美華是唯一的 owner，她不能把自己降成 admin，也不能離開。
async changeRole(me: Principal, userId: string, role: Role) {
  return this.db.tx(async tx => {
    const target = await this.find(tx, userId)
    this.assertCanManage(me, target.role as Role)
    if (rank(role) > rank(me.role)) throw forbidden('不能指派比自己高的角色')
    if (target.role === 'owner' && role !== 'owner') await this.assertNotLastOwner(tx)
    await tx.membership.update({ where: { tenantId_userId: { tenantId: me.tenantId, userId } }, data: { role } })
    …
  })
}

// 鎖住所有 owner 的列再數：兩個人同時把對方降級，也不會變成沒有 owner
private async assertNotLastOwner(tx: Tx) {
  const owners = await tx.$queryRaw<{ user_id: string }[]>`SELECT user_id FROM memberships WHERE tenant_id = ${this.tenantId}::uuid AND role = 'owner' FOR UPDATE`
  if (owners.length <= 1) throw new ApiError(409, 'LAST_OWNER', '最後一位 owner 不能被降級或移除')
}

changeRole 依序套用三條規則：assertCanManage 檢查第二條（目標的角色不能比自己高），rank 的比較檢查第一條，目標原本是 owner、要被降級時才檢查第三條。

第三條最容易寫錯。直覺寫法是「數 owner 有幾位，大於 1 才允許」，但「先數、再改」有競態，跟階段 A 第 2 課的名額是同一類問題。假設好日子咖啡後來有兩位 owner，兩人同時把對方降成 admin：

  1. 交易 A 數 owner，數到 2，通過。
  2. 交易 B 同時數 owner，也數到 2，通過。
  3. A 把 B 降級，B 把 A 降級，兩個都提交。租戶沒有 owner 了。

交易本身不會讓兩個交易互相等待。FOR UPDATE 會：它鎖住查到的列，直到交易結束。A 先鎖住所有 owner 的列，B 要鎖同樣的列就得等 A 結束；等 B 拿到鎖、真正數的時候，A 的降級已經提交，B 數到的是 1，就回 409。這句 $queryRaw 在 tx 裡執行，有 app.tenant_id（第 9 課），也自己寫了 tenant_id 條件（第 8 課）。

移除成員用同樣的檢查：移除別人要比較角色高低，移除自己（離開租戶）時不比較；不管哪一種，最後一位 owner 都不能走。

規則都在了，林雅婷只能在 admin 的範圍裡工作。一個月後合作結束，陳美華把她移出好日子咖啡。這時第 7 課的那個洞就要驗收了：她手上那張還沒過期的 access token，還能不能用？

一個月後移除林雅婷：她手上的 token 會立刻失效嗎？

先看洞在哪裡。陳美華在 10:00 移除林雅婷，林雅婷 9:55 拿到的 access token 要到 10:10 才過期。這張 token 的簽章沒問題、也還沒過期，JWT 本身沒有辦法收回（auth 第 11 課）。如果 guard 只驗 token，這 10 分鐘裡她照樣能打好日子咖啡的 API。

上一節的 guard 不只驗 token，還每個請求都查 membership。陳美華移除她之後，資料庫裡已經沒有「林雅婷在好日子咖啡」這一列，所以她的下一個請求就 401。其他路也一起堵上：

  • refresh：輪替（rotate）之後也檢查 isMember，她用 refresh token 換不到新的好日子咖啡 token。
  • switch-tenant：她想再切進好日子咖啡，回 403。
  • 舊的邀請連結：那封信早就用過，條件式更新只會成功一次，回 410。

她在自己事務所的 token 不受影響：那是另一個租戶的 membership，好日子咖啡移除的只是其中一列。

代價是每個請求多一次查詢。它是主鍵查詢，很快，但數量跟請求數一樣多。想省下這次查詢有幾種做法，差別在「移除、改角色之後多久生效」：

guard 看的是移除、改角色後多久生效代價
每個請求查 membership（參考實作）下一個請求每個請求一次查詢
快取 30 秒，移除或改角色時主動刪掉快取（NestJS 第 19 課）下一個請求每個改成員的地方都要記得刪快取
只有快取、沒有主動失效等快取過期看起來有做，其實有空窗
角色寫進 token等 token 過期（最多 15 分鐘）不用查詢

同樣的時間差也發生在改角色：陳美華在合作中途把林雅婷從 admin 降成 viewer，用參考實作的話，林雅婷的下一個請求就只剩 viewer 的權限；角色寫在 token 裡的話，她還能用 admin 的權限操作到 token 過期。

選了哪一種、為什麼，寫進 ADR 0003 的後果。第 7 課在那裡記下了「access token 撤銷不了」這個洞，現在把它更新成你的做法與代價。

💡 實務上：員工離職是最常見的權限事件
B2B 客戶最在意的權限場景不是駭客，是「昨天離職的員工今天還登得進來」，就像合作結束後的林雅婷。企業客戶的資安問卷幾乎都會問：「移除使用者後多久失效？」答得出「下一個請求」而且有測試證明，是作品裡很有說服力的一點。工作上還會遇到相關的需求：移除時把他負責的工單轉給別人、保留他的稽核紀錄（第 11 課，稽核記的是 user id，不會因為移除 membership 而消失）。

好日子咖啡的故事走完了：邀請、加入、切換、分權、移除，每一步都有 API 檢查。最後把同樣的分層套到你自己的業務模組。

套到你的業務模組

前面「誰能做什麼」那一節把權限分成兩層，你的業務模組也照這樣分：角色層照權限矩陣，在 permissions.ts 加上你的權限（例如 tickets:write）並決定哪些角色有，由 guard 檢查；資料層的規則（例如只有被指派的人能改）放在 service 的查詢或判斷裡，不新增角色。判斷方法是問「這條規則看的是人的角色，還是這一筆資料的內容」：看資料內容的，guard 做不到，因為 guard 不讀業務資料。

題目角色層資料層的規則
客服工單member 可以建立、留言；admin 可以指派、關閉只有被指派的人與 admin 能改狀態：service 用 where: { id, OR: [{ assigneeId: me.userId }, …] } 或先查再判斷
預約排程member 可以預約；admin 可以管理資源與替別人取消member 只能取消自己的預約，而且要在截止時間前
進銷存member 可以入庫、出庫；viewer 只能看報表異動只能新增、不能修改：連 owner 也沒有「改異動」的權限，更正用一筆反向異動

練習

練習 1：做出邀請：POST/GET/DELETE /api/v1/invitations、POST /api/v1/auth/invitations/accept。邀請 → 從信裡的連結取出 token → 接受 → 新成員登入後 /me 是這個租戶、角色正確；同一個 token 再用回 410 INVITATION_USED；撤銷的邀請回 410 INVITATION_REVOKED；請求的 Host 是 evil.example 時，信裡的連結仍然是設定的前端網址。

練習 2：權限矩陣：viewer、member、admin、owner 對 projects、members、invitations 各端點的狀態碼照契約（測試會列出不對的那幾格）；owner 把 admin 降成 viewer 之後，他手上同一張 access token 立刻沒有 admin 的權限。

練習 3：角色規則：admin 邀請 owner、把人升成 owner、降級或移除 owner 都回 403 FORBIDDEN；唯一的 owner 降級自己或離開回 409 LAST_OWNER；有第二位 owner 時可以降級另一位。

練習 4：做出 GET /api/v1/auth/tenants 與 POST /api/v1/auth/switch-tenant。B 接受 A 租戶的邀請、switch 進 A 拿到 token；A 移除 B 之後，那張 token 打 /api/v1/projects 要 401 或 403，B 再 switch 進 A 回 403；B 在自己租戶的 token 不受影響。switch 到不是成員的租戶回 403。

練習 5：為了讓 guard 少查一次資料庫，同事提議把角色寫進 access token（效期 15 分鐘），guard 直接用 token 裡的角色。主要的代價是什麼？

✓ 省下查詢的代價是「改了之後多久生效」。token 裡的內容在發出那一刻就固定了，降級、移除都要等它過期。b 錯：token 有簽章，改了 payload 驗不過；問題不是被竄改，而是內容過時。d 錯：只有被改的那個人受影響，而且也不會強制重新登入，正是它的問題。（第 10 課，auth 第 11 課）

練習 6：邀請信的連結寫成 `${req.protocol}://${req.get('host')}/invitations/accept?token=…`，理由是「這樣開發、測試、正式環境都不用另外設定」。攻擊者能怎麼利用？

✓ Host（以及代理設定下的 X-Forwarded-Host）是請求者決定的。信從正牌系統寄出、寄件人可信，使用者很難察覺連結被換掉了。連結的網址一律來自設定（APP_URL）。b 是 API 主動對外發請求，這裡 API 沒有連到那個網址，連過去的是受害者。（第 10 課，auth 第 16 課）

練習 7：工單系統的新需求：「member 只能改被指派給自己的工單，admin 可以改全部。」最自然的做法是？

✓ 角色決定「能做哪類動作」，「這一筆是不是你的」是資料的屬性，放在 service 的查詢或判斷裡（auth 第 19 課的 ABAC 思路）。a 把一個人的租戶角色跟某一筆工單綁在一起，指派兩張工單就亂了。c 讓通用的 guard 知道每個業務模組的資料，guard 會越長越大。d 只是畫面，API 照樣能被直接呼叫。（第 10 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • 邀請會過期：在資料庫把一筆邀請的 expires_at 改成過去，用它接受要得到 410 INVITATION_EXPIRED（測試不測時間，要自己試）。
  • 資料庫裡沒有邀請 token 原文：Mailpit 裡的連結 token 跟 invitations.token_hash 對不上。
  • 同一個 token 同時接受兩次只成功一次：用 Promise.all 同時送兩個 accept，一個 200、一個 410。
  • 每個路由都有宣告：暫時拿掉某個路由的 @Permissions，所有角色打它都要 403。
  • 權限矩陣有自己的測試：你 repo 裡有一份資料驅動的測試（角色 × 端點 → 狀態碼），新增端點時加一列。
  • ADR 0003 的後果寫了「每個請求查一次 membership」，以及想省這次查詢時的選項（短快取＋主動失效）。

常見錯誤

  • 信裡的連結用請求的 Host：攻擊者能讓正牌信件指向他的網站。用設定的前端網址。
  • 接受邀請沒有檢查、也沒有標記用過：同一個連結可以一直用；被移除的人點舊連結就回來了。用條件式更新標記 acceptedAt。
  • 邀請 token 存原文：資料庫外洩等於所有待接受的邀請都能被冒用。存雜湊。
  • 角色從 token 讀：降級、移除要等 token 過期。每個請求查 membership，或做有主動失效的快取。
  • membership 快取了卻沒有失效：效果跟角色放在 token 裡一樣，而且更難察覺。改角色、移除成員時一起刪快取。
  • 沒宣告權限的路由放行：忘了加 @Permissions 的路由所有人都能用。沒宣告一律 403。
  • 只靠權限矩陣，沒有角色規則：admin 有 members:write 就能把自己升成 owner。比較目標角色與自己的角色。
  • 最後一位 owner 的檢查沒有鎖：兩位 owner 同時降級對方，兩邊都數到 2。先 FOR UPDATE 鎖住 owner 的列再數；移除也要檢查，不只改角色。

寄信改成佇列

主線的寄信寫在請求裡：郵件伺服器慢，API 就跟著慢；寄信失敗，要陳美華自己重新邀請。想要失敗自動重試、不讓 API 等郵件伺服器，就把寄信改成佇列工作，請求只負責把「寄這封信」放進佇列（NestJS 第 20 課，選做）。

小結

  • 邀請 token 四個條件：存雜湊、條件式更新標記用過、72 小時過期、可撤銷；用過、撤銷、過期回 410，不存在回 404。真正保證只能用一次的是交易裡的條件式更新，不是前面的 if。
  • token 開頭帶 tenantId，讓還沒有上下文的接受邀請路徑能先設好租戶；信裡的連結來自設定，不來自請求的 Host。寄信放在交易之後。
  • 一個人屬於多個租戶時，換租戶就是 switch-tenant 換一張 token；不是成員回 403。
  • 權限矩陣寫成常數，程式只問權限；guard 每個請求查 membership，角色以資料庫為準；沒宣告就 403。「這一筆是不是你的」放在 service，不放在 guard。
  • 角色規則：不能給或管比自己高的角色；最後一位 owner 不能降級或移除，數之前先鎖。
  • 被移除的成員下一個請求就失效；省查詢的選項是短快取＋主動失效，寫進 ADR。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 8：使用者屬於好幾個租戶，前端用 x-tenant-id 標頭表示目前選的租戶。guard 這樣寫，哪裡會出事？

const payload = await this.jwt.verifyAsync(token)
const m = await db.membership.findUnique({ where: { tenantId_userId: { tenantId: payload.tid, userId: payload.sub } } })
if (!m) throw unauthenticated()
store.tenantId = req.headers['x-tenant-id'] ?? payload.tid

✓ 檢查與使用的不是同一個值：membership 查的是 tid，擴充與 RLS 用的是標頭。租戶只從驗過簽章的 token 來，要換租戶就呼叫 switch-tenant 換 token。b 錯：JwtModule 的 verifyOptions 已經寫死演算法。a 是最多人會選的：「驗過了」驗的是另一個租戶。（第 7、8 課）

練習 9：CI 的跨租戶 E2E 測試全部通過，正式環境卻發生了洩漏：一支手寫的 $queryRaw 報表忘了 tenant_id。RLS 明明開了，事後發現 CI 與正式環境的 API 都用 migration 那組帳號連線。為什麼 RLS 沒擋下？

✓ RLS 是資料庫依「誰在連線」執行的，連線的角色能繞過，policy 寫得再好也沒用，而且所有測試照樣通過。應用程式要用 NOSUPERUSER NOBYPASSRLS、不擁有表的角色，表再加 FORCE。b 把兩道防線搞混了：不經過的是 Prisma extension，RLS 在資料庫裡，所有 SQL 都受它管。c 錯：USING 就是管讀取的那一個。（第 9 課）

練習 10：同事想避免每個查詢都開交易，把擴充改成這樣。上線後所有列表都是空的，為什麼？

async $allOperations({ args, query }) {
  await base.$executeRaw`SELECT set_config('app.tenant_id', ${ctx.tenantId}, true)`
  return query(args)
}

✓ is_local = true 只在目前交易有效，而這裡沒有包交易，設定在同一句結束時就失效了；查詢還可能落在另一條連線上。設定與查詢要放進同一個交易（batch $transaction([set, query])）。a 是最危險的「修法」：改成 false 列表會出現資料，但設定留在連線上，連線池會把它交給別的請求。（第 9 課）

練習 11：Prisma extension 與 RLS 兩道防線，各自擋得住哪種錯？

✓ extension 在應用程式裡，讓正常的寫法就是安全的，錯誤也在程式裡就被擋下；RLS 在資料庫裡，管的是所有連線進來的 SQL，補 extension 管不到的地方。a 把兩者說反了：extension 管不到 $queryRaw。c 錯：兩道防線擋不同的錯，RLS 還多了每個操作一個交易的成本，不是為了效能。（第 8、9 課）

練習 12：owner 在 10:00 移除了一位成員。他的 access token 10:10 才過期。這段時間他的請求會怎樣，取決於什麼？

✓ access token 本身撤銷不了，失效的速度由「guard 每次看的是什麼」決定。查資料庫最快生效，代價是每個請求一次查詢；短快取要搭配主動失效。a 是最常見的誤解：撤銷 refresh token 只擋得住「換新的」。d 錯：被移除的人自己就是那個不會配合的前端。（第 7、10 課）

練習 13：admin 移除了一位成員。第二天那位前成員點了一週前收到、早就接受過的邀請連結，又回到了租戶。接受邀請的程式最可能漏了什麼？

✓ 連結一週前收到、早就用過，照理既「已使用」又「已過期」（72 小時）；還能用，代表兩個條件都沒做。用條件式更新標記 acceptedAt，並檢查 expiresAt。這裡他是重新「加入」了，不是沿用舊的登入，所以 b、d 都不是原因：就算 guard 每次都查，membership 也被這個連結重新建立了。c 是另一個條件（防資料庫外洩），跟重複使用無關。（第 10 課）

練習 14：租戶有兩位 owner。兩人同時把對方降成 admin，程式是「數 owner 有幾位，大於 1 才允許」，包在交易裡。結果租戶沒有 owner 了，為什麼？

✓ 「先數、再改」是典型的檢查與寫入競態，交易本身不會讓兩個交易互相等待。鎖住要數的那些列（或鎖租戶列），判斷才不會被插隊。a 錯：PostgreSQL 的 READ UNCOMMITTED 行為跟 READ COMMITTED 一樣，而且看到未提交的資料也解決不了競態。d 是事實但不是原因：就算同一台伺服器、同一個連線池也會發生。（第 10 課）

這個階段的重點整理成一頁圖解。
