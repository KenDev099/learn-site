階段 A：小專案走完一次 · 第 5 課

CI、部署與 README：一個專案的完整樣子

想像下週一你要休假，同事小陳接手你的活動報名 repo。他會做四件事：clone 下來跑起來、改一段程式、確認自己沒改壞、把新版上線。到第 4 課為止，這四件事每一件都要靠「有人記得」：記得先開資料庫、記得 push 前跑測試、記得 build 映像確認 Dockerfile 沒壞、記得 migration 要比新版 API 先跑。你在的時候，這些都在你腦子裡；你不在，小陳只能一步一步問，或者猜錯。

面試官打開你的 repo 時，處境跟小陳一模一樣：沒有人在旁邊解釋，他看的是 README 與 Actions 頁面上那一排綠勾勾。這一課的任務是讓 repo 自己回答小陳的四個問題，不靠你記得。做完之後，repo 會多出 .github/workflows/ci.yml（每次 push 與 PR 自動做型別檢查、migration、測試、build 映像）、一份有五個固定段落的 README，以及（選做）一個部署好的網址。這也是階段 A 的終點，最後一節回顧整個 repo，它就是階段 B 的起點。

這課會用到：
  • DevOps 課第 15 課的 GitHub Actions（workflow、job、step；services: 在 job 旁邊開資料庫容器）。
  • DevOps 課第 16 課的部署與回滾（映像標籤用 commit SHA，出事時換回上一個標籤）。
  • 求職課第 3 課的作品 README（面試官 30 秒內要看到什麼）。
  • 第 3 課的 npm test（會自己建 _spec 資料庫並 migrate deploy）與第 4 課的 Dockerfile。
練習 1、2 讀你 repo 的檔案（不用啟動 API）。練習 3 是選做：部署之後在 work/portfolio.json 的 small 加 "deployUrl"，沒填時那一題會顯示「選做，未填部署網址」並判為沒過，不影響其他題。判分：node check.mjs nestjs pf05。

這課的路線：

  • 小陳改完程式，誰來確認沒改壞？CI 是什麼、為什麼要在乾淨的機器上跑。
  • CI 每一步在擋什麼，順序怎麼排；為什麼要連真的 PostgreSQL。
  • CI 紅了，小陳要從哪裡看起。
  • 綠燈的版本怎麼變成一個網址（選做）：兩條部署路線的取捨，上線的順序與回滾。
  • 小陳怎麼不問你就跑起來：README 的五個段落，「如何執行」為什麼要能照著打，「設計決定」怎麼寫。
  • 回顧整個 repo：每個檔案是哪一課、為什麼存在。

小陳改完程式，誰來確認他沒改壞？

先看第三件事：確認沒改壞。從這件開始，是因為後面兩件都靠它：上線的應該是驗過的版本，README 裡「如何執行」的指令，CI 每次也會在乾淨的機器上替你跑一遍；先有 CI，部署與 README 才有東西可以對照。你在第 3 課寫好了 npm test，它會建測試資料庫、套 migration、跑單元測試與併發報名的 E2E。問題是它只有在有人執行時才有用。小陳趕著下班，可能只跑了自己改的那個測試檔；他的電腦上可能有一份你沒 commit 的 .env、一個舊的 node_modules、一張他手動建過的表，於是測試在他電腦上通過，換一台機器就壞。這就是常聽到的「在我電腦上會動」：程式其實依賴了某個只存在於那台電腦的東西。

持續整合（continuous integration，簡稱 CI）就是為了把「有人記得跑」換成「每次都自動跑」：每當有人 push 或開 PR，就在一台全新、什麼都沒裝的機器上，把專案從零跑一遍，結果顯示在 GitHub 上。全新這件事是重點：那台機器沒有 .env、沒有舊的 node_modules、資料庫是空的，所以 repo 少 commit 了什麼、migration 檔少了哪一步，都會在這裡現形，而不是在小陳上線後才發現。

GitHub 上做這件事的工具是 GitHub Actions。你在 repo 的 .github/workflows/ 放一個 YAML 檔，這個檔叫 workflow，描述「什麼時候觸發、做哪些事」。一個 workflow 裡有一或多個 job，每個 job 在一台獨立的機器上跑；job 裡是一串依序執行的 step，每個 step 是一個指令（run:）或一個別人寫好的動作（uses:，例如把程式碼 checkout 下來、安裝 Node）。任何一個 step 失敗，整個 job 就停下來並標成紅色。

所以小陳的第三個問題，答案是：他 push 之後不用記得任何事，Actions 會在乾淨的機器上替他跑一遍。接下來要決定的是，這台機器上具體要做哪些事。

CI 的每一步在擋什麼？

這個專案的 workflow 只有一個 job，在 job 旁邊開一個 PostgreSQL 容器，然後依序做六件事：

# .github/workflows/ci.yml
name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:18.6-alpine
        env:
          POSTGRES_USER: app
          POSTGRES_PASSWORD: app
          POSTGRES_DB: event_signup
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U app" --health-interval 2s --health-timeout 3s --health-retries 30
    env:
      DATABASE_URL: postgresql://app:app@localhost:5432/event_signup
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npx prisma generate
      - run: npm run lint
      - run: npx prisma migrate deploy
      - run: npm test
      - run: docker build -t event-signup:${{ github.sha }} .

由上往下讀：on: 是觸發條件，push 到 main 與每一個 PR 都會跑，所以小陳開 PR 時就會看到結果，不必等合進 main。runs-on 選機器。services: 在這台機器旁邊開一個 PostgreSQL 容器，options 裡的健康檢查讓 step 等到資料庫真的能連才開始，跟第 4 課 compose 的 service_healthy 是同一個用意。job 層級的 env: 把 DATABASE_URL 指向這個容器，每個 step 都讀得到。setup-node 的 cache: npm 會快取下載過的套件，下次 npm ci 不用全部重新下載。

六個 run: 的順序不是隨便排的。每一步只檢查一件事，排法有兩個原則：後面步驟需要的前置先跑（安裝套件、prisma generate），其餘便宜、快的先跑：型別錯誤幾秒就查得出來，沒必要先等資料庫測試跑完才知道。前面一步失敗，後面就不跑，小陳看紅掉的那一步就知道是哪一類問題：

步驟擋下什麼
npm cipackage.json 與 lockfile 對不上
npx prisma generateschema 寫錯；後面的型別檢查要用產生的 client
npm run lint型別錯誤。Vitest 只轉譯不檢查型別，不先擋，型別錯的程式測試照樣會過
npx prisma migrate deploymigration 在全新的資料庫從頭套用失敗（例如你手動在開發資料庫改過表，migration 檔其實少了一步）
npm test行為壞了。第 3 課的設定會在同一個 PostgreSQL 建 event_signup_spec 再跑一次 migration
docker buildDockerfile 壞了（例如新增的檔案被 .dockerignore 排除）

表裡有四步值得多說。第一步用 npm ci 而不是平常的 npm install，兩者的差別在誰說了算。npm install 以 package.json 為準，版本範圍（例如 ^）內有新版就可能裝新版，並順手改寫 lockfile；npm ci 以 lockfile 為準，照它裝出一模一樣的版本、不改 lockfile，兩個檔案對不上就直接失敗，而且會先刪掉既有的 node_modules 再裝。所以 CI 測的就是你 commit 的那組版本，它失敗通常代表 lockfile 沒 commit 或沒跟著 package.json 更新。

npm run lint 在參考實作是 package.json 的 scripts 裡的 "lint": "tsc --noEmit"：讓 TypeScript 編譯器只做型別檢查、不輸出檔案。你的 scripts 沒有 lint 就加上。為什麼不能交給測試？因為 Vitest 執行 TypeScript 時只把型別拿掉再跑，不檢查型別，型別寫錯的程式只要執行起來結果對，測試照樣綠。

migrate deploy 擋的是一種只有 CI 看得到的錯。你的開發資料庫是一路用 migrate dev 改過來的，中間也許你手動 ALTER TABLE 過一次；資料庫的現況是對的，但 migration 檔裡少了那一步。在你的電腦上永遠不會出錯，因為表早就在那裡。CI 的資料庫是空的，migration 檔必須從第一個照順序套到最後一個，少的那一步就會在這裡失敗，而不是在正式環境部署時失敗。

最後一步 docker build 的映像標籤用 ${{ github.sha }}，也就是這次 commit 的 SHA。每個 commit 對應一個映像，之後部署與回滾時，才說得出「現在跑的是哪一版」「上一版是哪一個」。這個 workflow 只 build、不把映像推到任何地方，用意是確認 Dockerfile 沒壞；部署需要推映像時怎麼加，見課末「補充與查表」。

六步都排好了，但其中兩步（migrate deploy 與 npm test）需要一個真的 PostgreSQL，讓 CI 每次都要開資料庫容器。這個成本值得嗎？

為什麼 CI 要連真的 PostgreSQL？

開資料庫容器會讓 CI 慢一些，常有人提議「CI 只跑不連資料庫的單元測試，E2E 留在本機跑」。這個專案不行，原因是第 3 課的結論：這個專案最重要的規則不在 TypeScript 裡，而在資料庫裡。名額不超賣靠的是交易裡的條件式 UPDATE，email 不重複靠的是唯一約束，名額不變負數靠的是 CHECK。單元測試把資料庫 mock 掉，這些規則就一條也沒被驗到；只有連上真的 PostgreSQL、同時送出報名請求，才知道它們有沒有作用。

所以 CI 跑的是同一份 npm test，跟小陳在本機跑的一模一樣，不另外寫一套「CI 版」的測試。兩套測試遲早會分歧：本機那套改了，CI 那套沒跟上，CI 綠的意義就變了。services: 開的 PostgreSQL 也跟第 4 課 compose 裡用同一個映像版本（postgres:18.6-alpine），讓 CI 與本機的資料庫版本一致，避免另一層的「在我電腦上會動」。部署時也要讓正式環境的 PostgreSQL 主版本對齊：走 VM＋compose 時用的就是同一份映像；走託管平台時，資料庫版本由平台決定，建資料庫時選同一個主版本。

CI 太慢的時候，先看是哪一步慢，通常是沒有快取套件或測試沒有清資料，不要先拿掉步驟或拿掉資料庫。省下的幾十秒，換來的是上面那些規則沒人驗。

CI 紅了，小陳要從哪裡看起？

CI 會跑了，小陳遲早會看到紅燈。這時候到 Actions 頁面點進那次執行，再點紅掉的那一步看 log。這個專案最常見的三種紅燈：

  • npm ci 失敗：package-lock.json 沒 commit，或改了 package.json 沒更新 lockfile。
  • migrate deploy 失敗：migration 檔在全新資料庫套不上，也就是上一節說的「少了一步」。
  • npm test 失敗但本機會過：測試依賴了你本機才有的資料。

實戰課第 6 課練過怎麼讀壞掉的 CI。

💡 實務上：分支保護讓 CI 有牙齒
CI 紅了還能 merge，它就只是裝飾：小陳趕時間時照樣可以把紅的 PR 合進 main。GitHub 的分支保護（branch protection）可以設定「這個 workflow 要綠才能 merge 到 main」，這樣「沒改壞」就不再靠任何人的自律。一個人的作品也值得開：面試官看到 main 的每個 commit 都是綠的，就知道你不是寫完才補測試。

到這裡，「沒改壞」有了自動的答案：main 上的每個 commit 都在乾淨環境驗過，而且有一個以 SHA 為標籤的映像。但一個驗過的映像還只是一個檔案，小陳的第四件事是把它上線，讓它有一個別人打得到的網址。

綠燈的版本怎麼變成一個網址？（選做）

CI 證明「這一版是好的」，部署讓它有一個網址。DevOps 課第 16 課與第 18 課教過部署的做法，這裡只比較作品常用的兩條路，不教特定平台的點擊步驟，因為平台的介面改得比課程快。

比較之前先認識一個名詞。對外的網址要用 HTTPS：瀏覽器會把 HTTP 網站標成「不安全」，面試官一點就看到警告，而且請求內容（包括密碼與 token）在網路上是明文傳輸，路上的任何人都看得到。API 直接對外時，HTTPS 憑證要有人申請、續期、設定；常見的做法是在 API 前面放一個反向代理（reverse proxy）：一個擋在 API 前面的伺服器，例如 Caddy、Nginx，由它負責 HTTPS 憑證，收到請求後再轉給 API。API 本身只講 HTTP，不用管憑證。

做法你要做的事費用取捨
單台 VM＋compose開一台雲端主機、裝 Docker、把第 4 課的 compose 搬上去，API 前面加反向代理處理 HTTPS；資料庫在同一台的容器主機固定月費，不管有沒有人用什麼都看得到、學到最多；備份、更新、HTTPS 憑證、主機安全都是你的事
託管平台平台從 repo 或映像部署 API，資料庫用平台的託管 PostgreSQL；在平台設環境變數，migration 設成部署前的步驟多半依用量計費，免費額度常有休眠或期限省事、HTTPS 與備份平台處理；被平台的限制綁住（冷啟動、網路設定、價格調整）

表裡的冷啟動（cold start）是託管平台免費額度最常見的現象：服務一段時間沒人用就被休眠，下一個請求進來時要等服務重新啟動，第一個請求會特別慢。面試官點你的部署網址剛好遇到，會以為 API 壞了，所以 README 裡值得寫一句。

兩條路怎麼選，看你想學什麼、想管多少事：想親手碰 HTTPS、備份、主機安全，選 VM；只想讓作品有個能點的網址，選託管平台。不管哪一條，上線的順序都跟第 4 課一樣：先跑 migration，成功才換新版 API。原因也一樣：新版程式可能用到新欄位，欄位還沒建好就先換程式，請求會 500；migration 失敗時，舊版 API 還在跑，服務不受影響。設定（DATABASE_URL）在平台或主機上設，不進 repo 也不進映像。部署後的第一件事是打一次 /health/ready，確認 API 連得上資料庫。

上線後如果出事，例如 /health/ready 是 200 但報名一直 500，順序是先回滾、再修。回滾就是把 API 換回上一個 SHA 的映像：這就是 CI 用 SHA 當標籤的用處，你說得出上一版是哪一個。服務壞著的每一分鐘都有人報不了名，所以先讓服務恢復，再慢慢用 requestId 查 log。回滾只換程式、不動資料庫，前提是這次的 migration 跟舊版程式相容：只新增、不刪欄位，舊版程式看不到新欄位也照樣能跑。這是 DevOps 課第 17 課的 expand／contract：先只加欄位（expand），等舊版程式都下線後，再刪舊欄位（contract）。

部署完成後，要怎麼確認「這個網址真的能用」，而不只是「首頁打得開」？做法是冒煙測試（smoke test）：上線後跑一遍最基本的幾個動作，確認核心功能沒壞。這個專案的冒煙測試就是練習 3：把網址填進 portfolio.json 的 deployUrl，它會依序打 health、建立活動、報名、重複報名要回 409。注意這會在你部署的資料庫留下幾筆測試資料。

到這裡，小陳的第三、第四件事都有了答案：CI 確認沒改壞，部署有固定的順序與回滾的退路。剩下的是第一件，也是他最先遇到的那件：clone 下來之後，到底要打哪些指令才跑得起來？

小陳怎麼不問你就把 repo 跑起來？

不管有沒有部署，README 都是每個看你 repo 的人第一個讀的檔案。對小陳來說它是操作手冊，對面試官來說它是專案簡介。求職課第 3 課講過作品 README 給誰看、先放什麼；這個專案用五個固定段落，每一段回答讀者的一個問題：

段落寫什麼參考實作
（標題下一句話）這是什麼、解決什麼問題讀書會、工作坊的報名後端；名額不超賣、email 不重複
## 如何執行從 clone 到跑起來的每一個指令，越少越好，但一步都不能漏，照著打就能動npm ci、cp .env.example .env、npm run db:up、npx prisma generate && npx prisma migrate deploy && npm run start:dev；整套容器另一行
## 架構技術選擇、模組怎麼切、一個請求怎麼走NestJS＋Prisma＋PostgreSQL；src/events/、src/common/、src/health/
## API端點表，錯誤格式五個端點＋健康檢查；{ statusCode, errorCode, message, requestId }
## 測試怎麼跑、測了什麼、連什麼資料庫npm test；單元＋E2E，資料庫自動加 _spec
## 設計決定你做過的取捨，一條一句，附理由條件式 UPDATE 而不是先查再新增；email 存小寫＋唯一約束；游標分頁；migration 是獨立服務

「如何執行」是小陳第一天就會照著打的段落，每一個指令都有它的理由。剛 clone 的 repo 沒有 node_modules，所以要 npm ci；沒有 .env（第 1 課放進了 .gitignore），所以要從 .env.example 複製一份；也沒有 src/generated（同樣在 .gitignore），所以 prisma generate 不能省，少了它程式連 Prisma client 都 import 不到。在你的電腦上這些東西早就在了，你寫 README 時很容易把它們當成理所當然而漏寫。

這個段落也最容易壞：寫的時候對，三個月後你把某個 script 改了名字，README 沒跟著改，第一個照著打的人就卡住。README 不會報錯，所以沒有人會發現，直到小陳卡住。這課的練習 2 就是把這種錯變成會紅的檢查：README 裡寫的 npm run xxx 在 package.json 的 scripts 裡要真的存在，提到 docker compose 就要有 compose.yaml。參考實作為此把開資料庫包成一個 script，README 裡只寫 npm run db:up：

"db:up": "docker compose up -d --wait db"

--wait 會等到 db 的健康檢查通過才回來，下一個指令 migrate deploy 執行時資料庫已經能連，小陳不會遇到「第一次執行連不上、再打一次就好了」這種讓人困惑的情況。

README 寫多長？讀者 30 秒內要知道這是什麼、怎麼跑；細節（每個端點的欄位）放連結或 OpenAPI（第 15 課），不要把契約整份貼進來。工程實務課第 7 課的技術寫作原則在這裡一樣適用：先寫結論，一段一件事。

💡 實務上：README 要有人照著打過
寫完 README，找一個新的資料夾 clone 你的 repo，只看 README 照著打一遍，就是在扮演小陳。通常會發現漏了一步：沒寫要先 cp .env.example .env、沒寫要先開資料庫、某個指令只在你的 shell 設定下才會動。團隊裡新人第一天照 README 卡住的每一個地方，都是一個該修的 README bug。

五個段落裡，四個是在描述 repo 現在的樣子，照著事實寫就好。只有「設計決定」需要你自己判斷要寫什麼，它也是面試官讀得最仔細的一段。

「設計決定」要寫什麼，面試時才講得出東西？

小陳接手後遲早會問：「名額為什麼不先查剩幾個再新增？那樣比較好懂。」如果 README 沒寫，他可能就照直覺改回去，超賣的 bug 就回來了。「設計決定」記錄的是這種「看起來可以換個寫法，但當初是刻意這樣做」的地方，讓後來的人知道哪些東西不能隨便動、為什麼。這就是小陳第二件事「改一段程式」的答案：README 告訴他哪些地方是刻意的、不能照直覺改回去，CI 則在他改壞時亮紅燈。

面試時，這一段的用處更直接。面試官問「這個專案最難的地方是什麼」，你就從這裡挑一條講，順序是：問題是什麼（同時報名會超賣）、考慮過哪些做法（先查再新增、FOR UPDATE、條件式 UPDATE）、選了哪個、為什麼、怎麼驗證（併發測試）。面試官想聽的不是你用了什麼技術，而是你遇到問題時怎麼想。

所以每一條都要是你真的做過、說得出理由的。不要列「使用 TypeScript 提高可維護性」這種每個專案都能寫的話：它沒有取捨，看不出你的判斷，面試官追問「為什麼」時你也講不出這個專案特有的東西。參考實作的四條（條件式 UPDATE、email 存小寫＋唯一約束、游標分頁、migration 是獨立服務），每一條都對應前面某一課解決過的具體問題。

CI、部署、README 都到位了，小陳的四個問題都有了不靠你的答案。最後退一步，看看階段 A 做出來的整個 repo。

階段 A 到這裡結束。回頭看第 1 課畫的那張檔案樹，現在每一個檔案都有了：

練習

練習 1：.github/workflows/ 底下有 workflow：job 的 services: 開了 postgres 映像、有一步 prisma migrate deploy、有一步 npm test。測試只做文字檢查（不解析 YAML、不連 GitHub），push 之後到 Actions 頁面確認它真的是綠的。

練習 2：README 有「如何執行」「架構」「API」「測試」「設計決定」五個標題（## 或 ###，標題文字包含這幾個字即可）；「如何執行」有放在 ``` 區塊裡的指令，裡面寫的 npm run xxx 都在 package.json 的 scripts，提到 docker compose 就要有 compose.yaml。

練習 3（選做）：把 API 部署到任何地方，網址填進 work/portfolio.json 的 small.deployUrl。測試對它跑冒煙測試：/health/ready 200、建立活動 201、報名 201、同一個 email 再報 409 ALREADY_REGISTERED。

練習 4：同事想讓 CI 快一點：「E2E 要開 PostgreSQL 很慢，CI 只跑單元測試，E2E 在本機跑就好。」這個專案這樣做的風險是什麼？

✓ CI 的價值是「每次都自動、在乾淨環境」驗證最重要的規則，而這個專案最重要的規則在資料庫裡。真的太慢先找原因（套件快取、測試資料清法），不要先拿掉驗證。a 是最常見的說法：覆蓋率只代表每一行被執行過，mock 掉的資料庫行為沒有被驗證（第 3 課）。（第 5 課）

練習 5：週五下午部署了新版，/health/ready 是 200，但報名一直回 500。這次部署包含一個只新增欄位的 migration。最先做什麼？

✓ 服務壞著的每一分鐘都有人報不了名，先回滾讓服務恢復，再查。只新增欄位的 migration 跟舊版程式相容，所以只要換回舊映像，不用動資料庫（b 反而有風險：回滾 migration 可能刪掉新資料）。a 讓使用者一直等你除錯。（第 5 課）

練習 6：README 的「設計決定」要寫什麼？

✓ 設計決定是面試時的題材：面試官要聽的是你怎麼想，例如「名額為什麼用條件式 UPDATE 而不是先查再新增」。b 是每個專案都能寫的話，看不出判斷；版本放「架構」一句帶過。c 該放 API 段落或 OpenAPI；d 放「已知限制與下一步」。（第 5 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • CI 真的會紅：開一個分支，故意讓一個測試失敗、push，Actions 要紅；刪掉那個分支。
  • main 受保護：GitHub 的分支保護設定「CI 要通過才能 merge」。
  • README 照著打得起來：在新的資料夾 clone，只看 README，照著打完 API 回應 /health/ready。
  • 設計決定每一條都講得出來：對著每一條，用一分鐘口頭說明問題、選項、選擇與驗證方式。
  • repo 公開前：git log --all --oneline -- .env 什麼都沒印；README 裡沒有真實的密碼或私人網址。
  • 部署了的話：部署的資料庫密碼不是 app／app，而且只在平台或主機上設定。

常見錯誤

  • CI 沒有 prisma migrate deploy：本機資料庫是一路 migrate dev 過來的，CI 才是第一次在全新資料庫套用；沒跑就不知道 migration 檔完不完整。
  • CI 用 npm install：會依 ^ 範圍更新 lockfile，CI 測的跟你 commit 的版本不一樣。用 npm ci。
  • CI 的資料庫連線字串寫正式環境的：CI 的測試會清空資料表。CI 只連 services: 開的容器。
  • 映像標籤用 latest：出事時說不出現在跑的是哪一版，也回滾不到「上一版」。用 commit SHA。
  • README 的指令跟 package.json 對不上：改了 script 名稱沒改 README。練習 2 會檢查。
  • 「設計決定」寫成技術清單：寫取捨與理由，不寫「使用了 X」。
  • 部署時在 API 啟動時跑 migration：第 4 課的問題換個地方又出現。migration 是部署流程裡獨立的一步，成功才換新版。

小結

  • 這課的任務：讓 repo 自己回答接手的人的四個問題（怎麼跑起來、怎麼改、怎麼確認沒改壞、怎麼上線），不靠任何人記得。
  • CI 把「有人記得跑測試」換成「每次 push 與 PR 都在乾淨的機器上自動跑」，「在我電腦上會動」的問題在這裡現形；分支保護讓紅燈不能 merge。
  • CI 先跑後面需要的前置，其餘便宜的先跑：npm ci → prisma generate → 型別檢查 → migrate deploy（在全新資料庫驗 migration 檔）→ npm test（連 services: 的 PostgreSQL）→ build 映像（標籤用 commit SHA）。
  • CI 跟本機跑同一份 npm test；連真的資料庫，因為規則在資料庫裡。
  • 部署兩條路：單台 VM＋compose（全部自己管）或託管平台（省事但受限）；都是先 migration、成功才換新版，出事先換回上一個 SHA 的映像再修，上線後跑冒煙測試。
  • README 五段：如何執行、架構、API、測試、設計決定；「如何執行」要在新資料夾照著打得起來，設計決定寫你做過的取捨與理由。
  • 階段 A 的 repo 每個檔案都說得出是哪一課、為什麼存在；它就是階段 B 的骨架。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 7 件事。先在心裡回答，再選。

練習 7：報名的 service 這樣寫。單機測試全過，熱門活動開放報名後，名額 30 的活動收了 34 個人。問題出在哪？

const e = await this.prisma.event.findUnique({ where: { id: eventId } })
if (e.remaining <= 0) throw new ApiError(409, 'EVENT_FULL', '名額已滿')
const r = await this.prisma.registration.create({ data: { eventId, email, name } })
await this.prisma.event.update({ where: { id: eventId }, data: { remaining: e.remaining - 1 } })

✓ 讀、判斷、寫回之間有空檔，併發的請求會一起穿過判斷，而且 remaining: e.remaining - 1 還會互相蓋掉（lost update）。改成交易裡的 UPDATE … SET remaining = remaining - 1 WHERE remaining > 0，看 count。b 錯：這裡 remaining 不會變負數，是被蓋掉，CHECK 擋不到超賣。（第 2 課）

練習 8：扣名額用了條件式 UPDATE，但扣名額與新增報名是兩個獨立的 Prisma 呼叫（沒有 $transaction）。重複報名的 email 被唯一約束擋下、回了 409。這時資料會怎樣？

✓ 沒有交易，每個呼叫各自提交；扣名額已經成功，新增才失敗，名額就漏掉了。扣名額與新增報名放在同一個 $transaction，新增撞到 P2002 時一起回滾。c 是常見的誤解：同一個請求不等於同一個交易。（第 2 課）

練習 9：使用者回報「報名時出現錯誤」，附上的截圖有 requestId: 7c1e…，狀態碼 500。你第一步做什麼？

✓ 500 回應刻意不帶細節，細節與 requestId 一起寫在 log 裡，requestId 就是從回報找到那一行 log 的鑰匙。c 在併發或資料相關的問題上常常重現不了；d 會把內部資訊（路徑、SQL）給所有使用者看。（第 2 課）

練習 10：要加一條新規則：「同一個 email 在同一天最多報名 3 場活動」，用一句帶條件的 SQL 擋。這條規則的測試要怎麼寫？

✓ 規則的正確性取決於那句 SQL 與併發時的行為，只有連真的資料庫、同時送請求才驗得到。a 只測到「service 收到 3 時會丟錯」，SQL 的 where 寫錯也會過；d 錯在 SQL 是你寫的，資料庫只保證照你寫的執行。（第 3 課）

練習 11：這份 Dockerfile 的最後一個 stage 有什麼問題？

FROM node:24.22.1-alpine
WORKDIR /app
COPY . .
RUN npm ci && npx prisma generate && npm run build
ENV DATABASE_URL=postgresql://app:secret@db:5432/event_signup
CMD ["node", "dist/main.js"]

✓ 一個 stage 包了建置工具與原始碼、沒有 USER 所以是 root，而 ENV 裡的密碼任何拿到映像的人都看得到。改成多階段、最後一個 stage USER node、DATABASE_URL 在執行時給。a 反了：陣列寫法讓 node 直接收到 SIGTERM。（第 4 課）

練習 12：部署平台會自動重啟 crash 的容器。migration 寫在 api 的 command 開頭（migrate deploy && node dist/main.js），這次的 migration 裡有一句 SQL 會失敗。部署後會看到什麼？

✓ migration 綁在 API 啟動上，失敗就讓 API 起不來，平台只會不斷重啟它。把 migration 拿成部署流程裡獨立的一步（compose 的一次性 migrate 服務），失敗一次就停、原因清楚，新版 api 因為 service_completed_successfully 不會被啟動。b 是常見的期待：平台不知道你的 migration 是什麼，不會替你決定回滾。（第 4 課）

練習 13：CI 的步驟是 npm ci → npm test，沒有 prisma migrate deploy；測試用 db push 建表。本機與 CI 都綠，部署時 migrate deploy 卻失敗了。最可能的原因是？

✓ 測試綠燈只證明 schema 對，不證明 migration 檔對。CI（與測試的 globalSetup）用 migrate deploy 在全新資料庫從頭套用，部署前就會發現。d 可能發生，但錯誤會是連不上，不是套用失敗。（第 3、5 課）
