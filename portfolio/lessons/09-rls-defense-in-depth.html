階段 B1：多租戶 SaaS 的平台地基 · 第 9 課

租戶隔離（二）：PostgreSQL RLS 當第二道防線

第 8 課結尾列過 Prisma extension 管不到的地方。這一課從其中一個最常見的情況開始：同事要在專案列表旁邊顯示「每個專案有幾個檔案」，覺得用 Prisma 的 API 拼不出想要的 GROUP BY，就改寫手寫 SQL：

// 假設的新程式：專案列表加上檔案數
const rows = await this.db.client.$queryRaw`
  SELECT p.id, p.name, count(f.id) AS file_count
  FROM projects p LEFT JOIN files f ON f.project_id = p.id
  GROUP BY p.id`

這段 SQL 沒有 tenant_id 條件。第 8 課的擴充只改寫 model 的操作（project.findMany 這類），$queryRaw 是你自己寫好的整句 SQL，擴充不會去動它。所以 A 租戶的使用者打開專案列表，會看到所有租戶的專案名稱。測試大概也抓不到：開發時資料庫裡多半只有一個租戶的資料。這就是一次跨租戶洩漏，在 SaaS 裡是要通報客戶的資安事件。

這一課的任務：讓這句漏寫條件的 SQL 也洩漏不了。做法是在資料庫加第二道防線，PostgreSQL 的 Row Level Security（RLS）：就算程式漏了條件，資料庫也只交出目前租戶的列。做完之後，這句 SQL 最壞的結果是「查到 0 筆」，而不是「查到別人的」。

這課會用到：
  • PostgreSQL 課第 24 課的 RLS：表開了 RLS 之後，每個查詢都會被資料庫自動加上 policy 的條件；USING 管讀，WITH CHECK 管寫。
  • auth 課第 20 課：RLS 用 set_config('app.tenant_id', …, true) 把租戶告訴資料庫；它跟應用層的條件是兩道各自擋不同錯誤的防線。
  • PostgreSQL 課第 36 課的連線池（應用程式先開好幾條連線，請求輪流借用、用完歸還）與 pg_stat_activity（看現在有誰連著資料庫）。
  • 第 8 課的 TenantDb：擴充過的 client，業務程式只用它的 client 與 tx()。

這課的路線：

  • 為什麼開了 RLS，上面那句 SQL 照樣洩漏？先換掉應用程式連線用的資料庫角色。
  • policy 要怎麼寫，才能在不知道租戶時一列都不給？在 migration 裡開 RLS。
  • 現在連正常的查詢也是 0 筆：怎麼讓每個查詢告訴資料庫「現在是哪個租戶」，又不被連線池弄混？
  • 好幾個操作要一起成功或失敗時怎麼辦？還沒有租戶的註冊、登入怎麼辦？
  • 這道防線的代價是什麼、怎麼證明它真的在擋？最後套到你的業務模組。

開了 RLS，為什麼那句 SQL 照樣洩漏？

直覺的第一步是幫 projects 開 RLS、寫一條「只看得到自己租戶」的 policy。先複習 RLS 在做什麼：一張表執行 ENABLE ROW LEVEL SECURITY 之後，PostgreSQL 會在每個碰到這張表的查詢上，自動加上 policy 裡寫的條件，效果就像有人替你在 WHERE 後面補了一段。這段條件由資料庫加，程式寫的 SQL 有沒有 tenant_id 都一樣，所以它擋得住開場那句漏寫的 SQL。

但如果你在現在的專案裡照做，再打開專案列表，會發現還是看得到所有租戶。原因不在 policy，而在是誰在連線。PostgreSQL 課第 24 課講過，有三種角色不受 policy 限制：

  • superuser：資料庫的最高管理者，所有權限檢查都跳過，RLS 也是。
  • 有 BYPASSRLS 屬性的角色：這個屬性的意思就是「RLS 對我無效」，通常給備份、資料搬遷這類工作用。
  • 表的擁有者：建立這張表的角色。PostgreSQL 預設認為擁有者可以管理自己的表，所以 policy 不套用在它身上，除非表另外加了 FORCE ROW LEVEL SECURITY（下一節會加）。

第 6 課的 compose 只有一個帳號 owner。所有表都是它建立的，所以它是擁有者；而開發用的 PostgreSQL 映像裡，POSTGRES_USER 指定的帳號還是 superuser。應用程式一直用它連線，等於同時佔了三種例外中的兩種。這時寫多少 policy 都沒有作用，而且所有測試照樣通過：policy 存在、語法正確，只是對這個連線不生效，沒有任何錯誤訊息提醒你。

解法是分成兩個角色，讓應用程式執行時用的那個不屬於任何一種例外：

擁有者（owner）應用程式（參考實作叫 pf_app）
做什麼prisma migrate deploy：建表、改表、建 policyAPI 與 worker 執行時的所有查詢
屬性表的擁有者（開發環境還是 superuser）NOSUPERUSER NOBYPASSRLS，不擁有任何表
權限全部只有 GRANT 給它的：SELECT, INSERT, UPDATE, DELETE
環境變數DATABASE_URL（只有 prisma.config.ts 讀）APP_DATABASE_URL（只有 PrismaService 讀）

擁有者仍然需要：改表結構、建 policy 都要有足夠的權限，這是 migration 的工作。但 migration 只在部署時跑一次，API 處理請求時用的是 pf_app。pf_app 沒有 superuser、沒有 BYPASSRLS、不擁有任何表，只能做 GRANT 給它的四種操作，policy 對它一定生效。

兩個角色各用一個連線字串，而且環境變數名稱刻意取得不一樣：

# .env.example
# DATABASE_URL 是擁有者，只給 prisma migrate 用；APP_DATABASE_URL 是應用程式執行時用的 pf_app
DATABASE_URL=postgresql://owner:owner@127.0.0.1:5434/my_saas
APP_DATABASE_URL=postgresql://pf_app:pf_app@127.0.0.1:5434/my_saas
// src/config/env.ts：應用程式只認得 APP_DATABASE_URL
APP_DATABASE_URL: z.url(),   // 執行時只用 pf_app；DATABASE_URL（擁有者）只給 prisma migrate

// src/prisma/prisma.service.ts
constructor(config: ConfigService<Env, true>) {
  super({ adapter: new PrismaPg({ connectionString: config.get('APP_DATABASE_URL', { infer: true }), connectionTimeoutMillis: 5_000 }) })
}

名稱不一樣的用意是讓「拿錯帳號」做不到：應用程式的 zod schema 裡根本沒有 DATABASE_URL，ConfigService 讀不到它，就不會有人「順手」拿擁有者的連線字串來連。如果兩者都叫 DATABASE_URL、只是在不同環境填不同的值，某天有人在部署設定裡填錯一次，RLS 就安靜地失效。

pf_app 這個角色本身要有人建立，參考實作把它寫在 migration 最後，跟 policy 放在一起，也就是下一節要寫的那段手寫 SQL。

💡 實務上：正式環境的資料庫帳號由基礎設施管
migration 裡的 CREATE ROLE pf_app … PASSWORD 'pf_app' 只給開發與測試用，密碼寫在程式碼裡沒關係。正式環境的角色與密碼通常由基礎設施建立，密碼放在 secrets manager（devops 第 11 課），部署時只把 APP_DATABASE_URL 交給 API。資深工程師做資安檢查時會先問：「API 執行時用的資料庫帳號是誰？它擁有表嗎？」答案是擁有者或 superuser，後面的 policy 就不用看了。

policy 怎麼寫，才能在不知道租戶時一列都不給？

換成 pf_app 之後，policy 終於會生效，接下來要決定 policy 的條件寫什麼。條件要拿每一列的 tenant_id 跟「這個請求的租戶」比，但資料庫不認得 JWT，也不知道 NestJS 的請求上下文。所以要有一個地方讓應用程式把租戶告訴資料庫，PostgreSQL 的做法是自訂設定參數。

PostgreSQL 有很多設定參數（例如 statement_timeout），也允許你自己取名字，只要名字裡有一個點，像 app.tenant_id。應用程式用 set_config('app.tenant_id', 'A 的 id', …) 把值寫進這條連線，SQL 裡用 current_setting('app.tenant_id', true) 讀出來。這個值只存在於這條連線（或這個交易，下一節會講差別），別的連線看不到。policy 的條件就是「這一列的 tenant_id 等於 current_setting 讀到的值」。

Prisma 的 schema 寫不出 RLS，跟階段 A 的 CHECK 一樣：migrate dev --create-only 產生 migration 後，在最後手寫。參考實作的 prisma/migrations/…_init/migration.sql 最後一段：

-- ===== 以下手寫 =====
-- 角色是整個 PostgreSQL 叢集共用的：已經有了就跳過
DO $$
BEGIN
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'pf_app') THEN
    CREATE ROLE pf_app LOGIN PASSWORD 'pf_app' NOSUPERUSER NOBYPASSRLS;
  END IF;
EXCEPTION WHEN duplicate_object OR unique_violation THEN NULL;
END $$;

GRANT USAGE ON SCHEMA public TO pf_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO pf_app;
-- 之後的 migration（同一個擁有者）新建的表也自動給權限；RLS 還是要每張表自己開
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO pf_app;

-- 沒設 app.tenant_id 時 NULLIF(…) 是 NULL，條件不成立 → 一列都看不到（fail closed）
-- FORCE：表的擁有者也受 policy 限制
ALTER TABLE "projects" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "projects" FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "projects"
  USING ("tenant_id" = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK ("tenant_id" = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
-- tags、files、exports、audit_logs、invitations 同上

由上往下分四段讀。

第一段建角色。角色不屬於某個資料庫，而是整個 PostgreSQL 叢集（一個 PostgreSQL 伺服器上的所有資料庫）共用的。開發資料庫跑過一次 migration 建了 pf_app，測試資料庫再跑同一份 migration 時角色已經在了，直接 CREATE ROLE 會報錯，所以先用 IF NOT EXISTS 查 pg_roles。兩個 migration 同時執行時（例如測試平行建好幾個資料庫），兩邊都可能查到「還沒有」再同時建立，後到的那個會撞錯；EXCEPTION … THEN NULL 把這種錯當成「已經有了」。

第二段給權限。pf_app 不是擁有者，預設什麼表都不能碰，要明確 GRANT。ON ALL TABLES 只涵蓋執行當下已經存在的表；ALTER DEFAULT PRIVILEGES 讓擁有者之後的 migration 新建的表也自動給 pf_app 權限。注意它只自動處理權限，RLS 不會自動開：新表沒開 RLS 也不會報錯，pf_app 照樣讀寫得了全部的列。這是這套設計最容易漏的地方，所以練習 2 的測試檢查「每張有 tenant_id 的表」都開了。

第三段開 RLS。ENABLE 打開 RLS；FORCE 讓表的擁有者也受 policy 限制。應用程式已經不是擁有者，沒有 FORCE 也受限制；FORCE 擋的是另一種情況：哪天有人用擁有者帳號跑腳本或修資料，那時一樣只看得到設定的租戶，不會一句 UPDATE 改到所有租戶。

第四段是 policy 的條件，三個細節各有理由：

  • current_setting('app.tenant_id', true)：第二個參數 true 表示沒設定時回 NULL 而不是報錯。但同一條連線上設過、再結束交易後，它會變成空字串，''::uuid 會報錯；NULLIF(…, '') 把空字串也變成 NULL。
  • NULL 讓條件不成立：tenant_id = NULL 的結果不是 true，所以沒有上下文的查詢一列都看不到。這叫 fail closed：資訊不足時選擇拒絕，而不是放行。
  • WITH CHECK 跟 USING 寫成一樣：USING 管「看得到、改得到、刪得到哪些列」，WITH CHECK 管「寫進去（INSERT、UPDATE 之後）的列要符合什麼」。只寫 USING 的話，PostgreSQL 會拿它同時當 WITH CHECK；真正的坑是 WITH CHECK 寫得比 USING 寬（例如只檢查「有設租戶」），那樣 A 的請求就能寫一筆 B 的資料進去。兩個寫成一樣最安全。

不是每張表都屬於某個租戶，所以 policy 也不全一樣。有些請求發生時使用者還沒選租戶，例如登入：這時資料庫只能靠「這個人是誰」來過濾，所以有第二個自訂參數 app.user_id（目前登入的使用者）。它跟 app.tenant_id 一起設定，下一節會看到；完整的流程在「還沒有租戶」那一節。

表policy為什麼
projects、tags、files、exports、audit_logs、invitationstenant_id = app.tenant_id屬於一個租戶的資料
membershipstenant_id = app.tenant_id OR user_id = app.user_id；寫入只看租戶租戶內看得到所有成員；登入、列出自己的租戶時還沒選租戶，只看得到自己那幾列
refresh_tokensuser_id = app.user_id屬於使用者、不屬於租戶
users、tenants不開 RLS全域的表：登入時要先用 email 找到人，那時什麼上下文都沒有。代價是這兩張表只靠應用層保護，查詢時只取需要的欄位

回到開場那句 SQL。它碰的 projects 與 files 都開了 RLS，pf_app 又沒有設定 app.tenant_id，所以它現在回 0 列，洩漏擋住了。但問題換了一個：其他所有查詢也是 0 列，包括第 8 課那些寫得完全正確的 project.findMany。資料庫在等 app.tenant_id，還沒有人告訴它。

怎麼讓每個查詢告訴資料庫「現在是哪個租戶」？

最直覺的做法是每個請求開始時執行一次 set_config('app.tenant_id', 'A', false)，之後的查詢都帶著它。這行不通，原因在連線池，要先看清楚設定參數「活多久」。

set_config 的第三個參數 is_local 決定設定的壽命：

  • false：session 層級。設定留在這條連線上，直到連線關閉或被改掉。
  • true：交易層級，等於 SQL 的 SET LOCAL。設定只在目前這個交易有效，交易 COMMIT 或 ROLLBACK 時就消失。

連線池會把同一條連線輪流借給不同的請求。這帶來兩個問題：

  • 兩句可能跑在不同連線上：先 set_config、再查詢，分成兩次執行，連線池可能給兩句不同的連線。設定落在 1 號連線，查詢跑在 2 號，而 2 號上留著別的請求設的租戶。
  • session 層級的設定會留給下一個人：用 is_local = false，請求結束、連線還給池子時設定還在。這條連線下次借給一個沒設定的程式（例如背景工作），它就用上一個請求的租戶查詢。

兩個錯誤一起發生時，時間軸是這樣（每一列是時間往下走）：

時間1 號連線2 號連線
1請求 B：set_config('app.tenant_id', 'B', false)，連線記住 B
2（請求 B 結束，連線還給池子，仍然記著 B）請求 A：set_config('app.tenant_id', 'A', false)
3請求 A 的查詢被分到這條：用的是 B 的租戶（設定了 A，卻沒有查詢用它）

請求 A 讀到了 B 的資料，而且 RLS 是幫兇：policy 照設定過濾，只是設定錯了。這比沒有 RLS 更難查，因為每一句 SQL 單獨看都對。

解法是兩件事一起做：設定與查詢放在同一個交易，而且 is_local = true。一個交易從 BEGIN 到 COMMIT 一定在同一條連線上，所以設定與查詢不會分開；COMMIT 時設定消失，下一個借到這條連線的程式看到的是空的，套用上一節的 policy 就是 0 列，不會用到別人的租戶。

剩下的問題是怎麼讓「每個操作都包成交易」不靠人記得。Prisma 有兩種交易：

  • batch 交易 $transaction([a, b])：傳一個陣列，Prisma 在同一條連線、同一個交易裡依序執行，全部完成後一起回傳結果。中間不能根據 a 的結果決定要不要做 b。
  • 互動式交易 $transaction(async tx => { … })：傳一個函式，裡面用 tx 執行的操作都在同一個交易，可以寫判斷、迴圈，函式丟錯就回滾。

「先 set_config 再查詢」不需要中間的判斷，用 batch 交易剛好。第 9 課在第 8 課的擴充外面再包一層：

// src/prisma/tenant-db.ts（第 9 課的版本）
@Injectable()
export class TenantDb {
  readonly scoped: ScopedClient
  readonly client: ScopedClient   // 一般的單一操作用這個

  constructor(private readonly base: PrismaService, private readonly ctx: RequestContext) {
    this.scoped = scoped(base, ctx)                     // 第 8 課：自動加 tenantId
    this.client = this.scoped.$extends({                // 第 9 課：每個操作包一個交易，先 set_config
      query: {
        $allModels: {
          async $allOperations({ args, query }) {
            const [, result] = await base.$transaction([setContext(base, ctx.tenantId, ctx.userId), query(args)])
            return result
          },
        },
      },
    }) as ScopedClient
  }

  // 互動式交易：開頭 set_config 一次（交易結束就失效），裡面的操作都在這條連線上
  tx<T>(fn: (tx: Tx) => Promise<T>): Promise<T> {
    return this.scoped.$transaction(async tx => {
      await setContext(tx, this.ctx.tenantId, this.ctx.userId)
      return fn(tx)
    })
  }
}

// is_local = true：只在這個交易有效
const setContext = (db: Pick<PrismaService, '$executeRaw'>, tenantId?: string, userId?: string) =>
  db.$executeRaw`SELECT set_config('app.tenant_id', ${tenantId ?? ''}, true), set_config('app.user_id', ${userId ?? ''}, true)`

這段先看 client（tx() 是下一節的主題）。scoped 是第 8 課那層，client 是在它外面再 $extends 一次：每個 model 操作進來時，外層把 setContext 與 query(args) 放進同一個 batch 交易，回傳查詢的結果。外層拿到的 args 還沒有 tenantId；query(args) 執行時會先交給內層（第 8 課那層），內層把 where 加上 tenantId 之後才真正送出，所以外層不用自己處理租戶條件。setContext 一次設兩個值：app.tenant_id 與上一節表裡提到的 app.user_id，都從請求上下文讀。

業務程式寫的一句 this.db.client.project.findUnique({ where: { id } })，在 A 租戶的請求裡會變成：

步驟在哪裡發生什麼
1兩層擴充都從請求上下文讀出租戶 A：第 8 課那層把 where 改成 { id, tenantId: 'A' }，第 9 課那層把 setContext 與這個查詢放進同一個 batch 交易
2連線池借出一條連線，依序送出 BEGIN → set_config('app.tenant_id', 'A', true) → SELECT … WHERE id = $1 AND tenant_id = $2（$2 是 A）→ COMMIT
3PostgreSQLpolicy 再過濾一次：只留 tenant_id 等於 app.tenant_id（A）的列
4連線池COMMIT 後 app.tenant_id 失效，連線還給池子，沒有留下任何租戶

業務程式完全不用改，this.db.client、this.db.tx() 的用法跟第 8 課一樣。兩層擴充這樣疊在參考實作的版本上實測過，細節見課末「補充與查表」。

現在回頭看開場那句 SQL 跟第 8 課列的其他洞：

  • 忘了加進 SCOPED 的 model：內層不加條件，但外層照樣設了 app.tenant_id，policy 只交出 A 的列。
  • this.db.client.$queryRaw（開場那句）：$queryRaw 不是 model 操作，兩層擴充都不經過，跑在沒有設定的連線上，查到 0 列。
  • 透過 tx() 執行的 $queryRaw：跑在設了 app.tenant_id 的交易裡，policy 只交出 A 的列。

每一種的結果都從「查到別人的」變成「只查到自己的」或「查不到」。查不到會被測試或使用者回報抓到，查到別人的不會。開場那句 SQL 的正確寫法因此是：放進 this.db.tx(tx => tx.$queryRaw…) 裡執行，SQL 裡也寫上 tenant_id 條件，兩道防線都在。

💡 實務上：連線池放大器（PgBouncer）也吃這一套
正式環境常在 PostgreSQL 前面放 PgBouncer 這類連線池，用「transaction 模式」讓幾千個應用程式連線共用幾十條資料庫連線：每個交易結束，連線就可能給別的應用程式用。session 層級的 SET 在這個模式下會漏到別的客戶端，而交易內的 set_config(…, true) 不受影響，因為它跟著交易結束。你的作品現在每個操作都在交易裡設定，換成 PgBouncer 也不用改；面試被問到「RLS 跟連線池怎麼配合」，就講這一點。

好幾個操作要一起成功或失敗時，交易怎麼開？

上一節每個操作各自包一個 batch 交易。單一查詢沒問題，但「建立專案，同時寫一筆稽核紀錄」這種要嘛一起成功、要嘛一起失敗的工作，需要互動式交易。這裡有一個不明顯的坑：不能用 client 開互動式交易。

原因是外層擴充對每個 model 操作都生效，包括在互動式交易裡面的操作。用 client.$transaction(async tx => …) 開交易時，裡面每個 tx.project.create(…) 仍會經過外層。上一節程式碼裡，外層呼叫的是 base.$transaction([...])，base 是最底層的 PrismaService，不知道外面已經有一個互動式交易，所以會從連線池另外借一條連線、另開一個 batch 交易。外面那個互動式交易形同虛設，回滾不了：實測在裡面 create 之後丟錯，資料還在。

所以 TenantDb 另外提供 tx()：用只有內層（第 8 課那層）的 scoped 開互動式交易，開頭自己呼叫一次 setContext。設定是 is_local = true，在整個交易裡都有效、交易結束就消失；裡面的操作都在同一條連線上，內層照樣自動加 tenantId，函式丟錯就整個回滾。

這個規則要寫進 ADR（最後一節會寫）：需要好幾個操作一起成功或失敗，一律用 tx()；單一操作用 client。

到這裡，所有「有租戶的請求」都帶得上上下文了。但有一群請求在發生時還沒有租戶。

註冊、登入這些還沒有租戶的請求怎麼辦？

每個操作都要上下文，而註冊時租戶還不存在，登入時還不知道使用者要進哪個租戶。它們會碰到 memberships、refresh_tokens 這些開了 RLS 的表，沒有上下文就是 0 列，註冊寫不進去、登入找不到人。

最省事的做法是給這些路徑另一條 BYPASSRLS 的連線。但那等於留一個什麼都看得到的後門：程式裡有兩個 client，只要有一個呼叫用錯，那一句就看得到所有租戶，而且跟第一節一樣，不會有任何錯誤提醒你。參考實作的原則是明確地設定「剛好夠用」的上下文，不關掉 RLS：

路徑上下文怎麼來碰到哪些有 RLS 的表
註冊程式先產生 tenantId、userId（第 7 課），設進上下文再開 tx()memberships（WITH CHECK：要是這個新租戶）
登入users 沒有 RLS，用 email 找到人；再把 userId 設進上下文，查他的 membershipmemberships（user_id = app.user_id）、refresh_tokens
refresh、logouttoken 的開頭是 userId（第 7 課的格式），先設進上下文再用雜湊查refresh_tokens
接受邀請（第 10 課）邀請 token 的開頭是 tenantId，先設進上下文再用雜湊查invitations、memberships

這張表也解釋了第二節 policy 表裡的 app.user_id：登入時只知道是誰、還不知道租戶，所以 memberships 的 policy 多一個 OR user_id = app.user_id，讓他看得到自己的成員身分、選出要進的租戶；refresh_tokens 屬於使用者，只看 app.user_id。users、tenants 不開 RLS，就是因為登入的第一步「用 email 找人」發生在任何上下文都還沒有的時候。

程式裡的寫法是先把 id 寫進請求上下文，TenantDb 就會照常設定：

// src/auth/auth.service.ts 的 signup
const tenantId = randomUUID(), userId = randomUUID()
Object.assign(this.ctx.store!, { tenantId, userId })   // 明確的上下文：這個新租戶、這個新使用者
const passwordHash = await this.passwords.hash(dto.password)
return await this.db.tx(async tx => { … })

// src/auth/auth.service.ts 的 defaultTenant（登入）
this.ctx.store!.userId = userId
const m = await this.db.client.membership.findFirst({ where: { userId }, orderBy: { createdAt: 'asc' } })

你可能會擔心 refresh token、邀請 token 的開頭帶著 id 是不是洩漏了什麼。id 不是秘密，秘密是後面的隨機值；id 只是讓資料庫知道「要在哪個範圍裡找」。這些路徑裡，資料庫仍然只交出這個人、這個租戶的列，就算程式哪裡寫錯，最多也只影響這個範圍。

兩道防線到這裡都接好了，每一種請求都有上下文。最後要問的是：這樣做花了什麼，以及怎麼證明它真的在擋。

這道防線的代價是什麼，怎麼證明它真的在擋？

代價是每個操作多一個交易與一句 set_config。原本一個 findUnique 是一句 SQL，現在是 BEGIN、set_config、查詢、COMMIT 一起送，同一條連線上多一次往返。交易數變多，也讓突發流量更容易用完連線池：連線都被借走時，新的交易要排隊等，等太久就失敗（Prisma 的等待上限見課末）。對這個規模的 SaaS 可以接受；這是寫進 ADR 的後果，量測到瓶頸時再處理，例如只讀的列表改成一個 tx() 裡做完多個查詢。

代價要寫下來，選擇也要。docs/adr/0002-rls-defense-in-depth.md 比較三個選項：

選項問題
只用 extension$queryRaw、新 model、新同事都會漏，漏了就是洩漏
只用 RLS錯誤要到資料庫才發現；少了「用 id 查到 0 筆就 404」的明確程式路徑
兩者都用多一個交易的效能代價

決定是兩者都用。兩道擋的是不同的錯，各自補對方的洞，兩道都漏才會洩漏：

出錯的情況第 8 課 extension（應用程式裡）第 9 課 RLS（資料庫裡）
業務程式的查詢沒寫 tenantId擋：自動加條件擋
$queryRaw 忘了 tenant_id、直接用 PrismaService、新 model 沒加進 SCOPED擋不到擋：沒設租戶就 0 列，設了只看到自己的
新表忘了開 RLS、應用程式用擁有者帳號連線擋（model 在 SCOPED 裡的話）擋不到
用別人的 id 查詢，要回 404查到 0 筆，程式明確回 404也是 0 筆，但只靠它的話錯誤要到資料庫才發現

ADR 的後果寫三件事：上面的效能代價、「還沒有租戶的路徑要明確設定上下文，不能關掉 RLS」、「擴充過的 client 不能開互動式交易，一律用 tx()」。

最後是證明。第一節說過，RLS 失效時所有測試照樣通過，所以只打 API 的黑箱測試不夠：它看得到回應，看不到 API 背後是用哪個角色連線。這一課的驗收測試是灰箱：除了打 API，還用你 API 實際使用的資料庫角色直連資料庫，檢查角色屬性、FORCE 與 policy。在 work/portfolio.json 填 appDatabaseUrl：

"saas": {
  …
  "appDatabaseUrl": "postgresql://pf_app:pf_app@localhost:5434/my_saas"
}

測試只讀不寫（寫入的檢查在交易裡做完就 ROLLBACK）。其中一項查 pg_stat_activity：先打一次 API 讓連線池留著閒置連線，再看連著這個資料庫的有哪些角色，只能有 appDatabaseUrl 的那一個。這一項擋的是「填給測試的是 pf_app，API 實際用的卻是擁有者」。所以跑測試時先關掉你自己用擁有者開的 psql 或 Prisma Studio，它們也會出現在 pg_stat_activity 裡。

套到你的業務模組

專案列表的那句 SQL 擋住了，你自己的業務模組也要同樣處理。每加一張業務表，migration 裡就要有同樣的三句（ENABLE、FORCE、policy），練習 2 的測試會檢查每張有 tenant_id 的表。三個題目各有一個要多想一步的地方：

題目要注意
客服工單SLA 提醒是排程，沒有請求：排程要先列出「有快到期工單的租戶」再逐一 ctx.run。列出租戶這一步跨租戶，查的是沒有 RLS 的 tenants 表或專用的函式，不是給排程一個 BYPASSRLS 帳號（第 13 課）。
預約排程排除約束檢查的是整張表，不受 RLS 影響；它的條件包含 tenant_id（第 8 課），衝突時回的錯誤也只說「時段重疊」，不會帶出別的租戶的資料。
進銷存月結報表的 $queryRaw 透過 this.db.tx(tx => tx.$queryRaw…) 執行，才有 app.tenant_id；直接用 this.db.client.$queryRaw 不經過擴充、沒有設定，RLS 讓它查到 0 筆。

客服工單的排程與開場那句 SQL 是同一個教訓的兩面：需要跨租戶的地方，明確地只拿需要的那一點（租戶清單），再回到逐一租戶、有上下文的查詢，而不是開一個看得到全部的後門。

練習

練習 1：應用程式改用自己的資料庫角色。測試用 appDatabaseUrl 直連：這個角色不是 superuser、沒有 BYPASSRLS、不是任何有 tenant_id 的表的擁有者；先打一次 API，pg_stat_activity 裡連著這個資料庫的只能有這個角色。

練習 2：每張有 tenant_id 欄位的表都 ENABLE 而且 FORCE ROW LEVEL SECURITY（測試讀 pg_class 的 relrowsecurity、relforcerowsecurity）。

練習 3：policy 真的有效：用 appDatabaseUrl 直連、沒設 app.tenant_id 時 projects 一列都看不到；在交易裡 set_config 成租戶 A 之後只看到 A 的；這時寫入一筆 tenant_id 是 B 的列要被 policy 擋下。另外 200 個 A、B 交錯的 GET /api/v1/projects（同時 20 個）每個都只看到自己的那一筆。

練習 4：RLS 開了之後，還沒有租戶的路徑照樣能用：註冊、登入、refresh、/me 正常；projects 建立、讀、改、刪正常，別的租戶讀不到（404）。

練習 5：新同事寫了一個「每晚清除 30 天前封存的 project」的排程，為了方便直接注入 PrismaService（沒有任何擴充），呼叫 project.deleteMany({ where: { archivedAt: { lt: 三十天前 } } })。在這一課的設定下會發生什麼？

✓ 繞過擴充的程式碰到 RLS，沒有上下文就是 0 列：錯誤變成「沒效果」，會被發現、不會造成洩漏或誤刪。正確做法是逐一租戶 ctx.run 再用 TenantDb。如果只有擴充、應用程式又用擁有者連線，就會是 a：刪掉所有租戶的資料。d 只在用 session 層級的 set_config 時才會發生，這一課用的是只在交易內有效的設定。（第 9 課）

練習 6：正式環境在 PostgreSQL 前面加了 PgBouncer（transaction 模式）。下面哪一種設定租戶的方式在這個架構下是安全的？

✓ transaction 模式下，連線只在一個交易的期間屬於你；交易內有效的設定跟著交易結束，不會漏給下一個客戶端。a、c 是 session 層級的設定，下一句查詢可能已經在另一條連線上，或者這條連線先被別人借走；c 的 RESET 也救不了中間被借走的那段時間。d 讓連線池無法共用，幾千個租戶就是幾千組連線。（第 9 課）

練習 7：RLS 上線後，客服回報「工單列表突然是空的」，其他頁面都正常。程式最近只改了一處：列表的排序改成手寫 SQL。最先該查什麼？

✓ 「突然變空、其他正常、剛改成手寫 SQL」指向那句 SQL 沒有上下文：$queryRaw 不經過擴充，也就沒有 set_config，RLS 讓它看到 0 列。改成在 tx() 裡執行，並在 SQL 裡寫上 tenant_id 條件。a 錯：WITH CHECK 只管寫入，不影響讀取。b 會得到權限錯誤（500），不是空陣列。（第 9 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • 擴充拿掉之後 RLS 還擋得住：暫時把 SCOPED 改成空集合，跑你 repo 的跨租戶測試：要全部仍然通過（別人的資料仍然 404），證明 RLS 真的在擋。試完改回來。
  • 互動式交易真的回滾：在某個 tx() 裡建立資料之後丟錯，資料庫裡不能留下那筆。
  • 應用程式的設定裡沒有擁有者的帳密：grep -rn "DATABASE_URL" src 只有 APP_DATABASE_URL；部署的環境變數（第 17 課）也只給 API 這一組。
  • 新表一定會開 RLS：新增一張有 tenant_id 的表，忘了寫 policy，node check.mjs nestjs pf09 的練習 2 要失敗；把這個檢查也放進你自己的測試（查 pg_class）。
  • ADR 0002 寫了三個選項與代價：只用 extension、只用 RLS、兩者都用；後果有效能代價與「不能開互動式交易」。

常見錯誤

  • 應用程式用擁有者或 superuser 連線：RLS 對它沒有作用，所有測試照樣通過，你不會發現。分兩個角色、兩個環境變數。
  • 開了 RLS 沒有 FORCE：擁有者不受限制，用擁有者跑的腳本、修資料的 SQL 看得到所有租戶。
  • policy 沒有 NULLIF：同一條連線設過一次後，沒設定時 current_setting 回空字串，''::uuid 讓查詢報錯，而不是安靜地回 0 列。
  • WITH CHECK 比 USING 寬：看得到的只有自己的，寫得進去的卻不限租戶。兩個寫成一樣。
  • 先設定、再查詢，分兩句：連線池可能給兩句不同的連線；用 is_local = false 時設定還會留給下一個請求。設定與查詢放在同一個交易，is_local = true。
  • 用外層擴充過的 client 開互動式交易：裡面每個操作各開一個交易，回滾不了。互動式交易一律用 tx()。
  • 為了註冊、登入開一個 BYPASSRLS 的連線：只要一個呼叫用錯 client 就是全部資料。明確設定剛好夠用的上下文。

補充與查表

  • 兩層擴充疊起來的實測：內層加 where.tenantId，外層把改好的 query(args) 放進 batch 交易。2026-11 用 Prisma 7.10.1＋@prisma/adapter-pg 7.10.1 實測：兩句在同一個交易；60 個 A、B 交錯的請求沒有一個讀到別的租戶。
  • 連線池用完時的錯誤：等不到連線的交易在 Prisma 的 maxWait（預設 2 秒）後失敗，錯誤訊息是 Unable to start a transaction in the given time。看到它，先查是不是突發流量把連線池用完。

小結

  • 開場那句漏寫 tenant_id 的 $queryRaw，extension 管不到；RLS 讓它最壞只查到 0 筆，不會查到別的租戶。
  • 兩個資料庫角色：擁有者只跑 migration（DATABASE_URL），應用程式用 NOSUPERUSER NOBYPASSRLS、不擁有表的角色（APP_DATABASE_URL）。用擁有者或 superuser 連線，policy 不生效，測試也照樣通過。
  • 每張有 tenant_id 的表 ENABLE＋FORCE；policy 用 NULLIF(current_setting('app.tenant_id', true), '')::uuid，USING 與 WITH CHECK 一樣嚴格；沒有上下文就 0 列（fail closed）。
  • TenantDb.client 把每個操作包成 batch 交易：set_config(…, true)＋查詢，同一條連線、交易結束就失效，連線池不會把租戶留給下一個請求。
  • 互動式交易用 tx()：只有內層擴充的 client 開交易，開頭設一次上下文。
  • 還沒有租戶的路徑（註冊、登入、refresh、接受邀請）明確設定剛好夠用的上下文，不關掉 RLS。
  • 代價是每個操作多一個交易；寫進 ADR 0002。灰箱測試用 appDatabaseUrl 檢查角色、FORCE 與 policy。
