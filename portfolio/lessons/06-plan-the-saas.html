階段 B1：多租戶 SaaS 的平台地基 · 第 6 課

作品規劃：範圍、架構與第一份 ADR

階段 A 的活動報名 API 證明你能把一個小專案從需求做到部署。面試官看完會接著問：「這個規模你做得出來，那更像真實產品的東西呢？」真實的 B2B 產品（賣給公司、不是賣給個人的軟體）大多是多租戶 SaaS。SaaS 是放在網路上、用訂閱方式賣的軟體；「租戶」指的是一個付費的客戶單位，通常是一家公司。多租戶的意思是很多家公司共用同一套程式、同一個資料庫，但彼此看不到對方的資料，每家公司裡又有不同角色的成員（老闆、管理員、一般成員）。這種系統最常出事的地方不在業務功能，而在所有功能底下那層平台地基：查詢少了一個租戶條件，A 公司就看到 B 公司的資料；token 發出去收不回來；權限檢查放錯層。

階段 B（第 6～19 課）會在一個新的 repo（下面叫它 my-saas）做出這樣的 SaaS 後台。這一課還不寫業務程式，任務是：在寫第一行業務程式之前，把 my-saas 準備到「面試官打開 repo 十分鐘看得懂你要做什麼、怎麼做，這課加上後面 13 課（第 6～19 課）你自己也不會走錯方向」。做完這課，repo 裡會有四樣東西：README 裡的範圍說明、模組地圖 docs/architecture.md、第一份架構決策紀錄 docs/adr/0001-…，以及一個跑得起來的骨架，連打錯路徑得到的 404 都符合契約的錯誤格式。課文用「客服工單」當你選的題目來舉例，你換成自己的題目照做。

這課會用到：
  • auth 課第 20 課的三種隔離方式（共用資料表＋tenant_id、每個租戶一個 schema、每個租戶一個資料庫）與「租戶只從 token 來」。
  • system-design 課第 18 課的 ADR（一個決定一份短文件：背景、決定、後果；被推翻時寫新的取代，不改舊的）。
  • NestJS 課第 26 課的模組邊界三條規則（資料歸屬、最小公開、單向依賴）。
  • NestJS 課第 8 課的錯誤格式（errorCode 給程式判斷、message 給人看）與全域 filter；這門課第 2 課在活動報名做過一次。
階段 B 的程式寫在你另開的 repo my-saas，判分方式跟階段 A 一樣：先啟動你的 API，再在 learn 資料夾執行 node check.mjs nestjs pf06。這個階段多用兩個服務：Redis（限流、佇列）與 Mailpit（收邀請信），learn 的 nestjs/practice 的 docker compose up -d --wait 會一起開好。
這課的路線：
  1. 面試官只看十分鐘：作品的力氣該花在哪？把範圍切成「平台」與「業務」兩半。
  2. 業務那一半挑什麼題目，才看得出你的程度？
  3. SaaS 有十個左右模組：怎麼放才不會互相纏住？
  4. 後面每一課都踩在上面的決定：租戶資料怎麼隔離，怎麼寫成 ADR 留下理由？
  5. 開 repo：骨架從哪裡來？錯誤回應第一天要長什麼樣？使用者回報錯誤時怎麼找到那一次請求？

面試官只看十分鐘：作品的力氣該花在哪？

先想清楚作品是給誰看、對方怎麼看。面試官打開你的 repo，通常只花 5～10 分鐘：讀 README 的第一段、看架構圖、挑一兩個檔案點進去、看有沒有測試。他不會把每個端點都打一遍，也沒時間理解你的業務細節。這十分鐘裡他真正想回答的問題是：這個人會不會在對的地方花力氣。工作上，資深與資淺的差別很少是「會不會寫 CRUD」，而是知不知道哪裡出錯代價最高、先把那裡做對。

作品最常見的失敗正好相反：「什麼都做一點」。二十張資料表、每張都有新增修改刪除查詢、沒有一個有測試。面試官從這種 repo 只看得出你花了很多時間，看不出你懂什麼，因為 CRUD 是框架替你做的那部分。要讓判斷力被看見，就要讓 repo 本身說出「我在哪裡多花了力氣、為什麼」。

所以這個作品的範圍切成兩半，用兩種不同的標準：

  • 平台功能：每個多租戶 SaaS 都需要、跟你賣什麼無關的那層。註冊登入、租戶隔離、成員與角色、稽核紀錄、檔案、背景工作、方案上限、API 文件、可觀測性。這層出錯的後果是全面性的：隔離漏一個條件，洩漏的是所有客戶的資料。它也有業界共通的「做對」標準，所以適合照一份規格做完整，讓人逐條檢查。
  • 業務模組：讓這個產品成為「客服工單系統」而不是「預約系統」的那部分，由你自選。這層要展示的是深度：挑一條真的有規則的流程（狀態只能照特定順序變、時段不能重疊、庫存不能變負數），把它做對，並證明兩個請求同時進來時規則也不會被破壞。一條做深，比十個 CRUD 更能看出程度。
平台功能業務模組
是什麼註冊登入、租戶隔離、成員與角色、稽核、檔案、背景工作、方案上限、OpenAPI、可觀測性你自選的題目（工單、預約、進銷存），掛在租戶底下
做到什麼程度照契約做完整：每個端點、狀態碼、錯誤情況都有，驗收測試會逐條檢查一條有深度的流程：一個真的業務規則做對（狀態機、不能重疊、不能為負），不是十個 CRUD
面試時講什麼「每個 SaaS 都會遇到的坑，我怎麼擋」：隔離、token、權限、競態「這個業務最難的那一條規則，我怎麼保證它在併發下也成立」

平台那一半的「規格」已經寫好了：SaaS 契約。它跟階段 A 的契約一樣，只規定外面看得到的東西：路徑、方法、狀態碼、errorCode 與少數欄位；裡面怎麼實作由你決定。驗收測試就是照這份契約打你的 API。

這裡有個問題：契約要檢查「A 租戶看不到 B 租戶的資料」「一般成員不能刪東西」，就需要一種實際的資料來測，但契約不知道你會選什麼題目。所以契約自帶一個示範模組 projects，只有名稱、描述、封存三樣，用它來示範隔離、權限、方案上限、稽核、檔案與匯出。它代表每個 SaaS 都有的「頂層容器」：專案管理工具的專案、協作工具的工作區、電商後台的店鋪。你的業務模組可以掛在 project 底下（例如工單屬於某個專案），也可以獨立。

從這課到第 19 課，每課在 my-saas 加一塊功能。契約只會加端點，不會改舊的，所以前面做對的東西不會因為後面的課被推翻。每課加什麼，查課末的「補充與查表」。

💡 實務上：範圍是你的第一個設計決定
工作上，PM 給的需求清單永遠做不完。資深工程師會先講清楚「這一版保證什麼、不保證什麼」，把力氣放在出錯代價最高的地方，再把沒做的事明白寫出來，讓 PM 和主管知道風險在哪。作品也一樣：在 README 寫一段「範圍與刻意不做的事」，例如「沒有接金流，方案升級是模擬的」「工單只做狀態流轉與指派，不做知識庫與滿意度調查」。這段本身就是判斷力的展示，也替面試官省下猜你為什麼沒做某功能的時間。

範圍切成兩半之後，平台那一半照契約做就好；但業務那一半是空白的，接下來要決定它到底做什麼。

業務那一半挑什麼題目，才看得出你的程度？

上一節說業務模組要「一條有深度的流程」，這裡先講清楚什麼叫有深度。一條流程有深度，是因為它有一條單看程式碼很容易寫錯、出錯會造成實際損失的規則。最典型的是併發：兩個請求幾乎同時進來，各自先讀資料、判斷「可以」、再寫入，結果兩個都成功，規則被破壞。你在階段 A 的活動報名看過這種情況：兩個人同時搶最後一個名額，單機測試抓不到，上線後名額就被超收。能把這種規則做對、並寫出測試證明的人，跟只會寫 CRUD 的人，面試官一眼就分得出來。

課程不規定題目，給三個建議。每個都有一條「做對很難」的規則，而且剛好用到你在前面課程學過的東西：

題目深流程（做這一條就夠）難在哪、用到哪一課面試能講的故事
客服工單工單狀態機（新建 → 處理中 → 等待回覆 → 已解決 → 關閉），指派給成員，SLA 快到期時背景工作提醒狀態轉換寫成純函式（NestJS 第 18 課）、條件式更新擋「兩個人同時改狀態」（第 15 課）、排程（第 21 課）「非法的狀態轉換在哪一層擋、併發時怎麼不會變成兩個狀態」
預約排程教室、會議室或診所的時段預約：同一個資源的時段不能重疊，取消有截止時間PostgreSQL 的排除約束（PostgreSQL 第 38 課）讓資料庫擋重疊；時區（第 13 課）「為什麼不能先查有沒有衝突再寫入，資料庫怎麼替我擋」
進銷存品項的入庫、出庫異動只追加不修改，庫存不能變成負數，月結報表匯出交易與鎖（PostgreSQL 第 32 課）、只追加的帳本設計、第 13 課的背景匯出「庫存為什麼不直接存一個數字讓人改，同時出庫兩筆怎麼不會超賣」

三個題目的共同點是：規則都能用一句話講完，但要讓它在併發下成立，得靠資料庫或條件式更新，而不是「先查再寫」。以客服工單為例，規則是「工單只能照狀態機的箭頭走」，難點在併發：客服 A 和客服 B 同時打開同一張工單，兩人讀到的狀態都是「處理中」。A 把它改成「已解決」並寫入；B 依自己讀到的「處理中」判斷「可以改成等待回覆」，接著也寫入。結果資料庫出現「已解決 → 等待回覆」這個狀態機不允許的轉換。B 的程式確實檢查過，但檢查用的是讀進來那一刻的狀態，寫入時它已經過期了，這就是「先查再寫」擋不住的地方。解法是把檢查放進寫入本身，也就是條件式更新：UPDATE … SET status = '等待回覆' WHERE id = … AND status = '處理中'。A 已經改掉狀態的話，這句更新影響 0 列，B 就知道要重新讀取，而不是蓋過去。

怎麼選：挑一個你講得出「真實的人會怎麼用」的。面試官追問「誰會用這個功能、他們遇到什麼麻煩」時，答得出來的題目才撐得住後續的追問。挑定之後在 README 寫兩三句：使用者是誰、那條深流程是什麼、最難的規則是哪一條。以客服工單為例：「給中小企業客服團隊用的工單後台。深流程是工單狀態機與指派；最難的規則是兩個客服同時改同一張工單時，狀態不能被覆蓋成不合法的轉換。」從第 8 課起，每課最後一節「套到你的業務模組」會說明同一件事在三個題目裡各要注意什麼。

題目定了，知道要做什麼之後，下一個問題是程式要怎麼放：平台加業務，my-saas 會有十個左右的模組。

十個模組怎麼放，才不會互相纏住？

階段 A 只有一個 events 模組，模組之間的關係不是問題。SaaS 有十個左右模組，如果邊寫邊決定誰 import 誰，很快會出兩種問題。第一種是循環依賴：auth import projects、projects 又 import auth，兩邊綁死，改一邊就要顧另一邊，想把其中一個拿出來單獨測試或拆出去都做不到。第二種是繞過規則：業務模組為了方便，直接寫 memberships 表加一個成員，跳過了 members 模組裡「檢查方案人數上限、寫稽核紀錄」的那段邏輯，規則就破了。

解法是先定好依賴的方向。照 NestJS 第 26 課的單向依賴：業務模組依賴平台模組，平台模組不依賴業務模組。方向這樣定，是因為平台是穩定、共用的那層：註冊登入不會因為你從工單換成預約而改變；業務模組則會一直改。依賴應該指向比較不會變的那一邊，這樣業務怎麼改都不會牽動到平台，平台也可以原封不動地拿去配另一個業務。

具體的模組地圖如下。「可以依賴」那一欄就是規則：一個模組只能 import 這一欄列出的模組。

模組負責可以依賴哪一課
common、config、prisma錯誤格式、請求上下文、log、環境變數、資料庫 client—6、8、9
auth註冊、登入、tokencommon、prisma7
tenancy權限矩陣、全域 guard、/meauth、common、prisma7、8、10
members成員、邀請、寄信auth、audit、billing10
audit、billing稽核紀錄；方案、用量、每租戶限流common、prisma11、14
projects、files、exports、你的業務模組業務以上全部8、12、13

讀這張表時注意兩件事。一是越上面的模組越底層，最上面那一列什麼都不依賴，所有人都依賴它。二是 members 依賴 audit 與 billing：邀請一個人加入租戶時，要先問 billing「這個方案還能不能加人」，成功後要請 audit 記一筆「誰邀請了誰」。這正是上面說的「繞過規則」的反面：加成員的規則全部集中在 members，其他模組要加人就呼叫它，不直接寫表。

這張表放在 repo 的 docs/architecture.md（參考實作在 nestjs/practice/portfolio-ref/saas/docs/architecture.md），旁邊用 Mermaid 畫一張元件圖，標出 API、PostgreSQL、Redis、SMTP、worker 之間誰連誰。Mermaid 是在 Markdown 裡用文字描述圖的語法，GitHub 會直接把它顯示成圖，所以圖跟著程式碼一起進版本控制。第 19 課會再補一張「一個帶租戶的請求」的時序圖；現在先有表就好。

資料夾照模組切，跟階段 A 一樣不照種類切（不是 controllers/、services/ 各一個資料夾），這樣表上的一列就對應 src/ 下的一個資料夾，對照得起來：

寫下來的規則要守得住才有用。最省事的檢查是搜尋平台模組有沒有 import 業務模組，例如 grep -r "from '../projects" src/auth src/tenancy src/common 應該沒有結果；每次覺得「平台這裡需要知道業務的某件事」時，先停下來想是不是方向反了。

程式怎麼切定了。但有一個決定比模組更底層，每個模組的每個查詢都會受它影響：租戶的資料在資料庫裡要怎麼分開。

後面每一課都踩在上面的決定：租戶資料怎麼隔離？

第 8 課要讓查詢自動加上租戶條件、第 9 課要在資料庫再加一道防線、第 10 課要做跨租戶的權限，全都建立在「租戶資料怎麼隔離」這個決定上。它一旦定了，之後要換，等於每個模組重寫一次。所以它是第一個要做、也是第一個要寫下來的決定。

auth 第 20 課比較過三種做法，這裡用一張表回顧：

做法隔離強度代價
共用資料表，每列帶 tenant_id最弱：靠每個查詢都加條件最省；但漏一個條件就洩漏
每個租戶一個 schema較強migration 要對每個租戶各跑一次，租戶越多越慢
每個租戶一個資料庫最強：實體分開連線、migration、監控都乘以租戶數，成本與維運最高

原理那一課講過了，這裡要做的事不一樣：把你的選擇和理由寫下來，放進 repo。為什麼要特地寫下來？程式碼只告訴讀的人「現在是怎麼做的」，不會告訴他「為什麼這樣做、當時考慮過什麼、什麼情況下該改」。半年後新同事（或面試官、或你自己）看到每張表都有 tenant_id，會想「為什麼不每個租戶一個資料庫，比較安全吧？」如果答案只在當初某個人的腦袋或某則聊天訊息裡，這個問題每次都要重新爭論一次，甚至有人會在不知道代價的情況下把它改掉。

記錄這種決定的標準做法是 ADR（Architecture Decision Record，架構決策紀錄）。它是一份很短的 Markdown 檔，一個決定寫一份，檔名帶流水編號（0001-tenant-isolation.md、0002-…），放在 docs/adr/。短是刻意的：一頁內讀完，大家才會真的去讀。驗收測試要求它有四段：

段落寫什麼常見的錯
狀態提議中、已採用、已被 ADR N 取代；加日期不寫：半年後分不出這份還算不算數
背景當時的限制與條件：租戶數量、資料量、團隊大小、考慮過的選項只寫「我們需要隔離」，沒寫數字與限制
決定選了什麼，一兩句；要具體到能照著寫程式寫成教學文，把三種做法的原理都講一遍
後果好處、代價、要額外做的事、什麼情況要重新考慮只寫好處：沒有代價的決定通常是沒想清楚

四段的順序就是一個決定的因果：在什麼條件下（背景），選了什麼（決定），因此得到什麼、付出什麼（後果），以及這份紀錄現在還算不算數（狀態）。參考實作的 docs/adr/0001-tenant-isolation.md：

# 0001. 租戶隔離：共用資料表＋tenant_id

## 狀態

已採用（2026-11-19）

## 背景

這是給小型團隊用的 SaaS 後台，預計有數百到數千個租戶，每個租戶的資料量小。
隔離方式有三種：共用資料表加 `tenant_id`、每個租戶一個 schema、每個租戶一個資料庫。

## 決定

所有租戶共用資料表，每張租戶資料表都有 `tenant_id`。
租戶只從 access token 的 `tid` 來，不接受請求送來的租戶 ID。

## 後果

- 好處：migration 只跑一次、連線池共用、新增租戶不用建資源。
- 代價：漏一個條件就是跨租戶洩漏。用兩道防線補：Prisma extension 自動加條件、
  PostgreSQL RLS（為什麼兩道都要，寫在 0002）；再加跨租戶 E2E 測試。
- 大客戶要求實體隔離時，再為他們另開資料庫（寫新的 ADR 取代這份）。

逐段看它怎麼回答「為什麼」：

  • 背景寫了數字：數百到數千個租戶、每個資料量小。有了這兩個條件，「每個租戶一個資料庫」的 N 倍成本就明顯不划算，讀的人不用再問。
  • 決定具體到能照著寫程式：每張租戶資料表都有 tenant_id，而且租戶只從 token 來。第二句很重要，它直接排除了「前端在 header 或 body 送租戶 ID」這種寫法，因為使用者可以竄改自己送出的任何東西。
  • 後果的第二點最關鍵：選了最省的做法，就要說清楚怎麼補它的弱點。「漏一個條件就洩漏」這個代價，換來的是兩道防線加跨租戶測試，這一點直接決定了第 8、9 課要做什麼。第三點則寫出什麼時候該重新考慮，讓以後的人知道這個決定的邊界。

你的 ADR 不用照抄。背景要寫你自己的題目，例如「客服工單後台，每個租戶是一家公司的客服團隊，工單量每月數百到數千張」；結論可能跟參考實作一樣，但理由要是你的。

ADR 還有一條規則：寫好之後不再修改內容。決定被推翻時，寫一份新的（例如 0007），新的寫「取代 0001」並說明為什麼改；舊的只把狀態那一行改成「已被 0007 取代」，其他一字不動。這樣做的原因是 ADR 記錄的是「當時」的判斷：直接改舊的，當時的背景與理由就消失了，半年後讀 repo 的人只看得到最新結論，看不到「當時為什麼那樣選、後來為什麼改」，也就無從判斷新的改法有沒有重蹈覆轍。

💡 實務上：ADR 是面試時最好用的講稿
面試官常問「你的專案裡有什麼取捨？」沒準備的人會講技術選型（「我用 NestJS 因為它有 DI」），這種答案誰都講得出來。有 ADR 的人可以打開檔案說：「我選共用資料表，代價是漏條件就洩漏，所以我加了兩道防線和跨租戶測試；如果有客戶要求實體隔離，我會這樣改。」這是背景、決定、後果的順序，也是面試官想聽的順序。工作上，ADR 也是新人 onboarding 時最先讀的東西之一。第 19 課整理作品時，ADR 清單會是 README 裡「設計決定」那一段的內容。

範圍、題目、模組地圖、隔離方式都寫在文件裡了。接下來開 repo，把這些決定變成一個跑得起來的骨架。

錯誤回應第一天就要對：前端怎麼只寫一套錯誤處理？

從前端的角度想。你在 Vue 專案裡大概寫過 axios 的攔截器（interceptor）：所有請求的錯誤都先經過它，依錯誤種類決定要跳回登入頁、顯示「沒有權限」，還是把欄位錯誤標在表單上。這段程式要能運作，前提是每個錯誤回應都長得一樣，它才能用同一個欄位判斷。只要有一部分錯誤長得不一樣，攔截器就得為它們寫特例，而且通常是上線後才發現。

所以 SaaS 契約規定每個錯誤回應都是 { statusCode, errorCode, message, requestId }：errorCode 是給程式判斷的固定代碼（例如 NOT_FOUND、FORBIDDEN），message 給人看、可以改字，requestId 下一節講。階段 A 第 2 課做過同樣的東西，這裡要多確認一件容易漏的事：Nest 內建的例外也要被轉換。路由不存在、方法不對、body 太大，這些錯誤不是你的程式丟的，是 Nest 或底層的 Express 丟的；Nest 預設回 { statusCode, message, error }，沒有 errorCode。如果只轉換自己丟的錯誤，前端的攔截器剛好就會遇到上面說的特例。

參考實作分三個檔案，前兩個處理錯誤格式。第一個是 src/common/api-error.ts：程式裡預期內的錯誤（找不到、沒權限）一律用它丟，把狀態碼與 errorCode 綁在一起，這兩個是契約；message 給人看。

export class ApiError extends HttpException {
  constructor(status: number, readonly errorCode: string, message: string) {
    super({ statusCode: status, errorCode, message }, status)
  }
}
export const notFound = () => new ApiError(404, 'NOT_FOUND', '找不到')
export const forbidden = (message = '沒有權限') => new ApiError(403, 'FORBIDDEN', message)

第二個是 src/common/error.filter.ts，一個全域 filter。@Catch() 不帶參數，表示所有例外都經過它，不管是誰丟的。它的工作是把各種來源的例外整理成同一個格式：

  • 自己丟的 ApiError：body 裡已經有 errorCode，直接用。
  • Nest 內建的例外（例如路由不存在的 NotFoundException）：沒有 errorCode，就照 CODE_BY_STATUS 依狀態碼補一個；表上沒有的狀態碼補成 HTTP_<狀態碼>，保證一定有值。
  • 500：一律回 INTERNAL_ERROR，錯誤細節只寫進 log，不回給使用者，因為 stack trace 可能洩漏檔案路徑、SQL 之類的內部資訊（第 16 課會再談）。
const CODE_BY_STATUS: Record<number, string> = {
  400: 'VALIDATION_FAILED', 401: 'UNAUTHENTICATED', 403: 'FORBIDDEN', 404: 'NOT_FOUND',
  413: 'PAYLOAD_TOO_LARGE', 415: 'UNSUPPORTED_MEDIA_TYPE', 429: 'RATE_LIMITED', 503: 'SERVICE_UNAVAILABLE',
}

@Catch()
export class ErrorFilter implements ExceptionFilter {
  constructor(private readonly ctx: RequestContext) {}

  catch(exception: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse<Response>()
    const requestId = this.ctx.requestId
    if (exception instanceof HttpException && exception.getStatus() < 500) {
      const status = exception.getStatus()
      const body = exception.getResponse() as string | { errorCode?: string; message?: string | string[] }
      const message = typeof body === 'string' ? body : [body.message ?? exception.message].flat().join('；')
      const errorCode = (typeof body === 'object' && body.errorCode) || CODE_BY_STATUS[status] || `HTTP_${status}`
      res.status(status).json({ statusCode: status, errorCode, message, requestId })
      return
    }
    // …503 與 500 的處理見參考實作
  }
}

message 那一行處理的是 Nest 的驗證錯誤：ValidationPipe 擋下來時，message 是一個陣列（每個欄位一條），這裡用 flat().join('；') 接成一個字串，讓契約的 message 永遠是字串。

filter 裡的 requestId 是從 this.ctx 讀的，不是自己產生的。這個值從哪來、為什麼不能在 filter 裡隨手產生一個，是第三個檔案要解決的事。

使用者回報錯誤時，怎麼找到那一次請求？

想像上線後客服收到一則回報：「我按儲存，畫面跳出『伺服器發生錯誤』。」API 一天處理幾萬個請求，你要怎麼從 log 裡找到他那一次？時間不夠精確，使用者帳號也不一定登入了。requestId 就是為這件事存在的：每個請求一進來就給它一個唯一的編號，這個編號同時出現在回應標頭、錯誤回應的 body，以及處理這個請求時寫的每一行 log。前端把它顯示在錯誤畫面上（或使用者截圖時一起截到），客服拿著它就能在 log 裡搜到那一次請求的完整經過。

這個機制要成立，編號必須只產生一次，之後每個地方都讀同一份。如果 filter 自己產生一個、log 又產生一個，三個地方的編號對不起來，客服拿著 body 裡的那個去查，什麼都查不到。所以編號在請求最一開始的中介軟體（middleware）產生。src/common/request-id.middleware.ts 做三件事：產生編號，或沿用前面的負載平衡器已經送來的合法值（這樣負載平衡器的 log 和你的 log 用的是同一個編號）；寫進回應標頭 x-request-id；放進 RequestContext，讓後面的程式讀得到。外面送來的值不能全信，所以用 VALID 限制成英數、底線與減號、最多 64 個字元，不合格就自己產生，避免有人把換行或超長字串塞進你的 log：

// src/common/request-context.ts（節錄）
export type Context = { requestId: string; tenantId?: string; userId?: string }

@Injectable()
export class RequestContext {
  private readonly als = new AsyncLocalStorage<Context>()
  run<T>(ctx: Context, fn: () => T): T { return this.als.run(ctx, fn) }
  get store() { return this.als.getStore() }
  get requestId() { return this.store?.requestId ?? 'none' }
}

// src/common/request-id.middleware.ts（節錄）
const VALID = /^[A-Za-z0-9_-]{1,64}$/
use(req: Request, res: Response, next: NextFunction) {
  const incoming = req.get('x-request-id')
  const requestId = incoming && VALID.test(incoming) ? incoming : randomUUID()
  res.setHeader('x-request-id', requestId)
  this.ctx.run({ requestId }, next)
}

接下來的問題是：middleware 產生的編號，要怎麼送到 filter、service、log 手上？一層層當參數傳下去不實際，controller 呼叫 service、service 呼叫另一個 service，每個函式都得多一個參數。RequestContext 用的是 Node 的 AsyncLocalStorage（NestJS 第 24 課）：它提供一個「跟著這次請求走」的儲存空間，同一個請求裡任何地方都讀得到，不用傳參數。

關鍵是 this.ctx.run({ requestId }, next) 這一行。它的意思是：從 next 開始，這個請求後面跑的所有程式（guard、controller、service，包括 await 之後才繼續執行的部分）讀 ctx.store，都拿到這一份 { requestId }；同時進來的另一個請求，跑在它自己的 run 裡，拿到的是它自己的那一份，兩者不會混在一起。這是它跟「放在一個全域變數」的差別：全域變數會被同時進來的請求互相覆蓋。

現在 Context 只裝 requestId，但型別已經先留好 tenantId、userId。第 7 課的 guard 驗過 token 後會把它們填進來，第 8 課的資料庫擴充就是靠它知道「這個請求是哪個租戶」，自動替查詢加條件。換句話說，這一課為了錯誤追查建的請求上下文，之後會成為租戶隔離的一部分。

最後在 app.module.ts 把 filter 和 middleware 登記上去：

providers: [{ provide: APP_FILTER, useClass: ErrorFilter }]
// …
configure(consumer: MiddlewareConsumer) {
  consumer.apply(RequestIdMiddleware).forRoutes('{*path}')   // 每個路徑都套用，包括不存在的
}

forRoutes('{*path}') 讓每個路徑都經過這個 middleware，包括根本不存在的路徑，所以連 404 也有 requestId。用 curl 打一個不存在的路徑，三件事都看得到：標頭的 x-request-id、body 的 errorCode，以及 body 的 requestId 跟標頭是同一個值：

curl -i http://localhost:3100/api/v1/no-such-route
# HTTP/1.1 404 Not Found
# x-request-id: 6f1c…
# {"statusCode":404,"errorCode":"NOT_FOUND","message":"Cannot GET /api/v1/no-such-route","requestId":"6f1c…"}

這個 404 不是你丟的，是 Nest 找不到路由時丟的，但它照樣符合契約。這就是這課開場說的「連打錯路徑得到的 404 都符合契約」。

還有一種錯誤不會經過這個 middleware：壞掉的 JSON 或超過大小上限的 body。Nest 模組登記的 middleware 在 body parser 之後才跑，body parser 先擋下請求，middleware 就沒機會產生編號。參考實作怎麼讓這種錯誤也有 requestId，見課末「參考實作與本課節錄的差異」。

骨架與錯誤格式都好了，最後一步是讓驗收測試知道去哪裡打你的 API。

練習

練習 1：在 my-saas 做出 GET /health/live、GET /health/ready（資料庫 up），以及契約的錯誤格式：不存在的路徑（GET /api/v1/no-such-route）與不存在的方法（DELETE /health/live）都回 404，body 是 { statusCode, errorCode: "NOT_FOUND", message, requestId }，requestId 等於回應標頭 x-request-id。

練習 2：在 repo 加 docs/adr/0001-<主題>.md，寫你的租戶隔離決定，要有「狀態、背景、決定、後果」四段（Markdown 標題；英文 Status、Context、Decision、Consequences 也可以），「後果」不能是空的；另外加 docs/architecture.md（或 README 的「## 架構」）寫模組地圖與依賴方向。

練習 3：你選了「客服工單」，剩三週可以做作品。哪一種安排最能讓面試官看出你的程度？

✓ 作品要展示「在出錯代價最高的地方花力氣」：平台的隔離與權限照契約做完整，業務挑一條有真規則的流程做深，並且有測試證明。a 的十個 CRUD 看不出判斷力，也沒時間寫測試；c 錯在隔離最難事後補：每個查詢、每張表都要回頭改，漏一處就是洩漏。（第 6 課）

練習 4：ADR 0001 選了「共用資料表＋tenant_id」。半年後有個大客戶要求資料放在獨立的資料庫，團隊決定為大客戶另開資料庫。ADR 該怎麼處理？

✓ ADR 記的是「當時為什麼這樣選」，內容不改；新決定寫新的一份，舊的只更新狀態，讀的人才看得到演變與理由。a、b 都抹掉了當時的背景：半年後沒人知道為什麼一開始不選獨立資料庫。d 錯在 commit 訊息分散、沒有背景與後果，找不到也讀不完。（第 6 課，system-design 第 18 課）

練習 5：下面哪一種情況，最有理由改成「每個租戶一個資料庫」？

✓ 每租戶一個資料庫的成本是連線、migration、監控都乘以 N，只有合約或法規要求實體隔離、單獨備份還原，而且租戶數量少時才划算。b 正好相反，十萬個資料庫維運不起。c 用兩道防線（第 8、9 課）加測試就能補，不需要付 N 倍的成本；d 是雜訊鄰居，先用每租戶限流（第 14 課）或把那幾個大租戶單獨搬走。（第 6 課，auth 第 20 課）

自評清單

測試判不出來、但作品裡看得出來的事。每一項自己確認：

  • README 第一段講得出範圍：使用者是誰、你選的業務題目、那條深流程與它最難的規則、刻意不做的事。自己確認：給沒參與的朋友看 30 秒，他說得出這個專案在做什麼。
  • ADR 的背景是你的：寫了你的租戶規模與資料量，不是照抄參考實作。自己確認：把「客服工單」換成別的題目，這份 ADR 會不會需要改；完全不用改，就是寫得太空泛。
  • 依賴方向寫得出來也守得住：docs/architecture.md 的表跟 src/ 的資料夾對得上。自己確認：grep -r "from '../projects" src/auth src/tenancy src/common 沒有結果。
  • 錯誤格式涵蓋 Nest 內建的例外：送一個超過大小上限的 body、一個壞掉的 JSON，回應也有 errorCode 與 requestId。
  • 開發環境一個指令起得來：docker compose up -d --wait 之後 db、redis、mailpit 都是 healthy 或 running，port 全部只綁 127.0.0.1。

常見錯誤

  • 先做業務、平台之後再補：租戶隔離、權限是每個查詢都要遵守的規則，事後補要回頭改每個模組。平台地基（第 6～10 課）先做完，業務模組才開始。
  • filter 只轉換自己丟的錯誤：路由不存在、方法不對、body 太大是 Nest 丟的，沒有 errorCode。filter 要依狀態碼補上，前端才能只寫一套錯誤處理。
  • requestId 在 filter 裡重新產生：body 的 requestId 跟標頭、log 對不上，客服拿著它查不到東西。在中介軟體產生一次、放進請求上下文，filter 與 log 都從那裡讀。
  • ADR 只寫好處：「後果」沒有代價，讀的人不知道這個決定要額外做什麼（例如兩道防線、跨租戶測試），也不知道什麼時候該重新考慮。
  • 改舊的 ADR：決定變了就寫新的一份取代它，舊的只改狀態；改內容會讓「當時為什麼這樣選」消失。
  • 平台模組 import 業務模組：例如 auth 為了註冊時建一個預設 project 去 import projects。依賴變成雙向，之後拆不開；改成業務模組自己監聽事件，或在註冊流程外另做。

小結

  • 這課的任務是在寫業務程式之前，讓 my-saas 有四樣東西：README 的範圍說明、模組地圖、第一份 ADR、符合契約的骨架。
  • 作品範圍分兩半：平台照契約做完整，業務只做一條有真規則的深流程；沒做的事寫進 README 的「刻意不做」。
  • 業務題目自選（工單、預約、進銷存），挑一條在併發下也要成立的規則；在 README 寫出使用者、深流程與最難的規則。
  • 模組依賴單向：業務依賴平台，平台不依賴業務，依賴指向比較不會變的一邊；地圖寫在 docs/architecture.md，資料夾照模組切。
  • ADR 記錄「為什麼」：狀態、背景、決定、後果四段，後果要寫代價；決定改變時寫新的取代，舊的只改狀態。
  • 第一份 ADR 是租戶隔離：共用資料表＋tenant_id 最省，代價是漏條件就洩漏，所以後面要兩道防線與跨租戶測試。
  • 錯誤格式從第一天就照契約：全域 filter 讓 Nest 內建的例外也有 errorCode，前端只寫一套錯誤處理；requestId 在中介軟體產生一次，放進 AsyncLocalStorage 的請求上下文，標頭、body、log 都讀同一份。

下一課做帳號、租戶與 token：註冊時一個交易建立使用者、租戶與 owner，登入發 access token 與會輪替的 refresh token，全域 guard 讓每個路由預設都要登入。

參考實作與本課節錄的差異

本課節錄只在 AppModule 登記 middleware，參考實作讓同一個 middleware 跑兩次，並讓兩次用同一個編號：

  • 跑兩次：app.setup.ts 的 configureApp 在 body parser 之前先 app.use 一次，因為壞掉的 JSON 在 body parser 就失敗，模組 middleware 來不及跑；AppModule 再套用一次，因為 body parser 讀完 body 之後，AsyncLocalStorage 的 store 不一定還在。
  • 同一個編號：middleware 第一行先讀 res.getHeader('x-request-id')，有值就沿用。少了這一步，第二次會再產生一個新的 UUID 蓋掉第一次的標頭，三個地方的編號又對不起來。

為了同一件事，參考實作的 error.filter.ts 取 requestId 時，先讀回應標頭 x-request-id，讀不到才用 this.ctx.requestId：body parser 擋下的請求沒有走到第二次 middleware，store 裡沒有編號，但標頭在 body parser 之前就設好了。節錄省略的 503 與 500 分支也在同一個檔案：503 回 SERVICE_UNAVAILABLE，其他一律寫 log 後回 500 INTERNAL_ERROR。
