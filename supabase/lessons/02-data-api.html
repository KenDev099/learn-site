階段 1：起步：一個 Postgres 加上一組服務 · 第 2 課

表與自動產生的 API：supabase-js 的查詢、關聯與型別

咖啡店的前端做了三個頁面：菜單頁、訂單明細頁、結帳。同事寫了 7 個 API 呼叫，上線前你看了一下 Network 分頁：打開一張有 5 個品項的訂單發出 7 個請求（先查訂單、再查品項、再每個品項各查一次商品名稱）；菜單搜尋把整張 products 抓回瀏覽器，再用 filter 找 100 元以下的；結帳後拿不到新訂單的編號，頁面跳不到「訂單完成」。三個問題都不是 Supabase 的限制，是不知道自動產生的 API 能做到什麼。

這一課把 PostgREST（第 1 課介紹過，看資料庫的表自動產生 REST API 的服務）和 supabase-js 的用法講完整：篩選、排序、分頁、一次請求取回關聯資料、新增修改刪除、錯誤處理，以及從資料庫產生 TypeScript 型別。

這課的路線
  • 一張表一個端點：supabase-js 的每個方法變成網址的哪一段、篩選與分頁怎麼寫。
  • 關聯嵌入：一次請求取回訂單、品項與商品名稱，解決 N+1。
  • 新增、修改、刪除：為什麼拿不到新的 id、為什麼 update 一定要有條件。
  • 錯誤與上限：{ data, error } 不會丟例外、筆數上限 1000。
  • 從資料庫產生型別，以及 API 不夠用的時候。
這課會用到：第 1 課的 supabase-js 入門（createClient(網址, publishable key) 建 client，from('表').select(…) 組出 HTTP 請求）；外鍵與 JOIN（外鍵是「這一欄的值一定是另一張表的某個主鍵」，JOIN 靠它把兩張表接起來，PostgreSQL 課第 8、9 課）；篩選與排序（WHERE、ORDER BY、LIMIT／OFFSET，PostgreSQL 課第 4、5 課）。
環境：這課用到資料庫、gateway、Data API（db、kong、rest），npm run up 預設都會開。課程的 public.orders 只開放給後台（第 1 課看過的 42501），所以練習的測試會在你專屬的 schema 複製一份開放讀取的訂單資料；這一課的範例輸出也是在那份複本上跑的。

一張表一個端點：supabase-js 變成網址

PostgREST 在啟動時讀資料庫有哪些表、欄位、外鍵，每張表產生一個端點 /rest/v1/<表名>。網址的 query string 就是查詢條件。supabase-js 做的事是把方法鏈翻成這個網址，所以先看清楚對應關係，之後除錯只要看 Network 分頁。

菜單頁要「100 元以下、名稱有咖啡、依價格排」。執行後看網址每一段跟哪個方法對應：

const { data, error } = await supabase
  .from('products')
  .select('name, price')
  .lte('price', 100)
  .ilike('name', '%咖啡%')
  .order('price')
  .order('id')
GET /rest/v1/products?select=name,price&price=lte.100&name=ilike.%咖啡%&order=price.asc,id.asc
→ [{"name":"美式咖啡","price":80}]

每個篩選方法變成一個 欄位=運算子.值 的參數，PostgREST 再把它翻成 SQL 的 WHERE。常用的運算子：

supabase-js網址SQL
.eq('id', 1)id=eq.1id = 1
.gt('price', 100)、.lte(…)price=gt.100、lte>、<=（另有 gte、lt、neq）
.in('id', [2, 5])id=in.(2,5)id in (2, 5)
.ilike('name', '%咖啡%')name=ilike.%咖啡%name ilike '%咖啡%'（不分大小寫）
.is('phone', null)phone=is.nullphone is null（eq 比不到 NULL）
.order('price', { ascending: false })order=price.descorder by price desc
.range(3, 5)offset=3&limit=3offset 3 limit 3（第 4～6 筆，兩端都包含）

查表用，不用背。要記的是：條件都要寫在方法鏈裡、交給資料庫算。開場的菜單搜尋把整張表抓回來再 filter，資料少時看不出差別；products 有一萬筆時，每次搜尋都把一萬筆傳進瀏覽器，而且第 4 課開始，抓回來的資料還會受權限影響，前端過濾等於在瀏覽器裡做權限判斷。

分頁要配穩定的排序

分頁用 range(from, to)：第 page 頁（從 1 開始）、每頁 n 筆，就是 range((page - 1) * n, page * n - 1)。上面的範例多寫了一個 .order('id')，原因是拿鐵和卡布奇諾都是 110 元：只依價格排時，資料庫可以用任何順序回傳同價格的兩列，第 2 頁和第 3 頁的邊界剛好切在它們中間時，同一個商品可能出現兩次、另一個消失。最後加一個唯一的欄位（通常是主鍵）當第二排序，順序才固定。

💡 實務上：列表 API 只拿需要的欄位、一定配穩定排序
後台的訂單列表、顧客列表幾乎都要分頁。寫列表時先確認三件事：select 只列畫面用到的欄位（select('*') 會把之後新增的欄位、甚至不該給前端的欄位一起帶出去）；排序最後一個欄位是唯一的；頁數很深（幾萬筆之後）時 offset 會變慢，改成「用上一頁最後一筆的值當條件」的 keyset 分頁（PostgreSQL 課第 29 課）。

關聯嵌入：一次請求取回訂單與品項

單表查詢會寫了，接著解決開場最慢的那一頁：訂單明細。同事的寫法是先查訂單、再查品項、再對每個品項查商品名稱。5 個品項就是 1＋1＋5 = 7 個請求，這叫 N+1 問題（N 個項目，各多查一次）。每個請求都要跑一趟網路，手機網路下一個請求 100 毫秒，這頁就要等快一秒。

PostgREST 的解法叫嵌入（embedding）：在 select 裡寫另一張表的名字和要的欄位，它靠外鍵知道兩張表怎麼接，在資料庫裡做好 JOIN，把結果組成巢狀的 JSON。執行後看回應的形狀：

const { data, error } = await supabase
  .from('orders')
  .select('id, total, order_items(quantity, unit_price, products(name))')
  .eq('id', 1)
  .single()
{
  "id": 1,
  "total": 190,
  "order_items": [
    { "quantity": 1, "unit_price": 80,  "products": { "name": "美式咖啡" } },
    { "quantity": 1, "unit_price": 110, "products": { "name": "拿鐵" } }
  ]
}
  • order_items(…) 是陣列：order_items.order_id 有外鍵指向 orders.id，一張訂單對多個品項。
  • products(name) 是物件：order_items.product_id 指向 products.id，一個品項對一個商品。
  • .single() 讓回傳值是一個物件而不是陣列，下一節細講。

兩張表之間沒有外鍵時，嵌入會回錯誤（PGRST200，找不到關聯）：PostgREST 不會猜要用哪一欄接。所以在 Supabase 裡，外鍵不只是資料正確性的保護，也是 API 能不能嵌入的開關。

嵌入的篩選與 !inner

想找「有點起司蛋糕（product_id 6）的訂單」，直覺會在嵌入的表上加條件。執行後比較兩種寫法回傳的訂單數：

// 寫法 1：只篩選嵌入的資料，訂單本身不受影響
supabase.from('orders').select('id, order_items(product_id)').eq('order_items.product_id', 6)
// → 8 張訂單全部回來，沒點起司蛋糕的訂單 order_items 是 []

// 寫法 2：!inner 讓嵌入的條件也篩選父表
supabase.from('orders').select('id, order_items!inner(product_id)').eq('order_items.product_id', 6)
// → 只有第 6、8 張訂單

預設的嵌入是 LEFT JOIN 的意思：條件只決定「嵌入的陣列裡放哪些」，父表一列都不少。加 !inner 變成 INNER JOIN：嵌入的部分沒有符合的列，父表那一列也不要。這是最常寫錯的地方，看到結果多出一堆空陣列，就是少了 !inner。

💡 實務上：在 Network 分頁數請求
效能問題在 Supabase 前端最常見的形狀就是 N+1：列表的每一列再各打一次 API。code review 時看到迴圈裡有 await supabase.from(…)，或 Vue 元件的每一列在 onMounted 裡自己查資料，就要問能不能在父層用一次嵌入拿完。打開頁面看 Network 分頁裡 /rest/v1/ 的請求數，是最快的檢查方式。

新增、修改、刪除

讀資料的問題解決了，接著是開場的第三個問題：結帳後拿不到新訂單的 id。先看 insert 預設回傳什麼：

const { data, error } = await supabase.from('orders').insert({ customer_id: 2, total: 290 })
// data → null，HTTP 201、沒有內容

PostgREST 寫入時預設不回傳資料（請求帶著 Prefer: return=minimal），省下傳輸，也不需要讀取權限。要拿回新的列，接 .select()，它會改送 return=representation，相當於 SQL 的 insert … returning：

const { data, error } = await supabase.from('orders').insert({ customer_id: 2, total: 290 }).select('id').single()
// data → { id: 101 }

.select() 回傳的是陣列（一次可以新增好幾列），只新增一列時再接 .single() 變成物件。兩個「只要一筆」的方法差在 0 筆時：

1 筆0 筆2 筆以上
.single()物件錯誤 PGRST116（HTTP 406）錯誤 PGRST116
.maybeSingle()物件null，沒有錯誤錯誤

「一定存在」的情況（剛新增的列、用主鍵查自己的資料）用 single()；「可能不存在」的情況（使用者在網址輸入的訂單編號）用 maybeSingle()，找不到時顯示「查無此訂單」，而不是當成錯誤。

update 與 delete 一定要有篩選

修改和刪除的寫法是先說要改什麼，再用篩選說改哪幾列：

await supabase.from('orders').update({ total: 300 }).eq('id', 101)
await supabase.from('orders').delete().eq('id', 101)

忘了篩選會怎樣？執行後看錯誤：

await supabase.from('orders').update({ total: 0 })
// error → { code: '21000', message: 'UPDATE requires a WHERE clause' }

Supabase 在 PostgREST 連資料庫用的角色上載入了 safeupdate 這個擴充套件：從 API 來的 UPDATE、DELETE 沒有 WHERE 一律拒絕，避免一行程式清掉整張表。它只是防手滑，不是權限：真的想全部改，加一個永遠成立的條件就過了。誰能改哪幾列，要靠第 4 課的 RLS。

還有一個寫入方法 upsert：有就更新、沒有就新增（SQL 的 insert … on conflict do update，PostgreSQL 課第 31 課）。它靠主鍵或唯一約束判斷「有沒有」，例如 .upsert({ order_id: 101, product_id: 2, quantity: 3, unit_price: 110 }) 用 order_items 的複合主鍵決定是改數量還是新增品項；要用別的唯一欄位判斷就加 { onConflict: '欄位' }。

錯誤與上限：{ data, error } 不會丟例外

前面每個範例都寫了 const { data, error }，因為 supabase-js 的查詢不會丟例外：HTTP 4xx、5xx 都變成 error，data 是 null。沒檢查 error 的程式不會停下來，而是拿著 null 繼續跑，錯誤在很遠的地方才出現（例如「Cannot read properties of null」），或者根本沒出現：結帳顯示成功，訂單其實沒建立。

const { data, error } = await supabase.from('products').select('nme')
if (error) throw new Error(`讀菜單失敗：${error.message}`)

error.code 有兩種來源，看到碼就知道往哪裡查：

code來源常見原因
42501Postgres：沒有權限沒有 GRANT（第 3 課），或寫入違反 RLS（第 4 課）
42703Postgres：欄位不存在select 的欄位名稱打錯（hint 會建議正確的名字）
23503、23505Postgres：違反外鍵、唯一約束顧客不存在、重複新增
21000safeupdateupdate／delete 沒有篩選
PGRST116PostgRESTsingle() 拿到 0 筆或多筆
PGRST200、PGRST205PostgREST嵌入找不到外鍵、表不在 schema cache（剛建的表、或 schema 不對）

五位數字的是 Postgres 的錯誤碼（SQLSTATE），PGRST 開頭的是 PostgREST 自己的。查表用，不用背。

還有一個 supabase-js 2.119.0 的行為要知道：讀取（GET、HEAD）遇到 HTTP 503、520 這兩種「暫時性」錯誤時，它會自動重試最多 3 次，間隔 1、2、4 秒，所以 API 掛掉時查詢可能要等 7 秒才拿到 error。寫入不會自動重試，因為重送一次可能變成兩張訂單。

計數與 1000 筆上限

分頁需要總筆數才能畫頁碼。加 { count: 'exact' }，PostgREST 會另外算總數，放在回應的 count；只要總數、不要資料就再加 head: true（發 HEAD 請求）：

const { data, count } = await supabase.from('products').select('name', { count: 'exact' }).range(0, 1)
// data → 2 筆，count → 6
const { count: total } = await supabase.from('products').select('*', { count: 'exact', head: true })
// total → 6

exact 是真的跑一次 count(*)，表很大時會慢；另外有 planned（用統計資訊估）、estimated（小的時候精確、大的時候估）可選。

另一個要知道的上限：config.toml 的 [api] max_rows = 1000，一個請求最多回 1000 列，超過的部分不會報錯，直接截掉。雲端專案在 Dashboard 的 API 設定裡也有這個值，預設同樣是 1000。「匯出全部訂單」這種功能沒做分頁，資料過了一千筆就默默少了。

💡 實務上：把 { data, error } 包成一個會丟錯的小函式
每個呼叫都寫一次 if (error) throw … 很容易漏。Vue 專案常見的做法是在 composable 或 API 層統一處理：檢查 error、依 code 轉成使用者看得懂的訊息（42501 →「沒有權限」、23505 →「已經存在」）、把原始錯誤送到錯誤追蹤服務。客服回報「按了沒反應」時，九成是某個 error 被吞掉了。

從資料庫產生 TypeScript 型別

到這裡 data 的型別都是 any：欄位名稱打錯（nme）要到執行時才知道。Supabase CLI 可以讀資料庫的結構，產生 TypeScript 型別檔：

cd supabase/practice
npx supabase gen types typescript > database.types.ts

CLI 3.x 預設就是本機資料庫（2.x 的教學會寫 --local，3.1.0 會提示它不需要；要產生雲端專案的型別改加 --remote）。產生出來的檔案，每張表有三個型別：

export type Database = {
  public: {
    Tables: {
      orders: {
        Row:    { customer_id: number; id: number; ordered_at: string; total: number }
        Insert: { customer_id: number; id?: never; ordered_at: string; total: number }
        Update: { customer_id?: number; id?: never; ordered_at?: string; total?: number }
        Relationships: [/* 外鍵，supabase-js 用它推出嵌入結果的型別 */]
      }
      …
  • Row：讀出來的一列。可以是 NULL 的欄位會是 string | null。
  • Insert：新增時要傳的物件。有預設值的欄位變成可選；generated always as identity 的 id 是 id?: never，代表「不能自己給」。
  • Update：全部可選，只傳要改的欄位。

把 Database 傳給 createClient<Database>(…) 之後，from('orders') 只接受存在的表名，select('id, total') 的結果型別會自動推成 { id: number; total: number }[]，連嵌入的巢狀結構都推得出來。檔案裡也附了 Tables<'orders'>、TablesInsert<'orders'> 這些捷徑型別，在元件的 props 裡用。

💡 實務上：型別檔進 git，CI 檢查它有沒有過期
型別檔是從資料庫產生的，有人改了表卻忘了重新產生，前端的型別就在說謊。常見做法是把 database.types.ts 進 git，CI 裡啟動本機 Supabase、套用 migration（第 9 課）、重新產生一次，跟 git 裡的版本比較，不一樣就讓 PR 失敗。這樣「改了表」和「前端跟著改」會出現在同一個 PR 裡被一起審。

什麼時候 API 不夠用

最後回到結帳。練習 3 會用三個請求完成它：查商品價格、新增訂單、新增品項。這有兩個 Data API 解決不了的問題：

  • 不是同一個交易：每個 HTTP 請求是一個獨立的交易（PostgreSQL 課第 18 課）。新增訂單成功、新增品項失敗時，資料庫留下一張沒有品項的訂單，前端沒辦法 rollback。
  • 計算在前端：總價是前端算好送上來的，任何人都能自己組一個 total: 1 的請求。

這類「好幾步要一起成功或一起失敗、或結果不能讓使用者決定」的寫入，要放進資料庫函式，用 supabase.rpc('place_order', …) 一次呼叫（第 8 課）。Data API 適合的是單表的讀寫，加上權限能用列描述的情況。

練習

練習 1、3 的測試會在你專屬的 schema 複製一份咖啡店的四張表（cafe.ts，不用改），傳給你的函式的 client 已經指向那份複本；練習 2 讀的是共用的 public.products。三題的 client 都用 publishable key。

練習 1：完成 getOrderDetail(client, id)：用一個請求取回訂單的 id、total，每個品項的 quantity、unit_price，以及品項對應的商品名稱（products: { name }），回傳一個物件；找不到這張訂單回傳 null；API 回錯誤時丟出 Error。測試會用 proxy 數你發了幾個請求。

練習 2：完成 searchMenu(client, { maxPrice, keyword, page })：只取 name、price；有 maxPrice 時只要價格小於等於它，有 keyword 時只要名稱包含它（不分大小寫）；依價格、再依 id 由小到大；回傳第 page 頁（從 1 開始，預設 1），每頁 PAGE_SIZE 筆。篩選、排序、分頁都要交給 API。

練習 3：完成 placeOrder(client, customerId, items)：用一個請求查出這些商品的價格（有商品查不到就丟出 Error，而且不要新增訂單），新增一張訂單（total 用資料庫的價格算），再新增每個品項（unit_price 也用資料庫的價格），回傳新訂單的 id。任何一步 API 回錯誤都要丟出 Error。

練習 4：下面的 Database 是 supabase gen types 產生的檔案節錄。不用它附的捷徑型別，自己寫出 Tables<T>（表 T 讀出來的一列）和 TablesInsert<T>（新增時要傳的物件），再完成兩個函式：

  • toCard(order, customer)：回傳 { title: '#<訂單 id> <顧客名>', total, city }，城市沒填（NULL）時 city 是 '未填'。
  • newOrder(customerId, total, now)：回傳新增訂單要傳的物件，ordered_at 是 now 的 ISO 字串；不帶 id（資料庫產生）。

不能用 any：型別測試會檢查 Tables<'orders'> 就是 orders 的 Row、新增時帶 id 會報錯。

練習 5：supabase.from('orders').select('id, order_items(quantity)') 能把品項嵌入訂單裡，PostgREST 是怎麼知道兩張表怎麼接的？

✓ PostgREST 啟動時讀資料庫的外鍵，嵌入就是靠外鍵在資料庫裡做 JOIN，整個結果是一個請求。a 錯在它不猜欄位名稱，沒有外鍵就回 PGRST200。c 描述的是 N+1，嵌入正是用來避免它。

練習 6：前端寫了 await supabase.from('orders').delete()，忘了加 .eq('id', …)。在 Supabase 會發生什麼事？

✓ Supabase 讓 API 的 UPDATE、DELETE 必須有 WHERE（safeupdate），錯誤放在 error。a 是最多人以為的結果，但 safeupdate 先擋下了；不過它只防手滑，加個永遠成立的條件照樣能全刪，誰能刪哪幾列還是要靠 RLS。b 錯在 supabase-js 不丟例外，也不是它檢查的。

練習 7：結帳的程式寫成下面這樣。顧客編號不存在時，使用者會看到什麼？

const { data } = await supabase.from('orders').insert({ customer_id: 999, total: 190 }).select('id').single()
router.push(`/orders/${data?.id}/done`)

✓ supabase-js 不丟例外，HTTP 409 的外鍵錯誤（23503）變成 error，data 是 null。b 是最常見的誤解：以為失敗會丟例外，所以沒寫檢查。修法是 if (error) throw … 或顯示錯誤訊息，不要只解構 data。

常見錯誤

  • 抓整張表回來在前端篩選：資料一多就慢，而且把不需要的資料送進瀏覽器。條件寫成 eq、lte、ilike、in，分頁用 range。
  • 迴圈裡每一列各查一次（N+1）：用嵌入 select('…, 子表(…)') 一次取回；兩張表要有外鍵。
  • 嵌入的條件以為會篩父表：預設只篩嵌入的陣列，父表一列都不少；要連父表一起篩就加 !inner。
  • 分頁只依一個會重複的欄位排序：同值的列在頁與頁之間會重複或消失。最後加主鍵當第二排序。
  • insert 後拿不到 id：寫入預設不回傳資料，要接 .select()，一筆時再接 .single()。
  • 用 single() 查可能不存在的資料：0 筆時是錯誤 PGRST116；可能不存在就用 maybeSingle()。
  • 只解構 data、不看 error：supabase-js 不丟例外，錯誤會被靜靜吞掉。
  • 以為查詢會回全部資料：一個請求最多 max_rows（預設 1000）列，超過的直接截掉，不會報錯。

小結

  • PostgREST 每張表一個端點 /rest/v1/<表>；supabase-js 的方法鏈翻成 query string：select、eq／lte／in／ilike／is、order、range。條件與分頁交給資料庫，分頁配唯一的第二排序。
  • 嵌入靠外鍵在資料庫裡 JOIN，一次請求取回巢狀資料，解決 N+1；嵌入的條件預設只篩子表，!inner 才連父表一起篩。
  • 寫入預設不回傳資料，要 .select()；single() 在 0 筆時是錯誤、maybeSingle() 回 null；API 的 update／delete 沒有篩選會被 safeupdate 拒絕（21000），但它不是權限。
  • supabase-js 回 { data, error } 不丟例外，一定要檢查 error；code 是 Postgres 的 SQLSTATE 或 PGRST 碼。一個請求最多 1000 列。
  • npx supabase gen types typescript 產生 Database 型別（Row、Insert、Update），傳給 createClient<Database>；型別檔進 git，CI 檢查有沒有過期。
  • 好幾步要在同一個交易、或計算不能交給前端的寫入，Data API 做不到，要用 RPC（第 8 課）。
