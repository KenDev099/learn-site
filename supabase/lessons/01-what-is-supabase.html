階段 1：起步：一個 Postgres 加上一組服務 · 第 1 課

Supabase 是什麼：一個 Postgres 加上一組服務

咖啡店要做線上點餐。前端用 Vue 你很熟，但後端要有：存菜單和訂單的資料庫、給前端呼叫的 API、顧客註冊登入、上傳付款收據、店員即時看到新訂單、接金流的付款通知。全部自己用 NestJS 寫，加上部署和維運，一個人要好幾個月。有人說「用 Supabase 就不用寫後端」。這句話只對一半：Supabase 幫你省掉很多樣板程式，但不懂它怎麼組成，你會把不該公開的 key 放進前端，或以為「沒有後端」就「沒有權限問題」，結果顧客 A 看得到顧客 B 的訂單。

這一課先講清楚 Supabase 由哪些服務組成、每個服務負責什麼、權限為什麼是寫在資料庫裡，然後在你的 Mac 上把整套本機 Supabase 跑起來，用三種方式讀同一份菜單，最後談什麼時候該用這類服務、什麼時候不該。

這課的路線
  • 咖啡店的後端要做哪些事、Supabase 各用哪個服務做：先回答「Supabase 到底是什麼」。
  • 權限寫在資料庫裡：前端直接打 API 時，是誰在擋人。
  • 在 Mac 上啟動本機 Supabase：安裝、port、要開哪些服務、佔多少記憶體。
  • 同一份菜單的三個入口：直連資料庫、HTTP、supabase-js。
  • 什麼時候該用、什麼時候不該用：跟自己寫後端、跟 Firebase 比。
這課會用到：表、欄、主鍵（一張表就像一份有固定欄位的試算表，主鍵是每一列的唯一編號，PostgreSQL 課第 2 課）；認證與授權的差別（認證是「你是誰」，授權是「你能做什麼」，認證課第 1 課）；容器與映像（映像是打包好的程式，容器是跑起來的那一份，devops 課第 7 課）。
環境：這課要 Docker Desktop（記憶體設 6 GB 以上）和 Node 24。本機 Supabase 第一次啟動要下載約 5 GB 的映像。這課用到的服務：資料庫、gateway、Data API、Auth、Studio。

所以 Supabase＝一個 PostgreSQL＋圍著它的一組服務。每個服務都是獨立的開源程式，各跑在自己的容器裡；它們共用同一個資料庫：使用者存在 auth 這個 schema、檔案資訊存在 storage schema、你的表預設在 public schema。schema 是資料庫裡的資料夾，用來把表分組，表的完整名稱寫成 schema.表名，例如 public.products。

這種「後端功能做成現成服務，前端直接呼叫」的產品叫 BaaS（Backend as a Service，後端即服務）。Supabase 跟其他 BaaS 最大的不同是：底下是你完全擁有的 PostgreSQL。你可以直連、下任何 SQL、用 pg_dump 整個匯出搬走。

權限寫在資料庫裡

上一節的表格少了一個傳統後端一定有的東西：檢查權限的那一層。用 NestJS 寫的時候，前端呼叫 GET /orders/42，你的 controller 先確認「這張訂單是不是登入的人的」，再去查資料庫。用 Supabase 時，前端直接呼叫 PostgREST，PostgREST 直接查資料庫，中間沒有你寫的程式。那誰來擋？

答案是資料庫自己。每個請求帶著兩樣東西：apikey（代表「哪個 app」）和登入後拿到的 JWT（JSON Web Token，Auth 簽發、內容是「這是哪個使用者」的憑證，認證課第 8 課教過它的結構）。服務把它們換成一個 PostgreSQL 的角色（role，資料庫裡的帳號）去查詢：沒登入是 anon，登入了是 authenticated。接著資料庫用兩道門檢查：

  1. GRANT：這個角色能不能碰這張表。沒給就直接拒絕，錯誤碼 42501（permission denied）。
  2. RLS（Row Level Security，列層級安全）：能碰這張表的話，能看到、能改哪幾列。例如「訂單只有下單的人看得到」。

所以「用 Supabase 就不用寫後端」的正確說法是：不用寫 API 的樣板程式，但權限設計從後端的程式碼搬到了資料庫的規則裡，而且更重要了，因為前端的 key 任何人都拿得到。第 3 課講 key 與角色，第 4、5 課整個階段在講 RLS。

💡 實務上：審 Supabase 專案先看資料庫權限
接手一個 Supabase 專案或審 PR 時，資深工程師第一件事不是看前端程式，而是看資料庫：哪些表開了 RLS、每張表給了哪些角色什麼 GRANT、policy 寫什麼條件。前端程式寫得再小心都沒用，任何人都能拿你的 key 自己組請求。資安團隊問「顧客資料怎麼保護」時，答案要能指到具體的 policy。

在 Mac 上啟動本機 Supabase

知道了它由哪些服務組成，接著把整套跑在自己的電腦上。Supabase 有雲端版（supabase.com 上建專案），也有本機開發環境：用 Supabase CLI（命令列工具）在 Docker 裡把每個服務跑成一個容器，行為跟雲端幾乎一樣，不需要帳號、不會產生費用。這門課全部在本機做。

安裝與啟動

cd learn/supabase/practice
npm ci          # 安裝課程鎖定的版本：Supabase CLI 3.1.0、supabase-js 2.119.0 等
npm run up      # 啟動本機 Supabase（第一次要下載約 5 GB 的映像，幾分鐘到十幾分鐘）

課程用 npm ci 把 CLI 裝在 supabase/practice/node_modules，用 npx supabase … 執行。你電腦上如果已經裝了別的版本的 CLI（例如 Homebrew 裝的 2.x），不用升級也不用移除，課程不會用到它。選 CLI 3.1.0 的原因：3.x 從 2026 年 11 月起是預設版本，而且它預設只操作本機，要改雲端專案得明確加 --remote，還會先問你確定嗎，練習時不會誤動到正式環境。網路上較舊的教學會出現 --linked、--db-url 這些 2.x 的旗標，3.x 改成 --remote。

npm run up 實際執行的是：

supabase start --workdir . -x imgproxy,logflare,vector,supavisor
  • --workdir .：指定專案資料夾。CLI 不指定時會往上層找名叫 supabase 的資料夾，而這門課的課程資料夾本身就叫 supabase，容易找錯。專案的設定檔在 supabase/practice/supabase/config.toml（兩層 supabase：外層是課程、內層是 CLI 的專案）。
  • -x（exclude）：不啟動這些服務。imgproxy 做圖片縮圖（雲端付費功能），logflare 和 vector 收集 log，supavisor 是連線池（第 9 課講），這門課都用不到，排掉省記憶體。

啟動完成後，在同一個資料夾執行 npx supabase status 看網址與 key：

啟動時如果有服務沒通過健康檢查而失敗，先再執行一次 npm run up（已經起來的容器會直接沿用）；還是失敗，訊息會寫出是哪個容器，用 docker logs supabase_<服務>_learn-supabase 看原因。啟動完成時 CLI 會提醒所有服務都開在 0.0.0.0：同一個網路裡的其他電腦也連得到，而 key 和密碼都是公開的預設值，所以在公共 Wi-Fi 上不用的時候就 down 掉。

其他指令：npm run down 停止（資料保留，下次 up 只要幾十秒）、npm run status 等於 npx supabase status。要整個重來（刪掉資料）才用 npx supabase stop --no-backup 再 up。

為什麼 port 不是預設的 54321

Supabase CLI 預設用 543xx 的 port（API 54321、資料庫 54322、Studio 54323）。如果你同時有別的 Supabase 專案在本機跑，兩邊會搶同一個 port，後啟動的那個會失敗。這門課在 config.toml 改成 554xx，並把專案名稱設成 learn-supabase：

project_id = "learn-supabase"   # 容器名稱會是 supabase_db_learn-supabase、supabase_kong_learn-supabase…

[api]
port = 55421                    # API gateway（Project URL）
auto_expose_new_tables = false  # 新表不會自動開放給 API（第 3 課）

[db]
port = 55422                    # PostgreSQL

[studio]
port = 55423

容器名稱帶著 project_id，所以兩個專案的容器、資料 volume 不會混在一起。用 docker ps 會看到十個 supabase_…_learn-supabase 容器。

💡 實務上：一台電腦跑好幾個 Supabase 專案
接案或在公司同時維護兩三個 Supabase 專案很常見。每個專案的 config.toml 都設自己的 project_id 和一組不重疊的 port，寫進 git，團隊每個人拿到的設定就一樣。啟動失敗、訊息提到 port 已被使用時，先 docker ps 看是不是另一個專案還開著，用 npx supabase stop（在那個專案的資料夾）停掉它。

同一份菜單的三個入口

環境跑起來之後，用三種方式讀同一份菜單。課程啟動時已經建好咖啡店的四張表（customers、products、orders、order_items）和資料，跟 PostgreSQL 課用的是同一份。下面的指令都在 supabase/practice 資料夾執行。

入口 1：直連資料庫

npx supabase db query "select name, price from products order by price limit 3"
┌──────────┬───────┐
│ name     │ price │
├──────────┼───────┤
│ 可頌     │ 70    │
│ 美式咖啡 │ 80    │
│ 伯爵紅茶 │ 90    │
└──────────┴───────┘

supabase db query 用超級使用者 postgres 直連資料庫執行一句 SQL。這條路不經過 gateway，也不受 GRANT、RLS 限制，所以只給開發者和伺服器端程式用。select 欄位 from 表 order by 欄位 limit 筆數 是最基本的查詢：取哪些欄、從哪張表、照什麼排、取幾筆（PostgreSQL 課第 4、5 課有完整說明）。

入口 2：HTTP

同樣的查詢，換成 PostgREST 產生的 API。執行後看回傳的 JSON 跟上一格的表格是不是同一份資料：

curl "http://localhost:55421/rest/v1/products?select=name,price&order=price&limit=3" \
  -H "apikey: sb_publishable_ACJWlzQHlZjBrEguHvfOxg_3BJgxAaH"
[{"name":"可頌","price":70},
 {"name":"美式咖啡","price":80},
 {"name":"伯爵紅茶","price":90}]

網址的每一段對應 SQL 的一部分：/rest/v1/products 是表名、select=name,price 是要哪些欄、order=price 是排序、limit=3 是筆數。PostgREST 把網址翻譯成 SQL，用 anon 角色執行，結果轉成 JSON。apikey 這個 header 告訴 gateway 是哪個 app 在呼叫。

換一張表試試。執行後看回應是不是錯誤：

curl "http://localhost:55421/rest/v1/orders?select=id" \
  -H "apikey: sb_publishable_ACJWlzQHlZjBrEguHvfOxg_3BJgxAaH"
{"code":"42501","details":null,
 "hint":"Grant the required privileges to the current role with: GRANT SELECT ON public.orders TO anon;",
 "message":"permission denied for table orders"}

這就是上一節的第一道門：課程的設定只把 products 的讀取權限給了 anon，orders 沒有給，所以沒登入的人一筆都拿不到。訂單應該怎麼開放（只給下單的人看自己的），是第 3、4 課的主題。

本機跟雲端不一樣的地方：本機的 gateway 就算沒帶 apikey、或帶了錯的 key 也會放行（以 anon 身分）；雲端專案會直接回 401。所以練習的測試不靠伺服器的回應判斷你有沒有帶 key，而是在中間攔下請求檢查 header。寫程式時一律照雲端的規則：每個請求都帶 apikey。

入口 3：supabase-js

前端實際上用的是官方的 JavaScript 套件 supabase-js。它做的事就是組出上面那個網址、帶上 header、呼叫 fetch：

import { createClient } from '@supabase/supabase-js'

const supabase = createClient('http://localhost:55421', 'sb_publishable_ACJWlzQHlZjBrEguHvfOxg_3BJgxAaH')
const { data, error } = await supabase.from('products').select('name, price').order('price').limit(3)

createClient 只需要 Project URL 和 publishable key；from('products').select(…).order(…) 對應網址的每一段。它不會丟出例外，結果和錯誤分別放在 data、error。第 2 課整課在講它的查詢、關聯和型別。這一課的練習 3 刻意用原生 fetch 寫一次，讓你確定它底下就只是 HTTP。

💡 實務上：除錯時先把 supabase-js 還原成 HTTP
前端回報「資料拿不到」時，打開 DevTools 的 Network 分頁，找到打 /rest/v1/… 的那個請求：網址看得出查詢條件，回應看得出是 42501（權限）、空陣列（RLS 擋掉或真的沒資料）還是 400（欄位名稱打錯）。把它複製成 curl 自己重打，就能排除前端程式的問題。三個入口查到的結果不同時，差別幾乎都出在「用哪個角色查」。

什麼時候該用、什麼時候不該用

看過它怎麼運作之後，回到開場的問題：咖啡店該不該用 Supabase？跟另外兩條路比：

Supabase自己寫後端（例如 NestJS＋PostgreSQL）Firebase
資料庫PostgreSQL：關聯、JOIN、交易、外鍵都有自己選，通常也是 PostgreSQLFirestore：文件型（NoSQL），沒有 JOIN
API表建好就有每個端點自己寫用 SDK 直接讀寫文件
權限寫在哪資料庫的 GRANT 與 RLS（SQL）後端程式碼Security Rules（Firebase 自己的規則語言）
複雜的業務流程放資料庫函式或 Edge Function最自由放 Cloud Functions
想搬走的時候資料是標準的 PostgreSQL，可以 pg_dump 帶走；服務也都開源、能自架本來就是你的資料模型與規則都綁在 Firebase

適合用 Supabase 的訊號：功能以「列表、新增、修改、刪除」為主；權限能用「這筆資料屬於誰、屬於哪個團隊」說清楚；團隊小、要快上線；需要登入、檔案、即時通知這類標準功能。要另外寫伺服器端程式（Edge Function 或自己的後端）的訊號：

  • 要相信的不是使用者的輸入：例如付款。金流的通知要驗簽章、更新訂單、寄收據、對帳，這些步驟不能交給前端，因為前端的程式和請求使用者都改得到（第 8 課）。
  • 流程跨好幾個外部系統：發票、物流、ERP，失敗要重試、要冪等。
  • 重運算或長時間的工作：報表、影像處理。
  • 團隊沒有人熟 SQL 與 RLS：權限全在資料庫，沒人看得懂 policy 是很大的風險。

實務上常見的是混合：Supabase 管資料、登入、檔案與即時通知，付款這類流程放 Edge Function 或另一個後端服務，兩邊用同一個資料庫。這門課的期末專題就是這樣組的。

💡 實務上：評估要不要用 Supabase 時先問的四件事
資深工程師會先問：(1) 權限能不能用「資料屬於誰」表達，有沒有很複雜的審核流程；(2) 有沒有金流、對帳這類一定要在伺服器端做的流程，打算放哪裡；(3) 資料有沒有法規要求要放在特定地區或自架；(4) 團隊誰負責寫和審 RLS。四個問題都有答案，再談雲端費用（第 9 課）。結論寫進架構決策紀錄，條件改變時重新評估。

練習

本機練習的流程：在 learn 資料夾執行頁面上的指令，第一次會把起始檔複製到 supabase/practice/work/01/，你改那裡的檔案、存檔、再執行一次，切回這一頁就看得到結果。測試會先檢查 Docker 和本機 Supabase 有沒有在跑，沒有的話會告訴你要執行哪個指令。

練習 1：照上面的步驟啟動本機 Supabase（cd supabase/practice && npm ci && npm run up），執行 npx supabase status，把 APIs 的 Project URL 和 Authentication Keys 裡前端該用的那把 key 填進 stack.json 的 apiUrl、publishableKey（網址寫 localhost 或 127.0.0.1 都可以）。測試會自己再讀一次 supabase status 比對、確認這課需要的服務都在跑，並用你填的兩個值真的讀一次菜單。

練習 2：寫 gateway 的轉送規則 serviceFor(path)：傳入請求的路徑（可能帶 ? 之後的 query string），回傳要轉給哪個服務。規則：

  • 路徑的第 1 段是服務名稱（rest、auth、storage、realtime、functions、graphql），第 2 段一定是 v1；後面可以沒有、也可以接任意路徑。
  • 其他情況都回傳 null：服務名稱不在清單裡、版本不是 v1、只是開頭的字一樣（/restaurants、/rest/v1abc）、大小寫不同。
  • query string 裡的內容不影響結果，例如 /rest/v1/products?select=auth 還是 rest。

真的 gateway 設定也是這樣寫：每個服務一條規則，比對路徑前綴 /rest/v1/，轉給對應的容器，並把前綴拿掉。所以「路徑打錯一個字」的請求不會到達任何服務，回應的是 gateway 的 404，而不是 PostgREST 的錯誤格式；看到不是 JSON 錯誤格式的 404，先檢查路徑。

練習 3：在 menu.ts 完成 fetchMenu(apiUrl, key)：用原生 fetch 向 <apiUrl>/rest/v1/products 發一個請求，帶上 apikey header，取回只有 name、price 兩欄、先依價格再依名稱由小到大排好的菜單；回應不是 2xx 時丟出 Error。測試會在你的程式和 API 之間放一個記錄請求的 proxy，檢查你發了幾個請求、用了哪把 key、欄位和排序是不是交給 API 處理，再拿結果跟資料庫比對。

練習 4：咖啡店的前端直接用 supabase-js 查 orders，沒有自己的後端。是誰決定顧客 A 能不能讀到顧客 B 的訂單？

✓ 請求最後都落在資料庫，擋人的是資料庫裡的 GRANT（表）與 RLS（列）。a 最常見：在瀏覽器過濾等於沒擋，任何人都能自己組請求、跳過你的前端程式。b、d 描述的自動隔離不存在，表沒寫 policy 就沒有列層級的保護。

練習 5：同事在 DevTools 裡看到前端打包檔裡有 sb_publishable_…，緊張地說 key 外洩了，要立刻輪替。比較好的回應是？

✓ publishable key 一定會出現在前端，能做什麼完全由資料庫權限決定（第 3 課）。c 錯在 VITE_ 開頭的變數會被直接寫進打包檔，照樣看得到。d 最危險：secret key 繞過所有權限，放進前端才是真的外洩。

練習 6：下面哪一項需求，只靠前端加 supabase-js、不寫任何伺服器端程式，做不好？

✓ 付款通知是金流打給你的伺服器，要用只有伺服器知道的密鑰驗簽章，訂單狀態也不能讓前端自己改，這要放 Edge Function 或自己的後端（第 8 課）。b 用 RLS 的「擁有者」規則就能做（第 4 課），c 是公開讀取，d 是 Realtime，都不需要自己寫伺服器端程式。

常見錯誤

  • 以為用了 Supabase 就沒有權限問題：前端直接打 API，權限全靠資料庫的 GRANT 與 RLS。每一張要給前端用的表，都要想清楚誰能讀、誰能改哪幾列。
  • 把 secret key 放進前端：它對應的角色繞過所有 RLS。前端只放 publishable key；secret key 只放伺服器與 Edge Function 的環境變數。
  • 在前端過濾資料當作權限：先把全部訂單抓回來、再用 JavaScript 只顯示自己的，等於把別人的資料送進瀏覽器。過濾要在資料庫做，權限要寫成 RLS。
  • 不帶 --workdir 執行 CLI：在 learn 資料夾執行時，CLI 往上找 supabase 資料夾會找到課程資料夾。這門課的指令都在 supabase/practice 裡執行，或用 npm run …。
  • 兩個 Supabase 專案用同一組 port：後啟動的會失敗。每個專案設自己的 project_id 和 port，這門課用 554xx。
  • 以為本機和雲端行為完全一樣：本機不帶 apikey 也能打 API、密碼都是 postgres。程式照雲端的規則寫，上線前在雲端的測試專案再驗一次。

小結

  • Supabase＝一個你完全擁有的 PostgreSQL＋一組服務：PostgREST（/rest/v1）、Auth（/auth/v1）、Storage、Realtime、Edge Functions，前面由 API gateway 依路徑轉送，Studio 是管理介面。
  • 前端直接呼叫 API，中間沒有你寫的程式；權限由資料庫決定：請求換成角色（anon、authenticated），先過 GRANT（表），再過 RLS（列）。
  • 本機用 Supabase CLI 3.1.0（課程鎖在 practice 裡，npx supabase）在 Docker 跑整套；這門課改用 554xx 的 port 與 learn-supabase 這個 project_id，用 -x 排掉用不到的服務，閒置約 1.3 GB。
  • 同一份資料有三個入口：直連資料庫（超級使用者，不受權限限制）、HTTP（PostgREST 把網址翻成 SQL）、supabase-js（包裝 fetch）。查不到資料時先分清楚是 42501（沒有 GRANT）還是空陣列。
  • 適合 CRUD 為主、權限能用「資料屬於誰」表達的產品；付款、跨系統流程、重運算要另外寫伺服器端程式，常見做法是混合。
