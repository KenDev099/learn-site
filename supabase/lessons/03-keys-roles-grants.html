階段 1：起步：一個 Postgres 加上一組服務 · 第 3 課

API key、角色與 GRANT：誰能碰到哪張表

咖啡店的專案出了兩件事。第一件：一位工程師覺得 publishable key 讀不到訂單很麻煩，把 secret key 放進 .env 的 VITE_SUPABASE_KEY，前端從此什麼都讀得到。第二件：另一位工程師建了一張新的 coupons 表，前端讀的時候回 42501 permission denied，他上網查到「把 RLS 關掉就好」，照做之後還是 42501。

兩件事的根源一樣：不知道一個請求在資料庫裡「是誰」、要過哪幾道門。這一課講清楚 key 代表什麼、請求怎麼變成 PostgreSQL 的角色、GRANT 和 RLS 各擋什麼，最後寫出一張新表正確開放給前端的完整步驟。

這課的路線
  • 兩種 key：它代表哪個 app，不代表哪個人；為什麼 secret key 不能進前端。
  • 請求怎麼變成資料庫角色：apikey 與 JWT 各決定什麼，auth.uid() 從哪裡來。
  • 五個角色各做什麼，service_role 到底繞過了什麼。
  • 兩道門：GRANT 回 42501、RLS 回空陣列；2026 年起新表不會自動開放。
  • 一張新表開放給前端的正確步驟，以及什麼時候才用 secret key。
這課會用到：第 1 課的兩道門（GRANT 決定能不能碰這張表、RLS 決定能碰哪幾列）；JWT 的結構（header.payload.signature 三段，payload 是 base64url 編碼的 JSON，認證課第 8 課）；role 與 GRANT（資料庫的帳號，grant select on 表 to 角色 給它權限，PostgreSQL 課第 24 課）。
環境：這課用到資料庫、gateway、Data API、Auth（db、kong、rest、auth），npm run up 預設都會開。練習 1 的測試會建兩個真的使用者，用他們登入後的 JWT 打 API。

兩種 key：代表哪個 app，不代表哪個人

先回答第一件事為什麼危險。npx supabase status 印出兩把 key：

key開頭在資料庫裡是放哪裡
Publishablesb_publishable_anon；請求另外帶了使用者的 JWT 時是 authenticated前端，本來就是公開的
Secretsb_secret_service_role：不受 RLS 限制只放伺服器、Edge Function 的環境變數

API key 的作用是告訴 gateway「這是哪個 app 的請求」，不是「這是哪個人」。publishable key 打包進前端，任何人打開 DevTools 都看得到，這是設計上就預期的；所以 Supabase 的安全不能靠 key 保密，只能靠資料庫裡的 GRANT 與 RLS。

secret key 不一樣：拿到它的人在資料庫裡就是 service_role，RLS 對它無效，所有列都看得到、改得到。開場的工程師把它放進 VITE_ 開頭的變數：Vite 會把 VITE_ 開頭的環境變數直接寫進打包後的 JavaScript，所以那把 key 已經在每個顧客的瀏覽器裡了。不是「可能外洩」，是已經外洩。雲端專案會擋下帶著瀏覽器 User-Agent 的 secret key 請求（回 401），算是最後一道保險，但 curl、Postman 不是瀏覽器，擋不住；本機則完全不擋。

你在網路上還會看到另一組舊的 key：anon key 和 service_role key，都是 eyJ 開頭的長字串（其實就是 JWT）。它們跟 publishable／secret 一一對應，supabase status -o env 也還印得出來（ANON_KEY、SERVICE_ROLE_KEY）。官方文件說舊的 JWT key 在 2026 年底淘汰，新專案只用 publishable／secret。

💡 實務上：secret key 外洩時的處理順序
發現 secret key 進了前端或 git：(1) 在 Dashboard 的 API Keys 建一把新的 secret key，換掉伺服器與 Edge Function 的環境變數；(2) 刪掉舊的那把，它從那一刻起失效；(3) 從程式碼移除，並假設資料已經被讀過，評估要不要通知（顧客個資、訂單）。新制的 secret key 可以有好幾把、各自撤銷，所以平常就讓不同的伺服器用不同的 key，外洩時只換一把。publishable key 被看到則不用換，它本來就是公開的。

請求怎麼變成資料庫角色

key 只說了「哪個 app」，那「哪個人」從哪裡來？從 Authorization: Bearer <JWT> 這個 header：使用者登入後，Auth 簽發一張 JWT（access token），supabase-js 之後的每個請求都帶著它。一個請求經過三站：

  1. gateway 檢查 apikey 是不是這個專案的 key（雲端認不得就回 401；本機不檢查，第 1 課提過）。請求沒有帶使用者的 JWT 時，gateway 依 key 補上一張代表 anon 或 service_role 的 JWT。
  2. PostgREST 驗證 JWT 的簽章與到期時間（exp），讀出 payload 的 role（例如 authenticated）。
  3. PostgreSQL：PostgREST 在一個交易裡執行 set local role authenticated，並把整包 payload 放進設定 request.jwt.claims。SQL 裡的 auth.uid() 就是讀這包 claims 的 sub（使用者 id）；沒登入時沒有 sub，auth.uid() 是 NULL。

所以「這個請求是誰」完全由 JWT 決定，而 JWT 有簽章，使用者改不了內容（改了驗章就失敗）。各種組合在本機實測的結果：

apikeyAuthorization資料庫角色auth.uid()
publishable沒帶anonNULL
publishable使用者的 JWTauthenticated使用者 id
secret沒帶service_roleNULL
secret使用者的 JWTauthenticated（JWT 優先，RLS 照樣套用）使用者 id
任何過期或簽章不對的 JWT不執行，回 401—

第四列常讓人意外：用 secret key 建的 client，只要帶著使用者的 JWT，在資料庫裡就是那個使用者。第 8 課的 Edge Function 會用到這個行為：伺服器端程式「代替使用者」查資料時，RLS 仍然有效。

五個角色

知道請求會變成哪個角色之後，看這些角色各自是什麼。role 與 GRANT 的語法在 PostgreSQL 課第 24 課教過，這裡只看 Supabase 預先建好的這幾個：

角色誰會變成它特性
anon沒登入的請求只有你 GRANT 給它的權限
authenticated帶著使用者 JWT 的請求所有登入的人共用這一個角色，「是哪個人」要用 auth.uid() 分
service_rolesecret key、沒帶使用者 JWT有 BYPASSRLS：不受 RLS 限制。但仍然要有 GRANT
authenticatorPostgREST 連資料庫用的帳號自己幾乎沒有權限，只能切換成上面三個角色
postgres直連資料庫（Studio、db query、migration）表的擁有者，不受 GRANT、RLS 限制；不會出現在 API 請求裡

「service_role 仍然要有 GRANT」可以直接驗證：課程的 public.products 只 GRANT 給 anon 和 authenticated，用 secret key 讀它，回的是 42501 permission denied for table products。BYPASSRLS 只跳過第二道門（列），第一道門（表）照樣要過。Supabase 的 Dashboard 建表時會順便 GRANT 給 service_role，所以平常感覺不到；自己寫 SQL 建表就要記得。

authenticated 只有一個，是這門課最重要的觀念之一：「有登入」不等於「是這筆資料的主人」。grant select on orders to authenticated 之後，如果沒有 RLS，每個登入的顧客都讀得到所有人的訂單。分辨是哪個人，是第 4 課 RLS 的工作。

兩道門：GRANT 回 42501，RLS 回空陣列

角色清楚了，看它們怎麼被兩道門擋。兩道門擋下來的樣子不同，這是除錯時最有用的線索：

第一道門：GRANT第二道門：RLS
管什麼這個角色能不能對這張表做 select／insert／update／delete能做的話，是哪幾列
沒過時 API 回錯誤 42501 permission denied for table …（anon 是 HTTP 401、登入後是 403），hint 直接寫出要下的 GRANT讀取：[]，沒有錯誤；寫入：42501 new row violates row-level security policy
怎麼開grant select on 表 to 角色alter table 表 enable row level security 再寫 policy

回到開場第二件事。新表 coupons 回 42501，是第一道門：沒有 GRANT。關掉 RLS 動的是第二道門，所以錯誤一樣；更糟的是，之後補上 GRANT 時，因為 RLS 已經關了，所有列對那個角色全部開放。

為什麼新表沒有 GRANT？Supabase 從 2026 年起改了預設值：新建的表不會自動開放給 Data API（新專案 2026-05-30、所有專案 2026-10-30 起）。以前在 public 建表，anon、authenticated、service_role 會自動拿到全部權限，很多專案就這樣不小心把表公開了。現在新表只會給這三個角色 TRUNCATE、REFERENCES、TRIGGER 這幾個 API 用不到的權限，要讀寫必須自己 GRANT。本機用 config.toml 的 [api] auto_expose_new_tables = false 對齊雲端（CLI 沒設時是舊行為），所以你在這門課看到的就是雲端的樣子。2025 年以前的教學、AI 給的範例常常省略 GRANT，照抄就會遇到 42501。

一張新表開放給前端的正確步驟

兩道門都要自己開，順序也重要。以「顧客能讀可用的優惠券」為例：

-- 1. 建表
create table public.coupons (id bigint generated always as identity primary key, code text not null, active boolean not null default true);

-- 2. 先開 RLS：從這一刻起，沒有 policy 的角色一列都看不到
alter table public.coupons enable row level security;

-- 3. 寫 policy：誰能看到哪幾列
create policy "可用的優惠券大家都看得到" on public.coupons for select to anon, authenticated using (active);

-- 4. 最後才 GRANT，而且只給需要的角色、需要的動作
grant select on public.coupons to anon, authenticated;

先開 RLS、最後才 GRANT 的理由：在第 4 步之前，表對 API 是完全關著的；如果先 GRANT，在你寫完 policy 之前，那張表有一段時間是對所有人敞開的（migration 跑到一半失敗就會停在那個狀態）。

不要寫 grant all：它包含 insert、update、delete、truncate，等於讓前端也能改菜單，只剩 RLS 一道門擋著，而 RLS 只要一個 policy 寫錯就失守。只讀的表就只 grant select。

💡 實務上：上線前讓工具幫你找漏掉的 RLS
Supabase 的 Security Advisor（Dashboard 的 Advisors 頁，或 CLI 的 npx supabase db advisors --type security）會列出 public 裡沒開 RLS 的表（rls_disabled_in_public）、會繞過 RLS 的 view、沒鎖 search_path 的函式等問題。把它放進 CI（--fail-on warn 讓它有問題時失敗），比靠人記得可靠。審 migration 的 PR 時，每個 create table 後面都應該看到 enable row level security、policy 和最小的 GRANT 三件事。

什麼時候才用 secret key

secret key 適合「本來就該看到全部資料」的伺服器端工作：後台的每日報表、從舊系統匯入資料、金流通知進來時更新訂單狀態（第 8 課）。判斷方式是問：這個動作是代表某個使用者做的嗎？是的話，就該用那個使用者的 JWT，讓 RLS 照常檢查。

它不是「解決權限錯誤」的工具。前端遇到 42501，答案是補上正確的 GRANT 與 policy；換成 secret key 讓錯誤消失，等於把所有人的資料都開放給所有人。

💡 實務上：key 放哪裡、本機服務開在哪裡
前端專案的 .env 只放 VITE_SUPABASE_URL 與 VITE_SUPABASE_PUBLISHABLE_KEY；secret key 只出現在伺服器的環境變數或雲端的 secrets 設定，而且 .env* 不進 git。另外，本機 Supabase 啟動時會提醒服務綁在 0.0.0.0：同一個 Wi-Fi 的其他電腦也能連到你的 55421、55422，而本機的 key 與資料庫密碼是人人都知道的預設值。在咖啡廳或共用網路上不用的時候就 npm run down，或用 macOS 的防火牆擋掉外來連線。

練習

練習 1：測試會在你專屬的 schema 建好 products（6 項菜單）與 orders（customer_id 預設是 auth.uid()），再套用你的 grants.sql。要做到：沒登入和登入的人都能讀菜單，但任何人都不能透過 API 改菜單；登入的人能用自己的身分新增訂單，沒登入的人不能；訂單先不開放讀取；兩張表都開 RLS。下單的 policy 已經寫好在檔案裡。SQL 不要寫 public. 前綴（判分時表在你專屬的 schema）。

練習 2：寫 requestRole(headers, keys, now)，照上面「請求怎麼變成資料庫角色」的表，推出這個請求在資料庫裡是哪個角色、auth.uid() 是什麼：

  • header 名稱都是小寫。apikey 不是 keys.publishable 也不是 keys.secret（或沒帶）時，回傳 { error: … }（雲端會回 401）。
  • authorization 沒帶，或 Bearer 後面不是 JWT（不是三段、例如 Bearer sb_publishable_…）時：publishable 是 anon、secret 是 service_role，uid 是 null。
  • 帶著 JWT 時以 JWT 為準：解出 payload（base64url 編碼的 JSON），exp 小於等於 now（秒）回傳 { error: … }；否則角色是 payload 的 role，uid 是 sub（沒有就是 null）。

這題只解讀、不驗簽章（驗章是 PostgREST 的工作，認證課第 9 課寫過完整的驗證）。

練習 3：專案的 code review 工具要掃出「放在前端的 key 安不安全」。寫 classifyKey(value)，回傳 { kind, browserSafe }：

  • sb_publishable_ 開頭：'publishable'，可以放前端；sb_secret_ 開頭：'secret'，不行。
  • JWT（三段、payload 解得開）：payload 的 role 是 anon 就是 'legacy-anon'（可以放前端），是 service_role 就是 'legacy-service_role'（不行）；其他 role（例如使用者的 access token）是 'unknown'。
  • 其他都是 'unknown'。不認得的東西一律當成不能放前端。

練習 4：前端查 coupons，一個回 42501 permission denied for table coupons，另一個環境回 []。各是哪道門擋下的？

✓ 第一道門 GRANT 沒過是錯誤 42501，hint 會寫出要下的 GRANT；第二道門 RLS 沒有符合的 policy 時，讀取不是錯誤而是空陣列。b 剛好說反了，也是開場那位工程師的誤會：關 RLS 解決不了 42501。d 能讓錯誤消失，但等於把整張表交給所有人。（第 3 課）

練習 5：資安掃描報告指出「前端打包檔裡有 sb_publishable_…，以及 eyJ… 開頭、payload 的 role 是 service_role 的字串」。該怎麼處理？

✓ publishable key 設計上就是公開的；舊制的 service_role key 跟 secret key 一樣繞過 RLS，出現在前端就是外洩。c 錯在簽章只保證內容沒被改，不代表能公開：拿到它的人就有 service_role 的權限。d 沒有用，VITE_ 變數會被寫進打包檔。（第 3 課）

練習 6：後台的匯入程式用 secret key 連 Supabase，寫入自己用 SQL 新建的 imports 表，回 42501。service_role 不是不受 RLS 限制嗎？

✓ 兩道門是分開的：service_role 有 BYPASSRLS，但第一道門 GRANT 照樣要過，而新表預設不會自動 GRANT。c 正好相反：帶了使用者 JWT，請求就變成那個使用者，連 RLS 都會套用。d 關 RLS 動的是第二道門，42501 不會消失。（第 3 課）

常見錯誤

  • secret key 放進前端（包括 VITE_ 變數、舊制的 service_role key）：拿到的人繞過所有 RLS。前端只放 publishable key。
  • 遇到 42501 就關 RLS：42501 是沒有 GRANT，跟 RLS 無關；關掉 RLS 只會讓之後補上的 GRANT 開放整張表。
  • grant all：前端也能改、能刪、能 truncate，只剩 RLS 擋。只給需要的動作。
  • 先 GRANT 再寫 RLS：中間那段時間表是全開的。順序是建表 → 開 RLS → policy → GRANT。
  • 以為 service_role 不用 GRANT：它只跳過 RLS。自己用 SQL 建的表要記得 GRANT 給它。
  • 以為 authenticated 等於「資料的主人」：所有登入的人共用這個角色，分辨是誰要靠 auth.uid() 與 RLS。
  • 用 secret key 解決前端的權限錯誤：問題被藏起來，資料被打開。代表使用者做的事，就用使用者的 JWT。

小結

  • publishable key（→ anon）放前端、本來就公開；secret key（→ service_role，繞過 RLS）只放伺服器。key 代表哪個 app，不代表哪個人，安全只能靠 GRANT＋RLS。舊制的 anon／service_role JWT key 一一對應，2026 年底淘汰。
  • 請求的身分由 JWT 決定：gateway 認 key、沒帶 JWT 時依 key 補一張；PostgREST 驗 JWT、set local role、把 payload 放進 request.jwt.claims；auth.uid() 讀 sub。帶了使用者 JWT 時，就算用 secret key 也是那個使用者。
  • 角色：anon、authenticated（所有登入的人共用）、service_role（BYPASSRLS，但仍要 GRANT）、authenticator（PostgREST 連線用）、postgres（直連、表的擁有者）。
  • 兩道門：沒有 GRANT 是 42501；有 GRANT、RLS 沒有符合的 policy 時讀取是 []。2026 年起新表不會自動 GRANT（本機 auto_expose_new_tables = false）。
  • 新表的步驟：建表 → 開 RLS → policy → 最小的 GRANT；用 Security Advisor 檢查。secret key 只用在本來就該看到全部資料的伺服器端工作。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 7：面試官問：「用了 Supabase，前端直接打資料庫的 API，那後端的權限檢查去哪了？」最好的回答是？

✓ PostgREST 直接查資料庫，中間沒有你寫的程式，權限只能寫成資料庫的 GRANT 與 RLS。a 是最常見的錯：前端的程式與請求使用者都改得到，在瀏覽器過濾等於沒擋。b 錯在 apikey 只代表哪個 app。（第 1、3 課）

練習 8：訂單明細頁打開要等快一秒，Network 分頁看到同一頁打了 7 個 /rest/v1/ 請求：1 個 orders、1 個 order_items、5 個 products。怎麼改？

✓ 這是 N+1，用嵌入一次取回；兩張表之間要有外鍵。b 是最多人會先想到的，請求數不變、只是並行，手機網路下仍慢，而且列表頁會變成 N 倍。c 在菜單很小時可行，但它繞開問題而非解決，換成顧客、訂單這類大表就做不到。（第 2 課）

練習 9：下面的結帳程式，測試環境一切正常，上線後客服說「有人付款成功卻沒有訂單」。最可能的原因？

const { data } = await supabase.from('orders').insert({ customer_id, total }).select('id').single()
await supabase.from('order_items').insert(items.map(i => ({ order_id: data.id, ...i })))
return data.id

✓ 失敗的結果放在 error，程式不會停；第二個 insert 失敗也沒人知道，留下沒有品項或沒有訂單的狀態。每一步都要檢查 error，多步驟寫入要放進 RPC 才會在同一個交易（第 8 課）。a 錯在程式已經有 .select('id')。c 錯在每行都有 await。（第 2 課）

練習 10：新同事在 SQL 裡建了 coupons 表，前端讀到 42501。他打算執行下面哪一個？你該建議哪一個？

✓ 42501 是沒有 GRANT，2026 年起新表不會自動開放；正確順序是 RLS → policy → 最小的 GRANT。c 會讓錯誤消失，但前端也能改、能刪優惠券，只剩 RLS 一道門。a 根本解決不了 42501，還拿掉了列層級保護。（第 3 課）

練習 11：Edge Function 用 secret key 建 client，並把呼叫者的 Authorization: Bearer <使用者 JWT> 帶上去查 orders。查詢在資料庫裡以什麼身分執行？

✓ key 只代表 app，身分由 Authorization 的 JWT 決定；只有沒帶使用者 JWT 時，gateway 才依 secret key 補上 service_role。a 是最常見的誤解。這個行為讓伺服器端程式能代替使用者查資料，同時保住 RLS（第 8 課會用到）。（第 3 課）

練習 12：本機測試時，前端忘了帶 apikey 也查得到菜單，同事說「看吧，apikey 根本不用帶」。怎麼回應？

✓ 本機和雲端在這點不同：本機沒帶或帶錯 key 都以 anon 放行，雲端直接 401。c 混淆了兩件事：policy 決定 anon 看得到哪幾列，key 決定請求能不能進來。d 錯在沒帶 key 時是 anon。（第 1、3 課）
