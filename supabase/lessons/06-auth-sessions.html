階段 3：Auth 與檔案 · 第 6 課

Auth：登入、session、伺服器端驗證與 profiles

咖啡店的點餐網站上線一週，客服收到三種回報。第一種：顧客登入後放著分頁去開會，回來按「我的訂單」就出現 401。第二種：資安同事發現用 Nuxt 寫的 /api/me 只要改瀏覽器裡的 cookie，就能變成別的顧客。第三種：新註冊的顧客在「會員資料」頁一片空白，因為 profiles 表裡沒有他那一列。三個問題都出在同一件事：沒弄清楚 Supabase Auth 登入後給了你什麼、誰該相信什麼。

這一課講 Supabase Auth 的實際用法：登入後的 session 怎麼保存與更新、信箱驗證與 magic link、OAuth 要設定哪些東西、伺服器端怎麼可靠地知道「這個請求是誰」，以及怎麼在註冊時自動建立 profiles。token 的原理別門課教過，這裡只回顧一句，篇幅放在 Supabase 怎麼做。

這課的路線
  • 登入之後手上有什麼：session 的兩個 token、誰負責更新它，回答「一小時後 401」。
  • 信箱驗證與 magic link：本機的信寄到哪、怎麼換成 session。
  • OAuth 在 Supabase 要設定什麼：redirect 白名單與 PKCE。
  • 伺服器端：session 放在 cookie 裡時，getClaims、getUser、getSession 各信得過什麼，回答「改 cookie 變成別人」。
  • profiles 與 trigger：auth.users 為什麼不能直接用，註冊時怎麼自動建一列；最後一段帶過 MFA、自訂 token 內容與匿名登入。
這課會用到：access token 與 refresh token（短效的通行證＋換新通行證用的長效憑證，認證課第 10 課）；JWT 的簽章（簽章只有持有金鑰的人算得出來，改了內容簽章就對不上，認證課第 8 課）；請求怎麼變成資料庫角色（publishable key 是 anon，帶使用者 JWT 是 authenticated，第 3 課）；顧客只讀自己訂單的 policy（customer_id = (select auth.uid())，第 4 課）。
環境：這課用到資料庫、gateway、Data API、Auth 與 Mailpit（db、kong、rest、auth、mailpit），npm run up 預設都會開。練習 3 用到 @supabase/ssr 0.12.7，已經寫在 supabase/practice/package.json，第一次做先在 supabase/practice 執行 npm ci。

登入之後手上有什麼

先看登入這個動作本身。supabase-js 的登入與註冊各一行：

const supabase = createClient('http://localhost:55421', 'sb_publishable_…')

await supabase.auth.signUp({ email: 'ming@example.com', password: '…', options: { data: { display_name: '王小明' } } })
const { data, error } = await supabase.auth.signInWithPassword({ email: 'ming@example.com', password: '…' })

登入成功時 data.session 是一個 session 物件。把它印出來（節錄）：

{
  access_token: 'eyJhbGciOiJFUzI1NiIs…',   // JWT，帶在每個請求的 Authorization header
  expires_in: 3600,                         // 秒
  expires_at: 1795155112,                   // 到期時間（Unix 秒）
  refresh_token: 'u3kq…',                   // 換新 access token 用，只能用一次
  user: { id: '6205ef23-…', email: 'ming@example.com', user_metadata: { display_name: '王小明' }, … }
}
  • access token：Auth 簽發的 JWT，sub 是使用者 id、role 是 authenticated。第 3 課講過，PostgREST 驗過它的簽章後，用 authenticated 角色查詢，auth.uid() 讀到的就是 sub。有效期是 config.toml 的 [auth] jwt_expiry = 3600（一小時，雲端在 Dashboard 設）。
  • refresh token：access token 過期前，拿它向 Auth 換一組新的 access token＋新的 refresh token。舊的 refresh token 換過就作廢（輪替，rotation）；refresh_token_reuse_interval = 10 是寬限秒數，讓同時發出的兩個換新請求不會互相打架。為什麼這樣設計，認證課第 10 課講過。
  • user：登入當下的使用者資料。

登入之後，同一個 client 發出的每個請求都會自動帶 Authorization: Bearer <access token>。supabase-js 也會在背景自動換新 token，並把 session 存起來：在瀏覽器存 localStorage，重新整理頁面還是登入狀態。

所以開場「放著一小時就 401」，常見原因是有人繞過了這個機制：把 access token 複製出來自己組 fetch（token 過期了沒人換）、每次請求都 createClient 一個新的 client（新的 client 不知道 session）、或在伺服器端把 autoRefreshToken 關掉後忘了自己處理。原則是整個前端共用一個 client，讓它管 session。

登入失敗時 error.code 會告訴你原因，畫面要依它給不同的提示：

error.code意思畫面該說
invalid_credentialsemail 或密碼錯「帳號或密碼錯誤」，不要說是哪一個錯（避免讓人試出哪些 email 有註冊）
email_not_confirmed帳號存在、密碼對，但還沒點驗證信「請先到信箱點驗證連結」，附「重寄驗證信」按鈕
over_request_rate_limit 等太頻繁，被限流「稍後再試」

監聽登入狀態：onAuthStateChange

畫面要跟著登入狀態變（右上角顯示名字、登出後跳回首頁），用 onAuthStateChange 訂閱事件：

// stores/auth.ts（Pinia）
export const useAuthStore = defineStore('auth', () => {
  const user = ref<User | null>(null)
  supabase.auth.onAuthStateChange((event, session) => {
    // INITIAL_SESSION（剛載入）、SIGNED_IN、SIGNED_OUT、TOKEN_REFRESHED、USER_UPDATED、PASSWORD_RECOVERY
    user.value = session?.user ?? null
  })
  return { user }
})

callback 寫成同步函式，裡面只更新狀態。supabase-js 2.119.0 把 async 的 callback 標成不建議使用：在 callback 裡 await 其他會觸發換新 token 的呼叫，可能互相等待而卡住（deadlock）。要在登入後查資料，先存狀態，再由元件或 watch 去查。

💡 實務上：token 過期的使用者體驗
顧客的分頁開一整天很常見。共用一個 client、讓它自動換新，一般情況使用者感覺不到 token 過期。真的換新失敗（refresh token 被撤銷、帳號被停用）時，onAuthStateChange 會收到 SIGNED_OUT：在 Pinia 裡接這個事件，把使用者導回登入頁，並保留他原本要去的網址，登入後再導回去。客服回報「突然被登出」時，先在 Network 看 /auth/v1/token?grant_type=refresh_token 回了什麼錯。

信箱驗證與 magic link

知道了 session 長什麼樣，接著看另一條拿到 session 的路：靠信箱。config.toml 的 [auth.email] enable_confirmations 決定註冊後要不要先點驗證信才能登入。課程的本機設定是 false，所以 signUp 直接回傳 session；雲端新專案預設要驗證（Dashboard 的 Confirm email）。沒驗證的帳號用密碼登入，就是上一節表格裡的 email_not_confirmed。

magic link（神奇連結）是免密碼登入：輸入 email，收到一封信，點信裡的連結就登入。supabase-js 的寫法：

await supabase.auth.signInWithOtp({ email: 'ming@example.com', options: { shouldCreateUser: false } })

OTP 是 one-time password（一次性密碼）。shouldCreateUser 預設是 true：沒註冊過的 email 也會直接建立帳號。登入頁通常要設成 false，不然顧客打錯一個字就多一個帳號；設了之後沒註冊過的 email 會回錯誤 otp_disabled。

本機 Auth 寄出的信不會真的寄出去，全部進 Mailpit（第 1 課看過的假信箱，網頁在 http://localhost:55424）。上面那行執行完，Mailpit 裡會多一封：

Your sign-in link

Follow the link below to sign in. This link expires shortly and can only be used once.

Sign in ( http://127.0.0.1:55421/auth/v1/verify?token=e7d6f66c…&type=magiclink&redirect_to=http://localhost:5173 )

連結指向 Auth 的 /auth/v1/verify：Auth 驗過 token 之後，把瀏覽器導回 redirect_to（預設是 site_url），並把 session 交給前端。這個 token 是 token hash（雜湊過的值），也可以不經過瀏覽器跳轉，直接交給 supabase-js 換成 session：

const { data, error } = await supabase.auth.verifyOtp({ token_hash: '<信裡的 token>', type: 'email' })
// data.session 就是登入後的 session；同一個連結第二次用會得到 otp_expired

正式專案常把信的範本改成連到自己網站的 /auth/confirm?token_hash=…&type=email，由那一頁呼叫 verifyOtp。這樣信件掃描器（有些公司的信箱會先「點一次」信裡的連結檢查安全性）不會把一次性的連結用掉。練習 2 用 Mailpit 的 API 收信，自動化地走一次這個流程。

同一個 email 寄信有頻率限制（本機 [auth.email] max_frequency = "1s"），太快重寄會收到「For security purposes, you can only request this after N seconds」。

💡 實務上：上線前一定要換自己的寄信服務
Supabase 內建的寄信服務只適合開發測試，寄送量有很低的上限，上線前在 Dashboard 設定自己的 SMTP（例如公司已經在用的寄信服務）。同時改信件範本：寄件人名稱、中文內容、連到自己網域的確認頁。驗證信寄不到是上線第一週最常見的客訴之一，順序是先查 Auth 的 log 有沒有寄出、再查 SMTP 服務的退信紀錄。

OAuth 在 Supabase 要設定什麼

信箱登入之外，顧客更常用「用 Google 登入」。OAuth 授權碼流程與 PKCE 的原理在認證課第 12 課講過：瀏覽器跳到 Google，使用者同意後帶著一次性的 code 跳回你的網站，再用 code 換 token；PKCE 讓攔到 code 的人換不到 token。在 Supabase 裡，換 token 這件事由 Auth 服務做，你要做的是設定：

  • provider：在 Dashboard（本機是 config.toml 的 [auth.external.google]）填 Google 給你的 client id 與 secret。本機沒辦法真的連 Google，這門課不實作。
  • redirect 白名單：登入完成後，Auth 只會把使用者導回 site_url 或 additional_redirect_urls 列出的網址。課程本機設成 http://localhost:5173 與 http://localhost:5173/**（Vite 的預設 port）。正式環境要列出正式網域、預覽環境的網域，不要用太寬的萬用字元。
  • PKCE：supabase-js 在瀏覽器預設用 PKCE 流程（flowType: 'pkce'），跳回來的網址帶 ?code=…，由 exchangeCodeForSession(code) 換成 session。用 @supabase/ssr 時一律是 PKCE。
await supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: 'http://localhost:5173/auth/callback' } })

// /auth/callback 那一頁（或伺服器端的 route）
const code = new URL(location.href).searchParams.get('code')
if (code) await supabase.auth.exchangeCodeForSession(code)

為什麼一定要白名單：如果 Auth 願意把使用者導回任何網址，攻擊者就能寄一個「用 Google 登入」的連結，把 redirectTo 設成自己的網站，使用者登入後，code 或 token 就被送到攻擊者那裡。redirectTo 不在白名單時，Auth 會改導回 site_url。

伺服器端：session 放在 cookie 裡

前面的流程都在瀏覽器裡，session 存在 localStorage。改用 Nuxt、Next.js 這類有伺服器端渲染的框架時，伺服器也要知道「這個請求是誰」，但伺服器讀不到瀏覽器的 localStorage。做法是把 session 存在 cookie（瀏覽器每個請求都會自動帶上的小資料，認證課第 4 課），官方套件 @supabase/ssr（這門課用 0.12.7）就是做這件事：

import { createServerClient, parseCookieHeader } from '@supabase/ssr'

// 每個請求建一個 client：cookie 從這個請求讀，要更新的 cookie 寫回這個回應
const supabase = createServerClient(url, publishableKey, {
  cookies: {
    getAll: () => parseCookieHeader(req.headers.get('cookie') ?? ''),
    setAll: (list) => { for (const c of list) res.headers.append('Set-Cookie', serialize(c.name, c.value, c.options)) },
  },
})

登入後，cookie 名稱是 sb-<專案代號>-auth-token（本機網址是 127.0.0.1，代號就是 127），內容是 base64- 開頭、把整個 session 物件用 base64url 編碼的字串。重點在這裡：cookie 的內容是瀏覽器送來的，使用者自己改得到。所以伺服器端從 client 取出身分有三個方法，可信度不同：

方法做了什麼能拿來做授權嗎
getSession()把 cookie 裡的 session 讀出來（過期時會先換新），不驗簽章不行。session.user 就是 cookie 裡寫的內容
getClaims()驗 access token 的簽章與到期時間，回傳裡面的 claims。專案用非對稱金鑰時在你的伺服器上就驗完（金鑰從 /auth/v1/.well-known/jwks.json 取一次後快取）可以。伺服器端判斷身分的首選
getUser()每次都把 token 送到 Auth 伺服器查可以。還能發現「使用者已經被刪除或停用」，代價是每次多一個網路請求

本機的金鑰是非對稱的，實際打一次就看得到：

curl http://localhost:55421/auth/v1/.well-known/jwks.json
{"keys":[{"alg":"ES256","crv":"P-256","kty":"EC","use":"sig","kid":"b81269f1-…","x":"M5Sj…","y":"P6IX…"}]}

ES256 是橢圓曲線簽章：Auth 用私鑰簽，任何人都能用這把公鑰驗，但算不出新的簽章（認證課第 9 課）。開場那個「改 cookie 變成別人」的 bug，就是 handler 用 getSession() 的 user.id 做授權：攻擊者把 cookie 裡的 user.id 改成別人的，getSession() 照單全收（supabase-js 還會在 console 印警告「could be insecure」）。換成 getClaims()，竄改過的 token 會得到 Invalid JWT signature。

💡 實務上：Nuxt 的 server route 一律先 getClaims
在 Nuxt 的 server/api/*.ts、middleware 裡，判斷「是誰、能不能做」一律用 getClaims() 的 sub；getSession() 只在需要把 access token 轉交給別的服務時用。要擋「剛被停權的人」（例如刪帳號、退款爭議）的高風險操作，改用 getUser() 多問 Auth 一次。code review 看到伺服器端程式出現 getSession() 再讀 .user，就要問一句。

profiles 與 trigger

伺服器知道了「是誰」，接著要放這個人的資料：暱稱、電話、生日。使用者存在 auth.users，但 auth 這個 schema 不對 Data API 開放（裡面有密碼雜湊等敏感欄位），前端讀不到也不該讀。慣例是在 public 另建一張 profiles，用同一個 id 一對一對應，並用 trigger 在註冊時自動建一列。trigger（觸發器）是「某張表發生某件事時自動執行的函式」，語法在 PostgreSQL 課第 23 課：

create table public.profiles (
  id uuid primary key references auth.users (id) on delete cascade,   -- 使用者刪掉時跟著刪
  display_name text not null default ''
);
alter table public.profiles enable row level security;
create policy "看自己的 profile" on public.profiles for select to authenticated using (id = (select auth.uid()));
grant select on public.profiles to authenticated;

create function public.handle_new_user() returns trigger
language plpgsql
security definer          -- 以函式擁有者的權限執行
set search_path = ''      -- 不依賴呼叫者的 search_path，裡面的名字都寫完整
as $$
begin
  insert into public.profiles (id, display_name)
  values (new.id, coalesce(new.raw_user_meta_data ->> 'display_name', ''));
  return new;
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();

三個關鍵：

  • 為什麼要 security definer：新增 auth.users 的是 Auth 服務，它用資料庫角色 supabase_auth_admin 連線，這個角色沒有 public.profiles 的權限。不加的話 trigger 失敗，整個註冊跟著失敗：前端只收到「Database error saving new user」。加了之後函式以擁有者（建函式的 postgres）的權限執行。
  • 為什麼要 set search_path = ''：security definer 函式權限比呼叫者大，第 5 課講過：沒鎖住 search_path，呼叫者可能讓函式裡沒寫 schema 的名字解析到別的東西。鎖成空的，函式裡每個名字都寫完整（public.profiles）。
  • raw_user_meta_data：signUp 的 options.data 存在這裡，就是使用者看得到、也改得到的 user_metadata。拿來當暱稱的初始值可以；第 5 課說過，授權用的角色不能放這裡。

回傳 trigger 的函式不能被直接呼叫，所以它雖然在 public，也不會變成可以從 API 呼叫的 RPC。

💡 實務上：trigger 出錯，註冊就全掛
profiles 的 trigger 在註冊的同一個交易裡執行，它失敗，所有人都註冊不了。上線前會檢查：新增欄位時 trigger 裡的 insert 有沒有跟著改、not null 的欄位有沒有預設值、metadata 缺欄位時有沒有 coalesce。客服回報「註冊一直失敗」時，先去 Postgres 的 log 找 trigger 函式的錯誤訊息，前端那句「Database error saving new user」不會告訴你原因。

一段帶過：MFA、自訂 token 內容、匿名登入

這三件事都會改變 access token 的內容，進而影響 policy：

  • MFA（多因素驗證，TOTP 的原理在認證課第 14 課）：Supabase 的流程是 mfa.enroll()（綁定驗證器 App）→ mfa.challenge() → mfa.verify()，完成後 access token 的 aal claim 從 aal1 變成 aal2。第 5 課的 restrictive policy (auth.jwt() ->> 'aal') = 'aal2' 就是讀它。本機要先在 config.toml 開 [auth.mfa.totp] enroll_enabled 與 verify_enabled（課程預設關著）。
  • Custom Access Token Hook：Auth 簽發 token 前呼叫你寫的資料庫函式，可以把資料庫裡的角色（例如 store_members 裡的店長身分）寫進 claims，policy 就不用每次查表。代價是角色改了，要等 token 換新才生效。
  • 匿名登入（signInAnonymously()，課程本機關著）：不用 email 就拿到一個帳號，常用在「先逛、先加購物車，結帳前再註冊」。陷阱是匿名使用者的角色也是 authenticated：policy 只寫 to authenticated 的表，匿名使用者全都碰得到。要區分就看 claims 的 is_anonymous。

練習

練習都在本機，題目資料夾是 supabase/practice/work/06/。每個函式收到一個 cfg（harness.ts 的 Config），像伺服器的環境變數：網址、兩把 key、你這一題專屬的 schema、Mailpit 的網址都在裡面，用哪一個是你要判斷的。測試會建立 <代號>-a@learn.test 這類測試帳號，跑完刪掉。

練習 1：完成 login(cfg, email, password)：用 publishable key 建 client（db.schema 用 cfg.schema），用密碼登入，再用同一個 client 讀 orders 的 id、total（依 id 排序），回傳 { ok: true, userId, orders }。登入失敗時依 error.code 回傳 { ok: false, reason: 'unconfirmed' }（信箱還沒驗證）或 'invalid'（帳密錯），其他錯誤丟出。orders 已經套上第 4 課的 policy，測試會檢查你只讀到自己的訂單、每個請求用哪把 key。

練習 2：完成 magicLogin(cfg, email)：寄出 magic link（只給已經註冊的人，沒註冊的 email 要丟出錯誤），用 Mailpit 的 API 找到寄給這個 email 的最新那封信，取出連結裡的 token，用 verifyOtp 換成 session，回傳 { userId, accessToken }。測試在你收信的同時會寄一封信給另一位顧客，也會連續登入兩次。

練習 3：完成伺服器端的 handleMe(req, cfg)（GET /api/me）：用 @supabase/ssr 的 createServerClient 從請求的 cookie 讀 session，取得驗過簽章的身分，已登入回 200 { userId, email }，沒登入或 token 不可信回 401。測試會送正常的 cookie、沒有 cookie，以及把內容改成另一位顧客的 cookie。

練習 4：在 profiles.sql 建 public.profiles（RLS：登入的人只讀得到自己那一列）、trigger 函式與 after insert on auth.users 的 trigger，讓從 API 註冊的人自動有一列 profile，display_name 取註冊時 options.data 傳的值（沒有就空字串）。照正式專案的寫法寫 public.；判分時測試會把 public. 換成你這一題的 schema、把 trigger 改名並限定只對這一題的測試帳號觸發，避免影響同時在跑的其他題目。測試會真的從 API 註冊，並檢查函式的設定。

練習 5：Nuxt 的 server route 要決定「這個請求能不能取消這張訂單」。下面哪個做法可以拿來做這個判斷，又不用每個請求都多打一次 Auth 伺服器？

✓ getClaims() 驗過簽章與到期時間才回傳內容，非對稱金鑰在你的伺服器上就能驗。a 最常見：getSession() 只是讀出 cookie，內容使用者改得到。b 一樣沒驗簽章。c 也安全，但每次都要打 Auth 伺服器，題目要的是不用多一次請求。

練習 6：後台把一位惡意顧客從 auth.users 刪掉了。他瀏覽器裡那個 30 分鐘前拿到的 access token（有效期 1 小時），接下來會怎樣？

✓ JWT 只要簽章對、沒過期就會被接受，PostgREST 與 getClaims() 都只驗這兩件事（本機實測刪掉使用者後，舊 token 讀 API 仍是 200）。getUser() 會問 Auth，得到「使用者不存在」；refresh token 也已經作廢，所以最多撐到 access token 到期。a 是最常見的誤解。要更快踢人：縮短 jwt_expiry，或高風險操作改用 getUser()（取捨在認證課第 11 課）。

練習 7：同事為了讓預覽環境也能用 Google 登入，想把 Auth 的 redirect 白名單設成 https://**。這樣做的風險是？

✓ 白名單決定登入結果能送去哪裡；設成任何網址，等於讓任何人收得到登入結果。c 是最多人會選的：PKCE 保護的是「攔到 code 的人換不到 token」，但在某些流程（例如 magic link、隱式流程）導回的網址本身就帶著可以用的憑證，而且讓使用者在登入後落在釣魚網站本身就是問題。預覽環境要明確列出它的網域規則。

常見錯誤

  • 每次請求都 createClient 一個新的：新的 client 沒有 session、也不會自動換新，一小時後開始 401。前端整個 app 共用一個 client。
  • 把 access token 複製出來自己組 fetch：token 過期沒人換。要嘛用 supabase-js 發請求，要嘛每次從 getSession() 取最新的 token。
  • 伺服器端用 getSession() 的 user 做授權：cookie 的內容使用者改得到。改用 getClaims()（或 getUser()）。
  • 在 onAuthStateChange 的 callback 裡 await 其他 supabase 呼叫：可能卡住。callback 只更新狀態，查資料放到外面。
  • signInWithOtp 沒加 shouldCreateUser: false：登入頁打錯 email 就多一個帳號。
  • profiles 的 trigger 沒有 security definer：Auth 的角色沒有權限寫 profiles，所有人都註冊失敗。加了 security definer 也要 set search_path = ''。
  • 以為刪掉使用者就立刻登出他：手上的 access token 到期前都有效。

小結

  • 登入後的 session＝access token（JWT，預設 3600 秒，帶在每個請求）＋refresh token（輪替，只能用一次）。共用一個 client，讓 supabase-js 自動換新與保存；用 onAuthStateChange（同步 callback）讓畫面跟著狀態變。
  • 登入失敗看 error.code：invalid_credentials 與 email_not_confirmed 要給不同提示。magic link 用 signInWithOtp({ shouldCreateUser: false })，信裡的 token hash 用 verifyOtp 換成 session；本機的信在 Mailpit。
  • OAuth 在 Supabase 只要設定 provider、redirect 白名單（site_url、additional_redirect_urls）；瀏覽器用 PKCE，跳回來用 exchangeCodeForSession。
  • 伺服器端用 @supabase/ssr 把 session 放 cookie。cookie 的內容不可信：授權用 getClaims()（本地驗簽章）或 getUser()（問 Auth），不用 getSession() 的 user。
  • auth.users 不對 API 開放，用 public.profiles＋after insert on auth.users 的 trigger；函式要 security definer＋set search_path = ''，trigger 失敗會讓註冊失敗。
  • MFA 完成後 token 的 aal 是 aal2；Custom Access Token Hook 能把角色寫進 token；匿名使用者也是 authenticated。
