階段 4：伺服器端邏輯與上線 · 第 8 課

伺服器端邏輯放哪裡：資料庫函式（RPC）與 Edge Functions

咖啡店的結帳流程是前端寫的：先 insert 一張訂單、再 insert 每個品項、最後呼叫金流。上線後出了三件事。顧客在第二步斷網，資料庫留下一張沒有品項的半張訂單；有人改了前端送出的價格，用 1 元買到拿鐵；金流的 API 金鑰為了讓前端能呼叫，被寫進了 Vite 的環境變數，打包後任何人都看得到。

這三件事都在說：有些邏輯不能放在前端。用 Supabase 不代表沒有伺服器端，而是伺服器端邏輯有好幾個地方可以放。這一課先給一張判斷表，再實作其中兩個：資料庫函式（透過 RPC 呼叫）與 Edge Function，最後談什麼時候該改用自己的 NestJS 服務。

這課的路線
  • 四個可以放邏輯的地方：先給判斷表，回答「結帳該放哪」。
  • RPC：把多步驟寫入包成一個資料庫函式，一個交易做完；它的權限怎麼設。
  • Edge Functions：要呼叫外部 API、要藏金鑰時；用呼叫者的身分還是 secret key。
  • 其他伺服器端工具一段帶過：trigger、排程、佇列、webhook。
  • 什麼時候改用自己的後端：混合架構。
這課會用到：函式與 plpgsql（資料庫裡的程式，begin … end 之間可以有變數、判斷，PostgreSQL 課第 23 課）；交易（一組操作全部成功或全部取消，PostgreSQL 課第 18 課）；security definer 的規則（以擁有者的權限執行，要鎖 search_path、不放在公開的 schema，第 5 課）；publishable 與 secret key 對應的角色（第 3 課）。
環境：這課用到資料庫、gateway、Data API、Auth（db、kong、rest、auth）。練習 2 的測試用 Docker 跑 Edge Runtime 的映像（edge-runtime:v1.78.1，跟本機 Supabase 同一個，已經下載過）：每次判分開一個自己的容器，跑完刪掉。

四個可以放邏輯的地方

先回答開場的問題。用 Supabase 時，一段邏輯可以放在四個地方，由近到遠：

放哪裡適合咖啡店的例子
直接打 Data API（前端＋RLS）單張表的讀寫，權限能用「這列屬於誰」表達菜單、我的訂單列表、改自己的暱稱
資料庫函式（RPC）好幾個寫入要一起成功或一起失敗；價格、庫存這類要由資料庫決定的計算；RLS 很難表達的規則結帳建立訂單＋品項；店員把訂單改成「已出餐」
Edge Function要呼叫外部 API、要用不能給前端的金鑰、要接別人打進來的 webhook；短時間就能做完向金流扣款、接金流的付款通知、寄收據信
自己的後端（例如 NestJS）流程長、跨好幾個系統、要排程與失敗重試，或團隊本來就熟 Node 的生態系每晚跟 POS 對帳、月底產生發票

判斷的順序：先問「需不需要離開資料庫（外部 API、金鑰、webhook）」，不需要的話，再問「是不是多個寫入、或要資料庫算」。結帳拆成兩段：「建訂單、算總價」放 RPC，「向金流扣款」放 Edge Function，由 Edge Function 呼叫 RPC。這一課的兩個練習就是這兩段。

RPC：一個交易做完多步驟寫入

從判斷表的第二格開始。RPC（Remote Procedure Call，遠端程序呼叫）在 Supabase 指的是：PostgREST 把資料庫函式也變成 API，POST /rest/v1/rpc/<函式名>，body 是參數。supabase-js 的寫法：

const { data: orderId, error } = await supabase.rpc('place_order', {
  items: [{ product_id: 2, quantity: 2 }, { product_id: 5, quantity: 1 }],
})

函式本體（plpgsql 的語法在 PostgreSQL 課第 23 課）：

create function public.place_order(items jsonb) returns integer
language plpgsql
set search_path = ''
as $$
declare
  uid uuid := (select auth.uid());
  order_total integer;
  found_count integer;
  new_id integer;
begin
  if uid is null then
    raise exception '請先登入' using errcode = '42501';
  end if;

  -- 價格從資料庫讀，不看前端傳了什麼
  select sum(p.price * (i ->> 'quantity')::integer), count(*)
    into order_total, found_count
    from jsonb_array_elements(items) as i
    join public.products p on p.id = (i ->> 'product_id')::integer;
  if found_count is distinct from jsonb_array_length(items) or found_count = 0 then
    raise exception '有商品不存在';
  end if;

  insert into public.orders (customer_id, total) values (uid, order_total) returning id into new_id;
  insert into public.order_items (order_id, product_id, quantity, unit_price)
    select new_id, p.id, (i ->> 'quantity')::integer, p.price
      from jsonb_array_elements(items) as i
      join public.products p on p.id = (i ->> 'product_id')::integer;
  return new_id;
end;
$$;

它解決開場的兩件事：

  • 半張訂單：PostgREST 把每個請求包在一個交易裡，函式裡任何一步 raise exception 或違反約束，前面的 insert 全部回滾。前端從「三個請求」變成「一個請求」，不會停在中間。
  • 前端改價格：參數只收商品 id 與數量，單價與總價由函式從 products 讀。前端就算多送 unit_price，函式也不看。

raise exception 會變成 API 的錯誤回應：supabase-js 的 error.message 就是那段文字、error.code 是 SQLSTATE（沒指定時是 P0001）。用 errcode = '42501'（權限不足）時，PostgREST 會回 401 或 403，跟沒有 GRANT 的錯誤一樣。

函式以誰的身分執行

函式預設是 security invoker：以呼叫者的角色執行，裡面的 insert 照樣受 orders、order_items 的 GRANT 與 RLS 管。所以上面的函式能插入訂單，是因為第 4 課那條「顧客只能替自己下單」的 INSERT policy 允許；auth.uid() 也照常讀到呼叫者。這是首選：函式只是把幾個本來就允許的動作包成一個交易。

需要做到呼叫者自己沒權限的事（例如扣全店共用的庫存表），才改成 security definer，並照第 5 課的規則：放在不公開的 schema 或至少 set search_path = ''，函式裡自己檢查 auth.uid()，因為 RLS 已經不會替你擋了。

誰能呼叫：EXECUTE 權限

函式也有自己的 GRANT。這裡有個容易誤會的地方：第 3 課講過 2026 年起新表預設不開放給 API（本機 auto_expose_new_tables = false），但函式不在這個規則裡。在本機實測，postgres 在 public 新建的函式，has_function_privilege('anon', …, 'execute') 是 true：Postgres 對新函式的內建預設是 PUBLIC（所有角色）都能執行，所以沒登入的人也能 POST /rest/v1/rpc/place_order。每個要公開的函式都明確設定：

revoke execute on function public.place_order(jsonb) from public, anon;
grant execute on function public.place_order(jsonb) to authenticated;

上面的函式就算沒 revoke，anon 呼叫也會被 uid is null 擋下；但 security definer 的函式、或忘了檢查身分的函式，就會變成任何人都能呼叫的後門。把「只給該給的人執行」當成每個函式的固定兩行。

💡 實務上：金額一律在伺服器端算
任何跟錢有關的數字（單價、折扣、運費、總價）都不能信任前端送來的值，前端只送「要買什麼、買幾個、用哪張優惠券」，由 RPC 或後端從資料庫讀價格算出來。code review 看到 insert 的資料裡有前端傳來的 price、total，就是要修的 bug。同樣的道理也適用庫存、點數、會員等級。

Edge Functions：要離開資料庫的時候

RPC 解決了資料庫裡的事，但向金流扣款要呼叫外部 API、要用金流給的金鑰。資料庫函式不適合做 HTTP 呼叫（會把交易拖住，金鑰也得存在資料庫裡），前端又不能拿金鑰，這就是判斷表第三格：Edge Function。

Edge Function 是你寫的一段 TypeScript，跑在 Supabase 的 Edge Runtime 上。Edge Runtime 以 Deno 為基礎（另一個 JavaScript／TypeScript 執行環境，直接跑 .ts、內建 fetch、用 Deno.env.get 讀環境變數）。每個函式一個資料夾，網址是 /functions/v1/<名稱>：

npx supabase functions new checkout      # 建立 supabase/functions/checkout/index.ts
npx supabase functions serve             # 本機執行所有函式，改檔案會自動重新載入
npx supabase functions deploy checkout   # 部署到雲端（CLI 3.x：預設部署到 link 的專案）

一個函式就是一個處理 HTTP 請求的 handler：

import { createClient } from 'npm:@supabase/supabase-js@2'

Deno.serve(async (req) => {
  // 用「呼叫者自己的 token」建 client：之後的查詢都以這位顧客的身分執行，RLS 照常
  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!,
    JSON.parse(Deno.env.get('SUPABASE_PUBLISHABLE_KEYS')!).default,
    { global: { headers: { Authorization: req.headers.get('Authorization')! } } },
  )
  const { items } = await req.json()
  const { data: orderId, error } = await supabase.rpc('place_order', { items })
  if (error) return Response.json({ error: error.message }, { status: 400 })

  const { data: order } = await supabase.from('orders').select('total').eq('id', orderId).single()
  const charge = await fetch('https://api.payments.example/charges', {
    method: 'POST',
    headers: { Authorization: `Bearer ${Deno.env.get('PAYMENT_API_KEY')}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ order_id: orderId, amount: order!.total }),
  })
  if (!charge.ok) return Response.json({ error: '扣款失敗' }, { status: 502 })
  return Response.json({ order_id: orderId, total: order!.total, charge_id: (await charge.json()).id })
})

逐一看這段程式用到的設定：

  • 預設環境變數：Supabase 自動提供 SUPABASE_URL、SUPABASE_PUBLISHABLE_KEYS、SUPABASE_SECRET_KEYS（JSON，例如 {"default":"sb_publishable_…"}）、SUPABASE_DB_URL，以及舊的 SUPABASE_ANON_KEY、SUPABASE_SERVICE_ROLE_KEY（官方文件 guides/functions/secrets，2026-11-20 查詢）。
  • secrets：自己的金鑰（金流、寄信服務）本機寫在 supabase/functions/.env（加進 .gitignore），雲端用 npx supabase secrets set --env-file supabase/functions/.env 設定。程式裡一律 Deno.env.get，不寫死。
  • JWT 驗證：雲端與 functions serve 預設會先驗 Authorization 裡的 JWT，沒帶或無效直接回 401，不會執行你的程式。要給「別人打進來」的請求用（例如金流的 webhook，對方不會有你使用者的 JWT），在 config.toml 對那個函式關掉：[functions.payment-webhook] 下寫 verify_jwt = false，再自己驗簽章。
  • import：Deno 用 npm: 前綴直接載入 npm 套件，第一次執行時下載。

JWT 驗證只確認「token 是真的」。真正的權限還是靠程式裡用哪個身分查資料庫：

用哪個身分建 client結果什麼時候用
publishable key＋呼叫者的 Authorization以那位顧客的身分執行，RLS、auth.uid() 都照常預設。代替使用者做事的函式都用這個
secret key（service_role）繞過所有 RLS，auth.uid() 是 null真的需要跨使用者的管理工作：webhook 更新訂單狀態、後台批次作業。用的時候自己檢查權限

常見的錯是圖方便全部用 secret key：函式收到「替訂單 42 付款」的請求，用 secret key 查得到每一張訂單，於是顧客 A 傳別人的訂單編號也能操作。用呼叫者的 token，同樣的請求會因為 RLS 查不到而失敗。

💡 實務上：Edge Function 有時間與資源上限，長流程不要放這裡
官方文件（guides/functions/limits，2026-11-20 查詢）列的上限：記憶體 256 MB；每個請求的 CPU 時間 2 秒（等待網路的時間不算）；整體執行時間（wall clock）免費方案 150 秒、付費方案 400 秒；請求閒置 150 秒逾時。適合「收到請求、呼叫一兩個 API、回應」這種短流程。要跑幾分鐘的報表、要等外部系統回呼、要失敗後隔一段時間重試的流程，放進佇列交給背景工作（自己的後端），不要在 Edge Function 裡硬撐。

其他伺服器端工具，一段帶過

這幾樣別門課教過，在 Supabase 裡一樣能用，記得它們存在就好：

  • trigger：資料變動時自動執行的函式，例如自動更新 updated_at、第 6 課的 profiles（PostgreSQL 課第 23 課）。
  • pg_cron：資料庫裡的排程，例如每天凌晨清掉沒有訂單的收據檔案紀錄。pgmq：資料庫裡的訊息佇列。原理在 PostgreSQL 課第 33 課、NestJS 課第 21 課。
  • webhook：金流的付款通知打到一個 verify_jwt = false 的 Edge Function，函式驗簽章、用唯一約束做到同一個通知重送也只處理一次，再用 secret key 更新訂單狀態。簽章與冪等在 NestJS 課第 22 課、delivery 課第 8 課講過。

什麼時候改用自己的後端

最後一格。判斷表上的「自己的後端」不是失敗的選項，而是很常見的組合：Supabase 繼續管資料、登入、檔案，另外跑一個 NestJS 服務處理複雜流程，兩邊連同一個 Postgres（NestJS 用 SUPABASE_DB_URL 這類直連網址，或用 secret key 呼叫 API）。這叫混合架構。出現下面的訊號時考慮它：

  • 流程要跨好幾個系統（POS、發票、物流），每一步失敗都要重試、要能查進度。
  • 工作要跑很久，或要排程、要佇列。
  • 業務規則多到 SQL 函式難以閱讀與測試，而團隊熟悉 TypeScript 的測試工具。
  • 需要 Supabase 沒有的東西：特定的函式庫、長連線、自訂的快取層。

代價是多一個要部署、監控、維護的服務，權限也變成兩套：API 走 RLS，NestJS 直連資料庫時通常是高權限的角色，要在程式裡自己檢查（作品專案課的 第 9 課示範了在自己的後端裡也用 RLS 當第二道防線）。架構上的取捨在 system-design 課第 15 課。

💡 實務上：用一張表記下「這段邏輯為什麼放這裡」
專案長大後，同一類邏輯散在前端、RPC、Edge Function、後端四個地方，新同事很難找。團隊會在 README 或 ADR 寫一張表：哪些功能在哪裡、為什麼。審新功能時先對照判斷表決定放哪，並寫進那張表。出問題時也知道該去哪裡看 log：RPC 看 Postgres 的 log，Edge Function 看函式的 log。

練習

練習 1、2 在本機，題目資料夾是 supabase/practice/work/08/。這一題的 products、orders、order_items 在你專屬的 schema（policy 跟第 4 課一樣：顧客只能讀寫自己的訂單），SQL 照正式專案的寫法寫 public.，判分時測試會換成那個 schema。

練習 1：在 place_order.sql 寫 public.place_order(items jsonb) returns integer：沒登入就 raise exception；單價一律從 public.products 讀（前端多傳的 unit_price 不能用），有商品不存在就 raise exception；建一張屬於呼叫者的 orders（total 是總價）與每個 order_items，回傳訂單 id；最後設定只有 authenticated 能執行。測試會用顧客的身分透過 rpc() 呼叫，也會送不存在的商品、數量 0，確認失敗時一筆都沒留下。

練習 2：完成 Edge Function functions/checkout/index.ts：收到 POST { items }，用呼叫者的 Authorization 呼叫練習 1 的 place_order（失敗就把狀態碼原樣回傳、不扣款），再讀這張訂單的 total，用環境變數裡的金流金鑰向金流扣款（失敗回 502），回傳 { order_id, total, charge_id }。這一題沒有 supabase-js（容器不連外網下載套件），用 fetch 直接呼叫 /rest/v1/rpc/place_order 與 /rest/v1/orders，檔案開頭的註解列了可以用的環境變數與金流 API 的格式。測試會在你的函式與 Supabase 之間放一個記錄請求的 proxy，並開一個假的金流 API。

練習 3：寫 whereToPut(req)，依需求的特徵回傳邏輯該放哪裡。規則照「四個可以放邏輯的地方」那一節，由上往下，第一條符合的就是答案：

  1. 要跑 60 秒以上（seconds >= 60），或要排程與失敗重試（scheduledRetry）→ 'own-backend'
  2. 要呼叫外部 API、要用不能給前端的金鑰、或要接 webhook → 'edge-function'
  3. 要寫兩張以上的表而且要一起成功（tablesWritten >= 2 && atomic），或權限沒辦法直接寫成 RLS（!fitsRls）→ 'rpc'
  4. 其他 → 'data-api'

真實的需求不會剛好是幾個布林值，這張判斷表的價值在於逼你先問對問題：要不要離開資料庫、要不要一起成功、要跑多久。答案常常是組合：結帳的入口是 Edge Function，它呼叫 RPC 做交易，再把「寄收據信」丟進佇列給背景工作。

練習 4：前端的結帳寫成先 insert 訂單、拿到 id 後再 insert 品項，兩個請求都有 RLS 保護，而且都檢查了 error。為什麼還是不安全？

✓ PostgREST 每個請求一個交易，跨請求的「一起成功」只能靠把它們包進同一個函式。另一個問題是金額來自前端。修法是 place_order 這類 RPC。b 錯：INSERT 的 WITH CHECK 確實會擋，只是擋不住「半張訂單」和「自己改價格」這兩件事。

練習 5：Edge Function cancel-order 收到 { order_id } 後，用 secret key 建的 client 執行 update orders set status = 'cancelled' where id = order_id，函式有開 verify_jwt。哪裡會出事？

✓ verify_jwt 只確認「有一個真的使用者在呼叫」，沒確認「他能不能動這張訂單」。用呼叫者的 Authorization 建 client，RLS 就會擋；真的要用 secret key，就自己比對訂單的 customer_id 與 token 的 sub。b 是最常見的誤會：認證不等於授權。

練習 6：咖啡店要做「每晚 2 點跟 POS 系統對帳：拉一整天的交易、逐筆比對、有差異就建工單並通知店長，POS 偶爾會逾時要重試」。放哪裡比較合適？

✓ 長時間、跨系統、要重試，是判斷表上「自己的後端」的典型訊號。c 是最多人會選的：Edge Function 有整體執行時間與 CPU 時間上限，失敗重試也要自己另外做。b 讓資料庫去呼叫外部 API，一筆逾時就拖住交易。a 依賴有人打開頁面，而且金鑰會到前端。

常見錯誤

  • 前端連續發好幾個寫入當成一個流程：中間失敗會留下半套資料。要一起成功的寫入包成 RPC。
  • RPC 收前端傳的價格：參數只收 id 與數量，價格在函式裡從資料庫讀。
  • 以為新函式跟新表一樣預設不公開：函式預設 PUBLIC 可以執行。每個函式都 revoke execute … from public, anon 再 grant 給需要的角色。
  • security definer 函式沒自己檢查 auth.uid()：RLS 不會替它擋，等於給了呼叫者擁有者的權限。
  • Edge Function 一律用 secret key：繞過 RLS，任何人都能操作別人的資料。代替使用者做事時轉交呼叫者的 Authorization。
  • 金鑰寫死在程式碼或放進 VITE_ 變數：放 secrets（本機 supabase/functions/.env，雲端 supabase secrets set），用 Deno.env.get 讀。
  • webhook 的函式開著 verify_jwt：對方沒有你的使用者 JWT，每次都 401。關掉之後一定要自己驗簽章。
  • 把長流程塞進 Edge Function：有執行時間與 CPU 上限，失敗也沒有重試。改放背景工作。

小結

  • 邏輯可以放四個地方：Data API（單表、權限能寫成 RLS）→ RPC（多步驟寫入要一起成功、由資料庫算）→ Edge Function（外部 API、金鑰、webhook，短流程）→ 自己的後端（長流程、跨系統、排程與重試）。
  • RPC 是 POST /rest/v1/rpc/<函式>，一個請求一個交易；預設 security invoker，RLS 照套；definer 要照第 5 課的規則並自己檢查身分。
  • 新函式預設 PUBLIC 可執行（不受 auto_expose_new_tables 影響）：每個函式都 revoke 再 grant。
  • Edge Function 跑在 Deno 上，Deno.serve 處理請求；預設驗 JWT；金鑰放 secrets；代替使用者做事時用呼叫者的 Authorization 建 client，secret key 只給真正的管理工作。有記憶體、CPU、執行時間上限。
  • trigger、pg_cron、pgmq、webhook 在 Supabase 都能用；複雜流程用混合架構，多一個服務的代價要算進去。
