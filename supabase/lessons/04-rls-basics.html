階段 2：權限：Row Level Security · 第 4 課

RLS 實戰：auth.uid()、USING 與 WITH CHECK，以及 API 看到的結果

咖啡店的訂單明細頁網址是 /orders/6。顧客王小明好奇把 6 改成 7，看到了陳美華的訂單：買了什麼、什麼時候買的。前端程式明明只會用登入者自己的訂單編號，但 API 不管你的前端怎麼寫，它只看請求。這叫 IDOR（Insecure Direct Object Reference，直接用 id 存取到別人的物件），是 API 最常見的漏洞（認證課第 19 課的 BOLA 是同一件事）。

上一課的第一道門 GRANT 只能說「authenticated 能讀 orders」，分不出是哪個顧客。這一課寫第二道門：用 auth.uid() 寫 RLS，讓每個顧客只讀得到、只改得到自己的訂單，並看清楚每種寫法從 API 看是什麼結果。

這課的路線
  • 先修好 IDOR：一個擁有者 policy，以及它在 API 上的樣子。
  • USING 與 WITH CHECK：一個管「看得到哪些既有的列」，一個管「寫進去的新列」。
  • UPDATE 的兩個陷阱：把資料轉給別人、改了 0 列卻沒有錯誤。
  • 不用 API 也能測：在 SQL 裡模擬一個登入的請求。
  • 效能：policy 是加在每一列的條件，怎麼寫才快。
這課會用到：第 3 課的請求怎麼變成角色（帶使用者 JWT 的請求是 authenticated，auth.uid() 讀 JWT 的 sub）；兩道門（沒 GRANT 是 42501，RLS 沒放行時讀取是 []）；RLS 的語法（enable row level security、create policy … using … with check，PostgreSQL 課第 24 課，下一節有一段回顧）。
環境：這課用到資料庫、gateway、Data API、Auth（db、kong、rest、auth）。練習的測試會建兩個真的使用者 A、B，用他們登入後的 JWT 打 API，表建在你專屬的 schema。

先修好 IDOR：擁有者 policy

先回顧 RLS 的語法（PostgreSQL 課第 24 課有完整說明）：表開了 RLS 之後，每一列預設都看不到；每個 policy 說「對哪個動作、對哪些角色、哪些列可以」；同一個動作有好幾個 policy 時，任何一個放行就算放行（OR）。表的擁有者與有 BYPASSRLS 的角色（Supabase 的 postgres、service_role）不受 RLS 限制。

咖啡店的 orders 用 customer_id 記下單的人，存的是 Auth 使用者的 id（uuid）。修好 IDOR 只要一個 policy：

alter table orders enable row level security;

create policy "顧客讀自己的訂單" on orders
  for select                                   -- 管讀取
  to authenticated                             -- 只套用在登入的請求
  using (customer_id = (select auth.uid()));   -- 這一列的主人是發請求的人

grant select on orders to authenticated;

auth.uid() 是第 3 課看過的函式：讀這個請求 JWT 裡的 sub。所以同一句 SQL，王小明發的請求只會看到 customer_id 是王小明的列。(select auth.uid()) 外面那層 select 是效能寫法，最後一節解釋，先照寫。

從 API 看，王小明把網址改成陳美華的訂單時：

const { data, error } = await supabase.from('orders').select('id, total').eq('id', 7).maybeSingle()
// data → null，error → null

不是 403，也不是「你沒有權限」，而是查不到：對王小明來說，陳美華的那一列不存在。讀取被 RLS 擋下時一律是這樣，列表變成 []、單筆變成 null（用 single() 則是 PGRST116）。這對安全是好事（攻擊者分不出「沒有這張訂單」和「有但不是你的」），對除錯是陷阱：「資料不見了」的回報，常常是 policy 的條件不符合，而不是資料真的不在。

沒登入的請求呢？policy 寫了 to authenticated，對 anon 來說這張表沒有任何 policy，加上沒有 GRANT，回的是 42501。就算忘了寫 to authenticated（預設是 to public，也就是所有角色），未登入時 auth.uid() 是 NULL，customer_id = NULL 的結果是 NULL 而不是 true，一樣看不到。但明確寫 to authenticated 讓意圖清楚，Postgres 也能在 anon 的請求裡直接跳過這個 policy。舊的教學會寫 using (auth.role() = 'authenticated')，現在官方不建議用，改用 to authenticated。

「有登入」不等於「是主人」

最常見的錯誤 policy 長這樣：

create policy "登入的人讀訂單" on orders for select to authenticated using (true);

看起來有限制（只有登入的人），實際上任何一個註冊過的帳號都能讀所有人的訂單。開放註冊的 app 裡，「登入」不是門檻：攻擊者註冊一個帳號就過了。第 3 課說過所有登入的人共用 authenticated 一個角色，分辨是誰只能靠 auth.uid()。

💡 實務上：每張 public 的表都要回答四個問題
上線前或審 PR 時，對每張前端會碰到的表逐一問：(1) 開 RLS 了嗎；(2) 誰能讀哪幾列（擁有者？同團隊？所有人？）；(3) 誰能新增，新增時哪些欄位要被鎖住（例如 customer_id 只能是自己）；(4) 誰能改、能刪，改的時候能不能把資料變成別人的。答不出來的格子，就是還沒寫的 policy。這張表本身也是很好的文件，可以放進 PR 描述給審的人看。

USING 與 WITH CHECK

讀取只需要一個條件，寫入就有兩個問題要分開問：「你能動哪些既有的列」和「你寫進去的列合不合規矩」。這就是 policy 的兩個子句：

子句檢查的是不符合時 API 看到
USING既有的列：看得到、能被改、能被刪的是哪幾列那幾列像不存在一樣：讀取 []，改刪 0 列
WITH CHECK寫入後的新列：新增的列、改完之後的列錯誤 42501 new row violates row-level security policy

每個動作用到哪幾個：

  • SELECT、DELETE：只有既有的列，只寫 USING。
  • INSERT：只有新列，只寫 WITH CHECK。寫 USING 會直接報錯（only WITH CHECK expression allowed for INSERT）。
  • UPDATE：兩個都有。USING 決定能改哪幾列，WITH CHECK 決定改完的樣子合不合法。

新增訂單的 policy，重點是 customer_id 只能填自己：

create policy "顧客新增自己的訂單" on orders for insert to authenticated
  with check (customer_id = (select auth.uid()));

grant insert on orders to authenticated;

王小明送出 insert({ customer_id: 陳美華的 id, total: 1 }) 時，新列不符合 WITH CHECK，整個請求失敗、一列都不會寫入，error.code 是 42501。跟讀取不同，寫入被擋是明確的錯誤。另一種常見寫法是讓欄位預設值等於 auth.uid()（customer_id uuid not null default auth.uid()），前端就不用傳；但 WITH CHECK 仍然要寫，因為使用者還是可以自己帶 customer_id。

UPDATE 的兩個陷阱

INSERT 只有一個條件，UPDATE 的兩個條件各有一個陷阱。換一張表看比較清楚：商品評論 reviews(id, product_id, author_id, rating, body)，所有人都看得到全部評論，作者能改自己寫的：

create policy "評論公開可讀" on reviews for select to anon, authenticated using (true);

create policy "作者改自己的評論" on reviews for update to authenticated
  using (author_id = (select auth.uid()))
  with check (author_id = (select auth.uid()));

grant select on reviews to anon, authenticated;
grant update (rating, body) on reviews to authenticated;

陷阱 1：WITH CHECK 寫成 true，資料就能轉給別人。USING 只限制「能改哪幾列」，改成什麼樣子由 WITH CHECK 管。寫成 with check (true)，王小明就能對自己的負評送 update({ author_id: 陳美華的 id })，讓那則負評變成陳美華寫的；換成訂單、退款、積分紀錄也是同一個洞。兩個細節：

  • UPDATE policy 如果完全不寫 WITH CHECK，Postgres 會拿 USING 的條件當 WITH CHECK 用，所以只寫 USING 也擋得住；出事的是「寫了，但寫得比 USING 寬鬆」。明確寫出兩個條件，審的人才不用記這條規則。
  • UPDATE 用到 WHERE 時，改完的新列也要通過 SELECT policy。所以如果 orders 的 select policy 是「只看得到自己的」，把訂單轉給別人會因為「改完自己就看不到了」而失敗（42501）。評論的 select 是公開的，這層就幫不上忙。不要依賴這種巧合，WITH CHECK 照樣寫好。

上面還多了一層：grant update (rating, body) 只開放這兩欄。GRANT 可以細到欄位，作者只該改評分和內容，就只給這兩欄；這樣 RLS 寫錯時還有 GRANT 擋著，想改 author_id 直接是 42501。

陷阱 2：沒有 SELECT policy，update 改了 0 列，而且沒有錯誤。只寫了 update policy、沒寫 select policy 時，前端的 update({ body: '…' }).eq('id', 6) 回 HTTP 204，error 是 null，資料庫卻沒變。原因跟上面一樣：where id = 6 要讀那一列才能比對，UPDATE 用到 WHERE 時 SELECT 的 policy 也要通過；看不到的列，自然改不到。改不到不是錯誤，跟讀取一樣是「那一列不存在」。所以能改的，一定也要能讀。除錯時 update 沒反應，先接 .select() 看回傳幾列：[] 就是被 RLS 過濾掉了。

💡 實務上：「改了沒反應」先查三件事
前端回報「按儲存沒有錯誤，重新整理資料又變回來」，九成是 RLS：(1) update 接 .select()，看回傳是不是 []；(2) 有沒有 select policy、條件跟 update 的 USING 是否一致；(3) GRANT 有沒有包含要改的欄位（欄位層級的 GRANT 漏了會是 42501，比較好查）。在 PR 裡新增 update policy 時，順手確認同一張表的 select policy 也涵蓋那些列。

不用 API 也能測：在 SQL 裡模擬一個請求

每改一次 policy 就開前端點一次太慢。第 3 課說過 PostgREST 做的事就是兩行：切換角色、放 claims。自己在交易裡做一樣的事，就能在 SQL 裡扮演任何一個使用者。用課程容器裡的 psql 連進資料庫（或貼到 Studio 的 SQL Editor）：

docker exec -it supabase_db_learn-supabase psql -U postgres
begin;
set local role authenticated;
select set_config('request.jwt.claims', '{"sub":"6f1c2a4e-0b7d-4c2e-9a51-3d8e7f6a2b10","role":"authenticated"}', true);

select auth.uid(), current_user;   -- 6f1c2a4e-…、authenticated
select id, total from orders;      -- 只會看到這個使用者的訂單
rollback;
  • set local role 和 set_config(…, true) 的 local／true 都是「只到交易結束」：rollback 之後恢復成 postgres，不會影響之後的查詢。
  • claims 的 sub 換成另一個 uuid，就是另一個使用者；不 set_config 就是未登入（auth.uid() 是 NULL）。
  • 測試寫入時，在 rollback 前查一次結果，資料也不會真的留下。

第 5 課會把這個做法整理成一套 RLS 測試：每張表測「自己看得到、別人看不到、不能改成別人的」。

效能：policy 是加在每一列的條件

最後回到 (select auth.uid())。RLS 的 policy 等於 Postgres 自動在每個查詢加上 WHERE：顧客查 select * from orders，實際執行的是 select * from orders where customer_id = (select auth.uid())。所以有兩件事決定它快不快：

  • 函式只算一次：直接寫 customer_id = auth.uid()，Postgres 可能對每一列都呼叫一次 auth.uid()（它每次都要解析 claims 的 JSON）。包成 (select auth.uid())，它變成一個子查詢，整個查詢只算一次、結果重複使用。官方的 RLS 效能建議（docs: row-level-security#rls-performance-recommendations）實測在大表上差距很大。auth.jwt() 也一樣包。
  • 條件用到的欄位要有索引：customer_id 沒有索引，每次查詢都要掃過整張訂單表再過濾。create index on orders (customer_id)。索引怎麼運作在 PostgreSQL 課第 20 課。

前端查詢時也加上 .eq('customer_id', userId)：結果跟只靠 RLS 一樣，但查詢本身就帶著條件，Postgres 能更直接地用索引。RLS 是安全網，不是查詢條件的替代品。怎麼用 EXPLAIN 確認查詢真的用到索引，回顧 PostgreSQL 課第 21 課。

💡 實務上：RLS 讓查詢變慢時的檢查順序
上線一陣子後列表頁變慢，資料量一大 RLS 很常是原因。資深工程師會先看：policy 裡的函式有沒有包 (select …)；policy 條件的欄位有沒有索引；policy 裡有沒有對其他表的子查詢（第 5 課的多租戶寫法）、那張表的欄位有沒有索引。Supabase 的 Performance Advisor（npx supabase db advisors --type performance）會標出沒包 select 的 auth.uid()（auth_rls_initplan）與缺少的外鍵索引。

練習

練習 1、2 的測試會在你專屬的 schema 建 orders(id, customer_id uuid, total, note, ordered_at)，放 3 張訂單：使用者 A 兩張、B 一張，再套用你的 SQL。SQL 不要寫 public. 前綴。

練習 1：表還沒開 RLS、也沒有任何 GRANT。在 ex1.sql 讓登入的顧客只讀得到自己的訂單（A 讀不到 B 的、改網址的 id 也一樣），沒登入的人什麼都讀不到。policy 只給 authenticated、auth.uid() 包一層 (select …)，並替 policy 用到的欄位加索引。

練習 2：測試已經開好 RLS，也讓擁有者讀得到自己的訂單。在 ex2.sql 讓登入的顧客能新增自己的訂單（新增後能用 .select() 拿回那一列），但 A 送出 customer_id 是 B 的訂單時要被拒絕（42501），沒登入的人不能新增。

練習 3：這一題換成商品評論 reviews(id, product_id, author_id uuid, rating, body)，A 寫了兩則、B 一則；表已經開了 RLS，但沒有任何 policy、沒有任何 GRANT。在 ex3.sql 讓任何人（含沒登入）都讀得到所有評論；作者能改自己評論的 rating、body；改不到別人的評論（0 列）；也不能把自己的評論改成別人寫的（改 author_id 要失敗）。測試會直接查資料庫確認真的改了。

練習 4：顧客的訂單列表突然變成空的，API 沒有任何錯誤，data 是 []。資料庫裡確認有他的訂單。最可能的原因？

✓ RLS 擋下讀取時不是錯誤，是空結果：對這個請求來說那些列不存在。先確認請求帶了使用者的 JWT（沒帶就是 anon），再用 SQL 模擬那個使用者查一次。a 是第一道門，會是 42501 錯誤而不是 []。d 只管 UPDATE、DELETE。

練習 5：評論所有人都看得到，作者能改自己的評論。審 PR 時你該指出哪個問題？

create policy "評論公開可讀" on reviews for select to anon, authenticated using (true);
create policy "改自己的評論" on reviews for update to authenticated
  using (author_id = (select auth.uid()))
  with check (true);
grant update on reviews to authenticated;

✓ USING 決定能改哪幾列，WITH CHECK 決定改完的樣子；true 讓作者能冒名成任何人。改成跟 USING 一樣的作者條件，GRANT 也只給 update (rating, body)。d 是最多人會選的：只想到「改哪一列」，沒想到「改成什麼」。b 錯在 UPDATE 的 USING 本身就限制了能改哪幾列。

練習 6：同一個 policy 寫成 using (customer_id = (select auth.uid())) 比 using (customer_id = auth.uid()) 快，原因是？

✓ policy 等於加在每一列的條件；直接呼叫函式可能每一列算一次，包成 (select …) 後算一次、重複使用。結果完全一樣，只差在效能，表大時很明顯；policy 用到的欄位也要有索引。b 錯在 RLS 照樣檢查。c 錯在只在同一個查詢裡重用，不跨請求。

常見錯誤

  • using (true) 或只寫 to authenticated：有登入不等於是主人，任何註冊的人都看得到全部。要有擁有者條件 customer_id = (select auth.uid())。
  • INSERT 寫 USING：新增沒有既有的列，只能寫 WITH CHECK，寫 USING 會報錯。
  • WITH CHECK 寫成 true：USING 管得了改哪幾列，管不了改成什麼；擁有者能把資料轉給別人或冒名。不要依賴 select policy 剛好擋住。
  • 只寫 update policy、沒有 select policy：update 默默改了 0 列，沒有錯誤。能改的列一定要能讀。
  • 把空結果當成資料不存在：RLS 擋下讀取時是 []／null，不是錯誤。先用 SQL 模擬那個使用者查一次。
  • 用 auth.role() 判斷有沒有登入：已經不建議用，改寫 to authenticated。
  • auth.uid() 沒包 (select …)、policy 欄位沒索引：資料量大時每個查詢都慢。

小結

  • 擁有者 policy：for select to authenticated using (customer_id = (select auth.uid()))，配上 GRANT。未登入時 auth.uid() 是 NULL，比對結果不是 true，看不到。
  • 從 API 看：讀取被擋是 []／null（像那一列不存在），寫入被擋是 42501 new row violates row-level security policy。
  • USING 管既有的列（看得到、改得到、刪得到哪些），WITH CHECK 管寫入後的新列。INSERT 只有 WITH CHECK；UPDATE 兩個都有，WITH CHECK 不能比擁有者條件寬鬆（不寫時沿用 USING）。
  • UPDATE 要先看得到：用到 WHERE 時既有的列與改完的列都要通過 SELECT policy，沒有 SELECT policy 時改了 0 列、沒有錯誤。GRANT 可以細到欄位（grant update (rating, body)）。
  • 在交易裡 set local role authenticated＋set_config('request.jwt.claims', …, true)，就能在 SQL 裡扮演任何使用者測 policy。
  • policy 是加在每一列的條件：(select auth.uid()) 只算一次、條件欄位加索引、查詢也帶上 .eq('customer_id', …)。
