階段 3：Auth 與檔案 · 第 7 課

Storage：bucket、policy、signed URL 與上傳

咖啡店開放轉帳付款，顧客要上傳轉帳收據的截圖，店員核對後出餐。收據上有姓名、帳號末幾碼，只有顧客本人和店員能看。第一版上線時，工程師為了讓 <img> 直接顯示，把存檔的地方設成「公開」；一週後有人發現把網址裡的使用者 id 換掉，就能看到別人的收據。

這一課講 Supabase Storage：檔案放在哪、權限怎麼寫（答案還是 RLS，第 4、5 課學的寫法直接套用）、怎麼給前端一個會過期的下載網址，以及上傳時要擋什麼。

這課的路線
  • bucket 與檔案：檔案的資訊是 storage.objects 這張表的一列，先回答「權限寫在哪」。
  • 公開與不公開的 bucket：開場那個漏洞是怎麼發生的。
  • 寫 policy：路徑慣例、storage.foldername、上傳與覆蓋各要哪些 policy。
  • 給前端看檔案：signed URL 與 public URL。
  • 上傳的限制與大檔案：bucket 的大小、類型限制，以及圖片轉換、續傳的取捨。
這課會用到：RLS 的 USING 與 WITH CHECK（USING 決定哪些既有的列看得到、改得到，WITH CHECK 檢查寫入後的新列，第 4 課）；用 app_metadata 判斷角色（只有伺服器改得到，user_metadata 使用者自己改得到，第 5 課）；登入後的 client 會帶使用者的 access token（第 6 課）。
環境：這課用到資料庫、gateway、Data API、Auth 與 Storage（db、kong、rest、auth、storage），npm run up 預設都會開。Storage 的檔案實際存在 storage 容器的 volume 裡，npm run down 不會刪掉。

bucket 與檔案：權限寫在哪

Supabase Storage 用 bucket（桶）分組檔案，像是最上層的資料夾，每個 bucket 有自己的設定：公不公開、單檔大小上限、允許的檔案類型。bucket 裡的檔案用路徑命名，例如 receipts 這個 bucket 裡的 6205ef23-…/7.png。

上傳一個檔案時，Storage 做兩件事：把檔案內容存進儲存空間（本機是容器的磁碟，雲端是 S3 相容的物件儲存），再在資料庫的 storage.objects 表新增一列記錄它。看一下那一列：

select bucket_id, name, owner_id, metadata ->> 'mimetype' as type from storage.objects;
 bucket_id |                   name                   |               owner_id               |   type
-----------+------------------------------------------+--------------------------------------+-----------
 receipts  | 6205ef23-b33f-41c8-bc98-6c28481d6e44/7.png | 6205ef23-b33f-41c8-bc98-6c28481d6e44 | image/png

所以「誰能上傳、誰能下載、誰能刪」就是「誰能對 storage.objects 的哪些列做 INSERT、SELECT、DELETE」。Storage 服務收到請求時，用請求帶的 JWT 切換成 anon 或 authenticated 角色去操作這張表，RLS 決定結果，跟 PostgREST 一模一樣。storage.objects 已經開了 RLS、也已經 GRANT 給這些角色，你只要寫 policy；沒有任何 policy 時，除了 secret key（service_role）以外誰都不能上傳或讀取。

Storage 的動作（supabase-js）對 storage.objects 做的事要有的 policy
upload(path, file)INSERT 一列INSERT
upload(path, file, { upsert: true })檔案已經存在時是 UPDATE 那一列（還要先找到它）INSERT＋SELECT＋UPDATE
download、list、createSignedUrlSELECTSELECT
removeDELETE（要先看得到）SELECT＋DELETE
move、copyUPDATE／INSERT依動作

（查表用，不用背。）本機實測：只有 INSERT policy 時，第一次上傳成功，同一個路徑再 upsert 會得到 403「new row violates row-level security policy」；補上 SELECT 還是一樣，要 SELECT、UPDATE 都有才成功。

直接 delete from storage.objects 會被擋下（「Direct deletion from storage tables is not allowed. Use the Storage API instead.」）：只刪資料庫的列，儲存空間裡的檔案會變成沒人管的孤兒。刪檔一律走 Storage API。

公開與不公開的 bucket

知道權限在 storage.objects 之後，回到開場的漏洞。bucket 有一個 public 設定：

  • public bucket：任何人只要知道網址，就能用 /storage/v1/object/public/<bucket>/<路徑> 下載，讀取不經過 policy（上傳、刪除仍然要 policy）。本機實測，public bucket 裡別的顧客用 download() 也讀得到檔案。適合商品照片、店家 logo 這類本來就公開的東西，可以被瀏覽器和 CDN 快取。
  • private bucket（預設）：每次讀取都要過 SELECT policy；前端要顯示時，用下面會講的 signed URL。

開場的收據放在 public bucket，網址又是「使用者 id／訂單編號」這種猜得到的格式，所以換個 id 就看到別人的收據。收據、證件、合約這類私人檔案一律放 private bucket。

建 bucket 可以在 Studio 按按鈕，也可以寫成 SQL 放進 migration（第 9 課），團隊每個人的環境才會一樣：

insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values ('receipts', 'receipts', false, 2097152, array['image/png', 'image/jpeg']);
💡 實務上：一個 bucket 一種存取規則
常見的切法是依「誰看得到」分 bucket，而不是依功能：public-assets（商品圖，public）、receipts（顧客本人＋店員）、exports（後台匯出的報表，只有管理員）。同一個 bucket 裡混放公開與私人檔案，policy 會越寫越複雜，也很難一眼看出哪些東西是公開的。資安審查時，先列出每個 bucket 的 public 設定，public 的逐一確認裡面沒有私人資料。

寫 policy：路徑就是權限的依據

private bucket 的權限全靠 policy，而 policy 能用的資訊主要是 bucket_id 與 name（路徑）。所以 Supabase 的慣例是讓路徑的第一層資料夾等於擁有者的 user id：顧客 A 的收據放 <A 的 id>/7.png。storage.foldername(name) 把路徑切成資料夾陣列（Postgres 的陣列從 1 開始數），[1] 就是第一層：

select storage.foldername('6205ef23-b33f-41c8-bc98-6c28481d6e44/2026/7.png');
-- {6205ef23-b33f-41c8-bc98-6c28481d6e44,2026}

顧客的三條 policy：

create policy "收據：顧客上傳到自己的資料夾" on storage.objects for insert to authenticated
  with check (bucket_id = 'receipts' and (storage.foldername(name))[1] = (select auth.uid())::text);

create policy "收據：顧客讀自己的" on storage.objects for select to authenticated
  using (bucket_id = 'receipts' and (storage.foldername(name))[1] = (select auth.uid())::text);

create policy "收據：顧客覆蓋自己的" on storage.objects for update to authenticated
  using (bucket_id = 'receipts' and (storage.foldername(name))[1] = (select auth.uid())::text)
  with check (bucket_id = 'receipts' and (storage.foldername(name))[1] = (select auth.uid())::text);
  • bucket_id = 'receipts' 每一條都要寫：storage.objects 是所有 bucket 共用的一張表，漏寫就變成「所有 bucket 裡，路徑第一層是自己 id 的檔案」都適用。
  • auth.uid() 轉成 text：路徑是字串，auth.uid() 是 uuid。包一層 (select …) 讓它只算一次（第 4 課）。
  • INSERT 的 WITH CHECK 一定要檢查路徑：只寫 bucket_id = 'receipts' 的話，顧客 B 可以上傳檔案到 A 的資料夾，A 的收據列表就多了一張別人塞進來的圖。

店員要看全部收據，角色照第 5 課的規則放在 app_metadata：

create policy "收據：店員讀全部" on storage.objects for select to authenticated
  using (bucket_id = 'receipts' and ((select auth.jwt()) -> 'app_metadata' ->> 'role') = 'staff');

多條 SELECT policy 是 OR：顧客讀得到自己的，店員讀得到全部。店員沒有 INSERT、UPDATE policy，所以不能替顧客上傳或改檔。要做「店員只看自己分店的收據」，路徑改成 <store_id>/<user_id>/檔名，policy 用第 5 課的 store_members 查詢判斷第一層。

owner_id 欄位記錄上傳者，也可以拿來寫 policy（owner_id = (select auth.uid())::text）。差別是它跟著「誰上傳」走：店員代顧客上傳時，擁有者就變成店員。用路徑表達擁有者，規則看路徑就懂。

💡 實務上：路徑設計在第一天就決定了權限
路徑格式一旦有幾萬個檔案就很難改（搬檔要逐一 move，policy 和程式要同時換）。開新功能時先問：這些檔案誰能看？以後會不會多一種角色（店員、分店、會計）？把那個維度放進路徑的前幾層。檔名本身用伺服器或程式產生（訂單編號、uuid），不要用顧客上傳時的原始檔名：可能重複、可能有奇怪字元，也會洩漏資訊（「王小明身分證正面.jpg」），原因在 NestJS 課第 22 課講過。

給前端看檔案：signed URL

policy 寫好了，接著是前端怎麼顯示 private bucket 裡的圖。<img src> 發出的請求不會帶 Authorization header，所以不能直接指向 Storage 的一般網址。做法是產生 signed URL（簽過名的網址）：

const { data, error } = await supabase.storage.from('receipts').createSignedUrl(`${userId}/7.png`, 60)
// data.signedUrl：
// http://127.0.0.1:55421/storage/v1/object/sign/receipts/6205ef23-…/7.png?token=eyJhbGciOiJIUzI1NiJ9.eyJ1cmwiOi…

token 是 Storage 簽的 JWT，內容寫著哪個檔案、何時到期（第二個參數是秒數）。產生網址時要通過 SELECT policy；之後任何拿到網址的人在到期前都能下載，不用登入。所以：

  • 有效期取「畫面需要多久」：預覽圖 60 秒、後台列表幾分鐘。過期後重新產生。
  • signed URL 不要存進資料庫或寫進 log、不要放進會被分享的頁面網址。資料庫存的是路徑，要顯示時才換成 signed URL。
  • 網址過期後，已經下載到瀏覽器（或被別人存下來）的檔案不會消失。過期只擋「之後再用這個網址下載」。
  • 一次要很多張（店員的收據列表）用 createSignedUrls(paths, 秒數)，一個請求換回全部，不要每張各發一次。

getPublicUrl(path) 只是在本機組出 public bucket 的網址字串，不發請求、也不檢查權限；對 private bucket 用它，拿到的網址下載會失敗（本機實測回 400）。

這跟 S3 的 presigned URL 是同一個概念（data-stores 課第 12 課）：權限在產生網址時檢查一次，網址本身就是一張有期限的通行證。

上傳的限制與大檔案

最後看上傳這一端。檔案是前端直接傳給 Storage 的，中間沒有你的伺服器，所以「單檔多大、什麼類型」要設在 bucket 上，由 Storage 擋：

  • file_size_limit：單檔上限（bytes）。還受整個專案的上限限制（本機 config.toml 的 [storage] file_size_limit = "50MiB"）。
  • allowed_mime_types：允許的類型，例如 {image/png,image/jpeg}。本機實測上傳 text/plain 得到「mime type text/plain is not supported」。

要注意 mime type 是上傳的人宣告的（contentType），不是 Storage 讀檔頭判斷的。它擋得住「不小心傳錯檔」和把 HTML 檔放進來被當成網頁打開，擋不住刻意偽裝。收據要做到「真的是圖片」，要在伺服器端（Edge Function，第 8 課）讀檔頭檢查，原理在 NestJS 課第 22 課。

另外兩件事一句帶過：大檔案（影片、幾百 MB 的備份）用可續傳上傳（resumable upload，TUS 協定），斷線後從中斷處繼續；圖片縮圖與轉檔（image transformation）是雲端付費方案的功能，課程本機排除了負責它的 imgproxy 服務。

💡 實務上：上傳流程要想清楚「失敗一半」
顧客上傳收據通常是兩步：檔案上傳到 Storage、再把路徑寫進訂單。第二步失敗，就留下沒人用的檔案；先寫訂單再上傳失敗，訂單指向不存在的檔案。常見做法是路徑由訂單編號決定（<user_id>/<order_id>.png），重傳就 upsert 覆蓋，不需要另外記路徑；再搭配定期清理「沒有對應訂單的檔案」的排程（第 8 課帶過的 pg_cron）。

練習

練習都在本機，題目資料夾是 supabase/practice/work/07/。Storage 的 bucket 與 policy 是整個 Supabase 共用的，所以判分時測試會把你寫的 'receipts' 換成這一題專屬的 bucket 名稱、在 policy 名稱前面加上這一題的代號，跑完再刪掉；練習 2、3 的函式收到的 bucket 參數就是那個名稱。

練習 1：在 receipts.sql 建收據的 bucket 與 policy：bucket receipts 不公開、單檔最大 2 MB（2097152 bytes）、只收 image/png 與 image/jpeg；顧客只能在自己的資料夾（路徑第一層是自己的 user id）上傳、讀取、用 upsert 覆蓋；店員（app_metadata 的 role 是 staff）讀得到全部但不能上傳。測試會用顧客 A、顧客 B（他在自己改得到的 user_metadata 寫了 role: staff）、店員與沒登入的人逐一嘗試。

練習 2：完成 uploadReceipt(client, bucket, userId, orderId, image)：上傳到 <userId>/<orderId>.png（contentType 是 image/png，同一張訂單重傳要覆蓋舊檔），回傳 60 秒內有效的下載網址；任何一步出錯都丟出 Error。這一題的 bucket 不公開，測試會用你回傳的網址真的下載一次。

練習 3：完成店員後台用的 receiptLinks(client, bucket, customerId)：列出這位顧客資料夾裡的收據（依檔名排序），一次替全部產生 300 秒有效的下載網址，回傳 [{ name, url }]（name 是檔名，不含資料夾）。測試會數你發了幾個請求，也會用一般顧客的身分呼叫，確認 RLS 一樣管得到列檔案。

練習 4：顧客上傳收據時，第一次成功，同一張訂單重傳（upsert: true）卻得到 403「new row violates row-level security policy」。bucket 上只有一條 INSERT policy。缺了什麼？

✓ 檔案已經存在時，upsert 對 storage.objects 做的是 UPDATE，要先看得到（SELECT）、再改得到（UPDATE）。本機實測只補 SELECT 還是 403。b 是最常見的猜測，但覆蓋不經過 DELETE。a 會讓任何人上傳到任何路徑。d 讓所有人讀得到收據，跟這個錯誤無關。

練習 5：商品照片放在 public bucket menu-images，上面有一條 SELECT policy「只有店員看得到」。沒登入的訪客打開 /storage/v1/object/public/menu-images/latte.jpg，結果是？

✓ public bucket 用 public 網址讀取時不檢查 policy，任何知道網址的人都能下載。b 是最多人以為的：寫了 policy 就有保護，但對 public bucket 的讀取沒有作用。c 是 signed URL 的行為。要「只有店員看得到」，bucket 就要設成不公開。

練習 6：店員在後台打開顧客的收據，系統給了一個 5 分鐘的 signed URL。店員把圖片下載到自己的電腦，10 分鐘後網址過期。接下來？

✓ signed URL 的期限只管「用這個網址下載」；檔案一旦到了別人手上就收不回來。所以有效期要短，私人檔案也要想清楚誰需要拿到網址。b 錯在產生網址之後下載時就不再看 policy，過期就是過期，跟店員的權限無關。

常見錯誤

  • 私人檔案放 public bucket：讀取不經過 policy，知道網址就能下載。收據、證件放 private bucket，顯示用 signed URL。
  • policy 漏寫 bucket_id：storage.objects 是所有 bucket 共用的表，條件會套到別的 bucket。
  • INSERT 只檢查 bucket、沒檢查路徑：別人可以把檔案放進你的資料夾。WITH CHECK 要比對 (storage.foldername(name))[1]。
  • 只寫 INSERT policy 就用 upsert：重傳會 403。upsert 要 INSERT＋SELECT＋UPDATE。
  • 用 user_metadata 判斷店員：使用者自己改得到，用 app_metadata。
  • 把 signed URL 存進資料庫：過期後就壞了，而且外洩時誰都能下載。存路徑，要用時再產生。
  • 以為 allowed_mime_types 會檢查檔案內容：它只看上傳時宣告的類型。真的要確認內容，伺服器端讀檔頭。

小結

  • 檔案用 bucket 分組；每個檔案是 storage.objects 的一列，Storage 用請求的角色操作這張表，權限就是它的 RLS policy。刪檔走 Storage API，不能直接刪表。
  • public bucket 的讀取不經過 policy，只放本來就公開的東西；私人檔案放 private bucket。
  • 路徑第一層放擁有者的 user id，policy 用 (storage.foldername(name))[1] = (select auth.uid())::text，每條都寫 bucket_id。上傳要 INSERT，upsert 再加 SELECT＋UPDATE，讀取、列檔、產生網址要 SELECT。角色用 app_metadata。
  • 前端顯示私人檔案用 signed URL：產生時檢查 SELECT policy，之後到期前誰拿到都能下載；有效期取最短夠用的，資料庫只存路徑；多個檔案用 createSignedUrls。
  • bucket 設 file_size_limit 與 allowed_mime_types；mime type 是宣告的，不是檔頭。大檔用可續傳上傳，圖片轉換是雲端付費功能。

階段檢核：面試會問的觀念

這個階段一定要講得出來的 6 件事。先在心裡回答，再選。

練習 7：咖啡店的 Vue 前端在每個元件裡各自 createClient(url, key)，再把登入時存下來的 access token 放進 global.headers。客服回報顧客放著分頁一小時後，每個操作都 401。原因是？

✓ access token 預設 3600 秒過期，換新是持有 session 的那個 client 的工作。修法是整個 app 共用一個 client，讓它自動換新，或每次從 getSession() 取最新的 token。a 最常見：publishable key 不會過期，它只代表哪個 app。（第 6 課）

練習 8：Nuxt 的 server/api/orders/[id].delete.ts 這樣判斷能不能取消訂單。哪裡會出事？

const supabase = createServerClient(url, key, { cookies: { getAll: () => parseCookieHeader(cookieHeader) } })
const { data } = await supabase.auth.getSession()
if (data.session?.user.id !== order.customer_id) throw createError({ statusCode: 403 })
await admin.from('orders').delete().eq('id', order.id)   // admin 用 secret key

✓ cookie 的內容使用者改得到，getSession() 只是讀出來；後面又用 secret key 刪除，RLS 也幫不上忙。改用 getClaims()（本地驗簽章）或 getUser()（問 Auth）。b 剛好說反了：getSession() 不發請求，getUser() 才會。（第 6 課）

練習 9：上線後所有人都註冊失敗，前端只看到「Database error saving new user」。前一天剛部署了 profiles 表加 phone text not null 欄位的 migration。最先查什麼？

✓ profiles 的 trigger 跟註冊在同一個交易，它失敗註冊就失敗，而這個錯誤訊息正是 trigger 出錯的典型樣子。修法是欄位給預設值或允許 null，並在 trigger 裡處理。去 Postgres 的 log 看實際的錯誤。b、d 的錯誤訊息不同，c 會讓所有 API 都失敗、不只註冊。（第 6 課）

練習 10：咖啡店要讓顧客上傳大頭貼。下面哪個做法同時做到「大家看得到大頭貼」與「只有本人能換自己的大頭貼」？

✓ 大頭貼本來就公開，用 public bucket 讓瀏覽器與 CDN 快取；上傳與覆蓋仍然要 policy 檢查路徑。b 最常見的誤會：public 只開放讀取，沒有 policy 時誰都不能上傳。a 的 getPublicUrl 對 private bucket 下載不到。c 把 secret key 拿去做前端該做的事，也沒有必要。（第 7 課）

練習 11：顧客 B 的收據列表裡出現一張不是他上傳的圖。檢查 storage.objects 發現 owner_id 是顧客 C、路徑卻在 B 的資料夾。policy 最可能哪裡寫錯？

create policy "上傳" on storage.objects for insert to authenticated
  with check (bucket_id = 'receipts');
create policy "讀自己的" on storage.objects for select to authenticated
  using (bucket_id = 'receipts' and (storage.foldername(name))[1] = (select auth.uid())::text);

✓ 讀取有檢查路徑，所以 B 只看得到自己資料夾的檔案；但上傳沒檢查，C 能把檔案寫進 B 的資料夾，B 就看到了。修法是 INSERT 的 WITH CHECK 也比對 (storage.foldername(name))[1]。a 只改了讀取的判斷，C 仍然能把檔案塞進 B 的資料夾。（第 7 課）

練習 12：店員後台的收據列表，工程師為了「不用每次都產生網址」，把 7 天有效的 signed URL 存進 orders.receipt_url。這樣做的問題是？

✓ 權限只在產生網址時檢查一次，之後任何拿到網址的人都能下載。資料庫只存路徑，要顯示時用 createSignedUrls 換成短效網址。b 是最多人以為的：下載時不再看身分。（第 7 課）
