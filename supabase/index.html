Supabase：用 Postgres 當後端

咖啡店想做線上點餐：顧客登入點餐、店員即時看到新單、上傳付款收據、接金流的付款通知。前端你會寫，但後端要有資料庫、API、登入、檔案、即時推播、權限，自己從零寫要好幾個月。Supabase 把這些做成圍著一個 PostgreSQL 的一組服務：表建好就有 API，登入、檔案、即時通知都有現成的。很多新創與內部工具用它，面試也常被問「Supabase 的權限怎麼做」「publishable key 放前端安全嗎」。它省掉的是樣板程式，省不掉的是權限設計：前端直接連資料庫的 API，誰能看哪一列，全靠你寫在資料庫裡的規則。

這是一門選修課，只教 Supabase 獨有的兩件事：一是「PostgREST＋RLS 當後端」的設計方式，前端直接打自動產生的 API，權限全部寫在資料庫；二是判斷什麼時候該用 BaaS、什麼時候要搭配或改回自己的後端。課程在你的 Mac 上跑整套本機 Supabase，依序學自動產生的 API 與 supabase-js、API key 與資料庫角色、Row Level Security（列層級的權限規則，這門課的核心）、Auth 與伺服器端 session、Storage，再到「伺服器端邏輯放 RPC 還是 Edge Function」。期末把點餐功能寫成 migration、修好幾個被故意埋進去的權限漏洞，最後寫一份「要不要繼續用 Supabase」的決策紀錄。別門課教過的東西（RLS 語法、OAuth 與 MFA、trigger 與排程、付款 webhook）不重教，用到時一句回顧並連到原課。

練習在你自己的電腦上做：你寫 SQL（建表、GRANT、policy）與 TypeScript（supabase-js、fetch），執行 node check.mjs supabase <題號>，測試會把你的 SQL 套進一個只屬於這一題的 schema，再用真的使用者 token 從 API 打打看，確認該看到的看得到、不該看到的看不到。少數純邏輯的題目（解讀 JWT 的角色、判斷 key）在頁面裡用 TypeScript 完成。每課有 3 題選擇題針對常見誤解。先備：會 JavaScript／TypeScript 與 fetch；需要 Docker Desktop（記憶體建議 6 GB 以上），本機 Supabase 閒置時約佔 1.3 GB；不需要 Supabase 帳號，也不會產生任何費用。
